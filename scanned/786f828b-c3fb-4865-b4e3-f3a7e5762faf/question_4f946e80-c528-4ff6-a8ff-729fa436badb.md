In http.rs, decode_http_request enforces MAX_HTTP_HEADERS = 32 and MAX_HTTP_HEADER_LEN = 4096 per header value, but places no bound on the number of times headers.insert is attempted relative to req.headers.len() returned by httparse before the duplicate-key Err is raised, nor a bound on cumulative header bytes vs body_offset. Can a remote HTTP client send a request with headers whose combined raw byte length (not per-value) is crafted so body_offset returned by httparse points past the actual payload length, and decode_http_body(&headers, &buf[body_offset..]) is later invoked with buf[body_offset..] panicking on out-of-bounds slicing? Preconditions: attacker opens a TCP connection to any endpoint that calls decode_http_request (e.g., a signer's own outbound RPC parsing path when acting as a client, or a StackerDBSession consumer). Call sequence: decode_http_request -> httparse::Request::parse returns Complete(body_offset) -> caller later slices &buf[body_offset..]. Equality/fault: named panic site - body_offset (attacker-controlled via httparse's own successful parse) must be <= buf.len(); if httparse can return a body_offset equal to payload length exactly but a caller assumes more bytes follow, slicing &buf[body_offset..] on a shorter subsequent buffer causes an index-out-of-bounds panic. Impact: Critical, single-message remote panic in the shared HTTP decode path. Proof idea: unit test calling decode_http_request on a minimal payload (headers only, no body) then reproducing the caller pattern buf[body_offset..] on a buffer shorter than body_offset to confirm/deny the panic.
