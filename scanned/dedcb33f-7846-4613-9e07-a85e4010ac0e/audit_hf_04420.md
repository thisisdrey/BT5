# [H] H-03 | Crucial Storage Overwritten On configureDependencies

## Summary
Severity: High
Contest weight: 0.0857
Dataset id: 21896
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability consists of an unrestricted function that reinitialises three critical storage variables governing the contract's timing logic. The function, intended to be called only once during deployment to set initial values for the sweep interval, slide interval, and the timestamp of the last drop, lacks any form of access control such as an onlyOwner modifier. Because there is no guard, any external account can invoke the function again at any time, overwriting the previously stored values. This root cause is a missing permission check combined with an unconditional assignment of state variables that should be immutable after initialisation. An attacker can exploit the flaw by simply calling the function with arbitrary parameters, thereby resetting the sweepTick, slideTick and lastDropTimestamp to their defaults or to attacker‑chosen values. The immediate impact is a disruption of the protocol’s scheduled operations: sweeps that move funds, slide calculations that adjust balances, and timestamp‑based checks all rely on these variables. When they are reset, users may experience missing rewards, delayed fund releases, or complete stagnation of the contract’s accounting cycle. The bug manifests whenever the function is called after the initial deployment, which can happen at any block because no role or time restriction is enforced. All participants who rely on the contract’s timing – token holders, liquidity providers, or any party expecting periodic payouts – are affected because the contract no longer behaves according to its documented business logic. The issue was discovered during a manual audit when the reviewer observed that configureDependencies performed state writes without any modifier and that the same variables were also used later in time‑sensitive functions. It can be hard to notice in routine testing because the function may be exercised only once in a typical deployment scenario, and the erroneous behaviour only appears later when the overwritten timestamps cause scheduled actions to fail or behave unexpectedly. To remediate, the contract should either restrict configureDependencies to a trusted role or make the assignments conditional on a one‑time initialisation flag, ensuring that subsequent calls cannot alter the critical timing parameters. In broader terms, this is an instance of an unauthorized state variable overwrite, a class of bugs where missing access control allows an attacker to corrupt essential protocol state, leading to logical failures and potential loss of expected funds.

## Recommendation
Consider only assigning these values on the first call to configureDependencies, and if necessary include a separate trusted function to re-assign the values.
