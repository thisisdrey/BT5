Can an attacker whose `DepositMessage.action == DepositAction::Notify(NotifyOnTransfer{state_init: Some(...)})` get `ft_on_transfer` to deploy their contract via NEP-616 `state_init`, have that contract's `mt_on_transfer` call back into `ft_withdraw` on the same signer's freshly-deposited balance before `ft_resolve_deposit` runs, so that the same NEP-141 deposit is both refunded via the resolve callback AND withdrawn via `ft_withdraw`, netting more assets out of the Verifier than were deposited? Preconditions: attacker controls an FT contract and calls `ft_transfer_call` to the Verifier with msg = DepositMessage{receiver_id: attacker_derived_account, action: Notify(NotifyOnTransfer{state_init: Some(state_init), msg})}. Call sequence: ft_on_transfer -> self.deposit credits attacker_derived_account with amount -> DepositAction::Notify branch -> notify_on_transfer creates promise with state_init deploying attacker's contract -> mt_on_transfer on attacker's just-deployed contract calls ft_withdraw(attacker_derived_account's public key, same token, same amount) directly (attacker enabled auth_by_predecessor_id for that derived account beforehand) -> ft_resolve_deposit later runs resolve_deposit_internal reading the (now zero, already withdrawn) balance and computing refund based on stale expectations. Binding: value debited (=amount originally transferred in) should equal value delivered (kept by receiver) + value re-credited by resolver; but the resolver's refund_amount is computed against balance_left which has since been drained by the reentrant ft_withdraw, so the ledger ends up owing the fungible token issuer more than the Verifier custodies for token T. Impact: Critical, ledger conservation violated / assets owed exceed assets custodied. Proof idea: near-workspaces test asserting Verifier's real held FT balance (as seen by the underlying FT contract) matches sum of all Nep141TokenId(T) mt_balance_of entries after the sequence; expect mismatch showing more owed than held.
