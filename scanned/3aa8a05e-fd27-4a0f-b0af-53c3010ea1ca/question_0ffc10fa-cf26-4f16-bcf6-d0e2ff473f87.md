Can an attacker deploy a receiver contract named in a `Transfer` intent's `NotifyOnTransfer.contract_id`-equivalent (`receiver_id`) that, in its `mt_on_transfer`, returns a `PromiseOrValue::Promise` chaining to `ext_intents::execute_intents` with a payload that withdraws the *sender's* funds using a stolen/replayed nonce, exploiting the window between `internal_add_balance(receiver_id, tokens)` (already committed synchronously) and `mt_resolve_transfer`'s refund computation (still pending), to make the sender pay for a transfer intent it never separately authorised beyond the original Transfer? Preconditions: sender signs one DefuseIntents{Transfer{receiver_id: attacker, tokens: {T:A}, notification: Some(NotifyOnTransfer{msg})}}; the attacker's mt_on_transfer msg is crafted to trigger `MTReceiverMode::ExecuteAndRefund` style behavior (as seen in the receiver stub) that calls `ext_intents::execute_intents(vec![some_other_signed_payload])` against the *same signer's* other pending nonce before returning its own refund amount, effectively getting two settlements (the original Transfer's delivery to attacker AND a second one triggered from inside the notify) for the price of one authorised message if the second payload's nonce/signature was captured off-chain (e.g. leaked via an earlier failed broadcast) - but note nonce reuse is blocked by `commit_nonce`; the real question is whether the *timing* of when nonce is committed (synchronously, before any promise fires, per Engine::execute_signed_intent) closes this, or whether a batch of independently-signed multi-payloads submitted in the *same* `execute_intents(Vec<MultiPayload>)` call can have intent B's nonce committed and executed only if intent A's reentrant callee inside its own on_transfer notify manages to submit intent B concurrently causing a race on the nonce bitmap. Binding: the number of times any one signed MultiPayload settles == 1, forever, regardless of how many promises are outstanding when a later entry in the same execute_intents Vec is processed. Impact: Critical, one signature settling more than once. Proof idea: near-workspaces test submitting execute_intents([payload_A_with_notify_reentry, payload_B]) where payload_A's receiver's mt_on_transfer tries to call execute_intents([payload_B]) again reentrantly while the outer loop is also about to process payload_B synchronously later in the same call - since NEAR promises are always async (never re-executed synchronously within the same receipt), assert payload_B's nonce ends up committed exactly once and its second reentrant attempt fails with NonceUsed.
