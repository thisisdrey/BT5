Can an unprivileged signer whose AuthCall.contract_id points to a contract they wrote, deployed via `state_init` (NEP-616) in the same receipt as `AuthCall::execute_intent`, call back into `execute_intents` on the same Verifier from inside `on_auth()` before the outer receipt's promises settle, spending the signer's balance that the outer `DefuseIntents` batch already committed to move? Preconditions: signer has balance B of token T, signs a `DefuseIntents` with [Transfer{T,B}, AuthCall{contract_id: attacker_derived_account, state_init: Some(...), msg}], attacker's on_auth() calls `ext_intents::execute_intents` with a second signed payload from the same signer transferring the same balance B again. Call sequence: Engine::execute_signed_intent debits T from signer for the Transfer intent (synchronous state change) -> AuthCall::execute_intent -> Contract::auth_call -> do_auth_call creates promise to attacker contract -> attacker's on_auth re-enters execute_intents with a *different* signed nonce moving the *already-committed* balance again before Engine::finalize's conservation check for the first receipt has any bearing on the second. Binding: sum of token_balances[T] deltas across both receipts == 0 fails; the signer's balance is debited twice for one deposited amount. Impact: Critical, tokens moved without owner authorisation, signer or downstream victim loses funds. Proof idea: near-workspaces sandbox test with a stub contract implementing AuthCallee::on_auth that itself calls execute_intents with a pre-signed payload, assert mt_balance_of ends up negative-equivalent (underflow prevented) or that the second transfer succeeds using balance the first Transfer already zeroed out, via a TOCTOU where the attacker's contract deposits into itself between the sub and the notify.
