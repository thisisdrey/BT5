### Title
`claim_rewards` permanently reverts for Snowbridge relayer rewards because `BeneficiaryOf` derived from the caller is always `LocalAccount`, which `BridgeRewardPayer` rejects for `BridgeReward::Snowbridge` - ([File: cumulus/parachains/runtimes/bridge-hubs/bridge-hub-westend/src/bridge_common_config.rs])

### Summary
This is the closest local analog to the `Gauge.votingReward` bug: a reward-payout code path that is wired up but structurally guaranteed to revert for a whole class of legitimate callers, because the beneficiary type produced by the "default" entry point can never satisfy the payment procedure's requirements for that reward kind.

### Finding Description
`pallet-bridge-relayers` exposes two claim entry points: `claim_rewards` (pays to the caller, via a `Beneficiary` derived automatically from the signer) and `claim_rewards_to` (pays to an explicit `beneficiary` parameter) [1](#0-0) . On BridgeHub Westend, `BridgeRewardBeneficiaries` has two variants, `LocalAccount` and `AssetHubLocation`, and `From<sp_runtime::AccountId32> for BridgeRewardBeneficiaries` always maps a bare relayer `AccountId` to `LocalAccount` [2](#0-1) .

`BridgeRewardPayer::pay_reward` explicitly rejects the `LocalAccount` beneficiary whenever `reward_kind == BridgeReward::Snowbridge`, returning `Err("LocalAccount beneficiary is not supported for Snowbridge rewards!")`, and only accepts `AssetHubLocation` for that reward kind, routing it through `PayAccountOnLocation` [3](#0-2) .

Because `claim_rewards` derives the beneficiary from the caller's own `AccountId` (i.e. always `LocalAccount`), any relayer who has accumulated a `Snowbridge` reward and calls the "default" `claim_rewards` extrinsic will unconditionally hit this rejection branch and receive `FailedToPayReward` — regardless of balance, nonce, or any other on-chain state. This is confirmed by the integration test, which shows `claim_rewards` for a `BridgeReward::Snowbridge` credit failing with `FailedToPayReward` purely because of the `LocalAccount` beneficiary shape, while `claim_rewards_to` with an explicit `AssetHubLocation` is required instead [4](#0-3) . Note also that the "already claimed" reversion of `RelayerRewards` inside `do_claim_rewards` uses `try_mutate_exists`, which only commits the removal on success, so this doesn't lose funds by itself — but the mirrors of the Gauge bug are: (1) a reward class is registered and accrues correctly (`RewardLedger::register_reward` / `RewardRegistered` events fire fine for Snowbridge rewards, as seen throughout the Snowbridge V2 inbound/outbound integration tests) [5](#0-4) , but (2) the natural, "no extra parameters needed" claim path for that same reward class is wired to a payment procedure branch that always returns an error.

### Impact Explanation
This does not create fund loss by itself since `RelayerRewards` is only cleared on successful payment (guarded by `try_mutate_exists`), so no coins are silently destroyed. However, it functions exactly like the Solidity analog: a public entrypoint (`claim_rewards`) that is nominally available to any relayer holding a `Snowbridge`-kind reward is a guaranteed-revert dead end, forcing every affected relayer to discover and use `claim_rewards_to` with a manually constructed `AssetHubLocation`. Any tooling, wallet, or automated relayer client that calls the generic `claim_rewards` extrinsic (which is the natural/expected call for "claim my own reward") will always fail for this reward class, degrading relayer participation and reward distribution reliability for the bridge — a self-DoS on legitimate reward settlement analogous to the Gauge fee-distribution revert.

### Likelihood Explanation
High: this is not a race condition or requires any special preconditions — any relayer who accrues a `Snowbridge` reward and calls the straightforward `claim_rewards(origin, BridgeReward::Snowbridge)` extrinsic will deterministically hit the error on every attempt, as demonstrated directly by the existing unit test.

### Recommendation
Either (a) make `claim_rewards` reward-kind aware, so that for `BridgeReward::Snowbridge` the default beneficiary is constructed as an `AssetHubLocation` wrapping the relayer's account instead of `LocalAccount`, or (b) reject `claim_rewards` for `Snowbridge`-kind rewards at the dispatch level with a clear, documented error (e.g. `UnsupportedClaimMethod`) instead of relying on an opaque `FailedToPayReward` deep inside the payment procedure, and clearly surface that `claim_rewards_to` must be used for this reward kind.

### Proof of Concept
1. A relayer accrues a `BridgeReward::Snowbridge` credit via `register_reward` (this happens automatically through `EthereumInboundQueueV2::process_message` / `process_delivery_receipt` flows).
2. The relayer calls `BridgeRelayers::claim_rewards(origin, BridgeReward::Snowbridge)`.
3. `claim_rewards` builds `beneficiary = BridgeRewardBeneficiaries::from(relayer_account_id)` → always `LocalAccount(relayer)`.
4. `BridgeRewardPayer::pay_reward` matches `(Snowbridge, LocalAccount(_))` and returns `Err("LocalAccount beneficiary is not supported for Snowbridge rewards!")`.
5. `do_claim_rewards` maps this to `Error::FailedToPayReward`; the call reverts every time, as reproduced in [6](#0-5) .

/// An enum representing the different types of supported beneficiaries.
#[derive(
	Clone, Debug, Decode, DecodeWithMemTracking, Encode, Eq, MaxEncodedLen, PartialEq, TypeInfo,
)]
pub enum BridgeRewardBeneficiaries {
	/// A local chain account.
	LocalAccount(AccountId),
	/// A beneficiary specified by a VersionedLocation.
	AssetHubLocation(VersionedLocation),
}

impl From<sp_runtime::AccountId32> for BridgeRewardBeneficiaries {
	fn from(value: sp_runtime::AccountId32) -> Self {
		BridgeRewardBeneficiaries::LocalAccount(value)
	}
}
