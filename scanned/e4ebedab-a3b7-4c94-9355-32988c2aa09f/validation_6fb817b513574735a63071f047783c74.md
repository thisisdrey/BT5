### Title
`swap_exact_tokens_for_tokens` allows zero-output swaps to complete when no `amount_out_min` is supplied, letting an attacker donate tokens to an LP pool while draining state without an explicit rounding-to-zero guard - (`substrate/frame/asset-conversion/src/lib.rs`)

### Summary
The external report's core broken invariant is: a swap-calculation function can silently return zero output despite the pool having liquidity, because a rounding/boundary check is applied inconsistently between exact-input and exact-output code paths, and callers do not verify that the final computed amount is non-zero before committing state. `pallet-asset-conversion` shows the same class of gap in its actual (non-quote) swap execution path.

### Finding Description
The pallet has two amount-calculation primitives with intentionally asymmetric rounding: `get_amount_out` floors the integer division result, and `get_amount_in` always rounds up by `+1`, as seen at: [1](#0-0) [2](#0-1) 

This asymmetry is by design for AMM correctness, but it means very small `amount_in` values can legitimately floor to `amount_out = 0` while `reserve_in`/`reserve_out` are both non-zero (i.e., "there is liquidity available" but the computed swap output is zero), exactly the class of defect described in the external report.

The maintainers already recognized and patched this exact defect in the *view/query* functions (`quote_price_exact_tokens_for_tokens` / `quote_price_tokens_for_exact_tokens`), per `prdoc/stable2606/pr_11795.prdoc` ("Hardens... to return `None` for zero input amounts and when integer rounding produces a zero output"). The current code reflects that fix: [3](#0-2) 

However, the actual state-mutating swap extrinsics were **not** hardened with the same explicit zero-output check. `do_swap_exact_tokens_for_tokens` only validates `amount_in > 0` and, *if the caller supplied* `amount_out_min`, that it is non-zero and that `amount_out >= amount_out_min`. If the caller passes `amount_out_min = None`, there is no check that the actual computed `amount_out` is non-zero before `Self::swap` is invoked and the event is emitted: [4](#0-3) 

By contrast, the credit-based sibling function `do_swap_exact_credit_tokens_for_tokens` also has no unconditional check that `amount_out != 0` — it merely checks `amount_out >= amount_out_min` when a minimum is provided, same gap: [5](#0-4) 

So both the public dispatchable `swap_exact_tokens_for_tokens` (calling `do_swap_exact_tokens_for_tokens`) and the `SwapCredit` trait implementation allow the swap to proceed and settle state (asset transfer of `amount_in`, pool reserve update, `SwapExecuted`/`SwapCreditExecuted` events) even when `amount_out` rounds to zero, as long as the caller omits (or accepts) `amount_out_min = 0`/`None`. This is exactly the "returns a value of zero even when there is liquidity available" defect from the report, except here it is not merely a quoting bug — it lets a real state transition (fund transfer into the pool with zero output) execute.

### Impact Explanation
This lets an unprivileged, unprivileged caller (no admin/governance/relayer/validator involvement) execute a real swap extrinsic that transfers a positive `amount_in` from themselves into the pool while receiving `amount_out = 0` back, and have it recorded as a normal, successful `SwapExecuted`/`SwapCreditExecuted` event. While the caller loses their own funds (self-inflicted), the broader concern under the "conserve value / settle exactly once to the rightful beneficiary and amount" pivot is that the swap accounting can complete with a non-conservative, degenerate exchange rate (all value in, none out) without any explicit `ZeroAmount`/"AmountOutTooSmall" rejection at the execution layer, unlike the already-hardened quoting layer. This is inconsistent with the fix already applied to `quote_price_*` (which now explicitly rejects rounding to zero), showing the team's own acknowledged threat model classifies this pattern as a defect worth guarding against — yet the guard was not propagated to the actual execution path.

### Likelihood Explanation
Medium-to-low: triggering requires a heavily skewed pool (large `reserve_in`, small `reserve_out`) and a caller submitting a very small `amount_in` with `amount_out_min` omitted or `0`. This is an easy, permissionless, single-transaction precondition (as demonstrated by the pallet's own test `quote_price_returns_none_for_zero_output`, which shows realistic reserve skew: `1_000_000`/`200` reserves and `amount_in=1` rounds to zero) — the same numeric conditions apply to the real swap path, not just quoting: [6](#0-5) 

### Recommendation
Add an explicit, unconditional check in `do_swap_exact_tokens_for_tokens`, `do_swap_exact_credit_tokens_for_tokens`, and any other exact-input swap execution path that `amount_out` (and each intermediate hop's amount, for multi-hop paths) is non-zero, mirroring the fix already applied to `quote_price_exact_tokens_for_tokens`/`quote_price_tokens_for_exact_tokens` in PR 11795. Reject with `Error::<T>::ZeroAmount` (or a dedicated error) before calling `Self::swap`/`Self::credit_swap`, regardless of whether the caller supplied `amount_out_min`.

### Proof of Concept
1. Create a pool with heavily skewed reserves, e.g. `reserve_in = 1_000_000`, `reserve_out = 200` (as in the existing test `quote_price_returns_none_for_zero_output`).
2. Call the public extrinsic `swap_exact_tokens_for_tokens(path=[asset1, asset2], amount_in=1, amount_out_min=None, send_to=attacker, keep_alive=false)`.
3. Internally, `get_amount_out(fee, 1, 1_000_000, 200)` computes `1*997*200 / (1_000_000*1000 + 997) = 0` (per the pallet's own comment/test), so `amount_out = 0`.
4. Because `amount_out_min` is `None`, the `ensure!(amount_out >= amount_out_min, ...)` check at lines 997-1002 is skipped entirely, and `do_swap_exact_tokens_for_tokens` proceeds to call `Self::swap`, transferring `amount_in=1` out of the caller into the pool and emitting `SwapExecuted { amount_in: 1, amount_out: 0, .. }` with no error — unlike the quote functions, which would return `None` for the identical inputs.
