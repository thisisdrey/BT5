### Title
Outbound queue `calculate_fee` can round the remote-fee component to zero while `do_process_message` still commits the full wei-denominated reward/gas cost to Ethereum, letting message senders systematically underpay for guaranteed relayer payouts - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
The bug report's core invariant break is: a single unguarded price source can produce a degenerate (zero/invalid) value that is nevertheless treated as valid, causing downstream logic to proceed on bad data. The local analog is Snowbridge's outbound-queue fee pricing: `calculate_fee` converts an Ethereum-denominated cost into a local-currency fee by dividing by a single governance-set `exchange_rate` with no floor/sanity check on the *output*, and the pallet's own test suite already documents that this can legitimately compute a remote fee of `0` even with fully "valid", non-zero `PricingParameters`.

### Finding Description
`PricingParameters::validate()` only checks that each input field is non-zero: [1](#0-0) 

It never validates that the *resulting* computed fee is non-zero. `calculate_fee` performs the actual conversion: [2](#0-1) 

Because `gas_used_at_most` (attacker-influenced via the command's gas metering), `fee_per_gas`, `multiplier`, and `exchange_rate` are combined via fixed-point integer division and then further divided in `convert_from_ether_decimals`, the final local "remote" fee can floor to `0` even though every individual `PricingParameters` field passed `validate()`. This is confirmed directly in the pallet's own tests: [3](#0-2) 

Meanwhile, `validate()` in `send_message_impl.rs` is the public entrypoint used by any XCM-triggered send (e.g. token transfers to Ethereum) — it calls `calculate_fee` to derive the `Fee` charged to the submitter, and enqueues the message unconditionally regardless of whether the computed remote fee is zero: [4](#0-3) 

Critically, the amount actually **committed** to Ethereum — the `max_fee_per_gas` and `reward` the Gateway contract will pay relayers — is taken directly from the raw `pricing_params`, completely independent of the (possibly zero) fee that was actually collected from the sender: [5](#0-4) 

So there is no reconciliation between "fee charged to the public sender" and "reward/gas promise embedded in the committed message." A public, unprivileged actor who triggers outbound messages with a small `gas_used_at_most` (i.e., commands with low `maximum_dispatch_gas_used_at_most`) relative to the configured `exchange_rate`/`multiplier` can have their remote-fee obligation round down to zero while the queue still emits a `CommittedMessage` promising the full fixed `reward` (e.g. `meth(1)`) to whichever relayer submits it to Ethereum.

### Impact Explanation
This is the "reserve price source" bug class applied locally: exactly one governance-set price ratio feeds an unguarded division, and its degenerate output (zero) is accepted as if it were a legitimate fee. Repeated exploitation lets senders push messages through `do_process_message` that under-fund (in local currency) the guaranteed relayer reward/gas commitment recorded in the committed message and eventually claimed on Ethereum, i.e. public underpriced work that erodes the fee base backing bridge relayer payouts without a corresponding matching charge — a direct instance of "public underpriced work that degrades block production or stalls bridge processing" from the impact gate.

### Likelihood Explanation
The path is reachable by any unprivileged account via `SendMessage::validate`/`deliver`, which back ordinary XCM-triggered bridge operations (asset transfers, register token, etc.) — no governance, relayer, or validator collusion is required. The exact zero-fee scenario is already demonstrated as reachable with plausible parameter combinations in the pallet's own test suite, meaning it is not a purely theoretical edge case but a documented, unresolved rounding gap ("though none zero pricing params the remote fee calculated here is invalid which should be avoided").

### Recommendation
Add a floor/validity check on the *output* of `calculate_fee` (reject or round up to a minimum non-zero remote fee) before returning it from `validate()`, and/or reject message submission in `send_message_impl::validate` when the computed `fee.remote` is `0` but the underlying committed message still carries a non-zero `reward`/`max_fee_per_gas` obligation, ensuring the local fee always covers the promised remote-side payout.

### Proof of Concept
Using the existing test harness pattern from `bridges/snowbridge/pallets/outbound-queue/src/test.rs`:
1. Configure `PricingParameters` with a small `gas_used_at_most` (via a command with minimal `maximum_dispatch_gas_used_at_most`), `fee_per_gas = 1`, `rewards.remote = 1`, `exchange_rate = 1/1`, `multiplier = 1` — all individually pass `PricingParameters::validate()`.
2. Call `OutboundQueue::calculate_fee(gas_used, price_params)` as in `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` — observe `fee.remote == 0` while `fee.local` (weight cost) is charged.
3. Submit this message through `SendMessage::validate`/`deliver`; `do_process_message` still constructs a `CommittedMessage` with `max_fee_per_gas` and `reward` copied straight from `pricing_params` (non-zero), which will be honored on Ethereum, despite the sender having paid zero for that remote-side cost.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {
		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
			exchange_rate: FixedU128::from_rational(1, 1),
			fee_per_gas: 1_u32.into(),
			rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});
}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}
