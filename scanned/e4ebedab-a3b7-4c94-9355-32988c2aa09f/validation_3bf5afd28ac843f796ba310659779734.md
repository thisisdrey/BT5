## Title
Yield theft via JIT `join`/`bond_extra` front-running `payout_stakers` deposits into a Nomination Pool's reward account - (File: `substrate/frame/nomination-pools/src/lib.rs`)

## Summary

The `LiquidityReserve` bug is a JIT (just-in-time) liquidity sandwich: an attacker adds a large stake right before a fee-generating event lands, and the fee gets pro-rated across all current liquidity providers — including the attacker who contributed nothing to earning it. The direct analog in this repository is `pallet-nomination-pools`: rewards accrued by `pallet-staking`/`pallet-staking-async` are periodically pushed into a pool's `reward_account` by the permissionless `payout_stakers` extrinsic [1](#0-0) , and are only attributed to member shares lazily, the next time `RewardPool::update_records` runs, using the pool's points *at call time* rather than the points that were active while the reward accrued.

## Finding Description

`RewardPool::current_balance` simply reads the live, reducible balance of the pool's reward account [2](#0-1) . `RewardPool::update_records`/`current_reward_counter` compute `current_payout_balance` from that live balance and divide the newly-observed payout by `bonded_points`, the pool's **current total points** [3](#0-2) .

`Call::join` calls `reward_pool.update_records(..)` using the pool's points *before* the joiner's funds are bonded, then only afterwards increases `bonded_pool.points` and inserts the new `PoolMember` with `last_recorded_reward_counter` set to the just-computed counter [4](#0-3) . This correctly excludes rewards that were *already sitting in the reward account* at join time. But it does **not** protect against rewards that land *after* the join but *before* the next `update_records` call: the deposit from `payout_stakers` is a plain `Currency::transfer` into the reward account [5](#0-4)  that does not itself call `update_records`. The next time anyone (including the same account) triggers `update_records` — e.g. via `claim_payout` → `do_reward_payout` [6](#0-5)  — the entire newly-arrived reward is split across `bonded_pool.points`, which by then **already includes the attacker's freshly-joined points**.

`payout_stakers`/`payout_stakers_by_page` are unrestricted, permissionless, signed-origin calls that anyone can submit at any time for any validator/era combination [7](#0-6) , so their landing block is fully visible/predictable in the mempool.

Attack sequence:
1. Attacker observes a pending `payout_stakers` (or `payout_stakers_by_page`) call that will deposit a large reward `R` into a pool's `reward_account` (because the pool's bonded/nominator stash has `RewardDestination::Account(reward_account)`).
2. Attacker submits `join` (or `bond_extra`) with a large `amount`, ordered to land in the same or an earlier block than the payout, but before anyone calls `claim_payout`/`bond_extra`/`unbond` again. `update_records` runs with old points, so the attacker is not charged for rewards already booked, but the attacker's points are added to `bonded_pool.points` going forward.
3. `payout_stakers` executes, transferring `R` straight into the reward account balance, unattributed.
4. Attacker (or anyone) calls `claim_payout`. `update_records`/`current_reward_counter` see `current_payout_balance ≈ R` and divide by the pool's total points, which now include the attacker's just-added stake. The attacker collects a share of `R` proportional to their newly-joined stake, despite having contributed zero time/stake while `R` was earned.
5. Unlike `LiquidityReserve.removeLiquidity()`, the attacker does **not** need to `unbond` to realize the theft — `claim_payout` alone extracts the stolen yield while the principal remains bonded (and can keep earning or be withdrawn normally later), so the usual `bonding_duration` unbonding lock provides no protection against this specific theft.

## Impact Explanation

Every genuine, long-term pool member's yield is diluted whenever a large `payout_stakers` deposit is imminent and visible in the mempool, exactly mirroring the "Yield of `LiquidityReserve` can be stolen" class: value that should accrue only to depositors who bore risk/time is captured, risk-free, by a JIT depositor. This is a direct value-conservation violation for pool balances (fund misdirection to the wrong beneficiary/amount), matching the "Balances... must conserve value and settle exactly once to the rightful beneficiary" pivot.

## Likelihood Explanation

`payout_stakers` calls are public, frequent (once per era per validator), and their landing time is visible before inclusion; `join`/`bond_extra` are unprivileged, fee-only operations with no cooldown before `claim_payout` is callable. No malicious validator, relayer, or governance actor is required — only an attacker capable of ordinary transaction submission/tip-based ordering.

## Recommendation

- Snapshot/checkpoint the reward-account balance whenever new points are admitted (`join`/`bond_extra`) so that rewards can only be attributed to points that existed when the underlying stake was actually earning; alternatively, require `update_records` to be invoked (and reward-counter "frozen") atomically with `payout_stakers` execution, e.g. by having `payout_stakers` trigger `update_records` on any nomination pool it pays into before the transfer completes.
- Introduce a minimum bonding delay before newly-joined/added points become eligible for already-pending (not-yet-recorded) rewards, analogous to withdrawal locks.
- Alternatively, distribute newly observed reward-account balance increases pro-rata to the points held at the *previous* checkpoint rather than the points at the time of the next `update_records` call.

## Proof of Concept

1. Pool `P` has one long-term member `A` with 100 points, `RewardDestination::Account(P.reward_account)`.
2. Mempool shows pending `payout_stakers(validator, era)` that will transfer `R = 1000` into `P.reward_account`.
3. Attacker `B` submits `Pools::join(pool_id, amount=10000)` ordered just before the payout lands: `update_records` runs with `bonded_pool.points = 100` (old), balance not yet containing `R`; `B` is added with points ≈ 10000·(ratio), total points now ≈ 10100.
4. `payout_stakers` executes, reward account balance increases by `R = 1000`.
5. `B` calls `Pools::claim_payout`. `do_reward_payout` → `current_reward_counter` computes `new_pending_rewards ≈ 1000` divided by `bonded_points = 10100`, giving `B` ≈ `990` of the `1000` reward that `A` alone should have earned, while `A`'s eventual `claim_payout` only nets ≈ `10`.
6. `B` may `unbond`/exit later at leisure; no penalty or lock prevented the theft since `claim_payout` requires no unbonding. [8](#0-7) [9](#0-8)

		pub fn join(
			origin: OriginFor<T>,
			#[pallet::compact] amount: BalanceOf<T>,
			pool_id: PoolId,
		) -> DispatchResult {
			let who = ensure_signed(origin)?;
			// ensure pool is not in an un-migrated state.
			ensure!(!Self::api_pool_needs_delegate_migration(pool_id), Error::<T>::NotMigrated);

			// ensure account is not restricted from joining the pool.
			ensure!(!T::Filter::contains(&who), Error::<T>::Restricted);

			ensure!(amount >= MinJoinBond::<T>::get(), Error::<T>::MinimumBondNotMet);
			// If a member already exists that means they already belong to a pool
			ensure!(!PoolMembers::<T>::contains_key(&who), Error::<T>::AccountBelongsToOtherPool);

			let mut bonded_pool = BondedPool::<T>::get(pool_id).ok_or(Error::<T>::PoolNotFound)?;
			bonded_pool.ok_to_join()?;

			let mut reward_pool = RewardPools::<T>::get(pool_id)
				.defensive_ok_or::<Error<T>>(DefensiveError::RewardPoolNotFound.into())?;
			// IMPORTANT: reward pool records must be updated with the old points.
			reward_pool.update_records(
				pool_id,
				bonded_pool.points,
				bonded_pool.commission.current(),
			)?;

			bonded_pool.try_inc_members()?;
			let points_issued = bonded_pool.try_bond_funds(&who, amount, BondType::Extra)?;

			PoolMembers::insert(
				who.clone(),
				PoolMember::<T> {
					pool_id,
					points: points_issued,
					// we just updated `last_known_reward_counter` to the current one in
					// `update_recorded`.
					last_recorded_reward_counter: reward_pool.last_recorded_reward_counter(),
					unbonding_eras: Default::default(),
				},
			);

			Self::deposit_event(Event::<T>::Bonded {
				member: who,
				pool_id,
				bonded: amount,
				joined: true,
			});

			bonded_pool.put();
			RewardPools::<T>::insert(pool_id, reward_pool);

			Ok(())
		}

	fn do_reward_payout(
		member_account: &T::AccountId,
		member: &mut PoolMember<T>,
		bonded_pool: &mut BondedPool<T>,
		reward_pool: &mut RewardPool<T>,
	) -> Result<BalanceOf<T>, DispatchError> {
		debug_assert_eq!(member.pool_id, bonded_pool.id);
		debug_assert_eq!(&mut PoolMembers::<T>::get(member_account).unwrap(), member);

		// a member who has no skin in the game anymore cannot claim any rewards.
		ensure!(!member.active_points().is_zero(), Error::<T>::FullyUnbonding);

		let (current_reward_counter, _) = reward_pool.current_reward_counter(
			bonded_pool.id,
			bonded_pool.points,
			bonded_pool.commission.current(),
		)?;

		// Determine the pending rewards. In scenarios where commission is 100%, `pending_rewards`
		// will be zero.
		let pending_rewards = member.pending_rewards(current_reward_counter)?;
		if pending_rewards.is_zero() {
			return Ok(pending_rewards);
		}

		// IFF the reward is non-zero alter the member and reward pool info.
		member.last_recorded_reward_counter = current_reward_counter;
		reward_pool.register_claimed_reward(pending_rewards);

	fn do_bond_extra(
		signer: T::AccountId,
		member_account: T::AccountId,
		extra: BondExtra<BalanceOf<T>>,
	) -> DispatchResult {
		// ensure account is not restricted from joining the pool.
		ensure!(!T::Filter::contains(&member_account), Error::<T>::Restricted);

		if signer != member_account {
			ensure!(
				ClaimPermissions::<T>::get(&member_account).can_bond_extra(),
				Error::<T>::DoesNotHavePermission
			);
			ensure!(extra == BondExtra::Rewards, Error::<T>::BondExtraRestricted);
		}

		let (mut member, mut bonded_pool, mut reward_pool) =
			Self::get_member_with_pools(&member_account)?;

		// payout related stuff: we must claim the payouts, and updated recorded payout data
		// before updating the bonded pool points, similar to that of `join` transaction.
		reward_pool.update_records(
			bonded_pool.id,
			bonded_pool.points,
			bonded_pool.commission.current(),
		)?;
		let claimed = Self::do_reward_payout(
			&member_account,
			&mut member,
			&mut bonded_pool,
			&mut reward_pool,
		)?;

		let (points_issued, bonded) = match extra {
			BondExtra::FreeBalance(amount) => {
				(bonded_pool.try_bond_funds(&member_account, amount, BondType::Extra)?, amount)
			},
			BondExtra::Rewards => {
				(bonded_pool.try_bond_funds(&member_account, claimed, BondType::Extra)?, claimed)
			},
		};

		bonded_pool.ok_to_be_open()?;
		member.points =
			member.points.checked_add(&points_issued).ok_or(Error::<T>::OverflowRisk)?;

		Self::deposit_event(Event::<T>::Bonded {
			member: member_account.clone(),
			pool_id: member.pool_id,
			bonded,
			joined: false,
		});
		Self::put_member_with_pools(&member_account, member, bonded_pool, reward_pool);

		Ok(())
	}
