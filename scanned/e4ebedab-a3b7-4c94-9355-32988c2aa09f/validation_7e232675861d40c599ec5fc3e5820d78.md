### Title
`add_tip` irreversibly burns the tip asset on AssetHub before the tip can be validated on BridgeHub, permanently losing user funds when the tip fails to apply - ([File: bridges/snowbridge/pallets/system-frontend/src/lib.rs])

### Summary
`pallet_snowbridge_system_frontend::Pallet::add_tip` on AssetHub swaps/burns the caller's fee asset for Ether *before* sending an XCM `Transact` to BridgeHub that actually tries to apply the tip to a specific message nonce via `InboundQueue::add_tip` / `OutboundQueue::add_tip`. If that downstream call fails (e.g. the nonce has already been rewarded, is unknown, or the order cannot be found), BridgeHub's `EthereumSystem::add_tip` only records the amount in `LostTips` storage — it never refunds anything, and there is currently no extrinsic to reclaim it. This is the same core broken invariant as the external report: a function accepts value from the caller without verifying, atomically, that the value can actually be put to its intended use, and the excess/unusable payment is irrecoverably lost.

### Finding Description
The user-facing entrypoint is `add_tip` in `bridges/snowbridge/pallets/system-frontend/src/lib.rs`: [1](#0-0) 

This calls `swap_fee_asset_and_burn`, which either swaps the supplied asset into Ether and burns it, or burns it directly if already Ether: [2](#0-1) 

Both branches are irreversible on AssetHub: `swap_and_burn` executes `T::Swap::swap_exact_tokens_for_tokens` and then `burn_for_teleport`, and the direct-Ether branch also calls `burn_for_teleport` immediately: [3](#0-2) 

Only *after* the burn succeeds does the pallet build and send the XCM `Transact` call carrying the tip amount to BridgeHub's `EthereumSystem::add_tip`: [4](#0-3) 

On BridgeHub, `snowbridge_pallet_system_v2::Pallet::add_tip` tries to apply the tip to the referenced Inbound/Outbound message nonce: [5](#0-4) 

If `InboundQueue::add_tip` / `OutboundQueue::add_tip` returns an error (e.g. the nonce's reward order was already consumed, already delivered, or not found — realistic and unprivileged conditions any user can trigger simply by tipping a message whose processing races ahead of their tip, or a nonce they mis-specify), the code path only accumulates the lost amount into `LostTips`: [6](#0-5) 

The doc comment explicitly acknowledges there is no way today to recover these funds — it is future work: [7](#0-6) 

The corrupted/lost value is the user's tip asset amount that was swapped/burned on AssetHub: the burn on the source chain is not atomic with, nor conditioned on, successful application of the tip on the destination chain. There is no existing guard preventing this: the source-side pallet has no way to know in advance whether the nonce/order is still tippable, and the destination-side pallet has no compensating action (refund, mint-back, or reversible hold) — it just books a permanent liability in `LostTips` with no corresponding withdrawal call anywhere in the codebase.

### Impact Explanation
This is a permanent, protocol-level fund loss for any unprivileged user who calls `add_tip`, whenever the targeted message/order has already been rewarded, is unknown, or otherwise cannot accept the tip by the time the cross-chain `Transact` executes on BridgeHub (a race that is entirely plausible given relayers process messages continuously and asynchronously from user submissions). The funds are burned unconditionally on AssetHub regardless of the outcome on BridgeHub, and BridgeHub has no mechanism to return them — it only records the debt. This satisfies the "permanent user-fund or bridge-state lock" impact category, as real value (post-swap Ether) is destroyed with no path back to the rightful owner.

### Likelihood Explanation
Likelihood is high in practice: `add_tip` is a public, unprivileged, permissionless extrinsic (`ensure_signed(origin)`), and the failure mode (nonce already rewarded / order not found) is a normal race condition rather than an edge case requiring any malicious actor — it can occur simply because relayers process and reward messages concurrently with tips being submitted, or because a user tips a nonce that has already completed. No governance, admin, relayer collusion, or malicious peer is required.

### Recommendation
Do not irrevocably burn the tip asset on the source chain before the downstream tip-application outcome is known. Options:
1. Defer the burn until BridgeHub confirms the tip was successfully applied (e.g. via a receipt/callback mechanism), or
2. Implement (and ship, not just plan) a withdrawal/refund extrinsic against `LostTips` so affected users can reclaim the Ether-equivalent value that failed to apply, or
3. Validate tip applicability atomically as part of the same state transition that performs the burn (e.g. check nonce validity synchronously before burning, if cross-chain synchronous validation is achievable), reducing the window in which loss can occur.

### Proof of Concept
1. User A observes an in-flight (not yet finally rewarded) message with `message_id = Outbound(nonce)`.
2. User A calls `snowbridge_pallet_system_frontend::add_tip(origin=A, message_id, asset)` on AssetHub with a nonzero `asset`.
3. `swap_fee_asset_and_burn` swaps/burns A's asset for Ether unconditionally (`bridges/snowbridge/pallets/system-frontend/src/lib.rs:372-404`); A's balance is now reduced.
4. Concurrently, before the XCM `Transact` lands on BridgeHub, the relayer for `nonce` submits its delivery receipt and the reward for that nonce is finalized/consumed (a realistic race, not requiring any malicious actor).
5. The XCM `Transact` executes `EthereumSystem::add_tip` on BridgeHub (`bridges/snowbridge/pallets/system-v2/src/lib.rs:251-281`); `OutboundQueue::add_tip(nonce, amount)` returns `Err` because the nonce is already consumed.
6. The pallet only records `amount` into `LostTips::<T>::get(&sender)` (`bridges/snowbridge/pallets/system-v2/src/lib.rs:136-142`) and emits `TipProcessed { success: false }`.
7. User A's burned Ether-equivalent value is now permanently unrecoverable: no extrinsic in the repository consumes or refunds `LostTips`.

		fn swap_and_burn(
			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether
			let ether_asset = Asset::from((ether_location.clone(), ether_gained));

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}

		#[pallet::call_index(3)]
		#[pallet::weight(<T as pallet::Config>::WeightInfo::add_tip())]
		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}
