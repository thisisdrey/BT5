Target: WalletImpl::execute_signed, SignatureSchema::verify_request_msg. Attacker action: attacker takes a validly-signed RequestMessage and mutates a field that is NOT covered by the signature's canonical encoding (e.g. re-encodes the borsh/json message with a different but semantically-equal representation of `chain_id` or reorders untouched optional fields) so that `msg.hash()` and the byte sequence verified by `proof` change but `S::verify_request_msg` still returns true due to a non-canonical (de)serialization accepted by borsh/serde. Preconditions: RequestMessage implements PartialEq/Hash and Borsh/Serde with cfg-gated encodings (TimestampNanoSeconds, DurationSeconds) that could admit multiple byte-level encodings of the same logical value. Call sequence: attacker resubmits the re-encoded msg with the original proof; verify_request_msg(&public_key, &msg, proof) is called on the mutated msg. Binding: the exact request the owner signed == the exact request executed (bit-for-bit equality of the signed payload). Impact: High — a re-encoded RequestMessage that still verifies lets an attacker alter execution semantics (e.g. widen `request.external` deposit) without a valid new signature. Proof idea: property test (proptest/arbitrary) generating alternate valid encodings of the same logical RequestMessage and asserting verify_request_msg fails whenever any semantic field differs from what was originally signed.
