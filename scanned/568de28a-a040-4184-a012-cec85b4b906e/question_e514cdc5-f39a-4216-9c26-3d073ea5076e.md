Target: `mt_resolve_deposit`/`ft_resolve_deposit`/`nft_resolve_deposit` (contracts/defuse/src/contract/tokens/{nep245,nep141,nep171}/deposit.rs) and their shared `resolve_deposit_internal`. Attacker deploys a malicious `NotifyOnTransfer` receiver contract and deposits via `ft_on_transfer` with `msg` selecting `DepositAction::Notify`, whose receiver contract's return value is attacker-controlled and is fed back into `ft_resolve_deposit(receiver_id, contract_id, amount)` — the `contract_id` here is `env::predecessor_account_id()` (trusted), but the attacker controls the receiver's promise result consumed inside `resolve_deposit_internal`. Preconditions: attacker deploys the notify-receiver contract naming itself in `msg`; a real deposit of amount N was already credited before the notify call. Call sequence: `ft_on_transfer` -> `deposit` (credits N) -> `notify_on_transfer` (calls attacker's receiver) -> `ft_resolve_deposit` reads the receiver's promise result to decide how much (if any) to claw back via `resolve_deposit_internal`. Binding: the amount clawed back in `resolve_deposit_internal` must equal exactly `amount - (amount actually accepted by the notify receiver)`, i.e. `value re-credited by resolver + value delivered == value originally debited/deposited`, and must never claw back MORE than was originally credited for that exact `TokenId`. Impact: Critical — a malicious receiver could return a crafted result causing the resolver to subtract from the wrong `TokenId` or over/under-adjust, breaking SETTLEMENT for the depositor's balance. Proof idea: cargo test / near-workspaces test with a notify receiver returning adversarial promise results (oversized numbers, wrong type), asserting `resolve_deposit_internal` either panics safely or leaves the balance for that exact `TokenId` mathematically consistent with `value delivered + value re-credited == value debited`.
