Target: `TokenDiff` intents carrying `token_id.to_string()` (contracts/defuse/core/src/intents/token_diff.rs). Attacker signs a `MultiPayload` containing a `TokenDiff` intent referencing a `TokenId` constructed from a self-controlled NEP-245 contract with an `mt_token_id` designed to serialize identically to another party's `TokenId` in a currently-open, unmatched `TokenDiff` (multi-party swap matching by string/`TokenId` equality). Preconditions: victim has an open, signed `TokenDiff` intent quoting token X; attacker crafts a `TokenDiff` quoting a `TokenId` that displays identically to X but internally differs (or vice versa) due to a serialization edge case. Call sequence: `execute_intents` batches both signed payloads -> `TokenDiff::closure_delta`/`closure_deltas` matches deltas keyed by `TokenId` -> if the two `TokenId`s are `PartialEq`-equal because of a collision, deltas net against each other. Binding: `TokenDiff::closure_deltas` must only net two deltas when their `TokenId`s are truly identical `(contract, token)` pairs, i.e. `sum of deltas for a given displayed id == 0` only reflects real conservation when `TokenId` equality implies asset equality. Impact: Critical — a collision would let a worthless-asset delta be netted against a valuable-asset delta, breaking CONSERVATION (`sum of all token_balances changes across the call == 0` in terms of custodied assets, not display strings). Proof idea: cargo test constructing two `TokenId`s with different underlying `(contract, token)` but attempting to force `Display` equality; assert `closure_deltas` panics or errors rather than silently netting non-equal-`PartialEq` structs, and that no code path derives `TokenId` equality from `to_string()` comparison instead of struct `PartialEq`.
