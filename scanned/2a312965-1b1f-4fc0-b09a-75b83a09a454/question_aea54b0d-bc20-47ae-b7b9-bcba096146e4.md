Target: `Contract::do_auth_call` and `State::auth_call` in `contracts/defuse/src/contract/intents/state.rs`. Attacker signs a `MultiPayload` whose `DefuseIntents` contains an `AuthCall{contract_id: <attacker_contract>, msg: "reenter", attached_deposit: NearToken::ZERO, state_init: None, min_gas: None}` intent followed in the same batch by an `FtWithdraw` intent debiting the signer's `token_balances`. Preconditions: signer_id has token_balances[TokenId::Nep141(usdc)] = 1000 and a valid nonce/salt. Call sequence: `Engine::execute_signed_intent` executes `AuthCall::execute_intent` -> `engine.state.auth_call` -> `Contract::do_auth_call` builds `Promise::new(auth_call.contract_id)` and calls `ext_auth_callee::ext_on(p).on_auth(signer_id, msg)`, detached after `Engine::finalize` already computed the batch's committed deltas; attacker's `on_auth` implementation calls `execute_intents` again with a second valid signature over the same balance before the first receipt's promises settle. Binding broken: the set of `token_balances` changes committed by the first `execute_intents` receipt != the set the signer's single signature authorised, because the re-entrant `execute_intents` call observes pre-settlement state and drains the same balance twice. Scoped impact: Critical, double-spend of the signer's own custodied balance, funds effectively lost from the Verifier's assets backing other users. Proof idea: `near-workspaces` sandbox test deploying a stub `on_auth` callee that calls `execute_intents` recursively, asserting `sum(token_balances deltas across both receipts) != 0` and that signer's post-balance is negative-equivalent (i.e. below zero-clamped floor) relative to a single authorised debit.
