# [M] Deposit Function Should be Disabled Before Starting a Game

## Summary
Severity: Medium
Contest weight: 0.0287
Dataset id: 8805
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability is a logical access‑control flaw in the game contract where the function that accepts user deposits remains callable even after the game has been started. The root cause is that the contract does not check the game state before allowing deposits, so the deposit function is not gated by a game‑not‑started flag. An attacker or any user can invoke deposit after the startGame transaction, causing the contract to accept ether that will never be used in the current round. Because the contract does not revert or forward the funds, the transaction succeeds but the deposited amount is effectively locked or ignored, leading to wasted gas and a potential denial‑of‑service vector where a malicious actor repeatedly deposits small amounts to fill the block gas limit or to increase the contract’s balance without participating in the game. The impact is that honest participants see their own balances unchanged while the contract’s internal accounting may become out of sync, users may receive no reward or refund for the deposited amount, and the overall user experience degrades as transactions appear to succeed but produce no game‑related benefit. The condition occurs whenever a user calls the deposit function after the startGame function has been executed but before the contract disables further deposits. All participants of the game, including the contract owner, are affected because the contract’s economic model assumes deposits only happen before the game begins. The issue was discovered during a manual audit that examined the state transitions of the game lifecycle and noticed that the deposit function lacks a require statement checking the game status. It can be hard to notice because the transaction does not revert and the UI may simply show a successful deposit, while the backend logic never incorporates the funds into the game round. To remediate, the contract should enforce a state check that disables deposits once the game is started, typically by adding a require(!gameStarted) or similar guard, and optionally emit an event when deposits are rejected. This class of bug belongs to the broader category of improper state‑based access control or lifecycle‑management errors, where functions are callable in an invalid contract phase, leading to unintended fund flow and potential gas griefing. From a user’s perspective, they may see a successful transaction receipt but later notice that their balance in the game remains zero or that no refund is issued, contradicting the expectation that a deposit should enable participation. The mismatch between expected participation and actual outcome constitutes a violation of the protocol’s accounting assumptions.

## Recommendation
Ensure that the deposit function is disabled for the user before starting a game.
