In `NakamotoBlocksData::consensus_deserialize` (stackslib/src/net/codec.rs), an attacker relays `StacksMessageType::NakamotoBlocks` containing more than `NAKAMOTO_BLOCKS_PUSHED_MAX` `NakamotoBlock` entries by nesting them inside a single block's oversized `BoundReader::from_reader(fd, MAX_MESSAGE_LEN as u64)` window so that `read_next_at_most` never rejects them but the per-block Nakamoto codec allocates transaction vectors sized from wire-controlled counts. Preconditions: any P2P peer, no handshake privilege beyond an accepted connection, `preamble.payload_len < MAX_MESSAGE_LEN`. Call sequence: `StacksMessage::deserialize_body` -> `StacksMessageType::consensus_deserialize` dispatch on `StacksMessageID::NakamotoBlocks` -> `NakamotoBlocksData::consensus_deserialize` -> `read_next_at_most::<_, NakamotoBlock>` bound only by byte count, not memory. Equality/fault: total bytes consumed by all `NakamotoBlock` entries must equal `MAX_MESSAGE_LEN`'s bound with no intermediate allocation exceeding a validated per-field length. Impact: Critical, unauthenticated DoS via oversized allocation from a single message. Proof idea: `stackslib::net` test building a byte buffer whose declared vector length field asks for a large `Vec<NakamotoBlock>` capacity near `MAX_MESSAGE_LEN` and asserting either a bounded rejection or a memory/time blowup.
