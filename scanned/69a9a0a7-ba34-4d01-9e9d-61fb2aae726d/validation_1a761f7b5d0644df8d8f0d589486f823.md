### Title
On-demand spot-traffic decay formula omits the base term, letting an attacker crash blockspace pricing to near-floor with a single call - (File: `polkadot/runtime/parachains/src/on_demand/mod.rs`)

### Summary
`Pallet::calculate_spot_traffic` computes the multiplicative update applied to the on-demand `traffic` value (which directly scales `spot_price` in `do_place_order`/`update_spot_traffic`). The increasing branch correctly implements `traffic * (1 + diff + diff²/2)`, but the decreasing branch drops the `1 +` term entirely and instead computes `traffic * (diff − diff²/2)`. This is the same class of bug as the reported Infinity-Swap issue: instead of applying the intended near-unity multiplier around a reference point of `1`, the code multiplies by the *raw deviation itself*, producing a wildly different (and far more aggressive) decay than intended. [1](#0-0) 

### Finding Description
The function is meant to mirror `pallet_transaction_payment`'s `TargetedFeeAdjustment`, which updates a multiplier as `previous * (1 + t1 + t2)` when above target and `previous * (1 − t1 + t2)`-equivalent (via `saturating_sub`) when below target, always centered at `1`. [2](#0-1) 

`calculate_spot_traffic` implements the "above target" branch correctly:
```rust
let new_traffic = queue_util_diff
    .saturating_add(div_by_two)
    .saturating_add(One::one())
    .saturating_mul(traffic);
```
but the "below target" branch is:
```rust
let new_traffic = queue_util_diff.saturating_sub(div_by_two).saturating_mul(traffic);
```
There is no `One::one()` term here at all. Instead of multiplying `traffic` by something close to `1` (e.g. `1 − diff + diff²/2`), it multiplies `traffic` directly by the deviation magnitude `diff − diff²/2`. Because `diff ∈ [0,1]` (a `Perbill`-derived `FixedU128`), whenever the queue is under-utilized `diff` is typically small (e.g. 0.1), and the new traffic collapses to roughly `traffic * diff` — a near-instant 90%+ drop for only a 10% under-utilization, rather than the intended gentle ~10% reduction. [3](#0-2) 

The existing unit tests do not catch this because they all exercise `variability = 100%` together with `diff = 1.0` (fully empty queue vs. 100% target), where `diff − diff²/2` and the intended `1 − diff + diff²/2` happen to coincide numerically (both evaluate to `0.5` when `diff = 1`), masking the discrepancy for any smaller/partial `diff`. [4](#0-3) 

`traffic` directly feeds `spot_price` computation used to gate/charge `place_order_allow_death`/`place_order_with_credits` via `do_place_order`, so any miscalculation here is immediately exploitable by any unprivileged account placing on-demand orders. [5](#0-4) 

### Impact Explanation
The on-demand pricing mechanism exists specifically to prevent underpriced blockspace consumption during congestion by ramping price up quickly and letting it decay only gradually back toward the floor. This bug inverts that guarantee for the decay path: any period of even modest under-utilization (which any actor can trivially engineer by simply not ordering for a block or two, or by orders draining from the queue) causes `traffic` to crash almost immediately toward the configured floor (`TrafficDefaultValue`). Once collapsed, subsequent orders are charged the near-minimum `on_demand_base_fee` instead of a price that reflects recent congestion, allowing an attacker to obtain parachain blockspace far below its intended market-clearing price — a public, underpriced-work condition that degrades the anti-congestion economics of block production, matching the "public underpriced work that degrades block production" impact category.

### Likelihood Explanation
No privileged access, governance, validator, or malicious peer/relayer role is required — this is a pure public dispatch path (`place_order_allow_death`/`place_order_with_credits`) reachable by any signed account. Triggering the bug only requires letting the on-demand queue briefly go below the configured `on_demand_target_queue_utilization` (e.g., by pausing orders for one block or letting existing orders drain), which is trivial and low-cost for an attacker who wants to keep spot price artificially depressed while continuing to buy blockspace.

### Recommendation
Fix the decreasing branch to mirror the increasing branch's structure, centering the multiplier at `1`, e.g.:
```rust
let new_traffic = One::one()
    .saturating_sub(var_times_qud)   // use the variability-scaled diff, matching the doc's intent
    .saturating_add(div_by_two)
    .saturating_mul(traffic);
```
Also verify the increasing branch uses `var_times_qud` (variability-scaled) rather than the raw `queue_util_diff`, consistent with the documented `p/(k*(1-s))` variability semantics, and add regression tests with `diff < 1` and `variability < 100%` to catch this class of asymmetry before merge.

### Proof of Concept
1. Configure `on_demand_target_queue_utilization = 50%`, `on_demand_fee_variability = 100%`, `on_demand_queue_max_size = 100`.
2. Drive `traffic` up via congestion (queue full) to some elevated value, e.g. `traffic = 100`.
3. Let the queue drain to `queue_size = 40` (i.e., 40% utilization, `diff = 10% = 0.1`, below target so the negative branch executes).
4. Compute: `var_times_qud = 0.1`, `div_by_two ≈ 0.005`.
   - Buggy code: `new_traffic = (0.1 − 0.005) * 100 ≈ 9.5` — a ~90% instantaneous collapse in a single block for only a 10% under-utilization.
   - Intended behavior: `new_traffic = (1 − 0.1 + 0.005) * 100 ≈ 90.5` — a mild ~10% reduction.
5. `spot_price = traffic * on_demand_base_fee` is now ~10x cheaper than intended after a single mildly-under-target block, letting any account place on-demand orders at a fraction of the price the congestion-pricing mechanism was designed to enforce. [6](#0-5)

fn spot_traffic_can_decrease() {
