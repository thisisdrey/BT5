Target: `WalletImpl::execute_signed` / `RequestMessage.timeout` field. Attacker action: relay (as a permissionless relayer) a signed `RequestMessage` whose `msg.timeout` is set by the signer to a very large value while wallet's own `self.0.nonces.timeout()` (the wallet's configured `timeout`) is smaller, and delay submission until `created_at` is outside the wallet's own window but inside `msg.timeout`. Preconditions: signer signed with `msg.timeout` larger than wallet.timeout. Call sequence: `commit` computes `now - self.timeout.min(timeout) <= created_at <= now` — uses the *minimum* of the two timeouts. Binding: the effective validity window used at commit == min(wallet.timeout, msg.timeout), never the signer-chosen larger value alone. Impact: High, a stale/expired-per-owner-intent request executing later than the owner intended could reach a locked/rotated key state. Proof idea: cargo test asserting `NonceError::ExpiredOrFuture` when `created_at` predates `now - wallet.timeout` even though `msg.timeout` alone would have allowed it.
