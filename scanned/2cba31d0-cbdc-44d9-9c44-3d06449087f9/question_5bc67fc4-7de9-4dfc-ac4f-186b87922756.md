In `ft_resolve_withdraw` (contracts/defuse/src/contract/tokens/nep141/withdraw.rs, `impl FungibleTokenWithdrawResolver for Contract`), an attacker who owns the FT contract named in `FtWithdraw::token` implements `ft_transfer_call` to always succeed but silently keep the tokens (never actually transferring value to `receiver_id`), while returning a small `U128` `used` value so most of `amount` is refunded back via `self.deposit`; preconditions: attacker has `auth_by_predecessor_id` enabled account with `token_balances` credit for `token`; call sequence: `ft_withdraw` -> `internal_ft_withdraw` debits via `self.withdraw` -> `do_ft_withdraw` calls attacker's `ft_transfer_call` -> `ft_resolve_withdraw` reads `promise_result_checked_json::<U128>(0)` and trusts attacker-returned `used`; binding that breaks: `used_reported_by_callee == tokens_actually_leaving_Verifier_custody`; scoped impact: Critical, attacker gets both the refund credit and the real off-chain tokens since the callee controls the only source of truth for `used`; proof idea: cargo test with a stub token contract returning `used=0` from `ft_transfer_call` while actually keeping/moving the real asset, asserting SETTLEMENT (`amount.0 == used + refund`) still 'holds' internally but does not reflect real custody.
