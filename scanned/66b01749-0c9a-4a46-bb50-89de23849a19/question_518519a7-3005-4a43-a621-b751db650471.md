In ReceiptSinkV2::forward_from_buffer_to_shard, num_forwarded (raw buffer pop_n count) is computed by counting every forwarded receipt, while outgoing_metadatas_updates only accumulates entries for receipts where should_update_outgoing_metadatas() is true. Can an attacker craft a mixed sequence of receipts (some metadata-tracked, some not) to the same receiver shard such that the ordering assumption inside ReceiptGroupsQueue::update_on_receipt_popped (which always pops from the logical front group) desyncs from the physical order receipts are removed from OutgoingReceiptBuffer via pop_n, so metadata group boundaries no longer correspond to actual buffered receipts? Preconditions: funded account able to produce receipts of at least two different should_update_outgoing_metadatas() kinds (e.g. action receipt vs PromiseYield/data receipt) to the same target shard. Sequence: buffer_receipt(kind A, tracked), buffer_receipt(kind B, not tracked), buffer_receipt(kind A, tracked); drain all three in one forward_from_buffer_to_shard call. Invariant: value conservation (metadata group sizes equal sum of tracked receipt sizes in FIFO order). Impact: state-root divergence between nodes if any downstream logic (bandwidth request generation) assumes group order equals buffer order for every receipt including untracked ones. Proof: differential test comparing ReceiptGroupsQueue group contents against an in-memory oracle that only tracks the 'tracked' subset in buffer order.
