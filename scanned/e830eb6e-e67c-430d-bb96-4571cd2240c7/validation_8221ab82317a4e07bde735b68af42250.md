Based on my research, the closest verifiable local analog to the Compound "silent mint failure not causing revert" issue is in `pallet-accumulate-and-forward`'s XCM `Forwarder` implementation, where a local operation is treated as fully successful based only on local execution status, while the corresponding remote effect (the actual "mint"/credit at the destination) is never confirmed.

### Title
Irrecoverable burn-without-mint on remote XCM rejection in `TeleportForwarderForAccountId32::forward` - (File: `polkadot/xcm/xcm-builder/src/forwarder.rs`)

### Summary
`pallet_accumulate_and_forward` periodically forwards pooled native-token balance from a local accumulation account to a destination chain via `T::Forwarder::forward`, implemented by `TeleportForwarderForAccountId32::forward` [1](#0-0) . This implementation burns the source's balance locally (via `WithdrawAsset`) and teleports it to a destination beneficiary via `InitiateTransfer`, but only checks the *local* XCM `Outcome` to decide whether to commit the burn [2](#0-1) . `Outcome::Complete` only certifies that the outbound message was validated and queued for delivery — it says nothing about whether the destination chain will successfully execute `ReceiveTeleportedAsset → AliasOrigin → DepositAsset`. If the destination-side execution fails, the assets are trapped remotely, while locally the burn (and the corresponding reduction of `total_issuance`) has already been irreversibly committed.

### Finding Description
`forward()` wraps the whole operation in `with_transaction`, committing only when `XcmExecutor::prepare_and_execute` returns `Outcome::Complete` [3](#0-2) . This correctly rolls back local storage if *local* preparation/dispatch fails. However, `Outcome::Complete` here reflects only successful local processing of the `UnpaidExecution`/`WithdrawAsset`/`InitiateTransfer` instructions — i.e. that the outbound XCM was validated and successfully enqueued in the router. It does not, and cannot, reflect whether the remote chain will successfully execute the appended `remote_xcm` (`ReceiveTeleportedAsset`, `AliasOrigin(source)`, `UnpaidExecution`, `DepositAsset` to `StagingLocation`) [4](#0-3) .

The doc comment on the adapter itself acknowledges this gap: "Once the local executor reports success, the message is queued and any destination-side rejection results in trapped assets at the destination with no automatic recovery path" [5](#0-4) . The pallet's crate-level docs confirm the accounting assumption that is violated when this happens: "Accumulated funds are burnt upon forwarding (reducing `total_issuance` here) and the same funds are minted at the destination when the sent message is received" [6](#0-5) .

In `on_idle`, once `forward()` returns `Ok(())`, the pallet unconditionally emits `ForwardSucceeded` and considers the funds delivered — there is no retry, no pending-transfer bookkeeping, and no way to detect or recover from destination-side rejection [1](#0-0) . This is structurally the same defect class as the Compound `mint()` bug: a caller treats a callee's local, non-reverting "success" signal as proof that the entire intended state transition (crediting the beneficiary) has occurred, when in fact a downstream step can fail independently without rolling back the already-committed side effect (the burn).

### Impact Explanation
Any destination-side rejection of the remote `DepositAsset`/`AliasOrigin` (e.g. filters, weight limits, an unfunded/below-ED beneficiary account, or asset registration issues on the destination) causes: (1) `total_issuance` on the source chain to be permanently reduced (funds burned) with no corresponding credit ever reaching the `StagingLocation` beneficiary, and (2) the teleported assets to be trapped at the destination chain, recoverable in principle only via a manual `ClaimAsset`/governance path (out of scope per the "no automatic recovery" note). This is a genuine, permanent value-destruction/fund-lock scenario, matching "permanent user-fund or bridge-state lock" and violating the invariant that balances "must conserve value and settle exactly once to the rightful beneficiary."

### Likelihood Explanation
This code path runs unconditionally and periodically via `on_idle` on every system chain configuring `pallet_accumulate_and_forward` (bridge-hub-westend, collectives-westend, coretime-westend, people-westend, westend relay) [7](#0-6) . No attacker action or privileged actor is required to trigger the underlying gap — any transient destination-side condition (congestion, filter misconfiguration, an unfunded/removed beneficiary account) that causes the remote XCM to fail after the local burn has already been committed will reproduce it. The existing test suite explicitly validates only the *local*-failure rollback path (`forward_rolls_back_balance_and_issuance_on_xcm_failure`) [8](#0-7)  and does not cover destination-side rejection, confirming the gap is untested and unmitigated.

### Recommendation
Do not treat local `Outcome::Complete` as final settlement. Either (a) hold the burned funds in an intermediate/escrow state with a receipt that is only cleared upon a confirmed remote acknowledgement (e.g. a `QueryResponse`/receipt XCM from the destination) before finalizing the burn/`total_issuance` reduction, or (b) keep a local pending-transfer record so that trapped-asset scenarios can be automatically or governance-recoverable and reflected in accounting, rather than emitting `ForwardSucceeded` based solely on local queuing.

### Proof of Concept
1. Configure `AssetHub` (or whichever `Dest`) such that the `StagingLocation` beneficiary account is filtered/blocked or below ED (e.g., account reaped or barrier disallows `DepositAsset` for that origin).
2. Let `pallet_accumulate_and_forward::on_idle` trigger at a `TransferPeriod` boundary with `available_funds >= MinTransferAmount`.
3. `TeleportForwarderForAccountId32::forward` executes locally: `WithdrawAsset` burns from the accumulation account, `InitiateTransfer` is validated and enqueued — `XcmExecutor::prepare_and_execute` returns `Outcome::Complete`, so `with_transaction` commits the burn.
4. The remote chain executes `ReceiveTeleportedAsset → AliasOrigin → DepositAsset`; `DepositAsset` fails due to the blocked/underfunded beneficiary — assets are trapped remotely per XCM's standard AssetTrap mechanism.
5. Locally, `Event::ForwardSucceeded` was already emitted and `total_issuance` permanently reduced; no record exists to reconcile, retry, or recover the lost value.

	fn forward(source: AccountId, amount: Balance) -> Result<(), ()> {
		let dest = Dest::get();
		let asset = Asset { id: AssetId(NativeAsset::get()), fun: Fungible(amount.into()) };
		let beneficiary: Location = StagingLocation::get().into_location();

		let remote_xcm = Xcm(vec![DepositAsset { assets: Wild(AllCounted(1)), beneficiary }]);

		// The XCM flow: `ReceiveTeleportedAsset → AliasOrigin(source) → UnpaidExecution →
		// DepositAsset`. `preserve_origin: true` causes `InitiateTransfer` to prepend
		// `AliasOrigin(source_location)` to the remote XCM.
		let xcm: Xcm<XcmConfig::RuntimeCall> = Xcm(vec![
			UnpaidExecution { weight_limit: WeightLimit::Unlimited, check_origin: None },
			DescendOrigin(Junction::AccountId32 { network: None, id: source.into() }.into()),
			WithdrawAsset(asset.into()),
			InitiateTransfer {
				destination: dest,
				remote_fees: None,
				preserve_origin: true,
				assets: BoundedVec::truncate_from(alloc::vec![AssetTransferFilter::Teleport(
					Wild(AllCounted(1))
				),]),
				remote_xcm,
			},
		]);

/// Verify that when the XCM router fails (simulating a mid-program failure after `WithdrawAsset`
/// has debited the source account), `forward` rolls back all storage changes via
/// `with_transaction`. Both the source balance and total issuance must remain unchanged.
#[test]
fn forward_rolls_back_balance_and_issuance_on_xcm_failure() {
	let source: AccountId = AccountId32::from([1u8; 32]);
	let initial_balance = 1_000u128;

	new_test_ext(source.clone(), initial_balance).execute_with(|| {
		let initial_issuance = Balances::total_issuance();

		ROUTER_SHOULD_FAIL.with(|f| f.set(true));
		let result = TeleportForwarderForAccountId32::<
			TestXcmConfig,
			AssetHubLocation,
			HereLocation,
			AccumulationInterior,
		>::forward(source.clone(), 500u128);
		ROUTER_SHOULD_FAIL.with(|f| f.set(false));

		assert!(result.is_err(), "expected forward to fail when router fails");
		assert_eq!(
			Balances::balance(&source),
			initial_balance,
			"source balance must be unchanged after XCM failure"
		);
		assert_eq!(
			Balances::total_issuance(),
			initial_issuance,
			"total issuance must be unchanged after XCM failure"
		);
	});
