Based on my research, I identified a concrete local analog to the OTP weak-authentication bug class in the `sc-hop` module: the `hop_claim` and `hop_ack` RPC methods verify recipient identity purely via cryptographic signature and hold no per-account rate limiting, unlike `hop_submit`, which explicitly says the same RPC-level rate limiter applies to all methods but only `submit()` actually calls `self.rate_limiter.check(...)`.

### Title
Missing rate limiting on `hop_claim`/`hop_ack` recipient-signature verification enables unbounded free crypto-cost DoS and blob exfiltration probing - (File: `substrate/client/hop/src/pool.rs`)

### Summary
`HopDataPool::claim` and `HopDataPool::ack` [1](#0-0)  verify a caller-supplied `MultiSignature` against every recipient key on an entry via `find_recipient_idx`, but neither path calls into `self.rate_limiter` at all — the `RateLimiter` (`rate_limit.rs`) is only invoked from `insert()` (the `hop_submit` path) [2](#0-1) . The README explicitly documents "per-account rate limiting" as a HOP-specific mitigation layered on top of the node's generic `--rpc-rate-limit` [3](#0-2) , but that HOP-specific limiter is not wired to `claim`/`ack`.

### Finding Description
`hop_claim(hash, signature)` and `hop_ack(hash, signature)` are unauthenticated, unsigned-origin JSON-RPC calls (no signer identity is required up front — unlike `submit`, which is gated by `can_account_promote` before signature verification). Any caller can invoke these with an arbitrary `hash` and an arbitrary `signature` blob. `find_recipient_idx` decodes the signature and then iterates `meta.recipients`, calling `multi_sig.verify(...)` against every recipient's public key for that entry [4](#0-3) . For an entry submitted with up to `MAX_RECIPIENTS` = 256 keys [5](#0-4) , a single unauthenticated RPC call forces the node to perform up to 256 signature verifications.

Because there is no HOP-level, per-account rate limiter on `claim`/`ack` (unlike `submit`, which is explicitly rate-limited before any crypto work is done — see the "Size and authorization are both checked before signature verification" note [6](#0-5) ), an attacker can flood `hop_claim`/`hop_ack` with garbage signatures against known or guessed content hashes to force unbounded, free, per-request asymmetric-crypto work on the collator. This mirrors the OTP report's core defect exactly: a verification gate (OTP code / signature) that is checked repeatedly with no per-account throttling, letting an attacker hammer the check at will. The only generic protection is the node-wide `--rpc-rate-limit`, which throttles by connection, not by account/content, so a botnet of connections bypasses it while still saturating a single collator's CPU with crypto work per request — exactly the "no rate limiting on the OTP verification endpoint" failure mode from the source report, but landing on a collator's block-production-critical resource instead of an email code.

### Impact Explanation
`sc-hop` runs inside the collator/node process alongside block authoring. Unbounded signature-verification churn per unauthenticated RPC call is a public, underpriced-work vector that can degrade block production on the affected collator (CPU starvation), which falls squarely within the in-scope "public underpriced work that degrades block production or stalls bridge processing" category. It does not require a malicious peer, validator, or leaked key — any external RPC client can trigger it.

### Likelihood Explanation
High: `hop_claim`/`hop_ack` are public, no-privilege JSON-RPC methods reachable by any client once `--enable-hop` is set; hashes for many entries are learnable (content-addressed, and senders/recipients routinely need to communicate hashes out-of-band) or can simply be probed since `find_recipient_idx` runs for any submitted hash. Repeated calls with garbage 256-recipient entries maximize verification cost per call with zero fee and zero HOP-side throttling.

### Recommendation
Apply the same per-account/per-connection HOP `RateLimiter` token-bucket check used in `insert()` to `claim()` and `ack()` before performing any `MultiSignature::verify` work, and/or cap verification cost by rejecting once a fixed number of recipient-signature checks have failed within a time window per caller/IP.

### Proof of Concept
1. Enable `--enable-hop` on a target collator.
2. Submit one entry via `hop_submit` with the maximum 256 recipients (any distinct valid `MultiSigner` keys) and small data, paying the `hop_submit` rate-limit cost once.
3. Repeatedly call `hop_claim(hash, signature)` (or `hop_ack`) with the same `hash` and a freshly-generated, invalid `MultiSignature` each time. Each call triggers up to 256 signature verifications in `find_recipient_idx` [7](#0-6) .
4. Because `claim`/`ack` never call `self.rate_limiter.check` (grep of `pool.rs` shows the only call site is inside `insert`) [8](#0-7) , repeat step 3 as fast as the node-global `--rpc-rate-limit` allows (or from multiple connections/IPs to bypass that too), sustaining continuous 256x-signature-verification load per request indefinitely at no cost, degrading the collator's block production.

Note: I could not fully trace `rate_limit.rs`'s internals or `runtime_api.rs`/`types.rs` in this pass due to iteration limits; if `RateLimiter::check` is somehow invoked indirectly elsewhere (e.g., wrapped at the RPC layer outside `pool.rs`), that would need to be re-verified, but `rpc.rs`'s `claim`/`ack` implementations call `self.pool.claim`/`self.pool.ack` directly with no rate-limit call in between [9](#0-8) , confirming the gap.

	fn find_recipient_idx(
		meta: &HopEntryMeta,
		hash: &HopHash,
		signature: &[u8],
		context: &[u8],
	) -> Result<usize, HopError> {
		let multi_sig =
			MultiSignature::decode(&mut &signature[..]).map_err(|_| HopError::InvalidSignature)?;
		let payload = signing_payload(context, hash);

		meta.recipients
			.iter()
			.position(|r| multi_sig.verify(&payload[..], &r.signer.clone().into_account()))
			.ok_or(HopError::NotRecipient)
	}
```

	pub fn claim(&self, hash: &HopHash, signature: &[u8]) -> Result<Vec<u8>, HopError> {
		{
			let index = self.index.lock();
			let meta = index.get(hash).ok_or(HopError::NotFound)?;
			// Map NotRecipient → NotFound so callers cannot probe whether a hash
			// exists by observing different error codes.
			let idx = Self::find_recipient_idx(meta, hash, signature, HOP_CLAIM_CONTEXT)
				.map_err(|_| HopError::NotFound)?;

			// If this recipient already acked, the data may be gone.
			if meta.recipients[idx].claimed {
				return Err(HopError::AlreadyClaimed);
			}
		}
		// Read blob from disk and verify its content hash. May be gone if
		// concurrently acked and deleted, in which case we surface NotFound.
		self.read_and_verify_blob(hash)
	}

	/// Acknowledge receipt of claimed data. Marks the recipient as claimed and triggers
	/// cleanup when all recipients have acked.
	///
	/// Idempotent: acking a recipient that already acked returns `Ok(())`.
	pub fn ack(&self, hash: &HopHash, signature: &[u8]) -> Result<(), HopError> {
		// Phase 1: idempotent fast path under read lock.
		{
			let index = self.index.lock();
			let meta = index.get(hash).ok_or(HopError::NotFound)?;
			let idx = Self::find_recipient_idx(meta, hash, signature, HOP_ACK_CONTEXT)
				.map_err(|_| HopError::NotFound)?;
			if meta.recipients[idx].claimed {
				return Ok(());
			}
		}

		// Phase 2: re-run the lookup against the current meta — the entry could
		// have been removed and re-submitted with a different recipient list since Phase 1.
		let mut index = self.index.lock();
		let meta = index.get_mut(hash).ok_or(HopError::NotFound)?;
		let idx = Self::find_recipient_idx(meta, hash, signature, HOP_ACK_CONTEXT)
			.map_err(|_| HopError::NotFound)?;

		if meta.recipients[idx].claimed {
			return Ok(());
		}
```
