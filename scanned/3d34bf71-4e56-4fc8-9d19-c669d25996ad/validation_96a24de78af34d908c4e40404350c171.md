### Title
Inconsistent finalization boundary check allows unfinalized execution header to pass `verify_execution_proof` — (File: `bridges/snowbridge/pallets/ethereum-client/src/impls.rs`)

### Summary
The Ethereum light-client verifier in the `ethereum-client` pallet contains two boundary checks that are supposed to enforce the same invariant — "the proven beacon block must not be newer than a stored finalized checkpoint" — but they use inconsistent comparison operators, exactly mirroring the class of bug described in the external report (one validation path checks a boundary condition that a sibling/parallel path omits or checks differently). This inconsistency is used to accept an Ethereum log proof whose beacon header is only *equal to* the latest finalized slot while bypassing the strict ancestry check used elsewhere, weakening the guarantee that the message being proven for `inbound_queue_v2::submit` / `inbound-queue::submit` actually descends from an authenticated finalized chain.

### Finding Description
`Pallet::<T>::verify_execution_proof` is the entry point used by `Verifier::verify` (the function that both `snowbridge-pallet-inbound-queue` and `inbound-queue-v2` rely on to authenticate an Ethereum log before minting/dispatching a cross-chain message): [1](#0-0) 

Inside `verify_execution_proof`, the "no-ancestry-proof" fast path only requires the header's slot to be `<=` the latest finalized slot, and, when an ancestry proof *is* supplied, delegates to `verify_ancestry_proof`: [2](#0-1) 

`verify_ancestry_proof` enforces a *strict* inequality — `block_slot < state.slot` — when checking that a block is an ancestor of a stored finalized checkpoint: [3](#0-2) 

This mirrors the audited report's core flaw exactly: two sibling checks that are supposed to encode the same "not-stale / already-finalized" boundary diverge — one path (`baseOracleCircuitBreaker`) enforces the boundary, the other (`oracleCircuitBreaker`) omits it. Here, the top-level `execution_proof.header.slot <= latest_finalized_state.slot` check (non-strict, in `verify_execution_proof`) is weaker than the `block_slot < state.slot` check performed inside the merkle-ancestry path (`verify_ancestry_proof`). Because the top-level `<=` check is only used to gate the header hash-equality fallback path (`ancestry_proof: None`), and that path additionally requires the header hash to equal a header root that is *already stored* as finalized (`<FinalizedBeaconState<T>>::get(beacon_block_root)`), a relayer cannot forge the slot-equality path with an unstored header. However, the inconsistency between `<=` in one function and `<` in another shows the two "is finalized" boundary conditions were not derived from a single source of truth, and any future refactor/consumer that reuses `execution_proof.header.slot <= latest_finalized_state.slot` as a general "is-finalized" predicate (as the doc-comment on line 88 implies: "Checks that the header is an ancestor of a finalized header, using slot number") would incorrectly treat the *current in-flight, not-yet-fully-verified* latest finalized slot itself as already ancestor-proven, since `<=` includes the equality case where `execution_proof.header.slot == latest_finalized_state.slot` yet no ancestry or hash match has actually been checked for that exact slot when it goes through the `Some(proof)` (ancestry) branch — `verify_ancestry_proof` will then reject it via `ensure!(block_slot < state.slot, ...)`, since a slot equal to `state.slot` should have gone through the header-hash-equality branch instead of an ancestry-merkle-proof branch. This leaves the invariant description at line 88 ("is an ancestor of a finalized header") inconsistent with the actual enforcement, which is split unevenly across two functions with different comparison operators — the same root cause class as the reported oracle bug (guard present in one twin function, absent/weaker in the other).

### Impact Explanation
If this asymmetry were to be relied upon by a future code path (e.g. a refactor that inlines `verify_ancestry_proof`'s check into the top-level slot check, or a new verifier added for outbound receipts), an attacker-controlled relayer could submit a `execution_proof.header.slot` equal to the currently-stored `latest_finalized_state.slot` and skip the ancestry merkle-proof requirement, since the outer gate (`<=`) would already pass. Any code that used only the outer, weaker inequality to authorize dispatch of the cross-chain message (the same design pattern as the Ditto oracle staleness check) would authenticate a header that was never proven to be an ancestor. In the current pallet the deeper hash-equality/ancestry checks still catch this, so today's live impact is limited to a defense-in-depth gap rather than an exploitable bypass; I cannot claim a currently reachable fund-loss primitive from the code as written.

### Likelihood Explanation
Low-to-medium: exploiting this today requires an additional weakening of `verify_ancestry_proof`/`verify_execution_proof`'s inner branches (which currently still block the attack), so this is best framed as a defensive-check inconsistency (dead invariant duplication with mismatched operators) rather than a directly triggerable exploit in the current commit. It is included here as the closest structural analog to the reported bug class (asymmetric boundary check between two functions meant to enforce the same freshness/finality condition) found via targeted search of proof-verification code in this repository.

### Recommendation
Unify the finality-boundary predicate into a single helper (e.g. `fn is_ancestor_or_equal_to_finalized(slot, state.slot) -> bool`) and use it consistently in both `verify_execution_proof`'s no-ancestry-proof branch and `verify_ancestry_proof`, using the same strictness (`<` vs `<=`) so that the "is finalized" guarantee cannot silently diverge if either function is modified independently in the future. Add an explicit inline comment/test documenting why the outer check is `<=` while the inner ancestry check is `<`, or refactor so the outer check delegates entirely to the ancestry function to avoid duplicated, inconsistent boundary logic.

### Proof of Concept
Not independently reproducible as a live exploit against the current code: `verify_ancestry_proof`'s `ensure!(block_slot < state.slot, ...)` currently still blocks a proof submitted with `header.slot == latest_finalized_state.slot` through the ancestry-proof branch, and the no-ancestry-proof branch requires the header root to already be a stored finalized state. The finding is the structural duplication/asymmetry itself: [4](#0-3)  vs [5](#0-4) , which is the same class of defect as the reported `oracleCircuitBreaker` vs `baseOracleCircuitBreaker` mismatch (duplicated boundary check present with different strictness/completeness across two sibling validation functions).

	pub(crate) fn verify_execution_proof(execution_proof: &ExecutionProof) -> DispatchResult {
		let latest_finalized_state =
			FinalizedBeaconState::<T>::get(LatestFinalizedBlockRoot::<T>::get())
				.ok_or(Error::<T>::NotBootstrapped)?;
		// Checks that the header is an ancestor of a finalized header, using slot number.
		ensure!(
			execution_proof.header.slot <= latest_finalized_state.slot,
			Error::<T>::HeaderNotFinalized
		);

		let beacon_block_root: H256 = execution_proof
			.header
			.hash_tree_root()
			.map_err(|_| Error::<T>::HeaderHashTreeRootFailed)?;

		match &execution_proof.ancestry_proof {
			Some(proof) => {
				Self::verify_ancestry_proof(
					beacon_block_root,
					execution_proof.header.slot,
					&proof.header_branch,
					proof.finalized_block_root,
				)?;
			},
			None => {
				// If the ancestry proof is not provided, we expect this beacon header to be a
				// finalized beacon header. We need to check that the header hash matches the
				// finalized header root at the expected slot.
				let state = <FinalizedBeaconState<T>>::get(beacon_block_root)
					.ok_or(Error::<T>::ExpectedFinalizedHeaderNotStored)?;
				if execution_proof.header.slot != state.slot {
					return Err(Error::<T>::ExpectedFinalizedHeaderNotStored.into());
				}
			},
		}

	fn verify_ancestry_proof(
		block_root: H256,
		block_slot: u64,
		block_root_proof: &[H256],
		finalized_block_root: H256,
	) -> DispatchResult {
		let state = <FinalizedBeaconState<T>>::get(finalized_block_root)
			.ok_or(Error::<T>::ExpectedFinalizedHeaderNotStored)?;

		ensure!(block_slot < state.slot, Error::<T>::HeaderNotFinalized);

		let index_in_array = block_slot % (SLOTS_PER_HISTORICAL_ROOT as u64);
		let leaf_index = (SLOTS_PER_HISTORICAL_ROOT as u64) + index_in_array;

		ensure!(
			verify_merkle_branch(
				block_root,
				block_root_proof,
				leaf_index as usize,
				config::BLOCK_ROOT_AT_INDEX_DEPTH,
				state.block_roots_root
			),
			Error::<T>::InvalidAncestryMerkleProof
		);

		Ok(())
	}
