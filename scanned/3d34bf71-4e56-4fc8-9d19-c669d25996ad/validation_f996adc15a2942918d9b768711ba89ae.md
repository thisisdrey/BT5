## Analysis

The GMX bug's core broken invariant: *when a swap is invoked to convert a user's asset into an expected output, and no minimum-output/slippage bound is enforced, the user can receive an amount far below what the operation implies, and the code proceeds anyway rather than reverting.*

The direct local analog is in the Snowbridge `system-frontend` pallet's tip/fee conversion path, which swaps a user-supplied asset for Ether via `pallet_asset_conversion::Swap` with slippage protection explicitly disabled. [1](#0-0) 

### Title
Snowbridge `system-frontend` pallet swaps tip/fee assets for Ether with no minimum-output (slippage) protection - ([File: bridges/snowbridge/pallets/system-frontend/src/lib.rs])

### Summary
`Pallet::<T>::swap_and_burn` calls `T::Swap::swap_exact_tokens_for_tokens` with `amount_out_min` hard-coded to `None`, meaning the AMM swap of a user's tip/fee asset into Ether can execute at an arbitrarily bad price without reverting, before the resulting (possibly heavily discounted) Ether amount is burned and reported to Ethereum as the tip/registration fee value.

### Finding Description
`swap_and_burn` is invoked from `swap_fee_asset_and_burn`, which is called by the public extrinsics `register_token` and `add_tip`: [2](#0-1) [3](#0-2) 

The actual swap call:
```rust
let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
    who.clone(),
    swap_path,
    tip_amount,
    None, // No minimum amount required
    who,
    true,
)?;
``` [4](#0-3) 

Compare this to `pallet_asset_conversion`'s own `do_swap_exact_tokens_for_tokens`, whose entire purpose for the `amount_out_min` parameter is to guarantee the caller doesn't get less than they expect and to `ensure!(amount_out >= amount_out_min, ...)` before committing the swap: [5](#0-4) 

By passing `None`, `system-frontend` deliberately bypasses this guard. This is exactly the GMX pattern: the code path that converts one asset into another for onward use (there: PnL payout; here: tip/registration-fee conversion to Ether for bridging) is not bound by any minimum-acceptable-output check, so it "succeeds" and proceeds even when the AMM price is unfavorable — whether due to low pool liquidity, large trade-relative-to-reserve price impact, or a sandwich/front-run of the pool immediately before this swap. The result, `ether_gained`, is then burned via `burn_for_teleport` and encoded directly into a `RegisterToken`/`AddTip` XCM `Transact` call sent to the Ethereum-system pallet on BridgeHub, i.e., it becomes the recorded value transferred/tipped cross-chain: [6](#0-5) [7](#0-6) 

Unlike other swap consumers in the codebase (e.g. `asset-conversion-tx-payment`'s `withdraw_fee`/`correct_and_deposit_fee`, which always quote a minimum via `quote_price_*` and check it, or revert/merge-back on failure — see the `swap_tokens_for_exact_tokens` calls at lines 159-176 and 283-317 of `payment.rs`) — this call site has no minimum bound at all, so there is no existing guard to catch this class of loss.

### Impact Explanation
A user's entire withdrawn `tip_amount`/`fee_amount` is irrevocably consumed by the swap and burned for teleport regardless of how little Ether it converts to. Because `amount_out_min` is `None`:
- A thinly-liquid or freshly-created pool for the tip asset/Ether pair can yield a tiny `ether_gained` relative to the tip asset's real value, with the extrinsic still succeeding.
- The user has no way to bound their downside — the transaction cannot be made to fail based on unfavorable execution price, unlike the corresponding `pallet_asset_conversion` extrinsics which always support `amount_out_min`.
- Because the swap and burn happen atomically inside one publicly-callable extrinsic (`register_token`, `add_tip`), there's no user-supplied slippage parameter to opt out of this risk.

This causes value loss to the calling user, functionally identical to the GMX finding: "a user will get back fewer [output units] than they expect... if there was a large price impact."

### Likelihood Explanation
`register_token` and `add_tip` are unrestricted public entry points (any signed origin, or the location-scoped origin for `register_token`) that unconditionally trigger this swap whenever the supplied fee/tip asset isn't already the target Ether-equivalent asset: [8](#0-7) [9](#0-8) 

No privileged actor, relayer, or governance intervention is required — any unprivileged caller supplying a non-Ether tip/fee asset against a pool with low liquidity (or one they can manipulate immediately before their own call within the same block/extrinsic-ordering) triggers the unbounded-slippage swap.

### Recommendation
Add a `min_ether_out` (or equivalently derive a bound from a pre-swap quote via `QuotePrice`) parameter to `swap_and_burn`/`swap_fee_asset_and_burn`, and pass it as `Some(min_ether_out)` to `T::Swap::swap_exact_tokens_for_tokens`, causing the call to revert (`Error::<T>::ProvidedMinimumNotSufficientForSwap` from the swap pallet) rather than silently accepting an unfavorable rate — mirroring the pattern already used in `pallet-asset-conversion-tx-payment`'s `withdraw_fee`, which quotes price before withdrawing/swapping.

### Proof of Concept
1. Configure/observe a low-liquidity pool for `(tip_asset, EtherLocation)` in `T::Swap`'s backing `pallet_asset_conversion` instance.
2. Call `SnowbridgeSystemFrontend::add_tip(origin, message_id, asset)` where `asset` is the low-liquidity tip token with a non-trivial amount.
3. Internally, `swap_fee_asset_and_burn` → `swap_and_burn` invokes:
   ```rust
   T::Swap::swap_exact_tokens_for_tokens(who, swap_path, tip_amount, None, who, true)
   ```
   with no floor on the output. Because of AMM constant-product pricing, a large `tip_amount` relative to the pool's Ether reserve yields disproportionately little `ether_gained` (compare to `do_swap_exact_tokens_for_tokens`'s `amount_out_min` check which would have reverted such a trade at `substrate/frame/asset-conversion/src/lib.rs:997-1002`).
4. The extrinsic succeeds; `ether_gained` (far below the tip asset's fair value) is burned via `burn_for_teleport` and encoded into the `AddTip` XCM `Transact` message sent to BridgeHub — the caller has irreversibly lost the difference in value with no on-chain recourse, exactly mirroring the GMX "slippage not respected on swap" finding.

		fn swap_and_burn(
			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether
			let ether_asset = Asset::from((ether_location.clone(), ether_gained));

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}
