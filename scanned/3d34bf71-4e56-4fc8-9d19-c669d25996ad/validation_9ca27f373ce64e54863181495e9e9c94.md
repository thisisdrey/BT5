### Title
Coretime Region partition lets the seller keep the traded `RegionId` while shifting nearly all its value to a newly minted ID - (File: `substrate/frame/broker/src/dispatchable_impls.rs`)

### Summary
`pallet-broker` exposes Coretime Regions as an NFT-like asset (`Inspect`/`Transfer`/`Mutate` for `nonfungible`, keyed by `RegionId` encoded as a `u128` item id). The `partition` extrinsic lets the *owner* split a Region into two new Regions at an arbitrary time pivot. Exactly as in the OTC lockup-plan bug report, one of the two resulting pieces **keeps the original `RegionId`** unchanged while the other piece is issued under a **brand-new `RegionId`**. An owner who has agreed to sell/settle a trade referencing a specific `RegionId` (e.g. via an OTC contract, marketplace listing, or XCM reserve-transfer expecting that item id) can, in the same block just before settlement, call `partition` with the smallest possible pivot (1 timeslice) so that the *old* `RegionId` now only represents a near-worthless sliver of the original duration, while almost the entire remaining duration/value moves to the freshly created `RegionId` that the buyer never agreed to receive.

### Finding Description
`do_partition` computes the split as: [1](#0-0) 

Note that `new_region_ids.0` is set to the **same `region_id`** passed in (same `begin`, `core`, `mask`), while `new_region_ids.1` is a **new** `RegionId` with `begin: pivot`. The only constraints are `pivot > region_id.begin` and `pivot < region.end`: [2](#0-1) 

So the minimum valid pivot offset is `1`, meaning the owner can shrink the *original* `RegionId`'s remaining record down to a single timeslice while the rest of the (potentially many-timeslice) duration is reassigned a new `RegionId`.

The `partition` dispatchable is public/unprivileged, gated only by ownership of the region (no root/governance needed): [3](#0-2) 

Regions are traded as NFT-like items keyed by `RegionId` (`ItemId = u128`), and ownership/attributes are looked up strictly by that id: [4](#0-3) 

This mirrors the external report's core broken invariant: a counter-party (buyer, marketplace escrow, or bridge/XCM reserve-transfer flow) that references a fixed item/plan id and assumes the record behind that id is stable for the duration of the trade window is not protected — the seller can locally reduce that specific id's value to almost nothing and move the real value to a new id, all within the same block as order fulfillment (batchable calls: `partition` immediately followed by `transfer`/settlement).

### Impact Explanation
Any protocol, escrow, OTC contract, or cross-chain transfer flow that treats a specific `RegionId` as a stable representation of "N timeslices of Coretime for account X" can be defrauded: the seller executes `partition(region_id, 1)` right before the trade executes, retains the valuable new-ID region, and delivers only a near-empty (1-timeslice) region under the originally-agreed `RegionId`. This is a direct theft/value-mismatch: the buyer pays full price and receives a functionally worthless asset, while the seller keeps essentially all of the underlying value under a different, unlisted id.

### Likelihood Explanation
The attack requires no privileged role, no validator/collator collusion, and no external infrastructure — only that the attacker owns the Region being traded and can batch two of their own signed extrinsics (`partition` then `transfer`/settlement) in one block, which is standard, permissionless behavior available to any signed account. The `partition` call has no cooldown, no minimum-duration retained-on-old-id guard, and no owner-neutral re-identification, so the exploit is trivially repeatable whenever a counter-party's protocol keys its escrow/settlement logic to a fixed `RegionId`.

### Recommendation
Do not let either resulting piece retain the pre-image `RegionId`. When splitting a Region via `partition` (and analogously `interlace`), assign **both** resulting pieces fresh `RegionId`s (e.g., derive both from a monotonically incremented salt/nonce or the pivot value for both halves) so that the original id is fully retired once a split occurs, and any external reference to the old id unambiguously fails (`UnknownRegion`) instead of resolving to a diminished remnant. This forces trade counter-parties to re-validate against a live id rather than silently accepting a shrunk record.

### Proof of Concept
1. Attacker purchases/owns a Region with `RegionId { begin: b, core: c, mask: m }` covering timeslices `[b, e)`, and lists/promises it in an OTC trade referencing this exact `RegionId`.
2. Buyer (or an escrow contract) prepares to pay for `RegionId { begin: b, core: c, mask: m }` expecting the full `[b, e)` duration.
3. In the settlement block, attacker submits (batched):
   - `Broker::partition(origin, region_id=RegionId{begin:b,core:c,mask:m}, pivot=1)` — per `do_partition` this creates `new_region_ids.0 = RegionId{begin:b,...}` (same id, now covering only `[b, b+1)`) and `new_region_ids.1 = RegionId{begin:b+1,...}` (new id, covering `[b+1, e)`), see `substrate/frame/broker/src/dispatchable_impls.rs:255-285`.
   - Immediately calls/accepts the trade settlement that transfers/pays for `RegionId{begin:b,...}` via `Pallet::transfer`/`do_transfer` (`substrate/frame/broker/src/nonfungible_impl.rs:49-53`), which succeeds because that id still exists in `Regions` storage — just now representing 1 timeslice instead of `e-b`.
4. Buyer receives the original `RegionId`, but `Inspect::attribute(region_id, b"length")` now returns `1` instead of the originally expected `e-b`, while the attacker retains `RegionId{begin:b+1,...}` holding the remaining `e-b-1` timeslices of value. [5](#0-4)

	pub(crate) fn do_partition(
		region_id: RegionId,
		maybe_check_owner: Option<T::AccountId>,
		pivot_offset: Timeslice,
	) -> Result<(RegionId, RegionId), Error<T>> {
		let status = Status::<T>::get().ok_or(Error::<T>::Uninitialized)?;
		let mut region = Regions::<T>::get(&region_id).ok_or(Error::<T>::UnknownRegion)?;

		if let Some(check_owner) = maybe_check_owner {
			ensure!(Some(check_owner) == region.owner, Error::<T>::NotOwner);
		}
		let pivot = region_id.begin.saturating_add(pivot_offset);
		ensure!(pivot < region.end, Error::<T>::PivotTooLate);
		ensure!(pivot > region_id.begin, Error::<T>::PivotTooEarly);

		region.paid = None;
		let new_region_ids = (region_id, RegionId { begin: pivot, ..region_id });

		// Remove this region from the pool in case it has been assigned provisionally. If we get
		// this far then it is still in `Regions` and thus could only have been pooled
		// provisionally.
		Self::force_unpool_region(region_id, &region, &status);

		// Overwrite the previous region with its new end and create a new region for the second
		// part of the partition.
		Regions::<T>::insert(&new_region_ids.0, &RegionRecord { end: pivot, ..region.clone() });
		Regions::<T>::insert(&new_region_ids.1, &region);
		Self::deposit_event(Event::Partitioned { old_region_id: region_id, new_region_ids });

		Ok(new_region_ids)
	}

impl<T: Config> Inspect<T::AccountId> for Pallet<T> {
	type ItemId = u128;

	fn owner(item: &Self::ItemId) -> Option<T::AccountId> {
		let record = Regions::<T>::get(RegionId::from(*item))?;
		record.owner
	}

	fn attribute(item: &Self::ItemId, key: &[u8]) -> Option<Vec<u8>> {
		let id = RegionId::from(*item);
		let item = Regions::<T>::get(id)?;
		match key {
			b"begin" => Some(id.begin.encode()),
			b"end" => Some(item.end.encode()),
			b"length" => Some(item.end.saturating_sub(id.begin).encode()),
			b"core" => Some(id.core.encode()),
			b"part" => Some(id.mask.encode()),
			b"owner" => Some(item.owner.encode()),
			b"paid" => Some(item.paid.encode()),
			_ => None,
		}
	}
}

impl<T: Config> Transfer<T::AccountId> for Pallet<T> {
	fn transfer(item: &Self::ItemId, dest: &T::AccountId) -> DispatchResult {
		Self::do_transfer((*item).into(), None, dest.clone()).map_err(Into::into)
	}
}
