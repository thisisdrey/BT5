In `SignedTonConnectPayload` (contracts/defuse/core/src/payload/ton_connect.rs), `verify()` recovers a public key from `self.signature` over `self.payload`, and `extract_defuse_payload()` independently parses `signer_id` out of the JSON `text` inside `TonConnectPayloadSchema::Text`. Can an attacker craft a `SignedTonConnectPayload` where `public_key` cryptographically verifies against `self.payload` but the embedded `DefusePayload.signer_id` names a *different* victim account, so that `execute_intents` executes intents attributed to `signer_id` while the actual signing key belongs to the attacker? Preconditions: victim `signer_id` account already holds `token_balances` inside the Verifier; attacker controls an Ed25519 keypair and crafts `TonConnectPayload{ payload: TonConnectPayloadSchema::Text{ text } }` where `text` is `{"signer_id":"victim.near",...}`. Call sequence: `MultiPayload::TonConnect(payload)` -> `execute_intents` -> `SignedPayload::verify` -> `ExtractDefusePayload::extract_defuse_payload`. Binding that must hold: the `(signer_id, public_key)` pair the engine authorises == the pair that actually produced `self.signature`. Impact: Critical, unauthorized balance move against victim's `token_balances`. Proof idea: cargo test asserting engine rejects when the recovered `public_key` is not a registered key of `signer_id`.
