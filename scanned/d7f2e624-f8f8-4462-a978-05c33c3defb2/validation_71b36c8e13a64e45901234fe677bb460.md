## Title
Silent payout failure due to `debug_assert!` on ignored `Currency::transfer` result in bounty/tips/society payout paths - (File: `substrate/frame/bounties/src/lib.rs`, `substrate/frame/child-bounties/src/lib.rs`, `substrate/frame/tips/src/lib.rs`, `substrate/frame/society/src/lib.rs`)

### Summary
The external report flags `Pool` operations that use raw ERC20 `transfer()` without checking the boolean return value, so a failing transfer is silently accepted and the contract proceeds as if funds moved. The direct Substrate analog is the pattern `let res = T::Currency::transfer(...); debug_assert!(res.is_ok());` used in several pallets' payout paths. `debug_assert!` is compiled out entirely in release builds (the build used in production chains), so the transfer's success/failure is never actually checked at runtime — the pallet unconditionally proceeds to finalize/remove the bounty/tip/payout record and emit a "paid" event regardless of whether the underlying `Currency::transfer` actually moved funds.

### Finding Description
In `pallet-bounties::claim_bounty` [1](#0-0) , any signed account can trigger the claim ("anyone can trigger claim" per the doc comment) once the bounty is `PendingPayout` and the unlock block has passed:
```
let res = T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath); // should not fail
debug_assert!(res.is_ok());
let res = T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath); // should not fail
debug_assert!(res.is_ok());
```
The function then unconditionally clears `Bounties`, removes `BountyDescriptions`, and emits `Event::BountyClaimed` with the intended `payout`/`beneficiary` [2](#0-1) , whether or not the transfer succeeded.

The identical pattern exists in `pallet-child-bounties::claim_child_bounty` [3](#0-2) , in `pallet-tips::payout_tip` [4](#0-3) , and in `pallet-society`'s `reserve_payout`/`unreserve_payout` helpers [5](#0-4) .

`Currency::transfer` (`pallet_balances`) can fail for reasons other than "insufficient balance," most notably when the destination account does not yet exist and the transferred amount is below `ExistentialDeposit` — this returns `Err` rather than creating an account with a sub-ED balance. Since `final_fee`/`payout`/tip amounts are computed dynamically (e.g. `balance.saturating_sub(fee)`, `T::TipFindersFee::get() * payout`), it is straightforward for the payout amount sent to a not-yet-existing beneficiary/curator/finder account to fall below ED. In `debug_assert!`-stripped release builds, that failure is invisible to the pallet: the funds remain stuck in the bounty/child-bounty/tip sub-account (which is then never referenced again once the storage entry is removed), while the chain state and events assert the payout succeeded.

### Impact Explanation
This causes permanent fund lock: the payout amount stays locked in an now-orphaned bounty/child-bounty/tip pallet sub-account (no code path revisits a removed bounty ID to retry payment), while state and events falsely indicate the beneficiary/curator/finder was paid. This matches the "permanent user-fund... lock" and "runtime bugs that compromise intended behavior" impact categories, and is reachable by any unprivileged signed account calling `claim_bounty`/`claim_child_bounty` (anyone can trigger the claim) once the payout is due — no admin, governance, or malicious-peer assumption is required.

### Likelihood Explanation
Medium: it requires a beneficiary/curator/finder account that has not yet been touched on-chain (no existing free balance) and a computed payout amount smaller than `ExistentialDeposit`. This is plausible for low-value bounty fees/tips or newly-created reward-recipient accounts, and the trigger extrinsic itself is fully public and unprivileged.

### Recommendation
Replace the `debug_assert!(res.is_ok())` pattern with a proper failure-handling strategy in `claim_bounty`, `claim_child_bounty`, `payout_tip`, and the society payout helpers:
- Propagate the error via `?` so the storage mutation aborts atomically instead of silently deleting/finalizing state on failure, or
- Explicitly detect the "sub-ED transfer to new account" case and route funds accordingly (e.g., keep the storage entry / mark it `Failed` for retry rather than removing it), mirroring the `PaymentState::Failed` retry mechanism already used in `pallet-treasury::payout`/`check_status` [6](#0-5)  and `pallet-treasury::check_status` [7](#0-6) , which correctly check the payment result before removing state.

### Proof of Concept
1. Create a bounty and assign a curator; move it to `PendingPayout` with a `beneficiary` account that has zero prior balance and never existed on-chain.
2. Fund the bounty account such that `payout = balance.saturating_sub(fee)` computes to an amount smaller than `ExistentialDeposit` (achievable by tuning bounty value/fee/curator deposit).
3. In a release build (no `debug_assertions`), call `claim_bounty(origin, bounty_id)` from any signed account after `unlock_at`.
4. `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` returns `Err` (destination account creation below ED), but `debug_assert!` is a no-op — execution continues, `Bounties` entry is removed, `BountyDescriptions` is removed, and `Event::BountyClaimed { payout, beneficiary, .. }` is emitted.
5. Query `beneficiary`'s balance: it remains `0`. Query the bounty sub-account: it retains the un-transferred `payout` amount, now permanently unreachable since the bounty ID has been purged from storage.
