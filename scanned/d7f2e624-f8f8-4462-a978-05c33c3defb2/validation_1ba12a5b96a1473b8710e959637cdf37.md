### Title
Redeem path skips live-decimals validation, allowing stale scaling factor to mis-price external-asset payouts - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
`pallet-psm`'s `mint` and `redeem` extrinsics both convert between an "internal" stablecoin and "external" collateral assets using a `10^diff` scaling factor derived from each asset's `decimals()`. `mint` re-validates this factor against the *live* metadata every call via `Self::ensure_decimals_match(...)` [1](#0-0) , and halts with `DecimalsMismatch` if live decimals have drifted from the registration snapshot [2](#0-1) . `redeem`, however, reads `ext_decimals`/`internal_decimals` directly from the stored snapshot and never calls this check [3](#0-2) . This is the same bug class as the Bloom `SwapFacility._getTokenPrices` report: a fixed/unverified scaling constant is applied to compute an `outAmount`-equivalent (`external_out`), and if the real conversion basis has moved, the payout is silently mis-scaled by a power of ten, while `mint` (the "deposit" side) is protected but `redeem` (the "withdraw" side) is not.

### Finding Description
`ExternalAssetInfo::decimals` and `PsmInfo::internal_decimals` are snapshots taken at registration time [4](#0-3) . The conversion helpers `external_to_internal`/`internal_to_external` scale strictly by `10^|ext_decimals - internal_decimals|` using whatever decimals values are passed in [5](#0-4) .

`mint()` guards against drift by calling `ensure_decimals_match`, which compares `T::Fungibles::decimals(external_asset)` and `T::Fungibles::decimals(internal_asset)` against the stored snapshot and errors out (`DecimalsMismatch`) if they differ [6](#0-5) , exactly as documented in the pallet's own PR notes: *"Runtime drift guard: mint/redeem return DecimalsMismatch if live metadata diverges from the registration snapshot; that asset halts until governance intervenes."* [7](#0-6) 

But the actual `redeem()` implementation never performs this check — it pulls `ext_decimals`/`internal_decimals` straight from the snapshot and immediately computes `external_out = Self::internal_to_external(internal_net, ext_decimals, internal_decimals)` [8](#0-7) . Any external asset whose `decimals()` metadata is mutable (pallet-assets supports admin-controlled `set_metadata`) can therefore drift after registration without redemption ever detecting it. Because the scaling factor is `10^n`, even a one-unit drift in reported decimals multiplies or divides `external_out` by 10, 100, etc., relative to what the true unit conversion should be.

This directly mirrors the root cause in the external report: a hard-coded/unverified decimal-scaling assumption feeding directly into an output-amount calculation that is then used to move real value out of a reserve, with no live cross-check on the decimals actually in effect at settlement time.

### Impact Explanation
`redeem()` moves real external-asset collateral out of the PSM reserve account and burns internal-asset debt based on `effective_internal_net`/`external_out`, both computed from the (potentially stale) decimals factor [9](#0-8) . If the true decimals convention has shifted upward relative to the snapshot, `internal_to_external` will multiply by a larger `10^diff` than correct, over-paying `external_out` for a given `internal_amount` burned — draining the reserve beyond what debt accounting authorizes, i.e., theft of reserve funds from other position holders. If it shifted the other way, users are underpaid relative to the debt burned, permanently trapping value in the reserve for later redeemers who will also be mis-priced. Either direction breaks the "conserve value and settle exactly once to the rightful beneficiary/amount" invariant for asset accounting.

### Likelihood Explanation
This requires only that an external asset's `decimals()` value differ from the value recorded at PSM-registration time by the time `redeem` is called — no admin/governance action against the PSM itself, no malicious relayer/validator, and no privileged action on the PSM is required; it only depends on the mutability of the external asset's own metadata (a normal, permitted action for that asset's team, wholly independent of the PSM's own admin model). Given `mint()` was deliberately hardened against exactly this scenario, `redeem()`'s omission is a straightforward, reachable oversight rather than a theoretical edge case.

### Recommendation
Apply the same `ensure_decimals_match` (or an equivalent live-decimals check) at the start of `redeem()` before using `ext_decimals`/`internal_decimals` in any conversion, mirroring `mint()`. If backward-unwind of pre-existing debt positions must be supported even after legitimate decimal migrations, introduce an explicit, governance-gated re-snapshot/migration path rather than silently trusting a possibly stale value in the value-moving redemption code path.

### Proof of Concept
1. Register an external asset `X` with `decimals = 18` against a PSM with `internal_decimals = 6`; snapshot stored as `ExternalAssetInfo { decimals: 18, .. }`.
2. Users `mint` internal tokens against `X`, building up `PsmDebt` and reserve balances consistent with the `18`-decimal conversion factor.
3. The asset team for `X` (unrelated to PSM admin) later calls `pallet_assets::set_metadata` to change `X`'s reported `decimals` to `6` (e.g., after a real supply/precision migration on `X`).
4. `mint()` on `X` now correctly halts with `Error::DecimalsMismatch` because it revalidates live decimals via `ensure_decimals_match`.
5. `redeem()` on `X` does **not** call `ensure_decimals_match`; it keeps using the stale snapshot (`ext_decimals = 18`) in `internal_to_external`, computing `external_out` scaled by `10^12` relative to `X`'s now-true `6`-decimal unit convention — paying out roughly `10^12`× the correct amount of `X` for the internal amount redeemed, draining the PSM reserve of `X` far beyond what the burned debt entitles.

		/// Scales by `10^(ext_decimals - internal_decimals)` — multiplies up when internal has more
		/// decimals, floor-divides when it has fewer. Returns [`Error::ConversionOverflow`] if
		/// the scaling factor or the product does not fit in the balance type.
		pub(crate) fn external_to_internal(
			amount: BalanceOf<T>,
			ext_decimals: u8,
			internal_decimals: u8,
		) -> Result<BalanceOf<T>, Error<T>> {
			use core::cmp::Ordering::*;
			match ext_decimals.cmp(&internal_decimals) {
				Equal => Ok(amount),
				Less => {
					let diff = (internal_decimals - ext_decimals) as u32;
					let factor = Self::pow10(diff)?;
					amount.checked_mul(&factor).ok_or(Error::<T>::ConversionOverflow)
				},
				Greater => {
					let diff = (ext_decimals - internal_decimals) as u32;
					let factor = Self::pow10(diff)?;
					Ok(amount.checked_div(&factor).unwrap_or_else(BalanceOf::<T>::zero))
				},
			}
		}
