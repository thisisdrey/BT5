## Analysis

The core broken invariant in the external report is: **irrevocable state advance (removal of the caller's claim) happens before the actual value transfer to the beneficiary is confirmed**, so if the transfer step fails or is intercepted, the state has already moved on and the value is lost. The closest verifiable local analog in `polkadot-sdk` is in the Snowbridge relayer reward-claim flow, which removes the reward entitlement from storage as soon as an outbound XCM is *sent*, without any guarantee that the XCM actually *executes* successfully at the destination.

### Title
Snowbridge relayer reward claim permanently deletes the reward record before destination-chain execution is confirmed, risking fund loss on `DepositAsset` failure - (File: `bridges/snowbridge/primitives/core/src/reward.rs`)

### Summary
`pallet_bridge_relayers::claim_rewards_to` removes the caller's accumulated reward from `RelayerRewards` as soon as `PaymentProcedure::pay_reward` returns `Ok`. For Snowbridge rewards, `pay_reward` is implemented by `PayAccountOnLocation::pay_reward`, which only checks that the XCM message was *validated and delivered* to the XCMP/UMP queue towards AssetHub — it never confirms that the `ReserveAssetDeposited`/`DepositAsset` instructions actually executed successfully on AssetHub.

### Finding Description
`do_claim_rewards` takes the reward balance out of storage via `maybe_reward.take()` and calls `T::PaymentProcedure::pay_reward`; only a synchronous `Err` aborts the mutation: [1](#0-0) 

For `BridgeReward::Snowbridge`, this delegates to `PayAccountOnLocation::pay_reward`, which builds an XCM program and only validates/delivers it — success is defined purely by local queuing, not remote execution: [2](#0-1) 

The XCM program itself has no error handling (no `SetErrorHandler`/`ReportError`) around the `DepositAsset` step:
```
UnpaidExecution { weight_limit: Unlimited, check_origin: None },
DescendOrigin(InboundQueueLocation::get().into()),
UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
ReserveAssetDeposited(assets.into()),
DepositAsset { assets: AllCounted(1).into(), beneficiary },
``` [3](#0-2) 

If `DepositAsset` fails on AssetHub for any ordinary reason (beneficiary account below ED, an asset/filter mismatch, congestion causing the message to be dropped after execution starts, or barrier/weight issues), the minted `ReserveAssetDeposited` assets are trapped in the AssetHub `AssetTrap` under the *derived XCM origin* (`DescendOrigin` + `UniversalOrigin`), not under an account the relayer/beneficiary directly controls. Recovering trapped assets requires calling `pallet_xcm::claim_assets` with an origin matching that exact derived location — something an ordinary signed account cannot produce. Meanwhile, on BridgeHub, `RelayerRewards` has already been permanently zeroed by the `take()` in `do_claim_rewards`, and there is no compensating mechanism to re-credit or retry.

This mirrors the report's broken invariant exactly: a two-phase settlement (local bookkeeping vs. remote asset delivery) where the first phase is treated as final before the second phase's success is verified, but here the trigger is ordinary destination-side execution failure/congestion rather than front-running, so it is not excluded by the "front-run-only" carve-out.

### Impact Explanation
An unprivileged relayer calling the public `claim_rewards_to` extrinsic can end up with the entitlement removed from `RelayerRewards` while receiving nothing, and no straightforward recovery path exists because the trapped-asset origin on AssetHub is not one the caller can reconstruct or sign for. This is a permanent user-fund lock in the bridge reward-payout state machine — a value-conservation violation matching the "Balances... must conserve value and settle exactly once" and "payout state must only advance after ... execution ... succeed atomically" pivots.

### Likelihood Explanation
No malicious actor, governance, relayer collusion, or leaked keys are required — only a normal cross-consensus message that fails to execute cleanly on the destination for a routine reason (ED shortfall, congestion, transient barrier rejection). Given XCM delivery across chains is inherently asynchronous and not guaranteed to execute exactly as validated, this is a structurally reachable condition rather than a contrived edge case.

### Recommendation
Do not treat local XCM `deliver()` success as final settlement. Options:
1. Keep the reward pending until a delivery/execution confirmation (e.g., XCM `ReportError`/`QueryResponse`) is received from AssetHub, only clearing `RelayerRewards` on confirmed success.
2. On execution failure, ensure trapped assets are deposited under a location/origin the relayer can actually reclaim (e.g., derive the trap origin identically to the beneficiary account, or add a `SetErrorHandler` that redirects failed deposits back to a claimable account).
3. Add a retry/refund path analogous to `pallet-treasury`'s `check_status`/`PaymentState::Failed` pattern, instead of unconditionally removing the storage entry.

### Proof of Concept
1. Relayer accrues a Snowbridge reward on BridgeHub via `register_reward`.
2. Relayer calls `claim_rewards_to(BridgeReward::Snowbridge, AssetHubLocation(beneficiary))` where `beneficiary` is a fresh account below AssetHub's `ExistentialDeposit` for the WETH foreign asset (or any condition causing `DepositAsset` to fail on AssetHub, e.g. temporary HRMP congestion).
3. On BridgeHub: `pay_reward` returns `Ok` because `XcmSender::deliver` succeeded; `do_claim_rewards` removes the `RelayerRewards` entry and emits `RewardPaid`.
4. On AssetHub: the XCM executes, `ReserveAssetDeposited` mints WETH into the holding register, `DepositAsset` fails (ED/filter/weight), and the asset is trapped under the derived `DescendOrigin`+`UniversalOrigin` location.
5. Relayer has no signed origin matching the trap and cannot invoke `pallet_xcm::claim_assets`; `RelayerRewards` for that relayer/reward-kind is already gone — funds are permanently unrecoverable through the intended flow.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
