## Analysis

The reported bug class — a public/authorized caller supplying an **unvalidated identifier** (`epochId`) that is accepted and persisted without being checked against the legitimate state window it is meant to restrict — has a direct analog in the Snowbridge V2 inbound tipping flow. [1](#0-0) 

### Title
Unbounded `nonce` accepted in `InboundQueue::add_tip` permanently locks user funds - (File: `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs`)

### Summary
`snowbridge-pallet-inbound-queue-v2`'s `AddTip::add_tip` implementation accepts any caller‑supplied `u64` `nonce` and stores a tip against it as long as that nonce has not yet been "consumed" (processed). It never validates that the `nonce` corresponds to a legitimate, soon‑to‑arrive inbound message. This mirrors the `RewardOracle._updateEpochReward` flaw: an unconstrained index/identifier is accepted from an unprivileged, signed extrinsic path and used to gate/allocate value, with no check that the identifier is bound to real, current chain state.

### Finding Description
`add_tip` is reachable by any signed AssetHub account through a public dispatch chain:

- `pallet-snowbridge-system-frontend::add_tip` (AssetHub, signed origin) swaps the user's asset for Ether/burns it, then XCM‑Transacts a call to BridgeHub. [2](#0-1) 
- `pallet-snowbridge-system-v2::add_tip` (BridgeHub) dispatches to either `InboundQueue::add_tip` or `OutboundQueue::add_tip` depending on `MessageId`. [3](#0-2) 
- For `MessageId::Inbound(nonce)`, `InboundQueue::add_tip` is invoked:
```rust
fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
    ensure!(amount > 0, AddTipError::AmountZero);
    // If the nonce is already processed, return an error
    ensure!(!Nonce::<T>::get(nonce.into()), AddTipError::NonceConsumed);
    // Otherwise add the tip.
    Tips::<T>::mutate(nonce, |tip| {
        *tip = Some(tip.unwrap_or_default().saturating_add(amount));
    });
    return Ok(());
}
``` [4](#0-3) 

The only guard is "has this nonce already been processed" — there is no check that `nonce` is close to the current/expected nonce, that it corresponds to a real in‑flight Ethereum event, or any expiry mechanism. Contrast this with `OutboundQueue::add_tip`, which is properly bound to an existing `PendingOrder` and rejects unknown nonces:
```rust
fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
    ensure!(amount > 0, AddTipError::AmountZero);
    PendingOrders::<T>::try_mutate_exists(nonce, |maybe_order| -> Result<(), AddTipError> {
        match maybe_order {
            Some(order) => { order.fee = order.fee.saturating_add(amount); Ok(()) },
            None => Err(AddTipError::UnknownMessage),
        }
    })
}
``` [5](#0-4) 

Because `InboundQueue::add_tip` returns `Ok(())` for any not-yet-consumed nonce, `pallet-snowbridge-system-v2::add_tip` records the call as a **success** and never routes the amount into `LostTips` (that fallback only triggers on an `Err` result): [6](#0-5) 

If a user (by typo, guesswork, or malicious intent) tips a nonce that will never actually be relayed from Ethereum (e.g., a far-future or entirely bogus `u64`), the real value already burned/transacted to fund the tip sits permanently in `Tips` storage with no expiry, no reclaim call, and no recovery path — it is neither paid out (since `Nonce::<T>::get(nonce)` will never become true) nor moved to `LostTips`.

### Impact Explanation
This falls under "permanent user-fund lock" and "public underpriced work" impact categories: a normal signed user, with no privileged role, can cause their own (or by griefing, another relayer's expected reward path) funds to be irrecoverably stranded on-chain, growing unbounded `Tips` storage entries that can never be cleaned up, since there is no boundedness or expiry tied to the nonce's validity window — exactly the invariant violation flagged in the external report (`epochId`/index accepted without correlating it to real, current state).

### Likelihood Explanation
High likelihood: this is a single, unprivileged, signed extrinsic call (`system-frontend::add_tip`) reachable by any AssetHub account, requires no governance, relayer, validator, or malicious-peer assumptions, and the missing check is a direct, one-line comparison to the analogous `OutboundQueue::add_tip`'s `PendingOrders` existence check that is absent here.

### Recommendation
Bind `InboundQueue::add_tip` to a legitimate, bounded nonce window, e.g., only allow tipping nonces within `[Nonce::<T>::get()+1, Nonce::<T>::get()+T::MaxTipAheadWindow::get()]`, or track pending/expected nonces analogously to `OutboundQueue`'s `PendingOrders`, and reject (returning `AddTipError::UnknownMessage`) tips for nonces outside that window so the tip amount is instead routed to `LostTips` and remains recoverable.

### Proof of Concept
1. On AssetHub, a signed user calls `EthereumSystemFrontend::add_tip(origin, MessageId::Inbound(u64::MAX - 1), asset)` with a nonzero DOT-denominated asset.
2. The asset is swapped to Ether and burned/transacted to BridgeHub (`system-frontend::add_tip`).
3. On BridgeHub, `EthereumSystemV2::add_tip` dispatches to `InboundQueue::add_tip(u64::MAX - 1, amount)`.
4. `Nonce::<T>::get(u64::MAX - 1)` is `false` (never processed, and never will be, since real Ethereum message nonces are sequential and far from `u64::MAX`), so the call succeeds and `Tips::<T>::insert(u64::MAX - 1, amount)`.
5. `TipProcessed { success: true, .. }` is emitted; `LostTips` is untouched.
6. The tip value is now permanently stranded — no message with that nonce will ever arrive to consume/pay it out, and there is no dispatchable to reclaim it.

		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}
