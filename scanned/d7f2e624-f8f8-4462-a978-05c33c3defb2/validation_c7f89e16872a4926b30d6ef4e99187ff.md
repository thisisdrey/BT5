### Title
`pallet-psm` `redeem` skips the decimals-drift guard that `mint` enforces, letting redemptions use a stale decimal-scaling snapshot - (File: substrate/frame/psm/src/lib.rs)

### Summary
This is a direct local analog of the `OracleRef` bug: the report's core flaw is that a fallback data source (backup oracle) is *assumed* to share the same scaling/normalizer as the primary source, and that assumption is enforced inconsistently. In `pallet-psm`, decimal-scaling between an external asset and the internal pUSD unit is snapshotted at registration time (`AssetDecimals` / `StableDecimals`) and this snapshot is used by the conversion helpers `external_to_internal` / `internal_to_external` [1](#0-0)  instead of re-reading live asset metadata. The `mint` path defends against snapshot staleness with a `DecimalsMismatch` check, but the `redeem` path does not perform the same check, so it silently converts using the outdated snapshot.

### Finding Description
`pallet-psm` normalizes external-asset amounts to internal pUSD units via `pow10`-based scaling factors derived from a decimals snapshot stored per asset at registration (`AssetDecimals`) and pallet-wide (`StableDecimals`), as introduced in the "support external assets with different decimal precision" change [2](#0-1) . The PR description explicitly states that "mint and redeem" both return `DecimalsMismatch` if live metadata diverges from the registration snapshot [3](#0-2) .

However, the test suite demonstrates this guard is asymmetric:
- `mint_halts_when_asset_decimals_drift` shows that after the external asset's live decimals are changed via `Assets::set_metadata`, `Psm::mint` correctly reverts with `Error::<Test>::DecimalsMismatch` [4](#0-3) .
- `redeem_uses_snapshot_when_asset_decimals_drift` shows that under the identical drift condition (decimals changed from 2 to 4 after the position was minted), `Psm::redeem` succeeds (`assert_ok!`) and simply uses the stale snapshot decimals to compute the payout, rather than rejecting the call like `mint` does [5](#0-4) .

The same asymmetry is repeated for internal-asset decimal drift: `mint_halts_when_internal_decimals_drift` reverts with `DecimalsMismatch` [6](#0-5) , while the corresponding `redeem_uses_snapshot_when_internal_decimals_drift` test (immediately following) exercises redeem succeeding under the same drift instead of halting.

This is the same class of bug as `OracleRef`: one code path (the "primary" source/mint) is hardened against a scaling-source mismatch, while the other path (the "backup"/redeem) implicitly assumes the previously-recorded scaling factor is still correct and uses it unconditionally. Any legitimate, non-malicious metadata change to an external asset's `decimals` (e.g., a token issuer migrating decimal precision, which is a normal `pallet-assets` `set_metadata` operation available to that asset's owner/admin — not a PSM or chain governance action) silently desynchronizes the scaling factor used on redemption from the asset's actual precision.

### Impact Explanation
If an external asset's decimals change after PSM registration, `redeem` continues to scale amounts using the old snapshot in `internal_to_external`/`external_to_internal` [1](#0-0) . Depending on the direction of the decimals change, this causes redeemers to receive an external-asset amount that is off by a power of ten relative to the true precision — i.e., users can redeem internal pUSD for a vastly inflated (or deflated) amount of the external asset, directly matching the "mint volt cheap or redeem volt for inflated underlying amounts" impact described in the source report. Because `mint` and `PsmDebt` accounting were also computed against the stale scaling, the reserve/debt invariants also become inconsistent with real external-asset value, risking insolvency of the PSM reserve or permanent misallocation of internal-asset issuance versus backing.

### Likelihood Explanation
The trigger condition — an external asset's live `decimals` metadata diverging from the value snapshotted at PSM registration — is a foreseeable, non-malicious event (asset issuers can and do change token metadata for legitimate reasons, and the pallet's own migration/guard code treats this as an expected drift scenario, not an attack). No privileged PSM/chain-governance action, validator misbehavior, or malicious relayer is required: any signed account can call `redeem` at any time after such a metadata change, and the existing `mint`-side guard proves the drift condition is realistically reachable and already tested for in this exact repository.

### Recommendation
Apply the same live-metadata-vs-snapshot `DecimalsMismatch` check in the `redeem` path (and in `redeem_uses_snapshot_when_internal_decimals_drift`'s equivalent code path) that is already applied in `mint`, so that any asset whose decimals have drifted from the registered snapshot halts on both mint and redeem symmetrically until governance re-registers/updates the snapshot, consistent with the stated design intent in the PR description.

### Proof of Concept
The repository's own test suite constitutes the proof of concept:
1. `register_external_asset_with_weight(USDX_ASSET_ID, ...)` snapshots USDX decimals as 2.
2. `Psm::mint` succeeds, creating debt/reserve state scaled at 2 decimals.
3. The asset owner calls `Assets::set_metadata(..., USDX_ASSET_ID, ..., 4)`, changing live decimals to 4 — no PSM privilege required, only ownership of the USDX asset itself.
4. `Psm::mint` now correctly reverts with `DecimalsMismatch` (`mint_halts_when_asset_decimals_drift`) [4](#0-3) .
5. Yet `Psm::redeem` for the exact same drifted asset **succeeds** and pays out based on the stale 2-decimal snapshot rather than the live 4-decimal metadata (`redeem_uses_snapshot_when_asset_decimals_drift`) [5](#0-4) , demonstrating the exploitable inconsistency.

		/// Convert an amount denominated in internal units into external-asset units.
		///
		/// Inverse of [`Self::external_to_internal`]. Floor-divides when internal has more
		/// decimals, multiplies up when it has fewer.
		pub(crate) fn internal_to_external(
			amount: BalanceOf<T>,
			ext_decimals: u8,
			internal_decimals: u8,
		) -> Result<BalanceOf<T>, Error<T>> {
			use core::cmp::Ordering::*;
			match ext_decimals.cmp(&internal_decimals) {
				Equal => Ok(amount),
				Less => {
					let diff = (internal_decimals - ext_decimals) as u32;
					let factor = Self::pow10(diff)?;
					Ok(amount.checked_div(&factor).unwrap_or_else(BalanceOf::<T>::zero))
				},
				Greater => {
					let diff = (ext_decimals - internal_decimals) as u32;
					let factor = Self::pow10(diff)?;
					amount.checked_mul(&factor).ok_or(Error::<T>::ConversionOverflow)
				},
			}
		}

title: 'pallet-psm: support external assets with different decimal precision'
doc:
- audience: Runtime Dev
  description: |-
    Previously pallet-psm rejected any external stablecoin whose decimals did
    not match pUSD. This change normalizes to pUSD units internally so the PSM
    can approve assets with arbitrary decimal precision within a safe range.

    Core changes:
    - New storage: per-asset `AssetDecimals` snapshot and pallet-wide
      `StableDecimals` snapshot. Storage version bumped to 2.
    - Conversion helpers `external_to_pusd` / `pusd_to_external` with checked
      arithmetic and `MAX_DECIMALS_DIFF = 24` to prevent overflow.
    - `mint` and `redeem` use round-trip rounding. Truncation dust stays in the
      caller's wallet on both paths (symmetric behavior), no value is trapped
      in the reserve and no hidden dust is routed to the fee destination.
    - `PsmDebt` now denominates in pUSD units so aggregate ceilings and issuance
      checks are meaningful across mixed-decimal assets.
    - Runtime drift guard: `mint`/`redeem` return `DecimalsMismatch` if live
      metadata diverges from the registration snapshot; that asset halts until
      governance intervenes.

	#[test]
	fn redeem_uses_snapshot_when_asset_decimals_drift() {
		new_test_ext().execute_with(|| {
			register_external_asset_with_weight(USDX_ASSET_ID, Permill::from_percent(100));
			set_zero_fees(USDX_ASSET_ID);

			// Mint first, then change decimals.
			assert_ok!(Psm::mint(
				RuntimeOrigin::signed(ALICE),
				INTERNAL_ASSET_ID,
				USDX_ASSET_ID,
				10_000 * USDX_UNIT,
				Permill::zero()
			));
			assert_ok!(Assets::set_metadata(
				RuntimeOrigin::signed(ALICE),
				USDX_ASSET_ID,
				b"USDX".to_vec(),
				b"USDX".to_vec(),
				4
			));

			let alice_usdx_before = get_asset_balance(USDX_ASSET_ID, ALICE);
			let alice_internal_before = get_asset_balance(INTERNAL_ASSET_ID, ALICE);
			let debt_before = PsmDebt::<Test>::get(INTERNAL_ASSET_ID, USDX_ASSET_ID);

			assert_ok!(Psm::redeem(
				RuntimeOrigin::signed(ALICE),
				INTERNAL_ASSET_ID,
				USDX_ASSET_ID,
				100 * INTERNAL_UNIT,
				Permill::zero()
			));

			assert_eq!(
				get_asset_balance(USDX_ASSET_ID, ALICE),
				alice_usdx_before + 100 * USDX_UNIT
			);
			assert_eq!(
				get_asset_balance(INTERNAL_ASSET_ID, ALICE),
				alice_internal_before - 100 * INTERNAL_UNIT
			);
			assert_eq!(
				PsmDebt::<Test>::get(INTERNAL_ASSET_ID, USDX_ASSET_ID),
				debt_before - 100 * INTERNAL_UNIT
			);
		});
	}
