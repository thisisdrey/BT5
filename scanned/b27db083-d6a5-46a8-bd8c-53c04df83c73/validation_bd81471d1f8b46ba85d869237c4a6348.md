### Title
Fixed compile-time `ChainId` in `permit` pallet's EIP-712 domain separator enables cross-chain/cross-fork signature replay for ERC20 permit approvals - (File: `substrate/frame/assets/precompiles/src/permit.rs`)

### Summary
The `permit` pallet added to support EIP-2612 gasless approvals for `pallet-assets` ERC20 precompiles computes its EIP-712 `DOMAIN_SEPARATOR` using a chain ID that is a fixed, compile-time `Config::ChainId: Get<u64>` constant rather than a value that is bound to the actual, currently-effective EVM chain identity used elsewhere in the runtime (e.g. `pallet_revive`'s own `ChainId`). This is the exact bug-class described in the external report: a chain identifier baked in once and never re-derived, so signed permits remain valid and replayable if the effective chain identity ever diverges (chain fork, chain-id reassignment, or migration to a different runtime/parachain sharing the same asset ids and precompile addresses).

### Finding Description
`compute_domain_separator` in `substrate/frame/assets/precompiles/src/permit.rs` builds the EIP-712 domain separator like this: [1](#0-0) 

The `chain_id` value comes directly from `T::ChainId::get()`, declared as a `#[pallet::constant]` `Get<u64>` in the pallet config: [2](#0-1) 

This mirrors precisely the vulnerable pattern in the external report: the chain ID is fixed at the time the runtime/pallet is configured (analogous to being fixed "at deployment" in the Solidity constructor), and there is no mechanism to detect or react to a change in the chain's actual identity. In the Solidity report, the domain separator's `chainId` value was set once in the constructor and never revisited; here, `T::ChainId` is a `Get<u64>` implementation supplied statically in the runtime configuration (analogous to `impl pallet_permit::Config for Runtime { type ChainId = ConstU64<...>; }`), so it is likewise fixed independent of any real runtime notion of "current chain" and cannot be regenerated if that identity changes.

Unlike a standard Substrate extrinsic, which is naturally chain-scoped via `frame_system::CheckGenesis`/`CheckSpecVersion` in the transaction extension pipeline (as used elsewhere, e.g. `substrate/frame/system/src/extensions/check_genesis.rs` and the various runtimes' `MetaTxExtension` tuples), this permit signature is verified purely via `ecrecover` against a digest computed from `DOMAIN_SEPARATOR` and the `Permit` struct hash — it never goes through `frame_system`'s replay-protection extensions: [3](#0-2) 

The nonce (`Nonces` storage map keyed by verifying contract + owner) is the only per-signature replay guard, and the domain separator's `chainId`/`verifyingContract` fields are the only cross-chain/cross-contract binding. Existing tests confirm the domain separator is bound to `verifyingContract` and token name, but there is no test or mechanism that re-derives `chain_id` from any live/authoritative source (e.g. `pallet_revive::Config::ChainId`) — it is a static constant per the pallet definition: [4](#0-3) 

Because Substrate/Cumulus parachains can be forked, migrated to a new runtime, or have their EVM-visible chain id changed (e.g. asset-hub migrating between test/production configurations, or a runtime upgrade reconfiguring `pallet_revive`'s chain id while `permit::Config::ChainId` is left stale, or a chain being cloned for a testnet with intentionally identical asset/precompile addresses), any previously-signed but not-yet-consumed permit remains valid on both the original and the forked/cloned chain as long as the nonce hasn't been consumed on that specific chain's storage. Since `Nonces` storage is chain-local, a signature signed once can be replayed on the fork/clone chain that never saw the original permit's nonce increment, exactly as in the reported exploit scenario.

### Impact Explanation
If the runtime's configured `permit::Config::ChainId` becomes stale relative to the chain's real identity (fork, chain clone for testing purposes accidentally sharing state/config, or a deliberate but improperly-coordinated chain-id change), an attacker holding a previously valid but unconsumed permit signature can replay it on the diverged chain to gain an ERC20 `approve`-equivalent authorization they were never granted on that chain, and then drain the victim's asset balance through the granted allowance. This is a direct violation of the "conserve value / settle exactly once to rightful beneficiary" invariant for asset-holding balances, matching the "theft or unbacked mint or unlock" / "duplicate settlement" impact classes.

### Likelihood Explanation
Likelihood depends on an actual chain fork/clone/chain-id divergence event occurring — this is not exploitable under normal single-chain operation since nonces prevent same-chain replay. However, this is exactly the same likelihood profile as the original report: the vulnerability is latent until a fork/clone event happens, at which point it becomes trivially and directly exploitable by any holder of a previously-signed, unconsumed permit, without needing any privileged actor, malicious validator, or leaked key — purely a signature-replay primitive against public, unprivileged `permit()`-style calls.

### Recommendation
Bind the EIP-712 domain separator's chain identifier to a live, single source of truth rather than a separately configured static constant — e.g. derive `permit::Config::ChainId` from `pallet_revive`'s runtime API chain id (or re-derive/cache-and-invalidate the domain separator based on a chain-id read at call time), so that `compute_domain_separator` cannot diverge from the chain's actual, currently effective EVM chain id. Additionally, document and test the behavior expected across runtime upgrades/migrations that could alter chain identity, ensuring outstanding nonces/signatures cannot be replayed against a diverged chain.

### Proof of Concept
1. Deploy/configure a chain (Chain A) with `pallet_permit::Config::ChainId = X` and an asset with a given `verifying_contract` (precompile) address.
2. Alice signs an EIP-2612 `Permit(owner=Alice, spender=Eve, value=..., nonce=0, deadline=...)` digest using Chain A's `DOMAIN_SEPARATOR` (which embeds `chain_id = X`), authorizing Eve to spend her tokens, but does not submit it yet.
3. Chain A is forked/cloned into Chain B (e.g., via a testnet fork, chain-spec clone, or migration) that retains the same asset id, same `verifying_contract` address, and — critically — the same static `permit::Config::ChainId = X` constant (since it was never re-derived from any live chain property), while `Nonces` storage for Alice's account on Chain B is fresh/zero (no permit ever consumed there).
4. Eve submits Alice's original signature to `permit()` on Chain B via `use_permit`/`do_verify_permit`. Because `DOMAIN_SEPARATOR` on Chain B is identical (same static `ChainId`, same `verifying_contract`, same token name) and nonce on Chain B is still `0`, `ecrecover` succeeds and `recovered == owner` in `do_verify_permit`: [5](#0-4) 
5. Eve's allowance is granted on Chain B despite Alice never intending to authorize spending on that chain, allowing Eve to transfer Alice's tokens there — reproducing the "signature reused across forks" exploit from the external report.

		pub fn compute_domain_separator(verifying_contract: &H160, name: &[u8]) -> H256 {
			let name_hash = keccak_256(name);
			let version_hash = keccak_256(b"1");
			let chain_id = T::ChainId::get();

			// Encode: typehash || name_hash || version_hash || chainId || verifyingContract
			let mut data = Vec::with_capacity(DOMAIN_SEPARATOR_ENCODED_LEN);
			data.extend_from_slice(&DOMAIN_TYPEHASH);
			data.extend_from_slice(&name_hash);
			data.extend_from_slice(&version_hash);
			// Pad chain_id to 32 bytes (big-endian)
			data.extend_from_slice(&[0u8; 24]);
			data.extend_from_slice(&chain_id.to_be_bytes());
			// Pad address to 32 bytes
			data.extend_from_slice(&[0u8; 12]);
			data.extend_from_slice(verifying_contract.as_bytes());

			H256(keccak_256(&data))
		}
