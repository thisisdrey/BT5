### Title
`SnowbridgeSystemFrontend::add_tip` missing the `Halted`/export-pause check present on its sibling `register_token` — ([File: bridges/snowbridge/pallets/system-frontend/src/lib.rs])

### Summary
`snowbridge-pallet-system-frontend` gates `register_token` with an explicit halt check (`ensure!(!Self::export_operating_mode().is_halted(), Error::<T>::Halted)`) before it burns fee assets and forwards a `Transact` call to BridgeHub [1](#0-0) . The sibling dispatchable `add_tip`, which performs the same class of operation (swap/burn a user asset for Ether and forward a `Transact` call that ultimately mutates relayer reward/payout state on BridgeHub) has no such check at all [2](#0-1) . This is the same bug class as the external report: a state-changing entry point that should respect the module's pause/halt flag but doesn't, while an equivalent function in the same contract/pallet correctly enforces it.

### Finding Description
`ExportOperatingMode` is the pallet's halt flag, and `is_halted()` is meant to stop "exporting messages to Ethereum" style operations [3](#0-2) . `register_token` treats this as a hard precondition, checked before any funds are swapped/burned and before any BridgeHub `Transact` call is built and sent [4](#0-3) .

`add_tip` calls `swap_fee_asset_and_burn` (which swaps the caller's asset for Ether and withdraws/burns it via `AssetTransactor::withdraw_asset`) and then unconditionally builds and sends the `EthereumSystemCall::AddTip` `Transact` call to BridgeHub, with no equivalent `ensure!(!Self::export_operating_mode().is_halted(), ...)` guard [5](#0-4) , [6](#0-5) .

The `ExportPausedQuery` implementation backing `PausableExporter` only wraps whatever `SendXcm` implementation is configured as the Ethereum-export router [7](#0-6) ; `add_tip`'s `Transact` message is routed to `T::BridgeHubLocation` via the ordinary XCM sender (`T::XcmSender`), not through the Ethereum-blob export path, so it is not implicitly protected by that wrapper — the explicit `ensure!` in `register_token` is exactly what closes this gap for that call, and `add_tip` lacks it. This mirrors the reported class of bug: `SecuritizeInternalNavProvider::setRate` had `whenNotPaused` while `SecuritizeAmmNavProvider`'s equivalent state-changing functions did not.

### Impact Explanation
Governance sets `ExportOperatingMode` to `Halted` specifically to stop bridge-affecting Ethereum-side fund/reward flows (e.g., during a suspected compromise, mirrored by the related fix in `pr_11856` that closed an analogous gap in the Ethereum verifier for `inbound_queue_v2::submit` / `outbound_queue_v2::submit_delivery_receipt`) [8](#0-7) . While `add_tip` is halted for `register_token`-style flows, an unprivileged signed caller can still invoke `add_tip` to burn/swap assets and dispatch `Transact { AddTip }` to BridgeHub, continuing to feed relayer reward/payout state (`PendingOrders`/reward registration in inbound/outbound-queue-v2) that governance intended to freeze via the halt. This directly violates the "message queues, bridge markers, receipts, and payout state must only advance after ... succeed atomically" and "public dispatch wrappers must not bypass filters" pivots for the Snowbridge delivery flow.

### Likelihood Explanation
Likelihood is high for any unprivileged, signed account with the ability to obtain/hold a fee/tip asset: `add_tip` requires only `ensure_signed(origin)` and a nonzero `asset`, with no privileged input. The bug is triggered purely by calling the public extrinsic while governance has set `Halted` — no relayer, validator, or admin misbehavior is required, only normal use of a public dispatchable during an emergency-halt window.

### Recommendation
Add the same `ensure!(!Self::export_operating_mode().is_halted(), Error::<T>::Halted);` guard at the top of `add_tip`, mirroring `register_token`, before any asset is swapped/burned and before the `Transact` call is constructed/sent.

### Proof of Concept
1. Root calls `SnowbridgeSystemFrontend::set_operating_mode(Root, BasicOperatingMode::Halted)` — confirmed to correctly block `register_token` (per its `ensure!`) but there is no corresponding check for `add_tip`.
2. A signed, unprivileged account calls `SnowbridgeSystemFrontend::add_tip(origin, message_id, asset)` with a valid fee asset while the pallet is halted.
3. `swap_fee_asset_and_burn` executes: the caller's asset is swapped for Ether and burned via `burn_for_teleport` [6](#0-5) .
4. `build_add_tip_call` and `send_transact_call` execute, dispatching `EthereumSystemCall::AddTip` to BridgeHub via ordinary XCM routing, unaffected by the `Halted` mode — demonstrating that the halt has no effect on this state-changing entrypoint, unlike `register_token` in the same pallet.

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}

pub struct PausableExporter<PausedQuery, InnerExporter>(PhantomData<(PausedQuery, InnerExporter)>);

impl<PausedQuery: ExportPausedQuery, InnerExporter: SendXcm> SendXcm
	for PausableExporter<PausedQuery, InnerExporter>
{
	type Ticket = InnerExporter::Ticket;

	fn validate(
		destination: &mut Option<Location>,
		message: &mut Option<Xcm<()>>,
	) -> SendResult<Self::Ticket> {
		match PausedQuery::is_paused() {
			true => Err(SendError::NotApplicable),
			false => InnerExporter::validate(destination, message),
		}
	}

	fn deliver(ticket: Self::Ticket) -> Result<XcmHash, SendError> {
		match PausedQuery::is_paused() {
			true => Err(SendError::NotApplicable),
			false => InnerExporter::deliver(ticket),
		}
	}
}

title: 'Snowbridge: halt the Ethereum verifier when the bridge is in emergency stop'

doc:
  - audience: Runtime Dev
    description: |
      When `pallet-ethereum-client` is in `Halted` operating mode, its `Verifier::verify`
      implementation now short-circuits with the new `VerificationError::Halted` instead of
      attempting to verify Ethereum-side proofs.

      Previously, halting the light client only blocked new beacon header updates via
      `EthereumBeaconClient::submit`. Proof verification still ran, which meant
      `inbound_queue_v2::submit` and `outbound_queue_v2::submit_delivery_receipt` could
      continue to process receipts and pay out relayer rewards from `PendingOrders` while
      governance had halted the bridge (e.g. after a suspected beacon light client compromise).

      Halting the verifier closes that gap in one place — covering both inbound dispatch and
      outbound delivery-receipt reward payments.
