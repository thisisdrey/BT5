## Title
Contract termination can be permanently blocked by holds/locks on the contract's own account, preventing forced cleanup/settlement — analogous to the Notional vault-settlement DoS - (File: `substrate/frame/revive/src/exec.rs`, `substrate/frame/revive/src/lib.rs`)

### Summary
The Sherlock finding shows that `VaultAccount.repayAccountPrimeDebtAtSettlement()` unconditionally refunds excess cash to the vault account via a native transfer that the vault (as a smart contract) can make revert, which blocks the mandatory settlement path and prevents liquidation. The equivalent broken invariant — *"a value-return step that is a hard precondition for a forced/administrative state transition can be made to fail by the recipient itself, permanently blocking that transition"* — exists in `pallet-revive`'s contract termination path. `do_terminate` requires `T::Deposit::refund_all` (storage-deposit hold release) to succeed before it can transfer the contract's remaining balance and delete it; if the contract's own account carries a competing hold/freeze/lock, this step fails and the whole termination is rolled back, leaving the contract permanently un-terminated.

### Finding Description
`Contracts::do_terminate` in `substrate/frame/revive/src/exec.rs` performs deletion inside `delete_contract`: [1](#0-0) 

The very first step is `T::Deposit::refund_all(&contract_account, ...)?` — if this fails, the `?` propagates the error and `with_transaction` rolls back the *entire* termination (see the `TransactionOutcome::Rollback` branch): [2](#0-1) 

The refund itself, `refund_deposit` in `lib.rs`, explicitly documents that this can fail due to *locks* on the contract's own account (e.g. from staking/governance participation), and in that case returns `Error::<T>::StorageRefundLocked`, which is a hard error, not a best-effort/soft failure: [3](#0-2) 

Termination/deletion is also the mechanism by which one contract can forcibly terminate another contract that is on the call stack (its *caller*), via `terminate_caller`, which schedules deletion through the same `do_terminate`/`refund_deposit` path: [4](#0-3) 

This mirrors the Notional bug precisely: the entity that is supposed to be "settled"/cleaned up (the contract account) is also the one whose state (locks/holds) determines whether that settlement succeeds. If any lock or hold exists on the contract account that the refund logic cannot move (see the code's own comment: *"There are some locks preventing the refund. This could be the case if the contract participates in government."*), termination fails every single time it is attempted, exactly like the vault that reverts its own settlement transfer to remain permanently unliquidatable.

### Impact Explanation
Failure to terminate means:
- The contract's storage, code reference count, and account entry are never cleaned up — a permanent state lock (`ContractInfoOf`, `PristineCode`, deposits held) that cannot be resolved through the normal path.
- Any protocol logic that relies on `terminate`/`SELFDESTRUCT`/`terminate_caller` succeeding as a forced-cleanup or "liquidation-like" mechanism (e.g., a caller contract designed to force-remove a misbehaving/insolvent counterpart) can be defeated by the target simply having (or arranging to have) a hold/lock on its own account.
- This matches the "permanent user-fund or bridge-state lock" and "runtime bugs that compromise intended behavior" categories in the impact gate: value that should be released/settled is stuck, and a state transition that is supposed to be unconditionally forceable can be indefinitely obstructed.

### Likelihood Explanation
The precondition — the contract's account carrying a hold/lock that the refund path cannot move — is exactly the scenario the code's own defensive log message anticipates ("First remove locks (staking, governance) from the contracts account"), meaning the failure mode is a known, reachable state, not a hypothetical. Any flow where the contract account's balance participates in a hold-based mechanism external to `pallet-revive`'s own storage-deposit hold (freezes, additional holds from other pallets sharing the same `T::Currency`) will trigger `StorageRefundLocked`/`StorageRefundNotEnoughFunds` and abort termination unconditionally, with no fallback or best-effort path (unlike other transfers in the codebase that use `Precision::BestEffort`).

### Recommendation
- Make the deposit refund at termination best-effort (as already done for the analogous storage-deposit charge path elsewhere) rather than a hard precondition that aborts the whole termination.
- Alternatively, decouple "releasing the depositor's storage-deposit hold" from "removing the contract and sending its balance to the beneficiary," so that a stuck refund cannot block deletion of the contract and delivery of funds to the beneficiary — mirroring the Notional fix ("remove transfers from Settle Vault Account") by removing the hard dependency between value movement and the mandatory state transition.
- Add explicit handling/telemetry and a permissionless recovery path (e.g. force-refund with `Fortitude::Force`) so a locked contract account cannot indefinitely block termination.

### Proof of Concept
1. Deploy a contract `C` whose account accumulates the pallet-revive storage-deposit hold (normal instantiation).
2. Arrange for `C`'s account to also carry a competing lock/freeze under the same `T::Currency` (e.g., via any pallet in the runtime that applies a `Freeze`/`Lock` to arbitrary accounts holding native balance, reachable without privileged access) such that `T::Currency::transfer_on_hold(...,Restriction::Free, Fortitude::Polite)` inside `refund_deposit` can no longer move the full deposit.
3. Call `terminate`/`SELFDESTRUCT` on `C`, or have another contract call `terminate_caller` targeting `C` as its caller.
4. Observe `do_terminate` → `delete_contract` → `T::Deposit::refund_all` returning `Err(StorageRefundLocked)`; `with_transaction` rolls back the whole termination (per `substrate/frame/revive/src/exec.rs:1851-1866`), and `C` remains fully intact and un-terminated no matter how many times termination is retried — mirroring the vault that can never be settled/liquidated.

	fn terminate_caller(&mut self, beneficiary: &H160) -> Result<(), DispatchError> {
		ensure!(self.top_frame().delegate.is_none(), Error::<T>::PrecompileDelegateDenied);
		let parent = self.frames_mut().nth(1).ok_or_else(|| Error::<T>::ContractNotFound)?;
		ensure!(parent.entry_point == ExportedFunction::Call, Error::<T>::TerminatedInConstructor);
		ensure!(parent.delegate.is_none(), Error::<T>::PrecompileDelegateDenied);

		let info = parent.contract_info();
		let trie_id = info.trie_id.clone();
		let code_hash = info.code_hash;
		let contract_address = T::AddressMapper::to_address(&parent.account_id);
		let beneficiary = T::AddressMapper::to_account_id(beneficiary);

		let parent_account_id = parent.account_id.clone();

		// balance transfer is immediate
		Self::transfer(
			&self.origin,
			&parent_account_id,
			&beneficiary,
			<Contracts<T>>::evm_balance(&contract_address),
			Preservation::Preserve,
			&mut top_frame_mut!(self).frame_meter,
			&self.exec_config,
		)?;

		// schedule for delayed deletion
		let args = TerminateArgs { beneficiary, trie_id, code_hash, only_if_same_tx: false };
		self.top_frame_mut().contracts_to_be_destroyed.insert(parent_account_id, args);

		Ok(())
	}

	/// Refund a deposit.
	///
	/// `dst` is usually the transaction origin and `from` a contract or
	/// the pallets own account.
	fn refund_deposit(
		hold_reason: HoldReason,
		from: &T::AccountId,
		dst: deposit_payment::Funds<T::AccountId>,
		amount: BalanceOf<T>,
	) -> Result<(), DispatchError> {
		if amount.is_zero() {
			return Ok(());
		}

		let to = match &dst {
			deposit_payment::Funds::Balance(to) | deposit_payment::Funds::TxFee(to) => *to,
		};
		let result = T::Deposit::refund_on_hold(hold_reason, from, dst, amount);

		result.defensive_map_err(|err| {
			let available = T::Deposit::total_on_hold(hold_reason, from);
			if available < amount {
				// The storage deposit accounting got out of sync with the balance: This would be a
				// straight up bug in this pallet.
				log::error!(
					target: LOG_TARGET,
					"Failed to refund storage deposit {amount:?} from contract {from:?} to origin {to:?}. Not enough deposit: {available:?}. This is a bug.",
				);
				Error::<T>::StorageRefundNotEnoughFunds.into()
			} else {
				// There are some locks preventing the refund. This could be the case if the
				// contract participates in government. The consequence is that if a contract votes
				// with its storage deposit it would no longer be possible to remove storage without first
				// reducing the lock.
				log::warn!(
					target: LOG_TARGET,
					"Failed to refund storage deposit {amount:?} from contract {from:?} to origin {to:?}: {err:?}. First remove locks (staking, governance) from the contracts account.",
				);
				Error::<T>::StorageRefundLocked.into()
			}
		})
	}
