Target: `WalletImpl::execute_signed`, `SignatureSchema::verify_request_msg` for the `webauthn-p256`/`webauthn-ed25519` variants (schema-specific proof format). Attacker action: attacker captures a valid WebAuthn assertion `proof` (clientDataJSON + authenticatorData + signature) produced by the owner for a DIFFERENT `RequestMessage` (different `nonce`/`request`), and submits it alongside a NEW `msg` whose `challenge`-bound fields the webauthn verifier does not fully re-derive from `msg` (e.g. if `verify_request_msg` checks only that the WebAuthn `challenge` equals `msg.hash()` for a DIFFERENT hash function/encoding than the one used elsewhere, or if `clientDataJSON.challenge` base64 padding/charset differences let a crafted new `msg` hash-collide with the old challenge string). Preconditions: owner has previously signed at least one WebAuthn request via the wallet's supported webauthn schema. Call sequence: `execute_signed`->`S::verify_request_msg(public_key, &new_msg, &old_proof)`. Binding: the `RequestMessage` bytes actually hashed into the WebAuthn `challenge` == the `msg` object whose `Request` gets executed, one-to-one. Impact: Critical - proof-reuse across a different `msg` executes a `Request` the owner never actually authorised via that specific WebAuthn ceremony, potentially moving Verifier balances. Proof idea: unit test in the webauthn signature crate constructing two distinct `RequestMessage`s and asserting a `proof` for one is rejected by `verify_request_msg` for the other (mismatched `msg.hash()` vs decoded `challenge`).
