[Function: remove_account] Attacker with account A holding an outstanding yield (PromiseYieldTimeout indexed by height/index) deletes A right before the timeout height is reached, and recreates A beforehand. Preconditions: yield_create called with a timeout number of blocks small enough for attacker to control block timing via normal tx submission cadence. Sequence: 1) create yield with short timeout; 2) delete A (PromiseYieldTimeout entry at TrieKey::PromiseYieldTimeout{index} untouched since it's not account-keyed but the linked PromiseYieldReceipt/YieldIdToDataId keyed to A is untouched by remove_account); 3) recreate A; 4) let timeout height pass so the runtime's yield-timeout processing (lib.rs) looks up PromiseYieldReceipt for A and executes the timeout callback against the new account. Invariant: authorization exactness / value conservation. Impact: timeout callback (which can include a Transfer or FunctionCall with attached balance) executes against the newly created A, potentially crediting/debiting balance the new owner never authorized and without corresponding validator/predecessor consent. Proof: test-loop test scheduling a short yield timeout, deleting+recreating the yielding account before the timeout height, and asserting the timeout receipt either errors as 'account no longer exists in original form' or (bug) silently applies to the new account — assert on account balance delta being non-zero and unauthorized.
