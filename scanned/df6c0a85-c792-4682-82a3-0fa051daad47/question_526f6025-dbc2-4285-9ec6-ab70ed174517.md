[Function: remove_account] Attacker on account A issues a cross-contract call receipt to itself, deletes A while a ReceivedData/PendingDataCount/PostponedReceipt/PostponedReceiptId row is pending for a still-outstanding input data id, then recreates A. Preconditions: A has an outstanding postponed action receipt awaiting a data dependency (predecessor calls promise_then targeting A). Sequence: 1) receipt with two input data ids sent to A, one delivered (PendingDataCount decremented, ReceivedData/PostponedReceipt written), one still pending; 2) A executes DeleteAccountAction; 3) A is recreated by the same predecessor. Invariant: value/authorization conservation — a receipt should not resolve for an account it was never sent to. Impact: the second data dependency arrives after recreation and the runtime looks up PostponedReceiptId/PostponedReceipt for account A that predates its recreation, resuming a postponed action receipt with the old actor_id context against the new account. Proof: unit test comparing set(TrieKey variants written during postponed-receipt setup for A) vs set(TrieKey variants removed by remove_account); assert non-empty symmetric difference and drive a runtime apply test where the stale receipt fires post-recreation.
