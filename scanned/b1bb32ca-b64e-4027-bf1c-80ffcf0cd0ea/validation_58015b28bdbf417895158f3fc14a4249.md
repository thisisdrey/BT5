### Title
Unvalidated `reward_address` in Snowbridge delivery receipts permanently burns relayer rewards - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The external report's core invariant is: an unprivileged actor can nominate an arbitrary, unvalidated "referral"/reward-destination address for a protocol-tracked fee, and if that address can never claim the funds, the fee is permanently lost instead of reaching a legitimate beneficiary. The same broken invariant exists in Snowbridge's Outbound Queue V2 delivery-receipt flow: the `reward_address` that ultimately receives the relayer fee is taken verbatim from Ethereum-side event data and is never validated to correspond to a real, controllable Polkadot account before the fee is irreversibly credited and the pending order is destroyed.

### Finding Description
`Pallet::process_delivery_receipt` in [1](#0-0)  is the entrypoint that pays out the fee (`order.fee`) that was locked when the original message was queued via `do_process_message` (see the `PendingOrder` construction) [2](#0-1) .

The reward destination comes straight from the `DeliveryReceipt.reward_address` field, a raw `[u8; 32]` decoded from the `InboundMessageDispatched` Solidity event emitted on Ethereum: [3](#0-2) 

The pallet's only special-case handling is a check for the all-zero sentinel (in which case it falls back to the submitting relayer); any other 32-byte value — including addresses derived from unspendable/unkeyed data, or values that simply don't correspond to any real Polkadot account — is accepted as-is and used to permanently register the reward: [4](#0-3) 

`T::RewardPayment::register_reward` credits `RelayerRewards` for that arbitrary account (see the analogous accounting pattern in `pallet_bridge_relayers::register_relayer_reward`, which simply mutates the map keyed by whatever `AccountId` it is given, with no existence/claimability check) [5](#0-4) . Immediately after, `PendingOrders` is removed for that `nonce` [6](#0-5) , so there is no retry or reconciliation path — the fee value is settled exactly once, to whatever address was embedded in the Ethereum-side event, with no proof that this address is bound to a controllable key on the Polkadot side.

This mirrors the reported bug class precisely: the party that controls the "reward/referral" destination field (here, whoever triggers the dispatch on the Ethereum Gateway contract that emits `reward_address`) can set it to an address nobody can claim from, and the protocol-tracked fee (`order.fee`, funded up-front by the original message sender) is burned rather than paid to a real participant — reducing usable value in the bridge reward pot with no recovery mechanism, exactly as the referral-griefing report describes for a fee-splitting mechanism.

### Impact Explanation
Every successful message that carries a nonzero `fee` can have its entire relayer reward permanently stranded if `reward_address` is not a real, key-controlled `AccountId32`. Because `PendingOrders` is removed unconditionally once `process_delivery_receipt` succeeds, there is no way to re-attempt payment to a corrected address. This is a "public underpriced work" / "permanent … bridge-state lock" outcome under the accepted impact categories: relayers effectively donate delivery work for free whenever the reward destination is misconfigured or adversarially chosen, and the fee capital sits inert in `RelayerRewards` forever, degrading the incentive model that keeps Snowbridge message delivery running.

### Likelihood Explanation
No malicious peer, validator, governance actor, or leaked key is required. The `reward_address` bytes originate from the Ethereum-side event data associated with dispatching the message, and `process_delivery_receipt` performs no validation beyond the all-zero-sentinel check before crediting the reward and destroying the pending order. Any dead/unkeyed 32-byte value (e.g. `0xdead...`, a hash with no known private key, a burn-style constant) passes the existing checks (`GatewayAddress` match and valid pending `nonce`) and results in silent, permanent loss of the fee.

### Recommendation
Validate `reward_address` before crediting `RewardPayment` — e.g., reject/park orders whose destination cannot be shown to correspond to a legitimate, previously-registered or well-formed account, or require the reward destination to be supplied and bound at message-submission time by a trusted party (the relayer claiming the reward, as is intended, rather than data sourced from the Ethereum event that any caller of the Gateway can influence). At minimum, keep the `PendingOrder` (or an equivalent reward record) recoverable/re-payable instead of unconditionally removing it, so a misdirected reward is not unrecoverably burned.

### Proof of Concept
1. A message is queued via `do_process_message`, creating `PendingOrders[nonce] = { fee: F, .. }` [2](#0-1) .
2. The Ethereum-side dispatch of that message emits `InboundMessageDispatched(nonce, topic, success, reward_address)` with `reward_address` set to an arbitrary 32 bytes that do not correspond to any keyed Polkadot account (not the all-zero sentinel, so the relayer-fallback branch is skipped).
3. A relayer submits this receipt through `submit_delivery_receipt` → `process_delivery_receipt(relayer, receipt)`.
4. `receipt.reward_address` (arbitrary/unclaimable) is used directly as `reward_account`; `T::RewardPayment::register_reward(&reward_account, .., order.fee)` credits the fee to that account [7](#0-6) , matching the integration-test pattern that already exercises this exact code path with an attacker-chosen `reward_address` [8](#0-7) .
5. `PendingOrders::remove(nonce)` executes unconditionally; the fee `F` is now permanently stuck in `RelayerRewards` under an address nobody can call `claim_rewards` from, with no path to reclaim or redirect it.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

		pub(crate) fn register_relayer_reward(
			reward_kind: T::Reward,
			relayer: &T::AccountId,
			reward_balance: T::RewardBalance,
		) {
			if reward_balance.is_zero() {
				return;
			}

			RelayerRewards::<T, I>::mutate(
				relayer,
				reward_kind,
				|old_reward: &mut Option<T::RewardBalance>| {
					let new_reward =
						old_reward.unwrap_or_else(Zero::zero).saturating_add(reward_balance);
					*old_reward = Some(new_reward);

					tracing::trace!(
						target: crate::LOG_TARGET,
						?relayer,
						?reward_kind,
						?new_reward,
						"Relayer can now claim reward for serving payer"
					);

					Self::deposit_event(Event::<T, I>::RewardRegistered {
						relayer: relayer.clone(),
						reward_kind,
						reward_balance,
					});
				},
			);
