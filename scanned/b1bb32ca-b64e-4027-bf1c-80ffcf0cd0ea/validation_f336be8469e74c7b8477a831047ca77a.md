### Title
Reentrancy through external-asset transfer callback lets `redeem()`/`mint()` act on stale `PsmDebt`, desynchronizing debt accounting from the real reserve - (File: substrate/frame/psm/src/lib.rs)

### Summary
`pallet-psm`'s `redeem()` (and symmetrically `mint()`) follows the exact broken pattern the external report describes for `LineOfCredit::_close()`: it performs the external token transfer to/from a caller-influenced asset **before** committing the accounting state that the transfer's own guard conditions depend on. This opens a window for a token with a transfer hook (an ERC777-style "extensive" asset, analogous to any `fungibles` implementation that calls back into the runtime on transfer) to re-enter the pallet and act on a stale `PsmDebt` value, exactly as the lender re-entered `_close()` before `count` was decremented.

### Finding Description
In `redeem()`: [1](#0-0) 
reads `current_debt` and checks `current_debt >= effective_internal_net`, and checks the live reserve balance. [2](#0-1) 
then burns the caller's internal asset and **transfers the external asset out to the caller** via `T::Fungibles::transfer`.

Only after this external transfer completes does the pallet update its bookkeeping: [3](#0-2) 
`PsmDebt::<T>::mutate(..., |debt| *debt = debt.saturating_sub(effective_internal_net))`.

This is a textbook checks-effects-interactions violation identical in shape to the reported bug: the "effects" (`PsmDebt` decrement) happen strictly *after* the "interaction" (external asset transfer). If the registered `external_asset` implementation invokes caller-controlled code on transfer (this is exactly the class of asset the report's `RevenueTokenWithHook`/ERC777 exemplifies — any `fungibles::Mutate` backing whose `transfer` triggers a hook, e.g. contract-controlled or bridged/foreign assets wired into `T::Fungibles`), the recipient can re-enter `redeem()` (or `mint()`) for the same `(internal_asset, external_asset)` pair from within the hook, before the outer call's `PsmDebt::mutate` executes.

Because Rust call frames unwind LIFO, the *outer* call's decrement only applies after all nested re-entrant calls return. Every nested call therefore reads the same **stale** `current_debt` at line 848, so the `ensure!(current_debt >= effective_internal_net, Error::<T>::InsufficientReserve)` guard (line 849) is checked against a value that has not yet reflected any of the in-flight redemptions in the call stack — the exact analog of the original bug's lender repeatedly reading a `count`/deposit value that hadn't been zeroed yet. The same stale-read problem applies to the debt-ceiling checks in `mint()`: [4](#0-3) 
`current_total_psm_debt` and `PsmDebt::<T>::get` are read before the `T::Fungibles::transfer`/`mint_into` calls, and `PsmDebt::<T>::insert(new_debt)` is only committed afterward (line 756) — so nested re-entrant mints during the transfer/mint hooks can each pass the `ExceedsMaxPsmDebt` checks against the same pre-reentry debt figures.

Existing guards do not stop this path:
- `ensure!(current_debt >= effective_internal_net, ...)` (line 849) and `ensure!(new_debt <= max_debt, ...)` (line 741) are storage reads taken before the external call, not re-validated after it, so they cannot see concurrent nested mutations from the same transaction's call stack.
- The reserve check `if reserve < external_out { ... }` (lines 851-855) reads live balance via `Self::get_reserve`, so raw fund draining beyond actual reserve is bounded — but the **debt bookkeeping** (`PsmDebt`, `total_psm_debt`) used for risk limits (`max_debt`, `ExceedsMaxPsmDebt`) is not similarly bounded, since it's a pallet-tracked counter, not a live balance query.
- There is no reentrancy guard anywhere in the pallet call path (`redeem`/`mint`); nothing prevents the pallet's own dispatchable from being re-entered mid-execution via the external asset's transfer hook.

### Impact Explanation
The corrupted value is `PsmDebt::<T>` (per `(internal_asset, external_asset)`) and `total_psm_debt`, which back the debt-ceiling risk controls (`Error::ExceedsMaxPsmDebt`) that gate how much of the internal stablecoin can be minted against a given reserve. By re-entering during the external-asset transfer, an attacker can cause `PsmDebt` to under-track actual outstanding debt (via repeated `saturating_sub` decrements applied to a stale, unchanged base) or, on the mint path, allow the same stale debt reading to be used to justify multiple nested mints that collectively exceed `info.max_debt`/`max_asset_debt`, defeating the peg-stability and reserve-solvency invariant the PSM is designed to enforce. This is a runtime-level accounting-integrity bug (implementation bug that compromises intended behavior of a Substrate-based pallet) rather than fund theft bounded purely by live balances, but it desynchronizes the debt ledger from real reserve backing, which is precisely the invariant PSM design depends on to remain solvent and to safely gate future `mint()`/`redeem()` operations.

### Likelihood Explanation
This requires the runtime operator to have approved (`add_external_asset`) an external asset whose `fungibles::Mutate::transfer` implementation invokes caller-reachable code on transfer/receive — the same "if you add malicious things, malicious things happen" scenario the original judge explicitly rejected as a valid excuse, since the vulnerable pattern (external call before state commit) is squarely in the pallet's own control flow, not a property of the token being "malicious" per se. No validator, collator, governance, or admin compromise is needed — any unprivileged holder of the internal asset who also controls (or uses) a hook-bearing external asset already approved for the PSM can trigger this purely through the public `redeem`/`mint` extrinsics.

### Recommendation
Apply checks-effects-interactions ordering: update `PsmDebt::<T>` (and any global `total_psm_debt` accounting) **before** invoking `T::Fungibles::transfer`/`mint_into`/`burn_from` for the external asset, or add an explicit reentrancy guard around `mint()`/`redeem()` so that a nested re-entrant call fails immediately rather than reading stale debt state.

### Proof of Concept
1. Governance/operator approves an `external_asset` for a PSM instance via `add_external_asset` where the asset's `fungibles::Mutate` implementation is backed by a token that invokes a callback on the recipient when tokens are transferred out (analogous to `RevenueTokenWithHook`/ERC777 in the original report).
2. Attacker holds internal asset and calls `redeem(internal_asset, external_asset, internal_amount, max_fee)`.
3. Execution reaches `T::Fungibles::transfer(external_asset, &psm_account, &who, external_out, ...)` at [5](#0-4) , which invokes the attacker's registered hook.
4. Inside the hook (still within the outer `redeem` call, before line 889 executes), the attacker re-enters `redeem()` for the same `(internal_asset, external_asset)` pair; `PsmDebt::<T>::get` at line 848 returns the same value the outer call already read, so `ensure!(current_debt >= effective_internal_net, ...)` passes again as if the outer redemption had never happened.
5. The nested call burns more internal asset and transfers more external asset out, then (deepest-first) each nested call finally applies `PsmDebt::<T>::mutate(saturating_sub(...))` on unwind — the debt ledger no longer matches the sequence of real transfers, and the identical mistaken-stale-read pattern can be repeated on the `mint()` path to bypass `ExceedsMaxPsmDebt` debt-ceiling checks (lines 732-741).
