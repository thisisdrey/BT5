## Title
ERC20Transactor credits full `amount` on withdrawal without verifying the checking account's actual balance delta, allowing fee-on-transfer/deflationary ERC20 tokens to insolvent the shared escrow and permanently lock other users' funds - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` move ERC20 tokens into/out of a shared `TransfersCheckingAccount` escrow by calling the Solidity `IERC20::transfer`/`transferFrom` ABI via `pallet_revive::Pallet::<T>::bare_call`, and treat a decoded `true` boolean return as proof that exactly `amount` tokens moved. [1](#0-0) [2](#0-1)  No balance-delta check of the checking account is performed before crediting `Erc20Credit(amount)` into `AssetsInHolding`.

### Finding Description
On `withdraw_asset_with_surplus`, the transactor calls `transfer(checking_address, amount)` from the user's account, and if the call doesn't revert and the ABI-decoded return is `true`, it unconditionally mints `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — i.e., it assumes the checking account's real ERC20 balance increased by exactly `amount`. [3](#0-2) 

`pallet_revive` permits permissionless deployment of arbitrary Solidity contracts (any user can deploy an ERC20-like contract and have it treated as a fungible asset once matched by `Matcher::matches_fungibles`). A contract can implement `transfer`/`transferFrom` to return `true` while moving less than `value` to `to` — this is the well-known "fee-on-transfer" / deflationary ERC20 pattern explicitly called out in the original report's referenced [weird-erc20](https://github.com/d-xo/weird-erc20) catalogue. The `ERC20Transactor` code has correctly hardened against the *missing-return-value* and *reverting-on-false* classes of bugs (it checks `did_revert()` and ABI-decodes the boolean), but it never verifies that the token amount actually received by `TransfersCheckingAccount` matches `amount`.

The same blind-trust pattern repeats symmetrically in `deposit_asset_with_surplus`, which transfers `amount` out of the checking account to a beneficiary and treats any `true` return as full settlement — again without checking that the checking account's balance decreased by exactly `amount`, or that it held enough real tokens for all outstanding `Erc20Credit` entries. [4](#0-3) 

Because `Erc20Credit`'s own imbalance-accounting logic performs no runtime-level balance enforcement by design (as documented in its own comment), the correctness of the entire escrow depends solely on the ERC20 contract's return value matching real token movement — an assumption that a fee-on-transfer or rebasing token violates by construction, not by malice of any privileged actor. [5](#0-4) 

### Impact Explanation
If a user (any unprivileged holder of a fee-on-transfer ERC20) withdraws such a token through this transactor, the checking account receives `amount - fee` real tokens but the XCM system is credited a full `amount` in `AssetsInHolding`. Over repeated withdraw/deposit cycles this creates a growing shortfall between the checking account's actual on-chain ERC20 balance and the sum of value the runtime believes is escrowed and payable. Eventually deposit attempts for other, honest users will fail or only partially settle once the real balance is depleted — a permanent fund-lock/insolvency condition for later claimants, functionally equivalent to unbacked issuance of escrowed value. This satisfies the "Balances… must conserve value and settle exactly once to the rightful beneficiary and amount" and "permanent user-fund… lock" impact classes, and requires no malicious peer, relayer, validator, or governance actor — any user deploying and using an ordinary fee-on-transfer contract via `pallet_revive` triggers it.

### Likelihood Explanation
Deploying an ERC20-like contract via `pallet_revive` is fully permissionless, and fee-on-transfer/deflationary tokens are a well-documented, common real-world ERC20 pattern (as cited directly in the original report). Triggering the underpayment merely requires performing an ordinary XCM withdraw/deposit against such a token through this transactor — no privileged role or off-chain coordination is needed, making the likelihood high once such an asset is registered/matched by `Matcher`.

### Recommendation
Before crediting `Erc20Credit(amount)` in `withdraw_asset_with_surplus`, read the checking account's ERC20 `balanceOf` before and after the `transfer` call and credit the actual observed delta rather than the requested `amount`. Symmetrically, in `deposit_asset_with_surplus`, verify the checking account's balance decreased by the intended amount (or otherwise fail/roll back the AssetsInHolding accounting) instead of trusting the boolean return value alone.

### Proof of Concept
1. Deploy a Solidity contract via `pallet_revive` implementing `IERC20` where `transfer`/`transferFrom` deduct a fee (e.g., burn 5%) before crediting `to`, but still `return true` on success — a standard "weird ERC20" pattern.
2. Register/allow this asset to be matched by the configured `Matcher` for `ERC20Transactor` (as is done for arbitrary user-deployed ERC20s reachable via the precompile/transactor path shown in `erc20_transactor.rs`).
3. User A executes an XCM `WithdrawAsset` of `amount = 1000` of this token. `withdraw_asset_with_surplus` calls `transfer(checking_address, 1000)`, the contract moves only `950` to the checking account and returns `true`; the code credits `Erc20Credit(1000)` regardless. [6](#0-5) 
4. Repeat with more users/rounds; the checking account's real ERC20 balance accumulates a persistent 5%-per-transfer shortfall versus the sum of `Erc20Credit` amounts the runtime believes are escrowed.
5. Eventually a `deposit_asset_with_surplus` call for a legitimate beneficiary requests `transfer(beneficiary, amount)` from the checking account for an `amount` that exceeds its actual remaining balance; the underlying ERC20 either reverts (breaking `DepositAsset` and locking the credited value in limbo) or, in more corrupted implementations, returns `true` on partial/failed transfer, permanently shorting the beneficiary while the code reports success. [7](#0-6)

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}
