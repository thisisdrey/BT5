## Analysis

The external report's core broken invariant is: **a "deadline" that supposedly bounds when an action is safe to execute is trivially satisfiable or can be reset by an untrusted party, so the temporal safety check becomes meaningless** — a stale or adversarially-timed action can still execute far outside its intended validity window.

The closest verifiable local analog is in `pallet_treasury`'s spend/payout lifecycle. A `spend` is approved with a bounded claim window (`expire_at`), enforced by `ensure!(spend.expire_at > now, Error::<T, I>::SpendExpired)` in `payout`. However, `payout` — which is **permissionless** (`ensure_signed(origin)?`, not restricted to the beneficiary) — unconditionally resets `spend.expire_at` to `now + PayoutPeriod` on every valid attempt, regardless of caller identity and regardless of whether the attempt ultimately succeeds: [1](#0-0) 

This mirrors the reported bug class: the temporal guard (`expire_at`) that is supposed to force a bounded claim window can be pushed out indefinitely by anyone, at will, defeating the purpose of the expiry (an effectively unbounded/"max deadline" claim window), and each reset re-triggers `T::Paymaster::pay(...)`.

### Title
Permissionless renewal of treasury spend expiry defeats bounded claim window - (File: `substrate/frame/treasury/src/lib.rs`)

### Summary
`Pallet::payout` is callable by any signed account for any `SpendIndex`, not just the beneficiary. Every valid call (`PaymentState::Pending | PaymentState::Failed`) unconditionally resets `spend.expire_at = now.saturating_add(T::PayoutPeriod::get())` before the transfer outcome is even known, and re-invokes `T::Paymaster::pay`.

### Finding Description
`spend()` approves a treasury spend with a bounded validity window: it must be claimed within `[valid_from, expire_at)` where `expire_at = valid_from + PayoutPeriod`. `payout()` is intended to consume that spend within this bounded window, after which `check_status()` / natural expiry reclaims stale, unclaimed approvals from storage: [2](#0-1) 

The `payout` dispatchable, however, is only gated by `ensure_signed(origin)` — no check that the caller is the beneficiary or any privileged party — and on every valid attempt it resets `expire_at` before the payment result is confirmed: [1](#0-0) 

Because any account can call `payout(index)` repeatedly (e.g., in an environment where `T::Paymaster` transiently fails, moving status to `Failed` via `check_status`, then calling `payout` again resets `expire_at` and re-attempts `T::Paymaster::pay`), the `SpendExpired` guard never fires as designed. The spend's temporal bound — the exact mechanism meant to guarantee that stale/undesirable-condition spends eventually die and free storage / return to normal treasury bookkeeping — can be kept alive forever by an unprivileged third party. This is functionally the same broken invariant as the "unsafe max deadline" report: a check meant to bound an action's validity window is rendered non-binding because the party who benefits from bypassing it (or an unrelated third party) fully controls when/whether the check is satisfied.

### Impact Explanation
This falls under "public underpriced work that degrades... stalls... processing" and "permanent... bridge-state lock" categories: for `Paymaster` implementations backed by cross-chain payment execution (e.g., `PayOverXcm`), each permissionless `payout` retry re-triggers outbound XCM send attempts from the treasury's sovereign/paymaster account, letting any signed account force unbounded, indefinite re-attempts of a payment against the treasury's payment pipeline with only the extrinsic's own weight/fee cost — the spend record and its associated payment side-effects never naturally expire as designed, so state that governance intended to be reclaimed after `PayoutPeriod` can be kept perpetually "live" and re-triggered by an unrelated account.

### Likelihood Explanation
Likelihood is high: `payout` requires only `ensure_signed`, no relationship to the beneficiary or spend proposer, and the reset happens on the common `Pending`/`Failed` path that is reached naturally whenever a `Paymaster` transfer fails or hasn't completed — no privileged actor, governance action, or malicious infrastructure component is needed, satisfying the "public entrypoint, unprivileged attacker" requirement.

### Recommendation
Do not unconditionally reset `expire_at` on every `payout` attempt. Reset it only when the previous attempt is confirmed to have genuinely failed (as already tracked via `check_status`/`PaymentState::Failed`), and/or restrict who can retry a payout to the beneficiary or a bounded number of retries, so the original `PayoutPeriod` bound (mirroring "let the caller provide/consume a real deadline" from the source report) is actually enforced rather than being infinitely renewable by third parties.

### Proof of Concept
1. Governance/`SpendOrigin` calls `spend(asset_kind, amount, beneficiary, None)` → `Spends[0]` created with `expire_at = now + PayoutPeriod`.
2. Any signed account `A` (unrelated to `beneficiary`) calls `payout(0)`. `expire_at` is reset to `now + PayoutPeriod`, and `T::Paymaster::pay` is invoked.
3. Suppose the paymaster transfer fails; `check_status(0)` is called (by anyone) transitioning status to `Failed`.
4. Account `A` calls `payout(0)` again before the (already-reset) `expire_at` — `expire_at` resets again, and `T::Paymaster::pay` is re-invoked.
5. Repeat steps 3–4 indefinitely: `Spends[0]` never satisfies `now > spend.expire_at` in `check_status`, so it is never pruned by natural expiry, and outbound payment attempts (potentially cross-chain XCM sends via `PayOverXcm`) can be re-triggered indefinitely by an account with no relation to the spend.

		///
		/// ## Dispatch Origin
		///
		/// Must be [`Config::SpendOrigin`] with the `Success` value being at least
		/// `amount` of `asset_kind` in the native asset. The amount of `asset_kind` is converted
		/// for assertion using the [`Config::BalanceConverter`].
		///
		/// ## Details
		///
		/// Create an approved spend for transferring a specific `amount` of `asset_kind` to a
		/// designated beneficiary. The spend must be claimed using the `payout` dispatchable within
		/// the [`Config::PayoutPeriod`].
		///
		/// ### Parameters
		/// - `asset_kind`: An indicator of the specific asset class to be spent.
		/// - `amount`: The amount to be transferred from the treasury to the `beneficiary`.
		/// - `beneficiary`: The beneficiary of the spend.
		/// - `valid_from`: The block number from which the spend can be claimed. It can refer to
		///   the past if the resulting spend has not yet expired according to the
		///   [`Config::PayoutPeriod`]. If `None`, the spend can be claimed immediately after
		///   approval.
		///
		/// ## Events
		///
		/// Emits [`Event::AssetSpendApproved`] if successful.
		#[pallet::call_index(5)]
		#[pallet::weight(T::WeightInfo::spend())]
		pub fn spend(
			origin: OriginFor<T>,
			asset_kind: Box<T::AssetKind>,
			#[pallet::compact] amount: AssetBalanceOf<T, I>,
			beneficiary: Box<BeneficiaryLookupOf<T, I>>,
			valid_from: Option<BlockNumberFor<T, I>>,
		) -> DispatchResult {
			let max_amount = T::SpendOrigin::ensure_origin(origin)?;
			let beneficiary = T::BeneficiaryLookup::lookup(*beneficiary)?;

			let now = T::BlockNumberProvider::current_block_number();
			let valid_from = valid_from.unwrap_or(now);
			let expire_at = valid_from.saturating_add(T::PayoutPeriod::get());
			ensure!(expire_at > now, Error::<T, I>::SpendExpired);

			let native_amount =
				T::BalanceConverter::from_asset_balance(amount, *asset_kind.clone())
					.map_err(|_| Error::<T, I>::FailedToConvertBalance)?;

			ensure!(native_amount <= max_amount, Error::<T, I>::InsufficientPermission);

			with_context::<SpendContext<BalanceOf<T, I>>, _>(|v| {
				let context = v.or_default();
				// We group based on `max_amount`, to distinguish between different kind of
				// origins. (assumes that all origins have different `max_amount`)
				//
				// Worst case is that we reject some "valid" request.
				let spend = context.spend_in_context.entry(max_amount).or_default();

				// Ensure that we don't overflow nor use more than `max_amount`
				if spend.checked_add(&native_amount).map(|s| s > max_amount).unwrap_or(true) {
					Err(Error::<T, I>::InsufficientPermission)
				} else {
					*spend = spend.saturating_add(native_amount);
					Ok(())
				}
			})
			.unwrap_or(Ok(()))?;

			let index = SpendCount::<T, I>::get();
			Spends::<T, I>::insert(
				index,
				SpendStatus {
					asset_kind: *asset_kind.clone(),
					amount,
					beneficiary: beneficiary.clone(),
					valid_from,
					expire_at,
					status: PaymentState::Pending,
				},
			);
			SpendCount::<T, I>::put(index + 1);

			Self::deposit_event(Event::AssetSpendApproved {
				index,
				asset_kind: *asset_kind,
				amount,
				beneficiary,
				valid_from,
				expire_at,
			});
			Ok(())
		}

		pub fn payout(origin: OriginFor<T>, index: SpendIndex) -> DispatchResult {
			ensure_signed(origin)?;
			let mut spend = Spends::<T, I>::get(index).ok_or(Error::<T, I>::InvalidIndex)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now >= spend.valid_from, Error::<T, I>::EarlyPayout);
			ensure!(spend.expire_at > now, Error::<T, I>::SpendExpired);
			ensure!(
				matches!(spend.status, PaymentState::Pending | PaymentState::Failed),
				Error::<T, I>::AlreadyAttempted
			);

			let id = T::Paymaster::pay(&spend.beneficiary, spend.asset_kind.clone(), spend.amount)
				.map_err(|_| Error::<T, I>::PayoutError)?;

			spend.status = PaymentState::Attempted { id };
			spend.expire_at = now.saturating_add(T::PayoutPeriod::get());
			Spends::<T, I>::insert(index, spend);

			Self::deposit_event(Event::<T, I>::Paid { index, payment_id: id });

			Ok(())
		}
