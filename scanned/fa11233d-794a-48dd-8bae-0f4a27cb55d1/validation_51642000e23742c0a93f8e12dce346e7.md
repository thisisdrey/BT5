## Analog Identified: `ERC20Transactor` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`

The external report's core broken invariant is: **a public entrypoint recomputes a token amount that can legitimately round/settle to zero, then unconditionally attempts an ERC20 `transfer` of that amount, and the underlying token can revert on a zero-value transfer, blocking otherwise-legitimate settlement.** The closest verifiable local analog is the `ERC20Transactor` used by Asset Hub's XCM `AssetTransactors` to move `pallet-revive`-backed ERC20 tokens.

### Title
Unconditional zero-amount `IERC20::transfer` calls in `ERC20Transactor` allow public XCM messages to revert legitimate asset settlement - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` extract `amount` from the XCM `Asset` via `Matcher::matches_fungibles(what)` and pass it directly, without any zero check, into an on-chain `IERC20::transferCall { value: EU256::from(amount) }` executed against an arbitrary ERC20 contract via `pallet_revive::Pallet::<T>::bare_call`. [1](#0-0) [2](#0-1) 

### Finding Description
Any unprivileged user or incoming bridge/XCM message can construct an XCM program (e.g. via `pallet_xcm::execute`, an incoming reserve-transfer, or a Snowbridge inbound message routed through Asset Hub) that specifies a `Fungible` asset amount of `0`, or one that becomes `0` after upstream fee/multiplier/rounding logic elsewhere in the XCM pipeline. `ERC20Transactor` forwards this amount verbatim to `IERC20::transferCall`. If the target ERC20 contract implements the (common, standards-permitted) behavior of reverting on a zero-value `transfer` — exactly the class of token behavior described in the referenced Sherlock report — `bare_call` returns `did_revert() == true`, and the transactor returns `XcmError::FailedToTransactAsset("ERC20 contract reverted")`. [3](#0-2) [4](#0-3) 

Existing guards elsewhere in the codebase (e.g. `pallet-staking`'s `make_payout`, `pallet-nomination-pools`' `do_reward_payout`, and `pallet-assets`' zero-transfer no-op behavior) explicitly special-case `amount.is_zero()` before attempting a transfer, precisely to avoid this class of bug. [5](#0-4) [6](#0-5) 
`ERC20Transactor` has no equivalent guard, and `pallet-revive`'s own `fungibles::Mutate` implementation for ERC20s (`burn_from`/`mint_into`) has the identical gap. [7](#0-6) [8](#0-7) 

### Impact Explanation
Since `ERC20Transactor` is one of the `AssetTransactors` wired into Asset Hub's XCM configuration, any XCM message routing a zero (or rounded-to-zero) amount of an ERC20-backed asset causes `FailedToTransactAsset`, aborting the XCM instruction. This can permanently block settlement of otherwise-valid multi-asset XCM programs (e.g. bridged transfers, reserve-transfers with fee remnants) whenever the ERC20 asset leg computes to zero, matching the required "public underpriced work that degrades block production or stalls bridge processing" / "permanent user-fund or bridge-state lock" impact class — assets already withdrawn from the user for other legs of the same message may be stuck or require manual recovery via `SetAssetClaimer`, while the intended beneficiary never receives settlement. [9](#0-8) 

### Likelihood Explanation
Reaching this path requires no privileged access: any account that can submit `pallet_xcm::execute` or trigger an incoming reserve/bridge transfer that resolves to an ERC20-backed asset with a computed amount of zero can trigger it. Fee-splitting, multi-asset batching, and rounding in upstream XCM converters (as seen in the `outbound-queue`/`inbound-queue` converters that already explicitly test for and reject `ZeroAssetTransfer` in other paths) demonstrate that zero-amount asset legs are a realistic, recognized occurrence in this codebase's XCM flows — but `ERC20Transactor` was not given the same protection. [10](#0-9) 

### Recommendation
Add an explicit zero-amount short-circuit in `ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` (and in `pallet_revive::impl_fungibles::{burn_from, mint_into}`), returning success with zero fungible credit/no-op instead of invoking `IERC20::transferCall` when `amount == 0`, mirroring the zero-check pattern already used by `pallet-staking` and `pallet-nomination-pools`.

### Proof of Concept
1. Deploy or reference an ERC20 contract behind `pallet-revive` whose `transfer` function reverts when `value == 0` (a standards-permitted, documented ERC20 behavior).
2. Register this contract as a recognized asset for `ERC20Transactor` on Asset Hub.
3. Submit an XCM program (via `pallet_xcm::execute` or an incoming reserve transfer) that includes a `WithdrawAsset`/`DepositAsset` instruction for this ERC20 asset with `Fungible(0)`, or with an amount that is computed to `0` after upstream fee deduction.
4. Observe `ERC20Transactor::withdraw_asset_with_surplus`/`deposit_asset_with_surplus` call `bare_call` → `IERC20::transferCall{value:0}` → contract reverts → `Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))`, aborting the whole XCM program and stalling settlement for the involved parties. [11](#0-10)
