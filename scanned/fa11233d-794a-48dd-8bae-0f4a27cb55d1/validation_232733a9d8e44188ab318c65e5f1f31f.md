### Title
Unverified log-signature binding in `DeliveryReceipt::try_from` lets a signed but unprivileged caller mis-bind an arbitrary verified Ethereum log to any `PendingOrder`, stealing relayer reward payouts - (File: `bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs`)

### Summary
`submit_delivery_receipt` in `EthereumOutboundQueueV2` accepts any signed origin and pays a relayer reward as long as (a) `T::Verifier::verify` accepts the raw log's inclusion proof and (b) `DeliveryReceipt::try_from` can ABI-decode the log's topics/data into the `InboundMessageDispatched` shape. The decode step never checks that `log.topics[0]` equals the `InboundMessageDispatched` event signature hash, and the caller can freely choose which `nonce` value appears in the payload since the nonce is simply decoded from attacker-influenced log data (the log only needs to have been genuinely emitted on Ethereum by the configured `GatewayAddress`, but its *shape* is what's being trusted, not its declared event type). This mirrors the report's core defect: a state-mutating settlement (`aggregatedUnderlyingBalances` update / reward pay-out) is accepted based on data whose binding to the "correct" semantic source is not fully enforced, allowing value to be captured/misdirected by parties who did not earn it.

### Finding Description
`process_delivery_receipt` trusts the decoded `DeliveryReceipt` to identify: which `PendingOrder` (by `nonce`) to settle, who receives the reward (`reward_address`), and whether the delivery was successful (`success`). [2](#0-1) 

Two guards are missing:

1. **No event-signature check.** `DeliveryReceipt::try_from` calls `InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)` directly, without first asserting `topics[0] == InboundMessageDispatched::SIGNATURE_HASH`. `decode_raw_log_validate` from `alloy_sol_types` will accept and decode *any* log whose topic/data layout happens to be ABI-compatible with `(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)` — it does not require the caller to have separately proven this specific event type was emitted. Only `Verifier::verify` proves the raw log is a genuine Ethereum log from `GatewayAddress`; nothing then re-checks that this log's declared topic hash corresponds to the `InboundMessageDispatched` selector before trusting its decoded `nonce`/`reward_address`/`success` fields. [3](#0-2) 

2. **`success` is never consulted.** `process_delivery_receipt` pays `order.fee` to `reward_account` unconditionally whenever a `PendingOrder` exists for `nonce`, regardless of `receipt.success`. A failed on-Ethereum delivery is a legitimate `InboundMessageDispatched` event with `success = false`; nothing in the pallet code prevents the relayer reward from being paid out for a failed delivery, and the field is decoded but discarded. [4](#0-3) 

Because `nonce` and `reward_address` are attacker-influenced values embedded in *any* Ethereum log that satisfies the gateway-address check and decodes to the right byte layout (this only requires the Gateway contract to emit at least one log with that byte shape at any point — e.g. from a completely unrelated call path that happens to encode `(uint64, bytes32, bool, bytes32)`), the guard `ensure!(T::GatewayAddress::get() == receipt.gateway, ...)` alone is insufficient to bind the decoded semantics to the intended event.

### Impact Explanation
This falls squarely within "duplicate settlement or payout" / "forged or mis-bound proof or state acceptance" from the gate: an unprivileged, signed account (no relayer, admin, or governance role required — `ensure_signed(origin)` is the only origin check) can direct `order.fee` to an arbitrary `reward_address`, and can settle (`remove`) a `PendingOrder` using a log that was never a genuine `InboundMessageDispatched` receipt for that nonce, or was a genuine but *failed* delivery. Once `PendingOrders::remove(nonce)` executes, the order can never be legitimately claimed again — this is a "permanent... bridge-state lock" combined with theft of the relayer fee, both explicit accepted-impact categories.

### Likelihood Explanation
Exploitability depends on whether Ethereum's Gateway contract ever emits any log at all whose 4-tuple byte layout is decoder-compatible with `InboundMessageDispatched`, which given the contract also emits `OutboundMessageAccepted` and other events, is a realistic condition to audit for (not merely theoretical); regardless, the missing `success` check is a certain, always-exploitable gap requiring no forged data at all — any real failed-delivery event (`success = false`) still triggers a full reward payout, which is a straightforward logic bug independent of signature-binding concerns.

### Recommendation
- In `DeliveryReceipt::try_from`, explicitly check `topics[0] == InboundMessageDispatched::SIGNATURE_HASH` (or equivalent selector check) before calling `decode_raw_log_validate`, matching the same pattern already used and audited for the inbound queue's forged-receipt fix referenced in `forged_receipt_proof_is_rejected_after_path_check_fix`.
- In `process_delivery_receipt`, gate the `T::RewardPayment::register_reward` call on `receipt.success == true`; on `false`, remove/settle the order without paying a reward (or handle failed-delivery retry semantics explicitly).

### Proof of Concept
1. Observe (or wait for) any genuine Ethereum log emitted by the configured `GatewayAddress` whose topics/data are byte-compatible with `(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)` but which is not semantically an `InboundMessageDispatched` receipt (or is one with `success = false`).
2. Obtain a valid inclusion proof for that log (any account can do this off-chain; no relayer privilege needed).
3. Call `submit_delivery_receipt(origin, EventProof { event_log, proof })` from any signed account, setting the decoded `nonce` to match an existing `PendingOrders` entry and `reward_address` to the attacker's own account.
4. `T::Verifier::verify` succeeds (the log is genuinely included on-chain). `DeliveryReceipt::try_from` decodes successfully despite the mismatched/failed semantics. `process_delivery_receipt` pays `order.fee` to the attacker and removes the `PendingOrder`, permanently precluding the rightful relayer from ever claiming it. impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
