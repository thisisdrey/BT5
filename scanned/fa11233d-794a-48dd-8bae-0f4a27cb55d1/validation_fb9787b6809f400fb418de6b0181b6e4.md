### Title
Owner cannot invalidate a pending `ERC20Permit` (EIP-2612) signature before its `deadline` — no exposed nonce-bump/cancel path - ([File: substrate/frame/assets/precompiles/src/permit.rs])

### Summary
The `pallet_assets::precompiles::permit` module implements an EIP-2612-style off-chain `permit()` approval, storing a per-`(verifying_contract, owner)` nonce in `Nonces` and consuming it only inside `use_permit`. There is no dispatchable extrinsic, precompile selector, or any owner-callable entry point that lets the signer proactively invalidate an unconsumed permit signature before its `deadline` elapses — exactly the invariant break described in the external report (OpenZeppelin `Nonces`/`increaseNonce`/`useNonce` gap).

### Finding Description
`Nonces<T>` tracks nonces used by `use_permit`/`increment_nonce`, but `increment_nonce` is only ever invoked internally as part of `use_permit` after a valid signature has been checked: [1](#0-0) 

`use_permit` is the sole caller of `increment_nonce`, and it is only reachable through the `permit` precompile call path that requires a *valid* signature over the *current* nonce: [2](#0-1) [3](#0-2) 

There is no owner-facing precompile function (e.g., a `revokePermit`, `invalidateNonce`, or similar EIP-2612-adjacent selector) and no pallet dispatchable that calls `increment_nonce` directly for the owner's own account. Unlike `frame_system::CheckNonce`, where any ordinary signed extrinsic from the account automatically bumps `frame_system::Account::nonce` and thereby invalidates stale signed payloads (as exercised in `pallet-meta-tx`'s `meta_tx_extension_work` test, which explicitly calls `frame_system::Pallet::<Runtime>::inc_account_nonce` to invalidate a pending meta-tx), the permit pallet's `Nonces` storage is a wholly separate, permit-specific nonce space that only advances on a successful `use_permit` call. A signer who has handed out a signed `permit()` message to a relayer/dApp has no way to burn that specific `(verifying_contract, owner)` nonce before the `deadline` — they cannot outrace or cancel it, since no unprivileged code path increments the nonce except successful consumption of the very permit they want to revoke.

This mirrors the reported bug class precisely: OpenZeppelin's base `Nonces` contract also has no `increaseNonce`, and the client had to add a "useNonce()"-style external function so a signer can bump their own nonce independent of consuming a permit. This repository's permit pallet has the identical gap: `increment_nonce` exists but is `pub(crate)`-scoped to internal use only and never exposed as an owner-triggerable dispatch/precompile entry point.

### Impact Explanation
A permit signer who signs an EIP-2612 `permit` (e.g., handing it to a relayer or dApp, or accidentally leaking it) cannot invalidate it before `deadline`. If the relayer/dApp (or anyone who obtained the signature, e.g. via a mempool/off-chain leak) submits it later — even after the signer no longer wants the approval granted — the approval will still execute exactly as signed, because the nonce has not moved. This can result in an unwanted allowance grant to a spender (fund-risk primitive: `transferFrom` up to the granted `value` becomes exercisable by the spender), which the signer had no way to prevent despite wanting to. This falls under "unauthorized execution" / stale-approval acceptance and fund-loss risk categories, since the owner cannot revoke consent that they've already handed out but no longer wish to honor.

### Likelihood Explanation
This is a directly reachable, permissionless path: any owner who has ever produced a `permit` signature (a completely normal, encouraged usage pattern for gasless approvals) is affected. No malicious peer, validator, governance, or leaked key is required — the vulnerability is the *absence* of a cancellation mechanism, not an external actor's misbehavior. The only "trigger" needed is time passing before the owner wants to revoke and someone (a legitimate but now-unwanted relayer, or an adversary who intercepted the off-chain signed message) submitting it to the chain before `deadline`.

### Recommendation
Expose a signer-callable, unprivileged way to burn/advance the permit nonce independent of a successful `use_permit`, e.g.:
- Add a dispatchable/precompile selector such as `invalidateNonce(verifying_contract)` (or a generic `cancelPermit`) that lets `msg.sender`/the signed origin directly call `Pallet::increment_nonce(verifying_contract, caller)` for their own address, mirroring OpenZeppelin's `Nonces::useNonce()` fix referenced in the external report.
- Alternatively, bind the permit nonce to `frame_system::Account::nonce` (or otherwise let ordinary account activity invalidate stale permits), similar to how `pallet-meta-tx`/`CheckNonce` naturally invalidate old signed payloads when the account nonce advances.

### Proof of Concept
1. Owner `O` signs a `permit(owner=O, spender=S, value=V, deadline=D)` for `verifying_contract=C` at `nonce=0`, and shares/loses control of the signed `(v,r,s)` (e.g., gives it to a dApp/relayer, or it leaks off an intercepted request).
2. Owner later decides they no longer want `S` to receive the approval, but there is no `Nonces::increment_nonce` exposed to `O` — calling into `permit.rs`'s public API surface shows only `nonce()` (read-only) and the internal `increment_nonce`/`use_permit` used solely inside the `permit` precompile dispatch: [4](#0-3) 
3. At any point before block time `> D`, anyone holding the signature calls the `permit` precompile function with the original `(owner, spender, value, deadline, v, r, s)`.
4. `use_permit` recomputes the digest against `Nonces::get(C, O) == 0` (unchanged since step 1), the signature matches, and the approval is granted via `do_approve_transfer`/`do_cancel_approval` inside the precompile handler: [3](#0-2) 
5. `O`'s intended revocation never happened on-chain because no code path let them bump `Nonces::<T>` for `(C, O)` themselves — the approval executes despite the owner's wish to cancel it, exactly analogous to the reported OpenZeppelin `Nonces` gap.

	impl<T: Config> Pallet<T> {
		/// Get the current nonce for an owner on a specific verifying contract.
		pub fn nonce(verifying_contract: &H160, owner: &H160) -> U256 {
			Nonces::<T>::get(verifying_contract, owner)
		}

		/// Increment the nonce for an owner on a specific verifying contract.
		/// Returns the new nonce value, or an error if overflow would occur.
		pub fn increment_nonce(verifying_contract: &H160, owner: &H160) -> Result<U256, Error<T>> {
			Nonces::<T>::try_mutate(verifying_contract, owner, |nonce| {
				*nonce = nonce.checked_add(U256::one()).ok_or(Error::<T>::NonceOverflow)?;
				Ok(*nonce)
			})
		}

				s,
