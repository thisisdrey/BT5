## Finding

I found a real local analog: `SwapFirstAssetTrader::refund_weight` in `cumulus/primitives/utility/src/lib.rs` hardcodes `None` as the `amount_out_min` when swapping the residual `Target` fee credit back into the asset originally used by the message sender — the exact same "belief_price = None → slippage protection void" pattern as the Mantra report, but here the protection is fully absent (not even a default max-spread fallback exists in `pallet-asset-conversion`).

### Title
Unprotected zero-slippage refund swap in `SwapFirstAssetTrader::refund_weight` allows draining XCM fee refunds via pool price manipulation - (File: `cumulus/primitives/utility/src/lib.rs`)

### Summary
`SwapFirstAssetTrader` is a `WeightTrader` used by the XCM executor to let users pay execution fees in an asset other than the chain's `Target` fee asset, via `pallet-asset-conversion`. `buy_weight` correctly swaps the user's asset for an *exact* amount of `Target` needed for the fee, bounded by the amount the user supplied [1](#0-0) . However, when unused weight is refunded at the end of message execution, `refund_weight` swaps the leftover `Target` credit back into the user's original asset using `swap_exact_tokens_for_tokens` with `amount_out_min` hardcoded to `None`: [2](#0-1) 

### Finding Description
`pallet-asset-conversion`'s swap implementation only checks the output amount against `amount_out_min` when it is `Some`; when `None` is passed, no bound is enforced at all: [3](#0-2) 

Because `refund_weight` always passes `None`, the refund swap will accept *any* output amount the pool happens to return at execution time — including near-zero — with zero user-supplied price protection. This mirrors the Mantra `belief_price: None` defect exactly: a public-reachable flow performs an internal swap where the natural protection parameter (`amount_out_min`/`belief_price`) is discarded, and no other check substitutes for it (unlike Mantra, which at least retained a `max_spread` default; here there is none).

The corrupted value is the `refund` credit amount returned from the swap inside `refund_weight` — it can be driven arbitrarily low relative to its true value if the `CLIENT_ASSET`/`TARGET_ASSET` pool price shifts between `buy_weight` (start of message execution) and `refund_weight` (end of message execution, or across sequential XCM message processing within the same block that touches the same pool).

### Impact Explanation
An attacker who can influence the pool's spot price for the `Target`/client asset pair between the `buy_weight` and `refund_weight` calls (e.g., via ordinary swap extrinsics against the same `pallet-asset-conversion` pool processed earlier in the same block, or by crafting/ordering their own XCM messages) can cause legitimate users' fee refunds to be swapped at a heavily unfavorable rate, with the difference effectively captured by the pool/attacker. This is value loss for ordinary XCM senders paying fees in non-native assets, reachable without any admin, governance, validator, or relayer involvement — any unprivileged account can trigger it by sending XCM messages that overpay weight in a non-`Target` asset while the pool is manipulable in the same block.

### Likelihood Explanation
Any parachain configuring `SwapFirstAssetTrader` (used e.g. in Penpal's `XcmConfig::Trader`, as shown in `cumulus/parachains/runtimes/testing/penpal/src/xcm_config.rs`) is affected whenever a message overpays weight fees in a non-native, pool-exchangeable asset — a routine, unprivileged scenario. The missing bound is unconditional (`None` is hardcoded, not configurable), so every refund is exposed; the only requirement for exploitation is a same-block price shift in the relevant AMM pool, which is achievable through ordinary swap transactions.

### Recommendation
Pass a genuine minimum-output bound into the refund swap in `refund_weight`, e.g. compute an expected `refund_swap_asset` amount via `QuotePrice` (already a supertrait bound on `SwapCredit`) immediately before swapping, and pass `Some(min_acceptable_amount)` (with a configurable tolerance) instead of `None`. If quoting fails or the tolerance can't be met, keep the credit in the `Target` asset (as already happens on swap failure) rather than accepting an unbounded-loss swap.

### Proof of Concept
1. Configure a parachain with `SwapFirstAssetTrader<Target, AssetConversion, ...>` as in `cumulus/parachains/runtimes/testing/penpal/src/xcm_config.rs` (`XcmConfig::Trader`).
2. Create/seed an `AssetConversion` pool for `(ClientAsset, Target)`.
3. Send an XCM message that overpays weight using `ClientAsset` (e.g., `BuyExecution`/`PayFees` with more than needed) — `buy_weight` swaps just enough `ClientAsset` into `Target` for the fee, per `cumulus/primitives/utility/src/lib.rs:471-489`.
4. Within the same block, execute a large swap against the `(ClientAsset, Target)` pool (ordinary `pallet-asset-conversion::swap_exact_tokens_for_tokens` call) to skew the spot price against `Target`.
5. When the XCM message finishes and unused weight is refunded, `refund_weight` (`cumulus/primitives/utility/src/lib.rs:539-558`) swaps the residual `Target` credit back to `ClientAsset` via `SwapCredit::swap_exact_tokens_for_tokens(..., None)`.
6. Because `amount_out_min` is `None`, `do_swap_exact_credit_tokens_for_tokens` (`substrate/frame/asset-conversion/src/lib.rs:1081-1097`) skips the `ProvidedMinimumNotSufficientForSwap` check entirely, and the refunded `ClientAsset` credit reflects the manipulated (unfavorable) price with no floor — demonstrating the unbounded-loss refund.
