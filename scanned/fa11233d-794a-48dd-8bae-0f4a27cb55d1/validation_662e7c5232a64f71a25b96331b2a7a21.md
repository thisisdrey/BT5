### Title
`pallet-broker::do_remove_lease` removes a task from `Leases` but leaves its `AutoRenewals` and `Workplan` core assignment intact, letting a revoked lease keep consuming a core - ([File: substrate/frame/broker/src/dispatchable_impls.rs])

### Summary
The external report's core defect is a "remove" function that deletes an entity from the primary tracking list (`vaults` array) but forgets to clear a secondary piece of state (`vaultMapping`) that other privileged code paths rely on to decide whether the entity is still valid — so the removed entity keeps acting as if it were still registered. The closest, concretely supportable analog in this repository is `Pallet::<T>::do_remove_lease` in `substrate/frame/broker/src/dispatchable_impls.rs`, which removes a `task` from the `Leases` list but does not touch `AutoRenewals` (or the already-committed `Workplan` core assignment) that reference the same task/core, so the "removed" lease keeps being renewed and keeps occupying its bulk-coretime core after `remove_lease` was called by governance.

### Finding Description
`do_remove_lease` is implemented as:
```rust
pub(crate) fn do_remove_lease(task: TaskId) -> DispatchResult {
    let mut r = Leases::<T>::get();
    let i = r.iter().position(|lease| lease.task == task).ok_or(Error::<T>::LeaseNotFound)?;
    r.remove(i);
    Leases::<T>::put(r);
    Self::deposit_event(Event::<T>::LeaseRemoved { task });
    Ok(())
}
``` [1](#0-0) 

This only mutates the `Leases` bounded vec. It never inspects or clears `AutoRenewals`, the storage map that independently tracks which `(core, task)` pairs are scheduled to be auto-renewed each sale period:
```rust
AutoRenewals::<T>::try_mutate(|renewals| {
    let pos = renewals.binary_search_by(|r: &AutoRenewalRecord| r.core.cmp(&core)).unwrap_or_else(|e| e);
    renewals.try_insert(pos, AutoRenewalRecord { core, task, next_renewal: ... })
})
``` [2](#0-1) 

`AutoRenewals` is the authoritative state that downstream renewal logic uses to decide whether to keep charging/renewing a core for a task — exactly the role `vaultMapping` played in the `OperatorVCS` bug: it is a secondary "is this task still valid to hold a core" indicator, separate from the primary list (`Leases`), and it is never invalidated by the removal path. Because `do_remove_lease` never calls anything analogous to `cancel_auto_renew`/never touches `AutoRenewals` or the already-committed `Workplan` core entries for `task`, the removed lease's `AutoRenewalRecord` for its `core` remains in storage. On the next sale rotation, the renewal mechanics (driven off `AutoRenewals` and `PotentialRenewals`) will continue to treat the lease's task/core pairing as active and keep renewing/assigning the core to that task, exactly as a removed vault kept passing `vaultMapping[vault] == true` checks in the original report.

Guards that exist elsewhere do not stop this path: `do_remove_lease` only requires the caller to satisfy `AdminOrigin`/root when calling `remove_lease` — it performs no consistency check across `AutoRenewals`, and no other extrinsic automatically synchronizes `AutoRenewals` with `Leases`. `do_enable_auto_renew`/`do_renew` only look up `AutoRenewals`/`PotentialRenewals` by `core`, never cross-checking that the `task` is still present in `Leases`.

### Impact Explanation
A lease that governance has explicitly removed (e.g., because the lessee's agreement ended, or the lease was fraudulently/erroneously granted) can continue to occupy and be renewed on its coretime core indefinitely, because the auto-renewal bookkeeping that drives core (re-)assignment is untouched by the removal. This is a "removed entity still valid" state-consistency bug that:
- causes duplicate/incorrect settlement of coretime resources (core capacity that should have reverted to the sale/reservation pool remains locked to a revoked task),
- degrades the intended chain behavior of `remove_lease` (a runtime/root-privileged administrative action silently fails to fully take effect), and
- can stall correct block-production-adjacent resource allocation on coretime chains, since the core keeps being auto-assigned to a task that is supposed to no longer hold any entitlement.

This matches the "runtime bugs that compromise intended behavior" and "public underpriced work that degrades block production" categories in the impact gate, since coretime cores are a scarce, allocatable resource and stale auto-renewal state causes wrong allocation without any additional privileged or malicious actor involved (the auto-renewal path executes automatically at sale rotation).

### Likelihood Explanation
Likelihood is moderate-to-high: `remove_lease` is a normal, documented root/AdminOrigin operation (not a rare edge case), and any lease previously enrolled in auto-renewal (`enable_auto_renew`, permissionless-callable by the sovereign account owning the lease) will already have a matching `AutoRenewals` entry by the time removal happens. No attacker privilege beyond calling the already-permissionless `enable_auto_renew` before removal is required to set up the stale state; the removal itself is a legitimate governance action, but its effect is incomplete.

### Recommendation
Update `do_remove_lease` to also purge any `AutoRenewals` entries whose `task` matches the removed lease (and any corresponding `PotentialRenewals` scheduled renewal), and clear the current `Workplan` entry allocated to that task's core, mirroring the fix pattern from the `OperatorVCS::removeVault` recommendation (i.e., ensure every piece of "is this still active" state is invalidated atomically with the primary removal):
```rust
pub(crate) fn do_remove_lease(task: TaskId) -> DispatchResult {
    let mut r = Leases::<T>::get();
    let i = r.iter().position(|lease| lease.task == task).ok_or(Error::<T>::LeaseNotFound)?;
    r.remove(i);
    Leases::<T>::put(r);

    // NEW: purge stale auto-renewal state referencing this task.
    AutoRenewals::<T>::mutate(|renewals| {
        renewals.retain(|record| record.task != task);
    });

    Self::deposit_event(Event::<T>::LeaseRemoved { task });
    Ok(())
}
```

### Proof of Concept
1. Governance/root calls `Broker::force_reserve`/lease-setup flow so `task` `T1` holds `core` `C1` via `Leases`.
2. The sovereign account for `T1` calls `enable_auto_renew(sovereign_account, C1, T1, ...)`, inserting an `AutoRenewalRecord { core: C1, task: T1, .. }` into `AutoRenewals`.
3. Root calls `remove_lease(T1)`. `Leases` no longer contains `T1`.
4. Assert: `AutoRenewals::<Test>::get()` still contains the record for `core: C1, task: T1`.
5. Advance to the next sale rotation and call the renewal-processing logic (`do_renew` / rotate_sale path); observe that `C1` is still assigned/renewed to `T1` even though the lease was removed — the "removed" lease remains functionally valid, analogous to `isVaultValid(vault) == true` after `removeVault` in the original report.
