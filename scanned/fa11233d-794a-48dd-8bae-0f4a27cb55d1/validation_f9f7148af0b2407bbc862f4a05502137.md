## Finding

The `purchase` pallet's `payout()` (and `create_account()`) permanently blocks payment of `AccountStatus.free_balance`/`locked_balance` to any account that has *any* entry in `pallet_vesting`'s `Vesting` storage map — and any unrelated, unprivileged account can plant such an entry on a victim's address at will via the public `vested_transfer` extrinsic, with no cooperation, timing, or front-running of a specific transaction required.

### Title
Unrestricted `vested_transfer` target lets any account permanently block `Purchase::payout` for any DOT-purchase participant - (File: `polkadot/runtime/common/src/purchase/mod.rs`)

### Summary
`Purchase::payout()` refuses to pay out a participant if `T::VestingSchedule::vesting_balance(&who)` is `Some(_)` rather than `None`: [1](#0-0) 

`vesting_balance` returns `Some(_)` as soon as *any* schedule exists in the `Vesting` storage map for that account, regardless of whether it is fully vested: [2](#0-1) 

Schedule entries are only removed from storage by an explicit `vest`/`vest_other` call that filters out fully-unlocked schedules — they are never cleaned up automatically: [3](#0-2) 

`vesting_transfer` (the `vested_transfer` extrinsic) can be invoked by *any* signed account against *any* target account — there is no restriction requiring consent or relationship between `transactor` and `target`: [4](#0-3) 

### Finding Description
An attacker can call `Vesting::vested_transfer(origin, target=victim, schedule)` with a dust amount just above `MinVestedTransfer` and a `starting_block` far enough in the past that the schedule is already (or almost immediately) fully vested. This creates a `Vesting` storage entry for `victim` at negligible/no cost to the attacker (the funds simply move from attacker to victim and unlock right away). Because the entry is never proactively cleaned up, `T::VestingSchedule::vesting_balance(&victim)` returns `Some(0)` — not `None` — until someone explicitly calls `vest`/`vest_other(victim)`.

As a result:
- `Purchase::create_account()` will reject account creation for `victim` (`Error::VestingScheduleExists`) at [5](#0-4) .
- `Purchase::payout()` will reject payout of `victim`'s already-purchased `free_balance`/`locked_balance` with the same error at [1](#0-0) , even though `payout` only transfers real DOT out of `PaymentAccount` after this check passes.

Unlike the reported `AllocationVesting.transferPoints()` issue, which requires the attacker to race/front-run a specific pending transaction, this path needs no observation of the mempool at all: the attacker can poison the victim's address proactively, at any time, and re-poison it after any cleanup, since `vested_transfer` remains permissionless against any target forever. This is a direct, standing griefing primitive, not merely a front-run.

### Impact Explanation
A victim's already-allocated DOT purchase (`Accounts::<T>::get(who).free_balance/locked_balance`, set by the privileged `update_balance` call) becomes indefinitely unpayable: `payout()` will keep reverting with `VestingScheduleExists` as long as the attacker keeps a non-empty `Vesting` entry present for that address. Even if the victim (or anyone) calls `vest_other(victim)` to sweep the fully-vested dust schedule, the attacker can immediately submit another `vested_transfer` to re-poison the account before the victim's `payout` extrinsic lands, since both are ordinary signed extrinsics competing for block inclusion. This matches the "permanent user-fund... lock" impact category: legitimate purchasers can be denied their purchased and reserved funds by an unrelated, unprivileged party.

### Likelihood Explanation
High relative to the original report: the attack requires only (a) knowledge of a target address that is enrolled or about to be enrolled in the `purchase` pallet (public via `Accounts` storage/events), and (b) the `MinVestedTransfer` amount, which is refunded to the attacker immediately since the schedule can be constructed to vest instantly. No governance, validator, relayer, or malicious-peer assumption is needed — a single ordinary account can execute and repeat this at will.

### Recommendation
Decouple the purchase pallet's eligibility/payout checks from the mere existence of a `Vesting` storage entry:
- Check `vesting_balance(&who) == Some(0)` (or treat `Some(0)`/`None` equivalently) rather than requiring `None`, since a stale, fully-vested schedule carries no actual lock.
- Alternatively, have `payout()`/`create_account()` first attempt to sweep any dust/fully-vested schedules on behalf of `who` (i.e., call the equivalent of `do_vest`) before evaluating `VestingScheduleExists`, so a fully-unlocked schedule cannot be weaponized to block state transitions.
- More generally, any pallet gating logic on "no vesting schedule exists" should be aware that `pallet_vesting::vested_transfer` is a fully public, targetable primitive and must not treat its mere presence as equivalent to "funds are locked."

### Proof of Concept
1. Configure `Purchase` pallet with `VestingSchedule = pallet_vesting::Pallet<T>`.
2. `ValidityOrigin` calls `create_account`, `update_validity_status(ValidHigh)`, and `update_balance(who=victim, free=X, locked=Y, vat)` to set up `victim`'s purchase entry, per the flow tested in [6](#0-5) .
3. Before `PaymentAccount` calls `payout(victim)`, an unrelated attacker account calls:
   ```
   Vesting::vested_transfer(
       RuntimeOrigin::signed(attacker),
       victim,
       VestingInfo::new(MinVestedTransfer, MinVestedTransfer, current_block.saturating_sub(1)),
   )
   ```
   This creates a `Vesting` entry for `victim` that is already fully unlocked but remains in storage.
4. `PaymentAccount` calls `Purchase::payout(RuntimeOrigin::signed(payment_account), victim)`. This reverts with `Error::<T>::VestingScheduleExists` (see equivalent guard at [1](#0-0) ), because `vesting_balance(&victim)` returns `Some(0)`, not `None`.
5. Even if a third party subsequently calls `Vesting::vest_other(victim)` to clear the schedule, the attacker repeats step 3 to re-poison `victim`'s address, indefinitely denying payout.

	/// Write an accounts updated vesting schedules to storage.
	fn write_vesting(
		who: &T::AccountId,
		schedules: Vec<VestingInfo<BalanceOf<T>, BlockNumberFor<T>>>,
	) -> Result<(), DispatchError> {
		let schedules: BoundedVec<
			VestingInfo<BalanceOf<T>, BlockNumberFor<T>>,
			MaxVestingSchedulesGet<T>,
		> = schedules.try_into().map_err(|_| Error::<T>::AtMaxVestingSchedules)?;

		if schedules.len() == 0 {
			Vesting::<T>::remove(&who);
		} else {
			Vesting::<T>::insert(who, schedules)
		}

		Ok(())
	}

	/// Unlock any vested funds of `who`.
	fn do_vest(who: T::AccountId) -> DispatchResult {
		let schedules = Vesting::<T>::get(&who).ok_or(Error::<T>::NotVesting)?;

		let (schedules, locked_now) =
			Self::exec_action(schedules.to_vec(), VestingAction::Passive)?;

		Self::write_vesting(&who, schedules)?;
		Self::write_lock(&who, locked_now);

		Ok(())
	}

	fn vesting_balance(who: &T::AccountId) -> Option<BalanceOf<T>> {
		if let Some(v) = Vesting::<T>::get(who) {
			let now = T::BlockNumberProvider::current_block_number();
			let total_locked_now = v.iter().fold(Zero::zero(), |total, schedule| {
				schedule.locked_at::<T::BlockNumberToBalance>(now).saturating_add(total)
			});
			Some(T::Currency::free_balance(who).min(total_locked_now))
		} else {
			None
		}
	}
