### Title
Overreporting of a pending pool-member slash via `member_pending_slash` can trigger a real burn of unslashed funds - ([File: substrate/frame/nomination-pools/src/lib.rs])

### Summary
`pallet-nomination-pools`'s `member_pending_slash` computes a member's "amount to be slashed" purely as the difference between the member's actual held/delegated balance and their expected pool-derived balance: `actual_balance.saturating_sub(expected_balance)` [1](#0-0) . This mirrors exactly the external report's core flaw: a "loss" figure is derived from a balance/accounting delta rather than from a verified real loss event, and that manufactured figure is then used to trigger a real, irreversible value-destroying action (`member_slash` → burn of held funds) via `do_apply_slash` [2](#0-1) .

### Finding Description
`do_apply_slash` is permissionless (`Call::apply_slash` can be called by any account, and `withdraw_unbonded` also calls it automatically before withdrawal) [3](#0-2) . It relies entirely on `member_pending_slash` to determine the amount to actually slash from the member's real held balance through `T::StakeAdapter::member_slash` [4](#0-3) .

`member_pending_slash` treats `Delegation::pending_slash(pool_account)` (an aggregate, pool-level bookkeeping value) as authorization to slash, but computes the *individual member's* slash amount as a plain subtraction between the member's `actual_balance` (from `T::StakeAdapter::member_delegation_balance`, i.e. `Delegation::delegator_balance`) and the member's `expected_balance` (`pool_member.total_balance()`, derived from the member's points and the pool's reward/bonded-pool accounting) [5](#0-4) . This design assumes the invariant "actual delegated balance is always ≥ the member's point-derived expected balance, and any shortfall is caused exactly by a real staking slash." That invariant is exactly the kind of assumption the external report calls out as fragile: any bug, rounding drift, era-accounting mismatch (`CurrentEra` vs `ActiveEra`), or sub-pool merging edge case that transiently makes `actual_balance < expected_balance` for a reason *other* than an actual staking slash will make `member_pending_slash` report a nonzero "loss" even though nothing was actually lost.

The repository's own change history demonstrates this exact class of accounting mismatch is real and has happened in production-adjacent code: a documented bug fix notes "A bug (CurrentEra vs ActiveEra mismatch) caused one pool member's balance to become trapped: their points were dissolved but the held funds weren't released," fixed by a manual one-time migration that itself "Applies any pending slash for the member first" and "Calculates trapped amount by checking actual held balance vs expected balance from points" [6](#0-5) . This confirms the `actual_balance` vs `expected_balance` invariant that `member_pending_slash` depends on has already broken at least once due to an era-accounting mismatch unrelated to any genuine validator slash. In a scenario where `Delegation::pending_slash(pool_account)` is nonzero (e.g. due to some earlier partial pool-level slashing) while a *specific* member's own `actual_balance`/`expected_balance` divergence is caused by a similar accounting-mismatch bug rather than their fair share of that slash, `member_pending_slash` will still return a divergence amount and `do_apply_slash` will unconditionally execute `T::StakeAdapter::member_slash`, which for the `DelegateStake` adapter calls `Delegation::delegator_slash` — a real, on-chain burn/held-balance reduction — for a member who was never actually the target of that magnitude of loss [7](#0-6) .

Nothing in `do_apply_slash` cross-checks that the computed `pending_slash` for the *individual member* is bounded by, or proportional to, the pool-level slash event that actually occurred; it only guards against `pending_slash.is_zero()` and an optional minimum-slash-amount check [8](#0-7) . This is structurally the same failure the external report describes: a downstream, permissionless, "harvest"-like operation (`apply_slash`/auto-slash-on-withdraw) trusts an internally-derived "loss" number without verifying that a real loss actually occurred, and then irreversibly commits that loss to the ledger by burning real funds.

### Impact Explanation
If triggered, this results in real, permanent loss of a pool member's staked funds without any corresponding actual validator slash — i.e., unbacked burn of user funds, one of the explicitly in-scope impacts ("theft or unbacked mint or unlock," "permanent user-fund... lock/loss"). Because `apply_slash` is permissionless and `withdraw_unbonded` auto-invokes the same slash-application path, any account (not just the affected member) can trigger the burn once the divergence condition exists, without needing governance, an admin, or a malicious validator.

### Likelihood Explanation
This is not a trivial, always-exploitable bug — it requires the `actual_balance`/`expected_balance` invariant to break first (via an accounting-mismatch bug in era rotation, sub-pool merging, or ED-driven rounding, as already demonstrated by the CurrentEra/ActiveEra bug that necessitated a manual migration). Given that this exact invariant has already been observed to break at least once in this codebase's history, the likelihood of a similar future divergence recurring (through a different code path/edge case) and being weaponized via the permissionless `apply_slash`/auto-slash-on-withdraw flow is credible, though it depends on triggering a secondary accounting bug first rather than being independently exploitable from a fully-correct state.

### Recommendation
`member_pending_slash` should not derive a slash amount purely from a balance/points delta. Instead, the individual member's slash share should be computed strictly from the recorded pool-level slash event (proportional to the member's share of the pool-level `pending_slash` at slash time) and should never exceed what is provably attributable to a real, recorded slashing event. Additionally, `do_apply_slash` should defensively assert/bound the computed pending slash against the pool's own recorded `pending_slash` aggregate and refuse to proceed (rather than silently slashing) when the derived member-level amount cannot be reconciled with an actual recorded slash, surfacing a defensive error instead of executing `member_slash`.

### Proof of Concept
A concrete on-chain reproduction requires first inducing the `actual_balance < expected_balance` divergence through a secondary accounting bug (as already documented by the CurrentEra/ActiveEra mismatch fixed in `pr_11018.prdoc`) without an accompanying validator slash, then:
1. Any account calls `Pools::apply_slash(origin, member_account)` (permissionless call) — or the affected member calls `withdraw_unbonded`, which auto-invokes the same path.
2. `member_pending_slash` computes `actual_balance.saturating_sub(expected_balance) = X > 0` even though no real slash of that magnitude occurred for this member.
3. `do_apply_slash` proceeds since `pending_slash` is nonzero, calling `T::StakeAdapter::member_slash(member, pool, X, reporter)`.
4. For the `DelegateStake` adapter this calls `Delegation::delegator_slash`, burning `X` from the member's real held balance — an unbacked, permanent loss with no genuine underlying slash to justify it.

Full exploitation requires reproducing the specific triggering accounting-mismatch condition on a live chain, which was not independently re-derived in this analysis; the analog is grounded in the existing `member_pending_slash`/`do_apply_slash` code path and the repository's own documented historical occurrence of the underlying invariant violation.

	/// Slash member against the pending slash for the pool.
	fn do_apply_slash(
		member_account: &T::AccountId,
		reporter: Option<T::AccountId>,
		enforce_min_slash: bool,
	) -> DispatchResult {
		let member = PoolMembers::<T>::get(member_account).ok_or(Error::<T>::PoolMemberNotFound)?;

		let pending_slash =
			Self::member_pending_slash(Member::from(member_account.clone()), member.clone())?;

		// ensure there is something to slash.
		ensure!(!pending_slash.is_zero(), Error::<T>::NothingToSlash);

		if enforce_min_slash {
			// ensure slashed amount is at least the minimum balance.
			ensure!(pending_slash >= T::Currency::minimum_balance(), Error::<T>::SlashTooLow);
		}

		T::StakeAdapter::member_slash(
			Member::from(member_account.clone()),
			Pool::from(Pallet::<T>::generate_bonded_account(member.pool_id)),
			pending_slash,
			reporter,
		)
	}
