### Title
Reward-counter overflow permanently DoSes `pallet-nomination-pools` payout, join, and commission-claim paths - ([File: substrate/frame/nomination-pools/src/lib.rs])

### Summary
`pallet-nomination-pools` maintains a monotonically-increasing per-pool `RewardCounter` (`FixedU128`) that, like the Uniswap-style price accumulator in the external report, is only ever supposed to grow. Unlike the Solidity accumulator (which is meant to wrap), this counter uses **checked** arithmetic and returns `Error::OverflowRisk` instead of saturating/wrapping. Because every reward-affecting extrinsic (`join`, `bond_extra`, `claim_payout`, `claim_commission`) must first recompute this counter via `RewardPool::update_records`/`current_reward_counter`, a single scenario that pushes the counter past `FixedU128`'s representable range makes that computation fail forever, deterministically blocking all subsequent reward-affecting calls into the pool — the same “checked-arithmetic accumulator causes permanent DoS” bug class as the reported AMM issue.

### Finding Description
The reward counter is computed in `RewardPool::current_reward_counter`: [1](#0-0) 

and consumed via `checked_mul_int(...).ok_or(Error::<T>::OverflowRisk)` in `PoolMember::pending_rewards`: [2](#0-1) 

and in `RewardPool::update_records`, which every mutating extrinsic must call before touching pool state: [3](#0-2) 

The repository’s own test suite documents that this condition is reachable through ordinary user actions (a large slash shrinking `bonded_points` relative to accumulated `current_payout_balance`, followed by a large deposit joining the pool), and demonstrates that `Pools::join` fails with `Error::<T>::OverflowRisk`: [4](#0-3) 

`do_claim_payout` and `do_claim_commission` both route through `RewardPool::current_reward_counter`/`update_records` before performing any transfer: [5](#0-4) [6](#0-5) 

Because the overflow condition depends on the pool’s accumulated `last_recorded_total_payouts`/`last_recorded_reward_counter` and the current `bonded_points`, and these values do not shrink on their own, once the computation starts returning `None` it will keep returning `None` on every subsequent call with the same or worse inputs — there is no code path that resets or repairs the counter. Existing guards (`ok_or(Error::<T>::OverflowRisk)`) stop the *individual* call from corrupting storage, but they do not stop the *pool* from being permanently wedged, because there is no unchecked/saturating fallback and no privileged recovery extrinsic that bypasses `update_records`.

### Impact Explanation
Once triggered, the affected pool’s reward accounting becomes permanently unusable:
- `claim_payout` / `claim_payout_other` fail for every member, freezing already-earned rewards inside the reward account indefinitely.
- `claim_commission` fails, freezing the pool operator’s commission.
- `join` and `bond_extra` fail for new/existing members, since both call `update_records` before mutating bonded points.
This matches the “permanent user-fund or bridge-state lock” and “public underpriced work / stalled processing” criteria in the impact gate: unprivileged users (a large depositor joining after a slash event) can wedge a shared pool’s reward machinery with no admin/governance/relayer/validator involvement required.

### Likelihood Explanation
The repository’s own regression test (`reward_counter_update_can_fail_if_pool_is_highly_slashed`) proves the condition is reachable with realistic parameters (a pool slashed by 99% followed by a large `join`), not merely a theoretical `FixedU128::MAX` edge case. Any nomination pool that experiences a severe slash and subsequently receives a disproportionately large bond relative to its shrunken points is at risk, entirely through public, permissionless extrinsics (`join`, `bond_extra`).

### Recommendation
- Avoid making pool-wide reward availability depend on a single checked arithmetic operation with no recovery path; consider re-deriving/rebasing `last_recorded_reward_counter` (e.g., via a permissionless "resync" extrinsic that recomputes it from current balances without requiring the intermediate multiplication to fit) or bound `bonded_points`/`current_payout_balance` ratios to keep `FixedU128` operations within safe range.
- Add an explicit invariant check/guard in `join`/`bond_extra` that rejects deposits which would push the reward counter towards its overflow boundary, rather than allowing the deposit to succeed while wedging the *entire* pool for all other members.
- Provide a governance-independent recovery mechanism (callable by anyone) that can reset/re-baseline a pool’s reward accounting using saturating arithmetic if the checked path fails, so a single adverse event cannot permanently freeze all members’ funds.

### Proof of Concept
The existing unit test in the repository already demonstrates the failure mode end-to-end: [4](#0-3) 
1. Create a pool bonded with a large amount (`pool_bond = inflation(10) / 2`).
2. Slash the pool by 99% (`StakingMock::slash_by(1, pool_bond * 99 / 100)`), drastically shrinking `bonded_points` relative to reward-pool balance bookkeeping.
3. A new large depositor calls `Pools::join` with a comparable deposit; `current_reward_counter`'s `checked_add`/`checked_from_rational` chain overflows and returns `Error::<T>::OverflowRisk`.
4. From this point, every subsequent `join`, `bond_extra`, `claim_payout`, or `claim_commission` on the same pool would repeat the same failing computation, since `bonded_points`/accumulated payout state is unchanged by the failed calls — permanently locking pending rewards and blocking new deposits for that pool.

	fn reward_counter_update_can_fail_if_pool_is_highly_slashed() {
		// create a pool that has roughly half of the polkadot issuance in 10 years.
		let pool_bond = inflation(10) / 2;
		ExtBuilder::default().ed(DOT).min_bond(pool_bond).build_and_execute(|| {
			assert_eq!(
				pool_events_since_last_call(),
				vec![
					Event::Created { depositor: 10, pool_id: 1 },
					Event::Bonded {
						member: 10,
						pool_id: 1,
						bonded: 12_968_712_300_500_000_000,
						joined: true,
					},
					Event::MetadataUpdated { pool_id: 1, caller: 900 },
				]
			);

			// slash this pool by 99% of that.
			StakingMock::slash_by(1, pool_bond * 99 / 100);

			// some whale now joins with the other half ot the total issuance. This will trigger an
			// overflow. This test is actually a bit too lenient because all the reward counters are
			// set to zero. In other tests that we want to assert a scenario won't fail, we should
			// also set the reward counters to some large value.

			assert_err!(
				Pools::join(RuntimeOrigin::signed(20), pool_bond, 1),
				Error::<T>::OverflowRisk
			);
		})
