### Title
Reentrancy stipend guard is bypassed for real value-transferring calls (`.transfer()`/`.send()`) - (File: `substrate/frame/revive/src/vm/evm/instructions/contract.rs`)

### Summary
`pallet-revive`'s EVM-compatibility layer emulates Solidity's classic "2300-gas stipend" reentrancy defense — the same defense that `.transfer()`/`.send()` rely on — via an explicit `ReentrancyProtection::AllowNext` flag, because the developers know that on revive's weight scale, 2300 gas may actually be enough to perform a reentrant call (unlike on Ethereum, where it is not). The heuristic that is supposed to detect a stipend-limited call and apply `AllowNext` checks `value.is_zero()` *before* checking `gas_limit == CALL_STIPEND`, so any call that actually transfers a non-zero value — which is exactly what `.transfer()`/`.send()` do — always falls into the `AllowReentry` branch regardless of the gas limit. The protection is therefore dead code for the one call pattern it was built to protect.

### Finding Description
In `run_call` [1](#0-0) , the branch is selected via:

```rust
let (add_stipend, reentracy) =
    match (value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND))
    {
        (false, _) => (true, ReentrancyProtection::AllowReentry),
        // Heuristic: detect when solc passes `gas_limit = 2300` (the call stipend).
        (_, true) => (true, ReentrancyProtection::AllowNext),
        (_, _) => (false, ReentrancyProtection::AllowReentry),
    };
```

The first arm, `(false, _)`, matches whenever `value.is_zero()` is `false`, i.e. whenever the call transfers a non-zero native value — irrespective of the gas limit. Because Solidity's `address.transfer(amount)` and `address.send(amount)` are precisely the patterns that pass a **non-zero value together with a `gas_limit` of `2300`** (that is the entire purpose of the stipend: send value with just enough gas to log an event, not enough to reenter), this exact call shape is caught by the first arm and always resolves to `ReentrancyProtection::AllowReentry`. The second arm, which actually applies `AllowNext` (the correct, intentional reentrancy guard, see `ReentrancyProtection` docs at [2](#0-1) ), only fires for `value.is_zero() == true` with `gas_limit == 2300`, a call shape that never occurs for a genuine value-carrying transfer.

The `exec.rs` comment explicitly states why this guard exists at all: *"due to gas scale differences that guarantee does not automatically hold in revive and we enforce it explicitly here"* [3](#0-2) . In other words, the codebase already acknowledges that on revive the 2300-gas stipend alone is *not* sufficient to stop a reentrant call the way it is on Ethereum, and relies on `AllowNext` to enforce the safety guarantee explicitly. The match-arm ordering bug means that guarantee is never actually applied to the call pattern it exists for.

The `push_frame`/`allows_reentry` machinery (`Stack::allows_reentry`, `call`) does correctly deny reentry when `AllowNext`/`Strict` is set (see `exec.rs:2186-2192`), so the enforcement mechanism itself works — the corrupted value is the **selected `ReentrancyProtection` variant**, which is silently wrong for the value-transfer case, exactly mirroring the Vyper bug class: a reentrancy guard exists, is wired up, and looks correct, but a boolean/condition ordering defect makes it never trigger for the case that matters.

### Impact Explanation
This defeats the compatibility guarantee that Solidity contracts relying on `.transfer()`/`.send()` for reentrancy safety (a very common and historically-recommended pattern) remain safe when deployed on `pallet-revive`. A contract's `receive()`/`fallback()` invoked via `.transfer()` gets `AllowReentry` instead of the intended `AllowNext`, so it can call back into the caller and reenter state that the caller assumed was protected by the stipend — the classic reentrancy exploit primitive, now reachable through unprivileged, ordinary contract calls with no admin/relayer/validator involvement. This is a runtime bug that compromises intended execution-model behavior for `pallet-revive`, in scope per the impact gate ("runtime bugs that compromise intended behavior", "unauthorized execution").

### Likelihood Explanation
High. Any EVM contract on revive that uses `.transfer()` or `.send()` (an extremely common Solidity idiom, including for classic checks-effects-interactions withdrawal patterns) automatically triggers the vulnerable branch every time value is sent — this is not a rare edge case, it is the default and expected usage of the stipend pattern. No attacker privilege is required; a malicious contract simply needs to be the recipient of a value transfer from a victim contract that assumes stipend-based reentrancy safety.

### Recommendation
Reorder the heuristic so that the `AllowNext` stipend protection is applied whenever `gas_limit == CALL_STIPEND`, independent of whether `value` is zero, e.g.:

```rust
let (add_stipend, reentracy) = if gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND) {
    (true, ReentrancyProtection::AllowNext)
} else if value.is_zero() {
    (false, ReentrancyProtection::AllowReentry)
} else {
    (true, ReentrancyProtection::AllowReentry) // or reconsider whether this case should also be gated
};
```
Add/extend the `stipends.rs` test suite (`ReentrancyAttacker` fixture already present) to assert that a reentrant call attempted from within a `receive()` triggered by `.transfer()`/`.send()` is rejected with `ReentranceDenied`, not merely that balances end up consistent.

### Proof of Concept
1. Deploy a `Victim` contract holding a balance and a withdraw function using `msg.sender.transfer(amount)` after decrementing internal accounting (or even before, to make the bug maximally visible).
2. Deploy `ReentrancyAttacker` (already present in the repo's own fixture, [4](#0-3) ) whose `receive()` calls back into `msg.sender` (the `Victim`) attempting a second withdrawal.
3. Trigger `Victim.withdraw()` which internally does `payable(attacker).transfer(amount)`.
4. Because `value != 0`, `run_call` selects `(true, ReentrancyProtection::AllowReentry)` instead of `AllowNext`, so `Stack::allows_reentry` (`exec.rs:2186`) does **not** deny the nested call — the attacker's `receive()` callback into `Victim` succeeds and can re-enter the withdrawal logic before the victim's state update takes effect, in contrast to native Ethereum where the 2300-gas stipend alone would already prevent this by running out of gas mid-call. fn run_call<'a, E: Ext>(
	interpreter: &mut Interpreter<'a, E>,
	callee: H160,
	gas_limit: U256,
	input: Vec<u8>,
	scheme: CallScheme,
	value: U256,
	return_memory_range: Range<usize>,
) -> ControlFlow<Halt> {
	let (add_stipend, reentracy) =
		match (value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND))
		{
			(false, _) => (true, ReentrancyProtection::AllowReentry),
			// Heuristic: detect when solc passes `gas_limit = 2300` (the call stipend).
			// For zero-value transfer/send, solc injects `gas_limit = 2300` explicitly.
			// We apply `AllowNext` reentrancy protection and set `add_stipend = true` since the
			// raw 2300 gas value is only meaningful at Ethereum's gas scale.
			(_, true) => (true, ReentrancyProtection::AllowNext),
			(_, _) => (false, ReentrancyProtection::AllowReentry),
		};

	let call_result = match scheme {
		CallScheme::Call | CallScheme::StaticCall => interpreter.ext.call(
			&CallResources::from_ethereum_gas(gas_limit, add_stipend),
			&callee,
			value,
			input,
			// protect against rex-entrancy when we grant the stipend
			reentracy,
			scheme.is_static_call(),
		),
		CallScheme::DelegateCall => interpreter.ext.delegate_call(
			&CallResources::from_ethereum_gas(gas_limit, add_stipend),
			callee,
			input,
		),
		CallScheme::CallCode => {
			unreachable!()
		},
	};

/// Level of reentrancy protection.
///
/// This needs to be specifed when a contract makes a message call. This way the calling contract
/// can specify the level of re-entrancy protection while the callee (and it's recursive callees) is
/// executing.
#[derive(Copy, Clone, PartialEq, Debug)]
pub enum ReentrancyProtection {
	/// Don't activate reentrancy protection
	AllowReentry,
	/// Activate strict reentrancy protection. The direct callee and none of its own recursive
	/// callees must be the calling contract.
	Strict,
	/// Activate reentrancy protection where the direct callee can be the same contract as the
	/// caller but none of the recursive callees of the callee must be the caller.
	///
	/// This is used for calls that transfer value but restrict gas so that the callee only has a
	/// stipend gas amount. In Ethereum that is not sufficient for the callee to make another call.
	/// However, due to gas scale differences that guarantee does not automatically hold in revive
	/// and we enforce it explicitly here.
	AllowNext,
}
