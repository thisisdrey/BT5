# [M] Proposals overwrite

## Summary
Severity: Medium
Contest weight: 0.4295
Dataset id: 16693
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability concerns the governance proposal submission flow, where a new proposal is created through a function that obtains a proposal identifier from a separate storage contract. The submission routine does not verify whether the returned identifier already corresponds to an existing, valid proposal in the metadata mapping. Because the identifier is generated by a distinct contract that tracks an instruction counter, a contract upgrade, storage reset, or mis‑configuration can cause the counter to produce an identifier that collides with a previously stored proposal. When this happens, the metadata assignment overwrites the earlier entry without any guard, effectively replacing the title, author, timestamp, and URI of the original proposal. This class of bug is a missing existence check combined with cross‑contract state inconsistency. It can be exploited by an attacker who triggers a contract upgrade or manipulates the instruction storage so that the next call to submitProposal reuses an existing proposalId. The attacker then supplies malicious metadata, causing the governance interface to display incorrect information, potentially misleading voters or invalidating previously voted decisions. From a user perspective, a previously submitted governance proposal may suddenly disappear, show a different title, or point to a different URI, leading to confusion and loss of trust. The issue surfaces only under conditions where the storage contract’s counter is not monotonic across upgrades, which may not be obvious during normal operation, making it hard to notice until a proposal is unexpectedly altered. The protocol’s assets are not directly at risk, but the governance process can be disrupted, availability reduced, and value may be indirectly exposed if decisions are made on falsified proposals. The flaw was discovered during a security audit that examined the interaction between the governance contract and the instruction storage module, revealing that the submitProposal method lacks a check for an existing proposalId in getProposalMetadata. To remediate the issue, the proposal metadata should be stored atomically within the same contract that issues the identifier, or the submit function must include a verification step that ensures the identifier does not already map to a valid proposal before overwriting any data. This aligns the system with standard best practices for identifier uniqueness and cross‑contract state validation.

## Proof of Concept
If the project update the kernel module "`INSTR`" and reconfigure proposals and call `INSTR.store(instructions_);`, the counter may return a `proposalId` of an existing proposal and overwrite an existing previous one.

This is due to the fact that the proposals are saved in a mapping of a contract that is not related to the one that returns the counters, and furthermore, they do not check that the record already exists.

```solidity
uint256 proposalId = INSTR.store(instructions_);
getProposalMetadata[proposalId] = ProposalMetadata(
    title_,
    msg.sender,
    block.timestamp,
    proposalURI_
);
```

## Recommendation
* Store the proposal metadata in the same `INSTR` contract or ensure that the proposal doesn’t exist.
