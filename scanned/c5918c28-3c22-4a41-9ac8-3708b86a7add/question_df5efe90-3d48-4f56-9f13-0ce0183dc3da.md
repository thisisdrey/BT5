Target: `TokenId` used as `BTreeMap`/`Amounts` key in `ImtTokens` (contracts/defuse/core/src/tokens.rs, referenced from `intents/imt.rs`). Attacker action: submit a single `ImtMint` intent whose `tokens: ImtTokens` map contains two entries whose `DisplayFromStr`-serialized keys are textually distinct but which the receiving `BTreeMap<TokenId, u128>` deserializer coalesces due to a hash/ordering inconsistency between `TokenId`'s derived `Ord` and its `Display`. Preconditions: attacker signs the `MultiPayload` themselves; no victim funds needed at construction time. Call sequence: `serde_json` deserializes `Amounts<BTreeMap<_, DisplayFromStr>>` into `ImtTokens` -> `engine.state.imt_mint` sums per-key amounts. Binding: the number of distinct `TokenId` keys serialized by the attacker must equal the number of distinct keys the engine credits, i.e. `len(tokens_submitted) == len(balances_credited)` with each amount matching the submitted amount for that exact key. Impact: Critical if two different keys collapse into one, letting the attacker mint more of a single `TokenId` than they declared (breaking `AUTHORISATION`/mint-amount binding). Proof idea: cargo test signing `ImtMint` with two `TokenId` map entries differing only in a field known to be a hot spot for `split_once` ambiguity, asserting both balances land distinctly and sum correctly.
