Target: `Nep171TokenId`/`Nep245TokenId::mt_token_id` fields typed as free-form `String` with no charset restriction (crates/primitives/token-id/src/nep171.rs, nep245.rs). Attacker action: mint an NFT with `token_id` containing a NUL byte or other non-printable character adjacent to a colon, e.g. `"x\0:y"`, then deposit it. Preconditions: attacker's own NFT contract accepts arbitrary `token_id` strings for `nft_mint`. Call sequence: `nft_on_transfer` -> `Nep171TokenId::new(contract_id, "x\0:y")` -> `to_string()` = `"nep171:contract_id:x\0:y"` -> stored -> later `TokenId::from_str` re-parses this exact string during `mt_resolve_transfer` or `mt_tokens` enumeration. Binding: `TokenId::from_str(&t.to_string()) == t` must hold even when the payload field embeds control characters or additional colons, i.e. the round trip is lossless for the full Unicode `String` range, not just typical alphanumeric ids. Impact: Critical if any such byte sequence causes a different split point than the one used at construction, silently reassigning the balance to a different `(contract_id, nft_token_id)` key on a subsequent read (e.g. a resolver refund). Proof idea: `arbitrary`-based property test (already scaffolded via `make_arbitrary` in nep171.rs's own test module) extended to fuzz `nft_token_id` with embedded control/colon bytes and asserting the round-trip equality holds for every generated case.
