## Title
PSM `mint()`/`redeem()` assume `Fungibles::transfer` delivers the exact `amount` requested, without verifying the reserve account's actual balance change — breaks 1:1 backing when `T::Fungibles` wraps fee-on-transfer/deflationary assets (e.g. Solidity ERC20 assets exposed via `pallet-revive`) - ([File: substrate/frame/psm/src/lib.rs])

### Summary
The Peg Stability Module (`substrate/frame/psm`) computes the internal-stablecoin amount to mint from a *requested* external-asset transfer amount, then calls `T::Fungibles::transfer(...)` and unconditionally proceeds to mint/burn/settle based on that requested amount — never checking what the reserve account actually received. This is the exact "deflationary/fee-on-transfer token" bug class from the referenced report (Yieldy `Staking.sol`/`LiquidityReserve.sol`), reproduced at the pallet level because `T::Fungibles` is a generic trait bound that a runtime can satisfy with an asset backend whose `transfer` does not guarantee exact delivery (notably `pallet_revive`'s `impl_fungibles.rs`, which wraps arbitrary Solidity ERC20 contracts).

### Finding Description
In `mint()`: [1](#0-0) 
the pallet transfers `effective_external` from the user to `psm_account` and then immediately mints `internal_to_user` (and fee) of the internal asset — the minted amount is derived entirely from the *requested* transfer amount, not from any post-transfer balance delta on `psm_account`.

The pallet's own documentation states the invariant this breaks: *"PSM Debt: ... backed 1:1 by external assets in that PSM's reserve"* [2](#0-1) . `PsmDebt` is incremented by `new_debt` computed from `internal_equivalent`, again derived from the nominal `external_amount`, not from what was actually deposited [3](#0-2) .

`redeem()` has the same pattern in the opposite direction: it transfers `external_out` from `psm_account` to the user without verifying the account previously received the exact backing amount, and validates only `PsmDebt`/`get_reserve()` bookkeeping rather than the real token balance change on `psm_account` [4](#0-3) .

`T::Fungibles` is only bound to `FungiblesMutate<Self::AccountId, AssetId = Self::AssetId> + FungiblesMetadataInspect<...> + FungiblesRolesInspect<...>` [5](#0-4) , i.e. any type satisfying this generic interface can be plugged in by a runtime integrator — including `pallet_revive`'s `fungibles` implementation, which represents ERC20 contracts (arbitrary Solidity bytecode) as fungible assets and drives all balance changes through `bare_call` into the token contract: [6](#0-5) 
Because the actual balance effect of an `IERC20::transfer` call is entirely determined by arbitrary contract logic (fee-on-transfer, deflationary burn, rebasing, blacklists that silently reduce delivered amount, etc.), `T::Fungibles::transfer`/`mint_into`/`burn_from` calls into such a backend do not guarantee the nominal `amount` was actually moved — exactly the primitive the external report describes for `Staking.sol`/`LiquidityReserve.sol`.

Existing guards do not stop this path:
- `ensure_decimals_match`, `min_swap_amount`, `max_debt`/ceiling checks, and `FeeTooHigh` all operate on the *requested* nominal amount, not on the reserve account's measured balance delta.
- `redeem()`'s `defensive!("PSM reserve is less than expected output amount")` check at line 852-855 uses `Self::get_reserve()`, which (per the module docs) is *derived, not stored* — i.e., it is itself computed as a balance query against `psm_account`, so if a prior `mint()` under-delivered collateral, `get_reserve()` will correctly reflect the shortfall only *after* the damage (over-minted internal debt) has already occurred; it does not prevent the initial over-mint.

### Impact Explanation
If a PSM instance is configured (by a chain that exposes ERC20-backed assets, e.g. via `pallet_revive`, as an approved `external_asset`) with a token that is deflationary or applies any fee/burn on transfer, every `mint()` call will:
1. Deliver less than `effective_external` into `psm_account`.
2. Still credit the caller with the full `internal_to_user` amount of internal stablecoin.
3. Still record `PsmDebt` as though the PSM is fully collateralized.

This under-collateralizes the peg (theft/unbacked mint), and later legitimate `redeem()` calls by other users can exhaust the under-funded reserve, causing `Error::Unexpected`/`InsufficientReserve` failures or fund loss for users who redeem after the shortfall is discovered — i.e., duplicate/asymmetric settlement and permanent fund loss/lock for the last redeemers, matching the "theft or unbacked mint" and "permanent user-fund lock" impact classes.

### Likelihood Explanation
This requires no privileged actor: any unprivileged holder of a non-conforming external asset can call the public `mint` extrinsic with such a token registered on a PSM instance. The vulnerability is latent (not currently exploitable) unless a runtime integrator instantiates a PSM with a `T::Fungibles` backend whose transfer semantics are not guaranteed 1:1 (e.g. arbitrary ERC20-via-revive assets) — but the pallet's generic trait bound explicitly permits this configuration, and nothing in the PSM logic itself defends against it, unlike well-known patterns elsewhere in the codebase that verify balance deltas around external transfers.

### Recommendation
- After calling `T::Fungibles::transfer` into `psm_account` in `mint()`, measure the actual balance change on `psm_account` (via `Inspect::balance` before/after, or use a checked-delta wrapper) and use that measured amount — not the nominal request — to compute `internal_to_user`, `PsmDebt` increments, and event data.
- Symmetrically, in `redeem()`, verify the balance actually leaving `psm_account` matches the intended `external_out` before finalizing debt bookkeeping.
- Alternatively, restrict `T::Fungibles` (documentation/trait bound) to backends that guarantee exact-amount transfers, and explicitly disallow registering externally-controlled/arbitrary-code assets (e.g., ERC20-via-revive) as PSM external assets unless their transfer behavior is provably exact.

### Proof of Concept
1. Deploy/register (via runtime configuration) a PSM instance whose `T::Fungibles` implementation is (or wraps) `pallet_revive`'s ERC20 fungibles adapter, so `AssetId = H160` addresses of Solidity contracts.
2. Deploy a deflationary ERC20 contract (e.g., one that burns 5% on every `transfer`) and approve it as an `external_asset` on the PSM via `add_external_asset` (governance-configured, not attacker-controlled — the attacker only needs the asset to already be approved).
3. Attacker calls `Psm::mint(internal_asset, external_asset=deflationary_token, external_amount=1000, max_fee)`.
4. `T::Fungibles::transfer` invokes the ERC20 `transfer` call at [7](#0-6) ; the contract burns 5%, so `psm_account` actually receives only 950 tokens, but the PSM code at [8](#0-7)  still mints internal stablecoin equivalent to the full 1000 (minus protocol fee) and records `PsmDebt` as backed by 1000.
5. Repeat: PSM debt grows unbacked by real reserve; when other users later call `redeem()`, the reserve is insufficient, causing failed redemptions (`Error::Unexpected`/`InsufficientReserve`) or, for early redeemers, extraction of value that rightfully belongs to later redeemers — net fund loss for the protocol/other users.
