## Analysis Summary

The Curve report's core broken invariant is: **a security-critical status/accounting decision is derived from a value that can be freely and directly manipulated by an unprivileged external actor, bypassing the intended state-transition path** (a direct token transfer into the pool skews the "balanced" ratio, flipping collateral status). I evaluated several candidates in `polkadot-sdk--029` (nomination-pools ratio math, `pallet-asset-conversion` quote/execute race, Snowbridge V2 `ExchangeAsset`/pricing, on-demand spot-traffic price). The nomination-pools ratio (`balance_to_point`/`point_to_balance`) is **not** exploitable this way because it is keyed off `T::StakeAdapter::active_stake()`, which reads the `Staking` ledger, not the pool account's raw free balance — a direct transfer to the bonded pool account does not move this value. The Snowbridge/AssetConversion price paths are either fixed by governance parameters or protected by fee/slippage checks (`quote_price_...` now checks `reducible_balance`).

The one place where the exact analog survives is `pallet-nomination-pools`' **reward pool accounting**, which derives "claimable rewards" directly from the raw account balance of a deterministic, unguarded sub-account.

### Title
Nomination-pools reward accounting trusts the raw balance of an unguarded, publicly-known reward account, letting anyone inject unaccounted funds into the pro-rata payout calculation - (File: `substrate/frame/nomination-pools/src/lib.rs`)

### Summary
`RewardPool::current_balance` reads the reducible balance of the pool's reward account directly from the `Currency`/`fungible` pallet, and `RewardPool::current_reward_counter` treats any increase in that balance (beyond bookkeeping counters) as legitimate "income" to be split pro-rata across `bonded_points`. The reward account is a deterministic `PalletId`-derived `AccountId` (`generate_reward_account`) that is not access-controlled — any account can `transfer` arbitrary funds into it. This mirrors the Curve report's flaw: a value meant to represent a controlled, protocol-mediated state (pool token distribution / accrued staking rewards) is instead read straight from a freely-writable balance, and a security/financial decision (`current_reward_counter`, thus payout amounts) is computed from it without validating provenance. [1](#0-0) [2](#0-1) 

### Finding Description
`current_reward_counter` computes:
```
current_payout_balance = balance + total_rewards_claimed + total_commission_claimed - last_recorded_total_payouts
```
where `balance = Self::current_balance(id)` is simply `T::Currency::reducible_balance(&reward_account, Expendable, Polite)`. [3](#0-2) 

This function is invoked on every point-changing action (`join`, `bond_extra`, `unbond`, `claim_payout`) via `update_records`/`do_reward_payout`, and it does not distinguish between funds that arrived via the legitimate staking-payout flow and funds an attacker sends directly to the reward account with a plain `Balances::transfer`. Because `current_payout_balance` is split into `new_pending_commission`/`new_pending_rewards` and then divided by `bonded_points` at the exact moment the call executes (`checked_from_rational(new_pending_rewards, bonded_points)`), the timing and point-weight of whoever triggers the recalculation directly determines how the injected balance is distributed. [4](#0-3) 

This is the direct structural analog of the Curve bug: the "is the pool's internal state balanced/legitimate?" check (there: token distribution ratio; here: `current_payout_balance`) relies on a value (account balance) that is externally, atomically, and cheaply manipulable in a single transaction, with no guard rail (e.g., no restriction on transfers into the reward account, no separation between "recorded staking payout" and "raw balance").

### Impact Explanation
An attacker can:
1. Join or bump their point share in a target pool (`bond_extra`) so they hold a large fraction of `bonded_points`.
2. Directly transfer tokens to the pool's `reward_account()` (a value derivable off-chain via `generate_reward_account(pool_id)`), inflating `current_balance(id)` with funds the pool never legitimately earned.
3. Immediately call `claim_payout`, causing `current_reward_counter`/`do_reward_payout` to redistribute the injected balance pro-rata by points, letting the attacker reclaim a share of their own donation disproportionate to any other members' legitimate accrued stake, while diluting the recorded reward counter state for everyone else and potentially forcing `last_recorded_total_payouts`/counters into states that interact badly with subsequent slashing/commission bookkeeping.

This falls under "Balances, assets, ... treasury spends, bridge rewards, and contract-held value must conserve value and settle exactly once to the rightful beneficiary and amount" — an unprivileged actor can force settlement of value to the wrong beneficiary/amount by injecting unaccounted balance and racing the recomputation.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to be (or briefly become) a pool member with non-trivial points, and the net economic benefit is capped by the attacker effectively donating funds to also-present legitimate members, so a purely profit-seeking attack has diminishing returns unless the attacker is the dominant point-holder in the pool at the time (e.g., freshly created or low-membership pools, or immediately after `create`/`bond_extra`). The more concerning class of impact is not straightforward profit but state-integrity griefing (corrupting `last_recorded_reward_counter`/commission bookkeeping across the whole pool) — this requires no privileged access, node/validator collusion, or off-chain infrastructure, satisfying the "unprivileged attacker" bar in the task's pivots.

### Recommendation
Do not treat the raw reducible balance of the reward account as ground truth for "pending rewards". Track reward inflows explicitly (e.g., only credit `RewardPool` state via an internal, authenticated deposit path — staking payout hook or an explicit `deposit_reward` extrinsic that updates counters atomically with the transfer), and reconcile/ignore any balance delta that did not originate from that path (e.g., sweep unexpected balance to treasury rather than auto-distributing it pro-rata to whichever point-holder happens to call `claim_payout` next).

### Proof of Concept
Not independently executed against a live runtime in this pass (no terminal/build access); however, the exploit path is directly constructible from existing pallet primitives and is consistent with the pallet's own test helpers, which explicitly manipulate the reward account balance out-of-band to simulate rewards:
```rust
// substrate/frame/nomination-pools/src/mock.rs — test helper shows the reward

pub fn deposit_rewards(reward: Balance) {
    let a = default_reward_account();
    Currency::mint_into(&a, reward).unwrap(); // equivalent to an attacker's direct transfer
}
```
Combining `Pools::join`/`Pools::bond_extra` (to acquire points) + a plain `Balances::transfer` to `Pools::generate_reward_account(pool_id)` + `Pools::claim_payout` reproduces the same code path as `deposit_rewards` followed by `do_reward_payout`, shown to redistribute the injected balance pro-rata by `bonded_points` in `substrate/frame/nomination-pools/src/tests.rs` (`do_reward_payout_works_with_a_pool_of_1`, `commission_reward_counter_works_one_member`). [5](#0-4) [6](#0-5) 

**Uncertainty**: I was not able to run this against a live/emulated runtime to confirm whether any existing guard (e.g., `Preservation`/ED handling, or a `MinJoinBond`/dust-sweep mechanism elsewhere in the pallet) neutralizes the net economic gain in practice, nor whether the overflow path (`Error::<T>::OverflowRisk`) is reachable with realistic balances to cause a durable DoS. This should be validated with a concrete emulated/mock-runtime reproduction before treating the "griefing/DoS" portion of the impact as confirmed; the "reward accounting reads an unguarded raw balance" structural flaw itself is directly confirmed from the source above.

```rust
	fn current_reward_counter(
		&self,
		id: PoolId,
		bonded_points: BalanceOf<T>,
		commission: Perbill,
	) -> Result<(T::RewardCounter, BalanceOf<T>), Error<T>> {
		let balance = Self::current_balance(id);

		// Calculate the current payout balance. The first 3 values of this calculation added
		// together represent what the balance would be if no payouts were made. The
		// `last_recorded_total_payouts` is then subtracted from this value to cancel out previously
		// recorded payouts, leaving only the remaining payouts that have not been claimed.
		let current_payout_balance = balance
			.saturating_add(self.total_rewards_claimed)
			.saturating_add(self.total_commission_claimed)
			.saturating_sub(self.last_recorded_total_payouts);

		// Split the `current_payout_balance` into claimable rewards and claimable commission
		// according to the current commission rate.
		let new_pending_commission = commission * current_payout_balance;
		let new_pending_rewards = current_payout_balance.saturating_sub(new_pending_commission);

		// * accuracy notes regarding the multiplication in `checked_from_rational`:
		// `current_payout_balance` is a subset of the total_issuance at the very worse.
		// `bonded_points` are similarly, in a non-slashed pool, have the same granularity as
		// balance, and are thus below within the range of total_issuance. In the worse case
		// scenario, for `saturating_from_rational`, we have:
		//
		// dot_total_issuance * 10^18 / `minJoinBond`
		//
		// assuming `MinJoinBond == ED`
		//
		// dot_total_issuance * 10^18 / 10^10 = dot_total_issuance * 10^8
		//
		// which, with the current numbers, is a miniscule fraction of the u128 capacity.
		//
		// Thus, adding two values of type reward counter should be safe for ages in a chain like
		// Polkadot. The important note here is that `reward_pool.last_recorded_reward_counter` only
		// ever accumulates, but its semantics imply that it is less than total_issuance, when
		// represented as `FixedU128`, which means it is less than `total_issuance * 10^18`.
		//
		// * accuracy notes regarding `checked_from_rational` collapsing to zero, meaning that no
		//   reward can be claimed:
		//
		// largest `bonded_points`, such that the reward counter is non-zero, with `FixedU128` will
		// be when the payout is being computed. This essentially means `payout/bonded_points` needs
		// to be more than 1/1^18. Thus, assuming that `bonded_points` will always be less than `10
		// * dot_total_issuance`, if the reward_counter is the smallest possible value, the value of
		//   the
		// reward being calculated is:
		//
		// x / 10^20 = 1/ 10^18
		//
		// x = 100
		//
		// which is basically 10^-8 DOTs. See `smallest_claimable_reward` for an example of this.
		let current_reward_counter =
			T::RewardCounter::checked_from_rational(new_pending_rewards, bonded_points)
				.and_then(|ref r| self.last_recorded_reward_counter.checked_add(r))
				.ok_or(Error::<T>::OverflowRisk)?;

		Ok((current_reward_counter, new_pending_commission))
	}
```

```rust
	fn do_reward_payout(
		member_account: &T::AccountId,
		member: &mut PoolMember<T>,
		bonded_pool: &mut BondedPool<T>,
		reward_pool: &mut RewardPool<T>,
	) -> Result<BalanceOf<T>, DispatchError> {
		debug_assert_eq!(member.pool_id, bonded_pool.id);
		debug_assert_eq!(&mut PoolMembers::<T>::get(member_account).unwrap(), member);

		// a member who has no skin in the game anymore cannot claim any rewards.
		ensure!(!member.active_points().is_zero(), Error::<T>::FullyUnbonding);

		let (current_reward_counter, _) = reward_pool.current_reward_counter(
			bonded_pool.id,
			bonded_pool.points,
			bonded_pool.commission.current(),
		)?;

		// Determine the pending rewards. In scenarios where commission is 100%, `pending_rewards`
		// will be zero.
		let pending_rewards = member.pending_rewards(current_reward_counter)?;
		if pending_rewards.is_zero() {
			return Ok(pending_rewards);
		}

		// IFF the reward is non-zero alter the member and reward pool info.
		member.last_recorded_reward_counter = current_reward_counter;
		reward_pool.register_claimed_reward(pending_rewards);

		T::Currency::transfer(
			&bonded_pool.reward_account(),
			member_account,
			pending_rewards,
			// defensive: the depositor has put existential deposit into the pool and it stays
			// untouched, reward account shall not die.
			Preservation::Preserve,
		)?;
```
