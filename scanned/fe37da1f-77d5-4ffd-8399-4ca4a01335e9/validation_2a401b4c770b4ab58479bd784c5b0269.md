### Title
Relayer-supplied `reward_address` in Snowbridge delivery receipt is unauthenticated and redirects the order's fee/surplus - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`process_delivery_receipt` accepts a `DeliveryReceipt` decoded from an Ethereum-side event and uses a self-reported `reward_address` field to decide who receives the delivery reward for a pending order. Only `receipt.gateway` (the Gateway contract address) and `receipt.nonce` (used to look up the pending order) are checked against trusted state; `receipt.reward_address` is not bound to the relayer who actually performed the work, nor to any commitment made when the order was created. This mirrors the CoW `appData` bug: the "core" fields of the message (gateway, nonce) are validated, but an auxiliary field that determines where value/surplus goes is not checked, letting the party who controls message content redirect the payout.

```rust
pub fn process_delivery_receipt(
    relayer: <T as frame_system::Config>::AccountId,
    receipt: DeliveryReceipt,
) -> DispatchResult
where
    <T as frame_system::Config>::AccountId: From<[u8; 32]>,
{
    // Verify that the message was submitted from the known Gateway contract
    ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

    let reward_account = if receipt.reward_address == [0u8; 32] {
        relayer
    } else {
        receipt.reward_address.into()
    };

    let nonce = receipt.nonce;

    let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

    if order.fee > 0 {
        // Pay relayer reward
        T::RewardPayment::register_reward(
            &reward_account,
            T::DefaultRewardKind::get(),
            order.fee,
        );
    }
    ...
}
```

The function checks:
- `receipt.gateway` against the fixed `GatewayAddress` (chain binding), and
- `receipt.nonce` against `PendingOrders` (route/order binding).

It does **not** check `receipt.reward_address` against anything. This field arrives inside the decoded event data emitted from Ethereum and is ultimately attacker-influenced content in the same sense as CoW's `appData`: the "core" identifiers (gateway, nonce) that make the message look legitimate are verified, but the auxiliary field that determines the fund beneficiary is accepted unconditionally as long as it decodes to 32 bytes. Whoever controls the content of the Ethereum-side delivery event (e.g. an operator of the relayer infrastructure, or anyone able to influence the emitted event data before it reaches the on-chain receipt-processing logic) can set `reward_address` to an address they control instead of the address of the account that actually performed the delivery work and is entitled to `order.fee`.

### Impact Explanation
`order.fee`, the accumulated reward for successfully delivering an outbound Snowbridge message, is unconditionally routed to `receipt.reward_address` whenever it is non-zero, bypassing any linkage to the account identified via the `relayer` parameter (which is the only value covered by extrinsic-level authorization and is only used as a fallback when `reward_address == [0u8;32]`). This is a "wrong beneficiary" / value-conservation violation: relayer rewards intended for the delivering party can be diverted to an arbitrary account, corrupting `order.fee` payout and undermining the incentive structure that pays for bridge processing.

### Likelihood Explanation
Likelihood depends on whether upstream verification of the Ethereum event (before it becomes a `DeliveryReceipt`) also authenticates `reward_address` against the actual delivering relayer address recorded on Ethereum. From the pallet code alone, no such binding exists at this layer, and the field's only sentinel treatment is `[0u8; 32]` → fall back to `relayer`. Any non-zero value is accepted without cross-checking it against the relayer's own identity or the original order's relayer commitment, which is the exact "adversary manipulates an unchecked auxiliary field to redirect value" pattern from the source report.

### Recommendation
Bind `reward_address` to a value that cannot be independently manipulated by whoever crafts the event: either (a) drop the field entirely and always reward the `relayer` account established by the message-verification layer, or (b) require the reward beneficiary to be committed at order-creation time (stored in `PendingOrders`) and reject the receipt if `receipt.reward_address` does not match that committed value.

### Proof of Concept
1. A relayer relays a message and delivery is confirmed on Ethereum, generating an event that is packaged as `DeliveryReceipt { gateway, nonce, reward_address, .. }`.
2. An adversary who can influence the reward_address encoding of this event (e.g., a compromised or malicious component upstream of `process_delivery_receipt`, or a bug allowing arbitrary event replay with modified payload while still passing gateway/nonce checks) sets `reward_address` to their own 32-byte account.
3. `process_delivery_receipt` verifies only `receipt.gateway == GatewayAddress` and that `nonce` maps to a valid `PendingOrders` entry — both satisfied.
4. `T::RewardPayment::register_reward` credits `order.fee` to the adversary's `reward_address` instead of the legitimate relayer, exactly analogous to the CoW `appData` surplus-redirection bug. [2](#0-1)
