### Title
Staking reward payout silently drops nominator/validator rewards when the pot-to-payee transfer fails, while the era/page is permanently marked as claimed - ([File: substrate/frame/staking-async/src/pallet/impls.rs])

### Summary
The external report's core defect is: a contract that is supposed to *receive* native value has no mechanism to accept it, so the transfer reverts and the expected settlement never happens, even though the caller believes the operation is safe. The direct analog in this repository is in `pallet-staking-async`'s pot-based reward payout path (`payout_from_provider` / `make_payout_from_provider`), where a failed `T::Currency::transfer` to a payee account is swallowed as a soft failure (`log::error!` + `return None`) instead of being treated as a fatal condition, while the calling dispatchable still marks the era/page as claimed and disallows retries.

### Finding Description
`make_payout_from_provider` resolves the payee account for a stash and performs a **transfer** (not a mint) from the era reward pot to that account: [1](#0-0) 

If `T::Currency::transfer` fails for any reason (e.g., the destination account cannot accept the incoming transfer under its `Preservation::Expendable` constraints, is subject to freezes/holds, or otherwise rejects the deposit — the same broad "recipient cannot accept native value" class as the reported issue), the function only logs an error and returns `None`: [2](#0-1) 

The caller, `payout_from_provider`, only emits a `Rewarded` event and counts the nominator payout when `make_payout_from_provider` returns `Some`; on `None` it simply skips the reward with no error surfaced to the dispatchable: [3](#0-2) 

The public dispatchable `payout_stakers_by_page` invokes this whole page-payout routine and returns `Ok(...)` regardless of whether individual transfers inside the page succeeded: [4](#0-3) 

Because the dispatchable returns success and the page is tracked as claimed (guarded against retries via `Error::AlreadyClaimed`, confirmed in the test asserting a second payout call for the same page is rejected): [5](#0-4) 

there is no code path that rolls back the "claimed" marking or retries the payout when the underlying transfer silently failed. This mirrors the reported bug's root cause exactly: a value-receiving operation that can fail for the recipient's reasons (missing acceptance logic in the reported case; transfer preconditions here) is not gated atomically with the state that says "this obligation is settled."

### Impact Explanation
If any nominator's or validator's payee account cannot accept the `Preservation::Expendable` transfer from the era reward pot (for instance, an account below the destination's required existence/hold constraints, or one whose `fungible::Mutate` implementation rejects the deposit for currency-specific reasons), that staker's reward for the era/page is permanently and silently lost: it is never paid, the page is marked claimed, and `payout_stakers_by_page` cannot be called again for that page. This directly matches the "permanent user-fund lock" and "payout state must only advance after ... settlement succeed atomically" pivots — payout state advances (claimed) even though settlement (the transfer) did not succeed.

### Likelihood Explanation
Likelihood is significant because `payout_stakers_by_page` is a public, unprivileged dispatchable ("Any account can call this function, even if it is not one of the stakers") per its own doc comment, and payee accounts are attacker/user-controlled via `set_payee`/`Account(dest_account)`. A user can set an unusual reward destination account, and any transient or persistent inability of that account to accept an `Expendable`-preserved transfer (e.g., existential deposit edge cases, non-existent/frozen accounts, or asset-specific transfer restrictions) causes silent, permanent reward loss for that page with no built-in retry.

### Recommendation
`make_payout_from_provider` (and its `payout_legacy_mint`/`payout_from_provider` callers) should not swallow transfer failures as a no-op skip. Either:
- Fail the whole `payout_stakers_by_page` call (and do **not** mark the page as claimed) when any constituent transfer fails, allowing retry once the destination account's condition is fixed, or
- Explicitly track and emit a distinguishable "payout failed for stash X" event and provide a dedicated re-claim path for the specific failed entries, instead of conflating "page claimed" with "all transfers in the page succeeded."

### Proof of Concept
1. Set up a validator with nominators; call `payout_stakers_by_page` normally to see event `Event::Rewarded` per successful transfer.
2. Configure/target a nominator's payee account (`RewardDestination::Account(dest_account)`) such that a `T::Currency::transfer(pot, dest_account, amount, Preservation::Expendable)` call fails (e.g., an account state that rejects the incoming deposit under the runtime's configured `Currency` implementation).
3. Call `payout_stakers_by_page` for that era/page as any signed account.
4. Observe: the call returns `Ok`, no `Rewarded` event is emitted for that nominator, the era reward pot balance is unaffected for that stake share, but `ClaimedRewards`/page-claimed state is set such that a subsequent `payout_stakers_by_page` for the same era/page returns `Error::AlreadyClaimed`, permanently forfeiting that nominator's reward. 	/// Make a payment to a staker from an era reward pot (transfer, not mint).
	fn make_payout_from_provider(
		era: EraIndex,
		stash: &T::AccountId,
		amount: BalanceOf<T>,
	) -> Option<(BalanceOf<T>, RewardDestination<T::AccountId>)> {
		if amount.is_zero() {
			return None;
		}

		let dest = match Self::payee(Stash(stash.clone())) {
			Some(d) => d,
			None => {
				Self::deposit_event(Event::<T>::Unexpected(UnexpectedKind::MissingPayee {
					era,
					stash: stash.clone(),
				}));
				return None;
			},
		};

		let payout_account = Self::payout_account_for_dest(stash, &dest)?;

		let staker_rewards_pot =
			T::RewardPots::pot_account(RewardPot::Era(era, RewardKind::StakerRewards));
		if let Err(e) = T::Currency::transfer(
			&staker_rewards_pot,
			&payout_account,
			amount,
			Preservation::Expendable,
		) {
			log!(
				error,
				"Failed to transfer reward from pot for era {:?}, stash {:?}: {:?}",
				era,
				stash,
				e
			);
			return None;
		}
