Target: `SlotMetadata::auth_digest` in libstackerdb/src/libstackerdb.rs, used by `SlotMetadata::sign`/`SlotMetadata::verify` and by `StackerDBChunkData::sign`/`StackerDBChunkData::verify`. Attacker action: a legitimate owner of slot 3 in StackerDB contract A signs a `StackerDBChunkData{slot_id:3, slot_version:7, data}`; the attacker (who does not own slot 3 in StackerDB contract B, but the two contracts share the same reward-cycle signer set so the same StacksAddress is slot 3's owner in both) resubmits the identical `sig`+`data` to contract B's chunk-write endpoint. Preconditions: two StackerDB configs whose slot 3 owner resolves to the same StacksAddress at the current reward cycle; auth_digest hashes only `slot_id`, `slot_version`, `data_hash` and never the smart-contract identifier. Call sequence: POST /v2/stackerdb/{contract_B}/{name}/chunks -> StackerDBChunkData::consensus_deserialize -> StackerDBChunkData::verify(addr) -> SlotMetadata::verify -> stackerdb/db.rs write path. Equality broken: authenticated-owner(contract_A, slot 3) == authenticated-owner(contract_B, slot 3) is not required by auth_digest, so a signature never binding the contract identity satisfies OWNERSHIP for a slot it wasn't produced for. Impact: Critical, unauthenticated cross-DB chunk forgery. Proof: Rust test in stackslib::net constructing two StackerDBConfig with slot 3 owned by the same address, signing one StackerDBChunkData for contract A, and asserting it is (wrongly) accepted for contract B.
