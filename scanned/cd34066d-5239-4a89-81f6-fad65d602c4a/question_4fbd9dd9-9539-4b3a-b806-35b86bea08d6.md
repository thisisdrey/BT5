Target: interaction between `StackerDBChunkData::verify` (per-chunk boolean) and the transactional write in `StackerDBTx`/`StackerDBs` (stackerdb/db.rs). Attacker action: race two chunk submissions for the same slot at the same claimed version N+1 — one legitimately signed by the true owner, one with the same version but a bogus signature from the attacker — sent nearly simultaneously to exploit a check-then-act gap between `verify()` and the SQLite write. Preconditions: attacker can send concurrent requests to the chunk-POST endpoint for a slot whose current stored version is N. Call sequence: request A: verify(true owner)=Ok -> begins write; request B: verify(bogus)=Err should short-circuit before touching the DB. Equality to test: any request whose `verify` returns `Err`/`false` must NEVER reach `StackerDBTx` commit, regardless of interleaving with a concurrent valid write. Impact: Critical, a race window could let an unverified chunk's `INSERT/UPDATE` execute if verification and write are not enforced atomically per (stackerdb_id, slot_id). Proof: Rust test in stackslib::net spawning two threads submitting a valid and an invalid chunk for the same slot/version concurrently, asserting the DB only ever contains the valid one.
