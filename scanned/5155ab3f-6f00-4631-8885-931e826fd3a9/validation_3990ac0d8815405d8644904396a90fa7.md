### Title
`transfer_ownership` in pallet-uniques/pallet-nfts silently accepts partial deposit repatriation, letting a collection change owner while the old owner keeps part of the reserved deposit - ([File: substrate/frame/uniques/src/lib.rs])

### Summary
This mirrors the elfi-protocol H-23 pattern: a "best-effort" balance-reduction primitive is called, its unconsumed remainder is discarded, and the caller proceeds as if the full amount was moved, leaving accounting out of sync with real reserved balance. In elfi, `min(addMarginAmount, holdPoolAmount)` silently dropped the excess, letting a position keep its size while losing its debt/fee obligation. Here, `ReservableCurrency::repatriate_reserved` is documented as best-effort ("as much... as possible... if this is less than value, `Ok(non_zero)` is returned") [1](#0-0) , yet `pallet-uniques::transfer_ownership` and `pallet-nfts::do_transfer_ownership` call it and drop the `Result`'s remainder without checking it is zero, then unconditionally flip collection ownership.

### Finding Description
`pallet-assets::transfer_ownership` had exactly this bug and was fixed: the fix captures the remainder from `repatriate_reserved` and rejects the dispatch with `IncompleteDepositTransfer` if non-zero, rolling back the storage mutation [2](#0-1) , confirmed by the prdoc describing the exact root cause ("a lock or freeze on the current owner that overlaps their free balance can leave part of the reserved deposit behind... out of sync with what is actually reserved") [3](#0-2) .

`pallet-uniques` never received the analogous fix. Its `transfer_ownership` call performs the exact same call pattern, discarding the result of `repatriate_reserved`: [4](#0-3) 

`pallet-nfts::do_transfer_ownership` has the identical flaw: [5](#0-4) 

In both cases:
- `details.owner_deposit`/`details.total_deposit` records how much is supposed to be reserved for the collection deposit.
- `repatriate_reserved(&details.owner, &new_owner, deposit, Reserved)` is best-effort: if the current owner has a `lock`/`freeze` that overlaps their free balance (as demonstrated in the pallet-assets regression test) [6](#0-5) , only part of the reserved deposit actually moves.
- The return value (the un-moved remainder) is thrown away; `details.owner = new_owner` unconditionally proceeds, `CollectionAccount` mappings flip, and events are emitted as if the transfer fully succeeded.

The result: the collection's `owner_deposit`/`total_deposit` field (still recorded against the *old* owner's un-repatriated stake) no longer corresponds to what is actually reserved under the new owner. The new owner becomes the "owner of record" and controls the collection, while the deposit liability the protocol tracks for that collection is silently split/desynced from the actual reserved balances — the same "position retained, backing obligation quietly reduced/zeroed" primitive as H-23, just applied to a collection deposit instead of a borrowed/held amount.

### Impact Explanation
This breaks value conservation invariants for pallet-uniques/pallet-nfts deposits: the protocol's bookkeeping (`owner_deposit`/`total_deposit` on the `Collection`/`Item` storage) diverges from the actual on-chain reserved balances split across two accounts. An old owner can retain part of their previously-reserved deposit (which they can then unreserve/spend, since the lock that blocked repatriation is under their own control) while transferring away ownership and its associated accountability, and the new owner is recorded as fully responsible for a deposit they didn't fully post. This is a state-desync/fund-accounting bug reachable through a completely permissionless, unprivileged public extrinsic (`transfer_ownership`), matching the "public dispatch wrappers must not undercharge nested execution / conserve value and settle exactly once" pivot criteria.

### Likelihood Explanation
High likelihood of triggerability: any account can place a `lock`/`freeze` on itself (e.g. via `pallet-balances::set_lock`, staking bond, vesting, or other lock providers) that overlaps its free balance, satisfying the `Polite`-fortitude repatriation constraint used by `Currency::repatriate_reserved`'s underlying `Balances` implementation. The owner only needs to self-apply a lock before calling the already-public, self-service `transfer_ownership` extrinsic to an account they control (or collude with) — no privileged actor, relayer, or validator involvement required. The bug is a straightforward oversight of an unchecked `Result<Balance, _>` whose `Ok` value (the un-repatriated remainder) is silently dropped in both pallets, exactly the class of defect that was already found and fixed once in the sibling `pallet-assets` code.

### Recommendation
Apply the same fix pattern used in `pallet-assets::transfer_ownership` to `pallet-uniques::transfer_ownership` and `pallet-nfts::do_transfer_ownership`: capture the `Result<Balance, _>` returned by `repatriate_reserved`, and if the remainder is non-zero, fail the dispatch (e.g. new `IncompleteDepositTransfer` error) before mutating `Collection`/`CollectionAccount` storage, ensuring the storage mutation and the reserve-repatriation succeed atomically or not at all.

### Proof of Concept
1. Account `A` creates a uniques/nfts collection, reserving `total_deposit`/`owner_deposit` D from its free balance.
2. `A` calls `Balances::set_lock` (or bonds via staking, or uses any other lock provider) to lock an amount ≥ free balance, so that under `Polite` fortitude `frozen - free > 0`, meaning part of the reserved D is "untouchable" for a best-effort reserved-balance move.
3. `A` (as current owner) has `B` call `set_accept_ownership(collection)`, then `A` calls `transfer_ownership(collection, B)`.
4. Inside, `repatriate_reserved(&A, &B, D, Reserved)` moves only `D' < D` to `B`'s reserved balance and returns `Ok(D - D')` (non-zero) as the un-moved remainder — this return value is discarded.
5. `Collection::owner` is set to `B`, `CollectionAccount` mappings updated, `OwnerChanged` event emitted — as though the full deposit `D` transferred.
6. Now `A` still holds `D - D'` reserved under their own account (which they can later `unreserve`/spend once they lift their self-imposed lock), while the collection's on-chain `total_deposit`/`owner_deposit` figure is recorded as fully backed by `B`, who only actually has `D'` reserved. Ownership (control) fully transferred; the deposit backing that ownership did not.

#[test]
fn transfer_ownership_fails_when_deposit_is_locked() {
	build_and_execute(|| {
		Balances::make_free_balance_be(&1, 100);
		Balances::make_free_balance_be(&2, 100);
		// Reserves 1 from owner 1: free=99, reserved=1.
		assert_ok!(Assets::create(RuntimeOrigin::signed(1), 0, 1, 1));
		assert_eq!(Balances::free_balance(&1), 99);
		assert_eq!(Balances::reserved_balance(&1), 1);

		// Lock the owner's full balance, so frozen=100 > free=99 and 1 unit of the
		// reserve becomes immovable under `Polite` repatriation.
		Balances::set_lock(*b"test/lk0", &1, 100, WithdrawReasons::all());

		assert_noop!(
			Assets::transfer_ownership(RuntimeOrigin::signed(1), 0, 2),
			Error::<Test>::IncompleteDepositTransfer,
		);
		// State is rolled back: original owner still holds the deposit.
		assert_eq!(Balances::reserved_balance(&1), 1);
		assert_eq!(Balances::reserved_balance(&2), 0);

		// Clearing the lock unblocks the call.
		Balances::remove_lock(*b"test/lk0", &1);
		assert_ok!(Assets::transfer_ownership(RuntimeOrigin::signed(1), 0, 2));
		assert_eq!(Balances::reserved_balance(&1), 0);
		assert_eq!(Balances::reserved_balance(&2), 1);
	});
