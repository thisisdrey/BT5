### Title
`hop_submit` signature does not bind the recipient list or sender, allowing signature reuse to redirect delivery / hijack promotion credit - (File: `substrate/client/hop/src/types.rs`, `substrate/client/hop/src/pool.rs`)

### Summary
The ParaSpace report's root cause is that a signed authorization structure (`Credit`) omits a binding field (marketplace identifier), so a signature valid for one context can be replayed in a different, attacker-chosen context. The `substrate/client/hop` component (a data-availability handoff pool with an on-chain "promotion" step) has the same class of defect: the payload a submitter signs for `hop_submit`, `submit_signing_payload`, commits only to `blake2_256(data)` and `submit_timestamp` — it does **not** commit to the `recipients` list or the `sender_id`, both of which are supplied as separate, unsigned arguments to `HopDataPool::insert`.

### Finding Description
`submit_signing_payload` in `substrate/client/hop/src/types.rs` is defined as: [1](#0-0) 

The doc comment explicitly states this exact byte sequence — `HOP_SUBMIT_CONTEXT || blake2_256(data) || submit_timestamp` — is what "the runtime pallet re-derives ... to verify the signature on-chain." Neither the recipients (`RecipientVec`) nor the `sender_id` are folded into this digest.

`HopEntryMeta::new` and `HopDataPool::insert` accept `recipients`, `sender_id`, `signer`, `signature`, and `submit_timestamp` as independent parameters and store them together, but the signature was never computed over `recipients`/`sender_id`: [2](#0-1) [3](#0-2) 

Because the signature only proves "I signed off on this content hash at this timestamp," any party that observes a valid `(data, signer, signature, submit_timestamp)` tuple (e.g., from the pool's public RPC surface, from a node's replicated pool state, or simply as the recipient/counterparty of a legitimate handoff) can resubmit that exact tuple with an **arbitrary substituted `recipients` list** to `insert`. The signature check performed against `submit_signing_payload(hash, submit_timestamp)` will still pass, since neither of the substituted fields is part of the signed digest — this is structurally identical to the ParaSpace `Credit` struct missing `MarketplaceAddress`, which let a `taker`-chosen `orderId`/marketplace be substituted under a signature that never bound it.

The consequence in HOP's design is that the "submit implies consent to promote" protocol invariant (documented at `substrate/client/hop/src/types.rs:79`) is broken: the signer's consent was only ever over the content hash and timestamp, not over who receives the data or which account's per-user quota/promotion credit is charged. An attacker can therefore graft a victim's genuine signed submission onto a recipient set or sender identity the victim never authorized.

### Impact Explanation
This allows unauthorized redirection of privileged delivery/consent semantics: an attacker can cause data promoted on-chain to be attributed to a different `sender_id` (affecting quota accounting) or delivered/attested to different `recipients` than the signer intended, while still presenting a signature that the runtime pallet will accept as valid consent. This falls under "forged or mis-bound proof or state acceptance" and "duplicate settlement" classes in the impact gate, since the same signed artifact can be bound to a different outcome than what the signer authorized, without any privileged actor, governance, or key compromise involved — any unprivileged caller with access to a previously broadcast submission can perform this.

### Likelihood Explanation
Likelihood is elevated by design: `hop_submit` payloads (data + signer + signature + timestamp) are inherently observable by any recipient in the original recipient set or by any node that gossips/serves pool contents via RPC (`substrate/client/hop/src/rpc.rs`), and `insert` performs no independent check tying `recipients`/`sender_id` back into the signature. No relayer, validator, or admin compromise is required — a single dishonest recipient of a legitimate HOP submission is sufficient to reuse the enclosed signature.

### Recommendation
Fold `sender_id` and a commitment to the `recipients` list (e.g., a hash of the SCALE-encoded `RecipientVec`) into `submit_signing_payload`, mirroring the same fix ParaSpace was advised to apply (binding all context-defining fields into the signed struct before verification). This must be changed consistently in both the client-side pool logic and the on-chain pallet that re-derives and checks the digest.

### Proof of Concept
1. Victim signs a `hop_submit` request over `data` with `recipients = [R_v]`, `sender_id = victim`, producing `signature = Sign(submit_signing_payload(blake2_256(data), t))`.
2. Attacker observes this tuple `(data, signer=victim_key, signature, t)` (e.g., as one of the intended recipients, or via any node exposing the pool/RPC).
3. Attacker calls `HopDataPool::insert(data, recipients=[R_attacker], sender_id=attacker_or_victim, signer=victim_key, signature, submit_timestamp=t)`.
4. Since `submit_signing_payload` only depends on `blake2_256(data)` and `t` (both unchanged), the on-chain re-verification against the same digest succeeds, even though `recipients`/`sender_id` differ from what the victim actually authorized — confirming the signature is not scoped to the fields that determine delivery/quota outcome.

Note: I was unable to view the actual on-chain pallet verification code or `rpc.rs`'s `hop_submit` handler within the remaining budget to confirm exactly how `insert`'s parameters are sourced from the RPC request (i.e., whether the RPC layer itself constrains `recipients`/`sender_id` to match the original submitter before forwarding to `insert`). This should be verified directly in `substrate/client/hop/src/rpc.rs` and the corresponding pallet before treating this as fully confirmed end-to-end.

/// Compute the 32-byte payload signed at `hop_submit` time.
///
/// The runtime pallet re-derives this exact byte sequence to verify the
/// signature on-chain, so the construction must remain byte-identical to the
/// pallet's `signing_payload(data, submit_timestamp)`:
/// `blake2_256(HOP_SUBMIT_CONTEXT || blake2_256(data) || submit_timestamp.to_le_bytes())`.
pub fn submit_signing_payload(hash: &HopHash, submit_timestamp: u64) -> [u8; 32] {
	let mut buf = [0u8; HOP_SUBMIT_CONTEXT.len() + 32 + 8];
	buf[..HOP_SUBMIT_CONTEXT.len()].copy_from_slice(HOP_SUBMIT_CONTEXT);
	buf[HOP_SUBMIT_CONTEXT.len()..HOP_SUBMIT_CONTEXT.len() + 32].copy_from_slice(hash.as_bytes());
	buf[HOP_SUBMIT_CONTEXT.len() + 32..].copy_from_slice(&submit_timestamp.to_le_bytes());
	blake2_256(&buf)
}
