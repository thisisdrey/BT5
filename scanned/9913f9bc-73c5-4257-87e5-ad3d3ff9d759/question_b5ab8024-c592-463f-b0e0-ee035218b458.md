[Function: liquidate-multi] `liquidate-multi` maps `call-liquidate` over a `(list 64 {...})` of borrower/collateral-ft/debt-ft/debt-amount tuples, each internally invoking `liquidate`, which itself asserts `(is-eq contract-caller tx-sender)`. Attacker action: attacker submits `(contract-call? .v0-4-market liquidate-multi (list {borrower: V1, collateral-ft: .vault-ststx, debt-ft: .vault-stx, debt-amount: X, min-collateral-expected: u0} {borrower: V2, ...}))` in one transaction, deliberately ordering entries so that the FIRST liquidation's `vault-system-repay`/`collateral-remove` side effects on shared caches (`index-cache`, mask bits) are read stale by the SECOND entry before `accrue-and-cache` would have refreshed them within the same block. Preconditions: V1 and V2 both liquidatable, sharing the same debt asset id so `index-cache` keyed by `{timestamp: stacks-block-time, aid}` is reused across both `call-liquidate` invocations. Call sequence: single tx -> liquidate-multi -> call-liquidate(V1) mutates `v0-market-vault` debt/collateral maps and vault `principal-scaled`/`assets` -> call-liquidate(V2) reads `get-cached-indexes` from the SAME per-block cache entry populated during V1's pass, potentially using a stale borrow-index that doesn't reflect V1's `system-repay`-driven change to `total-borrowed`. Invariant tested: cached value and its source agree - `index-cache` entry for `{timestamp, aid}` must always equal the vault's true current index, i.e. accrual must be idempotent and correct across multiple liquidations of DIFFERENT borrowers sharing an asset in one atomic batch. Impact: Critical, protocol insolvency if V2's `debt-to-repay`/`coll-final` is computed against an index that no longer matches vault state, allowing V2's liquidator to seize more collateral than the debt actually repaid justifies. Proof idea: Clarinet simnet test executing `liquidate-multi` with two positions sharing debt asset stSTX-debt, snapshot vault `total-borrowed`/`principal-scaled` before and after, and assert `sum(debt-to-repay across both liquidations) == sum(scaled-to-remove * borrow-index / INDEX-PRECISION)` using the index each liquidation actually consumed, catching any cache-staleness that lets collateral-seized exceed debt-repaid*penalty for either entry.
