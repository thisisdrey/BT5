### Title
Unweighted "first vote" fee-waiver in `pallet-collective::vote` can be farmed via zero-cost dummy proposals - (File: `substrate/frame/collective/src/lib.rs`)

### Summary
`AgentDAO._castVote()` grants a permanent, unbounded "score" bump to *any* address the moment it casts its first vote on *any* proposal, with no check that the voter actually holds weight and no cost gate on proposal creation (threshold=0). `pallet-collective` has the structurally identical pattern: `vote()` grants a `Pays::No` fee waiver purely based on "is this the voter's first vote on this specific proposal hash", and proposal creation cost is fully configurable down to zero via the `Consideration` trait (`T::Consideration::new`, unit-type = no cost, per PR `pr_3151.prdoc`). Neither check verifies that the vote reflects any real economic weight or governance contribution — exactly the invariant break flagged in the source report ("anybody can create a dummy proposal and vote to increase score/benefit").

### Finding Description
`Collective::vote()` dispatches through `do_vote`, which determines `is_account_voting_first_time` solely from whether the caller's account already appears in `voting.ayes`/`voting.nays` for that one proposal hash: [1](#0-0) 

The extrinsic then converts that boolean directly into a transaction-fee waiver, with no requirement on stake, rank, or any other "weight": [2](#0-1) 

Proposal creation cost is fully pluggable through `T::Consideration`, and per the pallet's own PRDoc, a runtime may set it to the unit type to make proposal submission free: [3](#0-2) 

`do_propose_proposed` calls `T::Consideration::new(&who, active_proposals - 1)` and only stores a hold if the cost is non-`None`: [4](#0-3) 

With `Consideration = ()` (a config choice several runtimes use for zero submission friction) and a low `threshold`, a member can:
1. Submit `N` trivially distinct proposals (e.g. `remark` calls with different payloads) at zero deposit cost, bounded only by `MaxProposals`.
2. Cast a first vote on each — each vote is fee-free because `is_account_voting_first_time` is `true` per proposal, regardless of the vote's actual governance weight or outcome.
3. Close/disapprove the proposals (also cheap, `disapprove_proposal`/`close_early_disapproved` paths) to free slots and repeat indefinitely.

This mirrors AgentDAO's flaw exactly: the "reward" (there: `+1` score; here: fee waiver) is granted purely by the act of voting on a self-created, cost-free proposal, without any check that the vote carries real weight (`weight > 0` in AgentDAO's terms). The report's own recommended fix — "add a check that weight > 0 before increasing" — has no counterpart here either: `do_vote` never checks stake, rank, or any weight-like quantity before granting the waiver.

### Impact Explanation
An account can convert an unbounded stream of `propose` + `vote` (+ `close`/`disapprove`) extrinsics into fee-free transactions, i.e. public underpriced work: real block weight/storage churn is consumed while the extrinsic issuer pays no transaction fee for the votes. At scale this degrades block production economics for the chain running the collective (fee-based spam resistance is bypassed), which is one of the explicitly in-scope impacts ("public underpriced work that degrades block production").

### Likelihood Explanation
Requires only that (a) the runtime configures `Consideration` cheaply/free (an intended, documented configuration option, not a bug in itself) and (b) the caller is a `Collective` member — no admin/governance/validator privilege is being *abused*, the actor is simply using the permissionless `propose`/`vote` extrinsics as designed. The exploit primitive (spamming self-created proposals to farm an unweighted per-vote benefit) is directly analogous to and no more privileged than the AgentDAO case, where any token holder (not an admin) could do the same.

### Recommendation
Do not derive the `Pays::No` fee waiver purely from "first vote on this proposal hash". Either remove the automatic waiver, or gate it on a bounded per-account/per-period counter, or tie it to `T::Consideration` cost paid on the proposal (so the waiver cannot be repeated for free across attacker-created proposals). Ensure `Consideration::new` cannot resolve to "no cost" in permissionless collective configurations if the fee waiver feature remains enabled.

### Proof of Concept
Conceptually (mirrors the Solidity PoC structure):
1. Configure `Collective` with `Consideration = ()` and `threshold = 1`, attacker is a member.
2. Loop `i in 0..MaxProposals`: `propose(threshold, remark(i), len)` → zero deposit cost.
3. For each resulting `proposal_hash`: `vote(proposal_hash, index, true)` → `is_account_voting_first_time == true` → `Pays::No`.
4. `close_early_disapproved`/`disapprove_proposal` to clear `Proposals` storage and repeat from step 2.
5. Net effect: unlimited fee-free extrinsics processed by the chain, verifiable via `get_result_weight`/`Pays::No` post-dispatch info on each `vote` call.
