### Title
Permanently blocked bounty beneficiary can lock a parent bounty forever via `ChildBountiesPerParent` - (File: `substrate/frame/multi-asset-bounties/src/lib.rs`)

### Summary
`pallet-multi-asset-bounties` requires `ChildBountiesPerParent::<T, I>::get(parent_bounty_id) == 0` before a parent bounty can be closed or awarded. This counter is only decremented inside `remove_bounty`, which is only reached when a child bounty's payout or refund payment eventually *succeeds*. If a single child bounty's beneficiary/curator payout can never succeed (e.g. the beneficiary account is a frozen/blocked asset account, analogous to a "blacklisted" address in the original ERC20 report), the child bounty is stuck forever in `PayoutAttempted`/`RefundAttempted`, the counter never reaches zero, and the parent bounty — along with any correctly-behaving other child bounties' funding source — is permanently locked. This mirrors the `withdrawExcessRewards()` DoS: one uncooperative payee (cheap/negligible cost to create) blocks a shared state transition (`totalDepositsWei == 0` / `ChildBountiesPerParent == 0`) that gates fund recovery for everyone else.

### Finding Description
`award_bounty` and `close_bounty` (parent-level, `child_bounty_id: None`) both gate on: [1](#0-0) [2](#0-1) 

`ChildBountiesPerParent` is only decremented in `remove_bounty`, called exclusively from the success branches of `check_status` (`PaymentState::Succeeded` for `RefundAttempted` and `PayoutAttempted`): [3](#0-2) [4](#0-3) 

A child bounty enters `PayoutAttempted` when its curator calls `award_bounty`, which calls `do_process_payout_payment` → `T::Paymaster::pay(...)` to the caller-supplied `beneficiary`: [5](#0-4) 

If the beneficiary account can never accept the asset (frozen/blocked account status, analogous to a blacklisted ERC20 holder — see `pallet-assets`'s `AccountStatus::Frozen`/`Blocked` semantics used elsewhere in this repo for similar payout flows), `do_check_payout_payment_status` will keep reporting `PaymentState::Failed`/`Pending` on every `check_status` call, and `retry_payment` will keep re-attempting and failing. The child bounty never transitions to `Succeeded`, `remove_bounty` is never called, and `ChildBountiesPerParent` for the parent never reaches zero — permanently blocking `close_bounty(parent_bounty_id, None)` and `award_bounty` for the parent.

Unlike `pallet-bounties`/`pallet-child-bounties` (native currency only, `AllowDeath` transfers to system accounts that can't reject funds), `pallet-multi-asset-bounties` explicitly supports arbitrary asset kinds and beneficiary "locations" via `T::Paymaster`/`T::BeneficiaryLookup`, which is precisely the class of payee that can be uncooperative (frozen, blocked, or otherwise permanently rejecting), reintroducing the original bug-class risk that native-currency bounty payouts didn't have.

### Impact Explanation
An attacker who can be named as a beneficiary of a child bounty (or who controls/games an account that later becomes frozen/blocked for the relevant asset) can permanently prevent the parent bounty from being closed or having further child bounties awarded, indefinitely locking the value held in the parent bounty and any correctly-behaving sibling child bounty funds/state that depend on `close_bounty`/`award_bounty` succeeding. This is a permanent user-fund/state lock via a public entrypoint (`award_bounty`, `check_status`, `retry_payment`) with no privileged actor required to trigger the vulnerable path, matching the "permanent user-fund or bridge-state lock" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment where `T::Paymaster` is backed by an asset system supporting frozen/blocked accounts (e.g. `pallet-assets`) and beneficiaries are looked up via `T::BeneficiaryLookup` from potentially attacker-influenced input (e.g., a curator awarding to a beneficiary they control, or a beneficiary getting blocked after being named). No governance or validator collusion is needed — only a normal signed curator/beneficiary interaction plus one asset-level block/freeze condition on the payee account.

### Recommendation
Decouple the parent bounty's `close_bounty`/`award_bounty` gating from unconditional resolution of every child's payment. Options:
- Allow the parent to force-cancel/force-remove a child bounty stuck in `PayoutAttempted`/`RefundAttempted` after a timeout, independent of payment success, freeing the `ChildBountiesPerParent` slot (e.g., write off the stuck payment to a recoverable/pending state rather than blocking parent progress).
- Or allow `RejectOrigin`/parent curator to redirect a permanently-failing payment to an alternate account, so `remove_bounty` can eventually run.
- At minimum, add a "permanently failed" payment state (distinct from retryable `Failed`) that surfaces and allows administrative recovery instead of infinite retry deadlock.

### Proof of Concept
1. Create a parent bounty and a child bounty using an asset kind serviced by a `Paymaster` backed by `pallet-assets`.
2. As curator, call `award_bounty(parent_id, Some(child_id), beneficiary)` where `beneficiary` is an account that is (or later becomes) `Frozen`/`Blocked` for that asset — see the existing test pattern with blocked/frozen asset accounts in `substrate/frame/assets/src/tests.rs` (`transferring_to_blocked_account_should_not_work`, lines 866-880).
3. `do_process_payout_payment` initiates the payment; the underlying transfer to the frozen/blocked beneficiary fails.
4. Call `check_status(parent_id, Some(child_id))` repeatedly — status stays `PayoutAttempted { payment_status: Failed }` per `check_status`'s failure branch (lines 1256-1291); `retry_payment` also fails.
5. `ChildBountiesPerParent::<T, I>::get(parent_id)` remains `1` forever.
6. `close_bounty(parent_id, None)` and `award_bounty(parent_id, None, ...)` now always fail with `Error::<T, I>::HasActiveChildBounty` (lines 1014-1019, 1099-1105), permanently locking the parent bounty.

Note: I was unable to fully trace `do_check_payout_payment_status`/`retry_payment` bodies (only signatures matched via grep) and the exact `T::Paymaster`/asset-freeze integration wiring in the concrete runtime configuration within the given iteration budget — confirming the exact failure semantics of `Paymaster::pay` against a frozen/blocked account would benefit from a full read of those functions and the runtime's `Paymaster` implementation.

			let beneficiary = T::BeneficiaryLookup::lookup(beneficiary)?;

			let (asset_kind, value, _, status, _) =

			if child_bounty_id.is_none() {

				asset_kind,
				value,
				beneficiary.clone(),
				None,
			)?;

			let new_status = BountyStatus::PayoutAttempted {
				curator: curator.clone(),
				beneficiary: beneficiary.clone(),

			};
			Self::update_bounty_status(parent_bounty_id, child_bounty_id, new_status)?;

			Self::deposit_event(Event::<T, I>::BountyAwarded {
				index: parent_bounty_id,
				child_index: child_bounty_id,

			});
