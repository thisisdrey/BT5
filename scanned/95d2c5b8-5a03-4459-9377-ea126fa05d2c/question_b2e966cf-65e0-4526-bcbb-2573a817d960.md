Target: `process_event<T, E>` in `libsigner/src/events.rs`. Attacker action: send a POST to any recognized URL (e.g. `/stackerdb_chunks`) with a `Content-Length` header claiming an extremely large body size (bounded only by available memory) and slowly or fully stream that many bytes. Preconditions: TCP reachability only. Call sequence: `request.as_reader().read_to_string(&mut body)` reads the entire declared body length into a `String` with no explicit cap enforced by `process_event` itself (unlike `libsigner::http::decode_http_body`, which caps chunked bodies at `MAX_MESSAGE_LEN`). Equality/fault: BOUNDS — bytes read for the body should be capped at a validated maximum message size, but `process_event` imposes none. Scoped impact (Critical): a single crafted request can force the signer process to allocate an attacker-chosen amount of memory, a bounded-input remote resource-exhaustion/crash vector distinct from generic volumetric flooding since one request suffices. Proof idea: a test sends one POST with a huge (but not infinite) `Content-Length` and body to a bound `SignerEventReceiver`, and observes memory growth or timeout/panic proportional to the attacker-chosen length rather than to any capped constant.
