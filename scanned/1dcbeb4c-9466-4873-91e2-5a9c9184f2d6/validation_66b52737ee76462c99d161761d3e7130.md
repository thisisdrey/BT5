### Title
Permissionless dust-transfer griefing permanently blocks `refund_other` deposit reclamation in `pallet-assets` - ([File: substrate/frame/assets/src/functions.rs])

### Summary
The external report's core broken invariant is: a strict `balance == 0` guard on an account-closing instruction can be defeated by an unprivileged attacker permissionlessly sending a trivial amount of the tracked token directly into the target account, permanently blocking closure/refund and freezing the legitimate depositor's funds. The same pattern exists in `pallet-assets::do_refund_other`, which is the FRAME analog of the Solana `close_withdrawal_window` bug.

### Finding Description
`do_refund_other` is used to let a depositor (or asset admin) reclaim the existential deposit that was paid on behalf of another account via `touch_other`, once that account's asset balance is zero: [1](#0-0) 

Unlike `do_refund` (used for self-refund), which accepts an `allow_burn` flag that lets the caller force-close and burn any remaining dust, `do_refund_other` has no such escape hatch — it unconditionally requires:
```
ensure!(account.balance.is_zero(), Error::<T, I>::WouldBurn);
```

Any account holding a `pallet-assets` asset can receive tokens from *anyone* via the ordinary, permissionless `transfer`/`transfer_keep_alive` extrinsics as long as the asset is `Live` and the target account is not frozen — no cooperation or permission from the account owner is required. This mirrors the Solana bug exactly: a malicious third party can send a minimal (even a single unit, or an amount as small as `min_balance` if the account isn't `sufficient`) balance of the asset into `who`'s account at any time before `refund_other` executes, causing `account.balance.is_zero()` to become false forever (since a normal `transfer` back out is not something the depositor/admin can force upon the account holder).

This blocks the *only* code path (`do_refund_other`) available for a depositor/admin to reclaim the deposit they paid on behalf of `who`, permanently locking that deposit (analogous to `window_authority` being unable to close the ATA in the reported bug).

### Impact Explanation
This is a permanent value-lock (fund-lock) issue reachable by an unprivileged public entrypoint (`Assets::transfer`), satisfying the "permanent user-fund... lock" impact category. It does not require a malicious validator/collator/relayer/admin — any ordinary user can grief any `touch_other` deposit by sending dust to the target account. The depositor's reserved existential deposit becomes permanently stuck as long as the griefer (or anyone) keeps a nonzero balance on that account, since re-griefing can be repeated indefinitely after every attempted cleanup by the legitimate account holder.

### Likelihood Explanation
High feasibility: `transfer`/`transfer_keep_alive` are ordinary, permissionless, low-cost extrinsics available to any signed account; sending 1 unit of the asset costs negligible fees. The precondition — `who`'s account exists via `touch_other` and is not frozen — is a normal, common use case (e.g., a chain sponsoring account creation for users who don't yet hold the asset). No governance, validator, or privileged action is needed to trigger the block.

### Recommendation
- Add an `allow_burn`-style parameter (or a separate `force_refund_other` call restricted to the admin) to `do_refund_other`, mirroring `do_refund`'s handling, so the deposit can be reclaimed by burning/sweeping the dust balance instead of being unconditionally blocked.
- Alternatively, allow `refund_other` to forward any nonzero dust to the depositor or admin (analogous to the fix in the reported Solana bug: "transfer any remaining tokens... before closing") rather than reverting with `WouldBurn`.

### Proof of Concept
1. Admin (or any account) calls `Assets::touch_other(admin, asset_id, victim)`, creating `victim`'s asset account and reserving the existential deposit from `admin`.
2. Attacker (any unrelated account holding the asset) calls `Assets::transfer(attacker, asset_id, victim, 1)` — succeeds because `transfer` has no restriction on sending to arbitrary live, non-frozen accounts.
3. `victim`'s `Account::balance` is now `1` (nonzero).
4. Admin calls `Assets::refund_other(admin, asset_id, victim)` → `do_refund_other` hits `ensure!(account.balance.is_zero(), Error::WouldBurn)` and fails.
5. Attacker repeats step 2 any time admin/victim tries to zero the balance out via a transfer, permanently denying deposit reclamation. [2](#0-1)

```rust
	/// Refunds the `DepositFrom` of an account only if its balance is zero.
	///
	/// If the `maybe_check_caller` parameter is specified, it must match the account that provided
	/// the deposit or must be the admin of the asset.
	pub(super) fn do_refund_other(
		id: T::AssetId,
		who: &T::AccountId,
		maybe_check_caller: Option<T::AccountId>,
	) -> DispatchResult {
		let mut account = Account::<T, I>::get(&id, &who).ok_or(Error::<T, I>::NoDeposit)?;
		let (depositor, deposit) =
			account.reason.take_deposit_from().ok_or(Error::<T, I>::NoDeposit)?;
		let mut details = Asset::<T, I>::get(&id).ok_or(Error::<T, I>::Unknown)?;
		ensure!(details.status == AssetStatus::Live, Error::<T, I>::AssetNotLive);
		ensure!(!account.status.is_frozen(), Error::<T, I>::Frozen);
		if let Some(caller) = maybe_check_caller {
			ensure!(caller == depositor || caller == details.admin, Error::<T, I>::NoPermission);
		}
		ensure!(account.balance.is_zero(), Error::<T, I>::WouldBurn);
		Self::ensure_account_can_die(id.clone(), who)?;

		T::Currency::unreserve(&depositor, deposit);
```
