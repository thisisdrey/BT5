### Title
`Mutate::transfer` default implementation returns the requested amount instead of the actual amount moved - ([File: substrate/frame/support/src/traits/tokens/fungible/regular.rs])

### Summary
The default `transfer` implementation in the `fungible::Mutate` and `fungibles::Mutate` traits performs the withdrawal/deposit with `Precision::BestEffort` but unconditionally returns `Ok(amount)` (the *requested* amount), rather than the amount actually moved. This is the same broken invariant flagged in the external report: a transfer helper must report the true before/after balance delta, not the amount that was asked for. Any pallet logic that trusts this return value for accounting (mint/burn reconciliation, reward bookkeeping, "amount transferred" events) can be silently desynchronized from real token movement.

### Finding Description
`fungible::Mutate::transfer` is implemented as: [1](#0-0) 

```rust
fn transfer(
    source: &AccountId,
    dest: &AccountId,
    amount: Self::Balance,
    preservation: Preservation,
) -> Result<Self::Balance, DispatchError> {
    let _extra = Self::can_withdraw(source, amount).into_result(preservation != Expendable)?;
    Self::can_deposit(dest, amount, Extant).into_result()?;
    if source == dest {
        return Ok(amount);
    }

    Self::decrease_balance(source, amount, BestEffort, preservation, Polite)?;
    // This should never fail as we checked `can_deposit` earlier. But we do a best-effort
    // anyway.
    let _ = Self::increase_balance(dest, amount, BestEffort);
    Self::done_transfer(source, dest, amount);
    Ok(amount)
}
```

Note `decrease_balance` is invoked with `Precision::BestEffort`, meaning the actual amount withdrawn from `source` can be **less** than `amount` (e.g., it is capped by `reducible_balance`, dust handling, or account-preservation rules), and the result of `decrease_balance` (the actual amount decreased) is discarded — the code does not compare it to `amount`, does not propagate it, and still calls `increase_balance(dest, amount, BestEffort)` with the *original* requested amount rather than the actual decreased amount. Finally, the function returns `Ok(amount)` unconditionally instead of returning the real transferred quantity, exactly mirroring the reported anti-pattern of trusting the requested value instead of verifying before/after balances.

The identical pattern exists in `fungibles::Mutate::transfer`: [2](#0-1) 

```rust
fn transfer(
    asset: Self::AssetId,
    source: &AccountId,
    dest: &AccountId,
    amount: Self::Balance,
    preservation: Preservation,
) -> Result<Self::Balance, DispatchError> {
    let _extra = Self::can_withdraw(asset.clone(), source, amount)
        .into_result(preservation != Expendable)?;
    Self::can_deposit(asset.clone(), dest, amount, Extant).into_result()?;
    if source == dest {
        return Ok(amount);
    }

    Self::decrease_balance(asset.clone(), source, amount, BestEffort, preservation, Polite)?;
    // This should never fail as we checked `can_deposit` earlier. But we do a best-effort
    // anyway.
    let _ = Self::increase_balance(asset.clone(), dest, amount, BestEffort);
    Self::done_transfer(asset, source, dest, amount);
    Ok(amount)
}
```

Existing guards do not stop this: `can_withdraw`/`can_deposit` checks are pre-flight sanity checks against known state, but they don't guarantee that the subsequent `BestEffort`-precision mutation moves exactly `amount` — e.g. dust below ED can be swept, or `decrease_balance` can silently satisfy less than requested under `BestEffort`. The function never re-derives the truth from the actual before/after account balances (the fix pattern recommended in the external report), it simply echoes back the caller-supplied `amount`.

### Impact Explanation
Pallets across the runtime call `T::Currency::transfer(...)` (or the `fungibles` equivalent) and rely on the `?`-propagated success as proof that the full `amount` moved (e.g. `nomination-pools::do_reward_payout`, `staking-async::make_payout_from_provider`, `ah-ops` account migration, `asset-conversion-ops` pool migration which explicitly checks `balance2 == T::Assets::transfer(...)`). Because `transfer()` returns the nominal `amount` rather than the true delta, any caller that skips an explicit equality check (most callers do, since they only use `?`) can record/emit an amount that does not match what actually left/entered the accounts. In scenarios where `BestEffort` truncates the movement (dust, preservation edge-cases), this creates a mismatch between recorded balances/events and real token custody — a value-conservation violation matching the required-impact class ("theft or unbacked mint or unlock", "duplicate settlement or payout", value not conserved/settled exactly once).

### Likelihood Explanation
Low-to-moderate: triggering an actual discrepancy generally requires edge conditions where `BestEffort` decrease/increase truncates the amount (e.g., destination near account limits, dust thresholds, or an account close to being reaped). It does not require a malicious peer/validator/admin — any normal user-triggered transfer through a pallet call path that uses this helper without independently verifying pre/post balances can hit it. The explicit "PartialTransfer" guard in `asset-conversion-ops` (comparing declared balance to the return value) shows the code authors are aware transfer's return value can misrepresent the true amount, but other reward/payout paths in the repository do not perform this check.

### Recommendation
Change the default `Mutate::transfer` implementations in `fungible::regular.rs` and `fungibles::regular.rs` to capture and return the actual amount reported by `decrease_balance`/`increase_balance` (the minimum of the two, or the actual measured delta), rather than echoing back the caller-supplied `amount`. Audit callers (staking payouts, nomination-pools reward payout, ah-ops migration, snowbridge reward payment) to ensure they use the returned actual-transferred value for events/accounting instead of assuming it equals the requested amount.

### Proof of Concept
Conceptually:
1. Call `Balances::transfer(&source, &dest, amount, Preservation::Expendable)` in a scenario where `dest`'s `increase_balance` or `source`'s `decrease_balance` under `BestEffort` precision is capped below `amount` (e.g., destination integer overflow guard, or source has slightly less reducible balance than `amount` due to a hold/freeze not fully accounted in `can_withdraw`).
2. `decrease_balance`/`increase_balance` return an actual value smaller than `amount`, but `transfer()` discards it and returns `Ok(amount)`.
3. A caller such as `do_reward_payout` in `substrate/frame/nomination-pools/src/lib.rs` (lines 3556-3563) uses `T::Currency::transfer(...)? ` and then emits `Event::PaidOut { payout: pending_rewards }` using the pre-computed `pending_rewards` rather than the function's return value — so the emitted/recorded payout can diverge from the real balance change if a `BestEffort` truncation occurred, and downstream reward-pool bookkeeping (`register_claimed_reward`) is updated using the nominal, not actual, amount.
