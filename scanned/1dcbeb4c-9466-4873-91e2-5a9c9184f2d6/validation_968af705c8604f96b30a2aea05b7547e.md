### Title
`Perbill::from_rational` divide-by-zero returns 100% instead of zero, causing duplicate/over-payout of nominator rewards in `payout_from_provider` / `payout_legacy_mint` - (File: `substrate/frame/staking-async/src/pallet/impls.rs`)

### Summary
The external report's core invariant is: a ratio/share calculation with a zero total denominator must return zero, not a non-zero value. The exact same broken invariant exists in `substrate/primitives/arithmetic/src/per_things.rs`, where the infallible `PerThing::from_rational(p, q)` wrapper resolves a `q == 0` division by falling back to `Self::one()` (100%) rather than `Self::zero()`: [1](#0-0) 

This is confirmed by the library's own test fixture, which explicitly asserts `from_rational(1, 0) == one()`: [2](#0-1) 

This `from_rational` primitive is used unguarded to split nominator rewards in `pallet-staking-async`'s payout path.

### Finding Description
In `payout_from_provider` (transfer-based payout) and `payout_legacy_mint` (mint-based payout), the nominator share of the page reward is computed as: [3](#0-2) [4](#0-3) 

`total_nominator_stake` is computed as `exposure.total().saturating_sub(overview_own)`, where `exposure` comes from `Eras::<T>::get_paged_exposure(era, &stash, page)` (per-page snapshot) while `overview_own` comes from a *separate* storage read, `ErasStakersOverview::<T>::get(era, &stash)`: [5](#0-4) 

If these two independently-stored values become inconsistent for any reason (stale/partial page write, re-election overwrite ordering, or any storage-consistency edge case not covered by an explicit guard), such that `overview_own >= exposure.total()`, `saturating_sub` silently clamps `total_nominator_stake` to `0` instead of surfacing an error. Unlike the sibling function `calculate_validator_incentive_for_page` in the same file, which explicitly checks `sum_weighted_points.is_zero()` / `total_weight.is_zero()` before calling `Perbill::from_rational` and aborts with an `Unexpected` event, no such guard exists here: [6](#0-5) 

Once `total_nominator_stake == 0`, every nonzero `nominator.value` in the loop makes `Perbill::from_rational(nominator.value, 0)` evaluate to `Perbill::one()` (100%), not `Perbill::zero()`. Consequently `nominator_exposure_part.mul_floor(total_nominator_payout)` yields the **entire** `total_nominator_payout` for **every** nominator in the exposure page, instead of each nominator's proportional share.

### Impact Explanation
- In `payout_from_provider`, each nominator is paid the full `total_nominator_payout` from the era reward pot via `make_payout_from_provider`, i.e. the pot pays out `N×` the intended amount for `N` nominators on the page — fund drain / duplicate settlement from the reward pot.
- In `payout_legacy_mint`, the same over-allocation is realized via `make_payout_legacy`, which mints a `PositiveImbalanceOf<T>` per nominator. Because this path *mints* rather than transfers from a fixed pot, the result is unbacked token inflation: `N×` the intended issuance for a single validator's page, growing total supply without a corresponding backing. This directly matches the "theft or unbacked mint" / "duplicate settlement or payout" impact categories.
- The bug requires no relayer, admin, or governance action — it is triggered purely by calling the public extrinsic that invokes this payout path once the storage-inconsistency precondition (`overview_own >= exposure.total()`) exists.

### Likelihood Explanation
The precondition (`overview_own >= exposure.total()` for the specific page being paid) depends on `ErasStakersOverview` and the per-page `PagedExposure` diverging. These are written at different points in the election/snapshot pipeline (`session_rotation.rs`, exposure-paging logic), so this is a genuine internal-consistency risk rather than a hypothetical constructed by an external malicious actor — it is analogous to the exact class of defensive checks the authors already added for `ErasSumWeightedPoints`/`ErasSumValidatorIncentiveWeight` in the same module, indicating the underlying `Perbill::from_rational`-zero-denominator hazard is a recognized but incompletely mitigated pattern in this file. I could not fully trace every code path that writes `ErasStakersOverview::own` versus the per-page exposure to prove a concrete divergence scenario within the scope of this review, so likelihood should be assessed as "possible under storage-consistency edge cases," not proven-reachable from a fully worked-out sequence of ordinary user actions.

### Recommendation
Before computing `total_nominator_stake` (and similarly before any other `Perbill::from_rational(_, denominator)` call whose denominator is derived from `exposure`/`overview` state), explicitly check `is_zero()` on the denominator and short-circuit to a zero/no-op payout with a defensive event, mirroring the pattern already used in `calculate_validator_incentive_for_page`:
```rust
let total_nominator_stake = exposure.total().saturating_sub(overview_own);
if total_nominator_stake.is_zero() {
    // no or inconsistent nominator stake: pay nothing rather than 100% per nominator
    return 0;
}
```
More generally, consider hardening `PerThing::from_rational` call sites throughout `pallet-staking`/`pallet-staking-async` reward code with `checked_from_rational` (which returns `None`/`Err` on `q == 0`) instead of the infallible `from_rational`, so a zero-denominator condition cannot silently manifest as a 100% share.

### Proof of Concept
1. Contrive (or await) a state where, for era `E`, validator stash `S`, page `P`: `ErasStakersOverview::<T>::get(E, &S).own == X` and `Eras::<T>::get_paged_exposure(E, &S, P).total() == X` (i.e., `overview_own == exposure.total()`), while the page's `exposure.others()` still lists `k > 0` nominators each with `nominator.value > 0` (summing into the page's `others_total`, which is bounded by `exposure.total()` in normal bookkeeping but can be stale/mismatched relative to `overview_own` if the overview was updated independently).
2. Call the public extrinsic that invokes `payout_stakers_alive_staked`/`payout_stakers` for `(E, S, P)`.
3. Inside, `total_nominator_stake = exposure.total().saturating_sub(overview_own) = 0`.
4. For each nominator, `Perbill::from_rational(nominator.value, 0)` evaluates to `Perbill::one()` per [1](#0-0) , so `nominator_reward = total_nominator_payout` for every one of the `k` nominators.
5. Each nominator receives the full `total_nominator_payout` — via transfer from the reward pot (`payout_from_provider`) or via fresh minting (`payout_legacy_mint`) — instead of `total_nominator_payout / k`, resulting in `k×` over-payment/inflation for that single page.

Note: I was not able to fully enumerate, within this review's scope, the exact sequence of ordinary storage writes that produces `overview_own >= exposure.total()` for a live page (this would require deeper tracing of `session_rotation.rs` and the exposure-paging/election snapshot code). The vulnerability class (from_rational-zero-denominator → 100% instead of 0%) is proven at the primitive level and is exploited unguarded at this specific call site; the storage-divergence precondition is plausible but not exhaustively proven reachable here.
