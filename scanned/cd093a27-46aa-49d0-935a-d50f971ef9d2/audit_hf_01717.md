# [M] M-6 UUPSUpgradeable was not removed from KintoWallet.

## Summary
Severity: Medium
Contest weight: 0.0376
Dataset id: 9358
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability stems from an inappropriate inheritance of the UUPSUpgradeable contract in KintoWallet, which is deployed behind a BeaconProxy created by KintoWalletFactory. In the BeaconProxy pattern the implementation address is stored in a beacon contract and accessed through a dedicated beacon slot, while the UUPSUpgradeable pattern expects an IMPLEMENTATION_SLOT in the proxy’s storage to locate the current implementation. Because the beacon proxy does not define the IMPLEMENTATION_SLOT, the upgradeTo and upgradeToAndCall functions that UUPSUpgradeable provides are effectively non‑functional. This mismatch means that any attempt to upgrade the wallet using the UUPS interface will either revert or silently do nothing, leaving the contract’s logic unchanged. The root cause is the mixing of two distinct upgrade mechanisms: the contract was written as if it were a UUPS proxy but is actually a beacon proxy, so the storage layout and upgrade entry points do not align. Exploitation is indirect: a developer or governance process that assumes the wallet can be upgraded via the UUPS functions may try to invoke upgradeTo, expecting a new implementation to be installed. The call will fail, preventing the intended upgrade and potentially freezing the wallet’s logic, which can be critical if a bug or security patch needs to be applied. From a user’s perspective the wallet may appear to accept an upgrade transaction (e.g., a UI shows a successful transaction receipt) but the underlying contract code remains the same, leading to confusion such as “my wallet was upgraded but nothing changed” or “my funds are stuck because the contract cannot be patched”. The impact is primarily functional: the protocol loses the ability to evolve the wallet logic through the intended upgrade path, which can affect all wallet holders and any downstream applications that rely on upgradability. The issue is discovered during a manual audit that compared the proxy type (BeaconProxy) with the inherited upgrade logic (UUPSUpgradeable) and noticed that the IMPLEMENTATION_SLOT constant is absent in the beacon context. It can be hard to notice because the contract compiles without errors, the upgrade functions are present in the ABI, and static analysis tools may not flag the incompatibility unless the proxy pattern is explicitly examined. The recommended remediation is to remove the inheritance from UUPSUpgradeable entirely, ensuring that the wallet only relies on the beacon’s upgrade mechanism and that any upgrade functions are implemented in the beacon contract with proper access control. By aligning the contract’s inheritance hierarchy with the actual proxy pattern, the protocol restores a coherent upgrade path and eliminates the misleading, non‑functional UUPS functions that could cause operational failures or user distrust.

## Recommendation
We recommend removing inheritance from UUPSUpgradeable.
