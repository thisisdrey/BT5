[fastcallreadonly.rs vs callreadonly.rs] Attacker who knows fast-call-read is disabled (`self.auth==None`, returns 400) instead targets `/v2/contracts/call-read/...` (`callreadonly.rs`), which has NO `auth` field whatsoever and is unconditionally reachable. Preconditions: default node config (call-read-only has always been public; fast-call-read is the newer, optionally-gated, cheaper-cost variant). Call sequence: compare `RPCCallReadOnlyRequestHandler::try_parse_request` (no auth branch, straight to `parse_read_only_call_body`) against `RPCFastCallReadOnlyRequestHandler::try_parse_request` (auth-gated). Equality/fault: this is not itself a broken equality (call-read is intentionally public) but establishes the required baseline — verify `RPCFastCallReadOnlyRequestHandler` never accidentally shares the *unauthenticated* code path of `RPCCallReadOnlyRequestHandler` via its embedded `call_read_only_handler: RPCCallReadOnlyRequestHandler` field, e.g. if `try_parse_request` for fast-call-read were ever refactored to delegate directly to `self.call_read_only_handler.try_parse_request(...)` (which has no auth check) instead of performing its own gate first, unauthenticated callers would reach the free-cost-tracker (`LimitedCostTracker::new_free()`) execution path meant to be gated. Impact: Critical if such delegation ever bypasses the local auth block. Proof idea: Rust test asserting `RPCFastCallReadOnlyRequestHandler::try_parse_request`'s auth check executes strictly before any call into `parse_read_only_call_body`/`self.call_read_only_handler` fields are populated, by supplying a body that would panic/error if parsed and confirming a 401 (not a parse error) is returned when auth is missing.
