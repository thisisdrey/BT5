Target: SignedTip191Payload vs SignedErc191Payload structural identity (both `{payload: String, signature: Secp256k1RecoverableSignature}` in contracts/defuse/core/src/payload/{tip191.rs,erc191.rs}). Attacker action: take a victim's legitimately signed MultiPayload::Erc191{payload, signature} (Erc191::prehash uses Ethereum's "\x19Ethereum Signed Message:\n" + len prefix) and resubmit the identical JSON object but with "standard":"tip191" instead of "standard":"erc191" (TIP-191 uses Tron's "\x19TRON Signed Message:\n" + len prefix per defuse_tip191::Tip191). Preconditions: victim.near has registered a secp256k1 public key matching their signature; a real MultiPayload::Erc191 signed intent for victim.near exists. Call sequence: serde untagged dispatch on "standard" field routes to SignedTip191Payload::verify -> Tip191::recover with the TRON prefix scheme instead of ETH prefix; since the prefixes and thus the prehash digests differ, Tip191::recover should recover a DIFFERENT (or no) public key than the one Erc191::recover would, so has_public_key should fail for victim.near's registered key. Binding: public_key recovered under the substituted 'tip191' tag == public_key recovered under the original 'erc191' tag must be FALSE (i.e., prefix-domain separation must hold) for the substitution attack to fail; test asserts this inequality and that execute_signed_intent errors. Impact: Critical - if domain separation between TIP-191 and ERC-191 prefixes ever collapses (e.g. same prehash for some payload lengths), the same signature would authorize under either tag, letting a signature meant for one chain settle intents it wasn't scoped for. Proof idea: cargo test constructing one payload string, signing it once with a secp256k1 key, tagging it both erc191 and tip191, and asserting SignedTip191Payload::verify and SignedErc191Payload::verify never both succeed with the SAME recovered public key for the SAME signature bytes over realistic payload lengths.
