## Analysis

The Panoptic bug's core broken invariant is: **the protocol credits an accounting value (ERC1155 fee-bearing liquidity position) based on the completion of an external call into attacker-controlled code, without independently verifying that the corresponding real state change actually occurred** (the ERC1155 mint happens, then an attacker-controlled `tokensToSend` hook fires *before* `feesBase` is finalized, so the accounting is inconsistent with reality).

The local analog is in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`, the `ERC20Transactor` used by asset-hub's XCM executor to treat arbitrary `pallet_revive` contracts as XCM-fungible assets. It has the same fundamental flaw: XCM holding-register credit is minted purely from an external contract's self-reported ABI return value, with no independent verification of an actual balance change, and the "asset" address is **not registry-gated** — it's derived from any raw `AccountKey20` location. [1](#0-0) 

`IsLocalAccountKey20` matches *any* local `(0, [AccountKey20{..}])` location, so `ERC20Matcher` accepts any 20-byte address as an "asset id" with no allow-list check — any contract a user deploys via `pallet_revive` qualifies. [2](#0-1) 

`withdraw_asset_with_surplus` calls the asset contract's `transfer(checking_account, amount)` via `pallet_revive::Pallet::<T>::bare_call`, and if the call doesn't revert and ABI-decodes to `true`, it unconditionally mints `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — a bookkeeping credit whose value is `amount`, taken directly from the untrusted XCM message, not from any measured balance delta. [3](#0-2) 

`Erc20Credit` is a bare `UnsafeManualAccounting`/`ImbalanceAccounting` wrapper with no runtime-enforced balance check — the docstring explicitly says balance constraints are "enforced by the ERC20 smart contract itself rather than the runtime."

Because the contract at `asset_id` is fully attacker-controlled code, the attacker can implement `transfer()` to always `return true` without moving any real value (or backed by nothing at all) — exactly the "contract returns success while the corresponding real accounting change never happened" pattern from the Panoptic report, except here it doesn't even require reentrancy; the trust boundary itself is broken. This credit is then treated by the XCM executor identically to a real, value-backed asset: [4](#0-3) 

`WithdrawAsset` calls `Config::AssetTransactor::withdraw_asset_with_surplus` and unconditionally `self.holding.subsume_assets(withdrawn)` — the resulting holding-register credit is now indistinguishable from genuinely-backed assets for all subsequent instructions in the same (or forwarded) XCM program, e.g. `ExchangeAsset` against a liquidity pool, `DepositReserveAsset`/`InitiateTeleport` to another chain, or `DepositAsset` to any beneficiary.

### Title
Unbacked "ERC20" XCM asset credit minted from untrusted contract return value in `ERC20Transactor` - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` treats any `pallet_revive` contract address supplied in an XCM `Asset` `Location` as a valid ERC20 asset (no registry/allow-list gate via `IsLocalAccountKey20`), and mints XCM holding-register credit (`Erc20Credit(amount)`) purely because a `bare_call` to that contract's `transfer()` function ABI-decodes to `true`. No real balance delta is measured or enforced by the runtime. A user who deploys a trivial malicious contract whose `transfer()` always returns `true` can inject an arbitrary, unbacked "ERC20" credit into the XCM virtual machine's holding register via a self-executed `pallet_xcm::execute` program.

### Finding Description
`ERC20Matcher = MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>` accepts any `AccountKey20` junction as a valid asset id with no whitelist. `withdraw_asset_with_surplus` then performs `bare_call` into that arbitrary contract with `IERC20::transferCall{to: checking_address, value: amount}` and, upon a non-reverting call whose return decodes to `true`, mints `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))`. The `amount` value is attacker-supplied from the XCM message; the only verification is the boolean return of a call into code the attacker fully controls. There is no check that the calling account's real token balance in that contract decreased by `amount`, nor that the checking account's balance increased by `amount`. This credit is then merged into `self.holding` by the XCM executor and becomes usable by any subsequent instruction (`ExchangeAsset`, `DepositAsset`, `DepositReserveAsset`, `InitiateTeleport`, etc.) exactly as if it were a real, balance-verified asset.

### Impact Explanation
This is a "theft or unbacked mint" primitive: an unprivileged user can, at zero real cost, create an arbitrary amount of XCM-recognized fungible-asset credit tied to a contract they fully control. If that fabricated asset is ever paired against real value (e.g. an `pallet_asset_conversion` liquidity pool, or a remote chain trusting this chain as reserve for the asset's derived location), the attacker can drain the real-value side of that pairing repeatedly, since the "mint" step costs only gas/weight and requires no genuine balance backing. This directly matches the "theft or unbacked mint or unlock" impact category.

### Likelihood Explanation
Reachable by any signed account with no privileged action: deploy a `pallet_revive` contract implementing a trivial ERC20-shaped `transfer()` that always returns `true`, then submit a `pallet_xcm::execute` extrinsic (self-origin, permissionless) containing a `WithdrawAsset` instruction referencing that contract's address as the asset `Location`. No governance, admin, relayer, or malicious-validator assumption is required — only that `ERC20Transactor` is wired into the runtime's `AssetTransactor` (confirmed present in `asset-hub-westend`'s `xcm_config.rs`) and that some real-value pairing (pool or reserve-trusting destination) for this class of asset exists to convert the fabricated credit into real value.

### Recommendation
Do not trust the contract's boolean return value as proof of value movement. Before/after the `bare_call`, read the actual token balance of `who`/the checking account via `balanceOf` (or better, require the ERC20 contract itself be registry-gated / allow-listed rather than matched by raw address pattern), and mint the `AssetsInHolding` credit only for the measured balance delta, not the attacker-claimed `amount`. Alternatively, restrict `ERC20Matcher`/`IsLocalAccountKey20` to a governance-curated set of vetted contract addresses instead of "any `AccountKey20` location."

### Proof of Concept
1. Deploy a `pallet_revive` contract `FakeERC20` whose `transfer(address,uint256)` always returns `true` and performs no storage-backed balance accounting (or fakes an unlimited balance).
2. Submit `pallet_xcm::execute` (self-signed) with an XCM program: `WithdrawAsset(Asset { id: AssetId(Location::new(0, [AccountKey20{ key: FakeERC20_address, network: None }])), fun: Fungible(huge_amount) })`.
3. `ERC20Matcher` matches (no allow-list check), `ERC20Transactor::withdraw_asset_with_surplus` calls `FakeERC20.transfer(checking_account, huge_amount)`, which returns `true` with no real balance movement.
4. `Erc20Credit(huge_amount)` is minted into holding; append `ExchangeAsset` (or `DepositReserveAsset` to a chain trusting this asset's reserve) to convert the fabricated credit into real backed value from a pool/bridge counter-party.

pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),

struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}

impl UnsafeManualAccounting<u128> for Erc20Credit {
	fn saturating_subsume(&mut self, mut other: Box<dyn ImbalanceAccounting<u128>>) {
		let amount = other.forget_imbalance();
		self.0 = self.0.saturating_add(amount);
	}
}

impl ImbalanceAccounting<u128> for Erc20Credit {
	fn amount(&self) -> u128 {
		self.0
	}
	fn saturating_take(&mut self, amount: u128) -> Box<dyn ImbalanceAccounting<u128>> {
		let new = self.0.min(amount);
		self.0 = self.0 - new;
		Box::new(Erc20Credit(new))
	}
}

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}
