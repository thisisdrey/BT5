## Finding

The RocketPool bug is: a permissioned "kick/evict" action requires a fund transfer back to the party being evicted, and if that transfer fails (insufficient treasury balance), the entire kick reverts — leaving a party that "deserved" removal still in place. `pallet-nomination-pools` has a structurally identical pattern in the permissionless/administrative **kick** flow (`unbond` + `withdraw_unbonded` while the pool is `Blocked`), where the very last step of the extrinsic must succeed a currency transfer from the pool's bonded account back to the member, or the whole kick aborts.

### Title
Nomination-pools member kick can be permanently blocked by a failing `member_withdraw` transfer in `TransferStake` - (File: `substrate/frame/nomination-pools/src/lib.rs`, `substrate/frame/nomination-pools/src/adapter.rs`)

### Summary
When a pool is `Blocked`, the pool's `root`/`bouncer` can forcibly evict ("kick") a misbehaving member by calling `unbond` and then `withdraw_unbonded` on their behalf [1](#0-0) . The final, mandatory step of `withdraw_unbonded` is `T::StakeAdapter::member_withdraw(...)?`, which for the `TransferStake` adapter resolves to a fallible `T::Currency::transfer(&pool_account.0, &who.0, amount, Preservation::Expendable)?` from the pool's bonded account to the member [2](#0-1) . If that transfer errors (e.g. the pool account's actual free balance is lower than the `balance_to_unbond` computed from sub-pool bookkeeping), the whole extrinsic errors out and the member is never removed — exactly the RocketDAO pattern where a bond-refund failure blocks the eviction.

### Finding Description
`Call::withdraw_unbonded` computes `balance_to_unbond` from the sub-pools' internal accounting and only clamps it against `StakeAdapter::transferable_balance`, not against the pool account's live spendable balance at dispatch time [3](#0-2) . The code's own comment acknowledges the sub-pool accounting can drift from the pool account's real balance ("a bug in the slashing hook") [4](#0-3) .

It then unconditionally propagates the result of `member_withdraw`: [5](#0-4) 

For pools still on the (deprecated but still supported) `TransferStake` strategy, `member_withdraw` is a plain balance transfer that can fail with `InsufficientBalance`/`ExistentialDeposit`-related errors whenever the pool's bonded account doesn't actually hold `amount` in free, expendable balance [2](#0-1) . Because Substrate extrinsics are atomic, any `?` failure here rolls back the entire `withdraw_unbonded` call — the member is not removed from `PoolMembers`, `dec_members()` never runs, and the kick has no effect, just like the RocketDAO `actionKick` reverting because the vault lacked RPL.

This mirrors the reported bug's core broken invariant: **a forced-eviction path's success is coupled to an unrelated, attacker-influenceable fund-availability condition**, so there is no guarantee that a legitimately "blocked/should-be-kicked" member can actually be removed.

### Impact Explanation
If a pool's bonded account balance and the sub-pool/points bookkeeping diverge (via slashing edge cases, rounding in `dissolve`/`issue` on `UnbondPool`, or ED-related dust behavior), `root`/`bouncer` lose the ability to evict the member using the documented `Blocked`-state kick mechanism. The misbehaving/malicious member remains a pool member indefinitely, continuing to hold points and (until it is fully unbonded) potentially remain nominatable, defeating the pool's governance/anti-abuse mechanism (`PoolState::Blocked` kicking), which is the entire purpose of that pallet feature.

### Likelihood Explanation
This requires no privileged/malicious actor beyond the ordinary permissions already granted to `root`/`bouncer` performing routine kicks; the trigger condition is a legitimate discrepancy between `transferable_balance`-based accounting and the pool account's actual spendable balance (e.g. slashing sequencing, ED constraints, or the documented "bug in the slashing hook" case already called out in code comments). Because `TransferStake` is a supported (if deprecated) production strategy with existing unmigrated pools, this is a realistic, non-adversarial failure mode rather than a purely theoretical one.

### Recommendation
Decouple member removal from the success of the fund transfer, analogous to the RocketPool fix: clamp `member_withdraw`'s transferred amount to the pool account's actual reducible balance at dispatch time (not just `transferable_balance` from the adapter), and/or make the final leg of `withdraw_unbonded` best-effort (log/skip the transfer, e.g. via `defensive!`/saturating behavior) while still unconditionally removing the member's points/`PoolMembers` entry when the removal itself is otherwise valid — so a kick can never be blocked purely by a balance-transfer failure.

### Proof of Concept
1. Create a pool using `TransferStake`; add member `M` with a bonded amount.
2. Introduce a balance/accounting drift between the pool account's real free balance and the sub-pool points-to-balance computation (e.g. via a slashing sequence that under-updates `UnbondPool.balance` relative to `points`, as referenced by the "bug in the slashing hook" comment) [4](#0-3) .
3. Set the pool state to `Blocked`; have `root`/`bouncer` call `unbond` then `withdraw_unbonded` on `M` to kick them [6](#0-5) .
4. `balance_to_unbond` (derived from sub-pool bookkeeping) exceeds the pool account's actual spendable balance; `T::Currency::transfer` inside `member_withdraw` returns an error [2](#0-1) .
5. `withdraw_unbonded` returns `Err`, `M` remains in `PoolMembers`, and the kick has no effect — reproducing the RocketDAO "cannot kick because refund fails" condition.
