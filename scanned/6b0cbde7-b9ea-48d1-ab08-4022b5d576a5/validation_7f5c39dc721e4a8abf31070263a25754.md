## Analysis

The external report's core broken invariant is: **a strict equality check between a computed/quoted amount and an independently re-computed amount, where rounding in the calculation can make the two values differ by even 1 unit, causing valid operations to revert (DoS)**.

I found a direct structural analog in the fee-payment-via-swap logic of `pallet-asset-conversion-tx-payment`, which is part of the transaction validity pipeline (a public, unprivileged entrypoint executed on every extrinsic that opts to pay fees in a non-native asset).

### Title
Strict zero-change assertion in `SwapAssetAdapter::withdraw_fee` can reject valid fee-paying transactions due to AMM rounding mismatch - (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

### Summary
`SwapAssetAdapter::withdraw_fee` first *quotes* the amount of a non-native asset needed to cover a fee via `quote_price_tokens_for_exact_tokens` (which internally calls `AssetConversion::get_amount_in`), withdraws that quoted amount, and then performs the actual swap via `S::swap_tokens_for_exact_tokens`. It then asserts the swap's leftover `change` is exactly zero, on the assumption that "since the exact price for fee has been quoted, the change should be zero." [1](#0-0) 

### Finding Description
`get_amount_in` deliberately rounds the required input **up** by adding one unit to compensate for integer division loss: [2](#0-1) 

This quoted value is computed once, at `withdraw_fee` time, against the pool's *current* reserves. The actual swap execution (`swap_tokens_for_exact_tokens`) performs its own independent amount-in calculation against the pool state at execution time. Any of the following can cause the two computed amounts to diverge by even a single unit:
- Pool reserves changing between the quote and the swap call (e.g., another transaction in the same block touching the same pool, or the same transaction's own prior operations),
- Multi-hop swap paths compounding per-hop rounding (`get_amount_in` rounds up on each hop of a multi-asset route),
- The `+1` rounding-up behavior itself not being guaranteed to produce an *exact* zero-change execution once fed back into the AMM `k = x*y` formula on the actual swap path.

When the quoted `asset_fee` differs from what the swap actually consumes, `swap_tokens_for_exact_tokens` returns a non-zero `change`, and the code unconditionally rejects the entire transaction: [3](#0-2) 

This is precisely the pattern in the external report: two independently computed "expected" and "actual" fee-related values are compared for **strict equality**, and any rounding discrepancy — rather than being tolerated or reconciled — causes the whole operation to fail.

### Impact Explanation
`withdraw_fee` runs as part of the `SignedExtension`/transaction-validity pipeline for every extrinsic configured to pay fees in a non-native asset via this adapter. If the equality assumption is violated (even by 1 unit) for a given asset/pool state, the transaction is rejected with `InvalidTransaction::Payment` even though the sender supplied sufficient funds and the fee logic is otherwise correct. Because this is a **public, unprivileged, and permissionless path** (any signed extrinsic using this fee-payment option triggers it), an attacker (or even ordinary usage under contended pool conditions) can cause systematic transaction rejection for a specific asset, effectively denying block inclusion for all users attempting to pay fees with that asset — a chain-level degradation of transaction processing for legitimate users, consistent with "public underpriced work that degrades block production."

### Likelihood Explanation
Likelihood is contingent on pool volatility/contention and multi-hop routing being exercised: the code's own comment ("the change should be zero") signals the authors already recognized this as an assumption rather than an invariant guaranteed by the pool math across state transitions. Any concurrent activity on the same swap pool, or any route requiring more than one hop, is a realistic trigger, not a contrived edge case.

### Recommendation
- Do not require `change` to be exactly zero; instead, credit any leftover `change` back to the payer (or merge it into `fee_credit`) rather than erroring out.
- Alternatively, quote and swap atomically against the same pool state (e.g., don't withdraw based on a pre-computed quote and then swap separately) to eliminate the window for reserve drift.
- Add tolerance/reconciliation logic analogous to what the external report recommended: treat "quoted ≈ actual" scenarios as success, and only fail hard if the shortfall is structurally impossible to cover.

### Proof of Concept
1. Configure a runtime with `pallet_asset_conversion_tx_payment` using `SwapAssetAdapter` for fee asset `X` against native asset `A`, backed by a pool with limited reserves.
2. Have a background/other transaction alter the `X`/`A` pool reserves between block construction quoting time and the extrinsic's actual dispatch/fee-withdrawal execution (or use a multi-hop asset path `X -> B -> A`).
3. Submit a normal transaction paying fees in asset `X` with balance sufficient for the originally quoted amount.
4. Observe that `swap_tokens_for_exact_tokens` returns non-zero `change` due to the reserve/hop rounding drift, `ensure!(change.peek().is_zero(), ...)` fails, and the otherwise-valid transaction is rejected with `InvalidTransaction::Payment`.
