## Analysis

I found a solid local analog to the SteadeFi bug pattern. The core broken invariant in the original report is: **an operation's outcome (success/failure) is not checked before finalizing payout/accounting, causing costs/rewards to be settled as if the operation succeeded even when it failed.**

The matching Polkadot SDK case is in the Snowbridge V2 outbound queue's delivery-receipt settlement flow.

### Relevant code

`DeliveryReceipt` decodes a `success: bool` field straight from the `InboundMessageDispatched` Solidity event: [1](#0-0) 

But `process_delivery_receipt`, which is reachable via the permissionless, unprivileged extrinsic `submit_delivery_receipt`, never reads or checks `receipt.success` before paying the reward and clearing the order: [2](#0-1) [3](#0-2) 

### Title
Relayer reward is paid and `PendingOrder` settled unconditionally regardless of the on-chain `InboundMessageDispatched.success` flag - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
`submit_delivery_receipt` verifies only that an `InboundMessageDispatched` event log exists for a given nonce with a valid Merkle/beacon proof. The decoded `DeliveryReceipt::success` field — which tells whether the Gateway contract call on Ethereum actually executed successfully or reverted — is completely ignored in `process_delivery_receipt`. The relayer reward is paid and the `PendingOrder` is removed unconditionally, exactly as in the successful-withdrawal accounting path in the SteadeFi bug: **the outcome-failure branch is never distinguished from success**, so the fee/reward accounting proceeds as if the underlying action always succeeded.

### Finding Description
The pipeline is: outbound message → `PendingOrder{nonce, fee, block_number}` stored → relayer executes it on Ethereum → relayer submits a Merkle-proved event log back via `submit_delivery_receipt` → `process_delivery_receipt` pays `order.fee` to the reward account and removes the order. [4](#0-3) 

The function checks `T::GatewayAddress::get() == receipt.gateway` and that a `PendingOrder` exists for `receipt.nonce`, but never checks `receipt.success`. The `InboundMessageDispatched` event on Ethereum is emitted with `success = false` when the dispatched command (e.g. token unlock/mint, `Transact`, `Upgrade`) reverts on execution — this is a legitimate, verifiable outcome, not something a relayer can forge (the event still comes through the light-client proof). But because the pallet never inspects this flag, a message whose remote execution failed is settled identically to one that succeeded: the relayer collects the full fee and the order is closed out, with no retry, refund, or distinguishing event.

This mirrors the SteadeFi flaw precisely: an operation that in fact failed (withdrawal rejected / Ethereum call reverted) is treated by the settlement logic as if it succeeded, and the party who bore the cost (the pool/stakers there; the fee-paying sender/AssetHub sovereign account here) absorbs the loss with no compensating accounting adjustment.

### Impact Explanation
Any user whose cross-chain command reverts on Ethereum (e.g., an ERC-20/PNA unlock failing due to insufficient allowance, an upgrade/transact command reverting, or any other Gateway-side revert) still has their attached fee fully paid out to the relayer, and the `PendingOrder` is permanently closed. There is no automatic retry or fee refund path keyed off `success == false`. This is a public, permissionless-relayer-triggerable path (`submit_delivery_receipt` is callable by any signed account) that causes systematic fund loss/misallocated payout for message senders whenever legitimate Ethereum-side reverts occur — falling under "duplicate settlement or payout" / underpriced-work-with-fund-loss in the impact gate, without requiring a malicious relayer, validator, or governance actor.

### Likelihood Explanation
High. Reverts on the Ethereum Gateway side are an expected, non-adversarial occurrence (e.g., transient gas issues on a nested `Transact`, insufficient balance for an unlock, contract-level checks failing). Every such revert silently triggers this path since `submit_delivery_receipt` is the only way to resolve a `PendingOrder`, and any relayer (honest or not) will submit the proof to collect their fee regardless of the command's success.

### Recommendation
Branch on `receipt.success` in `process_delivery_receipt`: on failure, do not pay the reward from the sender's already-attached fee as if the command succeeded — either refund the fee to the original sender/hold it for a resubmission mechanism, or route it to a distinct "failed-delivery" accounting path, and emit a distinguishable event (e.g. `MessageDeliveryFailed`) instead of unconditionally emitting `MessageDelivered`.

### Proof of Concept
1. A message with `fee = F` is queued and committed on BridgeHub, creating `PendingOrders[nonce] = PendingOrder{nonce, fee: F, ..}` (see `do_process_message`, `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:426-436`).
2. The relayer submits the message to the Ethereum Gateway; the dispatched command reverts (e.g. an ERC-20 unlock target rejects the transfer), so the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. The relayer calls `submit_delivery_receipt` with a valid proof of this event. `T::Verifier::verify` succeeds (the log is real and proved); `DeliveryReceipt::try_from` decodes `success: false` correctly.
4. `process_delivery_receipt` runs: it never inspects `receipt.success`; it pays `order.fee` (`F`) to `reward_account` via `T::RewardPayment::register_reward`, removes the `PendingOrder`, and emits `Event::MessageDelivered { nonce }` — identical to the success case.
5. Result: the sender's fee `F` is fully spent even though their cross-chain command never executed on Ethereum, and there is no state left to retry or refund it. This can be repeated for every reverted command going through the bridge, systematically draining fees paid for failed deliveries. This exactly parallels the SteadeFi finding where a failed withdrawal still incurred cost with no corresponding accounting correction.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
