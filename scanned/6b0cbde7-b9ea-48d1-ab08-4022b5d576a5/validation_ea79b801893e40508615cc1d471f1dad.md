## Confirmed local analog: `hop_submit` signature does not bind `recipients` — attacker can hijack the recipient list

### Title
`hop_submit` signature omits `recipients` from the signed payload, allowing an attacker who observes a valid submission to hijack data delivery to attacker-chosen recipients - (File: `substrate/client/hop/src/rpc.rs`, `substrate/client/hop/src/types.rs`)

### Summary
The HOP off-chain data-relay service exposes `hop_submit(data, recipients, signature, signer, submit_timestamp)` via RPC [1](#0-0) . The signature is verified against `submit_signing_payload`, which is derived only from `blake2_256(HOP_SUBMIT_CONTEXT || blake2_256(data) || submit_timestamp)` [2](#0-1) . The `recipients` parameter — a separate argument of the RPC call that is SCALE-decoded and stored directly into the pool entry — is never included in the signed digest [3](#0-2) , [4](#0-3) .

This is structurally identical to the Crestal Network bug: a signature authorizes an action ("I consent to submit this data blob at this timestamp") but leaves a security-critical parameter (`recipients`, analogous to `privateWorkerAddress`/`tokenId`) unsigned, so anyone who observes the `(data, signature, signer, submit_timestamp)` tuple can resubmit it with a different `recipients` list.

### Finding Description
`HopRpcServer::submit` performs, in order: decode recipients from the raw request → authorization/quota check on the signer account → verify `multi_sig` against `submit_signing_payload(blake2_256(data), submit_timestamp)` → insert `(data, recipient_keys, sender_id, signer, multi_sig, submit_timestamp)` into the pool [4](#0-3) .

Nothing in the verified digest constrains which public keys are allowed to later `claim`/`ack` the blob. The `recipients` field carried in `HopEntryMeta` is populated straight from the RPC caller's input [5](#0-4) , and is later used by promotion logic to bind consent to on-chain settlement, and by `find_recipient`/claim logic to authorize which ephemeral key may pull the data. Because the signature the sender produced client-side (over just `data` + `submit_timestamp`) is valid for *any* `recipients` value, an attacker who is able to see or intercept a legitimate `(data, signature, signer, submit_timestamp)` tuple (e.g., it transits through a relay endpoint, gets logged, or is submitted to multiple RPC front-ends before inclusion) can replay it to their own `hop_submit` call with a `recipients` list that adds/replaces keys under the attacker's control — the signature check still passes because `recipients` never entered the hash.

This directly parallels the audited Crestal bug: signing "the deployment/token" but not the "who receives it" parameter, so grabbing the signature and pairing it with a malicious recipient list is sufficient to redirect the payload.

### Impact Explanation
Since the data blob (`data`) transiting HOP is presumably sensitive handoff material addressed to specific recipients via their ephemeral public keys, an attacker able to reuse the signer's `(data, signature, submit_timestamp)` with an attacker-supplied `recipients` list can:
- Cause the sender's data to be delivered to (claimable by) an attacker-controlled recipient key instead of/along with the intended one, since `claim`/`ack` authorization is scoped to whatever `recipients` ended up stored for that entry, not to what the original sender intended.
- Consume the sender's/account's storage quota and pool capacity a second time with a forged recipient set (since `account_id`, `data_len`, and authorization are all re-derived from the reused signer/signature and legitimate quota checks pass), amplifying DoS against that account's promotion budget.
- Potentially interfere with the "submit implies consent to promote" semantic referenced in `HopEntryMeta` doc comments [6](#0-5) , since the same signature and timestamp can now legitimize a different recipient set being promoted on-chain.

### Likelihood Explanation
No privileged actor is required — any party who observes a valid `(data, signature, signer, submit_timestamp)` tuple (multiple RPC front-ends, network taps, or a leaky client) can resubmit it with a different `recipients` argument through the public `hop_submit` RPC endpoint [7](#0-6) . The domain separation (`HOP_SUBMIT_CONTEXT`) and timestamp binding [8](#0-7)  only prevent cross-operation/stale replay; they do nothing to prevent same-operation replay with a mutated `recipients` field, since that field is entirely excluded from the hash.

### Recommendation
Include a commitment to `recipients` in the signed digest, e.g. change `submit_signing_payload` to `blake2_256(HOP_SUBMIT_CONTEXT || blake2_256(data) || blake2_256(encode(recipients)) || submit_timestamp.to_le_bytes())`, and update both the RPC-side verification in `HopRpcServer::submit` and any runtime-side re-verification during promotion to recompute the hash over the actual `recipients` list stored/promoted, rejecting the request if it does not match what the sender signed.

### Proof of Concept
1. Legitimate sender Alice signs `submit_payload = submit_signing_payload(blake2_256(data), submit_timestamp)` and calls `hop_submit(data, [alice_recipient_pubkey], signature, alice_signer, submit_timestamp)`.
2. Attacker Mallory observes this `(data, signature, alice_signer, submit_timestamp)` tuple (e.g., via network interception, a misbehaving/duplicated RPC gateway, or log access).
3. Mallory calls `hop_submit(data, [mallory_pubkey], signature, alice_signer, submit_timestamp)` on the same or another HOP node.
4. In `HopRpcServer::submit`, `account_id` is derived from `alice_signer` (unchanged), the authorization/quota check passes for Alice's account, and `multi_sig.verify(&submit_payload, &account_id)` succeeds because `submit_payload` only depends on `data` and `submit_timestamp` — both unchanged — not on the substituted `recipients` [4](#0-3) .
5. The entry is inserted into the pool with `mallory_pubkey` as the sole recipient, so Mallory (not the intended recipient) can later `claim`/`ack` the data, while Alice's quota is charged for the duplicate submission.

/// Domain-separator prefix for `hop_submit` signatures.
pub const HOP_SUBMIT_CONTEXT: &[u8] = b"hop-submit-v1:";

/// Domain-separator prefix for `hop_claim` signatures.
pub const HOP_CLAIM_CONTEXT: &[u8] = b"hop-claim-v1:";

/// Domain-separator prefix for `hop_ack` signatures.
pub const HOP_ACK_CONTEXT: &[u8] = b"hop-ack-v1:";

/// Compute the 32-byte payload that HOP recipients / submitters sign for a given
/// operation. This is `blake2_256(context || hash)` and ensures signatures from
/// one operation cannot be replayed in another.
pub fn signing_payload(context: &[u8], hash: &HopHash) -> [u8; 32] {
	let mut buf = Vec::with_capacity(context.len() + 32);
	buf.extend_from_slice(context);
	buf.extend_from_slice(hash.as_bytes());
	blake2_256(&buf)
}

/// Compute the 32-byte payload signed at `hop_submit` time.
///
/// The runtime pallet re-derives this exact byte sequence to verify the
/// signature on-chain, so the construction must remain byte-identical to the
/// pallet's `signing_payload(data, submit_timestamp)`:
/// `blake2_256(HOP_SUBMIT_CONTEXT || blake2_256(data) || submit_timestamp.to_le_bytes())`.
pub fn submit_signing_payload(hash: &HopHash, submit_timestamp: u64) -> [u8; 32] {
	let mut buf = [0u8; HOP_SUBMIT_CONTEXT.len() + 32 + 8];
	buf[..HOP_SUBMIT_CONTEXT.len()].copy_from_slice(HOP_SUBMIT_CONTEXT);
	buf[HOP_SUBMIT_CONTEXT.len()..HOP_SUBMIT_CONTEXT.len() + 32].copy_from_slice(hash.as_bytes());
	buf[HOP_SUBMIT_CONTEXT.len() + 32..].copy_from_slice(&submit_timestamp.to_le_bytes());
	blake2_256(&buf)
}
