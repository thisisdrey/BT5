### Title
`OutboundQueue::calculate_fee` truncates the remote fee to zero via integer division in `convert_from_ether_decimals`, allowing underpriced Snowbridge message delivery - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
`Pallet::calculate_fee` converts the wei-denominated remote fee into the local chain's balance units using `convert_from_ether_decimals`, which performs an integer division by `10^(18-Decimals)` (`10^8` for a 10-decimal chain like DOT). For any message whose remote fee is smaller than this denominator, the division truncates the fee to `0`, even though `fee_per_gas`, `reward`, and `exchange_rate`/`multiplier` are all non-zero, valid pricing parameters. This is analogous to the `get_cost_amount` bug: a public, unprivileged action (submitting an XCM message that Snowbridge exports to Ethereum) can be executed with a computed price of zero due to a rounding/logic flaw in the pricing function, rather than by any admin misconfiguration.

### Finding Description
`calculate_fee` computes the remote fee entirely in wei-scale fixed point and only divides down to native-currency precision at the very end: [1](#0-0) 

The final division happens in `convert_from_ether_decimals`: [2](#0-1) 

`decimals = ETHER_DECIMALS - T::Decimals::get()`, and for a chain with `Decimals = 10` (as enforced by the `integrity_test` allowing only 10 or 12) this is `18 - 10 = 8`, so `denom = 10^8`. Any wei-value remote fee below `10^8` is floor-divided to `0`. The pallet's own test explicitly reproduces and documents this as invalid behavior: [3](#0-2) 

That test uses `fee_per_gas = 1`, `reward = 1`, `exchange_rate = 1/1`, `multiplier = 1/1` — all technically "valid" (non-zero) pricing parameters — and still gets `fee.remote == 0`. The remote fee (in wei) is `fee_per_gas * gas_used + reward = 250000 + 1 = 250001`, which is far below the `10^8` truncation threshold, so it becomes `0` after `convert_from_ether_decimals`.

Crucially, none of the inputs that trigger this are attacker-privileged: `PricingParameters` are governance-set once and can be entirely reasonable (a low but non-zero `fee_per_gas` is a normal operational choice, not "admin abuse"); the actual trigger is the `gas_used_at_most` value returned by `T::GasMeter` for a given `Command`, which is determined by the *message content* an ordinary unprivileged user (via XCM `SendMessage::validate`) or `snowbridge-pallet-system` supplies: [4](#0-3) 

The computed `fee` from `validate` is what gets charged to the sender before `deliver` enqueues the message for processing and eventual relay to Ethereum. If the resulting `fee.remote` is `0` for low-gas commands under normal pricing parameters, users can submit real bridge messages that get processed and committed via `do_process_message`/`commit` (consuming block weight, `MessageLeaves` storage, and eventually relayer gas) while paying zero remote fee — the exact "public underpriced work" pattern from the seed report, just with pricing arithmetic instead of a length-threshold branch.

### Impact Explanation
Underpriced or zero-fee remote fee breaks the core invariant documented in the pallet's own fee model (`Fee(Message) = LocalFee + RemoteFeeAdjusted`), meaning relayers are not adequately reimbursed for the gas they front on Ethereum, and callers can spam low-gas Snowbridge messages without paying for the resource they consume. This matches "public underpriced work that degrades block production or stalls bridge processing" in the accepted-impact criteria: repeated free/underpriced message submissions inflate the outbound queue, `MessageLeaves`, and downstream relayer costs, potentially degrading BridgeHub throughput and increasing relayer's unfunded exposure on the Ethereum side.

### Likelihood Explanation
The bug does not require a malicious governance actor, leaked keys, or a compromised relayer — it is a pure arithmetic/rounding defect present under normal, low-value pricing parameters combined with any `Command` whose `GasMeter`-computed gas cost times `fee_per_gas` plus `reward` in wei stays under the `10^(18-Decimals)` threshold. The pallet's maintainers already wrote a dedicated regression test (`test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero`) acknowledging this exact scenario is "invalid" and "should be avoided," confirming the flaw is known and reachable with realistic parameter combinations, not a contrived edge case.

### Recommendation
Round the truncated remote fee up (ceiling division) instead of floor division in `convert_from_ether_decimals`, or enforce a non-zero floor/minimum remote fee whenever the computed pre-conversion wei value is non-zero, so that `fee.remote > 0` whenever `fee_per_gas > 0 || reward > 0`. Alternatively, perform the decimal scaling earlier (before combining gas cost and reward) so that sub-unit remote fees are rejected or bumped rather than silently zeroed.

### Proof of Concept
The existing test in the repository is a direct, unmodified proof of concept: [3](#0-2) 
With `gas_used = 250000`, `fee_per_gas = 1`, `reward = 1`, `exchange_rate = 1`, `multiplier = 1` (all non-zero/valid), `OutboundQueue::calculate_fee` returns `fee.remote == 0`. Any live command whose `GasMeter::maximum_gas_used_at_most` result, combined with governance-configured `fee_per_gas`/`reward`, yields a wei-scale total below `10^(18-Decimals)` will reproduce this in production via the public `SendMessage::validate` path used for ordinary XCM-triggered Snowbridge message submission.

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		// 1 KSM has 12 digits of precision
		// 1 ETH has 18 digits of precision
		pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
			let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
			let denom = 10u128.saturating_pow(decimals);
			value.checked_div(denom).expect("divisor is non-zero; qed").into()
		}

#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {
		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
			exchange_rate: FixedU128::from_rational(1, 1),
			fee_per_gas: 1_u32.into(),
			rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});
}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };
