`submit_delivery_receipt` is callable by any signed account (`ensure_signed`, no origin filtering beyond a valid Ethereum proof) [1](#0-0) , and the actual reward-payout logic in `process_delivery_receipt` never inspects `receipt.success` before crediting the reward and permanently deleting the `PendingOrder`.

### Title
`process_delivery_receipt` pays relayer reward and clears the pending order regardless of delivery outcome - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The report's core broken invariant is: a public data-submission path accepts an externally supplied value into consensus-critical state without validating that the value satisfies the semantic guarantee the rest of the system relies on (a "price" that is really zero). The same broken-invariant class exists in `snowbridge-pallet-outbound-queue-v2`: the `DeliveryReceipt` decoded from an Ethereum event log carries a `success: bool` field that is supposed to reflect whether the message actually executed on Ethereum, but `process_delivery_receipt` never checks it before paying the relayer reward and removing the `PendingOrder`.

### Finding Description
`DeliveryReceipt` is decoded from the `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)` Solidity event [2](#0-1) . The field `success` faithfully carries whether the Gateway contract's execution of the message succeeded or failed on Ethereum.

`process_delivery_receipt`, which is invoked from the public, unprivileged extrinsic `submit_delivery_receipt` after only proof verification and gateway-address matching, is:

```rust
pub fn process_delivery_receipt(...) -> DispatchResult {
    ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);
    let reward_account = if receipt.reward_address == [0u8; 32] { relayer } else { receipt.reward_address.into() };
    let nonce = receipt.nonce;
    let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;
    if order.fee > 0 {
        T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee);
    }
    <PendingOrders<T>>::remove(nonce);
    Self::deposit_event(Event::MessageDelivered { nonce });
    Ok(())
}
``` [3](#0-2) 

Nowhere in this function (nor in the calling extrinsic) is `receipt.success` checked. Any signed account can call `submit_delivery_receipt` for a nonce with a pending order, present a genuine, correctly-proven event log where `success == false` (a message that actually reverted/failed on the Gateway), and still: (1) get the `order.fee` credited to a reward account of their choosing (via `reward_address`), and (2) have the `PendingOrder` permanently removed from `PendingOrders`, closing the order forever. This is analogous to `submit_price` accepting a value without validating it satisfies the required bound before it is committed to state that other logic (median/payout) treats as authoritative — here the unvalidated field is `success`, and the downstream effect is an unconditional reward mint/settlement plus permanent removal of the order state, i.e., "public underpriced/misclassified work" being rewarded as if correctly delivered.

### Impact Explanation
- Theft/unbacked payout: A relayer (or any signed account observing a failed-delivery event on Ethereum) can claim the full fee for a message that never successfully executed, directly minting/transferring value it did not earn.
- Permanent state loss: because `PendingOrders::remove(nonce)` runs unconditionally once the order is found, the failed order can never be re-submitted, re-processed, or refunded — the pending order is settled exactly once, but to the wrong outcome (paid despite failure), which matches the "duplicate settlement or payout" / "permanent … bridge-state lock" impact class.
- No admin, governance, validator, or relayer-compromise assumption is needed: any signed account holding a legitimately generated (not forged) receipt with `success: false` can trigger this by simply calling the already-public extrinsic.

### Likelihood Explanation
High likelihood if a Gateway-side message execution ever fails after being accepted into the outbound queue (e.g. a downstream contract call reverts) — this is an expected code path (`success: bool` exists precisely to represent this outcome), not a corner case. No special privileges are required to call `submit_delivery_receipt`; the only precondition is possessing a valid Ethereum receipt/proof for a real transaction with `success = false`, which is trivially available to the relayer who submitted the corresponding message in the first place.

### Recommendation
- Short term: In `process_delivery_receipt`, branch on `receipt.success`. On `false`, do not call `T::RewardPayment::register_reward`; either leave the `PendingOrder` in place for retry/resubmission with a different execution, or move it to a distinct "failed" state/queue instead of unconditionally removing it, and emit a `MessageDeliveryFailed` event rather than `MessageDelivered`.
- Long term: Add an explicit test (as already partially done for the halted-bridge case in `test.rs`) covering `success: false` receipts to assert that no reward is paid and that order-state transitions correctly reflect failed execution, matching the “message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically” pivot.

### Proof of Concept
1. A message is queued via `do_process_message`, creating `PendingOrders[nonce] = { nonce, fee: F, block_number }` [4](#0-3) .
2. On Ethereum, the Gateway attempts to execute the message and the execution reverts (e.g., due to insufficient gas at the destination), emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
2. A relayer (or anyone with the log+proof) calls `submit_delivery_receipt(origin, event)` with `reward_address` set to their own account.
3. `T::Verifier::verify` succeeds (the proof is genuine), `DeliveryReceipt::try_from` decodes `success: false` successfully, `process_delivery_receipt` is invoked.
4. Since `receipt.success` is never inspected, `order.fee > 0` still triggers `T::RewardPayment::register_reward(&reward_account, ..., order.fee)`, and `PendingOrders::remove(nonce)` deletes the order — the relayer is paid in full for a failed delivery, and the record is gone, matching existing passing tests such as `submit_delivery_receipt_succeeds_after_unhalt` which only assert on `success: true`-style flows and never test the `success:false` branch [5](#0-4) .

#[test]
fn submit_delivery_receipt_succeeds_after_unhalt() {
	new_tester().execute_with(|| {
		let nonce = 0;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_valid_event_proof());

		// Bridge halted — receipt rejected, order untouched.
		set_verifier_halted(true);
		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);
		assert!(PendingOrders::<Test>::get(nonce).is_some());

		// Bridge resumed — same receipt succeeds and the order is settled.
		set_verifier_halted(false);
		assert_ok!(OutboundQueue::submit_delivery_receipt(origin, event));
		assert!(PendingOrders::<Test>::get(nonce).is_none());

		System::assert_has_event(mock::RuntimeEvent::OutboundQueue(Event::MessageDelivered {
			nonce,
		}));
	});
}
