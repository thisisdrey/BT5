In download.rs's `AttachmentsBatchStateMachine::try_proceed` `Done` arm, `network.atlasdb.find_all_attachment_instances(&attachment.hash())` is used to fan the received attachment out to every `AttachmentInstance` sharing that hash, then `resolve_attachment(&attachment.hash())` marks the batch resolved — all keyed purely on `attachment.hash()` computed from attacker-served bytes, not cross-checked against the specific `content_hash` that was originally requested for that batch entry. Can a remote peer serve, for a *different* outstanding `AttachmentRequest` in the same batch cycle, an `Attachment` whose hash happens to equal a `content_hash` requested by a *separate* batch entry (attacker deliberately crafts colliding-content-hash bytes for two different on-chain name commitments), causing `resolved_attachments` to pair the wrong `AttachmentInstance` with attacker bytes for both? Equality: `attachment.hash()` used for fan-out == the singular `content_hash` committed by the specific on-chain name operation tied to each `AttachmentInstance` (cross-instance pairing must not occur on a hash collision/reuse from an unrelated request). Scoped impact: High — BNS resolution serving one name's data as another's when hash reuse occurs across concurrently outstanding requests. Proof idea: net test with two `AttachmentInstance`s sharing identical `content_hash` (legitimate re-use) versus differing hashes, feeding a single `Attachment` matching only one, and asserting `find_all_attachment_instances` only pairs instances whose stored hash truly equals `attachment.hash()`.
