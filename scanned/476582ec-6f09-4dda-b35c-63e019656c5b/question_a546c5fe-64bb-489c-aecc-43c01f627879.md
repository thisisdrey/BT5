Target: `AccountEntry`'s `Lock<Account>` mutated via `Contract::internal_sub_balance` in contracts/defuse/src/contract/intents/state.rs during a `Transfer` intent whose `NotifyOnTransfer.msg` calls back the Verifier. Attacker action: attacker-controlled receiver contract implements `mt_on_transfer` (see `MultiTokenReceiver::mt_on_transfer` in contracts/defuse/src/contract/tokens/nep245/deposit.rs) that, inside the notification, submits a second `MultiPayload` re-using intent state that reads the receiver's not-yet-finalized balance. Preconditions: signer has balance B of `token_id=T`; `Transfer{receiver_id: attacker_contract, tokens: {T: B}, notification: Some(NotifyOnTransfer{msg, min_gas})}`. Call sequence: `Transfer::execute_intent` debits sender and credits receiver in `Deltas` synchronously, then schedules `notify_on_transfer` -> `Contract::notify_on_transfer` Promise to `mt_on_transfer` -> attacker calls `execute_intents` again referencing the freshly-credited balance before `mt_resolve_transfer` can claw back any refund. Binding: value debited from sender == value delivered to receiver plus value re-credited by `mt_resolve_transfer`'s refund logic. Impact: Critical, attacker spends a credit that is still eligible for refund, effectively duplicating T. Proof idea: sandbox test where attacker's `mt_on_transfer` reenters and transfers T out before returning a full-refund value from `mt_on_transfer`; assert total token_balances summed across sender+receiver+external recipient != B (i.e. > B).
