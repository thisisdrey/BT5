`decode_http_request` (libsigner/src/http.rs) parses headers with `httparse::Request::new(&mut headers_buf)` sized `MAX_HTTP_HEADERS=32` but returns `Err(EventError::Deserialize(...))` (a drop, not a crash) if `httparse::Status::Complete` isn't reached, e.g. when the signer/StackerDB HTTP client sends >32 headers. Can a remote peer POSTing a StackerDB chunk-ack response with 33+ headers cause `decode_http_response` to silently return `Deserialize` error, permanently dropping a validly-signed response that `StackerDBSession::rpc_request` was waiting on? Equality broken: acceptance of the HTTP response == an HTTP response with <= `MAX_HTTP_HEADERS` headers. Impact: High - bounded parsing DoS on a StackerDB session read path where a legitimate node's crafted (or attacker MITM-shaped) response never reaches the caller. Proof: Rust test in libsigner calling `decode_http_response` with a raw byte buffer containing 33 headers and asserting `Err(RPCError::Deserialize(_))` for an otherwise well-formed 200 response.
