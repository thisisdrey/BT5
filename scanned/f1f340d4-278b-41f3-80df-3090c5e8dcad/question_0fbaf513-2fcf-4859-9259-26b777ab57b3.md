`StackerDBSession::get_latest_chunks` (libsigner/src/session.rs) picks `limit` from `SIGNERS_STACKERDB_CHUNK_SIZE` (2MB) only `if self.stackerdb_contract_id.name.starts_with("signer")`, else falls back to `STACKERDB_MAX_CHUNK_SIZE` (16MB), and only filters oversized bodies AFTER the full `body_bytes` have already been read into memory by `rpc_request`/`decode_http_body`. Can a malicious node the signer is querying return a chunk body between 2MB and 16MB for a `signer-X-Y` contract, forcing the signer's HTTP client to fully buffer up to 16MB before the `body_bytes.len() > limit` check discards it as `None`? Equality broken: bytes buffered by `rpc_request` before rejection == bytes that should have been capped by the `signer`-contract's `SIGNERS_STACKERDB_CHUNK_SIZE` limit. Impact: High - bounded per-request memory amplification DoS on the signer's read path from an untrusted/compromised node response. Proof: Rust test with a local mock TCP server responding with a 15MB body to a `get_latest_chunks` call on a `signer-0-1` contract id, asserting memory captured before rejection and that `payloads` contains `None`.
