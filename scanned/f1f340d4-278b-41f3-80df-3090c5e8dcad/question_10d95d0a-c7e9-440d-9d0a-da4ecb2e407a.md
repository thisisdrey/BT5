`decode_http_body` (libsigner/src/http.rs) trusts the `transfer-encoding` header value equality check `val == "chunked"` case-sensitively, and for non-chunked bodies does `buf.to_vec()` with NO `Content-Length` cross-check against `buf.len()`. Can a remote node (or a MITM on the P2P/RPC-fed signer event path) send an HTTP response with `Content-Length: N` where `N` is smaller than the actual `buf` bytes following `body_offset`, causing `decode_http_body` to return extra unaccounted bytes past the declared length into `run_http_request`'s caller (e.g. `StackerDBSession::get_chunks`)? Equality broken: bytes returned as body == bytes declared by `Content-Length`. Impact: Critical - response body/length desync (a request-smuggling-adjacent framing bug) lets one HTTP response's trailing bytes bleed as chunk data for the next logical read, corrupting `StackerDBSession::list_chunks`/`get_chunks` parsing. Proof: Rust test constructing a buffer with `Content-Length: 4` header but a 40-byte body and asserting `decode_http_body` returns exactly 4 bytes, not 40.
