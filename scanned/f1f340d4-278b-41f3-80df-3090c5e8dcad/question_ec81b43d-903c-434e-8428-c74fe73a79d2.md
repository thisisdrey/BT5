`signer_message_payload_matches_lane` (libsigner/src/events.rs) gates chunk acceptance purely on `chunk.data.first()` (`SignerMessageTypePrefix::from_u8`) matching `message_id` derived from the contract name, before `read_next::<T,_>` fully deserializes the payload. Can a remote slot-owner attacker craft a `StackerDBChunkData.data` whose first byte equals a valid prefix for lane X (e.g. `BlockResponse=1`) but whose remaining bytes are a different, oversized or malformed encoding, so the type-prefix byte and the actual decoded variant diverge? Equality broken: `SignerMessageTypePrefix::from_u8(chunk.data[0])` == the true variant that `T::consensus_deserialize` will construct from `chunk.data`. Impact: High - a mismatched byte can cause `read_next::<T,_>` to consume differently than intended for the claimed lane, letting non-canonical/oversized payload bytes pass the lane filter and reach the runloop as if type-checked. Proof: Rust test in libsigner feeding a chunk with prefix byte 1 (BlockResponse) but body bytes that only decode successfully as a `StateMachineUpdate` under `T`, asserting the emitted `SignerEvent` variant differs from `chunk.data[0]`'s nominal type.
