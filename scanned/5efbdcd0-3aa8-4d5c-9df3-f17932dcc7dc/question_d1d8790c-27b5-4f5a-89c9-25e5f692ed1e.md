Target: `ft_resolve_withdraw`'s `Err(_) => amount.0` branch intentionally NOT refunding when the promise itself errors (comment cites a NEP-141 gas vulnerability). Attacker action: attacker deploys a receiver contract whose `ft_on_transfer` is designed to consume exactly enough gas to make the OUTER `ft_transfer_call`'s cross-contract promise appear to the Verifier's `ft_resolve_withdraw` callback as `Err(PromiseError)` (insufficient gas to read the result) while the receiver's `ft_on_transfer` ACTUALLY reverted/returned 0 used tokens on the underlying FT contract, meaning the FT contract's OWN `ft_resolve_transfer` already refunded the tokens back to the Verifier's real NEAR account. Preconditions: attacker controls receiver contract's gas consumption pattern; withdraw uses `msg: Some(..)`, `min_gas` set low by attacker via `FtWithdraw.min_gas` field if exposed to the withdrawer, or relies on default gas budgeting. Call sequence: `internal_ft_withdraw` debits `amount` -> `do_ft_withdraw`'s `ft_transfer_call` -> underlying FT contract's `ft_resolve_transfer` refunds tokens to Verifier's real account (since `ft_on_transfer` returned unused=amount) -> Verifier's `ft_resolve_withdraw` reads `Err(_)` for its own promise result index 0 due to insufficient gas -> sets `used = amount.0`, refund = 0, i.e. NO credit issued despite the real tokens having returned to Verifier's custody. Binding: (amount debited from sender) == (real tokens actually held by Verifier post-transfer, which is `amount` since they were refunded by the FT contract) + (amount re-credited to sender by `ft_resolve_withdraw`, which is 0); the equality fails — Verifier custodies `amount` extra real tokens with zero corresponding `token_balances` credit, meaning sender's funds are effectively lost from their perspective while real assets sit uncredited in the Verifier account. Scoped impact: Critical, sender's funds frozen/unrecoverable via normal ledger paths. Proof idea: near-workspaces test crafting a receiver contract that triggers a `PromiseError` on the withdraw's OWN resolve callback (e.g. via gas exhaustion in `ft_on_transfer`) while the FT's underlying transfer is refunded, assert sender's `token_balances[token]` stays reduced by `amount` with no compensating credit while Verifier's real FT balance is unchanged (i.e. tokens conceptually still there but inaccessible).
