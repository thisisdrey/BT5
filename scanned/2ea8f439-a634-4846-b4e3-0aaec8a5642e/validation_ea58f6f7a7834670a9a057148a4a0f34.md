## Title
Outbound queue `calculate_fee` can silently return a zero remote fee for a valid, non-zero pricing configuration, letting message senders be under-charged for Ethereum-side gas/reward - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
`Pallet::calculate_fee` in the Snowbridge outbound-queue pallet computes the fee a user must pay in `remote` currency to cover Ethereum-side gas and relayer reward. The computation chains several truncating integer operations (`FixedU128` inner-value division by `exchange_rate`, then `convert_from_ether_decimals`'s `checked_div` by a decimals-adjustment power of 10). With legitimate, non-zero `PricingParameters` (non-zero `fee_per_gas`, non-zero `reward`, non-zero `exchange_rate`, non-zero `multiplier`), the final `fee.remote` can still truncate to `0`. This is the same class of bug as the BarnBridge report: fee math rounds down to zero for small/adverse but otherwise valid inputs, and there is no floor/minimum-fee guard analogous to the `min_converted_fee = 1` pattern that other Substrate fee code (e.g. `pallet-transaction-payment/asset-tx-payment`) explicitly implements to close this exact hole.

### Finding Description
`calculate_fee` at [1](#0-0)  performs:

1. `calculate_remote_fee` — `fee_per_gas * gas_used_at_most + reward` in Ethereum-native `U256` [2](#0-1) .
2. Downcast to `u128`, then `FixedU128::from_inner(fee).saturating_mul(multiplier).checked_div(&exchange_rate).into_inner()`.
3. `convert_from_ether_decimals`, which does `value.checked_div(10^(18 - T::Decimals))` [3](#0-2) .

Step 3's `checked_div` is a plain integer division that truncates toward zero. When the intermediate fixed-point fee value is smaller than the decimals-adjustment divisor (e.g., `10^8` for a chain with 10-decimal native balance versus 18-decimal Ether), the result is `0`, even though every one of the pricing parameters that fed into it was strictly positive and "valid."

The repository's own test proves this is a real, reachable state and explicitly flags it as wrong: `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` sets `exchange_rate = 1`, `fee_per_gas = 1`, `rewards.remote = 1`, `multiplier = 1` — all non-zero — and asserts `fee.remote == 0`, with the comment "Though none zero pricing params the remote fee calculated here is invalid which should be avoided" [4](#0-3) . The test documents the defect but the production code path has no corresponding guard to prevent or reject it — unlike `pallet-transaction-payment/asset-tx-payment`'s `FungiblesAdapter`, which explicitly computes `min_converted_fee = if fee.is_zero() { Zero::zero() } else { One::one() }` to stop exactly this rounding-to-zero bypass [5](#0-4) . No such floor exists in `calculate_fee`/`convert_from_ether_decimals`.

Because `fee.remote` represents the portion of the total fee meant to reimburse the relayer/reward pot for executing the message on Ethereum (`pricing_params.rewards.remote`), a message can be committed and dispatched to the remote chain while the sender pays `0` in that component — the fee-paying step is fully bypassed for that message, exactly mirroring the BarnBridge "buyTokens fee rounds to 0" primitive: an unprivileged caller can repeatedly trigger message sends (any pallet routing XCM/messages through the outbound queue) under pricing/decimal configurations that produce this truncation, systematically avoiding the intended remote-fee charge.

### Impact Explanation
This falls under "public underpriced work that degrades... stalls bridge processing" and "runtime bugs that compromise intended behavior" in the impact gate: the remote fee is meant to fund the relayer reward and gas reimbursement for the Ethereum side of the bridge. If it silently computes to zero, senders extract free bridge delivery work, degrading the reward pot's ability to compensate relayers/executors and potentially causing under-funded or stalled message execution on the Ethereum side over time, without needing any privileged, admin, or malicious-relayer assumption — it is purely a consequence of the deployed `PricingParameters`/decimals configuration interacting with ordinary user-triggered message sends.

### Likelihood Explanation
Whether this is triggerable in a given deployment depends entirely on the live `PricingParameters` (fee_per_gas, exchange_rate, multiplier) and `T::Decimals` versus Ether's 18 decimals. The repository's own regression test demonstrates the exact non-zero parameter combination that reproduces the zero-fee outcome, showing it is not a purely theoretical corner case but a concretely reachable arithmetic state with realistic-looking values (unit exchange rate, unit multiplier, small `fee_per_gas`). Any parachain whose governance sets a low `fee_per_gas`/`reward` relative to its own decimals precision (e.g., during low Ethereum gas-price periods or for lightweight commands) can hit this without any adversarial input beyond ordinary message submission.

### Recommendation
Add an explicit floor to `calculate_fee` (and/or `convert_from_ether_decimals`) so that a non-zero pre-conversion fee never rounds down to a payable `0`, mirroring the `min_converted_fee` pattern used in `asset-tx-payment`: if the computed remote-currency amount before the final division is non-zero, `Fee.remote` should saturate to at least `1` (or the pallet should reject/queue-delay commitment) rather than silently accepting a zero charge. Alternatively, round the final `checked_div` up (`ceil`) instead of down when the dividend is non-zero.

### Proof of Concept
The existing unit test in the repository is itself the proof of concept:
```rust
// bridges/snowbridge/pallets/outbound-queue/src/test.rs:303-318
let price_params = PricingParameters {
    exchange_rate: FixedU128::from_rational(1, 1),
    fee_per_gas: 1_u32.into(),
    rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
    multiplier: FixedU128::from_rational(1, 1),
};
let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
assert_eq!(fee.remote, 0); // non-zero inputs -> zero remote fee charged
```
Any code path that invokes `Pallet::send`/message commitment using these (or similarly configured) `PricingParameters` will commit and dispatch the message to Ethereum while charging `0` in the remote-fee component, reproducing the fee-bypass primitive from the BarnBridge report.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}
