Based on my investigation, I found a genuine local analog in the Snowbridge inbound queue v2 relayer-fee payout flow.

### Title
Relayer fee is paid out even when the downstream XCM message send only partially succeeds, because success is judged on `Sender::deliver` returning `Ok`, not on execution/delivery of the payload - (File: `bridges/snowbridge/primitives/inbound-queue/src/v2/processor.rs`)

### Summary
`pallet-inbound-queue-v2`'s `process_message` pays the relayer their `relayer_fee` (plus any tip) whenever `T::MessageProcessor::process_message` returns `Ok`. `XcmMessageProcessor::process_xcm`/`send_xcm` treats the flow as successful as soon as `validate_send` produces a ticket and `Sender::deliver(ticket)` succeeds [1](#0-0) . This mirrors the ZKPay pattern: an outer settlement step (`register_reward`) is executed unconditionally once a fallible sub-operation returns any "successful enqueue" signal, without verifying that the sub-operation's real payload work (the actual XCM program encoded in the message, including the arbitrary attacker-supplied `remote_xcm`) will succeed when it is later executed on AssetHub.

### Finding Description
`process_message` in the pallet unconditionally pays `relayer_fee + tip` once `MessageProcessor::process_message` returns `Ok(message_id)`: [2](#0-1) 

`XcmMessageProcessor::process_xcm` only checks that message conversion succeeds and that `send_xcm` (validate + charge_fees + deliver) succeeds - it never inspects the outcome of executing the XCM at the destination: [3](#0-2) 

The message itself embeds an attacker-controlled `remote_xcm` fragment which is spliced directly into the instruction list built by `ConvertMessage`, after the `PayFees`/`ReserveAssetDeposited` instructions that only cover a small, attacker-chosen `execution_fee`: [4](#0-3) 

This is structurally the same broken invariant as the ZKPay bug: the outer function (`fulfillQuery` / `process_message`) settles payment as soon as a *dispatch attempt* completes, rather than gating settlement on the *actual completion* of the downstream logic (`zkPayCallback` / the appended `remote_xcm` instructions executing on AssetHub). Just as a fulfiller can starve `zkPayCallback` of gas via EIP-150's 1/64 rule while still reaching `settleQueryPayment`, a relayer/message-crafter here can under-fund `execution_fee` (which only pays for delivery/`PayFees`, not for the weight the attached `remote_xcm` needs on AssetHub) so that the appended XCM instructions fail or get dropped/trapped at the destination (`Outcome::Incomplete`/`Outcome::Error` in `XcmExecutor::execute`) — yet the reward has already been irrevocably registered on the source side because `send_xcm`'s `Ok` only proves *delivery*, not *execution*.

### Impact Explanation
If the relayer fee (and any user-supplied `execution_fee`) can be claimed regardless of whether the bridged XCM logic actually executes on AssetHub, this is a value-conservation break under the required-impacts gate ("duplicate settlement or payout" / underpriced public work): a caller can guarantee reward while causing the destination-side logic to fail/trap, effectively getting paid for unexecuted work, and repeatedly do so to drain the sovereign-account funded reward pool cheaply. This does not require a malicious relayer set, node, or governance actor — any signed account submitting a verified Ethereum event through `submit` triggers this path.

### Likelihood Explanation
Likelihood is **Low-to-Medium**: it requires crafting a valid, verifiable Ethereum event log with an intentionally underfunded `execution_fee`/heavy `remote_xcm`, which is feasible for anyone controlling the Ethereum-side Gateway contract interaction, but the exact economic benefit depends on relayer_fee vs. wasted execution_fee/asset-trap economics, and `AssetClaimer`/trapped-asset handling may partially mitigate fund loss (though not the reward-payout bypass itself). I could not fully verify from the available index whether `XcmExecutor::execute`'s outcome is checked anywhere further downstream (e.g., via `SendXcm` further gating) before this pallet's reward call — this is a partial pipeline view.

### Recommendation
Do not treat `Sender::deliver(ticket)` returning `Ok` as proof of successful execution of the appended `remote_xcm`. Either (a) require the appended remote XCM to itself measure/report execution outcome back before rewards are finalized (e.g., only pay the fee for the base delivery/asset-transfer portion immediately, and gate any reward tied to arbitrary `remote_xcm` execution behind a completion signal), or (b) require `execution_fee` to be validated against the actual weight of the full XCM program (base instructions + `remote_xcm`) before accepting the message, so under-funded destination execution cannot be crafted at low cost while still claiming full relayer reward.

### Proof of Concept
1. Attacker (or colluding relayer) emits a valid Ethereum Gateway event with a `Message` containing: a small, sufficient `execution_fee` to pass `PayFees`/delivery on the source side, but a `remote_xcm` payload requiring far more weight/deposit than `execution_fee` can buy on AssetHub (e.g., large storage writes or many nested calls).
2. Submit the event via `Pallet::submit` → `process_message` at `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs:185-198,215-245`.
3. `XcmMessageProcessor::process_xcm` converts and calls `send_xcm`, which only validates and delivers to the router; `Ok` is returned as soon as delivery succeeds [3](#0-2) .
4. `process_message` immediately calls `T::RewardPayment::register_reward(&relayer, ..., total_tip)` [5](#0-4) .
5. Later, on AssetHub, the appended `remote_xcm` instructions run out of weight/deposit and fail (`Outcome::Incomplete`/`Outcome::Error`), so the intended downstream logic never completes — but the reward has already been registered and is claimable, exactly mirroring the ZKPay pattern of settling payment while the "callback" (here, remote XCM execution) is starved of resources.

	fn send_xcm(
		dest: Location,
		fee_payer: &T::AccountId,
		xcm: Xcm<()>,
	) -> Result<XcmHash, SendError> {
		let fee_payer = AccountToLocation::try_convert(fee_payer).map_err(|err| {
			tracing::error!(
				target: LOG_TARGET,
				?err,
				"Failed to convert account to XCM location",
			);
			SendError::NotApplicable
		})?;
		let (ticket, fee) = validate_send::<Sender>(dest, xcm)?;
		Executor::charge_fees(fee_payer, fee).map_err(|error| {
			tracing::error!(
				target: LOG_TARGET,
				?error,
				"Charging fees failed with error",
			);
			SendError::Fees
		})?;
		Sender::deliver(ticket)
	}
