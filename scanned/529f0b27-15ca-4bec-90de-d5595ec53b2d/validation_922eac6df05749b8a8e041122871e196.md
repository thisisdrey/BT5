### Title
`process_delivery_receipt` ignores the Ethereum-reported `success` flag and pays relayer rewards for failed deliveries - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
`DeliveryReceipt::success` is decoded from the Ethereum `InboundMessageDispatched` event but is never inspected by `Pallet::process_delivery_receipt`. The outcome signal that should gate whether a relayer is paid is discarded exactly like the `verifyStateRoot` error was discarded in the external report: a fallible/negative outcome is computed, then the code proceeds down the same "pay and settle" path regardless of that outcome.

### Finding Description
`DeliveryReceipt` is decoded from the Ethereum event log and explicitly carries a `success: bool` field describing whether the message dispatch on Ethereum succeeded or failed: [1](#0-0) 

`submit_delivery_receipt` decodes this receipt and calls `process_delivery_receipt`: [2](#0-1) 

`process_delivery_receipt` then unconditionally pays the relayer reward and settles (removes) the `PendingOrder`, without ever checking `receipt.success`: [3](#0-2) 

This mirrors the external bug class exactly: an outcome value (`err` in the CometBFT report, `receipt.success` here) that is supposed to gate whether the "happy path" continues is computed/decoded but then silently dropped, so both the success case and the failure case take the identical settlement path (`RewardPayment::register_reward` + `PendingOrders::remove`). No guard exists elsewhere in the pallet — `submit_delivery_receipt` only checks `T::Verifier::verify` (proof validity) and `receipt.gateway` (origin binding); it never inspects `receipt.success`. Existing replay/duplicate protection (`PendingOrders` removal after processing) does not stop this because the vulnerable state (fee payout) is corrupted on the *first* legitimate call, not via replay.

### Impact Explanation
This falls under "duplicate settlement or payout" / "theft or unbacked mint" in the impact gate: an unprivileged relayer can submit a valid Merkle/receipt proof of a *failed* dispatch (Ethereum emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)` when a command execution reverts on Ethereum) and still receive the full relayer fee that was meant to reward *successful* delivery/execution. The reward is drawn from bridge-controlled funds via `T::RewardPayment::register_reward`, so this results in unbacked/incorrect fund payout from the bridge and, because the order is removed regardless of outcome, the record of a failed delivery is also discarded without recourse.

### Likelihood Explanation
Likelihood is high: no privileged actor, governance, or malicious infrastructure component is required — a normal relayer just submits a genuine, correctly-proven receipt for a message that failed to execute on Ethereum. This is a fully public entrypoint (`submit_delivery_receipt`) reachable by `ensure_signed` callers, and the missing check is a straightforward code-review-detectable omission of the `success` field that exists precisely to distinguish these two cases.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`:
- If `receipt.success == true`: pay the reward and remove the order as today.
- If `receipt.success == false`: remove/settle the order without paying the reward (or route to a distinct failure-handling path, e.g., no reward or a reduced "attempt" reward), and emit a distinct event (e.g., `MessageDeliveryFailed`) instead of `MessageDelivered`.

### Proof of Concept
1. A message is queued via `do_process_message`, creating `PendingOrders[nonce] = { fee > 0, ... }`. [4](#0-3) 
2. The message's commands are dispatched on Ethereum but fail (e.g., insufficient gas provided by the relayer, or a revert in the target contract), so the Ethereum Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. The relayer builds a valid receipt proof for this event and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (the proof is genuine), `DeliveryReceipt::try_from` decodes `success = false` correctly.
5. `process_delivery_receipt` is invoked; because `receipt.success` is never checked, `order.fee > 0` triggers `T::RewardPayment::register_reward(&reward_account, ..., order.fee)`, paying the relayer despite the failed delivery, and the order is removed as settled.

**Uncertainty note:** it is possible the bridge design intends to reward relayers purely for delivering the message (regardless of downstream command execution outcome), similar to the `bridges/modules/messages` pallet's stated policy of rewarding delivery transaction cost regardless of dispatch success. I was not able to find documentation or tests in this repository that explicitly confirm the intended semantics of the `success` field with respect to reward gating — the test suite only exercises `success: true` receipts. This should be verified against the Snowbridge V2 design docs/spec before treating this purely as a bug rather than an intentional simplification.

```rust
		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
