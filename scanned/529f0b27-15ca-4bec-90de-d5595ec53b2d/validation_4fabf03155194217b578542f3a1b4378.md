Confirmed: `DeliveryReceipt` decodes a `success: bool` field straight off the Ethereum `InboundMessageDispatched` event log [1](#0-0) , but `process_delivery_receipt` in the outbound-queue-v2 pallet never reads or checks `receipt.success` before paying the relayer reward and clearing the pending order [2](#0-1) .

### Title
Relayer reward and order settlement ignore the on-chain `success` flag in `DeliveryReceipt` - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`submit_delivery_receipt` verifies a Merkle/receipt proof that an `InboundMessageDispatched` event was emitted on Ethereum, then calls `process_delivery_receipt`, which pays the relayer reward and permanently removes the `PendingOrder` for that nonce. The decoded `DeliveryReceipt.success` boolean — which records whether the Ethereum-side dispatch actually succeeded — is decoded but never consulted.

### Finding Description
The pipeline is: `submit_delivery_receipt` → `T::Verifier::verify` (proves the log is really in a finalized Ethereum block) → `DeliveryReceipt::try_from` (decodes `nonce`, `topic`, `success`, `reward_address`) → `process_delivery_receipt` [3](#0-2) .

Inside `process_delivery_receipt`, only `receipt.gateway` is checked against the configured `GatewayAddress`; the nonce is looked up in `PendingOrders`, the fee is unconditionally paid via `T::RewardPayment::register_reward`, and the order is removed [4](#0-3) . `receipt.success` is silently discarded.

On Ethereum, `InboundMessageDispatched(nonce, topic, success, reward_address)` is emitted with `success = false` when message execution reverted/failed on the gateway contract (this is the entire reason the field exists — mirroring the design of the sibling inbound-queue pallet's message-processing flow, which conditions rewards on message outcome). Because this pallet does not gate on `success`, any Ethereum transaction that emits this event — including a failed/reverted dispatch — produces a valid receipt proof that a permissionless relayer can submit to claim the full fee and clear the order, exactly as if delivery had succeeded.

This is a genuine analog to the report's "immediate and permissionless finalization of unvalidated state": the report's flaw is that a state transition (withdrawal) is settled based only on the fact that *something was proposed*, without checking its validity/correctness before finalizing. Here, the settlement of `PendingOrders` (paying reward + irreversibly removing the order) is finalized based only on the fact that *an event with a matching nonce and gateway was proved to exist*, without checking the semantic correctness field (`success`) that determines whether the underlying action actually succeeded — no validator, admin, or relayer trust is required to exploit this; the check is simply missing in the public path.

### Impact Explanation
This breaks reward/settlement invariants for the outbound bridge queue: relayers can be rewarded for message deliveries that failed on Ethereum, and the corresponding `PendingOrder` is deleted regardless of actual delivery outcome, so there is no recovery/retry path and no on-chain record that the message needs to be redelivered. This is unbacked-payout / incorrect-settlement class impact against bridge reward funds, achievable by any signed account (permissionless relayer) with a real-but-failed transaction on Ethereum — no malicious validator, collator, or governance actor needed.

### Likelihood Explanation
High: an attacker only needs to cause (or opportunistically find) any Ethereum transaction that emits `InboundMessageDispatched` with `success = false` for a nonce they control the `reward_address` for (or leave zeroed to claim it themselves as the submitting relayer), then submit the standard proof via `submit_delivery_receipt`. No privileged access, race condition, or front-running is required — the code path unconditionally accepts it.

### Recommendation
In `process_delivery_receipt`, check `receipt.success` before paying the reward. On `success == false`, either (a) reject the receipt without consuming the pending order (allow legitimate redelivery/retry), or (b) explicitly define and implement the intended "failed delivery" settlement path (e.g., no reward, order requeued or refunded to sender) rather than silently treating failure identically to success.

### Proof of Concept
1. A message is queued via `do_process_message`, creating `PendingOrders[nonce] = { fee > 0, .. }` [5](#0-4) .
2. On Ethereum, the corresponding gateway dispatch reverts/fails, and the contract emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)` (per the `sol!` event definition) [6](#0-5) .
3. Any relayer builds the standard receipt/execution proof for that transaction and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (the log genuinely exists in a finalized block); `DeliveryReceipt::try_from` decodes `success = false` into the struct.
5. `process_delivery_receipt` ignores `success`, pays `order.fee` to `reward_account`, and removes `PendingOrders[nonce]` via `<PendingOrders<T>>::remove(nonce)` — identical behavior to a genuinely successful delivery [7](#0-6) .

I was unable to inspect `snowbridge_outbound_queue_primitives::v2::abi`/gateway Solidity source in this index to confirm the exact on-chain conditions under which `success=false` is emitted (e.g., whether it can also be triggered by an attacker-controlled command that intentionally fails cheaply), so the precise cost/ease of triggering a failing dispatch on the Ethereum side is not fully verified from this repo alone — that would need to be checked against the Gateway contract logic (outside this Rust codebase's index coverage).

```rust
		}
```

```rust
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
