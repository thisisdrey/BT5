## Analysis

Confirmed the key mechanism: `dispatch_transaction` (in `substrate/primitives/runtime/src/traits/transaction_extension/dispatch_transaction.rs`) calls `validate_and_prepare` — which runs `validate()` — and only *after* that returns `Ok` does it dispatch the call and run `post_dispatch`. There is no `with_transaction`/storage-layer wrapper around `validate()` itself inside `apply()`/`dispatch_transaction`. `frame_executive`'s `do_apply_extrinsic` also does not wrap `Applyable::apply` in a rollback-on-`Err` storage transaction — it just propagates the `TransactionValidityError` with `?`. [1](#0-0) [2](#0-1) 

In `substrate/frame/origin-restriction/src/lib.rs`, `RestrictOrigin::validate()` unconditionally writes the incremented `usage` into `Usages::<T>` storage at line 316 **before** it checks whether the new usage exceeds the allowance and returns the pass/fail verdict:

```
usage.used = usage.used.saturating_add(fee);
Usages::<T>::insert(&entity, &usage);
...
if usage.used <= allowance.max || allowed_one_time_excess() {
    Ok(...)
} else {
    Err(InvalidTransaction::Payment.into())
}
``` [3](#0-2) 

Since this write happens inside `validate()`, and `validate()`'s storage effects are not rolled back when the extrinsic is ultimately rejected (unlike the block-builder's speculative `push()` which explicitly wraps `apply_extrinsic` in `execute_in_transaction`/rollback-on-error at the *node* level, and unlike the pallet's own test harness `exec_tx`/`exec_signed_tx` in `mock.rs` which manually wraps its standalone validate-probe in `with_transaction(...Rollback...)`), the on-chain `apply_extrinsic` path used by real block execution has no such protective wrapper around `Applyable::apply`. [4](#0-3) 

This is the direct structural analog of the `UniActionPolicy` bug: the function that is supposed to be the "checker" (`validate`) mutates and persists the usage counter as a side effect of merely being *called*, regardless of whether the transaction it is checking is ultimately accepted. In the Solidity bug the check function failed to persist a needed update (`memory` instead of `storage`); here the inverse but equally invariant-breaking defect exists — a validation-only function persists a state update that should only become durable once the extrinsic is actually applied/committed.

### Title
Usage counter is persisted in `RestrictOrigin::validate()` even when the extrinsic is rejected - (`substrate/frame/origin-restriction/src/lib.rs`)

### Summary
`RestrictOrigin::validate()` writes the newly-incremented `Usage` record to storage via `Usages::<T>::insert` before determining whether the transaction is actually within the allowance and returning `Err(InvalidTransaction::Payment)` for excess. Because this write is not conditioned on the extrinsic being accepted/applied, and no transactional rollback wraps `validate()` on the normal `apply_extrinsic` path, usage can be inflated by transactions that never dispatch.

### Finding Description
`Usage.used` is meant to reflect only the accumulated cost of *successfully applied* extrinsics from a restricted entity, gradually recovering over blocks, and gating whether future transactions are allowed. The invariant is: usage must track applied calls, and a transaction that is rejected as invalid must have no lasting effect on chain state (this is the whole point of `validate()` being distinct from `prepare()`/dispatch).

`validate()` violates this invariant: it computes the candidate new usage, inserts it unconditionally, and only afterward evaluates whether that usage is within the allowance: [5](#0-4) 

The insert on line 316 happens for every call to `validate`, independent of the subsequent accept/reject decision. Any legitimate mechanism that invokes `validate()` outside of a full, atomically-committed `dispatch_transaction` — e.g. speculative/probe validation performed without the node-level rollback wrapper that the mock/test harness manually applies, or any runtime code path that calls the transaction-extension pipeline's `validate_only`/`validate` for inspection — will leave the storage mutation in place. The pallet's own doc comment states the intended remediation ("After dispatch, any call flagged as Pays::No fully restores the consumed usage") but there is no analogous restoration for a transaction that fails validation and is never dispatched at all; the usage increment from the rejected attempt is never reverted.

### Impact Explanation
An entity's `Usages` counter can be pushed towards (or past) `allowance.max` by validation-only "attempts" that are never actually dispatched, i.e. without the entity paying any fee or having any call executed. This directly corrupts the on-chain accounting value `Usages::<T>::get(entity).used`, which gates whether the entity's genuine transactions are accepted (`InvalidTransaction::Payment`) and whether it can use the one-time-excess allowance. This is a runtime bug that compromises intended behavior of the restriction/rate-limiting mechanism, potentially causing a legitimate restricted entity's transactions to be wrongly rejected (denial of service) or, depending on how `validate()` is invoked outside the atomic apply path, effectively grief usage state without cost.

### Likelihood Explanation
The write happens on every call to `validate()`, which is explicitly documented as being "called frequently by the transaction queue to obtain transaction validity against current state" — i.e., it is expected to be invoked outside of full dispatch. The mock/test harness in this very pallet demonstrates that the *safe* way to call `validate()` standalone is to wrap it in `with_transaction(...Rollback...)`; the fact that this wrapping was needed for tests to remain sound highlights that `validate()` alone is not self-contained/side-effect-free, and any caller (or path) that invokes it without that explicit rollback wrapper will leak the storage mutation.

### Recommendation
Move the `Usages::<T>::insert(&entity, &usage)` call so that it only happens once the transaction is determined to be within the allowance (or write it in `prepare()`/`post_dispatch` instead of `validate()`), mirroring the Solidity fix recommendation of only persisting usage updates in the code path that actually corresponds to accepted/applied execution, not in the "checking" function itself.

### Proof of Concept
1. Construct a signed extrinsic from a `RestrictedEntity` whose current `used` is close to `allowance.max`, with a `call`/`len` combination whose `fee` would push `used` over `allowance.max` (or that will fail during dispatch execution).
2. Invoke `RestrictOrigin::<T>::validate(...)` directly (or via any caller of the transaction-extension pipeline's `validate`/`validate_only` that does not wrap the call in a rollback storage transaction), observe `Usages::<T>::get(&entity)` afterward.
3. Even though `validate` returns `Err(InvalidTransaction::Payment)` (transaction rejected, never dispatched, no fee paid), `Usages::<T>::get(&entity).used` reflects the incremented value from line 314-316, corrupting the entity's usage accounting without any corresponding accepted transaction.
