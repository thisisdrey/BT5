[stackslib/src/net/codec.rs :: Preamble::consensus_deserialize] Can a remote peer send a P2P message whose Preamble.payload_len field is set to MAX_MESSAGE_LEN-1 (just under the `if payload_len >= MAX_MESSAGE_LEN` rejection) while the actual TCP payload delivered is far shorter, so that the downstream StacksMessageCodec payload reader (which trusts payload_len to size its BoundReader) blocks or reads short, and then a second attacker-controlled message is spliced onto the still-open connection and parsed as the tail of the first payload? Precondition: unauthenticated TCP connection to the P2P port, pre-handshake. Call sequence: Preamble::consensus_deserialize -> payload dispatch using payload_len as declared size -> per-message consensus_deserialize on a bound reader. Equality: bytes read for the payload by the message decoder == Preamble.payload_len, for every subsequent message on the same connection. Impact: Critical, request/message smuggling across the same P2P connection. Proof idea: a stackslib::net test that opens a mocked stream, writes a Preamble with payload_len=N but only N-k payload bytes, then appends a second full message, and asserts the parser either blocks correctly on EOF or misattributes byte k..N of the second message to the first payload.
