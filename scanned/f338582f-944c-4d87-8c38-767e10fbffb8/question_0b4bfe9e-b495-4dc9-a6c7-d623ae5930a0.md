Target: `ImtMint`/`ImtBurn` `minter_id: AccountId` authority field vs. `Engine::execute_signed_intent`'s `signer_id` used for `internal_add_balance`/`internal_sub_balance` bookkeeping keyed by `ImtTokenId::minter_id`. Attacker action: sign a `MultiPayload` as themselves (`signer_id = attacker`) containing `ImtMint { receiver_id: attacker, tokens: {tok: N}, memo: None, notification: None }`, i.e. `ImtTokenId::new(minter_id=attacker, token_id=tok)`; separately, from within a re-entrant callback triggered by a different intent's `AuthCall`/`NotifyOnTransfer` in the same batch, attempt a second `ImtMint` reusing `minter_id = attacker` but this time embedding it as an `ImtBurn.minter_id` field controlled by a *different* signer who never authorised burning attacker's tokens. Preconditions: two distinct signed payloads batched together via `execute_intents`, one from attacker (mint) and one forged/replayed from a victim's previously-seen signature fragment (should be rejected). Call sequence: `Engine::execute_signed_intent` checks `self.state.has_public_key(&signer_id, &public_key)` per payload before calling `ImtBurn::execute_intent` -> `engine.state.imt_burn(signer_id, &self.minter_id, ...)`. Binding: the `signer_id` that `imt_burn` receives as caller == the account whose balance of `ImtTokenId{minter_id: self.minter_id, token_id}` is actually debited; `self.minter_id` merely selects the token namespace and never substitutes for the authorising `signer_id`. Impact: Critical - unauthorised burn of another account's `imt:` balance. Proof idea: cargo test has attacker sign only an `ImtMint`, and separately crafts an `ImtBurn{minter_id: attacker, ...}` signed by a different unrelated account holding no balance of that token; assert `imt_burn` fails with an insufficient-balance/authorization error rather than draining the attacker's balance under someone else's signature.
