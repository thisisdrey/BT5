Target: `run_http_request` in `libsigner/src/http.rs`, which calls `sock.read_to_end(&mut buf)` to consume the entire HTTP response before calling `decode_http_response`. Attacker action: a malicious node the signer's `StackerDBSession` is configured to poll (or a rogue peer answering a signer's outbound GET) sends an HTTP response with `Connection: keep-alive` semantics but never closes the socket and never sends a terminating boundary, causing `read_to_end` to block until `socket_timeout` — but sends data at a slow trickle (a few bytes at the timeout interval) to keep the connection alive just under timeout repeatedly. Preconditions: `StackerDBSession::socket_timeout` is a fixed duration per read; attacker fully controls the response stream once connected. Call sequence: `rpc_request` → `with_socket` → `run_http_request`'s `read_to_end` loop respects only the per-read timeout, not a total-request timeout budget. Equality/fault: total wall-clock time bound for one `get_latest_chunks`/`list_chunks` call is not equal to a single `socket_timeout` interval, but can be multiplied indefinitely by an adversarial responder trickling bytes just under the read timeout each time — a bounded but attacker-controllable compute/time DoS on a single call. Impact: High — bounded read-endpoint DoS (each malicious response instance stalls the polling signer for attacker-chosen multiples of `socket_timeout`). Proof idea: Rust test standing up a `TcpListener` that writes one byte every `socket_timeout - 10ms` indefinitely, and measuring that `run_http_request` takes far longer than one `socket_timeout` to fail, demonstrating the missing total-deadline equality.
