## Analysis

The external report's core broken invariant: an async cross-chain "pay/undo" step is treated as final and the source-side bookkeeping is cleared before the remote step is confirmed to have succeeded, with no compensation/retry path if the remote step fails — causing permanent fund loss.

The local analog exists in the Snowbridge relayer-reward payout path.

### Title
Relayer reward is irrecoverably burned when the cross-chain `PayAccountOnLocation` reward XCM fails to execute on AssetHub - (File: `bridges/snowbridge/primitives/core/src/reward.rs`, `bridges/modules/relayers/src/lib.rs`)

### Summary
`pallet-bridge-relayers::do_claim_rewards` removes the relayer's accumulated reward from storage and then calls `T::PaymentProcedure::pay_reward`. For Snowbridge rewards, this procedure (`PayAccountOnLocation::pay_reward`) does not actually pay anything locally — it only validates and *hands off* a fire-and-forget XCM (`UnpaidExecution` + `ReserveAssetDeposited` + `DepositAsset`) to AssetHub, then returns `Ok(())` as soon as the message is queued for delivery, not once it has actually executed successfully on the destination chain.

### Finding Description
`do_claim_rewards` in [1](#0-0)  uses `RelayerRewards::try_mutate_exists` and calls `maybe_reward.take()` to remove the reward from storage *before* invoking `T::PaymentProcedure::pay_reward`. The storage mutation only rolls back if the closure returns `Err`.

For the Snowbridge reward kind, `pay_reward` is implemented by `PayAccountOnLocation` in [2](#0-1) . This builds an XCM program consisting of `UnpaidExecution`, `DescendOrigin(InboundQueueLocation)`, `UniversalOrigin(GlobalConsensus(Ethereum))`, `ReserveAssetDeposited(assets)`, and `DepositAsset { beneficiary }`, then only `validate`s and `deliver`s the ticket to `XcmSender`, returning `Ok(())` once delivery to the queue succeeds — **not** once the remote instructions actually execute.

If the remote `DepositAsset` instruction fails on AssetHub (e.g. the chosen beneficiary account does not satisfy the existential deposit for the newly-minted foreign asset, the asset isn't registered, or execution is otherwise rejected), the XCM executor traps the leftover holding via `AssetTrap::drop_assets` under the origin established by `UniversalOrigin(GlobalConsensus(Ethereum))`/`DescendOrigin(InboundQueueLocation)` — a virtual, Ethereum-anchored interior location that no real account on AssetHub controls. Since no `SetAssetClaimer` is set in this program, the resulting `AssetsTrapped` entry (see `DropAssets` at [3](#0-2) ) is permanently unclaimable by the relayer or beneficiary.

Meanwhile, on BridgeHub the `RelayerRewards` entry has already been irrevocably removed and the `RewardPaid` event has already fired — there is no mechanism to detect the remote failure, re-credit the reward, or retry the mint-and-deposit. This is precisely the pattern in the external report: the source side "believes" the compensating/forwarding action succeeded and discards the resource (the reward claim) before the counterpart step is confirmed, and there is no undo/retry path for the async failure.

### Impact Explanation
A legitimate relayer that has earned a Snowbridge reward can lose that reward permanently through no fault of a malicious third party — simply because the `DepositAsset` on AssetHub fails (dust/ED issues, foreign-asset registration edge cases, congestion causing weight/barrier failures, etc.). The funds are not returned to the relayer, not reclaimable via `claim_assets` (wrong/unreachable trap origin), and not retried by the protocol. This is a permanent-fund-lock/loss of bridge relayer rewards, which are meant to incentivize honest relaying — undermining the security assumption that reward payment is reliable.

### Likelihood Explanation
This does not require a malicious relayer, validator, governance actor, or leaked key. It can be triggered under ordinary operational conditions: any scenario in which the AssetHub-side `DepositAsset` fails after the BridgeHub-side reward has already been debited from storage (e.g., relayer picks a fresh/unfunded beneficiary account, or the account is reaped between claim submission and XCM execution). The `claim_rewards_to` extrinsic is a public, unprivileged entry point (`ensure_signed`), and the bug is deterministic given a failing deposit on the remote side.

### Recommendation
Do not remove the `RelayerRewards` entry until remote settlement is confirmed. Options:
- Use a two-phase approach: mark the reward as "in-flight" (locked) rather than deleting it, and only finalize removal upon receiving a confirmation message back from AssetHub (mirroring the `submit_delivery_receipt`/pending-order pattern already used elsewhere in Snowbridge, e.g. [4](#0-3) ).
- Always set `SetAssetClaimer` (or otherwise pin the trap origin to a real, relayer-controlled account) in the `PayAccountOnLocation` XCM program so that a failed `DepositAsset` traps assets that are actually claimable by the relayer/beneficiary.
- Alternatively, credit the reward back into `RelayerRewards` if a failure notification is observed (e.g. via `SetErrorHandler`/response reporting), restoring the two-phase-commit guarantee described in the original report's recommendation.

### Proof of Concept
1. A relayer accumulates a Snowbridge reward via `register_reward`, verified by `RelayerRewards::<T,I>::get`.
2. Relayer calls `claim_rewards_to(BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(beneficiary))` where `beneficiary` is an account with no existing entry (no ED) for the reward's foreign asset.
3. `do_claim_rewards` removes the reward and calls `PayAccountOnLocation::pay_reward`, which validates and enqueues the XCM to AssetHub, returning `Ok(())`; `RewardPaid` event fires and storage entry is gone.
4. On AssetHub, `DepositAsset` fails because `beneficiary` does not meet ED for the minted asset; the holding (the reward) is trapped under an Ethereum/InboundQueue-anchored virtual origin that the relayer cannot construct a matching signed origin for.
5. The relayer's reward is gone: not present on BridgeHub (already removed) and not claimable on AssetHub (`claim_assets` cannot match the trap origin).

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}

impl<T: Config> DropAssets for Pallet<T> {
	fn drop_assets(origin: &Location, holding: AssetsInHolding, _context: &XcmContext) -> Weight {
		if holding.is_empty() {
			return Weight::zero();
		}
		let assets: Vec<Asset> = holding.assets_iter().collect();
		// SAFETY: "forget" about any fungible imbalances so that they are not dropped/resolved
		// here. The mirrored asset claiming operation will "recover" the imbalances by minting
		// back into holding, effectively duplicating the imbalance and only then dropping the
		// duplicate. As a result, total issuance doesn't change.
		holding.fungible.into_iter().for_each(|(_, mut accounting)| {
			accounting.forget_imbalance();
		});
		let versioned = VersionedAssets::from(Assets::from(assets));
		let hash = BlakeTwo256::hash_of(&(&origin, &versioned));
		AssetTraps::<T>::mutate(hash, |n| *n += 1);
		Self::deposit_event(Event::AssetsTrapped {
			hash,
			origin: origin.clone(),
			assets: versioned,
		});
		// TODO #3735: Put the real weight in there.
		Weight::zero()
	}
