Based on my research, I found a solid local analog in the Snowbridge V2 outbound queue's gas/fee accounting for the `CallContract` command, which mirrors the EIP-7623 issue of user-declared/underpriced calldata cost not matching actual downstream execution cost.

### Title
Self-declared, unvalidated `gas` field for `Command::CallContract` lets senders underprice Snowbridge outbound message delivery cost - (File: `bridges/snowbridge/primitives/outbound-queue/src/v2/message.rs`)

### Summary
For every other `Command` variant, `GasMeter::maximum_dispatch_gas_used_at_most` returns a **fixed, protocol-defined** gas estimate [1](#0-0) . For `Command::CallContract`, however, the gas figure used to price the message is taken **verbatim from the caller-supplied `gas` field of the command itself**, with no relationship enforced to the size of the accompanying `calldata`: [2](#0-1) [3](#0-2) .

### Finding Description
`Message::commands` for the outbound-queue-v2 pallet is processed in `do_process_message`, which computes the per-command gas via `T::GasMeter::maximum_dispatch_gas_used_at_most(&command)` and stores it as the `gas` field of the committed `OutboundMessage`/`CommandWrapper` that is Merkle-committed for relaying to Ethereum [4](#0-3) . This same `Message` also carries a `fee` field that is copied unchanged into `PendingOrder.fee` and later paid out in full to the relayer that submits the delivery receipt, with no cross-check against the actual gas/computation required: [5](#0-4) [6](#0-5) .

Critically, `SendMessage::validate` for the v2 pallet performs **no fee computation or gas-based floor check at all** — it only checks the total encoded payload size against `MaxMessagePayloadSize` and passes the message straight through [7](#0-6) . Combined with `CallContract`'s gas meter simply trusting `*gas_limit` from the command payload [3](#0-2) , an XCM origin constructing a `CallContract` command can supply a large `calldata: Vec<u8>` (bounded only by `MaxMessagePayloadSize`) while declaring an arbitrarily small `gas`, decoupling the priced/rewarded cost of the message from its true relaying and processing cost — the same broken invariant as the EIP-7623 report, where calldata-driven cost was not reflected in the gas/fee figure used downstream.

### Impact Explanation
This breaks the invariant that "public underpriced work... degrades block production or stalls bridge processing." Since relayer compensation (`order.fee`) is decoupled from the real cost of delivering a message with large calldata, this can: (a) make large/expensive `CallContract` messages economically unattractive to relay, causing them to be indefinitely stuck in `PendingOrders`/never receive a delivery receipt (a stalled-bridge / permanent-lock condition on the Polkadot side of the pipeline), and (b) let a sender push oversized payloads into the Merkle-committed outbound queue while paying a fee sized for a much smaller declared gas figure, degrading the fairness/economics of bridge processing without any privileged actor being involved.

### Likelihood Explanation
Any origin capable of dispatching an `ExportMessage`/system-v2 `send` with a `CallContract` command controls both `calldata` and `gas` fields directly; there is no validator, admin, or relayer collusion required — this is reachable via the ordinary, unprivileged outbound message construction path already exercised by `send_message_impl.rs` and `do_process_message`.

### Recommendation
Make `GasMeter::maximum_dispatch_gas_used_at_most` for `Command::CallContract` derive a floor gas value from `calldata.len()` (mirroring an EIP-7623-style floor: base gas + per-byte calldata cost) rather than trusting the caller-supplied `gas` verbatim, and/or validate in `SendMessage::validate`/`do_process_message` that the message's declared `fee` is at least the fee computed from `T::GasMeter::maximum_gas_used_at_most` before accepting/queuing it.

### Proof of Concept
1. Construct an XCM `Transact`/`ExportMessage` (or use `snowbridge-pallet-system-v2::send`) carrying a `Command::CallContract { target, calldata: vec![0u8; MaxMessagePayloadSize::get() as usize - overhead], gas: 21_000, value: 0 }`.
2. Attach a `Message.fee` sized for a 21_000-gas call.
3. `SendMessage::validate` in `send_message_impl.rs` accepts it (only checks total payload size) [7](#0-6) .
4. `do_process_message` computes `gas = 21_000` via `GasMeter::maximum_dispatch_gas_used_at_most` [4](#0-3)  and commits the oversized-calldata/low-gas message, storing the underpriced `fee` in `PendingOrders` [5](#0-4) .
5. Relayers now must deliver a large-calldata message for a reward computed off a declared 21,000 gas figure, independent of true relaying/dispatch cost.

Note: I was unable to fully trace whether an upstream caller (e.g. `snowbridge-pallet-system-v2::send` or the XCM `ExportMessage` executor) enforces a minimum `fee` before calling `SendMessage::deliver`, since `bridges/snowbridge/primitives/outbound-queue/src/v2/converter.rs` was not found in the index. If such an upstream floor check exists and correctly ties `fee` to `GasMeter` output including calldata-length scaling, this specific path would already be mitigated at that layer — this should be verified in a live session with full file access.

impl GasMeter for ConstantGasMeter {
	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64 {
		match command {
			Command::SetOperatingMode { .. } => 40_000,
			Command::Upgrade { initializer, .. } => {
				// total maximum gas must also include the gas used for updating the proxy before
				// the the initializer is called.
				50_000 + initializer.maximum_required_gas
			},
			Command::UnlockNativeToken { .. } => 200_000,
			Command::RegisterForeignToken { .. } => 1_200_000,
			Command::MintForeignToken { .. } => 100_000,
			Command::CallContract { gas: gas_limit, .. } => *gas_limit,
		}
	}
}
