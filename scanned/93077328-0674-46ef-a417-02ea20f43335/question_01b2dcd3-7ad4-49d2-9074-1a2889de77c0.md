Can an attacker exploit `Secp256k1RecoverableSignature`-based recovery in `SignedErc191Payload::verify()` (`erc191.rs`) or `SignedTip191Payload::verify()` (`tip191.rs`), both calling `Erc191::recover`/`Tip191::recover` with an attacker-chosen `recovery_id`, to produce a `PublicKey::Secp256k1` different from the one that actually holds the private key that produced a malleable `(r,s)` pair, and pass that attacker-chosen public key into `self.state.has_public_key(&signer_id, &public_key)` where `signer_id` is an implicit account id `public_key.to_implicit_account_id()` never explicitly registered by anyone (falling back to the implicit derivation in `StateView::has_public_key`)? Preconditions: attacker has any valid ECDSA signature over arbitrary bytes (their own signature is sufficient since they choose `signer_id` to equal their own derived implicit account). Call sequence: `execute_signed_intent` -> `verify()` -> recovers `PublicKey` -> `has_public_key` implicit fallback path -> intents executed under `signer_id` == attacker's own account. Binding: (signer_id, public_key) authorised == (account, key) actually signed for. Scoped impact: this scenario is self-authorised (attacker signing for themselves) and not exploitable against a victim, so classify as: not a finding unless attacker can force `recovery_id` ambiguity to derive a *victim's* implicit account id from a signature the victim made for unrelated purposes off-chain — test whether ECDSA signature malleability (flipping `s` to `n-s` with adjusted `recovery_id`) yields two *different* valid recovered public keys for the same `(payload, signature)`, breaking uniqueness of signer identity. Proof idea: cargo test asserting `Erc191::recover` returns exactly one public key per `(message, r, s)` regardless of which of the two valid `recovery_id` values consistent with a given `s`/`-s` is supplied, i.e., that malleable variants of the same conceptual signature cannot recover to two distinct non-corresponding public keys.
