Preconditions: attacker has no valid key for wallet.near but can guess or enumerate nonces the real signer intends to use next (e.g. sequential nonce scheme recommended in README). Call sequence: execute_signed -> nonces.commit(msg.nonce,...) succeeds and sets the bit -> S::verify_request_msg fails -> Err(InvalidSignature) returned, but does the nonce bit get rolled back on Err, or does it persist consumed? Binding: a nonce is marked used == a request was actually authorized and executed; an invalid-signature attempt must not consume a nonce the legitimate signer intended to use next (no permanent DoS-via-nonce-burn that blocks the signer's next legitimately signed message reusing that nonce). Critical/High impact: if nonce commit is not rolled back on invalid-signature failure, an attacker can preemptively burn the signer's next planned nonce, and if the signer's off-chain client blindly resubmits with the same nonce (per README's incrementing recommendation) their subsequent legitimately signed request permanently fails to execute, effectively locking that nonce's associated action out. Proof idea: cargo test calling execute_signed with a known-invalid proof for nonce N, asserting Err(InvalidSignature), then calling execute_signed again with a validly signed msg using the same nonce N, asserting whether it succeeds (nonce not consumed) or fails (nonce erroneously consumed by the failed attempt).
