[File: mainnet/contracts/market/v0-4-market.clar] Can an attacker call `borrow` for an amount where `convert-to-scaled-debt(asset-id, amount, true)` (round-up) computes `scaled = mul-div-up(amount, INDEX_PRECISION, borrow-index)` that, due to `borrow-index` being refreshed via `accrue-and-cache` mid-transaction (cache keyed by `stacks-block-time`), differs from the `borrow-index` used later in the same block by `repay`'s `mul-div-down`, because a second unrelated user's borrow/repay in the same block also uses `accrue-and-cache` and the cache is per-timestamp not per-call, letting the attacker sandwich their own borrow+repay around another user's index-changing operation to extract a favorable index snapshot? Preconditions: two principals active in the same block, attacker controls call ordering. Call sequence: attacker borrow(asset,X) -> victim triggers vault-accrue via their own borrow -> attacker repay(asset,X) using the now-different cached index. Invariant: cached value and its source must agree — index used for scaled-debt at borrow time and at repay time within the same logical operation must be consistent per user's own accrual, not shared/stale from another user's cache write. Impact: High, theft of unclaimed yield (interest owed by attacker's position under-counted). Proof: assert scaled-debt recorded at borrow == scaled-debt required to fully clear at repay using the SAME index snapshot; flag if intervening cache write changes the effective conversion rate the attacker exploits.
