## Analysis

I found a direct local analog to the reported bug class in `pallet-nomination-pools`'s `withdraw_unbonded` extrinsic. The report's core broken invariant is: **"amount computed as owed to the user" ≠ "amount actually settled"**, and when the actual settlement is less than the computed entitlement, the difference becomes permanently stranded while the ledger has already marked the claim as fully resolved.

### Title
Under-withdrawal in `Pools::withdraw_unbonded` permanently strands member funds when `transferable_balance` is less than the dissolved sub-pool balance - (File: `substrate/frame/nomination-pools/src/lib.rs`)

### Summary
`withdraw_unbonded` computes `balance_to_unbond` by calling `dissolve()` on the member's unbonding sub-pool(s) — which **irreversibly decrements the sub-pool's `points` and `balance`** as if the member had been paid in full — and only afterward caps the amount actually transferred with `.min(T::StakeAdapter::transferable_balance(...))`. If the two diverge, the member receives less than the pool's own accounting says they are owed, and the shortfall is not attributed anywhere.

### Finding Description
In `withdraw_unbonded` [1](#0-0) , the sequence is:

1. `withdrawn_points` are removed from the member (`member.withdraw_unlocked`).
2. For each era, `era_pool.dissolve(*unlocked_points)` is called, which computes `balance_to_unbond = point_to_balance(...)` and **subtracts both points and balance from the sub-pool immediately** [2](#0-1) .
3. Only after all sub-pool state has been mutated does the code apply `.min(T::StakeAdapter::transferable_balance(...))` to cap the amount actually withdrawn [3](#0-2) .
4. `T::StakeAdapter::member_withdraw` is then called with this capped amount [4](#0-3) .

The code comment itself acknowledges the discrepancy is expected in some conditions: *"This check is also defensive in cases where the unbond pool does not update its balance (e.g. a bug in the slashing hook.)"* [5](#0-4) . This is structurally identical to the audited report's Case 1: the redemption ledger (`sub_pools`) is decremented as if `balance_to_unbond` was fully paid out (`amountOut` credited internally), but the actual transfer (`member_withdraw`) can be strictly less (`repayAmountIn`), and the difference (`balance_to_unbond - transferable_balance`) is never reconciled — it is not returned to the sub-pool, not credited to the member, and not distributed to remaining pool members. It simply vanishes from all pool-level accounting (`TotalValueLocked`, sub-pool balances) while remaining un-transferred inside the pool's bonded/agent account.

For `TransferStake`, `transferable_balance` is the pool account's `reducible_balance` (Expendable, Polite) [6](#0-5) , which can legitimately be lower than the sub-pool's computed balance whenever the bonded account holds a existential-deposit/frozen balance restriction, or whenever `active_stake`/staking-side underlying free balance updates lag the pool's own `points→balance` bookkeeping (e.g., via `StakeAdapter::withdraw_unbonded` not fully releasing funds in the same block, or a discrepancy introduced by slashing hooks as the code explicitly flags). For `DelegateStake`, `transferable_balance` additionally takes `.min(delegator_balance)`, introducing a second, independent source of divergence from the sub-pool's `balance_to_unbond` computation [7](#0-6) .

Existing tests directly demonstrate that a nonzero delta between `dissolve()` output and actual transfer is a known, reachable state (not merely theoretical): in `withdraw_unbonded_works_against_slashed_with_era_sub_pools` and related tests, `.min(transferable_balance)` reduces the amount actually paid relative to the sub-pool's tracked balance [8](#0-7) , and the delegate-stake test suite shows delegator-tracked balance and sub-pool tracked balance diverging by design in slashing scenarios [9](#0-8) .

Notably, this exact bug class ("points dissolved but held funds weren't released") was already found and required a one-time governance migration to fix a related instance (`CurrentEra` vs `ActiveEra` mismatch) [10](#0-9) , confirming this class of discrepancy is a real, previously-manifested defect in this exact pallet, not a hypothetical.

### Impact Explanation
Any divergence between the sub-pool's `point_to_balance` computation and the adapter's `transferable_balance`/`member_withdraw` path results in a **permanent, unrecoverable loss of member funds** with no compensating credit anywhere in the system: `sub_pools` storage, `TotalValueLocked`, and the member's points are all decremented as if the member was paid the full `balance_to_unbond`, but the actual transferred amount is capped lower. This is triggered by ordinary user calls to `withdraw_unbonded` (a public, permissionless-in-many-conditions extrinsic) — no admin/governance/malicious-validator action is required to reach the divergent branch; only chain-state conditions (slashing interactions, staking ledger timing) documented directly in the code's own comments.

### Likelihood Explanation
Medium. The code explicitly anticipates and defends against the mismatch ("defensive in cases where the unbond pool does not update its balance... a bug in the slashing hook"), meaning the divergence is a recognized, reachable condition rather than a purely theoretical edge case, and one very similar instance already occurred in production requiring a manual migration (`pr_11018`). Reproducing it deterministically requires orchestrating specific slashing/era timing interactions between `pallet-staking`(-async)/`pallet-delegated-staking` and `pallet-nomination-pools`, which is nontrivial but has precedent.

### Recommendation
Reorder the logic so that `sub_pools`/`TotalValueLocked`/member accounting are only decremented by the amount actually transferred (`min(balance_to_unbond, transferable_balance)`), not by the full `dissolve()` result; alternatively, if `transferable_balance < balance_to_unbond`, retain the shortfall as a claimable balance for the member (analogous to the trapped-balance migration in `pr_11018`) rather than silently discarding it from all pool bookkeeping.

### Proof of Concept
1. Create a pool and have a member unbond funds into an unbonding sub-pool (`Call::unbond`).
2. Induce a state where `T::StakeAdapter::transferable_balance` (pool account's reducible/delegator balance) is strictly less than the sub-pool's `point_to_balance` computation for the member's points — e.g., via a slashing interaction that updates the underlying staking ledger but not the sub-pool balance in the same block (as explicitly called out in the code comment at line 2489-2491), or via `DelegateStake`'s additional `delegator_balance` cap.
3. Call `Call::withdraw_unbonded` for that member once eligible (`active_era` past `bonding_duration`).
4. Observe: `sub_pools` and `TotalValueLocked` are decremented by the full `balance_to_unbond`; the `Event::Withdrawn` balance and actual `T::Currency`/delegation transfer equal only the capped `transferable_balance`; the delta is unaccounted for in any storage item and unrecoverable by the member or the pool. 	/// Dissolve some points from the unbonding pool, reducing the balance of the pool
	/// proportionally. This is the opposite of `issue`.
	///
	/// Returns the actual amount of `Balance` that was removed from the pool.
	fn dissolve(&mut self, points: BalanceOf<T>) -> BalanceOf<T> {
		let balance_to_unbond = self.point_to_balance(points);
		self.points = self.points.saturating_sub(points);
		self.balance = self.balance.saturating_sub(balance_to_unbond);

		balance_to_unbond
	}
