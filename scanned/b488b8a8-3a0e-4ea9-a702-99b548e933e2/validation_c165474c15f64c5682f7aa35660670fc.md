### Title
`InnerMigrateV1ToV2` seeds `BudgetAllocation` without the 100%-sum/registered-key checks that `set_budget_allocation` enforces, permanently breaking issuance conservation - (File: `substrate/frame/dap/src/migrations.rs`)

### Summary
`pallet_dap::set_budget_allocation` enforces two invariants before writing to `BudgetAllocation`: every key must be a registered `BudgetRecipient`, and the `Perbill` values must sum to exactly `Perbill::one()` (100%). The V1→V2 migration writes to the exact same storage item directly from a runtime-supplied constant, with none of those checks, mirroring the pattern in the external report where a constructor sets a value that only the setter function validates.

### Finding Description
The invariant is declared and enforced in the extrinsic: [1](#0-0) 

But `InnerMigrateV1ToV2::on_runtime_upgrade` seeds `BudgetAllocation` straight from `B::get()` (a `Get<BudgetAllocationMap>` type parameter wired in the runtime) with no sum check and no registered-key check: [2](#0-1) 

Every block, `on_initialize` → `drip_issuance` → `mint_and_distribute` reads `BudgetAllocation` and distributes minted issuance per key using `Perbill::mul_floor(issuance)` — it never re-validates that the map sums to 100%: [3](#0-2) 

If the runtime's `B: Get<BudgetAllocationMap>` constant is misconfigured (e.g. a typo, or the sum accidentally totals more or less than 100%, or includes a stale/unregistered `BudgetKey`), the migration writes this invalid map to storage unconditionally on the `current_budget.is_empty()` branch. There is no on-chain assertion analogous to `do_try_state`/`check_budget_allocation` gating this path in production — that check only runs under the `try-runtime` feature: [4](#0-3) 

Because `mint_and_distribute` performs independent per-key `mul_floor` calls rather than proportionally scaling by the total, a map whose values sum to more than 100% causes the pallet to mint more tokens per drip than `IssuanceCurve::issue` intended (over-minting, i.e., unbacked new supply every block), while a map summing to less than 100% silently under-distributes issuance forever with no error raised. Unlike the Solidity example, this doesn't cause a revert/brick, but it durably corrupts the issuance-conservation invariant that `set_budget_allocation` was specifically designed to guarantee, and the corruption persists across every block until a governance call to `set_budget_allocation` overwrites it (which requires becoming aware of the bug first).

### Impact Explanation
This breaks the "public underpriced work / value conservation" pivot: minted issuance no longer matches the `IssuanceCurve`-derived intended amount, on every block, indefinitely. Over-minting mints unbacked tokens system-wide (a supply-inflation bug); under-minting silently starves budget recipients (e.g. staker-rewards pot) of their designed share. Because the drip runs unconditionally in `on_initialize`, the incorrect distribution is baked into consensus state on every block until manually corrected via governance — a systemic accounting bug analogous to the vault being "bricked" by an unchecked corrupted parameter.

### Likelihood Explanation
This requires a runtime-configuration bug in the `B: Get<BudgetAllocationMap>` type used to instantiate `MigrateV1ToV2` in the actual production runtime (e.g. `asset-hub-westend`) — not privileged governance abuse, but a missing-validation defect in the migration itself, exactly mirroring the external report's "constructor lacks the same guard as the setter" bug class. No malicious actor, validator, or governance abuse is needed; it is a latent code defect that will silently activate the first time the migration runs if the wired constant is ever wrong.

### Recommendation
Have `InnerMigrateV1ToV2::on_runtime_upgrade` validate `B::get()` the same way `set_budget_allocation` does before calling `BudgetAllocation::<T>::put(...)`: verify every key is in `T::BudgetRecipients::recipients()` and that the `Perbill` values sum to exactly `Perbill::one()`, failing loudly (e.g. via `assert!`/`defensive!` panic acceptable at migration time, similar to other genesis-build assertions in this codebase such as `polkadot/runtime/parachains/src/configuration.rs`'s `panic_if_not_consistent()`) rather than silently writing an unchecked map into production storage.

### Proof of Concept
1. Runtime integrator wires `MigrateV1ToV2<T, P, B, M>` with a `B` whose `BudgetAllocationMap` sums to, say, 150% (or omits validation and accidentally double-counts a recipient) — a configuration bug, not a governance/malicious action.
2. Chain performs the runtime upgrade; `on_runtime_upgrade` runs, `current_budget.is_empty()` is true, so `BudgetAllocation::<T>::put(B::get())` writes the invalid 150% map with no check [5](#0-4) .
3. From that block onward, every `drip_issuance` call mints `issuance` split across recipients each via independent `Perbill::mul_floor`, totalling ~150% of the value `IssuanceCurve::issue` intended [6](#0-5) , permanently over-inflating supply until governance notices and calls `set_budget_allocation` to fix it.

		/// Checks that `BudgetAllocation` is consistent:
		/// - Every key in `BudgetAllocation` must be a registered recipient.
		/// - Allocation percentages must sum to exactly 100%.
		fn check_budget_allocation() -> Result<(), sp_runtime::TryRuntimeError> {
			let allocation = BudgetAllocation::<T>::get();

			ensure!(!allocation.is_empty(), "BudgetAllocation is empty");

			let registered: Vec<BudgetKey> =
				T::BudgetRecipients::recipients().into_iter().map(|(k, _)| k).collect();

			// Every allocation key must be a registered recipient.
			for key in allocation.keys() {
				ensure!(
					registered.contains(key),
					"BudgetAllocation contains key not in BudgetRecipients"
				);
			}

			// Allocation must sum to exactly 100%.
			let total_parts: u64 = allocation.values().map(|p| p.deconstruct() as u64).sum();
			ensure!(
				total_parts == Perbill::one().deconstruct() as u64,
				"BudgetAllocation does not sum to 100%"
			);

			Ok(())
		}
