## Vulnerability Analog Found

The Babylon `BtcPoller.Bootstrap` bug is fundamentally about **unbounded/uncharged work being performed on attacker- or environment-controlled input before any accounting or commit happens**. The direct on-chain analog in this repository is in the BEEFY bridge pallet, where a public extrinsic performs real cryptographic verification work (signature checks + MMR proof verification) while being charged **zero weight**, and the only "spam" guard is bypassed for invalid submissions.

### Title
`pallet-bridge-beefy::submit_commitment` performs full signature/MMR verification under `#[pallet::weight(0)]`, allowing unpriced work that can stall block production - (File: `bridges/modules/beefy/src/lib.rs`)

### Summary
`Pallet::submit_commitment` is declared with `#[pallet::weight(0)]`, meaning the extrinsic is charged **no weight and no fee** regardless of the actual computation performed inside it. The function nonetheless does substantial, attacker-triggerable cryptographic work: verifying a BEEFY signed commitment against the full authority set and verifying an MMR leaf proof. The only spam-limiting check (`MaxRequests`) is only ever incremented on a *successful* import, so an unprivileged, signed account can submit an unbounded stream of invalid `submit_commitment` calls, each free of charge in the weight/fee accounting but each consuming real CPU time for signature/proof verification. [1](#0-0) 

### Finding Description
The call is defined as:
```rust
#[pallet::call_index(3)]
#[pallet::weight(0)]
pub fn submit_commitment(
    origin: OriginFor<T>,
    commitment: BridgedBeefySignedCommitment<T, I>,
    validator_set: BridgedBeefyAuthoritySet<T, I>,
    mmr_leaf: Box<BridgedBeefyMmrLeaf<T, I>>,
    mmr_proof: BridgedMmrProof<T, I>,
) -> DispatchResult
``` [2](#0-1) 

Inside, it performs:
1. A `MaxRequests` check against the current stored `RequestCount`.
2. Full BEEFY commitment verification (`utils::verify_commitment`), which iterates the authority set validating signatures.
3. Full MMR leaf proof verification (`utils::verify_beefy_mmr_leaf` → `verify_mmr_leaves_proof`).
4. Only *after* both succeed does it mutate `RequestCount` (the only anti-spam counter). [3](#0-2) 

Because `RequestCount` is only incremented on the success path, the `MaxRequests` guard does nothing to bound the number of failed/invalid submissions an attacker can make. Combined with `#[pallet::weight(0)]`, this means:
- The runtime's weight-based block-fullness accounting sees these transactions as free/instant.
- The transaction-fee mechanism charges nothing, removing the economic disincentive that normally throttles spam.
- The actual work done (elliptic-curve signature verification over an authority set, plus Merkle/MMR proof hashing) is real CPU/time cost that is not reflected anywhere in the weight system.

This is the same broken invariant as the reported Babylon bug: **real, non-trivial processing work is performed without any bound or accounting tied to its cost**, just relocated from "memory consumption in an off-chain indexer" to "CPU time in an on-chain public extrinsic with zero declared weight."

### Impact Explanation
An attacker can craft (or simply resubmit garbage/expired) `submit_commitment` transactions repeatedly. Since each is weighed at `0`, block authors can pack many such calls into a single block believing it is nearly weightless, while actual execution requires real verification time proportional to authority-set size and proof length. This directly matches the required impact category "public underpriced work that degrades block production or stalls bridge processing" — validators/collators can be made to spend real time validating spam commitments that carry no weight cost, and legitimate `submit_commitment` traffic for the BEEFY light client can be starved or delayed, stalling the bridge's finality-tracking pipeline.

### Likelihood Explanation
The call is reachable by `ensure_signed(origin)` — any funded (or even fee-free, since weight is zero and dev-mode fee derivation is affected) account can call it. No privileged role, relayer trust, or governance action is required. The `MaxRequests` check only limits *successful* commitments, not the volume of submitted-but-invalid ones, so there is no effective rate limit on the actual expensive code path (`verify_commitment` / `verify_beefy_mmr_leaf`) being reached repeatedly.

### Recommendation
- Replace `#[pallet::weight(0)]` with a real weight function that charges for signature verification (proportional to `validator_set` size) and MMR proof verification (proportional to `mmr_proof.items.len()`), consistent with how `initialize`/`set_owner` are weighted with `T::DbWeight::get().reads_writes(...)`.
- Move or duplicate the `MaxRequests`/rate-limiting check so that it also throttles failed/invalid submissions, not only successful imports, e.g. by tracking failed-verification attempts per block/account.
- Benchmark `submit_commitment` like other pallet-bridge-* pallets (e.g. `pallet-bridge-messages`, `pallet-bridge-grandpa`) which use size/witness-aware weight functions.

### Proof of Concept
Conceptual PoC (would need to be executed against a runtime with this pallet configured):
1. Deploy/instantiate a chain with `pallet-bridge-beefy` configured with a non-trivial `BridgedChain::MAX_AUTHORITIES_COUNT`.
2. As any signed, unprivileged account, repeatedly call `submit_commitment` with syntactically valid but cryptographically invalid `commitment`/`mmr_proof` data (so it always fails verification and never increments `RequestCount`).
3. Observe: transactions are accepted into the pool and included in blocks with weight cost `0` (verified via `actual_weight`/`pallet::weight(0)` and no fee deduction), while node CPU profiling shows the block executor spending measurable time in `finality_grandpa`/ECDSA signature checks and MMR hashing for each call — demonstrating the underpriced, unbounded work class.

**Caveat/uncertainty**: I was not able to execute this PoC or inspect benchmarked weight files (`weights.rs`) for this pallet within the indexed content to confirm whether a benchmark-derived weight is substituted at runtime configuration time instead of the literal `0`. If a runtime configures a custom `WeightInfo` that overrides call weight outside of what's shown in `#[pallet::weight(0)]`, the practical severity would be reduced. A full Devin session with repo access should check `bridges/modules/beefy/src/weights.rs` (if it exists) and all runtime configs (`Config<I>::WeightInfo`, if such an associated type exists) to confirm no override is in effect before treating this as fully live.

```rust
		#[pallet::call_index(3)]
		#[pallet::weight(0)]
		pub fn submit_commitment(
			origin: OriginFor<T>,
			commitment: BridgedBeefySignedCommitment<T, I>,
			validator_set: BridgedBeefyAuthoritySet<T, I>,
			mmr_leaf: Box<BridgedBeefyMmrLeaf<T, I>>,
			mmr_proof: BridgedMmrProof<T, I>,
		) -> DispatchResult
		where
			BridgedBeefySignedCommitment<T, I>: Clone,
		{
			Self::ensure_not_halted().map_err(Error::<T, I>::BridgeModule)?;
			ensure_signed(origin)?;

			ensure!(Self::request_count() < T::MaxRequests::get(), <Error<T, I>>::TooManyRequests);

			// Ensure that the commitment is for a better block.
			let commitments_info =
				ImportedCommitmentsInfo::<T, I>::get().ok_or(Error::<T, I>::NotInitialized)?;
			ensure!(
				commitment.commitment.block_number > commitments_info.best_block_number,
				Error::<T, I>::OldCommitment
			);

			// Verify commitment and mmr leaf.
			let current_authority_set_info = CurrentAuthoritySetInfo::<T, I>::get();
			let mmr_root = utils::verify_commitment::<T, I>(
				&commitment,
				&current_authority_set_info,
				&validator_set,
			)?;
			utils::verify_beefy_mmr_leaf::<T, I>(&mmr_leaf, mmr_proof, mmr_root)?;

			// Update request count.
			RequestCount::<T, I>::mutate(|count| *count += 1);
			// Update authority set if needed.
