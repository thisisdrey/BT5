Confirmed: `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs` includes `Revive: pallet_revive` in the runtime, and its `ProxyType::NonTransfer` filter (lines 826-849) enumerates a denylist of "transfer-capable" calls — `Balances`, `Assets`, `NftFractionalization`, `Nfts`, `Uniques`, `Scheduler`, `Treasury`, `Vesting::vested_transfer`, `ConvictionVoting`, `Referenda`, `Whitelist` — but never mentions `RuntimeCall::Revive`. This is structurally the same bug class as the report: a hand-maintained allow/deny list of "value-moving" entry points that misses an equivalent alternate path.

### Title
`ProxyType::NonTransfer` proxy filter omits `pallet_revive::Call::call`, letting a non-transfer delegate move the delegator's native balance - (File: `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs`)

### Summary
`ProxyType::NonTransfer` is meant to let a delegate act on behalf of an account for everything *except* moving that account's funds. It is implemented as a denylist of `RuntimeCall` variants: `Balances`, `Assets`, `Nfts`, `Uniques`, `NftFractionalization`, `Scheduler`, `Treasury`, `Vesting::vested_transfer`, `ConvictionVoting`, `Referenda`, `Whitelist`. `pallet_revive` is enabled in this runtime but is not in that denylist, and `pallet_revive::Pallet::call` (extrinsic index 1) explicitly accepts a `value: BalanceOf<T>` that is transferred from `origin` to `dest`. ### Finding Description
`InstanceFilter::filter` is the sole gate `pallet_proxy::Pallet::proxy` uses to decide whether a delegate may execute a call as the real account (via `RuntimeCall::dispatch` under `OriginFor` with the delegator's identity). For `ProxyType::NonTransfer` the filter is a `!matches!(...)` denylist rather than an allowlist, meaning any `RuntimeCall` variant not explicitly named passes through unrestricted. `RuntimeCall::Revive(pallet_revive::Call::call { dest, value, .. })` is exactly such a case: it is a first-class, non-listed variant that moves native balance out of the proxied account to an arbitrary `dest` (either an EOA or a contract), functionally identical to `Balances::transfer`. The filter's intent ("omitting the entire Balances pallet" style comments seen in other runtimes' `NonTransfer` filters) is defeated because the equivalent value-transfer capability re-appears through a differently-named pallet call, exactly mirroring the external report's core flaw: a restriction keyed on a fixed enumeration of "the" transfer functions misses functionally equivalent alternate entry points.

### Impact Explanation
An account owner who grants a `NonTransfer` proxy — expecting the delegate to be unable to move funds — is fully exposed: the delegate can call `Revive::call(dest, value, weight_limit, storage_deposit_limit, data)` directly (proxy calls are not required to be batched via `Utility`, and even if they were, `Utility` batching is separately allowed) and drain the account's transferable balance to any address they control. This directly breaks the stated security guarantee of the `NonTransfer` proxy type and results in unauthorized fund transfer/theft from the real account, satisfying "theft or unbacked mint/unlock" and "unauthorized execution or origin escalation" in the impact gate.

### Likelihood Explanation
No privileged actor, governance, or leaked keys are required — any account that has legitimately granted a `NonTransfer` proxy to a delegate (a normal, encouraged security practice) is affected the moment that delegate is malicious or compromised, which is the exact threat model `NonTransfer` exists to mitigate. The path requires only a standard `pallet_proxy::proxy` extrinsic wrapping a `pallet_revive::call`, with no exotic preconditions.

### Recommendation
Add `RuntimeCall::Revive(..)` (or scope it to specifically deny `pallet_revive::Call::call`/`instantiate`/`instantiate_with_code`, which accept a `value`) to the `ProxyType::NonTransfer` denylist in `asset-hub-westend`'s `InstanceFilter` impl, matching how `Balances`/`Assets`/etc. are already excluded. More robustly, consider converting `NonTransfer` to an allowlist of explicitly vetted safe calls rather than a denylist, so that newly added pallets/calls default to being denied under `NonTransfer` instead of silently permitted.

### Proof of Concept
1. Account `A` grants `ProxyType::NonTransfer` to delegate `D` via `Proxy::add_proxy(D, ProxyType::NonTransfer, delay)`.
2. `D` calls `Proxy::proxy(A, Some(ProxyType::NonTransfer), Box::new(RuntimeCall::Revive(pallet_revive::Call::call { dest: attacker_address, value: A_full_balance, weight_limit: Weight::MAX, storage_deposit_limit: 0, data: vec![] })))`.
3. `ProxyType::NonTransfer::filter` returns `true` for this call because `RuntimeCall::Revive` is absent from the denylist match arm. [1](#0-0) 
4. `pallet_revive::Pallet::call` executes with `origin = A`, transferring `value` from `A` to `attacker_address` (a plain account or attacker-controlled contract), exactly as documented in the extrinsic's own doc-comment ("any value will be transferred"). [3](#0-2) 
5. `A`'s balance is drained despite `A` having explicitly restricted `D` to a `NonTransfer` proxy.
