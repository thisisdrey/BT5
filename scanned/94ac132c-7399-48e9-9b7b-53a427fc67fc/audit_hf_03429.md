# [M] ORDU-1 | Read-only Reentrancy

## Summary
Severity: Medium
Contest weight: 0.0273
Dataset id: 18730
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability is a classic read‑only reentrancy flaw that occurs in the cancelOrder function of the OrderUtils library. The function first performs an external call to orderVault.transferOut, which sends tokens back to the caller, and only afterwards removes the cancelled order from the contract’s internal dataStore. Because the state update (removing the order) happens after the external call, a malicious caller can re‑enter cancelOrder (or another function that ultimately calls transferOut) before the order entry is cleared. By recursively invoking cancelOrder during the transferOut callback, the attacker can trigger the transferOut logic multiple times while the order still appears in the dataStore, resulting in multiple withdrawals of the same funds. This breaks the accounting assumption that each order can be settled only once and that the vault balance reflects the net amount of outstanding orders. The impact is that an attacker can drain tokens from the order vault, effectively causing funds to disappear for honest users and leaving the order in an inconsistent state (the order may appear cancelled in the UI but still be present in storage). The issue manifests whenever a user calls cancelOrder on an order that has a non‑zero balance in the vault; the reentrancy can be triggered by any contract that can receive the transferred tokens and execute code during the callback. It was discovered during a manual audit that examined the ordering of state changes and external calls, noting that the removal of the order occurs after the external call, a pattern known to be vulnerable to reentrancy. The bug can be hard to notice because the UI may show the order as cancelled and the transaction may succeed, yet the underlying storage still contains the order, and the token balance of the vault may be reduced unexpectedly. The proper mitigation is to follow the checks‑effects‑interactions pattern: update the internal dataStore to remove the order before performing the external transferOut call, or use a reentrancy guard to block recursive entry. Conceptually, this belongs to the class of read‑only reentrancy bugs where a contract reads state, makes an external call, and then writes state, allowing the external call to manipulate the contract’s view of its own data. Users may experience symptoms such as receiving a refund of zero tokens when they expect a full amount, seeing their order still listed after cancellation, or noticing that their token balance has decreased without a corresponding transaction. The discrepancy between expected behavior (single refund, order removed) and reality (multiple refunds, order persists) violates the protocol’s financial logic and can be exploited to steal funds.

## Recommendation
Move the removal of the order from the dataStore to before the orderVault.transferOut call.
