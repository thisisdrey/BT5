Target: `HttpRequestPreamble::consensus_deserialize` header-value ASCII/UTF-8 gate (stackslib/src/net/http/request.rs) combined with `PeerHost::from_str` parsing of the Host header specifically. Attacker action: send 'Host: ' followed by a value containing valid ASCII digits and colons crafted to parse as a SocketAddr with port 0 (e.g. '0.0.0.0:0'), then use the resulting `PeerHost::IP(PeerAddress::from_ipv4(0,0,0,0),0)` as the `Host:` value driving any endpoint logic that branches on `PeerHost::hostname()`/`port()` for canonical-tip resolution (e.g. constructing callback URLs or comparing against configured rpc_bind). Preconditions: unauthenticated RPC connection. Call sequence: consensus_deserialize -> value.parse::<PeerHost>() -> PeerHost::IP(..) stored as preamble.host -> any handler using preamble.host.port()==0 or hostname()=='0.0.0.0' as a sentinel could mis-route. Equality/fault: the `PeerHost` value used to authorize/route the request must equal the actual TCP peer identity, not an attacker-supplied Host header value with no cross-check against the socket's real peer address; this test proves no such cross-check exists. Scoped impact: Critical - potential auth-bypass-adjacent confusion if any code path treats Host: as authoritative for peer identity instead of the accepted socket's real address. Proof idea: Rust test in stackslib::net::http constructing an HttpRequestPreamble from a raw socket connected from 8.8.8.8 but with 'Host: 0.0.0.0:0', asserting preamble.host != the actual peer socket address, and grepping call sites that key security decisions on preamble.host rather than the connection's peer address.
