### Title
Reentrancy-protection bypass for value-transferring EVM `CALL`/`transfer`/`send` in pallet-revive — ([File: substrate/frame/revive/src/vm/evm/instructions/contract.rs])

### Summary
The EVM-compatibility `CALL` handling in `pallet-revive` picks the wrong `ReentrancyProtection` mode for the common, real-world case of Solidity `.transfer(amount)` / `.send(amount)` (nonzero value, implicit 2300-gas stipend), leaving these calls with no explicit reentrancy guard even though the pallet's own documentation states that Ethereum's gas-stipend-based reentrancy guarantee "does not automatically hold in revive" and must be "enforce[d] ... explicitly."

### Finding Description
`run_call` in `substrate/frame/revive/src/vm/evm/instructions/contract.rs` decides the reentrancy mode with: [1](#0-0) 

```
let (add_stipend, reentracy) =
    match (value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND))
    {
        (false, _) => (true, ReentrancyProtection::AllowReentry),
        (_, true) => (true, ReentrancyProtection::AllowNext),
        (_, _) => (false, ReentrancyProtection::AllowReentry),
    };
```

Per the PR that introduced this table (`prdoc/stable2603/pr_11227.prdoc`), solc emits different gas values for the four ETH-sending styles: [2](#0-1) 

- `target.transfer(amount)` (`amount > 0`) → `gas_limit = 0` (EVM implicitly adds the 2300 stipend)
- `target.send(amount)` (`amount > 0`) → `gas_limit = 0` (implicit stipend)
- `target.transfer(0)` / `target.send(0)` → `gas_limit = 2300` (explicit, compiler-injected)
- `target.call{value: v}(data)` → forwards all remaining gas

Because the match's first arm `(false, _)` catches *every* nonzero-value call regardless of `gas_limit`, the two most common, security-critical patterns — `.transfer(amount)` and `.send(amount)` with `amount > 0` — always fall into `ReentrancyProtection::AllowReentry`. Only the rare, degenerate `transfer(0)`/`send(0)` case (value is zero, `gas_limit == 2300`) gets the explicit `ReentrancyProtection::AllowNext` guard.

The `ReentrancyProtection` enum's own documentation explains why this matters: [3](#0-2) 

```
	/// This is used for calls that transfer value but restrict gas so that the callee only has a
	/// stipend gas amount. In Ethereum that is not sufficient for the callee to make another call.
	/// However, due to gas scale differences that guarantee does not automatically hold in revive
	/// and we enforce it explicitly here.
	AllowNext,
```

The comment makes explicit that the 2300-gas stipend does not, by itself, reliably prevent a callee from making a further external call once metered on revive's weight scale — this is exactly why the `AllowNext` guard was added as compensation. Yet the dispatch logic only wires `AllowNext` to the artificial `value == 0 && gas_limit == 2300` combination, and leaves the actual `.transfer(amount>0)` / `.send(amount>0)` calls — the pattern virtually every Solidity contract relies on for "safe," reentrancy-resistant ETH payouts — on `AllowReentry`, i.e. no explicit reentrancy guard at all. Their safety then depends solely on whether the converted stipend resource budget (`add_stipend = true`) happens to be insufficient for revive-metered execution to perform a reentrant call, which the pallet's own comment says cannot be relied upon.

### Impact Explanation
Countless deployed EVM contracts (and any Solidity contract migrated/redeployed onto a `pallet-revive`-based chain) use `.transfer()`/`.send()` specifically because they assume the stipend blocks reentrancy. If the converted stipend weight budget in revive turns out to be sufficient to re-enter (which the code's own comment states is a real risk due to gas-scale differences), an attacker-controlled receiving contract can reenter the caller during a value payout — enabling classic reentrancy drains (double-withdrawal, unbacked balance credit, duplicate settlement) inside the EVM/PVM contract execution layer of a Substrate-based chain, all through a normal user-facing contract call with no privileged access, node compromise, or governance action required.

### Likelihood Explanation
The path is reachable by any unprivileged account calling any deployed EVM-compatible contract that performs `.transfer()` or `.send()` — one of the most common ETH-payout idioms in Solidity. No special permissions, malicious relayer/validator, or governance action is required; only a normal `eth_transact`/`call` extrinsic into a contract with a `.transfer()`/`.send()` sink and an attacker-supplied payee address whose `receive()`/`fallback()` attempts a reentrant call.

### Recommendation
Fix the match logic so that any nonzero-value call carrying an implicit or explicit stipend gas limit (`gas_limit == 0` or `gas_limit == CALL_STIPEND`) is treated uniformly and receives `ReentrancyProtection::AllowNext`, not just the `value == 0` degenerate case. I.e., the reentrancy-guard decision should key off "is this a stipend-style transfer" (any of `gas_limit == 0` or `gas_limit == CALL_STIPEND`) independent of whether `value` happens to be zero, so real `.transfer(amount)`/`.send(amount)` calls get the same explicit `AllowNext` protection that the pallet's own design intends to compensate for revive's differing gas scale.

### Proof of Concept
1. Deploy a victim contract `V` that does `payable(msg.sender).transfer(amount)` (or `.send(amount)`) to pay out a nonzero balance to a user-supplied address, following the standard "checks-effects-interactions" pattern that Solidity developers consider safe specifically because `.transfer`/`.send` are stipend-limited.
2. Deploy an attacker contract `A` whose `receive()` calls back into `V` to trigger another payout/withdrawal before `V`'s state is fully updated (classic reentrancy).
3. Call `V`'s payout function with `A` as recipient. In `run_call`, `value.is_zero() == false`, so regardless of `gas_limit` (0, as solc emits it for `.transfer(amount)`), the arm `(false, _) => (true, ReentrancyProtection::AllowReentry)` is selected — no explicit reentrancy guard is installed for this call.
4. If the pallet's converted stipend weight is enough for `A.receive()` to execute a further external call (the very risk flagged in the `AllowNext` doc comment), `A` reenters `V` and drains funds via duplicate withdrawal, exactly analogous to the `Stipends.sol` `ReentrancyAttacker`/`testTransferReentrancy` scenario in [4](#0-3)  — except here the target is a real payout contract instead of the test fixture, and the guard the code should be applying (`AllowNext`) is not engaged for this nonzero-value/gas_limit=0 path.
