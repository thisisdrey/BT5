## Title
Unbounded/unvalidated Ethereum-controlled `remote_xcm` payload accepted by `snowbridge_pallet_inbound_queue`/`inbound-queue-v2` `submit()` and forwarded verbatim into XCM, bypassing the documented `MaxMessageSize` cap - (`bridges/snowbridge/pallets/inbound-queue/src/lib.rs`, `bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs`)

### Summary
The external report's core invariant is: a caller-supplied variable-length field (`_toAddress`) is packed into a cross-chain payload without any enforced length cap, so it can be blown up beyond what the receiving side can safely process, breaking delivery. The local analog is in Snowbridge's inbound path from Ethereum to BridgeHub/AssetHub: the `Config::MaxMessageSize` type is explicitly documented as being "only used to estimate delivery cost" and is never actually enforced as a bound on the incoming `envelope.payload` / `event.event_log` before it is decoded and transcoded into an XCM program that is forwarded to AssetHub.

### Finding Description
In `snowbridge_pallet_inbound_queue::Pallet::submit` (`bridges/snowbridge/pallets/inbound-queue/src/lib.rs:237-311`), the flow is:
1. Verify the Ethereum event log/proof.
2. Decode `envelope.payload` into `VersionedMessage` with `decode_all` (no length check against `T::MaxMessageSize`).
3. `Self::do_convert(...)` transcodes the message into an `Xcm<()>` via `T::MessageConverter::convert`.
4. `Self::send_xcm(xcm, channel.para_id)` forwards it via `T::XcmSender` (ultimately XCMP/HRMP to AssetHub).

The `MaxMessageSize` config item (`lib.rs:138-139`) is annotated: *"The upper limit here only used to estimate delivery cost"* and is only consumed in `calculate_delivery_cost` / the `Get<BalanceOf<T>>` impl (`lib.rs:343-384`) for a *fee estimate*, never as an `ensure!` guard inside `submit()`. This differs materially from the sibling outbound-queue pallets, which *do* enforce a hard cap before enqueueing: `ensure!(payload.len() < T::MaxMessagePayloadSize::get(), SendError::MessageTooLarge)` (`bridges/snowbridge/pallets/outbound-queue/src/send_message_impl.rs:46-49`, `bridges/snowbridge/pallets/outbound-queue-v2/src/send_message_impl.rs:26-29`).

For the v2 flow, `snowbridge_inbound_queue_primitives::v2::converter::MessageToXcm::convert` (`bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs:375-426`) appends an Ethereum-origin-controlled `message.remote_xcm` directly to the outbound XCM instruction list (`instructions.extend(message.remote_xcm.0)`), with only a decode depth limit (`decode_raw_xcm`, `converter.rs:327-342`) — not a size/instruction-count limit — applied when parsing the raw bytes.

Because the Ethereum Gateway contract's `sendMessage`-style entrypoint is effectively open to be called with large calldata (bounded only by an Ethereum block's gas/calldata limits, which are far larger than what a parachain can safely absorb per HRMP/XCMP page or per-block PoV/weight budget), a relayer can submit a legitimately-proven Ethereum event whose payload decodes successfully but produces an oversized or instruction-heavy XCM program that cannot be delivered or executed within Substrate's messaging constraints (HRMP/XCMP `MaxPageSize`, weight limits enforced by `pallet-message-queue` / `cumulus-pallet-xcmp-queue`).

### Impact Explanation
Unlike the LayerZero bug where an unrecoverable nonce would permanently deadlock a lane, Substrate's `pallet-message-queue` is defensively designed against that exact failure mode (see `substrate/frame/message-queue/src/lib.rs:1550-1630`), classifying failed/oversized messages as *permanently overweight* or *unprocessable* and skipping them instead of blocking the ready ring. That mitigates full channel deadlock. However, the missing enforcement of `MaxMessageSize` in the inbound-queue `submit()` still represents a real gap versus the outbound-queue pattern: it allows public-underpriced/oversized work to be forced through decode → XCM-conversion → `send_xcm` on BridgeHub, at cost only bounded by `T::WeightInfo::submit()` (a fixed benchmark weight, not scaled to the actual payload size actually processed beyond `MaxMessageSize`), and can generate an XCM program whose delivery to AssetHub either fails at `validate_send` (reverting the whole submit, along with the relayer-fee transfer at `lib.rs:269-281` that already executed prior to conversion) or succeeds but cannot be executed on AssetHub, leaving associated reserved/withdrawn/teleported assets referenced in the XCM to be trapped rather than delivered to the intended beneficiary.

### Likelihood Explanation
Exploitation requires only a permissionless relayer able to obtain a valid Ethereum event-log Merkle/receipt proof for a message emitted from the configured Gateway address — no malicious validator, collator, governance actor, or leaked key is needed, satisfying the "unprivileged attacker via public entrypoint" bar. The likelihood is tempered by the fact that the actual Ethereum-side Gateway contract logic (off-repo, in Solidity) may itself constrain payload size before emitting the event; this repository cannot fully confirm whether that external contract enforces the cap that `MaxMessageSize` was clearly intended to represent on the Substrate side. That Solidity-side constraint is outside the scope of this repo, so the missing enforcement here is a code-level defense-in-depth gap regardless.

### Recommendation
Add an explicit `ensure!(envelope.payload.len() <= T::MaxMessageSize::get(), Error::<T>::InvalidPayload)` (v1) and an analogous check on `event.event_log`/decoded `Message` size (v2, `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs::submit`/`process_message`) before decoding/conversion, mirroring the guard already present in the outbound-queue pallets. Additionally, bound the size/instruction count of `remote_xcm` in `converter.rs` independent of decode depth, and ensure `T::WeightInfo::submit()` weight scales with actual decoded/converted payload size rather than a fixed benchmark constant.

### Proof of Concept
Not independently reproducible purely from this repository since the trigger requires an Ethereum-side event emission (Gateway contract, off-repo) with an oversized payload plus a valid consensus/receipt proof; however, the missing guard is directly demonstrable by reading `submit()` end-to-end (`bridges/snowbridge/pallets/inbound-queue/src/lib.rs:237-311`) and confirming no code path calls `T::MaxMessageSize::get()` other than the fee-estimation helper (`lib.rs:343-384`), in contrast to the explicit `ensure!(payload.len() < T::MaxMessagePayloadSize::get(), SendError::MessageTooLarge)` guard enforced on the *outbound* path (`bridges/snowbridge/pallets/outbound-queue/src/send_message_impl.rs:44-49`).
```rust
	/// Parse and (non-strictly) decode `raw` XCM bytes into a `Xcm<()>`.
	/// If decoding fails, return an empty `Xcm<()>`—thus allowing the message
	/// to proceed so assets can still be trapped on AH rather than the funds being locked on
	/// Ethereum but not accessible on AH.
	fn decode_raw_xcm(raw: &[u8]) -> Xcm<()> {
		let mut data = raw;
		if let Ok(versioned_xcm) =
			VersionedXcm::<()>::decode_with_depth_limit(MAX_XCM_DECODE_DEPTH, &mut data)
		{
			if let Ok(decoded_xcm) = versioned_xcm.try_into() {
				return decoded_xcm;
			}
		}
		// Decoding failed; allow an empty XCM so the message won't fail entirely.
		Xcm::new()
	}
```
