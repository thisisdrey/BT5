Based on the evidence gathered, I can identify a concrete local analog in the Snowbridge outbound queue v2 delivery-receipt/reward-settlement flow.

### Title
`submit_delivery_receipt` pays relayer reward without validating message `success` status, decoupling payout from actual delivery outcome - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The external report's core broken invariant is: a state-tracking variable (`minimumContractBalance`) is decremented using the wrong reference value (`avaxDepositAmount` instead of `avaxRedemptionAmount`), so the accounting state no longer reflects the actual amount that should have been settled, leading to DoS. The generalizable bug class is: **settlement/payout logic advances or transfers value based on a value that does not correctly reflect the actual verified outcome of the underlying operation.**

### Finding Description
In `Pallet::<T>::process_delivery_receipt` [1](#0-0) , the pallet decodes a `DeliveryReceipt` (built from an Ethereum event log via `TryFrom<&Log>` in `bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs`) which explicitly carries a `success: bool` field indicating whether the message dispatch succeeded on Ethereum [2](#0-1) .

However, `process_delivery_receipt` only checks `receipt.gateway` against `T::GatewayAddress::get()`, fetches the `PendingOrder` by `nonce`, and unconditionally pays out `order.fee` to the reward account whenever `order.fee > 0` — it never inspects `receipt.success` before calling `T::RewardPayment::register_reward` [3](#0-2) . The order is then unconditionally removed from `PendingOrders`, closing out the settlement regardless of whether the message actually executed successfully on the destination chain.

This means the accounting invariant "reward settles only if delivery succeeded" is never actually enforced by state — the `success` field decoded straight from the Ethereum log is dead data with respect to the payout path. This mirrors the Ignite bug's pattern of using the wrong/irrelevant value (or omitting the correct discriminating value) when finalizing a payout/state update, rather than the value that reflects the actual settlement outcome.

### Impact Explanation
Under the "Required Impacts" gate, this qualifies as duplicate/incorrect settlement: a relayer submitting a valid delivery receipt proof for a message that failed on Ethereum (`success = false`) still collects the full relayer reward fee from `T::RewardPayment`, exactly as if the message had succeeded. Because `PendingOrders` is removed on any accepted receipt regardless of `success`, there is no separate accounting path or clawback for failed deliveries — the fee is paid unconditionally once gateway and nonce validate. This is unbacked/incorrect reward payout logic reachable by any unprivileged relayer submitting a legitimate proof of a legitimately failed message, not requiring a malicious relayer/prover — the message itself may have failed for benign on-chain reasons (e.g., insufficient gas, revert in command execution) unrelated to relayer honesty.

### Likelihood Explanation
High: any relayer that submits a delivery receipt for a message that reverted or failed during Ethereum-side execution will still be rewarded, since `success` is decoded but not branched on. This does not require a malicious peer, node, or validator — it is triggered by ordinary/routine failed message execution on Ethereum (e.g., out-of-gas dispatch), a common occurrence, combined with an honest relayer simply calling the existing public extrinsic path.

### Recommendation
Branch on `receipt.success` in `process_delivery_receipt`: only call `T::RewardPayment::register_reward` when `receipt.success == true`; for `success == false`, either withhold/reduce the reward, or route it to a distinct failed-delivery accounting path, before removing the `PendingOrder`. Add a regression test asserting no `RewardRegistered` event is emitted (or a reduced amount is emitted) when `receipt.success` is `false`.

            topic: H256::zero(),

            reward_address: [0u8; 32],

            pallet_bridge_relayers::Event::RewardRegistered { .. }
        ));
        // Order is removed regardless of success, closing the settlement permanently.
        assert!(PendingOrders::<Test>::get(nonce).is_none());
    });
}

				receipt.reward_address.into()

			if order.fee > 0 {
				// Pay relayer reward

					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });
