### Title
Donation attack on `pallet-asset-conversion` pools — raw pool-account balance used as reserve lets anyone skew LP minting and swap pricing - ([File: substrate/frame/asset-conversion/src/lib.rs])

### Summary
`pallet-asset-conversion` computes pool "reserves" by directly reading the raw asset balance of the deterministic pool account (`get_reserves`/`get_balance`), rather than tracking reserves as an internal, mint-gated accounting value. Because the pool account address is derivable by anyone from the public `PoolLocator::address`/`pool_address` functions, an attacker can transfer assets straight into the pool account (bypassing `add_liquidity`) to inflate the reserve figures used for LP-token minting and swap-price quoting. This mirrors the Lido `LidoMevTxFeeVault` bug: value sent to an address that isn't gated by the contract's own deposit accounting function can distort the derived price/share ratio.

### Finding Description
`do_add_liquidity` reads `reserve1`/`reserve2` via `Self::get_balance(&pool_account, asset)` [1](#0-0) , and uses these reserves both to compute the "optimal" amount via `quote()` and to compute the LP tokens to mint via `mul_div(&amount, &total_supply, &reserve)` [2](#0-1) . The `get_reserves` view function used for swap pricing (`quote_price_exact_tokens_for_tokens`, `get_amount_out`/`get_amount_in`) reads the same raw balances [3](#0-2) .

The pool account address is not secret or access-controlled — it is a deterministic hash of the pool id, exposed through the public `PoolLocator::address`/`pool_address` trait methods [4](#0-3) [5](#0-4) . Any account can therefore call the underlying asset pallet's own `transfer` (e.g. `pallet-balances::transfer` or `pallet-assets::transfer`) to move funds straight into the pool account — completely outside of `add_liquidity`, `remove_liquidity`, or `swap_*` — with no LP tokens minted and no protocol-level restriction. This is the exact analog of the Lido report: the vault/pool account accepts value from any address, and that unaccounted value is then folded into the price/share (LP token / swap-rate) calculation as if it were legitimate.

There is direct project evidence that the maintainers themselves recognize this "unaccounted balance in the pool account" class of issue: PR 12408 changed reserve reads to "use full balances for pool prices" specifically because "reducible balances... could understate pool reserves when protected funds or unrelated non-sufficient assets were held in the pool account" [6](#0-5) . This confirms the pool's reserve value is fundamentally derived from whatever happens to sit in the pool account's balance rather than an internally reconciled ledger — which is precisely the invariant an unauthorized-donation attack exploits.

### Impact Explanation
- **LP mint dilution / share-price manipulation**: an attacker can donate one or both assets to an existing pool account right before a legitimate `add_liquidity` call. Because `reserve1`/`reserve2` are inflated by the donation while `total_supply` (LP token issuance) is unaffected, the `mul_div(&amount, &total_supply, &reserve)` computation returns fewer LP tokens than the depositor should be entitled to for the value they contribute, effectively transferring value to existing LP holders (or, depending on timing, letting the attacker later manipulate `remove_liquidity` payouts since `do_remove_liquidity` also reads `get_reserves` from the raw balance) [7](#0-6) .
- **Swap price manipulation**: `quote_price_exact_tokens_for_tokens`/`quote_price_tokens_for_exact_tokens`, used by wallets and by `pallet-asset-conversion-tx-payment` for fee conversion, rely on the same manipulable reserve figures, so a donation can skew quoted exchange rates presented to users or used for on-chain fee payment logic.
- **First-liquidity griefing**: an attacker can pre-fund a freshly created, empty pool account with a disproportionate donation before the deployer's first `add_liquidity`, corrupting the `reserve1.is_zero() || reserve2.is_zero()` branch logic and the resulting price used to compute `amount2_optimal`/`amount1_optimal`, causing unexpected `AssetOneDepositDidNotMeetMinimum`/`AssetTwoDepositDidNotMeetMinimum` failures or unfavorable pricing for the legitimate first LP.

This falls squarely in the "asset accounting" / "conserve value and settle exactly once to the rightful beneficiary and amount" impact category from an unprivileged, no-special-access attacker, matching the required impact gate.

### Likelihood Explanation
Likelihood is high: no privileged role, governance, relayer, or validator collusion is required. The attacker only needs to know the pool id (public) to derive the pool account address (deterministic, publicly computable) and issue an ordinary `transfer` extrinsic on the underlying asset pallet. This requires no calling into `pallet-asset-conversion` at all, so none of its existing guards (`ensure_signed`, `WrongDesiredAmount`, `AmountOneLessThanMinimal`, etc.) ever execute against the donation.

### Recommendation
Track reserves as pallet-internal accounting state (e.g., a `Reserves` storage item updated only by `do_add_liquidity`/`do_remove_liquidity`/swap execution) instead of reading the pool account's live balance for `get_balance`/`get_reserves`. Alternatively, reconcile any balance in excess of the tracked reserve into the LP token supply proportionally (protocol-level "skim"/"sync" function, as some Uniswap-style AMMs implement) rather than silently letting it distort minting and pricing math for existing users. At minimum, document and test that unauthorized transfers into the pool account are the operator's/protocol's responsibility to sweep, and that pricing/minting should be based on reconciled reserves, not raw balance queries.

### Proof of Concept
1. Attacker computes `pool_account = PoolLocator::address(pool_id)` for an existing `asset1/asset2` pool (deterministic, public function).
2. Attacker calls `pallet_assets::transfer` (or `pallet_balances::transfer` for the native asset) to send `asset1` directly to `pool_account`, bypassing `add_liquidity` entirely.
3. `Pools::<T>::get(pool_id)` and LP token `total_issuance` are unchanged, but `Self::get_balance(&pool_account, asset1)` now reports the inflated value.
4. A legitimate LP provider calls `add_liquidity`; `do_add_liquidity` computes `reserve1`/`reserve2` from the now-inflated balances and mints `lp_token_amount = min(side1, side2)` using `mul_div(&amount, &total_supply, &reserve)` — the provider receives fewer LP tokens than their contribution is worth relative to the true (pre-donation) pool value, and/or `quote_price_exact_tokens_for_tokens` returns a skewed swap rate to any external caller [8](#0-7) .

pub trait PoolLocator<AccountId, AssetKind, PoolId> {
	/// Retrieves the account address associated with a valid `PoolId`.
	fn address(id: &PoolId) -> Result<AccountId, ()>;
	/// Identifies the `PoolId` for a given pair of assets.
	///
	/// Returns an error if the asset pair isn't supported.
	fn pool_id(asset1: &AssetKind, asset2: &AssetKind) -> Result<PoolId, ()>;
	/// Retrieves the account address associated with a given asset pair.
	///
	/// Returns an error if the asset pair isn't supported.
	fn pool_address(asset1: &AssetKind, asset2: &AssetKind) -> Result<AccountId, ()> {
		if let Ok(id) = Self::pool_id(asset1, asset2) {
			Self::address(&id)
		} else {
			Err(())
		}
	}
