### Title
Underpriced/zero remote-fee acceptance in Snowbridge outbound-queue `calculate_fee` due to unit-scale mismatch - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
The external report's core broken invariant is: a function that is documented/expected to always charge a proportionate non-zero bond/fee can, through an alternate code path, silently return zero, weakening the economic incentive the fee/bond exists to enforce. The local analog is in `pallet-snowbridge-outbound-queue`'s `calculate_fee`, which is meant to compute a strictly positive `Fee.remote` that covers the cost of dispatching a command on Ethereum, but a documented unit-scale bug in the FixedU128 conversion can round `Fee.remote` down to `0` for legitimate, non-zero `PricingParameters`, allowing free/underpriced remote-execution work to be queued into the bridge.

### Finding Description
`Pallet::<T>::calculate_fee` at [1](#0-0)  computes the remote fee as:

1. `calculate_remote_fee` returns a raw `U256` value `fee_per_gas * gas_used_at_most + reward` (wei-denominated integer), at [2](#0-1) .
2. That raw integer is downcast to `u128` and then wrapped with `FixedU128::from_inner(fee)`, treating the raw wei integer as if it were *already* a fixed-point value scaled by `10^18` — i.e. it silently divides the true fee by `10^18` before any deliberate decimal conversion happens.
3. It is then multiplied by `params.multiplier` and divided by `params.exchange_rate`, and the result is passed through `convert_from_ether_decimals`, which does a second decimal-scale division based on `ETHER_DECIMALS - T::Decimals::get()` at [3](#0-2) .

Because of this compounding scale error, a low (but non-zero, governance-set) `fee_per_gas`/`reward` combined with an attacker-chosen `Command` that has low `gas_used_at_most` (from `T::GasMeter::maximum_gas_used_at_most`, driven by the specific `Command` the caller submits through `SendMessage::validate`, see [4](#0-3) ) causes the final `fee.remote` to be rounded to exactly `0` while the local fee remains non-zero. This is confirmed by the pallet's own test, which explicitly documents the invalid zero output with non-zero pricing parameters: [5](#0-4) 

This is functionally identical to the UMA bug class: one code path (`requestPrice`) enforces a proper non-zero economic charge by default, while a sibling/related computation path (`requestAndProposePriceFor` / here, `calculate_fee`) can silently produce a zero value that contradicts the documented intent ("Calculate total fee ... to cover all costs of delivering a message to the remote destination"), undermining the very cost-recovery mechanism the fee exists to guarantee.

### Impact Explanation
`Fee.remote` (see `Fee<Balance>` struct [6](#0-5) ) is the amount that sending parachains/users are expected to pay to cover Ethereum-side dispatch costs and relayer rewards for a message queued via `SendMessage::validate`/`deliver` [7](#0-6) . If `calculate_fee` returns `remote = 0` while the message still consumes real bridge/relayer resources on delivery, callers get "public underpriced work": messages are accepted into the outbound queue and eventually delivered/dispatched on Ethereum without the sender paying the true remote cost. This can be abused to spam the bridge queue cheaply, stalling honest message processing and leaving relayer rewards unfunded — directly matching the in-scope impact category "public underpriced work that degrades block production or stalls bridge processing."

### Likelihood Explanation
Likelihood is moderate: it requires no privileged actor, malicious relayer, or governance abuse — any ordinary account that can invoke bridge message sending (e.g. via XCM export to Ethereum) with a command whose `gas_used_at_most` is small enough triggers the rounding-to-zero condition under realistic, governance-configured `PricingParameters` (as demonstrated by the pallet's own unit test with non-degenerate parameters). The bug is inherent to the fee-calculation math rather than to adversarial parameter choice, so it can occur under normal operating parameters, not just contrived edge cases.

### Recommendation
Fix the unit handling in `calculate_fee`: convert the wei-denominated `U256` remote-fee value into a proper `FixedU128` fraction (e.g., via `FixedU128::from_rational` against `10^18`) instead of reinterpreting the raw integer with `from_inner`, and add an explicit guard (analogous to using the "default"/non-zero final fee in the UMA fix) that rejects or floors the computed `fee.remote` to a minimum charge when the true value is non-zero but rounds to zero, so that no message can be accepted for delivery with an under-priced or zero remote fee.

### Proof of Concept
The existing regression test in the repository already reproduces the exact defect: [5](#0-4) 
With `exchange_rate = 1/1`, `fee_per_gas = 1`, `rewards = {local: 1, remote: 1}`, `multiplier = 1`, and `gas_used = 250000`, `OutboundQueue::calculate_fee` yields `fee.remote == 0` even though all pricing parameters are non-zero. An attacker only needs to (1) pick/construct a `Command` whose `GasMeter::maximum_dispatch_gas_used_at_most` is small, and (2) call the public `SendMessage::validate`/`deliver` path (e.g. through the XCM bridge exporter that ultimately uses this queue) to have their message queued for remote delivery while paying `0` remote fee, confirming the underpriced-work path is reachable without any privileged or malicious-infrastructure precondition.

			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}
