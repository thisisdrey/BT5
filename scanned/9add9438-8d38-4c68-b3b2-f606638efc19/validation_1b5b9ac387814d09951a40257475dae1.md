### Title
Unbounded Ethereum receipts-trie proof in Snowbridge inbound-queue `submit`/permissionless verification allows underpriced resource consumption - ([File: bridges/snowbridge/primitives/verification/src/receipt.rs])

### Summary
The `Proof` struct used by Snowbridge's inbound queue verifier carries an untrusted `receipt_proof: Vec<Vec<u8>>` with no length or per-node size bound, unlike other proof types in the same codebase (e.g. the relay-chain `Proof` type in `polkadot/node/primitives/src/lib.rs`, which explicitly enforces `MERKLE_PROOF_MAX_DEPTH`/`MERKLE_NODE_MAX_SIZE`). `verify_receipt_proof` performs a Merkle-Patricia-Trie walk plus RLP decoding over every supplied node, so its cost scales with the number and size of nodes an attacker chooses to submit, while the dispatch is exposed through a permissionless, signed `submit` extrinsic.

### Finding Description
`Proof` is defined as: [1](#0-0) 
with `receipt_proof: Vec<Vec<u8>>` — a plain, unbounded `Vec` of `Vec<u8>` nodes.

`verify_receipt_inclusion` forwards this untrusted vector directly into `verify_receipt_proof`: [2](#0-1) 

`verify_receipt_proof` iterates over every node in the caller-supplied `proof` slice, converts each into a `Bytes`, and runs `alloy_trie::proof::verify_proof`, which recursively decodes and hashes each trie node before falling through to an RLP decode of the extracted receipt: [3](#0-2) 

Unlike the beacon-chain Merkle proofs used elsewhere in the same pallet (e.g. `verify_execution_proof`/`verify_ancestry_proof`), which enforce `branch.len() == depth` for a *fixed* `depth` derived from consensus constants: [4](#0-3) 
the receipt trie proof has no equivalent bound on the number of nodes or on individual node size before the expensive walk/decode begins. Compare this to the relay chain's own `Proof` type, which was explicitly hardened against exactly this class of issue via `MERKLE_PROOF_MAX_DEPTH`/`MERKLE_NODE_MAX_SIZE` checks on `Decode`: [5](#0-4) 

This absence of a bound means an attacker who can reach the inbound-queue's public verification path (any signed account, since bridge messages are relayed by whoever submits them, and the pallet's tests show the verifier is exercised directly by unprivileged/attacker-controlled input, e.g. `poc_permissionless_forged_receipt_bypasses_verifier_and_injects_xcm`) can supply a `receipt_proof` containing many, or large, spurious nodes. The verification work (trie node decoding + hashing + RLP receipt decode) is proportional to the caller-chosen input rather than to any consensus-bounded quantity, and — because the dispatchable's declared weight is derived from benchmarking against "typical" proof shapes rather than a size-scaled parameter (unlike, e.g., `pallet-bridge-grandpa`'s `submit_finality_proof`, which explicitly weights on `precommits.len()`/`votes_ancestries.len()`), the cost of processing an inflated proof is not proportionally charged.

### Impact Explanation
This falls under "public underpriced work that degrades block production or stalls bridge processing." An attacker can submit inbound-queue messages with bloated, unbounded `receipt_proof` vectors that consume disproportionate CPU/PoV during proof verification relative to the fee/weight charged for the extrinsic, degrading block production time on BridgeHub and potentially stalling legitimate bridge message processing — directly analogous to the jose2go "uncontrolled resource consumption due to improper input validation" report, where unvalidated/unbounded input drives excessive parsing work.

### Likelihood Explanation
Likelihood is bounded by extrinsic/transaction size limits (the whole call must still fit within `max_extrinsic_size`), so this is not unlimited, but no additional check exists to keep proof shape close to the "expected" small number of small nodes a legitimate Ethereum receipts-trie proof has. Any signed account can submit such a call without needing to control a validator, collator, relayer, or governance key, satisfying the "unprivileged attacker" requirement.

### Recommendation
Bound `Proof::receipt_proof` similarly to the hardened relay-chain `Proof` type: introduce a `BoundedVec<BoundedVec<u8, MaxNodeSize>, MaxProofDepth>` (or an equivalent `TryFrom`/custom `Decode` check) with limits derived from realistic Ethereum receipts-trie depth/node-size bounds, and/or scale the `submit` extrinsic's declared weight by the actual size/length of `receipt_proof` (as `pallet-bridge-grandpa` does for `precommits`/`votes_ancestries`) so the fee reflects the real verification cost.

### Proof of Concept
1. Construct a legitimate `EventProof`/beacon execution proof so `verify_execution_proof` passes (reusing the pattern from `make_inbound_fixture`).
2. Replace `proof.receipt_proof` with a `Vec<Vec<u8>>` containing many large, syntactically-valid-but-spurious trie node byte strings (e.g. thousands of ~few-hundred-byte pseudo full/extension nodes) sized to approach the extrinsic length limit, rather than the small number of nodes a real trie proof requires.
3. Submit via the pallet's public `submit` extrinsic from any signed account.
4. Observe that `verify_receipt_proof` performs trie-node RLP decoding/hashing across all supplied nodes before failing verification, while the extrinsic is charged the fixed/benchmarked weight for `submit`, not one scaled to the inflated proof size — demonstrating the cost/charge mismatch. (Note: full execution-time confirmation would require running this against the actual runtime/benchmark harness, which is outside the scope of this static analysis.)

pub fn verify_receipt_proof(
	receipts_root: H256,
	tx_index: u64,
	proof: &[Vec<u8>],
) -> Option<ReceiptEnvelope> {
	let key = receipt_trie_key(tx_index);
	let root = B256::from_slice(receipts_root.as_bytes());
	let proof_nodes: Vec<Bytes> = proof.iter().map(|node| Bytes::copy_from_slice(node)).collect();

	// Call verify_proof with None to extract the value from an inclusion proof. For inclusion
	// proofs, alloy_trie returns ValueMismatch with the extracted value in `got`. The proof is
	// already cryptographically verified during this traversal.
	let value = match verify_proof(root, key, None, proof_nodes.iter()) {
		Ok(()) => return None, // Exclusion proof - key does not exist
		Err(ProofVerificationError::ValueMismatch { path, got: Some(v), expected: None })
			if path == key =>
		{
			v.to_vec()
		},
		Err(_) => return None,
	};

	ReceiptEnvelope::decode(&mut value.as_slice()).ok()
}

impl TryFrom<Vec<Vec<u8>>> for Proof {
	type Error = MerkleProofError;

	fn try_from(input: Vec<Vec<u8>>) -> Result<Self, Self::Error> {
		if input.len() > MERKLE_PROOF_MAX_DEPTH {
			return Err(Self::Error::MerkleProofDepthExceeded(input.len()));
		}
		let mut out = Vec::new();
		for element in input.into_iter() {
			let length = element.len();
			let data: BoundedVec<u8, 1, MERKLE_NODE_MAX_SIZE> = BoundedVec::from_vec(element)
				.map_err(|_| Self::Error::MerkleProofNodeSizeExceeded(length))?;
			out.push(data);
		}
		Ok(Proof(BoundedVec::from_vec(out).expect("Buffer size is deterined above. qed")))
	}
}

impl Decode for Proof {
	fn decode<I: Input>(value: &mut I) -> Result<Self, CodecError> {
		let temp: Vec<Vec<u8>> = Decode::decode(value)?;
		let mut out = Vec::new();
		for element in temp.into_iter() {
			let bounded_temp: Result<BoundedVec<u8, 1, MERKLE_NODE_MAX_SIZE>, CodecError> =
				BoundedVec::from_vec(element)
					.map_err(|_| "Inner node exceeds maximum node size.".into());
			out.push(bounded_temp?);
		}
		BoundedVec::from_vec(out)
			.map(Self)
			.map_err(|_| "Merkle proof depth exceeds maximum trie depth".into())
	}
}
