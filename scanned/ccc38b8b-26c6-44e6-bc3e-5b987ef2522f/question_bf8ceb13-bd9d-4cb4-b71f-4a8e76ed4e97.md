The `wallet` contract family's `WalletImpl::execute_signed` (`contracts/wallet/src/contract.rs`) checks `msg.signer_id != env::current_account_id()` and commits `self.0.nonces.commit(msg.nonce, msg.created_at, msg.timeout)` BEFORE verifying `S::verify_request_msg(&self.0.public_key, &msg, proof)`. Does a `RequestMessage` with an INVALID `proof` (wrong signature) still consume/commit the nonce (`msg.nonce`) even though the request is ultimately rejected via `Err(Error::InvalidSignature)`, i.e. can an attacker who observes/guesses a victim's not-yet-broadcast `nonce`+`created_at`+`timeout` pre-commit that nonce with a garbage `proof` to grief the victim's LEGITIMATE subsequently-broadcast request (using the same nonce) into `NonceUsed`/expired rejection? Impact: High — griefing a specific victim's authorized request without attacker profit is normally excluded, but here it blocks a SPECIFIC signed authorization from ever settling, which is a `REPLAY`-adjacent binding failure (`nonce commits without valid signature`). Proof: `cargo test`/sandbox test committing a nonce via `w_execute_signed` with a bad `proof`, then submit the SAME `msg.nonce` with the CORRECT `proof` and assert whether it is rejected due to prior (invalid-signature) commit.
