## Title
Permissionless `claim_bounty` can silently drop payout/fee transfers while irreversibly clearing bounty state, permanently locking treasury/bounty funds - (File: `substrate/frame/bounties/src/lib.rs`)

### Summary
The Compound COMP bug in the external report is caused by code that assumes a transfer step "cannot fail" (or is permissionless and safe), so it finalizes bookkeeping regardless of the transfer's real outcome, letting funds get stranded with no recovery path. The Bounties pallet's `claim_bounty` extrinsic reproduces this exact pattern: it is callable by *any* signed account, computes `payout`/`final_fee` from the bounty account's balance, performs `T::Currency::transfer` calls whose results are only checked via `debug_assert!` (a no-op in production/release builds), and then unconditionally deletes the bounty record (`*maybe_bounty = None`) and its description in the same call, regardless of whether the transfers actually succeeded.

### Finding Description
`claim_bounty` in `substrate/frame/bounties/src/lib.rs` is dispatched by `ensure_signed(origin)?; // anyone can trigger claim`, i.e. no permission check ties the caller to the bounty's curator or beneficiary. [1](#0-0) 

Inside the mutation, the payout and curator fee are transferred out of `bounty_account`, but the results are discarded:
```rust
let res =
    T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath); // should not fail
debug_assert!(res.is_ok());
let res =
    T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath); // should not fail
debug_assert!(res.is_ok());

*maybe_bounty = None;

BountyDescriptions::<T, I>::remove(bounty_id);
T::ChildBountyManager::bounty_removed(bounty_id);
``` [2](#0-1) 

`debug_assert!` compiles to nothing when `debug_assertions` are disabled, which is the case for release/production runtime builds used by real chains. This means the code's "should not fail" comment is not actually enforced: if the transfer to `beneficiary` errors (e.g. `payout` is below the existential deposit and the beneficiary account doesn't exist, or the beneficiary account is frozen/blocked), the transfer silently fails, yet `*maybe_bounty = None` and `BountyDescriptions::remove` still execute unconditionally in the same call — the same call that computed the corrupted assumption of success. The `Bounties` storage entry (the only pointer that ties `bounty_account`'s remaining balance to a payout obligation) is destroyed, and the value stuck in `bounty_account` becomes permanently unreachable by any dispatchable: there is no other extrinsic that lets governance or anyone sweep an orphaned bounty account once its `BountyIndex` entry is gone (contrast with `close_bounty`, which explicitly calls `T::TransferAllAssets::force_transfer_all_assets` only while the bounty entry still exists). [3](#0-2) 

This mirrors the H-01 broken invariant precisely: a public, unprivileged entry point performs value movement whose success is assumed rather than checked, and finalizes irreversible bookkeeping in the same step, so funds become permanently stuck with no legitimate way to reclaim them short of a runtime upgrade/governance intervention.

### Impact Explanation
Any unprivileged account can call `claim_bounty` once a bounty enters `PendingPayout` and the payout delay has elapsed. If the beneficiary account has no existing balance and `payout` is smaller than the chain's existential deposit (a condition entirely reachable through normal bounty parameterization, e.g. small bounty amounts or a large curator fee leaving a small residual payout), the `beneficiary` transfer fails, but the bounty is deleted anyway. The residual DOT/KSM-equivalent value remains in the un-trackable `bounty_account` forever — a direct, permanent loss of treasury-sourced funds, matching the "permanent user-fund lock" impact class called out in the required impacts.

### Likelihood Explanation
The trigger condition (payout below ED, or the destination transfer failing for any other terminal reason) is fully reachable by an ordinary user setting bounty/fee parameters, and the call itself requires no privilege (`ensure_signed` only) — no malicious validator, relayer, or governance actor is needed. The bug is latent in every production build because `debug_assert!` never fires outside debug/test builds.

### Recommendation
Do not use `debug_assert!` to gate on the success of value-moving operations. Propagate transfer errors with `?` (or explicitly handle/refund on failure) before mutating `*maybe_bounty = None` and removing `BountyDescriptions`, so that bookkeeping is only finalized after the transfers are confirmed to have succeeded — analogous to the report's recommendation to avoid relying on unchecked balance assumptions.

### Proof of Concept
1. Create and fund a bounty; have the council `award_bounty` to a fresh `beneficiary` account with zero balance.
2. Set `curator_fee` such that `payout = balance.saturating_sub(fee)` is smaller than `ExistentialDeposit`.
3. Wait past `unlock_at`, then have any signed account call `claim_bounty(origin, bounty_id)`.
4. In a release build (`debug_assertions` disabled), `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` returns `Err` (deposit below ED) but is ignored; `*maybe_bounty = None` and `BountyDescriptions::remove` still execute, and `Event::BountyClaimed` is emitted despite the beneficiary never receiving funds.
5. `payout` worth of tokens remain locked in `bounty_account` with no `Bounty` entry referencing it and no dispatchable capable of recovering it.
