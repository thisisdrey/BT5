Found it: `process_delivery_receipt` in `outbound-queue-v2` never checks that the `DeliveryReceipt.topic` matches the `topic` (message id) that was actually committed for the `PendingOrder` at that `nonce`. This is the direct structural analog of the beacon-kit bug: a companion field (`topic`, analogous to `BeaconBlockHeader`) is carried in the verified envelope but never cross-checked against the entity it is supposed to correlate with (the `OutboundMessage.topic` stored when the order was created), so only the attacker-supplied `nonce` binds the receipt to state.

### Title
`process_delivery_receipt` accepts any `topic`/success value without binding it to the committed `OutboundMessage`, allowing reward claims decoupled from the actual delivered message - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`Pallet::process_delivery_receipt` (called from `submit_delivery_receipt`) looks up a `PendingOrder` purely by `receipt.nonce` and pays out the reward, but never verifies that `receipt.topic` (and `receipt.success`) correspond to the `OutboundMessage` that was actually committed under that nonce in `Messages`/`MessageLeaves`. [1](#0-0) 

### Finding Description
When an XCM message is exported to Ethereum, `do_process_message` builds an `OutboundMessage { origin, nonce, topic: id, commands }`, computes the committed hash from `OutboundMessageWrapper` (which includes `origin`, `nonce`, `topic`, `commands`), and stores a `PendingOrder { nonce, fee, block_number }` keyed only by `nonce` — note the order itself does **not** retain the `topic`/`origin`/`commands` that were committed. [2](#0-1) 

Later, `submit_delivery_receipt` verifies the Ethereum receipt/execution proof (proving the log exists on-chain) and decodes it into a `DeliveryReceipt { gateway, nonce, topic, success, reward_address }` via `TryFrom<&Log>`, which trusts whatever `topic`/`success`/`reward_address` values the Ethereum-side `InboundMessageDispatched` event log encodes. [3](#0-2) 

`process_delivery_receipt` then only checks `gateway` and looks up `PendingOrders` by `nonce`; it never re-derives or compares `receipt.topic` against the `topic` field that was stored in `Messages`/hashed into `MessageLeaves` for that nonce, and it pays the reward regardless of `receipt.success`: [1](#0-0) 

This is structurally identical to the reported bug class: two correlated on-chain-verifiable structures (the committed `OutboundMessage` and the relayed `DeliveryReceipt`) are supposed to refer to the same logical event, but only one weak field (`nonce`) ties them together, while the other correlating field (`topic`, standing in for `BeaconBlockHeader`) is accepted unchecked. Because the Ethereum-side log is only cryptographically proven to exist in a finalized block (via `T::Verifier::verify`), not that its `topic`/`success` fields match the specific `OutboundMessage` committed on the Substrate side for that `nonce`, the correlation between the two entities is never actually established beyond the nonce.

### Impact Explanation
Reward payouts (`T::RewardPayment::register_reward`) are settled based on `order.fee`, keyed only by nonce, with no assertion that the receipt's `topic`/`success` correspond to the actual dispatched message content. If a relayer/attacker can produce (via any real transaction on the Gateway contract, e.g. via `success=false`, or a different `topic` than the committed one) a validly-proven `InboundMessageDispatched(nonce, topic, success, reward_address)` log for the correct `nonce` but with mismatched `topic`/`success`, the pallet still pays out the full pending fee to an arbitrary `reward_address`, and unconditionally treats the order as fully and correctly delivered/settled (`MessageDelivered` event, order removed) even though delivery may not have actually succeeded as committed. This breaks the "settle exactly once to the rightful beneficiary/amount, only after execution succeeds" invariant for bridge reward payouts.

### Likelihood Explanation
The path is reachable by any signed account calling the public `submit_delivery_receipt` extrinsic with a real Ethereum event log/proof — no special privilege, validator, or governance role is required, only a valid execution/receipt proof for *some* on-chain Ethereum event with the target nonce. The missing check is a simple omission (topic/success not compared against stored state), not a cryptographic weakness, making it straightforward for any relayer to exploit by controlling which `success`/`topic`/`reward_address` values are emitted (they are event parameters, not part of the proof binding).

### Recommendation
Store the committed `topic` (and possibly a hash of the committed `OutboundMessage`) inside `PendingOrder` when it is created in `do_process_message`, and in `process_delivery_receipt` assert `receipt.topic == order.topic` before paying the reward. Additionally, gate reward payment on `receipt.success == true`, since currently the reward is paid unconditionally as long as an order exists for the nonce, irrespective of delivery outcome. [4](#0-3) 

### Proof of Concept
1. AssetHub sends an XCM export message; BridgeHub's `outbound-queue-v2::do_process_message` commits `OutboundMessage { origin: O, nonce: N, topic: T, commands: C }` and stores `PendingOrder { nonce: N, fee: F }`. [2](#0-1) 
2. On Ethereum, the Gateway contract processes message `N` but for any reason (e.g. partial failure of nested calls, or an attacker-influenced execution path) emits `InboundMessageDispatched(nonce=N, topic=T', success=false, reward_address=R_attacker)` where `T' != T`.
3. A relayer obtains a valid receipt/execution proof for this real (but semantically different) log and calls `submit_delivery_receipt`. `T::Verifier::verify` succeeds (the log genuinely exists on-chain), and `DeliveryReceipt::try_from` decodes `topic=T'`, `success=false`, `reward_address=R_attacker`. [5](#0-4) 
4. `process_delivery_receipt` finds `PendingOrders::get(N)` (matches by nonce only), pays `order.fee` to `R_attacker`, and removes the order and emits `MessageDelivered` — despite `success=false` and `topic` mismatch never being checked. [6](#0-5)

sol! {
	event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address);
}

/// Delivery receipt
#[derive(Clone, Debug)]
pub struct DeliveryReceipt {
	/// The address of the outbound queue on Ethereum that emitted this message as an event log
	pub gateway: H160,
	/// The nonce of the dispatched message
	pub nonce: u64,
	/// Message topic
	pub topic: H256,
	/// Delivery status
	pub success: bool,
	/// The reward address
	pub reward_address: [u8; 32],
}

#[derive(Copy, Clone, Encode, Decode, Eq, PartialEq, Debug, TypeInfo)]
pub enum DeliveryReceiptDecodeError {
	DecodeLogFailed,
	DecodeAccountFailed,
}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
}
