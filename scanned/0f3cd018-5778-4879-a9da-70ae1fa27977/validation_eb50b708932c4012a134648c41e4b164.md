## Analysis

The strongest local analog to the RLP burn/mint slippage report is in the Snowbridge **system-frontend** pallet, where a user-controlled swap explicitly disables slippage protection when converting a fee/tip asset into Ether before burning it for bridge delivery. [1](#0-0) 

### Title
Missing slippage protection in `SystemFrontend::swap_and_burn` lets an unprivileged caller under-fund Ethereum-side execution fees and relayer tips - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

### Summary
`swap_and_burn`, invoked from both the public `register_token` and `add_tip` extrinsics via `swap_fee_asset_and_burn`, calls `T::Swap::swap_exact_tokens_for_tokens` with `amount_out_min` hard-coded to `None`, explicitly commented `"No minimum amount required"`. The AMM-derived `ether_gained` from this unconstrained swap is then burned and forwarded as the `amount` field to BridgeHub's `RegisterToken`/`AddTip` calls, meaning the fee funding Ethereum-side execution or the relayer reward is fully dependent on spot pool price with no floor. [2](#0-1) [3](#0-2) 

### Finding Description
`register_token` and `add_tip` are both permissionless/signed public entrypoints: [4](#0-3) [5](#0-4) 

Both funnel into `swap_fee_asset_and_burn`, which, whenever the supplied `fee_asset` is not already Ether, routes through `swap_and_burn`. That function calls the generic `pallet_asset_conversion::Swap::swap_exact_tokens_for_tokens` trait method with `None` for `amount_out_min` — the exact parameter that exists specifically to protect against slippage, as demonstrated by its normal, protected use elsewhere in the codebase: [6](#0-5) [7](#0-6) 

Because `AssetConversion` pools are simple constant-product AMMs, their spot price can be moved arbitrarily within a single extrinsic batch (e.g., via `Utility::batch_all`: first call `AssetConversion::swap_exact_tokens_for_tokens` to push the `fee_asset`/`Ether` pool to an extreme ratio, then call `SystemFrontend::register_token` or `SystemFrontend::add_tip` in the same batch). Since `swap_and_burn` accepts *any* non-zero output, the attacker's own preceding swap in the batch determines how little Ether is actually produced from the `tip_amount`/`fee_amount` supplied.

The resulting `ether_gained` (which can be driven near zero) is what gets:
- Burned via `burn_for_teleport` and forwarded as the `amount` in `RegisterToken`, i.e. the execution-fee funding for the token registration on Ethereum, or
- Forwarded as the `amount` in `AddTip`, which BridgeHub allocates "to the reward in the Inbound/Outbound pallet" for the relayer that delivers the message. [8](#0-7) 

Existing guards do not stop this path: there is no `ensure!` on `ether_gained` versus any oracle-derived or user-supplied minimum anywhere in `swap_and_burn` or its callers, and `pallet_asset_conversion`'s own protection (`ProvidedMinimumNotSufficientForSwap`) is bypassed entirely because the caller explicitly opts out by passing `None`.

### Impact Explanation
This directly maps to the "public underpriced work that degrades block production or stalls bridge processing" category in the impact gate:
- For `register_token`, an attacker-manipulated swap can cause the Ethereum-side registration message to be dispatched with near-zero backing Ether, which can cause the corresponding execution on Ethereum to fail or be starved of gas/fee, stalling token registration for that asset.
- For `add_tip`, the relayer tip amount allocated on BridgeHub can be driven to near-zero even though the caller supplied a legitimate `fee_asset` amount, degrading relayer incentives and thus delivery-receipt/message processing throughput for the bridge.

No malicious validator, collator, relayer, or governance actor is required — only an ordinary signed account able to submit a batched extrinsic.

### Likelihood Explanation
Likelihood is high for any low-liquidity or newly-created `fee_asset`/Ether pool, since a single well-funded swap within the same batch can move the AMM price substantially before `swap_and_burn` executes, and nothing in the code path checks a minimum output or an on-chain oracle price.

### Recommendation
Thread a `minAmountOut` (and optionally a `deadline`/max-slippage) parameter through `register_token`/`add_tip` down into `swap_and_burn`, replacing the hard-coded `None` passed to `T::Swap::swap_exact_tokens_for_tokens`, and reject the call if the achieved `ether_gained` falls below the caller/system-configured minimum, mirroring the protection already present in `pallet_asset_conversion::do_swap_exact_tokens_for_tokens`.

### Proof of Concept
1. Attacker creates or identifies a low-liquidity `AssetConversion` pool for `(fee_asset_location, EthereumLocation)`.
2. Attacker submits `Utility::batch_all` containing:
   a. `AssetConversion::swap_exact_tokens_for_tokens` swapping a large amount of `fee_asset` into Ether, sharply reducing the Ether reserve and moving the price against subsequent `fee_asset -> Ether` swaps.
   b. `SystemFrontend::add_tip(message_id, fee_asset_amount)` (or `register_token` with a non-root origin and `fee_asset`), which internally calls `swap_and_burn` with `amount_out_min: None`.
3. Because of the attacker's own preceding swap, `ether_gained` computed inside `swap_and_burn` is far below the "fair" price, yet the call still succeeds since there is no floor check.
4. The resulting near-zero `ether_gained` is burned and forwarded as the `amount` in the `AddTip`/`RegisterToken` XCM Transact call to BridgeHub, under-funding the relayer reward or Ethereum-side execution fee despite the caller having supplied a full-value `fee_asset` amount.

		fn swap_and_burn(
			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether
			let ether_asset = Asset::from((ether_location.clone(), ether_gained));

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}
