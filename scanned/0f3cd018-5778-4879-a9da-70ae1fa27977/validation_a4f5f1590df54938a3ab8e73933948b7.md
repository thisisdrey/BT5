### Title
Silent fund loss when `ERC20Transactor::deposit_asset` receives multiple matched fungible ERC20 assets - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor`, the XCM `TransactAsset` implementation added to route ERC20 balances through `pallet-revive`'s bare-call interface, is a bespoke re-implementation of asset settlement logic on top of the standard `IERC20` interface (`ethereum-standards::IERC20`) rather than reusing the vetted, general-purpose `FungiblesAdapter`/`AssetsInHolding` settlement path. Because it hand-rolls the accounting instead of following the established pattern used by `fungibles_adapter.rs`, it only accounts for a single matched asset out of a potentially multi-asset `AssetsInHolding` value passed into `deposit_asset_with_surplus`, silently discarding the rest.

### Finding Description
`deposit_asset_with_surplus` receives `what: AssetsInHolding`, which per the `TransactAsset` trait can legitimately contain multiple distinct fungible assets (e.g., several different ERC20 contracts, each treated as its own asset class by `MatchesFungibles`). The implementation only ever extracts the *first* fungible asset from `what` via `what.fungible_assets_iter().next()` and issues a single ERC20 `transfer` call for that one asset/amount: [1](#0-0) 

The code comment and `defensive_assert!(what.len() == 1, ...)` at line 234 explicitly acknowledge that "the rest will be silently ignored" if `what` contains more than one asset: [2](#0-1) 

`defensive_assert!` only panics when the `frame-support`'s `try-runtime`/`std` defensive-checks feature is compiled in; in a production runtime it is a no-op, so this is not a hard invariant, just a debug hint. When the assumption is violated in production, the function consumes `what` (moved into `.fungible_assets_iter()`), transfers only the first asset to the beneficiary through the ERC20 `transfer` call, and on success returns `Ok(surplus)` — never returning the untransferred remainder of `what` back to the caller: [3](#0-2) 

Since the XCM executor's holding register had already deducted these assets when they were checked into the transactor and the function signature only allows returning either `Ok(Weight)` (asset fully handled) or `Err((AssetsInHolding, XcmError))` (nothing handled, return everything), there is no path to partially settle one asset and return the rest. Any additional fungible assets bundled in `what` are dropped when the local `what` variable goes out of scope — the value is neither credited to the beneficiary nor returned to the XCM holding register for later use, refund, or trapped-asset registration.

This differs from the standard, well-reviewed pattern used elsewhere (e.g. `fungibles_adapter.rs`), which is built to process assets from a matched set individually and correctly propagate/return whatever is not handled. The `ERC20Transactor` instead reimplements settlement ad hoc — exactly the "modify a standard mechanism instead of composing/inheriting it" anti-pattern flagged in the source bug report about ERC20, but here it produces an actual fund-loss bug rather than a maintainability concern.

### Impact Explanation
This is a permanent-fund-loss / value-non-conservation bug: an XCM program that deposits multiple ERC20-class assets to a single beneficiary in one holding transaction (e.g. a `DepositAsset` targeting a wildcard filter that matches several distinct ERC20 contracts registered as assets on the chain) will cause every asset after the first to vanish — not delivered to the intended beneficiary and not returned/trapped for recovery. This directly violates the "Balances/assets ... must conserve value and settle exactly once to the rightful beneficiary and amount" invariant, and can be triggered by any unprivileged XCM sender routing a multi-asset transfer through Asset Hub's ERC20 lane (`ERC20Transactor` is wired into `asset-hub-westend`'s `xcm_config.rs`).

### Likelihood Explanation
Likelihood depends on whether the composed `MatchesFungibles`/asset-transactor set on Asset Hub Westend can ever place more than one distinct ERC20 asset into the same `AssetsInHolding` value handed to this specific transactor in a single `deposit_asset` call (e.g., via a `TransferAsset`/`DepositAsset` instruction naming multiple ERC20 asset locations, or a wildcard matching several ERC20 contracts at once). This requires confirming the exact `xcm_config.rs` wiring and `MatchesFungibles` implementation for asset-hub-westend to determine how the executor batches assets before calling into this transactor — I was not able to fully verify from the available index whether the executor ever batches more than one asset into a single `deposit_asset` call for this specific adapter position in the transactor tuple (this is typically controlled by `XcmExecutor::to_holding`/`deposit_assets` semantics, which was not indexed here). If the executor always calls `deposit_asset` once per single asset for this adapter, the code path is dead in practice and only the maintainability concern from the bug report analog applies; if it can pass multiple assets (as the code's own comments assume is possible), the fund-loss is real and triggerable by any user constructing such an XCM message.

### Recommendation
Do not hand-roll partial/best-effort settlement in `ERC20Transactor::deposit_asset_with_surplus` (and the symmetric `withdraw_asset_with_surplus`). Either:
1. Restrict the type signature/contract so it structurally cannot receive more than one asset (e.g., require callers to invoke it per-asset, matching how `fungibles_adapter.rs` iterates), or
2. If multiple assets can arrive, loop over `what.fungible_assets_iter()`, attempt the ERC20 transfer for each, and correctly accumulate an `AssetsInHolding` of assets that failed/were not processed to return via the `Err` path — never silently drop unhandled assets.
Additionally, upgrade `defensive_assert!(what.len() == 1, ...)` to an actual runtime-enforced error return in production builds so violations fail closed (return `Err`) instead of proceeding under a false assumption.

### Proof of Concept
Conceptual (could not fully verify the exact XCM message construction against asset-hub-westend's live `xcm_config.rs` matcher/adapter tuple ordering due to index limits, but the vulnerable code path is directly demonstrable):
1. Register two distinct ERC20 contracts (`token_id: AccountKey20A`, `AccountKey20B`) as recognized fungible assets matched by `Matcher::matches_fungibles` in the `ERC20Transactor` tuple slot.
2. Construct an XCM program that withdraws both `AccountKey20A` and `AccountKey20B` amounts into the holding register, then issues a single `DepositAsset { assets: Wild(All), beneficiary }` (or an explicit multi-asset filter) targeting a beneficiary account.
3. If the XCM executor batches both matched ERC20 assets into one call to `ERC20Transactor::deposit_asset`, trace execution into `deposit_asset_with_surplus` at [4](#0-3)  — observe only the first asset in iteration order is transferred via `IERC20::transferCall`, `Ok(surplus)` is returned, and the second asset's balance (already debited from the checking account's XCM holding accounting) is never credited to the beneficiary's ERC20 balance nor returned to the caller.
4. Confirm on-chain that the beneficiary's ERC20 balance for the second token never increases and no `AssetsTrapped` or refund event is emitted for it, demonstrating permanent loss of the second asset amount.
