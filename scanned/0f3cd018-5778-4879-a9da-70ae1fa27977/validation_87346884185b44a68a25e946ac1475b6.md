### Title
Snowbridge Outbound Queue's Hardcoded `ConstantGasMeter` Gas Estimates Can Underprice `RemoteFee`, Causing Relayers to be Reimbursed Less Than Real Ethereum Execution Cost - (File: `bridges/snowbridge/primitives/outbound-queue/src/v1/message.rs`)

### Summary
`ConstantGasMeter` hardcodes per-command gas estimates (`MAXIMUM_BASE_GAS = 185_000`, `RegisterForeignToken => 1_200_000`, etc.) that are used as the sole input to the `RemoteFee` upfront-charged to users for delivering a Snowbridge message to Ethereum. These constants are, by the code's own comment, "extracted from [a] `forge test ... --gas-report`" run once and manually padded with a "healthy buffer" — they are never re-verified against live Ethereum gas costs. If actual Gateway contract gas consumption for a given command exceeds these baked-in figures (gas repricing, EVM upgrade, code-path growth, or a command variant whose constant was simply set too low), the upfront `RemoteFee` collected from the user will be smaller than what the relayer must actually spend on Ethereum to execute the delivery — the same underlying flaw as the Scroll `commitScalar` bug: a fixed scalar standing in for a variable real execution cost, with no live correction mechanism.

### Finding Description
`GasMeter::maximum_gas_used_at_most()` = `MAXIMUM_BASE_GAS + maximum_dispatch_gas_used_at_most(command)`, both of which are constants baked into `ConstantGasMeter`: [1](#0-0) 

This value flows directly, unmodified, into the fee formula that the module's own documentation defines as `RemoteFee(Message) = MaxGasRequired(Message) * Params.MaxFeePerGas + Params.Reward`: [2](#0-1) 

The actual computation is performed in `calculate_fee`/`calculate_remote_fee`, which multiplies the hardcoded gas estimate by `fee_per_gas` and adds the reward — there is no upward adjustment tied to observed/actual gas consumption on Ethereum: [3](#0-2) 

This fee is what gets charged to the sender at the public `SendMessage::validate` entrypoint (any unprivileged parachain/XCM sender reaching Snowbridge can trigger this): [4](#0-3) 

Per the module docs, on the Ethereum side the relayer is reimbursed for `GasUsed()` (i.e. actual gas consumed), not `min(actual, estimate)`: [5](#0-4) 

Because the ETH funded to the Gateway contract for a given message is sized by the (upfront, hardcoded-estimate-based) `RemoteFee`, and the relayer's reimbursement is sized by *actual* gas used, any systemic gap between the hardcoded `ConstantGasMeter` figures and real EVM gas cost is paid for out of the relayer's pocket — mirroring the Scroll case where `commitScalar` (a fixed multiplier standing in for the real `commitBatch()` gas cost) was 100x too low, causing the sequencer to spend far more than it collected.

Unlike `fee_per_gas`/`exchange_rate`, which are governance-updatable "pricing parameters" refreshed periodically (`set_pricing_parameters`), the `ConstantGasMeter` gas constants are compiled into the runtime and can only be corrected via a full runtime upgrade — there is no live safety mechanism (oracle, benchmark-check, or floor validation) preventing them from drifting stale relative to actual Ethereum execution cost.

### Impact Explanation
If any of the hardcoded per-command gas figures (e.g. `RegisterForeignToken => 1_200_000`, `AgentExecute::TransferToken => 200_000`, `MAXIMUM_BASE_GAS = 185_000`) understate real Gateway contract gas usage — due to gas-cost changes on Ethereum (EIP-1559/repricing forks), added logic in later Gateway contract versions, or simple benchmarking error — every message of that command type will underprice the relayer's true cost. Since this affects a public, unprivileged entrypoint (any parachain/user routed through Snowbridge's outbound queue), an attacker (or simply organic usage) can trigger a systematic drain: relayers keep servicing messages at a loss until they stop relaying, at which point the bridge stalls (message queue backs up, matching the "public underpriced work that degrades... stalls bridge processing" impact category).

### Likelihood Explanation
No malicious/privileged actor is required — ordinary use of the public `send`/`validate` path for a command whose hardcoded gas constant is under-provisioned is sufficient. The bug is purely a mispriced constant, structurally identical to the reported Scroll `commitScalar` issue, and given that Ethereum gas costs are not static (client-level repricing, contract upgrades via `Command::Upgrade`), the risk of drift over the contract's lifetime is high and cannot be corrected without a runtime upgrade (governance parameter updates only cover `fee_per_gas`/`exchange_rate`, not the `ConstantGasMeter` constants themselves).

### Recommendation
Treat the `GasMeter` per-command gas estimates as sensitive, periodically-audited security parameters just like `fee_per_gas`: expose them as governance-updatable `PricingParameters` (or a `Get<u64>` per command) rather than compile-time constants, add a CI check that re-runs the `forge --gas-report` benchmark against the current Gateway contract and fails if any `ConstantGasMeter` figure is smaller than the measured worst case, and consider capping relayer reimbursement at `Min(GasUsed(), MaxGasRequired)` symmetrically with the `MaxFeePerGas` cap so a stale estimate cannot silently transfer the cost onto relayers.

### Proof of Concept
1. Ethereum undergoes a gas-repricing hard fork (or the Gateway contract is upgraded via `Command::Upgrade`) increasing the real gas cost of, say, `RegisterForeignToken` execution above the hardcoded `1_200_000` in `ConstantGasMeter`. [6](#0-5) 
2. Any user calls the public outbound-queue `validate`/`send` path with a `RegisterForeignToken` command; `calculate_fee` computes `RemoteFee` using the stale `1_200_000` gas figure, charging the user (and thus funding the Gateway contract) too little ETH. [7](#0-6) 
3. The message is delivered and executed on Ethereum consuming more gas than `1_200_000`; per the documented settlement rule the relayer accrues `GasPrice * GasUsed() + Reward`, i.e. it is compensated for actual consumption from a pool that was underfunded relative to that consumption. [5](#0-4) 
4. Repeating step 2 with many `RegisterForeignToken` (or any other underpriced command) messages causes systematic relayer losses until relayers stop servicing the channel, stalling bridge message processing — the same "sequencer bleeding funds" dynamic described in the source report, just relocated to Snowbridge's outbound relayer economics.

/// A meter that assigns a constant amount of gas for the execution of a command
///
/// The gas figures are extracted from this report:
/// > forge test --match-path test/Gateway.t.sol --gas-report
///
/// A healthy buffer is added on top of these figures to account for:
/// * The EIP-150 63/64 rule
/// * Future EVM upgrades that may increase gas cost
pub struct ConstantGasMeter;

impl GasMeter for ConstantGasMeter {
	// The base transaction cost, which includes:
	// 21_000 transaction cost, roughly worst case 64_000 for calldata, and 100_000
	// for message verification
	const MAXIMUM_BASE_GAS: u64 = 185_000;

	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64 {
		match command {
			Command::SetOperatingMode { .. } => 40_000,
			Command::AgentExecute { command, .. } => match command {
				// Execute IERC20.transferFrom
				//
				// Worst-case assumptions are important:
				// * No gas refund for clearing storage slot of source account in ERC20 contract
				// * Assume dest account in ERC20 contract does not yet have a storage slot
				// * ERC20.transferFrom possibly does other business logic besides updating balances
				AgentExecuteCommand::TransferToken { .. } => 200_000,
			},
			Command::Upgrade { initializer, .. } => {
				let initializer_max_gas = match *initializer {
					Some(Initializer { maximum_required_gas, .. }) => maximum_required_gas,
					None => 0,
				};
				// total maximum gas must also include the gas used for updating the proxy before
				// the the initializer is called.
				50_000 + initializer_max_gas
			},
			Command::SetTokenTransferFees { .. } => 60_000,
			Command::SetPricingParameters { .. } => 60_000,
			Command::UnlockNativeToken { .. } => 200_000,
			Command::RegisterForeignToken { .. } => 1_200_000,
			Command::MintForeignToken { .. } => 100_000,
		}
	}
}

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		/// Calculate fee in remote currency for dispatching a message on Ethereum
		pub(crate) fn calculate_remote_fee(
			gas_used_at_most: u64,
			fee_per_gas: U256,
			reward: U256,
		) -> U256 {
			fee_per_gas.saturating_mul(gas_used_at_most.into()).saturating_add(reward)
		}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}
