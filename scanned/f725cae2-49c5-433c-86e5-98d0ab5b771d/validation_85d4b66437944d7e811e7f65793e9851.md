## Title
Session-boundary desync between `ActiveValidatorIndices` and the session pallet's live `DisabledValidators` list allows disabled/offending validators' backing votes to be counted - (File: `polkadot/runtime/parachains/src/shared.rs`)

### Summary
This mirrors the reported bug class exactly: code assumes a positional/index correspondence between two independently-updated collections and does not re-derive the correct mapping from the authoritative source at the moment they diverge. In the external report, `valset_execution` indices were assumed to line up with `valset_snapshot` members. In this repository, `polkadot_runtime_parachains::shared::Pallet::disabled_validators()` assumes that raw validator indices returned by `T::DisabledValidators::disabled_validators()` (indices into `pallet_session::Validators`) always correspond to the same validators as the indices baked into `ActiveValidatorIndices`/`ActiveValidatorKeys` (computed once per session in `initializer_on_new_session`). The function's own doc comment concedes the assumption breaks down: `"CAVEAT: this might produce incorrect results on session boundaries"` [1](#0-0) .

### Finding Description
`ActiveValidatorIndices` and `ActiveValidatorKeys` are computed exactly once when a new session starts, from the `all_validators` snapshot handed to `initializer_on_new_session`, and are shuffled/truncated for parachain-validator assignment [2](#0-1) .

`disabled_validators()` then builds a reverse-index from `ActiveValidatorIndices` (raw session index -> shuffled `ValidatorIndex`) and looks up each currently-disabled raw index (as reported live by `T::DisabledValidators::disabled_validators()`, i.e. `pallet_session::Pallet::<T>::disabled_validators()`) against that reverse-index:
```
let shuffled_indices = ActiveValidatorIndices::<T>::get();
let reverse_index = shuffled_indices.iter().enumerate()
    .map(|(i, v)| (v.0, ValidatorIndex(i as u32)))
    .collect::<BTreeMap<u32, ValidatorIndex>>();
T::DisabledValidators::disabled_validators()
    .iter()
    .filter_map(|v| reverse_index.get(v).cloned())
    .collect()
``` [3](#0-2) 

`pallet_session`'s `DisabledValidators` storage holds raw `u32` indices into the *current* `Validators::<T>` list and is explicitly documented as being reset "when `on_session_ending` returns a new set of identities": `"It gets cleared when on_session_ending returns a new set of identities."` [4](#0-3) . The clearing happens in `rotate_session` only conditionally, gated by the `changed` flag computed by comparing queued vs. new session keys [5](#0-4) . `Validators::<T>::put(&validators)` (the list that raw disabling indices are relative to) and the parachains pallet's own new-session hook (`initializer_on_new_session`, which rebuilds `ActiveValidatorIndices`) are triggered by two separate, independently-sequenced session-change callbacks (`T::SessionHandler::on_new_session` in `pallet_session` vs. the parachains `Initializer`'s session-change hook). Because the raw index space (`pallet_session::Validators`) can be updated, and the disabled-index list can be cleared or retained, in a different relative order/timing than the parachains pallet's `ActiveValidatorIndices` snapshot, the two collections are not guaranteed to be indexed against the same validator ordering exactly at session boundaries — which is precisely what the code comment warns about.

This function feeds directly into consensus-critical filtering: the disabled-validator index set computed here is used in `paras_inherent::mod.rs` to strip backing votes cast by disabled validators from `BackedCandidate`s before they are accepted on-chain [6](#0-5) , and is also exposed as a runtime API (`runtime_api_impl::v13::disabled_validators`) consumed by node-side subsystems (backing, disputes) to decide whether votes/statements from a validator should be trusted [7](#0-6) .

Why existing guards don't stop this: there is no re-validation that the raw indices from `T::DisabledValidators::disabled_validators()` were computed against the *same* validator ordering as `ActiveValidatorIndices`. The code simply performs a `BTreeMap` lookup and silently drops (via `filter_map`) any index that doesn't resolve — meaning a real disabled validator whose raw index doesn't currently line up (session boundary) is treated as *not* disabled rather than causing an error. There is no cross-check comparing session indices or validator identities, only positional (`u32`) correspondence, exactly like the reported `valset_execution`/`valset_snapshot` positional assumption.

### Impact Explanation
If, at the exact session-boundary block, the raw disabled-validator index from `pallet_session` does not map (or maps to the wrong validator) via the stale/rebuilt `ActiveValidatorIndices`, an equivocating/offending validator that should be excluded from backing/dispute-vote consideration can have its statements still counted as valid on-chain. Because this feeds the paras-inherent backing-vote filtering path, it can let statements from a validator who was just disabled (e.g., for equivocation or a slashable offence) still count toward `minimum_backing_votes`, allowing acceptance of a backed candidate that should have been rejected/dropped for insufficient valid votes. This is a runtime bug compromising intended validator-disabling behavior and backing-vote integrity — in scope per the "runtime bugs that compromise intended behavior" and "unauthorized execution... without direct machine access" categories.

### Likelihood Explanation
This requires no malicious node/validator/collator/relayer/prover assumption to trigger the underlying desync — it is a structural timing issue between two pallets' session-transition hooks that occurs naturally on ordinary session boundaries whenever a validator has been disabled near a rotation. The severity is bounded by the fact the window is a single session-boundary block and by the fact the developers already flagged it defensively in a comment, indicating the maintainers are aware of the general risk class but the code has not been hardened against it (no assertion, no fallback to conservative "treat unresolved index as disabled" behavior).

### Recommendation
Do not rely on positional/raw-index correspondence between `pallet_session::DisabledValidators` and `shared::ActiveValidatorIndices` across a session boundary. Instead:
- Resolve disabled validators by validator identity (`ValidatorId`/`AccountId`) rather than raw `u32` index wherever the lookup crosses a session-hook ordering boundary, or
- Explicitly track and use the disabled-validator raw indices as valid only for the *session in which they were computed* (tag the `DisabledValidators` list with the session index they belong to, akin to iterating `valset_snapshot` directly instead of assuming `valset_execution` order), and
- On the boundary block, fail closed (treat unresolved indices as still-disabled) rather than silently dropping them via `filter_map`.

### Proof of Concept
1. Validator `V` is reported/disabled near the end of session `N` via `pallet_session::Pallet::report_offence` → `disable_index_with_severity(i, ..)`, inserting raw index `i` (position of `V` in the session-`N` `Validators::<T>::get()` list) into `DisabledValidators` [8](#0-7) .
2. Session rotates to `N+1`. `pallet_session::rotate_session` updates `Validators::<T>` to the new (possibly reordered) validator set and conditionally clears `DisabledValidators` depending on the `changed` flag [9](#0-8) ; separately, the parachains `Initializer`'s new-session hook calls `shared::Pallet::initializer_on_new_session`, rebuilding `ActiveValidatorIndices` from a freshly shuffled/truncated index space over the session-`N+1` validator list [2](#0-1) .
3. At the boundary block, `shared::Pallet::disabled_validators()` is called (e.g., from `paras_inherent::apply_inherent_data` or a runtime API query used by node subsystems) while the raw index `i` from step 1 no longer identifies `V` in the session-`N+1` `Validators` ordering (or `V` was removed and its old index now silently resolves to a different validator or to nothing).
4. The lookup `reverse_index.get(v)` either fails to resolve (dropping `V` from the disabled-set entirely, via `filter_map`) or resolves to the wrong `ValidatorIndex`, so `V`'s backing statement is not filtered out of a `BackedCandidate` in `paras_inherent::mod.rs` [6](#0-5) .
5. As a result, the candidate is backed/accepted with a vote from a validator that governance/the offence-handling system intended to exclude, undermining the disabling mechanism's guarantee at exactly the session boundary it is documented to be unreliable for.

Note: I was not able to fully trace the precise ordering guarantee (or lack thereof) between `pallet_session`'s `on_new_session` handler invocation and the parachains `Initializer`'s session-change callback within a single block's `on_initialize`/session-rotation sequence in this pass — that ordering (which pallet's hook runs first in `construct_runtime!`) determines exactly how wide the exploitable window is per block. Confirming that exact hook ordering (and whether it can be manipulated or is fixed by macro-generated `AllPalletsWithSystem` ordering) would require an additional pass through the runtime's `construct_runtime!` pallet ordering and `SessionHandler`/`OneSessionHandler` composition, which I could not complete before the iteration limit.

	pub fn disable_index_with_severity(i: u32, severity: OffenceSeverity) -> bool {
		if i >= Validators::<T>::decode_len().defensive_unwrap_or(0) as u32 {
			return false;
		}

		DisabledValidators::<T>::mutate(|disabled| {
			match disabled.binary_search_by_key(&i, |(index, _)| *index) {
				// Validator is already disabled, update severity if the new one is higher
				Ok(index) => {
					let current_severity = &mut disabled[index].1;
					if severity > *current_severity {
						log!(
							trace,
							"updating disablement severity of validator {:?} from {:?} to {:?}",
							i,
							*current_severity,
							severity
						);
						*current_severity = severity;
					}
					true
				},
				// Validator is not disabled, add to `DisabledValidators` and disable it
				Err(index) => {
					log!(trace, "disabling validator {:?}", i);
					Self::deposit_event(Event::ValidatorDisabled {
						validator: Validators::<T>::get()[i as usize].clone(),
					});
					disabled.insert(index, (i, severity));
					T::SessionHandler::on_disabled(i);
					true
				},
			}
		})
	}
