### Title
Relayer reward paid on failed Ethereum message delivery because `DeliveryReceipt.success` is never checked - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`Pallet::process_delivery_receipt` in the Snowbridge outbound-queue-v2 pallet pays the relayer reward for a `PendingOrder` based solely on `order.fee > 0`, without ever inspecting the `success` field of the decoded `DeliveryReceipt`. This is the same broken invariant as the Ignite bug: a boolean "did this operation actually succeed" signal exists but is not consulted before releasing funds, so a failed execution is paid exactly like a successful one.

### Finding Description
The Ethereum Gateway contract emits `InboundMessageDispatched(nonce, topic, success, reward_address)`, and `success` explicitly indicates whether the message execution on Ethereum succeeded or failed: [1](#0-0) 

This field is faithfully decoded into `DeliveryReceipt::success`: [2](#0-1) 

However, `process_delivery_receipt`, which is reachable from the unprivileged, signed extrinsic `submit_delivery_receipt`, never reads `receipt.success`. It only checks the gateway address and whether `order.fee > 0` before calling `T::RewardPayment::register_reward`, then unconditionally removes the pending order: [3](#0-2) [4](#0-3) 

The corrupted value is the reward payout decision at line 466 (`if order.fee > 0 { ... register_reward ... }`) — it is derived purely from `PendingOrders` state, completely ignoring `receipt.success`, which is exactly the value meant to gate whether the reward should be paid at all. This mirrors the Ignite `releaseLockedTokens` bug: a `failed`/`success` boolean exists in the flow to indicate the operation outcome, but the reward-payout branch does not consult it, so failed executions are paid the same as successful ones.

Existing guards do not stop this:
- `ensure!(T::GatewayAddress::get() == receipt.gateway, ...)` only checks the message source, not the outcome.
- The verifier check (`T::Verifier::verify`) in `submit_delivery_receipt` only proves that the *event log itself* (whatever its `success` value) was really emitted by the gateway on Ethereum — it does not prove the message was delivered successfully; it can equally prove a `success: false` receipt.
- `<PendingOrders<T>>::get(nonce).ok_or(...)` only checks that an order is still pending, not that it succeeded.

All test call-sites in the repository construct `DeliveryReceipt { success: true, ... }` and there is no test exercising `success: false`, which confirms the `success` value is entirely inert in the current implementation — the pallet behaves identically for successful and failed deliveries.

### Impact Explanation
Any relayer can submit a genuine delivery receipt proof for a message whose execution on Ethereum failed (`success: false`, e.g., due to gas/griefing conditions, revert on the Gateway, or a legitimately failed dispatch) and still collect the full relayer fee recorded in `PendingOrders`, because the fee-payout condition never checks the outcome. This is unbacked/duplicate-style payout: a relayer is rewarded for a delivery that did not achieve its intended effect, draining reward funds (`T::RewardPayment` / `pallet-bridge-relayers` reward pool funded on AssetHub/BridgeHub) without a corresponding successful bridge action — directly matching the "duplicate settlement or payout" and "message queues... payout state must only advance after ... execution ... succeed" impact classes in the gate.

### Likelihood Explanation
The path requires only an unprivileged, signed call to `submit_delivery_receipt` with a legitimate, verifiable proof of an `InboundMessageDispatched` event — no relayer, validator, governance, or admin privilege beyond normal relaying is needed, and no malicious peer/prover assumption is required since the receipt can be a real, valid Ethereum event that simply happens to carry `success: false`. Given that failed executions on Ethereum (out-of-gas Transacts, reverted calls, etc.) are a normal occurrence in cross-chain messaging, this is readily triggerable in production rather than a purely theoretical edge case.

### Recommendation
In `process_delivery_receipt`, gate the reward payment on `receipt.success` (and consider handling/slashing or simply not rewarding on failure), e.g.:
```rust
if order.fee > 0 && receipt.success {
    T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee);
}
```
Additionally emit a distinct event (e.g., `MessageDeliveryFailed`) when `success == false` so failed deliveries are observable and can be retried/handled without a reward payout.

### Proof of Concept
1. A message is queued via `do_process_message`, creating `PendingOrders::<T>::insert(nonce, PendingOrder { fee: F, .. })` with `F > 0` (as in the existing benchmark/test setup, e.g. `submit_delivery_receipt_succeeds_after_unhalt`). [5](#0-4) 
2. On Ethereum, the Gateway contract processes the message but the dispatch fails, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address=relayer)`.
3. Any relayer obtains a valid proof for this real (failed) event and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (the event genuinely occurred), `DeliveryReceipt::try_from` decodes `success: false` correctly, but `process_delivery_receipt` still executes `if order.fee > 0 { register_reward(...) }` and pays out `order.fee` in full, then removes the order and emits `MessageDelivered` — identical to the success path. Replacing `success: true` with `success: false` in any of the existing integration tests (e.g. `cumulus/parachains/integration-tests/emulated/tests/bridges/bridge-hub-westend/src/tests/snowbridge_v2_outbound.rs:105-114`) and re-running would demonstrate the reward is still registered.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

// After governance resumes the bridge, legitimate delivery receipts flow through again:
// the order is paid out and removed from storage.
#[test]
fn submit_delivery_receipt_succeeds_after_unhalt() {
	new_tester().execute_with(|| {
		let nonce = 0;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_valid_event_proof());

		// Bridge halted — receipt rejected, order untouched.
		set_verifier_halted(true);
		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);
		assert!(PendingOrders::<Test>::get(nonce).is_some());

		// Bridge resumed — same receipt succeeds and the order is settled.
		set_verifier_halted(false);
		assert_ok!(OutboundQueue::submit_delivery_receipt(origin, event));
		assert!(PendingOrders::<Test>::get(nonce).is_none());

		System::assert_has_event(mock::RuntimeEvent::OutboundQueue(Event::MessageDelivered {
			nonce,
		}));
	});
