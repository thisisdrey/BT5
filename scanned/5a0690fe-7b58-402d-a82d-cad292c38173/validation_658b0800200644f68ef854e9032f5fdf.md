## Finding

### Title
ERC20Transactor credits the XCM holding register with the nominal transfer amount instead of the amount actually received, mishandling fee-on-transfer/deflationary ERC20 tokens - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor`, the `TransactAsset` implementation used by Asset Hub to let XCM programs move Solidity ERC20 tokens held under `pallet-revive`, moves tokens by calling the ERC20 contract's `transfer()` and, if the call does not revert and returns `true`, blindly credits the XCM holding register (or debits the checking account's expected balance) with the *requested* `amount`. It never compares the checking account's real balance before/after the call. This is the exact bug class from the external report: PositionsManager assumed the transferred amount equals the requested amount, ignoring ERC20 transfer fees; here the same assumption is baked into Asset Hub's ERC20 asset transactor.

### Finding Description
`ERC20Matcher` matches **any** local `AccountKey20` location with no allow-list, so an XCM program (executable by any signed account via `PolkadotXcm::execute`, or via reserve-transfer XCMs from any Location) can name an arbitrary attacker-deployed contract address as the asset: [1](#0-0) 

`withdraw_asset_with_surplus` performs the ERC20 `transfer()` call to the shared `TransfersCheckingAccount`, and on success unconditionally mints holding credit equal to the caller-supplied `amount`, not the observed balance delta of the checking account: [2](#0-1) 

`deposit_asset_with_surplus` mirrors this: it moves the full *credited* `amount` out of the checking account to the beneficiary by issuing another `transfer()` call, again trusting only the boolean/revert status: [3](#0-2) 

Nothing in either function reads `balanceOf(checking_account)` before and after the call to confirm the real amount moved, which is precisely the guard the external report recommends and Compound's `doTransferIn` implements. A compliant ERC20 that implements a transfer fee, burn-on-transfer, or any hook that delivers less than `value` to the recipient while still returning `true` will cause the checking account's on-chain balance to grow by less than the amount the executor believes it holds. Because `TransfersCheckingAccount` is a single shared pot for *all* ERC20s and *all* users, this creates a persistent desynchronization between the executor's internal accounting for a given operation and the real, shared, on-chain balance of the contract:
- The shortfall from one user's fee-on-transfer withdraw silently reduces the real backing available for other users' legitimate deposits of the same token.
- On the `deposit`/refund side, `transfer_asset_with_surplus`'s best-effort refund path also re-uses the same over-stated `amount`, so a failed deposit cannot correctly refund the original owner either: [4](#0-3) 

### Impact Explanation
This breaks the "balances/asset-hub value must conserve value and settle exactly once to the rightful beneficiary and amount" invariant for ERC20 assets bridged through `pallet-revive`. A fee-on-transfer or deflationary ERC20 (whether a real listed token that later toggles fees on, akin to USDT/USDC, or a token an unprivileged user deploys themselves and uses in an XCM program since `ERC20Matcher` has no allow-list) causes the shared checking account's real ERC20 balance to be smaller than the sum of credits the executor believes it has issued. This leads to unbacked internal accounting, unpredictable failure/locking of *other* users' legitimate ERC20 deposits from the same contract once the shortfall accumulates, and funds that get moved into the checking account without being redeemable 1:1 by the depositor's own follow-up instruction or the executor's best-effort refund.

### Likelihood Explanation
No privileged actor, governance action, relayer, or malicious validator is required. Any signed account can call `PolkadotXcm::execute` with a program targeting an arbitrary `AccountKey20` contract (its own deployed ERC20 with fee-on-transfer semantics), since `ERC20Matcher`/`IsLocalAccountKey20` accepts any local `AccountKey20` location without an asset registry check. This is a pure public-entrypoint, unprivileged path.

### Recommendation
In `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read `balanceOf(TransfersCheckingAccount)` (or the recipient) immediately before and after the `transfer()` call and credit/move the *observed delta*, not the caller-supplied `amount`, mirroring Compound's `doTransferIn` pattern referenced in the external report. Reject or explicitly document non-support for tokens whose delivered amount differs from the requested amount.

### Proof of Concept
1. Deploy a Solidity contract fully compliant with `IERC20` that on `transfer(to, value)` deducts a fee (e.g., burns 50% of `value`) before crediting `to`, and returns `true`.
2. Call `PolkadotXcm::execute` with an XCM program:
   `WithdrawAsset((AccountKey20 { key: feeToken }, amount))` → `DepositAsset(AllCounted(1), beneficiary)`.
3. `withdraw_asset_with_surplus` executes `transfer(checking_account, amount)`; the checking account's real ERC20 balance only increases by `amount/2`, but the executor's holding register is credited the full `amount` (`Erc20Credit(amount)` at `erc20_transactor.rs:197-203`).
4. `deposit_asset_with_surplus` then attempts to move the full `amount` out of the checking account to `beneficiary`; because the checking account is shared, if it holds residual balance from other users' previous fee-token transfers, the call can succeed and pay `beneficiary` more than what this particular withdraw actually backed — draining value contributed by other users of the same fee token, or, if under-collateralized, cause the transfer to revert and leave the shortfall permanently stuck since the refund path reuses the same unbacked `amount` (`transact_asset.rs:198-210`).
