### Title
Relayer reward paid out on `submit_delivery_receipt` regardless of the on-chain `success` flag of the Ethereum delivery event - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

### Summary
The Snowbridge V2 outbound queue pays a relayer reward for any verified `InboundMessageDispatched` event log without checking the event's `success` field, which records whether the message actually executed successfully on the Ethereum Gateway.

### Finding Description
`DeliveryReceipt` is decoded straight from the Ethereum `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)` event log: [1](#0-0) 

The `success` field is populated on decode but the public, unpermissioned extrinsic `submit_delivery_receipt` → `process_delivery_receipt` never inspects it before crediting the reward: [2](#0-1) 

The only checks performed are: (1) the event log came from the configured `GatewayAddress`, and (2) a `PendingOrder` exists for that `nonce`. Neither check depends on `receipt.success`. As long as the light-client `Verifier::verify` accepts the proof (i.e., the event genuinely happened on Ethereum), any relayer can submit a receipt for a message whose dispatch on Ethereum *failed* (`success == false`) and still receive the full `order.fee` reward, exactly as if the message had succeeded. `MessageDelivered` is emitted and the `PendingOrder` is removed in both cases, so the fund flow is indistinguishable from a real successful delivery.

This is structurally identical to the reported analog: a boolean signal meant to gate a critical action (`onTransferOwnership`'s return value gating ownership transfer; here `success` gating reward issuance) is decoded/available but never checked, so the guarded action always proceeds regardless of the signal's value.

### Impact Explanation
This is a "duplicate settlement or payout" / underpriced-work class impact under the pivot list: relayer rewards (`order.fee`, taken from the bridge's fee pool) are paid for work (message delivery) that did not actually complete on Ethereum. A relayer (or anyone controlling a relayer key, which is an ordinary permissionless role, not privileged) can be paid for failed deliveries at no extra cost beyond the normal proof-submission cost, draining the reward budget without providing the corresponding service, and potentially never triggering an actual redelivery/retry path since the order is removed as if resolved.

### Likelihood Explanation
High. The path is a plain signed extrinsic (`submit_delivery_receipt`) reachable by any account; the only prerequisite is a legitimate, provable Ethereum event log with `success = false`, which is a normal occurrence in existing Ethereum semantics (e.g., messages can legitimately fail dispatch on the Gateway for various reasons unrelated to the relayer). No malicious peer, validator, governance actor, or leaked key is required — only a standard relayer role interacting with the public extrinsic.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` when `receipt.success == true`. When `success == false`, still remove/settle the `PendingOrder` (or route it to a distinct "failed" handling path) but do not pay the relayer reward, mirroring how the Ownable fix removed/checked the previously-ignored boolean.

### Proof of Concept
1. A message is queued via `do_process_message`, creating `PendingOrders[nonce] = { nonce, fee: F, .. }` with `F > 0`.
2. On Ethereum, the Gateway attempts dispatch but it fails, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains the receipt proof for this event and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (the event is real), `DeliveryReceipt::try_from` decodes `success: false` but this value is discarded.
5. `process_delivery_receipt` checks only `gateway` match and `PendingOrders` existence — both pass — then unconditionally calls `T::RewardPayment::register_reward(&reward_account, .., order.fee)` and removes the order, emitting `MessageDelivered`.
6. The relayer is paid `order.fee` even though the underlying message dispatch failed on Ethereum, as confirmed by the existing test `submit_delivery_receipt_succeeds_after_unhalt` which shows the same code path pays out and removes the order for *any* verifiable receipt (that test uses a `success: true` mock event, but nothing in the pallet code distinguishes the `false` case): [3](#0-2)

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

#[test]
fn submit_delivery_receipt_succeeds_after_unhalt() {
	new_tester().execute_with(|| {
		let nonce = 0;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_valid_event_proof());

		// Bridge halted — receipt rejected, order untouched.
		set_verifier_halted(true);
		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);
		assert!(PendingOrders::<Test>::get(nonce).is_some());

		// Bridge resumed — same receipt succeeds and the order is settled.
		set_verifier_halted(false);
		assert_ok!(OutboundQueue::submit_delivery_receipt(origin, event));
		assert!(PendingOrders::<Test>::get(nonce).is_none());

		System::assert_has_event(mock::RuntimeEvent::OutboundQueue(Event::MessageDelivered {
			nonce,
		}));
	});
}
