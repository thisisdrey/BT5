### Title
`redeem` skips the live-decimals sanity check that `mint` enforces, letting a stale metadata snapshot drive external-asset payout math - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
Pallet `pallet-psm` snapshots each approved external asset's `decimals` at registration time (`ExternalAssetInfo::decimals`) and the internal asset's decimals at PSM creation (`PsmInfo::internal_decimals`). Both are used to compute the `10^diff` scaling factor between internal and external raw-balance units. The pallet already has a dedicated "sanity" check for this — `ensure_decimals_match` — but it is invoked only on the `mint` path, not on `redeem`. This is the same broken-invariant pattern as the CoinFabrik report: a validation routine exists to confirm a mutable external reference still matches expectations, but it is enforced inconsistently across the code paths that depend on that reference, so the contract/pallet can keep operating in an invalid state on the unguarded path.

### Finding Description
In `mint`, before computing the external→internal conversion, the pallet calls the sanity check against live metadata: [1](#0-0) 

In `redeem`, the same decimals values are consumed directly from the stored snapshots without any equivalent live-metadata check: [2](#0-1) 

The doc comment for `redeem` explicitly acknowledges the divergence, stating redemptions intentionally use the snapshot "even if live metadata later changes": [3](#0-2) 

The `decimals` values are not cosmetic: they directly parameterize the `10^diff` scaling factor applied in `internal_to_external` / `external_to_internal` to translate raw balances between the internal stablecoin and each external asset — the pallet's own `MAX_DECIMALS_DIFF` bound and dedicated `DecimalsMismatch` / `DecimalsRangeExceeded` errors confirm the developers treat decimal consistency as a load-bearing invariant, not a display detail: [4](#0-3) [5](#0-4) 

If the live decimals of an approved external asset diverge from the snapshot taken at `add_external_asset` time (the external asset's own metadata can change independently of the PSM instance, exactly like the `Crowdsale`'s `PricingStrategy`/`CeilingStrategy` references being "changed mid-crowdsale" without re-validation), `mint` correctly rejects the operation via `ensure_decimals_match`, but `redeem` proceeds and computes `external_out`/`effective_internal_net` using the stale scaling factor. Because `PsmDebt` accounting and the actual token transfer both derive from this now-incorrect scaling factor, redemptions can pay out external-asset amounts that no longer correspond to the correct 1:1-equivalent value, while `PsmDebt` bookkeeping is decremented by a mismatched `effective_internal_net`.

### Impact Explanation
This breaks the core invariant the pallet is built to guarantee — that internal debt is 1:1 backed by external reserve at redemption time. A scaling-factor mismatch on `redeem` can drain the PSM's per-external reserve faster than the tracked debt decreases (paying out more external asset per unit of internal burned than intended), causing fund loss for the PSM/other redeemers, or conversely under-pay legitimate redeemers. Either direction is a "theft or unbacked mint/unlock" / "wrong beneficiary or amount" class impact against a fund-holding pallet, consistent with the required impact categories (asset accounting must "conserve value and settle exactly once ... to the rightful beneficiary and amount").

### Likelihood Explanation
The trigger condition — live decimals of an already-approved external asset diverging from the registration-time snapshot — is exactly the scenario the pallet's own error variants (`DecimalsMismatch`, `DecimalsRangeExceeded`) and the `mint`-side check were written to guard against, showing the authors considered it a realistic occurrence, not a purely theoretical one. The gap is narrow (one dispatchable path checks, the sibling path does not) and requires no PSM-governance/admin misbehavior — the divergence originates from the external asset's own metadata, a state fully outside the PSM's admin's control, so it does not fall under "privileged governance or admin abuse as root cause" for the PSM pallet itself.

### Recommendation
Call the same `ensure_decimals_match` validation in `redeem` before using `external.decimals` / `info.internal_decimals` for conversion, mirroring the pattern the CoinFabrik fix applied (validate the referenced/mutable external state on every use, not just at one entry point). If snapshot-based redemption is intentionally desired for unwind-safety, then the conversion math must be decoupled from any assumption that snapshot decimals still equal live decimals, and reserve-sufficiency / debt-accounting checks must be re-derived to remain 1:1 correct under a stale snapshot rather than silently trusting it.

### Proof of Concept
1. `create_psm` registers `internal_asset` with `internal_decimals` snapshotted from live metadata (line 968).
2. `add_external_asset` approves `external_asset` and snapshots its `decimals` into `ExternalAssetInfo`.
3. Users mint against this pair; `PsmDebt` and reserve balances accumulate under the current decimals assumption.
4. The external asset's own admin (independent of the PSM) changes that asset's decimals metadata (e.g. via the fungibles/assets pallet's own metadata-update path) — this actor is not a PSM governance/admin, so it is outside the excluded "privileged governance/admin abuse" category for this pallet.
5. Any subsequent `mint` call now reverts with `DecimalsMismatch` via `ensure_decimals_match` (line 717) — confirming the check works and that the mismatch condition is live.
6. `redeem` is still callable and skips this check (lines 825-836), computing `external_out` from the now-stale `ext_decimals`/`internal_decimals` pair, resulting in an external payout amount inconsistent with the actual value of `internal_amount` burned, while `PsmDebt` is adjusted by the mis-scaled `effective_internal_net` — draining or under-crediting the reserve relative to real value.

Note: I could not fully inspect the body of `ensure_decimals_match` or the `MAX_DECIMALS_DIFF`-bounded scaling helpers (`internal_to_external`/`external_to_internal`) due to the file being truncated during review; the call sites and doc comments cited above were confirmed directly, but exact arithmetic bounds/overflow handling inside those helper functions are unverified.
