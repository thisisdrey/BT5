### Title
Fixed-weight charge for variable-length command batches in Snowbridge Outbound Queue V2 allows underpriced message processing - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/process_message_impl.rs])

### Summary
`Pallet::process_message` in the Snowbridge Outbound Queue V2 pallet charges a single, fixed benchmark weight (`T::WeightInfo::do_process_message()`) for processing an entire outbound message, regardless of how many `commands` that message actually contains, while `do_process_message` internally loops over an unbounded `Vec<Command>` to compute gas costs, ABI-encode payloads, and produce Merkle leaves.

### Finding Description
`ProcessMessage::process_message` reserves weight before doing any real work: [1](#0-0) 

The actual work done in `do_process_message` iterates over `commands: Vec<Command>` twice — once to build `OutboundCommandWrapper`s (which calls `T::GasMeter::maximum_dispatch_gas_used_at_most` per command) and once to build ABI-encoded `CommandWrapper`s that are hashed to build the committed Merkle leaf: [2](#0-1) 

The only bound on the number of commands per message is the aggregate encoded size limit, `MaxMessagePayloadSize` (configured to 2048 bytes on BridgeHub Westend): [3](#0-2) 

Because the weight charged to the `MessageQueue` pallet's weight meter is a single flat `do_process_message()` figure (not scaled per-`command`), a message packed with many minimal-size commands (maximizing count within the 2048-byte budget) performs proportionally more CPU work (per-command gas metering, ABI encoding, hashing) than the flat charge accounts for. This is the same broken invariant as the external report: work whose real cost scales with an attacker-controlled quantity is billed at a cost that does not scale with that quantity, so the caller of "fulfillment"/processing logic (here, `pallet-message-queue`'s weight-metered `on_initialize`/`service_queues` loop) can be handed underpriced work.

Unlike `HibernationDen.fulfillRandomWords`, `pallet-message-queue` is designed to be resilient to per-message weight underestimation via `WeightMeter`/bailing and the `Overweight` mechanism — but that mechanism only protects the *meter's* accounting, not the actual wall-clock/CPU cost incurred while `do_process_message` runs to completion. Since `process_message` unconditionally executes the full command loop after only consuming the fixed weight (rather than a per-command-scaled weight, and without pre-checking the message's command count against the charged weight), the discrepancy between charged and actual weight/PoV is not caught before the expensive work executes.

### Impact Explanation
Up to `MaxMessagesPerBlock` (32) such underpriced messages can be processed by `on_finalize`/the message queue in a single block, compounding the discrepancy between accounted and real per-block execution time. This degrades block production time on BridgeHub and can stall bridge message processing throughput, matching the "public underpriced work that degrades block production or stalls bridge processing" impact category.

### Likelihood Explanation
Any account able to enqueue an outbound message (e.g. via XCM `ExportMessage`/the `EthereumBlobExporter` from a sibling parachain, subject only to the existing per-message fee/size validation) can control the number and shape of `commands` packed into a message up to the payload-size bound, without needing a malicious relayer, validator, collator, or governance action — this is an ordinary user-facing message-submission path.

### Recommendation
Scale the weight consumed in `ProcessMessage::process_message` (and the corresponding benchmark) by the number of commands in the decoded message (or reject decode/processing early if the command count exceeds what the flat weight was benchmarked for), so that the meter's `try_consume` check reflects the true cost of the command loop in `do_process_message` before that loop executes.

### Proof of Concept
1. Construct an outbound `Message` (v2) whose ABI-encoded `commands` fill the 2048-byte `MaxMessagePayloadSize` with the maximum possible number of minimal-size `Command`s. [4](#0-3) 
2. Submit/enqueue this message (through the normal XCM export path feeding `T::MessageQueue`) up to `MaxMessagesPerBlock` (32) times in a block.
3. `pallet-message-queue` charges each message the flat `T::WeightInfo::do_process_message()` weight before invoking `Pallet::do_process_message`, which then executes the full per-command loop (gas metering + ABI encoding + hashing) for every packed command — real execution time scales with command count while accounted weight does not, producing underpriced block-time consumption relative to what was budgeted. 		/// Process a message delivered by the MessageQueue pallet.
		/// IMPORTANT!! This method does not roll back storage changes on error.
		pub(crate) fn do_process_message(
			_: ProcessMessageOriginOf<T>,
			mut message: &[u8],
		) -> Result<bool, ProcessMessageError> {
			use ProcessMessageError::*;

			// Yield if the maximum number of messages has been processed this block.
			// This ensures that the weight of `on_finalize` has a known maximum bound.
			let current_len = MessageLeaves::<T>::decode_len().unwrap_or(0);
			if current_len >= T::MaxMessagesPerBlock::get() as usize {
				Self::deposit_event(Event::MessagePostponed {
					payload: message.to_vec(),
					reason: Yield,
				});
				return Err(Yield);
			}

			// Decode bytes into Message
			let Message { origin, id, fee, commands } =
				Message::decode(&mut message).map_err(|_| {
					Self::deposit_event(Event::MessageRejected {
						id: None,
						payload: message.to_vec(),
						error: Corrupt,
					});
					Corrupt
				})?;

			// Convert it to OutboundMessage and save into Messages storage
			let commands: Vec<OutboundCommandWrapper> = commands
				.into_iter()
				.map(|command| OutboundCommandWrapper {
					kind: command.index(),
					gas: T::GasMeter::maximum_dispatch_gas_used_at_most(&command),
					payload: command.abi_encode(),
				})
				.collect();

			let nonce = <Nonce<T>>::get().checked_add(1).ok_or_else(|| {
				Self::deposit_event(Event::MessageRejected {
					id: None,
					payload: message.to_vec(),
					error: Unsupported,
				});
				Unsupported
			})?;

			let outbound_message = OutboundMessage {
				origin,
				nonce,
				topic: id,
				commands: commands.clone().try_into().map_err(|_| {
					Self::deposit_event(Event::MessageRejected {
						id: Some(id),
						payload: message.to_vec(),
						error: Corrupt,
					});
					Corrupt
				})?,
			};
			Messages::<T>::append(outbound_message);

			// Convert it to an OutboundMessageWrapper (in ABI format), hash it using Keccak256 to
			// generate a committed hash, and store it in MessageLeaves storage which can be
			// verified on Ethereum later.
			let abi_commands: Vec<CommandWrapper> = commands
				.into_iter()
				.map(|command| CommandWrapper {
					kind: command.kind,
					gas: command.gas,
					payload: Bytes::from(command.payload),
				})
				.collect();
			let committed_message = OutboundMessageWrapper {
				origin: FixedBytes::from(origin.as_fixed_bytes()),
				nonce,
				topic: FixedBytes::from(id.as_fixed_bytes()),
				commands: abi_commands,
			};
			let message_abi_encoded_hash =
				<T as Config>::Hashing::hash(&committed_message.abi_encode());
			MessageLeaves::<T>::append(message_abi_encoded_hash);
