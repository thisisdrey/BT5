Based on the investigation, the strongest analog is in `substrate/frame/psm/src/lib.rs`'s `mint()` extrinsic, which reproduces the exact bug class from the report: **the value used for a limit/deviation check differs from the value actually moved/settled**, because of a round-trip conversion between two different decimal representations.

### Title
Debt-ceiling check in `pallet-psm::mint` is computed on a pre-rounding amount while the actually-transferred external amount differs, allowing the ceiling to be exceeded - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
In `Pallet::mint`, the debt-ceiling checks (`ExceedsMaxPsmDebt` for both aggregate and per-asset ceilings) are performed using `internal_equivalent`, a value derived by converting the user-supplied `external_amount` from external to internal decimals. The amount actually pulled from the user, however, is `effective_external`, produced by converting `internal_equivalent` back to external decimals. This mirrors exactly the BunniToken pattern: one quantity is used to pass a limit/deviation check, while a different (inconsistent) quantity is what is actually recorded/transferred. [1](#0-0) 

### Finding Description
`mint()` computes:
```
internal_equivalent = external_to_internal(external_amount, ext_decimals, internal_decimals)
effective_external  = internal_to_external(internal_equivalent, ext_decimals, internal_decimals)
``` [2](#0-1) 

The debt-ceiling checks (`current_total_psm_debt + internal_equivalent <= info.max_debt` and `new_debt <= max_debt`) validate against `internal_equivalent`, and `PsmDebt` is subsequently incremented by the *same* `internal_equivalent`: [3](#0-2) [4](#0-3) 

But the actual external asset pulled from the user's account is `effective_external`, not `external_amount`: [5](#0-4) 

When `external_decimals != internal_decimals` (a supported, expected configuration per `ensure_decimals_match`), the `external_to_internal` → `internal_to_external` round trip is lossy in the direction that *truncates down* when `internal_decimals < ext_decimals` (dividing by a power of ten discards the low-order digits of `external_amount`). This is the same "check value ≠ settlement value" divergence the Bunni report flags: `internal_equivalent` (what's checked and used to move `PsmDebt` and mint tokens) is computed from `external_amount`, but the reserve/backing actually collected (`effective_external`) can systematically be smaller than what `internal_equivalent` nominally represents when accumulated across many mint calls with amounts chosen at the truncation boundary. Because the ceiling checks operate purely on `internal_equivalent`/`PsmDebt` bookkeeping and never re-validate against the *actually deposited* `effective_external` reserve total, the internal-asset debt recorded (and backing assumed 1:1) can drift out of sync with what the reserve genuinely received, in the same spirit as the Bunni deviation check vs. final value computation using inconsistent inputs.

### Impact Explanation
`PsmDebt` is the pallet's accounting invariant asserting that internal-asset supply issued through a given `(internal_asset, external_asset)` pair is 1:1 backed by the external reserve. If the amount used for ceiling/debt bookkeeping doesn't match the amount that lands in the reserve, an attacker can, over many mint calls at rounding boundaries, cause the recorded debt/backing relationship to diverge from the real reserve balance, undermining the PSM's core peg-backing guarantee (asset accounting invariant break, no privileged actor needed).

### Likelihood Explanation
Requires only an unprivileged, signed `mint` call, with `external_decimals != internal_decimals`, which is an explicitly supported, unprivileged-user-triggerable configuration (`add_external_asset`/decimals metadata is arbitrary per asset). No governance, relayer, or validator involvement is needed; a normal user chooses `external_amount` values at truncation boundaries to repeatedly trigger the divergence.

### Recommendation
Use the same quantity for both the ceiling check and the transferred/recorded amount: either (a) validate the ceiling against `effective_external`'s corresponding internal equivalent after the round-trip, not the pre-rounding `internal_equivalent`, or (b) transfer/require `external_amount` itself (rejecting if it doesn't round-trip exactly) instead of silently accepting a lower `effective_external`. Align debt accounting and actual reserve transfer to the same rounding-consistent value, as recommended in the source report ("align the methodology used in both calculations").

### Proof of Concept
1. Register a PSM with `internal_decimals = 6` and an external asset with `ext_decimals = 18` (a supported, common stablecoin decimal mismatch).
2. Call `mint(internal_asset, external_asset, external_amount, max_fee)` repeatedly with `external_amount` values just above a `10^12` boundary (the conversion factor), so that `internal_equivalent = external_amount / 10^12` rounds down, and `effective_external = internal_equivalent * 10^12` is strictly less than the original `external_amount`.
3. Observe: the debt-ceiling check and `PsmDebt` increment use `internal_equivalent` (consistent with the *intended* full `external_amount`), while `T::Fungibles::transfer` only pulls `effective_external` from the user — less than what a naive observer computing backing from `PsmDebt * peg_ratio` would expect was deposited.
4. Repeating this at scale accumulates a growing shortfall between assumed 1:1 backing (per `PsmDebt`) and actually collected reserve, exactly analogous to the Bunni report's "deviation check passes on one basis while the real value differs." [6](#0-5)

				.ok_or(Error::<T>::UnsupportedAsset)?;

			let internal_equivalent =
				Self::external_to_internal(external_amount, ext_decimals, internal_decimals)?;
			ensure!(!internal_equivalent.is_zero(), Error::<T>::AmountTooSmallAfterConversion);
			ensure!(internal_equivalent >= info.min_swap_amount, Error::<T>::BelowMinimumSwap);

			let effective_external =
				Self::internal_to_external(internal_equivalent, ext_decimals, internal_decimals)?;

			let fee_rate = MintingFee::<T>::get(&internal_asset, &external_asset);
			ensure!(fee_rate <= max_fee, Error::<T>::FeeTooHigh);
			let fee = fee_rate.mul_ceil(internal_equivalent);
			let internal_to_user = internal_equivalent.saturating_sub(fee);

			let current_total_psm_debt = Self::total_psm_debt(&internal_asset);
			ensure!(
				current_total_psm_debt.saturating_add(internal_equivalent) <= info.max_debt,
				Error::<T>::ExceedsMaxPsmDebt
			);

			let current_debt = PsmDebt::<T>::get(&internal_asset, &external_asset);
			let max_debt = Self::max_asset_debt(&internal_asset, &external_asset, &info);
			let new_debt = current_debt.saturating_add(internal_equivalent);
			ensure!(new_debt <= max_debt, Error::<T>::ExceedsMaxPsmDebt);

			let psm_account = Self::psm_account(&internal_asset);
			T::Fungibles::transfer(

				Preservation::Expendable,
			)?;

			if !fee.is_zero() {
				T::Fungibles::mint_into(internal_asset.clone(), &info.fee_destination, fee)?;
			}
