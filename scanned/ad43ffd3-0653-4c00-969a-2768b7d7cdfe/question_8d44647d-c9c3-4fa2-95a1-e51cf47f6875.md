Target: `StackerDBSession::get_chunks`/`get_chunk` slot-version request path in libsigner/src/session.rs. Attacker action: a malicious node responds to `GET /v2/stackerdb/.../<slot_id>/<slot_version>` with HTTP 200 and a chunk body for a *different* `slot_id`/`slot_version` than requested (server confusion or cache poisoning simulation). Preconditions: session communicates over a connection the attacker controls (relevant when the signer is itself acting as an HTTP client to an untrusted/compromised peer node). Call sequence: `rpc_request(\"GET\", &path, ...)` returns raw bytes with no re-validation that the returned payload's embedded slot/version metadata matches the requested `(slot_id, slot_version)`. Equality/fault: the `(slot_id, slot_version)` embedded in/implied by the returned chunk bytes must equal the tuple requested in `path`; `StackerDBSession` performs no such check, trusting the transport layer's URL routing alone. Impact: Critical - if reachable via a compromised/malicious peer serving the node role, this lets a wrong chunk be silently accepted as if it were the requested version. Proof: test with a fake HTTP server returning arbitrary bytes regardless of requested path, asserting `get_chunks` has no independent verification linking returned content to `(slot_id, version)` beyond trusting the HTTP layer.
