Target: `SignerHttpRequest::destruct`/`decode_http_request` body-offset computation in libsigner/src/http.rs feeding into `decode_http_body`. Attacker action: send an HTTP request/response where the `Content-Length` header value disagrees with the actual number of bytes following `body_offset` in `payload` (e.g. `Content-Length: 4` but 40 bytes follow, or vice versa), targeting the session client's `run_http_request` path. Preconditions: signer session connects to an attacker-controlled or MITM'd node endpoint (session.rs `rpc_request`). Call sequence: `run_http_request` -> `sock.read_to_end(&mut buf)` -> `decode_http_response` computes `body_offset` -> `decode_http_body(&headers, &buf[body_offset..])`. Equality/fault: bytes returned by `decode_http_body` must equal the length declared by `Content-Length` (non-chunked branch just does `buf.to_vec()` with no length re-validation against the header). Impact: Critical - HTTP response/request smuggling: a subsequent read on the same connection or a later chunk boundary could desynchronize, letting one logical message's trailing bytes be parsed as the start of the next. Proof: test constructing a raw response byte buffer with `Content-Length` smaller than the actual trailing bytes and asserting `decode_http_body`'s returned `Vec<u8>` length exactly matches the declared `Content-Length`, not the raw slice length.
