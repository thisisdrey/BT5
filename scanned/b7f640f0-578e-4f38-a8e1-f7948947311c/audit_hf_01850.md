# [C] C-4 Modiﬁer conditionCheck doesn't revert if no conditions passed

## Summary
Severity: Critical
Contest weight: 0.0820
Dataset id: 10273
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability is a logical flaw in a contract modifier that is intended to enforce a set of pre‑conditions before a function body is executed. The modifier iterates over configured conditions and is supposed to abort the transaction when none of the conditions evaluate to true. However, when all conditions are defined with a Logic.OR aggregation and every individual condition returns false, the modifier does not trigger a revert and the function continues to run. The root cause is the absence of a tracking flag that records whether at least one OR‑type condition has succeeded; the implementation only checks for a failure when a condition explicitly reverts, not when all conditions simply evaluate to false. An attacker can exploit this by deploying a contract that registers only OR‑type conditions that are deliberately crafted to never become true. Because the modifier mistakenly treats the “no condition passed” case as a successful check, the attacker can invoke protected functions without satisfying any of the intended safeguards. This can lead to unauthorized state changes, such as minting tokens, withdrawing funds, or altering protocol parameters, effectively bypassing access control and causing loss of assets. The issue manifests whenever a function guarded by the conditionCheck modifier is called and the set of conditions consists exclusively of OR logic with none satisfied; under those circumstances the transaction proceeds as if the conditions were met. All users, contract owners, and any parties relying on the correctness of the access‑control logic are affected because the contract may execute actions that should have been blocked. The flaw was discovered during a manual security audit where the auditors inspected the modifier’s control flow and observed that the execution path does not revert when the OR list is empty of true results. The problem can be subtle because the transaction does not fail – it appears to succeed – making it hard to notice without reviewing the condition‑evaluation logic. To remediate the issue, the modifier should maintain a boolean flag that is set to true when any OR‑type condition succeeds; after processing all conditions, the modifier must explicitly revert if the flag remains false, thereby enforcing the intended “at least one condition must be true” rule. In generic terms, this is a missing‑validation bug in composite condition handling that violates the contract’s business logic of requiring a satisfied predicate before proceeding. From a user’s perspective, actions that should be rejected (for example, a withdrawal request without proper authorization) are accepted, leading to unexpected zero‑balance checks, missing refunds, or funds disappearing without an obvious error message.

## Recommendation
We recommend adding a special ﬂag to help track that no conditions with a Logic.OR type have passed.
