## Local Analog Found

The `SecuritizeVault` bug's core invariant break is: **an accounting value (owed amount) is finalized/settled based on an optimistic assumption about an external operation's outcome, without verifying the actual result of that operation.** The closest local analog in `polkadot-sdk--037` is in the Snowbridge relayer-reward payout path, where the reward ledger entry is irrevocably deleted on the *sending* chain before there is any confirmation that the cross-chain payment actually landed on the destination.

### Title
Relayer reward ledger entry is irrevocably cleared before XCM delivery to AssetHub is confirmed, permanently losing rewards on remote execution failure - (`File: bridges/snowbridge/primitives/core/src/reward.rs`)

### Summary
`pallet_bridge_relayers::do_claim_rewards` removes the relayer's `RelayerRewards` entry and then calls `T::PaymentProcedure::pay_reward`. For `BridgeReward::Snowbridge`, this resolves to `snowbridge_core::reward::PayAccountOnLocation::pay_reward`, which only validates that an XCM *can be sent* to AssetHub — it never confirms that the `ReserveAssetDeposited`/`DepositAsset` program actually executes successfully and lands funds in the caller-supplied beneficiary. Because `pay_reward` returns `Ok(())` as soon as the message is handed to the transport layer, `try_mutate_exists` commits the removal of the reward record even though the remote deposit can still fail (e.g. trapped assets due to an unfunded/invalid beneficiary), permanently losing the reward with no way to re-claim.

### Finding Description
`do_claim_rewards` in [1](#0-0)  takes the stored reward balance out of `RelayerRewards` via `try_mutate_exists`, then calls `T::PaymentProcedure::pay_reward`. If `pay_reward` returns `Ok`, the closure returns `Ok` and the storage mutation (deleting/decrementing the reward entry) is committed.

For the Snowbridge reward kind, `pay_reward` is implemented by `BridgeRewardPayer` in [2](#0-1) , which delegates to `snowbridge_core::reward::PayAccountOnLocation::pay_reward`: [3](#0-2) 

This function builds an XCM program containing `ReserveAssetDeposited` (mint the reward asset into holding) followed by `DepositAsset { assets: AllCounted(1), beneficiary }`, and then:
1. `validate_send` — checks a route exists and computes the local delivery fee.
2. `XcmExecutor::charge_fees` — charges the relayer the local delivery fee.
3. `XcmSender::deliver(ticket)` — enqueues the message for transport (e.g., HRMP/XCMP) to AssetHub.

None of these three steps observe or wait for the *remote* execution outcome. The `DepositAsset` step executes asynchronously on AssetHub in a later block. If that deposit fails — for example the caller-supplied `beneficiary` (`BridgeRewardBeneficiaries::AssetHubLocation(VersionedLocation)` is fully attacker/user-controlled per `claim_rewards_to`, see [4](#0-3) ) resolves to an account that does not exist and cannot satisfy the Existential Deposit, or the asset isn't registered/sufficient, XCM traps the deposited asset instead of reverting the whole program. Meanwhile, on BridgeHub the `pay_reward` call already returned `Ok`, so `try_mutate_exists` has already deleted the `RelayerRewards` entry.

This exactly mirrors the external report's broken invariant: the code commits an accounting change (marks the reward as "paid"/cleared) based on the *initiation* of a value-moving operation rather than its *verified completion*, exactly like `SecuritizeVault.liquidate()` computing and transferring an amount based on a formula (`assets.mulDiv(rate, ...)`) instead of the balance actually received back from `redemption.redeem(assets)`.

### Impact Explanation
This falls under "permanent user-fund or bridge-state lock" and "duplicate settlement or payout" in the accepted impact list. A relayer's earned reward can be permanently destroyed with no recovery path: the ledger no longer records the debt (so `claim_rewards_to` can't be retried — `NoRewardForRelayer`), and the underlying value is trapped as unclaimed assets on AssetHub rather than being credited to the intended beneficiary. This directly breaks the pivot requirement that "bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" — here settlement on BridgeHub advances (storage cleared) before settlement on the destination (AssetHub) is confirmed.

### Likelihood Explanation
No privileged actor, malicious relayer/validator, or off-chain infrastructure compromise is required. Any legitimately registered relayer calling the public, signed extrinsic `claim_rewards_to` with a `beneficiary` location that cannot be credited on AssetHub (e.g., a freshly generated `AccountId32` with no existential deposit, or any location the XCM executor can't finalize `DepositAsset` against) reliably triggers this path. The existing guard (`try_mutate_exists` reverting only on an `Err` from `pay_reward`) does not help, because `pay_reward` cannot express failures that happen on the remote chain in a later block — it can only report success/failure of local send validation, fee charging, and enqueueing.

### Recommendation
Do not treat local `XcmSender::deliver` success as final settlement. Options: (1) keep the reward entry until a delivery/execution receipt (or an XCM query/notify) confirms remote success, only clearing it upon confirmation; or (2) route the payout through a mechanism that can revert/refund on remote failure (e.g., asset-trap recovery credited back to the relayer automatically), so the local ledger and remote state cannot diverge irreversibly.

### Proof of Concept
1. A relayer accumulates a `BridgeReward::Snowbridge` reward via `register_reward` (from processing inbound messages).
2. The relayer calls `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(VersionedLocation::V5(Location::new(0, [AccountId32 { network: None, id: <fresh, unfunded 32-byte id> }]))))`.
3. `do_claim_rewards` removes the `RelayerRewards` entry, calls `PayAccountOnLocation::pay_reward`, which validates/charges/delivers the XCM successfully on BridgeHub and returns `Ok(())`; the storage removal commits.
4. On AssetHub, `ReserveAssetDeposited` mints the WETH-denominated reward into holding, but `DepositAsset` to the unfunded beneficiary fails ED checks and the asset is trapped instead of credited.
5. The relayer has no reward record left (`relayer_reward` returns `None`) and cannot claim again; the value sits as an unclaimed/trapped asset on AssetHub, unrecoverable through the normal reward flow. [1](#0-0) [3](#0-2)

			relayer: T::AccountId,
			reward_kind: T::Reward,
			beneficiary: BeneficiaryOf<T, I>,

			RelayerRewards::<T, I>::try_mutate_exists(

						relayer: relayer.clone(),
						reward_kind,
						reward_balance,
						beneficiary,

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
