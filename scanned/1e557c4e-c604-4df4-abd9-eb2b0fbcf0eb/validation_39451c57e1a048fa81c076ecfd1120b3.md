## Analysis

The Hubble bug's core broken invariant is: **when the true ordering of two concurrent, price-relevant events is ambiguous, the contract lets whichever side happens to land in a favorable code-path position set the fill price for everyone — and an actor with control over ordering (the block producer choosing `orders[0]`/`orders[1]`) can exploit that ambiguity for MEV.**

Searching the repository for pricing logic that similarly derives a *shared, forward-looking* price from a single, order-dependent event inside a public dispatchable turns up `pallet-broker`'s Bulk Coretime sale mechanism.

### Title
Single-purchaser-determined `sellout_price` in `pallet-broker` lets one purchaser set the renewal/next-sale price for all other users - (`substrate/frame/broker/src/utility_impls.rs`)

### Summary
`Pallet::purchase_core` (in `substrate/frame/broker/src/utility_impls.rs:78-91`) records `sale.sellout_price = Some(price)` on **every** `purchase_core` call while `cores_sold <= ideal_cores_sold`. Because `sale_price` (line 62-66 of the same file) is a pure function of elapsed relay-chain blocks (a monotonically decreasing lead-in curve), the *last* purchase that pushes `cores_sold` across the `ideal_cores_sold` threshold permanently fixes `sellout_price` for that sale round. That single value is then propagated as the binding price for unrelated third parties: `tick_impls.rs::rotate_sale` (lines 177-241) feeds it into `T::PriceAdapter::adapt_price(...)`, and `CenterTargetPrice::adapt_price` (`adapt_price.rs:119-136`) sets `target_price: sellout_price`, which becomes the price written into every `PotentialRenewalRecord` for leases expiring that period (`tick_impls.rs:229-241`) and the baseline `end_price` for the *next* sale. ### Finding Description
`do_purchase` (`dispatchable_impls.rs:149-176`) is a fully public, unprivileged extrinsic — any signed account with funds and a `price_limit` can call it. Its price is `sale_price(&sale, now)`, which depends only on the current relay-chain block, not on which purchaser calls it or in what intra-block order. Consequently:

1. Every purchaser knows exactly what price they will pay before submitting.
2. Whoever's purchase happens to be the one that makes `cores_sold` reach/exceed `ideal_cores_sold` writes `sale.sellout_price`, unconditionally overwriting whatever the "true" market-clearing signal should have been.
3. This value is not scoped to the buyer's own transaction — it becomes `target_price` for the *next* sale and the fixed renewal price for *every other lease holder's* auto-renewal that period (`PotentialRenewalRecord.price`).

Because the lead-in price curve is strictly decreasing over time, a self-interested (or colluding-with-a-sequencer) actor can simply wait until late in the lead-in/fixed-price window — when the current `sale_price` is near its lowest point — and place the purchase that crosses the `ideal_cores_sold` boundary. This lets them fix an artificially low `sellout_price`/`target_price` that then becomes binding for all unrelated renewals and the next sale's baseline, exactly mirroring the Hubble pattern where one side's price, chosen by an arbitrary/controllable ordering event, is imposed on the counterparty who had no say in it.

`MinimumPrice` (`adapt_price.rs:145-166`) only clamps the floor an administrator configures; it does not prevent a purchaser from steering `sellout_price` anywhere between that floor and the lead-in ceiling by timing which purchase crosses the ideal-core threshold. This is precisely the historical vector referenced in `prdoc/1.13.0/pr_4521.prdoc` ("a price manipulation issue we discovered with the Kusama launch") and `prdoc/stable2506/pr_8630.prdoc` — the underlying design (one purchaser's transaction fixes a value binding on all other participants) is unchanged; only a configurable minimum bound was added. ### Impact Explanation
`sellout_price`/`target_price` sets the price for every other lease-holder's coretime renewal (`Event::Renewable`/`PotentialRenewalRecord.price` in `tick_impls.rs`) as well as the starting price of the *next* sale for the entire network of buyers. A single purchaser timing one call can therefore degrade the price signal that binds many unrelated third parties and future sale rounds, i.e. public underpriced/mispriced settlement of a shared chain resource (coretime), without needing governance, an admin, or a malicious validator/collator — only an unprivileged signed account calling a public dispatchable at the right relay-chain block.

### Likelihood Explanation
The lead-in price curve and `ideal_cores_sold` threshold are both public on-chain state (`SaleInfo`, `Configuration`), so any account can compute exactly which purchase index crosses the threshold and at what block the price will be minimal. No privileged role or block-reordering capability is required — only correctly timed submission of `purchase` calls, which is straightforward given fully deterministic, on-chain-readable state.

### Recommendation
Do not let a single purchase event irrevocably fix `sellout_price` for the whole sale. Consider deriving the price signal from an aggregate/statistic over multiple purchases around the threshold (e.g., average or median of purchases near `ideal_cores_sold`, or a VWAP-style measure) rather than "whoever happens to buy the ideal-th core," and/or bound how much a single sale's `sellout_price` can move `target_price`/renewal pricing from its prior baseline.

### Proof of Concept
1. Configure a broker sale with a lead-in period and `ideal_cores_sold = N`.
2. Track `SaleInfo::cores_sold`; as it approaches `N - 1`, wait until the relay-chain block advances toward the end of the lead-in period so `sale_price` is near its minimum.
3. Call `Pallet::purchase` (dispatching `do_purchase`) at that low price, making `cores_sold == N` (crossing the ideal threshold) — `purchase_core` sets `sale.sellout_price = Some(low_price)`.
4. At `rotate_sale`, `T::PriceAdapter::adapt_price` computes `target_price = low_price` (via `CenterTargetPrice`/`MinimumPrice`), which is then written as the renewal price for every other lease-holder's `PotentialRenewalRecord` and as the new sale's baseline — none of whom had any say in that price.

		sale: &mut SaleInfoRecordOf<T>,

		sale.cores_sold.saturating_inc();

		who: T::AccountId,
		price_limit: BalanceOf<T>,
	) -> Result<RegionId, DispatchError> {
		let status = Status::<T>::get().ok_or(Error::<T>::Uninitialized)?;
		let mut sale = SaleInfo::<T>::get().ok_or(Error::<T>::NoSales)?;
		Self::ensure_cores_for_sale(&status, &sale)?;

		let now = RCBlockNumberProviderOf::<T::Coretime>::current_block_number();
		ensure!(now > sale.sale_start, Error::<T>::TooEarly);
		let price = Self::sale_price(&sale, now);
		ensure!(price_limit >= price, Error::<T>::Overpriced);

		let core = Self::purchase_core(&who, price, &mut sale)?;

		SaleInfo::<T>::put(&sale);
		let id = Self::issue(
			core,
			sale.region_begin,
			CoreMask::complete(),
			sale.region_end,
			Some(who.clone()),
			Some(price),
		);
		let duration = sale.region_end.saturating_sub(sale.region_begin);
		Self::deposit_event(Event::Purchased { who, region_id: id, price, duration });
		Ok(id)
	}
