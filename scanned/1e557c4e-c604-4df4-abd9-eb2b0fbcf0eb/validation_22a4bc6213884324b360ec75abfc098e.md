Found a real analog: `process_delivery_receipt` in the Snowbridge outbound-queue-v2 pallet pays out relayer rewards from `PendingOrders` while completely ignoring the `success` field of the `DeliveryReceipt` decoded from the Ethereum event log.

### Title
Relayer reward paid regardless of on-chain delivery outcome due to ignored `success` field - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
`process_delivery_receipt` only checks that the `gateway` matches and that a `PendingOrder` exists for the given `nonce`; it never inspects `receipt.success`. Any signed relayer who can produce a verified event log (even one reporting a failed Ethereum-side execution) can drain the fee attached to a `PendingOrder`, exactly mirroring the reported bug class: a public entry point checks only a coarse invariant (order exists / gateway matches) instead of the semantic condition that should gate payout (successful delivery), letting an unprivileged caller access funds that were meant to be released only under a specific condition.

### Finding Description
`DeliveryReceipt` decoded from the Ethereum `InboundMessageDispatched` event carries a `success: bool` field [1](#0-0) . In `Pallet::process_delivery_receipt`, after verifying the gateway address matches and fetching the `PendingOrder` for `receipt.nonce`, the pallet pays the relayer reward and removes the order — without ever reading `receipt.success`: [2](#0-1) 

The `submit_delivery_receipt` extrinsic only performs Merkle/beacon proof verification (`T::Verifier::verify`) and gateway/envelope decoding before calling this function, and never checks `success` either: [3](#0-2) 

Because the Ethereum Gateway contract emits `InboundMessageDispatched` regardless of whether the dispatched command actually succeeded on Ethereum (the receipt records both outcomes), a legitimately-verified event log with `success: false` is treated identically to a successful delivery. The pallet's own tests confirm the code path never gates on `success` — the only two negative-path tests target `Halted` verifier state and a missing/invalid nonce, not the receipt's outcome flag: [4](#0-3) [5](#0-4) 

This is analogous to the reported burn-instruction bug: the withdrawal-adjacent function only validates a coarse structural invariant ("does a ticket/order exist for this identifier, and is the amount/gateway plausible") rather than the actual precondition that should authorize release of value ("was the withdrawal/delivery legitimately completed").

### Impact Explanation
Any account that submits a valid (but failed-on-Ethereum) delivery-receipt proof drains the fee reserved in `PendingOrders` for that nonce, which is meant to reward only relayers who actually completed delivery. This is theft/unbacked payout of bridge relayer rewards and duplicate/incorrect settlement of `PendingOrder` state (the order is removed and paid out even though delivery failed), directly matching the "theft or unbacked mint or unlock, duplicate settlement or payout" impact category for Snowbridge.

### Likelihood Explanation
Any signed account holding a genuine Ethereum event-log proof for a failed `InboundMessageDispatched` event (which the relayer network produces naturally whenever gas runs out or a dispatched command reverts on Ethereum) can call `submit_delivery_receipt` with `success: false` and still be paid. No malicious peer, validator, or governance actor is needed — this is exploitable by an ordinary relayer/user with access to public Ethereum chain data.

### Recommendation
Add an explicit check in `process_delivery_receipt` that `receipt.success` is `true` before paying the reward; on `false`, either reject the call, or handle the failed-delivery case explicitly (e.g., only remove the order and/or apply different accounting), so that reward payout is conditioned on the semantic success of the message dispatch and not just the existence of a `PendingOrder` matching the nonce.

### Proof of Concept
1. A message with `nonce = N` and `fee > 0` is queued via `do_process_message`, creating `PendingOrders[N]`.
2. On Ethereum, the Gateway attempts to dispatch the command but it reverts/fails; the Gateway still emits `InboundMessageDispatched(nonce=N, success=false, ...)`.
3. Any account obtains the standard Merkle/receipt proof for this real (but failed) event and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (it's a genuine proof), `DeliveryReceipt::try_from` decodes `success: false`, `gateway` matches, `PendingOrders::get(N)` returns `Some(order)`.
5. `process_delivery_receipt` pays `order.fee` to the relayer/reward account and removes the order from storage — exactly as it would for a successful delivery, per [6](#0-5) .

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

// should not pay out `PendingOrder` fees if the verifier reports the bridge as halted.

fn poc_m1() {
	new_tester().execute_with(|| {

		let origin = RuntimeOrigin::signed(relayer);

	});
