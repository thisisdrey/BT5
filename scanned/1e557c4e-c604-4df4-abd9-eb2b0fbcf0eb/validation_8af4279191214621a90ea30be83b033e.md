## Analysis

The external report's core broken invariant is: **a value that must exactly and unambiguously identify a deterministic address/state (the `CREATE2` salt) is computed/represented in a way that doesn't match what other legitimate consumers of the same protocol expect**, causing a mismatch between the address a caller believes will be produced and the address that is actually produced on-chain.

Searching `pallet-revive` (the EVM/CREATE1/CREATE2-compatible execution pallet) for an analogous "address-derivation value mismatch" turns up a documented, functionally identical class of bug in `Stack::new_frame`, and — critically — the fix described in `prdoc/stable2506/pr_8504.prdoc` for this exact bug is **not present in the current `exec.rs` code** in this repository snapshot (`grep_search` for `ExecContext` only matches the prdoc file, never `exec.rs`).

### Title
`CREATE1` contract address derivation in dry-run/RPC simulation uses the wrong nonce, producing an address that diverges from the actual on-chain deployment address - (File: `substrate/frame/revive/src/exec.rs`)

### Summary
`Stack::new_frame` derives the `CREATE1` contract address from `account_nonce.saturating_sub(1)` whenever `origin_is_caller` is true, regardless of whether the call is a real dispatched transaction or a dry-run/`eth_estimateGas`/RPC simulation. In a dry run the account nonce is never incremented pre-dispatch (there is no `CheckNonce` extension pass), so subtracting 1 computes an address for nonce `N-1` instead of the correct `N`, causing the address reported to callers (wallets, tooling, other contracts relying on `eth_call`-simulated `to`) to differ from the address that will actually be used once the real transaction executes.

### Finding Description [1](#0-0) 

```rust
FrameArgs::Instantiate { sender, executable, salt, input_data } => {
    let deployer = T::AddressMapper::to_address(&sender);
    let account_nonce = <System<T>>::account_nonce(&sender);
    let address = if let Some(salt) = salt {
        address::create2(&deployer, executable.code(), input_data, salt)
    } else {
        use sp_runtime::Saturating;
        address::create1(
            &deployer,
            // the Nonce from the origin has been incremented pre-dispatch, so we
            // need to subtract 1 to get the nonce at the time of the call.
            if origin_is_caller {
                account_nonce.saturating_sub(1u32.into()).saturated_into()
            } else {
                account_nonce.saturated_into()
            },
        )
    };
```

The comment states the premise explicitly: the nonce subtraction is only valid "because the nonce is incremented pre-dispatch" by `frame_system::CheckNonce`. This holds for a normal signed extrinsic, but not for the dry-run/simulation path exposed via `ExecConfig::is_dry_run` (set by `dry_run_eth_transact` and other RPC helpers in `substrate/frame/revive/src/lib.rs`), where no `CheckNonce` extension runs and the stored nonce is never bumped before `new_frame` reads it. [2](#0-1) 
The `ExecConfig` struct already carries an `is_dry_run` flag distinguishing this execution context, and it is consulted elsewhere in `exec.rs` (e.g. to decide whether to keep return data), but it is **not** consulted in the `create1` nonce computation shown above. [3](#0-2)  documents that upstream Parity fixed exactly this bug by additionally gating the subtraction on `matches!(exec_context, ExecContext::Transaction)`. That gate is absent from the `exec.rs` in this repository snapshot — `ExecContext` does not appear anywhere in `substrate/frame/revive/src/exec.rs`, only in the prdoc description of the fix, confirming the vulnerable pre-fix logic is what is actually shipped in this codebase state.

This is the direct structural analog of the `minievm` report: a value feeding into deterministic address derivation (there: an under-typed `salt`; here: a miscalculated `nonce`) is computed inconsistently across different call paths (CLI vs gRPC there; real transaction vs RPC dry-run here), so the derived contract address diverges from what other tooling/consumers expect for the "same" logical deployment.

### Impact Explanation
Any wallet, deployment tool, or on-chain integration that relies on `eth_call`/`eth_estimateGas`-style dry-run simulation (or any other `bare_instantiate`/`dry_run_eth_transact` caller with `origin_is_caller == true`) to predict the address of a `CREATE1` (no-salt) contract deployment will be given an address for nonce `N-1` rather than the nonce `N` address that is actually produced when the real transaction is submitted. Funds, approvals, or cross-contract references pre-computed against the simulated address will point at the wrong account. Since Ethereum tooling commonly funds or references a to-be-deployed contract address before deployment (counterfactual patterns, e.g. pre-funding a deterministic deploy address), this can result in value being sent to an address that never becomes the intended contract, causing permanent loss/lock of those funds — matching the "permanent user-fund lock" impact category.

### Likelihood Explanation
This is triggerable by any unprivileged user through the standard, publicly exposed dry-run/RPC simulation entrypoints (`eth_estimateGas`, `eth_call` for contract creation, `dry_run_eth_transact`), with no special permissions, malicious peer, relayer, or governance action required — it is a pure implementation defect in a public code path that any Ethereum-compatible wallet already exercises for every `CREATE1` deployment (i.e., whenever a caller submits contract-creation calldata with no `to` and no salt). The nonce mismatch is deterministic and reproducible on every such simulation, not a race condition or a rare edge case.

### Recommendation
Gate the `saturating_sub(1)` nonce adjustment on the actual execution context, not merely on `origin_is_caller`, matching the shape of the upstream fix: only subtract 1 when the call is genuinely a dispatched transaction where `CheckNonce` has already incremented the account nonce pre-dispatch (i.e., `exec_config.is_dry_run.is_none()`), and use the raw `account_nonce` otherwise. Add a regression test analogous to `nonce_not_incremented_in_dry_run()` that asserts dry-run and actual-transaction `CREATE1` deployments compute identical addresses.

### Proof of Concept
1. Fund `ALICE` and note her current on-chain nonce `N` for `pallet-revive`.
2. Call `dry_run_eth_transact` (or the equivalent runtime API `eth_estimate_gas`/`eth_call`) with `to = None` and `input` set to raw contract-creation bytecode (no salt) — this hits `FrameArgs::Instantiate` with `salt = None`, `origin_is_caller = true`, and `exec_config.is_dry_run = Some(..)`.
3. Observe the returned contract address, computed via `address::create1(&deployer, N - 1)`.
4. Submit the real signed extrinsic performing the same deployment. `CheckNonce` increments the stored nonce to `N + 1` pre-dispatch; `new_frame` reads `account_nonce = N + 1`, subtracts 1, and computes `address::create1(&deployer, N)` — one nonce value higher than what step 3 reported.
5. The two computed addresses differ, confirming the dry-run result is unreliable and diverges from the actual deployment address, exactly as described in `prdoc/stable2506/pr_8504.prdoc`'s "Before Fix" behavior — which remains present in this repository's `exec.rs`.

    The code correctly subtracts 1 from the account nonce during a transaction execution (because the nonce is incremented pre-dispatch), but doesn't account for execution context - whether it's a real transaction or a dry run through the RPC.

    ## Review Notes

    This PR adds a new condition to check for the `ExecContext` when calculating the nonce for address derivation:

    ```rust
    address::create1(
        &deployer,
        // the Nonce from the origin has been incremented pre-dispatch, so we
        // need to subtract 1 to get the nonce at the time of the call.
        if origin_is_caller && matches!(exec_context, ExecContext::Transaction) {
            account_nonce.saturating_sub(1u32.into()).saturated_into()
        } else {
            account_nonce.saturated_into()
        },
    )
    ```
