### Title
`process_offence` discards a stuck offence without decrementing `ProcessingOffence`/`OffenceQueueEras`, permanently blocking `withdraw_unbonded` chain-wide - ([File: substrate/frame/staking-async/src/slashing.rs])

### Summary
`pallet-staking-async` intentionally blocks `withdraw_unbonded` (via `calculate_earliest_withdrawal_era`) until all offences for older eras are drained from `OffenceQueueEras`. This is the same broken-invariant shape as the Astaria `PublicVault.processEpoch()` bug: a global "gate" function reverts/refuses to proceed while a per-item counter/flag remains non-zero, and that flag is only cleared by a specific processing path. In Astaria, `liquidate()` is the (permissionless) escape hatch. Here, offence processing (`process_offence`) is the automatic, non-permissioned "escape hatch" that runs once per block in `on_initialize` — but unlike `liquidate`, there is no separate, callable-by-anyone recovery function if `process_offence` hits a data path that causes it to give up on an item without removing it from the front of the queue.

### Finding Description
`calculate_earliest_withdrawal_era` (`substrate/frame/staking-async/src/pallet/impls.rs:229-257`) computes the earliest era withdrawals are permitted using `OffenceQueueEras::<T>::get().first()`; as long as any era remains at the head of `OffenceQueueEras`, withdrawals for all stakers system-wide are capped below that era. The only way this head era is removed is through `next_offence::<T>()` (`substrate/frame/staking-async/src/slashing.rs:114-176`), invoked from `process_offence`/`process_offence_for_era` in every block's offence-processing step.

`next_offence` pops the oldest queued entry from `OffenceQueue` immediately (line 160: `OffenceQueue::<T>::remove(oldest_era, &validator)`) and, if it is the last entry for that era, removes the era from `OffenceQueueEras` (lines 163-173) — **before** any check of whether the corresponding exposure data still exists. Control then returns to `process_offence` (`slashing.rs:200-210`), which tries to fetch `Eras::<T>::get_paged_exposure(offence_era, &offender, offence_record.exposure_page)`. If the exposure page is missing (`None`), the function comment states this "can only happen if the offence was valid at the time of reporting but became too old at the time of computing," and it simply `return`s, discarding the offence. Similarly, `compute_slash` (line 217-234) can return `None` and the record is silently discarded.

These "discard" paths are handled correctly **when the offence has already been dequeued** by `next_offence` (single-page offence, or last page of a multi-page offence). But for a **multi-page** offence that is not yet on its last page, `next_offence` (lines 145-157) instead **keeps** the entry alive by writing it into `ProcessingOffence` with the page decremented, without removing it from `OffenceQueueEras`. If `get_paged_exposure` for that decremented page also returns `None` (fully plausible: exposure was pruned across history-depth boundaries per page, or `ErasStakersOverview`/paged exposure for a specific page was never populated due to a prior era-transition edge case), `process_offence` returns early at line 209 **without clearing `ProcessingOffence`**. On the next block, `next_offence` will call the branch at lines 117-136: since `offence_record.exposure_page` is still greater than 0 (only decremented from the previous value, not reaching 0), it again just decrements and re-stores `ProcessingOffence`, then `process_offence` again fails the same exposure lookup and discards. This can repeat, but critically, **the offence era is never removed from `OffenceQueueEras`** until `exposure_page` eventually reaches `0` and `next_offence` explicitly `kill()`s `ProcessingOffence` (line 119-122) and returns the entry to `process_offence` for a final discard — at which point the era entry check in `next_offence` for *that* branch never re-runs to also purge `OffenceQueueEras`, because the "remove from `OffenceQueueEras`" logic only executes in the "fresh dequeue from `OffenceQueue`" branch (lines 163-173), not in the "continuing a `ProcessingOffence`" branch (lines 117-136).

Net effect: an offence whose exposure data is unavailable across all its remaining pages leaves `OffenceQueueEras` permanently populated with its era at the head, because the code path that clears `OffenceQueueEras` is skipped whenever the offence is resumed from `ProcessingOffence` rather than freshly pulled from `OffenceQueue`.

### Impact Explanation
Once `OffenceQueueEras` is stuck with a non-removable head era, `calculate_earliest_withdrawal_era` permanently returns a bounded era for the entire chain (`active_era.min(earliest_unlock_era_by_offence_queue)`), meaning **every staker's `withdraw_unbonded` call** across the whole runtime is capped, potentially indefinitely, well beyond `BondingDuration`. This is a chain-wide, permanent fund lock — a much larger blast radius than the original Astaria per-vault liquidate scenario, and unlike Astaria's `liquidate()`, there is no user-callable, permissionless function in this pallet to force-clear a stuck `OffenceQueueEras`/`ProcessingOffence` entry (the permissionless `apply_slash` extrinsic operates on `UnappliedSlashes`, which is never populated for a discarded offence, so it cannot help).

### Likelihood Explanation
Triggering requires a validator to have a multi-page exposure whose paged exposure data becomes unavailable for at least one page while an offence for it is queued — a scenario the code's own comments acknowledge as possible ("this can only happen if the offence was valid at the time of reporting but became too old at the time of computing"), i.e., it is a data-availability edge case reachable by legitimate historical-depth pruning / era rotation timing rather than requiring a malicious validator, governance, or relayer action. This matches the report's own framing of an "extremely rare" edge case (per `prdoc/stable2509/pr_9079.prdoc`) — exactly analogous to the medium-severity, acknowledged classification of the original Astaria finding.

### Recommendation
In `next_offence`'s "continuing `ProcessingOffence`" branch, when the offence is finally discarded (whether via `kill()` after `exposure_page == 0`, or via early-return paths in `process_offence`/`compute_slash` on missing exposure/slash data), explicitly re-check whether `OffenceQueue` still has entries for that `offence_era`, and if not, remove `offence_era` from `OffenceQueueEras` — mirroring the cleanup that already happens in the "fresh dequeue" branch. Alternatively, expose a permissionless recovery call analogous to `apply_slash`/`liquidate()` that lets anyone force-purge an era from `OffenceQueueEras` once it is confirmed to have no live entries in `OffenceQueue`/`ProcessingOffence`.

### Proof of Concept
Conceptual reproduction (concrete PoC requires wiring a mock exposure store that returns `None` for a specific paged index while the offence is mid-processing, which needs full test-harness access beyond static code review):
1. Report a multi-page offence for validator `V` in era `E` such that `exposure_page > 0` when first dequeued by `next_offence` (`slashing.rs:145-157`), so it is pushed into `ProcessingOffence` and `OffenceQueue::remove` fires — leaving `OffenceQueueEras` still containing `E` only if other entries exist for `E`, or removed if `E` was the sole entry (either way `ProcessingOffence` holds the live cursor).
2. Arrange (e.g., via history-depth eviction/era pruning race, or by manipulating exposure page bounds through repeated offence reports across era boundaries) for `Eras::<T>::get_paged_exposure(E, V, page)` to return `None` on a subsequent page before `exposure_page` reaches `0`.
3. Each subsequent block, `process_offence` returns early at `slashing.rs:204-210` without ever calling `next_offence`'s `OffenceQueueEras` cleanup logic for the "continuing" branch.
4. Confirm via `OffenceQueueEras::<T>::get()` that `E` remains listed indefinitely, and that `Staking::withdraw_unbonded` for an unrelated staker with unlocking chunks at or above `E` continues returning less than the full unlocked amount (or is capped) forever, per `calculate_earliest_withdrawal_era` (`pallet/impls.rs:232-257`).

**Uncertainty note:** I was not able to execute the runtime test suite to confirm whether some other code path (e.g. `ErasStakersOverview`/history-depth invariants) makes the "missing paged exposure while `exposure_page > 0`" scenario actually unreachable in practice; this analysis is based on static reading of `substrate/frame/staking-async/src/slashing.rs` and `substrate/frame/staking-async/src/pallet/impls.rs`. Confirming exploitability would require running/instrumenting the existing `substrate/frame/staking-async/src/tests/slashing.rs` test harness (e.g. extending `withdrawals_are_blocked_for_unprocessed_and_unapplied_slashes`) to force a paged-exposure miss mid-processing.
