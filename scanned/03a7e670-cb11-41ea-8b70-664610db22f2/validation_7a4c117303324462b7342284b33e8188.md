## Title
Snowbridge Outbound Queue V2 accepts an unvalidated, user-supplied `fee` per message, allowing cheap AssetHub-originated spam to clog the shared per-block Merkle commitment and stall Ethereum-bound bridge delivery — ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
The Across report's core broken invariant is: *the cost of admitting work into a queue is decoupled from the cost of executing that work downstream, and legitimate work gets batched together with spam so no one can safely execute or safely ignore the batch.* The Snowbridge Outbound Queue V2 pallet reproduces this exact pattern. `Message.fee` is a caller-supplied `u128` that is never checked against the actual Ethereum gas cost of the commands it carries, and every accepted message — spam or legitimate — is committed into the *same* per-block Merkle root in `MessageLeaves`, which a relayer must relay/execute on Ethereum to earn any reward at all.

### Finding Description
`Message` (outbound v2 primitive) carries an attacker-controlled fee field with no bound relative to the cost of processing: [1](#0-0) 

`SendMessage::validate` for V2 only checks payload size — it does **not** validate or enforce any minimum fee, unlike the V1 pipeline which computes `Fee` from `GasMeter::maximum_dispatch_gas_used_at_most` and `PricingParameters`: [2](#0-1) 

Compare with V1, where the fee is computed by the protocol itself from gas usage and pricing parameters, not supplied by the caller: [3](#0-2) 

`do_process_message` in V2 takes the caller-supplied `fee` verbatim and stores it as the `PendingOrder.fee` that will eventually be paid to whichever relayer submits the delivery receipt — with no minimum-fee floor, and it appends the message's leaf hash into the *shared* `MessageLeaves` for that block regardless of fee level: [4](#0-3) 

The only throttle is a raw count cap (`MaxMessagesPerBlock`) that yields/postpones messages once the block's leaf count is reached — it has no notion of "value" or "fee-worthiness", so a flood of `fee: 0` (or negligible-fee) messages can consume this budget every block ahead of legitimate messages: [5](#0-4) 

Each block's commitment mixes every accepted message — spam and legitimate — into one Merkle root that is written into the header digest, exactly mirroring Across's "batched leaves" problem: the whole batch must be relayed as a unit, and a relayer who wants to collect real rewards from legitimate messages must relay/execute the entire commitment on Ethereum (i.e., pay Ethereum gas) including the worthless spam entries mixed into the same tree: [6](#0-5) 

Origination of these messages is gated only by "sender is Asset Hub" (a whole parachain, not a specific privileged actor) — any unprivileged AssetHub account can construct an XCM program that gets exported to Ethereum via this exporter, and the exporter passes through whatever `Message` (including its `fee`) the converter produces: [7](#0-6) 

The pattern is identical to the Across bug class: cheap-side admission (BridgeHub/AssetHub XCM execution is cheap relative to Ethereum) with no minimum-value gate, expensive-side settlement (Ethereum gas for `submit_delivery_receipt`/gateway execution) paid by a third party (the relayer, an unprivileged public role — analogous to the "dataworker"), and batching of spam with legitimate entries into one atomic unit (the per-block Merkle root) that must be executed together.

### Impact Explanation
This falls squarely within "public underpriced work that degrades block production or stalls bridge processing": an attacker can force the outbound-queue-v2 pipeline to accept large volumes of near-zero-fee messages every block. Because `MaxMessagesPerBlock` is a raw slot cap with no fee-based priority, spam consumes the block's message budget, causing legitimate, properly-fee-paying messages to be `Yield`-ed/postponed indefinitely (`Event::MessagePostponed`), delaying legitimate Ethereum-bound transfers/commands. Even where legitimate messages do get included, they are committed into the same Merkle root as the spam, so a relayer cannot cherry-pick and must incur the marginal Ethereum gas cost of proving/relaying the spam leaves as well, discouraging relaying and leaving `PendingOrders` for legitimate messages unresolved — i.e., stalled bridge processing and unpaid legitimate rewards, the direct analog of the Across "lose-lose" dataworker scenario.

### Likelihood Explanation
High. No privileged role, governance action, malicious validator/collator, or off-chain infrastructure is required — a normal, unprivileged AssetHub account can repeatedly submit XCM programs that get exported through this path with `fee = 0` (or trivially small), at the low cost of AssetHub XCM execution. The only "cost" to the attacker is ordinary transaction fees on AssetHub/BridgeHub, which are cheap relative to Ethereum gas, exactly reproducing the cross-chain cost asymmetry described in the source report.

### Recommendation
- Enforce a protocol-computed minimum fee for V2 messages (as V1 already does via `GasMeter`/`PricingParameters`), rejecting `validate` calls whose supplied `fee` is below the computed minimum cost of dispatch + expected Ethereum gas.
- Make `MaxMessagesPerBlock`/queue admission fee-aware (e.g., prioritize or reserve slots by fee) so zero/low-fee messages cannot crowd out legitimate ones.
- Consider partitioning or capping the number of low-fee messages that can be committed into a single Merkle root, or allow relayers to skip/exclude specific leaves rather than forcing all-or-nothing batch relay.

### Proof of Concept
1. From an unprivileged AssetHub account, construct an XCM program that is routed to the `EthereumBlobExporter`/V2 converter path with a `CallContract`/other command and set the resulting `Message.fee` to `0` (the converter/XCM instructions controlling fee are user-supplied; `validate` performs no fee check, only size).
2. Submit this repeatedly (bounded only by ordinary AssetHub/BridgeHub tx fees) until `MessageLeaves` reaches `MaxMessagesPerBlock` for several consecutive blocks, as shown to be an enforced cap in `do_process_message`.
3. Observe legitimate, properly-fee-paying messages submitted in the same window emit `Event::MessagePostponed` (`Yield`) because the block's leaf slots are consumed by the zero-fee spam.
4. Observe that spam messages nonetheless get committed into the shared `MessageLeaves` Merkle root each block (`commit()`), and their `PendingOrder{fee: 0}` entries remain unresolved since no rational relayer submits `submit_delivery_receipt` for zero reward, while any relayer wanting to collect on the legitimate messages must still prove/relay the same root containing the spam.

impl<T> SendMessage for Pallet<T>
where
	T: Config,

	type Ticket = Message;

	fn validate(message: &Message) -> Result<Self::Ticket, SendError> {
		// The inner payload should not be too large
		let payload = message.encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		Ok(message.clone())
	}

	fn deliver(ticket: Self::Ticket) -> Result<H256, SendError> {
		let origin = ticket.origin.into();

		let message =
			BoundedVec::try_from(ticket.encode()).map_err(|_| SendError::MessageTooLarge)?;

		T::MessageQueue::enqueue_message(message.as_bounded_slice(), origin);
		Self::deposit_event(Event::MessageQueued { message: ticket.clone() });
		Ok(ticket.id)
	}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large

		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}

			let count = MessageLeaves::<T>::decode_len().unwrap_or_default() as u64;

				return;
			}

			<frame_system::Pallet<T>>::deposit_log(digest_item);

			T::OnNewCommitment::on_new_commitment(root);

			Self::deposit_event(Event::MessagesCommitted { root, count });
		}
