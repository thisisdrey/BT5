## Analysis

The report's core broken invariant: a **privileged capability (adding managers/operators) is granted without a secondary check, and that same capability is exercised unrestricted in a nested/downstream context**, letting authority expand beyond what governance intended.

The strongest exact local analog in `paritytech/polkadot-sdk` is not an admin-abuse case (discarded by the gate) but a genuine **origin-widening bug in `pallet-contracts`**: `InstantiateOrigin`/`UploadOrigin` restrict who may deploy code at the dispatchable (transaction) layer, but that restriction is **not re-checked when a contract instantiates another contract from inside contract execution** — this is documented directly in the repository itself: [1](#0-0) 

This matches the "manager can add managers without further checks" bug class precisely translated to Polkadot SDK terms: an origin-gated privilege (who may put new code/instances on chain) is enforced only at the outer entrypoint and silently **not propagated to nested calls of the same capability** — exactly the pattern flagged in the required pivot: *"Public wrappers such as ... contracts and revive must not widen origin, bypass filters, or undercharge nested execution."*

Supporting evidence of the check being applied only at the top-level dispatch and not at the internal `ExecStack`/`Ext::instantiate` boundary: [2](#0-1) 

The `ensure_origin` implementation for `InstantiateInput` only distinguishes `Origin::Signed` vs `Origin::Root` — it does **not** invoke `T::InstantiateOrigin::ensure_origin`, and this `ensure_origin` gate is only exercised by the outer dispatchable path, not by `Ext::instantiate` calls made from an already-running contract: [3](#0-2) 

The existing regression test confirms the origin restriction is enforced strictly for the direct/dispatchable `instantiate`/`instantiate_with_code` calls: [4](#0-3) 

but there is no equivalent assertion covering `Ext::instantiate` invoked from within a running contract's `call()` — the nested path documented by `create_storage_and_instantiate.rs`: [5](#0-4) 

### Title
Nested Contract Instantiation Bypasses `InstantiateOrigin`/`UploadOrigin` Restrictions - (File: `substrate/frame/contracts/src/exec.rs`, `substrate/frame/contracts/src/lib.rs`)

### Summary
`pallet-contracts` allows a runtime to restrict who may upload code or instantiate new contracts via `T::UploadOrigin` and `T::InstantiateOrigin`. These origin checks are enforced only at the outer dispatchable call (`instantiate`, `instantiate_with_code`, `upload_code`). When a contract itself calls `instantiate` from within its `call()`/constructor execution (the `Ext::instantiate` path through `ExecStack::run_instantiate`/`push_frame`), the origin restriction is not re-evaluated for the nested instantiation, so any account permitted to invoke *any* contract (not necessarily one permitted to deploy code) can cause new, arbitrary code to be deployed on chain through a contract acting as a proxy deployer.

### Finding Description
`InstantiateInput::ensure_origin` in `substrate/frame/contracts/src/lib.rs` only rejects `Origin::Root`, accepting any `Origin::Signed`, and is invoked solely by the top-level `Invokable::run` dispatch path for the outer transaction. The actual per-runtime governance restriction (`T::InstantiateOrigin`/`T::UploadOrigin`, intended to be an allow-list of accounts permitted to deploy code) is checked at the dispatchable-call boundary only, as demonstrated by the `only_instantiation_origin_can_instantiate` test, which asserts `BadOrigin` for the outer `instantiate`/`instantiate_with_code` calls but does not exercise the nested `Ext::instantiate` path taken when a contract instantiates another contract mid-execution (`instantiation_from_contract` test, `push_frame`/`run_instantiate` in `exec.rs`). Once inside contract execution, `push_frame`/`new_frame` build and run the constructor frame without consulting the configured `InstantiateOrigin`. An unprivileged caller who is merely allowed to *call* a permissioned "factory" contract (or any contract with an instantiate primitive) can therefore cause deployment of new contract code that the runtime's governance intended to restrict to a privileged set of accounts — mirroring the `ckr_btc.cairo` pattern where a permission (manager/operator assignment) granted at one layer propagates uncontrolled authority (mint/burn, or here, code deployment) into a downstream operation without re-validation.

### Impact Explanation
Runtimes that configure `UploadOrigin`/`InstantiateOrigin` to restrict code deployment (e.g., to prevent unbounded state bloat, malicious code proliferation, or to gate contracts to an approved set) lose that guarantee the moment any permissioned contract exposes an instantiate primitive reachable by unprivileged callers. This is a runtime bug that compromises intended behavior of a security-relevant guard (origin-restricted contract deployment), directly matching the required-impact category of "runtime bugs that compromise intended behavior" and "public wrappers ... must not widen origin ... for nested execution."

### Likelihood Explanation
The bypass requires only an unprivileged, standard `call()` extrinsic against any contract that is permitted to call `instantiate` internally — no relayer, validator, governance actor, or leaked key is needed. Any deployed contract exposing a "factory"/proxy-deploy entrypoint (a common and legitimate contract pattern, exemplified by the repository's own `create_storage_and_instantiate.rs` fixture) becomes an unrestricted deployment gateway on any chain that relies on `InstantiateOrigin` for governance.

### Recommendation
Propagate and enforce `T::InstantiateOrigin`/`T::UploadOrigin` (or an equivalent contract-level authorization) at every nested `ExecStack::run_instantiate`/`push_frame` invocation, not only at the outer dispatchable boundary, so that permission checks bind to the actual code-deployment action regardless of call depth.

### Proof of Concept
1. Configure a test runtime with `InstantiateOrigin = EnsureSignedBy<Alice>` (as in `only_instantiation_origin_can_instantiate`).
2. Deploy, as Alice, a "factory" contract using the `create_storage_and_instantiate` fixture pattern, which calls `api::instantiate(...)` internally against an arbitrary `code_hash`.
3. As Bob (not authorized by `InstantiateOrigin`), call the factory contract's `call()` entrypoint, passing a `code_hash` for arbitrary code.
4. Observe that the nested `instantiate` succeeds and new contract code is deployed under Bob's initiation, despite Bob being rejected by `InstantiateOrigin` when calling `instantiate`/`instantiate_with_code` directly — confirming the origin restriction is bypassed for nested instantiation.

impl<T: Config> Invokable<T> for InstantiateInput<T> {
	type Output = (AccountIdOf<T>, ExecReturnValue);

	fn run(
		self,
		common: CommonInput<T>,
		mut gas_meter: GasMeter<T>,
	) -> InternalOutput<T, Self::Output> {
		let mut storage_deposit = Default::default();
		let try_exec = || {
			let schedule = T::Schedule::get();
			let InstantiateInput { salt, .. } = self;
			let CommonInput { origin: contract_origin, .. } = common;
			let origin = contract_origin.account_id()?;

			let executable = match self.code {
				WasmCode::Wasm(module) => module,
				WasmCode::CodeHash(code_hash) => WasmBlob::from_storage(code_hash, &mut gas_meter)?,
			};

			let contract_origin = Origin::from_account_id(origin.clone());
			let mut storage_meter =
				StorageMeter::new(&contract_origin, common.storage_deposit_limit, common.value)?;
			let CommonInput { value, data, debug_message, .. } = common;
			let result = ExecStack::<T, WasmBlob<T>>::run_instantiate(
				origin.clone(),
				executable,
				&mut gas_meter,
				&mut storage_meter,
				&schedule,
				value,
				data.clone(),
				&salt,
				debug_message,
			);

			storage_deposit = storage_meter.try_into_deposit(&contract_origin)?;
			result
		};
		InternalOutput { result: try_exec(), gas_meter, storage_deposit }
	}

	fn ensure_origin(&self, origin: Origin<T>) -> Result<(), DispatchError> {
		match origin {
			Origin::Signed(_) => Ok(()),
			Origin::Root => Err(DispatchError::RootNotAllowed),
		}
	}
}

#[test]
fn only_instantiation_origin_can_instantiate() {
	let (code, code_hash) = compile_module::<Test>("dummy").unwrap();
	InstantiateAccount::set(Some(ALICE));
	ExtBuilder::default().build().execute_with(|| {
		let _ = Balances::set_balance(&ALICE, 1_000_000);
		let _ = Balances::set_balance(&BOB, 1_000_000);

		assert_err_ignore_postinfo!(
			builder::instantiate_with_code(code.clone())
				.origin(RuntimeOrigin::root())
				.build(),
			DispatchError::BadOrigin
		);

		assert_err_ignore_postinfo!(
			builder::instantiate_with_code(code.clone())
				.origin(RuntimeOrigin::signed(BOB))
				.build(),
			DispatchError::BadOrigin
		);

		// Only Alice can instantiate
		assert_ok!(builder::instantiate_with_code(code).build());

		// Bob cannot instantiate with either `instantiate_with_code` or `instantiate`.
		assert_err_ignore_postinfo!(
			builder::instantiate(code_hash).origin(RuntimeOrigin::signed(BOB)).build(),
			DispatchError::BadOrigin
		);
	});
}
