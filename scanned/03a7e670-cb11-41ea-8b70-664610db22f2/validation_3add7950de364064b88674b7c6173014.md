## Analysis

The Chainlink report's core broken invariant is: **a monotonic external-feed window check that has no fallback path becomes unsatisfiable if the external source produces an update gap larger than the window, permanently freezing settlement.** The strongest local analog is the Snowbridge Ethereum beacon light client's finalized-header gap check in `submit_update`/`apply_update`, which plays an identical structural role — it gates whether the on-chain "price/finality feed" (the beacon chain's finalized header) can ever advance again.

### Title
Unsatisfiable `InvalidFinalizedHeaderGap` window permanently freezes the Snowbridge Ethereum light client and all dependent message verification - (File: `bridges/snowbridge/pallets/ethereum-client/src/lib.rs`)

### Summary
`verify_update` enforces that a new `finalized_header.slot` cannot be more than `SLOTS_PER_HISTORICAL_ROOT` slots ahead of the pallet's currently stored `latest_finalized_state.slot`: [1](#0-0) 

This is the same shape as the Chainlink `roundId` window check in the report: a strictly bounded acceptance window with no fallback for "no eligible update exists in this window." If no permissionless relayer manages to submit a valid `submit` update while the gap between the stored finalized state and the real Ethereum finalized chain grows past `SLOTS_PER_HISTORICAL_ROOT` (≈8192 slots, ~27.3 hours at 12s/slot — confirmed by the boundary tests `submit_finalized_header_update_with_too_large_gap`/`_with_gap_at_limit`), every subsequent `submit` call will *forever* fail `InvalidFinalizedHeaderGap`, because each new candidate `finalized_header.slot` is even further ahead of the frozen `latest_finalized_state.slot` than the last attempt — the gap can only grow, never shrink, once it exceeds the window. [2](#0-1) 

### Finding Description
`FinalizedBeaconState`/`LatestFinalizedBlockRoot` are the sole source of truth used by `verify_execution_proof`, which every inbound message (`inbound_queue_v2::submit`) and outbound delivery receipt relies on via the `Verifier` impl: [3](#0-2) 

Once the gap check becomes permanently unsatisfiable, `verify_execution_proof` can never validate any new Ethereum event, because `latest_finalized_state.slot` can never advance past the stall point. There is no unprivileged recovery path in `submit`: the only way to resynchronize is the root-only `force_checkpoint` extrinsic, which requires governance intervention (`ensure_root`): [4](#0-3) 

This is structurally identical to the Float Capital issue: a strict, monotonic acceptance window over an external, best-effort feed (Chainlink heartbeat / Ethereum finality) with no on-chain fallback, whose failure mode is a total, hard freeze of the dependent system rather than a graceful degradation.

### Impact Explanation
Once frozen, the beacon client can never accept new finalized headers via the permissionless `submit` path, and `verify_execution_proof` will reject all Ethereum-origin proofs (`HeaderNotFinalized`/gap errors), halting both inbound message verification (`inbound_queue_v2::submit`) and outbound delivery-receipt processing simultaneously — this is the "permanent ... bridge-state lock" and "stalls bridge processing" class explicitly in scope. Funds already committed cross-chain (locked/burned on the source side awaiting relay) become stuck until a privileged root call resets the checkpoint, which is an off-chain/governance recovery outside normal protocol operation.

### Likelihood Explanation
No malicious relayer, validator, or governance actor is required — only that no permissionless relayer successfully lands a `submit` call inside the ~27-hour window, which can genuinely happen due to real-world Ethereum consensus-layer finality delays, relayer infrastructure outages, or fee/congestion spikes (the same non-malicious causes cited by the Chainlink report's own heartbeat-outlier analysis). Because the check is strictly monotonic and the gap only widens over time absent a fix, this is a realistic, low-effort-to-trigger passive failure mode rather than a contrived edge case.

### Recommendation
Add a bounded catch-up/fallback mechanism analogous to the report's recommendation: allow `submit` to accept intermediate finalized headers even when the newest known header exceeds the gap, by walking forward through ancestor headers/roots one `SLOTS_PER_HISTORICAL_ROOT` window at a time instead of requiring the final target header to fit in a single window; alternatively, expose a permissionless (non-root) "resync via known ancestor root" path so recovery does not require a privileged extrinsic, reducing the freeze window from indefinite (until governance acts) to self-healing once relaying resumes.

### Proof of Concept
1. Bootstrap the pallet via `force_checkpoint` at slot `S`.
2. Ensure no successful `submit` lands until the real Ethereum chain's finalized slot advances beyond `S + SLOTS_PER_HISTORICAL_ROOT` (demonstrated boundary behavior in `submit_finalized_header_update_with_too_large_gap`, which asserts `InvalidFinalizedHeaderGap` for a gap of `SLOTS_PER_HISTORICAL_ROOT + 1`).
3. Any subsequent `submit` call with the true (further advanced) finalized header now fails `InvalidFinalizedHeaderGap` permanently, since the gap can never shrink through the permissionless path.
4. `verify_execution_proof` (used by inbound/outbound message verification) continues to check against the stale `latest_finalized_state`, so all new Ethereum-origin messages fail proof verification indefinitely until a root-privileged `force_checkpoint` is executed.

#[test]
fn submit_finalized_header_update_with_too_large_gap() {
	let checkpoint = Box::new(load_checkpoint_update_fixture());
	let update = Box::new(load_sync_committee_update_fixture());
	let mut next_update = Box::new(load_next_sync_committee_update_fixture());

	// Adds 8193 slots, so that the next update is still in the next sync committee, but the
	// gap between the finalized headers is more than 8192 slots.
	let slot_with_large_gap = checkpoint.header.slot + SLOTS_PER_HISTORICAL_ROOT as u64 + 1;

	next_update.finalized_header.slot = slot_with_large_gap;
	// Adding some slots to the attested header and signature slot since they need to be ahead
	// of the finalized header.
	next_update.attested_header.slot = slot_with_large_gap + 33;
	next_update.signature_slot = slot_with_large_gap + 43;

	new_tester().execute_with(|| {
		assert_ok!(EthereumBeaconClient::process_checkpoint_update(&checkpoint));
		let result = EthereumBeaconClient::submit(RuntimeOrigin::signed(1), update.clone());
		assert_ok!(result);
		assert_eq!(result.unwrap().pays_fee, Pays::No);
		assert!(<NextSyncCommittee<Test>>::exists());

		let second_result =
			EthereumBeaconClient::submit(RuntimeOrigin::signed(1), next_update.clone());
		assert_err!(second_result, Error::<Test>::InvalidFinalizedHeaderGap);
		assert_eq!(second_result.unwrap_err().post_info.pays_fee, Pays::Yes);
	});
}

	pub(crate) fn verify_execution_proof(execution_proof: &ExecutionProof) -> DispatchResult {
		let latest_finalized_state =
			FinalizedBeaconState::<T>::get(LatestFinalizedBlockRoot::<T>::get())
				.ok_or(Error::<T>::NotBootstrapped)?;
		// Checks that the header is an ancestor of a finalized header, using slot number.
		ensure!(
			execution_proof.header.slot <= latest_finalized_state.slot,
			Error::<T>::HeaderNotFinalized
		);
