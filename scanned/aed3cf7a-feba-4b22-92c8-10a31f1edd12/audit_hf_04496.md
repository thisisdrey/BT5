# [C] C-01 | increaseLiquidityPosition Uses The Wrong Id

## Summary
Severity: Critical
Contest weight: 0.0619
Dataset id: 22059
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability is an identifier mismatch in the increaseLiquidityPosition routine of the Foil protocol. The function is intended to add more liquidity to an existing Uniswap V3 position, but it mistakenly forwards the Foil‑specific position identifier to Uniswap’s NonfungiblePositionManager instead of the actual Uniswap token ID that represents the same position. The root cause is a conflation of two distinct ID namespaces: Foil maintains its own internal position IDs while Uniswap uses separate NFT IDs for each liquidity position. Because the code does not translate or validate the mapping between these namespaces, the wrong numeric ID is supplied to Uniswap. An attacker or a careless user can exploit this by invoking increaseLiquidityPosition with a Foil ID that points to a different Uniswap position, possibly one owned by another party or a dummy position that cannot receive liquidity. The call may succeed on Uniswap, but the liquidity is attached to an unintended position, leaving the caller’s intended position unchanged. From the user’s perspective the UI will show a successful transaction and may display an increased liquidity amount, yet the actual balance of the targeted position remains unchanged or the funds become locked in an unexpected NFT. This can lead to loss of capital, inaccurate accounting, and a breach of the protocol’s economic guarantees because the protocol assumes that each Foil ID maps one‑to‑one with a Uniswap position. The issue manifests whenever increaseLiquidityPosition is executed, i.e., any time a user tries to top‑up liquidity through the Foil front‑end. It affects all users of the protocol who rely on the function, as well as the protocol itself because the accounting layer will record liquidity that is not actually present in the intended position. The flaw was discovered during a manual security audit performed by the Guardian team, who noticed that the argument passed to NonfungiblePositionManager was the Foil ID variable rather than the stored Uniswap token ID. The problem is subtle because both IDs are simple uint256 values and the contract does not emit an explicit warning or revert when the mismatch occurs, making it easy to miss in testing. To remediate, the contract must retrieve the correct Uniswap NFT ID associated with the Foil position and pass that value to the NonfungiblePositionManager. Adding a validation step that checks the ownership of the supplied Uniswap ID against the caller, and emitting an event that records the mapping, would also help prevent future mismatches. In broader terms, this is a classic case of an identifier confusion bug where an application uses the wrong reference when interacting with an external system, leading to misdirected state changes and potential fund loss.

## Recommendation
Call Uniswap with the correct position ID.
