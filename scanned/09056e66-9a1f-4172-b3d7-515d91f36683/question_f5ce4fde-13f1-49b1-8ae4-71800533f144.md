[Function: remove_account] Is `TrieKey::GlobalContractNonce{identifier: GlobalContractCodeIdentifier::AccountId(account_id)}` or `TrieKey::GlobalContractCode{identifier: GlobalContractCodeIdentifier::AccountId(account_id)}` ever cleared when the underlying account is deleted, given `TrieKey::get_account_id()` explicitly returns `None` for `GlobalContractCode` (comment: 'doesn't correspond to the data stored for that account id')? Attacker action: deploy a global contract keyed by AccountId(A) via DeployGlobalContract, then delete account A, then have a third party create a NEW account A and have it (or any account referencing UseGlobalContract with identifier=AccountId(A)) resolve to the OLD global contract bytecode the original A published, even though A itself no longer exists or is a different entity. Preconditions: attacker deploys a global contract identified by their own account id (not hash), which per protocol design deliberately persists independent of the publishing account's lifecycle. Sequence: DeployGlobalContract(AccountId-identified) on A → DeleteAccount(A) → CreateAccount(A, new unrelated owner) → any account calling UseGlobalContract{identifier:AccountId(A)} now binds to code controlled historically by the OLD A, but the new A's owner cannot update or remove it since UseGlobalContract permission model ties updates to 'the account named A' which now has a different owner who did NOT publish that code, yet also cannot be blocked from being impersonated by future publishes if action_deploy_global_contract permission checks only actor_id==account_id at CURRENT ownership. Invariant: authorization exactness (this is intentional per design per comments, but flag for confirmation that no cleanup gap exists specifically at DeleteAccount time). Scoped impact: cross-owner code identity confusion for AccountId-identified global contracts is a known/intended design and likely a dead-end similar to the listed exclusions — flagged here only to confirm exclusion, not as a novel finding. Proof idea: quick unit test confirming GlobalContractCode/GlobalContractNonce rows are untouched by remove_account (expected, by design) so this is NOT counted toward the escalation impact unless a distinct actor-permission gap is found in action_deploy_global_contract/action_use_global_contract for the new owner.
