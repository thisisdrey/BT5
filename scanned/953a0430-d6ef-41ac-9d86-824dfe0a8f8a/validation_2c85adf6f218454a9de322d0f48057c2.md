## Title
ERC20Transactor withdraw/deposit performs unconditional ERC20 `transfer` without a zero-amount guard, letting a zero-value-revert token trap XCM asset transfers - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` unconditionally build and dispatch an `IERC20::transferCall` with `value: EU256::from(amount)` for whatever `amount` the XCM `Matcher::matches_fungibles` resolves, with no check that `amount > 0` before issuing the ERC20 `transfer`. This mirrors exactly the root cause in the external report: an unconditional token transfer of a value that may legitimately be zero, against an ERC20 implementation that is allowed to revert on zero-value transfers.

## Finding Description
Both transactor entry points build the call payload and dispatch it without any zero check: [1](#0-0) [2](#0-1) 

In both cases, `amount` comes directly from `Matcher::matches_fungibles(what)` on an XCM `Asset { fun: Fungible(amount), .. }`. Nothing in this transactor rejects `amount == 0`. A `Fungible(0)` XCM asset item is a value that can appear from legitimate XCM program construction (e.g., a `WithdrawAsset`/`DepositAsset` leg with a zero remainder after fee deduction, a defensively-included zero-amount asset in a multi-asset XCM, or a deliberately crafted message from an unprivileged XCM sender). The Snowbridge V1/V2 XCM converters explicitly guard against this exact case with `ensure!(amount > 0, ZeroAssetTransfer)` before constructing `Command::UnlockNativeToken`: [3](#0-2) [4](#0-3) 

`ERC20Transactor`, however, has no equivalent guard, and it is wired into the Asset Hub XCM executor configuration as a live `TransactAsset` implementation (confirmed usage in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`). Since arbitrary ERC20 contracts can be deployed via `pallet-revive` and registered/matched as XCM-fungible assets through `Matcher`, an attacker fully controls the ERC20 implementation backing this asset id. Per the well-known "weird-ERC20" class referenced in the source report, it is trivial to write a compliant-looking ERC20 that `revert`s when `value == 0` in `transfer`.

When such a token is the asset being withdrawn or deposited and the XCM program presents (or arithmetic produces) a zero amount for that asset:
- `withdraw_asset_with_surplus` calls `transferCall { to: checking_address, value: 0 }`, which reverts inside the contract, and the bare_call's `did_revert()` path returns `Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))`.
- `deposit_asset_with_surplus` behaves symmetrically and also fails.

## Impact Explanation
A failing `withdraw_asset`/`deposit_asset` step aborts the surrounding XCM instruction. Depending on where in the program this occurs (e.g., within `InitiateTransfer`/reserve-transfer XCM programs that also move other real assets alongside the zero-amount leg, or same-asset multi-item batches), this can:
- Cause otherwise-valid XCM messages carrying legitimate value to fail non-deterministically depending on an attacker-controlled token's zero-transfer behavior, leading to `AssetsTrapped` and other assets in the same holding register becoming stuck/unclaimed (fund lock), and
- Provide a repeatable way for an unprivileged party to make specific asset transfers involving a registered PNA-ERC20 token unusable/griefable, degrading normal chain operation for that asset class without needing any privileged, validator, or relayer role.

This aligns with the accepted impact classes "permanent user-fund or bridge-state lock" and the pivot that "message queues... and settlement state must only advance after decode, dispatch, execution, and settlement succeed atomically" — here settlement legitimately *can't* succeed atomically for a benign zero-value leg purely because of an unguarded unconditional external call.

## Likelihood Explanation
Likelihood is moderate-to-high in principle: no privileged actor, validator, relayer, or governance action is required — only (1) a registered ERC20-backed asset whose implementation reverts on `transfer(_, 0)` (fully within the token deployer's/attacker's control, since ERC20 contracts on `pallet-revive` are permissionlessly deployable) and (2) an XCM program that ends up presenting a zero-amount fungible item for that asset to the transactor (via direct crafting, fee-remainder rounding, or multi-asset XCM composition). The exact conditions under which a zero-amount item reaches this specific transactor from unprivileged, non-governance XCM execution were not fully verified in this session (full wiring/config of `Matcher` and asset registration flow on Asset Hub was not completely traced), so this should be validated with a concrete reproduction before being treated as fully proven.

## Recommendation
Add an explicit `amount == 0` guard at the top of both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, mirroring the `ensure!(amount > 0, ZeroAssetTransfer)` pattern already used in the Snowbridge XCM converters, and either:
- Return success trivially for a zero-amount transfer (matching most in-repo `fungible`/`fungibles` trait implementations that treat zero-value transfers as a no-op, e.g. `substrate/frame/support/src/traits/tokens/fungible/regular.rs`), avoiding any external call to the ERC20 contract, or
- Return a explicit `XcmError` before attempting the external call, so failure is deterministic and independent of the target contract's implementation quirks.

## Proof of Concept
1. Deploy (via `pallet-revive`) an ERC20 contract whose `transfer`/`transferFrom` implementation `revert`s when `value == 0` (trivial Solidity change from the standard OpenZeppelin template referenced at `substrate/frame/revive/fixtures/contracts/external/openzeppelin/contracts/token/ERC20/ERC20.sol`).
2. Register/match this contract as an XCM fungible asset id recognized by the `Matcher` used with `ERC20Transactor` in the Asset Hub XCM config.
3. Construct or trigger an XCM program (e.g., a multi-asset `WithdrawAsset`/`InitiateTransfer`/`DepositAsset` sequence) that includes a `Fungible(0)` entry for this asset alongside other real-value assets, sent by an unprivileged origin.
4. Observe that `ERC20Transactor::withdraw_asset_with_surplus` (or `deposit_asset_with_surplus`) issues `IERC20::transferCall { value: 0 }`, the call reverts (`did_revert() == true`), and the transactor returns `Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))`, aborting the XCM instruction and risking `AssetsTrapped` for the co-batched real assets.
