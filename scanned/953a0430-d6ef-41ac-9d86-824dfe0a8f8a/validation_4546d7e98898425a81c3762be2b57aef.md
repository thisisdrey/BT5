### Title
Node restart silently resets the monotonic `v3_ever_seen` flag, causing transition-safe candidate-descriptor logic to regress and diverge from network consensus - ([File: polkadot/node/core/candidate-validation/src/lib.rs], [File: polkadot/node/core/backing/src/lib.rs], [File: polkadot/node/core/dispute-coordinator/src/initialized.rs])

### Summary
The external report's core defect is: code trusts a value (`answeredInRound`) that is supposed to reflect "is this data still current/valid" but can silently regress to a stale/incorrect state, and the consuming logic has no mechanism to detect that regression, so it makes decisions based on outdated information. The Polkadot SDK analog is the `v3_ever_seen` / `v3_ever_seen: bool` flag used throughout candidate-descriptor V3-transition logic (`polkadot/primitives/src/v9/mod.rs` `version_for_candidate_validation`, and its consumers in `candidate-validation`, `backing`, `dispute-coordinator`, and `dispute-distribution`). This flag is documented as "monotonic: once set to true, never unset" [1](#0-0) , but it is only held in **in-memory subsystem state**, re-initialized to `false` on every subsystem/node restart [2](#0-1) . There is no persisted, on-chain, or otherwise durable record of "V3 has already been seen" that survives a restart.

### Finding Description
`CandidateDescriptorV2::version_for_candidate_validation(v3_ever_seen)` decides whether a candidate descriptor should be interpreted under new rules (`version()`, V3-capable) or old rules (`version_old_rules()`, which sees V3 descriptors as V1) purely based on the caller-supplied `v3_ever_seen` boolean: [3](#0-2) 

This flag directly determines `scheduling_parent_for_candidate_validation`, `scheduling_session_for_candidate_validation`, and `session_index_for_candidate_validation` — i.e., which relay-chain hash and session index are used to fetch session info, validator sets, and claim queues for backing/approval/dispute validation: [4](#0-3) 

Each subsystem maintains its own copy of this flag as plain in-memory state, set to `false` at construction and only flipped to `true` when a leaf/finalized block with the `CandidateReceiptV3` node feature is observed:

- Backing: `v3_ever_seen: false` in `State::new()` [5](#0-4) 
- Candidate-validation: `v3_ever_seen: false` in `State::default()` [6](#0-5) 
- Dispute-coordinator: consumed via `self.v3_ever_seen` in `process_on_chain_votes` [7](#0-6) 

None of these are backed by a database/db column or on-chain query that reconstructs "has V3 ever been confirmed enabled" after a process restart — the design explicitly relies on it being monotonic across the lifetime of the running process, not across restarts. The doc comment for `version_for_candidate_validation` states the safety argument depends on "once the feature is seen" behavior persisting, and PR fixing issue #11272 (`prdoc/stable2603/pr_11290.prdoc`) explicitly reasons about mismatches between backers/approval-checkers based on when each *observes* the feature via leaves, but does not address the restart-regression case [8](#0-7) .

### Impact Explanation
If a validator node's `candidate-validation`, `backing`, or `dispute-coordinator` subsystem restarts after the network-wide `CandidateReceiptV3` feature has been enabled and V3 candidates are already circulating and being backed on-chain, that node's `v3_ever_seen` resets to `false`. Until it re-observes a new leaf carrying the V3 feature signal, it will:
- Interpret genuine V3 candidates via `version_old_rules()`, mis-deriving `scheduling_parent`/`scheduling_session` (falling back to `relay_parent`/implicit session instead of the descriptor's real scheduling parent) [9](#0-8) .
- Fetch the wrong session info / validator set for backing-vote import and dispute-participant selection (`process_on_chain_votes`, `get_relevant_validators` in dispute-distribution) [10](#0-9) , [11](#0-10) .
- Diverge from peers still holding `v3_ever_seen = true`, producing candidate-validation results (`InvalidSchedulingSession`, wrong claim-queue, wrong PVF context) that disagree with the honest majority, which is exactly the class of "ambiguous candidate" scenario the V3-transition logic was built to prevent (per the PR-11290 rationale: mismatched interpretation → disputes → up to 100% slash of the participant that disagrees) [12](#0-11) .

This is a runtime/node-behavior bug that compromises intended consensus-safety behavior of a Substrate-based (Polkadot) chain without requiring a malicious actor — an ordinary validator restart (routine maintenance, crash-restart, upgrade) is sufficient to trigger it, potentially causing unjust dispute participation/votes and slashing exposure for the restarting node, and disruption of block/approval processing while it is desynchronized.

### Likelihood Explanation
Likelihood is moderate-to-high in the specific window during and shortly after the V3 feature rollout: any validator operator restarting their node (which happens routinely for upgrades, crash recovery, or maintenance) after V3 is enabled but before their local view catches up will hit this state. No malicious actor, governance action, or privileged access is required — it is purely an operational/restart timing issue combined with a design gap (monotonic flag not persisted). The window shrinks over time as V3 becomes universally deployed and code paths are expected to switch to using `version()` directly, but during the transition period (which the code itself frames as an active, ongoing period) this is a live condition.

### Recommendation
Persist confirmation of the `CandidateReceiptV3` feature (e.g., in the subsystem's on-disk DB, or by deriving it deterministically from finalized on-chain state on startup rather than relying purely on a runtime in-memory bool) so that `v3_ever_seen` cannot regress to `false` across a restart once it has legitimately become `true`. Alternatively, remove reliance on caller-tracked monotonic flags entirely in favor of self-contained, on-chain-derivable version detection (as the direction already indicated by "version detection is self-contained" for `version()` in `polkadot/primitives/src/v9/mod.rs`), ensuring every subsystem instance (including one that just started) can independently and correctly determine the current feature status before processing any V3 candidates.

### Proof of Concept
1. Enable `CandidateReceiptV3` on a live network; wait until validators are actively backing/approving V3 candidates and each subsystem's local `v3_ever_seen` is `true`.
2. Restart the `candidate-validation` (or `backing`, or `dispute-coordinator`) subsystem process on a validator node (e.g. via a routine node restart).
3. Immediately after restart, before the node observes a new active leaf/finalized block carrying the V3 feature signal, have it receive/process an existing V3 candidate (e.g., via gossip/backing-message import) as demonstrated by the test harness pattern in `polkadot/node/core/candidate-validation/src/tests.rs::pre_validation_v3_scheduling_offset_mismatch`, but constructing the call with `v3_ever_seen = false` while the candidate descriptor is genuinely V3 [13](#0-12) .
4. Observe that `scheduling_parent_for_candidate_validation(false)` returns `relay_parent` instead of the real `scheduling_parent`, and `session_index_for_candidate_validation(false)` returns `None`/wrong session as shown by the existing unit test `v3_feature_activation_changes_descriptor_interpretation` which explicitly demonstrates the pre/post-activation divergence in returned values for the identical descriptor [14](#0-13) .
5. This mismatched interpretation causes the restarted node to reach a validation/participation decision inconsistent with peers who still have `v3_ever_seen = true`, reproducing the ambiguous-candidate/dispute-slashing scenario the transition-safety logic was designed to avoid.

	/// Scheduling parent for use in candidate validation.
	///
	/// See [`Self::version_for_candidate_validation`] for the safety argument.
	pub fn scheduling_parent_for_candidate_validation(&self, v3_ever_seen: bool) -> H
	where
		H: Copy,
	{
		match self.version_for_candidate_validation(v3_ever_seen) {
			CandidateDescriptorVersion::V3 => self.scheduling_parent,
			_ => self.relay_parent,
		}
	}

	/// Scheduling session for candidate validation.
	///
	/// See [`Self::version_for_candidate_validation`] for the safety argument.
	pub fn scheduling_session_for_candidate_validation(
		&self,
		v3_ever_seen: bool,
	) -> Option<SessionIndex> {
		match self.version_for_candidate_validation(v3_ever_seen) {
			CandidateDescriptorVersion::V1 => None,
			CandidateDescriptorVersion::V2 => Some(self.session_index),
			CandidateDescriptorVersion::V3 => {
				Some(self.session_index.saturating_add(self.scheduling_session_offset as _))
			},
			CandidateDescriptorVersion::Unknown => None,
		}
	}

# See doc at https://raw.githubusercontent.com/paritytech/polkadot-sdk/master/prdoc/schema_user.json

title: Fix issue #11272 - Make candidate descriptor version detection self-contained

doc:
  - audience: Node Dev
    description: |
      Removes the `v3_enabled: bool` parameter from `CandidateDescriptorV2::version()` and all
      accessor methods (`core_index`, `session_index`, `scheduling_parent`, `scheduling_session`),
      making version detection self-contained. Previously, version detection depended on a node
      feature lookup from the relay parent, which could produce mismatches between backers (who
      derive the feature from a recent leaf) and approval checkers / dispute participants (who may
      not be able to determine the feature from an old relay parent). This mismatch could lead to
      disputes and backer slashing.

      The fix moves version gating responsibility to two places:
      - **Runtime**: `check_descriptor_version_and_signals()` rejects ambiguous candidates
        (where old-style and new-style version detection disagree) and V3 candidates before the
        feature is enabled.
      - **Backing subsystem**: Adds defense-in-depth `check_version_acceptance()` checks at the
        signing boundary, covering both the seconding path and the statement-import path.

      Downstream consumers (dispute coordinator, dispute distribution, statement distribution,
      collator protocol) no longer need to look up node features for version detection, since any
      candidate that reaches them on-chain was already validated by the runtime.

      Additional changes:
      - **Candidate validation**: V3 feature detection is based on session changes via
        `handle_active_leaves_update`. Uses `scheduling_parent_for_candidate_validation(v3_ever_seen)`
        and `version_for_candidate_validation(v3_ever_seen)` to transition safely.
      - **Dispute coordinator**: V3 feature detection on both first and subsequent leaves.
        Uses `scheduling_parent_for_candidate_validation(v3_ever_seen)` in dispute participation
        queue ordering (`CandidateComparator`), so V3 candidates are ordered by their scheduling
        parent's block number rather than relay parent.
