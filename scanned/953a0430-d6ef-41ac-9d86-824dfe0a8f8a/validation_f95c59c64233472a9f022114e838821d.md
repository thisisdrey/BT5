### Title
Incomplete XCM execution is treated as a final "Processed" message by `pallet-message-queue`, permanently committing partial side-effects of a message whose overall intent never completed - ([File: polkadot/xcm/xcm-builder/src/process_xcm_message.rs])

### Summary
The external report's core broken invariant is: a call that does not fully succeed still gets its permission/state treated as consumed and later completes "as success," because the code path that should revert or block re-completion does not fully undo/gate the effects of the failed attempt. The direct local analog is in the XCM message-processing pipeline: `ProcessXcmMessage::process_message` reports `Ok(false)` for an `Outcome::Incomplete` XCM program (i.e., the program partially executed and then hit an error), and `pallet-message-queue` treats *any* `Ok(_)` — true or false — as a final, committed, non-retried "Processed" message.

### Finding Description
`ProcessXcmMessage::process_message` maps the XCM executor's outcome as follows: [1](#0-0) 

`Outcome::Complete` → `Ok(true)`, but `Outcome::Incomplete` (a program that executed some instructions, then errored on a later one) also returns `Ok(false)` rather than an `Err(_)`.

`pallet-message-queue::process_message_payload` wraps the processor call in a storage transaction that only rolls back on `Err(_)`: [2](#0-1) 

and then, regardless of whether the inner `bool` is `true` or `false`, an `Ok(success)` result is unconditionally classified as `MessageExecutionStatus::Processed`: [3](#0-2) 

This is confirmed by the pallet's own test, which documents that `Ok(false)` intentionally "keeps storage changes" and is not retried: [4](#0-3) 

and by the design note in the PR that introduced this transactional model: [5](#0-4) 

The result: for an XCM message that withdraws/holds/transfers assets in its early instructions and then hits a barrier/filter/insufficient-weight/insufficient-balance error in a later instruction, the `Incomplete` outcome is not rolled back (only `Err` rolls back) and the message is filed away as fully `Processed` — never retried, never flagged as failed to the queue layer — even though the XCM program, from the sender's perspective, did not complete as intended. Once removed from the queue and marked `Processed`, there is no mechanism at the message-queue layer to revisit it; whatever state changes (withdrawals, asset trapping, deposits into intermediate accounts) already occurred before the erroring instruction are permanent.

### Impact Explanation
This directly matches the required pivot that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." Here, the *dequeue/settlement* decision (mark message `Processed`, remove from queue) is made independent of whether execution actually completed as intended (`Incomplete` vs `Complete`), which can permanently commit half-finished cross-chain fund movements (e.g., an asset withdrawn from an account and trapped or partially deposited) as if the program had cleanly finished, with no automatic retry or reversal path once the queue records it as `Processed`.

### Likelihood Explanation
`Outcome::Incomplete` is a normal, reachable outcome for any XCM program that a permissionless sender can construct: barrier rejections, insufficient weight after prior instructions consumed the meter, filter checks failing partway, or an asset transfer step failing after an earlier withdraw succeeded. Since XCM messages arriving over HRMP/UMP/DMP queues are routed into `pallet-message-queue` for `on_initialize` processing, this is exercised on every block that services XCM queues, making the partial-commit / no-retry behavior a routine occurrence rather than an edge case.

### Recommendation
Distinguish "fully complete" from "incomplete" at the message-queue commit boundary: either (a) treat `Outcome::Incomplete` as an error that triggers storage rollback of everything performed in that message's transaction (aligning with the `Err(_)` path), or (b) if partial execution must be allowed to persist (per XCM's asset-trapping semantics), explicitly surface `Incomplete` results as a distinct, auditable/queryable status rather than silently equating them with `Processed`, so that whatever mechanism handles trapped/partial assets is guaranteed to run and no queue-level "success" bookkeeping is asserted for a message that did not fully execute.

### Proof of Concept
1. Construct and send an XCM message whose program: (a) withdraws/holds an asset from the sending account or transfers it into a temporary holding register in an early instruction, then (b) contains a later instruction guaranteed to fail (e.g., depositing to a location blocked by a barrier, or an instruction requiring more weight than remains in the `WeightMeter`).
2. When `pallet-message-queue` services the queue and calls `ProcessXcmMessage::process_message`, `XcmExecutor::execute` returns `Outcome::Incomplete { used, error }`, which is mapped to `Ok(false)` (`polkadot/xcm/xcm-builder/src/process_xcm_message.rs:100-109`).
3. `process_message_payload`'s `with_transaction` closure commits on `Ok(_)` (`substrate/frame/message-queue/src/lib.rs:1573-1577`), so the effects of steps (a) already applied before the failing instruction remain in storage.
4. The overall match returns `MessageExecutionStatus::Processed` (`substrate/frame/message-queue/src/lib.rs:1618-1629`); the message is permanently removed from the queue, never retried, with no distinguishing on-chain signal that the program did not run to completion — reproducing the `process_message_ok_false_keeps_storage_changes` test behavior at `substrate/frame/message-queue/src/tests.rs:2010-2026` but with real asset-moving XCM instructions instead of a mock storage write.
