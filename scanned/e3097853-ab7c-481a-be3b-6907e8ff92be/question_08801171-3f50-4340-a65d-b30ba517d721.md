In `contracts/defuse/core/src/payload/multi.rs::MultiPayload::extract_defuse_payload` for the `WebAuthn` variant, an attacker crafts a `SignedWebAuthnPayload` where `client_data_json`'s `challenge` field does not actually correspond to `Nep413::prehash`/`.hash()` of the embedded `payload` string (i.e., a signature valid over the WebAuthn challenge bytes but where the DEFUSE payload extracted via `serde_json::from_str(&self.payload)` differs from what was actually 'shown' to the signer/authenticator). Preconditions: attacker controls both the WebAuthn credential and the payload JSON string (self-attack, or attacker convinces a relayer to submit their own crafted payload). Call sequence: `signed.verify()` checks the WebAuthn signature against `client_data_json.challenge`; separately, `extract_defuse_payload` just JSON-parses `self.payload` with no cross-check that `hash()` (used for signature verification) actually equals a hash derived from the SAME `signer_id`/`intents` extracted for execution. Binding: `the hash the signature was verified over == a hash uniquely determined by (signer_id, verifying_contract, deadline, nonce, intents)` that get executed, i.e., verify + extract must be over the IDENTICAL bytes, not two independently attacker-suppliable fields. Impact: Critical if attacker can make `.hash()` cover different bytes than `.extract_defuse_payload()` returns, enabling a valid signature over one message to authorize execution of a DIFFERENT message. Proof idea: cargo test constructing a `SignedWebAuthnPayload` where `.hash()` is computed from `client_data_json`/`authenticator_data` (the WebAuthn envelope) while `.extract_defuse_payload()` parses a `self.payload` string containing DIFFERENT intents than implied by the challenge, and confirm the codebase enforces `challenge == base64(sha256(payload))` (per NEP-413/webauthn binding) — assert execution fails if these diverge.
