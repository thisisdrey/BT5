Attacker action: deploy a malicious MT receiver contract, receive an `mt_transfer_call` from a victim, and have the receiver's `mt_on_transfer` return a manipulated `refund` value (e.g. `[U128(amounts[0])]`, larger than what was actually kept) crafted to exceed the true unused amount. Preconditions: victim already has `receiver_balance` credited from the initial transfer. Call sequence: `mt_on_transfer` credits attacker -> attacker returns oversized refund JSON -> `mt_resolve_transfer` reads `promise_result_checked_json` -> `refund.0 = refund.0.min(amount.0)` -> `refund.0.min(receiver_balance)`. Binding: value refunded back to `previous_owner_id` == value actually still held by `receiver_id` (bounded by `receiver_balance`), i.e. `refund <= receiver.token_balances.amount_for(&token_id)`. Impact: Critical -- if bound is bypassed, refund exceeds receiver's balance causing double-credit (sender gets refund + receiver keeps oversized amount effectively minting balance). Proof idea: cargo test with a stub MT receiver returning `[U128(u128::MAX)]` as refund and assert refunded amount == min(requested, deposited, receiver_balance), never exceeding CONSERVATION invariant.
