### Title
Unvalidated user-supplied `gas` in Snowbridge V2 `CallContract` command permits committed messages that cannot execute on Ethereum, stalling agent-fund transfers - (File: `bridges/snowbridge/primitives/outbound-queue/src/v2/message.rs`, `bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs`)

### Summary
Snowbridge's V2 outbound flow lets an unprivileged AssetHub user embed an XCM `Transact` instruction that is decoded into a `ContractCall::V1 { target, calldata, value, gas }` and converted 1:1 into `Command::CallContract { gas, .. }` [1](#0-0) [2](#0-1) . This `gas` field flows unchecked into `ConstantGasMeter::maximum_dispatch_gas_used_at_most`, which for `CallContract` simply returns `*gas_limit` verbatim (no floor, no sanity check), unlike every other command variant which uses a hard-coded minimum (40_000, 50_000+, 200_000, 1_200_000, 100_000) [3](#0-2) . This is structurally identical to the reported `_receiverGas` bug: a user-controlled cross-chain gas parameter is accepted with no minimum-value enforcement, and this parameter both (a) determines the fee charged to the relayer/agent and (b) determines whether the destination-chain execution can even complete.

### Finding Description
In the reported bug, `_receiverGas` is passed straight into `OptionsBuilder.addExecutorLzReceiveOption` with only a `> 0` check, letting a user set 1 wei of gas, causing `lzReceive` to run out of gas on the destination chain while the source chain already burned/locked the user's tokens.

The Snowbridge V2 analog:
1. A user (via AssetHub XCM `PolkadotXcm::execute`/`send`) builds an XCM containing asset transfer instructions (`WithdrawAsset`/`ReserveAssetDeposited`) plus a `Transact` carrying an ABI-encoded `ContractCall::V1 { gas, .. }` [1](#0-0) .
2. `XcmConverter::convert` builds a `Message` whose `commands` vector contains the asset-transfer commands (`UnlockNativeToken`/`MintForeignToken`) followed by the `CallContract` command with the attacker-chosen `gas` [4](#0-3) . There is no lower bound check on `gas` anywhere in `convert.rs` — the only `ensure!` calls guard asset amounts, fee asset identity, and origin aliasing, not `gas` [5](#0-4) .
3. `ConstantGasMeter::maximum_dispatch_gas_used_at_most` for `CallContract` returns the raw user-supplied `gas` with no `max(gas, MIN)` clamp, in contrast to every other command which is hard-coded to a safe minimum [3](#0-2) .
4. This unclamped value becomes the `gas` field committed on-chain in `CommandWrapper` and delivered to the Ethereum Gateway contract, which will forward at most that much gas to the target contract call.

Because the asset-transfer commands (`UnlockNativeToken`/`MintForeignToken`) are bundled in the *same* message alongside the `CallContract` command, and the local fee/reward charged for the whole message is calculated from `T::WeightToFee`/gas-based pricing that uses this same (potentially trivial) `gas` value, a user can craft a message where:
- The reserved/withdrawn assets on the Polkadot side are already consumed (via `WithdrawAsset`/`ReserveAssetDeposited` processed earlier in the XCM), and
- The `CallContract` gas is set to an unrealistically low value (e.g., 1), so the fee charged is minimal, yet execution will predictably run out of gas on Ethereum and revert/fail once delivered.

The net effect mirrors the report's core broken invariant: **a user-controlled gas parameter that gates cross-chain execution success is validated only implicitly (or not at all) rather than against an enforced minimum**, letting the source-side value transfer/fee commitment proceed even though destination execution is guaranteed to fail.

### Impact Explanation
This falls within the "public underpriced work that degrades block production or stalls bridge processing" and "message queues ... must only advance after decode, dispatch, execution, and settlement succeed atomically" impact categories. A malicious or careless user can:
- Under-price the gas component of the message fee (since fee calculation uses the same unclamped `gas` value), meaning the relayer that submits the message to Ethereum and pays real EVM gas is not adequately compensated for delivering a message that will revert.
- Cause committed messages that are guaranteed to fail on the Ethereum side (out-of-gas call to `target`), which can strand associated value transfers bundled in the same XCM/message and waste channel/nonce slots, degrading throughput of the Snowbridge V2 outbound channel.

### Likelihood Explanation
Likelihood is fairly high for the underpricing/DoS angle: constructing the XCM `Transact`/`ContractCall::V1{gas: 1, ..}` payload requires no special privilege — any account able to submit XCM through `PolkadotXcm::execute`/`send` from AssetHub can do it, exactly analogous to any wallet holder calling `send()` with `_receiverGas = 1` in the reported contracts. I was not able to fully verify from the available index whether a separate minimum-gas floor is enforced elsewhere in the Ethereum Gateway Solidity contract or in `EthereumSystemFrontend`/exporter code path (that Solidity/Gateway contract source was not found in the indexed portion of this repo), so it is possible additional validation exists outside the Rust primitives I could inspect. This uncertainty should be resolved by checking the Gateway.sol / inbound processing on the Ethereum side (not present in this repo) before treating this as fully confirmed end-to-end.

### Recommendation
Enforce a protocol-level minimum `gas` for `Command::CallContract`, analogous to the hard-coded floors already used for the other commands (40_000 / 50_000+ / 200_000 / 1_200_000 / 100_000), either by rejecting `ContractCall::V1{gas}` values below a configured minimum in `XcmConverter::convert` (return a new `XcmConverterError::GasTooLow`), or by clamping in `ConstantGasMeter::maximum_dispatch_gas_used_at_most` (e.g., `gas.max(MIN_CALL_CONTRACT_GAS)`), ensuring the fee charged always reflects at least the minimum gas required for the target call to plausibly succeed.

```rust
impl GasMeter for ConstantGasMeter {
	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64 {
		match command {
			Command::SetOperatingMode { .. } => 40_000,
			Command::Upgrade { initializer, .. } => {
				// total maximum gas must also include the gas used for updating the proxy before
				// the the initializer is called.
				50_000 + initializer.maximum_required_gas
			},
			Command::UnlockNativeToken { .. } => 200_000,
			Command::RegisterForeignToken { .. } => 1_200_000,
			Command::MintForeignToken { .. } => 100_000,
			Command::CallContract { gas: gas_limit, .. } => *gas_limit,
		}
	}
}
```
