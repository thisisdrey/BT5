## Analysis

The external report's core pattern is: a payout loop performs a **push-style external transfer** inside a state-transition function (`end()`/`placeBid()`); if that single transfer reverts for any reason (blacklist, pause, insufficient balance floor, etc.), the *entire* transaction aborts, and because FRAME/Solidity semantics roll back **all** storage/state changes for a reverted call, this leaves the whole settlement flow (and all future flows gated on it) permanently stuck.

The closest local analog is the **parachain slot-auction crowdloan pallet**, which still uses direct push-transfers instead of the pull/balance-accounting pattern that the audited contract was fixed to use (and that `pallet_auctions`/`pallet_broker` elsewhere in this repo already emulate via reserve/unreserve or try/skip-on-error).

### Title
Crowdloan pot can become permanently un-dissolvable due to un-refundable sub-Existential-Deposit contributions - (`File: polkadot/runtime/common/src/crowdloan/mod.rs`)

### Summary
`Crowdloan::refund` and `Crowdloan::withdraw` pay contributors back with a direct `Currency::transfer(&fund_account, &who, balance, AllowDeath)` call [1](#0-0) , and `refund` performs this inside a loop over up to `RemoveKeysLimit` contributors, using `?` to propagate any error [2](#0-1) . `dissolve()` can only succeed once `fund.raised` is exactly zero [3](#0-2) . The pallet's own `MinContribution` config is not provably enforced to be `>= ExistentialDeposit`, and a contributor account can independently be drained/reaped between contribution and refund. When the refund transfer targets an account whose balance would be re-created below the chain's `ExistentialDeposit`, `pallet_balances` refuses the deposit with `Error::ExistentialDeposit`, causing the whole dispatch (including the batch loop in `refund`) to fail and roll back.

### Finding Description
`do_contribute` accepts any contribution `>= T::MinContribution::get()` into the fund's pot account [4](#0-3) , but nothing ties `MinContribution` to `ExistentialDeposit`, and even if it did, a contributor's account balance outside of the crowdloan pot is entirely user-controlled and can be reduced to zero by the user themselves (or reaped by other operations) between contributing and claiming a refund. When `refund()`/`withdraw()` later try to pay that exact contribution amount back out of the pot with `ExistenceRequirement::AllowDeath` [5](#0-4) [6](#0-5) , if the destination account no longer exists and the amount is below `ExistentialDeposit`, `pallet_balances::Pallet::transfer` returns `Err(Error::ExistentialDeposit)`. Because this error is propagated with `?`, the enclosing dispatchable fails and FRAME rolls back all storage writes made during that call — including the loop's already-applied transfers to other, unrelated contributors when hit inside `refund()`.

Unlike `polkadot/runtime/common/src/auctions/mod.rs::manage_auction_end`, which explicitly `match`es on `LeaseError` variants and continues processing other winners on failure [7](#0-6) , `crowdloan::refund`/`withdraw` have no such defensive skip-and-continue or balance-accounting fallback — this is exactly the anti-pattern the external report flags (push-transfer failure blocking the whole settlement instead of a pull/ledger-based mechanism).

Because `dissolve()` requires `fund.raised.is_zero()` [8](#0-7) , a single un-refundable contribution permanently prevents `fund.raised` from reaching zero: neither `withdraw()` nor `refund()` can ever clear that entry (retrying hits the identical `ExistentialDeposit` failure every time), so the crowdloan can never be dissolved. This permanently locks the depositor's `SubmissionDeposit` reserve, keeps the pot account and its dust balance alive forever, and (in the `refund` batch case) can also transiently roll back legitimate refunds processed earlier in the same call.

### Impact Explanation
This is a public, unprivileged-entrypoint bug (`refund`/`withdraw` are callable by any signed account) that produces a **permanent fund lock**: the crowdloan's reserved `SubmissionDeposit`, the un-refundable dust contribution, and the pot account itself become permanently stuck, and the crowdloan lifecycle for that `ParaId` can never be cleanly concluded via `dissolve()`. This matches the "permanent user-fund lock" category in the impact gate.

### Likelihood Explanation
Triggering requires only:
1. A signed account contributing a small amount to a crowdloan (respecting `MinContribution`, which is a static runtime constant with no code-enforced relationship to `ExistentialDeposit`), and
2. That account's balance being reduced to zero and reaped before the refund/withdraw is processed (fully attacker-controlled, no privileged actor needed).

No malicious peer, validator, collator, governance actor, or leaked key is required — a normal user can self-trigger it on their own contribution, and the resulting stuck-`raised` state affects the whole fund's lifecycle. This makes the likelihood realistic on any runtime where `MinContribution < ExistentialDeposit`, which I could not fully rule out from the indexed code (the constant's value is set per-runtime in `polkadot/runtime/rococo/src/lib.rs` / `westend/src/lib.rs`, which I was not able to fully inspect in this pass) — this is the main residual uncertainty in the finding.

### Recommendation
- Enforce `MinContribution >= ExistentialDeposit` at `create()`/`contribute()` time, or
- Switch `refund`/`withdraw` to a pull/ledger-based accounting model (mirroring the audited fix pattern): record an internal "owed" balance and let it be claimed with a `Preservation`/dust-handling strategy that cannot permanently fail, and
- Make `refund()`'s batch loop skip-and-log a failing transfer instead of propagating the error with `?`, similar to the defensive pattern already used in `auctions::manage_auction_end`.

### Proof of Concept
1. On a runtime where `MinContribution < ExistentialDeposit` (or where a contributor's contribution equals exactly `MinContribution` and is less than `ExistentialDeposit`), have a fresh account `A` (no other balance) call `Crowdloan::contribute(A, index, MinContribution, None)` — succeeds because it deposits into the already-existing pot account.
2. Let the crowdloan end without winning (or reach its `end` block).
3. Call `Crowdloan::withdraw(anyone, A, index)` (or `refund`): `CurrencyOf::<T>::transfer(&fund_account, &A, MinContribution, AllowDeath)` attempts to (re)create account `A` with a balance below `ExistentialDeposit` and fails with `Error::ExistentialDeposit`, per `polkadot/runtime/common/src/crowdloan/mod.rs:490` / `:531`.
4. `fund.raised` never decreases to zero for `A`'s share; `dissolve()` at `polkadot/runtime/common/src/crowdloan/mod.rs:565-566` permanently reverts with `NotReadyToDissolve`.
