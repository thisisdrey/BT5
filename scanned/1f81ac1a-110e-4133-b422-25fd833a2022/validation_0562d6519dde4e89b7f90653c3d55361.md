## Title
ERC20Transactor credits/debits the XCM holding register with the nominal transfer amount instead of the actually-received amount, allowing fee-on-transfer/deflationary ERC20 tokens to desynchronize the checking-account reserve from XCM asset accounting - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` drive XCM asset accounting for arbitrary ERC20 contracts deployed via `pallet-revive`. Both functions only check the boolean `IERC20.transfer` return value and then unconditionally credit/debit the exact `amount` taken from the XCM `Asset` descriptor, never verifying that the `TransfersCheckingAccount` actually received/lost that amount. Any ERC20 contract with fee-on-transfer, deflationary/burn, or rebasing semantics (which is entirely possible since these are user-deployed Solidity contracts on `pallet-revive`, not a vetted, fixed-supply asset registry) causes the checking account's real token balance to diverge from the nominal amount recorded in the XCM holding register — precisely the invariant break described in the Polynomial Protocol report (`_addCollateral` crediting the pre-fee `amount` instead of the actually-received amount).

### Finding Description
In `withdraw_asset_with_surplus`: [1](#0-0) 
The code transfers `amount` from `who` to the checking account via a `transferCall`, and on a truthy boolean return, mints an `Erc20Credit(amount)` into the XCM holding register — using the requested `amount`, not any measured balance delta of the checking account.

In `deposit_asset_with_surplus`: [2](#0-1) 
The code instructs the checking account to send `amount` to the beneficiary, again trusting only the boolean success flag rather than measuring what the beneficiary actually received.

If the underlying token contract deducts a fee or burns a portion on transfer, `withdraw_asset_with_surplus` will credit the XCM holding register (and hence downstream `deposit_asset`/`AllCounted`/refund logic) with more value than the checking account's real balance increased by. Over repeated withdraw/deposit cycles, the checking account balance is drawn down faster than the credits recorded against it, so the XCM system effectively "mints" holding-register value that isn't backed 1:1 by the real ERC20 balance held by `TransfersCheckingAccount`. The `Erc20Credit` type is explicitly documented as unchecked: [3](#0-2) 
confirming that no runtime-level balance enforcement backs this credit — the contract's own (possibly non-standard) behavior is solely relied upon, exactly mirroring the fee-on-transfer collateral bug class.

There is no allow-list restricting `ERC20Transactor` to well-behaved, fixed-fee (zero-fee) tokens; any ERC20 contract deployed through `pallet-revive` and matched via `ERC20Matcher`/`MatchesFungibles` can be transacted (`asset-hub-westend` config wires this transactor into `AssetTransactors`): [4](#0-3) 

### Impact Explanation
Because the runtime credits the XCM executor's holding register with the pre-fee amount while only the post-fee amount is actually escrowed in the `TransfersCheckingAccount`, subsequent `deposit_asset` calls for other in-flight XCM programs draw down real token balance that is not backed by matching credit reductions elsewhere. This can (a) starve later legitimate withdraws/deposits of that asset once the checking account's real balance is exhausted relative to outstanding holding-register credits, causing fund lock for some users, and (b) in scenarios where the checking account carries surplus balance from prior transactions, allow a withdraw/deposit sequence to extract more real tokens than were ever deposited for that specific operation — an unbacked-credit/theft class impact under "theft or unbacked mint or unlock."

### Likelihood Explanation
This requires no privileged actor: any unprivileged user can deploy or select an ERC20 contract with fee-on-transfer or deflationary semantics (`pallet-revive` allows arbitrary Solidity/EVM bytecode deployment) and then issue ordinary `withdraw_asset`/`deposit_asset` XCM programs through `PolkadotXcm::execute`, which is a standard, unprivileged public entrypoint. No malicious relayer, validator, or governance action is needed — only a token contract whose `transfer` doesn't move the full nominal amount, which is common in real-world ERC20 tokens.

### Recommendation
Measure the checking account's (or beneficiary's) actual balance delta before and after the `transferCall` and use that measured delta — not the nominal `amount` — both when constructing `Erc20Credit` in `withdraw_asset_with_surplus` and when validating success in `deposit_asset_with_surplus`. Alternatively, restrict `ERC20Matcher`/allow-listing to tokens verified to transfer the exact requested amount, and reject/quarantine tokens whose transfer semantics can change post hoc (matching the external report's own recommendation to support disapproving/de-registering collateral once such behavior is detected).

### Proof of Concept
1. Deploy an ERC20 contract on `pallet-revive` whose `transfer` function burns/deducts 1% on every transfer (fee currently unused/zero is not required — attacker fully controls contract logic).
2. Register/allow this contract as an XCM-transactable asset matched by `ERC20Matcher`.
3. Submit an XCM program via `PolkadotXcm::execute` doing `withdraw_asset` for `amount = 1000` of this token from an account holding it.
4. `withdraw_asset_with_surplus` transfers `1000` to `ERC20TransfersCheckingAccount`, but the checking account's real balance only increases by `990` (1% fee burned); the function still mints `Erc20Credit(1000)` into the holding register.
5. Complete the XCM with `deposit_asset` to a beneficiary for the full `1000` credited amount; `deposit_asset_with_surplus` instructs the checking account to send `1000` to the beneficiary — draining `10` units of real balance that belongs to other users'/asset's previously-escrowed funds, since the checking account only actually gained `990` from this operation.
6. Repeating this sequence progressively insolvents the checking account relative to the sum of all `Erc20Credit` amounts recorded across concurrent/prior XCM programs, eventually causing failed deposits (fund lock) or first-mover extraction of tokens belonging to other pending transfers.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}
