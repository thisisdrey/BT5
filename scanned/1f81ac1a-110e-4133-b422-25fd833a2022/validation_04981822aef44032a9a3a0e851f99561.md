### Title
`PGasDeposit::charge_and_hold` withdraws the entire storage-deposit amount from native currency instead of the PGAS shortfall when PGAS balance is insufficient - (File: `substrate/frame/revive/src/deposit_payment.rs`)

### Summary
`pallet-revive`'s PGAS-backed storage-deposit payment backend decides how to fund a charge with an all-or-nothing check: if the payer's reducible PGAS covers the *entire* requested amount it pays fully in PGAS, otherwise it falls back to charging the *entire* amount from native currency (DOT), even though the payer may hold almost all of the required amount in PGAS already. This mirrors the Notional `TokenHandler._redeemMoneyMarketIfRequired` bug, where the code withdrew the full requested amount from the money market instead of only the shortfall beyond the existing on-hand balance.

### Finding Description
`PGasDeposit::charge_and_hold` in `substrate/frame/revive/src/deposit_payment.rs`: [1](#0-0) 

```rust
fn charge_and_hold(
    reason: HoldReason,
    src: Funds<T::AccountId>,
    to: &T::AccountId,
    amount: BalanceOf<T>,
) -> DispatchResult {
    let from = match &src {
        Funds::Balance(from) | Funds::TxFee(from) => *from,
    };

    if Self::pgas_reducible_balance(from) >= amount {
        // pay fully in PGAS
        ...
    } else {
        <() as Deposit<T>>::charge_and_hold(reason, src, to, amount)?;
        Self::record_native_deposit(from, to, amount);
    }

    Ok(())
}
```

The condition `pgas_reducible_balance(from) >= amount` is the exact analog of Notional's `withdrawAmountExternal <= currentBalance`. Just as Notional's `_redeemMoneyMarketIfRequired` fell through to `oracle.getRedemptionCalldata(withdrawAmountExternal)` — withdrawing the *full* target amount from the money market instead of `withdrawAmountExternal - currentBalance` — this code, on the `else` branch, calls `<() as Deposit<T>>::charge_and_hold(reason, src, to, amount)` with the **full** `amount`, charging it entirely to the native currency, instead of computing the PGAS shortfall (`amount.saturating_sub(pgas_reducible_balance(from))`) and drawing only that shortfall from native while consuming the available PGAS via the `Holder::transfer_and_hold` path.

Concretely: if a user has `999,900` PGAS reducible and a `1,000,000` storage-deposit charge is required, the `>=` check fails by `100` units, and the entire `1,000,000` is drawn from native currency (DOT) rather than `999,900` PGAS + `100` DOT shortfall. `record_native_deposit` then also records the full `1,000,000` as native-attributed in `NativeDepositOf`, meaning the user's `999,900` PGAS balance sits completely unused/idle for that charge even though it was available and intended to be the primary payment asset. There is no partial-PGAS + partial-native combined charge path anywhere in this function or `Deposit<T>` trait to prevent this.

### Impact Explanation
This degrades the intended dual-asset payment design: PGAS is meant to be consumed first ("Charges prefer PGAS and fall back to the native currency" per the doc comment), but the implementation only uses PGAS when it can cover the charge in full. Any deposit slightly larger than the user's PGAS balance forces the *entire* charge onto DOT, over-consuming the user's native balance while the (nearly sufficient) PGAS balance remains untouched for that operation. Since PGAS is described as a "protocol-level gas token or gas allowance mechanism for users verified through Polkadot's Proof of Personhood ecosystem," this behavior defeats its intended cost-subsidization purpose at scale: users churning many contract calls near their PGAS balance boundary will be repeatedly charged in native currency for the full amount rather than draining PGAS efficiently, causing systematic loss of the intended free-tier allowance and unnecessary DOT expenditure. This is a real, protocol-level accounting bug affecting runtime economics on any chain that enables `pallet-revive` with the PGAS backend, matching the "runtime bugs that compromise intended behavior" and "public underpriced work" impact categories.

### Likelihood Explanation
This triggers on the ordinary, unprivileged contract-execution path any time a user's PGAS reducible balance is below the requested deposit amount — a very common scenario near the boundary of a user's PGAS allowance. No malicious actor, governance action, or special permissions are required; it happens automatically inside `charge_and_hold`, called from the storage-deposit charging flow of every contract call/instantiation that touches storage.

### Recommendation
Compute the PGAS shortfall explicitly and only draw the difference from native currency, combining a partial PGAS hold with a partial native hold:
```rust
let pgas_available = Self::pgas_reducible_balance(from);
let pgas_amount = amount.min(pgas_available);
let native_amount = amount.saturating_sub(pgas_amount);

if !pgas_amount.is_zero() {
    <Holder as fungibles::MutateHold<T::AccountId>>::transfer_and_hold(
        Id::get(), &reason.into(), from, to, pgas_amount,
        Precision::Exact, Preservation::Expendable, Fortitude::Polite,
    )?;
}
if !native_amount.is_zero() {
    <() as Deposit<T>>::charge_and_hold(reason, src, to, native_amount)?;
    Self::record_native_deposit(from, to, native_amount);
}
```
This mirrors Notional's fix of using `withdrawAmountExternal - currentBalance` instead of the full `withdrawAmountExternal`.

### Proof of Concept
1. Configure `pallet-revive` with `PGasDeposit` as the `Deposit` backend, with `RefundPercent` and PGAS asset set up per `substrate/frame/revive/src/tests/deposit_payment.rs` test harness.
2. Set up an account ALICE with `native: 1_000`, `pgas: 999_900` (analogous to the `pay_mixed_refund_mixed` test at [2](#0-1) ).
3. Trigger a storage-deposit `charge_and_hold` for `amount = 1_000_000`.
4. Observe: `Self::pgas_reducible_balance(from) (999_900) >= amount (1_000_000)` is `false`, so the `else` branch executes `<() as Deposit<T>>::charge_and_hold(reason, src, to, 1_000_000)`, deducting the full `1,000,000` from ALICE's native balance and leaving `999,900` PGAS completely unused, and `NativeDepositOf` records a `1,000,000` native entitlement instead of the expected `100`.
