This maps directly to the seed pattern: a signature/proof-based authorization that binds an identity but is deliberately reusable within a validity window because the "deadline" (`call_valid_at` + `time_tolerance`) is not bound to a single outcome/account pairing — exactly the `expiresIn`-missing-binding class from the `PhiDaily.sol` report.

### Title
Time-windowed proof replay allows account takeover of a `PersonalAlias`/`PersonalIdentity` slot in `pallet-people`'s `AsPerson` transaction extension - (File: `substrate/frame/people/src/extension.rs`)

### Summary
The `AsPerson` transaction extension's `AsPersonalAliasWithProof` and `AsPersonalIdentityWithProof` branches authorize `set_alias_account`/`set_personal_id_account` using a `call_valid_at` block number plus a fixed `account_setup_time_tolerance` window, instead of a single-use nonce or a signature that is invalidated the moment it is consumed for one outcome. Any transaction "valid" in that window can be resubmitted, and any other transaction whose window overlaps the same `call_valid_at` range remains simultaneously replayable, letting the last submitter overwrite a previously set account binding.

### Finding Description
For `AsPersonalAliasWithProof(proof, ring_index, context)` and `AsPersonalIdentityWithProof(signature, index)`, validity is derived from: [1](#0-0) 
followed only by a check that the *exact same* `(account, rev_ca)` pair hasn't already been stored: [2](#0-1) 

There is no per-proof nonce, no consumption marker, and no binding of the proof to a unique/incrementing value — the only "expiry" is the coarse `call_valid_at .. call_valid_at + time_tolerance` block range, which is explicitly documented as insufficient: [3](#0-2) [4](#0-3) 

This is the structural analog of the `PhiDaily.sol` bug: the digest/proof is not bound to a single-use deadline value, so it stays valid and reusable for the entire tolerance window, and multiple distinct proofs whose windows overlap can be interleaved and replayed against each other for the whole overlapping duration. The test `replay_protection_for_identity` confirms this is real, observable behavior (not just a comment): [5](#0-4) 
It shows transaction 1 (binding account 10) and transaction 2 (binding account 11) can both be replayed indefinitely against each other as long as both remain within their own tolerance windows — each replay flips `AccountToPersonalId`/`AccountToAlias` back and forth between the two accounts.

### Impact Explanation
This directly violates the "public dispatch wrappers must not widen origin" and "message/proof binding must include replay domain exactly once" pivots: an unprivileged party who intercepts (or is given) any valid `AsPersonalAliasWithProof`/`AsPersonalIdentityWithProof` transaction can resubmit it at will during the tolerance window to flip the `PersonalId`/`PersonalAlias`-to-account binding, causing the wrong account to be recognized as the personal identity/alias owner. Since these bindings are what many chains use to gate governance/uniqueness features (proof-of-personhood), an attacker able to observe or acquire one of these transactions (e.g. from a mempool, or as a legitimately-authorized-once party) can grief or race a competing account assignment for as long as the windows overlap — a real state-acceptance/authorization integrity bug, not merely a griefing nuisance.

### Likelihood Explanation
Medium: this requires an attacker to have or observe a valid signed/proved transaction (not a stolen key — the "proof" and "signature" here are meant to be shared/broadcastable extension data, similar to a permit signature), which is realistic in this design since these are `None`-origin, unsigned-transaction style dispatches meant to be gossiped. The bug is inherent to the pallet's logic (present regardless of node/validator honesty) and is already demonstrated by the repository's own test suite, indicating it is a known, reproducible behavior of shipped code rather than a hypothetical.

### Recommendation
Bind consumption to a single-use value rather than a coarse time window: require the proof/signature to include (and the pallet to persist) a unique nonce or the specific `account` that becomes permanently non-replayable once processed (i.e., remove the "hasn't been stored yet" check as the *only* guard and replace the tolerance-window model with an atomic "authorize-and-consume" pattern, mirroring `use_permit`'s nonce-increment pattern in `substrate/frame/assets/precompiles/src/permit.rs`). At minimum, shrink `account_setup_time_tolerance` to the minimum operationally necessary and document/require that overlapping `call_valid_at` windows for the same `ring_index`/`index` be explicitly disallowed by the caller.

### Proof of Concept
The existing test `replay_protection_for_identity` in `substrate/frame/people/src/tests.rs` is itself the PoC: it constructs two signed setup transactions for `alice_index` binding two different accounts (10 and 11) with overlapping validity windows, and shows both `exec_tx` calls succeed repeatedly and flip the stored `AccountToPersonalId` mapping back and forth within the tolerance period: [6](#0-5) 
This demonstrates that a signature/proof without a strict single-use deadline binding is replayable to overwrite intended state — the exact bug class described in the seed report, realized locally in `pallet-people`.
