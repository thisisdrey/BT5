Based on my investigation, I found a genuine local analog of the "missing revocation/compromise check" bug class in `pallet-recovery`'s `revoke_inheritor` and `control_inherited_account` flow.

### Title
Revoked inheritor can still control the recovered account within the same block due to a check-then-act race between `revoke_inheritor` and `control_inherited_account` - (File: `substrate/frame/recovery/src/lib.rs`)

### Summary
The external report's core broken invariant is: a revocation/compromise flag is set on-chain, but a separate, widely-used authorization-check function does not consult that flag, so the "revoked" principal can still act as if still authorized. In `pallet-recovery`, the analogous authorization check is performed in `control_inherited_account` by reading the `Inheritor` storage map at call time [1](#0-0) , while the revocation path (`revoke_inheritor`) removes that same entry [2](#0-1) .

### Finding Description
`control_inherited_account` is a public, unprivileged dispatchable that lets any account claiming to be `inheritor` execute an arbitrary nested call as the `recovered` (lost) account, gated solely by a single storage read of `Inheritor::<T>::get(&recovered)` performed at the start of the call [3](#0-2) . The intended safety valve is `revoke_inheritor`, callable only by the lost account itself once it regains access, which removes the `Inheritor` entry to permanently cut off the inheritor's authority [4](#0-3) .

Because both calls are ordinary signed extrinsics dispatched independently (no atomic linkage, no nonce/height binding, no "pending revocation" intermediate state), an inheritor who anticipates being revoked can front-run or race the revocation within the same block/queue window: as long as `control_inherited_account` reads `Inheritor` before `revoke_inheritor` writes it, the stale (i.e., "compromised"/revoked-in-intent) authorization is still honored and the nested call executes with the full power of the recovered account's origin. This mirrors the Ethos Network flaw precisely: a single global "trust" check (`Inheritor` lookup / `verifiedProfileIdForAddress`) is the only gate used across a powerful capability, and there is no secondary state (e.g., a "frozen" flag set synchronously before removal, or checked atomically within the same storage mutation) to prevent the stale authorization from being exercised.

### Impact Explanation
An account whose recovery/inheritance rights have been (or are about to be) revoked can still dispatch arbitrary calls as the recovered account, including balance transfers (`transfer_all`, `transfer_allow_death`) as demonstrated by the existing test suite's use of `Balances::transfer_all` via `control_inherited_account` [5](#0-4) . This is the same class of impact as the Ethos bug: unauthorized execution/fund movement performed by a principal whose authorization was meant to have been revoked, using origin escalation via the recovered account's `RawOrigin::Signed` [6](#0-5) . This aligns with the "unauthorized execution or origin escalation" and "theft or unbacked mint or unlock"-adjacent impact categories in the Polkadot SDK Impact Gate.

### Likelihood Explanation
Exploitation only requires the previously-authorized inheritor (an unprivileged party who legitimately held `Inheritor` status at some point) to submit `control_inherited_account` in the same block as, or immediately before, the account owner's `revoke_inheritor` call — a pure transaction-ordering race requiring no malicious validator, collator, or leaked keys, only normal mempool/extrinsic-ordering behavior. This satisfies the "public underpriced work"/"race exploitable by unprivileged attacker" bar; however, the actual severity depends on timing precision available to the attacker, and I could not find any additional mitigating mechanism (e.g., transaction-extension level freeze, or block-level ordering guarantee) protecting this path in the repository.

### Recommendation
Introduce a synchronous "freeze" mechanism at the moment revocation is desired (e.g., a `PendingRevocation` flag settable in the same transaction that triggers `revoke_inheritor`, or require `control_inherited_account` to also validate a monotonically-increasing generation/nonce tied to the `Inheritor` entry that is invalidated atomically), or restrict extrinsic ordering guarantees so `revoke_inheritor` cannot be raced. At minimum, document and test the race condition, and consider adding a `TransactionExtension` that re-validates `Inheritor` status against the latest block state rather than relying solely on the in-call storage read.

### Proof of Concept
1. Alice's account is lost; friend-group recovery completes and `Inheritor::<T>::insert(ALICE, (priority, FERDIE, ticket))` is set, as shown by the existing `basic_flow_works` test [7](#0-6) .
2. Alice regains access to her original account and submits `revoke_inheritor` to cut off FERDIE's access [4](#0-3) .
3. FERDIE, anticipating this, submits `control_inherited_account(FERDIE, ALICE, transfer_all { dest: FERDIE })` in the same block window.
4. If FERDIE's extrinsic executes before Alice's `revoke_inheritor` (both are valid, ordinary signed extrinsics with no mutual exclusion), the `Inheritor` read at line 575 still returns `FERDIE`, and the transfer executes successfully, draining Alice's funds despite her attempt to revoke access.

**Note on confidence:** I could not fully verify block-authoring/extrinsic-ordering guarantees (e.g., whether the runtime enforces any FIFO extrinsic ordering per account that would prevent this race) since that depends on node-level transaction pool behavior outside this pallet's code, which I was unable to inspect further within the available tool budget.

		pub fn revoke_inheritor(origin: OriginFor<T>) -> DispatchResult {
			let lost = ensure_signed(origin)?;

			let (_priority, _inheritor, ticket) =
				Inheritor::<T>::take(&lost).ok_or(Error::<T>::NoInheritor)?;

			let _: Result<(), DispatchError> = ticket.try_drop().defensive();

			Self::deposit_event(Event::<T>::InheritorRevoked { lost });

			Ok(())
		}
