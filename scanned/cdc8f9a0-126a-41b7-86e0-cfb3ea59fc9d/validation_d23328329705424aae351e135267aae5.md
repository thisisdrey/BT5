### Title
`pallet-scarcity::do_mint_inner` / `do_force_transfer` place an NFT into a purse key with no destination consent, permanently blocking that account's ability to receive its intended instance - (File: `substrate/frame/scarcity/src/lib.rs`)

### Summary
The kycDAO report's core broken invariant is that a required "must-hold-this-NFT" precondition can be permanently unsatisfiable for the intended holder because the pallet issuing the NFT gives the recipient no say in whether it lands in their account, and the recipient side has no way to reconcile/receive it. `pallet-scarcity` reproduces the same broken invariant on-chain: any permissionless collection owner can `mint` (`do_mint`/`do_mint_inner`) or `force_transfer` an instance directly into *any* account's purse key with zero destination consent, and because the pallet enforces at most one NFT per purse key (`NftsByOwner`), that occupies the key and makes it permanently unable to receive the NFT it was actually supposed to hold until the unwilling holder manually notices and burns the unsolicited item.

### Finding Description
`pallet-scarcity`'s own module documentation states the invariant explicitly: [1](#0-0) 

`do_mint_inner` enforces the "one NFT per purse key" rule but performs no consent check on `to` — it only checks the key is currently empty: [2](#0-1) 

`create_collection` is permissionless — any unprivileged account can become a collection owner: [3](#0-2) 

`mint` is then callable by that same unprivileged collection owner into any destination account they choose: [4](#0-3) 

The collection-owner-authorized `force_transfer` path (around line 1200-1213) applies the identical `AddressOccupied`/no-consent semantics when moving an existing instance to a new owner. Because `NftsByOwner` is a single-value map keyed by `AccountId` (at most one instance per account), once an unsolicited instance lands in a victim's purse key, any subsequent legitimate mint or transfer that was supposed to deliver a real NFT to that same account will hit `Error::<T>::AddressOccupied` and fail outright — mirroring exactly the ERC4626KYCDaoForm scenario where the contract can never come to hold the required token because it has no mechanism to accept/consent to the transfer and no way to make room for it. The `AsScarcity` transaction extension (`substrate/frame/scarcity/src/extension.rs`) compounds this: it treats "having exactly the expected instance in `NftsByOwner`" as the authorization for feeless dispatch, so an account whose purse key is squatted by a spam instance cannot even use the intended feeless-transfer/burn UX path for the instance it should have received, since that instance was never granted to them.

### Impact Explanation
This is a public, underpriced, unprivileged-attacker griefing/lock primitive against the "assets/NFTs must conserve value and settle exactly once to the rightful beneficiary" invariant called out in the Polkadot SDK Pivots. Any account (including a contract-controlled or protocol-controlled purse key that a runtime integration expects to eventually hold a specific Scarcity instance, e.g. a soul-bound credential gating some other pallet call) can be preemptively occupied by an attacker's own collection, permanently preventing the rightful mint/transfer from ever landing there. This is a "permanent user-fund [state] lock" per the impact gate: the victim's account is denied delivery of the value it was entitled to receive until it independently discovers and burns the attacker's spam instance — a remediation the pallet gives the victim no signal to perform, and which the protocol layer minting the "real" NFT cannot force.

### Likelihood Explanation
Likelihood is high for any deployment that uses `pallet-scarcity` for anything with a well-known, predictable destination account (e.g., a protocol/treasury/derived address that must hold a specific badge NFT before some other pallet call is authorized). `create_collection` and `mint` are fully permissionless dispatchables reachable by any signed account, and the destination account address is typically public/derivable (a pallet-derived sovereign account, a proxy, a known parachain treasury key, etc.), so no privileged, validator, relayer, or governance access is required — only an ordinary signed extrinsic.

### Recommendation
Require explicit destination consent before an instance is deposited into a previously-empty purse key that the sender does not already control — e.g., a `claim`/two-step mint similar to the collection-ownership handoff already implemented (nominate + claim), or an allow-list/opt-in flag per account (`AcceptsInstance::<T>::get(&to)`) that `do_mint_inner`/`force_transfer` must check before writing into `NftsByOwner`. Alternatively, expose a `reject`/`vacate` extrinsic that lets a holder atomically burn an unsolicited instance and simultaneously re-open the key for the correct mint in the same transaction, so third-party protocol integrations depending on "this exact purse key holds this exact instance" cannot be permanently denied.

### Proof of Concept
1. A runtime integrates `pallet-scarcity` so that a well-known account `V` (e.g., a derived treasury/vault sovereign account, or an account whose held Scarcity NFT gates some other pallet's dispatchable) is expected to eventually receive instance `X` from collection `C1` owned by a legitimate issuer.
2. Before the legitimate issuer mints `X` to `V`, an unprivileged attacker calls `create_collection` to become owner of a throwaway collection `C2`, then `define_item` and `mint(C2, item, to = V, ...)`. Since `NftsByOwner::<T>::contains_key(&V)` is `false` at this point, `do_mint_inner` succeeds and inserts a spam instance into `V`'s purse key.
3. The legitimate issuer's later `mint(C1, item, to = V, ...)` now fails with `Error::<T>::AddressOccupied` because `V`'s purse key is occupied by the attacker's spam instance.
4. `V` never receives instance `X` and cannot pass any downstream check ("does `V` hold the expected Scarcity NFT?") until someone burns the attacker's spam instance from `V`'s key — which `V`'s own account may not be positioned to do if `V` is a pallet-derived account with no signing key (analogous to the ERC4626KYCDaoForm contract that can never hold the required kycDAO NFT).
