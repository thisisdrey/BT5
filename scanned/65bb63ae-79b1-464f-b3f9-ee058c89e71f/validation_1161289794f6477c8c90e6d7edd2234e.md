### Title
XCM message-queue processor collapses transient `Barrier`/weight/fee execution failures into a permanent `Unsupported` error, causing wrongful permanent message drop instead of retry - ([File: polkadot/xcm/xcm-builder/src/process_xcm_message.rs])

### Summary
`ProcessXcmMessage::process_message` in `polkadot/xcm/xcm-builder/src/process_xcm_message.rs` only special-cases `xcm::latest::Error::ExceedsStackLimit`, mapping it to the transient `ProcessMessageError::StackLimitReached`. Every other `Outcome::Error` variant returned by the XCM executor — including `Barrier`, `WeightNotComputable`, `TooExpensive`, `FeesNotMet`, `ExpectationFalse`, etc. — is collapsed into `ProcessMessageError::Unsupported`, which `pallet-message-queue` treats as a **permanent** failure and discards the message forever rather than retrying it on a later block. This mirrors the GMX report's core defect: legitimate transient failure conditions are misclassified as permanent, causing wrongful cancellation instead of retry.

### Finding Description
`process_message` decodes and executes an XCM message and maps the executor's outcome: [1](#0-0) 

Only `ExceedsStackLimit` is mapped to `ProcessMessageError::StackLimitReached`; all other `xcm::latest::Error` variants (defined at `polkadot/xcm/src/v5/traits.rs` lines 45-179, including `Barrier` at line 171, `WeightNotComputable` at line 172-173, `TooExpensive` at line 111, `FeesNotMet` at line 140-141) fall through to `ProcessMessageError::Unsupported`.

`pallet-message-queue`'s `process_message_payload` treats `Unsupported` as a **permanent** error: [2](#0-1) 

`service_page_item` then marks the message as processed and permanently skips/removes it from the page: [3](#0-2) 

`Barrier` is explicitly documented as a context-dependent (transient-by-nature) condition — "the conditions surrounding the message were not such that the chain considers the message worth spending time executing" — e.g. missing weight credit at the moment of check, fee-market/origin conditions, or paid-execution eligibility that can change block to block: [4](#0-3) 

This is the direct structural analog of the GMX report: the queue processor's error handler makes an all-or-nothing "permanent vs transient" decision, and several genuinely transient execution outcomes (barrier not currently satisfied, weight not currently computable, insufficient fees at this attempt) are lumped in with truly-permanent decode/format errors (`BadFormat`, `Corrupt`), so the message is irrecoverably dropped instead of retried when conditions become favorable — exactly analogous to GMX's `OracleBlockNumberNotWithinRange`/`OracleBlockNumbersAreNotEqual` being wrongly treated as cancel-worthy instead of retry-worthy.

Notably, the polkadot-sdk maintainers already recognized and fixed this exact bug class once before for `ExceedsStackLimit` specifically (PR 4202, "Treat XCM ExceedsStackLimit errors as transient in the MQ pallet"): [5](#0-4) 

but the fix was narrow (added only a `StackLimitReached` carve-out) and did not address the remaining transient-but-misclassified-as-`Unsupported` outcomes such as `Barrier`, `WeightNotComputable`, and fee-related errors.

### Impact Explanation
A message that fails only because a barrier condition is momentarily unmet (e.g., a paid-execution barrier that would succeed once the required fee asset arrives in a later block, or a weight-credit barrier that resets each block) is permanently discarded by the message queue on first attempt, rather than being retried. Because XCM messages routinely carry teleports, reserve transfers, and other value-moving instructions, a message dropped this way represents value that was "sent" (debited/reserved on the source side) but never executed on the destination — a form of permanent user-fund lock, matching the "permanent user-fund or bridge-state lock" impact category in the required-impacts list. This is a public/unprivileged-triggerable condition: any account submitting an ordinary XCM message that happens to hit a barrier check at an unfavorable moment (not a malicious actor) can trigger the permanent drop, purely as a consequence of normal usage and timing, not privileged/admin action.

### Likelihood Explanation
This does not require a malicious keeper, relayer, or validator — it is triggered by ordinary XCM traffic under normal, unprivileged conditions whenever a `ShouldExecute` barrier (e.g. weight-credit exhaustion, timing of fee arrival) or weight/fee computation transiently fails during a `MessageQueue` processing attempt. The message-queue's built-in retry mechanism (used for `Yield`, `Overweight`, and now `StackLimitReached`) is bypassed for these cases solely because of the coarse `_ => ProcessMessageError::Unsupported` fallthrough, making the wrongful-permanent-drop path readily reachable in ordinary operation, not an edge-case attack setup.

### Recommendation
Extend the mapping in `ProcessXcmMessage::process_message` (or the executor's `Outcome::Error` handling) to classify additional context-dependent, retry-worthy `xcm::latest::Error` variants — at minimum `Barrier`, `WeightNotComputable`, `TooExpensive`, and `FeesNotMet` — as a transient `ProcessMessageError` variant (e.g., `Yield` or a new dedicated transient error) instead of collapsing them into `Unsupported`, consistent with the precedent already set for `ExceedsStackLimit` in PR 4202. Ensure `pallet-message-queue`'s permanent/transient split is only applied to errors that are truly unrecoverable regardless of retry (decode/format errors), not to any error whose success depends on chain state that changes over time.

### Proof of Concept
1. Configure a `Barrier` (e.g. `AllowTopLevelPaidExecutionFrom` or `TakeWeightCredit`) on a runtime using `ProcessXcmMessage` as the `MessageProcessor` for `pallet-message-queue`.
2. Enqueue an XCM message from an origin whose weight credit is momentarily exhausted (e.g., due to prior messages in the same block) such that the barrier returns `Err(ProcessMessageError::Overweight(..))`/rejects execution and the executor ultimately surfaces `xcm::latest::Error::Barrier`.
3. Observe in `process_message` (`polkadot/xcm/xcm-builder/src/process_xcm_message.rs` lines 118-121) that `Barrier` falls to the `_ =>` branch and is returned as `ProcessMessageError::Unsupported`.
4. Observe in `process_message_payload` (`substrate/frame/message-queue/src/lib.rs` lines 1609-1613) that `Unsupported` is treated as `Unprocessable { permanent: true }`, causing `service_page_item` (lines 1378-1390) to mark the message processed and permanently remove it from the page — even though, had the message been retried on the next block (when weight credit resets), it would have executed successfully.
5. Compare against `execute_overweight_keeps_stack_ov_message`/`process_discards_stack_ov_message` tests in `substrate/frame/message-queue/src/tests.rs` (lines 1899-1991), which show the deliberate design distinction the codebase makes between transient and permanent errors — confirming `Barrier`/weight/fee errors are misclassified relative to that intended design.
