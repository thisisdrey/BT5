### Title
Incorrect `owner_deposit` accounting on depositor change in `do_set_item_metadata` causes permanent reserved-fund drift and stuck balances - (`File: substrate/frame/nfts/src/features/metadata.rs`)

### Summary
`Pallet::do_set_item_metadata` in `pallet-nfts` tracks a collection-level running total, `collection_details.owner_deposit`, that is supposed to represent exactly the sum of metadata/attribute deposits currently paid by the collection owner. When an item's metadata depositor is switched between "owner-paid" (`maybe_depositor == None`) and "explicitly-paid" (`maybe_depositor == Some(account)`), the code updates `owner_deposit` based only on the *new* call's depositor argument, not on whether the *previous* deposit was actually counted in `owner_deposit`. This is the same broken-invariant class as the reported `PrivateVesting.sol::setWhitelist()` bug: a per-entry value is reassigned/cleared while the aggregate total is adjusted using the wrong condition, desynchronizing the total from the real underlying value.

### Finding Description [1](#0-0) 

```rust
let depositor = maybe_depositor.clone().unwrap_or(collection_details.owner.clone());
let old_depositor = old_deposit.account.unwrap_or(collection_details.owner.clone());

if depositor != old_depositor {
    T::Currency::unreserve(&old_depositor, old_deposit.amount);
    T::Currency::reserve(&depositor, deposit)?;
} else if deposit > old_deposit.amount {
    T::Currency::reserve(&depositor, deposit - old_deposit.amount)?;
} else if deposit < old_deposit.amount {
    T::Currency::unreserve(&depositor, old_deposit.amount - deposit);
}

if maybe_depositor.is_none() {
    collection_details.owner_deposit.saturating_accrue(deposit);
    collection_details.owner_deposit.saturating_reduce(old_deposit.amount);
}
```

The bug: `owner_deposit` is only mutated when the **current** call's `maybe_depositor` is `None`. It ignores whether the **old** deposit (`old_deposit.account`) was owner-paid.

- Case A (owner → explicit depositor): item was previously owner-paid (`old_deposit.account == None`, so it *was* included in `owner_deposit`). Caller now sets `maybe_depositor = Some(other)`. The old amount is correctly unreserved from the owner (`old_depositor == owner`), but because `maybe_depositor.is_some()`, the `if maybe_depositor.is_none()` branch is skipped — `owner_deposit` is **never reduced** by `old_deposit.amount`. `owner_deposit` stays permanently inflated relative to what the owner actually has reserved.
- Case B (explicit depositor → owner): item was previously paid by `other` (not counted in `owner_deposit` at all). Caller now calls with `maybe_depositor = None`. The branch executes: `owner_deposit.saturating_accrue(deposit)` (correct, new deposit now owner-paid) but also `owner_deposit.saturating_reduce(old_deposit.amount)` — subtracting an amount that was **never part of `owner_deposit`** in the first place. This silently deflates `owner_deposit` below the owner's true reserved balance.

Both directions break the invariant "`owner_deposit` == sum of all owner-paid metadata/attribute deposits currently reserved," exactly mirroring the reported bug where an aggregate total is decremented/incremented based on the wrong branch condition instead of tracking the actual prior state of the per-entry value.

### Impact Explanation
`owner_deposit` is the value used elsewhere in the pallet (destroy-collection cleanup and deposit-refresh flows) to determine how much currency to unreserve from the collection owner. Because Case B causes `owner_deposit` to be silently deflated below the real reserved amount, any code path that later unreserves based on the tracked `owner_deposit` (rather than the actual `Currency::reserved_balance`) will release less than what is truly held on hold for the owner. The excess remains reserved indefinitely with no code path left to release it, since the pallet's only bookkeeping of "how much the owner is owed back" is the corrupted `owner_deposit` counter — a permanent fund lock for the collection owner. Conversely, Case A's inflation can cause internal over-accounting that desyncs displayed/tracked deposit totals from actual reserves, undermining accounting integrity used by downstream deposit-repricing logic (e.g., `poke_deposit`/redeposit style flows that key off collection-level deposit totals in this pallet family).

### Likelihood Explanation
Any account with `CollectionRole::Admin` on a collection can call `set_metadata`/`force_set_metadata` internals reaching `do_set_item_metadata` and alternate the depositor argument (owner vs. explicit account) across successive calls on the same item — this requires no privileged governance action, no malicious validator/relayer, and no race condition, just two ordinary permissioned calls in sequence. This is a deterministic, always-reachable state-corruption path, not a timing-dependent or validator-assumption-dependent bug.

### Recommendation
Base the `owner_deposit` adjustment on whether the **old** deposit was actually owner-paid (i.e., `old_deposit.account.is_none()`), not on the new call's `maybe_depositor`:
```rust
if old_deposit.account.is_none() {
    collection_details.owner_deposit.saturating_reduce(old_deposit.amount);
}
if maybe_depositor.is_none() {
    collection_details.owner_deposit.saturating_accrue(deposit);
}
```
This decouples the subtraction of the old value from the addition of the new value, matching the report's recommendation to always perform the correct debit/credit independently rather than gating both on a single unrelated condition.

### Proof of Concept
1. Create a collection with `DepositRequired` enabled; caller is the collection `owner`/`Admin`.
2. Call `set_metadata` (root/owner path, `maybe_depositor = None`) on `item_1`: deposit `D1` is reserved from `owner`, `owner_deposit += D1`.
3. Call the equivalent of `do_set_item_metadata` again on `item_1` with `maybe_depositor = Some(other_account)` (e.g., via an internal API/force path that allows specifying a depositor): `D1` is unreserved from `owner` (correct), but `owner_deposit` is **not reduced** by `D1` since the `if maybe_depositor.is_none()` guard is skipped.
4. `owner_deposit` is now permanently inflated by `D1` relative to `owner`'s actual reserved balance.
5. Symmetrically, setting metadata back to `maybe_depositor = None` afterward triggers `owner_deposit.saturating_reduce(old_deposit.amount)` for an `old_deposit.amount` that belonged to `other_account`, deflating `owner_deposit` below the owner's true holds and permanently orphaning reserved currency that no cleanup path will release.
