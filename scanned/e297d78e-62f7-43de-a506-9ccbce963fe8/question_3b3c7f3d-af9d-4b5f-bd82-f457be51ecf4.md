Cross-check `TokenId::from_str`'s outer `split_once(':')` against `ImtTokenId`'s inner `split_once(':')`: for `TokenId::Imt`, the full string is `imt:<minter_id>:<token_id>` — TWO colons. `TokenId::from_str` consumes only the FIRST colon (typ vs data=`<minter_id>:<token_id>`), then `ImtTokenId::from_str` consumes the data's first colon (minter vs token). Can an attacker choose `token_id` (arbitrary string) equal to another minter's full valid AccountId + ':' + a third string, so that if any code mistakenly re-parses just the `data` portion as a nested `ImtTokenId` a second time (e.g. double-unwrapping in a bridge/wrapper contract), the nested minter differs from `signer_id`, letting the attacker's mint be misattributed to `victim_minter`'s namespace and collide with `victim_minter`'s legitimately minted `TokenId::Imt(ImtTokenId{minter_id: victim_minter, token_id: X})`? Binding: no double-unwrap of `data` should ever occur outside `TokenId::from_str` itself. Impact: Critical if such re-parsing exists anywhere reachable from a bridge/wallet contract in this repo. Proof: cargo test asserting a single, non-recursive parse call at every `TokenId::from_str` call site handling untrusted strings.
