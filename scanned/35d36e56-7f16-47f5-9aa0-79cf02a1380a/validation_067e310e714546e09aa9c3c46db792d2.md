## Title
Silent swallowing of bounty payout `transfer()` failures via `debug_assert!` permanently locks funds and falsely emits `BountyClaimed` - (File: `substrate/frame/bounties/src/lib.rs`)

### Summary
`Pallet::claim_bounty` in `pallet-bounties` performs two value transfers out of the bounty sub-account (curator fee and beneficiary payout) and, instead of propagating any transfer failure with `?` or `ensure!`, only checks the result with `debug_assert!(res.is_ok())`. In a release/production runtime build, `debug_assert!` compiles to a no-op, so a failed transfer is silently ignored while the function proceeds to delete the bounty record and emit `Event::BountyClaimed` claiming the payout succeeded. This is the same root cause class as the reported `transfer()`-vs-`call()` issue: an unchecked, best-effort value-move whose failure is not surfaced to the caller, but here the failure mode is worse because the guard (`debug_assert!`) is entirely absent in production instead of merely reverting.

### Finding Description
`claim_bounty` computes `fee`, `payout`, and moves funds from `bounty_account` to `curator` and `beneficiary` using `T::Currency::transfer(..., AllowDeath)`: [1](#0-0) 

Both transfer calls are annotated "should not fail" and their `Result` is checked only via `debug_assert!(res.is_ok())`. `debug_assert!` is stripped out under `#[cfg(not(debug_assertions))]`, which is exactly the configuration used by production runtime builds (`cargo build --release`, WASM runtime builds shipped on-chain). Consequently, if either transfer returns `Err`, execution simply continues: the bounty entry is removed (`*maybe_bounty = None`), `BountyDescriptions` is cleared, `T::ChildBountyManager::bounty_removed` is invoked, and `Event::BountyClaimed { index, payout, beneficiary }` is deposited — all as if payment had succeeded.

A concrete failure trigger for `Currency::transfer` with `AllowDeath` is a payout to a fresh (never-before-existing) `beneficiary`/`curator` account for an amount below `ExistentialDeposit`: `pallet-balances` returns `Error::ExistentialDeposit` because it cannot create a new account below the ED, regardless of the `AllowDeath`/`AllowKeepAlive` setting on the *sender* side. `AllowDeath` only governs whether the *sender* account may be reaped; it does not bypass the ED requirement on the *receiver*.

Because the beneficiary is set earlier by the curator via `award_bounty` (an unprivileged-adjacent, curator-controlled but not admin-privileged action already baked into the bounty lifecycle) and the payout/fee split is derived from `bounty.fee` and `bounty.value` at proposal time, an attacker acting as curator/beneficiary of their own bounty (or a bounty they control both sides of) can engineer a tiny residual `payout` or `final_fee` (e.g. by setting `fee` very close to `value`, leaving `payout` below ED for the target chain) so that the beneficiary-side transfer fails while the record is deleted anyway.

### Impact Explanation
This breaks the "settle exactly once, and only after execution succeeds" invariant called out in the Pivots: payout state (`Bounties` storage, `BountyDescriptions`, child-bounty bookkeping) advances and an authoritative `BountyClaimed` event fires even though the value transfer did not occur. The bounty's backing funds remain stranded in the now-orphaned `bounty_account` (no longer referenced by any `Bounties` storage entry, so it cannot be re-claimed through the normal pallet flow), which is a permanent fund lock, and downstream consumers of `BountyClaimed` (indexers, treasuries, or other pallets relying on the event) observe a payout that never happened, which is exactly the "duplicate settlement or payout"/"false state acceptance" class the pivots target.

### Likelihood Explanation
This does not require a malicious validator, collator, relayer, or governance/admin actor — it can be triggered by any account that ends up as curator/beneficiary of a bounty (bounty creation is permissionless via `propose_bounty`, and curator proposal/acceptance is a normal signed flow), simply by shaping the bounty `fee`/`value` so the residual payout lands under the chain's `ExistentialDeposit`. `claim_bounty` itself is explicitly callable by "anyone" (`ensure_signed(origin)?; // anyone can trigger claim`), so triggering the code path requires no special origin.

### Recommendation
Replace `debug_assert!(res.is_ok())` with proper error propagation (`res?` or `ensure!`) for both transfers in `claim_bounty` (and the analogous `unreserve` check), or restructure the function so that fund transfers are executed and confirmed before the bounty record is removed and `BountyClaimed` is emitted, mirroring the async `PaymentState`/`check_status` pattern already used in `pallet-treasury` and `pallet-multi-asset-bounties`.

### Proof of Concept
1. Deploy a runtime built in release mode (`debug_assertions` disabled, as in production).
2. Propose and fund a bounty with `value` set so that after curator `fee` is subtracted, `payout = value - fee` is smaller than the chain's `ExistentialDeposit`, and set `beneficiary` to a brand-new account with zero prior balance.
3. Progress the bounty through `propose_curator` → `accept_curator` → `award_bounty` → wait `unlock_at` → call `claim_bounty(bounty_id)`.
4. Observe: `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` returns `Err(Error::ExistentialDeposit)` from `pallet-balances`, but since the runtime is release-built, `debug_assert!(res.is_ok())` is compiled out and ignored.
5. `Bounties::<T,I>::remove` proceeds, `Event::BountyClaimed` fires with the stated `payout`, yet the beneficiary's balance never increased and the funds remain in `bounty_account`, now unreachable through any pallet call. [2](#0-1)
