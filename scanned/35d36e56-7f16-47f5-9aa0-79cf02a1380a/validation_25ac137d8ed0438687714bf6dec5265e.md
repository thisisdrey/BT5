### Title
Snowbridge V2 `CallContract` gas metering trusts caller-supplied `gas` value instead of a calibrated constant, allowing underpriced relayer-refund commitments - (File: bridges/snowbridge/primitives/outbound-queue/src/v2/message.rs)

### Summary
In Snowbridge Outbound Queue V1, `ConstantGasMeter::maximum_dispatch_gas_used_at_most` uses hardcoded, protocol-calibrated gas constants for every command (e.g. `TransferToken => 200_000`), matching the pattern the Morph report says was miscalibrated (`commitScalar`). In V2, this metering trust model is broken: for `Command::CallContract`, the gas figure used to build the committed `OutboundCommandWrapper.gas` (and thus the `max_dispatch_gas`/fee basis relayers rely on to be refunded) is taken directly from the message itself (`gas: gas_limit`) rather than from a protocol-controlled constant: [1](#0-0) 

### Finding Description
`GasMeter::maximum_dispatch_gas_used_at_most` is the exact analog of Morph's `commitScalar`/`l1DataFee` machinery: it is the on-chain estimate of the "real cost" that determines the compensation (`reward`/fee) baked into the committed message for whoever delivers/executes it on the remote chain. For all other V2 commands (`SetOperatingMode`, `Upgrade`, `UnlockNativeToken`, `RegisterForeignToken`, `MintForeignToken`), this is a protocol-fixed constant, mirroring Scroll/Morph's correct `blobScalar`-style approach: [2](#0-1) 

But `Command::CallContract { gas: gas_limit, .. } => *gas_limit` takes the gas value straight from the `Command` enum's `gas` field, which is populated from the `ContractCall`/`Transact` payload constructed by the *user* on the source chain (as seen in the emulated test `transact_with_agent_from_asset_hub`, where `gas: 40000` is set arbitrarily by the test/user in the `ContractCall::V1` struct passed through `Transact`): [3](#0-2) 

This value becomes the committed `gas` field in the `OutboundMessageWrapper`/`CommandWrapper` that is Merkle-committed for the Ethereum Gateway contract, and directly determines `max_dispatch_gas` used to price/compensate delivery: [4](#0-3) 

The root problem, exactly analogous to Morph's `commitScalar`: the value used to *compute the fee/reward owed to whoever performs the costly remote work* (relayer, in this case) is not an accurate, protocol-verified representation of the actual on-chain execution cost — it is a number the message author chooses. A user can craft a `CallContract` command specifying an artificially low `gas` (e.g., 1) while the `PendingOrder.fee` stored for that nonce (which is what the relayer earns for successful delivery) is computed/set independently based on whatever the user paid via `PayFees`/`InitiateTransfer` on the source side, not tied to enforced minimum coverage of the real dispatch cost. Unlike V1's `SendMessage::validate`, which calls `Self::calculate_fee(gas_used_at_most, ...)` to derive `Fee` directly from the `GasMeter` output before enqueuing, the V2 `do_process_message` pipeline stores whatever `fee` value arrived in the decoded `Message` (`let Message { origin, id, fee, commands } = ...`), and separately computes `gas` from `T::GasMeter::maximum_dispatch_gas_used_at_most(&command)` — but for `CallContract`, that "measurement" is just an echo of the attacker-supplied value, so there's no cross-check forcing `fee` to actually cover `gas * fee_per_gas`: [5](#0-4) 

I was unable to fully trace, within the tool budget, the exact code path in `bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs` that derives the `Message.fee` value from the XCM `PayFees`/withdrawn WETH amount versus the `CallContract.gas` value, so I cannot state with certainty whether there is (or is not) a runtime-level assertion tying `fee >= gas * fee_per_gas` before a message is accepted into the queue. This is the missing link that would need verification (e.g., via a Devin session with full file access) to confirm the vulnerability is exploitable end-to-end rather than mitigated elsewhere.

### Impact Explanation
If `fee` is not enforced to cover `gas_limit * fee_per_gas` for `CallContract` commands, a user can submit a Transact/CallContract instruction via `pallet_xcm::execute` on Asset Hub with a high `gas` field (to ensure execution succeeds on Ethereum, since `gas` also becomes the actual gas limit passed to the target contract call) while paying a `PayFees`/reward amount calibrated to a much smaller nominal cost. This directly mirrors the Morph impact: relayers who deliver `CallContract` messages could be systematically underpaid relative to the real Ethereum gas cost of dispatch, degrading relayer economics and potentially stalling Snowbridge V2 outbound message delivery (bridge processing stall), which falls squarely within the "public underpriced work that degrades block production or stalls bridge processing" impact category.

### Likelihood Explanation
Medium — this requires an unprivileged user to construct a specific `Transact`/`ContractCall` XCM message via the standard `pallet_xcm::execute` public entrypoint on Asset Hub, exactly as demonstrated in existing test fixtures. No relayer, governance, or validator collusion is needed. The main uncertainty is whether an existing fee-validation check (not found within the explored files) already enforces `fee >= gas_limit * fee_per_gas + base_reward`, which would neutralize this.

### Recommendation
Verify and, if absent, add an explicit runtime-side check in `EthereumOutboundQueueV2::do_process_message` (or the `SendMessage::validate` equivalent in v2) that computes the minimum required fee from the `CallContract.gas` value (via `T::GasMeter` and `PricingParameters::fee_per_gas`) and rejects/adjusts messages whose `fee` field does not cover it — mirroring the V1 pattern where `calculate_fee(gas_used_at_most, params)` is computed and attached before the message is queued, rather than trusting an externally supplied `fee`.

### Proof of Concept
Conceptual PoC (pending confirmation of the missing fee-validation code path):
1. Construct an XCM on Asset Hub: `WithdrawAsset`, `PayFees` (minimal WETH amount), `InitiateTransfer` to Ethereum with `remote_xcm` containing `Transact { call: ContractCall::V1 { gas: <large value, e.g. 10_000_000>, ... } }`.
2. Submit via `pallet_xcm::execute` (public, unprivileged origin) as done in `transact_with_agent_from_asset_hub`.
3. Observe that `EthereumOutboundQueueV2::do_process_message` commits `gas = 10_000_000` (from `maximum_dispatch_gas_used_at_most`) into the `PendingOrder`/`OutboundMessage`, while the attacker controls the `fee` amount supplied via `PayFees` independently.
4. If no on-chain check ties `fee` to `gas * fee_per_gas`, the relayer who delivers this message and pays for ~10M gas on Ethereum will be compensated far less than actual cost — repeat at scale to bleed relayer/bridge economics, analogous to the Morph `commitBatch()` attack.

/// A meter that assigns a constant amount of gas for the execution of a command
///
/// The gas figures are extracted from this report:
/// > forge test --match-path test/Gateway.t.sol --gas-report
///
/// A healthy buffer is added on top of these figures to account for:
/// * The EIP-150 63/64 rule
/// * Future EVM upgrades that may increase gas cost
pub struct ConstantGasMeter;

impl GasMeter for ConstantGasMeter {
	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64 {
		match command {
			Command::SetOperatingMode { .. } => 40_000,
			Command::Upgrade { initializer, .. } => {
				// total maximum gas must also include the gas used for updating the proxy before
				// the the initializer is called.
				50_000 + initializer.maximum_required_gas
			},
			Command::UnlockNativeToken { .. } => 200_000,
			Command::RegisterForeignToken { .. } => 1_200_000,
			Command::MintForeignToken { .. } => 100_000,
			Command::CallContract { gas: gas_limit, .. } => *gas_limit,
		}
	}
}
