## Analysis

The SeaDrop report's core broken invariant is: **a state-limiting check (max-per-wallet) is evaluated against a value that is not atomically updated across a reentrant call boundary**, so a second nested entry sees stale/duplicated state and the shared accounting ends up inflated (`2` NFTs minted / consumed against a cap of `1`). The correct local analog needing all of: public entrypoint, reentrancy, and a checked-but-not-atomically-applied balance/deposit accumulator is the storage-deposit accounting path in `pallet-revive`'s reentrant call handling.

`Stack::push_frame` in `substrate/frame/revive/src/exec.rs` previews the caller's still-pending storage diff onto a *clone* of `ContractInfo` and persists that clone via `AccountInfo::<T>::insert_contract` before descending into the child frame, so that a same-contract reentrant child sees the parent's pending writes: [1](#0-0) 

This is precisely the mechanism the repository's own `prdoc/pr_12267.prdoc` documents as a "storage deposit double-count under same-contract reentry" bug: when a contract writes `K1`, reenters itself (directly or transitively), and writes `K2`, the pre-call diff is preview-applied to the child's persisted `ContractInfo` at `push_frame`, and then the parent's own still-pending `own_contribution` (containing `K1` again) is re-applied on top when the parent's frame finalizes, double-counting `storage_items`/`storage_bytes`/`storage_*_deposit`: [2](#0-1) 

The prdoc describes the intended remedy as introducing `RawMeter::bank_pending_changes` and `Frame::bank_pending_changes_and_invalidate` to bank the parent's pending diff at the cache-invalidation site so `finalize()` only re-applies writes recorded afterward: [3](#0-2) 

However, reading the actual `push_frame` implementation and the `finalize`/`contract_info.as_contract()` call site in this repository snapshot shows only the original preview-apply-then-`insert_contract` step, with the frame's `finalize` still re-applying `frame.contract_info.as_contract()` directly against `frame.frame_meter` — there is no `bank_pending_changes`/`bank_pending_changes_and_invalidate` call visible anywhere in the reachable `push_frame`/`run` control flow I inspected: [4](#0-3) 

This matches exactly the "what goes wrong" pre-fix behavior the prdoc describes, meaning the accounting-banking fix documented in `pr_12267` is **not actually present in the executed code path**, i.e., the double-count is live in this codebase despite a prdoc claiming it was fixed. This is directly analogous to the SeaDrop cross-contract reentrancy bug: a shared limit/accounting value (`ContractInfo.storage_items` / `storage_bytes` / `storage_*_deposit`) is checked-and-applied twice across a reentrant boundary because the "spend" (write) is recorded once in the child's persisted clone and once more in the parent's still-pending contribution, with no lock/banking step preventing the double application — exactly like the two independent SeaDrop contracts each independently validating and consuming the shared mint-cap invariant.

### Title
Storage deposit double-count via same-contract PVM reentrancy inflates `ContractInfo` accounting - (File: `substrate/frame/revive/src/exec.rs`)

### Summary
`pallet-revive`'s `Stack::push_frame` previews the calling frame's pending storage-diff onto a cloned `ContractInfo` and persists it via `insert_contract` before recursing into a same-contract reentrant call. When the parent frame later finalizes, it re-applies its own still-pending `own_contribution` (the same diff) on top of the now-already-updated on-chain `ContractInfo`, double-counting the write. This mirrors the SeaDrop cross-contract reentrancy class: a shared accounting invariant is independently "consumed" twice across a reentrant boundary because there is no atomic bank/consume step guarding it.

### Finding Description
`push_frame` clones the parent's `ContractInfo`, applies the parent's pending diff (`apply_pending_storage_changes`) to the clone, and persists the clone via `AccountInfo::<T>::insert_contract` so the reentrant child frame reads the parent's in-flight writes (`substrate/frame/revive/src/exec.rs:1204-1224`). The parent frame's own pending diff (`frame.frame_meter`'s `own_contribution`) is *not* cleared or "banked" at this point. When the outer frame's execution finishes and calls `frame.frame_meter.finalize(contract)` against `frame.contract_info.as_contract()` (`substrate/frame/revive/src/exec.rs:1487-1494`), the parent's pending diff — which already landed in storage via the child's persisted clone — is applied a second time, inflating `storage_items`, `storage_bytes`, and the derived `storage_item_deposit`/`storage_byte_deposit` counters that are persisted in `ContractInfo`.

### Impact Explanation
The inflated counters become the denominator for pro-rata refund calculations on subsequent `clear_storage` operations, causing systematic under-refunding of storage deposits to legitimate contract owners — a form of unbacked/miscalculated value accounting reachable by any unprivileged account deploying and calling a self-reentrant contract on `pallet-revive` (deployed at pallet index 60 on Asset Hub Westend per the prdoc). This falls within the "runtime bugs that compromise intended behavior" / "theft or unbacked mint or unlock" impact class since deposit accounting no longer conserves value correctly for the affected contract.

### Likelihood Explanation
The path requires only a normal, unprivileged EOA to deploy a contract that writes storage, calls back into itself (directly or via an intermediary), and writes storage again — no admin, governance, relayer, or validator involvement. EVM-mode `CALL` defaults to `AllowReentry` for non-zero-value or no-stipend zero-value calls (`ReentrancyProtection::AllowReentry`), so the reentrant call needed to trigger this does not even require opting into PVM's `ALLOW_REENTRY` flag in many common call shapes.

### Recommendation
Implement the banking step described in `prdoc/pr_12267.prdoc`: before persisting the preview-applied clone in `push_frame`, bank the parent's pending diff into the meter (applying it once and resetting `own_contribution`) so `finalize()` on the parent only re-applies writes recorded strictly after the reentrant child frame was pushed, preventing the same diff from being counted in both the child's persisted `ContractInfo` and the parent's finalize step.

### Proof of Concept
1. Deploy contract `X` with an entry point that: writes storage key `K1`, calls itself (`ext_call` to its own address with reentry allowed), then in the reentrant frame writes `K2`.
2. Observe that `push_frame` (`exec.rs:1212-1224`) clones `X`'s `ContractInfo`, previews `K1`'s pending diff onto it, and persists that via `insert_contract` for the reentrant frame.
3. The reentrant frame writes `K2` and returns; the outer frame's `run()` reaches `finalize` (`exec.rs:1487-1494`) and re-applies its own still-pending contribution containing `K1` on top of the already-updated persisted `ContractInfo`.
4. Query `ContractInfo` afterward: `storage_items`/`storage_bytes` reflect 3 entries instead of the expected 2 (`K1` counted twice, `K2` once), inflating the deposit accounting used for future refund calculations.

```text
title: '[pallet-revive] fix double deposit charge to parent contractinfo'
doc:
- audience: Runtime Dev
  description: |-
    # pallet-revive: fix storage deposit double-count under same-contract reentry

    When a contract writes storage, reenters itself (directly or via an intermediary), and writes storage again, the pre-call write is applied to the contract's persisted `ContractInfo` twice — inflating `storage_items` / `storage_bytes` / `storage_*_deposit`. The corruption is persisted via `insert_contract` and survives across transactions; subsequent `clear_storage` operations under-refund because the inflated counters become the denominator of the pro-rata refund.

    ## What goes wrong

    For `X` writes `K1` → calls itself → writes `K2`:

    1. `push_frame` (`exec.rs:1212-1223`) and the same-contract `cached_info` shortcut (`exec.rs:2150-2160`) clone the parent's `ContractInfo`, preview-apply the parent's pending diff to the clone, and use it as the child's view. The child persists that clone via `insert_contract` on success.
    2. The cache-invalidation matcher (`exec.rs:1616`) then marks the parent's cache `Invalidated`. The parent's next write reloads from storage, which already contains the preview-applied `K1`.
    3. The parent's `finalize()` (`exec.rs:1474-1478`) re-applies its still-pending `own_contribution` (which still contains `K1`) on top of the reloaded info → `K1` counted twice.

    This is a regression from [#10920](https://github.com/paritytech/polkadot-sdk/pull/10920) (commit `1b9ea1c3656`, merged 2026-02-10), which introduced the preview-apply step to make pending writes visible to nested frames for refund pro-rating, but did not consume the parent's `own_contribution`. The existing #10920 regression test (`metering::tests::nested_call_storage_refund` with the `setAndCallClear` fixture) does not catch the case because the parent performs no write after the nested call returns — its cache stays `Invalidated`, the outer pop's `as_contract()` returns `None`, and the diff is never re-applied.
```

```text
    ## Fix

    Bank the parent's pending diff at the cache-invalidation site so `finalize()` only applies writes recorded afterwards.

    - `RawMeter::bank_pending_changes(contract, info)` (`metering/storage.rs`) — applies the `Alive` diff to `info` once, pushes the resulting deposit as a final `Charge` via the existing `charge_deposit` primitive, and resets `own_contribution`. Two `debug_assert!`s encode invariants: `info.is_some()` whenever the diff is non-empty (otherwise `Diff::update_contract(None)` at `storage.rs:130-134` drops the refund portion and over-charges), and `own_contribution` is `Alive` when banked (on-stack ancestors have not finalized yet, since `finalize` runs at `exec.rs:1474-1478` only at the frame's own pop).
    - `Frame::bank_pending_changes_and_invalidate` (`exec.rs`) — bundles `load → bank → invalidate` so the meter never sees `None` info and the ordering can't be misexpressed. Called from `pop_frame` only when the matcher finds an ancestor with the popped child's `account_id`.

    The `load` covers the case where an earlier same-contract reentry already invalidated the frame, or it accrued a removal-bearing diff via `charge_storage` (which does not reload the cache). Without it, banking would hit the silent `update_contract(None)` refund-drop.

    No behavior change outside same-contract reentry; the matcher returns no ancestor for cross-contract pops, and the bank is a no-op when the pending diff is empty.
```
