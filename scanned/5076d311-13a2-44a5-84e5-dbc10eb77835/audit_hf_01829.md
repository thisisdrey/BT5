# [M] Unable to check `state`

## Details
The vulnerability consists of a mismatch between the governance contract's proposal queuing logic and its state‑query function. When a proposal is added through the queue() entry point, there is no validation that the supplied proposal identifier is non‑zero, allowing any caller to create a proposal with proposalId == 0. The state(uint proposalId) view function, however, contains a guard that requires proposalId to be greater than the contract's initialProposalId (which is defined as zero) and also that the overall proposalCount is at least as large as the identifier. Because the guard explicitly checks proposalId > initialProposalId, a call to state(0) triggers a revert with the message "GovernorBravo::state: invalid proposal id". As a result, a proposal that has been queued with an identifier of zero becomes permanently untrackable: any attempt to read its current state, and consequently to trigger its execution flow, fails. This creates a dead‑end where the governance mechanism cannot progress, potentially locking funds or preventing protocol upgrades that rely on successful proposal execution. The issue manifests whenever the governance system is invoked with a zero identifier, which can happen because the queue() function does not enforce the non‑zero constraint. Users of the protocol, including token holders, developers, and the governing committee, are affected because they may see proposals appear in the queue but never be executable, leading to confusion and a loss of trust in the governance process. The flaw was uncovered during a manual audit when the security researcher demonstrated that a mis‑configured proposal could be queued with id 0, causing the state() call to revert and halting the proposal lifecycle. The problem is subtle because the contract assumes that proposal IDs are always generated by the underlying Cosmos‑SDK and therefore never zero, an assumption that is not enforced at the Solidity level. To remediate the issue, the contract should introduce an explicit check in queue() (or any function that accepts an external proposalId) that rejects zero values, or alternatively adjust the state() guard to handle the zero case consistently with the rest of the system. By aligning the input validation across both entry points, the governance contract will regain its ability to report and execute proposals correctly, restoring expected behavior where users can query a proposal's state and see successful execution rather than an unexpected revert.

## Proof of Concept
There is no check to prevent queueing a `proposalId` with a value of 0 via the [`queue()`](https://github.com/Plex-Engineer/lending-market/blob/755424c1f9ab3f9f0408443e6606f94e4f08a990/contracts/Governance/GovernorBravoDelegate.sol#L37-L47) function.  
However, in the `state()` function there is a check preventing using a `proposalId == 0`.  
For clarity: `initialProposalId` must be zero according to `_initiate()`, therefore, `proposalId` cannot be 0 according to check below.

## Recommendation
Implement check to preventing queueing a `proposalId == 0`.

The ProposalId cannot be 0 as the proposal IDs are fixed and will be set via the cosmos-sdk.

The warden has shown how, through a misconfiguration, a proposal could never be executable due to a revert in `state()`.

While I believe the warden has already shown a remediation that would cover this scenario, I believe the Warden has shown a unique possible situation that can cause the system to stop working as intended.

While the sponsor says the proposalId will never be 0, there is no way to avoid that at the Smart Contract level, meaning that any caller can set the proposal to 0.

For these reasons, I think Medium Severity to be appropriate.
