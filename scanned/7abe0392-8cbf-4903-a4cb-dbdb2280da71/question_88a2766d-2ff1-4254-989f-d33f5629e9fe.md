Target: `AuthCall::execute_intent` and `Contract::auth_call_callback_gas` (contracts/defuse/src/contract/intents/auth_call.rs). Attacker action: signs a `MultiPayload` with two `AuthCall` intents in the same `DefuseIntents`, both naming `contract_id: attacker_contract` with `state_init: Some(StateInit::V1{...})` deriving to the *same* deterministic `AccountId`, each with distinct `msg`. Preconditions: the deterministic account does not exist yet; signer holds sufficient wNEAR to fund `attached_deposit` twice. Call sequence: both `auth_call` calls independently schedule `p.state_init(state_init, NearToken::ZERO)` + `on_auth` promises in the same receipt, `Engine::finalize` has already committed both wNEAR debits; NEAR runtime handles at most one successful `StateInit` and the second either fails to deploy or double-charges storage, while both `on_auth` calls still fire against the same contract instance. Binding: the number of times a given wNEAR debit funds a distinct on-chain effect == the number of `AuthCall` intents that authorised a debit for that account. Impact: Critical, an attacker-controlled contract's `on_auth` is invoked twice off a single deployment while the signer is billed for state_init/attached_deposit twice, or a corrupted deploy consumes only one wNEAR debit for two nominally independent calls. Proof: near-workspaces sandbox test asserting `on_auth` call count == number of successful `StateInit` deploys, and wNEAR debited == wNEAR usefully spent.
