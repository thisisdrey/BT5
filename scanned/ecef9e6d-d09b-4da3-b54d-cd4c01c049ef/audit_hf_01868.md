# [M] M-5 Conditions' order impact

## Summary
Severity: Medium
Contest weight: 0.0415
Dataset id: 10400

Type: audit-finding

## Details
The vulnerability is an order‑dependent condition evaluation flaw in the contract that manages escrow or similar state transitions. The contract iterates through a list of pre‑defined conditions and decides whether a user action, such as releasing funds, is allowed based on the result of each check. Because the implementation assumes a fixed sequence, the logical outcome changes if the conditions are reordered. This dependency originates from the fact that the code does not treat each condition as an independent predicate; instead, later checks may be skipped, overridden, or incorrectly combined depending on the result of earlier checks. An attacker who controls the ordering – typically the contract owner or any party that can propose a new set of conditions – can manipulate the flow so that a required safety check is never evaluated, or a check that should block a release is bypassed. Exploitation consists of arranging the conditions so that a malicious or faulty condition appears after a condition that already returns true, causing the subsequent checks to be ignored. As a result, funds may be released without satisfying all intended safeguards, or conversely, legitimate releases may be blocked, leading to locked assets. The issue manifests whenever the contract evaluates its condition list, which occurs on every state‑changing operation that depends on those checks, such as escrow settlement, withdrawal, or dispute resolution. All participants who rely on the escrow – users depositing funds, beneficiaries awaiting payment, and third‑party auditors – are affected because the protocol no longer guarantees that every required rule is enforced. The flaw was discovered during a manual security audit that examined the condition manager’s source code and identified the hard‑coded sequence of checks. It is subtle because the contract may behave correctly under the default ordering used in tests, making the problem easy to miss unless alternative orderings are deliberately tried. The bug belongs to the broader class of “order‑dependent logic” or “state‑machine ordering” vulnerabilities, where the correctness of a system relies on an implicit sequence rather than explicit, order‑agnostic validation. From a user’s perspective the symptom is that a withdrawal may succeed even though a prerequisite condition (for example, a dispute resolution or a time lock) was not satisfied, or a legitimate withdrawal may fail with no clear error, leading to confusion and potential loss of confidence. To remediate the issue the condition evaluation should be redesigned so that each predicate is evaluated independently and the final decision is derived from a deterministic aggregation (e.g., logical AND of all conditions) that does not depend on their position in the list. This makes the protocol resilient to changes in condition ordering, reduces owner‑related risk, and restores the intended security guarantees.

## Recommendation
We recommend redesigning the conditions check architecture to make its order independent.
