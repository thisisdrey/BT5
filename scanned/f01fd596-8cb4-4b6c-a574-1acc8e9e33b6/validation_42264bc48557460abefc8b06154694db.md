### Title
Unbounded on-demand order queue rewrite on every scheduling advance causes underpriced, growing per-block work - (File: polkadot/runtime/parachains/src/on_demand/mod.rs)

### Summary
The Solidity report flags `_removeFromQueue` for rewriting the *entire remaining queue* to storage every time even a single element is removed. The direct structural analog in this repository is `OrderQueue::pop_assignment_for_cores` in `polkadot/runtime/parachains/src/on_demand/mod.rs`, which is invoked every block through `Pallet::pop_assignment_for_cores` (called from the scheduler when advancing the claim queue). Instead of removing only the matched entries, it does `mem::take(&mut self.queue)`, iterates the **whole** queue, and rebuilds a brand-new `remaining_orders` vector that is written back wholesale via `self.queue = BoundedVec::truncate_from(remaining_orders)`. [1](#0-0) 

### Finding Description
`OrderQueue::pop_assignment_for_cores` is the on-demand analog of `_removeFromQueue`: regardless of how many orders are actually served (`num_cores` can be as low as 1), the function walks and rewrites the full `BoundedVec<EnqueuedOrder<N>, ConstU32<ON_DEMAND_MAX_QUEUE_MAX_SIZE>>` (capacity up to `ON_DEMAND_MAX_QUEUE_MAX_SIZE`, referenced in `polkadot/primitives/src/lib.rs`), even for entries that did not change position and were not popped: [2](#0-1) 

This is called every block through the thin wrapper `Pallet::pop_assignment_for_cores`, which mutates the single `OrderStatus` `StorageValue` and therefore re-serializes and re-writes the queue to storage on each call: [3](#0-2) 

The queue is populated by any signed account via the public, unprivileged extrinsics `place_order_allow_death`, `place_order_keep_alive`, and `place_order_with_credits`, all of which push into the same `OrderStatus.queue` up to the bounded maximum: [4](#0-3) [5](#0-4) 

Since the dispatchables' declared weights (`WeightInfo::place_order_allow_death`, etc.) only cover the cost of *placing* an order, not the future amortized cost every block pays to rebuild the queue while draining it, an attacker who fills the queue near `ON_DEMAND_MAX_QUEUE_MAX_SIZE` forces every subsequent block's scheduling advance to pay O(queue length) work to remove even a single ready order — exactly the "gas greedy for one removal" pattern from the original report, translated to per-block weight/PoV cost instead of gas.

### Impact Explanation
Because the whole remaining order set is cloned into a new `Vec`, re-encoded, and written back to the single `OrderStatus` storage value on every scheduling round regardless of how many entries were actually consumed, an attacker-controlled queue size directly inflates the fixed per-block cost of `on_demand`'s scheduling step. This is public underpriced work that scales the per-block PoV/weight cost of core-block production with attacker-supplied queue depth, which can degrade block production performance for the relay chain's scheduling pipeline — matching the "public underpriced work that degrades block production" impact class.

### Likelihood Explanation
No privileged actor, validator, collator, or off-chain component is required. Placing on-demand orders is permissionless (`ensure_signed` only) and inexpensive relative to the queue's maximum bound; each order enqueued only needs enough balance/credits to cover the spot price. Reaching queue sizes near the bound and keeping them populated (by repeatedly ordering for paras that are deliberately never scheduled) is realistically achievable by any funded account, making the described degradation path low-effort and repeatable every block.

### Recommendation
Avoid rebuilding the entire order vector on partial removal. Track removed/served indices and only rewrite the delta (e.g., use a front-index cursor or a `VecDeque`-like structure keyed by `(start, end)` indices, analogous to the reporter's own recommendation), or bound the amount of per-call work strictly by `num_cores * lookahead` rather than the full queue length, and ensure weight accounting for the scheduling step scales with actual queue occupancy rather than being treated as fixed.

### Proof of Concept
1. An attacker account repeatedly calls `place_order_with_credits` (or `place_order_allow_death`) for a `para_id` that is never actually granted a core (e.g., a para without available cores in a given round), pushing entries via `OrderQueue::try_push` until the queue approaches `ON_DEMAND_MAX_QUEUE_MAX_SIZE`. [6](#0-5) 
2. Each block, the scheduler calls `Pallet::pop_assignment_for_cores(now, num_cores)` with a small `num_cores` (e.g., 1), but `pop_assignment_for_cores::<T>` still iterates and rewrites the entire large queue via `mem::take`/rebuild/`BoundedVec::truncate_from`. [7](#0-6) 
3. Because the attacker's orders for the blocked para are never ready/served, they remain in `remaining_orders` and get rewritten to storage every single block, imposing an O(queue length) storage-write/PoV cost on the relay chain's scheduling hot path for the lifetime of the attack, at a cost not reflected in the fixed weight of the original `place_order_*` calls that created the queue entries.

impl<N> OrderQueue<N> {
	/// Pop `num_cores` from the queue, assuming `now` as the current block number.
	pub fn pop_assignment_for_cores<T: Config>(
		&mut self,
		now: N,
		mut num_cores: u32,
	) -> impl Iterator<Item = ParaId>
	where
		N: Saturating + Ord + One + Copy,
	{
		let mut popped = BTreeSet::new();
		let mut remaining_orders = Vec::with_capacity(self.queue.len());
		for order in mem::take(&mut self.queue) {
			// Order is ready 2 blocks later (asynchronous backing):
			let ready_at = order.ordered_at.saturating_plus_one().saturating_plus_one();
			let is_ready = ready_at <= now;

			if num_cores > 0 && is_ready && popped.insert(order.para_id) {
				num_cores -= 1;
			} else {
				remaining_orders.push(order);
			}
		}
		self.queue = BoundedVec::truncate_from(remaining_orders);
		popped.into_iter()
	}
