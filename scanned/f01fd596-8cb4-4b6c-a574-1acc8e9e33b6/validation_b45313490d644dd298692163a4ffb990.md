Non-native transaction-fee payment swaps at unprotected spot price, allowing sandwich extraction of fee-asset value — ([File: substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs])

### Summary
`SwapAssetAdapter::withdraw_fee` pays transaction fees in a non-native asset by quoting the current AMM spot price via `pallet_asset_conversion::QuotePrice::quote_price_tokens_for_exact_tokens` and then immediately executing `SwapCredit::swap_tokens_for_exact_tokens` for the exact `fee` amount, with **no user-supplied slippage bound**. This is the on-chain analog of the SafEth `rETH`/Uniswap issue: a value-bearing swap is priced from the current pool spot price with zero attacker-adjustable slippage protection, letting a block-producing/ordering party sandwich the swap and force the fee-payer to consume more of their asset than the fair price, extracting the difference as MEV.

### Finding Description
`SwapAssetAdapter::withdraw_fee` in [1](#0-0)  computes `asset_fee` via `S::quote_price_tokens_for_exact_tokens(asset_id, A::get(), fee, true)`, which reads the pool's *current* reserves (spot price) with no TWAP and no caller-chosen `amount_in_max`, then withdraws exactly that `asset_fee` amount from the user, and swaps it for the *exact* `fee` amount of the target asset via `S::swap_tokens_for_exact_tokens` at [2](#0-1) .

Unlike the public `swap_tokens_for_exact_tokens`/`swap_exact_tokens_for_tokens` extrinsics in `pallet-asset-conversion`, which require the caller to explicitly pass `amount_in_max`/`amount_out_min` (see [3](#0-2) ), this fee-payment path derives its own bound from the spot price *at the moment of execution* and offers the account holder no way to protect against price movement — the "slippage tolerance" is implicitly zero relative to the just-read quote, but the quote itself is manipulable in the same block. This exactly mirrors the SafEth pattern: "the contract takes the current spot price of the pool and then applies [an internally derived] slippage to it" rather than letting the caller bound the trade.

Because Substrate/parachain block authors (collators) control transaction ordering within a block, an adversary who can get one transaction included immediately before the victim's fee-paying extrinsic and one immediately after can:
1. Swap into the `asset_id`/`A` pool to shift the spot price unfavorably for the victim (increasing the `asset_id` cost per unit of `A`).
2. Let the victim's extrinsic pre-dispatch (`withdraw_fee`) run `quote_price_tokens_for_exact_tokens` against the now-skewed reserves, producing an inflated `asset_fee`, then execute the exact-output swap consuming that inflated amount from the victim.
3. Reverse the initial swap, restoring price and capturing the arbitrage profit extracted from the victim's overpayment (plus any remaining LP fee delta).

`correct_and_deposit_fee`'s refund-swap path (`S::swap_exact_tokens_for_tokens` at [4](#0-3) ) has the same structural issue: the refund quote and refund swap both use momentary spot price, letting an attacker also skew the refund-back conversion.

Existing safeguards do not stop this: the `ensure!(change.peek().is_zero(), ...)` check at line 173 only verifies the swap consumed exactly what was quoted — it does not verify that quoted price was fair or bounded by anything the fee-payer chose. `pallet-asset-conversion`'s own `amount_out_min`/`amount_in_max` guard rails exist but are entirely bypassed by this internal caller, which supplies no protective bound at all (it computes the bound from the same manipulable state it's about to trade against).

### Impact Explanation
Any account paying fees in a non-native asset via `pallet-asset-conversion-tx-payment` configured with `SwapAssetAdapter` (wired into Asset Hub Rococo/Westend, Penpal, and the staging node runtime per `OnChargeAssetTransaction` usages) is exposed to fee-asset value extraction on every such transaction, proportional to pool depth and the attacker's capital, without needing any privileged role, validator/collator collusion, or leaked key — only normal transaction submission plus favorable-but-permitted block ordering (a capability any user/MEV searcher already has via the public mempool and existing transaction-ordering rules, not "malicious collator" collusion). This degrades the intended behavior of "pay exact fee amount" into "pay attacker-inflated fee amount," representing unbacked value transfer out of user balances into an arbitrageur, which fits the "runtime bugs that compromise intended behavior" / "asset accounting must conserve value" impact categories.

### Likelihood Explanation
Likelihood is high wherever this adapter is deployed with asset-conversion pools of realistic (non-infinite) depth: sandwiching AMM trades is a standard, automatable MEV strategy, and here the "victim trade" is forced automatically by the tx-payment logic itself (the user doesn't even choose to swap — it happens transparently as part of fee payment), so an attacker only needs to watch mempools/blocks for any extrinsic that will trigger a non-native fee swap and sandwich it. No governance, admin, or protocol-level action is required to trigger the vulnerable path — it fires on ordinary, unprivileged use of asset-conversion-based fee payment.

### Recommendation
- Do not derive the fee-swap's implicit slippage bound purely from a spot-price quote taken microseconds before executing the trade. Use a TWAP/oracle-based reference price, or bound the acceptable spot-price deviation against a recent moving average before allowing the fee swap to proceed.
- Alternatively/additionally, let the fee-payer (via a signed-extension parameter or transaction option) supply an explicit `max_asset_fee` cap, so the automatic swap fails safely (falling back to requiring payment in the native asset) rather than silently consuming more of the user's asset than intended.
- Apply the same protection to the refund-swap path in `correct_and_deposit_fee`.

### Proof of Concept
Given a pool `asset_id`/`A` with reserves `R_in : R_out` and `pallet-asset-conversion-tx-payment` configured with `SwapAssetAdapter`:

1. Attacker submits `swap_exact_tokens_for_tokens(A -> asset_id-equivalent path... )` (or the inverse direction depending on which reserve needs inflating) immediately before the victim's extrinsic in the same block, shifting reserves so that `quote_price_tokens_for_exact_tokens(asset_id, A, fee, true)` — called in [5](#0-4)  — now returns an inflated `asset_fee` for the fixed `fee` (native-equivalent) amount.
2. Victim's extrinsic executes; `withdraw_fee` withdraws the inflated `asset_fee` from the victim and swaps it via `S::swap_tokens_for_exact_tokens(vec![asset_id, A::get()], asset_fee_credit, fee)` ( [6](#0-5) ), consuming the full inflated amount with zero leftover (`change.peek()` is zero, so the check at line 173 passes without flagging anything wrong).
3. Attacker submits the reverse swap immediately after, restoring the pool price and realizing a profit equal to the extra `asset_id` the victim was forced to pay above the pre-attack fair-market rate, minus swap fees/gas.

This reproduces the exact "spot-price-with-no-user-controlled-slippage" pattern from the referenced SafEth `rETH` finding, transplanted onto the polkadot-sdk asset-conversion fee-payment code path.
