Based on my investigation, I found a real analog: `process_delivery_receipt` in the Snowbridge Outbound Queue V2 pallet does not verify that the `receipt.success` flag is `true` before paying out the relayer reward, and does not use it at all when deciding whether to remove the pending order and pay the fee.

### Title
Outbound Queue V2 pays relayer reward and clears `PendingOrders` regardless of on-chain delivery `success` flag - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` that carries a `success: bool` field describing whether the message actually executed successfully on Ethereum, but the field is silently dropped: it is never read or passed into the reward/settlement logic that follows.

### Finding Description
`DeliveryReceipt` is decoded from the `InboundMessageDispatched` event log and explicitly carries a `success` flag alongside `nonce`, `topic`, and `reward_address`: [1](#0-0) 

`process_delivery_receipt` verifies the gateway and proof, fetches the `reward_account`, looks up the `PendingOrder` by `nonce`, and unconditionally pays the reward and removes the pending order — the decoded `receipt.success` value is never consulted: [2](#0-1) 

This is structurally the same bug class as the reported H-02: a value that exists specifically to gate downstream behavior (`_withdraw_only` in the AdapterVault report; `success` here) is computed/decoded but never threaded into the function that performs the sensitive state change (fee payout + order settlement). Any relayer who can produce a valid Merkle/receipt proof for *any* `InboundMessageDispatched` log — including one where `success = false` (i.e., the message reverted/failed execution on Ethereum) — still gets paid the full relayer fee and the `PendingOrder` is deleted as if delivery succeeded.

### Impact Explanation
This breaks the intended invariant that reward and settlement state must only advance after execution actually succeeds. A relayer can be paid the `order.fee` for messages that failed to execute on Ethereum, and the corresponding `PendingOrder` will be irrecoverably removed (`<PendingOrders<T>>::remove(nonce)`), preventing any future re-processing/re-delivery accounting for that nonce. This causes theft of relayer-reward funds and can permanently corrupt the delivery-accounting state for failed messages, which falls under "duplicate settlement or payout" / "theft or unbacked mint" impact categories.

### Likelihood Explanation
Likelihood is high: `submit_delivery_receipt` is a public, unprivileged extrinsic (`ensure_signed(origin)?` only) callable by anyone who has a valid proof for a Ethereum log — it does not need a malicious relayer/validator/governance actor, just a genuine but failed message execution log (which occurs during ordinary Ethereum-side failures, e.g., an XCM leg reverting on the destination). No existing guard (`ensure!` checks) references `success`, so the code path is reached unconditionally whenever `order.fee > 0`.

### Recommendation
Branch on `receipt.success` in `process_delivery_receipt`: only call `T::RewardPayment::register_reward` and remove/settle the `PendingOrder` when `receipt.success == true`. For `success == false`, either retain the order for retry/refund handling or apply an explicit failure-settlement path that does not release the reward fee to the submitting relayer.

### Proof of Concept
1. A message with `nonce = N` and non-zero `fee` is queued via `do_process_message`, creating `PendingOrders[N]`.
2. The message is relayed to Ethereum but execution fails there (e.g., destination XCM leg reverts), causing Ethereum to emit `InboundMessageDispatched(nonce=N, topic, success=false, reward_address=...)`.
3. Any account submits `submit_delivery_receipt` with a valid proof for that event log.
4. `T::Verifier::verify` succeeds (the log is genuine), `DeliveryReceipt::try_from` decodes `success: false` but `process_delivery_receipt` never checks it.
5. `order.fee > 0` is true, so `T::RewardPayment::register_reward` pays the full fee to `reward_account`, and `PendingOrders::remove(N)` deletes the order — as if the message had been delivered successfully. [3](#0-2)

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
