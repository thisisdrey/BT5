Target: `Contract::mt_resolve_transfer` early return `return amounts` when `self.accounts.get_mut(&receiver_id)` is `None` (contracts/defuse/src/contract/tokens/nep245/resolver.rs, receiver-lookup branch). Attacker withdraws to a `receiver_id` that has never been created as an account inside the Verifier (no `Account` state ever initialized), and the external MT contract's `mt_transfer_call` returns a promise result claiming a partial success (used amount less than debited). Preconditions: signer's own account debited `amount=100` prior to the outbound `mt_transfer_call`; `receiver_id` (the external contract) is not itself tracked in `self.accounts`. Call sequence: since `receiver_id` has no `Account`, `mt_resolve_transfer` returns the full original `amounts` (implying full 'used', zero refund) regardless of what the external call's promise result actually reported. Binding SETTLEMENT: `value debited from sender == value delivered to receiver_id (external) + value re-credited back to sender`, which here forces the entire debited amount to be treated as delivered with NO refund path, even if the external `mt_transfer_call` panicked. Scoped impact: Critical, funds permanently lost/frozen from the signer with no re-credit if the external MT contract predictably never gets an `Account` entry (e.g. an EOA/non-Verifier contract as receiver) and its `mt_transfer_call` fails. Proof idea: near-workspaces test withdrawing to a plain (non-Verifier-registered) receiver and asserting no silent full-debit occurs without genuine on-chain delivery.
