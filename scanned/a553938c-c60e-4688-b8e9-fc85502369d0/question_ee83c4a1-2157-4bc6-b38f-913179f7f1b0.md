Preconditions: `receiver_id` matches the deterministic account derivable from `malicious_state_init` and does not yet exist; signer balance >= N. Call sequence: `Transfer::execute_intent` synchronously credits `receiver_id` (not-yet-existing account) inside the ledger via `internal_add_balance`, then schedules `notify_on_transfer` which builds `Promise::new(receiver_id).state_init(state_init, NearToken::ZERO)` and calls `mt_on_transfer`; the freshly deployed contract's `mt_on_transfer` re-enters `execute_intents`, spending the just-credited ledger balance for `receiver_id` before any subsequent intents in the SAME `DefuseIntents` batch (fired concurrently per the target's own description) execute against the same account. Binding: the set of balance changes committed for `receiver_id` == the set the one signed `DefuseIntents` authorises; a re-entrant spend from the state_init'd contract mid-batch breaks this for other intents in the batch still pending against `receiver_id`. Impact: Critical, other queued intents in the same batch see mutated (already-spent) state, letting the attacker's deployed contract front-run same-batch balance movement.
