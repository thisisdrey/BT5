# [M] GMXC-5 | Blacklisted Callee Incorrectly Reset

## Summary
Severity: Medium
Contest weight: 0.0442
Dataset id: 125
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability is an incorrect state‑reset order in the closeOrder function of the GMX V2 contract. When a user closes an order the contract first overwrites the stored order address with the zero address, and only afterwards attempts to clear the corresponding entry in the blacklistedCallees mapping by setting it to false. Because the order address has already been set to 0x0, the contract writes the false flag to the mapping key 0x0 instead of the original callee address. As a result the original callee remains marked as blacklisted. The root cause is the improper sequencing of state updates: the dependent mapping is updated after the primary reference is cleared, causing a mismatch between the key used and the intended target. An attacker or a malformed user interaction can exploit this by triggering closeOrder on an order that had a blacklisted callee; the blacklisting flag will persist and subsequent contract calls that check the blacklistedCallees mapping will incorrectly reject legitimate actions. The impact is a denial‑of‑service condition for the affected user and potentially for the protocol, as the user may be unable to open new positions or execute withdrawals due to a stale blacklist entry. This condition occurs whenever closeOrder is invoked on an order whose callee was previously blacklisted; it does not depend on external parameters beyond the presence of a blacklisted entry. All users of the protocol who rely on order closure are affected, as are any downstream contracts that respect the blacklist flag. The issue was discovered during a manual audit that inspected state‑transition logic and identified that the mapping update used a variable that had already been overwritten. It is subtle because the contract does not emit an event when the mapping is cleared, and the false value is written to the zero address, which is a no‑op in the context of the mapping, making the bug invisible in normal execution traces. To remediate, the contract should clear the blacklistedCallees entry before resetting the order address, or store the original callee address in a temporary variable and use that to update the mapping. Conceptually, the fix is to ensure that any auxiliary state that depends on a primary reference is updated while the reference still holds the correct key. From the user’s perspective the UI may report that the order was closed successfully, yet later attempts to place a new trade or withdraw funds fail with a generic “callee is blacklisted” error, which contradicts the expectation that closing the order also removes the blacklist. This mismatch between expected behavior (blacklist cleared) and actual behavior (blacklist persists) breaks the accounting assumptions of the protocol and leads to funds that appear to be locked or unavailable.

## Recommendation
Update the blacklistedCallees mapping before zeroing out the user’s order.
