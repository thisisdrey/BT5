In `contracts/defuse/core/src/intents/token_diff.rs::TokenDiff::execute_intent`, fees are computed as `Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount)` and added to `fees_collected`, then `engine.state.internal_add_balance(engine.state.fee_collector().into_owned(), fees_collected)`. Can an attacker who signs many small `TokenDiff` intents each with `delta` just below the rounding threshold of `fee_ceil` (ceiling division) cause the SUM of `fee_ceil` per-intent fees collected across a batch to be LESS than `fee_ceil` would compute if the same total delta were submitted as ONE intent, letting the attacker split a large trade into many small `TokenDiff` intents within one `MultiPayload` (or across many batches with the same nonce-window) to systematically under-pay protocol fees relative to `engine.state.fee()`? Attacker action: submit N `TokenDiff` intents each with `delta = -1` (unsigned_abs=1) on `TokenIdType::Nep141` at `Pips::ONE_BIP` fee, where `fee_ceil(1)` rounds up to at least 1 unit fee per intent (if fee representable), versus one `TokenDiff` with `delta = -N` where `fee_ceil(N)` could be less than `N * fee_ceil(1)` due to ceiling-per-call vs ceiling-once. Preconditions: attacker has balance >= N, `protocol_fee = Pips::ONE_BIP` (or any nonzero fee), signs N separate `TokenDiff` intents batched in one `execute_intents` call. Call sequence: `execute_intents` -> N x `TokenDiff::execute_intent` -> each independently calls `Self::token_fee(...).fee_ceil(amount)` -> `internal_add_balance(fee_collector, ...)`. Binding broken: FEES - fees credited to `fee_collector` == fees the executed deltas owed (computed once over the true aggregate amount, not the sum of independently-ceiled small amounts) -- verify whether splitting increases or decreases total fee owed and whether the protocol systematically OVER-collects (each split rounds up) which is not a vulnerability, versus whether some ordering could cause UNDER-collection. Scoped impact: Critical only if attacker can make aggregate `fees_collected` < what a single equivalent `TokenDiff` would owe (fee bypass); if splitting only ever increases total fee (since ceiling per call rounds up each time), this is not exploitable and question should confirm the equality holds. Scoped funds: `fee_collector`'s expected revenue vs actual. Proof idea: cargo test in `contracts/defuse/core/src/intents/token_diff.rs` comparing `fee_ceil` applied once to amount=N vs N times to amount=1 each, asserting `N * fee_ceil(1, fee) >= fee_ceil(N, fee)` always holds (proving no under-collection) or finding a fee/amount combination where it's reversed.
