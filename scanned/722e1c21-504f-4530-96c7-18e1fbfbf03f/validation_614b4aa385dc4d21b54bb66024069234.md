### Title
Same-block AMM reserve manipulation lets a signed account underpay transaction fees via `SwapAssetAdapter`/`AssetConversionAdapter` - (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

### Summary
`pallet-asset-conversion-tx-payment`'s `SwapAssetAdapter::withdraw_fee` prices the fee-asset amount to withdraw purely from the live spot reserves of the on-chain AMM pool (`pallet-asset-conversion`), with no oracle, TWAP, or slippage/price bound. Because the AMM's reserves can be moved arbitrarily within the same block by ordinary, unprivileged extrinsics, an attacker can mint themselves an artificially cheap fee quote and later reverse the trade, extracting value from the pool/treasury — the same broken invariant as the referenced `VaderPoolV2` bug (spot-reserve price used for value-critical accounting, manipulable via same-block trades).

### Finding Description
`SwapAssetAdapter::withdraw_fee` computes the amount of `asset_id` a user must pay for a fee quoted in the native asset `A` by calling: [1](#0-0) 

i.e. `S::quote_price_tokens_for_exact_tokens(asset_id, A::get(), fee, true)`, which is a direct call into `pallet_asset_conversion::Pallet::quote_price_tokens_for_exact_tokens`. That function reads the pool's live reserves and applies the constant-product formula with no external price reference: [2](#0-1) 

The reserves it reads come straight from `get_reserves`, which is just the current pool account balances: [3](#0-2) 

Any signed account can move those reserves arbitrarily via ordinary `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` calls — no flashloan primitive is even required, since Substrate blocks execute several extrinsics from the same account sequentially with no atomicity barrier between them. An attacker can, within one block:
1. Submit a large swap that skews the `asset_id`/native pool so that `asset_id` is priced far above its real market value relative to native `A`.
2. Submit the fee-paying extrinsic with `asset_id` selected as the fee asset; `ChargeAssetTxPayment::prepare` calls `withdraw_fee`, which quotes and withdraws only a small amount of the now-inflated `asset_id` to cover the native fee, then executes `swap_tokens_for_exact_tokens` against the same skewed pool to extract the native fee amount from the pool: [4](#0-3) 

3. Submit a third extrinsic reversing the initial skewing swap, restoring the pool to its original state and recovering the capital used to move the price.

The net effect: the attacker pays a real fee in `asset_id` that is far below its true market value, extracted from the pool (and ultimately from the pool's other liquidity providers / the chain's fee recipient `OU`), while the "cost" of the fee-asset the attacker actually surrenders is economically worthless (or negligible) once the skew is reversed. This is structurally identical to VaderPoolV2's `mintSynth`/burn exploit: a value-critical accounting step (fee pricing) is tied 1:1 to a manipulable spot AMM price with no time-weighting or bound.

### Impact Explanation
`SwapAssetAdapter` (aliased `AssetConversionAdapter` in earlier versions) is wired into live production runtimes as `pallet_asset_conversion_tx_payment::Config::OnChargeAssetTransaction`, including `asset-hub-westend` and `asset-hub-rococo` (confirmed via direct references to `SwapAssetAdapter`/`OnChargeAssetTransaction` in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs` and `asset-hub-rococo/src/lib.rs`), as well as `substrate/bin/node/runtime/src/lib.rs`. This maps to the "public underpriced work that degrades block production" category: the chain accepts extrinsics while being paid systematically less than the intended native-equivalent fee, and the shortfall is siphoned from the AMM pool's liquidity providers (theft/unbacked value extraction), i.e. it also reaches "theft or unbacked mint or unlock" territory since real value leaves the pool without a corresponding real payment.

### Likelihood Explanation
No privileged actor, validator/collator collusion, or malicious relayer is required — only an ordinary signed account submitting three ordinary extrinsics that a normal transaction-pool/block-builder will happily sequence together (same sender, increasing nonce, all individually valid). Extremely shallow pools (e.g., newly created or low-liquidity fee-asset pools) make the skew cheap; the profitability scales with pool depth versus the fee amount extracted, exactly mirroring the flashloan/sandwich economics in the source report.

### Recommendation
Do not use raw, single-block AMM spot reserves as the sole price source for fee-asset conversion. Options: (1) bound the swap by a caller-approved `asset_fee` maximum (already partly enabled via `can_withdraw_fee`, but with no cross-block replay/slippage protection at the point of `withdraw_fee`), (2) use a time-weighted or multi-block average price for `quote_price_tokens_for_exact_tokens` when used for fee purposes, or (3) cap the fraction of pool reserves that a single fee-conversion swap may consume, rejecting fee-asset swaps that would move the pool price beyond a configured tolerance within the block.

### Proof of Concept
Conceptual sequence (single block, one signer, no special privileges):
1. Attacker holds `asset_id = X` and a chain configured with `OnChargeAssetTransaction = SwapAssetAdapter<Native, Fungibles, AssetConversion, OU>` (as in `asset-hub-westend`/`asset-hub-rococo`).
2. Tx1: `pallet_asset_conversion::swap_exact_tokens_for_tokens([Native, X], large_native_amount, ...)` — dumps native asset into the `Native/X` pool, sharply inflating the price of `X` in terms of `Native` (per `get_amount_out` in `substrate/frame/asset-conversion/src/lib.rs:1388-1419`).
3. Tx2: Any call wrapped in `ChargeAssetTxPayment { tip, asset_id: Some(X) }`. `withdraw_fee` (payment.rs:119-176) calls `quote_price_tokens_for_exact_tokens(X, Native, fee, true)` against the now-skewed reserves, withdraws a tiny `asset_fee` of `X` from the attacker, and performs `swap_tokens_for_exact_tokens([X, Native], asset_fee_credit, fee)` pulling `fee` (real native value) out of the pool for a near-worthless amount of `X`.
4. Tx3: `swap_exact_tokens_for_tokens([X, Native], ...)` reverses Tx1, restoring the pool and recovering the attacker's capital, minus swap fees.
Net result: attacker pays negligible real value for a transaction fee that is fully honored in native terms, with the difference extracted from the pool's liquidity providers — an unbacked value transfer analogous to the `VaderPoolV2` synth-mint drain.

	fn withdraw_fee(
		who: &T::AccountId,
		_call: &T::RuntimeCall,
		_dispatch_info: &DispatchInfoOf<<T>::RuntimeCall>,
		asset_id: Self::AssetId,
		fee: Self::Balance,
		_tip: Self::Balance,
	) -> Result<Self::LiquidityInfo, TransactionValidityError> {
		if asset_id == A::get() {
			// The `asset_id` is the target asset, we do not need to swap.
			let fee_credit = F::withdraw(
				asset_id.clone(),
				who,
				fee,
				Precision::Exact,
				Preservation::Preserve,
				Fortitude::Polite,
			)
			.map_err(|_| InvalidTransaction::Payment)?;

			return Ok((fee_credit, fee));
		}

		// Quote the amount of the `asset_id` needed to pay the fee in the asset `A`.
		let asset_fee =
			S::quote_price_tokens_for_exact_tokens(asset_id.clone(), A::get(), fee, true)
				.filter(|asset_fee| !asset_fee.is_zero())
				.ok_or(InvalidTransaction::Payment)?;

		// Withdraw the `asset_id` credit for the swap.
		let asset_fee_credit = F::withdraw(
			asset_id.clone(),
			who,
			asset_fee,
			Precision::Exact,
			Preservation::Preserve,
			Fortitude::Polite,
		)
		.map_err(|_| InvalidTransaction::Payment)?;

		let (fee_credit, change) = match S::swap_tokens_for_exact_tokens(
			vec![asset_id, A::get()],
			asset_fee_credit,
			fee,
		) {
			Ok((fee_credit, change)) => (fee_credit, change),
			Err((credit_in, _)) => {
				defensive!("Fee swap should pass for the quoted amount");
				let _ = F::resolve(who, credit_in).defensive_proof("Should resolve the credit");
				return Err(InvalidTransaction::Payment.into());
			},
		};

		// Since the exact price for `fee` has been quoted, the change should be zero.
		ensure!(change.peek().is_zero(), InvalidTransaction::Payment);

		Ok((fee_credit, asset_fee))
	}

		pub fn quote_price_tokens_for_exact_tokens(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount: T::Balance,
			include_fee: bool,
		) -> Option<T::Balance> {
			// Swaps reject zero amounts, match that behavior.
			if amount.is_zero() {
				return None;
			}
			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2).ok()?;

			let (balance1, balance2) = Self::get_reserves(asset1.clone(), asset2.clone()).ok()?;

			if balance1.is_zero() {
				return None;
			}

			// Swap withdrawals from pools use `keep_alive=true` (Preserve). Use the same
			// preservation level to determine the actual withdrawable amount.
			let max_output =
				T::Assets::reducible_balance(asset2.clone(), &pool_account, Preserve, Polite);
			if amount > max_output {
				return None;
			}

			if include_fee {
				let fee = Self::pool_fee_for(&asset1, &asset2).ok()?;
				Self::get_amount_in(fee, &amount, &balance1, &balance2).ok()
			} else {
				Self::quote(&amount, &balance2, &balance1).ok()
			}
		}
