### Title
`process_delivery_receipt` ignores the on-chain `success` flag and always pays the relayer reward and clears the pending order - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
`DeliveryReceipt` decoded from Ethereum's `InboundMessageDispatched` event carries an explicit `success: bool` field, but `Pallet::process_delivery_receipt` never reads or checks it. Any relayer can submit a valid proof of the event log — even one reporting `success = false` — and still have the relayer reward paid and the `PendingOrders` entry for that nonce permanently removed, exactly mirroring the "call returns a result the caller trusts as success without checking it" pattern in the solmate report.

### Finding Description
The event schema in `bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs` is: [1](#0-0) 

`success` is faithfully decoded into `DeliveryReceipt.success`, but it is dropped on the floor. `submit_delivery_receipt` only verifies the log's inclusion/authenticity via `T::Verifier::verify`, decodes the receipt, and forwards it straight to `process_delivery_receipt`: [2](#0-1) 

`process_delivery_receipt` checks only the gateway address and the presence of a `PendingOrder` for the nonce — it never inspects `receipt.success` before paying the reward and clearing the order: [3](#0-2) 

This is the direct local analog of the solmate bug: in the report, a call that "returns success" is treated as proof the intended transfer happened, even though the actual condition of interest (real token movement) was never verified. Here, a verified-but-failed Ethereum event (`success = false`, meaning the Gateway's dispatch of the inbound command reverted) is treated identically to a verified-success event, because the code checks that the *event log exists and is authentic*, not that the *event says the delivery succeeded*. There is no separate rejection/refund/retry path keyed off `success == false`; the order is removed regardless.

### Impact Explanation
This breaks the required invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." Concretely:
- A relayer reward is paid for a message whose execution the relayer's own submitted proof states failed (`success=false`) — this is an unbacked/incorrect payout, i.e. theft of protocol funds by a relayer who did no useful work (or whose delivery failed for any reason on the Ethereum side).
- `PendingOrders::remove(nonce)` deletes the bookkeeping entry once a `success=false` receipt is processed, so there is no way to later retry or re-settle that nonce — this is a permanent state loss/incorrect settlement for that bridge message, since the pallet has no other mechanism tracking failed dispatches once the order is removed.
- Because settlement is final and duplicate-safe only with respect to the *nonce*, not the *success* flag, this allows guaranteed reward extraction independent of actual delivery outcome — an unprivileged relayer (no admin/governance/validator access needed) can trigger this by simply waiting for (or engineering, if the Gateway ever legitimately reverts) a failed dispatch on Ethereum and then submitting the receipt as usual through the public `submit_delivery_receipt` extrinsic.

### Likelihood Explanation
`submit_delivery_receipt` is a public, unprivileged, signed extrinsic; any account can call it once it has a valid Ethereum receipt proof. Nothing about the light-client `Verifier` or origin checks constrains this — `Verifier::verify` only attests the log is real and included in a finalized Ethereum block, it does not (and cannot) know the semantic content of the log. The `success` boolean is legitimately produced by the Ethereum Gateway itself whenever a genuine inbound-command dispatch fails on-chain (e.g., insufficient gas provided by the relayer, a reverting downstream call, etc.), so `success=false` receipts are an expected, reachable code path in normal operation — not a contrived edge case requiring a malicious peer/validator/prover.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`:
- If `true`: keep current behavior (pay reward, remove order).
- If `false`: do not pay the relayer reward for that nonce (or pay a strictly reduced/no fee), and either keep the order for retry, or transition it to an explicit "failed" state/event (e.g. emit `Event::MessageDeliveryFailed { nonce }`) instead of `MessageDelivered`, so the failure is auditable and the settlement bookkeeping isn't silently finalized as if it succeeded.

### Proof of Concept
1. A message is enqueued and gets a `PendingOrder { nonce, fee, .. }` via `do_process_message`.
2. The message is relayed to the Ethereum Gateway; suppose dispatch of the underlying command reverts/fails there, so the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a valid inclusion proof for this log (it's a real, finalized event) and calls the public extrinsic `submit_delivery_receipt(event)`.
4. `T::Verifier::verify` succeeds (the log is genuine and included). `DeliveryReceipt::try_from` decodes `success = false` correctly.
5. `process_delivery_receipt` is invoked: gateway check passes, `PendingOrders::get(nonce)` returns `Some(order)`, `order.fee > 0` so `T::RewardPayment::register_reward(..)` is called unconditionally, and `PendingOrders::remove(nonce)` deletes the order — despite `receipt.success == false` never being consulted.
6. Result: the relayer is rewarded and the pending order permanently vanishes even though the receipt itself states the delivery failed. [3](#0-2) [1](#0-0)

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
