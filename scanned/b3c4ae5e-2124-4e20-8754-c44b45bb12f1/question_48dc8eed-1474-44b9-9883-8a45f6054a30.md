`CachedState::balance_of` (cached.rs:99-105) reads `account.token_amounts.get(token_id).copied()` from the cache OR falls back to `self.view.balance_of` only if the cache has no entry for that exact `TokenId` — meaning once ANY amount (even zero after a net-zero sequence of add/sub) is cached for a `TokenId`, `view.balance_of` is never consulted again within that `CachedState`'s lifetime. Attacker triggers, within one batch, a credit then an equal debit of a `TokenId` (net zero) followed by an intent that reads `balance_of` expecting it to reflect any OUT-OF-BAND on-chain change to that same account/token that occurred via a concurrent NEP-141 `ft_on_transfer` callback landing mid-flight (cross-contract call reentrancy). Precondition: attacker deploys a malicious FT contract used as the `TokenId`'s underlying asset, whose `ft_transfer`/withdraw promise re-enters the Verifier via `ft_on_transfer` before `finalize()`. Call sequence: initial `internal_add_balance` seeds cache from stale `view.balance_of`; reentrant deposit lands on-chain but is invisible to the already-cached entry; subsequent `balance_of` calls in the same `CachedState` return the stale cached figure. Binding: `CachedState::balance_of(owner_id, token_id)` at any point in a batch == `view.balance_of(owner_id, token_id)` + all deltas validly applied so far in THIS batch, with no on-chain concurrent mutation able to desynchronize the two once a `TokenId` entry is seeded (there is no re-derivation point). Scoped impact: Critical, conservation violated across the call if a reentrant transfer lets the same underlying asset be counted both by the stale seed and the new reentrant credit.
