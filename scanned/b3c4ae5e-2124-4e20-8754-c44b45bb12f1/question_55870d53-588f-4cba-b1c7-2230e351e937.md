`CachedState::set_auth_by_predecessor_id` (cached.rs:346-360) XORs a `toggled` flag rather than storing an absolute enable/disable state, and `is_auth_by_predecessor_id_enabled` (cached.rs:113-121) computes `was_enabled ^ toggled`. Attacker signs a `MultiPayload` containing an intent that calls `set_auth_by_predecessor_id(account_id, enable=true)` TWICE within the same batch (e.g., via two sub-intents), each XOR-toggling the underlying flag. Precondition: `was_enabled` initially false on-chain for `account_id` (attacker's own account). Call sequence: call #1 flips `auth_by_predecessor_id_toggled` true (net-enabled per intent semantics); call #2, since `is_auth_by_predecessor_id_enabled` is now true, computes `toggle = true ^ true = false`, so the flag is left unchanged from call #1's effect — but the SECOND call's return value `was_enabled` (now true) misreports state to the caller if it relies on this for gating a subsequent same-batch `ft_withdraw` under `auth_by_predecessor_id`. Binding: the toggled state read by any downstream `auth_by_predecessor_id`-gated withdraw in this batch == the state that the LAST valid signed intent in the batch actually requested, no lost update from double-XOR collapsing two explicit 'enable' requests into a no-op. Scoped impact: High, an `auth_by_predecessor_id`-gated call proceeding against a toggle state the signer did not intend within the same batch. Proof idea: cargo test calling `set_auth_by_predecessor_id(true)` twice in sequence on a fresh `CachedState` and asserting `is_auth_by_predecessor_id_enabled` after both calls equals `true` (idempotent enable), not reverting to `false` via the XOR mechanics.
