In MultiTokenResolver::mt_resolve_transfer (contracts/defuse/src/contract/tokens/nep245/resolver.rs), refunds are computed from promise_result_checked_json_with_len::<Vec<U128>>(0, amounts.len()) and clamped via refund.0.min(amount.0).min(receiver_balance). Can a malicious mt_on_transfer receiver contract return a refund vector whose length exactly equals amounts.len() (passing the .filter check) but with refund values for a DIFFERENT set of token_ids than were actually sent (since the resolver zips token_ids with refunds positionally, not by content), letting the receiver claim near-zero refund on a token it actually rejected while claiming full refund on a token it fully consumed, thereby causing the sender to receive an inflated refund credit exceeding what the receiver's real remaining receiver_balance for that specific token justifies? Precondition: attacker deploys a receiver contract implementing mt_on_transfer that accepts token A fully (consuming it) and rejects token B fully, but returns refund=[0, B_amount] when actual semantics should be refund=[0,0]/[A_amount,0] mismatched from real balances, exploiting the receiver_balance clamp which is per-token-id but positionally matched to the WRONG token_id due to receiver contract lying about which failed. Binding: the token_id whose balance is refunded to previous_owner_id == the token_id the receiver contract actually failed to consume (IDENTITY). Impact: Critical if positional mismatch lets sender reclaim balance for a token receiver actually kept, effectively duplicating that token's balance across sender and receiver. Proof: cargo test with a stub MT receiver returning a refund array claiming full refund for token index 0 while consuming token 0 and rejecting token 1, asserting mt_resolve_transfer credits sender for token 0 (which was never sent back) if receiver_balance for token 0 on receiver's account happens to be nonzero from unrelated funds.
