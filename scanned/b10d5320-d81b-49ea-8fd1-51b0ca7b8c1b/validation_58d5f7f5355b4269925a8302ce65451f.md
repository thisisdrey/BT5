### Title
Snowbridge Inbound Queue V2 marks a message nonce as consumed before verifying successful processing, permanently locking failed messages - ([File: bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs])

### Summary
The bug pattern in the external report is: a state field that gates a resource (a cooldown/nonce) is unconditionally updated as if the underlying operation succeeded, even when it did not. The `CraftingSystem` contract stamped `lastCompletionTime` regardless of whether a craft actually completed. The same broken invariant exists in `Pallet::process_message` of `snowbridge-pallet-inbound-queue-v2`: the message `Nonce` is marked as "received"/consumed *before* the downstream `T::MessageProcessor::process_message` call is known to succeed. If that call fails, the extrinsic returns an error, but because FRAME dispatchables do not automatically roll back storage writes performed before the error (that is a documented pallet-author responsibility, not an engine guarantee), the `Nonce` write persists. The message becomes permanently unprocessable, matching the "permanent fund/bridge-state lock" impact class.

### Finding Description
In `process_message`: [1](#0-0) 

```rust
pub fn process_message(relayer: T::AccountId, message: Message) -> DispatchResult {
    ensure!(T::GatewayAddress::get() == message.gateway, Error::<T>::InvalidGateway);
    let (nonce, relayer_fee) = (message.nonce, message.relayer_fee);

    // Verify the message has not been processed

        .map_err(|e| match e { ... })?;

```

`Nonce::<T>::set(nonce)` is written *before* `T::MessageProcessor::process_message(...)` is attempted and its result checked. If `process_message` returns any of the `MessageProcessorError` variants (`ProcessMessage`, `ConvertMessage`, `SendMessage` — e.g. an XCM send failure, a message conversion failure, or a downstream weight/queue-congestion failure), the `?` propagates the error and `submit`/`process_message` returns `Err(...)`. There is no `#[transactional]` wrapper or `with_transaction` block around this function, so the `Nonce::<T>::set(nonce)` write is **not rolled back**: FRAME only automatically discards storage changes made during validation/prepare of transaction extensions, not arbitrary writes made inside a dispatchable's body before it returns an error (this is a widely documented FRAME footgun — pallet authors must order all `ensure!`/fallible calls before any storage mutation, which this function fails to do).

Because the nonce is now permanently marked as consumed (`Nonce::<T>::get(nonce) == true`), any subsequent retry of the exact same message (e.g., resubmission by another relayer after the transient failure condition clears) is rejected at the very first guard:

```rust
ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);
```

The message — and any associated Ethereum-side locked/burned funds represented by that nonce — can never be delivered or reprocessed on Polkadot side again.

### Impact Explanation
This is a public, unprivileged-reachable path (`submit` is callable by any signed relayer once they have a valid proof) that can permanently and irreversibly lock bridge state/funds for a legitimate cross-chain message, matching the in-scope "permanent user-fund or bridge-state lock" and "Snowbridge delivery flow" impact categories. No malicious relayer, validator, or governance actor is required — an ordinary transient failure in `T::MessageProcessor::process_message` (congested XCMP queue, temporary weight limit, conversion edge case) is sufficient to trigger permanent loss.

### Likelihood Explanation
Likelihood is moderate-to-high: any of the three `MessageProcessorError` variants naturally occurring during normal operation (bridge congestion, XCM version/weight issues, malformed-but-verification-passing asset/XCM payload) triggers the bug deterministically, with no attacker collusion needed. The `prdoc/stable2503-4/pr_8240.prdoc` note ("a minor change to when the nonce is set in the Inbound Queue V2") confirms the Snowbridge team had already identified nonce-ordering as an audit concern in this exact pallet, but the code in this repository still sets the nonce before process-success confirmation. [2](#0-1) 

### Recommendation
Only persist `Nonce::<T>::set(nonce)` after `T::MessageProcessor::process_message` has returned `Ok(..)`, mirroring the crafting-system fix ("only update the last completion time if at least one craft was completed successfully"). Concretely, reorder the code so the nonce write happens after the `?` on `process_message`, or wrap the whole function body in `with_transaction` and only commit on the success path so a downstream error cannot leave the nonce marked consumed.

### Proof of Concept
1. A relayer submits `submit(origin, event)` for message with `nonce = N`; `T::Verifier::verify` and the gateway/nonce checks pass.
2. `Nonce::<T>::set(N)` executes, marking nonce `N` consumed in storage.
3. `T::MessageProcessor::process_message` fails (e.g., `MessageProcessorError::SendMessage` due to a temporarily congested XCMP queue to the destination parachain), causing `process_message` to return `Err(...)`.
4. The extrinsic is reported as failed on-chain, but `Nonce::<N>` remains `true` because no rollback occurred.
5. Any later resubmission of the identical (still-valid) event/message for nonce `N` — even after the congestion clears — is rejected with `Error::<T>::InvalidNonce`, permanently orphaning the funds/message associated with that Ethereum-side nonce. [3](#0-2)

	impl<T: Config> Pallet<T> {
		pub fn process_message(relayer: T::AccountId, message: Message) -> DispatchResult {
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == message.gateway, Error::<T>::InvalidGateway);

			let (nonce, relayer_fee) = (message.nonce, message.relayer_fee);

			// Verify the message has not been processed
			ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);

			// Mark message as received
			Nonce::<T>::set(nonce);

			let message_id = T::MessageProcessor::process_message(relayer.clone(), message)
				.map_err(|e| match e {
					MessageProcessorError::ProcessMessage(e) => e,
					MessageProcessorError::ConvertMessage(e) => Error::<T>::from(e).into(),
					MessageProcessorError::SendMessage(e) => Error::<T>::from(e).into(),
				})?;

			// Pay relayer reward
			let tip = Tips::<T>::take(nonce).unwrap_or_default();
			let total_tip = relayer_fee.saturating_add(tip);
			if total_tip > 0 {
				T::RewardPayment::register_reward(&relayer, T::DefaultRewardKind::get(), total_tip);
			}

			// Emit event with the message_id
			Self::deposit_event(Event::MessageReceived { nonce, message_id });

			Ok(())
		}
