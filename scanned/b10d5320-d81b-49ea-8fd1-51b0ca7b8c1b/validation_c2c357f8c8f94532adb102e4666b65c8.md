### Title
A single message returning `ProcessMessageError::Yield` permanently blocks all subsequent messages queued behind it in the same origin's queue - ([File: substrate/frame/message-queue/src/lib.rs])

### Summary
The Augur bug is a Denial-of-Service where a single order that reverts on a mandatory step (the ERC777 `tokensReceived` hook) becomes permanently unfillable, and because orders must be filled strictly in price order, that one unfillable order blocks all orders behind it, letting an attacker halt or cap a market with a single crafted order. The Substrate `pallet-message-queue` has the same broken invariant: messages within a page/queue are serviced strictly in FIFO order, and a message that is reported as `Unprocessable { permanent: false }` (i.e. the processor returned `ProcessMessageError::Yield`) causes `service_page_item` to return `NoProgress`, which makes `service_page`/`service_queue` `break` out of the servicing loop for that queue *without advancing past the stuck message*. Every message enqueued after it in that page is therefore never touched, for as long as the stuck message keeps returning `Yield`.

### Finding Description
`process_message_payload` maps a processor error to a `MessageExecutionStatus`: [1](#0-0) 
Errors such as `BadFormat`, `Corrupt`, `Unsupported` are treated as permanent and the message is dropped/skipped, letting the queue continue. But `Yield` is explicitly `Unprocessable { permanent: false }`, meaning it must be retried indefinitely and never dropped: [2](#0-1) 

`service_page_item` converts this into `ItemExecutionStatus::NoProgress`: [3](#0-2) 

`service_page` treats `NoProgress` exactly like `Bailed` — it stops iterating the page and does **not** call `page.skip_first`, so the head of the page never advances past the offending message: [4](#0-3) 

`service_queue` then also breaks and does not advance `book_state.begin` to the next page: [5](#0-4) 

This is the same "unfillable order at the head of the book blocks everything behind it" pattern as the Augur report: the queue is strictly FIFO per origin, and a single message that the `MessageProcessor` cannot ever successfully process (but that keeps returning the *transient* `Yield` error rather than a *permanent* error) will forever occupy the head-of-queue position and prevent every later message in that page/origin from being serviced by `on_initialize`/`service_queues`. This exact class of bug was already observed in this codebase: `prdoc/1.12.0/pr_4202.prdoc` documents a related incident where "the MessageQueue can incorrectly assume that a message will permanently fail to process and disallow retrial of it," confirming this control-flow area is fragile and has previously produced live incidents: [6](#0-5) 

The consumer of `ProcessMessage` used for DMP/UMP/HRMP is the XCM executor via `ProcessXcmMessage` (in `xcm-builder`/`xcm-executor`), which is the `T::MessageProcessor` for the runtime's `MessageQueue` instance handling parachain-inbound messages. Any XCM instruction sequence that the executor classifies as "should be retried later" (`Yield`) rather than a hard `Unsupported`/`Corrupt` error becomes a durable, attacker-craftable blocker: because a normal user can trigger arbitrary XCM programs to be sent from/via a given origin (e.g. through XCM execution barriers, suspension logic, or content-dependent conditions that map to `Yield`), a message crafted to permanently hit that `Yield` branch will camp at the head of that origin's queue.

### Impact Explanation
This directly matches the "message queues ... must only advance after decode, dispatch, execution, and settlement succeed atomically" and "public underpriced work that degrades block production or stalls bridge processing" impact categories. A single crafted message from an unprivileged actor (anyone able to get a message routed through the affected origin's queue, e.g. a parachain's UMP/DMP/HRMP channel or any `EnqueueMessage` consumer) can permanently stall that queue's processing, denying service to every legitimate message queued after it — analogous to Augur's single unfillable order halting an entire market. Since MessageQueue underlies DMP/UMP/XCMP dispatch on Cumulus-based chains, this can stall bridge/parachain message processing broadly, not just a niche feature.

### Likelihood Explanation
Likelihood depends entirely on whether any reachable code path in the configured `T::MessageProcessor` (the XCM executor / barriers in `xcm-builder`) can be forced by attacker-controlled message content into returning `ProcessMessageError::Yield` *unconditionally and repeatedly* for the same message (rather than only transiently, e.g., due to weight availability which naturally resolves). This is plausible because `Yield` is explicitly documented as "a hint" that queue processing should retry later without any guarantee of eventual success, and the mechanism (`CheckSuspension`/barrier logic) is intentionally content- and state-dependent. The PR history (`pr_4202`) shows this exact "permanent vs transient" classification boundary has already caused a bug in production reasoning, underscoring that the boundary is easy to get wrong. Full confirmation requires enumerating every `ShouldExecute`/`CheckSuspension` implementation wired into a given runtime's `ProcessXcmMessage` to find one where attacker-controlled inputs alone (no privileged actor) can force permanent `Yield`.

### Recommendation
- Ensure the `MessageProcessor` never returns `ProcessMessageError::Yield` based purely on attacker-controlled message content in a way that can never resolve; any content-based rejection should map to a permanent error (`Unsupported`/`Corrupt`) so `service_page_item`/`service_page` can skip past it.
- Add a bounded retry counter or per-message "stuck" cutover in `pallet-message-queue` so a message that yields more than N times in a row is escalated to permanently unprocessable (with an event) instead of blocking the queue indefinitely, mirroring how `Overweight` already has a permanent/temporary split with a hard limit.
- Audit all `ShouldExecute`/`CheckSuspension`/barrier implementations feeding into `ProcessXcmMessage` to confirm no attacker-only-controlled condition can produce a permanent `Yield`.

### Proof of Concept
Conceptual reproduction using the pallet's own test harness pattern (as in `service_queues_failing_messages_works`):
1. Enqueue message A with content that a custom/real `MessageProcessor` is designed to interpret as "always `Yield`" (e.g., an XCM program crafted to always land in a suspension/backpressure branch that is—incorrectly—reachable indefinitely by the attacker) into origin `O`.
2. Enqueue legitimate messages B, C, D into the same origin `O` afterward.
3. Call `service_queues`/`on_initialize` repeatedly with ample weight.
4. Observe (as shown by the existing test `service_queues_failing_messages_works`, where the `"yield"` message is left un-skipped and the "last page with the `yield` stays in") that message A never leaves the page and B, C, D are never serviced: [7](#0-6) 

This test already demonstrates the mechanism in isolation (a `Yield` message freezes the page); the security question is only whether a real `MessageProcessor` (XCM executor) can be driven into unconditional, permanent `Yield` by an unprivileged sender — this last step needs runtime-specific configuration review to fully confirm exploitability end-to-end.

#[test]
fn service_queues_failing_messages_works() {
	use MessageOrigin::*;
	build_and_execute::<Test>(|| {
		set_weight("service_page_item", 1.into_weight());
		MessageQueue::enqueue_message(msg("badformat"), Here);
		MessageQueue::enqueue_message(msg("corrupt"), Here);
		MessageQueue::enqueue_message(msg("unsupported"), Here);
		MessageQueue::enqueue_message(msg("stacklimitreached"), Here);
		MessageQueue::enqueue_message(msg("yield"), Here);
		// Starts with four pages.
		assert_pages(&[0, 1, 2]);

		assert_eq!(MessageQueue::service_queues(1.into_weight()), 1.into_weight());
		assert_last_event::<Test>(
			Event::ProcessingFailed {
				id: blake2_256(b"badformat").into(),
				origin: MessageOrigin::Here,
				error: ProcessMessageError::BadFormat,
			}
			.into(),
		);
		assert_eq!(MessageQueue::service_queues(1.into_weight()), 1.into_weight());
		assert_last_event::<Test>(
			Event::ProcessingFailed {
				id: blake2_256(b"corrupt").into(),
				origin: MessageOrigin::Here,
				error: ProcessMessageError::Corrupt,
			}
			.into(),
		);
		assert_eq!(MessageQueue::service_queues(1.into_weight()), 1.into_weight());
		assert_last_event::<Test>(
			Event::ProcessingFailed {
				id: blake2_256(b"unsupported").into(),
				origin: MessageOrigin::Here,
				error: ProcessMessageError::Unsupported,
			}
			.into(),
		);
		assert_eq!(MessageQueue::service_queues(1.into_weight()), 1.into_weight());
		assert_eq!(System::events().len(), 4);
		// Last page with the `yield` stays in.
		assert_pages(&[2]);
	});
