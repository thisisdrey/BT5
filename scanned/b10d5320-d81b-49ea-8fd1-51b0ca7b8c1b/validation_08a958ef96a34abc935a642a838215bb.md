## Analysis

The Uniswap V2 report's core broken invariant is: **LP-share accounting assumes reserves only change through the pool's own liquidity-provisioning logic, but reserves can be inflated by a direct token donation to the pool's account, causing proportional LP minting to round in favor of the existing owner and against later depositors.**

The Polkadot SDK analog lives in `pallet-asset-conversion`, which implements the same constant-product/LP-share design (including its own `MintMinLiquidity` protection, the direct analog of Uniswap's `MINIMUM_LIQUIDITY`).

### Title
Reserve inflation via direct donation to the deterministic pool account lets an unprivileged user dilute later liquidity providers in `pallet-asset-conversion` - (`substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`do_add_liquidity` computes pool "reserves" by reading the live, full asset balance of the pool's sovereign account rather than an internally tracked, mint-controlled reserve value. Because the pool account address is deterministically derivable off-chain (`T::PoolLocator::address`), any unprivileged account can transfer tokens of either pair asset directly to that account (bypassing `add_liquidity` entirely). This inflates `reserve1`/`reserve2` without increasing LP `total_supply`, so a subsequent depositor's `lp_token_amount = min(amount1*total_supply/reserve1, amount2*total_supply/reserve2)` rounds down disproportionately, causing the depositor to transfer real tokens into the pool while receiving a minted LP share far below their proportional contribution.

### Finding Description
`do_add_liquidity` reads reserves as raw balances: [1](#0-0) 

then, once `total_supply` is non-zero, derives the LP mint amount purely from that manipulable ratio: [2](#0-1) 

`get_balance` and the view-function `get_reserves` both resolve to full account balances of the pool's sovereign account, confirmed by the `pr_12408` change that made this explicitly use **full** balances instead of reducible balances: [3](#0-2) 

The pool account is a deterministic `PalletId`-derived account (`T::PoolLocator::address`/`pool_address`), so an attacker can precompute it before or after pool creation and send tokens to it via ordinary `pallet_balances::transfer`/`pallet_assets::transfer`, entirely outside `pallet-asset-conversion`'s call surface. The pallet already anticipates a variant of this (see `cannot_block_pool_creation` and `add_tiny_liquidity_directly_to_pool_address` tests), but those only cover unrelated/non-pair assets or the very first liquidity add — not a `total_supply > 0` donation of pair assets: [4](#0-3) [5](#0-4) 

`MintMinLiquidity` only guards the **initial** mint (`total_supply.is_zero()` branch) and the final `ensure!(lp_token_amount > T::MintMinLiquidity::get())` check on the total mint result — it does not protect the ratio computation itself, so it does not stop a valid-but-heavily-diluted mint (e.g. `lp_token_amount == MintMinLiquidity + 1`) once `total_supply` is already positive: [6](#0-5) 

### Impact Explanation
This directly matches the "theft or unbacked mint" and "false state acceptance / wrong beneficiary or amount" impact classes: an unprivileged user's tokens are transferred into the pool (`T::Assets::transfer` at lines 855-856) while the LP tokens minted to them are computed against an attacker-inflated denominator, permanently transferring economic value to whoever already holds LP tokens in that pool (including the attacker if they had pre-existing minimal liquidity). No governance, admin, validator, or relayer role is involved — the whole attack is executable by a normal signed account using only public extrinsics/transfers.

### Likelihood Explanation
Likelihood is moderate-to-high in any low-total-supply pool: the pool address is computable without any privileged access, the donation transfer is a standard `transfer`/`transfer_allow_death` call, and the victim only needs to add liquidity using an on-chain/off-chain quoted price that does not account for a same-block donation. Pools with recently created but thin liquidity (e.g., freshly created via `create_pool` + a minimal `add_liquidity`) are the most exposed, similar to the original Uniswap first-depositor scenario.

### Recommendation
Track reserves internally (e.g., in `PoolInfo` or a dedicated reserve storage item) updated only by `do_add_liquidity`/`do_remove_liquidity`/swap logic, instead of trusting the pool account's live balance for LP-mint-ratio math; alternatively, bound the acceptable deviation between tracked and live balances, or require `add_liquidity` to "sync" using a governance/permissioned path only, never using raw balances for share-issuance math.

### Proof of Concept
1. User A creates pool `(asset1, asset2)` and adds minimal liquidity via `add_liquidity`, receiving `total_supply` slightly above `MintMinLiquidity` (e.g., 101 LP tokens as in `add_liquidity_works`-style tests).
2. Attacker computes the pool's sovereign account via `PoolLocator::address`/`pool_address` (public, deterministic) and sends a very large amount of `asset1` and `asset2` directly to that account using `pallet_assets::transfer`/`pallet_balances::transfer` (no interaction with `pallet-asset-conversion` needed).
3. Victim calls `add_liquidity` with a reasonable, price-quoted amount; `do_add_liquidity` transfers the victim's tokens into the now-inflated pool account (lines 855-856) and computes `lp_token_amount = min(side1, side2)` off the inflated `reserve1`/`reserve2` (lines 868-871), minting the victim only a tiny LP amount relative to their deposit.
4. Attacker (or User A, who effectively controls `total_supply`) can later call `remove_liquidity` to redeem a disproportionately large share of the pool's real assets, extracting the victim's deposited value.

#[test]
fn cannot_block_pool_creation() {
	new_test_ext().execute_with(|| {
		// User 1 is the pool creator
		let user = 1;
		// User 2 is the attacker
		let attacker = 2;

		let ed = get_native_ed();
		assert_ok!(Balances::force_set_balance(RuntimeOrigin::root(), attacker, 10000 + ed));

		// The target pool the user wants to create is Native <=> WithId(2)
		let token_1 = NativeOrWithId::Native;
		let token_2 = NativeOrWithId::WithId(2);

		// Attacker computes the still non-existing pool account for the target pair
		let pool_account =
			<Test as Config>::PoolLocator::address(&(token_1.clone(), token_2.clone())).unwrap();
		// And transfers the ED to that pool account
		assert_ok!(Balances::transfer_allow_death(
			RuntimeOrigin::signed(attacker),
			pool_account,
			ed
		));
		// Then, the attacker creates 14 tokens and sends one of each to the pool account
		for i in 10..25 {
			create_tokens(attacker, vec![NativeOrWithId::WithId(i)]);
			assert_ok!(Assets::mint(RuntimeOrigin::signed(attacker), i, attacker, 1000));
			assert_ok!(Assets::transfer(RuntimeOrigin::signed(attacker), i, pool_account, 1));
		}

		// User can still create the pool
		create_tokens(user, vec![token_2.clone()]);
		assert_ok!(AssetConversion::create_pool(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone())
		));

		// User has to transfer one WithId(2) token to the pool account (otherwise add_liquidity
		// will fail with `AssetTwoDepositDidNotMeetMinimum`)
		assert_ok!(Balances::force_set_balance(RuntimeOrigin::root(), user, 10000 + ed));
		assert_ok!(Assets::mint(RuntimeOrigin::signed(user), 2, user, 10000));
		assert_ok!(Assets::transfer(RuntimeOrigin::signed(user), 2, pool_account, 1));

		// add_liquidity shouldn't fail because of the number of consumers
		assert_ok!(AssetConversion::add_liquidity(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone()),
			10000,
			100,
			10000,
			10,
			user,
		));
	});
}
