## Title
Delivery-fee-factor compounds per-message-count rather than per-byte, letting a low-cost attacker exponentially inflate XCM/DMP delivery fees for all other users - (File: `cumulus/pallets/xcmp-queue/src/lib.rs`, `polkadot/runtime/parachains/src/lib.rs`, `polkadot/runtime/parachains/src/dmp.rs`)

## Summary
The XCMP/DMP delivery-fee mechanism multiplies a shared, per-destination `DeliveryFeeFactor` by a constant `EXPONENTIAL_FEE_BASE` (1.05) **every time** an outbound message causes the channel to be over a byte-size threshold, regardless of how large that individual message actually is. Any unprivileged account that can send XCM (e.g. via `pallet_xcm::send`) can split what would be one moderately sized message into many minimal messages. Each tiny message independently re-triggers the multiplicative update, so `N` small messages compound the factor to `≈1.05^N`, dramatically more than the single multiplication `≈1.05` that an equivalent-size single message would cause. This inflates the delivery fee paid by every other, legitimate sender to that destination — the same "repeated-small-action compounds a shared rate faster than an equivalent single large action" pattern as the LoopFi interest-rate report, but here it corrupts a public/shared fee state rather than a private debt.

## Finding Description
The compounding logic lives in the shared `FeeTracker` trait: [1](#0-0) 

```rust
fn do_increase_fee_factor(fee_factor: &mut FixedU128, message_size: u128) {
    let message_size_factor = FixedU128::from(message_size.saturating_div(1024))
        .saturating_mul(Self::MESSAGE_SIZE_FEE_BASE);
    *fee_factor = fee_factor
        .saturating_mul(Self::EXPONENTIAL_FEE_BASE.saturating_add(message_size_factor));
}
```

`EXPONENTIAL_FEE_BASE` is a fixed constant (1.05) applied on *every call*, independent of message size; `message_size_factor` is a small size-proportional addend (only ~0.001 per KB). For any message under 1KB, `message_size_factor` rounds to (near) zero, so the multiplier collapses to essentially the fixed `1.05` per call.

This is invoked from the XCMP outbound path on every send that keeps the channel over threshold: [2](#0-1) 

```rust
let threshold = channel_info.max_total_size / delivery_fee_constants::THRESHOLD_FACTOR;
if channel_details.queued_bytes > threshold {
    Self::increase_fee_factor(recipient, encoded_fragment_len as u128);
}
```

and from the DMP path identically: [3](#0-2) 

```rust
let threshold =
    Self::dmq_max_length(config.max_downward_message_size).saturating_div(THRESHOLD_FACTOR);
if q_len > threshold as u64 {
    Self::increase_fee_factor(para, serialized_len as u128);
}
```

`send_fragment` is reachable by any unprivileged account through `pallet_xcm::send`/`SendXcm`, since `XcmpQueue` implements `SendXcm` and is exercised by ordinary `send_xcm` calls, as shown in the pallet's own test: [4](#0-3) 

```rust
let smaller_xcm = Xcm(vec![ClearOrigin; 30]);
// When we get to half of `max_total_size`, because `THRESHOLD_FACTOR` is 2,
// then the fee factor starts to increase.
assert_ok!(send_xcm::<XcmpQueue>(destination.clone(), xcm.clone())); // Size 520
assert_eq!(DeliveryFeeFactor::<Test>::get(sibling_para_id), FixedU128::from_float(1.05));

for _ in 0..12 {
    // We finish at size 929
    assert_ok!(send_xcm::<XcmpQueue>(destination.clone(), smaller_xcm.clone()));
}
assert!(DeliveryFeeFactor::<Test>::get(sibling_para_id) > FixedU128::from_float(1.88));
```

This confirms the exact primitive: the pallet's own test shows that 12 small (30-byte) messages compound the factor from 1.05 to >1.88 — an ~80% jump attributable purely to *call count*, not to bytes actually enqueued (only ~409 additional bytes were queued in total). A single message carrying the same ~409 bytes would have triggered `do_increase_fee_factor` once, producing only the base `1.05` multiplication (plus a negligible size term). The `DeliveryFeeFactor::<T>` storage value (`cumulus/pallets/xcmp-queue`) / `DeliveryFeeFactor::<T>` (`polkadot/runtime/parachains::dmp`) is the corrupted shared value: it is read by `ExponentialPrice::price_for_delivery` to charge **every subsequent sender** to that destination, so this is not a self-inflicted cost like in LoopFi — it is a public, shared parameter whose inflation directly taxes all unrelated users routing through the same channel/para.

No existing guard prevents this: the threshold check is a boolean "is the channel currently over the threshold" gate evaluated independently on every `send_fragment`/`queue_downward_message` call, with no normalization by elapsed time, message count, or marginal bytes contributed. Nothing throttles how many small messages a single account can send in a block/relay-parent to keep re-triggering the multiplier (limited only by ordinary transaction fees for `pallet_xcm::send`, which are cheap relative to the fee inflation inflicted on the shared channel).

## Impact Explanation
This falls squarely within "public underpriced work that degrades block production or stalls bridge/message processing": an attacker pays only for cheap, tiny XCM sends, yet the resulting delivery-fee-factor increase is borne by every other account that subsequently sends XCM to the same parachain/downward-message-queue destination. Sustained abuse can push delivery fees to levels that price out legitimate cross-chain messages, degrading XCMP/DMP throughput and effectively griefing a specific parachain's message channel — a chain-wide/bridge-processing availability impact, not merely a private financial loss to the attacker.

## Likelihood Explanation
The path requires only an ordinary signed account able to call `pallet_xcm::send` (or any pallet built on `SendXcm`) targeting a live XCMP or DMP channel that is already moderately loaded (over `THRESHOLD_FACTOR`-derived threshold, which for HRMP defaults to half of `max_total_size`/`max_capacity` — realistic under normal network activity or with modest attacker-induced padding). No governance, validator, relayer, or leaked-key assumptions are needed; the pallet's own test suite demonstrates the exact amplification with a dozen small sends.

## Recommendation
Base the multiplicative fee-factor update on the actual marginal bytes/queue-depth contributed since the last update rather than applying a fixed `EXPONENTIAL_FEE_BASE` per call. For example, scale the exponent by `bytes_added / threshold_unit` (continuous accrual proportional to congestion contributed) instead of a constant per-invocation multiplier, so that splitting one message into many small ones yields the same total fee-factor growth as sending it as a single message of equivalent size.

## Proof of Concept
Using the existing pallet test harness (`cumulus/pallets/xcmp-queue/src/tests.rs::verify_fee_factor_increase_and_decrease`) as the base:
1. Open an HRMP channel with `max_total_size = 1000`, `THRESHOLD_FACTOR = 2` (threshold = 500).
2. Push the channel to just over 500 bytes with a few normal-size messages (factor stays at `MIN_FEE_FACTOR`).
3. As the attacker, call `send_xcm::<XcmpQueue>` repeatedly with minimal `smaller_xcm` (30-byte) messages, each individually cheap and each keeping `queued_bytes > threshold`.
4. Observe `DeliveryFeeFactor::<Test>::get(sibling_para_id)` after 12 such sends rise from `1.05` to `>1.88`, versus the `~1.05` that a single message of the same aggregate size increment would have produced — demonstrated directly in the existing test assertions at [5](#0-4) .
5. Any third-party account calling `validate_send::<XcmpQueue>` for the same destination now pays a delivery fee amplified by the attacker's message-count (not byte-volume) manipulation.
