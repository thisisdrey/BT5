Target: `RequestMessage::hash()` used in `execute_signed` (`let hash = msg.hash(); WalletEvent::SignedRequest{hash}`) versus `SignatureSchema::verify_request_msg(public_key, msg, proof)`. Attacker action: attacker re-encodes a captured `RequestMessage` by adding/reordering an untyped extra JSON field or altering `pay_for_gas` default-skipped field (`#[serde(default, skip_serializing_if = "Not::not")]`) so that the borsh/JSON bytes hashed by the client signer differ from what `w_execute_signed` deserializes, while `S::verify_request_msg` still returns true because it re-serializes canonically rather than checking raw bytes. Preconditions: owner signed a benign `Request` (e.g. empty `external`); attacker controls the relayer submission bytes. Call sequence: relayer submits mutated `msg` + original `proof` to `w_execute_signed`->`S::verify_request_msg` passes on the mutated struct because verification recomputes canonical bytes from the *mutated* struct fields, not the originally signed bytes. Binding: the `Request` executed == the exact `Request` the owner's signature covers, field-for-field. Impact: Critical - a re-encoded `Request` (e.g. with injected `external` promise) executes and moves funds/state the owner never signed for. Proof idea: unit test constructing two `RequestMessage`s differing only in a normally-insignificant field, verify signature acceptance for both against one signature, and assert only the originally-signed struct is accepted.
