Target: `WalletImpl::resolve_auth` / `AuthorizationResolution` (`contracts/wallet/src/contract.rs:347-408`, NEP-641). Attacker action: attacker crafts an off-chain `WalletAuthorization::Signature{msg: OffchainMessage{signer_id: OTHER_WALLET.near, chain_id, path:[], timestamp, payload:"transfer_all"}, proof}` signed with the ATTACKER's own key (a valid signature under attacker's own wallet schema) but submits it as the `authorization` argument to `victim_wallet.near::w_resolve_auth(path=[], authorization)` expecting the resolver to accept `msg.payload` since `msg.signer_id` is only compared against `env::current_account_id()` of whichever contract is queried, not against the caller's actual signing key ownership. Preconditions: an off-chain settling party (not DAO) trusts `w_resolve_auth`'s returned `AuthorizationResolution.payload` as authorization to move Verifier assets. Call sequence: `w_resolve_auth`->`resolve_auth`->checks `msg.signer_id != env::current_account_id()`, `msg.path != path`, `S::verify_offchain_msg(public_key,...)`. Binding: `AuthorizationResolution.payload` accepted == a payload actually signed by the `public_key` stored in *this* `env::current_account_id()`'s state, for exactly this `signer_id`/`path`. Impact: Critical - if `verify_offchain_msg` is checked against `self.0.public_key` (the queried wallet's own key) this holds; the exploitable variant is calling `w_resolve_auth` on `victim_wallet.near` with a message whose `signer_id` field equals `victim_wallet.near` but which the attacker never actually got signed by `victim_wallet.near`'s real key - verify that `verify_offchain_msg` truly binds to `self.0.public_key` and rejects. Proof idea: unit test calling `resolve_auth` with a `msg.signer_id` matching `current_account_id()` but a `proof` produced by a different keypair, asserting `Error::InvalidSignature`.
