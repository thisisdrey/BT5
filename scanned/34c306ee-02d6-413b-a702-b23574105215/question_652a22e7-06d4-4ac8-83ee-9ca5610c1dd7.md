Target: `WalletImpl::execute_signed`, `msg.created_at`/`msg.timeout` vs `Nonces::commit`'s window check (`contracts/wallet/src/nonces.rs:120-133`): `now - self.timeout.min(timeout) <= created_at <= now`. Attacker action: attacker (permissionless relayer) captures a validly-signed `msg` with `timeout = u32::MAX seconds` (owner mistakenly or maliciously set an enormous per-message timeout) and `created_at` far in the past, then submits it long after the owner intended it to expire, relying on `self.timeout.min(timeout)` picking the WALLET's fixed, possibly-long `wallet.timeout` (e.g. `DEFAULT_TIMEOUT=1h`) as the effective window rather than the message's stricter intent. Preconditions: wallet's own `nonces.timeout()` (`w_timeout_secs`) is at its default 1h; owner signed thinking a short-lived nonce would expire quickly but `timeout` field only shrinks, never extends beyond `wallet.timeout`, so this is fine in normal cases — the exploit angle is when the owner's `msg.timeout` is smaller than intended due to client bug and attacker replays right at the wallet.timeout boundary hoping the min() computation off-by-one lets an expired message through. Call sequence: `commit`->boundary check `created_at <= now` and `now - min(...) <= created_at`. Binding: a request settles only while `now ∈ [created_at, created_at + min(msg.timeout, wallet.timeout)]`; outside that == rejected. Impact: High - an expired signed `Request` (e.g. an old `Transfer`) executes after the owner believed it lapsed, moving funds under a stale authorisation. Proof idea: sandbox test advancing block timestamp to exactly `created_at + min(msg.timeout, wallet.timeout) + 1` and asserting `commit` returns `NonceError::ExpiredOrFuture`.
