### Title
Reward-per-token accumulator in `pallet-asset-rewards` can overflow `T::Balance` when `total_tokens_staked` is dust, permanently freezing staked tokens - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` implements a Synthetix-style "reward per token" accumulator that is structurally identical to the vulnerable formula in the external report (`RewardsDistributor.sol`): a reward rate is multiplied by elapsed blocks and a fixed precision scaling factor, then divided by the total amount currently staked. When `total_tokens_staked` is small relative to `reward_rate_per_block`, the accumulator (`reward_per_token_stored`) can grow to the point where the `EnsureMul`/`EnsureAdd` arithmetic in `reward_per_token` returns an error instead of silently saturating, causing every subsequent `stake`, `unstake`, and `harvest_rewards` call for that pool to fail permanently.

### Finding Description
The core computation lives in `Pallet::<T>::reward_per_token`: [1](#0-0) 

```rust
Ok(pool_info.reward_per_token_stored.ensure_add(
    pool_info
        .reward_rate_per_block
        .ensure_mul(rewardable_blocks_elapsed.into())?
        .ensure_mul(PRECISION_SCALING_FACTOR.into())?
        .ensure_div(pool_info.total_tokens_staked)?,
)?)
```

This mirrors exactly the vulnerable pattern in the report: `emissionPerSecond * timeDelta * scalingFactor / totalBalance`. `PRECISION_SCALING_FACTOR` is a fixed constant (`4096`) analogous to `10 ** decimals` in the report: [2](#0-1) 

Because `T::Balance` is a bounded generic (`type Balance: Balance + TypeInfo`), and this division is by `total_tokens_staked` (the pool's currently staked amount, fully controlled by unstake actions of ordinary, unprivileged stakers), an attacker/staker can drive `total_tokens_staked` down toward a small residual (dust) amount by unstaking, and then simply let blocks pass. Once `reward_rate_per_block * blocks_elapsed * 4096 / total_tokens_staked` grows large enough that `ensure_add`/`ensure_mul` overflow `T::Balance`, `reward_per_token` returns `Err`, and this propagates up through `update_pool_rewards`/`update_pool_and_staker_rewards`: [3](#0-2) 

Every pallet call that must call `update_pool_and_staker_rewards` prior to mutating staker/pool state (stake, unstake, harvest) will therefore fail with the same error for as long as `total_tokens_staked` remains small and blocks continue to elapse — the accumulator only grows monotonically larger the longer it's left unfixed, so the condition is self-reinforcing rather than self-healing.

This differs from the report's original context (an AAVE-style aToken index) mainly in bound type (`T::Balance`, which in most runtimes is `u128`, larger than the contract's `uint104`), so triggering it requires more extreme ratios of `reward_rate_per_block` to `total_tokens_staked` and/or elapsed blocks — but the same class of unbounded-growth/dust-denominator bug is present, and there is no minimum-stake threshold or growth cap on `reward_per_token_stored`.

### Impact Explanation
If `reward_per_token_stored` overflow is hit for a pool, the pool becomes permanently unusable:
- Any staker still holding staked tokens in that pool cannot `unstake` (which internally calls `update_pool_and_staker_rewards` before releasing the `MutateFreeze`), so their tokens are frozen indefinitely.
- No further rewards can be harvested by any staker of that pool.
- New stakers cannot join the pool either, since `stake` similarly triggers the same reward calculation. This is a genuine, permanent fund-lock/DoS condition reachable with a normal, unprivileged staking configuration and normal user actions (no admin, governance, or privileged actor required) — matching the "permanent user-fund … lock" and "runtime bugs that compromise intended behavior" impact categories.

### Likelihood Explanation
Because `T::Config::Balance` is typically `u128` in production runtimes, triggering an actual overflow requires an extreme configuration: a pool with a very large `reward_rate_per_block` relative to `total_tokens_staked`, combined with either an unusually long window of inactivity or aggressive draining of the staked pool to near-zero by stakers unstaking. This is plausible for pools created with permissive parameters (pool creation is gated by `CreatePoolOrigin`, but the rate can subsequently only be increased via `set_reward_rate_per_block`/admin, and a pool can legitimately end up with near-zero `total_tokens_staked` if all but a dust amount of stakers exit) and pools intentionally left running for long periods without being cleaned up (`cleanup_pool` requires the pool to be non-empty of stakers already, so it cannot rescue an already-affected pool). The likelihood is lower than the original Solidity report (`uint104` is far smaller than `u128`), but the structural flaw — unbounded growth of a reward accumulator divided by a caller-influenced total supply with no minimum-stake floor — is directly analogous.

### Recommendation
- Enforce a minimum non-dust `total_tokens_staked` threshold below which `reward_per_token` returns the last stored value instead of performing the division (mirroring the report's recommended fix of skipping accrual below a threshold).
- Alternatively, bound `reward_rate_per_block` relative to a minimum expected `total_tokens_staked`, or periodically checkpoint/reset the accumulator to prevent unbounded growth.
- Add a `try-runtime`/integration test that exercises a pool drained to a minimal stake with a high reward rate over many blocks to confirm `reward_per_token` does not error out and brick `stake`/`unstake`/`harvest_rewards`.

### Proof of Concept
1. `create_pool` with `reward_rate_per_block` set to a large value (e.g., near the practical maximum allowed by `T::Balance`).
2. Have a staker `stake` a small amount so that `total_tokens_staked` is minimal (dust) relative to `reward_rate_per_block`.
3. Let a large number of blocks pass (or use `BlockNumberProvider` mocked to jump far ahead, as tests in `substrate/frame/asset-rewards/src/tests.rs` do for other scenarios).
4. Call `unstake` or `harvest_rewards`: `reward_per_token` computes `reward_rate_per_block.ensure_mul(blocks_elapsed).ensure_mul(4096).ensure_div(total_tokens_staked)`, which for a big enough numerator/small denominator overflows `T::Balance` and returns `Err`, causing the call to fail and permanently freezing the staker's tokens for that pool. 		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
