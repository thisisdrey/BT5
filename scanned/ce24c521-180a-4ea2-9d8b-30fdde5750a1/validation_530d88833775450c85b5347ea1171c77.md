Based on my investigation, I found a strong local analog: the `pallet-staking`/`pallet-staking-async` `VoterList` (typically backed by `pallet-bags-list`) is used exactly like `SortedTroves` — election snapshot generation walks the list assuming its stored order reflects current voting weight, but the pallet's own documentation admits that reward/slash-driven stake changes are **not** propagated to the list automatically.

### Title
Election snapshot selection relies on stale `VoterList` ordering, letting truncated bounded snapshots admit lower-stake voters over higher-stake ones - ([File: substrate/frame/staking-async/src/pallet/impls.rs])

### Summary
`pallet-staking`/`pallet-staking-async` stores nominator "score" (stake weight) inside the `SortedListProvider` (`pallet-bags-list`) at insertion/explicit-update time, exactly mirroring `SortedTroves.Node.ICR` in the external report. The pallet's own docs concede this score becomes stale: "changes made to the staked amount via rewards and slashes are not reported and thus need to be manually fixed by the staker" via `rebag`/`putInFrontOf`. [1](#0-0) 

### Finding Description
`get_npos_voters` iterates `T::VoterList::iter()` (or `iter_from` for paging) in the list's *stored* order and stops once a bounded `page_len_prediction`/count limit is reached, or once `NPOS_MAX_ITERATIONS_COEFFICIENT * page_len_prediction` items have been scanned. [2](#0-1) [3](#0-2) 

The weight actually used for the voter tuple pushed into the election snapshot is freshly recomputed via `weight_of(&voter)` at line 913, but the **iteration order that decides which accounts are ever reached before the bound/iteration cap is hit** is entirely governed by the possibly-stale `Node.score` stored in `pallet-bags-list`, since `VoterList` (bags-list) is only reordered on an explicit `on_insert`/`on_update` call (`nominate`, `chill`, or a permissionless `rebag`/`put_in_front_of` call), not automatically when validator/era rewards or slashes change a nominator's real stake. [4](#0-3) 

The test `voter_list_not_updated_when_locked` explicitly demonstrates the acknowledged consequence: a nominator who `bond_extra`s a large amount remains in their old (lower) bag, "not reflected in this election," while another already-large staker who partially `unbond`s also keeps their old (higher) bag/position for the ongoing snapshot. [5](#0-4) 

This is structurally identical to the Liquity report: the "sort key" (`Node.score`/`Node.ICR`) drifts from the true underlying value (stake weight/ICR) because updates are optional and permissionless-but-not-automatic, and the code that consumes the ordering (`get_npos_voters` truncating by bound / `TroveManagerRedemptions` walking `SortedTroves` for redemption order) assumes the order is accurate.

### Impact Explanation
When a bounded/paged election snapshot is generated (as is standard for `election-provider-multi-block`/multi-phase with `DataProviderBounds`), the truncation point (`page_len_prediction`, `NPOS_MAX_ITERATIONS_COEFFICIENT` cap) is applied against stale ordering. A nominator who has legitimately increased their real stake (via era rewards compounding, or `bond_extra`) but whose `VoterList` position was never refreshed can be excluded from the voter snapshot entirely if the cutoff falls before their stale (lower) bag, while a nominator whose real stake has fallen (via `unbond`/slashing) keeps voting with more influence than warranted until someone calls `rebag`. This degrades the intended-behavior invariant that NPoS election "must weigh voters/targets according to their true stake," corrupting election desired-outcome integrity (who gets to elect validators, indirectly affecting reward and slash exposure for the whole active set) without requiring any privileged, admin, or malicious-relayer actor — any nominator can trigger the drift simply by bonding/unbonding through the ordinary public `bond_extra`/`unbond`/`nominate` extrinsics.

### Likelihood Explanation
High under normal chain operation: staking rewards and slashes happen every era without any corresponding list reordering call (per the pallet's own doc comment), and `rebag`/`put_in_front_of` are optional permissionless catch-up calls with real transaction cost that are not guaranteed to be called before a snapshot round runs, especially under `election-provider-multi-block`'s multi-page snapshot flow where `VoterList` is explicitly `lock()`ed mid-snapshot to freeze order. [6](#0-5) 

### Recommendation
Mirror the report's first recommendation: do not rely solely on stored `Node.score` for truncation decisions in bounded snapshots, or require the score be refreshed (via `weight_of`) before it counts toward the ordering used to decide inclusion/exclusion, not just the value stored in the emitted voter tuple. At minimum, document explicitly (as already partly done) that bounded/paged snapshots can silently drop legitimately high-stake voters and admit stale high-score but now-lower-stake voters, and consider incentivizing/automating `rebag` before snapshot-taking (e.g., an `on_idle` sweep prior to election start, similar to the existing `PendingRebag`/auto-rebag machinery already added to `pallet-bags-list`). [7](#0-6) 

### Proof of Concept
1. Nominator `A` bonds a small stake and is placed in a low `bags-list` bag.
2. `A` calls the public `bond_extra` extrinsic to substantially increase stake — `VoterList`/bags-list position is **not** updated automatically (only `Nominators`/`Ledger` storage changes); confirmed by `voter_list_not_updated_when_locked`, where after `bond_extra(RuntimeOrigin::signed(11), 5000)` the node's `bag_upper` in `pallet_bags_list::ListNodes` is unchanged. [8](#0-7) 
3. An election round begins and `electing_voters`/`get_npos_voters` is invoked with a bounded `DataProviderBounds` (`voters_count`), iterating `VoterList::iter()`/`iter_from` in stale bag order and stopping once `page_len_prediction` voters are collected. [9](#0-8) 
4. Because `A`'s bag position still reflects the pre-`bond_extra` low stake, `A` is scanned late (or not at all before the iteration cap of `NPOS_MAX_ITERATIONS_COEFFICIENT * page_len_prediction`), so `A`'s true, larger, up-to-date stake never influences the election even though `weight_of(A)` (used elsewhere, e.g. for `min_active_stake`) would show the correct higher amount — demonstrating the ordering/inclusion decision used stale data despite fresh weight being technically available.

	pub(crate) fn get_npos_voters(
		bounds: DataProviderBounds,
		status: &SnapshotStatus<T::AccountId>,
	) -> Vec<VoterOf<Self>> {
		let mut voters_size_tracker: StaticTracker<Self> = StaticTracker::default();

		let page_len_prediction = {
			let all_voter_count = T::VoterList::count();
			bounds.count.unwrap_or(all_voter_count.into()).min(all_voter_count.into()).0
		};

		let mut all_voters = Vec::<_>::with_capacity(page_len_prediction as usize);

		// cache a few things.
		let weight_of = Self::weight_of_fn();

		let mut voters_seen = 0u32;
		let mut validators_taken = 0u32;
		let mut nominators_taken = 0u32;
		let mut min_active_stake = u64::MAX;

		let mut sorted_voters = match status {
			// start the snapshot processing from the beginning.
			SnapshotStatus::Waiting => T::VoterList::iter(),
			// snapshot continues, start from the last iterated voter in the list.
			SnapshotStatus::Ongoing(account_id) => T::VoterList::iter_from(&account_id)
				.defensive_unwrap_or(Box::new(vec![].into_iter())),
			// all voters have been consumed already, return an empty iterator.
			SnapshotStatus::Consumed => Box::new(vec![].into_iter()),
		};

		while all_voters.len() < page_len_prediction as usize &&
			voters_seen < (NPOS_MAX_ITERATIONS_COEFFICIENT * page_len_prediction as u32)
		{
			let voter = match sorted_voters.next() {
				Some(voter) => {
					voters_seen.saturating_inc();
					voter
				},
				None => break,
			};

	fn electing_voters(
		bounds: DataProviderBounds,
		page: PageIndex,
	) -> data_provider::Result<Vec<VoterOf<Self>>> {
		let mut status = VoterSnapshotStatus::<T>::get();
		let voters = Self::get_npos_voters(bounds, &status);

		// update the voter snapshot status.
		match (page, &status) {
			// last page, reset status for next round.
			(0, _) => status = SnapshotStatus::Waiting,

			(_, SnapshotStatus::Waiting) | (_, SnapshotStatus::Ongoing(_)) => {
				let maybe_last = voters.last().map(|(x, _, _)| x).cloned();

				if let Some(ref last) = maybe_last {
					let has_next =
						T::VoterList::iter_from(last).ok().and_then(|mut i| i.next()).is_some();
					if has_next {
						status = SnapshotStatus::Ongoing(last.clone());
					} else {
						status = SnapshotStatus::Consumed;
					}
				}
			},
			// do nothing.
			(_, SnapshotStatus::Consumed) => (),
		}

	fn on_insert(id: T::AccountId, score: T::Score) -> Result<(), ListError> {
		if Pallet::<T, I>::ensure_unlocked().is_err() {
			// Pallet is locked - store in PendingRebag for later processing
			// Only queue if auto-rebagging is enabled
			if T::MaxAutoRebagPerBlock::get() > 0u32 {
				PendingRebag::<T, I>::insert(&id, ());
				return Ok(());
			}

			return Err(ListError::Locked);
		};
		List::<T, I>::insert(id, score)
	}

	fn on_update(id: &T::AccountId, new_score: T::Score) -> Result<(), ListError> {
		Pallet::<T, I>::ensure_unlocked()?;
		Pallet::<T, I>::do_rebag(id, new_score).map(|_| ())
	}
