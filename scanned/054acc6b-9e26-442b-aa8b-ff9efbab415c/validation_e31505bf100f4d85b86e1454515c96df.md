This local analog fits the bug-class well: an optimistic "success" signal from a fire-and-forget dispatch (XCM `deliver`) is treated as final settlement even though the ultimate value transfer happens asynchronously on a different chain and can fail, permanently losing funds while local state records the payout as done.

### Title
Snowbridge reward claim is finalized on XCM *send* success, not on actual beneficiary deposit, causing permanent loss of relayer rewards - (File: `bridges/snowbridge/primitives/core/src/reward.rs`)

### Summary
`PayAccountOnLocation::pay_reward` (used as `BridgeRewardPayer` for the `BridgeReward::Snowbridge` variant on BridgeHub Westend) returns `Ok(())` as soon as an XCM instruction sequence has been successfully *handed off* to the XCM router (`XcmSender::deliver`). It never confirms that the remote `DepositAsset` on AssetHub actually credits the intended beneficiary. `pallet-bridge-relayers::do_claim_rewards` uses this `Ok(())` to permanently remove the reward entry from storage. This mirrors the reported bug class: a low-level dispatch that "returns success" without guaranteeing the intended recipient actually received the funds, and once that success is recorded, there is no path back for the victim.

### Finding Description
`claim_rewards_to` calls `Self::do_claim_rewards`, which uses `RelayerRewards::try_mutate_exists` to take the reward out of storage and calls `T::PaymentProcedure::pay_reward(...)`: [1](#0-0) 

For the Snowbridge reward kind, `PaymentProcedure` is implemented by `BridgeRewardPayer`, which for `AssetHubLocation` beneficiaries delegates to `PayAccountOnLocation::pay_reward`: [2](#0-1) 

`PayAccountOnLocation::pay_reward` builds an XCM program that reserve-deposits Ethereum-origin assets and calls `DepositAsset` to the user-supplied `beneficiary: Location`, then simply validates, charges fees, and calls `XcmSender::deliver`: [3](#0-2) 

Crucially, once `XcmSender::deliver(ticket)` succeeds, the function returns `Ok(())` — this only means the message was queued for delivery to AssetHub, not that `DepositAsset` executed successfully there. Execution on AssetHub happens later, asynchronously, and can fail for reasons entirely under the control of the (unprivileged) relayer supplying their own beneficiary `Location` — e.g. a malformed or unroutable `VersionedLocation`, a beneficiary account requiring an ED the deposit doesn't cover, or any other filter/config on AssetHub side that traps the assets (`AssetTraps`) instead of crediting them.

Because `do_claim_rewards` on BridgeHub already returned `Ok(())` (the local `try_mutate_exists` commits, wiping the `RelayerRewards` entry) the moment `pay_reward` returned `Ok(())`, the relayer's accumulated reward record is destroyed permanently on the source chain regardless of whether the funds ever landed with the beneficiary. There is no receipt/callback mechanism in this pay_reward path to re-credit the reward if the remote `DepositAsset` traps.

This is structurally identical to the reported low-level-call bug: a "call" (here, XCM `deliver`) is treated as fully successful execution, when in fact the receiving side ("contract"/AssetHub execution) can silently fail to do the intended work, and the caller (BridgeHub relayers pallet) has already committed state assuming success.

### Impact Explanation
A relayer who claims their accumulated reward via `claim_rewards_to` with an `AssetHubLocation` beneficiary can permanently lose that reward if the XCM's `DepositAsset` traps on AssetHub (e.g., non-existent/misconfigured beneficiary account, asset registration issues, or any other execution-time failure not visible at send time). The `RelayerRewards` storage entry is already removed, so the relayer has no way to re-claim the same reward — this is a permanent fund loss condition tied to public dispatch (`claim_rewards_to`) accepting an unvalidated remote outcome as final settlement.

### Likelihood Explanation
This requires only an ordinary signed relayer calling the public `claim_rewards_to` extrinsic with a `Location` beneficiary that fails to resolve/deposit correctly on AssetHub — no malicious peer, validator, collator, or governance action is needed. Given `Location`/`VersionedLocation` values are attacker (relayer)-supplied and not validated against AssetHub-side deposit preconditions before local settlement, the failure mode is readily reachable, though the fund loss falls on the relayer who provided the bad location (self-inflicted, similar severity classification to the seed report).

### Recommendation
Do not finalize (remove) the reward record on the source chain merely upon successful XCM `deliver`. Either: (a) use a report-based/versioned-notify mechanism so the reward entry is only cleared after confirmed successful execution on AssetHub, or (b) keep the claim pending/re-claimable until a delivery/execution receipt is observed, with a fallback path to restore the `RelayerRewards` entry (or credit an escrow) if the remote deposit traps.

### Proof of Concept
1. Relayer accrues a reward under `BridgeReward::Snowbridge`.
2. Relayer calls `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(bad_location))` where `bad_location` is a `VersionedLocation` that will cause the eventual `DepositAsset` to trap on AssetHub (e.g., pointing at an account/asset combination AssetHub cannot resolve/deposit into).
3. On BridgeHub: `validate_send`, `charge_fees`, and `XcmSender::deliver` all succeed (the message is only being queued for cross-chain delivery), so `pay_reward` returns `Ok(())`.
4. `do_claim_rewards`'s `try_mutate_exists` commits, and the `RelayerRewards` entry for this relayer/reward_kind is deleted; `RewardPaid` event is emitted.
5. On AssetHub, the XCM program executes; `DepositAsset` fails to credit `bad_location` and the reserve-deposited assets are trapped into `AssetTraps` instead.
6. The relayer's reward is now gone from BridgeHub storage with no corresponding funds received at any location the relayer controls, and no automated mechanism restores or re-credits the reward.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
