## Analysis

The external report's core broken invariant is: **a permissionless entrypoint derives a deterministic identifier from caller-supplied data and lets the caller also attach arbitrary trust-relevant metadata, so an unprivileged party can "claim" that identifier — with poisoned metadata — before the legitimate flow does.** The fix in the report was to restrict the call so it can only be reached through the privileged/canonical path.

The closest local analog is Snowbridge's `register_token` extrinsic in the **system-v2 frontend pallet**, which registers a Polkadot asset `Location` as a wrapped ERC20 on Ethereum using a deterministic `TokenId` and attacker-suppliable name/symbol/decimals metadata.

I want to flag upfront: I could not fully inspect the concrete `FrontendOrigin` implementation wired in `cumulus/parachains/runtimes/bridge-hubs/bridge-hub-westend/src/bridge_to_ethereum_config.rs` within the remaining tool budget, so the precise set of accounts able to reach this call (all signed AssetHub accounts vs. some narrower XCM-origin filter) is not fully confirmed from the index. The finding below is based on the pallet logic itself plus the test evidence that the extrinsic accepts an arbitrary `Location`/metadata pair independent of any check that the caller owns/created the underlying asset at that location.

### Title
Permissionless `register_token` lets anyone squat a deterministic Ethereum `TokenId` with forged name/symbol metadata - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

### Summary
`EthereumSystem::register_token` (system-v2 / "frontend" flow) computes a fully deterministic `TokenId` from a `Location` and inserts a first-come `ForeignToNativeId` mapping, then forwards caller-supplied `name`/`symbol`/`decimals` verbatim to Ethereum via `Command::RegisterForeignToken`, with no verification that the caller controls or owns the asset behind that `Location`.

### Finding Description
`register_token` is gated only by `T::FrontendOrigin::ensure_origin(origin)?`, not by asset ownership: [1](#0-0) 

The `token_id` is `TokenIdOf::convert_location(&location)` — a pure hash of the (reanchored) `Location`, fully predictable/public, exactly analogous to the report's `salt = keccak256(_poolId, _expiry, _generation)`: [2](#0-1) 

The guard is only "not already registered" (`if !ForeignToNativeId::<T>::contains_key(token_id)`), and the `metadata.name` / `metadata.symbol` / `metadata.decimals` used to construct the `RegisterForeignToken` command sent to the Ethereum Gateway are taken from the caller's input, not derived from the actual on-chain asset's registered metadata: [3](#0-2) 

The unit test confirms the call accepts an arbitrary `Location` and metadata from an XCM origin without any ownership binding between the calling parachain/account and the `asset_id` location supplied: [4](#0-3) 

This mirrors the `CoverRightTokenFactory.deployCRToken` pattern precisely: (1) a public/unprivileged call, (2) a deterministic identifier computed from caller-suppliable parameters that can be pre-computed, and (3) arbitrary attacker-chosen display metadata (`poolName`/`tokenName` there, `name`/`symbol`/`decimals` here) bound to that identifier the moment it is first "deployed"/registered. Just as anyone could deploy a CR token at the future salt before `PolicyCenter` did, here anyone can register a `Location`'s `TokenId` on Ethereum with forged metadata before the legitimate asset issuer does — and since the mapping/registration is first-come, the legitimate flow (root-gated `register_token` in the older `pallets/system` v1) or a later legitimate `system-v2` caller cannot correct it once claimed: [5](#0-4) 

### Impact Explanation
An unprivileged actor can cause Ethereum-side infrastructure/wallets to display a fraudulent name/symbol for a wrapped representation of a real (or soon-to-be-real) Polkadot asset, because the `TokenId → metadata` binding is claimed on a first-write basis with no verification tying the caller to the underlying asset. This is a "forged or mis-bound proof/state acceptance" class issue on the bridge registration path: the state (`ForeignToNativeId` + the Ethereum `RegisterForeignToken` command) gets permanently bound to attacker-controlled metadata for a deterministic, predictable identifier, which can be used to deceive users/integrators who rely on this metadata as authentic, a direct analog of the "tricking users via poolName/tokenName" harm called out in the source report.

### Likelihood Explanation
Likelihood depends entirely on how broadly `T::FrontendOrigin` is configured in the deployed runtime (e.g., whether it permits any signed AssetHub account to trigger registration for an arbitrary `Location`, versus requiring the calling location to match/own the asset's reserve chain). Given the doc comment ("The system frontend pallet on AH proxies this call to BH" / "sender: The original sender initiating the call on AH") suggests this is intended to be reachable by ordinary AssetHub users rather than only root, the likelihood is non-trivial but the exact origin bound was not fully confirmed in this review — this is a known limitation of the analysis.

### Recommendation
Before accepting a `register_token` call and inserting into `ForeignToNativeId`, verify that the sending origin's location (or the AssetHub-resolved owner/creator of the local asset represented by `asset_id`) actually matches/owns the asset referenced by `location`, mirroring the report's fix of "verify calls only originate through the canonical/privileged path." Additionally, once a `TokenId` is registered, metadata should not be re-writable by a different, unrelated origin, and registration should require proof that the caller is the asset's registered admin/owner on the local chain rather than accepting arbitrary caller-supplied metadata.

### Proof of Concept
1. Attacker observes (or predicts) the `Location` that will represent a soon-to-be-popular Polkadot asset (e.g. a new parachain's native/reserve asset about to be teleported to Ethereum).
2. Attacker calls `EthereumSystemFrontend::register_token` (or the equivalent XCM `Transact` reaching `system-v2::register_token`) from an account satisfying `FrontendOrigin`, supplying that `Location` as `asset_id` and forged `AssetMetadata { name: "USD Coin", symbol: "USDC", decimals: 6 }` as shown reachable in the existing test harness: [4](#0-3) 
3. `TokenIdOf::convert_location(&location)` computes the same deterministic `TokenId` the legitimate issuer would later compute.
4. `ForeignToNativeId::<T>::contains_key(token_id)` is false, so the attacker's mapping and `Command::RegisterForeignToken{ token_id, name: "USD Coin", symbol: "USDC", decimals: 6 }` are accepted and dispatched to the Ethereum Gateway, permanently squatting that `TokenId` with the forged metadata.
5. When the legitimate asset issuer later attempts registration for the same `Location`, the `TokenId`/wrapped contract on Ethereum already exists with attacker-controlled branding, and no code path shown re-registers/corrects metadata for an already-claimed `TokenId`.

		#[pallet::call_index(2)]
		#[pallet::weight(<T as pallet::Config>::WeightInfo::register_token())]
		pub fn register_token(
			origin: OriginFor<T>,
			sender: Box<VersionedLocation>,
			asset_id: Box<VersionedLocation>,
			metadata: AssetMetadata,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let sender_location: Location =
				(*sender).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;
			let asset_location: Location =
				(*asset_id).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;

			let location = Self::reanchor(asset_location)?;
			let token_id = TokenIdOf::convert_location(&location)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			if !ForeignToNativeId::<T>::contains_key(token_id) {
				ForeignToNativeId::<T>::insert(token_id, location.clone());
			}

			let command = Command::RegisterForeignToken {
				token_id,
				name: metadata.name.into_inner(),
				symbol: metadata.symbol.into_inner(),
				decimals: metadata.decimals,
			};

			let message_origin = Self::location_to_message_origin(sender_location)?;
			Self::send(message_origin, command, amount)?;

			Self::deposit_event(Event::<T>::RegisterToken {
				location: location.into(),
				foreign_token_id: token_id,
			});

			Ok(())
		}
