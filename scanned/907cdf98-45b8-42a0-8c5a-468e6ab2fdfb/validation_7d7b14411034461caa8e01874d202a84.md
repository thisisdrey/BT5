### Title
Renaming an asset can resurrect previously "revoked" ERC-2612 permits and drain approvals - (File: `substrate/frame/assets/precompiles/src/permit.rs`)

### Summary
The `pallet_assets` metadata functions `set_metadata`/`force_set_metadata` allow a token's `name` to be changed an unlimited number of times, with no restriction on reverting to a previously-used value. The permit precompile's EIP-712 domain separator is computed live from this mutable `name` field on every verification call rather than being bound to an immutable, monotonically-increasing identifier. The repository's own tests document that changing the name is treated as a mechanism to invalidate outstanding signed permits, but because the name can be changed back, that "invalidation" is not durable — an old signature that was believed to be revoked can become valid again.

### Finding Description
`pallet_assets::set_metadata` (owner-signed, permissionless for the asset owner) and `force_set_metadata` (ForceOrigin) let the `name`/`symbol` be overwritten arbitrarily many times with no one-time-use guard: [1](#0-0) [2](#0-1) 

The `do_set_metadata` implementation freely overwrites the existing `AssetMetadata` value on every call — there is no check that metadata has not been set before, and no versioning of the name: [3](#0-2) 

The permit precompile derives the EIP-712 `DOMAIN_SEPARATOR` from this same mutable `name` on every call to `compute_domain_separator`/`permit_digest`, and nonces are only incremented when a permit is actually *consumed* via `use_permit`, never when the name changes: [4](#0-3) [5](#0-4) 

The project's own regression test explicitly frames a name change as a security-relevant revocation mechanism, since the domain separator "binds the asset's current `name` metadata": [6](#0-5) 

The corrupted value is the on-chain `name` baked into `DOMAIN_SEPARATOR` at verification time: because it is not tied to a monotonic version/epoch counter, any name value that was valid in the past can become valid again simply by calling `set_metadata`/`force_set_metadata` a second time with the original bytes. Since the nonce for a given `(verifying_contract, owner)` pair is untouched by name changes (it only advances on successful `use_permit`), a permit signature produced under name `A`, then apparently invalidated by renaming to `B`, is fully re-armed the moment the name is changed back to `A` — with the same nonce, same signature, and same digest as before.

### Impact Explanation
Any relying party who assumes that renaming a token cancels stale, unused, but not-yet-expired `permit` signatures (a workflow the code's own comments and tests promote as a de-facto revocation) is exposed to signature resurrection: an attacker or the original signer's counterparty holding an old signed permit can wait for the name to be reverted (a normal, permissionless, or admin rebranding action unrelated to any malicious intent) and then submit the "revoked" permit, granting an allowance the signer believed was dead. This can lead to unauthorized ERC-20-style approvals being (re)granted and subsequently drained via `transferFrom`, i.e. unauthorized execution / fund loss for the signer, without needing a malicious peer, validator, or governance actor as the root cause — the flaw is in the domain-separator design binding to mutable, revertible state instead of an immutable or monotonic identifier.

### Likelihood Explanation
Likelihood is moderate: it requires (1) a signer to have produced a permit signature with a future deadline that is not immediately consumed, and (2) the asset's `name` to be changed away and later reverted to the exact original bytes (or to any other prior name for which stale signatures exist) before the deadline expires. Both metadata changes are ordinary, unprivileged (owner) or privileged (ForceOrigin) asset-management operations that require no compromise of keys, nodes, or validators — simply performing routine rebranding twice (e.g., correcting a typo and reverting) is enough to trigger the resurrection unintentionally, and a token owner relying on renaming as an emergency revocation tool could unknowingly restore attacker-held signatures.

### Recommendation
Do not bind the EIP-712 domain separator to a value that can be reverted to a prior state. Introduce a monotonically increasing `MetadataVersion`/`nonce` per asset that is incremented (never reused) every time `set_metadata`/`force_set_metadata` changes the name, and fold that version into `compute_domain_separator` (or otherwise invalidate all outstanding nonces on any metadata change, e.g. by including a per-asset epoch counter in `Nonces` key or digest). Alternatively, treat token metadata name as append-only/immutable after first non-empty use, or explicitly disallow reusing a previously-set name value for the same asset.

### Proof of Concept
1. Asset owner calls `set_metadata` with `name = "Test Token"`, deploying the ERC20Permit-capable asset via the precompile.
2. Signer Alice signs a `Permit(owner=Alice, spender=Bob, value=1000, nonce=0, deadline=FAR_FUTURE)` digest computed with `DOMAIN_SEPARATOR` bound to `name = "Test Token"` (per `compute_domain_separator`).
3. Alice, suspecting the signature was leaked, asks (or the owner independently decides) to rename the token to `"Test Token v2"` via `set_metadata`/`force_set_metadata`. As shown by `permit_rejects_after_token_name_change`, submitting Alice's old signature now fails with `SignerMismatch` because the recomputed domain separator differs — Alice reasonably believes the leaked permit is now dead. Nonce for `(verifying_contract, Alice)` is still `0` because `use_permit` was never called.
4. At any later point, the owner calls `set_metadata`/`force_set_metadata` again reverting `name` back to `"Test Token"` (e.g., during a rebrand rollback) — nothing in `do_set_metadata`/`force_set_metadata` prevents reusing the original bytes.
5. Bob (or whoever holds Alice's leaked signature) resubmits the exact same `(v, r, s)` permit call. `do_verify_permit` recomputes the same `DOMAIN_SEPARATOR` as in step 2 (same `name`, same nonce `0`), `ecrecover` returns Alice's address, and `use_permit` succeeds — silently re-granting Bob a 1000-unit allowance against Alice's wishes.

	pub(super) fn do_set_metadata(
		id: T::AssetId,
		from: &T::AccountId,
		name: Vec<u8>,
		symbol: Vec<u8>,
		decimals: u8,
	) -> DispatchResult {
		let bounded_name: BoundedVec<u8, T::StringLimit> =
			name.clone().try_into().map_err(|_| Error::<T, I>::BadMetadata)?;
		let bounded_symbol: BoundedVec<u8, T::StringLimit> =
			symbol.clone().try_into().map_err(|_| Error::<T, I>::BadMetadata)?;

		let d = Asset::<T, I>::get(&id).ok_or(Error::<T, I>::Unknown)?;
		ensure!(d.status == AssetStatus::Live, Error::<T, I>::AssetNotLive);
		ensure!(from == &d.owner, Error::<T, I>::NoPermission);

		Metadata::<T, I>::try_mutate_exists(id.clone(), |metadata| {
			ensure!(metadata.as_ref().map_or(true, |m| !m.is_frozen), Error::<T, I>::NoPermission);

			let old_deposit = metadata.take().map_or(Zero::zero(), |m| m.deposit);
			let new_deposit = Self::calc_metadata_deposit(&name, &symbol);

			if new_deposit > old_deposit {
				T::Currency::reserve(from, new_deposit - old_deposit)?;
			} else {
				T::Currency::unreserve(from, old_deposit - new_deposit);
			}

			*metadata = Some(AssetMetadata {
				deposit: new_deposit,
				name: bounded_name,
				symbol: bounded_symbol,
				decimals,
				is_frozen: false,
			});

			Self::deposit_event(Event::MetadataSet {
				asset_id: id,
				name,
				symbol,
				decimals,
				is_frozen: false,
			});
			Ok(())
		})
	}

		/// Compute the EIP-712 domain separator for a given verifying contract.
		///
		/// DOMAIN_SEPARATOR = keccak256(abi.encode(
		///   keccak256("EIP712Domain(string name,string version,uint256 chainId,address
		/// verifyingContract)"),
		///   keccak256(name),
		///   keccak256("1"),
		///   chainId,
		///   verifyingContract
		/// ))
		///
		/// The `name` parameter should be the token name per EIP-2612 specification.
		pub fn compute_domain_separator(verifying_contract: &H160, name: &[u8]) -> H256 {
			let name_hash = keccak_256(name);
			let version_hash = keccak_256(b"1");
			let chain_id = T::ChainId::get();

			// Encode: typehash || name_hash || version_hash || chainId || verifyingContract
			let mut data = Vec::with_capacity(DOMAIN_SEPARATOR_ENCODED_LEN);
			data.extend_from_slice(&DOMAIN_TYPEHASH);
			data.extend_from_slice(&name_hash);
			data.extend_from_slice(&version_hash);
			// Pad chain_id to 32 bytes (big-endian)
			data.extend_from_slice(&[0u8; 24]);
			data.extend_from_slice(&chain_id.to_be_bytes());
			// Pad address to 32 bytes
			data.extend_from_slice(&[0u8; 12]);
			data.extend_from_slice(verifying_contract.as_bytes());

			H256(keccak_256(&data))
		}

/// Renaming an asset invalidates outstanding permits — the EIP-712
/// domain separator binds the asset's current `name` metadata. Kept
/// parametrized over both prefixes for confidence on this
/// security-relevant invariant.
#[test_case(PRECOMPILE_ADDRESS_PREFIX)]
#[test_case(PRECOMPILE_ADDRESS_PREFIX_FOREIGN)]
fn permit_rejects_after_token_name_change(asset_index: u16) {
	new_test_ext().execute_with(|| {
		let setup = permit_setup(asset_index);

		let (v, r, s) =
			sign_permit(setup.asset_addr, setup.spender_addr, AlloyU256::from(100), setup.deadline);

		assert_ok!(Assets::force_set_metadata(
			RuntimeOrigin::root(),
			setup.asset_id,
			b"Renamed Token".to_vec(),
			b"RNM".to_vec(),
			18,
			false,
		));

		let result = raw_permit(
			setup.submitter,
			setup.asset_addr,
			HARDHAT_ACCOUNT_0,
			setup.spender_addr,
			AlloyU256::from(100),
			setup.deadline,
			v,
			r,
			s,
		);
		assert_permit_reverted_with(result, "Signer does not match owner");
		assert_eq!(
			permit::Pallet::<Test>::nonce(&setup.asset_addr, &HARDHAT_ACCOUNT_0),
			U256::zero()
		);
	});
