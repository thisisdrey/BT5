Confirmed: `get_balance` at [1](#0-0)  reads the raw on-chain fungible balance of the deterministic pool account, not an internally tracked reserve. This means any direct transfer to the pool address (outside of `add_liquidity`) permanently poisons the reserve ratio used for AMM math before the first liquidity provider arrives.

### Title
First-liquidity griefing via direct token donation to pool account permanently blocks `add_liquidity` - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`pallet-asset-conversion` computes reserves for a pool by directly reading the pool account's on-chain balances via `get_balance`/`T::Assets::balance`, rather than from internally accounted reserve state. The pool account address is deterministically derivable from the asset pair via `T::PoolLocator::address`/`pool_id` before the pool even exists. An attacker can transfer (donate) an extreme, skewed ratio of `asset1`/`asset2` directly to this address before the first legitimate `add_liquidity` call. Because `total_supply` of the LP token is still zero at that point, `do_add_liquidity` takes the zero-supply branch or the ratio-quoting branch depending on which reserves are nonzero, but the price-quoting math (`quote`/`mul_div`) then operates on the attacker-controlled reserve ratio, not the depositor's intended ratio, causing overflow, `AssetOneDepositDidNotMeetMinimum`/`AssetTwoDepositDidNotMeetMinimum`, `OptimalAmountLessThanDesired`, or rounding one side down to zero, which is then rejected by `InsufficientLiquidityMinted` since `calc_lp_amount_for_zero_supply` underflows against `T::MintMinLiquidity`. This mirrors the reported `StakingPool.donateTokens` bug: a pre-deposit donation permanently prevents any share/LP-token minting for that pool.

### Finding Description
`do_add_liquidity` at [2](#0-1)  reads `reserve1`/`reserve2` from `Self::get_balance(&pool_account, ...)`, i.e., the pool account's actual token balances [3](#0-2) . It branches on whether those reserves are zero:

```
if reserve1.is_zero() || reserve2.is_zero() {
    amount1 = amount1_desired;
    amount2 = amount2_desired;
} else {
    let amount2_optimal = Self::quote(&amount1_desired, &reserve1, &reserve2)?;
    ...
}
``` [4](#0-3) 

If an attacker transfers a small amount of `asset1` and a disproportionately large amount of `asset2` (or vice versa) straight to the pool account before any legitimate `add_liquidity` call, `reserve1` and `reserve2` become nonzero and heavily skewed, even though `total_supply` of the LP token is still `0`. Legitimate depositors are then forced into the `else` branch, where `quote` (`mul_div`) computes an "optimal" amount based on the attacker's ratio [5](#0-4) . Depending on the skew, this either overflows (`Error::Overflow`), fails the `amountXDepositDidNotMeetMinimum`/`OptimalAmountLessThanDesired` checks, or rounds one side to zero.

Even if a caller bypasses those checks by setting `amount1_min`/`amount2_min` to `0`, the resulting `amount1` or `amount2` can round to zero, and `calc_lp_amount_for_zero_supply` then computes `sqrt(amount1*amount2)` as `0`, then does `checked_sub(MintMinLiquidity)`, which underflows and returns `Error::InsufficientLiquidityMinted` [6](#0-5) . Because `total_supply` never becomes nonzero (no LP tokens are ever minted), the pool never exits this state — the poisoned reserve ratio is permanent and the failure recurs for every subsequent legitimate attempt.

The pallet does have a partial defense demonstrated by the `cannot_block_pool_creation` test [7](#0-6) , which shows the pool can still be *created* and liquidity added despite dust donations of unrelated assets to the pool account — but that test only donates small, non-skewing dust amounts of *other* asset IDs, not a deliberately extreme ratio of the exact `asset1`/`asset2` pair being pooled. It does not cover the ratio-skew griefing scenario against the two assets that actually form the pool's AMM reserves.

### Impact Explanation
This falls under "public underpriced work that degrades block production or stalls bridge processing" / permanent user-fund lock category, since it permanently prevents any liquidity provision for the targeted asset pair, rendering that pool unusable (a "permanent user-fund or bridge-state lock"-class DoS on the AMM). Any parachain or Asset Hub deployment relying on `pallet-asset-conversion` for its DEX functionality is exposed: an attacker only needs the ability to hold and transfer the two asset kinds and knowledge of the deterministic pool address, both of which are unprivileged, public capabilities.

### Likelihood Explanation
The pool account address is derivable ahead of pool creation/first liquidity add via `T::PoolLocator::address`/`pool_id`, which is a pure function of the asset pair, exactly like the `StakingPool`/`getSharesByStake` scenario where the vulnerable window is "before the first real deposit." No privileged role, governance, validator, or off-chain infrastructure is required — this is a plain unprivileged token-transfer griefing attack executable by any account holding a small balance of both assets, making it a high-likelihood public-entrypoint issue.

### Recommendation
Track pool reserves via internal pallet storage that is only updated by `do_add_liquidity`/`do_remove_liquidity`/swap execution paths, rather than trusting the raw on-chain balance of the pool account for AMM pricing. Alternatively, gate the zero-supply branch strictly on `total_supply.is_zero()` (not on `reserve1`/`reserve2` being zero) so that any pre-existing donated balance is absorbed into the first liquidity provider's minted share rather than being used to compute a poisoned quote ratio for the deposit path.

### Proof of Concept
1. Attacker computes the deterministic pool account for `(Native, AssetX)` via `T::PoolLocator::address`.
2. Before `create_pool`/first `add_liquidity`, attacker transfers `1` unit of `Native` and `u128::MAX/2` units of `AssetX` directly to that pool account (two plain `Balances::transfer`/`Assets::transfer` calls — no special call needed).
3. A legitimate user calls `create_pool` then `add_liquidity(Native, AssetX, amount1_desired, amount2_desired, amount1_min, amount2_min, ...)` with reasonable amounts and ratio.
4. Because `reserve1`/`reserve2` (attacker-donated) are nonzero and extremely skewed relative to the legitimate desired ratio, the `quote`/`mul_div` computation in `do_add_liquidity` either overflows or forces `amount1`/`amount2` toward zero, tripping `AssetOneDepositDidNotMeetMinimum`, `OptimalAmountLessThanDesired`, or (with `min=0`) `InsufficientLiquidityMinted` via the underflowing `calc_lp_amount_for_zero_supply` check. `total_supply` of the LP token remains `0` and the pool stays permanently unusable for `add_liquidity`, matching the reported `StakingPool` donation-DoS bug class.

		/// Add liquidity to a pool.
		pub(crate) fn do_add_liquidity(
			who: &T::AccountId,
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount1_desired: T::Balance,
			amount2_desired: T::Balance,
			amount1_min: T::Balance,
			amount2_min: T::Balance,
			mint_to: &T::AccountId,
		) -> Result<T::Balance, DispatchError> {
			let pool_id = T::PoolLocator::pool_id(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;

			ensure!(
				amount1_desired > Zero::zero() && amount2_desired > Zero::zero(),
				Error::<T>::WrongDesiredAmount
			);

			let pool = Pools::<T>::get(&pool_id).ok_or(Error::<T>::PoolNotFound)?;
			let pool_account =
				T::PoolLocator::address(&pool_id).map_err(|_| Error::<T>::InvalidAssetPair)?;

			let reserve1 = Self::get_balance(&pool_account, asset1.clone());
			let reserve2 = Self::get_balance(&pool_account, asset2.clone());

			let amount1: T::Balance;
			let amount2: T::Balance;
			if reserve1.is_zero() || reserve2.is_zero() {
				amount1 = amount1_desired;
				amount2 = amount2_desired;
			} else {
				let amount2_optimal = Self::quote(&amount1_desired, &reserve1, &reserve2)?;

				if amount2_optimal <= amount2_desired {
					ensure!(
						amount2_optimal >= amount2_min,
						Error::<T>::AssetTwoDepositDidNotMeetMinimum
					);
					amount1 = amount1_desired;
					amount2 = amount2_optimal;
				} else {
					let amount1_optimal = Self::quote(&amount2_desired, &reserve2, &reserve1)?;
					ensure!(
						amount1_optimal <= amount1_desired,
						Error::<T>::OptimalAmountLessThanDesired
					);
					ensure!(
						amount1_optimal >= amount1_min,
						Error::<T>::AssetOneDepositDidNotMeetMinimum
					);
					amount1 = amount1_optimal;
					amount2 = amount2_desired;
				}
			}

			ensure!(
				amount1.saturating_add(reserve1) >= T::Assets::minimum_balance(asset1.clone()),
				Error::<T>::AmountOneLessThanMinimal
			);
			ensure!(
				amount2.saturating_add(reserve2) >= T::Assets::minimum_balance(asset2.clone()),
				Error::<T>::AmountTwoLessThanMinimal
			);

			T::Assets::transfer(asset1, who, &pool_account, amount1, Preserve)?;
			T::Assets::transfer(asset2, who, &pool_account, amount2, Preserve)?;

			let total_supply = T::PoolAssets::total_issuance(pool.lp_token.clone());

			let lp_token_amount: T::Balance;
			if total_supply.is_zero() {
				lp_token_amount = Self::calc_lp_amount_for_zero_supply(&amount1, &amount2)?;
				T::PoolAssets::mint_into(
					pool.lp_token.clone(),
					&pool_account,
					T::MintMinLiquidity::get(),
				)?;
			} else {
				let side1 = Self::mul_div(&amount1, &total_supply, &reserve1)?;
				let side2 = Self::mul_div(&amount2, &total_supply, &reserve2)?;
				lp_token_amount = side1.min(side2);
			}

			ensure!(
				lp_token_amount > T::MintMinLiquidity::get(),
				Error::<T>::InsufficientLiquidityMinted
			);

			T::PoolAssets::mint_into(pool.lp_token.clone(), mint_to, lp_token_amount)?;

			Self::deposit_event(Event::LiquidityAdded {
				who: who.clone(),
				mint_to: mint_to.clone(),
				pool_id,
				amount1_provided: amount1,
				amount2_provided: amount2,
				lp_token: pool.lp_token,
				lp_token_minted: lp_token_amount,
			});

			Ok(lp_token_amount)
		}

		/// Calculates the optimal amount from the reserves.
		pub fn quote(
			amount: &T::Balance,
			reserve1: &T::Balance,
			reserve2: &T::Balance,
		) -> Result<T::Balance, Error<T>> {
			// (amount * reserve2) / reserve1
			Self::mul_div(amount, reserve2, reserve1)
		}

		pub(super) fn calc_lp_amount_for_zero_supply(
			amount1: &T::Balance,
			amount2: &T::Balance,
		) -> Result<T::Balance, Error<T>> {
			let amount1 = T::HigherPrecisionBalance::from(*amount1);
			let amount2 = T::HigherPrecisionBalance::from(*amount2);

			let result = amount1
				.checked_mul(&amount2)
				.ok_or(Error::<T>::Overflow)?
				.integer_sqrt()
				.checked_sub(&T::MintMinLiquidity::get().into())
				.ok_or(Error::<T>::InsufficientLiquidityMinted)?;

			result.try_into().map_err(|_| Error::<T>::Overflow)
		}

		fn mul_div(a: &T::Balance, b: &T::Balance, c: &T::Balance) -> Result<T::Balance, Error<T>> {
			let a = T::HigherPrecisionBalance::from(*a);
			let b = T::HigherPrecisionBalance::from(*b);
			let c = T::HigherPrecisionBalance::from(*c);

			let result = a
				.checked_mul(&b)
				.ok_or(Error::<T>::Overflow)?
				.checked_div(&c)
				.ok_or(Error::<T>::Overflow)?;

			result.try_into().map_err(|_| Error::<T>::Overflow)
		}

#[test]
fn cannot_block_pool_creation() {
	new_test_ext().execute_with(|| {
		// User 1 is the pool creator
		let user = 1;
		// User 2 is the attacker
		let attacker = 2;

		let ed = get_native_ed();
		assert_ok!(Balances::force_set_balance(RuntimeOrigin::root(), attacker, 10000 + ed));

		// The target pool the user wants to create is Native <=> WithId(2)
		let token_1 = NativeOrWithId::Native;
		let token_2 = NativeOrWithId::WithId(2);

		// Attacker computes the still non-existing pool account for the target pair
		let pool_account =
			<Test as Config>::PoolLocator::address(&(token_1.clone(), token_2.clone())).unwrap();
		// And transfers the ED to that pool account
		assert_ok!(Balances::transfer_allow_death(
			RuntimeOrigin::signed(attacker),
			pool_account,
			ed
		));
		// Then, the attacker creates 14 tokens and sends one of each to the pool account
		for i in 10..25 {
			create_tokens(attacker, vec![NativeOrWithId::WithId(i)]);
			assert_ok!(Assets::mint(RuntimeOrigin::signed(attacker), i, attacker, 1000));
			assert_ok!(Assets::transfer(RuntimeOrigin::signed(attacker), i, pool_account, 1));
		}

		// User can still create the pool
		create_tokens(user, vec![token_2.clone()]);
		assert_ok!(AssetConversion::create_pool(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone())
		));

		// User has to transfer one WithId(2) token to the pool account (otherwise add_liquidity
		// will fail with `AssetTwoDepositDidNotMeetMinimum`)
		assert_ok!(Balances::force_set_balance(RuntimeOrigin::root(), user, 10000 + ed));
		assert_ok!(Assets::mint(RuntimeOrigin::signed(user), 2, user, 10000));
		assert_ok!(Assets::transfer(RuntimeOrigin::signed(user), 2, pool_account, 1));

		// add_liquidity shouldn't fail because of the number of consumers
		assert_ok!(AssetConversion::add_liquidity(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone()),
			10000,
			100,
			10000,
			10,
			user,
		));
	});
}
