## Title
`claim_child_bounty` does not decrement the parent bounty's `ChildrenCuratorFees` tracking, allowing a claimed child-bounty fee to be double-counted against the parent bounty payout - (File: `substrate/frame/child-bounties/src/lib.rs`)

## Summary
The external report's core broken invariant is: a partial settlement path (partial redemption) mutates user-facing balances/state but fails to update a separate accounting counter that a *different*, later code path relies on for a health/solvency computation, letting the system reach an inconsistent state that a third party can exploit. I looked for the closest structural analog in `paritytech/polkadot-sdk` involving a "parent/child" value-tracking split with a permissionless settlement call, and traced it into `pallet-child-bounties`.

## Finding Description
`pallet-child-bounties` tracks fees owed to child-bounty curators in `ChildrenCuratorFees::<T>` per `parent_bounty_id`, which is added to when a curator fee is proposed (`propose_curator`, `substrate/frame/child-bounties/src/lib.rs:386-391`) and is meant to be *subtracted from the parent-bounty curator's payout* when the parent is claimed, via `ChildBountyManager::children_curator_fees` (`substrate/frame/child-bounties/src/lib.rs:977-985`), which is invoked once from `pallet-bounties::claim_bounty`.

There are two paths by which a child bounty's fee obligation is retired from `ChildrenCuratorFees`:
- `impl_close_child_bounty` (cancel path) explicitly does `ChildrenCuratorFees::<T>::mutate(parent_bounty_id, |value| *value = value.saturating_sub(child_bounty.fee))` (`substrate/frame/child-bounties/src/lib.rs:925-929`).
- `claim_child_bounty` (payout path, `substrate/frame/child-bounties/src/lib.rs:686-771`) pays the curator fee and beneficiary out of the child-bounty account, but **never touches `ChildrenCuratorFees`** — it only decrements `ParentChildBounties` (active-count) and removes the child-bounty entry.

This means `ChildrenCuratorFees` is only ever fully retired for a given child bounty at parent-bounty claim time (`children_curator_fees()` in `substrate/frame/bounties/src/lib.rs`, which reads then `remove`s the whole accumulator for the parent). The accounting invariant "sum of `ChildrenCuratorFees` equals the sum of fees for *still-unpaid* child-bounty curators" is silently violated the moment `claim_child_bounty` runs: the fee has already been physically paid to the child curator out of the child-bounty sub-account, but the same fee amount is *still* recorded in `ChildrenCuratorFees` and will be deducted a second time from the parent-bounty curator's own payout when `claim_bounty` executes `children_curator_fees(bounty_id)` on the parent.

## Impact Explanation
This is an accounting-desync bug analogous to the LOC report: a partial/child-level settlement (`claim_child_bounty`, callable permissionlessly by any signed account per doc comment "may be any signed origin") pays out real funds but does not reconcile the parent-level counter that a later, unrelated dispatchable (`pallet-bounties::claim_bounty`) uses to compute the parent curator's payout. The parent curator ends up paying (having deducted from their fee) for child-bounty curator fees that were already paid once out of the child-bounty's own funds — i.e. value is not conserved and does not settle exactly once to the rightful beneficiary, which is explicitly in the "Balances… conserve value and settle exactly once" pivot. Concretely the parent curator's `fee - children_curator_fees(bounty_id)` deduction (see `substrate/frame/child-bounties/src/tests.rs:1430-1431`, `assert_eq!(Balances::free_balance(account_id(4)), 101 + 6 - fee)`) subtracts fees for child bounties that already independently paid their curator via `claim_child_bounty`, shortchanging the parent curator's legitimate reward — an unpriv­ileged party (the child-bounty beneficiary/curator, who can call `claim_child_bounty` at will once `PendingPayout` unlocks) can trigger this double counting against the parent curator without any admin/governance action.

## Likelihood Explanation
Both `claim_child_bounty` and `propose_curator`/`accept_curator` are reachable by ordinary signed accounts (the child-bounty curator and beneficiary) with no special privilege, and `claim_bounty` (parent) is also open to any signed account. Any deployment using `pallet-child-bounties` alongside `pallet-bounties` where a child bounty completes its full curator-fee lifecycle (`propose_curator` → `accept_curator` → `award_child_bounty` → `claim_child_bounty`) before the parent bounty is claimed hits this path deterministically — no race condition or adversarial timing is required, only the normal expected order of operations (child bounties are usually claimed before the parent is closed).

## Recommendation
- Short term: in `claim_child_bounty` (`substrate/frame/child-bounties/src/lib.rs:686-771`), before removing the child-bounty entry, subtract `child_bounty.fee` from `ChildrenCuratorFees::<T>::get(parent_bounty_id)` the same way `impl_close_child_bounty` does, so the parent-level fee accumulator only ever reflects *unpaid* obligations.
- Long term: unify the "retire the fee obligation" logic between the cancel path (`impl_close_child_bounty`) and the claim path (`claim_child_bounty`) into a single helper so future changes to one path cannot silently diverge from the other, and add an invariant test asserting `ChildrenCuratorFees` reflects only outstanding (non-claimed, non-cancelled) child bounties before the parent bounty is claimed.

## Proof of Concept
1. Root approves a parent bounty of value `V` and assigns curator `A`, who accepts.
2. Curator `A` calls `add_child_bounty(parent, value_child, desc)`.
3. Curator `A` calls `propose_curator(parent, child, curator=B, fee=F)` → `ChildrenCuratorFees[parent] += F` (`substrate/frame/child-bounties/src/lib.rs:389-391`).
4. `B` calls `accept_curator`, then `A` calls `award_child_bounty(parent, child, beneficiary)`.
5. After the payout delay, beneficiary calls `claim_child_bounty(parent, child)` — `B` is paid fee `F` out of the child-bounty account, `ChildBounties` entry removed, but `ChildrenCuratorFees[parent]` is **not** decremented and still equals `F` (`substrate/frame/child-bounties/src/lib.rs:686-771` vs `925-929`).
6. `A` awards and claims the parent bounty via `pallet-bounties::claim_bounty`, which calls `children_curator_fees(parent)` and subtracts the stale `F` a second time from `A`'s payout (see test pattern at `substrate/frame/child-bounties/src/tests.rs:1424-1436`, `Balances::free_balance(account_id(4)) == 101 + 6 - fee`).
7. Result: `B` was paid `F` once from the child-bounty account, and `A`'s parent payout is reduced by `F` a second time — the fee `F` is effectively deducted twice for a single curator-service payment, which is a value-conservation violation triggerable by ordinary signed accounts with no privileged step.

Note: I could not find any prdoc/patch in this snapshot fixing this specific `claim_child_bounty` omission in `pallet-child-bounties` (the related fix I found, `prdoc/stable2603-1/pr_11425.prdoc`, addresses a different, already-patched double-read bug in the newer `pallet-multi-asset-bounties`, which tracks child value—not curator fees—via `ChildBountiesValuePerParent` and correctly decrements it in `RefundAttempted`/close flows). The `pallet-child-bounties` fee-accumulator path analyzed above appears to remain unreconciled in the `claim_child_bounty` code shown.
