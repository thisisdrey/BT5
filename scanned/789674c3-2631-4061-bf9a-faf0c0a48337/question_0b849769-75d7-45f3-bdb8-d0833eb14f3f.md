target: Transfer::execute_intent (contracts/defuse/core/src/intents/tokens.rs) and its call to engine.state.notify_on_transfer(sender_id, self.receiver_id, self.tokens, notification) when Transfer::notification is Some(NotifyOnTransfer). Attacker signs a Transfer intent with receiver_id = attacker-deployed contract R, tokens = {X: A}, notification = NotifyOnTransfer{msg:'reenter'}. Preconditions: signer has token_balances[signer][X] >= A; internal_sub_balance and internal_add_balance already committed A from signer to R inside Transfer::execute_intent BEFORE notify_on_transfer's promise resolves. Call sequence: engine.internal_sub_balance(sender_id) then internal_add_balance(receiver_id) run synchronously in-memory, then notify_on_transfer schedules an async mt_on_transfer promise to R; R's mt_on_transfer callback re-enters execute_intents with a NEW MultiPayload signed by the (now-credited) attacker account R spending the just-received A before mt_resolve_transfer can claw back any refund on failure. Binding: value debited from signer_id (A) == value delivered to receiver_id (A) plus value re-credited by the resolver on failure; if R spends A during its own mt_on_transfer callback and then the outer mt_transfer_call fails, mt_resolve_transfer's refund path finds receiver_id's token_balances already short by A, so the resolver refund silently mints an accounting gap. Scoped impact: Critical, signer's debited A is not recoverable while R has already respent it, breaking conservation (sum of token_balances deltas across the call != 0). Proof idea: sandbox test where R's on_mt_transfer callback issues a second signed intent spending the received funds, then simulate a downstream failure and assert mt_resolve_transfer's computed refund plus R's spent amount does not exceed the original A.
