# [C] Stuck ETH in Curve exchanges due to sending msg.value to the exchange instead of amountIn

## Summary
Severity: Critical
Contest weight: 0.0805
Dataset id: 15187
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability originates from an incorrect handling of the value transferred to Curve exchange contracts when a user attempts to swap assets using previously deposited ETH wrapped in note commitments. In the intended design, a user deposits ETH once, receives a note representing that deposit, and later calls the exchange function to trade the note for another asset without sending additional ETH. However, the implementation mistakenly forwards the transaction’s msg.value as the amount of ETH to be exchanged, even though the required amount (amountIn) has already been locked in the contract during the initial deposit. This mismatch causes the exchange call to accept an extra, unintended ETH payload that the contract does not forward or refund, effectively trapping the funds inside the exchange contract. The bug can be triggered by any user invoking the exchange function with a non‑zero msg.value, leading to the contract accepting the extra ETH and then having no logic to release it, so the user’s balance after the swap appears unchanged or zero while the transaction reports success. The impact is that users lose access to the ETH they unintentionally sent, resulting in missing balances, failed refunds, and overall erosion of trust in the protocol’s accounting guarantees. The condition under which this occurs is any swap operation that relies on note commitments after an initial deposit, where the wrapper contract forwards msg.value instead of the already‑recorded amountIn. The issue was discovered during a security audit that examined the flow of funds between the deposit and exchange steps and identified that the value parameter was not aligned with the protocol’s accounting model. Because the transaction does not revert and the contract does not emit explicit error messages, the problem can be subtle and may only be noticed when users observe that their ETH disappears after a seemingly successful swap. Conceptually, the bug belongs to the class of “incorrect value forwarding” or “double‑payment” vulnerabilities, where a contract erroneously requires an additional payment for an operation that should be free after a prior deposit. To remediate the issue, developers should replace the use of msg.value with the explicit amountIn variable when calling the exchange function, ensuring that only the intended amount of ETH is considered and that no extra funds are unintentionally locked. This correction restores the expected behavior where a user’s deposited ETH is used for the swap without requiring an extra transfer, aligning the contract’s logic with its financial assumptions and preventing funds from disappearing or becoming unrecoverable.

## Recommendation
Replace IExchange(exchangeContract).exchange{value: msg.value} by IExchange(exchangeContract).exchange{value: amountIn}.
