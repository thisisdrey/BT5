### Title
Liquidity pool reserves are read from live token balances, allowing direct-transfer "donation" to skew the LP mint ratio and steal a later provider's deposit — ([File: substrate/frame/asset-conversion/src/lib.rs])

### Summary
The Jet report's root cause is that a conversion rate between shares and tokens was derived from a mutable counter (`shares_bonded`) that any unprivileged user could change (via `unbond`) independently of the actual token balance, letting an attacker warp the rate before another user's action is priced against it. `pallet-asset-conversion` in this repository has the same structural weakness: the pool's "reserves" used to price LP-token minting/burning are not an internally accounted, mutation-gated value — they are read live from the pool account's actual asset balance via `Self::get_balance`/`Self::get_reserves`. Because any account can transfer assets directly into the pool account (bypassing `add_liquidity`), an attacker can inflate a reserve figure the pallet trusts for its ratio math without minting any LP tokens, then capture a disproportionate share of a subsequent depositor's contribution when removing liquidity.

`do_remove_liquidity` similarly prices a withdrawal against `Self::get_reserves`, and the amounts returned to the withdrawer are proportional to `lp_redeem_amount * reserve / total_supply`: [3](#0-2) 

The pallet does not maintain reserves as a value that is only updated atomically alongside LP-token issuance/burn (the way a correctly isolated accounting invariant would). Instead, `reserve1`/`reserve2` are exactly the pool account's current token balance, which any account can alter with an ordinary asset transfer that never touches `Pools`, `PoolAssets` (LP) issuance, or any of the pallet's extrinsics. This mirrors the Jet bug precisely: the value used in the conversion (`self.shares_bonded` there, `get_balance(pool_account, asset)` here) can be moved by an unprivileged actor through an action that is disjoint from the LP/points accounting that everyone else's math depends on. The pallet's own documentation implicitly acknowledges the resulting rate can become "incorrect": [4](#0-3) 
but that note is scoped to explaining a mitigation for *legitimate* imbalance, not to closing the underlying attacker primitive of directly donating tokens to bias the mint ratio in one's own favor ahead of a victim's deposit.

### Impact Explanation
An attacker who is first (or nearly first) into a pool can seed it with the smallest amount that clears `MintMinLiquidity`, then transfer a large amount of one asset directly to the pool account. When a subsequent honest liquidity provider calls `add_liquidity`, the `quote`/`mul_div` computations against the inflated reserve will assign that provider disproportionately few LP tokens relative to the pool value they contributed, or force them into a lopsided ratio. Because the attacker's existing (even minimal) LP-token holding represents a claim on `reserve * lp_burn / total_supply` at `remove_liquidity` time, and `reserve` now includes both the victim's freshly added liquidity and the attacker's earlier donation, the attacker can redeem for materially more value than they contributed — a direct value-conservation violation ("theft ... duplicate settlement or wrong beneficiary/amount" in the impact gate) against a fund-holding, publicly reachable pallet used on Asset Hub production chains.

### Likelihood Explanation
The exploit only requires two ordinary, permissionless actions available to any signed account: (1) `create_pool` + `add_liquidity` with a minimal amount, and (2) a plain asset transfer (via `pallet-assets`/`pallet-balances`) directly to the pool's derived account, which is a deterministic, publicly known address (`T::PoolLocator::address`). No admin, governance, validator, or off-chain actor is involved, and the pallet performs no check that `get_balance`/`get_reserves` match an internally tracked "expected" reserve before pricing a mint or burn.

### Recommendation
Track pool reserves as an internally accounted value that is updated only atomically with LP-token issuance/burn (mirroring the Jet patch's separation of bonded/unbonding pools with independent, gated accounting), rather than reading the pool account's live balance. Alternatively, on `add_liquidity`/`remove_liquidity`, reconcile any balance in excess of the tracked reserve to a neutral outcome (e.g., syncing it in via a permissionless "skim"/donation-absorbing call that mints LP fairly, or rejecting a mint if `get_balance != tracked_reserve`) so that unaccounted transfers cannot bias the mint/burn ratio for any depositor other than the party that already holds a proportional LP claim.

### Proof of Concept
1. Attacker calls `create_pool(asset1, asset2)` then `add_liquidity(asset1, asset2, amt1_desired=X, amt2_desired=Y, ...)` with the smallest `X, Y` that clears `InsufficientLiquidityMinted` (`lp_token_amount > MintMinLiquidity`). Attacker now holds `lp_token_amount` LP tokens; `total_supply = MintMinLiquidity + lp_token_amount`; pool reserves are `(X, Y)`.
2. Attacker performs a normal `pallet-assets`/`pallet-balances` `transfer` of a large amount `D` of `asset1` directly to the pool account (`T::PoolLocator::address(pool_id)`), bypassing `AssetConversion` entirely. Reserve1 is now `X + D`, while `total_supply` is unchanged.
3. Victim calls `add_liquidity(asset1, asset2, amt1_desired, amt2_desired, ...)` with reasonable amounts. Because `quote`/`mul_div` price against the inflated `reserve1`, the LP tokens minted to the victim (`side1.min(side2)`) undervalue their real contribution relative to the pool's true worth.
4. Attacker calls `remove_liquidity` burning their original `lp_token_amount`; the returned `amount1 = lp_redeem_amount * reserve1 / total_supply` now reflects a reserve inflated by both the donation `D` and the victim's newly added liquidity, yielding the attacker more value than deposited — extracted directly from the victim's contribution.
