## Analysis

The external report's core broken invariant is: **a caller assumes a fixed, small gas allowance passed to a callee is sufficient to prevent that callee from re-entering / making further calls, but the runtime's actual gas/resource accounting does not honor that assumption**, allowing reentrancy or unexpected resource consumption. The local Polkadot SDK analog for this exists in `pallet-revive`'s EVM-compatibility layer, where a real "2300-gas stipend equals no further calls" guarantee from Ethereum is reproduced only for one narrow case, leaving the far more common non-zero-value low-gas call pattern unprotected.

### Title
Non-zero-value EVM calls with an explicit low `gas_limit` (e.g. the classic `call{value: x, gas: 2300}("")` anti-reentrancy pattern) are unconditionally granted `AllowReentry` and an unearned stipend in `pallet-revive`'s EVM interpreter - (File: `substrate/frame/revive/src/vm/evm/instructions/contract.rs`)

### Summary
`run_call` in the EVM instruction interpreter decides reentrancy protection using a heuristic keyed off `value.is_zero()` and `gas_limit == CALL_STIPEND (2300)`. Any call transferring non-zero value — including one explicitly capped at `gas: 2300` by the calling contract as a deliberate anti-reentrancy defense (a widely used and ported Solidity pattern) — falls into the `(false, _)` match arm and is unconditionally given `ReentrancyProtection::AllowReentry` plus an *additional* stipend on top of the caller-specified gas, exactly the opposite of the caller's intent and of real EVM gas-stipend semantics.

### Finding Description
In `substrate/frame/revive/src/vm/evm/instructions/contract.rs`: [1](#0-0) 

```rust
let (add_stipend, reentracy) =
    match (value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND))
    {
        (false, _) => (true, ReentrancyProtection::AllowReentry),
        // Heuristic: detect when solc passes `gas_limit = 2300` (the call stipend).
        (_, true) => (true, ReentrancyProtection::AllowNext),
        (_, _) => (false, ReentrancyProtection::AllowReentry),
    };
```

The comment and the accompanying fixture/tests (`substrate/frame/revive/fixtures/contracts/Stipends.sol` and `prdoc/stable2603/pr_11227.prdoc`) make clear the *only* case the maintainers hardened against reentrancy is the **zero-value** `transfer(0)`/`send(0)` compiler-injected `gas=2300` pattern: [2](#0-1) 

The documented rationale for needing this special-case guard at all is explicit in the design PR: [3](#0-2) 

> "Re-entrancy protection now has three modes... `AllowNext` allows to re-enter the same contract but only for the next frame. This is required to implement reentrancy protection for simple transfers with call stipends"

This shows the team recognized that on `pallet-revive`'s weight/deposit gas scale, a "2300 Ethereum-gas equivalent" budget is **not** naturally insufficient to make a further external call the way it is on real Ethereum — hence the need for an explicit `ReentrancyProtection::AllowNext` flag to emulate that guarantee.

However, this explicit protection is only reached via the second match arm, which requires `value.is_zero() == true`. Any call that transfers non-zero value — **regardless of how small `gas_limit` is set, including exactly `2300`** — takes the first arm `(false, _)` and receives `ReentrancyProtection::AllowReentry` (no restriction at all) plus `add_stipend = true` (an *additional* 2300-gas-equivalent weight budget stacked on top of whatever gas the caller specified): [4](#0-3) 

A large class of real Solidity contracts (ported/deployed on revive via `pallet_revive::Config::AllowEVMBytecode`) use the manual low-level pattern `target.call{value: amount, gas: 2300}("")` as a deliberate, still-common anti-reentrancy guard (an alternative to `.transfer()`/`.send()` that gives the same intended gas ceiling but explicit control). On `pallet-revive`, that exact call is misclassified: it is treated identically to an ordinary `call{value: amount}("")` that forwards *all* remaining gas — full `AllowReentry` — even though the developer's on-chain bytecode explicitly requested a minimal, stipend-only gas budget specifically to prevent the callee from reentering.

Existing guards do not stop this path because:
- `charge_call_gas` / `CallResources::from_ethereum_gas` only convert the specified gas value into a weight/deposit ceiling; they do not independently verify or restrict reentrancy — that logic lives solely in the `run_call` match shown above.
- The `(false, _)` arm is evaluated *before* the `gas_limit == CALL_STIPEND` check can apply, so no amount of gas-limiting by the caller when `value != 0` can trigger the `AllowNext` restriction; the only way to get restricted reentrancy is to pass `value == 0`.
- The frame-meter-based stipend (`determine_call_stipend`) is computed to intentionally be *just* enough to also process a `DepositEvent`, i.e., it is calibrated to allow a small amount of extra computation — not to be provably insufficient for a nested call, unlike genuine EVM 2300 gas. Combined with `AllowReentry`, the callee has both extra budget and no reentry barrier.

### Impact Explanation
Contracts relying on the manual "cap gas at 2300, send value via low-level `call`" defensive pattern to block reentrancy (a legitimate and still-encountered Solidity idiom, and the very remediation direction implied by the external report's "use `call()` instead of `transfer()`" recommendation) silently lose that protection when deployed on `pallet-revive`. An attacker-controlled receiving contract can reenter the caller during the callback and drain balances/state that the original contract logic assumed were safe from reentrancy due to the low gas cap — a direct fund-theft / unbacked-withdraw primitive matching the "theft or unbacked mint/unlock" impact bucket for a public, unprivileged entrypoint (any deployed EVM contract making value-bearing calls), with no malicious validator/collator/relayer required.

### Likelihood Explanation
High for any EVM contract ported to `pallet-revive` that uses this idiom. No special privileges are needed — this triggers on ordinary contract-to-contract calls during normal transaction execution, purely as a consequence of `run_call`'s match arm ordering. The bug is deterministic and reproducible for every non-zero-value call regardless of the caller-supplied `gas_limit`.

### Recommendation
In `run_call` (`substrate/frame/revive/src/vm/evm/instructions/contract.rs`), evaluate the `gas_limit == CALL_STIPEND` heuristic independent of `value.is_zero()`. Any call — zero or non-zero value — whose `gas_limit` equals `CALL_STIPEND` should receive `ReentrancyProtection::AllowNext`; only calls that forward gas materially above the stipend threshold should receive `AllowReentry`. This restores parity with the documented Ethereum-emulation intent stated in `pr_10166.prdoc`.

### Proof of Concept
1. Deploy (via `Code::Upload` EVM bytecode) a `Victim` contract with a `withdraw(uint amount)` function that follows the recommended defensive pattern: `(bool ok,) = msg.sender.call{value: amount, gas: 2300}("");` after debiting internal balance.
2. Deploy an `Attacker` contract whose `receive()`/fallback calls back into `Victim.withdraw(...)` before the outer call returns.
3. Call `Victim.withdraw()` from `Attacker`. In `run_call`, since `value != 0`, the match takes `(false, _)` → `ReentrancyProtection::AllowReentry` is granted regardless of the `gas: 2300` cap set in the bytecode.
4. `Attacker`'s callback successfully reenters `Victim.withdraw()` (unlike on real Ethereum, where the 2300 stipend would make the reentrant call run out of gas), allowing multiple withdrawals against a balance debited only once, draining more funds than `Attacker`'s recorded balance — analogous to the existing `testTransferReentrancy`/`testSendReentrancy` fixtures in `Stipends.sol`, except triggered via the non-zero-value + explicit-`gas:2300` path that those fixtures do not cover.
