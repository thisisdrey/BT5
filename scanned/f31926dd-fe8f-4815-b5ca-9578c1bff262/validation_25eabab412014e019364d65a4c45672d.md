## Analog Identified: Snowbridge V2 outbound `AliasOrigin` allow-list only denies AssetHub — every other parachain/consensus agent identity remains forgeable via the known `InitiateTransfer`/`ClearOrigin` origin-leak

### Title
Snowbridge outbound-queue-v2 `AliasOrigin` filter only blacklists AssetHub, letting an unprivileged caller forge any *other* chain's Ethereum agent identity - (File: `bridges/snowbridge/primitives/outbound-queue/src/v2/converter/mod.rs`)

### Summary
The Arbitrum report's core defect is that a security-relevant identity check (`onlyOperator`) is bound to a *representation* of an address that an attacker/protocol layer can manipulate (L1→L2 aliasing), so the wrong entity ends up being treated as (or blocked from being) the authorized party. The Polkadot-SDK analog is in the Snowbridge V2 outbound converter: the identity that is exported to Ethereum and used to derive the `AgentId` that authorizes `Transact` execution on the Gateway/Agent contract is taken from an XCM `AliasOrigin` instruction. A prior fix (`pr_12159`) added a filter, but the filter only excludes the single `AssetHubLocation`, not the class of privileged/foreign origins that the underlying primitive (a documented XCM executor origin-leak) allows to be forged.

### Finding Description
The V2 `EthereumBlobExporter`/`XcmConverter::validate()` requires an `AliasOrigin(Origin)` instruction to be present in the routed XCM and treats that `Origin` as the authoritative identity for the message [1](#0-0) . This location is later hashed via `AgentIdOf::convert_location` to produce the `AgentId` that governs the corresponding Agent contract on Ethereum (the entity permitted to have `Transact` executed on its behalf) [2](#0-1) .

`pr_12159` was merged specifically because this `AliasOrigin` value could be *forged* by a signed AssetHub user via a known XCM executor bug: clearing the origin register and then using `InitiateTransfer { preserve_origin: true, ... }` causes the executor to export the remote program without prepending any origin-altering instruction, so an attacker-supplied `AliasOrigin(...)` inside `remote_xcm` is accepted as-is (documented at the linked forum post-mortem) [3](#0-2) . The fix that was applied is narrow: it only blocks `AliasOrigin(AssetHubLocation)`, i.e. `AllowedAliasOrigin = EverythingBut<Equals<AssetHubLocation>>` [4](#0-3) , and the unit test that validates the fix only exercises the AssetHub case, returning `XcmConverterError::InvalidOrigin` [5](#0-4) , while every other Location — e.g. `Location::new(1,[GlobalConsensus(Polkadot),Parachain(1000)])` — is explicitly proven to still `convert()` successfully with an arbitrary `AliasOrigin` [6](#0-5) .

The root-cause primitive (the `ClearOrigin` + `InitiateTransfer{preserve_origin:true}` origin leak) is not fixed at the XCM-executor level in this repository snapshot; it is only mitigated for the single most valuable target. Any AssetHub-signed account can still build the identical forged XCM but substitute `AliasOrigin` with the location of any *other* sibling parachain, System chain, or arbitrary consensus location (anything not equal to `AssetHubLocation`). That forged location is accepted by the `EverythingBut<Equals<AssetHubLocation>>` filter, is hashed into a real `AgentId`, and is exported to the Ethereum Gateway, causing the corresponding Agent contract to execute the attacker's `ContractCall`/`Transact` payload as if it originated from the impersonated chain.

This exactly mirrors the Arbitrum bug class: an address/origin *representation* used for a privileged check (`onlyOperator`, here "is this AliasOrigin allowed to act as the exported identity") is bound to an incomplete/hardcoded comparison rather than to the actual security invariant ("only the genuine, currently-executing origin may alias itself"), so an attacker can manipulate that representation to seize a privilege that should never have been reachable from an unprivileged, signed extrinsic.

### Impact Explanation
Any signed AssetHub account can impersonate the Ethereum-side agent of any other Polkadot/Kusama-connected parachain (or other consensus system) that bridges through this exporter, since only the AssetHub agent is excluded. This is unauthorized execution/origin escalation with direct on-chain consequence on the Ethereum side: arbitrary `Transact`/`ContractCall` execution under a forged agent identity, which can drain or misuse funds/permissions held by that Agent contract, and duplicate/mis-bound settlement of bridge messages under the wrong sender. This falls squarely under "unauthorized execution or origin escalation" and "theft or unbacked mint or unlock" in the live-scope impact gate, requiring no privileged/governance actor, malicious relayer, or validator — only a normal signed extrinsic on AssetHub.

### Likelihood Explanation
The precondition (the `ClearOrigin`+`InitiateTransfer{preserve_origin:true}` origin leak) is already demonstrated as exploitable and reachable from a plain signed origin in this codebase's own regression test [7](#0-6) . The only thing standing between "AssetHub agent forgeable" (already fixed) and "any other agent forgeable" (still open) is the single-location denylist in `AllowedAliasOrigin`. No additional capability, timing, or trust assumption is required beyond what the already-accepted-as-valid fix (`pr_12159`) itself required.

### Recommendation
Change `AllowedAliasOrigin` from an exclusion-based allowlist (`EverythingBut<Equals<AssetHubLocation>>`) to an inclusion-based allowlist that only permits `AliasOrigin` values which structurally match the actual, verified sending origin of the XCM being exported (i.e., derive the expected `AliasOrigin` from the `universal_source`/`origin` register rather than trusting a user-suppliable instruction), or fix the underlying XCM executor `InitiateTransfer`/`ClearOrigin` origin-leak so `preserve_origin` cannot be defeated in the first place. Add regression tests exercising forged `AliasOrigin` values for sibling parachains and other system chains, not just `AssetHubLocation`.

### Proof of Concept
1. On AssetHub, as any signed account, execute an XCM (via `pallet_xcm::execute`) containing:
   - `WithdrawAsset` for local + remote fee assets, `PayFees`, `ClearOrigin`.
   - `InitiateTransfer { destination: ethereum(), preserve_origin: true, remote_xcm: [ AliasOrigin(Location::new(1, Parachain(VICTIM_PARA_ID))), DepositAsset{..}, Transact{ origin_kind: Xcm, call: <attacker ContractCall> }, SetTopic(..) ] }`
   as in `signed_assethub_user_cannot_bypass_origin_alteration_when_routing_to_ethereum` but replacing `forged_assethub_origin` with any `Location` other than `AssetHubLocation` (e.g., `Location::new(1,[Parachain(2000)])`) [8](#0-7) .
2. Because `AllowedAliasOrigin = EverythingBut<Equals<AssetHubLocation>>` only rejects the exact AssetHub location, `XcmConverter::convert()` succeeds (as proven generically by `xcm_converter_convert_success` using an arbitrary non-AssetHub `AliasOrigin`) [9](#0-8) .
3. The message is committed to `snowbridge_pallet_outbound_queue_v2::Messages` and delivered to Ethereum, where the Gateway derives the `AgentId` from `Parachain(VICTIM_PARA_ID)`'s location and executes the attacker's `Transact` under that agent's authority — impersonating the victim parachain on Ethereum.

#[test]
pub fn signed_assethub_user_cannot_bypass_origin_alteration_when_routing_to_ethereum() {
	fund_on_bh();
	fund_on_ah();

	let forged_assethub_origin = Location::new(1, [Parachain(AssetHubWestend::para_id().into())]);
	let expected_assethub_agent = AgentIdOf::convert_location(&forged_assethub_origin).unwrap();
	assert_eq!(
		expected_assethub_agent,
		hex!("81c5ab2571199e3188135178f3c2c8e2d268be1313d029b30f534fa579b69b79").into()
	);

	AssetHubWestend::execute_with(|| {
		type RuntimeOrigin = <AssetHubWestend as Chain>::RuntimeOrigin;

		let local_fee_asset =
			Asset { id: AssetId(Location::parent()), fun: Fungible(LOCAL_FEE_AMOUNT_IN_DOT) };

		let remote_fee_asset =
			Asset { id: AssetId(ethereum()), fun: Fungible(REMOTE_FEE_AMOUNT_IN_ETHER) };

		let arbitrary_agent_call = ContractCall::V1 {
			target: ETHEREUM_DESTINATION_ADDRESS,
			calldata: vec![0xde, 0xad, 0xbe, 0xef],
			value: 0,
			gas: 100_000,
		};

		let assets = vec![local_fee_asset.clone(), remote_fee_asset.clone()];
		let forged_xcm = Xcm(vec![
			WithdrawAsset(assets.into()),
			PayFees { asset: local_fee_asset },
			// Clear the origin register to None. Under the logic flaw in the XCM executor's
			// InitiateTransfer implementation (with preserve_origin: true), this causes the
			// executor to export the message without prepending any origin-altering instructions.
			// Details: https://forum.polkadot.network/t/postmortem-xcm-initiatetransfer-origin-leak/17357
			ClearOrigin,
			InitiateTransfer {
				destination: ethereum(),
				remote_fees: Some(AssetTransferFilter::ReserveWithdraw(Definite(
					remote_fee_asset.into(),
				))),
				preserve_origin: true,
				assets: BoundedVec::truncate_from(vec![]),
				remote_xcm: Xcm(vec![
					AliasOrigin(forged_assethub_origin),
					DepositAsset { assets: Wild(AllCounted(0)), beneficiary: beneficiary() },
					Transact {
						origin_kind: OriginKind::Xcm,
						call: arbitrary_agent_call.encode().into(),
						fallback_max_weight: None,
					},
					SetTopic([9u8; 32]),
				]),
			},
		]);

		assert_ok!(<AssetHubWestend as AssetHubWestendPallet>::PolkadotXcm::execute(
			RuntimeOrigin::signed(AssetHubWestendSender::get()),
			bx!(VersionedXcm::from(forged_xcm)),
			Weight::from(EXECUTION_WEIGHT),
		));
	});
