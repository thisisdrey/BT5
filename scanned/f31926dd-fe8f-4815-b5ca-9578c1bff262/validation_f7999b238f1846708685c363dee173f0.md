This is a direct, exact local analog of the reported bug class: the reward payout is silently capped/truncated to whatever the funding source can afford, and the shortfall is permanently lost with no bookkeeping to recover it later, exactly like `RewardDistributor.sol`'s `if (amount > balance) { amount = balance; }` pattern.

### Title
Relayer reward silently truncated and permanently lost when parachain sovereign account is underfunded - (`bridges/snowbridge/pallets/inbound-queue/src/lib.rs`)

### Summary
In `snowbridge-pallet-inbound-queue`'s `submit` extrinsic, the relayer reward for delivering an Ethereum→Substrate message is capped to whatever `reducible_balance` the destination parachain's sovereign account currently holds. If the sovereign account balance is less than the calculated `delivery_cost`, the relayer is paid only the reduced amount (or nothing), and the shortfall is neither tracked nor made recoverable when the sovereign account is later refunded.

### Finding Description
`submit()` computes `delivery_cost` via `Self::calculate_delivery_cost(...)` and then does: [1](#0-0) 

```rust
let sovereign_account = sibling_sovereign_account::<T>(channel.para_id);
let delivery_cost = Self::calculate_delivery_cost(event.encode().len() as u32);
let amount = T::Token::reducible_balance(
    &sovereign_account,
    Preservation::Preserve,
    Fortitude::Polite,
)
.min(delivery_cost);
if !amount.is_zero() {
    T::Token::transfer(&sovereign_account, &who, amount, Preservation::Preserve)?;
}
```

This is functionally identical to the reported `RewardDistributor.sol` bug: `amount = amount.min(available_balance)` and any deficit between the intended reward (`delivery_cost`) and the amount actually transferred is discarded — there is no storage entry, ledger, or "IOU" recorded for the difference, and no mechanism exists to top up the relayer later once the sovereign account is refunded. The pallet's own test suite documents this as intended behavior rather than a bug: [2](#0-1) 

The prior `pr_3761.prdoc` explicitly confirms the design intent — "If the AH sovereign account is depleted and relayer rewards cannot be paid, the message should still be processed" — i.e., message delivery proceeds unconditionally while reward payment is best-effort and lossy: [3](#0-2) 

By contrast, the newer `snowbridge-pallet-inbound-queue-v2` pallet fixed this exact class of loss by moving to a `register_reward` ledger (`RewardPayment::register_reward`) that accrues a claimable balance rather than doing an immediate, balance-capped transfer: [4](#0-3) 

This confirms v1's approach (immediate best-effort transfer capped to current balance, no bookkeeping) is the vulnerable pattern, and it is still live in the v1 pallet used by production bridge-hub runtimes.

### Impact Explanation
Relayers who perform real, useful work (submitting valid, verified Ethereum event proofs) can receive less than their entitled `delivery_cost`, or nothing at all, whenever the destination parachain's sovereign account is momentarily underfunded — a state that is common and outside relayer control (dependent on parachain treasury/XCM fee inflows). Because the deficit is never recorded, it can never be paid out even after the sovereign account is topped up, resulting in permanent, unrecoverable relayer fund loss. Since relayer compensation is the entire economic incentive keeping the bridge's inbound message flow running, systematic underfunding degrades relayer participation and can stall inbound Snowbridge message processing — directly matching the "public underpriced work that degrades... stalls bridge processing" impact category.

### Likelihood Explanation
This requires no privileged actor, governance, relayer collusion, or malicious component. Any ordinary relayer, submitting entirely legitimate messages through the standard, unprivileged `submit` extrinsic, is exposed whenever the sovereign account balance dips below the computed delivery cost — a state that naturally occurs under normal bridge load. The relevant test (`test_submit_no_funds_to_reward_relayers_just_ignore`) shows the team is aware submission succeeds even at zero available reward, and the ED-preservation test shows partial/reduced payouts are also possible.

### Recommendation
Implement bookkeeping (a reward ledger keyed by relayer, similar to what `inbound-queue-v2`/`pallet-bridge-relayers` already do via `RewardLedger::register_reward`/`claim_rewards`) so that any shortfall between `delivery_cost` and the amount actually transferable from the sovereign account is recorded as an outstanding, claimable amount rather than discarded, and provide a mechanism to settle it once the sovereign account is replenished. At minimum, document this loss behavior in public-facing relayer documentation, consistent with what the original report recommended for `RewardDistributor.sol`.

### Proof of Concept
1. Deploy/observe `snowbridge-pallet-inbound-queue` on a bridge-hub runtime where a parachain's sovereign account (`sibling_sovereign_account::<T>(channel.para_id)`) holds less than `Self::calculate_delivery_cost(...)`.
2. A relayer submits a valid `EventProof` via `submit()`. Verification, nonce check, and XCM forwarding all succeed.
3. `T::Token::reducible_balance(...).min(delivery_cost)` yields an amount smaller than `delivery_cost` (or zero if the sovereign account is at/near existential deposit, as in `test_submit_no_funds_to_reward_relayers_and_ed_preserved` [5](#0-4) ).
4. The relayer is paid only the truncated `amount`; the message is still marked processed (nonce incremented) and forwarded via XCM.
5. The sovereign account is later refunded (e.g., via XCM fee income). No storage in this pallet retains any record of the prior shortfall for this relayer/nonce, so the lost reward difference can never be reclaimed — permanent fund loss for the relayer, with no owner/governance intervention required to trigger it.

#[test]
fn test_submit_no_funds_to_reward_relayers_and_ed_preserved() {
	new_tester().execute_with(|| {
		let relayer: AccountId = Keyring::Bob.into();
		let origin = RuntimeOrigin::signed(relayer);

		// Reset balance of sovereign account to (ED+1) first
		let sovereign_account = sibling_sovereign_account::<Test>(ASSET_HUB_PARAID.into());
		Balances::set_balance(&sovereign_account, ExistentialDeposit::get() + 1);

		// Submit message successfully
		let event = EventProof {
			event_log: mock_event_log(),
			proof: Proof {
				receipt_proof: Default::default(),
				execution_proof: mock_execution_proof(),
			},
		};
		assert_ok!(InboundQueue::submit(origin.clone(), event.clone()));

		// Check balance of sovereign account to ED
		let amount = Balances::balance(&sovereign_account);
		assert_eq!(amount, ExistentialDeposit::get());

		// Submit another message with nonce set as 2
		let mut event_log = mock_event_log();
		event_log.data[31] = 2;
		let event = EventProof {
			event_log,
			proof: Proof {
				receipt_proof: Default::default(),
				execution_proof: mock_execution_proof(),
			},
		};
		assert_ok!(InboundQueue::submit(origin.clone(), event.clone()));
		// Check balance of sovereign account as ED does not change
		let amount = Balances::balance(&sovereign_account);
		assert_eq!(amount, ExistentialDeposit::get());
	});
}
