## Title
Snowbridge inbound-queue `submit` lets a relayer‑controlled, unvalidated `fee`/`weight_limit` decouple the on‑chain XCM execution cost from the price actually paid, enabling public underpriced work against BridgeHub/AssetHub - ([File: bridges/snowbridge/primitives/inbound-queue/src/v1.rs])

### Summary
The SEDA bug is a single broken invariant: a public entrypoint lets the caller choose the *price* for work (`gas_price`) independently of the *amount* of work requested (`exec_gas_limit`/`tally_gas_limit`), so `required = limit * price` can be minimized while the resource consumption dictated by `limit` is spent later at network expense. The closest local analog is `MessageToXcm::convert` in Snowbridge's inbound queue, which builds the destination‑chain XCM `BuyExecution { fees, weight_limit }` entirely from an Ethereum‑supplied `fee: u128` field with **`weight_limit: Unlimited`**, and never checks that `fee` is sufficient to cover the actual weight of the `Transact`/`DepositReserveAsset` program it constructs.

### Finding Description
`snowbridge_pallet_inbound_queue::Pallet::submit` (`bridges/snowbridge/pallets/inbound-queue/src/lib.rs:237-311`) is a `ensure_signed` extrinsic that any relayer can call with an `EventProof` from Ethereum. After verifying the Merkle/consensus proof and nonce, it decodes the payload into a `VersionedMessage` and calls `Self::do_convert` → `T::MessageConverter::convert`, i.e. `MessageToXcm::convert` (`bridges/snowbridge/primitives/inbound-queue/src/v1.rs:179-204`).

For every command (`RegisterToken`, `SendToken`, `SendNativeToken`) the converter takes an attacker/Ethereum‑controlled `fee: u128` value straight from the decoded message and inserts it into `BuyExecution { fees: xcm_fee, weight_limit: Unlimited }` (lines 244/261, 307/337, 416/444). Because `weight_limit` is `Unlimited`, the XCM executor's `WeightTrader::buy_weight` is invoked with the *actual* computed weight of the message (e.g. the `Transact` with `fallback_max_weight: Some(Weight::from_parts(400_000_000, 8_000))` for asset creation, or a full `DepositReserveAsset`/nested XCM send for `SendToken`), not a weight bounded by `fee`. `UsingComponents::buy_weight` (`polkadot/xcm/xcm-builder/src/weight.rs:365-391`) will reject the message with `XcmError::TooExpensive` only if `fee` cannot cover `WeightToFee::weight_to_fee(&weight)` for the *fees asset actually supplied in the message* — but nothing on the inbound-queue side validates that `fee` is not degenerate (e.g. `0` or `1`) *before* the message is accepted and dispatched into `MessageQueue`/XCM processing on BridgeHub, and before `Self::calculate_delivery_cost` charges the relayer only a fixed, benchmarked weight (`T::WeightInfo::submit()`), not the cost of the downstream cross-chain execution it triggers.

Concretely: the fixed extrinsic weight annotated on `submit` (`#[pallet::weight(T::WeightInfo::submit())]`, `bridges/snowbridge/pallets/inbound-queue/src/lib.rs:236`) only covers the local decode/verify/nonce/XCM-send cost on the sending chain. It does **not** account for, or gate on, the weight of the `Transact`/reserve-transfer instructions the converted XCM will consume on AssetHub/the destination parachain — that cost is supposed to be paid for entirely out of the attacker-controlled `fee` field carried inside the message, and `weight_limit: Unlimited` means the trader will happily attempt to buy exactly as much weight as the message needs, only failing after the `MessageQueue` has already dequeued and started processing it. This is structurally the same defect as SEDA's `post_request`: the amount of work (weight consumed downstream) is set independently from, and larger than, the price actually charged, with no floor enforced by the entrypoint accepting the request.

### Impact Explanation
Because Ethereum-side message construction is fully attacker-controlled (any address can call the real Gateway contract, or — more importantly — this is the exact multiplication vector the SEDA report describes: cheap requests that make validators do expensive work), a message can be crafted with a minimal `fee` (e.g. `fee = 1`) while the resulting XCM (`Transact` with an 8KB proof-size fallback weight, or a `DepositReserveAsset` forwarding to another parachain) still gets dispatched into the destination chain's `MessageQueue`. `BuyExecution`'s `Unlimited` weight_limit means the executor will attempt to charge whatever the true weight is; if the fee-paying asset covers *part* of it via `UsingComponents`/`TakeFirstAssetTrader` rounding or partial matches, or if the trader implementation used on that chain does not hard-fail (chain-specific `Trader` composition), work is executed against the fee-payer chain even where the amount actually collected is nominal, since there is no check inside `MessageToXcm::convert` itself that `fee` is anywhere near proportional to the weight of the instructions it is about to emit — the safety net is entirely delegated to the destination chain's `WeightTrader`, and the inbound-queue pallet itself charges only a fixed local weight for accepting and forwarding the message. This mirrors the SEDA impact: repeated cheap submissions can consume MessageQueue/XCM-executor CPU and storage-write budget on BridgeHub/AssetHub disproportionate to what was paid, degrading block production for the affected parachain(s).

### Likelihood Explanation
Medium. It requires control over messages accepted by `T::Verifier` (i.e. a legitimate, consensus-proof-backed Ethereum Gateway message — this is not "malicious relayer" since the relayer merely forwards proofs; the attacker is whoever controls the Ethereum-side call to the Gateway contract, an ordinary Ethereum user), and it depends on the specific `Trader`/`WeightToFee` configuration on the destination chain not defensively rejecting near-zero fees before consuming weight. This is exactly the "public underpriced work degrading block production" impact class called out in the assignment.

### Recommendation
- In `MessageToXcm::convert` (and its `convert_register_token`/`convert_send_token`/`convert_send_native_token` helpers), replace `weight_limit: Unlimited` with a `weight_limit: Limited(weight)` bound computed from the actual weight of the emitted instructions (analogous to `T::FeeInfo`/`WeightToFee` used elsewhere in the codebase), and reject conversion if `fee` does not cover `WeightToFee::weight_to_fee(&weight)` for that bounded weight.
- Add an explicit minimum-fee/minimum-fee-per-weight check in `snowbridge_pallet_inbound_queue::Pallet::submit` before calling `send_xcm`, rejecting messages whose declared `fee` cannot plausibly cover the weight of the command being executed (mirroring the SEDA fix of requiring a floor price proportional to declared work).

### Proof of Concept
Not executable from static analysis alone (would require constructing a signed Ethereum Gateway event with `Command::SendToken { fee: 1, .. }` or `Command::RegisterToken { fee: 1, .. }`, a valid consensus proof accepted by `T::Verifier`, and a destination-chain `Trader` configuration that does not hard-fail on the resulting `BuyExecution`). No PoC was run against this repository; this is a static code-path finding based on `bridges/snowbridge/primitives/inbound-queue/src/v1.rs:244-461` and `bridges/snowbridge/pallets/inbound-queue/src/lib.rs:237-349`, and should be validated by a Devin session that can spin up the Snowbridge integration test harness (`bridges/snowbridge/pallets/inbound-queue/src/test.rs`) and submit a low-`fee` `SendToken`/`RegisterToken` message to confirm whether the destination `Trader` rejects or accepts it, and measure the weight actually consumed relative to `fee` charged.

**Uncertainty note:** I was not able to fully confirm, from the indexed code alone, which concrete `WeightTrader` (e.g. `UsingComponents`, `TakeFirstAssetTrader`, or a tuple of these) is configured for the AssetHub/BridgeHub runtimes that receive these specific Snowbridge XCMs, nor whether governance-configured `PricingParameters`/`ByteFee` elsewhere in the router pipeline (e.g. `xcm-bridge-hub-router`) impose an additional floor that would block this in practice. This should be verified directly in the runtime configuration (`cumulus/parachains/runtimes/bridge-hubs/*/src/bridge_to_ethereum_config.rs` and the corresponding AssetHub XCM `Trader` config) before treating this as a confirmed, exploitable bug rather than a design-level gap.
