### Title
Irreversible tip burn before destination-side validation causes permanent, unrecoverable user fund loss in `snowbridge-pallet-system-frontend::add_tip` - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

### Summary
The external report's core broken invariant is: a user is documented/expected to pay a bounded, recoverable amount for a service (stake + fee), but the implementation irreversibly destroys more value than expected, with no path to recover the loss when the underlying operation does not succeed as intended. The local analog is Snowbridge's tip mechanism: `EthereumSystemFrontend::add_tip` burns the user's tip asset (swaps to Ether and permanently destroys it via `burn_for_teleport`) on the source chain *before* the destination chain (`BridgeHub`) validates that the target message nonce is still eligible for a tip. If the nonce is invalid or already consumed, the tip is simply recorded into a `LostTips` storage map with no extrinsic or mechanism to reclaim or refund it — the burned value is permanently lost to the user.

### Finding Description
`add_tip` in `bridges/snowbridge/pallets/system-frontend/src/lib.rs` first calls `Self::swap_fee_asset_and_burn(who.clone().into(), asset)?` [1](#0-0) , which swaps the caller's asset for Ether and then irreversibly burns it via `burn_for_teleport` [2](#0-1) . Only after this destructive step does the pallet build and dispatch an XCM `AddTip` transact call to the `EthereumSystem` pallet on BridgeHub [3](#0-2) .

On BridgeHub, `snowbridge-pallet-system-v2::add_tip` attempts to apply the tip to the corresponding inbound/outbound queue nonce:
```
let result = match message_id {
    Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
    Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
};

if let Err(ref e) = result {
    LostTips::<T>::mutate(&sender, |lost_tip| {
        *lost_tip = lost_tip.saturating_add(amount);
    });
}
``` [4](#0-3) 

If the target nonce does not exist yet, was already delivered/finalized, or the message has already been processed, `add_tip` on the inbound/outbound queue returns an error (see `AddTipError::UnknownMessage` in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`), and the amount is simply accumulated into `LostTips<T>` — a value that is never drained, refunded, or reclaimed anywhere in the codebase. A repo-wide search for `LostTips` shows it is only written to (via `mutate`) and read in tests; there is no extrinsic, hook, or storage-drain mechanism that returns this value to the user [5](#0-4) . The integration test `tip_to_invalid_nonce_is_added_to_lost_tips` explicitly demonstrates this outcome: the tip is burned on Asset Hub, fails to apply on BridgeHub, and ends up permanently recorded in `LostTips` with no further recovery step: [6](#0-5) .

### Impact Explanation
This matches the "Public underpriced/mispriced work" and "theft or unbacked... permanent user-fund lock" impact categories: an unprivileged user calling a public extrinsic (`add_tip`) can have real value irreversibly destroyed (teleport-burned to the Ethereum side) while receiving zero benefit, with no code path to restore or compensate the funds. Any user submitting a tip for a message nonce that is stale, already delivered, or otherwise no longer eligible loses their tip permanently — the loss is silent and by design of the current implementation, not a documentation-only mismatch, since `LostTips` is provably a dead-end storage item.

### Likelihood Explanation
The trigger requires no privileged actor, malicious peer, or race condition beyond ordinary usage: a user simply needs to tip a nonce that becomes invalid (e.g., already delivered) between construction and processing of the XCM message, or a user error providing wrong/expired nonce. Given asynchronous XCM message delivery between Asset Hub and BridgeHub, this timing window is easily reachable in normal operation, making this a realistic and repeatable fund-loss condition for any unprivileged sender.

### Recommendation
Reorder operations so the destination-side validity of the tip (nonce still pending) is confirmed before irreversibly burning the source-side asset, or introduce a refund/claim path keyed off `LostTips<T>` that lets affected senders reclaim (mint back or otherwise compensate) their lost tip amount once failure is recorded, rather than leaving the burned funds permanently unrecoverable.

### Proof of Concept
1. User calls `EthereumSystemFrontend::add_tip(origin, message_id=Outbound(N), asset)` on Asset Hub for nonce `N`.
2. `swap_fee_asset_and_burn` executes: asset is swapped for Ether and burned via `burn_for_teleport`, irreversibly removing value from the user's account.
3. XCM dispatches the `AddTip` transact call to BridgeHub's `snowbridge-pallet-system-v2::add_tip`.
4. Suppose nonce `N` has already been fully delivered/removed from `PendingOrders` (outbound-queue-v2) or already processed (inbound-queue-v2) by the time the XCM lands — `OutboundQueue::add_tip`/`InboundQueue::add_tip` returns `Err(AddTipError::UnknownMessage)`.
5. `system-v2::add_tip` catches the error and does `LostTips::<T>::mutate(&sender, ...)`, as shown directly in the test `tip_to_invalid_nonce_is_added_to_lost_tips` [6](#0-5) .
6. The user's burned Ether is gone; `LostTips` has no reader/drain/refund logic anywhere in the pallet, confirming permanent loss.

		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}
