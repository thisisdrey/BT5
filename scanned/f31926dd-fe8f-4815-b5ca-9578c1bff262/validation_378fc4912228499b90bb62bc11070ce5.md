Based on my research, I found a strong local analog to the reported precision-loss bug class in the Snowbridge outbound-queue fee calculation path.

### Title
Truncating integer division in Snowbridge outbound-queue fee conversion causes public underpriced message delivery - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
`Pallet::calculate_fee` (used by every public message-send path through the outbound queue) computes the remote/local fee owed by a caller by chaining a `FixedU128` multiply/divide and then truncating with `checked_div` / integer division in `convert_from_ether_decimals`. As in the Numa report, where `BASE_1000`-precision integer math caused a scaling factor to lose precision and shortchange the recipient of `NUMA`, here the fee owed to cover Ethereum-side execution and relayer reward is rounded down to the local currency's granularity, which for chains like Polkadot (10 decimals) or Kusama (12 decimals) versus Ethereum's 18 decimals means up to `10^(18-decimals)-1` wei of value is silently dropped every time a message is priced. [1](#0-0) 

### Finding Description
`calculate_fee` computes:
```
fee = FixedU128::from_inner(fee).saturating_mul(multiplier).checked_div(&exchange_rate)...into_inner();
fee = Self::convert_from_ether_decimals(fee);
``` [2](#0-1) 

`convert_from_ether_decimals` then does a plain truncating division to rescale from Ether's 18-decimal fixed point into the local chain's balance precision:
```rust
pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
    let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
    let denom = 10u128.saturating_pow(decimals);
    value.checked_div(denom).expect("divisor is non-zero; qed").into()
}
``` [3](#0-2) 

This is the exact bug class in the Numa report: a rational/scaling factor is applied with insufficient precision (`BASE_1000` there, a coarse local-decimal division here), causing the computed amount to be smaller than the true economic value. The pallet's own test suite documents this exact failure mode as acceptable/expected rather than guarded against:
```rust
// Though none zero pricing params the remote fee calculated here is invalid
// which should be avoided
assert_eq!(fee.remote, 0);
``` [4](#0-3) 

There is no floor/ceiling rounding-up guard, no minimum-fee enforcement, and no check that the truncated `fee.local`/`fee.remote` still covers the real weight-to-fee cost of `do_process_message` + `commit`. Because `calculate_fee` feeds directly into the public message-send/validate path (`SendMessage::validate`, used by XCM exporters and `snowbridge-pallet-system::send`), any unprivileged account routing a message through the bridge pays a fee rounded down from the true cost.

### Impact Explanation
This maps directly to the in-scope "public underpriced work that degrades block production or stalls bridge processing" impact category. Systematic truncation means the fee charged to cover on-chain processing weight and off-chain relayer reward is persistently lower than the real cost. An attacker can:
- Choose small `gas_used_at_most`/message parameters that make the pre-truncation ether-denominated fee sit just under a multiple of `10^decimals`, guaranteeing `fee.remote` rounds toward the minimum (as demonstrated by the pallet's own test producing `fee.remote == 0`).
- Repeatedly enqueue messages at this artificially low cost, since `MaxMessagesPerBlock` bounds weight but not the aggregate economic loss, degrading the incentive alignment for relayers and letting cheap messages fill the merkle-committed queue while paying near-zero reward, which can stall or economically starve the delivery pipeline over time.

### Likelihood Explanation
High likelihood: this is a pure, deterministic arithmetic path reachable by any account that can send a message over the bridge (no admin/governance/relayer trust assumption required), and the repository's own unit test already demonstrates the zero-fee degenerate case for realistic `exchange_rate`/`fee_per_gas` inputs, confirming the condition is trivially reachable, not a theoretical edge case.

### Recommendation
Round the decimal-rescaling division up (ceiling) rather than truncating, or enforce a floor comparing `fee.remote`/`fee.local` against `Self::calculate_local_fee()` plus a minimum reward, rejecting/adjusting messages whose computed fee would fall to zero or below actual processing/relay cost. Increasing the internal fixed-point precision (mirroring the "change precision to 1e18 or larger" fix from the Numa report) before the final decimal conversion, and adding an explicit `ensure!(fee.remote > 0 && fee.local >= minimal_cost)` check, would close this gap.

### Proof of Concept
The existing regression test in the codebase already reproduces the exact failure condition without any modification:
```rust
#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
    new_tester().execute_with(|| {
        let gas_used: u64 = 250000;
        let price_params = PricingParameters {
            exchange_rate: FixedU128::from_rational(1, 1),
            fee_per_gas: 1_u32.into(),
            rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
            multiplier: FixedU128::from_rational(1, 1),
        };
        let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
        assert_eq!(fee.local, 698000000);
        assert_eq!(fee.remote, 0); // remote fee/reward truncated to zero
    });
}
``` [4](#0-3) 

This confirms that with realistic pricing parameters set by the runtime (not an attacker-controlled admin value), an unprivileged message sender can be charged `fee.remote == 0`, i.e., zero relayer reward for real Ethereum-side gas usage, exactly analogous to the Numa report's "user will get less amount than expected due to precision loss in scaling."

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		/// Calculate fee in remote currency for dispatching a message on Ethereum
		pub(crate) fn calculate_remote_fee(
			gas_used_at_most: u64,
			fee_per_gas: U256,
			reward: U256,
		) -> U256 {
			fee_per_gas.saturating_mul(gas_used_at_most.into()).saturating_add(reward)
		}

		/// The local component of the message processing fees in native currency
		pub(crate) fn calculate_local_fee() -> T::Balance {
			T::WeightToFee::weight_to_fee(
				&T::WeightInfo::do_process_message().saturating_add(T::WeightInfo::commit_single()),
			)
		}

		// 1 DOT has 10 digits of precision
		// 1 KSM has 12 digits of precision
