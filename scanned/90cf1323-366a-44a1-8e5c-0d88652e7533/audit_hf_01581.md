# [H] MJR-3 creditManager isn't checked

## Summary
Severity: High
Contest weight: 0.0098
Dataset id: 8472
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability is an unchecked reference to the credit manager contract when granting token allowances. In the leverage action routine the contract calls an ERC20 approve function and passes the address supplied as the credit manager without verifying that this address belongs to a trusted system component. The root cause is the absence of a validation step that ensures the credit manager is a known, immutable system contract. An attacker can supply a malicious contract in place of the expected credit manager, causing the protocol to execute an unlimited approve call that authorises the attacker’s contract to transfer any amount of the underlying token on behalf of the protocol. Exploitation proceeds by the attacker deploying a contract that implements the expected interface, then invoking the leverage function with the address of this malicious contract. Because the protocol does not check the contract’s provenance, the approve call succeeds and the attacker gains an allowance that can be used to drain token balances. The impact is the potential loss of user funds or protocol assets, as the attacker can move tokens without restriction, effectively making funds disappear from user balances or from the protocol’s vault. This condition occurs whenever the leverage action is executed with a user‑controlled credit manager parameter, which is allowed by the current implementation. All participants that rely on the protocol’s accounting – lenders, borrowers, and the protocol itself – are affected because the accounting assumptions that only the system can move tokens are violated. The issue was discovered during a manual security audit that examined the flow of privileged parameters and identified that the credit manager address was not validated against a whitelist of system contracts. The bug can be subtle because the approve call itself is a standard ERC20 operation and may not raise an error; the malicious allowance is invisible until a token transfer is attempted, making it hard to notice through normal testing. The recommended remediation is to add an explicit check that the supplied credit manager address matches a contract that is registered as a system component, for example by consulting a registry or by using an immutable address constant, before performing the approve. Conceptually this belongs to the class of “missing access‑control validation” or “unrestricted delegate contract reference” bugs, where a privileged operation is performed on an untrusted contract. From a user’s perspective the symptom would be that after a transaction they see their token balance reduced unexpectedly or that a withdrawal returns zero tokens despite a successful transaction. The expectation that the protocol only authorises its own credit manager is broken, leading to a scenario where funds can be siphoned away without the user’s consent.

## Recommendation
We recommend adding a check that creditManager is a system contract.
