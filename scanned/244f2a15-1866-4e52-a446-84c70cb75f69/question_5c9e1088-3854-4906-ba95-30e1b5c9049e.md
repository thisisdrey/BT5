`ImtTokenId::new(minter_id, token_id)` in `crates/primitives/token-id/src/imt.rs` formats as `format!(\"{}:{}\", minter_id, token_id)` with no escaping of `:` inside `token_id`. Can an unprivileged signer of an `ImtMint` intent (`contracts/defuse/core/src/intents/imt.rs`, field `tokens: ImtTokens`) choose a `token_id` string containing a colon, e.g. `minter.near` mints `token_id = \"other.near:5\"`, so `ImtTokenId{minter_id: \"minter.near\", token_id: \"other.near:5\"}.to_string()` equals `imt:minter.near:other.near:5`, which differs from any legitimately-parsed `ImtTokenId` but when re-parsed via `ImtTokenId::from_str` (splitting only once on the first `:`) yields `minter_id = \"minter.near\"`, `token_id = \"other.near:5\"` again (round trip holds) - but is there a second attacker-chosen minter `other.near` whose legitimate `ImtTokenId{minter_id:\"other.near\", token_id:\"5\"}` also serializes to `imt:other.near:5`, distinct from the first `imt:minter.near:other.near:5`? Verify no two distinct constructible `(minter_id, token_id)` pairs produce identical `Display` output that `ImtTokenId::from_str` cannot invert to the original pair, i.e. `ImtTokenId::from_str(&t.to_string()) == t` for every attacker-constructible `t` via `ImtMint`. Impact: Critical if a collision lets one minter's `ImtMint` credit a balance keyed as if minted by a different minter, letting the attacker later burn/transfer tokens they never minted. Proof idea: cargo test with `#[rstest]` cases feeding crafted colon-containing `token_id` strings through `ImtTokens::into_generic_tokens` in `contracts/defuse/core/src/tokens.rs` and asserting `TokenId::from_str(&t.to_string()).unwrap() == t` plus that `t1 != t2 => t1.to_string() != t2.to_string()`.
