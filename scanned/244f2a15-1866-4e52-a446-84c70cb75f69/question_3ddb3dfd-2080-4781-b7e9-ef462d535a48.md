`Nep171TokenId::new(contract_id, nft_token_id)` and `Nep245TokenId::new(contract_id, mt_token_id)` in `crates/primitives/token-id/src/nep171.rs` / `nep245.rs` both `Debug`-format as `format!(\"{}:{}\", contract_id, sub_id)` with no length or character restriction on `nft_token_id`/`mt_token_id` beyond `MAX_TOKEN_ID_LEN` (checked only in `mt_on_transfer`, not in `nft_on_transfer`/withdraw paths that construct `Nep171TokenId` directly, e.g. `contracts/defuse/src/contract/tokens/nep171/withdraw.rs` line 67/187). Can an attacker deploying their own NFT contract at account id `X` mint an NFT with `token_id = \"Y:realtokenid\"` (colon embedded, unrestrained since NEP-171 `TokenId` is just `String`), deposit it via `nft_on_transfer`, producing `Nep171TokenId{contract_id: X, nft_token_id: \"Y:realtokenid\"}` whose `to_string()` is `X:Y:realtokenid`, which is indistinguishable in the intermediate join from a legitimate `Nep171TokenId{contract_id: \"X:Y\"... }` (impossible since `AccountId` disallows literal `:` mid-label, so `X:Y` can never itself be a valid `AccountId`) — but is there a real collision where `Nep171TokenId{contract_id: X, nft_token_id: \"Y:realtokenid\"}` and `Nep171TokenId{contract_id: X, nft_token_id: \"Y\"}` plus separate context collide inside `MtTransferEvent.token_ids` string-joined event logs read by an off-chain indexer used to settle `simulate_intents` results? Binding: `Nep171TokenId::from_str(&t.to_string()) == t` for every attacker-constructible `t` with colon-containing `nft_token_id`. Impact: Critical if the round-trip fails for any attacker-constructible NFT id, letting a deposit credit a differently-keyed balance than what is later withdrawn. Proof idea: cargo test `#[rstest]` feeding `nft_token_id` values containing `:` through `Nep171TokenId::new(...).to_string()` then `Nep171TokenId::from_str`, asserting equality holds, and separately asserting no two distinct attacker-constructible `(contract_id, nft_token_id)` pairs share a `to_string()` output.
