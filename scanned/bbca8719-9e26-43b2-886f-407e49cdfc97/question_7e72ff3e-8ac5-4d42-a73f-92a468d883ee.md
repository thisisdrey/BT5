target: WalletImpl::resolve_auth (NEP-641 AuthResolver, contracts/wallet/src/contract.rs). Attacker action: attacker submits authorization=WalletAuthorization::Signature{msg: OffchainMessage{signer_id omitted/mismatched, path, timestamp, payload}, proof} to w_resolve_auth(path, authorization) for a payload that authorizes moving Verifier funds, but msg.signer_id is not checked against a stored victim identity (only chain_id/signer_id-of-message equals env::current_account_id(), and msg.path equals provided path is checked). Preconditions: victim wallet account holds Verifier balances; a relying party (e.g. Verifier's AuthResolver-based execute path) will accept the returned AuthorizationResolution.payload as authorized for signer=victim. Call sequence: resolve_auth -> checks chain_id, signer_id==env::current_account_id(), path==provided path, timestamp not in future, S::verify_offchain_msg(pubkey, msg, proof) -> returns AuthorizationResolution::new(msg.payload). Binding: AuthorizationResolution.payload accepted by caller == payload actually authorized by the signer_id whose public_key verified it, for this exact wallet account (env::current_account_id()). Impact: Critical - if a relying contract calls w_resolve_auth on the wrong wallet account or the wallet returns a resolution for a payload string an attacker chose without a matching valid proof, unauthorized fund-moving payload gets treated as authorized. Proof idea: cargo test calling resolve_auth with a proof valid for a different public_key/message and assert Err(Error::InvalidSignature) results, never returning AuthorizationResolution with attacker-chosen payload.
