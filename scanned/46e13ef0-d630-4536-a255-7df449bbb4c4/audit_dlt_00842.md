## Root cause

`advance_time_to_allow_for_voting_and_node_rewards` computes:

```rust
let seconds_to_node_provider_reward_distribution = before_timestamp
    + NODE_PROVIDER_REWARD_PERIOD_SECONDS
    - state_machine.get_time().as_secs_since_unix_epoch();
```

all in `u64`. `before_timestamp` is the timestamp of the most recently
distributed monthly node provider reward, read from the golden NNS state
snapshot. `state_machine.get_time()` is the state machine's current
time, which `new_state_machine_with_golden_nns_state_or_panic` sets to
the real wall-clock time via `.with_current_time()` (see
`rs/nns/test_utils/golden_nns_state/src/lib.rs`), independent of when
the golden state snapshot was actually captured on mainnet.

This line assumes `before_timestamp +
NODE_PROVIDER_REWARD_PERIOD_SECONDS >= now`, i.e. that the last
distributed reward is less than one full reward period
(`NODE_PROVIDER_REWARD_PERIOD_SECONDS == ONE_MONTH_SECONDS`,
~2,629,800s) behind the current time. That assumption no longer holds
once node provider reward minting on mainnet is more than one period
behind: `before_timestamp + PERIOD` is then already in the past relative
to `now`, so the `u64` subtraction underflows and panics.

Notably, #10723 already anticipated this exact scenario in the doc
comment it added on `tick_until_node_provider_rewards_distributed`:

> "...so the number of ticks it needs grows with how far the golden
state's last reward is behind the current time."

That PR fixed the *tick-count* problem for the case where the reward is
behind schedule, but didn't update this earlier "seconds until next
distribution" computation to also tolerate an already-overdue
distribution, which is exactly what appears to be happening now on the
golden mainnet state.

## Fix

Use `saturating_sub` (and `saturating_add`) so that an already-overdue
distribution is represented as `0` seconds to wait, rather than
underflowing:

```rust
let seconds_to_node_provider_reward_distribution = before_timestamp
    .saturating_add(NODE_PROVIDER_REWARD_PERIOD_SECONDS)
    .saturating_sub(state_machine.get_time().as_secs_since_unix_epoch());
state_machine.advance_time(std::time::Duration::from_secs(
    seconds_to_node_provider_reward_distribution.saturating_sub(1),
));
```

When the distribution is already due, this correctly skips waiting and
proceeds straight to `tick_until_node_provider_rewards_distributed`,
which already handles ticking until the (overdue) reward is actually
minted. The subsequent `ONE_MONTH_SECONDS -
seconds_to_node_provider_reward_distribution` (used to make sure a full
month elapses for voting rewards too) is guarded the same way
defensively, though it cannot actually underflow given the clamped
value.

This is a minimal, targeted fix to the arithmetic; it does not change
the test's semantics or its ability to detect a genuinely stuck/broken
reward distribution (that's still caught by
`tick_until_node_provider_rewards_distributed`'s `MAX_TICKS` cap and the
`assert_increased` checks in `check_all`).
