Target: `ImtTokenId::from_str` (crates/primitives/token-id/src/imt.rs) vs `Nep245TokenId::from_str`. Attacker mints an IMT with `token_id` containing a colon so `ImtTokenId{minter_id: attacker.near, token_id: "x:y"}`.to_string() == `attacker.near:x:y`, identical byte-suffix to a `Nep245TokenId{contract_id: attacker.near, mt_token_id: "x:y"}` (differ only by the `imt:`/`nep245:` prefix added by `TokenId::Debug`). Preconditions: attacker controls an account named `attacker.near` usable both as IMT minter and as an MT contract address it deploys. Call sequence: intent that debits via `TokenId::Imt` and a resolver/refund path that reconstructs the key from a truncated substring omitting the outer `TokenIdType` prefix. Binding: the `(TokenIdType, contract/minter, sub_token)` tuple recovered must equal the one used to credit the balance for every consumer, i.e. `TokenId::from_str(&t.to_string()) == t`. Impact: Critical, a resolver refund could credit the IMT balance from a debit tagged as NEP-245 or vice versa. Proof idea: cargo test building both `TokenId` variants with identical `contract_id`/`minter_id` and colon-bearing sub-ids, asserting they never `to_string()`-collide and each parses back to itself.
