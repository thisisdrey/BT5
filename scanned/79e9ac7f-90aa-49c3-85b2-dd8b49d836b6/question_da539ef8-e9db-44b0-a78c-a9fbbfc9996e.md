Target: `TokenId::from_str` (lib.rs) invoked inside a resolver callback that receives `token_ids: Vec<String>` returned by an attacker-controlled MT contract as the RESULT of a cross-contract call (per program description: 'the return value of any contract the attacker deploys and names in msg ... flows back into the *_resolve_* callbacks'). Attacker's MT contract's `mt_resolve_transfer`-triggering call returns a manipulated `Vec<String>` where one entry is the victim's real deposited `TokenId` string (guessed/known) instead of the attacker's own. Preconditions: attacker knows or can compute the exact `to_string()` of a victim's `TokenId`. Call sequence: withdraw intent -> cross-contract call to attacker MT -> attacker's return value feeds `mt_resolve_transfer` -> `TokenId::from_str` on the returned string -> refund credited to that parsed key. Binding: the key refunded == the key originally debited for THIS call, i.e. `debited_token_id == refunded_token_id`, not an attacker-chosen victim key. Impact: Critical, a resolver could refund/credit the victim's token balance based on attacker-controlled callback data instead of the value actually debited. Proof idea: near-workspaces sandbox test with a malicious MT contract stub returning a forged `token_ids` string, asserting the resolver only ever credits the token id it itself debited, never one taken verbatim from the callback return.
