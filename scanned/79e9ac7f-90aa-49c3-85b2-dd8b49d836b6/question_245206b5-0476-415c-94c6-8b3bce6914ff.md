Target: `Nep245TokenId` (contract_id, mt_token_id) constructed inside `mt_on_transfer`'s deposit path (contracts/defuse/src/contract/tokens/nep245/deposit.rs) versus reconstruction inside the `mt_resolve_transfer` callback (contracts/defuse/src/contract/tokens/nep245/resolver.rs). Attacker deploys their own MT contract, deposits a token with `mt_token_id = ""` (empty string) so Debug renders `attacker_mt.near:` , then immediately triggers a withdraw whose resolver re-derives the `TokenId` from `token_ids: Vec<String>` supplied in the callback response. Preconditions: attacker controls the MT contract and its `mt_resolve_transfer`-style callback return value. Call sequence: deposit -> `token_balances` credited under `TokenId::Nep245{contract_id, mt_token_id:""}` -> withdraw -> resolver re-parses `token_ids` strings -> `TokenId::from_str`. Binding: the token id string returned by the resolver's callback == the exact `mt_token_id` originally credited, i.e. `TokenId::from_str(&returned_str) == TokenId::from_str(&original_str)`. Impact: Critical, a refund/credit on failed transfer could land on a different (attacker-chosen) key than what was debited. Proof idea: near-workspaces sandbox test depositing with an empty/colon-laden `mt_token_id`, forcing transfer failure, and asserting the refunded balance key equals the debited key.
