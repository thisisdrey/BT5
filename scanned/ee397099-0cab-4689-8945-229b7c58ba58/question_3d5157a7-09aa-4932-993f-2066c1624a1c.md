Attacker submits two deposits in the same `mt_on_transfer` batch (`token_ids` vector) with two distinct raw NEP-245 sub-token id strings that, after `Nep245TokenId::new(token, id)` and `Display`, produce `TokenId` values with equal `Ord`/`Hash` but different underlying `(contract_id, mt_token_id)`. Preconditions: attacker fully controls their own MT contract and can pick arbitrary `mt_token_id` strings including those with equal UTF-8 byte prefixes. Call sequence: `mt_on_transfer` -> `core_token_ids` iterator -> `self.deposit(receiver_id, core_token_ids.zip(amounts), ...)` where the `BTreeMap<TokenId,u128>` insertion under `Amounts::add` merges same-keyed entries. Binding: `TokenId` derives `PartialEq, Eq, PartialOrd, Ord, Hash` structurally; two distinct `(contract_id, mt_token_id)` pairs must never compare `Ord::eq` equal. Impact: Critical - if two distinct sub-tokens compare equal, one deposit's amount silently merges into another's balance, breaking conservation. Proof idea: cargo test constructing many `(contract_id, mt_token_id)` pairs including edge cases (unicode, max-length, embedded control chars) and asserting all `TokenId` values are pairwise distinct per `Ord`/`Hash` when the underlying tuples differ.
