Target: `DepositMessage` parsing (`msg.parse().unwrap_or_else(|e| panic!("{e}"))`) in `ft_on_transfer`/`nft_on_transfer`/`mt_on_transfer`, combined with `TokenId::to_string()` values later passed into `notify_on_transfer`. Attacker crafts `msg` so `DepositMessage::receiver_id` names a `NotifyOnTransfer` contract the attacker deployed, which the Verifier calls with `core_token_ids.map(|t| t.to_string())`. The attacker's notify contract returns a crafted response used later in `*_resolve_deposit`. Preconditions: attacker deploys the notify contract and deposits their own worthless FT with a `msg` naming their notify contract. Call sequence: `deposit()` credits attacker's own account first, then `notify_on_transfer` -> callback -> `ft_resolve_deposit`/`mt_resolve_deposit`/`nft_resolve_deposit` -> `resolve_deposit_internal`. Binding: the amount reversed by `resolve_deposit_internal` must equal exactly the unused amount reported, keyed by the same `TokenId` that was credited, i.e. `credited_amount - reversed_amount == amount actually consumed by the notify flow`, for that exact `TokenId` and account. Impact: Critical - a malicious notify contract must not cause `resolve_deposit_internal` to reverse a different token's balance than the one deposited. Proof idea: sandbox test where the attacker's notify contract's response references a token id string that does not match the deposited `contract_id`, asserting `resolve_deposit_internal` only ever mutates the exact `TokenId` passed to it and never another account's balance.
