In `Contract::do_auth_call` (contracts/defuse/src/contract/intents/auth_call.rs), `Promise::new(auth_call.contract_id)` is state-initialized via `p.state_init(state_init, NearToken::ZERO)` before `ext_auth_callee::ext_on(p).with_attached_deposit(auth_call.attached_deposit)...on_auth(signer_id, auth_call.msg)`. An attacker deploys a global contract at a deterministic account derived from `state_init` whose `on_auth()` implementation immediately calls back `Contract::do_auth_call` on the Verifier itself (since it's `#[private]` this direct call is blocked, but the attacker can instead re-enter via a fresh `execute_intents` call with a new `AuthCall` intent for the SAME `signer_id` reusing the still-in-flight wNEAR withdrawal window). Preconditions: signer has enabled no lock, has wNEAR balance sufficient for two `attached_deposit` withdrawals. Call sequence: intent1 `AuthCall` -> `withdraw`(signer wNEAR) -> `near_withdraw` -> `do_auth_call` -> `on_auth()` re-enters `execute_intents` with intent2 `AuthCall` for same signer -> second `withdraw`(signer wNEAR) before intent1's callback confirms delivery. Binding: total wNEAR withdrawn from `signer_id`'s `token_balances` across both `AuthCall`s == sum of `attached_deposit` fields the signer actually signed for, not double-counted from a shared pre-callback wNEAR balance snapshot. Impact: Critical, signer's wNEAR balance oversubscribed if `internal_sub_balance` isn't atomically re-checked per re-entrant call. Proof idea: sandbox test issuing a re-entrant `AuthCall` from `on_auth()` targeting the same signer's wNEAR, assert `internal_sub_balance` correctly errors with `BalanceOverflow` on the second withdrawal rather than allowing both to succeed.
