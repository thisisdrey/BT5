`NotifyOnTransfer` (contracts/defuse/core/src/intents/tokens.rs) combined with `Contract::notify_on_transfer` (contracts/defuse/src/contract/tokens/nep245/core.rs lines 273-307) allows an attacker to set `state_init: Some(state_init)` where `state_init.derive_account_id() != receiver_id` claimed in the signed `Transfer.receiver_id`. Craft `Transfer{receiver_id: X, tokens:{ft:1000}, notification: Some(NotifyOnTransfer{state_init: Some(StateInit::V1(StateInitV1{code: attacker_global_contract, data: crafted})), msg, min_gas:None})}` where the account derivation mismatch is expected to cause the whole receipt to fail per NEP-616 runtime validation, but the `Transfer::execute_intent` has already run `internal_sub_balance`/`internal_add_balance` synchronously in `Deltas` before the `Promise` with mismatched `state_init` is even created. Binding: the balance debited from `sender_id` and credited to `receiver_id` inside `Deltas` == the balance actually reachable by `receiver_id` after the receipt including the deterministic-account promise settles (no `Deltas` credit without a corresponding successfully-created receipt). Impact: Critical, an intent that is guaranteed to fail at the NEAR runtime level (state_init mismatch) still commits an internal balance move if `execute_intents` does not correctly propagate `Promise` creation failure back to `DefuseError::InvariantViolated`. Proof idea: sandbox test with mismatched `state_init.derive_account_id()` vs `receiver_id`, submit the whole batch, assert the transaction as a whole fails or that `mt_balance_of(receiver_id)` remains 0 post-execution.
