`Engine::execute_signed_intents` (contracts/defuse/core/src/engine/mod.rs) calls `self.execute_signed_intent(signed)?` for each `MultiPayload` in a batch sequentially, then `self.finalize()` once for the whole batch — meaning ALL intents across ALL signed payloads in one `execute_intents` call share ONE `Deltas` accumulator before any real NEAR promise fires. An attacker submits a batch `[payload1(AuthCall{contract_id: attacker, msg:'m1'}), payload2(Transfer{receiver_id: attacker, tokens:{ft:1000}})]` both signed by the same victim key (replayed/leaked signature is out of scope, but assume victim voluntarily signs both for a legitimate reason) where `payload1`'s `AuthCall.msg` is crafted so the attacker's `on_auth()` — invoked via a promise chained AFTER `Engine::finalize` already ran for the whole batch — can call `simulate_intents` (a view call) to read `Deltas` state that public API assumes reflects the committed batch, but before `finalize`'s invariant check (`self.state.finalize()`) has actually rejected an over-drawn balance if `payload2`'s transfer exceeds what's available after `payload1`'s side effects. Binding: `SimulationOutput.invariant_violated` reported by `simulate_intents` for a given `Deltas` snapshot == the actual invariant state `execute_intents` would commit for the same batch executed at the same predecessor time. Impact: High, a party relying on `simulate_intents`'s report while an `AuthCall`'s asynchronous callback is still in flight from a prior `execute_intents` could see a stale or inconsistent balance view. Proof idea: sandbox test issuing `execute_intents` with an `AuthCall` whose callback triggers a `simulate_intents` view call mid-flight, comparing its reported balances against the final settled state.
