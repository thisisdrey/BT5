### Title
Outbound-queue `calculate_fee` can truncate the remote (Ethereum) delivery fee to zero despite non-zero pricing parameters, enabling underpriced bridge delivery — (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
The external report's core broken invariant is: a downstream "excess/fee" quantity is computed from an intermediate value that can legitimately become zero, and when it does, the code silently treats the situation as "nothing owed" instead of guarding against it, corrupting settlement. The same broken-invariant shape exists in Snowbridge's outbound-queue fee pricing pipeline: `Pallet::calculate_fee` computes the DOT-denominated remote fee via a chain of fixed-point multiplication and a final **flooring integer division** in `convert_from_ether_decimals`, and this division can round a genuinely non-zero fee down to `0`, as the code's own test suite already demonstrates.

### Finding Description
`calculate_fee` derives the remote fee owed for delivering a message to Ethereum: [1](#0-0) 

The final step, `convert_from_ether_decimals`, rescales the 18-decimal (Ether) fixed-point amount down to the chain's native decimal precision using plain integer division: [2](#0-1) 

Because `value.checked_div(denom)` floors toward zero, any pre-division amount smaller than `denom = 10^(ETHER_DECIMALS - T::Decimals)` (e.g. `10^8` for a 10-decimal chain like Polkadot) collapses to `0`, even though `fee_per_gas`, `reward`, `multiplier`, and `exchange_rate` were all non-zero, valid, governance-set parameters. This is precisely the "adjustedRectangle == 0" pattern from the external report: an intermediate calculation collapsing to zero silently short-circuits the amount that should be deducted/charged, with no `require`/`ensure` guard analogous to the recommended `require(adjustedRectangle != 0, "err")`.

The repository's own test explicitly documents this exact failure mode: [3](#0-2) 

The test comment states plainly: *"Though none zero pricing params the remote fee calculated here is invalid which should be avoided."* This confirms the flaw is acknowledged in-repo as a real defect in the calculation, not a documentation or test artifact — it is production pallet logic (`pub(crate) fn calculate_fee`), reachable by any message routed for export to Ethereum, whose fee is charged based on this function's output.

### Impact Explanation
When `fee.remote` truncates to `0`, the fee charged to the message sender for the remote (Ethereum-side) leg of delivery collapses to zero while the message still requires gas-metered execution and relayer compensation on the Ethereum side. This is exactly the "public underpriced work that degrades block production or stalls bridge processing" impact category: messages can be queued and committed for export at effectively zero remote cost, meaning senders are not paying for the resource they consume from the bridge/relayer subsidy pool. Repeated triggering (e.g., via commands with small `max_dispatch_gas` or via governance-tuned pricing parameters that place the computed value near the rounding boundary) causes a systemic mismatch between fees collected from senders and rewards the bridge must fund for relayers, degrading the bridge's economic sustainability and creating incentive for relayers to stop servicing underpriced messages — stalling bridge processing.

### Likelihood Explanation
The rounding-to-zero behavior is deterministic and fully reproducible from public, non-privileged inputs (message content selects `gas_used_at_most` via `T::GasMeter::maximum_dispatch_gas_used_at_most`), combined with pricing parameters that, while governance-set, are not attacker-controlled but are ordinary, valid protocol configuration (not malicious governance abuse — the bug triggers under normal/low-cost commands and standard parameter ranges near the decimal-rescaling boundary). The existing unit test proves the collapse occurs with plausible parameter magnitudes, not only extreme edge values, and no `ensure!`/`require` exists in `calculate_fee` or `convert_from_ether_decimals` to reject or round up a zero result — unlike the analogous protection pattern used elsewhere in the same pallet doc: `LocalFee`/`RemoteFeeAdjusted` composition assumes non-zero results.

### Recommendation
Add an explicit guard in `calculate_fee`/`convert_from_ether_decimals` that rejects (or rounds up / applies a minimum floor to) a remote fee that computes to zero when the pre-division value was non-zero, mirroring the recommended fix pattern from the source report (`require(value != 0)` before finalizing the fee). Alternatively, use rounding-up (`div_ceil`) semantics for the decimal rescaling so genuinely non-zero fees are never silently zeroed, and add a defensive `ensure!(!fee.remote.is_zero() || pre_division_value.is_zero(), Error::<T>::InvalidFeeCalculation)` check before the fee is used to charge senders.

### Proof of Concept
The existing test in the repository is itself a proof of concept: [3](#0-2) 
With `exchange_rate = 1/1`, `fee_per_gas = 1`, `rewards = {local:1, remote:1}`, `multiplier = 1/1`, and `gas_used = 250000`, `OutboundQueue::calculate_fee` returns `fee.remote == 0` despite every pricing parameter being non-zero and the nominal remote fee being `250000 * 1 + 1 = 250001` wei-equivalent — the value is destroyed entirely by the flooring division in `convert_from_ether_decimals` before reaching native-chain decimal precision.

**Note on scope/verification limits:** I was not able to trace, within this pass, every call site of `calculate_fee` (i.e., exactly which extrinsic/XCM export path uses its output to charge senders) due to tool-call limits; the pallet doc comments and code indicate it governs the DOT-denominated fee charged for message export, but confirming the precise caller and end-to-end fund-flow (channel treasury vs. relayer reward payout on Ethereum) would benefit from a full Devin session with repository access to trace `T::PricingParameters`/export call sites across `snowbridge_router_primitives` and the XCM exporter integration.

			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {

		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {

			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});
}
