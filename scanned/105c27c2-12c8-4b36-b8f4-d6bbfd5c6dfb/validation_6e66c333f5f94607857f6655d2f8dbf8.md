## Analysis

The external report's core invariant break is: **a state-mutating "register" action can be invoked repeatedly for an already-registered entity because the idempotency check only guards the bookkeeping write, not the actual side-effecting action.** The Yaxis `addToken` bug allowed `vaults[_token]` to be silently overwritten and the token array to grow with duplicates because no check gated the whole operation.

The direct analog in this repository is in Snowbridge's foreign-token registration path. `register_token` is exposed to *any* unprivileged account via `pallet-snowbridge-system-frontend`, forwarded over XCM `Transact` to `pallet-snowbridge-system-v2::register_token` on BridgeHub, which calls the shared `do_register_token`/inline logic: [1](#0-0) [2](#0-1) 

In both `system` and `system-v2` pallets, the "already registered" check only wraps the `ForeignToNativeId` storage insert — it does **not** gate the subsequent `Command::RegisterForeignToken` dispatch to the outbound queue nor the event emission: [3](#0-2) 

### Title
Missing idempotency guard lets any account re-trigger `RegisterForeignToken` dispatch to Ethereum for an already-registered token - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

### Summary
`register_token` conditionally skips the `ForeignToNativeId` storage write when the `token_id` already exists (`if !contains_key { insert }`), but always sends `Command::RegisterForeignToken` to the outbound queue and always emits `Event::RegisterToken`, regardless of whether the token was already registered.

### Finding Description
The call chain is: `pallet-snowbridge-system-frontend::register_token` (doc states "All origins are allowed", only requiring the `asset_id` be nested in the caller's own location) → XCM `Transact` → `pallet-snowbridge-system-v2::register_token` (gated by `T::FrontendOrigin`, i.e. reachable by any account through the frontend) → the inline registration logic:
```rust
if !ForeignToNativeId::<T>::contains_key(token_id) {
    ForeignToNativeId::<T>::insert(token_id, location.clone());
}

let command = Command::RegisterForeignToken { token_id, name, symbol, decimals };
let message_origin = Self::location_to_message_origin(sender_location)?;
Self::send(message_origin, command, amount)?;

Self::deposit_event(Event::<T>::RegisterToken { location: location.into(), foreign_token_id: token_id });
``` [4](#0-3) 

The identical pattern exists in the root-only `pallet-snowbridge-system::do_register_token`: [5](#0-4) 

No `ensure!(!ForeignToNativeId::<T>::contains_key(token_id), Error::<T>::AlreadyRegistered)` exists anywhere in either call path. The corrupted/uncorroborated value is the outbound queue: the same `Command::RegisterForeignToken` message can be enqueued an unbounded number of times for a token that is already mapped, because the only guard (`contains_key`) is scoped solely to the storage `insert`, not to the command construction/send/event steps that follow it — exactly the same class of "check protects the bookkeeping but not the operation" gap as the Yaxis `addToken` finding (where `vaults[_token] == address(0)` was recommended precisely because the actual add-operation lacked any duplicate guard).

### Impact Explanation
Each `register_token` call that resolves to an already-registered `token_id` still produces a full `Command::RegisterForeignToken` message that is delivered through the outbound queue to the Ethereum Gateway, and consumes outbound-queue capacity/relayer processing/gas exactly like a first-time registration, satisfying the accepted impact category of "public underpriced work that degrades block production or stalls bridge processing." Because the frontend explicitly allows "All origins," any account holding an asset location under its own consensus system can trigger this repeatedly and cheaply relative to a fresh registration (they pay only the XCM delivery + tip, not any registration-specific anti-spam fee), letting them flood the Snowbridge outbound channel with redundant `RegisterForeignToken` commands for tokens that are already bridged.

### Likelihood Explanation
High likelihood: `register_token` is a normal, permissionless, non-privileged public extrinsic (per its own doc comment), requires no special origin beyond owning the asset location, and the missing guard is unconditionally reachable on every call — no race condition, governance action, or malicious relayer/validator is required.

### Recommendation
Move the `contains_key` check out from guarding only the `insert` and make it a hard `ensure!` that short-circuits the whole function before the `Command::RegisterForeignToken` is built and sent:
```rust
ensure!(!ForeignToNativeId::<T>::contains_key(token_id), Error::<T>::TokenAlreadyRegistered);
ForeignToNativeId::<T>::insert(token_id, location.clone());
```
Apply this in both `pallet-snowbridge-system::do_register_token` and `pallet-snowbridge-system-v2::register_token`.

### Proof of Concept
1. Any account `A` calls `pallet-snowbridge-system-frontend::register_token(asset_id = A's own asset location, metadata, fee_asset)` — succeeds, XCM `Transact` reaches BridgeHub, `ForeignToNativeId` is populated and `Command::RegisterForeignToken` is enqueued.
2. Account `A` (or any other account whose location nests the same `asset_id`) calls `register_token` again with the identical `asset_id`.
3. `ForeignToNativeId::<T>::contains_key(token_id)` is `true`, so the storage insert is skipped, but execution continues unconditionally to `Self::send(message_origin, command, amount)` and `Self::deposit_event(...)`, enqueuing a second `Command::RegisterForeignToken` for the same token.
4. Repeating step 2 an arbitrary number of times enqueues arbitrarily many duplicate `RegisterForeignToken` commands into the Snowbridge outbound queue for a token that is already registered, with no on-chain rejection.

		pub fn register_token(
			origin: OriginFor<T>,
			sender: Box<VersionedLocation>,
			asset_id: Box<VersionedLocation>,
			metadata: AssetMetadata,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let sender_location: Location =
				(*sender).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;
			let asset_location: Location =
				(*asset_id).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;

			let location = Self::reanchor(asset_location)?;
			let token_id = TokenIdOf::convert_location(&location)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			if !ForeignToNativeId::<T>::contains_key(token_id) {
				ForeignToNativeId::<T>::insert(token_id, location.clone());
			}

			let command = Command::RegisterForeignToken {
				token_id,
				name: metadata.name.into_inner(),
				symbol: metadata.symbol.into_inner(),
				decimals: metadata.decimals,
			};

			let message_origin = Self::location_to_message_origin(sender_location)?;
			Self::send(message_origin, command, amount)?;

			Self::deposit_event(Event::<T>::RegisterToken {
				location: location.into(),
				foreign_token_id: token_id,
			});

			Ok(())
		}

		pub(crate) fn do_register_token(
			location: &Location,
			metadata: AssetMetadata,
			pays_fee: PaysFee<T>,
		) -> Result<(), DispatchError> {
			let ethereum_location = T::EthereumLocation::get();
			// reanchor to Ethereum context
			let location = location
				.clone()
				.reanchored(&ethereum_location, &T::UniversalLocation::get())
				.map_err(|_| Error::<T>::LocationConversionFailed)?;

			let token_id = TokenIdOf::convert_location(&location)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			if !ForeignToNativeId::<T>::contains_key(token_id) {
				ForeignToNativeId::<T>::insert(token_id, location.clone());
			}

			let command = Command::RegisterForeignToken {
				token_id,
				name: metadata.name.into_inner(),
				symbol: metadata.symbol.into_inner(),
				decimals: metadata.decimals,
			};
			Self::send(SECONDARY_GOVERNANCE_CHANNEL, command, pays_fee)?;

			Self::deposit_event(Event::<T>::RegisterToken {
				location: location.clone().into(),
				foreign_token_id: token_id,
			});

			Ok(())
		}
