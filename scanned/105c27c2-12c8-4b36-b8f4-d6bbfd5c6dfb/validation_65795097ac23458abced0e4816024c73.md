## Title
`ProxyType::NonTransfer` fails to filter `pallet_asset_conversion` calls, allowing a proxy delegate to redirect a proxied account's assets to itself via `add_liquidity` (and `remove_liquidity`/swaps) - (File: `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs`, `cumulus/parachains/runtimes/assets/asset-hub-rococo/src/lib.rs`, `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`add_liquidity`'s `mint_to` parameter (and `remove_liquidity`'s `withdraw_to`, and the swap functions' `send_to`) let the caller of the extrinsic direct the resulting value to an arbitrary account, independent of the signed origin (`who`) that actually pays. `Pallet::add_liquidity` only calls `ensure_signed(origin)` and otherwise treats `mint_to` as fully attacker-controlled input. [1](#0-0) 

When composed through `pallet_proxy` with `ProxyType::NonTransfer`, the inner call is dispatched with the *delegator's* signed origin, while the *delegate* fully controls the call's parameters, including `mint_to`. `ProxyType::NonTransfer` is defined to block `Balances`, `Assets`, `NftFractionalization`, `Nfts`, and `Uniques` calls specifically to prevent a delegate from moving the delegator's value, but it does not include `AssetConversion` calls in that exclusion list: [2](#0-1) [3](#0-2) 

### Finding Description
`do_add_liquidity` transfers `amount1`/`amount2` out of `who` (the origin, i.e. the delegator when called via proxy) into the pool account, then mints LP tokens to `mint_to` — a completely separate, caller-supplied account: [4](#0-3) 

This design is safe for a normal signed extrinsic, because the signer chooses both `who`'s spend and the `mint_to` beneficiary consensually (e.g. sending LP tokens to a friend). The implicit local assumption is that the entity paying-in (`who`/origin) and the entity choosing the beneficiary (`mint_to`) are the same trusted actor. That assumption breaks under proxy composition: `pallet_proxy` preserves the delegator as the dispatch origin for accounting/authorization purposes, but the delegate crafts the call's arguments. A delegate holding only a `NonTransfer` proxy — which is documented/intended to disallow moving the delegator's funds — can nonetheless call `AssetConversion::add_liquidity` (not filtered) with `mint_to = <delegate's own account>`. This pulls funds out of the delegator's account into the pool and mints the LP-token claim on those funds directly to the delegate.

The delegate (owning the LP tokens outright, no proxy required) can then call `AssetConversion::remove_liquidity` with `withdraw_to = <delegate>` to redeem the pooled assets back out to themselves, completing a full value transfer from the delegator to the delegate — despite the delegator only ever authorizing a "non-transfer" proxy relationship.

Note this is not a bug purely local to `add_liquidity`'s bookkeeping (transfers/mint/rollback are internally correct and atomic); it is a composition-boundary problem: the pallet's public API exposes an arbitrary-beneficiary parameter that silently converts into a value transfer when the effective "who pays" and "who benefits" identities diverge under the `Proxy` wrapper, which the runtime's `ProxyType::NonTransfer` filter does not account for.

### Impact Explanation
This allows unauthorized transfer of user funds: an attacker granted (or receiving) a `NonTransfer` proxy over a victim account — a grant that the delegator expects to strictly forbid asset movement — can drain the delegator's fungible balances/asset holdings through `add_liquidity` + `remove_liquidity` (or via swaps with `send_to` set to themselves). This matches the "theft of user funds" / "wrongful beneficiary or amount" impact category, since value moves to an account never authorized to receive it.

### Likelihood Explanation
Requires only that a victim has granted any `NonTransfer` proxy relationship (a common pattern for "operational, non-custodial" delegate access) to an untrusted or later-compromised delegate, and that a liquidity pool exists for assets the victim account holds (or the attacker can call `create_pool` first, which is also unfiltered). No privileged operator or infrastructure compromise is required — purely unprivileged, delegate-controlled call composition.

### Recommendation
Add `pallet_asset_conversion` calls that accept an arbitrary destination/beneficiary account (`add_liquidity`'s `mint_to`, `remove_liquidity`'s `withdraw_to`, `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens`'s `send_to`) to the exclusion list of `ProxyType::NonTransfer` in all runtimes that define this filter (asset-hub-westend, asset-hub-rococo, and any other runtime including `pallet_asset_conversion` with a similar proxy filter), or restrict those filtered variants to only permit calls where the beneficiary is validated to equal the origin. Consider whether `Multisig`/`Utility` batching of these same calls under a `NonTransfer` proxy is equally guarded (it is, transitively, since `Utility`/`Multisig` dispatch preserves the same origin and calls back into the same filter).

### Proof of Concept
1. Victim account `V` grants delegate `D` a proxy of `ProxyType::NonTransfer`.
2. A liquidity pool for `(Native, AssetX)` already exists and `V` holds balance of both.
3. `D` submits `Proxy::proxy(real: V, force_proxy_type: Some(NonTransfer), call: AssetConversion::add_liquidity(Native, AssetX, amount1, amount2, 0, 0, mint_to: D))`.
   - `ProxyType::NonTransfer::filter` returns `true` because `RuntimeCall::AssetConversion { .. }` is not in the exclusion match against `Balances`/`Assets`/`NftFractionalization`/`Nfts`/`Uniques`.
   - Inner call executes with `ensure_signed(origin) == V`; `V`'s tokens are transferred to the pool account; LP tokens are minted to `D`.
4. `D` (using their own signed origin, no proxy needed) calls `AssetConversion::remove_liquidity(Native, AssetX, lp_token_burn, 0, 0, withdraw_to: D)`, redeeming the pooled assets to themselves.
5. Net effect: `V`'s assets have moved to `D` despite `V` only granting a `NonTransfer` proxy. [1](#0-0) [5](#0-4) [2](#0-1)

		pub(crate) fn do_remove_liquidity(
			who: &T::AccountId,
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			lp_token_burn: T::Balance,
			amount1_min_receive: T::Balance,
			amount2_min_receive: T::Balance,
			withdraw_to: &T::AccountId,
		) -> Result<(T::Balance, T::Balance), DispatchError> {
			let pool_id = T::PoolLocator::pool_id(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;

			ensure!(lp_token_burn > Zero::zero(), Error::<T>::ZeroLiquidity);

			let pool = Pools::<T>::get(&pool_id).ok_or(Error::<T>::PoolNotFound)?;

			let pool_account =
				T::PoolLocator::address(&pool_id).map_err(|_| Error::<T>::InvalidAssetPair)?;
			let (reserve1, reserve2) = Self::get_reserves(asset1.clone(), asset2.clone())?;

			let total_supply = T::PoolAssets::total_issuance(pool.lp_token.clone());
			let withdrawal_fee_amount = T::LiquidityWithdrawalFee::get() * lp_token_burn;
			let lp_redeem_amount = lp_token_burn.saturating_sub(withdrawal_fee_amount);

			let amount1 = Self::mul_div(&lp_redeem_amount, &reserve1, &total_supply)?;
			let amount2 = Self::mul_div(&lp_redeem_amount, &reserve2, &total_supply)?;

			ensure!(
				!amount1.is_zero() && amount1 >= amount1_min_receive,
				Error::<T>::AssetOneWithdrawalDidNotMeetMinimum
			);
			ensure!(
				!amount2.is_zero() && amount2 >= amount2_min_receive,
				Error::<T>::AssetTwoWithdrawalDidNotMeetMinimum
			);
			let reserve1_left = reserve1.saturating_sub(amount1);
			let reserve2_left = reserve2.saturating_sub(amount2);
			ensure!(
				reserve1_left >= T::Assets::minimum_balance(asset1.clone()),
				Error::<T>::ReserveLeftLessThanMinimal
			);
			ensure!(
				reserve2_left >= T::Assets::minimum_balance(asset2.clone()),
				Error::<T>::ReserveLeftLessThanMinimal
			);

			// burn the provided lp token amount that includes the fee
			T::PoolAssets::burn_from(
				pool.lp_token.clone(),
				who,
				lp_token_burn,
				Expendable,
				Exact,
				Polite,
			)?;

			T::Assets::transfer(asset1, &pool_account, withdraw_to, amount1, Expendable)?;
			T::Assets::transfer(asset2, &pool_account, withdraw_to, amount2, Expendable)?;

			Self::deposit_event(Event::LiquidityRemoved {
				who: who.clone(),
				withdraw_to: withdraw_to.clone(),
				pool_id,
				amount1,
				amount2,
				lp_token: pool.lp_token,
				lp_token_burned: lp_token_burn,
				withdrawal_fee: T::LiquidityWithdrawalFee::get(),
			});

			Ok((amount1, amount2))
