### Title
Reward-per-token snapshot advances `last_update_block` without gating on any minimum accrual, letting a staker's own zero-value `stake`/`unstake` calls fragment reward accrual and skim rounding remainder from other stakers - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`Pallet::stake` and `Pallet::unstake` are public, unprivileged, fee-paying extrinsics that unconditionally call `update_pool_and_staker_rewards` before touching balances. That helper recomputes `reward_per_token` from the elapsed blocks since `last_update_block` and then immediately re-snapshots `last_update_block = now` via `update_pool_rewards`, regardless of whether the `amount` argument is zero or economically insignificant. This mirrors the exact broken invariant in the reported `LiquidityPool` bug: a public entrypoint that both consumes elapsed-time-based accrual and resets the time snapshot can be called by anyone, cheaply, on every block, fragmenting the accrual window down to the smallest possible size and repeatedly forcing the integer division in `reward_per_token` to round down.

### Finding Description
`reward_per_token` computes:
```rust
pool_info.reward_per_token_stored.ensure_add(
    pool_info.reward_rate_per_block
        .ensure_mul(rewardable_blocks_elapsed.into())?
        .ensure_mul(PRECISION_SCALING_FACTOR.into())?
        .ensure_div(pool_info.total_tokens_staked)?,
)
``` [1](#0-0) 

and `update_pool_rewards` immediately persists the new snapshot point:
```rust
new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
new_pool_info.reward_per_token_stored = reward_per_token;
``` [2](#0-1) 

Both `stake` and `unstake` call `update_pool_and_staker_rewards` unconditionally at the top of the extrinsic body, before validating or acting on `amount`:
```rust
let (mut pool_info, mut staker_info) =
    Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;
``` [3](#0-2) [4](#0-3) 

Neither call requires `amount > 0`. `stake` only freezes `amount` tokens and increments the total after the reward snapshot has already been consumed and re-based; `unstake` allows `amount == 0` outright since `staker_info.amount >= 0` is trivially satisfied and there's no `ensure!(!amount.is_zero(), ...)` guard.

The corrupted value is `PoolInfo::reward_per_token_stored` (and derivatively `PoolStakerInfo::rewards` for every other concurrent staker in the pool via `derive_rewards`). Because `rewardable_blocks_elapsed` is truncated to whatever a caller chooses between their own zero-amount calls (as low as `1` block, or `0` if called twice in the same block), the numerator `reward_rate_per_block * elapsed * PRECISION_SCALING_FACTOR` shrinks per call, and each call's integer division by `total_tokens_staked` floors independently. Splitting one large elapsed-time reward computation into many tiny ones strictly increases the total floor-rounding loss versus computing it once over the full interval, exactly as in the reported LP contract where splitting `ownershipTime` into 3600 one-second calls understated interest by ~35% versus a single one-hour computation.

Existing guards do not stop this: there is no `ensure!(!amount.is_zero())` on either `stake` or `unstake`, no minimum-elapsed-blocks gate in `update_pool_rewards`, and `PRECISION_SCALING_FACTOR` is a small constant (`4096`), so the floor-division loss per call is non-negligible relative to typical `reward_rate_per_block` values.

### Impact Explanation
The scaling factor `PRECISION_SCALING_FACTOR = 4096` is intended to preserve reward precision, but repeated self-serving zero/low-amount calls to the public `stake`/`unstake` extrinsics let any pool participant fragment the elapsed-block accrual arbitrarily finely, each fragment floor-rounded independently. This systematically understates `reward_per_token_stored`, permanently reducing the rewards owed to every other staker in that pool relative to what a single, un-fragmented accrual would have produced, while the pool's underlying reward-asset balance (funded by the admin's `reward_rate_per_block` budget) does not shrink correspondingly — the difference becomes stranded dust in the pool account rather than being paid out, degrading the payout accounting for legitimate stakers. This is a value-conservation violation in a public, permissionless reward-accrual pallet (`pallet-asset-rewards`), aligning with the "public underpriced work" / "state settles incorrectly" impact category.

### Likelihood Explanation
Likelihood is Medium: `stake`/`unstake` are ordinary signed extrinsics reachable by any account holding the staked asset (or, for `unstake`, by the staker themselves at any time), require no elevated origin, and cost only normal transaction fees plus weight. An attacker who is also a staker in the pool is directly incentivized to depress `reward_per_token_stored` growth for competing stakers by spamming minimal `stake`/`unstake` calls each block, similar to the original report's incentive for a borrower to reduce their own accrued interest by spamming zero-amount `borrow` calls.

### Recommendation
Require `ensure!(!amount.is_zero(), Error::<T>::...)` in both `stake` and `unstake` (mirroring the report's suggested `require` on `LiquidityPool::borrow`), and/or gate `update_pool_rewards`'s snapshot advance so that `reward_per_token` accrual is computed and persisted using full precision independent of how many times it is invoked within an elapsed-block window (e.g., retain unconsumed remainder rather than flooring on every call, or accumulate a running remainder across snapshots).

### Proof of Concept
1. Runtime with `pallet-asset-rewards`; create a pool with `reward_rate_per_block = R` and `total_tokens_staked = S` (a value that does not evenly divide `R * PRECISION_SCALING_FACTOR`).
2. Staker A stakes once at block `N` and waits until block `N + 100` before calling `unstake(1)` (minimal amount) — record `reward_per_token_stored` after this single accrual: `reward_per_token_stored_A`.
3. Reset state; staker A instead calls `unstake(0)` (or `stake(0)` if permitted) once per block for 100 consecutive blocks starting at `N`, then observes `reward_per_token_stored` at block `N + 100`: `reward_per_token_stored_B`.
4. Compare: `reward_per_token_stored_B < reward_per_token_stored_A` because each of the 100 single-block accruals in step 3 independently floors `R * 1 * PRECISION_SCALING_FACTOR / S`, whereas step 2's single 100-block accrual floors `R * 100 * PRECISION_SCALING_FACTOR / S` only once, losing far less to rounding. 		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
