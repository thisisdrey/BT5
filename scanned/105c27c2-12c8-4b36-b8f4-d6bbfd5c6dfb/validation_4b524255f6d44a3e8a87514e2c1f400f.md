Based on my investigation, I found a concrete local analog to the "excess fees / unchecked value" bug class in the Snowbridge v2 tip mechanism.

### Title
Unbacked relayer-reward inflation via `add_tip` with no reconciliation to actually-collected value - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`, `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The Snowbridge `add_tip` extrinsic on BridgeHub takes a raw `amount: u128` parameter and forwards it directly to `AddTip::add_tip`, which unconditionally increases the stored `PendingOrders` fee for a message nonce. That inflated fee is later paid out in full to the relayer as a real reward via `T::RewardPayment::register_reward`. Nowhere in this call path does the pallet verify that `amount` corresponds to any value actually withdrawn/collected from the `sender`. This mirrors the `AssetController._relayTransfer` bug: a caller-supplied numeric value is trusted and propagated into fund-moving logic without a matching `msg.value`/collected-amount check.

### Finding Description
`snowbridge_pallet_system_v2::Pallet::add_tip` [1](#0-0)  is guarded only by `T::FrontendOrigin::ensure_origin(origin)`, then dispatches:
```
Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
```
The `amount` here is an arbitrary caller-supplied `u128` — there is no local storage read of a corresponding deposited/reserved asset amount, no `ensure!(collected == amount)` check, and no withdrawal call in this pallet.

On the outbound side, the `AddTip` implementation for the outbound-queue-v2 pallet blindly increments the pending fee:
```rust
impl<T: Config> AddTip for Pallet<T> {
    fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
        ensure!(amount > 0, AddTipError::AmountZero);
        PendingOrders::<T>::try_mutate_exists(nonce, |maybe_order| -> Result<(), AddTipError> {
            match maybe_order {
                Some(order) => {
                    order.fee = order.fee.saturating_add(amount);
                    Ok(())
                },
                None => Err(AddTipError::UnknownMessage),
            }
        })
    }
}
``` [2](#0-1) 

That `order.fee` is later paid out in full, with real value, to the relayer's reward account once a delivery receipt is submitted:
```rust
let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;
if order.fee > 0 {
    T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee);
}
``` [3](#0-2) 

`register_reward` credits `RelayerRewards` storage directly [4](#0-3) , and that reward is later paid out via `claim_rewards`/`claim_rewards_to`, which performs a real `Currency`/asset transfer to the relayer/beneficiary [5](#0-4) .

This is structurally the same defect pattern as the reported `AssetController._relayTransfer`: a caller-controlled numeric value (`fees[i]` / `amount`) is propagated into a value-moving/crediting path (`relayMessage{value: fees[i]}` / `order.fee.saturating_add(amount)`) with no local check that the number is backed by anything actually paid in. In the Solidity report the consequence is stuck excess ETH; here the consequence is inverted but analogous in class — a numeric "fee promise" is credited into a payout ledger (`PendingOrders.fee` → `RelayerRewards`) without verifying that value was actually collected anywhere in this pallet's own logic.

### Impact Explanation
If the value of `amount` passed by the calling side (the AssetHub `system-frontend` pallet, reached via XCM `Transact` with `FrontendOrigin`) is not perfectly reconciled 1:1 against an actual asset withdrawal on the AssetHub side for every code path, an attacker can inflate `PendingOrders.fee` for a nonce and cause `pallet-bridge-relayers` to register and pay out a reward that was never actually funded — i.e., unbacked mint of relayer rewards paid out of the bridge's reward/sovereign account. This directly matches the "theft or unbacked mint" impact criteria for live-scope Snowbridge/BridgeHub issues.

### Likelihood Explanation
The `add_tip` extrinsic is origin-gated by `FrontendOrigin`, which is intended to represent only the trusted sibling AssetHub `system-frontend` pallet acting through XCM `Transact`. The vulnerability is therefore latent rather than directly reachable by an arbitrary local BridgeHub account: exploitability depends entirely on whether `system-frontend`'s call-construction logic on AssetHub always withdraws/burns exactly `amount` before issuing this XCM call. I was not able to fully inspect `bridges/snowbridge/pallets/system-frontend/src/lib.rs` in the time available to confirm or rule out a mismatch there, so this should be treated as an unconfirmed but structurally real gap: the reconciliation guarantee is not enforced by the receiving pallet at all, so the entire security property rests on the sender-side implementation being perfectly correct on every call path (including benchmarking/test-only code paths, and any future callers of `FrontendOrigin`).

### Recommendation
Add a defensive check inside `outbound-queue-v2::AddTip::add_tip` (and the inbound-queue-v2 equivalent) and/or `system-v2::add_tip` to ensure the reward pot is only inflated by value that this pallet can itself verify was collected — e.g., require the caller to also transfer/burn the tip asset atomically within the same call (mirroring the `require(msg.value == totalFees)` pattern from the remediated report), rather than trusting a bare `u128` parameter forwarded across the XCM boundary. At minimum, add an explicit invariant test/assertion that `system-frontend`'s `amount` sent in `add_tip` always equals the amount actually withdrawn from the origin's account in the same XCM program, and reject the call otherwise.

### Proof of Concept
Conceptual PoC (requires confirming the `system-frontend` call path does not itself enforce withdrawal parity):
1. An account on AssetHub triggers (through whatever public path invokes `system-frontend`'s tip-forwarding logic) a call that ends up executing, via XCM `Transact` under `FrontendOrigin`, `snowbridge_pallet_system_v2::Pallet::add_tip(sender, Outbound(nonce), amount)` with `amount` larger than any value actually withdrawn from `sender`.
2. On BridgeHub, `outbound_queue_v2::AddTip::add_tip` increments `PendingOrders::<T>::get(nonce).fee` by `amount` unconditionally [2](#0-1) .
3. Once the relayer submits `submit_delivery_receipt`, `process_delivery_receipt` pays out the entire inflated `order.fee` (including the unbacked tip) to the reward account via `T::RewardPayment::register_reward` [6](#0-5) .
4. The relayer (or an account controlled by the attacker acting as "relayer"/reward beneficiary) calls `pallet_bridge_relayers::claim_rewards`/`claim_rewards_to` to withdraw the unbacked amount from the bridge reward/sovereign account [5](#0-4) .

Note: full confirmation requires reading `bridges/snowbridge/pallets/system-frontend/src/lib.rs` to verify whether it enforces amount-to-withdrawal parity before issuing the `add_tip` XCM call; this file's content could not be fully retrieved within the available tool budget. If the codebase index does not contain the full contents needed, a Devin session with full repository access would be required to verify this path conclusively.

				});
			}

				sender,
				message_id,
				amount,
				success: result.is_ok(),

		) {
			if reward_balance.is_zero() {

			RelayerRewards::<T, I>::mutate(

						old_reward.unwrap_or_else(Zero::zero).saturating_add(reward_balance);

					tracing::trace!(
						target: crate::LOG_TARGET,
						?relayer,
						?reward_kind,
						?new_reward,
						"Relayer can now claim reward for serving payer"
					);

					Self::deposit_event(Event::<T, I>::RewardRegistered {
						relayer: relayer.clone(),
						reward_kind,
						reward_balance,
