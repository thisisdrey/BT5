## Analysis

The external report's core broken invariant: a status/outcome field is captured from an external message but never actually enforced/checked before the contract commits state changes (payout + status finalization) based on the *unverified* value of that field. The real bug is that a field carried in the callback payload is decoded but not gated on before irreversible settlement happens.

A directly analogous flaw exists in `pallet_snowbridge_outbound_queue_v2`'s delivery-receipt handling. The `DeliveryReceipt` decoded from the Ethereum event log carries a `success: bool` field [1](#0-0)  indicating whether the message dispatch on Ethereum actually succeeded, but `Pallet::process_delivery_receipt` never reads or checks this field before paying the relayer reward and clearing the pending order: [2](#0-1) 

### Title
Reward for cross-chain message delivery is paid without checking the proven delivery `success` status - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`process_delivery_receipt` verifies the Ethereum event proof (gateway match, log validity) but ignores the `success` field of the decoded `InboundMessageDispatched` event. As a result, a delivery receipt proving that the message execution on Ethereum *failed* still triggers full reward payout to the relayer and permanently deletes the `PendingOrder`, exactly mirroring the reported class of bug: a status value is present and cryptographically/proof-bound, but the settlement logic does not actually gate on it before advancing state and paying out value.

### Finding Description
`submit_delivery_receipt` calls `T::Verifier::verify` on the event log/proof, then decodes it into a `DeliveryReceipt` and calls `process_delivery_receipt` [3](#0-2) . Inside `process_delivery_receipt`, only `receipt.gateway` is checked against `T::GatewayAddress`; `receipt.nonce` is used purely to look up the `PendingOrder`, and `receipt.success` is never read at all: [2](#0-1) 

The `PendingOrder` struct itself carries no success/failure tracking either — only `nonce`, `block_number`, and `fee` [4](#0-3) . So the pallet has cryptographic proof of the real outcome (`success = false` for a failed dispatch on Ethereum) but the on-chain reward/settlement logic is structurally incapable of distinguishing it from a successful delivery.

This is the same class of defect as H-14: a status field is transmitted and even proof-verified, but the code path that determines fund movement and final state (`MessageDelivered` event, removal of `PendingOrders` entry, `RewardPayment::register_reward`) does not condition on that status value.

### Impact Explanation
Any relayer who dispatches a message to Ethereum that fails execution (e.g., reverts on the Gateway/dispatch step, but still emits `InboundMessageDispatched` with `success = false`) can submit that receipt and still be paid the full relay reward (`order.fee`) from `T::RewardPayment`. This is a direct, unconditional value-transfer bug: an underpriced/incorrect payout that pays for work that was not actually completed. It also permanently deletes the `PendingOrder`, so there is no other in-protocol path to retry or correctly resolve a failed delivery — the fee is paid regardless of outcome and bookkeeping is finalized as if delivery succeeded. This satisfies the "duplicate settlement or payout" / conservation-of-value impact category directly, without any privileged, malicious-validator, or governance assumption — an ordinary relayer submitting a real, valid proof triggers it.

### Likelihood Explanation
No front-running, race condition, or malicious peer/validator assumption is required. Any relayer who happens to relay a message whose Ethereum-side dispatch fails (which is an expected, non-adversarial occurrence — e.g., insufficient gas, reverting command, or an intentionally malformed but validly-proven message) can simply call `submit_delivery_receipt` with the honestly-obtained proof and receive the reward anyway. This makes the issue trivially and repeatably triggerable under normal relayer operation, not merely a theoretical edge case.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` when `receipt.success == true`; for `success == false`, do not pay full reward (e.g., only refund/partial-refund or emit a `MessageDeliveryFailed` event without paying the relayer fee), and consider whether the pending order should be retried rather than unconditionally removed.

### Proof of Concept
1. A message is queued and committed via `do_process_message`, creating a `PendingOrder { nonce, fee, block_number }` [5](#0-4) .
2. The relayer submits the message to Ethereum; execution reverts/fails on the Gateway, but the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. The relayer obtains a valid receipt proof for this log and calls `submit_delivery_receipt` on-chain.
4. `T::Verifier::verify` succeeds (the proof is legitimate), `DeliveryReceipt::try_from` decodes `success = false`.
5. `process_delivery_receipt` checks only the `gateway` address, looks up the `PendingOrder` by `nonce`, and unconditionally calls `T::RewardPayment::register_reward(&reward_account, ..., order.fee)`, then removes the order and emits `MessageDelivered`. The relayer is paid in full despite delivery having failed.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
