### Title
Silent zero-fee output in outbound-queue `calculate_fee` lets under-collection of the Ethereum-side relayer fee - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

### Summary
The external report's core broken invariant is: *an oracle/price-lookup function can silently return a degenerate value (0 / stale) without erroring, and the caller treats it as valid, feeding bad data into downstream fund-affecting logic.* The local analog is `Pallet::<T>::calculate_fee` in the Snowbridge outbound-queue pallet, which computes the DOT fee a user must pay to cover the remote (Ethereum-side) relayer reward. Even with fully validated, non-zero `PricingParameters` (`exchange_rate`, `fee_per_gas`, `rewards.remote`, `multiplier` all checked non-zero by `PricingParameters::validate`), the arithmetic in `calculate_fee` can produce a `remote` fee of exactly `0` due to integer truncation, and the function returns this degenerate value with no error, no revert, and no defensive check — exactly analogous to Chainlink's `latestRoundData` silently returning `0`.

### Finding Description
`calculate_fee` computes the remote-fee component as: [1](#0-0) 

The pipeline is: `calculate_remote_fee` (gas × fee_per_gas + reward, in wei) → downcast to `u128` → `FixedU128` multiply by `multiplier` → `checked_div` by `exchange_rate` → `convert_from_ether_decimals` (integer division by `10^decimals`). Every one of `exchange_rate`, `fee_per_gas`, `multiplier`, and `rewards.remote` is validated to be non-zero at the governance level via `PricingParameters::validate`: [2](#0-1) 

Despite that validation, the pallet's own test suite demonstrates that a fully valid, non-zero parameter set still yields `fee.remote == 0`: [3](#0-2) 

The test's own comment acknowledges the bug class explicitly: *"Though none zero pricing params the remote fee calculated here is invalid which should be avoided."* No `ensure!`/error path exists in `calculate_fee` for this case — the zero value is silently propagated into `Fee<T::Balance>` and returned to callers (e.g. the XCM `SnowbridgeExporter` fee-charging path used by `send_message_impl.rs` and the runtime API `calculate_fee` in `api.rs`) exactly like Chainlink's zero-answer round data being fed straight into `PriceOracle` without a staleness/sanity check. [4](#0-3) 

This fee value is what gets charged to the user submitting a cross-chain message (via the XCM exporter fee-payment flow), while the *actual* reward promised to the Ethereum relayer is independently taken from `pricing_params.rewards.remote` at message-commit time in `do_process_message`: [5](#0-4) 

Because these two values are decoupled, a config/param combination that drives `calculate_fee`'s remote component to zero means users are charged $0$ DOT for the remote leg while the protocol still commits to paying the full (non-zero) `rewards.remote` reward to whichever relayer delivers the message on Ethereum. The sovereign/treasury account effectively subsidizes relayer rewards that were never collected from the fee payer — a systemic under-collection that can be triggered merely by parameter magnitudes (small `fee_per_gas`/`gas_used_at_most` relative to `exchange_rate`/decimals), not by any malicious actor with special access.

### Impact Explanation
This falls under "public underpriced work that degrades block production or stalls bridge processing" and value-conservation guarantees for bridge rewards: fees charged to users must cover the reward promised to relayers. When `calculate_fee` silently truncates to zero, the queue keeps accepting and committing messages (since `do_process_message` does not re-validate the fee actually collected against the reward it commits to pay) while the DOT fee charged under-collects relative to the ETH-denominated reward baked into the message. Over time and at scale this drains the bridge's sovereign account backing relayer rewards without matching inflows, an unbacked-payout-style value leak, and — separately — makes the delivery economically underpriced from the perspective of the fee actually paid by the message sender versus the reward guaranteed on Ethereum.

### Likelihood Explanation
No privileged actor is required to trigger the truncation-to-zero path once parameters are within a normal, validated range (the test reproduces it with ordinary, fully-valid non-zero parameters: `exchange_rate = 1/1`, `fee_per_gas = 1`, `reward = 1`, `multiplier = 1`). This is a pure integer-arithmetic edge case reachable by any user who triggers fee calculation through normal message submission (e.g., via XCM `SnowbridgeExporter`), not requiring governance, a malicious relayer, or a compromised prover. Likelihood is elevated by the fact that the exact scenario is already reproduced by the pallet's own regression test, confirming it's a known, reachable path rather than a theoretical one.

### Recommendation
Add an explicit non-zero (or minimum-floor) check on the computed `remote` fee in `calculate_fee` before returning `Fee`, mirroring the recommendation from the external report: revert/fail loudly (return an error from the pallet's fee-calculation flow, or clamp to a safe minimum) rather than silently returning `0`, and reconcile the fee actually charged to users with the `rewards.remote` value committed on-chain in `do_process_message` so they cannot diverge.

### Proof of Concept
The existing unit test is a direct PoC: [3](#0-2) 
With `PricingParameters { exchange_rate: 1/1, fee_per_gas: 1, rewards: { local: 1, remote: 1 }, multiplier: 1/1 }` — a fully valid, non-zero parameter set that passes `PricingParameters::validate` — `OutboundQueue::calculate_fee(250000, price_params)` returns `fee.remote == 0` while `fee.local == 698000000`. Any message sent under equivalent low-gas/param conditions would be charged zero for the remote leg while the committed message still carries the full non-zero `rewards.remote` value taken independently from `pricing_params.rewards.remote` in `do_process_message`, demonstrating the under-collection.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {
		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
			exchange_rate: FixedU128::from_rational(1, 1),
			fee_per_gas: 1_u32.into(),
			rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});
}

pub fn calculate_fee<T>(
	command: Command,
	parameters: Option<PricingParameters<T::Balance>>,
) -> Fee<T::Balance>
where
	T: Config,
{
	let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&command);
	let parameters = parameters.unwrap_or(T::PricingParameters::get());
	crate::Pallet::<T>::calculate_fee(gas_used_at_most, parameters)
}
