### Title
Missing EVM memory-expansion gas cost in pallet-revive allows underpriced memory-touching opcodes to degrade block production - (File: substrate/frame/revive/src/vm/evm/memory.rs)

### Summary
The external report concerns RSK failing to implement EIP-160 (EXP cost increase) and related Spurious Dragon EIPs, which were introduced specifically to raise the price of computation primitives that were previously too cheap relative to the work they generate, enabling DoS. The local analog is in `pallet-revive`'s custom EVM interpreter: while `EXP` itself correctly implements the EIP-160-style cost increase (`exp_cost` in `substrate/frame/revive/src/vm/evm/instructions/arithmetic.rs`), the interpreter's `Memory::resize` never charges the standard Ethereum quadratic memory-expansion cost. Every memory-touching opcode (`MLOAD`, `MSTORE`, `MSTORE8`, `RETURN`, `CODECOPY`, `CALLDATACOPY`, `KECCAK256`, `MCOPY`, call argument ranges) only pays a flat per-opcode price plus, at best, a cost linear in copied bytes — never a cost that scales with how much new memory was actually allocated/zeroed. This mirrors exactly the "missing EIP" bug class: a computation/resource-consuming primitive (memory growth) is underpriced relative to Ethereum's own anti-DoS gas schedule.

### Finding Description
`Memory::resize` in `substrate/frame/revive/src/vm/evm/memory.rs` only performs a hard cap check against `EVM_MEMORY_BYTES` (1 MiB) and then grows the backing `Vec<u8>`, without any gas/weight charge: [1](#0-0) 

Compare this to real Ethereum, where every memory expansion (whether via `MLOAD`, `MSTORE`, `RETURN`, `CODECOPY`, etc.) is charged the quadratic memory-expansion cost `Cmem(words) = 3*words + words^2/512`, precisely because linear zero-filling/growth of the machine's working memory is a real, non-trivial cost that must not be underpriced (this is the same category of hardening that EIP-160 applied to `EXP`).

In `pallet-revive`'s implementation, opcodes that call `interpreter.memory.resize(...)` charge only their fixed opcode price:
- `MLOAD`/`MSTORE`/`MSTORE8`: flat `EVMGas(VERYLOW)`, independent of how far the offset pushes memory growth [2](#0-1) 
- `RETURN`-family (`return_inner`): resizes memory for `offset+len` with no expansion charge at all [3](#0-2) 
- `CODECOPY`/`CALLDATACOPY`/`RETURNDATACOPY` via `memory_resize`: charge only `RuntimeCosts::CopyToContract(len)` (a linear byte-copy cost), then call `interpreter.memory.resize` with zero additional charge for the expansion itself [4](#0-3) 
- `KECCAK256`: charges `RuntimeCosts::HashKeccak256(len)` then resizes memory with no separate expansion charge [5](#0-4) 

Because `MSTORE`/`MSTORE8` charge a constant `VERYLOW` (3 gas-equivalent weight) regardless of offset, a contract can issue a single `MSTORE8` at offset close to `EVM_MEMORY_BYTES` (1 MiB) and force the interpreter to allocate and zero up to ~1 MiB of memory (`self.data.resize(target_len, 0)`), for the same fixed price as writing one byte at offset 0. Repeating this pattern (e.g., inside a loop that also invalidates the freshly grown memory or calls into nested frames) lets an attacker generate real allocation/zeroing/PoV work per opcode that is priced identically to trivial, no-growth operations — i.e. "public underpriced work" in EVM-execution terms, directly analogous to underpriced `EXP` in the original report.

### Impact Explanation
Weight/gas metering in `pallet-revive` is what bounds how much real computation and memory work a transaction can force per unit of declared weight/gas, which in turn bounds block-building time and PoV size. If memory-expansion is unpriced, an attacker can craft EVM-compatible contracts that repeatedly force maximal (bounded by `EVM_MEMORY_BYTES`) memory growth/zeroing across many nested calls/frames within one transaction, at a gas cost far below the real CPU/memory cost incurred by validators/collators executing it. This is the same "public underpriced work that degrades block production" class explicitly called out in the impact gate, since it lets an unprivileged attacker generate a favorable cost/work ratio purely through normal, permissionless contract execution — no relayer, validator, or governance actor is required.

### Likelihood Explanation
The path is reachable by any account able to deploy and call an EVM contract on a `pallet-revive`-enabled chain; no privileged role or malicious infra is needed. The affected opcodes (`MSTORE`, `MSTORE8`, `RETURN`, `CODECOPY`, `CALLDATACOPY`, `KECCAK256`, `MCOPY`) are all part of ordinary EVM bytecode and are exercised by essentially every real-world Solidity contract, making the underpriced primitive trivially triggerable and hard to distinguish from legitimate usage until abused at scale.

### Recommendation
Introduce an explicit EVM memory-expansion cost token (matching the standard `Cmem(words) = 3*words + words^2/512` formula, or an equivalent weight-based approximation) and charge it inside `Memory::resize` (or immediately before each call to it) whenever `target_len > current_len`, in addition to the existing per-opcode base cost and any linear copy/hash cost. This should be applied uniformly across all call sites in `substrate/frame/revive/src/vm/evm/instructions/{memory.rs,system.rs,control.rs,contract/call_helpers.rs}` so that no memory-touching opcode can grow the interpreter's memory buffer without paying a cost proportional to the newly allocated region, consistent with upstream Ethereum's post-Spurious-Dragon gas schedule.

### Proof of Concept
1. Deploy an EVM contract (via `pallet-revive`'s EVM compatibility path, `ContractBlob::from_evm_runtime_code`) containing a loop such as:
```
for i in 0..N {
    MSTORE8(OFFSET_NEAR_1MB, 0xFF)   // forces resize to ~1MiB every call, or repeatedly if OFFSET varies
}
```
2. Each `MSTORE8` call charges only the fixed `EVMGas(VERYLOW)` weight regardless of the actual size being zero-filled/allocated by `Memory::resize`, as shown in `substrate/frame/revive/src/vm/evm/instructions/memory.rs` lines 55-62 and `substrate/frame/revive/src/vm/evm/memory.rs` lines 65-79.
3. Measure `ext.frame_meter().weight_consumed()` before/after such a call (as done in the existing `test_long_exp_gas_cost_matches_specs` pattern in `modexp.rs`) and compare it against the real allocation/zero-fill cost of growing memory to `EVM_MEMORY_BYTES`; the charged weight will not scale with the memory growth, confirming the underpriced primitive.

	/// Resize memory to accommodate the given offset and length
	pub fn resize(&mut self, offset: usize, len: usize) -> ControlFlow<Halt> {
		let current_len = self.data.len();
		let target_len = revm::interpreter::num_words(offset.saturating_add(len)) * 32;
		if target_len > crate::limits::EVM_MEMORY_BYTES as usize {
			log::debug!(target: crate::LOG_TARGET, "check memory bounds failed: offset={offset} target_len={target_len} current_len={current_len}");
			return ControlFlow::Break(Error::<T>::OutOfGas.into());
		}

		if target_len > current_len {
			self.data.resize(target_len, 0);
		}

		ControlFlow::Continue(())
	}

/// Implements the MLOAD instruction.
///
/// Loads a 32-byte word from memory.
pub fn mload<E: Ext>(interpreter: &mut Interpreter<E>) -> ControlFlow<Halt> {
	interpreter.ext.charge_or_halt(EVMGas(VERYLOW))?;
	let ([], top) = interpreter.stack.popn_top()?;
	let offset = as_usize_or_halt::<E::T>(*top)?;
	interpreter.memory.resize(offset, 32)?;
	*top = U256::from_big_endian(interpreter.memory.slice_len(offset, 32));
	ControlFlow::Continue(())
}

/// Internal helper function for return operations.
///
/// Handles memory data retrieval and sets the return action.
fn return_inner<E: Ext>(
	interpreter: &mut Interpreter<E>,
	halt: impl Fn(Vec<u8>) -> Halt,
) -> ControlFlow<Halt> {
	let [offset, len] = interpreter.stack.popn()?;
	let len = as_usize_or_halt::<E::T>(len)?;

	// Important: Offset must be ignored if len is zeros
	let mut output = Default::default();
	if len != 0 {
		let offset = as_usize_or_halt::<E::T>(offset)?;
		interpreter.memory.resize(offset, len)?;
		output = interpreter.memory.slice_len(offset, len).to_vec()
	}

	ControlFlow::Break(halt(output))
}

pub fn keccak256<E: Ext>(interpreter: &mut Interpreter<E>) -> ControlFlow<Halt> {
	let ([offset], top) = interpreter.stack.popn_top()?;
	let len = as_usize_or_halt::<E::T>(*top)?;
	interpreter
		.ext
		.frame_meter_mut()
		.charge_or_halt(RuntimeCosts::HashKeccak256(len as u32))?;

	let hash = if len == 0 {
		H256::from(KECCAK_EMPTY)
	} else {
		let from = as_usize_or_halt::<E::T>(offset)?;
		interpreter.memory.resize(from, len)?;
		H256::from(keccak_256(interpreter.memory.slice_len(from, len)))
	};
	*top = U256::from_big_endian(hash.as_ref());
	ControlFlow::Continue(())
}

/// Common logic for copying data from a source buffer to the EVM's memory.
///
/// Handles memory expansion and gas calculation for data copy operations.
pub fn memory_resize<'a, E: Ext>(
	interpreter: &mut Interpreter<'a, E>,
	memory_offset: U256,
	len: usize,
) -> ControlFlow<Halt, Option<usize>> {
	if len == 0 {
		return ControlFlow::Continue(None);
	}

	interpreter.ext.charge_or_halt(RuntimeCosts::CopyToContract(len as u32))?;
	let memory_offset = as_usize_or_halt::<E::T>(memory_offset)?;
	interpreter.memory.resize(memory_offset, len)?;
	ControlFlow::Continue(Some(memory_offset))
}
