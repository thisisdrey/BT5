## Title
Unbounded `starting_block` in `pallet_vesting::vested_transfer` lets any signed account force a permanent, un-cancellable vesting lock and exhaust a victim's schedule slots - (File: `substrate/frame/vesting/src/lib.rs`, `substrate/frame/vesting/src/vesting_info.rs`)

### Summary
`vested_transfer` (call index 2) can be invoked by any signed account and lets the caller choose an arbitrary `target` and an arbitrary `VestingInfo{locked, per_block, starting_block}` for that target, with the only validation performed by `VestingInfo::is_valid()` and the `MinVestedTransfer` floor. Neither `starting_block` nor `per_block`/`locked` ratio have an upper bound. This mirrors the report's core flaw for `createVestingSchedule`: the function validates only that the numeric fields are non‑zero, but never bounds "how far in the future" a schedule can start, letting an attacker create a schedule for a victim account that can never begin vesting and can never be removed except by root.

### Finding Description
`is_valid()` only checks `locked != 0` and `per_block != 0`: [1](#0-0) 

`do_vested_transfer` re-uses this same weak check and then unconditionally transfers currency and calls `add_vesting_schedule`: [2](#0-1) 

`vested_transfer` is a plain signed extrinsic — `source` is the caller, but `target` is chosen by the caller and never has to consent: [3](#0-2) 

Because `starting_block` is unbounded (any `BlockNumberFor<T>` value, including near `BlockNumber::max_value()`), `locked_at` will always report the full `locked` amount as locked for as long as `n < starting_block`: [4](#0-3) 

`add_vesting_schedule` pushes this schedule into the target's `Vesting` storage and calls `write_lock`, so the victim's balance gets `set_lock`/`extend_lock`-ed and one of their limited `MAX_VESTING_SCHEDULES` slots is consumed, guarded only by a slot-count check: [5](#0-4) 

There is no dispatchable that lets the victim (a normal signed account) remove or cancel an unwanted schedule — the only removal path, `force_remove_vesting_schedule`, requires `ensure_root`: [6](#0-5) 

`merge_schedules` (also signed) cannot help either, since merging two not-yet-started schedules whose start is far in the future simply produces another far-future schedule (`starting_block = max(...)`), and `vest`/`vest_other` are no-ops while `now < starting_block`.

### Impact Explanation
An unprivileged attacker can, for the cost of `MinVestedTransfer` tokens per call, repeatedly call `vested_transfer(target, VestingInfo::new(MinVestedTransfer, 1, BlockNumber::MAX))` against any victim account. Each call:
1. Transfers a small (attacker-chosen minimum) amount of currency into the victim's account which becomes permanently locked (the schedule never starts, so `locked_at` never decreases) — a direct instance of "permanent user-fund lock".
2. Consumes one of the victim's fixed `MAX_VESTING_SCHEDULES` slots via `can_add_vesting_schedule`'s `AtMaxVestingSchedules` check.

Once the victim's schedule count reaches `T::MAX_VESTING_SCHEDULES`, all future legitimate `vested_transfer`/`force_vested_transfer` calls targeting that account fail with `AtMaxVestingSchedules`, permanently denying the account any further vesting-based payouts (e.g., salary/team vesting, ICO distributions) unless governance intervenes with root-only `force_remove_vesting_schedule`. This is a runtime bug compromising intended behavior (vesting availability) and causes fund lock/denial-of-service without requiring any privileged actor, satisfying the "runtime bugs that compromise intended behavior" and "permanent user-fund lock" impact categories.

### Likelihood Explanation
High: `vested_transfer` is a normal signed extrinsic reachable by any account with enough balance to cover `MinVestedTransfer` and existential deposit; no admin, governance, or privileged role is required. The only cost is the locked deposit amount (which can be the configured minimum) times the number of schedule slots to fill.

### Recommendation
- Add an upper bound on `starting_block` relative to the current block (e.g., a configurable `MaxVestingStart`), and/or require the transfer to be a no-op/rejected if the computed vesting never completes within a bounded horizon.
- Consider requiring target consent (e.g., an explicit "accept vesting" step) or letting the target account remove/cancel schedules that have not yet started, instead of restricting removal to `ensure_root`.
- Alternatively/additionally, allow signed self-service removal of not-yet-started schedules to prevent slot exhaustion griefing.

### Proof of Concept
1. Attacker account `A` (already has `>= MinVestedTransfer + ExistentialDeposit` balance) targets victim `V`.
2. For `i` in `0..MAX_VESTING_SCHEDULES`: `A` calls `Vesting::vested_transfer(A, V, VestingInfo::new(MinVestedTransfer, 1, BlockNumberFor::<T>::max_value()))`.
3. Each call passes `is_valid()` (locked != 0, per_block != 0) and `can_add_vesting_schedule` (slot count check), succeeds, transfers `MinVestedTransfer` from `A` to `V`, and adds a schedule that will never start (since `now` will never reach `BlockNumber::max_value()`), as shown by `locked_at` in `vesting_info.rs` lines 87-101.
4. After `MAX_VESTING_SCHEDULES` calls, `V`'s `Vesting` storage is full; any subsequent `vested_transfer`/`force_vested_transfer` to `V` fails with `Error::AtMaxVestingSchedules` (see `can_add_vesting_schedule`, lines 818-837), and `V` cannot self-remove any schedule (`force_remove_vesting_schedule` requires `ensure_root`, lines 462-490).

```rust
	/// Amount locked at block `n`.
	pub fn locked_at<BlockNumberToBalance: Convert<BlockNumber, Balance>>(
		&self,
		n: BlockNumber,
	) -> Balance {
		// Number of blocks that count toward vesting;
		// saturating to 0 when n < starting_block.
		let vested_block_count = n.saturating_sub(self.starting_block);
		let vested_block_count = BlockNumberToBalance::convert(vested_block_count);
		// Return amount that is still locked in vesting.
		vested_block_count
			.checked_mul(&self.per_block()) // `per_block` accessor guarantees at least 1.
			.map(|to_unlock| self.locked.saturating_sub(to_unlock))
			.unwrap_or(Zero::zero())
	}
```

```rust
			target: <T::Lookup as StaticLookup>::Source,

			ensure_root(origin)?;
			let who = T::Lookup::lookup(target)?;

				MaxLocksOf::<T>::get(),
				schedules_count as u32,

		}
```

```rust
	/// Ensure we can call `add_vesting_schedule` without error. This should always
	/// be called prior to `add_vesting_schedule`.
	fn can_add_vesting_schedule(
		who: &T::AccountId,
		locked: BalanceOf<T>,
		per_block: BalanceOf<T>,
		starting_block: BlockNumberFor<T>,
	) -> DispatchResult {
		// Check for `per_block` or `locked` of 0.
		if !VestingInfo::new(locked, per_block, starting_block).is_valid() {
			return Err(Error::<T>::InvalidScheduleParams.into());
		}

		ensure!(
			(Vesting::<T>::decode_len(who).unwrap_or_default() as u32) < T::MAX_VESTING_SCHEDULES,
			Error::<T>::AtMaxVestingSchedules
		);

		Ok(())
	}
```
