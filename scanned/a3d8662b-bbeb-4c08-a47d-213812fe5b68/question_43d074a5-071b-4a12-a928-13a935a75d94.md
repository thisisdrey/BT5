Preconditions: attacker crafts the `MultiPayload` JSON directly (bypassing the typed constructors) with two `TokenId` string keys that are byte-different but must serialize/deserialize to the same key. Call sequence: `execute_intents` -> deserialize `DefusePayload` -> `Amounts`/`TokenDeltas` collection construction -> intent execution. Binding: number of distinct `TokenId` keys after deserialization == number of distinct `(contract, token)` real assets named in the signed payload; no two syntactically different `TokenId` strings collapse into one key unless they denote the same asset. Scoped impact: Critical - a leg of a signed batch could be silently dropped or merged, leaving the executed deltas not netting to zero relative to what was signed. Whose funds: the signer whose intended balance change was dropped/merged. Proof idea: cargo test deserializing a `MultiPayload` JSON with two `TokenId` string variants that should be distinct and asserting the resulting `Amounts`/`TokenDeltas` map has exactly as many entries as distinct signed legs.
