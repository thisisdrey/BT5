In `FungibleTokenWithdrawResolver::ft_resolve_withdraw` (contracts/defuse/src/contract/tokens/nep141/withdraw.rs), the refunded amount is `amount.0.saturating_sub(used)` where `used` comes from `promise_result_checked_json::<U128>(0)` returned by the *token contract the attacker controls* as `withdraw.token`. Attacker action: deploy a malicious FT contract, then submit an `FtWithdraw{token: <malicious_ft>, receiver_id, amount, msg: Some(..)}` intent so `ft_transfer_call` is invoked on it. Preconditions: attacker's account has `token_balances` entry for `<malicious_ft>` token id (e.g. via prior deposit). Call sequence: `internal_ft_withdraw` -> `do_ft_withdraw` -> attacker's `ft_transfer_call` returns arbitrary `U128` -> `ft_resolve_withdraw`. Binding: `used <= amount.0` is enforced via `.min(amount.0)`, but does `used` (claimed return) equal `amount actually transferred out of the Verifier's real custody of that fictitious token`? Since the token contract is attacker-controlled, `token_balances` debited need not equal any real backing asset. Impact: Critical — `TokenId::Nep141(malicious_ft)` inflated/burned balances give attacker Verifier-tracked balance disconnected from any real custodied asset that can later be re-deposited/traded against real tokens via `TokenDiff`. Proof idea: cargo test where malicious FT's `ft_transfer_call` returns `U128(0)` always (claiming nothing used) while actually consuming attacker's real tokens elsewhere, then assert refund credited equals full `amount` regardless of real transfer.
