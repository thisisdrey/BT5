# [M] M-4 s_defaultClientBasisPoints should be restricted

## Details
Thevulnerability originates from an unchecked initialization parameter in the fee distribution factory contract. A state variable that stores the default client basis points – a value that represents a percentage in hundredths of a percent – is expected to be strictly less than 10,000 (the maximum representing 100%). The contract does not enforce this upper bound before using the value in the fee‑distribution logic. Because the basis‑points value is later used in arithmetic that assumes it is a proper percentage, providing a value equal to or greater than 10,000 triggers a division‑by‑zero or overflow condition, causing the constructor of each newly deployed fee distributor to revert. An attacker or a careless operator can supply an out‑of‑range basis‑points value when calling the factory, which results in the fee distributor contract failing to be created. The immediate impact is a denial‑of‑service condition: legitimate users attempting to stake or receive fee payouts encounter a transaction that reverts with no explicit error message, and the protocol cannot instantiate the fee distributor needed for fee accounting. This situation affects any participant that relies on the fee distribution mechanism – stakers, delegators, and the protocol’s revenue model – because the expected flow of fee allocation is broken. The issue was discovered during a manual audit that examined the initialization sequence of the fee distributor contracts and noticed the absence of a validation check on the basis‑points parameter. It can be hard to notice in normal operation because the variable is internal to the factory and the failure only manifests at deployment time, not during routine fee calculations, so users may only see generic transaction failures without understanding the root cause. To remediate the problem, the contract should include an explicit require statement that enforces s_defaultClientBasisPoints < 10,000 before any arithmetic is performed or before the fee distributor is instantiated. This simple input validation prevents the erroneous state from propagating and restores the expected business logic that fee percentages never exceed 100 %. In broader terms, the bug belongs to the class of unchecked input validation errors that lead to arithmetic exceptions and contract initialization failures, violating the accounting assumption that percentages are bounded between 0 % and 100 %. From a user’s perspective the symptom is a transaction that reverts with no fee distribution contract being created, leaving balances unchanged and expected refunds or fee shares missing, contrary to the expectation that staking should generate a proportional reward.

## Recommendation
We recommend adding a check that sdefaultClientBasisPoints < 10000.
