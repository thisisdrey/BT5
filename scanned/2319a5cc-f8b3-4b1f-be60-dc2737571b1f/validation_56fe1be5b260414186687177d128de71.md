### Title
Unchecked `debug_assert!`-guarded fund transfers in `claim_bounty`/`claim_child_bounty` allow bounty state finalization and success events without actual payout, permanently locking funds - ([File: substrate/frame/bounties/src/lib.rs], [File: substrate/frame/child-bounties/src/lib.rs])

### Summary
The external report's core broken invariant is: a subordinate fund-movement call can silently fail/short-circuit (returning less than requested, or not moving funds at all) while the calling function does not validate the actual outcome and instead proceeds to finalize state and pay out the originally *intended* amount, trusting the call succeeded. The same broken-invariant shape exists in `pallet-bounties::claim_bounty` and `pallet-child-bounties::claim_child_bounty`: both perform `T::Currency::transfer(...)` calls for curator fee and beneficiary payout, but only guard the result with `debug_assert!`, which compiles to a no-op in release/production builds. The extrinsics then unconditionally delete the bounty record and emit `BountyClaimed`/`Claimed` events carrying the full intended `payout`, regardless of whether the transfers actually succeeded.

### Finding Description
In `pallet_bounties::Pallet::claim_bounty`, the code computes `fee` and `payout` from the bounty account's `free_balance`, then does: [1](#0-0) 

Both `T::Currency::transfer` calls are only checked via `debug_assert!(res.is_ok())` — a macro that is stripped out entirely when `debug-assertions` are disabled (the default for production runtime builds). If either transfer returns `Err`, execution continues exactly as if it had succeeded: the bounty record is removed (`*maybe_bounty = None`), `BountyDescriptions` is removed, and `Event::BountyClaimed { payout, beneficiary }` is emitted with the full computed payout.

The exact same pattern exists in `pallet_child_bounties::Pallet::claim_child_bounty`: [2](#0-1) 

Here too, `fee_transfer_result` and `payout_transfer_result` are only checked with `debug_assert!`, after which the child bounty is unconditionally removed from storage (`*maybe_child_bounty = None`), counts are decremented, descriptions removed, and `Event::Claimed { payout, beneficiary }` is emitted — independent of whether the transfer actually moved funds.

Why the comments' assumption ("should not fail") does not hold: `T::Currency::transfer` with `Preservation::AllowDeath` only relaxes the *existential deposit* requirement on the source account; it does not override `Lock`/`Freeze` restrictions imposed on that account's balance (e.g. via `pallet_vesting`, `pallet_democracy` conviction locks, or any other freeze/lock provider configured in the runsime's `Balances` config). Both `bounty_account_id(bounty_id)` and `child_bounty_account_id(parent_id, child_id)` are addresses deterministically derived from a `PalletId` and public indices — they are computable off-chain by anyone and are ordinary `AccountId`s with no special protection. Any unprivileged account can send `pallet_vesting::vested_transfer` (or otherwise cause a lock to be placed) targeting that exact derived account, adding a `Frozen`/`Locked` balance component. When the legitimate transfer is later attempted for the exact fee/payout amount, `ensure_can_withdraw` fails due to insufficient *unlocked* balance and `T::Currency::transfer` returns `Err(LiquidityRestrictions)` (or similar) — silently swallowed by the `debug_assert!`.

### Impact Explanation
This breaks the required invariant that "payout state must only advance after ... settlement succeed[s] atomically." The consequence is:
- The bounty/child-bounty account funds remain permanently locked/orphaned: the storage entry that tracked them is deleted, so no other extrinsic can ever again reference or reclaim that derived account's balance through the pallet's normal flow.
- A `BountyClaimed`/`Claimed` event is emitted attesting a payout that never happened — false state acceptance/duplicate-settlement-adjacent behavior, misleading any off-chain indexer, treasury accounting, or downstream automation that treats the event as proof of payment.
- No admin, governance, validator, or relayer action is required — an ordinary user can pre-position a lock on the deterministic bounty account using a standard, permissionless extrinsic before the curator/anyone calls `claim_bounty`/`claim_child_bounty` (both are permissionless, `ensure_signed` is enough).

### Likelihood Explanation
Likelihood is moderate-to-high: bounty/child-bounty account addresses are trivially derivable off-chain from public `PalletId` and bounty index, `pallet_vesting::vested_transfer` (or comparable lock-adding extrinsics) is a standard public call available to any signed account, and the exploit requires no privileged role, no malicious relayer/validator, and no timing race beyond sending the lock-adding transaction before the claim is processed.

### Recommendation
Replace the `debug_assert!(...is_ok())` checks in both `claim_bounty` (`substrate/frame/bounties/src/lib.rs`) and `claim_child_bounty` (`substrate/frame/child-bounties/src/lib.rs`) with real error propagation (`?` or `ensure!`) so that a failed fee/payout transfer aborts the extrinsic (or at minimum prevents storage removal and event emission) rather than silently finalizing state. Additionally, consider using the actual transferred amount (returned/verified) rather than the pre-computed intended amount when emitting `BountyClaimed`/`Claimed`, mirroring the client's fix in the external report of validating the finalized amount against the requested amount before advancing state.

### Proof of Concept
1. Attacker (any account) observes/derives `bounty_account_id(bounty_id)` (or `child_bounty_account_id(parent_id, child_id)`) — a pure function of `PalletId` + index, needing no special permission to compute.
2. Before the bounty reaches `PendingPayout`/claim time, attacker calls `pallet_vesting::vested_transfer` (or another lock-adding public extrinsic) sending a small amount to that derived account with a long vesting schedule, causing a `Freeze`/`Lock` to be attached to that account's balance in excess of, or overlapping with, the bounty's principal/fee funds.
3. Once the bounty is awarded and the payout delay elapses, anyone calls `claim_bounty(bounty_id)` (or `claim_child_bounty`).
4. Inside the extrinsic, `T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath)` and/or the beneficiary transfer fail due to the lock (`ensure_can_withdraw` rejects the withdrawal), returning `Err`.
5. Because the check is only `debug_assert!(res.is_ok())` (no-op in release), the function proceeds: the bounty is removed from storage (`*maybe_bounty = None` / `*maybe_child_bounty = None`), descriptions removed, counts decremented, and `Event::BountyClaimed { payout, beneficiary }` / `Event::Claimed { payout, beneficiary }` is emitted with the full intended amount.
6. The actual bounty funds remain stuck in the now-untracked derived account; the beneficiary/curator received nothing despite the chain-emitted event claiming a successful payout of the full amount.
