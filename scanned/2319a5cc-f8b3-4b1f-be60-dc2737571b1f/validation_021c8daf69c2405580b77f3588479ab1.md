## Finding: `EthereumOutboundQueueV2::process_delivery_receipt` ignores the on-chain `success` flag, paying relayer rewards and permanently clearing settlement state for failed Ethereum-side deliveries

The zkSync report's core broken invariant is: *system state that represents "value moved/settled" is finalized based on an incomplete signal, without verifying that end-to-end execution actually succeeded.* The exact local analog is in Snowbridge's v2 outbound-queue delivery-receipt settlement path.

### Title
Outbound Queue V2 settles pending orders and pays relayer rewards without checking `DeliveryReceipt.success`, causing permanent loss of already-burned bridged assets on failed Ethereum execution - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` that explicitly carries a `success: bool` field sourced from Ethereum's `InboundMessageDispatched(nonce, topic, success, reward_address)` event [1](#0-0) , but never inspects `receipt.success` before paying the relayer reward and deleting the `PendingOrders` entry [2](#0-1) .

### Finding Description
When a user bridges assets from AssetHub to Ethereum (`InitiateTransfer` with `AssetTransferFilter::ReserveWithdraw`), the XCM executor's `do_reserve_withdraw_assets` immediately and irrevocably burns the assets locally via `reanchor_and_burn_local` before the message is even queued [3](#0-2) . The resulting `OutboundMessage` is committed to a merkle root and a `PendingOrder{nonce, fee, block_number}` is recorded [4](#0-3) .

Settlement is only supposed to finalize once the message is verified to have executed successfully on the Ethereum Gateway contract. However, `submit_delivery_receipt`/`process_delivery_receipt` only verifies the *proof* of the event log (that some `InboundMessageDispatched` event occurred with a matching gateway and nonce) — it never asserts `receipt.success == true`:

```
let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;
if order.fee > 0 {
    T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee);
}
<PendingOrders<T>>::remove(nonce);
Self::deposit_event(Event::MessageDelivered { nonce });
``` [5](#0-4) 

Any unprivileged, honest relayer (no malicious operator/relayer assumption required) can legitimately observe and submit a truthful receipt for a message whose Gateway-side execution reverted (`success: false` — e.g. insufficient user-supplied `gas`/`value` in a `CallContract`/Transact command, or an ERC-20 mint failure on the Ethereum side). The pallet still:
1. Pays the relayer's full fee reward via `T::RewardPayment::register_reward`, and
2. Permanently removes the `PendingOrders` entry, guarded against re-submission by `InvalidPendingNonce` [6](#0-5) .

Since the assets were already burned on the Substrate side before dispatch, and there is no code path that inspects `success` to trigger a refund/mint-back to the original sender, the assets are permanently lost with no recovery mechanism — this is the exact analog of the zkSync bug where `msg.value` accounting on one side is finalized independent of the true execution outcome on the other side, breaking the "value moves atomically and exactly once to the correct party" invariant.

### Impact Explanation
This breaks the required invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." Concretely:
- User funds bridged to Ethereum that fail to execute on the Gateway are permanently lost (burned on Substrate, never minted/refunded on Ethereum, and the corresponding `PendingOrder` accounting record is deleted so the failure can never be discovered/reconciled on-chain).
- Relayers are paid for delivering messages that did not actually succeed, an economic drain unrelated to actual useful work performed (public underpriced/incorrect settlement).

### Likelihood Explanation
This requires no malicious or privileged actor. Ethereum-side execution reverts happen naturally (e.g., insufficient `gas`/`value` supplied by the user in `ContractCall`, transient gas price spikes, or contract-level reverts), and any relayer — even an honest one just doing its job — can submit the resulting truthful `InboundMessageDispatched(success: false)` event as a valid delivery receipt, since `T::Verifier::verify` only checks header/receipt inclusion proofs, not the `success` semantics.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`:
- If `true`, proceed with the current reward payout and `PendingOrders` removal.
- If `false`, do not pay the relayer reward for successful delivery of a failed execution (or pay a reduced "delivery-only" reward if desired), and drive a compensating action (e.g. emit an event that triggers refund/mint-back of the burned assets to the original sender's location, or keep the order/failure recorded so governance/the user can claim recovery) instead of silently deleting the settlement record.

### Proof of Concept
1. A user submits `InitiateTransfer`/`ReserveWithdraw` from AssetHub to Ethereum; assets are burned immediately via `reanchor_and_burn_local`, and `EthereumOutboundQueueV2` records `PendingOrders[nonce] = {fee, ...}` [4](#0-3) .
2. On Ethereum, the Gateway contract processes the message but the `CallContract`/mint step reverts (e.g., insufficient `gas`), emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer (no collusion needed) gathers the proof of this real event and calls `submit_delivery_receipt`.
4. `T::Verifier::verify` succeeds (the event genuinely occurred and is provable); `DeliveryReceipt::try_from` decodes `success: false` correctly, but `process_delivery_receipt` never checks it — as shown by the existing test harness constructing `DeliveryReceipt { success: true, .. }` and asserting `assert_ok!(... process_delivery_receipt(...))` pays the reward and removes the order regardless [7](#0-6) ; substituting `success: false` in that same call still results in `Ok(())`, reward payout, and `PendingOrders::remove(nonce)`.
5. Result: the user's burned tokens are unrecoverable, the relayer is rewarded for a failed delivery, and the nonce can never be resubmitted (`InvalidPendingNonce` on retry).

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
