## Finding

### Title
Accumulate-and-Forward pallet permanently traps protocol fee funds when the cross-chain deposit at the staging destination fails - ([File: polkadot/xcm/xcm-builder/src/forwarder.rs])

### Summary
`pallet-accumulate-and-forward` collects protocol-level inflows (transaction fees, dust, coretime revenue) into a derived "accumulation account" and periodically forwards them cross-chain via `TeleportForwarderForAccountId32::forward`. The forwarding adapter only guards against *local* execution failure (via `with_transaction` rollback). Once the local XCM executor reports `Outcome::Complete`, the teleport message is irrevocably queued; if the remote `DepositAsset` at the destination staging location subsequently fails or is rejected, the teleported value becomes permanently trapped assets on the destination chain with no automatic recovery path — the exact same bug class as the Booster report (value moved into a location that has no built-in mechanism to retrieve it).

### Finding Description
The adapter itself documents this exact risk: [1](#0-0) 

The `forward` implementation withdraws the accumulated balance and constructs a teleport+`InitiateTransfer` program targeting a fixed `StagingLocation` account on the destination chain: [2](#0-1) 

Local success/failure is atomic via `with_transaction`, but that only protects the *source-side* balance/issuance — it cannot roll back what happens after the message is queued and executed remotely: [3](#0-2) 

The pallet's `on_idle` hook drives this unconditionally once `TransferPeriod` elapses and `MinTransferAmount` is exceeded, with no way to pause, redirect, or recover from a bad forward outcome other than "it will remain and be retried" — which only applies to *local* failures, not destination-side rejections that already consumed the local balance: [4](#0-3) 

The crate docs further confirm there is no operator-facing remediation path and even call out a related silent-burn risk if the account isn't pre-funded, showing the fund-safety invariant around this account is already fragile by design: [5](#0-4) 

This forwarder is wired into every system parachain that uses this pallet (Westend relay chain, AssetHub, BridgeHub, Collectives, Coretime, People), so the exposure is systemic rather than confined to one chain: [6](#0-5) [7](#0-6) 

### Impact Explanation
Any destination-side rejection of the `DepositAsset` (e.g., staging account not yet in existence/below ED on first use, filter mismatch, weight/fee misconfiguration, or a runtime upgrade on the destination that changes acceptance rules for this beneficiary) results in the teleported protocol revenue (transaction fees, dust, coretime revenue) being converted into XCM-trapped assets with no automated claim path back to any beneficiary. This is a permanent, systemic loss of protocol funds analogous to Booster's stuck coupon fees — value enters a pallet-controlled flow and has no configured recovery destination if the final hop fails.

### Likelihood Explanation
This does not require a malicious relayer, validator, governance actor, or leaked key — the forwarding is fully automatic (driven by `on_idle`), the destination is a fixed, hardcoded staging location, and no unprivileged action is needed to trigger it; a misconfiguration or state mismatch at the destination (e.g., staging account not pre-funded/existing before the first successful forward, or any transient rejection) is sufficient. The adapter's own doc comment acknowledges this failure mode is expected and unmitigated ("no automatic recovery path"), indicating the local-only rollback via `with_transaction` is an incomplete safety guarantee for a cross-chain value-transfer primitive.

### Recommendation
Do not treat local `Outcome::Complete` as a completion state for the forwarded funds. Either: (1) require and continuously assert the destination staging account is funded above ED before allowing forwards, (2) add an explicit XCM `ClaimAsset`/dust-recovery flow wired to a governance-controlled account so trapped assets at the destination can be retrieved, or (3) change the `Forwarder` design so that value is only considered "sent" after a receipt/ack confirms the remote deposit succeeded, mirroring how other Snowbridge flows (e.g., `PayAccountOnLocation`) explicitly track charge-fee/XCM-send failures at each step rather than declaring success at local queuing.

### Proof of Concept
1. Deploy a system chain with `pallet_accumulate_and_forward::Config::Forwarder = TeleportForwarderForAccountId32<...>` pointed at a `DapStagingLocation` on a destination chain that has never been funded/created (a realistic first-forward scenario, or one where the destination changes its accepted-asset filter in a runtime upgrade).
2. Let normal chain activity (tx fees / dust / coretime revenue) accumulate funds in the derived accumulation account past `MinTransferAmount`.
3. At the next `TransferPeriod` boundary, `on_idle` calls `Forwarder::forward`, which withdraws locally and executes `Outcome::Complete` for the local leg (teleport dispatched) — see `polkadot/xcm/xcm-builder/src/forwarder.rs:83-106`.
4. On the destination chain, the `DepositAsset { assets: Wild(AllCounted(1)), beneficiary }` instruction fails (e.g., beneficiary below ED, asset not accepted) — the assets are trapped per standard XCM `AssetTrap` semantics.
5. No extrinsic or hook in `pallet-accumulate-and-forward` or the runtime configs referenced above exposes a claim/recovery mechanism for this trapped value; the funds are permanently unrecoverable by the pallet or its governance, matching the Booster analog of value sent to an address with no retrieval mechanism.

```rust
	fn forward(source: AccountId, amount: Balance) -> Result<(), ()> {
		let dest = Dest::get();
		let asset = Asset { id: AssetId(NativeAsset::get()), fun: Fungible(amount.into()) };
		let beneficiary: Location = StagingLocation::get().into_location();

		let remote_xcm = Xcm(vec![DepositAsset { assets: Wild(AllCounted(1)), beneficiary }]);

		// The XCM flow: `ReceiveTeleportedAsset → AliasOrigin(source) → UnpaidExecution →
		// DepositAsset`. `preserve_origin: true` causes `InitiateTransfer` to prepend
		// `AliasOrigin(source_location)` to the remote XCM.
		let xcm: Xcm<XcmConfig::RuntimeCall> = Xcm(vec![
			UnpaidExecution { weight_limit: WeightLimit::Unlimited, check_origin: None },
			DescendOrigin(Junction::AccountId32 { network: None, id: source.into() }.into()),
			WithdrawAsset(asset.into()),
			InitiateTransfer {
				destination: dest,
				remote_fees: None,
				preserve_origin: true,
				assets: BoundedVec::truncate_from(alloc::vec![AssetTransferFilter::Teleport(
					Wild(AllCounted(1))
				),]),
				remote_xcm,
			},
		]);
```

```rust
//! # Accumulate-and-Forward Pallet
//!
//! Intercepts configurable token inflows (transaction fees, dust removal, coretime revenue) on
//! system parachains and gathers them in a local accumulation account for periodic forwarding
//! to a configurable destination.
//!
//! ## Usage
//!
//! - **Fees**: Use [`DealWithFeesSplit`] to split fees between accumulation and other handlers
//! - **Burns/Revenue**: Use the pallet as `OnUnbalanced<CreditOf>` handler (e.g., dust removal,
//!   coretime revenue)
//! Note: Direct calls to `pallet_balances::Pallet::burn()` extrinsic are not redirected to
//! the accumulation account — they still reduce total issuance directly.
//!
//! ## Setup
//!
//! The accumulation account must be pre-funded with at least the existential deposit.
//! For new chains, include the account in the balances genesis config.
//! For existing chains, fund it via a manual transfer.
//!
//! If the accumulation account is not pre-funded, deposits below ED will be silently burned.
//!
//! ## Total Issuance
//!
//! Accumulated funds are burnt upon forwarding (reducing `total_issuance` here) and the same
//! funds are minted at the destination when the sent message is received.
```

```rust
	#[pallet::hooks]
	impl<T: Config> Hooks<SystemBlockNumberFor<T>> for Pallet<T> {
		fn on_idle(_block: SystemBlockNumberFor<T>, remaining_weight: Weight) -> Weight {
			// Only attempt forwarding on blocks that are exact multiples of `TransferPeriod`.
			let block = T::BlockNumberProvider::current_block_number();
			if (block % T::TransferPeriod::get()) != Zero::zero() {
				return Weight::zero();
			}

			let mut meter = WeightMeter::with_limit(remaining_weight);

			// Need one read for the balance check.
			if meter.try_consume(T::DbWeight::get().reads(1)).is_err() {
				return meter.consumed();
			}

			let accumulation_account = Self::accumulation_account();
			// We use `reducible_balance` with `Preservation::Preserve` to get the
			// usable balance (excluding the ED).
			let available_funds = T::Currency::reducible_balance(
				&accumulation_account,
				Preservation::Preserve,
				Fortitude::Polite,
			);

			if available_funds < T::MinTransferAmount::get() {
				return meter.consumed();
			}

			// Ensure there is enough weight budget for the full XCM send.
			if meter.try_consume(T::WeightInfo::send_native()).is_err() {
				return meter.consumed();
			}

			// Attempt to forward accumulated funds.
			match T::Forwarder::forward(accumulation_account, available_funds) {
				Ok(()) => {
					Self::deposit_event(Event::ForwardSucceeded { amount: available_funds });
				},
				Err(()) => {
					log::debug!(
						target: LOG_TARGET,
						"accumulate-forward transfer of {:?} failed at block {:?}",
						available_funds,
						block,
					);
					Self::deposit_event(Event::ForwardFailed { amount: available_funds });
				},
			}

			meter.consumed()
		}
```
