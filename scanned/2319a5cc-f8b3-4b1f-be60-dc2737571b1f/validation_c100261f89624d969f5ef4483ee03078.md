### Title
Reward-per-point checkpoint in `pallet-nomination-pools` lets an attacker capture era rewards proportional to a stake bonded *after* the reward was earned - ([File: substrate/frame/nomination-pools/src/lib.rs])

### Summary
`pallet-nomination-pools` distributes staking rewards to members using a reward-per-point accumulator (`RewardPool::last_recorded_reward_counter`) that is only refreshed when a member's points change or when a reward/commission claim happens. Crucially, the amount that gets attributed to "new" rewards at each refresh is simply *whatever new balance has appeared in the pool's reward account since the last snapshot*, split among the **current** `bonded_pool.points` at the moment the refresh runs [1](#0-0) . Because `pallet-staking`'s `payout_stakers` is a fully public, permissionless extrinsic that anyone can call at any time (within `HistoryDepth`) to push an era's reward into the pool's reward account [2](#0-1) [3](#0-2) , an attacker can inflate their points share right before triggering that payout and claim a disproportionate cut of rewards that were actually earned by other members' stake during a past era, exactly like the reported Super DCA bug where rewards accrued over a period were distributed to whichever LP happened to be "in range" at the moment the distribution was triggered.

### Finding Description
The reward pool's accounting model works like this:
- `RewardPool::update_records` / `current_reward_counter` compute `current_payout_balance` as "whatever new balance is in the reward account since last snapshot" and divide it by the **current** `bonded_points` argument passed in, then merge it into `last_recorded_reward_counter` [4](#0-3) [5](#0-4) .
- Every points-changing extrinsic (`join`, `bond_extra`, `unbond`) is documented to call this checkpoint using the points *before* the change is applied, which correctly protects already-accrued balance from being diluted by a brand-new joiner [6](#0-5) , demonstrated concretely in `join()` [7](#0-6) .
- However, this checkpoint only protects balance that is **already sitting in the reward account** at the time of the call. It does nothing to protect balance that arrives **later**, via a completely independent, permissionless call to `pallet-staking::payout_stakers`, which mints/transfers an era's reward directly into the pool's `RewardDestination::Account` reward account [8](#0-7) , or the transfer-based equivalent in `staking-async` [9](#0-8) .
- When that new balance lands, whoever's points are current at the *next* reward-counter refresh gets a proportional share of it — regardless of whether they held those points during the era the reward corresponds to. `do_reward_payout` explicitly recomputes `current_reward_counter` using `bonded_pool.points` (the live, current total) at claim time [10](#0-9) .

Attack path (single or two adjacent extrinsics, fully permissionless, no privileged role needed):
1. An era's staking reward for the pool's validator has been computed but not yet paid out via `payout_stakers` (a public, unsigned-origin-checked-only call anyone can invoke) [11](#0-10) .
2. Attacker calls `bond_extra` on the pool, sharply increasing their `points` share (e.g., from 1% to 90%). This correctly checkpoints any *pre-existing* reward balance to the old point-holders before the attacker's points increase (per the documented `update_recorded` invariant) [6](#0-5) .
3. Attacker (or anyone) calls `payout_stakers(validator_stash, era)`, transferring the full era reward into the pool's reward account balance.
4. Attacker immediately calls `claim_payout` (or `unbond`), which recomputes the reward counter using the pool's **current** (now attacker-inflated) `bonded_points`, crediting the attacker a large fraction of a reward that was earned by other members' stake during the era in question [10](#0-9) .
5. Attacker unbonds the temporarily inflated stake (subject to the unbonding period), having already extracted the stolen reward share to their free balance.

This mirrors the Super DCA root cause precisely: the protocol cannot distinguish which participants actually contributed "in-range" (here, bonded) during the period a reward accrued, and instead distributes it based on whoever is present at the moment the distribution-triggering call executes.

### Impact Explanation
This allows an unprivileged actor to steal a share of legitimately-earned staking rewards from honest nomination-pool members by timing a `bond_extra`/`unbond` around the fully public and permissionless `payout_stakers` call. It falls under "theft or unbacked... duplicate settlement or payout" and "conserve value and settle exactly once to the rightful beneficiary and amount" — here settlement goes to the *wrong* beneficiary (the attacker) and in the *wrong* amount, at the expense of long-term pool members.

### Likelihood Explanation
- No malicious validator, collator, relayer, prover, or governance action is required — only a pool member (or someone willing to join) executing ordinary, unprivileged extrinsics (`bond_extra`, `payout_stakers`, `claim_payout`/`unbond`) in a predictable sequence.
- `payout_stakers` is explicitly documented as "Any account can call this function, even if it is not one of the stakers," making the trigger fully public and unauthenticated [12](#0-11) .
- The attacker needs enough capital to temporarily dominate the pool's points and accept the unbonding-duration lock-up on that capital, which limits (but does not eliminate) profitability — the same caveat the original report notes ("Even if not profitable, this would still lead to steal of rewards from other honest LPs").

### Recommendation
Decouple reward attribution from the *current* point snapshot for balance that arrives from external payout sources. Options: (a) require pool reward-account inflows to always pass through `update_records` immediately upon transfer (e.g., a hook invoked by `payout_stakers`/`make_payout`) so that the checkpoint against the pre-inflation point count happens atomically with the transfer rather than being deferred to the next arbitrary member action; (b) impose a minimum bonding/cooldown period before newly bonded points become eligible to receive already-pending (but not yet transferred) era rewards, analogous to time-weighted or checkpointed accounting; (c) more generally, apply the same fixed-epoch/locked-position style mitigation described in the original report to nomination-pools' reward-per-point accounting so that points changes cannot be sandwiched around a known, publicly-triggerable reward inflow.

### Proof of Concept
Conceptual sequence (would need to be validated against the actual `bond_extra`/`unbond` implementations, which were not fully inspected within tool-call limits):
1. Pool P has member A with 100 points; an era-N staking reward of size R is computed but `payout_stakers(validator, N)` has not yet been called.
2. Attacker B calls `Pools::bond_extra(pool=P, extra=9900)`, making B's points 9900 vs A's 100 (99% share). `update_records` runs first with the old 100 total points, correctly checkpointing any pre-existing reward balance to A only.
3. Anyone calls `Staking::payout_stakers(validator, N)`, transferring R into P's reward account.
4. Attacker B calls `Pools::claim_payout()`. `current_reward_counter` is computed against the new total of 10000 points, giving B ~99% of R even though B held 0 points during era N.
5. Attacker B calls `Pools::unbond(9900)` to reclaim capital (subject to unbonding duration), having already extracted ~99% of A's rightfully-earned era-N reward.

Note: I was unable to read the full body of `bond_extra`/`do_bond` in this session (ran out of tool iterations) to confirm the exact call ordering matches `join()`'s pattern byte-for-byte; the module documentation explicitly states `bond_extra` follows the same `update_recorded` discipline as `join`/`unbond`, but a Devin session with full repository access should verify this directly against `do_bond` before treating the PoC as conclusively validated.

	/// Update the recorded values of the reward pool.
	///
	/// This function MUST be called whenever the points in the bonded pool change, AND whenever the
	/// the pools commission is updated. The reason for the former is that a change in pool points
	/// will alter the share of the reward balance among pool members, and the reason for the latter
	/// is that a change in commission will alter the share of the reward balance among the pool.
	fn update_records(
		&mut self,
		id: PoolId,
		bonded_points: BalanceOf<T>,
		commission: Perbill,
	) -> Result<(), Error<T>> {
		let balance = Self::current_balance(id);

		let (current_reward_counter, new_pending_commission) =
			self.current_reward_counter(id, bonded_points, commission)?;

		// Store the reward counter at the time of this update. This is used in subsequent calls to
		// `current_reward_counter`, whereby newly pending rewards (in points) are added to this
		// value.
		self.last_recorded_reward_counter = current_reward_counter;

		// Add any new pending commission that has been calculated from `current_reward_counter` to
		// determine the total pending commission at the time of this update.
		self.total_commission_pending =
			self.total_commission_pending.saturating_add(new_pending_commission);

		// Total payouts are essentially the entire historical balance of the reward pool, equating
		// to the current balance + the total rewards that have left the pool + the total commission
		// that has left the pool.
		let last_recorded_total_payouts = balance
			.checked_add(&self.total_rewards_claimed.saturating_add(self.total_commission_claimed))
			.ok_or(Error::<T>::OverflowRisk)?;

		// Store the total payouts at the time of this update.
		//
		// An increase in ED could cause `last_recorded_total_payouts` to decrease but we should not
		// allow that to happen since an already paid out reward cannot decrease. The reward account
		// might go in deficit temporarily in this exceptional case but it will be corrected once
		// new rewards are added to the pool.
		self.last_recorded_total_payouts =
			self.last_recorded_total_payouts.max(last_recorded_total_payouts);

		Ok(())
	}

	/// Get the current reward counter, based on the given `bonded_points` being the state of the
	/// bonded pool at this time.
	fn current_reward_counter(
		&self,
		id: PoolId,
		bonded_points: BalanceOf<T>,
		commission: Perbill,
	) -> Result<(T::RewardCounter, BalanceOf<T>), Error<T>> {
		let balance = Self::current_balance(id);

		// Calculate the current payout balance. The first 3 values of this calculation added
		// together represent what the balance would be if no payouts were made. The
		// `last_recorded_total_payouts` is then subtracted from this value to cancel out previously
		// recorded payouts, leaving only the remaining payouts that have not been claimed.
		let current_payout_balance = balance
			.saturating_add(self.total_rewards_claimed)
			.saturating_add(self.total_commission_claimed)
			.saturating_sub(self.last_recorded_total_payouts);

		// Split the `current_payout_balance` into claimable rewards and claimable commission
		// according to the current commission rate.
		let new_pending_commission = commission * current_payout_balance;
		let new_pending_rewards = current_payout_balance.saturating_sub(new_pending_commission);

		// * accuracy notes regarding the multiplication in `checked_from_rational`:
		// `current_payout_balance` is a subset of the total_issuance at the very worse.
		// `bonded_points` are similarly, in a non-slashed pool, have the same granularity as
		// balance, and are thus below within the range of total_issuance. In the worse case
		// scenario, for `saturating_from_rational`, we have:
		//
		// dot_total_issuance * 10^18 / `minJoinBond`
		//
		// assuming `MinJoinBond == ED`
		//
		// dot_total_issuance * 10^18 / 10^10 = dot_total_issuance * 10^8
		//
		// which, with the current numbers, is a miniscule fraction of the u128 capacity.
		//
		// Thus, adding two values of type reward counter should be safe for ages in a chain like
		// Polkadot. The important note here is that `reward_pool.last_recorded_reward_counter` only
		// ever accumulates, but its semantics imply that it is less than total_issuance, when
		// represented as `FixedU128`, which means it is less than `total_issuance * 10^18`.
		//
		// * accuracy notes regarding `checked_from_rational` collapsing to zero, meaning that no
		//   reward can be claimed:
		//
		// largest `bonded_points`, such that the reward counter is non-zero, with `FixedU128` will
		// be when the payout is being computed. This essentially means `payout/bonded_points` needs
		// to be more than 1/1^18. Thus, assuming that `bonded_points` will always be less than `10
		// * dot_total_issuance`, if the reward_counter is the smallest possible value, the value of
		//   the
		// reward being calculated is:
		//
		// x / 10^20 = 1/ 10^18
		//
		// x = 100
		//
		// which is basically 10^-8 DOTs. See `smallest_claimable_reward` for an example of this.
		let current_reward_counter =
			T::RewardCounter::checked_from_rational(new_pending_rewards, bonded_points)
				.and_then(|ref r| self.last_recorded_reward_counter.checked_add(r))
				.ok_or(Error::<T>::OverflowRisk)?;

		Ok((current_reward_counter, new_pending_commission))
	}

	fn make_payout(
		stash: &T::AccountId,
		amount: BalanceOf<T>,
	) -> Option<(PositiveImbalanceOf<T>, RewardDestination<T::AccountId>)> {
		// noop if amount is zero
		if amount.is_zero() {
			return None;
		}
		let dest = Self::payee(StakingAccount::Stash(stash.clone()))?;

		let maybe_imbalance = match dest {
			RewardDestination::Stash => asset::mint_into_existing::<T>(stash, amount),
			RewardDestination::Staked => Self::ledger(Stash(stash.clone()))
				.and_then(|mut ledger| {
					ledger.active += amount;
					ledger.total += amount;
					let r = asset::mint_into_existing::<T>(stash, amount);

					let _ = ledger
						.update()
						.defensive_proof("ledger fetched from storage, so it exists; qed.");

					Ok(r)
				})
				.unwrap_or_default(),
			RewardDestination::Account(ref dest_account) =>
				Some(asset::mint_creating::<T>(&dest_account, amount)),
			RewardDestination::None => None,
			#[allow(deprecated)]
			RewardDestination::Controller => Self::bonded(stash)
					.map(|controller| {
						defensive!("Paying out controller as reward destination which is deprecated and should be migrated.");
						// This should never happen once payees with a `Controller` variant have been migrated.
						// But if it does, just pay the controller account.
						asset::mint_creating::<T>(&controller, amount)
		}),
		};
		maybe_imbalance.map(|imbalance| (imbalance, dest))
