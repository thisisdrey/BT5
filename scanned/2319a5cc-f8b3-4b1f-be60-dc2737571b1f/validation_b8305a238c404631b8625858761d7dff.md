## Analysis

This is a real local analog of the reported bug class: **a single "enabled/rate" flag is checked both when a user *enters* a queue and when that same user tries to *exit/cancel* before being processed — causing already-deposited funds to become permanently locked whenever an operator pauses new intake.**

### Title
Shared `ErasToCheckPerBlock` gate blocks `deregister` and permanently locks reserved deposits in `pallet-fast-unstake` - (`substrate/frame/fast-unstake/src/lib.rs`)

### Summary
`pallet-fast-unstake`'s `register_fast_unstake` and `deregister` dispatchables both gate on the *same* boolean-like flag `ErasToCheckPerBlock`. This flag is meant to control whether the pallet is actively *processing* the queue (i.e., whether new registrations should be accepted / whether `on_idle` should scan eras). However, `deregister` — the only way for an already-queued user to unwind their registration and reclaim their reserved `Deposit` before being checked — is gated by the exact same flag. If `ErasToCheckPerBlock` is set to `0` (the pallet's documented "halted" state, e.g. after `Self::halt(...)` is triggered defensively, or set by `T::ControlOrigin` via `control`), every account still sitting in `Queue` or `Head` loses the ability to deregister and recover its `Deposit`, even though their registration is a fully finished/pending user action independent of whether new registrations or era-checks are currently permitted.

### Finding Description [1](#0-0) 
`register_fast_unstake` checks `ErasToCheckPerBlock::<T>::get() != 0` before allowing a stash to enqueue for fast-unstake, reserving `T::Deposit::get()` from the caller. [2](#0-1) 
`deregister` — the escape hatch for a user who is *already* in `Queue` (i.e., their registration has already been "processed" into pending state, deposit already reserved) — re-uses the identical check `ensure!(ErasToCheckPerBlock::<T>::get() != 0, Error::<T>::CallNotAllowed);` before it will `Queue::<T>::take(...)` and `T::Currency::unreserve(...)` the deposit back to the user.

This mirrors exactly the reported bug class: `check_withdrawal_enabled()` gates both `request_withdrawal()` (entry) and `withdraw()` (exit/claim of already-processed state) using one flag, so disabling new requests also blocks users from reclaiming funds tied to requests that already succeeded. Here, `ErasToCheckPerBlock == 0` is also used by `on_idle`/`do_on_idle` to skip all queue processing: [3](#0-2) 

So when the flag is `0`:
- New registrations are correctly blocked (as intended).
- Queue/Head processing via `on_idle` is also halted (as intended).
- But users who are *already* enqueued (already fully unbonded/chilled and already had their `Deposit` reserved by a prior successful `register_fast_unstake`) have **no other path** to `deregister` and recover their reserved deposit while the flag is `0`. There is no alternate flag, no exemption, and no other dispatchable that releases `Queue` entries other than `deregister` (permissioned) or the halted `on_idle` processing path.

### Impact Explanation
Any account already sitting in `Queue::<T>` when the pallet is halted (`ErasToCheckPerBlock = 0`) has its `T::Deposit::get()` amount reserved and inaccessible for the entire duration the flag remains `0`. Because `Self::halt(...)` is itself invoked defensively from within `do_on_idle` on unexpected internal errors (e.g., insufficient balance to unreserve), a single defensive halt event freezes deposits for *every* queued account simultaneously, with no dispatchable able to unlock them until `T::ControlOrigin::control(...)` restores a nonzero value. This is a permanent user-fund lock as long as the halted condition persists — matching the "permanent user-fund ... lock" impact class from the pivot list.

### Likelihood Explanation
No malicious peer, validator, collator, or leaked key is required. Any unprivileged account can call `register_fast_unstake` (entering `Queue` and reserving its deposit), and the halt condition can be reached either via ordinary `ControlOrigin` administration or via the pallet's own defensive internal halt logic — a normal operational occurrence, not governance/admin abuse as root cause. The bug is purely in the shared-flag design of the public dispatchables, and is deterministically reproducible.

### Recommendation
Do not reuse `ErasToCheckPerBlock == 0` as the gate for `deregister`. `deregister` should only require that the caller is actually queued (`Queue::<T>::contains_key`) and not currently in `Head` (already being checked), regardless of whether new registrations or era-processing are currently halted. Consider removing the `ErasToCheckPerBlock` check from `deregister` entirely, or replacing it with a distinct "deregistration is enabled" flag that is independent from the intake/processing pause flag.

### Proof of Concept
1. `ControlOrigin` (or a defensive internal fault) sets `ErasToCheckPerBlock::<T>::put(0)` — see `substrate/frame/fast-unstake/src/lib.rs:405-412` (`control`) or `substrate/frame/fast-unstake/src/lib.rs:423-428` (`halt`).
2. Prior to the halt, account `A` had already called `register_fast_unstake`, successfully reserving `Deposit` and being inserted into `Queue::<T>`.
3. While `ErasToCheckPerBlock == 0`:
   - `on_idle`/`do_on_idle` early-returns without processing `Queue` (`substrate/frame/fast-unstake/src/lib.rs:447-450`), so `A` is never checked/unstaked.
   - `A` calls `deregister`; it fails with `Error::<T>::CallNotAllowed` due to the same `ErasToCheckPerBlock != 0` check (`substrate/frame/fast-unstake/src/lib.rs:374`).
4. `A`'s `Deposit` remains reserved indefinitely with no available dispatchable to release it until governance restores `ErasToCheckPerBlock` to a nonzero value.

		pub fn register_fast_unstake(origin: OriginFor<T>) -> DispatchResult {
			let ctrl = ensure_signed(origin)?;

			ensure!(ErasToCheckPerBlock::<T>::get() != 0, Error::<T>::CallNotAllowed);
			let stash_account =
				T::Staking::stash_by_ctrl(&ctrl).map_err(|_| Error::<T>::NotController)?;
			ensure!(!Queue::<T>::contains_key(&stash_account), Error::<T>::AlreadyQueued);
			ensure!(!Self::is_head(&stash_account), Error::<T>::AlreadyHead);
			ensure!(!T::Staking::is_unbonding(&stash_account)?, Error::<T>::NotFullyBonded);

			// chill and fully unstake.
			T::Staking::chill(&stash_account)?;
			T::Staking::fully_unbond(&stash_account)?;

			T::Currency::reserve(&stash_account, T::Deposit::get())?;

			// enqueue them.
			Queue::<T>::insert(stash_account, T::Deposit::get());
			Ok(())
		}

		pub fn deregister(origin: OriginFor<T>) -> DispatchResult {
			let ctrl = ensure_signed(origin)?;

			ensure!(ErasToCheckPerBlock::<T>::get() != 0, Error::<T>::CallNotAllowed);

			let stash_account =
				T::Staking::stash_by_ctrl(&ctrl).map_err(|_| Error::<T>::NotController)?;
			ensure!(Queue::<T>::contains_key(&stash_account), Error::<T>::NotQueued);
			ensure!(!Self::is_head(&stash_account), Error::<T>::AlreadyHead);
			let deposit = Queue::<T>::take(stash_account.clone());

			if let Some(deposit) = deposit.defensive() {
				let remaining = T::Currency::unreserve(&stash_account, deposit);
				if !remaining.is_zero() {
					Self::halt("not enough balance to unreserve");
				}
			}

			Ok(())
		}
