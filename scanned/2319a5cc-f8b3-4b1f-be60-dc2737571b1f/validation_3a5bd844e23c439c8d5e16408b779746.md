### Title
Child-bounty sub-accounts have no permissionless sweep, permanently trapping accidentally-sent balance/assets after closure/claim - ([File: substrate/frame/child-bounties/src/lib.rs])

### Summary
`pallet-child-bounties` derives a dedicated sub-account per child bounty (`child_bounty_account_id(parent_bounty_id, child_bounty_id)`) that can receive native balance (and, if configured, other fungible assets) exactly like the parent `pallet-bounties` bounty accounts did. `pallet-bounties` was found to have this exact "stuck funds" problem — after `close_bounty`/`claim_bounty` removed the `Bounties` storage entry, any balance/assets sent afterward to the now-orphaned bounty account (by mistake, dust, airdrop, etc.) had no way to be recovered — and it was fixed by adding a permissionless `reclaim_bounty_funds` extrinsic [1](#0-0)  together with `TransferAllAssets::force_transfer_all_assets` support for sweeping arbitrary assets, not just the native currency [2](#0-1) .

`pallet-child-bounties`, which is tightly coupled to `pallet-bounties` and uses the exact same sub-account pattern, never received an equivalent fix. Its `claim_child_bounty` and `close_child_bounty`/`impl_close_child_bounty` functions only move the child bounty account's *native* `free_balance` and then unconditionally remove the `ChildBounties` storage entry — after that, the sub-account is orphaned with no code path left in the pallet to reclaim any balance or assets subsequently sent to it.

### Finding Description
`impl_close_child_bounty` computes the child-bounty sub-account balance and transfers it to the parent bounty account, then removes the storage record: [3](#0-2) . Likewise, `claim_child_bounty` pays out `curator_fee` and `payout` computed from the account's balance *at that moment* and then deletes the storage entry: [4](#0-3) .

In both cases:
- Only the native `Currency::free_balance` is moved; there is no analogue of `TransferAllAssets::force_transfer_all_assets` used in `pallet-bounties::close_bounty`/`reclaim_bounty_funds` [5](#0-4) .
- Once `*maybe_child_bounty = None` executes, the `ChildBounties` map entry for that `(parent_bounty_id, child_bounty_id)` is gone permanently (child bounty indices are not reused/reactivated), and `child_bounty_account_id` still deterministically derives the same account for that id.
- Any value later credited to that sub-account — via a mis-sent transfer, dust from another pallet, an airdrop of a fungible asset, or even a delayed/duplicated payout transaction that lands after the storage removal — is now held by an account with no corresponding pallet entry and no dispatchable in `pallet-child-bounties` that can move funds out of it. `reclaim_bounty_funds` in `pallet-bounties` only operates on `Self::bounty_account_id(bounty_id)` (the *parent* bounty account), not on child-bounty sub-accounts [6](#0-5) , so it cannot rescue child-bounty funds either.

This is the same broken invariant flagged in the external report (value can reach an account through channels the code doesn't anticipate, and once it's not covered by any pending accounting record it becomes irretrievable), and it is directly analogous to the now-fixed `pallet-bounties` issue (`fixes paritytech/polkadot-sdk#10996`) — except the fix was not propagated to the sibling pallet that shares the identical sub-account architecture.

### Impact Explanation
Any native balance or configured fungible asset sent to a closed/claimed child-bounty sub-account is permanently locked with no extrinsic capable of retrieving it — a permanent user/treasury-fund lock. Because `pallet_bounties::force_transfer_all_assets` (used for the parent) is asset-aware, any runtime that configures child bounties in tandem with multi-asset treasuries is exposed to genuine, non-recoverable fund loss whenever assets or dust land in these deterministic sub-accounts after removal (e.g., an asset issuer's airdrop targeting `child_bounty_account_id`, or a race between an in-flight XCM/asset transfer and a curator's `close_child_bounty` call).

### Likelihood Explanation
The precondition is simply that some value reaches the sub-account after (or racing with) the child bounty's closure/claim — a permissionless, unprivileged action available to anyone able to transfer tokens to a well-known, deterministically-derived `AccountId` (`child_bounty_account_id` is a pure function of `parent_bounty_id`/`child_bounty_id`, so it is trivially computable/discoverable off-chain). No attacker capability beyond an ordinary account and the ability to send a transfer is required, matching the exact "receiving tokens/airdrops/refunds by mistake" scenario described in the external report. The impact is deterministic (not probabilistic) once such a transfer occurs.

### Recommendation
Add a permissionless `reclaim_child_bounty_funds` extrinsic to `pallet-child-bounties`, mirroring `pallet-bounties::reclaim_bounty_funds`: given `(parent_bounty_id, child_bounty_id)`, require `!ChildBounties::<T>::contains_key(parent_bounty_id, child_bounty_id)` (i.e., only act on closed/claimed child bounties), then sweep all native balance and any relevant assets from `child_bounty_account_id(parent_bounty_id, child_bounty_id)` back to the parent bounty account (or treasury), using the same `TransferAllAssets` mechanism already implemented for `pallet-bounties`, and emit a corresponding event. Pay-on-noop semantics should be preserved to prevent griefing.

### Proof of Concept
1. Create and fund a parent bounty, propose/accept a curator, and `add_child_bounty` to create child bounty `(0, 0)`; note the deterministic address `A = ChildBounties::child_bounty_account_id(0, 0)`.
2. Complete the lifecycle normally: `award_child_bounty` → `claim_child_bounty(0, 0)`. This pays curator fee + beneficiary and removes the `ChildBounties` storage entry for `(0, 0)`, per [4](#0-3) .
3. Any third party (no special permission needed) sends a plain `Balances::transfer` (or an asset transfer, if `T::Currency`/assets are configured) of amount `X` to `A` — this can be an accidental resend, dust, or an airdrop targeting the address (which is public/derivable).
4. `Balances::free_balance(A) == X` now, but there is no entry in `ChildBounties` for `(0, 0)` anymore, and no dispatchable in `pallet-child-bounties` or `pallet-bounties` references the child-bounty sub-account to sweep it — `reclaim_bounty_funds` only targets `bounty_account_id(0)` [6](#0-5) . Funds at `A` are permanently stranded.

This mirrors the exact test setup used to validate the parent-pallet fix (`reclaim_bounty_funds_works_after_accidental_refund`) [7](#0-6) , which confirms the identical scenario is reachable and was previously considered a real bug for `pallet-bounties`; the same code path is simply missing for `pallet-child-bounties`.

		/// Reclaim funds stranded in a closed bounty's account back to the treasury.
		///
		/// Permissionless. Moves all remaining assets from a closed bounty's account back to the
		/// treasury in a single call. Which assets are swept depends on the `TransferAllAssets`
		/// configuration.
		///
		/// The call is free if funds were reclaimed and paid otherwise, so no-op calls cannot be
		/// used to grief the network. Emits `BountyFundsReclaimed` on success.
		///
		/// ## Complexity
		/// - O(A) where A is the number of relevant assets configured in `TransferAllAssets`.
		#[pallet::call_index(11)]
		#[pallet::weight(<T as Config<I>>::WeightInfo::reclaim_bounty_funds())]
		pub fn reclaim_bounty_funds(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
		) -> DispatchResultWithPostInfo {
			ensure_signed(origin)?;

			// A live bounty still manages its account, so leave it untouched.
			ensure!(!Bounties::<T, I>::contains_key(bounty_id), Error::<T, I>::BountyStillActive);

			debug_assert!(
				T::ChildBountyManager::child_bounties_count(bounty_id) == 0,
				"child bounties should not exist for a closed bounty"
			);

			let bounty_account = Self::bounty_account_id(bounty_id);
			let treasury_account = Self::account_id();

			let transferred = T::TransferAllAssets::force_transfer_all_assets(
				&bounty_account,
				&treasury_account,
			)?;

			// Free only if something moved, otherwise paid to prevent griefing.
			if !transferred {
				return Ok(Pays::Yes.into());
			}

			Self::deposit_event(Event::<T, I>::BountyFundsReclaimed { bounty_id });

			Ok(Pays::No.into())
		}

#[test]
fn reclaim_bounty_funds_works_after_accidental_refund() {
	ExtBuilder::default().build_and_execute(|| {
		Balances::make_free_balance_be(&Treasury::account_id(), 101);

		// Full lifecycle: propose → approve → fund → curator → award → claim
		assert_ok!(Bounties::propose_bounty(RuntimeOrigin::signed(0), 50, b"12345".to_vec()));
		assert_ok!(Bounties::approve_bounty(RuntimeOrigin::root(), 0));
		go_to_block(2);

		let fee = 4;
		Balances::make_free_balance_be(&4, 10);
		assert_ok!(Bounties::propose_curator(RuntimeOrigin::root(), 0, 4, fee));
		assert_ok!(Bounties::accept_curator(RuntimeOrigin::signed(4), 0));
		assert_ok!(Bounties::award_bounty(RuntimeOrigin::signed(4), 0, 3));
		go_to_block(5);
		assert_ok!(Bounties::claim_bounty(RuntimeOrigin::signed(1), 0));

		// Bounty is now fully closed; verify it is gone from storage.
		assert!(pallet_bounties::Bounties::<Test>::get(0).is_none());

		let bounty_account = Bounties::bounty_account_id(0);
		// Account should already be empty after claim.
		assert_eq!(Balances::free_balance(&bounty_account), 0);

		// Simulate someone accidentally sending funds to the closed bounty account.
		Balances::make_free_balance_be(&bounty_account, 25);
		assert_eq!(Balances::free_balance(&bounty_account), 25);

		let treasury_before = Treasury::pot();

		// Dust the account.
		assert_ok!(Bounties::reclaim_bounty_funds(RuntimeOrigin::signed(99), 0));
		assert_eq!(last_event(), BountiesEvent::BountyFundsReclaimed { bounty_id: 0 },);

		assert_eq!(Balances::free_balance(&bounty_account), 0);
		assert!(Treasury::pot() > treasury_before);
	});
}
