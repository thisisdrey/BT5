StackerDBTx::try_replace_chunk (stackerdb/db.rs) calls `self.get_slot_validation(smart_contract, slot_desc.slot_id)` and `ok_or(NoSuchSlot(...))`, then immediately trusts `slot_validation.signer` as the ground truth for `slot_desc.verify(&slot_validation.signer)`. Can a remote attacker exploit a stale StackerDBTx handle held open across a `clear_stackerdb_slots`/`create_stackerdb` re-provisioning event (e.g. triggered by the smart contract's per-Bitcoin-block eviction), so that `get_slot_validation` inside an in-flight transaction reads a slot_validation row for an owner address from *before* re-provisioning while a concurrently-committed transaction has already reassigned that slot_id to a new owner, letting the attacker's old-owner signature (still valid against the stale row) write into the slot now owned by someone else? Equality broken: slot_validation.signer read inside try_replace_chunk == the *currently committed* owner of slot_id, not a snapshot from a stale transaction view. Impact: Critical unauthenticated write to a reassigned slot due to a stale-read TOCTOU across StackerDB re-provisioning. Proof: open two StackerDBTx handles, reprovision the DB via one (reassigning slot 0's owner), commit, then attempt try_replace_chunk with the old owner's signature on the other still-open handle and assert it is rejected rather than succeeding.
