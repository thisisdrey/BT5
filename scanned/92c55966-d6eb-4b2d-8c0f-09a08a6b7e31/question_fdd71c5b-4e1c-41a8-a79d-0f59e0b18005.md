StackerDBSync::add_downloaded_chunk (stackerdb/sync.rs) pushes into `self.downloaded_chunks.get_mut(&naddr)` without checking whether a chunk for the same slot_id from the same naddr was already downloaded and validated by validate_downloaded_chunk. Can a malicious sync-neighbor peer answer a StackerDBGetChunkData request for slot X twice with two different signed-but-differing-version chunks in the same round, both passing validate_downloaded_chunk independently, resulting in downloaded_chunks holding two entries for the same slot_id from the same naddr where only the chunk_fetch_priorities retain() filter (which matches on chunk.slot_id) determines which one ultimately gets processed by process_stacker_db_chunks, and the later one always wins regardless of which the priority queue actually intended to fetch? Equality: the chunk fed to try_replace_chunk == the chunk_fetch_priorities entry that was scheduled, not whichever arrived last. Impact: Critical since a peer can supply a lower legitimate version after a higher one already validated, causing try_replace_chunk to reject via StaleChunk but *only after* wasted processing, and if ordering is reversed the higher one is silently dropped from being broadcast to other neighbors, breaking eventual-consistency guarantees. Proof: call add_downloaded_chunk twice for the same naddr/slot_id with two valid StackerDBChunkData of different slot_version, then process_stacker_db_chunks, and assert both are attempted rather than the DB's greatest version being the one committed and relayed.
