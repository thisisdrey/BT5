## Analysis

The external report's core broken invariant is: **a validation function exists in the codebase, but it is not consistently applied at all the points where it is required, allowing a value to be accepted/used based on stale or unchecked state.** In Dexter this was the unused checksum validator for addresses. The closest local analog in `polkadot-sdk--040` is in the custom `pallet-psm` (Peg Stability Module), where the decimals-drift guard that protects `mint` is not enforced on the `redeem` path.

`pallet-psm` snapshots each approved external asset's decimals (and the internal asset's decimals) at registration time, and is documented to halt any operation if live on-chain metadata (via `pallet-assets::set_metadata`) has drifted from that snapshot: [1](#0-0) 

The pallet's own test suite confirms `mint` enforces this guard — changing an asset's decimals after registration causes `mint` to fail with `Error::DecimalsMismatch`: [2](#0-1) [3](#0-2) 

However, the corresponding tests for `redeem` are named `redeem_uses_snapshot_when_asset_decimals_drift` and `redeem_uses_snapshot_when_internal_decimals_drift`, and both assert the redeem call **succeeds** (`assert_ok!`) after the same decimals-drift setup that halts `mint`, silently using the stale registration-time decimal snapshot instead of rejecting the operation: [4](#0-3) [5](#0-4) 

The conversion itself is performed by `external_to_internal` / `internal_to_external`, which take `ext_decimals`/`internal_decimals` as plain arguments and blindly scale by `10^diff` — they have no way to know whether the caller passed live or stale decimals: [6](#0-5) 

## Why this matches the reported bug class

- The Dexter bug: a checksum-validation routine exists (`Tezos_Address.re`) but the actual `ofString` validator used at the point of signing never calls it, so unchecked/incorrect data is accepted downstream.
- The `pallet-psm` analog: a decimals-drift validation routine (comparing live `pallet-assets` metadata decimals against the pallet's `AssetDecimals`/`InternalDecimals` snapshot) exists and is wired into `mint`, but the equivalent check is not applied on `redeem`'s path before it calls `internal_to_external`/`external_to_internal`. The redeem dispatchable trusts the stored snapshot instead of re-validating against live decimals the way `mint` does.

## Impact

Asset decimals in `pallet-assets` are metadata that can be changed post-registration by the asset's `Owner`/`set_metadata`-privileged account — an entity distinct from the PSM instance's governance/admin (`full_admin`/`emergency_admin`). If an approved external asset's decimals are changed after registration:
- `mint` correctly halts (`DecimalsMismatch`), protecting deposits into the reserve.
- `redeem` does **not** halt; it silently reuses the stale snapshot decimals to compute `internal_to_external`, producing a conversion rate that no longer matches the asset's real on-chain unit scale.

Since `redeem` burns internal debt (`PsmDebt`) and pays out external reserve based on this now-incorrect scaling factor, this breaks the pallet's core 1:1-backing invariant between `PsmDebt` and the reserve balance — the exact kind of "asset accounting fails to conserve value / settle exactly once at the correct amount" issue this task is scoped to catch. Depending on the direction of the decimals change, this can either drain the PSM reserve disproportionately (external asset paid out at wrong scale) or credit/debit `PsmDebt` inconsistently with the actual reserve movement, silently breaking the peg-stability accounting the module exists to guarantee.

### Title
Missing decimals-drift validation on `pallet-psm::redeem` allows stale conversion scale to break PSM reserve/debt accounting - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
`pallet-psm::mint` halts with `Error::DecimalsMismatch` when an approved external or internal asset's live `pallet-assets` decimals diverge from the registration-time snapshot, but `pallet-psm::redeem` does not perform the same check and instead uses the stale snapshot decimals to compute the conversion, as demonstrated by the pallet's own test suite.

### Finding Description
`external_to_internal`/`internal_to_external` compute `amount * 10^diff` or `amount / 10^diff` purely from the `ext_decimals`/`internal_decimals` values passed to them [6](#0-5) . The pallet's design (documented in the README and enforced in `mint`) is to re-validate these decimals against live `pallet-assets` metadata on every operation and halt with `DecimalsMismatch` on drift [1](#0-0) , confirmed for `mint` by tests [2](#0-1) [3](#0-2) . The analogous `redeem` tests show the operation instead succeeds and silently uses the outdated snapshot [4](#0-3) [5](#0-4) .

### Impact Explanation
Decimals are asset metadata mutable by the asset owner, not by PSM governance. If any approved external asset's owner changes its decimals after registration, `redeem` will convert internal debt to external payout at the wrong scale (using the stale snapshot), breaking the 1:1 backing invariant between `PsmDebt` and the reserve balance held at `psm_account`. This can result in over- or under-payment from the reserve relative to the debt burned, i.e., asset-accounting value non-conservation in a public, unprivileged dispatchable.

### Likelihood Explanation
Triggering requires only that some already-approved external asset's owner (an ordinary, non-privileged-to-the-PSM account) call the standard `pallet-assets::set_metadata` to change decimals, then any user calls the public `redeem` extrinsic. No governance, validator, or node compromise is needed — this is directly reachable through normal public dispatch calls.

### Recommendation
Apply the same live-vs-snapshot decimals validation in `redeem` that is enforced in `mint` (i.e., call the equivalent decimals check before invoking `external_to_internal`/`internal_to_external` in `redeem`, returning `Error::DecimalsMismatch` on drift, consistent with `mint`'s behavior and the documented guarantee).

### Proof of Concept
1. Register an external asset (e.g., `USDX`) on a PSM instance and mint internal asset against it, establishing `PsmDebt` and reserve balance under the original decimals snapshot.
2. As the external asset's owner, call `Assets::set_metadata` to change its `decimals` field (simulating drift), as done in `redeem_uses_snapshot_when_asset_decimals_drift` [7](#0-6) .
3. Call the public `Psm::redeem` extrinsic — it succeeds (`assert_ok!`) instead of returning `DecimalsMismatch`, computing the external payout using the outdated decimals snapshot rather than the live value, producing an incorrect conversion relative to the asset's true current unit scale.

		/// Convert an amount denominated in external-asset units into internal units.
		///
		/// Scales by `10^(ext_decimals - internal_decimals)` — multiplies up when internal has more
		/// decimals, floor-divides when it has fewer. Returns [`Error::ConversionOverflow`] if
		/// the scaling factor or the product does not fit in the balance type.
		pub(crate) fn external_to_internal(
			amount: BalanceOf<T>,
			ext_decimals: u8,
			internal_decimals: u8,
		) -> Result<BalanceOf<T>, Error<T>> {
			use core::cmp::Ordering::*;
			match ext_decimals.cmp(&internal_decimals) {
				Equal => Ok(amount),
				Less => {
					let diff = (internal_decimals - ext_decimals) as u32;
					let factor = Self::pow10(diff)?;
					amount.checked_mul(&factor).ok_or(Error::<T>::ConversionOverflow)
				},
				Greater => {
					let diff = (ext_decimals - internal_decimals) as u32;
					let factor = Self::pow10(diff)?;
					Ok(amount.checked_div(&factor).unwrap_or_else(BalanceOf::<T>::zero))
				},
			}
		}
