## Title
Sybil-splittable, subadditive `incentive_weight` lets a single staker capture a disproportionate share of the fixed validator-incentive budget - ([File: substrate/frame/staking-async/src/reward.rs])

### Summary
The AJNA report's core defect is a reward formula whose denominator/inputs move as a side effect of the very action being paid, and whose curve is such that splitting one large action into several smaller ones inflates the *sum* of rewards versus doing it as one action. The direct analog in this repository is `incentive_weight()` in `substrate/frame/staking-async/src/reward.rs`, used by `DefaultStakerRewardCalculator::calculate_validator_incentive_weight` to convert a validator's self-stake into an "incentive weight" that determines its share of a fixed, era-scoped `ErasValidatorIncentiveBudget` pot.

### Finding Description
`incentive_weight` computes, below the configured `optimum`, `w(s) = √s` [1](#0-0) . `sqrt` is a strictly concave function with `f(0) = 0`, which makes it **subadditive**: for any split `s = s1 + s2`, `√s1 + √s2 > √s` (equality only when one term is zero). The same subadditivity holds across the `optimum..cap` segment (a scaled/shifted sqrt) and, less severely, at the plateau above `cap`.

Each validator's own weight is stored per era in `ErasValidatorIncentiveWeight`, summed into `ErasSumValidatorIncentiveWeight`, and the per-validator incentive payout is `budget * (own_weight / sum_weight)` — a proportional split of a **fixed** budget, computed in `Pallet::calculate_validator_incentive_for_page` and paid via `transfer_validator_incentive` inside `impls.rs`'s per-page payout logic [2](#0-1) . This mirrors the AJNA `_bpf()` pattern exactly: a nonlinear/piecewise function of a mutable "own" quantity feeds a *proportional share* calculation, and because the function is not additive across splits, an actor who can control multiple such "own" values in the same computation window can inflate their aggregate share.

Concretely: an entity that stakes `S` behind one validator identity gets weight `√S`. The same entity splitting the identical total capital `S` across `N` separate validator identities under its control (`s_1 + ... + s_N = S`, each below `optimum`) gets combined weight `Σ√s_i > √S`. This directly enlarges that entity's share of the fixed incentive pot at the expense of every other (honest) validator's share in the same era — the same "at the expense of the [shared pool]" impact called out in the AJNA report, where kicker reward inflation came at the expense of reserves.

Unlike the staking slash-reward path (`slash_validator` in `substrate/frame/staking-async/src/slashing.rs`), which was explicitly audited and fixed to be *linear* in the slash delta (comment: "Since repeat offences ... this reduction logic was unnecessary and removed" [3](#0-2) ), the `incentive_weight` curve was never linearized — it is intentionally concave ("dampened growth" is the stated design goal) but this concavity is exactly the mathematical property that creates the splitting incentive.

### Impact Explanation
This does not require a malicious validator/collator/relayer/prover in the excluded sense — it requires only an ordinary staker willing to run more than one validator node with the same aggregate capital, a normal, permitted, unprivileged action (registering additional validator candidacies is a public, permissionless operation subject only to normal bonding/election). By fragmenting self-stake across sybil validator identities the actor can systematically extract more than its proportional share of `ErasValidatorIncentiveBudget` every era, permanently degrading the reward received by honest, non-splitting validators — a duplicate/over-claimed settlement from a shared payout pot, falling under "duplicate settlement or payout" / unfair fund diversion in the accepted impact classes.

### Likelihood Explanation
Medium-High. It requires no timing tricks, no governance, no compromised keys — only enough capital to run multiple validator slots (bounded by the election set size, `MaxValidatorSet`/nominator selection, not by any anti-Sybil check in the incentive formula itself). The benefit scales predictably with the number of splits while `self_stake` stays below `optimum` (the region where the curve is pure `√s`), and the formula's own unit tests confirm strict monotonic concavity behavior (`incentive_weight_below_optimum`, `incentive_weight_between_optimum_and_cap`) without any additive-fairness test verifying `w(s1)+w(s2) <= w(s1+s2)`. No existing guard (bonding limits, `OptimumSelfStake`, `HardCapSelfStake`, `SelfStakeSlopeFactor`) enforces per-controller aggregation of self-stake across multiple validator identities — the pallet has no concept of "beneficial owner" linking multiple stashes.

### Recommendation
- Either replace the concave `sqrt`-based curve with a formula that is additive-neutral (or convex) with respect to legitimate stake aggregation, or
- Cap/aggregate `self_stake` per controlling identity (e.g. per proxy/session-key cluster or via an allow-listed "one incentive claim per beneficial owner" mechanism) before applying the curve, or
- Bound the total incentive budget claimable by stashes sharing a payee/controller/session-key fingerprint, similar to how `TakerActions.sol`'s recommended fix limited `takePenaltyFactor` to prevent the analogous distortion.
- At minimum, add an invariant test asserting `incentive_weight(a) + incentive_weight(b) <= incentive_weight(a+b)` (or documenting/bounding the violation), and quantify the maximum extractable excess share as a function of `MaxValidatorSet` size and `optimum`.

### Proof of Concept
Using the pallet's own documented values (`optimum = 100_000`, `cap = 500_000`, `slope = 1/2`):
- Single validator with `self_stake = 400_000` (from `incentive_weight_optimum_zero_cap_set`/`incentive_weight_monotonically_increasing_below_cap` test data, adjusted with `optimum = 100_000`): weight ≈ `418` (see test `incentive_weight_optimum_zero_cap_set`, line 341) for one identity holding all capital in the `optimum..cap` band.
- The same `400_000` split into 4 validator identities of `100_000` each (all `<= optimum`): each gets `√100_000 ≈ 316` (test `incentive_weight_at_optimum`, line 361-372), for a combined weight of `4 * 316 = 1264`, vastly larger than `418` for the unsplit case.
- Since payout is `budget * own_weight / sum_weight`, this quadruples-plus the entity's fraction of `ErasValidatorIncentiveBudget` relative to running one validator with the same total capital, all while every other validator's `own_weight` in the denominator is unaffected — directly diminishing their realized share of the same fixed pot.

Note: I was not able to fully trace `calculate_validator_incentive_for_page` and `transfer_validator_incentive` bodies in `substrate/frame/staking-async/src/pallet/impls.rs` beyond the call site shown, nor the exact budget-computation formula in `session_rotation.rs`, due to remaining tool-call budget; a Devin session with full repo access should confirm the exact `budget * weight / sum_weight` implementation and any un-surfaced per-controller aggregation guard before finalizing severity.

/// Piecewise sqrt-based incentive weight function.
///
/// - Below optimum: `w(s) = √s`
/// - Between optimum and cap: `w(s) = √(T + k² × (s - T))`
/// - Above cap: plateau at `w(cap)`
fn incentive_weight<Balance>(
	self_stake: Balance,
	optimum: Balance,
	cap: Balance,
	slope_factor: Perbill,
) -> Balance
where
	Balance: AtLeast32BitUnsigned + Copy + Into<u128> + From<u128>,
{
	debug_assert!(optimum <= cap, "config invariant: optimum must be <= cap");

	if self_stake.is_zero() {
		return Balance::zero();
	}

	if optimum.is_zero() && cap.is_zero() {
		return Balance::zero();
	}

	let self_stake_u128: u128 = self_stake.into();
	let optimum_u128: u128 = optimum.into();
	let cap_u128: u128 = cap.into();

	let weight_u128 = if self_stake <= optimum {
		sp_arithmetic::helpers_128bit::sqrt(self_stake_u128)
	} else if self_stake <= cap {
		let k_squared = slope_factor.square();
		let excess = self_stake_u128.saturating_sub(optimum_u128);
		let arg = optimum_u128.saturating_add(k_squared.mul_floor(excess));
		sp_arithmetic::helpers_128bit::sqrt(arg)
	} else {
		let k_squared = slope_factor.square();
		let excess = cap_u128.saturating_sub(optimum_u128);
		let arg = optimum_u128.saturating_add(k_squared.mul_floor(excess));
		sp_arithmetic::helpers_128bit::sqrt(arg)
	};

	Balance::from(weight_u128)
}

/// Compute the slash for a validator. Returns the amount slashed and the reward payout.
fn slash_validator<T: Config>(params: SlashParams<T>) -> (BalanceOf<T>, BalanceOf<T>) {
	let own_stake = params.exposure.exposure_metadata.own;
	let prior_slashed = params.prior_slash * own_stake;
	let new_total_slash = params.slash * own_stake;

	let slash_due = new_total_slash.saturating_sub(prior_slashed);
	// Audit Note: Previously, each repeated slash reduced the reward by 50% (e.g., 50% × 50% for
	// two offences). Since repeat offences in the same era are discarded unless the new slash is
	// higher, this reduction logic was unnecessary and removed.
	let reward_due = params.reward_proportion * slash_due;
	log!(
		warn,
		"🦹 slashing validator {:?} of stake: {:?} for {:?} in era {:?}",
		params.stash,
		own_stake,
		slash_due,
		params.offence_era,
	);

	(slash_due, reward_due)
}
