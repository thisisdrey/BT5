## Finding: LP share dilution via donation-inflation of pool reserves in `pallet-asset-conversion`

### Title
Unprotected balance-based reserve calculation in `pallet-asset-conversion::add_liquidity` enables LP-share inflation/theft attack - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`pallet-asset-conversion` computes pool "reserves" by directly reading the pool account's live asset balance via `get_balance`, rather than maintaining an internally-tracked reserve value that only advances through `add_liquidity`, `remove_liquidity`, and `swap`. Because the pool's sovereign account is a normal, publicly-transferable `AccountId`, any unprivileged actor can inflate the reported reserve by simply transferring tokens directly to it, without minting LP shares. This is the same broken invariant identified in the external report — a rebalancing/pricing function relying on raw token-balance state instead of a formula-consistent tracked reserve, making it trivially distortable by deposits that don't participate in the pricing/share logic — mapped onto this repository's constant-product AMM implementation.

### Finding Description
`get_balance` simply forwards to the underlying fungible balance: [1](#0-0) 

`get_reserves` (used by `quote_price_exact_tokens_for_tokens`, `quote_price_tokens_for_exact_tokens`, and internally by `add_liquidity`) derives both pool reserves purely from these live balances: [2](#0-1) 

When a subsequent liquidity provider calls `add_liquidity` on a non-empty pool, the LP token amount minted is `min(amount1 * total_supply / reserve1, amount2 * total_supply / reserve2)`: [3](#0-2) 

Because `reserve1`/`reserve2` are read straight from the pool account's balance (not from an internally maintained state that is only mutated by the pallet's own extrinsics), an attacker can:
1. Create a pool and add a minimal amount of liquidity, receiving a small number of LP shares (bounded below only by `MintMinLiquidity`).
2. Directly transfer (donate) a large amount of both assets to the pool's sovereign account using ordinary `Balances::transfer`/`Assets::transfer` calls — a `PoolLocator`-derived `AccountId` with no special protection against external deposits, as also exercised in the pallet's own migration tests operating on `pool_account` balances directly (`substrate/frame/asset-conversion/ops/src/tests.rs:75-105`).
3. This inflates `reserve1`/`reserve2` without minting any additional `total_supply`.
4. A subsequent honest depositor's `add_liquidity` call is now diluted: `amount * total_supply / reserve` rounds down severely, so the victim's real assets get pulled into the pool while receiving negligible LP shares (bounded only by the weak `lp_token_amount > MintMinLiquidity` check): [4](#0-3) 

5. The attacker then calls `remove_liquidity` with their initial (tiny) LP shares, redeeming a proportional share of the now much-larger real pool (which includes the victim's diluted contribution), extracting the victim's deposited value.

This mirrors exactly the external report's core broken invariant: the pricing/rebalancing formula treats raw token-account balance as if it were the protected, formula-consistent state variable ("reserve"/"active liquidity"), when in fact unrelated deposits can enter that balance and corrupt the computed ratio.

### Impact Explanation
This breaks the "conserve value and settle exactly once to the rightful beneficiary and amount" invariant for liquidity providers: an unprivileged attacker can cause wrong-beneficiary fund loss by minting themselves a disproportionate claim on a victim's deposited assets via LP-share dilution, purely through a public `add_liquidity` entrypoint plus ordinary token transfers to a derivable pool account — no admin/governance/relayer/validator assumption required. The same corrupted `reserve1`/`reserve2` values also feed `quote_price_exact_tokens_for_tokens`/`quote_price_tokens_for_exact_tokens`, which are consumed by `pallet-asset-conversion-tx-payment`'s `SwapAssetAdapter` for fee-asset conversion, so a donation can also transiently distort transaction-fee quoting for other users in the same block.

### Likelihood Explanation
The attack requires no privileged role, no malicious peer/validator/relayer, and no front-running of another user's transaction (the attacker triggers both the donation and the loss condition themselves, and it can be executed atomically within a `utility::batch_all` extrinsic before waiting for a victim's next `add_liquidity` call). The only cost to the attacker is the tokens donated, which are recovered — with profit — from the victim's subsequently diluted deposit. Pools with low total LP-token supply or thin early liquidity (freshly created pools, low-cap asset pairs) are the most exposed.

### Recommendation
Track pool reserves as pallet storage state that is only mutated by `add_liquidity`, `remove_liquidity`, and `swap` logic (Uniswap V2 style cached `reserve0`/`reserve1`, updated at the end of each state-changing call), rather than recomputing them from the pool account's live balance on every read. If balance-based accounting must be kept for backward compatibility, add a `sync`/`skim` mechanism (as Uniswap V2 does) so donated balance cannot silently enter the price/LP-mint formula, and/or bound LP-share minting so that `amount_desired / reserve` ratios computed from an attacker-inflatable balance cannot cause disproportionate donation-based dilution.

### Proof of Concept
1. Attacker calls `create_pool(asset1, asset2)`.
2. Attacker calls `add_liquidity(asset1, asset2, 1, 1, 1, 1, attacker)` — pool reserves become `(1, 1)`, attacker receives minimal LP shares (`> MintMinLiquidity`).
3. Attacker directly transfers a large amount, e.g. `1_000_000` of `asset1` and `asset2`, to the pool account address obtained via `PoolLocator::address(&pool_id)` (ordinary `Assets::transfer`/`Balances::transfer_keep_alive`, no interaction with `pallet-asset-conversion` extrinsics).
4. `get_reserves` now reports `(1_000_001, 1_000_001)` while `total_supply` of the LP token remains tied to the tiny original mint.
5. Victim calls `add_liquidity(asset1, asset2, 1_000_000, 1_000_000, 1, 1, victim)`. `lp_token_amount = min(amount1 * total_supply / reserve1, amount2 * total_supply / reserve2)` rounds to a value only marginally above `MintMinLiquidity`, while the victim's full `1_000_000`/`1_000_000` deposit is transferred into the pool account.
6. Attacker calls `remove_liquidity` with their original LP shares, redeeming a share of the pool now inflated by the victim's deposit, extracting value disproportionate to their true contribution. [5](#0-4)
