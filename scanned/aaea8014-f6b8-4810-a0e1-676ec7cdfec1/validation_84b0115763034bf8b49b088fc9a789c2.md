### Title
`transfer_approved` under-decrements the delegate's allowance relative to the actual amount swept from the owner's account - ([File: substrate/frame/assets/src/functions.rs])

### Summary
`pallet_assets::do_transfer_approved` reduces the `Approvals` storage entry by the caller-supplied nominal `amount`, but the underlying `transfer_and_die`/`prep_debit` logic can debit (and credit to the destination) an amount strictly *greater* than that nominal `amount` whenever the withdrawal would leave the owner's account balance between `0` and `min_balance`. This is the same broken invariant as the reported `transferFrom` bug: a value added on top of the nominal transfer amount (there a burn fee, here a forced dust-sweep) is applied to the owner's real balance but is not reflected in the bookkeeping value (there the allowance-spend accounting, here the `Approvals` remaining-amount accounting) that is supposed to cap the total deduction.

### Finding Description
`do_transfer_approved` is the implementation behind the public extrinsic `transfer_approved` (call index 25) and also behind the `fungibles::approvals::Mutate::transfer_from` trait implementation used by the ERC-20 `transferFrom` precompile: [1](#0-0) 

The allowance check and decrement operate on the caller-supplied `amount`:
```rust
let remaining = approved.amount.checked_sub(&amount).ok_or(Error::<T, I>::Unapproved)?;
let f = TransferFlags { keep_alive: false, best_effort: false, burn_dust: false };
owner_died = Self::transfer_and_die(id.clone(), owner, destination, amount, None, f)?.1;
``` [2](#0-1) 

`transfer_and_die` computes the real debit via `prep_debit`, whose doc explicitly states the actual debit "may be ... greater by up to the minimum balance less one": [3](#0-2) 

```rust
let actual = Self::reducible_balance(id.clone(), target, f.keep_alive)?.min(amount);
ensure!(f.best_effort || actual >= amount, Error::<T, I>::BalanceLow);
let conseq = Self::can_decrease(id, target, actual, f.keep_alive);
let actual = match conseq.into_result(f.keep_alive) {
    Ok(dust) => actual.saturating_add(dust), //< guaranteed by reducible_balance
    ...
```
When `owner`'s post-transfer balance would fall below `min_balance` (but is not already zero), `can_decrease` returns a non-zero `dust`, causing `actual` (the real debit) to be `amount + dust`. Since `burn_dust: false` is passed for this path, `prep_credit` sets `credit = debit = amount + dust`, so the *entire* dust amount is transferred to `destination`, not burned: [4](#0-3) 

The `Transferred` event even reports the real `credit` (i.e., `amount + dust`) as the transferred amount: [5](#0-4) 

But back in `do_transfer_approved`, the `Approvals` entry is only ever decremented by the nominal `amount` that was passed in, never by the real `debit`/`credit` value actually removed from the owner's account. The function signature and pallet-level docs assert the opposite invariant ("Will fail if `amount` is greater than the approval from `owner` to 'delegate'"), but nothing in the code enforces that the *actual* debited value stays within the approved cap: [6](#0-5) 

This mirrors the reported bug precisely: a secondary deduction (burn fee there, forced dust-sweep here) is computed and applied to the approver's real balance *after* the nominal transfer amount is decided, but the bookkeeping value that is supposed to bound total spend (`allowance` there, `Approvals::amount` here) is only ever reduced by the nominal amount, not the true debited amount.

### Impact Explanation
A delegate holding even a small residual allowance can call `transfer_approved` (or the ERC-20 `transferFrom` precompile, which calls `do_transfer_approved` directly) with an `amount` engineered so the owner's post-transfer balance lands strictly between `0` and `min_balance`. This forces the dust-sweep path, causing the destination to receive `amount + dust` and the owner to lose `amount + dust`, while `Approvals::amount` (and hence the owner's remaining allowance) is only reduced by `amount`. The owner is drained of more of their asset balance than they intended to authorize to that delegate, i.e. an unauthorized, uncapped extra deduction from the approver — a direct violation of "conserve value and settle exactly once to the rightful beneficiary and amount." This is exploitable by any unprivileged delegate holding a nonzero approval; no admin, governance, or validator involvement is needed.

### Likelihood Explanation
Likelihood is moderate: the attacker (the approved delegate) fully controls the `amount` parameter and can query the owner's live balance and the asset's `min_balance` (both public storage) to pick an `amount` that lands the owner's residual balance in the dust range. This requires no race condition, no privileged access, and works deterministically in a single call. The one constraint is that the owner's account must not already be "sufficient"-guaranteed to avoid dying entirely (i.e., the debit must leave a nonzero-but-below-min residual, not push straight to zero) — a condition the delegate can arrange by choosing `amount` appropriately relative to the owner's current balance and the asset `min_balance`.

### Recommendation
In `do_transfer_approved`, decrement `Approvals::amount` by the *actual* debited amount returned from `transfer_and_die`/`do_transfer`, not by the nominal `amount` argument. Concretely, capture the `credit`/`debit` value returned by `transfer_and_die` and use that value (bounded to not exceed `approved.amount`, erroring out if it would) when computing `remaining`, mirroring the fix recommended in the original report: compute the "extra" deduction up front and ensure `nominal_amount + extra <= approved.amount` before executing the transfer, rather than trusting the nominal amount alone to bound the withdrawal.

### Proof of Concept
1. Create asset `id` with `min_balance = M`. Owner `O` has balance `B` where `0 < B - X < M` for some `X`.
2. `O` calls `approve_transfer(id, delegate, X)`.
3. Delegate calls `transfer_approved(id, O, dest, X)` (or the `transferFrom(O, dest, X)` ERC-20 precompile call, which invokes the same `do_transfer_approved`).
4. Inside `transfer_and_die`, `prep_debit` computes `actual = X`, then `can_decrease` detects the post-transfer balance `B - X` is nonzero but `< M`, returning `dust = B - X`, so `actual` becomes `X + (B - X) = B` — the owner's entire remaining balance is swept to `dest`.
5. `Approvals::amount` is nonetheless decremented only by `X` (`remaining = approved.amount - X`), even though the owner actually lost `B` (their full balance), i.e., `B - X` more than what was approved and accounted for.
6. Observed result: owner's asset balance is drained by more than the nominal amount reflected in the allowance ledger, while `Assets::Transferred` event confirms `credit == B`, not `X`.

		target: &T::AccountId,
		amount: T::Balance,

	/// instead returns whether and how the `source` account died in this operation.
	fn transfer_and_die(
		id: T::AssetId,
		source: &T::AccountId,
		dest: &T::AccountId,
		amount: T::Balance,
		maybe_need_admin: Option<T::AccountId>,
		f: TransferFlags,
	) -> Result<(T::Balance, Option<DeadConsequence>), DispatchError> {
		// Early exit if no-op.
		if amount.is_zero() {
			return Ok((amount, None));
		}
		let details = Asset::<T, I>::get(&id).ok_or(Error::<T, I>::Unknown)?;
		ensure!(details.status == AssetStatus::Live, Error::<T, I>::AssetNotLive);
