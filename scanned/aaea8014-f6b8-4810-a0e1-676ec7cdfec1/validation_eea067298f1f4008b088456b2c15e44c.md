## Analysis

The external report's core broken invariant: **a value used to mint/allocate a scarce, protocol-controlled asset (fate) is derived from an instantaneous, atomically-manipulable AMM pool ratio**, letting an attacker cheaply distort that ratio via a swap, extract more value than intended, then reverse the swap for a small fee-only cost.

The strongest local analog is in `pallet-asset-conversion-tx-payment`'s `SwapAssetAdapter`, which uses the exact same AMM spot-price mechanism (`pallet-asset-conversion`'s constant-product reserves) to price a **protocol-critical, unprivileged, publicly reachable value: the transaction fee itself**.

### Title
Transaction fees paid in non-native assets are priced from a manipulable spot AMM ratio, enabling public underpriced work - (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

### Summary
`SwapAssetAdapter::withdraw_fee` computes how much of a user-chosen `asset_id` must be withdrawn to cover the native fee by calling `S::quote_price_tokens_for_exact_tokens(asset_id, A::get(), fee, true)`, which reads the current, unprotected pool reserves via `AssetConversion::get_reserves`/`get_amount_in`. Because this price is a raw constant-product spot price with no time-weighting, min/max bound, or external slippage check, any signed account can shift the reserve ratio with an ordinary swap extrinsic immediately before submitting the fee-paying extrinsic, causing the fee-conversion pallet to under-price the fee it charges relative to the actual native-token cost of the block resources consumed.

### Finding Description
`quote_price_tokens_for_exact_tokens` in `substrate/frame/asset-conversion/src/lib.rs` (lines 1571-1603) computes `get_amount_in`/`quote` purely from `Self::get_reserves(asset1, asset2)` at the moment of the call — the exact instantaneous-price pattern the pallet's own `QuotePrice` trait doc warns about: "The quoted price is only guaranteed if no other swaps are made ... before the target swap" (`substrate/frame/asset-conversion/src/swap.rs:116-120`).

`SwapAssetAdapter::withdraw_fee` (`substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs:142-157`) uses this quote directly and non-negotiably to decide `asset_fee`, the amount of `asset_id` withdrawn from the payer, then performs `swap_tokens_for_exact_tokens` for the exact quoted amount — there is no cap chosen by, or protecting, the chain (unlike a normal user-initiated swap where the user sets their own `amount_in_max`).

`ChargeAssetTxPayment::prepare` (`substrate/frame/transaction-payment/asset-conversion-tx-payment/src/lib.rs:327-343`) calls `withdraw_fee` before the wrapped `RuntimeCall` is dispatched, so an attacker cannot manipulate the pool from inside the very same extrinsic that pays with the manipulated price. However, nothing stops an attacker from submitting a sequence of same-account extrinsics in one block: (1) a swap that skews reserves in their favor, (2) the fee-paying extrinsic (using `asset_id` for payment), (3) a reversing swap. All three actions are unprivileged, ordinary calls from a single signed account with sequential nonces — this requires no malicious validator, collator, or relayer.

### Impact Explanation
This directly matches the "public underpriced work that degrades block production" impact category: the attacker consumes real block weight/resources while paying an artificially depressed fee in the `asset_id` token, at a cost bounded only by the AMM swap fee (e.g., 0.3%) for the round-trip manipulation — structurally identical to the original report's cost/benefit ratio (pay swap fees, extract inflated value). Repeated at scale, this allows systematically underpriced transaction inclusion, undermining the fee mechanism's role in preventing spam/DoS of block production, and drains value from the fee-recipient (`StakingPot`/collators) who receive less native-equivalent value than the dispatched weight actually cost.

### Likelihood Explanation
Likelihood is high wherever `pallet-asset-conversion-tx-payment` with `SwapAssetAdapter` is configured (used in `asset-hub-westend`, `asset-hub-rococo`, and `staking-async` parachain runtimes per `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs:1176-1188`). No privileged role is needed — only capital sufficient to move a pool's reserves and pay swap fees for one block, and ordinary control over one's own transaction ordering (nonce sequencing), which any account has.

### Recommendation
Do not use a raw, single-block spot AMM quote to price protocol fee payments. Options: use a time-weighted/oracle price, clamp the quoted fee-asset amount against a bounded deviation from a recent moving average, require the payer to specify (and the protocol to validate) a maximum acceptable `asset_id` amount independent of pool manipulation, or restrict `ChargeAssetTxPayment` to pools with sufficient depth/deposit-locking that makes single-block manipulation economically irrational (à la Alpha Finance's fair LP pricing recommendation from the original report).

### Proof of Concept
1. Attacker holds `asset_id` X and native asset A, with an X/A pool in `pallet-asset-conversion`.
2. Tx1 (attacker, nonce n): `swap_tokens_for_exact_tokens`/`swap_exact_tokens_for_tokens` pushing a large amount of A into the pool for X, skewing reserves so X is priced artificially high relative to A.
3. Tx2 (attacker, nonce n+1): a call using `ChargeAssetTxPayment::from(tip, Some(X))`; `SwapAssetAdapter::withdraw_fee` calls `quote_price_tokens_for_exact_tokens(X, A, fee, true)` against the now-skewed reserves, so a much smaller amount of X is withdrawn than would be required at the pre-manipulation price to cover the same native `fee`.
4. Tx3 (attacker, nonce n+2): reverse swap, returning A back out of the pool, recovering most of the capital from step 2, minus the AMM's swap fee.
5. Net result: attacker pays close to the LP swap fee (e.g., 0.3% twice) instead of the intended `fee` cost, for weight actually consumed by Tx2's dispatched call. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

			} else {
				Self::quote(&amount, &balance2, &balance1).ok()
