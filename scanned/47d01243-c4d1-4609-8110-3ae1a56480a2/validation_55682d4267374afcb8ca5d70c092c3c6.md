## Title
Unbounded reward inflation via minimal first-stake in `pallet-asset-rewards`'s `reward_per_token` — analogous to Synthetix `rewardPerTokenStored` first-depositor exploit - (`substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` implements the exact same Synthetix-style JIT reward accounting formula that the external report exploits: an accumulator `reward_per_token_stored` that is incremented each time it's queried by `reward_rate_per_block * elapsed_blocks * PRECISION_SCALING_FACTOR / total_tokens_staked`. Because `stake()` is a fully public, unprivileged extrinsic with **no minimum-stake enforcement**, any account can become the sole staker of a pool with an arbitrarily small amount (e.g. `1`), driving the denominator of this division to its minimum and inflating the accumulator disproportionately to their real economic contribution, then harvest/withdraw a reward share far exceeding their fair proportion — draining reward-asset tokens meant to be shared with subsequent, larger stakers.

### Finding Description
The reward accumulator is computed in `reward_per_token`: [1](#0-0) 

This is structurally identical to the vulnerable Synthetix `rewardPerToken()` formula in the external report: `rewardPerTokenStored + (elapsed * rewardRate * SCALE) / totalSupply`. The only difference is the precision constant is `PRECISION_SCALING_FACTOR = 4096` instead of `1e18`: [2](#0-1) 

Critically, `total_tokens_staked` (the denominator) is fully attacker-controlled with no floor: `stake()` is `ensure_signed`-only, with no minimum-stake check comparable to `MinJoinBond`/`MinCreateBond` in `pallet-nomination-pools`: [3](#0-2) 

An attacker can be the first (or sole) staker in a pool — either right after `create_pool` (which is permissioned, but staking into it is not), or after legitimate stakers have fully `unstake`d, driving `total_tokens_staked` back near zero — and stake a minimal amount, e.g. `1`. Each block that elapses while they remain the (near) sole staker, `reward_rate_per_block * elapsed_blocks * 4096` is divided by their tiny stake, producing a `reward_per_token_stored` value disproportionate to their actual contribution. When they call `harvest_rewards`, `derive_rewards` pays out based on this inflated accumulator: [4](#0-3) [5](#0-4) 

The payout is a real asset transfer out of the pool's reward account (`pool_info.account`), funded via `deposit_reward_tokens` or direct transfers by the admin: [6](#0-5) 

Existing guards (`ensure_add`, `ensure_mul`, `ensure_div` — checked arithmetic) only prevent overflow/panics; they do not bound the *economic* disproportion of the payout relative to stake size, so they do not stop this path.

### Impact Explanation
This directly maps to the "Balances, assets... treasury spends... must conserve value and settle exactly once to the rightful beneficiary and amount" pivot: reward tokens are transferred to a staker in an amount disproportionate to their actual stake share, at the expense of the reward budget legitimately owed to other stakers. Because the pool's reward-asset balance is finite (topped up manually), an attacker able to repeatedly execute this (stake minimal amount when total stake is low, wait, harvest, unstake) can systematically siphon a larger-than-fair share of the reward pot, potentially exhausting it before legitimate large stakers can claim their proportional rewards — a form of theft/underpaid settlement of a shared payout pool by an unprivileged actor.

### Likelihood Explanation
No privileged role, governance action, or malicious peer/validator is required — `stake`, `unstake`, and `harvest_rewards` are open, unprivileged, signed extrinsics. Any pool naturally passes through low-total-stake windows (right after creation, or after a mass unstake), which an attacker can exploit deterministically since the state is fully on-chain and observable. The only limiting factor is the smaller `PRECISION_SCALING_FACTOR` (4096) compared to Synthetix's `1e18`, which reduces (but does not eliminate) the magnitude of the achievable disproportion, especially for pools with a high `reward_rate_per_block` and long elapsed low-stake window.

### Recommendation
Enforce a `MinimumStake` (or similar floor, analogous to `nomination-pools`'s `MinJoinBond`) in `stake()` so `total_tokens_staked` cannot be driven to trivially small values relative to `reward_rate_per_block`, or virtually offset the denominator (e.g. add a fixed virtual stake, as recommended by common ERC4626 "first depositor" mitigations) in `reward_per_token` so the division cannot be dominated by a near-zero total.

### Proof of Concept
1. Admin calls `create_pool` with a non-trivial `reward_rate_per_block`.
2. Attacker calls `stake(pool_id, 1)` immediately, becoming sole staker with `total_tokens_staked = 1`.
3. Several blocks elapse (or attacker waits) while attacker remains the sole/dominant staker.
4. Attacker calls `harvest_rewards(pool_id, None)`; `reward_per_token()` returns `reward_per_token_stored + elapsed_blocks * reward_rate_per_block * 4096 / 1`, and `derive_rewards` pays out `1 * (reward_per_token - 0) / 4096 = elapsed_blocks * reward_rate_per_block`, i.e. the *entire* block reward budget for that period, despite staking only `1` unit.
5. Attacker then calls `unstake(pool_id, 1, None)`, exiting with a reward payout disproportionate to their contribution, depleting the pool's reward-asset balance available to legitimate future stakers. [7](#0-6)

		pub fn stake(origin: OriginFor<T>, pool_id: PoolId, amount: T::Balance) -> DispatchResult {
			let staker = ensure_signed(origin)?;

			// Always start by updating staker and pool rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let staker_info = PoolStakers::<T>::get(pool_id, &staker).unwrap_or_default();
			let (mut pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			T::AssetsFreezer::increase_frozen(
				pool_info.staked_asset_id.clone(),
				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.
			pool_info.total_tokens_staked.ensure_add_assign(amount)?;

			Pools::<T>::insert(pool_id, pool_info);

			// Update PoolStakers.
			staker_info.amount.ensure_add_assign(amount)?;
			PoolStakers::<T>::insert(pool_id, &staker, staker_info);

			// Emit event.
			Self::deposit_event(Event::Staked { staker, pool_id, amount });

			Ok(())
		}

		/// Harvest unclaimed pool rewards.
		///
		/// Parameters:
		/// - origin: must be the `staker` if the pool is still active. Otherwise, any account.
		/// - pool_id: the pool to harvest from.
		/// - staker: the account for which to harvest rewards. If `None`, the caller is used.
		#[pallet::call_index(3)]
		pub fn harvest_rewards(
			origin: OriginFor<T>,
			pool_id: PoolId,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool and staker rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info =
				PoolStakers::<T>::get(pool_id, &staker).ok_or(Error::<T>::NonExistentStaker)?;
			let (pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Transfer unclaimed rewards from the pool to the staker.
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&staker,
				staker_info.rewards,
				// Could kill the account, but only if the pool was already almost empty.
				Preservation::Expendable,
			)?;

			// Emit event.
			Self::deposit_event(Event::RewardsHarvested {
				caller,
				staker: staker.clone(),
				pool_id,
				amount: staker_info.rewards,
			});

			// Reset staker rewards.
			staker_info.rewards = 0u32.into();

			if staker_info.amount.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			Ok(())
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}

		/// Derives the amount of rewards earned by a staker.
		///
		/// This is a helper function for `update_pool_rewards` and should not be called directly.
		fn derive_rewards(
			staker_info: &PoolStakerInfo<T::Balance>,
			reward_per_token: &T::Balance,
		) -> Result<T::Balance, DispatchError> {
			Ok(staker_info
				.amount
				.ensure_mul(reward_per_token.ensure_sub(staker_info.reward_per_token_paid)?)?
				.ensure_div(PRECISION_SCALING_FACTOR.into())?
				.ensure_add(staker_info.rewards)?)
		}
