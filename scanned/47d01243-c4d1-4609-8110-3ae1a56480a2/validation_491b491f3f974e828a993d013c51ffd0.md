## Title
`process_delivery_receipt` pays relayer reward regardless of Ethereum delivery outcome, ignoring `receipt.success` - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`DeliveryReceipt` decoded from the Ethereum `InboundMessageDispatched` event carries a `success: bool` field indicating whether the message dispatch on Ethereum actually succeeded [1](#0-0) . `Pallet::process_delivery_receipt`, which is invoked from the public, unprivileged extrinsic `submit_delivery_receipt`, never reads or checks this `success` field before paying out the relayer reward and removing the `PendingOrder` [2](#0-1) . This mirrors the reported bug class: a guaranteed/queued state adjustment (here, the reward fee tied to a `PendingOrder`) is settled based on incomplete state — the pending state is resolved without checking the condition that determines whether the "trade" (delivery) actually completed as intended.

### Finding Description
The extrinsic entry point is: [3](#0-2) 

It verifies the Merkle/beacon proof of the event log via `T::Verifier::verify`, decodes the log into a `DeliveryReceipt`, and calls `process_delivery_receipt`. The verifier only proves that this particular log (including the `success` field as emitted by Ethereum) genuinely occurred on-chain on Ethereum — it does not imply `success == true`. The pallet logic then does:

```rust
pub fn process_delivery_receipt(...) -> DispatchResult {
    ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);
    let reward_account = ...;
    let nonce = receipt.nonce;
    let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;
    if order.fee > 0 {
        T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee);
    }
    <PendingOrders<T>>::remove(nonce);
    Self::deposit_event(Event::MessageDelivered { nonce });
    Ok(())
}
``` [4](#0-3) 

There is no `ensure!(receipt.success, ...)` or any branch on `receipt.success` anywhere in this function, nor is `receipt.success` referenced anywhere else in the pallet (confirmed by inspecting the full file). This means:
- Any relayer can call `submit_delivery_receipt` with a genuine, provable `InboundMessageDispatched(nonce, topic, success=false, reward_address)` event log — i.e. legitimately proving that the gateway attempted the dispatch but the underlying command execution *failed* on Ethereum — and still collect the full reward fee for the corresponding `PendingOrder`.
- The `MessageDelivered` event is emitted and the `PendingOrder` is removed as if delivery genuinely and successfully completed, even though the "trade" (cross-chain execution) is unhealthy/failed.

This is analogous to the intents bug: settlement of a pending, guaranteed-to-resolve state (`PendingOrder`/reward) is decided using a value from a broader payload (`DeliveryReceipt`) while the specific sub-field needed to make settlement fair/correct (`success`) is silently dropped from the invariant check, exactly like the intent price-adjustment field being computed elsewhere but omitted from the liquidation health check.

### Impact Explanation
This directly causes "duplicate/incorrect settlement" and "theft/unbacked payout" impact classes called out in the Polkadot SDK Impact Gate: an unprivileged relayer receives a reward funded from the sovereign/reward account for message deliveries that Ethereum itself reports as failed. Over many failed dispatches this drains the reward pool (`T::RewardPayment` / `bp_relayers::RewardLedger`) without providing the "useful" service the reward is meant to compensate (successful cross-chain execution), degrading the intended incentive/economic model of the bridge and constituting fund loss for the party funding rewards. No malicious peer, relayer collusion, or governance abuse is required — it's a plain unprivileged public dispatch.

### Likelihood Explanation
High. `submit_delivery_receipt` is a permissionless, signed extrinsic; the only requirement is a valid, real, provable Ethereum event log for a dispatch that failed on Ethereum (`success=false`), which is a common outcome (e.g., gas exhaustion, revert in a downstream `Command`, target contract failure) and entirely legitimate to produce and prove — no forgery needed.

### Recommendation
In `process_delivery_receipt`, check `receipt.success` before crediting the reward and/or handle the failure case distinctly (e.g., emit a `MessageDeliveryFailed` event, and either skip/reduce reward payment or route it based on policy) rather than unconditionally paying `order.fee` and removing the order for both success and failure receipts.

### Proof of Concept
1. A message is queued via `do_process_message`, creating `PendingOrders[nonce] = { nonce, fee: F, block_number }` [5](#0-4) .
2. On Ethereum, the Gateway contract processes the message but the command execution fails; the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)` (this is the honest/expected behavior of the Gateway for failed dispatches).
3. Any relayer builds an `EventProof` for this genuine log and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (log is real), `DeliveryReceipt::try_from` decodes `success: false` correctly [6](#0-5) .
5. `process_delivery_receipt` ignores `success`, pays `order.fee` to `reward_account` via `T::RewardPayment::register_reward`, removes the `PendingOrder`, and emits `MessageDelivered` [7](#0-6) .
6. The relayer collects the reward for a delivery that Ethereum itself recorded as failed — the existing test suite only exercises the halted/unhalted and tip-related paths and never asserts on `receipt.success == false` behavior [8](#0-7) , confirming the gap is untested and unguarded.

```rust
		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

// Reward processing must be blocked while the bridge is halted: `submit_delivery_receipt`
// should not pay out `PendingOrder` fees if the verifier reports the bridge as halted.
#[test]
fn poc_m1() {
	new_tester().execute_with(|| {
		let nonce = 1;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_event_proof());

		set_verifier_halted(true);

		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);

		let order_after = PendingOrders::<Test>::get(nonce).expect("order still present");
		assert_eq!(order_after.fee, fee);

		set_verifier_halted(false);
	});
}

// After governance resumes the bridge, legitimate delivery receipts flow through again:
// the order is paid out and removed from storage.
#[test]
fn submit_delivery_receipt_succeeds_after_unhalt() {
	new_tester().execute_with(|| {
		let nonce = 0;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_valid_event_proof());

		// Bridge halted — receipt rejected, order untouched.
		set_verifier_halted(true);
		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);
		assert!(PendingOrders::<Test>::get(nonce).is_some());

		// Bridge resumed — same receipt succeeds and the order is settled.
		set_verifier_halted(false);
		assert_ok!(OutboundQueue::submit_delivery_receipt(origin, event));
		assert!(PendingOrders::<Test>::get(nonce).is_none());

		System::assert_has_event(mock::RuntimeEvent::OutboundQueue(Event::MessageDelivered {
			nonce,
		}));
	});
}
