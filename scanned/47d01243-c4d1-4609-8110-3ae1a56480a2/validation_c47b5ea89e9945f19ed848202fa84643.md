### Title
Unbacked XCM asset credit from unverified ERC20 transfer amount in `ERC20Transactor` - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
The dPrime report's core broken invariant is: a supply-changing operation (`burn`) is trusted and recorded as having moved an exact amount of value, without the accounting layer (`LMCV`) verifying that the real token balance actually changed by that amount — creating a mismatch between recorded debt/collateral and real token supply. The closest verifiable local analog is in `ERC20Transactor::withdraw_asset_with_surplus` / `deposit_asset_with_surplus`, which treats an ERC20 `transfer()` call's boolean return value as proof that exactly the XCM-declared `amount` moved, and credits/debits the XCM `AssetsInHolding` ledger with that declared `amount` without checking the actual balance delta on the `checking_address`/beneficiary.

### Finding Description
In `withdraw_asset_with_surplus` [1](#0-0) , the `(asset_id, amount)` pair is derived from the caller-supplied XCM `Asset` via `Matcher::matches_fungibles`, and a `transferCall` for exactly `amount` is issued to the ERC20 contract at `asset_id`. The result is accepted purely based on the ABI-decoded boolean success flag: [2](#0-1) 
On success, the code unconditionally credits the XCM holding register with the full `amount` via `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — there is no read-back of the checking account's actual post-transfer balance to confirm the real balance increased by exactly `amount`.

The symmetric `deposit_asset_with_surplus` function performs the mirror operation, transferring the same *declared* `amount` from the checking account to the beneficiary and treating a `true` return as full settlement [3](#0-2) .

`Erc20Credit` — the imbalance type backing this bookkeeping — is explicitly documented as *not* runtime-enforced: "does not perform runtime-level balance enforcement... actual balance constraints are enforced by the ERC20 smart contract itself" [4](#0-3) . This design assumption only holds if the ERC20 contract's `transfer` semantics are exactly "moves `amount`, returns `true` iff `amount` moved." Any ERC20 contract behaving non-canonically (fee-on-transfer, rebasing, partial-transfer-then-`true`, or any Solidity/PVM bytecode deployed by an ordinary user via `pallet-revive`, since arbitrary contracts can be instantiated permissionlessly and then referenced as an XCM fungible asset id) breaks the invariant that the XCM holding register's recorded `amount` matches the real on-chain balance change — exactly analogous to `dPrime.burn` reducing real supply while `LMCV`'s recorded debt/collateral stays unchanged.

### Impact Explanation
If the declared `amount` and the true balance delta diverge, the XCM executor's internal holding accounting (used for `DepositAsset`, `BuyExecution`, fee/refund calculations, and cross-chain settlement) becomes internally inconsistent with the real ERC20 balances tracked by the underlying `pallet-revive` contract. This can result in credited holding value exceeding real backing (unbacked mint/credit) or a beneficiary receiving less than the ledger believes was settled (duplicate/incorrect settlement, permanent value discrepancy) — impacts explicitly in scope ("theft or unbacked mint or unlock", "duplicate settlement or payout").

### Likelihood Explanation
Exploitability depends on whether the asset-hub runtime's `Matcher` config allows attacker-controlled/arbitrary ERC20 contract addresses to be named as the XCM fungible asset id, or restricts `ERC20Transactor` to a fixed allow-list of vetted contracts. This runtime-wiring detail (`asset-hub-westend/src/xcm_config.rs` Matcher configuration) was not fully confirmed before the tool budget was exhausted — I located the type usage [5](#0-4)  but did not verify the exact `Matcher` bound. If the matcher restricts to a curated set of contracts, likelihood is low (Snowbridge/asset-hub team controls what tokens qualify); if it permits any deployed ERC20-shaped contract, likelihood is materially higher since anyone can deploy such a contract via `pallet-revive`.

### Recommendation
After each `transferCall`, read back the actual balance of the checking account (for withdraw) or beneficiary (for deposit) before and after the call and credit/settle only the observed delta rather than the XCM-declared `amount`. Alternatively, restrict `ERC20Transactor` to ERC20 contracts that are verified to implement exact, non-fee, non-rebasing transfer semantics, and treat any balance-delta mismatch as a hard transaction failure rather than trusting the boolean return value alone.

### Proof of Concept
Conceptual (not executed, since likelihood hinges on the unverified `Matcher` restriction):
1. Deploy (via `pallet-revive`, permissionlessly) an ERC20-like contract whose `transfer(to, value)` returns `true` but only moves `value - fee` tokens (or moves `value` but also silently mints tokens elsewhere, or reenters to manipulate its own reported balance).
2. If the asset-hub `Matcher` for `ERC20Transactor` accepts this contract's address as a valid XCM fungible `AssetId` (this is the unverified precondition), submit an XCM message causing `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` to be invoked with this contract.
3. Observe that `AssetsInHolding` is credited/debited with the full declared `amount` in `erc20_transactor.rs` lines 195-203 and 276-298, while the real balance change on the checking/beneficiary account differs — reproducing the "recorded supply/accounting diverges from real token balance" condition from the original report, without needing any admin, governance, or privileged actor.

Note: Because the exact `Matcher` binding in `asset-hub-westend/src/xcm_config.rs` was not fully read before the tool budget ran out, I cannot definitively confirm this is reachable by an unprivileged attacker in the shipped runtime configuration — this should be verified directly against that file before treating the finding as confirmed exploitable.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}
