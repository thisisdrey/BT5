## Analysis

I traced the reward-token bug class ("multiple items batched into one atomic transfer; one bad item blocks all, and the creator later reclaims everything") through the repo's fungible/asset-transfer code paths. The closest and most concrete analog is not in a payout pallet (treasury, staking, nomination-pools, bridge-relayers all pay a *single* asset per claim), but in the **Snowbridge Ethereum → AssetHub inbound message flow**, where a single XCM `DepositAsset` batches several caller-supplied assets, aborts entirely on one failure, and traps the whole batch under an origin that the Ethereum-side message sender fully controls.

### Title
Attacker-controlled Snowbridge inbound message origin lets the sender trap and later reclaim a beneficiary's legitimate bridged assets by including one malformed/unregistered asset - (File: `polkadot/xcm/xcm-executor/src/lib.rs`, `bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs`, `polkadot/xcm/pallet-xcm/src/lib.rs`)

### Summary
`MessageToXcm::prepare`/`convert` builds one XCM per inbound Ethereum message that batches all attacker-supplied assets (`NativeTokenERC20`/`ForeignTokenERC20`) into a single `WithdrawAsset`/`ReserveAssetDeposited` + `DepositAsset { assets: Wild(AllCounted(n)), beneficiary }` program [1](#0-0) [2](#0-1) . The XCM executor's `deposit_assets_with_retry` aborts the *entire* `DepositAsset` instruction if any single asset in the batch fails to deposit (e.g. an asset that was never created/registered on the destination, or one whose deposit fails for any other reason), and the whole pre-instruction holding — including the assets that would have deposited fine — is trapped rather than delivered [3](#0-2) . This exact behavior is documented and tested as intentional design in `polkadot/xcm/xcm-executor/src/tests/deposit_with_retry.rs` [4](#0-3) , and is reproduced end-to-end for Snowbridge in `send_weth_and_dot_to_penpal_v2`-style tests where a message with an unregistered/mis-ordered asset causes `Processed { success: false }` [5](#0-4) .

Trapped assets are recorded keyed by `hash(origin, assets)` in `pallet_xcm::AssetTraps`, and can only be reclaimed by an XCM/extrinsic whose *executing origin* matches that recorded `origin` exactly [6](#0-5) [7](#0-6) . For a Snowbridge inbound message the origin used on the destination is derived from `UniversalOrigin(GlobalConsensus(Ethereum))` plus `DescendOrigin(AccountKey20(message.origin))`, where `message.origin` is the attacker's own EVM sender address, fully controlled by whoever calls the Ethereum Gateway [8](#0-7) .

### Finding Description
An Ethereum-side sender crafts a `v2_sendMessage` call whose `assets` list mixes a legitimate asset (e.g. a registered WETH/ERC-20 already usable on AssetHub) with one asset that is guaranteed to fail deposit on AssetHub — for example a `ForeignTokenERC20` referencing a token that has not yet been registered/created, or one whose reanchoring/creation ordering is wrong (the repo's own test at lines 400-497 of `snowbridge_v2_inbound.rs` demonstrates this exact "asset creation vs. deposit ordering" failure mode) [9](#0-8) . The remote XCM constructed by the converter deposits *all* assets to a single `beneficiary` in one `DepositAsset { assets: Wild(AllCounted(n)) }` instruction. Because `deposit_assets_with_retry` fails the whole instruction on any per-asset failure and `transactional_process` rolls back the holding to its pre-instruction state, none of the batch — including the legitimate asset — reaches the beneficiary; instead the full holding is trapped under the attacker-controlled origin (`Ethereum/AccountKey20(attacker)`).

The intended `beneficiary` (a normal AssetHub account, analogous to the "solver" in the original report) has no way to claim these trapped assets, because `pallet_xcm::claim_assets` requires the caller's `ExecuteXcmOrigin` to resolve to exactly the trap's recorded origin location [10](#0-9)  — a signed AssetHub account can never produce a `GlobalConsensus(Ethereum)/AccountKey20(...)` origin. Only the attacker, by sending a second Ethereum message from the same EVM address with a `Payload::Raw` XCM containing `ClaimAsset { assets, ticket }` followed by `DepositAsset` to a beneficiary of their choosing, can reproduce that exact origin and reclaim the trapped value [11](#0-10) . This mirrors the IntentVault pattern precisely: a "reward-looking" message that is designed to always fail atomically, letting the creator (message sender) later reclaim what was ostensibly promised to someone else.

### Impact Explanation
An attacker can craft messages that look like legitimate token transfers/rewards to a beneficiary but are engineered to always fail the batched `DepositAsset`, permanently locking the legitimate portion of the transfer away from the intended recipient while retaining for themselves the exclusive, deterministic ability to reclaim it later via a follow-up message from the same Ethereum origin. This is a fund-lock/theft primitive against Snowbridge users, matching the "permanent user-fund or bridge-state lock" and "duplicate settlement or payout" impact classes in scope.

### Likelihood Explanation
Likelihood is medium: it requires a malicious/self-serving message sender on the Ethereum side (not a validator, relayer, or governance actor — an ordinary permissionless caller of the Gateway contract), and only needs one asset in the batch to be unregistered/mis-ordered/otherwise deposit-failing, which is trivial and fully within the sender's control (they choose both the asset list and the `origin` field).

### Recommendation
Do not batch attacker-supplied, heterogeneous assets from a single inbound message into one atomic `DepositAsset`/`Wild(AllCounted(n))` when partial failure can trap the whole batch under an origin the beneficiary cannot reach. Either (a) deposit each asset to the beneficiary independently so a single bad asset cannot block delivery of the others, mirroring the "handle individual transfers via low-level calls" fix pattern from the original report, or (b) ensure the AssetTrap origin used for inbound bridge messages is anchored to the beneficiary/claimer (as already done for the `claimer`-based Ether/fee refund path) rather than to the raw, attacker-controlled Ethereum sender location, so the intended recipient — not the message crafter — can always reclaim trapped funds.

### Proof of Concept
1. Attacker calls `v2_sendMessage` on the Ethereum Gateway from their own EVM address `A`, with `assets = [LegitimateAsset(value=X), BogusForeignTokenERC20]`, where `BogusForeignTokenERC20` references a token not yet created/registered on AssetHub (or crafted so `ConvertAssetId`/creation ordering fails as in the repo's own `send_weth_and_dot_from_asset_hub_to_ethereum`-style test) and `claimer = None`/absent so fallback claimer semantics don't rescue the beneficiary.
2. Relayer submits the proof; `EthereumInboundQueueV2::process_message` converts it via `MessageToXcm::convert`, producing an XCM with `DescendOrigin(AccountKey20(A))`, `WithdrawAsset`/`ReserveAssetDeposited` for both assets, then `DepositAsset { assets: Wild(AllCounted(2)), beneficiary }`.
3. On AssetHub, `deposit_assets_with_retry` succeeds for `LegitimateAsset` on the first pass but fails to deposit `BogusForeignTokenERC20` on the retry pass; the whole `DepositAsset` instruction errors, `transactional_process` restores the full pre-instruction holding, and `post_process` traps it under origin `GlobalConsensus(Ethereum)/AccountKey20(A)` — matching the mechanics shown in `partial_deposit_failure_aborts_instruction_and_traps_full_holding` and the message-processing failure asserted in `send_weth_and_dot_from_asset_hub_to_ethereum`'s inbound counterpart. `MessageQueue::Processed { success: false }` is emitted; the intended beneficiary receives nothing.
4. Attacker later sends a second Ethereum message from the same address `A` with `Payload::Raw` containing `ClaimAsset { assets: [LegitimateAsset(X), BogusForeignTokenERC20], ticket }` + `DepositAsset { assets: Wild(AllCounted(2)), beneficiary: <attacker's own AssetHub account> }`. Because this message again resolves to origin `Ethereum/AccountKey20(A)`, `pallet_xcm`'s `ClaimAssets::claim_assets` matches the stored trap hash and mints the trapped assets back into holding, which are then deposited to the attacker, completing the theft of the value originally destined for the first beneficiary.

```rust
	fn deposit_assets_with_retry(
		to_deposit: AssetsInHolding,
		beneficiary: &Location,
		context: Option<&XcmContext>,
	) -> Result<Weight, XcmError> {
		let mut total_surplus = Weight::zero();
		let mut failed_deposits = AssetsInHolding::new();

		// First pass: try to deposit each asset; failures go to retry.
		for single in to_deposit.into_per_asset_holdings() {
			match Config::AssetTransactor::deposit_asset_with_surplus(single, beneficiary, context)
			{
				Ok(surplus) => total_surplus.saturating_accrue(surplus),
				Err((unspent, _)) => {
					// First-pass failure: keep for retry. A subsequent deposit in the same
					// pass may create the destination account (by satisfying ED), allowing
					// the retry pass to succeed for assets that fall here.
					failed_deposits.subsume_assets(unspent);
				},
			}
		}

		// Retry previously failed deposits, this time short-circuiting on any error.
		for single in failed_deposits.into_per_asset_holdings() {
			let surplus =
				Config::AssetTransactor::deposit_asset_with_surplus(single, beneficiary, context)
					.map_err(|(unspent, error)| {
					tracing::debug!(
						target: "xcm::deposit_assets_with_retry",
						?error,
						?unspent,
						"Retry-pass deposit failed"
					);
					error
				})?;
			total_surplus.saturating_accrue(surplus);
		}

		Ok(total_surplus)
	}
```

```rust
impl<T: Config> DropAssets for Pallet<T> {
	fn drop_assets(origin: &Location, holding: AssetsInHolding, _context: &XcmContext) -> Weight {
		if holding.is_empty() {
			return Weight::zero();
		}
		let assets: Vec<Asset> = holding.assets_iter().collect();
		// SAFETY: "forget" about any fungible imbalances so that they are not dropped/resolved
		// here. The mirrored asset claiming operation will "recover" the imbalances by minting
		// back into holding, effectively duplicating the imbalance and only then dropping the
		// duplicate. As a result, total issuance doesn't change.
		holding.fungible.into_iter().for_each(|(_, mut accounting)| {
			accounting.forget_imbalance();
		});
		let versioned = VersionedAssets::from(Assets::from(assets));
		let hash = BlakeTwo256::hash_of(&(&origin, &versioned));
		AssetTraps::<T>::mutate(hash, |n| *n += 1);
		Self::deposit_event(Event::AssetsTrapped {
			hash,
			origin: origin.clone(),
			assets: versioned,
		});
		// TODO #3735: Put the real weight in there.
		Weight::zero()
	}
```

```rust
impl<T: Config> ClaimAssets for Pallet<T> {
	fn claim_assets(
		origin: &Location,
		ticket: &Location,
		assets: &Assets,
		context: &XcmContext,
	) -> Option<AssetsInHolding> {
		let mut versioned = VersionedAssets::from(assets.clone());
		match ticket.unpack() {
			(0, [GeneralIndex(i)]) => {
				versioned = match versioned.into_version(*i as u32) {
					Ok(v) => v,
					Err(()) => return None,
				}
			},
			(0, []) => (),
			_ => return None,
		};
		let hash = BlakeTwo256::hash_of(&(origin.clone(), versioned.clone()));
		match AssetTraps::<T>::get(hash) {
			0 => return None,
			1 => AssetTraps::<T>::remove(hash),
			n => AssetTraps::<T>::insert(hash, n - 1),
		}
		let mut claimed = AssetsInHolding::new();
		for asset in assets.inner() {
			match <T::XcmExecutor as XcmAssetTransfers>::AssetTransactor::mint_asset(asset, context)
			{
				Ok(minted) => {
					// SAFETY: Any fungible imbalances are now effectively duplicated because they
					// were not resolved when the asset was trapped (so total issuance tracks
					// trapped assets too), and now a duplicate asset was just minted.
					// To balance the system and keep total issuance constant, we drop and resolve
					// one of the duplicates. As a result, total issuance doesn't change.
					//
					// Note: This may emit Burned/Minted events even though the net issuance change
					// is zero. The mint creates a +X imbalance, and dropping the clone resolves -X,
					// resulting in no net change but potentially two events. This is an acceptable
					// tradeoff for the asset trap/claim mechanism.
					minted.fungible.iter().for_each(|(_, imbalance)| {
						let to_resolve = imbalance.unsafe_clone();
						core::mem::drop(to_resolve);
					});
					claimed.subsume_assets(minted)
				},
				Err(error) => tracing::debug!(
					target: "xcm::pallet_xcm::claim_assets",
					?asset, ?error, "Asset claimed from trap but unable to mint."
				),
			}
		}
		Self::deposit_event(Event::AssetsClaimed {
			hash,
			origin: origin.clone(),
			assets: versioned,
		});
		Some(claimed)
	}
```
