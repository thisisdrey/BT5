### Title
CREATE/CREATE2 initcode-size check uses hardcoded EIP-3860 mainnet constant instead of the chain's actual configured code-size limit - (File: `substrate/frame/revive/src/vm/evm/instructions/contract.rs`)

### Summary
`pallet-revive`'s EVM `CREATE`/`CREATE2` opcode implementation rejects initcode above the hardcoded Ethereum-mainnet constant `revm::primitives::eip3860::MAX_INITCODE_SIZE` (49152 bytes), rather than deriving the limit from the pallet's actual configured code-size ceiling (`limits::code::BLOB_BYTES` = 1 MiB). This is the exact bug class described in the Monad report: the opcode enforces an unrelated hardcoded external-protocol constant instead of the chain-specific configured parameter, silently under-allowing contract creation relative to what the chain actually supports.

### Finding Description
In `create()`: [1](#0-0) 
the length check is:
```rust
if len > revm::primitives::eip3860::MAX_INITCODE_SIZE &&
    !DebugSettings::is_unlimited_contract_size_allowed::<E::T>()
{
    return ControlFlow::Break(Error::<E::T>::BlobTooLarge.into());
}
```
`MAX_INITCODE_SIZE` is a hardcoded Ethereum-mainnet constant tied to EIP-3860 (`2 * eip170::MAX_CODE_SIZE` = 49152 bytes), same as in the Monad CREATE/CREATE2 report. This exact same hardcoded pair is reused identically in `ContractBlob::from_evm_init_code`: [2](#0-1) 

However, `pallet-revive`'s own configured maximum contract blob size is defined independently in `limits::code::BLOB_BYTES = 1024 * 1024` (1 MiB), enforced by `limits::code::enforce()` for the pallet's native PVM code path: [3](#0-2) 

The EVM `CREATE`/`CREATE2` path never consults `BLOB_BYTES` (or any Config-derived limit); it only compares against the EIP-3860 constant imported from `revm`, which is a fixed Ethereum-mainnet value unrelated to this chain's actual configured code-storage capacity. This mirrors the Monad bug precisely: the opcode's guard is bound to an external protocol's parameter value instead of the chain's own configured ceiling, so `CREATE`/`CREATE2` under-allows relative to what the runtime is actually provisioned to store and execute (1 MiB blobs). Any EVM factory pattern that assembles large embedded/init data (bytecode + constructor args, e.g., diamond-pattern deployers, minimal-proxy factories with embedded metadata, or contracts that bundle sizeable constructor-time data) that would otherwise fit comfortably within `BLOB_BYTES` will unconditionally fail at 49152 bytes.

The only escape hatch, `DebugSettings::is_unlimited_contract_size_allowed`, is a governance/debug-mode-gated flag — it does not fix the underlying mismatch, it only allows bypassing the check entirely (which is a different, coarser control, not a correct binding to `BLOB_BYTES`).

### Impact Explanation
Because CREATE2 addresses are deterministic (`keccak256(sender, salt, initcodehash)`), users, integrators, or protocol tooling reasonably assume contract deployment succeeds up to the chain's advertised/configured code-size capacity. If a legitimate factory contract's initcode exceeds 49152 bytes but is well within the chain's actual 1 MiB blob budget, deployment via `CREATE`/`CREATE2` will always revert with `BlobTooLarge`, while funds pre-sent to the deterministically computed (but never-deployed) CREATE2 address become permanently stranded — matching the "permanent user-fund lock" impact class, and functionally bricking any factory contract relying on larger initcode, consistent with the original Monad finding's characterization ("this might cause certain factory contracts to be bricked").

### Likelihood Explanation
This triggers deterministically and requires no privileged access: any unprivileged EVM caller issuing `CREATE`/`CREATE2` with initcode between 49153 bytes and the chain's real capacity (up to `BLOB_BYTES`) hits the hardcoded ceiling every time. It is a public, always-reachable code path (standard EVM opcode execution inside pallet-revive), not an edge case requiring a malicious actor, relayer, or governance action.

### Recommendation
Replace the hardcoded `revm::primitives::eip3860::MAX_INITCODE_SIZE` / `eip170::MAX_CODE_SIZE` comparisons in `create()` (`contract.rs`) and in `ContractBlob::from_evm_init_code` / `from_evm_runtime_code_with_deposit` (`evm.rs`) with checks against the pallet's actual configured limits (`crate::limits::code::BLOB_BYTES`, or a dedicated `Config`-exposed constant), so that EVM initcode/runtime-code size checks are bound to the chain's real configured capacity rather than an unrelated external-protocol constant.

### Proof of Concept
1. Deploy on a pallet-revive-based chain with default `BLOB_BYTES = 1 MiB`.
2. Craft EVM initcode (constructor bytecode + embedded constructor args/data) with length `L` such that `49152 < L <= 1_048_576` (i.e., within the chain's real configured capacity but above the hardcoded EIP-3860 constant).
3. Call `CREATE2` (or `CREATE`) with this initcode from an unprivileged EOA/contract, with `DebugSettings::is_unlimited_contract_size_allowed` left at its default (disabled) value.
4. Observe the opcode unconditionally returns `Error::BlobTooLarge` per [4](#0-3) , even though such a blob would pass the pallet's real `limits::code::enforce()` size gate for native PVM code.
5. If a counterpart precomputed the CREATE2 address and transferred funds to it beforehand (standard pattern for gas-efficient deployments), those funds are now unrecoverable since the contract can never be deployed at that address through the standard path.
