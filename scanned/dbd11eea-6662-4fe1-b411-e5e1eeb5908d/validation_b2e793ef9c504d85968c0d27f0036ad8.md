### Title
`pallet-accumulate-and-forward` provides no way to recover funds when `Forwarder::forward` permanently fails, permanently stranding accumulated tokens - (File: `substrate/frame/accumulate-and-forward/src/lib.rs`)

### Summary
`pallet-accumulate-and-forward` intercepts fees, dust, and coretime revenue into a deterministic `accumulation_account` and relies exclusively on an automatic `on_idle` hook to periodically forward the balance to a destination via `T::Forwarder::forward`. The pallet exposes **no extrinsics at all** — there is no `#[pallet::call]` section in the crate [1](#0-0)  — so if the configured `Forwarder` implementation fails persistently (e.g., XCM send failure, misconfigured destination, suspended HRMP channel, or a change in destination-chain configuration that makes the message undeliverable), the accumulated funds sit in the `accumulation_account` indefinitely with **no sweep, retry-trigger, or governance recovery path**, mirroring the `MarginAccount → InsuranceFund` stuck-funds bug class from the external report.

### Finding Description
Funds flow into the pallet's `accumulation_account` (`T::PalletId::get().into_account_truncating()`) via `OnUnbalanced` handlers (`DealWithFeesSplit`, direct `on_nonzero_unbalanced`, or the legacy `LegacyAdapter`) [2](#0-1) . The only exit path for this balance is the automatic `on_idle` hook, which checks the reducible balance against `MinTransferAmount` and, if sufficient weight remains, calls `T::Forwarder::forward(accumulation_account, available_funds)`: [3](#0-2) 

If `forward` returns `Err(())`, the pallet just emits a `ForwardFailed` event and leaves the funds in the account to be retried at the next `TransferPeriod` boundary — but the on-chain state and destination configuration that caused the failure are not addressed by this retry. There is no privileged or permissionless call in the pallet to:
- change or repair the `Forwarder`/destination configuration and re-trigger a forward on demand,
- manually withdraw/sweep the accumulation account's balance to an alternate destination, or
- transfer the stuck balance to treasury or any other recoverable account.

Compare this to two other pallets in the same repository that were patched specifically to close this exact bug class:
- `pallet-bounties` added a permissionless `reclaim_bounty_funds` extrinsic specifically because funds could get "stranded in a closed bounty's account" with no way to move them [4](#0-3) .
- `pallet-society` was patched because funds "backing pending payouts" could be "left … stranded in the sub-account with no `Payouts` entry left to claim it" [5](#0-4) .

`pallet-accumulate-and-forward` has no analogous recovery mechanism, and unlike `pallet-asset-rewards`'s `cleanup_pool`, which explicitly transfers the pool's residual reward balance back to the admin [6](#0-5) , the accumulate-and-forward pallet has no equivalent cleanup/sweep call.

### Impact Explanation
This pallet is wired into system parachains (Westend, Asset Hub Westend, Bridge Hub Westend, Collectives, Coretime, People) to redirect transaction fees, dust removal, and coretime revenue away from being burned [7](#0-6) . Since it continuously and automatically ingests protocol revenue (fees, coretime revenue, dust) with no manual override, any persistent failure of the destination `Forwarder` (e.g., broken XCM route, misconfigured destination `PalletId`, or a governance-driven runtime change to the destination parachain that rejects the forwarded message) results in real, ever-growing protocol revenue being permanently and irrecoverably locked in the `accumulation_account`, with the only "fix" requiring a runtime upgrade to add an extrinsic — exactly the medium-severity "assets locked forever, would need code change to unlock" outcome from the external report.

### Likelihood Explanation
The failure mode does not require a malicious actor: it can be triggered by ordinary operational conditions — a suspended/closed HRMP channel to the destination, a change to `Forwarder`/`CreateAssetCall`-style configuration on the destination chain, weight-limit exhaustion patterns in `on_idle`, or a bug in the specific `Forwarder` implementation used by a given runtime. Given the pallet is deployed on multiple live system parachains and continuously accumulates real fee/dust/coretime revenue, the probability of hitting a sustained forwarding failure over the pallet's operational lifetime is non-trivial, and once it happens the funds are stuck with no in-protocol remedy.

### Recommendation
Add a permissioned (or carefully rate-limited permissionless, following the `reclaim_bounty_funds` pattern) extrinsic to `pallet-accumulate-and-forward` that allows:
1. Manually triggering a forward attempt outside the `TransferPeriod` cadence (useful once the underlying issue is fixed), and
2. As a last resort, sweeping the `accumulation_account`'s reducible balance to a configurable fallback destination (e.g., treasury) under governance origin, so that funds are never permanently unrecoverable without a runtime upgrade.

### Proof of Concept
1. Configure a runtime with `pallet-accumulate-and-forward` and a `Forwarder` implementation that depends on a live XCM channel to a destination parachain (as is done for DOT forwarding to `pallet-dap`) [8](#0-7) .
2. Let fees/dust/coretime revenue accumulate into `accumulation_account` via `DealWithFeesSplit`/`OnUnbalanced` over multiple blocks [2](#0-1) .
3. Suspend or misconfigure the destination channel (e.g., close the HRMP channel or downgrade destination pallet index) so `T::Forwarder::forward` starts returning `Err(())`.
4. Observe `on_idle` repeatedly emitting `Event::ForwardFailed` every `TransferPeriod` while the balance in `accumulation_account` keeps growing [9](#0-8) .
5. Confirm there is no extrinsic in the pallet (absence of any `#[pallet::call]` block) that can move the stuck balance elsewhere — the funds remain locked until a runtime upgrade adds such a mechanism.

	#[pallet::hooks]
	impl<T: Config> Hooks<SystemBlockNumberFor<T>> for Pallet<T> {
		fn on_idle(_block: SystemBlockNumberFor<T>, remaining_weight: Weight) -> Weight {
			// Only attempt forwarding on blocks that are exact multiples of `TransferPeriod`.
			let block = T::BlockNumberProvider::current_block_number();
			if (block % T::TransferPeriod::get()) != Zero::zero() {
				return Weight::zero();
			}

			let mut meter = WeightMeter::with_limit(remaining_weight);

			// Need one read for the balance check.
			if meter.try_consume(T::DbWeight::get().reads(1)).is_err() {
				return meter.consumed();
			}

			let accumulation_account = Self::accumulation_account();
			// We use `reducible_balance` with `Preservation::Preserve` to get the
			// usable balance (excluding the ED).
			let available_funds = T::Currency::reducible_balance(
				&accumulation_account,
				Preservation::Preserve,
				Fortitude::Polite,
			);

			if available_funds < T::MinTransferAmount::get() {
				return meter.consumed();
			}

			// Ensure there is enough weight budget for the full XCM send.
			if meter.try_consume(T::WeightInfo::send_native()).is_err() {
				return meter.consumed();
			}

			// Attempt to forward accumulated funds.
			match T::Forwarder::forward(accumulation_account, available_funds) {
				Ok(()) => {
					Self::deposit_event(Event::ForwardSucceeded { amount: available_funds });
				},
				Err(()) => {
					log::debug!(
						target: LOG_TARGET,
						"accumulate-forward transfer of {:?} failed at block {:?}",
						available_funds,
						block,
					);
					Self::deposit_event(Event::ForwardFailed { amount: available_funds });
				},
			}

			meter.consumed()
		}

impl<T: Config> OnUnbalanced<CreditOf<T>> for Pallet<T> {
	fn on_nonzero_unbalanced(amount: CreditOf<T>) {
		let accumulation_account = Self::accumulation_account();
		let numeric_amount = amount.peek();

		// Resolve should never fail because:
		// - can_deposit on destination succeeds assuming accumulation account is pre-funded with ED
		// - amount is guaranteed non-zero by the trait method signature
		// The only failure would be overflow on destination or unfunded account.
		let _ = T::Currency::resolve(&accumulation_account, amount).inspect_err(|_| {
			frame_support::defensive!(
				"🚨 Failed to deposit to accumulation account - funds burned, it should never happen!"
			);
		});

		log::debug!(
			target: LOG_TARGET,
			"💸 Deposited {numeric_amount:?} to accumulation account"
		);
	}
}

		/// Cleanup a pool.
		///
		/// Origin must be the pool admin.
		///
		/// Cleanup storage, release any associated storage cost and return the remaining reward
		/// tokens to the admin.
		#[pallet::call_index(8)]
		pub fn cleanup_pool(origin: OriginFor<T>, pool_id: PoolId) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			ensure!(pool_info.admin == who, BadOrigin);

			let stakers = PoolStakers::<T>::iter_key_prefix(pool_id).next();
			ensure!(stakers.is_none(), Error::<T>::NonEmptyPool);

			let pool_balance = T::Assets::reducible_balance(
				pool_info.reward_asset_id.clone(),
				&pool_info.account,
				Preservation::Expendable,
				Fortitude::Polite,
			);
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&pool_info.admin,
				pool_balance,
				Preservation::Expendable,
			)?;

			if let Some((who, cost)) = PoolCost::<T>::take(pool_id) {
				T::Consideration::drop(cost, &who)?;
			}

			Pools::<T>::remove(pool_id);

			Self::deposit_event(Event::PoolCleanedUp { pool_id });

			Ok(())
		}
