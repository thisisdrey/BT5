Unbounded slippage in `SwapFirstAssetTrader::refund_weight` lets an attacker sandwich XCM fee refunds and drain refunded value via the AssetConversion pool - (File: cumulus/primitives/utility/src/lib.rs)

### Summary
`SwapFirstAssetTrader` is a `WeightTrader` used by XCM executors on Asset Hub Rococo, Asset Hub Westend, Penpal, and the staking-async parachain runtime to pay execution fees in a non-native asset by swapping it for the `Target` fee asset through `pallet_asset_conversion`'s `SwapCredit`. When it refunds unused weight, `refund_weight` swaps the surplus `Target` asset credit back into the user's original fee asset by calling `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min` hardcoded to `None`, i.e., with no minimum-output enforcement [1](#0-0) . This is the same missing-slippage-protection pattern flagged in the external report for `swapTokensForCounterpart`/`addLiquidity`, applied to a live, in-repo AMM swap path.

### Finding Description
`buy_weight` withdraws the user's non-target payment asset and swaps it for the `Target` asset via `SwapCredit::swap_tokens_for_exact_tokens`, correctly requesting an exact `fee` amount [2](#0-1) . `refund_weight`, however, extracts the unused portion of `total_fee` (held in `Target` asset) and swaps it back into `refund_swap_asset` (the user's original asset) using `swap_exact_tokens_for_tokens` with the minimum-output argument set to `None`: [1](#0-0) 

`pallet_asset_conversion::SwapCredit::swap_exact_tokens_for_tokens` treats `None` as "accept any output," bypassing the `ProvidedMinimumNotSufficientForSwap` check that normally guards swaps [3](#0-2) . The pool reserves used for this swap are the same public, permissionlessly-tradable AssetConversion pool (`Target`/user-asset pair) that any account can add liquidity to or swap against via the dispatchable `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` calls [4](#0-3) . This trader is instantiated in the live XCM `Trader` configuration of Asset Hub Rococo, Asset Hub Westend, Penpal, and the staking-async parachain runtime, so `refund_weight` executes on every XCM message that overpays weight fees in a swappable asset and gets a refund.

An attacker who observes an in-flight XCM message that will trigger `buy_weight`/`refund_weight` (fees are commonly overestimated, so refunds are routine) can move the pool's price against the refund swap immediately before it executes and restore it immediately after, extracting the difference between the fair refund amount and the manipulated amount. Existing guards (`ProvidedMinimumNotSufficientForSwap`) exist precisely to prevent this in every other call site of `SwapCredit`/`Swap` in the codebase (e.g. `SwapAssetAdapter::correct_and_deposit_fee` always quotes and passes `Some(refund_asset_amount)` before swapping back a refund [5](#0-4) ), but `refund_weight` in `SwapFirstAssetTrader` omits it entirely.

### Impact Explanation
The corrupted value is the amount of the original fee-payment asset credited back to the user (or effectively donated to the parachain, since if the swap fails the refund is retained internally rather than distributed to `who`). Because the swap accepts any nonzero output, a manipulated pool price can make the refund conversion yield far less than the fair amount, effectively transferring value from the intended refund recipient to whoever manipulated the pool (the sandwiching party captures the spread). This falls under "public underpriced work" / value non-conservation during settlement of bridge/XCM fee handling, degrading intended fee-refund behavior on a public AMM pool without needing any privileged actor.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to have advance knowledge of an incoming XCM message that will trigger a fee refund and the ability to submit swap transactions against the same `AssetConversion` pool before and after that refund executes within the same or adjacent blocks. Because pool `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` are public, permissionless dispatchables available to any account, and refunds are a routine consequence of weight overestimation in XCM execution, no privileged relayer, validator, or governance action is needed — only ordinary transaction ordering/timing, which is achievable by any actor able to observe pending XCM execution and race transactions within a block or across adjacent blocks.

### Recommendation
Compute a minimum acceptable refund amount before calling the swap-back in `refund_weight` — e.g., quote the current price via `QuotePrice::quote_price_exact_tokens_for_tokens(Target::get(), refund_swap_asset, refund_amount, true)` and pass `Some(quoted_min)` (with a small tolerance) as the `amount_out_min` argument to `swap_exact_tokens_for_tokens`, mirroring the pattern already used in `SwapAssetAdapter::correct_and_deposit_fee`. On swap failure, fall back to retaining the credit in `total_fee` as already implemented in the error branch.

### Proof of Concept
1. Configure a runtime using `SwapFirstAssetTrader` as XCM `Trader` (as in `asset-hub-rococo`/`asset-hub-westend`/`penpal`/staking-async parachain `xcm_config.rs`), with an `AssetConversion` pool between `Target` and a foreign/local asset.
2. Attacker account monitors the mempool/queue for an incoming XCM message that pays fees in the foreign asset with an over-provisioned `payment` amount (common since fee estimation is conservative).
3. Immediately before the message executes, attacker swaps a large amount of `Target` asset into the foreign asset in the same pool (via the public `swap_tokens_for_exact_tokens` dispatchable), skewing the pool reserves so that `Target -> foreign` conversion rate is unfavorable.
4. The XCM message executes; `SwapFirstAssetTrader::buy_weight` withdraws the exact fee in `Target`; unused weight triggers `refund_weight`, which calls `SwapCredit::swap_exact_tokens_for_tokens(vec![Target, foreign], refund, None)` — accepting whatever output the skewed pool gives, which is now far below fair value [1](#0-0) .
5. Attacker immediately reverses the initial swap, restoring the pool and pocketing the spread extracted from the undervalued refund.

Unverified/uncertain: I could not confirm the exact XCM message shapes/callers that most commonly trigger `refund_weight` with a non-trivial `refund_amount`, nor precisely quantify sandwich profitability under typical `LPFee`/pool-depth configurations in the shipped runtimes — a background agent with full repo/test access should validate profitability bounds and confirm there is no compensating check elsewhere (e.g., in `buy_weight`'s slippage-free swap-in) that neutralizes this in practice.
