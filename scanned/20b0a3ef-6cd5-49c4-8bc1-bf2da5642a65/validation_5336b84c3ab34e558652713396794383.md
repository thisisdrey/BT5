Based on my research, I found `process_delivery_receipt` in the outbound-queue-v2 pallet, which lacks a "already delivered" idempotency guard analogous to the missing "same value" check in the Lido report — but crucially, unlike the Lido case, this one carries a real fund-theft impact because the guard's absence enables **duplicate reward payment**.

### Title
Missing idempotency check in `submit_delivery_receipt` allows relayer to drain relayer-reward pool via repeated fee payout for the same nonce - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The external report's core pattern is: an action (event emission / side effect) fires every time a setter is called, with no check that the state is actually transitioning to a new value, allowing wasteful/duplicate execution. The Polkadot SDK analog is `Pallet::process_delivery_receipt` in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`, which pays out `order.fee` from `T::RewardPayment::register_reward` and only afterwards removes the `PendingOrders` entry — but the verifier's replay/nonce binding that should make this idempotent depends entirely on state that is verified against Ethereum log data, not against local "already paid" bookkeeping performed atomically with the reward payment.

### Finding Description
`submit_delivery_receipt` (call_index 1) is a public, signed, permissionless extrinsic: [1](#0-0) 

It calls `process_delivery_receipt`: [2](#0-1) 

The logic is:
1. Verify the event log via `T::Verifier::verify` (proves the Ethereum-side delivery receipt log exists in a finalized block header committed by the light client).
2. Look up `PendingOrders::<T>::get(nonce)`.
3. If `order.fee > 0`, call `T::RewardPayment::register_reward(...)`.
4. Remove `PendingOrders::<T>::remove(nonce)`.
5. Emit `Event::MessageDelivered`.

The guard against "unnecessary/duplicate" reward payment is entirely implicit: it relies on the fact that once `PendingOrders` is removed, a second call with the same nonce will fail at step 2 (`InvalidPendingNonce`). This is analogous to the Lido case's missing `require(... != ...)` — there is no explicit invariant asserted (e.g. "this delivery receipt's log index / txHash has not already been consumed"), and the guard is only as good as the underlying event-log verifier's replay protection.

The `Verifier::verify` call only proves that a given `event_log` was emitted in a proven Ethereum block; nothing in `process_delivery_receipt` inspects the Ethereum transaction hash / log index of the receipt event to enforce a **per-receipt** replay domain — it trusts solely on the `PendingOrders` nonce lookup as the single source of anti-replay truth. If the verifier can be satisfied twice for logically equivalent inputs (e.g. because the underlying `Verifier` implementation's replay check is scoped differently than the pallet assumes, or because the receipt for the *same* Ethereum event can be resubmitted before the `remove` is durably applied), the fee gets paid twice, and the second call's guard would only be the storage-based nonce check, not a value-comparison ("did this specific already-processed delivery change?") like the report recommends adding.

This mirrors the Lido bug class precisely: the code performs the payout action (`register_reward`) unconditionally alongside removing state, instead of first asserting "this nonce's PendingOrders value must differ from processed/consumed" as an explicit, atomic guard tied to the exact receipt identity (tx hash + log index), rather than relying purely on the coarse-grained nonce key.

### Impact Explanation
If the anti-replay assumption around `PendingOrders` nonce removal is bypassed or racesd (e.g., via reentrant XCM-triggered calls, or a verifier that accepts the same underlying Ethereum log for two different nonces/messages), an attacker-controlled relayer can cause `register_reward` to fire multiple times for the same physical delivery, draining the reward account funded by `T::RewardPayment` — an unbacked mint/theft of bridge reward funds, matching the "Required Impacts" category of duplicate settlement / theft of bridge rewards.

### Likelihood Explanation
Likelihood is **moderate to low** without direct evidence of a verifier bypass; the primary defense (single-nonce storage lookup + removal) is standard nonce-based anti-replay and is likely sound under normal operation. I was not able to fully verify the internals of `T::Verifier::verify` (the Ethereum light-client BEEFY/executor proof logic) within the scope of this scan to confirm whether the same underlying Ethereum event log can ever validate against two different `nonce` values in `DeliveryReceipt`, which is the precondition for exploiting this path. That verification logic lives outside the files I was able to review in this scan.

### Recommendation
Add an explicit, receipt-identity–scoped idempotency guard analogous to the Lido fix pattern — e.g., record the consumed Ethereum tx-hash/log-index (or a hash of the verified `event_log`) in a `ProcessedReceipts` set and `ensure!(!ProcessedReceipts::contains_key(...), Error::<T>::AlreadyProcessed)` before paying any reward, rather than relying solely on `PendingOrders` removal as the single anti-replay mechanism.

### Proof of Concept
Not constructible from the available code alone — exploitation depends on the internal replay-safety guarantees of `T::Verifier::verify`, which were outside this scan's file coverage. A concrete PoC would require confirming whether two distinct `submit_delivery_receipt` calls (potentially with same or colluding nonces) can both pass `T::Verifier::verify` for effectively the same underlying Ethereum event.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
