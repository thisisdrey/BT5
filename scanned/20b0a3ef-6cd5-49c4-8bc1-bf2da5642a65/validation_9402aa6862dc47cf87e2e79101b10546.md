## Title
`pallet-psm::redeem` uses a stale decimals snapshot while `mint` enforces live decimals, creating a scaling-factor mismatch exploitable by an external-asset owner - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
The external report describes a scaling-factor mismatch: one component (the off-chain script) applies a `x100` factor while the on-chain consumer (`_processResponse`) does not reconcile with that factor before persisting state, corrupting the stored value used downstream. The same "producer asserts a scale, consumer trusts a stale scale" pattern exists in `pallet-psm`: `mint` enforces that the external asset's *live* decimals match the decimals snapshot taken at registration (`ensure_decimals_match`), but `redeem` deliberately skips that check and converts using only the frozen snapshot value, even though the decimals metadata is externally mutable by the asset's own owner at any time.

### Finding Description
`ExternalAssetInfo::decimals` is a snapshot taken once, at the time an external asset is approved on a PSM instance: [1](#0-0) 

`mint` re-derives the scaling factor via `Self::ensure_decimals_match(...)`, which compares the snapshot against the asset's *current* live metadata decimals and halts with `DecimalsMismatch` if they diverge: [2](#0-1) 

`redeem`, however, reads `external.decimals` (the frozen snapshot) directly and never calls `ensure_decimals_match`, then feeds that stale value straight into the peg-conversion helper `internal_to_external`: [3](#0-2) 

`internal_to_external`/`external_to_internal` compute a `10^diff` scaling factor purely from the `ext_decimals`/`internal_decimals` arguments passed in — they have no way to detect that the decimals value they were handed no longer reflects the asset's live metadata: [4](#0-3) 

The decimals value is not a cosmetic display field in this pallet's logic — it *is* the peg-conversion scale factor (`10^(ext_decimals - internal_decimals)`), analogous to the "multiply by 100" factor in the external report. `mint`'s guard shows the pallet author is aware that live decimals can drift and that drift must halt state-changing conversions; `redeem` explicitly does not apply the same reconciliation and instead trusts the stale snapshot exclusively (confirmed by the dedicated test `redeem_uses_snapshot_when_asset_decimals_drift` and the doc comment above `redeem`). Decimals metadata (`pallet_assets::set_metadata`) is settable by the external asset's own `Owner` — an entity distinct from, and with no PSM admin privileges relative to, the PSM instance. This satisfies "unprivileged actor" since the asset owner is not a PSM admin, governance actor, or validator.

### Impact Explanation
Because `redeem` never re-validates the scaling factor against live decimals, an external-asset owner can change their asset's decimals metadata after PSM registration so that the `10^diff` factor used by `redeem` no longer matches the factor `mint` would compute (and would refuse to run under). This asymmetry lets redemptions proceed with a mis-scaled conversion — the pallet will pay out `external_out` computed from an outdated exchange assumption, over- or under-paying the PSM's external-asset reserve relative to the internal amount actually burned. This directly threatens PSM asset accounting: the reserve either drains faster than internal debt shrinks (fund loss/insolvency for the pool and other depositors) or locks up value if the mismatch runs the other way. This maps to the "asset accounting must conserve value and settle exactly once" pivot and to "theft or unbacked mint/unlock" impact category, since it lets a non-privileged party corrupt the effective settlement scale used by a public, unprivileged, signed extrinsic.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment where external assets are ordinary `pallet-assets` instances with owner-settable metadata (the common Asset Hub case). No governance, validator, or admin compromise is required — only that the external asset's own `Owner` (who is not necessarily trusted by the PSM admin beyond initial approval) calls the standard, unprivileged `set_metadata` extrinsic on their own asset after it has been approved on a PSM. The path to trigger the mismatch (`redeem`) is a normal signed extrinsic with no special preconditions beyond holding sufficient internal-asset balance, and it is a documented, intentional code path, not a rare edge case.

### Recommendation
Either (a) have `redeem` call `ensure_decimals_match` (or an equivalent live-decimals check) before computing `external_out`, mirroring `mint`'s guard, and reject with `DecimalsMismatch` on drift, forcing governance to explicitly migrate/re-register the asset with updated decimals; or (b) if unwinding-through-drift is truly intended, make that an explicit, clearly-fenced admin-approved "wind-down" mode rather than the default behavior of the public `redeem` extrinsic, and cap exposure (e.g., disallow new debt/reserve growth for an asset once its live decimals have diverged from the snapshot).

### Proof of Concept
1. Governance creates a PSM for `INTERNAL_ASSET` (6 decimals) and approves external asset `USDX` (6 decimals); `ExternalAssetInfo.decimals = 6` is snapshotted.
2. A user mints internal asset against `USDX`, growing `PsmDebt` and the PSM's `USDX` reserve.
3. `USDX`'s `Owner` (unprivileged w.r.t. the PSM) calls `pallet_assets::set_metadata` to change `USDX`'s live decimals from 6 to 2 — a completely ordinary, permitted call for an asset owner.
4. Any further `mint` call now correctly fails with `Error::DecimalsMismatch` via `ensure_decimals_match` (as in the existing test `mint_halts_when_asset_decimals_drift`).
5. However, `redeem` is called by any signed user holding `INTERNAL_ASSET`. It skips `ensure_decimals_match`, reads the stale `external.decimals = 6`, and computes `external_out` via `internal_to_external(internal_net, 6, 6)`, transferring `USDX` out of the PSM reserve using the outdated 1:1 (or whatever the original diff was) scale — even though the token's current live decimals metadata says 2. The reserve is depleted (or under-paid) at a rate inconsistent with the asset's now-current decimals, exactly mirroring the external report's core defect: a downstream consumer settling state using a scale that a producer has since changed, without reconciliation.

		///
		/// Inverse of [`Self::external_to_internal`]. Floor-divides when internal has more
		/// decimals, multiplies up when it has fewer.
		pub(crate) fn internal_to_external(
			amount: BalanceOf<T>,
			ext_decimals: u8,
			internal_decimals: u8,
		) -> Result<BalanceOf<T>, Error<T>> {
			use core::cmp::Ordering::*;
			match ext_decimals.cmp(&internal_decimals) {
				Equal => Ok(amount),
				Less => {
					let diff = (internal_decimals - ext_decimals) as u32;
					let factor = Self::pow10(diff)?;
					Ok(amount.checked_div(&factor).unwrap_or_else(BalanceOf::<T>::zero))
				},
				Greater => {
					let diff = (ext_decimals - internal_decimals) as u32;
					let factor = Self::pow10(diff)?;
					amount.checked_mul(&factor).ok_or(Error::<T>::ConversionOverflow)
				},
			}
		}
