# [M] WTDU-2 | Swap Required To Specify Output Amount

## Summary
Severity: Medium

## Details
The vulnerability is a logical flaw in the liquidity provision flow where the contract offers a minOutputAmount parameter but forces the execution of a token swap before the minimum‑output check is applied. Because the swap is performed unconditionally, the contract never validates that the amount of tokens returned to the liquidity provider meets the user‑specified minimum. This results in a situation where a liquidity provider who expects at least a certain amount of output tokens can receive less, or even zero, without any revert or warning. The root cause is an incorrect ordering of operations: the code path that should enforce the minimum output constraint is placed after the swap, or is omitted entirely for pure liquidity provision calls. An attacker does not need to craft a malicious transaction; any honest user adding liquidity will be exposed to the same risk simply by invoking the function with a minOutputAmount value. The impact is economic: users may lose value because the protocol does not honor their protection against slippage, leading to unexpected shortfalls in received LP tokens or underlying assets. This condition occurs whenever a liquidity provider attempts to add liquidity using the minOutputAmount field, which is currently only functional when a swap is also executed. The affected parties are liquidity providers and, indirectly, the protocol’s overall health because inaccurate accounting can erode trust. The issue was discovered during a manual audit that compared the intended behavior of the minOutputAmount guard with its actual implementation and noted that the guard never triggers unless a swap is performed. It can be hard to notice because the UI may still display the user‑specified minimum, giving the impression that the contract will enforce it, while the on‑chain execution silently ignores it. To remediate, the contract should decouple the minimum‑output validation from the swap logic, allowing the provider to specify a minimum amount that is checked before any state changes, or provide a separate function that enforces the constraint without requiring a swap. In generic terms, this is an instance of improper validation of user‑provided constraints, a class of bugs where business‑logic checks are placed after state‑changing operations, breaking accounting assumptions and leading to unexpected loss of funds. From the user’s perspective the symptom is a mismatch between the expected output shown in the UI and the actual amount received – for example, a user expects a refund of 100 tokens but receives only 70, or sees their balance drop unexpectedly after adding liquidity.

## Recommendation
Consider adding the functionality to specify the minimum output amounts without swapping.
