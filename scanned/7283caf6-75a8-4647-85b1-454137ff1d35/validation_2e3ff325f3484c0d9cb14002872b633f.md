## Title
Transaction fees paid via `pallet-asset-conversion-tx-payment` are priced from manipulable spot AMM reserves, allowing self-dealing traders to pay near-zero real value for block weight — (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

## Summary
The external report's broken invariant is: a value transfer (IL compensation) is computed from **instantaneous, attacker-controlled pool reserves** with no manipulation-resistant oracle, letting an LP who is also the price-manipulator extract value that should reflect a fair market price. The same primitive — pricing a privileged action off spot AMM reserves with no TWAP/oracle and no slippage bound enforced by the caller — exists in `pallet-asset-conversion-tx-payment`'s `SwapAssetAdapter::withdraw_fee`, which decides how much of a user-chosen asset is swapped to cover the native transaction fee.

## Finding Description
`SwapAssetAdapter::withdraw_fee` in [1](#0-0)  quotes the amount of the payer's chosen asset needed to fund the fixed native fee via `S::quote_price_tokens_for_exact_tokens`, which is a thin wrapper over `pallet_asset_conversion::Pallet::get_reserves` — the pool's raw, current balances, with no time-weighting: [2](#0-1) 

The `ChargeAssetTxPayment` extension struct only carries `tip` and `asset_id` — no caller-supplied maximum asset amount / slippage bound: [3](#0-2) 

Because the extension's `withdraw_fee` performs a *real* `swap_tokens_for_exact_tokens` against the live pool (not merely an estimate), a signer who also controls the pool reserves at that instant can shape the exchange rate in their own favor before the fee-charging transaction executes: skew the pool so that a large amount of asset is cheap relative to the native token, pay the transaction fee (a fixed, exact native amount) while surrendering only a token amount of the asset, then restore the pool ratio. The net native fee delivered to the treasury/block author is always correct (`fee` is the exact-output leg), but the *real economic value* the payer surrenders for consuming block weight can be driven arbitrarily close to zero, at the expense of the pool's other liquidity providers whose reserves absorb the swap.

This mirrors the VADER root cause exactly: a payout/charge is derived from **spot** AMM state that the beneficiary can unilaterally distort immediately before the state is read, with no oracle smoothing and no protecting bound from the pricing consumer (`ChargeAssetTxPayment`).

## Impact Explanation
This falls under the explicitly in-scope category "public underpriced work that degrades block production": an unprivileged, ordinary signed account can consume chain weight/blockspace while paying a fee whose true economic cost is manipulated toward zero, at LPs' expense, using only their own capital and ordinary extrinsics (no validator/collator/relayer/admin role required). At scale this both degrades the economic security assumption of weight-fee pricing and drains value from a public liquidity pool used to price fees for the whole chain.

## Likelihood Explanation
The attack requires no special role — any account with enough capital to temporarily move the fee-conversion pool's reserves (asset ↔ native token pool used for `ChargeAssetTxPayment`) can execute it entirely with their own transactions within the same block, since `withdraw_fee` reads reserves synchronously at `prepare()` time and there is no TWAP delay. The only cost is the AMM's built-in LP swap fee (`pool_fee_for`) on the round-trip, which is bounded and can be economically justified when block-weight value transferred exceeds it (e.g. bulk low-fee spam, or high-value calls paid with an artificially discounted asset).

## Recommendation
- Require `ChargeAssetTxPayment`/`SwapAssetAdapter` to accept and enforce a caller-supplied maximum asset amount (slippage bound) for the fee-swap, similar to `amount_in_max` in ordinary swaps.
- Price the fee-conversion swap off a manipulation-resistant reference (e.g., a short TWAP over `pallet_asset_conversion` reserves, or an external oracle asset-rate) rather than the raw spot `get_reserves()` result.
- Alternatively, cap per-block or per-account fee-asset swap volume against a given pool to bound single-block reserve distortion.

## Proof of Concept
1. Attacker holds a large balance of `asset_id` and enough native currency/asset to move the `(asset_id, Native)` pool used by `ChargeAssetTxPayment`.
2. In block N, attacker (tx #1) performs `AssetConversion::swap_exact_tokens_for_tokens` dumping a large amount of native into the pool, driving `balance1` (asset reserve) low relative to `balance2` (native reserve) — i.e. making `asset_id` "expensive" is the wrong direction; concretely the attacker skews reserves so that `get_amount_in` (used by `quote_price_tokens_for_exact_tokens`, see [4](#0-3) ) returns a minimal `asset_fee` for the fixed native `fee` needed by their next transaction.
3. Same block, tx #2: attacker submits a normal signed extrinsic with `ChargeAssetTxPayment::from(tip, Some(asset_id))`. `withdraw_fee` quotes and withdraws only the minimal `asset_fee` computed against the skewed reserves ( [5](#0-4) ), and the exact-output swap executes at that distorted rate.
4. Same block, tx #3: attacker swaps back to restore the pool to near its original ratio, absorbing only the AMM's built-in LP fee as cost.
5. Result: attacker's transaction fee is settled correctly in native terms to the fee recipient, but the attacker paid a negligible amount of real asset value, with the shortfall extracted from the pool's other liquidity providers — reproducing the VADER-style "manipulate reserves immediately before a reserve-priced settlement, then unwind" pattern in a live, in-scope Polkadot SDK pallet.

		pub fn quote_price_tokens_for_exact_tokens(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount: T::Balance,
			include_fee: bool,
		) -> Option<T::Balance> {
			// Swaps reject zero amounts, match that behavior.
			if amount.is_zero() {
				return None;
			}
			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2).ok()?;

			let (balance1, balance2) = Self::get_reserves(asset1.clone(), asset2.clone()).ok()?;

			if balance1.is_zero() {
				return None;
			}

			// Swap withdrawals from pools use `keep_alive=true` (Preserve). Use the same
			// preservation level to determine the actual withdrawable amount.
			let max_output =
				T::Assets::reducible_balance(asset2.clone(), &pool_account, Preserve, Polite);
			if amount > max_output {
				return None;
			}

			if include_fee {
				let fee = Self::pool_fee_for(&asset1, &asset2).ok()?;
				Self::get_amount_in(fee, &amount, &balance1, &balance2).ok()
			} else {
				Self::quote(&amount, &balance2, &balance1).ok()
			}
		}
