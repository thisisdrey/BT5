### Title
`submit_delivery_receipt` pays relayer reward and permanently clears `PendingOrder` regardless of the on-chain `success` flag - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
`DeliveryReceipt` decoded from the Ethereum `InboundMessageDispatched` event log carries a `success: bool` field indicating whether the corresponding outbound message actually executed successfully on the Gateway contract. `Pallet::process_delivery_receipt` never inspects this field: it pays the relayer reward whenever `order.fee > 0` and unconditionally removes the `PendingOrder`, treating failed and successful deliveries identically. This mirrors the external report's core flaw — a value produced by an external/relay process is trusted and used to finalize on-chain accounting without validating that it actually represents the intended successful outcome.

### Finding Description
`DeliveryReceipt` is defined with a `success` field decoded straight from the Ethereum event log: [1](#0-0) 

The public, unprivileged extrinsic `submit_delivery_receipt` verifies the Merkle/beacon proof of the log, decodes it into a `DeliveryReceipt`, and forwards it to `process_delivery_receipt`: [2](#0-1) 

`process_delivery_receipt` then pays the reward and clears the pending order based solely on `order.fee > 0`, never checking `receipt.success`: [3](#0-2) 

A grep across the crate confirms `receipt.success` is decoded but never read anywhere except its own struct definition, i.e. it is dead data with respect to reward/settlement logic. The proof verification (`T::Verifier::verify`) only attests that the log was genuinely emitted on Ethereum — it says nothing about whether the *message itself* executed successfully; `success=false` is a perfectly legitimate, verifiable outcome (e.g., the Gateway's command execution reverted due to insufficient gas, a malformed command, or any dispatch failure on the Ethereum side). Any relayer who submits such a legitimately-proved-but-failed receipt still collects the fee and the order is deleted forever, with no retry path.

### Impact Explanation
This breaks the invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." Concretely:
- Relayers are rewarded for messages that failed to execute on Ethereum, i.e. underpriced/incorrect payout for non-work — a duplicate/incorrect settlement of value that should not have been paid.
- The `PendingOrder` is irrevocably removed on any receipt regardless of `success`, so a failed message can never be retried or reconciled — a permanent bridge-state loss for the message's intended effect, even though the fee funds have already been spent on a "reward" for a failed delivery.

### Likelihood Explanation
No privileged actor is required. Any account can call `submit_delivery_receipt`; the attacker only needs a real Ethereum transaction receipt/log proving `InboundMessageDispatched` with `success=false` — a normal execution outcome that can occur naturally (e.g., insufficient gas limit encoded in the command, or a command that reverts), and can plausibly be engineered by controlling gas/command parameters on the Ethereum side of a message the attacker sent. No proof forgery, governance, or key compromise is needed.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` when `success` is `true`. For `success == false`, either keep the order available for a resubmission/retry mechanism, route it to a distinct failure-handling path (e.g. refund the fee to the original sender, emit a `MessageDeliveryFailed` event), or otherwise ensure the reward and order-removal path can't be exercised for a receipt that itself reports failure.

### Proof of Concept
1. Relayer sends a message through the outbound queue and it is committed with a `PendingOrder{ nonce, fee }`.
2. On Ethereum, the Gateway processes the message but the command execution fails/reverts, so `InboundMessageDispatched(nonce, topic, success=false, reward_address)` is emitted (a legitimate, provable event).
3. Relayer calls `submit_delivery_receipt` with a valid Merkle/beacon proof of this event.
4. `T::Verifier::verify` succeeds (the log is genuine); `DeliveryReceipt::try_from` decodes `success=false` correctly.
5. `process_delivery_receipt` checks only `order.fee > 0`, registers the reward for the relayer, and removes `PendingOrder` — identical behavior to the `success=true` case demonstrated in the repo's own test `submit_delivery_receipt_succeeds_after_unhalt`, which never varies or asserts on the `success` field: [4](#0-3)

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

#[test]
fn submit_delivery_receipt_succeeds_after_unhalt() {
	new_tester().execute_with(|| {
		let nonce = 0;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_valid_event_proof());

		// Bridge halted — receipt rejected, order untouched.
		set_verifier_halted(true);
		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);
		assert!(PendingOrders::<Test>::get(nonce).is_some());

		// Bridge resumed — same receipt succeeds and the order is settled.
		set_verifier_halted(false);
		assert_ok!(OutboundQueue::submit_delivery_receipt(origin, event));
		assert!(PendingOrders::<Test>::get(nonce).is_none());

		System::assert_has_event(mock::RuntimeEvent::OutboundQueue(Event::MessageDelivered {
			nonce,
		}));
	});
