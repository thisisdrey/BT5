Target: `Nep171TokenId::from_str` (crates/primitives/token-id/src/nep171.rs, `nft_token_id: TokenId` alias to `String`) versus `Nep245TokenId::from_str`. Attacker action: deploys an NFT contract and mints a token with `token_id = "x"`, then separately deploys an MT contract at the same account name pattern producing `Nep245TokenId{contract_id, mt_token_id:"x"}`. Preconditions: attacker controls both contract deployments and the token ids minted on them. Call sequence: `nft_on_transfer` -> `TokenId::Nep171(...)`; `mt_on_transfer` -> `TokenId::Nep245(...)`; both feed `deposit` keyed on `token_id.to_string()`. Binding: `TokenId::Nep171(Nep171TokenId{contract_id, nft_token_id:"x"}).to_string() == TokenId::Nep245(Nep245TokenId{contract_id, mt_token_id:"x"}).to_string()` must be false for all `contract_id`, since the `TokenIdType` (`nep171` vs `nep245`) prefix differs. Impact: Critical - if it were true, an attacker could deposit a cheap MT unit to credit an NFT-keyed balance. Proof idea: cargo test enumerating `TokenIdType::Nep171` and `TokenIdType::Nep245` variants sharing identical `(contract_id, token_id)` fields and asserting their `Display` strings never coincide (IDENTITY).
