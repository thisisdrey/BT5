Target: `ImtTokenId::from_str` (crates/primitives/token-id/src/imt.rs) where `minter_id: AccountId` and `token_id: String` are joined by `:` with no escaping of `:` inside `token_id`. Attacker action: signs an `ImtMint` intent (or crafts a deposit) where `token_id = "a:b"` under `minter_id = "m.near"`, producing `Display` = `"m.near:a:b"`; separately crafts `minter_id = "m.near:a"` which is rejected by `AccountId` parsing but probe whether any valid `AccountId` variant (e.g. differing normalization) can produce the same string. Preconditions: attacker is the signer of their own `ImtMint` intent for a token they mint. Call sequence: `ImtTokenId::new` -> stored in `token_balances` -> later `ImtTokenId::from_str` in a withdraw/resolve path. Binding: `ImtTokenId::from_str(&t.to_string()) == t` for every `t` with colon-bearing `token_id`. Impact: Critical - a minted worthless IMT token whose id collides with another IMT key would let the attacker credit/drain a balance under a different `(minter_id, token_id)`. Proof idea: cargo test with `#[from(make_arbitrary)] token_id: ImtTokenId` extended to force `token_id` fields containing `:` and assert round-trip equality (IDENTITY).
