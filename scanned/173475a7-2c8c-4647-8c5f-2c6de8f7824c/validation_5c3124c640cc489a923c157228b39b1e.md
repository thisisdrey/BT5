This confirms the analog: `do_mint` checks only `Item::<T, I>::contains_key` (line 55) to allow reuse of `item` ids after burn — it does not consult the `Attribute` storage map at all, and `item` is caller-supplied (not an auto-incrementing nonce), so an item id can legitimately be reused for a brand-new item once the old one is burned.

### Title
Stale `CollectionOwner`/`ItemOwner` NFT attributes survive `burn` and are inherited by a re-minted item with the same ID - (File: `substrate/frame/nfts/src/features/create_delete_item.rs`)

### Summary
`pallet-nfts::do_burn` deletes `Item`, `Account`, `ItemPriceOf`, `PendingSwapOf`, `ItemAttributesApprovalsOf`, and (conditionally) `ItemConfigOf` for a burned item, but never clears the `Attribute` storage map entries keyed by `(collection, Some(item), namespace, key)`. Because item IDs are caller-chosen values (not a monotonic nonce) and `do_mint` only guards against re-use via `Item::<T,I>::contains_key` [1](#0-0) , an item id freed by `burn` can immediately be re-minted (even by force_mint to a different owner), and the new item silently inherits every attribute still stored for the old item under the same `(collection, item)` key.

### Finding Description
`do_burn` removes the item's core records but leaves `Attribute` entries untouched: [2](#0-1) . The pallet's own test suite documents this as intended lazy-deletion behavior — attributes are shown to persist across `burn` until an explicit `clear_attribute` call is made [3](#0-2) . The `do_clear_attribute` code path even has a comment acknowledging that item config (and by extension identity) may already be gone by the time an attribute is cleared: "if the item was previously burned, the ItemConfigOf record might not exist... we allow to clear the attribute" [4](#0-3) .

Meanwhile, `do_mint` only checks `Item::<T,I>::contains_key(collection, item)` to reject collisions [1](#0-0) ; it performs no check against, and no clearing of, the `Attribute` map. `Attribute` entries are keyed purely by `(collection, maybe_item, namespace, key)` with no generation/nonce component (confirmed by `do_clear_attribute`'s key tuple) [5](#0-4) , so any stale `CollectionOwner` (admin-set, e.g. compliance/whitelist/KYC-style flags) or `ItemOwner` attribute from the burned item is immediately visible and attributed to the newly minted item at the same id.

This is the direct structural analog of the reported bug: `remove_investor` deletes the main record but leaves `attributes` keyed by the same id, so a newly registered entity with the reused id inherits the old entity's privileges. Here, `burn` deletes the item record but leaves `Attribute` keyed by the same `(collection, item)`, so a newly minted item at the reused id inherits the old item's attributes.

### Impact Explanation
If any downstream logic (marketplace, compliance pallet, cross-chain XCM asset-transfer eligibility check, or a custom runtime gating on `CollectionOwner`/`Account` namespace attributes such as "verified", "whitelisted", or transfer-permission flags) trusts `pallet-nfts::Attribute` state as authoritative for the *current* item, a completely unrelated new owner of the re-minted item id gets those privileges/flags without ever being vetted by the collection admin — this is an unauthorized-privilege/state-integrity issue consistent with the "runtime bugs that compromise intended behavior" and "unauthorized execution or origin escalation" impact classes.

### Likelihood Explanation
Any signed account that owns an item can call permissionless `burn` (or the collection admin/root can), and immediately re-mint (via `mint`/`force_mint`) at the same item id — there is no cooldown, no attribute-clearing enforcement, and no id-reuse restriction beyond `AlreadyExists`, which is satisfied once `Item` is removed. This requires no privileged, governance, or malicious-peer assumption — it's reachable purely through the two public extrinsics `burn` and `mint`/`force_mint`.

### Recommendation
In `do_burn`, iterate and remove all `Attribute` entries scoped to the burned item (`Attribute::<T, I>::clear_prefix` keyed by `(collection, Some(item))`, refunding any outstanding deposits) before dropping `Item`, mirroring how `ItemConfigOf`/`ItemMetadataOf` are already cleared/refunded during burn. Alternatively, gate `do_mint` to check for and reject/require-clearing of any surviving `Attribute` entries at the given `(collection, item)` id before allowing re-mint.

### Proof of Concept
1. Collection admin mints item `(collection=0, item=42)` to Alice and sets a `CollectionOwner` attribute e.g. `key="kyc", value="verified"`.
2. Alice calls `burn(0, 42)` — `Item`, `Account`, etc. are removed, but `Attribute::<T,I>::get((0, Some(42), CollectionOwner, "kyc"))` still returns `"verified"` [2](#0-1) .
3. Any account (e.g. via `force_mint` by admin, or by anyone if minting is public) mints a brand-new, unrelated item at `(0, 42)` to Bob — `do_mint`'s only guard is `Item::contains_key`, which now passes [1](#0-0) .
4. A downstream consumer reading `Attribute::<T,I>::get((0, Some(42), CollectionOwner, "kyc"))` still observes `"verified"`, now incorrectly bound to Bob's new item, without any admin action re-approving it — reproducing the exact "stale attribute reused with a new id" pattern from the reported bug.
