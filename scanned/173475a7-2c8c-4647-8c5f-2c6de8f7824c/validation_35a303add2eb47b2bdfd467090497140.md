### Title
Unvalidated `ContractCall.value` in Snowbridge V2 XCM-to-Ethereum converter allows draining agent's Ether reserves - (File: `bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs`)

### Summary
The Snowbridge outbound V2 `XcmConverter::convert()` decodes a user-supplied `Transact` payload (`ContractCall::V1 { value, .. }`) and forwards `value` unchecked into `Command::CallContract`, without validating it against the amount of Ether/ENA actually reserved and transferred earlier in the same XCM program (`WithdrawAsset`/`enas`). This is structurally the same class of bug as the `DelegationMetaSwapAdapter` report: two independently-attacker-supplied fields (the "authorized/transferred amount" vs. the "amount used at execution") are never cross-checked, letting the value used at execution exceed what was actually reserved/authorized.

### Finding Description
`XcmConverter::convert()` parses an XCM program in a fixed grammar: `WithdrawAsset` (ENA reserve), optional `ReserveAssetDeposited` (PNA), `AliasOrigin`, `DepositAsset`, and an optional `Transact`. The ENA amount reserved via `WithdrawAsset` is turned into `Command::UnlockNativeToken { amount, .. }` [3](#0-2)  completely independently from the `Transact` block, where the `ContractCall::V1.value` field — fully attacker-controlled since it is embedded in an arbitrary XCM the caller submits via `pallet_xcm::execute`/`send` — is decoded and pushed straight into `Command::CallContract { value, .. }` with zero cross-check against the ENA amount withdrawn/reserved earlier: [2](#0-1) .

The presence of the dedicated error variant `CallContractValueInsufficient` in `XcmConverterError` [1](#0-0)  shows the check was intended but is dead code — it is declared but never returned anywhere in the file. Confirming this intent, the integration test at `cumulus/parachains/integration-tests/emulated/tests/bridges/bridge-hub-westend/src/tests/snowbridge_v2_outbound.rs` explicitly comments: "value should be less than the transfer amount, require validation on BH Exporter" [4](#0-3)  — yet the code path being tested never enforces it.

On Ethereum, `Command::CallContract`'s `value` is understood to be Ether that the calling agent contract forwards to the target — i.e. it is meant to be backed by ENA that was actually locked/reserved via the corresponding `UnlockNativeToken`/deposit flow in the same message. Because `convert()` never asserts `value <= (sum of unlocked ENA amounts)`, a caller can construct an XCM that withdraws/reserves a tiny amount of ENA (or none at all, since ENA/PNA extraction is entirely optional — only `commands.len() > 0` is required, and `Transact` alone satisfies that) while declaring an arbitrary, much larger `value` in the `ContractCall`. This resulting `Message` is then queued and committed to Ethereum via the Gateway contract, instructing the corresponding on-chain agent to forward `value` Ether to an arbitrary target — an amount the origin was never authorized to move on this chain side, up to depleting whatever Ether the agent holds.

### Impact Explanation
This directly matches the "theft or unbacked mint/unlock" and "false state acceptance" impact classes: the amount committed for the Ethereum-side `CallContract` command is not backed by, or bound to, the actual asset amount reserved in the same message. An unprivileged, signed XCM-executing account (any account able to call `pallet_xcm::execute`/`send` targeting the Ethereum bridge) can cause the BridgeHub to commit outbound Ethereum instructions that authorize forwarding of Ether from the agent contract far beyond what was actually reserved on the Substrate side, draining agent-held Ether reserves on Ethereum.

### Likelihood Explanation
High likelihood for a public-entrypoint bug: no admin, governance, relayer, or validator collusion is required. Any account with the ability to submit an XCM via `pallet_xcm` (as demonstrated by the very similarly-shaped `transact_with_agent_from_asset_hub` and `exploit_v2_route_with_legacy_v1_transfer_will_fail` tests in the same test suite, which already show attackers manipulating the `Transact`/`ContractCall`/`AliasOrigin` structure) can freely construct the `value` field independent of the reserved ENA amount. The converter's parsing logic imposes no linkage between the two.

### Recommendation
In `XcmConverter::convert()`, after collecting the ENA transfer commands and before/while building the `Command::CallContract`, sum the ENA amounts unlocked to the agent's beneficiary/recipient in this message and assert `value <= total_ena_unlocked_amount`, returning `XcmConverterError::CallContractValueInsufficient` (the already-defined but unused variant) when this invariant is violated. Alternatively, derive `value` deterministically from the reserved ENA amount rather than trusting an independently supplied field in `ContractCall`.

### Proof of Concept
1. Attacker (any signed account) submits an XCM via `pallet_xcm::execute` targeting the Ethereum bridge, structured per the V2 converter grammar:
   - `WithdrawAsset` reserving a negligible or zero amount of Ether/ENA.
   - `PayFees` with minimal fee.
   - `AliasOrigin` set to attacker's own controlled/allowed origin (passes the `AllowedAliasOrigin` filter for a legitimate agent).
   - `DepositAsset` beneficiary set to attacker-controlled address.
   - `Transact` carrying an ABI-encoded `ContractCall::V1 { target: <attacker_target>, calldata: [], gas: <g>, value: <large_value> }`.
   - `SetTopic`.
2. `XcmConverter::convert()` accepts this because: ENA extraction only requires `amount > 0` [5](#0-4)  (satisfied trivially with amount=1), and the `Transact`/`CallContract` path never checks `value` against anything [2](#0-1) .
3. The resulting `Message` with `Command::CallContract { value: <large_value>, .. }` is queued to `EthereumOutboundQueueV2` and committed to the Merkle tree for relay to the Gateway contract.
4. On Ethereum, the Gateway instructs the agent contract to forward `value` Ether to `target`, draining the agent's Ether balance by far more than was ever reserved/authorized on the Substrate side.

Note: full confirmation of exploitability requires checking the Solidity Gateway/agent contract's handling of `CallContract.value` (outside this repo's Rust code, in the Snowfork contracts), which is not indexed here; the vulnerability described is specifically the missing cross-check within `polkadot-sdk`'s Rust converter that was evidently intended (per the dead error variant and the test comment) but never implemented.
