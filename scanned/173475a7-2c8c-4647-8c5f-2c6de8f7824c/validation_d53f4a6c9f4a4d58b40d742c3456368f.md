## Analysis

The external report's core broken invariant: **a value asserted by the caller (`mintFee`) is trusted and consumed by downstream logic without validating that it was actually backed by the funds/state that were supposed to secure it, and a privileged actor's actual data disagrees with what's later paid out — enabling loss of funds via an unvalidated fee amount.**

The closest local analog is in Snowbridge's V2 outbound queue, where the `fee` field carried inside a `Message` is trusted verbatim and later paid out to a relayer as a reward, with no on-chain check — at the point the message is accepted into the queue — that this `fee` corresponds to any amount actually reserved/collected. [1](#0-0) 

Compare this to the v1 pallet, which computes the fee itself from `PricingParameters` and gas metering via `calculate_fee` before a message is queued: [2](#0-1) 

In v2, `validate()` only checks payload size and clones the caller-supplied `Message` (which includes `fee`) as the ticket — it performs no fee computation or validation at all: [1](#0-0) 

That same untouched `fee` is then persisted into `PendingOrders` when the message is processed: [3](#0-2) 

Once a relayer submits a valid `submit_delivery_receipt` (which only requires a genuine delivery-receipt proof from Ethereum — an action any relayer, including the message's own author, can trigger), the pallet unconditionally registers a reward equal to the order's `fee`, with no check that this amount was ever actually collected from anyone: [4](#0-3) 

### Title
Outbound Queue V2 trusts caller-supplied `Message.fee` without validating it against real collected value before registering relayer rewards - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/send_message_impl.rs`, `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`SendMessage::validate` for outbound-queue-v2 only checks payload size and forwards the message unchanged; it never recomputes or verifies the `fee` field against an actual amount reserved from the sender. That unvalidated `fee` is stored verbatim in `PendingOrders` at `do_process_message`, and is paid out in full to whichever account submits a matching delivery receipt in `process_delivery_receipt`/`RewardPayment::register_reward`, with no cross-check against value actually escrowed at send time.

### Finding Description
This mirrors the `PhiFactory:claim` root cause: a numeric fee value is propagated through an execution pipeline and consumed/paid at the end without validating it corresponds to funds that were actually collected earlier. In `PhiFactory`, `mintFee` computed at claim time could diverge from what the user actually sent (`msg.value`), and the contract's own balance silently absorbed the difference or was drained. In outbound-queue-v2, the pipeline is: `SendMessage::validate` (no fee check) → `do_process_message` (persists `fee` from the decoded message directly into `PendingOrder`) → `process_delivery_receipt` (pays exactly `order.fee` to the relayer via `T::RewardPayment::register_reward`). Nowhere in this path does the pallet withdraw, hold, or otherwise verify that `fee` matches value actually collected from the message's origin (e.g., via XCM `PayFees`/`remote_fees` upstream). If the upstream caller (an XCM-originated message from any sibling parachain/account, not requiring any privileged role) can influence or set an inflated `fee` value in the `Message` it hands to this pallet's `SendMessage::validate`, that inflated value becomes an unconditionally paid reward once the message is delivered to Ethereum and a receipt is proven back — a path reachable by an ordinary, unprivileged relayer/user, not a malicious validator/collator/governance actor.

### Impact Explanation
If the `fee` value is not strictly bound to value that was actually escrowed/collected for that specific message at submission time, an attacker can cause `T::RewardPayment::register_reward` to credit relayer rewards unbacked by real funds — an unbacked mint/payout from whatever pot funds `RewardLedger`, directly matching the "theft or unbacked mint" and "duplicate settlement or payout" categories in the impact gate. This does not require a malicious relayer, validator, or governance actor — only an unprivileged party able to originate a Snowbridge V2 outbound message with a manipulated `fee` field and later obtain (or self-submit) a valid delivery receipt.

### Likelihood Explanation
Likelihood depends on whether any upstream component (the exporter/system pallet building the `Message` from an incoming XCM) enforces that `fee` cannot exceed value actually withdrawn from the origin before calling `SendMessage::validate`/`deliver` on this pallet — that check, if it exists, lives outside the files reviewed here. Within the outbound-queue-v2 pallet itself, no such invariant is enforced, so the pallet's own guarantees do not prevent this on their own; the overall exploitability therefore hinges on a boundary this analysis could not fully trace with the tools available.

### Recommendation
Have `do_process_message` (or the upstream message constructor) assert that `fee` equals an amount that was actually reserved/withdrawn from the message's paying account at enqueue time, or have `SendMessage::validate` recompute the required fee the same way v1 does via `calculate_fee`/`PricingParameters`, rejecting or clamping messages whose declared `fee` cannot be matched to collected value — analogous to validating `msg.value` against `mintFee` before forwarding it in `PhiFactory:claim`.

### Proof of Concept
Not independently reproducible from the indexed code alone: the decisive question — whether the `Message.fee` handed to `outbound-queue-v2::send_message_impl::validate` is bound to value actually withdrawn from the sending origin upstream (in the exporter/system pallet or XCM executor) — could not be confirmed with the available tool calls. The pallet-local code fact that is confirmed is that `validate`/`do_process_message`/`process_delivery_receipt` perform no such check themselves and unconditionally trust and pay out the `fee` field. A concrete PoC would require tracing `snowbridge_outbound_queue_primitives::v2::exporter.rs` and the system-v2 pallet's `send` path to confirm whether `fee` is ever cross-checked against collected value before reaching this pallet — recommend a Devin session with full repository access to complete that trace and build an executable PoC.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
