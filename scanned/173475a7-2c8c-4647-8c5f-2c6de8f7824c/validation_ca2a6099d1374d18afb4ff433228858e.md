### Title
`process_delivery_receipt` pays relayer reward and settles pending order without checking the on-chain delivery `success` flag - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
`snowbridge-pallet-outbound-queue-v2::Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` from an Ethereum `InboundMessageDispatched` event, which explicitly carries a `success: bool` field indicating whether the message actually executed successfully on Ethereum, but the pallet never inspects that field before paying out the relayer reward and permanently settling (removing) the `PendingOrder`. This mirrors the external report's root cause exactly: data decoded from an on-chain confirmation event is not cross-validated/consulted against the semantics required for correct settlement, so payout state advances unconditionally instead of only after real execution success.

### Finding Description
The outbound queue v2 flow is:

1. `do_process_message` creates a `PendingOrder { nonce, fee, block_number }` and stores it in `PendingOrders<T>` keyed by `nonce`. [1](#0-0) 

2. When a relayer later calls the public extrinsic `submit_delivery_receipt`, the event log is verified and decoded into a `DeliveryReceipt`, which is defined with a `success: bool` field sourced directly from the Ethereum `InboundMessageDispatched(nonce, topic, success, reward_address)` event: [2](#0-1) 

3. `submit_delivery_receipt` forwards the decoded `receipt` straight into `process_delivery_receipt`: [3](#0-2) 

4. `process_delivery_receipt` validates only the `gateway` address, looks up the `PendingOrder` by `nonce`, and unconditionally registers the reward for `order.fee` and removes the order — `receipt.success` is decoded but never read or branched on anywhere in this function: [4](#0-3) 

This is structurally the same class of bug as the external report: at creation time, state (`PendingOrder`) is committed based on the original message; at confirmation time, the code reads *some* fields from the on-chain event (`nonce`, `reward_address`) but silently drops the field (`success`) that determines whether the underlying obligation was actually fulfilled, and settles state (`RewardPayment::register_reward` + `PendingOrders::remove`) regardless. There is no guard anywhere else in the pallet (`do_process_message`, `send_message_impl.rs`, `types.rs`) that re-checks delivery success before payout — `Config::RewardPayment` unconditionally credits `order.fee` for both successful and failed inbound dispatch outcomes.

### Impact Explanation
The relayer reward is meant to pay for real, successful message delivery/execution on Ethereum (per the pallet's own doc comment: "the relayer will call the extrinsic `submit_delivery_receipt` to ... pay reward with fee attached in the order"). Because `success` is ignored, any relayer who gets their message included on Ethereum — even one that reverts/fails execution there — can submit the proof of the `InboundMessageDispatched` event with `success = false` and still receive the full relayer fee, while the `PendingOrder` is deleted so it can never be revisited or retried. This is a public, permissionless underpriced-work / duplicate-settlement issue: BridgeHub pays out value for work that did not actually complete, degrading the incentive alignment of the bridge relayer market and silently draining the reward pool over many failed deliveries, with no mechanism to detect, refund, or reprocess the failed message.

### Likelihood Explanation
The path is reachable by any signed account with a valid Merkle/receipt proof for an `InboundMessageDispatched` event — no privileged or governance role is required, and `success: false` outcomes are a normal occurrence on Ethereum (reverts, out-of-gas, target consuming failures), so this is not a contrived edge case. The bug fires on every "unsuccessful" delivery receipt that a relayer chooses (or is incentivized) to submit, making it a deterministic, repeatable, unprivileged path with medium-to-high practical likelihood.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success` before rewarding:
- If `receipt.success == true`, proceed exactly as today (register reward, remove `PendingOrder`, emit `MessageDelivered`).
- If `receipt.success == false`, do not call `T::RewardPayment::register_reward`; instead emit a distinct failure event (e.g. `MessageDeliveryFailed { nonce }`) and define an explicit policy for the `PendingOrder` (e.g., keep it for potential retry/expiry-based refund, or remove it while emitting an auditable failure event) so the fee is never paid for unsuccessful executions, and cumulative accounting of paid vs. failed deliveries is preserved.

### Proof of Concept
1. A message is enqueued and processed by `do_process_message`, creating `PendingOrders[nonce] = PendingOrder { nonce, fee: F, block_number }`.
2. The message is delivered to the Ethereum Gateway contract but its dispatched command reverts on execution, causing the Gateway to emit `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer (any signed account, no special role) gathers the standard receipt/execution proof for this event and calls:
   ```
   OutboundQueue::submit_delivery_receipt(origin, EventProof { event_log, proof })
   ```
4. `T::Verifier::verify` succeeds (the event genuinely occurred), `DeliveryReceipt::try_from` decodes `success: false` correctly, but `process_delivery_receipt` (bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:446-480) never reads `receipt.success`; it looks up `PendingOrders::get(nonce)`, finds `fee = F > 0`, calls `T::RewardPayment::register_reward(&reward_account, DefaultRewardKind, F)`, and removes the order.
5. Result: the relayer is rewarded `F` and the order is permanently settled even though the message dispatch failed on Ethereum — repeatable for every failed delivery a relayer chooses to submit proof for.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
