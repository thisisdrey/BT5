Found a solid local analog: `pallet-asset-conversion`'s `Swap` trait is invoked with **no minimum-out protection** inside the Snowbridge `system-frontend` pallet's `add_tip`/`register_token` public extrinsics.

### Title
`add_tip`/`register_token` swap tip assets for Ether with zero slippage protection before burn-for-teleport - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

### Summary
The Snowbridge `system-frontend` pallet exposes two unprivileged, signed extrinsics — `add_tip` and `register_token` — that convert an arbitrary user-supplied fee/tip asset into Ether via `T::Swap::swap_exact_tokens_for_tokens` before burning the Ether for teleportation to Ethereum. The call to the swap passes `None` for `amount_out_min`, explicitly disabling slippage protection, exactly mirroring the `rebalanceLite()` defect in the external report where a rebalance/swap operation lacked a caller-specified minimum-out guard. [1](#0-0) 

### Finding Description
`swap_and_burn` (called from both `add_tip` and `register_token` via `swap_fee_asset_and_burn`) swaps the caller's entire `tip_amount`/`fee_amount` of the tip asset into Ether using the generic `T::Swap` implementation (backed by `pallet_asset_conversion`, a constant-product AMM): [2](#0-1) 

The `amount_out_min` argument is hard-coded to `None` with the comment "No minimum amount required." The pallet's `Config::Swap` type is a generic trait object bound only by `Swap<AccountId, AssetKind = Location, Balance = u128>`, so callers of the public extrinsics `add_tip` and `register_token` have no ability whatsoever to bound the amount of Ether they will receive for their tip/fee asset: [3](#0-2) [4](#0-3) 

The resulting `ether_gained` (which could be an arbitrarily small amount, since it is entirely a function of pool reserves/price at execution time with no floor) is what actually gets burned and reported on-chain as the relayer tip/registration amount sent to BridgeHub: [5](#0-4) [6](#0-5) 

Just like the audited `rebalanceLite()` function, the caller (an unprivileged, `ensure_signed` origin) withdraws/consumes a fixed input amount from their account but has no contractual guarantee on the output amount that is actually converted and forwarded — the protocol computes the swap unilaterally and irreversibly commits the full input, with no path for the user to reject an unfavorable execution or recover any value. [7](#0-6) 

Unlike the Perp example (which involved literal leftover collateral stranded in a vault due to partial order fill), here the AMM swap is atomic and always fully executes the input amount — but the missing floor still permits catastrophic value loss whenever the tip-asset pool is thin relative to `tip_amount` (large price impact), is freshly created/low-liquidity, or has been manipulated by any other party's transaction earlier in the same block. There is no `amount_out_min` guard anywhere in the call path to stop this.

### Impact Explanation
A user calling `add_tip` or `register_token` can have their entire tip/fee asset consumed by the AMM swap while receiving a near-zero amount of Ether burned/reported to the Ethereum side, causing the tip or registration fee to be effectively destroyed with no benefit — real, unrecoverable user-fund loss with no way for the caller to protect themselves through the current pallet API. Because `add_tip` directly determines the relayer reward amount reported to `pallet-bridge-relayers` on BridgeHub, an ineffective swap also silently corrupts the intended reward economics of the bridge messaging flow.

### Likelihood Explanation
Likelihood is high for any user who calls these entrypoints against a thin or freshly-created tip-asset/Ether pool, which is a normal, unprivileged usage pattern (no malicious relayer, validator, or governance actor is required) — the vulnerability is a pure missing-parameter design defect identical in class to the audited report.

### Recommendation
Add a `min_ether_out` (or equivalent) parameter to `add_tip` and `register_token`, thread it through `swap_fee_asset_and_burn` / `swap_and_burn` as `Some(min_ether_out)` instead of hard-coded `None`, and revert the extrinsic if the swap cannot satisfy it — mirroring the `amount_out_min` pattern already implemented in `pallet_asset_conversion::swap_exact_tokens_for_tokens` itself. [8](#0-7) 

### Proof of Concept
1. Create a Snowbridge system-frontend deployment where `TipAsset`/`fee_asset` has a low-liquidity pool against Ether via `pallet_asset_conversion`.
2. Call `add_tip(message_id, asset)` where `asset` is a large amount relative to pool reserves.
3. Observe `swap_and_burn` invoking `T::Swap::swap_exact_tokens_for_tokens(who, [tip_asset, ether], tip_amount, None, who, true)` — the swap executes fully with heavy price impact and returns a minimal `ether_gained`. [9](#0-8) 
4. The minimal `ether_gained` is burned and encoded into the `AddTip` call sent to BridgeHub, permanently and irrecoverably losing the value gap between the user's intended tip and the executed amount, with no revert path available since no minimum was specified.

		fn swap_and_burn(
			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether
			let ether_asset = Asset::from((ether_location.clone(), ether_gained));

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}
