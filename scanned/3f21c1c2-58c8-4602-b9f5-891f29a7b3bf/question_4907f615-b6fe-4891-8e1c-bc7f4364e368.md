[Target: v0-market-vault.clar debt-add-scaled] Can an attacker force a debt-add-scaled call (via market.borrow) to be re-entered through a malicious ft-trait supplied as debt-ft (if send-tokens for borrowed funds happens after debt-add-scaled but the ft transfer for a PRIOR asset in the same tx has already committed), so a second debt-add-scaled for a different asset-id reads a stale mask and its insert (computed before the outer's) later gets overwritten by the outer's insert, hiding non-zero scaled debt from health checks? Preconditions: attacker holds two debt-eligible assets, deploys malicious ft, has collateral posted. Call sequence: market.borrow(asset1) -> market-vault.debt-add-scaled(asset1) reads mask, computes update-mask, calls add-user-scaled-debt (map-set debt) -> some transfer step reenters market.borrow(asset2) -> market-vault.debt-add-scaled(asset2) inserts registry with mask=bit(asset2) -> outer resumes, insert(updated-entry) with mask=bit(asset1) only, losing bit(asset2) though debt map row for asset2 is non-zero. Invariant tested: sum of user debt equals principal-scaled times index for every masked bit; mask bits equal set of non-zero debt rows. Impact class: Critical - protocol insolvency (borrower's real debt for asset2 becomes invisible to is-healthy/liquidation while debt map still owes tokens). Proof idea: Clarinet test comparing get-account-scaled-debt(account, asset2) > 0 against get-position(account, MAX-U64).debt list excluding asset2 due to cleared mask bit; show liquidate() cannot target asset2 debt.
