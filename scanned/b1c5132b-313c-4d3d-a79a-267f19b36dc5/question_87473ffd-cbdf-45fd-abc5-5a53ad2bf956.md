In session.rs, StackerDBSession::get_chunks builds `path` via stackerdb_get_chunk_path(contract_id, slot_id, Some(slot_version)) per requested (slot_id, slot_version) pair and issues one GET per pair with NO size-limit check on the returned body_bytes (unlike get_latest_chunks, which enforces `body_bytes.len() > limit`). Can a malicious StackerDB replica host respond to a get_chunks GET request with an arbitrarily large body (no SIGNERS_STACKERDB_CHUNK_SIZE/STACKERDB_MAX_CHUNK_SIZE bound enforced in this function), so the chunk stored in the returned Vec<Option<Vec<u8>>> and subsequently passed to StacksMessageCodec::consensus_deserialize by a caller has length unbounded by any wire-level chunk-size constant, unlike its sibling get_latest_chunks which explicitly checks the bound? Preconditions: attacker controls or has compromised the StackerDBSession's configured `host` (e.g., signer configured to a malicious/relay node, or MITM on an unencrypted plain-TCP RPC session). Call sequence: get_chunks -> rpc_request -> run_http_request -> decode_http_body -> Vec<u8> returned unbounded -> caller consensus_deserialize. Equality/fault: bytes returned by get_chunks == a size bounded by the same STACKERDB_MAX_CHUNK_SIZE/SIGNERS_STACKERDB_CHUNK_SIZE constant enforced in get_latest_chunks; here no such check exists, breaking the BOUNDS invariant. Impact: Critical, unbounded memory allocation / potential downstream parser DoS from a single oversized GET response with no chunk-size ceiling applied in get_chunks. Proof idea: unit test using a mock HTTP server returning a multi-hundred-MB body to a get_chunks call and asserting the function has no length guard comparable to get_latest_chunks' `limit` check.
