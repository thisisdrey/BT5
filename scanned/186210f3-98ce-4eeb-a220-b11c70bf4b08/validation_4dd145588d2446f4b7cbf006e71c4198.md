Found the bug I was looking for. In `IVestingCalls::vestedTransfer` in `substrate/frame/vesting/precompiles/src/lib.rs`, the `ensure_mutable::<T>(env)?` guard — the local equivalent of Ethereum's STATICCALL/`READ_ONLY` check used by every other state-mutating branch (`vest`, `vestOther`) — is missing.

### Title
Missing `READ_ONLY` (staticcall) guard on `vestedTransfer` lets a read-only/static call context mutate state - (File: substrate/frame/vesting/precompiles/src/lib.rs)

### Summary
`pallet-revive` precompiles enforce Ethereum's `STATICCALL` semantics via `Ext::is_read_only()`/`CallFlags::READ_ONLY`, requiring every state-mutating precompile branch to check `ensure_mutable`/`is_read_only` before touching storage [1](#0-0) . In the Vesting precompile, `vest` and `vestOther` correctly call `ensure_mutable::<T>(env)?` before dispatching [2](#0-1) [3](#0-2) , but `vestedTransfer` charges weight and immediately proceeds to call `pallet_vesting::Pallet::<T>::vested_transfer` without ever calling `ensure_mutable`, i.e. without checking `env.is_read_only()` [4](#0-3) .

### Finding Description
This is the direct local analog of the external report: a function path that is expected to behave as read-only/static (enforced via a "STATICCALL"-equivalent flag) actually performs mutating operations because the guard that should block state changes under that context is not applied. In the external report, `delegateToViewImplementation` (Solidity's `STATICCALL` idiom) assumed no state mutation would occur, and the underlying implementation broke that assumption. Here, the codebase's actual `STATICCALL` mechanism — `CallFlags::READ_ONLY` / `Ext::is_read_only()`, enforced consistently everywhere else in `pallet-revive` (contract-to-contract calls [5](#0-4) , the `Storage` precompile [6](#0-5) , the assets ERC20 precompile [7](#0-6) , the asset-conversion precompile [8](#0-7) , and the XCM precompile [9](#0-8)  — is simply not applied to `vestedTransfer`.

A caller that enters the Vesting precompile through a read-only execution context (e.g. a nested call made with `CallFlags::READ_ONLY` set, or any call inheriting `is_read_only()` from a parent frame per `Ext::call`/`delegate_call` propagation in `exec.rs` [10](#0-9) ) can still invoke `vestedTransfer`, which moves currency from the caller to a target account and locks it under a new vesting schedule — a genuine storage/balance mutation that the `READ_ONLY` contract is supposed to forbid.

### Impact Explanation
This breaks the "public wrappers … must not widen origin, bypass filters, or undercharge nested execution" invariant: a call flagged as read-only is a filter meant to guarantee no state change occurs in the sub-call, and it is relied upon by other contracts/tooling (e.g. `staticcall`-based view helpers, simulators, or contracts that make an "untrusted" call as `READ_ONLY` specifically to prevent reentrant state mutation). Silently allowing `vestedTransfer` through this filter permits unauthorized balance transfer/lock creation from what should be a guaranteed no-op call, i.e. unauthorized execution reaching real fund movement despite an explicit protocol-level restriction.

### Likelihood Explanation
High confidence, low complexity to trigger: any unprivileged account can construct a call with `CallFlags::READ_ONLY` (or be a nested call inheriting read-only status) targeting the Vesting precompile's `vestedTransfer` selector; no privileged actor, governance, or malicious peer/validator is required — it is a straightforward public-entrypoint filter-bypass, matching the sibling functions in the same file that correctly enforce the guard, making the omission clearly unintentional.

### Recommendation
Add `ensure_mutable::<T>(env)?;` immediately after the weight charge and before invoking `pallet_vesting::Pallet::<T>::vested_transfer` in the `vestedTransfer` branch, matching the pattern already used in `vest` and `vestOther`.

### Proof of Concept
1. Deploy/invoke a contract that calls the Vesting precompile address (`0x0902`) with `IVesting::vestedTransferCall { target, locked, perBlock, startingBlock }` using `CallFlags::READ_ONLY` (directly, or via a parent frame that is already `is_read_only()`).
2. Observe that unlike `vest`/`vestOther` (which revert with `StateChangeDenied`), `vestedTransfer` proceeds: `ensure_mutable` is never invoked in that branch [11](#0-10) , so `pallet_vesting::Pallet::<T>::vested_transfer` executes, transferring and locking the caller's balance into the target's vesting schedule despite the call being marked read-only.
3. Add a unit test analogous to `read_only_call_cannot_transfer` in `substrate/frame/revive/src/tests/pvm.rs` [12](#0-11)  that targets the Vesting precompile's `vestedTransfer` to confirm it does not return `StateChangeDenied`.

fn ensure_mutable<T: Config>(env: &impl Ext<T = T>) -> Result<(), Error> {
	if env.is_read_only() {
		return Err(pallet_revive::Error::<T>::StateChangeDenied.into());
	}
	if env.is_delegate_call() {
		return Err(pallet_revive::Error::<T>::PrecompileDelegateDenied.into());
	}
	Ok(())
}

#[test]
fn read_only_call_cannot_transfer() {
	let (binary_caller, _code_hash_caller) = compile_module("call_with_flags_and_value").unwrap();
	let (binary_callee, _code_hash_callee) = compile_module("dummy").unwrap();
	ExtBuilder::default().existential_deposit(200).build().execute_with(|| {
		let _ = <Test as Config>::Currency::set_balance(&ALICE, 1_000_000);

		// Create both contracts: Constructors do nothing.
		let Contract { addr: addr_caller, .. } =
			builder::bare_instantiate(Code::Upload(binary_caller)).build_and_unwrap_contract();
		let Contract { addr: addr_callee, .. } =
			builder::bare_instantiate(Code::Upload(binary_callee)).build_and_unwrap_contract();

		// Read-only call fails when a non-zero value is set.
		assert_err_ignore_postinfo!(
			builder::call(addr_caller)
				.data(
					(addr_callee, pallet_revive_uapi::CallFlags::READ_ONLY.bits(), 100u64).encode()
				)
				.build(),
			<Error<Test>>::StateChangeDenied
		);
	});
}
