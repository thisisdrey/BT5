### Title
`add_tip` in Snowbridge inbound-queue-v2 lets any signed account write unbounded, unvalidated entries into `Tips` for nonces that may never exist - (File: `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs`)

### Summary
The Bribe bug's core defect is that a state-mutating action which is supposed to be gated by a specific privileged caller (`gauge` for `_addRewardToken`) is reachable, unchecked against the intended precondition, through a second, permissionless entrypoint (`notifyRewardAmount`) that blindly performs an insert into a bounded/curated collection. The local analog is `AddTip::add_tip` in `snowbridge-pallet-inbound-queue-v2`, reachable by any signed AssetHub user via `snowbridge-pallet-system-frontend::add_tip` → XCM `Transact` → `snowbridge-pallet-system-v2::add_tip`. It inserts an entry into the `Tips` storage map keyed by an attacker-supplied `nonce: u64` with **no validation that the nonce corresponds to an actual, currently in-flight message** (unlike the outbound-queue-v2 sibling, which validates against `PendingOrders`).

### Finding Description
`Tips` is declared as an unbounded `StorageMap<_, Blake2_128Concat, u64, u128, OptionQuery>`: [1](#0-0) 

`AddTip::add_tip` for this pallet only checks that the amount is non-zero, then unconditionally writes into `Tips` for the given nonce: [2](#0-1) 

Contrast this with the outbound-queue-v2 implementation of the same trait, which requires the nonce to reference an existing `PendingOrders` entry before mutating anything, rejecting unknown nonces: [3](#0-2) 

The only consumer that removes an entry from `Tips` is `process_message`, which `take`s the tip keyed by the *real* nonce of a message that has actually arrived from Ethereum and passed nonce/gateway checks: [4](#0-3) 

Inbound message nonces are monotonically assigned on the Ethereum side and only ever consumed in the order real messages arrive, gated by `NonceBitmap`/`Nonce::<T>::get(nonce)`; `submit` is itself gated behind verifying an actual event proof from the Gateway contract, so nonce values are not attacker-choosable in the "real" stream: [5](#0-4) 

`add_tip` is reachable end-to-end without any relationship check between the caller and the message: any signed account on AssetHub can call `SnowbridgeSystemFrontend::add_tip(message_id, asset)`, which swaps/burns the asset for Ether and forwards a `Transact` to BridgeHub's `EthereumSystemV2::add_tip`, which only checks `T::FrontendOrigin::ensure_origin` (i.e., that the call legitimately originated from the frontend pallet's XCM, not that the caller has any connection to the referenced nonce): [6](#0-5) [7](#0-6) 

Because there is no bound on the key space (`u64`) and no requirement that a nonce currently be "live" (unprocessed but destined to arrive), an attacker can call `add_tip` for arbitrary/future/never-to-arrive nonces (e.g., far beyond the current nonce counter, or values for messages that will never be relayed) and permanently populate the `Tips` map, since removal only happens on actual message processing for that exact nonce. This is the direct analog of `notifyRewardAmount` bypassing the intended gauge-only gate on `_addRewardToken`: a "helper"/side-effect entrypoint performs an unguarded write into curated state that another, more careful code path (outbound queue's `add_tip`) explicitly protects with an existence check.

### Impact Explanation
This falls under "public underpriced work that degrades block production or stalls bridge processing." Each call costs the attacker only the burnt tip amount (which can be minimal, since only `amount > 0` is enforced) plus the fixed extrinsic weight, but creates a permanent (until an improbable/impossible future event) storage entry, since there is no expiry, cap, or reaping mechanism for `Tips`. Repeated calls with distinct, non-existent nonces cause unbounded storage growth in `pallet-inbound-queue-v2`'s state on BridgeHub, inflating state size/PoV weight for all future block validation and node storage, i.e., chain-level degradation is achievable by an unprivileged party without needing a malicious relayer, validator, or admin.

### Likelihood Explanation
Likelihood is high: the path requires only a signed account with a small amount of any asset that can be swapped/burned into Ether, and calls a fully public extrinsic (`SnowbridgeSystemFrontend::add_tip`) that is documented and intended to be user-facing. No governance, relayer, or validator collusion is required, and the discrepancy between the inbound and outbound `AddTip` implementations (one validates existence, the other does not) indicates this was not an intentionally accepted design tradeoff but an oversight, since the outbound implementation demonstrates the intended check.

### Recommendation
In `snowbridge-pallet-inbound-queue-v2::AddTip::add_tip`, validate that the nonce is plausible before inserting into `Tips`, mirroring the outbound-queue-v2 check against `PendingOrders`: e.g., reject nonces at or below the next-expected nonce (already consumed) as well as nonces too far ahead of what could plausibly be in flight (or maintain a small bounded window/cap for outstanding tips), and/or bound the total number of unconsumed `Tips` entries, evicting/rejecting once a cap is reached, so unprivileged callers cannot create unbounded persistent state.

### Proof of Concept
1. On AssetHub, as any signed, unprivileged account `attacker` holding a minimal balance of a fee-eligible asset, call:
   `SnowbridgeSystemFrontend::add_tip(origin = signed(attacker), message_id = MessageId::Inbound(nonce), asset = Asset{ id: <fee asset>, fun: Fungible(1) })`
   for a `nonce` far beyond any nonce that will realistically be relayed from Ethereum (e.g., `u64::MAX - k`, or any value skipped by real traffic).
2. This is forwarded via `add_tip` XCM `Transact` to BridgeHub, where `EthereumSystemV2::add_tip` only checks `T::FrontendOrigin::ensure_origin` and dispatches to `InboundQueue::add_tip(nonce, amount)`.
3. `Tips::<T>::mutate(nonce, ...)` unconditionally inserts the entry — no check exists that `nonce` corresponds to an actual pending/soon-to-arrive message (compare to `outbound-queue-v2`'s `PendingOrders::get(nonce).ok_or(...)` guard).
4. Repeat with many distinct bogus nonces at minimal per-call cost; each call permanently grows `Tips` storage since the entry is only removed by `process_message` for that exact nonce, which will never occur for a fabricated nonce.

	impl<T: Config> Pallet<T> {
		pub fn process_message(relayer: T::AccountId, message: Message) -> DispatchResult {
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == message.gateway, Error::<T>::InvalidGateway);

			let (nonce, relayer_fee) = (message.nonce, message.relayer_fee);

			// Verify the message has not been processed
			ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);

			// Mark message as received
			Nonce::<T>::set(nonce);

			let message_id = T::MessageProcessor::process_message(relayer.clone(), message)
				.map_err(|e| match e {
					MessageProcessorError::ProcessMessage(e) => e,
					MessageProcessorError::ConvertMessage(e) => Error::<T>::from(e).into(),
					MessageProcessorError::SendMessage(e) => Error::<T>::from(e).into(),
				})?;

			// Pay relayer reward
			let tip = Tips::<T>::take(nonce).unwrap_or_default();
			let total_tip = relayer_fee.saturating_add(tip);
			if total_tip > 0 {
				T::RewardPayment::register_reward(&relayer, T::DefaultRewardKind::get(), total_tip);
			}

			// Emit event with the message_id
			Self::deposit_event(Event::MessageReceived { nonce, message_id });

			Ok(())
		}

	impl<T: Config> AddTip for Pallet<T> {
		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			// If the nonce is already processed, return an error
			ensure!(!Nonce::<T>::get(nonce.into()), AddTipError::NonceConsumed);
			// Otherwise add the tip.
			Tips::<T>::mutate(nonce, |tip| {
				*tip = Some(tip.unwrap_or_default().saturating_add(amount));
			});
			return Ok(());
		}

			ensure!(amount > 0, AddTipError::AmountZero);
			PendingOrders::<T>::try_mutate_exists(nonce, |maybe_order| -> Result<(), AddTipError> {
				match maybe_order {
					Some(order) => {
						order.fee = order.fee.saturating_add(amount);
						Ok(())
					},
					None => Err(AddTipError::UnknownMessage),
				}
			})
		}

		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}
