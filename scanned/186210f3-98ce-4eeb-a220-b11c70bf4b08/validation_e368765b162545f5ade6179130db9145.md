### Title
Decimal-conversion rounding in Snowbridge outbound-queue fee calculation can zero out relayer reward while charging a non-zero fee - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
`OutboundQueue::calculate_fee` converts a message's Ethereum-side cost (denominated in wei, 18 decimals) into the local chain's native `Balance` decimals via `FixedU128`-based arithmetic and `convert_from_ether_decimals`. With legitimate, non-zero `PricingParameters` (non-zero `exchange_rate`, `fee_per_gas`, and `rewards.remote`), the computed `fee.remote` can truncate to `0` due to the decimal-scaling division, exactly mirroring the external report's core defect: a decimals-unaware unit conversion silently rounds a real value down to zero.

### Finding Description
`calculate_fee` computes the remote (Ethereum-side) fee as: [1](#0-0) 

It takes `fee_per_gas * gas_used + reward` (wei, 18 decimals), reinterprets that raw `u128` as a `FixedU128` (`from_inner`, which is itself scaled to 18 decimal places), multiplies by `multiplier`, divides by `exchange_rate`, and then calls `convert_from_ether_decimals`, which floor-divides by `10^(18 - T::Decimals)`: [2](#0-1) 

Because native chains use far fewer decimals than Ethereum (DOT = 10, KSM/BridgeHub = 12, vs. ETH's 18), this final division by `10^6`–`10^8` can floor small (but real, non-zero) wei-denominated remote costs down to `0`, even though every pricing parameter (`exchange_rate`, `fee_per_gas`, `rewards.remote`) is validated as non-zero by `PricingParameters::validate`: [3](#0-2) 

This is exactly the defect class in the external report: a conversion between two different decimal domains (wei/18-decimals vs. native/10-or-12-decimals) that does not account for the magnitude difference, causing legitimate non-zero inputs to compute a zero output. The repository's own test acknowledges this is a genuine bug, not intended behavior: [4](#0-3) 

The computed `Fee` (local + remote) is charged to the sender in `SendMessage::validate` without any check that `fee.remote` (which funds the relayer's on-Ethereum `Reward`) is non-zero: [5](#0-4) 

The message is then queued and dispatched to Ethereum with `Message.Reward = 0` (per the module's own documented fee-settlement formula `Min(GasPrice, MaxFeePerGas) * GasUsed() + Message.Reward`), even though governance configured a non-zero reward parameter.

### Impact Explanation
Relayers are only compensated on Ethereum for gas usage plus `Message.Reward`. If the reward component silently rounds to zero due to this decimal-truncation bug (which is realistic under normal parameter magnitudes, as demonstrated by the repository's own unit test), rational relayers have no incentive to submit messages whose reward is zero, especially during periods where gas refund alone does not cover relaying costs/risk. This degrades or stalls the bridge's outbound message-processing pipeline (messages sit in `MessageQueue` unrelayed) — this matches the "public underpriced work that degrades block production or stalls bridge processing" impact category for Snowbridge. The bug is entirely in-repo runtime logic (`calculate_fee`), not a relayer/prover/admin assumption issue: it fires under normal, valid, non-adversarial `PricingParameters`.

### Likelihood Explanation
High. The truncation depends only on ordinary parameter magnitudes (gas price, per-message max gas, reward size, ETH/DOT exchange rate) relative to the `10^6`–`10^8` decimal-scaling factor applied in `convert_from_ether_decimals`. Any message with a modest gas footprint, low configured reward, or an ETH/DOT exchange-rate regime that pushes the wei-denominated remote fee below the scaling threshold will produce `fee.remote == 0`. This does not require a malicious actor, governance abuse, or a compromised relayer — it is a deterministic consequence of the existing conversion formula and is already reproduced by an in-tree unit test (`test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero`), whose own comment states the result "is invalid which should be avoided."

### Recommendation
`calculate_fee` should reject or floor the computed `fee.remote` to a minimum non-zero value (or return an error / re-scale earlier, before precision is lost) whenever the underlying wei-denominated remote cost and reward are non-zero but round to zero in the target `Balance` decimals — mirroring the fix pattern already used elsewhere in this codebase in `pallet-psm`'s `AmountTooSmallAfterConversion` guard and `pallet-asset-conversion`'s hardening against zero-output rounding. Concretely, either raise the intermediate precision before the final `convert_from_ether_decimals` division, or explicitly `ensure!(!fee.remote.is_zero())` (returning `InvalidPricingParameters` or a dedicated error) when non-zero remote inputs round down to zero, forcing governance to adjust the pricing parameters rather than silently underpaying relayers.

### Proof of Concept
The existing repository test already demonstrates the defect end-to-end with realistic, fully non-zero `PricingParameters`:
```rust
// bridges/snowbridge/pallets/outbound-queue/src/test.rs:303-319
#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {
		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
			exchange_rate: FixedU128::from_rational(1, 1),
			fee_per_gas: 1_u32.into(),
			rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});
}
```
All `PricingParameters::validate()` checks pass (all fields non-zero), yet `fee.remote` — which funds the relayer's `Message.Reward` on Ethereum — is `0`. A message sent under these (or similarly-scaled) parameters via `SendMessage::validate` in `send_message_impl.rs` would be enqueued and charged fees, but the relayer reward transmitted to Ethereum would be zero, disincentivizing relaying and stalling bridge message delivery.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

			let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
			let denom = 10u128.saturating_pow(decimals);
			value.checked_div(denom).expect("divisor is non-zero; qed").into()
		}

		}

	}

		let payload = message.command.abi_encode();
		ensure!(

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
