## Analysis

The external report's core broken invariant: **a pause/halt flag is enforced at the "intake" function (`_blockingLzReceive`) but not at the actual "processing/settlement" function (`_nonblockingLzReceive`) that a message reaches via a secondary path (`retryMessage`), so state that should be frozen while paused keeps advancing.**

The closest, currently-live local analog is in Snowbridge's outbound message pipeline: `deliver()` checks the pallet's halted state before *enqueuing* a message, but `do_process_message()` — the function that actually drains the queue, builds the Ethereum-bound commitment, and creates the relayer `PendingOrder` — performs **no halted check at all**. Once a message is enqueued (before a halt), `pallet-message-queue`'s `on_initialize`/`on_idle` hooks will keep calling `ProcessMessage::process_message` → `do_process_message` and complete settlement regardless of a subsequent `set_operating_mode(Halted)` call.

### Title
Halting `OutboundQueue`/`OutboundQueueV2` does not stop already-enqueued messages from being committed and dispatched - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`, `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`snowbridge-pallet-outbound-queue` (and its v2 counterpart) checks `OperatingMode`/halted status only in the `deliver()` path that enqueues a message into `T::MessageQueue`, via `ensure!(!Self::operating_mode().is_halted(), SendError::Halted)` in `send_message_impl.rs`. [1](#0-0)  The actual settlement logic — `do_process_message`, invoked by `pallet-message-queue` on every block via its `ProcessMessage` hooks — never re-checks the halted flag before committing the message to `Messages`/`MessageLeaves` and creating the relayer `PendingOrder`. [2](#0-1)  The v2 pallet has the identical structure. [3](#0-2) 

### Finding Description
The intended semantics of `set_operating_mode(Halted)` — used by governance "when it suspects a compromise" — is to stop all outbound-queue activity. [4](#0-3)  However, the halt gate is only placed on the `deliver` entrypoint that *enqueues* new messages, exactly mirroring the reported bug where `_blockingLzReceive` gates a pause but the eventual processing routine (`_nonblockingLzReceive`) does not. Once a message has been accepted into the underlying `pallet-message-queue` (which is entirely decoupled and driven by its own `on_initialize`/`on_idle` weight budget), that queue keeps calling `Pallet::do_process_message` every block irrespective of Snowbridge's own `OperatingMode` storage. `do_process_message` contains no `ensure!(!OperatingMode::<T>::get().is_halted(), ...)` guard anywhere in its body. [2](#0-1)  The existing test `submit_upgrade_message_success_when_queue_halted` only proves that *new* low-priority sends are rejected while halted — it does not exercise (and the code does not protect) already-queued messages that get drained after the halt is set. [5](#0-4) 

The impact is state-consistency-breaking: after `do_process_message` runs, the message is ABI-encoded, hashed into `MessageLeaves`, and at the end of the block `commit()` inserts a merkle root into the parachain header digest via `Self::commit()` regardless of halted state — `commit()` also has no halt check. [6](#0-5)  This means the merkle root committed into the header (which Ethereum's light client ultimately verifies) still advances and a `PendingOrder` reward entry is still created, even though governance activated `Halted` specifically to stop this from happening.

### Impact Explanation
This directly matches the "Public underpriced work that degrades block production or stalls bridge processing" / "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" pivots, but inverted: settlement continues to advance *despite* an explicit emergency halt meant to stop it, because the guard is enforced only at intake and not at the point that state (`Messages`, `MessageLeaves`, `PendingOrders`, and the header digest commitment) is actually mutated. If governance halts the bridge because a bad/compromised message content was detected already sitting in the queue (e.g., a malformed or exploit-crafted `Command` accepted before the compromise was discovered), that message will still be committed to the Ethereum-bound merkle root and a relayer reward order will still be created for it, defeating the purpose of the halt and potentially allowing the malicious payload to reach Ethereum execution.

### Likelihood Explanation
No privileged action is required from the attacker beyond a normal, permitted `deliver()` call to enqueue a message before governance becomes aware of the need to halt. The attacker just needs to get a message into the queue (e.g., via a sibling parachain XCM send that goes through `EthereumBlobExporter::deliver`) shortly before/around the time an incident triggers a halt; the message-queue's routine block-by-block servicing (not any privileged/attacker action) then completes the settlement, since `do_process_message`/`commit` are unconditionally executed by `on_initialize`/`on_idle` regardless of the pallet's own operating mode.

### Recommendation
Add an explicit halted check inside `do_process_message` (and/or `commit`) for both `snowbridge-pallet-outbound-queue` and `snowbridge-pallet-outbound-queue-v2`, mirroring the fix already applied for the verifier in `pr_11856.prdoc`. [7](#0-6)  If halted, return `ProcessMessageError::Yield`/`TemporarilyUnprocessable` so queued messages remain intact and are resumed only once governance clears the halt, rather than silently settling while the bridge is supposed to be frozen.

### Proof of Concept
1. Sibling parachain calls `EthereumBlobExporter` which invokes `OutboundQueue::validate` + `OutboundQueue::deliver`, successfully enqueuing an attacker-influenced message (halted is `Normal` at this point). [1](#0-0) 
2. Governance detects an issue and calls `set_operating_mode(Halted)`. [8](#0-7) 
3. On the next block, `pallet-message-queue`'s `on_initialize` still invokes `ProcessMessage::process_message` → `Pallet::do_process_message`, which has no halted check, and the message is committed into `Messages`/`MessageLeaves` and a `PendingOrder` is created. [2](#0-1) 
4. `commit()` runs at block finalization and inserts the merkle root (which includes the attacker's message) into the header digest, exactly as if the pallet were never halted. [6](#0-5)

```rust
		/// Process a message delivered by the MessageQueue pallet
		pub(crate) fn do_process_message(
			_: ProcessMessageOriginOf<T>,
			mut message: &[u8],
		) -> Result<bool, ProcessMessageError> {
			use ProcessMessageError::*;

			// Yield if the maximum number of messages has been processed this block.
			// This ensures that the weight of `on_finalize` has a known maximum bound.
			ensure!(
				MessageLeaves::<T>::decode_len().unwrap_or(0) <
					T::MaxMessagesPerBlock::get() as usize,
				Yield
			);

			// Decode bytes into versioned message
			let versioned_queued_message: VersionedQueuedMessage =
				VersionedQueuedMessage::decode(&mut message).map_err(|_| Corrupt)?;

			// Convert versioned message into latest supported message version
			let queued_message: QueuedMessage =
				versioned_queued_message.try_into().map_err(|_| Unsupported)?;

			// Obtain next nonce
			let nonce = <Nonce<T>>::try_mutate(
				queued_message.channel_id,
				|nonce| -> Result<u64, ProcessMessageError> {
					*nonce = nonce.checked_add(1).ok_or(Unsupported)?;
					Ok(*nonce)
				},
			)?;

			let pricing_params = T::PricingParameters::get();
			let command = queued_message.command.index();
			let params = queued_message.command.abi_encode();
			let max_dispatch_gas =
				T::GasMeter::maximum_dispatch_gas_used_at_most(&queued_message.command);
			let reward = pricing_params.rewards.remote;

			// Construct the final committed message
			let message = CommittedMessage {
				channel_id: queued_message.channel_id,
				nonce,
				command,
				params,
				max_dispatch_gas,
				max_fee_per_gas: pricing_params
					.fee_per_gas
					.try_into()
					.defensive_unwrap_or(u128::MAX),
				reward: reward.try_into().defensive_unwrap_or(u128::MAX),
				id: queued_message.id,
			};

			// ABI-encode and hash the prepared message
			let message_abi_encoded = ethabi::encode(&[message.clone().into()]);
			let message_abi_encoded_hash = <T as Config>::Hashing::hash(&message_abi_encoded);

			Messages::<T>::append(Box::new(message));
			MessageLeaves::<T>::append(message_abi_encoded_hash);

			Self::deposit_event(Event::MessageAccepted { id: queued_message.id, nonce });

			Ok(true)
		}
```

```rust
		/// Process a message delivered by the MessageQueue pallet.
		/// IMPORTANT!! This method does not roll back storage changes on error.
		pub(crate) fn do_process_message(
			_: ProcessMessageOriginOf<T>,
			mut message: &[u8],
		) -> Result<bool, ProcessMessageError> {
			use ProcessMessageError::*;

			// Yield if the maximum number of messages has been processed this block.
			// This ensures that the weight of `on_finalize` has a known maximum bound.
			let current_len = MessageLeaves::<T>::decode_len().unwrap_or(0);
			if current_len >= T::MaxMessagesPerBlock::get() as usize {
				Self::deposit_event(Event::MessagePostponed {
					payload: message.to_vec(),
					reason: Yield,
				});
				return Err(Yield);
			}

			// Decode bytes into Message
			let Message { origin, id, fee, commands } =
				Message::decode(&mut message).map_err(|_| {
					Self::deposit_event(Event::MessageRejected {
						id: None,
						payload: message.to_vec(),
						error: Corrupt,
					});
					Corrupt
				})?;

			// Convert it to OutboundMessage and save into Messages storage
			let commands: Vec<OutboundCommandWrapper> = commands
				.into_iter()
				.map(|command| OutboundCommandWrapper {
					kind: command.index(),
					gas: T::GasMeter::maximum_dispatch_gas_used_at_most(&command),
					payload: command.abi_encode(),
				})
				.collect();

			let nonce = <Nonce<T>>::get().checked_add(1).ok_or_else(|| {
				Self::deposit_event(Event::MessageRejected {
					id: None,
					payload: message.to_vec(),
					error: Unsupported,
				});
				Unsupported
			})?;

			let outbound_message = OutboundMessage {
				origin,
				nonce,
				topic: id,
				commands: commands.clone().try_into().map_err(|_| {
					Self::deposit_event(Event::MessageRejected {
						id: Some(id),
						payload: message.to_vec(),
						error: Corrupt,
					});
					Corrupt
				})?,
			};
			Messages::<T>::append(outbound_message);

			// Convert it to an OutboundMessageWrapper (in ABI format), hash it using Keccak256 to
			// generate a committed hash, and store it in MessageLeaves storage which can be
			// verified on Ethereum later.
			let abi_commands: Vec<CommandWrapper> = commands
				.into_iter()
				.map(|command| CommandWrapper {
					kind: command.kind,
					gas: command.gas,
					payload: Bytes::from(command.payload),
				})
				.collect();
			let committed_message = OutboundMessageWrapper {
				origin: FixedBytes::from(origin.as_fixed_bytes()),
				nonce,
				topic: FixedBytes::from(id.as_fixed_bytes()),
				commands: abi_commands,
			};
			let message_abi_encoded_hash =
				<T as Config>::Hashing::hash(&committed_message.abi_encode());
			MessageLeaves::<T>::append(message_abi_encoded_hash);

			// Generate `PendingOrder` with fee attached in the message, stored
			// into the `PendingOrders` map storage, with assigned nonce as the key.
			// When the message is processed on ethereum side, the relayer will send the nonce
			// back with delivery proof, only after that the order can
			// be resolved and the fee will be rewarded to the relayer.
			let order = PendingOrder {
				nonce,
				fee,
				block_number: frame_system::Pallet::<T>::current_block_number(),
			};
			<PendingOrders<T>>::insert(nonce, order);

			<Nonce<T>>::set(nonce);

			Self::deposit_event(Event::MessageAccepted { id, nonce });

			Ok(true)
		}
```

```text
title: 'Snowbridge: halt the Ethereum verifier when the bridge is in emergency stop'

doc:
  - audience: Runtime Dev
    description: |
      When `pallet-ethereum-client` is in `Halted` operating mode, its `Verifier::verify`
      implementation now short-circuits with the new `VerificationError::Halted` instead of
      attempting to verify Ethereum-side proofs.

      Previously, halting the light client only blocked new beacon header updates via
      `EthereumBeaconClient::submit`. Proof verification still ran, which meant
      `inbound_queue_v2::submit` and `outbound_queue_v2::submit_delivery_receipt` could
      continue to process receipts and pay out relayer rewards from `PendingOrders` while
      governance had halted the bridge (e.g. after a suspected beacon light client compromise).

      Halting the verifier closes that gap in one place — covering both inbound dispatch and
      outbound delivery-receipt reward payments.
```
