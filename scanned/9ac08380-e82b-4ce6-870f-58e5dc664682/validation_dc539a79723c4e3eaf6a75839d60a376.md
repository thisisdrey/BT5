Based on my research, I found a concrete local analog in `pallet-asset-conversion`, though I was unable to fully verify the `do_add_liquidity` LP-token minting path before running out of iterations. I'll report what is solidly evidenced.

### Title
Underpriced/zero-output swap acceptance in `do_swap_exact_tokens_for_tokens` due to unguarded rounding-to-zero AMM output - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
The core broken invariant in the Cooler `roll`/`repay` report is: a public entrypoint performs an integer division that can round down to zero on small inputs, silently decoupling two values (`loan.amount` vs `loan.collateral`) that are supposed to stay proportional, corrupting downstream accounting. The same rounding-to-zero class exists in `pallet-asset-conversion`'s AMM math (`get_amount_out`/`quote`), and the repository's own `prdoc/stable2606/pr_11795.prdoc` confirms it was previously exploitable: `quote_price_exact_tokens_for_tokens` and `quote_price_tokens_for_exact_tokens` used to return `Some(0)` for small inputs on skewed pools instead of `None`. That patch fixed only the two read-only quote helpers, not the actual state-changing swap entrypoints, `Pallet::do_swap_exact_tokens_for_tokens` and `do_swap_exact_credit_tokens_for_tokens` [1](#0-0) , which only validate `amount_in > 0`, never that the computed `amount_out` is non-zero.

### Finding Description
`do_swap_exact_tokens_for_tokens` guards `amount_in > Zero::zero()` and, if `amount_out_min` is supplied, that `amount_out >= amount_out_min`, but it never checks `amount_out.is_zero()` when the caller omits `amount_out_min` (an `Option`) [2](#0-1) . The output amount is derived from `get_amount_out`, whose final step is an integer `checked_div` that floors the result [3](#0-2) . As demonstrated by the repo's own regression test, a tiny `amount_in` against a heavily skewed pool (`get_amount_out(1, 1_000_000, 200) = 0`) rounds the swap output to zero [4](#0-3) . That test only proves the *quote* function now rejects this case; the actual swap dispatchable path (`swap_exact_tokens_for_tokens` → `do_swap_exact_tokens_for_tokens` → `Self::swap`) performs the withdraw/deposit using the same unguarded `amount_out` computation, executing a real `T::Assets::transfer` of the input token from the caller into the pool for zero tokens back when `amount_out_min` is `None`. This is functionally identical to Cooler's `repay`: a public, unprivileged, permissionless call whose core ratio calculation rounds down to zero on small amounts, and no explicit `!amount_out.is_zero()` check exists to reject it, unlike the guard the maintainers added to the read-only quote helpers.

### Impact Explanation
This falls under "public underpriced work that degrades block production or stalls bridge processing" / conservation-of-value guarantees for AMM pools: an attacker can force the pool to execute weight-consuming storage writes, transfers, and event emissions in `do_swap_exact_tokens_for_tokens` and `Self::swap` while contributing input tokens for zero output, repeatable at scale to spam the chain with underpriced transactions that donate liquidity into a skewed pool with no economic return check enforced by the protocol itself (only avoidable by the caller voluntarily setting `amount_out_min`). It is lower severity than outright fund theft, since no beneficiary receives stolen funds, but it does represent unenforced invariant checking on a live public dispatchable that the team already recognized needed hardening for the read path.

### Likelihood Explanation
Likelihood is moderate: it requires an attacker to locate or intentionally create a skewed pool and submit swaps without `amount_out_min` (a caller-controlled optional parameter, so this is trivially triggerable by any unprivileged account calling `swap_exact_tokens_for_tokens`/`swap_exact_credit_tokens_for_tokens` and omitting the minimum-out guard). No privileged role, governance, relayer, or validator collusion is needed.

### Recommendation
Mirror the fix already applied to `quote_price_exact_tokens_for_tokens`/`quote_price_tokens_for_exact_tokens` (per `prdoc/stable2606/pr_11795.prdoc`) inside `do_swap_exact_tokens_for_tokens`, `do_swap_tokens_for_exact_tokens`, and `do_swap_exact_credit_tokens_for_tokens`: after computing `amount_out` (or `amount_in`), explicitly `ensure!(!amount_out.is_zero(), Error::<T>::ZeroAmount)` regardless of whether `amount_out_min` was supplied, so the state-changing swap path can never execute a real transfer for a rounded-to-zero result.

### Proof of Concept
1. Create a pool and add liquidity so reserves are heavily skewed, e.g. `reserve_in = 1_000_000`, `reserve_out = 200` (as in the existing test `quote_price_returns_none_for_zero_output`) [5](#0-4) .
2. Call `Pallet::swap_exact_tokens_for_tokens(origin, path, amount_in = 1, amount_out_min = None, send_to, keep_alive)` [6](#0-5) .
3. Trace into `do_swap_exact_tokens_for_tokens`: `amount_in > 0` passes, `amount_out_min` is `None` so the `>=` check is skipped entirely [2](#0-1) ; `get_amount_out` computes `1*997*200 / (1_000_000*1000 + 997) = 0` per the same arithmetic verified in the existing unit test [7](#0-6) .
4. `Self::swap` executes with `amount_out = 0`, withdrawing `amount_in = 1` from the caller into the pool and emitting `SwapExecuted { amount_out: 0, .. }`, with no error raised.

I was unable to fully confirm within the available iterations whether `do_add_liquidity`'s LP-token minting math (`mul_div`) has an analogous unguarded rounding-to-zero path that could desynchronize reserve ratios in a way that causes a later underflow (the Cooler-report's exact "later revert" pattern); that portion remains unverified and should be checked separately by a reviewer with file access to `substrate/frame/asset-conversion/src/lib.rs` around `do_add_liquidity`.

		pub(crate) fn do_swap_exact_tokens_for_tokens(
			sender: T::AccountId,
			path: Vec<T::AssetKind>,
			amount_in: T::Balance,
			amount_out_min: Option<T::Balance>,
			send_to: T::AccountId,
			keep_alive: bool,
		) -> Result<T::Balance, DispatchError> {
			ensure!(amount_in > Zero::zero(), Error::<T>::ZeroAmount);
			if let Some(amount_out_min) = amount_out_min {
				ensure!(amount_out_min > Zero::zero(), Error::<T>::ZeroAmount);
			}

			Self::validate_swap_path(&path)?;
			let path = Self::balance_path_from_amount_in(amount_in, path)?;

			let amount_out = path.last().map(|(_, a)| *a).ok_or(Error::<T>::InvalidPath)?;
			if let Some(amount_out_min) = amount_out_min {
				ensure!(
					amount_out >= amount_out_min,
					Error::<T>::ProvidedMinimumNotSufficientForSwap
				);
			}

			Self::swap(&sender, &path, &send_to, keep_alive)?;

			Self::deposit_event(Event::SwapExecuted {
				who: sender,
				send_to,
				amount_in,
				amount_out,
				path,
			});
			Ok(amount_out)
		}
