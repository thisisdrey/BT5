### Title
`pallet-accumulate-and-forward` reports `ForwardSucceeded` and irreversibly burns treasury funds on local XCM completion, even though remote deposit/settlement can fail and trap the assets permanently - (File: `polkadot/xcm/xcm-builder/src/forwarder.rs`, `substrate/frame/accumulate-and-forward/src/lib.rs`)

### Summary
`TeleportForwarderForAccountId32::forward` teleports accumulated funds to a destination chain and considers the operation successful purely on the basis of *local* XCM-executor completion (`Outcome::Complete`), which only means the local instructions (`WithdrawAsset`, `DescendOrigin`, `InitiateTransfer`) executed without local error. It does not, and structurally cannot, know whether the destination chain actually deposits the assets into the intended beneficiary. `on_idle` in `pallet-accumulate-and-forward` then emits `Event::ForwardSucceeded` and does not retry, treating the funds as delivered. If the remote `DepositAsset` fails on the destination for any reason, the teleported assets are trapped there with, per the code's own comment, "no automatic recovery path," while the source chain has already burned/withdrawn the funds and told the network (`ForwardSucceeded`) that settlement is complete.

### Finding Description
`forward()` in `polkadot/xcm/xcm-builder/src/forwarder.rs` builds an XCM program: `UnpaidExecution → DescendOrigin → WithdrawAsset → InitiateTransfer { remote_xcm: DepositAsset { beneficiary: StagingLocation } }`, executes it locally with `XcmExecutor::prepare_and_execute`, and treats `Outcome::Complete` as final success: [1](#0-0) 

The doc comment on the adapter itself acknowledges the gap: [2](#0-1) 

`Outcome::Complete` only reflects that the *local* leg (withdrawing/teleport-burning funds from the accumulation account and enqueuing the outbound message via `InitiateTransfer`) succeeded — it says nothing about whether the remote `DepositAsset { beneficiary: StagingLocation }` instruction on the destination chain (e.g. Asset Hub) actually deposits the funds to the intended staging account. That remote execution happens asynchronously in a completely separate block/consensus context, after this function has already returned `Ok(())`.

The pallet then treats this local-only success as final settlement: [3](#0-2) 

There is no retry, no re-queue, and no on-chain check tying `ForwardSucceeded` to confirmed remote settlement — the invariant "payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" is broken because settlement on the remote side is never verified before the local state (event + burned funds) advances to "succeeded."

The tests only cover the case where the local `SendXcm` router itself fails before delivery (in which case `with_transaction` correctly rolls everything back): [4](#0-3) 

There is no test, and no code path, that rolls back the local burn if the *destination* rejects the `DepositAsset` (e.g. staging account does not exist/below ED, asset not registered as sufficient/teleportable on that chain at the time of arrival, `Barrier` on the destination rejects `UnpaidExecution` from this origin, XCM version mismatch, or holding/weight limits exceeded on the remote side). Any of those remote failures cause the assets to be trapped at the destination (recorded only as `AssetsTrapped`, claimable in principle but with "no automatic recovery path" per the adapter's own documentation), while the source chain has already irreversibly burned the funds and recorded `ForwardSucceeded`.

This is the direct structural analog of the ThorChain `transferOut()` bug: an operation emits a "success" event/state transition describing the funds as delivered to the intended recipient, while the actual transfer to that recipient can silently fail and the funds end up somewhere else (or nowhere retrievable), with the emitting system having no way to detect or correct the mismatch.

### Impact Explanation
Every parachain wiring `pallet_accumulate_and_forward::Config::Forwarder = xcm_builder::TeleportForwarderForAccountId32<...>` (Westend relay chain, Asset Hub, Bridge Hub, Collectives, Coretime, People — confirmed via their runtime configs) periodically moves pooled DOT/native treasury funds via this mechanism on `on_idle`. Any remote-side failure during the destination's processing of the teleported deposit results in permanent loss of the forwarded funds from the perspective of the source chain's accounting (burned, marked `ForwardSucceeded`, never retried) while the actual funds are stuck as trapped assets on the destination with no automated way back into the accumulate-and-forward accounting/settlement flow. This directly conserves-value violation and duplicate/never-settled payout state matches the "permanent user-fund lock" and "runtime bug that compromise intended behavior" categories in scope.

### Likelihood Explanation
This does not require a malicious peer/relayer/validator/governance actor — it is triggered purely by ordinary asynchronous XCM failure modes on the destination chain (e.g. transient `Barrier` misconfiguration, temporary lack of sufficiency of the asset, staging account reaped below ED, weight-limit exhaustion in the destination's message queue, or XCM version negotiation issues), all of which are realistic operational conditions in a live multi-chain deployment and are entirely outside the sending chain's control or visibility. The `on_idle` hook runs autonomously and repeatedly (every `TransferPeriod`), so this is not a one-off edge case but a systemic gap in every forwarding cycle.

### Recommendation
Do not treat local `Outcome::Complete` as final settlement. Either (a) require a delivery/settlement receipt from the destination (analogous to `pallet_bridge_relayers`'s `DeliveryReceipt` pattern already used elsewhere in this codebase for Snowbridge) before emitting `ForwardSucceeded` and finalizing the local burn, or (b) keep the local funds in an intermediate "in-flight" state that can be reconciled/retried if the remote deposit is later observed to have failed/trapped, or (c) explicitly document and monitor `AssetsTrapped` on the destination and wire an automated claim-back path credited to the accumulation account so failed forwards are not silently permanent losses.

### Proof of Concept
1. Deploy the runtime with `pallet_accumulate_and_forward::Config::Forwarder = TeleportForwarderForAccountId32<...>` pointed at a destination whose `StagingLocation` account is intentionally made non-existent / below ED (or whose `Barrier` rejects `UnpaidExecution` from the teleport-forwarder's derived origin).
2. Fund the accumulation account above `MinTransferAmount` and let a block pass that is a multiple of `TransferPeriod`.
3. Observe `on_idle` invokes `Forwarder::forward`, which calls `XcmExecutor::prepare_and_execute` — locally this returns `Outcome::Complete` since `WithdrawAsset`/`InitiateTransfer` succeed on the source; `forward()` returns `Ok(())`.
4. `Event::ForwardSucceeded { amount }` is deposited and the accumulation account's balance is permanently reduced (teleport burn), per [3](#0-2) .
5. On the destination chain, the enqueued `DepositAsset { beneficiary: StagingLocation }` instruction fails to execute successfully (because the staging account can't receive the asset in that state or the `Barrier` rejects it) — the incoming assets get recorded as `AssetsTrapped` instead of being credited to the staging/buffer account.
6. Result: chain state says the forward succeeded and the funds were "delivered," but the funds are neither in the source accumulation account (burned) nor usable in the destination `pallet_dap` buffer — they sit as trapped assets with no automated recovery, reproducing the ThorChain-style "network believes the transfer succeeded but the real transfer failed" invariant break.
