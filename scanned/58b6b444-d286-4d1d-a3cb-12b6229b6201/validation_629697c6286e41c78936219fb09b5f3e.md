### Title
Manipulable `sellout_price` from a single low-cost core purchase permanently under-prices all coretime renewals for an entire sale period - (File: `substrate/frame/broker/src/tick_impls.rs`)

### Summary
`pallet-broker`'s Bulk Coretime sale uses a Dutch-auction leadin price that decays from a high starting price down to `end_price` over `leadin_length`. The price paid for the very last core sold in a sale period is recorded as `sellout_price` and, via `T::PriceAdapter::adapt_price`, becomes the `target_price` for the *next* sale rotation. That `target_price` is immediately written into every `PotentialRenewalRecord.price` for leases expiring in the upcoming region, fixing the renewal price for the whole following sale period. This is structurally the same defect as the Tokemak `navPerShareHighMark`: a single, cheap, permissionless action performed at a low-liquidity moment locks in an extreme value that is then used to compute payments/fees for an extended period, causing systemic underpricing/loss until the value is naturally recalculated again.

The default `CenterTargetPrice::adapt_price` implementation sets `target_price = sellout_price` verbatim when a sellout occurred:
```rust

    ...

Because the bulk sale price is a Dutch auction that decays from a high value down toward `end_price` over the `leadin_length` (see `leadin_factor_at`), an unprivileged bidder can simply wait near the end of the leadin window — when demand for the last remaining core is low — and purchase it at (or near) the current `end_price`. There is no requirement that multiple independent buyers set the sellout price; a single low-value purchase of the last core is sufficient to set `sellout_price` to the floor value. This single data point is then propagated as `target_price` and locked into every `PotentialRenewalRecord` for leases rolling over into the next sale region, fixing the renewal price for the entire subsequent region (potentially weeks) until the next `rotate_sale` recomputes prices again — and if that following sale is similarly thin, the depressed price can persist across multiple rotations.

This is the same broken invariant as the Tokemak report: a temporary, cheaply-achievable extreme value from a single permissionless action is latched into a state variable (`target_price`/`navPerShareHighMark`) that subsequently governs payments (renewal fees / performance fees) for an extended window, causing the protocol/treasury to under-collect revenue relative to fair market price. `MinimumPrice` (added later per `prdoc/stable2503-6/pr_8630.prdoc`) only clamps `end_price` to a configured floor — it does not prevent `target_price` (the renewal price) from being pinned to an artificially depressed `sellout_price`, nor does it require configuration; runtimes using the plain `CenterTargetPrice` or `()` adapters remain fully exposed. `do_renew` in `dispatchable_impls.rs` charges exactly this locked-in `price` for the renewal with no additional sanity check against market conditions.

### Impact Explanation
Every lease renewal charged during the affected sale period is billed at the manipulated, below-market `target_price`. Because bulk-coretime revenue funds the relay chain/treasury economics, this is a direct, protocol-wide loss of revenue (unbacked discount) that compounds across all renewing tasks for the sale region, not a one-off griefing of a single actor. The attack cost is bounded to the price of exactly one core near the end of the leadin decay, which can be arbitrarily cheap relative to the fair "ideal" price the adapter is supposed to converge toward.

### Likelihood Explanation
The attack requires only a signed extrinsic (purchase call) from any account with enough balance to buy a single core at the depressed end-of-leadin price — no validator, collator, relayer, or governance privilege is needed. Coretime sales with low core counts or thin demand (e.g., new/low-traffic coretime chains, or the tail of any sale where remaining cores are unpopular) make it trivial and cheap for an attacker (or even an unintentional slow bidder) to be the one who buys the very last core near the price floor.

### Recommendation
Do not derive `target_price` (used for renewal pricing) from a single last-sale transaction price. Instead, base `target_price` on a robust statistic of the whole sale (e.g., a time/volume-weighted average of all purchase prices, or the price achieved when reaching `ideal_cores_sold`) so a single cheap purchase cannot dictate the price charged to all other renewing tenants for an entire sale period. Additionally, consider bounding how much `target_price` can move between consecutive sales (a rate limiter, mirroring the `FeeTracker`/`DeliveryFeeFactor` symmetric increase/decrease pattern already used elsewhere in the codebase) rather than adopting the raw sellout price outright.

### Proof of Concept
1. Configure/observe a coretime chain sale with `cores_offered = N` where the last core is unpopular (or attacker waits until only the last core remains).
2. Attacker waits until the Dutch-auction leadin price decays close to `end_price` (a public, deterministic function of elapsed time via `leadin_factor_at`).
3. Attacker calls the bulk purchase extrinsic for the last remaining core at the depressed price; this sets `SaleInfoRecord.sellout_price` to that low value.
4. At the next `rotate_sale` tick, `T::PriceAdapter::adapt_price` computes `target_price = sellout_price` (per `CenterTargetPrice`), and this value is written into `PotentialRenewalRecord.price` for every lease scheduled to renew in the next region (`tick_impls.rs:227-240`).
5. For the duration of the next sale region, all `do_renew` calls for expiring leases are charged this artificially low `target_price`, resulting in systemic under-collection of coretime revenue versus the true market rate — mirroring the Tokemak `navPerShareHighMark` lock-in of a manipulated extreme value that suppresses fee collection until the next natural (and possibly equally manipulable) recalculation.

	fn adapt_price(performance: SalePerformance<Balance>) -> AdaptedPrices<Balance> {

				end_price: performance.end_price,

		let price = FixedU64::from_rational(1, 10).saturating_mul_int(sellout_price);
		let price = if price == Balance::zero() {
			// We could not recover from a price equal 0 ever.
			sellout_price
		} else {
			price
		};

		AdaptedPrices { end_price: price, target_price: sellout_price }
	}
