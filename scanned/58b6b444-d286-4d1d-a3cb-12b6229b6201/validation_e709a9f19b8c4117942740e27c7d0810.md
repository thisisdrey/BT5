## Summary

The polkadot-sdk analog of the "router incompatible with fee-on-transfer tokens" bug class is in `pallet-asset-conversion` (the Substrate DEX/AMM pallet, functionally the "router" equivalent of Uniswap Router02 mentioned in the report). Several of its internal accounting paths trust the *requested* transfer amount rather than the *actual* amount moved by `T::Assets::transfer`, exactly mirroring the GoatRouter flaw. [1](#0-0) 

## Finding Description

`pallet-asset-conversion::credit_swap` resolves a multi-hop swap path by moving the intermediate hop's output directly between pool accounts:

```rust
T::Assets::transfer(
    asset2.clone(),
    &pool_from,
    &pool_to,
    *amount_out,
    Preserve,
)?;
``` [2](#0-1) 

The `?` operator discards the `Result<Balance, DispatchError>` return value of `transfer` — the caller never checks whether `pool_to` actually received `amount_out`. `amount_out` for every hop was pre-computed once, up front, from the pools' reserves via `balance_path_from_amount_in`/`balance_path_from_amount_out`, before any transfers execute.

The same "trust the parameter, not the actual delta" pattern occurs in `do_add_liquidity` and `do_remove_liquidity`:

```rust
T::Assets::transfer(asset1, who, &pool_account, amount1, Preserve)?;
T::Assets::transfer(asset2, who, &pool_account, amount2, Preserve)?;
...
let side1 = Self::mul_div(&amount1, &total_supply, &reserve1)?;
let side2 = Self::mul_div(&amount2, &total_supply, &reserve2)?;
lp_token_amount = side1.min(side2);
``` [3](#0-2) 

LP tokens are minted using the *desired* `amount1`/`amount2`, not the actual amount credited to the pool account. Likewise `do_remove_liquidity` transfers `amount1`/`amount2` out and emits/accounts for those exact figures without validating what `withdraw_to` actually received:

```rust
T::Assets::transfer(asset1, &pool_account, withdraw_to, amount1, Expendable)?;
T::Assets::transfer(asset2, &pool_account, withdraw_to, amount2, Expendable)?;
``` [4](#0-3) 

This is the root cause enabler: the generic default `fungibles::Unbalanced` `transfer` implementation used by `T::Assets` internally calls `decrease_balance`/`increase_balance` with `Precision::BestEffort` yet unconditionally returns `Ok(amount)` — the *requested* amount, not what was actually moved:

```rust
fn transfer(...) -> Result<Self::Balance, DispatchError> {
    ...
    Self::decrease_balance(asset.clone(), source, amount, BestEffort, preservation, Polite)?;
    let _ = Self::increase_balance(asset.clone(), dest, amount, BestEffort);
    Self::done_transfer(asset, source, dest, amount);
    Ok(amount)
}
``` [5](#0-4) 

Notably, the sibling crate `pallet-asset-conversion-ops` (used for pool-account migration) *does* apply the correct defensive pattern that `pallet-asset-conversion` itself omits:

```rust
ensure!(
    balance1 == T::Assets::transfer(asset1.clone(), &prior_account, &new_account, balance1, Preservation::Expendable,)?,
    Error::<T>::PartialTransfer
);
``` [6](#0-5) 

The existence of `Error::<T>::PartialTransfer` in the `ops` crate shows the codebase is aware partial transfers are possible for pluggable `T::Assets`/`T::AssetKind` implementations, yet the core swap/liquidity paths in `pallet-asset-conversion` do not apply the same check.

## Impact Explanation

`T::AssetKind`/`T::Assets` are pallet-config-generic (`Config::Assets: Mutate<...>`, `Config::AssetKind`). Any runtime that plugs in an asset implementation whose `decrease_balance`/`increase_balance` (or a custom `Unbalanced`/`Balanced` implementation) can legitimately move less than the requested amount — e.g. due to holds/freezes interacting with ED enforcement, dust-sweeping on `Expendable` preservation, or a fee/tax-bearing asset type — breaks the AMM's core invariant:
- LP token minting in `do_add_liquidity` is computed from the *desired* deposit amount rather than what the pool account actually received, allowing minting of LP shares not fully backed by pooled assets (dilution/theft of existing LPs).
- The intermediate hop transfer in `credit_swap` silently drops any shortfall; the final leg still attempts to withdraw the originally computed `amount_out` from the last pool, which can either revert (stalling routed swaps) or, combined with rounding/dust behavior, desynchronize a pool's real balance from the invariant used for subsequent pricing.
- `do_remove_liquidity` reports/relies on `amount1`/`amount2` as delivered even if the recipient received less, silently under-delivering funds relative to the burned LP tokens.

This falls under the "Balances, assets, ... treasury spends, ... contract-held value must conserve value and settle exactly once to the rightful beneficiary and amount" pivot.

## Likelihood Explanation

This requires only an unprivileged user creating a pool and performing standard `add_liquidity`/`remove_liquidity`/`swap_exact_tokens_for_tokens` calls against an `AssetKind` whose transfer/deposit path can under-deliver relative to the requested amount — no malicious peer, relayer, governance, or validator behavior is needed. The trigger condition (non-exact `fungibles::Mutate` transfer semantics) is architecturally supported by the generic trait design and by the very existence of the `PartialTransfer` defensive check in the sibling `asset-conversion-ops` crate, indicating the maintainers recognize this failure mode is realistic for pluggable asset types.

## Recommendation

Apply the same discipline used in `pallet-asset-conversion-ops`: capture and validate the `Balance` returned by every `T::Assets::transfer`/`withdraw`/`resolve` call in `do_add_liquidity`, `do_remove_liquidity`, and `credit_swap`, and reject the operation (with a dedicated `PartialTransfer`-style error) whenever the actual amount moved differs from the amount used in LP-token math, swap-output math, or emitted events. Alternatively, switch these internal moves to `Precision::Exact` so any shortfall causes an explicit, safely-rolled-back error rather than silently propagating an incorrect requested-amount assumption.

## Proof of Concept

1. Configure a runtime's `pallet_asset_conversion::Config::Assets`/`AssetKind` such that at least one asset kind's `Unbalanced::decrease_balance`/`increase_balance` (or an overridden `transfer`) can move less than the requested amount under normal conditions (e.g. an asset variant with hold/freeze-driven dust truncation, or any future fee-bearing fungible plugged into the trait).
2. Create a pool for `(NativeAsset, FeeAsset)` and call `add_liquidity` with `amount1_desired`/`amount2_desired`; because `T::Assets::transfer` in `do_add_liquidity` (`substrate/frame/asset-conversion/src/lib.rs:855-856`) doesn't verify the actual amount credited to `pool_account`, LP tokens are minted using the full desired amount even though the pool received less of `FeeAsset`.
3. A second LP then calls `remove_liquidity`; since `reserve1`/`reserve2` are computed from `T::Assets::balance` (`get_reserves`), the pool balance is short relative to outstanding LP token supply, so early LPs can extract disproportionately more value relative to later depositors, or a chained `swap_exact_tokens_for_tokens` through a 3+ asset path fails/desyncs at `credit_swap`'s intermediate `T::Assets::transfer` (`substrate/frame/asset-conversion/src/lib.rs:1208-1214`) when the actual amount received by `pool_to` is less than the `amount_out` used for the next hop's pre-computed math.
