Target: `SignatureSchema::verify_request_msg` for `NoSign` (contracts/wallet/signatures/no-sign/src/lib.rs). Attacker action: deploy/interact with a `wallet-no-sign` variant contract and call `w_execute_signed(msg, proof)` with ANY `msg`/`proof`, expecting `NoSign::verify_request_msg` to always return `false`, but check `WalletImpl::execute_signed`'s early gate `is_signature_allowed()` -> `State::is_signature_allowed` returns `self.signature_enabled || self.extensions.is_empty()`. Preconditions: a `NoSign` wallet initialized via `w_init` sets `s.signature_enabled = false` explicitly but ALSO seeds `extensions=[env::current_account_id()]` (non-empty) per `w_init`. If an attacker can drive `extensions` to become empty transiently without triggering `check_lockout` (e.g. exploiting an execution-order bug across two ops in one `Request.internal` list), `is_signature_allowed()` would flip true, opening `execute_signed`'s nonce/signature gate even though `verify_request_msg` always returns false so no actual bypass occurs downstream. Binding: `is_signature_allowed()==true` implies `SignatureSchema::verify_request_msg` can be satisfied by SOME valid proof, for the `NoSign` schema this must always be impossible. Call sequence: `w_init` -> attempt `w_execute_extension` with `internal=[RemoveExtension{self}]` -> `check_lockout` should reject since `signature_enabled=false` and extensions would become empty. Impact: High — would only matter if `NoSign` combined with a future non-rejecting schema; document as regression guard. Proof idea: cargo test: after `w_init`, attempt `RemoveExtension{account_id: current_account_id}` via `w_execute_extension`, assert `Error::Lockout` and extensions set still contains self.
