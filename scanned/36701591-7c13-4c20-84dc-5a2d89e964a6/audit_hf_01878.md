# [M] mintGenesis() mints with a push pattern using _mint() which may lead to lost tokens

## Summary
Severity: Medium
Contest weight: 0.0554
Dataset id: 10455
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability originates from the mintGenesisfunction using the low‑level _mint operation to create a genesis ERC721 token and directly assign it to a caller‑provided address. Because _mint does not perform the ERC721Receiver check defined by the ERC721 standard, it can transfer a newly minted token to any address, including contracts that do not implement the onERC721Received callback. When such a contract receives the token, the token becomes locked in the contract’s balance because the contract cannot acknowledge or forward ERC721 tokens. This situation is often referred to as an unsafe mint or missing safe‑transfer check. The issue can be exploited by an attacker who supplies a malicious contract address that deliberately lacks the ERC721Receiver interface; the contract will accept the mint request, the token will be recorded in the internal ownership mapping, but the token will be unrecoverable and effectively burned. From a user’s perspective the expected outcome – receiving a visible NFT in their wallet – does not occur; the UI may show a zero balance or the token may be invisible, leading to confusion and the impression that the funds have disappeared. The problem manifests whenever mintGenesis is called with a recipient that is a contract or an address that cannot handle ERC721 tokens, which can happen unintentionally if a user interacts through a smart‑wallet or deliberately if an adversary crafts a malicious address. The affected parties include any user who receives a genesis NFT, the protocol’s accounting logic (because total supply includes tokens that are effectively inaccessible), and the contract owner who may face reputational risk. The flaw was discovered during a manual audit by ThreeSigma, which noted the push‑style minting pattern and the absence of a safe‑mint alternative. It is subtle because the transaction does not revert; the token is minted successfully according to the contract’s state, yet the token is unusable, making the loss hard to detect without inspecting ownership mappings or attempting transfers. To remediate the issue, the contract should replace the direct _mint call with _safeMint, which enforces the ERC721Receiver check and reverts if the recipient cannot handle the token. Alternatively, a claim‑by‑user design using a merkle tree can be employed, allowing each user to pull their own genesis NFT and eliminating the need for the contract to push tokens to arbitrary addresses, while also reducing storage costs. Implementing either approach restores the guarantee that minted NFTs are always receivable, prevents token loss, and aligns the implementation with ERC721 best practices.

## Recommendation
Use a merkle tree to allow users to claim their genesis NFTs. This way, each user is responsible for claiming their NFT correctly. Additionally, it would be much cheaper for the owner of the MetaZeroVortex contract and the isGenesis mapping could be verified against the merkle tree, saving up to 1000 storage writes.
