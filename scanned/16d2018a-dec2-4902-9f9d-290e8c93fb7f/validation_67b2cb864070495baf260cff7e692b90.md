## Summary

The Tapioca bug's core invariant break is: **a cross-chain command was constructed with an asset/amount that did not match what was actually withdrawn/reserved for that transfer**, causing the destination side to act on unbacked or mismatched value. The closest verified local analog is in the Snowbridge V2 outbound message converter, where the `CallContract` command's `value` field (ETH to be forwarded on the Ethereum-side contract call) is taken directly from user-supplied `Transact` calldata **without any check that it is backed by the Ether actually reserved via `WithdrawAsset`/ENA extraction** in the same XCM program.

### Title
Snowbridge V2 outbound converter builds `CallContract` command with unchecked `value`, decoupled from actually reserved Ether — (File: `bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs`)

### Finding Description
`XcmConverter::convert()` in `bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs` builds an outbound `Message` from a user-supplied `Xcm` program executed via `PolkadotXcm::execute` on AssetHub. The flow is:

1. `extract_remote_fee()` validates the `PayFees`/fee `WithdrawAsset` pair is Ether [1](#0-0) .
2. ENA (Ethereum-native asset, e.g. ETH/WETH) and PNA reserves are parsed and converted into `UnlockNativeToken`/`MintForeignToken` commands, each tied to an actual `Asset` amount extracted from `WithdrawAsset`/`ReserveAssetDeposited` [2](#0-1) .
3. Separately, if a `Transact` instruction is present, its encoded calldata is decoded into a `ContractCall::V1 { target, calldata, gas, value }`, and a `Command::CallContract { value, .. }` is pushed **directly from the user-decoded `value` field, with no cross-check against the ENA/PNA amounts extracted above**: [3](#0-2) .

Notably, the error enum defines `CallContractValueInsufficient` [4](#0-3) , but this variant is **never constructed anywhere in `convert()`** — it is dead code, indicating the intended validation (that `value` must be backed by actually-withdrawn/reserved Ether for the transfer) was never implemented in this path.

This is confirmed by the integration test itself, which explicitly flags the gap in a comment while asserting the call currently succeeds regardless: [5](#0-4) 

The test sets `value: 4 * (TOKEN_AMOUNT - REMOTE_FEE_AMOUNT_IN_ETHER) / 5` — an arbitrary value less than the transferred token amount purely by test construction, not because the converter enforces it — and the comment "require validation on BH Exporter" documents that this check is expected but not present.

### Impact Explanation
`Command::CallContract.value` is committed into the merkle-proven outbound message that the Ethereum Gateway contract executes trustlessly (BridgeHub's outbound queue is the sole point where message legitimacy is established before being merkelized and relayed). Because the `value` is decoupled from the ENA amount actually withdrawn/escrowed in the same XCM program, an unprivileged AssetHub-origin actor calling `PolkadotXcm::execute` can craft a `Transact` whose declared `value` exceeds (or is unrelated to) the Ether genuinely reserved for the beneficiary/agent in that message. Depending on how the Ethereum Gateway contract accounts value against per-message escrow, this creates a path to specify a call value not actually backed by locked funds in this message — matching the report's core impact class of "theft or unbacked mint/unlock" and "forged or mis-bound proof/message acceptance," since the BridgeHub-side conversion is the trust boundary that is supposed to bind the committed value to the actually reserved asset and currently does not.

### Likelihood Explanation
High from the local-code perspective: any account can submit an arbitrary `Xcm` program via `pallet_xcm::execute` on AssetHub containing `WithdrawAsset`/`PayFees`/optional ENA-`WithdrawAsset`/`AliasOrigin`/`DepositAsset`/`Transact`/`SetTopic`, which is exactly the syntax `XcmConverter::convert()` expects (as documented in its own doc comment) [6](#0-5) . No privileged origin, relayer, or validator collusion is required — this is a pure unprivileged, public-entrypoint path (`pallet_xcm::execute`), matching the "public wrappers must not undercharge nested execution" pivot.

### Recommendation
In `XcmConverter::convert()`, before pushing `Command::CallContract`, enforce that the decoded `value` does not exceed the sum of ENA amounts (in Ether, i.e. the `H160([0;20])`-token entries) that were actually extracted for the same `recipient`/agent in `extract_ethereum_native_assets`, returning `CallContractValueInsufficient` (already defined but unused) when the check fails. This restores the intended invariant that the committed value is always backed 1:1 by assets withdrawn within the same message.

### Proof of Concept
1. On AssetHub, call `PolkadotXcm::execute` (unprivileged, any signed account) with an XCM program of the form:
```
WithdrawAsset(ETH_FEE)
PayFees { asset: ETH_FEE }
WithdrawAsset(ENA: small amount, e.g. 1)
AliasOrigin(caller_location)
DepositAsset { assets: All, beneficiary: agent }
Transact { call: ContractCall::V1 { target, calldata, gas, value: LARGE_VALUE } }
SetTopic(topic)
```
2. `extract_ethereum_native_assets` produces `UnlockNativeToken { amount: 1, .. }` for the small ENA amount.
3. The `Transact` branch decodes `ContractCall::V1` and pushes `Command::CallContract { value: LARGE_VALUE, .. }` with **no comparison** to the `1`-unit ENA actually reserved [3](#0-2) .
4. `OutboundQueue::validate` and `deliver` accept the message as constructed; the mismatch between the declared `value` and the actually-reserved Ether is never checked or rejected locally, confirmed by the existence of an unused `CallContractValueInsufficient` error variant meant for exactly this case.

	/// Extract the fee asset item from PayFees(V5)
	fn extract_remote_fee(&mut self) -> Result<u128, XcmConverterError> {
		use XcmConverterError::*;
		let reserved_fee_assets = match_expression!(self.next()?, WithdrawAsset(fee), fee)
			.ok_or(WithdrawAssetExpected)?;
		ensure!(reserved_fee_assets.len() == 1, AssetResolutionFailed);
		let reserved_fee_asset =
			reserved_fee_assets.inner().first().cloned().ok_or(AssetResolutionFailed)?;
		let (reserved_fee_asset_id, reserved_fee_amount) = match reserved_fee_asset {
			Asset { id: asset_id, fun: Fungible(amount) } => Ok((asset_id, amount)),
			_ => Err(AssetResolutionFailed),
		}?;
		let fee_asset =
			match_expression!(self.next()?, PayFees { asset: fee }, fee).ok_or(InvalidFeeAsset)?;
		let (fee_asset_id, fee_amount) = match fee_asset {
			Asset { id: asset_id, fun: Fungible(amount) } => Ok((asset_id, *amount)),
			_ => Err(AssetResolutionFailed),
		}?;
		// Check the fee asset is Ether (XCM is evaluated in Ethereum context).
		ensure!(fee_asset_id.0 == Here.into(), InvalidFeeAsset);
		ensure!(reserved_fee_asset_id.0 == Here.into(), InvalidFeeAsset);
		ensure!(reserved_fee_amount >= fee_amount, InvalidFeeAsset);
		Ok(fee_amount)
	}

	/// Extract ethereum native assets
	fn extract_ethereum_native_assets(
		&mut self,
		enas: &Assets,
		deposit_assets: &AssetFilter,
		recipient: H160,
	) -> Result<Vec<Command>, XcmConverterError> {
		let mut commands: Vec<Command> = Vec::new();
		for ena in enas.clone().into_inner().into_iter() {
			// Check the the deposit asset filter matches what was reserved.
			if !deposit_assets.matches(&ena) {
				return Err(FilterDoesNotConsumeAllAssets);
			}

			// only fungible asset is allowed
			let (token, amount) = match ena {
				Asset { id: AssetId(inner_location), fun: Fungible(amount) } => {
					match inner_location.unpack() {
						(0, [AccountKey20 { network, key }]) if self.network_matches(network) => {
							Ok((H160(*key), amount))
						},
						// To allow ether
						(0, []) => Ok((H160([0; 20]), amount)),
						_ => Err(AssetResolutionFailed),
					}
				},
				_ => Err(AssetResolutionFailed),
			}?;

			// transfer amount must be greater than 0.
			ensure!(amount > 0, ZeroAssetTransfer);

			commands.push(Command::UnlockNativeToken { token, recipient, amount });
		}
		Ok(commands)
	}

	/// Extract polkadot native assets
	fn extract_polkadot_native_assets(
		&mut self,
		pnas: &Assets,
		deposit_assets: &AssetFilter,
		recipient: H160,
	) -> Result<Vec<Command>, XcmConverterError> {
		let mut commands: Vec<Command> = Vec::new();
		ensure!(pnas.len() > 0, NoReserveAssets);
		for pna in pnas.clone().into_inner().into_iter() {
			if !deposit_assets.matches(&pna) {
				return Err(FilterDoesNotConsumeAllAssets);
			}

			// Only fungible is allowed
			let Asset { id: AssetId(asset_id), fun: Fungible(amount) } = pna else {
				return Err(AssetResolutionFailed);
			};

			// transfer amount must be greater than 0.
			ensure!(amount > 0, ZeroAssetTransfer);

			// Ensure PNA already registered
			let token_id = TokenIdOf::convert_location(&asset_id).ok_or(InvalidAsset)?;
			let expected_asset_id = ConvertAssetId::maybe_convert(token_id).ok_or(InvalidAsset)?;
			ensure!(asset_id == expected_asset_id, InvalidAsset);

			commands.push(Command::MintForeignToken { token_id, recipient, amount });
		}
		Ok(commands)
	}
