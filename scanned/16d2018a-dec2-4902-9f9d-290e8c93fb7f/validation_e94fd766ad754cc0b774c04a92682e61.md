## Analysis: Locked accumulation-account funds analog to `BatonLaunchpad`'s unwithdrawable protocol fee

### Title
Accumulated protocol-level fees/revenue in `pallet-accumulate-and-forward`'s accumulation account have no manual/governance withdrawal or retry path if the automated `on_idle` forward stalls - (File: `substrate/frame/accumulate-and-forward/src/lib.rs`)

### Summary
The external report's core invariant break is: *value is routed into a contract-owned balance, but the contract exposes no function to move that value back out, so it is permanently stranded.* The local analog is `pallet-accumulate-and-forward`, which redirects transaction fees, dust removal, and coretime revenue into a pallet-derived `accumulation_account` [1](#0-0) . The only exit for these funds is the automatic `on_idle` hook, gated by a periodic block-number modulus and a weight budget check [2](#0-1) . The pallet defines no `#[pallet::call]` extrinsics at all, so there is no owner-, root-, or governance-triggered call to sweep, retry, or redirect the accumulation account's balance if the automated forward path stalls or is misconfigured.

### Finding Description
Fees and revenue are deposited into the accumulation account via `OnUnbalanced::on_nonzero_unbalanced`, which resolves the credit directly into the derived account [3](#0-2) . Movement out of that account happens exclusively inside `on_idle`:
- It only executes when `block % TransferPeriod == 0` [4](#0-3) .
- It requires enough `remaining_weight` to cover both a storage read and `T::WeightInfo::send_native()`; if the idle weight budget is insufficient on a given attempt, it returns early with no automatic follow-up attempt until the next period boundary [5](#0-4) .
- On failure of `T::Forwarder::forward`, the pallet simply emits `ForwardFailed` and leaves the balance untouched, to be retried at the next period [6](#0-5) .

The concrete `Forwarder` used in runtimes, `TeleportForwarderForAccountId32`, explicitly documents that this design has no recovery path once the executor's local prepare step fails or once assets are trapped remotely: *"Once the local executor reports success, the message is queued and any destination-side rejection results in trapped assets at the destination with no automatic recovery path."* and it is deliberately restricted to being called "only from rate-limited internal hooks such as `on_idle`" and "should never be wired to user-callable extrinsics" [7](#0-6) . On a local `prepare_and_execute` failure, the whole attempt is rolled back and the source funds remain in the accumulation account [8](#0-7) .

The exact corrupted/stranded value is the free balance of `Pallet::<T>::accumulation_account()` (`T::PalletId::get().into_account_truncating()`), which is deliberately not attributable to, or reachable by, any single depositor [1](#0-0) . Existing guards (`MinTransferAmount`, `TransferPeriod`, weight metering, `Rollback` on XCM failure) only govern *when* an automatic attempt is made — none of them provide a fallback mechanism if the destination/route is persistently unreachable (e.g. `Dest`, `NativeAsset`, or `StagingLocation` misconfigured, destination chain rejecting the teleport, or the destination account/filter permanently rejecting `DepositAsset`). In that state the funds accumulate in the pallet account indefinitely because, like `BatonLaunchpad`, there is no exposed withdrawal/sweep entry point anywhere in the pallet.

### Impact Explanation
This is a permanent protocol-fund lock: system-parachain transaction fees, dust, and coretime revenue accumulate in a pallet-controlled account with no code path to recover them if the automated forwarding mechanism cannot succeed. Given this pallet is wired into `polkadot/runtime/westend`, `bridge-hub-westend`, `collectives-westend`, `coretime-westend`, and `people-westend` [9](#0-8) , an unrecoverable forwarding stall directly represents unbacked, unclaimable protocol revenue across multiple system chains — matching "permanent user-fund or bridge-state lock" in the impact gate.

### Likelihood Explanation
Likelihood is moderate to high because the forward path depends on cross-chain XCM teleport success and on-idle weight availability every period; any persistent misrouting (e.g. a `StagingLocation`/beneficiary that the destination filters reject, or a destination-side asset-trust change) will silently and permanently strand funds with only a `ForwardFailed` event as the observable symptom, and there is no built-in fallback for an operator to react with on-chain.

### Recommendation
Add a privileged (root/governance-gated) extrinsic to `pallet-accumulate-and-forward` that allows forcing/retrying a forward with an explicit destination override, or allows sweeping the accumulation account balance to a specified beneficiary, so operators are not solely dependent on the automatic `on_idle` retry loop succeeding against the originally configured `Forwarder`.

### Proof of Concept
1. Deploy a runtime with `pallet-accumulate-and-forward` configured with `TeleportForwarderForAccountId32` pointing at a `Dest`/`StagingLocation` that becomes unreachable or whose remote `DepositAsset` is rejected (e.g., destination account is later filtered/removed, or teleport trust is revoked).
2. Let normal operation accrue tx-fee/dust/coretime credits into the accumulation account via `OnUnbalanced::on_nonzero_unbalanced` [3](#0-2) .
3. Each `TransferPeriod` boundary, `on_idle` invokes `Forwarder::forward`; because the destination path is broken, `prepare_and_execute` fails, `TransactionOutcome::Rollback` is returned, and `Event::ForwardFailed` fires while the balance remains untouched [6](#0-5) .
4. Repeat indefinitely: since there is no `#[pallet::call]` extrinsic in the pallet, no root/governance action, user transaction, or any other on-chain call can move the accumulated balance out — funds are permanently locked, directly analogous to ETH being stuck in `BatonLaunchpad` with no `withdraw()`.

	impl<T: Config> Hooks<SystemBlockNumberFor<T>> for Pallet<T> {
		fn on_idle(_block: SystemBlockNumberFor<T>, remaining_weight: Weight) -> Weight {
			// Only attempt forwarding on blocks that are exact multiples of `TransferPeriod`.
			let block = T::BlockNumberProvider::current_block_number();
			if (block % T::TransferPeriod::get()) != Zero::zero() {
				return Weight::zero();
			}

			let mut meter = WeightMeter::with_limit(remaining_weight);

			// Need one read for the balance check.
			if meter.try_consume(T::DbWeight::get().reads(1)).is_err() {
				return meter.consumed();
			}

			let accumulation_account = Self::accumulation_account();
			// We use `reducible_balance` with `Preservation::Preserve` to get the
			// usable balance (excluding the ED).
			let available_funds = T::Currency::reducible_balance(
				&accumulation_account,
				Preservation::Preserve,
				Fortitude::Polite,
			);

			if available_funds < T::MinTransferAmount::get() {
				return meter.consumed();
			}

			// Ensure there is enough weight budget for the full XCM send.
			if meter.try_consume(T::WeightInfo::send_native()).is_err() {
				return meter.consumed();
			}

impl<T: Config> OnUnbalanced<CreditOf<T>> for Pallet<T> {
	fn on_nonzero_unbalanced(amount: CreditOf<T>) {
		let accumulation_account = Self::accumulation_account();
		let numeric_amount = amount.peek();

		// Resolve should never fail because:
		// - can_deposit on destination succeeds assuming accumulation account is pre-funded with ED
		// - amount is guaranteed non-zero by the trait method signature
		// The only failure would be overflow on destination or unfunded account.
		let _ = T::Currency::resolve(&accumulation_account, amount).inspect_err(|_| {
			frame_support::defensive!(
				"🚨 Failed to deposit to accumulation account - funds burned, it should never happen!"
			);
		});

		log::debug!(
			target: LOG_TARGET,
			"💸 Deposited {numeric_amount:?} to accumulation account"
		);
	}
