In `stackslib/src/net/mod.rs`, `StacksNodeState::load_stacks_chain_tip` for `TipRequest::UseLatestUnconfirmedTip` first tries `chainstate.unconfirmed_state.get_unconfirmed_state_if_exists()` and, per the documented '# Warn' comment, has 'a potential race condition' where the unconfirmed tip 'may get invalidated by the time it is used in `maybe_read_only_clarity_tx`'. Can a remote caller repeatedly issue `tip=latest` requests to `callreadonly`/`getmapentry`/`getdatavar` timed around microblock/tenure-tip transitions so that `load_stacks_chain_tip` returns an unconfirmed `StacksBlockId` that becomes stale (no longer the tip) by the time `chainstate.maybe_read_only_clarity_tx(&sortdb.index_handle_at_block(chainstate, &tip)?, &tip, ...)` executes, causing either a spurious 404 ('Chain tip not found') for an otherwise-valid request, or — worse — a read served against a tip that has since been superseded, silently returning DATA FROM A BLOCK THE NODE NO LONGER CONSIDERS ITS LATEST UNCONFIRMED STATE while the caller believes they got 'latest'? Equality broken: state served for `tip=latest` == the node's unconfirmed tip AT RESPONSE TIME, not at a stale snapshot taken before the read. Impact: High — served-vs-committed race exploitable by an attacker who can influence microblock/tenure timing (their own transactions) to harvest stale-vs-fresh discrepancies. Proof idea: `stackslib::net::api::tests::mod` test racing a chain-tip-changing operation against a `load_stacks_chain_tip(UseLatestUnconfirmedTip)` call, asserting the returned tip id matches `chainstate.unconfirmed_state` at the moment `maybe_read_only_clarity_tx` actually executes.
