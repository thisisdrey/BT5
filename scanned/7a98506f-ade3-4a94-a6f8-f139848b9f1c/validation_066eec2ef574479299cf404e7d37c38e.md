### Title
`pallet_oracle` aggregated values can become stale and are served without freshness enforcement - (`substrate/frame/honzon/oracle/src/lib.rs`)

### Summary
The oracle pallet stores raw operator submissions as `TimestampedValue { value, timestamp }` and aggregates them through `DefaultCombineData`, but the public read paths `Pallet::get` and `DataProvider::get` return the cached `Values` entry without verifying that its `timestamp` is still within `ExpiresIn`. [1](#0-0) [2](#0-1) [3](#0-2)  When fresh operator feeds dry up, `DefaultCombineData` filters out the expired raw values and falls back to the previous aggregate, so `Values` can be older than the configured tolerance yet continue to be served as the current price. [4](#0-3)  This is the local equivalent of the Chainlink `latestRoundData` stale-result bug: a timestamp exists but is not enforced on the value returned to consumers.

### Finding Description
`feed_values` records each submission with `T::Time::now()` and then calls `combined` to update `Values`. [5](#0-4)  `combined` invokes `T::CombineData::combine_data(..., Self::values(key))`, passing the previous aggregate as the fallback value. [6](#0-5)  `DefaultCombineData::combine_data` drops raw values whose `timestamp + ExpiresIn <= now`, but if too few fresh values remain it returns `prev_value` unchanged. [4](#0-3)  `Pallet::get` returns `Self::values(key)` directly, and `DataProvider::get` strips the `timestamp` and returns only the `value`. [2](#0-1) [3](#0-2)  No read path checks `Values[key].timestamp + ExpiresIn > now`, so a stale aggregate can be returned indefinitely. [2](#0-1) [3](#0-2) 

### Impact Explanation
Any runtime pallet that consumes the oracle through `DataProvider::get` (or `Pallet::get` and ignores the returned `timestamp`) would act on an outdated price for collateral valuation, liquidations, fee conversions, or asset accounting. [3](#0-2)  Depending on the consumer, this can lead to wrong beneficiary or amount, unbacked mint or unlock, or fund loss. The node runtime already wires `pallet_oracle` with `DefaultCombineData<Self, ConstU32<5>, ConstU64<3600>>`, so the stale-price window is governed by that 3600-moment tolerance but is not closed by the read API. [7](#0-6) 

### Likelihood Explanation
The stale state is reached as soon as fewer than `MinimumCount` operators submit fresh values within `ExpiresIn`. [4](#0-3)  This can happen if operators go offline, are removed via `change_members_sorted`, or simply stop feeding. [8](#0-7)  Once `Values` is stale, every subsequent `get` call returns it, and any permissionless extrinsic that reads the oracle can act on the stale price. [2](#0-1) [3](#0-2)  The fallback to `prev_value` is explicit in `DefaultCombineData`, and the absence of a read-side age check makes the condition persistent. [9](#0-8) [3](#0-2) 

### Recommendation
Enforce freshness at the read boundary. `Pallet::get` and `DataProvider::get` should return `None` when `Values[key].timestamp + ExpiresIn <= T::Time::now()`. [2](#0-1) [3](#0-2)  Alternatively, keep timestamped access through `DataProviderExtended` and require callers to validate `timestamp`, or add a `MaxAge` config and reject stale reads. In `DefaultCombineData`, do not return `prev_value` if `prev_value.timestamp + ExpiresIn <= now`; return `None` so `Values` is not refreshed with stale data. [10](#0-9) 

### Proof of Concept
1. Three oracle members feed price `100` at block time `t0`. `do_feed_values` stores each raw value with timestamp `t0` and `combined` writes `Values[key] = TimestampedValue { value: 100, timestamp: t0 }`. [5](#0-4) [6](#0-5) 
2. Block time advances to `t0 + 3601`, past the runtime `ExpiresIn` of `3600`, and no new feeds arrive. [7](#0-6) 
3. A caller invokes `Pallet::get(key)`. `combined` reads the raw values, `DefaultCombineData` filters them all out because `t0 + 3600 <= t0 + 3601`, and `count < MinimumCount`, so it returns `prev_value` (the stale `Values` entry). [4](#0-3) 
4. `Pallet::get` returns `Some(TimestampedValue { value: 100, timestamp: t0 })`. [2](#0-1) 
5. `DataProvider::get` returns `Some(100)`, giving downstream code a price that is 3601 moments old with no revert or `None`. [3](#0-2) 
6. A downstream liquidation, conversion, or treasury/asset-accounting extrinsic executes against `100`, producing wrong payouts or unbacked positions. [3](#0-2)

```rust
	fn do_feed_values(who: T::AccountId, values: Vec<(T::OracleKey, T::OracleValue)>) {
		let now = T::Time::now();
		for (key, value) in &values {
			let timestamped = TimestampedValue { value: value.clone(), timestamp: now };
			RawValues::<T, I>::insert(&who, key, timestamped);

			// Update `Values` storage if `combined` yielded result.
			if let Some(combined) = Self::combined(key) {
				<Values<T, I>>::insert(key, combined);
			}

			T::OnNewData::on_new_data(&who, key, value);
		}
		Self::deposit_event(Event::NewFeedData { sender: who, values });
	}
```

```rust
	fn combine_data(
		_key: &<T as Config<I>>::OracleKey,
		mut values: Vec<TimestampedValueOf<T, I>>,
		prev_value: Option<TimestampedValueOf<T, I>>,
	) -> Option<TimestampedValueOf<T, I>> {
		let expires_in = ExpiresIn::get();
		let now = T::Time::now();

		values.retain(|x| x.timestamp.saturating_add(expires_in) > now);

		let count = values.len() as u32;
		let minimum_count = MinimumCount::get();
		if count < minimum_count || count == 0 {
			return prev_value;
		}
```
