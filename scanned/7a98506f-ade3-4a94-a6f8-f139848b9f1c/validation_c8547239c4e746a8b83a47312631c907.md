### Title
`ERC20Transactor` treats successful (but non-standard) ERC20 transfers as failed, causing permanent loss/lock of user funds - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
This is the local analog of the reported `usdt.approve`/`ERC20.approve` return-data mismatch bug. Instead of Solidity's automatic return-size check reverting a call, the polkadot-sdk `ERC20Transactor` (used to bridge XCM `TransactAsset` operations to ERC20 contracts hosted on `pallet-revive`) manually decodes the `transfer()` return value with `IERC20::transferCall::abi_decode_returns_validate`, and unconditionally errors out the whole XCM operation whenever that decode fails - even though the underlying EVM call already executed and moved the tokens.

### Finding Description
`withdraw_asset_with_surplus` and `deposit_asset_with_surplus` call an ERC20 contract's `transfer()` via `pallet_revive::Pallet::<T>::bare_call` and then branch on the outcome: [1](#0-0) 

The code only checks `return_value.did_revert()` for failure. If the call did *not* revert, it unconditionally tries to strictly ABI-decode the return data as a `bool` via `abi_decode_returns_validate`. Any ERC20 contract that implements `transfer(address,uint256)` without returning a `bool` (the same real-world non-conformance class as mainnet USDT's `approve`, cited in the external report) will produce zero-length return data. `did_revert()` is `false` (the EVM call succeeded and the token balance actually moved), but `abi_decode_returns_validate` fails to decode, so the code returns `Err(FailedToTransactAsset("ERC20 contract result couldn't decode"))`: [2](#0-1) 

The identical pattern exists in `deposit_asset_with_surplus`: [3](#0-2) 

The corrupted value is the boolean XCM/Rust-level "did this asset transfer succeed" signal returned to the XCM executor: it is derived purely from the ABI-decodability of the return payload, not from whether the on-chain ERC20 state actually changed. This breaks the required invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" — here decode failure is reported as settlement failure while dispatch/execution/settlement (the real ERC20 `_transfer`) already succeeded.

### Impact Explanation
- In `withdraw_asset_with_surplus`, the transfer from `who` to `TransfersCheckingAccount` (source-side escrow) has already executed on the EVM side (tokens are now custodied by `TransfersCheckingAccount`), but the function returns `Err`, so the XCM executor believes the withdrawal never happened. No compensating transfer back to `who` occurs. The user's ERC20 balance is now permanently stuck in `TransfersCheckingAccount` while the rest of the XCM program (mint of a foreign representation, bridge message, etc.) is aborted — a **permanent user-fund lock**.
- In `deposit_asset_with_surplus`, the transfer from `TransfersCheckingAccount` to the beneficiary has already executed (tokens are in the beneficiary's ERC20 balance), but the function returns `Err((what, ...))`. The XCM executor treats the `AssetsInHolding` as still undelivered and will trap them via the asset trap mechanism. This produces a state where the real ERC20 balance shows the funds delivered to the beneficiary, while the runtime's XCM asset-trap bookkeeping simultaneously records the same value as "trapped" and reclaimable — a **duplicate settlement** primitive: the beneficiary can receive the tokens twice (once via the actual `_transfer`, once via a legitimate `claim_assets` on the trapped record).
- This impacts any ERC20 asset registered for `ERC20Transactor` that does not strictly return a `bool` from `transfer` (mirroring the widely-deployed non-conformant token pattern the external report is about), which is common enough in real-world tokens that this is not a contrived edge case.

### Likelihood Explanation
No privileged actor, governance action, or malicious relayer/validator is required. Any unprivileged user performing an ordinary reserve-transfer/XCM operation involving a non-standard ERC20 asset (transfer without boolean return, the exact same real-world class as mainnet USDT referenced in the seed report) triggers this path deterministically on every transfer — it is not probabilistic or reliant on adversarial timing. The bug is purely in this transactor's response-decoding logic, independent of `pallet-revive`'s or the ERC20 contract's own correctness.

### Recommendation
Do not require a strictly ABI-decodable return value to treat the ERC20 operation as successful. Mirror the widely used `safeTransfer`/`safeApprove` pattern: treat a non-reverted call as success when the return data is either empty or decodes to `true`, and only treat non-reverted-but-explicitly-`false` return data as failure. Concretely, change the decode branch in both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` to accept `return_value.data.is_empty()` as success rather than routing it through `abi_decode_returns_validate`'s error branch.

### Proof of Concept
1. Deploy (or register via the configured `Matcher`) an ERC20 contract on `pallet-revive` whose `transfer(address,uint256)` performs the transfer but returns no data, e.g.:
```solidity
function transfer(address to, uint256 value) public {
    _transfer(msg.sender, to, value);
    // no return value, like mainnet USDT
}
```
2. Initiate an XCM operation that routes through `ERC20Transactor::withdraw_asset_with_surplus` for this asset (e.g., a reserve-transfer originated by an ordinary user).
3. Observe: the internal `bare_call` to `transfer` succeeds (`did_revert() == false`), the ERC20 balance moves from `who` to `TransfersCheckingAccount` (verifiable on-chain), but `IERC20::transferCall::abi_decode_returns_validate(&return_value.data)` fails on the empty return data, so `withdraw_asset_with_surplus` returns `Err(XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode"))`, aborting the XCM program with the user's tokens now stuck in `TransfersCheckingAccount` and unrecoverable through the normal flow.
