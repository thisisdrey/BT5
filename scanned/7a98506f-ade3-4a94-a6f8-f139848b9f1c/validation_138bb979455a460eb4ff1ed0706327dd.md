### Title
`pallet-oracle`'s `DataProvider` interface silently strips timestamps, letting consumers act on stale or zero-value price data with no freshness/heartbeat validation - ([File: substrate/frame/honzon/oracle/src/lib.rs])

### Summary
The external report's core broken invariant is: a price-feed consumer trusts oracle output without validating that the value is non-zero and fresh (per-asset heartbeat), and without handling feed/sequencer downtime. The direct local analog is Polkadot SDK's new `pallet-oracle` (added for the AssetHub stablecoin effort, PR referencing #9765), which is architecturally the Chainlink-style price-feed component of this codebase. Its public consumption interface (`DataProvider::get`) discards the timestamp that the pallet itself maintains, and neither the pallet nor its default aggregation logic enforces a "value > 0" or "freshness within heartbeat" check before a value is aggregated into `Values` and handed to consuming pallets.

### Finding Description
`pallet-oracle` stores each operator's submission with a timestamp: [1](#0-0) 

`do_feed_values` timestamps and stores `RawValues`, then immediately tries to aggregate via `T::CombineData::combine_data` and write the result into the public `Values` storage — with no validation that the value is non-zero, no rejection of duplicate/very-old raw values, and no per-key ("per-heartbeat") freshness gate before publishing.

The aggregated, "trusted" value is exposed to consumers through two paths: [2](#0-1) 

and, critically, through the `DataProvider` trait implementation that most consuming pallets are expected to use (per the pallet's own README: "other pallets can use the `DataProvider` trait to read the aggregated data"): [3](#0-2) 

`DataProvider::get` unwraps the `TimestampedValue` and returns only `.value`, throwing away `.timestamp`. Any consumer pallet coded against the generic `DataProvider<Key, Value>` trait (the intended, documented integration point) has no way to detect that a value is stale — the freshness metadata simply isn't in the type it receives. This mirrors exactly the Chainlink bug pattern: staleness data exists somewhere upstream (Chainlink's `updatedAt` / this pallet's `timestamp`) but the consuming contract/pallet path that actually gets used doesn't check it.

Compounding this, there is no built-in "price > 0" guard anywhere in the feed/aggregate/read path — `T::OracleValue` is a generic `Parameter + Member + Ord + MaxEncodedLen` with no numeric floor check, and `DefaultCombineData` (median-based combination) computes a median over whatever raw values exist, including a submitted `0`, without rejecting it. There is also no equivalent of Chainlink's L2 sequencer-uptime / `GRACE_PERIOD` concept: nothing in `feed_values`/`do_feed_values`/`on_finalize` (`HasDispatched` is only for anti-spam, one-feed-per-block) accounts for a data source being degraded or delayed — a stale value simply continues to sit in `Values` indefinitely and is returned by `get()`/`DataProvider::get()` with no expiry.

### Impact Explanation
Because `pallet-oracle` is explicitly designed to feed price data to other consuming pallets/pallets-in-runtime (stablecoin minting/redemption, collateral valuation, liquidation triggers, etc., per the pallet's stated purpose), any consumer that follows the documented `DataProvider` integration path is architecturally blind to staleness and to zero/invalid values. This can cause: minting or redemption at a wrong (stale or zero) exchange rate, incorrect collateral valuation, or improper liquidation/settlement decisions — i.e., exactly the "runtime bugs that compromise intended behavior" and "theft or unbacked mint" classes the impact gate targets, once a consumer pallet is wired to `DataProvider::get()` (the pallet is currently new/kitchensink-only, but is the sanctioned integration surface for the stablecoin work referenced in the PRDoc).

### Likelihood Explanation
Likelihood is Low-to-Medium standalone (no consumer pallet is fully wired into a production runtime yet in this snapshot), but the vulnerability is structural rather than incidental: the trait signature itself (`DataProvider<Key, Value>` returning bare `Value`) guarantees that any well-behaved, spec-compliant consumer written against the documented interface cannot access the timestamp to defend itself, and no validation is enforced pallet-side either. This is not a misuse bug in a specific consumer — it is a systemic lack of validation baked into the oracle primitive itself, which is the same root cause class flagged in the external report (validation missing at the data-source boundary, not in a single caller).

### Recommendation
- Add a staleness/heartbeat check inside `pallet-oracle` itself (e.g., reject aggregation results, or have `get`/`DataProvider::get` return `None`, when `now - timestamp` exceeds a per-`OracleKey`-configurable heartbeat), rather than relying on every downstream consumer to reimplement this from `TimestampedValue`.
- Add a "value must be non-zero/non-negative-sentinel" guard in `do_feed_values`/`DefaultCombineData` before writing to `Values`.
- Change the primary recommended integration surface so consumers receive the `TimestampedValue` (or an explicit staleness-checked wrapper) instead of the bare `Value` via `DataProvider::get`, or clearly document/enforce that all consumers must use `DataProviderExtended`/`get_all_values` plus an explicit timestamp check before trusting a price.
- Introduce a feed-degradation/circuit-breaker concept analogous to Chainlink's sequencer grace period (e.g., halt consumption or mark values suspect if all operators stop feeding for N blocks) rather than allowing an old aggregated value to persist and be served indefinitely.

### Proof of Concept
1. Register oracle members and call `feed_values` with a valid price for key `K` at block/time `T0`; `Values::<T>::get(K)` is populated via `combined()`.
2. Advance chain time far beyond any reasonable freshness window without any operator calling `feed_values` again (feeding is optional/voluntary — nothing forces refreshes; `HasDispatched` only rate-limits, it never expires stored values).
3. A consumer pallet wired via `DataProvider<T::OracleKey, T::OracleValue>::get(&K)` (the pallet's documented integration path) still receives the old value from step 1 with no error and no way to know it's stale, because `DataProvider::get` at `substrate/frame/honzon/oracle/src/lib.rs:449-453` discards `TimestampedValue.timestamp`.
4. Separately, an operator can call `feed_values(vec![(K, 0)])`; if it becomes (or contributes to) the median via `DefaultCombineData`, `Values::<T>::get(K)` can hold `0`, and `DataProvider::get(&K)` will happily return `Some(0)` to any consumer with no rejection — matching the "missing validation for price > 0" bug class from the external report one-to-one.

	fn do_feed_values(who: T::AccountId, values: Vec<(T::OracleKey, T::OracleValue)>) {
		let now = T::Time::now();
		for (key, value) in &values {
			let timestamped = TimestampedValue { value: value.clone(), timestamp: now };
			RawValues::<T, I>::insert(&who, key, timestamped);

			// Update `Values` storage if `combined` yielded result.
			if let Some(combined) = Self::combined(key) {
				<Values<T, I>>::insert(key, combined);
			}

			T::OnNewData::on_new_data(&who, key, value);
		}
		Self::deposit_event(Event::NewFeedData { sender: who, values });
	}
