### Title
Bounty and child-bounty claims silently drop payouts on transfer failure while still finalizing state, causing permanent fund loss - (File: `substrate/frame/bounties/src/lib.rs`, `substrate/frame/child-bounties/src/lib.rs`)

### Summary
`claim_bounty` in `pallet-bounties` and `claim_child_bounty` in `pallet-child-bounties` pay the curator fee and the beneficiary payout using `T::Currency::transfer(..., AllowDeath)` and only guard the result with `debug_assert!(res.is_ok())` instead of propagating the error. `debug_assert!` is compiled out in release/production builds, so if either transfer fails, execution continues unconditionally: the bounty/child-bounty record is deleted and a `Claimed`/`BountyClaimed` event is emitted as if payment succeeded, even though no funds moved. This is the mirror image of the reported `ERC314Factory.claimFees` bug: instead of one team's failed transfer *reverting* the whole payout (blocking the other team), here a failed transfer is *silently ignored* and the protocol still finalizes settlement — permanently losing/locking the funds that were supposed to be paid.

### Finding Description
In `claim_bounty`:
```rust
// substrate/frame/bounties/src/lib.rs:820-827
let res = T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath); // should not fail
debug_assert!(res.is_ok());
let res = T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath); // should not fail
debug_assert!(res.is_ok());

*maybe_bounty = None;
``` [1](#0-0) 

And in `claim_child_bounty`:
```rust
// substrate/frame/child-bounties/src/lib.rs:726-744
let fee_transfer_result = T::Currency::transfer(&child_bounty_account, curator, curator_fee, AllowDeath);
debug_assert!(fee_transfer_result.is_ok());

let payout_transfer_result = T::Currency::transfer(&child_bounty_account, beneficiary, payout, AllowDeath);
debug_assert!(payout_transfer_result.is_ok());
``` [2](#0-1) 

In both dispatchables, after these transfer attempts the code unconditionally removes the bounty/child-bounty storage entry (`*maybe_bounty = None`) and deposits a "Claimed" event, without checking whether the transfer actually succeeded. `debug_assert!` has no effect in a release/production runtime build (which is how live chains are compiled), so a failed transfer is completely swallowed.

`T::Currency::transfer` can legitimately fail even with `AllowDeath` on the *source* (bounty account) if the *destination* account does not yet exist and the amount transferred is below `ExistentialDeposit` — a very plausible situation:
- `curator_fee`/`final_fee` is set by the curator via `propose_curator`/`accept_curator` fee value and can be arbitrarily small (there is no minimum-fee-vs-ED check in the pallet).
- `beneficiary` can be any fresh account supplied at `award_bounty`/`award_child_bounty` time, with no prior existence and no ED check on `payout`.

Because the check is a no-op in production, once either transfer fails:
1. The `bounty_account`/`child_bounty_account` still holds the un-transferred balance.
2. The bounty/child-bounty record is deleted from storage (`*maybe_bounty = None`), so there is no future dispatchable path to retry the payout — `bounty_account_id`/`child_bounty_account_id` are deterministic derived accounts with no recovery mechanism once the bounty index is gone.
3. A `Claimed`/`BountyClaimed` event is emitted claiming the payout succeeded, misleading off-chain observers/accounting.

This directly maps to the report's core invariant break: a payout mechanism that should either (a) succeed for both recipients, or (b) surface/handle partial failure without silently declaring success — instead the code takes path (c): silently drop the failed leg and permanently finalize state as if it had succeeded.

### Impact Explanation
This causes a **permanent, unrecoverable fund lock**: value sitting in the bounty's dedicated sub-account becomes orphaned once the bounty entry is removed, with no code path referencing the deterministic account to reclaim or resweep the balance. This falls squarely under "permanent user-fund lock" in the accepted impact set, and is triggerable by an unprivileged, permissionless `claim_bounty`/`claim_child_bounty` call (any signed origin can call `claim_bounty`; `claim_child_bounty` is likewise permissionless).

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires a curator fee or payout amount smaller than `ExistentialDeposit` combined with a destination account (curator or beneficiary) that has never held a balance before. Curator fees are chosen by the assigned curator and beneficiaries are chosen freely at award time, so both conditions are within the control of the bounty's curator (an otherwise low-privilege, non-council actor) — no validator/relayer/governance compromise is required. On low-ED chains this is easy to trigger unintentionally; on higher-ED chains it requires deliberate low fee/payout selection.

### Recommendation
- Replace `debug_assert!(res.is_ok())` with a real error propagation (`res?`) so a failing transfer aborts the extrinsic and preserves state (the bounty is not removed) rather than silently declaring success — or,
- If atomic all-or-nothing payout to two recipients is undesired (to avoid the exact revert-blocks-everyone problem from the original report), then upon detecting a transfer failure, keep the bounty/child-bounty in a `PendingPayout`/partial state and allow retry rather than deleting the storage entry.
- Additionally, validate `final_fee`/`curator_fee` and `payout` against `T::Currency::minimum_balance()` before finalizing payout eligibility, or use `Preservation::Preserve`/dust-handling utilities that guarantee sub-ED transfers cannot silently no-op.

### Proof of Concept
1. Deploy a chain with `pallet-bounties`/`pallet-child-bounties` compiled in `release` mode (production configuration, where `debug_assert!` is a no-op).
2. Propose and fund a bounty with `bounty.fee` set to `1` (well below `ExistentialDeposit`).
3. Assign and accept a curator; have the curator call `award_bounty` with a brand-new, never-funded `beneficiary` account, and set `payout = balance - fee` such that `payout < ExistentialDeposit` as well (achievable by choosing a small bounty value).
4. Wait out `BountyDepositPayoutDelay`; any signed account calls `claim_bounty(bounty_id)`.
5. Internally: `T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath)` and/or the transfer to `beneficiary` return `Err(DispatchError::Token(BelowMinimum))` because the destination account doesn't exist and the transferred amount is below ED.
6. In production, `debug_assert!` is compiled out, so execution proceeds: `*maybe_bounty = None` executes, `Event::BountyClaimed` is emitted with the (unpaid) `payout` value, and the extrinsic returns `Ok(())`.
7. Result: funds remain stuck in `bounty_account_id(bounty_id)`, the bounty index is gone, and no dispatchable exists to recover the funds — permanent fund lock.
