Found a genuine local analog in `substrate/frame/staking/src/slashing.rs`: the legacy `pallet-staking` slashing reward calculation multiplies the configurable, governance-settable `SlashRewardFraction` by a second, hardcoded constant `REWARD_F1 = Perbill::from_percent(50)` that does not track any storage update.

### Title
Hardcoded `REWARD_F1` constant silently halves slash-reporter rewards regardless of `SlashRewardFraction` governance updates - (File: `substrate/frame/staking/src/slashing.rs`)

### Summary
`pallet-staking`'s legacy (non-async) slashing module computes the reward paid to a slash reporter as `REWARD_F1 * (reward_proportion * slash)`, where `reward_proportion` is the live, governance-configurable `SlashRewardFraction::<T>::get()` storage value, but `REWARD_F1` is a module-level `const` fixed at `Perbill::from_percent(50)`. [1](#0-0) [2](#0-1) 

### Finding Description
The intended reward-fraction knob for slash reporters is `SlashRewardFraction`, which is stored on-chain and can be updated via `T::AdminOrigin`/governance calls (analogous to `setMonsterMultiplier` in the FrankenDAO report). This value is correctly read live at `process_offence` time: [3](#0-2) 
and passed down as `reward_proportion` into `SlashParams`.

However, `compare_and_update_span_slash` — the function that actually computes the reward paid out to whoever reports the slash — does not use `reward_proportion` alone. It multiplies it by the module constant `REWARD_F1`:
```
let reward =
    REWARD_F1 * (self.reward_proportion * slash).saturating_sub(span_record.paid_out);
``` [2](#0-1) 

`REWARD_F1` is declared as:
```
/// The proportion of the slashing reward to be paid out on the first slashing detection.
/// This is f_1 in the paper.
const REWARD_F1: Perbill = Perbill::from_percent(50);
``` [1](#0-0) 

This constant is baked into the runtime binary at compile time and can never be affected by any dispatchable call. This exactly mirrors the FrankenDAO bug pattern: one code path (`stakedTimeBonus` / here, `compare_and_update_span_slash`) uses a hardcoded halving factor, while a parallel/related code path (`getTokenVotingPower` / here, `SlashRewardFraction` storage) is properly governance-updatable. Anyone who reads only `SlashRewardFraction`'s documented behavior ("The percentage of the slash that is distributed to reporters") would reasonably expect that setting `SlashRewardFraction` to, say, 100% would give reporters the full slashed amount as reward — but the actual payout is silently capped/scaled at 50% of that due to `REWARD_F1`, with no way to change this factor without a runtime upgrade. [4](#0-3) 

Notably, this is the historical design intent (an intentional two-stage "detection vs. era-end" reward split from the original slashing spec, `f_1` in the referenced paper), but it means `SlashRewardFraction`'s effective value never matches its configured value in this code path, unlike the newer `staking-async` slashing implementation which has since removed the analogous halving-on-repeat-offence logic, per its own inline audit note:
```
// Audit Note: Previously, each repeated slash reduced the reward by 50% ... this reduction logic was unnecessary and removed.
``` [5](#0-4) 

This confirms that the legacy `pallet-staking` (`substrate/frame/staking`) still contains the un-fixed hardcoded-halving pattern that was independently identified and removed in the newer `staking-async` pallet.

### Impact Explanation
The corrupted value is the reporter reward amount paid out of a validator's/nominator's slashed stake. Because `REWARD_F1` silently discounts the configured `SlashRewardFraction` by 50% on every first-detection slash, governance/root cannot actually set the true effective reporter incentive via the documented `SlashRewardFraction` storage item alone — any operator relying on that storage value to reason about incentive-compatibility for slash reporting gets an incorrect economic assumption. This is a runtime-behavior-compromising bug (the pallet's documented and configured invariant "SlashRewardFraction is the percentage of slash paid to reporters" does not hold), impacting reward accounting integrity for a live chain running legacy `pallet-staking` (e.g. Kusama/Polkadot relay chain and any parachain still on the non-async staking pallet).

### Likelihood Explanation
This triggers on essentially every slash event, since `compare_and_update_span_slash` is exercised whenever an unapplied slash is processed for a stash — it is not gated behind any admin or governance action; it fires automatically as part of the standard offence-processing pipeline. It is not an attacker-controlled path since the discrepancy is a design/implementation bug rather than an entry point for unprivileged fund theft, so likelihood of the discrepancy manifesting is effectively certain (every slash), though the "impact" (economic mis-calibration rather than fund loss or origin escalation) is bounded.

### Recommendation
Either (a) remove the extra `REWARD_F1` multiplication entirely so the reward paid equals `reward_proportion * slash` (matching `SlashRewardFraction`'s documented semantics, consistent with the fix already applied in `staking-async`), or (b) if the two-stage f_1/f_2 detection-vs-final split is still intentionally desired, expose `REWARD_F1` as a `Config` associated type / on-chain storage parameter settable via `T::AdminOrigin`, analogous to `SlashRewardFraction`, so operators can actually control the effective reporter incentive as documented.

### Proof of Concept
1. Deploy a chain running the legacy `pallet-staking` (not `staking-async`).
2. Governance sets `SlashRewardFraction` to `Perbill::from_percent(100)` via `set_slash_reward_fraction` (root/admin call), intending reporters to receive 100% of the slashed amount. [4](#0-3) 
3. Trigger an offence/slash against a validator with a reporter present, producing a `slash` amount `S`.
4. Observe `compare_and_update_span_slash` compute `reward = REWARD_F1 * (100% * S) = 50% * S` instead of the expected `100% * S`. [2](#0-1) 
5. The reporter receives only half of the intended reward, and the remaining 50% is instead routed to `T::Slash`/treasury handling rather than the reporter — confirming `SlashRewardFraction`'s configured value is not honored due to the hardcoded `REWARD_F1` constant.
