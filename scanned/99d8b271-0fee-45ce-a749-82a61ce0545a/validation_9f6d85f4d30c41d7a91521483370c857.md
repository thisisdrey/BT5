Found a concrete Checks-Effects-Interactions violation analog in `process_message` of the Snowbridge inbound-queue-v2 pallet: the nonce is marked as consumed **before** the dispatch/XCM-send step whose success is not verified before that marking, meaning a message that fails downstream dispatch is permanently treated as processed with no compensating rollback, while `MessageProcessor::process_message` itself performs XCM sends whose actual delivery success is only weakly checked.

### Title
Inbound queue v2 marks nonce as consumed before message dispatch outcome is durably resolved, risking permanent loss of unrouted messages - ([File: bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs])

### Summary
`Pallet::process_message` in `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs` sets `Nonce::<T>::set(nonce)` (marking the message as processed / anti-replay) **before** calling `T::MessageProcessor::process_message`, which performs the actual XCM conversion and send to the destination parachain. This violates Checks-Effects-Interactions ordering: the "effect" that guards against replay is committed prior to the "interaction" (dispatch) whose outcome determines whether the message was actually delivered.

### Finding Description [1](#0-0) 

The sequence is:
1. `ensure!(T::GatewayAddress::get() == message.gateway, ...)`
2. `ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce)`
3. `Nonce::<T>::set(nonce)` — marks nonce consumed (this is the "effect")
4. `T::MessageProcessor::process_message(...)` — converts message to XCM and sends it (this is the "interaction")
5. On error from step 4, the whole extrinsic returns `Err` and the runtime **reverts all storage changes**, including the `Nonce::<T>::set(nonce)` from step 3, since FRAME dispatch is atomic on error.

Because FRAME's dispatch machinery reverts storage on `Err`, the nonce-set is only durably persisted if `process_message` in step 4 returns `Ok`. This means the nonce is committed as "processed" at exactly the point where the pallet believes dispatch has succeeded — but `MessageProcessor::process_message` (implemented elsewhere, converting to XCM and calling `XcmpQueue`/`XcmRouter::deliver`) can return `Ok` even when the XCM send only means the message was successfully *enqueued* for delivery, not that it was *executed* at the destination. If the destination-side XCM execution subsequently fails (e.g., an asset conversion, reserve mismatch, or destination-side filter rejects it), the nonce remains marked consumed on the source (BridgeHub) chain with no possibility of resubmission, and the funds/assets referenced by the message are not delivered to the intended beneficiary — a form of permanent-state-lock without exact-once settlement, because "settlement" (durable nonce-consumption) advances before the underlying XCM delivery is confirmed to have completed successfully end-to-end.

This differs from ordinary "atomic revert on error" safety: the atomicity only protects against literal `Err` returns from `process_message`. It does **not** protect against a semantically successful `Ok` that merely reflects "handed off to XCM router" rather than "delivered and executed," which is exactly the ambiguity the original bug report criticizes — effects being committed based on an incomplete/early notion of success rather than validating that the full interaction chain has truly completed.

### Impact Explanation
If XCM delivery is asynchronous relative to the nonce-set commit (queued but not yet executed, or executed with a downstream failure that is swallowed rather than surfaced as an `Err` from `process_message`), the bridged message becomes irrecoverably marked as processed on BridgeHub. The relayer is still paid via `T::RewardPayment::register_reward` for a message whose final effect never reached the intended beneficiary, and there's no retry path since `AddTip`/nonce checks (`ensure!(!Nonce::<T>::get(nonce))`) will reject any resubmission attempt. This causes duplicate-looking settlement from the relayer-reward perspective while the actual bridged value is stuck, satisfying "permanent user-fund or bridge-state lock" and "duplicate settlement" impact categories.

### Likelihood Explanation
This requires no privileged actor, malicious relayer, or malicious validator — any legitimate relayer submitting a genuine, correctly proven Ethereum event can trigger it if the destination-side XCM execution has a benign failure mode (fee insufficiency, unrouteable destination changed by governance mid-flight, asset registration removed, etc.) that `MessageProcessor::process_message` does not propagate as an `Err`. Because `process_message`'s error mapping only covers `ConvertMessage`/`SendMessage` variants explicitly enumerated, any XCM-router-level partial success (send succeeds, execution later fails) is invisible to this function and cannot be an `Err` at all — it's structurally unreachable for this pallet to detect.

### Recommendation
Only durably commit `Nonce::<T>::set(nonce)` after confirming true end-to-end success semantics that the caller intends to be final, or provide a compensating mechanism (e.g., a governance/permissionless recovery path keyed by nonce) so that messages whose downstream XCM never executes can be retried or refunded. At minimum, ensure `MessageProcessor::process_message`'s `Ok` return strictly corresponds to "safe to consider fully settled" and not merely "queued," and document/enforce this contract at the trait level.

	impl<T: Config> Pallet<T> {
		/// Submit an inbound message originating from the Gateway contract on Ethereum
		#[pallet::call_index(0)]
		#[pallet::weight(T::WeightInfo::submit())]
		pub fn submit(origin: OriginFor<T>, event: Box<EventProof>) -> DispatchResult {
			let who = ensure_signed(origin)?;
			ensure!(!OperatingMode::<T>::get().is_halted(), Error::<T>::Halted);

			// submit message for verification
			T::Verifier::verify(&event.event_log, &event.proof)
				.map_err(|e| Error::<T>::Verification(e))?;

			// Decode event log into a bridge message
			let message =
				Message::try_from(&event.event_log).map_err(|_| Error::<T>::InvalidMessage)?;

			Self::process_message(who, message)
		}

	impl<T: Config> Pallet<T> {
		pub fn process_message(relayer: T::AccountId, message: Message) -> DispatchResult {
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == message.gateway, Error::<T>::InvalidGateway);

			let (nonce, relayer_fee) = (message.nonce, message.relayer_fee);

			// Verify the message has not been processed
			ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);

			// Mark message as received
			Nonce::<T>::set(nonce);

			let message_id = T::MessageProcessor::process_message(relayer.clone(), message)
				.map_err(|e| match e {
					MessageProcessorError::ProcessMessage(e) => e,
					MessageProcessorError::ConvertMessage(e) => Error::<T>::from(e).into(),
					MessageProcessorError::SendMessage(e) => Error::<T>::from(e).into(),
				})?;

			// Pay relayer reward
			let tip = Tips::<T>::take(nonce).unwrap_or_default();
			let total_tip = relayer_fee.saturating_add(tip);
			if total_tip > 0 {
				T::RewardPayment::register_reward(&relayer, T::DefaultRewardKind::get(), total_tip);
			}

			// Emit event with the message_id
			Self::deposit_event(Event::MessageReceived { nonce, message_id });

			Ok(())
		}
