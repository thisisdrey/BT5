## Title
Destroying a pool asset via `Assets::start_destroy` permanently locks all liquidity providers' funds in `pallet-asset-conversion` - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
The external report describes a scenario where a token-management admin action (`TokenManager.removeSupportedToken`) leaves a check in `removeLiquidity` that permanently blocks legitimate LPs from reclaiming their already-deposited funds. The equivalent local pattern exists between `pallet-assets` and `pallet-asset-conversion`: when the owner of an asset used inside a liquidity pool calls the ordinary, permissionless `start_destroy` on that asset, `pallet-assets` unconditionally rejects any further withdrawal (`can_decrease` returns `WithdrawConsequence::UnknownAsset` for `AssetStatus::Destroying`), and `pallet-asset-conversion`'s `do_remove_liquidity` has no fallback path, so LP token holders can never call `remove_liquidity` again for that pool.

### Finding Description
`do_remove_liquidity` unconditionally calls `T::Assets::transfer(asset1, &pool_account, withdraw_to, amount1, Expendable)` and the analogous call for `asset2`: [1](#0-0) 

Meanwhile, `pallet-assets::functions::can_decrease` (the consequence check invoked by every asset withdrawal path, including `transfer`) hard-codes an unconditional rejection when the asset's status is `Destroying`, before any per-account or amount checks: [2](#0-1) 

`do_start_destroy`, which flips the asset into `AssetStatus::Destroying`, only checks that there are no outstanding holds/freezes on the asset (not that no external pallet like `pallet-asset-conversion` is using it as reserve collateral), and can be triggered by the asset's own `owner` (a normal, non-privileged account for permissionless/foreign-created assets), not by chain governance: [3](#0-2) 

Once `Destroying` is set, `can_increase`/`can_decrease` both return `UnknownAsset` for that asset id regardless of caller, confirmed by the pallet's own test: [4](#0-3) 

Because `do_remove_liquidity` transfers `asset1`/`asset2` out of the pool account with `Expendable` preservation and no alternate/emergency code path, any attempt to call `remove_liquidity` on a pool containing the destroying asset fails at the `transfer` call. Since Substrate dispatchables execute in an implicit transactional context, the earlier `T::PoolAssets::burn_from` (LP token burn) is also rolled back, so the call simply errors out every time — the LP is stuck holding LP tokens that can never be redeemed for the underlying pool reserves, for as long as the asset remains in the `Destroying`/subsequently `Destroyed` state. There is no equivalent of `pallet-bounties`' new permissionless `reclaim_bounty_funds` sweep (added specifically to fix "stranded funds" bugs of this shape) for `pallet-asset-conversion` pool accounts: [5](#0-4) 

### Impact Explanation
This matches the "permanent user-fund lock" impact category. Any liquidity pool that includes a foreign/permissionless asset (i.e., not the chain's native currency) is exposed: if that asset's owner (who need not be a privileged/governance actor — merely the asset creator) calls the ordinary `start_destroy` extrinsic, every LP provider in every pool pairing that asset becomes permanently unable to redeem their LP tokens for the underlying reserves. Value is not directly stolen, but it is durably locked/unreachable, satisfying the accepted impact "permanent user-fund ... lock."

### Likelihood Explanation
`start_destroy` is a standard, documented, low-privilege lifecycle operation for `pallet-assets` (used e.g. to clean up unwanted/incorrectly created assets) and is expected to be called routinely, including by permissionless-asset owners who have no visibility into or control over which `asset-conversion` pools reference their asset. There is no cross-pallet check preventing `start_destroy` while an asset is used as pool collateral, and no recovery mechanism exists in `pallet-asset-conversion` to sweep/rescue reserves once this happens, making the scenario realistic under normal (non-adversarial) asset lifecycle management rather than requiring any malicious validator, relayer, or governance abuse.

### Recommendation
- Add a check in `do_start_destroy` (or in an `asset-conversion`-aware hook) that rejects/queues destruction while the asset still has a nonzero balance held by any registered pool account, similar to the existing `ContainsHolds`/`ContainsFreezes` guards.
- Alternatively, add a permissionless "reclaim/rescue" extrinsic to `pallet-asset-conversion` analogous to `pallet-bounties::reclaim_bounty_funds`, allowing LPs (or anyone) to force-withdraw pool reserves once an underlying asset is destroyed, bypassing the standard `remove_liquidity` withdraw-consequence check via a `Fortitude::Force` transfer path.
- At minimum, document the risk and provide an escape hatch so LP token holders are not permanently locked out when a pool's underlying asset lifecycle changes.

### Proof of Concept
1. Asset owner creates asset `X` via `pallet-assets::create`/`force_create`.
2. A user creates a pool `(Native, X)` via `AssetConversion::create_pool` and adds liquidity via `AssetConversion::add_liquidity`, receiving LP tokens (see `do_add_liquidity`) [6](#0-5) .
3. The owner of asset `X` calls `Assets::start_destroy(RuntimeOrigin::signed(owner), X)`. This succeeds unconditionally provided there are no holds/freezes on `X` (irrespective of the pool's balance) [3](#0-2) .
4. The LP attempts `AssetConversion::remove_liquidity(...)`. The extrinsic fails because `T::Assets::transfer(asset1_or_X, &pool_account, withdraw_to, amount, Expendable)` triggers `can_decrease`, which returns `WithdrawConsequence::UnknownAsset` due to `AssetStatus::Destroying` (test asserting this exact behavior exists in the assets pallet) [4](#0-3) .
5. The LP's tokens (and the pool's reserves) are now permanently unreclaimable through any pallet-provided call — `pallet-asset-conversion` has no sweep/rescue mechanism analogous to `pallet-bounties::reclaim_bounty_funds`.

	/// Start the process of destroying an asset, by setting the asset status to `Destroying`, and
	/// emitting the `DestructionStarted` event.
	pub(super) fn do_start_destroy(
		id: T::AssetId,
		maybe_check_owner: Option<T::AccountId>,
	) -> DispatchResult {
		Asset::<T, I>::try_mutate_exists(id.clone(), |maybe_details| -> Result<(), DispatchError> {
			let details = maybe_details.as_mut().ok_or(Error::<T, I>::Unknown)?;
			if let Some(check_owner) = maybe_check_owner {
				ensure!(details.owner == check_owner, Error::<T, I>::NoPermission);
			}

			ensure!(!T::Holder::contains_holds(id.clone()), Error::<T, I>::ContainsHolds);
			ensure!(!T::Freezer::contains_freezes(id.clone()), Error::<T, I>::ContainsFreezes);

			details.status = AssetStatus::Destroying;

			Self::deposit_event(Event::DestructionStarted { asset_id: id });
			Ok(())
		})
	}

		/// Reclaim funds stranded in a closed bounty's account back to the treasury.
		///
		/// Permissionless. Moves all remaining assets from a closed bounty's account back to the
		/// treasury in a single call. Which assets are swept depends on the `TransferAllAssets`
		/// configuration.
		///
		/// The call is free if funds were reclaimed and paid otherwise, so no-op calls cannot be
		/// used to grief the network. Emits `BountyFundsReclaimed` on success.
		///
		/// ## Complexity
		/// - O(A) where A is the number of relevant assets configured in `TransferAllAssets`.
		#[pallet::call_index(11)]
		#[pallet::weight(<T as Config<I>>::WeightInfo::reclaim_bounty_funds())]
		pub fn reclaim_bounty_funds(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
		) -> DispatchResultWithPostInfo {
			ensure_signed(origin)?;

			// A live bounty still manages its account, so leave it untouched.
			ensure!(!Bounties::<T, I>::contains_key(bounty_id), Error::<T, I>::BountyStillActive);

			debug_assert!(
				T::ChildBountyManager::child_bounties_count(bounty_id) == 0,
				"child bounties should not exist for a closed bounty"
			);

			let bounty_account = Self::bounty_account_id(bounty_id);
			let treasury_account = Self::account_id();

			let transferred = T::TransferAllAssets::force_transfer_all_assets(
				&bounty_account,
				&treasury_account,
			)?;

			// Free only if something moved, otherwise paid to prevent griefing.
			if !transferred {
				return Ok(Pays::Yes.into());
			}

			Self::deposit_event(Event::<T, I>::BountyFundsReclaimed { bounty_id });

			Ok(Pays::No.into())
		}
