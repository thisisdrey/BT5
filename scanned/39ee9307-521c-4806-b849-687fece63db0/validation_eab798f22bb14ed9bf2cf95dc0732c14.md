Based on my investigation, I found a concrete local analog of the reported bug class in `pallet-recovery`'s inheritance-control mechanism, which structurally mirrors the "arbitrary external call with attacker-crafted data bypassing an allow-list" pattern from the MetaRouterV2 report.

### Title
Inheritor call-filter in `pallet-recovery`'s `control_inherited_account` may be bypassable via `pallet-utility` batch wrapping - (File: `substrate/frame/recovery/src/lib.rs`, guarded by test in `substrate/frame/recovery/src/tests.rs`)

### Summary
`pallet-recovery` lets an `inheritor` account dispatch arbitrary calls on behalf of a `lost`/recovered account via `control_inherited_account`, similarly to how `pallet-proxy`'s `proxy` extrinsic lets a delegate dispatch calls as the `real` account under an `InstanceFilter`. The report's core invariant — "a public wrapper performs an external/dispatched call using attacker-influenced target/data, and that call should have been restricted to a whitelist of safe operations, but the wrapper only validates the outer call and not calls nested inside a generic pass-through pallet (`Utility::batch`)" — has a direct local analog here.

### Finding Description
`pallet-proxy` defends against this exact bypass class by installing a persistent `origin.add_filter` closure in `do_proxy` (`substrate/frame/proxy/src/lib.rs:994-1027`) so that *every* nested dispatch performed under that origin — including calls unwrapped by `pallet_utility::Call::batch`/`batch_all`/`as_derivative` — is re-checked against `ProxyType::filter`. This is confirmed by `substrate/frame/proxy/src/tests.rs:319-370`, where wrapping a restricted call inside `Utility::batch` still results in `CallFiltered`.

`pallet-recovery`'s test suite contains a purpose-built regression test, `inheritor_cannot_bypass_filter_via_utility_batch` (`substrate/frame/recovery/src/tests.rs:1423-1477`), which wraps the privileged `RecoveryCall::slash_attempt` inside `pallet_utility::Call::batch` and dispatches it through `Recovery::control_inherited_account`. The test's own inline comment states: *"The batch dispatched as ALICE, but the inner slash should have still executed since our filter only checks the outer call."* This indicates that, unlike `pallet-proxy`, the guard in `control_inherited_account` is implemented as a single top-level pattern match against the call variant rather than as a persistent, recursively-enforced `origin.add_filter`. If the filter only inspects the outer `RuntimeCall` shape, wrapping any disallowed inner call (e.g. `slash_attempt`, or other privileged recovery/administrative calls) inside `Utility::batch`/`batch_all`/`as_derivative` would let it execute under the recovered account's origin, exactly mirroring MetaRouterV2's flaw where an intermediate wrapper forwards attacker-supplied calldata to an arbitrary sub-call without validating what that calldata actually invokes.

### Impact Explanation
If the bypass is live, an inheritor of a recovered account could invoke otherwise-restricted operations against other friend groups or against the recovered account's own protections (e.g., forcing `slash_attempt` against a rival friend group, or invoking calls that should require higher-priority-group consensus), corrupting the recovery/inheritance state machine and potentially causing unauthorized fund movement or unauthorized administrative state changes tied to the `lost` account — a runtime bug compromising intended behavior and an origin-escalation primitive, both in-scope per the impact gate.

### Likelihood Explanation
The precondition (become an `inheritor` of a recovered account) is reachable through the pallet's own public, unprivileged recovery flow (`initiate_attempt`/`approve_attempt`/`finish_attempt`), not through a privileged admin/governance path, so this would qualify as an unprivileged-actor path if the bypass is confirmed live in the actual filter code.

### Recommendation
Verify the exact matching logic used by `control_inherited_account`'s call filter in `substrate/frame/recovery/src/lib.rs`. If it performs a single top-level `matches!` against the incoming `RuntimeCall` (rather than installing a persistent `origin.add_filter`, as `pallet-proxy` does), change it to use the same `origin.add_filter` pattern so nested calls dispatched through `Utility::batch`, `batch_all`, `force_batch`, and `as_derivative` are re-validated against the same allow-list at every nested dispatch.

### Proof of Concept
The existing test `inheritor_cannot_bypass_filter_via_utility_batch` in `substrate/frame/recovery/src/tests.rs:1423-1477` is itself the PoC scaffold: it sets up two friend groups, has the lower-priority group's inheritor (`FERDIE`) wrap `RecoveryCall::slash_attempt { friend_group_index: 0 }` inside `pallet_utility::Call::batch`, and dispatches it through `Recovery::control_inherited_account`. If `BOB`'s balance decreases (slash executes), the bypass is confirmed.

**Important caveat:** I was unable to view the actual implementation of `control_inherited_account`'s filter (`substrate/frame/recovery/src/lib.rs`, past the doc-comment header) before running out of tool budget, so I cannot confirm with certainty whether the current code already closes this gap (e.g., via an `origin.add_filter` mechanism like `pallet-proxy`) or whether the guard test currently passes only because the bypass has already been fixed. The evidence for this finding rests on the test's own inline comment describing the filter as checking "only the outer call," which is the strongest local signal I could gather, but this should be verified directly against `substrate/frame/recovery/src/lib.rs`'s `control_inherited_account`/`do_control_inherited_account` implementation before treating this as confirmed.
