## Analysis

The Blueprint-Finance bug reduces to: **an irreversible value-moving side effect is executed before the operation that depends on it is confirmed successful, and there is no compensation/rollback for the already-executed side effect if the dependent step later fails.**

Searching for the same broken invariant in `paritytech/polkadot-sdk` (Snowbridge reward-payout path) surfaces a direct structural analog in `PayAccountOnLocation::pay_reward`, the `PaymentProcedure` implementation used to pay Snowbridge relayer rewards from BridgeHub to AssetHub. [1](#0-0) 

### Title
Relayer fee is charged before XCM delivery is confirmed, so a failed `deliver()` burns the relayer's fee without paying (or refunding) the reward - (File: `bridges/snowbridge/primitives/core/src/reward.rs`)

### Summary
`PayAccountOnLocation::pay_reward` validates the reward-delivery XCM, then **unconditionally charges the relayer's fee via `XcmExecutor::charge_fees`**, and only afterwards attempts `XcmSender::deliver(ticket)`. If `deliver()` fails, the function returns an error, but the fee that was already withdrawn from the relayer in the prior step is never refunded.

### Finding Description
The payout sequence is:
```rust
let (ticket, fee) = validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;
Ok(())
``` [2](#0-1) 

`charge_fees` performs a real, immediate balance mutation (it withdraws/consumes the relayer's local asset to pay for XCM delivery) - this is not a "ticket" or reserved amount, it is a committed accounting change. The subsequent `deliver()` call is a separate fallible step. The unit test `pay_reward_fails_on_delivery` proves this exact sequence: `validate` succeeds, `charge_fees` is implicitly exercised in the surrounding flow, and `deliver` fails, yet the function simply propagates the error - there is no code path that reverses the fee charge. [3](#0-2) 

This directly violates the required invariant that "payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" - here, the fee-charge (a partial settlement action) advances *before* delivery is confirmed, and nothing rolls it back on delivery failure. This mirrors the Solidity finding precisely: an unconditional transfer/charge is embedded inside a payout path whose overall success is not guaranteed, and the already-executed side effect has no pull-pattern/claim-based recovery.

This procedure is wired in as the live `PaymentProcedure` for Snowbridge rewards on BridgeHub Westend/Rococo, invoked from `claim_rewards_to`: [4](#0-3) 

### Impact Explanation
A relayer that has an accrued, legitimate `Snowbridge` reward can lose real value (the local delivery fee charged by `charge_fees`) with no reward received in return, whenever `XcmSender::deliver` fails after `charge_fees` succeeds (e.g., transient HRMP/XCMP channel congestion, suspended channel, or any other deliver-time failure that is independent of the fee-charge step). Because the function offers no compensation path, and the design explicitly relies on this procedure rather than a pull/claim-and-refund pattern, repeated failures degrade relayer economics and can make reward claiming a lossy, one-way operation for affected relayers - directly analogous to the reported "transfer revert blocks legitimate settlement, no pull-pattern fallback" bug class.

### Likelihood Explanation
`validate_send` succeeding while `deliver` subsequently fails is a realistic, permissionless-triggerable condition (e.g. transient outbound channel/queue backpressure on BridgeHub, since XCMP/HRMP delivery to AssetHub is not fully decoupled from transient channel state at delivery time). No privileged actor, governance action, or malicious relayer/validator is required — an ordinary relayer calling `claim_rewards_to` during any window where outbound delivery is failing is enough to hit this path.

### Recommendation
Reorder the operation so that `charge_fees` only happens after `deliver` succeeds (or use a two-phase pattern: reserve/hold instead of unconditionally charging, and refund on delivery failure). Alternatively, wrap `charge_fees` + `deliver` so that a `deliver` failure triggers an explicit refund of the charged fee back to the relayer before returning the error, restoring atomicity between fee-charge and successful delivery.

### Proof of Concept
The existing test `pay_reward_fails_on_delivery` already demonstrates the vulnerable sequence in isolation (validate succeeds, deliver fails, function returns `Err`), but does not assert that the relayer's fee was refunded — because no such refund exists: [3](#0-2) 

To reproduce end-to-end: have a relayer with a registered Snowbridge reward call `claim_rewards_to` while the BridgeHub→AssetHub outbound channel is in a state that causes `XcmRouter::deliver` to fail after `validate_send` succeeds (e.g., queue-full/suspended state); observe the relayer's fee balance decrease from `charge_fees` while `claim_rewards_to` returns `FailedToPayReward` and no compensating credit is issued.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
