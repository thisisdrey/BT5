In `contracts/defuse/src/contract/tokens/nep245/core.rs::Contract::notify_and_resolve_transfer`, the callback `mt_resolve_transfer` is scheduled `.with_unused_gas_weight(0)` so that all remaining gas after static allocation goes to `mt_on_transfer`. Can an attacker's `mt_on_transfer` callee deliberately consume gas up to just below the point where it would fail, then re-enter `execute_intents` with a payload that itself is gas-heavy (e.g. many `TokenDiff` intents), such that the *outer* `mt_resolve_transfer` callback subsequently runs out of gas and fails entirely (not just its refund logic), causing `promise_result_checked_json_with_len` in a still-pending sibling resolver (if multiple tokens were batched in the same `Transfer`) to read a corrupted/absent result and default `refunds = amounts.clone()` (full refund) for tokens that were, in fact, delivered because the earlier per-token loop already committed a delivery before the gas ran out? Precondition: signer's `Transfer` batches N>1 tokens with `notification: Some(...)`. Call sequence: `Transfer::execute_intent -> notify_on_transfer -> mt_on_transfer(attacker, burns gas + reenters execute_intents) -> mt_resolve_transfer (OOG mid-loop)`. Binding: for each token in the batch, exactly one of {delivered to receiver, refunded to sender} holds, and the sum of `refunds` decisions must not double-count a token already committed as delivered in an earlier loop iteration of the same `mt_resolve_transfer` call before it ran out of gas. Scoped impact: Critical, partial-execution-then-panic of `mt_resolve_transfer` could leave a token both delivered (loop already ran `token_balances.sub`/`.add` for it) and, on retry/replay of the same receipt after failure, counted again -- verify NEAR's receipt semantics prevent replay of a failed private callback, and that the Verifier's own state doesn't get double-mutated by a single failed `mt_resolve_transfer` invocation being effectively atomic per-receipt. Proof idea: sandbox test with a large multi-token `Transfer` + gas-burning malicious `mt_on_transfer`, forcing `mt_resolve_transfer` to run out of gas, then asserting the receipt failed atomically (state == before `mt_resolve_transfer` ran) so CONSERVATION holds trivially via full revert, not partial commit.
