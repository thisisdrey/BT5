## Title
Attacker-controlled beneficiary permanently locks bounty funds by ensuring `Paymaster::pay` always fails after `award_bounty` - ([File: substrate/frame/multi-asset-bounties/src/lib.rs])

### Summary
`pallet-multi-asset-bounties` moves funds through an asynchronous, retryable payment abstraction (`T::Paymaster::pay`) instead of a synchronous `transfer`. When a bounty is awarded, `do_process_payout_payment` initiates payment to the `beneficiary` chosen in `award_bounty` and sets the bounty status to `PayoutAttempted`. If that payment permanently fails (analogous to the zkPay `refundSuccess` revert — a chosen beneficiary/location that always rejects the incoming funds), the only recovery paths available (`check_status`, `retry_payment`) keep re-attempting payment to the *same* beneficiary, and `close_bounty` explicitly does not accept the `PayoutAttempted` status. This mirrors the reported bug class: a party that controls the destination of a payout can make that payout permanently un-completable, locking the escrowed value with no fallback route back to the funding source.

Recovery from a failed payment is via `check_status`/`retry_payment`, both of which only re-drive `do_process_payout_payment`/`do_process_refund_payment` toward the *same* beneficiary or funding source recorded in the status enum: [3](#0-2) 

Crucially, `close_bounty`, the only dispatchable that can redirect a bounty's escrowed value back to the funding source, only accepts bounties whose status is `Funded`, `Active`, or `CuratorUnassigned`: [4](#0-3) 

There is no state transition defined that moves a bounty out of `PayoutAttempted` back to a cancelable state. If the beneficiary is a location/account that is guaranteed to reject the deposit forever (the exact analog of the zkPay attacker pre-configuring their contract's `receive`/`fallback` to always revert), `check_status`/`retry_payment` will forever observe `PaymentState::Failed` for the same doomed destination, and the bounty's escrowed value in the child-/bounty account is permanently unreachable — it can neither be delivered to the beneficiary nor reclaimed to the funding source (treasury/parent bounty).

This is structurally identical to the reported bug: the report's `fulfillQuery` always attempts the refund to a caller-chosen (and thus attacker-controllable) destination and has no alternate settlement path when that destination refuses funds; here, `award_bounty`/`retry_payment` always attempt payout to a beneficiary that, once chosen, cannot be changed, and there is no alternate settlement path (no "refund to funding source" fallback) once in `PayoutAttempted`.

### Impact Explanation
Escrowed bounty value (native or arbitrary `AssetKind`, since this is the multi-asset bounties pallet) becomes permanently locked in the child-/bounty account. This is a direct instance of "permanent user-fund ... lock" from the impact gate. Because bounties can carry arbitrary and potentially large treasury-sourced value, the blast radius scales with bounty size, and there is no governance-independent recovery once payment starts failing to a permanently-rejecting beneficiary.

### Likelihood Explanation
The trigger requires only:
1. A curator (or `RejectOrigin`) calling `award_bounty` with a `beneficiary` whose lookup/location is constructed (or later becomes) unable to accept the asset (e.g., a location where the concrete `Paymaster` implementation's deposit step deterministically fails — such as a destination that is not registered to receive the `AssetKind`, or that structurally rejects the transfer).
2. No governance/admin privilege abuse is required — the failure is a property of the destination the payout attempts to reach, not of any privileged actor's decision to misuse power. This matches the "unprivileged attacker primitive" requirement of the task: whoever controls or nominates that destination (which can be an attacker-supplied beneficiary/location) can render the payout permanently stuck, exactly as the zkPay attacker pre-arms a `receive()`-reverting contract before triggering `fulfillQuery`.

Likelihood is rated Medium because it depends on the concrete `Paymaster`/`AssetKind` implementation wired into the runtime allowing a "permanently rejecting" destination (this could not be fully verified against the pallet's abstract `Paymaster` trait alone, since `pay`'s concrete failure semantics are implementation-defined and I could not trace a specific runtime's `Paymaster` binding within the available index).

### Recommendation
Add a status transition that allows a bounty stuck in `PayoutAttempted` with `PaymentState::Failed` (after some threshold of failed retries, or via a governance/curator "redirect" call) to fall back to a refund path (`do_process_refund_payment` to the funding source) instead of only ever retrying the original, possibly permanently-failing beneficiary. This mirrors the zkPay report's own recommendation of avoiding an unconditional dependency on a caller-controlled destination succeeding, by introducing an escrow/claim-based fallback (e.g., let the beneficiary claim later, or default to returning funds to the funding source) rather than looping forever on the same failing destination.

### Proof of Concept
Conceptual reproduction (concrete PoC requires wiring a `Paymaster`/`AssetKind` combination in a test runtime where deposit to an attacker-chosen `Location`/account structurally and permanently fails, which could not be executed in this read-only analysis):
1. Fund and activate a child-/parent bounty (`propose_bounty` → accept → curator assigned → `Active`).
2. Curator calls `award_bounty(parent_bounty_id, child_bounty_id, beneficiary)` where `beneficiary` resolves to a destination that `Paymaster::pay` can never successfully deposit into (e.g., an unregistered/incompatible asset destination for the given `AssetKind`).
3. Status becomes `PayoutAttempted { payment_status: Attempted { id } }`.
4. Call `check_status` — observe `PaymentState::Failed`, status transitions to `PayoutAttempted { payment_status: Failed }` (see test pattern at [5](#0-4)  which demonstrates the analogous `RefundAttempted`/`Failed` cycle for cancellation, confirming the same failure/retry mechanics apply to payouts).
5. Call `retry_payment` repeatedly — payment to the same beneficiary fails every time; `close_bounty` cannot be called because status is not `Funded`/`Active`/`CuratorUnassigned`.
6. Bounty value remains permanently locked in the child-/bounty account with no path to recovery.
