## Analysis Summary

The `CampTimelockEscrowNativeOFT.sol` bug describes a queue where **(a)** entries are processed strictly in insertion order via a single global cursor, **(b)** cheap/no-minimum entries can be inserted at negligible cost, and **(c)** there is no way to service a specific entry out of order — so an attacker fills the front of the queue with worthless entries and forces everyone (including legitimate large deposits behind them) to pay for their processing before progress resumes.

The closest structural analog in this repository is the Snowbridge V2 outbound queue: `snowbridge-pallet-outbound-queue-v2`.

### Finding

`Pallet::validate()` in `send_message_impl.rs` only checks payload size, never a minimum relayer-reward fee: [1](#0-0) 

The `fee` field carried inside `Message` is fully attacker-controlled (it comes from the XCM `PayFees`/reward asset the sender chooses to attach) and is never validated to be non-zero or above any floor before being persisted into `PendingOrders`: [2](#0-1) 

Processing is strictly FIFO per `AggregateMessageOrigin` (e.g., per sibling parachain/channel) and is hard-capped per block by `MaxMessagesPerBlock`; once that cap is hit, remaining messages for the *same origin* are yielded/postponed to a later block — with no mechanism to skip ahead to a specific message: [3](#0-2) 

The underlying `pallet-message-queue` reinforces this: `service_queue` walks the per-origin book strictly from `begin` to `end`, and cannot skip an unprocessed message to reach a later one within the same page/queue: [4](#0-3) 

The project's own tests confirm that a burst of low-priority messages from one origin can occupy the entire `MaxMessagesPerBlock` budget and delay a subsequently-submitted message from the same origin by multiple blocks: [5](#0-4) 

### Why this mirrors the reported bug class

- No minimum relayer-reward fee is enforced at `validate()`/`do_process_message()` — an attacker can enqueue many minimal-payload, zero/near-zero-fee messages from the same origin.
- The queue is strictly FIFO per origin with a hard per-block cap (`MaxMessagesPerBlock`), so cheap messages queued first must be processed (i.e., consume `Messages`/`MessageLeaves`/`PendingOrders` slots and block-processing budget) before a legitimately large-fee message from the same origin, exactly like `batchRelease()`'s global cursor.
- There is no equivalent of "release a specific queue index" — messages cannot be serviced out of order, so a victim's higher-value message is deterministically delayed behind the attacker's spam until the spam is drained.
- Because zero/low-fee messages give relayers no incentive (`process_delivery_receipt` only pays if `order.fee > 0`), such spam messages can sit in `PendingOrders` indefinitely, and because `Nonce` only increments, this also inflates state (`PendingOrders`) that must eventually be cleared, extending the effect beyond a single block.

This satisfies "public underpriced work that degrades block production or stalls bridge processing," is triggerable by an ordinary unprivileged XCM sender (any account on the sending parachain able to construct an `ExportMessage` toward the Snowbridge V2 gateway), and requires no malicious relayer/validator/collator/governance actor — matching the required impact gate.

### Title
Unbounded, Fee-less Message Spam in `snowbridge-pallet-outbound-queue-v2` Can Delay/Stall FIFO Bridge Delivery for Legitimate Messages - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`, `send_message_impl.rs`)

### Summary
`Pallet::validate()` in the Snowbridge V2 outbound queue enforces only a maximum payload size, never a minimum fee. Combined with strict per-origin FIFO processing and a hard `MaxMessagesPerBlock` cap in `do_process_message`, an attacker can submit a stream of minimal-payload, zero/low-fee messages from a given origin to occupy the entire per-block processing budget for that origin ahead of a legitimate, properly-fee-paying message, delaying its commitment/bridging by an attacker-controlled number of blocks with no way for anyone to skip ahead to service the specific pending message.

### Finding Description
`send_message_impl.rs::validate` checks only `payload.len() < MaxMessagePayloadSize`, with no minimum-fee assertion. `do_process_message` in `lib.rs` processes messages strictly in the order the underlying `pallet-message-queue` delivers them for a given `AggregateMessageOrigin`, and yields once `MaxMessagesPerBlock` is reached for the block, deferring remaining same-origin messages via `MessagePostponed`/`Yield`. `pallet-message-queue::service_queue` enforces strict FIFO within a book/page for an origin — a later message cannot be serviced before an earlier undispatched one, and there is no public function to service a specific pending message out of order. Since `fee` is attacker-supplied and unchecked, and relayer reward is only paid if `fee > 0`, cheap zero-fee messages both (a) occupy processing slots ahead of legitimate ones from the same origin, and (b) may never be economically relayed, leaving stale `PendingOrders` entries.

### Impact Explanation
This degrades bridge throughput/availability for a specific origin (e.g., a sibling parachain/channel) by delaying commitment of legitimate, fee-paying messages behind cheap spam, and can leave `PendingOrders`/`Nonce` state polluted with unrewarded entries. This fits the "public underpriced work that ... stalls bridge processing" impact category for Snowbridge BridgeHub code.

### Likelihood Explanation
Any account capable of sending an XCM `ExportMessage` toward the Ethereum gateway from the affected origin can repeatedly submit minimal-payload messages with `fee = 0` (or a negligible fee), since neither `validate()` nor `do_process_message()` reject such messages. No privileged role, relayer collusion, or protocol-level manipulation is required.

### Recommendation
Enforce a minimum non-zero fee in `Pallet::validate()`/`do_process_message()` (mirroring `pallet-nis`'s `MinBid`, which is explicitly documented as a defense "to ensure there is no possible storage spam attack or queue-filling attack"), and/or expose a privileged-free mechanism to prioritize/skip to a specific pending order so legitimate, well-funded messages are not held hostage behind cheap same-origin spam.

### Proof of Concept
1. Attacker controls (or transacts from) a parachain origin routed through the V2 exporter.
2. Attacker repeatedly submits `ExportMessage`s converted into `Message { fee: 0, .. }` with minimal `commands` payload, each passing `validate()`'s size-only check.
3. Each block, `do_process_message` accepts up to `MaxMessagesPerBlock` of these before yielding (`Event::MessagePostponed`), as shown in the existing test `governance_message_not_processed_in_same_block_when_queue_congested_with_low_priority_messages`.
4. A legitimate user then submits a properly fee-paying message from the same origin; because messages are serviced strictly in order and there is no per-message skip mechanism, their message is queued behind all outstanding attacker messages and is only processed once the attacker's backlog is drained across multiple blocks — reproducible directly by extending the referenced test's message count indefinitely.

			_: ProcessMessageOriginOf<T>,
			mut message: &[u8],
		) -> Result<bool, ProcessMessageError> {
			use ProcessMessageError::*;

			// Yield if the maximum number of messages has been processed this block.
			// This ensures that the weight of `on_finalize` has a known maximum bound.
			let current_len = MessageLeaves::<T>::decode_len().unwrap_or(0);
			if current_len >= T::MaxMessagesPerBlock::get() as usize {
				Self::deposit_event(Event::MessagePostponed {
					payload: message.to_vec(),
					reason: Yield,
				});
				return Err(Yield);
			}
