### Title
Pool reserves for `pallet-asset-conversion` are read directly from raw account balances, letting anyone permissionlessly donate tokens into a pool to lock them outside LP accounting and skew swap pricing - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`pallet-asset-conversion`'s `get_reserves` computes the "reserves" used for all swap pricing (`get_amount_out`/`get_amount_in`, `quote_price_exact_tokens_for_tokens`, `quote_price_tokens_for_exact_tokens`) directly from the pool account's raw asset balance, rather than from balances tracked/updated through the pallet's own deposit logic (`add_liquidity`). This mirrors the external report's broken invariant: an unprivileged party can push value directly into a vault/pool account through a path that bypasses the contract's intended deposit accounting (`_performDepositRewardByRewardType` in the report, `add_liquidity`/LP-share minting here), leaving the funds un-attributed to any owner and permanently stuck, while also corrupting the state (reserves/price) that other logic relies on.

### Finding Description
`get_reserves` derives the AMM reserves purely from the current on-chain balance of the pool account: [1](#0-0) 

These reserves are consumed by the swap-quoting functions that determine how much a user gets/pays on a swap: [2](#0-1) [3](#0-2) 

Because the pool account is just a normal, derivable, key-less account (`T::PoolLocator::pool_address`), **any account can transfer either pooled asset directly to it** using the ordinary `Assets::transfer`/`Balances::transfer` extrinsics, completely bypassing `add_liquidity` (the only path that is supposed to mint LP shares in exchange for deposited funds). The pallet's own test suite demonstrates this donation path is possible and reachable pre-pool-creation: [4](#0-3) 

and a related fix (`pr_12408`) shows the team is aware that reading raw balances for "pool prices" is fragile and previously understated reserves; the remaining design still reads full balances rather than an internally maintained ledger of LP-attributed deposits: [5](#0-4) 

The `quote_price_ignores_unrelated_non_sufficient_assets_in_pool_account` test only demonstrates that *unrelated* (non-pooled) asset donations are ignored — it does not protect against donations of the actual pooled asset pair, which do change `balance1`/`balance2` and therefore change every subsequent swap's output/input amount and LP redemption ratio: [6](#0-5) 

This is the direct structural analog of the report: `getRewardForUser` let anyone push tokens into `InfraredBGTMetaVault` outside the path (`_performDepositRewardByRewardType`) that would correctly record/route them; here, anyone can push tokens into the AMM pool account outside the path (`add_liquidity`) that would correctly mint LP shares for them. In both cases the guarding logic that should run on every incoming transfer (deposit bookkeeping) only runs when the "self-service" entrypoint is used, and a plain token transfer to the same account defeats it entirely.

### Impact Explanation
- **Fund lock**: Any tokens sent directly to the pool account are never credited as LP shares to anyone; they are permanently donated to the pool and cannot be withdrawn by the sender, matching the report's "permanent user-fund ... lock" impact class.
- **Reserve/price corruption**: Because `get_reserves`/`get_amount_out`/`get_amount_in` read raw balances, an attacker can manipulate quoted swap prices for other users transacting through the pool (classic AMM donation/inflation-style manipulation), and can distort `quote_price_exact_tokens_for_tokens`/`quote_price_tokens_for_exact_tokens`, which other pallets (e.g. asset-conversion-based transaction payment) rely on for fee conversion — an unbacked change to intended economic behavior of a runtime pallet, not merely an off-chain concern.
- This is a runtime bug in a shipped FRAME pallet (`pallet-asset-conversion`), used on Asset Hub for swaps and fee payment, so it is in-scope under "runtime bugs that compromise intended behavior" and "permanent user-fund ... lock."

### Likelihood Explanation
High. No privileged role, relayer, validator, or governance action is required — a plain, unprivileged `Assets::transfer`/`Balances::transfer_allow_death` call to a deterministically-derivable pool account address is sufficient. Pool account addresses are computed deterministically via `T::PoolLocator::pool_address`, so any user can compute them in advance for any asset pair, even before the pool exists (as shown by `cannot_block_pool_creation`).

### Recommendation
Track pool reserves via an internal ledger that is only updated through `add_liquidity`/`remove_liquidity`/`swap` accounting (i.e., maintain `Pools` storage fields for `reserve1`/`reserve2` and update them explicitly on every state-changing call), rather than deriving reserves from the pool account's raw balance. If raw-balance reads must be kept for robustness, add a `sync`-style reconciliation entrypoint (as in Uniswap V2) that only privileged/LP-attributable flows can invoke to fold in donated balance as new liquidity credited to a specific depositor, instead of silently treating all incoming balance as unattributed pool reserve.

### Proof of Concept
1. Attacker (or anyone) computes the deterministic pool account for `(asset1, asset2)` via `PoolLocator::pool_address`, without needing the pool to exist yet or being an LP.
2. Attacker directly transfers `asset1` (or `asset2`) tokens to that pool account using `pallet-assets`'s ordinary `transfer` call — bypassing `AssetConversion::add_liquidity` entirely.
3. `get_reserves` (lib.rs:1499-1514) now reports an inflated `balance1`/`balance2` that includes the donated amount, even though no LP shares were minted for it.
4. Any subsequent `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` call uses these inflated reserves through `get_amount_out`/`get_amount_in`, producing swap outputs/inputs different from what genuine LP-backed reserves would produce, and the donated tokens remain permanently stuck in the pool account, unclaimable by the donor and not represented by any LP token.

This is directly evidenced by the existing test `cannot_block_pool_creation` (substrate/frame/asset-conversion/src/tests.rs:2334-2391), which shows an attacker pre-funding a not-yet-created pool address with arbitrary token balances that are absorbed into the pool's raw balance.

		pub(crate) fn balance_path_from_amount_out(
			amount_out: T::Balance,
			path: Vec<T::AssetKind>,
		) -> Result<BalancePath<T>, DispatchError> {
			let mut balance_path: BalancePath<T> = Vec::with_capacity(path.len());
			let mut amount_in: T::Balance = amount_out;

			let mut iter = path.into_iter().rev().peekable();
			while let Some(asset2) = iter.next() {
				let asset1 = match iter.peek() {
					Some(a) => a,
					None => {
						balance_path.push((asset2, amount_in));
						break;
					},
				};
				let fee = Self::pool_fee_for(asset1, &asset2)?;
				let (reserve_in, reserve_out) = Self::get_reserves(asset1.clone(), asset2.clone())?;
				balance_path.push((asset2, amount_in));
				amount_in = Self::get_amount_in(fee, &amount_in, &reserve_in, &reserve_out)?;
			}
			balance_path.reverse();

			Ok(balance_path)
		}

		pub fn get_reserves(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
		) -> Result<(T::Balance, T::Balance), Error<T>> {
			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;

			let balance1 = Self::get_balance(&pool_account, asset1);
			let balance2 = Self::get_balance(&pool_account, asset2);

			if balance1.is_zero() || balance2.is_zero() {
				Err(Error::<T>::PoolEmpty)?;
			}

			Ok((balance1, balance2))
		}

fn quote_price_ignores_unrelated_non_sufficient_assets_in_pool_account() {
	new_test_ext().execute_with(|| {
		let user = 1;
		let dot = NativeOrWithId::Native;
		let token = NativeOrWithId::WithId(2);
		let pool_id = (dot.clone(), token.clone());

		create_tokens(user, vec![token.clone()]);
		assert_ok!(AssetConversion::create_pool(
			RuntimeOrigin::signed(user),
			Box::new(dot.clone()),
			Box::new(token.clone())
		));

		assert_ok!(Balances::force_set_balance(RuntimeOrigin::root(), user, 100000));
		assert_ok!(Assets::mint(RuntimeOrigin::signed(user), 2, user, 1000));
		assert_ok!(AssetConversion::add_liquidity(
			RuntimeOrigin::signed(user),
			Box::new(dot.clone()),
			Box::new(token.clone()),
			10000,
			200,
			1,
			1,
			user,
		));

		let price = AssetConversion::quote_price_exact_tokens_for_tokens(
			token.clone(),
			dot.clone(),
			60,
			true,
		);
		assert_eq!(price, Some(2302));

		assert_ok!(Assets::force_create(RuntimeOrigin::root(), 3, user, false, 1));
		assert_ok!(Assets::mint(RuntimeOrigin::signed(user), 3, user, 1000));
		let pool_account = <Test as Config>::PoolLocator::address(&pool_id).unwrap();
		assert_ok!(Assets::transfer(RuntimeOrigin::signed(user), 3, pool_account, 1));

		assert_eq!(
			AssetConversion::quote_price_exact_tokens_for_tokens(token, dot, 60, true),

		);
	});

#[test]
fn cannot_block_pool_creation() {
	new_test_ext().execute_with(|| {
		// User 1 is the pool creator
		let user = 1;
		// User 2 is the attacker
		let attacker = 2;

		let ed = get_native_ed();
		assert_ok!(Balances::force_set_balance(RuntimeOrigin::root(), attacker, 10000 + ed));

		// The target pool the user wants to create is Native <=> WithId(2)
		let token_1 = NativeOrWithId::Native;
		let token_2 = NativeOrWithId::WithId(2);

		// Attacker computes the still non-existing pool account for the target pair
		let pool_account =
			<Test as Config>::PoolLocator::address(&(token_1.clone(), token_2.clone())).unwrap();
		// And transfers the ED to that pool account
		assert_ok!(Balances::transfer_allow_death(
			RuntimeOrigin::signed(attacker),
			pool_account,
			ed
		));
		// Then, the attacker creates 14 tokens and sends one of each to the pool account
		for i in 10..25 {
			create_tokens(attacker, vec![NativeOrWithId::WithId(i)]);
			assert_ok!(Assets::mint(RuntimeOrigin::signed(attacker), i, attacker, 1000));
			assert_ok!(Assets::transfer(RuntimeOrigin::signed(attacker), i, pool_account, 1));
		}

		// User can still create the pool
		create_tokens(user, vec![token_2.clone()]);
		assert_ok!(AssetConversion::create_pool(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone())
		));

		// User has to transfer one WithId(2) token to the pool account (otherwise add_liquidity
		// will fail with `AssetTwoDepositDidNotMeetMinimum`)
		assert_ok!(Balances::force_set_balance(RuntimeOrigin::root(), user, 10000 + ed));
		assert_ok!(Assets::mint(RuntimeOrigin::signed(user), 2, user, 10000));
		assert_ok!(Assets::transfer(RuntimeOrigin::signed(user), 2, pool_account, 1));

		// add_liquidity shouldn't fail because of the number of consumers
		assert_ok!(AssetConversion::add_liquidity(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone()),
			10000,
			100,
			10000,
			10,
			user,
		));
	});
}
