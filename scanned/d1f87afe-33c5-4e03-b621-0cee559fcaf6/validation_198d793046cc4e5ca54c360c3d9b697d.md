**Analysis:**

`create_pure` writes a single storage item, `Proxies::<T>`, keyed by a derived "pure" account, containing `(BoundedVec<ProxyDefinition<...>>, deposit)` [1](#0-0) [2](#0-1) . This is the exact same storage type and layout that `add_proxy_delegate`, `remove_proxy_delegate`, `poke_deposit`, `proxy`, `proxy_announced`, `announce`, and `find_proxy` all read and mutate — there is no separate "pure-flagged" schema or alternate encoding that a different entrypoint could interpret more permissively. `find_proxy` simply scans the `ProxyDefinition` vec for a matching delegate/type regardless of whether the underlying account was created via `create_pure` or `add_proxy` [3](#0-2) .

The only attacker-controlled derivation is the account-ID computation in `pure_account`, which folds `who`, `height`, `ext_index`, `proxy_type`, and `index` through `blake2_256` [4](#0-3) . `kill_pure` re-derives the same address using the identical formula and parameters supplied by the caller, then asserts `proxy == who` before permitting deletion [5](#0-4) . Both the write path (`create_pure`) and the "consuming" path (`kill_pure`, `proxy`, `proxy_announced`) treat this address and the stored `ProxyDefinition` with one consistent meaning — there is no dual interpretation of the same bytes.

`Duplicate` is guarded via `Proxies::<T>::contains_key(&pure)` before insertion, preventing a batched/looped `create_pure` call from silently overwriting another pure account's proxy list with different semantics [6](#0-5) . No public entrypoint reads `Proxies::<T>` with a looser or alternate trust model than the one used at write time, so the required "shared storage misread by a different public path" precondition for this finding does not hold.
