# [M] Missing EIP-165 supportsInterface not EIP-7579 compliant

## Summary
Severity: Medium
Contest weight: 0.0515
Dataset id: 3914
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability concerns a smart account that advertises support for certain ERC‑165 interfaces while it does not actually implement the required functionality. According to EIP‑7579, a contract that claims to support an interface must return true from the ERC‑165 supportsInterface function only if every function defined by that interface executes without reverting. In the examined contract, the supportsInterface implementation returns true for interface identifiers even though the corresponding functions revert, violating the EIP‑7579 rule. This mismatch occurs because the contract’s supportsInterface logic does not check the runtime behavior of the interface functions; it simply reports static support based on a hard‑coded list. An attacker or integrator can exploit this by querying supportsInterface, receiving a positive response, and then invoking functions that are expected to exist. When those calls revert, the calling contract may assume a successful interaction, leading to failed transactions, unexpected reverts, or loss of gas. The impact is primarily functional: users may experience transactions that appear to be accepted by the wallet UI but later fail, causing confusion, wasted gas, and a breakdown of trust in the protocol’s advertised capabilities. The issue manifests whenever a caller performs an ERC‑165 interface check before interacting with the contract, which is a common pattern for modular smart accounts and composable DeFi protocols. All users, developers, and third‑party services that rely on the contract’s interface declarations are affected because they base integration decisions on the false positive. The problem was discovered during a systematic audit that compared the contract’s ERC‑165 implementation against the requirements of EIP‑7579, revealing that the fallback handlers do not enforce the “return false when a function reverts” rule. The bug can be hard to notice because the supportsInterface function itself does not revert and therefore appears to work, while the underlying functional calls silently fail only when invoked. To remediate, the contract should be updated so that supportsInterface dynamically reflects the actual executability of each interface function, returning false for any interface whose functions revert. This can be achieved by adding explicit checks or by routing unsupported calls through fallback handlers that correctly report false, ensuring compliance with EIP‑7579 and restoring reliable interface discovery for users and integrators.
