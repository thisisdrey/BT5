[download.rs::AttachmentsBatchStateContext::extend_with_attachments] When a peer responds to an AttachmentRequest at `/v2/attachments/<content_hash>` with a GetAttachmentResponse whose Attachment.content hash does not equal the AttachmentRequest.content_hash that was requested, does extend_with_attachments insert that mismatched Attachment into `self.attachments: HashSet<Attachment>` and mark the peer's ReliabilityReport::bump_successful_requests unconditionally, without ever checking response.attachment.hash() == request.content_hash? Preconditions: attacker runs an outbound-sync peer selected via get_prioritized_attachments_requests after inventory gossip claims availability. Call sequence: BatchedRequestsState::Done -> extend_with_attachments -> response.decode_atlas_get_attachment() -> self.attachments.insert(response.attachment) with no hash check against request.content_hash -> AttachmentsDownloader::run's Done arm calls atlasdb.insert_instantiated_attachment(&attachment) keyed by attachment.hash() (self-consistent) but then resolves ALL attachment_instances found via find_all_attachment_instances(&attachment.hash()) — meaning if the served bytes' *own* hash happens to differ from the AttachmentInstance's committed content_hash that triggered the request, no instance is falsely resolved, but the reliability report is falsely inflated for a peer serving unrequested/wrong data. Equality broken: attachment bytes served for a hash == the bytes whose hash the requested AttachmentInstance.content_hash committed to; here reliability scoring trusts a peer regardless of match. Impact: High — a malicious peer can serve arbitrary unrelated attachment bytes (self-hash-consistent but never matching what was actually asked for) and be scored as reliable, steering future rarest-first requests preferentially to itself, poisoning which peer is trusted for genuine BNS content. Proof idea: stackslib::net test constructing an AttachmentRequest with content_hash=H1, returning a GetAttachmentResponse with an Attachment whose content hashes to H2 != H1, calling extend_with_attachments, and asserting report.bump_successful_requests() was invoked despite the mismatch.]
