# [H] UniswapLiquidityAssetManager::_validateCollectFeesArgs() validates nullifier instead of note footer

## Summary
Severity: High
Contest weight: 0.0482
Dataset id: 15191
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability resides in the fee‑collection validation routine of the UniswapLiquidityAssetManager contract. The internal function _validateCollectFeesArgs() is intended to ensure that each fee claim is associated with a unique note footer, which acts as a one‑time identifier preventing a fee note from being reused. Instead of checking the note footer, the function mistakenly validates the nullifier field, which is unrelated to the uniqueness of the fee note. This mismatch means that the contract does not detect when the same note footer is submitted more than once. An attacker can therefore craft multiple collectFees transactions that reuse an identical note footer while providing distinct nullifiers, causing the contract to accept each claim as fresh. The exploitation flow consists of the attacker first obtaining a legitimate fee note, then submitting a second transaction that reuses the note footer but supplies a different nullifier; because the contract only verifies the nullifier, the second transaction passes validation and the fees are transferred again. The impact is a potential double‑spend of protocol fees, allowing the attacker to drain funds that should be allocated to liquidity providers or the protocol treasury. This condition occurs whenever the collectFees function is called with a note whose footer has already been used, and the contract’s internal bookkeeping does not record used footers. The affected parties include any user or liquidity provider expecting correct fee distribution, as well as the protocol itself, which may lose revenue. The issue was discovered during a manual audit that compared the intended business logic—unique note footers per fee claim—with the actual implementation, revealing that the wrong variable was being checked. The bug is subtle because both nullifier and note footer are part of the note data structure, and a superficial review may assume that any check on note‑related fields is sufficient. From a user’s perspective the symptom is that fees appear to be paid out multiple times, or that the protocol’s accounting shows a deficit despite no legitimate fee events. The root cause is a logical error: the validation routine checks the wrong identifier, violating the accounting invariant that each fee note may be collected exactly once. To remediate, the contract should be updated to verify the uniqueness of the note footer, store a record of consumed footers, and reject any collectFees call that presents a previously used footer. This aligns the implementation with the intended one‑time‑use semantics and restores the integrity of fee distribution.

## Recommendation
Check for note footers correctly.
