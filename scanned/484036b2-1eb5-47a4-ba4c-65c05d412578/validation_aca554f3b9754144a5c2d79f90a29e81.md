### Title
Unprotected zero-slippage swap in `SwapFirstAssetTrader::refund_weight` allows fee-refund value extraction via pool manipulation - (File: `cumulus/primitives/utility/src/lib.rs`)

### Summary
`SwapFirstAssetTrader` is an `xcm_executor::traits::WeightTrader` implementation that lets a parachain accept XCM `BuyExecution` fees in a foreign asset by auto-swapping it into a `Target` fee asset via `pallet_asset_conversion`'s `SwapCredit`. When unused weight is refunded, `refund_weight` swaps the surplus `Target` asset back into the asset the user originally paid with — but it calls `swap_exact_tokens_for_tokens` with `amount_out_min = None`, i.e. with **no slippage protection**, exactly the pattern flagged in the external report for OUSD's Uniswap swaps.

### Finding Description
In `cumulus/primitives/utility/src/lib.rs`, `SwapFirstAssetTrader::refund_weight`: [1](#0-0) 

calls:
```rust
let refund = SwapCredit::swap_exact_tokens_for_tokens(
    vec![Target::get(), refund_swap_asset],
    refund,
    None,   // <-- no minimum output enforced
);
```
This is contrasted with `buy_weight` in the same struct, which uses `swap_tokens_for_exact_tokens` with an exact target `fee` amount [2](#0-1) , and with the top-level pallet extrinsic `swap_exact_tokens_for_tokens`, which mandates a non-optional `amount_out_min` enforced by `ProvidedMinimumNotSufficientForSwap` [3](#0-2) . The `Swap`/`SwapCredit` trait explicitly supports `amount_out_min` for this reason [4](#0-3) , but `refund_weight` deliberately opts out of that guard.

Because `pallet_asset_conversion` pools are public AMMs (anyone can add/remove liquidity and swap), and `refund_weight` is executed automatically as part of ordinary XCM message execution (any account can construct an XCM program with `BuyExecution` using a non-`Target` asset and slight over-payment to trigger a refund), an attacker can:
1. Manipulate the `Target`/payment-asset pool price immediately before the XCM message executes (e.g., by including a swap in the same block/extrinsic sequence or sandwiching the block containing the refund-triggering XCM), pushing the price of `Target` down relative to the refund asset.
2. Let the refund swap execute at this manipulated price, receiving less value transferred to the user's held credit than it should, with the difference captured by the attacker when they reverse their manipulating trade.

Existing guards do not stop this: the top-level `swap_exact_tokens_for_tokens` extrinsic enforces `amount_out_min`, but this internal call to the trait method bypasses that enforcement entirely by passing `None`, so `do_swap_exact_credit_tokens_for_tokens`'s `ensure!(amount_out_min.map_or(true, |a| amount_out >= a), ...)` check is a no-op [5](#0-4) .

### Impact Explanation
This falls under "public underpriced work that degrades ... or stalls bridge/queue processing" and "theft/unbacked value" categories: value collected as XCM execution fees (which should be returned to the user or accounted correctly) can be silently extracted by a third party via price manipulation of the public AMM pool, with no way for the affected refund path to detect or reject unfavorable pricing. Any runtime wiring `SwapFirstAssetTrader` as its `WeightTrader` (paying XCM execution fees in non-native assets via `pallet_asset_conversion`) is exposed. The magnitude scales with the size of the refund and the manipulability/depth of the specific asset pool, mirroring the original report's dependency on TVL.

### Likelihood Explanation
No privileged actor, relayer, or admin is required — only a public account able to submit ordinary transactions/XCM programs that trigger BuyExecution overpayment and interact with the relevant swap pool (which is itself permissionlessly created/funded via `pallet_asset_conversion`). This is directly analogous to the original report's "sandwich the call to harvest/allocate, no flash-loan needed" scenario.

### Recommendation
Do not pass `None` in `refund_weight`. Compute an acceptable minimum output (e.g., derive it from `QuotePrice::quote_price_exact_tokens_for_tokens` at call time, or track the amount originally paid in `refund_swap_asset` for that user and use it as the floor), and use `Some(min_amount)` so the refund is rejected (and reprocessed via `OnUnbalanced`/held asset) rather than silently executed at an unfavorable, manipulated price.

### Proof of Concept
1. Configure a runtime with `SwapFirstAssetTrader` as `WeightTrader`, using `pallet_asset_conversion` pools for `Target`↔other-asset conversion.
2. Attacker creates/uses an existing `Target`/`X` pool with modest liquidity.
3. Attacker submits an XCM message (or triggers one, e.g. a reserve transfer with `BuyExecution` in asset `X`) that overpays weight so a non-trivial `refund_weight` swap back into `X` will occur.
4. In the same block (or via sandwiching if the mempool/ordering allows), the attacker swaps in the `Target`/`X` pool to depress the price of `Target` in terms of `X` just before the refund executes, then reverses the trade after.
5. `refund_weight`'s `swap_exact_tokens_for_tokens(..., None)` executes at the manipulated price, delivering less `X` back to the fee-payer's credit than fair value; the attacker's reversing trade recoups the difference as profit, extracted from the fee-payer/protocol.
