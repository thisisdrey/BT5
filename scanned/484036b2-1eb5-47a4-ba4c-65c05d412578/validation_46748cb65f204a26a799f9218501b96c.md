### Title
`RewardDestination::Staked` reward payout is silently forfeited when the stash ledger lookup fails - ([File: substrate/frame/staking/src/pallet/impls.rs])

### Summary
The Velodrome bug is structurally: a reward-claim path unconditionally depends on a piece of account state (`veNFT` lock not expired) that can legitimately be false, and when it is false the payout call has **no fallback branch**, so the computed/earned reward is permanently unreachable for that account. The closest verifiable analog in this repository is in `pallet-staking`'s `make_payout` (and the `staking-async` equivalent `make_payout_legacy`), where a staker who set `RewardDestination::Staked` has their reward silently dropped — not reverted, not retried, just discarded — if the ledger lookup for their stash fails at payout time.

### Finding Description
`Pallet::<T>::make_payout` at [1](#0-0)  computes the payout destination via `Self::payee(...)`. When `dest == RewardDestination::Staked`, the code does:

```rust
RewardDestination::Staked => Self::ledger(Stash(stash.clone()))
    .and_then(|mut ledger| {
        ledger.active += amount;
        ledger.total += amount;
        let r = asset::mint_into_existing::<T>(stash, amount);
        let _ = ledger.update().defensive_proof(...);
        Ok(r)
    })
    .unwrap_or_default(),
``` [2](#0-1) 

If `Self::ledger(Stash(stash.clone()))` returns `Err` (e.g. the ledger entry is missing/corrupted for that stash — analogous in spirit to the veNFT's "expired" state that blocks the underlying operation), `.and_then` short-circuits and `.unwrap_or_default()` yields `None`. `make_payout` returns `None` for the imbalance, meaning **no tokens are minted at all** for that staker's share of the era reward. Crucially, this is not a `DispatchError` that aborts the extrinsic — `payout_stakers_by_page` still succeeds, the era/page is still marked as claimed (`ClaimedRewards`/history-depth bookkeeping advances), and the reward for that specific nominator/validator page entry is gone forever with no way to re-trigger it, exactly like the stuck VELO rebase reward that can never be pulled out of `RewardsDistributor` once the veNFT is expired.

The `staking-async` sibling code exhibits the identical pattern in `make_payout_legacy`: [3](#0-2) , and even the newer "provider" model (`make_payout_from_provider`) which uses `Currency::transfer` from an era pot only updates the ledger `if let Ok(mut ledger) = ...` — if the ledger fetch fails, the transfer to the payout account has already happened, but the ledger the staker expected to be “Staked” never sees the extra `active`/`total`, silently diverging state without any error surfaced: [4](#0-3) .

Existing guards do not stop this: there is no `ensure!`/ `Error::<T>::...` return path for this branch — it is a best-effort `.unwrap_or_default()` fallback, and the surrounding `payout_stakers*` dispatchable treats a `None` imbalance from `make_payout` identically to a legitimate zero-reward case (see the early-return `if amount.is_zero() { return None; }` guard at the top of the function, which cannot distinguish "nothing to pay" from "failed to pay Staked destination"). There is no defensive log/event on this silent-loss branch as there is for the equivalent `staking-async::transfer_validator_incentive` failure path, which does emit `Event::Unexpected`/`defensive!` [5](#0-4) .

### Impact Explanation
A legitimate staker's era reward is silently and permanently lost (never minted, never retried, and the era is marked as already paid), which is a fund-loss/permanent-lock class impact matching the required "theft or unbacked mint or unlock ... permanent user-fund ... lock" bar. Unlike the Treasury `payout.expire_at` case (already fixed via prdoc `pr_7959`) which is a *transient*, retryable liquidity shortage, this is a payout-branch that can never be retried once the extrinsic succeeds, because the claimed/paid bookkeeping for that era/page is advanced unconditionally regardless of whether the `Staked` branch actually succeeded.

### Likelihood Explanation
Triggering requires only that `Self::ledger(Stash(stash))` fail to resolve for a stash that has `RewardDestination::Staked` set at the moment `payout_stakers*` runs for a past era — no privileged/validator/relayer access is needed; this can be caused by ordinary user-facing operations that can leave a lookup momentarily inconsistent for a stash between reward-eligible eras and payout execution (e.g. after certain unbonding/migration sequences that null out or re-key the ledger entry, while the reward for a prior era is still pending). I was not able to fully confirm, in the time available, an exact concrete transaction sequence in the current codebase that reliably drives `Self::ledger` to return `Err` for a stash that still has a `RewardDestination::Staked` payee and an unpaid era reward — this would require deeper investigation of `Ledger`/`Bonded` storage invariants and any related migrations to pin down a fully reproducible sequence.

### Recommendation
In `make_payout` / `make_payout_legacy` (and the analogous `make_payout_from_provider`), when the `RewardDestination::Staked` ledger lookup fails, do not silently drop the reward: either (a) fall back to crediting the free balance of the stash directly (mirroring the VELO fix's "send to owner instead"), or (b) return an explicit error/defensive event and refuse to mark the era/page as claimed, so the payout can be retried once the ledger inconsistency is resolved, ensuring the reward is conserved and eventually settled to the rightful beneficiary exactly once.

### Proof of Concept
Not independently reproduced against this repository within the current investigation. The code path is shown above; a full PoC would require constructing a runtime test that (1) sets a stash's `Payee` to `RewardDestination::Staked`, (2) reaches a state where `Ledger::<T>::get`/`Self::ledger(Stash(...))` returns `Err` for that stash while an era reward is still pending, and (3) calls `payout_stakers_by_page` to observe that the call returns `Ok` (era marked paid) while `asset::stakeable_balance`/free balance shows no increase. This last step (finding a legitimate way to null the ledger while `Payee` still points to `Staked` and rewards are pending) is the part I could not fully verify in the time available, so confidence in end-to-end exploitability is moderate rather than definitive.

	fn make_payout(
		stash: &T::AccountId,
		amount: BalanceOf<T>,
	) -> Option<(PositiveImbalanceOf<T>, RewardDestination<T::AccountId>)> {
		// noop if amount is zero
		if amount.is_zero() {
			return None;
		}
		let dest = Self::payee(StakingAccount::Stash(stash.clone()))?;

		let maybe_imbalance = match dest {
			RewardDestination::Stash => asset::mint_into_existing::<T>(stash, amount),
			RewardDestination::Staked => Self::ledger(Stash(stash.clone()))
				.and_then(|mut ledger| {
					ledger.active += amount;
					ledger.total += amount;
					let r = asset::mint_into_existing::<T>(stash, amount);

					let _ = ledger
						.update()
						.defensive_proof("ledger fetched from storage, so it exists; qed.");

					Ok(r)
				})
				.unwrap_or_default(),
			RewardDestination::Account(ref dest_account) =>
				Some(asset::mint_creating::<T>(&dest_account, amount)),
			RewardDestination::None => None,
			#[allow(deprecated)]
			RewardDestination::Controller => Self::bonded(stash)
					.map(|controller| {
						defensive!("Paying out controller as reward destination which is deprecated and should be migrated.");
						// This should never happen once payees with a `Controller` variant have been migrated.
						// But if it does, just pay the controller account.
						asset::mint_creating::<T>(&controller, amount)
		}),
		};
		maybe_imbalance.map(|imbalance| (imbalance, dest))
