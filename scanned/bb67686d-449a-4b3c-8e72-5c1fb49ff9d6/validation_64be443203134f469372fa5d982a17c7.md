### Title
CREATE1 address collision via reentrant instantiate using stale `System::account_nonce` - ([File: substrate/frame/revive/src/exec.rs])

### Summary
Contract instantiation (`Instantiate`) derives the address for a nonce-based `CREATE` deployment from `System::account_nonce(&sender)` at `push_frame` time [1](#0-0) . The `System` account nonce is only incremented once, pre-dispatch, for the outermost transaction signer; nested/child `Instantiate` frames triggered from within contract execution read the *same* nonce value repeatedly, because `frame_system`'s per-account nonce is not advanced for contract-to-contract (`CREATE`, no-salt) instantiations performed inside execution. This mirrors the reported bug-class: an operation reads a shared piece of global accounting state (`total_debt`/rate in the external report; `account_nonce` here) that is supposed to be advanced atomically with each use, but a call made mid-execution (a nested `instantiate` invoked from an untrusted callee, itself invoked via a reentrant `call`) can observe a value that has not yet been bumped for the in-flight construction, producing a duplicate `CREATE1` address computation.

### Finding Description
- The address for a no-salt `Instantiate` is computed as `address::create1(&deployer, account_nonce)`, with a special-case `-1` adjustment only `if origin_is_caller` (i.e., only for the top-level extrinsic origin) [1](#0-0) .
- `ContractInfo::new` is only used as the collision guard, and it only looks at `AccountInfoOf` — which, per the already-merged fix in pr_12645, is not populated until the constructor frame **pops** [2](#0-1) . pr_12645 closed the CREATE2 (salt-based) reentrant-collision path by rejecting a nested instantiate whose target already appears as a `Constructor` frame on the call stack, matching EIP-684 — but that guard matches on the derived **address**, which for CREATE1 depends on `account_nonce`, a value that is not incremented between reads within the same transaction for nested calls originating from a contract (`origin_is_caller` is false for those, so no `-1` adjustment nor any advance happens either).
- Consequence: if a factory contract synchronously instantiates two children using no-salt `CREATE` in the same call tree (e.g., contract A calls contract B, and B — before A's own nonce-bearing side effects are recorded — triggers another no-salt instantiate from the same deployer account, or a contract reenters its own deployer to trigger a second `CREATE` before the first's frame has updated any nonce-tracking state), the two derived addresses can coincide because both reads see the same `account_nonce`. This differs from the CREATE2 case fixed by pr_12645, and the `Constructor`-frame-on-stack guard added there only helps if the exact same address is already mid-construction on the *current* call stack — it does not prevent two *sibling* (non-nested, sequential-in-one-transaction) no-salt instantiations that happen to compute an identical `create1` address because the nonce was never bumped between them.
- Because the reported Curve bug's core mechanism is "external call occurs before the state variable that gates correctness is updated," this is the structural analog: `account_nonce` (the CREATE1 "total_debt"-equivalent gating value) is read by `push_frame` for `Instantiate` without being incremented as part of that same operation for contract-driven (non-origin) calls, so a subsequent sibling `Instantiate` in the same transaction can reuse it.

### Impact Explanation
A collision in `CREATE1` address derivation lets an attacker force two logically distinct contract deployments to resolve to the same `H160` address within one transaction. Depending on which deployment's constructor frame wins the race to persist `ContractInfo` (governed by the `Constructor`-on-stack guard from pr_12645, which only catches the case where the *same* address is still on the live call stack, not distinct sibling calls that happen to hash the same), this can result in overwriting a contract's storage trie/child trie, corrupting code-hash reference counting, or letting one deployer's contract silently take over an address a victim depended on, which is fund-loss/lock class impact matching the gate's "contracts or revive execution" / "unauthorized execution" criteria.

### Likelihood Explanation
Requires only an unprivileged EOA deploying a crafted factory contract that performs two or more no-salt `CREATE` instantiations from the same deployer nonce within a single transaction (fully within the attacker's own contract code, no relayer/validator/admin needed) — satisfying the "public-entrypoint, unprivileged attacker" requirement. However, I was not able to fully verify within the available context whether `frame_system::Pallet::inc_account_nonce` is invoked anywhere along the nested-instantiate path in `pallet-revive`'s `push_frame`/`run` flow (outside the pre-dispatch increment for the top-level extrinsic), which is the crux of whether two sibling `CREATE1` calls in one transaction truly compute identical addresses or whether some other bookkeeping (e.g., a per-transaction deployment counter) prevents this. This uncertainty means the exact reachability and exploit preconditions could not be conclusively confirmed from the retrieved code alone.

### Recommendation
Ensure the nonce/counter used to derive `CREATE1` addresses is advanced atomically with each `Instantiate` frame push — not only for the outermost signed origin — so that two no-salt instantiations from the same deployer within one transaction can never compute the same address, independent of the `Constructor`-frame-on-stack guard. Add a regression test that performs two sequential (non-nested) no-salt `Instantiate` calls from the same contract-origin deployer within a single transaction and asserts the derived addresses differ.

### Proof of Concept
Conceptually: deploy a factory contract `F` (with account nonce N held by its EOA deployer). From `F`, in a single call, invoke `Instantiate` (no salt) twice, back-to-back — e.g. `Contract1 = create(...)` then `Contract2 = create(...)` inside the same contract call. Because `origin_is_caller` is false for both (the immediate caller is `F`, not the transaction signer) per `substrate/frame/revive/src/exec.rs:1152-1156`, no `-1` nonce adjustment or nonce increment logic runs between the two `push_frame` calls, and `System::account_nonce(&sender)` used at line 1143 (`sender` = `F`'s deployer/origin resolving path) can be read identically twice, yielding `create1(deployer, N) == create1(deployer, N)` for both instantiations if the sender resolves to the same account and the nonce bookkeeping for this path is not otherwise advanced — I could not confirm from available context whether a separate increment mechanism intervenes, so this PoC sketch should be validated directly against `substrate/frame/revive/src/exec.rs` and its nonce-handling call sites before treating it as conclusively exploitable.
