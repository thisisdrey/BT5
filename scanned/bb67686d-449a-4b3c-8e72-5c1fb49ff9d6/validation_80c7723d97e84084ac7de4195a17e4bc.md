## Analysis

The Frankencoin bug's core broken invariant: a state transition sets a lock/cooldown value with **no cap and no recovery path**, permanently trapping the legitimate owner's assets. The closest local analog is in `pallet-scarcity`'s `AsScarcity` transaction extension, which implements an unbounded, uncapped exponential backoff lock on an NFT purse key after a failed dispatch, with no self-service way to clear it. ### Title
Unbounded exponential backoff lock in `AsScarcity` permanently strands NFT purse keys with no owner-side recovery - (File: `substrate/frame/scarcity/src/extension.rs`)

### Summary
`pallet-scarcity`'s only path for a holder to move or burn their own NFT is a signed transaction validated through the `AsScarcity` transaction extension, which rewrites the signed origin into `Origin::Nft`. `transfer` and `burn` are only callable via that origin. On any dispatch failure, `post_dispatch_details` writes an ever-growing `LockInfo{ retries, until }` into `Locked<T>` for the purse's owner key [3](#0-2) , and `validate` rejects every further `AsScarcity` transaction from that account until `until` elapses [4](#0-3) . The backoff formula `multiplier = 2^(retries-1)` (capped only at exponent 63) has no ceiling on the resulting `until` timestamp [5](#0-4) , and `retries` only resets via `Locked::remove` on a *successful* dispatch [6](#0-5) . There is no root, governance, or permissionless call in the pallet to reset `Locked<T>` for a purse key.

### Finding Description
A dispatch can fail *after* validation passes because `transfer`'s occupancy/self-transfer checks are re-verified at dispatch time (module doc explicitly acknowledges this: "the dispatch-time checks remain for genuine same-block races") [7](#0-6)  while the actual `transfer` call re-checks `SelfTransfer`/`AddressOccupied` in the pallet itself [8](#0-7) . Any observer of the mempool can occupy the announced destination purse key before the victim's transaction executes, causing the victim's `transfer` to fail at dispatch. Each such failure doubles the backoff window (`multiplier = 2^(retries-1) * LockPeriod`), and because `retries` is never decremented and only clears on success, an attacker who can repeatedly force failures (or simple repeated bad luck/network races) drives `until` toward `now + 2^63 * LockPeriod` — for any non-trivial `LockPeriod` this is effectively "locked forever," with the owner unable to submit any further `AsScarcity`-gated `transfer`/`burn` since that is the *only* dispatch path for moving/burning their NFT. This exactly mirrors Position.sol's `deny()` setting `cooldown = expiration` with no cap and no way back for the position owner.

### Impact Explanation
The purse owner permanently loses the ability to transfer or burn their own NFT through the pallet's only exposed self-service path. There is no `unlock`/`force_unlock`/root call to reset `Locked<T>`; the only theoretical escape is the *collection owner* forcibly calling `force_transfer`/`force_burn` (a privileged, unrelated third party who may be unavailable, unaware, or uncooperative), which is not a guaranteed remedy for the purse holder. This is a permanent user-fund (NFT) lock, matching the "permanent user-fund ... lock" category in the impact gate.

### Likelihood Explanation
Triggering one failed dispatch (e.g., by occupying an announced destination purse key before a broadcast transaction executes) is unprivileged and requires no admin/governance/validator/relayer role — it only requires observing a pending transaction naming its destination purse, which the extension itself carries in cleartext (`AsScarcityInfo::AsNft` and the call's `to` parameter). Repeating this a handful of times drives the exponential lock past any practically recoverable duration, since the multiplier caps only the *exponent* (63) rather than the resulting lock length, and `LockPeriod` is a runtime constant with no configured upper bound on `until`.

### Recommendation
- Cap `until` to a fixed maximum absolute duration from `now`, independent of `retries`.
- Add a way to reset `retries`/`Locked<T>` for a purse key that does not require a *successful* `AsScarcity` dispatch — e.g., allow the purse owner to clear the lock via an ordinary signed (non-`AsScarcity`) call, or decay `retries` over elapsed time rather than only on success.
- Consider decoupling `AddressOccupied`/`SelfTransfer` validation-time and dispatch-time checks so that races against a mempool-visible destination cannot trigger the backoff penalty at all (e.g., don't apply/escalate the lock for errors caused solely by external state changes to the destination rather than the caller's own fault).

### Proof of Concept
1. Victim (purse `A`, holding NFT `X`) broadcasts a signed `transfer(to = B)` wrapped with `AsScarcity{instance: X, state_nonce: n}`. This passes `validate` because `B` is currently unoccupied [7](#0-6) .
2. Attacker observes the pending transaction in the mempool and submits (and gets included first) a `mint`/`transfer` that puts an NFT into purse `B`.
3. Victim's transaction reaches `prepare`, taking the NFT out of `A` [9](#0-8) , then dispatch fails with `AddressOccupied` because `B` is now occupied [10](#0-9) .
4. `post_dispatch_details` restores the NFT to `A` and writes `Locked::<T>::insert(A, LockInfo{retries:1, until: now + LockPeriod})` [3](#0-2) .
5. Attacker repeats steps 2–4 against every new destination the victim tries, each time doubling `retries` and the lock window (`2, 4, 8, ... 2^63` × `LockPeriod`), until `A` is locked out for a duration indistinguishable from permanent, with no call in the pallet to reset it except a privileged, unrelated collection owner's `force_transfer`/`force_burn`.

	fn failed_dispatch_lock(previous: Option<LockInfo>) -> LockInfo {
		let retries = previous.map(|lock| lock.retries.saturating_add(1)).unwrap_or(1);
		let exponent = retries.saturating_sub(1);
		let multiplier = 2u64.saturating_pow(u32::from(exponent).min(63));
		LockInfo {
			retries,
			until: T::UnixTime::now()
				.as_secs()
				.saturating_add(multiplier.saturating_mul(T::LockPeriod::get())),
		}
	}
}

	fn post_dispatch_details(
		pre: Self::Pre,
		_info: &DispatchInfoOf<<T as frame_system::Config>::RuntimeCall>,
		_post_info: &PostDispatchInfoOf<<T as frame_system::Config>::RuntimeCall>,
		_len: usize,
		result: &DispatchResult,
	) -> Result<Weight, TransactionValidityError> {
		if let Pre::UsingNft { owner, nft } = pre {
			if result.is_err() {
				NftsByOwner::<T>::insert(&owner, nft);
				Locked::<T>::insert(&owner, Self::failed_dispatch_lock(Locked::<T>::get(&owner)));
			} else {
				Locked::<T>::remove(&owner);
			}
		}
		Ok(Weight::zero())
	}

		pub fn transfer(origin: OriginFor<T>, to: T::AccountId) -> DispatchResultWithPostInfo {
			let Ok(Origin::Nft { owner, nft }) = origin.into() else {
				return Err(DispatchError::BadOrigin.into());
			};
			ensure!(to != owner, Error::<T>::SelfTransfer);
			ensure!(!NftsByOwner::<T>::contains_key(&to), Error::<T>::AddressOccupied);

			let nft = Nft { last_moved: T::UnixTime::now().as_secs(), state_nonce, ..nft };

			Instances::<T>::insert(nft.instance, &to);
			Self::deposit_event(Event::Transferred { instance: nft.instance, from, to });
