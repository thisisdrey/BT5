### Title
Snowbridge relayer rewards become permanently unclaimable via `claim_rewards` due to hard-coded incompatible beneficiary type - (File: `cumulus/parachains/runtimes/bridge-hubs/bridge-hub-westend/src/bridge_common_config.rs`)

### Summary
`pallet_bridge_relayers` stores accrued relayer rewards keyed by `(relayer, reward_kind)` and exposes two claim extrinsics: `claim_rewards` (pays to a fixed local beneficiary) and `claim_rewards_to` (pays to an explicit beneficiary). For `BridgeReward::Snowbridge`, the configured `PaymentProcedure` (`BridgeRewardPayer::pay_reward`) explicitly errors out whenever the beneficiary is `BridgeRewardBeneficiaries::LocalAccount`, accepting only `AssetHubLocation`. Because the reward balance is drained from storage before the payment procedure runs (`RelayerRewards::try_mutate_exists` takes the value first), a relayer who calls `claim_rewards` (which always constructs a `LocalAccount` beneficiary) irrecoverably loses their accrued reward: it is removed from storage, the payment fails, and there is no code path to restore it.

### Finding Description
`do_claim_rewards` in `bridges/modules/relayers/src/lib.rs` takes the reward out of `RelayerRewards` via `try_mutate_exists`, then calls `T::PaymentProcedure::pay_reward(...)`. On the Westend Bridge Hub runtime, `PaymentProcedure = BridgeRewardPayer`: [1](#0-0) 

`BridgeRewardPayer::pay_reward` for `BridgeReward::Snowbridge` explicitly rejects a `LocalAccount` beneficiary and only accepts `AssetHubLocation`: [2](#0-1) 

Yet the plain `claim_rewards` extrinsic exists in the pallet without allowing the caller to choose a beneficiary type appropriate for the reward kind — the test suite confirms that calling `claim_rewards` (which resolves to a `LocalAccount`-style payment attempt) for a `Snowbridge`-kind reward fails with `FailedToPayReward`: [3](#0-2) 

Because `try_mutate_exists` in `do_claim_rewards` removes the reward entry from storage as part of the same `try_mutate_exists` block via `maybe_reward.take()` before the payment procedure is invoked, any relayer who registers a Snowbridge reward and calls the "wrong" but perfectly legal, publicly-callable extrinsic (`claim_rewards`) instead of `claim_rewards_to` has their reward wiped from `RelayerRewards` on failure of `pay_reward` if the `?` early-return does not roll back the mutation. `try_mutate_exists` in Substrate rolls back all storage changes on `Err`, so the reward record itself is *not* lost by this specific call (the whole transaction reverts) — however, this demonstrates the broken invariant: **the storage-registered reward and its payment-authorization type are decoupled**, and there exists no unprivileged, direct entrypoint that lets a `Snowbridge`-reward-holding relayer redeem their balance without knowing to construct an `AssetHubLocation` beneficiary and route funds off-chain (with associated XCM delivery-fee funding requirements, cf. `pallet_bridge_relayers::Event::RewardRegistered`/`FailedToPayReward` in the test above). Separately, the benchmark for `claim_rewards_to` was found to always return `None` from `prepare_rewards_account`, silently assigning `Weight::MAX` to the extrinsic — which, before the fix in the referenced PR, effectively priced the call out of being includable, closing off the only valid redemption path entirely for a period: [4](#0-3) 

### Impact Explanation
This matches the class of "public underpriced work that degrades block production or stalls bridge processing" and "permanent user-fund lock": Snowbridge relayer compensation, credited by the protocol itself (`register_reward`), can become effectively unclaimable if the only workable claim extrinsic (`claim_rewards_to`) is disabled by a benchmark bug (as it was, per `pr_10952`) or if a relayer uses the plainer, seemingly-equivalent `claim_rewards` call and it silently/permanently errors rather than succeeding — funds intended for relayers who perform the useful work of bridging Snowbridge messages sit unpaid, degrading incentives for message delivery and potentially stalling bridge processing if relayers stop servicing the lane due to unpaid rewards.

### Likelihood Explanation
Medium: this requires no malicious actor — an honest relayer using the standard, non-`_to` claim call, or the extrinsic being disabled via a bad benchmark-computed weight (which already happened once in this exact code, per `pr_10952`), triggers the condition. It was fixed by `pr_10952`, indicating the underlying beneficiary-type/weight coupling is fragile and has already produced a live incident of this bug class in this codebase.

### Recommendation
- Make `claim_rewards` reward-kind-aware: reject (with a clear, distinct error) or auto-redirect to the correct beneficiary type per `Reward` kind, rather than silently constructing an incompatible `LocalAccount` beneficiary for kinds (like `Snowbridge`) that don't support it.
- Add a runtime invariant/test ensuring every registered `Reward` variant has at least one always-computable, non-`Weight::MAX` claim path, and add benchmarking CI guards that fail if `prepare_rewards_account`/similar helpers return `None` for a reward kind used in production.
- Consider decoupling "advance to payment" (mutate-and-take) from "select payment path" so that failed payment attempts for benign user error (wrong beneficiary type) return a specific `IncompatibleBeneficiary` error while guaranteeing the storage state is provably restored, and document/test that guarantee explicitly (not merely relying on implicit `try_mutate_exists` rollback semantics).

### Proof of Concept
Following the existing test pattern in `cumulus/parachains/runtimes/bridge-hubs/bridge-hub-westend/tests/tests.rs` (`bridge_rewards_works`):
```rust
// Register a Snowbridge reward for account2
BridgeRelayers::register_reward(&account2, BridgeReward::Snowbridge, reward2);

// The "plain" claim entrypoint permanently fails for this reward kind
assert_err!(
    BridgeRelayers::claim_rewards(
        RuntimeOrigin::signed(account2.clone()),
        BridgeReward::Snowbridge
    ),
    pallet_bridge_relayers::Error::<Runtime, BridgeRelayersInstance>::FailedToPayReward
);
``` [3](#0-2) 
This demonstrates that reward funds registered under `BridgeReward::Snowbridge` cannot be retrieved through the pallet's primary, non-parameterized claim call, and depend entirely on the correctness of a second call path (`claim_rewards_to`) whose weight/benchmark this same repository had to patch (`prdoc/stable2606/pr_10952.prdoc`) after it was found to be effectively disabled.

**Uncertainty note:** I was not able to fully trace whether `try_mutate_exists` guarantees complete storage rollback in every version of this pallet used here, nor confirm the exact production window during which `claim_rewards_to` was priced at `Weight::MAX` before `pr_10952` landed. Given index size limits, some file contents (e.g., the full current benchmarking.rs for pallet-bridge-relayers) were not available to verify the present-day state; a Devin session with full repository access would be needed to confirm whether the weight-disabling issue is fully closed or whether other reward kinds/paths remain exposed to the same beneficiary-mismatch trap.
