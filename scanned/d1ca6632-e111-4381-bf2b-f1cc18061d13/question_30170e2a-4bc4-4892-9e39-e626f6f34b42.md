Target: `MultiPayload::verify` and `MultiPayload::hash` (contracts/defuse/core/src/payload/multi.rs), each variant computing hash differently (SHA-256 for NEP-413/raw/webauthn, Keccak256-based prehash for ERC-191/TIP-191, TonConnect cell hash, SEP-53). Attacker submits the SAME `DefusePayload<DefuseIntents>` JSON string embedded inside two different `MultiPayload` variants they can both produce valid signatures for using two DIFFERENT keys they hold under two DIFFERENT `signer_id` accounts they control, then executes both in one `execute_intents` batch expecting `verify_intent_nonce`/`commit_nonce` (keyed by `(signer_id, nonce)`) to treat them as independent. Preconditions: attacker registers same nonce value under two different signer_ids (both self-owned) -- not a victim exploit but tests whether the per-standard `hash()` used for event logging/intent hash could be confused with the value bound to nonce commitment. Call sequence: `execute_signed_intent` computes `hash = signed.hash()` (envelope-specific) purely for event/logging (`inspector.on_intent_executed`), while nonce uniqueness is enforced via `self.state.commit_nonce(signer_id.clone(), nonce)` keyed on `signer_id`+`nonce`, NOT on `hash`. Binding: the number of times a given `(signer_id, nonce)` pair settles == 1 forever, independent of which standard/envelope produced the hash. Impact: Critical only if two different envelope encodings of the SAME `DefusePayload` (same signer_id, same nonce) both pass `commit_nonce` because envelope bytes differ - verify this is impossible since dedup keys off `(signer_id, nonce)` not raw bytes. Proof: cargo test executing two `MultiPayload` variants (e.g., Nep413 and RawEd25519) carrying identical `signer_id`+`nonce`+intents signed by the SAME underlying key re-encoded in two envelopes, asserting the second call errors with a nonce-already-used error.
