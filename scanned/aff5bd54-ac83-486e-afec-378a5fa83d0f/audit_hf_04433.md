# [M] M-05 | GLV Actions Cannot Be Simulated

## Summary
Severity: Medium
Contest weight: 0.0380
Dataset id: 21909
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability concerns two internal simulation functions – simulateExecuteGlvDeposit and simulateExecuteGlvWithdrawal – that are intended to provide a read‑only preview of a GLV (Generalized Liquidity Vault) deposit or withdrawal. Both functions are protected by the onlyController modifier, which restricts calls to the contract’s controller address, but they are not linked to the public GlvRouter contract that external callers use to interact with the GLV system. Because the router does not expose any external entry point for these simulation methods, they cannot be invoked from off‑chain tools, front‑end interfaces, or other contracts. The root cause is a mismatch between the access control design (onlyController) and the contract architecture (router as the sole public gateway). An attacker does not need to exploit a classic code execution flaw; instead, the issue can be abused by any user or integrator who expects to call the simulation functions to estimate outcomes before committing real funds. When a user attempts to simulate a deposit or withdrawal through the usual UI or SDK, the call silently fails or returns no data, leading the user to believe the operation will succeed with certain parameters while in reality the system cannot provide the preview. This can cause users to submit transactions with incorrect assumptions, potentially resulting in unexpected slippage, insufficient gas, or even failed transactions that waste fees. The problem manifests whenever a caller tries to invoke the simulation functions directly or indirectly via the router – which, by design, does not forward those calls. The affected parties include end‑users, front‑end developers, and any protocol component that relies on accurate pre‑execution estimates for risk management or UI display. The issue was discovered during a manual audit of the GLV contract suite, where the auditor noted the presence of the simulate functions but could not locate any public accessor. The bug is subtle because the functions compile without errors and appear in the source, yet they are effectively dead code from the perspective of external callers, making it easy to overlook during testing. To remediate, the simulateExecuteGlvDeposit and simulateExecuteGlvWithdrawal functions should be added to the GlvRouter’s public interface, either by exposing them directly or by providing a proxy that forwards calls while preserving the onlyController restriction. This change restores the intended simulation capability, aligns the access control model with the contract architecture, and prevents users from encountering silent failures when trying to preview GLV actions.

## Recommendation
Expose the simulateExecuteGlvDeposit and simulateExecuteGlvWithdrawal functions through the GlvRouter.
