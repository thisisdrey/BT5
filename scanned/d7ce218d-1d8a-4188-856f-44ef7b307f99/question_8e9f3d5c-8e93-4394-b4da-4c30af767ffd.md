Target: `StacksMessage::verify_secp256k1` and `Preamble::verify` (chat.rs `is_preamble_valid` / connection layer). Attacker action: send a `StacksMessage` whose `preamble.signature` is a valid ECDSA-recoverable signature over an EMPTY or mismatched `message_bits` (relayers+payload serialized differently from what was actually transmitted). Preconditions: attacker owns the raw TCP connection, no public key negotiated yet. Call sequence: `verify_secp256k1` re-serializes `self.relayers` and `self.payload` into `message_bits`, then calls `preamble.clone().verify(message_bits, pubkey)`. Equality: the bytes verified by `Preamble::verify` must be byte-identical to the exact wire bytes originally received for `relayers`+`payload`; if the node re-serializes rather than verifying the original wire bytes, a signature over a different canonical encoding could pass while the stored/relayed payload differs (transaction malleability at the message level). Impact: Critical, message content forgery. Proof idea: `stackslib::net::codec` test crafting a `StacksMessageType` variant with two distinct wire encodings (if any exist), verifying `verify_secp256k1` only accepts the exact serialization it re-derives, and that mismatched raw bytes vs `message_bits` cannot both validate.
