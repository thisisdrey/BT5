Target: WalletImpl::resolve_auth (NEP-641 AuthResolver::w_resolve_auth) WalletAuthorization::Signature branch. Attacker submits an authorization JSON blob to a view-caller/off-chain resolver claiming msg.signer_id = victim_wallet_account_id but the OffchainMessage.msg itself was actually signed with an ATTACKER key, relying on the resolver to skip the S::verify_offchain_msg step or on a schema mismatch (e.g. calling resolve_auth on a wallet deployed with WalletEd25519 while proof was produced under WalletP256) where verify_offchain_msg silently returns true due to type confusion in public_key deserialization. Precondition: attacker knows victim's AccountId and can call the view method w_resolve_auth(path, authorization) directly (it's a view method, callable by anyone). Call sequence: resolve_auth checks chain_id, signer_id==env::current_account_id() (always true since it's a view call on victim contract itself), path, timestamp, then S::verify_offchain_msg(public_key, msg, proof) — if this returns true for an attacker-forged proof, AuthorizationResolution::new(msg.payload) is returned as authorized. Binding: the (signer_id, public_key) pair that authorized the payload == the actual keypair that produced proof over msg.hash(); AuthorizationResolution.payload must only be returned when this equality holds. Impact: Critical - a downstream resolver (e.g. RpcResolver in crates/signatures/nep641/src/resolver/mod.rs) or any protocol trusting w_resolve_auth would accept an attacker-controlled payload as if the wallet owner authorized it, potentially settling a payload that moves Verifier funds. Proof: cargo test calling w_resolve_auth with a proof signed by a non-owner key against the wallet's stored public_key and asserting Error::InvalidSignature is returned, never AuthorizationResolution.
