In contracts/defuse/core/src/intents/token_diff.rs, TokenDiff carries token_id: TokenId internally but MtTransferEvent/TokenDiff events emit token_id.to_string() for off-chain observers while on-chain execution keys strictly on the TokenId struct via TokenDeltas::with_apply_delta(token_id, ...). Can an attacker submit two TokenDiff intents in the SAME signed MultiPayload batch whose token_id fields are structurally different TokenId values (e.g. TokenId::Nep245(Nep245TokenId::new(c,'a:b')) vs TokenId::Nep245(Nep245TokenId::new(c,'a') then separately ':b' folded differently)) that nonetheless both emit the identical token_id.to_string() in their TokenDiff/MtTransferEvent logs, so that an off-chain relayer or simulate_intents consumer reconciling by string believes only one delta occurred while the Verifier's TokenDeltas internally applied two distinct, unmerged entries? Binding: the set of distinct TokenId values applied to TokenDeltas in one execute_intents call has cardinality equal to the set of distinct token_id.to_string() values emitted in that call's events. Scoped impact: High, simulate_intents/event-log-based settlement diverges from the TokenDeltas actually applied by execute_intents. Proof idea: near-workspaces test submitting a MultiPayload with two TokenDiff intents on colliding-by-string-but-distinct TokenId values and diffing simulate_intents' reported deltas against the post-execute_intents on-chain token_balances.
