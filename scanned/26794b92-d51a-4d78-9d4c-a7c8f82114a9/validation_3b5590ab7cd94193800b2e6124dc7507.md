### Title
Unprotected AMM swap in Snowbridge `system-frontend` lets an attacker sandwich `register_token`/`add_tip` and steal the swapped tip/fee value - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

### Summary
`pallet_snowbridge_system_frontend`'s public extrinsics `register_token` and `add_tip` swap a user-supplied fee/tip asset into Ether via `T::Swap::swap_exact_tokens_for_tokens` before burning the Ether for teleport to Ethereum, exactly mirroring the reported Omnipool pattern of an AMM swap with no slippage protection sitting behind a reward/fee-claim entry point.

### Finding Description
`Pallet::swap_and_burn` calls the generic `Swap` trait (backed in production by `pallet_asset_conversion`, an on-chain constant-product AMM) with `amount_out_min` hard-coded to `None`: [1](#0-0) 

This is invoked from two unprivileged, signed/XCM-origin extrinsics:
- `register_token`, via `swap_fee_asset_and_burn`, when the caller is not the root/`Here` origin. [2](#0-1) 
- `add_tip`, callable by any signed account, which swaps the tip asset for Ether before forwarding the resulting `ether_gained` amount to BridgeHub to be credited as a relayer reward tip. [3](#0-2) 

`pallet_asset_conversion::do_swap_exact_tokens_for_tokens` only enforces the `amount_out_min` check when `Some` is supplied — when `None`, it accepts any resulting output amount, however small: [4](#0-3) 

Because Substrate transactions are fully visible in the mempool before inclusion, and swaps against the on-chain AMM move the pool's reserves according to public, deterministic bonding-curve math, an attacker can front-run a `register_token`/`add_tip` call with a large trade that skews the pool price, let the victim's zero-slippage swap execute at a degraded rate, then back-run it to restore the price and capture the difference — the same sandwich primitive described in the external report.

### Impact Explanation
The victim's tip/fee asset is converted into far less Ether than the fair-market amount. Consequences:
- For `add_tip`, the relayer reward amount forwarded to the bridge (`ether_gained`) can be driven to near zero, so the intended "additional tip" theft equals nearly 100% of the amount the user paid — directly matching the reported "theft of rewards" impact.
- For `register_token`, the burned Ether amount funds the fee that finances the Ethereum-side execution of registering the token; if it is skimmed to near zero, the on-chain accounting still records the debited fee asset as spent, but almost all of its economic value is captured by the sandwich attacker instead of the protocol/relayer, degrading the reliability of bridge processing for that message.
In both cases this is unbacked value transfer out of the user, extracted by an ordinary (non-privileged, non-validator) actor purely by ordering transactions around a public call — falling within the "theft or unbacked mint or unlock" / "duplicate settlement or payout" class of the program scope.

### Likelihood Explanation
Likelihood is high: `add_tip` and the fee-payment path of `register_token` are unprivileged, permissionless, publicly documented entry points. No governance, validator, relayer, or leaked-key assumption is required — only mempool visibility and the ability to submit two ordinary transactions (front-run and back-run), which is standard MEV/sandwich tooling on any chain with a public mempool and an on-chain AMM. The code path explicitly disables the one built-in defense (`amount_out_min`) with the comment "No minimum amount required," so there is no existing guard that would stop this.

### Recommendation
Do not hard-code `None` for `amount_out_min` in `swap_and_burn`. Instead:
1. Derive a minimum acceptable output using `QuotePrice::quote_price_exact_tokens_for_tokens` (already used elsewhere in the codebase, e.g. `pallet_asset_conversion_tx_payment`) immediately before the swap, and apply a bounded tolerance (e.g. a configurable `Perbill` slippage constant), passing `Some(min_out)` to `swap_exact_tokens_for_tokens`.
2. Alternatively, expose an explicit `min_ether_out`/`amount_out_min` parameter on `register_token`/`add_tip` so the caller (or their UI) can set their own tolerance, consistent with how `pallet_asset_conversion`'s own dispatchables require `amount_out_min`.
3. Ensure the swap failing due to slippage results in an atomic rollback of the whole extrinsic (already provided by `#[transactional]` on `Swap::swap_exact_tokens_for_tokens`), so no partial/incorrect burn-and-forward can occur.

### Proof of Concept
1. Attacker observes a pending `EthereumSystemFrontend::add_tip(message_id, asset)` (or `register_token` with a non-`Here` origin and non-Ether `fee_asset`) transaction in the mempool, where `asset` is a pool-tradable token X and the pool is X/Ether.
2. Attacker submits, with higher priority/tip, a large swap `X -> Ether` (or `Ether -> X`, depending on desired direction) via `pallet_asset_conversion::swap_exact_tokens_for_tokens`, moving the X/Ether pool reserves so that X is now valued far below fair price in Ether terms.
3. The victim's `add_tip`/`register_token` transaction executes next, calling `swap_and_burn` → `T::Swap::swap_exact_tokens_for_tokens(..., tip_amount, None, ...)` — with no floor, the trade executes at the manipulated (bad) rate, and `ether_gained` is far smaller than the fair-value amount for `tip_amount` of X.
4. Attacker submits a third transaction swapping back `Ether -> X` (or vice versa) to restore the pool to its prior state, realizing the difference between what the victim should have received and what the pool paid out as arbitrage profit.
5. Result: the victim's intended relayer tip / registration fee is reduced to near zero, while the attacker profits — value stolen with no privileged access, matching the "theft of rewards via sandwich attack" bug class from the external report.

*Note: the exact production runtime configuration wiring `type Swap = pallet_asset_conversion::Pallet<Runtime>` for `snowbridge-pallet-system-frontend` (e.g., on Asset Hub or BridgeHub) was not directly located in the indexed search results within the iteration budget — the trait bound (`Swap<AccountId, AssetKind = Location, Balance = u128>`) and the mock configuration (`type Swap = SwapExecutor` in `bridges/snowbridge/pallets/system-frontend/src/mock.rs`) confirm the pallet is designed to be backed by a real AMM swap implementation such as `pallet_asset_conversion`, but readers should verify the live runtime wiring directly if deeper confirmation is needed.*
