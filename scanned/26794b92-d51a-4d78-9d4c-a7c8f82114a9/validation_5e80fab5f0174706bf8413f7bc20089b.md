### Title
`process_delivery_receipt` ignores the on-chain `success` flag from Ethereum and always pays relayer reward - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
The Snowbridge V2 outbound queue pallet decodes a `DeliveryReceipt` from an Ethereum `InboundMessageDispatched` event log, which explicitly carries a `success: bool` field indicating whether the corresponding message actually executed successfully on the Gateway contract. `Pallet::process_delivery_receipt` never reads or checks this field — it pays the relayer's reward and clears the pending order unconditionally, as long as the receipt decodes and the nonce matches a `PendingOrders` entry.

### Finding Description
The `DeliveryReceipt` type is decoded from the Solidity event `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)`: [1](#0-0) 

This struct is produced via `TryFrom<&Log>`, faithfully carrying `success` into the Rust value: [2](#0-1) 

The extrinsic `submit_delivery_receipt` verifies the Merkle/event proof and decodes the receipt, then forwards it straight to `process_delivery_receipt`: [3](#0-2) 

`process_delivery_receipt` checks the gateway address and resolves the reward account and pending order by nonce, but at no point reads `receipt.success`. It pays the reward (`T::RewardPayment::register_reward`) whenever `order.fee > 0`, and always removes the order and emits `MessageDelivered`: [4](#0-3) 

A grep across the whole pallet module confirms `success` is never referenced anywhere in `bridges/snowbridge/pallets/outbound-queue-v2/src/*.rs` — the field is decoded and then completely dropped. This mirrors the reported bug class exactly: an operation returns/carries an explicit success/failure indicator, and the caller advances state and disburses funds without checking it.

### Impact Explanation
Any relayer can submit a valid, correctly-signed/proved Ethereum event log for a message whose execution on the Gateway contract actually failed (`success = false`) — the proof itself only attests that the *event was emitted*, not that the underlying command succeeded. Because `success` is ignored:
- The relayer still collects the full `order.fee` reward for a message that did not actually get delivered/executed correctly.
- The `PendingOrders` entry is removed regardless, permanently closing out state for a failed delivery, which forecloses any downstream retry/accounting logic that depends on `PendingOrders` reflecting outstanding, unresolved deliveries.

This breaks the "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" invariant, and results in reward payout independent of actual message outcome — an unbacked/duplicate-style payout condition reachable by any unprivileged relayer, without needing a malicious validator, admin, or governance actor.

### Likelihood Explanation
High. The path is a public, unprivileged extrinsic (`submit_delivery_receipt`) reachable by any signed account holding a legitimate Ethereum receipt proof for a message nonce still in `PendingOrders`. No special conditions (front-running, colluding validators, leaked keys) are required — the only requirement is that the Ethereum-side event with `success = false` exists and is provable, which is a normal execution outcome (e.g., a command that reverts on Ethereum due to insufficient gas, bad target call, etc.), not an attacker-crafted anomaly.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only invoke `T::RewardPayment::register_reward` when `success == true`; when `success == false`, still clear/settle the `PendingOrders` entry (or route to a distinct failure-handling path such as re-queueing or slashing) but must not pay reward. Emit distinguishable events (`MessageDelivered { success: true }` vs. a failure variant) so downstream consumers (e.g., the parachain sender pallet) can react correctly.

### Proof of Concept
1. A message is enqueued and processed by `do_process_message`, creating `PendingOrders[nonce]` with `fee > 0`. [5](#0-4) 
2. On Ethereum, the Gateway contract dispatches the message but the inner command execution fails; the contract still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)` (this is the documented purpose of the `success` flag).
3. A relayer builds an `EventProof` for this log and calls `submit_delivery_receipt`.
4. `T::Verifier::verify` succeeds (the log genuinely exists), `DeliveryReceipt::try_from` decodes `success = false` correctly.
5. `process_delivery_receipt` is called; since it never inspects `receipt.success`, it pays `order.fee` to `reward_account` via `T::RewardPayment::register_reward` and removes `PendingOrders[nonce]`, emitting `MessageDelivered { nonce }` exactly as if delivery had succeeded. [6](#0-5)

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
