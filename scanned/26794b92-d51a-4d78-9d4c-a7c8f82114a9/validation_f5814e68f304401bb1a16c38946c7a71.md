## Title
Proxy call authorization is checked against the *current* `ProxyType`/permission state at execution time instead of the state that existed when the delayed call was announced, letting the delegate/real pair's permission be silently widened or narrowed between `announce` and `proxy_announced` - ([File: substrate/frame/proxy/src/lib.rs])

### Summary
The `pallet-proxy` time-delayed proxy flow mirrors the LlamaCore bug: an "action" (the announced call) is committed to (hashed) by `announce`, but the actual authorization parameter that governs how it will be executed — the `ProxyType`/permission filter — is **not bound at announcement time**. It is only resolved later, in `proxy_announced`, by looking up whatever `ProxyDefinition` currently exists in the `Proxies` storage for `(real, delegate)`. Because `add_proxy`/`remove_proxy` are independent, immediately-effective extrinsics that any account controlling `real` can call at any time, the permission level backing an already-announced call can be changed after the announcement and before execution, exactly as the Llama report describes for the `call`/`delegate_call` opcode.

### Finding Description
`announce` (substrate/frame/proxy/src/lib.rs, `pub fn announce`) only records `{real, call_hash, height}` in `Announcements`: [1](#0-0) 

Nothing about the currently held `ProxyType` (permission/filter) or `delay` is captured or pinned at this point — only the hash of the call and the `real`/`delegate` accounts.

Execution happens later via `proxy_announced`, which re-resolves the applicable `ProxyDefinition` from the *live* `Proxies` storage at dispatch time via `find_proxy`: [2](#0-1) [3](#0-2) 

`find_proxy` simply scans the current `Proxies::<T>::get(real)` list for a definition matching `delegate` (and optionally the caller-forced `proxy_type`); it has no knowledge of what permission existed when `announce` was called. The resolved `def.proxy_type` is then used directly to construct the filtered origin in `do_proxy`: [4](#0-3) 

`add_proxy`/`remove_proxy` are ordinary signed extrinsics that take effect immediately and independently of any pending announcement: [5](#0-4) 

This is the same broken invariant as the Llama report: an approval/commitment step (`announce`, analogous to policyholder approval of an action) leaves a critical execution parameter (proxy permission level, analogous to `call` vs `delegate_call`) unbound, deferring its resolution to whatever unrelated state (`Proxies` storage) happens to hold at execution time — state that can be changed by a completely different, unrelated transaction (`add_proxy`/`remove_proxy`) issued by a different actor (the `real` account) with no relationship to the original announcement's intent.

### Impact Explanation
If `real` (the account being proxied) widens the delegate's `ProxyType` (e.g., from a restrictive type to `ProxyType::Any`) after a delay-restricted delegate has already announced a call, that previously-announced, hash-committed call will be executed under the new, more permissive filter once the delay elapses — even though the delegate had no permission to make that filter-widened call when they announced it. Conversely, `real` could narrow or remove a delegate's rights after announcement, causing an execution-time failure (`NotProxy`) for a call that the delegate legitimately committed to earlier, or `real` could re-add the same delegate under a different `proxy_type`/`delay` combination to manipulate which filter is checked at settlement time. Because proxy delegation gates unauthorized execution of arbitrary `RuntimeCall`s (including balance transfers via `ProxyType::Any`), a mismatch between the permission at announcement-time and permission at execution-time is a genuine "unauthorized execution / permission escalation" class issue matching the report's `call`→`delegate_call` opcode-drift pattern.

### Likelihood Explanation
The trigger requires only ordinary signed extrinsics available to the `real` account (`add_proxy`, `remove_proxy`) plus the delegate's own `announce`/`proxy_announced` calls — no validator, relayer, governance, or admin privilege is needed. The delay window that exists specifically to let `real` react to an announced call is itself the window in which `real` can also change the proxy type instead of only cancelling/rejecting the announcement, so the race condition is a natural, always-available side effect of the existing delayed-proxy design rather than an exotic edge case.

### Recommendation
Bind the authorized `ProxyType` (and/or a snapshot of the relevant `ProxyDefinition`) into the `Announcement` record at `announce` time (or require `proxy_announced` to re-validate that the `ProxyType` used matches one that was valid continuously since the announcement's `height`), so that a permission change made via `add_proxy`/`remove_proxy` cannot retroactively alter how an already-announced, hash-committed call is authorized and filtered at execution.

### Proof of Concept
1. `real` (account `1`) calls `add_proxy(delegate=2, proxy_type=JustTransfer, delay=D)`.
2. `delegate` (account `2`) calls `announce(real=1, call_hash=H)` where `H` is the hash of a call that `JustTransfer` would filter out (e.g. `Utility::batch` containing `add_proxy`), intending only to use it later if permissions change — or, more directly: `2` announces a call `C` that is disallowed under `JustTransfer`.
3. Before the delay elapses, `real` calls `remove_proxy(delegate=2, proxy_type=JustTransfer, ...)` followed by `add_proxy(delegate=2, proxy_type=Any, delay=D')` (e.g. rotating trust levels for legitimate reasons, or an attacker with transient access to `real`'s account doing this deliberately).
4. Once the original delay has elapsed (measured from the original `announce` height, unaffected by the type change), account `0` (or anyone) calls `proxy_announced(delegate=2, real=1, force_proxy_type=None, call=C)`.
5. `find_proxy` now resolves `def.proxy_type = Any` (the current storage value), and `C` — originally filtered/disallowed under `JustTransfer` at announcement time — is dispatched successfully under `Any`, even though no relationship between `real` and `delegate` ever combined "announce under JustTransfer" with "execute under Any" as an atomic, approved decision. 		pub fn announce(
			origin: OriginFor<T>,
			real: AccountIdLookupOf<T>,
			call_hash: CallHashOf<T>,
		) -> DispatchResult {
			let who = ensure_signed(origin)?;
			let real = T::Lookup::lookup(real)?;
			Proxies::<T>::get(&real)
				.0
				.into_iter()
				.find(|x| x.delegate == who)
				.ok_or(Error::<T>::NotProxy)?;

			let announcement = Announcement {
				real: real.clone(),
				call_hash,
				height: T::BlockNumberProvider::current_block_number(),
			};

			Announcements::<T>::try_mutate(&who, |(ref mut pending, ref mut deposit)| {
				pending.try_push(announcement).map_err(|_| Error::<T>::TooMany)?;
				Self::rejig_deposit(
					&who,
					*deposit,
					T::AnnouncementDepositBase::get(),
					T::AnnouncementDepositFactor::get(),
					pending.len(),
				)
				.map(|d| {
					d.expect("Just pushed; pending.len() > 0; rejig_deposit returns Some; qed")
				})
				.map(|d| *deposit = d)
			})?;
			Self::deposit_event(Event::Announced { real, proxy: who, call_hash });

			Ok(())
		}

		pub fn proxy_announced(
			origin: OriginFor<T>,
			delegate: AccountIdLookupOf<T>,
			real: AccountIdLookupOf<T>,
			force_proxy_type: Option<T::ProxyType>,
			call: Box<<T as Config>::RuntimeCall>,
		) -> DispatchResult {
			ensure_signed(origin)?;
			let delegate = T::Lookup::lookup(delegate)?;
			let real = T::Lookup::lookup(real)?;
			let def = Self::find_proxy(&real, &delegate, force_proxy_type)?;

			let call_hash = T::CallHasher::hash_of(&call);
			let now = T::BlockNumberProvider::current_block_number();
			Self::edit_announcements(&delegate, |ann| {
				ann.real != real ||
					ann.call_hash != call_hash ||
					now.saturating_sub(ann.height) < def.delay
			})
			.map_err(|_| Error::<T>::Unannounced)?;

			Self::do_proxy(def, real, *call);

			Ok(())
		}

	pub fn find_proxy(
		real: &T::AccountId,
		delegate: &T::AccountId,
		force_proxy_type: Option<T::ProxyType>,
	) -> Result<ProxyDefinition<T::AccountId, T::ProxyType, BlockNumberFor<T>>, DispatchError> {
		let f = |x: &ProxyDefinition<T::AccountId, T::ProxyType, BlockNumberFor<T>>| -> bool {
			&x.delegate == delegate &&
				force_proxy_type.as_ref().map_or(true, |y| &x.proxy_type == y)
		};
		Ok(Proxies::<T>::get(real).0.into_iter().find(f).ok_or(Error::<T>::NotProxy)?)
	}

	fn do_proxy(
		def: ProxyDefinition<T::AccountId, T::ProxyType, BlockNumberFor<T>>,
		real: T::AccountId,
		call: <T as Config>::RuntimeCall,
	) {
		use frame::traits::{InstanceFilter as _, OriginTrait as _};
		// This is a freshly authenticated new account, the origin restrictions doesn't apply.
		let mut origin: T::RuntimeOrigin = frame_system::RawOrigin::Signed(real).into();
		origin.add_filter(move |c: &<T as frame_system::Config>::RuntimeCall| {
			let c = <T as Config>::RuntimeCall::from_ref(c);
			// We make sure the proxy call does access this pallet to change modify proxies.
			match c.is_sub_type() {
				// Proxy call cannot add or remove a proxy with more permissions than it already
				// has.
				Some(Call::add_proxy { ref proxy_type, .. }) |
				Some(Call::remove_proxy { ref proxy_type, .. })
					if !def.proxy_type.is_superset(proxy_type) =>
				{
					false
				},
				// Proxy call cannot remove all proxies or kill pure proxies unless it has full
				// permissions.
				Some(Call::remove_proxies { .. }) | Some(Call::kill_pure { .. })
					if def.proxy_type != T::ProxyType::default() =>
				{
					false
				},
				_ => def.proxy_type.filter(c),
			}
		});
		let e = call.dispatch(origin);
