Target: `ft_resolve_withdraw` NEP-141 vulnerability comment: 'do not refund on failed `ft_transfer_call` ... insufficient gas'. Attacker action: as `receiver_id` in `FtWithdraw{..., msg: Some(msg), min_gas: Some(<very small gas>)}`, attacker deploys a contract whose `ft_on_transfer` deliberately consumes gas such that the resolve callback's `promise_result_checked_json::<U128>(0)` returns `Err(_)` (insufficient gas to read result) even though the tokens were fully accepted on the receiver side. Preconditions: signer has token_balance == amount; attacker sets `min_gas` intentionally low via the `FtWithdraw.min_gas` field they can influence when constructing the withdraw intent for their own account. Call sequence: `do_ft_withdraw` forwards `min_gas` -> `ft_transfer_call` -> gas-starved callback -> `ft_resolve_withdraw` treats `Err(_) => amount.0` (used = full amount, no refund). Binding: `used == actual tokens accepted by attacker's ft_on_transfer`, which the `Err(_) => amount.0` branch does NOT re-derive independently — it just assumes full success. Scoped impact: Critical only if attacker can make the *opposite* condition true (fail to consume, but get refunded) — verify whether an attacker can invert this to get BOTH a refund AND the FT tokens by having the receiver accept then intentionally causing resolve to read `Err` on a different oracle path. Proof idea: cargo test sandbox with a receiver contract that returns `U128(0)` (rejects) but still keeps tokens transferred out-of-band via a secondary internal transfer inside `ft_on_transfer`, asserting `refund credited by ft_resolve_withdraw == token contract's actual outbound FT balance change`.
