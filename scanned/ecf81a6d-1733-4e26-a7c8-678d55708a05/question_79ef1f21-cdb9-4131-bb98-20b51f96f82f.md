Target: `MultiTokenWithdrawResolver::mt_resolve_withdraw` (contracts/defuse/src/contract/tokens/nep245/withdraw.rs). Attacker action: deploys a malicious MT-receiver contract as `receiver_id`, and in an `MtWithdraw{ token, receiver_id, token_ids: [a,b], amounts: [X,Y] }` intent, has `mt_on_transfer` return a `Vec<U128>` of mismatched length or reordered values. Preconditions: `promise_result_checked_json_with_len::<Vec<U128>>(0, amounts.len())` requires exact length match else falls back to `vec![U128(0); amounts.len()]`. Call sequence: `internal_mt_withdraw` -> `do_mt_withdraw` (`mt_batch_transfer_call`) -> `mt_resolve_withdraw` zips `token_ids`,`amounts`,`used` and re-credits refund via `self.deposit`. Binding: for every `token_id`, `used[i] == amount actually accepted by receiver for that specific token_id`, not just clamped per-index against `amounts[i]` — index/order must match the real per-token acceptance. Scoped impact: Critical, a `TokenId` (`(contract, token_ids[i])`) could be refunded against the wrong `amounts[i]` slot if attacker's contract returns a permuted-but-same-length vector, letting attacker claim a bigger refund on a valuable token while a worthless token absorbs the shortfall. Proof idea: cargo test with a stub `mt_on_transfer` returning `[U128(Y), U128(X)]` (swapped) for a two-token withdraw with X != Y and asserting `deposit` re-credits token_ids[0] and token_ids[1] using their OWN accepted amounts, not swapped ones.
