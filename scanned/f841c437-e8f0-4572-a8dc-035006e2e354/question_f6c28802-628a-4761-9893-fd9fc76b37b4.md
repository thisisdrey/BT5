Target: `execute_signed_intents` batch semantics — does committing nonce for payload i in a batch make its effect visible to payload i+1's OWN nonce/salt checks within the same batch (via `Deltas`/`CachedState` read-your-own-writes), such that an attacker could use payload i to invalidate salt S (only if such an intent exists) and payload i+1 (signed by a THIRD PARTY under salt S, replayed by attacker as the caller since signature is the only authority) is then rejected as `InvalidSalt` for a reason the third-party signer never intended, purely because the attacker chose batch ordering. Preconditions: attacker holds two independently-signed payloads (own + a third party's, since intents.near allows anyone to submit anyone else's validly-signed payload) and controls their ORDER in one `execute_intents` call. Call sequence: `execute_signed_intents` iterates `signed` in caller-supplied order, so `Deltas`' cumulative in-memory salt/account state from payload i IS visible to payload i+1's `verify_intent_nonce`. Binding: the outcome (accept/reject) of a third party's independently-signed payload == the outcome intended by that signer's own deadline/salt choice, NOT a function of unrelated attacker-chosen batch ordering. Scoped impact: High, an attacker could grief a legitimate signed payload into `InvalidSalt`/`DeadlineExpired` rejection by ordering; Critical only if ordering can instead cause an UNAUTHORISED SETTLEMENT (not just rejection) of a third party's funds. Proof idea: `cargo test` building a batch with a third-party payload placed after an attacker-crafted payload designed to alter shared salt/deadline state, asserting settlement outcomes match single-payload execution outcomes.
