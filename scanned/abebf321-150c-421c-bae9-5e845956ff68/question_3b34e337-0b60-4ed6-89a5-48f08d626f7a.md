Target: contract.rs execute_request ops-before-promises ordering. Attacker action: attacker, as a previously-enabled extension, crafts a Request whose `internal` contains WalletOp::AddExtension{account_id: attacker_second_account} and whose `external` contains a promise executed in the SAME call, attempting to have the second account's added-extension status take effect and be usable by a nested cross-contract call within the same execution before the top-level call fully commits (near reentrancy via async promises). Preconditions: attacker controls two accounts, one already an enabled extension. Call sequence: execute_request loops `for op in request.internal { execute_op(...) }` synchronously (state mutation immediate) then `for promise in request.external { build_promise(promise)?.detach() }` (async, scheduled after current receipt). Binding: any promise scheduled in the same call sees State.extensions as of AFTER all internal ops in that same Request are applied (deterministic ordering), and no promise can be scheduled with a stale/pre-op extension list this call relied on. Impact: High — used to validate no reentrancy window lets an attacker's not-yet-committed AddExtension be exploited by a callback racing the outer call. Proof idea: sandbox test where the external promise callback (a mock contract) calls back into w_execute_extension using the newly added account within the same block and asserting behavior matches synchronous NEAR execution order (extension usable only in the NEXT receipt, not concurrently).
