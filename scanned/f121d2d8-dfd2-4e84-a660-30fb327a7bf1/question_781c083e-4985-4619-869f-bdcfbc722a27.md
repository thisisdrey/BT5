Target: WalletImpl::execute_signed signer_id check (`msg.signer_id != env::current_account_id()`). Attacker action: attacker (owner of wallet-B) obtains a RequestMessage originally signed for wallet-A (msg.signer_id = wallet-A) whose proof was produced by wallet-A's key, and, if wallet-B shares the same public_key (subwallet derivation reuse), submits it to wallet-B via w_execute_signed. Preconditions: two wallet contracts derived from the same public key with different subwallet_id but Wallet's SignatureSchema::verify_request_msg does not bind subwallet_id into the signed bytes beyond signer_id. Call sequence: w_execute_signed -> execute_signed -> signer_id check should reject since msg.signer_id(wallet-A) != env::current_account_id()(wallet-B). Binding: msg.signer_id == env::current_account_id() for the executing contract, exactly the account that owns the funds. Impact: Critical - if this check is bypassed or msg re-encoded with wallet-B's id but proof still verifies (schema not binding signer_id into signature), Verifier balances of wallet-B move without wallet-B owner's authorization. Proof idea: cargo test with two WalletImpl<S> instances sharing a public key, cross-submit a msg signed with signer_id=wallet-A to wallet-B, assert Error::InvalidSignerId(msg.signer_id) is returned and no request.internal ops or request.external promises execute.
