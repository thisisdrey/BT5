Target: Nonces::commit ordering (`commit` is called BEFORE `S::verify_request_msg` in execute_signed). Attacker action: attacker (unprivileged, no valid key) submits a RequestMessage with a completely bogus `proof` string but a nonce N and created_at within the valid window, chosen to match a nonce the real owner intends to use for a future legitimate signed request. Preconditions: attacker can predict or race the nonce the owner's relayer will use next (e.g., sequential nonce scheme recommended in docs). Call sequence: w_execute_signed -> execute_signed -> `self.0.nonces.commit(msg.nonce, msg.created_at, msg.timeout)?` succeeds and marks nonce N used via `current.set_bit(nonce)` -> `S::verify_request_msg` then fails and the call errors out, but the nonce bit is already permanently set (no rollback since commit mutates self.0 directly, not via a transaction that reverts on later Err). Binding: a nonce N consumed by an invalid/unauthorized submission == nonce N that the real owner can no longer use, which breaks the intended 'REPLAY' binding's guarantee that only successfully-authorized requests consume the nonce space. Impact: Critical - an unprivileged attacker permanently denies the wallet owner the ability to execute a specific relayer-chosen nonce, and if nonces are sequential this can be leveraged to block the wallet from executing further signed intents that move/settle Verifier balances (funds effectively frozen for that action).
