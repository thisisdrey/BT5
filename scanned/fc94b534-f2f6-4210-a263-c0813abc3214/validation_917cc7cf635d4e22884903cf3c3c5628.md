## Finding: Snowbridge outbound-queue fee calculation can truncate a valid, non-zero remote fee to zero, letting messages be relayed to Ethereum for free

This is a direct local analog of the GLP `usdToGlp` bug: a value is divided at a stage of the pipeline where the scale of the numerator is still too small relative to the divisor, so a mathematically non-zero result collapses to `0` even though every individual pricing parameter is valid and non-zero.

### Title
Outbound-queue `calculate_fee` can truncate the Ethereum relayer reward (`remote` fee) to zero for legitimately-priced messages, allowing free bridge message delivery - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
`Pallet::calculate_fee` computes the fee charged to a user for delivering a message to Ethereum. The "remote" portion of the fee (used to reward relayers for the Ethereum-side gas they pay) is computed as a `FixedU128` with 18-decimal precision, then converted to local-chain decimals by an integer division: `value.checked_div(10^(ETHER_DECIMALS - T::Decimals))`. When the computed 18-decimals-scaled fee is smaller than that divisor, the result truncates to `0`, exactly like the reported `usdToGlp` bug where `/ 1e24` was applied after the numerator had already lost scale. [1](#0-0) 

### Finding Description
`calculate_remote_fee` computes `fee_per_gas * gas_used_at_most + reward` in wei (`U256`), then this is:
1. Downcast to `u128` and wrapped as `FixedU128::from_inner(fee)` — this treats the raw wei integer as an already-18-decimal fixed-point number, i.e. it silently divides the "real" value by `1e18`.
2. Multiplied by `multiplier` and divided by `exchange_rate` (both `FixedU128`, so scale is preserved here).
3. The `.into_inner()` raw integer is passed to `convert_from_ether_decimals`, which does one more integer division by `10^(ETHER_DECIMALS - T::Decimals)` (e.g. `10^8` for a 10-decimal DOT-like balance) to rescale from Ether's 18 decimals to the local chain's decimals. [2](#0-1) 

Because step 1 already shrinks the raw wei amount by treating it as an 18-decimal fixed-point value, and step 3 divides again by up to `1e8`+, a perfectly legitimate, non-zero wei fee (e.g. `fee_per_gas=1, reward=1, gas=250000` ⇒ raw remote fee `250001` wei) ends up computing to local-balance `0`. This is confirmed by an existing test in the repo that documents the exact defect without asserting it's fixed: [3](#0-2) 

The only guard against bad pricing parameters is `PricingParameters::validate`, which only rejects parameters that are *exactly* zero (`exchange_rate == 0`, `fee_per_gas == 0`, `rewards.local == 0`, `rewards.remote == 0`, `multiplier == 0`). It performs no check on the resulting *computed* fee after all the scaling divisions, so it does not catch the truncation-to-zero case: [4](#0-3) 

`calculate_fee` is invoked directly from the public message-send entrypoint `SendMessage::validate`, which every outbound XCM-to-Ethereum message and every `snowbridge-pallet-system` command goes through — this is unprivileged, user-triggerable code: [5](#0-4) 

### Impact Explanation
The `remote` component of the fee exists specifically to reimburse relayers for the gas they spend executing the message on Ethereum, and to add an extra reward incentive (see module doc comment: "The gas refund paid out to relayers... An additional reward paid out to relayers..."). If this component truncates to `0`, messages are queued and dispatched to Ethereum without collecting any compensation for the relayer's real gas cost. This is a public, underpriced-work condition: an attacker (or just ordinary usage under a governance-set parameter combination with small `fee_per_gas`/`reward` values, or for low `gas_used_at_most` commands) can cause the outbound queue to keep committing messages that no rational relayer will deliver (since they aren't compensated), stalling the bridge's message-delivery flow — directly matching the "public underpriced work that... stalls bridge processing" pivot. [6](#0-5) 

### Likelihood Explanation
This does not require a malicious relayer, validator, or governance abuse — it is a pure arithmetic property of `calculate_fee` reachable through the normal public `validate`/`deliver` flow used for every outbound Snowbridge message, with only ordinary (non-adversarial) `PricingParameters` values that pass `validate()`. The repository's own test suite already demonstrates the exact zero-fee outcome with realistic parameter magnitudes, showing this isn't a contrived edge case. [3](#0-2) 

### Recommendation
Perform the Ether-decimals-to-local-decimals conversion in a single combined operation using higher precision (e.g., multiply first by the local scale then divide once by `1e18`, or use `U256`/`u256`-based `mul_div` with rounding) instead of two sequential lossy divisions (`FixedU128::from_inner` treating wei as already-scaled, then `checked_div` by `10^(ETHER_DECIMALS - Decimals)`). Additionally, add a runtime check (or extend `PricingParameters::validate`) that rejects/queries pricing parameter updates whose computed minimal remote fee (for the smallest expected `gas_used_at_most`) would round down to zero, mirroring the fix pattern for `usdToGlp`/`glpToUsd`: keep the multiplication before the division so precision isn't lost before scaling down.

### Proof of Concept
Using the pallet's own test harness (`bridges/snowbridge/pallets/outbound-queue/src/test.rs`):
```rust
let gas_used: u64 = 250000;
let price_params = PricingParameters {
    exchange_rate: FixedU128::from_rational(1, 1),
    fee_per_gas: 1_u32.into(),
    rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
    multiplier: FixedU128::from_rational(1, 1),
};
let fee = OutboundQueue::calculate_fee(gas_used, price_params);
assert_eq!(fee.remote, 0); // non-zero inputs -> zero remote fee charged to sender
```
This is exactly `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero`, already present and passing in the repository, confirming the truncation is reproducible with `PricingParameters` that pass `validate()`. [3](#0-2)

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}
