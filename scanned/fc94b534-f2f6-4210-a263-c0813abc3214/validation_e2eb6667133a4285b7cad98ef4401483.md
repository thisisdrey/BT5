## Analysis

The Boba report's core broken invariant: a **manually-refreshed, governance-controlled price ratio** is used to price a swap against a **fixed-denomination payout on the other side**, and because the ratio update cadence lags real market movement, an unprivileged caller can exploit the gap between the stale ratio and the real price to drain value from the contract's reserve.

The closest structural analog in this repository is Snowbridge's outbound message fee model. `PricingParameters.exchange_rate` (the "ETH/DOT exchange rate") is exactly this kind of manually-maintained ratio: the module docs state governance "should manually update these parameters every few weeks using the `set_pricing_parameters` extrinsic" [1](#0-0) , and it is only ever changed via `EthereumSystem::set_pricing_parameters` [2](#0-1) .

Any unprivileged caller who sends a message to Ethereum (via `SendMessage::validate`) has their DOT-denominated fee computed by converting a **fixed** remote-side cost (`fee_per_gas * gas_used + reward.remote`, both quoted in wei) into DOT using this cached `exchange_rate`: [3](#0-2) 

That fixed ETH reward (`params.rewards.remote`) is then embedded verbatim into the `CommittedMessage` sent to the Gateway contract and paid out to relayers from the Gateway's held ETH, independent of whatever DOT was actually collected from the sender: [4](#0-3) . The fee itself is computed and charged at `validate()`/`send()` time, using whatever `exchange_rate` happens to be stored at that moment: [5](#0-4) .

This reproduces the Boba pattern precisely: `exchange_rate` is the analog of `marketPriceRatio` (root-updated, infrequently, with a documented multi-week cadence), and `rewards.remote` is the analog of the fixed BOBA/ETH payout leg. If ETH appreciates materially against DOT between governance updates (exactly the "high volatility" scenario the Boba report describes), any ordinary user submitting bridge messages pays DOT fees priced off the stale ratio while the Gateway contract unconditionally disburses the full fixed ETH reward to relayers per message — allowing unbounded, cheap message spam that drains the Gateway's ETH reserve disproportionately to what was collected on the Substrate side. The `multiplier` safety factor [6](#0-5)  only guards against fluctuation *within* the update interval, not against multi-week staleness, exactly like Boba's fixed `_metaTransactionFee` failing to guard against >8% rate moves.

### Title
Stale governance-set `exchange_rate` lets unprivileged senders underpay for a fixed ETH relayer reward, draining Snowbridge Gateway reserves - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
Snowbridge's outbound message fee is derived by converting a fixed ETH-denominated relayer reward into DOT using `PricingParameters::exchange_rate`, a value that governance updates manually "every few weeks." Any unprivileged account can call the public send/`validate` path at any time; if the real ETH/DOT market rate has moved materially since the last governance update, the DOT fee charged is calculated against the stale rate while the fixed ETH reward paid out on Ethereum is unaffected, letting an attacker submit disproportionately cheap messages to drain the Gateway contract's ETH-held relayer-reward reserve.

### Finding Description
`calculate_fee` converts the remote (ETH-denominated) component of the message cost into the local currency by dividing by `params.exchange_rate` [3](#0-2) . `exchange_rate`, together with `multiplier` and `fee_per_gas`, is stored in `PricingParameters` and is only mutated by the root-only `set_pricing_parameters` extrinsic [7](#0-6) , which per the module docs is expected to run on a multi-week cadence [1](#0-0) .

Every call to `SendMessage::validate` (reachable by any account routing an XCM to Ethereum through the bridge exporter) recomputes the fee against whatever `exchange_rate` is currently stored [5](#0-4) . The remote reward amount committed into the message (`params.rewards.remote`, a fixed wei amount) is independent of the same `exchange_rate` and is paid to relayers from the Gateway contract's held ETH on the Ethereum side [4](#0-3) .

This is structurally identical to Boba's flaw: a manually refreshed ratio prices a swap/settlement leg denominated in one asset (DOT here, ETH in Boba), while the other leg is paid out at a fixed rate in the other asset (fixed ETH reward here, fixed BOBA fee/ETH payout in Boba). Nothing forces `exchange_rate` to be pulled fresh at the point of fee computation from a live source; it is a cached governance value that can lag the real market for weeks, precisely the "high volatility / stale ratio" condition the Boba report flags.

### Impact Explanation
If DOT depreciates (or ETH appreciates) versus the cached `exchange_rate` between governance updates, the DOT fee charged per message becomes underpriced relative to the real-world ETH value of the fixed reward paid to relayers. An attacker can spam outbound messages paying the artificially cheap DOT fee while each message still guarantees the full fixed ETH reward be disbursed from the Gateway's reserve, draining bridge-held ETH value disproportionately and consuming reward funds meant to sustainably compensate relayers — falling under "public underpriced work that degrades block production or stalls bridge processing" and risking depletion of bridge-side value backing.

### Likelihood Explanation
The `exchange_rate`/`multiplier` update is explicitly documented as an infrequent (multi-week), manual, off-chain governance action rather than a live oracle pull, so staleness during volatile market conditions is an expected operating mode rather than an edge case. Any account able to route a message through the bridge (no elevated privilege required) can exploit the pricing gap the moment it opens, requiring no validator, relayer, or admin collusion.

### Recommendation
Recompute or bound the effective exchange rate closer to real-time (e.g., via a decentralized on-chain price source once ETH/DOT liquidity pools are available, as the module doc already anticipates), or make the `multiplier` safety factor adapt dynamically to elapsed time since the last `set_pricing_parameters` update so that the guard band scales with staleness risk, and consider capping message throughput or reward payout per unit time to limit exposure during a mispriced window.

### Proof of Concept
1. Governance calls `set_pricing_parameters` setting `exchange_rate` reflecting current ETH/DOT market price, e.g. `FixedU128::from_rational(1, 400)` [8](#0-7) .
2. Over the following weeks the real ETH/DOT market rate moves such that ETH is now worth substantially more DOT than `1/400`, but governance has not yet refreshed the parameter (matches the documented multi-week update cadence).
3. An attacker submits an XCM that routes through `SnowbridgeExporter`, invoking `Pallet::validate` → `calculate_fee`, paying DOT fee computed with the stale (too-favorable) `exchange_rate` [3](#0-2) .
4. The committed message still carries the full fixed `reward.remote` in wei [4](#0-3) , which the Gateway contract pays out in real (now more valuable) ETH terms once delivered.
5. Attacker repeats step 3 at scale, paying cheap, stale-rate DOT fees while draining ETH value from the Gateway's reward reserve disproportionately to the DOT actually collected.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		pub fn set_pricing_parameters(
			origin: OriginFor<T>,
			params: PricingParametersOf<T>,
		) -> DispatchResult {
			ensure_root(origin)?;
			params.validate().map_err(|_| Error::<T>::InvalidPricingParameters)?;
			PricingParameters::<T>::put(params.clone());

			let command = Command::SetPricingParameters {
				exchange_rate: params.exchange_rate.into(),
				delivery_cost: T::InboundDeliveryCost::get().saturated_into::<u128>(),
				multiplier: params.multiplier.into(),
			};
			Self::send(PRIMARY_GOVERNANCE_CHANNEL, command, PaysFee::<T>::No)?;

			Self::deposit_event(Event::PricingParametersChanged { params });
			Ok(())
		}
