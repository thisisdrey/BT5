## Analog Found: Pallet-NFTs Atomic Swap – Offered Item State Is Not Locked Between `create_swap` and `claim_swap`

### Title
Atomic swap offer allows metadata/attribute manipulation of the offered NFT between `create_swap` and `claim_swap`, defeating the counterparty's value assessment - (File: `substrate/frame/nfts/src/features/atomic_swap.rs`)

### Summary
The Teller bug's root cause is that collateral is checked (ownership verified) at bid-submission time but not locked, so its value can be silently degraded before the counterparty's transaction actually executes. The same "verify-now, act-later" gap exists in `pallet-nfts`'s atomic swap feature: `do_create_swap` only checks that the caller currently owns the offered item and records a `PendingSwapOf` entry, but it never freezes the item's metadata/attributes. The offer's counterparty inspects the item at offer time, but the actual settlement happens later in `do_claim_swap`, by which time the offeror can have altered the item's attributes/metadata to reduce its perceived value, without triggering any invalidation of the pending swap.

### Finding Description
`do_create_swap` (`substrate/frame/nfts/src/features/atomic_swap.rs:49-103`) checks `item.owner == caller` and stores a `PendingSwapOf` entry keyed by `(offered_collection_id, offered_item_id)`, but performs no lock on the item's config, metadata, or attributes:
<cite repo="Lauraivanka/polkadot-sdk--002" path="substrate/frame/nfts/src/features/atomic_swap.rs" start="64="76" end="91" /> [1](#0-0) 

The only invalidation mechanism for a pending swap is `PendingSwapOf::<T, I>::remove(&collection, &item)`, which is called exclusively inside `do_transfer` when ownership of the item changes: [2](#0-1) 

This means the swap is only invalidated if the offered item is *transferred away*. It is **not** invalidated if the same owner instead calls `set_metadata`, `set_attribute`, or `clear_attribute` on the offered item to change what makes the item valuable (rarity data, associated content hash, trait attributes, etc.) while retaining ownership.

When the counterparty later calls `claim_swap` → `do_claim_swap` (`substrate/frame/nfts/src/features/atomic_swap.rs:160-233`), the pallet re-fetches the item and re-verifies ownership and swap parameters, but it never re-verifies metadata/attributes against what was inspected off-chain by the counterparty when they decided to accept the offer: [3](#0-2) 

This precisely mirrors the Teller `submitBid`/`lenderAcceptBid` pattern: the counterparty's decision to accept ("lenderAcceptBid" ≈ `claim_swap`) is based on state observed at offer time ("submitBid" ≈ `create_swap`), but the underlying asset's value-defining state can be freely mutated by the offeror in between, because only *ownership transfer* — not *content/attribute mutation* — invalidates the pending commitment.

### Impact Explanation
A malicious offeror can advertise a high-value NFT (with rich attributes/metadata such as rarity traits, a linked media hash, or a "verified" attribute) in `create_swap`, wait for a counterparty to evaluate it and submit `claim_swap` for a valuable item or `PriceDirection::Send`/`Receive` currency, then front-run/precede the claim with `set_attribute`/`clear_attribute`/`set_metadata` calls that strip the item of the traits that made it valuable — all while keeping ownership unchanged so the `PendingSwapOf` entry (and thus the swap) remains valid. The claimer's `claim_swap` still succeeds, and they receive a now-worthless NFT while paying the agreed price or handing over their own item/currency. This is a direct fund-loss / mis-valued settlement analogous to the Teller honeypot, executed entirely by an unprivileged, ordinary NFT owner with no need for a malicious validator, relayer, or governance actor.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment where `pallet-nfts`' `Swaps` feature is enabled and item attributes/metadata are mutable by the item owner after minting (the default configuration allows owner-controlled attribute/metadata updates unless explicitly locked via `lock_item_properties`/`lock_metadata`). No special privileges, timing races with block producers, or off-chain infrastructure are required — the attacker only needs to submit an ordinary attribute-mutation extrinsic before the counterparty's `claim_swap` is included, which is trivially achievable given the swap has an open `duration`/`deadline` window during which the offeror retains full owner rights over the item.

### Recommendation
When a swap is created for an item, either:
1. Lock the item's mutable state (attributes, metadata) for the duration of the pending swap (analogous to `T::Locker::is_locked` checks in `do_transfer`), rejecting `set_attribute`/`set_metadata`/`clear_attribute` calls while a `PendingSwapOf` entry references that item; or
2. Require callers of `set_attribute`/`set_metadata`/`clear_attribute` (and similar owner-mutation calls) to check and invalidate any `PendingSwapOf` entry for the affected item, mirroring the invalidation already done in `do_transfer`; or
3. Snapshot a content/attribute hash at `create_swap` time and require `claim_swap` to pass a witness that is checked against the current item state, failing the claim if the item was mutated since the offer.

### Proof of Concept
1. Account `A` mints NFT `(collection=0, item=1)` and sets attractive attributes (e.g., `rarity="legendary"`) via `set_attribute`.
2. `A` calls `create_swap(offered_collection=0, offered_item=1, desired_collection=2, desired_item=None, price=None, duration=100)`, creating a `PendingSwapOf` entry — no lock is placed on item `1`'s attributes.
3. Account `B`, observing the "legendary" attribute, prepares to claim by sending an item from collection `2` in return.
4. Before `B`'s `claim_swap` extrinsic is included, `A` calls `clear_attribute(0, 1, "rarity")` (or `set_attribute` to overwrite it with garbage) — this succeeds because `do_transfer`'s `PendingSwapOf::remove` invalidation path is never invoked (ownership didn't change), and `set_attribute`/`clear_attribute` perform no `PendingSwapOf` check.
5. `B`'s `claim_swap` still succeeds because `do_claim_swap` only re-checks `send_item.owner == caller`, `swap.desired_collection`, `witness_price`, and the deadline — not attribute/metadata state — so `B` receives the now-devalued item `1` while irrevocably transferring their own item/collection-2 item to `A`.
