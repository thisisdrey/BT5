### Title
Delivery receipt `success` flag is never checked before paying relayer rewards - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
`Pallet::<T>::process_delivery_receipt` in the Snowbridge Outbound Queue V2 pallet verifies the Ethereum event proof and the gateway address, then unconditionally registers the relayer reward and removes the pending order — without ever inspecting the `success` field of the `DeliveryReceipt` it just decoded. This mirrors the external report's core defect class: an operation-outcome flag is decoded/available but a specific failure branch is not handled, so the code proceeds as if the operation always succeeded.

### Finding Description
`process_delivery_receipt` performs the following checks only:
- `T::Verifier::verify(...)` — proves the log came from the gateway contract on Ethereum.
- `ensure!(T::GatewayAddress::get() == receipt.gateway, ...)`.
- `<PendingOrders<T>>::get(nonce).ok_or(...)`.

It then does: [1](#0-0) 

```
pub fn process_delivery_receipt(...) -> DispatchResult {
    ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);
    let reward_account = ...;
    let nonce = receipt.nonce;
    let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;
    if order.fee > 0 {
        T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee);
    }
    <PendingOrders<T>>::remove(nonce);
    Self::deposit_event(Event::MessageDelivered { nonce });
    Ok(())
}
```

Nowhere is `receipt.success` read. The `DeliveryReceipt` struct explicitly carries a `success: bool` field (confirmed by its use in integration tests, e.g. `success: true` in delivery-receipt construction), which strongly implies the protocol intends for a failed on-chain delivery on Ethereum to be distinguishable from a successful one: [2](#0-1) 

Because the flag is ignored, any relayer can submit a delivery receipt proof for a message whose execution on the Ethereum side actually **reverted/failed**, and the pallet will:
1. Pay the relayer the full fee via `T::RewardPayment::register_reward` (an unbacked/incorrect reward payout — the relayer did not deliver working execution).
2. Permanently remove the `PendingOrder` for that nonce (`<PendingOrders<T>>::remove(nonce)`), which is the accounting record that lets the fee/nonce be resolved. Once removed, there is no other path to re-attempt or correctly resolve that nonce — this is a "duplicate settlement/duplicate no-recourse" advance of state without an outcome check, which is exactly the class of bug the finding is scoped to catch ("payout state must only advance after decode, dispatch, execution, and settlement succeed").

This is reachable by any signed account calling the public extrinsic `submit_delivery_receipt`, requiring no admin/governance/relayer-privilege abuse — merely a legitimate but failed-execution event log from the real gateway contract (which is a normal, non-malicious occurrence, e.g., out-of-gas or reverted command on the Ethereum side), satisfies `T::Verifier::verify` and the gateway-address check.

### Impact Explanation
This breaks the "duplicate settlement or payout" and "message queues/bridge markers/receipts and payout state must only advance after ... settlement succeed" invariants. Relayer fees (`order.fee`) come from real user-paid amounts held by the outbound queue's fee logic; paying them out for message deliveries that failed on Ethereum constitutes theft-of-fee / unbacked reward payout at the expense of the protocol/users, and removes the record needed for correct accounting or retry, permanently losing the ability to reconcile that nonce.

### Likelihood Explanation
High likelihood: this requires only a real Ethereum event log proof from the configured gateway (which anyone monitoring the bridge can obtain when any relayer's delivery genuinely fails, e.g. due to insufficient gas at execution time on Ethereum, or a legitimately-reverting command), and a normal signed extrinsic call. No malicious peer, validator, governance, or leaked-key assumption is needed — a routine failed cross-chain execution combined with normal relayer/observer behavior triggers the incorrect payout path every time.

### Recommendation
Check `receipt.success` in `process_delivery_receipt` before calling `T::RewardPayment::register_reward`. On `success == false`, the pallet should not reward the relayer (or should reward only a reduced/verification-only amount per spec), and should emit a distinct failure event (e.g. `MessageDeliveryFailed`) while still resolving/removing the `PendingOrder` in a way consistent with the intended protocol (or keep it for retry logic if applicable), rather than always emitting `Event::MessageDelivered` and paying full fee unconditionally.

### Proof of Concept
1. A message is enqueued and gets a `PendingOrder` with nonce `N` and fee `F > 0` via `do_process_message`.
2. On Ethereum, the relayer's execution of that message reverts/fails; the gateway contract still emits a `DeliveryReceipt`-shaped event log with `success = false` (this is normal/expected chain behavior on execution failure, not an attacker action).
3. Any account observes this real event, obtains its proof, and calls `submit_delivery_receipt(event)` → decodes into `DeliveryReceipt { nonce: N, success: false, gateway: <valid>, ... }`.
4. `process_delivery_receipt` passes `T::Verifier::verify` (real proof) and the gateway check, finds the `PendingOrder`, and — because `success` is never inspected — calls `T::RewardPayment::register_reward(&reward_account, ..., F)`, then removes the `PendingOrder` and emits `Event::MessageDelivered { nonce: N }`, exactly as if the message had been delivered successfully.
5. Result: full fee paid out for a failed delivery, and the nonce's accounting record is destroyed with no differentiation from a successful delivery.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,

			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

		}
