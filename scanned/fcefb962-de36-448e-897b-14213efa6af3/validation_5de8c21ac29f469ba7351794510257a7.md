### Title
Live pool balances (not cached reserves) drive fee-quote pricing, letting anyone donate tokens to skew tx-fee-in-asset conversion - (`File: substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`pallet-asset-conversion`'s `get_reserves` computes "reserves" by reading the pool account's **live token balances** (`Self::get_balance(&pool_account, asset)`), exactly the pattern the external report flags as dangerous for `ConnextPriceOracle.getPriceFromDex`. These live balances feed `quote_price_exact_tokens_for_tokens` / `quote_price_tokens_for_exact_tokens`, which are in turn used by `pallet-asset-conversion-tx-payment`'s `ChargeAssetTxPayment` to convert transaction fees denominated in native currency into a fee amount payable in an arbitrary asset. [1](#0-0) [2](#0-1) 

### Finding Description
`get_reserves` derives the AMM's price basis directly from `T::Assets`/`T::Currency` balances of the pool account rather than from an internally tracked, swap-invariant-checked reserve value:
```rust
pub fn get_reserves(...) -> Result<(T::Balance, T::Balance), Error<T>> {
    let pool_account = T::PoolLocator::pool_address(&asset1, &asset2)...;
    let balance1 = Self::get_balance(&pool_account, asset1);
    let balance2 = Self::get_balance(&pool_account, asset2);
    ...
}
``` [1](#0-0) 

Any account can transfer tokens directly to the deterministic `pool_account` address (derivable via `T::PoolLocator::pool_address`) without going through `add_liquidity`, instantly inflating one side of the "reserve" used for pricing. `quote_price_exact_tokens_for_tokens`/`quote_price_tokens_for_exact_tokens` use these balances verbatim in `get_amount_out`/`get_amount_in`/`quote` to compute a fee-in-asset quote: [3](#0-2) 

This price is consumed by `ChargeAssetTxPayment` to determine how much of a chosen asset a signed extrinsic's sender is debited (and refunded) for transaction fees: [4](#0-3) 

The pallet's own doc comment concedes the price is only reliable "if no other swaps are made after the price is quoted and before the target swap," acknowledging the balance-based quote is spot-manipulable within the same block/transaction window, i.e., the exact "balanceOf can be gamed" primitive from the external report. [5](#0-4) 

Unlike Uniswap V2's `getReserves()` (which the report recommends as the safe alternative because it returns internally-tracked, swap-boundary-updated reserves rather than raw `balanceOf`), this pallet has no separate cached-reserve concept at all — `get_reserves` *is* the raw balance read, so there is no safer alternative call to switch to within this codebase; the design itself conflates "reserve" with "current balance."

### Impact Explanation
Because `ChargeAssetTxPayment` re-quotes price at `validate_and_prepare` and again at `post_dispatch_details` using this same balance-derived function, an attacker who can transiently inflate/deflate the pool account's balance for either asset around their own transaction's fee-charging points can cause the fee-payment pallet to under- or over-charge the fee-asset amount relative to the true swap-executable price, or produce a refund quote inconsistent with the actual debit. Since `ChargeAssetTxPayment` doesn't execute an atomic swap against the pool but instead independently derives a quote and then withdraws/deposits the asset amount, a balance-based quote divergent from true liquidity depth is used to directly move value (fee amount / refund amount) without the swap's own AMM-invariant guard rails validating it against pool solvency at settlement time.

### Likelihood Explanation
The pool account address is public and derivable, and sending tokens to it is an ordinary, unprivileged transfer — no malicious node, validator, relayer, or governance actor is required. However, exploiting this for tx-fee mispricing specifically requires the attacker's donation and their own extrinsic (which triggers `validate_and_prepare`) to land in a window where the manipulated balance is observed before it's reverted/absorbed, and profitability depends on the relative size of the donation vs. pool depth and the fee magnitude — a real but narrow, execution-order-dependent condition, not a guaranteed high-value exploit path. This keeps likelihood moderate rather than high.

### Recommendation
Do not derive fee-payment quotes (or any pricing consumed by settlement logic outside of an atomic swap) directly from live pool-account balances. Either (a) introduce pallet-tracked reserve values updated only within `add_liquidity`/`remove_liquidity`/`swap_*` extrinsics (mirroring Uniswap V2's `_update()`-gated `reserve0`/`reserve1`) and have `get_reserves`/`quote_price_*` read from that tracked state instead of raw balances, or (b) require `ChargeAssetTxPayment` to execute its fee conversion as an actual atomic swap against the pool (subject to the same slippage/solvency checks as `swap_tokens_for_exact_tokens`) rather than an independent balance-based quote followed by a separate withdraw/deposit.

### Proof of Concept
Conceptual sequence (not independently executed against a live node in this session, given tool limitations):
1. Attacker computes `pool_account = PoolLocator::pool_address(native, asset_X)`.
2. Attacker transfers a large amount of `asset_X` directly to `pool_account` (a plain balance transfer, no `add_liquidity` call, so no LP tokens are minted and no invariant check runs).
3. Attacker (or accomplice) submits a signed extrinsic paying fees in `asset_X`; `ChargeAssetTxPayment::validate_and_prepare` calls `quote_price_tokens_for_exact_tokens`, which calls `get_reserves`, reading the now-inflated `asset_X` balance, producing a skewed (cheaper) fee-in-asset quote than the pool's true tradeable depth would allow via `swap_tokens_for_exact_tokens`.
4. Attacker withdraws the donated `asset_X` back out of the pool account is not directly possible without `remove_liquidity`, but the transient balance skew during the single-block quote window is sufficient to distort the fee charged in that block, as documented by the pallet's own "no other swaps... within the same transaction" caveat. 		/// Gets a quote for swapping an exact amount of `asset1` for `asset2`.
		///
		/// If `include_fee` is true, the quote will include the liquidity provider fee.
		/// If the pool does not exist or has no liquidity, `None` is returned.
		/// Note that the price may have changed by the time the transaction is executed.
		/// (Use `amount_out_min` to control slippage.)
		/// Returns `Some(quoted_amount)` on success.
		pub fn quote_price_exact_tokens_for_tokens(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount: T::Balance,
			include_fee: bool,
		) -> Option<T::Balance> {
			// Swaps reject zero amounts, match that behavior.
			if amount.is_zero() {
				return None;
			}

			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2).ok()?;

			let (balance1, balance2) = Self::get_reserves(asset1.clone(), asset2.clone()).ok()?;

			if balance1.is_zero() {
				return None;
			}

			let amount_out = if include_fee {
				let fee = Self::pool_fee_for(&asset1, &asset2).ok()?;
				Self::get_amount_out(fee, &amount, &balance1, &balance2).ok()?
			} else {
				Self::quote(&amount, &balance1, &balance2).ok()?
			};

			// Small inputs can round output to zero due to integer division.
			if amount_out.is_zero() {
				return None;
			}

			// Swap withdrawals from pools use `keep_alive=true` (Preserve). Use the same
			// preservation level to determine the actual withdrawable amount.
			let max_output = T::Assets::reducible_balance(asset2, &pool_account, Preserve, Polite);
			if amount_out > max_output {
				return None;
			}

			Some(amount_out)
		}

		/// Gets a quote for swapping `amount` of `asset1` for an exact amount of `asset2`.
		///
		/// If `include_fee` is true, the quote will include the liquidity provider fee.
		/// If the pool does not exist or has no liquidity, `None` is returned.
		/// Note that the price may have changed by the time the transaction is executed.
		/// (Use `amount_in_max` to control slippage.)
		/// Returns `Some(quoted_amount)` on success.
		pub fn quote_price_tokens_for_exact_tokens(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount: T::Balance,
			include_fee: bool,
		) -> Option<T::Balance> {
			// Swaps reject zero amounts, match that behavior.
			if amount.is_zero() {
				return None;
			}
			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2).ok()?;

			let (balance1, balance2) = Self::get_reserves(asset1.clone(), asset2.clone()).ok()?;

			if balance1.is_zero() {
				return None;
			}

			// Swap withdrawals from pools use `keep_alive=true` (Preserve). Use the same
			// preservation level to determine the actual withdrawable amount.
			let max_output =
				T::Assets::reducible_balance(asset2.clone(), &pool_account, Preserve, Polite);
			if amount > max_output {
				return None;

				Self::get_amount_in(fee, &amount, &balance1, &balance2).ok()
			} else {
				Self::quote(&amount, &balance2, &balance1).ok()
			}
		}
