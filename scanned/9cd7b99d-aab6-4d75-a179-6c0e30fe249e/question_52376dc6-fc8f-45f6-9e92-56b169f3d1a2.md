Target: `HttpChunkedTransferReaderState` `chunk_size`/`last_chunk_size` fields parsed as hex in the chunk boundary, feeding `read_chunk_bytes(fd, &mut buf[decoded..])`. Attacker action: send a chunk-size hex value large enough that decoding it as `u64` succeeds but is inconsistent with `max_size` (constructed from `MAX_MESSAGE_LEN as u64` via `StacksHttpRecvStream::new`), e.g. `chunk_size = u64::MAX`. Preconditions: node acting as HTTP client via `allow_arbitrary_response` or a peer-initiated response flow. Call sequence: verify `do_read`/`read_chunk_bytes` enforces `total_size + chunk_size <= max_size` (or equivalent) before attempting to read that many bytes, rather than trusting the attacker's `chunk_size` and looping until the peer stops sending (a slow-loris style single-message resource hold). Equality: declared `chunk_size` accumulated into `total_size` must never exceed `self.max_size`; violation must abort the read, not permit unbounded buffering. Impact: Critical, unauthenticated memory exhaustion / DoS from a single crafted chunked response of nominal declared size but attacker-controlled real length. Proof idea: test `HttpChunkedTransferReaderState::do_read` with a chunk boundary declaring a chunk size exceeding `max_size` and assert it errors immediately rather than allocating/reading toward that size.
