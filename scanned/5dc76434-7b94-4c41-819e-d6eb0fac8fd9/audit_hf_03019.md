# [H] FR-1 | Cannot Withdraw Fees

## Summary
Severity: High
Contest weight: 0.0706
Dataset id: 16893
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability is a missing withdrawal mechanism in the FeeReceiver contract, which is designated to collect protocol fees in both ERC20 tokens and native ether. Because the contract does not provide any public or privileged functions to transfer out the accumulated assets, any fees sent to it become permanently locked in the contract's balance. The root cause is a design omission: the contract’s code includes only receipt logic and lacks any method—such as a withdraw or sweep function with appropriate access controls—to move the funds elsewhere. An attacker does not need to exploit a flaw; the issue is that the protocol itself cannot retrieve the funds, so any user or protocol component that sends fees to the contract experiences a loss of those assets. This can be exploited unintentionally by simply sending tokens or ether to the address; the assets will sit in the contract forever because there is no code path to release them. The impact is that protocol revenue, reimbursement pools, or any intended redistribution of fees cannot be realized, effectively causing a reduction in available capital and potentially breaking accounting assumptions that fees are available for future operations. The condition under which this occurs is any transaction that transfers ERC20 tokens or ether to the FeeReceiver contract address. All parties that rely on fee collection—protocol administrators, token holders, and end‑users expecting refunds or reward calculations—are affected because the expected balance cannot be withdrawn. The issue was discovered during a manual audit of the contract’s source code, where the auditor noted the absence of any external or internal function that calls token.transfer or address.send. It may be hard to notice because the contract compiles without errors and appears to accept funds correctly; the problem only manifests when a withdrawal is attempted, which simply fails silently or reverts due to missing code. To remediate, the contract should be extended with a withdraw function that allows an authorized role (e.g., owner or a designated fee manager) to transfer out ERC20 tokens and ether, and proper access controls should be enforced to prevent unauthorized draining. This class of bug is commonly referred to as a "locked funds" or "missing withdrawal" vulnerability, where the smart contract’s logic does not provide a way to retrieve assets that it can hold, violating the business logic that fees collected should be usable by the protocol. From the user’s perspective, the UI may show that fees have been deposited but no button or notification to claim them, leading to confusion such as "my balance stays at zero after paying fees" or "the protocol shows high fee revenue but I never see any payouts". Expectations that the protocol can later use those fees are unmet, resulting in funds that appear to disappear from the system.

## Recommendation
Add a withdraw function with proper access controls to withdraw and manage fees.
