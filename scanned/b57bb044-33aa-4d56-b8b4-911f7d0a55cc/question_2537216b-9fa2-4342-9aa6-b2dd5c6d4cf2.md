Target: `TokenId::from_str` / `Display` in `crates/primitives/token-id/src/lib.rs` and `Nep171TokenId::new` in `crates/primitives/token-id/src/nep171.rs`. Attacker deploys an NFT contract `evil.near` and, via `nft_on_transfer`, deposits a token whose `nft_token_id` field itself contains a colon, e.g. `token_id = "real.near:1"`, while `token` (the calling contract) is `evil.near`, so the resulting `Nep171TokenId{contract_id: "evil.near", nft_token_id: "real.near:1"}` displays as `nep171:evil.near:real.near:1`. Preconditions: attacker owns `evil.near` and has never deposited into `real.near:1`'s legitimate `TokenId`. Call sequence: `nft_on_transfer` -> `Nep171TokenId::new(token, token_id).into()` -> stored under `token_balances` keyed by the `Display` string. Binding broken if `TokenId::from_str(&t.to_string()) != t`, i.e. re-parsing `nep171:evil.near:real.near:1` yields `contract_id="evil.near"`, `nft_token_id="real.near:1"` (same, since split_once takes only first colon) - verify this holds and does NOT collide with a genuine `Nep171TokenId{contract_id:"real.near", nft_token_id:"1"}`'s `to_string()` = `nep171:real.near:1`. Scoped impact: Critical, IDENTITY binding (`(contract, token)` named by `TokenId` == asset actually moved) breaks if any two distinct constructible `Nep171TokenId` share a `Display` string, crediting the wrong owner's balance. Proof idea: `cargo test` unit test constructing both `TokenId`s, asserting `to_string()` values differ and each round-trips via `from_str`.
