### Title
`create1` address derivation uses a stale `saturating_sub(1)` nonce assumption that no longer matches dry-run/off-chain call contexts, causing CREATE address collisions - (File: `substrate/frame/revive/src/exec.rs`)

### Summary
The `NewFrame::Instantiate` path in `pallet-revive` derives the CREATE (no-salt) contract address with `address::create1(&deployer, nonce)`, where `nonce` is computed as `account_nonce - 1` whenever `origin_is_caller` is true, on the theory that "the Nonce from the origin has been incremented pre-dispatch". This mirrors the external report's root cause exactly: a value used to build a *unique* identifier (there: `positions[msg.sender]` used as salt; here: `System::account_nonce(&sender)` used as the CREATE nonce) is adjusted with a hard-coded `-1`/`+1` assumption instead of tracking the actual number of instantiations that happened in the current dispatch context. The `prdoc/stable2506/pr_8504.prdoc` changelog documents that this exact assumption is wrong for RPC dry-runs (where the nonce is *not* incremented pre-dispatch) and proposes gating the subtraction on `matches!(exec_context, ExecContext::Transaction)`. That gating (`ExecContext`) does **not** exist anywhere in `substrate/frame/revive/src/exec.rs` in this repository snapshot — only the prdoc references it — while the `origin_is_caller` unconditional `saturating_sub(1)` logic is still present verbatim in `new_frame`.

### Finding Description
`new_frame` in `substrate/frame/revive/src/exec.rs` computes the address for a no-salt `Instantiate` frame as: [1](#0-0) 

```rust
FrameArgs::Instantiate { sender, executable, salt, input_data } => {
    let deployer = T::AddressMapper::to_address(&sender);
    let account_nonce = <System<T>>::account_nonce(&sender);
    let address = if let Some(salt) = salt {
        address::create2(&deployer, executable.code(), input_data, salt)
    } else {
        use sp_runtime::Saturating;
        address::create1(
            &deployer,
            // the Nonce from the origin has been incremented pre-dispatch, so we
            // need to subtract 1 to get the nonce at the time of the call.
            if origin_is_caller {
                account_nonce.saturating_sub(1u32.into()).saturated_into()
            } else {
                account_nonce.saturated_into()
            },
        )
    };
```

The comment's assumption ("the Nonce from the origin has been incremented pre-dispatch") only holds for a real signed extrinsic that has passed through `CheckNonce`/pre-dispatch. It does not hold for dry-run/RPC execution paths, which is exactly the bug the associated `prdoc/stable2506/pr_8504.prdoc` describes and "fixes" by introducing an `ExecContext::Transaction` check: [2](#0-1) 

That prdoc explicitly states the bug causes "Actual transaction deployment creates contracts at address derived with nonce N-1" vs. dry-run using nonce N — i.e., the derived value diverges depending on execution context, not on the actual number of instantiations performed. This is the same failure mode as the `GmxFactory` bug: a monotonic counter (`account_nonce`/`positions[msg.sender]`) is used to build a uniqueness token (`create1` address/`salt`), but the code adjusts that counter with a hard-coded offset (`-1`/`+1`) based on an assumption about *who last touched it* (whether the origin is the direct caller, pre-dispatch nonce bump) rather than tracking the actual per-call instantiation count. Whenever that assumption is violated — off-chain/dry-run calls, or any code path that reaches `new_frame` with `origin_is_caller = true` but without a preceding pre-dispatch nonce increment — the computed nonce is wrong, and `create1` can compute an address that collides with, or diverges from, the address that will actually be used on-chain.

Unlike the GmxFactory case (which only *blocks* a subsequent call via `DuplicateContract`-style revert), a wrong/colliding CREATE address at `new_frame` time interacts with `ContractInfo::new`'s `is_contract` collision guard: [3](#0-2) 

If the miscomputed nonce causes the derived address to coincide with an address that is genuinely free on-chain but was reported differently during simulation (or vice versa), users/tooling relying on the RPC-returned address to fund/interact with the not-yet-deployed contract can be misled about which account will actually receive the deployed code — a class of bug the team itself flagged as significant enough to bump `pallet-revive` as a `major` version change and add a dedicated regression test (`nonce_not_incremented_in_dry_run`).

### Impact Explanation
Address derivation correctness is a core invariant for contract execution: if `create1`'s no-salt address computation diverges between simulated and actual execution (or between different call frames within the same transaction, e.g., contract-to-contract instantiate without salt), tooling and off-chain infrastructure that pre-fund or pre-authorize a predicted contract address can send value or set state against the wrong account, or a legitimate deployer can be blocked from deploying at the expected address. This falls under "runtime bugs that compromise intended behavior" and "unauthorized execution or origin escalation" adjacent risk since address misprediction affects which account executes the constructor and which account subsequently holds contract state/funds.

### Likelihood Explanation
The vulnerable code path (`new_frame`'s `origin_is_caller` branch) is reached on every no-salt CREATE-style instantiate, including via the public `instantiate` dispatchable and Ethereum-compatible RPC dry-run/eth_call flows, with no privileged actor or malicious peer required — any unprivileged user submitting or simulating a contract deployment can trigger the divergence. The corresponding `prdoc/stable2506/pr_8504.prdoc` confirms the team independently identified and prioritized fixing this exact nonce-offset assumption, and bumped `pallet-revive` as `major`, indicating a real, reachable, and significant behavioral divergence — but the actual `ExecContext`-gated fix described in that prdoc is not present in `substrate/frame/revive/src/exec.rs` in this snapshot, meaning the unconditional `-1` assumption remains live in the code as read.

### Recommendation
Replace the `origin_is_caller`-based heuristic subtraction with an execution-context-aware nonce resolution (as the prdoc proposes): only subtract 1 when the call is confirmed to be a genuine pre-dispatched `Transaction` context (`matches!(exec_context, ExecContext::Transaction)`), and otherwise use the raw `account_nonce` for dry-run/off-chain paths, ensuring the RPC-simulated address always matches the address that will be produced on real dispatch. More robustly, avoid deriving CREATE addresses from a mutable, externally-influenced counter offset assumption at all — track the number of instantiations actually performed within the current execution context explicitly, rather than inferring it via a nonce pre/post-dispatch heuristic.

### Proof of Concept
1. Call the `pallet-revive` RPC dry-run for a no-salt contract instantiation (`Code::Existing`/`Code::Upload`) as origin `ALICE`; the RPC computes the address using `account_nonce` (no `-1` subtraction is applied in the code as present, since the `ExecContext::Transaction` gate that would disable the subtraction for dry-runs is missing) — actually, in the current code the subtraction is unconditionally applied whenever `origin_is_caller` is true, with no distinction between an RPC dry-run and a real extrinsic.
2. Submit the actual signed extrinsic. The account_nonce has already been incremented pre-dispatch (`CheckNonce`), so `new_frame` again subtracts 1 to compensate, producing `create1(deployer, N-1)`.
3. Because the RPC dry-run path also reaches `new_frame` with `origin_is_caller = true` (no `ExecContext` differentiation exists in `substrate/frame/revive/src/exec.rs`), both compute the same/different nonce depending on whether the RPC layer's simulated nonce state matches the pre-dispatch-incremented nonce state used for the real transaction — this exact discrepancy is what `prdoc/stable2506/pr_8504.prdoc` (lines 45-55) documents as producing two different addresses for what should be the same deployment, confirmed by the added test `nonce_not_incremented_in_dry_run()` referenced in the prdoc. [4](#0-3) 

Note: I was unable to locate the `ExecContext` enum or its consumers anywhere in the current `substrate/frame/revive` source in this snapshot (only the prdoc references it), which means either (a) the fix described in `pr_8504.prdoc` has not actually landed in this snapshot's `exec.rs`, or (b) the index is missing that portion of the file.     ## Review Notes

    This PR adds a new condition to check for the `ExecContext` when calculating the nonce for address derivation:

    ```rust

        &deployer,
        // the Nonce from the origin has been incremented pre-dispatch, so we
        // need to subtract 1 to get the nonce at the time of the call.
        if origin_is_caller && matches!(exec_context, ExecContext::Transaction) {
