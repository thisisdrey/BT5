### Title
Non-read-only nested contract execution inside `fungibles::Inspect` queries lets a malicious ERC20 contract mutate state (and reenter) during what callers treat as a pure balance/total-supply read - (File: `substrate/frame/revive/src/impl_fungibles.rs`)

### Summary
`pallet-revive` exposes a `fungibles::Inspect`/`fungibles::Mutate` adapter (`Pallet<T>` in `substrate/frame/revive/src/impl_fungibles.rs`) that lets any generic fungible-asset consumer (e.g. `xcm_builder::FungiblesAdapter`, per the code's own doc comment) treat an arbitrary EVM/PVM contract as a fungible asset identified by its `H160` address. The "read" functions `total_issuance()` and `balance()` are implemented by issuing a full, **non-read-only** `Self::bare_call(...)` into the target contract's `totalSupply()`/`balanceOf()` selector. Unlike pallet-revive's own contract-to-contract calling convention, which has an explicit `READ_ONLY` `CallFlag` (`substrate/frame/revive/uapi/src/flags.rs:79`) enforced in `exec.rs`/`pvm.rs`, this externally-facing "query" path never sets `read_only`, so the callee contract executes with full state-mutation and reentrancy capability while the caller believes it is only reading a number.

### Finding Description
This is a direct structural analog of the Balancer read-only-reentrancy bug class: the report's core broken invariant is "code that treats a getter as a safe, atomic read is actually vulnerable to state mutation triggered from inside that getter, via attacker-controlled callee logic."

In `impl_fungibles.rs`:
- `total_issuance()` (`impl_fungibles.rs:66-87`) and `balance()` (`impl_fungibles.rs:100-123`) both call `Self::bare_call(...)` with `TransactionLimits::WeightAndDeposit` and no read-only restriction.
- `bare_call` runs the full contract dispatch stack (`Stack::run_call` → `push_frame`/`run`), which for an EVM-mode contract defaults `ReentrancyProtection` to `AllowReentry` for many call shapes (as documented in `prdoc/pr_12267.prdoc:45`, "In EVM mode, `CALL`/`STATICCALL` default to `ReentrancyProtection::AllowReentry`... PVM (Wasm) defaults to `Strict`").
- The contract author fully controls the code behind `totalSupply()`/`balanceOf()`. Nothing in `impl_fungibles.rs` sets `CallFlags::READ_ONLY`, so `is_read_only`/`StateChangeDenied` protections in `exec.rs` (`fn call`, `read_only || self.is_read_only()`) never trigger; the callee can write its own storage, transfer value, emit events, or call back into the runtime.
- Because `fungibles::Inspect`/`Mutate` are generic traits consumed by other subsystems that assume "querying a balance/total supply is side-effect free and atomic with respect to the surrounding operation" (exactly the assumption the Balancer bug violated for `Vault.getPoolTokens()`/`pool.totalSupply()`), any caller that reads `balance()`/`total_issuance()` and then acts on that number (e.g. computing a transferable amount, comparing before/after balances, or sequencing a burn/mint pair as in `burn_from`/`mint_into`, `impl_fungibles.rs:161-241`) can be fed a value that was mutated mid-call by the contract it just "read."

The `READ_ONLY` flag and `allows_reentry`/`ReentranceDenied` checks that protect pallet-revive's own contract-to-contract call surface (`exec.rs:1242-1244`, `1277-1298`) are the functional equivalent of Balancer's `ensureNotInVaultContext()`. They exist in the codebase, but are never invoked on this specific "asset query" path, exactly mirroring the report's finding that `VaultReentrancyLib` exists but is referenced without being called at the pricing functions.

### Impact Explanation
Any pallet or off-chain-facing logic that is generically written against `fungibles::Inspect`/`Mutate` and happens to be backed by pallet-revive's ERC20 adapter (deployer-controlled contract as an "asset") can be driven to operate on inconsistent balance/supply data: a malicious contract's `balanceOf`/`totalSupply` handler can transfer its own tokens away, self-destruct-equivalent, or trigger further transfers between the two halves of a burn/mint pair (`burn_from` computes balance via a nested call, then a second nested call fetches the "resulting" balance at `impl_fungibles.rs:194` and `232`), letting an attacker manipulate downstream accounting (mis-priced or mis-settled fungible transfers) — the same class of harm as the Balancer BPT price manipulation: incorrect settlement amounts derived from data that was mutated by the very code being queried.

### Likelihood Explanation
Reachability requires only deploying a normal, unprivileged ERC20-style contract on pallet-revive and having it be treated as a fungible asset through this adapter (a documented, intended use case — `xcm_builder::FungiblesAdapter`). No malicious peer, validator, relayer, or governance action is needed; the attacker is simply the deployer of the queried contract, matching the "unprivileged attacker" requirement.

### Recommendation
Set `CallFlags`/an equivalent `read_only = true` (or an explicit `ReentrancyProtection::Strict`, no-state-change execution mode) on the `bare_call` invocations used purely for `balance()`/`total_issuance()`/`reducible_balance()` in `impl_fungibles.rs`, so that these "read" queries cannot execute state-mutating or reentrant code, mirroring pallet-revive's own `READ_ONLY` `CallFlag` guarantee used for in-contract `STATICCALL` semantics.

### Proof of Concept
1. Deploy a pallet-revive contract whose `balanceOf(address)`/`totalSupply()` selector, instead of simply returning storage, performs a state-mutating action (e.g. transfers its own balance, or calls back into the runtime) before returning a value.
2. Register/treat this contract as a fungible asset through the `fungibles::Inspect`/`Mutate` adapter in `impl_fungibles.rs` (e.g. via `xcm_builder::FungiblesAdapter` or any generic consumer of the trait).
3. Trigger any flow that calls `Pallet::<T>::balance(asset_id, account)` or `total_issuance(asset_id)` followed by an action based on that value (e.g. `burn_from`/`mint_into`, which itself calls `balance()` again afterward at `impl_fungibles.rs:194`/`232`).
4. Observe that the contract's callback executed during the "read" can alter its own state (or trigger a further transfer) between the two nested `bare_call`s, so the final balance used by the caller does not reflect an atomic, unmutated snapshot — analogous to the Vault/pool desync in the Balancer report.
