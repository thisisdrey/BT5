### Title
Fungible `transfer` credits destination with the requested amount instead of the actual amount debited from source, breaking conservation when `decrease_balance` is `BestEffort` - ([File: substrate/frame/support/src/traits/tokens/fungible/regular.rs])

### Summary
The default `Mutate::transfer` implementation withdraws from `source` using `Precision::BestEffort` (which may silently transfer less than requested, e.g. when the account would be dusted below the existential deposit) but then deposits the full originally-requested `amount` into `dest`, and returns `Ok(amount)` unconditionally rather than the actually-decreased amount. This is the same class of bug the external report describes for inflationary/deflationary ERC20 tokens: bookkeeping trusts a nominal "amount" value instead of the value actually observed/moved, so the true supply of value at `source` and `dest` can diverge from the value the caller believes was transferred.

### Finding Description
`Unbalanced::decrease_balance` with `Precision::BestEffort` caps the amount actually removed at `reducible_balance(who, preservation, force)`: [1](#0-0) 

`Mutate::transfer` calls `decrease_balance` with `BestEffort` precision, discards its `Result<Balance, _>` return value (the *actual* amount withdrawn), and then calls `increase_balance(dest, amount, BestEffort)` using the *original requested* `amount`, not the actual amount removed from `source`: [2](#0-1) 

Because `decrease_balance`'s return value (`Self::decrease_balance(source, amount, BestEffort, preservation, Polite)?;`) is not bound to a variable, any shortfall caused by best-effort withdrawal is invisible to the caller. The function then unconditionally returns `Ok(amount)` — the value requested, not the value that moved. This is an identical failure mode to the report's core complaint: code assumes `amount_requested == amount_actually_moved` and performs bookkeeping (crediting the destination, returning a result to the caller) based on the nominal amount rather than the observed value.

The identical pattern exists in the multi-asset version, `fungibles::Mutate::transfer`: [3](#0-2) 

### Impact Explanation
If `decrease_balance` returns less than `amount` (a legitimate, documented `BestEffort` outcome — e.g. the withdrawal would leave `source` below the existential deposit and the remainder is swept as dust via `handle_dust`), then:
- `dest` is still credited with the full nominal `amount` via `increase_balance(dest, amount, BestEffort)`.
- The caller of `transfer` receives `Ok(amount)`, believing the full amount moved.
- Total issuance is not directly touched by `transfer` (unlike `mint_into`/`burn_from`), but the *pairwise* value conservation between `source` and `dest` is broken: value is created out of nothing, since `dest` gains more than `source` lost. Any pallet built on top of `fungible::Mutate::transfer`/`fungibles::Mutate::transfer` that assumes atomic, exact-value-preserving transfers (nomination pools bonding, treasury payouts, asset-conversion pool joins, bridge sovereign-account routing, etc.) can end up crediting more value to a beneficiary than was actually removed from the payer, which is precisely the false-bookkeeping/unbacked-credit primitive called out in the external report.

### Likelihood Explanation
This is a design characteristic of the shared, widely-used `fungible`/`fungibles` trait default implementation in FRAME support, reachable any time a pallet calls the trait's default `transfer()` with `Preservation::Expendable` on an account near the existential deposit, or any custom `Unbalanced` implementation with unusual `reducible_balance`/dust rules that make `decrease_balance` reduce less than requested. It requires no privileged actor — any unprivileged account performing ordinary transfers close to the ED can trigger the shortfall path.

### Recommendation
- Short term: In `fungible::Mutate::transfer` and `fungibles::Mutate::transfer`, capture the actual value returned by `decrease_balance` and use that (not the caller-supplied `amount`) as the amount passed to `increase_balance`, and return that actual value from `transfer` rather than the requested `amount`.
- Long term: Add proptest/QuickCheck-style invariant tests asserting `balance(dest)_after - balance(dest)_before == balance(source)_before - balance(source)_after` for all `Preservation`/`Precision` combinations across all `Unbalanced` implementations in the codebase (pallet-balances, pallet-assets, and any custom fungible implementations).

### Proof of Concept
1. Configure an implementer of `fungible::Unbalanced` where `reducible_balance(source, Expendable, Polite)` returns less than the requested `amount` (e.g., `source`'s balance is `ED + amount - 1`, so withdrawing `amount` under `Expendable` preservation would dust the account and `reducible_balance` caps at `ED + amount - 1 - ED = amount - 1`).
2. Call `<T as fungible::Mutate<AccountId>>::transfer(&source, &dest, amount, Preservation::Expendable)`.
3. Observe: `decrease_balance` removes only `amount - 1` from `source` (dust handling may destroy the remaining ED-worth via `handle_dust`), yet `increase_balance(dest, amount, BestEffort)` credits `dest` the full `amount`. `transfer` returns `Ok(amount)`.
4. Assert `balance(dest)_after - balance(dest)_before == amount` while `balance(source)_before - balance(source)_after < amount` (plus any dust destroyed) — confirming value was created rather than conserved, mirroring the external report's core invariant break (bookkeeping trusts nominal transfer amount instead of actual value moved).

	fn decrease_balance(
		who: &AccountId,
		mut amount: Self::Balance,
		precision: Precision,
		preservation: Preservation,
		force: Fortitude,
	) -> Result<Self::Balance, DispatchError> {
		let old_balance = Self::balance(who);
		let reducible = Self::reducible_balance(who, preservation, force);
		match precision {
			BestEffort => amount = amount.min(reducible),
			Exact => ensure!(reducible >= amount, TokenError::FundsUnavailable),
		}

		let new_balance = old_balance.checked_sub(&amount).ok_or(TokenError::FundsUnavailable)?;
		if let Some(dust) = Self::write_balance(who, new_balance)? {
			Self::handle_dust(Dust(dust));
		}
		Ok(old_balance.saturating_sub(new_balance))
	}

	fn transfer(
		source: &AccountId,
		dest: &AccountId,
		amount: Self::Balance,
		preservation: Preservation,
	) -> Result<Self::Balance, DispatchError> {
		let _extra = Self::can_withdraw(source, amount).into_result(preservation != Expendable)?;
		Self::can_deposit(dest, amount, Extant).into_result()?;
		if source == dest {
			return Ok(amount);
		}

		Self::decrease_balance(source, amount, BestEffort, preservation, Polite)?;
		// This should never fail as we checked `can_deposit` earlier. But we do a best-effort
		// anyway.
		let _ = Self::increase_balance(dest, amount, BestEffort);
		Self::done_transfer(source, dest, amount);
		Ok(amount)
	}
