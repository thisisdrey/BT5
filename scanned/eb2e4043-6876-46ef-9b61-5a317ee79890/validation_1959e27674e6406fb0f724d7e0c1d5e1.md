## Finding



### Title
Relayer reward is paid and delivery order settled even when the Ethereum `success` flag reports message dispatch failure - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`submit_delivery_receipt` verifies the authenticity of an Ethereum `InboundMessageDispatched` log (nonce, gateway, reward address, topic, **and** `success`) via the beacon-client `Verifier`, then decodes it into a `DeliveryReceipt`. `process_delivery_receipt` validates the `gateway` field and looks up the `PendingOrder` by `nonce`, but never checks `receipt.success`, so it pays the relayer's fee and removes the pending order unconditionally, regardless of whether the message actually dispatched successfully on Ethereum.

### Finding Description
`DeliveryReceipt` decodes the `success` field straight from the verified `InboundMessageDispatched` event log: [1](#0-0) 

`submit_delivery_receipt` verifies the proof and forwards the decoded receipt straight to `process_delivery_receipt`: [2](#0-1) 

`process_delivery_receipt` only checks `gateway` and looks up `PendingOrders` by `nonce`; `receipt.success` is read into a local (`receipt` destructure omits it implicitly, it's simply unused) and never gated on: [3](#0-2) 

The doc comment for the extrinsic even states the intended flow is "Fetch the pending order by nonce ... pay reward ... Remove the order," with no mention of gating on dispatch success: [4](#0-3) 

This is architecturally identical to the reported bug class: the pallet validates *some* fields of an externally supplied record (`gateway`, and implicitly `nonce` via the storage lookup) but not another field (`success`) that determines whether the settlement (reward payout + queue-state advance) should be recorded at all. As a result, an incorrect/failure signal in the authenticated data does not stop the on-chain state from advancing as if the delivery had succeeded — exactly the "mismatch between actual event outcome and on-chain tracking" pattern from the report.

### Impact Explanation
Every failed Ethereum-side dispatch (e.g., the Gateway contract's inner call reverts due to insufficient gas estimation by `GasMeter`, a malformed command, or any other execution-time failure that the Solidity Gateway still logs as `success: false`) still results in:
- The relayer being paid `order.fee` via `T::RewardPayment::register_reward`, even though the corresponding message never actually executed on Ethereum.
- `PendingOrders::remove(nonce)` — permanently discarding all delivery/settlement tracking for that message, even though it functionally failed.

This violates the required invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." It results in relayers being rewarded for non-delivery and a permanent loss of the on-chain record needed to reconcile or retry/re-verify the failed message, i.e., unbacked reward payout plus permanent loss of delivery-tracking state.

### Likelihood Explanation
No malicious actor is required: any legitimate relayer submitting a real, correctly-proven Ethereum event log with `success: false` (which can occur under normal operational conditions — gas underestimation, contract-level reverts, etc.) triggers this path. The proof-verification step (`T::Verifier::verify`) only authenticates that the log genuinely exists on Ethereum; it says nothing about whether the pallet should honor the record if the log reports failure. This makes the bug reachable by ordinary bridge operation, not just adversarial input.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`:
- If `true`: proceed with reward payment and order removal as today.
- If `false`: do not pay the reward (or pay only a reduced/no fee), and either remove the order while emitting a distinct `MessageDeliveryFailed`/`MessageDispatchFailed` event, or retain it for potential resubmission/retry logic, rather than silently treating it as a successful settlement.

### Proof of Concept
1. A message is queued via `process_message` with a nonzero `fee`, creating a `PendingOrder { nonce, fee, block_number }` (`PendingOrders::<T>::insert(nonce, order)`).
2. The message is delivered to the Ethereum Gateway contract, but the inner dispatch fails during execution (e.g., an XCM-command-triggering call reverts on the EVM side). The Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)` per the existing ABI (`InboundMessageDispatched` event definition in `delivery_receipt.rs`).
3. A relayer (no special privilege needed) collects the genuine receipt+beacon proof for this real log and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds because the log is real; `DeliveryReceipt::try_from` decodes `success: false`.
5. `process_delivery_receipt` checks only `gateway` and `PendingOrders::get(nonce)`, pays `order.fee` to the reward account, and calls `PendingOrders::remove(nonce)` — exactly as if the message had succeeded, confirmed by the existing test `submit_delivery_receipt_succeeds_after_unhalt` and integration tests that always set `success: true` and assert `RewardRegistered`/`MessageDelivered` (no test exercises `success: false` at all, which itself demonstrates the field is unchecked): [5](#0-4)

```rust
		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```

```rust
// After governance resumes the bridge, legitimate delivery receipts flow through again:
// the order is paid out and removed from storage.
#[test]
fn submit_delivery_receipt_succeeds_after_unhalt() {
	new_tester().execute_with(|| {
		let nonce = 0;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_valid_event_proof());

		// Bridge halted — receipt rejected, order untouched.
		set_verifier_halted(true);
		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);
		assert!(PendingOrders::<Test>::get(nonce).is_some());

		// Bridge resumed — same receipt succeeds and the order is settled.
		set_verifier_halted(false);
		assert_ok!(OutboundQueue::submit_delivery_receipt(origin, event));
		assert!(PendingOrders::<Test>::get(nonce).is_none());

		System::assert_has_event(mock::RuntimeEvent::OutboundQueue(Event::MessageDelivered {
			nonce,
		}));
	});
```
