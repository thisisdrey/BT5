Based on my investigation, the strongest local analog to the reported bug — a formerly-privileged transfer function that lost its "only an authorized entity admin" gate and became reachable by any signed caller — is `pallet_scarcity::force_transfer` in this repository.

### Title
Unrestricted `force_transfer` extrinsic allows any signed account to force-move an NFT instance without holder or admin privilege - (File: `substrate/frame/scarcity/src/lib.rs`)

### Summary
`pallet-scarcity`'s `force_transfer` dispatchable is documented as a privileged, collection-owner-level operation ("the collection owner has full control over its definitions, metadata, and live instances, including force-transfer and force-burn"), yet the extrinsic itself performs only `ensure_signed(origin)` before calling `Self::do_force_transfer(&owner, instance, to)` — there is no check that `owner` is the collection's admin/owner or otherwise privileged over `instance`.

### Finding Description
The pallet doc explicitly states: *"The collection layer intentionally applies no holder-level ACL. When a runtime exposes this call to its contract environment, a contract-owned collection can enforce its own consent and game rules before calling it."* [1](#0-0) 

The dispatchable itself is:
```rust
#[pallet::call_index(13)]
#[pallet::weight(T::WeightInfo::force_transfer())]
#[transactional]
pub fn force_transfer(
    origin: OriginFor<T>,
    instance: InstanceId,
    to: T::AccountId,
) -> DispatchResult {
    let owner = ensure_signed(origin)?;
    Self::do_force_transfer(&owner, instance, to)
}
``` [2](#0-1) 

The only origin gate applied is `ensure_signed`, which proves the caller controls *some* account, not that the account is the collection's admin/owner, or the current holder of `instance`. This is the same broken-invariant class as the external report: `internalTransferFromEntity()` lost the `onlyEntityAdmin` modifier and became reachable by any address that is merely a "child" of an object, letting it move tokens it does not administer. Here, `force_transfer` is meant to be gated behind a runtime/contract-level ACL layer (per the module doc, "A runtime must separately expose Scarcity calls to its chosen contract environment; this crate does not provide a contract adapter") but the pallet dispatchable is a normal `#[pallet::call]` entry point — reachable directly by any external signed extrinsic in any runtime that includes `pallet-scarcity` in its `Call` enum without adding its own call-filter restricting `force_transfer` to privileged callers.

The companion `transfer` extrinsic is properly purse-based and gated via the `AsScarcity` transaction extension, which only recognizes `Call::transfer` and `Call::burn` for origin substitution to `Origin::Nft` [3](#0-2) ; `force_transfer` is deliberately excluded from that authorization pipeline, relying entirely on an assumed-but-unenforced external ACL for its safety.

I was not able to retrieve the body of `do_force_transfer` itself in this session (index/tool limits), so I cannot confirm with 100% certainty whether an internal admin check exists inside that helper. However, the doc comment directly preceding the call ("intentionally applies no holder-level ACL... a contract-owned collection can enforce its own consent... before calling it") strongly implies that no such check exists at the pallet layer, and that safety is expected to be supplied by a wrapper that a bare runtime integration would omit.

### Impact Explanation
If a runtime includes `pallet-scarcity` and exposes `force_transfer` without adding an additional call-filter or origin-restriction wrapper, any signed account on the chain can force-transfer any other holder's NFT instance to an arbitrary destination — an unauthorized-execution / theft-of-asset primitive matching "theft or unbacked mint or unlock" and "unauthorized execution or origin escalation" in the impact gate. This directly parallels the reported Solidity bug where losing the `onlyEntityAdmin` modifier let unprivileged callers move internal token balances.

### Likelihood Explanation
Likelihood is high in any runtime that includes this pallet as-is and assumes the documented "administer at contract layer" contract, since the doc string is the only protection and nothing in the pallet enforces it. No malicious peer, validator, relayer, or leaked key is required — it needs only a signed transaction from an unprivileged account, satisfying the "unprivileged attacker" requirement of the task.

### Recommendation
Add an explicit privilege check inside `force_transfer` (or `do_force_transfer`) verifying that `owner` matches the collection's `admin`/`owner` field for the collection containing `instance`, mirroring the `collection_details.admin == signer` checks used in the sibling `uniques`/`nfts` pallets' transfer paths [4](#0-3) . If the pallet intends this to remain a bare low-level primitive for a contract adapter, gate the call behind `T::ForceOrigin`/`EnsureOrigin` rather than plain `ensure_signed`, so it cannot be dispatched directly by ordinary signed accounts.

### Proof of Concept
1. Deploy a runtime that includes `pallet-scarcity` in its `construct_runtime!` without a custom `BaseCallFilter` restricting `Scarcity::force_transfer`.
2. Account `Eve` (who owns no NFT and has no admin role in any Scarcity collection) submits a signed extrinsic `Scarcity::force_transfer(instance = <Alice's instance id>, to = Eve)`.
3. `ensure_signed(origin)` succeeds since `Eve` is a valid signed account; `do_force_transfer(&Eve, instance, Eve)` executes with no check that `Eve` is the collection admin or `instance`'s holder, transferring Alice's NFT to Eve.
