[Function: check_account_existence] Can an attacker submit a single-action transaction `Transfer` to a nonexistent NEAR-implicit account whose `account_id` collides (via `PublicKey::from_near_implicit_account`) with a public key the attacker does NOT control but can predict/grind (e.g., a vanity implicit account matching a victim's future key), such that `action_implicit_account_creation_transfer` grants `AccessKey::full_access()` to the implicit-derived public key before the true owner ever registers it — is this an inherent design (not exploitable) or does the derivation allow a second party to front-run account creation and later be locked out? Preconditions: attacker computes a 64-hex `account_id` for which they do not hold the private key. Sequence: attacker sends `Transfer` deposit to that hex account id first. Invariant: authorization exactness (only the key matching the implicit account id gets the full-access key — verify no alternate key is granted). Impact: none if the derivation is a pure function of account_id (expected); use this only to confirm no code path lets `deploy_contract`/`add_key` piggyback in the same tx (already gated by `OnlyImplicitAccountCreationAllowed`). Proof idea: unit test confirming `check_account_existence` rejects any non-`Transfer` action bundled with implicit-account creation, preventing key hijacking via multi-action batching.
