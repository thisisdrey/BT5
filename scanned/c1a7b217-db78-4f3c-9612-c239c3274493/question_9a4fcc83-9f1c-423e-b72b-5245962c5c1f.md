`Engine::execute_signed_intent` (`contracts/defuse/core/src/engine/mod.rs`) calls `signed.verify().ok_or(DefuseError::InvalidSignature)?` to get `public_key`, then separately checks `self.state.has_public_key(&signer_id, &public_key)`. Since `signer_id` comes from the untrusted `DefusePayload` itself (not derived from `public_key`), can an attacker who owns `public_key_A` registered under `account_A` craft a `DefusePayload{signer_id: account_B, ...}` signed by `public_key_A`, where `account_B` also happens to have `public_key_A` registered (e.g. shared implicit key derivation), executing intents as `account_B` — violating IDENTITY: the `(signer_id, public_key)` pair authorised == pair actually signed for THAT `signer_id`? Preconditions: attacker controls `public_key_A`; some account_B has `has_public_key(account_B, public_key_A) == true` (e.g. implicit account collision). Call sequence: attacker signs payload with `signer_id: account_B`, submits to `execute_intents`. Impact: Critical, funds of account_B moved by attacker signature. Proof: cargo test constructing two accounts sharing one public key and asserting one can move the other's `token_balances`.
