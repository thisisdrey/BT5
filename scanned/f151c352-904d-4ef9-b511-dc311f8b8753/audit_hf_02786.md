# [H] Note footers should not be 0 in curveRemoveLiquidity() if the corresponding assetOuts are non null

## Summary
Severity: High
Contest weight: 0.0520
Dataset id: 15189
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability resides in the curveRemoveLiquidity function of the protocol, where the routine creates a note that records the details of a liquidity removal. A note footer is intended to serve as a unique identifier for each removal operation. The implementation fails to enforce a non‑zero footer when an assetOut value is supplied (i.e., when the caller actually receives tokens). Because the check is missing, a caller can submit a removal request with a valid assetOut but a footer value of zero. This allows the contract to generate two distinct removal notes that share the same zero footer, effectively creating duplicate note footers. The root cause is an absent validation condition that should reject a zero footer whenever the assetOut field is non‑null. An attacker can exploit this by crafting a removal transaction that reuses the zero footer, causing the protocol’s internal accounting to map multiple removal events to the same identifier. As a result, the protocol may overwrite or merge accounting entries, leading to inconsistencies such as missing refunds, balances that appear unchanged after a removal, or funds that seemingly disappear from the pool. The impact is high because liquidity providers rely on accurate accounting for their deposits and withdrawals; duplicate footers break the invariant that each note uniquely represents a withdrawal, potentially allowing malicious actors to claim more assets than entitled or causing honest users to lose funds. The bug manifests only when curveRemoveLiquidity is called with a non‑null assetOut and a footer of zero; calls with a null assetOut or a non‑zero footer behave correctly. All participants who interact with the liquidity removal path—regular users, liquidity providers, and any contracts that call this function—are affected. The issue was discovered during a manual audit performed by ThreeSigma, which identified the missing require statement. It can be hard to notice because a zero footer may be interpreted as a default or placeholder value, and duplicate notes do not immediately raise an exception; the problem surfaces later when accounting reports show mismatched totals or when users receive no tokens despite a successful transaction. To remediate the flaw, the contract should include a guard that reverts the transaction if the note footer equals zero while assetOut is non‑null, thereby preserving the uniqueness of each note and restoring the integrity of the protocol’s accounting logic. This class of bug falls under improper input validation leading to identifier collision, a common pattern in smart contracts that rely on unique keys for state tracking.

## Recommendation
Revert if the note footer is 0 but the corresponding asset out is not.
