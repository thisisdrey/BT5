## Title
`submit_delivery_receipt` pays relayer reward and settles `PendingOrder` even when the Ethereum delivery `success` flag is `false` - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
`snowbridge_pallet_outbound_queue_v2::Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` (which carries an explicit `success: bool` field reported by the Ethereum `Gateway` contract's `InboundMessageDispatched` event) but never inspects that field before paying the relayer reward and permanently removing the `PendingOrder` entry. This is a structural analog of the Lombard bug: a state that should only be "settled" once the underlying action is *confirmed as actually succeeded* is instead settled merely because *a message about the action was received*, regardless of the confirmation value embedded in that message.

### Finding Description
The `DeliveryReceipt` primitive explicitly carries a `success` field decoded straight from the Solidity event log: [1](#0-0) 

`submit_delivery_receipt` verifies the cryptographic proof of the event log and decodes it into a `DeliveryReceipt`, then unconditionally calls `process_delivery_receipt`: [2](#0-1) 

Inside `process_delivery_receipt`, the pallet validates the gateway address, resolves the reward beneficiary, looks up the `PendingOrder` by nonce, pays the reward if `order.fee > 0`, and removes the order from `PendingOrders` — all without ever reading `receipt.success`: [3](#0-2) 

The doc comment for the module even states the receipt "Verifies the message with proof for a transaction receipt containing the event log ... Fetch the pending order by nonce ... pay reward ... Remove the order," with no mention of checking delivery success: [4](#0-3) 

This mirrors the reported flaw exactly: the guard that should gate settlement ("has the receipt actually confirmed successful completion?") is bypassed. Just as the Lombard `processReceipt()` marked an unstake request paid from *any* retrievable notary session regardless of quorum confirmation, this pallet marks a `PendingOrder` settled (removed) and pays a reward from *any* verifiable Ethereum receipt regardless of whether Ethereum-side execution actually succeeded (`success == false`).

### Impact Explanation
- **Relayer reward is paid for a failed delivery.** A message whose execution reverted on Ethereum (`success = false`, e.g., dispatch of the command failed on the Gateway contract) still causes `T::RewardPayment::register_reward` to run, over-rewarding relayers for non-productive/failed work — public underpriced/unbacked payout, directly matching the "duplicate settlement or payout" / "theft or unbacked mint" impact category.
- **Permanent state loss for failed messages.** Once `<PendingOrders<T>>::remove(nonce)` executes, the order bookkeeping for that message is gone. There is no separate path to retry, refund, or specially account for a message whose delivery failed on Ethereum; the settlement is treated as final and correct even though the underlying action did not succeed, which is the "permanent... bridge-state lock / incorrect settlement" pattern called out in the impact gate.
- Because `submit_delivery_receipt` is a plain `ensure_signed` (unprivileged) extrinsic and the only real gate is proof verification (which any relayer holding a valid Ethereum receipt can produce, honestly reporting `success = false`), this is exploitable by an ordinary relayer with no special privileges, node access, or governance role.

### Likelihood Explanation
Likelihood is moderate-to-high: any relayer that already possesses a legitimately-generated proof of the `InboundMessageDispatched` event (which is emitted regardless of whether the inner command succeeded) can submit it via `submit_delivery_receipt` today. No malicious peer, validator, or governance actor is required — an honest relayer processing an on-chain-failed message would trigger this incorrect settlement/payout during normal operation whenever Ethereum-side command execution fails.

### Recommendation
In `process_delivery_receipt`, only pay the reward and remove the `PendingOrder` when `receipt.success == true`. For `success == false` receipts, either: (a) still remove the order but skip reward payment (if failure should end the retry cycle without reward), or (b) retain the order and emit a distinct `MessageDeliveryFailed` event so downstream logic (fee refund to sender, re-issue, etc.) can act correctly — mirroring the recommended fix pattern from the Lombard report of gating settlement strictly on confirmed success, not mere message receipt.

### Proof of Concept
1. A message is sent from BridgeHub to Ethereum; `do_process_message` inserts a `PendingOrder { nonce, fee, block_number }` into `PendingOrders`.
2. On Ethereum, the Gateway's dispatch of the inner command reverts/fails, but the Gateway still emits `InboundMessageDispatched(nonce, topic, success = false, reward_address)` (this is standard: the event records the *outcome*, not just that dispatch was attempted).
3. Any relayer generates a valid execution/receipt proof for this event log (this is a normal, honest action — no forgery needed) and calls:
   ```
   OutboundQueue::submit_delivery_receipt(origin, Box::new(EventProof { event_log, proof }))
   ```
4. `T::Verifier::verify` succeeds (proof is legitimate), `DeliveryReceipt::try_from` decodes `success = false` correctly.
5. `process_delivery_receipt` proceeds anyway: pays `order.fee` to the reward account via `T::RewardPayment::register_reward`, and calls `<PendingOrders<T>>::remove(nonce)`, emitting `Event::MessageDelivered { nonce }` — even though the message delivery on Ethereum actually failed.
6. Reward is paid for a failed job, and the failed message's order bookkeeping is permanently destroyed, with no compensating mechanism.

This is confirmed directly from the current source; I could not verify from the index whether any downstream code path (e.g., a separate `success == false` branch) exists elsewhere that intercepts this call before reaching `process_delivery_receipt` — based on all located call sites (`submit_delivery_receipt`, direct test/integration calls), no such gating was found.

		) -> DispatchResult

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
