## Title
Off-by-one deadline boundary lets an unpermissioned caller cancel a still-claimable NFT swap at the exact deadline block - ([File: substrate/frame/nfts/src/features/atomic_swap.rs])

### Summary
`pallet-nfts`'s atomic-swap feature checks the swap deadline with two boundary conditions that are supposed to be complementary (swap active vs. swap expired), but they overlap by exactly one block. At `now == swap.deadline`, `do_claim_swap` still treats the swap as valid and lets the counterparty claim it, while `do_cancel_swap` simultaneously treats it as already expired and drops the owner-only permission check, allowing *any* signed account to cancel it. This is the same class of bug as the reported `oToken` issue — a time-boundary value that is not consistently assigned to exactly one of the two mutually-exclusive states — except here the mismatch produces an authorization gap instead of a revert.

### Finding Description
`do_create_swap` stores `deadline = now + duration` [1](#0-0) .

`do_claim_swap` allows the claim as long as the current block is **not after** the deadline: [2](#0-1) 
i.e. `now <= swap.deadline` → still valid, claimable, at `now == deadline`.

`do_cancel_swap` gates the owner-only permission check on whether the deadline **has not yet passed**: [3](#0-2) 
The condition is `swap.deadline > now`. At `now == swap.deadline` this is `false`, so the branch that enforces `item.owner == caller` is skipped entirely, and cancellation proceeds unconditionally for *any* signed origin.

The doc comment even states the intended invariant explicitly: "If the swap offer's deadline has not yet passed, the caller must be the owner of the offered item; otherwise, anyone can cancel an expired offer" — but "has not yet passed" is implemented as strict `>`, while claim's "still valid" is implemented as `<=`. These two conditions should partition the deadline block into exactly one state each; instead, for the single block where `now == deadline`, both "claimable by counterparty" and "cancelable by anyone" are simultaneously true.

The public dispatchables `cancel_swap` and `claim_swap` route directly into these functions with only `ensure_signed` as an origin check [4](#0-3) [5](#0-4) , so any account on the chain can trigger `do_cancel_swap` at that block.

### Impact Explanation
An unprivileged third party (not the item owner, not the swap counterparty) can call `cancel_swap` in the exact block equal to `swap.deadline` and have it succeed without the `NoPermission` check that is otherwise enforced for the entire lifetime of the swap. This deletes `PendingSwapOf` for that item, which:
- Bypasses the origin/permission filter that is supposed to protect the offering party's control over their own listing (a public-wrapper "widen origin / bypass filter" issue).
- Can deny/grief the legitimate counterparty's `claim_swap` in that very block: if the attacker's `cancel_swap` executes first in block `deadline`, the subsequent `claim_swap` call (which is otherwise valid per `now <= swap.deadline`) fails with `UnknownSwap` because the storage entry is gone, even though the protocol's own "still valid" condition says the swap should be honorable at that block.

This does not itself move funds to a wrong beneficiary, but it lets an unauthorized account destroy pending state that governs asset/fund exchange, and it is exploitable purely by an ordinary signed user with no special access — matching the "unauthorized execution" and "public wrappers must not bypass filters" impact categories.

### Likelihood Explanation
Deterministic and trivially triggerable: the attacker only needs to observe (or compute) `swap.deadline` for any pending swap (public storage) and submit `cancel_swap` in that exact block, before or racing with the counterparty's `claim_swap`. No validator/collator/relayer collusion or privileged role is required.

### Recommendation
Make the two conditions partition the deadline consistently, e.g. change `do_cancel_swap`'s guard to `if swap.deadline >= now` (mirroring `do_claim_swap`'s `now <= swap.deadline`), so that at `now == swap.deadline` the swap is still considered "not yet expired" and the owner-only permission check still applies. Add a regression test that exercises `cancel_swap` and `claim_swap` at exactly `now == swap.deadline` from a non-owner, non-counterparty account to pin the boundary.

### Proof of Concept
1. `user_1` creates a swap on `item_1` with `duration = D`; deadline is recorded as `now0 + D`.
2. Advance the chain to block `now0 + D` exactly (`System::set_block_number(deadline)`).
3. An unrelated `attacker` account (not `item_1` owner) calls `Nfts::cancel_swap(RuntimeOrigin::signed(attacker), collection_id, item_1)`.
4. Because `swap.deadline > now` evaluates to `false` at equality, `do_cancel_swap` skips the `ensure!(item.owner == caller, NoPermission)` check and succeeds, removing `PendingSwapOf`.
5. If the intended counterparty then calls `claim_swap` in the same block, it fails with `Error::<Test>::UnknownSwap`, even though `now <= swap.deadline` would otherwise have permitted the claim (existing tests only check `deadline + 1` for permissionless cancel and never exercise the exact-equality block, e.g. [6](#0-5) ).
