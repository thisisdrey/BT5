## Finding: Snowbridge `register_token` binds ERC20 name/symbol to attacker-chosen strings, not to the canonical on-chain asset metadata

### Title
Unvalidated `AssetMetadata` name/symbol in `register_token` allows any asset owner to mint an Ethereum ERC20 wrapper impersonating a legitimate token's ticker - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`, `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

### Summary
The external report's core defect is that asset identity is derived from a spoofable, self-reported string (`symbol()`/`name()`) instead of a canonical, immutable identifier bound to the real token. The same broken invariant exists in Snowbridge's token-registration flow: the `name`/`symbol`/`decimals` fields supplied in `AssetMetadata` are taken verbatim from the caller and forwarded into the `RegisterForeignToken` command that instantiates a wrapped ERC20 on Ethereum, with no check that they match the actual metadata registered for the underlying asset (`pallet_assets::Metadata`). Only the `asset_id` `Location` is authorization-checked; the ticker/name shown to relayers, wallets and users is fully attacker-controlled.

### Finding Description
`SnowbridgeSystemFrontend::register_token` on AssetHub validates only that the caller is authorized for the given `asset_id` location: [1](#0-0) 

`T::RegisterTokenOrigin::ensure_origin(origin, &asset_location)` proves the caller is nested within/owns that particular `Location` — it says nothing about the `metadata: AssetMetadata` argument, which is passed through untouched: [2](#0-1) 

This call is relayed via XCM `Transact` to `EthereumSystem::register_token` on BridgeHub (`system-v2` pallet), which again forwards `metadata.name`/`metadata.symbol`/`metadata.decimals` directly into the `Command::RegisterForeignToken` without cross-checking them against the asset's actual registered metadata (e.g. `pallet_assets::Metadata` for that `Location`): [3](#0-2) 

The legacy `snowbridge-pallet-system::do_register_token` (root-gated path) has the same pattern — metadata is taken as-is and encoded into the outbound command: [4](#0-3) 

The `Command::RegisterForeignToken` variant carries free-form `name`/`symbol` bytes that get ABI-encoded and used by the Ethereum Gateway contract to deploy/label the wrapped ERC20: [5](#0-4) [6](#0-5) 

Because `pallet_assets` permits permissionless creation of new (foreign or local) assets, any user can create their own worthless asset at some `Location`, satisfy `RegisterTokenOrigin` for that location (they own it), and then call `register_token` with `metadata.symbol = "USDC"` / `metadata.name = "USD Coin"`. The resulting `token_id` (derived from `TokenIdOf::convert_location(&location)`) is unique and legitimate from the pallet's point of view, but the human-readable name/symbol shown on the deployed Ethereum ERC20 has zero binding to any real USDC asset — exactly the "use of name to identify a token" flaw from the external report, just inverted (name spoofs identity outward to Ethereum instead of inward from a fake token).

### Impact Explanation
Wallets, relayers, bridge front-ends and off-chain tooling commonly display/select bridged assets by symbol/name for user convenience. A registered "USDC" wrapped ERC20 whose backing `token_id`/`Location` is actually an attacker-owned, valueless asset can deceive users and integrators who key off name/symbol rather than the opaque `token_id`. Funds bridged toward the fraudulent wrapper, or reserve/liquidity commitments made against it under the belief it represents canonical USDC, are lost or diverted to the attacker — a fund-loss/impersonation impact consistent with "theft or unbacked mint" and "forged or mis-bound... state acceptance" in the impact gate, since the protocol itself creates the mis-bound state (name/symbol not bound to canonical asset) rather than requiring a malicious relayer/validator.

### Likelihood Explanation
The attack requires only: (1) creating an asset via the standard, permissionless `pallet_assets::create`/foreign-asset creation path, and (2) calling the public `register_token` extrinsic with attacker-chosen metadata — both are unprivileged, single-transaction actions requiring no governance, no relayer collusion, and no validator control. This is a public-entrypoint, unprivileged-attacker path as required by the impact gate.

### Recommendation
When registering a foreign token, derive `name`/`symbol`/`decimals` from the canonical on-chain metadata already stored for the asset at `asset_location` (e.g. read `pallet_assets::Metadata` keyed by the resolved `AssetId`) rather than accepting arbitrary caller-supplied `AssetMetadata`. If a caller-supplied override must be supported, enforce uniqueness of `symbol`/`name` per Ethereum Gateway (or store the canonical location as an immutable identifier and reject re-registration attempts under an already-used symbol), analogous to storing a constant, address-bound identifier in `CelerIMFacet.sol` rather than trusting a self-reported name.

### Proof of Concept
1. On AssetHub, call `pallet_assets::create` (or the foreign-assets equivalent) to create asset `X` at `Location` `L_attacker`, owned by the attacker — this is publicly permitted.
2. Call `SnowbridgeSystemFrontend::register_token(origin=attacker, asset_id=L_attacker, metadata={name:"USD Coin", symbol:"USDC", decimals:6}, fee_asset=...)`. [1](#0-0) 
3. `T::RegisterTokenOrigin::ensure_origin` succeeds because the attacker genuinely owns `L_attacker`; no check compares `metadata` to `L_attacker`'s real registered metadata.
4. The XCM `Transact` reaches BridgeHub's `EthereumSystem::register_token`, which emits `Command::RegisterForeignToken{ token_id: TokenIdOf(L_attacker), name: "USD Coin", symbol: "USDC", decimals: 6 }`. [7](#0-6) 
5. The Ethereum Gateway deploys/labels an ERC20 wrapper displaying "USDC" that is, in fact, backed by the attacker's worthless asset `X`, not real USDC — deceiving any party that identifies the token by name/symbol. [8](#0-7)

		/// Registers a Polkadot-native token as a wrapped ERC20 token on Ethereum.
		///
		/// The system frontend pallet on AH proxies this call to BH.
		///
		/// - `sender`: The original sender initiating the call on AH
		/// - `asset_id`: Location of the asset (relative to this chain)
		/// - `metadata`: Metadata to include in the instantiated ERC20 contract on Ethereum
		#[pallet::call_index(2)]
		#[pallet::weight(<T as pallet::Config>::WeightInfo::register_token())]
		pub fn register_token(
			origin: OriginFor<T>,
			sender: Box<VersionedLocation>,
			asset_id: Box<VersionedLocation>,
			metadata: AssetMetadata,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let sender_location: Location =
				(*sender).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;
			let asset_location: Location =
				(*asset_id).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;

			let location = Self::reanchor(asset_location)?;
			let token_id = TokenIdOf::convert_location(&location)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			if !ForeignToNativeId::<T>::contains_key(token_id) {
				ForeignToNativeId::<T>::insert(token_id, location.clone());
			}

			let command = Command::RegisterForeignToken {
				token_id,
				name: metadata.name.into_inner(),
				symbol: metadata.symbol.into_inner(),
				decimals: metadata.decimals,
			};

			let message_origin = Self::location_to_message_origin(sender_location)?;
			Self::send(message_origin, command, amount)?;

			Self::deposit_event(Event::<T>::RegisterToken {
				location: location.into(),
				foreign_token_id: token_id,
			});

			Ok(())
		}

			metadata: AssetMetadata,

			let ethereum_location = T::EthereumLocation::get();

				.map_err(|_| Error::<T>::LocationConversionFailed)?;

				token_id,
				name: metadata.name.into_inner(),
				symbol: metadata.symbol.into_inner(),
				decimals: metadata.decimals,

			Self::send(SECONDARY_GOVERNANCE_CHANNEL, command, pays_fee)?;

				location: location.clone().into(),
