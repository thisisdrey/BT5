## Finding: `ChargeAssetTxPayment` fee swap has no user-supplied maximum, exposing payers to unbounded price impact

The bug report's core pattern — a module computes a value-transfer amount from a live, potentially stale/volatile price feed, and the caller has no way to bound that amount — has a direct analog in `pallet-asset-conversion-tx-payment`'s `SwapAssetAdapter`.

### Where it lives

`ChargeAssetTxPayment<T>` is the `TransactionExtension` that lets a signed extrinsic pay fees in a non-native asset. It only carries `tip` and `asset_id` — there is no field allowing the signer to cap how much of that asset they are willing to spend: [1](#0-0) 

At `withdraw_fee` time (which runs as part of `pre_dispatch`, i.e. at the moment the extrinsic is actually applied inside a block — not when the user signed it), the pallet queries the **current, live** AMM pool price via `quote_price_tokens_for_exact_tokens`, withdraws exactly that quoted amount of the user's asset, and swaps it for the exact native fee: [2](#0-1) 

### Why this is the same broken invariant as `LiquidateBorrow`

In the Umee report, `LiquidateBorrow` computes a transfer amount from an oracle price at execution time with no caller-supplied bound (`minRewardAmount`), so a price update landing just before the call can make the payout far worse than the caller expected. Here, the corrupted value is `asset_fee` in `SwapAssetAdapter::withdraw_fee` — it is derived from the pool's spot price **at inclusion time**, not at signing time, and the extension exposes no `max_fee_in_asset` (or similar) parameter for the signer to bound it. Any other transaction included earlier in the same block that moves the `asset_id`/native pool ratio (e.g., a large legitimate swap, or one crafted deliberately) directly changes how much of the fee-payer's asset gets debited, with the fee-payer having no on-chain mechanism to cap the loss. This exactly mirrors the recommended fix in the report: "enable the caller to add ... an upper limit for a transfer of the caller's funds to a module."

`can_withdraw_fee` (used for dry-run/mempool validation) performs the same unbounded quote, so even the validation step gives the user no enforceable guarantee about the final debited amount: [3](#0-2) 

Contrast this with `pallet-asset-conversion`'s own public swap extrinsics, which do implement exactly the caller-supplied bound the report recommends (`amount_out_min` / `amount_in_max`) and reject the swap if the bound is violated: [4](#0-3) 

`SwapAssetAdapter` reuses the same `SwapCredit` machinery but never plumbs a user-chosen upper bound into it for the fee-payment path.

### Impact and likelihood

This does not let an attacker steal funds outright, but it does let anyone move the AMM price (via ordinary, permissionless swap transactions) to force other users paying fees in a non-native asset to pay more of that asset than intended, with no on-chain mechanism to protect them — a value-conservation issue for unprivileged, always-reachable fee-payment flow, consistent with "runtime bugs that compromise intended behavior" in the impact gate. It requires no malicious validator, relayer, or governance actor — only an ordinary account submitting a swap in the same block, which is normal permissionless activity.

### Recommendation

Add an optional `max_fee_in_asset` (or similar) field to `ChargeAssetTxPayment`/`OnChargeAssetTransaction::withdraw_fee`, and have `SwapAssetAdapter::withdraw_fee` reject the transaction (return `InvalidTransaction::Payment`) if the freshly quoted `asset_fee` exceeds the caller-specified bound, mirroring the `amount_in_max`/`amount_out_min` pattern already used by `pallet-asset-conversion`'s public swap extrinsics. [5](#0-4)

pub struct SwapAssetAdapter<A, F, S, OU>(PhantomData<(A, F, S, OU)>);

impl<A, F, S, OU, T> OnChargeAssetTransaction<T> for SwapAssetAdapter<A, F, S, OU>
where
	A: Get<T::AssetId>,
	F: fungibles::Balanced<T::AccountId, Balance = BalanceOf<T>, AssetId = T::AssetId>,
	S: SwapCredit<
			T::AccountId,
			Balance = BalanceOf<T>,
			AssetKind = T::AssetId,
			Credit = fungibles::Credit<T::AccountId, F>,
		> + QuotePrice<Balance = BalanceOf<T>, AssetKind = T::AssetId>,
	OU: OnUnbalanced<fungibles::Credit<T::AccountId, F>>,
	T: Config,
{
	type AssetId = T::AssetId;
	type Balance = BalanceOf<T>;
	type LiquidityInfo = (fungibles::Credit<T::AccountId, F>, BalanceOf<T>);

	fn withdraw_fee(
		who: &T::AccountId,
		_call: &T::RuntimeCall,
		_dispatch_info: &DispatchInfoOf<<T>::RuntimeCall>,
		asset_id: Self::AssetId,
		fee: Self::Balance,
		_tip: Self::Balance,
	) -> Result<Self::LiquidityInfo, TransactionValidityError> {
		if asset_id == A::get() {
			// The `asset_id` is the target asset, we do not need to swap.
			let fee_credit = F::withdraw(
				asset_id.clone(),
				who,
				fee,
				Precision::Exact,
				Preservation::Preserve,
				Fortitude::Polite,
			)
			.map_err(|_| InvalidTransaction::Payment)?;

			return Ok((fee_credit, fee));
		}

		// Quote the amount of the `asset_id` needed to pay the fee in the asset `A`.
		let asset_fee =
			S::quote_price_tokens_for_exact_tokens(asset_id.clone(), A::get(), fee, true)
				.filter(|asset_fee| !asset_fee.is_zero())
				.ok_or(InvalidTransaction::Payment)?;

		// Withdraw the `asset_id` credit for the swap.
		let asset_fee_credit = F::withdraw(
			asset_id.clone(),
			who,
			asset_fee,
			Precision::Exact,
			Preservation::Preserve,
			Fortitude::Polite,
		)
		.map_err(|_| InvalidTransaction::Payment)?;

		let (fee_credit, change) = match S::swap_tokens_for_exact_tokens(
			vec![asset_id, A::get()],
			asset_fee_credit,
			fee,
		) {
			Ok((fee_credit, change)) => (fee_credit, change),
			Err((credit_in, _)) => {
				defensive!("Fee swap should pass for the quoted amount");
				let _ = F::resolve(who, credit_in).defensive_proof("Should resolve the credit");
				return Err(InvalidTransaction::Payment.into());
			},
		};

		// Since the exact price for `fee` has been quoted, the change should be zero.
		ensure!(change.peek().is_zero(), InvalidTransaction::Payment);

		Ok((fee_credit, asset_fee))
	}
