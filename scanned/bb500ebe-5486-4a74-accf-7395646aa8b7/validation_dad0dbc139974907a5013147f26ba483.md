### Title
Out-of-bounds pointer dereference in EVM bytecode interpreter via unchecked `unsafe` jump/read operations - (File: `substrate/frame/revive/src/vm/evm/ext_bytecode.rs`)

### Summary
`pallet-revive`'s EVM-compatible interpreter tracks the current bytecode position with a raw pointer (`instruction_pointer: *const u8`) and moves/dereferences it through `unsafe` blocks in `relative_jump`, `absolute_jump`, `opcode`, `pc`, and `read_slice`. The `SAFETY` comments claim the caller has validated the offsets, but the only enforcement present is a `debug_assert!`, which is compiled out entirely in release/production builds (the configuration a live chain actually runs). This is the same failure class as the reported Uniswap issue: code annotated as memory-safe that does not actually enforce the invariants it depends on, letting attacker-controlled input violate memory safety.

### Finding Description
`ExtBytecode` in [1](#0-0)  stores a raw `*const u8` instruction pointer into the contract's bytecode buffer.

- `relative_jump` advances the pointer by a caller-supplied signed `offset` inside `unsafe { self.instruction_pointer.offset(offset) }`, guarded only by a `debug_assert!` that checks the resulting `pc` is within bounds: [2](#0-1) 
- `absolute_jump` sets the pointer to `self.base.bytes_ref().as_ptr().add(offset)` for a caller-supplied `offset`, again only checked via `debug_assert!`: [3](#0-2) 
- `opcode()` unconditionally dereferences the pointer: `unsafe { *self.instruction_pointer }` [4](#0-3) 
- `read_slice(len)` builds a slice directly from the raw pointer with `core::slice::from_raw_parts(self.instruction_pointer, len)`, bounds-checked only via `debug_assert!`: [5](#0-4) 

Because `debug_assert!` is stripped from release builds, a production runtime built without debug assertions performs **no bounds validation at all** at the point of unsafe pointer arithmetic/dereference. The confirmation that this was previously entirely unchecked is captured in the project's own PR history: [6](#0-5)  explicitly states this PR only "Add[ed] debug assertions for unsafe bytecode operations: in relative_jump, absolute_jump, and read_slice" — i.e., these functions previously had zero bounds enforcement, and even after the patch the enforcement is debug-build-only.

These operations back the EVM `JUMP`/`JUMPI` and `PUSH*` opcodes, invoked from `substrate/frame/revive/src/vm/evm/instructions/control.rs` and `substrate/frame/revive/src/vm/evm/instructions/stack.rs`. An unprivileged user can deploy arbitrary EVM bytecode to `pallet-revive` (via the public `instantiate`/`instantiate_with_code` extrinsics) and craft a jump target or push length that is out of range for the deployed code buffer.

### Impact Explanation
If the offset/length passed into these functions is attacker-controlled and not independently bounds-checked upstream (which the codebase's own historical fix implies it was not), this leads to:
- Out-of-bounds pointer arithmetic and dereference (`opcode()`, `read_slice`) reading adjacent heap memory outside the bytecode allocation — undefined behavior in Rust that can crash the node process (denial of service / halted block production for every validating/collating node that executes the transaction) or leak adjacent heap bytes into the interpreter's stack state (potential information disclosure).
- Because this executes inside block execution (not sandboxed guest memory like PolkaVM's own linear memory model, but the *host's* Rust heap), an out-of-bounds read/crash here directly threatens node availability across the network processing the same block — a "bring down a Substrate-based chain without direct machine access" class impact.

### Likelihood Explanation
Likelihood depends on whether callers in `control.rs`/`stack.rs` perform their own independent bounds checks before invoking these functions (unconfirmed within the excerpts retrieved). However, the project's own PR description for `pr_10922.prdoc` explicitly frames these three functions as having previously lacked any assertion, and the "fix" applied is only a `debug_assert!`, which provides zero protection in a release-mode validator/collator binary. This strongly suggests the bounds checking burden was assumed to live at the call site but was not actually enforced end-to-end, matching exactly the "safe-annotated but not actually safe" pattern from the seed report.

### Recommendation
Replace the `debug_assert!` guards in `relative_jump`, `absolute_jump`, and `read_slice` with real, always-on bounds checks (`assert!`, or better, return a `Result`/trap on out-of-range offsets) so that malformed/malicious bytecode cannot move the instruction pointer or slice length outside the underlying buffer in release builds. Audit all call sites in `instructions/control.rs` and `instructions/stack.rs` to confirm jump targets and push lengths are validated against the actual bytecode length before calling into `ExtBytecode`.

### Proof of Concept
Conceptual PoC (pending confirmation of call-site validation, since full caller code was not retrievable):
1. Deploy an EVM contract to `pallet-revive` whose bytecode ends with a `JUMP`/`JUMPI` opcode targeting an offset equal to or greater than the bytecode length, or a `PUSH32` at the very end of the code (fewer than 32 trailing bytes available).
2. Call the contract so the interpreter executes the crafted opcode; in a release build, `absolute_jump`/`relative_jump` moves `instruction_pointer` out of the bytecode allocation with no check, and the subsequent `opcode()`/`read_slice()` dereferences/reads out-of-bounds memory.
3. Observe undefined behavior: a crash of the executing node process (chain-wide execution halt for that block) or leakage of adjacent heap bytes into the EVM stack, depending on heap layout.

	/// Relative jumps does not require checking for overflow.
	pub fn relative_jump(&mut self, offset: isize) {
		// SAFETY: The offset is validated by the caller to ensure it points within the bytecode
		debug_assert!(
			{
				let bytes = self.base.bytes_ref();
				let new_pc = self.pc().wrapping_add_signed(offset);
				new_pc <= bytes.len()
			},
			"relative_jump would move instruction pointer out of bounds"
		);
		self.instruction_pointer = unsafe { self.instruction_pointer.offset(offset) };
	}
