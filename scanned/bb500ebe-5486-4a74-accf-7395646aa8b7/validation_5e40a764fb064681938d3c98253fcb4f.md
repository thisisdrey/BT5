### Title
Unbounded-price AMM swap in transaction-fee payment enables sandwich extraction of user funds - (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

### Summary
`pallet-asset-conversion-tx-payment`'s `SwapAssetAdapter::withdraw_fee` pays transaction fees in a non-native asset by quoting a price from `pallet-asset-conversion`'s AMM pool and then executing a real swap at whatever price the pool holds at inclusion time. There is no user-supplied maximum-acceptable-input parameter exposed to the signer of the extrinsic (unlike the pallet's own `swap_tokens_for_exact_tokens` extrinsic, which does expose `amount_in_max`). This mirrors exactly the reported bug class: an AMM swap executed without a caller-specified minimum-return/maximum-cost bound, letting MEV searchers sandwich the trade and extract value from the victim.

### Finding Description
`SwapAssetAdapter::withdraw_fee` (`substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs:119-176`) is used as the `OnChargeAssetTransaction` implementation for `pallet_asset_conversion_tx_payment` (confirmed wired up in `substrate/bin/node/runtime/src/lib.rs:683-695`, and referenced in `cumulus/parachains/runtimes/assets/asset-hub-rococo/src/lib.rs`, `asset-hub-westend/src/lib.rs`, `staking-async/runtimes/parachain/src/lib.rs`, and `penpal/src/lib.rs`).

The relevant flow:

The user never provides (and the transaction extension `ChargeAssetTxPayment` never accepts) any bound such as `amount_in_max` or `max_asset_fee`. The amount of the fee-asset that will actually be debited is determined solely by the *current* AMM reserves at the moment this transaction is validated/executed on-chain — `Self::credit_swap`/`get_amount_in` in `substrate/frame/asset-conversion/src/lib.rs` computes `amount_in` purely from live reserves, with no ceiling supplied by the caller.

Contrast this with the pallet's own dispatchable `swap_tokens_for_exact_tokens` (`substrate/frame/asset-conversion/src/lib.rs:527-545` and companions), which requires an explicit `amount_out_min`/`amount_in_max` from the caller and rejects the swap via `Error::<T>::ProvidedMaximumNotSufficientForSwap` if the price has moved unfavorably. The `SwapCredit` trait itself (`substrate/frame/asset-conversion/src/swap.rs:93-113`) provides no such parameter for the exact-output variant used here, so `SwapAssetAdapter` has no mechanism to protect the fee payer even if it wanted to.

### Impact Explanation
Because the swap price is resolved from whatever pool reserves exist at the exact block/position where the victim's extrinsic executes, an attacker who can influence transaction ordering within a block (a normal, unprivileged actor competing for block space via tip/priority — not a validator, collator, or relayer) can:
1. Submit a swap that shifts the `asset_id`/`A::get()` pool reserves unfavorably immediately before the victim's transaction.
2. Let the victim's fee-payment swap execute at the now-worse price, causing `quote_price_tokens_for_exact_tokens`/`swap_tokens_for_exact_tokens` to consume more of the victim's asset than the fair-market rate would require for the fixed `fee`.
3. Reverse the price shift with a follow-up transaction, capturing the extracted spread as MEV profit.

This is a direct funds-loss primitive against the account paying transaction fees in a non-native asset, and it is triggered on the hot path of ordinary transaction execution (every transaction that opts into `asset_id: Some(...)` in `ChargeAssetTxPayment`) — not merely an XCM/bridge edge case. It matches "public underpriced work that degrades ... / theft or unbacked mint" style value leakage called out in the impact gate, and the "message queues/payout state must only advance after settlement succeeds atomically" pivot is violated in spirit because the settlement amount is not bounded by the payer's actual intent.

### Likelihood Explanation
Likelihood is high in any production runtime configuring `SwapAssetAdapter` with low-liquidity or thinly-traded fee-asset pools, since:
- The attack requires only ordinary signed transactions (a swap call plus the fee-paying extrinsic), no elevated privilege, no leaked keys, and no compromised infrastructure.
- Sandwiching around specific extrinsics via priority/tip manipulation or same-block ordering is a well-established, practical technique in Substrate-based chains where transaction ordering is influenced by fee/tip rather than strict FCFS.
- The vulnerability requires no cooperation from the block author beyond normal inclusion of fee-paying transactions, and `asset-conversion` pools on Asset Hub-style runtimes are permissionlessly creatable/fundable by anyone, letting an attacker choose or create a shallow pool to amplify slippage.

### Recommendation
Extend `OnChargeAssetTransaction`/`ChargeAssetTxPayment` to accept an optional caller-supplied maximum acceptable `asset_fee` (analogous to `amount_in_max`), and have `SwapAssetAdapter::withdraw_fee` reject the transaction (return `InvalidTransaction::Payment`) if the live-quoted/actual `asset_fee` exceeds that bound, mirroring the protection already present in `Pallet::swap_tokens_for_exact_tokens`. At minimum, expose the quoted price used for fee estimation to the signer at submission time and re-validate against it at inclusion, so a moved price causes a rejected/invalid transaction rather than a silently worse execution.

### Proof of Concept
1. Deploy/observe a runtime with `pallet_asset_conversion_tx_payment::Config::OnChargeAssetTransaction = SwapAssetAdapter<Native, NativeAndAssets, AssetConversion, ...>` (as in `substrate/bin/node/runtime/src/lib.rs:683-695`) and a shallow `AssetX/Native` pool.
2. Victim submits a normal call with `ChargeAssetTxPayment::from(tip, Some(asset_id))`, expecting to pay `fee_in_asset ≈ quote_price_tokens_for_exact_tokens(asset_id, Native, fee, true)` based on current reserves.
3. Attacker submits, in the same block ahead of the victim's transaction (using tip/priority ordering), a large `AssetConversion::swap_exact_tokens_for_tokens` trade that moves the `asset_id`/`Native` pool price unfavorably for anyone buying `Native`.
4. Victim's transaction executes `SwapAssetAdapter::withdraw_fee`, which requotes at the now-worse reserves (`payment.rs:142-176`) and withdraws a materially larger `asset_fee` than the victim would have accepted, with no on-chain mechanism to cap or reject this.
5. Attacker submits a reverse trade immediately after, restoring the pool and pocketing the price-impact spread extracted from the victim's fee payment — the sandwich completes within one or two blocks using only ordinary signed extrinsics. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

		pub(crate) fn do_swap_credit_tokens_for_exact_tokens(
			path: Vec<T::AssetKind>,
			credit_in: CreditOf<T>,
			amount_out: T::Balance,
		) -> Result<(CreditOf<T>, CreditOf<T>), (CreditOf<T>, DispatchError)> {
			let amount_in_max = credit_in.peek();
			let inspect_path = |credit_asset| {
				ensure!(
					path.first().map_or(false, |a| a == &credit_asset),
					Error::<T>::InvalidPath
				);
				ensure!(amount_in_max > Zero::zero(), Error::<T>::ZeroAmount);
				ensure!(amount_out > Zero::zero(), Error::<T>::ZeroAmount);

				Self::validate_swap_path(&path)?;
				let path = Self::balance_path_from_amount_out(amount_out, path)?;

				let amount_in = path.first().map(|(_, a)| *a).ok_or(Error::<T>::InvalidPath)?;
				ensure!(
					amount_in <= amount_in_max,
					Error::<T>::ProvidedMaximumNotSufficientForSwap
				);

				Ok((path, amount_in))
			};
			let (path, amount_in) = match inspect_path(credit_in.asset()) {
				Ok((p, a)) => (p, a),
				Err(e) => return Err((credit_in, e)),
			};

			let (credit_in, credit_change) = credit_in.split(amount_in);
			let credit_out = Self::credit_swap(credit_in, &path)?;

			Self::deposit_event(Event::SwapCreditExecuted { amount_in, amount_out, path });

			Ok((credit_out, credit_change))
		}
