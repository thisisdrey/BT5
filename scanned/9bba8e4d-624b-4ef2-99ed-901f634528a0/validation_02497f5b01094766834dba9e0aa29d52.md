### Title
Restricted/blacklisted accounts can still receive staking reward payouts via `payee`, bypassing the staking participation `Filter` - (File: `substrate/frame/staking/src/pallet/mod.rs`, `substrate/frame/staking/src/pallet/impls.rs`)

### Summary
`pallet-staking` (and its async counterpart `pallet-staking-async`) introduced a `T::Filter: Contains<AccountId>` check to block "restricted" accounts from participating in staking (e.g. accounts that already stake via `pallet-nomination-pools`, see PR-doc `prdoc/stable2503/pr_7685.prdoc`). The filter is enforced on the *stash* for `bond`, `bond_extra`, and `rebond`, but it is never enforced on the `payee`/reward-destination account. Any unrestricted staker can set an arbitrary restricted account as their `RewardDestination::Account`, so restricted accounts can still receive staking payouts, mirroring the BakerFi bug where the recipient of vault shares was never checked against the whitelist even though the caller was.

### Finding Description
`Pallet::<T>::bond` checks the filter only for the stash origin: [1](#0-0) 

```rust
let stash = ensure_signed(origin)?;
ensure!(!T::Filter::contains(&stash), Error::<T>::Restricted);
```

The `payee: RewardDestination<T::AccountId>` parameter accepted by the same call, and by `set_payee`/the `StakingInterface::set_payee`/`bond` implementations, is never passed through `T::Filter::contains`: [2](#0-1) [3](#0-2) 

The `Config::Filter` doc comment states its purpose explicitly: to blacklist accounts "participating in staking in another way (such as pools)": [4](#0-3) 

Because the check is only applied to the `stash`/`controller` origin and not to the `payee` account, any unrestricted account can bond and name a restricted account as its reward destination. The restricted account then continuously accumulates staking reward payouts to its free balance every era, without ever passing through the `Filter` gate itself — exactly the "receiver isn't whitelist-checked" pattern from the BakerFi report, where the whitelist was enforced on the caller/depositor but not on the beneficiary receiving the value.

### Impact Explanation
The restriction mechanism is designed to prevent double participation/economic exposure to staking for a designated set of accounts (e.g., accounts already staking through `pallet-nomination-pools`, or accounts a runtime operator wants excluded from staking economics for policy reasons). This gap lets any signer route staking reward payouts to a restricted account indefinitely, defeating the intended invariant that restricted accounts cannot obtain staking-economics value. This is a compromise of intended runtime behavior in the staking/reward-payout subsystem, matching the "runtime bugs that compromise intended behavior" category and the "reward payouts" pivot named in the task.

### Likelihood Explanation
The action requires no privileged role: any signed, unrestricted account can call `bond`/`set_payee` and name any restricted account as `payee`. No malicious peer/validator/relayer/admin is required — an ordinary user triggers it via the standard public `bond`/`set_payee` extrinsics.

### Recommendation
Extend the `T::Filter::contains` check in `bond`, `set_payee`, and the `StakingInterface::bond`/`set_payee` implementations to also validate the `payee`/`reward_acc` account (when it resolves to `RewardDestination::Account`), rejecting the call with `Error::<T>::Restricted` if the destination account is in the restrict list — consistent with how the stash side is already checked.

### Proof of Concept
1. Runtime configures `Filter = MockedRestrictList` and adds account `B` to the restrict list (as in `restrict(&bob)` in the test helpers): [5](#0-4) 
2. Unrestricted account `A` calls `Staking::bond(origin_A, value, RewardDestination::Account(B))` — this succeeds because only `T::Filter::contains(&A)` is checked, not `B`.
3. Every era, `B`'s free balance receives staking reward payouts even though `B` is restricted and could never itself call `bond` (`Staking::bond(origin_B, ...)` would fail with `Error::<T>::Restricted`, as demonstrated by the existing test `restricted_accounts_can_only_withdraw`): [6](#0-5) 
4. `A` can additionally call `Staking::set_payee(origin_A, RewardDestination::Account(B))` at any time to redirect rewards to `B`, again with no filter check on `B`: [7](#0-6)

	fn set_payee(stash: &Self::AccountId, reward_acc: &Self::AccountId) -> DispatchResult {
		// Since virtual stakers are not allowed to compound their rewards as this pallet does not
		// manage their locks, we do not allow reward account to be set same as stash. For
		// external pallets that manage the virtual bond, they can claim rewards and re-bond them.
		ensure!(
			!Self::is_virtual_staker(stash) || stash != reward_acc,
			Error::<T>::RewardDestinationRestricted
		);

		let ledger = Self::ledger(Stash(stash.clone()))?;
		ledger
			.set_payee(RewardDestination::Account(reward_acc.clone()))
			.defensive_proof("ledger was retrieved from storage, thus its bonded; qed.")?;

		Ok(())
	}

#[test]
fn restricted_accounts_can_only_withdraw() {
	ExtBuilder::default().build_and_execute(|| {
		start_active_era(1);
		// alice is a non blacklisted account.
		let alice = 301;
		let _ = Balances::make_free_balance_be(&alice, 500);
		// alice can bond
		assert_ok!(Staking::bond(RuntimeOrigin::signed(alice), 100, RewardDestination::Staked));
		// and bob is a blacklisted account
		let bob = 302;
		let _ = Balances::make_free_balance_be(&bob, 500);
		restrict(&bob);

		// Bob cannot bond
		assert_noop!(
			Staking::bond(RuntimeOrigin::signed(bob), 100, RewardDestination::Staked,),
			Error::<Test>::Restricted
		);

		// alice is blacklisted now and cannot bond anymore
		restrict(&alice);
		assert_noop!(
			Staking::bond_extra(RuntimeOrigin::signed(alice), 100),
			Error::<Test>::Restricted
		);
