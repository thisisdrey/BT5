### Title
Integer-division truncation in Snowbridge outbound-queue fee conversion lets senders underpay for guaranteed relayer rewards - (File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs)

### Summary
`Pallet::calculate_fee` (`bridges/snowbridge/pallets/outbound-queue/src/lib.rs:368-393`) converts an Ethereum-denominated fee (18 decimals) into native currency via `convert_from_ether_decimals`, which performs plain floor division `value.checked_div(denom)` (line 417). This is directly analogous to the reported `_calculateInterest` bug: a value that is genuinely non-zero pre-division can be truncated to zero (or under-collected) purely because of integer-division rounding, while the corresponding on-chain commitment (the relayer `reward` written into the committed message) is set independently from a fixed governance parameter and is **not** re-derived from the rounded value.

### Finding Description
`calculate_fee` computes the remote fee owed to relayers as:
```
bridges/snowbridge/pallets/outbound-queue/src/lib.rs:368-393
let fee = Self::calculate_remote_fee(gas_used_at_most, params.fee_per_gas, params.rewards.remote);
let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);
let fee = FixedU128::from_inner(fee)
    .saturating_mul(params.multiplier)
    .checked_div(&params.exchange_rate)
    .expect("exchange rate is not zero; qed")
    .into_inner();
let fee = Self::convert_from_ether_decimals(fee);
Fee::from((Self::calculate_local_fee(), fee))
```
and
```
bridges/snowbridge/pallets/outbound-queue/src/lib.rs:411-418
pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
    let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
    let denom = 10u128.saturating_pow(decimals);
    value.checked_div(denom).expect("divisor is non-zero; qed").into()
}
```
For DOT (`T::Decimals = 10`), `denom = 10^8`; for KSM (`Decimals = 12`), `denom = 10^6`. Any `value` smaller than `denom` truncates to `0`, and any value that is not an exact multiple of `denom` loses its remainder permanently (rounded down, never rounded up).

Meanwhile, `do_process_message` (lines 332-352) independently writes the reward the relayer will actually be paid on Ethereum:
```
bridges/snowbridge/pallets/outbound-queue/src/lib.rs:332-350
let pricing_params = T::PricingParameters::get();
...
let reward = pricing_params.rewards.remote;
...
reward: reward.try_into().defensive_unwrap_or(u128::MAX),
```
This `reward` value is the raw, ungoverned-by-rounding `pricing_params.rewards.remote` — it is committed to the message as-is and is what the Ethereum gateway pays the relayer per the module doc's own fee-settlement formula (`Min(GasPrice, MaxFeePerGas) * GasUsed() + Message.Reward`, lines 72-78). The amount the *sender* is actually charged, however, is `Fee` returned from `calculate_fee` via `SendMessage::validate` (`send_message_impl.rs:41-74`), which is the rounded-down converted value.

Because the multiplier/exchange-rate division happens before the ether→native decimal conversion, and because that conversion floors rather than rounds up, there exist governance-configurable combinations of `fee_per_gas`, `rewards.remote`, `multiplier`, and `exchange_rate` for which the computed native-currency fee is strictly less than the true cost of the reward that will be paid out on Ethereum — in the worst case, zero. Nothing in `validate`, `deliver`, or `do_process_message` checks that the calculated fee is non-zero or covers the committed `reward`; the `expect(...)` calls only guard against a zero *divisor*, not a zero or under-collected *result*.

This mirrors the Beedle root cause exactly: a chain of divisions (rate conversion, then decimal-scaling division) that always rounds toward zero, applied on the path that determines how much value the protocol collects versus how much value it has unconditionally promised to pay out.

### Impact Explanation
If the fee collected from the message sender is silently zero or below cost while the Ethereum-side reward obligation is fixed and non-zero, users of Snowbridge (any XCM sender or the system pallet's own send path) can enqueue governance or user commands to Ethereum while under-paying (or not paying) the "remote" component of the fee that is meant to cover the guaranteed relayer reward. This falls under "public underpriced work that degrades block production or stalls bridge processing" — relayers are still promised the full reward from `pricing_params.rewards.remote`, but the parachain has not collected the value to back it, creating a shortfall that must be absorbed elsewhere or leaving relayers effectively subsidized by the protocol at the sender's expense. Repeated over many messages, this is a public, un-privileged path (no governance, no relayer, no validator, no admin action required) to accrue an accounting mismatch in the fee/reward system.

### Likelihood Explanation
The core rounding bug is deterministic and requires no attacker collusion — it triggers under specific, plausible governance-configured `PricingParameters` (small `rewards.remote`/`fee_per_gas` combined with a `Decimals`/`multiplier`/`exchange_rate` selection that pushes the intermediate value below `10^(18-Decimals)`). It is a pure arithmetic property of the existing code path, exercised on every call to `calculate_fee`, which runs on every outbound message (`send_message_impl.rs:60` and the `calculate_fee` runtime API in `api.rs`). No malicious peer/validator/relayer/admin is needed — only a message sender using the standard, permissionless `SendMessage::validate`/`deliver` path.

### Recommendation
- In `convert_from_ether_decimals`, round the division up (ceiling division) rather than floor, so the fee charged never under-covers the promised reward: e.g. `(value + denom - 1) / denom`, or use `sp_arithmetic`'s existing `multiply_by_rational_with_rounding` / `Rounding::Up` helpers already present in `substrate/primitives/arithmetic`.
- After computing the final native fee, assert/ensure it is sufficient to cover `pricing_params.rewards.remote` converted at the same rate (i.e., re-derive the reward guarantee from the same rounded value actually collected, rather than writing the un-rounded `pricing_params.rewards.remote` independently into the committed message).
- Add an explicit `ensure!(fee.remote > 0, Error::<T>::FeeTooLow)` (or similar) guard so degenerate parameter combinations cannot silently produce a zero remote fee for a non-zero reward commitment.

### Proof of Concept
1. Governance sets `PricingParameters` such that, for a given command's `gas_used_at_most`, `calculate_remote_fee(...)` (line 396-402) yields an ether-wei value `v` where, after `saturating_mul(multiplier).checked_div(&exchange_rate)`, the resulting `value` passed into `convert_from_ether_decimals` is smaller than `10^(18 - T::Decimals)` (e.g. `< 10^8` for a DOT-denominated BridgeHub).
2. Any user calls `SendMessage::validate` (via XCM export or `pallet_system::send`) for a command with this gas profile; `calculate_fee` returns `Fee { remote: 0, .. }` (or a rounded-down value), which is the amount actually withdrawn from the sender.
3. `deliver` enqueues the message; when processed, `do_process_message` still writes `reward: pricing_params.rewards.remote` (the full, ungoverned-by-rounding wei amount) into the committed message that is proven and relayed to the Ethereum Gateway.
4. On Ethereum, the relayer is paid the full `Message.Reward` per the documented settlement formula, while the parachain collected `0` (or less than the equivalent value) from the sender for the remote fee component — demonstrating the value obligation exceeds the value collected due to the rounding-down decimal conversion.

Note: I was not able to fully trace, within the available iterations, the exact runtime `PricingParameters` values configured on production BridgeHub (Polkadot/Kusama) to confirm whether current parameters happen to avoid triggering this rounding-to-zero case in practice; this would need to be verified against live/governance-set `PricingParameters` before treating it as exploitable under current configuration, but the code path itself contains no protective check against it.
