Based on my research, I found a concrete structural analog to the SALT quorum-manipulation bug in how `pallet-conviction-voting`'s "support" ratio is calculated live from a mutable, unprivileged-controllable denominator (`ActiveIssuance`/`TotalIssuance`), rather than being snapshotted when a referendum starts deciding.

### Title
Referendum "support" quorum can be gamed via live, attacker-shrinkable issuance denominator (NIS deactivation) instead of a snapshot - (File: substrate/frame/conviction-voting/src/types.rs)

### Summary
Exactly like the SALT bug — where `requiredQuorumForBallotType()` recomputed the quorum from the live, staker-controlled `totalStaked` value at finalization time instead of a value fixed at proposal creation — `pallet-referenda`'s "is passing" check recomputes the *support* ratio at every service call from `Tally::support()`, whose denominator (`Total::get()`, i.e. `MaxTurnout`) is a live runtime value (`TotalIssuanceOf`/`ActiveIssuanceOf`) rather than a value captured when the referendum entered its deciding period.

### Finding Description
`Tally::support()` is: [1](#0-0) 

`Total::get()` is bound in runtime configs to `TotalIssuanceOf<Balances, ...>` or, on Polkadot/Kusama governance configs, `ActiveIssuanceOf<Balances, ...>`: [2](#0-1) [3](#0-2) [4](#0-3) 

This "support" value is consumed, every time the referendum is serviced (via the scheduler alarm or `nudge_referendum`, both callable without special privilege), by `is_passing`, which compares it live against the track's `min_support` curve to decide whether the referendum should start/continue its Confirmation period and ultimately be scheduled for enactment: [5](#0-4) [6](#0-5) 

`ActiveIssuance` is not immutable public state — `pallet-nis` (`substrate/frame/nis/src/lib.rs`) exposes permissionless calls (`place_bid`, and later maturation/`thaw`) that lock a user's funds into receipts and *deactivate* an equivalent amount of issuance, directly shrinking `ActiveIssuanceOf` used as `MaxTurnout`. Because `support = self.support / Total::get()`, shrinking `Total::get()` after votes have already been cast increases the reported support percentage without adding any actual aye votes — the same mechanic as unstaking xSALT to shrink `totalStaked` in the SALT report.

### Impact Explanation
An attacker (or colluding group) who already holds an "aye" vote position near a track's `min_support` threshold can call the permissionless `pallet_nis::place_bid` extrinsic to deactivate a chunk of issuance, mechanically inflating the referendum's computed support ratio. If this pushes the ratio over the track's `min_support` curve at the current elapsed-time fraction, `is_passing` flips to `true` earlier than the organic vote turnout would justify, starting (or continuing) the Confirmation period and potentially causing a proposal — including calls dispatched with elevated origins per track (Root, Treasurer, WhitelistedCaller, etc.) — to be scheduled for enactment prematurely, i.e. false quorum/support acceptance without commensurate votes. This matches the "forged/mis-bound proof or state acceptance" and "runtime bugs that compromise intended behavior" impact classes.

### Likelihood Explanation
This requires no validator, collator, relayer, or admin — only an ordinary token holder able to submit `place_bid` and having (or coordinating) enough aye-weighted votes near the support boundary. The main uncertainty (which I could not fully verify from available context) is the exact reversibility/cost profile of NIS deactivation — whether a bid can be retracted before entering the queue (no cost) versus only unwound after the receipt matures (locked capital, opportunity cost). This affects how cheaply an attacker can flip support up and later restore issuance, analogous to the SALT staker's "unstake then re-stake for free" trick. Regardless of full reversibility, the underlying invariant break — a public quorum/support check reading a live, externally-movable denominator instead of a value fixed for the referendum's deciding period — is present and directly analogous to the root cause confirmed in the SALT report.

### Recommendation
Snapshot the `MaxTurnout`/active-issuance value used as the support/approval denominator once, when a referendum's `DecidingStatus` begins (or track-tracked at least periodically with anti-manipulation smoothing), and store it in `ReferendumStatus`, rather than calling `Total::get()` live on every `is_passing` evaluation. This removes the ability of any single actor's issuance-affecting extrinsic (NIS bids, burns, etc.) to shift a referendum's quorum requirement mid-flight.

### Proof of Concept
1. Attacker casts an "aye" `conviction_voting::vote` on an ongoing referendum on a track whose current `min_support` curve value is just above the current `tally.support()/Total::get()` ratio.
2. Attacker calls `pallet_nis::Pallet::place_bid` with a large amount, which invokes `T::Currency::deactivate`, reducing `ActiveIssuance` (and thus `Total::get()` for `ActiveIssuanceOf`-configured `MaxTurnout`).
3. On the next scheduler alarm / `nudge_referendum` call, `Referenda::is_passing` recomputes `tally.support(track_id) = Perbill::from_rational(self.support, Total::get())` with the now-smaller `Total::get()`, producing a higher support percentage with no new votes.
4. If this crosses `track.min_support.threshold(elapsed_fraction)`, the referendum enters/continues its Confirmation period earlier than legitimate turnout warrants (`substrate/frame/referenda/src/lib.rs:1184-1222`), potentially leading to premature `Approved` state and scheduled enactment.

	/// Determine whether the given `tally` would result in a referendum passing at `elapsed` blocks
	/// into a total decision `period`, given the two curves for `support_needed` and
	/// `approval_needed`.
	fn is_passing(
		tally: &T::Tally,
		elapsed: BlockNumberFor<T, I>,
		period: BlockNumberFor<T, I>,
		support_needed: &Curve,
		approval_needed: &Curve,
		id: TrackIdOf<T, I>,
	) -> bool {
		let x = Perbill::from_rational(elapsed.min(period), period);
		support_needed.passing(x, tally.support(id)) &&
			approval_needed.passing(x, tally.approval(id))
