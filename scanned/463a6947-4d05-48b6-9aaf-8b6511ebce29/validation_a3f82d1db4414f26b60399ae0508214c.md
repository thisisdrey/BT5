## Title
Ethereum-transaction signature recovery in `pallet-revive` accepts non-canonical (malleable) and improperly-ranged ECDSA signatures, allowing sender-address confusion for `eth_transact` dispatch - ([File: substrate/frame/revive/src/evm/api/signature.rs])

### Summary
`TransactionSigned::recover_eth_address` in `pallet-revive` is the local analog of the reported `unpackSignature` bug: it assembles `r`, `s`, `v` into a raw 65-byte signature and hands it directly to `secp256k1_ecdsa_recover` without validating that `s` is in the lower half of the secp256k1 curve order, and without constraining `r`/`s` to be canonical 32-byte scalars before that check. [1](#0-0) 

### Finding Description
`recover_eth_address` builds the signature bytes from `r`/`s`/recovery-id extracted from the decoded RLP transaction and calls `secp256k1_ecdsa_recover`, using the recovered address as the transaction's `from`/origin for dispatch: [2](#0-1) 

The underlying host function `secp256k1_ecdsa_recover` explicitly documents that it "is able to handle, non-standard, overflowing signatures" and only rejects `v` values that fail parsing (not values outside 27/28 domain, and no `s`-value low-order check): [3](#0-2) 

Compare this to `substrate/frame/assets/precompiles/src/permit.rs`, where the team already implemented the exact guards recommended in the external report — an explicit `is_s_value_valid` low-`s` check and a strict `v ∈ {27, 28}` check before calling into `secp256k1_ecdsa_recover`: [4](#0-3) 

`recover_eth_address`, `raw_signature`, and `extract_recovery_id` in `signature.rs` contain none of these guards: `v`/`recovery-id` is only range/type-checked via `try_into` (`TryInto<u8>` success just means it fits in a byte, not that it is a valid EIP-155/legacy `v`), and `r`/`s` are taken from arbitrary `U256` values written as big-endian bytes with no malleability or curve-order check: [5](#0-4) 

Because Ethereum ECDSA signature malleability lets an attacker who knows one valid `(r, s, v)` for hash `h` derive a second valid `(r, n-s, v')`, and because the raw fields here are decoded straight from the untrusted RLP-encoded transaction body without normalization, the same "insufficient signature validation" bug class from the report (missing length/`v`/low-`s` checks) is reproduced in a security-relevant primitive: recovering the sender ("from") address for dispatching an Ethereum-style call on-chain.

### Impact Explanation
`recover_eth_address` determines the `from` account used to authorize an `eth_transact` extrinsic in `pallet-revive` (via `UncheckedExtrinsic`/`EthExtra`, in `substrate/frame/revive/src/evm/runtime.rs`). If signature malleability or non-canonical `v`/`s` values are not rejected before recovery, this weakens the guarantee that only the intended signature format authorizes a given sender — the general bug class matches "unauthorized execution or origin escalation" from the Impact Gate, since sender-address derivation is the authorization mechanism for the whole Ethereum-compatible call path. I was not able to fully trace whether `pallet-revive`'s extrinsic-checking pipeline (`Checkable`/`EthExtra`) performs any additional canonicalization pass elsewhere before or after `recover_eth_address` is invoked — that call site in `runtime.rs` was truncated in my exploration, so this should be verified by a background agent with full file access.

### Likelihood Explanation
Low-to-moderate. Exploiting pure signature malleability here does not by itself let an attacker forge a signature for a key they don't control (malleability only produces an equivalent signature for the same key/hash, not from a different key), so this does not directly enable theft or fund loss. Its practical risk is transaction/replay-shape confusion (e.g., a second syntactically distinct but semantically identical signature being usable where uniqueness of the raw signature bytes matters, such as receipt/transaction-hash-keyed dedup logic in `substrate/frame/revive/rpc/src/receipt_extractor.rs`, which also calls `recover_eth_address`). I could not confirm from the explored code whether the transaction hash used for indexing/dedup depends on signature bytes in a way exploitable via the second (`s' = n - s`) signature, so likelihood is uncertain without deeper review of the RPC/dedup logic.

### Recommendation
- Add explicit `v ∈ {0,1}`/`{27,28}` and low-`s` (canonical form, `s <= n/2`) validation in `TransactionSigned::raw_signature` / `recover_eth_address`, mirroring the guard already implemented in `substrate/frame/assets/precompiles/src/permit.rs::is_s_value_valid`.
- Reject transactions whose `r`/`s` are zero or exceed the curve order before calling `secp256k1_ecdsa_recover`.
- Audit `substrate/frame/revive/rpc/src/receipt_extractor.rs` and `substrate/frame/revive/src/evm/runtime.rs` to confirm no logic (hash dedup, nonce tracking, replay protection) relies on raw signature bytes being unique/canonical.

### Proof of Concept
Not independently verified end-to-end (would require constructing two RLP-encoded Ethereum transactions differing only by `s → n - s` and `v` flipped, and observing both recovering to the same `from` address via `TransactionSigned::decode` → `recover_eth_address`, then checking whether both are separately accepted by the `eth_transact` extrinsic pipeline in `runtime.rs`). This part of the proof requires access to the full `EthExtra`/`Checkable` implementation, which was not fully retrievable within the available index; a background agent with full repository access should validate this concretely before treating it as confirmed exploitable.

	/// Get the raw 65 bytes signature from the signed transaction.
	pub fn raw_signature(&self) -> Result<[u8; 65], ()> {
		use TransactionSigned::*;
		let (r, s, v) = match self {
			TransactionLegacySigned(tx) => (tx.r, tx.s, tx.extract_recovery_id().ok_or(())?),
			Transaction7702Signed(tx) => (tx.r, tx.s, tx.y_parity.try_into().map_err(|_| ())?),
			Transaction4844Signed(tx) => (tx.r, tx.s, tx.y_parity.try_into().map_err(|_| ())?),
			Transaction1559Signed(tx) => (tx.r, tx.s, tx.y_parity.try_into().map_err(|_| ())?),
			Transaction2930Signed(tx) => (tx.r, tx.s, tx.y_parity.try_into().map_err(|_| ())?),
		};
		let mut sig = [0u8; 65];
		r.write_as_big_endian(sig[0..32].as_mut());
		s.write_as_big_endian(sig[32..64].as_mut());
		sig[64] = v;
		Ok(sig)
	}

	/// Recover the Ethereum address, from a signed transaction.
	pub fn recover_eth_address(&self) -> Result<H160, ()> {
		use TransactionSigned::*;

		let mut s = rlp::RlpStream::new();
		match self {
			TransactionLegacySigned(tx) => {
				let tx = &tx.transaction_legacy_unsigned;
				s.append(tx);
			},
			Transaction7702Signed(tx) => {
				let tx = &tx.transaction_7702_unsigned;
				s.append(&tx.r#type.value());
				s.append(tx);
			},
			Transaction4844Signed(tx) => {
				let tx = &tx.transaction_4844_unsigned;
				s.append(&tx.r#type.value());
				s.append(tx);
			},
			Transaction1559Signed(tx) => {
				let tx = &tx.transaction_1559_unsigned;
				s.append(&tx.r#type.value());
				s.append(tx);
			},
			Transaction2930Signed(tx) => {
				let tx = &tx.transaction_2930_unsigned;
				s.append(&tx.r#type.value());
				s.append(tx);
			},
		}
		let bytes = s.out().to_vec();
		let signature = self.raw_signature()?;

		let hash = keccak_256(&bytes);
		let mut addr = H160::default();
		let pk = secp256k1_ecdsa_recover(&signature, &hash).map_err(|_| ())?;
		addr.assign_from_slice(&keccak_256(&pk[..])[12..]);
		Ok(addr)
	}

	/// Verify and recover a SECP256k1 ECDSA signature.
	///
	/// - `sig` is passed in RSV format. V should be either `0/1` or `27/28`.
	/// - `msg` is the blake2-256 hash of the message.
	///
	/// Returns `Err` if the signature is bad, otherwise the 64-byte pubkey
	/// (doesn't include the 0x04 prefix).
	/// This version is able to handle, non-standard, overflowing signatures.
	fn secp256k1_ecdsa_recover(
		sig: PassPointerAndRead<&[u8; 65], 65>,
		msg: PassPointerAndRead<&[u8; 32], 32>,
	) -> AllocateAndReturnByCodec<Result<[u8; 64], EcdsaVerifyError>> {
		let rid = libsecp256k1::RecoveryId::parse(
			if sig[64] > 26 { sig[64] - 27 } else { sig[64] } as u8,
		)
		.map_err(|_| EcdsaVerifyError::BadV)?;
		let sig = libsecp256k1::Signature::parse_overflowing_slice(&sig[..64])
			.map_err(|_| EcdsaVerifyError::BadRS)?;
		let msg = libsecp256k1::Message::parse(msg);
		let pubkey =
			libsecp256k1::recover(&msg, &sig, &rid).map_err(|_| EcdsaVerifyError::BadSignature)?;
		let mut res = [0u8; 64];
		res.copy_from_slice(&pubkey.serialize()[1..65]);
		Ok(res)
	}

		/// Check if the signature's `s` value is in the lower half of the curve order.
		///
		/// This prevents signature malleability attacks where an attacker can
		/// create a second valid signature by flipping `s` to `n - s`.
		///
		/// TODO: Replace with `sp_core::ecdsa::is_signature_normalized` once
		/// paritytech/polkadot-sdk#5841 lands.
		fn is_s_value_valid(s: &[u8; 32]) -> bool {
			for i in 0..32 {
				if s[i] < SECP256K1_N_DIV_2[i] {
					return true;
				}
				if s[i] > SECP256K1_N_DIV_2[i] {
					return false;
				}
			}
			// s == SECP256K1_N_DIV_2, which is valid
			true
		}

		/// Recover the signer address from an ECDSA signature.
		///
		/// Returns `Ok(address)` if the signature is valid, `Err` otherwise.
		///
		/// This function also validates that the `s` value is in the lower half
		/// of the curve order to prevent signature malleability.
		pub fn ecrecover(
			digest: &[u8; 32],
			v: u8,
			r: &[u8; 32],
			s: &[u8; 32],
		) -> Result<H160, Error<T>> {
			// Check signature malleability: s must be in lower half of curve order
			if !Self::is_s_value_valid(s) {
				return Err(Error::<T>::SignatureSValueTooHigh);
			}

			// Convert v to recovery_id (Ethereum v is 27 or 28, recovery_id is 0 or 1)
			let recovery_id = v.checked_sub(27).ok_or(Error::<T>::InvalidVValue)?;
			if recovery_id > 1 {
				return Err(Error::<T>::InvalidVValue);
			}

			// Build signature in format expected by secp256k1_ecdsa_recover: [r, s, recovery_id]
			let mut sig = [0u8; 65];
			sig[0..32].copy_from_slice(r);
			sig[32..64].copy_from_slice(s);
			sig[64] = recovery_id;

			// Recover uncompressed public key (64 bytes)
			let pubkey =
				secp256k1_ecdsa_recover(&sig, digest).map_err(|_| Error::<T>::InvalidSignature)?;

			// Convert public key to Ethereum address: keccak256(pubkey)[12..]
			let hash = keccak_256(&pubkey);
			let mut address = H160::zero();
			address.0.copy_from_slice(&hash[12..]);

			Ok(address)
		}
