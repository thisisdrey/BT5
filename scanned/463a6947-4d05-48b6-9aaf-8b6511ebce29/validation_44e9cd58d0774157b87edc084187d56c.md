## Title
Unvalidated non-UTF8 asset name/symbol bytes cause permanent revert of the ERC-20 precompile `name()`/`symbol()` interface - (File: `substrate/frame/assets/precompiles/src/lib.rs`)

### Summary
`pallet_assets` stores token `name` and `symbol` as raw `BoundedVec<u8, StringLimit>` and only validates their *length*, never their UTF-8 validity, when they are written via `set_metadata`/`force_set_metadata`. The `pallet-assets` EVM/`pallet_revive` precompile that exposes these assets as ERC-20 contracts (`substrate/frame/assets/precompiles/src/lib.rs`) later tries to decode those same bytes strictly as UTF-8 and reverts if decoding fails. Any asset owner can permanently poison their own asset's `name()`/`symbol()` ERC-20 view calls by writing non-UTF8 bytes, exactly mirroring the Gravity Bridge bug where data accepted without a UTF-8 check on write is later force-decoded as UTF-8 on read and errors out unrecoverably.

### Finding Description
`do_set_metadata` in `substrate/frame/assets/src/functions.rs` (lines 1058-1105) only bounds-checks length:
```rust
let bounded_name: BoundedVec<u8, T::StringLimit> =
    name.clone().try_into().map_err(|_| Error::<T, I>::BadMetadata)?;
let bounded_symbol: BoundedVec<u8, T::StringLimit> =
    symbol.clone().try_into().map_err(|_| Error::<T, I>::BadMetadata)?;
``` [1](#0-0) 

There is no `str::from_utf8` check anywhere in this write path, so `name`/`symbol` can contain arbitrary, non-UTF8 byte sequences and are persisted into `Metadata::<T, I>`.

Separately, `substrate/frame/assets/precompiles/src/lib.rs` implements the ERC-20 `name()` and `symbol()` interface functions for `pallet_assets`-backed tokens exposed through `pallet-revive`. These functions fetch the same stored bytes and *force* a UTF-8 decode, reverting on failure:
```rust
let name = alloc::string::String::from_utf8(metadata.name.to_vec())
    .map_err(|_| Error::Revert(Revert { reason: "Invalid UTF-8 in name".into() }))?;
...
let symbol = alloc::string::String::from_utf8(metadata.symbol.to_vec())
    .map_err(|_| Error::Revert(Revert { reason: "Invalid UTF-8 in symbol".into() }))?;
``` [2](#0-1) 

This is the same broken invariant as the Gravity Bridge H-02 finding: an untrusted-content field is accepted without a validity check at write time, then a downstream component enforces the check at read time and fails permanently, with no recovery path (the corrupted metadata can only be overwritten by the same permissionless `set_metadata` path, but nothing prevents the same actor — or any future write — from reintroducing invalid bytes, and in the meantime every `name()`/`symbol()` call reverts). Once written, there is no on-chain guard preventing or repairing the invalid state; any client, wallet, or other contract calling `name()`/`symbol()` on that asset's ERC-20 façade gets an unconditional revert.

### Impact Explanation
This degrades the public read-only ERC-20 interface (`name`/`symbol`) of any `pallet_assets`-backed token exposed via the precompile, for as long as the metadata contains invalid UTF-8 (i.e., until the owner overwrites it with valid bytes, if they choose to). Any tooling, wallet, DEX router, or smart contract relying on standard ERC-20 `name()`/`symbol()` calls for that specific asset will get a permanent revert, breaking composability and potentially breaking any downstream logic (e.g., UIs, other contracts using `try/catch` incorrectly, or code paths that don't handle the revert) that depends on these view functions succeeding. It matches the "public underpriced work that degrades... processing" and "runtime bugs that compromise intended behavior" categories, though the blast radius is scoped to the affected asset's ERC-20 metadata calls rather than the whole chain.

### Likelihood Explanation
High: `set_metadata` is callable by the asset's own `owner`/`admin`, i.e., an unprivileged party for their own permissionlessly-created asset (no governance or root required), and takes raw `Vec<u8>` for `name`/`symbol` with no UTF-8 validation. Triggering the revert simply requires calling `pallet_assets::set_metadata` (or `force_set_metadata` if permissioned) with a byte sequence like `b"symbo\xC0"` and then invoking `name()`/`symbol()` via the ERC-20 precompile.

### Recommendation
Validate UTF-8 validity of `name` and `symbol` in `do_set_metadata` / `force_set_metadata` (and any other paths setting `AssetMetadata`) at write time, returning `Error::<T, I>::BadMetadata` on invalid UTF-8, so the invariant relied upon by the precompile is enforced where the data is written, not only where it is read. Alternatively, make the precompile's `name()`/`symbol()` implementations non-panicking/non-reverting by falling back to a lossy conversion (`String::from_utf8_lossy`) or hex-encoding invalid bytes, following the same mitigation Althea applied to the original Gravity Bridge bug.

### Proof of Concept
1. Create a `pallet_assets` asset (permissionless, e.g. via `pallet_assets::create`).
2. As the asset owner, call:
```rust
Assets::set_metadata(
    RuntimeOrigin::signed(owner),
    asset_id,
    b"token".to_vec(),
    vec![0x73, 0x79, 0x6d, 0x62, 0x6f, 0xC0], // invalid UTF-8 symbol, mirrors PoC in H-02
    18,
);
```
This succeeds because `do_set_metadata` only checks the `BoundedVec` length bound. [3](#0-2) 

3. Call the ERC-20 precompile's `symbol()` entry point for that asset (e.g. via `pallet_revive` contract call to the asset's precompile address). The call always reverts with `"Invalid UTF-8 in symbol"`: [4](#0-3) 

This revert is permanent for every subsequent caller until the owner overwrites the metadata with valid UTF-8 bytes — an on-chain analog of the Gravity Bridge freeze where non-UTF8 token metadata, accepted at write time, permanently breaks a downstream consumer that strictly requires UTF-8.

	fn name(
		asset_id: <Runtime as Config<Instance>>::AssetId,
		env: &mut impl Ext<T = Runtime>,
	) -> Result<Vec<u8>, Error> {
		env.charge(<Runtime as Config<Instance>>::WeightInfo::get_metadata())?;

		let metadata = pallet_assets::Pallet::<Runtime, Instance>::get_metadata(asset_id)
			.ok_or(Error::Revert(Revert { reason: "Metadata not found".into() }))?;

		let name = alloc::string::String::from_utf8(metadata.name.to_vec())
			.map_err(|_| Error::Revert(Revert { reason: "Invalid UTF-8 in name".into() }))?;

		Ok(IERC20::nameCall::abi_encode_returns(&name))
	}
