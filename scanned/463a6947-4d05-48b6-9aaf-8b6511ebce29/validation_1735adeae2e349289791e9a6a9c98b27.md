### Title
`remove_external_asset` can be permanently blocked by an admin-set `AllDisabled` circuit breaker, trapping the PSM instance with an unremovable external asset - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
`Pallet::remove_external_asset` requires `PsmDebt` to be exactly zero before an external asset can be de-registered from a PSM instance. The only way to drain `PsmDebt` to zero is via `redeem`, but `redeem` is itself gated by the same asset's circuit-breaker level. If the circuit breaker is set to `CircuitBreakerLevel::AllDisabled` (the pallet's own "full emergency halt" level, intended for a hacked/compromised external), redemptions are blocked exactly like minting, so outstanding debt can never be reduced to zero, and `remove_external_asset` can never succeed. This mirrors the Derby `Vault.blacklistProtocol` bug: the emergency/removal action is coupled to a fund-flow precondition that can be prevented by the very hack/pause condition the emergency action exists to handle. [1](#0-0) 

### Finding Description
`remove_external_asset` enforces `ensure!(PsmDebt::<T>::get(&internal_asset, &external_asset).is_zero(), Error::<T>::AssetHasDebt)` before wiping the external's state (`ExternalAssets`, `MintingFee`, `RedemptionFee`, `AssetCeilingWeight`, `PsmDebt`) and decrementing `PsmInfo::external_count`. [2](#0-1) 

The documented offboarding workflow explicitly relies on redemptions draining debt to zero: "Redemptions slowly drain `PsmDebt[internal_asset, asset_id]` ... Once debt reaches zero, call `remove_external_asset`." [3](#0-2) 

However, the circuit breaker's `AllDisabled` level is described as "Full emergency halt of an external," blocking *both* minting and redemption: [4](#0-3) 

`Error::AllSwapsStopped` and `Error::MintingStopped` are the errors returned by `mint`/`redeem` when the circuit breaker forbids the operation, and `Error::AssetHasDebt` is the sole "cannot remove asset" guard. [5](#0-4) 

This is the exact broken-invariant shape as the Derby report: an emergency de-listing operation (`remove_external_asset`, analogous to `blacklistProtocol`) is gated on completing a fund-movement step (draining debt via `redeem`, analogous to `withdrawFromProtocol`) that the emergency condition itself (a hacked/compromised external asset, analogous to a hacked/paused protocol) is precisely what motivates disabling in the first place via `AllDisabled`. Once `AllDisabled` is set and any nonzero debt remains, there is no code path that can ever bring `PsmDebt` back to zero — `redeem` is blocked, and there is no admin override or forced-write to zero the debt counter outside of `remove_external_asset` itself. The external asset (and its `AssetCeilingWeight`, `MintingFee`, `RedemptionFee` entries) becomes permanently stuck in `ExternalAssets` storage, and the PSM instance itself can never be fully torn down either, since the instance-removal path requires `Error::PsmHasApprovedExternals` to be cleared first (the PSM "still has approved externals; remove them before removing the PSM"). [6](#0-5) 

### Impact Explanation
This produces a permanent state lock analogous to the required-impact category "permanent user-fund or bridge-state lock": governance/emergency admins lose the ability to remove a compromised or misbehaving external asset from a PSM instance once its debt cannot be redeemed to zero (e.g., because the external asset itself is depegged, its `Fungibles` implementation is frozen/paused externally, or the admin has intentionally set `AllDisabled` to stop further exposure). The pallet's own emergency mechanism (the circuit breaker) directly conflicts with its own cleanup mechanism (debt-must-be-zero to remove), so using the safety feature as designed disables the only path to safely retire the asset. This also blocks `remove_psm`/instance teardown since `PsmHasApprovedExternals` remains unsatisfied.

### Likelihood Explanation
This is deterministic, not probabilistic: any operator who follows the documented "full emergency halt" (`AllDisabled`) on an external asset that still carries outstanding debt permanently forfeits the ability to call `remove_external_asset` for that asset, since `redeem` — the only debt-reducing entrypoint — is blocked by the same status flag. No external attacker action, governance abuse, or malicious actor is needed; it is a direct consequence of normal use of the pallet's documented emergency controls interacting with its removal precondition.

### Recommendation
Decouple the emergency-halt action from the removal precondition:
- Allow `remove_external_asset` (or a dedicated force-removal call restricted to the `full_admin`) to proceed even with nonzero debt when the asset is in `AllDisabled` state, writing off/transferring the outstanding debt accounting explicitly (mirroring the Derby recommendation of a `needToWithdraw`-style flag), or
- Carve out an exception in `redeem`'s circuit-breaker check that still permits redemption (fund exit) even when `AllDisabled`, since blocking exits during an emergency is the opposite of what "safely exit users" during an incident requires, or
- Provide a governance-only "force zero debt" / "write off debt" call so that `remove_external_asset`'s precondition can be satisfied without requiring a live, unblocked `redeem` path.

### Proof of Concept
1. Instance is created via `create_psm` with an internal asset and an approved external asset that has nonzero `PsmDebt` (e.g. via `mint`).
2. Admin discovers the external asset is compromised (depegged/frozen/hacked) and calls `set_asset_status(internal_asset, external_asset, CircuitBreakerLevel::AllDisabled)` to halt exposure, per the documented "Full emergency halt of an external" use case. [7](#0-6) 
3. Admin (or anyone) attempts `redeem(internal_asset, external_asset, amount, ..)` to drain the outstanding debt — this now fails with `Error::AllSwapsStopped`/`MintingStopped` gate, because `AllDisabled` blocks all swaps, matching the test pattern where debt must be drained via `redeem` before removal is possible. [8](#0-7) 
4. Admin calls `remove_external_asset(internal_asset, external_asset)` — this reverts with `Error::AssetHasDebt` because `PsmDebt` is still nonzero and can never be reduced while `AllDisabled` remains in effect. [9](#0-8) 
5. The external asset remains permanently registered in `ExternalAssets`, and the PSM instance cannot be torn down (`Error::PsmHasApprovedExternals`), reproducing the exact "hacked/paused protocol can't be set to blacklist" failure mode from the Derby report.

		#[pallet::call_index(10)]
		#[pallet::weight(T::WeightInfo::remove_external_asset())]
		pub fn remove_external_asset(
			origin: OriginFor<T>,
			internal_asset: T::AssetId,
			external_asset: T::AssetId,
		) -> DispatchResult {
			Self::ensure_psm_admin(origin, &internal_asset, |l| l.can_manage_assets())?;
			let mut info = Psm::<T>::get(&internal_asset).ok_or(Error::<T>::PsmNotFound)?;
			ensure!(
				ExternalAssets::<T>::contains_key(&internal_asset, &external_asset),
				Error::<T>::AssetNotApproved
			);
			ensure!(
				PsmDebt::<T>::get(&internal_asset, &external_asset).is_zero(),
				Error::<T>::AssetHasDebt
			);
			ExternalAssets::<T>::remove(&internal_asset, &external_asset);
			MintingFee::<T>::remove(&internal_asset, &external_asset);
			RedemptionFee::<T>::remove(&internal_asset, &external_asset);
			AssetCeilingWeight::<T>::remove(&internal_asset, &external_asset);
			PsmDebt::<T>::remove(&internal_asset, &external_asset);
			info.external_count = info.external_count.saturating_sub(1);
			Psm::<T>::insert(&internal_asset, info);

			Self::deposit_event(Event::ExternalAssetRemoved { internal_asset, external_asset });
			Ok(())
		}

```markdown
## Circuit Breaker

Each approved external on each instance has an independent circuit breaker
with three levels:

| Level             | Minting | Redemption | Use Case                          |
| ----------------- | ------- | ---------- | --------------------------------- |
| `AllEnabled`      | Allowed | Allowed    | Normal operation                  |
| `MintingDisabled` | Blocked | Allowed    | Drain debt from a problematic external |
| `AllDisabled`     | Blocked | Blocked    | Full emergency halt of an external |

`set_asset_status` is callable at both the `Full` (`full_admin`) and
`Emergency` (`emergency_admin`) levels.
```

```markdown
### Asset Offboarding Workflow

For an external `asset_id` on instance `internal_asset`:

1. Set the external's ceiling weight to `0%` (or use `set_asset_status(.., MintingDisabled)`):
   either pauses new minting while still allowing redemptions
2. Redemptions slowly drain `PsmDebt[internal_asset, asset_id]`
3. Once debt reaches zero, call `remove_external_asset(internal_asset, asset_id)`

Lowering a ceiling weight (or `max_debt`) below outstanding debt is allowed: the ceiling is a
mint-time throttle, so the external simply cannot be minted until redemptions bring its debt
back under the new ceiling.
```
