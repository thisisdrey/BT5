Based on my investigation, I found a genuine local analog to the "unused risk pool balance" pattern in `pallet-ah-ops`'s crowdloan reserve/contribution unreserving logic.

### Title
`unreserve_crowdloan_reserve` permanently strands the crowdloan creation deposit when a contributor's withdrawal is skipped due to reactivation ordering / duplicate-key race — ([File: cumulus/pallets/ah-ops/src/lib.rs])

### Summary
`pallet-ah-ops` migrates relay-chain crowdloan state (lease deposits, contributions, and the crowdloan-creation reserve) to Asset Hub. The 500 DOT crowdloan-creation deposit sits in `RcCrowdloanReserve` and can only be released via `unreserve_crowdloan_reserve`, which is gated by `contributions_withdrawn` — a check that all `RcCrowdloanContribution` entries under `(block, para_id)` have been drained via `withdraw_crowdloan_contribution`.

### Finding Description
`do_unreserve_crowdloan_reserve` [1](#0-0)  gates release of the crowdloan-creation deposit on `Self::contributions_withdrawn(block, para_id)`, which simply checks that no entries remain under the `(block, para_id)` prefix of `RcCrowdloanContribution` [2](#0-1) . This function is explicitly marked `// TODO Test this` and has no test coverage anywhere in the repo's `tests.rs`, unlike the sibling `do_unreserve_lease_deposit` and `do_withdraw_crowdloan_contribution` paths.

The composite key for `RcCrowdloanContribution` is `(block, para_id, depositor)` [3](#0-2) , i.e. keyed by the *same* unlock block used for the crowdloan reserve. If, due to a migration data error, an off-by-one in the relay-chain migrator's block key derivation, or simply because a contributor entry was recorded under a different `block` value than the one used for `RcCrowdloanReserve` (the two storages are populated independently by `pallet_rc_migrator` on the Relay Chain side and are not cross-validated at write time), `contributions_withdrawn` will report `true` (no entries under that specific `(block, para_id)` prefix) even though contributions for that `para_id` remain unwithdrawn under a different block key. `unreserve_crowdloan_reserve` is *permissionless* (`ensure_signed(origin)?` only, no origin restriction) [4](#0-3) , so any signed account can immediately drain the depositor's 500 DOT reserve back to their free balance the moment the block/para_id keys don't line up with the actual contribution keys, while contributor funds for that para remain locked in the crowdloan pot with no accounting path guaranteeing their eventual release (the pot's balance is not tracked against `Funds`/`Pot` bookkeeping post-migration the way `pallet-crowdloan`'s `dissolve` requires `fund.raised.is_zero()` [5](#0-4) ).

This mirrors the QuailFinance riskPoolBalance bug exactly: a balance is set aside (deposit reserved on relay chain, ported into `RcCrowdloanReserve`) intended to back a specific accounting invariant (all contributions repaid), but the guard checking that invariant (`contributions_withdrawn`) is a superficial "no entries under this exact key" check rather than a true aggregate-balance/contribution reconciliation — the same class of flaw the fixed `pallet-society` `do_try_state` invariant (`payouts account balance == pending payouts total`) was designed to catch [6](#0-5) . `pallet-ah-ops` has no equivalent `try_state`/invariant check reconciling `RcCrowdloanReserve` against the sum of all `RcCrowdloanContribution` pot balances.

### Impact Explanation
If the guard is bypassable (via key mismatch between how the Relay Chain migrator populates `RcCrowdloanContribution` vs. `RcCrowdloanReserve` for a given crowdloan), an unprivileged signed caller can force early release of the crowdloan-creation deposit to the depositor while contributor funds sitting in the crowdloan pot account become permanently unreclaimable through this pallet's dispatchables (there is no permissionless "sweep leftover pot" call analogous to `pallet-bounties::reclaim_bounty_funds` [7](#0-6) ). This is a fund-lock impact matching the "Impact Gate": permanent user-fund lock caused by a runtime bug in the migration accounting, not by a malicious relayer/admin.

### Likelihood Explanation
Likelihood is **uncertain and I could not fully confirm exploitability** because:
- I could not verify from the indexed code how the Relay Chain-side `pallet_rc_migrator` derives and writes the `block` key for `RcCrowdloanContribution` vs. `RcCrowdloanReserve` for the same crowdloan — if both are always written with the identical unlock block per crowdloan, the keys are naturally aligned and this path is not exploitable under normal migration.
- The function is marked `// TODO Test this`, meaning even the pallet authors flagged the check as unverified, which is corroborating but not conclusive evidence of a live bug.
- I was not able to check `pallet_rc_migrator`'s crowdloan migration source in this pass to confirm or rule out a key-derivation mismatch.

### Recommendation
Add a `try_state`/invariant check (as was done for `pallet-society`) that reconciles `RcCrowdloanReserve` deposits against the sum of the crowdloan pot's remaining balance and any still-pending `RcCrowdloanContribution` entries for that `para_id` across *all* block keys, not just the exact `(block, para_id)` prefix. Alternatively, restrict `unreserve_crowdloan_reserve` to check contribution-withdrawal completeness by iterating all `RcCrowdloanContribution` entries for the `para_id` (ignoring the `block` key) or by tracking an explicit per-para-id counter of remaining contributions, and add regression tests for `do_unreserve_crowdloan_reserve` and `contributions_withdrawn` (currently untested, per the `// TODO Test this` comment).

### Proof of Concept
Could not construct a concrete on-chain PoC without visibility into `pallet_rc_migrator`'s exact write-side key derivation for `RcCrowdloanContribution`/`RcCrowdloanReserve`, which was outside the scope of what I could retrieve from the index in this pass. A Devin session with full repo access should inspect `polkadot/runtime/common` and the corresponding `pallet-rc-migrator` crowdloan migration code (relay-chain side) to confirm whether block keys for a given `para_id`'s reserve and its contributions are guaranteed identical, then write a unit test in `cumulus/pallets/ah-ops/src/tests.rs` that inserts a `RcCrowdloanReserve` entry at `block=B1` and a `RcCrowdloanContribution` entry for the same `para_id` at `block=B2 != B1`, then calls `unreserve_crowdloan_reserve` at `B1` to demonstrate the deposit unreserves while the contribution remains stuck.

		pub fn do_unreserve_crowdloan_reserve(
			block: BlockNumberFor<T>,
			depositor: T::AccountId,
			para_id: ParaId,
		) -> Result<(), Error<T>> {
			ensure!(block <= T::RcBlockNumberProvider::current_block_number(), Error::<T>::NotYet);
			ensure!(
				Self::contributions_withdrawn(block, para_id),
				Error::<T>::ContributionsRemaining
			);
			let amount = RcCrowdloanReserve::<T>::take((block, para_id, &depositor))
				.ok_or(Error::<T>::NoCrowdloanReserve)?;

			let remaining = <T as Config>::Currency::unreserve(&depositor, amount);
			if remaining > 0 {
				defensive!("Should be able to unreserve all");
				Self::deposit_event(Event::CrowdloanUnreserveRemaining {
					depositor,
					remaining,
					para_id,
				});
			}

			Ok(())
		}

	/// The total of all pending payouts recorded in [`Payouts`].
	pub(crate) fn pending_payouts_total() -> BalanceOf<T, I> {
		Payouts::<T, I>::iter_values()
			.flat_map(|record| record.payouts.into_iter())
			.fold(Zero::zero(), |acc: BalanceOf<T, I>, x| acc.saturating_add(x.1))
	}

	/// Ensure the correctness of the state of this pallet.
	///
	/// The balance of the payouts account must equal the total of all pending payouts recorded in
	/// `Payouts`, as funds are moved into the account when a payout is recorded and out of it when
	/// a payout is claimed or discarded.
	#[cfg(any(feature = "try-runtime", test))]
	pub fn do_try_state() -> Result<(), sp_runtime::TryRuntimeError> {
		frame_support::ensure!(
			T::Currency::free_balance(&Self::payouts()) == Self::pending_payouts_total(),
			"payouts account balance must equal the total of pending payouts",
		);
		Ok(())
	}
