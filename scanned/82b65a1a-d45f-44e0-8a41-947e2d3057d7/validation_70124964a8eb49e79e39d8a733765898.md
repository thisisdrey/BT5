The `general staker pot` used by `pallet-staking-async`'s non-minting DAP reward path is a plain, unprotected `AccountId` (derived by `T::RewardPots::pot_account(RewardPot::General(...))`), and `snapshot_era_rewards()` blindly transfers whatever `reducible_balance` sits in that account into the era pot at era-end, exactly the "trust the current balance instead of tracking accrual" pattern that broke `mintOpenInterestDebt()`.

### Title
Unprotected general reward pot balance is snapshotted as era reward, allowing balance injection/drain to corrupt `ErasValidatorReward` payouts - (File: substrate/frame/staking-async/src/reward.rs)

### Summary
`EraRewardManager::snapshot_era_rewards` (analogous to Tapioca's `mintOpenInterestDebt`) computes the era's staker reward by reading the *current* free balance of the general reward pot account, rather than a value that is incrementally tracked and reconciled against expected drips. Because the general pot is an ordinary `AccountId` (not gated behind any origin check on `transfer`/`transfer_keep_alive`), any account can move balance into or out of it before the era boundary, corrupting the snapshotted `ErasValidatorReward`/`ErasValidatorIncentiveBudget` values used to pay all stakers for that era.

### Finding Description
`pallet-staking-async` supports a "non-minting" reward mode (`DisableMinting = true`) where `pallet-dap` continuously drips inflation into the **general** reward pots via `mint_and_distribute` [1](#0-0) . At era boundary, `end_era_dap` calls `EraRewardManager::snapshot_era_rewards(era)` [2](#0-1) .

`snapshot_era_rewards` does not read any pallet-tracked "accrued reward" counter. Instead it directly queries the *live* `reducible_balance` of the general pot accounts and transfers whatever is currently sitting there into the era-specific pot: [3](#0-2) 

The general pot accounts (`RewardPot::General(RewardKind::StakerRewards)` / `RewardPot::General(RewardKind::ValidatorSelfStake)`) are derived, ordinary `AccountId`s obtained from `T::RewardPots::pot_account(...)`. Nothing in the balances pallet prevents an arbitrary signed account from calling `Balances::transfer_keep_alive` (or any other fund-moving extrinsic) to that address — deposits into an `AccountId` are permissionless by design in Substrate. This is the same root cause as the Tapioca bug: the "reward to be paid" is derived from a live, externally-influenceable value (`usdoToken.totalSupply()` there, `reducible_balance(general_pot)` here) instead of an incrementally-tracked internal ledger that only advances through the pallet's own accounting path.

Existing guards do not stop this path:
- `snapshot_era_rewards` has no invariant check comparing the observed balance against an expected drip total; it accepts whatever value is present verbatim.
- There is no `ensure_signed`/origin gate on deposits to the pot account — funds transfer to any `AccountId` is a normal, permissionless balances operation.
- `do_try_state`/try-runtime checks elsewhere in the codebase (e.g. `pallet-psm`'s `do_try_state`, `pallet-assets`' `do_try_state`) exist for other pallets but there is no equivalent invariant asserted for `RewardPot::General` balances vs. expected DAP drip totals in `staking-async`.

### Impact Explanation
Because `ErasValidatorReward`/`ErasValidatorIncentiveBudget` (the values later divided pro-rata among all validators/nominators for an era via `do_payout_stakers_by_page`) are set directly from this unguarded snapshot [4](#0-3) , an attacker can:
- Inflate the era's declared reward by depositing extra tokens into the general pot right before the era rotation, causing `payout_stakers` to distribute more than DAP actually issued for that period (analogous to the "bridge-in inflates supply, distribution miscalculates" branch of the referenced report) — degrading intended tokenomics/inflation guarantees, a runtime-behavior-compromising bug in scope.
- Conversely, an attacker (or bug elsewhere funneling funds out via a permissioned withdrawal path before snapshot) can drain the pot immediately before the snapshot, forcing `snapshot_era_rewards` to record a reward far below what DAP actually dripped, causing genuine stakers to receive less reward than earned for that era — a permanent, unrecoverable value loss for the affected era's stakers since the reward figure is fixed once written to `ErasValidatorReward`.

This directly maps to the "Reward payouts... must conserve value and settle exactly once to the rightful beneficiary and amount" pivot in scope, since the snapshotted value used for exact-once settlement can be desynchronized from the actual DAP-issued amount by anyone able to move balance into/out of a public account.

### Likelihood Explanation
Likelihood is constrained by economics rather than access control: moving funds into the general pot before era rotation requires the attacker to actually spend/donate real tokens (raising the payout for everyone, not just the attacker, unless the attacker is also a large staker who recoups a share). It is nonetheless a fully unprivileged, no-special-condition action (a plain balance transfer to a well-known derived account, timed before era-end), requiring no malicious validator/relayer/governance role — squarely within the allowed threat model. The more severe direction (draining the pot before snapshot to shortchange stakers) would require some other permissioned/legitimate withdrawal path from that same account; if none exists in the current runtime wiring, only the inflate-and-reduce-share-precision griefing vector is exploitable today, which is still a runtime-behavior-compromising accounting bug.

### Recommendation
Do not derive `ErasValidatorReward` from the live balance of a public, unguarded pot account. Instead:
- Have `pallet-dap`'s `mint_and_distribute` increment an explicit, pallet-private storage counter (e.g. `PendingGeneralReward: BalanceOf<T>`) each drip, and have `snapshot_era_rewards` consume/reset that counter rather than reading `reducible_balance`.
- If the balance-based snapshot approach must be kept, assert (and hard-fail, not just log) that `observed_balance == expected_drip_total_since_last_snapshot` before writing `ErasValidatorReward`, and add a `do_try_state` invariant enforcing this, mirroring the `pallet-psm` `do_try_state` pattern that reconciles `PsmDebt` against the derived reserve/backing value.

### Proof of Concept
1. Deploy a runtime with `pallet-staking-async` configured with `DisableMinting = true` and `pallet-dap` as the funding source, as done in the `stable2606` era-reward migration (`pr_11616`, `pr_11527`).
2. Note the general staker pot address via `RewardPots::pot_account(RewardPot::General(RewardKind::StakerRewards))` (publicly derivable, e.g. as computed in tests: `SequentialTest::pot_account(RewardPot::General(RewardKind::StakerRewards))` [5](#0-4) ).
3. Shortly before the era boundary (era rotation is deterministic/observable on-chain), submit `Balances::transfer_keep_alive(general_staker_pot, X)` from any unprivileged account, injecting `X` extra tokens.
4. When `end_era_dap` fires, `snapshot_era_rewards` reads `reducible_balance(general_staker_pot)`, which now includes the attacker's injected `X`, and transfers the whole amount into the era pot, and `ErasValidatorReward::<T>::get(era)` is set to (legitimate DAP drip + `X`) as confirmed by the direct balance-read logic [6](#0-5) .
5. Subsequent `payout_stakers`/`payout_stakers_by_page` calls distribute this inflated total pro-rata to all validators/nominators for that era, permanently baking the injected amount into recorded payouts, deviating from the intended `IssuanceCurve`-governed inflation schedule.

							Self::deactivate_buffer_funds(amount);
						}
					}

	pub(crate) fn snapshot_era_rewards(era: EraIndex) -> EraRewardAllocation<BalanceOf<T>> {
		let staker_era_pot = Self::create(era, RewardKind::StakerRewards);
		let incentive_era_pot = Self::create(era, RewardKind::ValidatorSelfStake);

		let general_staker_pot =
			T::RewardPots::pot_account(RewardPot::General(RewardKind::StakerRewards));
		let general_incentive_pot =
			T::RewardPots::pot_account(RewardPot::General(RewardKind::ValidatorSelfStake));

		// Leave ED in the general pots to keep them alive.
		let staker_balance = T::Currency::reducible_balance(
			&general_staker_pot,
			Preservation::Preserve,
			Fortitude::Polite,
		);
		let incentive_balance = T::Currency::reducible_balance(
			&general_incentive_pot,
			Preservation::Preserve,
			Fortitude::Polite,
		);

		let actual_staker = if !staker_balance.is_zero() {
			match T::Currency::transfer(
				&general_staker_pot,
				&staker_era_pot,
				staker_balance,
				Preservation::Preserve,
			) {
				Ok(_) => staker_balance,
				Err(e) => {
					log!(error, "Era {:?}: staker reward transfer failed: {:?}", era, e);
					defensive!("Failed to transfer staker rewards to era pot");
					Zero::zero()
				},
			}
		} else {
			Zero::zero()
		};
