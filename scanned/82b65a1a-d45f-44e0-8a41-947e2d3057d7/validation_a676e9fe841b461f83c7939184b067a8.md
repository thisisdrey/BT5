### Title
Fee charged to user at `validate()` time is desynchronized from `max_fee_per_gas`/`reward` committed to the relayer at `do_process_message()` time - ([File: bridges/snowbridge/pallets/outbound-queue/src/send_message_impl.rs])

### Summary
Snowbridge's `outbound-queue` pallet computes the delivery fee owed by the user (`Fee::total()`) at message *validation* time using the current `PricingParameters` (exchange rate, `fee_per_gas`, reward, multiplier). This fee is withdrawn from the user synchronously via XCM in the same call. However, the actual `max_fee_per_gas` and `reward` values embedded in the `CommittedMessage` that the relayer will later claim on Ethereum are computed a *second time*, independently, when the message is later dequeued and processed by `do_process_message`. Because message queue processing is decoupled in time from `validate()`/`deliver()`, and `PricingParameters` is a mutable, freely-updatable storage value (via `set_pricing_parameters`), these two reads can diverge, producing a fee actually collected from the user that no longer matches the fee promised on-chain to the relayer — the exact "stale price at charge-time vs. real price at settlement-time" defect described in the external report.

### Finding Description
The fee the user pays is fixed at `validate()`: [1](#0-0) 

`calculate_fee` there reads `T::PricingParameters::get()` once, and the resulting `Fee` is turned into an `Asset` and withdrawn from the user by the exporter in the same XCM execution: [2](#0-1) 

The message is then merely enqueued (`T::MessageQueue::enqueue_message`) — it is not processed atomically: [3](#0-2) 

Later, when the `MessageQueue` pallet actually services the queued message (which may be a later block, subject to weight availability and queue backlog), `do_process_message` re-reads `PricingParameters` **again**, independently, and bakes the *current* `fee_per_gas` and `reward` into the `CommittedMessage` that is Merkle-committed and eventually consumed by the Ethereum gateway contract to pay the relayer: [4](#0-3) 

`PricingParameters` is not a value locked in at enqueue time; it is a single global storage item that can be updated by `set_pricing_parameters`. The pallet's own documentation acknowledges parameters are intended to be updated periodically ("every few weeks") and that a multiplier is meant to buffer volatility, but this buffer is applied only once, at the time of `validate()`, against the parameters current *then* — it does nothing to reconcile with the parameters read again at `do_process_message()` time: [5](#0-4) 

This is structurally identical to the reported bug class: a fee is locked in and collected based on a "price" (gas price / `fee_per_gas`) that is valid at submission time, but the party actually being compensated (the relayer, analogous to the validator in the report) is paid according to a price re-derived at a later, unsynchronized point in time. If `fee_per_gas`/`reward`/`exchange_rate` increases between enqueue and processing, the amount the user paid (computed with the old, lower values) is insufficient to cover the `reward + max_fee_per_gas * max_dispatch_gas` actually promised in the committed message, exactly mirroring Alice's "validators refuse to submit because gas got more expensive" scenario — except here the mismatch is baked directly into the message committed on-chain for the relayer to claim, rather than merely being an off-chain refusal. If parameters instead decrease, the user is systematically overcharged relative to what is committed, with no reimbursement path, mirroring the report's recommendation that was never implemented (no escrow-and-refund mechanism exists in this code).

### Impact Explanation
This breaks the "fee charged == fee promised at settlement" invariant that must hold for a bridge fee/reward system. Underpayment relative to the committed message can cause a relayer to be paid less than what off-chain economics require to profitably relay the message, degrading or stalling delivery of already-committed, already-charged Snowbridge messages — a public underpriced-work / stalled-bridge-processing condition. Overpayment is a straightforward, uncompensated fund loss for the user with no refund mechanism, since the whole fee (`fee.total()`) is deducted unconditionally at validate-time. Both directions are triggered purely by the ordinary passage of time between enqueue and processing plus routine, non-malicious `PricingParameters` updates — no malicious governance, relayer, or validator action is required.

### Likelihood Explanation
Likelihood is Medium: it requires that `PricingParameters` change (via the documented, expected `set_pricing_parameters` maintenance flow) or that queue backlog grows large enough that appreciable time passes between `validate()`/`deliver()` and the message actually being drained by `do_process_message`. Both conditions are normal, expected operational occurrences for this pallet, not adversarial edge cases.

### Recommendation
Snapshot the `PricingParameters` used to compute the user-facing fee into the `QueuedMessage`/`Ticket` at `validate()` time, and reuse that exact snapshot (rather than re-reading current storage) inside `do_process_message` when constructing `max_fee_per_gas` and `reward` for the `CommittedMessage`. This guarantees the amount collected from the user and the amount promised to the relayer are always derived from the same price point, closing the TOCTOU-style gap.

### Proof of Concept
1. User calls into AH/XCM which routes through `EthereumBlobExporter::validate`, which calls `OutboundQueue::validate` → `Pallet::calculate_fee` using current `PricingParameters` P1 (e.g. `fee_per_gas = 20 gwei`). The exporter withdraws `fee.total()` computed from P1 from the user's account in the same XCM execution.
2. The message is `deliver()`ed and merely `enqueue_message`d into `T::MessageQueue`; it is not processed in the same block if the queue is backlogged or over the per-block message weight limit (`MaxMessagesPerBlock`/`WeightMeter`).
3. Governance calls `set_pricing_parameters` (a normal, expected periodic operational action per the pallet docs) to update `fee_per_gas` to P2 (e.g. `40 gwei`) before the message is processed.
4. When `do_process_message` finally runs for the still-queued message, it reads `T::PricingParameters::get()` again, now returning P2, and bakes `max_fee_per_gas`/`reward` derived from P2 into the `CommittedMessage`.
5. Result: the amount debited from the user in step 1 (based on P1) no longer matches the amount promised to the relayer in the committed, Merkle-proven message from step 4 (based on P2) — the relayer is under- or over-compensated relative to what the user actually paid, with no reconciliation or refund mechanism anywhere in the pallet.

//! # Fees
//!
//! An upfront fee must be paid for delivering a message. This fee covers several
//! components:
//! 1. The weight of processing the message locally
//! 2. The gas refund paid out to relayers for message submission
//! 3. An additional reward paid out to relayers for message submission
//!
//! Messages are weighed to determine the maximum amount of gas they could
//! consume on Ethereum. Using this upper bound, a final fee can be calculated.
//!
//! The fee calculation also requires the following parameters:
//! * Average ETH/DOT exchange rate over some period
//! * Max fee per unit of gas that bridge is willing to refund relayers for
//!
//! By design, it is expected that governance should manually update these
//! parameters every few weeks using the `set_pricing_parameters` extrinsic in the
//! system pallet.
//!
//! This is an interim measure. Once ETH/DOT liquidity pools are available in the Polkadot network,
//! we'll use them as a source of pricing info, subject to certain safeguards.
//!
//! ## Fee Computation Function
//!
//! ```text
//! LocalFee(Message) = WeightToFee(ProcessMessageWeight(Message))
//! RemoteFee(Message) = MaxGasRequired(Message) * Params.MaxFeePerGas + Params.Reward
//! RemoteFeeAdjusted(Message) = Params.Multiplier * (RemoteFee(Message) / Params.Ratio("ETH/DOT"))
//! Fee(Message) = LocalFee(Message) + RemoteFeeAdjusted(Message)
//! ```
//!
//! By design, the computed fee includes a safety factor (the `Multiplier`) to cover
