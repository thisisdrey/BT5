### Title
`ERC20Transactor` credits/settles a fixed XCM amount without verifying the actual ERC20 balance delta, breaking accounting for non-standard (fee-on-transfer / falsely-successful) ERC20 tokens - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor`, used as the XCM `TransactAsset` implementation for ERC20-backed assets on Asset Hub (wired in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`), moves value by calling the Solidity `IERC20.transfer` function on an arbitrary registered ERC20 contract and only checks the boolean `bool` return value / revert status. It never compares the recipient's pre- and post-call balance to confirm that the *actual* amount transferred equals the requested `amount`. This is exactly the invariant broken in the referenced report: relying on a boolean success flag from `transfer`/`transferFrom` instead of measuring the real balance delta.

### Finding Description
`withdraw_asset_with_surplus` (lines 150-216) and `deposit_asset_with_surplus` (lines 225-306) both:
1. Build an `IERC20::transferCall { to, value: amount }` and dispatch it via `pallet_revive::Pallet::<T>::bare_call`.
2. Only inspect whether the call reverted and whether the decoded boolean return is `true`.
3. On success, unconditionally treat the *full requested `amount`* as moved: [1](#0-0) 
for the withdraw path, and [2](#0-1) 
for the deposit path.

No pre/post `balanceOf` check is performed anywhere in this file, unlike the checked-transfer pattern already used elsewhere in the codebase, e.g. `substrate/frame/asset-conversion/ops/src/lib.rs` which explicitly asserts the returned actual transferred amount equals the requested balance: [3](#0-2) 

Consequently, for any legitimately-registered ERC20 token that:
- returns `true` from `transfer` without moving the full amount (non-reverting failure/partial-success semantics), or
- implements a fee-on-transfer / deflationary / rebasing mechanism, so the checking account (`TransfersCheckingAccount`) actually receives `amount - fee`,

the pallet's XCM holding register (`AssetsInHolding` populated via `Erc20Credit(amount)`, lines 197-201) is credited with more units of the asset than the checking account actually possesses. This over-crediting silently accumulates because `withdraw_asset_with_surplus` never reconciles it against the checking account's real on-chain ERC20 balance.

The direct downstream effect is on `deposit_asset_with_surplus`: it later attempts to pay out from `TransfersCheckingAccount` an amount that was never fully backed. Eventually a legitimate deposit for some later user fails (reverts) because the checking account's true ERC20 balance is insufficient — the same "last user to call unstake gets reverted" failure mode described in the external report, but here it manifests as XCM message execution failure / stuck cross-chain transfers instead of a staking `unstake` revert.

### Impact Explanation
This breaks the core value-conservation invariant for asset transfers ("Balances, assets ... must conserve value and settle exactly once to the rightful beneficiary and amount"). Over time, using a fee-on-transfer or non-standard-return ERC20 as a registered XCM asset causes:
- Under-collateralization of the `TransfersCheckingAccount`, i.e., the pallet believes it holds more ERC20 balance than it actually does.
- Denial of service for legitimate deposits/withdrawals once the discrepancy exceeds the checking account's real balance (reverted XCM execution, stuck funds, or `AssetsTrapped` events).
- Because the credited surplus is used as spendable XCM holding within the same message, it can also enable value to be moved/deposited elsewhere in excess of what was ever actually backed by the underlying ERC20 contract, before the shortfall surfaces on a subsequent unrelated transfer.

### Likelihood Explanation
This does not require a malicious peer, validator, relayer, or governance abuse — it only requires that governance registers (via the `Matcher: MatchesFungibles<H160, u128>` configuration) any ERC20 contract that is not a "vanilla" OpenZeppelin-style token (fee-on-transfer, deflationary, or non-reverting-false-return tokens are common in the wild). Any ordinary unprivileged user submitting a normal `withdraw`/`deposit` XCM instruction against such a token then triggers the accounting drift; no special crafted message or attacker capability is needed beyond using the affected asset.

### Recommendation
- After each successful `transfer` call, read back the actual balance delta of the sender/recipient (or use `balanceOf` before and after the transfer) and use that measured delta — not the requested `amount` — when constructing `Erc20Credit` in `withdraw_asset_with_surplus`, and when reporting success in `deposit_asset_with_surplus`.
- If the observed delta is less than `amount`, return `XcmError::FailedToTransactAsset` (or credit only the actual delta) instead of assuming full success on `true`.
- Consider maintaining an explicit list of ERC20 contracts vetted as standard-compliant (no fee-on-transfer, correct revert-on-failure semantics) before permitting registration via the `Matcher`.

### Proof of Concept
1. Governance/Matcher registers ERC20 contract `T` implementing a 1% fee-on-transfer (a common real-world token behavior), as backing for an XCM-transactable asset on Asset Hub.
2. User Alice holds 1000 `T` and initiates an XCM `WithdrawAsset` for 1000 `T`. `ERC20Transactor::withdraw_asset_with_surplus` calls `T.transfer(checking_account, 1000)`. The fee mechanism causes the checking account to actually receive only 990 `T`, but `transfer` returns `true`.
3. Code path at `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs:195-203` credits `AssetsInHolding` with the full `1000` regardless, and the XCM proceeds as if the checking account holds 1000 more `T` than it truly does.
4. Repeat step 1-3 with multiple users; the checking account's real `T` balance is now cumulatively short by 1% per withdrawal versus the amount the pallet believes is available.
5. A subsequent legitimate `deposit_asset_with_surplus` for a beneficiary attempts `T.transfer(beneficiary, amount)` from the checking account for an amount that exceeds its actual token balance; the ERC20 `transfer` reverts, causing `Err((what, XcmError::FailedToTransactAsset("ERC20 contract reverted")))` at line 274 — the legitimate user's deposit fails/gets stuck, mirroring the "last unstaker reverts" scenario from the source report.
