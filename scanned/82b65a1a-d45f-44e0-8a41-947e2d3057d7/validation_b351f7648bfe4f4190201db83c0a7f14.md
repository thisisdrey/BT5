### Title
`process_delivery_receipt` in Snowbridge Outbound Queue V2 ignores `DeliveryReceipt.success`, rewarding relayers for failed message dispatch - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The external report's core broken invariant is: a field that is supposed to gate/shape privileged execution (the `marketHelper` address determining the call sequence) is decoded from attacker/user-controlled input but never validated before being used to authorize value movement. The closest verifiable local analog is in `Pallet::process_delivery_receipt` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:445-481`): the pallet decodes a `DeliveryReceipt` that carries a `success: bool` field describing whether the message dispatch on Ethereum succeeded or reverted, but this field is never checked before paying out the relayer's reward and clearing the pending order.

### Finding Description
`DeliveryReceipt` (`bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs:14-27`) is decoded from the `InboundMessageDispatched(nonce, topic, success, reward_address)` event log emitted by the Ethereum Gateway, and contains an explicit `success` field documented as "Delivery status".

`process_delivery_receipt` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:445-481`) performs the following checks only:
- `receipt.gateway == T::GatewayAddress::get()` (correct contract)
- resolves `reward_account` from `receipt.reward_address`
- looks up the `PendingOrder` by `receipt.nonce`
- if `order.fee > 0`, calls `T::RewardPayment::register_reward(...)`
- removes the order and emits `MessageDelivered`

At no point is `receipt.success` inspected. The relayer's proof-verified receipt (verified via the beacon/receipt Merkle proof pipeline, so it cannot be forged) can legitimately report `success: false` — meaning the message dispatch failed/reverted on the Ethereum side — yet the pallet still pays the full relayer fee and permanently removes the `PendingOrder`, exactly as if the message had been executed successfully. This mirrors the report's pattern: a value that is present specifically to represent whether the intended operation validly happened is decoded but silently discarded, letting the code proceed down the "success" code path (fund payout + state settlement) regardless of the actual outcome.

Existing guards (gateway check, nonce lookup, proof verification of the receipt itself) only ensure the *receipt* is authentic — they do not ensure the *outcome it reports* is favorable before authorizing payout. This is the same class of gap as the marketHelper case: whitelisting/verifying one input (`market`/`gateway`) while leaving a second, outcome-determining input (`marketHelper`/`success`) completely unchecked before it's used to drive an unconditional payout.

### Impact Explanation
This falls under "duplicate settlement or payout" / "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" from the impact gate. Relayers are economically incentivized to deliver messages even to Gateway calls that are known/crafted to revert on the destination (e.g., malformed commands, insufficient gas relative to complex commands, or genuinely failing execution), since they are paid the fee unconditionally as long as the receipt's nonce and gateway match. This decouples relayer compensation from actual successful bridge delivery, degrading the incentive alignment that message-queue processing is supposed to enforce, and can be exploited to systematically drain the fee budget of `PendingOrders` without ever completing the intended cross-chain action.

### Likelihood Explanation
The path is reachable by any relayer (an unprivileged, permissionless role — the report requires no malicious peer/validator/governance actor) simply submitting a real proof for a real Ethereum transaction where the Gateway's inner command dispatch fails but the outer transaction (and its `InboundMessageDispatched` log) still completes with `success: false`. No collusion or privileged access is required; it only requires crafting or waiting for an on-chain execution failure at the destination and then relaying its proof — a normal operational scenario in a bridge, not a contrived edge case.

### Recommendation
Check `receipt.success` in `process_delivery_receipt` before paying the reward. If the outcome is a legitimate delivery-but-failed-execution case that should still compensate for gas/delivery effort, make that an explicit, separately reasoned policy (e.g., partial fee, or a distinct code path with its own invariant), rather than silently ignoring the field:

```diff
 pub fn process_delivery_receipt(
     relayer: <T as frame_system::Config>::AccountId,
     receipt: DeliveryReceipt,
 ) -> DispatchResult
 where
     <T as frame_system::Config>::AccountId: From<[u8; 32]>,
 {
     ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);
+    ensure!(receipt.success, Error::<T>::MessageDispatchFailed);

     let reward_account = if receipt.reward_address == [0u8; 32] {
         relayer
     } else {
         receipt.reward_address.into()
     };
     ...
```

### Proof of Concept
1. A message is queued via `do_process_message`, generating a `PendingOrder { nonce, fee, .. }` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:426-436`).
2. A relayer delivers the message to the Ethereum Gateway, but the inner command dispatch on the Ethereum side fails/reverts (e.g., insufficient gas for the specific command, or a command that is invalid at execution time). The Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. The relayer obtains a legitimate Merkle/receipt proof for this event and calls `submit_delivery_receipt`, which decodes it into a `DeliveryReceipt{ success: false, .. }` (`bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs:35-51`).
4. `process_delivery_receipt` validates only `gateway` and `nonce` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:454-464`), never inspecting `receipt.success`, and unconditionally calls `T::RewardPayment::register_reward(&reward_account, .., order.fee)` and removes the `PendingOrder`.
5. Result: the relayer is fully rewarded and the order is settled as "delivered" even though the underlying message execution failed on Ethereum — confirmed by reading the field definitions and the full body of `process_delivery_receipt`, which contains no reference to `receipt.success` anywhere in the function.

Note: I was not able to find (within index limits) an explicit test in `bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs` that exercises `success: false`, so I could not directly observe a runtime assertion confirming this is unintended vs. a deliberate "pay for delivery attempt regardless of outcome" design choice; this uncertainty should be verified against Snowbridge's intended reward semantics before treating this purely as a bug rather than a design decision.
