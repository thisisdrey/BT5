## Title
Stale child-bounty curator fee is never reverted from the parent bounty's aggregate fee pot after `unassign_curator`, letting a parent curator accumulate un-earned deductions - (File: `substrate/frame/child-bounties/src/lib.rs`)

## Summary
`propose_curator` in `pallet-child-bounties` unilaterally commits a curator fee into the parent bounty's cumulative fee ledger (`ChildrenCuratorFees`) the moment it is called, before the proposed child curator ever accepts the role. `unassign_curator`, when called against a `CuratorProposed` (i.e. not-yet-accepted) child bounty, resets the bounty status back to `Added` but never decrements `ChildrenCuratorFees` and never resets `child_bounty.fee`. A subsequent `propose_curator` call on the same child bounty then *adds* a new fee on top of the stale one instead of replacing it, so the parent bounty's fee ledger silently accumulates fees for curators who never accepted, agreed, or did any work. This is the exact broken invariant from the external report: a party unilaterally sets a fee that gets baked into settlement accounting without the counterparty's agreement, and it is never cleaned up when the proposal is withdrawn.

## Finding Description
`propose_curator` writes the fee unconditionally into the shared accumulator as soon as it is called, before any curator acceptance: [1](#0-0) 

`unassign_curator`'s handling of the `CuratorProposed` state only checks authorization and falls through to reset the status — it does not touch `child_bounty.fee` or `ChildrenCuratorFees`: [2](#0-1) [3](#0-2) 

Compare this with `close_child_bounty` (`impl_close_child_bounty`), which correctly reverts the fee from the ledger when a child bounty is fully cancelled/removed: [4](#0-3) 

Because `unassign_curator` does not go through this reversal path, calling `propose_curator` again on the same child bounty index simply adds the new fee on top of the old one that was never removed: [5](#0-4) 

The accumulated (and now partially stale) total is only read and cleared once, when the parent bounty is claimed, via `children_curator_fees`, which is subtracted from the parent curator's award in `pallet-bounties`: [6](#0-5) 

No guard exists anywhere in `propose_curator` or `unassign_curator` to detect that a previous, never-accepted proposal already contributed to `ChildrenCuratorFees` for that same child-bounty slot, so the ledger permanently overstates fees actually owed to real, accepted curators — precisely mirroring the reported escrow bug where `proposeArbitrator` committed a fee to be deducted from the counterparty's share without the arbitrator ever confirming participation.

## Impact Explanation
This corrupts the `ChildrenCuratorFees` storage value for a parent bounty, which is a value directly used to reduce the payout the parent bounty curator receives when the parent bounty is claimed. A parent curator (or any actor who can invoke `propose_curator`/`unassign_curator` combinations, since the parent curator itself can trigger both) can cause the treasury-funded parent bounty's payout accounting to permanently lose funds to phantom, unaccepted "curator fees" that are never paid to anyone (no curator ever accepted them, so no counterpart transfer happens for the stale portion) — this is unbacked fund loss/lock in the treasury/bounty accounting path, matching the "theft/unbacked" and "duplicate settlement" impact classes for on-chain fund accounting.

## Likelihood Explanation
Reachable purely through the normal signed public extrinsics `propose_curator` and `unassign_curator`, both callable by the parent bounty curator (a normal signed account, not governance/root) without any special privilege beyond already being the curator of an active parent bounty — no malicious validator, relayer, or admin abuse is required, only ordinary calls in a slightly unusual but fully permitted order (propose → unassign → propose again).

## Recommendation
In `unassign_curator`, when transitioning out of `ChildBountyStatus::CuratorProposed { .. }` (and similarly whenever a fee is discarded/replaced), decrement `ChildrenCuratorFees::<T>::mutate(parent_bounty_id, |v| *v = v.saturating_sub(child_bounty.fee))` and reset `child_bounty.fee = Zero::zero()`, mirroring the reversal logic already present in `impl_close_child_bounty`. Additionally, `propose_curator` should not blindly `saturating_add` onto the fee pool without first subtracting any previously proposed (but not yet accepted) fee for that same child bounty.

## Proof of Concept
1. Governance funds and approves a parent bounty; curator `C` accepts and the parent bounty becomes `Active`.
2. `C` calls `add_child_bounty` to create child bounty `#0` with value `V`.
3. `C` calls `propose_curator(parent, 0, X, fee=F1)` → `child_bounty.fee = F1`, `ChildrenCuratorFees[parent] += F1`.
4. Before `X` accepts, `C` calls `unassign_curator(parent, 0)` → status resets to `Added`, but `ChildrenCuratorFees[parent]` still equals `F1` and is never reduced.
5. `C` calls `propose_curator(parent, 0, Y, fee=F2)` → `child_bounty.fee = F2` (overwritten), but `ChildrenCuratorFees[parent] += F2`, making the total `F1 + F2`.
6. `Y` accepts and is awarded/claims the child bounty normally, paying out only `F2` from the child bounty account (correct locally).
7. When the parent bounty is later claimed, `children_curator_fees(parent)` returns `F1 + F2` and this full amount is deducted from curator `C`'s parent-bounty payout in `pallet-bounties`, even though only `F2` was ever paid to an accepting curator — `F1` is lost from `C`'s rightful payout with no corresponding recipient, reproducing the "fee deducted despite no arbitrator/curator ever accepting" defect from the external report.
