Based on my investigation, I found a locally provable analog in the Snowbridge inbound-queue-v2 tip mechanism, but I was not able to fully confirm the exact mechanics of how real value is deducted in `pallet-system-v2`/`system-frontend` before it's forwarded here — I note that uncertainty below.

### Title
Permanently unrecoverable relayer tip funds via `Tips` storage with no cancel/refund path - (File: bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs)

### Summary
`pallet-inbound-queue-v2` exposes an `AddTip` trait implementation that lets any caller (via `pallet-system-v2`/`system-frontend`, which forward user-supplied value) increase the relayer reward tied to a specific future Ethereum-origin `nonce`. The tip is stored keyed only by `nonce` in `Tips<T>` and is only ever released when `process_message` for that exact nonce succeeds. There is no extrinsic or code path to cancel, refund, or reclaim a tip once it has been added for a nonce that is never submitted or never resolves.

### Finding Description
`Tips<T>` is a simple `StorageMap<u64, u128>` keyed by nonce [1](#0-0) . The `AddTip` trait implementation only guards against adding a tip to an already-consumed nonce, but performs no other validation and provides no way to remove an entry outside of successful processing: [2](#0-1) 

The only place `Tips` is drained is inside `process_message`, which `take()`s the tip and pays it to whichever relayer eventually submits that exact nonce: [3](#0-2) 

Because nonces originate from events on the Ethereum Gateway contract and are consumed strictly in the order relayers submit them, a tip added for a nonce that never gets emitted/relayed (e.g., the corresponding Ethereum transaction is never sent, is reverted, the Gateway is later changed, or the message permanently fails `Verifier::verify`/decoding before `process_message` is ever reached) can never be paid out and can never be withdrawn by the user who funded it. There is no `remove_tip`, `cancel_tip`, or timeout/expiry mechanism anywhere in this pallet.

This mirrors the core broken invariant from the external report: "users should be guaranteed to be able to redeem their staked tokens... no entity in the system should be able to lock them indefinitely." Here the locking party is not an admin but the protocol design itself — an ordinary, unprivileged user who adds a tip for a nonce that subsequently fails to resolve loses that value permanently, with no code path to recover it.

Notably, a very similar defect (`pr_9746`, "Snowbridge Inbound Queue V2 relayer tip payout fix") was previously found and fixed where tips were lost because the backing value had already been burnt before the reward was registered [4](#0-3) , confirming that tips are backed by real, burnable/transferable value and that loss-of-tip has already occurred as a bug class in this exact code path. The remaining gap — no cancellation/refund path for a tip whose nonce never resolves — was not addressed by that fix.

### Impact Explanation
This falls under "permanent user-fund ... lock," an explicitly accepted impact category. Any unprivileged user who adds a tip for a nonce that is never actually relayed (due to relayer inaction, verifier failure, gateway address change via governance, or the Ethereum-side event simply never occurring for that nonce) permanently loses the value backing that tip, with no code path in the pallet to reclaim it.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: nonces are assigned externally on Ethereum and there is no guarantee within this pallet that a tipped nonce will ever be submitted (relayers might skip a low-value message, the message might fail verification permanently, or the tip could be added speculatively for a nonce that turns out to be invalid/never emitted). No malicious actor, admin, or front-run is required — an ordinary user simply exercises the public tip-adding functionality and the funds become stuck.

### Recommendation
Add an expiry or explicit cancellation mechanism for `Tips<T>` entries — e.g., allow the original tipper (tracked by including the payer's account in the storage value) to reclaim the tip after a bounded number of blocks/nonces have passed without that nonce being consumed, consistent with the report's recommendation of guaranteeing users a way to redeem locked value rather than allowing indefinite, unrecoverable locks.

### Proof of Concept
1. An unprivileged user calls the `AddTip`-backed extrinsic (via `pallet-system-v2`/`system-frontend`) to add a tip for a future `nonce` N, and real value is deducted/held against that call.
2. `Tips::<T>::mutate(N, ...)` stores the tip; `Nonce::<T>::get(N)` is `false`, so `add_tip` succeeds [5](#0-4) .
3. The Ethereum-side event for nonce N never occurs (or its relay permanently fails verification before reaching `process_message`), so `process_message` for nonce N is never successfully executed and `Tips::<T>::take(N)` is never called [6](#0-5) .
4. `Tips::<T>::get(N)` remains permanently populated with no extrinsic capable of removing it or refunding the underlying value to the original tipper — the value is locked indefinitely.

		pub fn process_message(relayer: T::AccountId, message: Message) -> DispatchResult {
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == message.gateway, Error::<T>::InvalidGateway);

			let (nonce, relayer_fee) = (message.nonce, message.relayer_fee);

			// Verify the message has not been processed
			ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);

			// Mark message as received
			Nonce::<T>::set(nonce);

			let message_id = T::MessageProcessor::process_message(relayer.clone(), message)
				.map_err(|e| match e {
					MessageProcessorError::ProcessMessage(e) => e,
					MessageProcessorError::ConvertMessage(e) => Error::<T>::from(e).into(),
					MessageProcessorError::SendMessage(e) => Error::<T>::from(e).into(),
				})?;

			// Pay relayer reward
			let tip = Tips::<T>::take(nonce).unwrap_or_default();
			let total_tip = relayer_fee.saturating_add(tip);
			if total_tip > 0 {
				T::RewardPayment::register_reward(&relayer, T::DefaultRewardKind::get(), total_tip);
			}

			// Emit event with the message_id
			Self::deposit_event(Event::MessageReceived { nonce, message_id });

			Ok(())
		}

	impl<T: Config> AddTip for Pallet<T> {
		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			// If the nonce is already processed, return an error
			ensure!(!Nonce::<T>::get(nonce.into()), AddTipError::NonceConsumed);
			// Otherwise add the tip.
			Tips::<T>::mutate(nonce, |tip| {
				*tip = Some(tip.unwrap_or_default().saturating_add(amount));
			});
			return Ok(());
		}
	}
