The strongest local analog to the Beanstalk `LibTokenPermit._buildDomainSeparator` bug is the EIP-712 domain-separator computation in the `pallet_assets` ERC20Permit precompile pallet, which mirrors the exact same anti-pattern: binding a signature domain to a **static, compile-time chain identifier** instead of the chain's actual live identity.

### Title
EIP-712 permit domain separator binds to a static compile-time `ChainId` constant, enabling cross-fork signature replay - (File: `substrate/frame/assets/precompiles/src/permit.rs`)

### Summary
`permit::Pallet::compute_domain_separator` builds the EIP-2612 domain separator using `T::ChainId::get()`, a `#[pallet::constant]` baked into the runtime at compile time, rather than any value that reflects the chain's actual live network identity at execution time.

### Finding Description
The domain separator is computed as: [1](#0-0) 

`T::ChainId` is declared as a plain configuration constant on the pallet's `Config` trait: [2](#0-1) 

and every runtime that wires up this pallet sets it to a hardcoded literal, e.g. `ConstU64<420_420_421>` on Asset Hub Westend and `ConstU64<420_420_420>` in the kitchensink runtime — the exact same "static constant" pattern flagged in the Beanstalk report as `C.getChainId()`: [3](#0-2) [4](#0-3) 

This constant is compiled into the runtime WASM blob itself. It is not derived from `block.chainid`-equivalent runtime state (there is no such native Substrate concept), nor from the chain's genesis hash, nor from any other value that is guaranteed to differ between two independently-running networks that happen to share the same runtime code. The final signed digest is built purely from this domain separator plus the permit struct hash: [5](#0-4) 

If two live chains end up running the *same compiled runtime* (and therefore the same `ChainId` constant) — for example after a contentious hard fork of a parachain, a runtime that is deliberately reused to spin up a new/canary network sharing the same code but a different genesis, or any scenario where the same runtime image serves two distinct chains — every previously-issued `permit()` signature is valid on both. Unlike `frame_system`'s own transaction-validity extensions (`CheckGenesis`/`CheckMortality`), which explicitly bind extrinsics to the genesis hash and a specific block hash to guarantee fork-uniqueness: [6](#0-5) 

the `permit()` EIP-712 flow inside `pallet_revive`'s precompile layer has no equivalent binding — it relies solely on the constant `ChainId`, which is identical across both forks by construction.

The same static-constant pattern also governs `pallet_revive`'s own EIP-155 chain-id check for raw Ethereum-style transactions (`eth_transact`), which checks incoming `chain_id` against `<T as Config>::ChainId::get()`: [7](#0-6) 
This reinforces that "chain id" throughout `pallet_revive` and its precompiles is treated as a fixed, code-level constant rather than a chain-instance-specific value — precisely the broken invariant identified in the external report.

### Impact Explanation
Any user who has ever signed an EIP-2612 `permit()` message granting an allowance to a spender on one chain can have that exact signature replayed on a sibling chain running the same runtime binary (post-fork or parallel-deployment scenario), because `nonces` storage is independent per chain and `chain_id` matches in both domain separators. The replayed permit grants the same spender the same allowance on the second chain without the owner's fresh consent, which the spender can then use to transfer/drain the token allowance — a direct "theft" / "unauthorized execution" style impact on asset accounting, consistent with the required impact categories (unauthorized execution, unbacked/duplicate settlement of value).

### Likelihood Explanation
This does not require a malicious validator, collator, relayer, or governance actor — it is a pure protocol/runtime-code property that manifests automatically whenever the same runtime code backs two live chains (accidental fork recovery, deliberate hard fork, or intentional reuse of a runtime image for a new network). Any already-signed, still-valid (non-expired, unconsumed-nonce) permit is replayable with zero additional attacker capability beyond broadcasting the existing signature on the second chain.

### Recommendation
Do not rely solely on a compile-time `ChainId` constant for domain separation. Either:
- derive the EIP-712 domain separator's chain-id component from a value that is guaranteed unique per live chain instance (e.g., incorporate the chain's genesis hash, as `frame_system::CheckGenesis`/`CheckMortality` already do for native extrinsics), or
- require operators to mint a fresh, chain-unique `ChainId` on every runtime deployment/fork and treat it as a governance-settable storage value (recomputing/invalidating cached domain separators on change) rather than a hardcoded `Get<u64>` baked into the runtime binary.

### Proof of Concept
1. Deploy runtime `R` with `pallet_revive::Config::ChainId = ConstU64<X>` and the ERC20Permit precompile enabled, as Chain A.
2. Fork Chain A at some block to create Chain B, keeping the same runtime code (and hence the same compiled `ChainId = X`), but a different genesis/chain state going forward (this is exactly the scenario the Beanstalk report describes for Ethereum/ETHPoW).
3. On Chain A, owner signs a `permit(owner, spender, value, deadline, v, r, s)` message; `compute_domain_separator` for this uses `chain_id = X`. [1](#0-0) 
4. Spender submits the permit on Chain A — succeeds, nonce increments to 1 on Chain A only (nonces are chain-local storage).
5. Spender submits the *same* `(v, r, s)` permit calldata to the ERC20Permit precompile on Chain B. Since Chain B's nonce for `(verifying_contract, owner)` is still 0 (independent storage) and `chain_id` in the recomputed domain separator is still `X` (same compiled constant), the digest matches, `secp256k1_ecdsa_recover` returns `owner`, and the permit is accepted on Chain B — granting the spender the allowance a second time without the owner ever intending or re-signing anything for Chain B. /// Replay of a consumed permit must fail through the precompile path.
/// EIP-2612's headline guarantee — `permit()` atomically verifies and

/// submodule. Pinning the invariant at the precompile layer.
///
/// First submission consumes the permit (nonce 0 → 1). The same
/// `(v, r, s)` is then re-submitted; the precompile re-derives the
/// digest using the new on-chain nonce, recovery yields a different
/// signer, and `recovered != owner` fires "Signer does not match
/// owner".
#[test]
fn permit_replay_through_precompile_is_rejected() {
	use frame_support::traits::fungibles::approvals::Inspect;

	new_test_ext().execute_with(|| {
		let setup = permit_setup(PRECOMPILE_ADDRESS_PREFIX);

		let (v, r, s) =
			sign_permit(setup.asset_addr, setup.spender_addr, AlloyU256::from(100), setup.deadline);

		let first = raw_permit(
			setup.submitter,
			setup.asset_addr,
			HARDHAT_ACCOUNT_0,
			setup.spender_addr,
			AlloyU256::from(100),
			setup.deadline,
			v,
			r,
			s,
		);
		assert!(first.result.is_ok(), "first permit must succeed: {:?}", first);
		assert!(!first.result.expect("checked above").did_revert(), "first permit must not revert",);
		assert_eq!(
			permit::Pallet::<Test>::nonce(&setup.asset_addr, &HARDHAT_ACCOUNT_0),
			U256::one(),
			"first permit must advance the nonce",
		);
