Target: MAX_TOKEN_ID_LEN (contracts/defuse/core/src/tokens.rs const, checked in imt::into_generic_tokens and nft_on_transfer/mt_on_transfer). Attacker crafts a token_id string of length exactly MAX_TOKEN_ID_LEN whose content, when concatenated with contract_id and discriminant prefix in TokenId::Display, produces a string that upon FromStr's split_once(':') is truncated or misattributed due to any length-based validation applied to the WRONG substring (e.g. validating raw msg length instead of the wrapped TokenId string length). Preconditions: attacker deposits via mt_on_transfer with a token_id at the boundary length. Call sequence: DefuseError::TokenIdTooLarge(token_id.len()).panic() checks token_id.len() (the raw MT-side id) before wrapping into Nep245TokenId::new(token, token_id), but the wrapped TokenId's full Display string (prefix+contract_id+':'+token_id) is longer and unchecked; if any storage key length limit elsewhere truncates the wrapped string, two different original token_ids could produce identical truncated keys. Binding: TokenId::from_str(&t.to_string())==t must hold for the actual stored/keyed representation, not just the pre-wrap substring. Impact: Critical if truncation causes two distinct deposits to collide on the same stored balance key. Proof idea: cargo test depositing two MT tokens whose raw token_id differ only after the truncation boundary and asserting their wrapped TokenId values and stored balances remain distinct.
