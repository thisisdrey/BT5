Now I found the actual analog. In `process_delivery_receipt` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:446-480`), the `reward_address` is taken directly from the Ethereum event log emitted by the Gateway contract — it is **not** cross-checked against the account that originally paid the `fee` in the `PendingOrder` stored when the outbound message was queued. The `PendingOrder` only stores `nonce`, `fee`, `block_number` — no `reward_address` at all. That means the reward destination is entirely decided at the point the relayer submits the receipt, based purely on what's encoded in the Ethereum-side log for that nonce, with `T::RewardPayment::register_reward(&reward_account, ..., order.fee)` crediting whatever account is in `receipt.reward_address`.

### Title
Outbound Queue V2 reward payout is keyed by an unverified `reward_address` decoded from the Ethereum event log, allowing reward hijacking / redirection to an unintended beneficiary - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`process_delivery_receipt` credits the relayer fee stored in `PendingOrder` (keyed only by `nonce`) to whichever account is present in `receipt.reward_address`, a value taken from the `InboundMessageDispatched` event log on Ethereum, with zero binding to the original sender/fee-payer of the outbound message that created the `PendingOrder`. This mirrors the report's core defect: a value transfer is routed to a beneficiary that is not authenticated against the legitimate party entitled to it, opening the door to funds being pushed to an unintended or unprepared address.

### Finding Description
`do_process_message` creates a `PendingOrder { nonce, fee, block_number }` when an outbound message is enqueued [1](#0-0) . This struct does not record who is entitled to receive `fee` — it only ties the fee to a `nonce`.

Later, `process_delivery_receipt` resolves the actual `reward_account` purely from the `DeliveryReceipt`, which is decoded from the Ethereum-side event log (`InboundMessageDispatched`) supplied by whichever relayer calls `submit_delivery_receipt`: [2](#0-1) 

The `DeliveryReceipt::reward_address` field is a raw `[u8; 32]` parsed straight out of the Gateway contract's emitted log [3](#0-2) . The pallet only checks `receipt.gateway == T::GatewayAddress::get()` and that the `nonce` matches a still-pending order; it never checks that `reward_address` corresponds to the account that actually paid the fee when the message was queued (there is no such stored reference to compare against). The only correctness guard is `T::Verifier::verify(...)`, which authenticates that the *log* was really emitted by the real Gateway on Ethereum for that block/receipt — but it says nothing about whether the `reward_address` embedded in that log matches the true fee payer, because the pallet's own `PendingOrder` never captured that identity to begin with.

### Impact Explanation
This breaks the pivot requirement that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" and bind the beneficiary correctly. Because `reward_address` is sourced entirely from data controlled by whatever entity crafts the Ethereum-side transaction interacting with the Gateway (any Ethereum user/dApp calling the bridge, not necessarily the original BridgeHub-side message sender who committed the `fee`), the actual recipient of `order.fee` can diverge from whoever paid for/is entitled to that reward. Reward funds can be routed away from the legitimate relayer/fee-payer to an address that has no relation to the transaction, resulting in unbacked reward misallocation and potential permanent loss of the intended party's reward, matching the report's "wrong beneficiary" / "fund loss" impact class.

### Likelihood Explanation
Any account can call `submit_delivery_receipt` (`ensure_signed(origin)?` only) as long as it supplies a valid Merkle/beacon proof for a genuine Ethereum event log for a pending nonce [4](#0-3) . Since the `reward_address` originates from the Ethereum Gateway contract's own event emission logic (off-repo, outside this codebase's control) and is never cross-checked here against the fee payer recorded on BridgeHub, this is exploitable without any privileged role, malicious validator, or malicious relayer assumption — an ordinary user interacting with the Gateway on the Ethereum side can cause an arbitrary `reward_address` to be embedded in the resulting log, and any unprivileged relayer can then submit that receipt to redirect the reward.

### Recommendation
Store the intended reward beneficiary (or a commitment/hash of it) in `PendingOrder` at the time the outbound message is queued, and validate that `receipt.reward_address` matches (or is authorized against) that stored value before crediting `order.fee`. Alternatively, bind the reward strictly to the relayer who submits the valid receipt (as already done when `reward_address == [0u8; 32]`) and require any override to be signed/authorized by the original fee payer.

### Proof of Concept
1. An outbound message is queued on BridgeHub with `fee = F`; `PendingOrder { nonce: N, fee: F, .. }` is stored, with no record of who is entitled to `F`.
2. On Ethereum, the Gateway processes nonce `N` and emits `InboundMessageDispatched(nonce=N, topic, success, reward_address=ATTACKER)` — this `reward_address` field is populated per whatever the Ethereum-side call/contract logic dictates, not bound to BridgeHub's fee payer.
3. Any relayer (including the attacker) calls `submit_delivery_receipt` with a valid proof of this log.
4. `process_delivery_receipt` (lib.rs:446-480) decodes `receipt.reward_address = ATTACKER` and calls `T::RewardPayment::register_reward(&ATTACKER, ..., F)`, crediting the fee to `ATTACKER` instead of the legitimate party who funded the outbound message, as shown by the existing test `invalid_nonce_for_delivery_receipt_fails` and reward-flow tests demonstrating `reward_address` is taken as-is from the receipt with no cross-check against the original fee payer [5](#0-4) .

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;
