Based on my investigation, I found a concrete local analog in `pallet-psm` (Peg Stability Module), which explicitly has debt-vs-raw-reserve semantics that mirror the CToken `cash` vs `internalCash` problem described in the report.

### Title
Peg Stability Module redemption capacity is bounded by tracked debt while donated/raw reserve balance can diverge from it, risking exchange-rate/accounting desync - ([File: substrate/frame/psm/src/lib.rs])

### Summary
`pallet-psm` maintains a `PsmDebt` storage value per (internal asset, external asset) pair that is meant to represent the pool's accounted liability, separate from the actual raw balance held in the `psm_account()`. The pallet's own test suite (`fails_when_reserve_exceeds_debt_donated_reserves`) demonstrates that an actor can fund the `psm_account()` directly (bypassing `mint`), inflating the real reserve above the tracked `PsmDebt` value [1](#0-0) . This is structurally the same "cash vs internalCash" mismatch identified in the CToken report: a public entrypoint (`redeem`) computes payout eligibility from an internally tracked debt/accounting variable rather than the live token balance, so any external donation to the module's account can desynchronize the two values.

### Finding Description
`Psm::mint` and `Psm::redeem` operate against `PsmDebt::<T>::get(internal_asset, external_asset)` as the authoritative peg amount, while the actual external asset balance held by `psm_account()` is queried separately via `get_asset_balance` [2](#0-1) . The test confirms that `redeem` is limited by `debt`, not by the raw reserve, and that direct funding of the `psm_account()` (`fund_external_asset`) can push `reserve > debt` without going through the pallet's mint accounting path [3](#0-2) . The redeem call fails only because it explicitly checks against `debt`, returning `Error::<Test>::InsufficientReserve` for `debt + 1` [4](#0-3) . This shows the pallet is aware of, and defends the "redeem beyond debt" case for the redeeming user, but the existence of this defensive test path (labeled "Defensive path: simulate donated reserves ... to create a reserve > debt scenario") indicates the underlying invariant — that `psm_account()`'s live balance and `PsmDebt` must stay reconciled — can be broken by any account transferring the external asset directly into `psm_account()`, exactly analogous to the CToken bug where a direct `transfer()` of the underlying to the market account inflates `cash` independent of the tracked ledger.

Because I could not retrieve the full `substrate/frame/psm/src/lib.rs` source (the file content was not returned by the tools available to me before this session ended), I cannot confirm the exact `do_mint`/`do_redeem` formulas, whether minting fees/exchange rate calculations reference the raw balance anywhere else (e.g., in a price/backing ratio calculation rather than just the debt cap), or whether there is a public code path where the *exchange rate* (rather than just the redemption cap) is derived from the live/raw balance in a way a first-depositor or empty-pool donation could exploit for profit (mirroring the CToken flow of mint → redeem-to-near-zero → donate → third-party mint → attacker redeem-for-more).

### Impact Explanation
If any function in the module computes minting output or a peg ratio from the live external-asset balance of `psm_account()` (rather than exclusively from `PsmDebt`), an attacker could donate tokens directly to `psm_account()` to skew that computed ratio, causing incorrect internal-asset minting/redemption amounts for other users — a direct value-conservation violation consistent with the "Balances ... must conserve value and settle exactly once to the rightful beneficiary and amount" pivot. Given the test only asserts the debt-capped redemption is safe, and does not assert what happens to the *raw reserve accounting* after a donation (e.g., whether a later `mint`/`redeem` cycle can "absorb" the donated funds into a favorable rate for the depositor who made the donation), the severity cannot be confirmed without reading the full pallet implementation.

### Likelihood Explanation
Unconfirmed. The precondition (transferring the external asset directly to `psm_account()`) requires no special privilege — any user can call the underlying assets pallet's `transfer` to a known, deterministic sovereign account — which matches the report's "public underpriced work / unauthorized value extraction by unprivileged actor" profile. However, without the full `mint`/`redeem` implementation I cannot verify whether such a donation actually corrupts a value used for minting math, or whether it is inert (as the test's naming "Defensive path" suggests the pallet already guards this case for redemption).

### Recommendation
Because the exact vulnerable code path in `substrate/frame/psm/src/lib.rs` could not be retrieved and verified in this session, no proof-of-concept or corrupted-value citation for the mint/redeem exchange-rate computation can be produced with certainty here. A full read of `substrate/frame/psm/src/lib.rs` (the `do_mint`/`do_redeem`/`mint`/`redeem` functions and every place `PsmDebt` and `get_asset_balance`/raw reserve are used together) is required to confirm or rule out an exploitable divergence between tracked debt and actual balance, analogous to the CToken `internalCash` recommendation (i.e., all pool-accounting pallets — `pallet-psm` and `pallet-asset-conversion` alike — should base exchange-rate and payout calculations exclusively on internally tracked ledger values, never on live `T::Assets::balance` queries that can be inflated by unsolicited transfers).

	#[test]
	fn fails_when_reserve_exceeds_debt_donated_reserves() {
		ExtBuilder::default().mints(ALICE, 5000 * INTERNAL_UNIT).build_and_execute(|| {
			set_redemption_fee(USDC_ASSET_ID, Permill::zero());

			let debt = PsmDebt::<Test>::get(INTERNAL_ASSET_ID, USDC_ASSET_ID);
			let donation = 5000 * INTERNAL_UNIT;

			// Defensive path: simulate donated reserves by funding psm_account()
			// directly, bypassing mint to create a reserve > debt scenario.
			fund_external_asset(USDC_ASSET_ID, psm_account(), donation);

			let reserve = get_asset_balance(USDC_ASSET_ID, psm_account());
			assert!(reserve > debt, "reserve should exceed debt after donation");

			// Give user enough internal to try redeeming more than debt
			let redeem_amount = debt + donation;
			fund_internal(ALICE, redeem_amount);

			// Should fail because redemption is limited by debt, not reserve
			assert_noop!(
				Psm::redeem(
					RuntimeOrigin::signed(ALICE),
					INTERNAL_ASSET_ID,
					USDC_ASSET_ID,
					redeem_amount,
					Permill::zero()
				),
				Error::<Test>::InsufficientReserve
			);

			// Verify boundary: exactly debt works, but debt+1 does not
			hypothetically!({
				assert_ok!(Psm::redeem(
					RuntimeOrigin::signed(ALICE),
					INTERNAL_ASSET_ID,
					USDC_ASSET_ID,
					debt,
					Permill::zero()
				));
				assert_eq!(get_asset_balance(USDC_ASSET_ID, psm_account()), donation);
			});

			assert_noop!(
				Psm::redeem(
					RuntimeOrigin::signed(ALICE),
					INTERNAL_ASSET_ID,
					USDC_ASSET_ID,
					debt + 1,
					Permill::zero()
				),
				Error::<Test>::InsufficientReserve
			);
		});
