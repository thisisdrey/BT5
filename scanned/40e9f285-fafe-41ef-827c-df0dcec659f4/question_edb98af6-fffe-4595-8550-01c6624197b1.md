Preconditions: attacker withdraws two token_ids with different amounts, e.g. `token_ids=[cheap_id, expensive_id]`, `amounts=[large, small]`. Call sequence: `mt_resolve_withdraw` zips `token_ids.into_iter().zip(amounts).zip(&mut used)` and computes `used.0 = used.0.min(amount.0)`, refund = `amount.0 - used.0`, deposited back keyed by `token_id` at that same zipped index. Binding: (used[i] as reported reflects settlement of token_ids[i]) == (the actual on-chain transfer outcome for token_ids[i] specifically); if attacker's contract permutes the array, refund is credited against the WRONG `token_id`, e.g., crediting a refund for `expensive_id` when only `cheap_id`'s transfer actually failed. Impact: Critical, TokenId identity/settlement mismatch lets attacker manufacture a refund for a higher-value token while sacrificing a low-value one that they never intended to give up (or vice versa, extracting extra value). Proof idea: sandbox test with mt receiver returning permuted `used` vector for a two-token batch of differing value, assert refunded `token_id` matches the token whose real transfer actually failed, not an arbitrary index-shuffled one.
