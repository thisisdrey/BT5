Target: `WalletImpl::resolve_auth` / `WalletAuthorization::Signature` path check in contracts/wallet/src/contract.rs. Attacker action: submit an off-chain `authorization` blob of `WalletAuthorization::Signature{msg, proof}` where `msg.path` is empty `[]` while calling `w_resolve_auth` with a non-empty `path` argument supplied by a nested resolver traversal (i.e. attacker controls which `path` gets passed in by controlling an intermediate extension's `pending.account_id`/`expect`), attempting to get the top-level signature accepted at a `path` depth it wasn't signed for. Preconditions: attacker is an installed extension able to trigger sub-resolution with an arbitrary `path` argument value passed to a sibling/descendant resolver. Call sequence: `resolve_auth` -> `if msg.path != path { return Err(InvalidPath) }`. Binding: `msg.path == path` exactly, i.e. the traversal path the resolver used equals the one the signer signed over. Scoped impact (High): if this equality check can be bypassed via mismatched reversed/forward path encoding between `client.rs`'s `Reversed` serde wrapper and the resolver's internal `rev_path`, an authorization signed for one traversal depth is accepted at another, letting an attacker's payload be authorized at an unintended path. Proof idea: `cargo test` constructing `WalletAuthorization::Signature{msg: RequestMessage-like with path=[a,b]}` and calling `resolve_auth` with `path=[b,a]` (reversed) or `path=[a]` (truncated) and asserting `Error::InvalidPath` in every case.
