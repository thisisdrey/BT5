Target: `Nonces::commit` bitmap key/value encoding (`27`-bit key / `5`-bit position doc comment) in contracts/wallet/src/message.rs and `BitMap<BTreeMap<u32,u32>>` in contracts/wallet/src/nonces.rs. Attacker action: choose two distinct `u32` nonce values `n1 != n2` that map to the SAME `(word_pos, bit_pos)` pair under whatever bit-splitting scheme `BitMap`'s `get_bit`/`set_bit` implementation uses for a plain `u32` domain (as opposed to the `U256`/`U248` split used in `defuse-bitmap` for the main Verifier), i.e. probe for an implementation mismatch between the wallet's `u32`-nonce `BitMap` and the Verifier's `U256`-nonce `BitMap256`, then commit `n1` and check whether `n2` is now falsely reported as used (denying the owner's legitimate future nonce) or, worse, whether committing `n2` after `n1` is wrongly treated as already-committed letting a DIFFERENT signed request silently be treated as a replay-preventable duplicate of a distinct one (which would be a false-positive, not exploitable) versus the inverse bug where two DIFFERENT logical nonces collide to the SAME bit letting a nonce appear "fresh" when it structurally aliases a used one only in one direction. Preconditions: none beyond crafting nonce values. Call sequence: `commit(nonce, ...)` -> `self.current.set_bit(nonce)`. Binding: `Nonces::is_used`-equivalent state after `commit(n)` must reflect exactly the single bit for `n` and no other `n' != n`, so no unrelated nonce silently becomes "pre-used" (which would only block, not authorize) — but ALSO no single physical bit must be shared by two nonces the client is told are independent, since that would let a client believe nonce `n2` is fresh while it structurally is `n1`, letting a replay slip through as a "new" nonce commit that is actually rejected as reused, masking failed replay attempts as fresh ones in monitoring. Scoped impact (High): a colliding bit mapping could let an attacker force the wallet to reject a legitimate distinct nonce as `AlreadyUsed`, effectively freezing that specific concurrent-signer's request path, or invert to allow a used nonce's `msg` to be treated as fresh due to a differently-encoded but colliding `n`. Proof idea: `cargo test` iterating adjacent `u32` values around 32-bit boundaries feeding `BitMap::set_bit`/`get_bit` and asserting bijectivity between `nonce` and `(word_pos,bit_pos)`.
