## Title
Missing BLS12-381 G1 subgroup check on sync-committee public keys allows forged Ethereum light-client updates in Snowbridge - (File: `bridges/snowbridge/primitives/beacon/src/bls.rs`)

## Summary
The external report's core defect is that a PLONK verifier accepts curve-point inputs (commitments) without confirming they are valid points on the correct group, relying instead on an implicit assumption (EC precompile behavior) rather than an explicit check required by the security proof. The equivalent broken invariant exists in Snowbridge's Ethereum Beacon light client: sync-committee BLS public keys are deserialized and used directly in signature aggregation without verifying that they belong to the prime-order G1 subgroup, relying on the implicit assumption that "the beacon chain enforces subgroup membership so Merkle-proven keys are safe" — an assumption that is not enforced by any code in this repository.

## Finding Description
`prepare_milagro_pubkey` decompresses a compressed BLS public key from beacon-chain SSZ data using `PublicKeyPrepared::from_bytes`, and `prepare_g1_pubkeys` maps this over the full sync-committee key set with no additional validation: [1](#0-0) 

These prepared keys are stored as `SyncCommitteePrepared` (used for both `CurrentSyncCommittee`/`NextSyncCommittee` storage) via a `TryFrom` impl that calls `prepare_g1_pubkeys`/`prepare_milagro_pubkey` with no subgroup check: [2](#0-1) 

The prepared aggregate key is then combined via `AggregatePublicKey` point arithmetic (subtracting absent participants) and used in BLS `fast_aggregate_verify`, the sole gate that accepts a `Update` as a valid, finalized consensus update: [3](#0-2) 

This is invoked from `verify_update` inside the `ethereum-client` pallet, which is the single check standing between an untrusted, publicly-submitted `Update`/`CheckpointUpdate` and acceptance of a new finalized beacon header / sync committee, feeding execution-header and Merkle-ancestry proofs used elsewhere in the bridge: [4](#0-3) 

Notably, the repository already contains an in-tree PR doc that explicitly names this exact gap and describes a fix ("harden BLS public key deserialization ... validate all cryptographic inputs ... check [subgroup membership] as defense-in-depth"), acknowledging that an attacker who can produce a Merkle-proof-consistent public key that is on-curve but outside the G1 subgroup could break the light client: [5](#0-4) 

However, no subgroup-membership check (`is_in_correct_subgroup`/cofactor multiplication or milagro-side rejection of non-subgroup points) exists anywhere in `bridges/snowbridge/primitives/beacon/src/bls.rs` or `types.rs` in this snapshot — the code matches the pre-fix state described in the prdoc, meaning the documented mitigation was never actually applied to `prepare_milagro_pubkey`/`prepare_g1_pubkeys`. `PublicKeyPrepared::from_bytes` (from the external `milagro_bls` crate) only guarantees the deserialized point is on the BLS12-381 curve, not that it lies in the correct prime-order subgroup — this is the classic small-subgroup/rogue-key confusion class the report's "commitments must be valid elliptic curve points" recommendation targets, generalized here to "public keys must be valid subgroup elements," which the PLONK spec analog and BLS spec both require to inherit the underlying security proof.

## Impact Explanation
If an attacker can get a subgroup-invalid-but-on-curve public key accepted as part of a sync committee (e.g., via any weakness in the Merkle-branch/hash-tree-root binding chain, or simply because `verify_update`/`process_checkpoint_update` never independently re-validates points before caching them into long-lived `CurrentSyncCommittee`/`NextSyncCommittee` storage), an attacker with knowledge of a small-order component can manipulate the aggregate public key arithmetic (`aggregate_pubkey.point.sub(&absent_aggregate_key.point)`) to make `fast_aggregate_verify` accept a signature that was not actually produced by the legitimate super-majority of validators. This directly threatens the Polkadot SDK Impact Gate's "forged or mis-bound proof or state acceptance" and "runtime bugs that compromise intended behaviour" categories: a forged/mis-verified beacon update would let an unprivileged submitter push arbitrary finalized headers, sync committees, and downstream execution-header/ancestry proofs into BridgeHub state, corrupting bridge state without needing a malicious relayer, validator, or governance action — matching the required "public dispatch wrapper" attack surface (`submit`/checkpoint extrinsics are open to any signed account).

## Likelihood Explanation
Exploitation requires finding a point that both (a) satisfies the Merkle/SSZ hash-tree-root binding to a legitimate-looking beacon state and (b) is on-curve but outside G1 — the prdoc itself concedes this needs "compromise of the Merkle proof verification chain," which raises difficulty. However, the check is cheap (subgroup check ~512 times per period) and was already identified by the project's own security review as necessary defense-in-depth; its complete absence from the shipped code (despite an in-repo prdoc claiming it exists) means the light client currently has zero enforcement of a BLS-spec-mandated invariant, leaving the security margin entirely dependent on the strength of unrelated hash-collision resistance rather than an explicit, cheap, independent check.

## Recommendation
Add an explicit G1 subgroup-membership check (cofactor-multiplication or equivalent, as `milagro_bls`/other BLS crates typically expose) inside `prepare_milagro_pubkey` (and thus `prepare_g1_pubkeys`) in `bridges/snowbridge/primitives/beacon/src/bls.rs`, rejecting any decompressed public key that is on-curve but not in the correct subgroup, before it is cached into `SyncCommitteePrepared`/`CurrentSyncCommittee`/`NextSyncCommittee` storage or used in `fast_aggregate_verify`.

## Proof of Concept
1. Craft a compressed BLS12-381 G1 byte string that decodes to a point satisfying the curve equation (`y² = x³ + 4`) but that is not in the standard prime-order subgroup (i.e., has a nontrivial component of small order, obtainable by scaling a valid subgroup point by the cofactor's complementary factor and adjusting to stay on-curve).
2. Show that `milagro_bls::PublicKey::from_bytes` accepts this bytestring (only an on-curve check, no subgroup check) — matches `prepare_milagro_pubkey` at `bridges/snowbridge/primitives/beacon/src/bls.rs:38-39`.
3. Demonstrate that with such a point substituted as one sync-committee member's key (or the aggregate key), `AggregatePublicKey::from_public_key` / `.sub()` arithmetic in `prepare_aggregate_pubkey_from_absent` (`bls.rs:59-69`) can be manipulated so `fast_aggregate_verify_pre_aggregated` (`bls.rs:79-89`) returns `Ok(())` for a signature not produced by the honest majority, thereby getting `verify_update` in `bridges/snowbridge/pallets/ethereum-client/src/lib.rs:436-461` to accept and persist a forged `Update`.

/// Decompress one public key into a point in G1.
pub fn prepare_milagro_pubkey(pubkey: &PublicKey) -> Result<PublicKeyPrepared, BlsError> {
	PublicKeyPrepared::from_bytes(&pubkey.0).map_err(|_| BlsError::InvalidPublicKey)
}

/// Prepare for G1 public keys.
pub fn prepare_g1_pubkeys(pubkeys: &[PublicKey]) -> Result<Vec<PublicKeyPrepared>, BlsError> {
	pubkeys
		.iter()
		// Deserialize one public key from compressed bytes
		.map(prepare_milagro_pubkey)
		.collect::<Result<Vec<PublicKeyPrepared>, BlsError>>()
}

/// Prepare for G1 AggregatePublicKey.
pub fn prepare_aggregate_pubkey_from_absent(
	aggregate_key: &PublicKeyPrepared,
	absent_pubkeys: &Vec<PublicKeyPrepared>,
) -> Result<AggregatePublicKey, BlsError> {
	let mut aggregate_pubkey = AggregatePublicKey::from_public_key(aggregate_key);
	if !absent_pubkeys.is_empty() {
		let absent_aggregate_key = prepare_aggregate_pubkey(absent_pubkeys)?;
		aggregate_pubkey.point.sub(&absent_aggregate_key.point);
	}
	Ok(AggregatePublicKey { point: aggregate_pubkey.point })
}

/// Prepare for G2 AggregateSignature, normally more expensive than G1 operation.
pub fn prepare_aggregate_signature(signature: &Signature) -> Result<AggregateSignature, BlsError> {
	Ok(AggregateSignature::from_signature(
		&SignaturePrepared::from_bytes(&signature.0).map_err(|_| BlsError::InvalidSignature)?,
	))
}

/// fast_aggregate_verify_pre_aggregated which is the most expensive call in beacon light client.
pub fn fast_aggregate_verify_pre_aggregated(
	agg_sig: AggregateSignature,
	aggregate_key: AggregatePublicKey,
	message: H256,
) -> Result<(), BlsError> {
	ensure!(
		agg_sig.fast_aggregate_verify_pre_aggregated(&message[..], &aggregate_key),
		BlsError::SignatureVerificationFailed
	);
	Ok(())
}

      ### snowbridge: harden BLS public key deserialization
      
      Defense-in-depth: validate all cryptographic inputs.
      
      The Merkle proof binding means the public keys must match exactly what the Ethereum beacon chain committed. Since the beacon chain itself enforces G1 subgroup membership for validator keys, invalid subgroup points cannot appear in honest beacon chain state.

This is negligible compared to the BLS signature verification that occurs on every update. So just check it as defense-in-depth.
