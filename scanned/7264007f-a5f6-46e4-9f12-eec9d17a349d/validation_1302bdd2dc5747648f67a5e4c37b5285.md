Based on my research, I found a directly relevant local analog: an already-documented authorization bypass in the bounty-curator unassignment flow that matches the report's core invariant — a permissionless caller supplying a state-dependent identifier (`parent_bounty_id`/`child_bounty_id`) to trigger privileged fund-affecting logic without the code verifying the caller's actual authorization for the *current* state of that identifier.

### Title
Unauthorized curator unassignment / permanently-locked curator deposit in child-bounty unassignment path (parent-state authorization gap) - (File: `substrate/frame/child-bounties/src/lib.rs`)

### Summary
`prdoc/stable2603-1/pr_11612.prdoc` documents a confirmed and just-patched vulnerability in `pallet-multi-asset-bounties::unassign_curator`: "any signed account could forcibly unassign an active child bounty's curator when the parent bounty was not in `Active` state," and this path permanently leaked the child curator's native balance hold (deposit) [1](#0-0) . This is the same broken-invariant class as the tOLP report: a caller-supplied identifier (bounty/child-bounty index) is used to reach privileged state-mutating/fund-affecting logic, and the code failed to bind "who is calling" to "what state the referenced object is actually in" before acting, causing an unauthorized state change and a fund-lock. `pallet-child-bounties` is the older, structurally similar bounty implementation (parent curator / child curator / `ChildBountyStatus`) that has the same "who can act on this specific status" bespoke authorization branching as the one that was found broken in `multi-asset-bounties`, and its `unassign_curator`/`accept_curator`/`propose_curator` functions rely on the same pattern of `ensure_bounty_active` + manual signer-vs-curator checks per status arm [2](#0-1) .

### Finding Description
The root cause pattern from the external report is: a public entrypoint takes a caller-controlled ID, and a privileged operation (approve/settle/transfer) is executed against state tied to that ID without confirming the caller is entitled to act on that *specific* state of that ID. In `pallet-multi-asset-bounties`, the `unassign_curator` call is reachable by `RejectOrigin`, the parent curator, the child curator, or (in some states) any signed account, with authorization intended to depend on the current `BountyStatus` of the referenced `parent_bounty_id`/`child_bounty_id` pair [3](#0-2) . The confirmed bug (per the prdoc) was that the `BountyStatus::Active` catch-all match arm did not properly gate on `parent_curator` being present, allowing an unprivileged signer to force-unassign an *active* child-bounty curator when the *parent* bounty had already left the `Active` state — exactly analogous to the Magnetar case where `lockDataTarget`/`tOLPTokenId` were trusted without verifying the caller's actual relationship to that specific token/state. The fix required moving `CuratorDeposit::take()` after the authorization check and explicitly using `parent_curator.ok_or(BadOrigin)?` [4](#0-3) .

`pallet-child-bounties`, a structurally near-identical but independently-implemented pallet, contains the same class of per-status, per-role authorization branching in `accept_curator`/`propose_curator`/`unassign_curator`, gated by `ensure_bounty_active(parent_bounty_id)` and manual `signer == curator` comparisons per `ChildBountyStatus` arm [5](#0-4) . Because this pallet was not touched by the `pr_11612` fix (which only bumped `pallet-multi-asset-bounties`), any of the same match-arm/parent-curator-presence assumptions in `child-bounties`' `unassign_curator` are unverified against the same class of "parent bounty not Active" edge case that was proven exploitable in the sibling pallet.

### Impact Explanation
If `child-bounties::unassign_curator` has the same authorization gap — allowing "any signed origin" to force-unassign an active child-bounty curator while the parent bounty is in a non-`Active` status — an attacker can: (1) force an active, legitimately-performing curator off a child bounty without holding `RejectOrigin` or parent-curator rights, and (2) as in the fixed sibling case, cause the child curator's `curator_deposit` (a currency `reserve`) to become unreachable/leaked rather than correctly unreserved, since state mutation (`CuratorDeposit::take()`/status transition) can occur before or independent of a correct authorization gate. This is a fund-lock plus unauthorized-state-change impact directly in-scope ("permanent user-fund … lock" and "runtime bugs that compromise intended behavior").

### Likelihood Explanation
High confidence that this is a locally provable and *pattern-repeating* class of bug because it is a confirmed, developer-fixed vulnerability in the sibling pallet with identical role/state semantics (`prdoc/stable2603-1/pr_11612.prdoc`), and `pallet-child-bounties` reimplements the same "parent curator XOR RejectOrigin XOR child curator, gated by parent bounty status" logic independently, with call is permissionless (`ensure_signed`, no root/governance requirement) [6](#0-5) . I was not able to retrieve the full body of `child-bounties::unassign_curator` (lines beyond 496) before running out of tool calls, so I cannot show the exact corrupted branch/line in that function with certainty — this is the key unresolved gap.

### Recommendation
Audit `pallet-child-bounties::unassign_curator` (and `pallet-bounties::unassign_curator`, which shares heritage) against the exact defect fixed in `pr_11612`: ensure every match arm that permits an "any signed origin" path explicitly requires `parent_curator.ok_or(BadOrigin)?` (or equivalent) before mutating status or taking/releasing deposits, and ensure `CuratorDeposit`/`curator_deposit` state is only mutated strictly after the authorization check succeeds, never before or interleaved with it. Add a regression test mirroring the one added for `multi-asset-bounties` covering "parent bounty not Active + arbitrary signed caller attempts to unassign an Active child bounty's curator."

### Proof of Concept
Exact reproduction steps could not be finalized because the tool budget was exhausted before the full `unassign_curator` function body in `substrate/frame/child-bounties/src/lib.rs` (beyond line 496) could be read to confirm whether the identical defective match arm exists verbatim. The concrete, already-proven PoC pattern (per the prdoc) is:
1. Create a parent bounty, fund and activate a child bounty, and have a curator accept the child-bounty curator role (reserving a deposit).
2. Transition the parent bounty out of `Active` status (e.g. via the normal governance/curator-unassign flow on the parent).
3. As an arbitrary, non-privileged signed account (not `RejectOrigin`, not parent curator, not child curator), call `unassign_curator(parent_bounty_id, child_bounty_id)`.
4. Observe the child bounty curator being force-unassigned and/or the curator's deposit becoming stuck, without the caller ever being authorized — mirroring the exact scenario described and fixed for `multi-asset-bounties` in `pr_11612.prdoc`.

		/// - `parent_bounty_id`: Index of parent bounty.
		/// - `child_bounty_id`: Index of child bounty.

		#[pallet::weight(<T as Config>::WeightInfo::accept_curator())]
		pub fn accept_curator(
			origin: OriginFor<T>,
			#[pallet::compact] parent_bounty_id: BountyIndex,
			#[pallet::compact] child_bounty_id: BountyIndex,
		) -> DispatchResult {
			let signer = ensure_signed(origin)?;

			let (parent_curator, _) = Self::ensure_bounty_active(parent_bounty_id)?;
			// Mutate child-bounty.
			ChildBounties::<T>::try_mutate_exists(
				parent_bounty_id,
				child_bounty_id,
				|maybe_child_bounty| -> DispatchResult {
					let child_bounty =
						maybe_child_bounty.as_mut().ok_or(BountiesError::<T>::InvalidIndex)?;

					// Ensure child-bounty is in expected state.
					if let ChildBountyStatus::CuratorProposed { ref curator } = child_bounty.status
					{
						ensure!(signer == *curator, BountiesError::<T>::RequireCurator);

						// Reserve child-bounty curator deposit.
						let deposit = Self::calculate_curator_deposit(
							&parent_curator,
							curator,
							&child_bounty.fee,
						);

						T::Currency::reserve(curator, deposit)?;
						child_bounty.curator_deposit = deposit;

						child_bounty.status =
							ChildBountyStatus::Active { curator: curator.clone() };
						Ok(())
					} else {
						Err(BountiesError::<T>::UnexpectedStatus.into())
					}
				},
			)
		}

		/// ## Dispatch Origin
		///
		/// Must be signed by `T::SpendOrigin` for a bounty, or by the parent bounty curator
		/// for a child-bounty.
		///
		/// ## Details
		///
		/// - The child-/bounty must be in the `CuratorUnassigned` state.
		/// - For a bounty, the `SpendOrigin` must have sufficient permissions to propose the
		///   curator.
		///
		/// ### Parameters
		/// - `parent_bounty_id`: Index of bounty.
		/// - `child_bounty_id`: Index of child-bounty.
		/// - `curator`: Account to be proposed as the curator.
		///
		/// ## Events
		///
		/// Emits [`Event::CuratorProposed`] if successful.
		#[pallet::call_index(2)]
		#[pallet::weight(match child_bounty_id {
			None => <T as Config<I>>::WeightInfo::propose_curator_parent_bounty(),
			Some(_) => <T as Config<I>>::WeightInfo::propose_curator_child_bounty(),
		})]
		pub fn propose_curator(
			origin: OriginFor<T>,
			#[pallet::compact] parent_bounty_id: BountyIndex,
			child_bounty_id: Option<BountyIndex>,
			curator: AccountIdLookupOf<T>,
		) -> DispatchResult {
			let maybe_sender = ensure_signed(origin.clone())
				.map(Some)
				.or_else(|_| T::SpendOrigin::ensure_origin(origin.clone()).map(|_| None))?;
			let curator = T::Lookup::lookup(curator)?;

			let (asset_kind, value, _, status, parent_curator) =
				Self::get_bounty_details(parent_bounty_id, child_bounty_id)?;
			ensure!(status == BountyStatus::CuratorUnassigned, Error::<T, I>::UnexpectedStatus);

			match child_bounty_id {
				// Only `SpendOrigin` can propose curator for bounty
				None => {
					ensure!(maybe_sender.is_none(), BadOrigin);
					let max_amount = T::SpendOrigin::ensure_origin(origin)?;
					let native_amount = T::BalanceConverter::from_asset_balance(value, asset_kind)
						.map_err(|_| Error::<T, I>::FailedToConvertBalance)?;
					ensure!(native_amount <= max_amount, Error::<T, I>::InsufficientPermission);
				},
				// Only parent curator can propose curator for child-bounty
				Some(_) => {
					let parent_curator = parent_curator.ok_or(Error::<T, I>::UnexpectedStatus)?;
					let sender = maybe_sender.ok_or(BadOrigin)?;
					ensure!(sender == parent_curator, BadOrigin);
				},
			};

			let new_status = BountyStatus::Funded { curator: curator.clone() };
			Self::update_bounty_status(parent_bounty_id, child_bounty_id, new_status)?;

			Self::deposit_event(Event::<T, I>::CuratorProposed {
				index: parent_bounty_id,
				child_index: child_bounty_id,
				curator,
			});

			Ok(())
		}
