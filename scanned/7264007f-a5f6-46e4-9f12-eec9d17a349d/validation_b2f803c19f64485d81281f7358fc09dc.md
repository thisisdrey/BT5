### Title
PSM `mint`/`redeem` credit internal debt and mint tokens based on the nominal transfer amount instead of the actual balance delta moved into/out of the PSM reserve - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
`pallet-psm`'s `mint()` and `redeem()` extrinsics move external collateral via `T::Fungibles::transfer(...)` and then unconditionally update `PsmDebt` and mint/burn the internal stablecoin based on the *requested* amount, discarding the `Result<Balance, _>` returned by `transfer`. This mirrors the reported Solidity bug class exactly: crediting internal accounting from the nominal/requested amount rather than verifying the actual pre/post balance delta of the receiving account.

### Finding Description
In `mint()`, the pallet computes `effective_external` (the amount that should leave the caller) and calls: [1](#0-0) 
The transfer's returned value (the actual amount moved) is never captured or compared against `effective_external`; the code proceeds to `mint_into` the user and later records `PsmDebt` growth by the full `internal_equivalent`, assuming the reserve (`psm_account`) received exactly `effective_external`.

The same pattern repeats in `redeem()`, where `external_out` is transferred from `psm_account` to the user and `PsmDebt` is decremented by `effective_internal_net` without validating the actual amount that left the reserve: [2](#0-1) 

The underlying `fungible::Mutate::transfer` default implementation that many `Fungibles`/`Fungible` adapters rely on does not guarantee the returned value reflects an exact balance delta — it performs a `BestEffort` decrease and a `BestEffort` increase internally, yet always returns the *requested* `amount`: [3](#0-2) 
Because `mint`/`redeem` treat a successful `transfer()` call as proof that the full nominal amount landed (or left), any asset-backend behavior that legitimately moves a different amount than requested (e.g. `BestEffort` dust-sweep edge cases at `Preservation::Expendable`, or a `Fungibles` implementation whose `transfer` semantics diverge from "exact") breaks the PSM's collateralization invariant: internal debt/minted supply is recorded as backed by `effective_external`, while the reserve's actual holdings of `external_asset` may be less.

### Impact Explanation
If the actual amount credited to `psm_account` (mint) or debited from it (redeem) diverges from the nominal amount used to update `PsmDebt`/mint the internal asset, the PSM becomes under-collateralized: users can end up holding internal stablecoin balances not fully backed by real external reserve, i.e. unbacked mint — directly matching the "theft or unbacked mint" impact class for asset accounting pallets.

### Likelihood Explanation
Likelihood is low-to-moderate: exploiting this requires an `external_asset`/`Fungibles` implementation whose `transfer` can legitimately return success while moving less than the requested amount without erroring — a condition that is architecture-dependent and not guaranteed to be reachable with the standard `pallet-assets`/`pallet-balances` backends under normal conditions, since `can_withdraw`/`can_deposit` are checked immediately before the mutation in the same atomic call. It becomes exploitable primarily when a non-standard `Fungibles` implementation (e.g. a wrapped/foreign-asset adapter) is plugged in as the external asset backend.

### Recommendation
In both `mint()` and `redeem()`, capture the `Balance` returned by every `T::Fungibles::transfer`/`mint_into`/`burn_from` call and assert it equals the expected nominal amount before updating `PsmDebt` or crediting the user; alternatively, snapshot `T::Fungibles::balance(asset, &psm_account)` before and after the transfer and use the actual delta to compute the debt/mint amounts, matching the "check pre/post balance" remediation from the original report.

### Proof of Concept
1. Register an `external_asset` backed by a `Fungibles` implementation whose `transfer()` can return `Ok(amount)` while moving less than `amount` into the destination (e.g. a custom adapter following the default `fungible::Mutate::transfer` pattern shown above under a `BestEffort` edge case).
2. Call `Psm::mint(origin, internal_asset, external_asset, external_amount, max_fee)`.
3. Observe: `PsmDebt` increases by the full `internal_equivalent` and the caller receives `internal_to_user` of the internal asset, while `psm_account`'s actual `external_asset` balance increase is less than `effective_external` — the PSM's collateral is now short by the undelivered difference, producing unbacked internal-asset supply.

	fn transfer(
		source: &AccountId,
		dest: &AccountId,
		amount: Self::Balance,
		preservation: Preservation,
	) -> Result<Self::Balance, DispatchError> {
		let _extra = Self::can_withdraw(source, amount).into_result(preservation != Expendable)?;
		Self::can_deposit(dest, amount, Extant).into_result()?;
		if source == dest {
			return Ok(amount);
		}

		Self::decrease_balance(source, amount, BestEffort, preservation, Polite)?;
		// This should never fail as we checked `can_deposit` earlier. But we do a best-effort
		// anyway.
		let _ = Self::increase_balance(dest, amount, BestEffort);
		Self::done_transfer(source, dest, amount);
		Ok(amount)
	}
