Target: `WalletImpl::resolve_auth` (NEP-641 `AuthResolver::w_resolve_auth`), `WalletAuthorization::Signature` branch. Attacker action: attacker submits `authorization` JSON encoding `WalletAuthorization::Signature{msg: OffchainMessage{signer_id: victim_wallet, chain_id: "mainnet", path: [], payload: "malicious_payload"}, proof: reused_proof}` where `reused_proof` was originally signed for a DIFFERENT `path`. Preconditions: attacker previously observed one signature over some path P1. Call sequence: `resolve_auth` checks `msg.path != path` (the caller-supplied `path: Vec<AccountId>` argument) — verify this rejects mismatched paths and that `path` argument itself cannot be spoofed by the caller of `w_resolve_auth` to match whatever `msg.path` the attacker chose. Binding: the `path` argument the resolving caller supplied == `msg.path` inside the signed offchain message, exactly, for every accepted `AuthorizationResolution`. Impact: Critical, an authorization resolved for the wrong call-path lets a payload be authorized outside its intended context, causing balance moves the signer did not scope. Proof idea: cargo test calling `w_resolve_auth(path=[other_contract], authorization=sig_for_path=[fee_collector])`, asserting `Error::InvalidPath` and `AuthorizationResolution` not returned.
