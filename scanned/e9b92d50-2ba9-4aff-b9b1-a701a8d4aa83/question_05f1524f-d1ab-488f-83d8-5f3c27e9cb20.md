Target: `CachedState::internal_add_balance`, called via wallet's external promise resolving a Verifier deposit callback (`ft_on_transfer` style) that ultimately credits the wallet's account. Attacker action: attacker deploys a malicious FT contract, deposits into the Verifier naming the WALLET as receiver with `msg` crafted so the resulting credited `TokenId` collides with (i.e. is constructed identically to) an existing legitimate `TokenId` the wallet already holds real value in, then triggers the wallet's extension path to withdraw using the legitimate `TokenId`'s accumulated (inflated) balance. Preconditions: wallet holds real balance B of `Nep141TokenId(token=legit_token)`; attacker's FT contract account id is crafted so `Nep141TokenId::new(attacker_token)` string-encodes identically to `legit_token`'s `TokenId` (verify `TokenId` construction from `AccountId` cannot collide for distinct contract accounts). Call sequence: `internal_add_balance` -> `account.token_amounts.add(token_id.clone(), ...)` credits under the (possibly colliding) `TokenId`; later `ft_withdraw`/`internal_sub_balance` debits the SAME `TokenId` believing it's backed by `legit_token`. Binding: the `(contract, token)` a `TokenId` names == the asset actually moved/credited, i.e. no two distinct NEP-141 contracts ever produce an equal `TokenId`. Impact: Critical, a `TokenId` collision would let a worthless attacker-issued token inflate a balance redeemable against real, valuable token reserves. Proof idea: cargo test constructing `Nep141TokenId::new` for two different `AccountId`s crafted to attempt collision (e.g. via punycode/case tricks) and asserting the resulting `TokenId`s are never equal.
