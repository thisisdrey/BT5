Target: `WalletImpl::w_resolve_auth` return value consumed by an external caller (e.g. Verifier's `AuthCall` intent) — cross-check with `AuthResolver`/`AuthorizationResolution` NEP-641 contract. Attacker action: attacker names their OWN wallet contract as the target of a Verifier `AuthCall{contract_id: attacker_wallet, ...}` intent inside a signed `MultiPayload`, where `attacker_wallet`'s `w_resolve_auth` is fully attacker-controlled (attacker deploys their own `WalletImpl`) and can return `AuthorizationResolution::new(arbitrary_payload)` for ANY `signer_id`/`path` without verifying anything, since the resolver logic lives in the CALLEE not the Verifier. Preconditions: attacker deploys own wallet contract implementing `AuthResolver` trivially returning success for all inputs. Call sequence: Verifier's `*_resolve_*` callback trusts the return of `w_resolve_auth` from whatever `contract_id` the ORIGINAL signer named in `AuthCall` — verify the Verifier itself, not the callee, is the one enforcing that the resolution's `signer_id`/authorized payload actually corresponds to the ORIGINAL intent signer, so a malicious `contract_id` cannot forge resolution for accounts it doesn't own. Binding: an `AuthorizationResolution` is accepted by the Verifier only if it resolves the payload for the `signer_id` that SIGNED the enclosing `MultiPayload`'s `AuthCall` intent, == the account whose balance is being debited, never an arbitrary `contract_id`'s self-declared success. Impact: Critical, if the Verifier trusts any `contract_id`-returned resolution unconditionally, an attacker's own trivial wallet contract could authorize moves of a DIFFERENT signer's funds. Proof idea: near-workspaces test with two accounts — deploy attacker's own no-op `AuthResolver`-returning-always-true wallet as `contract_id` in an `AuthCall` intent signed by a DIFFERENT victim signer_id, and assert the Verifier's resolve callback rejects the resolution because it doesn't match the enclosing intent's actual `signer_id`.
