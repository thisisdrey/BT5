Target: `CachedState::internal_sub_balance` / `internal_add_balance` (contracts/defuse/core/src/engine/state/cached.rs), invoked as the balance-effecting result of a wallet-authorized `Request`. Attacker action: attacker, as a registered wallet extension, submits a `Request{internal: [], external: [promise calling Verifier ft_withdraw for wallet's own balance to attacker's account]}` sized so the wallet's cached `token_amounts.sub` underflows/overflows across two chained calls within one batch. Preconditions: wallet's cached balance for `TokenId` T is B; attacker submits two overlapping `internal_sub_balance` calls (e.g. via two separate wallet ops in the same `execute_request` loop) each requesting `B` so the second must fail. Call sequence: first `sub` succeeds bringing balance to 0; second `sub` calls `account.token_amounts.sub(token_id, amount)` which must return `None`→`Err(DefuseError::BalanceOverflow)` on going negative. Binding: sum of all `token_balances` deltas for token T across the whole `Request`/batch == the net signed-for amount; balance can never go negative. Impact: Critical, a negative-balance escape would let wallet extension debit more than it holds, breaking conservation for the Verifier. Proof idea: cargo test calling `internal_sub_balance` twice with amounts summing to more than the initial cached/view balance, asserting the second call errors and no negative `token_amounts` entry results.
