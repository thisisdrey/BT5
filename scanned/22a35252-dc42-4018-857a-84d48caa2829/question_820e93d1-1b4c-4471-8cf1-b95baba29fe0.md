Target: `SignatureSchema::verify_request_msg` for `WalletEd25519` vs `webauthn-p256`/`webauthn-ed25519` variants (`contracts/wallet/signatures/*/src/lib.rs`). Attacker action: attacker who knows the `RequestMessage::hash()` domain-separated digest for one schema variant attempts to replay a proof crafted for a DIFFERENT schema variant (e.g. submitting a `webauthn-p256` `authenticatorData`+`clientDataJSON`-derived proof string to a wallet deployed with the `ed25519` schema) hoping the generic `String` proof type is accepted without schema-specific structural validation. Preconditions: attacker has any validly-formatted proof string from a different schema for the same signer's public key material (not the private key). Call sequence: `execute_signed` -> `S::verify_request_msg(&self.0.public_key, &msg, proof)` where `S` is fixed at compile time per deployed contract variant. Binding: the schema `S` used to verify == the schema the owner's `public_key` type corresponds to; a proof valid under a different schema must not verify. Impact: Critical if cross-schema proof confusion lets an invalid signature pass. Proof: cargo test feeding a webauthn-shaped proof string into `WalletEd25519::verify_request_msg` and asserting it returns false.
