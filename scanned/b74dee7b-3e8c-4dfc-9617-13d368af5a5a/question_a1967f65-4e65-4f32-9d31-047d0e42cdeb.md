[trie_key.rs] Function: TrieKey::GlobalContractNonce{identifier} monotonicity vs TrieKey::GlobalContractCode{identifier} redeployment (idempotency check). Attacker action: deploy a global contract under GlobalContractIdentifier::AccountId(self) with nonce N, then rapidly resubmit DeployGlobalContract with the same or a replayed lower nonce via a duplicate/racing meta-transaction. Preconditions: attacker's own account_id used as the global contract identifier. Sequence: DeployGlobalContract -> code checks TrieKey::GlobalContractNonce{identifier} to decide whether to accept the new deployment -> on acceptance both GlobalContractNonce and GlobalContractCode rows are updated. Invariant: DETERMINISM - re-deployment must be rejected whenever the incoming nonce does not strictly exceed the stored TrieKey::GlobalContractNonce value, so global contract code referenced by other accounts cannot be swapped out-of-order. Scoped impact: if the nonce check reads GlobalContractNonce from a stale/prefetched value (see prefetch.rs's TrieKey handling) rather than the freshly committed value within the same chunk, an attacker could submit two DeployGlobalContract receipts in the same chunk that both pass the nonce check, causing nondeterministic final code selection across nodes (state-root divergence). Proof idea: apply-path test submitting two DeployGlobalContract receipts for the same identifier with nonces N and N+1 in the same chunk/block, and asserting every node deterministically ends with the N+1 code and TrieKey::GlobalContractNonce == N+1, not N.
