[trie_key.rs] Function: TrieKey::ReceivedData / TrieKey::PendingDataCount / TrieKey::PostponedReceipt cleanup ordering for a receipt with multiple input_data_ids. Attacker action: submit a FunctionCall receipt that generates several async data dependencies (e.g., multiple cross-contract calls awaited via promise_and) targeting the same receiver. Preconditions: deployed contract issuing several outgoing calls combined with promise_and, then only some data arriving before others. Sequence: as each DataReceipt arrives, TrieKey::ReceivedData is written and TrieKey::PendingDataCount is decremented; when it reaches zero, TrieKey::PostponedReceipt and TrieKey::PostponedReceiptId are removed and the ready receipt is dispatched. Invariant: VALUE_CONSERVATION - the postponed receipt must be dispatched exactly once, and after dispatch none of ReceivedData/PendingDataCount/PostponedReceipt/PostponedReceiptId rows for that receipt_id may remain in the trie (no residue that could re-trigger dispatch). Scoped impact: a leftover PostponedReceipt row plus a reset PendingDataCount could allow the same receipt to be re-postponed and re-executed by a later, unrelated DataReceipt to the same receiver (double execution / double-spend of its actions). Proof idea: apply-path integration test constructing a multi-input postponed receipt, letting it resolve, then asserting via trie inspection that all four TrieKey rows for that receipt_id are absent, and that a subsequent unrelated DataReceipt to the same receiver_id/data_id space cannot re-trigger the already-dispatched receipt.
