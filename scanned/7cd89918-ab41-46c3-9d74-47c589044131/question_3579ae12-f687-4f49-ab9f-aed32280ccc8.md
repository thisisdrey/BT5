Target: `TokenIdType` (`strum::EnumString`, `serialize_all = "snake_case"`) parsing the type prefix in `TokenId::from_str`. Attacker crafts an NFT/MT token whose sub-token id string begins with a valid type keyword followed by a colon, e.g. depositing under contract `x.near` with `nft_token_id = "nep141:y.near"`, so the outer `TokenId::Nep171(Nep171TokenId{contract_id:"x.near", nft_token_id:"nep141:y.near"})` displays as `"nep171:x.near:nep141:y.near"`. They then submit a signed withdraw intent that a naive downstream parser (splitting only once instead of using `TokenId::from_str` from the start) misreads by skipping the true `"nep171:x.near:"` prefix and treating the remainder `"nep141:y.near"` as a standalone `TokenId::Nep141(Nep141TokenId::new("y.near"))`. Precondition: a victim already has a real `TokenId::Nep141(Nep141TokenId::new("y.near"))` balance. Call sequence: crafted deposit -> any resolver/event path doing a second independent `.parse()` on a substring of the full id. Binding: the `(contract, token)` recovered by every parser in the codebase for a given stored key must be identical to the `(contract, token)` recovered by `TokenId::from_str` on the canonical `.to_string()`. Impact: Critical, misparse would let the attacker's crafted NFT be treated as a claim on `y.near`'s NEP-141 balance. Proof idea: cargo test feeding the crafted string into every `.parse::<TokenId>()` call site reachable from `mt_resolve_transfer` and `ft_on_transfer`, asserting they all agree with the canonical parse.
