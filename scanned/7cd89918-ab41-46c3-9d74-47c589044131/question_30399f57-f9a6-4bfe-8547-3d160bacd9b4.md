Target: `ImtTokenId::new(minter_id, token_id)` and its `Display`/`FromStr` in `crates/primitives/token-id/src/imt.rs`, reached via `imt::ImtTokens::into_generic_tokens` in `contracts/defuse/core/src/tokens.rs`. Attacker signs an `ImtMint` intent (`intents::imt::ImtMint`) minting an IMT sub-token whose `token_id` string equals another minter's account id plus a colon, e.g. `token_id = "othermint.near:5"`, while `minter_id` in the intent is the attacker's own account `attacker.near`. Precondition: `othermint.near` already minted `ImtTokenId{minter_id:"othermint.near", token_id:"5"}` with a nonzero balance owed to some account. Call sequence: `ImtMint` intent -> `into_generic_tokens` -> `ImtTokenId::new(minter_id, token_id).into()` -> credited into `token_balances`. Binding: `ImtTokenId{minter_id:"attacker.near", token_id:"othermint.near:5"}.to_string() != ImtTokenId{minter_id:"othermint.near", token_id:"5"}.to_string()` must hold. Impact: Critical, if the two ever produce equal strings the attacker mints into the othermint's balance slot without othermint's signature. Proof idea: cargo test comparing both `Display` outputs and asserting the resulting `TokenId` keys are distinct `BTreeMap` entries with independent balances.
