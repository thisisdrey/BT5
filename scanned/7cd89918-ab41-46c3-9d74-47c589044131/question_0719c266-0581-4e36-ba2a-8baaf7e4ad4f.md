Target: `TokenDiff` (`contracts/defuse/core/src/intents/token_diff.rs`) carrying `token_id.to_string()` inside a signed `MultiPayload`. Attacker signs their own `TokenDiff` intent naming a `TokenId` string for a token they do not actually hold, exploiting any code path in `token_diff.rs` that reconstructs the `TokenId` from the signed string via `FromStr` rather than validating it against the balances actually debited in the same batch. Precondition: attacker's account has zero balance of the named token but nonzero balance of a different token whose `Display` differs only by a crafted colon inside a controlled sub-token string on a contract they deployed. Call sequence: `execute_intents` -> `TokenDiff` applies deltas keyed by the re-parsed `TokenId` -> engine credits/debits based on string identity, not on which contract actually transferred value. Binding: `sum of all token_balances deltas for the token named by the TokenDiff's TokenId across the batch == 0` (CONSERVATION), and that `TokenId` must equal the asset attacker actually possesses. Impact: Critical, a mismatched `TokenId` string in a self-signed `TokenDiff` could let the attacker post a net-zero diff on paper while actually being net-positive on a colliding real asset. Proof idea: cargo test executing a `TokenDiff` intent with a crafted colliding token string and asserting the resulting balance delta for every real on-chain asset nets to zero relative to what was actually deposited/withdrawn.
