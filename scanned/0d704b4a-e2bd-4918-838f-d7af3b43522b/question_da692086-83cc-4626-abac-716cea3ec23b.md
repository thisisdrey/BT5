Target: WalletImpl::execute_signed hash/event emission ordering (contracts/wallet/src/contract.rs, `let hash = msg.hash(); WalletEvent::SignedRequest{hash}.emit(); self.execute_request(msg.request, ...)`). Attacker action: attacker submits a signed Request whose internal ops legitimately pass all checks up to signature verification, but whose `execute_request` call panics partway through executing `external` NearPromise actions (e.g. build_promise returns Err for one of several promises) after some `internal` WalletOps (like SetSignatureMode) already mutated self.0 in-memory. Preconditions: Request contains both internal ops and external promises, one external promise references an unsupported NearAction (e.g. DeployContract). Call sequence: execute_request first applies ALL internal ops via the for-loop (mutating state), THEN iterates external promises and returns Err(Error::UnsupportedPromiseAction) on the bad one, propagating up through execute_signed as `err.panic()`, which reverts the ENTIRE receipt/state including the nonce commit and internal-op mutations (NEAR contract state changes are only persisted if the method returns without panicking). Binding: on any panic inside execute_signed, State::nonces/extensions/signature_enabled == the pre-call state (full atomicity), so no partial internal-op application survives while the external promise is rejected. Impact: Critical if partial state (e.g. nonce marked used, or SetSignatureMode toggled) persists despite the overall call panicking, corrupting the AUTHORISATION/REPLAY bindings for the next legitimate signed request. Proof idea: cargo test/near-workspaces test constructing a Request with a benign internal SetSignatureMode op plus an external NearPromise{receiver_id: self} that trips Error::SelfCallsNotAllowed, asserting the whole w_execute_signed call fails AND that w_is_signature_allowed()/nonce-used-state are unchanged from before the call.
