Preconditions: victim account V already holds token_balances > 0 in accounts map; attacker crafts a StateInit whose derive_account_id() == V (requires attacker to find/construct a global_contract_id + data combination hashing to V's AccountId, or V is itself a NEP-616 derived account the attacker can also derive with attacker-chosen code). Call sequence: execute_intents(AuthCall{contract_id: V, state_init: Some(colliding_state_init)}) -> do_auth_call -> Promise::state_init deploys/overwrites at V -> on_auth(signer_id, msg) executes with V's NEAR-level code now attacker controlled while V's Verifier-level token_balances remain intact. Binding: IDENTITY - the AccountId that on_auth() executes at == the AccountId the signer intended to call, and must not silently become an account with pre-existing custodied balances the attacker now controls at the NEAR-account level. Impact: Critical, attacker gains control of the NEAR account backing a Verifier-tracked balance holder. Proof: near-workspaces test constructing two StateInit values with different global_contract_id/data that both derive to the same target existing AccountId (or demonstrate the derivation determinism forces state_init to fail against a pre-existing account, proving no collision path — a negative-result proof is acceptable here).
