`TokenDiff::execute_intent` never checks whether `signer_id`'s account is locked before calling `engine.state.internal_apply_deltas`. Given the project context states intents must not execute against a locked account, can an unprivileged attacker who has caused their OWN account to enter a locked state (e.g. via a self-triggered lock intent earlier in the same batch, if such an intent exists and is signer-controllable) still get a LATER `TokenDiff` intent in the same `MultiPayload` (same `signer_id`, same batch) to execute and mutate `token_balances`, contradicting the lock the contract is supposed to enforce mid-batch? Binding: for a `signer_id` whose account is locked at the time a given intent index executes within `execute_intents`, that intent's `internal_apply_deltas` call must return `Err`, i.e. locked-state-at-execution-time == enforced for every intent index, not just checked once at batch start. Impact: High, intent executed against a locked account. Proof: cargo test constructing a `MultiPayload` with a lock intent followed by a `TokenDiff` from the same signer in the same batch, asserting the `TokenDiff` fails or the lock intent's effect is properly checked per-intent.
