### Title
`PGasDeposit::charge_and_hold` decides PGAS-vs-native funding on a stale balance snapshot, letting nested contract calls drain PGAS between the check and the transfer - ([File: substrate/frame/revive/src/deposit_payment.rs])

### Summary
`pallet-revive`'s PGAS-backed storage-deposit backend picks its funding source with the exact "check-then-use, otherwise silently switch source" pattern flagged in the Sushi report: it reads `pgas_reducible_balance(from)` once and, if it is `>= amount`, commits to charging entirely in PGAS; otherwise it falls back entirely to native currency and separately records the fallback in `NativeDepositOf`. Between that read and the actual `transfer_and_hold`, nested/re-entrant contract execution invoked by the very same call frame can change the payer's PGAS balance, so the branch taken no longer reflects the payer's real, current balance.

### Finding Description
`charge_and_hold` in `PGasDeposit` is invoked from `substrate/frame/revive/src/storage/meter.rs` while a contract call is being metered for storage deposits, i.e., mid-execution of a call stack that can contain nested calls into other contracts (including calls back into assets/pallets that can move PGAS). [1](#0-0) 

The check `Self::pgas_reducible_balance(from) >= amount` (lines 358) is taken as a binary decision: fully PGAS or fully native, with no re-validation immediately before the mutating calls that follow. `pgas_reducible_balance` itself is a plain `Inspect::reducible_balance` read with no lock: [2](#0-1) 

This mirrors the Sushi bug precisely: `_depositToBentoBox` decided ETH-vs-WETH based on a balance comparison computed at one point in time (`address(this).balance >= underlyingAmount`), and by the time the actual transfer executed, the real state had moved, so the wrong asset ended up being used/left behind. Here, the same "greater-or-equal snapshot decides funding source" logic governs whether a nested call's storage deposit is charged in PGAS or in DOT.

Storage-meter charges happen per call frame as the meter is nested (`enforce_subcall_limit`/`enforce_limit` in `substrate/frame/contracts/src/storage/meter.rs`, and the revive equivalent), and `TransactionMeter` invokes deposit charging potentially several times across a single transaction's call stack, i.e., across contract-to-contract calls, not just once at entry. A contract can therefore execute an inner call to another contract that consumes or moves its own PGAS (e.g., paying another contract, or triggering an unrelated hold/burn on PGAS such as `settle_pgas_refund`'s burn path) between the moment `charge_and_hold` samples `pgas_reducible_balance` for an *outer* frame's deposit and the moment that outer frame's deposit is actually applied on unwind. Because Substrate/PolkaVM execution for a single extrinsic is not one atomic snapshot read followed immediately by one atomic write — deposit charges are interleaved with arbitrary further dispatch (nested calls, `Transact`, cross-contract calls) inside the same transaction — the balance used to pick the branch can be stale by the time the mutating operation executes.

### Impact Explanation
If the PGAS branch is taken based on a stale "sufficient" reading but the balance has since dropped, `transfer_and_hold` (with `Precision::Exact`) will hard-fail and abort the whole extrinsic — a denial-of-service on that call, not a silent fund-loss by itself. The more consequential half of the analog is the *native fallback* branch: when the check reports PGAS as insufficient (even though it may have just become sufficient again, or vice versa) the code unconditionally shifts the **entire** `amount` to native currency and records the entire amount into `NativeDepositOf` via `record_native_deposit`, exactly like the Sushi bug's "ignore whatever ETH is available and pull the full amount from WETH instead." This can cause the account to be charged/held in DOT (potentially against a payer with thin native liquidity) when a fraction or all of it should have come from PGAS, and it inflates `NativeDepositOf[to][from]`, which is the accounting map that later caps how much of a refund can be returned in native currency — a corrupted attribution here skews future storage-deposit refunds between PGAS and native for that contributor.

### Likelihood Explanation
The attacker primitive required is only "deploy/call a contract with nested calls that manipulate its own PGAS balance during its own storage-deposit-metered execution" — no privileged actor, relayer, governance action, or malicious validator is needed. However, exploiting this into a strictly beneficial fund-theft (rather than a self-inflicted DoS/branch-misattribution) requires precise control over nested call ordering and PGAS balance timing within one extrinsic, which is a non-trivial but plausible construction for an unprivileged EVM/PolkaVM contract author on a chain that has opted into the PGAS-backed deposit backend (`PGasDeposit` is optional per-runtime configuration, not the default `()` backend).

### Recommendation
Re-check `pgas_reducible_balance(from) >= amount` immediately before performing `transfer_and_hold`, ideally within the same atomic mutation (e.g., using `MutateHold::transfer_and_hold` with `Precision::BestEffort` plus a post-hoc actual-amount reconciliation, or re-querying balance right at the point of transfer under a `with_transaction` guard) rather than branching once far ahead of the mutating call. Alternatively, split the charge so any *actually available* PGAS is applied first (up to what is truly reducible at the moment of transfer) and only the shortfall is charged to native, instead of an all-or-nothing branch driven by a possibly stale snapshot — mirroring the report's own recommendation to use available ETH first and top up with WETH only for the remaining difference.

### Proof of Concept
Conceptual PoC (requires a runtime configured with `Deposit = PGasDeposit<...>`):
1. Deploy contract `A` with PGAS balance exactly at the threshold needed for its own storage deposit charge (`pgas_reducible_balance(A) == amount`).
2. `A`'s constructor/call, before triggering the storage-deposit charge for its own frame, performs a nested call to contract `B` that causes `A` to spend/transfer away some of its PGAS (e.g., `A` pays `B` in PGAS, or triggers a `PGasDeposit::refund_on_hold`/`settle_pgas_refund` burn on `A`'s own PGAS hold from an unrelated reason).
3. When the storage meter later calls `PGasDeposit::charge_and_hold` for `A`'s frame, the snapshot check may pass or fail against a `pgas_reducible_balance(A)` value from before step 2 executed, depending on measurement ordering within the nested `TransactionMeter` bookkeeping, causing either a spurious `transfer_and_hold` failure (abort) or an unwarranted full native fallback that pollutes `NativeDepositOf[contract][A]` with the entire `amount` instead of the correct split.

Note: I was unable to fully trace the exact ordering/atomicity guarantees between `TransactionMeter`'s postponed-deposit execution (`execute_postponed_deposits`, referenced in `substrate/frame/revive/src/lib.rs`) and nested-call PGAS mutations from within this ask-only investigation; a background engineering session with full build/test access would be needed to confirm whether a concrete transaction can be constructed that flips the branch outcome and to quantify the resulting native/PGAS misattribution end-to-end.

	fn charge_and_hold(
		reason: HoldReason,
		src: Funds<T::AccountId>,
		to: &T::AccountId,
		amount: BalanceOf<T>,
	) -> DispatchResult {
		let from = match &src {
			Funds::Balance(from) | Funds::TxFee(from) => *from,
		};

		if Self::pgas_reducible_balance(from) >= amount {
			<Holder as fungibles::MutateHold<T::AccountId>>::transfer_and_hold(
				Id::get(),
				&reason.into(),
				from,
				to,
				amount,
				Precision::Exact,
				Preservation::Expendable,
				Fortitude::Polite,
			)?;
		} else {
			<() as Deposit<T>>::charge_and_hold(reason, src, to, amount)?;
			Self::record_native_deposit(from, to, amount);
		}

		Ok(())
	}
