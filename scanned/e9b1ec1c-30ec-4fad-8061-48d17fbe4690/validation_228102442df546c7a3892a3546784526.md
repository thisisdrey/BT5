## Analysis

The Sherlock report's core broken invariant: a price/exchange-rate value that determines whether economic terms (collateral vs. loan) are safe is **hard-coded / manually-set rather than continuously oracle-derived**, so it silently drifts out of sync with the real market rate, and nothing in the code enforces staleness bounds before the value is used to accept/settle a transaction.

The closest local analog in this repository is the Snowbridge outbound-queue delivery-fee mechanism, which uses a manually governance-set `exchange_rate` (ETH/DOT) that the pallet's own documentation says is updated "every few weeks," with no staleness check anywhere in the fee-calculation path that every unprivileged user's message passes through.

### Title
Stale/manually-set ETH/DOT `PricingParameters.exchange_rate` in Snowbridge outbound queue lets unprivileged users underpay delivery fees, causing public underpriced work that can stall relayer processing - (`bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
`Pallet::calculate_fee` converts the Ethereum-side delivery cost (gas × `fee_per_gas` + `reward`) into the local currency fee charged to the caller by dividing by `PricingParameters.exchange_rate`, a `FixedU128` value stored in `snowbridge-system`'s `PricingParameters` storage item and only refreshed manually via `set_pricing_parameters`. The module doc explicitly states this rate is expected to be updated "every few weeks" as an interim measure until an on-chain ETH/DOT liquidity pool exists. [1](#0-0) 

Every call to `SendMessage::validate` (invoked by any unprivileged user submitting an XCM export to Ethereum) computes the fee against whatever `exchange_rate` currently sits in storage, with no check on how long ago it was updated or how far it may have drifted from the real market rate. [2](#0-1) [3](#0-2) 

### Finding Description
`calculate_fee` performs:
```
fee = (gas_used_at_most * fee_per_gas + reward)  // in wei
fee = fee * multiplier / exchange_rate            // converted to local currency
``` [3](#0-2) 

`PricingParameters::validate()` only rejects a zero exchange rate, fee_per_gas, reward, or multiplier — it never checks freshness or bounds relative to a live price feed. [4](#0-3) 

The `multiplier` field is described as a "safety factor... to cover unfavourable fluctuations in the ETH/DOT exchange rate," which is the same class of mitigation the DAI/gOHM report's recommendation targets (an oracle-driven adjustment), but here it is itself a static, governance-set constant rather than something computed from live volatility. [5](#0-4) 

Because `exchange_rate`/`fee_per_gas`/`multiplier` are only refreshed manually and infrequently ("every few weeks"), any window in which the real ETH/DOT rate or ETH gas price moves unfavorably before the next manual update causes `calculate_fee` to systematically undercharge users relative to the actual relayer reward that must later be paid out in ETH on the Ethereum side (`Min(GasPrice, MaxFeePerGas) * GasUsed + Reward`). [6](#0-5) 

This mirrors the Sherlock finding precisely: a constant meant to encode an economic bound (`maxLTC` there, `exchange_rate`/fee formula here) is not tied to a live price source, and the guard that exists (`ltc > maxLTC` there; `PricingParameters::validate()` here) only checks for non-zero/sane values, not staleness — so any ordinary, unprivileged caller can transact under an out-of-date price without any admin action being the proximate cause of the exploit window.

### Impact Explanation
Because message senders are ordinary, unprivileged users (any parachain/XCM caller routing through `SendMessage::validate`), a stale `exchange_rate` directly produces "public underpriced work" in the sense of the Polkadot SDK Pivots: messages are accepted into the outbound queue and committed to Ethereum-bound merkle roots while paying less local-currency fee than the true ETH-denominated delivery cost requires. Over time this either drains the funds set aside to reward relayers or makes relaying unprofitable, causing relayers to stop delivering messages — i.e., it degrades block production/bridge throughput and can stall bridge processing, which is an explicitly in-scope impact category.

### Likelihood Explanation
No malicious peer, relayer, validator, or admin action is required to trigger the underlying condition — it arises purely from time passing between manual governance updates while real market prices for ETH/DOT and Ethereum gas move, which is stated by the module's own documentation to be expected behavior ("every few weeks"). Any user who sends a bridge message during such a window automatically pays the stale (and therefore incorrect) fee; this is a structural, always-present timing gap rather than a one-off misconfiguration.

### Recommendation
- Add a staleness bound (e.g., a `LastUpdated` block number or timestamp) to `PricingParameters`, and reject/pause `calculate_fee` (or force it to use a conservative fallback multiplier) once the parameters exceed a maximum age.
- Where feasible, source `exchange_rate` and `fee_per_gas` from a decentralized, continuously updated price feed instead of a manually-set storage value, consistent with the module's own stated long-term intent ("Once ETH/DOT liquidity pools are available... we'll use them as a source of pricing info").
- Add integrity checks in `PricingParameters::validate()` that compare newly-set values against bounded deviation from previous values to detect obviously stale or manipulated updates.

### Proof of Concept
1. Governance sets `PricingParameters { exchange_rate: R0, fee_per_gas: G0, multiplier: M0, rewards }` via `set_pricing_parameters`. [7](#0-6) 
2. Over subsequent weeks, the real ETH/DOT market rate and/or Ethereum gas price rises materially versus `R0`/`G0`, but governance has not yet issued a new `set_pricing_parameters` call (as documented, updates are only expected "every few weeks").
3. Any unprivileged user calls the XCM path that invokes `SendMessage::validate`, which calls `Self::calculate_fee(gas_used_at_most, T::PricingParameters::get())` using the stale `R0`/`G0`/`M0`. [8](#0-7) 
4. The returned `Fee.remote` (local-currency-denominated cost of the ETH-side reward/gas) is computed against the outdated rate and is charged to the user; the message is enqueued and later committed for relaying regardless of whether the collected fee actually covers the real ETH-denominated relayer payout. [9](#0-8) 
5. Repeated at scale by ordinary users during the stale window, this systematically underprices bridge delivery work, which — per the pallet's own fee-settlement model — either underfunds relayer rewards (causing relayers to stop servicing the queue) or drains bridge-held reward reserves, both of which stall bridge message processing.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

	pub fn validate(&self) -> Result<(), InvalidPricingParameters> {
		if self.exchange_rate == FixedU128::zero() {
			return Err(InvalidPricingParameters);
		}
		if self.fee_per_gas == U256::zero() {
			return Err(InvalidPricingParameters);
		}
		if self.rewards.local.is_zero() {
			return Err(InvalidPricingParameters);
		}
		if self.rewards.remote.is_zero() {
			return Err(InvalidPricingParameters);
		}
		if self.multiplier == FixedU128::zero() {
			return Err(InvalidPricingParameters);
		}
		Ok(())
	}
