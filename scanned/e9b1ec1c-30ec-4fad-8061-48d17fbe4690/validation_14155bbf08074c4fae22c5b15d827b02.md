## Analysis

The BetaFinance bug's core invariant break is: **using an undersized fixed-point scaling factor when computing a per-unit accrual rate causes integer-division truncation to permanently round legitimate value to zero**, especially when the denominator (a large stake/balance) dwarfs the scaling factor.

The closest local analog is in `substrate/frame/asset-rewards/src/lib.rs`, the FRAME Staking-Rewards pallet (Synthetix-style JIT reward accounting), which uses a scaling constant that is far too small for realistic 18-decimal-token stake sizes.## Finding

### Title
`asset-rewards` pallet's `PRECISION_SCALING_FACTOR` is too small, causing `reward_per_token` accrual to permanently round down to zero and lose staker rewards - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
The `pallet-asset-rewards` (FRAME Staking-Rewards) computes a per-token reward accumulator using a hardcoded scaling constant `PRECISION_SCALING_FACTOR: u16 = 4096` [1](#0-0)  . This scale (2^12 ≈ 4.1k) is orders of magnitude smaller than the balance precision typically in use (18-decimal fungible/LP tokens, i.e. 10^18), so `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked` truncates to zero whenever `total_tokens_staked` exceeds `reward_rate_per_block * blocks_elapsed * 4096`, which is the normal case for any moderately large pool. This is the same broken invariant as the external BetaFinance report: an undersized fixed-point scale combined with integer division causes legitimate accrual to be rounded to zero, and every public interaction (`stake`, `unstake`, `harvest_rewards`) persists the truncated value, so the lost precision is never recovered.

### Finding Description
`reward_per_token` computes the incremental reward-per-staked-token since the last update:
```rust
Ok(pool_info.reward_per_token_stored.ensure_add(
    pool_info
        .reward_rate_per_block
        .ensure_mul(rewardable_blocks_elapsed.into())?
        .ensure_mul(PRECISION_SCALING_FACTOR.into())?
        .ensure_div(pool_info.total_tokens_staked)?,
)?)
``` [2](#0-1) 

and `derive_rewards` converts that back into an absolute reward for a staker:
```rust
Ok(staker_info
    .amount
    .ensure_mul(reward_per_token.ensure_sub(staker_info.reward_per_token_paid)?)?
    .ensure_div(PRECISION_SCALING_FACTOR.into())?
    .ensure_add(staker_info.rewards)?)
``` [3](#0-2) 

Both operations are gated by the same `PRECISION_SCALING_FACTOR = 4096` [1](#0-0) . For an 18-decimal staked asset, `total_tokens_staked` for even a modest pool (e.g. 1,000 tokens) is `1000 * 10^18 = 10^21`. For the accumulator delta to be non-zero, `reward_rate_per_block * blocks_elapsed * 4096` must exceed `10^21`, i.e. `reward_rate_per_block * blocks_elapsed > 2.44 * 10^17`. With a reward rate of `10^12` (a tiny fraction of one 18-decimal token per block, a realistic configuration), this requires `blocks_elapsed > 244,000` — and every time `update_pool_and_staker_rewards` is invoked (via `stake`, `unstake`, or `harvest_rewards`, all of which are unprivileged public extrinsics) [4](#0-3) , the truncated `reward_per_token_stored` is persisted and `last_update_block` is reset [5](#0-4) , discarding the fractional remainder for good. Any staker (or third party performing griefing `stake`/`unstake` cycles on behalf of others, which the pallet permits for anyone once the pool has expired, or the staker themself for accidental self-harm) that interacts frequently enough will repeatedly reset the accumulation window before `rewardable_blocks_elapsed` accrues enough magnitude to survive the `/PRECISION_SCALING_FACTOR` truncation, causing reward funds that were deposited into the pool's reward account to never be attributed to any staker.

This mirrors the external report precisely: the external bug's `IRM_SCALE = 1e9` combined with `365 days` division caused `interestAmount` to round to zero for low-decimal tokens / short time deltas, and users could call `accrue()` repeatedly to avoid ever paying interest. Here, `PRECISION_SCALING_FACTOR = 4096` is even smaller in relative terms (12 bits vs. the ~30 bits used by `IRM_SCALE`), and the truncated intermediate state (`reward_per_token_stored`) is written back to storage on every call rather than being fixed at pool creation, so the loss compounds identically.

### Impact Explanation
This causes stakers to permanently lose rewards that the pool's `reward_asset_id` balance was funded to pay out — a form of value that is "conserved but not settled to the rightful beneficiary." Reward tokens remain locked in the pool account and, on `cleanup_pool`, get swept back to the pool `admin` rather than the stakers who should have earned them [6](#0-5) . This matches the "permanent user-fund…lock" / value-conservation-violation impact class in scope.

### Likelihood Explanation
This is triggerable by any unprivileged account through the ordinary `stake`/`unstake`/`harvest_rewards` extrinsics, no privileged actor, governance, or malicious peer/validator is required. It requires no unusual configuration beyond typical 18-decimal reward/staked assets and realistic reward rates, both of which are the pallet's expected use case (LP token staking incentive programs), making the precision-loss condition highly likely to occur in production rather than a contrived edge case.

### Recommendation
Increase `PRECISION_SCALING_FACTOR` to match the balance precision actually used (e.g., derive it from asset decimals or use a much larger fixed constant, such as `10^18` or a `FixedU128`-style accumulator as used in `pallet-nomination-pools`'s `RewardCounter` [7](#0-6) ), and/or carry forward the unresolved fractional remainder across calls instead of discarding it when persisting `reward_per_token_stored`.

### Proof of Concept
1. Create a pool with an 18-decimal `staked_asset_id` and `reward_rate_per_block = 10^12` via `create_pool` [8](#0-7) .
2. Have a staker `stake(pool_id, 1_000 * 10^18)` [9](#0-8) .
3. Advance fewer than ~244,000 blocks and call `harvest_rewards` or perform another `stake`/`unstake` action, which invokes `update_pool_and_staker_rewards` → `reward_per_token` [4](#0-3) .
4. Observe `reward_per_token()`'s computed delta is `0` due to integer division, and `reward_per_token_stored`/`last_update_block` get reset to reflect zero accrual for the elapsed window, permanently discarding those blocks' rewards.
5. Repeat step 3 periodically (analogous to the "call accrue every X minutes" trick in the original report) to indefinitely suppress reward accrual for the staked amount, while the pool's reward-asset balance remains funded and is later reclaimed by the admin via `cleanup_pool`.
