### Title
Unrecoverable Tip Funds Locked in `LostTips` When Inbound/Outbound Nonce Races Ahead of `add_tip` — (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

### Summary
The Connext report's broken invariant is: a protocol credits/withdraws value from a user in anticipation of a follow-up settlement step, but if that settlement step never completes, the funds are neither returned to the payer nor delivered to the intended beneficiary — they simply vanish into an unbacked, unresolved state that no code path ever repays. The local analog is Snowbridge's relayer-tip mechanism: `snowbridge_pallet_system_v2::Pallet::add_tip` records failed tip additions into a `LostTips` map that has no corresponding extrinsic or automatic mechanism to refund the user whose real funds were already withdrawn/burnt on the AssetHub side.

### Finding Description
`add_tip` in `bridges/snowbridge/pallets/system-v2/src/lib.rs` (lines 251-281) is the BridgeHub-side handler invoked (via `FrontendOrigin`) after a user on AssetHub has already had `amount` withdrawn from their account to fund a relayer tip for a specific inbound/outbound message nonce: [1](#0-0) 

If the target nonce has already been consumed by the time this call executes (a nonce is consumed the moment a relayer permissionlessly calls `submit`/`process_message`, independent of when the AssetHub-origin tip message arrives via XCM), `InboundQueue::add_tip`/`OutboundQueue::add_tip` return `AddTipError::NonceConsumed`: [2](#0-1) 

On this error, `system-v2::add_tip` does not revert or return an error to the caller — it swallows the failure and moves the `amount` into `LostTips<T>`, then returns `Ok(())`: [3](#0-2) 

The storage declaration itself documents the gap: [4](#0-3) 

"Capturing the lost tips here supports implementing a recovery method **in the future**" — i.e., at present there is no `claim_lost_tip`/refund extrinsic anywhere in this pallet, `bridges/modules/relayers`, or the snowbridge frontend pallets that reads `LostTips` and returns funds to `sender`. The value is permanently stranded in on-chain storage with no code path that ever moves it back to the user or forward to a relayer.

This is structurally identical to the AAVE Portal issue: the "loan" (the user's already-withdrawn tip funds) is expected to be repaid/settled by an out-of-band step (arrival of the XCM tip-registration before nonce consumption), but when that race is lost, nothing in the protocol enforces or provides the repayment/refund path — the funds are simply left in unbacked limbo (`LostTips`), exactly like Connext being left with unrepaid AAVE debt when the router chooses not to call `repayAavePortal`.

### Impact Explanation
Any user who adds a relayer tip for a message near the time it gets relayed will race against permissionless relayers who can call `submit` at any time. Because relaying is fully permissionless and asynchronous XCM delivery from AssetHub to BridgeHub is not instantaneous, this race is a normal, non-adversarial occurrence, not a crafted attack. When the race is lost, the user's already-withdrawn funds are added to `LostTips` and become permanently inaccessible — a "permanent user-fund lock," which is explicitly in-scope per the Impact Gate ("permanent user-fund or bridge-state lock"). At protocol scale, `LostTips` balances can only ever grow, representing value withdrawn from users that is unbacked by any redeemable claim.

### Likelihood Explanation
This does not require any privileged actor, governance action, or malicious relayer/prover — it happens whenever a nonce is naturally consumed before its associated tip-registration XCM lands, which is an ordinary timing condition in an asynchronous cross-chain system with permissionless message submission. The `ensure!(!Nonce::<T>::get(nonce.into()), AddTipError::NonceConsumed)` guard in `add_tip` (inbound-queue-v2) is precisely what triggers the lost-tip path rather than preventing it — the guard stops the tip from corrupting nonce/reward state, but does nothing to make the user whole.

### Recommendation
Add a signed extrinsic (e.g., `reclaim_lost_tip`) that allows the original `sender` recorded in `LostTips<T>` to withdraw their stranded balance back to their account (or have the `system-frontend` pallet forward it automatically via XCM once a `TipProcessed { success: false }` event is observed). Alternatively, before debiting the user on the frontend side, first confirm nonce liveness/finality with a bounded-time hold-and-release (escrow) pattern so that value is only burnt after confirmed non-consumption, mirroring the escrow-based remediation suggested in the original report.

### Proof of Concept
1. User on AssetHub calls the frontend extrinsic (proxied to `snowbridge-pallet-system-v2::add_tip`) to tip nonce `N`, and their account is debited `amount`.
2. Independently, any relayer calls `InboundQueue::submit` for message nonce `N` and it gets processed before the tip XCM arrives on BridgeHub — `Nonce::<T>::set(nonce)` marks `N` consumed (`bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs:222-225`).
3. The tip XCM subsequently executes `system-v2::add_tip(sender, Inbound(N), amount)`; `InboundQueue::add_tip` returns `Err(AddTipError::NonceConsumed)` (`inbound-queue-v2/src/lib.rs:248-258`).
4. `system-v2::add_tip` catches the error, moves `amount` into `LostTips::<T>::mutate(&sender, ...)`, emits `TipProcessed { success: false }`, and returns `Ok(())` (`system-v2/src/lib.rs:266-280`).
5. No extrinsic in the repository reads or drains `LostTips<T>` — the `amount` is permanently locked, confirmed by the code comment stating recovery is only a future possibility.

		#[pallet::call_index(3)]
		#[pallet::weight(<T as pallet::Config>::WeightInfo::add_tip())]
		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}

	impl<T: Config> AddTip for Pallet<T> {
		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			// If the nonce is already processed, return an error
			ensure!(!Nonce::<T>::get(nonce.into()), AddTipError::NonceConsumed);
			// Otherwise add the tip.
			Tips::<T>::mutate(nonce, |tip| {
				*tip = Some(tip.unwrap_or_default().saturating_add(amount));
			});
			return Ok(());
		}
