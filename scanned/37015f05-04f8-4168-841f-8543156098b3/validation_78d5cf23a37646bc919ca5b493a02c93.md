## Analysis

The Real Wagmi H-3 finding boils down to one core invariant break: **share/token minting math derives its price/amount inputs from a single, instantaneous, freely-writable state value (`slot0`) with no deviation check, so an attacker can move that value in the same block/transaction window and skew how many shares a victim receives.**

The direct local analog is in `pallet-asset-conversion`, Polkadot SDK's on-chain AMM. Its `do_add_liquidity` and `do_remove_liquidity` functions compute mint/redeem ratios directly from the live, unguarded balance of the pool's sovereign account — there is no internally-accounted "reserve" state, only a raw `Assets::balance` read, exactly like reading `slot0` instead of a TWAP. [1](#0-0) 

This `get_balance` helper is called to derive `reserve1`/`reserve2` inside `do_add_liquidity`, which then drives both the deposit-ratio calculation (`quote`) and, critically, the LP-token minting math (`side1`/`side2`/`lp_token_amount`): [2](#0-1) [3](#0-2) 

Because the pool account is a deterministic, publicly-derivable `PalletId` sub-account (`T::PoolLocator::address`), any unprivileged account can send a plain `transfer` directly to that account — bypassing `add_liquidity`/`swap` entirely — and thereby move `reserve1`/`reserve2` at will, immediately before a victim's `add_liquidity` transaction executes in the same block. This has the same effect as manipulating `slot0` in the Real Wagmi Multipool: the value used to compute a depositor's LP-token allocation is corrupted by a single, attacker-controlled data point read at call time, with no TWAP, no minimum-liquidity-change guard, and no price-deviation check comparable to the `_checkPriceDeviation` fix that resolved the original issue.

`do_remove_liquidity` has the identical pattern via `get_reserves`, which also just wraps `get_balance`: [4](#0-3) 

The only anti-manipulation mechanism present is `MintMinLiquidity`, which is solely an anti-first-depositor-inflation guard (mirroring Uniswap V2's `MINIMUM_LIQUIDITY` burn) — it does nothing to prevent an attacker from donating tokens to skew reserves for a *subsequent* depositor's ratio calculation once the pool already has liquidity: [5](#0-4) [6](#0-5) 

### Title
Live pool-account balance used as unguarded reserve for LP mint/redeem ratios enables donation-based share manipulation - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`pallet-asset-conversion`'s `do_add_liquidity`/`do_remove_liquidity` compute LP-token minting and redemption ratios from `Self::get_balance`/`Self::get_reserves`, which is nothing more than a live read of `T::Assets::balance(asset, pool_account)`. There is no internally accounted, update-gated reserve, no TWAP, and no deviation check. Because the pool's sovereign account is a deterministic, publicly known address, any unprivileged account can inflate or deflate the "reserve" read by simply transferring tokens directly to that account before a victim's `add_liquidity`/`remove_liquidity` extrinsic executes — the same class of bug as using Uniswap V3 `slot0` for share-price calculations.

### Finding Description
`get_balance` is a bare wrapper around `T::Assets::balance` with no protection against out-of-band deposits: [7](#0-6) . `do_add_liquidity` reads `reserve1`/`reserve2` from this function before performing the depositor's transfer and before computing `lp_token_amount = min(side1, side2)` from `total_supply` and those same reserves. Since the pool account is not a privileged/sealed account (it is a normal `AccountId` derived from `PalletId`), a third party can pad its balance with a direct `Balances::transfer_keep_alive` or `Assets::transfer` in the block/transaction immediately preceding a target's `add_liquidity` call, changing `reserve1`/`reserve2` and therefore the `quote()`-derived optimal amounts and the `side1`/`side2` mint ratio the victim receives — without ever going through the pool's own swap/liquidity accounting.

### Impact Explanation
An attacker can shortchange a legitimate liquidity provider's minted LP-token amount (or force their `add_liquidity` call to revert on slippage bounds, a griefing/DoS effect), and correspondingly shift value toward existing LP holders (including the attacker, if they already hold LP tokens) at the moment of the deposit. This directly matches the "Required Impact" class of public underpriced/mis-valued work causing wrong beneficiary/amount in the LP-mint settlement path, achievable by any unprivileged account with no admin, validator, or relayer involvement.

### Likelihood Explanation
The attack requires only an ordinary token transfer to a publicly-computable account address, timed before a target's `add_liquidity`/`remove_liquidity` extrinsic — no special block-production or validator control is needed, since normal transaction-ordering/mempool visibility is sufficient. The barrier is economic (the donated tokens are only partially recoverable by the attacker, proportional to their existing LP share), which lowers but does not eliminate practical exploitability against depositors who are unaware their add-liquidity ratio can be moved by front-running donations.

### Recommendation
Replace the raw live-balance reads in `do_add_liquidity`/`do_remove_liquidity` with an internally tracked reserve value that is only updated atomically by the pallet's own extrinsics (swap/add/remove), or add a deviation/staleness check comparing the live balance against the last-known accounted reserve before using it for ratio math — mirroring the `_checkPriceDeviation` fix applied in the original Real Wagmi remediation.

### Proof of Concept
1. Pool `(A, B)` exists with `reserve_A = 1000`, `reserve_B = 1000`, `total_supply = 1000` LP tokens, attacker holds 0 LP tokens.
2. Victim submits `add_liquidity(A, B, amount1_desired=100, amount2_desired=100, ...)` expecting ~100 LP tokens minted.
3. Attacker, seeing the pending transaction, submits (and gets included first in the same block) a plain `Assets::transfer(A, attacker, pool_account, 500)`, donating 500 units of `A` directly to the pool's sovereign account with no interaction with `pallet-asset-conversion`.
4. When the victim's `do_add_liquidity` executes, `reserve1` for asset `A` is now `1500` instead of `1000`, skewing `quote()`'s `amount2_optimal` and reducing `side1 = amount1 * total_supply / reserve1`, so the victim mints far fewer LP tokens than intended for the same contributed `amount1`/`amount2`, or the call reverts on `AssetTwoDepositDidNotMeetMinimum`/`OptimalAmountLessThanDesired` depending on slippage bounds set.
5. No error is raised for the reserve manipulation itself since `get_balance` treats the donated tokens as legitimate pool reserves.

		pub(super) fn calc_lp_amount_for_zero_supply(
			amount1: &T::Balance,
			amount2: &T::Balance,
		) -> Result<T::Balance, Error<T>> {
			let amount1 = T::HigherPrecisionBalance::from(*amount1);
			let amount2 = T::HigherPrecisionBalance::from(*amount2);

			let result = amount1
				.checked_mul(&amount2)
				.ok_or(Error::<T>::Overflow)?
				.integer_sqrt()
				.checked_sub(&T::MintMinLiquidity::get().into())
				.ok_or(Error::<T>::InsufficientLiquidityMinted)?;

			result.try_into().map_err(|_| Error::<T>::Overflow)
		}
