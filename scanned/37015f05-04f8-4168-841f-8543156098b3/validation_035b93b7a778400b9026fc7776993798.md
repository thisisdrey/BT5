The bug class from the C4 report — a shared weight/denominator variable (`totalAllocPoint`) mutated before accrued rewards are snapshotted, causing incorrect reward re-rating — has a direct local analog in `pallet-nomination-pools`'s commission mechanism, and it has already been identified and fixed in this exact repository.

### Title
Historical: `set_commission_max` re-rated already-accrued rewards at a lowered commission before snapshotting (fixed) - (substrate/frame/nomination-pools/src/lib.rs)

### Summary
The `RewardPool::current_reward_counter` split (`current_payout_balance` divided into pending rewards vs. pending commission) uses `bonded_pool.commission.current()` as the live divisor variable, exactly analogous to Convex's `totalAllocPoint` being used as the live denominator in reward-per-block math [1](#0-0) . Mutating that variable (`commission.current`) before calling `update_records` (the pallet's analog of `massUpdatePools()`) causes rewards accrued under the old rate to be recomputed under the new rate at the next update, exactly mirroring the external finding's broken invariant.

### Finding Description
`RewardPool::update_records` documents that it "MUST be called whenever ... the pool's commission is updated," because a commission change alters how the reward balance is split between members and the commission payee [2](#0-1) . `try_update_max` on `Commission` can force-lower `current` when the new max is below the active rate [3](#0-2) .

The prdoc in this repo, `prdoc/pr_12397.prdoc`, records that `set_commission_max` previously force-lowered `commission.current` via `try_update_max` **without first calling `update_records`**, so rewards accrued at the higher rate since the last snapshot were re-rated at the new lower rate on the next `update_records` call, crediting the differential to pool members instead of to the commission payee [4](#0-3) . This is precisely the `add()`/`totalAllocPoint` pattern in the external report: a shared accrual-denominator variable mutated before the pending reward is checkpointed against the old value.

The current code in this snapshot of the repository already contains the fix: `set_commission_max` now calls `reward_pool.update_records(...)` at the old commission rate immediately before `bonded_pool.commission.try_update_max(...)` is applied [5](#0-4) , mirroring the ordering already used in `set_commission` [6](#0-5) .

### Impact Explanation
Had this analog remained unpatched, an unprivileged member could exploit the mis-rated commission split to claim a differential share of rewards that should have belonged to the commission payee via `claim_payout`/`bond_extra` (`do_reward_payout`) [7](#0-6) , i.e. wrong-beneficiary/wrong-amount settlement of value, matching the "Impacts" gate ("theft or unbacked mint or unlock," "duplicate settlement or payout"). However, this exact path is already fixed in the current source, per the ordering seen at lines 3016–3030 and the corroborating `prdoc`.

### Likelihood Explanation
Not applicable to the current codebase state — the vulnerable ordering has already been corrected (`update_records` now precedes `try_update_max`). No other commission-mutating call path (`set_commission`, `set_commission_change_rate`) was found to skip the required `update_records` snapshot for a value that feeds the reward/commission split formula: `set_commission` correctly snapshots first [6](#0-5) , and `set_commission_change_rate` only mutates `change_rate`/`throttle_from`, which do not enter the `current_reward_counter` split formula and therefore do not require a snapshot [8](#0-7) , [9](#0-8) .

### Recommendation
No action required in this repository snapshot; the fix (snapshot-before-mutate ordering in `set_commission_max`) is already in place and matches the pattern used in `set_commission`. Any future call that adds a new way to mutate `bonded_pool.commission.current` (the divisor consumed by `current_reward_counter`) must call `reward_pool.update_records(...)` at the pre-mutation commission rate before applying the change, and this invariant should be covered by a regression test analogous to the existing `bond_extra_updates_recorded_data`/`join_updates_recorded_data` tests [10](#0-9) .

### Proof of Concept
Not applicable — no exploitable path currently exists. The historical PoC (documented in `prdoc/pr_12397.prdoc`) would have been: set commission to X%, accrue rewards, call `set_commission_max` with a max below X% before any `update_records` snapshot, then claim payout to observe the differential `(X% - new_max%) * accrued` credited to members instead of the commission payee [11](#0-10) .

	fn try_update_max(&mut self, pool_id: PoolId, new_max: Perbill) -> DispatchResult {
		ensure!(
			new_max <= GlobalMaxCommission::<T>::get().unwrap_or(Bounded::max_value()),
			Error::<T>::CommissionExceedsGlobalMaximum
		);
		if let Some(old) = self.max.as_mut() {
			if new_max > *old {
				return Err(Error::<T>::MaxCommissionRestricted.into());
			}
			*old = new_max;
		} else {
			self.max = Some(new_max)
		};
		let updated_current = self
			.current
			.as_mut()
			.map(|(c, _)| {
				let u = *c > new_max;
				*c = (*c).min(new_max);
				u
			})
			.unwrap_or(false);

		if updated_current {
			if let Some((_, payee)) = self.current.as_ref() {
				Pallet::<T>::deposit_event(Event::<T>::PoolCommissionUpdated {
					pool_id,
					current: Some((new_max, payee.clone())),
				});
			}
			self.register_update();
		}
		Ok(())
	}

	fn do_reward_payout(
		member_account: &T::AccountId,
		member: &mut PoolMember<T>,
		bonded_pool: &mut BondedPool<T>,
		reward_pool: &mut RewardPool<T>,
	) -> Result<BalanceOf<T>, DispatchError> {
		debug_assert_eq!(member.pool_id, bonded_pool.id);
		debug_assert_eq!(&mut PoolMembers::<T>::get(member_account).unwrap(), member);

		// a member who has no skin in the game anymore cannot claim any rewards.
		ensure!(!member.active_points().is_zero(), Error::<T>::FullyUnbonding);

		let (current_reward_counter, _) = reward_pool.current_reward_counter(
			bonded_pool.id,
			bonded_pool.points,
			bonded_pool.commission.current(),
		)?;

		// Determine the pending rewards. In scenarios where commission is 100%, `pending_rewards`
		// will be zero.
		let pending_rewards = member.pending_rewards(current_reward_counter)?;
		if pending_rewards.is_zero() {
			return Ok(pending_rewards);
		}

		// IFF the reward is non-zero alter the member and reward pool info.
		member.last_recorded_reward_counter = current_reward_counter;
		reward_pool.register_claimed_reward(pending_rewards);

		T::Currency::transfer(
			&bonded_pool.reward_account(),
			member_account,
			pending_rewards,
			// defensive: the depositor has put existential deposit into the pool and it stays
			// untouched, reward account shall not die.
			Preservation::Preserve,
		)?;

		Self::deposit_event(Event::<T>::PaidOut {
			member: member_account.clone(),
			pool_id: member.pool_id,
			payout: pending_rewards,
		});
