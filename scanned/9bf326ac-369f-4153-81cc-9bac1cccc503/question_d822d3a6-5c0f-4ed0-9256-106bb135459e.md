`Contract::mt_resolve_deposit`/`resolve_deposit_internal`'s refund logic (`contracts/defuse/src/contract/tokens/mod.rs`) computes `refund_amount = requested_refund.min(*deposited).min(balance_left)` PER TOKEN in a loop that also does `receiver.token_balances.sub(...)` and `self.storage.state.total_supplies.sub(...)` inside the SAME loop, meaning `balance_left` for token N is read via `receiver.token_balances.amount_for(&token_id)` potentially AFTER token N-1's refund already changed `receiver.token_balances`. Since each `token_id` is distinct within a single `mt_on_transfer` batch, does this loop-order dependency ever cause the refund for a LATER token in the loop to read a `balance_left` that has been altered by an EARLIER unrelated token's refund in the same call (e.g. via aliasing if `zip_eq` iteration order isn't what's assumed)? Impact: Critical if cross-token refund amounts leak state incorrectly, breaking SETTLEMENT for unrelated tokens in the same batch. Proof: `cargo test` depositing 2+ distinct `TokenId`s in one `mt_on_transfer` batch with a malicious receiver requesting maximal refunds on both, and assert each token's refund strictly depends only on its OWN `deposited`/`balance_left`, never a sibling token's.
