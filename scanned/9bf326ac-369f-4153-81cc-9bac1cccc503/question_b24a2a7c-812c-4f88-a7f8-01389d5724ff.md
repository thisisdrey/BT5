`Contract::mt_resolve_deposit`/`ft_resolve_deposit`/`nft_resolve_deposit` all funnel into `resolve_deposit_internal`, which trusts `promise_result_checked_json_with_len::<Vec<U128>>(0, tokens_count)` — the return value of `notify_on_transfer`'s cross-contract call to an attacker-deployed `receiver_id` contract — as `requested_refunds`. If the attacker's receiver contract returns a `Vec<U128>` shorter or malformed such that `.filter(|refunds| refunds.len() == tokens_count)` fails, code falls back to `requested_refund = *deposited` (i.e., refund everything, effectively rejecting the whole deposit back to `receiver_id`... wait, it BURNS `refund_amount` from `receiver.token_balances`, crediting nothing back on-chain in this function). Does the amount burned from `receiver.token_balances` in this fallback path always equal an amount the ORIGINAL DEPOSITOR (not the receiver) intended to be refunded, given the receiver never actually requested it (malformed response)? Impact: Critical — a receiver contract error state can force burn of a receiver's balance that isn't part of `SETTLEMENT`'s `value debited == value delivered + value re-credited`, if the true depositor never gets an on-chain refund credit. Proof: `cargo test` with a receiver stub returning a mis-sized `Vec<U128>`, deposit tokens with `DepositAction::Notify`, and assert the depositor eventually receives back exactly `deposited - value delivered` via the returned promise `PromiseOrValue::Value`, not that funds vanish.
