[Target: StackerDBTx::reconfigure_stackerdb slot-to-owner remapping.] When a StackerDB contract is reconfigured across a reward-cycle boundary (StackerDBTx::reconfigure_stackerdb(smart_contract, slots)), can a remote party who owned slot_id=K in the PREVIOUS reward cycle's mapping still write successfully to slot_id=K in the NEW mapping if get_slot_validation returns a stale signer row before reconfigure_stackerdb's UPDATE executes, due to a race between reading old validation and committing new owner rows? Preconditions: reward-cycle transition triggers reconfigure_stackerdb while a concurrent try_replace_chunk transaction is in flight for the same slot_id. Call sequence: reconfigure_stackerdb -> get_slot_validation(smart_contract, slot_id) compares existing_validation.signer to *principal -> if unchanged, 'continue' (no reset) -> else INSERT OR REPLACE resets signer/version/data. Equality: OWNERSHIP must reflect the reward-cycle-correct owner for slot_id at the time of write; a chunk written by the old owner after remap must be rejected. Impact: Critical unauthorized write persisting across reward-cycle owner change. Proof: Rust test in stackslib::net::stackerdb::db: create_stackerdb with owner A at slot 0, reconfigure_stackerdb assigning slot 0 to owner B, then attempt try_replace_chunk signed by A's key at slot 0, asserting BadSlotSigner.
