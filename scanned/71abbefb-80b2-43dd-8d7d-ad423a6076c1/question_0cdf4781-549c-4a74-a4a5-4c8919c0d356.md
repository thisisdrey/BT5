Target: `StacksHttpResponse::decode_atlas_get_attachment` (stackslib/src/net/api/getattachment.rs). Attacker action: run a peer that answers a `GET /v2/attachments/{attachment_hash}` request from a syncing node with a `GetAttachmentResponse` whose `attachment.content` bytes hash (via `Attachment::hash()`) to a value different from the requested `attachment_hash` path segment. Preconditions: victim node has an outstanding `AttachmentRequest` with `content_hash = H` queued by `AttachmentsBatchStateMachine`; attacker peer is in `network.get_outbound_sync_peers()` and returned in `get_data_url`. Call sequence: `AttachmentsBatchStateContext::extend_with_attachments` decodes the response via `decode_atlas_get_attachment` and inserts the returned `Attachment` into `self.attachments` with no comparison against `request.content_hash`; the `Done` arm of `AttachmentsDownloader::run` then calls `network.atlasdb.insert_instantiated_attachment(&attachment)` and `context.attachments_batch.resolve_attachment(&attachment.hash())`. Equality broken: attachment.hash() (bytes actually served) != request.content_hash (hash committed by the confirmed name operation via AttachmentInstance::content_hash). Scoped impact (High): BNS resolution can end up serving attacker-chosen bytes under a hash never committed on-chain, or the legitimate attachment is marked resolved/absent incorrectly, corrupting BNS zonefile/profile data returned to RPC clients. Proof idea: a stackslib::net test constructing an AttachmentsBatchStateContext with one pending AttachmentRequest{content_hash: H}, feeding a crafted StacksHttpResponse whose body hashes to H' != H, and asserting resolve_attachment/insert_instantiated_attachment either wrongly resolves H or silently stores content under H' with no on-chain committer.
