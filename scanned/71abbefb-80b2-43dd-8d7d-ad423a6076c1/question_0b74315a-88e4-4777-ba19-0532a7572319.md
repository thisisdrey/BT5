Target: `AttachmentsBatchStateContext::get_prioritized_attachments_requests` (stackslib/src/net/atlas/download.rs:404-478). Attacker action: as one of several peers responding to an attachments-inventory request, advertise `AttachmentPage{index, inventory}` bits (`GetAttachmentsInvResponse`) claiming to HAVE an attachment at `position_in_page` for a `content_hash` the attacker never actually possesses matching bytes for. Preconditions: attacker is included in `network.get_outbound_sync_peers()` for the requested contract_id/page. Equality: peer's claimed inventory bit == peer's actual possession of bytes hashing to content_hash - never verified before selection. Scoped impact (High): a malicious peer can steer the downloader to always pick it as source, then serve wrong bytes or repeatedly fail, achieving attachment/BNS data mismatch or denial of resolution for that content_hash. Proof idea: net test where a fake peer's GetAttachmentsInvResponse claims inventory=1 for a content_hash it cannot serve correctly, and assert get_prioritized_attachments_requests still selects it as the only source, then downstream AttachmentRequest never resolves and blocks legitimate resolution (queue starvation on that content_hash).
