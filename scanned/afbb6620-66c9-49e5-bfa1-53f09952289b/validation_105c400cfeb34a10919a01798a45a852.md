### Title
Inbound Queue V2 marks a message nonce as permanently "processed" before the destination-chain XCM execution succeeds, causing irreversible fund loss with no invalidation or retry path - ([File: bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs])

### Summary
The external report's core broken invariant is: an intent/message identifier is finalized as "consumed" independently of whether the underlying value transfer actually settles to the intended beneficiary, and there is no mechanism to invalidate or retry that identifier once the transfer fails. The same pattern exists in Snowbridge's `pallet-inbound-queue-v2`: `process_message` marks a message `nonce` as processed as soon as the XCM is *handed off* to the XCM sender, not once it has actually executed successfully on the destination chain (Asset Hub). If the downstream XCM program fails or traps assets after that point, the nonce can never be reused, resubmitted, or invalidated, and the funds are permanently unrecoverable.

### Finding Description
`Pallet::process_message` in `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs` does: [1](#0-0) 

```
ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);
Nonce::<T>::set(nonce);                       // <-- marked "processed" here
let message_id = T::MessageProcessor::process_message(relayer.clone(), message)?;
```

`Nonce` is a `SparseBitmapImpl`-backed `StorageMap<_, Twox64Concat, u64, u128, ValueQuery>` tracking whether a nonce has been used, and the pallet doc explicitly says "Message nonces are unique and never repeated." [2](#0-1) 

The `T::MessageProcessor` implementation (`XcmMessageProcessor::process_xcm`) converts the Ethereum event into an XCM program and calls `Sender::deliver(ticket)`: [3](#0-2) 

`Sender::deliver` only confirms the message was successfully *handed off* to the outbound/XCMP delivery mechanism — it says nothing about whether the receiving chain (Asset Hub) will actually execute the `DepositAsset`/`RefundSurplus` instructions successfully once the message arrives. If `deliver` succeeds, `process_message` returns `Ok`, the relayer is rewarded, and `Nonce::<T>::set(nonce)` (already committed inside the same successful extrinsic) permanently marks this nonce as used.

If the destination XCM execution later fails — e.g. because of a beneficiary account issue, an under-computed `execution_fee`/weight, a `RefundSurplus` interaction with insufficient remaining weight, or any other runtime condition on Asset Hub causing the assets to be trapped (`AssetTrap`) rather than delivered — the user's assets are lost or stuck in the asset trap. There is no extrinsic in this pallet (or the outbound processing path) that allows:
- the original relayer/payer to invalidate the nonce and retry with a corrected payload, or
- anyone to reprocess message `nonce` once `Nonce::<T>::get(nonce)` is `true`.

This is structurally the same invariant violation as the Transfers.sol report: state that should only be finalized after successful, atomic settlement is instead finalized at submission/hand-off time, and the affected identifier can never be invalidated or reused to make the payer/beneficiary whole.

### Impact Explanation
This falls under "permanent user-fund or bridge-state lock" and "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" from the impact gate. Once `Nonce::<T>::set(nonce)` commits and the extrinsic succeeds (because `Sender::deliver` itself succeeded), the corresponding Ethereum-side transfer intent can never be replayed or corrected on the Polkadot side, even though the actual value transfer to the beneficiary may still fail asynchronously on Asset Hub. Funds bridged from Ethereum become unrecoverable, and the relayer is nonetheless paid via `T::RewardPayment::register_reward`, decoupling payout from actual settlement success. [4](#0-3) 

### Likelihood Explanation
No malicious relayer, validator, governance actor, or leaked key is required. The condition is triggered by an ordinary, low-probability but realistic runtime failure on the destination chain (fee/weight underestimation, `RefundSurplus` weight shortfall, asset trap due to conversion mismatch, etc.) that occurs *after* the nonce has already been irreversibly committed in the source-chain pallet, and this pallet provides no compensating invalidation/retry extrinsic. This matches the "public underpriced work" / "permanent lock" categories without needing any privileged or adversarial actor.

### Recommendation
- Do not treat `Nonce::<T>::set(nonce)` as the final settlement marker for value-bearing messages; only finalize it after the destination chain confirms successful execution (e.g., via delivery-confirmation/receipt callback), or explicitly document/handle the asynchronous gap with a dedicated recovery path.
- Add a supervised mechanism (e.g., analogous to `AddTip`'s nonce-gated storage) that allows re-driving or refunding a message whose destination XCM execution failed, keyed by the already-consumed `nonce`, instead of leaving it permanently dead.
- Consider using XCM's reporting mechanisms (`ReportError`/`SetTopic` with an on-success callback) so that `Nonce` (or a companion "settled" flag) is only flipped after confirmed successful execution, mirroring the "processedTransferIntents should be set only on success, with an explicit invalidation path" recommendation from the reference report.

### Proof of Concept
1. A user on Ethereum calls `v2_sendMessage`, emitting an `OutboundMessageAccepted` event with `nonce = N`, assets, and an XCM payload intended to `DepositAsset` to a beneficiary on Asset Hub.
2. A relayer submits the proof via `InboundQueueV2::submit`, which calls `process_message`:
   - `Nonce::<T>::set(N)` is written.
   - `XcmMessageProcessor::process_xcm` converts the message and calls `Sender::deliver(ticket)`, which succeeds (message is enqueued to XCMP).
   - `process_message` returns `Ok`, the relayer is rewarded, `MessageReceived { nonce: N, .. }` is emitted. [5](#0-4) 
3. When the enqueued XCM program executes on Asset Hub, `RefundSurplus`/`DepositAsset` fails (e.g., insufficient remaining weight/fee, or an asset registration/conversion mismatch), and the assets are trapped instead of reaching the beneficiary.
4. `Nonce::<T>::get(N)` is now permanently `true`; there is no extrinsic on-chain to reset it or replay message `N`. The user's bridged funds are stuck, with the only avenue being an out-of-protocol governance intervention (asset-trap claim), not a protocol-guaranteed settlement or retry mechanism.

	impl<T: Config> Pallet<T> {
		pub fn process_message(relayer: T::AccountId, message: Message) -> DispatchResult {
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == message.gateway, Error::<T>::InvalidGateway);

			let (nonce, relayer_fee) = (message.nonce, message.relayer_fee);

			// Verify the message has not been processed
			ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);

			// Mark message as received
			Nonce::<T>::set(nonce);

			let message_id = T::MessageProcessor::process_message(relayer.clone(), message)
				.map_err(|e| match e {
					MessageProcessorError::ProcessMessage(e) => e,
					MessageProcessorError::ConvertMessage(e) => Error::<T>::from(e).into(),
					MessageProcessorError::SendMessage(e) => Error::<T>::from(e).into(),
				})?;

			// Pay relayer reward
			let tip = Tips::<T>::take(nonce).unwrap_or_default();
			let total_tip = relayer_fee.saturating_add(tip);
			if total_tip > 0 {
				T::RewardPayment::register_reward(&relayer, T::DefaultRewardKind::get(), total_tip);
			}

			// Emit event with the message_id
			Self::deposit_event(Event::MessageReceived { nonce, message_id });

			Ok(())
		}
