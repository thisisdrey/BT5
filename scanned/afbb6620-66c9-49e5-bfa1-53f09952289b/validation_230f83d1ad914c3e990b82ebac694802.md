## Title
Unvalidated relayer-supplied XCM beneficiary in `claim_rewards_to` permanently burns/traps Snowbridge relayer rewards - (File: `bridges/snowbridge/primitives/core/src/reward.rs`)

### Summary
The reported bug class is "missing validation of a critical destination/identity parameter before it is committed to state, with no way to recover once set." In `pallet-bridge-relayers`, the `claim_rewards_to` extrinsic lets a relayer supply an arbitrary `beneficiary` location that is never validated for resolvability to a real account. The reward record is deleted from storage as soon as the XCM *send* succeeds locally, before it is known whether the remote `DepositAsset` will actually resolve the beneficiary. An invalid/degenerate beneficiary location causes the reward to be irreversibly lost — the on-chain analog of "immutable / unchecked destination causes permanent loss of funds."

### Finding Description
`claim_rewards_to` accepts a caller-supplied beneficiary and forwards it, unchecked, straight to the payment procedure: [1](#0-0) 

`do_claim_rewards` uses `try_mutate_exists`, which takes (deletes) the reward entry from `RelayerRewards` and only calls `PaymentProcedure::pay_reward` afterwards inside the same closure: [2](#0-1) 

For the `Snowbridge` reward kind, `PaymentProcedure` is implemented by `BridgeRewardPayer`, which only converts the `VersionedLocation` to the current XCM version (a compatibility check, not an identity/validity check) and passes it straight through as `beneficiary`: [3](#0-2) 

The actual payment logic, `PayAccountOnLocation::pay_reward`, builds an XCM program that ends with `DepositAsset { assets: AllCounted(1).into(), beneficiary }` on AssetHub, and only returns `Err` if the *local* `validate_send`/`charge_fees`/`deliver` steps fail — it never checks that `beneficiary` actually resolves to a spendable account: [4](#0-3) 

Because `pay_reward` returning `Ok` only reflects successful local dispatch of the XCM (not successful remote execution), `try_mutate_exists` commits the deletion of the relayer's `RelayerRewards` entry unconditionally once the message is handed to the router. If `beneficiary` is a degenerate/invalid `Location` (e.g. `Here`, a location without an `AccountId32`/`AccountKey20` junction, or one that the `AssetTransactor`/location-to-account converter on AssetHub cannot resolve), the remote `DepositAsset` instruction fails when actually executed on AssetHub. The reserve-deposited assets are trapped (`AssetTrap`) under an origin equal to `DescendOrigin(InboundQueueLocation) + UniversalOrigin(EthereumNetwork)` — an origin a normal user cannot reproduce to reclaim the trap via `ClaimAsset`. Meanwhile the BridgeHub-side accounting already shows the reward as paid/cleared, matching the event `RewardPaid`: [5](#0-4) 

The existing test suite only exercises "wrong beneficiary type" rejections (`LocalAccount` for Snowbridge, `AssetHubLocation` for legacy lanes) — it never exercises a syntactically-valid-but-unresolvable `Location` (e.g. `Here`, or a Location whose interior junctions do not include an account key): [6](#0-5) 

This is the structural analog of the reported bug: a critical "destination" value (there: `token`/`zapTreasury` address; here: reward `beneficiary` location) is accepted and immediately committed/consumed without a validity check, and once committed it cannot be corrected — resulting in unrecoverable loss.

### Impact Explanation
A relayer that mistakenly (or an attacker crafting a malicious front-end/tool that) submits a malformed `beneficiary` location to `claim_rewards_to` loses their accumulated Snowbridge relayer reward permanently: the `RelayerRewards` entry is deleted on BridgeHub, but the corresponding assets never land in a spendable account on AssetHub and are trapped under an origin the relayer cannot reproduce. This is a permanent user-fund lock, one of the explicitly in-scope impact categories (public entrypoint, unprivileged, no relayer/validator/admin misbehavior required — the caller is the relayer acting normally through the documented API).

### Likelihood Explanation
Likelihood is more moderate than high because most legitimate callers use tooling that constructs correct `AccountId32` junction locations. However, `claim_rewards_to` is a fully public, unprivileged extrinsic that accepts an arbitrary `VersionedLocation`/`Location`, the only check performed is an XCM-version conversion, and there is no defensive check anywhere in the call path (`do_claim_rewards`, `BridgeRewardPayer::pay_reward`, `PayAccountOnLocation::pay_reward`) that the beneficiary resolves to an account before the local reward ledger entry is irreversibly cleared.

### Recommendation
Add an explicit validation step before consuming/deleting the `RelayerRewards` entry (or before committing to the XCM send) that the beneficiary `Location` resolves to a valid account under the destination chain's location-to-account converter — analogous to adding the missing zero-address checks recommended for `LiquidityFreeLaunch`/`LiquidityFreeLaunchFactory`. Concretely:
- In `PayAccountOnLocation::pay_reward` (`bridges/snowbridge/primitives/core/src/reward.rs`), reject beneficiaries that are `Here`/empty or otherwise cannot be converted to a 32/20-byte account key before constructing/sending the XCM.
- Alternatively/additionally, in `pallet-bridge-relayers::do_claim_rewards`, only remove the `RelayerRewards` entry after confirming (via a query/callback or a deferred confirmation flow) that the remote deposit succeeded, rather than eagerly deleting on local send success.

### Proof of Concept
1. A registered relayer accrues a Snowbridge reward via `register_reward`, as shown in existing tests: [7](#0-6) .
2. The relayer calls `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(VersionedLocation::from(Location::new(0, Here))))` — a syntactically valid `Location` with no `AccountId32`/`AccountKey20` junction.
3. On BridgeHub: `Location::try_from` succeeds (version conversion only), `PayAccountOnLocation::pay_reward` validates and delivers the XCM successfully (`validate_send`/`charge_fees`/`deliver` all succeed since these don't inspect `beneficiary`'s resolvability) — see [8](#0-7) . `do_claim_rewards`'s `try_mutate_exists` therefore commits, deleting the `RelayerRewards` entry and emitting `RewardPaid`.
4. On AssetHub: the XCM executes `ReserveAssetDeposited` followed by `DepositAsset { assets: AllCounted(1), beneficiary: Here }`. Since `Here` does not resolve to a spendable account via the configured `AssetTransactor`, the deposit fails and the reserved assets are trapped under the descended/universal origin (`InboundQueueLocation` + `EthereumNetwork`), which the relayer cannot reproduce to reclaim via `ClaimAsset`.
5. Net result: the relayer's reward is permanently gone — cleared from `RelayerRewards` on BridgeHub with no corresponding funds ever landing in a controllable account.

			relayer: T::AccountId,
			reward_kind: T::Reward,
			beneficiary: BeneficiaryOf<T, I>,

			RelayerRewards::<T, I>::try_mutate_exists(

					})?;

						relayer: relayer.clone(),
						reward_kind,
						reward_balance,
						beneficiary,

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}

#[test]
fn claim_snowbridge_rewards_to_local_account_fails() {
	let assethub_location = BridgeHubWestend::sibling_location_of(AssetHubWestend::para_id());
	let assethub_sovereign = BridgeHubWestend::sovereign_account_id_of(assethub_location);

	let relayer_account = BridgeHubWestendSender::get();
	let reward_address = AssetHubWestendReceiver::get();

	BridgeHubWestend::fund_accounts(vec![
		(assethub_sovereign.clone(), INITIAL_FUND),
		(relayer_account.clone(), INITIAL_FUND),
	]);
	set_up_eth_and_dot_pool();

	BridgeHubWestend::execute_with(|| {
		type Runtime = <BridgeHubWestend as Chain>::Runtime;
		type RuntimeEvent = <BridgeHubWestend as Chain>::RuntimeEvent;
		type RuntimeOrigin = <BridgeHubWestend as Chain>::RuntimeOrigin;
		let reward_amount = ETHER_MIN_BALANCE * 2; // Reward should be more than Ether min balance

		type BridgeRelayers = <BridgeHubWestend as BridgeHubWestendPallet>::BridgeRelayers;
		BridgeRelayers::register_reward(
			&relayer_account.clone(),
			BridgeReward::Snowbridge,
			reward_amount,
		);

		// Check that the reward was registered.
		assert_expected_events!(
			BridgeHubWestend,
			vec![
				RuntimeEvent::BridgeRelayers(pallet_bridge_relayers::Event::RewardRegistered { relayer, reward_kind, reward_balance }) => {
					relayer: *relayer == relayer_account,
					reward_kind: *reward_kind == BridgeReward::Snowbridge,
					reward_balance: *reward_balance == reward_amount,
				},
			]
		);

		let reward_beneficiary = BridgeRewardBeneficiaries::LocalAccount(reward_address);
		let result = BridgeRelayers::claim_rewards_to(
			RuntimeOrigin::signed(relayer_account.clone()),
			BridgeReward::Snowbridge,
			reward_beneficiary.clone(),
		);
		assert_err!(result, FailedToPayReward::<Runtime, ()>);
	})
}
