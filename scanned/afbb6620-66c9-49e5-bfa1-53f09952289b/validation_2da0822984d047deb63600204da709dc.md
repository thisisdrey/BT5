## Finding [1](#0-0) 

### Title
Same-block AMM spot-price manipulation lets a user extract pool value via the fee-refund path in `pallet-asset-conversion-tx-payment` - (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/lib.rs` / `src/payment.rs`)

### Summary
`ChargeAssetTxPayment`'s `TransactionExtension` withdraws the estimated fee in a user-chosen asset *before* the call executes (`prepare`), and refunds the unspent portion by re-quoting/re-swapping the AMM pool *after* the call executes (`post_dispatch_details`). Because the pool used for both the pre-charge quote and the post-dispatch refund swap is the same `pallet-asset-conversion` pool the dispatched call is free to manipulate, a single unprivileged signed extrinsic can atomically skew the pool, cause the refund step to swap at the skewed price, and pocket the difference from the pool's liquidity — with no malicious relayer, collator, or governance actor involved. This mirrors the external report's root cause: valuation used at "deposit" (pre-charge) time differs from valuation used at "withdraw" (refund) time, and an attacker who controls the intervening state transition can profit from the mismatch.

### Finding Description
The extension is defined in `ChargeAssetTxPayment::prepare` and `post_dispatch_details`:

- `prepare()` calls `withdraw_fee`, which for an asset-denominated fee invokes `T::OnChargeAssetTransaction::withdraw_fee` → `SwapAssetAdapter::withdraw_fee`, which quotes `S::quote_price_tokens_for_exact_tokens(asset_id, A::get(), fee, true)` against the **current** pool reserves and withdraws that amount of `asset_id` from the signer, *before* the call is dispatched. [2](#0-1) 

- The actual `T::RuntimeCall` is then dispatched by the executive between `prepare()` and `post_dispatch_details()`. This call is entirely user-controlled and can be anything the runtime permits, including a swap/add_liquidity/remove_liquidity against the very same `asset_id`↔native pool.

- `post_dispatch_details()` computes the corrected fee and calls `T::OnChargeAssetTransaction::correct_and_deposit_fee` → `SwapAssetAdapter::correct_and_deposit_fee`, which re-quotes `S::quote_price_exact_tokens_for_tokens(A::get(), asset_id, refund_amount, true)` and then actually executes `S::swap_exact_tokens_for_tokens(...)` to convert the native refund back into `asset_id` for the user — using the pool state **as it stands after** the call has already run. [3](#0-2) [4](#0-3) 

The corrupted value is the AMM spot price/reserve ratio of the `asset_id`↔native pool that both the pre-charge quote and the post-dispatch refund swap depend on. `pallet-asset-conversion` has no TWAP, no per-block price cap, and no re-entrancy/atomicity guard preventing the fee-paying call itself from moving that exact pool before the refund swap executes — exactly the "deposit distributed one way, withdraw serviced another way against a value that changed in between" pattern from the report, except here the entire deposit→valuation-shift→withdraw sequence happens inside one atomic, self-authored extrinsic instead of requiring cross-transaction timing.

### Impact Explanation
An attacker can extract real value from the AMM pool's liquidity providers by asymmetrically pricing the fee-withdrawal and fee-refund legs of a single transaction: withdraw priced against pool state P1, refund-swap executed and priced against pool state P2 that the attacker's own call moved to. This is value extraction from the shared liquidity pool by an ordinary signed account, i.e. underpriced/mispriced settlement that drains pool funds to the attacker's benefit — squarely within the "theft or unbacked mint or unlock," "duplicate/mispriced settlement," and "public underpriced work" impact categories for the runtime dispatch path.

### Likelihood Explanation
Any chain that enables `pallet-asset-conversion-tx-payment` together with `pallet-asset-conversion` pools is exposed. The attack requires only an unprivileged signed account, one extrinsic (which can itself be a call that swaps/adds/removes liquidity in the targeted pool, or a `pallet-utility::batch` composed of such calls), and no cooperation from any validator, collator, relayer, or governance actor — matching the required "no malicious peer/node/relayer/prover/admin" constraint exactly.

### Recommendation
- Use a single, consistent price snapshot (or a TWAP / bounded-deviation check) for both the pre-dispatch `withdraw_fee` quote and the post-dispatch refund quote/swap, rather than re-reading live spot price after the call has executed.
- Alternatively, disallow the fee-paying call itself from mutating the reserves of the pool used for its own fee asset within the same extrinsic (e.g., snapshot-and-compare reserves, or defer/reject refund-swap if reserves changed beyond a tolerance since `prepare`).
- Consider capping the refund-swap's acceptable price impact relative to the pre-dispatch quote, failing closed (keep native fee, skip refund) if the deviation exceeds a threshold, similar to slippage protection already used elsewhere in `pallet-asset-conversion`.

### Proof of Concept
1. Attacker (unprivileged) has balances in `asset_id` X and native token, and an existing X↔Native pool via `pallet-asset-conversion`.
2. Attacker submits one signed extrinsic with `ChargeAssetTxPayment { tip: 0, asset_id: Some(X) }`:
   - `prepare()` quotes and withdraws `q1` units of X for the estimated fee against the pool's current reserves (`SwapAssetAdapter::withdraw_fee`, `payment.rs:142-146`).
   - The call itself is (or contains, via `pallet_utility::batch`) a large `pallet_asset_conversion::swap_exact_tokens_for_tokens` or `add_liquidity`/`remove_liquidity` against the X↔Native pool, sharply skewing the reserve ratio so that native becomes "expensive" in X terms.
3. `post_dispatch_details()` computes `refund_amount` in native, then re-quotes and swaps it back into X using the now-skewed pool (`payment.rs:262-297`, `lib.rs:402-410`). Because native is now priced higher in X terms than at withdrawal time, the attacker receives a disproportionately large `refund_asset_amount` of X relative to what was fairly owed, funded by the pool's other liquidity providers.
4. The attacker's call can undo the manipulation (swap back) in a later, separate transaction, or simply leave value extracted — the entire withdraw→manipulate→refund sequence completed atomically in one extrinsic, unlike the external report which needed two separate deposit/withdraw transactions.
