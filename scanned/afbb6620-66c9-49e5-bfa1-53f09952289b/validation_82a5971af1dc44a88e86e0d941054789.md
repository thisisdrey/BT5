## Title
`burn` extrinsic leaves a stale `NftsByOwner` entry, permanently bricking the purse key and enabling ghost-ownership desync in `pallet-scarcity` - (File: `substrate/frame/scarcity/src/lib.rs`)

### Summary
The external report's core invariant is: "a mapping that is supposed to track current NFT ownership (`ownerToId`) must be kept in sync with every operation that changes or destroys ownership; if it isn't, an account's ownership record diverges from reality." In `pallet-scarcity`, the same broken-invariant pattern exists between `NftsByOwner` (the purse-key → NFT ownership map, functionally identical to `ownerToId`) and `Instances` (instance-id → purse-key map) on the **burn** path.

### Finding Description
`pallet-scarcity` enforces a strict "one NFT per purse key" model. Ownership is tracked in two mirrored storages:
- `NftsByOwner: purse -> Nft`
- `Instances: instance_id -> purse`

Every state-changing operation is expected to update both maps consistently. This is done correctly in `do_force_transfer` (removes `NftsByOwner` for `from`, `Locked` for `from`, then inserts for `to`) and in `do_force_burn`, which explicitly does: [1](#0-0) 
```
NftsByOwner::<T>::remove(&purse);
Locked::<T>::remove(&purse);
Self::do_burn(nft)
```

However, the permissionless `burn` extrinsic (called through the `Origin::Nft` purse-key origin, used by ordinary NFT holders burning their own item) calls `Self::do_burn(nft)` directly, without first removing the caller's `NftsByOwner` entry: [2](#0-1) 

`do_burn` itself only touches metadata/deposit/supply bookkeeping and `Instances::<T>::remove(instance)` — it never touches `NftsByOwner`: [3](#0-2) 

Consequence: after a normal (non-force) `burn`, `Instances` no longer contains the instance, but `NftsByOwner::<T>::get(purse)` still returns the old `Nft` struct referencing the now-burned `instance`. The purse-key's ownership record is now permanently stale/desynced from actual state — exactly the same class of bug as the reported `ownerToId` not being cleared/updated on transfer.

### Impact Explanation
Every entry point that must accept a new NFT into a purse key checks `NftsByOwner::<T>::contains_key(&to)` to enforce the one-NFT-per-key invariant, e.g. in `transfer`: [4](#0-3) 
and in `do_force_transfer`: [5](#0-4) 
and `mint`/`mint_without_deposit` similarly check `AddressOccupied` (see benchmarking test at lines 1082-1094 asserting `AddressOccupied` on remint).

Because burning via the ordinary `burn` call never clears `NftsByOwner`, the purse key that legitimately burned its own NFT becomes permanently unable to receive any future mint, transfer, or force-transfer — the key is bricked forever, because `NftsByOwner::contains_key` will always return `true` even though the underlying `Instances` slot is empty. This is a **public, unprivileged, permanent state-lock**: any account can trigger it on itself by calling `burn` once, and no recovery path exists in the pallet (nothing ever removes a stale `NftsByOwner` entry once `Instances` has already been cleared, since `do_force_burn`/`do_force_transfer` both look up the purse via `Instances::<T>::get(instance)` first — and after the ordinary `burn`, `Instances` no longer contains that instance, so a collection owner cannot even force-clean the stale `NftsByOwner` entry through `do_force_burn`/`do_force_transfer`, since those functions resolve the purse through `Instances`, not `NftsByOwner`).

This matches the "permanent user-fund or bridge-state lock" / "duplicate settlement or payout" class of impact called out in the gate: it is a public, underprivileged action that permanently locks a purse-key's ability to hold any future asset issued by this pallet, without any admin/governance/relayer involvement.

### Likelihood Explanation
High likelihood: `burn` is a normal, permissionless, feeless dispatchable intended for everyday use by NFT holders (`#[pallet::call_index(4)]`, feeless via `AsScarcity`). No special preconditions, race, or privileged actor is required — a single call by the NFT holder against their own instance triggers the desync deterministically, every time.

### Recommendation
In the `burn` call handler (or inside `do_burn`), remove the caller's `NftsByOwner` (and `Locked`) entry for the purse key, mirroring what `do_force_burn` already does:
```rust
pub fn burn(origin: OriginFor<T>) -> DispatchResultWithPostInfo {
    let Ok(Origin::Nft { owner, nft }) = origin.into() else {
        return Err(DispatchError::BadOrigin.into());
    };
    NftsByOwner::<T>::remove(&owner);
    Locked::<T>::remove(&owner);
    let metadata_count = Self::do_burn(nft)?;
    Ok((Some(T::WeightInfo::burn(metadata_count)), Pays::No).into())
}
```
Additionally add a `do_try_state` invariant asserting that every `NftsByOwner` entry's `instance` exists in `Instances` and points back to the same owner, to catch this class of desync going forward.

### Proof of Concept
1. Collection owner creates a collection and item definition; mints an instance to purse `P` (via `mint` or `mint_without_deposit`), so `NftsByOwner::<T>::get(P) == Some(Nft{instance: 0, ..})` and `Instances::<T>::get(0) == Some(P)`.
2. Purse `P` (holder of NFT 0) submits `Scarcity::burn` through the `AsScarcity` extension using `Origin::Nft { owner: P, nft }`.
3. After execution: `Instances::<T>::get(0) == None` (removed by `do_burn`), but `NftsByOwner::<T>::get(P) == Some(Nft{instance: 0, ..})` — unchanged, since `do_burn` never removes it.
4. Any subsequent attempt to mint or (force-)transfer a new NFT to `P` fails with `Error::<T>::AddressOccupied` (`ensure!(!NftsByOwner::<T>::contains_key(&to), ...)`), even though `P` legitimately holds nothing. Reference check pattern confirmed at: [6](#0-5) 
5. `P` is now permanently unable to hold any NFT minted by this pallet — the purse-key is bricked, and the ownership bookkeeping (`NftsByOwner`) diverges from real state (`Instances`), exactly mirroring the external report's `ownerToId` desync after transfer.

			let instance = nft.instance;
			let expected_metadata_count = InstanceMetadataCount::<T>::take(instance);
			let mut actual_metadata_count = 0u32;
			let mut deposit = InstanceDeposits::<T>::take(instance).unwrap_or_else(Zero::zero);
			for (_, entry) in InstanceMetadata::<T>::drain_prefix(instance) {
				actual_metadata_count = actual_metadata_count.saturating_add(1);
				deposit = deposit.checked_add(&entry.deposit).ok_or(ArithmeticError::Overflow)?;
			}
			debug_assert_eq!(actual_metadata_count, expected_metadata_count);

			ItemDefs::<T>::try_mutate(nft.collection, nft.item, |maybe_definition| {
				let definition = maybe_definition.as_mut().ok_or(Error::<T>::UnknownItem)?;

					definition.live_supply.checked_sub(1).ok_or(ArithmeticError::Underflow)?;
