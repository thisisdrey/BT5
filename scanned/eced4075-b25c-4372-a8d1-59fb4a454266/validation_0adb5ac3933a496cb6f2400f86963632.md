### Title
Frozen/held/locked contract balance permanently blocks `terminate`, stranding the deposit and any funds sent post-scheduling - (File: `substrate/frame/revive/src/exec.rs`)

### Summary
The external report shows that a paused ERC721/ERC1155 causes `stopRent`'s mandatory "return the asset to the lender" step to revert, permanently stalling settlement. The equivalent broken invariant exists in `pallet-revive`'s contract termination flow: `do_terminate` unconditionally sweeps the *entire* balance of a contract's account (via `T::Deposit::refund_all` and `Self::transfer`) as a mandatory step of destroying the contract, and wraps the whole operation in `with_transaction` so that **any** failure in that sweep rolls back the entire termination. If the contract account ever accumulates a currency freeze/hold that the currency implementation refuses to move (governance locks, staking locks, or any other freeze placed on the same `Currency`/fungible type used by `pallet-revive`), `terminate` can never succeed again — exactly analogous to the paused-token blocking `stopRent`.

### Finding Description
`do_terminate` (`substrate/frame/revive/src/exec.rs:1793-1866`) performs contract destruction as an atomic, all-or-nothing operation: [1](#0-0) 

- It first calls `T::Deposit::refund_all(&contract_account, ...)` to release the storage-deposit hold.
- It then computes the *total balance* of the account (`AccountInfo::<T>::total_balance`, not merely the reducible/expendable balance) and calls `Self::transfer(...)` to sweep it to the beneficiary with `Preservation::Expendable`.
- The whole `delete_contract` closure is executed inside `with_transaction`, and any `Err` triggers `TransactionOutcome::Rollback`, undoing the termination entirely: [2](#0-1) 

The code comment even documents the intended (but exploitable-in-effect) behavior: [3](#0-2) 

`refund_all`'s underlying `refund_on_hold` was deliberately changed from `Precision::BestEffort` to a hard-failing precision so that a locked/held storage deposit now causes `refund_all` (and thus the whole terminate) to fail instead of silently under-refunding, per PR `pr_10302`: [4](#0-3) 

Separately, `refund_deposit`'s own error path documents the exact scenario where a contract's held balance can become permanently locked by an unrelated pallet (e.g. staking or governance) sharing the same `Currency`: [5](#0-4) 

If a runtime configuration allows any pallet (staking, conviction-voting, treasury-style locks, or a "pausable"/freezable fungible used as `T::Currency`) to place a freeze/hold on a contract's account balance that outlives the contract's own deposit-hold reasons, then:
1. The contract account never regains a fully "expendable" balance.
2. `Self::transfer` inside `delete_contract` (or `refund_all`) will always error.
3. `with_transaction` rolls back the entire termination.
4. `terminate`/`SELFDESTRUCT` becomes permanently unusable for that contract, exactly mirroring `stopRent` reverting forever due to a paused ERC721/1155.

This directly matches the "Public wrappers ... must not ... undercharge nested execution" and "contract-held value must ... settle exactly once" pivots: the terminate/self-destruct path is a public, permissionless entrypoint (`terminate` syscall/precompile) whose settlement can be indefinitely denied by state that is entirely legitimate (freezes/holds), not by a malicious actor.

### Impact Explanation
This is a permanent-fund-lock class issue: once a contract account carries an un-thawable freeze/hold under the shared `Currency` type, its storage-deposit hold and any native balance become permanently unrecoverable — `terminate` can never complete, the deletion queue entry is never created, and the contract's storage rent/deposit remains locked forever with no code path to reclaim it. This is stronger than the original report's "temporary DoS" because there is no external unpause mechanism analogous to a game re-enabling transfers — the lock is a first-class Substrate primitive (freeze/hold) that the runtime, not an external malicious actor, controls. It satisfies "permanent user-fund or bridge-state lock" from the Required Impacts.

### Likelihood Explanation
Likelihood depends on whether the runtime's `pallet-revive::Config::Currency` (and any hold reasons it recognizes) is shared with pallets that can freeze/hold balances outside pallet-revive's control (e.g., staking, conviction voting, or any freezable/pausable fungible asset backing). This is plausible in any parachain runtime that reuses its native `Balances`/`Currency` type across pallet-revive and governance/staking, since nothing in `do_terminate` special-cases or clears non-pallet-revive freezes before attempting the sweep. No malicious peer, validator, or admin is required — a contract's own held balance interacting with an unrelated pallet is sufficient.

### Recommendation
- In `do_terminate`, transfer only the *reducible* (non-frozen, non-held-by-others) balance to the beneficiary rather than the full `total_balance`, and explicitly define semantics for any un-transferable residue (e.g., leave a "ghost" balance-only account, or require an explicit unlock step before termination is retried).
- Decouple the mandatory-success balance sweep from the atomic termination transaction: allow termination/code deletion to proceed even if a small trailing sweep needs to be retried, mirroring the "decouple NFT claim from stopRent" mitigation recommended in the original report.
- Add regression tests that place an external freeze/hold on a contract account's `Currency` balance (unrelated to pallet-revive's own storage-deposit hold reasons) and assert `terminate` either succeeds after sweeping only the free portion, or fails with a documented, retryable error rather than silently blocking forever.

### Proof of Concept
1. Deploy a contract via `pallet-revive` (e.g., using the `MultiContributorStorage`/`Terminate` fixtures already in the test suite: [6](#0-5) ).
2. Fund the contract's mapped account and place a `Freeze`/`Hold` on part of its native balance via any pallet sharing `Currency` with `pallet-revive` (e.g., simulate a governance/staking lock as done in `substrate/frame/assets/src/tests.rs::set_frozen_balance` patterns, or `T::Currency::set_freeze`/`hold` directly in a unit test against the `pallet-revive` mock runtime).
3. Call `terminate` (via the `ISystem.terminate` precompile as in `MultiContributorStorage::terminate`, see [7](#0-6) ).
4. Observe that `Self::transfer` inside `do_terminate` fails because the frozen portion cannot be swept under `Preservation::Expendable`, `with_transaction` rolls back ( [8](#0-7) ), and the contract remains alive with its deposit permanently held — repeatable indefinitely with no way to clear the block from within pallet-revive itself.

Note: I was not able to fully verify, from the indexed content alone, whether any currently-deployed production runtime actually configures a shared `Currency`/freeze reason that a normal user can trigger against a contract's own account (this requires reviewing runtime-specific configs such as Asset Hub's `pallet-revive::Config`, which may be outside the indexed snippets). This should be confirmed in a full checkout before treating the impact as runtime-deployed.

	/// Call terminate and forward any revert.
    /// Internal dispatcher: executes termination by
    /// - delegatecall (METHOD_DELEGATE_CALL) to system precompile
    /// - direct call (METHOD_PRECOMPILE) to system precompile
    /// - selfdestruct (METHOD_SYSCALL) sending balance to beneficiary
	function _terminate(uint8 method, address beneficiary) private {
		bytes memory data = abi.encodeWithSelector(ISystem.terminate.selector, beneficiary);
		(bool success, bytes memory returnData) = (false, "");

		if (method == METHOD_DELEGATE_CALL) {
			(success, returnData) = SYSTEM_ADDR.delegatecall(data);
		} else if (method == METHOD_PRECOMPILE) {
			(success, returnData) = SYSTEM_ADDR.call(data);
		} else if (method == METHOD_SYSCALL) {
			assembly {
				selfdestruct(beneficiary)
			}
			// selfdestruct halts execution, so if we reach here, something went wrong.
			revert("selfdestruct opcode returned");
		} else {
			revert("Invalid TerminateMethod");
		}

		if (!success) {
			assembly {
				revert(add(returnData, 0x20), mload(returnData))
			}
		}
	}
