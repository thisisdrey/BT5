### Title
Outbound queue v2 ignores `DeliveryReceipt.success`, permanently reconciling failed Ethereum dispatches as settled and paying rewards for undelivered value - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The external report describes a bridge pool that keeps a "last known balance" for the counterparty chain, and when a cross-chain transfer fails irrecoverably, that ledger is never corrected — the pool believes more value has arrived on the other side than actually has, permanently distorting balance/fee accounting. The Snowbridge `EthereumOutboundQueueV2` pallet exhibits the direct local analog: it tracks in-flight cross-chain command execution via `PendingOrders`, and settles that state purely on “message was delivered”, never checking whether the commands encoded in the message (e.g. token unlock/mint on the Ethereum Gateway) actually succeeded.

### Finding Description
`Pallet::process_delivery_receipt` in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` (lines 446-480) is the settlement path for outbound messages sent from BridgeHub to Ethereum: [1](#0-0) 

It decodes a `DeliveryReceipt` produced from Ethereum's `InboundMessageDispatched(nonce, topic, success, reward_address)` event and:
1. Checks `gateway` matches the configured `GatewayAddress`.
2. Looks up the `PendingOrder` by `nonce`.
3. Unconditionally pays `order.fee` to the reward account via `T::RewardPayment::register_reward`.
4. Unconditionally removes the `PendingOrder` and emits `Event::MessageDelivered`.

The `success` field of `DeliveryReceipt` (`bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs`, lines 16-27) is decoded from the on-chain event but is **never read** anywhere in `process_delivery_receipt`: [2](#0-1) 

This event is emitted by the Ethereum Gateway after attempting to execute the commands encoded in the outbound message (token mint/unlock, `Transact`, etc. — see `do_process_message` at lines 346-443 of the same pallet file, which builds `OutboundCommandWrapper`s from `Message.commands`). On the Polkadot side, the assets referenced by a `ReserveWithdraw`/`Teleport`/native-unlock command are already burned/checked-out (via `AssetTransactor::check_out`/`withdraw_asset` in the XCM executor, `polkadot/xcm/xcm-executor/src/lib.rs` lines 787-813) **before** the message is queued into `PendingOrders`. If dispatch of those commands on Ethereum reverts or runs out of gas — a scenario the Gateway explicitly signals via `success: false` — the pallet still:
- Deletes the `PendingOrder` (marking the transfer as fully settled), and
- Pays the relayer a reward,

with no branch that reconciles the failed value transfer, no re-queueing, no compensating mint back on the source chain, and no distinct event/error path for `success == false`. This is functionally identical to the reported bug: a failed cross-chain transfer is recorded as if it succeeded, and there is no recovery mechanism to correct the resulting permanent drift between the value withdrawn on BridgeHub/AssetHub and the value actually realized on Ethereum.

### Impact Explanation
Every reserve-withdraw/teleport-out flow through Snowbridge V2 (e.g. `send_weth_from_asset_hub_to_ethereum`, `send_weth_and_dot_from_asset_hub_to_ethereum` in the integration tests) burns/locks the corresponding assets on the Polkadot side at enqueue time. If the Ethereum Gateway later fails to execute the mint/unlock commands (any out-of-gas, revert, or malformed-beneficiary condition on Ethereum), the pallet has no way to detect or correct this: the `PendingOrder` is removed as "delivered" regardless of `success`. The result is a permanent, unrecoverable loss of user funds and — because `PendingOrders`/fee accounting is the only on-chain ledger of in-flight bridge value — a permanent, growing bookkeeping drift between what BridgeHub/AssetHub believes was sent and what Ethereum actually received, mirroring the "growing gap" and "cannot accurately manage incentives through fees" impact called out in the source report. There is no admin/root-only path in this specific settlement flow that would exclude it from the impact gate — it is triggered purely by normal relayer submission of a legitimately-verified (BEEFY/light-client proven) receipt.

### Likelihood Explanation
This is not a hypothetical or malicious-actor-dependent path: `success: false` is an expected, protocol-defined outcome of the `InboundMessageDispatched` event whenever Gateway-side execution fails (e.g., insufficient gas limit computed by `GasMeter::maximum_dispatch_gas_used_at_most`, or a reverting ERC-20/agent call). Any honest relayer submitting a truthful, cryptographically verified delivery receipt for a failed dispatch will trigger this code path — no relayer misbehavior, governance action, or privileged access is required.

### Recommendation
Branch on `receipt.success` in `process_delivery_receipt`. On `success == false`, do not treat the order as normally delivered: emit a distinct `MessageDispatchFailed`/`MessageDeliveryFailed` event, and implement a recovery/reconciliation mechanism (e.g., allow the failed order value to be reclaimed or re-minted back to the original sender if the failure is provably unretryable), analogous to the "recv"/"withdrawConfirm" error handlers added in the referenced external fix. At minimum, do not silently equate "delivery receipt received" with "commands executed successfully" — track success/failure separately from the reward-payment/removal of the `PendingOrder`.

### Proof of Concept
1. On AssetHub, execute a `WithdrawAsset` + `InitiateTransfer` XCM sending WETH to Ethereum (as in `send_weth_from_asset_hub_to_ethereum`), which burns/checks-out the WETH on BridgeHub and enqueues a `PendingOrder{nonce, fee}` via `do_process_message`.
2. On Ethereum, have the Gateway's dispatch of the resulting `InboundMessageDispatched` command fail (e.g., due to gas exhaustion or an invalid beneficiary decode) — Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer proves this receipt and calls `submit_delivery_receipt` → `process_delivery_receipt(relayer, receipt)` with `receipt.success == false`.
4. Observe: `order.fee` is still paid via `T::RewardPayment::register_reward`, `PendingOrders::<T>::remove(nonce)` still executes, and `Event::MessageDelivered` is emitted — identical to the `success == true` path in `submit_delivery_receipt_succeeds_after_unhalt`/`poc_m1` tests (`bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs`). The WETH burned in step 1 is never recovered on the Polkadot side, and no on-chain state reflects the failure.
