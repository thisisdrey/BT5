### Title
Unsafe reliance on ERC20 boolean return value in `ERC20Transactor` allows accounting desync between XCM holding credits and real checking-account balance - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` move value into/out of a shared `TransfersCheckingAccount` by calling the target contract's `IERC20.transfer()` and trusting only its boolean return value, exactly the unsafe-ERC20 pattern described in the referenced report. They never verify that the checking account's real token balance actually changed by `amount`. Since `ERC20Matcher` permissionlessly treats *any* `AccountKey20` location as a valid asset id pointing to an arbitrary user-deployed `pallet-revive` contract, any unprivileged user can create an ERC20-like contract whose `transfer()` returns `true` while moving less (fee-on-transfer/deflationary) or more/less-than-declared amounts, corrupting the shared checking-account accounting used by this transactor for that asset.

### Finding Description
`withdraw_asset_with_surplus` calls `transfer(checking_account, amount)` and, on `true` return, unconditionally credits `Erc20Credit(amount)` — the full nominal `amount` — into the XCM `AssetsInHolding` register: [2](#0-1) 

`deposit_asset_with_surplus` mirrors this by debiting `amount` from the checking account via `transfer(beneficiary, amount)`, again trusting only the boolean return: [3](#0-2) 

Neither path measures the actual `balanceOf` delta on the checking account. For any ERC20-like contract that:
- Takes a transfer fee (deflationary/reflection tokens), or
- Rebases, or
- Simply implements `transfer()` to return `true` unconditionally regardless of internal balance movement,

the amount credited into XCM's holding register (and later debited from the same shared checking account for a *different* XCM message/user) diverges from the real token balance actually held by `TransfersCheckingAccount` for that asset id. Because the checking account is shared across all users transacting the same asset id, this creates a systemic accounting deficit: nominal credits recorded via XCM execution outpace the real balance backing them.

This is a direct structural analog of the reported bug class (blind trust in ERC20 return values without accounting for non-conforming token behavior), and the repository's own regression test confirms that *any* deployed contract can be targeted this way without registration: [4](#0-3) 

The matcher backing this transactor is fully permissionless — it accepts any `H160` embedded in an `AccountKey20` junction as a valid asset id: [5](#0-4) 

Existing guards (revert check, ABI-decode-validate of the boolean) only reject the "hard failure" cases (revert / undecodable return) — they do **not** detect "soft" non-conformance where `transfer()` returns `true` but moves an amount different from what was requested, which is exactly the class of behavior the referenced report warns about.

### Impact Explanation
Since the checking account's real balance for a given asset id is shared across all XCM transactions referencing that asset id, a systemic desync between nominal (accounted) and real balances constitutes an unbacked-accounting condition for that asset: nominal XCM credits are not fully backed by real tokens. This can (a) cause later legitimate users' `deposit_asset` calls to revert once the checking account is drained below what nominal accounting implies (permanent fund lock/DoS for that in-flight XCM operation's trapped assets), and (b) in the case of a contract crafted to always return `true` on `transfer()` irrespective of real balance movement, allow a value mismatch that lets a caller extract more real token value out of the checking account than was ever deposited into it via other operations touching the same asset id — an unbacked-value condition. This satisfies the "theft or unbacked mint/unlock" and "permanent user-fund or bridge-state lock" impact categories.

### Likelihood Explanation
High, given: no privileged action is required (deploying an arbitrary `pallet-revive` contract and driving XCM `execute`/`transfer_assets` is fully permissionless), the asset-id matcher accepts any `AccountKey20` address unconditionally, and the transactor's success criterion is solely the boolean return of `transfer()` rather than a verified balance delta.

### Recommendation
Compute the actual balance delta of the checking account (and beneficiary) via `balanceOf()` before and after the `transfer()` call, and use that measured delta — not the requested `amount` — as the value credited to/debited from the XCM `AssetsInHolding` register. Reject or explicitly account for any mismatch between requested and actually-moved amounts, mirroring the "use `SafeERC20`-style verified transfer" recommendation from the original report.

### Proof of Concept
1. Deploy on `pallet-revive` a Solidity contract implementing `IERC20` where `transfer(to, value)` always returns `true` but internally moves `value - fee` (or, for the worst case, moves `0`) to `to`.
2. Reference this contract as an XCM asset via `Location::new(0, [AccountKey20 { key: <contract_address>, network: None }])` — no registration needed, matching the pattern already exercised in `smart_contract_does_not_return_bool_fails`.
3. Submit an XCM program via `PolkadotXcm::execute` that `WithdrawAsset`s this "asset" from the caller (invoking `ERC20Transactor::withdraw_asset_with_surplus`), which credits the full nominal `amount` to holding based only on the `true` return, while the checking account's real balance only increases by `amount - fee` (or not at all).
4. Repeat/chain such operations (or have a legitimate holder of a real deflationary ERC20 use the pathway organically) until the checking account's real balance for that asset id is less than the sum of nominal amounts recorded as available; a subsequent legitimate `deposit_asset_with_surplus` for that same asset id then fails or, depending on downstream fee-token behavior, allows extraction exceeding what was actually deposited. /// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}
