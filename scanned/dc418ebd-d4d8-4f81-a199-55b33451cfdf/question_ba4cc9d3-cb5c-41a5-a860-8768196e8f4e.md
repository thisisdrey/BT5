Target: `Contract::notify_on_transfer` static helper used by both `Transfer::execute_intent` (core) and NEP-245 `mt_on_transfer` (`contracts/defuse/src/contract/tokens/nep245/deposit.rs`), and its paired `mt_resolve_transfer` / `mt_resolve_deposit` callbacks. Attacker deploys a receiver contract implementing `MultiTokenReceiver::mt_on_transfer` that returns a crafted `Vec<U128>` refund array claiming zero was used (full refund) while ALSO, within the same `on_transfer` call, re-entering `execute_intents` to withdraw the tokens it just nominally 'refused' before `mt_resolve_transfer` runs its `resolve_deposit_internal`/`resolve_transfer_internal` logic that trusts `promise_result_checked_json_with_len::<Vec<U128>>(0, ...)`. Precondition: attacker's contract is named `receiver_id` in a `Transfer{notification: Some(NotifyOnTransfer{..})}` intent, tokens already credited to attacker's Verifier account before the promise fires. Call sequence: `notify_on_transfer` -> attacker's `mt_on_transfer` re-enters `execute_intents` withdrawing the full credited balance via `FtWithdraw`/`MtWithdraw` -> returns full-refund array -> `mt_resolve_transfer`'s `resolve_deposit_internal` reads `receiver.token_balances.amount_for(&token_id)` (now zero after the reentrant withdraw) and caps the refund at `balance_left`, so the resolver silently refunds 0 instead of the claimed amount, but the sender was already debited the full transferred amount with no compensating credit. Binding: value debited from sender == value delivered to receiver (net of any refund actually re-credited by `resolve_deposit_internal`'s `refund_amount = requested_refund.min(*deposited).min(balance_left)`); if `balance_left` is manipulated via reentrant withdrawal between debit and resolve, refund_amount < what sender is owed. Impact: Critical, sender loses tokens with no matching refund because the resolver's `balance_left` check is defeated by reentrant self-withdrawal. Proof: cargo test/sandbox test reproducing this sequence and asserting sender's balance-after == balance-before minus (amount actually retained by receiver), i.e. SETTLEMENT invariant.
