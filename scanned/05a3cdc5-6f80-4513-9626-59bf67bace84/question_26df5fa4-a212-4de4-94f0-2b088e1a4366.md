Target: `Contract::internal_on_auth`-style reentrancy surface generalized: any attacker-deployed contract implementing `AuthCallee::on_auth` (crates/near/auth-call/src/lib.rs) that, upon being called by `do_auth_call`, issues a **synchronous low-level `Promise::new(intents_verifier).function_call("execute_intents", ...)`** carrying a SEPARATE valid signed payload from a DIFFERENT signer who granted the attacker's contract account a public key via a prior `AddPublicKey` intent, exploiting the fact `on_auth`'s only authorization check recommended (not enforced) is `predecessor_id` whitelisting — the Verifier itself does NOT restrict which `contract_id` an `AuthCall` may target, and does NOT restrict what that target does afterward. Precondition: a separate victim-controlled account (or attacker's second account acting as "victim") previously executed `AddPublicKey` intent registering attacker_contract's derived key OR the attacker is simply signer of the second payload (self-authorized, not third-party). Call sequence: payload1 `AuthCall{contract_id: attacker_contract}` -> `on_auth` -> attacker_contract submits payload2 (its own valid signature) to `execute_intents` reentrantly. Binding: `(signer_id, public_key)` authorised by payload2's signature == pair actually used; since payload2 is validly signed by attacker for their own account, this is authorized — the real check is whether reentrant `execute_intents` calls can process a nonce/nonced payload for a DIFFERENT signer_id than the one that triggered the AuthCall, and whether that could let attacker settle a THIRD PARTY's stale but still-valid-looking payload out of expected order/context (e.g., a payload with a far-future deadline intended for later use, replayed earlier via reentrancy to front-run a state change). Impact: Critical if reentrancy allows executing a legitimately-signed-but-not-yet-submitted third-party payload in a context that changes its effect (e.g., before a `TokenDiff` counter-offer is available), causing settlement against a worse rate/state than the signer expected — an authorization/timing violation. Proof: cargo test where a valid third-party payload with a long deadline is executed via attacker-triggered reentrancy at an earlier state than the relayer intended, asserting the resulting balance changes equal exactly what the signature authorizes regardless of trigger path/timing, or documenting a timing-dependent settlement discrepancy.
