Target: `TokenId` borsh serialization (`borsh(use_discriminant = true)` on the enum) versus the JSON/`Display` string form used in `MultiPayload`/`DefusePayload` signing. Attacker signs a `MultiPayload` whose JSON encodes a `TokenId` field as the string `"nep141:realtoken.near"`, but crafts the payload so that after `serde` deserialization the resulting in-memory `TokenId::Nep141` gets borsh-serialized into `token_balances` storage using the enum's `#[repr(u8)]` discriminant `0`. Precondition: verify no other variant's discriminant (`1`,`2`,`3`) can be coerced to also read back as variant `0` due to a borsh schema mismatch between the JSON-signed payload and the on-chain storage schema. Call sequence: `execute_intents` deserializes the signed JSON `TokenId` (via `DeserializeFromStr`) then stores it under its borsh encoding in `token_balances`; a later withdrawal re-reads the SAME storage entry via borsh and must decode back to `TokenId::Nep141(Nep141TokenId{contract_id: realtoken.near})`. Binding: `borsh::from_slice::<TokenId>(&borsh::to_vec(&t).unwrap()).unwrap() == t` for every `t` reachable via attacker-signed JSON, matching the existing `borsh_roundtrip` test pattern in `crates/primitives/token-id/src/lib.rs`. Impact: Critical if any signed JSON `TokenId` fails this round-trip, since the debited key and the stored/withdrawn key would diverge.
