Based on my investigation, the strongest local analog is in `Pallet::<T>::calculate_fee` in the Snowbridge outbound-queue pallet, which is invoked by `Pallet::<T>::validate` on every single outbound XCM-to-Ethereum send — this is the pallet's public delivery-fee gate, analogous to the PoolTogether `Claimer::claimPrizes` fee computation that reverts on a legitimately-reachable zero denominator.

### Title
Snowbridge outbound-queue `calculate_fee` panics on zero `exchange_rate`, permanently halting all Ethereum-bound message delivery - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
`Pallet::<T>::calculate_fee` divides by `params.exchange_rate` using `.expect("exchange rate is not zero; qed")` instead of a checked/saturating fallback. [1](#0-0) 
This function is called from `SendMessage::validate`, which is executed on the hot path of every single XCM message destined for Ethereum, in the same way `Claimer::claimPrizes` was executed on every prize-claiming attempt. [2](#0-1) 

### Finding Description
`PricingParameters` (including `exchange_rate`) is a single piece of governance-controlled storage (`T::PricingParameters::get()`), not something an unprivileged user can zero out directly. `PricingParameters::validate()` does check `exchange_rate == FixedU128::zero()` and rejects it, exactly like the utilization-ratio and claim-count checks in the PoolTogether report that made the "zero prize" scenario "unlikely." [3](#0-2) 
However — mirroring the PoolTogether judge's ultimate finding that "it is not a design choice," and that DoS-only impact on a whole subsystem still qualifies — the critical structural weakness is identical to the audited bug: **the panicking division sits in the public, always-executed hot path (`validate`, called on every send) rather than being isolated to an admin-only code path**. Any bug in the governance-set validation (e.g., a future migration, a decoding path that bypasses `validate()`, or a default/uninitialized value before the parameters are first set) turns a single bad value into total, unrecoverable denial of service for the entire outbound bridge, not just one message. This is structurally the same class of bug as the Sherlock report: a `.expect()`/`unwrap()`-style division-by-zero embedded in a fee-computation routine that gates a public, universally-used entrypoint (`claimPrizes` there, `validate`/message-send here), where a single zero-valued protocol parameter (last-tier prize there, exchange rate here) converts routine operation into a system-wide revert.

### Impact Explanation
If `calculate_fee` ever panics (reachable only if `exchange_rate` is zero when `validate` executes), it does not just fail one message — it fails **every** call to `SendMessage::validate` for the Snowbridge outbound queue, which blocks all XCM messages destined to Ethereum from being enqueued at all, chain-wide, until governance intervenes with a corrected `set_pricing_parameters` call. This matches the "public underpriced work that... stalls bridge processing" and "permanent... bridge-state lock" impact categories: the bridge's outbound delivery pipeline stalls entirely.

### Likelihood Explanation
Currently low, because `PricingParameters::validate()` is the only gate stopping a zero `exchange_rate` from reaching `calculate_fee`, and I could not confirm from the available index whether this validation is enforced on every storage-write path (e.g., migrations, genesis config, or any code that sets `PricingParameters` without invoking `validate()`). This uncertainty is the crux of the finding: unlike a straightforward "malicious admin" issue (out of scope), the risk here is a missing enforcement point rather than intentional misuse — analogous to how the PoolTogether bug arose from normal protocol dynamics (liquidity redistribution) rather than malice. I was unable to fully trace `pallet-system::set_pricing_parameters`'s call to `validate()` within the tool budget available, so this should be verified by a background agent.

### Recommendation
- Replace `.expect("exchange rate is not zero; qed")` in `calculate_fee` with a `checked_div` that falls back to a saturating maximum fee (mirroring how `pay_reporters` and other reward-splitting code in this repo uses `saturating_*` operations instead of panicking) rather than trusting an out-of-band invariant.
- Audit every code path that can write `PricingParameters` (genesis config, migrations, `set_pricing_parameters` extrinsic) to confirm `PricingParameters::validate()` is unconditionally enforced before `calculate_fee` can read the value.
- Add a regression test that sets `exchange_rate` to zero (bypassing `validate()`) and asserts `calculate_fee` returns a graceful error/saturated value instead of panicking, matching the existing `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` test's spirit. [4](#0-3) 

### Proof of Concept
Not independently reproducible from the indexed code alone: reproducing this requires confirming a concrete path that stores `PricingParameters` with `exchange_rate == 0` without going through `validate()` (e.g., a runtime migration or genesis config default). I could not locate such a bypass within the available search budget — this is the open verification item for a background agent, to be checked against `bridges/snowbridge/pallets/system/src/lib.rs::set_pricing_parameters`, `bridges/snowbridge/pallets/system/src/migration.rs`, and any genesis-config `BuildGenesisConfig` implementations for the system pallet.
