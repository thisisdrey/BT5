### Title
Remote fee for Snowbridge outbound messages can silently round to zero due to fixed-point rescaling bug - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

### Summary
`Pallet::<T>::calculate_fee` in the Snowbridge outbound-queue pallet computes the remote (Ethereum-side) delivery fee by reinterpreting a raw wei integer as a `FixedU128` value and then rescaling decimals twice. With legitimate, non-zero `PricingParameters`, this can make the computed remote fee round down to `0`, i.e. the exact "minimum premium when it should be expensive" failure pattern from the Carapace report: a value that should reflect real economic cost collapses to the degenerate minimum because of how a fallback/rescaling path handles small or edge-case inputs.

### Finding Description
`calculate_fee` computes the raw remote cost in wei as `fee_per_gas * gas_used_at_most + reward` (`calculate_remote_fee`), then: [1](#0-0) 

```
let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);
let fee = FixedU128::from_inner(fee)
    .saturating_mul(params.multiplier)
    .checked_div(&params.exchange_rate)
    .expect("exchange rate is not zero; qed")
    .into_inner();
let fee = Self::convert_from_ether_decimals(fee);
```

`FixedU128::from_inner(fee)` treats the raw wei integer as an already-scaled fixed-point number (implicit division by `10^18`), and `convert_from_ether_decimals` then divides again by `10^(18 - local_decimals)` (e.g. `10^8` for a 10-decimal chain such as DOT). This double rescaling means the raw wei value must exceed roughly `10^8`–`10^10` (depending on chain decimals) merely to survive integer division without collapsing to zero — independent of whether `fee_per_gas`, `reward`, `multiplier`, and `exchange_rate` are all valid, non-zero, in-range parameters set by governance in the normal way.

This is directly analogous to the Carapace bug: there, a legitimate-but-degenerate input (`_totalCapital < minRequiredCapital`) caused the "cannot calculate risk" fallback to silently substitute the *minimum* premium instead of a correctly-scaled (and here, correctly expensive) one. In this codebase, a legitimate-but-small combination of `fee_per_gas`/`gas_used`/`reward` causes the fixed-point rescaling to silently collapse the *actual* remote fee to `0`, even though the inputs are all valid and non-zero.

The bug is explicitly reproduced and acknowledged in the pallet's own test suite: [2](#0-1) 

```
#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	...
	let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
	assert_eq!(fee.local, 698000000);
	// Though none zero pricing params the remote fee calculated here is invalid
	// which should be avoided
	assert_eq!(fee.remote, 0);
}
```

This zero-fee value flows unguarded into the public, unprivileged message-send path. `Pallet::<T>::validate` (the `SendMessage::validate` implementation used by every outbound message, governance and user alike) calls `calculate_fee` directly and returns the result as the fee to be charged to the caller before the message is queued for delivery to Ethereum: [3](#0-2) 

There is no guard (`ensure!(fee.remote > 0, ...)` or similar) rejecting a degenerate zero remote fee before the ticket is validated and the message is admitted to the queue via `deliver`. The message-level pricing documentation itself states the intended invariant: [4](#0-3) 

i.e. `RemoteFee(Message) = MaxGasRequired * MaxFeePerGas + Reward`, scaled by exchange rate and multiplier — the fixed-point rescaling silently violates this documented formula for a real, reachable parameter range.

### Impact Explanation
The remote fee is the amount that is supposed to reimburse relayers on Ethereum for gas plus reward for delivering the message. If `calculate_fee` returns `remote = 0` while the message is still queued and eventually dispatched to Ethereum requiring real gas and a real relayer reward, one of two outcomes occurs:
- The sender is undercharged (pays only the local fee), meaning "public underpriced work" is admitted into the outbound queue — degrading the bridge's economic model and its relayers' incentive to service messages, which can stall bridge delivery for accepted-but-unfunded messages, matching the "public underpriced work that degrades block production or stalls bridge processing" impact category.
- Any downstream charge tied to `fee.remote` (e.g. reward escrow for relayers) is silently set to zero even though the pricing parameters were configured as intended, breaking the fee-settlement invariant that message queue/payout state should reflect the correct configured cost before advancing.

### Likelihood Explanation
This does not require a malicious relayer, prover, validator, or governance actor — it is a pure arithmetic/rescaling defect triggerable by an ordinary unprivileged caller of `validate`/`deliver` whenever the currently governance-configured `PricingParameters` (fee_per_gas, reward, exchange_rate, multiplier) combined with a message's gas usage produce a raw wei amount below the rescaling threshold (~`10^8` for a 10-decimal chain). The pallet's maintainers have already reproduced this exact scenario in a dedicated regression test with the comment "which should be avoided," confirming the codebase itself recognizes the computed value is invalid, but no corrective guard currently exists in `calculate_fee` or `validate`.

### Recommendation
In `calculate_fee` (`bridges/snowbridge/pallets/outbound-queue/src/lib.rs`), avoid the double implicit rescaling: perform the multiplier/exchange-rate adjustment using types that preserve wei-level precision (e.g. rational arithmetic on `U256`/`u128` without reinterpreting the raw integer as an already-scaled `FixedU128`), or perform the decimal conversion once, consistently, before or after the ratio math—not both. Additionally, add an explicit check in `validate`/`calculate_fee` that rejects (or defensively upgrades) a computed `remote` fee of `0` when the underlying raw parameters (`fee_per_gas`, `reward`) are non-zero, so that underpriced messages cannot be silently admitted to the outbound queue.

### Proof of Concept
The existing unit test in the repository is itself a working PoC: [2](#0-1) 

With `fee_per_gas = 1`, `reward = 1`, `gas_used = 250000`, `exchange_rate = 1`, `multiplier = 1` (all valid, non-zero parameters), `calculate_fee` returns `fee.remote == 0`. Any message sent through `OutboundQueue::validate` under equivalent low-magnitude pricing parameters will be queued and later delivered to `send_message_impl::deliver` with a real local fee charged but zero remote fee reserved for the relayer, even though `MessageQueued`/`MessageAccepted` events are emitted and the message is committed to the outbound Merkle root as if pricing succeeded normally.

```rust
		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}
```

```rust
	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}
```
