## Analysis

The strongest local analog to the reported "isContract-based signature/logic broken under EIP-7702" bug class is `address_runs_no_code` in `substrate/frame/revive/src/lib.rs`, which is used by `is_simple_transfer` to short-circuit `eth_estimate_gas`.

### Title
Gas Estimation Short-Circuit Misclassifies EIP-7702 Delegated EOAs as Code-Free Addresses - (File: `substrate/frame/revive/src/lib.rs`)

### Summary
`Pallet::address_runs_no_code` decides whether a destination address executes any code by checking `RUNTIME_PALLETS_ADDR`, `is_precompile`, and `<AccountInfo<T>>::is_contract(address)` only. It has no notion of EIP-7702 delegation designators. This is precisely the report's bug class: code makes a binary EOA-vs-contract decision that becomes stale once EIP-7702 lets an EOA carry delegated code, causing the classification to silently diverge from actual execution behavior.

### Finding Description
`is_simple_transfer` treats a transaction as a "plain value transfer" if it has no calldata/access-list/blob fields **and** `address_runs_no_code(&to)` is true [1](#0-0) . `address_runs_no_code` itself contains an explicit acknowledgment of the gap:

```
// TODO(eip-7702): also reject delegated (authorized) destinations once EIP-7702
// delegations land, since a transfer to one executes the delegate's code.
*address != RUNTIME_PALLETS_ADDR &&
    !exec::is_precompile::<T, ContractBlob<T>>(address) &&
    !<AccountInfo<T>>::is_contract(address)
``` [2](#0-1) 

`AccountInfo::is_contract` only inspects the pallet-native `AccountInfoOf` storage entry and matches on `AccountType::Contract(_)` [3](#0-2) . It has no relationship to EIP-7702 authorization/delegation, which is already modeled in the transaction layer (`Transaction7702Signed`/`AuthorizationListEntry`) [4](#0-3) , but the delegation-designator bookkeeping (making a signed EOA point at delegate code, à la the `0xef0100` marker in mainnet EIP-7702) is not yet implemented/consulted anywhere `is_contract`/`address_runs_no_code` is evaluated.

This mirrors the external report's core broken invariant exactly: a piece of logic assumes "no stored contract record ⇒ no code executes at this address," which is only true until an EOA is delegated. Once delegation exists, an address that is nominally an EOA (no `ContractInfo` in `AccountInfoOf`) can execute delegate code, but `address_runs_no_code` will still return `true`.

### Impact Explanation
`is_simple_transfer` is used to short-circuit `eth_estimate_gas`: when it evaluates `true`, the estimator skips the full binary-search dry-run loop and returns the result of a single `dry_run_at(high)` call, assuming the transfer is a fixed-cost, code-free operation [5](#0-4) . If `to` is (or becomes, via a landed EIP-7702 authorization) a delegated EOA that actually runs delegate code, this short-circuit produces a gas estimate that reflects only a bare transfer, not the delegate execution. Wallets/clients relying on `eth_estimate_gas` would submit transactions with insufficient gas, causing execution failures (out-of-gas reverts) once the recipient's delegated code runs. This is exactly the "public underpriced work" pattern called out in the impact gate: an unprivileged caller (anyone querying `eth_estimate_gas` for a transfer to a delegated address) gets a wrong, under-priced gas figure purely from mis-classification logic, not from any privileged/relayer/prover assumption.

### Likelihood Explanation
Likelihood is currently constrained by the fact that EIP-7702 authorization-list *processing* (i.e., actually writing a delegation designator against an EOA's account) is not confirmed to be wired up elsewhere in this snapshot — the code itself flags this as a pending `TODO(eip-7702)`. This means the flaw is real and reachable via the public `eth_estimate_gas` RPC/runtime API path today, but its practical severity depends on whether/when EIP-7702 delegation execution semantics are completed in `pallet-revive`. As written, the comment is a maintainer-acknowledged forward-looking gap rather than a confirmed exploited state — I was not able to locate the delegation-application code path in this pass to confirm whether delegated code already affects `code_size`/execution while `AccountInfo::is_contract` still reports `false`. This uncertainty should be resolved before treating this as fully live.

### Recommendation
Extend `address_runs_no_code` (and any other `AccountInfo::is_contract`-style code-presence check used for classification/estimation decisions) to also query whether the address has an active EIP-7702 delegation designator, and treat delegated addresses as "runs code" for the purposes of `is_simple_transfer`. Until EIP-7702 delegation is fully implemented, this check should conservatively fail closed (treat any address that could plausibly be delegated, or disable the short-circuit) rather than assuming absence of a native `ContractInfo` implies no code execution.

### Proof of Concept
1. Land/enable an EIP-7702 authorization mechanism (or, once implemented, submit an authorization tuple) that delegates EOA `X` to run contract code `C`.
2. Call `eth_estimate_gas` for a plain-looking transfer (`to: X`, empty `input`, no access list) — `has_simple_transfer_fields()` returns `true`.
3. `address_runs_no_code(&X)` returns `true` because `AccountInfo::is_contract(&X)` is `false` (no native `ContractInfo` exists for `X`) and `X` isn't a precompile or the runtime pallets address.
4. `is_simple_transfer` short-circuits to a single `dry_run_at(high)` that does not account for delegate code execution cost, returning an under-estimated gas figure.
5. A transaction built with that gas limit against `X` fails at execution time once delegate code `C` actually runs, because the estimate never modeled it.
