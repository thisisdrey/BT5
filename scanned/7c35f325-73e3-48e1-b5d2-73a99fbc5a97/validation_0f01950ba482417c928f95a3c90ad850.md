## Analysis

The external ERC777 report's core broken invariant is: **a settlement flow marks itself "complete" and discards recoverable state as soon as a transfer/handoff step *returns without error*, even though the recipient side can still fail asynchronously** (the `tokensReceived` hook reverting after `stopRent` had already assumed success). The concrete local analog is in the bridge relayer reward-claim flow.

`do_claim_rewards` in the bridge relayers pallet takes the relayer's accumulated reward balance out of storage and calls `T::PaymentProcedure::pay_reward`; the removal is only rolled back if `pay_reward` itself returns `Err`: [1](#0-0) 

For `BridgeReward::Snowbridge`, the payment procedure is `PayAccountOnLocation`, wired in via `BridgeRewardPayer`: [2](#0-1) 

`PayAccountOnLocation::pay_reward` treats the reward as "paid" the moment `XcmSender::deliver(ticket)` succeeds — i.e. the moment the XCM instruction (an `UnpaidExecution` + `ReserveAssetDeposited` + `DepositAsset` mint on AssetHub) is merely *enqueued* for cross-chain delivery, not once it is actually executed and the beneficiary's balance is credited: [3](#0-2) 

### Why existing guards don't stop this

- `do_claim_rewards`'s `try_mutate_exists` only reverts the `RelayerRewards` removal if `pay_reward` returns `Err` synchronously; it has no visibility into whether the *remote* XCM (`ReserveAssetDeposited`/`DepositAsset` on Asset Hub) ever actually executes.
- Unlike the Treasury pallet's asset-spend flow, which explicitly models this exact "payment initiated but not yet confirmed" gap with a `PaymentState::{Attempted, Failed}` state machine and a `check_status`/retry dispatchable, the bridge-relayers reward flow has **no equivalent retry or failure-recovery path** — once the local ledger entry is deleted, the claim is gone permanently, regardless of what happens to the XCM afterwards.
- Remote failure is a realistic path, not a contrived one: the emulated test suite itself demonstrates that XCM programs delivered through this exact inbound/outbound pipeline can fail on the destination chain and leave assets stranded (`AssetsTrapped`), while the fee/reward side of the same message is unconditionally registered regardless of remote outcome, showing the settlement and the ledger update are not atomically linked: [4](#0-3) 

### Impact

A relayer who claims a Snowbridge reward pays the local XCM-send fee and has their `RelayerRewards` entry deleted as soon as `deliver()` succeeds. If the destination-side execution subsequently fails (Barrier rejection, unregistered/paused foreign asset, decode/weight issues on Asset Hub, congested/suspended HRMP channel causing the message to be dropped or discarded by `pallet_message_queue`'s permanent-error paths), the reward is **never minted to the beneficiary**, yet the chain's local bookkeeping already shows it as settled with no way to re-claim it. This is a permanent, irrecoverable loss of relayer-earned funds triggered by ordinary asynchronous cross-chain failure modes — not by a malicious relayer, validator, or governance actor.

### Recommendation
Do not remove/finalize the `RelayerRewards` entry (or equivalent local settlement marker) purely on successful XCM enqueue. Model the Snowbridge reward payout the same way the Treasury pallet models `AssetSpendApproved`/`Attempted`/`Failed`/retry: keep the claim in an "attempted" state until a delivery/execution receipt (or timeout) confirms remote settlement, and provide a `check_status`/retry or refund path for the attempted-but-unconfirmed case.

### Proof of Concept (conceptual, since this requires cross-chain XCM execution not reproducible purely in this repo's unit tests)
1. Relayer accrues a `BridgeReward::Snowbridge` reward via `register_reward`.
2. Relayer calls `claim_rewards_to` with a beneficiary `Location` on Asset Hub.
3. `PayAccountOnLocation::pay_reward` builds and sends an `UnpaidExecution` XCM containing `ReserveAssetDeposited` + `DepositAsset`; `XcmSender::deliver` succeeds (message enqueued), so `pay_reward` returns `Ok`.
4. `do_claim_rewards`'s `try_mutate_exists` commits, permanently removing the relayer's `RelayerRewards` entry and emitting `RewardPaid`.
5. On Asset Hub, the XCM program fails during execution (e.g. the foreign-asset registration is momentarily paused, the Barrier rejects the `UnpaidExecution` due to an unrelated config change, or the message is dropped from an overloaded HRMP queue) — no ETH-denominated asset is ever deposited into the beneficiary account.
6. The relayer has no recourse: the reward is gone from `RelayerRewards`, `RewardPaid` was already emitted, and there is no retry/check-status call analogous to `pallet_treasury::check_status`/`payout` to recover or re-attempt the payment.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
