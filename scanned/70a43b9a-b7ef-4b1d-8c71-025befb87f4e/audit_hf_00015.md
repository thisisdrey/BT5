# [H] PORT-3 | swapOnUniswap has 0 slippage protection

## Summary
Severity: High
Contest weight: 0.1043
Dataset id: 91
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability consists of missing slippage protection in the functions that execute token swaps on Uniswap when a user removes margin or when the protocol liquidates a position. Because the swap call does not enforce a maximum acceptable price deviation, an attacker controlling the transaction ordering (typically a MEV bot) can place a trade immediately before the victim's transaction (front‑run) to move the pool price, then allow the victim's swap to execute at the manipulated price, and finally execute a back‑run trade to restore the original price. This sandwich pattern enables the attacker to capture a portion of the value that should have been transferred to the user or to the protocol's liquidity pool. The root cause is the lack of a slippage tolerance parameter and the design choice to perform the swap atomically within the removeMargin and liquidate paths, rather than separating asset seizure from price conversion. Exploitation occurs whenever a user initiates a margin removal or a liquidation while the pool price is susceptible to rapid change, which is common on public AMMs where anyone can submit a transaction. The impact includes users receiving less tokens than expected, margins being drained, or the AMM losing value, effectively leading to funds disappearing from user balances and reduced liquidity for the protocol. The issue affects all participants who interact with these functions – regular traders, lenders, borrowers, and the protocol itself – because the underlying accounting assumptions (that the swap will execute at the market price at the moment of call) are violated. The problem was discovered during a manual security audit performed by Guardian, where the auditor noted that the swap calls lacked any price‑limit checks and therefore constituted a classic sandwich‑attack surface. The flaw is subtle because the transaction appears successful on‑chain; only a careful analysis of price movement and the token amounts received reveals the discrepancy, making it hard for users to detect without off‑chain monitoring. To remediate, the contract should be refactored to accept a user‑defined slippage tolerance for any swap that is part of a margin‑related action, and liquidators should be allowed to seize collateral and transfer it to a designated vault without performing an immediate swap. The seized assets can then be swapped in a separate transaction where slippage can be bounded. This design eliminates the need for a time‑critical price conversion within the same block and restores the intended accounting guarantees of the protocol.

## Recommendation
Allow users to provide a slippage tolerance when they are initiating an action that should have a slippage tolerance. Upon liquidations, consider refactoring the design such that liquidators are able to seize the assets and transfer them to the IVXLP contract without swapping them. The seized assets can be swapped in a separate transaction.
