Target: `Nep413DefuseMessage<T>` and `DefusePayload<T>` both using `#[serde(flatten)]` on the `message: T` field (contracts/defuse/core/src/payload/nep413.rs and payload/mod.rs). Attacker action: signs a legitimate NEP-413 payload where the outer `Nep413Payload.message` JSON string contains both a top-level `signer_id` key (consumed by `Nep413DefuseMessage`) AND, nested inside the flattened `T = DefuseIntents`, a duplicate/conflicting key such as `signer_id` or `nonce` that serde's flatten resolves ambiguously (last-key-wins or silently ignored) so the final decoded `DefusePayload.signer_id` differs from what a human/wallet UI displayed when confirming the signature. Preconditions: victim's wallet displays only `Nep413Payload.message` raw string without canonicalizing duplicate JSON keys; attacker submits this crafted message to be signed via UI showing benign preview but embedding a shadow field. Call sequence: `Nep413::verify` confirms signature over the raw message bytes (hash includes exact bytes signed) -> `Nep413DefuseMessage::extract_defuse_payload` -> `serde_json::from_str` on the message -> flatten field-shadowing resolves `signer_id`/`nonce`/`deadline` to attacker's injected duplicate value rather than the one the victim visually confirmed. Binding: the `signer_id`/`nonce`/`deadline` bytes hashed and signed by the victim (`Payload::hash()` over `self.payload` verbatim) must equal exactly the `DefusePayload` fields the engine later authorizes/executes against — a duplicate-key JSON breaks this 1:1 mapping. Impact: Critical, an intent executes with a `signer_id`/`nonce`/`deadline` combination the signer did not actually intend, potentially bypassing the nonce replay-protection entirely (see REPLAY binding) or targeting a different account's balance. Proof: cargo test constructing a JSON string with duplicate `signer_id` keys (top-level vs nested in flattened intents map) and asserting `serde_json::from_str::<DefusePayload<DefuseIntents>>` behavior against `Nep413::prehash` computed over the exact same bytes, verifying no field-shadowing discrepancy exists between what's hashed and what's executed.
