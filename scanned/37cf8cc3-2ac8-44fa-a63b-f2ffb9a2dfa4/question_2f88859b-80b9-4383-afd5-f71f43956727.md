Target: `Engine::execute_signed_intent` (contracts/defuse/core/src/engine/mod.rs) and `MultiPayload::verify`/`extract_defuse_payload` (contracts/defuse/core/src/payload/multi.rs). Attacker crafts a `MultiPayload::Erc191(SignedErc191Payload{payload, signature})` where `payload` is a JSON string that both parses as valid ERC-191 signed text AND deserializes via `serde_json::from_str::<DefusePayload<DefuseIntents>>` into a `DefusePayload{signer_id: victim.near, ...}` even though the actual secp256k1 key that signed it recovers to the attacker's own Ethereum-derived key. Preconditions: victim account `victim.near` already has some `PublicKey::Secp256k1` OR falls into the implicit-account fallback branch of `StateView::has_public_key`. Call sequence: attacker submits `execute_intents([multipayload])` -> `signed.verify()` recovers attacker's `Secp256k1UncompressedPublicKey` -> `extract_defuse_payload()` returns `signer_id = victim.near` -> `self.state.has_public_key(&victim.near, &attacker_pubkey)` is checked. Binding: `(signer_id, public_key)` the engine authorizes with (`victim.near`, attacker_key) must equal the pair actually signed for by the private-key holder (attacker_key, attacker's own implicit id) — they differ. Impact: Critical, tokens moved from `victim.near`'s `token_balances` without their authorization. Proof: cargo test in near-workspaces sandbox registering `victim.near` with no public keys, then submitting an ERC191 MultiPayload naming `signer_id=victim.near` signed by an unrelated key, assert `has_public_key` returns false and execution fails with `PublicKeyNotExist`; then also test the case where `victim.near` HAS added the attacker's exact `Secp256k1` key (mistakenly) to confirm binding equality holds only in that narrow case.
