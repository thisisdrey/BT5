Target: `SignedWebAuthnPayload::extract_defuse_payload` (contracts/defuse/core/src/payload/webauthn.rs) reading `self.payload` field via `serde_json::from_str(&self.payload)`, versus `Payload::hash()` for WebAuthn digesting `client_data_json`/`authenticator_data` separately (not `self.payload` directly). Attacker action: constructs `SignedWebAuthnPayload{payload: JSON_A, client_data_json, authenticator_data, public_key, signature}` where the WebAuthn signature is computed over `authenticator_data || sha256(client_data_json)` per spec, and `client_data_json.challenge` is base64url(sha256(JSON_B)) for a DIFFERENT `DefusePayload` JSON_B, while `self.payload` (used only for `extract_defuse_payload`) is set to JSON_A naming `signer_id=victim` and a favorable intent. Preconditions: victim has previously signed (in some other, legitimate flow) a WebAuthn assertion whose challenge equals sha256(JSON_A) is NOT required — attacker only needs their OWN valid WebAuthn signature over challenge=sha256(JSON_B), then swaps in unrelated `payload=JSON_A` string, since `verify()` never checks that challenge derived from `self.payload`. Call sequence: `signed.verify()` checks signature against `client_data_json`+`authenticator_data` only (independent of `self.payload`) -> succeeds returning attacker's own public key -> `signed.hash()` also computed from client_data/authenticator_data (independent of `payload` field) -> `extract_defuse_payload()` parses attacker-supplied `self.payload=JSON_A` into `DefusePayload{signer_id: victim, message: favorable_intent}`. Binding: the `DefusePayload` that `hash()` binds to (derived from `client_data_json.challenge`) must equal the `DefusePayload` `extract_defuse_payload` returns from `self.payload`; if the code never enforces `sha256(canonical(self.payload)) == decoded_challenge`, the two diverge and `signer_id=victim` is accepted with an intent nobody signed for that content, purely on attacker's own signature. Impact: Critical — an intent (e.g., transfer of `victim`'s tokens) executes though victim never signed over that specific message; funds of any account whose signer_id an attacker types into their own crafted WebAuthn payload are at risk.
