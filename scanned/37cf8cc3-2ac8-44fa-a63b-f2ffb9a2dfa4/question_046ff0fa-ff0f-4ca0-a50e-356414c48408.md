Target: `SignedTonConnectPayload::verify` (contracts/defuse/core/src/payload/ton_connect.rs) and `TonConnectPayload::extract_defuse_payload`'s deadline/timestamp check `if p.deadline < self.timestamp`. Attacker action: submits a `MultiPayload::TonConnect` where `self.payload.timestamp` is set far in the past (satisfying `p.deadline >= self.timestamp` trivially) while the actual Ed25519 signature was produced by the victim's TON wallet for an entirely different, older intent whose bytes happen to be reusable because `TonConnect::verify` only checks signature over `payload.try_prehash()` which depends on `payload` fields but the `text` field (holding the `DefusePayload` JSON) is attacker-substituted post-hoc if `try_prehash()` does not commit to `text` content itself. Preconditions: TonConnect prehash function's domain-separation must be checked to confirm `text` is included in the signed digest. Call sequence: `signed.verify()` -> `TonConnect::verify` against `self.payload` (includes `text`) -> if hash truly commits to `text`, this attack fails; if it only commits to a subset (e.g., domain+timestamp without the intents text), attacker can swap `text` freely post-signature. Binding: `Payload::hash()` bytes actually signed by victim's private key == bytes `extract_defuse_payload` decodes the executed `DefusePayload` from. Impact: Critical, executing an intent whose content the victim never signed (classic hash/decode divergence). Proof: cargo test taking a genuine TonConnect signed message and attempting to swap `payload.payload` (the `TonConnectPayloadSchema::Text.text` field) with a different `DefusePayload` JSON while keeping the same signature; assert `verify()` returns `None` (fails) because `try_prehash()` recomputation over the tampered `text` no longer matches the original signature.
