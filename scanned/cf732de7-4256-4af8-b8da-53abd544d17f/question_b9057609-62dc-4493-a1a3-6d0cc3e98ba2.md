Target: `sync.rs`'s chunk-gossip ingestion path (receiving StackerDB chunks relayed from another peer's inventory) versus the local-write path guarded by `StackerDBChunkData::verify`. Attacker action: run a peer that gossips a `StackerDBChunkData` for a slot the attacker does not own, relying on the receiving node's sync logic storing the chunk into its local chunk store as soon as it downloads it (to satisfy inventory-diffing) before the ownership/version check that the direct-POST path performs runs. Preconditions: attacker's peer is connected and included in the receiving node's StackerDB peer list for that contract. Call sequence: inbound chunk-inv diff -> sync.rs chunk fetch -> store into `StackerDBTx` -> (later) `StackerDBChunkData::verify`. Equality broken: stored-chunk == chunk-signed-by-current-slot-owner-with-greater-version must hold BEFORE persistence, not after; if storage precedes verification, an unverified/forged chunk is momentarily (or permanently, if verification is skipped on error) part of node state and can be re-gossiped. Impact: Critical, network-wide propagation of an unauthenticated chunk via one dishonest relay. Proof: Rust test in stackslib::net simulating sync.rs's gossip-fetch path with an unsigned/wrongly-signed chunk and asserting the DB never contains it, checking ordering of verify() vs storage calls.
