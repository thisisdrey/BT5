Target: `SaltedNonce`/`ExpirableNonce` field layout (`salt: Salt`, `nonce: ExpirableNonce<[u8;15]>` with `deadline`, inner random bytes) versus the derived borsh `Nonce` via `From<VersionedNonce> for Nonce`. Attacker action: construct two DIFFERENT `VersionedNonce::V1` values with different `salt`/`deadline`/random-byte fields that, after `Serialize` into the fixed 32-byte array via `(VERSIONED_MAGIC_PREFIX, value).serialize(&mut result.as_mut_slice())`, produce the IDENTICAL 32-byte `Nonce` output (a borsh serialization collision). Preconditions: attacker fully controls all fields since salt just needs to be currently valid and deadline/random bytes are attacker-chosen. Call sequence: if such a collision existed, `commit_nonce` on the resulting bitmap key would treat two semantically distinct signed intents (potentially from two different `DefuseIntents` messages if the nonce were reused across payloads) as consuming the same bit, but since `Nonce` -> bitmap key is exactly the 32 bytes, a TRUE collision would only matter if the attacker could get a victim to sign a payload with an attacker-chosen colliding nonce for one purpose then reuse the physical bytes for another purpose that was never signed. Binding: for any two distinct signed `DefuseIntents` M1, M2 authorized by the SAME signer with the SAME 32-byte nonce, at most one may ever `commit_nonce` successfully (== 1 total settlement across both). Scoped impact: Critical if a signer could be tricked into producing two different valid signed messages sharing one nonce where BOTH successfully settle. Proof idea: cargo test asserting borsh round-trip determinism of `VersionedNonce::V1` -> `Nonce` for a wide range of arbitrary salts/deadlines/random bytes (using the existing `arbitrary` feature) and confirming no two distinct `VersionedNonce` values ever serialize to the same 32 bytes.
