### Title
`Command::CallContract.value` in the Snowbridge outbound v2 message converter is not bound to any withdrawn/reserved asset amount, allowing an unbacked ETH-value instruction to be committed for Ethereum execution - ([File: bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs])

### Summary
The Livepeer bug's root cause was that an amount (`amount` withdrawn from `BridgeMinter`) was computed and withdrawn on L1, but the value forwarded in the cross-chain call (`sendTxToL2`'s `_l1CallValue`) never included it, so the destination-side execution that assumed the value was funded failed/lost the funds. The local analog is `XcmConverter::convert` in Snowbridge's outbound-queue v2 primitives, which builds the `Message`/`Command` list that Bridge Hub commits (via Merkle root) for the Ethereum Gateway to execute. For a `Transact` instruction, the decoded `ContractCall::V1.value` field is placed directly into `Command::CallContract { value, .. }` with **no check that this value is backed by any asset actually withdrawn or reserved earlier in the same XCM** (the only assets accounted for are the `PayFees` fee and the ENA/PNA transfer assets used to build `UnlockNativeToken`/`MintForeignToken` commands).

### Finding Description
`XcmConverter::convert` (`bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs:217-325`) parses an Ethereum-context XCM into an outbound `Message` with `Command`s that will be ABI-encoded, Merkle-committed by `outbound-queue-v2::do_process_message` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:346-443`), and eventually executed by the Ethereum Gateway contract after relayer proof submission. [1](#0-0) 

The `Transact` branch decodes an arbitrary, user-supplied `ContractCall::V1 { target, calldata, gas, value }` and pushes `Command::CallContract { target, calldata, gas, value }` straight into the outbound command list. Compare this with the only value that *is* tracked and validated in the same function — the remote fee: [2](#0-1) 

`extract_remote_fee` enforces `reserved_fee_amount >= fee_amount`, i.e. the fee amount charged is checked against an asset that was actually withdrawn earlier in the XCM (`WithdrawAsset` immediately preceding `PayFees`). No equivalent check exists for `Command::CallContract.value`: it is taken verbatim from the encoded `Transact` payload and is never compared against, or subtracted from, any `WithdrawAsset`/`ReserveAssetDeposited` amount processed by `extract_ethereum_native_assets` / `extract_polkadot_native_assets` (lines 119-186). There is therefore no on-chain invariant in this pallet ensuring that "ETH value promised to be attached to the Ethereum-side contract call" is backed by any ETH actually taken from the caller on the Polkadot side — mirroring exactly the L1Migrator flaw where the amount instructed to move cross-chain (`amount`) was decoupled from the value actually funded in the outbound call (`msg.value`).

The only gate on who can reach this path is the `AliasOrigin` check, validated against `AllowedAliasOrigin` (line 246-254). The test fixtures for this converter configure this filter as `EverythingBut<Equals<AssetHubLocation>>` — i.e., essentially unrestricted except for the AssetHub's own location: [3](#0-2) 

If the production runtime configuration for `AllowedAliasOrigin` is similarly permissive (this repo's fixture strongly implies the design intends broad, not per-agent-authorized, aliasing), any account able to originate an `ExportMessage`/`InitiateTransfer` XCM to Ethereum with a `Transact` instruction can set an arbitrary `value` in the encoded `ContractCall`, independent of what it actually paid/withdrew in `PayFees` or the ENA/PNA transfer. That instruction becomes a Merkle-committed, cryptographically-authenticated command that the Ethereum Gateway will execute as coming from a legitimately aliased origin.

### Impact Explanation
If the Ethereum-side Gateway funds `Command::CallContract.value` from its own pooled ETH balance (as is architecturally implied — the Gateway is the bridge's on-chain treasury of bridged ETH/WETH), then an attacker-controlled outbound message can instruct the Gateway to attach real ETH value to a call targeting an attacker-controlled contract, without that ETH ever having been withdrawn/reserved from the attacker on the Polkadot side. This is the theft/unbacked-transfer impact class explicitly listed in the impact gate ("theft or unbacked mint or unlock"). Even absent full confirmation of the Solidity-side spending semantics (out of scope of this repository), the local defect is concrete and unambiguous: the converter enforces a withdrawn-amount invariant for the fee but omits it entirely for the `CallContract` value, which is the same class of "amount sent to destination ≠ amount actually collected on source" bug as the reported finding.

### Likelihood Explanation
Likelihood depends on (a) the runtime's actual `AllowedAliasOrigin` configuration (only the test mock permissiveness was directly confirmed) and (b) the Ethereum Gateway's contract logic for funding `value` in `CallContract` execution, which lives outside this Rust repository and could not be verified here. These are the two open items that would need runtime/contract-level confirmation, but the structural gap in `XcmConverter::convert` — no invariant tying `Command::CallContract.value` to any withdrawn asset — is fully evidenced in-repo.

### Recommendation
In `XcmConverter::convert`, require that any non-zero `value` in a decoded `ContractCall` be matched against an explicit ETH asset withdrawn/reserved earlier in the same XCM (analogous to the `reserved_fee_amount >= fee_amount` check already done for fees), and reject the message (`XcmConverterError`) if the value is not fully backed. Additionally, audit the production `AllowedAliasOrigin` configuration for the v2 exporter to ensure it is scoped to legitimately owned agents/origins rather than the broad `EverythingBut<...>` pattern seen in the test fixtures.

### Proof of Concept
1. An account controls (or is permitted to alias as, per `AllowedAliasOrigin`) some `Location` origin on a system parachain routed through AssetHub/BridgeHub to Ethereum.
2. It constructs an XCM ending in `ExportMessage`/`InitiateTransfer` to Ethereum containing:
   - `WithdrawAsset(ETH, small_fee)` / `PayFees(ETH, small_fee)` — pays only the minimal relay fee.
   - `AliasOrigin(<its own location>)`.
   - `DepositAsset { .. }`.
   - `Transact { call: ContractCall::V1 { target: <attacker contract>, calldata: [], gas: X, value: LARGE_VALUE } }`.
   - `SetTopic(..)`.
3. `XcmConverter::convert` (`convert.rs:217-325`) accepts this XCM: `extract_remote_fee` only validates the small fee amount; the `Transact` branch (lines 294-305) pushes `Command::CallContract { value: LARGE_VALUE, .. }` unconditionally.
4. `outbound-queue-v2::do_process_message` commits this command into the Merkle-proven outbound message (`lib.rs:346-443`) with no fee/value cross-check.
5. Once relayed and executed on Ethereum, the Gateway is instructed to attach `LARGE_VALUE` ETH to the call to the attacker's contract — value the attacker never withdrew or reserved on the Polkadot side.
