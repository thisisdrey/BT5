## Confirmed local analog found

### Title
Snowbridge relayer reward is irreversibly deleted from the ledger before the cross-chain payment is confirmed, causing permanent loss of the reward when the sovereign account cannot settle it - (File: `bridges/modules/relayers/src/lib.rs`, `bridges/snowbridge/primitives/core/src/reward.rs`)

### Summary
`PayAccountOnLocation::pay_reward` (used by `BridgeReward::Snowbridge`) does not actually transfer value — it only builds and *sends* an unpaid `ReserveAssetDeposited`/`DepositAsset` XCM to AssetHub, from BridgeHub's sovereign account, and returns `Ok(())` as soon as the XCM is validated, fee-charged, and handed to the transport layer for delivery [1](#0-0) . `Pallet::do_claim_rewards` treats this `Ok(())` as final settlement: it removes the relayer's `RelayerRewards` entry via `try_mutate_exists`/`take()` and emits `RewardPaid` in the same call [2](#0-1) . There is no mechanism analogous to "increase approval" or retry the settlement if the remote leg fails — once the local storage entry is removed and the XCM ticket is delivered, the claim can never be re-issued.

### Finding Description
The 0x report's core defect is: a finite, unrenewable resource is consumed to authorize a transfer, and once depleted there is no path to top it up, so the intended beneficiary never receives funds and the failure is silent/unrecoverable from the contract's own accounting perspective.

The Snowbridge reward path exhibits the same broken invariant class ("message queues... and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically"):

- `pay_reward` only confirms that the XCM was *accepted for delivery* (`XcmSender::deliver(ticket)` succeeding) — it has no visibility into whether the destination (AssetHub) successfully executes `ReserveAssetDeposited` + `DepositAsset` [3](#0-2) .
- The `UnpaidExecution` instruction means AssetHub's XCM executor is trusted to run the message with no fee-based retry/backpressure; if execution fails on AssetHub (e.g., the bridge's foreign-asset reserve for Ethereum on AssetHub cannot mint due to an asset-registration or filter issue, or the message is dropped/trapped), the funds never reach the beneficiary.
- Meanwhile, on BridgeHub, `do_claim_rewards` has already deleted the `RelayerRewards` entry for that relayer/reward-kind as soon as `pay_reward` returned `Ok`. There is no callback, receipt, or reconciliation path that re-credits `RelayerRewards` if the remote deposit fails.
- This mirrors the 0x wrapper bug precisely: a one-shot authorization/dispatch ("approve" in 0x; "send unpaid XCM + delete ledger entry" here) is treated as final settlement, but the actual value movement depends on a separate, unverified step (spending the ZRX allowance in 0x; executing the XCM on AssetHub here) that can fail independently, with no top-up/retry mechanism for the depleted resource (finite ZRX allowance in 0x; the one-time reward-ledger entry here).

Prior related prdocs even acknowledge parts of this fragility class in the Snowbridge codebase — e.g., a fix for a similar issue where inbound relayer tips were lost because they were "burnt" before being paid out (PR 9746) [4](#0-3) , and another where the AssetHub sovereign account being depleted was explicitly called out as a payment-failure scenario needing special handling for message processing (PR 3761) [5](#0-4) . These show the "reward accounting can diverge from actual on-chain settlement" class is a recognized recurring risk area in this codebase, and the `claim_rewards_to` reward path for `BridgeReward::Snowbridge` has not been hardened against remote execution failure.

### Impact Explanation
If the cross-chain deposit XCM fails to execute on AssetHub (destination-side asset/filter issue, insufficient sovereign-account reserve backing for the wrapped Ethereum asset, or any transient AssetHub-side rejection), the relayer's earned reward is permanently and irrecoverably destroyed on BridgeHub: `RelayerRewards` no longer contains the entry (it was `take()`n), `RewardPaid` was already emitted, and there is no on-chain state or extrinsic to reclaim or re-register the lost reward. This is a "permanent user-fund lock/loss" impact — the relayer performed real, valued work (message relay) and is left with nothing, with no admin/governance path required to trigger the loss (it happens as a direct, unprivileged consequence of calling `claim_rewards`/`claim_rewards_to`).

### Likelihood Explanation
Any registered relayer with an accrued reward can trigger `claim_rewards`/`claim_rewards_to` at will; this is a routine, permissionless operation performed continuously by third-party relayers in production. The failure condition (remote XCM execution failure on AssetHub) is not attacker-induced or malicious-actor-dependent — it can occur from ordinary asset-registration state, XCM version skew, or capacity/HRMP conditions on the destination side, none of which require a malicious peer, validator, or governance action. Given `SendXcm::deliver` succeeding is a low bar (it only confirms message queuing, not destination execution), the local "settlement" and remote "settlement" can diverge under realistic operating conditions.

### Recommendation
- Do not treat `XcmSender::deliver` success as final settlement. Either (a) require an explicit delivery/execution acknowledgment (analogous to how `snowbridge_pallet_outbound_queue_v2::process_delivery_receipt` gates reward registration on relay proof) before removing the `RelayerRewards` entry, or (b) keep the ledger entry pending and only clear it upon a confirmed receipt/callback from AssetHub.
- Add a reconciliation/retry path: if the AssetHub-side deposit fails, re-credit `RelayerRewards` on BridgeHub so the relayer can re-claim, instead of silently discarding the entitlement.
- Consider making the `PayAccountOnLocation` XCM paid/verifiable rather than best-effort `UnpaidExecution`, so a failure at the destination can be observed and acted upon by BridgeHub rather than assumed successful.

### Proof of Concept
1. Relayer accrues a `BridgeReward::Snowbridge` entry via `register_reward` (as exercised in `claim_rewards_works`) [6](#0-5) .
2. Relayer calls `claim_rewards_to(BridgeReward::Snowbridge, AssetHubLocation(...))`, which invokes `do_claim_rewards` → `RelayerRewards::take()` removes the entry, then calls `PayAccountOnLocation::pay_reward` [2](#0-1) .
3. `pay_reward` validates/charges/delivers the XCM ticket and returns `Ok(())` purely based on local delivery success [3](#0-2) ; `RewardPaid` is emitted and the ledger entry is gone.
4. On AssetHub, suppose the `ReserveAssetDeposited`/`DepositAsset` XCM instructions fail to execute (e.g., due to asset-registration state or a destination-side error not modeled by the sender). No `ForeignAssets::Deposited` event fires for the beneficiary (contrast with the success case shown in the integration test, where this event is the only confirmation of actual settlement) [7](#0-6) .
5. Result: the relayer's reward is gone from BridgeHub storage, no funds landed on AssetHub, and no retry/reclaim path exists — a permanent loss identical in structure to the 0x wrapper's "depleted, non-renewable approval leading to trapped funds."

Note: I was not able to fully trace AssetHub-side XCM barrier/filter configuration for the exact destination-execution failure trigger within the indexed portion of the repo; a Devin session with full repo/file access would be needed to construct and run an end-to-end emulated-chain reproduction confirming a concrete destination-side failure mode (rather than the structural gap demonstrated above from the source code itself).

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}

		fn do_claim_rewards(
			relayer: T::AccountId,
			reward_kind: T::Reward,
			beneficiary: BeneficiaryOf<T, I>,
		) -> DispatchResult {
			RelayerRewards::<T, I>::try_mutate_exists(
				&relayer,
				reward_kind,
				|maybe_reward| -> DispatchResult {
					let reward_balance =
						maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;
					T::PaymentProcedure::pay_reward(
						&relayer,
						reward_kind,
						reward_balance,
						beneficiary.clone(),
					)
					.map_err(|e| {
						tracing::error!(
							target: LOG_TARGET,
							error=?e,
							?relayer,
							?reward_kind,
							?reward_balance,
							?beneficiary,
							"Failed to pay rewards"
						);
						Error::<T, I>::FailedToPayReward
					})?;

					Self::deposit_event(Event::<T, I>::RewardPaid {
						relayer: relayer.clone(),
						reward_kind,
						reward_balance,
						beneficiary,
					});
					Ok(())
				},
