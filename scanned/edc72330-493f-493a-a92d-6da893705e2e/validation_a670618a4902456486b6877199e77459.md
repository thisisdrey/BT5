### Title
`instantiate_with_code`/`instantiate` address prediction diverges from actual deployed address during dry-run (eth_call/RPC simulation) vs. real transaction — (File: `substrate/frame/revive/src/exec.rs`)

### Summary
`pallet-revive`'s `Stack::new_frame` computes the CREATE1 address for a new contract using `address::create1(&deployer, nonce)` where the nonce is adjusted only by the boolean `origin_is_caller` — it does not distinguish between a genuine on-chain transaction and a dry-run/RPC simulation (`exec_config.is_dry_run`). This mirrors the wagmi `computePoolAddress()` bug class: a deterministic address is precomputed under one set of environment assumptions and is trusted as ground truth, but the actual execution environment computes it differently, producing address mismatches that a caller relies on for correctness.

### Finding Description
`address::create1` in `substrate/frame/revive/src/address.rs` implements `keccak256(rlp(deployer, nonce))[12..]`, and is invoked in `Stack::new_frame` (`substrate/frame/revive/src/exec.rs`, `FrameArgs::Instantiate` arm): [1](#0-0) 

The nonce used is `account_nonce.saturating_sub(1)` when `origin_is_caller` is true, on the theory that the system nonce was already incremented pre-dispatch for a live extrinsic. However, `new_frame`/`Stack::new` is invoked identically whether the call originates from:
- a real signed extrinsic (nonce already incremented pre-dispatch), or
- a dry-run / `eth_call`-style simulation invoked through the runtime API (nonce **not** incremented, since no extrinsic is actually applied),

as shown by `Stack::new`, which passes `origin_is_caller = true` unconditionally for the first frame and only special-cases dry-run for *timestamp*, not nonce: [2](#0-1) 

This is precisely the divergence that was documented (but only in a changelog entry, not in code) by `prdoc/stable2506/pr_8504.prdoc`, which describes the exact bug: "the returned address does not match the actual address that will be used when the transaction is submitted" and proposes gating the nonce-subtraction on `matches!(exec_context, ExecContext::Transaction)`. [3](#0-2) 

Critically, in this repository the `ExecContext` type and the described fix do not exist anywhere in the Rust source — a grep for `ExecContext` only matches the prdoc file, and `exec.rs` still contains only the unconditional `origin_is_caller` branch with no `is_dry_run` gating on the nonce computation. That means the prdoc was merged/backported without the accompanying code change, so the underlying address-mismatch bug the prdoc claims to fix is still live in this codebase.

Because Uniswap-style "trust the locally computed CREATE address" patterns are exactly what the external report flags as unsafe when execution-environment assumptions differ, the local analog is: any off-chain tooling, wallet, bridge, or smart contract on pallet-revive that pre-computes the deployment address via a dry-run call (e.g. `revive_api().instantiate()` or `eth_call` gas estimation) and then relies on that address to fund it, register it as a counterparty, or authorize a callback, will receive a **wrong address** — one that does not match the address actually produced when the real, signed transaction executes (which uses `nonce - 1`).

### Impact Explanation
This falls in the "runtime bugs that compromise intended behavior" category: a public runtime-API/RPC codepath returns a contract address that provably diverges from where funds/contracts actually land, for a contract deployment that is unprivileged and available to any user. Funds sent to the pre-funded (incorrectly computed) address before the real deployment tx lands would be sent to an address other than the one that ultimately holds the deployed contract's code — the deposited value is not lost outright (it stays on-chain at a valid H160/AccountId pair) but is misdirected relative to the contract the user actually intended to fund, and any logic (bridges, escrow, callback validation) trusting the dry-run address as authoritative for a not-yet-existing contract will authenticate/settle against the wrong account. This is analogous in class to the wagmi issue: "unlikely but real DoS / fund-misdirection" from address-derivation inconsistency between the computed value and the actual chain-execution outcome.

### Likelihood Explanation
Medium/low-frequency but structurally guaranteed to occur any time a dApp/tooling computes the deploy address via dry-run (a documented, encouraged pattern per the same prdoc — "users can rely on the address returned by a dry run") and then acts on it before/without confirming against the real receipt. No malicious actor, validator, or governance action is required — it's a deterministic divergence triggered purely by normal usage of the public dry-run RPC path alongside `instantiate_with_code`/`instantiate` CREATE1 (no-salt) deployments.

### Recommendation
Land the fix actually described in `pr_8504.prdoc`: thread an explicit `ExecContext` (or equivalent dry-run flag) into `Stack::new`/`new_frame` and only subtract 1 from the nonce when running inside a real transaction dispatch, not during a dry run/RPC simulation. Add a regression test (e.g. `nonce_not_incremented_in_dry_run`) asserting the dry-run-computed CREATE1 address equals the address produced by the subsequent real extrinsic.

### Proof of Concept
1. Call the `revive_api` runtime API (or `eth_call`/`eth_estimateGas` via `substrate/frame/revive/rpc`) to dry-run `instantiate_with_code` with `salt = None` for account `A` at nonce `N`. Because `is_dry_run` doesn't affect the nonce branch, and `origin_is_caller = true`, the returned address is `create1(A, N-1)`.
2. Submit the real signed extrinsic for the same account `A` (nonce still `N` at submission time, framework increments pre-dispatch to `N+1`, so `account_nonce` observed inside `new_frame` is `N+1`, giving `create1(A, N)`).
3. Compare: the dry-run predicted address `create1(A, N-1)` and the on-chain deployed address `create1(A, N)` are different H160 values (as confirmed directly by the `create1` test vectors in `substrate/frame/revive/src/address.rs` showing address depends strictly on the nonce integer).
4. Any funds sent to the dry-run-predicted address, or any external system that treats that address as the future contract's identity (e.g., pre-authorizing a callback or escrow to it), will operate on an account that never receives the deployed contract. [4](#0-3) [1](#0-0)

title: Fix generated address returned by Substrate RPC runtime call
doc:
- audience: Runtime Dev
  description: |-
    ## Description

    When dry-running a contract deployment through the runtime API, the returned address does not match the actual address that will be used when the transaction is submitted. This inconsistency occurs because the address derivation logic doesn't properly account for the difference between transaction execution and dry-run execution contexts.

    The issue stems from the `create1` address derivation logic in `exec.rs`:

    ```rust
    address::create1(
        &deployer,
        // the Nonce from the origin has been incremented pre-dispatch, so we
        // need to subtract 1 to get the nonce at the time of the call.
        if origin_is_caller {
            account_nonce.saturating_sub(1u32.into()).saturated_into()
        } else {
            account_nonce.saturated_into()
        },
    )
    ```

    The code correctly subtracts 1 from the account nonce during a transaction execution (because the nonce is incremented pre-dispatch), but doesn't account for execution context - whether it's a real transaction or a dry run through the RPC.

    ## Review Notes

    This PR adds a new condition to check for the `ExecContext` when calculating the nonce for address derivation:

    ```rust
    address::create1(
        &deployer,
        // the Nonce from the origin has been incremented pre-dispatch, so we
        // need to subtract 1 to get the nonce at the time of the call.
        if origin_is_caller && matches!(exec_context, ExecContext::Transaction) {
            account_nonce.saturating_sub(1u32.into()).saturated_into()
        } else {
            account_nonce.saturated_into()
        },
    )
    ```
```

/// Determine the address of a contract using CREATE semantics.
pub fn create1(deployer: &H160, nonce: u64) -> H160 {
	let mut list = rlp::RlpStream::new_list(2);
	list.append(&deployer.as_bytes());
	list.append(&nonce);
	let hash = keccak_256(&list.out());
	H160::from_slice(&hash[12..])
}
