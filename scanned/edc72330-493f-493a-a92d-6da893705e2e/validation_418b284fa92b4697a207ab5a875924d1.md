## Analysis

The core broken invariant in the MozBridge report is: **a fee/gas estimator computes cost from a fixed/simplified representation of a message type, while the actual encoded payload that is delivered can be significantly larger (contains variable-length structures), causing the estimate to under-price gas and the delivery transaction to run out of gas.**

This exact pattern exists in Snowbridge's outbound message gas metering.

### Location
`ConstantGasMeter::maximum_dispatch_gas_used_at_most` in `bridges/snowbridge/primitives/outbound-queue/src/v2/message.rs` returns a **flat, constant gas figure per command variant**, independent of the actual ABI-encoded payload size: [1](#0-0) 

For `Command::RegisterForeignToken`, the gas estimate is a hard-coded `1_200_000`, regardless of the lengths of the `name: Vec<u8>` and `symbol: Vec<u8>` fields: [2](#0-1) [3](#0-2) 

The only length limit enforced before ABI-encoding is the overall `MaxMessagePayloadSize` cap checked in `OutboundQueue`/`send_message_impl.rs`, not a per-field bound tied to the constant gas figure: [4](#0-3) 

This computed `gas` value is embedded directly into the committed `OutboundCommandWrapper`/`CommandWrapper.gas` field that is Merkle-committed and later verified/executed on the Ethereum Gateway contract: [5](#0-4) 

### Why this is the strongest surviving analog
- It's the same "flat estimate vs. variable-length actual payload" class as MozBridge's `quoteLayerZeroFee`.
- `RegisterForeignToken.name`/`symbol` are attacker/user-influenced variable-length byte vectors (derived from token metadata), so the actual on-chain gas needed to decode/store a long name/symbol on Ethereum scales with payload size, while `ConstantGasMeter` charges the same `1_200_000` gas no matter how long `name`/`symbol` are.
- Existing guards (`MaxMessagePayloadSize` checked in `SendMessage::validate`) only bound the *total message* size to prevent queue overflow — they do **not** scale the gas estimate with the field length, so a message can pass the size check yet still be under-gassed for its actual Ethereum-side execution cost.
- Underpriced work here matches the "public underpriced work that degrades block production or stalls bridge processing" impact class: an under-gassed `RegisterForeignToken`/similar command will revert on execution at the Gateway, consuming the relayer's real gas without completing delivery, and leaving the committed message/nonce state stalled until a manual gas top-up path (if any) or governance intervention is used.

I could not fully verify, within the remaining budget, whether the `register_token` extrinsic path (in `system-v2`/`system-frontend`) that produces `Command::RegisterForeignToken` restricts `name`/`symbol` length via a small bounded type (e.g., pallet-assets `StringLimit`) before forwarding to the outbound queue — this would affect how large the underestimation gap can practically grow. The vulnerable estimator code itself is confirmed and is unconditional on any such upstream bound.

### Title
Constant per-command gas estimate for RegisterForeignToken ignores variable-length name/symbol payload, causing under-gassed Ethereum execution - (File: `bridges/snowbridge/primitives/outbound-queue/src/v2/message.rs`)

### Summary
`ConstantGasMeter::maximum_dispatch_gas_used_at_most` assigns a fixed gas budget (`1_200_000`) to `Command::RegisterForeignToken` regardless of the actual size of the `name`/`symbol` fields that get ABI-encoded into the command payload delivered to Ethereum. This mirrors the MozBridge flaw of estimating fees from a simplified representation of the message rather than its true encoded size.

### Finding Description
`GasMeter::maximum_dispatch_gas_used_at_most` is used to compute the `gas` value committed on-chain for each outbound command [6](#0-5) . For most commands with fixed-size fields (e.g. `UnlockNativeToken`, `MintForeignToken`) a constant is appropriate. But `RegisterForeignToken` contains `name: Vec<u8>` and `symbol: Vec<u8>`, whose ABI-encoded size (and hence the actual EVM gas needed to decode/copy/store them in the Gateway contract) grows with their length [2](#0-1) . `ConstantGasMeter` nonetheless returns the same flat gas number for every `RegisterForeignToken` command irrespective of these lengths [1](#0-0) .

The only size guard in the pipeline is the aggregate `MaxMessagePayloadSize` check performed against the whole message, not against the specific fields that drive the constant-vs-actual gas mismatch [4](#0-3) . This check bounds total size but does not adapt the gas estimate, so any `name`/`symbol` length within the allowed message size can be delivered with an unchanged, potentially insufficient gas figure.

### Impact Explanation
The mis-estimated `gas` value is baked into the Merkle-committed `OutboundMessage`/`CommandWrapper` that the relayer submits to the Ethereum Gateway. If the actual gas required to execute `registerForeignToken` on Ethereum (proportional to `name`/`symbol` length) exceeds the constant estimate, the Gateway call will run out of gas and revert. Because message state (nonce, committed leaf) on the Substrate side is already advanced once the message is accepted into the outbound queue, a reverting delivery causes the relayer to waste real ETH gas without completing settlement, and the specific registration message becomes stuck/unprocessable via the low-gas path — a stalled/underpriced bridge processing condition affecting bridge delivery flow.

### Likelihood Explanation
Triggering this only requires submitting (or having submitted, depending on `register_token`'s permission model) a foreign-token registration whose metadata name/symbol are long enough that constant gas of `1_200_000` is insufficient for the ABI decode/storage cost on Ethereum. No malicious relayer, validator, or governance actor is needed — the flaw is purely in the local gas-metering logic, exercised by ordinary token-registration message construction.

### Recommendation
Make `ConstantGasMeter::maximum_dispatch_gas_used_at_most` scale with the actual ABI-encoded payload size for variable-length commands (in particular `RegisterForeignToken`, and revisit `Upgrade`'s `initializer.params` handling), e.g. `base_gas + per_byte_gas * payload.len()`, analogous to the MozBridge fix of using the real payload for fee/gas estimation instead of a fixed representation. Add an explicit test asserting the estimated gas is monotonic and sufficient with respect to `name.len() + symbol.len()`.

### Proof of Concept
1. Construct `Command::RegisterForeignToken { token_id, name: <near MaxMessagePayloadSize-sized bytes>, symbol: <near MaxMessagePayloadSize-sized bytes>, decimals }`.
2. Observe `ConstantGasMeter::maximum_dispatch_gas_used_at_most` still returns `1_200_000`, unchanged from the case where `name`/`symbol` are empty (`bridges/snowbridge/primitives/outbound-queue/src/v2/message.rs:291-306`).
3. This command passes `SendMessage::validate`'s aggregate size check as long as total message size stays under `MaxMessagePayloadSize` (`bridges/snowbridge/pallets/outbound-queue/src/send_message_impl.rs:44-49`).
4. The committed `gas` field for this larger payload is identical to the small-payload case, demonstrating the estimate does not scale with actual payload/execution cost — the same broken invariant identified in the MozBridge report.

impl GasMeter for ConstantGasMeter {
	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64 {
		match command {
			Command::SetOperatingMode { .. } => 40_000,
			Command::Upgrade { initializer, .. } => {
				// total maximum gas must also include the gas used for updating the proxy before
				// the the initializer is called.
				50_000 + initializer.maximum_required_gas
			},
			Command::UnlockNativeToken { .. } => 200_000,
			Command::RegisterForeignToken { .. } => 1_200_000,
			Command::MintForeignToken { .. } => 100_000,
			Command::CallContract { gas: gas_limit, .. } => *gas_limit,
		}
	}
}
