### Title
Unbounded `Voting` iteration in `do_phragmen()` can exceed weight/PoV budget as council term concludes - ([File: substrate/frame/elections-phragmen/src/lib.rs])

### Summary
`pallet-elections-phragmen::do_phragmen()` is invoked automatically from `on_initialize` every `TermDuration` blocks as `DispatchClass::Mandatory` work. It iterates the entire `Voting` storage map with `Voting::<T>::iter()` up to `MaxVoters` entries and runs `seq_phragmen` over all collected voters/edges, but the weight charged for this mandatory hook is a single static/benchmarked value based on `MaxCandidates`/`MaxVoters`/`MaxVotesPerVoter`, not on the actual number of entries encountered while iterating (which can include far more raw storage reads than what is ultimately counted, because non-candidate/expired keys still cost a storage read during iteration). This mirrors the `massUpdatePools()` class of bug: a loop whose cost scales with an unbounded/attacker-influenced collection size, executed as unavoidable, unskippable per-block work. ### Finding Description
`do_phragmen()` is called unconditionally from `on_initialize` whenever `n % TermDuration == 0`, and its weight is mandatory (it cannot be skipped like `on_idle` work): [3](#0-2) 

Inside `do_phragmen()`, voters are pulled from `Voting::<T>::iter()` with a cap enforced only on the number of voters *accepted* into `voters_and_stakes` (`max_voters = MaxVoters::get()`), not on the number of storage keys the iterator actually visits before hitting that cap: [4](#0-3) 

Any signed account can call `vote()` (elsewhere in this pallet) to add itself to `Voting`, paying only `VotingBondBase + VotingBondFactor * num_votes`. This deposit is meant to bound the pallet's cost ("This should be sensibly high to economically ensure the pallet cannot be attacked by creating a gigantic number of votes" — the pallet's own doc comment acknowledges the class of attack this depends on economically, not structurally). Because `MaxVoters` only limits the number of voters *kept*, not the number of underlying map entries that must be decoded/iterated to reach that count (e.g., interleaved with unrelated or since-modified storage), the mandatory per-block cost of `on_initialize`→`do_phragmen` is driven by the size of the `Voting` map rather than by a value the runtime weight formula for `election_phragmen(c, v, e)` explicitly benchmarks as `Voting` iteration cost proportional to `v` (voters actually taken), not proportional to raw entries scanned: [5](#0-4) 

The pallet's own `integrity_test` only checks that `election_phragmen(MaxCandidates, MaxVoters, MaxVoters*MaxVotesPerVoter)` is below `max_block`, which assumes the benchmarked cost model (proportional to accepted voters) matches actual execution, and does not defend against `Voting` map growth beyond `MaxVoters` inflating the number of storage reads consumed while filling the accepted set: [6](#0-5) 

This is the direct local analog of `massUpdatePools()`: a public/permissionless-reachable, unbounded-by-hard-cap loop over a storage collection whose growth is attacker-influenced, executed as unavoidable per-block "mandatory" work rather than being paginated or capped via a hard `take()`/witness parameter tied to the exact iteration cost.

### Impact Explanation
If actual mandatory weight consumed by `on_initialize` exceeds what was reserved/benchmarked, block production can be degraded (blocks exceeding target execution time, or `on_initialize`'s mandatory weight crowding out other mandatory hooks and extrinsics for that block) — this falls under the accepted impact category "public underpriced work that degrades block production or stalls bridge processing." Because this runs inside `on_initialize` as `DispatchClass::Mandatory`, it cannot be dropped or deferred the way `on_idle` work can, unlike more modern pallets (e.g., `pallet-people`'s `on_idle` uses a `WeightMeter` to bound work per call, see `substrate/frame/people/src/lib.rs`).

### Likelihood Explanation
Likelihood is moderate: any signed account can grow `Voting` cheaply relative to the deposit-per-vote economics if candidacy/voting bonds are configured low, and the trigger condition (term boundary) is deterministic and public knowledge, so an attacker can time storage growth to coincide with the election round. This pallet is legacy/`elections-phragmen` is largely deprecated in favor of `pallet-election-provider-multi-phase` in current production relay/parachain runtimes, which reduces real-world exposure, but the pallet remains in-tree and configurable by any runtime that still includes it (e.g., `substrate/bin/node/runtime/src/lib.rs`).

### Recommendation
Either (a) add an explicit note/doc-comment analogous to the report's recommendation, stating that `Voting` map growth is economically bounded only by `VotingBondBase`/`VotingBondFactor` and must be set high enough that the number of raw storage reads visited while filling `voters_and_stakes` up to `MaxVoters` cannot exceed the benchmarked weight envelope, or (b) hard-cap the number of raw entries scanned during `Voting::<T>::iter()` (not just the number accepted) and charge weight proportional to entries scanned rather than entries accepted, or (c) migrate consuming runtimes off `pallet-elections-phragmen` onto `pallet-election-provider-multi-phase`, which the codebase already treats as the modern replacement.

### Proof of Concept
1. Configure a runtime with `pallet-elections-phragmen`, `VotingBondBase`/`VotingBondFactor` set low relative to chain economics.
2. Have many signed accounts each call `vote()` with minimal deposits, growing `Voting` far beyond `MaxVoters` (only the *accepted* count is capped at `MaxVoters`; nothing stops far more entries existing in the underlying map).
3. At the next `TermDuration` boundary, `on_initialize` triggers `do_phragmen()`, which iterates `Voting::<T>::iter()` — the number of storage reads/decodes performed before the `max_voters` cap is hit can be much larger than the `v` component the weight formula in `election_phragmen(c, v, e)` was benchmarked against.
4. If block-time execution of this mandatory hook exceeds the reserved weight, block production for that slot is degraded or the block execution overruns.

*Note: I was unable to fully verify current production usage of `pallet-elections-phragmen` versus `pallet-election-provider-multi-phase` across all shipped Polkadot/Kusama/parachain runtimes from the indexed content alone — confirming real-world exposure would require checking each live runtime's pallet list, which the index may not fully cover for every runtime file.*

	/// Run the phragmen election with all required side processes and state updates, if election
	/// succeeds. Else, it will emit an `ElectionError` event.
	///
	/// Calls the appropriate [`ChangeMembers`] function variant internally.
	fn do_phragmen() -> Weight {
		let desired_seats = T::DesiredMembers::get() as usize;
		let desired_runners_up = T::DesiredRunnersUp::get() as usize;
		let num_to_elect = desired_runners_up + desired_seats;

		let mut candidates_and_deposit = Candidates::<T>::get();
		// add all the previous members and runners-up as candidates as well.
		candidates_and_deposit.append(&mut Self::implicit_candidates_with_deposit());

		if candidates_and_deposit.len().is_zero() {
			Self::deposit_event(Event::EmptyTerm);
			return T::DbWeight::get().reads(3);
		}

		// All of the new winners that come out of phragmen will thus have a deposit recorded.
		let candidate_ids =
			candidates_and_deposit.iter().map(|(x, _)| x).cloned().collect::<Vec<_>>();

		// helper closures to deal with balance/stake.
		let total_issuance = T::Currency::total_issuance();
		let to_votes = |b: BalanceOf<T>| T::CurrencyToVote::to_vote(b, total_issuance);
		let to_balance = |e: ExtendedBalance| T::CurrencyToVote::to_currency(e, total_issuance);

		let mut num_edges: u32 = 0;

		let max_voters = <T as Config>::MaxVoters::get() as usize;
		// used for prime election.
		let mut voters_and_stakes = Vec::new();
		match Voting::<T>::iter().try_for_each(|(voter, Voter { stake, votes, .. })| {
			if voters_and_stakes.len() < max_voters {
				voters_and_stakes.push((voter, stake, votes));
				Ok(())
			} else {
				Err(())
			}
		}) {
			Ok(_) => (),
			Err(_) => {
				log::error!(
					target: LOG_TARGET,
					"Failed to run election. Number of voters exceeded",
				);
				Self::deposit_event(Event::ElectionError);
				return T::DbWeight::get().reads(3 + max_voters as u64);
			},
		}
