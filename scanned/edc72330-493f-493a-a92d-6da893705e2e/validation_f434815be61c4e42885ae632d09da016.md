### Title
Shared per-block `MaxMessagesPerBlock` cap on Snowbridge outbound queue lets low-value bridge messages starve the governance channel - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

### Summary
The Snowbridge outbound-queue pallet (both v1 and v2) enforces a single, global `MaxMessagesPerBlock` limit on how many messages can be committed into `MessageLeaves`/`Messages` in one block, shared across *all* channels including the `PRIMARY_GOVERNANCE_CHANNEL`. Any account can cheaply enqueue outbound messages to Ethereum from a sibling parachain (e.g. ordinary asset transfers), and because the queue's round-robin servicing does not prioritize the governance channel within the same block, an attacker can fill the entire per-block quota with low-value messages, delaying processing of governance/high-priority messages by at least one block per attack round - the same "cheap-resource, shared-per-block-cap" pattern as the reported `VirtualToken.takeLoan` `MAX_LOAN_PER_BLOCK` exhaustion.

### Finding Description
`Config::MaxMessagesPerBlock` bounds the number of messages the outbound-queue pallet will commit per block [1](#0-0) . This is configured as `ConstU32<32>` in production runtimes for both v1 and v2 outbound queues on Bridge Hub Westend/Rococo [2](#0-1) [3](#0-2) .

The `process_message`/`do_process_message` path yields (`ProcessMessageError::Yield`) once this cap is reached in a block, regardless of which channel/origin the message came from, as demonstrated directly by the test [4](#0-3) .

Any user (or any parachain such as Asset Hub) can trigger delivery of outbound messages to this queue merely by sending assets/tokens over the bridge (via `EthereumBlobExporter`/XCM `ExportMessage`) at the cost of the message's delivery fee [5](#0-4) ; the fee only needs to cover local weight + remote gas refund, it is not designed as a scarce-slot auction fee, so at low gas-price/low-value transfers many cheap messages can be queued per block. The pallet's own test explicitly documents and reproduces the resulting starvation: 40 low-priority messages from a sibling parachain, combined with 1 governance message, result in the governance message *not* being processed in the same block because the 20/32-message cap is consumed first by the sibling channel's backlog [6](#0-5) . The identical behavior is reproduced for the v2 pallet [7](#0-6) .

This is structurally the same broken invariant as the external report: a public, cheap-to-trigger operation consumes a shared, hard, per-block resource cap (`MAX_LOAN_PER_BLOCK` ↔ `MaxMessagesPerBlock`), letting an unprivileged actor deny the cap to legitimate/priority users for that block. Existing guards do not prevent it: the halted-operating-mode bypass only protects governance messages from being *rejected* while halted [8](#0-7) , it does nothing to guarantee governance messages get priority *processing slots* within the shared per-block cap once enqueued alongside a queue congested with cheap low-priority messages.

### Impact Explanation
Governance commands sent to Ethereum through this channel (e.g. upgrades, gateway operating-mode changes, agent operations) are the mechanism intended to remain uninterruptible even when the bridge is halted for normal traffic. An attacker who can repeatedly refill the sibling channel's backlog every block (a low-cost, unprivileged, public action - simply initiating outgoing bridge transfers) can keep delaying/pushing back time-sensitive governance dispatch to Ethereum, degrading bridge processing and potentially delaying incident-response actions (e.g., an emergency Halt/Upgrade command) exactly when the bridge needs fast governance intervention. This falls under "public underpriced work that degrades block production or stalls bridge processing" in the impact gate.

### Likelihood Explanation
Triggering the condition requires no privileged access: any account can submit standard cross-chain asset transfers or other exportable XCM messages from a sibling parachain to Ethereum, paying only the message's calculated delivery fee, and repeat this every block. The pallet's own test suite demonstrates the exact starvation scenario deterministically (not a theoretical edge case), which is strong evidence the interaction is a real, reproducible property of the code rather than a rare corner case.

### Recommendation
- Reserve a dedicated per-block quota (separate counter) for the `PRIMARY_GOVERNANCE_CHANNEL` within `MaxMessagesPerBlock`, analogous to `reserved` capacity per dispatch class in `frame_system::limits::BlockWeights` [9](#0-8) , so governance messages are always guaranteed a processing slot in the same block regardless of low-priority channel congestion.
- Alternatively, service the governance channel first/unconditionally before counting other channels' messages against `MaxMessagesPerBlock`, or exempt governance messages from the shared cap entirely (mirroring how they already bypass `Halted` mode).
- Consider making the per-message fee scale with current queue congestion so that flooding many cheap messages in a single block becomes economically costly.

### Proof of Concept
The existing regression test already constitutes a working PoC of the starvation:
`governance_message_does_not_get_the_chance_to_processed_in_same_block_when_congest_of_low_priority_sibling_messages` [10](#0-9) :
1. Submit 40 low-priority messages from a sibling parachain (`sibling_id = 1000`).
2. Submit 1 governance message to `PRIMARY_GOVERNANCE_CHANNEL`.
3. Advance one block with unlimited `ServiceWeight`.
4. Assert only 20 sibling messages processed and the governance message's footprint count is still `1` (i.e., not processed in that block) - proving the cheap sibling traffic consumed the shared per-block cap ahead of governance.

An attacker only needs to repeat step 1 every block (paying the standard, non-prohibitive delivery fee) to keep pushing governance dispatch behind, reproducing the "low-cost consumption of a shared per-block cap blocks legitimate/priority use" pattern from the original report.

#[test]
fn governance_message_does_not_get_the_chance_to_processed_in_same_block_when_congest_of_low_priority_sibling_messages(
) {
	use snowbridge_core::PRIMARY_GOVERNANCE_CHANNEL;
	use AggregateMessageOrigin::*;

	let sibling_id: u32 = 1000;
	let sibling_channel_id: ChannelId = ParaId::from(sibling_id).into();

	new_tester().execute_with(|| {
		// submit a lot of low priority messages from asset_hub which will need multiple blocks to
		// execute(20 messages for each block so 40 required at least 2 blocks)
		let max_messages = 40;
		for _ in 0..max_messages {
			// submit low priority message
			let message = mock_message(sibling_id);
			let (ticket, _) = OutboundQueue::validate(&message).unwrap();
			OutboundQueue::deliver(ticket).unwrap();
		}

		let footprint = MessageQueue::footprint(Snowbridge(sibling_channel_id));
		assert_eq!(footprint.storage.count, (max_messages) as u64);

		let message = mock_governance_message::<Test>();
		let (ticket, _) = OutboundQueue::validate(&message).unwrap();
		OutboundQueue::deliver(ticket).unwrap();

		// move to next block
		ServiceWeight::set(Some(Weight::MAX));
		run_to_end_of_next_block();

		// first process 20 messages from sibling channel
		let footprint = MessageQueue::footprint(Snowbridge(sibling_channel_id));
		assert_eq!(footprint.storage.count, 40 - 20);

		// and governance message does not have the chance to execute in same block
		let footprint = MessageQueue::footprint(Snowbridge(PRIMARY_GOVERNANCE_CHANNEL));
		assert_eq!(footprint.storage.count, 1);

		// move to next block
		ServiceWeight::set(Some(Weight::MAX));
		run_to_end_of_next_block();

		// now governance message get executed in this block
		let footprint = MessageQueue::footprint(Snowbridge(PRIMARY_GOVERNANCE_CHANNEL));
		assert_eq!(footprint.storage.count, 0);

		// and this time process 19 messages from sibling channel so we have 1 message left
		let footprint = MessageQueue::footprint(Snowbridge(sibling_channel_id));
		assert_eq!(footprint.storage.count, 1);

		// move to the next block, the last 1 message from sibling channel get executed
		ServiceWeight::set(Some(Weight::MAX));
		run_to_end_of_next_block();
		let footprint = MessageQueue::footprint(Snowbridge(sibling_channel_id));
		assert_eq!(footprint.storage.count, 0);
	});
}

/// full. For instance one might want to prevent high-priority `Normal` transactions from pushing
/// out lower-priority `Operational` transactions. In such cases you might add a `reserved` capacity
/// for given class.
///
/// ```test,ignore
///              _
///   #           \
///   #   `Ext8`   - `reserved`
///   #          _/
/// | # | `Ext7                 | - - `Operational` limit
/// |#  | `Ext6`                |   |
/// |#  | `Ext5`                |-# - `Normal` limit
/// |#  | `Ext4`                |## |
/// |  #| `on_initialize`       |###|
/// |  #| `base_block`          |###|
/// |NOM|                       |NOM|
/// ```
///
/// In the above example, `Ext4-6` fill up the block almost up to `max_block`. `Ext7` would not fit
/// if there wasn't the extra `reserved` space for `Operational` transactions. Note that `max_total`
/// limit applies to `reserved` space as well (i.e. the sum of weights of `Ext7` & `Ext8` mustn't
/// exceed it). Setting `reserved` to `None` allows the extrinsics to always get into the block up
/// to their `max_total` limit. If `max_total` is set to `None` as well, all extrinsics witch
/// dispatchables of given class will always end up in the block (recommended for `Mandatory`
/// dispatch class).
///
/// As a consequence of `reserved` space, total consumed block weight might exceed `max_block`
/// value, so this parameter should rather be thought of as "target block weight" than a hard limit.
