# [H] AaveV3 RewardsController provides rewards in any token, should be handled separately

## Summary
Severity: High
Contest weight: 0.1261
Dataset id: 8539
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability originates from the assumption that rewards distributed by the Aave V3 RewardsController are always a single, known token (typically WAVAX). In reality the RewardsController can emit rewards in any ERC‑20 token, and these reward tokens are accounted for separately from the protocol’s yield. The strategy contract treats the rewards as if they were always WAVAX and does not provide a dedicated mechanism to claim, convert, or otherwise manage arbitrary reward tokens. Consequently, when a reward token other than WAVAX is received, it is deposited into the ReservePool without being swapped or forwarded to the network wallet. This mismatch can cause the ReservePool to hold unexpected token balances, leading to accounting inconsistencies, inability to use the rewards for intended purposes, and potential loss of value if the tokens cannot be swapped or are left idle. The issue can be exploited by simply triggering a reward distribution in a non‑WAVAX token; the protocol will silently accept the token, but downstream logic that expects only WAVAX will fail to process it, resulting in funds that appear to disappear from the network’s perspective. The impact is that users and the protocol may see lower network balances, missing refunds, or zero‑value rewards despite a successful distribution event. The problem manifests whenever the RewardsController emits a token that the strategy does not explicitly handle, which can happen at any time the Aave market adds a new incentive token or when an existing incentive changes its reward asset. All participants that rely on the ReservePool’s balance – including liquidity providers, network operators, and auditors – are affected because the protocol’s accounting assumptions are violated. The flaw was discovered during a security audit that examined the interaction between the AaveV3Strategy and the ReservePool and noted that the code only references WAVAX when processing rewards. It is subtle because the contract does not revert or emit an obvious error; the unexpected token simply sits in the pool, making the problem easy to overlook during normal operation. To remediate, the strategy should implement a separate claim‑rewards function that can retrieve any reward token, and the ReservePool should either forward those tokens to a designated network wallet for conversion or include a generic swap routine that converts non‑WAVAX assets into WAVAX, handling failures gracefully. This class of bug falls under improper token handling or reward‑asset assumption errors, where the contract’s logic is tightly coupled to a specific token type instead of being token‑agnostic. From a user’s perspective, a participant may expect to receive a reward in WAVAX but sees no increase in their balance, or they may notice stray token contracts appearing in the pool’s holdings, leading to confusion and the perception that “funds disappeared” or “rewards are missing”.

## Recommendation
Add a separate function in AaveV3Strategy that allows us to claim the rewards. Returning the rewards is optional, depending on the option chosen below. If a strategy has no extra rewards to be claimed, add the function but only return from it to keep compatibility. The ReservePool might end up with tokens other than WAVAX due to the fact that the rewards distributed might be any token. To address this, there are several options:
1. Add a claim rewards function that sends all rewards to the network wallet, so it can swap for wAVAX and increase the network balance.
2. Add a swap function in the ReservePool that swaps all the rewards assets different than WAVAX for WAVAX. If the swap fails, send to the addresses.networkWalletAddress().
