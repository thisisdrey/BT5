### Title
Snowbridge relayer reward is marked paid and deleted before the cross-chain settlement XCM is confirmed to execute - permanent reward loss on downstream failure - ([File: bridges/snowbridge/primitives/core/src/reward.rs])

### Summary
The external report's core defect is a **type/behavior mismatch between what a payout path assumes and what the underlying beneficiary actually requires**, causing the payout to fail when the assumption is wrong, with no safety net protecting the already-committed accounting state. The closest verified analog in this repository is the Snowbridge relayer reward-claim path: `pallet_bridge_relayers::do_claim_rewards` deletes the relayer's `RelayerRewards` entry and emits `RewardPaid` as soon as `PaymentProcedure::pay_reward` returns `Ok(())`, but for `BridgeReward::Snowbridge` that `Ok(())` only means an XCM was *successfully queued for delivery* to AssetHub — not that the reward-minting `DepositAsset` instruction actually executed there. [1](#0-0) 

### Finding Description
`do_claim_rewards` takes the stored reward out of `RelayerRewards` via `try_mutate_exists`, calls `T::PaymentProcedure::pay_reward(...)`, and only on `Err` does the mutation roll back (preserving the reward for retry): [1](#0-0) 

For the BridgeHub Westend runtime, `BridgeRewardPayer::pay_reward` routes `BridgeReward::Snowbridge` claims to `snowbridge_core::reward::PayAccountOnLocation::pay_reward`, which requires a `BridgeRewardBeneficiaries::AssetHubLocation` beneficiary: [2](#0-1) 

`PayAccountOnLocation::pay_reward` builds an XCM (`UnpaidExecution`, `DescendOrigin`, `UniversalOrigin`, `ReserveAssetDeposited`, `DepositAsset { beneficiary, ... }`), validates it, charges the relayer for delivery fees, and delivers the ticket to the XCM router. It returns `Ok(())` as soon as `XcmSender::deliver` succeeds — it never inspects or waits on the actual execution result of the `DepositAsset` on AssetHub: [3](#0-2) 

Because `pay_reward` reports success purely on message *delivery*, `do_claim_rewards` treats the reward as fully settled: the `RelayerRewards` entry is permanently removed and `RewardPaid` is emitted on BridgeHub before the message has been decoded/dispatched/executed on the destination chain. If the downstream `ReserveAssetDeposited` + `DepositAsset` sequence fails on AssetHub for any reason not visible to BridgeHub — e.g. the foreign asset (Ether, `eth_location()`) requiring the destination account to already satisfy a minimum/sufficient balance, `AllCounted(1)` instruction constraints not matching, insufficient weight for execution, or any other XCM-execution-time failure — the assets are trapped (`AssetsTrapped`) or simply never materialize, while BridgeHub's bookkeeping has already irreversibly declared the reward paid and erased. There is no compensating mechanism (no re-credit, no reconciliation, no receipt-based rollback) between the two chains.

This exactly mirrors the report's underlying broken invariant: a payout code path silently assumes the target/beneficiary handling will always succeed and advances irreversible local state on that assumption, instead of gating state advancement on confirmed successful execution — the same "commit-before-execute" flaw called out in the required pivot: *"Message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically."*

The project's own integration test explicitly checks for this exact failure mode on the happy path (asserting no `AssetsTrapped` events occur), which shows the team is aware trapped/failed settlement is a live risk for this reward-payment route, but no protection exists for the general case: [4](#0-3) 

### Impact Explanation
If the destination-side settlement (`DepositAsset` on AssetHub) fails after BridgeHub has already deleted the reward record and emitted `RewardPaid`, the relayer's earned reward is permanently and unrecoverably lost — a "permanent user-fund lock/loss" outcome, and a duplicate/asymmetric settlement bug: BridgeHub's local ledger says "paid" while no value was actually delivered anywhere. This directly violates the payout-atomicity pivot and can occur without any malicious peer, validator, relayer, or governance actor — it is a pure protocol/design gap in the reward pallet + Snowbridge payment procedure.

### Likelihood Explanation
This requires no privileged access and no adversarial party: it triggers whenever the AssetHub-side XCM execution of the reward-minting instructions fails for any ordinary reason (asset-sufficiency/ED constraints, execution weight shortfalls, transient AssetHub congestion, or future changes to `ForeignAssets` configuration) after the message has already been successfully delivered from BridgeHub's perspective. Because `pay_reward` treats "delivered" as "settled," this is a structural gap rather than an edge case dependent on attacker behavior, though it is conditioned on downstream execution failing, which is not something BridgeHub controls or observes.

### Recommendation
Do not treat `XcmSender::deliver` success as final settlement for `PayAccountOnLocation::pay_reward`. Either (a) require and wait for an execution/delivery confirmation from AssetHub (e.g., via a receipt/ack XCM back to BridgeHub) before removing the `RelayerRewards` entry, or (b) keep the reward entry in a "pending" state that can be retried/reclaimed if the destination-side execution is later observed (via events/telemetry) to have failed or trapped the assets, mirroring the atomic "advance only after execution and settlement succeed" pattern required elsewhere in the bridging pivots.

### Proof of Concept
1. A relayer accrues a `BridgeReward::Snowbridge` reward via `register_reward`, as shown in the emulated test `claim_rewards_works` (`cumulus/parachains/integration-tests/.../snowbridge_v2_rewards.rs:25-102`).
2. The relayer calls `claim_rewards_to` with a valid `BridgeRewardBeneficiaries::AssetHubLocation` pointing to an account/location on AssetHub that will fail to receive the `DepositAsset` at execution time (e.g., an account that does not satisfy the foreign asset's minimum-balance/sufficiency requirements, or a scenario causing execution to exceed the granted weight).
3. On BridgeHub: `do_claim_rewards` → `PayAccountOnLocation::pay_reward` succeeds because `validate_send`, `charge_fees`, and `XcmSender::deliver` all succeed (message queued) — see `bridges/snowbridge/primitives/core/src/reward.rs:145-150`. The `RelayerRewards` entry is deleted and `RewardPaid` is emitted (`bridges/modules/relayers/src/lib.rs:268-299`).
4. On AssetHub: the `ReserveAssetDeposited`/`DepositAsset` instructions fail or trap the asset instead of crediting the beneficiary (no `ForeignAssets::Deposited` event, potentially an `AssetsTrapped` event instead — the exact negative-path counterpart of the assertion made in `snowbridge_v2_inbound.rs:129-137`).
5. Result: the relayer's reward is gone from BridgeHub storage (cannot be re-claimed — `NoRewardForRelayer` on any retry) and was never actually delivered on AssetHub — a permanent, unrecoverable loss of the relayer's earned reward.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
