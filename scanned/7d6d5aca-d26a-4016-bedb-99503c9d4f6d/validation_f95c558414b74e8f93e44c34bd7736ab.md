### Title
Reward tokens are permanently locked in `pallet-asset-rewards` pool accounts when `total_tokens_staked` is zero during elapsed blocks - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` implements a Synthetix-style JIT reward accrual scheme where `reward_rate_per_block` tokens are meant to accrue to stakers every block until `expiry_block`. When a pool has zero staked tokens for any span of blocks (e.g. right after creation before the first staker joins, or after all stakers fully unstake), the reward accounting silently "skips" that period rather than reserving the tokens for later distribution. Because the pool's reward account is expected to hold exactly `reward_rate_per_block * (blocks elapsed)` worth of reward asset for the whole pool lifetime, and there is no function to reclaim unallocated rewards, the JPEG'd `LPFarming.sol`-style loss recurs: reward tokens corresponding to any zero-stake window become permanently stranded in the pool's `pool_account_id` with no path to recovery.

### Finding Description
The core reward-per-token function explicitly early-returns without accounting for elapsed time whenever `total_tokens_staked` is zero: [1](#0-0) 

```rust
pub(super) fn reward_per_token(
    pool_info: &PoolInfoFor<T>,
) -> Result<T::Balance, DispatchError> {
    if pool_info.total_tokens_staked.is_zero() {
        return Ok(pool_info.reward_per_token_stored);
    }
    ...
}
```

Whenever this is combined with `update_pool_rewards`, `last_update_block` is unconditionally advanced to the current block: [2](#0-1) 

```rust
pub fn update_pool_rewards(
    pool_info: &PoolInfoFor<T>,
    reward_per_token: T::Balance,
) -> Result<PoolInfoFor<T>, DispatchError> {
    let mut new_pool_info = pool_info.clone();
    new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
    new_pool_info.reward_per_token_stored = reward_per_token;
    Ok(new_pool_info)
}
```

This means any block range where `total_tokens_staked == 0` is effectively erased from the reward accrual clock: `reward_per_token_stored` is left unchanged and `last_update_block` jumps forward, so those blocks' worth of `reward_rate_per_block` tokens are never distributed to any staker's `reward_per_token_stored`/`derive_rewards` calculation: [3](#0-2) 

Despite this, the pallet documentation explicitly instructs pool operators to keep the pool's dedicated reward account "adequately funded with the reward asset" for the reward rate over the pool's lifetime: [4](#0-3) 

There is no `sweep`/`reclaim`/`withdraw_unallocated_rewards` extrinsic in the pallet to recover this stranded balance once `expiry_block` passes; the reward asset held in `pool_account_id(&pool_id)` corresponding to the zero-stake window is unrecoverable by anyone, including the pool admin, mirroring exactly the JPEG'd `LPFarming.sol` finding where reward corresponding to the epoch's initial no-deposit block was permanently stuck with no `claimRemainRewardsForOwner`-equivalent function.

### Impact Explanation
This is a direct fund-conservation violation: reward asset transferred by the pool creator/admin into the pool's dedicated account is silently and permanently locked whenever the pool experiences any period with zero staked tokens — which is a normal, unprivileged, and easily-triggered condition (pool creation before first stake, or all members unstaking simultaneously, which any staker can cause by unbonding). No malicious actor, governance action, or privileged misuse is required; it's simply a gap in the reward-rate-vs-time accounting model that leaves value permanently unclaimable, matching the "permanent user-fund lock" impact category.

### Likelihood Explanation
High likelihood in practice: any newly created pool naturally has zero stakers between `create_pool` and the first `stake` call, and any pool can transiently empty out if all stakers `unstake` before new stakers arrive (both are ordinary, permissionless actions). Every such window causes a proportional, permanent loss of reward funds with no recovery mechanism, and this reproduces on every affected pool without requiring privileged access.

### Recommendation
Change `reward_per_token`/`update_pool_rewards` so that when `total_tokens_staked` is zero, `last_update_block` is **not** advanced (freezing the reward clock until a staker exists) rather than silently discarding the elapsed-block reward. Alternatively, track and carry forward the un-distributed reward amount for zero-stake periods and add an admin-gated `reclaim_unallocated_rewards` extrinsic (analogous to the recommended `claimRemainRewardsForOwner` in the original report) that can only withdraw funds strictly proven unallocated to any staker, gated on `block_number > expiry_block`.

### Proof of Concept
1. Admin calls `create_pool` with `reward_rate_per_block = R`, funds the pool account with `R * (expiry_block - creation_block)` reward tokens.
2. No staker calls `stake` for `N` blocks after pool creation.
3. A staker then calls `stake`; internally `update_pool_and_staker_rewards` → `reward_per_token` returns unchanged `reward_per_token_stored` (since `total_tokens_staked == 0`), then `update_pool_rewards` sets `last_update_block` to the current block, discarding the `N` blocks' worth of `R` reward tokens from ever being credited.
4. The pool runs to `expiry_block`; all stakers eventually harvest all rewards computable from `reward_per_token_stored`.
5. `N * R` reward tokens remain in the pool's `pool_account_id`, permanently unclaimable — there is no extrinsic in the pallet to withdraw them.

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
