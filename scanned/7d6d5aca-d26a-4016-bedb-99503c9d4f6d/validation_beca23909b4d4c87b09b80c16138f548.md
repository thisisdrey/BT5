## Analysis

The core broken invariant from the Chainlink report is: **a security-critical address/location mapping can be set exactly once via a public-ish entrypoint, with no update or removal path — so any incorrect or later-stale binding becomes permanent and can misroute or lock value forever.**

The direct analog in this repo is the `ForeignToNativeId` mapping in the Snowbridge Ethereum-system pallets, which binds a derived `TokenId` to a Polkadot `Location` and is the sole routing table used to resolve inbound ERC-20 transfers back to their native asset location.

### Title
Permanent, unfixable `ForeignToNativeId` token routing binding in Snowbridge system pallets - (File: `bridges/snowbridge/pallets/system/src/lib.rs`, `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

### Summary
`do_register_token` (legacy system pallet) and `register_token` (system-v2 pallet) both bind a `TokenId` to a `Location` with a strict "set-once" pattern and provide no dispatchable to update or remove the binding afterwards. [1](#0-0) [2](#0-1) 

### Finding Description
Both `register_token` implementations compute a `token_id` from a `Location` via `TokenIdOf::convert_location`, and write it into `ForeignToNativeId` only if the key is not already present:
```rust
if !ForeignToNativeId::<T>::contains_key(token_id) {
    ForeignToNativeId::<T>::insert(token_id, location.clone());
}
``` [3](#0-2) [4](#0-3) 

There is no companion call in either pallet to overwrite or remove an entry from `ForeignToNativeId` — the storage map only grows. `MaybeConvert<TokenId, Location>` exposes it read-only for the rest of the runtime. [5](#0-4) [6](#0-5) 

Critically, the system-v2 entrypoint is **not privileged**: it is guarded only by `T::FrontendOrigin::ensure_origin(origin)`, and is fed from the `system-frontend` pallet's `register_token`, whose doc explicitly states "All origins are allowed, however `asset_id` must be a location nested within the origin consensus system." [7](#0-6) [8](#0-7) 

Because the binding is derived purely from location-description bytes hashed into a `TokenId`, any edge case in the `describe`/`convert_location` logic that produces a collision or an unintended value permanently and irreversibly poisons `ForeignToNativeId` for that `token_id` — there is no root/governance call anywhere in the pallet to correct it. This is exactly the same "set-once, no admin override" defect pattern as `ChainlinkARBOracle.addTokenPriceFeed`. Notably, the repository's own change history shows this class of defect has already manifested once: a prior collision was possible for `GeneralKey` junctions differing only in length, which produced identical description bytes and thus identical `TokenId`s, before being patched to include the length field. [9](#0-8) 

Since fixing any *future* variant of such a collision, or any other case of a wrongly-derived `TokenId → Location` binding, requires touching on-chain storage that has no update/removal extrinsic, the pallet has no recovery path other than a runtime storage migration.

### Impact Explanation
`ForeignToNativeId` is the resolution table used to route inbound wrapped-ERC20 transfers from Ethereum back to the correct Polkadot-side asset location. If a `token_id` is ever bound to the wrong `Location` (through a hash/description collision, a bug in a future `TokenIdOf` implementation, or simply an unrecoverable user mistake that the location-ownership check does not prevent), all inbound transfers for that ERC20 token permanently resolve to the wrong destination on Polkadot, with no way for governance or the pallet itself to correct the mapping short of a full runtime migration. This matches the report's "medium/DoS of the underlying token" impact, upgraded here to a potential fund-misdirection/lock scenario for bridged assets.

### Likelihood Explanation
Triggering the write path requires no privileged access — any signed account can call `register_token` for a `Location` "nested within" their own origin, and the very first successful registration for a given `TokenId` is immutable forever after. The prior in-repo `GeneralKey`-length collision demonstrates that the `Location → TokenId` derivation is not trivially collision-free, so the class of bug that produces a wrong, permanent binding is realistic and has already occurred once in this codebase.

### Recommendation
Add a governance/root-gated dispatchable to update or remove entries in `ForeignToNativeId` (mirroring the recommendation for `ChainlinkARBOracle`), and/or make the initial `register_token` reject re-registration attempts more strictly while allowing a privileged correction path when a mis-binding is detected, rather than making the map append-only with no way back.

### Proof of Concept
Conceptual reproduction (storage-level, no privileged actor required for the initial write):
1. Caller A registers `token_id = TokenIdOf::convert_location(location_A)` via `register_token`; `ForeignToNativeId[token_id] = location_A` is written. [4](#0-3) 
2. Due to any derivation edge case (as historically occurred with `GeneralKey` length collisions before the linked patch) a different, unintended `location_B` produces the same `token_id`. [9](#0-8) 
3. The `contains_key` guard silently skips the write for subsequent callers, so `ForeignToNativeId[token_id]` remains bound to `location_A` (or whichever location won the race) forever. [10](#0-9) 
4. No extrinsic exists in `system`, `system-v2`, or `system-frontend` to overwrite or clear the entry — `grep` across the pallets shows only `insert` guarded by `contains_key`, never `remove`/`mutate` on `ForeignToNativeId`.
