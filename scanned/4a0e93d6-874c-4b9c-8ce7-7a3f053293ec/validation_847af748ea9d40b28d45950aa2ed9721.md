## Analysis

The external report's core broken invariant: **a state-changing operation (service returned to owner) is gated behind a value transfer to a fixed address; if that transfer is blocked (blocklist/pause), the whole operation reverts, permanently trapping the underlying asset with no path to recover it.**

The closest real analog in this repo is the reward-transfer path in `pallet-staking-async`'s DAP (transfer-based, non-minting) payout flow.

### Title
Reward marked claimed before transfer succeeds allows permanent, silent loss of staker rewards on transfer failure - (File: `substrate/frame/staking-async/src/pallet/impls.rs`)

### Summary
`payout_stakers_by_page` marks `(era, stash, page)` as claimed via `Eras::<T>::set_rewards_as_claimed` *before* any currency is actually moved to the payout account. [1](#0-0) 
The actual transfer happens later in `make_payout_from_provider`, and if it fails (e.g. the destination account is frozen/held, or the payout amount plus destination's zero balance is below the existential deposit so a `Preservation::Expendable` transfer to a non-existent account errors), the error is only logged and the function returns `None` — the claim is not rolled back. [2](#0-1) 

### Finding Description
The write order is: set claimed flag → compute payout → call `payout_from_provider`/`make_payout_from_provider` → attempt `T::Currency::transfer` from the era's staker-rewards pot to the payout account. If this transfer errors, the function simply logs and returns `None`, leaving the funds in the era pot, but the page/era is already permanently flagged as claimed: [3](#0-2) 
A retry of `payout_stakers_by_page` for the same `(era, stash, page)` will now fail with `Error::<T>::AlreadyClaimed`, since the claimed-flag check happens unconditionally at the top of the function: [4](#0-3) 
Meanwhile the era's reward pot is a temporary, rotating-pool account that is drained to `UnclaimedRewardHandler` once the era falls outside `HistoryDepth` — regardless of whether some stakers never actually received their share: [5](#0-4) 
So the sequence is: claim flag set → transfer fails silently → no retry possible (`AlreadyClaimed`) → funds eventually swept away by `EraRewardManager::drain`/`cleanup_era` to the unclaimed-reward handler, never reaching the intended staker. This mirrors the M-12 pattern exactly: an unprivileged, naturally-occurring transfer failure (frozen/held account, or reaped/non-existent destination account with a sub-ED reward amount) at the payout step causes the protocol to treat the operation as settled while the value never reaches the rightful beneficiary, and there is no mechanism to re-attempt or recover it — a permanent loss of staker funds rather than a revert-and-retry.

### Impact Explanation
Any staker (validator or nominator) whose reward-destination account is a `pallet-balances` frozen/held account, or one that has been fully reaped (zero providers, zero balance) can have their per-page reward amount fall below the existential deposit at payout time. `T::Currency::transfer(..., Preservation::Expendable)` to a non-existent account for such an amount fails with `TokenError::BelowMinimum`/`FundsUnavailable`-class errors (or a runtime `pallet-balances` freeze can independently block the transfer to a live account). Since `payout_stakers_by_page` never rolls back `set_rewards_as_claimed` on such a failure, the staker permanently and irrecoverably loses that era's reward: it cannot be re-claimed (`AlreadyClaimed`), and the era pot funding it is later swept to `UnclaimedRewardHandler` once history depth passes. This is a "permanent user-fund lock/loss" impact affecting real chain state (the DAP/transfer-based reward path used by `asset-hub`-style runtimes per `pr_11930.prdoc`), not merely a griefing nuisance.

### Likelihood Explanation
This requires no privileged actor, malicious peer, or governance action — it can be triggered by an ordinary account naturally reaching zero balance/being reaped between bonding and reward payout (a common occurrence for small nominators), or by any pallet in the runtime that legitimately freezes/holds balance on the payout account (e.g. via `pallet-balances` holds used elsewhere in the runtime). `payout_stakers_by_page`/`payout_stakers_by_page` (and its underlying pagination-triggered auto-calls) are unprivileged, permissionless dispatchables, so anyone can trigger the payout attempt against any stash's page and lock in the "claimed" state regardless of transfer outcome.

### Recommendation
Do not set the claimed flag unconditionally before the transfer succeeds. Either:
1. Move `Eras::<T>::set_rewards_as_claimed` to after a successful transfer (or track per-payout success and only mark claimed for the portions that were actually delivered), or
2. On transfer failure in `make_payout_from_provider`/`payout_from_provider`, keep an explicit "pending" record so the amount can be retried or swept to a recoverable account (rather than being silently dropped and later drained by `EraRewardManager::drain`), and emit a dedicated failure event that off-chain tooling/governance can act on before `cleanup_era` sweeps the pot.

### Proof of Concept
1. Nominator `N` accrues staking rewards during era `E`; before payout, `N`'s account balance drops to `0` and its account is fully reaped (e.g., via `transfer_all` elsewhere), so it has zero providers.
2. `N`'s exposure share for page `p` in era `E` computes to an amount smaller than the chain's `ExistentialDeposit`.
3. Anyone calls `Staking::payout_stakers_by_page(origin, validator_stash, E, p)`.
4. `Eras::<T>::set_rewards_as_claimed(E, validator_stash, p)` executes immediately (line 386), marking the page permanently claimed.
5. `payout_from_provider` → `make_payout_from_provider` attempts `T::Currency::transfer(&staker_rewards_pot, &N, small_amount, Preservation::Expendable)`; since `N` doesn't exist and `small_amount < ED`, the transfer fails and is only logged (lines 602-616); `N` receives nothing.
6. Any subsequent call to `payout_stakers_by_page` for `(E, validator_stash, p)` returns `Error::<T>::AlreadyClaimed` — no retry is possible.
7. Once era `E` exceeds `HistoryDepth`, `EraRewardManager::cleanup_era`/`drain` withdraws the era pot's remaining balance (which still includes `N`'s undelivered share) to `T::UnclaimedRewardHandler`, permanently removing it from `N`'s reach.

	/// Make a payment to a staker from an era reward pot (transfer, not mint).
	fn make_payout_from_provider(
		era: EraIndex,
		stash: &T::AccountId,
		amount: BalanceOf<T>,
	) -> Option<(BalanceOf<T>, RewardDestination<T::AccountId>)> {
		if amount.is_zero() {
			return None;
		}

		let dest = match Self::payee(Stash(stash.clone())) {
			Some(d) => d,
			None => {
				Self::deposit_event(Event::<T>::Unexpected(UnexpectedKind::MissingPayee {
					era,
					stash: stash.clone(),
				}));
				return None;
			},
		};

		let payout_account = Self::payout_account_for_dest(stash, &dest)?;

		let staker_rewards_pot =
			T::RewardPots::pot_account(RewardPot::Era(era, RewardKind::StakerRewards));
		if let Err(e) = T::Currency::transfer(
			&staker_rewards_pot,
			&payout_account,
			amount,
			Preservation::Expendable,
		) {
			log!(
				error,
				"Failed to transfer reward from pot for era {:?}, stash {:?}: {:?}",
				era,
				stash,
				e
			);
			return None;
		}

	/// Drains an era pot's remaining balance to the unclaimed reward handler.
	///
	/// The pot account itself is kept alive (provider retained) so the same slot
	/// can be reused by a future era. No-op if the pot was never created (e.g.
	/// the era ran in legacy minting mode).
	pub(crate) fn drain(era: EraIndex, kind: RewardKind) {
		let pot_account = T::RewardPots::pot_account(RewardPot::Era(era, kind));

		// Skip if pot was never created (legacy mode doesn't create pots).
		if frame_system::Pallet::<T>::providers(&pot_account) == 0 {
			return;
		}

		let remaining = T::Currency::balance(&pot_account);

		if remaining.is_zero() {
			return;
		}

		match T::Currency::withdraw(
			&pot_account,
			remaining,
			Precision::BestEffort,
			Preservation::Expendable,
			Fortitude::Force,
		) {
			Ok(credit) => {
				T::UnclaimedRewardHandler::on_unbalanced(credit);
				log!(
					debug,
					"Drained {:?} unclaimed rewards from era {:?} {:?} pot",
					remaining,
					era,
					kind
				);
			},
			Err(e) => {
				defensive!("Failed to withdraw unclaimed rewards from era pot");
				log!(
					error,
					"Era {:?} {:?}: unclaimed reward withdrawal failed: {:?}",
					era,
					kind,
					e
				);
			},
		}
	}
