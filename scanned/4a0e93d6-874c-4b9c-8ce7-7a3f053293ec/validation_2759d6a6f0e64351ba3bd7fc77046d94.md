### Title
Rounding-to-zero in Snowbridge outbound-queue fee conversion lets the relayer reward for legitimate command types silently collapse to 0, stalling Ethereum-bound message delivery - (File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs)

### Summary
`pallet_asset_conversion`-style hardcoded/mis-derived parameter bugs in the Peapods Zapper (fixed `10000` fee, fixed `V3_ROUTER`, wrong chain check) all share one root cause: a value that is supposed to be dynamically and safely derived is instead computed through a path that can silently produce a wrong/degenerate result with no validation catching it. The Snowbridge `snowbridge-pallet-outbound-queue::calculate_fee` has the same class of defect: the remote (Ethereum-side) portion of the delivery fee is computed through a chain of fixed-point multiplication, division, and integer truncation that can legitimately round down to `0` for valid, non-zero `PricingParameters`, even though `PricingParameters::validate()` only checks that individual fields are non-zero and never checks the *computed* result.

### Finding Description
`Pallet::calculate_fee` in [1](#0-0)  computes the remote fee as:

1. `calculate_remote_fee(gas_used_at_most, fee_per_gas, reward)` → `U256` in wei [2](#0-1) 
2. Downcast to `u128`, multiply by `params.multiplier`, divide by `params.exchange_rate` (both `FixedU128`) [3](#0-2) 
3. `convert_from_ether_decimals` divides by `10^(18 - Decimals)` (`10^8` for a 10-decimal chain like Polkadot) using integer division, truncating any remainder [4](#0-3) 

This exact scenario is demonstrated by the pallet's own test, which is explicitly annotated as a defect:
```
// Though none zero pricing params the remote fee calculated here is invalid
// which should be avoided
assert_eq!(fee.remote, 0);
``` [5](#0-4) 

`PricingParameters::validate()` — the only guard invoked when governance sets these parameters via `set_pricing_parameters` — only checks that `exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, and `multiplier` are individually non-zero; it never checks that the derived `Fee::remote` for any in-scope `Command`/gas figure stays above zero [6](#0-5) , [7](#0-6) .

`gas_used_at_most` itself is not attacker-controlled in the classic sense (it's fixed per `Command` via `ConstantGasMeter`, e.g. 200_000 for `AgentExecuteCommand::TransferToken`/`UnlockNativeToken`, 40_000 for `SetOperatingMode`, etc. [8](#0-7) ), but this is precisely what makes the bug systemic rather than a one-off: for a given governance-approved `PricingParameters` configuration, if the resulting integer division rounds to zero for any of these small, fixed-gas command types, **every** message of that command type sent afterwards inherits `fee.remote == 0`, permanently, until governance is alerted and manually corrects `PricingParameters` again via another `set_pricing_parameters` call.

`Fee::validate()` in `send_message_impl.rs` returns this `fee` verbatim to the exporter/XCM executor that charges the sending parachain [9](#0-8) . Only `local_fee` (weight-to-fee) is guaranteed non-zero; the `remote` component — meant to reimburse relayers for real Ethereum gas plus their reward — can drop to zero. Relayers have no economic incentive to submit messages that pay `reward = 0` (effectively wei-denominated rounding loss, since the reward itself must also pass through the same divide/truncate path), so messages queue up without being relayed, degrading/stalling the Snowbridge outbound processing pipeline for that channel.

### Impact Explanation
This falls under "public underpriced work that degrades block production or stalls bridge processing": messages continue to be accepted, committed into merkle roots, and occupy queue/commitment storage (`Messages`, `MessageLeaves`), but the actual off-chain relayer economics for delivering them to Ethereum are broken because the computed reward is zero. Because the bug is baked into arithmetic reachable from ordinary, valid, non-zero configuration values (not requiring a malicious governance actor — governance sets values in good faith without knowing the derived per-command result can be zero), and because `validate()` provides no defense against it, the outbound bridge processing for the affected channel/command combination stalls until an operator notices and manually re-tunes `PricingParameters`.

### Likelihood Explanation
Likelihood is contingent on the specific `PricingParameters` chosen (`fee_per_gas`, `exchange_rate`, `multiplier`, `rewards.remote`) relative to the fixed, small gas figures used by `ConstantGasMeter` for common commands. The pallet's own regression test proves the zero-fee outcome is reachable with fully valid, non-zero parameters, and `validate()` provides no protection against it — this is a genuine gap in the invariant "the computed relayer fee must always be economically meaningful," not a hypothetical edge case.

### Recommendation
- Extend `PricingParameters::validate()` (or add a dedicated check invoked by `set_pricing_parameters`) to simulate `calculate_fee` for the full set of supported `Command` variants and their fixed gas costs, rejecting parameter sets that yield `fee.remote == 0` for any of them.
- Alternatively, enforce a `MinimumRemoteFee` floor in `calculate_fee`/`convert_from_ether_decimals` so the remote component can never round down to a value below what is needed to economically incentivize relayers.
- Increase internal precision of the divide/truncate chain in `convert_from_ether_decimals` (e.g., round up, or delay truncation) so genuine non-zero fees are not lost to integer division.

### Proof of Concept
The existing unit test already demonstrates the exact defect on this code path:
```rust

        };
        let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());

        // which should be avoided
        assert_eq!(fee.remote, 0);

}
``` [5](#0-4) 
All input fields pass `PricingParameters::validate()` (none are zero) [10](#0-9) , yet the resulting `fee.remote` charged/promised for the message is `0`, confirming the invariant break is reachable via normal, non-privileged code paths (any message of that command type sent afterward), not merely via a contrived internal-only call.

impl<Balance> PricingParameters<Balance>
where
	Balance: BaseArithmetic + Unsigned + Copy,
{
	pub fn validate(&self) -> Result<(), InvalidPricingParameters> {
		if self.exchange_rate == FixedU128::zero() {
			return Err(InvalidPricingParameters);
		}
		if self.fee_per_gas == U256::zero() {
			return Err(InvalidPricingParameters);
		}
		if self.rewards.local.is_zero() {
			return Err(InvalidPricingParameters);
		}
		if self.rewards.remote.is_zero() {
			return Err(InvalidPricingParameters);
		}
		if self.multiplier == FixedU128::zero() {
			return Err(InvalidPricingParameters);
		}
		Ok(())
	}
}

pub struct ConstantGasMeter;

impl GasMeter for ConstantGasMeter {
	// The base transaction cost, which includes:
	// 21_000 transaction cost, roughly worst case 64_000 for calldata, and 100_000
	// for message verification
	const MAXIMUM_BASE_GAS: u64 = 185_000;

	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64 {
		match command {
			Command::SetOperatingMode { .. } => 40_000,
			Command::AgentExecute { command, .. } => match command {
				// Execute IERC20.transferFrom
				//
				// Worst-case assumptions are important:
				// * No gas refund for clearing storage slot of source account in ERC20 contract
				// * Assume dest account in ERC20 contract does not yet have a storage slot
				// * ERC20.transferFrom possibly does other business logic besides updating balances
				AgentExecuteCommand::TransferToken { .. } => 200_000,
			},
			Command::Upgrade { initializer, .. } => {
				let initializer_max_gas = match *initializer {
					Some(Initializer { maximum_required_gas, .. }) => maximum_required_gas,
					None => 0,
				};
				// total maximum gas must also include the gas used for updating the proxy before
				// the the initializer is called.
				50_000 + initializer_max_gas
			},
			Command::SetTokenTransferFees { .. } => 60_000,
			Command::SetPricingParameters { .. } => 60_000,
			Command::UnlockNativeToken { .. } => 200_000,
			Command::RegisterForeignToken { .. } => 1_200_000,
			Command::MintForeignToken { .. } => 100_000,
		}
	}
}

		// Generate a unique message id unless one is provided
		let message_id: H256 = message

			channel_id: message.channel_id,
			command: message.command.clone(),

		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;
