### Title
`min_swap_amount` Threshold Is Checked Against the Gross Pre-Fee Amount Instead of the Actual Net/Settled Amount - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
The `pallet-psm` `mint` and `redeem` extrinsics enforce a configured minimum swap size (`PsmInfo::min_swap_amount`) to prevent dust-sized operations. In both extrinsics the check is performed against the **gross, pre-fee** quantity supplied by the caller, not against the **actual net amount that is minted/burned and settled** after the (admin-configurable) fee is deducted. This is the same class of bug as the reported UniswapHelper issue: a minimum-amount invariant is validated against the wrong variable in the computation pipeline, decoupling the guard from the value it is meant to protect. [1](#0-0) [2](#0-1) 

### Finding Description
In `mint`:
```
let internal_equivalent = Self::external_to_internal(external_amount, ext_decimals, internal_decimals)?;
ensure!(!internal_equivalent.is_zero(), Error::<T>::AmountTooSmallAfterConversion);
ensure!(internal_equivalent >= info.min_swap_amount, Error::<T>::BelowMinimumSwap);
...
let fee = fee_rate.mul_ceil(internal_equivalent);
let internal_to_user = internal_equivalent.saturating_sub(fee);
```
The `min_swap_amount` gate fires on `internal_equivalent` — the value **before** the minting fee is subtracted. The value that is actually minted to the user (`internal_to_user`) and that matters economically is never compared to `min_swap_amount`. [3](#0-2) 

In `redeem` the same pattern repeats:
```
ensure!(internal_amount >= info.min_swap_amount, Error::<T>::BelowMinimumSwap);
...
let fee = fee_rate.mul_ceil(internal_amount);
let internal_net = internal_amount.saturating_sub(fee);
let external_out = Self::internal_to_external(internal_net, ext_decimals, internal_decimals)?;
```
The floor is enforced on the gross `internal_amount`, not on `internal_net`/`external_out`, which is what is actually burned/transferred. [2](#0-1) 

`MintingFee`/`RedemptionFee` are runtime storage values that are only bounded by the caller-supplied `max_fee` and the pallet's own admin-settable rate — there is no hard-coded pallet-level cap preventing a fee close to `Permill::one()` from being configured for a given asset pair. Because the `min_swap_amount` check happens on the pre-fee amount, an operation that nominally clears the minimum-size floor can still settle (mint/burn/transfer) a real amount that is far below the intended floor once the fee is deducted — the exact "check against the wrong quantity" defect described in the external report, just inverted in direction (there it caused false rejection of valid swaps; here it causes false acceptance of swaps that violate the intended dust-prevention invariant).

### Impact Explanation
`min_swap_amount` exists to prevent uneconomical/dust PSM operations (which can create rounding griefing opportunities, spam small `PsmDebt` mutations, or generate a large number of near-zero-value events/storage writes at low cost). Because the check is bound to the gross amount rather than the settled amount, the guard can be defeated whenever fee configuration pushes the net settled amount below the intended floor, undermining the "conserve value / settle correctly" and "no underpriced public work" invariants for this pallet's public, unprivileged `mint`/`redeem` calls. This is a runtime invariant violation reachable by any signed account, not requiring a malicious validator, relayer, or governance actor.

### Likelihood Explanation
Likelihood is moderate: it requires PSM instances configured with a `MintingFee`/`RedemptionFee` close to the size of `min_swap_amount`'s tolerance, which is entirely within the range of legitimately-set fee parameters (fee rate is a `Permill` set independently per instance and per asset pair, with no code-enforced relationship to `min_swap_amount`). No attacker privilege beyond a signed extrinsic call is needed to trigger the mismatch once such a configuration exists.

### Recommendation
Perform the `min_swap_amount` check against the actual settled quantity:
- In `mint`, check `internal_to_user >= info.min_swap_amount` (or equivalently check post-fee amount), not `internal_equivalent`.
- In `redeem`, check `internal_net`/`effective_internal_net` (or `external_out`, converted appropriately) against the minimum, not the gross `internal_amount`.

Alternatively, explicitly document and enforce a maximum fee rate relative to `min_swap_amount` so the pre-fee check remains a sound proxy for the post-fee amount.

### Proof of Concept
1. Governance/admin configures a PSM instance with `min_swap_amount = 100` (internal units) for asset pair `(internal, external)`.
2. Admin sets `RedemptionFee` for the pair to `Permill::from_percent(99)` (or any high rate close to the fee ceiling permitted by pallet config/`max_fee` semantics).
3. A user calls `redeem(internal_asset, external_asset, internal_amount = 100, max_fee = Permill::from_percent(99))`.
4. `ensure!(internal_amount >= info.min_swap_amount, ...)` passes (100 >= 100). [4](#0-3) 
5. `fee = fee_rate.mul_ceil(100) = 99`; `internal_net = 100 - 99 = 1`.
6. The dust-prevention invariant intended by `min_swap_amount` is bypassed: the operation is executed and settled (`external_out` computed from `internal_net = 1`, burn/transfer performed) even though the economically meaningful (net) amount is far below the configured floor — mirroring the reported bug's root cause of validating a threshold against the wrong value in the pipeline. [5](#0-4)
