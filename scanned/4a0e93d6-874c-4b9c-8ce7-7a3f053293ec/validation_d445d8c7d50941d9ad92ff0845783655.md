### Title
Era-bookkeeping mismatch between `pallet-nomination-pools` unbonding schedule and `pallet-staking-async` withdrawal eligibility can permanently trap member funds - (File: `substrate/frame/nomination-pools/src/lib.rs`, `substrate/frame/staking-async/src/pallet/impls.rs`)

### Summary
The external report's core broken invariant is: a state-check gate (`whileBorrowing`) that validates only *one* accounting field (`principal`) while a second, independently-accruing field (`interestAccrued`) can silently diverge from it, leaving the contract in a state where the "close" path is permanently unreachable even though the underlying obligation is trivially small/settled. The Polkadot SDK analog is the exact same class of bug already documented in this repo: a member's exit/withdrawal bookkeeping in `pallet-nomination-pools` is driven by an *era number computed and stored independently* of the era number the underlying staking pallet actually uses to decide when funds are released. When the two diverge, a member's points get dissolved locally while the real held/staked balance is never released — i.e. same "one check advances state, a second silently-diverging value blocks final settlement" pattern.

### Finding Description
`pallet-nomination-pools::unbond()` computes the era at which a member's unbonding chunk becomes withdrawable using the pool's own view of the current era: [1](#0-0) 

This `unbond_era` is stored per-member (`member.try_unbond`) and used later purely as a **local key** to decide whether `withdraw_unlocked(active_era)` in `withdraw_unbonded()` will release the member's points and compute `balance_to_unbond`: [2](#0-1) 

That local dissolution of points is *independent* from whether the underlying `pallet-staking-async` ledger has actually released the equivalent stake. The staking-async withdrawal path introduces an additional, more conservative era boundary that did not exist in the simpler `CurrentEra` model of legacy `pallet-staking`: [3](#0-2) 

`calculate_earliest_withdrawal_era` can push the *actual* releasable era earlier than the pool's naive `bonding_duration + active_era` schedule when there are unprocessed offences in `OffenceQueueEras`, meaning the ledger may retain funds (or, symmetrically, may already have advanced) beyond the era the pool used when it minted the sub-pool bucket. The `min(...)` clamp against `transferable_balance` was added specifically as a defensive patch for this exact class of drift: [4](#0-3) 

This is not a hypothetical concern — the repository's own PRDoc documents that this exact mismatch already caused a real incident: a member's `points were dissolved but the held funds weren't released` due to a `CurrentEra vs ActiveEra mismatch`, requiring a one-off, permissioned migration to manually recover the trapped balance: [5](#0-4) 

Critically, the fix that shipped was a **one-time migration for the already-affected member**, not a structural fix that binds the pool's era bookkeeping to the staking backend's authoritative unlock-era computation. With `pallet-staking-async` now adding a *second* source of era drift (`OffenceQueueEras`-adjusted `calculate_earliest_withdrawal_era`, layered on top of the original `CurrentEra`/`ActiveEra` split), the same class of divergence remains structurally possible for any new pool member whose unbonding straddles an era in which offences are queued but not yet processed, or whose adapter's `current_era()` does not track `Rotator::active_era()` precisely at the block the chunk is created vs. consolidated.

### Impact Explanation
When the two era views diverge, `member.withdraw_unlocked(active_era)` in `withdraw_unbonded()` can dissolve the member's local points (as "processed") while `T::StakeAdapter::withdraw_unbonded` / `consolidate_unlocked` has not actually freed the equivalent balance in the ledger, or vice versa. The defensive `.min(transferable_balance)` clamp silently truncates the payout to whatever happens to be transferable at that moment, and the member's points are still removed. The result: the member's remaining claim on the bonded pool is permanently lost from pool accounting even though the corresponding stake is still locked in the staking backend (or already spent) — funds become unrecoverable through the normal, permissionless `unbond`/`withdraw_unbonded` extrinsics, exactly mirroring the LineOfCredit deadlock where a small residual (interest) value blocks/breaks the state machine used to reconcile and close a position. This is a real fund-lock condition already evidenced by the need for an ad-hoc governance migration.

### Likelihood Explanation
This is not merely theoretical: the referenced PRDoc confirms it already happened once in production/testing conditions caused by ordinary era-timing drift, not by any privileged or malicious actor. With `pallet-staking-async`'s newly introduced `OffenceQueueEras`-based `calculate_earliest_withdrawal_era`, there is an additional, more complex era-adjustment surface than the simple `CurrentEra`/`ActiveEra` split that caused the original incident, so the same bookkeeping-drift precondition can recur for any unprivileged pool member simply by unbonding/withdrawing during a period where offence processing lags behind era rotation — no relayer, validator, or governance action is required to trigger it.

### Recommendation
Do not let `pallet-nomination-pools` maintain its own, independently-computed unlock era. Instead, have `unbond()`/`withdraw_unbonded()` query the authoritative "earliest era the backend will actually release funds for this bond" (i.e., the same value `calculate_earliest_withdrawal_era` produces) through the `StakeAdapter` trait at both bond-time and withdraw-time, and make the sub-pool era key derived from that single source of truth rather than recomputed twice from potentially different era snapshots. Additionally, extend the `try-state`/`pre-migrate` invariant checks (in the spirit of `pr_5465`'s `points >= stake` invariant) to detect any pool member whose recorded `total_balance()` exceeds their actual `StakeAdapter::member_delegation_balance`, and fail loudly rather than requiring a manual, per-incident migration to reconcile trapped funds.

### Proof of Concept
Conceptual reproduction (mirrors the documented `pr_11018` incident):
1. Member calls `Pools::unbond(who, member, points)` at era `E`; pool records `unbond_era = E + BondingDuration` via `T::StakeAdapter::current_era()` [6](#0-5) .
2. Before `unbond_era` is reached in wall-clock era progression, an offence is reported and queued (`OffenceQueueEras` non-empty), causing `calculate_earliest_withdrawal_era` in `pallet-staking-async` to lag behind the pool's naively-computed `active_era` [7](#0-6) .
3. Member calls `Pools::withdraw_unbonded`; `member.withdraw_unlocked(active_era)` dissolves their points locally because the pool's local `active_era` view says the chunk is due [2](#0-1) , but `T::StakeAdapter::transferable_balance` is lower than the computed `balance_to_unbond` because the backend has not actually released the stake yet, so the `.min(...)` clamp truncates the payout [4](#0-3) .
4. The member's points/`PoolMembers` entry is now gone (or reduced) with no remaining code path to reclaim the difference — exactly the scenario the repository had to patch with a manual, one-off migration in `pr_11018.prdoc` [5](#0-4) .

Note: I was unable to fully trace the exact `StakeAdapter::current_era()` implementation wiring for the `staking-async` adapter within the available search budget, so I cannot definitively confirm whether current mainline code has since bound these two era sources together for new withdrawals versus only the historical incident being patched via migration. This uncertainty should be verified directly in `substrate/frame/nomination-pools/src/adapter.rs` and the `staking-async` `StakeAdapter` implementation before treating this as fully unpatched.

	/// Calculate the earliest era that withdrawals are allowed for, considering:
	/// - The current active era
	/// - Any unprocessed offences in the queue
	fn calculate_earliest_withdrawal_era(active_era: EraIndex) -> EraIndex {
		// get lowest era for which all offences are processed and withdrawals can be allowed.
		let earliest_unlock_era_by_offence_queue = OffenceQueueEras::<T>::get()
			.as_ref()
			.and_then(|eras| eras.first())
			.copied()
			// if nothing in queue, use the active era.
			.unwrap_or(active_era)
			// above returns earliest era for which offences are NOT processed yet, so we subtract
			// one from it which gives us the oldest era for which all offences are processed.
			.saturating_sub(1)
			// Unlock chunks are keyed by the era they were initiated plus their unbond duration.
			// We use full BondingDuration (validator duration) here because:
			// - For validators: this is their actual unbond duration
			// - For nominators: when slashable, they use full duration; when not slashable, their
			//   chunks already have shorter unlock eras (set during unbond), so this calculation
			//   still correctly allows their withdrawals.
			.saturating_add(T::BondingDuration::get());

		// If there are unprocessed offences older than the active era, withdrawals are only
		// allowed up to the last era for which offences have been processed.
		// Note: This situation is extremely unlikely, since offences have `SlashDeferDuration` eras
		// to be processed. If it ever occurs, it likely indicates offence spam and that we're
		// struggling to keep up with processing.
		active_era.min(earliest_unlock_era_by_offence_queue)
	}
