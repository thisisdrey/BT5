Target: `Contract::ft_resolve_withdraw` (contracts/defuse/src/contract/tokens/nep141/withdraw.rs). Attacker deploys a receiver contract implementing `ft_on_transfer` that always returns `0` (claims 0 unused, i.e. accepts full amount) but the attacker's own FT token contract's `ft_transfer_call` never actually calls back into ft_resolve_withdraw's promise chain with a real transfer (attacker uses a token they deployed with custom `ft_transfer_call` logic that credits itself the tokens but returns a JSON value of `used=0`). Preconditions: attacker owns account A with token_balances[T]=100 inside the Verifier, signs an FtWithdraw{token=T, receiver_id=attacker_receiver, amount=100, msg=Some('x')} via `execute_intents`. Call sequence: `internal_ft_withdraw` -> `withdraw()` debits 100 from A -> `do_ft_withdraw` calls `ft_transfer_call` -> attacker's malicious token replies with `used=0` in its callback result even though tokens moved to attacker_receiver -> `ft_resolve_withdraw` reads `promise_result_checked_json::<U128>(0)` and computes `used = min(0,100)=0`, then credits `refund=100` back to sender_id via `self.deposit`. Binding: (balance debited=100) == (assets that actually left the contract to attacker_receiver=100) + (amount re-credited=100) is violated since RHS=200. Scoped impact: Critical, double-credit lets attacker keep both the transferred tokens and the refunded internal balance. Proof idea: near-workspaces sandbox test with a custom FT contract whose ft_transfer_call performs the real balance move but returns U128(0) in its promise return value, then assert post-call token_balances[A][T] == 100 (double-credit) while token contract balance shows tokens delivered to receiver.
