# [H] MJR-1 Withdraw "with ratio" without fee via reentrancy

## Summary
Severity: High
Contest weight: 0.0219
Dataset id: 220
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability is a classic reentrancy flaw that appears in the withdraw functions of the FixedRateSwap contract when the contract interacts with tokens that implement a callback mechanism such as ERC‑777. The root cause is that the contract transfers tokens to the caller before it finalises the accounting state (for example, before it updates the recorded withdrawal amounts or applies the protocol fee). Because ERC‑777 tokens can execute arbitrary code in the receiver’s contract via the token hook, a malicious caller can re‑enter the withdraw function during the first transfer, invoke the same withdraw logic a second time, and receive a second payout before the fee calculation is applied. This results in a withdrawal with non‑equal proportions that bypasses the intended fee, effectively allowing the attacker to extract more value from the pool than the protocol permits. The exploit can be performed by calling the withdraw function with a token that supports callbacks, then in the token hook invoking withdraw again; each re‑entry repeats the same logic while the internal balances have not yet been adjusted, so the attacker can repeat the operation until the pool’s liquidity is drained or the fee revenue is severely reduced. The impact is a loss of fee revenue for the protocol and an unfair advantage for the attacker, potentially leading to a reduction of funds available to honest users. The condition for the attack is that the withdraw function is external, performs an external token transfer before state changes, and the token used supports callbacks – a situation that is not obvious when only ERC‑20 tokens are considered. The vulnerability was discovered during a formal security audit by MixBytes, which inspected the control flow of the FixedRateSwap contract and identified the missing reentrancy guard. Because the flaw relies on a token’s optional callback feature, it can be hard to notice in testing that only uses standard ERC‑20 tokens; the re‑entrancy surface only becomes apparent when the contract interacts with ERC‑777 or similar tokens. From the user’s point of view, the contract appears to allow a normal withdrawal, but an attacker sees the balance of the pool decrease without the expected fee being deducted, and honest users may later notice that the pool has less liquidity than expected or that fees are not being collected. The bug belongs to the broader class of reentrancy vulnerabilities, specifically those caused by performing external calls before internal state is safely updated. To remediate the issue, the contract should adopt the checks‑effects‑interactions pattern by updating balances and fee calculations before any token transfer, or alternatively apply a nonReentrant modifier (or a reentrancy guard) to all external functions that perform token transfers. This ensures that any recursive call is blocked until the first execution completes, eliminating the possibility of bypassing fee logic via a callback.

## Recommendation
We recommend adding nonReentrant modifier to all external functions.
