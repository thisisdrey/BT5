Target: `ConversationP2P::check_relayers_remote` in `stackslib/src/net/chat.rs`. Attacker action: forge a `RelayData` in a pushed message's `relayers` list whose `peer.public_key_hash` is set to the *local node's own* `local_peer.to_neighbor_addr().public_key_hash`, computed by the attacker via a prior handshake with the victim (the local peer's pubkey hash is learnable from any `HandshakeAccept`). Preconditions: attacker previously handshook with the victim to learn its public key hash. Call sequence: `process_relayers` -> `check_relayers_remote` compares each relayer's `public_key_hash` against `local_peer.to_neighbor_addr().public_key_hash`; if matched, the message is dropped with 'message originates from us'. Equality/fault: a message must be dropped IFF it truly already passed through the local node; the check only compares a self-reported field, so an attacker can either (a) forge this hash to force-drop a message from a legitimate third party who relays through this path (targeted valid-message drop = a finding per the rules), or (b) omit/spoof it to bypass would-be loop protection entirely on a genuinely looping message. Impact: Critical — a forged relayer hash causes the node to permanently drop a legitimate, distinct message that never actually passed through it, mislabeling it as a self-relay loop. Proof idea: `stackslib::net::chat` test constructing a message whose `relayers` list contains a `RelayData` with `public_key_hash` equal to the victim's own hash but where the message payload/txid is one the victim has never seen, and asserting `process_relayers` incorrectly returns `false` (drop) for this fully novel message.
