[Target: engine::state::mod::State::ft_withdraw, contract::tokens::nep141::withdraw::ft_resolve_withdraw] Attacker deposits tokens from a FT contract they fully control (self-deployed, registered inside the Verifier as `Nep141TokenId::new(attacker_ft)`), then signs an `FtWithdraw{token: attacker_ft, amount, receiver_id: attacker_receiver, msg: Some(..)}` (is_call = true) MultiPayload. Precondition: attacker's FT contract's `ft_transfer_call` implementation returns an arbitrary `U128` JSON value regardless of what it actually transferred. Call sequence: `execute_intents` -> `ft_withdraw` debits the Verifier's `token_balances` -> Promise to attacker's own `ft_transfer_call` -> `ft_resolve_withdraw` reads `promise_result_checked_json::<U128>(0)` and sets `used = returned.0.min(amount.0)`; attacker returns `used = 0` -> `self.deposit(sender_id, [(token_id, refund)])` re-credits the FULL amount back into the internal ledger even though the FT contract (attacker's own) may have already delivered/kept the tokens outside. Binding: value debited from `token_balances` == value delivered externally + value re-credited by `ft_resolve_withdraw`. Impact: Critical - a `TokenId` backed by a worthless/attacker-controlled asset can be inflated to claim a valuable-looking balance inside the ledger with no on-chain re-derivation of what actually moved. Proof: cargo test / near-workspaces sandbox deploying a malicious FT contract whose `ft_transfer_call` performs a real transfer but returns `U128(0)`, asserting the withdrawer's post-call internal balance equals the pre-withdraw balance (i.e. no net debit occurred) despite tokens having left custody.
