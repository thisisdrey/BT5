`ConnectionInbox::new` and `NetworkConnection::set_public_key` (stackslib/src/net/connection.rs) allow `self.inbox.public_key` to be changed mid-connection (e.g. on re-key via `handle_handshake` in chat.rs calling `update_from_handshake_data`). Between the moment a re-key `Handshake` message is accepted and `set_public_key` is called, can messages already buffered in `self.buf`/`self.preamble` from the OLD key epoch be verified against the NEW public key by `consume_payload_known_length`'s `protocol.verify_payload_bytes(pubk, ...)`, meaning the equality 'message verified under key == key active when message was sent' does not hold across a re-key boundary, letting a message actually signed under the stale key be silently accepted (or a validly-old-signed message be wrongly rejected, dropping it permanently)? Preconditions: peer performs a legitimate re-key handshake mid-session while other messages are in flight. Call sequence: `recv_bytes` buffers old-key message -> re-key `Handshake` processed and `set_public_key` called -> buffered old message flushed through `consume_payload_known_length` under new key. Impact: Critical if acceptance (auth bypass under new key check) — otherwise a permanent-drop rejection of a validly-signed message. Proof idea: Rust test that queues raw bytes for a message signed with key A into `ConnectionInbox.buf`, calls `set_public_key(Some(key_B))` before the buffered bytes are drained, then calls `consume_messages` and asserts whether the message is (wrongly) accepted or (permanently) dropped.
