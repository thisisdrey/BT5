`ConnectionInbox::consume_payload_known_length` (stackslib/src/net/connection.rs) treats any `Err(e)` from `protocol.read_payload` as `net_error::InvalidMessage` regardless of whether `e` was itself an `UnderflowError` (meaning 'not enough data yet', which should NOT be a permanent rejection) — the comment even says 'will never be valid, even if underflowed, since the preamble ought to have told us the message length'. Given `verify_payload_bytes` is called and can succeed BEFORE `read_payload` is attempted, can a remote peer craft a payload that is `preamble.payload_len` bytes long (so it passes `buf_bytes.len() >= payload_len` and signature verification against those exact bytes succeeds), but whose CONTENTS make `read_payload`'s deserializer report `UnderflowError` internally (e.g. a length-prefixed sub-field claiming more bytes than the outer payload actually contains), such that a validly-signed-by-the-peer message is permanently discarded as `InvalidMessage` — is this a rejection that drops a validly authenticated message permanently, and does it also mean the equality 'bytes verified by signature == bytes successfully structurally parsed' can diverge with no recovery path? Preconditions: attacker is an already-handshaked, known-public-key peer (able to produce a message that passes `verify_payload_bytes`). Call sequence: `consume_payload_known_length` -> `verify_payload_bytes` (pass) -> `read_payload` (Err) -> `InvalidMessage`. Impact: Critical, permanent drop of a validly-signed message from a legitimate peer, and the connection may be torn down as a result of trusting `InvalidMessage` as attacker-malice signal when it is a parser/framing bug. Proof idea: Rust test constructing a `StacksMessage` payload that is correctly signed for its declared `payload_len` but whose inner field-length claims exceed the outer buffer, asserting `consume_payload_known_length` returns `InvalidMessage` for a validly-signed message.
