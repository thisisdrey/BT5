`ConnectionOutbox::queue_message` (stackslib/src/net/connection.rs) enforces `if self.outbox.len() > self.outbox_maxlen { return Err(OutboxOverflow) }`, but this check happens BEFORE the new message is pushed, meaning up to `outbox_maxlen + 1` `InflightMessage<P>` entries (each holding a `PipeRead` and optional `ReceiverNotify`) can exist simultaneously, mirroring the same off-by-one pattern as the inbox check. Given that outbound queuing is driven by processing of remotely-supplied unsolicited/relay traffic (e.g. relaying a gossiped block to many peers), can a remote peer that triggers `outbox_maxlen+1` back-to-back relay-worthy messages in one processing batch cause transient over-allocation past the configured `ConnectionOptions.outbox_maxlen`, and is this bound actually load-bearing for memory safety anywhere downstream (e.g. `PipeRead`/`PipeWrite` OS pipe fd exhaustion)? Preconditions: attacker gossips `outbox_maxlen+1` relayable items in a single relay round. Call sequence: relay logic -> `make_relay_handle`/`make_request_handle` -> `queue_message`. Impact: High, bounded per-connection resource over-allocation from a single relay batch, a bounded compute/resource DoS distinct from volumetric flooding. Proof idea: Rust test calling `queue_message` `outbox_maxlen+1` times in a loop and asserting the actual `outbox.len()` observed exceeds `outbox_maxlen` before the overflow error is returned.
