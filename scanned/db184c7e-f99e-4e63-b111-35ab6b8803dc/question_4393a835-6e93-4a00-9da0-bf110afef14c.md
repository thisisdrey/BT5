`Preamble::verify` in codec.rs, invoked transitively from `StacksP2P::verify_payload_bytes` which `ConnectionInbox::consume_payload_known_length` (stackslib/src/net/connection.rs) calls, recomputes the digest over `preamble_bits` (with `signature` zeroed) concatenated with the exact `bytes` slice passed in (`buf_bytes = self.buf.get(self.message_ptr..)`, unbounded past `payload_len`). Since `verify_payload_bytes` internally does `bytes.get(..preamble.payload_len as usize)` to re-slice before hashing, can a remote peer append extra trailing bytes AFTER a validly signed `payload_len`-sized message in the same TCP segment such that those trailing bytes are silently treated as belonging to a subsequent message rather than counted toward what was cryptographically authenticated, and is there any path where `read_payload`'s returned `message_len` differs from `preamble.payload_len` such that the 'authenticated span' (`preamble.payload_len`) and the 'consumed span' (`message_len`) diverge, breaking 'bytes verified == bytes advanced past'? Preconditions: post-handshake connection with known public key. Call sequence: `consume_payload_known_length` -> `verify_payload_bytes` (hashes `..payload_len`) -> `protocol.read_payload` (returns its own `message_len`) -> `message_ptr += message_len`. Impact: Critical, potential message-boundary desync where unauthenticated bytes get spliced into the authenticated stream. Proof idea: Rust test crafting `payload_len` and a `read_payload` deserializer stub where the actual consensus-deserialized message consumes fewer bytes than `payload_len`, asserting the leftover unauthenticated bytes influence the next parsed message rather than being discarded/rejected.
