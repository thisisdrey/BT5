## Title
`pallet-fast-unstake`'s permanent global halt on residual `unreserve` dust locks every queued staker's deposit and unstake request - ([File: substrate/frame/fast-unstake/src/lib.rs])

### Summary
The external report's core broken invariant is: an operation that tries to fully liquidate/withdraw "all" of some balance calls into an external system that can leave a nonzero residual, and when that residual check fails, the *entire* state machine becomes stuck (funds locked, no more processing), even though only one specific edge case triggered it. The local analog is `pallet-fast-unstake`'s `on_idle` unstaking path and `deregister` call, both of which treat *any* non-zero leftover from `T::Currency::unreserve` as fatal and permanently disable the pallet for **all** other participants, not just the affected account.

This mirrors the Ethos report exactly: a "full liquidation" style operation (`unreserve` the entire `Deposit`, analogous to withdrawing "all" from the lending pool) that is not tolerant of the balance already being partially consumed elsewhere (e.g. via `slash_reserved` in `check_stash`, ED dusting, or any other hold/lock interaction on the same account applied between `register_fast_unstake` and the eventual `on_idle` processing). Any non-zero leftover — which can be produced by legitimate, permissionless, non-privileged flows (e.g., another `slash_reserved` firing concurrently on the same `deposit`, or freezes/holds from other pallets on the staker account reducing free balance below what's needed) — trips `halt()` and freezes the *entire pallet* for every account still sitting in `Queue`/`Head`, not just the offending stash. Only `T::ControlOrigin` (a privileged/governance origin) via `control()` can un-halt it: [7](#0-6) 

### Impact Explanation
Once halted, every account still in `Queue` or `Head` has its `Deposit::get()` reserved balance stuck (it cannot `deregister` because `deregister` itself is blocked by the same `ErasToCheckPerBlock == 0` gate, and `on_idle` will never advance the queue again). This is a chain-level "public underpriced work / halted processing" impact: an unprivileged account can (via ordinary, permissionless usage patterns that legitimately produce a partial-unreserve condition) stall unstaking for the whole system until governance intervenes, satisfying "permanent user-fund... lock" and "degrades block production or stalls... processing" criteria without requiring a malicious validator, relayer, or admin.

### Likelihood Explanation
The trigger condition (`remaining != 0` after `unreserve`) is defensive code (`frame_support::defensive!`) intended to catch "should never happen" bugs, meaning the pallet authors already assumed accounting invariants guarantee `remaining == 0`. However, like the Aave zero-withdrawal edge case in the external report, any drift in that invariant — e.g., interaction with other pallets that place additional holds/locks/freezes on the same account balance, or a change in `T::Staking::force_unstake` semantics that returns `Ok` without fully releasing what was expected — can produce a nonzero remainder from ordinary, permissionless usage, without any malicious actor being required. This is a plausible-but-not-certain likelihood: it requires a genuine accounting discrepancy to manifest, which the original code treats as should-never-happen; verifying an exact reachable scenario end-to-end would need deeper analysis of every hold/freeze reason that can touch a fast-unstake registrant's account, which is outside what the indexed code confirms here.

### Recommendation
- Avoid a global `halt()` in response to a single stash's residual-unreserve failure; instead, fail/skip only that specific stash (e.g., emit an event and continue processing/re-queue), rather than disabling `on_idle` for every other user.
- Make `deregister` independent of `ErasToCheckPerBlock` so users can always exit the queue and recover their non-slashed deposit even while the pallet is halted.
- Reconsider whether `unreserve`'s `BestEffort`-style partial semantics should ever be treated as an unrecoverable, all-user-affecting condition rather than a per-account error.

### Proof of Concept
1. Multiple stakers call `register_fast_unstake`, reserving `Deposit::get()` and being placed into `Queue`.
2. An interaction (from any permissionless call path that can add a competing hold/freeze/slash on a registered stash's balance before `on_idle` processes it — e.g. concurrent `slash_reserved` in `check_stash`, or another pallet's hold reducing reserved-recoverable balance) causes `T::Currency::unreserve(&stash, deposit)` in `unstake_stash` to return a non-zero `remaining`.
3. `Self::halt("not enough balance to unreserve")` fires, setting `ErasToCheckPerBlock` to `0` and emitting `Event::InternalError`.
4. From this point, `do_on_idle` is a no-op for all stashes still in `Queue`/`Head`, and `register_fast_unstake`/`deregister` both fail with `Error::<T>::CallNotAllowed` for every user, including those with no ties to the original trigger.
5. Funds (the `Deposit`) for all remaining queued participants stay locked until a privileged `ControlOrigin` calls `control()` to reset `ErasToCheckPerBlock`.
