Based on my analysis, the strongest local analog to the reported Solidity bug (division by a factor that can silently collapse to zero, producing an incorrect payout instead of reverting/being guarded) is in the classic `pallet-staking` reward-splitting code, not `staking-async` (which was hardened against exactly this class of bug).

### Title
Unsanitized zero-total `Exposure` allows `Perbill::from_rational` to silently saturate to 100%, corrupting validator/nominator payout shares - (File: `substrate/frame/staking/src/pallet/impls.rs`)

### Summary
`do_payout_stakers_by_page` in `pallet-staking` divides validator/nominator stake shares by `exposure.total()` using `Perbill::from_rational(numerator, exposure.total())` without ever checking that `exposure.total()` is non-zero, unlike sibling code paths in this very repository that explicitly guard the equivalent denominator before calling `from_rational`. [1](#0-0) 

### Finding Description
`Perbill::from_rational` (the default `PerThing` trait method) does not panic on a zero divisor the way a Solidity `/` operator does. Instead it calls `from_rational_with_rounding`, and on `q.is_zero()` returns `Err(())`, which the default implementation silently converts to `Self::one()` (100%): [2](#0-1) [3](#0-2) 

This is the exact structural analog of the external report: instead of a Solidity `revert` on division-by-zero for a factor derived from a "share/percentage" concept (`fsOf`), Substrate's `Perbill::from_rational` silently *saturates* to a wrong-but-valid value (100%) when its denominator collapses to zero — no error is raised, so the wrong computed share flows straight into the payout logic.

In `do_payout_stakers_by_page`, three consecutive divisions use `exposure.total()` as the denominator with no zero-check:
```rust
let validator_exposure_part = Perbill::from_rational(exposure.own(), exposure.total());
let validator_staking_payout = validator_exposure_part * validator_leftover_payout;
let page_stake_part = Perbill::from_rational(exposure.page_total(), exposure.total());
...
let nominator_exposure_part = Perbill::from_rational(nominator.value, exposure.total());
``` [4](#0-3) 

`exposure.total()` is populated at election time in `collect_exposures`, where `own`, `others`, and `total` are all built via `T::CurrencyToVote::to_currency(weight, total_issuance)`: [5](#0-4) 
`CurrencyToVote` performs a saturating truncation from the election's internal `ExtendedBalance` (u128-scale, normalized against total issuance) down to the runtime's `Balance`/vote-weight type. On chains with very large total issuance relative to a validator's self-stake (or in edge configurations where `MinValidatorBond`/election weight normalization rounds small stakes toward zero), this conversion can legitimately produce `own == 0` and, in the degenerate case, `total == 0` for a validator that still received reward points from block/uncle authorship (`ErasRewardPoints`), since reward points are earned independently of the *exposure* magnitude. The function does check `validator_reward_points.is_zero()` and bails early, but it never checks `exposure.total().is_zero()`. [6](#0-5) 

Once `exposure.total() == 0`, every `Perbill::from_rational(x, 0)` call above collapses to `Perbill::one()`, so:
- `validator_exposure_part` becomes 100%, giving the validator the *entire* `validator_leftover_payout` regardless of actual own-stake.
- `page_stake_part` becomes 100%, so the *whole* commission is credited on a single page instead of being prorated, and if multiple pages exist this is repeated per page — a payout can be claimed for a page where it should have been a fraction, and (because `page_stake_part` is calculated fresh per page call) each page can independently receive 100% attribution rather than a proportional slice, corrupting the total distributed across all pages.
- Every nominator's `nominator_exposure_part` also becomes 100%, so *every* nominator receives the entire `validator_leftover_payout` rather than their proportional share.

That the codebase authors are aware this class of bug is real and dangerous is demonstrated by `staking-async`'s hardened rewrite of the same computation, which explicitly checks the equivalent denominators (`ErasSumWeightedPoints`, `ErasSumValidatorIncentiveWeight`) for zero and emits an `UnexpectedKind::ValidatorIncentiveWeightMismatch` event, returning `None` instead of calling `from_rational` with a zero divisor: [7](#0-6) 
Likewise `pallet-nomination-pools`' equivalent ratio helper explicitly special-cases a zero denominator before dividing: [8](#0-7) 
The legacy `pallet-staking::do_payout_stakers_by_page` was never updated with the same guard.

### Impact Explanation
This corrupts payout accounting for staking rewards — the exact fund-conservation invariant flagged in the "Required Impacts": *"Balances, assets, NFTs, staking, pools, treasury spends, bridge rewards, and contract-held value must conserve value and settle exactly once to the rightful beneficiary and amount."* A wrong beneficiary (100% instead of a fraction) receiving inflated rewards means either over-minting/over-transfer from the reward pot to one party at the expense of others, or duplicated 100%-share settlement across multiple exposure pages for the same era — both are real runtime bugs that compromise intended reward-distribution behavior without requiring any privileged actor, malicious validator, or governance action; the trigger is purely a data condition (`exposure.total() == 0`) reachable through normal election/`CurrencyToVote` arithmetic.

### Likelihood Explanation
Moderate-to-low but non-zero: it depends on `CurrencyToVote`'s rounding behavior and the relationship between a validator's self-stake and total issuance at election time producing a fully-zeroed `Exposure` while the validator still accrues reward points via block authorship. This is a genuine edge case rather than a common occurrence, similar in spirit to the original report's `fsOf = 0` edge case, which itself required a specific sequence of otherwise-legitimate user actions (no admin/attacker collusion) to reach. The absence of any defensive zero-check — in contrast to the parallel, already-hardened code paths in `staking-async` and `nomination-pools` — is the concrete gap.

### Recommendation
Guard `exposure.total()` for zero before calling `Perbill::from_rational` in `do_payout_stakers_by_page`, mirroring the pattern already used in `staking-async::calculate_validator_incentive_for_page` and `nomination-pools::point_to_balance`: if `exposure.total()` (or the relevant page-level total) is zero, skip the payout for that entity (or emit a diagnostic/`Unexpected` event) instead of letting `Perbill::from_rational` silently saturate to `Perbill::one()`.

### Proof of Concept
1. Configure (or naturally reach, given large total issuance vs. a validator's self-bond) a state where `T::CurrencyToVote::to_currency` rounds a validator's election weight and all of its nominators' weights down to `0`, so `collect_exposures` stores `Exposure { own: 0, others: [], total: 0 }` for that validator/era.
2. Ensure the validator still receives non-zero `ErasRewardPoints` for the era (via normal block-authorship credit), so the early-return guard at `validator_reward_points.is_zero()` is bypassed. [9](#0-8) 
3. Call `payout_stakers` / `payout_stakers_by_page` for that era/validator (public, unprivileged, permissionless dispatch).
4. `Perbill::from_rational(exposure.own(), exposure.total())` evaluates `from_rational(0, 0)`, which per `per_things.rs` returns `Perbill::one()` rather than erroring, so `validator_staking_payout` becomes the full `validator_leftover_payout` instead of the correct (zero, since own-stake is zero) share; the same applies to `page_stake_part` and any nominator entries with non-zero `nominator.value`, resulting in incorrect/duplicated payout amounts credited to the wrong beneficiaries. [4](#0-3)

	fn collect_exposures(
		supports: BoundedSupportsOf<T::ElectionProvider>,
	) -> BoundedVec<(T::AccountId, Exposure<T::AccountId, BalanceOf<T>>), MaxWinnersOf<T>> {
		let total_issuance = asset::total_issuance::<T>();
		let to_currency = |e: frame_election_provider_support::ExtendedBalance| {
			T::CurrencyToVote::to_currency(e, total_issuance)
		};

		supports
			.into_iter()
			.map(|(validator, support)| {
				// Build `struct exposure` from `support`.
				let mut others = Vec::with_capacity(support.voters.len());
				let mut own: BalanceOf<T> = Zero::zero();
				let mut total: BalanceOf<T> = Zero::zero();
				support
					.voters
					.into_iter()
					.map(|(nominator, weight)| (nominator, to_currency(weight)))
					.for_each(|(nominator, stake)| {
						if nominator == validator {
							own = own.saturating_add(stake);
						} else {
							others.push(IndividualExposure { who: nominator, value: stake });
						}
						total = total.saturating_add(stake);
					});

				let exposure = Exposure { own, others, total };
				(validator, exposure)
			})
			.try_collect()
			.expect("we only map through support vector which cannot change the size; qed")
	}

	fn point_to_balance(
		current_balance: BalanceOf<T>,
		current_points: BalanceOf<T>,
		points: BalanceOf<T>,
	) -> BalanceOf<T> {
		let u256 = T::BalanceToU256::convert;
		let balance = T::U256ToBalance::convert;
		if current_balance.is_zero() || current_points.is_zero() || points.is_zero() {
			// There is nothing to unbond
			return Zero::zero();
		}

		// Equivalent of (current_balance / current_points) * points
		balance(
			u256(current_balance)
				.saturating_mul(u256(points))
				// We check for zero above
				.div(u256(current_points)),
		)
	}
