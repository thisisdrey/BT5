Target: `ft_resolve_withdraw`. Attacker action: deploy an FT receiver contract that on `ft_on_transfer` transfers the received tokens onward to a third account (draining itself) before the promise resolves, then returns `U128(0)` as the unused amount so the resolver thinks nothing was used. Preconditions: attacker controls receiver contract logic, has deposited `token` inside the Verifier. Call sequence: `ft_withdraw(token, receiver_id=attacker_receiver, amount, msg=Some(...))` -> `internal_ft_withdraw` debits `token_balances` -> `do_ft_withdraw` sends `ft_transfer_call` -> receiver drains balance and returns `0` -> `ft_resolve_withdraw` computes `used=0`, `refund=amount.0`, credits `sender_id` full amount again via `self.deposit`. Binding: (amount debited) == (tokens that left the Verifier and stayed at receiver, which is 0 since drained) + (amount re-credited, amount.0), giving a double credit of `amount.0` to attacker relative to actual tokens moved. Scoped impact: Critical — attacker doubles their `token_balances` entry inside the Verifier while the underlying FT tokens are gone, breaking CONSERVATION: sum of token_balances changes across this call != actual assets custodied change. Affected party: the Verifier's solvency (all other depositors of that token). Proof idea: cargo test simulating self-transfer-then-lie receiver, assert Verifier's on-chain FT balance decreases while token_balances sum for that token stays flat (should decrease, doesn't).
