Based on my investigation, I found a directly analogous bug in `pallet-scarcity`, a Substrate NFT pallet that tracks two separate supply counters per item definition: a permanent `supply` (cumulative mint count, never decremented) and a `live_supply` (current outstanding count, decremented on burn).

### Title
`ItemDefinition::supply` is never decremented on burn while it gates per-collection minting limits, causing permanent under-issuance and skewed relative ownership - (File: `substrate/frame/scarcity/src/lib.rs`)

### Summary
`pallet-scarcity`'s `do_burn` function decrements only `live_supply` and leaves the immutable, mint-gating `supply` counter untouched, mirroring the Nouns Builder `Token::_addFounders`/`totalSupply` bug: a counter meant to represent "how many units are in circulation" is used both to gate future minting and (implicitly, by any collection-level share logic built on it) as the denominator for ownership accounting, but burns never decrement it.

### Finding Description
`Pallet::do_burn` in `substrate/frame/scarcity/src/lib.rs` explicitly decrements only the "live" counter: [1](#0-0) 
while `supply` (the historical/cumulative mint counter used to gate whether more items can still be minted for a definition) is left untouched. The pallet's own regression test names this behavior explicitly — `burn_releases_instance_deposit_and_preserves_supply_and_item_metadata` — and asserts that after a burn, `definition.supply` is unchanged while `definition.live_supply` drops to zero: [2](#0-1) 

This is structurally identical to the Nouns Builder finding: a "total minted so far" counter is treated as permanent and never reduced when an item is destroyed, even though the destroyed item's slot in any fixed-size or percentage-based allocation scheme is now empty. Any collection-owner or runtime logic built on top of `pallet-scarcity` that (a) caps total mintable instances per item definition using `supply`, or (b) computes a party's ownership share as `owned / supply` (the Nouns Builder pattern) will permanently under-count available/burned capacity or skew percentages upward for large holders whose peers had NFTs burned, exactly like the founder-share drift in the original report. Because `supply` never comes back down, burning items permanently reduces effective circulating count relative to the frozen `supply` denominator, and it can never be re-minted up to the original cap even though it should be able to.

### Impact Explanation
This falls under "Balances, assets, NFTs, staking, pools, treasury spends, bridge rewards, and contract-held value must conserve value and settle exactly once to the rightful beneficiary and amount." Here, the invariant broken is: `supply` should represent currently-issued instances for the purposes of any capacity check or share calculation, but it drifts upward permanently relative to actual circulating (`live_supply`) instances once burns occur. Any higher-level pallet or contract built on `MintWithoutDeposit`/`Pallet::mint`/`do_burn` that treats `supply` as "current outstanding count" (rather than "all-time minted count") for allocation, ownership-percentage, or remaining-capacity purposes will produce incorrect, permanently-skewed results — mirroring the exact M-22 impact (unfair increase in relative ownership/power as burns accumulate).

### Likelihood Explanation
Likelihood is moderate-to-high: this is not a peripheral code path — burn is a first-class public entrypoint (any purse holder can burn their own NFT, and the collection owner can force-burn), and the divergence between `supply` and `live_supply` accrues automatically and permanently with every ordinary burn, requiring no adversarial conditions, malicious peer, admin, or governance action — exactly matching the "public, unprivileged attacker path" requirement.

### Recommendation
Decide the intended semantics of `ItemDefinition::supply` explicitly. If it is meant to represent "currently circulating supply" for capacity gating or proportional-ownership calculations, `do_burn` must decrement it alongside `live_supply`. If `supply` is intentionally an immutable "all-time minted" counter (which the test name `preserves_supply` suggests is the deliberate design), then any runtime or contract layer built on this pallet must be documented to never use `supply` as a live-ownership-share denominator, and a separate, clearly-named "currently mintable capacity" field (distinct from both `supply` and `live_supply`) should be exposed if per-definition mint caps are intended to free up on burn.

### Proof of Concept
1. Collection owner creates an item definition with a mint cap enforced via `supply`.
2. 100 instances are minted; `supply == 100`, `live_supply == 100`.
3. 10 instances are burned by their holders (mirroring "unsold auction NFTs" being burned): `live_supply == 90`, but `supply` remains `100`, confirmed by the test's own assertion `assert_eq!(definition.supply, supply)` post-burn. [3](#0-2) 
4. Any runtime logic computing an account's ownership share as `owned_count / definition.supply` (the direct analog of Nouns Builder's `totalSupply`-based founder percentage) will compute `2/100` instead of the fair `2/90`, permanently understating the effective denominator's shrinkage and overstating relative power for holders unaffected by the burns — with no way to correct this since `supply` is a monotonically non-decreasing, mint-gating counter.
