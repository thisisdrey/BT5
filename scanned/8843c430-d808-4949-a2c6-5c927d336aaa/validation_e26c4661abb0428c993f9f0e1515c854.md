## Title
Strict sequential-nonce enforcement in `pallet-inbound-queue::submit` permanently halts an entire bridge channel if any downstream step for a message fails deterministically, with no admin recovery path - ([File: bridges/snowbridge/pallets/inbound-queue/src/lib.rs])

### Summary
Snowbridge's `pallet-inbound-queue` `submit()` extrinsic enforces strict, gapless nonce ordering per channel via `Nonce<T>::try_mutate` before performing several fallible downstream operations (fee-burn via `AssetTransactor`, XCM conversion, XCM send). Because a dispatchable's storage effects (including the nonce bump) are rolled back atomically on any `Err` return, a message whose *later* steps fail deterministically can never advance the channel's nonce, and — because nonce N+1 can only ever be accepted after nonce N is durably recorded — every subsequent message on that channel becomes permanently unprocessable. This mirrors the reported Oracle bug: a stuck "previous provider" commit blocks all forward progress, and there is no fallback/skip mechanism to recover.

### Finding Description
`submit()` performs, in order: verify the light-client proof, decode/validate the envelope, look up the channel, then commit the strictly-sequential nonce bump: [1](#0-0) 

only *after* that nonce commit does it attempt the fee-relayer transfer, decode the XCM payload, convert it, burn the teleport fee via `AssetTransactor`, and finally call `send_xcm`: [2](#0-1) 

`burn_fees` can fail deterministically with `TokenError::FundsUnavailable` if the destination's sovereign account cannot satisfy `can_check_out`/`withdraw_asset` for the fee amount embedded in the payload: [3](#0-2) 

`do_convert`/`send_xcm` can likewise fail deterministically (`ConvertMessageError`, `XcmpSendError::Unroutable/DestinationUnsupported/ExceedsMaxMessageSize`, etc.): [4](#0-3) 

Since `submit` is a normal FRAME dispatchable (not wrapped so the nonce-write is committed independently of the rest of the call), any `Err(...)` returned from it — including those from `burn_fees`/`do_convert`/`send_xcm` — reverts the entire extrinsic's storage mutations, including the `Nonce<T>` bump performed earlier in the same call. Because `Nonce<T>` requires the *exact* successor nonce (`envelope.nonce != nonce.saturating_add(1)` → `InvalidNonce`), no future message with a higher nonce for that channel can ever be accepted until the stuck nonce N is durably recorded. The only two calls exposed by the pallet are `submit` (permissionless) and `set_operating_mode` (root, halt/resume only) — there is no root-level or automatic mechanism to skip, force-advance, or replay-with-different-parameters a stuck nonce: [5](#0-4) 

This is structurally identical to the reported Oracle issue: a state machine that gates all forward progress on successfully finalizing one specific pending item, with no cancellation/skip path, and a deterministic failure condition (a fee/liquidity/XCM condition) that can arise from ordinary system operation rather than any attacker or governance action.

### Impact Explanation
If message nonce N cannot be durably processed (e.g., the destination parachain's sovereign account balance is insufficient to cover the embedded teleport fee, or the destination channel becomes unroutable/oversized for XCM at that point in time), the entire inbound channel for that `ChannelId` stalls permanently: no further Ethereum→Polkadot messages for that channel can ever be delivered, regardless of how many retries a relayer performs, because retrying the identical failing message will always fail the same way, and no other nonce can be substituted. This is a permanent bridge-state lock: relayer rewards for that channel stop, all queued cross-chain asset transfers for that destination are frozen, and there is no operator-controlled repair function in the pallet to unblock it (the only governance lever, `set_operating_mode`, can halt/resume the whole pallet but cannot skip or replace a stuck nonce).

### Likelihood Explanation
The triggering condition does not require a malicious relayer, validator, or governance actor — it is a foreseeable operational condition: the sovereign account funding for a given destination parachain's relayer-reward/fee-burn balance can be temporarily or permanently exhausted (e.g., due to fee-price changes, account reaping, or simply insufficient top-ups), or a destination channel/XCM route can become unroutable. Because `submit` is permissionless and open to any relayer supplying a valid Ethereum proof, once such a condition exists for the next expected nonce, the channel is stuck until the underlying condition changes on its own (if it can at all) — there is no built-in remediation.

### Recommendation
Decouple nonce acceptance from unrelated downstream fallibility: commit the nonce advance unconditionally once the message is validated as authentic and properly sequenced, and treat failures in fee-burn/conversion/XCM-send as non-fatal to nonce progression (e.g., emit a `ProcessingFailed`/dead-letter event and skip dispatch, similar to `pallet-message-queue`'s permanent-vs-temporary overweight/unprocessable classification), or add a root-only extrinsic to force-advance/skip a stuck nonce for a channel. At minimum, wrap the "downstream" steps so their failure does not roll back the `Nonce<T>` bump, and expose telemetry/events so operators can detect and remediate a stuck channel without requiring a runtime upgrade.

### Proof of Concept
1. Configure a destination parachain channel whose sovereign account balance is intentionally at or near zero for the relevant fee-token.
2. Relayer submits a valid Ethereum event proof for nonce `N` whose embedded XCM teleport `fee` exceeds what `T::AssetTransactor::withdraw_asset` can satisfy from the sovereign account (see `burn_fees` at `bridges/snowbridge/pallets/inbound-queue/src/lib.rs:352-375`).
3. `submit` proceeds through proof verification, envelope decode, and the `Nonce<T>::try_mutate` bump (lines 256-267), then fails at `Self::burn_fees(...)?` (line 298), returning `Err`.
4. FRAME reverts all storage changes for the extrinsic, including the nonce bump — `Nonce<T>` for the channel remains at `N-1`.
5. Any subsequent relayer submission for nonce `N` (retried) fails identically as long as the sovereign account remains underfunded; any submission for nonce `N+1` fails with `InvalidNonce` because the check at line 261 requires exact sequencing.
6. No call in the pallet (`submit`, `set_operating_mode`) can skip or force-advance the nonce, so the channel is permanently stalled until/unless the sovereign account is refunded by an unrelated process — which the protocol does not guarantee will happen.

	#[pallet::call]
	impl<T: Config> Pallet<T> {
		/// Submit an inbound message originating from the Gateway contract on Ethereum
		#[pallet::call_index(0)]
		#[pallet::weight(T::WeightInfo::submit())]
		pub fn submit(origin: OriginFor<T>, event: EventProof) -> DispatchResult {
			let who = ensure_signed(origin)?;
			ensure!(!Self::operating_mode().is_halted(), Error::<T>::Halted);

			// submit message to verifier for verification
			T::Verifier::verify(&event.event_log, &event.proof)
				.map_err(|e| Error::<T>::Verification(e))?;

			// Decode event log into an Envelope
			let envelope =
				Envelope::try_from(&event.event_log).map_err(|_| Error::<T>::InvalidEnvelope)?;

			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == envelope.gateway, Error::<T>::InvalidGateway);

			// Retrieve the registered channel for this message
			let channel =
				T::ChannelLookup::lookup(envelope.channel_id).ok_or(Error::<T>::InvalidChannel)?;

			// Verify message nonce
			<Nonce<T>>::try_mutate(envelope.channel_id, |nonce| -> DispatchResult {
				if *nonce == u64::MAX {
					return Err(Error::<T>::MaxNonceReached.into());
				}
				if envelope.nonce != nonce.saturating_add(1) {
					Err(Error::<T>::InvalidNonce.into())
				} else {
					*nonce = nonce.saturating_add(1);
					Ok(())
				}
			})?;

			// Reward relayer from the sovereign account of the destination parachain, only if funds
			// are available
			let sovereign_account = sibling_sovereign_account::<T>(channel.para_id);
			let delivery_cost = Self::calculate_delivery_cost(event.encode().len() as u32);
			let amount = T::Token::reducible_balance(
				&sovereign_account,
				Preservation::Preserve,
				Fortitude::Polite,
			)
			.min(delivery_cost);
			if !amount.is_zero() {
				T::Token::transfer(&sovereign_account, &who, amount, Preservation::Preserve)?;
			}

			// Decode payload into `VersionedMessage`
			let message = VersionedMessage::decode_all(&mut envelope.payload.as_ref())
				.map_err(|_| Error::<T>::InvalidPayload)?;

			// Decode message into XCM
			let (xcm, fee) = Self::do_convert(envelope.message_id, message.clone())?;

			tracing::info!(
				target: LOG_TARGET,
				?xcm,
				?fee,
				"💫 xcm decoded"
			);

			// Burning fees for teleport
			Self::burn_fees(channel.para_id, fee)?;

			// Attempt to send XCM to a dest parachain
			let message_id = Self::send_xcm(xcm, channel.para_id)?;

			Self::deposit_event(Event::MessageReceived {
				channel_id: envelope.channel_id,
				nonce: envelope.nonce,
				message_id,
				fee_burned: fee,
			});

			Ok(())
		}

		/// Halt or resume all pallet operations. May only be called by root.
		#[pallet::call_index(1)]
		#[pallet::weight((T::DbWeight::get().reads_writes(1, 1), DispatchClass::Operational))]
		pub fn set_operating_mode(
			origin: OriginFor<T>,
			mode: BasicOperatingMode,
		) -> DispatchResult {
			ensure_root(origin)?;
			OperatingMode::<T>::set(mode);
			Self::deposit_event(Event::OperatingModeChanged { mode });
			Ok(())
		}
	}

		pub fn do_convert(
			message_id: H256,

		) -> Result<(Xcm<()>, BalanceOf<T>), Error<T>> {

		pub fn send_xcm(xcm: Xcm<()>, dest: ParaId) -> Result<XcmHash, Error<T>> {

			let (xcm_hash, _) = send_xcm::<T::XcmSender>(dest, xcm).map_err(Error::<T>::from)?;
			Ok(xcm_hash)
