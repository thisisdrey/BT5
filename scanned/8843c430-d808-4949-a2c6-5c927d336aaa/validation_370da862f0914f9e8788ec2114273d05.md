## Analysis

The reported bug class is: **reward-obligation state (rate, expiry) is not kept consistent with the actual token balance backing those obligations**, so legitimate claimants later hit "insufficient funds" or get starved while earlier claimants drain the pot.

The closest local analog is in `pallet-asset-rewards` (`substrate/frame/asset-rewards/src/lib.rs`), specifically the pair `set_pool_reward_rate_per_block` / `set_pool_expiry_block` versus `harvest_rewards`.

### Title
Reward pool obligations (`reward_rate_per_block` / `expiry_block`) can be increased without any check that the pool's actual token balance can cover them, causing harvest starvation for legitimate stakers - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`RewardsPool::set_pool_reward_rate_per_block` and `RewardsPool::set_pool_expiry_block` allow a pool's admin to raise the promised reward obligation (`reward_rate_per_block * remaining_blocks`) at any time, with no check that `pool_info.account` actually holds (or will be topped up with) enough `reward_asset_id` tokens to cover the new obligation. `harvest_rewards` then unconditionally transfers `staker_info.rewards` — an amount computed purely from the rate/expiry accounting, decoupled from the pot's real balance [1](#0-0) . This is the same broken invariant as the `ActivityRewardDistributor` report: the accounting parameters that drive future payout math are mutated without any accompanying check/update against the real underlying balance.

### Finding Description
- `reward_per_token` computes accrued rewards strictly from `reward_rate_per_block`, elapsed blocks, and `total_tokens_staked` — it has no notion of the pool's actual reward-asset balance [2](#0-1) .
- `set_pool_reward_rate_per_block` only enforces that the new rate is *strictly greater* than the old one; it never checks `T::Assets::reducible_balance(pool_info.reward_asset_id, &pool_info.account, ...)` against the new implied total obligation until `expiry_block` [3](#0-2) .
- `set_pool_expiry_block` similarly only enforces the new expiry is later than the old one, again with no balance check against the extended obligation window [4](#0-3) .
- `deposit_reward_tokens` is a permissionless, optional top-up call — nothing forces the pot to actually be funded to match the promised rate/expiry before stakers start accruing entitlement at the new rate [5](#0-4) .
- `harvest_rewards` then transfers the staker's full computed `rewards` from the pool account using `Preservation::Expendable`, with no partial-payout or balance-sufficiency accounting update if the transfer fails [6](#0-5) .

This exactly mirrors the PMX report's broken invariant: mutating a parameter that drives future reward math (`rewardPerDay`/`endTimestamp` there, `reward_rate_per_block`/`expiry_block` here) without reconciling it against the token balance that must actually back it, and without any atomic guard tying the promise to the funding.

### Impact Explanation
Once the promised obligation (`rate * remaining_blocks`, summed across all stakers proportional to points) exceeds the pool's actual `reward_asset_id` balance, `harvest_rewards` for later-calling (but equally, or more, entitled) stakers will fail with an `Assets` transfer error, since the pot is drained by whoever calls first. This is a first-come-first-served fund race baked into the protocol: honestly-accrued rewards for some stakers become permanently unclaimable once the shared pot is exhausted by others, which is a "public underpriced work" / "permanent user-fund lock" class impact — legitimate stakers can lose access to rewards they are entitled to under the pallet's own accounting rules.

### Likelihood Explanation
Reaching this state does not require a malicious admin — it only requires the admin using the *intended* (and only-increasing) knobs `set_pool_reward_rate_per_block` / `set_pool_expiry_block` in good faith without perfectly forecasting funding, or simply an admin who under-funds the pool relative to a rate increase. Because these calls have zero coupling to `T::Assets::reducible_balance`, this is not a hypothetical edge case — any rate increase or expiry extension that isn't matched 1:1 by a `deposit_reward_tokens` call creates exactly this exposure, and any staker who is slow to harvest (or joined near pool depletion) is put at risk of an unclaimable, correctly-computed reward balance.

### Recommendation
In `set_pool_reward_rate_per_block` and `set_pool_expiry_block`, before committing the new rate/expiry, compute the pool's total outstanding obligation to expiry (`reward_rate_per_block * (expiry_block - last_update_block)`, or equivalent covering already-accrued-but-unclaimed rewards) and assert it does not exceed `T::Assets::reducible_balance(pool_info.reward_asset_id, &pool_info.account, ...)`, returning an `InsufficientFunds`-style error otherwise. Alternatively, require `deposit_reward_tokens` to be called atomically as part of the same extrinsic when raising rate/expiry, so the promise and the funding move together, analogous to updating `endTimestamp`/`lastUpdatedRewardTimestamp` together with `totalReward` in the original PMX fix.

### Proof of Concept
1. Admin creates a pool with `reward_rate_per_block = R1` and `expiry_block = E1`, funded with exactly enough `reward_asset` to cover `R1 * (E1 - start)`.
2. Two stakers, Alice and Bob, stake equal amounts early in the pool's life.
3. Admin calls `set_pool_reward_rate_per_block` to raise the rate to `R2 > R1` (allowed unconditionally) — see `substrate/frame/asset-rewards/src/lib.rs:900-922`. No corresponding `deposit_reward_tokens` call is made.
4. Time advances to `E1`. Both Alice and Bob's computed `reward_per_token`/`rewards` now reflect the higher `R2` rate for the period after step 3, but the pool account was never topped up to cover the delta.
5. Alice calls `harvest_rewards` first and successfully drains most of the remaining pot (`substrate/frame/asset-rewards/src/lib.rs:586-595`).
6. Bob calls `harvest_rewards` for his equally-valid, equally-computed `rewards` and the `T::Assets::transfer` fails/reverts because the pot no longer has sufficient `reward_asset_id` balance — Bob's legitimately accrued reward is unclaimable.

		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}

	fn set_pool_reward_rate_per_block(
		admin: &T::AccountId,
		pool_id: PoolId,
		new_reward_rate_per_block: T::Balance,
	) -> DispatchResult {
		let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
		ensure!(pool_info.admin == *admin, BadOrigin);
		ensure!(
			new_reward_rate_per_block > pool_info.reward_rate_per_block,
			Error::<T>::RewardRateCut
		);

		// Always start by updating the pool rewards.
		let rewards_per_token = Self::reward_per_token(&pool_info)?;
		let mut pool_info = Self::update_pool_rewards(&pool_info, rewards_per_token)?;

		pool_info.reward_rate_per_block = new_reward_rate_per_block;
		Pools::<T>::insert(pool_id, pool_info);

		Self::deposit_event(Event::PoolRewardRateModified { pool_id, new_reward_rate_per_block });

		Ok(())
	}

	fn set_pool_expiry_block(
		admin: &T::AccountId,
		pool_id: PoolId,
		new_expiry: DispatchTime<BlockNumberFor<T>>,
	) -> DispatchResult {
		let now = T::BlockNumberProvider::current_block_number();
		let new_expiry_block = new_expiry.evaluate(now);
		ensure!(new_expiry_block > now, Error::<T>::ExpiryBlockMustBeInTheFuture);

		let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
		ensure!(pool_info.admin == *admin, BadOrigin);
		ensure!(new_expiry_block > pool_info.expiry_block, Error::<T>::ExpiryCut);

		// Always start by updating the pool rewards.
		let reward_per_token = Self::reward_per_token(&pool_info)?;
		let mut pool_info = Self::update_pool_rewards(&pool_info, reward_per_token)?;

		pool_info.expiry_block = new_expiry_block;
		Pools::<T>::insert(pool_id, pool_info);

		Self::deposit_event(Event::PoolExpiryBlockModified { pool_id, new_expiry_block });

		Ok(())
	}
