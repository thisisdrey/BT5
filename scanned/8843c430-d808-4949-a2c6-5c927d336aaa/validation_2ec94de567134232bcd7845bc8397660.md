### Title
Unbounded slippage in Snowbridge tip/fee swap-and-burn lets a caller receive an arbitrarily reduced Ether credit while still burning the full swap output and paying real value - (File: bridges/snowbridge/pallets/system-frontend/src/lib.rs)

### Summary
`pallet-snowbridge-system-frontend::swap_and_burn` swaps a user-supplied "tip" or "fee" asset for Ether via the generic `Swap` trait, but hardcodes `amount_out_min` to `None`, i.e. it explicitly disables the exact protection mechanism (`ProvidedMinimumNotSufficientForSwap`) that `pallet-asset-conversion` itself provides and enforces on all its own public extrinsics.

### Finding Description
`register_token` and `add_tip` both call `Self::swap_fee_asset_and_burn`, which calls `Self::swap_and_burn`: [1](#0-0) 

The swap is executed with:
```rust
let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
    who.clone(),
    swap_path,
    tip_amount,
    None, // No minimum amount required
    who,
    true,
)?;
``` [2](#0-1) 

This is the exact analog of the external report's core broken invariant: an automated swap that does not enforce any output-value floor, so an attacker (or normal market conditions on a thin/high-fee pool) can cause the swap to return far less Ether than the input's fair value, exactly as `pallet-asset-conversion`'s own guard is designed to prevent: [3](#0-2) 

Because `T::Swap` is the generic `Swap` trait (implemented by `pallet-asset-conversion::Pallet<T>` in production runtimes), `swap_exact_tokens_for_tokens` will happily execute against whatever the pool's current reserves are, no matter how disadvantageous, as long as `amount_out` is non-zero: [4](#0-3) 

The resulting `ether_gained` (whatever residual amount the depleted/imbalanced pool returned) is what gets burned for teleport and reported to BridgeHub as the tip/fee amount that will back the message's relayer reward or execution fee: [5](#0-4) [6](#0-5) 

Existing guards do not stop this path because:
- `do_swap_exact_tokens_for_tokens` only checks `amount_out >= amount_out_min` *when `amount_out_min` is `Some`*; passing `None` deliberately bypasses this the sole slippage check in the pallet.
- There is no additional validation in `system-frontend` (no equivalent of "significantCollateralDrop") comparing `ether_gained` to any oracle/expected value before it is burned and reported onward.
- The caller (an unprivileged, ordinary signed origin via `add_tip`, or any origin satisfying `RegisterTokenOrigin` via `register_token`) fully controls `tip_amount`/`fee_asset`, and cannot be blamed as a "malicious relayer/validator" — this is normal end-user interaction with a public extrinsic.

### Impact Explanation
Since the swap output directly determines the Ether amount reported to BridgeHub as the message's tip/fee (via `EthereumSystemCall::AddTip`/`RegisterToken`'s `amount` field), an unbounded-slippage swap means:
- The relayer reward or execution-fee amount credited on the Ethereum side can be silently and arbitrarily reduced relative to what the user actually paid in, with no on-chain enforcement of a fair minimum.
- In low-liquidity or thinly-traded tip-asset/Ether pools, this can be triggered incidentally (large trade vs. pool depth) or manipulated by the caller structuring pool state (e.g., interacting in the same block via other public calls) to force a bad price, since there is no protection at all (not even a loose one).
- This directly affects Snowbridge's reward/fee accounting integrity — a core "duplicate settlement or payout"/"public underpriced work" concern for bridge delivery flow, because the amount burned/reported does not reliably reflect value actually extracted from the user.

### Likelihood Explanation
High likelihood relative to the original report's scenario: unlike the audited vault contract (which at least used the USD-equivalent value as `amountOutMin`), this code path uses no minimum at all, so the failure mode is strictly worse — it will silently succeed with an unfavorable price rather than reverting. Any signed account can trigger it via the public `add_tip` extrinsic with an arbitrary `asset` whose pool has poor liquidity or a high effective price impact for the traded size.

### Recommendation
Do not pass `None` for `amount_out_min` in `swap_and_burn`. Compute an expected minimum output using `pallet_asset_conversion::QuotePrice::quote_price_exact_tokens_for_tokens` (or an oracle) with a bounded slippage tolerance, and enforce it via `Some(min_out)`, mirroring the check already present in `do_swap_exact_tokens_for_tokens`. Consider also validating that the realized `ether_gained` is not "significantly" below the pre-swap quoted value before proceeding to burn/report it, analogous to the `significantCollateralDrop()` mitigation recommended in the source report.

### Proof of Concept
1. Deploy a runtime with `pallet-snowbridge-system-frontend` configured with `type Swap = pallet_asset_conversion::Pallet<Runtime>`.
2. Create a low-liquidity pool between an arbitrary `tip_asset_location` and the `EthereumLocation` (Ether) asset, e.g. reserves of `10` Ether vs `10` tip-asset units (see pool setup pattern in `swap_should_not_work_if_too_much_slippage` test: [7](#0-6) ).
3. Call `add_tip(message_id, Asset { id: tip_asset_location, fun: Fungible(large_tip_amount) })` where `large_tip_amount` is a large fraction of pool reserves.
4. Observe that `swap_and_burn` executes successfully with `amount_out_min = None`, burning/reporting an `ether_gained` far below the fair-value expectation (e.g., quoted via `quote_price_exact_tokens_for_tokens` before the call), with no error and no on-chain check flagging the disproportionate loss — contrasted with `pallet-asset-conversion`'s own extrinsic `swap_exact_tokens_for_tokens`, which would require the caller to accept this risk explicitly via a chosen `amount_out_min` rather than have it silently disabled by the pallet.

		fn swap_and_burn(
			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether
			let ether_asset = Asset::from((ether_location.clone(), ether_gained));

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}
