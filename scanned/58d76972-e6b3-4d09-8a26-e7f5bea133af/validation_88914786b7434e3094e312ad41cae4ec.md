### Title
Confiscated auction bids for a duplicated para lease have no user-facing withdrawal path - ([File: polkadot/runtime/common/src/auctions/mod.rs])

### Summary
In `Pallet::manage_auction_end`, when a winning bidder's lease request collides with an existing lease for the same para (`LeaseError::AlreadyLeased`), the pallet re-reserves the bidder's funds and emits `Event::ReserveConfiscated`, but provides **no dispatchable call** for the bidder (or anyone) to reclaim those funds. This mirrors the NMKT report's core invariant break: a legitimate value-holder becomes permanently unable to withdraw an amount they are entitled to because of a downstream ownership/state collision that the withdrawal logic never accounts for.

### Finding Description
`handle_bid` reserves a bidder's funds when they place/raise a winning bid [1](#0-0) . When the auction ends, `manage_auction_end` first unreserves **all** amounts held in `ReservedAmounts`, then attempts to call `T::Leaser::lease_out` for each computed winner to actually grant the lease and re-reserve the deposit [2](#0-1) .

If `lease_out` returns `LeaseError::AlreadyLeased` (the leaser/para pair already has an active lease for the requested period), the code explicitly re-reserves the bid amount from the account and emits `ReserveConfiscated`, with the comment "Let's keep the amount reserved and let governance sort it out": [3](#0-2) 

The `AuctionClosed` event is then emitted and the auction state is fully cleared [4](#0-3) . At this point, `AuctionInfo` and `Winning` are gone, `ReservedAmounts` no longer tracks this confiscated deposit (it's a plain `reserve()` call outside of `ReservedAmounts`), and no other pallet call (`bid`, `new_auction`, `cancel_auction`) reads or unreserves this balance. The funds sit reserved on the account indefinitely with no defined governance call in this pallet to release them — the comment names "governance" as the remedy but no such extrinsic exists in the `auctions` pallet to complete that promise for this specific case.

This is directly analogous to the NMKT-7 report: a user's bid/deposit becomes permanently stuck because a *state condition unrelated to fraud* (already holding/owning the resource being bid on) causes the withdrawal/refund path to be skipped, with the system relying on an undocumented, unimplemented-in-this-pallet manual process to fix it.

### Impact Explanation
Any account that legitimately wins overlapping/renewal auction ranges for a para they already lease (e.g., a renewal bid scenario, or a bidder who wins two overlapping sample ranges resolving to the same para/lease-period combination through `calculate_winners`) can have their reserved bid balance permanently locked with no path to reclaim it through the `auctions` or `slots` pallet extrinsics. This is a permanent user-fund lock, which is one of the explicitly in-scope impact categories (permanent user-fund lock).

### Likelihood Explanation
This does not require a malicious peer, validator, collator, or governance actor — it can be triggered purely by ordinary bidding behavior during the auction's ending period combined with the `calculate_winners` dynamic-programming selection, which can select overlapping ranges whose underlying `lease_out` call collides for the same para. The pallet's own comment acknowledges the possibility ("possibly griefing us") but doesn't distinguish malicious griefing from an innocent renewal/overlap collision, and does not implement any recovery mechanism regardless of intent.

### Recommendation
Track confiscated amounts in a dedicated storage item (e.g., `ConfiscatedDeposits: StorageMap<(AccountId, ParaId), Balance>`) at the point `ReserveConfiscated` is emitted, and expose a governed or permissionless extrinsic to resolve/release these funds (e.g., a root-only `resolve_confiscation` call, or an automatic requeue/refund if the collision is detected to be non-malicious, such as the leaser already owning the exact same para lease). At minimum, document precisely which call and origin is expected to "let governance sort it out," since none currently exists in this pallet.

### Proof of Concept
1. Start an auction with `Auctions::new_auction`.
2. Account `A` already holds an active lease for `para` covering lease periods `[p, p+k]` for a prior auction/`force_lease`.
3. During the new auction, `A` bids on `para` for an overlapping/renewal range such that `calculate_winners` selects `A` as a winner for a range whose `lease_out` call collides with the existing lease (`LeaseError::AlreadyLeased`), while `A`'s deposit for this new bid is not already covered by `existing_lease_deposit` (e.g., a slightly larger bid amount).
4. On auction end, `manage_auction_end` runs; `T::Leaser::lease_out` returns `AlreadyLeased`; the code re-reserves `amount` on `A` and emits `ReserveConfiscated { para_id: para, leaser: A, amount }` [3](#0-2) .
5. Inspect the pallet's dispatchables (`new_auction`, `bid`, `cancel_auction`) and confirm none reference or release this reserved amount [5](#0-4) ; the funds remain reserved on `A`'s account with no code path in the repository to release them.
