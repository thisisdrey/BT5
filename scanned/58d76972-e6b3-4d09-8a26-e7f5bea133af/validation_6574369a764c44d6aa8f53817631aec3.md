## Analog Found: Missing halt-state guard in Snowbridge Outbound Queue V2 `deliver()` [1](#0-0) 

### Title
Missing operating-mode/halt check on `snowbridge-pallet-outbound-queue-v2::deliver()` allows continued message enqueuing during bridge emergency halt - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/send_message_impl.rs`)

### Summary
The V1 Snowbridge outbound queue enforces a halt check before accepting new messages for delivery to Ethereum, but the V2 outbound queue pallet has no equivalent guard at all — not even a storage item to hold an operating mode, nor a `set_operating_mode` extrinsic. This is the same bug class as the reported `bridgeMessage()`/`bridgeMessageWETH()` issue: a state-changing public entrypoint that is supposed to be paused during an emergency/halt but is missing the guard.

### Finding Description
`pallet_bridge_messages`, `pallet_bridge_grandpa`, `pallet_bridge_parachains`, the beacon light client (`snowbridge-pallet-ethereum-client`), `snowbridge-pallet-inbound-queue`, and `snowbridge-pallet-outbound-queue` (v1) all implement a halt/`OperatingMode` mechanism that must be checked before performing state-changing bridge operations:

- V1 outbound queue explicitly checks the halt flag before enqueuing a new message for non-governance channels: [2](#0-1) 

- Inbound queue v2 checks it at the top of `submit`: [3](#0-2) 

- The ethereum-client verifier now halts proof verification (fixed by `pr_11856`), which protects `submit_delivery_receipt` in outbound-queue-v2 indirectly: [4](#0-3) 

However, `outbound-queue-v2`'s `SendMessage::deliver` implementation — the function responsible for accepting and enqueuing new outbound messages (analogous to `bridgeMessage()`/`bridgeMessageWETH()`) — has no halt/operating-mode check whatsoever: [5](#0-4) 

A grep of the whole `outbound-queue-v2` pallet confirms there is no `OperatingMode` storage item and no `set_operating_mode` call — the `Halted` error variant and `OperatingModeChanged` event are declared in the pallet's `Error`/`Event` enums but are dead code, never emitted or checked: [6](#0-5) [7](#0-6) 

So while governance can halt the beacon light-client (blocking proof verification and delivery-receipt reward payout) or halt inbound-queue-v2, there is no mechanism at all to stop new outbound messages from being validated, enqueued, assigned a `PendingOrder` with a fee, and committed to the Merkle root by `outbound-queue-v2`. This breaks the "message queues, bridge markers, receipts, and payout state must only advance after ... settlement succeed atomically" and emergency-pause invariants that every other Snowbridge/bridge pallet in this repo enforces.

### Impact Explanation
During an active security incident (e.g. the beacon light client is halted because a sync-committee compromise is suspected, per `pr_11856`), governance has no way to stop new messages from being accepted into `outbound-queue-v2` and committed for relaying to Ethereum. New `PendingOrder`s with attached fees continue to be created via `do_process_message`, continuing normal chain operation and fee accrual/exposure even though the bridge is supposed to be in emergency stop. This is consistent with "public underpriced work that degrades block production or stalls bridge processing" / "duplicate settlement or payout" risk categories, since outbound processing keeps running unchecked while the rest of the bridge (verification side) is halted, and there is no governance lever to stop it.

### Likelihood Explanation
This requires no privileged actor, malicious relayer, or governance abuse — it is simply the absence of a control that exists everywhere else in the codebase for the analogous v1 pallet and the analogous inbound-queue-v2 pallet. Any sibling parachain or the `snowbridge-pallet-system-v2` can call `validate`/`deliver` normally; the gap only manifests when governance needs to halt v2 outbound processing and discovers there is no such capability, unlike every comparable pallet.

### Recommendation
Add an `OperatingMode` storage item and `set_operating_mode` extrinsic to `snowbridge-pallet-outbound-queue-v2` (mirroring `inbound-queue-v2` and v1 `outbound-queue`), and add a halt check (`ensure!(!Self::operating_mode().is_halted(), SendError::Halted)`) in `send_message_impl.rs::deliver` (and/or in `do_process_message`), consistent with how v1 guards non-governance channel messages.

### Proof of Concept
1. Governance halts the beacon light client (`EthereumBeaconClient::set_operating_mode(Halted)`) after detecting a compromise, per the intended flow in `pr_11856`.
2. A sibling parachain or `snowbridge-pallet-system-v2` continues to call `OutboundQueue::validate` / `OutboundQueue::deliver` for new v2 messages.
3. `deliver()` in `bridges/snowbridge/pallets/outbound-queue-v2/src/send_message_impl.rs` performs no halt check, so the message is unconditionally enqueued via `T::MessageQueue::enqueue_message`.
4. `do_process_message` in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` runs normally, creating a new `PendingOrder` with a fee and committing the message to the Merkle root — despite the bridge being in emergency halt, with no governance call available to stop this pallet specifically.

where
	T: Config,
{
	type Ticket = Message;

	fn validate(message: &Message) -> Result<Self::Ticket, SendError> {
		// The inner payload should not be too large
		let payload = message.encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		Ok(message.clone())
	}

	fn deliver(ticket: Self::Ticket) -> Result<H256, SendError> {
		let origin = ticket.origin.into();

		let message =
			BoundedVec::try_from(ticket.encode()).map_err(|_| SendError::MessageTooLarge)?;

		T::MessageQueue::enqueue_message(message.as_bounded_slice(), origin);
		Self::deposit_event(Event::MessageQueued { message: ticket.clone() });
		Ok(ticket.id)
	}
