## Analysis

The external report's core broken invariant: **an admin-only batch operation iterates a user-controlled, unbounded array whose size can be cheaply inflated by an attacker, causing the operation to run out of gas/weight and become permanently unusable.**

The strongest local analog is not the `pallet-crowdloan` `refund()` (already fixed with `RemoveKeysLimit` batching, `polkadot/runtime/common/src/crowdloan/mod.rs:507-550`), nor `pallet-elections-phragmen`'s `do_phragmen` (already guarded with an explicit `MaxVoters` early-exit, `substrate/frame/elections-phragmen/src/lib.rs:976-993`). Both of those pallets already anticipated and mitigated this exact bug class.

`pallet-society`'s bid/intake mechanism reproduces the same broken invariant and is **not** bounded or weight-metered proportionally.

### Title
Unbounded, flat-weight iteration of the permissionless `Bids` queue in `pallet-society::select_new_candidates` allows cheap DoS of block-level intake processing - (File: `substrate/frame/society/src/lib.rs`)

### Summary
Any signed account can call the public `bid()` extrinsic to push an entry into the `Bids` storage vector [1](#0-0) . Every rotation period, `on_initialize` unconditionally calls `rotate_intake`, which calls `select_new_candidates`, which does a full linear `retain` scan over the entire `Bids` vector [2](#0-1) . The weight charged for this work in `on_initialize` is a **fixed heuristic** (`weights.max_block / 20`), independent of the actual number of bids being processed [3](#0-2) .

### Finding Description
- `bid()` is a `Signed` origin (unprivileged) dispatchable that reserves `candidate_deposit` and appends to the `Bids` vector with no cap on total queue length enforced in the visible insertion path [4](#0-3) .
- `rotate_intake`, invoked automatically and unconditionally from `on_initialize` at every intake period boundary (no admin trigger, no permission check), calls `Self::select_new_candidates(round_count, member_count, pot)` [5](#0-4) .
- `select_new_candidates` retrieves the *entire* `Bids` vector and runs `bids.retain(...)` over it — `retain` visits every element regardless of how many are ultimately selected (`max_selections` only bounds acceptance, not iteration) [6](#0-5) .
- Crucially, the weight accounted for this in `on_initialize` is `weights.max_block / 20`, a constant fraction of the block weight limit, **not** a function of `Bids.len()` [7](#0-6) . This is exactly the flaw described in the external report: an admin/automatic batch loop over a user-populated array with weight accounting that does not scale with the true iteration cost.

### Impact Explanation
Because the deposit is *reserved, not burned*, an attacker can create many bid entries cheaply (paying only the opportunity cost of a lockup, refundable via `unbid()`), inflating `Bids` to a size where a single `retain` pass at intake time exceeds the flat weight budgeted for it. Since this logic runs inside `on_initialize` for every block that crosses an intake boundary, this can push actual execution time past the declared/charged weight, degrading or stalling block production for the runtime that includes `pallet-society` — matching the "public underpriced work that degrades block production" impact category.

### Likelihood Explanation
The precondition is only a signed account and enough balance to cover `candidate_deposit` per bid (refundable via `unbid`), with no root/governance/admin interaction required — the same "malicious user invests trivial amount across many addresses" primitive from the source report. The trigger (`on_initialize`) is automatic and cannot be paused by users once the queue is inflated.

### Recommendation
- Bound `Bids` with a `BoundedVec<..., T::MaxBids>` and reject `bid()` once the cap is reached, or
- Charge `on_initialize`/`rotate_intake` weight proportionally to `Bids::decode_len()` (similar to how `elections-phragmen::do_phragmen` bounds/early-exits on `MaxVoters`), and
- Process `select_new_candidates` in bounded batches across multiple blocks rather than a single unbounded `retain` pass.

### Proof of Concept
1. Attacker controls N funded accounts, each calls `Society::bid(origin, value)` with the minimum `candidate_deposit`, growing `Bids` to N entries — no per-account or global cap prevents this [1](#0-0) .
2. At the next intake boundary, `on_initialize` calls `rotate_intake` → `select_new_candidates`, which performs `Bids::<T,I>::get()` then `bids.retain(...)` over all N entries [8](#0-7) .
3. The weight charged for this entire step is fixed at `max_block / 20` regardless of N [7](#0-6) , so for sufficiently large N the actual computation time exceeds the weight accounted, degrading block production.

**Uncertainty**: I could not confirm from the available index whether a `MaxBids`-style bound exists elsewhere in `Config` (e.g. enforced at a different call site not captured in this scan) that would cap `Bids.len()`; the grep search for `MaxBids` returned no clear declaration in the pallet's config trait within the indexed content. If such a bound exists in code not surfaced by the index, this weakens the finding. A full-repo Devin session (with complete file access beyond the index) would be needed to verify the `Config` trait for `pallet_society` and the exact declaration of `pub type Bids<T, I>` to conclusively confirm the absence of any cap.

	fn rotate_intake(rng: &mut impl RngCore) {
		// We assume there's at least one member or this logic won't work.
		let member_count = MemberCount::<T, I>::get();
		if member_count < 1 {
			return;
		}
		let maybe_head = NextHead::<T, I>::take();
		if let Some(head) = maybe_head {
			Head::<T, I>::put(&head.who);
		}

		// Bump the pot by at most `PeriodSpend`, but less if there's not very much left in our
		// account.
		let mut pot = Pot::<T, I>::get();
		let unaccounted = T::Currency::free_balance(&Self::account_id()).saturating_sub(pot);
		pot.saturating_accrue(T::PeriodSpend::get().min(unaccounted / 2u8.into()));
		Pot::<T, I>::put(&pot);

		// Bump round and create the new intake.
		let mut round_count = RoundCount::<T, I>::get();
		round_count.saturating_inc();
		let candidate_count = Self::select_new_candidates(round_count, member_count, pot);
		if candidate_count > 0 {
			// Select a member at random and make them the skeptic for this round.
			let skeptic = Self::pick_member(rng).expect("exited if members empty; qed");
			Skeptic::<T, I>::put(skeptic);
		}
		RoundCount::<T, I>::put(round_count);
	}

	pub fn select_new_candidates(
		round: RoundIndex,
		member_count: u32,
		pot: BalanceOf<T, I>,
	) -> u32 {
		// Get the number of left-most bidders whose bids add up to less than `pot`.
		let mut bids = Bids::<T, I>::get();
		let params = match Parameters::<T, I>::get() {
			Some(params) => params,
			None => return 0,
		};
		let max_selections: u32 = params
			.max_intake
			.min(params.max_members.saturating_sub(member_count))
			.min(bids.len() as u32);

		let mut selections = 0;
		// A running total of the cost to onboard these bids
		let mut total_cost: BalanceOf<T, I> = Zero::zero();

		bids.retain(|bid| {
			// We only accept a zero bid as the first selection.
			total_cost.saturating_accrue(bid.value);
			let accept = selections < max_selections &&
				(!bid.value.is_zero() || selections == 0) &&
				total_cost <= pot;
			if accept {
				let candidacy = Candidacy {
					round,
					kind: bid.kind.clone(),
					bid: bid.value,
					tally: Default::default(),
					skeptic_struck: false,
				};
				Candidates::<T, I>::insert(&bid.who, candidacy);
				selections.saturating_inc();
			}
			!accept
		});

		// No need to reset Bids if we're not taking anything.
		Bids::<T, I>::put(&bids);
		selections
	}
