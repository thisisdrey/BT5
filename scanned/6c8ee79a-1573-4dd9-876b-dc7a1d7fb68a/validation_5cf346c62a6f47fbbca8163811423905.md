## Title
`pallet-assets::approve_transfer` uses additive (not set) semantics, allowing a delegate's spend allowance to silently exceed the owner's intended cap - (File: substrate/frame/assets/src/functions.rs)

## Summary
`Pallet::do_approve_transfer` (called from the public `approve_transfer` extrinsic) accrues the requested `amount` onto any existing `Approvals` entry via `approved.amount.saturating_add(amount)` rather than setting it to the caller-supplied value. [1](#0-0)  This is functionally the same broken invariant as the Teller `updateCommitment` bug: the owner believes each call defines "the maximum a delegate may spend," but the pallet instead accumulates across calls, so a benign resubmission (e.g., to top up a deposit, adjust after a partial revoke, or simply re-issue an approval with a fresh value) can leave the delegate able to pull far more than the owner most recently authorized.

## Finding Description
The dispatchable `approve_transfer` is fully public/unprivileged and documents itself as setting an authorized spend cap for `delegate`: "the amount of asset that may be transferred by delegate." [2](#0-1)  Internally, however, the implementation does not overwrite `approved.amount`; it always adds the newly supplied `amount` to whatever is already on record:
- `let approved = maybe_approved.take().unwrap_or_default()` when an entry already exists it is reused, not replaced.
- `approved.amount = approved.amount.saturating_add(amount);` [3](#0-2) 

This means two successive `approve_transfer(delegate, X)` calls by the same owner leave the delegate authorized for `2*X`, not `X`. There is no guard comparing the new value against the current value, and no way for the owner to specify "set" semantics through the public dispatchable — `cancel_approval` must be called first to reset to zero, and there is no atomic "set-to-value" call.

Contrast this with the `pallet-assets` **precompile** layer (`substrate/frame/assets/precompiles/src/lib.rs`), which explicitly works around this by canceling any non-zero existing approval before calling `do_approve_transfer` again, precisely to avoid additive semantics and match ERC-20 "set" behavior. [4](#0-3)  That workaround exists in the precompile shim but the underlying pallet extrinsic `approve_transfer` itself still exposes the additive/accumulating behavior directly to any signed caller, and any code (or other pallet/precompile) that calls `do_approve_transfer` or `approve_transfer` without first canceling will silently compound allowances.

This is the same root defect as the Teller `updateCommitment` report: a public "update authorization" entrypoint that is supposed to define a maximum but instead compounds on top of previously granted (and potentially already-partially-consumed) state, without any bookkeeping of "amount already allocated / already used" versus "amount currently re-authorized." No malicious peer, validator, collator, or front-running condition is required — the bug manifests purely from an owner or any authorized caller invoking the same public extrinsic twice with the intention of resetting/adjusting the allowance, and it also can be weaponized: an owner who calls `approve_transfer` a second time believing they are lowering/resetting the delegate's cap (e.g. from 100 to 10) instead ends up granting the delegate 110, entirely because of an implementation detail contradicting the plain reading of the parameter and the amount previously already spent by `transfer_approved` not being reconciled against the new intended cap.

## Impact Explanation
An owner can be tricked (or can mistakenly believe, since nothing in the API signature indicates non-set semantics beyond a doc comment) into granting a delegate a spend allowance far larger than intended, leading to unauthorized/unbacked-by-intent asset transfers out of the owner's account via `transfer_approved`. This falls under "theft or unbacked mint or unlock" / "unauthorized execution" impact classes for assets pallets, since the delegate is able to move more of the owner's `pallet-assets` balance than the owner most recently authorized, purely due to how the public entrypoint accumulates state instead of setting it.

## Likelihood Explanation
Likelihood is moderate: it requires the owner (or any code path built on top of `do_approve_transfer`, such as a wallet, DApp, or other pallet) to call `approve_transfer` more than once for the same `(asset, owner, delegate)` triple without first canceling — a very common operational pattern (e.g., "increase my approval," "re-approve after partial use," or naive UI code that always calls approve with the desired new cap). No coordination with a malicious third party, validator, or front-running is needed; the owner's own second call is sufficient to trigger the miscalculation.

## Recommendation
Change `do_approve_transfer` to either (a) set `approved.amount = amount` (true "set" semantics, matching the precompile's cancel-then-approve workaround and standard ERC-20 `approve` behavior), or (b) explicitly rename/document the extrinsic as "increase approval" and add a companion `set_approval`/`decrease_approval` that lets the owner define an absolute cap atomically, consistent with the `increaseApproval`-style remediation recommended in the original Teller report. Any fix must ensure the new cap accounts for the amount already consumed by `delegate` via `transfer_approved`, so a lowered cap cannot be bypassed by outstanding usage.

## Proof of Concept
1. Owner mints/holds `Assets` balance and calls `approve_transfer(asset_id, delegate, 100)`. `Approvals::(asset_id, owner, delegate).amount == 100`.
2. Owner later calls `approve_transfer(asset_id, delegate, 10)` intending to reduce the delegate's authorized spend to `10` (e.g., after deciding to scale back trust in `delegate`).
3. Because of `approved.amount.saturating_add(amount)` in `do_approve_transfer` [5](#0-4) , the stored allowance becomes `110`, not `10`.
4. `delegate` calls `transfer_approved(asset_id, owner, dest, 110)` via `do_transfer_approved`, which succeeds because `Approvals` records `110`, moving assets far beyond the owner's most recently intended cap. [6](#0-5)
