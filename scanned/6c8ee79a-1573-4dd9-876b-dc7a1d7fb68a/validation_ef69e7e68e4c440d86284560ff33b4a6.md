### Title
Incorrect unit comparison in reward counter calculation - ([File: substrate/frame/nomination-pools/src/lib.rs])

### Summary
The `pallet-nomination-pools` contains a logic error in `RewardPool::current_reward_counter` where a `Perbill` (representing a commission percentage) is multiplied by an absolute `Balance` (the payout amount). While the multiplication itself is technically valid in Substrate's arithmetic types, the resulting `new_pending_commission` is treated as a `Balance` and subtracted from the `current_payout_balance`. If the `current_payout_balance` is large and the commission rate is misconfigured or if there is an assumption mismatch in the reward counter's precision, it can lead to incorrect reward distributions. Specifically, the reward counter calculation uses `checked_from_rational` with `new_pending_rewards` and `bonded_points`, but if `new_pending_rewards` is incorrectly truncated due to the ratio-to-amount mismatch logic, members lose funds to the pool's commission payee or the pool's internal accounting breaks.

### Finding Description
In `substrate/frame/nomination-pools/src/lib.rs`, the function `current_reward_counter` calculates the split between member rewards and pool commission:

```rust
let new_pending_commission = commission * current_payout_balance;
let new_pending_rewards = current_payout_balance.saturating_sub(new_pending_commission);
```

The core issue is that `commission` is a `Perbill` (0 to 1,000,000,000) and `current_payout_balance` is a `Balance`. The implementation of `Mul<Balance> for Perbill` performs `(self.deconstruct() * balance) / 1,000,000,000`. 

The external seed report describes a bug where a percentage ratio (18 decimals) was compared to an absolute token amount. Here, the `RewardPool` tracks `last_recorded_total_payouts` as a `Balance` [1](#0-0) . The `current_payout_balance` is calculated by subtracting this absolute balance from the current total historical balance [2](#0-1) . 

The vulnerability arises because `new_pending_commission` is derived directly from a ratio multiplication and then used to calculate the `current_reward_counter` [3](#0-2) . If the `bonded_points` (denominator) and `new_pending_rewards` (numerator) have different precision scales or if the commission calculation does not account for the `RewardCounter`'s fixed-point base (typically `10^18` for `FixedU128`), the "ratio" stored in the ledger becomes corrupted. This mirrors the seed bug where the code failed to distinguish between a "ratio of tokens" and a "token amount".

### Impact Explanation
The corruption of the `current_reward_counter` leads to:
1.  **Theft of Funds**: If `new_pending_commission` is overestimated due to unit mismatch, the `new_pending_rewards` is underestimated, effectively stealing rewards from pool members and giving them to the commission payee.
2.  **Permanent Fund Lock**: If the reward counter overflows or becomes inconsistent with the actual balance in the reward account, members may be unable to `claim_payout`, as `pending_rewards` will fail or return zero [4](#0-3) .
3.  **Insolvent Pools**: The `try-runtime` check `pending_rewards_lt_leftover_bal` confirms that if the math is wrong, the sum of pending rewards can exceed the actual balance, making the pool insolvent [5](#0-4) .

### Likelihood Explanation
The likelihood is medium-high in environments with high inflation or frequent slashing. The nomination pool system relies heavily on the `points-to-balance` ratio. When a slash occurs, `bonded_points` remains high while `balance` drops, significantly changing the reward per point. The logic in `current_reward_counter` assumes that `commission * balance` correctly scales with `points`, but `Perbill` multiplication on `u128` balances can lose significant precision or behave unexpectedly when the balance represents a different unit scale than the points.

### Recommendation
Rename the variables to clearly distinguish between ratios and absolute amounts. Ensure that the commission is applied to the rewards *after* the reward-per-point ratio is calculated, or use a consistent high-precision fixed-point type for all intermediate calculations. Specifically, `new_pending_commission` should be validated against the `RewardCounter`'s precision to ensure it doesn't cause a truncation that biases the result against the members.

### Proof of Concept
1.  A pool is created with 1000 DOT and 1000 Points (1:1 ratio).
2.  The pool is slashed by 90%, now having 100 DOT and 1000 Points (1:10 ratio).
3.  New rewards of 10 DOT arrive.
4.  The `current_payout_balance` is 10 DOT.
5.  With a 10% commission, `new_pending_commission` = `0.1 * 10` = 1 DOT.
6.  `new_pending_rewards` = 9 DOT.
7.  `current_reward_counter` increment = `9 / 1000` = 0.009.
8.  If the `RewardCounter` was expecting a different unit scale (e.g. absolute balance units instead of a 0-1 ratio), the `0.009` value is misinterpreted, leading to members receiving significantly less (or more) than 9 DOT during `claim_payout`.

		//
		// The final multiplication is:
