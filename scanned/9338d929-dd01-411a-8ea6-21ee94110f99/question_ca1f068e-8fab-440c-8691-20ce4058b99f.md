`CachedState::has_public_key` (cached.rs:65-75) returns true if `account.public_keys_added.contains(public_key)` in the CACHED overlay even when the underlying `view.has_public_key` would return false and the account is otherwise locked or nonexistent on-chain. Attacker submits a batch: intent #1 adds a new public key to an account they don't yet own on-chain but which is not yet locked; intent #2 in the SAME batch signs a payload with the just-added key claiming to be `signer_id` for that account. Precondition: account has no prior public key restriction, not locked at time `get_or_create` first caches it. Call sequence: `add_public_key` (cached.rs:132-150) inserts into `public_keys_added`; a later `execute_signed_intent` call within the same `execute_signed_intents` loop verifies `has_public_key` against the cache and succeeds despite the key not existing on the authoritative `view` until `finalize()` commits. Binding: the `(signer_id, public_key)` pair the engine treats as authorised == the pair that was validly added by an already-authorised operation for that exact account BEFORE this intent's signature was produced (temporal ordering), not a key added later in the same still-uncommitted batch used to retroactively authorise itself. Scoped impact: Critical, unauthorised balance change if an attacker can add-then-immediately-use a key for an account whose ownership they don't yet control validly. Proof idea: cargo test building a two-intent batch (add_public_key + a signed transfer using that key) against a fresh account and asserting the transfer is rejected because the key-adding intent itself required the very authorisation it purports to grant.
