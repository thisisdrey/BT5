Target: `Contract::mt_on_transfer` (contracts/defuse/src/contract/tokens/nep245/deposit.rs) `DepositAction::Execute(execute) => { if execute.refund_if_fails { self.execute_intents(execute.execute_intents); } else { ext_intents::ext(...).execute_intents(...).detach(); } }`. Attacker deposits their own NEP-245 token into `intents.near` via `mt_transfer_call` with `msg` = `DepositMessage{receiver_id: victim_or_self, action: Execute(ExecuteIntents{execute_intents: [self_signed_payload_that_withdraws_the_just_deposited_balance], refund_if_fails: false})}`. Preconditions: attacker controls the source MT contract and can make the deposit `amounts` arbitrary since it's their own token. Call sequence: `self.deposit(receiver_id, ..)` credits the ledger balance synchronously inside `mt_on_transfer` BEFORE `ext_intents::execute_intents(...).detach()` fires as a SEPARATE receipt; because it's detached (fire-and-forget, no `.then()` callback checking success), if the nested `execute_intents` panics (e.g. an invalid intent), the deposit that already landed is NOT rolled back, but neither is anything refunded to the original MT contract, since `mt_on_transfer`'s return value `vec![U128(0); token_ids.len()]` tells the source token NOTHING was refunded regardless of whether the nested execute succeeded. Binding: value credited to `receiver_id`'s `token_balances` by `self.deposit(...)` == value the depositor intended to be usable, and REPLAY: since the detached `execute_intents` isn't tied via callback, a duplicate/replayed signed payload inside `execute_intents` there could re-settle. Scoped impact: Critical if the same signed `execute_intents` payload used inside multiple concurrent `mt_on_transfer` deposit `msg`s from the same attacker settles more than once because nonce commit happens per-Engine-instance and each `mt_on_transfer` invocation constructs a fresh `Engine`. Proof: sandbox test sending two concurrent `mt_transfer_call`s each embedding the identical signed `MultiPayload` (same nonce) in their `msg.execute_intents`, and assert only one of the two nested executions succeeds (REPLAY count == 1) while the other fails with `NonceUsed`.
