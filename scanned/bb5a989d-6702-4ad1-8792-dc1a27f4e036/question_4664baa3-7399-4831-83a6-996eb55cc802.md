Target: TokenId identity across Nep141TokenId, Nep171TokenId, Nep245TokenId construction (contracts/defuse/core/src/token_id/*). Attacker action: attacker deploys their own NEP-245 contract at an AccountId string that, when combined with a token_id substring, serializes to the exact same TokenId string representation as an existing valuable Nep141TokenId(real_token) held by other users, by exploiting the TokenId Display/FromStr format's separator characters. Preconditions: attacker controls contract deployment and can choose the MT sub-token_id string freely. Call sequence: attacker deposits 1 unit under their crafted MT (contract, token_id) via mt_on_transfer with msg, receiving a credited token_balances[attacker][TokenId] where TokenId's string collides with an existing token_balances[victim][TokenId::Nep141(real_token)]. Attacker then signs a Transfer intent moving 'that' TokenId from themselves, but the engine resolves it against the colliding entry. Binding: the (contract, token) that TokenId names must equal the asset actually moved -- i.e., TokenId::to_string()/from_str() must be an injective mapping to (standard, contract, sub_id). Scoped impact: Critical - a worthless attacker-controlled MT unit could parse to the same key as a valuable NEP-141 balance, letting the attacker claim value they never deposited. Proof idea: cargo test constructing two TokenId values from different (standard, contract, sub_token_id) tuples and asserting their string encodings are never equal for any attacker-chosen sub_token_id containing separator characters used internally by the TokenId parser.
