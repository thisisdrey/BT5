[Function: StateStoredReceiptMetadata.congestion_gas vs recomputation guard] When config.use_state_stored_receipt is true, congestion_gas is computed once at push time (DelayedReceiptQueueWrapper::push / ReceiptSink::buffer_receipt) and stored verbatim in StateStoredReceiptMetadata; at pop/forward time receipt_congestion_gas just reads that stored value without ever re-validating it against a freshly recomputed value. Can an attacker submit a receipt right before a protocol upgrade that changes total_prepaid_exec_fees' fee table, so the value baked into StateStoredReceiptMetadata.congestion_gas (computed under the old, lower fee table) is smaller than what compute_receipt_congestion_gas would return under the new table, and this stale, too-low value is what gets subtracted from CongestionInfo at pop time -- meaning the shard's real backlog (measured under new fees) was never fully reflected while the receipt sat delayed? Preconditions: funded account, receipt submitted in the chunk immediately preceding a scheduled fee-table protocol upgrade. Sequence: submit receipt at version N (fee table A), let it delay past the version N+1 upgrade (fee table B), pop it. Invariant: metering totality - the congestion accounting must reflect current protocol cost, not a stale snapshot. Impact: systematic under-reporting of real backlog cost across a protocol upgrade boundary, allowing near-free additional throughput and inflating block application time right after upgrades. Proof idea: unit test computing compute_receipt_congestion_gas for the same receipt under two RuntimeConfig fee tables, asserting the values differ, then showing StateStoredReceiptMetadata locks in the stale one for the receipt's whole lifetime in the queue.
