## Title
`get_reserves`/`get_balance` in `pallet-asset-conversion` compute pool reserves from total balance instead of the actually swappable amount, letting swaps/mints be priced against funds the pool cannot deliver - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
This mirrors the Yeti `_getValueOfContract` bug class: an accounting/pricing function reads the *whole* balance of an account instead of the amount actually usable for the operation, so downstream math (LP minting, swap amount-out/amount-in) is computed against a reserve figure that the pool cannot actually pay out, producing a mismatch between promised and deliverable value.

### Finding Description
`Pallet::<T>::get_balance` reads the raw total balance of the pool account for an asset: [1](#0-0) 

This is used unconditionally by `get_reserves` (the core reserve accessor used by `add_liquidity`, `remove_liquidity`, and the swap-amount math): [2](#0-1) 

`do_add_liquidity` and `do_remove_liquidity` use these `reserve1`/`reserve2` values directly to compute LP token amounts (`side1`/`side2`) and withdrawal amounts (`amount1`/`amount2`): [3](#0-2) [4](#0-3) 

The repository's own `prdoc` history confirms this exact "whole balance vs. usable balance" tension was already fought over twice in this code path: `pr_12408` deliberately switched reserve reads from `reducible_balance` to full balance (to avoid *understating* reserves from held/frozen non-sufficient assets): [5](#0-4) 

...while a later fix, `pr_11761`, had to specifically patch only the two view-function quoters (`quote_price_exact_tokens_for_tokens`, `quote_price_tokens_for_exact_tokens`) to cap their output against `reducible_balance(Preserve, Polite)` because swap execution withdraws with `Preserve`: [6](#0-5) [7](#0-6) [8](#0-7) 

Critically, that `pr_11761` fix only patched the two *quote* view functions. `get_reserves`/`get_balance`, which back `add_liquidity`, `remove_liquidity`, and the actual swap execution math (`get_amount_out`/`get_amount_in` via `balance_path_from_amount_in`/`balance_path_from_amount_out`), still reads the unguarded total balance: [9](#0-8) 

The actual withdraw path (`Self::withdraw`) does check `reducible_balance` under `Preserve`, but only at the very end, per-hop, per-asset — it is not consulted when computing `reserve1/reserve2` or when computing `side1/side2` for LP-minting math, and it is not consulted for `remove_liquidity`'s reserve-based redemption math at all (that uses `Expendable` withdraw with no equivalent guard on `reserve1_left`/`reserve2_left` against the ED-preserving usable balance): [10](#0-9) [11](#0-10) 

### Impact Explanation
Because `get_reserves` reports the pool's *total* balance (including amounts effectively locked by ED/`Preserve` semantics, or by any non-sufficient/held asset accounting), any liquidity provider or swapper who can create a state where the pool's on-chain balance differs from what is actually withdrawable will get LP token mint ratios, swap `amount_out` predictions, and remove-liquidity redemption amounts computed off an inflated (or at least uncontrolled) reserve number. This is the direct analog of Yeti: the check uses the whole balance instead of the delta/usable amount, so downstream commitments (LP shares issued, tokens promised in a swap, tokens redeemed on liquidity removal) can exceed what the pool can actually pay, causing under/over-crediting of LP shares relative to real backing and potential failed or inconsistent settlement between "reserves used for pricing" and "reserves actually deliverable."

### Likelihood Explanation
This is reachable entirely through the public, unprivileged `add_liquidity`, `remove_liquidity`, `swap_exact_tokens_for_tokens`, and `swap_tokens_for_exact_tokens` extrinsics — no admin, governance, relayer, or validator involvement is required. The fact that maintainers already had to patch the quote functions specifically because "swap execution withdraws from pools with `Preserve`... the quote functions did not account for this" (`pr_11761`) is direct in-repo evidence that the reserve-computation function is still out of sync with the actual withdrawal constraints for the paths that were not patched (`add_liquidity`, `remove_liquidity`, actual swap execution's `get_amount_out`/`get_amount_in`).

### Recommendation
Apply the same `reducible_balance(Preserve/Expendable matching the actual withdraw call, Polite)` correction used in `pr_11761`'s quote fix directly inside `get_reserves`/`get_balance` (or at each call site that feeds LP-mint and redemption math), so that reserve figures used for pricing, minting, and redemption always match the actually withdrawable balance under the same preservation mode used by the corresponding withdraw call in `do_add_liquidity`, `do_remove_liquidity`, and `swap`.

### Proof of Concept
Not independently reproducible from the index alone (no full test harness state was inspected for a concrete held/frozen-asset repro), but the existing regression test `post_dispatch_ok_when_pool_asset_dusted_post_withdraw` and `quote_price_returns_none_swap_fails` in `substrate/frame/asset-conversion/src/tests.rs` demonstrate the underlying mechanism (pool's nominal/`total_balance` reserve figure diverging from its `reducible_balance`/withdrawable amount) that the unfixed `get_reserves` call sites (`add_liquidity`/`remove_liquidity`/actual swap execution) do not guard against: [12](#0-11)

		pub(crate) fn balance_path_from_amount_out(
			amount_out: T::Balance,
			path: Vec<T::AssetKind>,
		) -> Result<BalancePath<T>, DispatchError> {
			let mut balance_path: BalancePath<T> = Vec::with_capacity(path.len());
			let mut amount_in: T::Balance = amount_out;

			let mut iter = path.into_iter().rev().peekable();
			while let Some(asset2) = iter.next() {
				let asset1 = match iter.peek() {
					Some(a) => a,
					None => {
						balance_path.push((asset2, amount_in));
						break;
					},
				};
				let fee = Self::pool_fee_for(asset1, &asset2)?;
				let (reserve_in, reserve_out) = Self::get_reserves(asset1.clone(), asset2.clone())?;
				balance_path.push((asset2, amount_in));
				amount_in = Self::get_amount_in(fee, &amount_in, &reserve_in, &reserve_out)?;
			}
			balance_path.reverse();

			Ok(balance_path)
		}

		pub fn get_reserves(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
		) -> Result<(T::Balance, T::Balance), Error<T>> {
			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;

			let balance1 = Self::get_balance(&pool_account, asset1);
			let balance2 = Self::get_balance(&pool_account, asset2);

			if balance1.is_zero() || balance2.is_zero() {
				Err(Error::<T>::PoolEmpty)?;
			}

			Ok((balance1, balance2))
		}
