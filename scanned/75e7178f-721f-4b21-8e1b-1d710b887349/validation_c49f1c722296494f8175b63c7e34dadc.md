## Title
Reward ledger entry is deleted on successful XCM *send*, not on confirmed settlement — relayer reward can be irrecoverably lost/trapped when the cross-chain deposit fails - (File: `bridges/modules/relayers/src/lib.rs`)

## Summary
The external report's core broken invariant is: a value-transfer is treated as "settled" and downstream state is advanced (releasing collateral rights / marking the loan repaid) as soon as the transfer call returns, even though the recipient can make that call *appear* to fail/succeed without the value actually being usably received — causing the payer to permanently lose access to the funds/right they thought they exercised. The local analog is `pallet-bridge-relayers`' `claim_rewards_to`/`claim_rewards` flow: the reward ledger entry is irreversibly deleted the moment `PaymentProcedure::pay_reward` returns `Ok(())`, but for the Snowbridge reward path that `Ok(())` only means "the XCM instructing AssetHub to deposit the reward was successfully *sent*", not that the deposit actually succeeded on AssetHub. If the remote `DepositAsset` traps (e.g., beneficiary lacks the asset-specific existential deposit, or the location cannot receive the asset), the reward is permanently lost with no retry path — mirroring the ERC777 pattern of "state assumes settlement succeeded when only the attempt succeeded."

## Finding Description
`do_claim_rewards` removes the reward atomically with the call to `pay_reward`: [1](#0-0) 

Crucially, `maybe_reward.take()` happens *inside* the `try_mutate_exists` closure and is only rolled back if `pay_reward` itself returns an `Err`. For the Snowbridge reward kind, `pay_reward` is `PayAccountOnLocation::pay_reward`: [2](#0-1) 

This function builds an XCM containing `ReserveAssetDeposited` + `DepositAsset { beneficiary, .. }`, and returns `Ok(())` as soon as `XcmSender::deliver(ticket)` succeeds — i.e., once the message is *queued for delivery to AssetHub*, not once the `DepositAsset` instruction has actually executed and settled funds into the beneficiary account. The `RewardPaid` event is emitted and the ledger entry is gone at this point: [3](#0-2) 

If the remote `DepositAsset` later fails on AssetHub (beneficiary account has no existential deposit for the ETH-derived foreign asset, or the beneficiary `Location` cannot legally hold assets, etc.), the assets are trapped under the `UniversalOrigin(GlobalConsensus(Ethereum))` origin used in the XCM — not under an origin the relayer or a normal user can present to `ClaimAssets`. The relayer's ledger entry, however, has already been deleted, so there is no `NoRewardForRelayer`-guarded retry, no `Failed`/`Attempted` intermediate state, and no way to re-claim.

Contrast this with `pallet-treasury`, which handles exactly this async-settlement problem correctly: `payout` stores `PaymentState::Attempted { id }` and requires a later `check_status` call against `T::Paymaster::check_payment(id)` before the spend is ever removed from storage; on failure it transitions to `PaymentState::Failed` and can be retried: [4](#0-3) [5](#0-4) 

`pallet-bridge-relayers`' `PaymentProcedure` trait has no equivalent "in-flight" / "check status" concept — `pay_reward` is a single boolean-ish `Result<(), Error>` that is asserted to mean final settlement, but for the XCM-routed Snowbridge implementation it only asserts successful dispatch.

## Impact Explanation
This breaks the invariant that "payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." A relayer's earned reward can be permanently and unrecoverably lost/trapped in a way that mirrors the reported bug: the on-chain ledger (`RelayerRewards`) says the reward was paid and removes the claim right, while the actual value transfer to the beneficiary can silently fail downstream. This is a genuine fund-loss/fund-lock defect against the relayer that runs the extrinsic — a normal, non-malicious, non-privileged account — with no admin/governance/relayer-collusion assumption required, matching the "permanent user-fund or bridge-state lock" and "duplicate settlement or payout" impact categories in scope.

## Likelihood Explanation
No adversarial cooperation is needed: any relayer picking (or the runtime picking on their behalf via `prepare_rewards_account`) an `AssetHubLocation` beneficiary that does not already hold the destination foreign asset's existential deposit, or any transient AssetHub-side congestion/filter that traps the `DepositAsset`, triggers this path. The existing test suite even had to special-case funding beneficiaries above `ETHER_MIN_BALANCE` to avoid tripping this exact failure mode, indicating the underlying fragility is already known to be reachable in normal use: [6](#0-5) 

## Recommendation
Do not delete the `RelayerRewards` entry (or otherwise finalize payout state) on `pay_reward`'s `Ok(())` alone when the underlying procedure is asynchronous/XCM-routed. Adopt the treasury pallet's pattern: introduce an "attempted" intermediate state keyed by a payment id, and only clear the ledger entry after a `check_status`-style confirmation of remote execution, with the ability to revert to a retryable/failed state (and give the relayer a path to reclaim/redirect) if the remote deposit traps.

## Proof of Concept
1. A relayer accumulates a Snowbridge reward via `register_reward` (as in `bridges/modules/relayers/src/lib.rs`).
2. The relayer calls `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(some_location))` where `some_location` decodes to an account that has no existential deposit for the bridged asset on AssetHub (a very ordinary, non-malicious condition — e.g. a fresh account, or a location whose account-conversion doesn't map to a pre-funded account).
3. `do_claim_rewards` calls `PayAccountOnLocation::pay_reward`, which successfully builds and `deliver`s the XCM (`Ok(())`), so `RelayerRewards` is unconditionally cleared and `RewardPaid` is emitted.
4. On AssetHub, the `DepositAsset` instruction in the delivered XCM fails to credit the account (ED not met / cannot receive asset) and the assets are trapped under the Ethereum `UniversalOrigin`, unreachable by the relayer.
5. The relayer has no reward left in storage (`NoRewardForRelayer` on any further claim) and no path to recover the trapped value — the reward is permanently lost despite the runtime having recorded it as paid.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}

				.map_err(|_| Error::<T, I>::PayoutError)?;

			Spends::<T, I>::insert(index, spend);

		#[pallet::weight(T::WeightInfo::check_status())]
		pub fn check_status(origin: OriginFor<T>, index: SpendIndex) -> DispatchResultWithPostInfo {
			use PaymentState as State;
			use PaymentStatus as Status;

			ensure_signed(origin)?;
			let mut spend = Spends::<T, I>::get(index).ok_or(Error::<T, I>::InvalidIndex)?;
			let now = T::BlockNumberProvider::current_block_number();

			if now > spend.expire_at && !matches!(spend.status, State::Attempted { .. }) {
				// spend has expired and no further status update is expected.
				Spends::<T, I>::remove(index);
				Self::deposit_event(Event::<T, I>::SpendProcessed { index });
				return Ok(Pays::No.into());
			}

			let payment_id = match spend.status {
				State::Attempted { id } => id,
				_ => return Err(Error::<T, I>::NotAttempted.into()),
			};

			match T::Paymaster::check_payment(payment_id) {
				Status::Failure => {
					spend.status = PaymentState::Failed;
					Spends::<T, I>::insert(index, spend);
					Self::deposit_event(Event::<T, I>::PaymentFailed { index, payment_id });
				},
				Status::Success | Status::Unknown => {
					Spends::<T, I>::remove(index);
					Self::deposit_event(Event::<T, I>::SpendProcessed { index });
					return Ok(Pays::No.into());
				},
				Status::InProgress => return Err(Error::<T, I>::Inconclusive.into()),
			}
			return Ok(Pays::Yes.into());
