## Analysis

The Forta report's root cause is a state-transition function that unconditionally assumes an internal token transfer succeeds and advances protocol state (marks the operation as done) without checking the transfer result. The Polkadot SDK analog is `pallet-bounties::claim_bounty`, where the payout transfers are guarded only by `debug_assert!`, which compiles to a no-op in release/production builds — meaning a failed transfer is silently ignored while the bounty is deleted from storage and a `BountyClaimed` success event is emitted anyway.

### Title
Silent payout failure in `claim_bounty` allows bounty funds to be diverted from the beneficiary while state falsely reports settlement - (File: `substrate/frame/bounties/src/lib.rs`)

### Summary
`Pallet::claim_bounty` transfers the curator fee and beneficiary payout using `T::Currency::transfer(..., AllowDeath)` and only checks the result with `debug_assert!(res.is_ok())`. In a production (release) runtime build `debug_assert!` compiles to nothing, so if the transfer to the beneficiary fails (e.g. the beneficiary is a fresh account and `payout` is below `ExistentialDeposit`), the failure is silently discarded. Execution proceeds to delete the `Bounties` entry, remove `BountyDescriptions`, and emit `Event::BountyClaimed { index, payout, beneficiary }` as if the transfer succeeded, even though the funds never reached the beneficiary.

```rust
pub fn claim_bounty(...) -> DispatchResult {
    ensure_signed(origin)?; // anyone can trigger claim
    Bounties::<T, I>::try_mutate_exists(bounty_id, |maybe_bounty| -> DispatchResult {
        let bounty = maybe_bounty.take().ok_or(Error::<T, I>::InvalidIndex)?;
        if let BountyStatus::PendingPayout { curator, beneficiary, unlock_at } = bounty.status {
            ...
            let res = T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath); // should not fail
            debug_assert!(res.is_ok());
            let res = T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath); // should not fail
            debug_assert!(res.is_ok());

            *maybe_bounty = None;
            BountyDescriptions::<T, I>::remove(bounty_id);
            T::ChildBountyManager::bounty_removed(bounty_id);
            Self::deposit_event(Event::<T, I>::BountyClaimed { index: bounty_id, payout, beneficiary });
            Ok(())
        } ...
    })?;
    Ok(())
}
```

`claim_bounty` is callable by any signed account ("anyone can trigger claim"), not just the beneficiary or curator. The comment "should not fail" is only true under the *assumption* that the beneficiary account already exists and meets `ExistentialDeposit`. `AllowDeath` only permits the *sender* (bounty sub-account) to be reaped; it does not waive the receiver's requirement to reach `ExistentialDeposit` to be created. If a curator awards a bounty to a beneficiary account that has never held a balance, and the computed `payout` (`balance - fee`) is below `ExistentialDeposit` (a realistic scenario for small bounties, high fees, or partial slashing of the bounty account via `claim_handles_high_fee`-style situations), `T::Currency::transfer` returns `Err`.

Because the check is only a `debug_assert!`, in a standard release WASM runtime (`debug_assertions` disabled — the normal build used to produce runtimes deployed on live chains) the error is dropped. Execution continues unconditionally: the `Bounties` storage entry is deleted, `BountyDescriptions` is removed, and `Event::BountyClaimed` is emitted reporting the payout as delivered to `beneficiary`, even though the beneficiary's balance never increased.

Because the `Bounties` map entry no longer exists, the leftover funds sitting in the bounty sub-account (`Self::bounty_account_id(bounty_id)`) can then be swept by the permissionless `reclaim_bounty_funds` extrinsic to the Treasury account instead of the rightful beneficiary: [2](#0-1) 

This produces a settlement mismatch: the chain state and emitted events say the beneficiary was paid `payout`, but the actual value is redirected to the treasury (or perpetually stuck in the bounty sub-account if no `TransferAllAssets` sweep occurs), violating "settle exactly once to the rightful beneficiary and amount."

The exact same unguarded pattern (`debug_assert!(fee_transfer_result.is_ok())` / `debug_assert!(payout_transfer_result.is_ok())`) exists in `claim_child_bounty`: [3](#0-2) 

### Impact Explanation
Any unprivileged account can call `claim_bounty`/`claim_child_bounty` — the caller does not need to be the beneficiary. Once a bounty enters `PendingPayout` with a beneficiary/fee combination that produces a sub-`ExistentialDeposit` payout to a fresh account, the transfer silently fails, but the pallet finalizes the claim as successful, deletes the bounty record, and fires a "paid" event. This breaks the atomicity guarantee that payout state must only advance once the underlying settlement succeeds, and it results in funds being diverted away from the rightful beneficiary (to the treasury via `reclaim_bounty_funds`, or left orphaned), rather than reaching the intended recipient — a direct violation of "conserve value and settle exactly once to the rightful beneficiary and amount."

### Likelihood Explanation
This requires no admin/governance misbehavior beyond the normal, permission-appropriate `award_bounty` call by the assigned curator (a routine, expected action, not privileged abuse), followed by any arbitrary signed account invoking the permissionless `claim_bounty`. The triggering condition (payout below `ExistentialDeposit` to a never-used beneficiary account) is easily reachable through normal parameter choices (small bounty value, dust remaining after fee/slash deductions as already demonstrated by the existing `claim_handles_high_fee` test where `payout: 0`). Since production runtimes are compiled with `debug_assertions` disabled, the guard is inert on every live chain using this pallet.

### Recommendation
Replace the `debug_assert!(res.is_ok())` checks in `claim_bounty` (and the analogous checks in `claim_child_bounty`) with actual error propagation (`res?`) or explicit handling (e.g., use `Preservation::Expendable`/`KeepAlive` semantics correctly, or defensively top up/verify beneficiary existence before finalizing state), so that a failed transfer aborts the whole extrinsic (rolling back the `Bounties` removal) instead of silently finalizing a claim that never delivered funds.

### Proof of Concept
1. Configure/propose and fund a bounty of small `value` such that after `fee` deduction, `payout = balance - fee` is less than `ExistentialDeposit` (as already shown feasible by the existing `claim_handles_high_fee` test producing `payout: 0`; here use a payout strictly between `0` and `ExistentialDeposit`).
2. Curator calls `award_bounty` with `beneficiary` set to an account that has never held a balance (zero balance, non-existent in `frame_system::Account`).
3. After `unlock_at`, any signed account (not necessarily curator/beneficiary) calls `claim_bounty(origin, bounty_id)`.
4. In a release-mode (production) runtime, `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` returns `Err(TokenError::BelowMinimum)` because `beneficiary` cannot be created below ED; `debug_assert!` is compiled out and does nothing.
5. Execution continues: `Bounties` entry is deleted, `Event::BountyClaimed { index, payout, beneficiary }` is emitted, but `Balances::free_balance(beneficiary)` remains `0`.
6. Any account then calls `reclaim_bounty_funds(bounty_id)`, sweeping the un-delivered `payout` from the bounty sub-account to the Treasury account instead of the beneficiary — confirming funds never reached the reported recipient despite the on-chain event claiming settlement.

		pub fn claim_bounty(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
		) -> DispatchResult {
			ensure_signed(origin)?; // anyone can trigger claim

			Bounties::<T, I>::try_mutate_exists(bounty_id, |maybe_bounty| -> DispatchResult {
				let bounty = maybe_bounty.take().ok_or(Error::<T, I>::InvalidIndex)?;
				if let BountyStatus::PendingPayout { curator, beneficiary, unlock_at } =
					bounty.status
				{
					ensure!(Self::treasury_block_number() >= unlock_at, Error::<T, I>::Premature);
					let bounty_account = Self::bounty_account_id(bounty_id);
					let balance = T::Currency::free_balance(&bounty_account);
					let fee = bounty.fee.min(balance); // just to be safe
					let payout = balance.saturating_sub(fee);
					let err_amount = T::Currency::unreserve(&curator, bounty.curator_deposit);
					debug_assert!(err_amount.is_zero());

					// Get total child bounties curator fees, and subtract it from the parent
					// curator fee (the fee in present referenced bounty, `self`).
					let children_fee = T::ChildBountyManager::children_curator_fees(bounty_id);
					debug_assert!(children_fee <= fee);

					let final_fee = fee.saturating_sub(children_fee);
					let res =
						T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath); // should not fail
					debug_assert!(res.is_ok());
					let res =
						T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath); // should not fail
					debug_assert!(res.is_ok());

					*maybe_bounty = None;

					BountyDescriptions::<T, I>::remove(bounty_id);
					T::ChildBountyManager::bounty_removed(bounty_id);

					Self::deposit_event(Event::<T, I>::BountyClaimed {
						index: bounty_id,
						payout,
						beneficiary,
					});
					Ok(())
				} else {
					Err(Error::<T, I>::UnexpectedStatus.into())
				}
			})?;
			Ok(())
		}

		pub fn reclaim_bounty_funds(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
		) -> DispatchResultWithPostInfo {
			ensure_signed(origin)?;

			// A live bounty still manages its account, so leave it untouched.
			ensure!(!Bounties::<T, I>::contains_key(bounty_id), Error::<T, I>::BountyStillActive);

			debug_assert!(
				T::ChildBountyManager::child_bounties_count(bounty_id) == 0,
				"child bounties should not exist for a closed bounty"
			);

			let bounty_account = Self::bounty_account_id(bounty_id);
			let treasury_account = Self::account_id();

			let transferred = T::TransferAllAssets::force_transfer_all_assets(
				&bounty_account,
				&treasury_account,
			)?;

			// Free only if something moved, otherwise paid to prevent griefing.
			if !transferred {
				return Ok(Pays::Yes.into());
			}

			Self::deposit_event(Event::<T, I>::BountyFundsReclaimed { bounty_id });

			Ok(Pays::No.into())
		}
