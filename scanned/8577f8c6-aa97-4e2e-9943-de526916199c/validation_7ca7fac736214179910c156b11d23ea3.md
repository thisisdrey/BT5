### Title
PSM `redeem()` bypasses the live-decimals drift check enforced in `mint()`, allowing stale-decimal precision to corrupt the mint/redeem exchange rate - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
`pallet-psm` mirrors the Chainlink-style decimal-scaling bug: fee/value math is scaled by `10^diff` based on a *decimals* value, and if the decimals value used at redemption time diverges from the actual live decimals of the fungible asset, the scaling factor is wrong and the swap settles the wrong amount. The pallet added a `DecimalsMismatch` guard (`ensure_decimals_match`) specifically to prevent this drift, but that guard is only invoked on the `mint` path [1](#0-0) , while `redeem` reads the stale snapshot decimals directly without revalidating against the live asset metadata [2](#0-1) .

### Finding Description
The pallet keeps a snapshot of each approved external asset's decimals (`ExternalAssets::decimals`) and the internal asset's decimals (`PsmInfo::internal_decimals`), and converts between the two unit systems with `external_to_internal` / `internal_to_external`, which scale by `10^|ext_decimals - internal_decimals|` [3](#0-2) .

Because the fungibles backend's live `decimals()` metadata can change after the PSM registered the asset (this is exactly the class of drift the pallet's own doc calls out: *"Runtime drift guard: `mint`/`redeem` return `DecimalsMismatch` if live metadata diverges from the registration snapshot"* [4](#0-3) ), the pallet added `ensure_decimals_match` to re-check live decimals before using the snapshot for the fixed-point conversion.

`mint()` correctly calls this guard and uses its returned, freshly-validated decimals:
```
let (ext_decimals, internal_decimals) =
    Self::ensure_decimals_match(&info, &internal_asset, &external_asset, &external)?;
``` [1](#0-0) 

`redeem()`, however, pulls the decimals straight from the stored structs without any revalidation:
```
let ext_decimals = external.decimals;
let internal_decimals = info.internal_decimals;
``` [2](#0-1) 

Both `internal_to_external` and the round-trip `external_to_internal` calls that follow in `redeem` therefore use `ext_decimals`/`internal_decimals` values that are asserted, on the `mint` side, to require a live check — but on `redeem` never get that check [5](#0-4) . If the external asset's actual on-chain decimals diverge from the registration snapshot (documented explicitly as a supported/expected drift scenario the pallet must guard against), `redeem` will scale `internal_net` by the wrong power of ten. This is precisely the "decimal mismatch causes wrong-scaled value" bug class the external report describes for `V3Oracle.sol`, just for a swap settlement instead of an oracle price feed.

### Impact Explanation
A wrong scaling factor in `internal_to_external` means `redeem()` releases either far more or far less external collateral than the burned internal amount is actually worth — a direct value-conservation break in the PSM's core mint/redeem invariant ("Balances ... must conserve value and settle exactly once to the rightful beneficiary and amount"). If live decimals decreased relative to the snapshot, `redeem` would under-scale and drain the reserve for too much external collateral per internal token burned (fund loss from the PSM reserve, benefiting the redeemer at the protocol's expense). If they increased, users would be shortchanged. Either direction is an unbacked-value transfer without requiring any privileged or malicious actor — an ordinary, unprivileged user calling the public `redeem` extrinsic.

### Likelihood Explanation
This requires the external asset's live decimals metadata to actually drift from the PSM's stored snapshot after registration — the pallet's own migration notes and error variant (`DecimalsMismatch`) acknowledge this as a real, expected operational scenario (e.g., asset metadata correction, re-registration of an asset id, or a governance/asset-owner change to `Metadata::decimals` on the underlying `pallet-assets`/fungibles implementation, which is not prevented by this pallet). Because `mint` enforces the guard but `redeem` does not, the drift window is exploitable specifically through the redeem path once it exists, with no additional privilege needed by the caller.

### Recommendation
Apply the same `ensure_decimals_match` check in `redeem()` that is already used in `mint()`, and use its returned, freshly-validated decimals for `internal_to_external`/`external_to_internal`, instead of reading `external.decimals` / `info.internal_decimals` directly:
```rust
let (ext_decimals, internal_decimals) =
    Self::ensure_decimals_match(&info, &internal_asset, &external_asset, &external)?;
```

### Proof of Concept
1. `create_psm` for `internal_asset` with `internal_decimals = 6`; approve `external_asset` with snapshot `ext_decimals = 18` via `register_external_asset_with_weight`.
2. Mint normally to build up `PsmDebt` and reserve balance (mint enforces the live-decimals check and succeeds).
3. The external asset's live decimals metadata is changed (e.g., its `Metadata::decimals` is updated/re-set on the fungibles backend to `6`) without the PSM's stored `ExternalAssets::decimals` snapshot being updated — this is exactly the scenario the `DecimalsMismatch` error and migration logic in `pr_11819.prdoc` were built to catch.
4. Call `redeem()` with a chosen `internal_amount`. Because `redeem` never calls `ensure_decimals_match`, it computes `external_out = internal_to_external(internal_net, /*stale*/ 18, 6)`, scaling up by `10^12` instead of treating the (now equal) decimals as identity — resulting in a redemption payout inflated by `10^12`, draining the reserve account far beyond what the burned internal amount is worth.

		///
		/// Scales by `10^(ext_decimals - internal_decimals)` — multiplies up when internal has more
		/// decimals, floor-divides when it has fewer. Returns [`Error::ConversionOverflow`] if
		/// the scaling factor or the product does not fit in the balance type.
		pub(crate) fn external_to_internal(
			amount: BalanceOf<T>,
			ext_decimals: u8,
			internal_decimals: u8,
		) -> Result<BalanceOf<T>, Error<T>> {
			use core::cmp::Ordering::*;
			match ext_decimals.cmp(&internal_decimals) {
				Equal => Ok(amount),
				Less => {
					let diff = (internal_decimals - ext_decimals) as u32;
					let factor = Self::pow10(diff)?;
					amount.checked_mul(&factor).ok_or(Error::<T>::ConversionOverflow)
				},
				Greater => {
					let diff = (ext_decimals - internal_decimals) as u32;
					let factor = Self::pow10(diff)?;
					Ok(amount.checked_div(&factor).unwrap_or_else(BalanceOf::<T>::zero))
				},
			}
		}
