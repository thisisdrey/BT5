## Finding

The requested external report (ShapeShift Snap chain-switch confirmation) reduces to a core invariant: **state-changing/rewarding actions must only be authorized after verifying the specific condition (chain/context) they claim to represent** — not merely that *some* verifiable event occurred. The closest verifiable local analog in `Loderfordw/polkadot-sdk--023` is in the Snowbridge outbound queue v2 delivery-receipt settlement path, where the pallet verifies a genuine Ethereum receipt proof but never inspects the `success` field of the decoded event before paying out the relayer reward.

### Title
Outbound Queue V2 pays relayer reward on `submit_delivery_receipt` without checking `DeliveryReceipt.success` - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
`Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` from a verified Ethereum `InboundMessageDispatched` log and settles the relayer reward from `PendingOrders`, but it never reads the receipt's `success` boolean field before paying out.

### Finding Description
The `DeliveryReceipt` type explicitly carries a `success` flag decoded from the Ethereum-side `InboundMessageDispatched` event [1](#0-0) . The pallet doc comments state that `submit_delivery_receipt` should be called "when the message has been verified **and executed**" [2](#0-1) , implying settlement is conditioned on successful execution on Ethereum.

However, `process_delivery_receipt` only checks the gateway address and the pending nonce before unconditionally paying the reward whenever `order.fee > 0`: [3](#0-2) 

The `receipt.success` field is decoded but discarded — it is never referenced in `process_delivery_receipt`, and a grep of the whole pallet confirms no other check on this field exists. The extrinsic entrypoint `submit_delivery_receipt` is callable by any signed account and only performs proof verification (that the log inclusion is genuine and the bridge is not halted) before calling into this function: [4](#0-3) . The `Verifier::verify` implementation only checks the beacon light client halted-state, execution proof, and receipt inclusion — it has no notion of the semantic `success` value inside the log: [5](#0-4) .

### Impact Explanation
This breaks the required invariant (explicitly called out in the task's pivots) that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." Here, settlement (reward payout + removal of the `PendingOrder`) advances regardless of whether the corresponding Ethereum-side command execution actually succeeded. Any outbound command that fails on Ethereum (e.g., a reverted contract call, insufficient balance for `DepositAsset`, or a malicious/malformed payload crafted by a parachain sender) still results in the relayer being paid the full fee, since the pallet's own bookkeeping treats "delivered" and "executed successfully" as equivalent when they are not. This creates an economically unbacked payout path from bridge fee funds independent of correct execution outcome, and the `success:false` branch has no test coverage — all existing tests hardcode `success: true` [6](#0-5) .

### Likelihood Explanation
The path is reachable by any signed account able to relay a legitimately-included Ethereum log (an unprivileged relayer role by design), and no additional privilege, governance, or malicious-validator assumption is required — only a genuine but *failed* execution on the Ethereum side, which is a normal occurrence (e.g., griefing payloads, gas edge cases, or reverting destination logic), not an attacker-controlled forgery of the proof itself.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` when `receipt.success == true`; on failure, remove the `PendingOrder` (or handle it via a distinct failure/refund path) without paying the fee to the relayer, and emit a distinct event (e.g., `MessageDeliveryFailed`) so downstream consumers/tests can assert on this behavior.

### Proof of Concept
1. A message is queued via `do_process_message`, creating a `PendingOrder { nonce, fee, .. }` with `fee > 0` [7](#0-6) .
2. On Ethereum, the Gateway contract's dispatch of the message's commands reverts/fails, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer submits `submit_delivery_receipt` with a valid merkle/receipt proof of this real (failed) event.
4. `T::Verifier::verify` succeeds (the log genuinely exists and is included), `DeliveryReceipt::try_from` decodes `success: false`, but `process_delivery_receipt` ignores it and pays `order.fee` to `reward_account` exactly as it would for `success: true`, exactly mirroring the assertion pattern in the existing passing test but with `success: false` substituted [8](#0-7) .

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

impl<T: Config> Verifier for Pallet<T> {
	/// Verify a message by verifying the existence of the corresponding
	/// Ethereum log in a block. Returns the log if successful. The execution header containing
	/// the log is sent with the message. The beacon header containing the execution header
	/// is also sent with the message, to check if the header is an ancestor of a finalized
	/// header.
	fn verify(event_log: &Log, proof: &Proof) -> Result<(), VerificationError> {
		// Refuse to verify any Ethereum-side proof while the beacon light client is halted.
		// Governance halts the light client when it suspects a compromise (e.g. sync committee
		// takeover), at which point any signed headers/receipts must be treated as untrusted.
		// Covers every Verifier consumer, including `inbound_queue_v2::submit` and
		// `outbound_queue_v2::submit_delivery_receipt` (which would otherwise still drain
		// pending relayer rewards while the bridge is halted).
		ensure!(!Self::operating_mode().is_halted(), VerificationError::Halted);

		Self::verify_execution_proof(&proof.execution_proof)
			.map_err(|e| InvalidExecutionProof(e.into()))?;

		Self::verify_receipt_inclusion(
			proof.execution_proof.execution_header.receipts_root(),
			event_log.tx_index,
			&proof.receipt_proof,
			event_log,
		)?;

		Ok(())
	}

fn submit_delivery_receipt_succeeds_after_unhalt() {

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_valid_event_proof());

		// Bridge halted — receipt rejected, order untouched.
		set_verifier_halted(true);
		assert_noop!(

			Error::<Test>::Verification(VerificationError::Halted)

		System::assert_has_event(mock::RuntimeEvent::OutboundQueue(Event::MessageDelivered {

		}));
	});
