### Title
Governance change of `EthereumGatewayAddress` permanently strands in-flight `PendingOrders` in `pallet-outbound-queue-v2`, locking relayer rewards - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

### Summary
This mirrors the SecondSwap `VestingManager.setMarketplace` bug class: an admin/governance-controlled address change orphans previously-created state tied to the old address, with no recovery path. In `snowbridge-pallet-outbound-queue-v2`, every outbound message is recorded as a `PendingOrders` entry that can only be resolved by a delivery receipt whose `gateway` field equals the **current** `T::GatewayAddress`. `EthereumGatewayAddress` is a governance-mutable `parameter_types! { pub storage ... }` constant, not an immutable value. Changing it (e.g. redeploying the Ethereum Gateway contract) permanently strands any `PendingOrders` entries created before the switch that receive their delivery receipt after the switch, because the receipt will always carry the *old* gateway address (it's derived from the actual Ethereum contract that emitted the event), while the pallet now checks against the *new* one.

### Finding Description
`process_delivery_receipt` gates reward payout and cleanup strictly on address equality against a single mutable global value: [1](#0-0) 

`PendingOrders` are created for every outbound message processed by `do_process_message`, keyed only by `nonce`, holding the relayer `fee` owed once delivery is proven: [2](#0-1) 

There is no expiry, cancellation, admin override, or reclaim path for a `PendingOrders` entry — the only way to remove it is `process_delivery_receipt` succeeding, which requires `receipt.gateway == T::GatewayAddress::get()` at the time the receipt is submitted, not at the time the order was created.

`EthereumGatewayAddress` is defined as a governance-settable storage constant (not a fixed `Get` constant), and the runtime test suite explicitly documents and tests that it can be changed via governance (`system.setStorage`), exactly analogous to `VestingManager.setMarketplace`: [3](#0-2) [4](#0-3) 

When governance changes this value (to point at a redeployed/upgraded Gateway contract), any message that was already committed to the merkle root and physically executed by the *old* Ethereum Gateway contract before the switch, but whose delivery receipt is submitted *after* the switch, will always encode the old contract's address as `receipt.gateway` (this is derived from the real emitting contract on Ethereum, not from parachain state). The `ensure!(T::GatewayAddress::get() == receipt.gateway, ...)` check will then permanently fail with `Error::InvalidGateway` for that nonce. The corresponding `PendingOrders<T>` entry is never removed and the relayer fee is never paid — it becomes permanently orphaned state, exactly like the SecondSwap listings that could never be unlisted after `setMarketplace` pointed the `VestingManager` elsewhere.

### Impact Explanation
Any `PendingOrders` entries outstanding at the moment of a Gateway-address migration become permanently unresolvable: the relayer who successfully delivered the message on Ethereum can never claim their reward, and the storage entry (and the escrowed/allocated fee behind it) is stuck forever with no permissionless or admin extrinsic capable of clearing or redirecting it. This is a permanent fund-lock / broken settlement-state issue directly in the Snowbridge outbound delivery-receipt flow, matching the "Message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" pivot — here settlement can never succeed atomically across a gateway migration boundary.

### Likelihood Explanation
This does not require a malicious actor: it triggers under the officially supported and tested operational procedure of changing `EthereumGatewayAddress` via governance (as covered by `change_ethereum_gateway_by_governance_works`). Any real-world Gateway contract redeployment on Ethereum (upgrade path, migration, or incident response) combined with in-flight, already-committed-but-not-yet-relayed messages will hit this exact race, so it is a realistic operational scenario rather than a purely theoretical one.

### Recommendation
Before or during a `GatewayAddress` change, drain/settle all outstanding `PendingOrders`, or store the gateway address that was authoritative at message-creation time alongside each `PendingOrder` and validate receipts against that per-order snapshot instead of the current global value. Alternatively, add a governance-only reclaim/close function that can resolve orphaned orders tied to a superseded gateway address (paying out or refunding as appropriate), analogous to providing users a way to withdraw stranded listings after a marketplace migration.

### Proof of Concept
1. Outbound message `M` with `nonce = N` is processed by `do_process_message`, creating `PendingOrders[N] = { nonce: N, fee: F, block_number: B }` while `EthereumGatewayAddress == G_old`. [5](#0-4) 
2. The committed merkle root is relayed and `M` is executed on the real Ethereum Gateway contract at `G_old`, emitting a delivery-receipt event log carrying `gateway = G_old`.
3. Before the relayer submits `submit_delivery_receipt`, governance calls `system.setStorage` to update `EthereumGatewayAddress` to `G_new` (as demonstrated possible by `change_ethereum_gateway_by_governance_works`). [4](#0-3) 
4. The relayer now submits the (valid, correctly proven) receipt for `M`. `process_delivery_receipt` checks `ensure!(T::GatewayAddress::get() == receipt.gateway, ...)`, i.e. `G_new == G_old`, which fails, returning `Error::InvalidGateway`. [6](#0-5) 
5. `PendingOrders[N]` is never removed and `F` is never paid to any relayer — the entry is permanently stuck with no extrinsic in the pallet able to clear or reroute it.
