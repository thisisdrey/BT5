`RequestMessage` (`contracts/wallet/src/message.rs`) `hash()` = `SHA3-256(DOMAIN_SEPARATOR || borsh(msg))`, and `execute_signed` (`contracts/wallet/src/contract.rs`) checks `msg.chain_id`, `msg.signer_id == env::current_account_id()`, commits `msg.nonce` via `self.0.nonces.commit(msg.nonce, msg.created_at, msg.timeout)`, THEN verifies `S::verify_request_msg`. Since nonce commit happens BEFORE signature verification, can an attacker (any unprivileged relayer/caller of `w_execute_signed`) submit a VALID `msg` (correct `chain_id`/`signer_id`) paired with an INVALID/garbage `proof`, consuming/committing `msg.nonce` in storage (since `commit` runs regardless of subsequent signature failure being caught later) so that when the real signer LATER tries to submit the SAME legitimately-signed `msg` with a correct proof, the nonce is already committed and `w_execute_signed` rejects it as used — causing a griefing DoS on a specific pending authorized `Request` execution (owner intended `msg.request` to run, e.g. a withdrawal from an intents wallet)? Does the nonce committed for `msg` EQUAL the nonce that should only be consumed by a message which ALSO passed signature verification, i.e. does commit-then-verify order violate AUTHORISATION: nonce consumed == only for a message whose signature was independently confirmed valid FIRST? Preconditions: owner has produced/broadcast (but not yet had relayed) a valid signed `RequestMessage` intended to move funds; attacker observes the plaintext `msg` (public in relay networks) before relaying with a corrupted `proof`. Call sequence: attacker calls `w_execute_signed(msg, garbage_proof)` first; nonce commit succeeds; signature check fails and call reverts, but does the nonce COMMIT get rolled back on revert (need to confirm) — if NOT rolled back due to promise/host semantics, owner's legitimate later submission with correct proof fails with nonce-used. Impact: High, a signer's intended, authorized `Request` becomes permanently unexecutable (funds/authorization frozen) via nonce front-running, though impact is denial not theft. Proof: near-workspaces test submitting garbage-proof `w_execute_signed` for an observed `msg`, then submitting the correctly-signed version and asserting the honest transaction succeeds or is blocked by nonce reuse, confirming atomic rollback semantics.
