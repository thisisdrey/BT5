### Title
Precision loss in `convert_from_ether_decimals` causes underpriced/zero remote fee for outbound Snowbridge messages - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
`Pallet::calculate_fee` computes the DOT-denominated remote fee for delivering a message to Ethereum via `FixedU128` multiplication/division and then truncating integer division in `convert_from_ether_decimals`. When the computed remote-fee value (in 18-decimal "ether" fixed-point units) is smaller than the divisor used to rescale into the native 10/12-decimal currency, the division rounds down to zero, exactly mirroring the `boostPrice` precision-loss bug class from the external report (division that rounds a small positive quantity down to a degenerate value). This is acknowledged in-repo by the pallet's own test.

### Finding Description
`calculate_fee` computes:
```
fee = FixedU128::from_inner(fee).saturating_mul(params.multiplier).checked_div(&params.exchange_rate)...into_inner();
fee = Self::convert_from_ether_decimals(fee);
``` [1](#0-0) 

`convert_from_ether_decimals` performs a plain truncating integer division to rescale from Ether's 18 decimals down to the chain's native decimals (10 for DOT, 12 for KSM):
```rust
pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
    let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
    let denom = 10u128.saturating_pow(decimals);
    value.checked_div(denom).expect("divisor is non-zero; qed").into()
}
``` [2](#0-1) 

For DOT (10 decimals) the divisor is `10^8`. Any pre-division `fee` value below `10^8` (in the 18-decimal fixed-point ether representation) is truncated to `0`, exactly the same class of rounding-to-degenerate-value bug as `boostPrice`'s `sqrtPriceX96 ** 2 / Q96 ** 2` rounding to `1`. The pallet's own test suite documents this exact outcome as reachable with "valid" (non-zero) pricing parameters:
```rust
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
    ...
    let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
    assert_eq!(fee.local, 698000000);
    // Though none zero pricing params the remote fee calculated here is invalid
    // which should be avoided
    assert_eq!(fee.remote, 0);
}
``` [3](#0-2) 

This fee is directly consumed by the unprivileged, public message-send path. `SendMessage::validate`, invoked whenever a sibling parachain or the system pallet sends a message to Ethereum, calls `calculate_fee` and returns the (possibly zero) `Fee` to the caller without any lower-bound check:
```rust
let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());
...
Ok((ticket, fee))
``` [4](#0-3) 

No guard exists anywhere in `calculate_fee`, `convert_from_ether_decimals`, or `validate` to reject or round up a remote fee that truncates to zero (unlike, e.g., `asset-conversion::get_amount_in`, which explicitly adds 1 after division to avoid underpricing). There is also no minimum-fee floor check before `deliver()` enqueues the message.

### Impact Explanation
If governance-set `PricingParameters` (exchange rate, multiplier, fee-per-gas, reward) combine such that the pre-scaling remote fee value is less than `10^8` (for a 10-decimal chain) or `10^6` (for a 12-decimal chain), any unprivileged party who triggers an outbound Snowbridge message (via XCM export or system pallet send) is charged **zero** DOT/KSM for the remote-relay component of the fee, while the message is still queued and eventually delivered/relayed to Ethereum. This is public underpriced work: attackers can flood the outbound queue with messages that Ethereum-side relayers must gas-cover, without paying the reward/gas-refund fee that is supposed to compensate them, degrading bridge economics and potentially stalling relayer participation (relayers stop servicing an unprofitable queue), which is exactly the "public underpriced work that degrades... stalls bridge processing" impact class.

### Likelihood Explanation
The condition is purely parameter-dependent and requires no privileged actor, malicious relayer, or governance abuse to *trigger* — governance merely needs to set realistic-looking (non-zero) pricing parameters that happen to produce a small remote fee (e.g., low gas price, small reward, or a very favorable ETH/DOT exchange rate); any ordinary user can then call the public send path to exploit the resulting zero fee repeatedly. The pallet's authors already discovered and unit-tested this exact scenario, explicitly annotating it as "should be avoided," confirming it is a known, reachable, unresolved rounding defect rather than a purely theoretical one.

### Recommendation
Round the fee division up (or enforce a `MinimumFee` floor) so that `convert_from_ether_decimals` never returns `0` for a strictly positive input, e.g. use `multiply_by_rational_with_rounding(value, 1, denom, Rounding::Up)` or add `denom - 1` before dividing, and additionally reject/clamp the final fee in `calculate_fee`/`validate` if it would be zero for a non-zero pre-conversion value.

### Proof of Concept
Using the pallet's existing test harness (`bridges/snowbridge/pallets/outbound-queue/src/test.rs`), the following demonstrates the truncation to zero with non-zero, "valid" pricing parameters:
```rust
let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
    exchange_rate: FixedU128::from_rational(1, 1),
    fee_per_gas: 1_u32.into(),
    rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
    multiplier: FixedU128::from_rational(1, 1),
};
let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
assert_eq!(fee.remote, 0); // remote fee silently rounds to zero
``` [3](#0-2) 
Any message sent through the public `SendMessage::validate` entrypoint under these (or similarly small) parameters is queued with `fee.remote == 0`, meaning the sender pays nothing for relayer gas/reward while the message is still committed and eventually delivered to Ethereum. [5](#0-4)

		ensure!(

		// The whole message should not be too large
