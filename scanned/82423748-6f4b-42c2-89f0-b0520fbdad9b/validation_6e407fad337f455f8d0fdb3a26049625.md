## Title
Permanent stake and reward lock in `pallet-asset-rewards` from unbounded `last_update_block` after pool expiry - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` computes rewards based on the delta between the pool's `expiry_block`-capped "applicable" block and `last_update_block`, but `update_pool_rewards` always advances `last_update_block` to the *actual current block*, not the expiry-capped block. Once any account interacts with an already-expired pool (a permissionless action), `last_update_block` becomes greater than `expiry_block`. Every subsequent reward computation then underflows and errors out, permanently bricking `stake`, `unstake`, `harvest_rewards`, `set_pool_reward_rate_per_block`, and `set_pool_expiry_block` for that pool — freezing all staked tokens and unharvested rewards with no recovery path, since the very extension function that could "fix" the expiry also fails.

### Finding Description
`reward_per_token` computes the elapsed rewardable blocks as: [1](#0-0) 

```rust
let rewardable_blocks_elapsed: u32 =
    match Self::last_block_reward_applicable(pool_info.expiry_block)
        .ensure_sub(pool_info.last_update_block)?
        .try_into()
    { ... };
```

where `last_block_reward_applicable` caps at `expiry_block`: [2](#0-1) 

However, `update_pool_rewards` — called by every mutating extrinsic before it does anything else — unconditionally sets `last_update_block` to the *uncapped* current block number: [3](#0-2) 

```rust
pub fn update_pool_rewards(
    pool_info: &PoolInfoFor<T>,
    reward_per_token: T::Balance,
) -> Result<PoolInfoFor<T>, DispatchError> {
    let mut new_pool_info = pool_info.clone();
    new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
    ...
```

This is the same root-cause pattern as the external report: a "last updated" timestamp/blocknumber is advanced to the wall-clock present instead of being clamped to the last moment reward emission was actually active. In the Move report, this *inflated* rewards by counting an inactive gap. Here the analogous bug *inverts the gap*, producing `last_update_block > expiry_block`; the next call to `reward_per_token` does `expiry_block.ensure_sub(last_update_block)`, i.e. a smaller number minus a larger one, which is a checked/`ensure_*` operation that returns `Err` on underflow instead of saturating.

Crucially, the pool does not need an admin action to reach this expired-but-untouched state — any account can trigger the first post-expiry interaction. `unstake` and `harvest_rewards` explicitly allow **any caller** to act after expiry: [4](#0-3) 

```rust
let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
let now = T::BlockNumberProvider::current_block_number();
ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);
...
let (mut pool_info, mut staker_info) =
    Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;
```

The first such call succeeds (since at that moment `last_update_block <= expiry_block` still holds) but leaves `last_update_block = now > expiry_block` in storage. Every subsequent call to `stake`, `unstake`, `harvest_rewards`, `set_pool_reward_rate_per_block`, or `set_pool_expiry_block` starts by calling `reward_per_token`/`update_pool_and_staker_rewards`, which now underflows and returns `Err`, aborting the extrinsic. Even the pool admin's supposed recovery action, `set_pool_expiry_block`, calls `reward_per_token` with the *old* (already-passed) `expiry_block` before applying the new one, so it also fails: [5](#0-4) 

There is no other code path to reset `last_update_block` back below `expiry_block`, so the pool becomes permanently unusable.

### Impact Explanation
This is a public, unprivileged, permanent user-fund lock: any staked tokens (frozen via `T::AssetsFreezer`) and any unharvested reward-asset balance held in `pool_info.account` become permanently unreachable through the pallet's normal call surface once the bug is triggered, matching the "permanent user-fund or bridge-state lock" impact category. It also removes the admin's only documented recovery mechanism (`set_pool_expiry_block`), so there is no privileged path to unbrick the pool either — cleanup_pool cannot run since it requires an empty pool (`ensure!(stakers.is_none(), Error::<T>::NonEmptyPool)`), and stakers can never unstake to become empty.

### Likelihood Explanation
High. Any pool that reaches its `expiry_block` while stakers still hold positions will hit this the moment *any* account (staker or not, since post-expiry `unstake`/`harvest_rewards` allow any caller) performs a single interaction with it. This requires no privileged role, no malicious validator/relayer, and no special timing beyond simply waiting for `expiry_block` to pass — an entirely ordinary, expected pool lifecycle event.

### Recommendation
In `update_pool_rewards`, clamp the new `last_update_block` to `min(current_block_number(), pool_info.expiry_block)` (i.e., use the same `last_block_reward_applicable` value used to compute `reward_per_token`) rather than the raw current block number. This keeps `last_update_block` always `<= expiry_block` until the expiry is legitimately extended, preventing the underflow and restoring the admin's ability to call `set_pool_expiry_block` to resume rewards.

### Proof of Concept
1. `create_pool` with `expiry_block = E` and `reward_rate_per_block > 0`.
2. `staker` calls `stake` before `E`; pool now has `total_tokens_staked > 0`.
3. Advance chain to block `E + k` (`k > 0`), i.e. past expiry, with no interactions in between.
4. Any account (attacker) calls `unstake` (permitted post-expiry for any caller) or `harvest_rewards` for `staker`. This call succeeds; `Pools::<T>::get(pool_id).last_update_block` is now set to `E + k > E`.
5. `staker` now calls `unstake` to withdraw remaining stake, or `harvest_rewards`: `reward_per_token` computes `last_block_reward_applicable(E).ensure_sub(E + k)` = `E.ensure_sub(E + k)`, which underflows and returns `Err`, aborting the extrinsic.
6. Admin attempts `set_pool_expiry_block` to extend expiry and resume operation: this also calls `reward_per_token` with the stale `expiry_block = E` first, hits the same underflow, and fails.
7. All staked tokens for every staker in the pool, plus any unclaimed reward-asset balance in `pool_info.account`, are now permanently locked with no available extrinsic to recover them.

	fn set_pool_expiry_block(
		admin: &T::AccountId,
		pool_id: PoolId,
		new_expiry: DispatchTime<BlockNumberFor<T>>,
	) -> DispatchResult {
		let now = T::BlockNumberProvider::current_block_number();
		let new_expiry_block = new_expiry.evaluate(now);
		ensure!(new_expiry_block > now, Error::<T>::ExpiryBlockMustBeInTheFuture);

		let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
		ensure!(pool_info.admin == *admin, BadOrigin);
		ensure!(new_expiry_block > pool_info.expiry_block, Error::<T>::ExpiryCut);

		// Always start by updating the pool rewards.
		let reward_per_token = Self::reward_per_token(&pool_info)?;
		let mut pool_info = Self::update_pool_rewards(&pool_info, reward_per_token)?;

		pool_info.expiry_block = new_expiry_block;
		Pools::<T>::insert(pool_id, pool_info);
