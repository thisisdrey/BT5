### Title
ERC20 asset transactor silently drops non-first fungible assets on deposit, causing permanent fund loss - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::deposit_asset_with_surplus` only inspects and transfers the **first** fungible asset found in the `AssetsInHolding` batch it receives, then reports full success (`Ok(surplus)`) while discarding the entire `what` parameter — including any additional ERC20 (or other) assets bundled in the same call. This mirrors the 0x `transformERC20()` bug: the caller checks/acts on one designated value while other value carried through the same call is never accounted for and is effectively destroyed rather than delivered or trapped.

### Finding Description
`deposit_asset_with_surplus` explicitly documents the unsafe assumption: [1](#0-0) 

It takes `what: AssetsInHolding` by value, extracts only `what.fungible_assets_iter().next()`, performs a single Solidity `transfer()` call for that one asset via `pallet_revive::Pallet::<T>::bare_call`, and on success returns `Ok(surplus)` — the `what` value (and any other assets it may have contained) is simply dropped, never re-emitted, never routed to `AssetTrap`, and never actually transferred to the beneficiary: [2](#0-1) 

Inside the standard `xcm-executor` `DepositAsset` path, holdings are pre-split per asset id via `into_per_asset_holdings()` before calling the transactor: [3](#0-2) 

which limits exposure through that specific call site. However, `AssetTransactor::deposit_asset` (the un-split, non-surplus variant) is also invoked directly from other code paths that are not guaranteed to pre-split holdings into single-asset batches, e.g. `cumulus/primitives/utility/src/lib.rs` and `polkadot/xcm/xcm-builder/src/fee_handling.rs`, both of which call `AssetTransactor::deposit_asset` with an arbitrary `AssetsInHolding` (fee refunds / swapped fee assets) that can legitimately contain more than one asset id. Because `ERC20Transactor` is composed into the parachain's `AssetTransactors` tuple (`cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`), and its matcher `ERC20Matcher` accepts **any** local `AccountKey20` location as a valid asset id with no allow-list: [4](#0-3) 

any bundle of AssetsInHolding containing more than one ERC20-matched fungible entry that reaches this transactor's `deposit_asset`/`deposit_asset_with_surplus` will only transfer the first entry; the remainder is neither delivered to the beneficiary nor trapped for later reclaim — it is unconditionally destroyed while the call reports success. The runtime's `Erc20Credit` imbalance type further compounds this because it performs "no runtime-level balance enforcement" (per its own doc comment), so the destroyed credit has no corresponding on-chain reversal.

### Impact Explanation
Any code path that batches multiple ERC20-backed assets into a single `deposit_asset`/`deposit_asset_with_surplus` call (fee-refund logic, `PayFees`/`InitiateTransfer` composite flows, custom `TransactAsset` tuple compositions, or a future refactor that removes the per-asset split before calling the tuple) causes silent, permanent, unrecoverable loss of user or protocol-held ERC20 asset value — the exact "unaccounted-for tokens" failure mode from the source report, except here the result is loss rather than double counting. This qualifies as a fund-loss / permanent-lock impact under the accepted gate criteria (conservation-of-value violation on settlement of contract-held value).

### Likelihood Explanation
The vulnerable code path requires no privileged actor: any unprivileged party constructing or triggering an XCM program that funnels more than one ERC20-matched asset into a single `deposit_asset` call (via any composite instruction/utility helper that does not itself guarantee per-asset-id splitting) triggers the loss. The explicit code comment ("the rest will be silently ignored") demonstrates this is a known, reachable, unguarded gap rather than a purely theoretical one, and the `defensive_assert!` used to "catch misuse" is a no-op in production (non-debug) builds, providing no actual protection at runtime.

### Recommendation
`deposit_asset_with_surplus`/`deposit_asset` in `ERC20Transactor` must either (a) reject the call outright (return `Err` with the full, untouched `what`) whenever more than one distinct asset is present, instead of silently proceeding, or (b) iterate over and transfer *all* fungible entries in `what`, returning any that fail as unspent `AssetsInHolding` rather than dropping them. The `defensive_assert!` should be replaced with a hard runtime check (`ensure!`/early return) so both debug and release builds are protected.

### Proof of Concept
1. Deploy two distinct ERC-20-like contracts `A` and `B` at addresses `addrA`/`addrB` via `pallet-revive`.
2. Construct (or find/trigger) any XCM execution path that calls `AssetTransactor::deposit_asset` (not the executor's per-asset-split `deposit_assets_with_retry`) with an `AssetsInHolding` containing both `Fungible(addrA, amountA)` and `Fungible(addrB, amountB)` matched by `ERC20Matcher` — e.g. a fee-refund/swap path in `cumulus/primitives/utility/src/lib.rs` or `polkadot/xcm/xcm-builder/src/fee_handling.rs` that batches leftover assets before depositing to a beneficiary.
3. Observe that `ERC20Transactor::deposit_asset_with_surplus` (`erc20_transactor.rs:225-306`) picks `next()` of `fungible_assets_iter()` (say `addrA`), performs the real `transfer()` call for `amountA` only, and returns `Ok(surplus)`.
4. Confirm the beneficiary never receives `amountB` of asset `B`, no error is raised, no `AssetTrap` event fires, and the value tracked for asset `B` in the caller's `AssetsInHolding` is gone — permanently unaccounted for and irrecoverable.

	/// Note: This implementation only handles a single fungible asset at a time. The

	/// first fungible asset will be deposited and the rest will be silently ignored.
	/// The `defensive_assert!` helps catch misuse during development.

		what: AssetsInHolding,
		who: &Location,
		_context: Option<&XcmContext>,

			target: "xcm::transactor::erc20::deposit",

			.next()

			Some(inner) => inner,
			None => return Err((what, MatchError::AssetNotHandled.into())),
