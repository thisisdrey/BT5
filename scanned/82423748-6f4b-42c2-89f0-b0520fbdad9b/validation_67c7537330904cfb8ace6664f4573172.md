### Title
Reward accounting corrupted by external-effect-before-state-write ordering in `harvest_rewards` - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`Pallet::harvest_rewards` in the `pallet-asset-rewards` pallet transfers the staker's accrued reward token amount before it persists the updated accounting state (`staker_info.rewards = 0` and the recomputed `pool_info`) to storage. This is the exact ordering flaw described in the external report: the "payout" (external effect) happens ahead of the "state finalization" (accounting write) that is supposed to make that payout unrepeatable. [1](#0-0) 

### Finding Description
`harvest_rewards` computes the staker's owed reward (`staker_info.rewards`) from `update_pool_and_staker_rewards`, then immediately calls `T::Assets::transfer(...)` to pay the staker, and only afterwards zeroes `staker_info.rewards` and calls `PoolStakers::<T>::insert(...)`:

```rust
let (pool_info, mut staker_info) =
    Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

// Transfer unclaimed rewards from the pool to the staker.
T::Assets::transfer(
    pool_info.reward_asset_id,
    &pool_info.account,
    &staker,
    staker_info.rewards,
    Preservation::Expendable,
)?;
...
// Reset staker rewards.
staker_info.rewards = 0u32.into();

if staker_info.amount.is_zero() {
    PoolStakers::<T>::remove(&pool_id, &staker);
} else {
    PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
}
``` [2](#0-1) 

Compare this to the sibling extrinsics `stake` and `unstake`, both of which persist the recomputed `pool_info` to `Pools::<T>` immediately after mutating it and before/along with any other side effects: [3](#0-2) [4](#0-3) 

`harvest_rewards`, by contrast, never writes the recomputed `pool_info` back to `Pools::<T>` at all, and defers the staker's `rewards` reset until after the token transfer has already been executed. This is structurally identical to the Stakehouse `GiantMevAndFeesPool.withdrawETH` bug: the balance/accounting decrement (`idleETH -= _amount` moved after `burn`) versus the payout (`.call{value}`) — here the analog is "pay first, zero-out bookkeeping second."

### Impact Explanation
While I was not able to find, within the indexed portion of this repository, a concrete synchronous callback hook fired by `T::Assets::transfer` (the pallet's `Config::Assets` is a generic `fungibles::Mutate` associated type, and I could not confirm from available code whether any concrete runtime binds it to an implementation with a reentrant callback such as `FrozenBalance::died`, an `AssetsCallback`, or an XCM-`Transact`-capable adapter). If a runtime instantiates this pallet with a `Config::Assets` implementation whose `transfer` can synchronously trigger further logic (e.g. an asset-destruction/new-account callback, or a `fungibles` adapter that performs an XCM `Transact` back into this pallet), an attacker who re-enters `harvest_rewards` (or another extrinsic reading `PoolStakers`) during that window would observe `staker_info.rewards` still holding its pre-payout, non-zeroed value, and could be paid out again for the same accrued rewards — a duplicate-settlement bug matching the "must settle exactly once" invariant. Even absent a demonstrable reentrant callback, the missing `Pools::<T>::insert` write for `pool_info` after harvesting is an actual, unconditional accounting bug: the pool's `last_update_block`/`reward_per_token_stored` are silently discarded on every harvest, which is a correctness defect in the pool's canonical reward accounting though I could not prove a divergence in payout amounts under all sequences without deeper analysis.

### Likelihood Explanation
Confirmed with certainty (from the source shown above): the ordering itself, and the fact that `pool_info` is never persisted in `harvest_rewards`. Not confirmed: whether any concrete `Config::Assets`/`Config::AssetsFreezer` binding in a real runtime deployment of this pallet enables a synchronous reentrant call path during `transfer`. Because I could not verify that a reentrant primitive exists in-repo for the configured `Assets` type, I flag this finding's exploitability (i.e., whether an unprivileged caller can actually trigger double-payout without any privileged/malicious external actor or non-default runtime configuration) as unresolved rather than proven.

### Recommendation
Reorder the extrinsic so all storage writes (staker reward reset, pool state persistence) happen before the external `T::Assets::transfer` call, mirroring the pattern already used in `stake`/`unstake`:
```rust
let (pool_info, mut staker_info) = Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;
let payout = staker_info.rewards;
staker_info.rewards = 0u32.into();

Pools::<T>::insert(pool_id, pool_info.clone());
if staker_info.amount.is_zero() {
    PoolStakers::<T>::remove(&pool_id, &staker);
} else {
    PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
}

T::Assets::transfer(pool_info.reward_asset_id, &pool_info.account, &staker, payout, Preservation::Expendable)?;
```

### Proof of Concept
Not independently verifiable as a fully-executable duplicate-payout exploit from the indexed repository content alone: doing so requires confirming a concrete `Config::Assets`/`AssetsFreezer` binding used by a live runtime that permits a synchronous re-entrant call into `harvest_rewards` during `T::Assets::transfer`. The code-level ordering defect itself, however, is directly demonstrable by reading `harvest_rewards` (lines 584–614) against `stake`/`unstake` (lines 489–496, 543–554) as cited above, and reproducing it only requires: (1) create a pool, (2) stake, (3) accrue rewards, (4) call `harvest_rewards`, and inspect that `Pools::<T>::get(pool_id)` is unchanged (the recomputed `pool_info` was discarded) while the transfer already executed before the `staker_info.rewards` reset was committed.
