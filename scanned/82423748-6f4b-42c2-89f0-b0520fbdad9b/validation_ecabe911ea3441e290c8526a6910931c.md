## Analysis

The Cally bug's core invariant is: **a contract tracks an expected/recorded amount separately from the actual balance it physically holds, and when the two diverge, the surplus becomes permanently stranded with no code path to reclaim it.**

The closest verified local analog in this repository is in `pallet-society`'s payout accounting, documented in `prdoc/pr_12590.prdoc`.

### Title
Society payouts sub-account balance can permanently desync from recorded `Payouts` entries, stranding member funds - (File: `substrate/frame/society/src/lib.rs`)

### Summary
`pallet-society` moves funds backing a member's pending payout from the main society account into a dedicated `payouts` sub-account (`Self::payouts()`) whenever a payout is scheduled (`reserve_payout`), and is supposed to move the balance back whenever a payout entry is discarded before being paid (`unreserve_payout`). [1](#0-0) 

### Finding Description
Per `prdoc/pr_12590.prdoc`, four call paths mutate/clear a member's `Payouts` record without performing the corresponding `unreserve_payout` to move the backing balance out of the `payouts` sub-account: `waive_repay` clearing pending payouts without unreserving, `slash_payout` deducting from pending payouts without unreserving the deducted amount, `bump_payout` reserving funds even when the payment is discarded (member already at `MaxPayouts`), and `dissolve` clearing all payout records without returning the sub-account balance to the society account. [2](#0-1) 

This is structurally identical to the Cally rebasing-token bug: the pallet's `Payouts` storage (the "recorded" amount, analogous to `vault.tokenIdOrAmount`) is decoupled from the actual token balance held in the `payouts()` sub-account (analogous to the vault's real, growing `balanceOf`). When the two are supposed to stay in lock-step but a code path updates one without the other, the excess balance sits in an account (`Self::payouts()`) that has no `Payouts` entry pointing to it — exactly like rebasing rewards accruing to a vault with no accounting hook to claim them. [3](#0-2) 

The fix adds a `try_state` invariant asserting `payouts sub-account balance == total of all pending Payouts`, and ships an idempotent migration (`pallet_society::migrations::ReconcilePayoutsAccount`) specifically because existing deployments — the prdoc calls out Kusama Asset Hub by name — already have drifted, stranded balances from before the fix (and from the `v0` migration, which carried payout records over without moving balances). [4](#0-3) 

### Impact Explanation
Any live chain running `pallet-society` that has not yet applied `ReconcilePayoutsAccount` has society-member funds permanently locked in the `payouts` sub-account with no `Payouts` record entitling anyone to claim them — a "permanent user-fund lock," which is an accepted impact category. The corrupted value is the drifted balance of `Self::payouts()` (society's payouts sub-account) relative to `pending_payouts_total()`. [5](#0-4) 

### Likelihood Explanation
This requires no privileged actor, malicious peer, or governance action — it is triggered purely by unprivileged members interacting with normal public extrinsics (`waive_repay`, hitting `MaxPayouts` via `bump_payout`, or society `dissolve`) prior to the fix being deployed with its migration. Deployments that have not run the reconciliation migration remain permanently affected regardless of code fix, since the on-chain balance drift already occurred and is not self-correcting.

### Recommendation
Ensure every runtime using `pallet-society` includes `pallet_society::migrations::ReconcilePayoutsAccount` in its migration tuple before/alongside the code fix, and keep the `try_state` invariant (`payouts sub-account balance == sum(Payouts)`) enabled in CI/try-runtime for all such runtimes to detect any future desync between recorded and real balances.

### Proof of Concept
1. On an unfixed/un-migrated runtime, a member is scheduled a payout via `bump_payout`, which calls `reserve_payout` and moves funds into `Self::payouts()`.
2. Before the payout matures, the member (or society) triggers `waive_repay` or society `dissolve`, which clears the `Payouts` record for that member without calling `unreserve_payout`.
3. `Self::payouts()` sub-account now permanently holds the reserved balance with no corresponding `Payouts` entry and no other pallet call path that returns it to the society pot.
4. `pending_payouts_total()` (sum of remaining `Payouts` entries) is now permanently less than the actual balance sitting in `Self::payouts()`, and that delta can never be spent, paid out, or reclaimed by any extrinsic — matching the "rewards accrue and remain locked forever" impact from the source report. [5](#0-4)

	/// amount to the pot. Return the total amount that was deducted.
	fn slash_payout(who: &T::AccountId, value: BalanceOf<T, I>) -> BalanceOf<T, I> {
		let mut record = Payouts::<T, I>::get(who);
		let mut rest = value;
		while !record.payouts.is_empty() {
			if let Some(new_rest) = rest.checked_sub(&record.payouts[0].1) {
				// not yet totally slashed after this one; drop it completely.
				rest = new_rest;
				record.payouts.remove(0);
			} else {
				// whole slash is accounted for.
				record.payouts[0].1.saturating_reduce(rest);
				rest = Zero::zero();
				break;
			}
		}
		Payouts::<T, I>::insert(who, record);
		let slashed = value - rest;
		Self::unreserve_payout(slashed);
		slashed
	}

	/// Transfer some `amount` from the main account into the payouts account and reduce the Pot
	/// by this amount.
	fn reserve_payout(amount: BalanceOf<T, I>) {
		// Transfer payout from the Pot into the payouts account.
		Pot::<T, I>::mutate(|pot| pot.saturating_reduce(amount));

		// this should never fail since we ensure we can afford the payouts in a previous
		// block, but there's not much we can do to recover if it fails anyway.
		let res = T::Currency::transfer(&Self::account_id(), &Self::payouts(), amount, AllowDeath);
		debug_assert!(res.is_ok());
	}

	/// Transfer some `amount` from the main account into the payouts account and increase the Pot
	/// by this amount.
	fn unreserve_payout(amount: BalanceOf<T, I>) {
		// Transfer payout from the Pot into the payouts account.
		Pot::<T, I>::mutate(|pot| pot.saturating_accrue(amount));

		// this should never fail since we ensure we can afford the payouts in a previous
		// block, but there's not much we can do to recover if it fails anyway.
		let res = T::Currency::transfer(&Self::payouts(), &Self::account_id(), amount, AllowDeath);

	}
