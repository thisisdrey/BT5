## Analysis

The Spigot bug's core invariant break is: **an accounting/settlement step is marked "complete" based on an operation that can silently fail or leave value stranded in a different execution context, with no fallback branch to recover it.** The strongest local analog to this pattern is in the Snowbridge relayer-reward payout flow between BridgeHub and AssetHub.

### Title
Relayer rewards are irrevocably burned on BridgeHub before the cross-chain `DepositAsset` to the beneficiary actually settles on AssetHub - ([File: bridges/snowbridge/primitives/core/src/reward.rs])

### Summary
`pallet-bridge-relayers`'s `claim_rewards_to` removes the relayer's `RelayerRewards` entry and emits `RewardPaid` as soon as `PaymentProcedure::pay_reward` returns `Ok(())`. For Snowbridge rewards, `pay_reward` is implemented by `PayAccountOnLocation::pay_reward`, which only confirms that an XCM was *validated and handed to the outbound queue* for delivery to AssetHub — it never confirms that the remote `DepositAsset` instruction to the caller-supplied `beneficiary` actually executes and credits funds. If the beneficiary `Location` cannot be resolved into a valid AssetHub account by the remote `LocationToAccountId`/asset transactor, the XCM executor traps the assets under an origin the relayer does not control, while BridgeHub has already deleted the reward and declared it paid — a permanent, irrecoverable loss of the relayer's reward, structurally identical to the Spigot bug's "settlement declared success without confirming the value-transfer branch actually completed."

### Finding Description
In `bridges/modules/relayers/src/lib.rs`, `do_claim_rewards` does: [1](#0-0) 
The `try_mutate_exists` closure takes the reward out of storage, calls `T::PaymentProcedure::pay_reward`, and — only if `pay_reward` returns `Err` — the storage mutation rolls back. If `pay_reward` returns `Ok(())`, the reward is gone forever and `RewardPaid` is emitted.

For `BridgeReward::Snowbridge`, `pay_reward` is `PayAccountOnLocation::pay_reward` in `bridges/snowbridge/primitives/core/src/reward.rs`: [2](#0-1) 

This builds an XCM program `[UnpaidExecution, DescendOrigin, UniversalOrigin, ReserveAssetDeposited, DepositAsset { assets: AllCounted(1), beneficiary }]`, then only checks:
1. `validate_send` succeeded (message accepted into the router/queue), and
2. `deliver` succeeded (message queued for XCMP/HRMP delivery).

`Ok(())` is returned at this point — **before** the message is even executed on AssetHub, let alone before `DepositAsset` actually succeeds. The caller-supplied `beneficiary` (from `claim_rewards_to(origin, reward_kind, beneficiary: BeneficiaryOf<T,I>)`, `bridges/modules/relayers/src/lib.rs:227-235`) is fully attacker/relayer-controlled and is not pre-validated against AssetHub's account-conversion rules on BridgeHub.

If the resulting XCM's `DepositAsset` fails on AssetHub (e.g. `beneficiary` is a `Location` that AssetHub's `LocationToAccountId`/asset transactor cannot convert, or the target account cannot receive the asset per its existence/ED rules), the XCM executor traps the held assets via `AssetsTrapped`, with the trap **origin** being the XCM's execution origin (the descended `InboundQueueLocation` + `UniversalOrigin(Ethereum)` — a location the relayer does not own), not the relayer's real account. This exact "assets trapped under a foreign/uncontrollable origin" mechanic is demonstrated elsewhere in the codebase's own tests, e.g. `invalid_xcm_traps_funds_on_ah` and `fallback_claimer_traps_to_bridge_owner_and_claim_assets_succeeds` in `cumulus/parachains/integration-tests/emulated/tests/bridges/bridge-hub-westend/src/tests/snowbridge_v2_inbound.rs:857-926,1023-1121`, which show `AssetsTrapped` events firing under trap origins distinct from the intended recipient, requiring a separate, unrelated `claim_assets` call from whoever controls that trap origin.

By the time this trap happens, `do_claim_rewards` has already unconditionally removed the reward from `RelayerRewards` and emitted `RewardPaid` on BridgeHub — there is no atomic linkage between the source-chain settlement state and destination-chain execution success, unlike the invariant required: *"Message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically."*

### Impact Explanation
A relayer's earned reward can be permanently destroyed with no recovery path through the intended flow: the source-chain ledger (`RelayerRewards`) is decremented and the event says "paid," but the actual value never reaches (and may become permanently unclaimable by) the intended beneficiary. This is a direct instance of "permanent user-fund... lock" — the reward existed, was claimed, and then vanished due to an unhandled failure branch in the cross-chain settlement, mirroring the Spigot report's core defect of declaring completion without confirming the actual value transfer succeeded.

### Likelihood Explanation
Triggering only requires an ordinary, unprivileged relayer to call `claim_rewards_to` (a public, permissionless extrinsic) with a `Location` beneficiary that AssetHub cannot resolve/credit — no admin, governance, validator, or malicious-peer assumption is needed. Malformed or edge-case `Location`s (unsupported junction kinds, wrong network tag, insufficient-asset/ED account states) are easy to construct by mistake or intentionally, and the bug manifests deterministically whenever the remote `DepositAsset` fails after the local reward has already been erased.

### Recommendation
Do not remove/settle the reward on BridgeHub based solely on XCM queuing success. Options: (1) require delivery-receipt/execution confirmation from AssetHub (e.g., via XCM `ReportOutcome`/query mechanism) before finalizing the reward removal, or (2) keep the reward pending/refundable and only finalize on a confirmed success callback, with a fallback that restores the claimant's reward if the remote deposit fails or is trapped, so state advancement stays atomic with actual settlement.

### Proof of Concept
1. Relayer accrues a `BridgeReward::Snowbridge` reward via `register_reward` (`bridges/modules/relayers/src/lib.rs`).
2. Relayer calls `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(location))` where `location` is a `Location` that AssetHub's account-conversion/asset-transactor logic cannot resolve to a valid, ED-satisfying account (e.g., a junction combination not covered by AssetHub's `LocationToAccountId`).
3. On BridgeHub: `do_claim_rewards` → `PayAccountOnLocation::pay_reward` succeeds (`validate_send`+`deliver` only), reward is deleted from `RelayerRewards`, `RewardPaid` event fires.
4. On AssetHub: the received XCM's `DepositAsset` instruction fails to credit the invalid beneficiary; assets are trapped via `AssetsTrapped` under the Snowbridge-descended origin, not the relayer.
5. The relayer has no `RelayerRewards` entry left to reclaim, and cannot itself issue `claim_assets` against the trap origin (it is not their account) — the reward is permanently lost, contradicting the emitted `RewardPaid` semantics.

			relayer: T::AccountId,
			reward_kind: T::Reward,
			beneficiary: BeneficiaryOf<T, I>,

			RelayerRewards::<T, I>::try_mutate_exists(

					let reward_balance =
						maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;

						reward_balance,

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
