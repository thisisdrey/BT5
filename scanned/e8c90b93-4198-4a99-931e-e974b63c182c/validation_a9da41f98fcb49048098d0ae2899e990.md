### Title
Silent fund-lock in `close_child_bounty`: native balance transfer failure is only `debug_assert!`-checked, permanently stranding funds after storage removal - (File: `substrate/frame/child-bounties/src/lib.rs`)

### Summary
The RAAC report's core defect is a public value-receiving entrypoint (`mint`) that pulls funds into a contract-controlled account with no code path to move them back out, permanently locking user funds. The local analog is `pallet-child-bounties`'s `impl_close_child_bounty`, which sweeps the child-bounty account's native balance back to the parent bounty account but only checks the outcome with `debug_assert!`, then unconditionally deletes the child-bounty storage entry regardless of whether the transfer actually succeeded.

### Finding Description
`impl_close_child_bounty` performs the balance sweep like this: [1](#0-0) 

```
// Transfer fund from child-bounty to parent bounty.
let parent_bounty_account = pallet_bounties::Pallet::<T>::bounty_account_id(parent_bounty_id);
let child_bounty_account = Self::child_bounty_account_id(parent_bounty_id, child_bounty_id);
let balance = T::Currency::free_balance(&child_bounty_account);
let transfer_result = T::Currency::transfer(
    &child_bounty_account,
    &parent_bounty_account,
    balance,
    AllowDeath,
); // Should not fail; child bounty account gets this balance during creation.
debug_assert!(transfer_result.is_ok());

// Remove the child-bounty description.
ChildBountyDescriptionsV1::<T>::remove(parent_bounty_id, child_bounty_id);

*maybe_child_bounty = None;
```

`debug_assert!` is a no-op in release/production builds (runtime builds are always compiled in release mode), so `transfer_result` is never actually checked in a live chain. The code comment itself concedes this is only an assumption ("Should not fail"), but the sibling `pallet-bounties::close_bounty` path was specifically hardened by [2](#0-1)  precisely because account references (e.g. held assets/consumer refs) can block a native balance transfer/account reap — the exact scenario shown by the test in `close_bounty_with_random_references_works` where mutating `sufficients`/`consumers`/`providers` on the pot account changes whether the transfer completes cleanly: [3](#0-2) 

The child-bounty account is a plain `AccountId` derived from `PalletId` — nothing prevents any third party from sending an asset, or otherwise creating account references (via `pallet-assets`, `pallet-nfts`, etc., if configured in the runtime) to the child-bounty sub-account, exactly like the `close_bounty_with_additional_assets_works` test demonstrates for the parent-bounty pot: [4](#0-3) 

If such references exist on the child-bounty account when `close_child_bounty`/`impl_close_child_bounty` runs, `T::Currency::transfer(..., AllowDeath)` can fail (e.g. `ExistenceRequirement`/reference-count related `DispatchError`). Unlike `pallet-bounties`, which received `reclaim_bounty_funds` as a permissionless recovery mechanism after the bounty is closed [5](#0-4)  and its `close_bounty` itself was hardened to reap assets before reaping balance [6](#0-5) , `pallet-child-bounties` has no equivalent recovery call and no `TransferAllAssets`-style sweep. When the transfer silently fails, `*maybe_child_bounty = None;` still executes unconditionally, deleting the only on-chain state referencing that funded sub-account. There is no dispatchable in `pallet-child-bounties` to retry or reclaim funds from an orphaned child-bounty account once its storage entry is gone — the value is permanently unreachable.

### Impact Explanation
This breaks the invariant that "balances, assets, and contract-held value must conserve value and settle exactly once to the rightful beneficiary." Funds funded into a child bounty (drawn from the treasury via the parent bounty) can become permanently stranded in an account with no bookkeeping and no recovery mechanism, a direct instance of the "permanent user-fund lock" impact class called out in scope. Because the funds originate from the treasury/parent-bounty allocation, this is a protocol-level fund loss, not merely user error.

### Likelihood Explanation
Triggering an account reference/consumer-count condition on the child-bounty sub-account requires only a signed extrinsic from an unprivileged account (e.g. an asset transfer to that well-known derived `AccountId`, since `child_bounty_account_id` is deterministically computed from `PalletId` + indices and is therefore publicly known/predictable) prior to the curator or `RejectOrigin` calling `close_child_bounty`. No collusion with a validator, node operator, or governance actor is required — the closing call itself is a standard permissioned-but-not-privileged operation (curator/parent curator/`RejectOrigin`), and the attack setup step (sending assets to a predictable account) needs no special privilege at all.

### Recommendation
- Propagate the `transfer_result` as a real `DispatchResult` error instead of `debug_assert!`, so `close_child_bounty` fails loudly (and does not delete the storage entry) when the sweep cannot complete.
- Before transferring the native balance, sweep/clear any asset balances or account references on the child-bounty account (mirroring `TransferAllAssets`/`reclaim_bounty_funds` added to `pallet-bounties`).
- Add a permissionless recovery extrinsic analogous to `pallet-bounties::reclaim_bounty_funds` for orphaned child-bounty accounts, so funds are not unrecoverable even if a future edge case reintroduces this class of bug.

### Proof of Concept
1. Create and fund a parent bounty; propose and accept a parent curator; add and accept a child bounty (as in `close_child_bounty_active` test setup) — the child bounty account (`ChildBounties::child_bounty_account_id(0, 0)`) is now funded with native balance and is a deterministically-derivable `AccountId`.
2. As an unprivileged third party, transfer a "sufficient" asset (via `pallet-assets::transfer` or an equivalent fungible/NFT pallet configured in the runtime) directly to `ChildBounties::child_bounty_account_id(0, 0)`, mirroring `close_bounty_with_additional_assets_works`'s Case 4/6 setups that create account references blocking cheap balance reaping.
3. Call `close_child_bounty(origin, 0, 0)` as the parent curator. In a release build, if the underlying `T::Currency::transfer(..., AllowDeath)` fails due to the account reference, the failure is swallowed (`debug_assert!` is compiled out), and `ChildBounties::<T>::remove` still executes via `*maybe_child_bounty = None;`.
4. Observe: the child-bounty storage entry is gone, but the native balance remains in `child_bounty_account_id(0, 0)`. There is no extrinsic in `pallet-child-bounties` to recover it, unlike `pallet-bounties::reclaim_bounty_funds` for the parent-level equivalent.

```rust
		///
		/// Permissionless. Moves all remaining assets from a closed bounty's account back to the
		/// treasury in a single call. Which assets are swept depends on the `TransferAllAssets`
		/// configuration.
		///
		/// The call is free if funds were reclaimed and paid otherwise, so no-op calls cannot be
		/// used to grief the network. Emits `BountyFundsReclaimed` on success.
		///
		/// ## Complexity
		/// - O(A) where A is the number of relevant assets configured in `TransferAllAssets`.
		#[pallet::call_index(11)]
		#[pallet::weight(<T as Config<I>>::WeightInfo::reclaim_bounty_funds())]
		pub fn reclaim_bounty_funds(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
		) -> DispatchResultWithPostInfo {
			ensure_signed(origin)?;

			// A live bounty still manages its account, so leave it untouched.
			ensure!(!Bounties::<T, I>::contains_key(bounty_id), Error::<T, I>::BountyStillActive);

			debug_assert!(
				T::ChildBountyManager::child_bounties_count(bounty_id) == 0,
				"child bounties should not exist for a closed bounty"
			);

			let bounty_account = Self::bounty_account_id(bounty_id);
			let treasury_account = Self::account_id();

			let transferred = T::TransferAllAssets::force_transfer_all_assets(
				&bounty_account,
				&treasury_account,
			)?;

			// Free only if something moved, otherwise paid to prevent griefing.
			if !transferred {
				return Ok(Pays::Yes.into());
			}

			Self::deposit_event(Event::<T, I>::BountyFundsReclaimed { bounty_id });

			Ok(Pays::No.into())
		}
```
