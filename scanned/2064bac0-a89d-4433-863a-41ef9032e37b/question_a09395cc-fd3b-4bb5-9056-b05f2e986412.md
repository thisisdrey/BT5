[Target: DepositAction::Execute(ExecuteIntents{execute_intents, refund_if_fails: false})] Attacker crafts `msg` for `nft_on_transfer` as `DepositMessage{receiver_id: attacker, action: Some(DepositAction::Execute(ExecuteIntents{execute_intents: [malicious_payload], refund_if_fails: false}))}`. Preconditions: `refund_if_fails=false` so `ext_intents::ext(current_account_id()).execute_intents(execute_intents).detach()` is fired-and-forgotten without any linkage back to the deposit outcome. Call sequence: `nft_on_transfer` credits the NFT to `receiver_id` synchronously via `self.deposit`, returns `PromiseOrValue::Value(false)` (meaning 'not returned to sender', i.e. transfer accepted) to the NFT contract while `execute_intents` detached-promise runs concurrently and may fail or be exploited to move the just-deposited NFT via `TokenDiff`/`Transfer` before any invariant check ties back to this deposit. Binding: the deposited asset a `TokenId::Nep171(...)` names == the asset actually available to move in the detached `execute_intents`, and settlement value debited == value delivered, i.e. `nft_deposit_credited == balance_available_to(execute_intents)` at time of detached execution regardless of ordering. Scoped impact: Critical, since detach() means no atomicity guarantee links the deposit acceptance to the detached execute_intents outcome, letting an attacker construct a race where they claim the NFT is deposited (returning `false`/accepted) yet the follow-on intents can already move it out concurrently in the same or subsequent block, allowing a version of double count if combined with any other re-entrant path. Proof idea: cargo test sandbox depositing an NFT with Execute+refund_if_fails=false containing an intent that immediately withdraws the just-deposited token_id, verifying the NFT can be withdrawn even though `nft_on_transfer`'s outer receipt has not yet confirmed the deposit acceptance to the origin NFT contract.
