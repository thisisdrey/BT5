`ConnectionInbox::consume_payload_known_length` (stackslib/src/net/connection.rs) calls `self.buf.get(self.message_ptr..)` and `.ok_or_else(RecvError)` for bounds, but then does `next_message_ptr = self.message_ptr.checked_add(message_len)` followed by `self.buf.get(next_message_ptr..)`. Given `message_len` originates from `protocol.read_payload`'s returned consumed length rather than the wire-declared `payload_len`, can a remote peer craft a payload whose `read_payload` implementation reports a `message_len` inconsistent with `preamble.payload_len` (i.e. the equality 'bytes consumed == preamble-declared payload length' is broken), causing `next_message_ptr` to point mid-message and silently splice unrelated bytes into the next parsed message header, effectively smuggling attacker payload across message boundaries? Preconditions: open P2P port, one established connection with a known public key (post-handshake) so `verify_payload_bytes` passes. Call sequence: `consume_payload` -> `consume_payload_known_length` -> `protocol.read_payload`. Impact: Critical, request/message smuggling within the P2P framing layer, letting a byte sequence signed for one message boundary be reinterpreted as a different message. Proof idea: Rust test constructing a `Preamble.payload_len` and a payload where the deserializer intentionally consumes fewer bytes than `payload_len`, asserting the leftover bytes are mis-parsed as the start of the *next* message rather than rejected.
