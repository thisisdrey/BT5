`NetworkConnection::is_solicited` and `fulfill_request` (stackslib/src/net/connection.rs) match an inbound `P::Message` to a pending `ReceiverNotify<P>` purely via `inflight.expected_seq == msg.request_id()`, i.e. the 32-bit `Preamble.seq` field, with no check that the message came from the same authenticated peer that was sent the original request. Can a remote peer that guesses or brute-forces a live `expected_seq` value inject a forged reply that `fulfill_request` treats as solicited, closing the equality 'message delivered to waiting receiver == reply from the peer the request was sent to' as false? Preconditions: attacker is the connected peer on this `ConversationP2P`, `outbox.inflight` has an outstanding `ReceiverNotify` for some `seq`. Call sequence: `drain_inbox` -> `fulfill_request` -> `ReceiverNotify::send`. Impact: Critical, forged data (e.g. a bogus `HandshakeAccept`, `BlocksInvData`, or `StackerDBChunk` reply) is delivered to a state machine that trusts it as the genuine response to its outbound request. Proof idea: Rust test in `stackslib::net::connection` that queues a request via `make_request_handle(seq, ...)`, then calls `fulfill_request` with a `P::Message` whose `request_id()==seq` but whose payload is attacker-controlled garbage, and asserts the handle's receiver gets it despite no sender-identity check.
