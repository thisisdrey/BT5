`ConnectionInbox::consume_payload_unknown_length` (stackslib/src/net/connection.rs) calls `protocol.stream_payload(preamble, &mut to_buffer)` and then does `self.payload_ptr.checked_add(bytes_consumed)`, followed by `self.buf.get(next_message_ptr..)`. For `StacksHttp`, whose messages ARE of unknown length until headers parse, can a remote HTTP client send a request whose `Content-Length` header disagrees with the number of bytes `stream_payload` actually consumes, so that `next_message_ptr` (`= self.payload_ptr`) does not equal the attacker-declared `Content-Length`, breaking the equality 'bytes read for the message body == declared Content-Length' and leaving residual attacker bytes in `self.buf` to be reinterpreted as the start of the next HTTP request (request smuggling)? Preconditions: open RPC HTTP port, no auth needed for the smuggling primitive itself. Call sequence: `recv_bytes` -> `consume_messages` -> `consume_payload` -> `consume_payload_unknown_length`. Impact: Critical, HTTP request smuggling across the shared `NetworkConnection<StacksHttp>` buffer. Proof idea: Rust test feeding two concatenated pipelined HTTP requests where the first declares a `Content-Length` shorter than what `stream_payload` consumes, asserting the second 'request' is corrupted/misrouted rather than parsed as a clean independent request.
