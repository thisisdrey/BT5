In `StacksMessage::sign_relay` (stackslib/src/net/codec.rs), a malicious relayer forwards a message where it has added itself as a `RelayData` entry with `peer.public_key_hash` equal to the *original sender's* `public_key_hash` rather than its own, exploiting the fact that `sign_relay`'s dedup-by-hash loop (`relayer.peer.public_key_hash == our_addr.public_key_hash`) only runs on the honest relayer's own re-signs, not on attacker-constructed relay chains received directly off the wire. Preconditions: attacker runs its own peer and receives a legitimately signed message to relay onward. Call sequence: attacker rewrites `relayers: Vec<RelayData>` before re-serializing and re-signing with its own key via `do_sign`; downstream relay-loop-detection logic that trusts `RelayData.peer.public_key_hash` to identify prior hops is fed forged hashes. Equality: the `public_key_hash` recorded in each `RelayData` entry must equal the actual peer that signed at that hop; show the codec provides no binding between a `RelayData` entry's claimed hash and any signature, since only the outermost `preamble.signature` is checked via `verify_secp256k1`. Impact: Critical, network-wide propagation with forged relay provenance (defeats loop/relay-cycle detection, enabling amplification). Proof idea: `stackslib::net` test constructing a `StacksMessage` with fabricated `relayers` entries not matching any real signer, asserting the codec/`verify_secp256k1` layer accepts it since only the preamble signature is checked, not per-hop relay authenticity.
