## Title
`thaw_communal` burns fungible counterpart tokens before checking whether the payout transfer succeeds, and `privatize` burns the full counterpart amount even when the owed balance is capped by pot funds — value destroyed without guaranteed settlement (`File: substrate/frame/nis/src/lib.rs`)

### Summary
`pallet-nis` mirrors the exact broken invariant from the Illuminate report: a fungible "counterpart" token is burned to redeem a proportional share of pooled value, but the amount actually paid out is computed/capped independently of the burn, and the burn happens even when the payout can fail or be short-paid.

### Finding Description
In `thaw_communal` (`substrate/frame/nis/src/lib.rs:765-813`):
1. `T::Counterpart::burn_from(&who, cp_amount, ...)` is executed at line 792, unconditionally destroying the user's full counterpart balance for the receipt's proportion.
2. Only *after* the burn does the code compute `amount = receipt.proportion * effective_issuance` (line 797) and attempt `T::Currency::transfer(&our_account, &who, amount, Expendable)` (line 802).
3. If the transfer fails (`Error::<T>::Unfunded`, e.g., the pot account genuinely lacks `amount` free/expendable balance), the extrinsic returns `Err`, but this is a normal FRAME dispatch — if this call is ever reached through a context where the burn is not rolled back atomically with the error (e.g. any wrapping code that does not treat the whole call as transactional, or future refactors that split burn and transfer across different storage-mutating helpers), the user's tokens are gone with no receipt payout. Even within transactional dispatch, this ordering is fragile: the burn is performed as a side effect before the fallible operation that is supposed to justify it, which is precisely the anti-pattern flagged in the Illuminate finding ("burns the token in exchange for zero/less than expected").

`privatize` (lines 853-900) is worse: it explicitly clamps the payout to available funds — `let amount = max_amount.min(T::Currency::balance(&our_account));` (line 875) — while burning the *fixed*, uncapped counterpart amount derived from `receipt.proportion` at line 878-884: `T::Counterpart::burn_from(&who, T::CounterpartAmount::convert(receipt.proportion), ...)`. The burn quantity is **not** derived from `amount` (the capped, actually-transferred value); it's derived from `receipt.proportion`, which represents the *uncapped* entitlement. If the pot (`our_account`) balance is less than `max_amount` — which the code itself anticipates by clamping — the user burns counterpart tokens sized for the full proportion but receives (via hold) only the reduced `amount`. This is the same broken invariant as the Illuminate `redeem`: burn quantity and payout quantity are decoupled, and the payout can silently be less than what the burn represents.

### Impact Explanation
A user calling `privatize` when the NIS pot is under-funded relative to the receipt's proportional claim on `effective_issuance` burns the full counterpart-token entitlement but is held only the reduced, pot-limited amount — permanently losing the difference. This is a direct token/fund loss for an unprivileged, ordinary user performing a normal, documented operation (`privatize`), matching the "theft or unbacked mint/unlock" and "permanent user-fund lock" impact categories: the burn is irreversible while the corresponding value transfer is capped independently.

### Likelihood Explanation
This requires no malicious actor, governance action, or privileged party — only that the NIS pot account's free balance be less than the aggregate `effective_issuance`-derived claim at the moment `privatize` is called, which the pallet's own code anticipates (via the `.min()` clamp) and documents (`IssuanceInfo::required` field explicitly tracks the case where `required > holdings`, i.e., "the pallet will need funding" — see `substrate/frame/nis/src/lib.rs:914-916`). Any ordinary sequence of consolidations/thaws/privatizations that drains the pot below full backing turns this from theoretical into directly reachable by any receipt holder calling `privatize`.

### Recommendation
In `privatize`, compute the counterpart burn amount from the same capped `amount` value that is actually transferred/held, not from the uncapped `receipt.proportion`. If a partial burn/partial-receipt-retention model is needed, split the receipt's proportion into a "redeemed" portion sized to `amount` and leave the remainder as an outstanding receipt/counterpart claim, so the burn always exactly matches what the user received. In `thaw_communal`, reorder operations so the currency transfer (or a reservation/hold of the funds) is confirmed to succeed before burning the counterpart tokens, or perform both operations inside a single atomic step where a transfer failure guarantees the burn is reverted, and add an explicit invariant check that burn amount == settled amount.

### Proof of Concept
Conceptual sequence (mirrors the Illuminate PoC structure):
1. Multiple receipts are consolidated over time, and the pot (`Nis::account_id()`) balance is drawn down via prior `thaw`/`thaw_communal` calls until `T::Currency::balance(&our_account) < required` (a state the pallet's own `issuance_with().required` field is designed to detect).
2. A user holding a communal receipt calls `privatize(index)`.
3. `max_amount = receipt.proportion * effective_issuance` is computed; `amount = max_amount.min(pot_balance)` yields `amount < max_amount`.
4. `T::Counterpart::burn_from(&who, T::CounterpartAmount::convert(receipt.proportion), ...)` burns the counterpart tokens sized to the **full** `receipt.proportion` (i.e., corresponding to `max_amount`), not to `amount`.
5. `T::Currency::transfer_and_hold(..., amount, ...)` only holds the reduced `amount` for the user.
6. Net result: user's counterpart-token balance decreases by the full entitlement, but the funds placed on hold for them are only `amount < max_amount` — the difference is permanently lost, with no error raised (the call succeeds). [1](#0-0) [2](#0-1) [3](#0-2)

		#[pallet::call_index(4)]
		#[pallet::weight(T::WeightInfo::thaw_communal())]
		pub fn thaw_communal(
			origin: OriginFor<T>,
			#[pallet::compact] index: ReceiptIndex,
		) -> DispatchResult {
			let who = ensure_signed(origin)?;

			// Look for `index`
			let receipt: ReceiptRecordOf<T> =
				Receipts::<T>::get(index).ok_or(Error::<T>::UnknownReceipt)?;
			// If found, check it is actually communal.
			ensure!(receipt.owner.is_none(), Error::<T>::NotOwner);
			let now = frame_system::Pallet::<T>::block_number();
			ensure!(now >= receipt.expiry, Error::<T>::NotExpired);

			let mut summary: SummaryRecordOf<T> = Summary::<T>::get();

			let (throttle, throttle_period) = T::ThawThrottle::get();
			if now.saturating_sub(summary.last_period) >= throttle_period {
				summary.thawed = Zero::zero();
				summary.last_period = now;
			}
			summary.thawed.saturating_accrue(receipt.proportion);
			ensure!(summary.thawed <= throttle, Error::<T>::Throttled);

			let cp_amount = T::CounterpartAmount::convert(receipt.proportion);
			T::Counterpart::burn_from(&who, cp_amount, Expendable, Exact, Polite)?;

			// Multiply the proportion it is by the total issued.
			let our_account = Self::account_id();
			let effective_issuance = Self::issuance_with(&our_account, &summary).effective;
			let amount = receipt.proportion * effective_issuance;

			summary.proportion_owed.saturating_reduce(receipt.proportion);

			// Try to transfer amount owed from pot to receipt owner.
			T::Currency::transfer(&our_account, &who, amount, Expendable)
				.map_err(|_| Error::<T>::Unfunded)?;

			Receipts::<T>::remove(index);
			Summary::<T>::put(&summary);

			let e =
				Event::Thawed { index, who, amount, proportion: receipt.proportion, dropped: true };
			Self::deposit_event(e);

			Ok(())
		}
