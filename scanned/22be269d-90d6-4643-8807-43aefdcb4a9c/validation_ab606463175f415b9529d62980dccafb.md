Based on my investigation, I found a structurally similar analog in the Snowbridge system-v2 pallet, but I was not able to fully verify the AssetHub-side `system-frontend` pallet's binding of the `sender` parameter before running out of tool budget. I'll present the finding with that caveat explicitly noted.

### Title
`register_token` in `snowbridge-system-v2` trusts a caller-supplied `sender` location for message-origin attribution instead of binding it to the authenticated XCM origin - ([File: bridges/snowbridge/pallets/system-v2/src/lib.rs])

### Summary
The external report's core flaw is a mismatch between the *documented* caller binding (must originate from a specific counterpart chain/account) and the *enforced* check (a broad, unrelated authorization), letting the wrong party's identity leak into a privileged downstream action. The same broken-invariant class appears in `snowbridge_system_v2::Pallet::register_token`: the extrinsic is guarded only by `T::FrontendOrigin::ensure_origin(origin)` [1](#0-0) , which — per the mock configuration — only checks that the XCM origin equals one fixed aggregate `Location` representing "the frontend pallet instance on AssetHub" [2](#0-1) . The actual per-caller identity used to build the outbound message's `origin` field is taken from a fully attacker/caller-supplied extrinsic parameter, `sender: Box<VersionedLocation>` [3](#0-2) , with no code path re-deriving or validating it against the real dispatching account.

### Finding Description
`register_token`'s doc comment states the intended calling model explicitly: "The system frontend pallet on AH proxies this call to BH" and "`sender`: The original sender initiating the call on AH" [4](#0-3) . This is the same pattern as the report's NatSpec claim ("called from L2") describing an intended caller binding that the code should — but does not — cryptographically enforce.

In the implementation, the only authorization check performed is:
```rust
T::FrontendOrigin::ensure_origin(origin)?;
```
which verifies the *channel* (that the call arrived via XCM from the fixed frontend pallet instance location on AssetHub), not the *individual sender* [5](#0-4) . The pallet then unconditionally trusts the `sender` parameter to compute the message origin that gets embedded in the command sent to Ethereum:
```rust
let message_origin = Self::location_to_message_origin(sender_location)?;
Self::send(message_origin, command, amount)?;
``` [6](#0-5) 

This `origin: H256` field is not cosmetic — it becomes the `Message.origin` sent to the Ethereum Gateway [7](#0-6) , which the wider system design uses as an agent/channel identity to scope authority (see the sibling v1 system pallet's agent model, where each `agent_id` maps to a distinct authorized `Location`) [8](#0-7) . Because `FrontendOrigin` authorizes at the granularity of "any message from the frontend pallet instance on AssetHub" rather than "this specific caller," the code has no way to distinguish which AssetHub account actually invoked the flow — exactly the gap the external report flags (checked modifier is broader/different than the documented caller scope).

I was not able to fully trace, within the available tool budget, whether `pallet-system-frontend` on the AssetHub side (`bridges/snowbridge/pallets/system-frontend/src/lib.rs`) independently derives and locks `sender` to the true dispatch origin before constructing the Transact call to BridgeHub. That file exists in the repo but its contents were not retrieved before the iteration limit. This is the missing link required to determine definitively whether this is fully exploitable end-to-end or whether the AH-side pallet closes the gap.

### Impact Explanation
If the AssetHub-side `system-frontend` pallet does not strictly bind `sender` to the actual dispatch origin (e.g., if it forwards a user-supplied `Location` rather than deriving it from `ensure_signed`/XCM descend), an unprivileged AssetHub account could register a foreign token attributing an arbitrary `sender` identity to the resulting `RegisterForeignToken` command sent to Ethereum. Depending on how the Ethereum Gateway or agent-authority model consumes this `origin`, this could misattribute fee liability, reward crediting, or execution authority to an unrelated party — a violation of the "bind ... origin exactly once" pivot for message/delivery flows.

### Likelihood Explanation
Likelihood is uncertain without confirming the AssetHub-side pallet's sender-binding logic. The BridgeHub-side pallet itself performs no independent validation of `sender`, so the entire security property rests on code outside the file reviewed here. This significantly limits confidence that this is independently, locally exploitable purely from `system-v2`.

### Recommendation
- Confirm (or add) that `snowbridge_system_v2::register_token` derives `sender`/`message_origin` cryptographically from the authenticated XCM origin (e.g., via `DescendOrigin` reflecting the real AssetHub caller) rather than accepting it as a free-form call parameter.
- Audit `pallet-system-frontend` on AssetHub to ensure it fixes/locks the `sender` location to `ensure_signed(origin)` (reanchored) before dispatching the Transact to BridgeHub, and cannot be parameterized by the caller.
- Add a runtime/pallet-level invariant test asserting that `register_token`'s resulting `Message.origin` always equals a location derivable from the actual XCM origin, never from unchecked call data.

### Proof of Concept
Cannot be fully constructed without confirming the AssetHub-side `system-frontend` pallet's handling of `sender`. The demonstrable local defect is: in `bridges/snowbridge/pallets/system-v2/src/lib.rs::register_token`, replacing `sender` with any `VersionedLocation` value in a unit test (using the existing `EnsureXcm<AllowFromAssetHub>` mock and any origin satisfying `FrontendLocation`) allows the resulting `Message.origin` to be set to an arbitrary location's derived `H256`, independent of which underlying account triggered the call — see `tests.rs`/`mock.rs` harness for the pallet [9](#0-8) .
