[postblock_v3.rs::RPCPostBlockRequestHandler::try_parse_request] Attacker crafts a raw HTTP request line `POST /v3/blocks/upload/?broadcast=1&broadcast=0 HTTP/1.1` with a valid `authorization` header equal to a *guessed wrong* value, or omits the header while `broadcast=1` appears twice with conflicting values. Preconditions: `self.auth=Some(password)` configured. Call sequence: the loop `for (key,value) in form_urlencoded::parse(...) { if key==\"broadcast\" { broadcast = broadcast || value==\"1\" } }` at line 114-118 OR's every occurrence, so a single `broadcast=1` anywhere in a repeated-key query string sets `broadcast=true` even if a later `broadcast=0` is intended by the operator's proxy-layer expectations. Equality broken: `handler.broadcast` (used to decide whether to call `Relayer::process_new_nakamoto_block_ext` with a relay flag and whether `node.set_relay_message` propagates the block network-wide) must equal the *last* or *sole* value the operator's WAF thinks it stripped; with OR semantics an attacker who can inject a duplicate query key downstream of any header-stripping proxy can force `broadcast=true` even when authentication was expected to gate it off, or force `broadcast=false` where the operator's proxy only forwarded `broadcast=1` as the last key. Impact: Critical, request-smuggling style auth-bypass on a gated relay path. Proof idea: Rust test crafting a preamble query string `\"broadcast=0&broadcast=1\"` with no authorization header, asserting `try_parse_request` returns 401 (broadcast true) versus a proxy that only sees the first `broadcast=0` and assumes it is safe to forward.
