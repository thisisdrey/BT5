# [M] M-1 Expired proposals can be executed

## Summary
Severity: Medium
Contest weight: 0.0254
Dataset id: 9555
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability is a logic flaw in the governance execution contract that allows a proposal that has already passed its deadline to be executed if the global _gracePeriod variable is modified after the proposal was created. The contract checks proposal expiry by comparing the current block timestamp against the proposal’s start time plus the current _gracePeriod value. Because _gracePeriod is stored as a mutable state variable, any later update to this parameter retroactively extends the execution window of all previously created proposals. Consequently, an attacker who can trigger a change to _gracePeriod – for example through another governance action – can wait until a proposal expires, increase the grace period, and then call the execute function to run the proposal’s payload. This defeats the intended safety guarantee that expired proposals are immutable and should never be executable. The impact is that stale or malicious proposals may be executed, potentially altering protocol parameters, moving funds, or performing other privileged actions that were assumed to be blocked after expiry. The issue manifests only when a proposal is marked expired and the _gracePeriod is subsequently altered before an execution attempt, a condition that may be rare but is feasible in a system where governance can modify timing parameters. All participants who rely on the governance process – token holders, protocol users, and developers – are affected because the integrity of the decision‑making timeline is compromised. The flaw was discovered during a manual code review by the MixBytes audit team, who noticed that the expiration check references a mutable variable rather than a value captured at proposal creation. The bug is subtle because the contract still enforces a time window, and typical tests may only cover the happy path where _gracePeriod remains constant, making the vulnerability easy to overlook. To remediate, the contract should store the grace period value as part of each proposal’s immutable data at the moment of creation, or otherwise make the parameter read‑only for the lifetime of the proposal. By using a fixed per‑proposal grace period, later changes to the global setting cannot retroactively reopen execution windows, restoring the intended security property that expired proposals are permanently inert. This class of issue belongs to the broader category of “mutable time‑window parameters” or “expiration logic tampering”, where a contract’s time‑based access control can be altered after the fact, leading to unexpected execution of stale actions and breaking accounting assumptions about when actions are allowed.

## Recommendation
We recommend saving _gracePeriod as a parameter of the action, so the parameter updates will not affect the protocol.
