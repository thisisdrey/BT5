### Title
Unprotected AMM swap (no minimum-output/slippage check) lets an attacker drain the Ether/asset pool via `add_tip`/`register_token` fee-swap path - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

### Summary
The Pyth report's core defect is: a value with an inherent uncertainty bound (the confidence interval) is consumed with no sanity check against that bound, letting an attacker exploit a momentarily-wrong price. The local analog is `Pallet::swap_and_burn` in the Snowbridge `system-frontend` pallet, which converts a user-supplied "tip"/fee asset into Ether through `pallet_asset_conversion`'s AMM via `T::Swap::swap_exact_tokens_for_tokens`, passing `None` as the minimum-output bound. Just as the report's protocol ignored `σ/p` before trusting the oracle price, this code ignores any bound on the AMM's instantaneous spot price before trusting the swap output and burning/forwarding it as a reward amount.

### Finding Description
`add_tip` and `register_token` (non-root path) both call `Self::swap_fee_asset_and_burn`, which calls `Self::swap_and_burn`: [1](#0-0) 

The swap is executed with `min_amount_out = None` — "No minimum amount required" — meaning the pallet accepts whatever exchange rate the AMM pool happens to report at execution time, with no check that the rate is within any expected/sane bound (analogous to Pyth's confidence-interval sanity check that the Ampera team added: "making sure the Confidence Interval is smaller than the price"). The resulting `ether_gained` is:
- burned via `burn_for_teleport` for real value transfer, and
- forwarded as the `amount` field in `EthereumSystemCall::AddTip` / `RegisterToken` calls that are `Transact`-ed to BridgeHub, ultimately increasing a relayer reward or the register-token deposit: [2](#0-1) [3](#0-2) 

`add_tip` is callable by any signed account with no privilege requirement: [2](#0-1) 

The `pallet_asset_conversion` AMM pool referenced by `T::Swap` (e.g. the WND/DOT–WETH pools set up for Ether fee payment) is a normal, publicly-tradable liquidity pool that any account can swap against, so an unprivileged actor can move its spot price within the same block/transaction sequence (self-sandwich) before invoking `add_tip`, extract an inflated `ether_gained` for a fixed, small `tip_amount` of the fee asset, and then reverse the price move — extracting real Ether from the pool's reserves at the LPs' expense, funded by the AMM's ETH liquidity rather than by the attacker's tip.

### Impact Explanation
This falls squarely within "public underpriced work" / "theft or unbacked mint or unlock" and value-conservation guarantees for bridge reward and pool state: the AMM-derived Ether amount used to fund relayer rewards / registration deposits is not bounded by any sanity check, so it can be manipulated to extract more real value (burned Ether, ultimately debited from a public liquidity pool) than the tip asset is actually worth. This can drain liquidity-provider funds in the ETH/asset pool and inflate relayer rewards / register-token deposits recorded cross-chain on BridgeHub, without needing a malicious relayer, validator, or governance actor — only an unprivileged user manipulating a public AMM pool they can freely trade against.

### Likelihood Explanation
The path requires only a signed account and access to the public `pallet_asset_conversion` pool (no special permissions, no off-chain assumptions). AMM price-manipulation ("self-sandwich") attacks are a well-known and cheap primitive when a swap has no minimum-output/slippage protection, especially against thinly-liquidated bridge fee pools. The `None` minimum-amount value is an explicit, code-visible omission rather than a latent computational bug, making exploitation straightforward once a suitable (e.g. low-liquidity) pool exists.

### Recommendation
Apply the confidence-interval-style sanity check that the Pyth fix used: require `swap_and_burn` to pass a computed `min_amount_out` (e.g. derived from a recent TWAP, a configurable maximum slippage/tolerance parameter, or a governance-set floor rate) to `swap_exact_tokens_for_tokens` instead of `None`, and reject the tip/registration if the realized swap output deviates too far from the expected rate. Additionally consider bounding the tip/registration amount relative to pool depth to prevent one-block price manipulation from dominating the swap outcome.

### Proof of Concept
1. Attacker identifies (or helps create) an under-liquidated `pallet_asset_conversion` pool between a fee asset `X` and Ether (the pool referenced by `T::Swap` in `system-frontend`'s `Config`).
2. In one transaction (or atomically batched calls), the attacker:
   a. Swaps a large amount of `X` into the pool to skew the spot price of `X` in Ether's favor.
   b. Calls `add_tip(message_id, Asset{ id: X, amount: small_tip })`, which invokes `swap_and_burn` → `T::Swap::swap_exact_tokens_for_tokens(..., min_amount_out = None, ...)`, letting the manipulated pool report inflated Ether output for `small_tip`.
   c. Reverses step (a) by swapping back, restoring the price and recovering most of the capital used to manipulate it.
3. The inflated `ether_gained` from step (b) is burned via `burn_for_teleport` and forwarded on-chain (BridgeHub) as the tip/reward amount, net-draining real Ether from the pool's reserves while the attacker's actual cost is only the small tip plus manipulation slippage/fees, which round-trip arbitrage keeps low if the pool is thin relative to the manipulation size. 		fn swap_and_burn(
			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether
			let ether_asset = Asset::from((ether_location.clone(), ether_gained));

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}
