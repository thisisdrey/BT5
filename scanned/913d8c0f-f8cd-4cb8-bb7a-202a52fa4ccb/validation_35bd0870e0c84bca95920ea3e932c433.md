### Title
Silent transfer-failure swallowing via `debug_assert!` in `claim_child_bounty` permanently locks child-bounty funds - (File: `substrate/frame/child-bounties/src/lib.rs`)

### Summary
`Pallet::claim_child_bounty` pays out the curator fee and beneficiary payout using `T::Currency::transfer(..., AllowDeath)` and only checks the result with `debug_assert!`, which is compiled out in release/production builds. If either transfer fails (e.g. the destination is a new account and the amount is below the existential deposit), the error is silently discarded, yet the extrinsic still emits a `Claimed` event, decrements `ParentChildBounties`, and deletes the child-bounty storage entry as if payment had succeeded.

### Finding Description
In `claim_child_bounty`, `curator_fee` and `payout` are computed from the child-bounty account's free balance and then transferred with `AllowDeath`: [1](#0-0) 

Both transfer results are only validated via `debug_assert!`, which is a no-op unless `debug_assertions` is enabled (not the case in a production runtime build). `pallet-balances`'s `Currency::transfer` returns `TokenError::BelowMinimum`/`Error::ExistentialDeposit` when the destination does not already exist and would receive less than the configured `ExistentialDeposit`, as directly demonstrated in the balances pallet's own tests: [2](#0-1) 

Because the curator fee and beneficiary amount are arbitrary values set when the child-bounty curator was proposed/accepted (`fee`) and computed as `balance - fee` (`payout`), either amount can legitimately be smaller than the chain's `ExistentialDeposit`. Any signed account can trigger `claim_child_bounty` once the bounty is `PendingPayout`, so an attacker (or ordinary user with a small child-bounty fee/payout and a fresh, non-existent recipient account) can cause one or both transfers to fail while the surrounding logic proceeds unconditionally: `Self::deposit_event(Event::<T>::Claimed { ... })` fires, `ParentChildBounties` is decremented, `ChildBountyDescriptionsV1` is removed, and `*maybe_child_bounty = None` deletes the entry — all irreversibly.

### Impact Explanation
Once the child-bounty entry is removed from storage, there is no retry path: the funds remain stranded in the child-bounty's sub-account (`Self::child_bounty_account_id`), which is no longer referenced by any live bounty index. Unlike `pallet-bounties`, which has since gained a `reclaim_bounty_funds` recovery mechanism (seen in `substrate/frame/bounties/src/tests.rs`), `pallet-child-bounties` has no equivalent recovery call, meaning funds can be permanently locked. This directly matches the "permanent user-fund lock" and "public underpriced/false-state-acceptance" impact classes: the chain state falsely records payout as complete (event emitted, storage cleared) while the actual currency movement silently failed.

### Likelihood Explanation
No privileged actor is required. `claim_child_bounty` origin is any `ensure_signed` account. The failure condition depends only on the curator fee or remaining payout being below the runtime's `ExistentialDeposit` for a not-yet-existing destination account, a configuration that is easily reachable through normal curator-fee proposal flow (`propose_curator`) with a small fee, or a beneficiary chosen to be a brand-new account. Production Substrate/Polkadot-SDK runtime builds compile without `debug_assertions`, so the `debug_assert!` guard provides zero protection at runtime.

### Recommendation
Replace `debug_assert!(fee_transfer_result.is_ok())` / `debug_assert!(payout_transfer_result.is_ok())` with proper error propagation (`?`) or explicit handling that aborts the storage mutation (so `try_mutate_exists` returns an `Err` and no state change is committed) if either transfer fails — analogous to the SafeERC20 principle of never proceeding on an unchecked/ignored transfer result. Alternatively, follow the same pattern the `bounties` pallet later added (`reclaim_bounty_funds`) so stranded child-bounty funds can be recovered even if the original claim silently fails.

### Proof of Concept
1. Configure a runtime with `ExistentialDeposit = E > 0` and build in release mode (`debug_assertions` disabled, the normal production configuration).
2. Create a parent bounty, add a child bounty, propose/accept a curator with `fee < E`, and award the child bounty to a beneficiary account that has never held a balance (so it does not exist in `System`).
3. Ensure the child-bounty sub-account's balance minus `fee` (the `payout`) is also `< E`, or arrange `fee` itself `< E` for the curator's fresh account.
4. Call `claim_child_bounty` once `unlock_at` has passed. `T::Currency::transfer(&child_bounty_account, curator, curator_fee, AllowDeath)` returns `Err(TokenError::BelowMinimum)` (per `substrate/frame/balances/src/tests/dispatchable_tests.rs:31-45`), which is swallowed by `debug_assert!` in a release build.
5. Observe: `Event::Claimed` is emitted with the full `payout`, `ChildBounties` entry is deleted, `ParentChildBounties` count decremented — but the curator/beneficiary balance was never actually credited, and the funds remain locked in the now-orphaned `child_bounty_account_id`.
