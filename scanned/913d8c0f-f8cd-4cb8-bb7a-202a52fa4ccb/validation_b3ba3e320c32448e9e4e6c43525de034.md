### Title
Bounty payouts silently fail and are marked complete via no-op `debug_assert!`, permanently trapping user funds - (File: `substrate/frame/bounties/src/lib.rs`)

### Summary
`pallet_bounties::claim_bounty` (and the identical pattern in `pallet_child_bounties::claim_child_bounty` and `pallet_tips::payout_tip`) performs the beneficiary/curator payout via `T::Currency::transfer(...)` and checks the result only with `debug_assert!(res.is_ok())`. In a release build `debug_assert!` compiles to nothing, so if the transfer actually fails, execution proceeds exactly as if the payment had succeeded: the bounty record is deleted, the event is emitted claiming the payout happened, and the beneficiary never receives their funds. This is the same class of bug as the reported Solidity issue — a value-transferring low-level call whose failure/return value is not actually enforced, leading to loss of funds for the intended recipient.

### Finding Description
In `claim_bounty`: [1](#0-0) 

```rust
ensure_signed(origin)?; // anyone can trigger claim
...
let res = T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath); // should not fail
debug_assert!(res.is_ok());
let res = T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath); // should not fail
debug_assert!(res.is_ok());

*maybe_bounty = None;
...
Self::deposit_event(Event::<T, I>::BountyClaimed { index: bounty_id, payout, beneficiary });
```

`debug_assert!` is a `cfg(debug_assertions)` gated macro — in a production runtime built with `--release` (the only way a real chain runs), the macro expands to nothing. The `Result` returned by `T::Currency::transfer` is discarded (`let res = ...` is never checked with `?` or `ensure!`). If the transfer fails for any reason — most concretely because the payout amount to the `beneficiary` account is smaller than the chain's `ExistentialDeposit` and that account does not yet exist (a very common, unprivileged, and non-malicious scenario for a beneficiary that has never held a balance) — the function still:
1. Sets `*maybe_bounty = None`, deleting the on-chain bounty record.
2. Removes `BountyDescriptions`.
3. Emits `Event::BountyClaimed` with the `payout` amount, telling observers the payment succeeded.

The exact same non-enforced pattern recurs in:
- `pallet_child_bounties::claim_child_bounty` (curator fee transfer and beneficiary payout transfer both use `debug_assert!`). [2](#0-1) 
- `pallet_child_bounties::impl_close_child_bounty` (fund return to parent bounty account). [3](#0-2) 
- `pallet_tips::payout_tip` (finder's fee and tip payout). [4](#0-3) 

None of these paths check the `Result` returned by `T::Currency::transfer`; they all rely on the comment "should not fail"/"best-effort" plus a `debug_assert!` that provides zero protection in production.

### Impact Explanation
Once the transfer silently fails but the bounty/child-bounty/tip accounting is finalized (record removed, curator deposit unreserved, event emitted as successful), the funds remaining in the bounty/child-bounty pot account (a deterministic `PalletId`-derived sub-account, e.g. `Self::bounty_account_id(bounty_id)`) become unreachable through any pallet extrinsic: there is no bounty entry left to re-trigger `claim_bounty`, and no other extrinsic sweeps stranded bounty-account balances. This is a permanent, unrecoverable lock of treasury-sourced funds that were meant to reach a legitimate beneficiary — directly matching the "permanent user-fund ... lock" impact class, and it requires no malicious peer, validator, governance actor, or leaked key: any signed account can call `claim_bounty` once the bounty is `PendingPayout` (`ensure_signed(origin)?; // anyone can trigger claim`).

### Likelihood Explanation
`T::Currency::transfer` with `Preservation::AllowDeath`/`ExistenceRequirement::AllowDeath` can still fail with `DispatchError::Token(BelowMinimum)`/`ExistentialDeposit` when depositing into a *destination* account that does not yet exist and the deposited amount is below `ExistentialDeposit` — this is a normal, well-documented Substrate balances behavior, not an edge case requiring any adversarial setup. Small residual payouts easily arise whenever `bounty.fee` (curator fee) is close to the bounty's total value, leaving a `payout` remainder under the ED, or symmetrically a small `final_fee` under the ED for the curator. Since `claim_bounty` is callable by any signed account as soon as the payout-delay elapses, triggering this condition needs no privileged actor — only a bounty/tip configuration (set by ordinary governance/curator flow, not attacker-controlled admin abuse) that produces a sub-ED remainder, which is realistic in ordinary operation.

### Recommendation
Replace every `debug_assert!(res.is_ok())` around a value-transferring call in `pallet-bounties`, `pallet-child-bounties`, and `pallet-tips` with real error handling: propagate the error with `?`/`ensure!` before mutating/removing the bounty/tip state and before emitting the "success" event, or explicitly handle the failure path (e.g., leave the record in place / requeue) instead of assuming success. At minimum, do not delete the bounty record or emit a success event until the transfer's `Result` has been checked in all build profiles.

### Proof of Concept
1. Configure a bounty (via governance) with `value` and `fee` such that `payout = value - fee` is greater than zero but strictly less than `ExistentialDeposit` (e.g. `ED = 1_000_000_000`, bounty value gives `payout = 1`).
2. Assign a `beneficiary` account that has never held a balance (a freshly generated `AccountId`, zero balance, no `AccountData` entry).
3. Wait until `unlock_at` passes, then call `claim_bounty(origin, bounty_id)` from any signed account (per doc, "anyone can trigger claim").
4. Inside `claim_bounty`, `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` returns `Err(TokenError::BelowMinimum)` because the destination account does not exist and `payout < ED`.
5. In a release build, `debug_assert!(res.is_ok())` is a no-op, so execution continues: `*maybe_bounty = None`, `BountyDescriptions::remove(...)`, and `Event::BountyClaimed { payout, beneficiary, .. }` is emitted.
6. The `payout` amount remains stranded in `bounty_account_id(bounty_id)` forever; there is no bounty record left to retry the claim and no other pallet call that recovers this specific balance — a permanent, silent loss of the beneficiary's funds despite an on-chain event claiming success.
