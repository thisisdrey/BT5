### Title
Snowbridge outbound-queue message delivery fee can be rounded to zero via `convert_from_ether_decimals`, letting users pay nothing for real relayer/gas costs - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

### Summary
`Pallet::calculate_fee` in the Snowbridge outbound-queue pallet computes the native-currency fee charged to a sender for delivering a message to Ethereum. The final step, `convert_from_ether_decimals`, performs a plain integer division (`value / 10^(18-Decimals)`) with no minimum/non-zero enforcement. For small enough gas/reward inputs (or for chains with low native decimals, analogous to GUSD's 2 decimals in the external report), this division truncates the fee to `0`, so `Fee::remote` — and potentially the total fee — becomes zero while the message still consumes queue slots, weight, and real relayer gas-refund/reward obligations on Ethereum. This is structurally the same rounding-to-zero griefing pattern as the reported DAO-factory fee bug: an unprivileged caller can repeatedly trigger operations whose fee calculation rounds down to zero, extracting real work/value for free.

### Finding Description
`calculate_fee` (bridges/snowbridge/pallets/outbound-queue/src/lib.rs:368-393) computes:
```
fee = calculate_remote_fee(gas_used_at_most, fee_per_gas, reward)   // U256, in wei
fee = FixedU128::from_inner(fee).saturating_mul(multiplier).checked_div(&exchange_rate)... .into_inner()
fee = convert_from_ether_decimals(fee)
```
`convert_from_ether_decimals` (lines 411-418) does:
```rust
pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
    let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
    let denom = 10u128.saturating_pow(decimals);
    value.checked_div(denom).expect("divisor is non-zero; qed").into()
}
```
This is a raw floor division by a large constant (`denom = 10^(18-Decimals)`, e.g. `10^8` for a 10-decimal native currency). There is no check that the result is non-zero, unlike the guarded rounding paths elsewhere in the same repo (e.g. `pallet-asset-conversion`'s `quote_price_exact_tokens_for_tokens`, which explicitly rejects an `amount_out` that rounds to zero, and the `pallet-psm` mint/redeem paths, which return `Error::AmountTooSmallAfterConversion` when conversion truncates to zero).

The repository's own test explicitly demonstrates this rounding-to-zero condition and flags it as unintended:
```rust
// bridges/snowbridge/pallets/outbound-queue/src/test.rs:303-318
let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
assert_eq!(fee.local, 698000000);
// Though none zero pricing params the remote fee calculated here is invalid
// which should be avoided
assert_eq!(fee.remote, 0);
```

`SendMessage::validate` (bridges/snowbridge/pallets/outbound-queue/src/send_message_impl.rs:41-74) calls `Self::calculate_fee(...)` and returns the resulting `Fee` to the caller with **no** check that `fee.remote != 0` (or `fee.local + fee.remote != 0`) before returning `Ok((ticket, fee))`. `deliver` then unconditionally enqueues the message. Whatever integration charges the sender (XCM exporter/system pallet consuming this `Fee`) will collect the truncated (possibly zero) amount, while the message still occupies `MaxMessagesPerBlock` capacity, consumes local processing weight, and is ultimately relayed to Ethereum where the relayer is compensated `Min(GasPrice, MaxFeePerGas) * GasUsed + Reward` — real value that the on-chain fee was supposed to fund upfront.

### Impact Explanation
Because the fee that is supposed to reimburse relayers and cover local processing is computed via unguarded floor division, a message can be crafted (or naturally occur, depending on `PricingParameters` set by governance and the message's `gas_used_at_most`) such that the sender is charged zero while:
- the message still occupies a slot in the bounded `MaxMessagesPerBlock` / message queue,
- local processing weight is still consumed,
- the relayer is still owed `reward` (and gas refund) on the Ethereum side.

Repeated exploitation (many small/cheap messages hitting the zero-fee boundary) degrades bridge processing economics and can be used to flood the outbound queue with underpriced messages, consistent with the "public underpriced work that degrades block production or stalls bridge processing" impact class. Actual monetary loss magnitude depends on `PricingParameters` (governance-controlled), so severity is bounded but the underlying arithmetic gap is real and repo-acknowledged (impact rated Low/Medium-ish, matching the source report's own "Low impact / High likelihood" framing).

### Likelihood Explanation
Likelihood is high for the general bug class: no privileged actor, validator, relayer, or governance misbehavior is required. Any unprivileged account that can invoke message sending (e.g., via XCM transport that routes into `EthereumBlobExporter`/`OutboundQueue::validate`) can trigger `calculate_fee` with attacker-influenced `gas_used_at_most` (via command choice) under a given `PricingParameters` configuration, and repeatedly submit messages sized to land in the zero-fee-rounding region — exactly the "buy in chunks" strategy from the original report, translated to "send in chunks."

### Recommendation
Harden `convert_from_ether_decimals` (and/or `calculate_fee`) to reject or clamp truncation to zero when the pre-conversion fee is non-zero, mirroring the guard pattern already used in `pallet-asset-conversion` (`amount_out.is_zero()` rejection) and `pallet-psm` (`Error::AmountTooSmallAfterConversion`):
```rust
pub(crate) fn convert_from_ether_decimals(value: u128) -> Result<T::Balance, DispatchError> {
    let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
    let denom = 10u128.saturating_pow(decimals);
    let converted = value.checked_div(denom).expect("divisor is non-zero; qed");
    if !value.is_zero() && converted.is_zero() {
        return Err(Error::<T>::FeeRoundsToZero.into());
    }
    Ok(converted.into())
}
```
and propagate the error through `calculate_fee`/`validate` so message submission fails (or rounds up to a minimum non-zero fee) instead of silently accepting a zero-fee delivery.

### Proof of Concept
The repository's existing unit test already demonstrates the exploitable state without any code change:
```rust
// bridges/snowbridge/pallets/outbound-queue/src/test.rs:303-318
#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
    new_tester().execute_with(|| {
        let gas_used: u64 = 250000;
        let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
            exchange_rate: FixedU128::from_rational(1, 1),
            fee_per_gas: 1_u32.into(),
            rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
            multiplier: FixedU128::from_rational(1, 1),
        };
        let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
        assert_eq!(fee.local, 698000000);
        assert_eq!(fee.remote, 0);  // <-- attacker-reachable via validate()/send path
    });
}
```
An attacker (or low-value message flow) that keeps `gas_used_at_most * fee_per_gas + reward` small relative to `denom = 10^(18-Decimals)` after exchange-rate/multiplier adjustment reproduces `fee.remote == 0`; `SendMessage::validate` returns this zero fee unchecked, and `deliver` enqueues the message for real processing/relay regardless. 		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		/// Calculate fee in remote currency for dispatching a message on Ethereum
		pub(crate) fn calculate_remote_fee(
			gas_used_at_most: u64,
			fee_per_gas: U256,
			reward: U256,
		) -> U256 {
			fee_per_gas.saturating_mul(gas_used_at_most.into()).saturating_add(reward)
		}

		/// The local component of the message processing fees in native currency
		pub(crate) fn calculate_local_fee() -> T::Balance {
			T::WeightToFee::weight_to_fee(
				&T::WeightInfo::do_process_message().saturating_add(T::WeightInfo::commit_single()),
			)
		}

		// 1 DOT has 10 digits of precision

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}

	fn deliver(ticket: Self::Ticket) -> Result<H256, SendError> {
		let origin = AggregateMessageOrigin::Snowbridge(ticket.channel_id);

		if ticket.channel_id != PRIMARY_GOVERNANCE_CHANNEL {
			ensure!(!Self::operating_mode().is_halted(), SendError::Halted);
		}

		let message = ticket.message.as_bounded_slice();

		T::MessageQueue::enqueue_message(message, origin);
		Self::deposit_event(Event::MessageQueued { id: ticket.message_id });
		Ok(ticket.message_id)
	}
