Can an attacker exploit `mt_resolve_withdraw`'s length-mismatch fallback `Ok(_) => vec![U128(0); amounts.len()]` (triggered when their `mt_on_transfer`-style receiver for `mt_batch_transfer_call` returns a JSON array of `used` amounts with a DIFFERENT length than `amounts.len()`) to force a full-amount refund via `self.deposit` for every `token_id` even when the receiver contract actually kept some of the tokens, breaking (balance debited) == (assets delivered) + (amount re-credited), per token_id? Preconditions: attacker deploys an MT receiver returning a malformed-length success array, holds `Nep245TokenId` balances for multiple `token_ids` under one `token` contract. Call sequence: `mt_withdraw` -> `internal_mt_withdraw` -> `Contract::withdraw` -> `do_mt_withdraw` -> `mt_batch_transfer_call` -> `mt_resolve_withdraw` -> length check `used.len() == amounts.len()` fails -> `vec![U128(0); amounts.len()]` -> full refund for every token_id via `self.deposit`. Scoped impact: Critical, attacker gets both the batch-transferred MT tokens externally AND a full re-credit inside the Verifier across all `token_ids` in the batch. Proof idea: sandbox test with a mock MT receiver returning `Vec<U128>` of wrong length on `mt_on_transfer`; assert sum of `used` + sum of `refund` != sum of `amounts` actually withdrawn.
