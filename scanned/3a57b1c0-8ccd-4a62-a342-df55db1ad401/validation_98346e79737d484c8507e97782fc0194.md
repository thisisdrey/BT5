## Analysis

The Solidity report's core broken invariant is: **share price = totalSupply / totalAssets, where `totalAssets` is read from a raw token balance that can be inflated by a direct donation transfer, independent of the share-minting accounting path.** A small first deposit plus a large "donation" transfer distorts the assets-per-share ratio so badly that subsequent depositors get rounded down to near-zero shares while the attacker's existing shares now represent a disproportionate claim on the pool.

`pallet-asset-conversion` (Uniswap-V2-style AMM used on Asset Hub / the Substrate test-runtime) has the exact same structural weakness: LP token minting is priced off the pool account's **live, directly-transferable asset balance** (`get_balance`), not an internally tracked reserve variable that only changes through the accounted add/remove/swap paths. ### Title
Donation-inflatable reserves in `pallet-asset-conversion::do_add_liquidity` allow rounding-based griefing/theft of subsequent liquidity providers - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`do_add_liquidity` prices new LP tokens as `mul_div(amount, total_supply, reserve)`, where `reserve1`/`reserve2` come from `Self::get_balance(&pool_account, asset)` — i.e., the pool account's *actual* fungible-asset balance. Because that balance can be increased by any account simply transferring tokens straight to the deterministic pool address (via `T::Assets::transfer`, `Balances::transfer_allow_death`, etc., outside of `add_liquidity`), an attacker who is first (or an early) LP can donate a large amount directly to the pool account to blow up `reserve` relative to `total_supply` of LP tokens. The `MintMinLiquidity` dead-share mechanism (`T::MintMinLiquidity::get()`, e.g. 100) only guards the very first mint at `total_supply == 0`; it does nothing to stop a post-first-mint donation attack that skews the reserve:supply ratio for all future depositors.

### Finding Description
1. `do_add_liquidity` computes reserves from live balances, not from an internally-accounted state: [1](#0-0) 
2. LP minting for a non-empty pool is a straight ratio against those live balances and `total_supply`: [3](#0-2) 
3. The only anti-inflation guard, `MintMinLiquidity`, is applied solely on the `total_supply.is_zero()` branch (i.e., pool creation), permanently locking `T::MintMinLiquidity::get()` LP tokens to the pool account: [4](#0-3) 

Attack path:
- Attacker creates the pool and calls `add_liquidity` with the minimal amounts needed to just clear the `lp_token_amount > MintMinLiquidity` check (e.g. `amount1_desired = amount2_desired = MintMinLiquidity + 1`), obtaining a small number of LP tokens while `MintMinLiquidity` dead-shares are minted to the pool account. `total_supply` is now tiny (~`2*MintMinLiquidity + 1`).
- Attacker then sends a large amount of both pool assets directly to the deterministic pool account (`T::PoolLocator::address`) using ordinary asset transfers — this is not restricted to `pallet-asset-conversion` calls, since the pool account is just a normal account holding fungible balances.
- `reserve1`/`reserve2` (read live via `get_balance`) are now huge relative to `total_supply`.
- When a genuine liquidity provider calls `add_liquidity`, `lp_token_amount = min(mul_div(amount1, total_supply, reserve1), mul_div(amount2, total_supply, reserve2))` rounds toward zero because `total_supply` is minuscule compared to the inflated `reserve`. This either reverts with `InsufficientLiquidityMinted` (denial of service on new liquidity provisioning for that pool) or, for larger deposits that just clear the `MintMinLiquidity` threshold, mints a disproportionately small number of LP tokens relative to the assets actually contributed — the attacker's still-live LP shares (and the pool's existing LP holders) end up with an inflated claim on the pool's post-deposit reserves, which they can immediately extract via `remove_liquidity`.

This is a direct structural analog of the reported inflation attack: the vulnerable pricing formula treats a directly-manipulable raw balance as ground truth for share issuance, and the "decimals offset"-style dead-share mitigation only covers the very first mint, not later donations.

### Impact Explanation
- No governance/admin/privileged actor or malicious relayer/validator is needed — any unprivileged account controlling the first LP position can execute this with two ordinary extrinsics (an `add_liquidity` call and a plain asset transfer to a computable deterministic address).
- Impact ranges from denial-of-service on new liquidity provisioning for a pool (locked/degraded pool usability) to genuine value misallocation: a legitimate depositor's contributed assets get merged into reserves while receiving far fewer LP tokens than their pro-rata share, and the attacker's still-outstanding LP tokens capture a share of that value on `remove_liquidity`.
- This matches the "conserve value and settle exactly once to the rightful beneficiary and amount" and "public underpriced work" impact classes for asset accounting pallets in scope.

### Likelihood Explanation
Likelihood is comparable to the original report's "Low" rating: it requires the attacker to be an early participant in a specific pool (attacker-created pools trivially satisfy this) and to spend real capital on the donation, at a cost proportional to the reserve inflation needed. For any newly created pool — which is permissionless (`create_pool` has no origin restriction beyond paying the `PoolSetupFee`) — an attacker can front-run genuine liquidity providers with negligible cost since `MintMinLiquidity` is only ~100 units.

### Recommendation
- Track reserves as pallet storage updated only through accounted operations (`add_liquidity`/`remove_liquidity`/`swap`), rather than reading the pool account's live balance, so that unsolicited transfers cannot influence share pricing (equivalent to Uniswap V2's `sync`-free internal `reserve0`/`reserve1` state, or ERC-4626's `_decimalsOffset`/virtual-shares fix).
- Alternatively, when the ratio between the live balance and the internally accounted reserve diverges (i.e., unexpected surplus balance is detected on the pool account), sweep/burn the surplus or exclude it from the LP pricing formula rather than treating all account balance as priceable reserve.

### Proof of Concept
1. Attacker: `create_pool(native, X)`.
2. Attacker: `add_liquidity(native, X, amount1_desired = amount2_desired = MintMinLiquidity + 1, ..., mint_to = attacker)` → `total_supply = 2*MintMinLiquidity + 1`, attacker holds `MintMinLiquidity + 1` LP tokens, pool account holds `MintMinLiquidity` dead LP tokens.
3. Attacker: plain `Assets::transfer`/`Balances::transfer` of a large amount `D` of both `native` and `X` directly to the pool's deterministic account (`T::PoolLocator::address`).
4. Victim: `add_liquidity(native, X, amount1_desired, amount2_desired, ..., mint_to = victim)` where reserves are now `≈ D`. `lp_token_amount = mul_div(amount, total_supply, reserve) ≈ amount * total_supply / D → 0`, tripping `Error::<T>::InsufficientLiquidityMinted` for any reasonably-sized honest deposit, or minting a token amount far below the victim's pro-rata contribution if the deposit is large enough to clear the floor — after which the attacker's LP tokens capture a share of the victim's contributed reserves via `remove_liquidity`.
