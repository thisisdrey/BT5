Found it. The `snowbridge-pallet-system-frontend` `add_tip` extrinsic has exactly the SYMM-IO bug pattern: a new/alternate public entrypoint that funnels value into the same guarded pipeline (`register_token`) but skips the pipeline's own `Halted`/pause check.

### Title
`add_tip` in `snowbridge-pallet-system-frontend` bypasses the `ExportOperatingMode::Halted` guard enforced by `register_token`, allowing fee-asset burns and tip dispatch while Ethereum export is halted - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

### Summary
`Pallet::register_token` explicitly checks `ensure!(!Self::export_operating_mode().is_halted(), Error::<T>::Halted)` before doing any swap/burn/XCM-transact work [1](#0-0) . The `add_tip` extrinsic, added as an additional user-facing entrypoint into the same Ethereum-export/backend-Transact pipeline, performs the equivalent value-affecting operations (swap tip asset for Ether, burn Ether for teleport, and forward a `Transact` call to `EthereumSystemCall::AddTip` on Bridge Hub) but has **no such check** at all [2](#0-1) .

### Finding Description
The pallet's own `ExportOperatingMode` storage item and `set_operating_mode` extrinsic exist specifically to let governance halt "operations" that would otherwise send/export to Ethereum [3](#0-2) . `register_token` is guarded with `Error::Halted`. `add_tip` calls `swap_fee_asset_and_burn` (which swaps the caller's asset for Ether via `T::Swap` and burns it via `burn_for_teleport`) and then dispatches a remote `Transact` (`build_add_tip_call` → `send_transact_call`) to Bridge Hub's `EthereumSystemCall::AddTip`, all without checking `export_operating_mode().is_halted()` [4](#0-3) [5](#0-4) .

This mirrors the SYMM-IO bug precisely: `allocate`/`depositAndAllocate` are pause-guarded, but the newer `internalTransfer` function reaches the same underlying state-mutating logic without the guard. Here, `register_token` is halt-guarded, but the newer `add_tip` reaches the same swap/burn/XCM-transact machinery without the guard, even though the pallet's own documentation states the pallet acts as "the user-facing control-plane for Snowbridge" and the error variant `Halted` ("Message export is halted") is defined precisely to stop such exports [6](#0-5) .

Because `add_tip` is a fully public, unprivileged, signed extrinsic (`ensure_signed(origin)?` only) [7](#0-6) , any user can continue to burn assets and enqueue Ethereum-export-bound XCM `Transact` calls even after governance has set `ExportOperatingMode::Halted` — precisely the scenario the pause exists to prevent (e.g., after detecting an issue with the Ethereum export/backend pipeline).

### Impact Explanation
When governance halts Ethereum export (e.g., in response to a detected issue in the backend pipeline, Bridge Hub congestion, or a suspected compromise), `add_tip` still: (1) irreversibly swaps and burns user assets for Ether, and (2) forwards an XCM `Transact` to Bridge Hub's `EthereumSystemCall::AddTip`, which ultimately mutates `PendingOrders`/reward state in `outbound-queue-v2` on Bridge Hub. This can result in unbacked burns of user funds with no corresponding, verifiable delivery guarantee while the system is supposed to be frozen, and can continue queuing state-mutating cross-chain calls during an incident the halt was meant to contain — a fund-loss/inconsistent-state condition analogous to the referenced report's impact.

### Likelihood Explanation
High: `add_tip` is a normal, permissionless, always-available extrinsic requiring no special privilege — only `ensure_signed`. No node, relayer, validator, or governance collusion is needed; a normal user can call it at any time, including immediately after a halt is set, since nothing in the code path re-checks `export_operating_mode()`.

### Recommendation
Add the same guard used in `register_token` to `add_tip`:
```rust
pub fn add_tip(origin: OriginFor<T>, message_id: MessageId, asset: Asset) -> DispatchResult {
    ensure!(!Self::export_operating_mode().is_halted(), Error::<T>::Halted);
    let who = ensure_signed(origin)?;
    ...
}
```

### Proof of Concept
1. Governance calls `set_operating_mode(Root, BasicOperatingMode::Halted)`, setting `ExportOperatingMode::<T>::put(Halted)` [8](#0-7) .
2. Verify `register_token` now fails with `Error::Halted` due to the explicit check.
3. Call `add_tip(origin, message_id, fee_asset)` as any signed user — observe it succeeds: `swap_fee_asset_and_burn` executes the swap/burn, and `send_transact_call` dispatches the XCM `Transact` carrying `EthereumSystemCall::AddTip` to Bridge Hub, despite `ExportOperatingMode` being `Halted`.
4. This demonstrates the same operation class (`register_token`) is blocked while the parallel `add_tip` path is not, confirming the guard bypass.

Note: I could not fully trace whether Bridge Hub's `pallet-bridge-relayers`/`outbound-queue-v2` `AddTip::add_tip` handler applies any independent halt check on the receiving side (its `add_tip` implementations shown do not check operating mode either, per the read files above), so the bypass likely propagates end-to-end; this final leg was not exhaustively verified beyond the code shown.

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}

		fn send_transact_call(
			origin_location: Location,
			call: BridgeHubRuntime<T>,
		) -> DispatchResult {
			let dest = T::BridgeHubLocation::get();
			let remote_xcm = Self::build_remote_xcm(&call);
			let message_id = Self::send_xcm(origin_location, dest.clone(), remote_xcm.clone())
				.map_err(|error| Error::<T>::from(error))?;

			Self::deposit_event(Event::<T>::MessageSent {
				origin: T::PalletLocation::get().into(),
				destination: dest,
				message: remote_xcm,
				message_id,
			});

			Ok(())
		}
