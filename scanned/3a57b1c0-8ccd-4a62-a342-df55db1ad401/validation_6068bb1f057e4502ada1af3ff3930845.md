### Title
`PricingParameters::validate()` checks each field for non-zero individually but does not validate the combination that feeds `calculate_fee`, allowing the Ethereum-side relayer reward (`Fee.remote`) to be silently rounded to zero - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

### Summary
This mirrors the Bunni-v2 finding: individual parameters pass a per-field validity check (`isValidParams`/`validate()`), but the specific *combination* of those "valid" values, once run through the actual computation path, produces a degenerate result that silently disables the protective economic mechanism (surge fee → relayer reward). In `snowbridge-pallet-outbound-queue`, `PricingParameters::validate()` at `bridges/snowbridge/primitives/core/src/pricing.rs:39-56` only checks that `exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, and `multiplier` are individually non-zero. It never checks that the *combined* computation in `Pallet::calculate_fee` (`bridges/snowbridge/pallets/outbound-queue/src/lib.rs:368-393`) yields a non-zero remote fee after the `FixedU128` multiply/divide and the `convert_from_ether_decimals` truncation.

### Finding Description
`calculate_fee` computes:
```
fee = calculate_remote_fee(gas_used, fee_per_gas, reward)   // U256, in wei
fee = FixedU128::from_inner(fee) * multiplier / exchange_rate   // FixedU128 fixed-point op
fee = convert_from_ether_decimals(fee)                          // integer division by 10^(18-Decimals)
``` [1](#0-0) 

`convert_from_ether_decimals` does an integer division (`value.checked_div(denom)`), which truncates to zero whenever `value < denom`: [2](#0-1) 

The runtime's `set_pricing_parameters` extrinsic in `pallet_system` calls `params.validate()` before storing them, but that validation only inspects each field in isolation: [3](#0-2) [4](#0-3) 

The test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` in the same pallet explicitly demonstrates this: with all-nonzero, individually "valid" parameters (`exchange_rate=1`, `fee_per_gas=1`, `rewards.remote=1`, `multiplier=1`), `calculate_fee` returns `fee.remote == 0`, and the test comment states this is an invalid outcome that "should be avoided": [5](#0-4) 

This zero-fee output is not just a display artifact — it is the actual value attached to every enqueued outbound message and is what unprivileged, permissionless callers pay when sending a message via `SendMessage::validate` (invoked for every bridge-bound XCM transfer/command): [6](#0-5) 

Because `validate()` on `PricingParameters` (the governance-facing sanity check) does not simulate the downstream fixed-point/decimal-conversion pipeline, a parameter set that looks "safe" (all fields nonzero) can still cause the *per-message* remote fee charged to public callers to compute to zero. Every subsequent message sent through the channel while these parameters remain active is a piece of "public underpriced work": the sender pays no remote (Ethereum-side) fee, yet the message still gets queued, committed into a merkle root, and dispatched for relaying — with no reward available on the Ethereum Gateway side to compensate the relayer (`reward: 0` after `try_into` on `pricing_params.rewards.remote`, per the message construction path where `reward` used in the committed message is derived from the same pricing parameters).

### Impact Explanation
Once the fee is zero for the remote leg, the bridge's spam-resistance/relayer-incentive mechanism is defeated:
- Unprivileged accounts can flood `place`/`send`-style entry points (any pallet that calls `SendMessage::validate`/`deliver` on the outbound queue, e.g. token transfers to Ethereum) essentially for free on the remote-fee component, since only the local (weight-based) fee is nonzero.
- No relayer will have an economic incentive to deliver these messages to the Gateway contract (reward = 0), so messages accumulate in the outbound queue/`MessageLeaves` without being relayed, degrading bridge processing/throughput — this matches the "public underpriced work that degrades block production or stalls bridge processing" impact category.
- This does not require a malicious relayer, governance actor, or leaked key — any signed account submitting a normal bridge transfer while the parameters are in this state triggers the underpriced computation.

### Likelihood Explanation
The precondition is a specific but plausible combination of `PricingParameters` (small `fee_per_gas`, low `gas_used_at_most` for lightweight commands, `exchange_rate` and `multiplier` near 1, or more generally any values where the intermediate fixed-point value is smaller than `10^(18-Decimals)`, e.g. `10^8` on a 10-decimal chain). Since `validate()` — the only gate applied by `set_pricing_parameters` — does not simulate `calculate_fee`, such a configuration passes validation, and the resulting zero/near-zero remote fee then applies uniformly to every subsequent message sent by any unprivileged user until parameters are corrected. This is analogous to the Bunni-v2 report where a per-field/individually-valid configuration combination silently disabled a fee mechanism.

### Recommendation
Extend `PricingParameters::validate()` (or add an integrity check invoked from `set_pricing_parameters`) to simulate the full `calculate_fee` pipeline for at least the maximum-gas command and assert the resulting `Fee.remote` is non-zero (and ideally above some minimum bound), rather than only checking that each individual field is nonzero. Reject parameter updates where the combined computation truncates to zero.

### Proof of Concept
The existing unit test already demonstrates the broken invariant end-to-end:
```rust
// bridges/snowbridge/pallets/outbound-queue/src/test.rs:303-319
let price_params = PricingParameters {
    exchange_rate: FixedU128::from_rational(1, 1),
    fee_per_gas: 1_u32.into(),
    rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
    multiplier: FixedU128::from_rational(1, 1),
};
// price_params.validate() -> Ok(()), all fields nonzero
let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
assert_eq!(fee.remote, 0); // remote/relayer fee silently truncated to zero
```
Any signed account calling a pallet that routes through `snowbridge_pallet_outbound_queue::Pallet::validate`/`deliver` (e.g., a token transfer to Ethereum) while such parameters are active would have its message enqueued with `fee.remote == 0`, i.e., free remote-side dispatch with zero relayer reward — exactly the state the report is meant to guard against.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}
