### Title
Snowbridge outbound-queue fee validation only checks individual `PricingParameters` fields are non-zero, allowing the *computed* remote fee charged to senders to round to zero while a non-zero relayer reward is still committed - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

### Summary
This is the same broken-invariant class as the Portal.sol report: a set of governance-configured "economic" parameters (`fundingRewardRate`, `amountToConvert`, `fundingExchangeRatio`) is only checked for basic non-zero presence, not for whether the resulting derived value is economically sound. In `bridges/snowbridge/primitives/core/src/pricing.rs`, `PricingParameters::validate()` rejects the config only if `exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, or `multiplier` individually equal zero. [1](#0-0) 
It never checks whether the *combination* of these "valid" values still produces a usable, non-zero derived fee once put through `calculate_fee`/`calculate_remote_fee`/`convert_from_ether_decimals` in the outbound-queue pallet.

### Finding Description
`calculate_fee` computes the fee charged to a message sender from `PricingParameters` that have already passed `validate()`: [2](#0-1) 
The pallet's own test suite proves that this "validated" configuration can still yield a `remote` fee of exactly `0`, even though every individual pricing field is non-zero: [3](#0-2) 
Meanwhile, when the message is actually committed in `do_process_message`, the reward promised to the Ethereum-side relayer is **not** derived from the fee that was actually collected from the sender at submission time. It is pulled directly, unconditionally, from the static governance-set `pricing_params.rewards.remote` and baked into the `CommittedMessage.reward` field that is later paid out on Ethereum: [4](#0-3) 
This is exactly the `amountToConvert = 0` / `fundingRewardRate` mismatch from the external report: the value that is *charged* to the user (`fee.remote`, which can silently round to `0` via integer division in `convert_from_ether_decimals`) is decoupled from the value that the protocol *commits to pay out* (the fixed `rewards.remote`). `PricingParameters::validate()` guards individual fields but does not guard this cross-field/rounding invariant, so field-level non-zero checks give a false sense of safety while the actual economic guarantee (fee collected ≥ reward promised) can still be violated.

### Impact Explanation
Because message senders can be charged `0` for the `remote` component of the delivery fee while the protocol still queues a message that promises the full configured `rewards.remote` to relayers on Ethereum, this is public underpriced work: unprivileged users can submit governance/user messages into the outbound queue essentially for free on the remote-fee side, while the bridge keeps committing to pay relayers out of pooled/treasury funds that were never actually collected for those specific messages. Under sustained abuse (small `gas_used_at_most`/no configuration change needed, purely through the value ranges shown by the pallet's own test), this degrades the sustainability of relayer incentives and can stall Ethereum-bound message processing once reward funding is exhausted, matching the "public underpriced work that degrades block production or stalls bridge processing" impact class.

### Likelihood Explanation
No malicious relayer, validator, governance actor, or admin action is required. Any unprivileged account that can submit XCM messages routed through `EthereumBlobExporter`/the outbound queue can trigger the fee computation path with parameters that fall in the zero-rounding region demonstrated by the existing test (`fee_per_gas = 1`, `exchange_rate = 1/1`, small `gas_used_at_most`), which are entirely plausible values within currently deployed bridge-hub configurations such as `bridge_to_ethereum_config.rs`'s `Parameters` (`fee_per_gas: gwei(20)`, `exchange_rate: 1/400`). The condition is purely arithmetic/config-driven and already reproduced by an in-repo test, so likelihood is high relative to needing any privileged or off-chain actor.

### Recommendation
Extend `PricingParameters::validate()` (or add a post-computation check in `calculate_fee`) to assert that the fully computed, decimals-adjusted `remote` fee is non-zero for the minimum supported `gas_used_at_most`, not just that the raw input fields are individually non-zero. Alternatively, derive the `reward` embedded in `CommittedMessage` from the fee actually collected at submission time rather than from the static configured `rewards.remote`, so the amount promised to relayers can never exceed what was collected from the sender.

### Proof of Concept
The existing unit test already demonstrates the core primitive: [3](#0-2) 
With `exchange_rate = 1/1`, `fee_per_gas = 1`, `rewards = {local: 1, remote: 1}`, `multiplier = 1` — all individually non-zero and passing `PricingParameters::validate()` — `OutboundQueue::calculate_fee` returns `fee.remote == 0`. Any message submitted while pricing parameters land in this rounding regime is charged `0` for its remote/reward component at `validate()`/`deliver()` time, yet `do_process_message` still embeds the full non-zero `pricing_params.rewards.remote` as the `reward` in the `CommittedMessage` sent to Ethereum [5](#0-4) , decoupling collected fee from promised payout.

	pub fn validate(&self) -> Result<(), InvalidPricingParameters> {

			return Err(InvalidPricingParameters);
		}

			return Err(InvalidPricingParameters);
		}
		if self.multiplier == FixedU128::zero() {
			return Err(InvalidPricingParameters);
		}
		Ok(())
	}

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		/// Calculate fee in remote currency for dispatching a message on Ethereum
		pub(crate) fn calculate_remote_fee(
			gas_used_at_most: u64,
			fee_per_gas: U256,
			reward: U256,
		) -> U256 {
			fee_per_gas.saturating_mul(gas_used_at_most.into()).saturating_add(reward)
		}

		/// The local component of the message processing fees in native currency
		pub(crate) fn calculate_local_fee() -> T::Balance {
			T::WeightToFee::weight_to_fee(
				&T::WeightInfo::do_process_message().saturating_add(T::WeightInfo::commit_single()),
			)
		}

		// 1 DOT has 10 digits of precision
		// 1 KSM has 12 digits of precision
		// 1 ETH has 18 digits of precision
		pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
			let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
			let denom = 10u128.saturating_pow(decimals);
			value.checked_div(denom).expect("divisor is non-zero; qed").into()
		}

fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {
		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
			exchange_rate: FixedU128::from_rational(1, 1),
			fee_per_gas: 1_u32.into(),
			rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});
