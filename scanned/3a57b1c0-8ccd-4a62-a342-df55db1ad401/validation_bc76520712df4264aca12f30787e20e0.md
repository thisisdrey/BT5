### Title
`register_token` lets any origin re-register an already-bridged token and overwrite its Ethereum-side metadata (name/symbol/decimals) - ([File: bridges/snowbridge/pallets/system/src/lib.rs])

### Summary
The Mochi report's core defect is a public registration function that re-classifies an *already-registered* entity, silently changing downstream risk parameters, because the function never checks "does this ID already exist?" before writing new classification data. The same broken invariant exists in Snowbridge's token-registration flow: `do_register_token` guards the *reverse-lookup* insert (`ForeignToNativeId`) but always re-emits the `RegisterForeignToken` command carrying the caller-supplied `name`/`symbol`/`decimals`, regardless of whether the `token_id` was already registered.

### Finding Description
`do_register_token` in `bridges/snowbridge/pallets/system/src/lib.rs` only guards the storage insert, not the outbound command: [1](#0-0) 

```rust
if !ForeignToNativeId::<T>::contains_key(token_id) {
    ForeignToNativeId::<T>::insert(token_id, location.clone());
}

let command = Command::RegisterForeignToken {
    token_id,
    name: metadata.name.into_inner(),
    symbol: metadata.symbol.into_inner(),
    decimals: metadata.decimals,
};
Self::send(SECONDARY_GOVERNANCE_CHANNEL, command, pays_fee)?;
```

The `token_id` is fully derived from the reanchored `location` alone (`TokenIdOf::convert_location`), so calling this path twice for the *same* asset location always yields the *same* `token_id`, but the second call still ships a fresh `RegisterForeignToken` command with whatever `metadata` (name/symbol/decimals) the caller supplies this time — there is no `ensure!(!ForeignToNativeId::contains_key(token_id), Error::AlreadyRegistered)` guard analogous to the Mochi mitigation (`require(_assetClass[_asset]==0)`).

The `register_token` entry point on the system-frontend pallet is explicitly documented as callable by *any* origin, gated only by "asset_id must be a location nested within the origin consensus system," not by root/governance: [2](#0-1) 

That call is proxied over XCM to the backend `register_token` in `system-v2`, which is likewise gated by `T::FrontendOrigin::ensure_origin(origin)` (a configurable, non-root origin), and forwards straight into the same unconditional `ForeignToNativeId::contains_key` short-circuit before dispatching `Command::RegisterForeignToken`: [3](#0-2) 

By contrast, the pure-governance `register_token` on the base `system` pallet is `ensure_root`-gated: [4](#0-3) 

—but the frontend/v2 path bypasses that restriction for tokens nested in the caller's own location, and shares the same vulnerable `do_register_token` core logic.

### Impact Explanation
An asset owner (or anyone controlling a sub-location that already has a registered wrapped ERC20 on Ethereum) can call `register_token` again with different `metadata.decimals`/`name`/`symbol`. Because the on-chain `ForeignToNativeId` mapping is idempotently guarded but the outbound `RegisterForeignToken` command is not, the Gateway contract on Ethereum receives a "re-registration" command that can change the ERC20's declared decimals/symbol for a token that already has value locked/minted under the original metadata. A decimals change in particular breaks the fixed conversion factor between the Polkadot-native asset and its Ethereum wrapped representation, exactly mirroring the Mochi bug where changing `_assetClass` silently changes `liquidationFactor`/`riskFactor` for an already-active position — here it silently changes the value-conversion assumption for an already-active bridged asset, which can lead to a mismatch between minted/locked amounts and their represented value (unbacked mint/theft-class risk) or bridge processing stalls if the Gateway contract rejects/mishandles a metadata conflict for a live token.

### Likelihood Explanation
Likelihood is moderate-to-high: the `register_token` extrinsic in `system-frontend`/`system-v2` is intentionally permissionless (documented as "All origins are allowed"), requiring only that the asset be nested under the caller's own location — no `AlreadyRegistered`-style check exists anywhere in `do_register_token` to stop a second call with altered metadata for the same `token_id`. Any account that once legitimately registered a token can trivially call the same extrinsic again with different metadata values.

### Recommendation
Mirror the recommended Mochi fix: before building/sending `Command::RegisterForeignToken`, explicitly check `ForeignToNativeId::<T>::contains_key(token_id)` and reject the call (e.g. `Error::<T>::TokenAlreadyRegistered`) if the token is already registered, instead of only using that check to skip the storage insert. This should be applied in `do_register_token` in `bridges/snowbridge/pallets/system/src/lib.rs` so both the direct `register_token` call and the `system-v2`/`system-frontend` proxied paths are protected consistently.

### Proof of Concept
1. Account `A` owns asset location `L` and calls the frontend `register_token(asset_id = L, metadata = {name: "Foo", symbol: "FOO", decimals: 18})`. This proxies to `system-v2::register_token` → `ForeignToNativeId` gets `token_id -> L`, and `Command::RegisterForeignToken{token_id, "Foo", "FOO", 18}` is sent to Ethereum, deploying/configuring the wrapped ERC20 with 18 decimals.
2. Users bridge value using the 18-decimal assumption.
3. Account `A` (or anyone whose origin still resolves ownership of `L`) calls `register_token` again for the same `asset_id = L` but with `metadata = {decimals: 6, ...}`.
4. `do_register_token` sees `ForeignToNativeId::contains_key(token_id) == true` and skips the insert, but still unconditionally builds and sends a second `Command::RegisterForeignToken{token_id, ..., decimals: 6}` — corrupting the token's declared decimals on the Ethereum side for an asset that already has bridged value outstanding, with no on-chain guard preventing this second, conflicting registration. [5](#0-4)

		pub(crate) fn do_register_token(
			location: &Location,
			metadata: AssetMetadata,
			pays_fee: PaysFee<T>,
		) -> Result<(), DispatchError> {
			let ethereum_location = T::EthereumLocation::get();
			// reanchor to Ethereum context
			let location = location
				.clone()
				.reanchored(&ethereum_location, &T::UniversalLocation::get())
				.map_err(|_| Error::<T>::LocationConversionFailed)?;

			let token_id = TokenIdOf::convert_location(&location)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			if !ForeignToNativeId::<T>::contains_key(token_id) {
				ForeignToNativeId::<T>::insert(token_id, location.clone());
			}

			let command = Command::RegisterForeignToken {
				token_id,
				name: metadata.name.into_inner(),
				symbol: metadata.symbol.into_inner(),
				decimals: metadata.decimals,
			};
			Self::send(SECONDARY_GOVERNANCE_CHANNEL, command, pays_fee)?;

			Self::deposit_event(Event::<T>::RegisterToken {
				location: location.clone().into(),
				foreign_token_id: token_id,
			});

			Ok(())
		}

		/// Ethereum.
		/// - `asset_id`: Location of the asset

		///
		/// All origins are allowed, however `asset_id` must be a location nested within the origin
		/// consensus system.
		#[pallet::call_index(1)]
		#[pallet::weight(
			T::WeightInfo::register_token()
				.saturating_add(T::BackendWeightInfo::transact_register_token())
				.saturating_add(T::BackendWeightInfo::do_process_message())
				.saturating_add(T::BackendWeightInfo::commit_single())
				.saturating_add(T::BackendWeightInfo::submit_delivery_receipt())
		)]
		pub fn register_token(
			origin: OriginFor<T>,
			asset_id: Box<VersionedLocation>,
			metadata: AssetMetadata,
			fee_asset: Asset,
		) -> DispatchResult {
			ensure!(!Self::export_operating_mode().is_halted(), Error::<T>::Halted);

			let asset_location: Location =
				(*asset_id).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;
			let origin_location = T::RegisterTokenOrigin::ensure_origin(origin, &asset_location)?;

			let ether_gained = if origin_location.is_here() {
				// Root origin/location does not pay any fees/tip.
				0
			} else {
				Self::swap_fee_asset_and_burn(origin_location.clone(), fee_asset)?
			};

			let call = Self::build_register_token_call(
				origin_location.clone(),
				asset_location,
				metadata,
				ether_gained,
			)?;

			Self::send_transact_call(origin_location, call)
		}

		/// Registers a Polkadot-native token as a wrapped ERC20 token on Ethereum.
		///
		/// The system frontend pallet on AH proxies this call to BH.
		///
		/// - `sender`: The original sender initiating the call on AH
		/// - `asset_id`: Location of the asset (relative to this chain)
		/// - `metadata`: Metadata to include in the instantiated ERC20 contract on Ethereum
		#[pallet::call_index(2)]
		#[pallet::weight(<T as pallet::Config>::WeightInfo::register_token())]
		pub fn register_token(
			origin: OriginFor<T>,
			sender: Box<VersionedLocation>,
			asset_id: Box<VersionedLocation>,
			metadata: AssetMetadata,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let sender_location: Location =
				(*sender).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;
			let asset_location: Location =
				(*asset_id).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;

			let location = Self::reanchor(asset_location)?;
			let token_id = TokenIdOf::convert_location(&location)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			if !ForeignToNativeId::<T>::contains_key(token_id) {
				ForeignToNativeId::<T>::insert(token_id, location.clone());
			}

			let command = Command::RegisterForeignToken {
				token_id,
				name: metadata.name.into_inner(),
				symbol: metadata.symbol.into_inner(),
				decimals: metadata.decimals,
			};

			let message_origin = Self::location_to_message_origin(sender_location)?;
			Self::send(message_origin, command, amount)?;

			Self::deposit_event(Event::<T>::RegisterToken {
				location: location.into(),
				foreign_token_id: token_id,
			});

			Ok(())
		}
