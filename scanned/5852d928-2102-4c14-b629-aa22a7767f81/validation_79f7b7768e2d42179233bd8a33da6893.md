### Title
Reward pool accounting derives payouts from donation-inflatable live balance instead of tracked ledger value - (File: `substrate/frame/nomination-pools/src/lib.rs`)

### Summary
`RewardPool::current_balance` returns `T::Currency::reducible_balance` of the pool's reward account. This value feeds directly into `update_records` and `current_reward_counter`, which compute `current_payout_balance = balance + total_rewards_claimed + total_commission_claimed − last_recorded_total_payouts` [2](#0-1) . Because `balance` is the raw free balance of a public, non-gated account, any unprivileged account can transfer tokens directly to the reward account to inflate `current_payout_balance`, and thus `new_pending_rewards`/`new_pending_commission`, exactly as in the reported `OmoVault.topOff()` issue where `agentBalance` (an unguarded live balance) was used instead of the recorded `record.assets` value.

### Finding Description
The reward-pool ledger is supposed to be self-consistent: `last_recorded_total_payouts` tracks what has already been distributed, and `current_reward_counter` computes newly accrued (undistributed) rewards by comparing the account's *current* balance against that recorded baseline [3](#0-2) . The design assumes the only source of balance growth in the reward account is legitimate staking rewards. However, `current_balance` reads the account's raw `reducible_balance`, with no verification of provenance [4](#0-3) . Any signed account can call `Balances::transfer` (or any currency transfer) directly to `Pallet::<T>::generate_reward_account(id)` and immediately inflate `current_payout_balance` on the next `update_records`/`claim_payout`/`bond_extra` call, since the pool has no mechanism distinguishing "actual staking rewards" from "arbitrary external donation." This is the same root defect as `OmoVault.topOff()`: an accounting subtraction/addition that should use an internally tracked, trusted value (`record.assets`) instead uses a live balance that an attacker can freely manipulate by sending tokens to the swept account (`agentBalance` / reward account).

### Impact Explanation
An attacker can donate arbitrary tokens to any pool's reward account to accelerate or inflate the reward counter for that pool, effectively forcing early/inflated payouts to specific members or commission, or corrupting the historical payout ledger used for future accounting (`last_recorded_total_payouts` is `max`-clamped, so unders-recording persists) [5](#0-4) . While `saturating_sub`/`saturating_add` prevent outright panics, this still breaks the invariant that reward distribution should be proportional only to legitimate staking income, allowing manipulation of payout timing/amounts and misattributed commission across pool members — a violation of "value must settle exactly once to the rightful beneficiary and amount."

### Likelihood Explanation
Likelihood is high: `generate_reward_account(id)` is a deterministic, publicly derivable account for every pool, and depositing funds to any account via `pallet-balances::transfer` requires no special privilege, origin, or pool membership.

### Recommendation
Do not derive reward-distribution deltas from the raw `reducible_balance` of the reward account. Track legitimate reward inflows explicitly (e.g., record the amount actually paid into the reward account by the staking reward-payout mechanism, similar to how `OmoVault` should use `record.assets` instead of `agentBalance`), or reject/quarantine unexpected balance increases that do not correspond to a recognized reward-payout event before folding them into `current_payout_balance`.

### Proof of Concept
1. Pool 1 has reward account `R = generate_reward_account(1)`.
2. Attacker (unprivileged, non-member) calls `Balances::transfer_allow_death(attacker, R, X)` to donate `X` tokens directly to `R`.
3. Any subsequent call that triggers `update_records`/`current_reward_counter` (e.g., a member calling `claim_payout`, `bond_extra`, or `set_commission`) reads `current_balance(1) = reducible_balance(R)`, which now includes the attacker's donation `X`.
4. `current_payout_balance` and thus `new_pending_rewards`/`new_pending_commission` are inflated by `X`, and are paid out to the next claimant/commission recipient as though they were legitimate staking rewards, even though no such reward was ever earned by the pool's stake.

**Verification limitation:** I was able to confirm the core accounting logic (`current_balance`, `update_records`, `current_reward_counter`, `do_reward_payout`) via the index, but did not have tool access to run this scenario against a live test harness to confirm downstream saturating-math outcomes precisely (e.g., exact interplay with `total_commission_claimed`/`total_rewards_claimed` bookkeeping across multiple pools). This should be validated with an actual test run before treating severity as final.

	fn update_records(
		&mut self,
		id: PoolId,
		bonded_points: BalanceOf<T>,
		commission: Perbill,
	) -> Result<(), Error<T>> {
		let balance = Self::current_balance(id);

		let (current_reward_counter, new_pending_commission) =
			self.current_reward_counter(id, bonded_points, commission)?;

		// Store the reward counter at the time of this update. This is used in subsequent calls to
		// `current_reward_counter`, whereby newly pending rewards (in points) are added to this
		// value.
		self.last_recorded_reward_counter = current_reward_counter;

		// Add any new pending commission that has been calculated from `current_reward_counter` to
		// determine the total pending commission at the time of this update.
		self.total_commission_pending =
			self.total_commission_pending.saturating_add(new_pending_commission);

		// Total payouts are essentially the entire historical balance of the reward pool, equating
		// to the current balance + the total rewards that have left the pool + the total commission
		// that has left the pool.
		let last_recorded_total_payouts = balance
			.checked_add(&self.total_rewards_claimed.saturating_add(self.total_commission_claimed))
			.ok_or(Error::<T>::OverflowRisk)?;

		// Store the total payouts at the time of this update.
		//
		// An increase in ED could cause `last_recorded_total_payouts` to decrease but we should not
		// allow that to happen since an already paid out reward cannot decrease. The reward account
		// might go in deficit temporarily in this exceptional case but it will be corrected once
		// new rewards are added to the pool.
		self.last_recorded_total_payouts =
			self.last_recorded_total_payouts.max(last_recorded_total_payouts);

		Ok(())
	}

	/// Get the current reward counter, based on the given `bonded_points` being the state of the
	/// bonded pool at this time.
	fn current_reward_counter(
		&self,
		id: PoolId,
		bonded_points: BalanceOf<T>,
		commission: Perbill,
	) -> Result<(T::RewardCounter, BalanceOf<T>), Error<T>> {
		let balance = Self::current_balance(id);

		// Calculate the current payout balance. The first 3 values of this calculation added
		// together represent what the balance would be if no payouts were made. The
		// `last_recorded_total_payouts` is then subtracted from this value to cancel out previously
		// recorded payouts, leaving only the remaining payouts that have not been claimed.
		let current_payout_balance = balance
			.saturating_add(self.total_rewards_claimed)
			.saturating_add(self.total_commission_claimed)
			.saturating_sub(self.last_recorded_total_payouts);

		// Split the `current_payout_balance` into claimable rewards and claimable commission
		// according to the current commission rate.
		let new_pending_commission = commission * current_payout_balance;
		let new_pending_rewards = current_payout_balance.saturating_sub(new_pending_commission);

	/// Current free balance of the reward pool.
	///
	/// This is sum of all the rewards that are claimable by pool members.
	fn current_balance(id: PoolId) -> BalanceOf<T> {
		T::Currency::reducible_balance(
			&Pallet::<T>::generate_reward_account(id),
			Preservation::Expendable,
			Fortitude::Polite,
		)
	}
