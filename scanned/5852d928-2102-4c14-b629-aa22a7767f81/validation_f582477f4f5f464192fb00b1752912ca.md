Based on the code evidence, the closest local analog to the TON "unchecked outcome field" bug is in Snowbridge's `outbound-queue-v2` pallet, where a critical success/failure status decoded from an Ethereum event is never actually consulted before the pallet finalizes payout and settlement state.

### Title
Outbound queue v2 finalizes relayer reward and order settlement without checking the delivery receipt's `success` flag - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`DeliveryReceipt::try_from` decodes a `success: bool` field from the Ethereum `InboundMessageDispatched` event log [1](#0-0) , but `Pallet::process_delivery_receipt` — the only consumer of a decoded `DeliveryReceipt` — never reads that field. It unconditionally pays the relayer reward and removes the `PendingOrder`, treating a message that reverted/failed on Ethereum identically to one that succeeded.

Note that `receipt.success` is bound but never referenced in the function body — the branch that pays the reward (`if order.fee > 0 { ... }`) and the unconditional `<PendingOrders<T>>::remove(nonce)` / `Event::MessageDelivered` execute identically whether the underlying Ethereum-side command execution actually succeeded or reverted. A grep across the crate confirms `receipt.success`/`.success` is declared in the struct but read nowhere else in the pallet's logic.

This mirrors the reported bug class: an off-chain-sourced "outcome" value (TON's per-hash receive status; here, the Ethereum dispatch `success` flag) is captured by the protocol but the on-chain settlement logic does not gate finalization on that outcome — it commits to a single terminal state (`PendingOrders` removed, `MessageDelivered` emitted, reward paid) regardless of what the outcome actually was.

### Impact Explanation
Once `submit_delivery_receipt` is processed, `PendingOrders<T>` for that nonce is deleted and the message is marked `MessageDelivered` — this is the *only* mechanism in this pallet that reconciles the outbound message's fate. Because `success` is ignored, a message whose commands reverted on Ethereum (e.g., `AgentExecute`/token transfer failed) is settled exactly like a successful one: the relayer is still paid `order.fee`, and there is no code path here (or triggered from here) that requeues, refunds, or otherwise remediates the assets that were withdrawn/burned on the Polkadot side to fund that outbound transfer. The status field that exists specifically to distinguish these two outcomes has zero effect on state. This produces permanently unreconciled bridge state and forfeits any chance of automated recovery for the failed leg of the transfer, since the order is deleted the moment *any* receipt (success or failure) is submitted.

### Likelihood Explanation
Any account can call `submit_delivery_receipt` — it only requires a valid, verified event-log proof for a genuine Ethereum event; no privileged, admin, or malicious-relayer assumption is required to trigger this code path. Since Ethereum-side command execution can legitimately fail (out-of-gas, contract-level revert, invalid payload) independent of any protocol actor's intent, the failure path in `process_delivery_receipt` is reached under ordinary operating conditions, not just adversarial ones.

### Recommendation
Branch on `receipt.success` in `process_delivery_receipt`: only pay the relayer reward and finalize/remove the `PendingOrder` for the successful case; for `success == false`, drive a distinct code path (e.g., emit a `MessageDeliveryFailed` event, keep or transition the order to a state that can trigger fund recovery/refund flow for the affected assets, and decide whether the relayer should still be compensated for delivering the receipt vs. for successful execution).

### Proof of Concept
1. `EthereumOutboundQueueV2::do_process_message` queues an outbound message and inserts a `PendingOrder { nonce, fee, .. }` [4](#0-3) , corresponding to real value withdrawn/reserved on the Polkadot side for the transfer.
2. On Ethereum, the relayed message's commands revert (`InboundMessageDispatched(nonce, topic, success=false, reward_address)` is emitted).
3. A relayer submits this genuine event via `submit_delivery_receipt`; `DeliveryReceipt::try_from` decodes `success: false` correctly [5](#0-4) .
4. `process_delivery_receipt` runs the exact same logic as the success case: it registers `order.fee` as a reward for the relayer and calls `<PendingOrders<T>>::remove(nonce)`, emitting `MessageDelivered` [6](#0-5) .
5. The pallet's existing tests (`submit_delivery_receipt_succeeds_after_unhalt`, `poc_m1`) confirm this exact call path with hard-coded success fixtures pays out and removes the order [7](#0-6) ; no equivalent test exercises a `success:false` receipt to show any differing on-chain outcome, because none exists.

```rust
impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
```

```rust
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```

```rust
// After governance resumes the bridge, legitimate delivery receipts flow through again:
// the order is paid out and removed from storage.
#[test]
fn submit_delivery_receipt_succeeds_after_unhalt() {
	new_tester().execute_with(|| {
		let nonce = 0;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_valid_event_proof());

		// Bridge halted — receipt rejected, order untouched.
		set_verifier_halted(true);
		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);
		assert!(PendingOrders::<Test>::get(nonce).is_some());

		// Bridge resumed — same receipt succeeds and the order is settled.
		set_verifier_halted(false);
		assert_ok!(OutboundQueue::submit_delivery_receipt(origin, event));
		assert!(PendingOrders::<Test>::get(nonce).is_none());

		System::assert_has_event(mock::RuntimeEvent::OutboundQueue(Event::MessageDelivered {
			nonce,
		}));
	});
```
