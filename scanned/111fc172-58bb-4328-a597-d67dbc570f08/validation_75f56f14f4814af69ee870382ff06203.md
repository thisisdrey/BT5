### Title
`process_delivery_receipt` pays relayer reward regardless of Ethereum-side delivery success, and `reward_address` in the unverified event log fully controls the beneficiary - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
This is the closest local analog to the Stargate/`mTOFT` bug: a public, unprivileged extrinsic decodes an externally-supplied data blob and uses fields from it to redirect value to an attacker-chosen destination and to settle a payout, without checking that the operation actually completed as claimed. In the Sherlock case, `_sendToken`/`_routerSwap` blindly trusted an unchecked `bytes _ercData` to pick pool IDs, causing funds to be routed to/received as the wrong asset. Here, `process_delivery_receipt` in the Snowbridge outbound-queue-v2 pallet blindly trusts an `InboundMessageDispatched` event's `success` and `reward_address` fields to settle a `PendingOrder` reward payout, and it never gates payment on `receipt.success`.

### Finding Description
`submit_delivery_receipt` is a signed, unprivileged extrinsic (`ensure_signed(origin)`) that:
1. Verifies a Merkle/beacon proof for an Ethereum log via `T::Verifier::verify`.
2. Decodes the log into a `DeliveryReceipt` struct containing `gateway`, `nonce`, `topic`, `success`, `reward_address`. [1](#0-0) [2](#0-1) 

3. `process_delivery_receipt` then only checks `gateway` matches the configured address and that a `PendingOrder` exists for `nonce`. It computes `reward_account` directly from the untrusted `receipt.reward_address` (any 32-byte value the relayer/attacker embeds in the event they cause to be emitted on the Ethereum side), and unconditionally pays `order.fee` to that account whenever `order.fee > 0` — the decoded `receipt.success` field is never inspected:

```rust
pub fn process_delivery_receipt(...) -> DispatchResult {
    ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);
    let reward_account = if receipt.reward_address == [0u8; 32] {
        relayer
    } else {
        receipt.reward_address.into()
    };
    let nonce = receipt.nonce;
    let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;
    if order.fee > 0 {
        T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee);
    }
    <PendingOrders<T>>::remove(nonce);
    Self::deposit_event(Event::MessageDelivered { nonce });
    Ok(())
}
``` [3](#0-2) 

The event schema explicitly carries a `success: bool` flag distinguishing whether the dispatched Gateway commands actually executed correctly on Ethereum:
```solidity
event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address);
``` [4](#0-3) 

Just as the Sherlock finding shows the `_ercData`/pool-id fields were decoded but never bound/verified against the actual src/dst pair before moving funds, here `success` is decoded but never bound to the payout decision, and `reward_address` is trusted outright to redirect the beneficiary of a state-changing token payout (`T::RewardPayment::register_reward`).

### Impact Explanation
The Gateway contract on Ethereum genuinely emits this event whenever a message is dispatched (success or failure) — that emission is not attacker-controlled per se, since the event address/gateway is checked. However, the pallet uses this event solely to gate reward release, and by not checking `success`, a relayer earns the full fee for messages whose intended execution failed on Ethereum. This breaks the invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" — reward settlement here advances regardless of whether execution succeeded. Combined with the fact that `reward_address` is taken as-is from the event log (any 32 bytes chosen by whoever triggers the Ethereum-side event, which need not be the relayer submitting the Substrate extrinsic), this allows the payout beneficiary to diverge arbitrarily from the actual relayer who performed useful work, i.e., value can be steered to an unintended account whenever an attacker can influence what account ends up encoded as `reward_address` for a given nonce (e.g., by being the entity that triggers message dispatch on Ethereum for messages whose relayer differs from the entity setting the reward address). This is a fund-routing/beneficiary correctness bug analogous to `mTOFT` receiving/crediting an unintended party due to unchecked decoded parameters.

### Likelihood Explanation
`submit_delivery_receipt` is callable by any signed account (no special permission), and the only guard is a valid Merkle/beacon proof of a genuine Gateway log — an on-chain, permissionless, and repeatable action for every dispatched message. The missing `success` check is a straightforward code-review-detectable omission (no test exercises reward-denial-on-failure, only `poc_m1`/halted-verifier gating is tested), making the divergence from intended behavior easy to trigger simply by submitting receipts for messages whose dispatch failed on Ethereum.

### Recommendation
- Gate `register_reward` on `receipt.success`; do not pay (or pay a reduced/no fee) when `receipt.success == false`, and emit a distinct event (e.g., `MessageDeliveryFailed`) instead of `MessageDelivered`.
- Re-examine whether `reward_address` should be sourced from trusted, pallet-side state (e.g., recorded at the time the message was queued, similar to `PendingOrder`) rather than taken verbatim from the Ethereum-emitted event, to remove the ability for the beneficiary to be set by whoever can influence the on-chain event data.

### Proof of Concept
1. A message is queued via `send_message_impl`, creating `PendingOrders::<T>::insert(nonce, PendingOrder { nonce, fee, .. })` with `fee > 0`. [5](#0-4) 
2. The message is relayed to Ethereum but its dispatched commands fail on execution (e.g., insufficient gas for the inner call, or the target contract call reverts) — the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. Any signed account submits `submit_delivery_receipt` with a valid Merkle/beacon proof of that log.
4. `process_delivery_receipt` checks only `gateway` and `PendingOrders` existence; it ignores `receipt.success == false` and pays `order.fee` to `reward_account` anyway, exactly as it would for a successful dispatch — see the unconditional `if order.fee > 0 { register_reward(...) }` path and the existing test `send_foreign_erc20_token_back_to_polkadot`/`transact_with_agent_from_asset_hub_without_any_asset_transfer` style flows that call `process_delivery_receipt` directly with attacker-suppliable `DeliveryReceipt { success: true/false, reward_address, .. }` and observe `RewardRegistered` regardless.
