### Title
Relayer reward is paid regardless of message execution outcome because `DeliveryReceipt::success` is never checked — (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`SecuritizeSwap`'s bug was a mismatch between the *declared* type structure used for verification (`TXTYPE_HASH`) and the *actual* fields being processed, so the verifier accepted/settled on the wrong semantic content. The direct analog here is in Snowbridge's `outbound-queue-v2` pallet: the Ethereum `InboundMessageDispatched` event decodes a `success: bool` field indicating whether the relayed message actually executed successfully on Ethereum, but `Pallet::process_delivery_receipt` discards this field and unconditionally pays the relayer reward and clears the `PendingOrder` as if delivery always succeeded.

### Finding Description
`DeliveryReceipt` is parsed from the verified Ethereum log via `TryFrom<&Log>`, capturing `gateway`, `nonce`, `topic`, `success`, and `reward_address`: [3](#0-2) 

The pallet call `submit_delivery_receipt` verifies the Merkle/beacon proof of the log and constructs the `DeliveryReceipt`, then hands off to `process_delivery_receipt`: [4](#0-3) 

`process_delivery_receipt` only checks `gateway` matches the configured `GatewayAddress`, looks up the `PendingOrder` by `nonce`, and pays out `order.fee` to the reward account — the `receipt.success` and `receipt.topic` fields are read into local variables that are computed but structurally never gated on: [5](#0-4) 

This is exactly the EIP-712 pattern from the report: the type/structure that is *verified* (a proof over a log that legitimately encodes both `success` and the correct `nonce`/`topic`) diverges from the structure that is *acted upon* (only `nonce` and `gateway` are actually consulted, `success` is silently dropped). A message whose command execution reverted on Ethereum (Gateway emits `success = false`, which is valid, provable, unforged behavior — not a malicious relayer/prover condition) still results in full reward settlement and permanent removal of the `PendingOrder`.

### Impact Explanation
This causes duplicate/incorrect settlement in the reward-payout sense demanded by the impact gate: fees are paid out for message deliveries that did not actually execute the intended effect on Ethereum. Because `PendingOrders::<T>::remove(nonce)` fires unconditionally on success of proof verification (not on success of message execution), there is no future mechanism (retry, re-relay, refund) to reconcile a failed dispatch — the fee is spent and the record is gone, regardless of whether the user's cross-chain action (e.g., asset unlock/mint command relay) actually happened. This is public, underpriced/mis-costed work: any relayer, honest or not, submitting a legitimately-verified but failed-delivery receipt is rewarded identically to a successful one, and the protocol has no signal to distinguish or penalize non-productive relaying, degrading the incentive design of the bridge's payout mechanism.

### Likelihood Explanation
High likelihood in practice: any unprivileged relayer can trigger this by submitting a legitimate delivery receipt for a message whose Ethereum-side command execution failed (e.g. an XCM/command dispatch that reverts due to insufficient gas budget, target contract revert, etc. — situations that are expected to occur under normal operation, not requiring a malicious relayer, prover, or governance actor). The verifier check (beacon/Merkle proof) only attests that the log was emitted by the real Gateway; it says nothing about the `success` flag being `true`, so a fully honest submission of a real "failed dispatch" event still triggers full reward payment.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` when `receipt.success == true`. For `success == false`, define and take an explicit failure path (e.g. emit a `MessageDeliveryFailed` event, and either still remove the pending order without paying rewards, or requeue/handle refund logic depending on the intended reward semantics — but the fee must not be unconditionally paid to relayers for non-executed messages).

### Proof of Concept
1. A message is enqueued and processed by `do_process_message`, creating a `PendingOrder { nonce, fee, .. }` in storage. [6](#0-5) 
2. On Ethereum, the Gateway contract attempts to dispatch the corresponding command and it fails (e.g., reverts), so the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer builds a legitimate beacon/Merkle proof for this real (unmodified) event log and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (the proof is valid — no malicious prover needed), `DeliveryReceipt::try_from` decodes `success = false` correctly.
5. `process_delivery_receipt` ignores `success`, pays `order.fee` to `reward_account`, removes the `PendingOrder`, and emits `MessageDelivered { nonce }` — identical outcome to a successful delivery, as shown by the existing test asserting successful payout purely from proof validity: [7](#0-6)

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

// After governance resumes the bridge, legitimate delivery receipts flow through again:
// the order is paid out and removed from storage.
#[test]
fn submit_delivery_receipt_succeeds_after_unhalt() {
	new_tester().execute_with(|| {
		let nonce = 0;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_valid_event_proof());

		// Bridge halted — receipt rejected, order untouched.
		set_verifier_halted(true);
		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);
		assert!(PendingOrders::<Test>::get(nonce).is_some());

		// Bridge resumed — same receipt succeeds and the order is settled.
		set_verifier_halted(false);
		assert_ok!(OutboundQueue::submit_delivery_receipt(origin, event));
		assert!(PendingOrders::<Test>::get(nonce).is_none());

		System::assert_has_event(mock::RuntimeEvent::OutboundQueue(Event::MessageDelivered {
			nonce,
		}));
	});
}
