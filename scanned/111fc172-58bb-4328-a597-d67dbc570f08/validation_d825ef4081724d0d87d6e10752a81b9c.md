### Title
Admin's `burn` extrinsic in `pallet-assets` is blocked by the account-frozen check meant for ordinary transfers, contradicting the documented Admin override guarantee - (File: `substrate/frame/assets/src/functions.rs`)

### Summary
`pallet-assets` documents that the asset class's `admin` role is empowered to "thaw tokens, force transfers and burn tokens from any account" [3](#0-2) , and the pallet-level docs explicitly list `burn` as callable "from any account" by the Admin. However, the actual debit path used by `burn` re-applies the same per-account `Frozen`/`Blocked` status check that guards ordinary user-initiated transfers, with no bypass for the privileged caller — mirroring the rOUSG bug where `BURNER_ROLE` was blocked by a KYC check meant for regular transfers.

### Finding Description
The `burn` extrinsic is dispatched by any signed origin and internally passes that origin as `maybe_check_admin` to `do_burn`, which validates it equals `details.admin` before proceeding [4](#0-3) . `do_burn` then calls `decrease_balance`, which calls `prep_debit` [5](#0-4) .

`prep_debit` first calls `reducible_balance`, which unconditionally errors with `Error::<T, I>::Frozen` if the target account's `AccountStatus` is `Frozen` or `Blocked` [1](#0-0) , and separately calls `can_decrease`, which returns `WithdrawConsequence::Frozen` for the same condition [2](#0-1) . `AccountStatus::is_frozen()` returns `true` for both `Frozen` and `Blocked` states [6](#0-5) .

Crucially, an account's `Frozen` status is set by the `Freezer` role via the `freeze` extrinsic — a *different* role from `Admin` [7](#0-6) . Once frozen by the Freezer, the Admin's documented ability to "burn tokens from any account" is silently negated: `do_burn` (and hence the `burn` extrinsic) reverts with `Error::Frozen` for that account, exactly as `refund_other` was shown to revert with `Error::<Test>::Frozen` for a frozen account in the existing test suite [8](#0-7) . No `Fortitude::Force`-style override exists in `decrease_balance`/`prep_debit`/`can_decrease` to let the admin-checked burn path bypass this account-level freeze, unlike other parts of the codebase (e.g. `fungible::hold` traits) that explicitly support `Fortitude::Force` to bypass freezes for privileged operations like slashing [9](#0-8) .

### Impact Explanation
This breaks the documented separation-of-powers invariant of `pallet-assets`: the Freezer role (a lower-trust role intended only to prevent transfers) can unilaterally veto the Admin's ability to burn/clean up an account's balance, e.g., in incident response, compliance enforcement, or supply correction scenarios where the account was frozen specifically because it is compromised or malicious. This is a self-inflicted denial-of-service on a privileged administrative function via a check designed for regular user transfers — the same root cause pattern as the rOUSG finding, generalized to any Substrate chain configuring `pallet-assets` with distinct Admin/Freezer accounts (a common real-world setup, e.g. stablecoin or asset-hub style deployments).

### Likelihood Explanation
This requires no attacker at all beyond the ordinary, expected use of the Freezer role as designed (freezing a suspicious account) followed by the Admin attempting to burn that account's balance — a routine compliance/incident-response workflow. It is deterministically reproducible on every call, not a race condition or governance-abuse scenario.

### Recommendation
In `do_burn` (or `decrease_balance`/`prep_debit` when invoked from `do_burn`), bypass the account-level `AccountStatus::Frozen`/`Blocked` check when the caller has been validated against `details.admin` (i.e., add a `Fortitude::Force`-style parameter that `do_burn` sets when `maybe_check_admin` succeeds), consistent with how other force-capable primitives in the codebase (e.g. `fungible::hold::Mutate::burn_held`) already support ignoring freezes for privileged/administrative operations.

### Proof of Concept
1. Create asset `0` with owner=admin=1, freezer=2 via `force_create` + `set_team`.
2. `Assets::mint(signed(1), 0, 3, 100)` to give account `3` a balance.
3. `Assets::freeze(signed(2), 0, 3)` — Freezer freezes account `3` (sets `AccountStatus::Frozen`) [7](#0-6) .
4. `Assets::burn(signed(1), 0, 3, 100)` — Admin attempts to burn the frozen account's balance.
5. This reverts with `Error::<T, I>::Frozen` because `prep_debit`/`can_decrease` check `account.status.is_frozen()` unconditionally [2](#0-1) , even though `burn` is an Admin-only, permission-checked operation per the pallet documentation.
