Target: `SignatureSchema::verify_request_msg` webauthn variants (P256/Ed25519), contracts/wallet/signatures/webauthn/src/lib.rs `verify_hash`. Attacker action: attacker captures a legitimate webauthn `WalletWebauthnProof{signature, assertion}` produced for one `RequestMessage` hash H1, and since webauthn signs `authenticator_data || sha256(client_data_json)` where `client_data_json.challenge` embeds H1 as base64, attacker crafts a *different* `RequestMessage` (e.g. draining more funds) whose `.hash()` also happens to equal H1 by exploiting borsh-serialization ambiguity or a hash-truncation collision in how `msg.hash()` (32 bytes) is embedded as the webauthn `challenge`. Preconditions: signer previously authorized a small transfer producing hash H1; attacker searches for another Request whose canonical hash also equals H1 (would require a SHA3-256 collision, computationally infeasible directly, but attacker instead exploits any code path where the *same* proof string can be replayed against a *different* msg without hash re-verification). Call sequence: `verify_request_msg` recomputes `msg.hash()` fresh from the *new* msg and calls `verify_hash`, so any different msg produces different challenge and verification should fail. Binding: `proof` verifies against exactly the `msg.hash()` of the exact `Request` executed, none other. Impact: Critical if any msg field is excluded from `.hash()` (e.g. because of a `#[borsh(skip)]` or serde-only field not covered by borsh serialization) allowing a mutated Request to keep the same hash. Proof idea: cargo test enumerating every field of RequestMessage/Request and confirming each one changes `.hash()` output, closing any field-exclusion gap that could enable proof reuse across different executed requests.
