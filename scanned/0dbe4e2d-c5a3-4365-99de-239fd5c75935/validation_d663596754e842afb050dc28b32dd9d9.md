## Analysis

The RoyaltiesOracle bug is a cumulative-check invariant break: a per-entity value is added to a running total without ever removing the previous contribution for that same entity, so the running total silently drifts upward and eventually poisons a downstream check. The exact same broken invariant exists in `pallet-child-bounties`'s `ChildrenCuratorFees` accounting.

### Title
Child-bounty curator-fee accumulator is never decremented on `unassign_curator`, permanently locking parent-bounty funds - (File: `substrate/frame/child-bounties/src/lib.rs`)

### Summary
`propose_curator` unconditionally adds the proposed child-bounty fee to the parent's `ChildrenCuratorFees` accumulator whenever the child bounty is in the `Added` state [1](#0-0) . `unassign_curator` resets a child bounty's status back to `Added` from `CuratorProposed`/`Active`/`PendingPayout` without ever subtracting the fee that was previously added to `ChildrenCuratorFees` [2](#0-1) . Because `Added` is exactly the state required to call `propose_curator` again, a child bounty can be proposed and unassigned repeatedly, adding a new fee to the accumulator on every cycle while never removing the stale ones. This mirrors the RoyaltiesOracle flaw: the check/update treats the accumulator as if it only reflects the "current" entry, but it actually keeps summing every historical proposal for that child bounty.

### Finding Description
`ChildrenCuratorFees` is a per-parent-bounty running total, intended to represent "fees owed to active/paid child curators", which is later subtracted from the parent curator's fee at claim time via `children_curator_fees()` [3](#0-2) .

The only place this value is decremented is in `pallet_bounties::ChildBountyManager::children_curator_fees`, called once when the *parent* bounty is claimed, which removes the whole storage item [3](#0-2) . There is no decrement when a child bounty curator is unassigned before payout — even though `unassign_curator` explicitly transitions the child bounty back to `Added`, the very precondition `propose_curator` checks before adding a *new* fee to the same accumulator [4](#0-3) .

An unprivileged actor can trigger this loop entirely themselves:
1. Parent curator calls `propose_curator(parent, child, curator=X, fee=F1)` → `ChildrenCuratorFees += F1`.
2. `X` (the proposed curator, a normal signed account) self-unassigns via `unassign_curator` while status is `CuratorProposed` — this is explicitly permitted for the proposed curator with no slash [5](#0-4)  — status reverts to `Added`, but `ChildrenCuratorFees` still holds `F1`.
3. Parent curator (or any signer with permission) calls `propose_curator` again with a new fee `F2` → `ChildrenCuratorFees += F2`, now `F1 + F2`, even though only one child bounty exists and no curator fee was ever actually paid out.

Repeating this cycle grows `ChildrenCuratorFees` without bound, well past the parent bounty's own `fee`/`value`.

### Impact Explanation
`pallet_bounties::claim_bounty` uses `children_curator_fees(bounty_id)` to reduce the parent curator's payable fee: `final_fee = bounty.fee.saturating_sub(children_fee)`, while the beneficiary payout is computed from the original `bounty.value - bounty.fee` (not from `final_fee`). Once the accumulated `ChildrenCuratorFees` exceeds `bounty.fee` (achievable purely through the propose/unassign cycle above, with no bounty ever actually completing), `saturating_sub` clamps the parent curator's fee to zero. The difference between the original `fee` reserved for the curator and the zeroed-out `final_fee` is never transferred to anyone — it remains stranded in the bounty's pot account after the bounty record is removed on claim, permanently locking those funds. This falls squarely into the required-impact category of "permanent user-fund ... lock" through public, unprivileged, non-governance action.

### Likelihood Explanation
No admin, governance, validator, or privileged actor is required. Any account proposed as a child-bounty curator can self-unassign at the `CuratorProposed` stage with zero cost/slash, and the parent curator (who is not privileged relative to the parent-bounty/treasury governance — they are simply the assigned curator) can freely re-propose. The cycle is cheap (no deposit is reserved until `accept_curator`), repeatable, and entirely on-chain observable state (`ChildrenCuratorFees` storage item), making this straightforward to trigger deliberately or accidentally through normal curator churn.

### Recommendation
Subtract the child bounty's currently recorded `fee` from `ChildrenCuratorFees::<T>::get(parent_bounty_id)` inside `unassign_curator` whenever the previous status was `CuratorProposed`, `Active`, or `PendingPayout` (i.e., whenever a fee had actually been added for that child bounty), before resetting status to `Added` and clearing `child_bounty.fee`. This mirrors the RoyaltiesOracle fix of accounting for the specific entity's existing contribution before applying a new one, rather than only ever adding to the cumulative total.

### Proof of Concept
1. Treasury funds a parent bounty with `value = 100`, `fee = 50`; curator `C` accepted.
2. `C` calls `add_child_bounty(parent, value=10)` → child bounty `child_0` in `Added` state.
3. `C` calls `propose_curator(parent, child_0, X, fee=40)` → `ChildrenCuratorFees[parent] = 40` [6](#0-5) .
4. `X` calls `unassign_curator(parent, child_0)` (signed as the proposed curator, no penalty) → `child_0.status = Added`, but `ChildrenCuratorFees[parent]` remains `40` [5](#0-4) [7](#0-6) .
5. `C` calls `propose_curator(parent, child_0, Y, fee=40)` again → `ChildrenCuratorFees[parent] = 80`.
6. Repeat step 4–5 once more → `ChildrenCuratorFees[parent] = 120`, now exceeding the parent bounty's `fee = 50`.
7. `C` eventually cancels/finishes `child_0` (or it stays unassigned) and the parent bounty is claimed: `final_fee = fee.saturating_sub(children_fee) = 50.saturating_sub(120) = 0`. The curator `C` receives `0` fee instead of the deserved `50`, and that `50` remains stuck in the bounty's pot account after the bounty record is purged, permanently unrecoverable.

			origin: OriginFor<T>,
			#[pallet::compact] parent_bounty_id: BountyIndex,
			#[pallet::compact] child_bounty_id: BountyIndex,
			curator: AccountIdLookupOf<T>,
			#[pallet::compact] fee: BalanceOf<T>,
		) -> DispatchResult {
			let signer = ensure_signed(origin)?;
			let child_bounty_curator = T::Lookup::lookup(curator)?;

			let (curator, _) = Self::ensure_bounty_active(parent_bounty_id)?;
			ensure!(signer == curator, BountiesError::<T>::RequireCurator);

			// Mutate the child-bounty instance.
			ChildBounties::<T>::try_mutate_exists(
				parent_bounty_id,
				child_bounty_id,
				|maybe_child_bounty| -> DispatchResult {
					let child_bounty =
						maybe_child_bounty.as_mut().ok_or(BountiesError::<T>::InvalidIndex)?;

					// Ensure child-bounty is in expected state.
					ensure!(
						child_bounty.status == ChildBountyStatus::Added,
						BountiesError::<T>::UnexpectedStatus,
					);

					// Ensure child-bounty curator fee is less than child-bounty value.
					ensure!(fee < child_bounty.value, BountiesError::<T>::InvalidFee);

					// Add child-bounty curator fee to the cumulative sum. To be
					// subtracted from the parent bounty curator when claiming
					// bounty.
					ChildrenCuratorFees::<T>::mutate(parent_bounty_id, |value| {
						*value = value.saturating_add(fee)
					});

					// Update the child-bounty curator fee.
					child_bounty.fee = fee;

					// Update the child-bounty state.
					child_bounty.status =
						ChildBountyStatus::CuratorProposed { curator: child_bounty_curator };

					Ok(())
				},
			)
		}

	/// Returns cumulative child bounty curator fees for `bounty_id` also removing the associated
	/// storage item. This function is assumed to be called when parent bounty is claimed.
	fn children_curator_fees(bounty_id: pallet_bounties::BountyIndex) -> BalanceOf<T> {
		// This is asked for when the parent bounty is being claimed. No use of
		// keeping it in state after that. Hence removing.
		let children_fee_total = ChildrenCuratorFees::<T>::get(bounty_id);
		ChildrenCuratorFees::<T>::remove(bounty_id);
		children_fee_total
	}
