### Title
`redeem()` Skips Live Decimals Revalidation That `mint()` Enforces, Allowing Stale-Precision Redemption Miscalculation - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
`pallet-psm`'s `mint()` and `redeem()` both convert between an "internal" stablecoin and an "external" asset using per-asset decimal snapshots taken at `add_external_asset` time. `mint()` defensively re-validates that the live decimals of both assets still match those snapshots before doing any conversion, via `Self::ensure_decimals_match(...)` [1](#0-0) . `redeem()` performs no such check — it reads the stored snapshot values directly and feeds them straight into `internal_to_external` / `external_to_internal` [2](#0-1) . This is the same class of bug as the reported issue: a value with unvalidated decimal precision is trusted for a financial conversion, producing an incorrect amount calculation (here, the redeemed external-asset payout / burned internal-asset amount) for one of the two mirrored economic paths.

### Finding Description
`ensure_decimals_match` checks that `T::Fungibles::decimals(external_asset)` still equals the stored `external.decimals` snapshot and that `T::Fungibles::decimals(internal_asset)` still equals `info.internal_decimals`, returning `Error::DecimalsMismatch` on drift [3](#0-2) . `mint()` calls this helper before computing `internal_equivalent` and `effective_external` [4](#0-3) .

`redeem()`, however, pulls `ext_decimals` and `internal_decimals` straight from the stored structs without calling `ensure_decimals_match` or any live-metadata check at all [5](#0-4) , then uses those potentially-stale values to compute `external_out` and `effective_internal_net` [6](#0-5) .

The test suite itself documents this asymmetry: `mint_halts_when_asset_decimals_drift` and `mint_halts_when_internal_decimals_drift` assert that `mint()` returns `Error::DecimalsMismatch` once an asset owner changes live decimals via `Assets::set_metadata` [7](#0-6) [8](#0-7) , while `redeem_uses_snapshot_when_asset_decimals_drift` and `redeem_uses_snapshot_when_internal_decimals_drift` explicitly show `redeem()` continuing to succeed and settle amounts using the *old* snapshot decimals after the same drift, with no error and no halt [9](#0-8) .

The decimals value is not an oracle price feed, but it plays the exact same role as the unvalidated 18-decimal assumption in the reported bug: it is a precision parameter trusted, without re-verification at use time, to convert one asset amount into another for a balance-affecting operation. `pallet-assets` metadata `decimals` is caller-mutable by the asset's `Owner`/management origin at any time via `set_metadata`/`force_set_metadata`, independent of PSM governance, so this is not a "malicious admin of the PSM" or governance-abuse scenario — it is an external, unprivileged (relative to the PSM) asset manager unilaterally invalidating an assumption that only one of the two PSM entrypoints defends against.

### Impact Explanation
Because `PsmDebt` is denominated in internal-asset units and the 1:1 backing invariant between `PsmDebt` and the external reserve is only correct if the decimals pair used for conversion still reflects the actual token semantics, using a stale decimals pair in `redeem()` after a legitimate drift causes `external_to_internal` / `internal_to_external` to compute wrong exchange amounts. This can let a redeemer receive more external-asset than the burned internal-asset amount is actually worth (draining the PSM reserve disproportionately, i.e., unbacked value extraction from a shared reserve funded by other PSM depositors) or receive less (locking value the redeemer should have received), while the pallet's own defensive invariant checker (`do_try_state`) assumes `reserve >= debt_as_external` computed via the same conversion helper, so the drift can silently desynchronize actual token backing from tracked debt without tripping the invariant check itself (it uses the same stale decimals) [10](#0-9) . This falls under asset-accounting / fund-conservation impact: value is not settled exactly once to the rightful beneficiary and amount once decimals drift, because one of the two mirrored entrypoints omits the guard the other enforces.

### Likelihood Explanation
Triggering the drift only requires being the metadata-management authority of the *external* or *internal* asset in `pallet-assets` (an ordinary, non-privileged-to-the-PSM asset owner/admin) calling `set_metadata`/`force_set_metadata` to change `decimals` — no validator, collator, governance, or PSM-admin privilege is needed. This is a realistic misconfiguration/drift scenario the pallet authors clearly anticipated (hence building `ensure_decimals_match` and covering it with dedicated `mint` tests), but the guard was not applied symmetrically to `redeem`.

### Recommendation
Call `Self::ensure_decimals_match(&info, &internal_asset, &external_asset, &external)?` at the start of `redeem()`, exactly as `mint()` does, before deriving `ext_decimals`/`internal_decimals` and performing any conversion, so redemption halts with `Error::DecimalsMismatch` on live/snapshot divergence just like minting does.

### Proof of Concept
1. Register `USDX` (2 decimals) as an approved external on a PSM with 6-decimal internal via `add_external_asset` — this snapshots `decimals: 2` into `ExternalAssetInfo`.
2. A user mints internal asset against `USDX`, building up `PsmDebt` and reserve as usual.
3. `USDX`'s asset owner (unprivileged w.r.t. the PSM) calls `pallet_assets::Assets::set_metadata` to change USDX's live decimals from 2 to 4 (test scaffold shown at [11](#0-10) ).
4. Calling `Psm::mint` now correctly fails with `Error::DecimalsMismatch` (per existing test) — but calling `Psm::redeem` for the same asset pair still succeeds, using the stale `decimals: 2` snapshot in `internal_to_external`/`external_to_internal` instead of the live `4`, as shown by the existing `redeem_uses_snapshot_when_asset_decimals_drift` test flow [12](#0-11) .
5. Because the conversion factor used no longer matches the live/actual decimal semantics, the computed `external_out` is wrong relative to what a decimals-consistent system would compute, letting the redeemer extract an incorrect (potentially excessive) amount of external reserve per unit of internal asset burned, while `PsmDebt` bookkeeping and the `do_try_state` reserve-vs-debt check both keep using the same stale factor and therefore do not detect the inconsistency.

		pub(crate) fn ensure_decimals_match(
			info: &PsmInfo<T>,
			internal_asset: &T::AssetId,
			external_asset: &T::AssetId,
			external: &ExternalAssetInfo,
		) -> Result<(u8, u8), DispatchError> {
			ensure!(
				T::Fungibles::decimals(external_asset.clone()) == external.decimals,
				Error::<T>::DecimalsMismatch
			);
			ensure!(
				T::Fungibles::decimals(internal_asset.clone()) == info.internal_decimals,
				Error::<T>::DecimalsMismatch
			);
			Ok((external.decimals, info.internal_decimals))
		}

	fn redeem_uses_snapshot_when_asset_decimals_drift() {
		new_test_ext().execute_with(|| {
			register_external_asset_with_weight(USDX_ASSET_ID, Permill::from_percent(100));
			set_zero_fees(USDX_ASSET_ID);

			// Mint first, then change decimals.

				Permill::zero()
			));

				RuntimeOrigin::signed(ALICE),

				b"USDX".to_vec(),
				b"USDX".to_vec(),
				4
			));

			let alice_usdx_before = get_asset_balance(USDX_ASSET_ID, ALICE);
			let alice_internal_before = get_asset_balance(INTERNAL_ASSET_ID, ALICE);

	#[test]
	fn redeem_uses_snapshot_when_internal_decimals_drift() {
		new_test_ext().execute_with(|| {
			// Seed ALICE's internal balance and PSM reserve with a prior mint, then
			// drift the internal asset's decimals.
			assert_ok!(Psm::mint(
				RuntimeOrigin::signed(ALICE),
				INTERNAL_ASSET_ID,
				USDC_ASSET_ID,
				1000 * INTERNAL_UNIT,
				Permill::from_percent(1)
			));
			assert_ok!(Assets::set_metadata(
				RuntimeOrigin::signed(ALICE),
				INTERNAL_ASSET_ID,
				b"INTERNAL".to_vec(),
				b"INTERNAL".to_vec(),
				8
			));

			let alice_usdc_before = get_asset_balance(USDC_ASSET_ID, ALICE);
			let alice_internal_before = get_asset_balance(INTERNAL_ASSET_ID, ALICE);
			let insurance_internal_before = get_asset_balance(INTERNAL_ASSET_ID, INSURANCE_FUND);
			let debt_before = PsmDebt::<Test>::get(INTERNAL_ASSET_ID, USDC_ASSET_ID);
			let redeem = 100 * INTERNAL_UNIT;
			let fee = Permill::from_percent(1).mul_ceil(redeem);
			let external_out = redeem - fee;

			assert_ok!(Psm::redeem(
				RuntimeOrigin::signed(ALICE),
				INTERNAL_ASSET_ID,
				USDC_ASSET_ID,
				redeem,
				Permill::from_percent(1)
			));

			assert_eq!(get_asset_balance(USDC_ASSET_ID, ALICE), alice_usdc_before + external_out);
			assert_eq!(get_asset_balance(INTERNAL_ASSET_ID, ALICE), alice_internal_before - redeem);
			assert_eq!(
				get_asset_balance(INTERNAL_ASSET_ID, INSURANCE_FUND),
				insurance_internal_before + fee
			);
			assert_eq!(
				PsmDebt::<Test>::get(INTERNAL_ASSET_ID, USDC_ASSET_ID),
				debt_before - external_out
			);
		});
	}
