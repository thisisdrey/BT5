### Title
First equivocation reporter's slash-reward entitlement is silently overwritten and stolen when a second, more severe report arrives for the same validator/era - ([File: substrate/frame/staking-async/src/pallet/impls.rs])

### Summary
`Staking::on_new_offences` (called for every offence relayed from the relay chain, including offences generated by public, unpermissioned calls such as `report_equivocation`/`report_double_voting` in `pallet-babe`, `pallet-grandpa`, and `pallet-beefy`) stores a single `OffenceRecord` per `(offence_era, validator)` key in `OffenceQueue`. When a second report for the same offender/era arrives with a strictly higher `slash_fraction`, the code overwrites the whole `OffenceRecord`, including the `reporter` field, discarding the first reporter entirely. When the offence is eventually processed, only the *last* reporter recorded in the (single-slot) `OffenceRecord.reporter` is paid the `SlashRewardFraction`-derived reward, even though the first, still-valid report already contributed slash amount that is baked into the final payout. This mirrors the Angle `disputeTree()`/`resolveDispute()` bug class: a single mutable "current claimant" storage slot tied to a future payout is overwritten by a later caller before settlement, causing the original valid party to receive nothing.

### Finding Description
`on_new_offences` in `substrate/frame/staking-async/src/pallet/impls.rs` processes each incoming offence and stores/updates `OffenceQueue::<T>::get(offence_era, &validator)`: [1](#0-0) 

If an `OffenceRecord` already exists for `(offence_era, validator)` and the new report's `slash_fraction` is strictly greater than the existing one, the pallet does:

```rust
OffenceRecord {
    reporter: o.reporters.first().cloned(),
    reported_era: active_era.index,
    slash_fraction,
    ..existing
}
```

This unconditionally replaces `reporter` with the new report's reporter, dropping the previous `reporter` entirely — there is no mechanism to retain, split reward between, or otherwise compensate the earlier reporter. `OffenceRecord` (defined in `substrate/frame/staking-async/src/slashing.rs`) only has a single `Option<AccountId>` slot for the reporter: [2](#0-1) 

When the queued offence is finally processed, `process_offence` copies the (now-overwritten) `offence_record.reporter` onto the `UnappliedSlash`: [3](#0-2) 

and `pay_reporters` only pays that single stored reporter — the actual first reporter who legitimately reported and validated the offence at an earlier point in time, and whose report is what allowed the `prior_slash_fraction` baseline to exist, receives zero reward: [4](#0-3) 

The module doc itself documents this as intended "duplicate handling" behavior ("If an offence already exists for the same validator in the same era, only the higher slash fraction is kept") but omits that the reporter credit for the earlier (still valid) contribution is also destroyed: [5](#0-4) 

This is structurally identical to the Angle `disputeTree`/`resolveDispute` bug: a single mutable storage slot (`disputer` in Angle, `OffenceRecord.reporter` here) that is supposed to identify who is entitled to a future payout, but can be overwritten by a subsequent, unprivileged, and independently-valid action before the payout is settled, causing the payout to go entirely to the later party and none to the original one.

The entry point is fully public and unprivileged: `report_equivocation`/`report_equivocation_unsigned` in `pallet-babe`, `pallet-grandpa`, and `report_double_voting`/`report_double_voting_unsigned` in `pallet-beefy` are all `ensure_signed`/`ensure_none` callable by anyone with a valid proof: [6](#0-5) [7](#0-6) 

No existing guard prevents this: the only defense is the "keep higher slash fraction" comparison, which is designed to protect against *under*-slashing, not to protect the *first reporter's* reward attribution. There is no accumulation/array of reporters per era-slot, only `Option<AccountId>` — this is an architectural single-slot conflict identical to Angle's single `disputer` variable.

### Impact Explanation
An honest reporter who is first to submit a valid, severe misbehavior report (equivocation/double-voting) for a validator can have their `SlashRewardFraction`-based reward reassigned entirely to a second reporter who later reports an unrelated, independently-discovered, more severe offence by the *same* validator in the *same* era — even though the first report's contribution is still reflected in the final slash amount via `prior_slash_fraction`. This is fund misdirection to the wrong beneficiary for value that should have been split or attributed to the original reporter, discouraging honest, timely offence reporting (which underpins consensus safety) and violating the "settle exactly once to the rightful beneficiary" invariant.

### Likelihood Explanation
The scenario requires only that a validator commits two independently-valid, provable offences (e.g., two separate equivocations) in the same era, reported by two different unprivileged signed accounts, with the second report carrying a higher `slash_fraction`. This does not require any malicious peer, node, validator, collator, governance actor, or leaked key — any two ordinary network participants who each construct valid equivocation proofs trigger this. A validator being Byzantine enough to double-sign more than once in an era, while uncommon, is exactly the scenario the slashing system is designed to handle and reward reporters for; the current logic actively disincentivizes the first (lower-severity) report.

### Recommendation
Do not treat `OffenceRecord.reporter` as a single overwritable slot when a new, higher-severity report supersedes an existing queued offence for the same `(era, validator)`. Instead, accumulate all distinct reporters (bounded) across superseding reports for that slot, and split the `SlashRewardFraction` reward proportionally among them at settlement time — mirroring the model used for reporters passed within a single `Offence` (`reporters: Vec<AccountId>`), which already supports fair splitting via `pay_reporters`. At minimum, refuse to discard the previous reporter's credit when overwriting `slash_fraction`.

### Proof of Concept
1. Validator `V` is bonded in era `E`. Attacker/observer `R1` discovers and reports a valid equivocation for `V` in era `E` with `slash_fraction = 10%` via `Grandpa::report_equivocation(origin=R1, proof1, key_owner_proof1)`. `on_new_offences` creates `OffenceQueue[(E, V)] = OffenceRecord { reporter: Some(R1), slash_fraction: 10%, ... }` (see `substrate/frame/staking-async/src/pallet/impls.rs:1570-1589`).
2. Before this offence is processed (it sits in `OffenceQueue`/`OffenceQueueEras` until `on_initialize` drains it — can be several blocks, cf. `offence_discarded_correctly` test showing the record stays queued across blocks), a different, unrelated account `R2` reports a second, independently valid equivocation for the *same* `V` in the *same* era `E`, with `slash_fraction = 15%`, via `Grandpa::report_equivocation(origin=R2, proof2, key_owner_proof2)`.
3. `on_new_offences` sees `existing = OffenceRecord{reporter: Some(R1), slash_fraction: 10%}` and `slash_fraction(15%) > existing.slash_fraction(10%)`, so it executes the overwrite branch at `substrate/frame/staking-async/src/pallet/impls.rs:1534-1545`, setting `OffenceQueue[(E,V)] = OffenceRecord{reporter: Some(R2), slash_fraction: 15%, prior_slash_fraction: 0%, ...}` — `R1` is gone from storage.
4. When the offence is processed, `process_offence` (`substrate/frame/staking-async/src/slashing.rs:415`) sets `unapplied.reporter = Some(R2)`, and `pay_reporters` (`substrate/frame/staking-async/src/slashing.rs:658-688`) pays the entire `SlashRewardFraction * slash` reward to `R2` only. `R1`, despite submitting the first, fully valid report that established the baseline slash, receives nothing — confirmed by the existing test `only_first_reporter_receive_the_slice` (`substrate/frame/staking-async/src/tests/slashing.rs:189-227`), which shows that even the "first" position in a single reporters list is what matters for payout, and `offence_discarded_correctly` (`substrate/frame/staking-async/src/tests/slashing.rs:1982-2033`), which explicitly demonstrates the record (and thus the associated reporter) at `(era, validator)` being unconditionally overwritten on a higher slash fraction report.

	/// The account ID of the entity that reported the offence.

	/// Era at which the offence was reported.
	pub reported_era: EraIndex,

	/// If a new, higher slash fraction is reported, this field stores the prior fraction
	/// that was overwritten. This helps in tracking changes in slashes across multiple reports for
	/// the same era.

}

/// Apply a reward payout to some reporters, paying the rewards out of the slashed imbalance.
fn pay_reporters<T: Config>(
	reward_payout: BalanceOf<T>,
	slashed_imbalance: NegativeImbalanceOf<T>,
	reporters: &[T::AccountId],
) {
	if reward_payout.is_zero() || reporters.is_empty() {
		// nobody to pay out to or nothing to pay;
		// just treat the whole value as slashed.
		T::Slash::on_unbalanced(slashed_imbalance);
		return;
	}

	// take rewards out of the slashed imbalance.
	let reward_payout = reward_payout.min(slashed_imbalance.peek());
	let (mut reward_payout, mut value_slashed) = slashed_imbalance.split(reward_payout);

	let per_reporter = reward_payout.peek() / (reporters.len() as u32).into();
	for reporter in reporters {
		let (reporter_reward, rest) = reward_payout.split(per_reporter);
		reward_payout = rest;

		// this cancels out the reporter reward imbalance internally, leading
		// to no change in total issuance.
		asset::deposit_slashed::<T>(reporter, reporter_reward);
	}

	// the rest goes to the on-slash imbalance handler (e.g. treasury)
	value_slashed.subsume(reward_payout); // remainder of reward division remains.
	T::Slash::on_unbalanced(value_slashed);
}
