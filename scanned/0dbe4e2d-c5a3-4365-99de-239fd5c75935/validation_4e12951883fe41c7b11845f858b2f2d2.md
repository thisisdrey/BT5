## Finding [1](#0-0) 

The Berachain `distributeFor` bug is a textbook Checks-Effects-Interactions violation: read state → external transfer → update state. The repository contains an exact structural analog in `pallet_asset_rewards::Pallet::harvest_rewards`.

### Title
`harvest_rewards` transfers reward tokens before clearing the staker's reward balance, violating Checks-Effects-Interactions - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`harvest_rewards` is a public, unprivileged extrinsic that any staker (or, once a pool has expired, any caller on behalf of a staker) can invoke. It computes `staker_info.rewards`, then calls `T::Assets::transfer(...)` to move that amount out of the pool account to the staker, and only *afterwards* resets `staker_info.rewards = 0u32.into()` and writes the updated (or removed) `PoolStakers` entry back to storage.

### Finding Description [2](#0-1) 

```

    PoolStakers::<T>::remove(&pool_id, &staker);
} else {

```

The "interaction" (`T::Assets::transfer`) occurs strictly before the "effect" that would prevent double-spending (`staker_info.rewards = 0` and the corresponding `PoolStakers` write). This is the same ordering flaw as `Distributor.distributeFor`, where the incentive transfer preceded the `nextActionableBlock` increment. `T::Assets` is a generic, pallet-configurable `fungibles::Mutate` (in shipped runtimes wired to `NativeAndAllAssets`, see `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs:572` and `asset-hub-rococo/src/lib.rs:1074`), so the pallet itself does not control or bound what code path executes for an arbitrary configured `AssetId`/asset backend during the transfer — the pallet's own accounting update happens only after that external call returns.

### Impact Explanation
If the reward-asset transfer path used by any given runtime's `T::Assets` implementation can synchronously execute further logic before returning (e.g. a composed/foreign asset backend, hold/freeze hooks, or any future asset kind that performs additional dispatch as part of crediting the destination), a caller that can trigger a second invocation of `harvest_rewards` for the same `(pool_id, staker)` during that window would be paid out against the stale, not-yet-zeroed `staker_info.rewards`, allowing the pool's reward pot to be drained beyond what was actually accrued — the same "loss of BGT and incentive tokens" outcome described in the report, but against the pool's reward asset balance instead.

### Likelihood Explanation
This is a public, permissionless extrinsic (`ensure_signed` only) reachable by any staker with a nonzero reward balance, so no privileged/validator/relayer assumption is required to reach the vulnerable code path — satisfying the "unprivileged attacker, public entrypoint" bar. The actual exploitability, however, depends on whether the concrete `T::Assets` implementation wired into a given runtime ever permits a callback/re-entry to the pallet before returning from `transfer` (none of the currently-shipped `NativeAndAllAssets`/pallet-assets backends demonstrate this today). The code is nonetheless a genuine CEI violation independent of that: the accounting state (`staker_info.rewards`, `PoolStakers`) is left stale across an external call, which is exactly the anti-pattern the report flags, and it should be fixed regardless of whether a currently-configured backend can exploit it.

### Recommendation
Apply the same fix Berachain used: reorder the code so the effects happen before the interaction — zero `staker_info.rewards` and write/remove the `PoolStakers` entry *before* calling `T::Assets::transfer`, mirroring the pattern already used correctly in `nomination-pools::do_reward_payout` ( [3](#0-2) ), where `member.last_recorded_reward_counter` and `reward_pool.register_claimed_reward(pending_rewards)` are updated before the `T::Currency::transfer` call.

### Proof of Concept
1. Staker `S` stakes into a pool with `reward_asset_id` set (at pool creation, an admin-controlled parameter) to an asset backend whose `fungibles::Mutate::transfer` can invoke further logic before returning (e.g., a custom/foreign asset implementation plugged into `T::Assets`).
2. `S` accrues `staker_info.rewards = R` and calls `harvest_rewards(pool_id, None)`.
3. During the `T::Assets::transfer(reward_asset_id, pool_account, S, R, Expendable)` call, before it returns, a second `harvest_rewards(pool_id, None)` call is triggered for the same `(pool_id, S)`.
4. Because `staker_info.rewards` is still `R` in storage (not yet reset), the second call re-reads `R` from `PoolStakers` and transfers `R` again, doubling the payout from the pool account (or draining it) relative to what was actually accrued.

		/// Harvest unclaimed pool rewards.
		///
		/// Parameters:
		/// - origin: must be the `staker` if the pool is still active. Otherwise, any account.
		/// - pool_id: the pool to harvest from.
		/// - staker: the account for which to harvest rewards. If `None`, the caller is used.
		#[pallet::call_index(3)]
		pub fn harvest_rewards(
			origin: OriginFor<T>,
			pool_id: PoolId,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool and staker rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info =
				PoolStakers::<T>::get(pool_id, &staker).ok_or(Error::<T>::NonExistentStaker)?;
			let (pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Transfer unclaimed rewards from the pool to the staker.
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&staker,
				staker_info.rewards,
				// Could kill the account, but only if the pool was already almost empty.
				Preservation::Expendable,
			)?;

			// Emit event.
			Self::deposit_event(Event::RewardsHarvested {
				caller,
				staker: staker.clone(),
				pool_id,
				amount: staker_info.rewards,
			});

			// Reset staker rewards.
			staker_info.rewards = 0u32.into();

			if staker_info.amount.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			Ok(())
		}
