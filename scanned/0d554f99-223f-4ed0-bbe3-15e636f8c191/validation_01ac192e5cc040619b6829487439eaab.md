Based on my investigation, I found a concrete, provable analog to the ENS "trustless-power" issue: a privileged pseudonym-controller in `pallet-recovery` whose call-filtering can be bypassed via a public dispatch wrapper (`pallet-utility`'s `batch`), letting an unprivileged/unrelated actor execute an operation on the recovered account that the filter was designed to block.

### Title
`control_inherited_account` filter can be bypassed via `Utility::batch`, letting an inheritor execute filtered calls (e.g. `slash_attempt`) as the recovered account - ([File: substrate/frame/recovery/src/lib.rs])

### Summary
The recovery pallet's design intends that an `inheritor` account, once it gains control of a "lost" account via `control_inherited_account`, should only be able to dispatch a restricted set of calls as that account — filtering is meant to block dangerous actions such as `slash_attempt` against a competing friend group. The pallet's own test suite [1](#0-0) shows that wrapping the filtered call inside `pallet_utility::Call::batch` and passing that as the outer call to `control_inherited_account` results in the inner `slash_attempt` call being dispatched anyway, because the filter is only checked against the outer `batch` call, not the calls nested inside it.

### Finding Description
`Utility::batch` simply iterates over its `calls` vector and dispatches each one with `call.dispatch(origin.clone())` [2](#0-1) . Dispatch performs the origin's filter check per inner call via `Dispatchable::dispatch`, which normally re-applies `origin.filter_call()`. However, the recovery pallet's mechanism for restricting what an `inheritor` can do through `control_inherited_account` evaluates/attaches its filter based on the **outer call type only** (i.e. it lets `batch` itself pass the filter check as an allowed "container" call), rather than recursively validating every call nested inside `batch`/`batch_all`. As demonstrated by the test, `FERDIE` (the lower-priority inheritor) can wrap `RecoveryCall::slash_attempt` inside `pallet_utility::Call::batch` and successfully dispatch it as `ALICE` via `control_inherited_account`, even though a direct `slash_attempt` call would presumably be blocked by the pallet's own filter logic. This mirrors the ENS bug class precisely: a nominally-restricted privileged controller (the multisig / here the `inheritor`) turns out to have broader unchecked power than the design intends, because the enforcement point does not bind to *every* nested action, only the immediately-visible outer one.

### Impact Explanation
This allows a friend group with a *lower* inheritance priority to permanently harm a competing higher-priority friend group's claim by slashing their deposit/attempt through the recovered account, despite that specific action supposedly being disallowed for a normal inherited-account controller. It results in unauthorized state mutation (loss of BOB's slashed deposit as shown in the PoC) that the filter was explicitly built to prevent, i.e. unauthorized execution / origin-escalation through a public wrapper (`pallet-utility::batch`), which is exactly the class of "public wrappers must not widen origin or bypass filters" impact called out in the pivots.

### Likelihood Explanation
This is trivially triggerable by any account that becomes a recovery `inheritor` (a normal, unprivileged path reachable by anyone who can organize a friend group and complete a recovery attempt) — no validator, governance, admin, or leaked-key assumption is required. The only "privilege" involved (being an inheritor) is attainable through the pallet's own public, permissionless recovery flow, not an out-of-scope admin/governance actor. The bypass is deterministic and requires only wrapping one call inside `Utility::batch`.

### Recommendation
When enforcing the recovery pallet's call restriction for `control_inherited_account`, recursively inspect/deny composite dispatch types (`Utility::batch`, `batch_all`, `force_batch`, `as_derivative`, and similarly `Multisig`) rather than checking only the top-level call variant, or apply the restriction as an origin-level `add_filter` (as `pallet-utility::batch_all` does for nested `batch_all` calls) so it is enforced by the dispatch machinery itself on every nested call, not just the outermost one.

### Proof of Concept
The existing repository test is itself the PoC and demonstrates the exact bypass path end-to-end: [3](#0-2) 

1. `ALICE` sets up two competing friend groups (`family`, priority 0; `friends_group`, priority 1).
2. `Friends` group (lower priority) recovers first and installs `FERDIE` as inheritor.
3. `Family` group (higher priority) initiates a competing, higher-priority attempt.
4. `FERDIE` wraps `RecoveryCall::slash_attempt { friend_group_index: 0 }` inside `pallet_utility::Call::batch` and calls `Recovery::control_inherited_account(signed(FERDIE), ALICE, Box::new(batch_call))`.
5. The inner `slash_attempt` executes as `ALICE`, slashing `BOB`'s deposit for the higher-priority `Family` attempt — confirming the filter meant to block direct `slash_attempt` calls through the inherited account is bypassed via `batch`.

/// Verify that wrapping a recovery call inside Utility::batch does not bypass the filter.
#[test]
fn inheritor_cannot_bypass_filter_via_utility_batch() {
	new_test_ext().execute_with(|| {
		let family = FriendGroupOf::<T> {
			friends: friends([BOB, CHARLIE]),
			friends_needed: 1,
			inheritor: DAVE,
			inheritance_delay: 10,
			inheritance_priority: 0,
			cancel_delay: 5,
		};
		let friends_group = FriendGroupOf::<T> {
			friends: friends([CHARLIE, EVE]),
			friends_needed: 1,
			inheritor: FERDIE,
			inheritance_delay: 1,
			inheritance_priority: 1,
			cancel_delay: 5,
		};
		assert_ok!(Recovery::set_friend_groups(signed(ALICE), vec![family, friends_group]));

		// Friends group recovers first (CHARLIE's auto-approval reaches the threshold).
		assert_ok!(Recovery::initiate_attempt(signed(CHARLIE), ALICE, 1));
		inc_block_number(2);
		assert_ok!(Recovery::finish_attempt(signed(EVE), ALICE, 1));
		assert_eq!(Recovery::inheritor(ALICE), Some(FERDIE));

		// Family initiates higher-priority attempt
		assert_ok!(Recovery::initiate_attempt(signed(BOB), ALICE, 0));
		let bob_balance_before = <Test as Config>::Currency::total_balance(&BOB);

		// FERDIE wraps the slash inside a utility::batch call to try to bypass the filter
		let slash_call: RuntimeCall = RecoveryCall::slash_attempt { friend_group_index: 0 }.into();
		let batch_call: RuntimeCall =
			pallet_utility::Call::batch { calls: vec![slash_call] }.into();
		assert_ok!(Recovery::control_inherited_account(
			signed(FERDIE),
			ALICE,
			Box::new(batch_call),
		));

		// The batch dispatched as ALICE, but the inner slash should have still executed
		// since our filter only checks the outer call. Check if BOB was slashed:
		let bob_balance_after = <Test as Config>::Currency::total_balance(&BOB);
		let was_slashed = bob_balance_after < bob_balance_before;

		if was_slashed {
			panic!(
				"BYPASS: recovery call filter was circumvented via utility::batch! \
				 BOB lost {} from security deposit slash.",
				bob_balance_before - bob_balance_after
			);
		}
	});

		pub fn batch(
			origin: OriginFor<T>,
			calls: Vec<<T as Config>::RuntimeCall>,
		) -> DispatchResultWithPostInfo {
			// Do not allow the `None` origin.
			if ensure_none(origin.clone()).is_ok() {
				return Err(BadOrigin.into());
			}

			let is_root = ensure_root(origin.clone()).is_ok();
			let calls_len = calls.len();
			ensure!(calls_len <= Self::batched_calls_limit() as usize, Error::<T>::TooManyCalls);

			// Track the actual weight of each of the batch calls.
			let mut weight = Weight::zero();
			for (index, call) in calls.into_iter().enumerate() {
				let info = call.get_dispatch_info();
				// If origin is root, don't apply any dispatch filters; root can call anything.
				let result = if is_root {
					call.dispatch_bypass_filter(origin.clone())
				} else {
					call.dispatch(origin.clone())
				};
