### Title
`PendingOrders` fee never released or reclaimed if delivery receipt is never submitted — permanent lock of relayer reward in Snowbridge outbound queue v2 - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The Snowbridge `outbound-queue-v2` pallet earmarks a relayer fee for every outbound message by inserting a `PendingOrder{nonce, fee, block_number}` into the `PendingOrders` map at commit time [1](#0-0) . The fee is only ever released to a relayer — and the order only ever removed — inside `process_delivery_receipt`, which requires an Ethereum-side delivery receipt to be submitted through `submit_delivery_receipt` [2](#0-1) . There is no permissionless expiry, timeout, or fallback path that lets anyone reclaim/settle an order whose receipt is never submitted. This mirrors the external report's core invariant break: value is earmarked for a specific counterparty action (receiver calling `allocateNewEmissions` / relayer calling `submit_delivery_receipt`), and if that counterparty never performs the action — which can easily happen once the incentive to do so disappears — the earmarked value is permanently unreachable, with no way for anyone (including governance in the general case) to reclaim or reallocate it back into productive accounting state.

### Finding Description
When a message is queued for delivery, `do_process_message` builds an `OutboundMessage`, computes the merkle leaf, and stores a `PendingOrder` keyed by `nonce` holding the message's `fee` [1](#0-0) . This fee is described explicitly as being "attached in the message" for later reward payment: "When the message is processed on ethereum side, the relayer will send the nonce back with delivery proof, only after that the order can be resolved and the fee will be rewarded to the relayer" [1](#0-0) .

The only code path that removes a `PendingOrder` and pays out its fee is `process_delivery_receipt`, invoked from `submit_delivery_receipt` after verifying an Ethereum-side proof: [2](#0-1) 

There is no other extrinsic, hook, or `on_idle`/`on_initialize` sweep that inspects stale `PendingOrders` (e.g. by `block_number`) and either refunds the fee to the sender or moves it back into a reusable/unallocated pool. Compare this to `pallet-treasury`, which explicitly tracks `expire_at` on every `SpendStatus` and provides `check_status`/expiry cleanup so that a payout which is never claimed is removed and does not permanently strand funds [3](#0-2) , or `pallet-staking-async`'s era-pot `drain` function which explicitly sweeps unclaimed era rewards into an `UnclaimedRewardHandler` once they age out, rather than letting them sit forever [4](#0-3) . No analogous cleanup/expiry/permissionless-drain mechanism exists for `PendingOrders` in `outbound-queue-v2`.

This is functionally identical to the reported bug: `Vault::_allocateTotalWeekly` earmarks tokens for a receiver, and only that receiver's call to `allocateNewEmissions` can release/reintegrate them; if the receiver never calls it (e.g., because it was disabled and has no incentive), the tokens are permanently stuck. Here, the pallet earmarks a fee for a specific relayer action (`submit_delivery_receipt`); if no relayer ever submits a valid receipt (e.g., the bridge was halted for an extended period so receipts were rejected — see the halted-verifier PR discussion — or the destination command becomes uneconomical/impossible to execute on Ethereum, or the receipt is simply never produced due to any off-chain failure), the order and its earmarked fee remain in `PendingOrders` indefinitely, and the tokens backing that fee (already collected/reserved when the message was accepted) can never be paid out, refunded, or reused.

### Impact Explanation
The `fee` recorded in a `PendingOrder` represents value already committed to the outbound-queue's accounting for eventual payout to a relayer. If the corresponding delivery receipt never arrives, this value is unrecoverable: it cannot be claimed by the intended relayer (there is no proof to submit), cannot be refunded to the message sender, and cannot be swept by governance or any permissionless caller back into a usable pot. Over time — particularly during extended bridge halts, gateway migrations, or messages whose destination commands stop being deliverable — this leads to a growing set of permanently orphaned `PendingOrders`, each representing value that is functionally lost from correct accounting, matching "permanent user-fund or bridge-state lock" and "duplicate settlement or payout" classes of impact for the Snowbridge program scope.

### Likelihood Explanation
No malicious actor, validator, relayer, or governance action is required to trigger this: it happens purely from the *absence* of an action (a relayer simply not submitting a delivery receipt), exactly as in the original report where the *absence* of a disabled receiver calling `allocateNewEmissions` caused the loss. Given that receipts depend on external relayer behavior and can be blocked or made uneconomical by ordinary events (halted verifier periods lasting long enough that relayers move on, Ethereum-side reverts, gateway address changes), it is realistic that some fraction of `PendingOrders` will never be resolved, and no path exists to remediate this without a hard-fork/storage migration.

### Recommendation
Add either a permissionless or governance-triggered path to resolve stale `PendingOrders`:
- Track `block_number` (already stored) against a configurable `OrderExpiry` and allow any account to call a new extrinsic (e.g., `reap_expired_order`) that reclaims/refunds an order's fee once it is older than the expiry, similar to treasury's `expire_at`/`check_status` pattern [3](#0-2) .
- Alternatively, mirror `staking-async`'s `EraRewardManager::drain` pattern: periodically sweep orders past a bound into an `UnclaimedRewardHandler`-style sink so the value is not permanently orphaned [4](#0-3) .

### Proof of Concept
Conceptual sequence (matches the existing `submit_delivery_receipt_succeeds_after_unhalt` test structure in `bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs`, lines 420-449, but showing the negative case):
1. `do_process_message` is invoked for a message with `fee = F > 0`, inserting `PendingOrders::<T>::insert(nonce, PendingOrder{nonce, fee: F, block_number: N})` [1](#0-0) .
2. No relayer ever calls `submit_delivery_receipt` for this `nonce` (e.g., the verifier is halted for a long period as tested in `poc_m1` [5](#0-4) , and by the time it is unhalted no relayer bothers, or the receipt log can no longer be produced).
3. `PendingOrders::<T>::get(nonce)` still returns `Some(order)` indefinitely; `process_delivery_receipt` is the only function that can consume it [6](#0-5) .
4. There is no other call in the pallet (`Call` enum only exposes `submit_delivery_receipt` per the module doc [7](#0-6) ) that can remove or resolve this order — the fee `F` is permanently orphaned in the pallet's accounting with no path to payout, refund, or reallocation.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

			let now = T::BlockNumberProvider::current_block_number();

			if now > spend.expire_at && !matches!(spend.status, State::Attempted { .. }) {
				// spend has expired and no further status update is expected.
				Spends::<T, I>::remove(index);
				Self::deposit_event(Event::<T, I>::SpendProcessed { index });
				return Ok(Pays::No.into());
			}

				State::Attempted { id } => id,
				_ => return Err(Error::<T, I>::NotAttempted.into()),
			};

				Status::Failure => {
					spend.status = PaymentState::Failed;
					Spends::<T, I>::insert(index, spend);

				Status::Success | Status::Unknown => {

					Self::deposit_event(Event::<T, I>::SpendProcessed { index });
					return Ok(Pays::No.into());

	/// Drains an era pot's remaining balance to the unclaimed reward handler.
	///
	/// The pot account itself is kept alive (provider retained) so the same slot
	/// can be reused by a future era. No-op if the pot was never created (e.g.
	/// the era ran in legacy minting mode).
	pub(crate) fn drain(era: EraIndex, kind: RewardKind) {
		let pot_account = T::RewardPots::pot_account(RewardPot::Era(era, kind));

		// Skip if pot was never created (legacy mode doesn't create pots).
		if frame_system::Pallet::<T>::providers(&pot_account) == 0 {
			return;
		}

		let remaining = T::Currency::balance(&pot_account);

		if remaining.is_zero() {
			return;
		}

		match T::Currency::withdraw(
			&pot_account,
			remaining,
			Precision::BestEffort,
			Preservation::Expendable,
			Fortitude::Force,
		) {
			Ok(credit) => {
				T::UnclaimedRewardHandler::on_unbalanced(credit);
				log!(
					debug,
					"Drained {:?} unclaimed rewards from era {:?} {:?} pot",
					remaining,
					era,
					kind
				);
			},
			Err(e) => {
				defensive!("Failed to withdraw unclaimed rewards from era pot");
				log!(
					error,
					"Era {:?} {:?}: unclaimed reward withdrawal failed: {:?}",
					era,
					kind,
					e
				);
			},
		}
