Confirmed: the `DeliveryReceipt.success` field, decoded straight from the on-chain `InboundMessageDispatched(nonce, topic, bool success, reward_address)` Ethereum event, is never consulted by `Pallet::process_delivery_receipt` before paying out the relayer reward. This is a direct structural analog of the reported bug class — an error/status code returned by a lower-level function (here, the Gateway's delivery outcome) is silently dropped by the caller, which proceeds to act on the rest of the payload as if it were the success case.

### Title
`process_delivery_receipt` ignores the `success` flag of `DeliveryReceipt`, rewarding relayers for failed message deliveries - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

### Summary
`DeliveryReceipt` decoded from the Ethereum `InboundMessageDispatched` event carries a `success: bool` field indicating whether the Ethereum-side message execution actually succeeded [1](#0-0) . `Pallet::process_delivery_receipt` verifies the gateway address, looks up the pending order by nonce, and unconditionally pays the relayer reward whenever `order.fee > 0`, without ever reading `receipt.success` [2](#0-1) .

### Finding Description
The extrinsic `submit_delivery_receipt` verifies the Merkle/log proof via `T::Verifier::verify`, decodes the event into a `DeliveryReceipt`, and calls `process_delivery_receipt` [3](#0-2) . Inside `process_delivery_receipt`:

```
ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);
let reward_account = ...;
let nonce = receipt.nonce;
let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;
if order.fee > 0 {
    T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee);
}
<PendingOrders<T>>::remove(nonce);
``` [4](#0-3) 

The `receipt.success` field is read nowhere in this function or in `submit_delivery_receipt`. This mirrors exactly the reported bug class: the "status/error" output (`success`) of an operation (Ethereum-side message dispatch) is available to the caller but is discarded, and the caller proceeds to use the rest of the (from its perspective, "unusable/invalid" in the failure case) receipt data — the nonce and fee — as if delivery had succeeded.

Existing guards do not stop this path:
- `T::Verifier::verify` only proves that the log genuinely came from the gateway contract at that block/receipt-trie position; it says nothing about the semantic `success` flag embedded in the event data. A genuine, honestly-relayed event where the Ethereum-side dispatch reverted (`success = false`) — for example, because the destination contract call failed, ran out of gas, or was blocked — still passes proof verification.
- `InvalidPendingNonce` only checks that an order for that nonce exists; it does not gate on delivery outcome.
- The `success` field is preserved through decoding (`InboundMessageDispatched` ABI event) intact, so it is fully available; it's a business-logic omission, not a decode-loss issue.

### Impact Explanation
Any relayer can submit a delivery receipt for a message whose execution failed on Ethereum (`success = false`) and still collect the full relayer reward tied to that nonce's `PendingOrder.fee`, exactly as if the message had been delivered successfully. Because `PendingOrders` is removed after processing, this also permanently closes out the order, so a legitimate future retry/accounting flow for that nonce cannot re-trigger a correct reward computation tied to actual delivery success. This is a public, underpriced/incorrect settlement of value: it mints unearned relayer rewards from the reward pot and lets an unprivileged actor (any signed account can call `submit_delivery_receipt`) claim payment regardless of message dispatch success, directly violating the "message queues/receipts/payout state must only advance after ... execution ... succeed atomically" invariant.

### Likelihood Explanation
High — no privileged role, governance, or malicious relayer/prover assumption is needed. The event itself is genuine and its proof is honestly generated by the bridge (a failed Ethereum-side execution is a normal, permissionless occurrence, e.g. destination contract reverts or runs out of gas) — the relayer merely submits the true event, and the pallet logic itself fails to check `success` before rewarding. This is a pure runtime logic defect exploitable by any user submitting a legitimate delivery receipt for a message that failed to execute on Ethereum.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success` explicitly: only call `T::RewardPayment::register_reward` when `receipt.success == true`; for `success == false`, still consume/remove the `PendingOrder` (or route to a distinct failure-handling/refund path) but must not credit the relayer reward, and should emit a dedicated `MessageDeliveryFailed`/similar event distinct from `MessageDelivered` so downstream consumers (and other pallets keying off delivery success) are not misled.

### Proof of Concept
1. A message is sent through `do_process_message`, creating a `PendingOrder { nonce, fee > 0, .. }` [5](#0-4) .
2. On Ethereum, the Gateway attempts to dispatch the inbound message but execution fails (e.g., destination call reverts); the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)` per the ABI event definition [6](#0-5) .
3. Any relayer collects the log + inclusion proof and calls `submit_delivery_receipt(origin, event)` [7](#0-6) .
4. `T::Verifier::verify` succeeds (the log is genuine and included), `DeliveryReceipt::try_from` decodes `success = false` correctly, but `process_delivery_receipt` still executes `T::RewardPayment::register_reward(&reward_account, ..., order.fee)` because it never inspects `receipt.success`, and emits `MessageDelivered` [8](#0-7) .
5. The relayer is rewarded for a message that never actually completed successfully on Ethereum, and the existing integration test suite only exercises the `success: true` path, confirming the `false` branch is untested/unguarded [9](#0-8) .

```rust
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
