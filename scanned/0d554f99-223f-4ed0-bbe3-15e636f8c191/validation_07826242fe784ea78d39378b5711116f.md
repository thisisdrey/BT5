### Title
Unbounded `message.assets` array in Snowbridge V2 inbound converter permanently locks bridged Ethereum funds - (File: `bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs`)

### Summary
`MessageToXcm::prepare`/`convert` iterate over the attacker-controlled `message.assets: Vec<EthereumAsset>` with no upper bound, appending one `AssetTransfer`/XCM asset entry per element into the outgoing XCM instructions sent to Asset Hub. There is no size cap analogous to `pallet-xcm`'s `MAX_ASSETS_FOR_TRANSFER` check enforced on this path, so a message originated on Ethereum can carry an arbitrarily large asset list, producing an oversized/overweight XCM that Asset Hub cannot execute or that XCMP cannot deliver — while the funds are already irreversibly locked in the Ethereum Gateway contract.

### Finding Description
The inbound V2 pipeline decodes an Ethereum log into a `Message` with an unbounded `assets: Vec<EthereumAsset>` field: [1](#0-0) 

That field is decoded straight from the Solidity ABI-encoded event log without any length check: [2](#0-1) 

`MessageToXcm::prepare` then loops over `&message.assets` unbounded, pushing one `AssetTransfer::ReserveDeposit`/`ReserveWithdraw` entry per array element: [3](#0-2) 

`convert` then folds all of these into a single `ReserveAssetDeposited`/`WithdrawAsset` XCM instruction whose asset vector length is exactly `message.assets.len()`, with no cap: [4](#0-3) 

Compare this with `pallet-xcm`'s own equivalent extrinsics, which explicitly enforce `MAX_ASSETS_FOR_TRANSFER` (currently `2`) before building any multi-asset XCM: [5](#0-4) [6](#0-5) 

No equivalent guard exists anywhere in the Snowbridge V2 inbound path (`converter.rs`, `message.rs`, or `pallet::process_message`); a `grep` for `MAX_ASSETS`/`MaxAssets`/an assets-length `ensure!` across `bridges/snowbridge/**` returns no results.

In `process_message`, the nonce is marked as delivered and the relayer is paid *only if* `T::MessageProcessor::process_message` succeeds — a normal dispatch failure rolls back all storage writes, so an oversized message that fails to be converted/sent simply reverts: [7](#0-6) 

This is the exact bug class from the report: an unbounded loop over a user-controlled asset array with no upper bound, driven purely by data the (unprivileged) Ethereum-side caller controls, with no local guard capping the loop size before it becomes gas/weight-critical.

### Impact Explanation
Because the assets and their intended value are locked into the Ethereum Gateway contract the moment the user initiates the transfer (off-chain, unconditionally, before the relayer ever calls `submit`), and because `submit`/`process_message` on the Substrate side will permanently fail to convert/dispatch a message whose `assets` list is large enough to produce an XCM that:
- exceeds the max XCMP/DMP message size, or
- exceeds the weight/gas the destination can execute (Asset Hub `MessageQueue`/XCMP weight limits),

then every relayer submission for that specific Ethereum nonce will keep failing identically (the payload is fixed by the immutable Ethereum log), and the nonce can never be marked delivered. The user's assets, already irrevocably debited/locked on the Ethereum side, become permanently unrecoverable on the Polkadot side — a permanent fund lock matching the medium-severity "unexercisable/unwithdrawable" impact in the source report, except here it is a hard bridge-wide invariant break rather than a UI-level mitigation, because there is no local, protocol-level cap on `message.assets.len()`.

### Likelihood Explanation
`submit` is a fully public, permissionless extrinsic (`ensure_signed(origin)?`), and the number of Ethereum assets bundled into a single Gateway send is controlled entirely by whatever contract call the Ethereum-side sender makes — nothing in this repository constrains it. No malicious relayer, validator, governance actor, or leaked key is required: an ordinary Ethereum user (or an application built on top of the Gateway) can trigger this simply by including "too many" distinct ERC-20 assets in one bridge send, something that is easy to do accidentally as usage/asset variety grows and gas/weight limits change over time — exactly the scenario called out in the original report ("gas requirements can change... orders filled at T1 may not be exercisable at T2").

### Recommendation
Enforce an explicit, protocol-level maximum on `message.assets.len()` (and on the derived XCM asset vector) before or during `MessageToXcm::prepare`/`convert`, mirroring `pallet-xcm`'s `MAX_ASSETS_FOR_TRANSFER` guard, and return a well-defined `ConvertMessageError`/`Error<T>::TooManyAssets` early rather than allowing the loop to build an unbounded XCM. This bound should be chosen conservatively relative to the destination chain's XCM execution weight and the transport's max message size, and should be enforced consistently regardless of what the Ethereum-side Gateway contract itself permits.

### Proof of Concept
1. On Ethereum, call the Gateway's send function with a `Payload.assets` array containing `N` distinct `NativeTokenERC20`/`ForeignTokenERC20` entries, where `N` is large enough that the resulting XCM (one `ReserveAssetDeposited`/`WithdrawAsset` entry per asset, plus the remote XCM appended) exceeds Asset Hub's per-message execution weight or the XCMP/DMP max message size.
2. A relayer observes the `OutboundMessageAccepted` event and submits it via `EthereumInboundQueueV2::submit` with a valid Merkle/verifier proof.
3. `Message::try_from(&log)` decodes all `N` assets with no length check (`bridges/snowbridge/primitives/inbound-queue/src/v2/message.rs:182-192`).
4. `MessageToXcm::prepare`/`convert` build an XCM whose `ReserveAssetDeposited`/`WithdrawAsset` asset vector has length `N` (`converter.rs:159-200`, `396-411`).
5. `T::MessageProcessor::process_message` fails to route/execute this oversized XCM (`SendError::TooBig`/weight overshoot), causing `process_message` in `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs:215-245` to return an `Err`, rolling back the nonce update.
6. Every subsequent relayer submission of the same immutable Ethereum log fails identically, because `N` and the asset list are fixed by the already-emitted event — the user's funds, already locked on Ethereum, can never be settled on the Polkadot side.

	impl<T: Config> Pallet<T> {
		pub fn process_message(relayer: T::AccountId, message: Message) -> DispatchResult {
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == message.gateway, Error::<T>::InvalidGateway);

			let (nonce, relayer_fee) = (message.nonce, message.relayer_fee);

			// Verify the message has not been processed
			ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);

			// Mark message as received
			Nonce::<T>::set(nonce);

			let message_id = T::MessageProcessor::process_message(relayer.clone(), message)
				.map_err(|e| match e {
					MessageProcessorError::ProcessMessage(e) => e,
					MessageProcessorError::ConvertMessage(e) => Error::<T>::from(e).into(),
					MessageProcessorError::SendMessage(e) => Error::<T>::from(e).into(),
				})?;

			// Pay relayer reward
			let tip = Tips::<T>::take(nonce).unwrap_or_default();
			let total_tip = relayer_fee.saturating_add(tip);
			if total_tip > 0 {
				T::RewardPayment::register_reward(&relayer, T::DefaultRewardKind::get(), total_tip);
			}

			// Emit event with the message_id
			Self::deposit_event(Event::MessageReceived { nonce, message_id });

			Ok(())
		}
