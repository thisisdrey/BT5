Can an unprivileged attacker deploy a malicious NEP-171 `token` contract such that `nft_transfer_call`'s callback JSON deserializes as `Ok(Err(_deserialization_err)) => false` in `nft_resolve_withdraw` (contracts/defuse/src/contract/tokens/nep171/withdraw.rs), triggering `self.deposit(sender_id, [(Nep171TokenId::new(token, token_id).into(), 1)], ...)` even though the malicious contract kept the NFT and never returned it? Preconditions: attacker owns `token` and `token_id`; attacker's Verifier account previously deposited/owns this Nep171TokenId balance of 1, debited by `Contract::withdraw`. Call sequence: `nft_withdraw` -> `internal_nft_withdraw` -> `Contract::withdraw` debit of 1 -> `do_nft_withdraw` -> `nft_transfer_call` -> malformed callback -> `nft_resolve_withdraw` re-mints the NFT unit balance. Binding: (units debited == 1) == (NFT actually returned to Verifier custody) + (units re-credited); a re-credit when the NFT was truly transferred out breaks it, letting the attacker claim the intents-side unit again while the real NFT sits with the malicious receiver. Impact: Critical, TokenId double-credit for a unique NFT unit that can now be re-withdrawn or traded again. Proof idea: sandbox test with a receiver returning garbage JSON, assert `total_supplies` for the `Nep171TokenId` becomes 1 again despite the physical NFT having left custody.
