Target: `Nonces::commit` created_at/timeout bound (contracts/wallet/src/nonces.rs:120-133). Attacker action: relayer or attacker submits a signed `RequestMessage{nonce: N, created_at: <timestamp 2*wallet.timeout in the future>, timeout: <attacker-chosen huge value>, ...}` signed genuinely by the owner (owner might have been tricked into signing with a manipulated clock, or attacker replays an old signed message whose `created_at` the attacker cannot change since it's inside the signed hash — so this specifically targets whether `msg.timeout` chosen by signer, uncontrolled by contract's `wallet.timeout`, can extend validity window arbitrarily beyond `wallet.timeout`). Preconditions: signer sets `msg.timeout` very large in a legitimately signed message. Call sequence: `commit(nonce, created_at, timeout)` computes bound using `self.timeout.min(timeout)` (contract's own timeout caps it) - verify this MIN is actually applied and not `timeout` alone, i.e. `now - self.timeout.min(msg.timeout) <= created_at <= now`. Binding: effective validity window == `min(wallet.timeout, msg.timeout)`, never solely `msg.timeout`, so attacker-signer cannot use an oversized `msg.timeout` to make a stale signed request valid far longer than the contract's own timeout policy, extending the replay-relevant window unexpectedly. Scoped impact: High - an overlong window increases the chance a relayed request executes far later than intended context, potentially against stale account state (e.g. after extensions/signature mode changed), executing balance-moving `Request` when circumstances changed. Proof idea: cargo test setting `wallet.timeout` small (e.g. 60s) and `msg.timeout` huge (e.g. 1 year), created_at 6 months ago, asserting `commit` returns `Err(NonceError::ExpiredOrFuture)` because bound uses the wallet's `self.timeout`, not `msg.timeout`.
