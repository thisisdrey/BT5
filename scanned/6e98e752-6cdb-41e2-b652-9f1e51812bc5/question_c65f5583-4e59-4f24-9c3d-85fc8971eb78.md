Target: `AttachmentsBatch::track_attachment` (atlas/download.rs) guarding against mixing instances from different blocks. Attacker action: attacker cannot forge on-chain `AttachmentInstance` data directly (that requires consensus), but can influence which peer serves attachments for a batch by advertising a malicious inventory bitfield via `GetAttachmentsInvResponse` (`AttachmentPage.inventory`) claiming certain `attachment_index` slots are present (bit=1) when the underlying `content_hash` bytes it will later serve for those indices do not match the committed `AttachmentInstance.content_hash`. Preconditions: victim uses inventory bits only as a hint for which peer to query, then still fetches by content_hash from `getattachment.rs`. Call sequence: victim's downloader consults `AttachmentsInventoryRequest`/`GetAttachmentsInvResponse` to prioritize peers -> issues `GET /v2/attachments/<H>` -> attacker serves mismatched content per finding #1. Equality/fault: the inventory bit claiming availability must correlate with the peer's ability to serve bytes whose `Attachment::hash()` equals H; a false-positive bit that always resolves to a hash mismatch effectively poisons peer selection, wasting retry budget (`AttachmentsBatch::bump_retry_count`, `MAX_RETRY_DELAY`) for a real committed attachment. Impact (High): valid attachment for H is treated as unreachable/exhausted retries because every peer claiming to have it fails the hash check, i.e., BNS resolution serving no data (denial) for a name that has valid committed content elsewhere. Proof idea: net test simulating multiple peers where one advertises inventory bit=1 for an index but always returns hash-mismatched content, asserting the batch's `has_fully_succeed()` never becomes true despite a different honest peer's data being available and unretried within a bounded time window.
