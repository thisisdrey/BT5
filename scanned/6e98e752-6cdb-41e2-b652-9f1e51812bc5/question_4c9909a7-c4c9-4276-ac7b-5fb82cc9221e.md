Target: `AtlasDB::insert_instantiated_attachment` (atlas/db.rs) invoked from the downloader once an HTTP `GetAttachmentResponse` is received. Attacker action: send content C1 in response to a request for content_hash H, where `Hash160::from_data(C1) = H2 != H`. Preconditions: victim node has an outstanding `AttachmentRequest{content_hash:H}` (download.rs) it is trying to resolve for a real, committed BNS attachment instance. Call sequence: response bytes flow through `StacksHttpResponse::decode_atlas_get_attachment` -> `Attachment::new(bytes)` -> `insert_instantiated_attachment` runs `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (attachment.hash(), content, 1, now)`, using the *computed* hash H2, not the requested H. Equality: the row's `hash` column must equal the `content_hash` field of the specific `AttachmentInstance` the request was servicing (H), not merely equal `Attachment::hash()` of whatever bytes arrived. Impact (High): attacker fills the `attachments` table with `was_instantiated=1` rows keyed to H2 that no `AttachmentInstance.content_hash` in `attachment_instances` will ever reference (since real commitments specify H, not H2), i.e., storage consumption tied to no consensus commitment. Proof idea: net test asserting `AtlasDB::find_attachment(&H2)` becomes populated by unrelated attacker content while no `attachment_instances` row has `content_hash = H2`.
