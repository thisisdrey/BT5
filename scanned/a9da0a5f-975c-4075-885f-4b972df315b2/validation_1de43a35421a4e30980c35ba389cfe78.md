### Title
Silent loss of non-first fungible assets in `ERC20Transactor::deposit_asset_with_surplus` when a holding contains multiple ERC20 assets - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
The Tokemak bug root cause is a mismatch between what the contract *accounts for* (the amount wrapped/credited) and what it *actually settles* (the amount transferred), letting the untracked remainder be silently lost/stolen. `ERC20Transactor::deposit_asset_with_surplus` has the same class of flaw: it receives a full `AssetsInHolding` (which may legitimately contain several distinct fungible assets matched by the same generic ERC20 matcher), but only extracts and settles the **first** fungible asset via a real ERC20 `transfer` call, then reports the whole operation as `Ok`, causing the XCM executor to treat the entire holding as successfully deposited while any additional assets are silently dropped and permanently destroyed.

### Finding Description
`TransactAsset::deposit_asset`/`deposit_asset_with_surplus` receive the **entire** `AssetsInHolding` to be deposited for a `DepositAsset` XCM instruction (this can be built from `Wild(All)`, `AllCounted(n)`, or a `Definite` multi-asset set), and the tuple-of-transactors default implementation [1](#0-0)  stops iterating and treats the full `what` as consumed the moment one transactor in the tuple returns `Ok`.

`ERC20Transactor::deposit_asset_with_surplus` however only inspects the first fungible asset of that holding: [2](#0-1) 

It performs a single ERC20 `transfer` call for that one `(asset_contract_id, amount)` pair, and on success returns `Ok(surplus)` — the function signature discards `what` entirely on the success path: [3](#0-2) 

The doc comment on the function explicitly acknowledges the flaw but only relies on a `defensive_assert!`, which is a no-op in production/release builds: [4](#0-3) 

Because `Matcher: MatchesFungibles<H160, u160>` is generic over ERC20 contract addresses (it is meant to match *any* ERC20 token routed through this transactor, as used on Asset Hub Westend), any XCM program that deposits more than one ERC20-backed asset to the same beneficiary in a single `DepositAsset` instruction (e.g. `Wild(All)`/`AllCounted(2)` selecting two different ERC20 tokens both handled by this same matcher) will have all of them placed into a single `AssetsInHolding` passed to `deposit_asset_with_surplus`. Only the first is actually transferred on-chain; the remaining assets are never transferred, never returned as `unspent` (unlike the error branches which do return `(what, XcmError)`), and are simply dropped when the function returns `Ok`, permanently destroying them with no beneficiary credit and no asset-trap recovery path (trapping only occurs on the `Err` branches upstream).

This precisely mirrors the external bug's broken invariant: the accounted/settled amount (the single first-asset ERC20 transfer) diverges from the amount the protocol believes was settled (the full holding, silently accepted as `Ok`), and the delta is unrecoverably lost rather than being credited to anyone or refunded/trapped.

### Impact Explanation
This is a public, unprivileged-reachable fund-loss bug: any account able to construct or trigger an XCM `DepositAsset` (via `pallet_xcm::execute`, a cross-chain transfer landing on the parachain that uses `ERC20Transactor`, or a batched deposit instruction) holding two or more ERC20-backed assets in the same instruction will have all but the first asset permanently destroyed instead of delivered to the beneficiary. This falls under "theft or unbacked mint or unlock" / "permanent user-fund … lock" in the accepted impact categories, since value is not conserved and does not settle exactly once to the rightful beneficiary.

### Likelihood Explanation
`ERC20Transactor` is wired into Asset Hub Westend's XCM configuration to support ERC20 tokens deployed via `pallet-revive` (per PRDoc `pr_7762`), and the matcher is intentionally generic to any ERC20 contract address, so multiple distinct ERC20 assets can legitimately land in the same `AssetsInHolding` for a single `DepositAsset` instruction (e.g. teleport/reserve-transfer messages carrying two tokens to the same beneficiary, or `Wild(All)`-based deposits). No malicious relayer, validator, or governance action is required — a normal user or contract constructing a multi-asset XCM message triggers the loss path. The safety net (`defensive_assert!`) is inert in production.

### Recommendation
- Change `deposit_asset_with_surplus` (and the analogous `withdraw_asset_with_surplus`) to reject holdings containing more than one fungible asset with a hard `Err((what, XcmError::…))` returning the untouched `what`, instead of a `defensive_assert!` that compiles out in production.
- Alternatively, iterate over all fungible assets in `what`, execute an ERC20 transfer per asset, and only return `Ok` once every asset in the holding has been successfully settled; on partial failure, return the unsettled remainder as `unspent` so the XCM executor can trap/refund it rather than dropping it.

### Proof of Concept
1. Deploy two ERC20 contracts `A` and `B` on the pallet-revive side, both matched by `ERC20Transactor`'s `Matcher` (any `AccountKey20`-addressed ERC20 contract qualifies, per its generic design).
2. Fund a location `L` with balances of both `A` and `B` inside the XCM holding register (e.g. via `ReserveAssetDeposited`/`WithdrawAsset` for both assets in one XCM program).
3. Execute an XCM program ending in `DepositAsset { assets: Wild(AllCounted(2)), beneficiary: Bob }` (or an explicit `Definite` set containing both `A` and `B`), targeting `Bob`.
4. The XCM executor calls `ERC20Transactor::deposit_asset_with_surplus(what, Bob, ctx)` with `what` containing both `A` and `B`.
5. Only `A` (the first fungible asset returned by `what.fungible_assets_iter().next()`) is transferred to `Bob` via the ERC20 `transfer` call; the function returns `Ok(surplus)`.
6. `Bob`'s ERC20 balance of `B` is never credited, `L`'s claim on `B` is not preserved, and no trap event captures it — `B`'s tokens are permanently unaccounted for while the XCM program reports success for the whole `DepositAsset` instruction.

	///
	/// Note: This implementation only handles a single fungible asset at a time. The
	/// `AssetsInHolding` parameter is required by the `TransactAsset` trait, but callers
	/// should ensure only one asset is passed. If multiple assets are present, only the
	/// first fungible asset will be deposited and the rest will be silently ignored.
	/// The `defensive_assert!` helps catch misuse during development.
	fn deposit_asset_with_surplus(
		what: AssetsInHolding,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<Weight, (AssetsInHolding, XcmError)> {
		tracing::trace!(
			target: "xcm::transactor::erc20::deposit",
			?what, ?who,
		);
		defensive_assert!(what.len() == 1, "Trying to deposit more than one asset!");
		// Check we handle this asset.
		let maybe = what
			.fungible_assets_iter()
			.next()
			.and_then(|asset| Matcher::matches_fungibles(&asset).ok());
		let (asset_contract_id, amount) = match maybe {
			Some(inner) => inner,
			None => return Err((what, MatchError::AssetNotHandled.into())),
		};
		let who = match AccountIdConverter::convert_location(who) {
			Some(inner) => inner,
			None => return Err((what, MatchError::AccountIdConversionFailed.into())),
		};
