### Title
`submit_delivery_receipt` pays relayer reward and settles the order even when the Ethereum delivery event reports failure - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
`Pallet::process_delivery_receipt` in the Snowbridge outbound-queue-v2 pallet decodes a `DeliveryReceipt` that carries a `success: bool` field taken directly from the `InboundMessageDispatched` Ethereum event, but this field is never read or checked anywhere in the pallet before the relayer reward is registered and the `PendingOrders` entry is removed.

### Finding Description
`DeliveryReceipt` is decoded from the Ethereum event log and explicitly carries the on-chain execution outcome: [1](#0-0) 

`submit_delivery_receipt` is a permissionless, signed extrinsic — any account can call it as long as it supplies a valid Merkle/light-client proof for a genuine `InboundMessageDispatched` log: [2](#0-1) 

It forwards straight into `process_delivery_receipt`, which only validates the gateway address and the existence of a `PendingOrder` for the nonce. It never inspects `receipt.success` before paying the reward and clearing the order: [3](#0-2) 

A grep across the whole pallet confirms `success` is decoded but nowhere consumed in `outbound-queue-v2` — the only occurrence of the field in the crate tree is its declaration in `delivery_receipt.rs`. This means a message whose Ethereum-side dispatch actually **failed** (`success: false`, e.g. reverted inbound handler on Ethereum) is treated exactly the same as a successfully delivered message: the relayer still collects `order.fee` via `T::RewardPayment::register_reward`, and the `PendingOrders` entry for that nonce is deleted, permanently closing out the settlement record for that message.

### Impact Explanation
This breaks the intended queue/payout invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." Here settlement (fee payout + order removal) advances purely on proof-of-inclusion of the event log, independent of the `success` outcome encoded in that very same log. Consequences:
- Underpriced/incorrect work is rewarded: relayers are paid for messages whose payload execution failed on Ethereum, i.e., "public underpriced work" that misallocates bridge reward funds.
- The `PendingOrders` record is removed regardless of outcome, so there is no way to re-open, retry-track, or refund/re-settle a failed delivery through this pallet's state — a form of permanent bridge-state finalization on a false success signal.
- No malicious relayer, validator, or governance actor is required — this is triggerable by any account that legitimately relays real (but failed) Ethereum events, i.e., unprivileged and using genuine proofs.

### Likelihood Explanation
High. This does not require a malicious prover, forged proof, or governance abuse — it is triggered by the ordinary/expected relaying flow whenever an inbound message dispatch on Ethereum fails for any reason (e.g., insufficient gas at execution, reverted command, downstream contract failure) yet still emits the `InboundMessageDispatched(success=false)` event, which is a normal, foreseeable occurrence in bridge operation, not an edge case requiring adversarial capability.

### Recommendation
Check `receipt.success` in `process_delivery_receipt` before rewarding the relayer, e.g.:
```rust
if receipt.success {
    if order.fee > 0 {
        T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee);
    }
}
```
and decide explicitly what should happen to `PendingOrders` on failure (e.g., retain/mark for retry, or emit a distinct `MessageDeliveryFailed` event) rather than unconditionally removing the order and unconditionally paying the fee.

### Proof of Concept
1. A message is enqueued via `do_process_message`, creating `PendingOrders[nonce] = { nonce, fee > 0, block_number }`. [4](#0-3) 
2. On Ethereum, the Gateway contract processes the message but the inbound command execution fails, so the emitted `InboundMessageDispatched` event has `success = false` (this is a legitimate, correctly-formed event — no forgery needed). [5](#0-4) 
3. Any relayer submits this genuine event with a valid proof via `submit_delivery_receipt`. `T::Verifier::verify` succeeds (the event is real), `DeliveryReceipt::try_from` succeeds, and `process_delivery_receipt` runs: [6](#0-5) 
4. Because `receipt.success` is never checked, `order.fee > 0` still triggers `T::RewardPayment::register_reward`, and `PendingOrders::remove(nonce)` deletes the order — the relayer is paid and the record is finalized despite the failed on-chain execution.

Note: I could not find any downstream consumer (runtime, off-chain worker, or another pallet) that separately re-checks `success` before or after this call within the indexed portion of the codebase; if such a check exists elsewhere and is not indexed, a full-codebase review via a Devin session is recommended to confirm no compensating control exists.

```rust
		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
