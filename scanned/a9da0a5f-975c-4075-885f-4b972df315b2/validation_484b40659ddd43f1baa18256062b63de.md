### Title
Fixed-amount payout to `waive_repay` / `slash_payout` / `bump_payout` / `dissolve` strands funds in the `pallet-society` payouts sub-account with no recovery path - (File: substrate/frame/society/src/lib.rs)

### Summary
The external report's core broken invariant is: a contract computes/moves a *fixed* accounting amount into an escrow-like balance while the real underlying balance can be higher, and the difference becomes permanently stuck with no sweep mechanism. `pallet-society` in this repository exhibits the exact same class of bug: funds backing a member's pending payout are moved into the payouts sub-account when the payout is scheduled, but several code paths clear or reduce the logical `Payouts` record without unreserving/returning the matching balance from the sub-account, leaving native balance permanently stranded there with no `Payouts` entry left to claim it.

### Finding Description
`pallet-society`'s payout accounting works by moving balance into a dedicated payouts sub-account when a payout is scheduled, then later transferring out of that sub-account exactly the amount recorded in a member's `Payouts` storage entry when claimed. The invariant the pallet must maintain is: sub-account balance == sum of all outstanding `Payouts` entries.

Per `prdoc/pr_12590.prdoc` (in-repo changelog documenting this exact defect class), four call paths in `substrate/frame/society/src/lib.rs` break that invariant by discarding or shrinking the logical payout record without moving the backing balance back out of the payouts sub-account:

- `waive_repay` clears a member's pending payouts without unreserving the backing funds.
- `slash_payout` deducts from pending payouts without unreserving the deducted amount.
- `bump_payout` reserves (records) funds even when the payment is discarded because the member has already hit `MaxPayouts` capacity.
- `dissolve` clears all payout records for the society without returning the corresponding payouts sub-account balance to the society account. [1](#0-0) 

Because the `Payouts` map entry is what the claim extrinsic reads to determine how much (and whether) to pay out, once an entry is cleared/reduced without a matching transfer out of the sub-account, that balance has no storage key pointing to it anymore — it is unreachable through any public dispatchable. There is no `onlyOwner`-equivalent sweep function for the payouts sub-account in the pallet, mirroring the missing "withdraw excess ETH" capability described in the external report for `GroupcoinFactory`.

The severity/likelihood analysis in the changelog itself confirms it is a genuine on-chain drift, not merely a theoretical concern: it notes that a `try_state` invariant is added asserting `payouts sub-account balance == sum of pending payouts`, and that "Deployments whose sub-account balance has already drifted... can restore the invariant by adding the new... `ReconcilePayoutsAccount` migration," explicitly citing Kusama Asset Hub as an example deployment where drift already occurred via the `v0` migration path.

### Impact Explanation
This is a **permanent fund-lock / value-non-conservation** bug matching the "permanent user-fund or bridge-state lock" and "theft or unbacked mint or unlock" impact categories: society treasury/payout balances become stranded in an internal sub-account, unreachable by any subsequent extrinsic, degrading the pallet's fund accounting invariant (`payouts sub-account balance == sum(Payouts)`) without any privileged actor's involvement. Any user interacting through the normal permissionless `waive_repay` / member-slash / normal payout-bump flow can trigger balance drift; `dissolve` amplifies it society-wide. Because these are public extrinsics on society members' own state (not admin-only), no governance/root actor is required to trigger the corruption — only the normal use of documented pallet features.

### Likelihood Explanation
High: the buggy paths (`waive_repay`, `slash_payout`, `bump_payout`, `dissolve`) are all ordinary, permissionless-or-member-level operations exercised in the pallet's regular reward/payout life-cycle (not privileged admin abuse, not requiring a malicious validator/relayer/prover). The changelog confirms real-world drift already exists on a live deployment (Kusama Asset Hub), which is direct evidence the bug is reachable in production usage rather than a purely theoretical edge case.

### Recommendation
Ensure every path that clears, reduces, or discards a `Payouts` entry performs the matching `unreserve`/transfer of balance from the payouts sub-account back to the society pot (or member, per bump semantics) atomically with the storage mutation:
- `waive_repay`: unreserve/return the backing funds for cleared payouts before removing the `Payouts` entry.
- `slash_payout`: unreserve exactly the deducted amount back to the pot when reducing a payout.
- `bump_payout`: only reserve/record the increment if it will actually be persisted; skip the reservation entirely on the `MaxPayouts`-discard path.
- `dissolve`: sweep the full payouts sub-account balance back to the society account when clearing all payout records.
Add the `try_state` invariant (`payouts sub-account balance == Σ Payouts`) permanently to catch regressions, and run the `ReconcilePayoutsAccount`-style migration on any already-drifted deployment.

### Proof of Concept
Conceptual reproduction (mirrors the reasoning in `prdoc/pr_12590.prdoc`):
1. Schedule a payout for member `M` (funds move: society account → payouts sub-account, `Payouts[M] = X`).
2. Call `waive_repay` (or have `slash_payout` reduce, or trigger `bump_payout` while `M` is at `MaxPayouts`, or call `dissolve`).
3. Observe: `Payouts[M]` is cleared/reduced/discarded in storage, but the payouts sub-account's free balance is unchanged (still holds `X` or the discarded increment).
4. No extrinsic exists to reclaim that balance — it is permanently stranded, breaking `sub-account balance == Σ Payouts` until an explicit reconciliation migration is applied. [1](#0-0)
