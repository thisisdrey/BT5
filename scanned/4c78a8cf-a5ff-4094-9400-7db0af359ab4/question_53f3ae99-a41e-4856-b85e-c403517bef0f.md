Target: `TokenDiff::supply_delta`/`closure_delta` (contracts/defuse/core/src/intents/token_diff.rs) keyed by `TokenId`, invoked from state managed via `engine/state/mod.rs::internal_apply_deltas`. Attacker submits a `MultiPayload` batch with two `TokenDiff` intents from two different signers referencing what they intend to be the *same* token but constructed via different `TokenId` variants that happen to `to_string()` identically (e.g. one via `TokenId::Nep141(Nep141TokenId::new('ft.near'))` and a hypothetical colliding `TokenId::Imt(...)` string). Precondition: both signers have registered balances; the intents net to zero under each signer's own believed `TokenId` but not under the engine's actual `TokenId` equality (`derive(PartialEq, Eq, Hash)` on struct fields, not on `to_string()`). Call sequence: `execute_intents` -> `TokenDiff::closure_deltas` sums `TokenDeltas` per exact `TokenId` key -> `internal_apply_deltas` calls `internal_add_balance`/`internal_sub_balance` per exact key. Binding: sum of all `token_balances` deltas for the *string-identical* asset across the batch == 0 (CONSERVATION), which requires that no two distinct `TokenId` values sharing a `to_string()` are treated by the engine as different keys while downstream consumers (fee collector accounting, event logs) treat them as the same asset. Scoped impact: Critical - a colliding pair lets one signer's debit not be matched by the intended credit, leaving the Verifier owing more than it custodies for that asset. Proof idea: `cargo test` constructing two distinct `TokenId` structs with identical `to_string()` (if constructible) and asserting `TokenDeltas::default().with_apply_deltas([(a, 100), (b, -100)])` where `a != b` panics or errors rather than silently netting via string identity, and that `HashMap<TokenId,_>` never merges `a` and `b`.
