Target: `ft_on_transfer` (contracts/defuse/src/contract/tokens/nep141/deposit.rs) building `TokenId::Nep141(Nep141TokenId::new(env::predecessor_account_id()))`. Attacker registers a NEAR account literally named the same as `TokenIdType::Nep171` string tag concatenated with a real NFT contract id is impossible since `env::predecessor_account_id()` is validated by NEAR runtime as an `AccountId` and cannot itself contain ':'. Attacker instead creates account `wrap.near.evil` (a subaccount) and calls `ft_on_transfer` as `wrap.near.evil`, producing `TokenId::Nep141(Nep141TokenId{contract_id:'wrap.near.evil'})` -> `nep141:wrap.near.evil`. Precondition: real wNEAR is `wrap.near`; attacker owns `wrap.near.evil`. Call sequence: `ft_on_transfer` -> `Contract::deposit([(token_id, amount)])` -> credited under `nep141:wrap.near.evil`. Binding: the `(contract, token)` this `TokenId` names (`wrap.near.evil`) must equal the asset actually moved (FT from `wrap.near.evil`), and must not equal `StateView::wnear_token_id()` = `Nep141TokenId::new(self.wnear_id())` = `nep141:wrap.near`. Scoped impact: Critical if these two ever `to_string()`-collide (they should not, since AccountId equality is exact), meaning a worthless `wrap.near.evil` FT could satisfy a `storage_deposit`/wNEAR check gated on `wnear_token_id()`. Proof idea: `cargo test` calling `ft_on_transfer` from `wrap.near.evil`, then attempting `storage_deposit` (which withdraws from the exact `wnear_token_id()` key), asserting it fails with `BalanceOverflow`/insufficient balance rather than succeeding off the attacker's deposit.
