Can the attacker abuse AuthCall::state_init (NEP-616) to deploy a contract at a derived AccountId that collides with an account already holding a defuse balance or public key, so that Contract::do_auth_call's Promise::new(auth_call.contract_id).state_init(state_init, NearToken::ZERO) overwrites/initializes code at that address, and the subsequent on_auth() call executes attacker logic under an identity the signer did not intend to authorise a call to? Preconditions: signer submits AuthCall{contract_id: derived_account, state_init: Some(state_init), msg, attached_deposit: NearToken::ZERO, min_gas: None} where derived_account happens to equal an account with existing state (e.g. another user's implicit account or a previously-created defuse sub-account). Call sequence: AuthCall::execute_intent -> engine.state.auth_call -> Contract::do_auth_call -> Promise::new(contract_id).state_init(...) -> on_auth. Binding: the (contract, code) pair the signer's AuthCall names via contract_id/state_init == the (contract, code) pair actually executed after state_init runs. Scoped impact: High, wallet-like account executing logic its owner did not authorise for this call. Proof idea: sandbox test constructing a StateInit whose derive_account_id() matches a pre-existing account with a different global contract, and asserting the NEAR runtime's state_init verification (from near/nearcore verifier.rs) rejects the mismatch rather than silently deploying, per the code comment in notify_on_transfer.
