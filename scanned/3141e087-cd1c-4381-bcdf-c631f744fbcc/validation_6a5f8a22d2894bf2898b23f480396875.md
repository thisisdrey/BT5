### Title
`claim_commission` in `pallet-nomination-pools` permanently reverts (locking pool commission) when the configured commission payee account has been reaped or never funded to the Existential Deposit - (File: `substrate/frame/nomination-pools/src/lib.rs`)

### Summary
The Aave Lens bug is a case where a required sub-payment (the referral fee, sent via an unconditional `ownerOf()`/`transferFrom()` call) reverts the entire otherwise-valid user operation because the recipient account no longer exists. The same fragile pattern exists in `pallet-nomination-pools`'s commission claim flow: `do_claim_commission` performs an unconditional `T::Currency::transfer` to the pool's configured `payee` account with `Preservation::Preserve`, and propagates any error with `?`. If the `payee` account does not exist and the accrued commission is below the chain's Existential Deposit, the transfer — and therefore the whole extrinsic, including the prior `reward_pool.update_records()` state advance — fails and rolls back every time it is called, permanently locking the commission inside the reward pool.

### Finding Description
`do_claim_commission` reads the pool's configured commission payee and unconditionally transfers the pending commission to it: [1](#0-0) 

The critical lines are:
```rust
let payee = bonded_pool.commission.current.as_ref().map(|(_, p)| p.clone())
    .ok_or(Error::<T>::NoCommissionCurrentSet)?;

// Payout claimed commission.
T::Currency::transfer(
    &bonded_pool.reward_account(),
    &payee,
    commission,
    Preservation::Preserve,
)?;
```
There is no fallback, no `try`/catch-and-log path, and no way to route the commission elsewhere if `payee` cannot receive funds. Just as `IERC721(HUB).ownerOf(referrerProfileId)` reverts once the referring profile's NFT is burned, `T::Currency::transfer(..)` reverts once the `payee` account is dead (never created, or reaped after falling below ED by unrelated activity) and the pending `commission` amount is smaller than the Existential Deposit needed to (re)create it. Because Substrate dispatchables execute inside an implicit storage transaction, the failure also rolls back `reward_pool.update_records(...)`, so the pending commission is neither paid out nor written off — it is stuck.

This exactly mirrors the pivot: *"treasury spends...and contract-held value must conserve value and settle exactly once to the rightful beneficiary."* Here settlement can never occur at all if the beneficiary account state is not what the code implicitly assumes (funded/existing), and there is no fallback behavior (unlike, e.g., `slash_and_deregister` in `bridges/modules/relayers/src/lib.rs:331-397`, which explicitly tolerates and logs a failed `repatriate_reserved` instead of failing the whole call).

The existing regression tests implicitly acknowledge this fragility by always pre-funding the payee to the ED before calling `claim_commission`: [2](#0-1) 
No test exercises the case where the payee is unfunded/dead, which is exactly the scenario that reproduces the bug.

### Impact Explanation
This falls under the "permanent user-fund or bridge-state lock" impact category. Once a pool's commission payee account is destroyed (or was never funded and stays below ED while accrued commission remains below ED), `claim_commission` becomes permanently uncallable for that pool: every attempt fails and reverts, and the commission balance sitting in the reward account can never be extracted through the intended pathway. This is a real, non-privileged/no-attacker-required failure mode (it can arise from ordinary account lifecycle — e.g., dusting/reaping under `pallet-balances`) that permanently strands legitimate pool funds.

### Likelihood Explanation
This is not a contrived edge case: any `AccountId` configured as `commission.current`'s payee, if it has zero or near-zero balance and no other holds/consumers, can be reaped by the runtime's dust-removal logic. Small or slowly-accruing pools (or freshly-created pools with a payee that has not yet received the initial ED) are directly exposed the very first time `claim_commission` is invoked, requiring no adversarial action.

### Recommendation
Mirror the referral-fee mitigation approach: make the commission payout resilient to a non-existent/dead payee, e.g.:
- Use a transfer variant that tolerates dust/keeps a existing reserve, or explicitly check `System::account_exists(&payee)` / minimum balance before transferring and, if the payee cannot be created, either (a) top up the transfer amount to cover ED from the reward account when funds allow, or (b) emit an event and leave `total_commission_pending` unmodified without failing update_records, allowing commission to accumulate and be retried later without side effects being rolled back unexpectedly, or (c) allow root to redirect payee before retrying, but ensure the extrinsic itself never becomes permanently stuck.
- At minimum, add a defensive fallback path (similar to `slash_and_deregister`'s tolerant handling of `repatriate_reserved` failures) so that a stuck payee cannot indefinitely block commission accounting from ever making progress.

### Proof of Concept
1. Create a nomination pool and set a commission payee `P` to a fresh `AccountId` with zero balance via `set_commission(pool_id, Some((rate, P)))` — mirrors `Pools::set_commission` in `substrate/frame/nomination-pools/src/lib.rs:2963-2995`.
2. Do not fund `P` (skip the `Currency::set_balance(&P, ED)` step that existing tests perform, e.g. `substrate/frame/nomination-pools/src/tests.rs:7147`).
3. Accrue a small amount of rewards below the chain's Existential Deposit via `deposit_rewards(...)` and a member `claim_payout`, so `reward_pool.total_commission_pending` is nonzero but < ED.
4. Call `Pools::claim_commission(RuntimeOrigin::signed(root), pool_id)` — the `T::Currency::transfer(&reward_account, &P, commission, Preservation::Preserve)` in `do_claim_commission` (`substrate/frame/nomination-pools/src/lib.rs:3735-3740`) fails because `P` cannot be created below ED, causing the whole extrinsic (including `update_records`) to revert.
5. Repeat step 4 indefinitely — the call always fails identically, and the accrued commission can never be extracted through this pathway as long as `P` remains unfunded/dead.

```rust
	fn do_claim_commission(who: T::AccountId, pool_id: PoolId) -> DispatchResult {
		let bonded_pool = BondedPool::<T>::get(pool_id).ok_or(Error::<T>::PoolNotFound)?;
		ensure!(bonded_pool.can_claim_commission(&who), Error::<T>::DoesNotHavePermission);

		let mut reward_pool = RewardPools::<T>::get(pool_id)
			.defensive_ok_or::<Error<T>>(DefensiveError::RewardPoolNotFound.into())?;

		// IMPORTANT: ensure newly pending commission not yet processed is added to
		// `total_commission_pending`.
		reward_pool.update_records(
			pool_id,
			bonded_pool.points,
			bonded_pool.commission.current(),
		)?;

		let commission = reward_pool.total_commission_pending;
		ensure!(!commission.is_zero(), Error::<T>::NoPendingCommission);

		let payee = bonded_pool
			.commission
			.current
			.as_ref()
			.map(|(_, p)| p.clone())
			.ok_or(Error::<T>::NoCommissionCurrentSet)?;

		// Payout claimed commission.
		T::Currency::transfer(
			&bonded_pool.reward_account(),
			&payee,
			commission,
			Preservation::Preserve,
		)?;

		// Add pending commission to total claimed counter.
		reward_pool.total_commission_claimed =
			reward_pool.total_commission_claimed.saturating_add(commission);
		// Reset total pending commission counter to zero.
		reward_pool.total_commission_pending = Zero::zero();
		RewardPools::<T>::insert(pool_id, reward_pool);

		Self::deposit_event(Event::<T>::PoolCommissionClaimed { pool_id, commission });
		Ok(())
	}
```
