### Title
Silent short-refund of `pallet-revive` storage deposits when PGAS/native attribution is desynced permanently strands user funds under hold - (File: `substrate/frame/revive/src/deposit_payment.rs`)

### Summary
The external report's root cause is a missing pre-condition (an `approve()` call) that a downstream pull-transfer (`transferFrom`) silently/loudly depends on, so once the precondition is absent the funds that already moved into the intermediate contract become permanently unrecoverable. The direct local analog is in `pallet-revive`'s PGAS-backed deposit backend (`PGasDeposit`, added by `pr_11847`), where `refund_on_hold` depends on the bookkeeping map `NativeDepositOf` to know how much of a contract's held deposit is native vs. PGAS. When that bookkeeping is out of sync with the actual held funds (e.g. during the multi-block `v4` migration window, or any other path where `charge_and_hold`'s attribution write and the real custody amount diverge), the refund path does not error — it silently truncates the refund and returns `Ok(())`, permanently stranding the shortfall under `HoldReason::StorageDepositReserve` with no future call ever revisiting it.

### Finding Description
`PGasDeposit::charge_and_hold` (deposit_payment.rs:348-375) charges either PGAS or, on fallback, native currency, and — only on the native branch — records the contribution in `NativeDepositOf::<T>::mutate(to, from, ...)` via `record_native_deposit` (deposit_payment.rs:556-562). This map is the sole source of truth `refund_on_hold` uses to decide how much of a refund must come back in native currency vs. PGAS: [1](#0-0) 

```
let contribution = NativeDepositOf::<T>::get(from, to);
let native_requested = amount.min(contribution);
... release native up to native_requested ...
let pgas_needed = amount.saturating_sub(native_refunded);
Self::settle_pgas_refund(reason, from, to, pgas_needed)?;
```

`settle_pgas_refund` then caps whatever it settles at the PGAS actually held, and if that is less than requested, it just settles less — with no error and no signal to the caller: [2](#0-1) 

```
fn settle_pgas_refund(...) -> Result<BalanceOf<T>, DispatchError> {
    if amount.is_zero() { return Ok(BalanceOf::<T>::zero()); }
    let pgas_held = Self::pgas_on_hold(reason, from);
    let amount = amount.min(pgas_held);
    if amount.is_zero() { return Ok(BalanceOf::<T>::zero()); }
    ...
}
```

`refund_on_hold` propagates this as `Ok(())` regardless of whether the full requested `amount` was actually released. The caller, `Pallet::refund_deposit` in `lib.rs`, treats any `Ok` result as a fully successful refund and never re-checks the residual hold: [3](#0-2) 

The storage meter (`metering/storage.rs`) that drives these calls also treats `Deposit::Refund(amount)` as fully settled once `Ext::charge` returns `Ok(())`: [4](#0-3) 

The precondition `NativeDepositOf` bookkeeping can desync from the real custody split precisely because — as documented in the `v4` migration prdoc — pre-existing native deposits were never tracked per-contributor before this feature, and the flip from native to PGAS custody is done through a *separate*, multi-block migration path (`Deposit::migrate_native_to_pgas`) that is explicitly called out as "Not part of the regular charge/refund flow": [5](#0-4) [6](#0-5) 

Because the runtime's `Config::Deposit` type switches to `PGasDeposit` atomically at the runtime upgrade while the storage backfill (`NativeDepositOf` population, native→PGAS custody flip) runs over multiple blocks afterward, any `refund_on_hold` reached for a contract whose deposit hasn't yet been migrated sees `contribution = 0` (unrecorded) and `pgas_held = 0` (custody still native under the old `()` backend's hold), so both branches settle nothing — the refund silently vanishes while the meter/caller believe it succeeded.

### Impact Explanation
This is a permanent user-fund lock: contract-held storage-deposit value is not conserved and never settles to the rightful beneficiary — exactly the impact class called out in the gate ("permanent user-fund or bridge-state lock", "Balances... must conserve value and settle exactly once to the rightful beneficiary and amount"). Unlike the original Solidity bug, this failure mode is worse for detection because it does not revert: `refund_on_hold` returns `Ok(())`, so normal test assertions that only check for `assert_ok!` will pass while silently under-refunding. Funds stranded this way are only reachable again via `refund_all` at contract termination (which bypasses the `NativeDepositOf` cap entirely and pays whichever account happens to terminate the contract), meaning intermediate `clear_storage`/deposit-shrink refunds during the multi-block migration window are lost to the legitimate depositor, not just delayed.

### Likelihood Explanation
This requires no malicious actor, governance abuse, or privileged access — it is purely a consequence of the documented multi-block `v4` migration design combined with an unprivileged user calling ordinary storage-shrinking contract operations (which trigger `refund_on_hold`) during the migration's rollout window on any chain that adopts the PGAS deposit backend. Every existing regression test in `substrate/frame/revive/src/tests/deposit_payment.rs` constructs state through `PGasDeposit::init_contract`/`charge_and_hold`, which always correctly populates `NativeDepositOf` — none of the tests exercise a pre-migration contract mid-`v4`-migration state, so this desync path is untested, mirroring exactly how the original report's mock skipped the real `transferFrom` and thus never exercised the missing-approval path.

### Recommendation
Make `refund_on_hold`/`settle_pgas_refund` return an explicit error (or a `(released, shortfall)` tuple that callers must check) whenever the requested `amount` cannot be fully settled from either native or PGAS custody, instead of silently truncating and returning `Ok(())`. Additionally, ensure the `v4` migration's `migrate_native_to_pgas` phase runs to completion for a contract (or the runtime otherwise blocks non-migration-related refund/charge calls against not-yet-migrated contracts) before any `refund_on_hold` call can be dispatched against it, so `NativeDepositOf` and actual held custody can never diverge.

### Proof of Concept
1. Deploy a runtime using `PGasDeposit` as `Config::Deposit`, with an existing contract `C` whose storage deposit was charged and held entirely in native currency before this feature existed (so `NativeDepositOf` has no entry for `C`'s contributors, matching the documented pre-PR state).
2. Trigger the `v4` multi-block migration but stop/observe it before Phase 2 (`migrate_native_to_pgas`) has processed `C` (achievable simply by having many contracts ahead of `C` in the migration queue, since it is explicitly multi-block).
3. While still pre-migration for `C`, have the contract owner shrink storage, invoking `Ext::charge(Deposit::Refund(amount))` → `Pallet::refund_deposit` → `PGasDeposit::refund_on_hold(reason, C, dst, amount)`.
4. Observe: `NativeDepositOf::get(C, dst) == 0` (unbackfilled) and `pgas_on_hold(reason, C) == 0` (custody still native, unmigrated) — both refund branches settle `0`, the call returns `Ok(())`, the meter records the deposit as refunded, yet `T::Currency::balance_on_hold(&HoldReason::StorageDepositReserve.into(), &C)` remains unchanged: the funds are now permanently stranded until `C` is terminated, at which point `refund_all` pays whoever calls termination rather than the original depositor whose refund was silently dropped.

	fn refund_on_hold(
		reason: HoldReason,
		from: &T::AccountId,
		dst: Funds<T::AccountId>,
		amount: BalanceOf<T>,
	) -> DispatchResult {
		let to = match &dst {
			Funds::Balance(to) | Funds::TxFee(to) => *to,
		};
		let contribution = NativeDepositOf::<T>::get(from, to);
		let native_requested = amount.min(contribution);

		let native_refunded = if !native_requested.is_zero() {
			<() as Deposit<T>>::refund_on_hold(reason, from, dst, native_requested)?;
			let new_val = contribution.saturating_sub(native_requested);
			if new_val.is_zero() {
				NativeDepositOf::<T>::remove(from, to);
			} else {
				NativeDepositOf::<T>::insert(from, to, new_val);
			}
			native_requested
		} else {
			BalanceOf::<T>::zero()
		};

		let pgas_needed = amount.saturating_sub(native_refunded);
		Self::settle_pgas_refund(reason, from, to, pgas_needed)?;
		Ok(())
	}

	fn settle_pgas_refund(
		reason: HoldReason,
		from: &T::AccountId,
		to: &T::AccountId,
		amount: BalanceOf<T>,
	) -> Result<BalanceOf<T>, DispatchError> {
		if amount.is_zero() {
			return Ok(BalanceOf::<T>::zero());
		}
		// Cap the amount we settle at what's actually held in PGAS. A refund recipient with
		// no `NativeDepositOf` credit on a contract whose deposit was paid in native would
		// otherwise route the full amount through PGAS and revert on `Precision::Exact`.
		let pgas_held = Self::pgas_on_hold(reason, from);
		let amount = amount.min(pgas_held);
		if amount.is_zero() {
			return Ok(BalanceOf::<T>::zero());
		}

	/// Refund a deposit.
	///
	/// `dst` is usually the transaction origin and `from` a contract or
	/// the pallets own account.
	fn refund_deposit(
		hold_reason: HoldReason,
		from: &T::AccountId,
		dst: deposit_payment::Funds<T::AccountId>,
		amount: BalanceOf<T>,
	) -> Result<(), DispatchError> {
		if amount.is_zero() {
			return Ok(());
		}

		let to = match &dst {
			deposit_payment::Funds::Balance(to) | deposit_payment::Funds::TxFee(to) => *to,
		};
		let result = T::Deposit::refund_on_hold(hold_reason, from, dst, amount);

		result.defensive_map_err(|err| {
			let available = T::Deposit::total_on_hold(hold_reason, from);
			if available < amount {
				// The storage deposit accounting got out of sync with the balance: This would be a
				// straight up bug in this pallet.
				log::error!(
					target: LOG_TARGET,
					"Failed to refund storage deposit {amount:?} from contract {from:?} to origin {to:?}. Not enough deposit: {available:?}. This is a bug.",
				);
				Error::<T>::StorageRefundNotEnoughFunds.into()
			} else {
				// There are some locks preventing the refund. This could be the case if the
				// contract participates in government. The consequence is that if a contract votes
				// with its storage deposit it would no longer be possible to remove storage without first
				// reducing the lock.
				log::warn!(
					target: LOG_TARGET,
					"Failed to refund storage deposit {amount:?} from contract {from:?} to origin {to:?}: {err:?}. First remove locks (staking, governance) from the contracts account.",
				);
				Error::<T>::StorageRefundLocked.into()
			}
		})
	}
