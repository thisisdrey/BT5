## Title
Underpriced/miscalculated swap due to `withdraw()`'s `reducible_balance` gate diverging from `get_balance()`'s full-balance pool accounting - ([File: substrate/frame/asset-conversion/src/lib.rs])

### Summary
The Aave report describes an invariant check comparing a *full account balance* against an internal accounting sum that becomes permanently false once part of the balance is moved out-of-band (lent to Aave), because the check never accounts for externally-held funds. The closest verifiable local analog is in `pallet-asset-conversion`: `get_balance`/`get_reserves` price and quote swaps using the pool account's **full** balance (`T::Assets::balance`), while the actual token movement out of the pool in `withdraw()` is gated by `T::Assets::reducible_balance(..., Preserve, Polite)` [1](#0-0) . Reserves and prices are computed from the full balance [2](#0-1) , but any part of that balance that is held/frozen/non-reducible (e.g. via a `Hold`/`Freeze` placed by another pallet on the pool account, or non-sufficient-asset restrictions) is invisible to the AMM math yet blocks actual withdrawal. This exact "balance used for accounting ≠ balance actually movable" mismatch was flagged and partially fixed for pool *price* reads in `pr_12408.prdoc`, confirming the pattern is a real, previously-known class of bug in this pallet [3](#0-2) , but the `withdraw()` path (used for the actual token transfer out of the pool for both `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens`) still uses `reducible_balance` explicitly with a `TODO` marker referencing an unresolved upstream issue [4](#0-3) .

### Finding Description
`do_swap`/route resolution computes `amount_out` for each hop using `get_amount_out`/`get_amount_in`, which are derived from `reserve1`/`reserve2` fetched via `get_balance` — i.e. the **full** `T::Assets::balance` of the pool account, not the reducible portion [2](#0-1) . This is by design for pricing consistency (per the referenced fix in `pr_12408.prdoc`).

However, the actual settlement of the "amount out" leg is done via `withdraw()`, which for `keep_alive = true` (the common/default swap mode) checks `T::Assets::reducible_balance(asset, who, Preserve, Polite) >= value` before calling the real `T::Assets::withdraw` [1](#0-0) . The comment explicitly says this `ensure!` is a workaround for a known unresolved issue (`paritytech/polkadot-sdk#1698`) and should ideally not exist, meaning it is a known-fragile invariant, not an intentionally hardened guard [4](#0-3) .

Because two different balance notions are mixed in the same code path — pricing/reserve math on full balance, but withdrawal permission on reducible balance — whenever the pool account has any held/frozen/locked portion of an asset (which can legitimately occur, e.g. from `Freezer`/`Holder` implementations wired into `T::Assets` for that asset, or ED-driven `Preserve` requirements on the pool account itself), the AMM will:
- Quote/accept a swap based on reserves that include the non-reducible amount (over-crediting available liquidity), then
- Fail the withdrawal with `TokenError::NotExpendable` mid-execution once the reducible check kicks in, or
- Succeed in over/under-pricing trades relative to the actually spendable liquidity, distorting swap economics for the counterparty who already had `amount_in` transferred into the pool in `do_swap`/`resolve_path` before the final leg's `withdraw()` is attempted (transfer is executed hop-by-hop; on the final hop's failure the whole extrinsic is expected to be atomic/rolled back, but the AMM's price signal used by other pallets/off-chain quoting is already wrong, and the mismatch is precisely the "invariant using the wrong subset of balance" pattern seen in the Aave report).

This mirrors the Aave bug exactly: the report's checkInvariant() assumed `balance == vaultCollatSize + collatLentOut` and broke when tokens left the tracked slice; here, reserve pricing assumes `balance` (full) represents spendable liquidity while withdrawal enforcement uses a strictly smaller slice (`reducible_balance`), so the "invariant" (price computed == liquidity truly available) silently diverges instead of failing loudly, and the pallet authors themselves acknowledge (via the TODO) that the check is not properly aligned with the real state.

### Impact Explanation
This falls under "runtime bugs that compromise intended behavior" and "public underpriced work that degrades block production or stalls bridge processing" analogues for AMM pricing correctness: a public, unprivileged `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens`/`add_liquidity`/`remove_liquidity` caller can get inconsistent pricing/reserve accounting versus actual spendable liquidity, which can be leveraged to extract value at a wrong price or cause legitimate swaps to unexpectedly revert (denial of intended swap execution / stuck liquidity), particularly on any asset whose `T::Assets` implementation attaches holds/freezes to accounts (a supported, not hypothetical, configuration in FRAME's fungibles trait set).

### Likelihood Explanation
Moderate. It requires an asset configuration where the pool account's balance for some asset has a non-reducible portion (hold/freeze) — a supported and used pattern elsewhere in the runtime (e.g. `HoldReason`s from other pallets, or ED/`Preserve` requirements). The existence of the `TODO`/tracked upstream issue and the prior partial fix (`pr_12408`) for the price-reading half of this exact inconsistency strongly indicates the underlying class of bug is real and only partially remediated; the `withdraw()` leg was left untouched.

### Recommendation
Align the liquidity/reserve computation with the same "spendable" notion used at withdrawal time (or vice versa): either compute `get_balance`/`get_reserves` using `reducible_balance` consistently, or remove/replace the `ensure!` in `withdraw()` with logic that fails fast at quote time rather than deep in execution, and add an integration test that seeds a hold/freeze on the pool account's asset balance and verifies quoted price equals actually deliverable liquidity.

### Proof of Concept
1. Create a pool for `(asset1, asset2)` via `create_pool`.
2. Add liquidity so the pool account holds `reserve2` units of `asset2`.
3. Using `asset2`'s fungibles `Holder`/`Freezer` (or any pallet wired to place a hold on `T::Assets` for that asset — e.g., simulate with `T::Assets::hold` on the pool account) freeze a portion `H` of `asset2` on the pool account so that `reducible_balance(asset2, pool_account, Preserve, Polite) = reserve2 - H`.
4. Call `quote_price_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` requesting `amount_out` such that `reserve2 - H < amount_out <= reserve2`: the AMM math (based on full `reserve2`) will accept/quote it as valid, but `withdraw()`'s reducible-balance `ensure!` will reject it with `TokenError::NotExpendable`, demonstrating the divergence between priced/accepted reserves and actually deliverable liquidity described in `pr_12408.prdoc` and left unresolved in `withdraw()`.
