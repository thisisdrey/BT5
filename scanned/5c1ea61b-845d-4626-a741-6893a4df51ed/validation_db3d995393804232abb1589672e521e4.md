## Title
`set_configs` lowering `GlobalMaxCommission` retroactively re-rates already-accrued pool rewards, diverting commission from the payee to members - ([File: substrate/frame/nomination-pools/src/lib.rs])

## Summary
`Pallet::set_configs` writes `GlobalMaxCommission` directly with no snapshot of any pool's reward pool, while `Commission::current()` computes the *effective* commission dynamically as `min(current, GlobalMaxCommission)`. Every mutating pool operation (`join`, `bond_extra`, `unbond`, `claim_payout`, `set_commission`, `set_commission_max`) calls `RewardPool::update_records(..., bonded_pool.commission.current(), ...)` to rate the *entire unsnapshotted balance since the last update* at whatever `current()` returns at call time. Lowering `GlobalMaxCommission` therefore silently re-rates rewards that already accrued at the pool's higher intended commission rate, transferring the differential from the commission payee to the pool members. This is the same broken invariant already identified and fixed for the single-pool path (`set_commission_max`, patched in PR #12397/commit referenced in `prdoc/pr_12397.prdoc`), but the *global* cap path through `set_configs` was left unprotected.

## Finding Description
`RewardPool::update_records` computes payouts based on the pool balance delta since the last snapshot, split between members and commission using whatever commission rate is passed in at call time: [1](#0-0) 

The commission rate used is `bonded_pool.commission.current()`, which is **not** the pool's nominal `current` rate but a live, dynamically-bounded value: [2](#0-1) 

The pallet already recognizes that force-lowering the effective commission before a snapshot is a bug: `set_commission_max` was patched specifically because `try_update_max` could force-lower `current` and, absent a prior `update_records` call, subsequently re-rate *already-accrued* rewards at the new lower rate, crediting the differential to members instead of the commission payee: [3](#0-2) 

This fix (and the identical ordering in `set_commission`) is documented as the remediation for exactly this bug class in `prdoc/pr_12397.prdoc`. However, `GlobalMaxCommission` — which participates in the *same* `min()` clamp inside `current()` — can be lowered through `set_configs` without any equivalent snapshot, and it affects every pool in the system simultaneously, not just one: [4](#0-3) 

Because `set_configs` performs a bare `GlobalMaxCommission::<T>::put(v)` with no iteration over `RewardPools` and no call to `update_records`, any pool whose nominal `current` commission is above the new global max will have its *entire unsnapshotted reward history* (from the last `update_records` call up to whenever the next member action happens) re-rated at the lower global cap the moment any pool member action triggers `update_records`. The existing regression test `global_max_caps_max_commission_payout` only exercises the case where rewards are deposited *after* the global cap is lowered, so it does not exercise (or protect against) the case where rewards accrue at the higher rate first and the cap drop happens before the next snapshot: [5](#0-4) 

## Impact Explanation
This breaks the invariant that reward-pool value must "settle exactly once to the rightful beneficiary and amount." Commission that a pool operator legitimately earned at their configured (and previously global-max-compliant) rate is misattributed to pool members instead of the commission payee, purely as a side effect of a config update that never touches per-pool `RewardPool` state. Because `GlobalMaxCommission` is a single global storage item, a single `set_configs` call can retroactively divert commission away from the payee across every pool in the runtime simultaneously — a much larger blast radius than the single-pool case that was already fixed.

## Likelihood Explanation
This does not require a malicious actor: it is a straightforward interaction between two pre-existing extrinsics (`set_configs` and any member-mutating call such as `join`/`unbond`/`claim_payout`) that is already known to be dangerous in the single-pool analog (as evidenced by the dedicated fix and prdoc for `set_commission_max`). The pattern is deterministic and reproducible with two ordinary transactions plus any subsequent user action — no privileged abuse of intent is required, only the omission of a snapshot step that the codebase itself has already proven necessary elsewhere.

## Recommendation
Before mutating `GlobalMaxCommission` in `set_configs`, snapshot every affected pool's `RewardPool` at its pre-change effective commission, mirroring the ordering already used in `set_commission` / `set_commission_max`. Since iterating all pools inside one extrinsic is likely infeasible/unbounded, an alternative is to decouple "effective, bounded commission used for `update_records`" from the live `GlobalMaxCommission` value by recording, per pool, the last commission rate that was actually snapshotted, and only allow the global cap to apply prospectively (e.g., by lazily calling `update_records` with the pool's own last-snapshotted rate for the pre-change period, then the new bounded rate afterward) — or by treating `GlobalMaxCommission` reductions as taking effect only after each pool has been synced via an explicit permissionless "sync" call/hook before the new cap is enforced in `update_records`.

## Proof of Concept
1. Pool `P` has `commission.current = 90%`, payee `X`; `GlobalMaxCommission` is unset (or ≥ 90%).
2. Rewards of `100` units are deposited into `P`'s reward account (`deposit_rewards(100)` equivalent) — no `join`/`unbond`/`set_commission`/`claim_payout` is called yet, so `RewardPool::update_records` has not run and the pool balance increase is not yet snapshotted.
3. `AdminOrigin` calls `set_configs(..., global_max_commission = ConfigOp::Set(Perbill::from_percent(10)))`. This only does `GlobalMaxCommission::<T>::put(10%)`; no `RewardPools` entry is touched.
4. Any pool member calls `claim_payout` (or another member calls `join`/`unbond`). This invokes `RewardPool::update_records(pool_id, points, bonded_pool.commission.current())`, and `commission.current()` now returns `min(90%, 10%) = 10%`.
5. Result: the full `100` units of pending payout balance accrued while the *intended* rate was `90%` is split as if the rate had always been `10%` — `90` credited to members' claimable rewards instead of `10`, and only `10` (not `90`) credited as `total_commission_pending` for payee `X`. `X` permanently loses the `80` unit differential that was already earned under the pool's advertised 90% commission, with no mechanism to reclaim it, since the differential is spent to `deposit_rewards`/members' claimable balances once `update_records` runs.

	/// Update the recorded values of the reward pool.
	///
	/// This function MUST be called whenever the points in the bonded pool change, AND whenever the
	/// the pools commission is updated. The reason for the former is that a change in pool points
	/// will alter the share of the reward balance among pool members, and the reason for the latter
	/// is that a change in commission will alter the share of the reward balance among the pool.
	fn update_records(
		&mut self,
		id: PoolId,
		bonded_points: BalanceOf<T>,
		commission: Perbill,
	) -> Result<(), Error<T>> {
		let balance = Self::current_balance(id);

		let (current_reward_counter, new_pending_commission) =
			self.current_reward_counter(id, bonded_points, commission)?;

		// Store the reward counter at the time of this update. This is used in subsequent calls to
		// `current_reward_counter`, whereby newly pending rewards (in points) are added to this
		// value.
		self.last_recorded_reward_counter = current_reward_counter;

		// Add any new pending commission that has been calculated from `current_reward_counter` to
		// determine the total pending commission at the time of this update.
		self.total_commission_pending =
			self.total_commission_pending.saturating_add(new_pending_commission);

		// Total payouts are essentially the entire historical balance of the reward pool, equating
		// to the current balance + the total rewards that have left the pool + the total commission
		// that has left the pool.
		let last_recorded_total_payouts = balance
			.checked_add(&self.total_rewards_claimed.saturating_add(self.total_commission_claimed))
			.ok_or(Error::<T>::OverflowRisk)?;

		// Store the total payouts at the time of this update.
		//
		// An increase in ED could cause `last_recorded_total_payouts` to decrease but we should not
		// allow that to happen since an already paid out reward cannot decrease. The reward account
		// might go in deficit temporarily in this exceptional case but it will be corrected once
		// new rewards are added to the pool.
		self.last_recorded_total_payouts =
			self.last_recorded_total_payouts.max(last_recorded_total_payouts);

		Ok(())
	}
