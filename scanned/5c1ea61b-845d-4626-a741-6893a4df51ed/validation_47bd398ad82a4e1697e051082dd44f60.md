## Title
Donation-Inflation Attack on `pallet-asset-conversion` LP-Share Minting via Raw `balance()` Reserve Reads - (File: `substrate/frame/asset-conversion/src/lib.rs`)

## Summary
`pallet_asset_conversion::Pallet::do_add_liquidity` and `get_reserves` compute pool "reserves" by calling `Self::get_balance`, which is a thin wrapper around `T::Assets::balance(asset, owner)` — i.e., the *raw total balance* held by the deterministic `pool_account`, not an internally tracked accounting value. This is structurally identical to the reported `Aggregator.totalAssets()` bug: any account can push tokens directly to the pool's address (a value fully known in advance from `PoolLocator::pool_address`) and thereby distort the reserve values used in the LP-token minting formula, exactly mirroring the external report's root cause (`amount * totalShares / totalAssets` driven by raw `balanceOf`).

Because `T::Assets::balance()` reads the *actual on-chain balance* of the `pool_account` (an address deterministically derivable via `PoolLocator::pool_address`/`PoolLocator::address` before or after pool creation), an attacker can transfer (donate) `asset1`/`asset2` directly to that account without going through `add_liquidity` at all. This inflates `reserve1`/`reserve2` relative to `T::PoolAssets::total_issuance(pool.lp_token)`, which the pallet has no mechanism to detect or exclude — there is no internal ledger of "deposited-via-add_liquidity" balances separate from the raw asset balance, exactly the flaw called out in the original report ("create a mapping which handles any deposit and withdrawal rather than depending on ... `balanceOf(address(this))`").

The classic exploitation path (ERC4626-style inflation attack, here applied to the AMM's LP token):
1. Attacker is first liquidity provider, deposits a minimal amount, receiving `lp_token_amount = sqrt(amount1*amount2) - MintMinLiquidity` (via `calc_lp_amount_for_zero_supply`), while `MintMinLiquidity` LP units are minted to `pool_account` itself, locked forever.
2. Attacker then donates a large amount of `asset1`/`asset2` directly to `pool_account`, inflating `reserve1`/`reserve2` without minting any additional LP tokens.
3. When a genuine LP then calls `add_liquidity`, `Self::mul_div(&amount, &total_supply, &reserve)` (lines 869–871) computes their LP-token share against the inflated reserve, causing severe under-minting/rounding-to-near-zero for the victim's deposit relative to the value they contributed, while the attacker's existing LP tokens (plus the donated funds sitting in the pool) become disproportionately valuable when later redeemed via `remove_liquidity`, which pays out `mul_div(&lp_redeem_amount, &reserve, &total_supply)` (lines 919–920) using the same raw-balance reserves.

The `MintMinLiquidity` constant (locked to `pool_account` on first deposit) is the pallet's only mitigation — it is the same defense Uniswap V2 uses, and it only raises the cost of the attack; it does not close the underlying flaw that reserves are read directly from `balance()` instead of an internally accounted ledger. For any asset pair using a cheap/high-decimal, low-value token, or where an attacker has enough capital for the target pair, the mitigation is insufficient, and the same "attacker manipulates the amount that should be minted to users by donating to the balance the accounting logic reads" primitive from the report applies verbatim.

## Impact Explanation
This directly matches the "Balances, assets ... must conserve value and settle exactly once to the rightful beneficiary and amount" pivot. A successful attack causes:
- Under-minting of LP tokens to a genuine depositor relative to the value contributed (their funds are absorbed into the pool without fair LP-token compensation).
- Disproportionate value extraction by the attacker on `remove_liquidity`, since redemption is also computed from the same raw, donation-inflated `get_reserves()` values.

This is an unprivileged, public-entrypoint (`add_liquidity`/`remove_liquidity`/plain `transfer`) attack causing wrong-amount settlement of value inside a core FRAME pallet used on Asset Hub (`cumulus/parachains/runtimes/assets/asset-hub-*`), satisfying the "theft or wrong beneficiary or amount" impact category.

## Likelihood Explanation
Likelihood is constrained by the cost of the donation needed to meaningfully skew the ratio, and by the `MintMinLiquidity::get()` floor check (`ensure!(lp_token_amount > T::MintMinLiquidity::get())`), which somewhat limits (but does not eliminate) the attack's profitability, especially against pools with existing meaningful liquidity. The attack is most practical against freshly created, thinly-liquid pools right after `create_pool`, before other users add liquidity — a scenario an attacker fully controls without needing a malicious validator, collator, or relayer, and without relying on transaction-ordering/front-running of another user's specific transaction (the attacker acts entirely unilaterally: create pool → deposit minimal LP → donate → wait for victims).

## Recommendation
Track pool reserves via an internal storage-based accounting ledger (updated atomically inside `do_add_liquidity`, `do_remove_liquidity`, and swap paths) instead of deriving `reserve1`/`reserve2` from `T::Assets::balance(asset, &pool_account)`. If raw balances must still be used for view/quote purposes, gate LP-token minting/burning math against the tracked ledger value, and reconcile/ignore untracked "donated" balances (e.g., treat any balance above the tracked ledger as protocol-owned dust rather than part of the swap/mint invariant), similar to how Uniswap V2's `sync()` function is intentionally separated from mint/burn accounting.

## Proof of Concept
Conceptual sequence exercising `pallet_asset_conversion` extrinsics (values illustrative):
```text
1. attacker: create_pool(asset1, asset2)                     // pool_account derived deterministically
2. attacker: add_liquidity(asset1, asset2, 1, 1, 0, 0, attacker)
   -> lp_token_amount = sqrt(1*1) - MintMinLiquidity  (attacker holds this)
   -> MintMinLiquidity LP units locked to pool_account
3. attacker: Assets::transfer(asset1, attacker, pool_account, LARGE_AMOUNT)
   attacker: Assets::transfer(asset2, attacker, pool_account, LARGE_AMOUNT)
   -> reserve1, reserve2 (via get_balance/get_reserves) now include donated funds
4. victim: add_liquidity(asset1, asset2, V, V, 0, 0, victim)
   -> reserve1/reserve2 inflated by attacker's donation
   -> lp_token_amount = min(mul_div(V, total_supply, reserve1), mul_div(V, total_supply, reserve2))
   -> rounds down to a value far smaller than victim's fair share
5. attacker: remove_liquidity(asset1, asset2, attacker_lp_tokens, 0, 0, attacker)
   -> amount1/amount2 = mul_div(lp_redeem_amount, reserve, total_supply)
   -> attacker recovers disproportionate share, including part of victim's V deposit
```
