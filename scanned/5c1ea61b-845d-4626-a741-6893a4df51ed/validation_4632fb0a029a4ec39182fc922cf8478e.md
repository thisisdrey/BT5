## Title
Teleported protocol funds from `pallet-accumulate-and-forward` can be permanently trapped at the destination with no recovery path when the remote `DepositAsset` fails - (File: `polkadot/xcm/xcm-builder/src/forwarder.rs`)

### Summary
`pallet_accumulate_and_forward::Forwarder` is implemented by `TeleportForwarderForAccountId32`, which teleports the accumulated native-token balance from a system chain's accumulation account to a `StagingLocation` (e.g. the DAP buffer account) on a destination chain via `InitiateTransfer` + remote `DepositAsset`. The adapter's own doc comment concedes: *"Once the local executor reports success, the message is queued and any destination-side rejection results in trapped assets at the destination with no automatic recovery path."* Unlike the `BorrowLiquidation` contract in the external report — which receives ETH from `closeThePositionInSynthetix` with no `withdrawETH`/`withdrawTokens` function — this pallet burns real protocol funds (fees, dust, coretime revenue) on the source chain, and if the remote `DepositAsset` instruction fails on the destination, those funds are stuck in the destination's asset trap under an origin that nobody can practically reconstruct to sign a recovery `claim_assets` call. [1](#0-0) 

### Finding Description
`TeleportForwarderForAccountId32::forward` builds and executes the following program locally: [2](#0-1) 

The program is: `UnpaidExecution → DescendOrigin(source) → WithdrawAsset → InitiateTransfer{Teleport, preserve_origin: true, remote_xcm: [DepositAsset]}`. `with_transaction` only rolls back state if the **local** `prepare_and_execute` returns anything other than `Outcome::Complete`. Once local execution succeeds, the teleported credit and total-issuance burn (documented in the pallet: *"Accumulated funds are burnt upon forwarding … and the same funds are minted at the destination when the sent message is received"*) are committed and the XCM message is queued for delivery. [3](#0-2) 

If, on the destination chain, the remote program's `DepositAsset { assets: Wild(AllCounted(1)), beneficiary }` fails — e.g. the `StagingLocation`/buffer account is filtered, does not exist and can't be created (ED not met), the asset filter rejects the deposit, or `pallet-dap`/`pallet-society`-style config on the destination changes — the XCM executor traps the held assets via `AssetTrapper`/`DropAssets`, emitting `AssetsTrapped` keyed on the *effective origin at the destination*. Because `preserve_origin: true` causes `InitiateTransfer` to prepend `AliasOrigin(source_location)`, the trap is recorded against the **aliased source location**, i.e. the sending chain's `pallet-accumulate-and-forward` accumulation account (a `PalletId`-derived `AccountId32`, e.g. `*b"acf/dott"`). This account has no private key. Recovering trapped assets on Polkadot chains requires a signed origin whose `SignedToAccountId32`-derived `Location` matches the trap's origin key (as demonstrated by the Snowbridge fallback-claimer fix, where a mismatched `network` field alone made `claim_assets` permanently fail with `UnknownClaim`): [4](#0-3) 

Since the accumulation account is a pallet-derived technical account and not a keyed account anyone can sign for, there is no way to submit a matching `pallet_xcm::claim_assets` from that exact origin — the funds are burnt on the source chain and permanently stuck in the destination's trap.

### Impact Explanation
This is a real protocol-funds loss path, not a user self-inflicted mistake: `pallet-accumulate-and-forward` runs autonomously from `on_idle`, forwarding fees, dust-removal proceeds, and coretime revenue accumulated on system chains (Westend relay chain, Collectives, and other parachains per their runtime configs) into the shared DAP buffer account on Asset Hub. Any transient misconfiguration or destination-side condition that causes the `DepositAsset` to fail (e.g. buffer account temporarily below ED, filter change, `pallet-dap` unavailability) results in protocol revenue being burned on the source chain and permanently trapped at the destination, unrecoverable by any signer, directly matching the report's core invariant — "assets received by a component with no withdrawal mechanism are permanently locked."

### Likelihood Explanation
The path does not require a malicious actor, admin, or governance abuse — it only requires a destination-side execution failure that the source-side transactional rollback in `forward` cannot see or protect against (rollback only covers local execution, not remote XCM effects). The adapter's own inline documentation acknowledges this exact scenario as an accepted-but-unmitigated risk ("no automatic recovery path"), confirming this is a real, currently-unresolved gap rather than a hypothetical.

### Recommendation
Add an explicit, permissionless recovery mechanism analogous to `pallet-bounties::reclaim_bounty_funds` or `pallet-nomination-pools::do_claim_trapped_balance`: either (a) route the remote `DepositAsset` beneficiary/claimer through a keyed sovereign or governance-controlled account that can realistically sign `claim_assets`, or (b) add a governance-gated extrinsic on the destination chain that can claim assets trapped under the known `AccumulateForwardPalletId`-derived origin and re-credit them to the buffer account, mirroring the Snowbridge default-claimer fix that pinned the fallback claimer to a signable location.

### Proof of Concept
Conceptual reproduction (destination-side failure is not directly test-harnessed in-repo, but the code and docs establish the path):
1. On a system chain configured with `pallet_accumulate_and_forward::Config::Forwarder = TeleportForwarderForAccountId32<..., StagingLocation>` (e.g. Westend relay chain or Collectives-Westend, per their runtime configs), let fees/dust/coretime revenue accumulate past `MinTransferAmount`.
2. `on_idle` fires, `Forwarder::forward` executes locally with `Outcome::Complete`, burning the funds and queuing the teleport+`InitiateTransfer` XCM to Asset Hub.
3. On Asset Hub, arrange for the remote `DepositAsset { beneficiary: StagingLocation }` to fail (e.g. the DAP staging/buffer account is filtered or cannot receive the asset) — the executor traps the assets, recording the trap origin as the aliased source account (`AccumulateForwardPalletId`-derived `AccountId32`).
4. Attempt `pallet_xcm::claim_assets` from any signed account: no signer can produce a `Location` matching the pallet-derived technical account, so `UnknownClaim`/no valid claim exists — funds remain trapped indefinitely, while total issuance on the source chain has already been permanently reduced. 	fn forward(source: AccountId, amount: Balance) -> Result<(), ()> {
		let dest = Dest::get();
		let asset = Asset { id: AssetId(NativeAsset::get()), fun: Fungible(amount.into()) };
		let beneficiary: Location = StagingLocation::get().into_location();

		let remote_xcm = Xcm(vec![DepositAsset { assets: Wild(AllCounted(1)), beneficiary }]);

		// The XCM flow: `ReceiveTeleportedAsset → AliasOrigin(source) → UnpaidExecution →
		// DepositAsset`. `preserve_origin: true` causes `InitiateTransfer` to prepend
		// `AliasOrigin(source_location)` to the remote XCM.
		let xcm: Xcm<XcmConfig::RuntimeCall> = Xcm(vec![
			UnpaidExecution { weight_limit: WeightLimit::Unlimited, check_origin: None },
			DescendOrigin(Junction::AccountId32 { network: None, id: source.into() }.into()),
			WithdrawAsset(asset.into()),
			InitiateTransfer {
				destination: dest,
				remote_fees: None,
				preserve_origin: true,
				assets: BoundedVec::truncate_from(alloc::vec![AssetTransferFilter::Teleport(
					Wild(AllCounted(1))
				),]),
				remote_xcm,
			},
		]);

		with_transaction(|| -> TransactionOutcome<Result<(), DispatchError>> {
			let outcome = XcmExecutor::<XcmConfig>::prepare_and_execute(
				Location::here(),
				xcm,
				&mut [0u8; 32],
				Weight::MAX,
				Weight::MAX,
			);

			match outcome {
				Outcome::Complete { .. } => TransactionOutcome::Commit(Ok(())),
				exec_error => {
					tracing::debug!(
						target: LOG_TARGET,
						?exec_error,
						"accumulate-forward: XCM execution failed"
					);

					TransactionOutcome::Rollback(Err(DispatchError::Other("XCM execution failed")))
				},
			}
		})
		.map_err(|_| ())
	}

doc:
- audience: Runtime Dev
  description: |-
    The inbound-queue v2 message converter falls back to the Snowbridge sovereign
    account on AssetHub as the asset claimer when no explicit claimer is supplied.
    Previously this fallback used `AccountId32 { network: None, .. }`, which did

    `network: Some(LocalNetwork)`). The trap-key hash stored on `AssetsTrapped`

    making default-claimer trapped funds effectively unrecoverable without a
    runtime upgrade.

    This PR sets `network: Some(LocalNetwork::get())` on the fallback claimer so
    its `Location` agrees with what `SignedToAccountId32<_, _, LocalNetwork>`
    yields on AssetHub, and adds a test covering the no-claimer-supplied path.
