### Title
Hardcoded `determine_call_stipend` weight budget breaks EVM `.transfer()`/`.send()` reentrancy-protection guarantee as future weight re-benchmarks change - ([File: substrate/frame/revive/src/metering/math.rs])

### Summary
Pallet-revive emulates Ethereum's `.transfer()`/`.send()` 2300-gas stipend by converting the fixed `CALL_STIPEND` (2300) Ethereum-gas constant into a Substrate `Weight` via `determine_call_stipend::<T>()`, and using this hardcoded, benchmark-derived weight as the *entire* resource budget granted to the receiver of a value-bearing call. This is the same anti-pattern flagged in the M-3 report (a fixed, non-adjustable gas allowance for external calls that silently breaks when the true cost of operations changes), just moved from Solidity's `transfer()`/`send()` primitive into pallet-revive's own reimplementation of that primitive.

### Finding Description
`determine_call_stipend` computes a single fixed `Weight` value from the current benchmark-derived cost of the `EVMGas(CALL_STIPEND)` token plus a conservatively-sized `DepositEvent` weight: [1](#0-0) 

This value is used verbatim as the weight budget handed to the callee both in the "Substrate execution" nested-meter path and the "Ethereum execution" nested-meter path whenever `add_stipend` is set: [2](#0-1) [3](#0-2) 

`add_stipend`/`ReentrancyProtection` is decided purely by a heuristic in the EVM interpreter that pattern-matches on `value != 0` or `gas_limit == CALL_STIPEND` on the stack, exactly reproducing solc's `transfer`/`send` code-gen table: [4](#0-3) 

Because `determine_call_stipend` is derived from `RuntimeCosts::DepositEvent`/`EVMGas` weight constants that are periodically re-benchmarked (as documented for the exact same function in `prdoc/stable2603/pr_11151.prdoc`, which had to bump the stipend once already to "cover emitting a LOG event on top of the base 2300 gas operations"), any future increase to the weight cost of `SetStorage`, `DepositEvent`, or base instruction execution (due to new hardware benchmarking, PolkaVM interpreter changes, or new metering constants) shrinks the effective gas-equivalent budget available to a `receive()`/fallback function without any corresponding change on the Solidity side. A receiver contract that previously fit inside the 2300-gas-equivalent budget (e.g. `SimpleReceiver` emitting one event, as exercised by `evm_call_stipends_work_for_transfers`) can start reverting with `OutOfGas` purely because of a runtime-side weight re-benchmark, even though its EVM bytecode and gas usage are unchanged and it would succeed on real Ethereum. [5](#0-4) 

This is the runtime-side mirror of the original bug class: a fixed allowance meant to represent "just enough gas for simple bookkeeping" is baked into constant computation rather than tied to the actual EVM gas value carried by the transaction, so it can silently diverge and break previously-working integrations when the underlying cost model changes.

### Impact Explanation
This falls under "runtime bugs that compromise intended behavior": pallet-revive's entire premise is Ethereum equivalence (tooling, contracts, and dApps built for EVM should behave identically). A weight-benchmark update — a routine maintenance action, not an attack — can retroactively break `.transfer()`/`.send()` calls to previously-compatible receiver contracts across every deployed contract using those primitives, without any bytecode change, causing legitimate fund transfers to unexpectedly revert. Because `Currency::transfer`-based payouts throughout the ecosystem (vesting, marketplaces, escrow, reward distributors) commonly rely on `.transfer()`/`.send()` for safety against reentrancy, a stipend that becomes insufficient can turn "safe" payment paths into permanently failing ones, which is a fund-lock-adjacent availability regression at chain-upgrade time.

### Likelihood Explanation
The trigger condition is not attacker-controlled input but an ordinary maintenance event (weight re-benchmarking / runtime upgrade), which happens routinely in the polkadot-sdk release cycle. The repository's own history shows this has already occurred once (`pr_11151` had to inflate the stipend to also cover a `DepositEvent`), confirming the budget is fragile and was already found insufficient in practice for a case scoped in-repo as "simple" (`SimpleReceiver.receive()` emitting an event). Any future bump to `SetStorage`/`DepositEvent`/base instruction weights, or addition of new mandatory per-call overhead, reproduces the same class of regression without any code change to affected contracts.

### Recommendation
Do not derive the callee's resource budget for the stipend path from a single hardcoded weight snapshot. Instead, either (a) benchmark and pin the stipend to the actual EVM-gas-equivalent conversion used for the rest of the transaction (so it scales automatically with `FeeInfo`/`GasScale` updates rather than needing a manual weight recomputation each time base costs change), or (b) treat the 2300-gas budget as a floor and add explicit compensation for known "unavoidable" per-call overhead (event deposit, storage write) computed dynamically from current weight constants at call time rather than baked into a constant function that must be hand-updated whenever benchmarks change. Add a regression test that fails CI whenever `determine_call_stipend()` computed against current benchmarks would be insufficient for `SimpleReceiver`/`ComplexReceiver`-class fixtures, so future benchmark bumps are caught before release rather than discovered as behavioral regressions.

### Proof of Concept
1. Deploy `StipendTest` (already present in `substrate/frame/revive/fixtures/contracts/Stipends.sol`) with `SimpleReceiver` wired in as in the existing `evm_call_stipends_work_for_transfers` test.
2. Confirm `testTransfer()`/`testSend()` currently pass, i.e. `SimpleReceiver.transfer(amount)` succeeds because `determine_call_stipend::<T>()` happens to cover `CALL_STIPEND` gas-equivalent weight + one `DepositEvent`.
3. Simulate a routine weight re-benchmark by increasing the benchmarked weight for `RuntimeCosts::DepositEvent` or `SetStorage` (e.g. patch the weight constants file as would happen after new hardware benchmarking), without touching `Stipends.sol` or `determine_call_stipend`'s formula.
4. Re-run `evm_call_stipends_work_for_transfers`: the previously-passing `SimpleReceiver.transfer()`/`.send()` call now reverts with `OutOfGas`, demonstrating that a purely runtime-side maintenance change silently breaks a contract that is unchanged and was previously interoperable — the direct analog of the "changing gas costs may break integrations in the future" impact in the source report. [6](#0-5)

	let gas_weight = <EVMGas as Token<T>>::weight(&EVMGas(CALL_STIPEND));
