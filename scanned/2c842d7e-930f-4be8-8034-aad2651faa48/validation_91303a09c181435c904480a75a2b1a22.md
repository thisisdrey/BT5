### Title
Nomination-pools uses the staking `CurrentEra` (planned) instead of `ActiveEra` for unbonding/withdrawal accounting, permanently trapping member funds - (File: `substrate/frame/nomination-pools/src/adapter.rs`)

### Summary
`pallet-nomination-pools` computes both the era at which a member's unbond becomes unlockable (`unbond()`) and the era used to decide which unbonding chunks are releasable (`withdraw_unbonded()`) from `T::StakeAdapter::current_era()`. This adapter method is documented as returning the *active* era, but for the legacy `pallet-staking` backend it actually returns the *planned* era (`CurrentEra`), which can run one era ahead of the real `ActiveEra` while an election is in flight. This is the exact "CurrentEra vs ActiveEra mismatch" root cause that already caused a real trapped-balance incident fixed only via a one-time storage migration (`prdoc/stable2512-3/pr_11018.prdoc`), while the claimed fix (`prdoc/stable2512-2/pr_10986.prdoc`, "Use active era for withdrawals") was only applied to `pallet-staking-async`'s `StakingInterface::current_era()`, not to legacy `pallet-staking`.

### Finding Description
`StakeStrategy::current_era()` in nomination-pools is documented to return the active era: [1](#0-0) 

but it simply forwards to whatever the generic `T::CoreStaking: StakingInterface` implementation returns:
```rust
fn current_era() -> EraIndex {
    Self::CoreStaking::current_era()
}
```

For legacy `pallet-staking` (still the backend for the overwhelming majority of production nomination-pool deployments), the storage item backing this call is explicitly documented as the *planned*, not active, era: [2](#0-1) 

By contrast, the newer `pallet-staking-async` backend was patched to genuinely return the active era: [3](#0-2) 

The prdoc for that patch, `pr_10986` ("[Pool] Use active era for withdrawals... Current Era should only be used for election logic"), only bumps `pallet-nomination-pools` and `pallet-staking-async` — it never touches `pallet-staking`, confirming legacy staking's `StakingInterface::current_era()` was left returning the planned era.

Nomination-pools consumes this mismatched value in two security-critical call paths:

1. `unbond()` computes the unlock target era from the (possibly-ahead) planned era: [4](#0-3) 

2. `withdraw_unbonded()` uses the same mismatched value to decide which of the member's unbonding chunks are releasable *right now*, dissolving pool points and firing `Withdrawn`/`MemberRemoved` events before the underlying staking ledger has actually released the funds: [5](#0-4) 

Because `member.withdraw_unlocked(active_era)` and the `sub_pools.with_era` dissolution are keyed by whatever "active_era" nomination-pools believes is current, and this value is silently ahead of the staking pallet's real `ActiveEra` during an ongoing election, `withdraw_unbonded` can conclude a chunk is unlockable one era earlier than the staking pallet's own ledger considers it withdrawable. The pool-side bookkeeping (`PoolMembers`, `SubPoolsStorage`) is updated and the member's points are burned/removed unconditionally, while `T::StakeAdapter::withdraw_unbonded()` call into the real staking ledger may not yet unlock the corresponding balance, since the true active era hasn't advanced. This is precisely the failure mode already documented and patched-for-existing-victims in `pr_11018`: *"points were dissolved but the held funds weren't released."* No governance/privileged action, no malicious relayer, and no off-chain assumption is required — an ordinary pool member calling the public, permissionless `unbond`/`withdraw_unbonded` extrinsics around a normal election-transition window is sufficient to trigger the mismatch.

### Impact Explanation
This falls squarely under "permanent user-fund lock" and "runtime bugs that compromise intended behavior" in the impact gate. The pool's internal accounting (`PoolMembers::unbonding_eras`, `SubPoolsStorage`) can advance and settle a withdrawal (burning points, decrementing bonded balances, emitting `Withdrawn`) out of sync with the actual staking ledger's unlock state, since it relies on a value that is documented to be the active era but is, for the still-default legacy staking backend, the planned era. The prior real-world incident required a bespoke one-time on-chain migration to unlock a single victim's funds — evidence that this is not theoretical impact but a previously realized fund-lock bug whose root cause (the wrong era source in the adapter) has not been closed for the legacy backend.

### Likelihood Explanation
Any nomination-pool member using an `unbond`/`withdraw_unbonded` call that happens to fall while `CurrentEra > ActiveEra` (i.e., during the multi-block window between an election being triggered and the era actually rotating, which occurs every era on legacy `pallet-staking`) is exposed. No special privileges, front-running, or malicious actors are needed — this is a naturally recurring timing window in ordinary block production.

### Recommendation
Apply the same fix used for `pallet-staking-async`'s `StakingInterface::current_era()` to legacy `pallet-staking`'s implementation (or provide a distinct `active_era()` method that nomination-pools' adapter is required to use), so `unbond()`'s `unbond_era` computation and `withdraw_unbonded()`'s `member.withdraw_unlocked(active_era)` check are always keyed off the genuinely active era, matching the actual state of the underlying staking ledger's unlocking chunks. Add an integrity/try-state check asserting that `T::StakeAdapter::current_era()` never exceeds the true active era seen by the staking backend used in a given runtime.

### Proof of Concept
1. Deploy `pallet-nomination-pools` with `T::StakeAdapter` backed by legacy `pallet-staking` (the common production configuration).
2. A pool member calls `unbond()` while an election is in progress, i.e., `CurrentEra == ActiveEra + 1` (this state exists for multiple blocks every era under normal operation) — see `substrate/frame/staking/src/pallet/mod.rs:494-499` for the documented semantics of `CurrentEra`.
3. `unbond_era` is computed as `bonding_duration + current_era()` where `current_era()` returns the planned (ahead-by-one) era (`substrate/frame/nomination-pools/src/lib.rs:2290-2291`), placing the member's unlock bucket one era earlier than the era at which the real staking ledger will actually unlock the stake.
4. Once `bonding_duration` eras have passed by nomination-pools' reckoning (but the staking ledger, tracking the real active era, is still one era behind), the member calls `withdraw_unbonded()`. `active_era = T::StakeAdapter::current_era()` (`substrate/frame/nomination-pools/src/lib.rs:2410`) again yields the ahead-of-real value, so `member.withdraw_unlocked(active_era)` reports the chunk as unlockable and nomination-pools dissolves the sub-pool points and emits `Withdrawn`/`MemberRemoved`, while the underlying `T::StakeAdapter::withdraw_unbonded()` call (line 2443) may not yet release equivalent value from the real staking ledger because its own unlocking-chunk logic is keyed to the true active era.
5. Result: the member's pool-side balance/points are gone (event fired, member possibly removed), but the corresponding value was not actually freed from the staking ledger into the pool's transferable balance — reproducing the exact "points dissolved but held funds not released" trapped-balance condition that previously required the one-time migration in `pr_11018` to remediate.
