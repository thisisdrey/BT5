## Title
Unprivileged front-running of purchase payouts via public `vested_transfer` permanently locks user's crowdsale funds - (File: `polkadot/runtime/common/src/purchase/mod.rs`)

### Summary
The `pallet_purchase::payout` extrinsic requires that the target account have **no existing vesting schedule** before it will pay out and (optionally) apply a new vesting schedule for the locked portion of a DOT purchase. However, `pallet_vesting::vested_transfer` is a public, unprivileged, signed extrinsic that anyone can call against **any** target account. An attacker can call `vested_transfer` with a minimal amount targeting a known purchase participant's address, creating a vesting schedule there. When the trusted `PaymentAccount` later calls `Purchase::payout` for that victim, the call permanently fails with `Error::VestingScheduleExists`, locking the user's already-approved DOT purchase from ever being delivered through the normal flow. This is the same class of bug as the reported `FuelToken.sol` issue: a delivery/settlement function assumes a pre-condition (`no existing state`) that an unrelated, uncontrolled external actor can violate before settlement occurs.

### Finding Description
`payout` in `polkadot/runtime/common/src/purchase/mod.rs` enforces: [1](#0-0) 

```rust
pub fn payout(origin: OriginFor<T>, who: T::AccountId) -> DispatchResult {
    let payment_account = ensure_signed(origin)?;
    let test_against = PaymentAccount::<T>::get().ok_or(DispatchError::BadOrigin)?;
    ensure!(payment_account == test_against, DispatchError::BadOrigin);

    // Account should not have a vesting schedule.
    ensure!(
        T::VestingSchedule::vesting_balance(&who).is_none(),
        Error::<T>::VestingScheduleExists
    );
```

This same "must have zero prior state" pattern is also used at account-creation time: [2](#0-1) 

The precondition is that `who` has no vesting schedule at the moment `payout` executes (a privileged call, restricted to the configured `PaymentAccount`). But `T::VestingSchedule::vesting_balance` reads shared, globally-writable pallet-vesting storage that **any signed account** can mutate against **any target**, via the public `vested_transfer` extrinsic: [3](#0-2) 

```rust
pub fn vested_transfer(
    origin: OriginFor<T>,
    target: AccountIdLookupOf<T>,
    schedule: VestingInfo<BalanceOf<T>, BlockNumberFor<T>>,
) -> DispatchResult {
    let transactor = ensure_signed(origin)?;
    let target = T::Lookup::lookup(target)?;
    Self::do_vested_transfer(&transactor, &target, schedule)
}
```

`do_vested_transfer` only requires the schedule to meet `MinVestedTransfer` and be well-formed — it has no relationship to, or awareness of, the purchase pallet's assumptions: [4](#0-3) 

Because `Accounts` storage in the purchase pallet (and hence purchaser identities/addresses) is publicly readable on-chain (it is a `StorageMap` populated by `create_account`/`update_validity_status`), any address that has been validated for a purchase (`ValidLow`/`ValidHigh`) is a known, public target. An attacker only needs to send that address one minimal `vested_transfer` (amount ≥ `MinVestedTransfer`) before the `PaymentAccount` executes `payout`. Once a vesting schedule exists for the victim, every subsequent `payout(who)` call fails deterministically with `VestingScheduleExists`, and nothing in the purchase pallet clears or works around an externally-created vesting schedule — recovery would require a separate root-only `force_remove_vesting_schedule` call, which is outside of the normal purchase flow and not something an ordinary participant or the `PaymentAccount` operator can trigger themselves.

This is structurally identical to the reported `FuelToken.deliverPresaleFuelBalance` bug: a delivery function assumes "the receiver's relevant state is untouched," but an entity outside that function's control (a later dispatch, or here, any arbitrary unprivileged caller) can invalidate that assumption before delivery executes, permanently breaking one specific batch/account's settlement.

### Impact Explanation
This maps to "permanent user-fund lock" from the impact gate: an unprivileged, non-admin/non-validator attacker can grief any known purchase participant, indefinitely preventing their approved token purchase from being paid out through the `payout` entrypoint. Because purchase processing is presumably done in batches by the `PaymentAccount` operator (matching the original report's batching concern), an attacker can target many known purchaser addresses at low cost (only bounded by `MinVestedTransfer` and transaction fees), degrading or completely stalling the payout process for affected accounts until a privileged, out-of-band remediation (root `force_remove_vesting_schedule`) is performed.

### Likelihood Explanation
Likelihood is high: `vested_transfer` is a completely public, unprivileged extrinsic; the target account addresses are visible on-chain via `Accounts` storage entries created by `create_account`/`update_validity_status`; and the attack requires no special timing beyond front-running the eventual `payout` call, no validator/collator/relayer control, and no admin/governance action — precisely the class of vector the impact gate calls for.

### Recommendation
Do not treat "no vesting schedule" as a hard precondition for `payout`. Instead:
- Ignore or supersede any pre-existing vesting schedule not created by the purchase pallet itself (e.g., merge/overwrite deterministically), or
- Track whether the locked-balance vesting schedule was already applied via pallet-purchase's own storage flag rather than relying on the mutable, externally-writable global vesting balance check, or
- If a vesting schedule already exists, still transfer the free portion and defer/lock the vested portion in a way that doesn't cause the whole `payout` extrinsic to permanently fail.

### Proof of Concept
1. Validity origin creates and validates purchaser account `Alice` (`create_account`, `update_validity_status` to `ValidHigh`), then `update_balance` sets her `locked_balance` > 0.
2. Before `PaymentAccount` calls `payout(Alice)`, attacker `Mallory` (any signed account) calls `pallet_vesting::vested_transfer(target = Alice, schedule = { locked: MinVestedTransfer, per_block: 1, starting_block: current })`. This succeeds unconditionally per `do_vested_transfer`/`can_add_vesting_schedule`.
3. `PaymentAccount` calls `Purchase::payout(Alice)`. The check `ensure!(T::VestingSchedule::vesting_balance(&who).is_none(), Error::<T>::VestingScheduleExists)` now fails (test file confirms this exact failure mode already exists for legitimate pre-existing schedules): [5](#0-4) 
4. Every future retry of `payout(Alice)` fails identically until a root-only `force_remove_vesting_schedule` is executed against Mallory's injected schedule — something outside the normal purchase-flow operators' control.

	// Execute a vested transfer from `source` to `target` with the given `schedule`.
	fn do_vested_transfer(
		source: &T::AccountId,
		target: &T::AccountId,
		schedule: VestingInfo<BalanceOf<T>, BlockNumberFor<T>>,
	) -> DispatchResult {
		// Validate user inputs.
		ensure!(schedule.locked() >= T::MinVestedTransfer::get(), Error::<T>::AmountLow);
		if !schedule.is_valid() {
			return Err(Error::<T>::InvalidScheduleParams.into());
		};

		// Check we can add to this account prior to any storage writes.
		Self::can_add_vesting_schedule(
			target,
			schedule.locked(),
			schedule.per_block(),
			schedule.starting_block(),
		)?;

		T::Currency::transfer(source, target, schedule.locked(), ExistenceRequirement::AllowDeath)?;

		// We can't let this fail because the currency transfer has already happened.
		// Must be successful as it has been checked before.
		// Better to return error on failure anyway.
		let res = Self::add_vesting_schedule(
			target,
			schedule.locked(),
			schedule.per_block(),
			schedule.starting_block(),
		);
		debug_assert!(res.is_ok(), "Failed to add a schedule when we had to succeed.");

		Ok(())
	}
