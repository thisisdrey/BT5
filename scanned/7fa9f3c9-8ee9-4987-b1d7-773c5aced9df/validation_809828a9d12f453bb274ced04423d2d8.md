## Title
Single global `ExpiresIn` staleness window applied uniformly to all Oracle keys allows stale-price consumption for volatile feeds - (File: `substrate/frame/honzon/oracle/src/default_combine_data.rs`)

## Summary
`pallet-oracle`'s `DefaultCombineData` implements freshness filtering with one constant `ExpiresIn` duration shared by every `OracleKey`, exactly mirroring the reported `ChainLinkDataConsumer` bug where a single heartbeat is reused across price feeds with very different volatility/refresh characteristics.

## Finding Description
`DefaultCombineData::combine_data` filters raw operator submissions for staleness using a single type-level constant `ExpiresIn: Get<MomentOf<T, I>>`: [1](#0-0) 

This filter is applied identically for *every* `OracleKey` value combined by the pallet — there is no per-key/per-feed staleness parameter anywhere in the `Config` trait: [2](#0-1) 

In the concrete runtime wiring, this is instantiated with one fixed constant (`ConstU64<3600>`, one hour) applied to the entire `OracleKey = u32` keyspace, meaning every distinct asset/currency-pair feed identified by that key shares the same one-hour freshness tolerance regardless of what asset it represents: [3](#0-2) 

This is structurally identical to the reported issue: a stablecoin-style feed (long acceptable heartbeat) and a volatile-asset feed (short required heartbeat) are forced to share one expiry window. Setting `ExpiresIn` loosely enough to keep low-volatility feeds usable (e.g. an hour) means volatile-asset feeds can be treated as "fresh" and combined into `Values` up to that same duration after their last real update, even though a correct heartbeat for that asset should be far shorter. Conversely, tightening `ExpiresIn` to protect the volatile asset would cause frequent `combined()` failures (returning `prev_value` or `None`) for slow-moving feeds, exactly the "frequent reverts or stale prices" trade-off called out in the report and its referenced Tapioca finding.

Any downstream consumer of the oracle via the `DataProvider`/`DataProviderExtended` traits inherits this single global staleness assumption with no way to distinguish per-key risk: [4](#0-3) 

## Impact Explanation
Any pallet built to consume `pallet-oracle` prices for financial decisions (mint/redeem pricing, liquidation thresholds, collateral valuation) receives a `TimestampedValue` that is only checked against one pallet-wide staleness bound, not one appropriate to the specific asset's volatility. This compromises the intended "freshness" invariant of the data feed for at least one class of assets in the keyspace, allowing a consumer contract/pallet to act on a price up to `ExpiresIn` old for an asset that should require a much shorter window — a runtime bug that compromises intended behavior of any price-dependent logic built on top of this pallet.

## Likelihood Explanation
This is a structural design flaw, not a configuration mistake by an admin: `DefaultCombineData<T, MinimumCount, ExpiresIn, I>` provides no mechanism to differentiate `ExpiresIn` by `OracleKey` at all, so any runtime that feeds multiple heterogeneous assets through a single `pallet-oracle` instance (as the kitchensink runtime does with `OracleKey = u32` covering arbitrary asset ids) is inherently exposed. No malicious peer, validator, or governance action is required — the flaw is triggered purely by normal operation across multiple feeds with different natural refresh cadences.

## Recommendation
Change `CombineData`/`DefaultCombineData` (or the `Config` trait) to accept a per-`OracleKey` expiry lookup (e.g. `ExpiresIn: Get<Option<MomentOf<T,I>>>` keyed by `OracleKey`, or a `Convert<OracleKey, MomentOf<T,I>>`-style trait) rather than a single pallet-wide constant, so each feed can specify its own appropriate staleness bound.

## Proof of Concept
1. Runtime wires `pallet-oracle` with `OracleKey = u32` shared across a stable asset (e.g. key `1` = USDC-like, safe heartbeat ~24h) and a volatile asset (key `2` = a crypto asset, needing ~1h heartbeat), using `DefaultCombineData<Runtime, ConstU32<5>, ConstU64<3600>>` as in `substrate/bin/node/runtime/src/lib.rs` lines 3152-3165.
2. Oracle operators feed key `2` at `t=0`; no further updates occur for key `2` for 59 minutes while operators keep updating key `1` normally.
3. At `t=59min`, `combine_data` for key `2` still returns the value from `t=0` as non-expired (`timestamp + 3600 > now`), because the shared `ExpiresIn=3600` was tuned for key `1`'s acceptable staleness, not key `2`'s.
4. Any consumer pallet reading `pallet_oracle::Pallet::<Runtime>::get(&2)` receives a price that is ~59 minutes stale for a volatile asset, which is unsafe for that asset class but indistinguishable from a fresh read since the pallet enforces only one global expiry.
