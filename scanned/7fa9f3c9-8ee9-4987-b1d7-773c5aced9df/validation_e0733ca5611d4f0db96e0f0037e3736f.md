### Title
Pool reserves are read from live account balance, enabling a first-LP donation/inflation attack that DOSes `pallet-asset-conversion` liquidity provision - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
The reported bug's core invariant break is: a rounding-induced zero (or near-zero) pool invariant lets the first liquidity provider manipulate the pool's reserve accounting so that later depositors are rounded to zero shares, while the attacker can drain or lock the disproportionate reserve. `pallet-asset-conversion` reproduces the structural precondition for this class of attack: pool "reserves" are not tracked as pallet-internal state, they are read live from the pool's sovereign account balance via `Self::get_balance`, which any unprivileged account can inflate by directly transferring tokens to the pool account outside of `add_liquidity`.

### Finding Description
`do_add_liquidity` computes reserves directly from the live balance of the pool's sovereign account: [1](#0-0) 

For the very first deposit into a pool (`total_supply.is_zero()`), the LP token amount minted is `sqrt(amount1*amount2) - MintMinLiquidity`: [2](#0-1) 

and this is the only invariant guard applied for the first LP: [3](#0-2) 

For subsequent deposits, the LP share is computed as `min(amount1 * total_supply / reserve1, amount2 * total_supply / reserve2)`: [4](#0-3) 

Because `reserve1`/`reserve2` are just the pool account's current token balances (not a value the pallet tracks and reconciles against LP-token issuance), an attacker who is the pool's first LP can, after minting a minimal amount of LP tokens, directly `transfer` (via `pallet-assets`/`pallet-balances`, entirely outside the `AssetConversion` pallet) a very large amount of `asset1`/`asset2` straight into the pool's sovereign account. This inflates `reserve1`/`reserve2` far beyond what `total_supply` represents, without minting any new LP tokens for the donation.

Once this donation happens:
- Any honest user calling `add_liquidity` afterward gets `side1`/`side2` rounded down toward zero (`mul_div` truncates), causing `ensure!(lp_token_amount > T::MintMinLiquidity::get(), Error::<T>::InsufficientLiquidityMinted)` to fail (`lib.rs:874-877`), reverting their liquidity-provision transaction — a public-entrypoint denial of service on pool participation.
- The attacker, holding effectively all outstanding LP tokens, can call `remove_liquidity` and redeem `amount1 = lp_redeem_amount * reserve1 / total_supply` (`lib.rs:919-920`), which now includes the donated funds, letting them reclaim essentially the whole pool balance (including any assets that manage to land in the pool account, e.g., via other partially-completed operations or the setup-fee flow) disproportionate to their actual minted share.

The existing guards — `MintMinLiquidity` on the zero-supply mint and the `lp_token_amount > MintMinLiquidity` check on subsequent mints — only bound the LP-token rounding at the moment of minting; they do not prevent or detect that the *reserve* itself was inflated out-of-band relative to `total_supply`. There is no reconciliation between `Assets` balances of the pool account and the LP token issuance, unlike designs that maintain reserves as pallet storage updated only through `add_liquidity`/`swap`/`remove_liquidity`.

### Impact Explanation
This is a public, unprivileged-entrypoint issue reachable by any account holding a negligible amount of the pool's assets (the "first LP DOS" impact category): it can (a) permanently block other users from providing liquidity to a freshly created pool (denial of service on a core AssetConversion function used broadly across Asset Hub for XCM fee-swaps, as seen in the runtime integration flows), and (b) let the attacker walk away with a disproportionate share of subsequently pool-held funds relative to their own minted LP tokens, violating the "conserve value / settle exactly once to rightful beneficiary" requirement for asset accounting pallets.

### Likelihood Explanation
`create_pool` and `add_liquidity` are unauthenticated, ordinary signed extrinsics; anyone can create a new pool and be its first LP. Directly transferring assets into an arbitrary account (the deterministically-derived pool sovereign account, computable off-chain via `PoolLocator`) is a routine, unprivileged `Balances`/`Assets` operation requiring no special permissions, malicious validator/collator, or governance action — matching the "unprivileged attacker" requirement of the impact gate.

### Recommendation
Track pool reserves as pallet-internal storage that is updated only by `AssetConversion` extrinsics (`add_liquidity`, `remove_liquidity`, swaps), rather than deriving reserves from the live, externally-transferable balance of the pool account. Alternatively (or additionally), enforce a minimum absolute reserve/`total_supply` ratio bound and/or "skim/sync" semantics so that unaccounted-for balance deltas cannot be attributed as reserve growth for share-price purposes, and reject `add_liquidity`/`remove_liquidity` computations when the balance-derived reserve diverges from the pallet's tracked reserve.

### Proof of Concept
1. Attacker calls `create_pool(asset1, asset2)`, then `add_liquidity` with amounts just above `MintMinLiquidity + ED`, e.g. `amount1 = amount2 = 1_000`, becoming sole LP with a small `total_supply` (per `calc_lp_amount_for_zero_supply`, `substrate/frame/asset-conversion/src/lib.rs:1353-1368`).
2. Attacker calls `pallet_assets::transfer`/`pallet_balances::transfer` directly to the pool's sovereign account (computed via `PoolLocator::address`), sending a very large amount of `asset1` and `asset2` (e.g., `1_000_000_000`), bypassing `add_liquidity` entirely — this is legal because the pool account is an ordinary `AccountId`.
3. A victim calls `add_liquidity` with a normal deposit amount; `reserve1`/`reserve2` read via `Self::get_balance` (`lib.rs:813-814`) now reflect the inflated balances, so `side1`/`side2` in `lib.rs:869-871` round down to `0`, and `ensure!(lp_token_amount > T::MintMinLiquidity::get(), ...)` at `lib.rs:874-877` reverts the victim's transaction — DoS confirmed.
4. Attacker calls `remove_liquidity` burning their entire (small) LP balance; `amount1 = lp_redeem_amount * reserve1 / total_supply` at `lib.rs:919-920` returns close to the entire inflated reserve back to the attacker, letting them recapture essentially all pool-held value disproportionate to their genuine deposit.

		pub(super) fn calc_lp_amount_for_zero_supply(
			amount1: &T::Balance,
			amount2: &T::Balance,
		) -> Result<T::Balance, Error<T>> {
			let amount1 = T::HigherPrecisionBalance::from(*amount1);
			let amount2 = T::HigherPrecisionBalance::from(*amount2);

			let result = amount1
				.checked_mul(&amount2)
				.ok_or(Error::<T>::Overflow)?
				.integer_sqrt()
				.checked_sub(&T::MintMinLiquidity::get().into())
				.ok_or(Error::<T>::InsufficientLiquidityMinted)?;

			result.try_into().map_err(|_| Error::<T>::Overflow)
		}
