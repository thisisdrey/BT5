Preconditions: attacker deposits real FT into Verifier with `msg` selecting `DepositAction::Notify(notify)` where `notify.msg` names attacker's own malicious `mt_on_transfer`-implementing contract as `receiver_id`. Call sequence: `ft_on_transfer` deposits amount to `receiver_id` (attacker-controlled), calls `notify_on_transfer` -> attacker's `mt_on_transfer` returns crafted `used`/refund array -> `.then(ft_resolve_deposit)` -> `resolve_deposit_internal` computes `refund_amount = requested_refund.min(*deposited).min(balance_left)`. Binding: `refund_amount <= balance_left` (the receiver's ACTUAL remaining balance at resolve time) — verify the `.min(balance_left)` clamp correctly prevents the attacker from getting refunded (i.e., double-credited elsewhere) more than what is actually still in their account after any intents executed in between. Impact: Critical if `balance_left` is stale/read before other concurrent mutations, allowing refund beyond real balance. Proof idea: cargo test where attacker's `mt_on_transfer` callback ALSO triggers `execute_intents` to move part of the freshly-deposited balance elsewhere before returning a large forged refund request in its own return value, then assert `resolve_deposit_internal`'s clamp uses the POST-move balance, not the pre-move one, so `refund_amount` never exceeds `token_balances[receiver_id][token_id]` at resolve time.
