Target: `Account::commit_nonce` reached only via `self.accounts.get_or_create(...).get_mut().ok_or(DefuseError::AccountLocked(...))?`. Attacker action: submit a `MultiPayload` for an account that is concurrently being locked within the same batch (e.g., a prior intent in the batch locks the account, e.g. via `Lock::lock`), then a later intent in the batch attempts `commit_nonce` for that now-locked account. Preconditions: batch contains an intent that locks `signer_id`'s account before the nonce-committing intent executes. Call sequence: `get_or_create(...).get_mut()` returns `None` because `Lock::get_mut` returns `None` when locked -> `commit_nonce` returns `Err(AccountLocked)` -> the whole `execute_signed_intent` call fails and is NOT committed. Binding: an intent must either fully commit its nonce AND its balance effects, or commit NEITHER (atomicity) - partial state where nonce is marked used but balance change reverts (or vice versa) breaks CONSERVATION. Scoped impact: Critical if the nonce bit is set despite the surrounding transaction/batch aborting, permanently burning a legitimate nonce without ever moving funds (funds frozen) or, worse, moving funds without a persisted nonce commit (replay window open). Proof idea: cargo test crafting a batch that locks an account then submits a nonce-bearing intent for it, asserting the entire batch call returns an error and that NEITHER the nonce bit NOR the balance changed (verify via `is_nonce_used` and `token_balances` before/after).
