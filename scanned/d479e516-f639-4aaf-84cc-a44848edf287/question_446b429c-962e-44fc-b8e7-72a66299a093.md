Target: `decode_http_response` status-code handling in libsigner/src/http.rs. Attacker action: a malicious node/event-source the signer's session code talks to (`run_http_request` in `session.rs`) replies with a non-200 status and a body that also contains a second, smuggled HTTP response appended after `body_offset`. Preconditions: attacker controls the node/relay endpoint the `StackerDBSession` connects to (in-scope: connection is over TCP the attacker can influence as a rogue 'node' the session dials, per the RPCError::HttpError path). Call sequence: `run_http_request` -> `sock.read_to_end(&mut buf)` reads the FULL stream -> `decode_http_response(&buf)` only inspects headers up to first `body_offset`, then `decode_http_body(&headers, &buf[body_offset..])` treats everything after as one body without validating `Content-Length` boundaries against a following, smuggled response. Equality/fault: bytes treated as 'the body' (`buf[body_offset..]`) must equal exactly `Content-Length` bytes (or the fully chunk-terminated body), not the entire remaining socket buffer; the code trusts `buf.len()` as body length only, no `Content-Length` cross-check present. Impact: High - a response-smuggling-adjacent condition where a compromised/rogue peer can prepend/append extra HTTP framing that gets concatenated into what the signer treats as a single JSON/StackerDB body, potentially confusing the caller into parsing attacker-chosen trailing bytes as message content. Proof idea: unit test feeding `decode_http_response` a buffer containing one complete `200 OK` response followed immediately by a second smuggled HTTP response, and asserting the returned body is bounded to the declared `Content-Length` of the first response, not the whole buffer.
