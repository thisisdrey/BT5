### Title
Unpermissioned `vested_transfer` allows an attacker to fill a victim's `MaxVestingSchedules` slots and permanently block legitimate vested transfers - (File: `substrate/frame/vesting/src/lib.rs`)

### Summary
`pallet_vesting::vested_transfer` is a public, unprivileged extrinsic that lets **any signed account** create a new vesting schedule on behalf of **any other account** (`target`), as long as the locked amount is at least `MinVestedTransfer`. Each account has a hard-capped, bounded number of vesting schedules (`MAX_VESTING_SCHEDULES`). An attacker can repeatedly call `vested_transfer` against a victim with the minimum allowed amount to fill up the victim's schedule slots. Once the cap is reached, any further attempt — by the victim themselves or by a legitimate third party (e.g., an exchange, vesting service, or the runtime's own `force_vested_transfer` flow) — to create a new vesting schedule for that victim fails with `Error::AtMaxVestingSchedules`, and this cannot be resolved until the attacker's schedules fully vest. This is structurally identical to the reported `create_lock_for()` DoS: a public "create X on behalf of Y" entrypoint with a low minimum cost and a bounded per-account slot count.

### Finding Description
`vested_transfer` is dispatched by any signed origin and lets the caller choose an arbitrary `target`: [1](#0-0) 

It delegates to `do_vested_transfer`, which only checks that `schedule.locked() >= MinVestedTransfer` and that the schedule is internally valid, then calls `can_add_vesting_schedule` (a slot-availability check) before performing the currency transfer and inserting the schedule: [2](#0-1) 

The per-account slot limit is enforced via `can_add_vesting_schedule` / `add_vesting_schedule`, both of which push into a `BoundedVec<..., MaxVestingSchedulesGet<T>>` and return `Error::AtMaxVestingSchedules` once the bound is reached: [3](#0-2) [4](#0-3) 

The storage itself is a bounded map keyed by the *target* account, not the caller: [5](#0-4) 

There is no check that the `target` consents to receiving the schedule, and no cap on how many *distinct callers* may create schedules for the same target — only a global per-account cap that any external caller can exhaust. This mirrors the reported bug exactly: `create_lock_for(_value, _lock_duration, _to)` let an attacker lock `1 wei` for `MAXTIME` on behalf of `_to` up to `MAX_DELEGATES` times, permanently DoS-ing the victim's ability to create new locks until expiry. Here, an attacker can call `vested_transfer(target, MinVestedTransfer, per_block, starting_block)` repeatedly (with `starting_block` set far in the future or a schedule with a very long vesting duration) to consume all of the victim's `MAX_VESTING_SCHEDULES` slots at the minimum required cost.

Existing guards do not stop this: `MinVestedTransfer` only guards against a *dust* amount, not against the attack being cheap relative to `MAX_VESTING_SCHEDULES` occurrences; and there is no `target == origin` or allow-list restriction on who may create a schedule for whom. The pallet's own test suite confirms the resulting hard failure state once schedules are maxed out: [6](#0-5) 

### Impact Explanation
Once an attacker fills a victim's vesting-schedule slots, any subsequent `vested_transfer` targeting that account (from the victim's employer, an exchange doing payroll/vesting, a DEX vesting integration, or the runtime's own `VestedTransfer`/`VestingSchedule` trait consumers) fails with `AtMaxVestingSchedules` until the attacker's schedules fully vest — which the attacker controls by choosing the vesting duration/starting block. This is a public, low-cost, unprivileged denial-of-service against a specific account's ability to receive vesting-based payouts, consistent with "public underpriced work that degrades... processing" and "permanent user-fund or bridge-state lock"-style impacts, scoped to any account on a Substrate chain that includes `pallet-vesting` (used broadly, including in `substrate/bin/node/runtime`, `polkadot/runtime/westend`, `polkadot/runtime/rococo`, `cumulus/parachains/runtimes/assets/asset-hub-westend`).

### Likelihood Explanation
The attack requires only a signed account with enough balance for `MAX_VESTING_SCHEDULES × MinVestedTransfer` (a per-account constant, not adjustable by governance mid-attack) plus transaction fees — no privileged origin, no malicious validator/collator, and no governance action is needed, satisfying the "unprivileged attacker" requirement. The number of calls needed equals `MAX_VESTING_SCHEDULES`, a small bounded constant, making this trivially automatable in a single block or a few blocks.

### Recommendation
- Require `target == origin` (i.e., only allow self-directed vesting schedule creation) for the permissionless `vested_transfer`, and move "on behalf of another account" creation behind `force_vested_transfer` (root-only) or an explicit opt-in/allow-list mechanism.
- Alternatively, track and cap schedules-created-by-third-party separately from self-created schedules, or require the target to pre-authorize incoming vesting schedules from unrelated senders.
- Consider making `MinVestedTransfer` scale so that filling `MAX_VESTING_SCHEDULES` is prohibitively expensive relative to the intended use case, and/or allow the target (or root) to evict/merge schedules created by non-consenting senders before they naturally vest.

### Proof of Concept
Analogous to the reported POC, using the existing pallet test harness (`substrate/frame/vesting/src/tests.rs`), an attacker (account `3`) can exhaust account `4`'s vesting slots:
```rust
#[test]
fn dos_via_vested_transfer_fills_target_slots() {
    ExtBuilder::default().existential_deposit(ED).build().execute_with(|| {
        let max_schedules = <Test as Config>::MAX_VESTING_SCHEDULES;
        let sched = VestingInfo::new(<Test as Config>::MinVestedTransfer::get(), 1, 10);

        // Attacker (account 13) fills victim (account 4)'s vesting schedule slots
        // using only the minimum allowed amount per call.
        for _ in 0..max_schedules {
            assert_ok!(Vesting::vested_transfer(Some(13).into(), 4, sched));
        }

        // A legitimate vested transfer to account 4 (e.g. payroll/vesting payout)
        // now permanently fails until the attacker's schedules fully vest.
        assert_noop!(
            Vesting::vested_transfer(Some(3).into(), 4, sched),
            Error::<Test>::AtMaxVestingSchedules,
        );
    });
}
```
This matches the existing `vested_transfer_allows_max_schedules` test's observed behavior [6](#0-5) , demonstrating that account `4` cannot receive any further vesting schedule from a legitimate third party until the attacker-created schedules expire.

```rust
	// Execute a vested transfer from `source` to `target` with the given `schedule`.
	fn do_vested_transfer(
		source: &T::AccountId,
		target: &T::AccountId,
		schedule: VestingInfo<BalanceOf<T>, BlockNumberFor<T>>,
	) -> DispatchResult {
		// Validate user inputs.
		ensure!(schedule.locked() >= T::MinVestedTransfer::get(), Error::<T>::AmountLow);
		if !schedule.is_valid() {
			return Err(Error::<T>::InvalidScheduleParams.into());
		};

		// Check we can add to this account prior to any storage writes.
		Self::can_add_vesting_schedule(
			target,
			schedule.locked(),
			schedule.per_block(),
			schedule.starting_block(),
		)?;

		T::Currency::transfer(source, target, schedule.locked(), ExistenceRequirement::AllowDeath)?;

		// We can't let this fail because the currency transfer has already happened.
		// Must be successful as it has been checked before.
		// Better to return error on failure anyway.
		let res = Self::add_vesting_schedule(
			target,
			schedule.locked(),
			schedule.per_block(),
			schedule.starting_block(),
		);
		debug_assert!(res.is_ok(), "Failed to add a schedule when we had to succeed.");

		Ok(())
	}
```

```rust
	fn add_vesting_schedule(
		who: &T::AccountId,
		locked: BalanceOf<T>,
		per_block: BalanceOf<T>,
		starting_block: BlockNumberFor<T>,
	) -> DispatchResult {
		if locked.is_zero() {
			return Ok(());
		}

		let vesting_schedule = VestingInfo::new(locked, per_block, starting_block);
		// Check for `per_block` or `locked` of 0.
		if !vesting_schedule.is_valid() {
			return Err(Error::<T>::InvalidScheduleParams.into());
		};

		let mut schedules = Vesting::<T>::get(who).unwrap_or_default();

		// NOTE: we must push the new schedule so that `exec_action`
		// will give the correct new locked amount.
		ensure!(schedules.try_push(vesting_schedule).is_ok(), Error::<T>::AtMaxVestingSchedules);

		debug_assert!(schedules.len() > 0, "schedules cannot be empty after insertion");
		let schedule_index = schedules.len() - 1;
		Self::deposit_event(Event::<T>::VestingCreated {
			account: who.clone(),
			schedule_index: schedule_index as u32,
		});

		let (schedules, locked_now) =
			Self::exec_action(schedules.to_vec(), VestingAction::Passive)?;

		Self::write_vesting(who, schedules)?;
		Self::write_lock(who, locked_now);

		Ok(())
	}
```

```rust
	/// Ensure we can call `add_vesting_schedule` without error. This should always
	/// be called prior to `add_vesting_schedule`.
	fn can_add_vesting_schedule(
		who: &T::AccountId,
		locked: BalanceOf<T>,
		per_block: BalanceOf<T>,
		starting_block: BlockNumberFor<T>,
	) -> DispatchResult {
		// Check for `per_block` or `locked` of 0.
		if !VestingInfo::new(locked, per_block, starting_block).is_valid() {
			return Err(Error::<T>::InvalidScheduleParams.into());
		}

		ensure!(
			(Vesting::<T>::decode_len(who).unwrap_or_default() as u32) < T::MAX_VESTING_SCHEDULES,
			Error::<T>::AtMaxVestingSchedules
		);

		Ok(())
	}
```

```rust
#[test]
fn vested_transfer_allows_max_schedules() {
	ExtBuilder::default().existential_deposit(ED).build().execute_with(|| {
		let mut user_4_free_balance = Balances::free_balance(&4);
		let max_schedules = <Test as Config>::MAX_VESTING_SCHEDULES;
		let sched = VestingInfo::new(
			<Test as Config>::MinVestedTransfer::get(),
			1, // Vest over 2 * 256 blocks.
			10,
		);

		// Add max amount schedules to user 4.
		for _ in 0..max_schedules {
			assert_ok!(Vesting::vested_transfer(Some(13).into(), 4, sched));
		}

		// The schedules count towards vesting balance
		let transferred_amount = <Test as Config>::MinVestedTransfer::get() * max_schedules as u64;
		assert_eq!(Vesting::vesting_balance(&4), Some(transferred_amount));
		// and free balance.
		user_4_free_balance += transferred_amount;
		assert_eq!(Balances::free_balance(&4), user_4_free_balance);

		// Cannot insert a 4th vesting schedule when `MaxVestingSchedules` === 3,
		assert_noop!(
			Vesting::vested_transfer(Some(3).into(), 4, sched),
			Error::<Test>::AtMaxVestingSchedules,
		);
		// so the free balance does not change.
		assert_eq!(Balances::free_balance(&4), user_4_free_balance);

		// Account 4 has fully vested when all the schedules end,
		System::set_block_number(
			<Test as Config>::MinVestedTransfer::get() + sched.starting_block(),
		);
		assert_eq!(Vesting::vesting_balance(&4), Some(0));
		// and after unlocking its schedules are removed from storage.
		vest_and_assert_no_vesting::<Test>(4);
	});
}
```
