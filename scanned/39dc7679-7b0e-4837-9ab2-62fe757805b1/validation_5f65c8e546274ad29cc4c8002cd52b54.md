### Title
Fixed-point decimal truncation zeroes out relayer reward in Snowbridge `calculate_fee` - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
`Pallet::calculate_fee` computes the DOT-denominated cost of relaying a message to Ethereum by converting a wei-denominated remote fee through `FixedU128` arithmetic and then truncating it down to native decimals in `convert_from_ether_decimals`. Because the final step is an integer division (`value.checked_div(denom)`), any remote fee whose value is smaller than the decimal-adjustment denominator rounds down to exactly `0`, even though every individual `PricingParameters` field is non-zero and passes `PricingParameters::validate()`. This mirrors the Basin `Stable2LUT1` finding: an approximation/interpolation step (there, LUT interpolation; here, decimal truncation) silently produces a result that diverges from the intended value for parameter ranges near the edge of the represented domain, and nothing downstream detects or rejects the degenerate output.

### Finding Description
`calculate_fee` computes:

```
RemoteFee = gas_used_at_most * fee_per_gas + reward        (wei, U256)
fee (u128) = RemoteFee.try_into()
fee = FixedU128::from_inner(fee).saturating_mul(multiplier).checked_div(&exchange_rate).into_inner()
fee = convert_from_ether_decimals(fee)
``` [1](#0-0) 

`convert_from_ether_decimals` truncates by plain integer division:
```rust
pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
    let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
    let denom = 10u128.saturating_pow(decimals);
    value.checked_div(denom).expect("divisor is non-zero; qed").into()
}
``` [2](#0-1) 

`PricingParameters::validate()` only rejects parameters that are individually zero (`exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, `multiplier`), it never checks whether the *derived* fee after the full pipeline (multiply → divide by exchange rate → truncate decimals) is non-zero: [3](#0-2) 

The codebase itself already demonstrates the exact failure mode with fully "valid" (non-zero) parameters:
```rust
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
    ...
    let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
    assert_eq!(fee.local, 698000000);
    // Though none zero pricing params the remote fee calculated here is invalid
    // which should be avoided
    assert_eq!(fee.remote, 0);
}
``` [4](#0-3) 

The computed `fee.remote` (and therefore the `reward`/`max_fee_per_gas` embedded in the committed message, per `do_process_message`) is the exact value later ABI-encoded and stored in `CommittedMessage`: [5](#0-4) 

Once the message is committed with a `reward` field of `0` (or a `max_fee_per_gas` too low to cover real Ethereum execution costs), on the Ethereum gateway side the relayer only accrues `Min(GasPrice, Message.MaxFeePerGas) * GasUsed() + Message.Reward`, as documented in the module's own fee-computation spec: [6](#0-5) 

This is the same failure class as the Basin report: a numeric approximation/conversion path that is correct for "typical" parameter magnitudes but silently collapses to a degenerate value (there: a reserve far from the target price; here: a reward of zero) once the ETH/DOT `exchange_rate`, `fee_per_gas`, or message gas cost drift into a ratio where the intermediate value becomes smaller than the truncation denominator (`10^(18-Decimals)`, e.g. `10^6` for a 12-decimal chain, `10^8` for a 10-decimal chain). No downstream check rejects committing a message whose derived economic incentive rounds to zero.

### Impact Explanation
Once a message with a zero/near-zero embedded reward and fee cap is committed and its Merkle root is included in the parachain header, the nonce advances and the message is irrevocably queued for the offchain relayer network — there is no way for the sender to resubmit or cancel it. Since relayers are economically rational actors that accrue `Message.Reward` plus gas reimbursement capped at `Message.MaxFeePerGas`, a message whose derived reward/fee is zero or insufficient to cover Ethereum gas provides no incentive to relay. This is exactly the "public underpriced work that... stalls bridge processing" impact category: work (message delivery) is priced at zero even though users paid the local DOT fee, and the message can become permanently stuck with no relayer willing to deliver it, without any admin or governance misconfiguration being the intended trigger — it results purely from normal parameter ranges (a low/legitimate `fee_per_gas`, `exchange_rate`, or small gas-cost command) passing through the flawed truncating conversion.

### Likelihood Explanation
The bug is deterministic and requires no privileged actor: it triggers whenever `gas_used_at_most * fee_per_gas + reward`, after the multiplier/exchange-rate adjustment, is numerically smaller than `10^(ETHER_DECIMALS - T::Decimals)` (e.g. `10^6` wei-equivalent units for a 12-decimal chain such as Kusama/BridgeHub-Kusama, `10^8` for a 10-decimal chain such as Polkadot). `PricingParameters::validate()` cannot catch this because it only inspects the raw input fields, not the derived output, so any governance-set (or naturally market-drifting) combination of `exchange_rate`/`fee_per_gas` that is individually valid but numerically small relative to the decimal gap reproduces the zero-fee outcome shown by the repository's own regression test.

### Recommendation
- Round up (ceiling division) instead of truncating in `convert_from_ether_decimals`, or
- After computing the final fee, explicitly reject/clamp to a protocol-defined minimum reward and fail `calculate_fee`/message submission if the derived remote fee or reward rounds to zero, rather than silently committing an under-priced message, and
- Add a post-computation invariant check (analogous to Basin's PR #137 fix narrowing the LUT step size) that asserts the derived `Fee` stays proportional to the input parameters rather than collapsing due to intermediate truncation.

### Proof of Concept
The existing repository test is a self-contained PoC of the defect:
```rust
#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
    new_tester().execute_with(|| {
        let gas_used: u64 = 250000;
        let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
            exchange_rate: FixedU128::from_rational(1, 1),
            fee_per_gas: 1_u32.into(),
            rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
            multiplier: FixedU128::from_rational(1, 1),
        };
        let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
        assert_eq!(fee.local, 698000000);
        assert_eq!(fee.remote, 0); // reward encoded in the committed message becomes 0
    });
}
``` [4](#0-3) 
All inputs pass `PricingParameters::validate()` (none are zero) [3](#0-2) , yet the resulting message's `reward`/fee fields, which are exactly what gets ABI-encoded into `CommittedMessage` and relied upon by the Ethereum-side relayer payout logic, are zero.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}
