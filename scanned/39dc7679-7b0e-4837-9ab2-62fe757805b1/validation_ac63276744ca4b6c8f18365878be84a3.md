## Analysis

The report's core broken invariant: code paths that execute during a restricted **validation phase** (where mutation is prohibited/limited by protocol convention) instead perform **state-mutating writes**, and the entity used for accounting is decoupled from strict per-call accuracy — causing usage/fee state to be corrupted or inconsistent relative to what actually gets executed.

The closest local analog is `pallet-origin-restriction`'s `RestrictOrigin` `TransactionExtension`. Per FRAME's own documented contract (`prdoc/stable2412/pr_3685.prdoc`, and the `TransactionExtension` trait docs), `validate()` "runs transaction validation logic both off-chain and on-chain, and is **non-mutating**" — mutation is supposed to happen in `prepare()`. `RestrictOrigin::validate()` in `substrate/frame/origin-restriction/src/lib.rs` violates this contract directly: [1](#0-0) 

It reads `Usages::<T>::get(&entity)`, computes a new usage value including `extrinsic_fee` for the **candidate** call, and immediately calls `Usages::<T>::insert(&entity, &usage)` — a storage write — inside `validate()`, not `prepare()`. `prepare()` afterwards only forwards the already-computed `Val` without re-deriving or re-checking anything: [2](#0-1) 

## Why this matters

`validate()` is invoked far more often, and in more contexts, than `prepare()`:
- It is called repeatedly by the transaction pool for revalidation of pending/gossiped transactions against every new best-block state, via `Executive::validate_transaction` [3](#0-2) , which is explicitly commented as being expected to have its storage changes discarded: "Changes made to storage should be discarded."
- It is also called as the first half of `validate_and_prepare`/`dispatch_transaction`, and it is called independently in `TransactionExtension` tuple compositions and pipeline wrappers (`StorageWeightReclaim`, `SkipCheckIfFeeless`, `ChargePGAS`, etc.), any of which may invoke an inner extension's `validate()` more than once relative to `prepare()`/dispatch in speculative or off-chain code paths [4](#0-3) .

Because `RestrictOrigin` performs its accounting mutation (`Usages::insert`) inside `validate()`, every speculative/off-chain re-validation of a still-pending transaction increments the tracked `Usage.used` for the entity **as a side effect of code paths that are only supposed to be read-only and discardable**. Unlike a normal on-chain `prepare()`/dispatch mutation (which only happens once, atomically, when a call actually executes), this write is exposed to the pool's "guess-and-discard" validation model — a `TransactionSource::External`/`Local` revalidation performed against non-committing state should never leave permanent effects, yet the contract of `validate()` is broken here by design of this specific extension.

This is the same class of bug reported externally: code that must behave as a pure/read-only check during the "validation" phase (in ERC-4337, enforced by opcode/storage rules for bundler compatibility; in Substrate, enforced only by documentation/convention, not by the runtime) instead performs real state writes, corrupting shared accounting state (`Usages` map values keyed by `RestrictedEntity`, not the raw origin) whenever `validate()` runs more than once per eventually-included (or never-included) extrinsic.

## Impact

- **Guarding-of-record fee/usage accounting can be desynchronized from reality**: `Usage.used` for a `RestrictedEntity` can be incremented by `validate()` calls that never lead to an actual `prepare()`/dispatch (e.g., the extrinsic is later dropped from the pool, superseded, or fails a later extension in the pipeline). Since `prepare()` performs no independent, idempotent recomputation — it simply forwards the `Val` computed in `validate()` — there is no re-validation gate to prevent using a phantom usage snapshot from a `validate()` that will never be followed by a real dispatch.
- Practically this manifests as a public, low-cost griefing/DoS vector: an attacker holding a restricted origin (or anyone able to trigger repeated revalidation of transactions from that origin, e.g., via chain reorgs/new blocks triggering pool revalidation) can cause `Usages` for that entity to appear artificially inflated relative to actual on-chain work performed, denying that entity legitimate throughput ("public underpriced work that ... stalls processing" for the accounted origin) — without needing any privileged/admin/relayer/validator role.

## Likelihood / caveats

This is a genuine deviation from the documented `TransactionExtension::validate()` contract, directly analogous in spirit to the ERC-7562 report's "side-effectful code inside a phase meant to be side-effect free." However, I was not able to fully trace, within the remaining tool budget, whether the client-side offchain revalidation path for `validate_transaction` truly executes against a discarded/ephemeral overlay in all call sites (this is asserted only by a doc-comment in `substrate/frame/executive/src/lib.rs`), nor whether `frame_executive::apply_extrinsic`'s on-chain path wraps `validate_and_prepare` in a transactional storage layer that would roll back this write if a later extension in the same pipeline fails `prepare()`. Confirming the exact persistence/rollback semantics across all pool-revalidation and multi-extension-pipeline scenarios would require deeper node-client-side tracing beyond what the indexed codebase context here supports.

### Title
`RestrictOrigin` transaction extension mutates `Usages` storage inside the non-mutating `validate()` phase, corrupting fee-usage accounting - (File: `substrate/frame/origin-restriction/src/lib.rs`)

### Summary
`RestrictOrigin::validate()` writes to `Usages::<T>` storage directly instead of deferring the mutation to `prepare()`, violating the documented "validate is non-mutating" contract of `TransactionExtension`.

### Finding Description
`TransactionExtension::validate()` is documented and relied upon across FRAME as non-mutating logic used for transaction-pool validation, gossip revalidation, and pipeline composition, with actual on-chain effects reserved for `prepare()`. `RestrictOrigin::validate()` instead performs `Usages::<T>::insert(&entity, &usage)` directly [1](#0-0) , and `prepare()` performs no independent recomputation, simply forwarding the pre-computed value [2](#0-1) .

### Impact Explanation
Any code path that invokes `validate()` without a subsequent committed `prepare()`/dispatch (transaction-pool revalidation, speculative pipeline validation) leaves a real mutation to `Usages`, desynchronizing tracked usage from actual on-chain work and enabling griefing of the restricted entity's throughput allowance.

### Likelihood Explanation
No privileged actor, relayer, or malicious node is required — any account whose origin maps to a `RestrictedEntity` (or whose pending transactions get revalidated repeatedly by ordinary pool/gossip mechanics) can trigger this path through normal transaction submission.

### Recommendation
Move the `Usages::<T>::insert` mutation out of `validate()` and into `prepare()`, keeping `validate()` purely a read/check function (compute the prospective usage, return it via `Val`, and only persist it in `prepare()`), consistent with the documented `TransactionExtension` semantics used elsewhere in FRAME (e.g., `pallet_transaction_payment`, `pallet-asset-tx-payment`, `pallet-pgas-allowance` patterns).

### Proof of Concept
1. Configure a runtime with `RestrictOrigin` in the extension pipeline for a `RestrictedEntity`.
2. Submit a signed transaction from the restricted origin; do not include it in a block (e.g., let the pool revalidate it against several new best-block states without inclusion, or construct a scenario where a later extension in the same tuple pipeline fails `prepare()`).
3. Observe `Usages::<T>::get(entity)` reflecting accumulated `used` from `validate()` invocations that never had a corresponding successful dispatch, matching the pattern demonstrated by the existing test `restricted_origin_works` [5](#0-4)  — but here triggered by repeated/never-finalized `validate()` calls instead of actually-dispatched calls.

/// cumbersome and would lead to a lot of boilerplate. Instead, transaction extensions are
/// aggregated into pipelines, which are tuples of transaction extensions. Each extension in the
/// pipeline is executed in order, and the output of each extension is aggregated and/or relayed as
/// the input to the next extension in the pipeline.
///
/// This ordered composition happens with all data types ([Val](TransactionExtension::Val),
/// [Pre](TransactionExtension::Pre) and [Implicit](TransactionExtension::Implicit)) as well as
/// all functions. There are important consequences stemming from how the composition affects the
/// meaning of the `origin` and `implication` parameters as well as the results. Whereas the
/// [prepare](TransactionExtension::prepare) and
/// [post_dispatch](TransactionExtension::post_dispatch) functions are clear in their meaning, the
/// [validate](TransactionExtension::validate) function is fairly sophisticated and warrants further
/// explanation.
///
/// Firstly, the `origin` parameter. The `origin` passed into the first item in a pipeline is simply
/// that passed into the tuple itself. It represents an authority who has authorized the implication
/// of the transaction, as of the extension it has been passed into *and any further extensions it
/// may pass though, all the way to, and including, the transaction's dispatch call itself. Each
/// following item in the pipeline is passed the origin which the previous item returned. The origin
/// returned from the final item in the pipeline is the origin which is returned by the tuple
/// itself.
///
/// This means that if a constituent extension returns a different origin to the one it was called
/// with, then (assuming no other extension changes it further) *this new origin will be used for
/// all extensions following it in the pipeline, and will be returned from the pipeline to be used
/// as the origin for the call's dispatch*. The call itself as well as all these extensions
/// following may each imply consequence for this origin. We call this the *inherited implication*.
///
/// The *inherited implication* is the cumulated on-chain effects born by whatever origin is
/// returned. It is expressed to the [validate](TransactionExtension::validate) function only as the
/// `implication` argument which implements the [Encode] trait. A transaction extension may define
/// its own implications through its own fields and the
/// [implicit](TransactionExtension::implicit) function. This is only utilized by extensions
/// which precede it in a pipeline or, if the transaction is an old-school signed transaction, the
/// underlying transaction verification logic.
///
/// **The inherited implication passed as the `implication` parameter to
/// [validate](TransactionExtension::validate) does not include the extension's inner data itself
/// nor does it include the result of the extension's `implicit` function.** If you both provide an
/// implication and rely on the implication, then you need to manually aggregate your extensions
/// implication with the aggregated implication passed in.
///
/// In the post dispatch pipeline, the actual weight of each extension is accrued in the
/// [PostDispatchInfo](PostDispatchInfoOf<Call>) of that transaction sequentially with each
/// [post_dispatch](TransactionExtension::post_dispatch) call. This means that an extension handling
/// transaction payment and refunds should be at the end of the pipeline in order to capture the
/// correct amount of weight used during the call. This is because one cannot know the actual weight
/// of an extension after post dispatch without running the post dispatch ahead of time.
