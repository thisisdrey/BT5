# [M] ADLU-2 | Latest ADL Block Updated Without ADL State Change

## Summary
Severity: Medium
Contest weight: 0.0529
Dataset id: 18201
Source: https://huggingface.co/datasets/Zaevlad/audit-findings-dataset
Type: audit-finding

## Details
The vulnerability concerns the automatic update of the latest Auto‑Deleveraging (ADL) block identifier each time the function that refreshes ADL state is invoked, regardless of whether the ADL flag is actually enabled or whether the underlying ADL state has changed. The root cause is a missing conditional guard that checks if the ADL mechanism should be active before recording the current block number as the “latest ADL block”. Because the guard is absent, any keeper or external actor that calls the state‑update routine will overwrite the stored block number even when the market is not in an ADL‑eligible condition. An attacker or even a benign keeper can therefore trigger a continuous stream of updates, causing the contract to believe that a new ADL period has just begun on every block. This prevents legitimate ADL decrease orders – which are only allowed after a specific block interval following an ADL enablement – from being accepted, as the contract’s logic always sees the “latest ADL block” as too recent. From a user’s perspective, decrease orders appear to be rejected or silently ignored, balances may remain locked, and the UI may show that no ADL‑related actions are possible even though the market is otherwise healthy. The impact is a denial‑of‑service for participants who rely on ADL decrease orders to unwind positions, potentially leading to increased liquidation risk and loss of capital. The issue manifests whenever the updateAdlState function is called – which can be on every block by an automated keeper – and the market is not currently in an ADL‑enabled state. It affects all users of the protocol who need to submit decrease orders, as well as the protocol itself because the intended risk‑mitigation mechanism is effectively disabled. The flaw was discovered during a systematic audit of the ADL workflow, where the auditor observed that the latest ADL block variable was being written unconditionally. The problem is subtle because the contract still records a block number, so there is no outright error or revert; the symptom is a silent blockage of a specific order type, which can be hard to detect without tracing the ADL state transitions. To remediate, the contract should only update the latest ADL block when the ADL condition is actually being enabled – for example by checking a shouldEnableAdl flag before writing the block number – or, if the current behaviour is intentional, the developers should add explicit documentation clarifying why the block is updated on every call and how keepers should interact with the function. In essence, the bug belongs to the class of “unconditional state mutation” or “incorrect guard condition” that leads to logical denial‑of‑service in financial smart contracts.

## Recommendation
Consider using if (shouldEnableAdl) setLatestAdlBlock(dataStore, market, isLong, Chain.currentBlockNumber()). Otherwise, if current functionality is intended, add more documentation surrounding ADL block updates.
