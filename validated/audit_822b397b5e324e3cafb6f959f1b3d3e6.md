### Title
Witness brokerage fee truncates instead of rounding up, causing systematic under-payment of witness rewards - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.payReward` computes the witness's brokerage cut from block/transaction-fee rewards using `double` arithmetic and a `(long)` cast, which truncates toward zero. Every fractional-sun remainder of the intended brokerage percentage is silently discarded and re-routed into the general voter reward pool instead of being paid to the witness, mirroring the "platform fee should round up" rounding-direction bug class from the referenced report.

### Finding Description
`payReward` is the function that splits a witness's block reward or transaction-fee reward between the witness (via its configured `brokerage` percentage) and the voter reward pool: [1](#0-0) 

```java
private void payReward(byte[] witnessAddress, long value) {
  long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
  int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
  double brokerageRate = (double) brokerage / 100;
  long brokerageAmount = (long) (brokerageRate * value);
  value -= brokerageAmount;
  delegationStore.addReward(cycle, witnessAddress, value);
  adjustAllowance(witnessAddress, brokerageAmount);
}
```

`brokerageAmount` is the witness's fee ("platform fee") for producing the block / collecting transaction fees. `(long) (brokerageRate * value)` truncates any fractional sun toward zero (floor, since both operands are non-negative). The truncated remainder is not paid to the witness; instead it stays in `value`, which is deposited into `delegationStore.addReward` — the pool later split among voters via `MortgageService.computeReward` / `withdrawReward`. This is called twice per block: [2](#0-1) 

`payBlockReward` and `payTransactionFeeReward` are invoked once per produced block during block application (every ~3 seconds, for every active/standby SR), for the entire lifetime of the chain. Since the brokerage amount should be the witness's exact configured share, but is instead rounded down, the witness systematically receives less than its configured percentage, with the shortfall flowing to the voter pool. The rounding direction is the wrong way for the fee-taking party, exactly analogous to the reported "platform fee should round up" pattern.

Reachability: this is reachable purely through normal, unprivileged chain operation — any witness (which is a standard permissionless role reachable by staking/voting, not a "malicious SR" precondition) accumulates this systematic shortfall on every reward distribution; no special privilege or malicious behavior is required to trigger the miscalculation, it fires on every block via `Manager`'s block-application reward flow.

### Impact Explanation
Every witness reward payment underpays the witness by up to `1` sun (the truncated fractional brokerage) and misallocates that sun to the voter reward pool instead. This happens on every block for every active witness, continuously, across the lifetime of the network. While individually tiny, the effect is systemic and cumulative — it is a genuine specification-vs-implementation mismatch that causes the "platform fee" (witness's brokerage share) collector to permanently receive less than configured, with the shortfall value leaking to a different set of beneficiaries (voters) than intended. This is a Medium-severity fund-misallocation/rounding-direction bug consistent with the reported bug class.

### Likelihood Explanation
High likelihood of triggering: the rounding truncation occurs deterministically on essentially every reward payment (every block reward and every transaction-fee reward distribution to every witness), whenever `brokerage * value` is not an exact multiple of 100. No attacker action, special permission, or malicious actor is needed — it is baseline behavior of block application.

### Recommendation
Round the brokerage (and correspondingly the remaining voter-pool share) calculation using a rounding-up scheme consistent with which party is the intended "fee taker." If the brokerage is meant to be the witness's guaranteed minimum cut, use ceiling division (e.g. `(brokerage * value + 99) / 100`) instead of truncating `double` multiplication, and adjust `value -= brokerageAmount` accordingly so that the two shares always sum exactly to `value`. Apply the same fix to the analogous truncation in `IncentiveManager.reward` and `MortgageService.computeReward`, which have the same `(long) (double * value)` truncation pattern.

### Proof of Concept
1. A witness sets `brokerage = 33` via `UpdateBrokerageActuator` (any valid witness can do this for itself).
2. A block reward of `value = 100` sun is paid via `payBlockReward` → `payReward`.
3. `brokerageRate = 0.33`; `brokerageAmount = (long)(0.33 * 100) = (long)(32.999999...) = 32` (due to `double` precision/truncation) instead of the exact `33`.
4. The witness receives `32` instead of `33`; the voter pool receives `68` instead of `67`.
5. Repeated over every block (~28,800 blocks/day) and every witness, this produces a small but continuous, deterministic underpayment to witnesses in favor of voters, contrary to the configured brokerage split.
