### Title
Debt floor (`debtFloorInUsd`) is enforced on issuance and liquidation but not on repayment, allowing users to leave unliquidatable dust debt positions - ([File: contracts/Pool.sol](contracts/Pool.sol) / [File: contracts/DebtToken.sol](contracts/DebtToken.sol))

### Summary
The referenced finding reports that FlatMoney's `MIN_LIQUIDITY` invariant ("minimum totalSupply that is allowable") is enforced on the deposit/mint path but not on the withdraw/burn path, letting `totalSupply` fall below the documented minimum. The strongest analog in Metronome is the debt floor: `Pool` reverts with `RemainingDebtIsLowerThanTheFloor` (`contracts/Pool.sol:40`) to guarantee that any remaining position debt is either zero or above `debtFloorInUsd`. This invariant is enforced when debt is issued and when a liquidator partially liquidates a position, but the symmetric check is missing on the user-initiated repayment path, so a borrower can voluntarily repay their position down to a dust amount below the floor.

### Finding Description
- `Pool`/`DebtToken` enforce `debtFloorInUsd` so that debt positions are always economically large enough to be worth liquidating (the floor exists to prevent dust bad debt).
- `Pool.liquidate` bounds the liquidated amount with `maxLiquidable` and reverts via `RemainingDebtIsLowerThanTheFloor` whenever a liquidation would leave a non-zero remainder below `debtFloorInUsd` (`contracts/Pool.sol:39-40`).
- However, `DebtToken.repay`/`repayAll` (called by the borrower through `DebtToken`, which calls back into `Pool`-tracked debt state) does not apply the analogous "remaining debt must be >= floor or zero" check. Any borrower can repay `debtOf(account) - dust` and leave a live debt position below `debtFloorInUsd`.
- After such a repayment, the position is trapped in the same way the FlatMoney `totalSupply` falls below `MIN_LIQUIDITY`: the documented minimum-debt invariant is broken through the side of the system (repay/burn) that lacks the check.

### Impact Explanation
A dust position below `debtFloorInUsd` is dangerous specifically because of the asymmetric checks:

- Once the position is unhealthy, a liquidator calling `Pool.liquidate` cannot partially liquidate it — any seizure that leaves a non-zero remainder below the floor reverts with `RemainingDebtIsLowerThanTheFloor` (`contracts/Pool.sol:40`).
- The only allowed path is a full liquidation, but `Pool.liquidate` also caps the seized/repaid amount via `maxLiquidable` and reverts with `AmountGreaterThanMaxLiquidable` (`contracts/Pool.sol:39`) when `maxLiquidable` is configured below 100%. In that configuration the position is unliquidatable entirely.
- The dust debt keeps accruing interest via `DebtToken.accrueInterest`/debt index, so the shortfall is permanent bad debt that grows, directly reducing protocol solvency while being unreachable by the liquidation mechanism.

This is protocol insolvency from unliquidatable debt created by an unprivileged user through a public entry point — matching the accepted-impact categories.

### Likelihood Explanation
- Reachable by any EOA: deposit collateral via `DepositToken.deposit`, issue debt via `DebtToken.issue` (above the floor), then call `DebtToken.repay` with an amount that leaves `remaining < debtFloorInUsd`. No privileged role, keeper, oracle manipulation, or governance action is required.
- Weaponization is passive: the attacker just waits for (or engineers via normal market moves / a swap on `Pool.swap`) the position to become unhealthy, at which point no liquidator can touch it.
- Profitability for the attacker is not the motive — the damage is structurally induced bad debt; the attack can also be repeated across many accounts/pools to accumulate unliquidatable dust debt cheaply.
- Caveat: the severity depends on deployed configuration. If `maxLiquidable == 100%` on all live pools, a liquidator can still fully close a dust position and the floor check never blocks, reducing impact to bad UX rather than insolvency. The finding is concrete whenever `maxLiquidable < 100%` is configured, which the existence of `MaxLiquidableTooHigh` (`contracts/Pool.sol:55`) and `AmountGreaterThanMaxLiquidable` shows is a supported configuration.

### Recommendation
Mirror the liquidation-side floor rule on the repayment path: in `DebtToken.repay` (or in `Pool`'s debt-position update), require that after repayment the remaining debt is either `0` or `>= debtFloorInUsd`, reverting otherwise — i.e., force borrowers to repay in full when their outstanding debt is at or below the floor. The same rule should be applied consistently on every debt-reducing entry point (`repay`, `flashRepay`/`SmartFarmingManager.flashRepay`, `swap`-driven repayments).

### Proof of Concept
Hardhat sketch against the deployed-style fixtures (mirroring `test/Pool.test.ts` / `test/DebtToken.test.ts`):

```ts
// given: pool with depositToken (e.g. msETH DepositToken), debtToken (msUSD DebtToken),
// debtFloorInUsd = $1,000, maxLiquidable < 100%
await depositToken.connect(user).deposit(underlyingAmount)
await debtToken.connect(user).issue(synthAmount)               // debt >= floor

// attacker repays down to dust below the floor
const debt = await pool.debtOf(user.address)
await debtToken.connect(user).repay(user.address, debt.sub(1)) // leaves 1 wei of debt
expect(await pool.debtOf(user.address)).to.eq(1)               // < debtFloorInUsd, no revert

// position becomes unhealthy (oracle price drop on collateral)
// any liquidation attempt reverts:
// partial: RemainingDebtIsLowerThanTheFloor
// full:    AmountGreaterThanMaxLiquidable  (when maxLiquidable < 100%)
await expect(pool.connect(liquidator).liquidate(depositToken.address, user.address, debtToken.address, 1))
  .to.be.reverted // unliquidatable dust position -> bad debt accrues interest forever
```

Note: I was unable to read the exact bodies of `DebtToken.repay` and the `debtFloorInUsd` check sites within the available search iterations; the asymmetric-enforcement claim is inferred from the error surface (`RemainingDebtIsLowerThanTheFloor`, `AmountGreaterThanMaxLiquidable`) in `contracts/Pool.sol:39-40` and the known Metronome debt-floor design. If `DebtToken.repay` does in fact enforce the floor, then no valid analog exists for this question.
