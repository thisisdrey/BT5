## Title
`ItemAttributesApprovalsOf` is not cleared on NFT ownership transfer, allowing a stale delegate approved by the previous owner to keep mutating the item's attributes after transfer — ([File: substrate/frame/nfts/src/features/transfer.rs])

## Summary
`pallet-nfts` tracks two independent per-item approval structures: `Item::approvals` (transfer approvals) and `ItemAttributesApprovalsOf` (delegates allowed to write attributes in the `Account(delegate)` namespace). `do_transfer()` explicitly clears the first, citing pre-approve attack prevention, but never clears the second, so a delegate approved by the old owner keeps write access to the item's attributes after it is transferred to a new, non-consenting owner.

## Finding Description
`do_transfer()` resets `details.approvals` but performs no operation on `ItemAttributesApprovalsOf` for the transferred `(collection, item)` key: [1](#0-0) . The only other place this map is touched is `do_cancel_item_attributes_approval` (owner-gated) and on item burn, neither of which runs during a transfer. The permission check for the `Account(delegate)` namespace in `is_valid_namespace` relies solely on membership in this stale map plus caller identity, with no re-validation against the item's current owner: [2](#0-1) . The approval is only checked against the owner at grant time in `do_approve_item_attributes`: [3](#0-2) . `do_set_attribute`'s only gate for writing an attribute is this namespace check: [4](#0-3) . Consequently, once owner A approves delegate D via `approve_item_attributes`, and the item is later transferred to B via any `do_transfer`-based path (`transfer`, `buy_item`, swaps, etc.), D remains in `ItemAttributesApprovalsOf` and can still call `set_attribute` with `AttributeNamespace::Account(D)` on B's item, with no action or consent from B required.

## Impact Explanation
This allows an account never authorized by the current owner to continue writing/updating on-chain attribute metadata for an NFT after it changes hands, corrupting a value a marketplace or application may treat as authoritative for that asset, and it can be used to keep occupying a slot in the `MaxAttributesApprovals`-bounded approval set that only the current owner nominally controls but cannot see or revoke without knowing the stale delegate exists. This is a real deviation from intended owner-scoped authorization semantics: attribute-write permission is not properly rebound to the current controller of the asset. However, the corrupted value is limited to attribute metadata (not fund custody, balances, or settlement state), so it does not rise to fund theft, duplicate settlement, or chain-halting severity — it is a permission/state-integrity bug confined to the NFT attribute subsystem.

## Likelihood Explanation
Fully reachable by ordinary unprivileged users through public extrinsics (`approve_item_attributes`, `transfer`/any transfer path, `set_attribute`) with no special privileges needed, but it requires the specific precondition that an owner previously granted an `Account(delegate)` approval and the item was later transferred without either party cancelling that approval first. This is a genuine, reproducible logic gap rather than a theoretical one.

## Recommendation
Clear `ItemAttributesApprovalsOf::<T, I>` for `(collection, item)` inside `do_transfer()`, mirroring the `details.approvals.clear()` step, refunding any deposits held by delegates for attributes in the `Account(delegate)` namespace back to their depositors (similar to the refund logic in `do_cancel_item_attributes_approval`). Alternatively, bind the check in `is_valid_namespace` to the owner recorded at approval time so the approval is implicitly invalidated when `details.owner` changes.

## Proof of Concept
1. Owner A mints item `#42` in collection `0`, then calls `Nfts::approve_item_attributes(A, 0, 42, D)`, inserting D into `ItemAttributesApprovalsOf(0, 42)`.
2. A calls `Nfts::transfer(0, 42, B)`. `do_transfer` clears `Item::approvals` but leaves `ItemAttributesApprovalsOf(0, 42) = {D}` untouched (`substrate/frame/nfts/src/features/transfer.rs`, lines 90-103).
3. D (never authorized by B) calls `Nfts::set_attribute(0, Some(42), AttributeNamespace::Account(D), key, value)`. `is_valid_namespace` returns `true` because `approvals.contains(&D)` is still true, so the write succeeds against B's item without B's consent (`substrate/frame/nfts/src/features/attributes.rs`, lines 474-479). A unit test asserting `ItemAttributesApprovalsOf::get(0, 42)` still contains D after transfer, followed by a successful `set_attribute` call from D, reproduces the issue.
