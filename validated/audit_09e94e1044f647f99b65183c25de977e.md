### Title
Unsynchronized Mutation of Shared `JumpTable` Races with Concurrent TVM Execution - (File: `actuator/src/main/java/org/tron/core/vm/OperationRegistry.java`)

### Summary
`OperationRegistry` keeps a single shared, static `JumpTable` per call type — one for ordinary transactions (`tableMap.get(LATEST_VERSION)`) and one `CONSTANT_CALL_TABLE` for constant calls (`eth_call` / `triggerConstantContract`) [1](#0-0) . Every single execution — including every concurrent, unauthenticated `triggerConstantContract`/JSON-RPC `eth_call` request handled on the API thread pool — calls `VMActuator.execute()`, which invokes `OperationRegistry.prepareAndGetTable(isConstantCall)` immediately before `VM.play()` [2](#0-1) . `prepareAndGetTable` unconditionally mutates the shared table in place via `adjustTable(table)` (`adjustMemOperations`, `adjustVoteWitness`, `adjustSelfdestruct`, all calling `table.set(...)`) [3](#0-2) , and `JumpTable.set()`/`JumpTable.get()` perform plain, unsynchronized array writes/reads with no lock, no `volatile`, and no memory barrier [4](#0-3) .

This is the same bug class as the Algernon CVE: a single mutable, shared interpreter/VM-configuration object (`gopher-lua`'s `LState` there, `JumpTable` here) is written and read concurrently by multiple request-handling goroutines/threads without a lock protecting the whole read-modify-execute sequence.

### Finding Description
- `OperationRegistry.getTable(isConstantCall)` returns one of exactly two static `JumpTable` instances shared by *all* threads executing that call type [5](#0-4) .
- `ConfigLoader.load(..., isolate)` is documented to install a **thread-local** `VMConfig` snapshot for constant calls specifically so a call bound to a historical (solidity/PBFT) snapshot "cannot pollute the flags the block-processing path reads concurrently" [6](#0-5) . This design intent is explicitly *only* about the boolean flags in `VMConfig`, but `adjustTable()` reads those same possibly-thread-local flags and writes the *result* into the single shared, non-thread-local `JumpTable` instance (`CONSTANT_CALL_TABLE` for constant calls) [3](#0-2) .
- Consequently, two concurrent, unauthenticated constant-call API requests bound to *different* block/snapshot contexts (e.g., one querying HEAD, one querying an older solidity snapshot) each call `prepareAndGetTable(true)`, and each overwrites array slots of the *same* `CONSTANT_CALL_TABLE` object with `Operation` instances derived from its own — possibly stale or differently-configured — `VMConfig` view, while other concurrently running `VM.play()` invocations are reading `table.get(opcode)` from that same object to fetch `getEnergyCost()` and `execute()` for the opcode currently being interpreted [7](#0-6) .
- Because `Operation` objects are immutable value objects swapped by whole-object array-slot writes [8](#0-7) , individual `Operation` reads cannot be torn mid-object, but there is no happens-before relationship between the writer thread's `table.set()` and any other thread's later `table.get()` for the *same* opcode during the *same* transaction's execution — the table can be legitimately mutated mid-flight by a concurrent, unrelated request. The regression tests added around this area (`OperationRegistryTest`, `VMActuatorMockTest`) only assert single-threaded identity/reuse semantics; none exercise concurrent mutation, confirming there is no synchronization guarding `adjustTable` against concurrent `VM.play()` readers [9](#0-8) .

### Impact Explanation
Any anonymous API client can trigger this race simply by issuing ordinary, unauthenticated concurrent `triggerConstantContract` / JSON-RPC `eth_call` requests (the exact reachable surface called out in scope) — no privileged access is required, matching the Algernon report's "modest concurrency via `ab -n 1000 -c 100`" trigger condition. The result is that one request's TVM execution can silently pick up opcode cost/behavior/enablement (`isEnabled()`, energy cost function, action) intended for a *different* config snapshot than the one it is supposed to run under, because the shared `JumpTable` was concurrently rewritten mid-execution by another unrelated request. This yields non-deterministic/incorrect energy accounting and opcode semantics for constant-call query results (`estimateEnergy`/`triggerConstantContract` responses), i.e., the node can no longer reliably serve this class of query API request under concurrency — an accepted impact category ("an API the node can no longer serve") given the explicit design comment that this table is meant to stay isolated per snapshot but is not.

### Likelihood Explanation
High likelihood of triggering the race under realistic conditions: the query API endpoints are processed on a thread pool and routinely receive concurrent requests from independent clients/dApps; every single such request calls `prepareAndGetTable(true)`, guaranteeing writes to the shared table on essentially every request. No special timing, privileged key, or malicious peer is required — it is a pure client-side concurrency trigger, directly analogous to the `ab -c 100` reproduction in the CVE report.

### Recommendation
Do not mutate a globally shared `JumpTable` per-request. Either (a) protect `adjustTable()` and all `JumpTable.get/set` accesses with a lock/`ReadWriteLock` scoped around the entire "adjust-then-execute" sequence for a given execution, or (b) make table adjustment produce a fresh, execution-local `JumpTable` (or thread-local table) instead of mutating the shared static instance, so concurrent executions with different `VMConfig` snapshots never share mutable interpreter state.

### Proof of Concept
1. Deploy any contract exposing a view function; run two concurrent loops of `triggerConstantContract` (or JSON-RPC `eth_call`) against it — one continuously targeting HEAD, one continuously targeting an older solidity block/snapshot (or simply toggling a config-dependent flag, e.g. `allowHigherLimitForMaxCpuTimeOfOneTx`, between requests as `OperationRegistryTest.constantAdjustmentsDoNotMutateTransactionTable` demonstrates is possible per-table) [10](#0-9) .
2. Both requests call `VMActuator(true).validate()` → `ConfigLoader.load(..., true)` → `OperationRegistry.prepareAndGetTable(true)` → `adjustTable(CONSTANT_CALL_TABLE)`, mutating the same static `CONSTANT_CALL_TABLE` object concurrently with the other thread's in-flight `VM.play(program, CONSTANT_CALL_TABLE)`.
3. Observe (with `-ea`/instrumentation or a Java data-race detector such as ThreadSanitizer-for-JVM equivalents, or simply by asserting on returned energy costs across many concurrent runs) that the energy cost / enablement for a given opcode returned to one client's constant call intermittently reflects the *other* concurrent request's config view rather than its own — confirming cross-request state bleed through the unsynchronized shared `JumpTable`.

  public static JumpTable prepareAndGetTable(boolean isConstantCall) {
    JumpTable table = getTable(isConstantCall);
    // Apply configuration-dependent changes once at the top level.
    adjustTable(table);
    return table;
  }

  public static JumpTable getTable(boolean isConstantCall) {
    return isConstantCall ? CONSTANT_CALL_TABLE : tableMap.get(LATEST_VERSION);
  }

  private static void adjustTable(JumpTable table) {
    // Make the corresponding changes, excluding opcode activation.
    adjustMemOperations(table);
    adjustVoteWitness(table);
    adjustSelfdestruct(table);
  }
