### Title
Two-pass validate-then-lock split in `AccountLocks::try_lock_transaction_batch` allows in-batch write-write conflicts to both succeed - (File: `accounts-db/src/account_locks.rs`)

### Summary
`AccountLocks::try_lock_transaction_batch` checks every transaction's account-lock feasibility in a first pass against the pre-batch lock state, and only actually applies the locks in a second, separate pass. Because the first pass never mutates `self` while validating, two transactions in the same batch that write the same account both pass `can_lock_accounts` (each sees the account as unlocked) and are both subsequently locked in the second pass, incrementing `write_locks` for that key to 2 instead of rejecting the second one.

### Finding Description
`Accounts::lock_accounts` (accounts-db/src/accounts.rs:455-474) builds `validated_batch_keys` for every transaction in the batch, takes the `account_locks` mutex once, and calls `account_locks.try_lock_transaction_batch(validated_batch_keys)`.

Inside `try_lock_transaction_batch` (accounts-db/src/account_locks.rs:22-40):
```rust
validated_batch_keys.iter_mut().for_each(|validated_keys| {
    if let Ok(keys) = validated_keys.as_ref()
        && let Err(e) = self.can_lock_accounts(keys.clone())
    { *validated_keys = Err(e); }
});

validated_batch_keys
    .into_iter()
    .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
    .collect()
```
The first loop only *reads* the current lock state via `can_lock_accounts` (account_locks.rs:56-71) — it does not lock anything. It therefore validates every transaction in the batch against the *same* pre-batch snapshot of `write_locks`/`readonly_locks`. Only after all transactions have been validated does the second pass call `lock_accounts` (account_locks.rs:73-81), which unconditionally increments `write_locks[key]` or `readonly_locks[key]` for every transaction that was marked `Ok` in the first pass — without re-checking against locks acquired by earlier transactions within the same batch.

Consequence: if transaction A and transaction B in the same wire batch both write account X, and X is not locked by any other in-flight transaction, both A and B pass the first-pass `can_lock_accounts` check (both see `write_locks[X]` absent), and both then get locked in the second pass (`write_locks[X]` becomes 2). `try_lock_transaction_batch` returns `Ok(())` for both, so `Accounts::lock_accounts` reports both transactions as successfully locked. This is downstream of `Bank::lock_accounts`/`TransactionBatch`, wired from an attacker-controlled batch of transactions submitted through the normal transaction-ingress/QUIC path — the check is purely a function of transaction *content* (both transactions declaring the same writable account), not the sender's stake, so an unstaked attacker can trigger it. The intra-batch construction (transaction ordering within the batch/entry) is controlled by scheduler/consumer code that relies on `lock_accounts`'s return values to guarantee mutual exclusion for concurrent execution; if that invariant is broken, downstream code that assumes "locked accounts in a batch cannot conflict" (e.g. parallel execution assumptions in `load_and_execute_transactions`) can be violated.

Note on the test cited: the in-repo test `test_accounts_locks_intrabatch_conflicts` (accounts-db/src/accounts.rs:1223-1296) has a case commented "ww conflict in-batch succeeds" (line 1287) but it actually reuses `[w_tx, r_tx]` (the same pair as the "wr conflict in-batch succeeds" case just above it), not two write-conflicting transactions. So this specific test does **not** demonstrate a genuine write-write same-account in-batch success; it is a copy/paste duplicate of the wr case. However, tracing the implementation independently (above) shows the underlying two-pass validate/lock split would indeed allow a genuine ww conflict to both succeed, which is the real bug — the existing test suite simply fails to cover the actual ww case.

### Impact Explanation
If two write-conflicting transactions from the same batch both acquire "successful" write locks, `Bank::load_and_execute_transactions` may schedule/execute them concurrently under the (violated) assumption of exclusive write access, and both may be committed into the same `Entry`. The final committed account state would depend on execution/interleaving order rather than being a function of a single canonical serial order, which is inconsistent with the "no invalid recorded block" / "invariant broken" bounty categories around scheduling/lock/PoH correctness described in the prompt scope. This is a correctness/determinism defect in a core PoH-adjacent locking primitive rather than a straightforward crash or DoS.

### Likelihood Explanation
Feasibility is entirely a function of code path structure, not privilege: any unstaked client can submit a batch containing two transactions that write the same account (e.g. same fee-payer or same target account, differing only in a nonce/blockhash to produce distinct signatures) to the leader's TPU. The precondition that the account isn't already locked by unrelated in-flight transactions is trivially satisfiable by picking a fresh/unused account. The bug is deterministic given the code as read (two-pass split), but I was not able to fully verify in this session whether higher-level scheduler code (e.g. `greedy_scheduler.rs`, `thread_aware_account_locks.rs`, or `consumer.rs`) pre-filters batches to prevent duplicate writable accounts from ever reaching `Accounts::lock_accounts` together, which would neutralize the practical impact even though the primitive itself is unsafe in isolation. This needs further inspection of the batching/scheduling call sites before treating the impact as confirmed rather than a latent internal invariant flaw.

### Recommendation
Merge the validate and lock passes in `AccountLocks::try_lock_transaction_batch` into a single interleaved loop: for each transaction in order, call `can_lock_accounts` against the *current* (progressively mutated) `self` state and, if it succeeds, immediately call `lock_accounts` before moving to the next transaction — mirroring the original single-pass validate-then-lock-per-transaction semantics so that intra-batch conflicts are correctly rejected for the second conflicting transaction.

```rust
fn test_accounts_locks_intrabatch_ww_conflict_rejected() {

    }]);

    let results = accounts.lock_accounts(
        [w_tx_1, w_tx_2].iter(),
        [Ok(()), Ok(())].into_iter(),
        MAX_TX_ACCOUNT_LOCKS,
    );

    // Expected (correct) behavior: second write-conflicting tx must be rejected.
    assert_eq!(results, vec![Ok(()), Err(TransactionError::AccountInUse)]);

    // account_locks.write_locks[pubkey] == 2, which should never happen
    // since a write lock is meant to be exclusive.
}
```
Expected result on current code: the assertion fails because both results are `Ok(())`, demonstrating that `try_lock_transaction_batch`'s two-pass structure fails to serialize write-write conflicts within a single batch.
