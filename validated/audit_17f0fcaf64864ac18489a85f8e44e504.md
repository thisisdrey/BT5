### Title
Truncated-division ordering in `hsTimeout` undersizes the handshake timer-wheel max duration, shrinking the anti-replay/pending-handshake retry window an unauthenticated peer can influence - ([File: handshake_manager.go])

### Summary
`hsTimeout` computes the maximum duration of the `OutboundHandshakeTimer` timer wheel, which governs how long Nebula keeps retrying/tracking a pending handshake before giving up. Like the reported `beanUsdPrice` bug, the formula performs an integer division before completing the multiplication that the division is supposed to be dividing, so the result is systematically truncated for odd `tries` values instead of matching the intended closed-form sum.

### Finding Description
`hsTimeout` is intended to compute the total elapsed time for `tries` linear-backoff retries (retry *i* is scheduled at `i * interval`), i.e. the triangular-number sum `interval * tries * (tries+1) / 2`: [1](#0-0) 

```go
func hsTimeout(tries int64, interval time.Duration) time.Duration {
	return time.Duration(tries / 2 * ((2 * int64(interval)) + (tries-1)*int64(interval)))
}
```

Expanding the second factor: `2*interval + (tries-1)*interval = interval*(tries+1)`, so the mathematically correct expression is `(tries*(tries+1)/2) * interval`. However, the code performs `tries / 2` as **integer division first**, then multiplies by `interval*(tries+1)`. Because `tries` and `2` are both `int64`, Go's integer division truncates any fractional remainder *before* the multiplication that should have compensated for it — exactly the same class of error as the reported `beanUsdPrice = 1e30 / (a * b)` vs. `beanTknPrice * 1e18 / a` ordering bug, where doing the division too early (on the wrong operand, in the wrong place in the expression) discards precision that the correct order preserves.

This value is fed straight into `NewLockingTimerWheel[netip.Addr](config.tryInterval, hsTimeout(config.retries, config.tryInterval))` as the wheel's `max` duration, which sizes the wheel (`wheelLen = (max/min)+2`, see `NewTimerWheel`) and clamps any `Add` timeout larger than `max` down to `max`: [2](#0-1) [3](#0-2) 

Since `hsTimeout` under-computes the wheel's `max` for odd `retries` counts (truncating up to `interval-1` off the true value), the last scheduled retry duration `tryInterval * retries` can exceed the computed `max`, and `findWheel` will clamp it down, causing the final retry(ies) in the outbound handshake backoff sequence to fire earlier than the configured backoff schedule intends.

### Impact Explanation
This is a state/timing miscalculation reachable purely from network input: an unauthenticated remote party interacting with the handshake process (e.g. a peer that never completes the handshake, or an attacker withholding/delaying responses) directly drives how long `HandshakeManager.handleOutbound`'s retry loop and `OutboundHandshakeTimer` keep a pending handshake alive before `hm.DeleteHostInfo(hostinfo)` tears it down. A truncated `max` shortens/skews the backoff window computed at startup, causing pending-handshake retries to be purged earlier than the configured linear-backoff schedule intends. This is a timing/availability degradation of the handshake retry state machine rather than a cryptographic authentication bypass — it does not defeat certificate verification, decrypt traffic, or bypass the firewall.

### Likelihood Explanation
The bug is deterministic and always present for odd `handshakes.retries` configurations (the default `DefaultHandshakeRetries` value would need to be checked to confirm parity, which I could not verify in the available index), so it fires on every node startup, not conditionally on attacker action. No special attacker capability beyond normal unauthenticated handshake-initiation traffic is required to be affected by the shortened window, but this is a constant, low-severity miscalculation, not an exploitable protocol bypass.

### Recommendation
Restructure `hsTimeout` to perform the division only once, over the fully-formed numerator, matching the correct closed-form triangular-number formula and avoiding intermediate truncation:

```go
func hsTimeout(tries int64, interval time.Duration) time.Duration {
	return time.Duration(tries * (tries + 1) / 2 * int64(interval))
}
```

(or promote to a wider/float representation before dividing) so that the multiply-then-divide ordering preserves the intended precision, analogous to the fix recommended in the external report (`beanTknPrice.mul(1e18).div(usdPrice)` instead of `1e30.div(usdPrice.mul(beanTknPrice))`).

### Proof of Concept
Given `tryInterval = 1s`, `retries = 5`:
- Correct value: `5*6/2 * 1s = 15s`
- Actual code: `tries/2 = 2` (integer division truncates `2.5` → `2`); `((2*1s)+(5-1)*1s) = 6s`; `2*6s = 12s` — 3s short of the correct 15s, a 20% undersizing of the wheel's `max` duration purely from evaluating the division before the compensating multiplication, mirroring the reported analog's root cause.

I was unable to verify from the indexed code whether `DefaultHandshakeRetries` (referenced in `handshake_manager_test.go`) is itself odd or even; confirming the exact default-config impact would require reading `handshake_manager.go`'s constant definitions in full, which were not returned by the index. // findWheel find the next position in the wheel for the provided timeout given the current tick
func (tw *TimerWheel[T]) findWheel(timeout time.Duration) (i int) {
	if timeout < tw.tickDuration {
		// Can't track anything below the set resolution
		timeout = tw.tickDuration
	} else if timeout > tw.wheelDuration {
		// We aren't handling timeouts greater than the wheels duration
		timeout = tw.wheelDuration
	}

	// Find the next highest, rounding up
	tick := int(((timeout - 1) / tw.tickDuration) + 1)

	// Add another tick since the current tick may almost be over then map it to the wheel from our
	// current position
	tick += tw.current + 1
	if tick >= tw.wheelLen {
		tick -= tw.wheelLen
	}

	return tick
}
