Audit Report

## Title
Crowdloan `withdraw`/`refund` uses manipulable raw account balance instead of tracked bid/lease state to gate fund release - (`polkadot/runtime/common/src/crowdloan/mod.rs`)

## Summary
`ensure_crowdloan_ended` gates the unprivileged `withdraw` and `refund` extrinsics solely on comparing the fund account's `free_balance` to the internally tracked `fund.raised`, intending this as a proxy for "no bid/lease is active." [1](#0-0)  Because the fund account is an ordinary, deterministically-derivable `AccountId` (`fund_account_id`), any external party can raise its `free_balance` with a plain `Balances::transfer_allow_death`/`transfer_keep_alive`, defeating this check the same way `selfdestruct`-based balance donation defeats a Solidity contract's `address(this).balance` check.

## Finding Description
`ensure_crowdloan_ended` is the sole guard used before `withdraw` [2](#0-1)  and `refund` [3](#0-2)  pay out contributions and irreversibly delete contribution records via `contribution_kill`.

The `Auctioneer::place_bid` trait contract explicitly states that an implementation "MUST remove or reserve `amount` funds from `bidder`" [4](#0-3) , and `Leaser::deposit_held` confirms held deposits are tracked as reserved balance on the leaser's account [5](#0-4) . This corroborates that a winning bid/lease genuinely lowers `free_balance` of the fund account below `fund.raised`, which `ensure_crowdloan_ended` relies on as its only signal of an active bid/lease. Since the fund account accepts arbitrary incoming transfers (demonstrated in the existing `withdraw_cannot_be_griefed` test) [6](#0-5) , anyone can top up `free_balance` back to/above `fund.raised` while the reserved deposit for a live bid/lease is still held, tricking `ensure_crowdloan_ended` into passing.

I was unable to fully verify, within the available tool budget, the exact reserve/transfer mechanics inside `polkadot/runtime/common/src/slots/mod.rs`'s concrete `place_bid`/`lease_out` implementation (whether it uses `reserve()` on the fund account itself vs. transferring to a separate module account) to conclusively confirm the exact numeric relationship between `deposit_held` and the fund account's `free_balance` in all code paths. The trait documentation strongly implies the vulnerable pattern applies, but full confirmation of the current slots pallet's implementation details was not completed.

## Impact Explanation
If confirmed, this would allow duplicate settlement of crowdloan funds: contributors could be refunded via `withdraw`/`refund` while the para's slot deposit remains reserved/committed, and when that deposit is later released it has no contribution record left to attribute to (since `contribution_kill` already ran), ultimately being burned in `dissolve`. This matches the "duplicate settlement or payout" / "permanent user-fund lock" impact classes in the Polkadot SDK gate.

## Likelihood Explanation
The described donation step (`Balances::transfer_allow_death` to a publicly-derivable fund account) requires only an ordinary, unprivileged extrinsic and no compromised relayer, prover, or governance action, making it feasible if the underlying reserve mechanics work as documented in the `Auctioneer`/`Leaser` trait contracts.

## Recommendation
Do not use `free_balance(&fund_account)` as a proxy for "no active bid/lease." Replace the check in `ensure_crowdloan_ended` with an explicit query against `T::Auctioneer`/`T::Leaser` (e.g., `has_won_an_auction` or an explicit reserved-deposit accessor) or track the bid-reserved amount directly in `FundInfo`, comparing against that tracked value instead of the raw account balance.

## Proof of Concept
1. Contributors fund a crowdloan for `para`; `fund.raised = R`.
2. The crowdloan wins the slot auction; the winning bid deposit is reserved/held against the fund account, so `free_balance(fund_account) < fund.raised`.
3. Attacker calls `Balances::transfer_allow_death(attacker, fund_account, R)` to raise `free_balance(fund_account)` back to `>= fund.raised`.
4. Attacker calls `Crowdloan::withdraw` or `Crowdloan::refund`; `ensure_crowdloan_ended` passes despite the lease deposit remaining reserved.
5. Contribution records are deleted and `fund.raised` is zeroed while the para's lease deposit is still locked, and any later release of that deposit is stranded with no contribution record to return to.

	/// This function checks all conditions which would qualify a crowdloan has ended.
	/// * If we have reached the `fund.end` block OR the first lease period the fund is trying to
	///   bid for has started already.
	/// * And, if the fund has enough free funds to refund full raised amount.
	fn ensure_crowdloan_ended(
		now: BlockNumberFor<T>,
		fund_account: &T::AccountId,
		fund: &FundInfo<T::AccountId, BalanceOf<T>, BlockNumberFor<T>, LeasePeriodOf<T>>,
	) -> sp_runtime::DispatchResult {
		// `fund.end` can represent the end of a failed crowdloan or the beginning of retirement
		// If the current lease period is past the first period they are trying to bid for, then
		// it is already too late to win the bid.
		let (current_lease_period, _) =
			T::Auctioneer::lease_period_index(now).ok_or(Error::<T>::NoLeasePeriod)?;
		ensure!(
			now >= fund.end || current_lease_period > fund.first_period,
			Error::<T>::FundNotEnded
		);
		// free balance must greater than or equal amount raised, otherwise funds are being used
		// and a bid or lease must be active.
		ensure!(
			CurrencyOf::<T>::free_balance(&fund_account) >= fund.raised,
			Error::<T>::BidOrLeaseActive
		);

		Ok(())
