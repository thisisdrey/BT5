## Title
Wallet Contract fails to refund an external caller's attached deposit when an intermediate cross-contract check (registrar lookup / NEP-141 `storage_balance_of`) fails, permanently stranding funds - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::address_check_callback` and `WalletContract::nep_141_storage_balance_callback` both branch on `env::promise_result(0)`, exactly mirroring the C4 pattern where a callee-controllable external-call outcome (success vs. failure) selects between two very differently-protected code paths. The `PromiseResult::Failed` arm of the *final* action callback (`rlp_execute_callback`) refunds the external caller's `caller_deposit`, but the `PromiseResult::Failed` arms of the two *intermediate* callbacks do not, even though `caller_deposit` was already threaded through as an argument specifically to be refunded on failure.

### Finding Description
`inner_rlp_execute` computes `caller_deposit` from the attached NEAR deposit of whoever called `rlp_execute` (an external, unprivileged, non-self relayer/caller), specifically to be returned if the eventual on-chain action fails: [1](#0-0) 

For two transaction kinds this deposit is threaded through an extra hop before the action executes:
- `EOABaseTokenTransfer{address_check: Some(_), ..}` → calls the address registrar, then `address_check_callback`.
- `ERC20Transfer` → calls `token::storage_balance_of`, then `nep_141_storage_balance_callback`.

Both intermediate callbacks receive `caller_deposit: Option<CallerDeposit>` as a parameter (so the deposit is clearly meant to be tracked through this extra hop), but their `PromiseResult::Failed` branches simply return an `ExecuteResponse{success:false,...}` without ever issuing the refund promise: [2](#0-1) [3](#0-2) 

Compare this to the only place the refund is actually implemented, `rlp_execute_callback`, which is reached solely when the underlying action itself (not an intermediate check) is dispatched and fails: [4](#0-3) 

The wallet contract's own test suite (`test_caller_refunds`) only exercises the refund behavior for a *direct* action failure (`FunctionCall` to a non-existent account), i.e., the path through `rlp_execute_callback`, not the two-hop `address_check_callback` / `nep_141_storage_balance_callback` paths: [5](#0-4) 

This is structurally the same bug class as the Zora report: an external, adversary-influenceable call's failure (the registrar's `lookup`, or — more importantly — an arbitrary NEP-141-labelled `target` account's `storage_balance_of`, both of which are ordinary cross-contract calls that can be made to return `PromiseResult::Failed` e.g. by the target contract panicking, running out of gas, or simply not existing/implementing the method) silently routes execution into a code path that skips the safety net (deposit refund) that exists on the "normal" failure path.

### Impact Explanation
Any account (predecessor of `rlp_execute`, distinct from the eth-implicit wallet account itself) that attaches a NEAR deposit while relaying an `ERC20Transfer`-emulated action, or an `EOABaseTokenTransfer` with `address_check`, permanently loses that deposit if the intermediate cross-contract call fails — the funds are neither returned to the caller nor used to complete the intended action; they remain stuck in the wallet contract's balance with no code path that recovers them for the original depositor. This is a freezing/loss-of-funds condition reachable by an ordinary, unprivileged account (any relayer or fee-paying caller of the wallet contract) without needing any special access key or governance power, triggered purely by the failure mode of a called contract (which can be attacker-influenced by choosing/deploying a `target`/token account that reverts on `storage_balance_of`).

### Likelihood Explanation
Likelihood is real but conditioned on external contract behavior: the registrar account is fixed/trusted (`ADDRESS_REGISTRAR_ACCOUNT_ID`), lowering likelihood for the `address_check_callback` path to genuine outages/misconfiguration rather than active attacker control. The `ERC20Transfer` path is more concerning because `target`/`token_id` is attacker- or relayer-supplied — a token contract that reverts on `storage_balance_of` (intentionally malicious, buggy, paused, or simply nonexistent) will deterministically trigger the unrefunded-failure branch whenever a caller attaches a deposit to relay through it.

### Recommendation
Add the same `caller_deposit` refund logic (issue a `promise_batch_create` + `promise_batch_action_transfer` to `caller_deposit.account_id`) inside the `PromiseResult::Failed` arms of both `address_check_callback` and `nep_141_storage_balance_callback`, mirroring the handling already present in `rlp_execute_callback`, so that any intermediate cross-contract call failure results in the caller's deposit being returned rather than stranded.

### Proof of Concept
1. Deploy the Wallet Contract for an eth-implicit account and fund it as in `test_wallet_contract_interaction`.
2. Deploy a NEP-141-labelled contract at some account `evil.near` whose `storage_balance_of` method always panics (or simply do not deploy any contract at that account so the call fails with `MethodNotFound`/execution error).
3. Have an external, unprivileged relayer account call `rlp_execute` targeting `evil.near` with an RLP-encoded `ERC20Transfer` transaction, attaching a nonzero NEAR deposit (as in `test_caller_refunds`'s relayer-fee pattern, but using `evil.near` as target instead of the address registrar).
4. Observe: `storage_balance_of` promise resolves to `PromiseResult::Failed`, `nep_141_storage_balance_callback` returns `ExecuteResponse{success:false,...}` without creating any refund promise, and the caller's balance decreases by the full attached deposit permanently (unlike the `test_caller_refunds` scenario where the deposit differential stays below `deposit_amount`).

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
