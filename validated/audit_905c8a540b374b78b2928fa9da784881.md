### Title
Stale StackerDB signer-set config kept across a reward-cycle boundary lets old/removed signers keep writing while the new signer set is silently ignored - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::create_or_reconfigure_stackerdbs` skips reconfiguration whenever the freshly-evaluated smart-contract config differs from the in-memory config *but* the newly-evaluated signer list happens to be empty. This mirrors the Olas bug class: a boundary-crossing event (a reward-cycle rollover analogous to the Olas "year" rollover) produces a value that is only partially/temporarily consistent with the new period, and the code keeps using the stale, previously-committed state instead of reconciling to the new one, silently.

### Finding Description
`StackerDBs::create_or_reconfigure_stackerdbs` decides whether to call `reconfigure_stackerdb` (which rewrites the slot-to-signer mapping used by `try_replace_chunk`'s signature check) using this condition: [1](#0-0) 

```
} else if (new_config != stackerdb_config && !new_config.signers.is_empty())
    || (new_config == stackerdb_config
        && new_config.signers.len()
            != self.get_slot_versions(&stackerdb_contract_id)?.len())
{
    // only reconfigure if the config has changed
    ...
    self.reconfigure_stackerdb(&stackerdb_contract_id, &new_config)?;
}
```

`StackerDBConfig::from_smart_contract` re-evaluates the controlling contract's `stackerdb-get-signer-slots` on every reward-cycle transition (config refresh is only invoked once per cycle, per the module docs: “This smart contract is queried once per reward cycle”). If, at the exact moment of the reward-cycle rollover, the contract's read-only evaluation legitimately (or transiently, e.g. due to a temporary node view lagging the canonical tip) returns an empty signer list for that cycle, the `!new_config.signers.is_empty()` guard fails and the whole reconfiguration is skipped — even though `new_config != stackerdb_config`. The previous cycle's `StackerDBConfig` (with its old slot→signer mapping) is kept both in `self.stacker_db_configs` and, more importantly, in the persistent slot-validation table used by `try_replace_chunk`: [2](#0-1) 

Since `try_replace_chunk` (and `validate_received_chunk` for gossip) authenticate a chunk purely against `slot_validation.signer`, which is only updated by `reconfigure_stackerdb`, a signer who was valid in the prior reward cycle but has since been removed/rotated out of the new cycle's signer set can continue to have their chunks accepted, stored, and rebroadcast network-wide via `process_stacker_db_chunks`: [3](#0-2) 

This breaks the equality "authenticated writer == currently-authorized signer for the active reward cycle": the DB keeps accepting writes signed by a stale, no-longer-canonical signer set, exactly the same class of bug as the Olas report where a stale (pre-boundary) accounting value is used to gate an action that should have been re-evaluated against the post-boundary state.

### Impact Explanation
An unauthorized (rotated-out) signer's chunk could be stored and propagated as canonical StackerDB content across the network, i.e. unauthorized write to state and network-wide propagation of forged/unauthorized data — matching the "Critical" bucket (unauthenticated/unauthorized write to state or StackerDB; network-wide propagation of forged data).

### Likelihood Explanation
This requires the config-eval path to observe an empty signer list transiently at a reward-cycle boundary (a race/degenerate contract-evaluation outcome), which is a narrower trigger than a fully attacker-controlled condition. I was not able to fully confirm, within the available index, whether `eval_signer_slots`/`stackerdb-get-signer-slots` can realistically return an empty list mid-transition for the production `.signers-*` contracts (the `signers.clar` control contract always returns a stored list rather than an empty one by default), so likelihood is uncertain and depends on conditions I could not fully verify from the indexed code (e.g., whether a `NoSuchStackerDB`/read failure path can produce an empty-but-different `new_config` rather than falling into the `noop()` fallback branch, which is handled separately).

### Recommendation
Remove the `!new_config.signers.is_empty()` special case, or make it fail safe: if the config legitimately changed, always call `reconfigure_stackerdb` (or explicitly clear/deny writes) rather than silently retaining a stale slot→signer mapping across a reward-cycle boundary. Alternatively, treat an empty signer list from a live contract as an error requiring the config load to be retried before being merged, rather than deferring to the old configuration for chunk-authentication decisions.

### Proof of Concept
Not independently reproduced from the index; this is based on static analysis of the branch condition in `create_or_reconfigure_stackerdbs` at [1](#0-0)  combined with the `try_replace_chunk` signer-authorization check at [4](#0-3) . Confirming exploitability end-to-end (i.e., proving the contract-eval path can actually yield an empty-but-changed signer list at a live reward-cycle boundary) would require running the node/test harness, which is outside what I could verify from the indexed code alone.
