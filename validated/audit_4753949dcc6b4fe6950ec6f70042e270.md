### Title
Unbounded array allocation in `BatchValidateSign`/`ValidateMultiSign` precompile helpers leads to excessive memory allocation / DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `extractBytes32Array` and `extractBytesArray` helper methods used by the `BatchValidateSign` and `ValidateMultiSign` TVM precompiled contracts allocate Java arrays whose size is taken directly from attacker-controlled call data, with no upper bound enforced unless a specific hard-fork feature flag is active. This mirrors the CVE-2018-20543 bug class: a length value parsed from untrusted input is used to allocate memory without validating it against the actual size of available data, enabling an attempted excessive memory allocation.

### Finding Description
`extractBytes32Array` reads a count directly from the decoded call data and immediately allocates an array of that size: [1](#0-0) 

Similarly, `extractBytesArray` and `extractSigArray` compute `len` from `words[offset].intValueSafe()` and allocate `new byte[len][]` before any comparison with the actual remaining data length: [2](#0-1) 

These helpers are invoked from `BatchValidateSign.doExecute` and `ValidateMultiSign.execute`. A bound check (`sigArraySize > MAX_SIZE` / `addrArraySize > MAX_SIZE`) is only performed when `VMConfig.allowTvmSelfdestructRestriction()` is enabled; the extraction calls themselves are otherwise made unconditionally on the raw, attacker-supplied length: [3](#0-2) [4](#0-3) 

Because `intValueSafe()` clamps to `Integer.MAX_VALUE` rather than to the actual data length, a crafted call to these precompiles with a huge encoded array-length word (e.g. `0x7fffffff`) causes the JVM to attempt to allocate an array of that many elements, before the loop that would otherwise fail on out-of-bounds access to `words[]`.

### Impact Explanation
An attacker who can invoke the `BatchValidateSign` or `ValidateMultiSign` precompiled contract (address `0x0a` / `0x09`, callable via `CALL`/`STATICCALL` from any contract, including on `eth_call`/constant calls with no fee) can force the node to attempt allocation of an oversized array. This can trigger `OutOfMemoryError`, degrading or crashing the node process — a denial-of-service condition affecting all node functions, not just the calling transaction, since `OutOfMemoryError` can destabilize the whole JVM.

### Likelihood Explanation
The precompile is reachable by any address via a plain contract call with attacker-controlled ABI-encoded input; no special privilege, deployment, or witness/SR status is required. The unconditional path (flag `allowTvmSelfdestructRestriction` disabled) has no size gate at all before allocation, only relying on the fact that a real length field is bounded by `intValueSafe`'s clamp to `Integer.MAX_VALUE` rather than by actual call-data size.

### Recommendation
Validate the declared array length against the size of the actual decoded `words` array (or raw call-data length) before allocating `byte[][]` buffers in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, independent of the `allowTvmSelfdestructRestriction` feature flag. Enforce a strict maximum (e.g., `MAX_SIZE`) unconditionally prior to allocation, not only in the gated branch.

### Proof of Concept
Craft ABI-encoded call data to `BatchValidateSign` (precompile address `0x0a`) where the address-array-length word at the offset pointed to by `words[2]` is set to a very large value (e.g. `0x7fffffff`), while `allowTvmSelfdestructRestriction` is not yet activated. Invoking this via a `CALL` from a contract (or a constant `eth_call`) causes `extractBytes32Array` to execute `new byte[0x7fffffff][]`, attempting a multi-gigabyte allocation and triggering `OutOfMemoryError` in the node's TVM execution thread.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
