### Title
Self-escalation via `AccountPermissionUpdateContract` executable under a low-threshold Active permission - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
The Timelock report shows a governance model where a role meant to be constrained by a delay/threshold can rewrite the very permission structure that constrains it, instantly and without further checks. In java-tron's account permission system, `AccountPermissionUpdateContract`/`AccountPermissionUpdateActuator` is the analog "role-management" surface: it lets an `owner_address` account overwrite its `Owner`, `Witness`, and `Active` permissions in one step. The critical question — analogous to "can the new governor remove the delay?" — is whether execution of this contract is itself gated only by the (potentially weak) `Active` permission that is allowed to hold it in its operations bitmap, rather than requiring the stronger `Owner` permission's threshold.

### Finding Description
`AccountPermissionUpdateActuator#execute` unconditionally overwrites the account's `Owner`, `Witness`, and all `Active` permissions with whatever is supplied in the contract, with no re-validation against the pre-existing `Owner` permission's signers/threshold: [1](#0-0) 

Authorization to submit any contract type — including `AccountPermissionUpdateContract` itself — is controlled purely by `Transaction.Contract.permission_id`. If `permission_id != 0`, the signer only needs to satisfy an `Active` permission's threshold, not the `Owner` permission's threshold, and the sole extra check is that the contract's type bit is set in that `Active` permission's 32-byte `operations` bitmap: [2](#0-1) [3](#0-2) 

The `checkPermission`/`checkAvailableContractType` logic in the actuator only verifies that the requested operations bitmap is a subset of `dynamicStore.getAvailableContractType()` — it does not exclude `AccountPermissionUpdateContract` from being assignable to an `Active` permission: [4](#0-3) 

The test `checkAvailableContractTypeCorrespondingToCode` documents that the "available contract type" bitmap covers essentially all contract types (it explicitly excludes only `ClearABIContract` and `UpdateBrokerageContract`), meaning `AccountPermissionUpdateContract` is a normal, assignable operation for any `Active` permission: [5](#0-4) 

As a result, an account owner (or an attacker who has compromised only a low-weight `Active` key that was granted the `AccountPermissionUpdateContract` bit) can submit an `AccountPermissionUpdateContract` signed only under that weak `Active` permission's threshold and instantly replace the strong `Owner` permission with keys/thresholds fully controlled by the attacker — exactly the pattern in the Timelock bug, where a role with limited authority reconfigures the governing structure that was supposed to constrain it, with no additional delay, multi-party check, or requirement that the change be authorized under the very permission being replaced.

### Impact Explanation
Once the `Owner` permission is overwritten via a transaction validated only against a weaker `Active` permission, the attacker gains unrestricted control of the account: they can subsequently replace `Active`/`Witness` permissions, transfer all TRX/TRC10/TRC20 assets, and change resource delegation — a full unauthorized account takeover leading to theft of funds. This satisfies the "unauthorized account operation / theft of funds" impact bar.

### Likelihood Explanation
This requires that an account owner has configured an `Active` permission with the `AccountPermissionUpdateContract` bit set (which is not prevented by validation) and that an attacker obtains signing capability under that `Active` permission — a realistic scenario for exchanges, multisig wallets, or DApps that create broad, low-threshold "operator" active keys for automation while assuming account-level permission changes remain protected by the stronger `Owner` threshold. Because nothing in `AccountPermissionUpdateActuator#validate`/`execute` or `TransactionCapsule#checkPermission` requires that an `AccountPermissionUpdateContract` be authorized under `Owner` (permission_id 0), the bypass is directly reachable by any signed transaction from that weaker key, with no reliance on malicious SR/witness/peer behavior.

### Recommendation
Disallow `AccountPermissionUpdateContract` (and any other permission-management contract types) from being included in the `operations` bitmap of non-`Owner` permissions, or explicitly require that `AccountPermissionUpdateContract` transactions be authorized under the account's `Owner` permission (`permission_id == 0`) regardless of what bits are set in an `Active` permission's operations mask. This mirrors the Timelock fix of forcing self-referential/governance-altering calls through the strongest authority rather than a delegate.

### Proof of Concept
1. Account `A` sets up permissions via `AccountPermissionUpdateContract`: `Owner` permission with high threshold/strong keys, and an `Active` permission (id ≥ 2) whose `operations` bitmap includes the bit for `AccountPermissionUpdateContract`, with a low threshold or a single weak key (a common "automation/operator" configuration), as validated by `checkPermission`: [6](#0-5) 
2. Attacker obtains the weak `Active` key (e.g., via a compromised automation server).
3. Attacker builds a new `AccountPermissionUpdateContract` for account `A` that sets a brand-new `Owner` permission entirely controlled by the attacker, sets `Transaction.Contract.permission_id` to the weak `Active` permission's id, and signs only with that `Active` key.
4. `TransactionCapsule#checkPermission` accepts the signature because `permission_id != 0` only requires the `Active` permission's own type/operations/threshold check, not `Owner`'s: [2](#0-1) 
5. `AccountPermissionUpdateActuator#execute` applies the update unconditionally, overwriting `Owner` with the attacker's keys: [1](#0-0) 
6. Attacker now controls `Owner` permission and can drain the account's assets in a follow-up transaction.

  private boolean checkPermission(Permission permission) throws ContractValidateException {
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (permission.getKeysCount() > dynamicStore.getTotalSignNum()) {
      throw new ContractValidateException("number of keys in permission should not be greater "
          + "than " + dynamicStore.getTotalSignNum());
    }
    if (permission.getKeysCount() == 0) {
      throw new ContractValidateException("key's count should be greater than 0");
    }
    if (permission.getType() == PermissionType.Witness && permission.getKeysCount() != 1) {
      throw new ContractValidateException("Witness permission's key count should be 1");
    }
    if (permission.getThreshold() <= 0) {
      throw new ContractValidateException("permission's threshold should be greater than 0");
    }
    String name = permission.getPermissionName();
    if (!StringUtils.isEmpty(name) && name.length() > 32) {
      throw new ContractValidateException("permission's name is too long");
    }
    //check owner name ?
    if (permission.getParentId() != 0) {
      throw new ContractValidateException("permission's parent should be owner");
    }

    long weightSum = 0;
    List<ByteString> addressList = permission.getKeysList()
        .stream()
        .map(x -> x.getAddress())
        .distinct()
        .collect(toList());
    if (addressList.size() != permission.getKeysList().size()) {
      throw new ContractValidateException(
          "address should be distinct in permission " + permission.getType());
    }
    for (Key key : permission.getKeysList()) {
      if (!DecodeUtil.addressValid(key.getAddress().toByteArray())) {
        throw new ContractValidateException("key is not a validate address");
      }
      if (key.getWeight() <= 0) {
        throw new ContractValidateException("key's weight should be greater than 0");
      }
      try {
        weightSum = addExact(weightSum, key.getWeight());
      } catch (ArithmeticException e) {
        throw new ContractValidateException(e.getMessage());
      }
    }
    if (weightSum < permission.getThreshold()) {
      throw new ContractValidateException(
          "sum of all key's weight should not be less than threshold in permission " + permission
              .getType());
    }

    ByteString operations = permission.getOperations();
    if (permission.getType() != PermissionType.Active) {
      if (!operations.isEmpty()) {
        throw new ContractValidateException(
            permission.getType() + " permission needn't operations");
      }
      return true;
    }
    //check operations
    if (operations.isEmpty() || operations.size() != 32) {
      throw new ContractValidateException("operations size must 32");
    }

    byte[] types1 = dynamicStore.getAvailableContractType();
    for (int i = 0; i < 256; i++) {
      boolean b = (operations.byteAt(i / 8) & (1 << (i % 8))) != 0;
      boolean t = ((types1[(i / 8)] & 0xff) & (1 << (i % 8))) != 0;
      if (b && !t) {
        throw new ContractValidateException(i + " isn't a validate ContractType");
      }
    }
    return true;
  }

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException("operations size must be 32");
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
