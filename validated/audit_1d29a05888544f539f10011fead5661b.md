Audit Report

## Title
Native value sent alongside non-payable ERC20 precompile calls (`balanceOf`, `totalSupply`, `allowance`, `name`, `symbol`, `decimals`, `nonces`, `permit`, `DOMAIN_SEPARATOR`) is silently transferred and permanently trapped - (File: `substrate/frame/assets/precompiles/src/lib.rs`)

## Summary
`pallet-revive`'s call-frame execution unconditionally transfers `frame.value_transferred` to the target precompile account before invoking the precompile logic, regardless of which Solidity selector is being called. The `ERC20` precompile's `call` dispatch in `substrate/frame/assets/precompiles/src/lib.rs` never checks `env.value_transferred()` for the non-payable, view/pure selectors (`balanceOf`, `totalSupply`, `allowance`, `name`, `symbol`, `decimals`, `nonces`, `permit`, `DOMAIN_SEPARATOR`), so any value attached to such a call is deposited into the precompile's fixed address with no code path to reclaim it.

## Finding Description
`Stack::run` in `substrate/frame/revive/src/exec.rs` performs the balance transfer for any non-delegate frame before the target (contract or precompile) executes: [1](#0-0) 

The `ERC20::call` dispatch then matches on the decoded selector and only guards against **state mutation on read-only calls** for `transfer`/`approve`/`transferFrom`/`permit`; it performs no check on `env.value_transferred()` anywhere for any selector, including the getters: [2](#0-1) 

Each of the read-only handlers (`total_supply`, `balance_of`, `allowance`, `name`, `symbol`, `decimals`, `nonces`, `domain_separator`) only reads pallet-assets/permit state and returns ABI-encoded output — none of them inspects, forwards, or refunds `env.value_transferred()`: [3](#0-2) [4](#0-3) 

`ERC20` sets `const HAS_CONTRACT_INFO: bool = false`, meaning it lacks the contract-info-backed account lifecycle checked in `exec.rs` (mint of minimum balance / consumer tracking) that is applied for other precompiles: [5](#0-4) 

The prdoc for a not-yet-completed fix explicitly documents that `pallet-assets-precompiles` and related precompiles "currently violate Solidity state mutability... potentially introducing a new attack vector" and that a `const MUTATES: bool`-style trait guard is insufficient because mutability depends on the Solidity selector, not the trait: [6](#0-5) 

This confirms the maintainers' own characterization of the defect class, and the code in this repository still lacks the enforcement (the `is_read_only` check only prevents mutation attempts during static calls; it says nothing about rejecting non-zero value on non-payable selectors).

## Impact Explanation
This matches the "permanent user-fund lock" impact: any value attached to a call targeting a non-payable ERC20 precompile selector is transferred to the precompile's address by `Self::transfer_from_origin(...)` in `exec.rs` before the selector's handler runs, and the handler for that selector provides no mechanism to move, refund, or claim that value afterward. Since Solidity's high-level ABI-encoded calls normally prevent attaching value to non-payable functions, exploitation specifically requires a low-level call (e.g., `address.call{value: N}(abi.encodeWithSelector(...))`) or direct `bare_call`/`eth_call` usage that bypasses that Solidity-level guard — the guard does not exist at the Rust dispatch layer that actually executes the precompile.

## Likelihood Explanation
The precondition is an unprivileged, ordinary caller issuing a low-level EVM-style call with non-zero `value` against a read-only ERC20 precompile selector; no privileged actor, governance action, or compromised infrastructure is needed. This is directly reachable from a contract's Solidity code using `call{value: N}(...)` or from any transaction builder that crafts the raw call data, matching the report's proof-of-concept pattern (`CallSelfWithDust.sol`).

## Recommendation
Add an explicit `env.value_transferred().is_zero()` (or equivalent) check in `ERC20::call` for every non-payable selector (`totalSupply`, `balanceOf`, `allowance`, `name`, `symbol`, `decimals`, `nonces`, `DOMAIN_SEPARATOR`, and non-value-carrying `permit`), reverting cleanly instead of allowing `exec.rs` to transfer value into the precompile account. Ideally this should be enforced generically at the dispatch layer (as intended by the in-progress `pr_10080` fix) by deriving per-selector mutability metadata and validating it consistently for both "no state change" and "no unexpected value" before any handler executes.

## Proof of Concept
1. Target the `ERC20` precompile address for an existing asset.
2. From a contract, invoke a low-level `call{value: N}(...)` encoding `balanceOf(address)` (or any other read-only selector), bypassing Solidity's own `payable` ABI-level guard.
3. `Stack::run` in `exec.rs` transfers `N` into the precompile's account via `transfer_from_origin` before the `ERC20::call` dispatch executes.
4. `ERC20::call` matches `IERC20Calls::balanceOf` and returns the balance without inspecting or using `N`.
5. The call succeeds and returns the queried value; `N` remains permanently held at the precompile's address, which has no code path (no `has_contract_info`-based lifecycle, no owner-controlled withdrawal) to release it — unrecoverable fund loss for the caller.

	) -> Result<Vec<u8>, Error> {

			Self::to_u256(pallet_assets::Pallet::<Runtime, Instance>::balance(asset_id, account))?;
		Ok(IERC20::balanceOfCall::abi_encode_returns(&value))
	}

This PR implements corresponding checks at the function dispatch.

    Could be enforced in `pallet-revive`, however:
    1. Adding something like a `const MUTATES: bool` to the `Precompile` trait won't help because whether the call is mutating or not depends on the [Solidity function selector.](https://docs.soliditylang.org/en/latest/abi-spec.html#function-selector).
    2. Alloy, which we are using to parse the interface definitions prior to calling precompile implementations, doesn't provide a mapping from function selector to its mutability [modifier](https://docs.soliditylang.org/en/latest/cheatsheet.html#modifiers).
