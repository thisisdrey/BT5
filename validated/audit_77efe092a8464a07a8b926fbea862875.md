## Title
Unbounded in-memory HTTP response buffering in `libsigner::http::run_http_request` - ([File: libsigner/src/http.rs])

### Summary
`run_http_request` reads an entire HTTP response into an unbounded `Vec<u8>` via `sock.read_to_end(&mut buf)` before any `Content-Length` or size check is applied, mirroring the Scrapy CVE-2017-14158 pattern of reading arbitrarily large data into memory prior to any bound enforcement.

### Finding Description
`run_http_request` writes the request and then does: [1](#0-0) 
`sock.read_to_end(&mut buf)` has no size cap — the socket peer can stream indefinitely and every byte is appended into `buf`, growing without bound, before `decode_http_response` is even invoked to inspect headers. Only afterwards is `MAX_MESSAGE_LEN` enforced, and only for the *chunked* body-decoding path: [2](#0-1) 
For a non-chunked response, `decode_http_body` simply does `buf.to_vec()` on whatever was already fully buffered by `read_to_end` — i.e., the "as-is" branch performs no bound check at all, and by that point the unbounded read has already occurred regardless.

This differs from the P2P wire path (`stackslib/src/net/connection.rs`), which explicitly caps preamble and payload buffering against `preamble_size_hint()`/`payload_len()` and `MAX_MESSAGE_LEN`: [3](#0-2) [4](#0-3) 
and the HTTP node-server path (`stackslib/src/net/httpcore.rs`), which bounds preamble reads to `HTTP_PREAMBLE_MAX_ENCODED_SIZE` and streams chunked bodies with a bound reader. `libsigner`'s client-side `run_http_request`, used by `StackerDBSession`/`SignerSession` to talk to the configured Stacks node RPC endpoint, has no equivalent cap on the initial full-response read.

### Impact Explanation
If the endpoint the signer connects to (an untrusted, malicious, or compromised RPC server at the configured `host`) sends a very large or endless response body, `run_http_request` will keep growing `buf` in memory with no limit, exhausting the signer process's memory and crashing/DoS'ing the signer. This matches the CWE-400 (uncontrolled resource consumption) class from the report.

However, per the stated impact criteria (remote crash/DoS "from few messages" originating from an unauthenticated remote peer), this is bounded in severity because: the target of this unbounded read is the specific host address the signer operator configured (`self.host` in `StackerDBSession::connect`), not an arbitrary internet-facing listener. It requires that endpoint (or a MITM/compromised version of it) to behave maliciously — this is closer to a "traffic-volume" issue from a semi-trusted party rather than an unauthenticated remote attacker reaching internal state. This weakens confidence that it meets the "Critical/High, remote, unprivileged" bar strictly, but the underlying code defect (missing bound before reading) is real and directly analogous to the reported CVE's memory-consumption pattern.

### Likelihood Explanation
Likelihood is moderate: it requires the signer to be pointed at (or have its traffic to) a malicious/compromised node RPC endpoint. It does not require any secret key or admin privilege on the signer's own side, only control of the remote HTTP responder the signer is configured to trust for RPC.

### Recommendation
Wrap the socket read in a bounded reader (e.g. `BoundReader` capped at `MAX_MESSAGE_LEN`, consistent with the rest of the codebase) before calling `read_to_end`, and enforce the advertised `Content-Length` against that same cap prior to allocating/reading the full body, for both chunked and non-chunked responses.

### Proof of Concept
1. Configure a signer's `StackerDBSession`/`SignerSession` to point at a malicious/compromised "node" endpoint (`host`).
2. Have that endpoint accept the request and stream an HTTP/1.1 response with a very large or unbounded body (with or without a `Content-Length` header understating the true size, or simply an extremely large body).
3. `run_http_request` (`libsigner/src/http.rs:246-253`) calls `sock.read_to_end(&mut buf)`, which will buffer unbounded bytes into memory, exhausting the signer process's memory before any size check is applied. [5](#0-4)

/// Decode an HTTP body, given the headers.
pub fn decode_http_body(headers: &HashMap<String, String>, mut buf: &[u8]) -> io::Result<Vec<u8>> {
    let chunked = if let Some(val) = headers.get("transfer-encoding") {
        val == "chunked"
    } else {
        false
    };

    let body = if chunked {
        // chunked encoding
        let ptr = &mut buf;
        let mut fd = HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into());
        let mut decoded_body = vec![];
        fd.read_to_end(&mut decoded_body)?;
        decoded_body
    } else {
        // body is just as-is
        buf.to_vec()
    };

    Ok(body)
}

/// Run an HTTP request, synchronously, through the given read/write handle
/// Return the HTTP reply, decoded if it was chunked
pub fn run_http_request<S: Read + Write>(
    sock: &mut S,
    host: &str,
    verb: &str,
    path: &str,
    content_type: Option<&str>,
    payload: &[u8],
) -> Result<Vec<u8>, RPCError> {
    let content_length_hdr = if !payload.is_empty() {
        format!("Content-Length: {}\r\n", payload.len())
    } else {
        "".to_string()
    };

    let req_txt = if let Some(content_type) = content_type {
        format!(
            "{verb} {path} HTTP/1.1\r\nHost: {host}\r\nConnection: close\r\nContent-Type: {content_type}\r\n{content_length_hdr}User-Agent: libsigner/0.1\r\nAccept: */*\r\n\r\n"
        )
    } else {
        format!(
            "{verb} {path} HTTP/1.1\r\nHost: {host}\r\nConnection: close\r\n{content_length_hdr}User-Agent: libsigner/0.1\r\nAccept: */*\r\n\r\n"
        )
    };
    debug!("HTTP request\n{}", &req_txt);

    sock.write_all(req_txt.as_bytes())?;
    sock.write_all(payload)?;

    let mut buf = vec![];

    sock.read_to_end(&mut buf)?;

    let (headers, body_offset) = decode_http_response(&buf)?;
    if body_offset >= buf.len() {
        // no body
        debug!("No HTTP body");
        debug!("Headers: {:?}", &headers);
        return Ok(vec![]);
    }

    decode_http_body(&headers, &buf[body_offset..]).map_err(|e| e.into())
}

    fn buffer_message_bytes(
        &mut self,
        bytes: &[u8],
        message_len_opt: Option<usize>,
    ) -> Result<usize, net_error> {
        let message_len = message_len_opt.unwrap_or(MAX_MESSAGE_LEN as usize);
        let buffered_so_far = self
            .buf
            .len()
            .checked_sub(self.message_ptr)
            .ok_or_else(|| {
                net_error::RecvError(format!("Message ptr {} overran buffer", self.message_ptr))
            })?;

        let Some(message_remaining) = message_len.checked_sub(buffered_so_far) else {
            // can happen if we receive so much data when parsing the preamble that we've
            // also already received the message, and part of the next preamble (or more).
            return Ok(0);
        };

        let to_consume = bytes.len().min(message_remaining);

        trace!("Consume {} bytes from input buffer", to_consume);
        self.buf.extend_from_slice(
            bytes
                .get(..to_consume)
                .expect("FATAL: bad length check in buffer handling"),
        );
