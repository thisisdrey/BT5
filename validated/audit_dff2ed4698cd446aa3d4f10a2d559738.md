### Title
TOCTOU in `LinkRepositoryToObjectPool` allows racing concurrent links to bypass alternates isolation - (File: internal/git/objectpool/link.go)

### Summary
The Beedle report's bug class is a check-then-act race: a value that gates a security-relevant action (`maxLoanRatio`) is read, decided upon, and then the action executes later using freshly-read mutable state instead of a value fixed atomically at decision time, letting an attacker mutate the state in the gap. Gitaly's `objectpool.Link` (invoked by the unprivileged, per-repository `LinkRepositoryToObjectPool` RPC) exhibits the same class of flaw: it reads whether a repository is already linked to a pool, then unconditionally writes a new `objects/info/alternates` file, with no exclusive lock held across the read-then-write window.

### Finding Description
`Link` in `internal/git/objectpool/link.go` performs the classic check-then-act sequence without synchronization: [1](#0-0) 

1. It computes the `expectedRelPath` for the target pool.
2. It calls `linkedToRepository(ctx, pool, repo)` (a pure read of the repository's current `objects/info/alternates` file via `stats.AlternatesInfoForRepository`) to decide if any write is needed. [2](#0-1) 
3. If not linked, it opens a `safe.NewLockingFileWriter` and writes the new alternates content, then calls `removeMemberBitmaps`.

Critically, `safe.NewLockingFileWriter` only guards the write of the single file itself (an atomic rename-based writer) — it does not serialize the read-check (step 2) with the write (step 3) against a second, concurrent `LinkRepositoryToObjectPool` call for the *same* repository but naming a *different* object pool. Both concurrent calls can observe "not linked" from `linkedToRepository`, then race to write their own alternates content; whichever writer's atomic rename finishes last wins, silently discarding the other pool's assignment. Unlike `repoutil.Create`, which explicitly takes a repository-wide lock via `Lock(ctx, ...)` before re-checking existence and moving files into place, the `Link` code path (reachable from the unprivileged, per-repository `LinkRepositoryToObjectPoolRequest` RPC, whose only inputs are `object_pool` and `repository`) has no analogous exclusive lock: [3](#0-2) 

The RPC handler itself performs no additional locking around the call to `pool.Link`: [4](#0-3) 

The project's own test suite acknowledges this race exists and is currently only prevented when the WAL/transaction subsystem is active (which detects the resulting read-write conflict on the alternates file and aborts the second commit); the non-WAL path has no such protection: [5](#0-4) 

Because the `objects/info/alternates` file is what grants a repository transparent read access to all objects of the referenced pool (this is exactly the mechanism documented for object-pool deduplication), whichever pool "wins" the race becomes fully readable through the member repository via any subsequent Git operation or Gitaly RPC on that repository.

### Impact Explanation
An ordinary user who can trigger two concurrent `LinkRepositoryToObjectPool` RPCs against a repository they control (e.g., their own fork, or a repository for which they have mutator access) — one naming the intended/authorized pool and one naming an object pool belonging to a different project/user — can, outside of the WAL-protected path, cause the repository to end up linked to the unintended pool. Since alternates directories are used as a full object search path, this grants cross-repository object read access: any object present in the "winning" pool (including a fork upstream's history) becomes reachable from the racing repository, bypassing the intended isolation between repositories/pools that don't share a lineage. This matches the "cross-repository object access" impact category via object-pool/alternates isolation bypass.

### Likelihood Explanation
Triggering the race only requires the ability to issue two `LinkRepositoryToObjectPool` RPCs concurrently for a repository the caller already controls, which is an ordinary, unprivileged action (no admin, no leaked token, no MITM required). The precondition of naming a second, unrelated object pool depends on the caller having a valid `ObjectPool` reference to link against (in GitLab's usage this maps to fork-network pools the caller is permitted to name); this is analogous to how `CreateObjectPool`/`LinkRepositoryToObjectPool` are already exposed as per-repository RPCs, so the reachability bar is low, though exploitability depends on the surrounding authorization layer (e.g., Rails/GitLab) permitting the caller to reference the victim pool. This is a genuine, but timing-dependent (racy), condition — moderate likelihood.

### Recommendation
Serialize the check-then-write sequence in `Link` (and symmetrically in `Disconnect`) with an exclusive, per-repository lock (the same mechanism used by `repoutil.Create`/`repoutil.Lock`) so that the "is linked" check and the alternates-file write happen atomically with respect to other concurrent link/disconnect/create operations on the same repository, regardless of whether WAL transactions are enabled. Additionally, consider re-validating that the repository is still unlinked immediately before the atomic rename inside the lock, and reject the operation (rather than silently overwrite) if the alternates file was concurrently changed to point at a different pool than expected.

### Proof of Concept
Not independently reproducible without running Gitaly; based on the existing test `transaction_manager_alternate_test.go` ("repository can't be linked concurrently multiple times") this race is demonstrated to matter under WAL and is unguarded in the non-WAL `objectpool.Link` code path: [5](#0-4) 
Conceptually: (1) create repos `member`, `poolA` (authorized), `poolB` (attacker-named, unrelated); (2) fire two concurrent `LinkRepositoryToObjectPool` RPCs for `member` → `poolA` and `member` → `poolB` without WAL enabled; (3) observe that `member`'s `objects/info/alternates` ends up referencing `poolB`, and objects only present in `poolB` become readable via RPCs against `member`.

// linkedToRepository tests if a repository is linked to an object pool
func linkedToRepository(ctx context.Context, pool, repo *localrepo.Repo) (bool, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting repo path: %w", err)
	}

	altInfo, err := stats.AlternatesInfoForRepository(repoPath)
	if err != nil {
		return false, fmt.Errorf("getting alternates info: %w", err)
	}

	if !altInfo.Exists || len(altInfo.ObjectDirectories) == 0 {
		return false, nil
	}

	relPath := altInfo.ObjectDirectories[0]
	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return false, err
	}

	if relPath == expectedRelPath {
		return true, nil
	}

	if filepath.Clean(relPath) != filepath.Join(poolPath, "objects") {
		return false, fmt.Errorf("unexpected alternates content: %q", relPath)
	}

	return false, nil
}

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}
