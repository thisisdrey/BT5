### Title
Handshake replay accepted with no absolute freshness bound, allowing re-derivation of stale (non-forward-secret) session keys - (File: `handshake_manager.go`, `hostmap.go`)

### Summary
The M-17 report flags that `ThecosomataETH`'s price oracle trusts an EMA-derived value with neither a freshness bound (time-since-update check) nor a tamper/deviation bound. In nebula, the field that plays the equivalent trust-anchoring role for accepting a handshake — `lastHandshakeTime` (sourced from the attacker-suppliable `Payload.Time` field carried inside the Noise handshake payload) — is checked only *relative to whatever hostinfo currently happens to be cached in memory*, never against the verifier's own wall clock, and the anti-replay memory (`HandshakePacket`) evaporates the instant the hostinfo is torn down. This mirrors the oracle bug's dual gap: no freshness check, and no tamper-resistance check.

### Finding Description
`HostInfo.lastHandshakeTime` is documented as the mechanism meant "to avoid an attack where a handshake packet is replayed after some time": [1](#0-0) 

That value is populated straight from the wire, with no cross-check against the receiver's own clock: [2](#0-1) 

The only place this value is ever consulted is `CheckAndComplete`, and only as a *relative* ordering test against whatever `HostInfo` is presently resident in the main hostmap: [3](#0-2) 

There is no absolute bound (e.g. "handshake Time must be within N seconds of now") comparable to the report's recommendation of checking `block.timestamp - lastPricesTimestamp <= 1 hour`, and no sanity/deviation check comparable to the report's "reported price must not deviate more than 5% from `price_oracle`". The only protection against a captured, previously-valid stage-0/stage-1 packet is `HandshakePacket` dedup inside the *currently live* `HostInfo`: [4](#0-3) 

That dedup memory is scoped to the lifetime of the in-memory `HostInfo` object. Once a tunnel is torn down (idle timeout, `CloseTunnel`, process restart, connection-manager eviction), the `HandshakePacket` history and the `lastHandshakeTime` baseline disappear along with it: [5](#0-4) 

At that point `beginHandshake` treats a re-submitted, previously-captured, still-cert-valid stage-0 packet exactly like a brand-new handshake — there is no existing hostinfo to compare `lastHandshakeTime` against, so the "freshness" check trivially passes: [6](#0-5) 

Because the Noise IX pattern derives session keys from the ephemeral+static DH values embedded in that exact captured packet, re-processing the identical byte sequence re-derives the *identical* `eKey`/`dKey` pair that was in use during the original session — defeating the entire purpose of using per-handshake ephemeral keys for forward secrecy.

### Impact Explanation
An observer who has captured a legitimate stage-0 handshake packet (this requires no CA-signed certificate of their own — it is a passive network capture-and-replay, not a scheme requiring the attacker to possess valid credentials) can, once the original tunnel is torn down, re-inject that exact packet to the responder at any later point while the embedded certificate remains unexpired. The responder will re-run the noise state machine, reconstruct the same session keys as the original handshake, and complete a "new" tunnel with those stale keys. If the attacker also captured application ciphertext exchanged under the original session (or the corresponding stage-2 response), the key re-derivation directly enables decryption/forgery of that traffic — a `traffic decryption/forgery/replay` impact, and independently a remote hostmap state-poisoning vector (an old, stale identity's handshake can resurrect/hijack hostmap state for a vpn address at a time of the attacker's choosing, since nothing bounds how "stale" an accepted handshake may be).

### Likelihood Explanation
Exploitation only requires the ability to observe and replay UDP traffic to the target (no valid certificate needed) plus a window in which: (1) the original tunnel has since been torn down (a routine, frequent event — idle timeout, roam, restart, `CloseTunnel`), and (2) the certificate embedded in the captured packet has not yet expired (host certificates commonly have multi-day/multi-month validity). This is a realistic condition in long-lived nebula meshes, making the likelihood moderate-to-high wherever an attacker has network visibility to capture handshake traffic.

### Recommendation
Mirror both of the report's mitigations in the handshake path:
1. **Freshness**: reject handshake payloads whose `Time` differs from the verifier's own wall clock by more than a bounded skew window (e.g., a few minutes), independent of whatever hostinfo happens to be cached.
2. **Tamper/replay resistance**: maintain a short-lived, persistent (not tied to the live `HostInfo` object) record of recently-seen handshake identifiers/nonces (e.g., a bounded time-keyed cache of `(remote identity, ephemeral public key or full stage-0 hash)`) so that a captured stage-0 packet cannot be replayed to re-derive prior session keys after the original `HostInfo` has been evicted.

### Proof of Concept
1. Attacker passively captures the stage-0 handshake UDP packet Alice → Bob (contains Alice's still-valid certificate and Noise IX ephemeral key material).
2. Bob's tunnel with Alice is later torn down (idle timeout / restart / `CloseTunnel`), which deletes `HostInfo` and its `HandshakePacket` dedup history: [5](#0-4) 
3. While Alice's certificate is still within its `NotBefore`/`NotAfter` window, attacker re-sends the exact captured stage-0 packet to Bob.
4. `HandleIncoming` → `beginHandshake` sees `h.MessageCounter == 1`, `RemoteIndex == 0`, runs the Noise machine and cert verification against `time.Now()` (which still passes since the cert isn't expired), and — finding no existing `HostInfo` for Alice's vpn address — accepts it as a fresh handshake, re-deriving the original session's `eKey`/`dKey`: [7](#0-6) [2](#0-1) 
5. If the attacker also captured Bob's original stage-2 response (or any ciphertext under that key pair from the original session), it is now decryptable/forgeable using the freshly re-established, identical keys — with no check anywhere in the accept path bounding how "stale" the accepted `Time`/handshake actually was.

```go
func (hm *HandshakeManager) beginHandshake(via ViaSender, packet []byte, h *header.H) {
	f := hm.f
	cs := f.pki.getCertState()

	v := cs.DefaultVersion()
	if cs.GetCredential(v) == nil {
		f.l.Error("Unable to handshake with host because no certificate is available",
			"from", via, "certVersion", v)
		return
	}

	machine, err := handshake.NewMachine(
		v, cs.GetCredential,
		hm.certVerifier(), func() (uint32, error) { return generateIndex(f.l) },
		false, header.HandshakeIXPSK0,
	)
	if err != nil {
		f.l.Error("Failed to create handshake machine", "from", via, "error", err)
		return
	}

	response, result, err := machine.ProcessPacket(nil, packet)
	if err != nil {
		f.l.Error("Failed to process handshake packet", "from", via, "error", err)
		return
	}

	if result == nil {
		// Multi-message pattern: the responder Machine would need to be
		// registered in hm.indexes so a future inbound packet finds it via
		// continueHandshake. The current manager doesn't do that yet, so
		// fail loudly rather than silently dropping the in-flight handshake.
		// TODO: support multi-message responder flows (XX, pqIX, etc.).
		// See also the IX-shaped cipher key assignment in handshake.Machine.
		f.l.Error("multi-message handshake responder is not supported",
			"from", via, "error", handshake.ErrMultiMessageUnsupported)
		return
	}

	remoteCert := result.RemoteCert
	if remoteCert == nil {
		f.l.Error("Handshake did not produce a peer certificate", "from", via)
		return
	}

	// Validate peer identity
	vpnAddrs, anyVpnAddrsInCommon, ok := hm.validatePeerCert(via, remoteCert)
	if !ok {
		return
	}
```

```go
// closeTunnel closes a tunnel locally, it does not send a closeTunnel packet to the remote
func (f *Interface) closeTunnel(hostInfo *HostInfo) {
	final := f.hostMap.DeleteHostInfo(hostInfo)
	if final {
		// We no longer have any tunnels with this vpn addr, clear learned lighthouse state to lower memory usage
		f.lightHouse.DeleteVpnAddrs(hostInfo.vpnAddrs)
	}
}
```
