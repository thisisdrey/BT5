Audit Report

## Title
Relayer reward is paid regardless of Ethereum-side delivery `success` flag - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` whose `success: bool` field reports whether the dispatched message actually executed successfully on the Ethereum Gateway contract, but the function never inspects this field before paying the relayer reward. As a result, `order.fee` is registered via `T::RewardPayment::register_reward` purely based on `order.fee > 0`, whether the message succeeded or failed on Ethereum.

## Finding Description
`DeliveryReceipt::try_from` decodes the `success` field straight from the `InboundMessageDispatched` Ethereum event log at [1](#0-0) , defined in the struct at [2](#0-1) . `submit_delivery_receipt` verifies the proof, decodes the receipt, and calls `process_delivery_receipt` at [3](#0-2) . Inside `process_delivery_receipt`, the code checks the gateway address, resolves the reward account, fetches the `PendingOrder` by nonce, and pays out `order.fee` solely based on `order.fee > 0` at [4](#0-3)  — `receipt.success` is decoded into the struct but never read anywhere in the function or in the rest of the codebase (confirmed by searching for all `.success` usages across `bridges/snowbridge/`, which shows the field is only referenced at its point of definition/decoding). The doc comment documents the intended flow as paying the reward with no success gating at [5](#0-4) , confirming this is a structural omission rather than a one-off typo.

## Impact Explanation
This is public underpriced work in bridge reward accounting: any relayer permitted to call `submit_delivery_receipt` can submit a valid proof for a message whose Ethereum-side execution failed (`success = false`, e.g., due to reverted commands or exhausted gas) and still collect the full `order.fee` reward via `T::RewardPayment::register_reward` at [6](#0-5) . Failed relaying work is compensated identically to successful work, undermining the incentive design and allowing systematic fee extraction for messages that never completed on Ethereum.

## Likelihood Explanation
High likelihood: this occurs on the normal `submit_delivery_receipt` path with no special preconditions. Any relayer submitting a legitimate proof of a failed-execution log (the proof only attests log authenticity, not the outcome value) realizes the incorrect reward, since `T::Verifier::verify` and the pending-order lookup say nothing about the dispatched command's success at [7](#0-6) .

## Recommendation
Branch on `receipt.success` before paying the reward, e.g.:
```rust
if receipt.success && order.fee > 0 {
    T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee);
}
```

## Proof of Concept
1. A message is queued via `do_process_message`, creating a `PendingOrder { nonce, fee, .. }` with `fee > 0` at [8](#0-7) .
2. On Ethereum, the Gateway contract processes the message but the command execution reverts, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer builds a valid proof for this event log and calls `submit_delivery_receipt`; `T::Verifier::verify` succeeds because the log is authentic regardless of the `success` value it carries.
4. `DeliveryReceipt::try_from` decodes `success = false` into the struct at [1](#0-0) .
5. `process_delivery_receipt` never reads `receipt.success`, finds `order.fee > 0`, and calls `T::RewardPayment::register_reward`, paying the relayer the full fee despite the failed execution at [4](#0-3) .
