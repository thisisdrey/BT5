## Title
Take-profit / stop-loss orders bound the Keeper's execution fee using the *current* `FeeState.order_execution_max_fee`, not a value cached at order placement time - ([File: programs/marginfi/src/instructions/marginfi_account/order.rs])

### Summary
This is a direct structural analog of the SecondSwap `unlistVesting` bug: the SecondSwap penalty fee was read live from mutable admin state at unlist time rather than being cached when the user listed, so a user who committed to an action under one fee regime could be charged under a different, later regime. In marginfi, an unprivileged user calls `PlaceOrder` to create a Take-Profit/Stop-Loss `Order`, which encodes only `take_profit`/`stop_loss` thresholds and `max_slippage`. The order sits on-chain, potentially for a long time, until a Keeper triggers `StartExecuteOrder`/`EndExecuteOrder`. The maximum "haircut" a Keeper may take from the user's proceeds is governed by the global, admin-mutable `FeeState.order_execution_max_fee`, which is read fresh at `EndExecuteOrder` time rather than being snapshotted when the user placed the order.

### Finding Description
In `end_execute_order`, the allowed value extraction for a Take-Profit trigger is bounded by: [1](#0-0) [2](#0-1) 

`fee_state.order_execution_max_fee` is loaded from the live `FeeState` account inside `end_execute_order`, not from any value stored in the `Order` account at `PlaceOrder` time. `Order::initialize` only stores `take_profit`, `stop_loss`, `max_slippage`, and tags - there is no `order_execution_max_fee` snapshot field: [3](#0-2) 

The comment in the same file even documents the intended design assumption that `ORDER_EXECUTION_MAX_FEE` "usually dominates the slippage constraint" for take-profit orders, confirming that the fee cap is a first-class part of the user's execution-price guarantee, just like SecondSwap's `penaltyFee` was part of the user's expected unlisting cost: [4](#0-3) 

`order_execution_max_fee` is a global, admin-settable field on `FeeState`, changeable at any time via `edit_global_fee_state` (analogous to SecondSwap's `penaltyFee` being adjustable by `s2Admin`): [5](#0-4) 

The gap between order placement and order execution can span an arbitrary amount of time - orders are stored and wait for a price trigger, so the fee parameter can legitimately change (e.g., raised from 5% to a higher configured maximum) between `PlaceOrder` and `EndExecuteOrder`, exactly mirroring SecondSwap's gap between `listVesting` and `unlistVesting`.

### Impact Explanation
An unprivileged user places a Take-Profit order expecting to lose at most `ORDER_EXECUTION_MAX_FEE` (default 5%, per test fixtures) of their equity value to the executing Keeper: [6](#0-5) 

If the global fee admin later raises `order_execution_max_fee` (up to `MAX_ORDER_SLIPPAGE`-adjacent bounds) before the order triggers, the Keeper is now permitted to extract a larger share of the user's take-profit proceeds than the user could have anticipated at order-creation time, without the user having any opportunity to re-evaluate or cancel under the new terms before execution occurs. This directly reduces the value returned to the user relative to their reasonable expectation when placing the order — an unauthorized state/economic outcome from the user's perspective, matching the accepted Medium-severity classification of the original SecondSwap finding ("the user should be protected from such cases... the responsibility is on the user" otherwise).

### Likelihood Explanation
Likelihood is moderate: it requires (1) a legitimate/administrative change to `order_execution_max_fee` via `edit_global_fee_state`, and (2) an outstanding order that has not yet triggered at the time of the change. Since orders can remain open indefinitely awaiting a price trigger, and fee parameters are expected to be tunable over the life of the protocol, this window is realistically reachable without any malicious insider action — the same low bar that made the original C4 finding a valid Medium.

### Recommendation
Cache `order_execution_max_fee` (and/or `order.max_slippage`'s effective interaction with it) into the `Order` account at `PlaceOrder` time, and use that cached value in `end_execute_order` instead of re-reading the live `FeeState`. Alternatively, require `StartExecuteOrder` to snapshot the currently active `order_execution_max_fee` into `ExecuteOrderRecord` so at minimum the value is fixed for the duration of the execution, and consider exposing/alerting order owners when the global fee changes so they can cancel/update stale orders (`CloseOrder`) before they are executed under new terms.

### Proof of Concept
1. User calls `PlaceOrder` with `OrderTrigger::TakeProfit { threshold, max_slippage }` while `FeeState.order_execution_max_fee = 5%` (the tests use this default).
2. Global fee admin calls `edit_global_fee_state` and raises `order_execution_max_fee` to, e.g., 20% (test harness demonstrates this exact mutation path): [7](#0-6) 
3. Later, the market price crosses the user's take-profit threshold, and a Keeper calls `StartExecuteOrder` → withdraw/repay → `EndExecuteOrder`.
4. `end_execute_order` computes `max_fee_frac` from the now-20% `fee_state.order_execution_max_fee`: [8](#0-7) 
5. The Keeper is permitted to leave the user with as little as `(1 - 0.20) * start_health`, instead of the `(1 - 0.05) * start_health` the user relied on when the order was placed — the user's realized take-profit proceeds are reduced purely due to a fee parameter change that occurred after they committed to the order, with no cached protection in the `Order` account.

```rust
impl OrderImpl for Order {
    fn initialize(
        &mut self,
        marginfi_account: Pubkey,
        trigger: OrderTrigger,
        tags: [u16; ORDER_ACTIVE_TAGS],
        bump: u8,
    ) -> MarginfiResult {
        self.marginfi_account = marginfi_account;
        match trigger {
            OrderTrigger::StopLoss {
                threshold,
                max_slippage,
            } => {
                self.trigger = OrderTriggerType::StopLoss;
                self.stop_loss = threshold;
                self.max_slippage = max_slippage;
                self.take_profit = WrappedI80F48::default();
                // Threshold must be > 0
                let val: I80F48 = self.stop_loss.into();
                check!(
                    val > I80F48::ZERO,
                    MarginfiError::InvalidOrderTakeProfitOrStopLoss
                );
            }
            OrderTrigger::TakeProfit {
                threshold,
                max_slippage,
            } => {
                self.trigger = OrderTriggerType::TakeProfit;
                self.take_profit = threshold;
                self.max_slippage = max_slippage;
                self.stop_loss = WrappedI80F48::default();
                // Threshold must be > 0
                let val: I80F48 = self.take_profit.into();
                check!(
                    val > I80F48::ZERO,
                    MarginfiError::InvalidOrderTakeProfitOrStopLoss
                );
            }
            OrderTrigger::Both {
                stop_loss,
                take_profit,
                max_slippage,
            } => {
                self.trigger = OrderTriggerType::Both;
                self.stop_loss = stop_loss;
                self.take_profit = take_profit;
                self.max_slippage = max_slippage;
                // Both thresholds must be > 0 && tp > sl
                let sl: I80F48 = self.stop_loss.into();
                let tp: I80F48 = self.take_profit.into();
                check!(
                    sl > I80F48::ZERO && tp > sl,
                    MarginfiError::InvalidOrderTakeProfitOrStopLoss
                );
            }
        }

        // Orders are capped at MAX_ORDER_SLIPPAGE. Stop-loss execution is also gated by maintenance
        // health. Take-profit execution is additionally bounded by ORDER_EXECUTION_MAX_FEE, which
        // usually dominates the slippage constraint at this cap,
        check!(
            self.max_slippage <= MAX_ORDER_SLIPPAGE,
            MarginfiError::SlippageTooHigh
        );

        self.tags = tags;
        self.bump = bump;

        Ok(())
    }
```
