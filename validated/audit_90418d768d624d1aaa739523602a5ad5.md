### Title
Unbounded array allocation from unvalidated ABI length field in TVM precompiled contracts - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The WavPack CVE-2018-10538 root cause is that `ParseRiffHeaderConfig` computes an allocation size (`bytes_to_copy`) directly from an attacker-controlled length field without validating it against the actual available input, leading to a mis-sized `malloc`. The java-tron `PrecompiledContracts` ABI-array helpers exhibit the same root-cause pattern: an attacker-controlled 32-byte length word from the precompiled-contract call `data` is converted with `intValueSafe()` and used directly to size a Java array allocation, with no upper bound check against the actual remaining `data` length before allocation.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` read a length field straight out of attacker-supplied `data`: [1](#0-0) [2](#0-1) [3](#0-2) 

In each function, `int len = words[offset].intValueSafe();` is taken from the caller-supplied word array with no comparison against `words.length` (the actual amount of supplied ABI data) before it is used to size `new byte[len][]` (or, in `extractBytes32Array`, before iterating `words[offset + i + 1]`, which will simply throw `ArrayIndexOutOfBoundsException` for a mismatched length, but only after the array has already been allocated). `intValueSafe()` returns any 32-bit non-negative value up to `Integer.MAX_VALUE` for inputs that fit in 4 bytes: [4](#0-3) 

This is analogous to WavPack’s `bytes_to_copy` calculation: a length value derived from untrusted input is used to size a buffer/array without first validating that the input actually contains that many bytes/elements.

### Impact Explanation
An attacker can call the precompiled contract address with crafted calldata whose length header word encodes an extremely large value (e.g., near `Integer.MAX_VALUE`). This drives `new byte[len][]` to attempt to allocate an object-reference array with up to ~2^31 elements (many gigabytes on a 64-bit JVM). This is a heap allocation request satisfied by the JVM allocator itself (not bounded by TVM memory-expansion gas accounting, which only governs the EVM `Memory` byte buffer, not native Java object arrays created inside precompiled-contract logic). A resulting `OutOfMemoryError` is a JVM `Error`, not a `RuntimeException`, and is not caught by the VM interpreter’s exception handling in `VM.play()`, which only catches `RuntimeException`/`JVMStackOverFlowException`/`OutOfTimeException`: [5](#0-4) 

An uncaught `OutOfMemoryError` during block/transaction processing can destabilize or crash the node process (or leave the JVM in a degraded, unrecoverable state affecting subsequent block processing), matching the "node crash or halt" impact bar.

### Likelihood Explanation
Reachable by any unprivileged account: a contract call (or direct API call) to the affected precompiled contract address with attacker-controlled calldata is enough to trigger the oversized length field — no special privileges, staking, or witness/committee role required. The trigger is a single crafted transaction/contract invocation.

### Recommendation
Validate the decoded `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` against the actual remaining size of `words`/`data` before allocating any array (e.g., reject if `len` exceeds `(words.length - offset - 1)` or a sane protocol-defined maximum), mirroring the fix pattern applied for the WavPack CVE (validate declared size against actual available bytes before allocating).

### Proof of Concept
1. Deploy or call an existing contract that performs a `STATICCALL`/`CALL` to the precompiled contract address handled by the code path using `extractBytesArray`/`extractBytes32Array`/`extractSigArray` (the array-based ABI decoding routines in `PrecompiledContracts.java`).
2. Craft calldata such that the 32-byte word at the expected "array length" offset encodes a very large positive integer (e.g., `0x7FFFFFFF`).
3. Submit the transaction; when the precompiled contract's `execute(byte[] data)` reaches `extractBytesArray`/`extractBytes32Array`, `len` is read directly as `words[offset].intValueSafe()` and used in `new byte[len][]` before any check that `words` actually contains that many trailing elements, causing the JVM to attempt an oversized allocation.

Note: I was not able to fully trace, within the available iterations, exactly which precompiled contract entry point(s) in `getContractForAddress` invoke each of `extractBytesArray`/`extractSigArray` at runtime (they support ecrecover/multisig-style batch verification precompiles), nor confirm whether an outer `getEnergyForData` bound on `data.length` indirectly caps `len` in all call sites. This should be verified against the live `PrecompiledContracts.java` dispatch table before treating this as a confirmed, exploitable finding.
