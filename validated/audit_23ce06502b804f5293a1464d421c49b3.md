### Title
Unauthenticated `recv_error` message allows remote attackers to force tunnel teardown for arbitrary peers - ([File: outside.go])

### Summary

### Finding Description
The `Voter.sol` report's root cause is a state-mutating function (`poke()`) that lacks the guard (`onlyNewEpoch`) its siblings (`vote()`/`reset()`) enforce, letting an attacker invoke it an unlimited number of times to corrupt shared accounting state that other, honest participants rely on — resulting in denial of fair rewards for those other users.

The reachable analog in this repository is `handleRecvError` in [1](#0-0) . `header.RecvError` packets are dispatched straight out of `readOutsidePackets` before any handshake/cert verification and before packet decryption [2](#0-1) , so an attacker with **no CA-signed certificate** and no established tunnel can send them. The only two conditions checked are: (1) `ShouldRecvError` config gate, which defaults to "always" per the changelog entry `Add a config option to control accepting recv_error packets which defaults to always` [3](#0-2) , and (2) whether the sender's UDP address matches the hostinfo's *currently known* remote — but only `if hr.IsValid()`:

```
hr := hostinfo.GetRemote()
if hr.IsValid() && hr != addr {
    f.l.Info("Someone spoofing recv_errors?", ...)
    return
}
f.closeTunnel(hostinfo)
f.handshakeManager.DeleteHostInfo(hostinfo)
``` [4](#0-3) 

The lookup key, `h.RemoteIndex`, is a cleartext 32-bit index carried in every packet header on the wire (see the same field used unauthenticated in the handshake path at [5](#0-4) ), so it is observable/guessable by a network attacker without ever completing a handshake or holding a CA-signed certificate. Unlike the handshake path, which gates state-creating actions behind full noise/cert verification (`beginHandshake` only creates a `HostInfo` after `machine.ProcessPacket` succeeds and `validatePeerCert` passes, per [6](#0-5) ), `handleRecvError` performs a destructive action — full tunnel teardown via `closeTunnel` plus `DeleteHostInfo` — using only an unauthenticated index/address check with no cryptographic proof of possession and no rate limiting, mirroring the "missing modifier that sibling functions enforce" pattern in the report.

### Impact Explanation
An attacker who observes or brute-forces a victim's `RemoteIndex` (or who is on-path and can read cleartext headers) can repeatedly forge `RecvError` packets to force disconnection/re-handshake of arbitrary victim tunnels, without ever needing to be a valid CA-signed peer. This is a remote, unauthenticated denial-of-service against other users' established tunnels — analogous to the report's "blocking other users" impact, since it can be repeated indefinitely (no `onlyNewEpoch`-style guard, no per-source rate limit) to keep victims permanently torn down/re-handshaking, degrading availability for the targeted peer(s) while the attacker holds no valid identity in the mesh.

### Likelihood Explanation
Reachable pre-authentication, over plain UDP, with a default configuration (`accept_recv_error` defaults to "always"). The only mitigating factor is the `hr.IsValid() && hr != addr` check, which is bypassed whenever `hr` is not yet valid (e.g., very early in a connection's life) or when the attacker can spoof/observe the legitimate remote address, and it provides no cryptographic authentication of the sender in any case.

### Recommendation
- Require the `RecvError` action to be authenticated (e.g., verify against a MAC/keyed value tied to the session rather than a bare index + best-effort address match), or bind acceptance to an established, live connection state with anti-replay protection.
- Add rate limiting / backoff on `handleRecvError` per remote index or per source address, mirroring the guard that exists for handshake state creation but is currently missing here.
- Consider changing the default `accept_recv_error` behavior to be more conservative, and document the trust assumption that `RemoteIndex` is not itself a secret.

### Proof of Concept
1. Establish (or observe) a nebula tunnel between "victim" and "peer", noting the wire-visible `RemoteIndex` value carried in packet headers between them (this field is unencrypted per the header format used throughout `outside.go`/`handshake_manager.go`).
2. From an attacker host that has no CA-signed certificate and is not part of the mesh, craft a UDP packet with `header.Type = header.RecvError` and `RemoteIndex` set to the observed index, and send it to "victim"'s listening UDP port, spoofing the source address to match the peer's currently known remote address (or sending before `hr` becomes valid).
3. Observe that `handleRecvError` (outside.go:541-575) calls `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`, tearing down the victim's tunnel without any cryptographic proof from the attacker.
4. Repeat step 2 indefinitely to keep the victim's tunnel to that peer perpetually disrupted — a remote, unauthenticated denial-of-service directly analogous to the reward-griefing DoS in the original report.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```
