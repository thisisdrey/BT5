### Title
Access-Restriction Bypass: `node.jsonrpc.*` disabled-API config is not enforced on the JSON-RPC endpoint - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/FullNodeJsonRpcHttpService.java`)

### Summary
Node operators can block sensitive Wallet API methods (e.g. `getaccount`, `gettransactionbyid`, `getnowblock`, etc.) node-wide via `node.http.disabledApiList` / `node.rpc.disabledApiList`, expecting the restriction to apply to every access path exposed by the node. This restriction is enforced only for the HTTP servlet path (`HttpApiAccessFilter`) and the gRPC path (`RpcApiAccessInterceptor`), but the JSON-RPC HTTP servlet at `/jsonrpc` is registered with no equivalent check at all, so the same underlying data/functionality remains fully reachable by an unprivileged remote client through JSON-RPC method calls.

### Finding Description
`CommonParameter.getDisabledApiList()` is consulted by two access-restriction components:

- `HttpApiAccessFilter.isDisabled(String endpoint)` blocks HTTP wallet endpoints by comparing the path segment against the disabled list [1](#0-0) , and is wired into `FullNodeHttpApiService`, `SolidityNodeHttpApiService`, `HttpApiOnPBFTService`, and `HttpApiOnSolidityService` via `addFilter` [2](#0-1) .
- `RpcApiAccessInterceptor.isDisabled(String endpoint)` performs the equivalent check for gRPC method names [3](#0-2) .

However, `FullNodeJsonRpcHttpService` — which registers the `/jsonrpc` servlet (`JsonRpcServlet` → `TronJsonRpcImpl`) — only installs `HttpInterceptor` (a metrics-only filter) and never `HttpApiAccessFilter` or any disabled-API check: [4](#0-3) . `JsonRpcServlet.doPost` dispatches directly into the `TronJsonRpc` implementation with no call to `CommonParameter.getInstance().getDisabledApiList()` anywhere in the request path [5](#0-4) . `TronJsonRpcImpl` exposes Ethereum-style methods (`eth_getBalance`, `eth_getTransactionByHash`, `eth_getBlockByNumber`, `eth_call`, etc.) that are functionally equivalent to Wallet HTTP/gRPC methods such as `getaccount`, `gettransactionbyid`, `getnowblock`, and `triggerconstantcontract`.

This is structurally the same bug class as CVE-2018-6835: Etherpad Lite's `apicalls.js` enforced access restriction on one request path (regular JSON POST/API calls) but the alternate JSONP delivery mechanism for the same functionality was not covered by the same check, letting an attacker reach restricted data through the uncovered code path. Here, an operator's `disabledApiList` restriction covers the HTTP wallet servlets and gRPC, but the JSON-RPC servlet — an entirely separate, unprivileged, publicly reachable request path exposing overlapping functionality — has no equivalent gate, so the restriction can be trivially bypassed by simply calling the JSON-RPC equivalent method instead of the disabled HTTP/gRPC one.

### Impact Explanation
Operators use `disabledApiList` as a security control, e.g. to shut off account/transaction lookup APIs for privacy/compliance reasons, or to prevent DoS-prone or unsupported methods (`triggerconstantcontract`, `estimateenergy`) from being invoked. Because JSON-RPC is unaffected, any unprivileged remote caller can bypass the operator's intended restriction and continue to query or execute the "disabled" functionality (e.g., account balances/details, transaction data, calling contracts read-only) via the corresponding `eth_*` JSON-RPC method. This is an access-restriction bypass exposing data/functionality the node operator explicitly intended to block — matching the "unauthorized... API the node can no longer serve [as configured]" impact class.

### Likelihood Explanation
High: `node.jsonrpc.httpFullNodeEnable` (JSON-RPC) is enabled by default in most fullnode deployments alongside the standard Wallet HTTP API, and the bypass requires nothing more than sending a normal JSON-RPC request to `/jsonrpc` — no authentication, no special crafting, and no dependency on p2p, malicious SR/witness, or any privileged access.

### Recommendation
Add an equivalent disabled-API check to the JSON-RPC request path: either add an `HttpApiAccessFilter`-style filter (mapping JSON-RPC method names to the same `disabledApiList` semantics) to `FullNodeJsonRpcHttpService.addFilter`, or add an explicit disabled-method check inside `JsonRpcServlet`/`TronJsonRpcImpl` before dispatching to `TronJsonRpc`, keyed on the JSON-RPC method name mapped to its equivalent Wallet API name.

### Proof of Concept
1. Configure the node with `node.http.disabledApiList = ["getaccount"]` (or similar) and confirm `GET /wallet/getaccount` on the HTTP API returns `{"Error":"this API is unavailable due to config"}` as validated by the existing test [6](#0-5) .
2. With the same configuration and node enabled with `node.jsonrpc.httpFullNodeEnable = true`, send a JSON-RPC request to `/jsonrpc`:
   ```
   POST /jsonrpc
   {"jsonrpc":"2.0","method":"eth_getBalance","params":["0x...","latest"],"id":1}
   ```
3. Observe that the request succeeds and returns account data, because `FullNodeJsonRpcHttpService`/`JsonRpcServlet` never consult `CommonParameter.getDisabledApiList()`, confirming the disabled-API restriction is bypassed entirely via the JSON-RPC endpoint.

  @Override
  public <ReqT, RespT> Listener<ReqT> interceptCall(ServerCall<ReqT, RespT> call,
      Metadata headers,
      ServerCallHandler<ReqT, RespT> next) {

    String endpoint = call.getMethodDescriptor().getFullMethodName();

    try {
      if (isDisabled(endpoint)) {
        call.close(Status.UNAVAILABLE
            .withDescription("this API is unavailable due to config"), headers);
        return new ServerCall.Listener<ReqT>() {};

      } else {
        return next.startCall(call, headers);
      }
    } catch (Exception e) {
      logger.error("check rpc api access Error: {}", e.getMessage());
      return next.startCall(call, headers);
    }
  }

  @Override
  protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws IOException {
    CommonParameter parameter = CommonParameter.getInstance();

    // Transport IOException from readBody propagates as HTTP 500 (genuine IO failure).
    byte[] body = readBody(req.getInputStream());
    JsonNode rootNode;
    try {
      rootNode = MAPPER.readTree(body);
      if (rootNode == null || rootNode.isMissingNode()) {
        writeJsonRpcError(resp, JsonRpcError.PARSE_ERROR, "JSON parse error", null, false);
        return;
      }
    } catch (JsonProcessingException e) {
      if (e instanceof StreamConstraintsException) {
        writeJsonRpcError(resp, JsonRpcError.PARSE_ERROR, e.getMessage(), null, false);
      } else {
        writeJsonRpcError(resp, JsonRpcError.PARSE_ERROR, "JSON parse error", null, false);
      }
      return;
    }

    if (!rootNode.isObject() && !rootNode.isArray()) {
      writeJsonRpcError(resp, JsonRpcError.INVALID_REQUEST, "Invalid Request", null, false);
      return;
    }

    boolean isBatch = rootNode.isArray();
    if (isBatch && rootNode.isEmpty()) {
      writeJsonRpcError(resp, JsonRpcError.INVALID_REQUEST, "Invalid Request", null, false);
      return;
    }
    int batchSize = parameter.getJsonRpcMaxBatchSize();
    if (isBatch && batchSize > 0 && rootNode.size() > batchSize) {
      writeJsonRpcError(resp, JsonRpcError.EXCEED_LIMIT,
          "Batch size " + rootNode.size() + " exceeds the limit of " + batchSize, null, true);
      return;
    }

    int maxResponseSize = parameter.getJsonRpcMaxResponseSize();
    if (isBatch) {
      handleBatch(resp, rootNode, maxResponseSize);
    } else {
      handleSingle(req, resp, rootNode, body, maxResponseSize);
    }
  }

            response);
