## Title
Unauthenticated `RelayFromAddr` in `NebulaControl_CreateRelayRequest` allows relay/hostmap state poisoning without certificate verification - (File: `relay_manager.go`)

### Summary
`relayManager.handleCreateRelayRequest` uses the attacker-controlled `RelayFromAddr`/`RelayToAddr` fields taken directly from the received `NebulaControl` protobuf message to build relay state (`AddRelay`), rather than validating them against the actual, certificate-verified VPN address of the sending peer (`h.vpnAddrs`). This mirrors the reported bug class: a message field that drives a security-relevant state change is trusted as-is instead of being cross-checked against the value that should actually govern it (there, `debtOut`; here, the authenticated `h.vpnAddrs`).

### Finding Description
`HandleControlMsg` unmarshals the incoming `NebulaControl` message and only checks that `RelayFromAddr`/`RelayToAddr` are non-nil before dispatching: [1](#0-0) 

`handleCreateRelayRequest` then derives `from` and `target` purely from the message body: [2](#0-1) 

When the declared `target` happens to match one of *my* VPN addresses, the code installs relay state keyed by `from` — the value the peer supplied in the packet — associated with `h`, the `HostInfo` of the actual Noise-authenticated connection: [3](#0-2) 

Nowhere in this path is `from` checked against `h.vpnAddrs[0]` (the VPN address that was actually verified during the handshake via the peer's certificate, e.g. in `beginHandshake`/`continueHandshake`): [4](#0-3) [5](#0-4) 

By contrast, other parts of the codebase are careful to enforce this binding — e.g. the lighthouse's `handleHostUpdateNotification` explicitly checks that a self-reported VPN address is contained in the authenticated `fromVpnAddrs` before trusting it: [6](#0-5) 

No equivalent check exists for `RelayFromAddr` in `handleCreateRelayRequest`, so a fully-authenticated but malicious peer (its own valid certificate, no CA compromise needed) can claim to be relaying "from" an arbitrary victim VPN address it does not own. This is the direct analog of the SwapFacility bug: the attacker supplies a legitimate "credential" for one part of the transaction (a real, CA-signed handshake / real collateral) but manipulates an unchecked auxiliary parameter (`RelayFromAddr` / `sendParam.amountLD`) that the receiving logic uses to take a further, more consequential action (installing relay/hostmap state / minting tokens) without validating it against the value that was actually authenticated (`h.vpnAddrs` / `debtOut`).

### Impact Explanation
This lets an authenticated-but-malicious peer poison the receiver's relay/hostmap state: it can register itself (its own live connection `h`) as a `Terminal` relay entry for a VPN address it does not control, or manipulate `RelayToAddr`/`RelayFromAddr` combinations to steer how the victim's traffic is relayed. Since relay state is later consulted to route encrypted traffic (`SendVia`, `QueryVpnAddrsRelayFor`), this can enable remote hostmap/relay state poisoning and potential traffic misdirection toward an attacker-controlled path — without needing to compromise the CA or hold a certificate for the victim's address. This fits the "hostmap/lighthouse/relay address trust" analog class explicitly permitted by scope.

### Likelihood Explanation
Any peer that can complete a normal (CA-signed) handshake with the target — i.e., any legitimate but malicious network member — can send a `Control`/`CreateRelayRequest` message with forged `RelayFromAddr`/`RelayToAddr` fields; no special privilege beyond a valid certificate is required, and the check present in the code only guards against nil fields, not against mismatched identity.

### Recommendation
In `handleCreateRelayRequest` (and `handleCreateRelayResponse`/`EstablishRelay` where applicable), validate that `from` (`RelayFromAddr`) corresponds to an address actually present in the requesting peer's verified `h.vpnAddrs`/certificate networks (analogous to the lighthouse's `slices.Contains(fromVpnAddrs, detailsVpnAddr)` check) before using it to install or update relay state, rather than trusting the value taken from the wire message.

### Proof of Concept
Conceptual PoC (not run against the live repo, since this is a static-analysis analog finding):
1. Attacker `evil` establishes a normal, CA-signed Nebula tunnel to `me` (the potential relay/terminal node).
2. Attacker sends a `Control` message of type `NebulaControl_CreateRelayRequest` with `RelayToAddr` = `me`'s own VPN address (so `f.myVpnAddrsTable.Contains(target)` is true) and `RelayFromAddr` = `victim`'s VPN address (which `evil` does not own and has no certificate for).
3. `me.handleCreateRelayRequest` sees `target == me`, and since `h.relayState.QueryRelayForByIp(from)` finds nothing, calls `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)` — installing relay state on `h` (the attacker's authenticated hostinfo) keyed by `victim`'s address, with no check that `from` is in `h.vpnAddrs`.
4. `me` now believes it has an established relay path "for `victim`" through the attacker's connection, corrupting relay/hostmap state that other logic (`SendVia`, `QueryVpnAddrsRelayFor`) relies on for routing decisions.

Note: I was unable to fully trace how this poisoned relay entry is subsequently consumed for actual traffic forwarding (`outside.go`'s `MessageRelay` handling and `hostmap.go`'s `QueryVpnAddrsRelayFor`) within the available iterations, so the exact downstream traffic-redirection/DoS impact should be independently confirmed by a Devin session with full repo access.
