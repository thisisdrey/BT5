### Title
Deleting an account leaves its `PromiseYieldReceipt`/`PromiseYieldStatus` in state, letting a parked self-callback (e.g. `DeployContract`) execute against a later-recreated account of the same name - (File: `core/store/src/utils/mod.rs`)

### Summary
`remove_account` (core/store/src/utils/mod.rs:504-575) deletes the `Account`, `ContractCode`, access/gas keys and contract data, but never removes `TrieKey::PromiseYieldReceipt` or `TrieKey::PromiseYieldStatus` entries for the account. A self-targeted `promise_yield_create` receipt (whose action list can include arbitrary self actions such as `DeployContract`) that is never resumed survives account deletion, and `resolve_promise_yield_timeouts` (runtime/runtime/src/lib.rs:3009-3116) still finds it live via `state_update.contains_key(&promise_yield_key)`, synthesizes a `PromiseResume(data: None)` and executes the original action list against whatever account currently exists under that account id.

### Finding Description
`promise_yield_create` (runtime/runtime/src/ext.rs:353-369, host fn at runtime/near-vm-runner/src/logic/logic.rs:3660) creates a receipt targeted at `self.context.current_account_id` and writes `PromiseYieldStatus::Yielded` via `set_promise_yield_status`. Because `PromiseYield` receipts are instant receipts (`core/primitives/src/receipt.rs:474`), the receipt content (an `ActionReceipt` whose action list the caller controls via subsequent `promise_batch_action_*` calls on the same promise index, e.g. appending `Action::DeployContract(malicious_code)`) is stored immediately via `set_promise_yield_receipt` (core/store/src/utils/mod.rs:200-212, called at runtime/runtime/src/lib.rs:1498), keyed only by `(receiver_id, data_id)`.

`DeleteAccount` is also an instant receipt when it is the sole action (`core/primitives/src/receipt.rs:481-486`). `action_delete_account` (runtime/runtime/src/actions.rs:314-390) calls `remove_account` (:371), which removes `Account`, `ContractCode`, access keys/gas keys and contract data (core/store/src/utils/mod.rs:504-575) but does **not** touch `TrieKey::PromiseYieldReceipt` or `TrieKey::PromiseYieldStatus`, nor the `PromiseYieldTimeout` queue entry that was enqueued at yield-create time.

Later, once any party (including the victim) recreates an account with the same account id, `resolve_promise_yield_timeouts` runs each chunk (runtime/runtime/src/lib.rs:3009-3116). It walks the still-present `PromiseYieldTimeout` queue entry for `expires_at <= block_height`, checks `state_update.contains_key(&promise_yield_key)` (still true, since it was never removed), and forwards a synthetic `PromiseResume { data_id, data: None }` to the same account id. When that resume is processed (runtime/runtime/src/lib.rs:1500-1562), the runtime fetches the parked `Receipt` via `get_promise_yield_receipt`, removes the yield bookkeeping, and executes the stored action list via `apply_action_receipt` — against the account object that currently exists at that account id, i.e. the victim's freshly created account, not the account that existed when the yield was created.

The root authorization defect: privileged, self-only actions such as `DeployContract` are permitted in the delayed/parked receipt because `predecessor_id == receiver_id` (both equal the account-id string) at receipt-creation time. That "self" check is based purely on account-id string equality, not on the identity/version of the account object. `remove_account`'s failure to purge promise-yield state means this stale authorization is later replayed against an unrelated account object that happens to reuse the same id, with no re-validation of ownership or consent by the new account holder.

### Impact Explanation
This is an authorization-escalation and contract-hijack bug: an attacker who fully controls account X can plant a `DeployContract(malicious_code)` (or other privileged self-actions, e.g. adding a full-access key, transferring the account's future balance, etc.) action inside a parked promise-yield receipt, delete X, and have the payload silently detonate against whoever recreates the account X later — deploying attacker-chosen code (or granting attacker-chosen keys) into the victim's account without the victim's consent. This matches the "authorization escalation across accounts" and "contract-hijack / theft of funds routed through victim's account" bounty categories, since any funds subsequently sent to or held by the victim's account can be diverted via the malicious code.

### Likelihood Explanation
Preconditions are fully within attacker control and require no privileged role: an ordinary funded account, a deployed contract able to call `promise_yield_create` plus `promise_batch_action_deploy_contract` on the resulting promise index, and a standard `DeleteAccount` action, followed by waiting `yield_timeout_length_in_blocks` for the timeout to fire. Recreation of account X under the same name by a third party is required for the exploit to have victim impact; this is a normal, permissionless action on NEAR (accounts can always be re-registered once deleted). Cost to the attacker is limited to normal gas/storage costs of the yield-create and delete transactions; the attack is fully repeatable for any account name the attacker controls and later abandons/deletes.

### Recommendation
`remove_account` should also enumerate and remove any `TrieKey::PromiseYieldReceipt` / `TrieKey::PromiseYieldStatus` entries (and associated yield-id mappings) for the account being deleted, and/or `resolve_promise_yield_timeouts`/the resume-processing path should validate that the parked receipt's target account has not been deleted and recreated since the yield was created (e.g., by tying the yield to an account-creation nonce/epoch, or by refusing to execute an action receipt whose privileged self-actions no longer correspond to the account's original identity). Alternatively, disallow `DeleteAccount` while any `PromiseYieldReceipt`/timeout entries for that account are still outstanding.

### Proof of Concept
Test-loop integration test plan:
1. Deploy a contract to account `test0` that exposes a method calling `promise_yield_create` targeting itself with a callback method name, then `promise_batch_action_deploy_contract(promise_idx, MALICIOUS_WASM)` on the returned promise index, and never calls `promise_yield_resume`.
2. In the same or a following transaction, submit `DeleteAccountAction` for `test0` (beneficiary = attacker-controlled account).
3. Submit a `CreateAccount` transaction from a third "victim" signer to recreate `test0` (deploy victim's own legitimate contract/code and add victim's own access key).
4. Advance the chain via `run_until_executed_height` past `yield_timeout_height()` (block height `expires_at`), as done in `test-loop-tests/src/tests/yield_timeouts.rs`.
5. Assert that `resolve_promise_yield_timeouts` produced a `PromiseResume` and that the resulting execution deployed `MALICIOUS_WASM` (`account.code_hash()` / `account.contract()` on the recreated `test0` equals the malicious code hash), and that the `TrieKey::PromiseYieldReceipt` / `TrieKey::PromiseYieldStatus` entries for `test0` were present in state immediately after step 2 (i.e., not removed by `remove_account`) using `get(state_update, &TrieKey::PromiseYieldStatus{...})`/`get_promise_yield_receipt`.
