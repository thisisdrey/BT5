### Title
Access-key recreation nonce reset allows replay/double-execution of an already-executed transaction within the same chunk-apply height - ([File: runtime/runtime/src/access_keys.rs], [File: runtime/runtime/src/verifier.rs])

### Summary
`add_regular_key` reseeds a recreated access key's nonce to `initial_nonce_value(block_height) = (block_height-1) * 1_000_000` regardless of the key's prior nonce, and this reset happens via receipt processing which always runs *after* transaction processing within the same `Runtime::apply` call. If a transaction using a nonce close to the current height's upper bound executes and is charged in the transaction phase, and a `DeleteKey`+`AddKey` (recreating the same public key) lands as a receipt in the same chunk's receipt phase, the key's stored nonce is rolled back below the already-consumed nonce. The attacker can then resubmit the identical, already-executed `SignedTransaction` in a later block and have it pass `verify_nonce` again, causing the runtime to execute it a second time.

### Finding Description
`verify_nonce` (`runtime/runtime/src/verifier.rs:211-237`) only rejects a nonce that is `<= current_nonce` (Monotonic mode) or not `current_nonce+1` (Strict mode), plus an absolute upper bound `tx_nonce < block_height * 1_000_000`. It has no knowledge of "nonces already consumed"; it only compares against whatever nonce value is currently stored on the `AccessKey`.

`add_regular_key` (`runtime/runtime/src/access_keys.rs:230-255`), invoked whenever `action_add_key` recreates a key with the same public key after a prior `action_delete_key` (`runtime/runtime/src/access_keys.rs:52-91`, `:136-147`), unconditionally overwrites the nonce:
```
access_key.nonce = initial_nonce_value(block_height);
```
where `initial_nonce_value(H) = (H-1) * 1_000_000` (`runtime/runtime/src/access_keys.rs:46-49`). This design intentionally uses the *current* block height to stay ahead of nonces that could have been used at *earlier* heights (per the `#3779` rationale documented on `AccessKey::nonce`), and that holds as long as the recreation happens at a strictly later height than the transaction that used the old nonce, since `(H'-1)*1e6 >= H*1e6` for any `H' > H`.

The invariant breaks when recreation happens at the **same** height `H` as the transaction that used the key. `Runtime::apply` always processes all transactions of a chunk (`process_transactions`, `runtime/runtime/src/lib.rs:1862`) *before* processing any receipts of that same chunk (`process_receipts` → `process_local_receipts` → `process_delayed_receipts` → `process_incoming_receipts`, `runtime/runtime/src/lib.rs:1864-1866`, `:2694-2715`). This ordering is fixed and identical for every node validating the chunk (not a source of divergence), but it does mean:

1. Attacker signs `Tx_A` with public key `P` and a nonce `N_A` chosen close to the top of the currently valid range, i.e. `N_A ∈ [(H-1)*1_000_000, H*1_000_000)`, targeting height `H`.
2. Attacker also submits `Tx_B`, signed with a *different* access key on the same account, whose actions are `DeleteKey(P)` then `AddKey(P, ...)` (self-targeted, so it becomes a *local* receipt).
3. Both land in the chunk at height `H`. In the transaction phase, `Tx_A` is verified/charged via `verify_and_charge_tx_ephemeral` (`runtime/runtime/src/verifier.rs:269-361`), which succeeds and durably commits `access_key.nonce = N_A` for key `P`.
4. In the receipt phase (same `apply` call, same height `H`), `Tx_B`'s local receipt runs `action_delete_key` then `action_add_key` on key `P`, resetting its nonce to `(H-1)*1_000_000`, which is **less than** `N_A`.
5. At any later height, the attacker resubmits the exact same `Tx_A` bytes. `verify_nonce` compares `N_A` against the now-reset, lower stored nonce and passes, so `Tx_A` executes a second time.

No existing check stops this: nonce validation only looks at the currently stored value, the `UniqueChunkTransactions` duplicate-hash guard only dedupes within a single chunk (`runtime/runtime/src/lib.rs:2031-2042`), and there is no persistent "highest nonce ever seen" independent of the `AccessKey` record that survives delete+recreate.

### Impact Explanation
This is a double-spend/replay of a transaction the protocol's nonce mechanism is specifically documented to prevent (`AccessKey::nonce` docs and `runtime/runtime/src/access_keys.rs:46-49`, referencing near/nearcore#3779, exist precisely to block this class of replay). Any logic that assumes "a signed transaction, once executed, cannot be validly re-included" (this is exactly nonce monotonicity's purpose) is violated: the same signed payload runs twice, causing double execution of its actions (e.g. duplicate `FunctionCall`s, duplicate `Transfer`s/receipts) against a receiver that trusted this invariant. This maps to the "double-spend/replay" bounty category.

### Likelihood Explanation
The attacker needs only an ordinary account they control: two access keys on that account, ability to choose transaction nonces (fully attacker-controlled within the valid range), and the ability to get two of their own transactions included in the same chunk at the same height — all achievable by an unprivileged user submitting transactions to RPC, with no validator/chunk-producer cooperation required. The only non-trivial part is landing `Tx_A` and `Tx_B` in the same chunk, which is a timing/luck factor but repeatable by retrying across blocks (attacker's own txs, no third party needed).

### Recommendation
When recreating an access key with the same public key, do not blindly reset the nonce based on the current block height; instead take `max(old_nonce, initial_nonce_value(block_height))`, or persist a monotonic "last-seen nonce" for a given `(account_id, public_key)` pair independent of key deletion so it can't be lowered by delete+recreate within the same height, especially when the recreation is a receipt applied later in the same chunk that already saw a transaction against that key.

### Proof of Concept
Integration test (pattern following `runtime/runtime/src/tests/apply.rs`):
1. Set up an account `alice` with two full-access keys `P` and `Q` on the same shard/trie.
2. Call `runtime.apply(...)` at height `H` with `SignedValidPeriodTransactions` containing:
   - `Tx_A`: signed with `P`, nonce `= H*1_000_000 - 1`, a `Transfer`/`FunctionCall` action with an observable side effect (e.g. increments a counter on a helper contract or transfers to `bob`).
   - `Tx_B`: signed with `Q`, actions `[DeleteKey(P), AddKey(P, AccessKey::full_access())]`, receiver `= alice` (local receipt).
3. Assert both `Tx_A`'s outcome and the DeleteKey/AddKey local receipt outcome are `Success`.
4. Read back `AccessKey` for `(alice, P)` from the resulting trie root; assert `nonce == (H-1)*1_000_000`, confirming it is now below `Tx_A`'s nonce.
5. Commit the trie changes, advance to height `H+1`, and call `runtime.apply(...)` again passing the **same** `Tx_A` (same bytes/hash) as the sole transaction.
6. Assert the outcome is `Success` again (i.e. `verify_nonce` did not reject it) and assert the observable side effect (counter/balance) changed a second time — demonstrating double execution of a transaction that nonce monotonicity is supposed to make impossible to re-include. pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}
