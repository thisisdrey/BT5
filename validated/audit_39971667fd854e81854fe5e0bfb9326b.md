### Title
Node acknowledges/advertises a StackerDB chunk as stored before it is actually persisted, allowing forged/false inventory to be relayed on the strength of an unpersisted write - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary

### Finding Description
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` validates an incoming pushed chunk with `validate_received_chunk` (checks size, expected version, signer signature via `SlotMetadata::verify`, staleness, and max-writes), and then immediately mutates the *reply* inventory in memory: [1](#0-0) 

Specifically, `*slot_version = chunk_data.chunk_data.slot_version;` patches the `StackerDBChunkInvData` that will be sent back to the peer as an acknowledgment, and the function returns `(false, true)` — i.e., "don't buffer, forward to relayer" — without itself calling `try_replace_chunk`/`insert_chunk` against `StackerDBs` here. The actual on-disk write via `StackerDBTx::try_replace_chunk` / `insert_chunk` happens later, driven by the relayer, at: [2](#0-1) 

This breaks the equality that should hold between "advertised inventory version" (what the node tells peers it now has) and "actually persisted chunk version" (what is in `StackerDBs`). The ack/inventory reply is signed and sent back to the origin peer at: [3](#0-2) 

before the relayer has necessarily completed the corresponding `try_replace_chunk` call. This is directly analogous to the `FeeSplitter.onBalanceChange` bug class: an accounting/state field (`userFeeOffset` in the analog, `slot_versions` inventory here) is updated to reflect a transition that has not yet been durably completed/settled, so a reader relying on that field (a claimant in the analog, a peer relying on inventory here) observes a state that does not match the true underlying ledger. If the deferred `try_replace_chunk` subsequently fails (e.g. concurrent write from another source bumps the version past this one, hitting `StaleChunk`, or the relayer thread errors/panics/is delayed under load) the node has already told the network it has slot_version N, while its actual on-disk `SlotValidation.version` is stale. Peers that trust this advertised inventory (e.g. `StackerDBSync`'s download scheduler, which prioritizes "newest-first, rarest-first" per the inventory) will treat this node as an authoritative source for a chunk it does not actually hold, and any subsequent `StackerDBGetChunk` from them will be answered with stale/absent data — i.e. non-canonical (unwritten) state momentarily served as canonical via the inventory channel.

### Impact Explanation
This falls under "serving non-canonical state as canonical" / "steering a node off the tip via false inventory" (High), because a remote, unauthenticated peer can push a chunk that passes signature/version checks and, due to the ack being computed from validation success rather than actual storage success, cause the node to broadcast/acknowledge inventory that does not match its persisted `chunks` table. Downstream StackerDB sync consumers (signer message relay, `.miners` contract, block proposal/signature StackerDBs used by the Nakamoto mining path — see `SignerCoordinator::send_miners_message`) depend on inventory accuracy to schedule chunk downloads; false inventory can create download stalls or repeated round-trips as peers attempt to fetch a chunk this node claims to have but does not yet (or ever) actually store.

### Likelihood Explanation
The path is remote, unauthenticated, and reachable by any peer able to send an unsolicited `StackerDBPushChunk` p2p message. Triggering the race requires only that the deferred relay-driven store (`try_replace_chunk`) fail or lag after the ack/inventory patch has already been computed and sent — plausible under contention (e.g., a competing valid write for the same slot arriving concurrently and winning the DB update, or relayer backpressure), making this a timing-dependent but realistically reachable inconsistency rather than a purely theoretical one. I was not able to fully trace the exact relayer code path that performs the deferred `try_replace_chunk` call (searches for it in `stackslib/src/net/relay.rs` / `unsolicited.rs` were inconclusive within available iterations), so the precise failure window between ack and persistence should be confirmed by a Devin session with full repo access.

### Recommendation
Only patch/send the inventory acknowledgment after the chunk has been durably written via `StackerDBTx::try_replace_chunk`/`commit()`, mirroring the `poststackerdbchunk.rs` HTTP path which loads slot metadata and commits before constructing the `StackerDBChunkAckData`: [4](#0-3) 
For the p2p unsolicited push path, either perform the `try_replace_chunk` write synchronously inside `handle_unsolicited_StackerDBPushChunk` before patching `slot_versions`/sending the ack, or defer sending the ack/inventory reply until the relayer confirms the write succeeded.

### Proof of Concept
Not independently reproducible from the index alone (would require running the relayer/StackerDB storage race in an integration harness); the code-level root cause — inventory patched and ack sent prior to confirmed persistence — is shown at [5](#0-4)  combined with the deferred, separate persistence path at [6](#0-5) . Confirming an actual exploitable window (i.e., a reliable failure/race scenario) requires further investigation with full build/test access, which is recommended via a Devin session.

    /// It must be authenticated, and its lamport clock must be higher than the one that's already
    /// there.  These will not be checked.
    fn insert_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        let stackerdb_id = self.get_stackerdb_id(smart_contract)?;
        let sql = "UPDATE chunks SET version = ?1, data_hash = ?2, signature = ?3, data = ?4, write_time = ?5 WHERE stackerdb_id = ?6 AND slot_id = ?7";
        let mut stmt = self.sql_tx.prepare(sql)?;

        let args = params![
            slot_desc.slot_version,
            Sha512Trunc256Sum::from_data(chunk),
            slot_desc.signature,
            chunk,
            u64_to_sql(get_epoch_time_secs())?,
            stackerdb_id,
            slot_desc.slot_id,
        ];

        stmt.execute(args)?;
        Ok(())
    }

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
