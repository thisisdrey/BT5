### Title
ETH-implicit wallet contract can be permanently bricked (funds frozen forever) via `has_in_flight_tx` reset that is rolled back on out-of-gas / panic in a callback - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` used to control ETH-implicit accounts guards concurrent execution with an in-memory flag `has_in_flight_tx`, set to `true` before dispatching a promise chain and reset to `false` at the very start of the resolving callback (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`). [1](#0-0)  If the callback receipt fails (e.g. runs out of the statically-reserved gas, or panics for any other reason) *after* entering the function but before it returns successfully, all state mutations performed in that receipt — including the earlier `self.has_in_flight_tx = false` — are rolled back, because Near contract execution only commits state on success. This leaves `has_in_flight_tx == true` permanently, since only the contract itself can ever call these `#[private]` callbacks, and there is no external way to reset the flag.

### Finding Description
`rlp_execute` refuses to start a new transaction whenever `has_in_flight_tx` is `true`:
```
if self.has_in_flight_tx {
    return PromiseOrValue::Value(ExecuteResponse { success: false, ... "transaction already in progress" ... });
}
``` [2](#0-1) 

Every path that dispatches a promise sets `has_in_flight_tx = true` before returning the promise, and relies exclusively on a follow-up private callback to set it back to `false`:
- `address_check_callback`, `nep_141_storage_balance_callback`, and `rlp_execute_callback` each begin execution with `self.has_in_flight_tx = false;` as their very first statement. [3](#0-2) [4](#0-3) [5](#0-4) 

For NEAR contracts, state mutations performed by a function-call action are only persisted if the receipt succeeds; if the WASM execution of that receipt exhausts its gas (or panics for any other reason) partway through, the entire receipt fails and its state changes — including the assignment that already ran at the top of the function — are rolled back (`apply_action_receipt`/`state_update.rollback()` on failure). [6](#0-5)  The gas allotted to each of these callbacks is a small, fixed constant computed at dispatch time (e.g. `RLP_EXECUTE_CALLBACK_GAS = 5 Tgas`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`), chained together with `.with_static_gas(...)` and `.saturating_add(action.gas())`. [7](#0-6)  Because `action.gas()` and the size/complexity of the cross-contract response (e.g. an oversized or unusually shaped JSON payload from `storage_balance_of` on an attacker-controlled or malicious ERC-20/NEP-141 target contract) are attacker-influenceable, an attacker (or simply an unlucky/adversarial relayer) can cause the callback receipt to run out of gas or otherwise fail after `has_in_flight_tx` would have been reset but before the receipt commits.

Once this happens, `has_in_flight_tx` remains `true` forever. All subsequent calls to `rlp_execute` will be rejected with "transaction already in progress", and there is no other entry point that can reset the flag — the callbacks are `#[private]` (self-only), and per the contract's own design an ETH-implicit account "can only be used by calling the methods of the Wallet Contract. It cannot be deleted, nor can a full access key be added." [8](#0-7)  This permanently freezes any NEAR balance and NEP-141/ERC-20 assets controlled by that ETH-implicit account, with no emergency-withdraw or recovery mechanism.

### Impact Explanation
This is a permanent freezing-of-funds bug analogous to the reported LpWrapper issue: an internal guard state ("in-flight" flag / gauge deposit) that is supposed to be reset by a follow-up step can become irrecoverably stuck if that follow-up step fails due to an external dependency (killed gauge / out-of-gas or malformed external-contract response), and the contract offers no emergency/administrative escape hatch. Here the blast radius is every ETH-implicit account whose owner interacts with a hostile or misbehaving external contract (or an adversarial relayer who can influence gas/response size), and because ETH-implicit accounts cannot add full-access keys or be deleted, the funds are unrecoverable through any other path.

### Likelihood Explanation
Reachable from an ordinary, unprivileged transaction: any wallet owner (or a relayer acting on their behalf) simply calling `rlp_execute` to interact with an ERC-20/NEP-141 contract triggers the `nep_141_storage_balance_callback`/`rlp_execute_callback` chain. An attacker who controls or influences the target token contract's `storage_balance_of` response size, or who can influence the gas budget of the relayed Ethereum transaction, can push the callback receipt into an out-of-gas failure. No validator or protocol-level privilege is required.

### Recommendation
- Reset `has_in_flight_tx` in a way that is robust to callback failure — e.g., use `#[near_bindgen(finalize)]`-style guaranteed-cleanup pattern, or reserve enough gas headroom that the flag write always completes even in a callback failure path (a minimal "always-succeeds" trailing action/receipt dedicated solely to clearing the flag, scheduled to run regardless of the primary callback's success).
- Add an explicit, permissionless (or at least owner-controlled) "force-unlock"/"cancel in-flight transaction" method that can clear `has_in_flight_tx` after a timeout or once all associated receipts have resolved, so a stuck flag cannot permanently brick the account.
- Bound/validate the size of external cross-contract responses (e.g., `storage_balance_of`) before deserializing, and ensure gas reservations account for worst-case response sizes so parsing cannot itself trigger the out-of-gas condition.

### Proof of Concept
1. Deploy (or have an attacker deploy) a NEP-141 token contract whose `storage_balance_of` method returns an oversized/adversarially-shaped JSON payload (still valid enough to be routed to the `PromiseResult::Successful` branch) sized so that decoding it inside `nep_141_storage_balance_callback` consumes gas beyond `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`.
2. From the target ETH-implicit wallet, submit (via `rlp_execute`) an ERC-20 `transfer` call whose `to` is unregistered with that token, causing the flow: `rlp_execute` → `storage_balance_of` call → `nep_141_storage_balance_callback` (sets `has_in_flight_tx=false`, then dispatches `storage_deposit` + transfer + `rlp_execute_callback`) as in `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:239-269`.
3. Ensure the outer transaction's total attached gas is tight enough that the `nep_141_storage_balance_callback` receipt runs out of gas while deserializing the oversized payload or while building the follow-up promise (before its state changes commit).
4. Because the receipt fails, `has_in_flight_tx` remains `true` in the persisted account state (the earlier reset is rolled back).
5. Any further call to `rlp_execute` on this wallet now unconditionally returns `"Error: transaction already in progress, please try again later."` forever, per `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:97-105`, permanently freezing all NEAR and token balances controlled by the ETH-implicit account.

(Note: I was unable to execute this against a live/local NEAR node with the wallet-contract WASM to empirically confirm the exact gas thresholds at which the callback would run out of gas; this analysis is based on static review of the callback/flag logic and NEAR's documented all-or-nothing receipt state-commit semantics.)
