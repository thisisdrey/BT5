### Title
Firewall conntrack fast-path (`inConns`) allows traffic to bypass CA/certificate revalidation between rule-version bumps - (File: `firewall.go`)

### Summary
The bug report describes a value (`estimatedAPR`/`vestingProfit`) that is cached at one point in time and continues to be trusted after the underlying condition that would invalidate it (vesting completing) changes, because the recompute trigger (`accrue()`) doesn't fire reliably. The closest reachable analog in Nebula is the firewall's conntrack fast path in `firewall.go`, where a flow's "allowed" status is cached in a `conn` struct and only re-validated against the peer certificate/CA pool when the *firewall rule set version* changes — not when the certificate itself becomes invalid (expired/blocklisted).

### Finding Description
`Firewall.Drop` first checks the conntrack fast path via `inConns` before consulting the rule tables: [1](#0-0) 

Inside `inConns`, an existing conntrack entry is trusted as long as its cached `rulesVersion` still matches the firewall's current `rulesVersion`; only on a mismatch does it re-run `table.match(...)` against the live certificate and CA pool: [2](#0-1) 

If the `rulesVersion` has not changed, the entry is refreshed (`c.Expires = time.Now().Add(...)`) and the packet is allowed with **no re-check of certificate validity, expiration, or blocklist status** for the lifetime of the conntrack entry (up to `TCPTimeout`, "5 days max" per the comment): [3](#0-2) [4](#0-3) 

This mirrors the `estimatedAPR()` bug class exactly: a derived/cached authorization decision (`conn` entry created at flow-open time, when the peer cert was valid and matched the rules) is not invalidated when the real-world state that justified it (a valid, non-expired, non-blocklisted certificate) changes, because the only trigger for revalidation is an unrelated event (a rules reload bumping `rulesVersion`), not the certificate's own expiry.

Separately, `connection_manager.go`'s `isInvalidCertificate` does perform periodic certificate revalidation via `caPool.VerifyCachedCertificate` and can tear down the whole tunnel when `disconnectInvalid` is enabled: [5](#0-4) 

However, this is: (1) driven by a separate periodic timer (not per-packet), and (2) gated behind the `pki.disconnect_invalid` config flag — when unset (default false per the else-branch), the code explicitly keeps the tunnel and its conntrack entries open even after the cert is known to be invalid: [6](#0-5) 

So even the coarser tunnel-level defense does not guarantee that per-flow conntrack fast-path decisions in `firewall.go` are re-validated against the certificate's current validity.

### Impact Explanation
An already-established flow's conntrack entry continues to bypass explicit CA/certificate/group rule checks for as long as the entry stays alive and the rule set version doesn't change, even after the remote certificate has expired or been blocklisted. In default configuration (`disconnectInvalid` false), this can allow a peer whose certificate has expired (or was later blocklisted by an admin, e.g. due to key compromise) to continue sending/receiving traffic that was previously permitted, for up to the conntrack timeout window (default TCP timeout can be long). This is a remote-state-poisoning-style issue: a trust decision made at handshake/flow-open time is not re-derived when the fact that justified it (valid, non-revoked cert) becomes false, and the revocation/expiry only takes effect on the next rules reload or (if enabled) the connection manager's periodic tick.

### Likelihood Explanation
This requires a previously-valid, already-connected peer whose certificate later expires or is blocklisted while an active flow's conntrack entry is still cached — a scenario that occurs naturally over the lifetime of any long-lived connection (e.g., a long TCP session) as certificates near their `NotAfter`, or when an operator blocklists a compromised fingerprint expecting reachability to stop. No forged certificate or lighthouse manipulation is needed; it is a property of normal certificate lifecycle combined with the conntrack fast path's revalidation trigger being tied to rule-version changes rather than certificate state.

### Recommendation
Re-validate the association's certificate (expiry + blocklist, via `caPool.VerifyCachedCertificate`) inside `inConns`/`Firewall.Drop` on the fast path, not only when `rulesVersion` changes, or force `evict`/re-check of conntrack entries whenever the peer's certificate state changes (expiry crossed, added to blocklist). Additionally, consider making certificate-based teardown (`isInvalidCertificate`) independent of the `pki.disconnect_invalid` flag for the purposes of conntrack fast-path validity, so that expired/blocklisted certs cannot continue to benefit from previously-established conntrack entries.

### Proof of Concept
1. Two nebula nodes (A, B) complete a handshake and establish a flow that is conntracked and allowed via `table.match` in `Firewall.Drop` at time T0 (cert valid).
2. At T1 > `NotAfter` of B's certificate, B's certificate is expired, but A's firewall `rulesVersion` has not changed and `pki.disconnect_invalid` is false (default).
3. Traffic between A and B on the same 5-tuple continues to hit the `inConns` fast path in `firewall.go`, which only checks `c.rulesVersion != f.rulesVersion` before allowing the packet — it does not call `caPool.VerifyCachedCertificate` on B's now-expired cert.
4. As a result, traffic keeps flowing on the existing conntrack entry despite B's certificate being expired, until the conntrack entry naturally times out (`TCPTimeout`/`UDPTimeout`/`DefaultTimeout`) or the rule set is reloaded.

Note: I was unable to fully trace the exact CA-name/CA-SHA/group matching internals (`firewallPort.match`) within the available index to confirm whether `table.match` itself performs an expiry check separate from `caPool.VerifyCertificate`/`VerifyCachedCertificate` at flow-open time; this doesn't affect the core finding, which is that `inConns`'s fast path explicitly skips calling `table.match` (and thus any such check) unless `rulesVersion` differs.

// isInvalidCertificate decides if we should destroy a tunnel.
// returns true if pki.disconnect_invalid is true and the certificate is no longer valid.
// Blocklisted certificates will skip the pki.disconnect_invalid check and return true.
func (cm *connectionManager) isInvalidCertificate(now time.Time, hostinfo *HostInfo) bool {
	remoteCert := hostinfo.GetCert()
	if remoteCert == nil {
		return false //don't tear down tunnels for handshakes in progress
	}

	caPool := cm.intf.pki.GetCAPool()
	err := caPool.VerifyCachedCertificate(now, remoteCert)
	if err == nil {
		return false //cert is still valid! yay!
	} else if err == cert.ErrBlockListed { //avoiding errors.Is for speed
		// Block listed certificates should always be disconnected
		hostinfo.logger(cm.l).Info("Remote certificate is blocked, tearing down the tunnel",
			"error", err,
			"fingerprint", remoteCert.Fingerprint,
		)
		return true
	} else if cm.intf.disconnectInvalid.Load() {
		hostinfo.logger(cm.l).Info("Remote certificate is no longer valid, tearing down the tunnel",
			"error", err,
			"fingerprint", remoteCert.Fingerprint,
		)
		return true
	} else {
		//if we reach here, the cert is no longer valid, but we're configured to keep tunnels from now-invalid certs open
		return false
	}
}
