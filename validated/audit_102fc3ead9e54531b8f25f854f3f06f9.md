### Title
Unbounded array allocation from attacker-controlled length in TVM precompile signature-array decoders - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts decode signature/address arrays from raw call data using `extractBytesArray`, `extractBytes32Array`, and `extractSigArray`. Each of these helpers reads an array length directly from attacker-controlled call data and immediately allocates a Java array/nested array of that size (`new byte[len][]`) **before** any size-cap check runs, mirroring the kin-openapi pattern of materializing an attacker-sized collection before validation (`maxItems`/`MAX_SIZE`) can reject it. The `MAX_SIZE` bound is only enforced when the `allowTvmSelfdestructRestriction()` hard-fork flag is active; the un-gated legacy code path performs no bound check at all prior to allocation.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` all compute `len` from a `DataWord` taken straight out of the precompile's input `data`, then allocate accordingly with no upper bound: [1](#0-0) [2](#0-1) [3](#0-2) 

In `BatchValidateSign.doExecute`, the `MAX_SIZE` (16) cap on `sigArraySize`/`addrArraySize` is only checked when `VMConfig.allowTvmSelfdestructRestriction()` is true; when that flag is not active, `extractBytesArray`/`extractBytes32Array` are invoked directly with the attacker-controlled length and no prior bound check: [4](#0-3) 

`ValidateMultiSign.execute` has the identical pattern (`MAX_SIZE` = 5), gated the same way: [5](#0-4) 

Exactly as in the kin-openapi report — where `sliceMapToSlice` reads an attacker-supplied index and allocates `0..max` slots before `maxItems` validation ever runs — here the array length is read from call data and used to size `new byte[len][]` before the `MAX_SIZE` cap is applied, on any code path where the `allowTvmSelfdestructRestriction` chain parameter/hard-fork toggle is not enabled.

### Impact Explanation
Any account that can send a `TriggerSmartContract`/`TriggerConstantContract` transaction invoking the `ValidateMultiSign` or `BatchValidateSign` precompile addresses (a completely permissionless, unauthenticated operation reachable by any contract caller) can supply a crafted `data` payload whose length word is a huge integer. This forces the node executing/validating that transaction to allocate a correspondingly huge array before any cap check occurs, on any deployment/network state where `allowTvmSelfdestructRestriction()` returns false for the un-gated legacy path. This is a resource-exhaustion / node-crash primitive (OOM), matching CWE-400/CWE-789, and would be triggered by every full node that validates the transaction (or by constant-call/query serving nodes), since bandwidth/energy metering for this call is based on data length, not on the decoded array size.

### Likelihood Explanation
Reachability requires only a standard, unprivileged smart-contract call — no special permissions, no malicious spec authoring, and no state beyond normal TVM execution. The only mitigating factor is whether `allowTvmSelfdestructRestriction()` is active for the target chain; on any network/testnet/fork where that hard-fork parameter has not been activated, the un-gated legacy path in both precompiles is fully exposed with no length bound whatsoever before allocation.

### Recommendation
Move the `MAX_SIZE` bound check inside `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` themselves (or immediately before allocation) unconditionally, rather than gating it behind `VMConfig.allowTvmSelfdestructRestriction()`, so the array length is always validated before `new byte[len][]` is executed on any code path.

### Proof of Concept
1. Deploy/call the `ValidateMultiSign` (or `BatchValidateSign`) precompile via a `TriggerSmartContract` transaction whose call data encodes a signature-array length word (`words[words[3].intValueSafe()/WORD_SIZE]`) as a very large integer (e.g., hundreds of millions).
2. On any node/network state where `VMConfig.allowTvmSelfdestructRestriction()` evaluates false (legacy behavior, no hard fork activation), `extractBytesArray`/`extractSigArray` is invoked directly with this attacker-controlled `len`, allocating `new byte[len][]` before the `MAX_SIZE` check at line 1076/1179 is reached.
3. Repeated/cheap invocation of this call drives large heap allocation on any node executing or validating the transaction, producing OOM/DoS conditions.

Note: I could not fully verify within available tool calls the exact numeric bound returned by `DataWord.intValueSafe()` (whether it clamps to `Integer.MAX_VALUE` or another ceiling) or the current default/activation state of the `allowTvmSelfdestructRestriction` parameter on this codebase snapshot; these would determine the precise achievable allocation size and whether the un-gated path is currently reachable on mainnet.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
