### Title
Unbounded In-Memory Read of Conflicting Blob Content Enables Memory DoS in `ListConflictFiles` - (File: internal/gitaly/service/conflicts/list_conflict_files.go)

### Summary
The `ListConflictFiles` RPC reads the entire content of each conflicting file object into an unbounded `bytes.Buffer` before any size validation or streaming occurs, mirroring the reported Commit-Boost issue where a response was fully loaded into memory prior to any size check meant to guard against memory DoS.

### Finding Description
In `conflictFilesWithGitMergeTree`, for every conflicting blob, Gitaly resolves the blob object and then reads it fully into memory with no upper bound: [1](#0-0) 

`content.ReadFrom(object)` performs an unbounded read (`bytes.Buffer.ReadFrom` grows without limit) of the blob's entire content before the code ever checks size, validity, or streams data out in chunks. This differs from other blob-serving code paths in Gitaly which stream and bound reads, e.g. `ReadObjectWithLimit` in `internal/git/localrepo/objects.go` uses `io.LimitReader` to cap memory usage [2](#0-1) , and `processBlobs` in the Blob service streams object contents via `io.CopyN` with a caller-supplied `bytesLimit` rather than buffering the whole object [3](#0-2) . The conflict-resolution code path in `internal/git/conflict/resolve.go` also bounds its read explicitly with `io.LimitReader(src, int64(fileLimit)+1)` [4](#0-3) . `ListConflictFiles`, however, has no such bound: any authenticated user who can trigger a merge conflict (e.g., by pushing two branches with a large conflicting blob and calling `ListConflictFiles` between them) can force Gitaly to allocate memory proportional to the size of the conflicting blob, for every conflicting file in the merge, with no cap.

### Impact Explanation
Because `content.ReadFrom` has no size ceiling, a single `ListConflictFiles` RPC against a repository containing a very large blob involved in a merge conflict (git blobs can be gigabytes in size) can cause Gitaly to allocate memory equal to the blob size per conflicting file, and multiple large conflicting files multiply the effect. This can exhaust memory on the Gitaly node, potentially triggering the OOM killer and causing a denial of service that impacts unrelated repositories and RPCs served by the same node (per `doc/cgroups.md`, cgroup memory limits are shared across processes on a node) .

### Likelihood Explanation
This is reachable by an ordinary user who can push commits with large blobs and has access to the conflicts RPCs (e.g., via merge-request diff/conflict resolution UI flows in GitLab), which is a standard code path, not requiring any privileged access, leaked credentials, or a malicious peer — it directly matches the "RPC-handler resource limits" analog class called out in scope.

### Recommendation
Bound the read of conflicting blob content using the object's known size (available via `object.ObjectSize()`/`ObjectInfo`) against a configured maximum (similar to `TreeEntryRequest.max_size` handling), or stream content in fixed-size chunks directly into the response via `streamio` instead of buffering the entire blob with `bytes.Buffer.ReadFrom`. Reject or truncate files that exceed a sane limit before allocating buffers, consistent with the bounded pattern already used in `internal/git/conflict/resolve.go` and `ReadObjectWithLimit`.

### Proof of Concept
1. Create a repository and commit a very large blob (e.g., several hundred MB to a few GB) on two divergent branches such that the blob content conflicts when merged (same path, different content on each side).
2. Call the `ListConflictFiles` RPC with `OurCommitOid`/`TheirCommitOid` pointing at the two branch tips and `SkipContent=false`.
3. Observe that Gitaly's `conflictFilesWithGitMergeTree` allocates a `bytes.Buffer` sized to the full blob for each conflicting path via `content.ReadFrom(object)` [5](#0-4)  before any size check or streaming occurs, causing a large, uncontrolled memory spike proportional to blob size and conflict count.
