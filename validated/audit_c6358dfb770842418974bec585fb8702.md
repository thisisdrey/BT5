This confirms `data_bytes_cost` from `CostModel::get_instructions_data_cost` feeds directly into `TransactionCost::sum()`, which is what `CostTracker::would_fit` and `try_add` use to enforce `MAX_BLOCK_UNITS`/`MAX_WRITABLE_ACCOUNT_UNITS` (banking stage QoS gates), and into `calculate_priority`/`calculate_priority_and_cost` (forwarding/scheduler prioritization). ### Title
Instruction-data cost floor-division lets users submit unlimited free-of-cost data by fragmenting transactions - (File: cost-model/src/cost_model.rs)

### Summary
`CostModel::get_instructions_data_cost` computes the per-transaction "data bytes cost" component of the cost model using integer floor division by `INSTRUCTION_DATA_BYTES_COST` (a constant equal to `140/30 = 4`). Any transaction whose total instruction data length is below 4 bytes contributes `0` to `data_bytes_cost`, and this cost feeds directly into `CostTracker`'s block/account cost-limit enforcement and into transaction-priority calculations used for scheduling/forwarding.

### Finding Description
`get_instructions_data_cost` truncates via plain integer division rather than rounding up: [1](#0-0) 

`INSTRUCTION_DATA_BYTES_COST` is derived as `140 /*bytes per us*/ / COMPUTE_UNIT_TO_US_RATIO`, which floor-divides to `4`: [2](#0-1) 

This `data_bytes_cost` is one of the summed components of `TransactionCost` returned by `calculate_cost`, `calculate_cost_for_executed_transaction`, and `estimate_cost`: [3](#0-2) 

That `sum()` is exactly what `CostTracker::would_fit`/`try_add` compare against `MAX_BLOCK_UNITS` and per-account limits when banking-stage's `Consumer` commits transactions (`try_add_processed_transaction_costs` → `cost_tracker.try_add(cost)`), and what `check_block_cost_limits` uses during transaction execution/commit: [4](#0-3) [5](#0-4) 

The same undercounted cost is used as the divisor in the scheduler/forwarding-stage priority calculation `P = R/(1+C)`, so an attacker's cheap, data-light transactions also get inflated priority relative to their real resource footprint: [6](#0-5) 

Unlike the prioritization-fee calculation (`get_prioritization_fee`), which explicitly rounds *up* to avoid undercharging, this instruction-data cost path has no such protection, so it always truncates toward zero for any instruction data under 4 bytes (and similarly loses up to 3 bytes of "free" accounting per transaction regardless of size, since it's `len / 4` not `ceil(len / 4)`): [7](#0-6) 

### Impact Explanation
This is a genuine QoS/cost-accounting evasion: an attacker can craft many transactions whose combined instruction data is consistently under the 4-byte threshold (or otherwise a non-multiple of 4, discarding the remainder each time), each recording `data_bytes_cost = 0`, while cumulatively pushing more raw bytes through packet processing, sigverify, and banking stage than the cost model believes it is admitting into the block. Because this cost also drives account/block cost-limit checks and transaction-priority ranking used by the scheduler and forwarding stage, an attacker gets underpriced admission and inflated scheduling priority relative to actual resource consumption. The magnitude per-transaction is small (at most 3/4-byte-worth of undercount, worth `3` cost units out of `DEFAULT_HEAP_COST`-scaled costs that are typically dominated by CU execution cost), so this is a low-severity, low-magnitude discrepancy rather than a way to bypass block limits entirely.

### Likelihood Explanation
High likelihood of being triggerable: any unprivileged user can submit ordinary transactions with small instruction data payloads; no special permissions or validator/operator role is required, and the behavior is deterministic (`len / 4` truncation) rather than probabilistic.

### Recommendation
Change `get_instructions_data_cost` to round up (ceiling division), matching the pattern already used elsewhere in the codebase for prioritization fees and page-cost calculations (`calculate_pages_for_bytes` already does `saturating_add(PAGE_SIZE - 1).saturating_div(PAGE_SIZE)`):
```rust
fn get_instructions_data_cost(transaction: &impl TransactionMeta) -> u16 {
    let len = transaction.instruction_data_len();
    len.saturating_add(INSTRUCTION_DATA_BYTES_COST as u16 - 1) / (INSTRUCTION_DATA_BYTES_COST as u16)
}
```

### Proof of Concept
1. Construct a transaction whose total instruction data length is, e.g., 3 bytes (`instruction_data_len() = 3 < INSTRUCTION_DATA_BYTES_COST = 4`).
2. Call `CostModel::get_instructions_data_cost` on it — observe it returns `0` (`3 / 4 == 0`), confirmed by the existing test `test_cost_model_token_transaction` which asserts `data_bytes_cost == 0` for small instruction payloads: [8](#0-7) 
3. Submit many such transactions in a block; each contributes `0` to `TransactionCost::data_bytes_cost`, meaning `CostTracker::would_fit`/`try_add` never account for this real (if small) per-transaction data overhead, and `calculate_priority_and_cost`'s denominator `cost.saturating_add(1)` is likewise undercounted, giving these transactions relatively higher computed priority than their true footprint warrants.

pub(crate) fn calculate_priority_and_cost<Tx: TransactionMeta + SVMStaticMessage>(
    bank: &Bank,
    transaction: &Tx,
    transaction_configuration: &TransactionConfiguration,
) -> (u64, u64) {
    let cost = CostModel::calculate_cost_for_executed_transaction(
        transaction,
        u64::from(transaction_configuration.compute_unit_limit),
        transaction_configuration.loaded_accounts_data_size_limit,
        &bank.feature_set,
    )
    .sum();
    let fee_details = solana_fee::calculate_fee_details(
        transaction,
        bank.fee_structure().lamports_per_signature,
        transaction_configuration.priority_fee_lamports,
        bank.fee_features(),
    );
    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    (
        reward
            .saturating_mul(MULTIPLIER)
            .saturating_div(cost.saturating_add(1)),
        cost,
    )
}
