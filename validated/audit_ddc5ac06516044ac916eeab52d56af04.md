### Title
Orphaned PromiseYield state (PromiseYieldReceipt/Status/DataIdToYieldId) survives account deletion and is delivered/executed against a re-created account of the same name via the global PromiseYieldTimeout queue - (File: runtime/runtime/src/lib.rs, core/store/src/utils/mod.rs)

### Summary
`remove_account` (`core/store/src/utils/mod.rs:504-575`) removes `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` rows but never touches `TrieKey::PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId` entries keyed to that account, even though these are all listed as account-scoped columns (`core/primitives/src/trie_key.rs:87-102`). The account-independent `PromiseYieldTimeout` queue (`resolve_promise_yield_timeouts`, `runtime/runtime/src/lib.rs:3009-3116`) fires purely by `expires_at` and `contains_key(PromiseYieldReceipt{account_id, data_id})`, with no check that the account still exists or is "the same" account that created the yield.

### Finding Description
1. Attacker's account `A` calls `promise_yield_create`/`promise_yield_create_with_id`, which stores `PromiseYieldReceipt{A,D1}` (`process_receipt`, `lib.rs:1495-1499`), `PromiseYieldStatus{A,D1}=Yielded`, and (if `YieldWithId`) `YieldIdToDataId{A,Y1}=D1`/`DataIdToYieldId{A,D1}=Y1` (`core/store/src/utils/mod.rs:281-297`, `runtime/runtime/src/ext.rs:371-399`), plus a `PromiseYieldTimeout{account_id: A, data_id: D1, expires_at: T}` queue entry.
2. Attacker deletes `A` via `DeleteAccount` (`action_delete_account`, `runtime/runtime/src/actions.rs:314-390`), which calls `remove_account` (`core/store/src/utils/mod.rs:505-575`). This function never iterates or removes `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId` rows for `A`, so the orphaned yield state (including the full pending `Receipt` object with its embedded action list) persists in the trie.
3. `A` is re-created (e.g., as a subaccount, which is permissionless to the parent's controller) with new code/state.
4. At `expires_at = T`, `resolve_promise_yield_timeouts` (`lib.rs:3009-3116`) processes the (account-agnostic) timeout queue entry, checks `contains_key(TrieKey::PromiseYieldReceipt{A,D1})` (`lib.rs:3047-3051`) - true, because it was never cleaned up - and synthesizes a `PromiseResume{predecessor_id: A, receiver_id: A, data: None}` receipt.
5. That resume is processed by `process_receipt`'s `PromiseResume` arm (`lib.rs:1500-1563`): the status check at `lib.rs:1503-1508` only short-circuits if status is `ResumeInitiated` (never set here), so it proceeds to `get_promise_yield_receipt`, finds the stale receipt, and executes it via `apply_action_receipt` against the *new* account `A`'s state, with `predecessor_id == receiver_id == A`.

None of the existing signature/nonce/access-key/gas checks apply here, because this entire path is internal runtime receipt-queue processing that never re-validates account identity/existence against the state at time of execution - only `contains_key` on the (never-cleaned) `PromiseYieldReceipt` key.

### Impact Explanation
The delivered "self-call" receipt carries `predecessor_id == receiver_id == A`, which is exactly the pattern many contracts use for privileged/`#[private]` methods (self-only callbacks). This means a new occupant of account `A` (a distinct owner, if `A`'s name is later re-registered by someone else) can have an attacker-controlled `FunctionCall` action list — chosen entirely at the *original* `A`'s discretion, before deletion — executed against their new contract with self-call authorization, entirely without their contract explicitly initiating it. Depending on what the original attacker put in the promise's actions (arbitrary since `promise_yield_create` + subsequent `promise_batch_action_*` calls are controlled by the calling contract), this could satisfy self-only authorization checks (`assert_self()`), corrupt new-contract state, or trigger unintended transfers/callbacks. This maps to NEAR's "authorization escalation across accounts/promises" bounty category. However, whether this reaches a genuinely *different* new owner (rather than the original attacker re-using their own name) — which is required for meaningful cross-account escalation — depends on account-naming rules I could not fully verify (e.g., whether a distinct party could realistically claim a deleted top-level/sub-account name before the timeout fires); with a self-controlled subaccount, the "impact" is limited to the attacker griefing/self-triggering timing, which is not a genuine security boundary violation.

### Likelihood Explanation
Preconditions are cheap and fully attacker-controlled: create a yield, delete the account before the timeout, and either re-create it yourself or wait for someone else to claim the name. The `MAX_ACCOUNT_DELETION_STORAGE_USAGE` cap (`actions.rs:348`) does not block this, since yield state is unbounded in count but each row is small. Repeatable across yields/timeouts. The main uncertainty limiting a full "yes this is exploitable across trust boundaries" conclusion is confirming (a) that `promise_yield_create`'s `receiver_id` argument is unconditionally forced to `current_account_id` (self) by the host function layer (not verified in the snippets retrieved — `logic.rs`'s `fn promise_yield_create` body was not shown), and (b) a realistic scenario where a *different, non-colluding* party re-registers the exact same account name within the yield-timeout window (default yield timeout is short, typically tens of blocks) to actually receive the stale receipt as a victim rather than as the same attacker.

### Recommendation
`remove_account` should also purge all `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` rows for the account being deleted (mirroring the existing access-key/contract-data iteration-and-remove pattern), and/or `resolve_promise_yield_timeouts` should additionally verify the account still exists (or track a deletion epoch/nonce) before dispatching a timeout-resume receipt to `queue_entry.account_id`.

### Proof of Concept
Integration test (test-loop) plan:
1. Deploy a test contract on account `A` exposing a private self-call method with a state-mutating side effect, and a method that calls `promise_yield_create`, chaining a self-`FunctionCall` action to the private method.
2. Submit a transaction invoking the yield-creating method; advance one block so the yield is parked (mirrors `test_simple_yield_timeout`, `test-loop-tests/src/tests/yield_timeouts.rs:337-384`).
3. Submit `DeleteAccount` for `A` before `yield_timeout_height()`; verify via direct trie/store inspection that `PromiseYieldReceipt`/`PromiseYieldStatus`/`DataIdToYieldId` keys for `A` are still present post-deletion (this alone already demonstrates the cleanup asymmetry).
4. Re-create `A` with a fresh, different contract deployment (simulating a new occupant) before `yield_timeout_height()`.
5. Advance to `yield_timeout_height()` and `+1`, then assert the new contract's state reflects the side effect of the stale private method (i.e., it was invoked with `predecessor_id == receiver_id == A`), proving that a resume receipt from a defunct promise chain executed against the new account.
