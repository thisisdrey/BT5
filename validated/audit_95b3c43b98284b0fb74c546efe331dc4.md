### Title
Floating-point `pow()`-based exchange math causes rounding-error/inconsistent settlement amounts - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The reported bug class is that a `pow()` implementation used for computing financial value (staking points in the Tokemak report) can produce imprecise/inconsistent results. The analogous path in java-tron is `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, which compute TRC10 bancor-style exchange amounts using Java `double` arithmetic and `Maths.pow(...)`, a pattern the codebase itself has since flagged as unsafe by introducing a BigDecimal-based `SafeExchangeProcessor` "hardened" replacement.

### Finding Description
`ExchangeProcessor.exchangeToSupply` and `exchangeFromSupply` compute the bancor-relay-token math using double-precision floating point and a `pow()` call: [1](#0-0) 

The exponent, base and division operations are all performed in `double`, and truncated via `(long) issuedSupply`. `Maths.pow` dispatches either to `StrictMathWrapper.pow` (plain `StrictMath.pow`) or to the legacy `MathWrapper.pow`, which is a hardcoded lookup table of previously observed `(base, exponent) -> result` bit patterns with a `StrictMath.pow` fallback for any input not already in the table: [2](#0-1) 

This lookup-table-with-fallback design exists specifically because historical floating-point `pow()` computations in this exchange path produced values that needed to be patched/pinned block-by-block to stay consistent with chain history, which is documented in `MathWrapper`'s deprecation note pointing developers to `StrictMathWrapper` "for cross-platform consistency."

Separately, the same repository already replaced this arithmetic with a fixed-point `BigDecimal` implementation, `SafeExchangeProcessor`, selected via a `hardenedCalc` flag in `ExchangeCapsule.transaction`: [3](#0-2) [4](#0-3) 

The existence of `SafeExchangeProcessor` as an explicit "hardened" alternative confirms the project's own recognition that the double/`pow()`-based `ExchangeProcessor` path can yield rounding errors or overflow inconsistent with the intended fixed-point token economics — exactly the class of bug described in the external report (a `pow()` function whose floating-point/algorithmic behavior can diverge from the mathematically correct or previously-agreed value).

### Impact Explanation
`ExchangeCapsule.transaction` computes the `buyTokenQuant` returned to a trader and the new `firstTokenBalance`/`secondTokenBalance` stored for the exchange pair. If the legacy (non-hardened) `ExchangeProcessor` path is exercised, floating-point rounding/precision loss in the `pow()`-driven bancor formula can result in a minted/paid-out token quantity that does not correctly correspond to the pool's true bonding-curve value, which can manifest as an unbacked balance for one side of the exchange pair (value extracted or lost by pool participants). This falls under "unbacked balance / theft or permanent freezing of funds" in the sense that any systematic bias in `pow()` rounding is directly monetized by traders issuing/withdrawing relay-token supply.

### Likelihood Explanation
This code path is reachable by any unprivileged account that broadcasts an `ExchangeTransactionContract` (a TRC10 bancor-exchange trade) processed by `ExchangeTransactionActuator`/`MarketSellAssetActuator`, i.e., a normal order-placer transaction, requiring no special privilege. However, I was not able to confirm within the available iterations whether the legacy `ExchangeProcessor` (double/`pow()`) path or the `SafeExchangeProcessor` (BigDecimal, hardened) path is the one actually selected by current mainnet chain parameters (the `hardenedCalc` gating condition/proposal flag). If `hardenedCalc` is already unconditionally `true` in current production configuration, the vulnerable double-based path may be dead code retained only for historical replay compatibility, which would reduce this to a non-issue for new transactions. This should be verified against the live chain parameter/proposal that controls `hardenedCalc` before treating this as exploitable going forward.

### Recommendation
- Confirm whether `hardenedCalc` (routing to `SafeExchangeProcessor`) is enabled by default for all new blocks/transactions; if not, gate all new exchange transactions to the BigDecimal-based `SafeExchangeProcessor` path exclusively.
- Deprecate and remove reliance on `MathWrapper`'s hardcoded `pow()` value table for any new consensus-critical computation, since it is a strong signal that floating-point `pow()` in this codebase has historically produced values requiring manual reconciliation.
- Where compatibility with historical state is unnecessary, migrate all remaining `Maths.pow`/`StrictMathWrapper.pow` usages that affect balances (e.g., `ExchangeProcessor`) to fixed-point/`BigDecimal` arithmetic to eliminate reliance on IEEE-754 `pow()` semantics.

### Proof of Concept
Not independently reproduced; the finding is based on static analysis of `ExchangeProcessor` vs. `SafeExchangeProcessor` and the `MathWrapper` compensation table, showing the codebase's own acknowledgment that the floating-point `pow()`-based exchange calculation can diverge from the intended fixed-point result. A concrete PoC would require confirming the live chain parameter that selects `hardenedCalc=false` and then crafting an `ExchangeTransactionContract` with balances/quantities chosen to maximize the `double` rounding bias in `Math.pow(1 + quant/newBalance, 0.0005)` / `Math.pow(1 + quant/supply, 2000.0)`.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }
