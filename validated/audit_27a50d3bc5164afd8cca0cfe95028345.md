### Title
Non-constant-time password comparison in block-replay auth check enables timing side-channel attack - (File: stackslib/src/net/api/blockreplay.rs)

### Summary
`RPCNakamotoBlockReplayRequestHandler::try_parse_request` authenticates the `authorization` header against the configured `self.auth` secret using Rust's default `String`/`str` `PartialEq`, which is not constant-time and short-circuits on the first mismatching byte. A remote unprivileged attacker who knows the endpoint is auth-gated can measure response latency across repeated guesses to recover the secret byte-by-byte instead of needing the full secret up front.

### Finding Description
The equality the endpoint is supposed to enforce is: *"authorization succeeds only if the attacker already possesses the full secret."* The code implements this as: [1](#0-0) 

`auth_header != password` compares two `String`/`&str` values using the standard library's `PartialEq`, which internally does a length check followed by a byte-wise/memcmp-style comparison that returns as soon as a mismatch is found (or, for length mismatches, immediately). This is not designed to run in constant time with respect to the position of the first differing byte. An attacker can send repeated `GET /v3/blocks/replay/<block_id>` requests with an `authorization` header that varies only in the byte at position `i`, and observe that requests matching a longer correct prefix take marginally longer (more comparison work / cache behavior) than those that mismatch earlier. By iterating over all candidate byte values at each position and keeping the one that produces the largest average latency (or statistically distinguishable timing), the attacker can recover `password` one byte at a time, reducing the search space from brute-forcing the entire secret to O(length × alphabet_size) timing-oracle queries.

The comparison happens *before* `self.block_replay(...)` is ever invoked (that call is gated behind this check in `try_handle_request`), so this is squarely an auth-bypass primitive on this specific gated endpoint, not merely a side observation elsewhere in the pipeline.

The same anti-pattern (`... != password` or `... != self.auth`) is used identically in several other RPC handlers (`postblock_v3.rs`, `postblock_proposal.rs`, `txsimulate.rs`, `fastcallreadonly.rs`, `blocksimulate.rs`), confirming this is a systemic, non-constant-time secret comparison, not a one-off typo.

Existing guards do not mitigate this: there's no rate limiting or constant-time comparison in `try_parse_request`, and the `password` is only checked with a naive `!=`.

### Impact Explanation
An attacker who statistically recovers the block-replay secret gains unauthorized access to the block-replay endpoint, which lets them force the node to re-execute/re-mine arbitrary historical Nakamoto blocks (`remine_nakamoto_block`), consuming CPU/DB resources and exposing internal execution/profiling data (transaction receipts, VM errors, merkle-root validity, execution costs) that was intended to be gated behind the shared secret. This matches the stated Critical category: "unauthenticated/unauthorized access bypassing the auth-gated endpoint entirely."

### Likelihood Explanation
Preconditions: the node operator must have configured `self.auth = Some(password)` (block-replay auth enabled) and the RPC port must be remotely reachable — both explicitly allowed as in-scope preconditions by the question. The attacker needs no prior secret, peer role, or privileged access — only the ability to send repeated HTTP GET requests and measure response timing, which is exactly the unprivileged remote capability defined in scope. Practical extraction requires many samples per byte to average out network/system jitter, but this is a well-documented, repeatable, low-cost class of attack (CWE-208, Observable Timing Discrepancy) against naive string-equality secret checks, and is why constant-time comparison primitives (e.g., the `subtle` crate) exist and are standard practice for exactly this kind of check.

### Recommendation
Replace the direct `!=` string comparison with a constant-time comparison, e.g. using the `subtle` crate's `ConstantTimeEq` on the byte representations (after first comparing/hashing lengths in a way that doesn't leak length either), or by comparing pre-hashed values (e.g., HMAC digest comparison) instead of raw secret bytes. Apply the same fix consistently to all other handlers using the same pattern (`postblock_v3.rs`, `postblock_proposal.rs`, `txsimulate.rs`, `fastcallreadonly.rs`, `blocksimulate.rs`).

### Proof of Concept
A `stackslib::net` test (in `blockreplay.rs`'s test module or a new integration test) would:
1. Construct an `RPCNakamotoBlockReplayRequestHandler` with `auth = Some("supersecretpassword".to_string())`.
2. For increasing prefix lengths `k` (0..len), build an `authorization` header value that matches the first `k` bytes of the real password and differs at byte `k+1`, wrapped in a `StacksHttpRequest::new_block_replay`-style preamble.
3. Call `handler.try_parse_request(&preamble, &captures, None, &[])` many times (e.g., 10k iterations) for each `k`, using `std::time::Instant` to record elapsed time for the comparison branch (`if auth_header != password`).
4. Compute average latency per `k` and assert that average latency is monotonically (or statistically significantly) correlated with `k` (Pearson correlation > some threshold), demonstrating the timing side channel that would let an attacker binary/linear-search the correct byte at each position instead of brute-forcing the full secret.
