### Title
Non-atomic replay-window check-then-update in `ConnectionState.Decrypt`/`VerifyRelay` allows concurrent replay acceptance - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` protect against duplicate/replayed messages using a two-step `Check()`/`Update()` pattern on the shared `Bits` replay window, but the two steps are protected by *separate* lock acquisitions with the lock released in between and real work (AEAD decryption) done outside the lock. This mirrors the reported class of bug in `RevenueHandler.sol`: a piece of shared, mutable accounting state (`epochRevenues` there, the replay-window bitmap here) is read once to authorize an action, but the actual "commit" of that state happens later and non-atomically with the read, so the same stale/unmarked state can be used to authorize the action more than once before it is finally marked "consumed."

### Finding Description
In `connection_state.go`: [1](#0-0) 

The `Decrypt` function:
1. Locks `decryptLock`, calls `window.Check(l, messageCounter)`, unlocks.
2. Runs `dKey.DecryptDanger(...)` (AEAD decrypt) with no lock held.
3. Locks `decryptLock` again, calls `window.Update(l, messageCounter)`, unlocks.

`VerifyRelay` follows the identical pattern: [2](#0-1) 

`Bits.Check` only *reads* the replay bitmap; it does not mark the counter as seen — only `Bits.Update` does that: [3](#0-2) 

Because Nebula's UDP receive path can run with multiple concurrent reader routines processing packets for the same `HostInfo`/`ConnectionState` (the `outside.go` packet handler is invoked per received datagram, and the underlying UDP listener can be configured with multiple reader goroutines), two threads that receive the exact same (replayed) ciphertext with the same `messageCounter` can each acquire `decryptLock`, call `Check()`, see the counter as not-yet-seen (since neither has called `Update()` yet), release the lock, and both proceed to decrypt/verify the same message successfully. Only after both have already accepted the packet does either call `Update()` to actually record the counter. This is the same underlying fault class as the report: state that should gate a single acceptance (unspent revenue / an unseen counter) is read and acted upon before it is durably updated, so the same authorization can be exercised more than once.

### Impact Explanation
This breaks the anti-replay guarantee for the data-plane (`Decrypt`) and for relay frames (`VerifyRelay`). A captured packet or relay frame replayed at the right time (a race is enough, not even attacker-controlled precision, though an attacker can increase the race window by flooding duplicate copies to increase the chance both are in-flight concurrently) can be accepted twice instead of being rejected as a duplicate, i.e., traffic replay bypassing the anti-replay window described by `TestRelayReplayProtection`'s own stated invariant that replayed frames "must be dropped by the replay window." [4](#0-3) 

### Likelihood Explanation
The race requires the same duplicate/replayed ciphertext to be processed concurrently by two goroutines against the same `ConnectionState`, which is plausible whenever the receive path is multi-threaded per socket/tunnel and an attacker (on the wire, with no valid certificate needed since this happens pre-authentication of packet freshness) can inject the same captured frame multiple times close together to win the race. It's not deterministic, but it's a straightforward TOCTOU that will eventually fire under load or with repeated injection attempts.

### Recommendation
Make the check-and-mark operation atomic: hold `decryptLock` for the entire `Check`+decrypt+`Update` sequence, or better, fold `Check` and `Update` into a single locked operation that first tests-and-tentatively-reserves the counter, then rolls back the reservation if decryption fails. This closes the window where two concurrent callers can both observe "not yet seen" for the same counter.

### Proof of Concept
Conceptually:
1. Attacker captures one valid relay/data frame with counter `N`.
2. Attacker sends two copies of the same frame in rapid succession (or relies on natural retransmission/duplication at the network layer) so that both are read by different reader goroutines and dispatched to `Decrypt`/`VerifyRelay` for the same `ConnectionState` at nearly the same time.
3. Goroutine A: `window.Check(N)` returns true (not yet marked), releases lock, begins `DecryptDanger`.
4. Goroutine B: before A calls `Update`, B also calls `window.Check(N)`, also returns true, releases lock, begins `DecryptDanger`.
5. Both A and B successfully decrypt/verify and accept the same counter `N` as valid, each later calling `Update(N)` — the second `Update` will correctly report a duplicate, but by then the packet has already been processed/forwarded twice, defeating replay protection guaranteed by the `Bits` window and asserted in `TestRelayReplayProtection`.

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
