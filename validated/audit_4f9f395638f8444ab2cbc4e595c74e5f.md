This confirms the premise is invalid. Every intent type (`Transfer`, `FtWithdraw`, `NftWithdraw`, `MtWithdraw`, `TokenDiff`, etc.) carries an explicit `TokenId`/`amount` field that the signer names at signing time — none of them authorize a signer's "whole balance" implicitly.

### Analysis

**The claimed binding:** "intents.near identity checked at signing time == intents.near identity checked at execution time" for `verifying_contract`/`signer_id`, and the fear that this being re-checked at execution time (not baked in at signing) lets a stale payload move funds arriving after signing.

This binding is a non-issue on two independent grounds:

1. **`verifying_contract` is immutable, not re-derivable.** It is a fixed field embedded inside the signed `DefusePayload` at signing time [1](#0-0) , and it's compared against `self.state.verifying_contract()` (the actual contract being called) purely to reject cross-contract replay — not to bind to a mutable "identity" that could shift underneath the signer [2](#0-1) . On NEAR, `current_account_id()` for a deployed contract never changes without an actual account/contract redeploy under a different `AccountId`, which is out of scope (no migration mechanism is described in this repo that reassigns `current_account_id` semantics).

2. **Intents specify exact amounts, not balances.** The premise's proof idea — sign today, deposit more funds later, then execute the old payload and check "no implicit whole-balance authorization drift" — is already structurally impossible because every `ExecutableIntent` (`Transfer` [3](#0-2) , `FtWithdraw` [4](#0-3) , `TokenDiff` [5](#0-4) ) carries an explicit `TokenId` and `amount`/`diff` chosen by the signer at signing time. `internal_sub_balance` only subtracts the named `amount` for the named `token_id` from whatever the current balance is [6](#0-5) ; it never reads "full balance" and never moves more than what was explicitly signed. A far-future-deadline payload executed after additional deposits arrive will move exactly the amount specified in the signed intent — nothing more — and if that amount now exceeds or falls short relative to a changed balance, it just succeeds/fails according to the `sub`/`checked_*` arithmetic, with no "drift" toward moving newly-arrived funds beyond what was named.

Additionally, since the attacker in this scenario is signing their **own** payload over their **own** account, any funds moved are already funds they are entitled to authorize — this is definitionally self-harm/self-authorization, explicitly out of scope ("attacker only affects their own funds"). There is no mechanism by which signing a payload for account A grants authority over funds later credited to A beyond the named token/amount, and no privilege escalation to a third party's funds occurs at any point in this flow (`Transfer`/`FtWithdraw` require `sender_id`/`owner_id` to match the verified `signer_id` who owns the signature [7](#0-6) ).

    fn internal_sub_balance(
        &mut self,
        owner_id: &AccountIdRef,
        token_amounts: impl IntoIterator<Item = (TokenId, u128)>,
    ) -> Result<()> {
        let account = self
            .accounts
            .get_or_create(owner_id.to_owned(), |owner_id| {
                self.view.is_account_locked(owner_id)
            })
            .get_mut()
            .ok_or_else(|| DefuseError::AccountLocked(owner_id.to_owned()))?;
        for (token_id, amount) in token_amounts {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            if account.token_amounts.get(&token_id).is_none() {
                account
                    .token_amounts
                    .add(token_id.clone(), self.view.balance_of(owner_id, &token_id))
                    .ok_or(DefuseError::BalanceOverflow)?;
            }
            account
                .token_amounts
                .sub(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }
