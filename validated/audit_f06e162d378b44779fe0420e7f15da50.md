### Title
DoS via ReDoS-vulnerable PCRE regex passed unrestricted to `git grep --perl-regexp` in `SearchFilesByContent` - (File: internal/gitaly/service/repository/search_files.go)

### Summary
The `SearchFilesByContent` RPC takes a user-supplied `Query` string and passes it directly as the pattern to `git grep --perl-regexp -e <query>`. Unlike Go's `regexp` package (RE2, linear-time, no catastrophic backtracking), `git grep --perl-regexp` uses a PCRE-compatible backtracking regex engine, which is exactly the class of engine the original Rouge report exploited. An ordinary user who can call this RPC (any consumer with repository read access, e.g. GitLab code search) can submit a pattern with nested/ambiguous quantifiers to trigger catastrophic backtracking and hang the `git grep` subprocess.

### Finding Description
`SearchFilesByContent` builds the git command as: [1](#0-0) 

The `--perl-regexp` flag forces git to use PCRE for regex parsing when git was compiled with `USE_LIBPCRE2` (the standard case in most Git distributions, including the one Gitaly bundles), whereas Go's own `regexp` calls elsewhere in this same file (used for `SearchFilesByName`'s `Filter` field) are RE2-based and immune to backtracking blowup: [2](#0-1) 

Notably, the length-limiting protection that exists for the `Filter` field (`searchFilesFilterMaxLength`, used only in `SearchFilesByName`) is not applied to `req.GetQuery()` in `SearchFilesByContent`: [3](#0-2) [4](#0-3) 

This is a direct structural analog to the Rouge ReDoS report: the query is untrusted input, it's evaluated by a backtracking regex engine (PCRE via `git grep --perl-regexp`, analogous to Rouge's Ruby regex engine), and there's no length or complexity restriction guarding it before it reaches that engine.

### Impact Explanation
Constructing a classic exponential-backtracking PCRE pattern (e.g., `(a+)+$`, `(a|a)*b`, or similar nested-quantifier constructs) combined with non-matching input in the repository content causes `git grep` to consume CPU for an extremely long time (potentially unbounded, scaling exponentially with input/pattern size). Because this runs as a subprocess spawned per-RPC on the Gitaly node, a single request can pin a CPU core indefinitely, and repeated requests can exhaust the process/command execution pool, degrading or denying the `SearchFilesByContent` RPC and potentially other RPCs on the same Gitaly node due to resource contention (RPC-handler resource exhaustion / DoS).

### Likelihood Explanation
High. `SearchFilesByContent` is a routinely exposed, unprivileged, read-path RPC (it's the backend of GitLab's "search code" feature) reachable by any user with read access to a repository. No special permissions, malicious peer, or leaked token is required — a single crafted `Query` string in a normal API/RPC call is sufficient.

### Recommendation
- Bound the length/complexity of `req.GetQuery()` similarly to the existing `searchFilesFilterMaxLength` guard used for `SearchFilesByName`.
- Avoid or restrict `--perl-regexp` for untrusted input; prefer git's default (POSIX extended, non-backtracking-heavy) grep mode or `--fixed-strings` where feasible.
- Apply a hard execution timeout / CPU/wall-clock limit specifically to `git grep` subprocesses spawned for this RPC so a pathological pattern cannot hang the RPC indefinitely.
- Consider validating/rejecting patterns with known catastrophic-backtracking shapes, or run pattern matching through an engine with linear-time guarantees (e.g., RE2) when full PCRE semantics aren't required.

### Proof of Concept
1. As an ordinary user with read access to a repository, call `SearchFilesByContent` with:
   - `Query`: a PCRE pattern susceptible to catastrophic backtracking, e.g. `(a+)+$` or `(a|aa)+b`.
   - `Ref`: any valid ref containing a large text file with a long run of `a` characters that never satisfies the trailing anchor (e.g., a file containing `"a" * 50000` with no trailing `b`/match).
2. Gitaly executes `git grep --ignore-case -I --line-number --null --before-context 2 --after-context 2 --perl-regexp -e '(a+)+$' <ref>` against that file.
3. The PCRE engine backtracks catastrophically on the non-matching long run of `a`s, causing the `git grep` subprocess (and the RPC handling goroutine waiting on it) to hang, consuming a full CPU core for a duration that grows exponentially with the length of the crafted input — a low-cost, repeatable DoS vector against the Gitaly node.
