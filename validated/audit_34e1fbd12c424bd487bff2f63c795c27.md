### Title
Self-destructed contract's storage rows persist and are silently reused when a new contract is redeployed to the same address via CREATE2, allowing replay of stale on-chain state - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java, actuator/src/main/java/org/tron/core/vm/program/Storage.java)

### Summary
The report's bug class is: a mutable authority/binding (the settlement address) can be swapped out, and the handler contract has no independent record of "already executed" state, so old state tied to the previous binding becomes replayable once the binding changes. The closest reachable analog in java-tron is TVM's `SELFDESTRUCT` + `CREATE2` redeploy path: when a contract self-destructs, its storage rows are **not deleted** from `StorageRowStore`; they are only removed from the current row cache. When a new contract is deployed to the *same address* afterward, `RepositoryImpl.getStorage()` looks up storage keyed primarily by `sha3(address)` (`Storage.addrHash`), so unless the contract explicitly recorded a `trxHash`-salted key, the freshly deployed contract inherits the previous contract's storage values, i.e. stale/previously-"executed" state is silently replayed into a "new" implementation, analogous to the settlement/handler desync described in the report.

### Finding Description
`Program.suicide()`/`suicide2()` mark the contract self-destructed and delete the account balance/resources, but never clear its VM storage: [1](#0-0) 

`RepositoryImpl.markSelfDestruct`/`isSelfDestructed` only track a destruction flag in an in-memory cache set; they never touch `StorageRowStore`: [2](#0-1) 

When a contract is later created at that address (`createContractImpl`), the address collision guard `contractAlreadyExists` only blocks creation if code/account metadata still exists; if the account was fully deleted after suicide, a new contract can be created at the exact same address (this is the entire point of CREATE2 redeploy patterns): [3](#0-2) 

Storage lookups are keyed by `addrHash = sha3(address)` unless a `trxHash` salt is supplied for CREATE2 deployments (`Storage.addrHash(address, trxHash)` / `generateAddrHash`): [4](#0-3) 

`RepositoryImpl.getStorage()` only re-salts the address hash with `contract.getTrxHash()` when that field is non-empty: [5](#0-4) 

The `trxHash` salting is set only when `isCreate2` is true, at contract-creation time: [6](#0-5) 

This means: (1) the storage-row database (`StorageRowStore`, a `TronStoreWithRevoking`) never purges rows for a destructed address, and (2) any code path that constructs `Storage` directly from `address` without a `trxHash` (e.g. the JSON-RPC `getStorageAt` handler, or CREATE contracts, or CREATE2 in non-Istanbul/legacy configurations) will read/write the same physical rows that belonged to the previously self-destructed contract at that address: [7](#0-6) 

This is functionally the same defect pattern as the Chakra finding: a component (the storage backing an address) that is treated as "belonging to the current implementation" is not invalidated/cleared when the implementation at that address changes, so stale state (equivalent to "already processed" cross-chain messages) is silently replayed against the new implementation, which has no independent way to detect this since it trusts whatever is already in its storage slots.

### Impact Explanation
A contract deployer who controls a CREATE2 factory (any unprivileged, permissionless actor — deploying and self-destructing contracts is a normal user-level operation, not a privileged action) can:
1. Deploy contract A at a CREATE2 address, populate storage slots that represent balances, allowances, ownership flags, "already claimed" flags, etc.
2. Self-destruct A.
3. Deploy contract B (different bytecode, possibly with a different owner/access model) at the exact same address.
4. Contract B's `SLOAD`s return contract A's leftover values for any storage slot B did not explicitly overwrite, because the physical row is unchanged unless the trxHash-salting path is engaged.

Depending on how B's logic uses uninitialized-looking storage, this can lead to unauthorized privilege ("already-initialized" flags carried over so an initializer can't be re-run, or is skipped when it shouldn't be), stale balance/allowance accounting being reused, or "replay" of prior state that a naive contract assumes is zero on fresh deployment — matching the report's core harm category (financial discrepancy from state-replay across an implementation change) since real value-bearing contracts (tokens, escrows, etc.) are deployed via TVM.

### Likelihood Explanation
This requires no special privilege: any account can deploy a factory contract, trigger `CREATE2`, `SELFDESTRUCT`, and redeploy — this is a well-known "metamorphic contract" pattern already exercised in the codebase's own test suite (`Create2Test`, `FreezeTest#testFreezeAndUnfreezeToCreate2Contract`, `testCreate2SuicideToBlackHole`), confirming the redeploy-at-same-address path is fully reachable and intentionally supported: [8](#0-7) 
The severity is contingent on the specific higher-level contract logic reusing an address and not defensively re-initializing all storage slots, and on whether the `trxHash`-salting is bypassed in a given deployment path — this residual uncertainty (whether every CREATE2 code path always salts with `trxHash`) is not fully verified from the index and would benefit from direct execution testing in a Devin session.

### Recommendation
- On `SELFDESTRUCT`, actively purge all storage rows associated with the destructed contract's `addrHash` in `StorageRowStore`, not merely mark a destruction flag.
- Ensure every contract-creation code path (CREATE and CREATE2 alike) unconditionally derives a fresh, unpredictable/unique storage salt (e.g., always incorporate the creating transaction hash or a monotonically increasing per-address generation counter) rather than defaulting to `sha3(address)` alone, so no code path can inherit a prior deployment's storage.
- Audit `TronJsonRpcImpl.getStorageAt` and any other direct `new Storage(address, store)` construction to confirm they read state consistent with the currently deployed contract's salt.

### Proof of Concept
1. Deploy `FactoryContract` (as in `FreezeTest`) and use it to CREATE2-deploy contract A at `predictedAddr`, writing a sensitive storage slot (e.g., slot 0 = 1 to represent "initialized"/"claimed").
2. Trigger `SUICIDE`/`SELFDESTRUCT` on A, sending balance elsewhere (`suicideToAccount` pattern used in `FreezeTest#testCreate2SuicideToBlackHole`).
3. Use the same factory and salt/bytecode combination (or a differently-coded contract compiled to hash to the same CREATE2 address) to redeploy contract B at the identical address without the `trxHash` salting path engaged.
4. Read storage slot 0 from B via `getStorageAt` (or an in-contract `SLOAD`) before B's constructor sets it — observe it still equals `1` from contract A, demonstrating unauthorized inheritance/replay of prior contract state at the "upgraded" address. [9](#0-8)

  public boolean isSelfDestructed(byte[] address) {
    Key key = Key.create(address);
    if (selfDestructCache.contains(key)) {
      return true;
    }

    if (parent != null) {
      boolean isSelfDestructed = parent.isSelfDestructed(address);
      if (isSelfDestructed) {
        selfDestructCache.add(key);
      }
      return isSelfDestructed;
    } else {
      return false;
    }
  }

  public Storage getStorage(byte[] address) {
    Key key = Key.create(address);
    if (storageCache.containsKey(key)) {
      return storageCache.get(key);
    }
    Storage storage;
    if (this.parent != null) {
      Storage parentStorage = parent.getStorage(address);
      if (StorageUtils.getEnergyLimitHardFork()) {
        // deep copy
        storage = new Storage(parentStorage);
      } else {
        storage = parentStorage;
      }
    } else {
      storage = new Storage(address, getStorageRowStore());
    }
    ContractCapsule contract = getContract(address);
    if (contract != null) {
      storage.setContractVersion(contract.getContractVersion());
      if (!ByteUtil.isNullOrZeroArray(contract.getTrxHash())) {
        storage.generateAddrHash(contract.getTrxHash());
      }
    }
    return storage;
  }

  private static byte[] addrHash(byte[] address) {
    return Hash.sha3(address);

  private static byte[] addrHash(byte[] address, byte[] trxHash) {
    if (ByteUtil.isNullOrZeroArray(trxHash)) {
      return Hash.sha3(address);
    }
    return Hash.sha3(ByteUtil.merge(address, trxHash));
  }

  public void generateAddrHash(byte[] trxId) {
    // update addreHash for create2
    addrHash = addrHash(address, trxId);
  }

  @Override
  public String getStorageAt(String address, String storageIdx, String blockNumOrTag)
      throws JsonRpcInvalidParamsException {
    requireLatestBlockTag(blockNumOrTag);

    if (storageIdx == null || storageIdx.length() > MAX_STORAGE_KEY_HEX_LEN) {
      throw new JsonRpcInvalidParamsException("invalid storage key value");
    }

    byte[] addressByte = addressCompatibleToByteArray(address);

    DataWord index;
    try {
      index = new DataWord(ByteArray.fromHexString(storageIdx));
    } catch (Exception e) {
      throw new JsonRpcInvalidParamsException("invalid storage key value");
    }

    // get contract from contractStore
    BytesMessage.Builder build = BytesMessage.newBuilder();
    BytesMessage bytesMessage = build.setValue(ByteString.copyFrom(addressByte)).build();
    SmartContract smartContract = wallet.getContract(bytesMessage);
    if (smartContract == null) {
      return ByteArray.toJsonHex(new byte[32]);
    }

    StorageRowStore store = manager.getStorageRowStore();
    Storage storage = new Storage(addressByte, store);
    storage.setContractVersion(smartContract.getVersion());
    storage.generateAddrHash(smartContract.getTrxHash().toByteArray());

    DataWord value = storage.getValue(index);
    return ByteArray.toJsonHex(value == null ? new byte[32] : value.getData());
  }
