`git_object_directory` is a field on the `Repository` message defined in `proto/shared.proto`, which is embedded in essentially every RPC request (`Repository repository = 1`). This field is attacker-controlled from the perspective of an ordinary gRPC client — it's part of the `gitalypb.Repository` message that callers populate (used e.g. by `UserCommitFiles`, `PreReceiveHook`, and other RPCs to point Gitaly at a quarantine object directory established by `git-receive-pack`) [1](#0-0) .

### Title
Quarantine directory ownership check uses prefix match instead of exact match, allowing cross-request quarantine directory access - (File: internal/git/localrepo/paths.go)

### Summary
`Repo.ObjectDirectoryPath` validates a client-supplied `GitObjectDirectory` value by checking that it lies within a "manual" object-quarantine directory belonging to the repository. Instead of verifying the full, unique directory, it only checks that the resolved absolute path has a given string as a *prefix*, mirroring the same class of bug as the ENS `equals()` finding: a boundary check built on `HasPrefix`/length comparison that should require exact identity but instead accepts any value that merely shares a leading substring.

### Finding Description
`Repo.ObjectDirectoryPath` computes:

```go
expectedQuarantinePrefix := filepath.Join(tempDir, storage.QuarantineDirectoryPrefix(repo))
absoluteObjectDirectoryPath := filepath.Join(repoPath, objectDirectoryPath)

if !strings.HasPrefix(absoluteObjectDirectoryPath, expectedQuarantinePrefix) {
    return "", structerr.NewInvalidArgument("not a valid relative path: %w", origError)
}
``` [2](#0-1) 

`QuarantineDirectoryPrefix` returns a deterministic, repository-scoped string, `fmt.Sprintf("quarantine-%x-", hash[:8])`, based only on the repository's relative path [3](#0-2) . Actual quarantine directories are created with `tempdir.NewWithPrefix(ctx, storageName, QuarantineDirectoryPrefix(repo), ...)` [4](#0-3) , i.e. the deterministic prefix plus an unpredictable random suffix appended by the temp-dir helper, producing many *distinct* directories over time (one per concurrent push/operation) that all share the exact same `expectedQuarantinePrefix` string.

Because the validation is a bare `strings.HasPrefix` on the fully joined path rather than an exact match (or an "is this the one specific directory that this request created" check), **any** manual quarantine directory ever created for that repository — including ones created concurrently by a different push/operation/actor — satisfies the check. The comparison is directly analogous to the ENS `equals(bytes, offset, bytes)` bug: a length/prefix-style check (`self.length >= offset + other.length` / `HasPrefix`) is used where an exact boundary (`==` / exact directory identity) is required, letting a value that is merely "at least as long as, and starting the same as" the expected value pass a check meant to assert full equality.

### Impact Explanation
An ordinary, unprivileged gRPC client that can set the `GitObjectDirectory` field of the `Repository` message on a request (this field is part of `gitalypb.Repository`, forwarded by callers such as `PreReceiveHook`/other hook RPCs and read by `Repo.ObjectDirectoryPath` before it's used to compute `GIT_OBJECT_DIRECTORY`/build git commands) can point Gitaly's object-directory resolution at a *different*, concurrently-existing quarantine directory for the same repository, as long as its deterministic name prefix matches. This is a cross-request object access issue: objects that were quarantined by another in-flight push/operation on the same repository — and therefore not yet part of the permanent object database and not yet access-checked/hook-approved for the requesting operation — could be read or referenced through the wrong operation's context, and any code paths that trust `ObjectDirectoryPath` for read/consistency purposes are exposed to state confusion between concurrent, unrelated operations on the same repo.

### Likelihood Explanation
Likelihood is dependent on there being a second, concurrent legitimate quarantine directory in existence at the time of the request, and the client independently knowing (or being able to derive) the deterministic hash-based prefix and enough of the true directory to construct a matching relative path via `GitObjectDirectory`/`filepath.Join`. Since the prefix is fully deterministic from the repository's relative path (which any client operating on that repo already knows), and multiple concurrent quarantine directories are a normal, expected occurrence for busy repositories under simultaneous pushes, the precondition is realistically reachable by an ordinary client racing its own request against other in-flight ones, though it does not trivially defeat storage-root escape protections (the check still bounds the path to `tempDir`).

### Recommendation
Replace the prefix comparison with an exact-match check against a specific quarantine directory associated with the current request (e.g., store and compare the request's own quarantine directory path/ID rather than relying on the shared, repo-scoped literal prefix), or otherwise ensure `absoluteObjectDirectoryPath` corresponds to exactly one directory entry uniquely tied to the operation, not merely any path sharing the `quarantine-<hash>-` prefix.

### Proof of Concept
1. Repository `R` has relative path `P`; `QuarantineDirectoryPrefix` yields a fixed string `quarantine-<hash8>-` for `P`.
2. Two concurrent operations (e.g., two simultaneous pushes) against `R` each create their own quarantine directory under the storage temp dir: `.../tmp/quarantine-<hash8>-AAAA` and `.../tmp/quarantine-<hash8>-BBBB`.
3. A client for operation A sets `GitObjectDirectory` in its `Repository` message to a relative path that resolves to `.../tmp/quarantine-<hash8>-BBBB` (operation B's quarantine directory).
4. `Repo.ObjectDirectoryPath` computes `expectedQuarantinePrefix = tempDir/quarantine-<hash8>-` and checks `strings.HasPrefix(absoluteObjectDirectoryPath, expectedQuarantinePrefix)`, which returns true for the `BBBB` directory even though it does not belong to operation A's request, because the check never verifies the full directory name/identity, only the shared deterministic prefix [5](#0-4) .

Note: I was unable to fully trace every downstream RPC entry point that populates `GitObjectDirectory` from external client input across the whole codebase within the available search budget (the field appears in dozens of files); some of those call sites may additionally validate/override `GitObjectDirectory` server-side before it reaches `ObjectDirectoryPath`, which would reduce reachability. A full audit of all RPC handlers that forward the `Repository.git_object_directory` field from the wire without overriding it would be needed to confirm end-to-end exploitability with full confidence.

// QuarantineDirectoryPrefix returns a prefix for use in the temporary directory. The prefix is
// based on the relative repository path and will stay stable for any given repository. This allows
// us to verify that a given quarantine object directory indeed belongs to the repository at hand.
// Ideally, this function would directly be located in the quarantine module, but this is not
// possible due to cyclic dependencies.
func QuarantineDirectoryPrefix(repo Repository) string {
	hash := [20]byte{}
	if repo != nil {
		hash = sha1.Sum([]byte(repo.GetRelativePath()))
	}
	return fmt.Sprintf("quarantine-%x-", hash[:8])
}
