## Analysis

The tx.origin bug class is about using an unverified, self-declared "who is the real actor" value instead of the cryptographically-authenticated identity of the direct caller/party. In Nebula, the analogous ambient-trust decision point is in the relay-establishment control-plane handler, `relayManager.handleCreateRelayRequest`, which trusts the `RelayFromAddr` field carried inside a `NebulaControl_CreateRelayRequest` payload, sourced from the sender `h` (a `*HostInfo` whose only guaranteed property is that *its own* certificate/VPN address was verified during the handshake) — but never checks that the claimed `RelayFromAddr` actually equals `h`'s own certificate-verified VPN address (`h.vpnAddrs[0]`). The only sanity check performed is that the claimed "from" address is not one of *my* own addresses: [2](#0-1) 

After that, the code unconditionally binds a `TerminalType` relay entry on the sender's `HostInfo` (`h`) to the attacker-chosen `from` address: [3](#0-2) 

`AddRelay` then just writes this claim into `relayHostInfo.relayState` without any further verification against the certificate: [4](#0-3) 

### Title
Relay control plane trusts self-declared `RelayFromAddr` instead of the sender's certificate-verified VPN address, enabling relay/hostmap state poisoning — (File: `relay_manager.go`)

### Summary
`relayManager.handleCreateRelayRequest` derives the "who does this relay serve" binding from the `RelayFromAddr` field embedded in an authenticated-but-attacker-controlled `NebulaControl_CreateRelayRequest` payload, rather than from the cryptographically verified VPN address of the peer that actually sent the control message (`h.vpnAddrs[0]`). This is the same class of bug as the referenced `tx.origin` issue: a downstream trust decision is made using an ambient/self-asserted identity field instead of the identity that was actually authenticated for the current call/message.

### Finding Description
When a `HostInfo h` (whose identity was authenticated via the Noise handshake and certificate verification) sends a `CreateRelayRequest` control message, the message itself carries `RelayFromAddr`/`RelayToAddr` fields that are *not* cryptographically bound to `h`'s certificate — they are plain protobuf fields the sender can set to any value. `HandleControlMsg` only validates that these fields are non-nil: [5](#0-4) 

`handleCreateRelayRequest` then only rejects the case where the claimed `from` equals one of *my own* addresses (self-relay), never checks that `from == h.vpnAddrs[0]` (i.e., that the peer is only allowed to claim relay traffic on its own behalf) before registering `h` as a `TerminalType` relay for `from`: [6](#0-5) 

Because `h`'s identity was verified only for `h`'s own address, but the relay bookkeeping records "`h` is my relay path to reach `from`" using an unverified value, a compromised or malicious peer `h` can claim `from` = the VPN address of an arbitrary legitimate third-party host. This is directly analogous to the `tx.origin` phishing bug: the system infers the "true" originating party from an unauthenticated, self-reported field carried through an intermediary, instead of relying on the value that was actually authenticated at the point of the call.

### Impact Explanation
This corrupts the local hostmap's relay-routing state (`hostinfo.relayState`), a form of remote state poisoning: a compromised peer can register itself as a valid relay for a victim's VPN address it has no legitimate relationship with. Any subsequent decision keyed off this state (e.g., `QueryRelayForByIp`, `QueryVpnAddrsRelayFor`, `sshPrintRelays` reporting, and relay path selection in `SendVia`/`sendNoMetrics`) can then be misled into treating the malicious peer as an authorized relay path for traffic addressed to the victim, or produce confusing/incorrect relay topology state that other logic (migration, re-establishment) builds on.

### Likelihood Explanation
Exploitation requires only that the attacker be an already-connected Nebula peer able to send a `CreateRelayRequest` control message (no special privilege such as `am_relay` is required for the "target is me" branch) with a forged `RelayFromAddr`. No malicious lighthouse, no valid certificate for the impersonated address, and no MITM position are required — matching the "no CA-signed certificate for the impersonated identity" reachability constraint.

### Recommendation
When processing `CreateRelayRequest`/`CreateRelayResponse`, verify that the claimed `RelayFromAddr` (in the "target is me" branch) equals the sender's own certificate-verified VPN address (`h.vpnAddrs[0]` / one of `h.GetCert().Certificate.Networks()`), rejecting the request otherwise. Only in the middle-man ("target is not me") branch, where `from` legitimately refers to a third party the sender is relaying *for*, should a non-self value be accepted — and even then, cross-checks (e.g. against advertised relay lists from a trusted lighthouse) should be considered before establishing terminal relay state on behalf of an unverified claim.

### Proof of Concept
1. Attacker `A` (address `X`) establishes a normal, cert-verified Nebula tunnel to node `M`.
2. `A` sends `M` a `NebulaControl_CreateRelayRequest` with `RelayFromAddr = V` (a legitimate victim's VPN address, not `A`'s own) and `RelayToAddr = M`'s own address.
3. `handleCreateRelayRequest` on `M` sees `target == myVpnAddrsTable`, does not check `from == h.vpnAddrs[0]`, and calls `AddRelay(rm.l, h, f.hostMap, from, ...)`, registering `A`'s `HostInfo` as a `TerminalType` relay for `V` in `M`'s hostmap.
4. `M` now believes it can reach `V` via a relay through `A`, and any relay-state introspection (`sshPrintRelays`) or future relay-selection logic keyed on this entry reflects attacker-controlled, unverified data rather than `V`'s actual relay relationships.

func (rm *relayManager) handleCreateRelayRequest(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl) {
	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}

	// Is the target of the relay me?
	if f.myVpnAddrsTable.Contains(target) {
		existingRelay, ok := h.relayState.QueryRelayForByIp(from)
		if ok {
			switch existingRelay.State {
			case Requested:
				ok = h.relayState.CompleteRelayByIP(from, m.InitiatorRelayIndex)
				if !ok {
					logMsg.Error("Relay State not found")
					return
				}
			case Established:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
			case Disestablished:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
				// Mark the relay as 'Established' because it's safe to use again
				h.relayState.UpdateRelayForByIpState(from, Established)
			case PeerRequested:
				// I should never be in this state, because I am terminal, not forwarding.
				logMsg.Error("Unexpected Relay State found",
					"existingRemoteIndex", existingRelay.RemoteIndex,
					"state", existingRelay.State)
			}
		} else {
			_, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
			if err != nil {
				logMsg.Error("Failed to add relay", "error", err)
