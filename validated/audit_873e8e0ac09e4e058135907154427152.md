### Title
Unverified peer-supplied attachment content accepted into AtlasDB without matching requested `content_hash` - (`stackslib/src/net/atlas/download.rs`)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` inserts a peer's `GetAttachmentResponse.attachment` into the `attachments` `HashSet` without ever comparing `Attachment::hash()` to the `content_hash` of the `AttachmentRequest` that was sent. The subsequent commit path (`AttachmentsDownloader::run`) then calls `AtlasDB::insert_instantiated_attachment`, which recomputes the hash purely from the bytes it just received and blindly writes them to the `attachments` table.

### Finding Description
The download flow issues an `AttachmentRequest{content_hash: H1, ...}` and later resolves it in `extend_with_attachments`: [1](#0-0) 
There is no check here (or anywhere before insertion) that `response.attachment.hash() == request.content_hash`. Any peer answering a `GET /v2/attachments/<hash>` request can return an `Attachment{content: garbage}` and it is accepted into `self.attachments` unconditionally, as confirmed by the client-side decode which just performs JSON deserialization with no hash validation: [2](#0-1) 

The batch is then finalized in `AttachmentsDownloader::run`, which drains `context.attachments` and, for each attachment, recomputes `attachment.hash()` only to look up any existing matching `AttachmentInstance`s and to key the SQL insert — it never compares this recomputed hash to the specific `content_hash` (`H1`) that originally caused the fetch to be queued: [3](#0-2) 

`insert_instantiated_attachment` itself only ever writes `attachment.hash()` (i.e., `Hash160::from_data(&attachment.content)` of whatever bytes were supplied) as the primary key, and only updates `attachment_instances` rows whose `content_hash` happens to equal that computed hash: [4](#0-3) 

Because `attachments.hash` is `UNIQUE PRIMARY KEY` and always derived from the actual bytes written, `Hash160::from_data(garbage) == stored_hash` trivially holds — but that stored hash is generally **not** `H1`, the hash committed on-chain by the confirmed name/BNS operation that queued the original `AttachmentRequest`. The `AttachmentInstance` that triggered the fetch is never re-checked against the returned bytes; the garbage blob is simply persisted under its own self-consistent (but on-chain-uncommitted) hash, and `AttachmentsBatch::resolve_attachment` marks the *original* tracked `content_hash` entry as resolved/removed from the batch regardless of whether the returned bytes actually satisfy that hash: [5](#0-4) 

So a single malicious peer, in response to a legitimate attachment fetch for `H1`, can supply arbitrary bytes; the node stores those bytes under `Hash160(garbage)` in the `attachments` table and stops retrying for `H1` (treating it as "resolved"), even though no confirmed on-chain BNS/name operation ever committed to `Hash160(garbage)`.

### Impact Explanation
Any peer that a node syncs Atlas attachments from can inject arbitrary BLOBs into the local `attachments` table under a hash that was never committed by any confirmed contract-call attachment event, filling the table with junk data (bounded only by `max_uninstantiated_attachments`/eviction logic for the *uninstantiated* path, but `insert_instantiated_attachment` — reached via this exact flow — has no equivalent count/size eviction check shown in the traced code). It also causes the node to falsely mark the originally-requested `content_hash` as "resolved" without ever having obtained the real content, so a legitimately-needed attachment can be silently dropped from retry. This matches the "attachment/BNS mismatch" High-severity category: the node ends up storing/serving attachment data that no canonical name operation actually committed.

### Likelihood Explanation
Trivial and repeatable: any outbound sync peer the node selects (`network.get_outbound_sync_peers()`) can serve this response to a routine `/v2/attachments/<hash>` request; no signature, secret, or privileged role is required — this is a normal unauthenticated RPC response path. The attacker only needs to be a peer the node is willing to sync Atlas data from, which requires no special permission beyond running a reachable Stacks peer.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs`), before inserting into `self.attachments`, verify `response.attachment.hash() == request.content_hash`; on mismatch, treat it as a failed request (`report.bump_failed_requests()`) and do not insert. Additionally, `AtlasDB::insert_instantiated_attachment` should require/verify a caller-supplied expected hash rather than trusting `attachment.hash()` alone as authoritative for pairing with `attachment_instances`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
