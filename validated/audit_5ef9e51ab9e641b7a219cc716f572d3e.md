### Title
Out-of-bounds read in `InputZipFile::ProcessCentralDirEntry` when parsing a crafted ZIP/JAR central directory - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` reads variable-length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) directly from an attacker-controlled central directory header and advances the read cursor `p` by those values without ever verifying the cursor stays inside the mmap'd input buffer. This mirrors the libmobi bug class in CVE-2018-11437: a length/offset value taken straight from untrusted file structure is used to walk a buffer with no bounds check, producing a read access violation / out-of-bounds read.

### Finding Description
`ijar` (and `singlejar`'s equivalent code) memory-maps the whole input jar/zip file with `mmap(..., PROT_READ, ...)` [1](#0-0) , then processes the central directory over that raw buffer.

In `ProcessLocalFileEntry`, every variable-length read is preceded by an explicit `EnsureRemaining()` check against the mapped file's length before dereferencing: [2](#0-1) .

However, `ProcessCentralDirEntry`, which walks the *central directory* portion of the same buffer, performs **no equivalent bounds check at all**. It reads `file_name_length`, `extra_field_length`, and `file_comment_length` from attacker-controlled bytes and then advances `p` and `extra_p` by these values, and even follows a nested while-loop over "extra field" TLV records using a second attacker-controlled `data_size`, all without validating against the buffer end: [3](#0-2) .

The only prior validation is a single aggregate check in `FindZipCentralDirectory` that the *whole* central directory region (`central_dir_offset + central_dir_size`) fits within the file: [4](#0-3) . This does not bound any individual entry: a crafted header near the end of that region can declare `file_name_length`/`extra_field_length`/`file_comment_length` values that push `p` (and the `memcpy` read of the filename) past `bytes + in_length`, i.e., past the actual mmap'd region. The extra-field loop is even more fragile: `while (extra_p != p)` assumes `data_size` values divide evenly up to `p`; a crafted `data_size` can make `extra_p` overshoot `p`, causing the loop to keep dereferencing `get_u2le(extra_p)` far beyond the mapped file/central directory, i.e., an unbounded, uncontrolled out-of-bounds read: [5](#0-4) .

Since a jar's `mmap` is not padded (unlike the *output* mapping which intentionally over-allocates by a page specifically "to ensure any buffer overflow... will result in SIGSEGV" for detection purposes) [6](#0-5) , an out-of-bounds read that crosses a page boundary of the *input* mapping can hit an unmapped page and crash the process (info disclosure / read access violation), exactly the CVE-2018-11437 bug class (`mobi_reconstruct_parts` reading crafted offsets/lengths without bounds checking).

### Impact Explanation
`ijar` runs automatically as part of the default Java toolchain to produce interface jars for every `java_library`/`java_import` target, and equivalent central-directory-walking logic exists in `singlejar`. Both tools process third-party `.jar` files that can originate from untrusted, attacker-controlled sources reachable by an unprivileged origin (e.g., `http_jar`, `http_archive`/Maven artifacts consumed as byte content, or any jar checked into an untrusted CI branch). A single crafted jar dependency can therefore cause a native-code out-of-bounds read (crash, or in principle leak adjacent memory across the map boundary) purely by being consumed as a build input — with no other privileged access required.

### Likelihood Explanation
Any build that consumes an externally-fetched `.jar` as a Java dependency will run it through `ijar`/`singlejar`. Since central-directory parsing does zero bounds validation (unlike local-header parsing, which is properly guarded via `EnsureRemaining`), constructing a `.jar` whose central directory entry declares oversized `file_name_length`/`extra_field_length`/`file_comment_length`, or an extra-field TLV chain with an inconsistent `data_size`, is straightforward and does not require breaking any checksum, since Bazel does not validate the internal structure of a jar beyond the (optional) whole-file `sha256`/`integrity` of the downloaded archive — the archive's internal ZIP structure is fully attacker-controlled content once the outer hash (if any) matches.

### Recommendation
Add the same bounds validation used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry`: before reading/advancing past `file_name_length`, `extra_field_length`, `file_comment_length`, and each extra-field `data_size`, verify the resulting cursor position does not exceed the mapped buffer bounds (`bytes + in_length`) or the declared central directory region, and fail parsing with a clear error rather than proceeding.

### Proof of Concept
A reproducible test can be modeled after the existing `MalformedExtraField` singlejar test, but targeting `ijar`'s `ProcessCentralDirEntry` path (the analogous `output_jar_simple_test.cc` test already demonstrates the general technique of constructing a CDH/EOCD with an oversized `extra_field`/`payload_size` to trigger malformed-structure handling, but that test's target enforces bounds and aborts cleanly) [7](#0-6) . A new `BuildIntegrationTestCase`/`src/test/shell/bazel` test should:
1. Build a minimal ZIP with one Central Directory Header whose `file_name_length` + `extra_field_length` + `file_comment_length` sum exceeds the remaining bytes to end-of-file, while keeping the aggregate `central_dir_size` check in `FindZipCentralDirectory` satisfied.
2. Alternatively, craft an extra-field TLV chain inside the CDH extra fields where an entry's `data_size` does not align with the remaining `extra_field_length`, causing `extra_p` in the `while (extra_p != p)` loop to overshoot `p`.
3. Feed this file to the `ijar` binary (or invoke `ZipExtractor::Create`/`ProcessAll` directly in a unit test) and confirm the process crashes (SIGSEGV/SIGBUS) or reads out-of-bounds memory, rather than returning a controlled parse error, when run against a `java_library` depending on the crafted jar via `http_jar`.

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);

  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
