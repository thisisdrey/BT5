### Title
Unprivileged attacker can permanently block a victim from adding new collateral or debt positions by dust-filling `depositTokensOfAccount` to `MAX_TOKENS_PER_USER`, forcing liquidation losses - ([File: contracts/Pool.sol])

### Summary
CVE-2025-21580 is an easily-exploitable, low-complexity denial-of-service (repeatable crash/hang). The Metronome analog is a state-slot exhaustion DoS: `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert once an account's combined deposit-token + debt-token count reaches `MAX_TOKENS_PER_USER = 30` [1](#0-0) [2](#0-1) . Because `DepositToken.deposit(amount_, onBehalfOf_)` accepts an arbitrary beneficiary and `DepositToken._mint`/`_transfer` unconditionally push the token onto the recipient's per-account list, anyone can cheaply fill a victim's slots with dust and brick all subsequent `addTo*` calls for that account.

### Finding Description
- `DepositToken.deposit(uint256 amount_, address onBehalfOf_)` is a public, unauthenticated entry point that mints msdTOKEN to any `onBehalfOf_` address [3](#0-2) .
- `_mint` and `_transfer` call `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's prior balance is zero [4](#0-3) [5](#0-4) .
- `Pool.addToDepositTokensOfAccount` enforces `debtTokensOfAccount.length + depositTokensOfAccount.length < MAX_TOKENS_PER_USER` and reverts with `UserReachedMaxTokens` [2](#0-1) [6](#0-5) .
- `DebtToken._mint` applies the same limit for new debt positions via `pool.addToDebtTokensOfAccount` [7](#0-6) .

Attack path (all public, unprivileged):
1. Enumerate the pool's deposit tokens via `getDepositTokens()` and debt tokens via `getDebtTokens()`.
2. For each `DepositToken` the victim does not yet hold, call `depositToken.deposit(dust, victim)` (or acquire msdTOKEN and `transfer` dust to the victim). Each call pushes that token into `depositTokensOfAccount[victim]`.
3. Once `depositTokensOfAccount[victim].length + debtTokensOfAccount[victim].length == 30`, every subsequent call that would add a *new* token reverts: victim deposits of a new collateral type, inbound msdTOKEN transfers of new types, `DebtToken.issue`/`_mint` of a new synthetic debt, and SmartFarmingManager leverage deposits on the victim's behalf.

### Impact Explanation
This is a repeatable, deterministic availability break matching the CVE's "easily exploitable → hang/crash" class:

- **Forced liquidation / loss of funds**: A victim with an open debt position whose collateral is falling cannot deposit a *different* collateral type to restore health — `deposit` reverts with `UserReachedMaxTokens`. If they do not hold more of their existing collateral type, the position is liquidated and the liquidation incentive + protocol fee are seized from them [8](#0-7) .
- **Temporary freezing of functionality**: The victim cannot open new collateral/debt token positions, receive new msdTOKENs, or use leverage until they fully withdraw a token to zero (freeing a slot). Locked (debt-backed) collateral cannot be withdrawn, so while debt exists the freeze on new position types is effectively permanent for that account.
- The check cannot be bypassed by the victim: removing a slot requires burning the entire balance of one of the dusted tokens, which requires withdrawing it — possible, but only for unlocked balances, and each dusted token must be individually withdrawn/transferred, which itself costs the victim gas and may be impossible for tokens whose balance is locked against debt.

### Likelihood Explanation
- Fully unprivileged: any EOA can call `deposit(dust, victim)` — no governor, keeper, oracle, or privileged role is involved.
- Cost is dust amounts of each collateral underlying plus gas; nothing in `deposit`, `_mint`, `_transfer`, or `addToDepositTokensOfAccount` blocks a zero-health-factor-relevant dust amount. `SynthContext`/Operator paths do not change the outcome since `_msgSender` only needs to be a real DepositToken contract.
- No existing mitigation: `nonReentrant`, `whenNotPaused`, and `onlyIfDepositTokenExists` all pass for legitimate deposits; there is no opt-in or minimum-deposit threshold, and `DepositToken` transfers are unrestricted.
- Limitation: the victim can recover by emptying a dusted token balance (withdraw/transfer it fully), so impact is "temporary freeze + liquidation forcing" rather than permanent theft — consistent with Medium severity.

### Recommendation
- Do not auto-register tokens for the recipient on mint/transfer. Track the account's positions only for tokens they deposited/borrowed themselves, or let users opt in (e.g., a whitelist/claim step) before a token occupies a slot.
- Alternatively, only push to `depositTokensOfAccount` when the *sender* initiated the action for themselves (`onBehalfOf_ == _msgSender()` in `deposit`), and exempt `seize`/liquidation flows.
- As a partial mitigation, allow `withdraw`/repay paths to prune the list even when the balance isn't fully zero (e.g., keep entries sorted by balance or allow removal of dust below a threshold).

### Proof of Concept
Foundry/Hardhat fork sketch (Hardhat, repo-style):

```ts
// victim: alice has 1 collateral position (msdMET) + 1 debt (msEthDebtToken)
// attacker: bob
const depositTokens: IDepositToken[] = await pool.getDepositTokens() // all registered
// 1) Attacker dust-fills alice's account list
for (const dt of depositTokens) {
  if ((await dt.balanceOf(alice.address)).eq(0) && dt.address !== msdMET.address) {
    const underlying = await ethers.getContractAt('ERC20', await dt.underlying())
    await underlying.connect(bob).approve(dt.address, MaxUint256)
    await dt.connect(bob).deposit(1, alice.address) // 1 wei dust to alice
  }
}
expect(await pool.getDepositTokensOfAccount(alice.address)).to.have.lengthOf(/* 30 - debtCount */)

// 2) alice's collateral crashes -> she is unhealthy and tries to deposit a NEW collateral type
await masterOracle.updatePrice(met.address, crashedPrice)
const tx = newDepositToken.connect(alice).deposit(parseEther('100'), alice.address)
await expect(tx).revertedWithCustomError(pool, 'UserReachedMaxTokens') // in Pool.addToDepositTokensOfAccount

// 3) new debt positions are bricked too
await expect(msUsdDebtToken.connect(alice).issue(1, alice.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')

// 4) anyone can now liquidate alice; she could not add the collateral that would have cured her
await pool.connect(liquidator).liquidate(msEth.address, alice.address, maxRepay, msdMET.address)
```

The test suite already confirms the revert path at `Pool.sol` (`should revert when reach max tokens`) [9](#0-8) ; the gap is that third parties can force a victim across the threshold via `deposit(..., onBehalfOf_)` / `transfer` dust, which no test covers.
