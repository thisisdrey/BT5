### Title
`ExchangeInjectContract` and `ExchangeWithdrawContract` execute AMM ratio-based mint/burn without any slippage/minimum-received protection - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeInjectActuator` and `ExchangeWithdrawActuator` both compute a counter-asset amount (`anotherTokenQuant`) from the current on-chain AMM pool ratio at execution time and mint/burn the account's asset balances accordingly, exactly like the reported `depositIntoRewardPool()`/`withdrawFromRewardPool()` pattern that mints/burns ERC4626 shares from a live, fluctuating exchange ratio. Unlike `ExchangeTransactionContract`, which carries an `expected` minimum-received field enforced in `ExchangeTransactionActuator`, neither `ExchangeInjectContract` nor `ExchangeWithdrawContract` has any minimum/maximum bound field, so a transaction broadcast against one ratio can execute against a materially different ratio if the pool is moved by other transactions (e.g. `ExchangeTransactionContract` swaps) ordered before it in the same block.

### Finding Description
`ExchangeTransactionContract` explicitly supports slippage protection via its `expected` field [1](#0-0) , which `ExchangeTransactionActuator.doValidate()` enforces by rejecting the transaction if the computed `anotherTokenQuant` is below `tokenExpected` [2](#0-1) .

In contrast, `ExchangeInjectContract` and `ExchangeWithdrawContract` have no analogous `expected`/minimum field [3](#0-2) . Their actuators compute the counter-asset quantity purely from the live pool balances at execution time and immediately mutate account balances and the exchange reserves with no bound on the deviation between the value assumed at broadcast time and the value realized at execution time:

- `ExchangeInjectActuator.execute()` computes `anotherTokenQuant` from `firstTokenBalance`/`secondTokenBalance` and reduces the caller's balance of both tokens by whatever the current ratio dictates [4](#0-3) .
- `ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` from the current pool ratio and credits the caller accordingly, again with no expected/minimum check [5](#0-4) .

Both operations are restricted to the exchange's creator address (`account[...] is not creator`) [6](#0-5) [7](#0-6) , which mirrors the `msg.sender == veALCX` restriction in the reported `RewardPoolHandler` functions — a privileged-but-still-reachable single-signer path, not a validator/witness-only path. Any unprivileged account can still submit `ExchangeTransactionContract` swaps that shift `firstTokenBalance`/`secondTokenBalance` before the creator's inject/withdraw transaction is packed into a block, because transaction ordering within a block is controlled by the block-producing witness, not the submitter, and Tron's mempool/ordering gives no guarantee that a broadcast transaction executes against the ratio observed when it was signed.

### Impact Explanation
Because there is no bound on the computed `anotherTokenQuant`, a pool ratio shift between broadcast and execution (via unrelated `ExchangeTransactionContract` swaps or a same-block `ExchangeInject`/`ExchangeWithdraw`) causes the creator to inject more value than intended or withdraw less value than expected, with the difference effectively captured by whoever moved the ratio. This matches the reported impact class "Contract fails to deliver promised returns" / "Theft of unclaimed yield" — the creator loses value relative to the ratio they observed and signed against, without any mechanism to cap this loss or abort the transaction.

### Likelihood Explanation
The exchange creator address is a single, specific account (whoever created that trading pair), so this is not exploitable against arbitrary users, but it is directly analogous to the `veALCX`-gated functions in the report: a real, currently-deployed on-chain feature reachable by a single signed transaction, with the ratio-shifting precondition (other `ExchangeTransactionContract` swaps) freely triggerable by any unprivileged account. Given `ExchangeTransactionContract` already required a fix (the `expected` field) for exactly this class of issue, the omission on Inject/Withdraw is a genuine gap in the same subsystem.

### Recommendation
Add an `expected`/`min_receive` (for withdraw) and `max_cost`/similar bound (for inject) field to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` and `ExchangeWithdrawActuator.doValidate()`/`execute()` the same way `tokenExpected` is enforced in `ExchangeTransactionActuator`, rejecting the transaction if the computed `anotherTokenQuant` falls outside the caller-specified bound.

### Proof of Concept
1. Creator observes pool ratio R0 and signs an `ExchangeWithdrawContract` expecting to receive `anotherTokenQuant0` computed from R0.
2. Before this transaction is packed, an unprivileged account submits an `ExchangeTransactionContract` swap that shifts the pool to ratio R1 (allowed, no permission check beyond normal balance checks, per `ExchangeTransactionActuator.doValidate()`).
3. Both transactions are included in the same block (or the swap is included in an earlier block reachable before the withdraw is processed); `ExchangeWithdrawActuator.execute()` recomputes `anotherTokenQuant` from the now-shifted `firstTokenBalance`/`secondTokenBalance` [8](#0-7) , crediting the creator a different (lower) amount than assumed at signing time, with no validation step to reject the deviation.
