### Title
Fixed-window (non-sliding) per-connection stream throttle allows ~2x instantaneous burst at window boundaries - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Finding Description
`ConnectionStreamCounter::reset_throttling_params_if_needed` implements a **fixed-window counter**, not a sliding window: it only resets `stream_count` and `last_throttling_instant` when `now - last_throttling_instant > STREAM_THROTTLING_INTERVAL` (100ms), and the new window boundary is set to whatever instant the triggering stream happened to arrive at [1](#0-0) . `throttle_stream` then checks `stream_count >= max_streams_per_throttling_interval` and, if exceeded, sleeps only until `throttle_interval_start.elapsed()` reaches the interval boundary [2](#0-1) .

Because the counter tracks "streams since last reset" rather than "streams in the trailing 100ms," an attacker who controls stream arrival timing can concentrate `max_streams_per_throttling_interval` streams at the very end of window N (just before the reset threshold is crossed) and another full `max_streams_per_throttling_interval` streams immediately at the start of window N+1 (right after the reset). Both bursts land inside an actual wall-clock span far smaller than `STREAM_THROTTLING_INTERVAL`, so a sliding 100ms window measured around the boundary observes close to `2 * max_streams_per_throttling_interval` streams — double the intended per-connection ceiling — even though each fixed window individually never exceeds its own budget.

This is reachable by any unstaked/low-stake remote peer: streams arrive via `connection.accept_uni()` in `handle_connection`, which calls `qos.on_new_stream` → `throttle_stream` before incrementing the counter in `on_stream_accepted` [3](#0-2) , and `SwQosController::on_new_stream` wires this directly to `throttle_stream`/`ConnectionStreamCounter` for real connections [4](#0-3) . No sigverify, dedup, or additional rate-limit guard sits between stream acceptance and this counter check, so nothing else stops the boundary-straddling burst.

### Impact Explanation
An attacker can transiently push up to ~2x the configured per-connection stream/tx ingress rate for a brief window around each 100ms boundary, repeatable at every subsequent boundary. This falls under the QoS-evasion bounty category: the per-connection cap that is supposed to bound a single connection's share of leader TPU capacity can be locally violated by ~2x, letting one connection crowd out other connections' fair share during that burst. The effect is bounded (not unbounded amplification) — over any *aligned* 100ms window the cap is still respected — so the impact is a transient fairness/QoS degradation rather than resource exhaustion or consensus-affecting behavior.

### Likelihood Explanation
Feasibility requires only: (1) an unstaked/low-stake QUIC connection to the TPU port, (2) the attacker's ability to measure/derive the current window boundary (observable via connection RTT and the deterministic `sleep(throttle_duration)` back-off behavior when throttled, which reveals when the next window starts), and (3) sending streams in two tight bursts straddling that boundary. This is a client-side timing trick with no need for staked keys, gossip, or validator control, and is repeatable at every window transition (roughly every 100ms), making it low-effort and highly repeatable.

### Recommendation
Replace the fixed-window reset with a true sliding-window or token-bucket algorithm (similar to `TokenBucket`/`ConnectionRateLimiter` already used elsewhere in `streamer/src/nonblocking/quic.rs` and the alternative `simple_qos.rs` `on_new_stream` path, which uses `stream_counter.consume_tokens`/`us_to_have_tokens` instead of a hard reset) so that the enforced invariant becomes "no more than N streams in *any* trailing `STREAM_THROTTLING_INTERVAL`," not just "no more than N streams since the last reset."

### Proof of Concept
```rust
// streamer/src/nonblocking/stream_throttle.rs (test module)
#[tokio::test(start_paused = true)]
async fn test_boundary_straddle_doubles_burst() {
    use std::sync::Arc;
    let stats = Arc::new(StreamerStats::default());
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max_streams = 20u64; // e.g. unstaked cap per 100ms

    // Fill window N almost to the reset boundary.
    for _ in 0..max_streams {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, "127.0.0.1:0".parse().unwrap(),
                         &counter, max_streams).await;
        counter.stream_count.fetch_add(1, std::sync::atomic::Ordering::Relaxed);
    }

    // Advance time just past STREAM_THROTTLING_INTERVAL to trigger the reset
    // on the *next* call, simulating a stream arriving right after the boundary.
    tokio::time::advance(STREAM_THROTTLING_INTERVAL + Duration::from_micros(1)).await;

    let window_start = std::time::Instant::now();
    // Second burst: full max_streams again, essentially back-to-back with the first burst.
    for _ in 0..max_streams {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, "127.0.0.1:0".parse().unwrap(),
                         &counter, max_streams).await;
        counter.stream_count.fetch_add(1, std::sync::atomic::Ordering::Relaxed);
    }

    // Assert: total streams accepted across the two adjacent bursts (2*max_streams)
    // occurred within a wall-clock span << 2*STREAM_THROTTLING_INTERVAL,
    // i.e. close to 2*max_streams within one sliding STREAM_THROTTLING_INTERVAL window
    // centered on the boundary — violating the intended per-interval cap.
    assert!(window_start.elapsed() < STREAM_THROTTLING_INTERVAL);
}
```
This demonstrates that `ConnectionStreamCounter`'s reset logic bounds streams only within its own (traffic-triggered) fixed window, not within any sliding `STREAM_THROTTLING_INTERVAL`, letting a timed attacker double the effective burst rate at each boundary.

    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
