### Title
Non-atomic replay-window check-then-update allows packet replay across concurrent UDP reader routines - ([File: connection_state.go])

### Summary
The report's core bug pattern is a **decision made from a value that is read at one moment but can be invalidated/changed before the corresponding state update is committed** — i.e., a check-then-act gap that an attacker exploits by acting inside that gap. In Nebula, the exact same class of gap exists in the replay-window logic used to authenticate/de-duplicate incoming ciphertext, not in a voting system but in `ConnectionState.Decrypt` / `VerifyRelay`.

### Finding Description
`ConnectionState.Decrypt` performs the replay check and the replay-window update as two separate critical sections, with the actual AEAD decryption happening *outside* the lock in between them: [1](#0-0) 

```
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)   // (1) check
cs.decryptLock.Unlock()
...
out, err = cs.dKey.DecryptDanger(...)          // (2) decrypt (no lock)
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)   // (3) commit "seen"
cs.decryptLock.Unlock()
```

`Bits.Check` only tests whether a counter has *already* been marked seen; it does not itself mark it seen — that only happens in `Update`: [2](#0-1) 

Because `Check` and `Update` are two independent, unlocked-in-between operations, two goroutines processing the same wire packet (or an attacker who captures a valid ciphertext and replays it a second time before the first copy's `Update` call runs) can both pass `Check` for the same `messageCounter`, both successfully run `DecryptDanger`, and both proceed to deliver plaintext / respond, exactly one packet late in the pipeline from being treated as a duplicate. `VerifyRelay` has the identical pattern: [3](#0-2) 

This is reachable purely from the network: an unauthenticated attacker who has captured (or is on-path for) a single valid ciphertext packet from an established tunnel can fire two (or more) copies of it at the receiving Nebula node in quick succession. Nebula's UDP layer is explicitly designed to support multiple concurrent reader routines bound to the same port via `SO_REUSEPORT` (`listen.routines`), so duplicated packets delivered to different reader goroutines land in `readOutsidePackets` concurrently and reach `hostinfo.ConnectionState.Decrypt` for the *same* `ConnectionState` object at the same time: [4](#0-3) [5](#0-4) 

This mirrors the reported bug class precisely: "a value (here, replay-window membership) is checked, but the authoritative state that should have been the single-source-of-truth for the decision is only committed after the sensitive action (decryption/processing) — leaving a window where the value can no longer be trusted."

### Impact Explanation
A successful race lets an attacker replay a single sniffed application-layer ciphertext packet through the tunnel a second time. Depending on the payload this can duplicate application-level messages (e.g. duplicate transactions/commands relayed over the tunnel), or repeatedly trigger side effects tied to packet delivery (roaming updates, `connectionManager.In`, firewall conntrack state, or forwarding through the tun device) using a packet that should have been rejected as a duplicate. It does not by itself break confidentiality of the AEAD, but it defeats the intended one-packet-per-counter guarantee of the replay window, the same “stale/duplicated state accepted as valid” impact class described in the report.

### Likelihood Explanation
Exploitability requires (a) the ability to capture or otherwise obtain a valid ciphertext+counter pair from an existing tunnel, and (b) `listen.routines`/multiple reader goroutines being enabled (which Nebula explicitly supports and documents as a performance feature), so that two deliveries of the duplicated datagram are processed by different goroutines close together in time. This is a narrower race window than a straightforward logic bug, but it is deterministically reproducible by an attacker that can inject the same UDP datagram twice in rapid succession while multiple reader routines are active — no CA-signed certificate or valid handshake key material is needed by the attacker, only a copy of one legitimate ciphertext packet.

### Recommendation
Make the replay check-and-mark atomic: hold `decryptLock` across the "is-this-counter-already-seen" test and its corresponding window update, or fold `Check`+`Update` into a single locked operation performed *before* decryption is attempted, so that a second concurrent delivery of the same counter is rejected before `DecryptDanger` runs rather than being allowed to race past the check.

### Proof of Concept
1. Establish a tunnel between two Nebula nodes with `listen.routines` > 1 (multiple UDP reader goroutines, `SO_REUSEPORT`).
2. Passively capture one legitimate data-plane ciphertext packet (`header.Message`) sent by peer A to peer B, noting its `MessageCounter`.
3. As an attacker, send two copies of that exact captured UDP datagram to peer B "simultaneously" (back-to-back, aimed to land on two different SO_REUSEPORT-bound listener sockets/goroutines).
4. Because `Bits.Check` in both goroutines runs before either goroutine's `Bits.Update` commits the counter as seen (`connection_state.go:61-82`), both goroutines can pass the replay check, both successfully decrypt (same key/nonce, valid ciphertext), and the packet is processed twice by peer B instead of the second copy being dropped with `ErrAlreadySeen`.

Note: I was not able to fully verify from the indexed code whether the two SO_REUSEPORT listener sockets actually load-balance duplicate datagrams to different reader goroutines in a way that reliably produces the race in practice (kernel-level scheduling details for `SO_REUSEPORT`/`recvmmsg` batching are outside what the index surfaces), so the practical reliability of triggering the race under real-world scheduling is uncertain and would benefit from further runtime testing.

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
