### Title
Gas-key nonce reset on DeleteKey+AddKey reseeds by block height only, allowing replay of an already-executed gas-key transaction - (File: `runtime/runtime/src/access_keys.rs`, `runtime/runtime/src/verifier.rs`)

### Summary
`add_gas_key` re-seeds every nonce slot to `initial_nonce_value(block_height) = (block_height-1) * 1_000_000`, independent of the highest nonce that slot ever reached before deletion. If a gas key is deleted and re-added (with a smaller or equal `num_nonces`) for the same public key in the same block height as an earlier high-value nonce consumption, the new per-index nonce can be lower than an already-consumed nonce for that index, letting an old signed transaction be replayed and re-executed.

### Finding Description
- `add_gas_key` (`runtime/runtime/src/access_keys.rs:194-228`) seeds every nonce index with a single value derived only from the current block height:
```
let nonce = initial_nonce_value(block_height);   // (block_height-1) * 1_000_000
for i in 0..num_nonces { set_gas_key_nonce(..., i, nonce); }
```
`initial_nonce_value` (`access_keys.rs:46-50`) has no knowledge of, and does not read, any previously stored nonce for that `(account_id, public_key, index)` triple.
- `action_delete_key` → `delete_gas_key` (`access_keys.rs:52-134`) fully removes the access key and all its nonce entries, and `action_add_key` (`access_keys.rs:149-192`) only rejects re-adding a key if `get_access_key` still finds an existing entry (`AddKeyAlreadyExists`, `:157-164`) — after a `DeleteKey`, the same public key can be re-added with a *different* `num_nonces` in the very same block.
- `verify_and_charge_gas_key_tx_ephemeral` (`runtime/runtime/src/verifier.rs:370-479`) only checks `nonce_index >= gas_key_info.num_nonces` (`:408-413`) — a purely range check against the *current* `num_nonces`, with no memory of a prior, larger `num_nonces`.
- `verify_nonce` (`verifier.rs:210-237`) is the sole replay guard: `Monotonic` requires `tx_nonce > current_nonce`, and enforces only `tx_nonce < block_height * 1_000_000` as an upper bound.

Exploit flow (single account, self-controlled, no privileged access needed):
1. Attacker owns account `alice`, adds a `GasKeyFullAccess` gas key with `num_nonces = 4` and funds it.
2. At block height `H`, attacker submits gas-key transactions consuming nonce index 0 up to a nonce value `X` close to the upper bound, i.e. `(H-1)*1_000_000 < X < H*1_000_000`. This is achievable because a signer fully controls the nonce value it puts in its own signed transactions.
3. In the *same block height* `H`, attacker submits `DeleteKey` (removing the gas key and wiping all nonce entries) followed by `AddKey` re-adding the identical public key with `num_nonces = 1`. `add_gas_key` reseeds index 0 to `(H-1)*1_000_000`, which is strictly less than `X` by construction.
4. `nonce_index = 0` is still `< num_nonces (1)`, so `InvalidNonceIndex` does not trigger.
5. Attacker (or anyone holding the originally broadcast signed bytes) resubmits the *original* signed transaction with `nonce = X`, `nonce_index = 0`. At the later inclusion height `H' > H`: `verify_nonce` passes because `X > (H-1)*1_000_000` (the reset value) and `X < H'*1_000_000`. The transaction is accepted and executed a second time with the identical signature/hash.

This bypasses the "authorization exactness / no double execution" invariant: a signed transaction, once finalized, is executed again solely because the signer chose to shrink/recreate the gas key at the same block height as the original consumption.

### Impact Explanation
This is a concrete double-spend/replay primitive against gas-key transactions (NEAR bounty category: "double-spend/replay"). Concretely, any action authorized by the replayed transaction is re-executed: a `Transfer`, or a `FunctionCall` under a `GasKeyFunctionCall` permission (e.g., "claim reward"/"withdraw from pool" style calls on a contract that is not itself idempotent), fires a second time using the identical old signature. If the gas key balance and/or account balance are refunded after the reset (`TransferToGasKey`/`Transfer`), the replay can drain that refunded balance or cause a second real transfer/receipt to be produced from a single authorization — this is a genuine break of the nonce replay-protection guarantee gas keys are supposed to provide, not merely a resource-hygiene nit. The scope of self-harm vs third-party harm depends on what the replayed action does (e.g., a call into a shared contract that isn't itself idempotent is the clearest theft vector); the on-chain mechanism itself unambiguously permits double execution of an already-finalized signed transaction.

### Likelihood Explanation
- Fully attacker-controlled: requires only ordinary account actions (`AddKey`/`DeleteKey`/`Transfer`/gas-key transactions) that any unprivileged client can submit.
- Requires precise but easily achievable timing: getting the nonce-consuming tx and the `DeleteKey`+`AddKey` pair included within the same block height (attacker fully controls nonces and can retry across blocks until the timing aligns; the 1,000,000-wide nonce window per height gives ample slack).
- Repeatable: the attacker can perform this cycle repeatedly with different indices/heights.
- Cost is limited to normal gas/storage fees for the AddKey/DeleteKey/transaction actions.

### Recommendation
When recreating a gas key nonce slot (via `add_gas_key`), do not blindly reseed to `initial_nonce_value(block_height)`. Options:
- Track and persist a per-`(account_id, public_key)` (or account-wide) monotonic "highest nonce ever used" watermark that survives `DeleteKey`, and seed new gas-key nonce entries to `max(initial_nonce_value(block_height), watermark + 1)`.
- Alternatively, disallow reusing the exact same public key for a new gas key within the same block height as its previous deletion, or require `num_nonces` growth to always start new indices at a value at least as large as `block_height * 1_000_000` regardless of the deletion height of the same key.

### Proof of Concept
Unit test in `runtime/runtime/src/verifier.rs`, adapted from `test_gas_key_tx_nonce_index_out_of_range`:
1. `setup_gas_key_account` with `num_nonces = 4` at `block_height = H` (via `action_add_key`), fund the gas key.
2. Manually call `set_gas_key_nonce` (or drive it through `verify_and_charge_gas_key_tx_ephemeral` + apply) to advance nonce index 0 to `X` where `(H-1)*1_000_000 < X < H*1_000_000`. Save a `SignedTransaction` (`tx_old`) with `TransactionNonce::from_nonce_and_index(X, 0)`.
3. At the same `block_height = H`, call `action_delete_key` for the gas key's public key (asserting nonce entries removed), then `action_add_key` re-adding the same public key with `num_nonces = 1`.
4. Assert `get_gas_key_nonce(..., index 0)` now equals `(H-1)*1_000_000 < X`.
5. Call `verify_and_charge_gas_key_tx_ephemeral`/`validate_verify_and_charge_transaction` with `tx_old` at a later `block_height = H' > H` and assert it returns `TxVerdict::Success` (i.e., the stale, already-consumed nonce/index pair is wrongly accepted), demonstrating replay of a transaction that had already been finalized once.
