This confirms it: `FindRefsByOID` is a unary RPC that accumulates an unbounded number of results into an in-memory `[]string` slice before returning a single response, with no default cap on the number of matched refs.

### Title
Unbounded ref accumulation in `FindRefsByOID` unary RPC enables memory/CPU exhaustion DoS - ([File: internal/gitaly/service/ref/find_refs_by_oid.go])

### Summary
The `FindRefsByOID` RPC handler loops over every reference returned by `git-for-each-ref(1)` and appends each one to an in-memory `refs []string` slice before sending a single unary response. When the client-supplied `Limit` field is left at its default value of `0`, no `--count` flag is passed to `for-each-ref` and the loop is effectively unbounded, mirroring the reported AnteTest bug class of "looping over an array of unbounded size" causing denial of service.

### Finding Description
`FindRefsByOID` builds a `gitpipe.ForEachRef` iterator with `gitpipe.WithCount(int(in.GetLimit()))` [1](#0-0) . The proto documents `limit` as "0 means no limit" [2](#0-1) . Inside `gitpipe.ForEachRef`, the `--count` flag is only added `if cfg.count > 0` [3](#0-2) , so when `Limit` is unset, `git-for-each-ref` is invoked without any cap and streams every matching reference back through the pipe.

The handler then consumes this iterator in an unbounded loop, appending every single matched reference name into an in-memory Go slice: `for forEachRefIter.Next() { refs = append(refs, string(forEachRefIter.Result().ObjectName)) }` [4](#0-3) . Because `FindRefsByOID` is a unary (non-streaming) RPC, the entire `refs` slice must be built and held in memory before a single `FindRefsByOIDResponse` can be returned [5](#0-4) . Default patterns fall back to `refs/tags/` and `refs/heads/` when none are provided [6](#0-5) , so any ordinary user who can push a large number of branches/tags to a repository can inflate the number of matching references arbitrarily.

This differs from the sibling `ListRefs` RPC, which is a *streaming* RPC with mandatory pagination support (`PaginationParameter`, `PageToken`, chunked responses) as seen in its handler and tests [7](#0-6) [8](#0-7) , which naturally bounds per-message memory even for huge ref counts. `FindRefsByOID` has no equivalent pagination and no server-enforced maximum on `Limit`.

Gitaly's only generic backpressure mechanism is the optional per-RPC concurrency limiter, which throttles the number of *concurrent* calls to an RPC per repository, but does not cap the amount of work or memory a single call may consume [9](#0-8) [10](#0-9) . This is opt-in configuration and does not protect against a single expensive unbounded call.

### Impact Explanation
A repository with a very large number of branches/tags matching the target OID (or matching default `refs/heads/`+`refs/tags/` patterns when patterns aren't restricted) causes the server to allocate memory proportional to the number of matching refs and to hold the entire process (`git for-each-ref` scan + string building + response marshaling) before responding. With enough refs, this can exhaust Gitaly worker memory or CPU, or trigger gRPC max-message-size failures only after significant work has already been done, degrading or denying service for the RPC handler and potentially the whole storage shard under concurrent requests.

### Likelihood Explanation
Any client with ordinary push access can create a large number of refs in a repository they control (this is a normal git operation, not requiring elevated privileges), then invoke `FindRefsByOID` with `Limit=0` (the default, and the documented "no limit" value) to trigger the unbounded accumulation. No authentication bypass or privileged actor is required beyond standard repository write access, making this readily reachable from a crafted RPC field (`Limit=0` combined with a ref-heavy repository).

### Recommendation
- Enforce a mandatory server-side maximum on the number of refs returned by `FindRefsByOID` regardless of client-supplied `Limit`, similar to how other unary RPCs cap result sizes.
- Convert `FindRefsByOID` to a streaming RPC with cursor-based pagination, following the pattern already implemented for `ListRefs`, so that memory usage per call is bounded independent of total ref count.
- Alternatively, reject or clamp `Limit=0` requests above a configurable ref-count threshold before invoking `git-for-each-ref`.

### Proof of Concept
1. As an ordinary user with push access, create a large number of branches/tags in a repository (e.g., hundreds of thousands) via normal `git push` operations.
2. Call the `FindRefsByOID` RPC with `Limit` unset (defaults to `0`, "no limit") and an `Oid` that no ref points to, or `RefPatterns` matching all the created refs.
3. Observe that the server executes `git-for-each-ref` without a `--count` cap [3](#0-2)  and accumulates every matched reference into memory before returning a single response [4](#0-3) , causing elevated memory/CPU usage proportional to the number of refs, with no per-call bound enforced by the server.

// UnaryInterceptor returns a Unary Interceptor
func (c *LimiterMiddleware) UnaryInterceptor() grpc.UnaryServerInterceptor {
	return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {
		lockKey := c.getLockKey(ctx)
		if lockKey == "" {
			return handler(ctx, req)
		}

		// Check if request is authenticated
		limiter := c.methodLimiters[info.FullMethod]
		unauthLimiter, ok := c.methodLimitersUnauthenticated[info.FullMethod]
		if !auth.IsAuthenticated(ctx) && ok {
			limiter = unauthLimiter
		}

		if limiter == nil {
			// No concurrency limiting
			return handler(ctx, req)
		}

		return limiter.Limit(ctx, lockKey, func() (interface{}, error) {
			return handler(ctx, req)
		})
	}
}
