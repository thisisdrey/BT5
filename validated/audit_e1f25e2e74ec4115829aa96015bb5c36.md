### Title
Attachments-inv page-index parsing builds a full `HashSet<u32>` before the `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` cap is ever checked - ([File: stackslib/src/net/api/getattachmentsinv.rs])

### Summary
`RPCGetAttachmentsInvRequestHandler::try_parse_request` parses every comma-separated value in the `pages_indexes` query parameter, inserting each into a `HashSet<u32>`, with no per-request cap applied during parsing. The `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` (8) check is only enforced later, in `try_handle_request`, after the full set has already been built and sorted into a `Vec<u32>`.

### Finding Description
The claimed equality break is real: parsing work performed on `pages_indexes` is decoupled from the bound that is supposed to limit it. In `try_parse_request` [1](#0-0) , the handler iterates every `entry` in the comma-separated `pages_indexes` value, parses it as `u32`, and unconditionally inserts it into a `HashSet<u32>` — with no length check anywhere in this function. Only after `try_parse_request` returns and the request proceeds to `try_handle_request` is `page_indexes.len() > MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` checked [2](#0-1) . Additionally, `try_parse_request` itself sorts the entire collected set into a `Vec<u32>` before returning [3](#0-2) , meaning the full parse-insert-sort cost is paid regardless of the eventual 8-page cap.

An attacker can send a single `GET /v2/attachments/inv?index_block_hash=<32-byte-hex>&pages_indexes=1,2,3,...,N` request with as many distinct numeric entries as fit within the node's HTTP request/header size limit. Each entry costs a `u32::parse` and a `HashSet` insertion (hashing + potential resize), and the whole set is subsequently sorted — all before the 8-page cap has any chance to reject the request. The number of entries an attacker can pack is bounded only by the HTTP layer's maximum request/header size, not by any explicit cap tied to `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST`.

### Impact Explanation
This is a bounded compute/allocation amplification on a read endpoint: a single unauthenticated GET request forces the node to perform O(n) parsing, hashing, and set-insertion work (plus a sort) for a value of n far larger than the eventual permitted page count of 8, before the request is finally rejected. This matches the "bounded compute DoS on a read endpoint" category. It is repeatable per request and requires no privileges — `/v2/attachments/inv` is an unauthenticated RPC endpoint reachable by any remote client.

### Likelihood Explanation
No preconditions beyond network reachability to the node's RPC port are required. The attacker only needs to construct a query string; no signature, secret, or peer state is needed. The amplification factor is limited by the maximum HTTP request/header size the node's HTTP layer accepts (not confirmed here — the exact limiting constant in the HTTP framing/parsing layer could not be located in this pass), so the amplification, while real, is bounded rather than unbounded per request.

### Recommendation
Move the `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` bound check into `try_parse_request`, enforcing it incrementally while iterating `pages_indexes` entries (e.g., reject or stop inserting once the set size would exceed the cap) rather than after the full `HashSet` has been built and sorted.

### Proof of Concept
Add a stackslib net test that constructs a query string `index_block_hash=<valid 32-byte hex>&pages_indexes=` followed by e.g. 100,000 distinct comma-separated integers, and calls `RPCGetAttachmentsInvRequestHandler::try_parse_request` directly with this query. Assert that `self.page_indexes` after the call contains all 100,000 entries (i.e., the full `HashSet`/`Vec` was materialized and sorted) despite exceeding `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` (8), demonstrating the parse cost is paid before the cap check in `try_handle_request` ever runs.
