### Title
Anti-replay window Check/Update race allows duplicate packet acceptance - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split their anti-replay bookkeeping into two separately-locked steps — a `window.Check` before the AEAD operation and a `window.Update` after it — releasing `decryptLock` in between. This breaks the intended Checks-Effects-Interactions ordering for replay protection: the "effect" that actually prevents replay (marking the counter as seen) happens only after the expensive interaction (AEAD decrypt), with no lock held across the gap. When packets are processed concurrently — which the interface architecture explicitly allows via multiple UDP reader goroutines — two threads can both pass `Check` for the same `messageCounter` before either calls `Update`, and both then successfully decrypt and hand the same message to the caller as legitimate traffic.

### Finding Description
`Decrypt` and `VerifyRelay` in `connection_state.go` each perform:
1. Lock, `window.Check(messageCounter)`, unlock.
2. Perform `DecryptDanger` (AEAD open) with no lock held.
3. Lock, `window.Update(messageCounter)`, unlock. [2](#0-1) 

`Bits.Check` only tests whether the counter has already been recorded; it does not itself mark the counter as seen — only `Update` does that, and it runs on a separate lock acquisition after the AEAD operation completes. [3](#0-2) 

Because the state mutation that prevents replay (`Update`) is deferred until after the "interaction" (decrypting/verifying the packet), a second copy of the same UDP datagram — trivially producible by a network-path attacker who has no cert and no session key, simply by duplicating the wire-format ciphertext — can enter `readOutsidePackets` on a different reader goroutine while the first copy's decrypt is still in flight. Both goroutines pass `Check` for the same `messageCounter` (since neither has called `Update` yet), both successfully decrypt (the ciphertext is identical and valid), and both are delivered onward as accepted plaintext to `handleOutsideMessagePacket`/tun or forwarded through the relay path in `handleOutsideRelayPacket`.

The interface intentionally parallelizes inbound packet handling across `f.routines` UDP reader goroutines, each independently calling `f.readOutsidePackets` for the same `hostinfo`/`ConnectionState`: [1](#0-0) 

This is the direct structural analogue of the reported dHedge issue: the code increments the durable anti-replay state (`l1BurntAmountOf`/window marker) only after performing the risky external interaction, rather than committing the state change atomically with (or before) the interaction, allowing multiple concurrent invocations to each observe pre-update state and pass validation.

### Impact Explanation
On the message path this results in the same application-layer datagram being delivered twice to the TUN device (traffic duplication/replay bypassing the anti-replay window, `ErrAlreadySeen` not enforced under the race). On the relay path (`VerifyRelay` → `handleOutsideRelayPacket`), a replayed relay frame that wins the race is forwarded a second time toward the relay target, which is exactly the class of relay-replay issue the codebase's CHANGELOG (#1751) and `TestRelayReplayProtection` were written to close for the sequential/locked case — but the check-then-later-update pattern still leaves a window when calls happen concurrently across reader goroutines. This is a remote-forgeable duplication/replay of authenticated traffic, not merely a benign duplicate log line, since it defeats the anti-replay guarantee the `Bits` window is designed to provide.

### Likelihood Explanation
The race window requires only that an attacker on the network path (no valid certificate needed) capture and resend one UDP datagram while the first copy is still being processed, and that the two copies land on different reader goroutines (`f.routines` > 1, the normal multi-queue configuration). Both are readily attacker-controlled/likely conditions; no cryptographic material or handshake participation is required from the attacker, only duplication of an already-observed ciphertext on the wire.

### Recommendation
Make the anti-replay check-and-mark atomic: hold `decryptLock` across `Check`, `DecryptDanger`, and `Update` for a given `ConnectionState` (or perform an atomic "test-and-set" of the counter before decrypting, rolling back only on genuine decrypt failure) so that no two concurrent invocations can observe the same pre-update window state for the same `messageCounter`.

### Proof of Concept
1. Establish a tunnel between two nodes using the existing e2e harness so a valid `ConnectionState` with cipher keys exists.
2. Configure the receiving side with `listen.routines` (or channel count) > 1 so `listenOut` spawns multiple concurrent `readOutsidePackets` goroutines. [4](#0-3) 
3. Capture one legitimate `header.Message` (or relay) UDP packet in flight and inject two copies back-to-back onto sockets serviced by different reader goroutines (mirroring the pattern in `TestRelayReplayProtection`, but issuing the duplicate concurrently rather than sequentially). [5](#0-4) 
4. Observe that under sufficient concurrency both copies pass `window.Check` before either `window.Update` completes, resulting in the payload being delivered/forwarded twice instead of the second copy being rejected with `ErrAlreadySeen`.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Update has three branches:
//   - i == b.current+1: fast path; advance the cursor by one and lose-count
//     the slot we just stomped (only past warmup; see the i > b.length guard
//     below).
//   - i  >  b.current+1: jump path; clear all slots between current and i
//     (or up to a full window's worth, whichever is smaller) via clearRange,
//     then mark i. Two arms here: a warmup arm that handles the very first
//     window before the cursor has slid, and a steady-state arm that treats
//     every cleared empty slot as a lost packet.
//   - i  <= b.current: in-window check for duplicates; out-of-window otherwise.
//
// NewBits seeds bits[0]=1 so counter 0 looks "received" — Update never
// clears that marker during warmup (clearRange skips position 0 when
// startPos=1), and once b.current >= b.length the marker is no longer
// consulted. The marker prevents a fictitious "lost" hit on the first real
// counter.
func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
