## Title
Meta-transaction (`DelegateAction`/`VersionedSignedDelegateAction`) signatures omit any chain/network-binding value, enabling cross-chain replay — (File: `core/primitives/src/signable_message.rs`, `core/primitives/src/action/delegate.rs`)

### Summary
The NEP-461-style signing scheme used to authorize NEAR meta-transactions (`DelegateAction`, `DelegateActionV2`) hashes only a fixed discriminant (NEP number + on/off-chain flag) and the action payload itself. Unlike ordinary `SignedTransaction`s, which include a recent `block_hash` that is intrinsically chain-specific, `DelegateAction`/`DelegateActionV2` never include any chain-identifying value (no `chain_id`, no genesis hash, no `block_hash`) in the bytes that get signed. This mirrors the root cause of CVE-2022-23507: a signature scheme that fails to bind to the identity of the chain it is meant for, permitting a validly-signed message from one chain to be replayed as valid on another.

### Finding Description
`SignableMessage::sign`/`SignedDelegateAction::verify` compute the signed hash from only the `MessageDiscriminant` and the `DelegateAction`/`VersionedDelegateActionPayload` struct itself: [1](#0-0) 

The `DelegateAction`/`DelegateActionV2` payloads carry `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key` — but no `block_hash` and no `chain_id`: [2](#0-1) 

Compare this to ordinary transactions, whose `block_hash` field is a per-chain value used as an implicit chain/replay anchor: [3](#0-2) 

On-chain, `apply_delegate_action` verifies only the signature, `max_block_height`, and that `sender_id` matches the tx receiver — it performs no chain-identity check whatsoever: [4](#0-3) 

`validate_delegate_action_key` then checks only the access key's existence and nonce, again with no chain-binding check: [5](#0-4) 

Consequently, a `SignedDelegateAction`/`VersionedSignedDelegateAction` produced for use on one NEAR-protocol chain (identified by `GenesisConfig.chain_id`, e.g. `"mainnet"`, `"testnet"`, or any NEAR-compatible fork/mirror network) is byte-for-byte and signature-for-signature identical to what would be required to submit the same delegate action on any other NEAR chain that happens to share the same `sender_id` account with the same public key, nonce state, and a compatible block height. Whenever two networks share genesis/account state — a documented and supported nearcore workflow (`tools/fork-network`, `tools/mirror`) that forks/copies mainnet accounts and keys to create new networks — a delegate action signed by a user for their sender-side chain remains fully valid on the other chain, because nothing in the signed payload discriminates between them.

Notably, nearcore's own `tools/mirror` tool re-signs every delegate action when mapping it onto a target chain (`resign` closures in `map_action`), because it must map secret keys — but this masks the underlying fact that the base NEP-461 signing scheme itself provides no cryptographic separation between chains: [6](#0-5) 

### Impact Explanation
If the same account and access key exist with matching nonce state on two NEAR-protocol networks (a realistic scenario for forked/mirrored/disaster-recovery/testnet-from-mainnet-snapshot deployments, which nearcore explicitly tooling supports via `fork-network`), an attacker who observes (or is given, e.g. by a relayer who serves both networks) a `SignedDelegateAction` intended for chain A can resubmit it verbatim as a valid, correctly-authorized meta-transaction on chain B before the sender's nonce there advances past it and before `max_block_height` is exceeded there. Since delegate actions can carry arbitrary NonDelegateAction lists (transfers, `AddKey`, `DeleteAccount`, function calls with deposits, etc.), this allows unauthorized execution of privileged actions on the victim's account on the "wrong" chain — i.e., authorization escalation / replay of a signed action outside its intended chain context, which can result in theft of funds or unauthorized account modification (e.g. adding an attacker-controlled full-access key) on the second network.

### Likelihood Explanation
Exploitation requires the specific condition of overlapping account/key/nonce state across two networks that both accept the replayed action, which is not the default situation between fully independent, freshly-bootstrapped mainnet and testnet deployments (different account namespaces in practice). However, it is squarely reachable within nearcore's own supported operational surface: fork-network/mirror-created networks intentionally clone mainnet accounts, keys and nonce state onto a second chain, and relayers or wallets that serve multiple such NEAR-protocol-compatible chains would generate/relay identical signed bytes. The root cause — absence of any chain-binding value in the meta-transaction signing domain — is a design gap, not a random one-off configuration mistake, matching the "theoretical but structurally present" characterization of the referenced advisory.

### Recommendation
Include a chain-identifying value (e.g., `genesis_config.chain_id`, or the genesis block hash) inside the `SignableMessage`/`DelegateAction`/`DelegateActionV2` payload that gets hashed and signed, and validate it against the executing chain's own chain ID in `apply_delegate_action`/`validate_delegate_action_key` before accepting the delegate action, analogous to how `block_hash` anchors ordinary transactions to a chain.

### Proof of Concept
1. Fork or mirror a NEAR chain (e.g., via `tools/fork-network`) so that account `alice.near` with access key `K` and nonce `N` exists identically on both chain `A` (`chain_id = "networkA"`) and chain `B` (`chain_id = "networkB"`).
2. Alice signs a `DelegateAction{sender_id: alice.near, receiver_id: alice.near, actions:[AddKey(attacker_pubkey, FullAccess)], nonce: N+1, max_block_height: H}` intending it to be relayed only on chain `A`, using `SignableMessage::sign`/`SignedDelegateAction::sign` as shown in `core/primitives/src/action/delegate.rs:83-95`.
3. A relayer (or an attacker who intercepts the delegate action) submits the identical `SignedDelegateAction` bytes as a meta-transaction on chain `B`, where `alice.near`'s access key state is at the same nonce and current block height is `<= H`.
4. `apply_delegate_action`/`validate_delegate_action_key` on chain `B` perform signature, `max_block_height`, `sender_id`, and nonce checks only — none of which detect that the action was authorized for chain `A` — so the `AddKey` executes on chain `B`, granting the attacker a full-access key on Alice's account there.

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}
