### Title
`ft_resolve_withdraw` treats an unparseable-but-successful `ft_transfer_call` return value as a total transfer failure, causing a full refund on top of tokens that actually left custody - (File: `contracts/defuse/src/contract/tokens/nep141/withdraw.rs`)

### Summary
`ft_resolve_withdraw` derives `used` from deserializing the promise-0 return bytes as `U128`; if the promise succeeds (`Ok`) but the bytes fail to deserialize, it sets `used = 0` and refunds the *entire* withdrawn amount via `self.deposit`, regardless of whether the underlying `ft_transfer_call` genuinely moved tokens out of the Verifier's custody. An attacker who controls the token contract (and thus the return value it produces) can make the transfer succeed for real while returning malformed bytes, causing the Verifier to both lose custody of the tokens and re-credit the withdrawer's internal balance for the same amount.

### Finding Description
The binding that should hold is::
`balance_debited(A) == tokens_actually_left_custody + amount_refunded`

Trace: `ft_withdraw` → `internal_ft_withdraw` (`contracts/defuse/src/contract/tokens/nep141/withdraw.rs:54-106`) calls `self.withdraw(...)` which unconditionally debits `A` from the caller's `token_balances` for `Nep141TokenId::new(token)` [1](#0-0) . It then schedules `do_ft_withdraw` → `ext_ft_core.ft_transfer_call(receiver_id, amount, memo, msg)` on the attacker-controlled `token` contract, followed by `ft_resolve_withdraw` as the resolving callback [2](#0-1) .

In `ft_resolve_withdraw`, for `is_call = true`:
```
match promise_result_checked_json::<U128>(0) {
    Ok(Ok(used)) => used.0.min(amount.0),
    Ok(Err(_deserialize_err)) => 0,
    Err(_) => amount.0,
}
``` [3](#0-2) 

The `Ok(Err(_deserialize_err))` branch assumes that if the returned bytes cannot be parsed as `U128`, the transfer must have failed, so it sets `used = 0` and fully refunds `amount.0` via `self.deposit(sender_id, ...)` [4](#0-3) . This assumption is false when the callee is malicious: the token contract's own promise-return value is fully under the attacker's control (they wrote the contract), independent of whether the contract's internal ledger actually moved tokens to `receiver_id`. NEP-141 conformance of the return value is not verified anywhere in this path - only the JSON-deserializability of the bytes is checked (`promise_result_checked_json`, in `crates/near/utils/src/promise.rs:38-52`), and a malformed-but-successful (`Ok`) promise result is treated identically to "nothing was transferred."

Exploit flow:
1. Attacker deploys a custom FT contract they fully control.
2. Attacker deposits `A` units of that token into their own Defuse account (`ft_transfer_call` to the Verifier credits `A` to their `token_balances`, and the Verifier's account on the FT ledger genuinely holds `A`).
3. Attacker calls `ft_withdraw(token=<attacker FT>, receiver_id=<attacker-controlled account>, amount=A, msg=Some(...))` with `is_call = true`.
4. `internal_ft_withdraw` debits `A` from the attacker's Verifier balance.
5. The scheduled `ft_transfer_call` executes on the attacker's FT contract: it genuinely transfers `A` out of the Verifier's balance to `receiver_id` (custody is honestly moved), but the top-level `ft_transfer_call` return value is crafted to be JSON that fails to deserialize as `U128` (e.g., a string, an object, or truncated JSON).
6. `ft_resolve_withdraw` observes `Ok(Err(_deserialize_err))`, sets `used = 0`, and refunds the full `A` back into the attacker's internal `token_balances` via `self.deposit`.

Net result: attacker's internal Verifier balance ends up back at `A` (as if nothing was withdrawn), while `A` real tokens were actually moved out of the Verifier's custody to `receiver_id`. The attacker can now withdraw the re-credited `A` again, extracting real value with no corresponding custody backing it.

No existing guard prevents this: `promise_result_checked_json` only checks the promise succeeded and the bytes are within a length bound, it does not validate the *semantics* of the returned value against actual token movement, and there is no reconciliation between "was tokens actually transferred" and "was the return value parseable."

### Impact Explanation
This inflates the attacker's own `token_balances` beyond what `total_supplies`/custody in the Verifier actually backs for that `TokenId`, matching the Critical category "a refund or resolver credit that does not match what failed to settle." Because the attacker controls the token contract, this is repeatable across arbitrary amounts and can be repeated by re-depositing and re-withdrawing, effectively minting unbacked internal balance for that custom `TokenId` each cycle. The blast radius is scoped to tokens the attacker registers themselves (custom FT contracts), since the exploit fundamentally relies on the callee being attacker-controlled; it does not directly threaten balances of pre-existing, honest token contracts.

### Likelihood Explanation
The precondition is simply deploying and controlling an FT-like contract - within the stated unprivileged attacker capabilities ("deploy and control their own FT/NFT/MT and receiver contracts"). No role, relayer key, or victim signature is needed. The attacker cost is only the gas to deploy a contract and perform deposit/withdraw calls, which is trivially affordable and fully repeatable.

### Recommendation
Do not distinguish `Ok(Err(_deserialize_err))` from `Err(_)` (promise failure) as "nothing used." Both cases represent an untrusted/unverifiable outcome from the callee and should be treated conservatively as "assume the callee already had the tokens" only under the same NEP-141-vulnerability rationale used for `Err(_)`, i.e. also set `used = amount.0` (no refund) rather than `used = 0` (full refund), since the promise itself succeeded from the runtime's perspective and the Verifier cannot prove no transfer occurred.

### Proof of Concept
`cargo test` (near-workspaces sandbox) plan:
1. Deploy a malicious FT contract `evil_ft` implementing `ft_transfer_call` that: (a) debits the caller's (Verifier's) balance and credits `receiver_id` by the full `amount` on its own internal ledger (simulating an honest transfer), and (b) returns a JSON payload that is valid JSON but not deserializable as `U128` (e.g. `"\"not-a-number\""` or `{"foo":1}`).
2. As attacker, deposit `A` of `evil_ft` into the Verifier (assert Verifier's `evil_ft` balance == `A`, attacker's Verifier `token_balances[evil_ft]` == `A`).
3. Call `ft_withdraw(token=evil_ft, receiver_id=attacker_receiver, amount=A, msg=Some("x"))` with 1 yoctoNEAR.
4. After execution:
   - Assert attacker's Verifier `token_balances[evil_ft]` == `A` (refunded despite the transfer having "succeeded" on-ledger).
   - Assert `evil_ft`'s on-chain balance for `receiver_id` == `A` (tokens genuinely left custody).
   - Assert the binding is broken: `debited(A) != actually_left_custody(A) + refunded(A)` because `A != A + A`, i.e. total credited to the attacker (`Verifier balance A` + `receiver balance A`) exceeds the single `A` unit of custody that ever existed, proving unbacked double-credit.
