### Title
Unvalidated attacker-controlled array length in precompile ABI decoding causes uncontrolled allocation / DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` precompiled contracts decode a dynamic signature array from raw transaction/call data using `extractBytesArray`, taking the array length directly from attacker-supplied calldata without validating it against the actual size of the decoded `words` array or any sane upper bound before allocating memory. This mirrors the CVE-2021-26222 bug class: a length value taken from untrusted input is used to size a buffer/array without first checking it against the resources actually available, so a value large enough to exhaust the allocator can corrupt program state (in ezXML: an OOB heap write; in java-tron: an uncontrolled/oversized allocation attempt).

### Finding Description
`extractBytesArray` and `extractBytes32Array` read the declared element count straight from the caller-controlled `DataWord[] words` and immediately allocate a Java array of that size before doing any bound checking against the true payload size: [1](#0-0) 

In `ValidateMultiSign.execute`, the size guard (`sigArraySize > MAX_SIZE`) that would prevent an oversized allocation is only applied when the `allowTvmSelfdestructRestriction` chain parameter/hard-fork flag is active; when that flag is not active, `extractBytesArray` is invoked directly on the raw offset taken from calldata with no such check: [2](#0-1) 

The same unguarded call pattern exists in `BatchValidateSign.doExecute`: [3](#0-2) 

Both precompiles are reached from ordinary TVM `CALL`/`STATICCALL` opcodes to fixed precompile addresses (`validateMultiSignAddr`, `batchValidateSignAddr`), which any contract-calling transaction can trigger: [4](#0-3) 

Because `intValueSafe()` on a `DataWord` can return any value up to `Integer.MAX_VALUE`, an attacker can set the length word to a huge number, causing `new byte[len][]` to attempt to allocate on the order of billions of array-reference slots, well beyond the transaction's memory/energy accounting, which governs TVM memory but does not govern this precompile-internal Java heap allocation.

### Impact Explanation
An unbounded/huge allocation triggered from a single crafted, low-cost transaction can throw `OutOfMemoryError` on the node's JVM heap. Because this allocation happens before any of the method's own `try/catch(Throwable)` blocks (the call sites shown above are outside the local try-blocks), the `OutOfMemoryError` is not locally suppressed and can propagate up through TVM contract-call/precompile execution during block processing. Depending on how far it propagates before being caught elsewhere in the runtime, this can disrupt transaction execution for the whole node process (heap pressure affecting concurrent execution, GC thrash, or an uncaught error terminating a critical thread), which is a node-availability (denial-of-service) impact rather than the direct memory-corruption/RCE impact of the original ezXML CVE — the underlying root cause (unchecked externally-supplied length used to size an allocation) is the same class of bug, but Java's bounds-checked arrays prevent it from becoming an out-of-bounds *write* as in the C-based ezXML case.

### Likelihood Explanation
The path is reachable by any account that can send a transaction invoking a smart contract that calls the `ValidateMultiSign` or `BatchValidateSign` precompile addresses (0x...16/…17 style low addresses), which requires no special privilege — any unprivileged contract-calling transaction sender can exercise it. The unguarded branch is taken whenever `VMConfig.allowTvmSelfdestructRestriction()` is false, i.e., before that specific hard-fork/committee proposal is activated on a given network; this makes the issue conditional on chain configuration state, which I could not fully verify as active/inactive on any particular mainnet snapshot from the available code index.

### Recommendation
- In `extractBytesArray` and `extractBytes32Array`, validate `len` against a strict upper bound (e.g., `MAX_SIZE`) and against the actual bounds of `words.length` *before* allocating, regardless of the `allowTvmSelfdestructRestriction` flag.
- Remove the flag-gated conditional bypass so the size check always applies, independent of hard-fork activation state.
- Add an explicit check that `len >= 0` and `len <= words.length` to avoid both huge allocations and out-of-range reads in the subsequent loop.

### Proof of Concept
1. Deploy or use any contract that calls the `validatemultisign(...)`/`batchvalidatesign(...)` precompile address with hand-crafted calldata.
2. Encode the ABI so that the word at the "signature array length" offset (the word referenced via `words[3]`/`words[1]` in `ValidateMultiSign`/`BatchValidateSign`) is set to a very large value (e.g., `0x7FFFFFFF`).
3. On a node where `allowTvmSelfdestructRestriction` is not yet active, submitting this transaction causes `extractBytesArray`/`extractBytes32Array` to execute `new byte[len][]` with `len` ≈ 2^31, triggering an immediate large-allocation attempt/`OutOfMemoryError` outside of any local exception guard.

Note: I could not fully trace, within the available indexed code, whether an outer `try/catch(Throwable)` exists at the `Program.callToPrecompiledAddress` call site that would fully contain this `OutOfMemoryError` before it destabilizes block processing, nor could I confirm the current activation state of `allowTvmSelfdestructRestriction` on a live network — these would need to be confirmed in a full checkout/session to determine the precise severity (contained per-transaction failure vs. broader node instability).

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
