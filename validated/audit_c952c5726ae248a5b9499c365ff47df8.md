### Title
Unbounded input consumption in `SwapFirstAssetTrader::buy_weight` fee-swap due to missing caller-controlled `amount_in_max` - (File: `cumulus/primitives/utility/src/lib.rs`, trait: `substrate/frame/asset-conversion/src/swap.rs`)

### Summary
`SwapFirstAssetTrader` (exercised in `cumulus/primitives/utility/src/tests/swap_first.rs`) converts whatever non-native asset is sitting in the XCM holding register into the exact fee amount needed to pay for weight, using `pallet_asset_conversion`'s `SwapCredit::swap_tokens_for_exact_tokens`. That trait method, unlike the extrinsic-facing `Swap::swap_tokens_for_exact_tokens`, has no `amount_in_max` parameter at all, so there is no way for the message/asset owner to cap how much of their held asset can be consumed to obtain the fixed fee output. This mirrors the ToB `Liquidator.liquidatePortion` finding: an amount is computed from a live, manipulable price (AMM reserves instead of an oracle) with no upper bound the payer can enforce.

### Finding Description
`pallet_asset_conversion::SwapCredit` defines: [1](#0-0) 
compared to the `Swap` trait used by dispatchables, which does expose an `amount_in_max`: [2](#0-1) 

`SwapFirstAssetTrader` (instantiated in tests as `Trader = SwapFirstAssetTrader<TargetAsset, mock::Swap, mock::WeightToFee, mock::Fungibles, mock::FungiblesMatcher, (), AccountId>`) calls the credit-based `swap_tokens_for_exact_tokens` to buy an exact `fee` amount of the target asset from whatever asset is present in the XCM holding register: [3](#0-2) 

The real (non-mock) implementation in `pallet_asset_conversion::Pallet` computes the required input amount from the *current* pool reserves at execution time (`do_swap_credit_tokens_for_exact_tokens` → `balance_path_from_amount_out` → `get_amount_in`), and returns the leftover as "change": [4](#0-3) 

Because the amount consumed from the holding register is derived purely from live AMM reserves and there is no `amount_in_max` the message issuer can supply through this path, an attacker who executes an ordinary large swap against the same pool earlier in the same block (a normal, unprivileged transaction — no malicious validator/collator/relayer needed) can shift reserves so that the fee-swap consumes substantially more of the victim's asset than the price at message-construction time implied. The victim's XCM message still succeeds (no revert, no `FeesNotMet`) as long as `credit_in` is nominally sufficient, so the loss silently manifests as diminished "change"/refunded assets to the beneficiary — the same "no upper bound, no revert" pattern flagged in the external report, just implemented via AMM reserves rather than an oracle feed.

The same missing-bound pattern exists in `xcm-builder`'s `SingleAssetExchangeAdapter::exchange_asset` for the `maximal: false` branch, which also invokes `SwapCredit::swap_tokens_for_exact_tokens` with no `amount_in_max`: [5](#0-4) 

### Impact Explanation
This affects generic XCM fee payment/asset-exchange infrastructure used by parachains (`SwapFirstAssetTrader`, `SingleAssetExchangeAdapter`). A user paying XCM execution fees (or performing an `ExchangeAsset` with `maximal: false`) in a non-native asset can be charged substantially more of that asset than the swap-time price would imply, without any transaction-level protection, because the credit-based swap primitive intentionally omits the caller-facing maximum-input safeguard that the equivalent dispatchable-facing `Swap` trait provides. This is an asset-accounting integrity issue: value is not conserved for the payer at the price they reasonably expected, and no explicit consent/limit mechanism exists to prevent it.

### Likelihood Explanation
Requires only an ordinary unprivileged account executing a normal large swap on the shared AMM pool in the same block prior to the victim's XCM message being executed — no validator, collator, relayer, or governance compromise is needed, and it is not merely a front-run of the victim's own transaction (the victim need not even be visible in the mempool; any pool-reserve movement in the same block window between quote-time and swap-execution-time triggers it). This is a realistic, low-cost condition for any parachain wiring `SwapFirstAssetTrader` or `SingleAssetExchangeAdapter` (non-maximal path) into its `WeightTrader`/`AssetExchange` configuration.

### Recommendation
Extend `SwapCredit::swap_tokens_for_exact_tokens` (and its callers `SwapFirstAssetTrader::buy_weight` and `SingleAssetExchangeAdapter::exchange_asset` non-maximal branch) to accept and enforce an optional `amount_in_max`, mirroring the `Swap` trait's `amount_in_max` and pallet-asset-conversion's `ProvidedMaximumNotSufficientForSwap` error, so fee/exchange conversions revert instead of silently over-charging when reserves have moved unfavorably.

### Proof of Concept
1. Configure a parachain with `SwapFirstAssetTrader<TargetAsset, pallet_asset_conversion::Pallet<Runtime>, WeightToFee, Fungibles, Matcher, (), AccountId>` as its `WeightTrader`, backed by a live `CLIENT_ASSET`/`TARGET_ASSET` pool.
2. Attacker submits an ordinary large swap (e.g., via `pallet_asset_conversion::swap_exact_tokens_for_tokens`) against the `CLIENT_ASSET`/`TARGET_ASSET` pool in the same block, shifting the price sharply against `CLIENT_ASSET`.
3. Victim's XCM message with `BuyExecution` using `CLIENT_ASSET` and a `WithdrawAsset` sized for the pre-attack price is executed later in the same block; `SwapFirstAssetTrader::buy_weight` calls `swap_tokens_for_exact_tokens(path, credit_in, fee)` with no `amount_in_max`, consuming a much larger portion of `credit_in` than the victim intended, as shown by the mechanics exercised in `holding_asset_swap_for_target`/`holding_asset_swap_for_target_twice` tests where the entire input amount minus a computed "change" is silently taken with no cap check: [6](#0-5) .
4. The victim receives less "change"/refund than expected and has no on-chain mechanism within this call path to have bounded or rejected the excess spend.

	fn swap_tokens_for_exact_tokens(
		path: Vec<Self::AssetKind>,
		credit_in: Self::Credit,
		amount_out: Self::Balance,
	) -> Result<(Self::Credit, Self::Credit), (Self::Credit, DispatchError)> {
		let credit_asset = credit_in.asset();
		with_transaction(|| -> TransactionOutcome<Result<_, DispatchError>> {
			let res = Self::do_swap_credit_tokens_for_exact_tokens(path, credit_in, amount_out);
			match &res {
				Ok(_) => TransactionOutcome::Commit(Ok(res)),
				// wrapping `res` with `Ok`, since our `Err` doesn't satisfy the
				// `From<DispatchError>` bound of the `with_transaction` function.
				Err(_) => TransactionOutcome::Rollback(Ok(res)),
			}
		})
		// should never map an error since `with_transaction` above never returns it.
		.map_err(|_| (Self::Credit::zero(credit_asset), DispatchError::Corruption))?
	}

#[test]
fn holding_asset_swap_for_target() {
	let client_asset_total = 15;
	let fee = 5;

	setup_pool(CLIENT_ASSET, 1000, TARGET_ASSET, 1000);

	let holding_asset = create_holding_asset(CLIENT_ASSET, client_asset_total);
	let holding_change = create_holding_asset(CLIENT_ASSET, client_asset_total - fee);

	let target_total = Fungibles::total_issuance(TARGET_ASSET);
	let client_total = Fungibles::total_issuance(CLIENT_ASSET);

	let mut trader = Trader::new();
	let change = trader.buy_weight(weight_worth_of(fee), holding_asset, &xcm_context()).unwrap();
	assert_eq!(&change, &holding_change);

	assert_eq!(trader.total_fee.peek(), fee);
	assert_eq!(trader.last_fee_asset, Some(create_asset_id(CLIENT_ASSET)));

	assert_eq!(Fungibles::total_issuance(TARGET_ASSET), target_total);
	assert_eq!(Fungibles::total_issuance(CLIENT_ASSET), client_total);
}
