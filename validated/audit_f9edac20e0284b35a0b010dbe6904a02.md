### Title
Out-of-bounds slice panic in ARM ELF attribute parsing during linking - ([File: src/cmd/link/internal/loadelf/ldelf.go])

### Summary
`parseArmAttributes` in the Go linker's ELF object loader parses the `.ARM.attributes` section of ELF object files without validating attacker-controlled length fields against the remaining buffer size. A malformed ELF object file (e.g. supplied via cgo-compiled `.o`/`.syso` files, a vendored archive, or any externally-produced object linked with `go build`) with an oversized `sectionlength` or `subsectionsize` value causes a slice-bounds-out-of-range panic, directly analogous to the out-of-bounds read that CVE-2024-24583 describes for libigl's `readMSH` when processing crafted element data.

### Finding Description
Attacker-controlled input: a crafted `.ARM.attributes` ELF section inside an object file consumed by the Go linker (`cmd/link`) when building/linking a Go program that links in externally supplied ELF object code (cgo objects, `.syso` files, archives).

Entry point: `parseArmAttributes(e binary.ByteOrder, data []byte)` in `src/cmd/link/internal/loadelf/ldelf.go` (lines 190-234), invoked from the ELF loader (`src/cmd/link/internal/ld/elf.go`) while resolving hard-float ABI attributes for ARM object files.

Failed checks / sinks: [1](#0-0) 
`sectionlength := e.Uint32(data)` is read directly from attacker data with no check that `sectionlength >= 4` or `sectionlength <= len(data)`. The subsequent `sectiondata := data[4:sectionlength]` and `data = data[sectionlength:]` will panic with "slice bounds out of range" if `sectionlength` is smaller than 4 or larger than `len(data)`. [2](#0-1) 
Similarly, `subsectionsize := e.Uint32(sectiondata[sz:])` is used unchecked in `subsectiondata := sectiondata[sz+4 : subsectionsize]` and `sectiondata = sectiondata[subsectionsize:]`. If `subsectionsize` is less than `sz+4` (high < low) or exceeds `len(sectiondata)`, this also panics.

Neither field is validated before being used to slice `data`/`sectiondata`, unlike other binary parsers in the same tree (e.g. `debug/elf/file.go`, `debug/macho/file.go`) that explicitly bound-check offsets/sizes with `FormatError` before slicing.

### Impact Explanation
The concrete effect is a reproducible panic (denial of service of the `go build`/linker process) when linking a crafted ARM ELF object file — matching Go's accepted category of "plausible malicious-input parser panic." This does not achieve code execution or data disclosure; it is a crash bug in a build-time parser triggered by untrusted binary input reaching the linker. Per Go's security decisions, `go build` must not execute malicious source, but parsing a malformed object file that is *linked* (not run) still falls under normal parser-safety expectations, so this would be assessed on Go's PUBLIC track as a low-severity robustness bug rather than a security vulnerability with a strong security boundary violation.

### Likelihood Explanation
The victim workflow requires building a Go program that links object code originating from an untrusted source (e.g. a cgo package or vendored `.syso`/`.o` file with attacker-influenced content) targeting an ARM architecture. The attacker only needs to control the bytes of the ELF object's `.ARM.attributes` section, not the build environment or credentials — an "ordinary user data" / "published module" scenario consistent with the required threat model.

### Recommendation
Add explicit bounds validation before slicing in `parseArmAttributes`: verify `sectionlength >= 4 && sectionlength <= len(data)` before computing `sectiondata`/advancing `data`, and verify `subsectionsize >= sz+4 && subsectionsize <= len(sectiondata)` before slicing `subsectiondata`/advancing `sectiondata`; return a descriptive error (as already done for other malformed cases in this function) instead of panicking.

### Proof of Concept
```go
package loadelf

import (
    "encoding/binary"
    "testing"
)

func TestParseArmAttributesOOBPanic(t *testing.T) {
    // ".ARM.attributes" section: magic 'A', then a corrupt section
    // with sectionlength larger than the remaining buffer.
    data := []byte{'A'}
    var lenBuf [4]byte
    binary.LittleEndian.PutUint32(lenBuf[:], 0xFFFFFFFF) // huge, attacker-controlled
    data = append(data, lenBuf[:]...)
    data = append(data, []byte("aeabi\x00")...) // minimal name

    defer func() {
        if r := recover(); r == nil {
            t.Fatal("expected panic due to out-of-bounds slice, got none")
        }
    }()

    // Calls into the vulnerable slicing logic.
    _, _, _ = parseArmAttributes(binary.LittleEndian, data)
}
```
Expected: the test recovers a panic (`slice bounds out of range`) triggered by `data[4:sectionlength]` in `parseArmAttributes`, demonstrating the unchecked out-of-bounds slice on attacker-controlled length data.
