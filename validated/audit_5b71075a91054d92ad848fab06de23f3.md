### Title
Missing pool-provenance validation in `LinkRepositoryToObjectPool` allows arbitrary cross-repository object disclosure - (File: internal/gitaly/service/objectpool/link.go)

### Summary
The `LinkRepositoryToObjectPool` RPC accepts any `(Repository, ObjectPool)` pair without validating that the target repository was ever a legitimate member of, or fork related to, the specified object pool. It only checks that both paths independently resolve to valid repositories on disk, then unconditionally rewrites the target repository's `objects/info/alternates` file to point at the pool.

### Finding Description
`LinkRepositoryToObjectPool` validates the `repository` field with `s.locator.ValidateRepository` and resolves the pool via `s.poolForRequest`, which only checks that the pool directory is structurally a valid pool repository (`objectpool.FromProto` / `ErrInvalidPoolDir` / `ErrInvalidPoolRepository`) — there is no check that the caller-supplied repository has any prior relationship (fork lineage, ownership, existing membership) with the pool being linked to: [1](#0-0) 

The underlying `Link` function then writes the pool's path directly into the repository's alternates file as long as the alternates file is empty or already points at the same pool, with the only defensive check being that a *different* existing alternates entry causes a hard failure — this only guards re-pointing, not initial linking of unrelated repositories: [2](#0-1) 

Object pools are documented as sharing objects "of both repositories" purely via the alternates mechanism, and any repository whose alternates file references a pool gains full read access to every object contained in that pool:



Because there is no whitelist/authorization check tying the `repository` argument to the specific `object_pool` argument (e.g. verifying the repository descends from the pool's origin or already has legitimate access), any caller able to invoke this Mutator RPC for a repository they control can supply an arbitrary existing object pool ID and immediately gain read access to all objects contained in that pool, including objects that were never pushed to, or fetched by, their own repository. This mirrors the reported bug class: a "provider" function (`Link`/`LinkRepositoryToObjectPool`) that performs a security-relevant linking operation on arbitrary caller-supplied identifiers without checking that the pairing is on an authorized/whitelisted set, allowing any unprivileged party who can reach the operation to bind their own resource to someone else's shared resource pool.

### Impact Explanation
A successful call discloses the full object graph (commits, blobs, trees) of an object pool — which may include another organization's fork-network's private objects — to an unrelated repository, since once linked, standard Gitaly RPCs (e.g. CommitService) will happily resolve objects that only exist via the alternates path, as shown by the pool commit becoming readable through the linked repository: [3](#0-2) 

This is a cross-repository object confidentiality violation, and additionally corrupts the pool-membership invariant (`removeMemberBitmaps`, bitmap uniqueness, fsck consistency) that the rest of the housekeeping/dissociation logic relies on being a curated, authorized set of members.

### Likelihood Explanation
`LinkRepositoryToObjectPool` is a `MUTATOR` RPC declared in the public proto surface and reachable by any client holding valid gRPC/Gitaly access to the target repository's storage; it performs no verification linking the two identifiers beyond structural path validation, so exploitation requires only the ability to name an existing pool relative path and a repository the caller nominally controls.

### Recommendation
- **Short term:** Before performing the link, verify that the `object_pool` is actually the pool the `repository` is authorized to join — e.g. require that the pool's recorded origin/member relationship (as tracked via `CreateObjectPool`'s origin repository or a persisted membership record) includes the target repository, and reject the RPC otherwise.
- **Long term:** Introduce an explicit, persisted pool-membership whitelist (analogous to the recommended token whitelist in the external report) that `Link`/`LinkRepositoryToObjectPool`, `FetchIntoObjectPool`, and `DisconnectGitAlternates` all consult, rather than trusting caller-supplied `(repository, pool)` pairs based purely on path validity.

### Proof of Concept
1. Actor A creates repository `pool-a` and calls `CreateObjectPool` to seed pool `P` from it, pushing sensitive/private content into `P`.
2. Actor B, who controls unrelated repository `repo-b` (no fork relationship to `pool-a`), calls `LinkRepositoryToObjectPool` with `Repository = repo-b` and `ObjectPool = P` (only the pool's storage name/relative path is needed, which may be guessable/enumerable or observed via replication/logs).
3. `link.go`'s validation only checks that `repo-b` is a valid repository and `P` is a structurally valid pool; `objectpool.Link` writes `P`'s objects path into `repo-b/objects/info/alternates`.
4. Actor B now issues normal read RPCs (e.g. `CommitService.GetCommit`) against `repo-b` for object IDs known only to exist in `P`, and successfully retrieves Actor A's private objects, as demonstrated by the pattern in [3](#0-2) .

```go
func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
```
