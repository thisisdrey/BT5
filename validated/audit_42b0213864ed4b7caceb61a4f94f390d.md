### Title
Out-of-bounds read when parsing a malicious ZIP central directory entry - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in Bazel's bundled `ijar` tool parses the ZIP central directory of a jar file directly out of an mmap'd buffer with no bounds checking, unlike its sibling `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` before every field read. A crafted/corrupted jar whose central directory declares a `file_name_length`, `extra_field_length`, or `file_comment_length` that runs past the end of the mapped file causes reads beyond the buffer boundary — the same bug class as CVE-2022-1207 (OOB read from insufficiently validated structured binary input).

### Finding Description
`ProcessCentralDirEntry` reads the fixed-size portion of a central directory header with `get_u4le`/`get_u2le` calls and then advances `p`/`extra_p` by attacker-controlled lengths taken straight from the header, with no verification that the underlying mmap region (`zipdata_in_`, sized by `input_file_->Length()`) actually contains that many bytes: [1](#0-0) 

Specifically:
- `file_name_length`, `extra_field_length`, `file_comment_length` are read from the header and used to advance `p` and to `memcpy` into the fixed `filename[PATH_MAX]` buffer, with no call to `EnsureRemaining()`.
- The subsequent `while (extra_p != p)` loop reads `header_id`/`data_size` from `extra_p` and advances `extra_p += data_size` again without bounds checks, so a malformed extra field can walk `extra_p` arbitrarily far past the mapped region.

This is in stark contrast to `ProcessLocalFileEntry`, which validates every field with `EnsureRemaining()` before reading it: [2](#0-1) 

The `EnsureRemaining` helper itself proves the intended invariant (bytes remaining in the mmap'd file must be checked before every read), but it is never invoked in the central-directory parsing path: [3](#0-2) 

The class comment claims "the central directory is always followed by another data structure that has a signature, so parsing it this way is safe" — but that assumption does not hold if the length fields in the record itself are corrupted/oversized, which is exactly the attacker-controlled input this parses.

### Impact Explanation
An attacker who can get a victim's Bazel build to process a maliciously crafted `.jar`/`.zip` file through `ijar` (e.g. as a prebuilt dependency jar for header-jar/interface-jar generation, or as any other zip input the tool is invoked on) can trigger reads past the end of the mmap'd input buffer. On most platforms this manifests as a crash (denial of service via SIGSEGV on an unmapped page) but can also leak adjacent process memory into the parsed `filename` buffer or `attr`/`offset` fields, which is the same OOB-read information-disclosure class as the radare2 CVE. Because `ijar` runs as a build-time action, this is reachable purely by supplying attacker-controlled archive bytes — no local machine access or credential compromise is required, consistent with the required unprivileged-attacker threat model (a hostile artifact source publishing a malformed jar/zip that Bazel's build consumes).

### Likelihood Explanation
Likelihood is moderate: it requires the target file to be processed through `ijar`'s central-directory parsing path with a corrupted/oversized length field, which is a straightforward, deterministic construction (no need to defeat compression or checksums — `ijar` doesn't validate any content hash of the archive, it only trusts the ZIP structure it parses). No sha256/integrity check would catch this because the checksum being validated by `http_archive`/`http_jar` (if present) covers the file bytes as downloaded, not internal consistency of the ZIP structure being unpacked/re-processed by `ijar`; a bit-for-bit correct download can still contain a self-consistent-looking but oversized `extra_field_length`/`file_name_length` in one central directory record.

### Recommendation
Add `EnsureRemaining()` (or equivalent bounds checks against `input_file_->Length()`) before every read and pointer-advance operation in `ProcessCentralDirEntry`, mirroring the pattern already used in `ProcessLocalFileEntry`:
- Validate `file_name_length`, `extra_field_length`, and `file_comment_length` against remaining buffer size before advancing `p`.
- Validate `data_size` inside the extra-field loop against the number of bytes remaining within the declared `extra_field_length` region before advancing `extra_p`.
- On any check failure, call `error(...)` and return `false` instead of continuing to parse.

### Proof of Concept
A reproducible test can be added under `third_party/ijar/test/` (or a new `src/test/shell/bazel` shell test) that:
1. Constructs a minimal ZIP file whose central directory record declares `file_name_length = 0xFFFF` (or `extra_field_length` large enough) while the actual file is only a few bytes long, so no such bytes exist after the fixed header.
2. Invokes `ZipExtractor::Create()`/`ProcessAll()` (as `PartialZipExtractor`/`ijar` main does) on this file.
3. Observes an out-of-bounds read (crash under AddressSanitizer, or a segfault) instead of a graceful `error()`-reported failure, demonstrating the missing bounds check identified in `InputZipFile::ProcessCentralDirEntry`. [4](#0-3) 

Note: I was unable to fully verify within the available tools whether `ijar`'s central-directory parser is reachable on attacker-supplied prebuilt jars via `java_import`/`java_common.run_ijar` in this exact checkout (searches for `JavaCompilationHelper`/`java_import` invocation sites returned no matches), so the precise build-rule call site that feeds untrusted jar bytes into this code path should be confirmed by a Devin session with full repository access before finalizing severity/likelihood.

  // Check that at least n bytes remain in the input file, otherwise
  // abort with an error message.  "state" is the name of the field
  // we're about to read, for diagnostics.
  int EnsureRemaining(size_t n, const char *state) {
    size_t in_offset = p - zipdata_in_;
    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "
                   "expected %zd more bytes but found %zd.\n",
                   in_offset, state, n, remaining);
    }
    return 0;
  }

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
