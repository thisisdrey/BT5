## Analog Found: Wallet Contract fails to refund unused portion of an external caller's attached deposit

### Title
Wallet Contract `rlp_execute` permanently retains unused external-caller deposit on success - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `near-wallet-contract` (used for eth-implicit accounts) accepts a `#[payable]` call to `rlp_execute` from an external, unprivileged relayer/caller, and only tracks that deposit via `CallerDeposit` for a refund if the resulting cross-contract promise **fails**. If the promise succeeds, the entire attached deposit is kept by the wallet contract, even if the actual Near action that was executed needed less (or none) of it — the same "exact-out"-style bug class as `DODORouteProxy#externalSwap`.

### Finding Description
`rlp_execute` is `#[payable]` and forwards `env::attached_deposit()` into an `ExecutionContext`, and `CallerDeposit::new` captures the *entire* attached deposit from an external (non-self) `predecessor_account_id`: [1](#0-0) 

This deposit amount is **not validated or reconciled against the actual value needed by the parsed Near action** (`near_action`), which is instead derived purely from the RLP-encoded Ethereum transaction's own `tx.value`/`yocto_near` fields: [2](#0-1) 

The `CallerDeposit` is only used inside `rlp_execute_callback`, and only on the `Failed` branch — a full refund of the tracked deposit is sent back to the caller: [3](#0-2) 

On the `Successful` branch, there is no refund logic at all — the caller's attached deposit (whatever amount it was) is simply absorbed by the wallet contract regardless of whether the underlying action actually consumed it: [4](#0-3) 

This is confirmed by the contract's own test, `test_caller_refunds`, whose second case explicitly documents that "External caller does not get a refund when their tokens are spent" — i.e. any amount attached beyond what's minimally needed to trigger success is not returned: [5](#0-4) 

This is structurally identical to the DODORouteProxy issue: a contract pulls a caller-specified amount of value up front, executes an action that may not need the whole amount, and only refunds on the failure path — never accounting for/returning the unused remainder on success.

### Impact Explanation
Any external, unprivileged account that calls `rlp_execute` on behalf of an eth-implicit wallet (e.g. as a relayer paying `attached_deposit` to cover an action) permanently loses any deposit amount beyond what the wallet's inner action actually required, whenever that inner promise succeeds. Because there's no reconciliation between attached deposit and the ABI/RLP-derived action value, an external caller attaching an over-generous deposit (or a relayer bug/miscalculation) results in silent, permanent loss of the surplus to the wallet-contract account. This is a genuine, confirmed loss of funds for an ordinary, unprivileged caller — not merely an economic inefficiency, since there is no path in the contract logic to recover it after success.

### Likelihood Explanation
This is reachable by any account that is not the wallet owner (`predecessor_account_id != current_account_id`) simply by calling the public, `#[payable]` `rlp_execute` method with a deposit larger than needed for the relayed action. No malicious node, network, or privileged access is required — it is purely a contract-logic path exercised by ordinary transactions/relayers, matching the reachable transaction/contract-execution analog constraints. The wallet's own test suite demonstrates and accepts this exact behavior as "no refund when tokens are spent," confirming it's a real, currently-existing code path, not a hypothetical one.

### Recommendation
In `rlp_execute_callback`'s `Successful` branch, compute how much of the `CallerDeposit` was actually consumed by the executed action (e.g., the `Transfer`/`FunctionCall` deposit derived from `near_action`), and refund the remainder to `caller_deposit.account_id`, mirroring the deposit-reconciliation approach recommended for `DODORouteProxy#externalSwap`. Alternatively, require attached deposit to exactly equal the value needed by the parsed action and reject/refund any excess at parse time rather than after the promise resolves.

### Proof of Concept
1. An external relayer account (not the wallet owner) calls `rlp_execute` with `attached_deposit = 3 NEAR`, targeting a Near action (e.g. a `FunctionCall`) that only actually needs a smaller amount, or none, to succeed (as in `test_caller_refunds`'s second case using the `address_registrar`'s `register` method).
2. `CallerDeposit::new` records the full `3 NEAR` as belonging to the caller (`types.rs:180-191`).
3. `inner_rlp_execute` builds the actual `near_action` purely from the RLP transaction's `tx.value`, independent of the attached deposit (`internal.rs:159-166`).
4. The promise created for the target action succeeds.
5. `rlp_execute_callback` reaches the `PromiseResult::Successful` branch, and no refund is issued for the caller's deposit (`lib.rs:313-317`) — the full `3 NEAR` remains in the wallet contract's account, confirmed by the test's assertion that `pre_tx_account_balance - post_tx_account_balance >= deposit_amount` with no refund path (`sanity.rs:215-227`).
