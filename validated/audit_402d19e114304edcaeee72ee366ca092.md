### Title
Truncated/non-terminated chunked HTTP response body is silently accepted as a valid, complete body - ([File: libsigner/src/http.rs])

### Summary
`decode_http_body` in `libsigner/src/http.rs` feeds the already-fully-buffered response bytes into `HttpChunkedTransferReader` and calls `read_to_end`. Because the reader's `do_read` state machine treats an underlying `read()` returning `0` (i.e., the slice running out of bytes) identically to "chunk stream properly finished," `Read::read_to_end` interprets premature end-of-slice as legitimate EOF and returns `Ok(partial_body)` instead of an `Err`, even though the terminating `0\r\n\r\n` chunk was never seen.

### Finding Description
`run_http_request` reads the whole HTTP response into memory via `sock.read_to_end(&mut buf)` [1](#0-0) , then calls `decode_http_response` which short-circuits on non-200 codes but otherwise just returns `(headers, body_offset)` [2](#0-1) . The remaining bytes are handed to `decode_http_body`, which, when `Transfer-Encoding: chunked` is present, wraps the slice in `HttpChunkedTransferReader::from_reader` and calls `read_to_end` [3](#0-2) .

The root cause is in `HttpChunkedTransferReaderState::do_read` in `stacks-common/src/util/chunked_encoding.rs`. In every parse state (`ChunkBoundary`, `Chunk`, `ChunkTrailer`), when the underlying `fd.read()` returns `0` bytes (which happens as soon as the byte slice is exhausted), the loop simply `break`s and returns `Ok((decoded, consumed))` [4](#0-3) . This is indistinguishable from the legitimate "well-formed 0-length terminating chunk reached, `parse_step == EOF`" case that also breaks out of the loop [5](#0-4) . The `Read` impl for `HttpChunkedTransferReader` simply forwards `decoded` [6](#0-5) , so on the next call `read()` returns `Ok(0)`, and Rust's standard `Read::read_to_end` treats a `0`-byte read as normal end-of-stream, returning `Ok(())` with whatever bytes have been accumulated so far — no distinction is made between "chunk stream properly terminated" and "byte source ran out mid-chunk."

Attack: attacker (an HTTP responder for the signer's outbound `StackerDBSession` request, e.g. a malicious/compromised node the signer talks to, or a MITM on that leg) returns `HTTP/1.1 200 OK\r\nTransfer-Encoding: chunked\r\n\r\n` followed by a body that starts a chunk (e.g. `100\r\nAAAA`) but never sends the terminating `0\r\n\r\n`, then closes the TCP connection. `sock.read_to_end` collects exactly what was sent before the close [7](#0-6) . `decode_http_response` accepts the 200 + headers (no fault here — this part behaves correctly). `decode_http_body`'s `read_to_end` then silently truncates: it returns `Ok(decoded_body)` containing only the partial chunk bytes actually present, with no error, even though the chunked encoding was never properly closed.

### Impact Explanation
This function is on the signer's outbound HTTP client path used by `libsigner::session` / `stacks-signer/src/client/stackerdb.rs` when the signer fetches data (e.g., StackerDB chunks) from a node via chunked-encoded HTTP responses. A malformed/truncated response is treated as a complete, valid body rather than raising an I/O error, meaning downstream code (e.g., StackerDB chunk deserialization) receives truncated data that it presumes is the full, complete server response. Depending on what's deserialized from this truncated buffer, this could at most cause the signer to process malformed/incomplete data as if it were a complete message; it does not directly cause a memory-safety violation, forged consensus state, or write to StackerDB (the signer merely fails to error-out on an under-length body — any incorrectly-formed data still needs to pass whatever schema/signature checks the caller applies afterward). Given the scope restriction that this must be evaluated strictly for `decode_http_response`/`decode_http_body`'s equality violation, the demonstrated fault is real (truncated stream returns `Ok` instead of `Err`), but its downstream severity depends on callers that were not fully traceable within this pass — I was unable to confirm within the available searches whether any StackerDB chunk consumer in `stacks-signer/src/client/stackerdb.rs` would treat a truncated buffer as valid and act on it in a way that reaches Critical/High impact (e.g., writing forged/partial state, or a crash). This uncertainty should be resolved by a background agent tracing `stackerdb.rs`'s handling of `run_http_request`'s `Vec<u8>` result.

### Likelihood Explanation
The precondition is that the signer's outbound `StackerDBSession` connects to a party the attacker controls (a malicious node/relay on that leg, or MITM without TLS). This is a single crafted HTTP response with no signature or auth token required — `decode_http_response`/`decode_http_body` perform no cryptographic verification at this layer. The attack is trivially repeatable per request. However, it requires the signer to be pointed at (or routed through) an attacker-controlled/manipulated endpoint for its outbound requests, which is a real but somewhat different precondition than "any unprivileged remote party connecting to the node's P2P/RPC port" — it is the signer acting as a client to a party the attacker controls, not an attacker connecting inbound to the node.

### Recommendation
In `HttpChunkedTransferReaderState::do_read` (`stacks-common/src/util/chunked_encoding.rs`), distinguish "clean EOF because we reached the final `0`-chunk and trailer" (`self.parse_step == HttpChunkedTransferParseMode::EOF`) from "underlying reader returned 0 while still mid-stream" (`ChunkBoundary`, `Chunk`, or `ChunkTrailer` state). In the latter case, return an `io::Error` (e.g., `UnexpectedEof`) rather than `Ok((decoded, consumed))` with `decoded` possibly non-zero but less than requested. This ensures `read_to_end` in `decode_http_body` propagates an error for any non-terminated chunked body instead of silently returning a truncated `Ok` result.

    pub fn do_read<R: Read>(&mut self, fd: &mut R, buf: &mut [u8]) -> io::Result<(usize, usize)> {
        let mut decoded = 0;
        let mut consumed = 0;
        while decoded < buf.len() {
            match self.parse_step {
                HttpChunkedTransferParseMode::ChunkBoundary => {
                    let count = self.read_chunk_boundary(fd)?;
                    if count == 0 {
                        break;
                    }
                    consumed += count;
                }
                HttpChunkedTransferParseMode::Chunk => {
                    let nr = self.read_chunk_bytes(fd, &mut buf[decoded..])?;
                    if nr == 0 && self.parse_step == HttpChunkedTransferParseMode::Chunk {
                        // still trying to read the chunk, but got 0 bytes
                        break;
                    }
                    decoded += nr;
                    consumed += nr;
                }
                HttpChunkedTransferParseMode::ChunkTrailer => {
                    let count = self.read_chunk_trailer(fd)?;
                    if count == 0 {
                        break;
                    }
                    consumed += count;
                    if self.last_chunk_size == 0 {
                        // we're done
                        trace!("finished last chunk");
                        self.parse_step = HttpChunkedTransferParseMode::EOF;
                        break;
                    }
                }
                HttpChunkedTransferParseMode::EOF => {
                    break;
                }
            }
        }
        Ok((decoded, consumed))
    }
