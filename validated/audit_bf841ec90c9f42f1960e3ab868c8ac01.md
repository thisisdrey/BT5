### Title
Stale `PromiseYieldReceipt`/`PromiseYieldStatus` entries survive `remove_account`, allowing resume of a deleted account's queued self-call actions against a re-created account of the same name - (File: core/store/src/utils/mod.rs, runtime/runtime/src/ext.rs)

### Summary
`remove_account()` deletes the `Account`, `ContractCode`, access keys, gas-key nonces and contract data for an account, but never removes `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, or the `YieldIdToDataId`/`DataIdToYieldId` mappings keyed by that account id. `submit_promise_resume_data()` in `ext.rs` authorizes a resume purely by checking whether `(self.account_id, data_id)` exists in `has_promise_yield_receipt`/`has_promise_yield_status`, with no concept of "which incarnation" of the account created the entry. This lets a party who created and then deleted an account reuse a retained `data_id` to resume a stale, privileged self-call receipt (e.g. containing `DeployContractAction`) against a freshly re-created account of the same name.

### Finding Description
`remove_account` at [1](#0-0)  removes `TrieKey::Account`, `TrieKey::ContractCode`, access keys/gas-key nonces, and `TrieKey::ContractData`. It does not touch `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, or `TrieKey::YieldIdToDataId`/`DataIdToYieldId`, even though helper functions to remove them exist (`remove_promise_yield_receipt`, `remove_promise_yield_status`, `remove_yield_id_mappings` at [2](#0-1)  and [3](#0-2) ). `action_delete_account` in `actions.rs` calls only `remove_account` [4](#0-3) , so any pending yield state for that account name is left dangling in the trie after deletion.

The authorization check for resuming a yield, `submit_promise_resume_data`, does a pure key-existence check on `(self.account_id, data_id)`: [5](#0-4) 
There is no binding to any account "generation" counter, creation timestamp, or the account's current storage root — a `data_id` from a long-deleted incarnation of an account is indistinguishable from one belonging to the current incarnation, as long as the stale trie entry has not yet been purged.

The only mechanism that eventually purges these entries is the `PromiseYieldTimeout` queue (`enqueue_promise_yield_timeout`, `TrieKey::PromiseYieldTimeout`) processed independently of account existence at `expires_at`; until that height is reached, the stale `PromiseYieldReceipt`/`PromiseYieldStatus` remain resolvable.

Exploit flow:
1. Attacker owns `A`, calls `promise_yield_create` with a callback action list `[DeployContractAction]` targeting `A` itself (a legitimate self-call, so `actor_id == account_id == A` at execution time, passing `check_actor_permissions`'s `actor_id != account_id` check for `DeployContractAction` [6](#0-5) ). The returned `data_id` is retained by the attacker off-chain.
2. Attacker deletes `A` via `DeleteAccountAction` → `action_delete_account` → `remove_account`, which does not clear the pending `PromiseYieldReceipt`/`PromiseYieldStatus` entries for `data_id`.
3. A third party later registers account `A` again and deploys its own, unrelated contract that (as is common for yield/resume "resolver" style dApps) exposes a public method forwarding caller-supplied `data_id`/`data` into `promise_yield_resume`.
4. Attacker, as an ordinary unprivileged caller, invokes that method on the new `A` with the retained original `data_id`. Inside `RuntimeExt`, `self.account_id == A`, so `submit_promise_resume_data` finds the stale `has_promise_yield_receipt`/`has_promise_yield_status` entries and succeeds, releasing the original queued self-call receipt containing `DeployContractAction`, which executes against the new `A` because it is stored as a self-call (`actor_id == account_id == A`) — bypassing any authorization tied to the new owner.

This breaks the "authorization exactness" invariant: an outsider, not the new account's owner, triggers execution of privileged self-call actions on the new account purely by knowing a `data_id` from a previous incarnation of the account name.

### Impact Explanation
This is an authorization-escalation-across-accounts bug: it allows an unprivileged, unrelated attacker to force execution of a privileged self-call action (e.g., overwrite the account's contract via `DeployContractAction`, or other actions restricted to `actor_id == account_id`) against a re-created account without any signature or access key from the new owner. This maps to the "authorization escalation across accounts or promises" bounty category and can lead to compromise/loss of funds or control of the re-created account if the queued action is a state-changing self-call.

### Likelihood Explanation
Preconditions are non-trivial but realistic:
- Attacker must control the account before deletion (cheap — attacker can create and fund a throwaway named account).
- Attacker must delete that account and retain the `data_id` returned at `promise_yield_create` time.
- A third party must reuse the exact same account name and deploy a contract that exposes a resolver-style method forwarding external `data_id`/`data` to `promise_yield_resume` — a common but not universal pattern.
- The exploit window is bounded by the yield's timeout (`PromiseYieldTimeout.expires_at`); after that height, timeout processing purges the stale entries, closing the window.
Given these constraints, exploitation is feasible but conditional on the timing window and the specific contract pattern deployed on the reused name, making likelihood moderate rather than trivial/universal.

### Recommendation
`remove_account` should also purge all `PromiseYieldReceipt`, `PromiseYieldStatus`, and `YieldIdToDataId`/`DataIdToYieldId` entries associated with the account being deleted (iterating the relevant trie prefixes, similar to how access keys and contract data are enumerated and removed), and/or the timeout queue should be immediately consulted to clear the account's live yields as part of deletion. Alternatively, bind resumability to an account "generation"/incarnation identifier so that a `data_id` produced by a previous incarnation can never resolve against a later one.

### Proof of Concept
Unit test outline (in `runtime/runtime/src/ext.rs` or `core/store/src/utils/test_utils.rs` style):
1. Create `TrieUpdate`, set account `A`.
2. Call `set_promise_yield_status`/`set_promise_yield_receipt` directly (simulating `create_promise_yield_receipt`) for `data_id = D` on `A`, with a stored `Receipt` whose action is `DeployContractAction` and `predecessor_id == receiver_id == A`.
3. Call `remove_account(&mut state_update, &A)`.
4. Assert `has_promise_yield_receipt(&state_update, A.clone(), D).unwrap() == true` and `has_promise_yield_status(&state_update, &A, D).unwrap() == true` — proving the entries survive account deletion.
5. Re-create `A` (set a new `Account`).
6. Call `submit_promise_resume_data` on a `RuntimeExt` scoped to `account_id = A` with `data_id = D`; assert it returns `Ok(true)` and enqueues a `PromiseResume` receipt / sets `PromiseYieldStatus::ResumeInitiated`, demonstrating the resume succeeds against the new incarnation using only the stale `data_id`, with no check binding it to the new account's creation.

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })

    fn submit_promise_resume_data(
        &mut self,
        data_id: CryptoHash,
        data: Vec<u8>,
    ) -> Result<bool, VMLogicError> {
        let has_yield_receipt_in_state =
            has_promise_yield_receipt(self.trie_update, self.account_id.clone(), data_id)
                .map_err(wrap_storage_error)?;
        let has_yield_status_in_state =
            has_promise_yield_status(self.trie_update, &self.account_id, data_id)
                .map_err(wrap_storage_error)?;

        if has_yield_receipt_in_state || has_yield_status_in_state {
            self.receipt_manager.create_promise_resume_receipt(data_id, data);
            set_promise_yield_status(
                &mut self.trie_update,
                &self.account_id,
                data_id,
                PromiseYieldStatus::ResumeInitiated,
            );
            return Ok(true);
        }

        Ok(false)
    }
