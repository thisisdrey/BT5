### Title
Missing length parameter in `InputZipFile::ProcessCentralDirEntry()` causes out-of-bounds read when parsing the Zip64 extra field of a crafted JAR/ZIP central directory entry - (File: `third_party/ijar/zip.cc`)

### Summary
`third_party/ijar/zip.cc` implements Bazel's bundled `ijar`/`zip.cc` archive parser, used whenever Bazel processes a JAR (e.g. `java_common.run_ijar`, `java_common.stamp_jar`, and interface-jar generation for `java_import`/prebuilt jars that come from `http_jar`/`http_archive`/registry artifacts). `InputZipFile::ProcessCentralDirEntry()` [1](#0-0)  reads central-directory-entry fields from a raw pointer `p` with no length/end parameter to bound the reads, unlike its sibling `ProcessLocalFileEntry()` which explicitly calls `EnsureRemaining()` before every variable-length read [2](#0-1) [3](#0-2) . This mirrors the libgphoto2 bug class exactly: a callee that unpacks structured binary fields is given a pointer but not the buffer's remaining size, while the caller (`FindZipCentralDirectory`, which validates `cd.central_dir_offset + cd.central_dir_size <= in_length`) has the necessary bound but never passes it down into per-entry/per-extra-field parsing.

### Finding Description
The vulnerable loop is the Zip64 "extra field" parser inside `ProcessCentralDirEntry`: [4](#0-3) 

- `extra_field_length` is a fully attacker-controlled `u2` taken directly from the entry header (`get_u2le(p)` at line 511).
- `p += extra_field_length;` sets the end pointer `p` used as the loop bound, but this is never checked against `extra_p`'s ability to advance in exact-width steps: the loop condition is `while (extra_p != p)`, not `while (extra_p < p)`.
- Inside the loop, `header_id` and `data_size` are each read via `get_u2le`, unconditionally consuming 4 bytes, with no check that at least 4 bytes remain before `p`. If `extra_field_length` is not a multiple of the per-record size (e.g. 1–3, or an odd remainder after several records), the read of `header_id`/`data_size` walks past `p` into adjacent central-directory / file-comment / next-entry data (or past the mapped file entirely), an out-of-bounds read relative to the parsed extra field.
- Worse, `extra_p += data_size;` uses an attacker-controlled `data_size` with no validation that it is ≤ the bytes actually remaining in the extra field. If `header_id == ZIP64_EXTRA_FIELD_TAG`, the code then calls `get_u8le(extra)` up to three times (for uncompressed size, compressed size, offset) [5](#0-4) , reading 8 bytes from `extra` regardless of whether `data_size` is actually ≥ 8/16/24. A crafted `data_size` of e.g. 0–7 causes `get_u8le` to read past the declared extra-field boundary — an unbounded read whose extent is dictated entirely by attacker-chosen `data_size`/`extra_field_length`, exactly analogous to `ptp_unpack_EOS_ImageFormat()`/`ptp_unpack_EOS_CustomFuncEx()` reading past `xsize` because no length was passed in.
- Additionally, because the loop's termination condition (`extra_p != p`) can be skipped over entirely by an oversized `data_size`, `extra_p` can run past `p` and keep iterating (since it will never again equal `p` exactly), continuing to call `get_u2le`/`get_u4le`/`get_u8le` over unbounded memory until it happens to hit unmapped pages (crash) or wraps/segfaults.

The only bound enforced anywhere in this call chain is the aggregate check in `FindZipCentralDirectory()`: `cd.central_dir_offset + cd.central_dir_size > in_length` [6](#0-5) . That check validates the *outer* central-directory region against the file length, but nothing constrains individual field lengths (`file_name_length`, `extra_field_length`, per-record `data_size`) against the *remaining* bytes inside that region or inside the mapped file, which is precisely the missing invariant.

### Impact Explanation
An attacker who controls the content of a JAR/ZIP that Bazel's `ijar` tool processes (e.g. a prebuilt jar supplied via `http_jar`/`http_archive`/a registry module, or any archive fed to `run_ijar`/`stamp_jar`) can trigger out-of-bounds reads of process memory in the `ijar` binary. Depending on adjacent memory layout this can crash the build (denial of service in the build tool itself, not the general "resource exhaustion" case excluded by the rules — this is a genuine OOB memory read/segfault due to an invariant violation) or cause bogus size/offset values to be used in later archive processing (`compressed_size`, `uncompressed_size`, `offset` are used to drive later reads via `ProcessLocalFileEntry`/`UncompressFile`), which is C: High-consistent with the referenced CVE's "OOB read" classification.

### Likelihood Explanation
`extra_field_length` and the per-record `header_id`/`data_size` are entirely attacker-controlled bytes in the ZIP central directory that require no special privilege to craft — any party who can get their JAR content processed by `ijar` (a common step for `java_import` deps and interface-jar generation) can trigger this. No checksum bypass is needed because the corruption is internal to the parser, not a tampering-of-verified-bytes scenario; the sha256/integrity check on the original download (if any) protects only the fetched bytes' identity, not the correctness of `ijar`'s own parsing logic once those (attacker-authored) bytes are legitimately consumed.

### Recommendation
Thread an explicit end/length bound (e.g. `const u1 *end`) into `ProcessCentralDirEntry` and its extra-field loop, mirroring `EnsureRemaining()` used in `ProcessLocalFileEntry`. Specifically:
- Validate `extra_field_length`, `file_name_length`, `file_comment_length` against remaining central-directory bytes before advancing `p`.
- Change the extra-field loop condition to `while (extra_p + 4 <= p)` before reading `header_id`/`data_size`, and additionally verify `data_size <= (p - extra_p)` before advancing/interpreting the record.
- Before each `get_u8le(extra)` call, verify `data_size >= 8 * n` for the `n`-th 8-byte field being read.

### Proof of Concept
A JUnit/`BuildIntegrationTestCase`-style reproduction would construct (or a `src/test/shell/bazel` test would drop in) a minimal ZIP whose single central-directory entry has:
- `extra_field_length = 3` (or any value not a multiple of 4), with the extra bytes containing a truncated `header_id`/`data_size` pair that reads past the declared extra field, or
- `extra_field_length ≥ 4`, `header_id == 0x0001` (`ZIP64_EXTRA_FIELD_TAG`), and `data_size = 1` (so `get_u8le(extra)` reads 8 bytes from a 1-byte-declared record), and `*uncompressed_size == U4_MAX` in the entry so the `get_u8le` branch executes.

Feeding this file to `ZipExtractor::Create()`/`ProcessAll()` (the code path `ijar_main.cc` and `stamp_main.cc` invoke) under a memory-sanitized build (ASan) would demonstrate the out-of-bounds read/crash in `ProcessCentralDirEntry`, confirming the analog to CVE-2026-40333's missing-length-parameter OOB read pattern.

    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "
