### Title
Missing validation that `CallContract.value` does not exceed the ether actually transferred to the agent, allowing drain of accumulated agent ether balance - (File: bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs)

### Summary
The Snowbridge V2 outbound XCM-to-Ethereum message converter builds a `Command::CallContract { target, calldata, gas, value }` from an unprivileged `Transact` XCM instruction, where `value` represents ether that the agent contract on Ethereum will forward to `target`. The converter defines an error variant `CallContractValueInsufficient` intended to reject a `value` that exceeds the ether actually withdrawn/transferred in the same message, but this check is never invoked, mirroring the DODO `GatewayTransferNative.withdrawToNativeChain` bug where a native-token amount field was never validated against the amount actually provided.

### Finding Description
`XcmConverter::convert` in [1](#0-0)  decodes an optional `Transact` instruction into a `ContractCall::V1 { target, calldata, gas, value }` and directly pushes `Command::CallContract { target, calldata, gas, value }` without any relationship check between `value` and the ether amount actually reserved via `WithdrawAsset`/`extract_ethereum_native_assets` earlier in the same conversion [2](#0-1) .

The `ContractCall::V1.value` field is explicitly documented as "Include ether held by the agent contract" [3](#0-2) , meaning it is meant to draw from the agent's accumulated Ethereum-side ether balance (built up from prior bridge messages/fees), not solely from the ether transferred in the current message. The converter even defines a dedicated error, `CallContractValueInsufficient`, for exactly this scenario [4](#0-3) , but it is never returned or checked anywhere in the `convert()` function — a grep across the repository confirms this variant is constructed nowhere else and referenced only in its own enum declaration and one unrelated match arm in `message.rs`.

An integration test comment explicitly flags this gap: "value should be less than the transfer amount, require validation on BH Exporter" [5](#0-4) , indicating this validation was intended but never implemented, exactly like the DODO report's missing `require(msg.value >= amount, ...)` for native-token withdrawals.

Any unprivileged origin able to send an `InitiateTransfer`/`Transact` XCM (as demonstrated by the `transact_with_agent_from_asset_hub` test, which is a normal signed-origin XCM execute call) can set `ContractCall::V1.value` to an arbitrary amount, independent of how much ether the message itself reserved/transferred for the agent. Because the corrupted `value` field is not bound to the message's own transferred amount, the Gateway/agent contract on Ethereum ends up forwarding ether it holds from other unrelated messages (fees, prior deposits) to an attacker-chosen `target`, draining the agent's accumulated balance — the same "steal accumulated funds via unchecked amount field" pattern as the DODO report.

### Impact Explanation
This allows theft of the Ethereum-side agent contract's accumulated ether balance, which functions as pooled/shared value analogous to the ZRC20 tokens accumulated in `GatewayTransferNative`. Because `target` and `calldata` are also attacker-controlled, the attacker can direct the drained ether to an arbitrary contract or address, achieving unbacked value transfer out of the bridge with only the cost of the XCM execution fee — a direct fund-theft impact on the bridge.

### Likelihood Explanation
The `Transact`/`InitiateTransfer` path is reachable by any signed origin executing XCM on a chain that allows `AliasOrigin` for a permitted set (`AllowedAliasOrigin`), as shown by the `transact_with_agent_from_asset_hub` test using a plain signed-origin XCM execute call. No governance, privileged key, or malicious relayer/validator is required — the bug is purely in the missing amount-binding check inside the converter logic itself.

### Recommendation
Enforce that `value` in `ContractCall::V1` cannot exceed the ether amount actually reserved for the agent in the same message (i.e., validate against the aggregated `enas`/`extract_ethereum_native_assets` ether total, or track a running "ether reserved for this recipient" tally), returning `CallContractValueInsufficient` when it is exceeded, as the dead error variant and test comment both indicate was originally intended.

### Proof of Concept
1. Attacker (any signed AssetHub account permitted to alias, per `AllowedAliasOrigin`) submits an XCM `execute` with:
   - `WithdrawAsset` / `PayFees` covering only a minimal ether fee.
   - `InitiateTransfer` to Ethereum with `remote_xcm` containing `AliasOrigin`, `DepositAsset`, and a `Transact` encoding `ContractCall::V1 { target: <attacker_contract>, calldata: [], gas: 40000, value: <large_amount> }` where `value` is far larger than any ether reserved in the message.
2. `XcmConverter::convert` in `convert.rs` decodes this into `Command::CallContract { target, calldata, gas, value }` with no check that `value` is bounded by the message's transferred ether (mirrors the missing-`require` step in `withdrawToNativeChain`).
3. The message is queued and, on execution by the Ethereum Gateway contract, the agent forwards `value` ether (drawn from its accumulated balance) to `target`, draining funds belonging to other bridge participants.

	fn extract_ethereum_native_assets(
		&mut self,
		enas: &Assets,
		deposit_assets: &AssetFilter,
		recipient: H160,
	) -> Result<Vec<Command>, XcmConverterError> {
		let mut commands: Vec<Command> = Vec::new();
		for ena in enas.clone().into_inner().into_iter() {
			// Check the the deposit asset filter matches what was reserved.
			if !deposit_assets.matches(&ena) {
				return Err(FilterDoesNotConsumeAllAssets);
			}

			// only fungible asset is allowed
			let (token, amount) = match ena {
				Asset { id: AssetId(inner_location), fun: Fungible(amount) } => {
					match inner_location.unpack() {
						(0, [AccountKey20 { network, key }]) if self.network_matches(network) => {
							Ok((H160(*key), amount))
						},
						// To allow ether
						(0, []) => Ok((H160([0; 20]), amount)),
						_ => Err(AssetResolutionFailed),
					}
				},
				_ => Err(AssetResolutionFailed),
			}?;

			// transfer amount must be greater than 0.
			ensure!(amount > 0, ZeroAssetTransfer);

			commands.push(Command::UnlockNativeToken { token, recipient, amount });
		}
		Ok(commands)
	}
