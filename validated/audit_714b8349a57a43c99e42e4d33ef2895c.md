CVE-2017-15720 describes a Python/Apache Airflow issue where an authenticated user could get remote code execution by crafting a Python object that gets deserialized (a classic Python pickle/YAML-style unsafe deserialization primitive tied to Python's object model). This bug class does not have a structural analog in the Go standard library code housed in this repository (`Kohvert/go--025`, a Go language source tree). Go's `encoding/json`, `encoding/gob`, and other decoders in `src/encoding/...` do not support arbitrary object/class reconstruction from untrusted data the way Python pickle/YAML loaders do — `Unmarshal` only populates fields of a caller-provided, statically-typed Go value via reflection, and interface values decode only into `map[string]any`, `[]any`, or scalar types, never into attacker-chosen concrete types or executable code paths. [1](#0-0) [2](#0-1) 

I searched the JSON v2 decoder (`unmarshalObjectAny`, `makeMethodArshaler`'s `UnmarshalJSON`/`UnmarshalJSONFrom` dispatch) and struct-field unmarshal logic for any path that would let attacker-controlled input select or instantiate an arbitrary Go type/method for execution (the closest structural analog to "creating a special object" triggering code execution), and found none — decoding always targets the statically declared Go type of the destination value, with unknown members either rejected or captured into typed fallback fields, never used to construct new callable objects. [3](#0-2) 

No reachable, unauthenticated (or even authenticated) production Go path in this repository exhibits the "attacker-controlled object construction leading to code execution" primitive that CVE-2017-15720 represents. This is a cross-language, cross-project analogy without a demonstrable Go root cause, so per the rules it should not be stretched into a finding.
