### Title
Relay identity spoofing via unauthenticated `RelayFromAddr` field in `handleCreateRelayRequest` - (File: relay_manager.go)

### Summary
`handleCreateRelayRequest` derives the identity of the relay's initiator (`from`) directly from the attacker-controlled `NebulaControl.RelayFromAddr` / `OldRelayFromAddr` field of an incoming `CreateRelayRequest` control message, rather than from the cryptographically authenticated `h.vpnAddrs` of the peer that actually sent the message. This mirrors the Notional `liquidator` bug class: an action-relevant identity parameter is taken from caller-supplied data instead of being bound to the authenticated sender.

### Finding Description
The handler is invoked from `HandleControlMsg` with `h` being the `*HostInfo` of the already-authenticated peer that physically sent the packet (its identity is bound via the Noise handshake and its certificate). Inside `handleCreateRelayRequest`: [1](#0-0) 

`from` is unmarshalled straight out of the message body (`m.RelayFromAddr`), not taken from `h.vpnAddrs[0]` (the authenticated identity of the sender `h`). The only check performed is that `from` is not one of *my* addresses: [2](#0-1) 

There is no check that `from == h.vpnAddrs[0]` (or is otherwise consistent with the sender's certificate). Consequently, any already-connected peer `h` can send a `CreateRelayRequest` claiming an arbitrary `from` address — including the address of a third, unrelated victim host — and the receiver will:

- Install relay state (`AddRelay`) associating that spoofed `from` VPN address with `h`'s tunnel: [3](#0-2) 
- If the receiver is itself a relay for the true target, forward traffic addressed to that spoofed identity through `h`'s connection: [4](#0-3) 

Because `from` is used as the relay's `PeerAddr` (`AddRelay(..., from, ..., TerminalType/ForwardingType, ...)`), and later matched against `hostinfo.relayState.QueryRelayForByIp` in the outside-packet path (`f.hostMap.QueryVpnAddrsRelayFor`), a malicious peer `h` can register itself as the relay endpoint for a victim's VPN address it does not control, poisoning the relay routing state.

This is analogous to the Sherlock M-21 finding: there, `liquidator` was an unauthenticated parameter accepted from the caller instead of being validated against `msg.sender`; here, `from` (the relay-initiator VPN address) is an unauthenticated parameter accepted from the message payload instead of being validated against the authenticated sender `h.vpnAddrs`.

### Impact Explanation
An authenticated-but-malicious peer can poison another node's relay-state table (`HostInfo.relayState`) by claiming to be relaying on behalf of an arbitrary victim VPN address. This can be used to:
- Hijack a victim's traffic path through the malicious relay node (once `AddRelay`/`Established` state is created, subsequent packets addressed to the victim's VPN address that traverse this relay path get forwarded via the attacker's tunnel — see `QueryVpnAddrsRelayFor` usage in `sendNoMetrics`/`handleOutsideRelayPacket`), enabling traffic interception/redirection.
- Cause remote state poisoning of the hostmap's relay index tables (`hm.Relays`, `relayState`) for a victim address the attacker does not own, potentially leading to denial of service for the legitimate relay path or misdirected relayed traffic.

This satisfies the "remote state poisoning" / "traffic forgery" impact bar required for a valid analog.

### Likelihood Explanation
Reachable by any peer that has already completed a legitimate Nebula handshake (an authenticated node, but not necessarily one that should be trusted to speak for other VPN addresses) — this fits the "no CA-signed certificate needed by attacker beyond being any legitimate peer" reachable-path requirement, since the control message itself carries no proof binding `from` to the sender's own certificate identity. No special configuration (e.g., being the actual relay target) is required to send the spoofed request; the check is only applied for `from == myself`, not `from == h.vpnAddrs[0]`.

### Recommendation
In `handleCreateRelayRequest` (and the analogous `EstablishRelay`/response handling), validate that the claimed `from` (`m.RelayFromAddr`/`OldRelayFromAddr`) equals one of the sender's own authenticated `h.vpnAddrs` before using it to install or update relay state:
```go
if !slices.Contains(h.vpnAddrs, from) {
    logMsg.Error("Relay request 'from' address does not match sender identity")
    return
}
```
This binds the relay-initiator identity to the cryptographically authenticated peer, mirroring how `_authenticateDeleverage` should bind `liquidator` to `msg.sender` in the referenced Sherlock finding.

### Proof of Concept
1. Establish two legitimate Nebula tunnels: attacker node `A` (real cert `A`, VPN addr `10.0.0.5`) and relay node `R` connects to `A`.
2. `A` sends a `Control`/`CreateRelayRequest` message to `R` with `RelayFromAddr` set to victim `V`'s VPN address (e.g., `10.0.0.9`), instead of its own address, and `RelayToAddr` set to some target `T`.
3. `R`'s `handleCreateRelayRequest` only checks `f.myVpnAddrsTable.Contains(from)` (i.e., that `from` isn't `R` itself); since `from` (`10.0.0.9`) is not `R`, the check passes.
4. `R` calls `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)` binding the relay state for VPN address `10.0.0.9` to `A`'s `HostInfo` (`h`), even though `A`'s authenticated `h.vpnAddrs` is `10.0.0.5`, not `10.0.0.9`.
5. Subsequent packets that `R` routes for `10.0.0.9` via relay lookup (`QueryVpnAddrsRelayFor`) may now be forwarded through `A`'s tunnel instead of the legitimate `V` tunnel, achieving relay-state poisoning/traffic redirection without ever presenting a certificate for `V`.

Note: I was unable to fully trace every downstream consumer of the poisoned `relayState` entry (e.g., exact conditions under which `R` would already have or later establish a conflicting/overriding relay entry for the real `V`), so the precise conditions for full traffic hijacking versus a milder DoS/log-poisoning effect could not be fully confirmed from the indexed code alone.
