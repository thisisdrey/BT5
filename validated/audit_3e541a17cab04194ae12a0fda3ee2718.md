### Title
Attacker can permanently brick a leveraged victim's collateral top-ups by filling `depositTokensOfAccount` to `MAX_TOKENS_PER_USER` via dust deposits/transfers - (contracts/Pool.sol)

### Summary
`Pool` enforces a hard cap of 30 tokens (`MAX_TOKENS_PER_USER`) across a user's combined deposit- and debt-token lists. Any unprivileged user can add arbitrary supported `DepositToken`s to a victim's per-account set without the victim's consent — via `DepositToken.deposit(amount, onBehalfOf=victim)` or a plain `transfer` — because `_mint`/`_transfer` unconditionally call `pool.addToDepositTokensOfAccount(recipient)` when the recipient balance moves from 0. Once the set is full, every action that would add a *new* token to the account reverts with `UserReachedMaxTokens`, and a victim whose position is fully locked (`unlockedBalanceOf == 0`) cannot remove the injected entries at all.

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert once `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` (30). [1](#0-0) 
- `DepositToken._mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's balance was zero, and `deposit()` accepts an arbitrary `onBehalfOf_` with no consent check. [2](#0-1) [3](#0-2) 
- `DepositToken._transfer` does the same for the recipient of any transfer, and `transfer`/`transferFrom` only check the *sender's* lock, so an attacker holding msdTOKENs can push dust to any address. [4](#0-3) [5](#0-4) 
- Removal of an entry requires the victim's balance to go to zero, i.e. `transfer`/`withdraw`, both gated by `_revertIfLocked`. `unlockedBalanceOf` returns 0 when the account has debt and `_issuableInUsd == 0`, so an unhealthy/at-limit victim cannot shed the injected dust tokens. [6](#0-5) [7](#0-6) 
- The same cap blocks `DebtToken` issuance: `DebtToken.issue/mint` on a synthetic the victim doesn't already hold calls `addToDebtTokensOfAccount`, which reverts once the combined list is full.

Attack trace (all public, unprivileged):
1. Attacker deposits dust of underlying into each of the pool's deposit tokens (or acquires msdTOKENs and transfers 1 wei) with `onBehalfOf_ = victim` / `to_ = victim`, filling `depositTokensOfAccount[victim]` to 30.
2. Victim, now at the cap and with `_issuableInUsd == 0`, calls `depositTokenB.deposit(amount, victim)` → `_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`. Same for issuing a new synth or receiving seized collateral.
3. Victim tries `dustToken.transfer(attacker, dust)` → `_revertIfLocked` → `unlockedBalanceOf(victim) == 0` → `NotEnoughFreeBalance`. Entries cannot be removed while debt ≥ limit.

### Impact Explanation
Temporary-to-indefinite freezing of funds plus forced-loss-of-liquidation-surplus: a leveraged victim at their collateral factor limit is unable to deposit *new* collateral types to restore health (and cannot issue debt in new synthetics), while simultaneously being unable to purge the injected tokens because all balances are locked. They can only free slots by repaying debt or depositing more of a token already in their list; if they hold none in sufficient size, the position is liquidated where timely collateral top-up would have saved it — a direct, attacker-caused loss. The cost to the attacker is only dust amounts of each supported underlying. This is a state-growth/resource-cap exhaustion analog of the CVE's uncontrolled-resource-consumption DoS, not a gas/unbounded-loop issue: the loop bound (30) is exactly what makes the griefing deterministic.

### Likelihood Explanation
- Requires no privileged role, no oracle manipulation, no malicious contract beyond standard calls; works on the deployed configuration since `deposit(amount_, onBehalfOf_)` is `whenNotPaused` public and transfers are unrestricted.
- Requires a pool with enough supported deposit/debt tokens to reach 30 combined; Metronome pools list many collaterals and msAssets per deployment.
- Cost scales linearly with the number of distinct tokens (dust deposits only); attacker can even reuse one underlying balance by depositing to self then transferring dust.
- Only fully effective against victims whose `unlockedBalanceOf` is 0 (debt at/above limit); healthy users can clear slots at the cost of gas and inconvenience, which tempers the likelihood of permanent loss but still permits targeted freezing of accounts near liquidation.

### Recommendation
- Exclude tokens from the victim's set cap when the balance was received without an opt-in, or track "user-initiated" vs received tokens separately; alternatively, always allow `withdraw`/`transfer` of amounts below a dust threshold regardless of lock status so users can eject unwanted tokens.
- Let `deposit` on behalf of an account that is at the cap still succeed if it's a token already in the set (already true) and allow the *removal* path (`removeFromDepositTokensOfAccount`) even for locked accounts when the balance is being burned/transferred out.
- Consider raising/removing the shared deposit+debt cap accounting so injected deposit tokens cannot crowd out debt tokens needed for repayment-adjacent operations.

### Proof of Concept
Hardhat (fork of a live deployment or local fixture with ≥2 deposit tokens and 2 debt tokens):

```ts
// Setup: pool with deposit tokens msdA..msdN, debt tokens for msUSD, msETH
// Victim deposits A and mints debt up to collateral limit
await depositTokenA.deposit(parseEther('100'), victim.address)
await debtToken.connect(victim).issue(parseEther('X'), victim.address) // issuableInUsd ~= 0

// Attacker fills victim's token list with dust of every other deposit token
for (const dt of otherDepositTokens) {
  await underlying.connect(attacker).approve(dt.address, 1)
  await dt.connect(attacker).deposit(1, victim.address) // adds to victim's list
}
// also issue/transfer debt-token-adjacent entries if needed to reach 30
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(30)

// 1) Victim cannot add a NEW collateral type
await expect(
  depositTokenB.connect(victim).deposit(parseEther('10'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// 2) Victim cannot eject the dust (locked by debt)
await expect(
  depositTokenC.connect(victim).transfer(attacker.address, 1)
).to.be.revertedWithCustomError(depositTokenC, 'NotEnoughFreeBalance')
await expect(
  depositTokenC.connect(victim).withdraw(1, victim.address)
).to.be.revertedWithCustomError(depositTokenC, 'NotEnoughFreeBalance')

// 3) Victim cannot issue debt in a new synthetic either
await expect(
  newDebtToken.connect(victim).issue(1, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// 4) Oracle move or interest accrual makes victim unhealthy; liquidation proceeds
//    while the only remediation (deposit a different collateral) remains blocked.
```
