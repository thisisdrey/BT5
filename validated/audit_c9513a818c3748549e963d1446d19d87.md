## Title
Remote-triggerable `assert!` panic on StackerDB push chunk validation - (File: `stackslib/src/net/chat.rs`)

## Summary
`ConversationP2P::validate_stackerdb_push` contains a hard `assert!(preamble.payload_len > 1)` that operates on the `payload_len` field of a `Preamble`, which is data taken directly from an incoming, attacker-controlled network message. This mirrors the reported bug class: an `assert` on a value that is expected to satisfy an invariant but that is not actually guaranteed to hold for all legitimate/attacker-reachable inputs, causing the process to abort (panic) instead of gracefully rejecting the message.

## Finding Description
`validate_stackerdb_push` is called when a `StackerDBPushChunk` message arrives on a `ConversationP2P`, before any bandwidth/relay checks are performed: [1](#0-0) 

The very first line of the function is:
```rust
assert!(preamble.payload_len > 1); // don't count 1-byte type prefix
```
`preamble.payload_len` is a `u32` field of the `Preamble` struct that is deserialized straight from the wire (via `StacksMessageCodec`), and it is nominally intended to reflect "signature + relayers + message-type byte + payload" length as computed by the sender. Per `CONTRIBUTING.md`'s explicit coding standard for this codebase: "Data from the network... is untrusted... must handle any possible byte sequence" and "Untrusted data ingestion must not panic. ... Panicking failures are forbidden for such data": [2](#0-1) [3](#0-2) 

The assert assumes that by the time this code path is reached, `payload_len` is always `> 1`. However, `payload_len` is a value parsed off the wire and only loosely validated elsewhere (e.g., against `MAX_MESSAGE_LEN` during preamble/message deserialization) — there is no code path shown that specifically guarantees `payload_len > 1` before `validate_stackerdb_push` is invoked for a `StackerDBPushChunk` message. If an attacker crafts (or a legitimate relay forwards, e.g., after a middlebox truncation or a deliberately malformed preamble) a `StackerDBPushChunk` message whose declared `payload_len` is `0` or `1` while the message still deserializes successfully as a `StackerDBPushChunk` payload, the `assert!` fires and the process panics — an unhandled `panic!` in production Rust code aborts/unwinds the thread handling the P2P connection (and, depending on panic-handling configuration, can crash the whole node process).

This is directly analogous to the reported Vyper bug: both are "developer-added sanity assertions" meant to catch programmer/logic errors, but which are reachable via externally-influenced state and revert/panic instead of failing gracefully — trading a recoverable error path for a hard abort.

## Impact Explanation
A successful trigger causes an unhandled panic in the P2P message-handling thread from a single unauthenticated network message. Per the repo's own severity framework, "remote crash/unauthenticated DoS from few messages" is explicitly classified as Critical impact. This is a full, unauthenticated, single-message DoS vector against a node's networking stack — no signature, node key, or privileged role is required to send a `StackerDBPushChunk` message.

## Likelihood Explanation
Likelihood depends on whether any earlier validation step in the message-dispatch pipeline strictly guarantees `payload_len > 1` before this function executes for every reachable code path (I was not able to fully trace/confirm this guarantee across all callers of `validate_stackerdb_push` within the available tool budget — the call sites in `chat.rs` were located but not all fully inspected). If such a guarantee exists and is airtight, the assert is dead code (still risky/fragile) rather than remotely reachable. Given the uncertainty, I flag this as a plausible but **not fully confirmed** finding — the exact reachability of `payload_len <= 1` at the point of the assert needs to be verified against all call sites and the preamble-deserialization/dispatch logic before treating this as certain.

## Recommendation
Replace the `assert!(preamble.payload_len > 1)` with a proper `Result`-returning check that returns `Err(net_error::InvalidMessage)` (or similar) on failure, consistent with the rest of the function's error-handling style and with the project's documented rule that "functions that act on externally-submitted data must never panic."

## Proof of Concept
Not independently confirmed within this session — would require constructing/sending a `StackerDBPushChunk` P2P message with `preamble.payload_len` set to `0` or `1` (via direct socket-level crafting, bypassing the sender-side encoder which normally computes this field correctly) and observing whether it reaches `ConversationP2P::validate_stackerdb_push` before any length re-validation, and confirming the resulting panic terminates/crashes the handling thread or process.     /// Update bandwidth accounting, but forward the stackerdb chunk along if we can accept it.
    /// Possibly return a reply handle for a NACK if we throttle the remote sender
    fn validate_stackerdb_push(
        &mut self,
        network: &PeerNetwork,
        preamble: &Preamble,
        relayers: Vec<RelayData>,
    ) -> Result<Option<ReplyHandleP2P>, net_error> {
        assert!(preamble.payload_len > 1); // don't count 1-byte type prefix

        let local_peer = network.get_local_peer();
        let chain_view = network.get_chain_view();

        if !self.process_relayers(local_peer, preamble, &relayers) {
            warn!(
                "Drop pushed stackerdb chunk -- invalid relayers {:?}",
                &relayers
            );
            self.stats.msgs_err += 1;
            return Err(net_error::InvalidMessage);
        }

            .add_stackerdb_push((preamble.payload_len as u64) - 1);

## Data Input

- **Data from the network, from Bitcoin, and from the config file is untrusted.** Code that ingests such data _cannot assume anything_ about its structure, and _must_ handle any possible byte sequence that can be submitted to the Stacks node.

- **Data previously written to disk by the node is trusted.** If data loaded from the database that was previously stored by the node is invalid or corrupt, it is appropriate to panic.

- **All input processing is space-bound.** Every piece of code that ingests data must impose a maximum size on its byte representation. Any inputs that exceed this size _must be discarded with as little processing as possible_.

- **All input deserialization is resource-bound.** Every piece of code
  that ingests data must impose a maximum amount of RAM and CPU
  required to decode it into a structured representation. If the data
  does not decode with the allotted resources, then no further
  processing may be done and the data is discarded. For an example, see
  how the parsing functions in the http module use `BoundReader` and
  `MAX_PAYLOAD_LEN` in [http.rs](https://github.com/stacks-network/stacks-core/blob/4852d6439b473e24705f14b8af637aded33cb422/src/net/http.rs#L2260-L2285).

- **All network input reception is time-bound.** Every piece of code that ingests data _from the network_ must impose a maximum amount of time that ingestion can take. If the data takes too long to arrive, then it must be discarded without any further processing. There is no time bound for data ingested from disk or passed as an argument; this requirement is meant by the space-bound requirement.

- **Untrusted data ingestion must not panic.** Every piece of code that ingests untrusted data must gracefully handle errors. Panicking failures are forbidden for such data. Panics are only allowed if the ingested data was previously written by the node (and thus trusted).
