### Title
Debt positions below `2 * debtFloorInUsd` can never be liquidated, permanently trapping bad debt - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate` enforces two bounds on `amountToRepay_` that are mutually unsatisfiable for small positions: `maxLiquidable` (50% of debt, set at initialize) caps the repayable fraction, and `debtFloorInUsd` forbids leaving a nonzero remainder below the floor. Any account whose per-synthetic debt is `< 2 * debtFloorInUsd` cannot be liquidated at all, so an attacker can intentionally open positions in that range that become un-liquidatable once they go unhealthy, permanently accumulating bad debt in the pool. This is the direct analog of the availability/DoS class in the report (a liveness break of the liquidation function).

### Finding Description
In `Pool.liquidate`:

```solidity
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}

if (debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(
        address(syntheticToken_),
        _debtTokenBalance - amountToRepay_
    );
    if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
        revert RemainingDebtIsLowerThanTheFloor();
    }
}
``` [1](#0-0) 

`maxLiquidable` is initialized to `0.5e18` (50%) and capped by `updateMaxLiquidable`/`MaxLiquidableTooHigh` so it stays below 100%. [2](#0-1) 

For a position with debt `D` (USD value of `_debtTokenBalance`) where `0 < D < 2 * debtFloorInUsd`:

- Repaying the full debt (`amountToRepay_ = _debtTokenBalance`) gives `wadDiv = 1e18 > 0.5e18` → reverts `AmountGreaterThanMaxLiquidable`.
- Repaying at most 50% leaves `D - amount ≥ 0.5 * D > 0`, and since `D < 2 * floor`, the remainder `0.5*D ≤ remainder < D` either stays `< floor` (reverts `RemainingDebtIsLowerThanTheFloor`) or — for `D` in `(floor, 2*floor)` — any repay amount that keeps remainder `≥ floor` requires `amount ≤ D - floor < D/2`, i.e. only trivially small, still-below-cap partial repays are possible, and each successive repay shrinks `D` further into the un-liquidatable zone. Once `D ≤ floor`, **no** amount satisfies both checks (full repay exceeds `maxLiquidable`; partial leaves `0 < remainder < floor`).

So once a debt position drifts to `D ≤ debtFloorInUsd` — or is created with `D < 2 * floor` and interest accrual/partial liquidation reduces it — liquidation reverts for every possible `amountToRepay_`. There is no alternative liquidation path (`liquidate` is the only function that burns another account's `DebtToken` and seizes `DepositToken`), and `debtFloorInUsd` is a live, governor-tunable parameter designed precisely to keep liquidations profitable.

Attack path (unprivileged EOA, public entry points only):
1. Call `DepositToken.deposit` (or `NativeTokenGateway.deposit`) to post collateral.
2. Call `DebtToken.issue`/`Pool`-level mint to mint synthetic debt `D` just under `2 * debtFloorInUsd`.
3. Let the position become unhealthy via normal market movement (or repeat across many accounts/synths).
4. Any liquidator calling `Pool.liquidate` reverts with either `AmountGreaterThanMaxLiquidable` or `RemainingDebtIsLowerThanTheFloor`. The undercollateralized debt can never be closed.

The test suite even demonstrates both revert paths in the same position (`contracts/test/Pool.test.ts` `describe('debt floor')` and `should revert if repaying more than max allowed to liquidate`), but never the combined case where both bounds exclude all amounts. [3](#0-2) 

### Impact Explanation
Permanent liveness failure of `Pool.liquidate` for every position whose per-synthetic debt is at or below `2 * debtFloorInUsd`. Underwater positions in this band accumulate indefinitely, converting into protocol bad debt (insolvency) and unseizable collateral. An attacker can deliberately mass-produce such positions cheaply (debt just under the floor is by design "unprofitable" to liquidate, but here it is *impossible*), guaranteeing the pool — i.e., other depositors and synthetic holders — absorbs the loss. This satisfies the "temporary freezing of funds / protocol insolvency" acceptance bar via a permanent liquidation-blocking DoS.

### Likelihood Explanation
- `debtFloorInUsd > 0` is the intended configuration (it exists to keep liquidations incentive-compatible), and `maxLiquidable = 50%` is the default.
- Attacker cost is only the collateral for a small position plus gas; positions can be replicated across many accounts and synthetic tokens.
- Positions can also enter the dead zone organically: interest accrual vs. collateral depreciation, or a successful partial liquidation that leaves `remainder ≥ floor` but `remainder < 2*floor` — after which further liquidation becomes impossible once `remainder ≤ floor`.
- No privileged role, oracle manipulation, or mock is required; the revert is deterministic on-chain math.

### Recommendation
Make the two bounds consistent. Options:
- When the remaining debt after a `maxLiquidable`-bounded repay would fall below `debtFloorInUsd`, allow full liquidation (waive `maxLiquidable`) so the position can always be closed — e.g. `if remaining < floor → repay entire balance`.
- Or enforce a **minimum debt at issuance time** in `DebtToken.issue`/`mint` (revert if resulting debt `< 2 * debtFloorInUsd`), plus the same check on the post-liquidation remainder, so the dead zone is unreachable.

### Proof of Concept
Hardhat-style fork/unit PoC mirroring `test/Pool.test.ts`:

```ts
// Setup: pool.initialize() sets maxLiquidable = 0.5e18; governor sets debtFloor.
await pool.updateDebtFloor(parseEther('3000')); // floor = $3,000

// Attacker: deposit collateral, mint synthetic debt worth ~$4,000 (< 2*floor)
await collateral.connect(attacker).approve(depositToken.address, MAX);
await depositToken.connect(attacker).deposit(collateralAmount, attacker.address);
await debtToken.connect(attacker).issue(synthAmount, attacker.address); // debt ≈ $4,000

// Price drops -> attacker position is unhealthy
await masterOracle.updatePrice(collateral.address, droppedPrice);
expect((await pool.debtPositionOf(attacker.address))._isHealthy).false;

// Liquidator tries ANY repay amount:
// (a) partial repay <= 50% leaves ~$2,000 < floor
await expect(
  pool.connect(liquidator).liquidate(msSynth.address, attacker.address, debt.div(2), msdCollateral.address)
).revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor');

// (b) full repay exceeds maxLiquidable (100% > 50%)
await expect(
  pool.connect(liquidator).liquidate(msSynth.address, attacker.address, debt, msdCollateral.address)
).revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');

// No amount in (0, debt] satisfies both -> position is permanently un-liquidatable.
```

The intermediate case: pick `amount = D - floor_equiv` so remainder equals floor — allowed only while `D > floor`; once accrued interest/partials push `D ≤ floor`, even that disappears and every call reverts.
