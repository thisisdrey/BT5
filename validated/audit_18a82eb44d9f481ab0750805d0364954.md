### Title
Kamino integration withdraw path has no fallback for ticket-queued withdrawals, permanently locking user funds when the underlying reserve is illiquid - ([File: programs/marginfi/src/instructions/kamino/withdraw.rs])

### Summary
Kamino's real lending program supports two withdrawal modes: an instant `withdraw_obligation_collateral_and_redeem_reserve_collateral(_v2)` call, and a ticket-based `enqueue_to_withdraw` / `withdraw_queued_liquidity` flow used when the reserve's `total_available_amount` cannot satisfy the withdrawal instantly (analogous to sUSDe's cooldown-gated `withdraw()`). `marginfi`'s `kamino_withdraw` instruction (`programs/marginfi/src/instructions/kamino/withdraw.rs`) exclusively calls the instant CPI path and never issues, tracks, or redeems withdraw tickets, and there is no other marginfi instruction that does so for Kamino-integration banks.

### Finding Description
`kamino_withdraw` decrements the user's marginfi bank shares via `bank_account.withdraw()` / `withdraw_all()` and then unconditionally CPIs into `withdraw_obligation_collateral_and_redeem_reserve_collateral_v2` [1](#0-0) [2](#0-1) . This is a single atomic instruction: if the CPI fails (e.g., because the reserve's `WithdrawQueue`/`total_available_amount` cannot satisfy the request instantly, per Kamino's own `WithdrawTicket` lifecycle documentation [3](#0-2) ), the whole transaction reverts, including the marginfi-side share decrement.

Unlike the WStable/sUSDe case, an individual marginfi user has **no workaround at all**: the Kamino obligation is owned by the bank's `liquidity_vault_authority` PDA, not by the end user [4](#0-3) , so the user cannot directly sign an `enqueue_to_withdraw` call on the underlying reserve to obtain a `WithdrawTicket` and later redeem it via `withdraw_queued_liquidity`. Because marginfi's program never implements these two Kamino instructions for the Kamino-integration bank type, once a Kamino reserve enters a state where instant collateral redemption cannot be satisfied (high utilization / low available liquidity — the same "cooldown/queue" bug class flagged in the WStable/sUSDe report, just triggered by utilization instead of a time-based cooldown), marginfi users depositing into that Kamino bank are completely unable to withdraw until reserve liquidity recovers, with no queued-ticket fallback path exposed by the protocol.

The developer guide itself flags this exact risk class as a known "Ongoing Consideration": *"Liquidity constraints: Insufficient reserve liquidity or withdrawal halts prevent users from accessing funds despite marginfi allowing the operation"* [5](#0-4) , and the getting-started guide confirms `kamino_withdraw` "Can fail if the Bank doesn't have enough liquidity" [6](#0-5) , but this documented behavior is treated as an accepted risk rather than mitigated by implementing the queue path — the exact WStable/sUSDe bug class (missing support for a downstream protocol's non-instant withdrawal mechanism).

### Impact Explanation
When a Kamino reserve integrated as a marginfi bank becomes utilization-constrained (a realistic and externally-triggerable condition, not an admin/privileged action), all marginfi users with deposits in that bank are unable to withdraw their principal via `kamino_withdraw`, and marginfi provides no alternate instruction (no `kamino_enqueue_withdraw`/`kamino_redeem_withdraw_ticket` equivalent) to access the ticket-based queue that Kamino itself offers for exactly this situation. This is a fund-lock/freeze condition reachable by ordinary (unprivileged) depositors with no admin action required, directly mirroring the impact class in the referenced report (funds locked with no protocol-provided exit).

### Likelihood Explanation
Kamino reserves used as collateral sources routinely experience high utilization during volatile markets or large withdrawals, at which point `total_available_amount` can be insufficient for an instant redemption, causing the reserve to fall back to the ticket-queue mechanism. This is a normal operating condition Kamino explicitly designed for (not an edge case), so the likelihood of marginfi users hitting this exact gap is realistically high for actively used Kamino-integration banks with high utilization.

### Recommendation
Implement marginfi-side support for Kamino's ticket-based withdraw flow: add instructions that let marginfi (as the obligation/collateral owner via the `liquidity_vault_authority` PDA) call `enqueue_to_withdraw` when the instant CPI would fail, track the resulting `WithdrawTicket`, and later call `withdraw_queued_liquidity` (or expose a permissionless helper, per Kamino's design allowing any payer to invoke it) to finally deliver the underlying liquidity to the original marginfi depositor once available. Alternatively, gate new deposits/or emit a clear operational-state signal for Kamino banks whose reserve liquidity is low, so integrators/users are warned before the lock is realized.

### Proof of Concept
1. A Kamino reserve backing a marginfi `ASSET_TAG_KAMINO` bank experiences high borrow utilization such that `reserve.liquidity.total_available_amount` (or equivalent) is less than a user's requested `collateral_amount`-equivalent liquidity.
2. User calls `kamino_withdraw` on their marginfi account for that bank; marginfi decrements the user's bank shares in the same instruction as the CPI to `withdraw_obligation_collateral_and_redeem_reserve_collateral_v2` [1](#0-0) .
3. Kamino's CPI handler rejects the instant redemption because available liquidity is insufficient (per Kamino's own `WithdrawTicket` design docs) [3](#0-2) ; the whole marginfi transaction reverts.
4. No other marginfi instruction exists to enqueue a Kamino withdraw ticket on behalf of the bank PDA or to redeem a queued ticket, so the user's withdraw is permanently blocked until reserve utilization drops — with no protocol-provided fallback, unlike Kamino's own native users who can use `enqueue_to_withdraw`/`withdraw_queued_liquidity` directly.

        let program = self.kamino_program.to_account_info();

            bank_key.as_ref(),

        ];
        let signer_seeds: &[&[&[u8]]] = &[seeds];
        let cpi_ctx = CpiContext::new_with_signer(program.key(), accounts, signer_seeds);
        withdraw_obligation_collateral_and_redeem_reserve_collateral_v2(
            cpi_ctx,
            collateral_amount,
        )?;
        Ok(())
