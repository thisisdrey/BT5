## Title
Object pool disconnect race: stale snapshot of pool object files can cause `Disconnect()` to fail (DoS of `DisconnectGitAlternates`) - (File: `internal/git/objectpool/disconnect.go`)

## Summary
`Disconnect()` snapshots the list of object files present in an object pool's `objects` directory, then hard-links each entry from that stale snapshot into the pool member's own object directory before removing the alternates link and validating connectivity. If a concurrent, ordinary housekeeping operation (`FetchIntoObjectPool`, which repacks/consolidates the pool's loose objects and packfiles as part of its normal workflow) mutates the pool's object directory between the snapshot and the hard-link/verification steps, the operation can fail, denying the member repository the ability to disconnect from its pool.

## Finding Description
`Disconnect` first reads the alternates info for a repository and computes the absolute alternate object directory, then calls `findObjectFiles(altObjectDir)` to build a static list of every loose object and packfile currently present in the pool: [1](#0-0) 

This list — analogous to the report's cached `s.totalLiquidity` — is then iterated to hard-link each entry from the pool into the member repository's `objects/` directory: [2](#0-1) 

Only after this loop completes does the code proceed to actually remove the alternates link and perform the connectivity check via `git rev-list --objects --all`, which is the analog of the Uniswap `burn()` precondition check that must hold true at execution time: [3](#0-2) 

Between the moment `findObjectFiles` takes its snapshot and the moment the hard-link loop and subsequent connectivity check run, the object pool is not locked against other mutators. `FetchIntoObjectPool` is a normal, unprivileged mutator RPC (triggered as part of ordinary housekeeping for object pool members, i.e., reachable from an ordinary user's push/fork activity) that fetches into the pool and then repacks it: [4](#0-3) 

If a repack consolidates or removes the specific loose object/pack files that were captured in the stale `objectFiles` snapshot (e.g., loose objects get folded into a new packfile and deleted), the subsequent `storage.Link` call in the hard-link loop will fail with `fs.ErrNotExist` for files not equal to `fs.ErrExist`, causing `Disconnect` to return an error and abort before ever reaching the connectivity check or alternates removal: [5](#0-4) 

This mirrors the reported bug class precisely: a cached/snapshotted piece of external state (`s.totalLiquidity` there, the pool's object-file listing here) is used later to perform an operation with a strict precondition (`burn()` requiring exact zero liquidity there; `os.Link`/hard-link requiring the source file to still exist here), and a concurrent, ordinary, unprivileged operation (an added-liquidity transaction there; a `FetchIntoObjectPool`-triggered repack here) can invalidate that snapshot between calculation and use, causing the operation to revert/fail.

## Impact Explanation
When the race is hit, `DisconnectGitAlternates` fails with an internal error instead of successfully dissociating the repository from its object pool. This is a denial-of-service of that specific RPC/handler: legitimate dissociation requests (e.g., as part of repository migration or fork detachment workflows) can be made to fail reliably by triggering concurrent pool housekeeping via `FetchIntoObjectPool`, which any pool member's ordinary push/fetch activity can schedule. Because `Disconnect`'s own code comments already note that failures partway through this function can leave the repository in a broken/inconsistent alternates state until manually repaired, the impact is amplified beyond a simple retryable failure.

## Likelihood Explanation
`FetchIntoObjectPool` runs housekeeping (fetch + repack) on the pool as part of its normal, expected operation and is not a privileged-only action — it is scheduled as ordinary maintenance for any object pool that has active members receiving pushes. `DisconnectGitAlternates` can be invoked at any time by the controlling application. The window between the `findObjectFiles` snapshot and the completion of the hard-link loop plus connectivity check is proportional to the pool's object count, giving a realistic window for the race to be hit on busy or large pools without requiring any special timing precision from an attacker — an attacker who controls when `FetchIntoObjectPool`/pushes into the pool member happen (which is ordinary usage) can increase the likelihood of hitting the race.

## Recommendation
Ensure the object-file snapshot used for hard-linking and the state used for the connectivity check are mutually consistent, e.g., by:
- Acquiring an exclusive lock or reference-holding mechanism against the object pool for the duration of `Disconnect` (beyond the transaction voting already used for consistency across replicas) so that `FetchIntoObjectPool`/repack cannot run concurrently on the same pool.
- Re-reading the object file listing immediately before performing each hard-link, or retrying the whole disconnect using a freshly re-computed listing if any individual `storage.Link` fails due to a missing source file, instead of aborting the entire operation.
- Treating `fs.ErrNotExist` for source files the same as `fs.ErrExist` for target files (i.e., as benign "someone else already handled or removed this object" cases) rather than as a fatal error, since the relevant object is presumably obtainable via the alternate itself at that point, or by re-fetching the listing.

## Proof of Concept
1. Create a repository and link it to an object pool via `LinkRepositoryToObjectPool`, ensuring the pool contains multiple loose objects/packfiles.
2. Concurrently invoke `FetchIntoObjectPool` for the pool member (this internally performs `git-repack(1)`/housekeeping on the pool as documented in `doc/object_pools.md`), consolidating or removing existing loose objects/packfiles in the pool's `objects` directory.
3. At the same time, invoke `DisconnectGitAlternates` for the linked member repository.
4. `Disconnect()` computes `objectFiles` via `findObjectFiles(altObjectDir)` before the repack removes/renames some of those files, then attempts `storage.Link` on the now-missing source paths in its hard-link loop.
5. Observe `DisconnectGitAlternates` fails with an internal error (e.g., "no such file or directory") instead of completing, demonstrating the concurrent-repack race causes the handler to fail.

```go
// removeAlternatesIfOk is dangerous. We optimistically temporarily
// rename objects/info/alternates, and run `git fsck` to see if the
// resulting repo is connected. If this fails we restore
// objects/info/alternates. If the repo is not connected for whatever
// reason, then until this function returns, probably **all concurrent
// RPC calls to the repo will fail**. Also, if Gitaly crashes in the
// middle of this function, the repo is left in a broken state. We do
// take care to leave a copy of the alternates file, so that it can be
// manually restored by an administrator if needed.
func removeAlternatesIfOk(ctx context.Context, repo *localrepo.Repo, altFile, backupFile string, logger log.Logger, txManager transaction.Manager) error {
	// Acquire distributed lock
	if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("disconnect alternate")), voting.Preparing); err != nil {
		return fmt.Errorf("preparatory vote for disconnecting alternate: %w", err)
	}

	if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("disconnect alternate")), voting.Prepared); err != nil {
		return fmt.Errorf("preparatory vote for disconnecting alternate: %w", err)
	}

	if err := os.Rename(altFile, backupFile); err != nil {
		return err
	}

	rollback := true
	defer func() {
		if !rollback {
			return
		}

		// If we would do a os.Rename, and then someone else comes and clobbers
		// our file, it's gone forever. This trick with os.Link and os.Rename
		// is equivalent to "cp $backupFile $altFile", meaning backupFile is
		// preserved for possible forensic use.
		tmp := backupFile + ".2"

		if err := os.Link(backupFile, tmp); err != nil {
			logger.WithError(err).ErrorContext(ctx, "copy backup alternates file")
			return
		}

		if err := os.Rename(tmp, altFile); err != nil {
			logger.WithError(err).ErrorContext(ctx, "restore backup alternates file")
		}
	}()

	// The choice here of git rev-list is for performance reasons.
	// git fsck --connectivity-only performed badly for large
	// repositories. The reasons are detailed in https://lore.kernel.org/git/9304B938-4A59-456B-B091-DBBCAA1823B2@gmail.com/
	cmd, err := repo.Exec(ctx, gitcmd.Command{
		Name: "rev-list",
		Flags: []gitcmd.Option{
			gitcmd.Flag{Name: "--objects"},
			gitcmd.Flag{Name: "--all"},
			gitcmd.Flag{Name: "--quiet"},
		},
	})
	if err != nil {
		return err
	}

	if err := cmd.Wait(); err != nil {
		return &connectivityError{error: err}
	}
```

```markdown
## Housekeeping

Housekeeping for object pools is handled differently from normal repositories as
it not only involves repacking the pool, but also updating it. The housekeeping
task is thus hosted by the `FetchIntoObjectPool` RPC. This task is typically
only executed with the original object pool member from which the pool has been
seeded and updates the pool by fetching from that member.

It performs the following tasks:

1. Common housekeeping tasks are performed. These are common cleanups which are
   shared between object pools and normal repositories. Most importantly, it
   removes stale lockfiles and deletes known-broken stale references.

1. A fetch is performed from the object pool member into the object pool with a
   `+refs/*:refs/remotes/origin/*` refspec. This fetch is most notably not a
   pruning fetch, that is any reference which gets deleted in the member will
   stay around in the pool.

1. The fetch may create new dangling objects which are not referenced anymore in
   the pool repository. These dangling objects will be kept alive by creating
   dangling references such that they do not get deleted in the pool. See
   [Dangling Objects](#dangling-objects) for more information.

1. Loose references are packed via `git-pack-refs(1)`.
1. The pool is repacked via `git-repack(1)`. The repack produces a single packfile
   including all objects with a bitmap index. In order to improve reuse of
   packfiles where Git will read data from the packfile directly instead of
   generating it on the fly, the packfile uses a delta island including
   `refs/heads` and `refs/tags`. This restricts Git to only generate deltas for
   objects which are directly reachable via either a branch or a tag. Most
   notably, this causes us to not generate deltas against dangling references.
```
