Based on my research, the strongest analog to the Botan TLS 1.3 bug — where the server treats a peer as authenticated and processes protected application data before the Finished/authentication step has actually been (re-)verified — is the transaction verification-caching logic used during block/fork processing in `Manager`, where a transaction's signature/permission validity is inherited from an earlier point in time without being re-checked against the current account permission state before the transaction is applied.

### Title
Stale signature/permission verification reused during fork-switch block application allows a revoked-key transaction to be applied - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
`Manager.getVerifyTxs` marks a transaction contained in an incoming block as already verified (`capsule.setVerified(true)`) purely by matching its raw signature bytes against a transaction already sitting in `pendingTransactions`, instead of re-running `TransactionCapsule.validateSignature`/`checkWeight` against the account's *current* `Permission` at block-application time. [1](#0-0) 

### Finding Description
`TransactionCapsule.validatePubSignature` short-circuits with an `isVerified` flag: once a transaction capsule has been verified once, all subsequent calls skip re-checking the signature/permission weight entirely. [2](#0-1) 

`getVerifyTxs` exploits this same "verified" concept across two different `TransactionCapsule` instances: it looks up whether a transaction with the *same transaction ID and identical signature bytes* already exists in `pendingTransactions` (where it was verified against the permission state at pool-time), and if so calls `capsule.setVerified(true)` on the corresponding transaction found in the new block, entirely skipping `validateSignature`/`checkWeight` for that transaction during block processing: [3](#0-2) 

The core problem is a TOCTOU (time-of-check/time-of-use) gap analogous to the Botan bug class: the "authentication" (signature/permission-weight check against `Permission.threshold`) is performed once, at an earlier point in time (when the transaction entered the pending pool), but the "protected data" (the state-mutating actuator `execute()` for the transaction's contract) is processed later, at block-application time, without re-confirming that the authentication result is still valid for the *current* chain state. If the owning account's `Permission` is updated in between — e.g., via an `AccountPermissionUpdateContract` (handled in `AccountPermissionUpdateActuator`) that lowers a key's weight, raises the threshold, or removes a key from the `Active` permission's `getKeysList()` — a transaction signed under the old permission and cached as `isVerified=true` will still be treated as fully authorized when it is finally included in a block, because `getVerifyTxs` bypasses `TransactionCapsule.checkWeight` (`chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java:233-270`) for it.

The only mitigating check is that the address must not be present in `multiAddresses` (built from `ownerAddressSet` and any `isMultiSignTransaction` in the pending pool), which reduces but does not eliminate the exposure for single-signature owner updates that race with pending non-multisig-marked transactions sharing the identical raw signature bytes.

### Impact Explanation
If exploitable, this allows a transaction that should be rejected under the account's up-to-date permission configuration (e.g., signed by a key whose weight was just reduced or removed by the account owner) to still be executed by the corresponding actuator during block application, i.e. an unauthorized account operation is committed to the chain — matching the "unauthorized account operation" impact bar in the validation criteria.

### Likelihood Explanation
Exploitation requires precise timing: an attacker (or a legitimate account owner responding to a suspected key compromise) must have a transaction sitting in the pending pool, then have the owner's permission changed via a separate committed transaction, and then have the original pending transaction land in a subsequent block via the `switchFork`/`getVerifyTxs` path before it is dropped from the pool. This is a narrower, timing-dependent condition rather than a directly, trivially reachable one-shot attack, so likelihood is moderate rather than high.

### Recommendation
`getVerifyTxs` should not unconditionally trust cached `isVerified` state across pool-time and block-application-time; it should re-run `TransactionCapsule.validateSignature`/`checkWeight` against the current `AccountStore`/`Permission` state before skipping verification, or invalidate cached verification results for any pending transaction whenever the sender's account permissions change.

### Proof of Concept
Conceptual PoC (exact reachability of `getVerifyTxs` from `pushBlock`/`switchFork` in all code paths was not fully traced due to index/time constraints):
1. Attacker/account owner broadcasts TX1 (e.g., a `TransferContract`) signed by key K, which is currently part of the account's Active permission with sufficient weight; TX1 enters `pendingTransactions` and is marked `isVerified=true`.
2. Before TX1 is packed into a block, the account owner (or an attacker with a different still-valid key) broadcasts and gets committed an `AccountPermissionUpdateContract` that removes K or lowers its weight below threshold, validated via `AccountPermissionUpdateActuator.checkPermission`.
3. A later block still contains TX1 (e.g. due to fork switching / re-org), and `getVerifyTxs` matches it against the pending-pool copy by identical signature bytes and marks it verified without recomputing `checkWeight` against the now-updated permission.
4. TX1's actuator executes despite K no longer satisfying the account's current signature-weight threshold.

**Note on completeness:** I was not able to fully confirm, within the available tool budget, every call site that invokes `getVerifyTxs` (it appeared nested under `switchFork` in the retrieved context) or whether additional guards elsewhere in `Manager` fully close this gap before the fork-switch/block-application flow executes the transaction's actuator. A Devin session with full repository access would be needed to trace the complete `pushBlock`/`switchFork`/`getVerifyTxs` call graph and confirm end-to-end exploitability before treating this as a confirmed, actionable vulnerability.

  public List<TransactionCapsule> getVerifyTxs(BlockCapsule block) {

    if (pendingTransactions.size() == 0) {
      return block.getTransactions();
    }

    List<TransactionCapsule> txs = new ArrayList<>();
    Map<String, TransactionCapsule> txMap = new HashMap<>();
    Set<String> multiAddresses = new HashSet<>(ownerAddressSet);

    pendingTransactions.forEach(capsule -> {
      String txId = Hex.toHexString(capsule.getTransactionId().getBytes());
      if (isMultiSignTransaction(capsule.getInstance())) {
        String address = Hex.toHexString(capsule.getOwnerAddress());
        multiAddresses.add(address);
      } else {
        txMap.put(txId, capsule);
      }
    });

    block.getTransactions().forEach(capsule -> {
      String address = Hex.toHexString(capsule.getOwnerAddress());
      String txId = Hex.toHexString(capsule.getTransactionId().getBytes());
      if (multiAddresses.contains(address) || !isSameSig(capsule, txMap.get(txId))) {
        txs.add(capsule);
      } else {
        capsule.setVerified(true);
      }
    });

    return txs;
  }

      DynamicPropertiesStore dynamicPropertiesStore)
      throws ValidateSignatureException {

      try {

          isVerified = false;
          throw new ValidateSignatureException("sig error");
        }
      } catch (SignatureException | PermissionException | SignatureFormatException e) {
        isVerified = false;
        throw new ValidateSignatureException(e.getMessage());
      } finally {
        logSlowSigVerify(startNs);
      }
      isVerified = true;
    }
    return true;
  }
