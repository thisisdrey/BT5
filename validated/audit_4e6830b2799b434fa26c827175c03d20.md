### Title
Missing `on_transaction_aborted` Notification in `CrossShardCommitSender` Causes Permanent Deadlock of Dependent Shard — (`aptos-move/aptos-vm/src/sharded_block_executor/cross_shard_client.rs`)

---

### Summary

`CrossShardCommitSender` implements `TransactionCommitHook` with only `on_transaction_committed`, which sends `RemoteTxnWriteMsg` exclusively for keys present in the committed transaction's write set. When a transaction with cross-shard dependent edges aborts (Move abort or gas exhaustion), the dependent key is absent from the write set, so no message is ever sent. The dependent shard's `CrossShardStateView` blocks indefinitely on a condvar, and its `CrossShardCommitReceiver` thread never receives a `StopMsg` from the source shard. The result is a permanent deadlock of the dependent shard thread, wedging the coordinator and all subsequent block processing.

---

### Finding Description

**`TransactionCommitHook` has no abort notification path.** [1](#0-0) 

The trait exposes only `on_transaction_committed`. There is no `on_transaction_aborted` method. `CrossShardCommitSender` implements this trait: [2](#0-1) 

`send_remote_update_for_success` iterates over the committed transaction's write set and sends `RemoteTxnWriteMsg` only for keys that appear in both the write set and the dependent edges map: [3](#0-2) 

For an aborted transaction (Move abort), the write set contains only gas charges — not the cross-shard key K. For a discarded transaction (gas exhaustion), the write set is empty. In both cases, no `RemoteTxnWriteMsg` is sent for K.

**The design acknowledged this case but never implemented it.**

The `RemoteTxnWrite` struct explicitly documents that `write_op` can be `None` for aborted transactions: [4](#0-3) 

The infrastructure to send `RemoteTxnWriteMsg(None)` exists, but `CrossShardCommitSender` never calls it for the abort path.

**The dependent shard blocks forever.**

`CrossShardStateView` initializes every cross-shard dependency key in `RemoteStateValue::waiting()` state: [5](#0-4) 

`RemoteStateValue::get_value()` spins on a condvar with no timeout: [6](#0-5) 

`CrossShardCommitReceiver::start` loops on `receive_cross_shard_msg` and only exits on `StopMsg`: [7](#0-6) 

After shard 0 finishes execution, it sends `StopMsg` to **itself** (its own channel), not to shard 1: [8](#0-7) 

Shard 1's `CrossShardCommitReceiver` therefore never receives a `StopMsg` from shard 0. Shard 1's block executor thread blocks on `get_value()` for key K. Both of shard 1's threads are permanently stuck.

The coordinator collects results from all shards sequentially: [9](#0-8) 

It blocks forever waiting for shard 1's result, wedging all subsequent block processing.

---

### Impact Explanation

A permanent deadlock of the dependent shard thread prevents the coordinator from completing block execution. No further blocks can be processed on the affected validator. All user transactions in the dependent shard and all subsequent blocks are permanently wedged, preventing any fund movement or state transition. This is a material chain availability failure.

---

### Likelihood Explanation

The attack requires submitting a transaction that:
1. Declares a write to a key K that another transaction in a different shard reads (so the partitioner assigns a cross-shard dependent edge).
2. Aborts during execution (trivially achieved by setting a very low gas limit or including a Move abort).

The partitioner runs before execution and assigns cross-shard dependencies based on declared read/write sets. An attacker who can observe the mempool and understands the partitioning algorithm can craft such a transaction. The abort is fully attacker-controlled via gas limit. No privileged access is required.

---

### Recommendation

1. Add `fn on_transaction_aborted(&self, txn_idx: TxnIndex)` to `TransactionCommitHook`.
2. Implement it in `CrossShardCommitSender` to send `RemoteTxnWriteMsg(RemoteTxnWrite::new(state_key, None))` for every key in the aborted transaction's dependent edges, unblocking the waiting `RemoteStateValue` condvars in the dependent shard.
3. Add a timeout or cancellation mechanism to `RemoteStateValue::get_value()` as a defense-in-depth measure.

---

### Proof of Concept

```
Construct a two-shard PartitionedTransactions:
  - Shard 0, round 0: txn A writes key K, has dependent edge to shard 1 txn B on K.
  - Shard 1, round 0: txn B reads key K (required edge from shard 0 txn A).

Force txn A to abort: set max_gas_amount = 1 (below minimum execution cost).

Expected (correct) behavior:
  CrossShardCommitSender sends RemoteTxnWriteMsg(None) for K to shard 1.
  Shard 1 unblocks, txn B reads None for K, execution completes.

Actual behavior:
  on_transaction_committed is called for txn A with an output whose write set
  contains only gas charges (or is empty for a discard).
  send_remote_update_for_success iterates the write set, finds no entry for K,
  sends nothing to shard 1.
  Shard 1's CrossShardStateView::get_value() for K blocks on condvar forever.
  Shard 1's CrossShardCommitReceiver blocks on receive_cross_shard_msg forever.
  Coordinator blocks on result_rxs[1].recv() forever.
  Assert: shard 1 result channel times out (never receives a result).
```

                            *dependent_shard_id,
                            *round_id,
