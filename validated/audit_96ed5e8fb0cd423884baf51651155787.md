### Title
Cross-lane type confusion: `.miners` StackerDB chunks bypass `SignerMessageTypePrefix` lane validation applied to `.signers-X-Y` contracts - ([File: libsigner/src/events.rs])

### Summary
`TryFrom<StackerDBChunksEvent>` applies `signer_message_payload_matches_lane` to reject payload types that don't match the contract's `MessageSlotID` only on the `SIGNERS_NAME` branch, but the `MINERS_NAME` branch performs no equivalent check before calling `T::consensus_deserialize`. Any chunk written to a `.miners` slot is decoded purely by its embedded type-prefix byte and forwarded as `SignerEvent::MinerMessages`, regardless of whether that variant is semantically valid for the miner lane.

### Finding Description
In `libsigner/src/events.rs`, the `TryFrom<StackerDBChunksEvent> for SignerEvent<T>` implementation branches on the contract name: [1](#0-0) 

For `MINERS_NAME`, each `chunk.data` is fed directly to `T::consensus_deserialize` with no inspection of the type-prefix byte, no `recover_pk`/signature-identity check, and no comparison against an expected set of miner-only variants (`BlockProposal`, `BlockPushed`, `MockProposal`, `MockBlock`).

By contrast, the `SIGNERS_NAME` branch explicitly reads the first byte, maps it to `SignerMessageTypePrefix`, and calls `signer_message_payload_matches_lane(payload_kind, message_id)` to reject any payload whose type doesn't belong to that specific `signers-X-Y` contract's `MessageSlotID`: [2](#0-1) [3](#0-2) 

`SignerMessageTypePrefix` and `MessageSlotID` in `libsigner/src/v0/messages.rs` confirm that `BlockPreCommit` (=7) and `StateMachineUpdate` (=6) are signer-lane-only types (`msg_id()` maps them to `MessageSlotID::BlockPreCommit`/`StateMachineUpdate`), while `BlockProposal`/`BlockPushed`/`MockProposal`/`MockBlock` are miner-only and return `None` from `msg_id()`: [4](#0-3) [5](#0-4) 

This confirms the asymmetry: the codebase itself defines an expected type/lane mapping and enforces it for signer contracts, but never enforces it for the `.miners` contract. Any owner of a `.miners` StackerDB slot (an elected miner able to sign valid chunks for their allotted slot, per `send_miners_message` in `stacks-node/src/nakamoto_node/signer_coordinator.rs`) can put a chunk whose first byte is `6` or `7` into their slot, and it will decode as `SignerMessage::StateMachineUpdate` or `SignerMessage::BlockPreCommit` and be delivered inside `SignerEvent::MinerMessages`, which is architecturally supposed to carry only miner-only variants.

### Impact Explanation
This is a real, code-confirmed architectural gap: the guard (`signer_message_payload_matches_lane`) that exists for the signer contracts is entirely absent for the miner contract path, exactly as the question states. However, I was unable to fully verify the downstream consumer logic in `stacks-signer` (the file `stacks-signer/src/v0/signer.rs`, where `SignerEvent::MinerMessages` is consumed) within the available indexing — the retrieved content for that file was truncated/unavailable. Whether this type confusion translates into an actual state-corrupting or crash-inducing effect (e.g., the runloop trusting/relaying a `StateMachineUpdate` as if it came from a peer signer, bypassing the signer-lane's identity/signature binding) depends on how that consumer dispatches on `SignerMessage` variants irrespective of which `SignerEvent` variant carried them. I could not confirm this with certainty from the available code.

### Likelihood Explanation
The precondition is that the attacker legitimately owns/controls a `.miners` StackerDB slot (i.e., is a currently/recently elected miner, per the slot-range logic in `send_miners_message`), which the stated threat model treats as an allowed "legitimately held slot" scenario. Given that precondition, crafting an arbitrary chunk with a `6` or `7` prefix byte and pushing it via a normal signed StackerDB `put_chunk` call is trivial and repeatable.

### Recommendation
Add an equivalent lane-restriction check to the `MINERS_NAME` branch in `libsigner/src/events.rs`: peek the type-prefix byte, resolve it to `SignerMessageTypePrefix`, and require `payload_kind.msg_id().is_none()` (i.e., only accept `BlockProposal`, `BlockPushed`, `MockProposal`, `MockBlock`) before calling `T::consensus_deserialize`, mirroring the filter already applied via `signer_message_payload_matches_lane` on the signer-contract path.

### Proof of Concept
Add a test in `libsigner/src/events.rs` analogous to `test_signer_message_payload_matches_lane`, but constructing a `StackerDBChunksEvent` with `contract_id.name == MINERS_NAME` and `chunk.data` starting with byte `7` (`BlockPreCommit`) followed by a validly-encoded `Sha512Trunc256Sum`/hash payload; assert that `SignerEvent::MinerMessages` from `TryFrom<StackerDBChunksEvent>` contains a `SignerMessage::BlockPreCommit` entry, demonstrating no filtering occurs for the miner lane. Full confirmation of exploitable severity would additionally require tracing `stacks-signer/src/v0/signer.rs`'s handling of `SignerEvent::MinerMessages` entries, which was not available to verify in this pass.

fn signer_message_payload_matches_lane(
    payload_kind: SignerMessageTypePrefix,
    lane_message_id: u32,
) -> bool {
    payload_kind
        .msg_id()
        .is_some_and(|slot| slot.to_u32() == lane_message_id)
}

impl SignerMessageTypePrefix {
    /// The signer-message lane (`MessageSlotID`) this payload type is broadcast on, if any.
    ///
    /// Miner-only payloads (`BlockProposal`, `BlockPushed`, `MockProposal`, `MockBlock`) do
    /// not broadcast over a `.signers-X-Y` contract and return `None`.
    pub fn msg_id(self) -> Option<MessageSlotID> {
        match self {
            // Mock signature uses the same slot as block response since it's exclusively for
            // epoch 2.5 testing.
            Self::BlockResponse | Self::MockSignature => Some(MessageSlotID::BlockResponse),
            Self::StateMachineUpdate => Some(MessageSlotID::StateMachineUpdate),
            Self::BlockPreCommit => Some(MessageSlotID::BlockPreCommit),
            Self::BlockProposal | Self::BlockPushed | Self::MockProposal | Self::MockBlock => None,
        }
    }
