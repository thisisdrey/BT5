## Title
Missing chain-ID / domain separator in `ValidateMultiSign` precompile hash allows cross-chain signature replay - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The externally reported bug concerns the Forwarder contract's `_verifySig`, which builds a digest from a domain separator, request data, and a type hash but never checks that the domain separator's embedded chain ID matches the executing chain's ID — letting a signature valid on one chain be replayed on another. The `ValidateMultiSign` TVM precompile in java-tron has the analogous defect: it hashes `address || permissionId || data` with no chain identifier at all, so any smart contract that relies on this precompile for off-chain signature authorization is vulnerable to cross-chain replay.

### Finding Description
`ValidateMultiSign.execute` recovers signer addresses and checks permission weight against a hash computed purely from the account address, permission ID, and caller-supplied `data`: [1](#0-0) 
There is no chain ID, genesis block hash, or any other chain-specific domain separator mixed into this hash. Any TRC20/DApp contract using this precompile (a common on-chain multisig-authorization primitive, exposed at a fixed precompiled address and reachable from any smart-contract call an unprivileged caller triggers) verifies signatures the exact same way regardless of which java-tron-based network it is deployed on.

Similarly, base transaction signing in `TransactionCapsule.sign`/`addSign`/`checkWeight` signs over `getTransactionId()` (a hash of `raw_data`, which contains `ref_block_hash`/`ref_block_num`/expiration, but no explicit `chain_id` field) rather than a domain separator bound to chain identity: [2](#0-1) 
Base-layer transaction replay is normally mitigated because `ref_block_hash` ties the transaction to a specific block that (in practice) will not exist identically across independent chains. However, the `ValidateMultiSign`/`BatchValidateSign` precompiles are a general-purpose off-chain signature-authorization mechanism used inside arbitrary smart contracts (e.g., meta-transaction/permit-style flows), and they carry **no chain-binding data whatsoever** — an account's signature approving an operation (e.g., an ERC20/TRC20-style permit, a bridge withdrawal, a governance vote) on one java-tron-based network (mainnet, Nile/Shasta testnet, or any private/forked deployment sharing the same account address and permission configuration) can be captured and replayed verbatim against the same contract logic deployed on a different chain.

### Impact Explanation
Because the same private key controls the same account address across every java-tron-derived chain (mainnet, testnets, private forks), and `ValidateMultiSign`'s hash has no chain-specific component, a signature authorizing a sensitive action (fund transfer, permission change, contract-specific approval) can be replayed on a different chain sharing the same account/permission state, resulting in unauthorized execution of that action and potential theft of assets on the replay-target chain.

### Likelihood Explanation
Exploitation requires only that a signed authorization (data + signature pair) intended for use with `ValidateMultiSign` on one chain be observable (e.g., from a public mempool, block explorer, or bridge relay) and then submitted to a contract on another java-tron-based deployment with matching account/permission state — no special privileges are needed, matching the "unprivileged transaction broadcaster / anonymous API client" reachability bar.

### Recommendation
Include a chain-specific domain component (e.g., the network's `chain_id` value, exposed via the `CHAINID` opcode/`getChainId()` dynamic property) in the hash computed by `ValidateMultiSign`/`BatchValidateSign` (and encourage/require dependent contracts to do the same), so signatures are bound to a specific chain and cannot be replayed elsewhere.

### Proof of Concept
1. Deploy a contract on java-tron mainnet that uses `ValidateMultiSign` to authorize a sensitive operation (e.g., transferring TRC20 tokens) via a signed `data` payload.
2. Deploy the identical contract bytecode/state configuration on a separate java-tron-based chain (fork/testnet) where the same account address exists with the same permission structure (achievable since TRON addresses/keys are chain-independent).
3. Capture a valid `(data, signature)` pair authorized on the first chain.
4. Submit the same `(data, signature)` to the contract on the second chain; because `combine = address || permissionId || data` in `PrecompiledContracts.java` lines 1057-1064 contains no chain identifier, `ValidateMultiSign` returns success, and the operation executes without the signer's fresh consent on that chain.
