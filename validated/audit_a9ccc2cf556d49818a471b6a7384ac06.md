Confirmed: `ExchangeWithdrawContract` in `protocol/src/main/protos/core/contract/exchange_contract.proto` has only `owner_address`, `exchange_id`, `token_id`, and `quant` — no minimum-output/expected field at all, unlike `ExchangeTransactionContract` which has `expected` for exactly this purpose. This is reachable via the `/wallet/exchangewithdraw` HTTP endpoint served by `ExchangeWithdrawServlet` and executed through `ExchangeWithdrawActuator`.

### Title
No slippage protection for Exchange withdrawal allows front-running of LP withdrawals - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeWithdrawContract` lacks any minimum-output parameter, so a user withdrawing liquidity from a bancor-style TRON `Exchange` pool cannot bound the amount of the counterpart token they will receive. The paired output amount (`anotherTokenQuant`) is computed at execution time from the exchange's live token balances, which can be manipulated by an attacker inserting `ExchangeTransactionContract` trades immediately before the withdrawal is packed into a block.

### Finding Description
In `ExchangeWithdrawActuator.execute()`, when a user submits an `ExchangeWithdrawContract`, the contract only supplies `token_id` and `quant` — the amount of one side of the pool they intend to withdraw. The corresponding amount of the other token (`anotherTokenQuant`) is derived purely from the current pool ratio at execution time: [1](#0-0) 

This calculation uses `firstTokenBalance`/`secondTokenBalance` fetched from the `ExchangeCapsule` at the moment of execution, not at the moment the user signed the transaction: [2](#0-1) 

`doValidate()` only performs sanity/precision checks ("exchange balance is not enough", "withdraw another token quant must greater than zero", "Not precise enough") — none of which are a user-supplied minimum-output bound: [3](#0-2) 

Compare this to `ExchangeTransactionContract`, which does have an `expected` field enforced as slippage protection during trades: [4](#0-3) [5](#0-4) 

Because `ExchangeWithdrawContract` was never given an equivalent `expected`/minimum field, and `ExchangeWithdrawActuator` never checks any user-provided floor on `anotherTokenQuant`, there is no mechanism at all — analogous to the GMX report's "no swap path" case — for a withdrawing LP to protect against price movement between transaction creation and block inclusion.

### Impact Explanation
An attacker observing a pending `ExchangeWithdrawContract` in the mempool (or a block producer with transaction ordering control) can front-run it with `ExchangeTransactionContract` trades that shift the pool ratio, then optionally back-run with a reverse trade, extracting value from the withdrawing user's redeemed tokens — a classic sandwich attack. The withdrawing user has no way to reject the transaction if the resulting `anotherTokenQuant` falls below their acceptable threshold, resulting in direct loss of funds for the affected account, which is reachable by any account holding tokens deposited into an `Exchange` and by any account that can submit `ExchangeTransactionContract` trades to manipulate the pool.

### Likelihood Explanation
The `Exchange` (bancor-style pools) feature and its HTTP/gRPC APIs (`/wallet/exchangewithdraw`, `/wallet/exchangetransaction`) remain part of java-tron's actuator and Wallet API surface and are reachable by any signed transaction or unprivileged API client; no special privilege is required to submit either an `ExchangeTransactionContract` (to move the pool ratio) or an `ExchangeWithdrawContract` (the victim's own withdrawal). This makes exploitation feasible whenever an `Exchange` with LP participants has enough liquidity depth for an attacker to move the price meaningfully within a block.

### Recommendation
Add a minimum-expected-output field (e.g., `expected_another_token_quant`) to `ExchangeWithdrawContract`, and in `ExchangeWithdrawActuator.doValidate()`/`execute()` verify that the computed `anotherTokenQuant` meets or exceeds the user-supplied minimum, mirroring the `expected` check already present in `ExchangeTransactionActuator`.

### Proof of Concept
1. Attacker monitors the mempool/pending transactions for an `ExchangeWithdrawContract` withdrawing `tokenID` from `exchangeId`.
2. Attacker submits an `ExchangeTransactionContract` trade that shifts the pool ratio in `exchangeCapsule` (e.g., sells a large amount of `anotherTokenID` into the pool), executed via `ExchangeTransactionActuator.execute()`.
3. The victim's `ExchangeWithdrawContract` executes afterward; `ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` using the now-skewed `firstTokenBalance`/`secondTokenBalance`, giving the victim far less of the paired token than expected at the time they signed the transaction.
4. Since neither the protobuf contract nor `doValidate()` contains any user-specified floor on `anotherTokenQuant`, the withdrawal succeeds regardless of how unfavorable the resulting amount is.
