## Title
Stale Cached Signature/Permission Verification in `Manager.getVerifyTxs()` Allows Transactions Signed Under Revoked Permissions to Bypass Re-validation During Block Application - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
The reported PX4 CVE-2024-24255 is a race condition where a mission-feasibility precheck's result is trusted at execution time even though vehicle state changed in between, letting the drone fly a mission that should have been rejected. `java-tron`'s `Manager.getVerifyTxs()` has the analogous pattern: a transaction's signature/permission verification result computed at one point in time (`pushTransaction`, when the tx entered the local mempool) is blindly trusted and reused at a later point (block application), skipping re-validation even though the account's permission configuration may have changed in the interim.

### Finding Description
When a block arrives, `Manager.getVerifyTxs()` compares the block's transactions against the locally cached `pendingTransactions` pool. If a transaction in the incoming block has the same transaction id and identical raw signature bytes as one already sitting in `pendingTransactions`, the capsule is trusted outright: [1](#0-0) 

`capsule.setVerified(true)` is set directly, bypassing `TransactionCapsule.validateSignature()`'s normal check-then-verify flow entirely for this transaction when `processTransaction`/`applyBlock` later runs: [2](#0-1) 

Because `isVerified` is already `true`, `validateSignature()` short-circuits and never calls `validatePubSignature()` again — the method that actually re-derives the account's current `Permission`, its threshold, and re-checks signer weights against that permission. The original verification in `pushTransaction()` was only ever performed against the account/permission state that existed at the moment the transaction was placed into the mempool: [3](#0-2) 

Between that moment and the moment the block (which may contain earlier transactions, e.g. an `AccountPermissionUpdateContract`, that change the same account's signer keys/threshold) is actually applied via `processTransaction` inside `applyBlock`/`processBlock`, no re-check of permission validity occurs for the trusted transaction — only the byte-identical signature match is checked (`isSameSig`), not whether that signature is still authorized under the account's *current* permission set at block-apply time.

Notably, the project's own test suite shows the authors were aware of this exact class of staleness bug in the `switchFork` path and added a fix there (clearing `isVerified` before re-applying the new branch): [4](#0-3) [5](#0-4) 

However, the normal `pushBlock` → `getVerifyTxs` path that trusts the mempool cache has no equivalent re-validation guard: it never re-derives permission state, it only compares signature bytes.

### Impact Explanation
An account owner who revokes or rotates a key via `AccountPermissionUpdateContract` (e.g. because the key was compromised, or an authorized multisig cosigner's weight is reduced/removed) can have a previously mempool-cached transaction — signed under the *old* permission — still execute as if it were still authorized, because the node trusts the cached `isVerified=true` flag instead of re-checking the signature against the account's current permission at the time the block is actually applied. This is an unauthorized account operation: a transaction that should be rejected (signed by a since-revoked key or by signers who no longer meet the current threshold) is allowed to execute against account state/funds, directly matching the "concrete unauthorized account operation" acceptance criterion.

### Likelihood Explanation
Requires: (1) a transaction sitting in `pendingTransactions` signed under an account's current permission set, and (2) a subsequent transaction (broadcastable by anyone with appropriate permission on the account, or the account owner) that changes that same account's permission before the block containing the first transaction is applied. Both are reachable purely through normal transaction broadcasting (`AccountPermissionUpdateContract` + any other contract type) — no privileged witness/SR behavior is required, only ordinary account/permission management activity and normal node mempool/block-processing timing, which is common on a live chain with multisig accounts.

### Recommendation
In `Manager.getVerifyTxs()`, do not unconditionally set `capsule.setVerified(true)` based solely on transaction-id/signature-byte equality with the mempool copy. Either drop this optimization for transactions whose owner address is affected by any permission-changing contract in the same or intervening blocks, or re-run `validatePubSignature()`/permission-threshold checks at `processTransaction` time regardless of the cached flag, mirroring the fix already applied for `switchFork` (`tx.setVerified(false)` before re-applying transactions on a diverged/updated state).

### Proof of Concept
1. Account `A` initially has `Permission` P1 (single-key owner `K1`, threshold 1).
2. Attacker submits Transaction `T1` (e.g. a `TransferContract` moving funds out of `A`) signed by `K1`. It passes `pushTransaction()`'s `validateSignature` check under P1 and is placed in `pendingTransactions` with `isVerified=true`.
3. Account owner submits Transaction `T2`, an `AccountPermissionUpdateContract` revoking `K1` and installing permission P2 (new key `K2`), intending to invalidate any pending signature made by `K1`.
4. A block is produced/received containing both `T2` and the still-cached `T1` (with identical id/signature bytes to the mempool copy).
5. `Manager.getVerifyTxs()` matches `T1` by id+signature against the mempool entry and calls `capsule.setVerified(true)` directly — see `framework/src/main/java/org/tron/core/db/Manager.java:1260-1268`.
6. During `processBlock`/`applyBlock`, `processTransaction` executes `T2` first (revoking `K1`), then executes `T1`; because `T1.isVerified == true`, `validateSignature()` returns immediately without re-checking `K1` against the now-updated permission P2 — see `TransactionCapsule.java:698-719`.
7. `T1` executes and transfers funds even though `K1` was revoked before the block was applied, demonstrating the stale-verification bypass.

  public boolean validateSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore) throws ValidateSignatureException {
    if (!isVerified) {
      //Do not support multi contracts in one transaction
      Transaction.Contract contract = this.getInstance().getRawData().getContract(0);
      if (contract.getType() != ContractType.ShieldedTransferContract) {
        validatePubSignature(accountStore, dynamicPropertiesStore);
      } else {  //ShieldedTransfer
        byte[] owner = getOwnerAddress();
        if (!ArrayUtils.isEmpty(owner)) { //transfer from transparent address
          validatePubSignature(accountStore, dynamicPropertiesStore);
        } else { //transfer from shielded address
          if (this.transaction.getSignatureCount() > 0) {
            throw new ValidateSignatureException("there should be no signatures signed by "
                    + "transparent address when transfer from shielded address");
          }
        }
      }
      isVerified = true;
    }
    return true;
  }

    dbManager.pushBlock(p);

        a.getBlockId(), chainManager.getDynamicPropertiesStore().getLatestBlockHeaderHash());

    // re-validates against the fork-chain state
