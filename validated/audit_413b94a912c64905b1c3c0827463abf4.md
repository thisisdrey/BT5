### Title
Scheduler permanently drops (instead of retrying) tasks whose dispatch is rejected by `CallFiltered`, letting a permissionless `SafeMode::enter` attacker discard another user's scheduled call - (File: `substrate/frame/scheduler/src/lib.rs`)

### Summary
`pallet-scheduler` executes queued tasks in `on_initialize` via `execute_dispatch`, which calls the filtered `Dispatchable::dispatch` for `RuntimeCall`. Any account can permissionlessly activate `pallet-safe-mode` (`SafeMode::enter`, a signed, deposit-gated extrinsic) or a privileged actor can pause via `pallet-tx-pause`. While the runtime call filter is active, non-whitelisted calls dispatched by the Scheduler fail with `frame_system::Error::CallFiltered`. Because `service_task` treats any `Ok(result)` (including an inner `Err(CallFiltered)`) as "task serviced," the agenda slot is unconditionally cleared and the task is dropped forever - never retried or rescheduled - unless the task happened to have a pre-configured retry policy. This mirrors the Notional `PauseRouter` bug class: a pause mechanism silently and permanently blocks a protective/beneficial state transition (here: a queued call) with no recourse once the pause lifts, and it can be triggered by an unprivileged party.

### Finding Description
`Scheduler::on_initialize` → `service_agendas` → `service_agenda` → `service_task` → `execute_dispatch`: [1](#0-0) 

`execute_dispatch` calls `call.dispatch(dispatch_origin)`, which routes through the generated `RuntimeCall::dispatch` that enforces `frame_system::Config::BaseCallFilter` for every non-root origin (per the pallet's own doc: scheduled calls are dispatched "with the default filter for the origin ... except root which will get no filter"): [2](#0-1) 

Back in `service_task`, the outer `Ok(result)` arm is taken regardless of whether `result` itself is `Ok` or `Err` (e.g. `Err(CallFiltered)`); the task slot is set to `None` (removed from `Agenda`) unless it is periodic: [3](#0-2) 

The active call filter that causes `CallFiltered` can be `pallet-safe-mode`, which any signed account can enter permissionlessly by posting a deposit - no root/governance/relayer/validator involved: [4](#0-3) 

`SafeMode::is_allowed`/`Contains` implementation is what feeds into `BaseCallFilter` and blocks any non-whitelisted call, including calls dispatched internally by the Scheduler (whitelisting only covers `System`, `SafeMode`, `TxPause` in the reference runtime): [5](#0-4) [6](#0-5) 

Because `EnterDuration`/`ExtendDuration` are attacker-chosen up to the configured max (any signed account can call `enter`, and other accounts can `extend`), an attacker can time entry so that the safe-mode window covers exactly the block at which a target's non-root, non-periodic, non-retry-configured scheduled task (e.g. a `Treasury`-driven spend payout, a vesting release, a proxy-scheduled call, or any dApp-level "future action") is due. When `on_initialize` runs at that block, the call fails with `CallFiltered` and is irrecoverably purged from `Agenda`/`Lookup` - there is no automatic re-queue after safe mode exits.

### Impact Explanation
This breaks the required invariant that "queues, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." Here the queue (the Scheduler's `Agenda`) advances (the task is consumed) even though execution demonstrably failed. For any protocol or user relying on the Scheduler to eventually deliver a call - fund releases, unlocks, unbonding completions, proxy time-locks, governance-adjacent automation - a permissionless, deposit-bonded actor can force a specific queued action to be silently and permanently dropped, resulting in a stuck/lost user-fund or state-transition scenario with no recourse, matching the "permanent user-fund lock" and "message queue must only advance after ... execution ... succeeds" impact classes.

### Likelihood Explanation
`SafeMode::enter` is a public, unprivileged, signed extrinsic gated only by a deposit (`EnterDepositAmount`), not by any admin/governance/validator/relayer role, so the precondition ("malicious peer/validator/governance") exclusion does not apply. The attacker only needs to predict/observe the block at which a target's scheduled, non-periodic, filter-non-exempt call is due (visible on-chain via `Agenda` storage) and enter safe mode so that block falls inside the `[now, EnteredUntil]` window. This is a low-cost, deterministic, and repeatable griefing primitive, not merely a front-running race - the attack works because the discard logic is unconditional on filter failure, independent of MEV/ordering.

### Recommendation
In `service_task`/`execute_dispatch`, distinguish `DispatchError::from(frame_system::Error::CallFiltered)` (or, more generally, any error indicating the runtime is in a temporary blocked state) from genuine call-level failures, and treat it like the `Overweight`/`Unavailable` postponement path (re-insert the task into the agenda for a later block, or explicitly requeue after the filtering condition is known to lift) instead of unconditionally clearing the `Agenda` slot on any `Ok(result)` regardless of the inner `Err`.

### Proof of Concept
1. Configure a runtime with `pallet-scheduler` and `pallet-safe-mode` as in `substrate/bin/node/runtime/src/lib.rs` (`SafeModeWhitelistedCalls` only whitelists `System`, `SafeMode`, `TxPause`).
2. Victim (or a pallet on the victim's behalf, e.g. Treasury) schedules a non-periodic, non-root-origin call `C` for block `N` via `Scheduler::schedule`/`schedule_named` (no retry configuration set).
3. Attacker, at block `N - k`, calls `SafeMode::enter(origin: signed(attacker))`, posting `EnterDepositAmount`, with `EnterDuration` chosen (or extended via `SafeMode::extend`) so that `EnteredUntil >= N`.
4. At block `N`, `Scheduler::on_initialize` runs `service_task` for `C`; `execute_dispatch` calls `C.dispatch(origin)`, which fails with `frame_system::Error::CallFiltered` because `SafeMode::is_allowed` returns `false` for `C`'s pallet/call.
5. `service_task`'s `Ok(result)` arm executes: since `C` is not periodic, `Agenda[N][index] = None` and `T::Preimages::drop(&task.call)` runs — `C` is now irrecoverably gone, even though safe mode exits at `EnteredUntil` (block `N + few`) and the transfer/unlock/payout that `C` represented never happens.
6. This can be reproduced deterministically in the existing `substrate/frame/scheduler/src/tests.rs` harness combined with a `Contains` filter mock analogous to `substrate/frame/safe-mode/src/tests.rs::fails_to_filter_calls_to_safe_mode_pallet`, by scheduling a call, activating the filter for exactly the target block, and observing the `Event::Dispatched { result: Err(CallFiltered) }` followed by absence from `Agenda`.

	fn execute_dispatch(
		weight: &mut WeightMeter,
		origin: T::PalletsOrigin,
		call: <T as Config>::RuntimeCall,
	) -> Result<DispatchResult, ()> {
		let base_weight = match origin.as_system_ref() {
			Some(&RawOrigin::Signed(_)) => T::WeightInfo::execute_dispatch_signed(),
			_ => T::WeightInfo::execute_dispatch_unsigned(),
		};
		let call_weight = call.get_dispatch_info().call_weight;
		// We only allow a scheduled call if it cannot push the weight past the limit.
		let max_weight = base_weight.saturating_add(call_weight);

		if !weight.can_consume(max_weight) {
			return Err(());
		}

		let dispatch_origin = origin.into();
		let (maybe_actual_call_weight, result) = match call.dispatch(dispatch_origin) {
			Ok(post_info) => (post_info.actual_weight, Ok(())),
			Err(error_and_info) => {
				(error_and_info.post_info.actual_weight, Err(error_and_info.error))
			},
		};
		let call_weight = maybe_actual_call_weight.unwrap_or(call_weight);
		let _ = weight.try_consume(base_weight);
		let _ = weight.try_consume(call_weight);
		Ok(result)
