Confirmed root cause: `EntryBytesBudget` at [1](#0-0)  only exposes `reserve()`, which atomically increments `consumed` via CAS, with **no corresponding release/decrement method anywhere in the struct**. When `consumer.rs::execute_and_commit_transactions_locked` reserves bytes for a batch and then `record_transactions` fails (e.g. `PohRecorderError::MaxHeightReached`/other recorder error), the code explicitly reverts the cost-tracker state via `Self::remove_added_transaction_costs(bank, &transaction_costs)` but never reverts the `entry_bytes_budget` reservation for the same batch, at [2](#0-1) .

### Title
Failed-to-record transaction batches permanently consume `EntryBytesBudget` slot capacity, causing premature and unrecoverable `MaxHeightReached` for the remainder of the slot - (File: `runtime/src/bank/entry_bytes_budget.rs`, `core/src/banking_stage/consumer.rs`)

### Summary
`EntryBytesBudget::reserve()` [3](#0-2)  irreversibly increments the `consumed` counter once a batch's serialized size is reserved. `Consumer::execute_and_commit_transactions_locked` reserves `entry_bytes` for the batch's processed transactions and then attempts `record_transactions` [4](#0-3) . If recording fails, the code path at lines 397-414 unwinds the cost-tracker accounting (`remove_added_transaction_costs`) but takes no analogous action to release the just-reserved `entry_bytes` back to the budget. This mirrors the reported bug class: a resource is "charged" against a shared running total to compute/gate subsequent capacity, but the corresponding decrement/release on the failure/rollback path is missing, leaving the total permanently overstated relative to the actual state.

### Finding Description
`entry_bytes_budget.rs` models remaining serialized-entry space for a slot as `slot_limit - consumed`, checked with `next > self.slot_limit` in `reserve()` [3](#0-2) . There is no `release`, `unreserve`, or `sub` method defined on `EntryBytesBudget` — the only mutating operation is the CAS-loop that adds to `consumed`. Every call site that reserves bytes assumes recording will subsequently succeed and does not need to compensate on failure.

In `Consumer::execute_and_commit_transactions_locked`, `entry_bytes` is computed by summing `tx.serialized_size()` for every transaction that `was_processed()` [5](#0-4) , then reserved against the bank's `entry_bytes_budget()` prior to calling `record_transactions` [4](#0-3) . If `record_transactions` returns an error (e.g. the PoH recorder rejects because the working bank's max tick height was reached, or any other `PohRecorderError`), the transactions are never actually written to the PoH stream/entries, yet the bytes were already irreversibly added to `consumed`. The failure-handling branch only calls `Self::remove_added_transaction_costs(bank, &transaction_costs)` [6](#0-5)  to revert the `CostTracker`, showing the authors' intent to fully unwind side effects on this path — but the `entry_bytes_budget` reservation is left uncompensated.

Since `PohRecorderError::MaxHeightReached` can legitimately occur for transient reasons unrelated to `entry_bytes_budget` itself (e.g. bank already frozen, `bank_already_frozen` check just above at lines 306-330, or races on `working_bank`/tick height near the end of a slot), any unstaked or staked client whose transactions get batched into a `record_transactions` call that ends up racing against the recorder near end-of-slot will cause that batch's `entry_bytes` to be permanently subtracted from the slot's remaining budget without any block space actually being produced.

### Impact Explanation
Because `consumed` never decreases within a slot (no release path exists), repeated failed-record attempts progressively and permanently shrink the slot's usable `entry_bytes_budget` capacity — space that is never returned even though no data was recorded. In a busy/contended banking stage where recording races against approaching the bank's max tick height (a normal, frequent occurrence at the tail of every leader slot, and also possible whenever a batch is executed concurrently with slot completion), this can cause the effective per-slot entry-bytes budget to be exhausted prematurely, causing `PohRecorderError::MaxHeightReached` for subsequent, otherwise-valid transaction batches for the remainder of the slot. This degrades the amount of legitimate transaction throughput a leader can pack into a slot, without any adversary needing to do anything unusual — normal end-of-slot contention triggers it. This is a state-corruption/no-decrement bug directly analogous to the reported issue: a running total used to gate a limited resource is charged but never uncharged on the failure path, permanently and cumulatively wasting capacity.

### Likelihood Explanation
This code path executes on every leader slot in `Consumer::execute_and_commit_transactions_locked` and the reserve-then-maybe-fail-to-record sequence is unconditional; the failure branch (record error) is a normal occurrence near slot boundaries (the exact class of races the surrounding code already anticipates, per the `bank_already_frozen` early-return at lines 306-330). No special privileges, malicious input, or attacker control are required — it is a straightforward consequence of normal validator leader operation whenever a recording attempt loses a race against slot completion.

### Recommendation
Add a `release`/`unreserve` method to `EntryBytesBudget` (symmetric, saturating decrement of `consumed`) and call it in the error branch of `execute_and_commit_transactions_locked` whenever `record_transactions` fails after a successful `reserve()`, mirroring the existing `remove_added_transaction_costs` rollback for the cost tracker.

### Proof of Concept
Not independently executable from static analysis alone, but reproducible by construction from the code: 
1. Drive the banking stage to process and successfully cost-track a transaction batch, calling `entry_bytes_budget().reserve(entry_bytes)` successfully.
2. Force `self.transaction_recorder.record_transactions(...)` to return `Err(PohRecorderError::MaxHeightReached)` (naturally occurs when the working bank's tick height reaches `max_tick_height` between reservation and record, or can be forced in a unit test analogous to the existing `test_bank_process_and_record_transactions_already_frozen` test at [7](#0-6) ).
3. Observe that `bank.read_cost_tracker().unwrap().transaction_count()`/`block_cost()` are correctly reverted to 0 (as asserted in that existing test), but there is no equivalent assertion or reset for `bank.entry_bytes_budget()`'s consumed bytes — repeating the failure accumulates `consumed` without bound up to `slot_limit`, after which all further `reserve()` calls in the same slot fail with `ExceedsSlotLimit` even though zero entries were ever actually recorded.

#[derive(Debug)]
pub struct EntryBytesBudget {
    consumed: AtomicU64,
    slot_limit: u64,
}

impl EntryBytesBudget {
    pub const fn new(slot_limit: u64) -> Self {
        Self {
            consumed: AtomicU64::new(0),
            slot_limit,
        }
    }

    pub const fn slot_limit(&self) -> u64 {
        self.slot_limit
    }

    pub fn reserve(&self, bytes: u64) -> std::result::Result<(), EntryBytesReserveError> {
        loop {
            let current = self.consumed.load(Ordering::Acquire);
            let next = current.saturating_add(bytes);
            if next > self.slot_limit {
                return Err(EntryBytesReserveError::ExceedsSlotLimit);
            }

            if self
                .consumed
                .compare_exchange(current, next, Ordering::AcqRel, Ordering::Acquire)
                .is_ok()
            {
                return Ok(());
            }
        }
    }
