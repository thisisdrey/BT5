### Title
Time-of-check-to-time-of-use race in JSON-RPC filter maps causes NullPointerException / crash reachable by any anonymous JSON-RPC client - (File: framework/src/main/java/org/tron/core/services/jsonrpc/TronJsonRpcImpl.java)

### Summary
`TronJsonRpcImpl.getFilterResult()` and `uninstallFilter()` use a check-then-act pattern (`containsKey()` followed by a separate `get()`/`remove()`) on the shared `ConcurrentHashMap` instances that back `eth_newFilter`/`eth_newBlockFilter`/`eth_getFilterChanges`/`eth_uninstallFilter`. These same maps are concurrently mutated by the block-application and log-dispatch paths (`handleBLockFilter`, `handleLogsFilter` → `processLogFilterEntry`), which remove entries the instant a filter is found to be expired. Because the check and the use are not atomic, an unauthenticated JSON-RPC client can observe a filter entry with `containsKey()` and then have it evaporate (due to expiry-driven removal from the block/log processing thread) before the subsequent `get(filterId)` call, producing a stale/`null` reference that is immediately dereferenced.

### Finding Description

``` [1](#0-0) 

Both `blockFilter2ResultFull`/`Solidity` and `eventFilter2ResultFull`/`Solidity` are plain `ConcurrentHashMap`s exposed via getters, with no external synchronization between readers and the background eviction path. [2](#0-1) 

Concurrently, `handleBLockFilter` iterates the same map and calls `it.remove()` on expired entries while a new block is applied:
```java
if (entry.getValue().isExpire()) {
  it.remove();
  continue;
}
``` [3](#0-2) 

Similarly, `processLogFilterEntry` removes expired log filters:
```java
if (logFilterAndResult.isExpire()) {
  eventFilterMap.remove(entry.getKey());
  return;
}
``` [4](#0-3) 

If a client's `eth_getFilterChanges` call (`getFilterChanges` → `getFilterResult`) executes `containsKey(filterId)` returning `true` right as the filter transitions to expired and is removed by the block/log processing thread that runs on every applied block (Manager block application triggers `handleBLockFilter`/`handleLogsFilter` from the production path), the subsequent `get(filterId)` returns `null`, and `.popAll()`/`.updateExpireTime()` throws a `NullPointerException`. This is the same bug class as the Samba CVE: a value is freed/removed by one path while another path still holds and dereferences a now-invalid reference obtained under a prior existence check — a classic TOCTOU/use-after-free pattern, here manifesting as a null dereference rather than memory corruption because Java is memory-safe, but the race and crash-triggering effect are structurally identical.

`uninstallFilter` has the identical hazard:
```java
if (eventFilter2Result.containsKey(filterId)) {
  eventFilter2Result.remove(filterId);
} else if (blockFilter2Result.containsKey(filterId)) {
  blockFilter2Result.remove(filterId);
}
``` [5](#0-4) 
While `remove()` on a missing key is a no-op (so this particular call is not itself crash-prone), it demonstrates the pervasive check-then-act idiom used across this filter subsystem instead of atomic `compute`/`remove(key,expected)` operations.

### Impact Explanation
Any anonymous JSON-RPC client can create a filter via `eth_newFilter`/`eth_newBlockFilter` (no authentication required on the JSON-RPC endpoint) and then poll it via `eth_getFilterChanges` near its 5-minute expiry window (`EXPIRE_SECONDS = 5 * 60`, `TronJsonRpcImpl.java:125`). Because block production and log dispatch run continuously and independently evict expired filters from the same map the RPC handler reads, a client-triggerable race causes an unhandled `NullPointerException` inside the request-handling thread. Depending on how `JsonRpcServlet` surfaces uncaught runtime exceptions, this can result in a malformed/broken response for that request, and if triggered repeatedly across concurrently-served RPC threads, it degrades or disrupts the node's ability to serve the JSON-RPC filter API — matching the "API the node can no longer serve" impact category. It does not require any special privilege, matches "unprivileged... anonymous API client" reachability, and is a Medium-severity denial-of-service-style defect analogous to the Samba LDAP use-after-free's crash impact.

### Likelihood Explanation
The race window is narrow but deterministically reachable: block production happens roughly every 3 seconds and triggers filter-expiry sweeps on every produced block, so any long-lived filter near its expiry timestamp has a reliably recurring window in which `containsKey` and `get` can straddle a concurrent `remove`. An attacker fully controls both ends of the race (creates the filter, chooses when to poll it, and can spray many `eth_getFilterChanges` calls right around the 300-second expiry mark, or simply lets many filters expire while flooding `getFilterChanges` calls) making exploitation practical without any special network position or privilege — only public JSON-RPC access is required.

### Recommendation
Replace the check-then-act patterns in `getFilterResult` and `uninstallFilter` with atomic map operations, e.g. `Map.remove(key)` capturing the removed value in one call, or `Map.compute`/`computeIfPresent` so retrieval and mutation happen atomically with respect to the concurrent eviction sweeps in `handleBLockFilter`/`processLogFilterEntry`. For example:
```java
BlockFilterAndResult bf = blockFilter2Result.get(filterId);
if (bf != null) {
  List<String> blockHashList = bf.popAll();
  bf.updateExpireTime();
} else {
  LogFilterAndResult lf = eventFilter2Result.get(filterId);
  if (lf != null) { ... } else { throw new ItemNotFoundException(FILTER_NOT_FOUND); }
}
```
This eliminates the window where the key can vanish between a positive `containsKey` and the paired `get()`.

### Proof of Concept
1. Call `eth_newBlockFilter` (or `eth_newFilter`) to obtain a `filterId`; do not poll it for close to `EXPIRE_SECONDS` (300s) so it becomes eligible for expiry-driven removal on the next `handleBLockFilter`/`handleLogsFilter` sweep triggered by ordinary block production.
2. In a tight loop, repeatedly invoke `eth_getFilterChanges(filterId)` right around the expiry boundary while blocks continue to be produced/applied on the node (this happens automatically every ~3s in normal chain operation).
3. On the iteration where `containsKey(filterId)` in `getFilterResult` returns `true` but the concurrent block-application thread's `it.remove()` (in `handleBLockFilter`) or `eventFilterMap.remove()` (in `processLogFilterEntry`) executes before the following `blockFilter2Result.get(filterId)`/`eventFilter2Result.get(filterId)` call, `get()` returns `null` and the subsequent `.popAll()`/`.updateExpireTime()` call throws `NullPointerException`, demonstrating the crash-triggering race, unauthenticated and reachable purely through the public JSON-RPC filter API.
