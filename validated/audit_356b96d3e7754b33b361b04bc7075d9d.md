### Title
Maximal-size `DeployGlobalContractAction` deterministically produces an oversized `GlobalContractDistributionReceipt` that fails `validate_receipt`'s `ReceiptSizeExceeded` check, burning the deployer's storage fee with no contract deployed - (File: runtime/runtime/src/global_contracts.rs)

### Summary
`validate_deploy_global_contract_action` admits `code.len()` up to and including `max_contract_size` (4,194,304 bytes), but `initiate_distribution` wraps that same code plus framing (identifier, shard id, nonce, empty `already_delivered_shards`, and outer `Receipt`/`ReceiptEnum` fields) into a `GlobalContractDistributionReceipt`, whose borsh size is checked against the identical bound `max_receipt_size` (4,194,304) in `validate_receipt`. Because the receipt necessarily contains more bytes than the raw code, every maximal-size deploy produces a receipt that exceeds `max_receipt_size` and is rejected, while `action_deploy_global_contract` has already burned the account's storage fee before that rejection is observed.

### Finding Description
`validate_deploy_global_contract_action` in `runtime/runtime/src/action_validation.rs` only checks `action.code.len() as u64 > limit_config.max_contract_size`, admitting `code.len() == max_contract_size` exactly: [1](#0-0) 

When such a transaction is applied, `action_deploy_global_contract` first debits `storage_cost` from the account (burning tokens) and only then calls `initiate_distribution`: [2](#0-1) 

`initiate_distribution` builds a `GlobalContractDistributionReceipt` (identifier + `target_shard` + empty `already_delivered_shards` + `code` + `nonce`) and wraps it into a full `Receipt` via `Receipt::new_global_contract_distribution`, pushing it to `result.new_receipts`: [3](#0-2) 

The receipt structure adds framing overhead beyond the raw code bytes - the `GlobalContractDistributionReceipt` V1/V2 enum discriminant, the `GlobalContractIdentifier` enum (code hash or account id), `target_shard` (`ShardId`), the length-prefixed (empty) `already_delivered_shards` vector, the `nonce` (`u64`), plus the outer `ReceiptEnum` discriminant and the enclosing `Receipt::V0` fields (`predecessor_id`, `receiver_id = "system"`, `receipt_id`): [4](#0-3) [5](#0-4) 

`validate_receipt`, run in `ValidateReceiptMode::NewReceipt` on freshly produced receipts, computes `borsh::object_length(receipt)` for the **entire** wrapped receipt and compares it to `limit_config.max_receipt_size` - the same numeric bound (4,194,304) used to admit the code in the first place, with no accounting for the extra framing: [6](#0-5) 

Since `GlobalContractDistribution` receipts fall through to `Ok(())` in the per-type match (no additional exemption at the top-level size gate), the size check at lines 533-542 still applies to them: [7](#0-6) 

An analogous, already-acknowledged pattern exists for yield receipts, where a value exactly at the code/args limit produces a receipt that is measurably larger than `max_receipt_size` and is rejected with `ReceiptSizeExceeded` (overhead of 200 bytes observed for the yield/args case), confirming the framing-overhead mechanism is real and previously encountered in this codebase: [8](#0-7) 

For the global-contract-distribution case, the minimum overhead (V1/V2 discriminant, id discriminant + 32-byte code hash, 8-byte `ShardId`, 4-byte empty-vec length, 4-byte code length prefix, 8-byte `nonce`, plus outer `ReceiptEnum` discriminant and `Receipt::V0`'s `predecessor_id`/`receiver_id`/`receipt_id`) is well over 50 bytes - enough to push a `code.len() == max_contract_size` deploy's receipt past `max_receipt_size` deterministically, on every single maximal deploy.

### Impact Explanation
Every unprivileged account that submits a `DeployGlobalContractAction` with `code.len()` at the officially-permitted maximum (4,194,304 bytes, which `validate_deploy_global_contract_action` explicitly allows) will have `action_deploy_global_contract` debit `storage_cost` from its balance (a real token burn recorded via `result.tokens_burnt`) before the newly produced `GlobalContractDistributionReceipt` fails `validate_receipt`'s size check. This is a metering-totality violation: the admission check and the downstream size guard disagree on the same nominal bound. Scoped impact is inconsistent size-limit enforcement causing action rejection for every maximal-size global contract deploy; because the storage-fee debit occurs as an in-place mutation on the account object inside the action function prior to the receipt-validation failure being surfaced, this raises a concrete risk of the storage fee being burned with no contract successfully deployed and no compensating refund, i.e., loss of user funds for legitimate use of the documented interface boundary.

### Likelihood Explanation
Fully reachable by an ordinary funded account with no special privileges: sign and submit a single `DeployGlobalContractAction` with `code = vec![0u8; 4_194_304]` via `SignedTransaction::deploy_global_contract`. This requires only sufficient balance to cover the storage cost of a 4 MiB global contract and normal gas/nonce/signature handling, all of which are already satisfied by a standard client. The bug is deterministic and 100% repeatable for any maximal-size deploy attempt (not probabilistic or resource-dependent).

### Recommendation
Reserve headroom in `validate_deploy_global_contract_action` (and/or in the global-contract-specific size check) so that `code.len()` is bounded well below `max_receipt_size` minus the fixed `GlobalContractDistributionReceipt`/`Receipt` framing overhead, or introduce a dedicated `max_global_contract_code_size` distinct from `max_receipt_size` that accounts for the wrapping. Additionally, ensure `action_deploy_global_contract` does not commit the storage-fee burn until after the produced distribution receipt has passed `validate_receipt`, so a downstream size-validation failure cannot silently burn user funds.

### Proof of Concept
Unit test in `runtime/runtime/src/global_contracts.rs` or `runtime/runtime/src/verifier.rs`:
1. Construct `code = Arc::from(vec![0u8; max_contract_size])` (`max_contract_size = 4_194_304`).
2. Call `GlobalContractDistributionReceipt::new(GlobalContractIdentifier::CodeHash(hash(&code)), current_shard_id, vec![], code.clone(), nonce)` and wrap with `Receipt::new_global_contract_distribution(account_id, receipt)`.
3. Assert `borsh::object_length(&receipt).unwrap() > limit_config.max_receipt_size`, demonstrating the receipt exceeds the same bound that admitted the code.
4. As an integration-level PoC (mirroring `test-loop-tests/src/tests/max_receipt_size.rs`), submit `SignedTransaction::deploy_global_contract` with `code = vec![0u8; 4_194_304]` from a funded account with no prior deploy, run it through the test loop, and assert the resulting `FinalExecutionStatus::Failure` carries `ActionErrorKind::NewReceiptValidationError(ReceiptValidationError::ReceiptSizeExceeded { .. })`, then inspect the account balance to confirm the storage fee for the failed deploy was not refunded.

/// Validates `DeployGlobalContractAction`. Checks that the given contract size doesn't exceed the limit.
fn validate_deploy_global_contract_action(
    limit_config: &LimitConfig,
    action: &DeployGlobalContractAction,
) -> Result<(), ActionsValidationError> {
    if action.code.len() as u64 > limit_config.max_contract_size {
        return Err(ActionsValidationError::ContractSizeExceeded {
            size: action.code.len() as u64,
            limit: limit_config.max_contract_size,
        });
    }

    Ok(())
}

pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
}

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}

/// Validates a given receipt. Checks validity of the Action or Data receipt.
pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }
