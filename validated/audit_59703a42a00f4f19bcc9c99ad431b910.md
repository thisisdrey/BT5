## Finding: JupLend deposit can accept user funds while minting zero marginfi shares due to floor-division precision loss

### Title
Tiny JupLend deposits can consume user underlying tokens while crediting zero marginfi asset shares - ([File: programs/marginfi/src/instructions/juplend/deposit.rs])

### Summary
The `juplend_deposit()` instruction computes expected shares using a floor-division formula that can round down to `0` for small deposit amounts whenever the JupLend `liquidity_exchange_price`/`token_exchange_price` deviate from `1e12`. Because the user's underlying tokens are transferred into the vault and CPI'd into JupLend *before* the shares check, and because the on-chain check only verifies that CPI-minted fTokens equal the (also zero) expected value, the transaction can succeed while crediting the depositor `0` marginfi asset shares — the same "deposit accepted, shares minted = 0" failure mode described in the GlmManager report.

### Finding Description
`juplend_deposit()` in [1](#0-0)  computes `expected_shares` via `expected_shares_for_deposit_from_rates`, which performs a two-step floor division:

```
raw    = floor(assets * 1e12 / liquidity_exchange_price)
norm   = floor(raw * liquidity_exchange_price / 1e12)
shares = floor(norm * 1e12 / token_exchange_price)
```

This is documented and tested to floor to zero for small amounts whenever `liquidity_exchange_price != 1e12` [2](#0-1) . The unit test `shares_for_deposit_tiny_amount_can_floor_to_zero` explicitly demonstrates this: an `amount` of `1` with `liquidity_exchange_price = 1.1e12` yields `shares = 0` [3](#0-2) . The same zero-mint edge case is reproduced again for `amount = 1` in `local_tests.rs` (`shares_for_deposit_matches_computed_values`, `round_trip_near_zero_amounts`) [4](#0-3) [5](#0-4) .

Critically, the instruction transfers the user's underlying tokens to the bank liquidity vault and issues the CPI deposit into JupLend *before* verifying the minted-share amount:

```
ctx.accounts.cpi_transfer_user_to_liquidity_vault(amount)?;
ctx.accounts.cpi_juplend_deposit(amount, authority_bump)?;
...
require_eq!(minted_shares, expected_shares, MarginfiError::JuplendDepositFailed);
``` [6](#0-5) 

When `expected_shares == 0` and the real JupLend CPI mirrors the same floor-division math (mints `0` fTokens for the tiny deposit), `minted_shares == expected_shares == 0`, so the `require_eq!` guard is satisfied and the transaction does **not** revert. The code then proceeds to credit the user's marginfi balance with `bank_account.deposit_no_repay(I80F48::from_num(minted_shares))` where `minted_shares = 0` [7](#0-6) . This is functionally identical to the GlmManager root cause: real user funds move into the underlying protocol, but the truncating conversion formula returns zero, so zero shares are minted for the depositor.

The project's own fuzz-invariant suite acknowledges this "zero-amount success" case is expected behavior for a legitimate zero-value deposit, only permitting it to open an *empty* balance slot with zero shares [8](#0-7)  — but this invariant does not distinguish between an intentional `amount = 0` call and a *non-zero* `amount` that happens to floor to zero shares due to the pricing precision loss. There is no minimum-deposit-amount check in `juplend_deposit()` analogous to the recommended fix in the original report.

### Impact Explanation
A user who deposits a sufficiently small JupLend-position amount (relative to the pool's current `liquidity_exchange_price`/`token_exchange_price`) transfers real, non-zero underlying tokens out of their wallet into the bank's liquidity vault and then into the JupLend pool via CPI, but receives `0` marginfi asset shares in return. Because they hold no corresponding shares, they have no way to withdraw or reclaim the deposited value through the marginfi account — a direct, permanent loss of user funds analogous to the reported GM-token issue (deposit accepted, zero shares minted, funds effectively stuck/lost).

### Likelihood Explanation
Likelihood is moderate: it requires the JupLend pool's exchange prices to have drifted away from the `1e12` baseline (which happens naturally over time as it accrues interest/rewards) combined with the user depositing a small enough raw amount. The repo's own rounding-loop test suite (`jlr11_rounding_loop.spec.ts`) actively searches for and exercises amounts that produce nonzero-but-lossy conversions [9](#0-8) , confirming these conditions are reachable in practice, though existing tests focus on the "loss per cycle" case rather than the "zero shares minted" edge exactly at `expected_shares == 0`.

### Recommendation
Add an explicit check in `juplend_deposit()` (and any other JupLend-based deposit flow using `expected_shares_for_deposit_from_rates`) to reject deposits where the computed `expected_shares == 0`, before any token transfer or CPI occurs — mirroring the recommended fix in the original report (reject dust deposits that would truncate to zero output).

### Proof of Concept
1. Wait until (or engineer, via test harness) the JupLend pool's `liquidity_exchange_price` diverges from `1e12` (e.g., `1.1e12`, as shown in the repo's own test fixtures).
2. Call `juplend_deposit(amount = 1)` (or any amount small enough that `floor(amount * 1e12 / liquidity_exchange_price) == 0`).
3. `expected_shares_for_deposit_from_rates` returns `Some(0)` per the tested behavior at [3](#0-2) .
4. `cpi_transfer_user_to_liquidity_vault(1)` moves 1 unit of underlying from the user to the bank vault; `cpi_juplend_deposit(1, ...)` deposits it into JupLend, minting `0` fTokens (matching the mock/expected math).
5. `require_eq!(minted_shares, expected_shares)` passes (`0 == 0`), so the instruction succeeds.
6. `bank_account.deposit_no_repay(I80F48::from_num(0))` credits the user with `0` asset shares while their token left their wallet — funds are gone with no corresponding claim in the marginfi account.

const findFirstPositiveLossAmount = (
  tokenExchangePrice: bigint,
  liquidityExchangePrice: bigint,
): RoundingProbe | null => {
  for (
    let amount = MIN_LOOP_DEPOSIT;
    amount <= SEARCH_MAX_AMOUNT;
    amount += SEARCH_STEP
  ) {
    const shares = previewSharesForDeposit(
      amount,
      liquidityExchangePrice,
      tokenExchangePrice,
    );
    if (shares < MIN_LOOP_SHARES) continue;

    const redeem = previewAssetsForRedeem(shares, tokenExchangePrice);
    const loss = amount - redeem;

    if (loss > 0n) {
      return { amount, shares, redeem, loss };
    }
  }

  return null;
};
