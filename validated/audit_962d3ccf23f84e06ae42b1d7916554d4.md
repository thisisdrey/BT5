### Title
Repository write-lock TTL shorter than actual PREPARING→PREPARED transit time allows lock theft and reintroduction of the cross-node ref-locking deadlock/race that serialization was designed to prevent - (File: internal/praefect/datastore/lock_manager.go)

### Summary
Praefect's serialized-writes feature is meant to guarantee that only one transaction per repository can be in the "on-disk ref lock has been taken" window at a time, preventing the cross-node deadlock described in `doc/serialized_writes.md`. The guarantee is enforced entirely by a Postgres-backed lock whose expiry (`renewInterval`, hard-coded to 20 seconds) is renewed only when the transaction reaches `PREPARED_PHASE`/`COMMITTED_PHASE`. If the time between the `PREPARING_PHASE` vote (lock acquired) and the `PREPARED_PHASE` vote (lock renewed) exceeds 20 seconds — which is fully influenceable by an ordinary client via the size/cost of the push being processed by Git on each node — the lock expires and can be atomically "stolen" by a second, unrelated transaction while the first transaction is still mid-flight. This is precisely the state serialization was introduced to prevent.

### Finding Description
The write-lock protocol is:
1. `PREPARING_PHASE`: `WriteLockManager.Lock` acquires a Postgres row with `expired_at = NOW() + renewInterval` (20s). [1](#0-0) 
2. Between this vote and the next, each Gitaly node actually performs the expensive part: it "locks refs on disk" and starts writing the update — this is Git driving the `reference-transaction` hook through Git's own internals, whose duration scales with the size/complexity of the push (number of refs, quorum round-trip across all replica nodes, disk I/O, etc.). [2](#0-1) 
3. Only when `PREPARED_PHASE` arrives does Praefect call `lock.Renew(ctx)` to extend the lease. [3](#0-2) 

The Postgres `tryLock` UPSERT used for lock acquisition explicitly allows takeover once `expired_at < NOW()`, regardless of whether the original holder is still alive and progressing: [4](#0-3) 

There is no mechanism that ties the 20-second TTL to the actual worst-case duration of the PREPARING→PREPARED interval. A large or deliberately expensive push (many ref updates, slow object writes, or a slow/contended secondary delaying quorum on the `preparing` vote) can make this interval exceed 20 seconds. Once it does, the row is deleted/overwritten by the background sweep or by a second transaction's own `tryLock`, and that second transaction is granted the lock and allowed to proceed to lock refs on disk for the *same repository* while the first transaction is still holding its now-orphaned on-disk locks and has not yet voted `PREPARED`/`COMMITTED`. This reconstitutes exactly the two-transactions-holding-overlapping-on-disk-locks scenario that serialized writes exists to eliminate: [5](#0-4) 

This is directly analogous to the reported bug class: a fixed, attacker-influenceable "lockup"/TTL window (`decreaseStakeLockupDuration`-equivalent = `renewInterval`) that is not guaranteed to exceed the duration of the protective multi-step process (`votingPeriod`-equivalent = the PREPARING quorum + on-disk locking time), allowing an ordinary actor to slip past the safety mechanism by making their own operation slow enough to outlast the guard.

### Impact Explanation
If exploited, two transactions can simultaneously hold conflicting on-disk ref locks for the same repository across the Gitaly node set, defeating the entire purpose of Praefect's serialized-writes feature. Per the project's own design document, this is the exact condition that causes the cluster-wide ref-locking deadlock the feature was introduced to fix, and/or non-deterministic interleaving of concurrent ref updates to the same repository, risking ref/data corruption or stuck transactions that never reach quorum. This is a correctness/availability issue reachable purely from ordinary client pushes.

### Likelihood Explanation
Reaching the vulnerable window does not require any privileged access — it only requires an ordinary user to submit a push whose per-node processing time (many ref updates, large object writes, or a temporarily slow/contended replica) exceeds the fixed 20-second `renewInterval` before the node manages to vote `PREPARED`. This is plausible under normal operational conditions (large monorepo pushes, disk contention, GC/housekeeping load) and can be reliably forced by a moderately sized push, without any exotic timing exploit.

### Recommendation
Do not rely on a small, fixed TTL as the sole correctness guarantee for lock possession across the PREPARING→PREPARED window. Options:
- Renew the lock (or extend its TTL) as soon as the `PREPARING_PHASE` vote is cast and periodically while waiting for `PREPARED`, rather than only at `PREPARED_PHASE`.
- Make `renewInterval` large enough to comfortably exceed the worst observed/configured PREPARING→PREPARED latency (analogous to making `decreaseStakeLockupDuration` >> `votingPeriod`), and/or make it configurable based on deployment characteristics (push size limits, node count, quorum size).
- Alternatively, tie lock validity to liveness (e.g., a heartbeat from the actively-processing node) instead of a flat wall-clock deadline set at acquisition time, so that a stalled-but-alive transaction cannot lose its lock to a takeover while a stuck/crashed transaction still expires promptly.

### Proof of Concept
1. Enable `featureflag.PraefectSerializedWrite`.
2. Client A issues a push to repository R that is engineered to take Git's on-disk ref-locking/writing phase (`PREPARING_PHASE` cast → local ref lock + write → `PREPARED_PHASE` vote) more than 20 seconds — e.g. a push touching thousands of refs or hitting slow storage/replica quorum.
3. At t=0s, node casts `PREPARING_PHASE`; Praefect's `tryLock` acquires the row with `expired_at = now+20s` (per `RepoReferenceWriteLockManager` semantics, see `internal/praefect/datastore/lock_manager.go` and description in `doc/serialized_writes.md` lines 181-196).
4. Around t=21s, before A's node reaches `PREPARED_PHASE` (which would call `renew`), the background sweep/or a second client's `tryLock` observes `expired_at < NOW()` and takes over the lock row for a completely different transaction B on the same repository (see the UPSERT semantics documented at `doc/serialized_writes.md` lines 198-221, and the analogous test pattern in `internal/praefect/transaction_write_serialization_test.go` `TestPraefectWriteSerialization_HangAfterPrepared`, which demonstrates a second transaction successfully "stealing" the expired lock via `PREPARING_PHASE` while the first transaction has not released it).
5. Transaction B now proceeds to lock refs on disk for repository R concurrently with transaction A, which is still mid-flight holding its own on-disk locks — the exact deadlock/race precondition documented in `doc/serialized_writes.md` lines 22-31 that serialized writes was designed to prevent. [6](#0-5)

The problem is that at the `prepared` phase, **on-disk ref locks have already

refs A and B:

1. Node 1: T1 locks A, T2 locks B

### Flow for one write

1. Client calls a write RPC against Praefect.
1. Praefect forwards the RPC to each Gitaly node in the replica set.
1. Each Gitaly node, in `UpdateReference` (or the equivalent write path),
   casts a `Preparing` vote **before** locking refs locally. The hook RPC
   reaches Praefect, which calls `lockRepoForTransaction(PREPARING_PHASE)`:
   `WriteLockManager.Lock` blocks until the per-repository lock is free.
1. Both nodes return from `Preparing` together (quorum reached).
1. Each Gitaly node locks refs on disk and votes `Prepared`. Praefect renews
   the lock.
1. Each Gitaly node writes the update and votes `Committed`. Praefect releases
   the lock.
```

```sql
INSERT INTO repository_reference_write_locks as locks (lock_id, holder_txn_id, expired_at)
VALUES ($1, $2, NOW() + $3::interval)
ON CONFLICT (lock_id) DO UPDATE
    SET holder_txn_id = EXCLUDED.holder_txn_id,
        expired_at    = EXCLUDED.expired_at
WHERE locks.expired_at < NOW() OR locks.holder_txn_id = $2
RETURNING lock_id, holder_txn_id, expired_at;
```

The `WHERE` clause is the **expiry guard**. Four outcomes:

| Existing row state                          | UPSERT result | Caller observes |
|---------------------------------------------|--------------|-----------------|
| No row                                      | INSERT, returns row | `Acquired`     |
| Held by same `txnID` (re-entry)              | UPDATE, returns row | `Acquired` (idempotent) |
| Held by different `txnID`, **expired**        | UPDATE, returns row | `Acquired` (lock stolen) |
| Held by different `txnID`, **not expired**    | No-op, returns no row | `Acquired=false` → wait |
```

func TestPraefectWriteSerialization_HangAfterPrepared(t *testing.T) {
	t.Parallel()
	db := testdb.New(t)
	ctx := testhelper.Context(t)
	logger := testhelper.SharedLogger(t)
	repoWriteLockMgr := datastore.NewRepoReferenceWriteLockManager(ctx, db, testdb.GetConfig(t, db.Name), logger)

	storageName := "mock"
	relativePath := "hang/after/prepared.git"
	voters := []transactions.Voter{{Name: "primary", Votes: 1}}
	threshold := uint(1)

	cc, txMgr, cleanup := runPraefectServerAndTxMgrAndLockMgr(t, ctx, repoWriteLockMgr)
	defer cleanup()
	client := gitalypb.NewRefTransactionClient(cc)

	// Txn1: PREPARING + PREPARED, then "hang" (no COMMITTED)
	txn1, _, err := txMgr.RegisterTransaction(ctx, voters, threshold)
	require.NoError(t, err)
	hash1 := sha1.Sum([]byte("txn1"))

	for _, phase := range []gitalypb.VoteTransactionRequest_Phase{
		gitalypb.VoteTransactionRequest_PREPARING_PHASE,
		gitalypb.VoteTransactionRequest_PREPARED_PHASE,
	} {
		_, err := client.VoteTransaction(ctx, &gitalypb.VoteTransactionRequest{
			TransactionId:        txn1.ID(),
			Repository:           &gitalypb.Repository{StorageName: storageName, RelativePath: relativePath},
			Node:                 voters[0].Name,
			ReferenceUpdatesHash: hash1[:],
			Phase:                phase,
		})
		require.NoError(t, err)
	}
	// Intentionally skip COMMITTED phase to simulate a stuck client.

	// Simulate lock expiry by back-dating the row
	_, err = db.ExecContext(ctx, `
          UPDATE repository_reference_write_locks
          SET expired_at = NOW() - INTERVAL '1 second'
          WHERE lock_id = $1`, storageName+"|"+relativePath)
	require.NoError(t, err)

	// Txn2: PREPARING should succeed (steals the expired lock)
	txn2, cancel2, err := txMgr.RegisterTransaction(ctx, voters, threshold)
	require.NoError(t, err)
	defer func() { require.NoError(t, cancel2()) }()
	hash2 := sha1.Sum([]byte("txn2"))

	_, err = client.VoteTransaction(ctx, &gitalypb.VoteTransactionRequest{
		TransactionId:        txn2.ID(),
		Repository:           &gitalypb.Repository{StorageName: storageName, RelativePath: relativePath},
		Node:                 voters[0].Name,
		ReferenceUpdatesHash: hash2[:],
		Phase:                gitalypb.VoteTransactionRequest_PREPARING_PHASE,
	})
	require.NoError(t, err)
}
