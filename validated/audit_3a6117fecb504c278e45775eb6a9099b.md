### Title
Attacker-controlled inventory bits with no matching sortition winner corrupt `TenureStartEnd::from_inventory` start/end mapping - ([File: stackslib/src/net/download/nakamoto/tenure.rs])

### Summary
`TenureStartEnd::from_inventory` (and the peer-driven `find_tenure_block_ids`/`find_available_tenures` pipeline that feeds it) trusts a remote peer's `NakamotoTenureInv` bitvector bit-by-bit to select which `WantedTenure` entry supplies the "start block" and "end block" `StacksBlockId` for a given tenure `ConsensusHash`, without validating that the referenced `WantedTenure.winning_block_id` is non-zero (i.e., that the sortition at that bit index actually had a winner). A malicious peer can set a bit for a sortition slot whose true `winning_block_id` is `StacksBlockId([0x00;32])` (no winner), causing `from_inventory` to select that zero block id as `start_block_id`/`end_block_id` for a legitimately requested, real tenure.

### Finding Description
In `TenureStartEnd::from_inventory` (`stackslib/src/net/download/nakamoto/tenure.rs:129-328`), the outer loop iterates `wanted_tenures`, and for index `i` checks only `invbits.get(bit)` from the peer-supplied `NakamotoTenureInv` to decide whether tenure `i` is "present." It then searches forward for the next index `j` (`wt_start_idx`) and the index after that (`wt_end_index`) purely by `invbits.get(bit)`, and uses `wanted_tenures[wt_start_idx].winning_block_id` / `wanted_tenures[wt_end_index].winning_block_id` directly as `start_block_id`/`end_block_id` [1](#0-0) . Nowhere in this scan is `wt_start.winning_block_id` or `wt_end.winning_block_id` checked against `StacksBlockId([0x00;32])`.

This is in contrast to the sibling function `find_available_tenures`, which explicitly guards against this: `if ibh == &StacksBlockId([0x00; 32]) { continue; }` before ever recording a neighbor as serving that tenure [2](#0-1) . That guard, however, only protects the "which CH has any serving neighbor" map (`available`); it does not protect the `start_block_id`/`end_block_id` chosen inside `TenureStartEnd::from_inventory`, which is a separate structure (`tenure_block_ids` / `AvailableTenures`) built by `find_tenure_block_ids` [3](#0-2) .

An attacker peer answering `GetNakamotoInv` can therefore send a `NakamotoInv` where an honest, real tenure bit `i` is set (as any honest peer would), but where a *following* bit `j` (used by the scan as `wt_start_idx`) is also set true even though `wanted_tenures[j].winning_block_id == StacksBlockId([0x00;32])` (a missed/no-winner sortition slot). Because the scan only checks the bit, not the winner, it will build `TenureStartEnd { tenure_id_consensus_hash: CH_i, start_block_id: StacksBlockId([0;32]), ... }` for the real tenure `CH_i`, instead of the correct next real tenure's `winning_block_id`.

### Impact Explanation
`make_tenure_downloaders` looks up the neighbor-supplied `AvailableTenures` (`tenure_block_ids.get(&naddr)`) to get `tenure_info` for the scheduled `ch`, and directly forwards `tenure_info.start_block_id` into `NakamotoTenureDownloader::new` as `tenure_start_block_id` [4](#0-3) . However, whether this corruption is actually exploitable to "stage the wrong tenure" depends on `try_accept_tenure_start_block`'s handling of a zeroed `tenure_start_block_id` (i.e., whether it matches against `block.header.block_id()` collision, panics, or is rejected outright as an invalid/degenerate ID) — I was not able to retrieve `stackslib/src/net/download/nakamoto/tenure_downloader.rs` (the tool call to read it failed due to a missing parameter, and no further iterations were available). Without confirming that code path, I cannot state definitively whether this results in a stored/served wrong block (High severity) or is instead caught (e.g., downloader errors out on an all-zero expected block id, or a genuine collision with the real all-zero StacksBlockId is cryptographically infeasible since it would require a peer to actually produce a block whose `index_block_hash()` is all-zero, which is not achievable for a real block).

Given the missing verification of `try_accept_tenure_start_block`'s behavior on this input, I can confirm the corrupted `AvailableTenures` mapping (a real, reachable fault in `from_inventory`/`find_tenure_block_ids`) but cannot confirm the full "mis-slotted tenure fetch causing wrong block staged" chain end-to-end as required by the question's proof idea.

### Likelihood Explanation
Reachable via any attacker-run peer that legitimately answers `GetNakamotoInv` requests during a normal IBD/reward-cycle sync — no privileged role or secret is required, and the attacker only needs to control the bits of their own advertised inventory. This part of the finding is low-cost and repeatable per reward cycle sync attempt.

### Recommendation
In `TenureStartEnd::from_inventory`, when scanning for `wt_start_idx`/`wt_end_index` (and their `next_wanted_tenures` counterparts), additionally require that the candidate `WantedTenure.winning_block_id != StacksBlockId([0x00;32])`, mirroring the guard already present in `find_available_tenures`. Also validate `wt.winning_block_id` for the outer-loop tenure `i` itself before treating a peer's bit as trustworthy.

### Proof of Concept
Given the incomplete verification of the downstream `try_accept_tenure_start_block` behavior, I cannot provide a fully validated end-to-end PoC. The partial PoC for the confirmed root-cause fault (`from_inventory` mis-mapping) would be:

        let mut tenure_block_ids = HashMap::new();
        while let Some((naddr, tenure_inv)) = inventory_iter.next() {

                wanted_tenures,
                next_wanted_tenures,
                pox_constants,
                first_burn_height,
                tenure_inv,
            ) else {
                // this peer doesn't know about this reward cycle
                continue;
            };
