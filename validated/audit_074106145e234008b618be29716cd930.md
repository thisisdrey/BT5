### Title
`x-gitaly-cost` trailer undercounts bulk data transferred over sidechannel RPCs, letting large clones/fetches evade upstream complexity-based rate limiting - (File: `internal/grpc/middleware/costhandler/costhandler.go`)

### Summary
The `costhandler` package computes a per-RPC `x-gitaly-cost` gRPC trailer that Rails/Workhorse forward as the `X-Score` header to drive Cloudflare's complexity-based rate limiting [1](#0-0) . The score is `static + dynamic`, where the dynamic portion is derived from gRPC payload byte counts collected by the `grpcstats.PayloadBytes` stats handler [2](#0-1) [3](#0-2) . However, for sidechannel RPCs such as `PostUploadPackWithSidechannel` and `SSHUploadPackWithSidechannel` — which are used precisely because they transfer "a high volume of byte stream data" outside the gRPC/Protobuf channel [4](#0-3)  — the bulk pack data never passes through the gRPC stream that `grpcstats.PayloadBytes` instruments; only small control messages do. `HandleRPC` only increments `InPayloadBytes`/`OutPayloadBytes` on `stats.InPayload`/`stats.OutPayload` events from the gRPC transport [5](#0-4) , so `dynamicCostFromContext` always resolves to near-zero for these RPCs regardless of the actual pack size served.

### Finding Description
`PostUploadPackWithSidechannel` and `SSHUploadPackWithSidechannel` open a separate Yamux stream and stream the packfile over it directly, bypassing gRPC message framing entirely for performance reasons [6](#0-5) . The actual bytes served to the client are tracked separately via a `CountingWriter` wrapped around the sidechannel connection and only recorded into a dedicated Prometheus metric (`uploadPackServedBytesMetrics`), not into the gRPC `stats.OutPayload` events that `grpcstats.PayloadBytes` consumes [7](#0-6) .

Because `costhandler.dynamicCostFromContext` only reads `grpcstats.PayloadBytesStatsFromContext`, it never sees the sidechannel-transferred bytes [3](#0-2) . The static override table hardcodes a fixed weight of `10` for these RPCs specifically because they are large data transfers [8](#0-7) , but this static weight is the same whether the clone serves 1 MB or 100 GB — the doc itself acknowledges "A static score hides variance (e.g. `PostUploadPackWithSidechannel` is the same cost whether it serves 1 MB or 10 GB)" and states the dynamic component is intended to reconcile this [9](#0-8) . That reconciliation never actually happens for the sidechannel path because the dynamic byte counter is blind to sidechannel traffic. This is directly analogous to the ZetaChain report's flaw: a value used to compute an outward-facing cost/fee signal (there: gas limit driving fee; here: `x-gitaly-cost` driving rate-limit budget) fails to reflect the actual resource consumed, letting an ordinary user's request appear far cheaper than it truly is.

### Impact Explanation
Any unprivileged client performing a `git clone`/`git fetch` over HTTP or SSH — the two primary, unprivileged, high-volume code paths in Gitaly — will have their RPC under-reported at a fixed cost of 10 regardless of repository/pack size, because the dynamic byte-based cost addition is structurally incapable of seeing sidechannel-transferred bytes. This directly undermines the "cost-aware admission"/complexity-based rate-limiting layer described in `doc/load-management-architecture.md`, which the `X-Score` header exists specifically to drive at the Cloudflare/Workhorse layer [10](#0-9) . An attacker can repeatedly issue large clones/fetches that are individually reported as cheap (fixed cost 10) to the upstream rate limiter while consuming disproportionate CPU/IO/network resources on the Gitaly node, degrading the accuracy of the outward DoS-mitigation signal that Rails/Workhorse and Cloudflare rely on.

### Likelihood Explanation
This requires no special privileges — it triggers on the standard, most common Gitaly RPCs (`PostUploadPackWithSidechannel`, `SSHUploadPackWithSidechannel`) used by every `git clone`/`fetch`, and the mismeasurement is a systemic architectural property of how sidechannel data bypasses `grpcstats.PayloadBytes`, not a corner case requiring specific crafted input. It occurs on every sidechannel-served fetch/clone regardless of size.

### Recommendation
Feed the actual sidechannel byte count (already captured by `CountingWriter`/`counter.N` in the upload-pack handlers, e.g. `internal/gitaly/service/ssh/upload_pack.go` and the smarthttp equivalent) into the same `PayloadBytesStats`/context value that `costhandler.dynamicCostFromContext` reads, or expose a dedicated mechanism for RPC handlers to report out-of-band transferred bytes into the cost calculation before the trailer is set, so that `x-gitaly-cost` for sidechannel RPCs scales with actual data volume rather than remaining pinned to the static override.

### Proof of Concept
1. An unauthenticated-relative-to-cost or ordinary authorized client issues `git clone` (or `git fetch`) against a large repository via HTTP (routed to `PostUploadPackWithSidechannel`) or SSH (`SSHUploadPackWithSidechannel`).
2. Gitaly opens a sidechannel and streams the multi-GB packfile directly over the Yamux stream, per `doc/sidechannel.md` [11](#0-10) .
3. The gRPC call itself only carries small control/request messages, so `grpcstats.PayloadBytes.HandleRPC` records only these bytes into `PayloadBytesStats` [5](#0-4) .
4. `costhandler.UnaryInterceptor` calls `computeCost`, which adds `staticCostForMethod` (10, from the override table) plus `dynamicCostFromContext`, the latter computed from the (near-empty) `PayloadBytesStats` and thus ~0 regardless of the multi-GB transfer [12](#0-11) .
5. The `x-gitaly-cost` trailer is set to a flat `10` no matter how large the clone was, so repeated large clones are all scored identically to trivial ones by any upstream consumer of `X-Score`.

```go
func UnaryInterceptor(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {
	resp, err := handler(ctx, req)

	_ = grpc.SetTrailer(ctx, metadata.Pairs(
		CostHeader, fmt.Sprintf("%d", computeCost(ctx, info.FullMethod)),
	))

	return resp, err
}

// StreamInterceptor is a gRPC stream server interceptor that sets the
// x-gitaly-cost trailer after the handler completes.
func StreamInterceptor(srv interface{}, stream grpc.ServerStream, info *grpc.StreamServerInfo, handler grpc.StreamHandler) error {
	err := handler(srv, stream)

	stream.SetTrailer(metadata.Pairs(
		CostHeader, fmt.Sprintf("%d", computeCost(stream.Context(), info.FullMethod)),
	))

	return err
}

// computeCost returns the cost score for a completed RPC. It combines a static
// base cost for the RPC type with a dynamic component from actual bytes
// transferred, read from the RPCEntry in context.
func computeCost(ctx context.Context, fullMethod string) int {
	static := staticCostForMethod(fullMethod)
	dynamic := dynamicCostFromContext(ctx)
	return static + dynamic
}
```

```go
// dynamicCostFromContext computes the dynamic cost contribution from payload
// bytes tracked by the grpcstats.PayloadBytes stats handler.
func dynamicCostFromContext(ctx context.Context) int {
	stats := grpcstats.PayloadBytesStatsFromContext(ctx)
	if stats == nil {
		return 0
	}
	totalBytes := stats.InPayloadBytes + stats.OutPayloadBytes

	return int(math.Ceil(float64(totalBytes) / float64(byteCostDivisor)))
}
```

```markdown
# Gitaly sidechannels

Since GitLab 14.4, Gitaly supports a custom protocol for RPCs that
transfer a high volume of byte stream data. Currently, this only
applies to `PostUploadPackWithSidechannel`, which is used for Git HTTP
traffic, as well as `SSHUploadPackWithSidechannel` for SSH traffic, as well as
`PackObjectsHookWithSidechannel`.

Prior to sidechannel, the only way for Gitaly to serve a byte stream
was to encapsulate the bytes in gRPC Protobuf messages. Because of the
per-message overhead, this acted as a limiting factor on how much Git
fetch traffic a Gitaly server could serve up.

The sidechannel protocol works around this by:

1. Allowing the Gitaly server to establish a sidechannel to the Gitaly client during an RPC call.
1. Performing the bulk data transfer on the sidechannel.
```

A sidechannel is another byte stream sent over the same TCP connection.

- Stream 1: gRPC connection (persistent, used for control)
- Stream 2: Backchannel (persistent, used by Praefect for voting)
- Stream 3: First sidechannel (short-lived)

```markdown
### Sidechannel Usage

When an RPC needs to transfer bulk data (e.g., `PostUploadPackWithSidechannel`):

1. The server opens a **new short-lived Yamux stream**
1. Bulk data flows over this stream without gRPC/Protobuf overhead
1. The stream closes when the data transfer completes
```

```go
// HandleRPC implements per-RPC tracing and stats instrumentation.
func (s *PayloadBytes) HandleRPC(ctx context.Context, rs stats.RPCStats) {
	switch st := rs.(type) {
	case *stats.InPayload:
		bytesStats := ctx.Value(payloadBytesStatsKey{}).(*PayloadBytesStats)
		bytesStats.InPayloadBytes += int64(st.Length)
	case *stats.OutPayload:
		bytesStats := ctx.Value(payloadBytesStatsKey{}).(*PayloadBytesStats)
		bytesStats.OutPayloadBytes += int64(st.Length)
	}
}
```

```go
func (s *server) SSHUploadPackWithSidechannel(ctx context.Context, req *gitalypb.SSHUploadPackWithSidechannelRequest) (*gitalypb.SSHUploadPackWithSidechannelResponse, error) {
	conn, err := sidechannel.OpenSidechannel(ctx)
	if err != nil {
		return nil, structerr.NewInternal("opennig sidechannel: %w", err)
	}
	defer conn.Close()

	// Count all bytes written back to the client so we can report the
	// client-facing transfer size, labeled by clone type.
	counter := &helper.CountingWriter{W: conn}
	sidebandWriter := pktline.NewSidebandWriter(counter)
	stdout := sidebandWriter.Writer(stream.BandStdout)
	stderr := sidebandWriter.Writer(stream.BandStderr)
	stats, _, err := s.sshUploadPack(ctx, req, conn, stdout, stderr)
	if err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	s.recordServedBytes(stats, counter.N)

	if err := conn.Close(); err != nil {
		return nil, structerr.NewInternal("close sidechannel: %w", err)
	}

	return &gitalypb.SSHUploadPackWithSidechannelResponse{
		PackfileNegotiationStatistics: stats.ToProto(),
	}, nil
}
```

```markdown
### RPC Cost Score (`x-gitaly-cost`)

Gitaly returns a cost score for each RPC as a gRPC response trailer.
Gitaly has the most context about the actual cost of each RPC, making it the right
place to own this value. Rails and Workhorse translate the `x-gitaly-cost`
trailer into an `X-Score` HTTP response header, making the cost signal
available to any upstream rate limiter.

> On GitLab.com, the `X-Score` header feeds Cloudflare's
> [complexity-based rate limiting](https://developers.cloudflare.com/waf/rate-limiting-rules/request-rate/#complexity-based-rate-limiting).
> Self-managed deployments can use the same header with any upstream
> rate limiter or ignore it.
```
