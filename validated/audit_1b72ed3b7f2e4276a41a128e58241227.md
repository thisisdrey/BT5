The claim is substantiated by the code. I confirmed the full chain described in the report:

1. **V1 enforces an on-chain fee floor.** `calculate_fee` derives the fee from `GasMeter::maximum_gas_used_at_most(command)` and governance `PricingParameters`, and this fee is returned from `validate()` in `bridges/snowbridge/pallets/outbound-queue/src/send_message_impl.rs`, forcing the caller to pay it. Audit Report

## Title
Snowbridge Outbound Queue V2 accepts user-controlled `fee` and `gas` values with no on-chain minimum check, allowing underpriced messages to consume the shared per-block Ethereum delivery capacity - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
Unlike the V1 outbound queue, which computes and enforces an on-chain fee floor (`calculate_fee` derived from `GasMeter::maximum_gas_used_at_most` and governance `PricingParameters`) before admitting a message, the V2 pipeline's `SendMessage::validate` performs no fee computation or enforcement whatsoever. The `fee` stored on-chain is taken verbatim from the user's XCM, and for `Command::CallContract` the "maximum gas" used to compute the real Ethereum-side cost is itself taken directly from user-supplied input, so an attacker can submit arbitrarily underpriced messages that consume the fixed `MaxMessagesPerBlock` slot capacity.

## Finding Description
`bridges/snowbridge/pallets/outbound-queue-v2/src/send_message_impl.rs`'s `validate()` only checks the encoded payload size and returns the message itself as the ticket — it neither computes nor returns any `Fee`, in contrast to the V1 implementation which calls `calculate_fee(gas_used_at_most, params)` and forces the caller to pay it. The `fee` field that ends up in the `Message` struct comes from `XcmConverter::extract_remote_fee` in `bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs`, which only validates that two user-chosen asset amounts are mutually consistent (`reserved_fee_amount >= fee_amount`), never that they are commensurate with the actual command being requested. For `Command::CallContract`, `ConstantGasMeter::maximum_dispatch_gas_used_at_most` in `bridges/snowbridge/primitives/outbound-queue/src/v2/message.rs` returns `*gas_limit` verbatim — an unbounded, attacker-supplied number — whereas every other command has a fixed protocol constant. Finally, `do_process_message` in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` stores the unvalidated `fee` straight into `PendingOrder` with no `ensure!` comparing it against the computed gas cost, and no minimum non-zero check. The dead `XcmConverterError::CallContractValueInsufficient` enum variant exists but is never constructed anywhere in the codebase, confirming no actual enforcement exists for this invariant.

## Impact Explanation
`MaxMessagesPerBlock` gates how many outbound messages can be committed per block via the `Yield` check in `do_process_message`, and this is a shared, finite resource across all users/channels. Because there is no fee floor, an unprivileged attacker can flood the queue with `fee = 0` (or negligible) messages, each consuming a slot; since relayer rewards come from `fee`, no rational relayer delivers these, so they permanently occupy `PendingOrders` and consume per-block commit capacity that legitimate, well-paying bridge traffic must compete for. This matches the "public underpriced work that degrades block production or stalls bridge processing" impact category.

## Likelihood Explanation
The attack requires only an ordinary unprivileged user constructing an XCM through the standard export path to Bridge Hub (`EthereumBlobExporter`/`XcmConverter`) — the same path any user uses to bridge to Ethereum. No relayer, validator, or governance action is required, and the exploit is trivially repeatable across blocks.

## Recommendation
Reinstate an on-chain fee floor for V2 messages analogous to V1's `calculate_fee`: compute a minimum required fee from `GasMeter::maximum_dispatch_gas_used_at_most(command)` (bounding user-supplied `gas` for `CallContract` to a sane protocol maximum) multiplied by a governance-controlled `fee_per_gas`, and reject any message in `validate`/`do_process_message` whose attached `fee` falls below that floor.

## Proof of Concept
1. Attacker constructs an XCM on Asset Hub containing `WithdrawAsset`/`PayFees` with a negligible fee amount (e.g., 1) and a `Transact` instruction encoding a `ContractCall::V1` with a large `gas` value.
2. `XcmConverter::convert` in `convert.rs` accepts this, producing a `Message` with `fee = 1` and a `Command::CallContract { gas: <large>, .. }`.
3. `OutboundQueue::validate` in `send_message_impl.rs` accepts the ticket without computing or enforcing any fee.
4. `do_process_message` in `lib.rs` stores `PendingOrder { fee: 1, .. }`, consuming one of the `MaxMessagesPerBlock` slots, with the real gas requirement (`maximum_dispatch_gas_used_at_most`) set to the attacker's large `gas` value.
5. Repeating this across blocks fills the fixed per-block commit capacity with unprofitable messages that no rational relayer delivers, degrading throughput for legitimate bridge traffic while `PendingOrders` accumulates unresolved entries indefinitely.
