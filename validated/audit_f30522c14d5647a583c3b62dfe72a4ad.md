### Title
Stale `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` state survives account deletion and lets a leftover self-receipt execute against a recreated account with forged `predecessor_id == receiver_id` trust - (File: runtime/runtime/src/lib.rs, core/store/src/utils/mod.rs)

### Summary
`process_action_receipt` stores per-`data_id` links (`TrieKey::PostponedReceiptId`), a `TrieKey::PendingDataCount` counter, and the serialized receipt (`TrieKey::PostponedReceipt`) when an action receipt is waiting on input data. `remove_account`, invoked when an account self-deletes via `DeleteAccount`, wipes the `Account`, `ContractCode`, access keys, and `ContractData` rows but never enumerates/removes these postponed-receipt-related keys, so a still-pending self-receipt keyed to the deleted account name survives account deletion and recreation.

### Finding Description
When an action receipt has unresolved `input_data_ids`, `process_action_receipt` writes, for every missing `data_id`, a `TrieKey::PostponedReceiptId { receiver_id, data_id } -> receipt_id` entry and a `TrieKey::PendingDataCount { receiver_id, receipt_id }` counter, and separately persists the full receipt under `TrieKey::PostponedReceipt`. [1](#0-0) 

`remove_account` is the routine invoked to clear all trie state for an account being deleted (via `DeleteAccount`). It removes `Account`, `ContractCode`, access/gas keys, and `ContractData`, but has no logic that iterates or removes `PostponedReceiptId`, `PendingDataCount`, or `PostponedReceipt` rows for that account. [2](#0-1) 

Later, when a `Data` receipt is delivered to an account, `process_receipt` looks up `TrieKey::PostponedReceiptId { receiver_id: account_id, data_id }` purely by account name/data-id — it has no way to distinguish "the same account before deletion" from "a freshly created account with the same name." If found, it decrements/consumes `PendingDataCount` and, once satisfied, fetches and executes the previously-postponed receipt via `apply_action_receipt`. [3](#0-2) 

Exploit flow:
1. Attacker's contract at `victim.near` issues a self-directed action receipt (predecessor_id == receiver_id == `victim.near`) with two `input_data_ids` (e.g., two `promise_then` callback dependencies), which becomes postponed because neither data item has arrived yet.
2. One of the two data items is delivered, decrementing `PendingDataCount` to 1 but leaving one `PostponedReceiptId` entry, the `PendingDataCount` counter, and the `PostponedReceipt` body still in state.
3. `victim.near` calls `DeleteAccount`, running `remove_account`, which deletes the account/keys/code/data but leaves the postponed-receipt trie keys behind untouched.
4. The name `victim.near` is recreated (e.g., re-registered by any party, since account creation has no knowledge of leftover postponed-receipt state) with new keys/contract.
5. The second, still-outstanding `Data` receipt for the original `data_id` arrives and is routed to `victim.near`. `process_receipt` finds the stale `PostponedReceiptId` link, decrements `PendingDataCount` to 0, fetches the original `PostponedReceipt`, and executes it via `apply_action_receipt` with the original `predecessor_id == receiver_id` intact — even though the account has since changed ownership/content.

None of the existing checks (nonce, access-key permission, signature, gas) intercept this because the flow never revalidates account identity/continuity when resolving postponed receipts by name+data_id; the trie-key namespace is keyed purely by `AccountId`, not by any account "generation" or creation nonce.

### Impact Explanation
This breaks authorization exactness for self-call trust: contracts (e.g., multisig/DAO-style contracts) commonly treat `predecessor_id == current_account_id` as proof that an action was internally pre-approved. A leftover postponed self-receipt from a prior incarnation of the account can be forced to execute against the new incarnation's state, potentially triggering privileged self-trusted logic (fund transfers, key additions, config changes) that the new account owner never authorized. This falls into the "authorization escalation across accounts or promises" bounty category and could result in fund loss or unauthorized state mutation on the recreated account.

### Likelihood Explanation
The attacker needs to control the original `victim.near` account to author the crafted self-receipt with two `input_data_ids`, delete it, and get the name recreated (possible whenever an account name becomes free and is later re-registered — a normal, permissionless action on NEAR). No validator/node privilege is required; only standard transaction submission (`DeployContract`, self promise creation, `DeleteAccount`) from an ordinary funded account. This is deterministic and repeatable given a name-reuse scenario. The main uncertainty is confirming there is no other guard (e.g., pending-receipt count check) blocking `DeleteAccount` while callbacks are outstanding — the code inspected does not show such a guard in `remove_account` or the delete-account path examined.

### Recommendation
Extend `remove_account` (or the `DeleteAccount` action handler) to also enumerate and remove all `PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` trie entries scoped to the account being deleted, mirroring the existing cleanup done for access keys and contract data, so no dangling postponed-receipt state can be resolved against a differently-owned, recreated account of the same name.

### Proof of Concept
Runtime/test-loop integration test outline:
1. Deploy a contract to `victim.near` that issues a self promise with two `PromiseThen`/`FunctionCall` dependencies producing two `input_data_ids` (or manually construct an `ActionReceipt` with `predecessor_id == receiver_id == victim.near` and two `input_data_ids` via the test harness), leaving the receipt postponed.
2. Deliver one `DataReceipt` for one of the two `data_id`s; assert `PendingDataCount` == 1 and `PostponedReceiptId` for the remaining `data_id` still present.
3. Submit `DeleteAccount` for `victim.near`; assert `Account`, `ContractCode`, access keys removed, but query state directly and assert `TrieKey::PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` entries for `victim.near` still exist (proving the bug).
4. Recreate `victim.near` (new keys/new or no contract).
5. Deliver the second `DataReceipt` for the outstanding `data_id`; assert the runtime executes the original postponed receipt's actions (e.g., observe the pre-scripted action's side effect, such as a transfer or key addition on the recreated account) and that `predecessor_id == receiver_id == victim.near` in the resulting execution outcome, despite the account having been deleted and recreated in between.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
