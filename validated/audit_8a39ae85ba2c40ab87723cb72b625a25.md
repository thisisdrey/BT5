## Analog Analysis

Mapping the Olympus bug class (an equality/authorization check that can be satisfied by data the authority never actually intended to authorize for that context) onto the StackerDB implementation, the closest reachable analog is that the StackerDB chunk-signing digest does not bind the target smart contract identifier (`QualifiedContractIdentifier`). A signature is only computed over `(slot_id, slot_version, data_hash)`: [1](#0-0) 

and verification checks only that this same triple recovers to the recorded slot owner for whichever contract is being written to: [2](#0-1) [3](#0-2) 

Because the digest never commits to *which* StackerDB contract the write is destined for, a chunk validly signed and stored in one StackerDB replica (e.g. one reward-cycle's `.signers-X-Y` contract, where slot assignment is derived purely from the signer's position in `stackerdb-get-signer-slots`) is fully "valid" for replay into any other StackerDB replica where that same signer address happens to own the same `slot_id`, as long as the target slot's version constraint is satisfied. This is the "equality that should include an authorization scope but doesn't" bug class, analogous to the Olympus finding where a value legitimately recorded by one path could be reused/moved in a way the revoking authority never anticipated.

### Title
Missing contract-identifier binding in StackerDB chunk signatures enables cross-StackerDB signature replay - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest` (and therefore `StackerDBChunkData::sign`/`verify`) commits only to `slot_id`, `slot_version`, and `data_hash`. It omits the target `QualifiedContractIdentifier`. Any node relaying traffic — an unprivileged, remote observer — can capture a validly signed chunk from StackerDB contract A and resubmit it (via the P2P push path or the `/v2/stackerdb/.../chunks` HTTP endpoint) as a write into a *different* StackerDB contract B, provided the signing address happens to own the same `slot_id` in B and B's stored version for that slot is lower than the replayed `slot_version`.

### Finding Description
`try_replace_chunk` performs slot signer verification purely against `(smart_contract, slot_id)` → `SlotValidation.signer`, then validates the signature over the contract-agnostic digest: [4](#0-3) 

The same contract-agnostic check is used on the P2P ingestion path in `validate_received_chunk`, which is invoked both for normal sync (`StackerDBChunkInv` path) and the buffered "FutureView" path for unsolicited pushes: [5](#0-4) [6](#0-5) 

Slot ownership per StackerDB is derived directly from `stackerdb-get-signer-slots` in that contract, so it is entirely plausible — and common by design (the same signer set frequently participates across consecutive `.signers-X-Y` reward-cycle contracts and across `.signers-0-N` / `.signers-1-N` message-type contracts) — for the same principal to be assigned an identical `slot_id` across multiple StackerDB contracts: [7](#0-6) 

Because `auth_digest()` never folds in `contract_id`, `signature verified == authorized for THIS specific StackerDB` is a false equality: it only proves `signature verified == authorized by this signer for SOME slot with this id/version/hash, in some StackerDB`. An attacker who observes any single valid chunk broadcast on the network (no key access required) can replay its `(slot_id, slot_version, sig, data)` tuple into any other contract with the same slot assignment for that signer, as long as the local `try_replace_chunk`/`validate_received_chunk` version check (`slot_version` greater than that replica's currently stored version) is satisfiable there — which is trivial for a freshly-instantiated or lagging replica for a new reward cycle where the version counter restarts near 0.

This directly parallels the Olympus bug's root cause: the check enforced ("this token/signature was legitimately produced by an authorized party for *a* protected action") is broader than the check that should be enforced ("...for *this specific* protected action/target"), letting the attacker route the same authorized artifact around a context-specific guarantee the system relies on.

### Impact Explanation
This allows an unprivileged network participant to cause **network-wide propagation of forged/misattributed data**: a message a signer produced and authorized for one round/topic (e.g., last reward cycle's block-response StackerDB) can be injected as an apparently fresh, validly-signed message into a different round/topic's StackerDB (e.g., the current reward cycle's StackerDB), and it will be accepted, stored, and rebroadcast by every peer that syncs it — see the storage/broadcast path: [8](#0-7) 

Nodes and signer software consuming these StackerDB messages (e.g. `stacks-signer`) treat "signature recovers to expected slot owner" as sufficient proof of an intentional, fresh statement, so a replayed chunk from an unrelated context can be misinterpreted as a legitimate current-round message from that signer, potentially corrupting the signer message stream/state for that reward cycle. This matches the "High" impact bucket (serving non-canonical/mismatched data as canonical within a specific StackerDB context).

### Likelihood Explanation
Exploitation requires no private key and no elevated privilege — only passively observing one broadcast chunk (trivial, since chunks are P2P-broadcast and served publicly over the `/v2/stackerdb` HTTP RPC) and resubmitting it to a StackerDB where the version-check gate is not yet past that value (e.g., early in a new reward cycle, or on any replica the attacker connects to before it catches up). The main friction is that the target StackerDB's slot for that `slot_id` must be owned by the same signer address, which is a data-dependent precondition rather than a hard blocker, given how slot ranges are contiguously assigned by index in `eval_signer_slots`.

### Recommendation
Include the target `QualifiedContractIdentifier` (and ideally a chain-view/reward-cycle-scoping value already used elsewhere, such as `rc_consensus_hash`) inside `SlotMetadata::auth_digest()` so a signature is only valid for the specific StackerDB replica/context it was produced for. This requires a coordinated protocol/version bump since it changes what data is hashed and signed by all StackerDB clients (`libstackerdb`, `stacks-signer`, node HTTP/P2P handlers).

### Proof of Concept
1. Signer `S` is assigned `slot_id = 0` in `.signers-1-5` (reward cycle N) and also `slot_id = 0` in `.signers-1-6` (reward cycle N+1) — plausible since slot assignment is purely positional per contract's `stackerdb-get-signer-slots` result [9](#0-8) .
2. `S` legitimately signs and pushes chunk `(slot_id=0, slot_version=3, data=D)` to `.signers-1-5`; it is accepted and broadcast [10](#0-9) .
3. Attacker observes this chunk on the wire (or fetches it via the public HTTP StackerDB chunk endpoint).
4. Attacker resubmits the identical `(slot_id=0, slot_version=3, sig, D)` tuple as a `StackerDBPushChunkData` targeting `.signers-1-6`, whose currently-stored version for slot 0 is `< 3` (true for a new reward cycle whose version counters reset).
5. `validate_received_chunk`/`try_replace_chunk` accept it because signature verification only checks `slot_desc.verify(&slot_validation.signer)` for `.signers-1-6`'s slot owner — which is the same address `S` — with no contract-binding check [3](#0-2) [2](#0-1) .
6. The chunk is stored as if freshly authored for `.signers-1-6` and rebroadcast network-wide, even though `S` never signed anything intended for that contract/round.

        if !slot_metadata.verify(&addr)? {

                smart_contract_id, data.slot_id, &addr

    fn parse_slot_entry(
        entry: ClarityValue,
        contract_id: &QualifiedContractIdentifier,
    ) -> Result<(StacksAddress, u32), String> {
        let ClarityValue::Tuple(slot_data) = entry else {
            let reason = format!(
                "StackerDB fn `{contract_id}.{STACKERDB_SLOTS_FUNCTION}` returned non-tuple slot entry",
            );
            return Err(reason);
        };

        let Ok(ClarityValue::Principal(signer_principal)) = slot_data.get("signer") else {
            let reason = format!(
                "StackerDB fn `{contract_id}.{STACKERDB_SLOTS_FUNCTION}` returned tuple without `signer` entry of type `principal`",
            );
            return Err(reason);
        };

        let Ok(ClarityValue::UInt(num_slots)) = slot_data.get("num-slots") else {
            let reason = format!(
                "StackerDB fn `{contract_id}.{STACKERDB_SLOTS_FUNCTION}` returned tuple without `num-slots` entry of type `uint`",
            );
            return Err(reason);
        };

        let num_slots = u32::try_from(*num_slots)
            .map_err(|_| format!("Contract `{contract_id}` set too many slots for one signer (max = {STACKERDB_INV_MAX})"))?;
        if num_slots > STACKERDB_INV_MAX {
            return Err(format!("Contract `{contract_id}` set too many slots for one signer (max = {STACKERDB_INV_MAX})"));
        }

        let PrincipalData::Standard(standard_principal) = signer_principal else {
            return Err(format!(
                "StackerDB contract `{contract_id}` set a contract principal as a writer, which is not supported"
            ));
        };
        let addr = StacksAddress::from(standard_principal.clone());
        Ok((addr, num_slots))
    }

    fn eval_signer_slots(
        chainstate: &mut StacksChainState,
        burn_dbconn: &dyn BurnStateDB,
        contract_id: &QualifiedContractIdentifier,
        tip: &StacksBlockId,
    ) -> Result<Vec<(StacksAddress, u32)>, NetError> {
        let value = chainstate.eval_read_only(
            burn_dbconn,
            tip,
            contract_id,
            &format!("({STACKERDB_SLOTS_FUNCTION})"),
        )?;

        let result = value.expect_result()?;
        let slot_list = match result {
            Err(err_val) => {
                let err_code = err_val.expect_u128()?;
                let reason = format!(
                    "Contract {} failed to run `stackerdb-get-signer-slots`: error u{}",
                    contract_id, &err_code
                );
                warn!("{}", &reason);
                return Err(NetError::InvalidStackerDBContract(
                    contract_id.clone(),
                    reason,
                ));
            }
            Ok(ok_val) => ok_val.expect_list()?,
        };

        let mut total_num_slots = 0u32;
        let mut ret = vec![];
        for slot_value in slot_list.into_iter() {
            let (addr, num_slots) =
                Self::parse_slot_entry(slot_value, contract_id).map_err(|e| {
                    warn!("Failed to parse StackerDB slot entry: {}", &e);
                    NetError::InvalidStackerDBContract(contract_id.clone(), e)
                })?;

            if num_slots > STACKERDB_INV_MAX {
                let reason = format!(
                    "Contract {} stipulated more than maximum number of slots for one signer ({})",
                    contract_id, STACKERDB_INV_MAX
                );
                warn!("{}", &reason);
                return Err(NetError::InvalidStackerDBContract(
                    contract_id.clone(),
                    reason,
                ));
            }

            total_num_slots =
                total_num_slots
                    .checked_add(num_slots)
                    .ok_or(NetError::OverflowError(format!(
                        "Contract {} stipulates more than u32::MAX slots",
                        &contract_id
                    )))?;

            if total_num_slots > STACKERDB_INV_MAX {
                let reason = format!(
                    "Contract {contract_id} stipulated more than the maximum number of slots"
                );
                warn!("{reason}");
                return Err(NetError::InvalidStackerDBContract(
                    contract_id.clone(),
                    reason,
                ));
            }

            ret.push((addr, num_slots));
        }
        Ok(ret)
    }
