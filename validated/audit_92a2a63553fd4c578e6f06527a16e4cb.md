## Finding: Out-of-bounds read parsing untrusted ZIP central directory entries in `ijar`'s `InputZipFile::ProcessCentralDirEntry`

### Title
Out-of-bounds read when parsing a malformed but hash-pinned ZIP/JAR central directory entry - (`third_party/ijar/zip.cc`)

### Summary
`ijar` (Bazel's interface-jar generator, exposed to Starlark via `java_common.run_ijar`/`stamp_jar` and used internally for every `java_library`/`java_import` compile-time jar) parses ZIP central-directory records with `InputZipFile::ProcessCentralDirEntry`. Unlike the local-file-header parsing path, this function performs **no bounds checking** before reading multi-byte length/offset fields and walking a variable-length "extra fields" chain, so a corrupted but checksum-matching JAR/ZIP can drive reads past the end of the mmap'd input buffer.

### Finding Description
`InputZipFile::ProcessLocalFileEntry`, `SkipFile`, and `ProcessFile` all guard every read with `EnsureRemaining(...)`, which checks that at least `n` bytes remain in the mapped input before advancing the cursor `p`: [1](#0-0) [2](#0-1) 

In contrast, `ProcessCentralDirEntry` — which walks the file's central directory to determine each entry's `compressed_size`, `uncompressed_size`, `file_name_length`, `extra_field_length`, `file_comment_length`, `attr`, and `offset`, and then iterates a chain of "extra field" records looking for a Zip64 extension — never calls `EnsureRemaining` and never validates that `p`, `extra_p`, or the Zip64 extra-field pointer stay within `zipdata_in_` + file length: [3](#0-2) 

Specifically:
- `p += 16` then four `get_u4le`/`get_u2le` reads, then a `memcpy` of `file_name_length` bytes from `p` with no check that `file_name_length` fits in the remaining mapped region [4](#0-3) .
- The extra-field loop advances `extra_p` by an attacker-controlled `data_size` read directly from the file and dereferences `extra` with `get_u8le` for Zip64 fields, with no bound against `p` (the end of the extra-fields region) or the mapped file end [5](#0-4) .

Since the ZIP file is opened via `mmap` (`MappedInputFile`/`zipdata_in_`), reading past the mapped region is a genuine out-of-bounds memory read (potentially a SIGSEGV, or leaking adjacent heap/page bytes into interpreted length fields) — directly analogous to the ncurses `convert_strings` OOB read in `tinfo/read_entry.c`, which similarly trusted length fields from an on-disk record without validating them against the buffer bounds.

### Impact Explanation
A crafted JAR/ZIP with a central-directory record whose `file_name_length`, `extra_field_length`, or embedded Zip64 extra-field `data_size` point beyond the actual file size causes `ijar` to read (and `memcpy`) memory outside the mapped input file. This can crash the Bazel build (denial of service for that action) or, in principle, cause length/offset fields to be computed from out-of-bounds bytes, propagating corrupted size/offset values into subsequent processing.

### Likelihood Explanation
`ijar`/`zip.cc` is on a directly reachable, unprivileged-attacker-controlled path: any JAR consumed by `java_library`, `java_import`, `http_jar`, or explicitly via `java_common.run_ijar`/`stamp_jar` is parsed by this code. Because Bazel's `sha256`/`integrity` pinning only guarantees byte-identity to whatever the attacker originally published — not well-formedness of the ZIP structure — a hostile origin server/mirror can publish a legitimately-hashable JAR that is internally malformed, and the developer pins that exact (malicious) hash without ever inspecting the ZIP's internal central-directory fields. The existing checksum verification therefore does not stop this class of bug: it verifies *which* bytes were fetched, not that those bytes form a well-formed archive.

### Recommendation
Add the same `EnsureRemaining` bounds validation used in `ProcessLocalFileEntry`/`SkipFile`/`ProcessFile` to `ProcessCentralDirEntry` before every multi-byte read, the filename `memcpy`, and each step of the extra-field iteration (bounding `extra_p`/`data_size` against both the extra-fields end and the mapped file end) so malformed length/offset fields are rejected with a diagnostic instead of causing an out-of-bounds read.

### Proof of Concept
Construct a JAR/ZIP whose central directory header advertises `extra_field_length` (or a nested Zip64 extra-field `data_size`) larger than the number of bytes actually remaining in the file after the central directory header, such that the resulting `p`/`extra_p` pointer walk in `ProcessCentralDirEntry` runs past the end of the mmap'd file. Feed this file to the `ijar`/`zipper` binary (or via `java_common.run_ijar` on a `java_import` jar fetched through `http_jar`/`http_archive` with a matching pinned `sha256`) and observe an out-of-bounds read/crash, which can be captured as a regression test analogous to the existing `input_jar_scan_entries_test.h` ZIP64/huge-entry tests [6](#0-5) , adapted to feed a truncated/malformed central directory record through `InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc`.

```text
  }
```

**File:** third_party/ijar/zip.cc (L493-545)
```text
bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
```
