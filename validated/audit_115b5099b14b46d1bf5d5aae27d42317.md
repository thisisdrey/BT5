### Title
Missing bounds validation for `consume_user_resource_percent` in `CreateSmartContract` execution path allows energy-metering corruption - (File: `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
`consume_user_resource_percent` (a percentage-type field that must be within `[0,100]`, analogous to the unbounded royalties field in the reported ERC721NFTProduct/ERC1155NFTProduct bug) is only range-checked in the client-side helper `Wallet.createTransactionCapsule`, not in the actual transaction-processing/validation path that consumes the value at execution time.

### Finding Description
For `CreateSmartContract` transactions, `Wallet.createTransactionCapsule` explicitly skips running any `Actuator.validate()` (`CreateSmartContract` and `TriggerSmartContract` are excluded from the actuator-validation loop), and instead performs an ad-hoc, standalone check on the percent value: [1](#0-0) 

This check only executes when a client uses this specific convenience method to *build* the transaction. A transaction is not required to be constructed this way — any actor able to build and sign a raw `Transaction` protobuf containing a `CreateSmartContract` contract (with an arbitrary `consume_user_resource_percent`, e.g. negative or > 100) and submit it through `Wallet.broadcastTransaction()` bypasses this check entirely, because `broadcastTransaction` never invokes `createTransactionCapsule` and there is no `CreateSmartContractActuator.validate()` performing an equivalent bound check (no such actuator class exists in the codebase — creation is not validated through the standard `Actuator` interface at all).

The unvalidated value is persisted into the deployed contract's `SmartContract.consume_user_resource_percent` field and later consumed directly, without any re-validation, whenever the contract is triggered: [2](#0-1) 

The only guard here is `originEnergyLimit < 0` — there is no check that `consumeUserResourcePercent` is within `[0,100]`, unlike the equivalent, correctly-guarded pattern used elsewhere in the codebase for the same kind of percentage field: [3](#0-2) [4](#0-3) 

Both `UpdateBrokerageActuator` and `UpdateSettingContractActuator` demonstrate that the codebase's intended pattern is to validate percentage-type fields inside the actuator's `validate()` method (which runs unconditionally for every transaction of that type during block application). `CreateSmartContract` breaks this pattern: its percent bound-check exists only in a client helper that is not on the mandatory transaction-processing path.

### Impact Explanation
If `consume_user_resource_percent` is out of `[0,100]` (e.g. negative or >100) when the contract is later triggered by a third-party caller, the ratio computation in `getTotalEnergyLimitWithFixRatio` becomes incorrect:
`(100 - consumeUserResourcePercent)` becomes negative or overshoots, producing a corrupted `creatorEnergyLimit`. Depending on the value, this can cause:
- The contract creator's energy limit computation to be negative/nonsensical, which can throw unexpected `ArithmeticException` from `longValueExact()`, potentially causing a mismatch between expected and actual transaction execution/receipt (a discrepancy between validate-time expectations and execute-time behavior for every future call into that contract).
- Energy resource accounting to be permanently skewed for that contract, effectively letting a contract owner shift disproportionate energy costs onto callers or the creator's own frozen energy incorrectly, which is a resource/fund-accounting integrity bug rather than a low-severity display issue.

This satisfies "unbacked balance"/energy-metering corruption class of impact rather than a purely cosmetic issue.

### Likelihood Explanation
Reachable by any unprivileged deployer: constructing the raw `CreateSmartContract` transaction bytes (skipping the `Wallet.createTransactionCapsule` helper) and calling `broadcastTransaction` is straightforward for any client that talks directly to the gRPC/HTTP broadcast endpoint instead of using the Java wallet SDK's convenience method. No special privileges (SR/witness/committee) are required — this is a normal contract-deployer action.

### Recommendation
Move the `consume_user_resource_percent` bound check (`0 <= percent <= 100`) into the mandatory transaction-processing path for `CreateSmartContract` — either by adding a dedicated `CreateSmartContractActuator.validate()` (matching the pattern used by `UpdateBrokerageActuator`/`UpdateSettingContractActuator`), or by enforcing the check unconditionally inside `TransactionTrace`/`VMActuator` before the contract is deployed, so that it cannot be bypassed by directly broadcasting a crafted transaction.

### Proof of Concept
1. Construct a raw `Transaction` protobuf with a `CreateSmartContract` contract whose `consume_user_resource_percent` is set to, e.g., `-1` or `1000` — do not go through `Wallet.createTransactionCapsule`.
2. Sign the transaction with a valid account key and submit it via `Wallet.broadcastTransaction` (gRPC/HTTP `broadcastTransaction` endpoint).
3. Observe that the transaction is accepted and the contract is deployed with the out-of-range percent stored in `ContractCapsule`.
4. Trigger the deployed contract from a different caller account; observe `VMActuator.getTotalEnergyLimitWithFixRatio` computing an incorrect/negative `creatorEnergyLimit` from the unbounded percent value.

  public TransactionCapsule createTransactionCapsule(com.google.protobuf.Message message,
      ContractType contractType) throws ContractValidateException {
    TransactionCapsule trx = new TransactionCapsule(message, contractType);
    trx.setTransactionCreate(true);
    if (contractType != ContractType.CreateSmartContract
        && contractType != ContractType.TriggerSmartContract) {
      List<Actuator> actList = ActuatorFactory.createActuator(trx, chainBaseManager);
      for (Actuator act : actList) {
        act.validate();
      }
    }
    trx.setTransactionCreate(false);
    if (contractType == ContractType.CreateSmartContract) {

      CreateSmartContract contract = ContractCapsule
          .getSmartContractFromTransaction(trx.getInstance());
      long percent = contract.getNewContract().getConsumeUserResourcePercent();
      if (percent < 0 || percent > 100) {
        throw new ContractValidateException("percent must be >= 0 and <= 100");
      }
    }
