### Title
Dust transfers permanently occupy victim's per-account token list slots, blocking deposits, mints and borrows (`UserReachedMaxTokens` DoS) - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The kernel bug (CVE-2019-15921) is a resource leak on a failed allocation path: `idr_alloc()` fails inside `genl_register_family()` and the already-allocated family object is never freed. The Metronome analog is the reverse side of the same class — a per-account resource (the `depositTokensOfAccount` / `debtTokensOfAccount` sets, capped at `MAX_TOKENS_PER_USER = 30`) that can be filled with junk entries by an unprivileged attacker via dust `DepositToken` transfers, after which every subsequent "allocation" (a new deposit-token mint or debt-token mint to that account) reverts in `onlyIfAdditionWillNotReachMaxTokens`.

### Finding Description
`Pool.addToDepositTokensOfAccount` and `Pool.addToDebtTokensOfAccount` both apply `onlyIfAdditionWillNotReachMaxTokens(account_)`, reverting with `UserReachedMaxTokens` when `debt + deposit` entries reach 30 ( [1](#0-0) [2](#0-1) ).

The problem: entries are added on *behalf* of the recipient, not the caller. `DepositToken._mint` and `_transfer` call `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's balance goes 0 → >0 ( [3](#0-2) ). `DepositToken.transfer`/`transferFrom` are public, permissionless, and only gated by `_revertIfLocked` on the *sender's* balance. So an attacker who deposits 1 wei of each underlying into every registered `DepositToken` can then `transfer(victim, 1)` on each token, filling the victim's `depositTokensOfAccount` set with up to 30 junk entries without any consent.

After that, every code path that would add a *new* token to the victim's set reverts inside `_mint` (the `addTo...` call is the last statement of `DepositToken._mint` and `DebtToken._mint`, so the revert propagates and rolls back the whole transaction):
- `DepositToken.deposit(amount, victim)` — reverts, no one (including the victim or a rescue contract like `NativeTokenGateway`/`SmartFarmingManager`) can top up the victim's collateral with a token the victim doesn't already hold.
- `DebtToken.issue`/`mint`/`flashIssue` → `_mint` → `pool.addToDebtTokensOfAccount(victim)` — reverts for any debt token the victim doesn't already hold, blocking all new borrowing.
- Any `transfer`/`transferFrom`/`seize` to the victim of a deposit token they don't hold — reverts with `DepositTokenAlreadyExists`? no — with `UserReachedMaxTokens`, so liquidations that credit the victim and third-party transfers are also blocked.

The victim can recover only by manually fully emptying each dust balance (`_burn`/transfer-out triggers `removeFromDepositTokensOfAccount` when balance hits 0, [4](#0-3) ), which is possible but requires up to 30 transactions and leaves the account DoS'd in the interim — during which price movement can push the position into liquidation.

### Impact Explanation
Temporary freezing of funds / forced liquidation: while the victim's list is saturated, they cannot add collateral of any new token type and cannot open new debt positions. If their position's health is deteriorating and the needed collateral type isn't already in their set, they cannot rescue the position until they spend gas clearing attacker-chosen junk entries — the window is attacker-controlled and repeatable (attacker re-fills each freed slot with a new dust transfer in the same or a following block, since re-adding after `remove` only requires another 1-wei transfer). This can cause an otherwise-saveable position to be liquidated, transferring collateral to a liquidator.

### Likelihood Explanation
- Fully unprivileged: attacker only needs `DepositToken.deposit` + `transfer` on whitelisted deposit tokens; no governor/keeper/oracle role needed.
- Cost is bounded: ~1 wei × up to 30 deposit tokens, plus gas. Pools with many registered deposit tokens make filling the set cheap; the cap is shared across debt + deposit tokens, so fewer transfers may suffice.
- The guard that was meant to bound gas (`onlyIfAdditionWillNotReachMaxTokens`) is exactly the mechanism that enforces the DoS.
- Escape exists (self-cleaning the list), which is why this is "temporary freezing / griefing" rather than permanent loss — matching a Medium-severity rating analogous to the CVE.

### Recommendation
- Charge slot usage to the *initiator*, not the recipient: revert in `transfer`/`deposit(onBehalfOf)`/`seize` when the recipient would hit the cap, rather than letting arbitrary senders consume the victim's slots — i.e., let a victim at the cap still receive tokens by treating incoming transfers differently, or
- Allow recipients to reject entries: add a `Pool.removeFromDepositTokensOfAccount`-callable path where the *account itself* (not just the token contract) can purge tokens with zero or dust balances, or
- Make the cap check smart: skip `addToDepositTokensOfAccount` revert when the mint is to a position already containing the token, and consider letting `seize`/liquidation credit bypass the cap since blocking it harms the protocol's liquidation liveness.

### Proof of Concept
Hardhat-style reproduction against deployed contracts (fork test):

```ts
// pool has N >= 30 whitelisted deposit tokens; victim already has 0 entries.
// attacker for each deposit token i:
const dust = 1n;
await underlying_i.mint(attacker, dust);               // or buy dust on AMM
await underlying_i.approve(depositToken_i, dust);
await depositToken_i.deposit(dust, attacker);          // msd_i balance > 0
await depositToken_i.transfer(victim, dust);           // adds msd_i to victim's set
// repeat for 30 tokens -> pool.getDepositTokensOfAccount(victim).length == 30

// now: any new deposit to victim reverts
await expect(
  depositToken_new.deposit(parseEther('1'), victim)    // _mint -> addToDepositTokensOfAccount
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// and any new borrow reverts
await expect(
  pool.connect(victim).issue(synth_new, amount)        // DebtToken._mint -> addToDebtTokensOfAccount
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Reference unit test confirming the cap revert already exists: `test/Pool.test.ts` `addToDepositTokensOfAccount` → `"should revert when reach max tokens"` ( [5](#0-4) ).
