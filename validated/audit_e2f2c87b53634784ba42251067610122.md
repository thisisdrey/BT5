### Title
`distribute_internal` Aborts with u64 Underflow When Active Validator Has Both `inactive` and `pending_inactive` Stake, Freezing Inactive Funds Until Next Lockup — (`aptos-move/framework/aptos-framework/sources/staking_contract.move`)

---

### Summary

`distribute_internal` computes `total_potential_withdrawable = inactive + pending_inactive`, then passes that value to `stake::withdraw_with_cap`. When the validator is active and the lockup has not expired, `withdraw_with_cap` only returns `inactive` coins (it never merges `pending_inactive` into `inactive` for an active validator). The resulting `distribution_amount` is therefore strictly less than `distribution_pool.total_coins()` whenever a prior `add_distribution` call (from `unlock_stake` or `request_commission`) set the pool's total to `pending_inactive + commission`. Passing this smaller value to `update_distribution_pool` causes `current_worth - previous_worth` to underflow (u64 arithmetic), aborting every subsequent call to the public `distribute` entry until the lockup expires. The staker's already-unlocked `inactive` stake is frozen for the entire remaining lockup duration.

---

### Finding Description

**Entrypoint — `distribute` (public entry, permissionless):** [1](#0-0) 

Anyone can call `distribute(staker, operator)` with no privilege check.

**Step 1 — `distribute_internal` reads both buckets and requests withdrawal of their sum:** [2](#0-1) 

`total_potential_withdrawable = inactive + pending_inactive`.

**Step 2 — `withdraw_with_cap` only merges `pending_inactive` into `inactive` for an *inactive* validator whose lockup has expired:** [3](#0-2) 

When the validator is **active**, the merge is skipped. The function caps the withdrawal to `min(total_potential_withdrawable, inactive)`, returning only `inactive` coins. So `distribution_amount = inactive < total_potential_withdrawable`.

**Step 3 — `update_distribution_pool` is called with the reduced amount:** [4](#0-3) 

**Step 4 — Underflow in `update_distribution_pool`:** [5](#0-4) 

`previous_worth = shares * distribution_pool.total_coins() / total_shares`
`current_worth  = shares * updated_total_coins / total_shares`

When `updated_total_coins (= inactive) < distribution_pool.total_coins()`, `current_worth < previous_worth`, and the u64 subtraction `current_worth - previous_worth` **aborts**.

**How `distribution_pool.total_coins()` becomes larger than `inactive`:**

`add_distribution` (called from `unlock_stake` / `request_commission_internal`) invokes `update_distribution_pool` with `pending_inactive` as the new total, then calls `buy_in(recipient, coins_amount)`: [6](#0-5) 

After this, `distribution_pool.total_coins() = pending_inactive + coins_amount`. If `inactive < pending_inactive + coins_amount`, the underflow fires.

---

### Impact Explanation

Every call to `distribute` (or any code path that calls `distribute_internal`) aborts with a u64 underflow. Because the abort reverts all state changes, the pool is left unchanged and every subsequent call also aborts. The staker's `inactive` stake — already fully unlocked from a prior lockup cycle — cannot be distributed until the **current** lockup expires and the epoch transition moves `pending_inactive` into `inactive`, making `distribution_amount ≥ distribution_pool.total_coins()`. Depending on the configured lockup duration (up to months), this constitutes a material temporary freeze of user funds with no workaround available inside `staking_contract.move`.

---

### Likelihood Explanation

The condition is reachable in ordinary usage: a staker who has stake from a previous lockup cycle sitting in `inactive`, then calls `unlock_stake` or `request_commission` during the current lockup cycle (populating `distribution_pool` with `pending_inactive`-sized totals), and then calls `distribute` before the lockup expires. No privileged access is required. The `distribute` entry function carries no permission check and is callable by any account.

---

### Recommendation

In `distribute_internal`, after computing `distribution_amount`, clamp `updated_total_coins` to never be less than `distribution_pool.total_coins()` before passing it to `update_distribution_pool`. Alternatively, guard `update_distribution_pool` against a decreasing total by short-circuiting (or skipping commission recalculation) when `updated_total_coins < distribution_pool.total_coins()`, since a decrease means no new rewards have accrued and no commission is owed on the delta.

```
// Pseudocode for a Move integration test
// 1. Initialize framework, create staker + operator accounts.
// 2. create_staking_contract(staker, operator, 1000 APT, 10% commission).
// 3. join_validator_set → end_epoch → validator is ACTIVE.
// 4. End one lockup cycle so 50 APT moves to inactive:
//      unlock_stake(staker, operator, 50 APT);
//      fast_forward_seconds(LOCKUP_CYCLE_SECONDS); end_epoch();
//      // Now: inactive=50, pending_inactive=0
// 5. Start new lockup: unlock_stake(staker, operator, 100 APT);
//      // add_distribution sets distribution_pool.total_coins = 100 + commission
//      // Now: inactive=50, pending_inactive=100
// 6. Call distribute(staker, operator) — validator still ACTIVE, lockup not expired.
//      // withdraw_with_cap returns only 50 (inactive), distribution_amount=50
//      // update_distribution_pool called with 50 < distribution_pool.total_coins (≈110)
//      // current_worth < previous_worth → u64 underflow → ABORT
// 7. assert transaction aborted with arithmetic error.
```
