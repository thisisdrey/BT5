Let me check the key remaining detail — whether `on_transaction_committed` is actually called for aborted transactions in the block executor, and what the write set looks like for an aborted transaction.

### Title
Cross-Shard Executor Deadlock on Transaction Abort: Missing Abort Notification Leaves `RemoteStateValue` Permanently in `Waiting` State — (`aptos-move/aptos-vm/src/sharded_block_executor/cross_shard_client.rs`)

---

### Summary

`CrossShardCommitSender` implements `TransactionCommitHook` but only handles the success path. When a source-shard transaction aborts, its cross-shard state key is never written to the dependent shard's `RemoteStateValue`, which blocks indefinitely in `cvar.wait()`. The dependent shard's executor thread never returns, and the `StopMsg` is never sent, causing a permanent deadlock. The `RemoteTxnWrite` struct's own comment — *"The write op is None if the transaction is aborted"* — confirms the design intended an abort notification path that was never implemented.

---

### Finding Description

**Step 1 — `TransactionCommitHook` has no abort callback.**

The trait is defined as:

```rust
pub trait TransactionCommitHook<O>: Send + Sync {
    fn on_transaction_committed(&self, txn_idx: TxnIndex, output: &O);
}
``` [1](#0-0) 

There is no `on_transaction_aborted` method. This is the root of the problem.

**Step 2 — `CrossShardCommitSender` only sends on success.**

`on_transaction_committed` delegates to `send_remote_update_for_success`, which iterates over the actual write set of the committed output:

```rust
fn send_remote_update_for_success(&self, txn_idx: TxnIndex, txn_output: &TransactionOutput) {
    let edges = self.dependent_edges.get(&txn_idx).unwrap();
    for (state_key, write_op) in txn_output.write_set().expect_write_op_iter() {
        if let Some(dependent_shard_ids) = edges.get(state_key) {
            // sends RemoteTxnWriteMsg(Some(write_op))
        }
    }
}
``` [2](#0-1) 

When a transaction aborts, its write set does **not** contain the cross-shard state key (the abort rolled back those writes). The loop finds nothing, and no message is sent to the dependent shard.

**Step 3 — The design intended an abort notification that was never implemented.**

`RemoteTxnWrite` explicitly documents the `None` case:

```rust
pub struct RemoteTxnWrite {
    state_key: StateKey,
    // The write op is None if the transaction is aborted.
    write_op: Option<WriteOp>,
}
``` [3](#0-2) 

The `None` variant exists in the message type but is never sent by `CrossShardCommitSender`.

**Step 4 — `RemoteStateValue::get_value()` blocks forever.**

The dependent shard initializes every cross-shard key as `Waiting`:

```rust
for key in cross_shard_keys {
    cross_shard_data.insert(key, RemoteStateValue::waiting());
}
``` [4](#0-3) 

When the dependent transaction reads that key, `get_state_value` calls `get_value()`:

```rust
pub fn get_value(&self) -> Option<StateValue> {
    let (lock, cvar) = &*self.value_condition;
    let mut status = lock.lock().unwrap();
    while let RemoteValueStatus::Waiting = *status {
        status = cvar.wait(status).unwrap();  // blocks forever
    }
    ...
}
``` [5](#0-4) 

Since `set_value` is never called (no message was sent), the condvar is never notified, and the thread hangs indefinitely.

**Step 5 — The `StopMsg` is never sent, completing the deadlock.**

After `execute_block` returns, the executor sends `StopMsg` to stop its own `CrossShardCommitReceiver`. But if the execution thread is blocked waiting for a cross-shard value, `execute_block` never returns:

```rust
// Send a self message to stop the cross-shard commit receiver.
cross_shard_client_clone.send_cross_shard_msg(shard_id, round, CrossShardMsg::StopMsg);
``` [6](#0-5) 

The dependent shard's `CrossShardCommitReceiver` thread also hangs waiting for its next message. Both threads are permanently stuck.

**Step 6 — `on_transaction_committed` IS called for aborted transactions.**

In both the parallel and sequential execution paths, the commit hook is called for all finalized outputs, including aborted ones (which still produce gas-charge outputs):

```rust
if let Some(hook) = &self.transaction_commit_hook {
    hook.on_transaction_committed(txn_idx, &committed_output);
}
``` [7](#0-6) 

The hook fires, but the aborted output's write set is empty of the cross-shard key, so no notification reaches the dependent shard.

---

### Impact Explanation

If sharded block execution is enabled, any transaction that:
1. Is assigned cross-shard dependencies by the block partitioner (based on read/write set overlap — not attacker-controlled, but happens naturally), and
2. Aborts during execution (Move abort, out-of-gas, assertion failure — all reachable by unprivileged user transactions)

…will permanently deadlock the dependent shard's executor thread. The shard cannot process any further transactions, causing a **material chain availability failure**.

---

### Likelihood Explanation

Transaction aborts are routine on-chain events (out-of-gas, Move aborts, etc.). The block partitioner assigns cross-shard dependencies based on read/write set overlap across shards. The combination is not rare. An attacker can deliberately submit a transaction designed to abort (e.g., always-abort script) and, if the partitioner assigns it cross-shard dependents, trigger the deadlock. Even without a deliberate attacker, organic transaction aborts with cross-shard dependencies will trigger this.

The primary uncertainty is whether sharded block execution is currently enabled on mainnet validators. If it is not enabled, the practical exploitability is zero despite the code-level defect being real and confirmed.

---

### Recommendation

In `CrossShardCommitSender`, add an abort notification path. When `on_transaction_committed` is called and the output status indicates an abort, send a `RemoteTxnWriteMsg` with `write_op: None` for every cross-shard dependent key. The `RemoteTxnWrite` message type already supports this (`write_op: Option<WriteOp>`). The receiver already handles `None` correctly via `write_op.and_then(|w| w.as_state_value())`, which resolves to `None` state value and unblocks `get_value()`.

Alternatively, add `on_transaction_aborted` to `TransactionCommitHook` and implement it in `CrossShardCommitSender` to send the `None` notifications.

---

### Proof of Concept

```
1. Partition a block with two transactions:
   - T1 on shard 0: writes state key K, has a dependent edge to shard 1
   - T2 on shard 1: reads state key K (cross-shard dependency on T1)

2. Make T1 always abort (e.g., Move script: abort 1).

3. Execute the sharded block:
   - Shard 0 executes T1 → aborts → on_transaction_committed called with empty write set
     → send_remote_update_for_success finds K not in write set → no message sent to shard 1
   - Shard 1 starts executing T2 → reads K → calls CrossShardStateView::get_state_value(K)
     → calls RemoteStateValue::get_value() → blocks in cvar.wait() forever

4. Assert: after a timeout, shard 1's execution has not returned → deadlock confirmed.
```
