### Title
Cross-StackerDB Signature Replay Due to Missing Contract-ID Binding in Chunk Authentication - (`libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata`/`StackerDBChunkData` signatures only commit to `(slot_id, slot_version, data_hash)` and never to the target smart-contract identifier. Because multiple StackerDB replicas (e.g. the per-message-type `.signers-{set}-{msg_id}` contracts) share the exact same slot-id→signer-address assignment, a validly-signed chunk captured from one StackerDB contract can be replayed and accepted into a *different* StackerDB contract, as long as the version check is satisfied there. This lets any relaying peer (no private key needed) write attacker-selected, legitimately-signed data into a StackerDB instance the signer never intended to write to.

### Finding Description
`SlotMetadata::auth_digest` computes the signed digest solely from the slot ID, slot version, and data hash: [1](#0-0) 

The verification routine likewise only checks this digest against the signer's public key hash — it never checks which StackerDB (contract) the chunk is destined for: [2](#0-1) 

The actual DB write path, `StackerDBTx::try_replace_chunk`, resolves the expected signer address for the *target* contract via `get_slot_validation(smart_contract, slot_desc.slot_id)`, then calls `slot_desc.verify(&slot_validation.signer)`. Since the signed digest doesn't reference `smart_contract`, this check succeeds for *any* contract in which the same address happens to own the same `slot_id` and where the version is still fresh: [3](#0-2) 

The same signature-only check (no contract binding) is used for chunks received from peers/gossip in `PeerNetwork::validate_received_chunk`: [4](#0-3) 

Crucially, the signer-slot assignment is *identical* across all per-message-type StackerDB contracts for a given signer set. The `.signers` boot contract stores a single slot list per parity (`stackerdb-signer-slots-0`/`-1`), and every `signers-{set}-{message_id}` contract (there are `SIGNER_SLOTS_PER_USER` of them) reads that same page: [5](#0-4) [6](#0-5) 

This is directly confirmed by `signers_db_get_slots`, which shows every `signers-{set}-{message_id}` contract returns the identical slot list for a given `set`: [7](#0-6) 

Consequently: a chunk `(slot_id=k, slot_version=v, sig)` signed by signer S and legitimately posted to `signers-0-BlockResponse` will pass `SlotMetadata::verify` in `signers-0-Transactions` (or any other `signers-0-*` contract) too, because slot `k` is owned by the same address `S` in *every* `signers-0-*` contract. Any observer of the network (StackerDB chunks are broadcast and readable) can capture such a chunk and POST it (via `RPCPostStackerDBChunkRequestHandler`, `stackslib/src/net/api/poststackerdbchunk.rs`) or gossip it (`StackerDBPushChunk`) into the *other* contract, provided the target slot's current version is `< v`. This is accepted and stored, and per `process_stacker_db_chunks`, re-broadcast network-wide as legitimate data for that (wrong) contract/message type: [8](#0-7) 

### Impact Explanation
This breaks the equality "authenticated for DB X" vs "stored as valid data in DB Y": data that a signer only ever authorized for one StackerDB instance/message-type gets accepted and propagated network-wide as authentic data for a different StackerDB instance, without the attacker possessing any private key. Depending on how downstream consumers (e.g. `StackerDBListener`, signer message parsers) interpret payloads by contract/message type, this can inject misinterpreted or stale-but-fresh-looking payloads into a different message channel — an unauthenticated/unauthorized write into StackerDB state that any network peer can trigger by simple message replay.

### Likelihood Explanation
Low complexity to exploit: StackerDB chunk contents and signatures are publicly readable/gossiped, slot-id-to-signer mappings are identical and predictable across all `signers-{set}-*` contracts (and potentially any two contracts where the operator reuses the same signer set/slot ordering), and the only gating condition is that the target contract's stored slot version is still behind the captured chunk's version — a condition attackers can wait for or induce (e.g. right after a new message-type contract initializes with version 0). No node secret or privileged role is required.

### Recommendation
Include the target StackerDB smart-contract identifier (`QualifiedContractIdentifier`) in the signed digest computed by `SlotMetadata::auth_digest`, so a chunk's signature is bound to exactly the DB instance it was authorized for. This requires updating `SlotMetadata`/`StackerDBChunkData` sign/verify call sites to pass in the contract ID (or otherwise domain-separate the digest per contract), and bumping the wire-format/version of these authenticated structures.

### Proof of Concept
1. Signer `S` owns slot `3` in both `signers-0-0` (message type 0) and `signers-0-1` (message type 1), since both read the same `stackerdb-signer-slots-0` list.
2. `S` legitimately signs and posts chunk `C = (slot_id=3, slot_version=7, data=D)` to `signers-0-0`; the chunk is broadcast/gossiped and publicly observable.
3. Attacker (any network peer, no keys needed) observes `C`, and if `signers-0-1`'s slot 3 is currently at version `< 7`, POSTs the identical `(slot_id, slot_version, sig, data)` tuple to `signers-0-1` via the `POST /v2/stackerdb_chunks/{signers-0-1}/chunks` RPC endpoint (`RPCPostStackerDBChunkRequestHandler`).
4. `try_replace_chunk` for `signers-0-1` calls `get_slot_validation(signers-0-1, 3)` → returns signer `S`; `slot_desc.verify(&S)` succeeds because the digest never referenced the contract; version check passes since `7 > current`.
5. Chunk `C`'s data is now stored as valid signer-message data for `signers-0-1` and network-broadcast, even though `S` never signed anything for that contract.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
