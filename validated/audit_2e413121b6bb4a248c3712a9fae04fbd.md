## Title
Division-Before-Multiplication in Scheduler Cost-Pacing Budget Truncates to Zero, Stalling Transaction Admission Within a Slot - (File: `core/src/banking_stage/transaction_scheduler/scheduler_controller.rs`)

### Summary
`CostPacer::scheduling_budget` linearly paces how much of the per-slot cost-model budget the central scheduler is allowed to consume, based on elapsed time since the leader slot started. The pacing calculation performs division before multiplication when computing `allocation_per_milli`, mirroring the `illuminate` `lend()` root cause (`(a - fee) * (order.premium / order.principal)`) where dividing first destroys precision and can truncate the result to zero.

### Finding Description
`CostPacer::scheduling_budget` computes:
```rust
let allocation_per_milli = self.block_limit / fill_time.as_millis() as u64;
let millis_since_detection = time_since.as_millis() as u64;
allocation_per_milli * millis_since_detection
``` [1](#0-0) 

`self.block_limit` is derived from the bank's cost-tracker block limit (tens of millions of cost units), and `fill_time` is a configurable pacing duration in milliseconds coming from `SchedulerPacing` (`--block-production-method`/pacing CLI configuration), consumed here: [2](#0-1) 

The order of operations — dividing `block_limit` by `fill_time` (in milliseconds) *before* multiplying by `millis_since_detection` — matches exactly the div-then-mul rounding pattern in the referenced report. When `fill_time` (in milliseconds) is larger than `block_limit`, or otherwise close enough in magnitude that `block_limit / fill_time_ms` truncates to `0`, `allocation_per_milli` becomes `0`. Multiplying zero by any `millis_since_detection` keeps the computed `target` at `0` for the *entire* pacing window until `time_since >= fill_time`, at which point the pacer jumps directly to the full `block_limit`. The correct, precision-preserving order (`block_limit * millis_since_detection / fill_time_ms`) is not used, exactly as flagged in the original report's recommended mitigation.

### Impact Explanation
If `allocation_per_milli` rounds to zero, `scheduling_budget()` returns `0.saturating_sub(shared_block_cost.load())` (i.e., 0) for the entire configured `fill_time` window rather than linearly ramping up. This causes the scheduler to withhold all transaction admission/consumption budget for that duration each time a new leader slot is detected, effectively starving the leader's own block production pipeline of transactions during that window — a scheduler/QoS-pacing correctness bug rather than fund loss, since no lamports or account state are involved. The severity is bounded by how `fill_time` is configured relative to `block_limit`.

### Likelihood Explanation
This code path executes automatically on every new leader slot when `scheduler_pacing` is configured with a fill-time-based mode (`SchedulerPacing::FillTimeMillis`) — it is not directly triggered by unprivileged user transactions but by validator-operator configuration of the pacing fill time versus the bank's cost-tracker block limit. Under default/typical values (block limit ~60–100M cost units vs. fill times on the order of hundreds of milliseconds), `allocation_per_milli` does not realistically truncate to zero, so triggering the zero-rounding case requires an operator-chosen `fill_time` config that is unusually large relative to the block cost limit. This significantly limits likelihood and ties the issue closer to operator/config-driven behavior rather than a purely unprivileged-user-triggerable exploit.

### Recommendation
Reorder the arithmetic to multiply before dividing, using saturating/checked math with a wider intermediate type to avoid overflow, e.g.:
```rust
let target = self.block_limit
    .saturating_mul(millis_since_detection)
    .checked_div(fill_time.as_millis() as u64)
    .unwrap_or(self.block_limit);
```
This mirrors the report's fix of computing `((a - fee) * order.premium) / order.principal` instead of `(a - fee) * (order.premium / order.principal)`.

### Proof of Concept
Given `block_limit = 100_000` cost units and `fill_time = Duration::from_millis(200_000)` (a misconfigured/very long fill time relative to block limit):
- `allocation_per_milli = 100_000 / 200_000 = 0` (integer division truncates)
- For any `millis_since_detection < 200_000`, `target = 0 * millis_since_detection = 0`
- The scheduler’s `scheduling_budget()` returns `0`, blocking all cost-based transaction admission for the pacing window, whereas correct order (`100_000 * millis_since_detection / 200_000`) would yield a proportionally increasing non-zero budget.

Note: I was unable to fully verify the exact default/allowed range of `fill_time` values enforced by CLI validation in `validator/src/commands/manage_block_production/mod.rs` and `validator/src/cli.rs` within the available exploration budget, so the practical achievability of the zero-truncation condition under real-world/default configurations remains uncertain.

impl CostPacer {
    fn scheduling_budget(&self, current_time: &Instant) -> u64 {
        let target = if let Some(fill_time) = &self.fill_time {
            let time_since = current_time.saturating_duration_since(self.detection_time);
            if time_since >= *fill_time {
                self.block_limit
            } else {
                // on millisecond granularity, pace the cost linearly.
                let allocation_per_milli = self.block_limit / fill_time.as_millis() as u64;
                let millis_since_detection = time_since.as_millis() as u64;
                allocation_per_milli * millis_since_detection
            }
        } else {
            self.block_limit
        };

        target.saturating_sub(self.shared_block_cost.load())
    }
