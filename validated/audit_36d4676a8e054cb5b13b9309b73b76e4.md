### Title
Failure of intermediate cross-contract calls in the eth-implicit `WalletContract` permanently strands the external caller's attached deposit - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::address_check_callback` and `WalletContract::nep_141_storage_balance_callback` are callbacks in a multi-hop promise chain used to emulate Ethereum transactions on the eth-implicit wallet contract. Both callbacks carry forward a `CallerDeposit` (the external caller's/relayer's attached NEAR representing the value of the emulated Ethereum transaction) which is only refunded in the terminal callback `rlp_execute_callback` on `PromiseResult::Failed`. However, when the *intermediate* cross-contract call in either of these two callbacks itself fails (`PromiseResult::Failed` for the address-registrar `lookup` or the NEP-141 `storage_balance_of` call), the function returns an error `ExecuteResponse` directly without ever creating the refund transfer to `caller_deposit.account_id`, unlike `rlp_execute_callback` which explicitly does so.

### Finding Description
`CallerDeposit` is documented as existing specifically "to refund the caller's deposit if the cross-contract call fails" [1](#0-0) . It is only populated for external (non-self) callers whose attached deposit is nonzero, and its `account_id` is the `predecessor_account_id` — i.e., the relayer that attached the deposit to `rlp_execute`.

The terminal callback correctly implements the intended refund pattern: [2](#0-1) 

But the two earlier-stage callbacks that also carry `caller_deposit` do **not** implement this refund when their own promise fails:

- `address_check_callback`, on `PromiseResult::Failed` from the `address_registrar.lookup(...)` call, returns an error without refunding: [3](#0-2) 

- `nep_141_storage_balance_callback`, on `PromiseResult::Failed` from the `storage_balance_of` call, likewise returns an error without refunding: [4](#0-3) 

Both callbacks accept `caller_deposit: Option<CallerDeposit>` as a parameter specifically to be forwarded/consumed [5](#0-4) [6](#0-5) , but the failure branch simply drops it. Because these are terminal execution paths in the promise DAG (the function returns a `Value`, not another `Promise`), the attached deposit that was moved into the wallet contract's own balance when `rlp_execute` was called is never sent back to the relayer, and no further promise exists to trigger the refund. The relayer's NEAR is retained by the wallet contract permanently.

This is a direct structural analog of the reported Renzo `xReceive` issue: an "unprivileged-signer"-reachable cross-contract callback that fails to defensively handle a downstream call's failure, resulting in funds becoming inaccessible to their rightful owner (the entity that attached them).

### Impact Explanation
Any relayer/caller submitting an `EOABaseTokenTransfer` to another eth-implicit account (triggering the `address_registrar.lookup` check) or an emulated `ERC20Transfer` (triggering `storage_balance_of`) with a nonzero attached deposit, where the intermediate cross-contract call fails (e.g., registrar or token contract runs out of gas, panics, does not exist, or otherwise reverts), permanently loses that deposit into the wallet contract's own balance instead of receiving it back. This is a concrete, non-recoverable loss of funds for an unprivileged external caller, matching the "permanent freezing/loss of funds" impact criterion.

### Likelihood Explanation
This is reachable by any unprivileged relayer submitting standard eth-implicit-account transactions through the documented `rlp_execute` entry point; no special privileges are required. It is triggered whenever the intermediate helper contract call (address registrar or NEP-141 token) fails for any reason (gas exhaustion, non-existent/paused contract, malformed response causing deserialization failure is already separately handled but the `PromiseResult::Failed` branch is not). Given that failures of downstream contracts (bad gas estimates by relayers, paused/broken tokens, non-existent registrar target under test/alternate deployments) are a realistic and not-rare occurrence, likelihood is at least moderate.

### Recommendation
In both `address_check_callback` and `nep_141_storage_balance_callback`, mirror the refund logic used in `rlp_execute_callback`: on `PromiseResult::Failed`, if `caller_deposit` is `Some`, issue a `promise_batch_create` transfer of `yocto_near` back to `caller_deposit.account_id` before returning the failed `ExecuteResponse`. Consider factoring this into a shared helper function to avoid the duplication/divergence that caused this bug in the first place.

### Proof of Concept
1. Deploy the eth-implicit `WalletContract`, fund it, and register an address registrar / a NEP-141 token contract as usual.
2. A relayer submits an RLP-encoded `EOABaseTokenTransfer` transaction to `rlp_execute` targeting another eth-implicit account with `address_check: Some(address)`, attaching a nonzero deposit representing the Wei value (`CallerDeposit::new` will populate `Some` because `predecessor_account_id != current_account_id`) — see `inner_rlp_execute` dispatch: [7](#0-6) .
3. Configure/force the `address_registrar.lookup` call to fail (e.g., insufficient gas via a low `REGISTRAR_LOOKUP_GAS` budget, or point the registrar at a non-existent/broken account).
4. Observe `address_check_callback` executes with `PromiseResult::Failed`, returns `ExecuteResponse { success: false, ... }`, and no transfer receipt is created back to the relayer.
5. Compare balances before/after: the relayer's attached deposit is retained by the wallet contract, unlike the analogous failure path in `rlp_execute_callback` (verified in the existing `test_caller_refunds` test, which only exercises the terminal-callback refund path) [8](#0-7) .

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );
