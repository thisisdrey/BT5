### Title
Missing bounds validation of `Contract.type` before indexing the 32-byte permission `operations` bitmap allows a single crafted transaction to crash node transaction/signature processing - (File: `actuator/src/main/java/org/tron/core/utils/TransactionUtil.java`, `chainbase/src/main/java/org/tron/common/utils/WalletUtil.java`, `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java`)

### Summary
The pam_access flaw (CVE-2024-10963) stems from an access-control decision being made on an input value that was never confirmed to be inside the domain the rule author intended (a "hostname" that was actually something else). The java-tron analog is `checkPermissionOperations`, used to decide whether a transaction's Active permission allows a given contract type: it blindly derives a bit index from the untrusted, attacker-controlled `Contract.type` wire value and uses it to index into a fixed 32-byte (256-bit) `operations` bitfield — without ever checking that the derived index is within `[0,256)`. The only code that constrains contract-type indices to `[0,256)` is `AccountPermissionUpdateActuator.checkPermission` (which validates the *stored* `operations` bitmap when a permission is created), but the runtime authorization check that consumes `contract.getTypeValue()` performs no such validation.

### Finding Description
`checkPermissionOperations` computes: [1](#0-0) 

The identical logic exists in `TransactionUtil.checkPermissionOperations`: [2](#0-1) 

Both call sites read `contract.getTypeValue()` — the raw protobuf wire integer for the `Contract.type` field. Protocol Buffers proto3 enums are "open": any int32 can be placed on the wire for an enum field; `getType()` maps unrecognized numbers to `UNRECOGNIZED`, but `getTypeValue()` returns the raw, attacker-chosen integer unchanged. Nothing in `checkPermissionOperations` validates that this value lies in `[0,255]` before computing `operations.byteAt(contractType / 8)` on a `ByteString` that is guaranteed to be exactly 32 bytes. A `contractType` of 256 or greater (e.g. 1000) produces `byteAt(125)`, which is out of bounds for a 32-byte `ByteString` and throws an unchecked `IndexOutOfBoundsException`.

This routine is invoked from the core signature/permission verification path used by every transaction that specifies a non-zero `permissionId` (i.e., uses a multi-sig Active permission): [3](#0-2) 
which is called from `validateSignature`: [4](#0-3) 
and ultimately from `validatePubSignature`, whose catch clauses are narrowly scoped to `SignatureException | PermissionException | SignatureFormatException` and do **not** catch `IndexOutOfBoundsException`: [5](#0-4) 

The only place in the codebase that enforces the intended `[0,256)` domain for contract-type indices is the permission-creation validator, which is a separate, one-time check on the *stored* 32-byte `operations` field when a user configures their own multi-sig permission via `AccountPermissionUpdateActuator`: [6](#0-5) 
That check bounds only the *stored* bitmap's bit positions against `i < 256`; it says nothing about the *transaction-supplied* `contractType` used later at verification time, which is exactly the "config token treated as trusted without confirming its actual type/range" mismatch analogous to pam_access misinterpreting a rule token as a hostname.

### Impact Explanation
An account that has configured a multi-sig Active permission (a normal, unprivileged self-service operation via `AccountPermissionUpdateContract`) can craft and sign a transaction whose `Contract.type` wire value is an out-of-range integer (>= 256) while referencing that Active `permissionId`. When any node (including the node broadcasting/validating/applying the block) performs signature/permission verification for that transaction, `checkPermissionOperations` throws an uncaught `IndexOutOfBoundsException` inside `TransactionCapsule.checkPermission`/`validateSignature`, which is not handled by the narrow catch clauses in `validatePubSignature`. This can abort transaction/block processing with an unhandled runtime exception, i.e. a remotely triggerable node crash or halt from a single signed transaction — matching the "node crash or halt" impact class permitted by the rules.

### Likelihood Explanation
High reachability: any unprivileged account can enable multi-sig (`AccountPermissionUpdateActuator`) and then submit one specially crafted transaction via the normal broadcast path. The only precondition is having any Active permission with `permissionId != 0`, which is trivial self-configuration. Constructing a `Contract` protobuf with an out-of-range `type` wire value is straightforward since proto3 enum fields do not validate range at parse time.

### Recommendation
In `checkPermissionOperations` (both copies in `TransactionUtil.java` and `WalletUtil.java`), validate `contractType` is within `[0, 255]` (i.e., `contractType >= 0 && contractType < operations.size() * 8`) before computing `operations.byteAt(contractType / 8)`, returning `false`/throwing a `PermissionException` for out-of-range values instead of allowing an unchecked exception to propagate. Additionally, widen the catch clause in `TransactionCapsule.validatePubSignature` (and equivalent callers in `Wallet.java`/`TransactionUtil.java`) to catch generic `RuntimeException` around permission/signature validation so that malformed transaction fields fail gracefully as invalid transactions rather than crashing the node.

### Proof of Concept
1. Attacker account `A` calls `AccountPermissionUpdateContract` to add an Active permission with `permissionId = 2` and a valid 32-byte `operations` bitmap (normal, in-scope operation) — see validator at [7](#0-6) .
2. Attacker builds a `Transaction` whose single `Contract` sets `permission_id = 2` and manually writes the `type` field's wire value to an out-of-range integer (e.g., 1000) instead of a valid `ContractType` enum constant — permitted because proto3 enum wire encoding accepts arbitrary int32 values.
3. Attacker signs the transaction with enough weight to satisfy the Active permission's threshold and broadcasts it via `Wallet.broadcastTransaction` / gRPC `BroadcastTransaction`.
4. During permission verification, `TransactionCapsule.validateSignature` → `checkPermission` → `checkPermissionOperations` computes `operations.byteAt(1000/8 = 125)` on a 32-byte `ByteString`, throwing `IndexOutOfBoundsException`, which is not caught by `validatePubSignature`'s narrow catch list and propagates up through transaction/block processing.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }

  private boolean checkPermission(Permission permission) throws ContractValidateException {
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (permission.getKeysCount() > dynamicStore.getTotalSignNum()) {
      throw new ContractValidateException("number of keys in permission should not be greater "
          + "than " + dynamicStore.getTotalSignNum());
    }
    if (permission.getKeysCount() == 0) {
      throw new ContractValidateException("key's count should be greater than 0");
    }
    if (permission.getType() == PermissionType.Witness && permission.getKeysCount() != 1) {
      throw new ContractValidateException("Witness permission's key count should be 1");
    }
    if (permission.getThreshold() <= 0) {
      throw new ContractValidateException("permission's threshold should be greater than 0");
    }
    String name = permission.getPermissionName();
    if (!StringUtils.isEmpty(name) && name.length() > 32) {
      throw new ContractValidateException("permission's name is too long");
    }
    //check owner name ?
    if (permission.getParentId() != 0) {
      throw new ContractValidateException("permission's parent should be owner");
    }

    long weightSum = 0;
    List<ByteString> addressList = permission.getKeysList()
        .stream()
        .map(x -> x.getAddress())
        .distinct()
        .collect(toList());
    if (addressList.size() != permission.getKeysList().size()) {
      throw new ContractValidateException(
          "address should be distinct in permission " + permission.getType());
    }
    for (Key key : permission.getKeysList()) {
      if (!DecodeUtil.addressValid(key.getAddress().toByteArray())) {
        throw new ContractValidateException("key is not a validate address");
      }
      if (key.getWeight() <= 0) {
        throw new ContractValidateException("key's weight should be greater than 0");
      }
      try {
        weightSum = addExact(weightSum, key.getWeight());
      } catch (ArithmeticException e) {
        throw new ContractValidateException(e.getMessage());
      }
    }
    if (weightSum < permission.getThreshold()) {
      throw new ContractValidateException(
          "sum of all key's weight should not be less than threshold in permission " + permission
              .getType());
    }

    ByteString operations = permission.getOperations();
    if (permission.getType() != PermissionType.Active) {
      if (!operations.isEmpty()) {
        throw new ContractValidateException(
            permission.getType() + " permission needn't operations");
      }
      return true;
    }
    //check operations
    if (operations.isEmpty() || operations.size() != 32) {
      throw new ContractValidateException("operations size must 32");
    }

    byte[] types1 = dynamicStore.getAvailableContractType();
    for (int i = 0; i < 256; i++) {
      boolean b = (operations.byteAt(i / 8) & (1 << (i % 8))) != 0;
      boolean t = ((types1[(i / 8)] & 0xff) & (1 << (i % 8))) != 0;
      if (b && !t) {
        throw new ContractValidateException(i + " isn't a validate ContractType");
      }
    }
    return true;
