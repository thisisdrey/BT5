Audit Report

## Title
Missing zero-address check in Snowbridge `CreateAsset` payload lets an attacker register an ERC‑20 ForeignAsset that collides with the native-ETH sentinel, corrupting `UnlockNativeToken` accounting - (File: `bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs`)

## Summary
`MessageToXcm::prepare` validates that the Ethereum-supplied token address is non-zero for the `EthereumAsset::NativeTokenERC20` branch, but performs no equivalent check for `Payload::CreateAsset`, which is routed to `make_create_asset_xcm`. This asymmetry lets an attacker cause AssetHub to register a `ForeignAssets` entry at `Location::new(2, [GlobalConsensus(Ethereum), AccountKey20 { key: [0;20] }])`, which is bit-for-bit the same address used as the sentinel for native Ether throughout the outbound converters.

## Finding Description
In `bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs`, the `prepare` function dispatches `Payload::CreateAsset { token, network }` directly to `Self::make_create_asset_xcm` with no zero-address guard: [1](#0-0) 

By contrast, the sibling `EthereumAsset::NativeTokenERC20` branch in the same function explicitly rejects `token_id == H160::zero()` before constructing a token `Location`: [2](#0-1) 

`make_create_asset_xcm` unconditionally builds `asset_id = Location::new(2, [GlobalConsensus(Ethereum), AccountKey20 { key: (*token).into() }])` and issues `Transact` calls that create this as a `ForeignAssets` entry with Ethereum set as its reserve — with no rejection of `token == H160::zero()`: [3](#0-2) 

On the return path, `extract_ethereum_native_assets` in the outbound v2 converter matches `(0, [AccountKey20 { network, key }])` (a token-specific ERC-20 location, evaluated in Ethereum's own context after reanchoring) and separately treats `(0, [])` as the "native Ether" sentinel producing `H160([0;20])`: [4](#0-3) 

Because the `AccountKey20{key}` match extracts `H160(*key)` directly regardless of whether `key` happens to be `[0;20]`, a ForeignAsset registered via `CreateAsset { token: H160::zero(), .. }` — once reanchored to Ethereum's own context for the outbound leg — collapses to the exact same `H160([0;20])` value produced for genuine native Ether transfers, resulting in `Command::UnlockNativeToken { token: H160([0;20]), .. }` regardless of whether the underlying transfer was of the bogus registered asset or real Ether. This mirrors the same sentinel-collision pattern documented for the v1 converter, which explicitly notes that an empty `AccountKey20` junction "signals to the gateway ... a native Ether transfer by using `0x000...0`": [5](#0-4)  and the v1 test explicitly confirms Solidity interprets token `0x0` as ETH: [6](#0-5) 

The existing guard in the `NativeTokenERC20` branch demonstrates the fix pattern was known to the authors, but it was not applied to `make_create_asset_xcm`, confirming the gap is a real oversight rather than an intentional design choice.

## Impact Explanation
This breaks the invariant that a bridge command must bind to exactly one, correctly-identified asset: a `ForeignAssets` balance nominally denominated in an ERC-20 at address `0x0` can be withdrawn from AssetHub and, via `UnlockNativeToken { token: H160([0;20]) }`, cause the Gateway/agent contract on Ethereum to release real native ETH instead of a (nonexistent) ERC-20 transfer. This is an unbacked/misrouted unlock of bridge-held Ether funds and a corruption of AssetHub's `ForeignAssets` ledger relative to the true Ethereum-side reserves, matching the "theft or unbacked mint or unlock" and "runtime bugs that compromise intended behavior" impact categories for BridgeHub/Snowbridge code.

## Likelihood Explanation
Triggering the vulnerable code path only requires an inbound message with `Payload::CreateAsset { token: H160::zero(), network: Polkadot }` to be relayed with the standard header/receipt proof through `EthereumInboundQueueV2::process_message` → `MessageToXcm::prepare`. No relayer collusion, governance action, or validator/collator compromise is needed on the Substrate side; the vulnerability is purely a missing input-validation check in the message-to-XCM conversion logic that any correctly-proven inbound message can reach. Note: this repository does not contain the Solidity Gateway contract source, so whether the Ethereum-side `registerToken`-style entry point itself permits registering `address(0)` could not be independently verified here; however, the Rust-side code shown has no defense against this input regardless of Ethereum-side behavior, and the asymmetric validation compared to the adjacent `NativeTokenERC20` branch is a genuine, verifiable code defect in-scope for this repository.

## Recommendation
Add the same guard used for `NativeTokenERC20` to the `CreateAsset` path: reject `token == H160::zero()` in `make_create_asset_xcm` (or in `prepare` before dispatching to it), returning `ConvertMessageError::InvalidAsset`. Additionally, audit all other locations deriving `AccountKey20 { key: token }` from Ethereum-supplied token addresses (inbound and outbound, v1 and v2) to consistently forbid the zero-address sentinel from aliasing to any specific ERC-20/PNA asset identity.

## Proof of Concept
1. Craft/relay an inbound v2 message with `Payload::CreateAsset { token: H160::zero(), network: Network::Polkadot }` and a legitimate header/receipt proof.
2. `EthereumInboundQueueV2::process_message` calls `MessageToXcm::prepare`, which calls `make_create_asset_xcm(token: &H160::zero(), ...)` — no rejection occurs, unlike the `ensure!(*token_id != H160::zero(), ...)` check a few lines above for `NativeTokenERC20`.
3. AssetHub creates a `ForeignAssets` entry at `Location::new(2, [GlobalConsensus(Ethereum), AccountKey20 { key: [0;20] }])` with Ethereum set as its reserve (via the `Transact` calls in `make_create_asset_xcm_for_polkadot`).
4. Obtain a balance of this asset and transfer it back to Ethereum via `InitiateTransfer`/`ReserveWithdraw`.
5. The outbound v2 converter's `extract_ethereum_native_assets` matches the reanchored `(0, [AccountKey20 { key: [0;20] }])` location and emits `Command::UnlockNativeToken { token: H160([0;20]), recipient, amount }` — identical in shape to the command for real native ETH transfers — which a unit test asserting this collision (mirroring the existing v1 test at `bridges/snowbridge/primitives/outbound-queue/src/v1/converter/tests.rs:534-542`) would confirm.
