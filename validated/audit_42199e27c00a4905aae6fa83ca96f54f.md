## Title
Multisig Weight Double-Counting via Signature Malleability in `ValidateMultiSign` TVM Precompile Bypasses Threshold Authorization - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

## Summary
The `ValidateMultiSign` precompiled contract, exposed to any smart contract on TRON at address `0x...0a`, is the canonical on-chain primitive contracts use to check whether an m-of-n TRON account `Permission` threshold has been satisfied. Its duplicate-signature guard rejects only byte-for-byte identical signatures per recovered address, not different-but-valid signatures produced by the same private key (classic ECDSA signature malleability). This lets a single key holder submit two distinct valid signatures over the same hash and have that key's weight counted twice, satisfying a threshold that is supposed to require multiple independent signers — an authentication bypass reachable from any contract call, analogous to the referenced CVE's "alternate path" bypass where a secondary authentication route enforces weaker checks than the primary one.

## Finding Description
`ValidateMultiSign.execute` iterates the caller-supplied `signatures` array, recovers the signer address for each entry, and accumulates `Permission` key weights toward `totalWeight`: [1](#0-0) 

The de-duplication logic only skips an entry when the *exact merged bytes* (`recoveredAddr` + raw `sign`) were already seen; if the same address recurs with different signature bytes, it falls through to `MUtil.checkCPUTime()` and then still adds the weight again via `TransactionCapsule.getWeight(permission, recoveredAddr)`: [2](#0-1) 

Because ECDSA signatures are malleable — for a valid `(r, s, v)` the pair `(r, n-s, v^1)` is also a valid signature that recovers to the *same address* — an attacker holding a single private key can trivially construct a second, byte-different signature over the identical hash and pass both in the `signatures` array. Each is treated as evidence of a distinct approver.

This is inconsistent with the canonical on-chain transaction signing path, `TransactionCapsule.checkWeight`, which correctly de-duplicates by recovered **address** (not exact bytes), explicitly rejecting a repeated signer with `"has signed twice!"`: [3](#0-2) 

The signature-recovery routine used by the precompile confirms nothing constrains `s`/`v` to a canonical form, so malleable variants are accepted as-is: [4](#0-3) 

Thus, the primary transaction-authorization channel (`TransactionCapsule.checkWeight`, used for `broadcastTransaction`) enforces per-address dedup, while the alternate authorization channel reachable from within smart contracts (`ValidateMultiSign` precompile) enforces only per-signature-bytes dedup — allowing the same underlying signer to be double-counted through this alternate path.

## Impact Explanation
Any smart contract (custodial wallet, vault, bridge, DAO executor, etc.) that gates a privileged operation on `ValidateMultiSign` returning success for a configured `Permission` threshold can have that gate satisfied by fewer distinct key holders than intended — in the limit, a single compromised or malicious signer submitting duplicate malleable signatures can reach a 2x (up to `MAX_SIZE`=5x) weight multiplier. This is a direct authorization/authentication bypass of the multisig guarantee that TRON's `Permission`/`ValidateMultiSign` mechanism is designed to provide, enabling unauthorized account operations or theft of funds in any contract relying on this precompile for m-of-n approval.

## Likelihood Explanation
`ValidateMultiSign` is reachable by any address once `VMConfig.allowTvmSolidity059()` is enabled (a mainnet-active feature), via a plain contract call from any unprivileged account — no special privileges, node access, or SR/witness role required. The exploit requires only ordinary ECDSA algebra (negating `s` modulo the curve order and flipping the recovery id), which is trivial and well-documented.

## Recommendation
Change the de-duplication check in `ValidateMultiSign.execute` to key strictly on `recoveredAddr` (mirroring `TransactionCapsule.checkWeight`), rejecting or ignoring any second signature that recovers to an address already counted, regardless of whether the raw signature bytes differ.

## Proof of Concept
1. Configure an account with an `Active` permission containing two keys, `key1` and `key2`, each weight 1, threshold 2 — the intended semantics require **both** keys to approve.
2. Attacker controls only `key1`. Attacker signs `hash` with `key1` to get signature `A = (r, s, v)`.
3. Attacker derives the malleable counterpart `B = (r, n - s, v ^ 1)`, which is also a valid signature over `hash` recovering to the same `key1` address (standard secp256k1 malleability).
4. Attacker calls the `ValidateMultiSign` precompile with `signatures = [A, B]`:
   - Iteration for `A`: `recoveredAddr = key1`, not yet in `executedSignList`; `weight += 1`.
   - Iteration for `B`: `recoveredAddr = key1` again; `matrixContains(executedSignList, recoveredAddr)` is true, but `matrixContains(executedSignList, merge(recoveredAddr, B))` is false (different signature bytes) — so the code does **not** `continue`; it falls through and adds `weight += 1` again.
   - `totalWeight = 2 >= threshold(2)` → precompile returns `true` (`dataOne()`), despite only `key1` having actually approved.
5. Any calling contract relying on this result as proof of the "2-of-2" approval is deceived into treating a single-key approval as fully authorized, bypassing the intended multi-party authentication check.
