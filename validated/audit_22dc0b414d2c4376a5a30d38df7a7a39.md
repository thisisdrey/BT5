### Title
Multisig Weight Double-Counting via ECDSA Signature Malleability in `ValidateMultiSign` Precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompile (invoked via the `validateMultiSign` opcode, reachable from any deployed contract or contract call) deduplicates recovered signers by exact signature bytes rather than by recovered address alone, before falling through to add weight. Because ECDSA signatures are malleable (a signature `(r,s)` and `(r, n-s)` with adjusted recovery id both recover the same address for the same message hash), an attacker can submit two different-looking signatures produced from a single private key and have that single signer's weight counted twice toward a multisig `threshold`. This mirrors the reported bug class (a credential intended to be accepted/consumed exactly once being accepted multiple times due to insufficient canonicalization before the uniqueness check).

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute()`: [1](#0-0) 

```java
long totalWeight = 0L;
List<byte[]> executedSignList = new ArrayList<>();
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);

  sign = merge(recoveredAddr, sign);
  if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
      continue;
    }
    MUtil.checkCPUTime();
  }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  if (weight == 0) {
    return Pair.of(true, DATA_FALSE);
  }
  totalWeight += weight;
  executedSignList.add(sign);
  executedSignList.add(recoveredAddr);
}
```

The intended invariant is "each distinct signer contributes weight at most once." The code attempts to enforce this by tracking `recoveredAddr` values already seen. However, the "already seen" branch only `continue`s (skips adding weight again) when the **exact byte sequence** `merge(recoveredAddr, sign)` was already recorded. If the address has been seen before but the raw signature bytes differ (as happens with a malleable variant of the same signature), the code does **not** skip; it merely calls `MUtil.checkCPUTime()` (a CPU-time throttling guard against DoS, unrelated to authorization) and falls through to add `weight` to `totalWeight` again.

Since standard secp256k1 ECDSA signatures are malleable — `(r, s)` and `(r, n - s)` (with the recovery id flipped accordingly) both validly verify against the same public key/hash — a holder of a single private key that is a party to a multisig `Permission` can derive a second, byte-distinct signature for the exact same hash and have `TransactionCapsule.getWeight(permission, recoveredAddr)` counted twice. This lets one real approver satisfy a `permission.getThreshold()` that was configured to require multiple independent co-signers.

Compare this to `TransactionCapsule.checkWeight()` (used for consensus-level transaction signature validation), which explicitly rejects a second signature from the same recovered address ("has signed twice!"), regardless of raw signature bytes: [2](#0-1) 

The `ValidateMultiSign` precompile diverges from that correct, address-keyed dedup semantics by additionally gating on exact signature byte equality, re-introducing the malleability class of bug.

### Impact Explanation
`validateMultiSign` is a general-purpose TVM precompile that any deployed smart contract can call to gate privileged logic (e.g., "release funds only if M-of-N co-signers approved this action hash"). If a contract relies on this precompile to enforce that a threshold number of *distinct* keys signed off, an attacker controlling only one of the required keys can forge a threshold pass using two malleable variants of that single key's signature, executing the gated logic without the required additional approvers. Depending on the calling contract's design, this can result in unauthorized fund transfers or unauthorized privileged operations that were meant to require multiple independent approvals — a concrete violation of an authorization invariant reachable purely from a contract call by an unprivileged party (Medium/High impact depending on downstream contract logic, satisfying "unauthorized account operation"/"theft of funds" categories).

### Likelihood Explanation
Exploitation requires no special privileges: any account can deploy or call a contract that invokes `validateMultiSign`, and the attacker needs to control only one of the keys in the targeted `Permission`. Deriving a valid malleable ECDSA signature variant from an existing `(r,s,v)` triple is a pure, well known, cheap computation (`s' = n - s`, flip `v`); no private key material beyond ordinary signing is needed. The precondition — a contract that uses `validateMultiSign` with a `threshold > 1` permission and passes attacker/controlled signature arrays directly through — is realistic given this precompile exists specifically to let contracts implement multisig-style co-authorization.

### Recommendation
In `PrecompiledContracts.ValidateMultiSign.execute()`, deduplicate strictly by `recoveredAddr` (skip weight accumulation whenever the address was already counted), matching the semantics already used in `TransactionCapsule.checkWeight()`, instead of allowing a fallthrough to double-count weight when only the raw signature bytes differ.

### Proof of Concept
1. Deploy/target a contract account with an Active permission requiring `threshold = 2`, containing two keys `K1` (attacker-controlled) and `K2` (victim/other-approver), each with weight 1.
2. Attacker signs the action hash `toSign` once with `K1`, obtaining `(r, s, v)`.
3. Attacker computes the malleable counterpart `(r, n - s, v')` (flip parity bit), which recovers to the same address as `K1` under `recoverAddrBySign`.
4. Attacker calls the `validateMultiSign` precompile (e.g., via a TVM contract) supplying `signatures = [sig1, sig1']` — no signature from `K2` at all.
5. In the loop: first iteration recovers `K1`'s address, adds weight 1, records `merge(K1,sig1)`. Second iteration recovers the same `K1` address again (since `matrixContains(executedSignList, K1_addr)` is true) but `merge(K1,sig1')` is not equal to the previously stored entry, so the code does **not** `continue` — it calls `MUtil.checkCPUTime()` and adds weight 1 again, for a `totalWeight` of 2, satisfying `threshold = 2` and returning `DataWord.ONE()` even though only one real signer (`K1`) ever participated.

      throws SignatureException, PermissionException, SignatureFormatException {
    long currentWeight = 0;

      throw new PermissionException(
          "Signature count is " + (sigs.size()) + " more than key counts of permission : "
              + permission.getKeysCount());

    HashMap addMap = new HashMap();
    for (ByteString sig : sigs) {
      if (sig.size() < 65) {
        throw new SignatureFormatException(
            "Signature size is " + sig.size());

      String base64 = TransactionCapsule.getBase64FromByteString(sig);
      byte[] address = SignUtils
          .signatureToAddress(hash, base64, CommonParameter.getInstance().isECKeyCryptoEngine());
      long weight = getWeight(permission, address);
      if (weight == 0) {
        throw new PermissionException(
            ByteArray.toHexString(hash) + " is signed by " + encode58Check(address)

      }
      if (ForkController.instance().pass(Parameter.ForkBlockVersionEnum.VERSION_4_7_1)) {
        base64 = encode58Check(address);
      }
      if (addMap.containsKey(base64)) {
        throw new PermissionException(encode58Check(address) + " has signed twice!");

      if (approveList != null) {
        approveList.add(ByteString.copyFrom(address)); //out put approve list.
      }

    }

  }
