### Title
A stale oracle price on any held token permanently reverts `Pool.liquidate`, blocking re-collateralization and trapping bad debt - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to the f(x) `TreasuryV2.mintXToken` finding — where a recovery action reverts on an invalid oracle price — Metronome's liquidation path unconditionally quotes USD prices for **every** debt token and deposit token in the account's lists inside `debtPositionOf`. If any single `IMasterOracle` quote reverts (stale pull-oracle price, feed halted), `Pool.liquidate` reverts entirely. Liquidation is the protocol's only re-collateralization mechanism, so positions become unliquidatable exactly when the oracle is degraded — the same liveness failure class.

### Finding Description
`Pool.liquidate` calls `debtPositionOf(account_)` to check health:

- `debtPositionOf` → `debtOf` iterates `debtTokensOfAccount` and calls `masterOracle().quoteTokenToUsd(...)` for each (`Pool.sol:227-237`).
- `debtPositionOf` → `depositOf` iterates `depositTokensOfAccount` and calls `masterOracle().quoteTokenToUsd(underlying, balance)` for each (`Pool.sol:274-288`).
- `liquidate` reverts if `debtPositionOf` reverts or reports healthy (`Pool.sol:559-563`), and also calls `quoteLiquidateOut` which again quotes the synthetic/collateral pair (`Pool.sol:581`, `456-460`).

There is no fallback pricing, no try/catch, and no way to liquidate using a conservative price. The deployed `MasterOracle` uses push/pull feeds (Chainlink/Pyth/RedStone per the E2E tests, which show `revertedWith('price-too-behind')` / `'invalid-token-price'` when prices lapse). Two reachable triggers:

1. **Natural staleness**: any configured feed lapses → every account holding that collateral or synth debt is unliquidatable for the entire stale window, including already-underwater positions.
2. **Attacker-forced staleness dependency**: `DepositToken` transfers call `Pool.addToDepositTokensOfAccount`, so an unprivileged attacker can dust-transfer a victim a `DepositToken` whose underlying has the most fragile/halted feed. `MAX_TOKENS_PER_USER` bounds count, not feed health, and `addToDepositTokensOfAccount` has no oracle check (`Pool.sol:216-220`). From then on the victim's `liquidate` always reverts in `depositOf`, so the attacker can let the position decay (e.g., crash the other collateral on a DEX, or wait for interest accrual) into unrecoverable bad debt while no liquidator can act.

### Impact Explanation
Protocol insolvency / liveness failure. The exact invariant that breaks is liquidation liveness: unhealthy positions must always be liquidatable. When a feed is stale, `liquidate` reverts 100% of the time for affected accounts, bad debt accrues interest, and the loss is socialized across synth holders. In the dust-griefing variant the attacker chooses which positions become permanently unliquidatable, then profits by shorting the synth or pushing the collateral price down externally.

### Likelihood Explanation
Likelihood is moderate: stale-price windows happen routinely on pull-oracle deployments (the repo's own E2E tests rely on this behavior), and the dust-transfer attack requires only a deposit token transfer — no privileged role, no governance action. `whenNotShutdown`/`nonReentrant` do not help; the revert is inside the oracle quote loop itself.

### Recommendation
- Make liquidation paths resilient to individual feed failures: e.g., skip or conservatively price collaterals whose oracle reverts inside `depositOf`/`debtOf` when invoked from `liquidate`, or provide a `liquidate` variant using only the specific `syntheticToken_`/`depositToken_` pair with a staleness-bounded but non-reverting quote.
- Add a check in `addToDepositTokensOfAccount` (or in `DepositToken.transfer`) to prevent adding tokens whose oracle is currently stale, and add invariant tests asserting `liquidate` succeeds for underwater positions even when unrelated feeds are down — mirroring the "actions that should never fail" recommendation from the reference report.

### Proof of Concept
Foundry fork sketch:

```solidity
// Setup: alice deposits msdVaUSDC, issues msUSD (healthy).
msdVaUSDC.deposit(1000e18, alice);
msUSDDebt.issue(500e18, alice);

// Attacker dust-transfers a DepositToken whose feed goes stale.
// Attacker first obtains dust of msdVaETH themselves, then:
msdVaETH.transfer(alice, 1);  // adds msdVaETH to alice's list

// Oracle for vaETH underlying goes stale (push feed missed heartbeat /
// pull price expired). masterOracle.quoteTokenToUsd(vaETH, ...) reverts.

// Alice's collateral crashes -> position underwater.
masterOracleHarness.setStale(vaETH);

// Any liquidator call reverts inside depositOf -> PositionIsHealthy check
// never reached; debt cannot be repaid.
vm.expectRevert(); // e.g. "price-too-behind" / invalid-token-price
pool.liquidate(msUSD, alice, 100e18, msdVaUSDC);
```

Same failure via natural staleness on mainnet deployment: warp past the feed heartbeat for any asset present in a borrower's lists, drop their other collateral's price below the collateral factor, and observe `liquidate` reverting for the whole stale window while interest accrues.
