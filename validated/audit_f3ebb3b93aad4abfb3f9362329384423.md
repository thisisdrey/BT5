### Title
Missing `chain_id` in `SignerCapabilityOfferProofChallengeV2` Enables Cross-Chain Replay of Signer Capability Delegation — (`File: aptos-move/framework/aptos-framework/sources/account/account.move`)

---

### Summary

`SignerCapabilityOfferProofChallengeV2`, the proof-of-intent struct signed by an account owner when calling `offer_signer_capability`, omits `chain_id` from its signed fields. The sister struct `RotationCapabilityOfferProofChallengeV2` was explicitly upgraded to include `chain_id` with a comment stating it "prevents replaying the challenge message," but the signer-capability variant was never given the same fix. A signature produced on one Aptos network (e.g., testnet) is therefore valid on any other Aptos network (e.g., mainnet) whenever the victim's account sequence number matches, allowing an attacker to replay the delegation and obtain an authorized signer for the victim's mainnet account without the victim's consent.

---

### Finding Description

`RotationCapabilityOfferProofChallengeV2` explicitly binds the signed message to a specific chain:

```move
struct RotationCapabilityOfferProofChallengeV2 has drop {
    chain_id: u8,          // ← present
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
```

The inline comment reads: *"This V2 struct adds the `chain_id` and `source_address` to the challenge message, which prevents replaying the challenge message."* [1](#0-0) 

`SignerCapabilityOfferProofChallengeV2`, used in the live `offer_signer_capability` entry function, is missing `chain_id`:

```move
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
    // ← NO chain_id
}
``` [2](#0-1) 

`offer_signer_capability` constructs and verifies this struct:

```move
let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
    sequence_number: get_sequence_number(source_address),
    source_address,
    recipient_address,
};
verify_signed_message(
    source_address, account_scheme, account_public_key_bytes,
    signer_capability_sig_bytes, proof_challenge);
``` [3](#0-2) 

`verify_signed_message` uses `signature_verify_strict_t`, which prepends the Move TypeInfo (module address `0x1`, module name `account`, struct name `SignerCapabilityOfferProofChallengeV2`) as a domain separator. Because `0x1` is the framework address on **every** Aptos network, this TypeInfo prefix provides no chain binding. [4](#0-3) 

The e2e test confirms the struct layout used for signing contains no `chain_id` field:

```rust
struct SignerCapabilityOfferProofChallengeV2 {
    account_address: AccountAddress,   // 0x1 — same on all chains
    module_name: String,
    struct_name: String,
    sequence_number: u64,
    source_address: AccountAddress,
    recipient_address: AccountAddress,
}
``` [5](#0-4) 

---

### Impact Explanation

`offer_signer_capability` stores the recipient address in the victim's `signer_capability_offer`. Any account holding that offer can call `create_authorized_signer` to obtain a live `signer` for the victim's account. With that signer the attacker can transfer APT, fungible assets, rotate the authentication key, or perform any other privileged operation on behalf of the victim — constituting direct, unauthorized theft or reassignment of user-controlled on-chain assets.

---

### Likelihood Explanation

The precondition is that the victim's account has the same sequence number on two different Aptos networks at the time of the replay. This is realistic because:

1. Many users create accounts on testnet/devnet for testing before mainnet deployment, often starting at sequence number 0.
2. A recipient (Bob) who was legitimately granted signer capability on testnet can replay the same signature on mainnet when Alice's mainnet account reaches the same sequence number.
3. The attacker does not need to intercept anything — the victim may have published the signature themselves (e.g., in a public transaction on testnet).

---

### Recommendation

Add `chain_id: u8` to `SignerCapabilityOfferProofChallengeV2` and populate it from `chain_id::get()` inside `offer_signer_capability`, exactly as `RotationCapabilityOfferProofChallengeV2` already does:

```move
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    chain_id: u8,          // add this
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
```

```move
let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
    chain_id: chain_id::get(),   // add this
    sequence_number: get_sequence_number(source_address),
    source_address,
    recipient_address,
};
```

This is a breaking change to the signed message format; existing off-chain tooling that constructs this signature must be updated accordingly.

---

### Proof of Concept

**Setup:** Alice has address `0xALICE` on both testnet (chain_id=2) and mainnet (chain_id=1). Her testnet account is at sequence number 5. Her mainnet account is also at sequence number 5 (e.g., she has sent exactly 5 transactions on mainnet).

**Step 1 — Obtain a testnet signature (legitimately or by observation):**

Alice signs a `SignerCapabilityOfferProofChallengeV2` on testnet to grant Bob (`0xBOB`) signer capability:

```
signed_bytes = sign({
    TypeInfo(0x1::account::SignerCapabilityOfferProofChallengeV2),
    sequence_number: 5,
    source_address: 0xALICE,
    recipient_address: 0xBOB,
})
```

**Step 2 — Replay on mainnet:**

Bob (or any observer who captured the signature) submits the following transaction on **mainnet**:

```
0x1::account::offer_signer_capability(
    signer_capability_sig_bytes = <Alice's testnet signature>,
    account_scheme = 0,
    account_public_key_bytes = <Alice's public key>,
    recipient_address = 0xBOB
)
```

Because `SignerCapabilityOfferProofChallengeV2` contains no `chain_id`, the BCS-serialized message is byte-for-byte identical on both networks. `verify_signed_message` passes, and Alice's mainnet `signer_capability_offer` is set to `0xBOB`.

**Step 3 — Exploit:**

Bob calls `create_authorized_signer(&bob, 0xALICE)` on mainnet, receives a `signer` for Alice's mainnet account, and drains her assets.
