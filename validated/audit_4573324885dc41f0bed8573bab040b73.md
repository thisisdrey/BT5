This confirms the mechanism: `priority_queue` (`BTreeSet<TransactionPriorityId>`) only holds `Unprocessed`/held transaction ids; once a transaction is popped and scheduled, it moves to `Pending` state and is removed from `priority_queue` while remaining counted toward `buffer_size` (`id_to_transaction_state.len()`, per the module doc: "the container maintains a fixed capacity" measured on the slab, not just the queue). `get_min_max_priority()` reads only the `priority_queue` (`BTreeSet`), so it returns `None` when that set is empty even though the buffer (slab) is still saturated with in-flight `Pending` transactions.

### Title
Scheduler priority floor silently disables anti-spam protection when the buffer is saturated by in-flight (scheduled) transactions - ([File: core/src/banking_stage/transaction_scheduler/scheduler_controller.rs])

### Summary
`update_scheduler_priority_floor` computes the anti-spam priority floor from `self.container.get_min_max_priority()`, which only inspects `TransactionStateContainer::priority_queue` [1](#0-0) [2](#0-1) . When that queue is empty but the container's buffer capacity is still saturated by transactions that have been popped into `Pending`/in-flight worker state (which "still occupy buffer space until workers finish them" per the code comment) [3](#0-2) , `get_min_max_priority()` returns `None`, and the floor is set to `0` instead of a meaningful minimum [4](#0-3) . A published floor of `0` disables the sigverify-side drop check entirely, because sigverify only applies the floor when `floor > 0` [5](#0-4) .

### Finding Description
The scheduler publishes a `SchedulerPriorityFloor` used by `SigVerifyStage` to drop "at-or-below-floor" packets before costly signature verification, specifically intended to protect the validator when its buffer is saturated [6](#0-5) [7](#0-6) . The floor computation logic is:

```
let priority_floor = if saturated {
    self.container.get_min_max_priority().map_or(0, |(min, _)| min)
} else {
    0
};
``` [8](#0-7) 

`saturated` is computed from `buffer_size()`, which is documented to include scheduled/in-flight transactions still occupying slots, not just queued ones [3](#0-2) . However, `get_min_max_priority()` only examines `priority_queue: BTreeSet<TransactionPriorityId>` [1](#0-0) , and per the module doc, once a transaction is popped by the scheduler and transitions to `Pending`, "the associated `TransactionId` is not in the queue, but is still in the map" [9](#0-8) . Therefore it is possible for the buffer to be at or above the saturation watermark (triggering `saturated = true`) while the `priority_queue` itself is empty (e.g., all currently-buffered transactions have been dispatched to workers and are `Pending`). In that state `get_min_max_priority()` returns `None`, `map_or(0, ...)` yields `0`, and the published floor becomes `0`.

Because sigverify only enforces the floor when `floor > 0` [5](#0-4) , a floor of `0` is functionally identical to "no floor" — the exact opposite of the intended behavior during saturation. This mirrors the reported bug class precisely: a pricing/threshold function (`getPrice()`/priority floor) that is supposed to enforce a non-zero gate after a state transition (sale ended/buffer saturated) instead silently degrades to its default `0` value, which the caller treats as "disabled," letting unpriced/low-priority work through for free during exactly the window meant to shed it.

### Impact Explanation
During saturation — the state in which the anti-spam floor is most needed to protect the leader's `BankingStage` — this defect can cause the floor to collapse to `0`, disabling the sigverify-side drop-before-verify optimization/anti-spam gate. This is a QoS-evasion condition: zero/near-zero priority transactions that would normally be dropped before consuming CPU on signature verification instead pass through, undermining the "drop below-floor arrivals ahead of signature verification" protection precisely under load, which is when it is designed to activate [10](#0-9) .

### Likelihood Explanation
The condition requires the scheduler buffer to be saturated (>= `SATURATION_BUFFER_PCT`, i.e., 99% full) [11](#0-10)  while the `priority_queue` happens to be empty because all buffered transactions were popped into `Pending`/in-flight worker state. This is plausible under heavy, bursty transaction load and back-to-back scheduling cycles, but it is a narrow timing window each cycle (this recomputation happens once per iteration of the scheduler's main loop) [12](#0-11) , rather than a persistent state, so exploitation would require sustained effort to keep the queue continuously drained into `Pending` while the buffer stays saturated.

### Recommendation
Change `update_scheduler_priority_floor` to avoid treating "no queued transactions" the same as "safe to fully open the gate" while `saturated` is true. For example, when `saturated` is true and `get_min_max_priority()` returns `None` (empty queue but buffer still saturated by in-flight work), retain the previously published non-zero floor instead of resetting it to `0`, or use a floor derived from the priorities of `Pending` transactions as well as queued ones.

### Proof of Concept
Not independently reproduced with a live validator in this analysis; the trace is code-level: (1) drive enough transaction volume so `buffer_size()` (slab length, including `Pending` entries) reaches the 99% `SATURATION_BUFFER_PCT` watermark, setting `saturated = true` [13](#0-12) ; (2) arrange for a scheduling pass to pop all currently-queued transactions into `Pending` (moving them out of `priority_queue` into the `Slab` only) before `update_scheduler_priority_floor` is called on the same loop iteration [14](#0-13) ; (3) observe that `get_min_max_priority()` returns `None`, the published floor is `0`, and `sigverify.rs`'s `floor > 0` check therefore skips the drop-before-verify step entirely, letting zero/low-priority packets through unimpeded during the saturation window [15](#0-14) . I was not able to trace the exact worker-completion/scheduling interleaving timing needed to confirm how frequently or reliably this empty-queue-while-saturated window occurs in practice — this would require dynamic testing/tracing of the live scheduler loop, which is outside the scope of static code review.

    batch: &mut PacketBatch,
    floor: u64,
    bank: &Bank,

    let mut dropped: usize = 0;
    let mut any_kept = false;
    for mut packet in batch.iter_mut() {
        if packet.meta().discard() {
            continue;
        }
        let Some(data) = packet.data(..) else {
            // Zero-length or otherwise unreadable: leave to downstream
            // stages to reject.
            any_kept = true;

                packet.meta_mut().set_discard(true);
                dropped = dropped.saturating_add(1);
            }
            _ => any_kept = true,
        }
    }

/// Priority floor shared from the banking-stage scheduler to sigverify.

/// When saturated, the scheduler publishes the queue-min transaction's
