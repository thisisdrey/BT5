### Title
Stale mask overwrite in `collateral-add` allows reentrant `debt-add-scaled` calls to be dropped from the account mask, hiding real debt from health checks and liquidation - ([File: mainnet/contracts/market/v0-market-vault.clar])

### Summary
`collateral-add` snapshots the account's `registry` entry (including `mask`) into local `let` bindings, performs an external token transfer via `receive-tokens`, and only afterwards calls `insert` to persist the snapshot-derived `updated-entry`. If the malicious FT's `transfer` hook re-enters the market to add debt (`debt-add-scaled`) during that window, the debt map is correctly updated, but the final `insert` in `collateral-add` overwrites `mask` with the stale, pre-callback value, silently clearing the newly-set debt bit(s) while the underlying `debt` map retains the non-zero scaled debt.

### Finding Description
In `collateral-add` [1](#0-0) , the `let` bindings compute `entry`, `mask`, `updated-mask`, and `updated-entry` from the account's registry state *before* any external call is made. The external token transfer then happens via `(try! (receive-tokens ft amount account))` [2](#0-1) , which calls `contract-call? asset transfer ...` on an attacker-supplied `<ft-trait>` contract. Only after this external call returns does `collateral-add` call `(insert updated-entry)`, which unconditionally overwrites the `registry` map entry for that `id` [3](#0-2) .

Because the attacker controls the FT contract passed as `ft`, its `transfer` implementation can synchronously re-enter the market's borrow flow (through the market impl, which is the authorized `contract-caller` for `debt-add-scaled` per `check-impl-auth` [4](#0-3) ) before `receive-tokens` returns. Each nested `debt-add-scaled` call independently reads the *current* registry entry via `resolve-or-create`, correctly updates the mask to include the debt bit, and calls `insert` immediately, since `debt-add-scaled` itself contains no external call between its state read and its `insert` [5](#0-4) . Both nested calls therefore correctly accumulate `scaled1 + scaled2` into the separate `debt` map via `add-user-scaled-debt` [6](#0-5) .

When control returns to the outer `collateral-add`, it proceeds to call `(insert updated-entry)` with the `updated-entry` computed from the *pre-callback* snapshot — this mask only has the collateral bit added on top of the mask that existed before the nested debt-add-scaled calls ran. This overwrite clears the debt bit(s) that were set by the nested calls, even though `debt-scaled` for that asset is now non-zero. Since `get-position`/`lookup-debt` only enumerate debts present in the account's `mask` field [7](#0-6) , any downstream health-factor or liquidation logic built on `get-position` will silently miss this debt.

No reentrancy guard, lock, or "in progress" flag exists in `v0-market-vault.clar` to prevent this nested call pattern; `check-impl-auth` only restricts calls to come from the registered `impl` contract, which is satisfied by the legitimate borrow re-entry path through the market implementation itself.

### Impact Explanation
This is a **Critical / protocol insolvency** finding: a real, non-zero, scaled debt balance becomes permanently invisible to every mask-driven health check and liquidation enumeration, while the debtor retains the borrowed assets. This directly breaks the core invariant "sum of user debt equals principal-scaled times index, with mask bit set," enabling under-collateralized or effectively unbacked debt positions that can never be liquidated through the normal mask-based enumeration path, resulting in bad debt accruing against protocol solvency.

### Likelihood Explanation
The attacker needs only to: (1) deploy an ordinary `<ft-trait>`-conforming contract with a custom `transfer` function, (2) hold or acquire minimal pre-existing collateral to make at least one nested borrow health-check pass, and (3) call the market's deposit/collateral-add entrypoint with their malicious FT contract as the trait argument, receiving reentrant control during `transfer`. No privileged role, DAO action, or price manipulation is required; capital cost is limited to whatever collateral is needed to satisfy the nested borrow's own health check, and the attack is fully repeatable across blocks and assets.

### Recommendation
Follow checks-effects-interactions ordering in `collateral-add` (and equally in `collateral-remove`/`debt-remove-scaled`, which share the same pattern): perform `insert` of the updated registry entry (mask, timestamps) *before* the external token transfer, or add a per-account reentrancy lock in the vault so that nested calls affecting the same `id` cannot commit conflicting state during an in-flight `receive-tokens`/`send-tokens` external call. Alternatively, re-read the current mask/registry entry immediately before the final `insert` (right after the external call returns) and merge the intended bit change onto the fresh entry rather than the stale pre-call snapshot.

### Proof of Concept
Clarinet/vitest simnet test plan:
1. Deploy a malicious FT contract implementing `ft-trait` whose `transfer` function, when called with a specific memo/amount marker, performs two sequential `contract-call?`s into the market's borrow entrypoint for asset `D` (via the authorized `impl` contract), each borrowing a small scaled amount (`scaled1`, `scaled2`).
2. Set up an account with enough pre-existing collateral (a different asset) so both nested borrow calls pass their own health checks.
3. Call the market's deposit/`collateral-add` flow for some asset using the malicious FT as the transfer asset.
4. After the outer call completes, assert:
   - `debt-scaled(id, D)` equals `scaled1 + scaled2` (non-zero), confirming the debt map recorded both nested borrows.
   - The account's `mask` (via `lookup` / `get-position`) does **not** have the debt bit for asset `D` set, i.e., `lookup-debt` for the account's full mask does not include asset `D`.
5. This combination (non-zero debt, cleared mask bit) demonstrates the debt is invisible to mask-based enumeration used by health/liquidation logic, confirming the insolvency-class bug.
