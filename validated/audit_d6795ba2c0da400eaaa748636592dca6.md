### Title
Unprivileged dust deposits permanently block a victim from opening new collateral/debt positions via `MAX_TOKENS_PER_USER` cap exhaustion - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The reference report is an unauthenticated resource-exhaustion DoS: attacker-controlled input fills a bounded resource until the service fails. The Metronome analog is the per-account token-list cap: `Pool` enforces `MAX_TOKENS_PER_USER = 30` across `depositTokensOfAccount + debtTokensOfAccount` via `onlyIfAdditionWillNotReachMaxTokens`, and any unprivileged user can grow a victim's `depositTokensOfAccount` set without consent, either by calling `DepositToken.deposit(amount_, onBehalfOf_ = victim)` or `DepositToken.transfer(victim, dust)`. Once the combined set reaches 30, every action that would add a new token entry for the victim reverts with `UserReachedMaxTokens`.

### Finding Description
`Pool.addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are gated by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [1](#0-0) . Entries are added from two reachable paths:

- `DepositToken.deposit(amount_, onBehalfOf_)` mints to an arbitrary `onBehalfOf_`, and `_mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's balance transitions 0 → >0 [2](#0-1) [3](#0-2) .
- `DepositToken._transfer` does the same on a 0 → >0 recipient balance, only requiring the sender's `unlockedBalanceOf` covers the dust amount [4](#0-3) .

There is no opt-in, no minimum amount, and no victim authorization. An attacker loops over the pool's listed deposit tokens, depositing 1 wei of underlying `onBehalfOf` the victim (or transferring 1 wei of msdTOKEN), filling the victim's set to 30. Afterwards:

- `DepositToken.deposit` / `transfer` / `transferFrom` to the victim in any deposit token the victim does not already hold reverts inside `addToDepositTokensOfAccount` (the revert propagates out of `_mint`/`_transfer`).
- `DebtToken` mint/issue paths that add a new synthetic's debt token to the victim's `debtTokensOfAccount` also revert, so the victim cannot borrow any synthetic they don't already hold a debt position in.
- Liquidation `seize` flows that would credit a new deposit-token type to the victim side likewise revert.

### Impact Explanation
Temporary freezing of funds / liveness failure: the victim cannot deposit additional collateral types, receive msdTOKEN transfers, or open new debt positions while the set is saturated. If the victim's health is deteriorating, blocking a new collateral deposit can push them into liquidation — indirect loss of funds via inability to top up. Recovery requires the victim to spend gas transferring/withdrawing the dust entries one by one, and the attacker can front-run or re-fill the freed slots as long as dust remains, making the DoS sustainable.

### Likelihood Explanation
Fully unprivileged: `deposit` and `transfer` are public, `onBehalfOf_` is attacker-chosen, and no modifier (`onlyIfDepositTokenExists`, `whenNotPaused`, `nonReentrant`, `_revertIfLocked` on the sender's own balance) prevents crediting a third party. Cost is bounded: gas for N deposit-token transfers plus dust underlying. Effectiveness is capped by the number of deposit tokens actually listed in the pool (the cap is shared with the victim's existing debt/deposit entries, so fewer attacker transfers are needed if the victim already holds positions). Pools listing ≥ a dozen collaterals make filling a fresh/empty victim account to 30 feasible; against victims already holding many tokens it is nearly free.

### Recommendation
Add a victim-side opt-in or a minimum first-deposit threshold before registering a token in `depositTokensOfAccount` (e.g., only track tokens above a configurable dust floor, or skip list-addition for amounts below it), or exempt `deposit(onBehalfOf_)`/`transfer` credits from the per-account cap accounting by making the cap apply only to tokens that contribute collateral value. Alternatively, allow forced removal (`removeFromDepositTokensOfAccount`) of entries the holder wants to purge, or raise/derive the cap from actual liquidatable value so unsolicited dust cannot consume slots.

// attacker EOA holds dust of each underlying
for (const dt of depositTokens) {

  await dt.connect(attacker).deposit(1, victim.address)

await expect(newDt.connect(victim).deposit(parseEther('1'), victim.address))

// nor receive a transfer of a new msdTOKEN
await expect(dA.connect(attacker).transfer(victim.address, 1))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

        uint256 amount_,
        address onBehalfOf_
    ) external override whenNotPaused nonReentrant onlyIfDepositTokenExists returns (uint256 _deposited, uint256 _fee) {
        if (amount_ == 0) revert AmountIsZero();
        if (onBehalfOf_ == address(0)) revert BeneficiaryIsNull();

        IPool _pool = pool;
        IERC20 _underlying = underlying;
        address _msgSender = _msgSender();
        address _treasury = address(_pool.treasury());

        if (_msgSender == _treasury) revert TreasuryCanNotDeposit();

        uint256 _balanceBefore = _underlying.balanceOf(_treasury);
        _underlying.safeTransferFrom(_msgSender, _treasury, amount_);
        amount_ = _underlying.balanceOf(_treasury) - _balanceBefore;

        (_deposited, _fee) = quoteDepositOut(amount_);
        if (_fee > 0) {
            _mint(_pool.feeCollector(), _fee);
        }

        _mint(onBehalfOf_, _deposited);

        emit CollateralDeposited(_msgSender, onBehalfOf_, amount_, _deposited, _fee);
    }
