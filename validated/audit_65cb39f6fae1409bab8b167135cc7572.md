#No Vulnerability found for this question.

Analysis: `compute_max_allowed_uni_streams_with_rtt` in `streamer/src/nonblocking/swqos.rs` does scale `max_concurrent_uni_streams` upward with reported connection RTT (from `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS`=128 up to 128*350/50=896 at `MAX_RTT_MS`), and this value is attacker-influenceable since `connection.rtt()` reflects ACK timing that a malicious client can delay [1](#0-0) . However, `max_concurrent_uni_streams` is purely a QUIC-layer flow-control parameter governing how many streams can be simultaneously open/in-flight on one connection; it does not gate the rate at which streams are actually accepted and forwarded into the sigverify/dedup pipeline.

That admission-rate gating is done separately by `on_stream_accepted`/`throttle_stream` against a `ConnectionStreamCounter` that is shared across *all* connections registered under the same `ConnectionTableKey` (i.e., same source IP), as set up in `try_add_connection` (`connection_entry.first().map(|entry| entry.stream_counter.clone()).unwrap_or_else(stream_counter_factory)`) [2](#0-1) . The throttle limit for unstaked peers, `max_unstaked_load_in_throttling_window = MAX_UNSTAKED_TPS * STREAM_THROTTLING_INTERVAL_MS / 1000`, is a fixed constant independent of RTT, per-connection concurrency limits, or the number of connections opened by that IP [3](#0-2) . `on_stream_accepted` increments this shared, IP-scoped counter, and `throttle_stream` sleeps the reader when the shared counter exceeds the cap, regardless of how many concurrent streams/connections the attacker has opened or what `max_concurrent_uni_streams` was negotiated [4](#0-3) .

Additionally, the number of connections per IP is separately capped by `max_connections_per_unstaked_peer` (default 8) in `try_add_connection`, and total unstaked connections are pruned against `max_unstaked_connections` [5](#0-4) [6](#0-5) .

Therefore, inflating RTT to raise `max_concurrent_uni_streams` only widens the QUIC-level flow-control window (allowing more streams to be opened simultaneously and queued for the connection loop to `accept_uni`), but it does not increase the actual throughput of packets admitted into sigverify/dedup/scheduling, since that is bounded by the shared, RTT-independent per-IP `throttle_stream` rate limit. There is no code path by which manipulating RTT bypasses the per-IP throughput cap used for downstream capacity planning, so the described exploit does not hold.

fn compute_max_allowed_uni_streams_with_rtt(
    rtt_millis: u32,
    peer_type: ConnectionPeerType,
    total_stake: u64,

    let streams = match peer_type {
        ConnectionPeerType::Staked(peer_stake) => {
            // No checked math for f64 type. So let's explicitly check for 0 here
            if total_stake == 0 || peer_stake > total_stake {
                warn!(
                    "Invalid stake values: peer_stake: {peer_stake:?}, total_stake: \
                     {total_stake:?}"
                );

                QUIC_MIN_STAKED_CONCURRENT_STREAMS
            } else {
                let delta = (QUIC_TOTAL_STAKED_CONCURRENT_STREAMS
                    - QUIC_MIN_STAKED_CONCURRENT_STREAMS) as f64;

                (((peer_stake as f64 / total_stake as f64) * delta) as u32
                    + QUIC_MIN_STAKED_CONCURRENT_STREAMS)
                    .clamp(
                        QUIC_MIN_STAKED_CONCURRENT_STREAMS,
                        QUIC_MAX_STAKED_CONCURRENT_STREAMS,
                    )
            }
        }
        ConnectionPeerType::Unstaked => QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS,
    };

    // multiply first then divide to avoid rounding errors.
    (streams.saturating_mul(rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS))) / REFERENCE_RTT_MS
}
