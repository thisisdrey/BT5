Audit Report

## Title
Unbounded `message.assets` array in Snowbridge V2 inbound converter permanently locks bridged Ethereum funds - (File: `bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs`)

## Summary
`Message::extract_assets` decodes an unbounded `Vec<EthereumAsset>` straight from the Ethereum log with no length check, and `MessageToXcm::prepare`/`convert` iterate over the entire `message.assets` list, pushing one `AssetTransfer`/XCM asset entry per element into the outgoing `ReserveAssetDeposited`/`WithdrawAsset` instructions with no cap analogous to `pallet-xcm`'s `MAX_ASSETS_FOR_TRANSFER`. Since the Ethereum-side funds are locked before the relayer ever calls `submit`, and the message content is immutable once the Ethereum event is emitted, an oversized asset list that produces an XCM the destination cannot execute/deliver causes deterministic, permanent failure of `process_message`, and the corresponding Ethereum-side funds can never be settled on the Polkadot side.

## Finding Description
`Message::extract_assets` in `bridges/snowbridge/primitives/inbound-queue/src/v2/message.rs` (L182-192) loops over `payload.assets` with no bound, and the `Message` struct's `assets: Vec<EthereumAsset>` field (L101-120) has no `BoundedVec`/length constraint. [1](#0-0) [2](#0-1) 

`MessageToXcm::prepare` (`converter.rs` L159-200) then iterates `&message.assets` unbounded, pushing an `AssetTransfer::ReserveDeposit`/`ReserveWithdraw` entry per element, and `convert` (L396-411) folds these into `ReserveAssetDeposited`/`WithdrawAsset` XCM instructions whose length equals `message.assets.len()` exactly. [3](#0-2) [4](#0-3) 

No `MAX_ASSETS_FOR_TRANSFER`-style guard exists anywhere in this path, unlike `pallet-xcm`'s `transfer_assets`, which explicitly enforces `ensure!(assets.len() <= MAX_ASSETS_FOR_TRANSFER, ...)` before building any multi-asset XCM. [5](#0-4) [6](#0-5) 

`submit` in `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs` (L185-198) is a fully public, `ensure_signed` extrinsic that verifies the event, decodes `Message::try_from`, and calls `process_message`, which marks the nonce as delivered only if `T::MessageProcessor::process_message` succeeds — any conversion/send failure returns `Err`, atomically rolling back the `Nonce::<T>::set(nonce)` write via normal `DispatchResult` semantics. [7](#0-6) 

## Impact Explanation
Because funds are locked/debited on the Ethereum Gateway contract off-chain and unconditionally before the relayer submits the corresponding proof, and because the message payload (including `assets.len()`) is fixed by the immutable Ethereum event log, any message whose asset count is large enough to make the derived XCM exceed the destination's execution weight or the transport's max message size will fail conversion/dispatch identically on every resubmission attempt. This permanently prevents the nonce from being marked delivered, matching the "permanent user-fund or bridge-state lock" impact category, since the corresponding Ethereum-side funds become unrecoverable on the Polkadot side.

## Likelihood Explanation
`submit` requires no privileged role — any signed account can relay a valid Merkle-proven Ethereum log, and the number of assets bundled per Gateway send is controlled entirely by the unprivileged Ethereum-side caller, with nothing in this repository capping it. This can occur without malicious relayer/validator behavior, simply through increased asset diversity in a single bridge send.

## Recommendation
Enforce an explicit, protocol-level maximum on `message.assets.len()` before or during `MessageToXcm::prepare`/`convert`, mirroring `pallet-xcm`'s `MAX_ASSETS_FOR_TRANSFER` guard, returning a distinct `ConvertMessageError`/`Error<T>` variant early rather than allowing the loop to build an unbounded XCM asset vector. The cap should be chosen conservatively relative to the destination chain's execution weight and the transport's maximum message size.

## Proof of Concept
1. On Ethereum, call the Gateway's send function with `Payload.assets` containing `N` distinct asset entries, `N` large enough that the derived XCM exceeds Asset Hub's execution weight or the XCMP/DMP max message size.
2. A relayer submits the event via `EthereumInboundQueueV2::submit` with a valid proof; `Message::try_from` decodes all `N` assets with no length check (`message.rs` L144-192).
3. `MessageToXcm::prepare`/`convert` build an XCM with an `N`-length `ReserveAssetDeposited`/`WithdrawAsset` vector (`converter.rs` L159-200, L396-411).
4. `T::MessageProcessor::process_message` fails (`SendError::TooBig`/weight overshoot), causing `process_message` (`lib.rs` L214-245) to return `Err`, rolling back the nonce update.
5. Every subsequent resubmission of the same immutable log fails identically, since `N` and the asset list are fixed by the already-emitted Ethereum event.

		pub fn process_message(relayer: T::AccountId, message: Message) -> DispatchResult {
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == message.gateway, Error::<T>::InvalidGateway);

			let (nonce, relayer_fee) = (message.nonce, message.relayer_fee);

			// Verify the message has not been processed
			ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);

			// Mark message as received
			Nonce::<T>::set(nonce);

			let message_id = T::MessageProcessor::process_message(relayer.clone(), message)
				.map_err(|e| match e {
					MessageProcessorError::ProcessMessage(e) => e,
					MessageProcessorError::ConvertMessage(e) => Error::<T>::from(e).into(),
					MessageProcessorError::SendMessage(e) => Error::<T>::from(e).into(),
				})?;

			// Pay relayer reward
			let tip = Tips::<T>::take(nonce).unwrap_or_default();
			let total_tip = relayer_fee.saturating_add(tip);
			if total_tip > 0 {
				T::RewardPayment::register_reward(&relayer, T::DefaultRewardKind::get(), total_tip);
			}

			// Emit event with the message_id
			Self::deposit_event(Event::MessageReceived { nonce, message_id });

			Ok(())
		}
