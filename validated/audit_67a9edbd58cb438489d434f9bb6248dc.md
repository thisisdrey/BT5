### Title
Unbounded array allocation from attacker-controlled length word in `ValidateMultiSign` precompiled contract can trigger an OOM DoS - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` TVM precompiled contract parses signature-array metadata directly out of attacker-supplied call data. When the `allowTvmSelfdestructRestriction` hard fork flag is not active, the contract calls `extractBytesArray`, which allocates a Java array sized by a 32-byte word taken straight from the call data, with no upper bound check before the allocation.

### Finding Description
`ValidateMultiSign.execute()` parses `words` from the raw call data and, depending on `VMConfig.allowTvmSelfdestructRestriction()`, either calls the bounded `extractSigArray` (which is preceded by a `sigArraySize > MAX_SIZE` check) or the unbounded `extractBytesArray`: [1](#0-0) 

`extractBytesArray` itself performs no bound check on the parsed length before allocating the array: [2](#0-1) 

`int len = words[offset].intValueSafe();` is fully attacker-controlled (any transaction/contract caller supplies `rawData`, and `offset` is itself derived from `words[3]`, another attacker-controlled word). `intValueSafe()` clamps the value into the `int` range rather than rejecting out-of-range values, so an attacker can set this word to a large positive value close to `Integer.MAX_VALUE`. The subsequent `new byte[len][]` then attempts to allocate an object array with up to ~2^31 elements (each a reference, 4-8 bytes plus header on top of any populated `byte[]`), which is enough to exhaust heap memory well before the loop that fills the array even runs.

This is the same bug class as the reported libtiff flaw: an attacker-supplied "size" field is used directly to allocate memory without validating it against a sane upper bound, causing an out-of-memory condition triggered by a small, cheap input.

Comparable array-allocation code exists nearby (`extractBytes32Array`, `extractSigArray`) and follows the identical unguarded pattern: [3](#0-2) 
`extractSigArray` is only safe because callers currently gate it with a `MAX_SIZE` check before invocation when the fork flag is active: [4](#0-3) 
No equivalent bound exists on the `extractBytesArray` branch that executes when the fork flag is not enabled.

### Impact Explanation
A successful trigger throws a Java `OutOfMemoryError` inside the TVM execution path invoked from a `TriggerSmartContract`/`CREATE` call. Depending on where the OOM surfaces (heap exhaustion can affect unrelated threads/allocations across the JVM), this can crash the full-node process or make it unresponsive, denying service to the node and any downstream RPC clients — a concrete network/node availability impact reachable by any unprivileged transaction sender who can call the precompile address.

### Likelihood Explanation
The precompile is reachable by any account able to submit a `TriggerSmartContract` (or via a deployed contract that calls it), i.e. any unprivileged transaction broadcaster — no special permission is required. However, exploitability is conditioned on `VMConfig.allowTvmSelfdestructRestriction()` being disabled for the branch under attack; I was not able to fully confirm from the available index whether this fork flag is already permanently activated on the live chain (its associated `ForkBlockVersionEnum`/`DynamicPropertiesStore` gating could not be fully traced with the tools available in this session). If the flag is active network-wide, this exact code path is dead in current production use, which would reduce likelihood to low/none; if it is still reachable (e.g., during a fork-activation window, on a private/test network, or in another code path relying on `extractBytesArray`), the likelihood is high given the input is a single, cheap transaction.

### Recommendation
Add an explicit, low upper bound check (e.g. `MAX_SIZE`) on the parsed `len` in `extractBytesArray` and `extractBytes32Array` before allocating `bytesArray`/`bytes32Array`, mirroring the existing guard used in the `extractSigArray` call path, regardless of the `allowTvmSelfdestructRestriction` fork state. Confirm current mainnet fork status of `allowTvmSelfdestructRestriction` to determine whether this is a live or dormant path.

### Proof of Concept
Craft `rawData` for a `CALL`/`STATICCALL` to the `ValidateMultiSign` precompile address such that:
- `words[3]` (the "offset" pointer) is set so that `offset = words[3].intValueSafe() / WORD_SIZE` points to a controlled word.
- The word at that computed `offset` is set to a large value (e.g. `0x7FFFFFFF`).
- Ensure `VMConfig.allowTvmSelfdestructRestriction()` is not enforced for this call.

Submitting this as call data to the precompile causes `extractBytesArray` to execute `new byte[0x7FFFFFFF][]`, which attempts a multi-gigabyte allocation and throws `OutOfMemoryError`, potentially destabilizing the node process. (Full end-to-end confirmation of the fork-flag state on mainnet could not be completed with the tools available in this session — this should be verified before treating the finding as currently exploitable in production.)

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
