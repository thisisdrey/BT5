Audit Report

## Title
Unbounded `starting_block` in `pallet_vesting::vested_transfer` lets any signed account force a permanent, un-cancellable vesting lock and exhaust a victim's schedule slots - (File: `substrate/frame/vesting/src/lib.rs`, `substrate/frame/vesting/src/vesting_info.rs`)

## Summary
`vested_transfer` (call index 2) is a plain signed extrinsic that lets the caller pick an arbitrary `target` and an arbitrary `VestingInfo{locked, per_block, starting_block}`, with `starting_block` completely unbounded and validated only by `VestingInfo::is_valid()` (which only checks `locked != 0` and `per_block != 0`). This allows an attacker to force a schedule on a victim account that starts at `BlockNumberFor::max_value()`, permanently locking the transferred balance and consuming one of the victim's finite `MAX_VESTING_SCHEDULES` slots, with no self-service removal path available to the victim.

## Finding Description
`is_valid()` performs no bound on `starting_block`: [1](#0-0) 

`do_vested_transfer` relies solely on this weak check plus the `MinVestedTransfer` floor before unconditionally transferring currency and installing the schedule: [2](#0-1) 

`vested_transfer` is directly reachable by any signed account, with `target` chosen by the caller and never required to consent: [3](#0-2) 

Because `starting_block` is an arbitrary `BlockNumberFor<T>` value, `locked_at` computes `n.saturating_sub(self.starting_block)`, which stays `0` for as long as `n < starting_block`, so the full `locked` amount remains reported as locked indefinitely: [4](#0-3) 

`add_vesting_schedule` pushes the new schedule into the target's bounded `Vesting` storage (capped at `T::MAX_VESTING_SCHEDULES`) and calls `write_lock`, applying `set_lock`/`extend_lock` on the victim's balance: [5](#0-4) 

The only bound check, `can_add_vesting_schedule`, merely verifies the schedule count is below `T::MAX_VESTING_SCHEDULES` — it does not check whether the schedule can ever complete: [6](#0-5) 

The only removal path is root-gated: [7](#0-6) 

`merge_schedules` is signed but does not help the victim self-remedy: merging two schedules whose start is in the far future produces `starting_block = now.max(schedule1.starting_block()).max(schedule2.starting_block())`, which stays far in the future: [8](#0-7) 

## Impact Explanation
An unprivileged attacker can call `vested_transfer(target, VestingInfo::new(MinVestedTransfer, 1, BlockNumberFor::<T>::max_value()))` repeatedly against a victim. Each call transfers `MinVestedTransfer` currency into the victim's account under a lock that never decreases (satisfies "permanent user-fund lock" per the impact gate) and consumes one of the victim's `MAX_VESTING_SCHEDULES` slots via the check in `can_add_vesting_schedule`. Once the slot count is exhausted, all further legitimate `vested_transfer`/`force_vested_transfer` calls to that account fail with `Error::AtMaxVestingSchedules`, permanently denying the account further vesting-based payouts absent root intervention via `force_remove_vesting_schedule`. This is a genuine compromise of intended pallet behavior (vesting availability), reachable without any privileged actor.

## Likelihood Explanation
High. `vested_transfer` requires only a signed origin and enough balance to cover `MinVestedTransfer` plus existential deposit — no governance or admin action is needed. The attack is fully repeatable and its cost scales linearly with `T::MAX_VESTING_SCHEDULES`, which is a small fixed constant in shipped runtimes, making full slot exhaustion of a target account cheap and practical.

## Recommendation
- Bound `starting_block` relative to the current block (e.g., a configurable maximum horizon), or reject schedules whose `ending_block_as_balance` exceeds a sane bound.
- Require target consent for vested transfers (e.g., an explicit accept step), or let the target self-remove not-yet-started schedules instead of restricting removal to `ensure_root` via `force_remove_vesting_schedule`.
- At minimum, add a signed, self-service removal path for schedules where `now < starting_block`, since these cannot yet have conferred any benefit to the target and only exist to grief.

## Proof of Concept
1. Attacker `A` with balance `>= MinVestedTransfer + ExistentialDeposit` targets victim `V`.
2. For `i` in `0..T::MAX_VESTING_SCHEDULES`, `A` calls `Vesting::vested_transfer(A, V, VestingInfo::new(MinVestedTransfer, 1, BlockNumberFor::<T>::max_value()))`.
3. Each call passes `is_valid()` (`substrate/frame/vesting/src/vesting_info.rs:60-62`) and `can_add_vesting_schedule` (`substrate/frame/vesting/src/lib.rs:818-837`), transferring funds and installing a schedule that never starts, per `locked_at` (`substrate/frame/vesting/src/vesting_info.rs:87-101`).
4. After `T::MAX_VESTING_SCHEDULES` calls, `V`'s `Vesting` storage is full; subsequent `vested_transfer`/`force_vested_transfer` calls to `V` fail with `Error::AtMaxVestingSchedules`, and `V` has no signed-origin path to remove any schedule (`force_remove_vesting_schedule` requires `ensure_root`, `substrate/frame/vesting/src/lib.rs:472-490`).

	/// Amount locked at block `n`.
	pub fn locked_at<BlockNumberToBalance: Convert<BlockNumber, Balance>>(
		&self,
		n: BlockNumber,
	) -> Balance {
		// Number of blocks that count toward vesting;
		// saturating to 0 when n < starting_block.
		let vested_block_count = n.saturating_sub(self.starting_block);
		let vested_block_count = BlockNumberToBalance::convert(vested_block_count);
		// Return amount that is still locked in vesting.
		vested_block_count
			.checked_mul(&self.per_block()) // `per_block` accessor guarantees at least 1.
			.map(|to_unlock| self.locked.saturating_sub(to_unlock))
			.unwrap_or(Zero::zero())
	}

```rust
	fn add_vesting_schedule(
		who: &T::AccountId,
		locked: BalanceOf<T>,
		per_block: BalanceOf<T>,
		starting_block: BlockNumberFor<T>,
	) -> DispatchResult {
		if locked.is_zero() {
			return Ok(());
		}

		let vesting_schedule = VestingInfo::new(locked, per_block, starting_block);
		// Check for `per_block` or `locked` of 0.
		if !vesting_schedule.is_valid() {
			return Err(Error::<T>::InvalidScheduleParams.into());
		};

		let mut schedules = Vesting::<T>::get(who).unwrap_or_default();

		// NOTE: we must push the new schedule so that `exec_action`
		// will give the correct new locked amount.
		ensure!(schedules.try_push(vesting_schedule).is_ok(), Error::<T>::AtMaxVestingSchedules);

		debug_assert!(schedules.len() > 0, "schedules cannot be empty after insertion");
		let schedule_index = schedules.len() - 1;
		Self::deposit_event(Event::<T>::VestingCreated {
			account: who.clone(),
			schedule_index: schedule_index as u32,
		});

		let (schedules, locked_now) =
			Self::exec_action(schedules.to_vec(), VestingAction::Passive)?;

		Self::write_vesting(who, schedules)?;
		Self::write_lock(who, locked_now);

		Ok(())
	}
```

	/// Ensure we can call `add_vesting_schedule` without error. This should always
	/// be called prior to `add_vesting_schedule`.
	fn can_add_vesting_schedule(
		who: &T::AccountId,
		locked: BalanceOf<T>,
		per_block: BalanceOf<T>,
		starting_block: BlockNumberFor<T>,
	) -> DispatchResult {
		// Check for `per_block` or `locked` of 0.
		if !VestingInfo::new(locked, per_block, starting_block).is_valid() {
			return Err(Error::<T>::InvalidScheduleParams.into());
		}

		ensure!(
			(Vesting::<T>::decode_len(who).unwrap_or_default() as u32) < T::MAX_VESTING_SCHEDULES,
			Error::<T>::AtMaxVestingSchedules
		);

		Ok(())
	}
