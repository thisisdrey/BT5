### Title
Exchange pool spot-price manipulation enables sandwich attacks against liquidity providers - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
java-tron's on-chain "Exchange" feature (`ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`/`ExchangeTransactionContract`) implements a Bancor-style AMM pool whose exchange rate is derived purely from the pool's current instantaneous reserves, with no time-weighted average price (TWAP) or manipulation resistance — the exact bug class described in the external report (reading price directly off a pool instead of a TWAP oracle). Unlike `ExchangeTransactionContract`, the `ExchangeInjectContract`/`ExchangeWithdrawContract` paths compute the counter-asset amount from this manipulable spot ratio with **no caller-supplied slippage/minimum-output protection at all**, making liquidity providers directly exploitable via a same-block sandwich.

### Finding Description
`ExchangeInjectActuator.execute()` and `ExchangeWithdrawActuator.execute()`/`doValidate()` compute `anotherTokenQuant` as a simple ratio of the pool's current `firstTokenBalance`/`secondTokenBalance`: [1](#0-0) [2](#0-1) 

These balances (`getFirstTokenBalance()`/`getSecondTokenBalance()`) are the same live, single-block reserves used by `ExchangeCapsule.transaction()` for actual swaps via the Bancor-relay formula in `ExchangeProcessor`/`SafeExchangeProcessor`: [3](#0-2) 

Critically, `ExchangeInjectContract` and `ExchangeWithdrawContract` carry no "expected"/minimum-output field, unlike `ExchangeTransactionContract`, which at least validates `anotherTokenQuant < tokenExpected`: [4](#0-3) 

Because ordinary Tron transactions in the same block can be ordered by the packing SR, and there is no TWAP smoothing or per-block price-change cap on the exchange pool, an attacker can:
1. Broadcast a large `ExchangeTransactionContract` swap that skews `firstTokenBalance`/`secondTokenBalance` (moving the spot ratio far from the "fair" ratio).
2. Immediately follow (or precede/sandwich) a victim's unprotected `ExchangeInjectContract` (adding liquidity) or `ExchangeWithdrawContract` (removing liquidity), which is forced to use the now-skewed ratio with no min-output check.
3. Reverse the initial swap with another `ExchangeTransactionContract`, extracting the victim's contributed value as arbitrage profit.

This mirrors the reported bug class precisely: computing a rate from a pool's manipulable instantaneous reserves rather than a TWAP, then acting on it for value transfer.

### Impact Explanation
A single unprivileged account can extract funds from any other account that injects or withdraws liquidity into/from a java-tron Exchange pool, by sandwiching the victim's transaction with `ExchangeTransactionContract` swaps that move the spot ratio, since `ExchangeInjectActuator`/`ExchangeWithdrawActuator` apply no slippage protection. This constitutes concrete unauthorized value transfer/theft of user funds reachable purely via signed transactions from an unprivileged broadcaster — satisfying the "theft of funds" impact bar.

### Likelihood Explanation
Likelihood is high: the attack requires only the ability to submit ordinary `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions (no special privilege, no contract deployment), and depends only on the existing bonding-curve math and lack of a min-output parameter on inject/withdraw contracts, both of which are permanent protocol-level design gaps rather than transient conditions.

### Recommendation
- Add a caller-specified minimum/maximum counter-token amount (slippage bound) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, validated in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` similar to the `expected` check already present in `ExchangeTransactionActuator`.
- Consider deriving pricing from a TWAP over the pool's recent reserve history rather than the single most-recent block's balances, or bound the maximum ratio change permitted within one block.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) from a victim targeting exchange `id=X` with `firstTokenId=TRX`, `secondTokenId=ABC`.
2. Attacker submits `ExchangeTransactionContract` selling a large amount of TRX into the pool, which — through `ExchangeCapsule.transaction()` — drastically shifts `firstTokenBalance`/`secondTokenBalance`.
3. Victim's `ExchangeInjectContract` executes and, per `ExchangeInjectActuator.execute()` lines 71-83, computes `anotherTokenQuant` from the now-skewed ratio, forcing the victim to inject ABC at an unfavorable rate relative to TRX (no `expected`/slippage field exists to reject this).
4. Attacker submits a second `ExchangeTransactionContract` reversing the initial swap, restoring the ratio and capturing the value differential extracted from the victim's injected liquidity, minus negligible fees (the exchange contracts have `calcFee() == 0` for transaction/inject/withdraw beyond bandwidth).
