### Title
Inconsistent enforcement of the `supportUnfreezeDelay` feature-gate between `WithdrawExpireUnfreezeActuator` and the TVM-reachable `WithdrawExpireUnfreezeProcessor` - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawExpireUnfreezeProcessor.java)

### Summary
The `WithdrawExpireUnfreezeActuator` (the normal transaction-broadcast path for withdrawing already-expired "unfreeze" balances from `UnFreezeV2`) explicitly gates execution on the committee-controlled feature flag `DynamicPropertiesStore.supportUnfreezeDelay()`, but the parallel TVM-reachable code path, `WithdrawExpireUnfreezeProcessor`, invoked from a Solidity contract through `Program.withdrawExpireUnfreeze()`, omits this check entirely. This is the same class of bug as the reported Redeemer.sol issue: a "pause"/feature-enable guard is applied inconsistently across functionally equivalent redeem/withdraw code paths.

### Finding Description
`WithdrawExpireUnfreezeActuator.validate()` requires the committee-controlled flag before allowing a normal transaction to withdraw expired unfreeze balances: [1](#0-0) 

The TVM native-contract counterpart, reachable by any deployed contract via the `withdrawExpireUnfreeze` opcode handler in `Program.java`, performs no equivalent check: [2](#0-1) 

The opcode entry point that any contract can call: [3](#0-2) 

This mirrors the reported pattern in Redeemer.sol, where the `unpaused` modifier guarding a critical fund-movement function was applied on one function but omitted from several other functionally-equivalent redeem functions.

### Impact Explanation
If the committee ever disables `ALLOW_UNFREEZE_DELAY`/`supportUnfreezeDelay` (a governance-controlled kill-switch for this v2 unstaking mechanism), ordinary account-level transactions calling `WithdrawExpireUnfreezeContract` are correctly blocked. However, a smart contract can still invoke `withdrawExpireUnfreeze()` via TVM and successfully process the same withdrawal, because `WithdrawExpireUnfreezeProcessor.validate()` never checks the flag. This defeats the intent of the feature gate as an emergency pause mechanism for this withdrawal functionality, since a contract-based caller has an unrestricted path.

### Likelihood Explanation
Reachable by any contract deployer/caller with an `UnFreezeV2` entry that has already matured (expired), with no special privilege required — only a standard TVM contract call. Likelihood depends on the committee actually toggling `supportUnfreezeDelay` off after having turned it on (governance/committee proposal action), which is the operational scenario this flag exists to support (similar to the "pause during hack/incident" scenario cited in the original report).

### Recommendation
Add the same `dynamicStore.supportUnfreezeDelay()` check to `WithdrawExpireUnfreezeProcessor.validate()` that is already enforced in `WithdrawExpireUnfreezeActuator.validate()`, so the TVM-reachable path cannot bypass the feature/pause gate that governs the account-transaction path.

### Proof of Concept
1. Committee enables `ALLOW_UNFREEZE_DELAY` (supportUnfreezeDelay() == true); a user unfreezes balance via `UnfreezeBalanceV2Actuator`, creating an `UnFreezeV2` entry with a future expire time.
2. Time passes until the entry's `unfreezeExpireTime` has elapsed.
3. Committee then disables `ALLOW_UNFREEZE_DELAY` (supportUnfreezeDelay() == false) as an emergency pause.
4. A normal `WithdrawExpireUnfreezeContract` transaction is rejected by `WithdrawExpireUnfreezeActuator.validate()` with "Not support WithdrawExpireUnfreeze transaction, need to be opened by the committee".
5. The same account instead deploys/uses a contract that calls the native `withdrawExpireUnfreeze()` TVM operation (`Program.withdrawExpireUnfreeze()` → `WithdrawExpireUnfreezeProcessor`), which succeeds and credits the balance, bypassing the pause. [2](#0-1) [1](#0-0)

  public void validate(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid address");
    }
    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    if (Objects.isNull(accountCapsule)) {
      String readableOwnerAddress = StringUtil.createReadableString(ownerAddress);
      throw new ContractValidateException(ACCOUNT_EXCEPTION_STR
          + readableOwnerAddress + NOT_EXIST_STR);
    }

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = accountCapsule.getInstance()
        .getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze < 0) {
      throw new ContractValidateException("no unFreeze balance to withdraw ");
    }
    try {
      LongMath.checkedAdd(accountCapsule.getBalance(), totalWithdrawUnfreeze);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }

    if (accountCapsule.hasInvalidDelegatedV2()) {
      MUtil.checkCPUTimeForInvalidDelegatedV2Balance();
    }
  }
