## Title
Relay-request `RelayFromAddr`/`RelayToAddr` fields are trusted without binding them to the sender's authenticated identity - (File: relay_manager.go)

### Summary
The RLN report describes a case where a caller-supplied identifier (`account`) is accepted at face value and used purely as a lookup/state key, without verifying it actually corresponds to the entity the caller is authorized to act as — letting an attacker dodge a security gate tied to that identity. The reachable analog in this codebase is `relayManager.handleCreateRelayRequest` (and its counterpart `handleCreateRelayResponse`), where the `RelayFromAddr`/`RelayToAddr` fields of an authenticated peer's `NebulaControl` message are trusted as-is and used to key relay state, without checking that `RelayFromAddr` equals the sender's own certificate-verified `vpnAddrs`.

### Finding Description
`relayManager.HandleControlMsg` is reached for `header.Control` packets from an already-handshaked `HostInfo h` [1](#0-0) . It unmarshals the message and only validates that `RelayFromAddr`/`RelayToAddr` are non-nil before dispatching — it never checks that `RelayFromAddr` matches `h`'s certificate-derived identity (`h.vpnAddrs`) [2](#0-1) .

In `handleCreateRelayRequest`, `from` and `target` are taken directly from the attacker-controlled message fields, not from `h.vpnAddrs[0]`: [3](#0-2) 

If `target` is the local node, the code builds/queries `h.relayState` keyed by `from`, and — critically — installs new relay state (`AddRelay(..., h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)`) associating the peer's `HostInfo h` (whose true identity is fixed by its certificate) with an arbitrary `from` address supplied only in the message body: [4](#0-3) 

This is the same bug class as the RLN report: a claimed identity field (`from`, analogous to `account`) is used as a state/lookup key and to authorize/establish behavior, but is never cross-validated against the actual authenticated principal (`h`'s certificate-bound `vpnAddrs`, analogous to the PK-derived `members[...]` check the report recommends). Any already-connected (certificate-holding) peer can claim to be relaying "from" an arbitrary other VPN address it does not own.

### Impact Explanation
An authenticated peer can register itself in a third node's `relayState`/`Relays` map under an address it doesn't actually control, poisoning relay-routing state (`h.relayState.InsertRelay(from, ...)` and `hm.Relays[index] = h`) for that unrelated `vpnAddr`. This mirrors the RLN "unrelated account" bypass: the identifier used to gate/attribute state is attacker-supplied rather than derived from the verified credential, allowing remote state poisoning of the relay subsystem (e.g., a peer inserting/overwriting relay associations for an address it isn't entitled to represent), which can affect routing decisions and traffic attribution through that relay for the spoofed address.

### Likelihood Explanation
This path is reachable by any peer that has already completed a normal, certificate-based handshake (an "in-scope" attacker with a valid cert can still exploit trust gaps that exist *after* authentication, similar to how the RLN slasher is a legitimately-permissioned but malicious actor). No packet/ASN.1 parsing bypass or crypto break is required — only sending a crafted `CreateRelayRequest` control message with a `RelayFromAddr` unequal to one's own identity, which the current code never rejects.

### Recommendation
In `relayManager.HandleControlMsg` / `handleCreateRelayRequest` / `handleCreateRelayResponse`, validate that `RelayFromAddr` (and, where applicable, `RelayToAddr` in responses) matches an address actually present in the sending `HostInfo`'s verified certificate (`h.vpnAddrs`), rejecting the control message otherwise — analogous to the RLN fix of validating the claimed account against the certificate-verified identity (`members[poseidonHash(privateKey)]`) rather than trusting the caller-supplied identifier.

### Proof of Concept
1. Node `A` completes a normal handshake with victim node `V` (A holds a valid certificate for VPN address `A_ip`, distinct from any other address `X_ip` it does not own).
2. `A` sends `V` a `NebulaControl_CreateRelayRequest` with `RelayFromAddr = X_ip` (an address `A` does not own) and `RelayToAddr = V_ip`.
3. `V`'s `handleCreateRelayRequest` sees `target == V` (itself), and — without checking that `X_ip` matches `A`'s certificate identity — calls `AddRelay(rm.l, h, f.hostMap, from=X_ip, ...)`, associating `A`'s `HostInfo` with `X_ip` in `V`'s relay state, as shown at [5](#0-4) .
4. `V` now believes `A` is a legitimate relay endpoint for `X_ip`, even though `A` never authenticated as `X_ip`.

Note: I could not fully trace, within the remaining tool budget, every downstream consumer of this poisoned `relayState`/`Relays[index]` entry (e.g., exact packet-forwarding code path in `outside.go`) to confirm the precise end-to-end traffic-redirection consequence; this should be verified further by reading `outside.go`'s relay-forwarding logic and `hostmap.go`'s `RelayState` methods in a full session.

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}
