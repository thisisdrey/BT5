## Title
Multisig-signature precompiles (`ValidateMultiSign` / `BatchValidateSign`) hash user-controlled data without any domain separator, chain ID, or caller binding — enabling cross-contract and cross-chain signature reuse - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts let any deployed smart contract ask the node "does this set of ECDSA signatures satisfy the weight threshold for account X's permission Y over this arbitrary `data`?" The hash that is actually signed/verified is built purely from `(address, permissionId, data)` with no chain ID, no calling-contract address, and no nonce/expiry — the same structural flaw Sherlock M-2 flagged in NFT Port's `Factory.sol` signature scheme.

### Finding Description

`recoverAddrBySign` recovers the signer and the recovered address's weight is checked against the target account's `Permission` (via `TransactionCapsule.getWeight`) with no additional context: [3](#0-2) 

Because the hash is `sha256(address || permissionId || data)`:
- It does not include the address of the calling smart contract (the contract that is requesting the signature check), so the exact same off-chain signature produced for one dApp's `data` payload can be replayed by an unrelated smart contract to satisfy the same check, as long as it reconstructs an identical `data` blob.
- It does not include a chain ID, so a signature produced on one TRON-compatible network is valid verbatim on any other network sharing the same account/permission structure (mainnet vs. Nile/other TRON-based chains).
- It relies entirely on whatever nonce/expiry the calling dApp chooses to embed inside `data` itself; the precompile provides none, so if a dApp's `data` scheme omits a nonce, replay is possible indefinitely.

This mirrors exactly the Sherlock M-2 root cause: a signature-based authorization mechanism that omits an EIP-712-style domain separator (verifying contract address + chain ID) and nonce, making the signature generic and reusable outside its intended context.

### Impact Explanation
Any DApp built on TVM that uses `ValidateMultiSign`/`BatchValidateSign` (opcode-reachable precompiles at fixed addresses, callable by any contract) to gate a privileged action — e.g., authorizing a transfer, withdrawal, or permission change based on an off-chain-collected multisig approval — inherits this weakness. An attacker can:
1. Capture a valid signature set intended for one contract/action and replay it against a different contract that happens to reconstruct the same `(address, permissionId, data)` triple, authorizing an unintended operation (unauthorized account operation / theft of funds gated by this check).
2. Replay signatures across TRON-compatible chains/forks sharing address derivation, since chain ID is absent from the hash.

Given this precompile is a generic building block relied upon by arbitrary user-deployed contracts for permission verification, a successful replay directly leads to unauthorized account operations or fund movement gated by the multisig check — satisfying the "unauthorized account operation / theft of funds" impact bar.

### Likelihood Explanation
Reachable from any account: an unprivileged contract deployer can deploy a contract invoking these precompiles, and any transaction sender can trigger the call. No special privilege (SR/witness/committee) is required — only a contract using this precompile as an authorization gate, which is a documented/intended use case for it. Exploitability further depends on whether the consuming DApp's `data` construction happens to omit its own domain binding, which is exactly the scenario the original report warns integrators about.

### Recommendation
Extend the hash construction inside `ValidateMultiSign`/`BatchValidateSign` (or document a mandatory convention) to bind the signature to an explicit domain: include the TVM chain ID (`CommonParameter`/`ChainConstant`), and ideally the calling contract's own address, in the hashed payload, following an EIP-712-like domain-separated scheme, rather than leaving domain separation entirely to the calling contract's `data` payload. At minimum, update precompile documentation to require callers to embed chain ID + calling-contract address + nonce in `data`, and consider adding a node-level check that reflects `msg.sender` (the calling contract) into the hash by default.

### Proof of Concept
1. Deploy `ContractA`, which calls the `ValidateMultiSign` precompile with `data = abi.encode(actionType, amount, recipient)` to authorize a withdrawal once a quorum of permission keys sign `sha256(address || permissionId || data)`.
2. Deploy `ContractB`, an unrelated contract, that reconstructs the identical `data` tuple (same `actionType`/`amount`/`recipient` encoding) for a different, attacker-controlled purpose (e.g., a different withdrawal target sharing the same encoded fields).
3. Reuse the signatures originally collected for `ContractA`'s call; because the hash in `PrecompiledContracts.java` lines 1062-1064 never incorporates `ContractA`'s address or chain ID, `ContractB` also gets `Pair.of(true, dataOne())` from `ValidateMultiSign`, authorizing the action for `ContractB` without new signer consent.
4. Alternatively, replay the same signed transaction payload on a second TRON-compatible network where the same accounts/permissions are configured, since chain ID is never part of the hash.
