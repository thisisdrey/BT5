### Title
StackerDB chunk signature omits smart_contract_id, enabling cross-contract signature replay - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest` — the digest signed and verified for every StackerDB chunk write — commits only to `slot_id`, `slot_version`, and `data_hash`. It does not include the `smart_contract_id` of the StackerDB the chunk is destined for. This mirrors the reported bug class: a value that materially changes the meaning/destination of a signed action (`final_amount` in the report; here, which StackerDB contract the write applies to) is left out of the signed payload, letting an attacker redirect a validly-signed message.

### Finding Description

This digest is what gets signed in `sign()` and checked in `verify()`: [2](#0-1) 

The database schema explicitly documents that the signer/contract binding is *not* covered by the signature: [3](#0-2) 

The actual write path, `StackerDBTx::try_replace_chunk`, resolves the expected signer for `(smart_contract, slot_id)` out-of-band via `get_slot_validation`, then calls `slot_desc.verify(&slot_validation.signer)`, which only checks the digest above (no contract binding): [4](#0-3) 

The same unbound digest is used on the p2p relay/sync path (`validate_received_chunk` / `PeerNetwork::handle_unsolicited_StackerDBPushChunk`), where the signer address is again looked up per-contract via `get_slot_signer`, and only `slot_metadata.verify(&addr)` — the contract-agnostic digest — gates acceptance: [5](#0-4) 

**Break of equality:** the system implicitly assumes "a chunk signed by address A for slot S" == "authorized only for the specific StackerDB contract that principal manages via that key/slot mapping." Because contract identity is absent from the signed bytes, this equality does not actually hold at the cryptographic layer — it is enforced only by whatever slot/signer table happens to be configured for each contract, checked independently per contract.

### Impact Explanation
If the same StacksAddress is registered as the slot signer for slot `X` in two different StackerDB replicas/contracts (e.g., two different `.signers-...` or application contracts, or a signer's own address reused across multiple StackerDB configs — a realistic configuration since signer/miner keys are frequently reused across contracts), a chunk validly signed for contract A can be replayed verbatim (or even re-broadcast by any observer, since chunks and signatures are public on the wire) into contract B, as long as `slot_id`/`slot_version`/`data_hash` line up with what B's replica expects. This is an unauthorized write to StackerDB state / forged-data propagation: the payload gets accepted, stored (`try_replace_chunk` → `insert_chunk`), and re-broadcast to the whole p2p network via `process_stacker_db_chunks`, causing network-wide propagation of data into a StackerDB it was never intended for.

This does not require the attacker's own key, the node secret, or any admin role — only a previously-published valid `(SlotMetadata, data)` pair for one contract and a target contract sharing the same signer address/slot layout, both of which are public/observable on the p2p network.

### Likelihood Explanation
Likelihood is bounded by how often the same signer address is reused with the same slot index across distinct StackerDB configs. This is plausible in practice: signer/miner keys are long-lived Stacks addresses referenced by multiple boot/application StackerDB contracts, and slot indices are typically small, deterministic values (0, 1, 2, ...) assigned per registered signer, making index collisions across contracts likely rather than incidental.

### Recommendation
Bind the destination `smart_contract_id` (and ideally the intended message/purpose) into `SlotMetadata::auth_digest`, e.g. hash the qualified contract identifier bytes in addition to `slot_id`, `slot_version`, and `data_hash`, and thread the contract id through `sign()`/`verify()`/`recover_pk()`. This requires updating both write paths (`try_replace_chunk`, `validate_received_chunk`) to pass the contract id into `verify`, and is a wire/protocol-breaking change requiring versioning/migration.

### Proof of Concept
1. Attacker (or any network observer) captures a validly-signed `StackerDBChunkData { slot_id: 0, slot_version: N, sig, data }` published to contract A, where the signer address `addr` is registered as slot-0 owner in contract A.
2. Attacker checks (via public StackerDB configuration / on-chain signer set) that `addr` is also registered as the slot-0 signer in contract B (plausible when the same operator key is reused across contract deployments), and that B's current slot-0 version is `< N`.
3. Attacker submits the same `(slot_id, slot_version, sig, data)` chunk to contract B via `POST /v2/stackerdb/{contract_B}/chunks` (or replays it as a `StackerDBPushChunk` p2p message for contract B).
4. `try_replace_chunk`/`validate_received_chunk` for contract B look up B's own configured signer for slot 0 (which happens to be the same `addr`), call `slot_desc.verify(&addr)` against the contract-agnostic digest, and accept — storing and rebroadcasting data that was never signed for contract B.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
