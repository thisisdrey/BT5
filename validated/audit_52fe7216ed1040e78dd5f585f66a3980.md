### Title
Unsynchronized time-of-check to time-of-use race in pending-transaction throttling allows unbounded queue growth under transaction bursts - (File: framework/src/main/java/org/tron/core/db/Manager.java)

### Summary
Arbitrum's outage stemmed from the Sequencer becoming stuck after receiving a large number of transactions in a short window because a resource-tracking/limiting mechanism wasn't robust against a burst. java-tron's `Wallet.broadcastTransaction` performs an admission check (`dbManager.isTooManyPending()`) before adding the transaction to `Manager.pushTransactionQueue`, but the check and the enqueue are not atomic with respect to each other, so under a burst of concurrent broadcasts the size limit is not actually enforced.

### Finding Description
`Wallet.broadcastTransaction` gates admission with: [1](#0-0) 
which calls `Manager.isTooManyPending()`: [2](#0-1) 
`isTooManyPending()` is a plain, unsynchronized read of `getCachedTransactionSize()` (`pushTransactionQueue.size() + pendingTransactions.size() + rePushTransactions.size()`) compared to `maxTransactionPendingSize` (default 2000, `common/src/main/resources/reference.conf:358`).

Immediately after this check passes, `Wallet.broadcastTransaction` calls `dbManager.pushTransaction(trx)`, which unconditionally appends to the unbounded `pushTransactionQueue` (`new LinkedBlockingQueue<>()`, no capacity bound): [3](#0-2) [4](#0-3) 

Because `broadcastTransaction` is reachable concurrently from many unprivileged callers (HTTP `BroadcastServlet`, gRPC `Wallet` service, JSON-RPC), many threads can simultaneously observe `isTooManyPending() == false` before any of them has incremented the queue, and all proceed to enqueue. There is no lock, semaphore, or atomic counter reservation between the check and the enqueue, so the effective limit of `maxTransactionPendingSize` is not enforced under concurrent load — this is exactly the class of bug the Arbitrum report describes: a limiter/queue that is not robust to a burst of many transactions arriving in a short period, leading to the processing component (Sequencer there, the transaction-admission/queue pipeline here) becoming overwhelmed/stuck.

Once `pushTransactionQueue` grows unbounded, every enqueued transaction still proceeds to `trx.validateSignature(...)` and then serializes on `synchronized (transactionLock)` inside `pushTransaction`: [5](#0-4) 
Because this section is fully serialized (only one thread executes the body between `synchronized (transactionLock)` and `synchronized (this)` at a time) while the queue keeps growing, the backlog of pushed-but-unprocessed transactions consuming heap grows without bound, and the block-producing/transaction-processing threads that acquire `transactionLock`/`this` are increasingly delayed, degrading availability similarly to the Sequencer stall.

### Impact Explanation
An unprivileged client can send a burst of concurrent `broadcastTransaction` calls (via gRPC, HTTP `/wallet/broadcasttransaction`, or JSON-RPC's `eth_sendRawTransaction` path that ultimately funnels through the same `Manager`/`Wallet` broadcast logic) fast enough that the racey check-then-act pattern allows the effective pending-queue bound to be bypassed. This can drive `pushTransactionQueue` far past the configured `maxTransactionPendingSize`, consuming memory and CPU (signature validation for every queued item) and increasing serialized-lock contention, resulting in degraded throughput or node instability — an availability/DoS impact on a full node's transaction-serving API, matching "node crash or halt" / "an API the node can no longer serve" criteria.

### Likelihood Explanation
The race window is small per request pair, but it is trivially amplified: an attacker just needs to fire many concurrent broadcast requests (no special privileges, keys, or SR/witness status required — any client with network access to the node's HTTP/gRPC/JSON-RPC endpoint can do this). Standard thread pools serving these endpoints allow many requests in flight simultaneously, so the probability of many threads passing the `isTooManyPending()` check before any of them enqueues is high during a burst, making this readily reachable by design rather than a theoretical/rare timing coincidence.

### Recommendation
Make the admission check and the enqueue atomic: reserve a slot (e.g., via an `AtomicInteger` counter that is incremented under CAS before enqueue and decremented on completion/removal, or perform the check inside the same lock used later in `pushTransaction`) so the effective queue size can never exceed `maxTransactionPendingSize` regardless of concurrency. Additionally, consider bounding `pushTransactionQueue` itself with a fixed capacity (`new LinkedBlockingQueue<>(maxTransactionPendingSize)`) and using `offer()` with a false-return rejection path instead of relying solely on the separate `isTooManyPending()` pre-check.

### Proof of Concept
1. Configure a node with default `maxTransactionPendingSize = 2000`.
2. From an unprivileged client, open N concurrent connections (HTTP/gRPC) and issue `broadcastTransaction` calls for N distinct valid, signed transactions simultaneously, where N significantly exceeds 2000 (e.g., 5000), sent within a very short window so they arrive before `pushTransactionQueue` fills relative to the limit.
3. Because each thread independently evaluates `dbManager.isTooManyPending()` (Manager.java:2099-2101) before calling `pushTransaction`, and there is no synchronization between the check and the `pushTransactionQueue.add(trx)` call (Manager.java:901), observe that `getCachedTransactionSize()` can exceed `maxTransactionPendingSize` by a large margin instead of being capped, evidenced by memory growth and increasing latency/backlog in transaction processing rather than the expected `SERVER_BUSY` rejection once the limit is reached.
