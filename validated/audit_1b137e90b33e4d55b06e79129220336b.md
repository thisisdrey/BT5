### Title
Zero-cost self-conflicting transactions can inflate `SchedulerPriorityFloor`, causing sigverify to silently drop unrelated honest transactions pre-verification - (File: `core/src/banking_stage/transaction_scheduler/scheduler_controller.rs`)

### Summary
`SchedulerController::update_scheduler_priority_floor` publishes the *current minimum priority of the buffered (unexecuted) transaction container* as a floor that `SigVerifyStage` uses to drop incoming packets before signature verification. Because the priority formula `P = R / (1 + C)` rewards low compute-cost transactions independent of whether they ever execute or pay any fee, and buffered transactions that never get scheduled (e.g. self-conflicting, or held while the node is not leader) never have their fee actually collected, an attacker can cheaply fill the buffer with minimal-compute-unit, minimal-fee "dust" transactions that never execute, driving `priority_floor` above the priority of legitimate, real-fee-paying transactions from unrelated senders.

### Finding Description
`update_scheduler_priority_floor` [1](#0-0)  computes `saturated` from `SaturationState::update`, which flips to saturated once `buffer_size` (the raw map size, including scheduled-but-not-finished and unscheduled entries, not just the priority queue) reaches 99% of `TOTAL_BUFFERED_PACKETS` [2](#0-1) . When saturated, it publishes `container.get_min_max_priority().min` as the floor into the shared `SchedulerPriorityFloor` [3](#0-2) , an `Arc` explicitly shared with sigverify workers [4](#0-3) [5](#0-4) .

In `run_transaction_task`, sigverify applies this floor to incoming packets, dropping at-or-below-floor arrivals, explicitly *before* full signature verification completes ("ahead of signature verification") [6](#0-5) [7](#0-6) .

Priority itself is computed as `P = R / (1 + C)` where `R` is the fee reward and `C` is the estimated compute cost [8](#0-7) . This formula deliberately rewards low-cost transactions, so a transaction with a tiny `compute_unit_limit` yields high `P` even for a tiny fee `R`. Transactions are admitted into the container after only a static sanitize + `check_fee_payer_unlocked` balance check — which validates the fee payer *can* pay, but does not deduct the fee [9](#0-8) [10](#0-9) . The fee is only actually collected when the transaction is scheduled and executed by a bank. Transactions that sit in the buffer during `Hold`/`ForwardAndHold` decisions (non-leader windows) are received and buffered but never scheduled/executed [11](#0-10) [12](#0-11) , so an attacker can construct minimal-CU, minimal-fee, mutually write-locked ("self-conflicting") transactions from a single funded but never-actually-charged fee payer, sign them (a real but cheap per-packet cost), and flood them to raise `buffer_size` toward `SATURATION_BUFFER_PCT` (99%). Once saturated, `get_min_max_priority().min` reflects the lowest-priority item still retained, which — because the attacker fully controls the priority distribution of dust filling the buffer — can be tuned above the priority of a legitimate but comparatively higher-compute-cost transaction from an unrelated sender, causing sigverify to drop it silently before verification.

### Impact Explanation
This allows an unprivileged, unstaked remote sender to cause silent, pre-verification drops of unrelated users' honestly fee-paying transactions at a specific leader's TPU, purely through floor manipulation with dust that costs the attacker no actual transaction fee (fees aren't collected unless scheduled/executed). This matches the "grossly underpriced pre-fee work" / QoS-evasion bounty category, since verification-stage decisions about unrelated legitimate traffic are being made based on unexecuted, unpaid attacker-controlled priority values.

### Likelihood Explanation
Preconditions are attacker-favorable per rules (unstaked remote sender, no lock conflicts needed with victim transactions). However, feasibility is bounded by:
- Container capacity (`TOTAL_BUFFERED_PACKETS`) is large; I could not confirm its exact numeric value in this session, which materially affects how much sustained throughput the attacker needs.
- Unstaked QUIC/UDP senders are subject to existing per-connection/per-IP QoS and stake-weighted throttling (`streamer/src/nonblocking/simple_qos.rs`, `swqos.rs`, `token_bucket.rs`), which likely constrains how quickly an unstaked attacker can push enough uniquely-signed, sanitizable, fee-payer-valid transactions to reach the 99% watermark — I was not able to fully verify within this session whether these existing QoS layers are sufficient to make the attack impractical.
- The floor is transient: `SaturationState` desaturates and clears the floor once buffer drains below 95% or `Drop`s [13](#0-12) , so the attacker must sustain the flood continuously to keep honest transactions suppressed.

Given the unresolved uncertainty on QoS effectiveness against this specific pattern and exact buffer sizing, likelihood is plausible but not fully confirmed as practically exploitable at scale from a single unstaked sender without further empirical testing.

### Recommendation
Do not use the *unexecuted, unpaid* buffered-transaction minimum priority as an authoritative floor for dropping unrelated arrivals pre-verification. Consider: (1) computing the floor only from transactions that have a proven non-trivial probability of executing (e.g., excluding held/self-conflicting transactions that have sat unscheduled beyond some age), (2) requiring some minimum absolute fee/cost floor independent of the R/(1+C) ratio to prevent near-zero-cost dust from ever registering a meaningfully high priority, or (3) rate-limiting/deduping by fee-payer to prevent one funded account from filling the buffer with many unpaid, unexecuted, self-conflicting entries.

### Proof of Concept
Integration test plan (extends `saturation_state_tests` / `receive_and_buffer` test harnesses):
1. Set up a `TransactionViewStateContainer` / `SchedulerController` with a small `TOTAL_BUFFERED_PACKETS`-equivalent capacity for test tractability, and a shared `SchedulerPriorityFloor`.
2. Generate `N` transactions from a single funded fee payer, each writing to the same account (mutually conflicting), each with `compute_unit_limit` set to the minimum and a minimal `compute_unit_price`, so `P = R/(1+C)` is high despite tiny `R`.
3. Feed these through `receive_and_buffer` under a `Hold`/`ForwardAndHold` decision (so none are scheduled/executed) until `container.buffer_size()` crosses the 99% `saturation_watermark`.
4. Assert `SchedulerPriorityFloor::get()` becomes non-zero and equals the min priority of attacker dust.
5. Craft a "genuine" transaction from a second funded keypair with a realistic, larger `compute_unit_limit` and a reasonable priority fee such that its computed `P` (via `calculate_priority_from_bytes`) falls below the published floor.
6. Feed this genuine packet through `sigverify::run_transaction_task`'s `apply_priority_floor_to_batch` path and assert it is dropped (`dropped > 0` / `all_below == true`) before any signature-verification call, demonstrating unrelated-user drop caused solely by attacker-controlled, unpaid dust.

/// Publish the priority floor once the scheduler's retained transaction buffer is
/// this full. Capacity is enforced on the buffer, not just the priority queue:
/// scheduled transactions still occupy buffer space until workers finish them.
const SATURATION_BUFFER_PCT: u8 = 99;
/// Clear the priority floor once the retained buffer drains below this watermark.
const DESATURATION_BUFFER_PCT: u8 = 95;

#[derive(Clone)]
pub struct SchedulerConfig {
    pub scheduler_pacing: SchedulerPacing,
}

impl Default for SchedulerConfig {
    fn default() -> Self {
        Self {
            scheduler_pacing: SchedulerPacing::FillTimeMillis(
                DEFAULT_SCHEDULER_PACING_FILL_TIME_MILLIS,
            ),
        }
    }
}

const DEFAULT_SCHEDULER_PACING_NON_FILL_TIME_MILLIS: u64 = 50;
pub(crate) const DEFAULT_SCHEDULER_PACING_FILL_TIME_MILLIS: NonZeroU64 =
    NonZeroU64::new(DEFAULT_MS_PER_SLOT - DEFAULT_SCHEDULER_PACING_NON_FILL_TIME_MILLIS).unwrap();

/// Detects saturation and publishes the priority floor for dropping low-priority transactions upstream.
struct SaturationState {
    priority_floor: Arc<SchedulerPriorityFloor>,
    saturated: bool,
    saturation_watermark: usize,
    desaturation_watermark: usize,
}

impl SaturationState {
    fn new(priority_floor: Arc<SchedulerPriorityFloor>, container_capacity: usize) -> Self {
        let saturation_watermark =
            container_capacity.saturating_mul(SATURATION_BUFFER_PCT as usize) / 100;
        let desaturation_watermark =
            container_capacity.saturating_mul(DESATURATION_BUFFER_PCT as usize) / 100;
        Self {
            priority_floor,
            saturated: false,
            saturation_watermark,
            desaturation_watermark,
        }
    }

    /// Update the saturation state.
    fn update(&mut self, buffer_size: usize, num_dropped_on_capacity: usize) -> bool {
        if self.saturated {
            if buffer_size < self.desaturation_watermark && num_dropped_on_capacity == 0 {
                self.saturated = false;
            }
        } else if buffer_size >= self.saturation_watermark || num_dropped_on_capacity > 0 {
            self.saturated = true;
        }

        self.saturated
    }

    /// Publish the priority floor.
    fn publish_floor(&self, floor: u64) {
        self.priority_floor.set(floor);
    }
}

impl Drop for SaturationState {
    fn drop(&mut self) {
        // The priority floor outlives individual scheduler controllers (it's
        // shared with sigverify). Clear it on tear-down so a stale floor
        // from this controller can't keep sigverify dropping packets.
        self.priority_floor.clear();
    }
}

/// Priority floor shared from the banking-stage scheduler to sigverify.
///
/// When saturated, the scheduler publishes the queue-min transaction's
/// priority. Sigverify drops at-or-below-floor arrivals.
/// In practice, transactions always have non-zero priorities.
#[derive(Debug)]
pub struct SchedulerPriorityFloor(AtomicU64);

impl SchedulerPriorityFloor {
    pub fn new() -> Self {
        Self(AtomicU64::new(0))
    }

    pub fn set(&self, floor: u64) {
        self.0.store(floor, Ordering::Relaxed);
    }

    pub fn clear(&self) {
        self.set(0);
    }

    pub fn get(&self) -> u64 {
        self.0.load(Ordering::Relaxed)
    }
}

/// Calculate priority and cost for a transaction:
///
/// Cost is calculated through the `CostModel`,
/// and priority is calculated through a formula here that attempts to sell
/// blockspace to the highest bidder.
///
/// The priority is calculated as:
/// P = R / (1 + C)
/// where P is the priority, R is the reward,
/// and C is the cost towards block-limits.
///
/// Current minimum costs are on the order of several hundred,
/// so the denominator is effectively C, and the +1 is simply
/// to avoid any division by zero due to a bug - these costs
/// are calculated by the cost-model and are not direct
/// from user input. They should never be zero.
/// Any difference in the prioritization is negligible for
/// the current transaction costs.
pub(crate) fn calculate_priority_and_cost<Tx: TransactionMeta + SVMStaticMessage>(
    bank: &Bank,
    transaction: &Tx,
    transaction_configuration: &TransactionConfiguration,
) -> (u64, u64) {
    let cost = CostModel::calculate_cost_for_executed_transaction(
        transaction,
        u64::from(transaction_configuration.compute_unit_limit),
        transaction_configuration.loaded_accounts_data_size_limit,
        &bank.feature_set,
    )
    .sum();
    let fee_details = solana_fee::calculate_fee_details(
        transaction,
        bank.fee_structure().lamports_per_signature,
        transaction_configuration.priority_fee_lamports,
        bank.fee_features(),
    );
    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    (
        reward
            .saturating_mul(MULTIPLIER)
            .saturating_div(cost.saturating_add(1)),
        cost,
    )
