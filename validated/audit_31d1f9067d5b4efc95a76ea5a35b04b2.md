### Title
Unbounded prefix-scan in `DelegatedResourceAccountIndexStore#getWithPrefix` allows unauthorized-transaction-triggered DoS of delegated-resource query APIs - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
`DelegateResourceContract` (a broadcastable, unprivileged transaction type) lets any account with as little as 1 TRX frozen create a new resource-delegation record to an arbitrary distinct receiver address. Each such delegation is written as a separate key-value entry keyed by `V2_FROM_PREFIX/from/to` and `V2_TO_PREFIX/to/from` in `DelegatedResourceAccountIndexStore`. There is no cap on the number of distinct receivers (or senders) one address can accumulate this way. When the delegated-resource index for that address is later read (`getV2Index`/`getIndex`), the store performs a full prefix scan and in-memory sort over every entry that has ever been created for that address, with no size limit — directly analogous to the reported `ProtectionPool#lockCapital` pattern where an attacker inflates an array via cheap repeated transactions and a later required operation must iterate over the entire unbounded collection.

### Finding Description
`DelegateResourceActuator.execute()` (actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java) calls `delegateResource()`, which invokes `delegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress, timestamp)` [1](#0-0) . `delegateV2` writes two new raw KV entries — one keyed `V2_FROM_PREFIX+from+to` and one keyed `V2_TO_PREFIX+to+from` — for every unique `(from,to)` pair, with no bound on how many such pairs may exist for a given address [2](#0-1) .

The validation path (`DelegateResourceActuator.validate()`) only checks that `delegateBalance >= 1 TRX`, that the receiver is a valid, non-contract, non-self address, and that sufficient frozen balance exists — it never checks how many distinct receivers the owner has already delegated to [3](#0-2) . Because the minimum delegable amount is only 1 TRX, an attacker who freezes a moderate amount of TRX for bandwidth/energy can then issue many cheap `DelegateResourceContract` transactions to newly generated, distinct receiver addresses, each creating new prefixed keys.

Later, whenever the index for that address is reconstructed via `getWithPrefix()` (used by both `getIndex()` and `getV2Index()`), the code performs an unbounded `prefixQuery`, collects all matching values into a `List`, sorts them with a `Comparator`, and streams/maps them into a `List<ByteString>` — twice (once for the "to" prefix, once for the "from" prefix) [4](#0-3) . There is no limit on the number of entries scanned or returned.

This method is reachable from multiple unauthenticated/low-privilege read paths that any API client can invoke: `Wallet.getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` [5](#0-4) , exposed via gRPC (`RpcApiService.getDelegatedResourceAccountIndex`/`V2`) [6](#0-5) , and via HTTP servlets such as `GetDelegatedResourceAccountIndexV2Servlet` [7](#0-6) .

### Impact Explanation
An attacker can cheaply (1 TRX per unique receiver, reusable across many freshly-generated receiver addresses) inflate the prefix-scanned key set for a single account to an arbitrarily large size. Subsequent legitimate queries of that address's delegated-resource index (`GetDelegatedResourceAccountIndex`/`V2` over HTTP or gRPC) force the node to perform an unbounded LevelDB/RocksDB prefix iteration plus an in-memory `Comparator` sort over the entire result set on every single request. Repeated or concurrent queries against a poisoned address can consume excessive CPU/I/O on the serving node, degrading or denying that query API for all clients — a concrete "API the node can no longer serve" condition. Because this is a full node/solidity/PBFT node HTTP+gRPC surface, it affects service availability rather than consensus state directly (this differentiates it in severity from a genuine block-processing halt, but it is still a High-severity resource-exhaustion/DoS vector triggerable by an unprivileged single-signer transaction stream).

### Likelihood Explanation
High. The precondition is trivial: `DelegateResourceContract` is a normal, unprivileged, broadcastable transaction; only 1 TRX of frozen balance is required per delegation, and receiver addresses can be freshly generated (no funding needed on the receiver besides existing as an `AccountCapsule`, and receivers must simply not be contracts). An attacker can script thousands of low-cost delegate transactions to inflate one address's prefix key set, then repeatedly hit the public query APIs to induce load.

### Recommendation
- Enforce an upper bound (e.g., `MAX_DELEGATE_TO_COUNT`) in `DelegateResourceActuator.validate()`/`DelegateResourceProcessor.validate()` on the number of distinct `(from,to)` delegation index entries an address may accumulate, similar to `MAX_VOTE_NUMBER` in `VoteWitnessProcessor.validate()`.
- Add pagination/limits to `DelegatedResourceAccountIndexStore#getWithPrefix` (bound the `prefixQuery` result count, or require callers to page through results) instead of loading and sorting the entire matching key set in memory on every query.
- Consider rate-limiting or requiring a minimum non-trivial delegation size that scales with the number of existing delegations to make index inflation economically costly.

### Proof of Concept
1. Freeze balance for bandwidth or energy on account `A` (`FreezeBalanceV2Contract`).
2. For `i` in `1..N` (N large, e.g. 50,000): generate a new receiver address `R_i` (create an on-chain account for it, e.g. via a small TRX transfer), then broadcast `DelegateResourceContract{owner=A, receiver=R_i, balance=1_TRX, resource=BANDWIDTH}`. Each call succeeds under current validation in `DelegateResourceActuator.validate()` and adds two new prefixed keys via `delegatedResourceAccountIndexStore.delegateV2` [2](#0-1) .
3. Call `GET /wallet/getdelegatedresourceaccountindexv2?value=A` (or the gRPC equivalent) repeatedly. Each call triggers `getV2Index(A)` → `getWithPrefix(...)`, which performs a full `prefixQuery` scan and sort over all `N` accumulated entries [4](#0-3) , causing increasing CPU/I/O cost proportional to `N` on every request, degrading the node's ability to serve this API to other clients.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
