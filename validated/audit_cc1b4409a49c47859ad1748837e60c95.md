### Title
Attacker can fill a victim's `depositTokensOfAccount`/`debtTokensOfAccount` list to `MAX_TOKENS_PER_USER` via dust transfers, DoS-ing the victim's minting, deposits, and token receipt - ([File: contracts/Pool.sol])

### Summary
The lol-html advisory is a "panic on crafted input → DoS" bug class: a valid public entry point reverts unconditionally once an attacker engineers the victim into a hostile state. In Metronome, the analog is `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount`, gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts `UserReachedMaxTokens` whenever an account's combined token list reaches `MAX_TOKENS_PER_USER = 30`. Because every `DepositToken.transfer`/`_mint`/`seize` and every `DebtToken` mint unconditionally calls the corresponding `addTo*` function when the recipient's balance transitions 0→nonzero, an unprivileged attacker can dust-flood a victim with `1 wei` of every whitelisted deposit token and permanently (until manually cleaned) revert the victim's `issue`/`mint`, `deposit onBehalfOf`, inbound transfers, and liquidation-related seizures.

### Finding Description
`Pool.sol:79` defines `MAX_TOKENS_PER_USER = 30`. The modifier `onlyIfAdditionWillNotReachMaxTokens` (Pool.sol:143-148) reverts `UserReachedMaxTokens` when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`. It guards `addToDebtTokensOfAccount` (Pool.sol:204) and `addToDepositTokensOfAccount` (Pool.sol:216), which are callable only by registered tokens.

Those callbacks are invoked from `DepositToken._mint` (DepositToken.sol:486-488) and `DepositToken._transfer` (DepositToken.sol:518-525) whenever the recipient's balance was previously zero — including `seize()` called by `Pool.liquidate` (Pool.sol:589-592) and fee/mint flows — and from `DebtToken._mint` on `issue`/`mint`/`flashIssue` when the victim's debt balance goes 0→nonzero.

Attack path (all public, unprivileged):

1. Attacker deposits a dust amount (e.g. `1 wei` net) of each whitelisted collateral via `DepositToken.deposit(amount, attacker)`, receiving msdTokens.
2. Attacker calls `depositToken.transfer(victim, 1)` for up to 30 distinct deposit tokens. Each transfer hits `_revertIfLocked` (only checks the sender) and then `_transfer`, which calls `pool.addToDepositTokensOfAccount(victim)` since the victim's balance was 0 (DepositToken.sol:518-520). No health check, allowance, or consent is required of the recipient.
3. Victim's `depositTokensOfAccount.length` reaches 30. From then on, every code path that would add a new token to the victim's list reverts `UserReachedMaxTokens`:
   - `DebtToken.issue`/`mint`/`flashIssue` of any synthetic the victim doesn't already hold → revert on `addToDebtTokensOfAccount`.
   - `DepositToken.deposit(x, onBehalfOf = victim)` (third-party deposits, zaps, leverage flows crediting the victim) → revert in `_mint`.
   - `depositToken.transfer(victim, ...)` of any new collateral → revert in `_transfer`.
   - `depositToken.seize(victim → liquidator)` is unaffected for existing tokens, but any flow crediting the *victim* a new token type reverts, and `SmartFarmingManager` leverage/flashRepay paths that mint or transfer new tokens `onBehalfOf` the victim revert.

Cleanup requires the victim to fully zero out each dusted token (transfer whole balance so `removeFromDepositTokensOfAccount` fires at DepositToken.sol:523-525), which costs 30+ transactions and must race a re-dusting attacker.

### Impact Explanation
Temporary freezing of funds / liveness break on a core invariant: a victim with healthy collateral cannot issue debt, cannot receive deposits or collateral transfers on their behalf, and cannot be credited new deposit tokens through `SmartFarmingManager` leverage. All reverts are unconditional `UserReachedMaxTokens` failures — the direct analog of lol-html panicking on inputs that put the parser in a bad state. The freeze persists until the victim performs gas-costly cleanup, and the attacker can re-apply it cheaply, so it is effectively indefinite for as long as the attacker keeps the list saturated.

### Likelihood Explanation
Requires only an EOA, dust capital across whitelisted collaterals (deposits are permissionless, `DepositToken.deposit` has no minimum), and ordinary `transfer` calls. No governor/guardian/keeper involvement, no oracle manipulation, no privileged state. `MAX_TOKENS_PER_USER = 30` and the `>=` check in `onlyIfAdditionWillNotReachMaxTokens` are in the deployed configuration (deployments/*/Pool.json). Reentrancy guards, `whenNotPaused`, and SynthContext meta-sender checks do not mitigate it — the revert happens inside the token's own `_transfer`/`_mint` bookkeeping.

### Recommendation
Do not couple token receipt to per-account list membership in a way strangers can manipulate. Concretely: (a) in `DepositToken._transfer`/`_mint`, skip reverting the transfer when the cap is hit — either ignore the add or allow it; enforce `MAX_TOKENS_PER_USER` only on actions the account initiates that enlarge its own position surface (e.g. `issue`, first `deposit` initiated by the account), or (b) track lists per-account only for tokens the account explicitly opted into, or (c) raise/remove the cap and bound `debtPositionOf`/`depositOf` gas by capping the number of pool-level tokens instead.

### Proof of Concept
Hardhat fork sketch (existing `test/Pool.test.ts` fixtures):

```ts
// attacker dusts victim's deposit-token list to MAX_TOKENS_PER_USER
for (const dToken of allDepositTokens /* up to 30 whitelisted collaterals */) {
  await underlying.connect(attacker).approve(dToken.address, DUST_GROSS)
  await dToken.connect(attacker).deposit(DUST_GROSS, attacker.address)
  await dToken.connect(attacker).transfer(victim.address, 1) // adds entry for victim
}
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(30)

// victim can no longer mint a new synthetic: DebtToken._mint -> addToDebtTokensOfAccount reverts
await expect(
  msEth.connect(victim).issue(MINT_AMOUNT, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// third-party deposit on behalf of victim reverts inside _mint
await expect(
  newCollateralToken.connect(donor).deposit(AMOUNT, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// inbound transfer of a new deposit token to victim reverts inside _transfer
await expect(
  anotherDToken.connect(attacker).transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```
