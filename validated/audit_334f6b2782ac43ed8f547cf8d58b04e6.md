Audit Report

## Title
Fee-on-transfer / reverting ERC20 tokens permanently strand user funds in the `TransfersCheckingAccount` of `ERC20Transactor` - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` credits a fixed-amount, purely in-memory `Erc20Credit(amount)` into `AssetsInHolding` as soon as the withdraw-leg `IERC20::transfer` call returns `true`, without verifying that `TransfersCheckingAccount` actually received `amount` tokens. If the deposit leg's subsequent `transfer` from the checking account to the beneficiary later fails (e.g., because the token deducted a transfer fee, or a transfer restriction triggers), the real tokens left in `TransfersCheckingAccount` become permanently disconnected from any recoverable XCM accounting entry.

## Finding Description
In `withdraw_asset_with_surplus`, the withdraw-side `IERC20::transfer(checking_address, amount)` call is issued via `pallet_revive::Pallet::<T>::bare_call`, and on a `true` boolean return, the function unconditionally mints `Erc20Credit(amount)` into `AssetsInHolding`: [1](#0-0)  There is no balance check on `TransfersCheckingAccount` before/after the call to confirm it actually received `amount`.

`Erc20Credit` is a bare `u128` wrapper implementing only the imbalance-accounting traits (`UnsafeConstructorDestructor`, `UnsafeManualAccounting`, `ImbalanceAccounting`), with no linkage to any on-chain balance: [2](#0-1) 

`deposit_asset_with_surplus` later attempts `IERC20::transfer(beneficiary, amount)` from `TransfersCheckingAccount`. If this call reverts, returns `false`, or fails to decode, the function returns the still-fictitious `AssetsInHolding` (`what`) back to the caller as an XCM error: [3](#0-2)  This triggers the XCM executor's asset-trapping/`ClaimAsset` machinery, but since `Erc20Credit` carries no reference to the real, fee-reduced balance actually sitting in `TransfersCheckingAccount`, any retry via `ClaimAsset` simply re-attempts the identical deposit-leg transfer against the same insufficient checking-account balance, failing identically forever.

The repository's own regression test only exercises the case where the deposit-leg contract call returns a non-bool value (still causing an intentional, immediate failure), not the fee-on-transfer/partial-receipt scenario where the withdraw leg succeeds but leaves less than `amount` in the checking account: [4](#0-3)  confirming no existing guard addresses this gap.

## Impact Explanation
This matches the "permanent user-fund ... lock" impact category: real ERC20 tokens transferred into `TransfersCheckingAccount` become unrecoverable once the deposit leg fails for a non-standard token, because the trapped `Erc20Credit` accounting entry is decoupled from the checking account's actual, fee-adjusted balance, and no code path reconciles or refunds the real leftover balance.

## Likelihood Explanation
No privileged actor is required — any user constructing a reserve-asset XCM transfer through `ERC20Transactor` for a fee-on-transfer, pausable, or deny-list-capable ERC20 token (a common class of real-world token) will trigger the mismatch between the amount debited from the sender and the amount later transferable out of the checking account. This is a normal, non-privileged operational path once such a token is configured/matched as a reserve asset for the transactor.

## Recommendation
- Measure the actual amount received by `TransfersCheckingAccount` (e.g., via a `balanceOf` delta check) after the withdraw-leg `transfer`, and credit `Erc20Credit` with that verified amount instead of the requested `amount`.
- On deposit-leg failure, avoid treating the unbacked `Erc20Credit` as a standard trappable/reclaimable XCM asset; instead maintain a reconciled per-account real-balance ledger for `TransfersCheckingAccount` and provide an explicit sweep/refund mechanism tied to the failed instruction/context.
- Alternatively, wrap all ERC20 `transfer` calls in both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` with pre/post balance verification, and restrict registrable reserve assets to tokens verified to be amount-preserving on transfer.

## Proof of Concept
1. Register a fee-on-transfer ERC20 token `T` (e.g., 5% fee) as a reserve asset routed through `ERC20Transactor`.
2. Send XCM `WithdrawAsset(T, 1000)`: `withdraw_asset_with_surplus` calls `T.transfer(checking_account, 1000)`; the checking account's real balance rises by only 950, yet `AssetsInHolding` is credited with `Erc20Credit(1000)` per lines 195-203 of `erc20_transactor.rs` because the boolean return was `true`.
3. Execute `DepositAsset(T, 1000, beneficiary)`: `deposit_asset_with_surplus` calls `T.transfer(beneficiary, 1000)` from the checking account, which only holds 950, causing the ERC20 `transfer` to fail/return `false`.
4. `deposit_asset_with_surplus` returns `Err((what, XcmError::FailedToTransactAsset(...)))` (lines 281-287), and the XCM executor traps `Erc20Credit(1000)` or offers it via `ClaimAsset`.
5. Any subsequent `ClaimAsset` + `DepositAsset` retry repeats step 3 identically, permanently locking the real 950 tokens in `TransfersCheckingAccount`.

	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}

impl UnsafeManualAccounting<u128> for Erc20Credit {
	fn saturating_subsume(&mut self, mut other: Box<dyn ImbalanceAccounting<u128>>) {
		let amount = other.forget_imbalance();
		self.0 = self.0.saturating_add(amount);
	}
}

impl ImbalanceAccounting<u128> for Erc20Credit {
