### Title
Unprivileged dust-transfer griefing fills a victim's per-account token list to `MAX_TOKENS_PER_USER`, DoS-ing new collateral deposits and debt issuance - ([File: contracts/Pool.sol])

### Summary
The CVE's bug class is a failed resource allocation (`alloc_percpu` returning NULL) causing a denial of service. The direct Metronome analog is the bounded per-account token lists `depositTokensOfAccount` / `debtTokensOfAccount`, capped at `MAX_TOKENS_PER_USER = 30`. `DepositToken` is a freely transferable ERC20, and every `_transfer`/`_mint` that gives a recipient a nonzero balance for the first time calls `pool.addToDepositTokensOfAccount(recipient)` [1](#0-0) , which reverts with `UserReachedMaxTokens` once the combined list length hits 30 [2](#0-1) . An attacker can deposit tiny amounts of each listed collateral and `transfer` 1-wei dust positions to a victim, occupying slots the victim never asked for, until any new-token `deposit()`, `issue()`, or inbound transfer reverts.

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` enforce the combined cap via `onlyIfAdditionWillNotReachMaxTokens` [3](#0-2) .
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever `recipient_`'s prior balance is zero, with no opt-in or approval from the recipient [4](#0-3) .
- `DepositToken._mint` does the same on first receipt [5](#0-4) , so `deposit(amount_, onBehalfOf_)` reverts for any *new* collateral type once the victim's list is full [6](#0-5) .
- `DebtToken._mint` similarly calls `addToDebtTokensOfAccount` on first debt [7](#0-6) , so `issue()` reverts for any synthetic the victim does not already owe [8](#0-7) .

Attack path (all public entry points, no privileged roles):
1. Attacker calls `depositToken.deposit(dust, attacker)` for each listed collateral, then `depositToken.transfer(victim, 1)` — allowed because `transfer` only requires the *sender's* balance be unlocked [9](#0-8) .
2. Each first-time dust receipt appends to `depositTokensOfAccount[victim]`.
3. When `len(depositTokensOfAccount[victim]) + len(debtTokensOfAccount[victim]) == 30`, every subsequent `deposit` into a new collateral, `issue` of a new synthetic, and even *inbound* transfers/seizures of new tokens revert.

### Impact Explanation
Temporary freezing of funds / liveness degradation: the victim cannot add any collateral type they don't already hold. For a position drifting toward liquidation, the victim may be unable to deposit the specific new collateral needed to restore health — forcing liquidation even though the victim holds that underlying. The victim can only free a slot by manually transferring each dust position away (paying gas per token and racing re-griefing). This mirrors the CVE: a per-account allocation table fails on insertion, blocking service.

Important constraint: `debtToken`s are non-transferable (`transfer`/`transferFrom` revert) [10](#0-9) , and only the governor can list deposit/debt tokens (pool-side cap is also 30 [11](#0-10) ). The attack therefore only fills as many slots as the pool has listed deposit tokens; on pools with few collaterals the cap may be unreachable. Feasibility is deployment-dependent.

### Likelihood Explanation
Requires a pool listing close to 30 deposit tokens for the attacker to force the victim to the cap unilaterally; with fewer listed collaterals the attacker can still consume all remaining free slots, so any victim with existing positions becomes unable to use a new collateral type. Cost is dust deposits plus gas for up to ~30 transfers. No privileged actor needed. Severity is bounded because the victim can shed slots by transferring dust out.

### Recommendation
Make list insertion non-reverting under the cap (e.g., emit and skip), or remove per-user caps and rely on off-chain iteration, or require recipient opt-in for first-time token list insertion, or exclude dust transfers by only adding to the list on `deposit`/`issue` rather than on arbitrary `transfer`.

### Proof of Concept
Foundry fork test outline:

```solidity
// contracts/Pool.sol cap: MAX_TOKENS_PER_USER = 30
function test_dustGriefingBlocksNewDeposits() public {
    // victim already holds some deposit/debt tokens
    uint256 slotsToFill = 30 - pool.getDepositTokensOfAccount(victim).length
                        - pool.getDebtTokensOfAccount(victim).length;

    // attacker: deposit 1 wei of each listed collateral, then dust-transfer to victim
    address[] memory dts = pool.getDepositTokens();
    for (uint256 i; i < slotsToFill; ++i) {
        IDepositToken dt = IDepositToken(dts[i]);
        deal(address(dt.underlying()), attacker, 2);
        dt.underlying().approve(address(dt), 2);
        dt.deposit(1, attacker);          // attacker gets balance
        dt.transfer(victim, 1);           // adds dt to victim's list (first-time receive)
    }

    // victim now at cap: depositing ANY collateral not already in list reverts
    vm.prank(victim);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    newDepositToken.deposit(amount, victim);

    // likewise, issuing a synthetic the victim doesn't owe reverts via
    // DebtToken._mint -> pool.addToDebtTokensOfAccount -> UserReachedMaxTokens
}
```

Caveat: I could not verify against a live fork how many deposit tokens are listed on deployed pools, so end-to-end cap exhaustion depends on the target pool's configuration.

        address sender_,
        address recipient_,
        uint256 amount_
    ) private updateRewardsBeforeTransfer(sender_, recipient_) {

        if (recipient_ == address(0)) revert TransferToTheZeroAddress();

        uint256 _senderBalanceBefore = balanceOf[sender_];
        if (_senderBalanceBefore < amount_) revert TransferAmountExceedsBalance();
        uint256 _recipientBalanceBefore = balanceOf[recipient_];

        unchecked {
            balanceOf[sender_] = _senderBalanceBefore - amount_;
            balanceOf[recipient_] += amount_;
        }

        emit Transfer(sender_, recipient_, amount_);

        // Add this token to the deposit tokens list if the recipient is receiving it for the 1st time
        if (_recipientBalanceBefore == 0 && amount_ > 0) {
            pool.addToDepositTokensOfAccount(recipient_);
        }

        // Remove this token from the deposit tokens list if the sender's balance goes to zero
        if (amount_ > 0 && balanceOf[sender_] == 0) {
            pool.removeFromDepositTokensOfAccount(sender_);
        }
    }
