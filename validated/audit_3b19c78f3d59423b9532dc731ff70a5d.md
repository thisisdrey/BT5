### Title
Unauthenticated dust transfers fill a victim's per-account token list, permanently blocking new deposits/borrows while debt exists - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` across the combined `depositTokensOfAccount` + `debtTokensOfAccount` lists via `onlyIfAdditionWillNotReachMaxTokens`. Entries are added not only on mint but on any `DepositToken._transfer` to a recipient with a zero balance. An attacker can deposit dust into every listed deposit token and `transfer()` 1 wei of each `msdTOKEN` to a victim, filling all 30 slots. If the victim has outstanding debt, the dust is locked (`_revertIfLocked` blocks transfers of locked balance), so the victim cannot evict the entries — and every subsequent `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` for a *new* token reverts with `UserReachedMaxTokens`.

### Finding Description
- `DepositToken.transfer` is a public, unprivileged entry point. It calls `_transfer`, which calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is zero (contracts/DepositToken.sol:348-354, 515-525).
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (contracts/Pool.sol:143-148, 204-220).
- The same add path is hit on `DepositToken._mint` (deposit of a new collateral, line 486-488) and on `DebtToken._mint` (issuing a new synthetic debt type).
- Removal only happens when a balance goes to zero, but a victim with debt cannot transfer/withdraw the dust: `unlockedBalanceOf` returns ~0 when `_issuableInUsd == 0` (contracts/DepositToken.sol:383-398), so `transfer`/`withdraw` revert via `_revertIfLocked`.

### Impact Explanation
Liveness / freezing impact matching the CVE's "partial DoS by unauthenticated network attacker" class:
1. Victim cannot deposit any *new* collateral type while the slots are occupied — `_mint` → `addToDepositTokensOfAccount` reverts.
2. Victim cannot mint/issue any *new* synthetic debt type.
3. Any `msdTOKEN` transfer to the victim of a token they don't already hold reverts (also breaks `seize` payouts to that account during liquidation and SmartFarmingManager flows that mint/transfer to the account).
4. If the victim's position is unhealthy and they hold none of their existing collateral types nor synth to repay, they cannot add a new collateral to restore health — forced liquidation / inability to rescue the position while the lock persists (which is the entire duration of their debt, i.e. potentially permanent).

No privileged role is needed; the attacker only needs to acquire 1 wei of each of up to 30 deposit tokens (attacker's own deposits), all via public functions.

### Likelihood Explanation
Requires a pool with enough listed deposit/debt tokens to reach 30 combined entries and a victim with an open debt position whose `unlockedBalanceOf` is zero (fully utilized). Cost to attacker is dust deposits plus gas; no oracle manipulation, flash loan, or privileged action required. The victim cannot clear the slots while locked, so the DoS persists until their debt is repaid/liquidated.

### Recommendation
- Don't count attacker-pushable entries against the cap: only charge the slot on protocol-initiated adds (deposit/mint), e.g. make `addToDepositTokensOfAccount` callable only in mint context, or let `_transfer` skip the add and treat zero-balance recipients off-list.
- Alternatively allow `transfer`/`seize` recipients to exceed the cap (apply `onlyIfAdditionWillNotReachMaxTokens` only on mint paths), or add a `sweepTokenFromAccount` escape so a user can always remove a dust entry regardless of lock status.

### Proof of Concept
Hardhat sketch (fork against a deployed pool with N listed deposit tokens):

```ts
// attacker deposits 1 wei of underlying into each deposit token -> receives dust msdTOKEN_i
for (const dt of depositTokens) {
  await underlying_i.approve(dt.address, 1);
  await dt.deposit(1);                    // mints dust msdTOKEN to attacker
  await dt.connect(attacker).transfer(victim.address, 1); // occupies 1 slot of victim
}
// after 30 - (victim's existing entries) iterations:
await pool.getDepositTokensOfAccount(victim.address) // length hits MAX_TOKENS_PER_USER = 30

// victim has debt so unlockedBalanceOf(victim) == 0 -> victim cannot transfer dust out:
await expect(dt.connect(victim).transfer(attacker.address, 1))
  .revertedWithCustomError(dt, 'NotEnoughFreeBalance');

// victim can never deposit a new collateral type nor mint a new synth:
await expect(newDepositToken.connect(victim).deposit(amount))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(newDebtToken.connect(victim).mint(amount)) // via Pool issue flow
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
```
