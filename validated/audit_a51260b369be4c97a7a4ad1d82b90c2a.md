### Title
Unbounded array allocation from attacker-controlled length field in `PrecompiledContracts.extractBytesArray`/`extractBytes32Array` enables energy-cheap OOM DoS - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`ValidateMultiSign` and `BatchValidateSign` precompiled contracts decode calldata into `DataWord[] words` and then read an array-length field directly from attacker-supplied words to size a Java array, without validating the length against the actual amount of data present or a sane upper bound in the pre-`allowTvmSelfdestructRestriction` code path.

### Finding Description
`extractBytesArray` and `extractBytes32Array` read `len = words[offset].intValueSafe()` and immediately allocate `new byte[len][]` [1](#0-0) , and `extractBytes32Array` does the same with no bound check at all [2](#0-1) . In `ValidateMultiSign.execute`, the `MAX_SIZE` guard on `sigArraySize` is only applied when `VMConfig.allowTvmSelfdestructRestriction()` is true; the unguarded branch calls `extractBytesArray` directly [3](#0-2) . In `BatchValidateSign.doExecute`, the same pattern applies to `extractSigArray`/`extractBytesArray`, and `extractBytes32Array` for the `addresses` array is called unconditionally with no size cap before allocation [4](#0-3) .

Energy charged for these calls is computed purely from the *raw byte length* of the calldata (`(data.length / WORD_SIZE - 5) / 6` or `/5`) [5](#0-4) , not from the value embedded inside a length word. This means an attacker can submit a small, cheap calldata blob whose in-bounds header word encodes an enormous array-length value (e.g. close to `Integer.MAX_VALUE`), causing the precompile to attempt an allocation of `new byte[len][]`/`new byte[len]` far exceeding available heap.

### Impact Explanation
An allocation request sized near `Integer.MAX_VALUE` array references will throw `OutOfMemoryError`. The severity of the memory-allocation request is disproportionate to the energy paid, matching the same fundamentally class as the FFmpeg XBIN report: unvalidated size fields from untrusted input driving disproportionate resource consumption. If this propagates as an unrecovered `OutOfMemoryError` in a validating node's VM execution path (not fully caught the same way for `ValidateMultiSign`, whose `execute` has no top-level `try/catch` around `extractBytesArray`, unlike `BatchValidateSign` which wraps `doExecute` in a `try { } catch (Throwable t)`), this could crash or destabilize the executing node's JVM, which is a node-crash/halt-class impact reachable by any contract caller invoking these long-standing precompiled contracts (addresses `0x9`/`0xa`).

### Likelihood Explanation
Reachability requires only a normal signed transaction that calls the `batchvalidatesign`/`validatemultisign` precompile with crafted calldata — no special privileges are needed. However, exploitability is gated by `VMConfig.allowTvmSelfdestructRestriction()`: if that feature switch is enabled on the deployed chain (which the extensive TIP-854/selfdestruct-restriction guard code and associated tests in this repo suggest is the intended, and likely already-activated, hardened configuration), the size checks (`sigArraySize > MAX_SIZE` / `addrArraySize > MAX_SIZE`) are performed before the vulnerable unbounded allocation, closing this path. I was not able to fully confirm in this session whether `allowTvmSelfdestructRestriction` is unconditionally true on current mainnet/this fork's default configuration or whether the legacy (pre-activation) unguarded branch remains reachable — the `VMConfig.java` and `DataWord.intValueSafe()` definitions I queried in the final round did not return before the tool budget was exhausted. Given the codebase's visible extensive hardening of these very precompiles against malformed-calldata classes (see the TIP-854 tests such as `testTip854RejectsMalformedCalldata`, `testTip854PreActivationNoOp`), it is plausible that this legacy branch is dead code on any chain with the guard activated, in which case there is no exploitable analog today.

### Recommendation
Bound `len` in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` against `MAX_SIZE`/a sane cap and against the actual remaining `words.length`/`data.length` unconditionally, not only when `allowTvmSelfdestructRestriction()` is active, so that the check cannot be bypassed by pre-activation code paths or future feature-flag rollbacks. Additionally wrap `ValidateMultiSign.execute` with the same defensive `try/catch` used in `BatchValidateSign.execute` so that `OutOfMemoryError`/`Throwable` from malformed input cannot propagate uncontained.

### Proof of Concept
Conceptual PoC (requires confirming default value of `allowTvmSelfdestructRestriction` to execute, which could not be verified within the tool budget):
1. Construct calldata for `validatemultisign(address,uint256,bytes32,bytes[])` where the static header words are minimal/in-bounds (so `words[3].intValueSafe()/WORD_SIZE` resolves to an in-bounds offset).
2. At that in-bounds offset, place a length word value like `0x000000000000000000000000000000000000000000000000000000FFFFFFF0` (a large but `intValueSafe()`-representable int).
3. Submit this as calldata to the `ValidateMultiSign` precompiled contract (address `0xa`) via a `TriggerSmartContract` transaction with only enough energy to cover `getEnergyForData`'s small `cnt` computed from the raw calldata length.
4. If `allowTvmSelfdestructRestriction()` is false in the executing environment, `extractBytesArray` executes `new byte[len][]` with `len` ≈ 4 billion, attempting a multi-gigabyte allocation and throwing `OutOfMemoryError`, uncaught by `ValidateMultiSign.execute`. [1](#0-0) [3](#0-2)

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
