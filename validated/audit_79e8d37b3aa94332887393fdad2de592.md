### Title
Attacker-supplied GitConfigOptions can override Gitaly's injected core.hooksPath, enabling hook bypass on receive-pack - ([File: internal/gitaly/service/smarthttp/receive_pack.go])

### Summary
`postReceivePack` converts the attacker-controlled `GitConfigOptions` field via `gitcmd.ConvertConfigOptions`/`GitConfig.Validate` with only a syntactic regex check (must contain a dot, no `=`, no leading/trailing dot) and no semantic denylist for dangerous keys such as `core.hooksPath`. Because `gitcmd.WithReceivePackHooks` (which injects Gitaly's own `core.hooksPath`) is applied before `gitcmd.WithConfig(config...)` (which appends the attacker's config), the attacker's config pair ends up later in `cc.globals` and therefore later in the final `git -c ...` argument list, where "last `-c` wins" semantics let it override Gitaly's own hook path.

### Finding Description
In `postReceivePack` [1](#0-0) , the request's `GitConfigOptions` is parsed with `gitcmd.ConvertConfigOptions` [2](#0-1)  and then passed as `gitcmd.WithConfig(config...)` as the *last* `CmdOpt` to `repo.Exec`, after `gitcmd.WithReceivePackHooks(...)`.

`WithConfig` simply appends the given `ConfigPair`s to `cc.globals` [3](#0-2) . `WithReceivePackHooks` → `configureHooks` appends `core.hooksPath` to `cc.globals` earlier in the call sequence [4](#0-3) , specifically at line 182 (`cc.globals = append(cc.globals, ConfigPair{Key: "core.hooksPath", ...})`).

When the final argument list is built in `combineArgs`, `cc.globals` (built in `CmdOpt` invocation order) is inserted as one contiguous block, with only Gitaly's admin-level `cf.cfg.Git.Config` appended after it [5](#0-4) . Because `WithReceivePackHooks` runs before `WithConfig(config...)` in the CmdOpt list passed by `postReceivePack`, Gitaly's `core.hooksPath` entry precedes the attacker's config entries in the emitted `-c` flags. Git applies scalar config keys with "last one wins" semantics, so if the attacker supplies `GitConfigOptions=["core.hooksPath=/tmp/attacker-hooks"]`, that key/value passes `GitConfig.Validate()`'s regex check (contains a dot, no `=`, no leading/trailing dot) [6](#0-5)  and is appended later in argv, overriding Gitaly's own `-c core.hooksPath=<tempHooksPath>`.

No code path filters or denies dangerous keys (`core.hooksPath`, `uploadpack.packObjectsHook`, `core.fsmonitor`, etc.) before they reach `-c`; only generic syntax validation exists. This directly contradicts the mechanism described in `doc/hooks.md`, where Gitaly intercepts hook execution exclusively via its own injected `core.hooksPath` [7](#0-6) . The same pattern (`WithReceivePackHooks` then `WithConfig(config...)`) exists in the SSH receive-pack path as well [8](#0-7) .

### Impact Explanation
If exploitable, this allows a pushing user to redirect `core.hooksPath` used by `git-receive-pack` to an attacker-controlled directory on the Gitaly host, replacing `pre-receive`/`update`/`post-receive`/`proc-receive` hooks with attacker scripts, executed as the Gitaly process user — full hook bypass and arbitrary command execution/RCE, matching a critical "hook or quarantine bypass"/command execution bounty class. The attacker would need a directory on the Gitaly filesystem containing executable hook scripts, which is a nontrivial additional precondition (an unprivileged push-capable user does not normally have arbitrary filesystem write access on the Gitaly server) — this materially limits real-world exploitability of the config-injection primitive itself.

### Likelihood Explanation
The GitConfigOptions field is fully attacker-controlled by any user with push access to their own repository, requiring no special privileges — this part of the precondition is trivially satisfied and repeatable. However, exploiting this specific vector to achieve hook execution additionally requires the value pointed at by the overridden `core.hooksPath` (e.g., `/tmp/attacker-hooks`) to actually contain hook executables reachable and writable by the attacker on the Gitaly host filesystem, which an unprivileged, non-admin, non-local GitLab user does not have by default (no shell/disk access per the threat model). Without confirmed filesystem write access to place hook scripts at the overridden path, the config override alone does not produce direct code execution, though it is still a config-integrity violation of the intended isolation.

### Recommendation
Add an explicit denylist/allowlist check in `GitConfig.Validate()` or in `ConvertConfigOptions`/`WithConfig` to reject security-sensitive keys such as `core.hooksPath`, `core.fsmonitor`, `uploadpack.packObjectsHook`, `receive.procReceiveRefs`, `alias.*`, and similar. Additionally, ensure Gitaly's own hook-related config entries are applied after any caller/user-supplied config (or via a dedicated "override-proof" mechanism, e.g. environment variables via `WithConfigEnv` instead of `-c`, or appending them last like `cf.cfg.Git.Config` admin overrides) so they cannot be shadowed regardless of option ordering.

// ConvertConfigOptions converts `<key>=<value>` config entries into `ConfigPairs`.
func ConvertConfigOptions(options []string) ([]ConfigPair, error) {
	configPairs := make([]ConfigPair, len(options))

	for i, option := range options {
		configPair := strings.SplitN(option, "=", 2)
		if len(configPair) != 2 {
			return nil, fmt.Errorf("cannot convert invalid config key: %q", option)
		}

		configPairs[i] = ConfigPair{Key: configPair[0], Value: configPair[1]}
	}

	return configPairs, nil
}

// WithReceivePackHooks returns an option that populates the safe command with the environment
// variables necessary to properly execute the pre-receive, update, post-receive, and proc-receive
// (if enabled) hooks for git-receive-pack(1).
func WithReceivePackHooks(objectHash git.ObjectHash, req ReceivePackRequest, protocol string, enableProcReceive bool) CmdOpt {
	return func(ctx context.Context, cfg config.Cfg, gitCmdFactory CommandFactory, cc *cmdCfg) error {
		requestedHooks := ReceivePackHooks
		if enableProcReceive {
			// When transactions are in use, Git should only invoke pre-receive and proc-receive.
			// Our proc-receive implementation handles invoking the later hooks.
			requestedHooks = PreReceiveHook | ProcReceiveHook
		}

		if err := cc.configureHooks(ctx, cfg, objectHash, req.GetRepository(), gitCmdFactory, &UserDetails{
			UserID:   req.GetGlId(),
			Username: req.GetGlUsername(),
			Protocol: protocol,
			RemoteIP: metadata.GetValue(ctx, "remote_ip"),
		}, requestedHooks); err != nil {
			return err
		}

		return nil
	}
}

// configureHooks updates the command configuration to include all environment
// variables required by the reference transaction hook and any other needed
// options to successfully execute hooks.
func (cc *cmdCfg) configureHooks(
	ctx context.Context,
	cfg config.Cfg,
	objectHash git.ObjectHash,
	repo storage.Repository,
	gitCmdFactory CommandFactory,
	userDetails *UserDetails,
	requestedHooks Hook,
) error {
	if cc.hooksConfigured {
		return errors.New("hooks already configured")
	}

	var transaction *txinfo.Transaction
	if tx, err := txinfo.TransactionFromContext(ctx); err == nil {
		transaction = &tx
	} else if !errors.Is(err, txinfo.ErrTransactionNotFound) {
		return err
	}

	if requestedHooks&ProcReceiveHook != 0 {
		cc.globals = append(cc.globals, ConfigPair{Key: "receive.procReceiveRefs", Value: "refs"})
	}

	payload, err := NewHooksPayload(
		ctx,
		cfg,
		repo,
		objectHash,
		transaction,
		userDetails,
		requestedHooks,
		featureflag.FromContext(ctx),
		storage.ExtractTransactionID(ctx),
	).Env()
	if err != nil {
		return err
	}

	cc.env = append(
		cc.env,
		payload,
		// Setting GOTRACEBACK=none ensures that if the gitaly-hooks process hits a fatal Go
		// runtime error, the runtime does not dump a verbose stacktrace to stderr. This causes
		// a lot of noise on the Git client side.
		"GOTRACEBACK=none",
	)
	cc.env = envInjector(ctx, cc.env)

	cc.globals = append(cc.globals, ConfigPair{Key: "core.hooksPath", Value: gitCmdFactory.HooksPath(ctx)})
	cc.hooksConfigured = true

	return nil
}

// Validate validates that the Git configuration conforms to a format that Git understands.
func (cfg GitConfig) Validate() error {
	// Even though redundant, this block checks for a few things up front to give better error
	// messages to the administrator in case any of the keys fails validation.
	if cfg.Key == "" {
		return cfgerror.NewValidationError(cfgerror.ErrNotSet, "key")
	}
	if strings.Contains(cfg.Key, "=") {
		return cfgerror.NewValidationError(
			fmt.Errorf(`key %q cannot contain "="`, cfg.Key),
			"key",
		)
	}
	if !strings.Contains(cfg.Key, ".") {
		return cfgerror.NewValidationError(
			fmt.Errorf("key %q must contain at least one section", cfg.Key),
			"key",
		)
	}
	if strings.HasPrefix(cfg.Key, ".") || strings.HasSuffix(cfg.Key, ".") {
		return cfgerror.NewValidationError(
			fmt.Errorf("key %q must not start or end with a dot", cfg.Key),
			"key",
		)
	}

	if !configKeyRegex.MatchString(cfg.Key) {
		return cfgerror.NewValidationError(
			fmt.Errorf("key %q failed regexp validation", cfg.Key),
			"key",
		)
	}

	return nil
}

## Hook Setup

By default, when Git executes hooks, it inspects the `.git/hooks` directory
inside the repository it's executing in. However, Gitaly intercepts this
mechanism. There are no repository-specific hooks we ever want to execute using
this mechanism. Instead, we want to inject our own global hooks that are
required for each repository.

We inject some information into Git commands to set up the hook execution
environment for both Git and ourselves so that the `gitaly-hooks` executable is
able to derive required information:

- We inject the `core.hooksPath` config entry, which points to the directory
  containing our global hooks. Global hooks are set up as a temporary directory
  containing symlinks to a wrapper script which is able to locate the
  `gitaly-hooks` executable.
