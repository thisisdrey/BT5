### Title
Single forged Nakamoto block in a pushed batch causes silent drop of all preceding valid blocks in that batch - ([File: stackslib/src/net/relay.rs])

### Summary
`Relayer::process_pushed_nakamoto_blocks` calls `validate_nakamoto_blocks_push`, which validates the *entire* `NakamotoBlocksData.blocks` vector up front and returns `Err` on the first invalid entry. When that happens, the caller does `break` before ever entering the per-block processing loop, so none of the blocks in that batch — including otherwise-valid ones — are stored via `process_new_nakamoto_block` or added to `accepted_blocks` for relay.

### Finding Description
The broken invariant: "a valid, relayable Nakamoto block in a pushed batch is processed/relayed independent of the validity of other unrelated entries in the same wire message" does not hold.

`validate_nakamoto_blocks_push` iterates `nakamoto_blocks_data.blocks.iter()` and returns `Err(net_error::InvalidMessage)` as soon as it finds a block whose sortition doesn't exist (`!sn.sortition`, line 664-670) or whose signer signature fails verification (line 740-752), regardless of that block's position in the vector. [1](#0-0) [2](#0-1) 

In `process_pushed_nakamoto_blocks`, this validation call gates the whole batch:
```
if let Err(e) = Relayer::validate_nakamoto_blocks_push(...) {
    info!(...);
    break;
}
for nakamoto_block in nakamoto_blocks_data.blocks.drain(..) { ... }
``` [3](#0-2) 

On error, `break` exits the loop entirely before the `drain(..)` loop that calls `Self::process_new_nakamoto_block` and populates `accepted_blocks`. So a single deliberately-invalid block placed anywhere in the batch (e.g., a block referencing a consensus hash with no sortition, or one with a bad signer signature) prevents *all* blocks in that same `NakamotoBlocksData` from being locally stored or forwarded — not just the entries after the bad one, since the pre-check inspects the whole vector before any processing begins.

Additionally, since this `break` sits inside the `for (relayers, nakamoto_blocks_data) in relayers_and_block_data.iter_mut()` loop with no enclosing loop between it and the check, one invalid batch also aborts processing of any subsequent `NakamotoBlocksData` entries queued for that same neighbor in `relayers_and_block_data`, compounding the suppression. [4](#0-3) 

No other guard mitigates this: there is no per-block try/continue semantics in `validate_nakamoto_blocks_push`, and `process_pushed_nakamoto_blocks` never re-attempts individual blocks from a failed batch.

### Impact Explanation
An attacker who can push a `NakamotoBlocksData` message to a peer (any P2P peer, no authentication required beyond a normal handshake) can bundle N legitimate, already-broadcast Nakamoto blocks together with one forged/invalid entry. The victim node will neither store the valid blocks locally via `process_new_nakamoto_block` nor add them to `accepted_blocks`/`pushed_blocks`, so they are not relayed onward from that node through this push path. This is a targeted, repeatable data-suppression/DoS against block propagation on a per-peer, per-message basis; the attacker can repeat this indefinitely against any peer connection they control, at negligible cost (crafting one bad block header per message). It does not crash the node, forge accepted state, or bypass authentication, so it does not cleanly meet the "Critical" categories (crash, unauthorized write, forged data propagation, smuggling, memory disclosure) listed, but it is a legitimate propagation-suppression defect in the relay logic.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs an established P2P connection to a node (unprivileged, remotely reachable) and the ability to send a `NakamotoBlocksData` message containing multiple blocks, one of which fails `validate_nakamoto_blocks_push` (e.g., wrong consensus hash or bad signature). No secrets, StackerDB ownership, or privileged role are required. The attack is cheap, remotely triggerable with a single crafted message, and repeatable against every connected peer independently.

### Recommendation
Change `process_pushed_nakamoto_blocks` (and ideally `validate_nakamoto_blocks_push`) to validate and process each block independently rather than gating the whole batch on a single failure: e.g., have `validate_nakamoto_blocks_push` return a per-block result (or filter out invalid blocks) instead of short-circuiting on the first `Err`, and change the `break` on line 1678 to `continue`/per-block handling so valid blocks preceding (or following) the bad one are still processed and relayed. Track/punish the sending neighbor for the bad block without discarding the valid ones.

### Proof of Concept
Add a net test in `stackslib/src/net/relay.rs` tests (or `tests/relay`) that:
1. Constructs a `NakamotoBlocksData` with `blocks = [valid_block_1, invalid_block]`, where `invalid_block.header.consensus_hash` refers to a snapshot with `sortition = false` (or a corrupted signer signature), and `valid_block_1` is a correctly signed/sorted Nakamoto block.
2. Feeds this via `network_result.pushed_nakamoto_blocks` and calls `Relayer::process_pushed_nakamoto_blocks(...)`.
3. Asserts that the returned `pushed_blocks` (or the chainstate, via `process_new_nakamoto_block`) contains/stored `valid_block_1` — this assertion fails today because `validate_nakamoto_blocks_push` returns `Err` for the whole slice and the `break` at relay.rs:1678 skips the `drain(..)` loop entirely, so `valid_block_1` is neither stored nor present in `pushed_blocks`.
