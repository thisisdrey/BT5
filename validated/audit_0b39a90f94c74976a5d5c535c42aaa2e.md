### Title
Heap buffer over-read parsing a crafted jar's ZIP central directory in ijar - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar's ZIP reader decodes the fixed and variable-length fields of a central directory record (file name, extra field, comment lengths, and the extra-field TLV loop) using unchecked `get_u4le`/`get_u2le`/`get_u8le`/`memcpy` calls, with no bounds validation against the memory-mapped input file's actual extent, unlike the local-file-header path in the same file which explicitly guards every variable-length read with `EnsureRemaining()`.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from attacker-controlled bytes and then advances the cursor `p` (and, in the extra-field loop, `extra_p`) by these attacker-controlled amounts without ever calling the file's own `EnsureRemaining(n, state)` bound-check helper: [1](#0-0) 

Contrast this with `ProcessLocalFileEntry`, which reads the same category of length-prefixed fields but wraps each variable-length read in `EnsureRemaining()` before touching the data: [2](#0-1) 

`EnsureRemaining` itself computes remaining bytes relative to the mmap'd file length, showing the codebase is aware such checks are required for untrusted zip content: [3](#0-2) 

`ProcessCentralDirEntry` is the function driving the main scan loop (`ProcessNext`) over every entry in the ZIP central directory of an input jar, as well as `CalculateOutputLength`: [4](#0-3) 

Because none of `file_name_length`, `extra_field_length`, `file_comment_length`, or the inner extra-field `data_size` values are validated against the mapped file's true size, a crafted jar with oversized length fields (or an extra-field TLV chain whose `data_size` values never make `extra_p` land exactly on `p`) drives `p`/`extra_p` past the end of the memory-mapped input, causing subsequent `get_u4le`/`get_u2le`/`get_u8le`/`memcpy` calls to read out-of-bounds memory. The `while (extra_p != p)` extra-field loop in particular has no termination guarantee or bound check at all — this is directly analogous to the CVE-2016-9827 class: a format-reader that trusts attacker-supplied length fields and walks a buffer without validating remaining size, producing an over-read on malformed/crafted input.

### Impact Explanation
This is a memory-safety violation (heap/mmap out-of-bounds read) in a C++ tool (`ijar`) that processes third-party jar files an unprivileged attacker can supply — e.g., a jar fetched via `http_jar`/`http_archive`/Maven-style external dependencies, or any prebuilt `.jar` on an untrusted branch that a CI build consumes and runs through ijar to produce an interface jar. The over-read can leak adjacent heap/mmap memory into the `filename` buffer (which is later used in build output/paths/error messages) or crash the process, both of which stem from untrusted content that should have stayed strictly "data" (i.e., bytes to be parsed defensively), not something that can steer memory reads past validated bounds.

### Likelihood Explanation
Reaching this code path only requires supplying a jar file with a manipulated central directory (oversized length fields) as an external dependency artifact processed by `ijar`; no privileged access, root-repo Starlark, or credential access is needed. The existing `EnsureRemaining()` mechanism demonstrates the codebase already recognizes and defends against exactly this attack surface in `ProcessLocalFileEntry`, but the equivalent protection is absent in `ProcessCentralDirEntry`, so the bug is concretely reachable with default flags on a standard jar-processing build.

### Recommendation
Add the same `EnsureRemaining()` (or an equivalent bounds check against `zipdata_in_`/`input_file_->Length()`) before every read in `ProcessCentralDirEntry`, including the fixed 46-byte central-directory-header prefix, the `file_name`/`extra_field`/`file_comment` regions, and each iteration of the extra-field TLV loop (validating that `header_id`/`data_size` reads and the resulting `extra_p` advance stay within `[extra_p_start, p)`), mirroring the existing, already-audited pattern in `ProcessLocalFileEntry`.

### Proof of Concept
A `BuildIntegrationTestCase`/unit test analogous to `third_party/ijar/test/IjarTests.java` fixtures can construct a minimal ZIP with a central directory record whose `file_name_length`/`extra_field_length`/`file_comment_length` fields (or an extra-field `data_size`) point past the actual mmap'd file size, feed it to the `ijar` binary/`InputZipFile::ProcessNext`, and run under ASan/Valgrind to observe the heap-buffer-overflow (read) report when `get_u4le`/`get_u2le`/`memcpy` dereference past the mapped region — reproducing the same class of crash `outputtxt.c`'s `_iprintf` triggered on a crafted SWF in CVE-2016-9827.

Note: I could not directly view the implementation of `get_u4le`/`get_u2le`/`get_u8le` in `third_party/ijar/common.h` before running out of tool iterations; based on their exclusive use inside `EnsureRemaining`-guarded call sites elsewhere in the same file, they are simple pointer-advancing decoders with no internal bounds checking, but this should be verified directly in `third_party/ijar/common.h` before finalizing a fix.

bool InputZipFile::ProcessNext() {
  // Process the next entry in the central directory. Also make sure that the
  // content pointer is in sync.
  u8 compressed, uncompressed;
  u8 offset;
  if (!ProcessCentralDirEntry(central_dir_current_, &compressed, &uncompressed,
                              filename, PATH_MAX, &attr, &offset)) {
    return false;
  }

  // There might be an offset specified in the central directory that does
  // not match the file offset, so always update our pointer.
  p = zipdata_in_ + in_offset_ + offset;

  if (EnsureRemaining(4, "signature") < 0) {
    return false;
  }
  u4 signature = get_u4le(p);
  if (signature == LOCAL_FILE_HEADER_SIGNATURE) {
    if (ProcessLocalFileEntry(compressed, uncompressed) < 0) {
      return false;
    }
  } else {
    error("local file header signature for file %s not found\n", filename);
    return false;
  }

  return true;
}
