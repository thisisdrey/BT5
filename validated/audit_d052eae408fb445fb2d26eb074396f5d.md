### Title
Negative energy cost from malformed input in `ValidateMultiSign`/`BatchValidateSign` precompiles bypasses TVM energy metering - (`File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `getEnergyForData` methods of the `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts compute the energy charge from attacker-controlled call-data length using plain integer arithmetic with no lower-bound / null check. For short or empty call-data the computed signature count becomes negative, causing the precompile to return a **negative** energy cost instead of failing or charging a minimum fee.

### Finding Description
`PrecompiledContracts.ValidateMultiSign.getEnergyForData` (around line 1044) is: [1](#0-0) 

```java
public long getEnergyForData(byte[] data) {
  long cnt = (data.length / WORD_SIZE - 5) / 5;
  // one sign 1500, half of ecrecover
  return cnt * ENGERYPERSIGN;
}
```

`WORD_SIZE` is 32. The formula assumes the ABI header always occupies 5 words (`ABI_HEADER_WORDS`) and each signature item occupies 5 words. There is no `data == null` guard and no clamp to a minimum of zero.

For any `data.length < 160` (i.e., fewer than 5 words, which happens whenever a caller supplies short/empty call-data to this precompile address), `data.length / WORD_SIZE` evaluates to 0–4, so `(0..4 - 5)` is negative, and dividing a negative number by 5 in Java yields a negative (or zero) result — e.g. `data.length = 0` → `cnt = (0 - 5) / 5 = -1` → `getEnergyForData` returns `-1500`.

The sibling precompile `BatchValidateSign.getEnergyForData` (around line 1138) has the exact same unguarded pattern: [2](#0-1) 

```java
public long getEnergyForData(byte[] data) {
  long cnt = (data.length / WORD_SIZE - 5) / 6;
  return cnt * ENGERYPERSIGN;
}
```

Note that the correctness/format guard added for TIP-854 (`isValidAbiEncoding`) is only applied inside `execute()`, gated behind `VMConfig.allowTvmOsaka()`, and is never consulted by `getEnergyForData()`. Energy accounting for a precompile call is computed from `getEnergyForData` before/independently of `execute()`'s validity check, so the negative-cost path is reachable regardless of the Osaka feature flag, and even when the Osaka guard is active it only causes `execute()` to fail — it does not prevent `getEnergyForData` from returning a negative number.

Both precompiles are invoked through ordinary TVM `CALL`/`STATICCALL` opcodes to their fixed precompile addresses, which is directly reachable by any unprivileged contract deployer/caller submitting a `TriggerSmartContract` transaction — no special privilege is required.

### Impact Explanation
Energy metering in java-tron is the core mechanism that bounds the amount of computation a single transaction may perform and that translates directly into TRX cost (via `energyFee`) charged to the caller. A negative cost returned from `getEnergyForData` corrupts this invariant: instead of debiting the caller's remaining energy, a negative value effectively credits energy back (or at minimum fails to charge the expected minimum fee for invoking the precompile). Because these precompiles can be called cheaply and repeatedly in a loop from a single contract invocation (well within `MAX_MATCH_NUM`-style loop bounds elsewhere in the VM, but here unconstrained), an attacker can:
- Artificially inflate remaining energy within one transaction execution, letting a transaction perform far more computation than its declared `feeLimit`/energy budget should allow.
- Under-pay the energy fee associated with invoking the precompile, effectively getting free execution cycles.

This directly undermines the "TVM opcodes, precompiles and energy metering" invariant and can be leveraged for a computational-resource DoS against block-producing nodes (excess computation for underpaid/no energy cost), which is accepted impact under the "node crash or halt" / metering-integrity category.

### Likelihood Explanation
The bug is trivially triggered: any account can deploy or call a contract that issues a `CALL` to the `ValidateMultiSign` (0x66-style) or `BatchValidateSign` precompile address with call-data shorter than 160/192 bytes (including empty call-data). No privileged role, witness/SR status, or special network condition is required — it is reachable from a single ordinary `TriggerSmartContract` transaction sent by any unprivileged account. The condition (`data.length < 5*WORD_SIZE`) is easy to hit unintentionally as well (e.g., a contract passing malformed/short data), making this both easily exploitable and likely to be hit by fuzzing/normal usage.

### Recommendation
In both `ValidateMultiSign.getEnergyForData` and `BatchValidateSign.getEnergyForData`:
- Add a `data == null || data.length < ABI_HEADER_WORDS * WORD_SIZE` guard that returns a fixed minimum/base energy cost (or throws/charges the maximum applicable cost) instead of falling through to the unguarded arithmetic.
- Clamp the final computed value to be `>= 0` (e.g., `return Math.max(cnt, 0) * ENGERYPERSIGN;`) as a defense-in-depth measure.
- Ensure the ABI/format validation (`isValidAbiEncoding`) used in `execute()` is also considered by, or aligned with, the energy calculation so malformed call-data cannot produce degenerate/negative cost independent of the Osaka feature flag.

### Proof of Concept
1. Deploy a simple contract that performs a raw `staticcall`/`call` to the `ValidateMultiSign` precompile address with zero-length (or otherwise <160-byte) call-data, e.g. in Solidity:
   ```solidity
   function poc() external {
       (bool ok, ) = address(0x0000000000000000000000000000000000000066).call("");
   }
   ```
   (address value illustrative; use the actual configured precompile address for `ValidateMultiSign`).
2. Submit a `TriggerSmartContract` transaction invoking `poc()`.
3. Observe that `PrecompiledContracts.ValidateMultiSign.getEnergyForData(new byte[0])` evaluates `cnt = (0/32 - 5)/5 = -1`, returning `-1500` as the energy cost for the call, instead of a legitimate non-negative cost or a validation failure.
4. Repeat the call in a loop within the same transaction to accumulate an unbounded/incorrect energy credit relative to the transaction's declared `feeLimit`.

Note: I was not able to directly inspect the exact call site in `Program.java`/`VM.java` that consumes the return value of `getEnergyForData` to confirm precisely how the negative number is applied to the energy counter (e.g., whether it is added or subtracted, and whether any downstream clamp exists) due to running out of search iterations — this should be verified in a live session to confirm the exact severity of energy-counter corruption, but the presence of unguarded negative-producing integer arithmetic in a production energy-cost function reachable from unprivileged contract calls is confirmed and is itself a metering-integrity defect regardless of the exact downstream consumption.
