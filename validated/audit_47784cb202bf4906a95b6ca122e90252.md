### Title
Per-IP QUIC connection rate limit bypass via parallel handshake race between `is_allowed` and `register_connection` - ([File: streamer/src/nonblocking/quic.rs])

### Finding Description
The main accept loop in `run_server` checks `rate_limiter.is_allowed(&incoming.remote_address().ip())` synchronously before accepting a connection, but this call is read-only and does not consume/decrement any token in `ConnectionRateLimiter` [1](#0-0) . The actual token consumption only happens in `rate_limiter.register_connection(&from.ip())`, which is called from `setup_connection`, a task spawned only *after* the QUIC handshake completes (bounded by `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`) [2](#0-1) .

The accept loop itself does not wait for `setup_connection`/handshake to finish before processing the next incoming connection — it merely spawns the handshake+registration as a task via `tasks.spawn(setup_connection(...))` and immediately loops back to accept more incoming connections [3](#0-2) . Because `is_allowed` only inspects the current token count and `register_connection` (the actual decrement) happens only once each handshake completes, an attacker opening many parallel connections from a single IP within the handshake timeout window can have all of them pass the pre-handshake `is_allowed` check (since none has yet decremented the bucket), and only afterward, once handshakes complete, do they call `register_connection` — by which point the "per-connection" admission decision has already been made and the connections were accepted for handshake. This is a classic time-of-check-to-time-of-use (TOCTOU) gap between check (`is_allowed`) and act (`register_connection`) split across an asynchronous boundary (the handshake).

The comment in `run_server` acknowledges the intended mitigation order ("rate-limit abusive peers by (control-asserted) ip" only after handshake) [4](#0-3) , but the pre-handshake `is_allowed` gate is a non-authoritative advisory check that provides no protection against parallel connection attempts issued faster than one handshake round-trip, since no state is reserved/decremented at check time.

### Impact Explanation
This allows a single unstaked attacker IP to force the server to spend handshake-processing resources (crypto, socket, task-spawn overhead) on far more concurrent connection attempts than `max_connections_per_ipaddr_per_min` intends to allow, before `register_connection` finally starts rejecting them. This matches the described scoped impact: an unstaked/unprivileged client can bypass or unfairly capture connection/QoS resources, causing disproportionate consumption of TPU accept/handshake capacity relative to what the per-IP QoS cap is meant to enforce, at the expense of legitimate senders' connection admission during the handshake window [5](#0-4) .

Note that the *ultimate* per-IP connection count is still eventually bounded because `register_connection` will start returning `false` for connections beyond the limit once their handshakes complete and the bucket is consumed [6](#0-5) , so the impact is a burst/race window of over-admission during the handshake period rather than a permanent bypass of the persistent rate limit. The global `overall_connection_rate_limiter` also caps total in-flight connection attempts across all IPs, limiting the blast radius somewhat [7](#0-6) .

### Likelihood Explanation
An attacker only needs to be able to open more connection attempts than `max_connections_per_ipaddr_per_min` within the `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` window, from a single IP, which is easily reproducible and does not require staking or special privileges. This is precisely the scenario tested by the repo's own `test_connection_rate_limiter` unit test, which demonstrates that `is_allowed` alone does not mutate state ("just checking should not mutate state") [8](#0-7) , confirming that many parallel `is_allowed` checks can pass before any `register_connection` call lands.

### Recommendation
Perform the per-IP admission check-and-reserve atomically at accept time (e.g., use `register_connection`-style token consumption, or a reservation/rollback pattern) instead of splitting the check (`is_allowed`, pre-handshake) from the mutation (`register_connection`, post-handshake). If a pre-handshake IP-based check is desired for early rejection of already-exhausted IPs, it should reserve a token immediately (consuming from the bucket) and release/refund it only if the handshake fails/times out, rather than deferring all consumption until after a successful handshake.

### Proof of Concept
Integration test outline (in `streamer/src/nonblocking/quic.rs` test module or a new integration test):
1. Configure `QuicStreamerConfig::default_for_tests()` with `max_connections_per_ipaddr_per_min = 2` (small value for determinism).
2. Spawn the QUIC server via `run_server`/`spawn_server` test helper as used in `setup_quic_server`.
3. From a single client IP, launch e.g. 20 QUIC connection attempts concurrently (`tokio::join!`/`FuturesUnordered` of `make_client_endpoint`), such that the handshakes complete roughly at the same time, well within `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`.
4. Assert that significantly more than `max_connections_per_ipaddr_per_min` connections reach the "handshake accepted" stage (e.g., via `stats.total_new_connections` incrementing beyond the configured per-IP cap before `connection_rate_limited_per_ipaddr` catches up), demonstrating that `is_allowed` passed for all of them simultaneously rather than serializing admission at the per-IP cap.
5. Expected (failing) assertion: `stats.total_new_connections` (or count of connections that got past `register_connection`'s initial pass) transiently exceeds `max_connections_per_ipaddr_per_min` for the burst, showing the check-then-act race allows over-admission during the handshake window, in contrast to the intended invariant that at most `max_connections_per_ipaddr_per_min` connections per interval should ever be admitted per IP.

            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
