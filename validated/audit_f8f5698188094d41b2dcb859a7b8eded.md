### Title
Relay Identity Poisoning via Unauthenticated `RelayFromAddr` Field in `CreateRelayRequest` - ([File: relay_manager.go])

### Summary
`relayManager.handleCreateRelayRequest` derives the peer identity used to create and index relay state (`from`) from the attacker-controlled `m.RelayFromAddr` field inside the `NebulaControl` message body, rather than from the authenticated identity of the sender (`h.vpnAddrs`, established via the certificate-bound handshake). This is the same bug class as the PearVault report: the code trusts a payload-supplied "who this is for/from" field instead of the cryptographically-authenticated sender identity when performing an authorization/state-tracking decision.

### Finding Description
The control channel is only reachable after a Noise handshake completes and traffic is decrypted under the resulting `HostInfo` (`h`), so the *transport-level* sender is authenticated. However, `handleCreateRelayRequest` does not enforce that the `RelayFromAddr` field inside the message equals the authenticated `h.vpnAddrs[0]`: [1](#0-0) 

Instead, `from` is parsed straight out of the message body: [2](#0-1) 

That attacker-controlled `from` value is then used to:
- Look up/insert relay state on `h.relayState` via `QueryRelayForByIp(from)` / `AddRelay(..., from, ...)`, and
- Set the `Relay.PeerAddr` field that governs which VPN address this relay will forward traffic for: [3](#0-2) 

`AddRelay` unconditionally stores whatever `vpnIp` (i.e., `from`) it is given as `Relay.PeerAddr`: [4](#0-3) 

There is no check anywhere in this path comparing `from` against `h.vpnAddrs` (the addresses actually bound to the peer's certificate for this authenticated tunnel). A malicious but otherwise-certificate-holding peer `h` can therefore claim `RelayFromAddr = victimAddr` for any `victimAddr`, causing the terminal relay node to register itself as a relay for `victimAddr` through `h`'s tunnel — i.e., relay state (`h.relayState`, `Relay.PeerAddr`) is indexed and keyed by an unverified value rather than the authenticated identity, mirroring the PearVault root cause of "checking/tracking the wrong identity field instead of the actual authenticated party."

### Impact Explanation
This allows relay state poisoning: a connected peer can register itself in another node's relay tables as the relay path for an arbitrary VPN address it does not own, without that address's actual owner being involved. Depending on how relay forwarding later trusts `Relay.PeerAddr` to route/forward data-plane packets (in `outside.go`/`inside.go`), this can enable a peer to intercept or redirect traffic destined for an arbitrary VPN address through itself, effectively a remote state-poisoning / traffic-redirection primitive reachable by any peer that can complete a handshake (no CA-signed cert required beyond the attacker's own valid cert, satisfying the "no CA-signed certificate" reachability constraint since the attacker only needs *their own* cert, not the victim's). I was not able to fully trace the downstream data-plane relay-forwarding code (in `outside.go`) within the available tool budget to confirm whether a secondary check against `h.vpnAddrs` exists there, so the exact severity of exploitation (silent redirection vs. mere bookkeeping corruption) is not fully verified.

### Likelihood Explanation
Medium. Requires the attacker to already hold a valid Nebula certificate and complete a handshake with the target relay node (which is the normal, expected condition for any mesh peer with `relay.am_relay` enabled), then send a single `CreateRelayRequest` control message with a forged `RelayFromAddr`. No additional privilege or race condition is needed.

### Recommendation
In `handleCreateRelayRequest` (and `handleCreateRelayResponse`), validate that `from` (`RelayFromAddr`/`OldRelayFromAddr`) matches one of `h.vpnAddrs` (the addresses bound to the already-authenticated peer certificate for this `HostInfo`) before using it to create or query relay state. Reject the message if it does not match, analogous to fixing PearVault's bug by tracking/limiting the actual `msg.sender` rather than an attacker-suppliable field.

### Proof of Concept
Conceptual (not fully verified end-to-end due to tool-call limits):
1. Attacker node A completes a legitimate handshake with relay node R (`h` = A's `HostInfo`, `h.vpnAddrs = [A]`).
2. A sends R a `CreateRelayRequest` control message with `RelayFromAddr = V` (victim V's VPN address, not A's) and `RelayToAddr = R`'s own address (or another value making R believe it is the target).
3. `handleCreateRelayRequest` reads `from = V` from the message (not from `h.vpnAddrs`), and since `f.myVpnAddrsTable.Contains(target)` is true, calls `AddRelay(rm.l, h, f.hostMap, from=V, ...)`, storing `Relay.PeerAddr = V` on `h` (A's HostInfo).
4. R now believes A's tunnel is a valid relay path for V's traffic, despite V never being involved, and responds to A with a `CreateRelayResponse` completing this state — establishing relay bookkeeping keyed on an unauthenticated identity claim.

				newRelay.RemoteIndex = *remoteIdx
			}
			relayHostInfo.relayState.InsertRelay(vpnIp, index, &newRelay)

		}

func (rm *relayManager) handleCreateRelayRequest(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl) {
	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}

	// Is the target of the relay me?
	if f.myVpnAddrsTable.Contains(target) {
		existingRelay, ok := h.relayState.QueryRelayForByIp(from)
		if ok {
			switch existingRelay.State {
			case Requested:
				ok = h.relayState.CompleteRelayByIP(from, m.InitiatorRelayIndex)
				if !ok {
					logMsg.Error("Relay State not found")
					return
				}
			case Established:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
			case Disestablished:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
				// Mark the relay as 'Established' because it's safe to use again
				h.relayState.UpdateRelayForByIpState(from, Established)
			case PeerRequested:
				// I should never be in this state, because I am terminal, not forwarding.
				logMsg.Error("Unexpected Relay State found",
					"existingRemoteIndex", existingRelay.RemoteIndex,
					"state", existingRelay.State)
			}
		} else {
			_, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
			if err != nil {
				logMsg.Error("Failed to add relay", "error", err)
				return
			}
		}

		relay, ok := h.relayState.QueryRelayForByIp(from)
		if !ok {
			logMsg.Error("Relay State not found", "from", from)
			return
		}
