## Analysis: `pallet-asset-rewards` — Reward Payout Not Backed by Actual Pool Liquidity

This maps directly to the rToken bug-class: a pallet promises a beneficiary "deposit + accrued interest/reward" using a purely formulaic accrual model, without any guarantee that the account holding the reward asset actually contains enough balance to honor the promised payout.

### Title
Reward pool payout accounting is decoupled from actual reward-asset liquidity, enabling permanent payout failure / stuck claims - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` computes a staker's claimable reward purely from a `reward_per_token` accumulator driven by `reward_rate_per_block` and elapsed blocks [1](#0-0) , entirely independent of the actual balance of `reward_asset_id` held by the pool's reward account (`pool_info.account`). Nothing enforces that the pool account is, or remains, funded enough to cover the sum of all accruing promises.

### Finding Description
- `create_pool` lets any `CreatePoolOrigin` set an arbitrary `reward_rate_per_block` and `expiry_block` with **no funding requirement** — the pool's reward account is not required to hold `reward_rate_per_block * (expiry_block - now)` in the reward asset at creation time. [2](#0-1) 
- `set_pool_reward_rate_per_block` allows the admin to *increase* the reward rate (only cut is disallowed) without any check against the pool account's actual reward-asset balance. [3](#0-2) 
- Reward accrual (`reward_per_token`, `derive_rewards`) is a pure accounting formula based on `reward_rate_per_block` and elapsed blocks, with no reference to the pool account's real balance. [4](#0-3) 
- `harvest_rewards` then tries to `T::Assets::transfer` the accrued `staker_info.rewards` from `pool_info.account` to the staker with `Preservation::Expendable`. [5](#0-4)  If the pool account's real balance is less than the sum of all stakers' formulaically-accrued rewards (e.g., because the admin under-funded the pool relative to the rate they set, or because earlier stakers already drained the account), this transfer fails and the extrinsic reverts — the staker's already-accrued (and documented/expected) reward becomes permanently unclaimable as long as the pool remains underfunded.
- Compounding this, `harvest_rewards` never persists the recomputed `pool_info` back into `Pools` storage (unlike `stake`/`unstake`/`set_pool_reward_rate_per_block`, which all call `Pools::<T>::insert(pool_id, pool_info)`) [6](#0-5) , meaning `reward_per_token_stored`/`last_update_block` used for the *next* staker's calculation is never advanced by a lone harvester who doesn't also stake/unstake — this can distort relative shares among stakers over time and is a separate correctness bug, but does not fix the liquidity issue: `derive_rewards` is still driven purely by the formula, not by available balance.
- There is no invariant check anywhere in the pallet (no `try_state`/`try_runtime` hook for this pallet was found) that the sum of all `PoolStakers` accrued+unclaimed rewards is `<=` the reward account's `reducible_balance`, unlike `pallet-nomination-pools`, which explicitly performs this comparison in its `try_runtime` checks: `RewardPool::<T>::current_balance(id) >= pools_members_pending_rewards...` and logs a warning if violated. [7](#0-6)  `pallet-asset-rewards` has no analogous accounting guard at all — the deficit is only discovered when `harvest_rewards`' `Assets::transfer` fails.

### Impact Explanation
- **Fund lock / broken invariant**: A staker's promised, already-accrued reward can become permanently unclaimable if the reward pool's real asset balance falls short of the accounting formula's output. There is no mechanism (top-up call, deficit tracking, pro-rata scaling) to reconcile the two, unlike nomination pools' `adjust_pool_deposit`/imbalance tooling.
- **Griefing / race for scarce funds**: Because reward computation is per-staker and payout is first-come-first-served against a shared, possibly underfunded pot, early harvesters can drain the pool account, leaving later — equally entitled — stakers permanently unable to redeem their formulaically-accrued rewards. This is functionally identical to the rToken scenario where "RToken represents deposit + accrued interest" but redemption fails because the backing liquidity was never guaranteed.
- This pallet is used in `asset-hub-westend` runtime configuration, so this is a live in-scope runtime component. [8](#0-7) 

### Likelihood Explanation
No privileged/malicious actor is required beyond the pool's own designated (non-root, potentially permissionless-configured via `CreatePoolOrigin`) admin setting an unrealistic `reward_rate_per_block`, or simply the natural passage of time/participants outpacing what was deposited into the reward account — both are ordinary usage patterns, not adversarial governance abuse. Any staker calling the public, unprivileged `harvest_rewards` extrinsic can trigger the failure once the pool account's real balance is insufficient.

### Recommendation
Before allowing `create_pool` or `set_pool_reward_rate_per_block` to set/increase a rate, require and check that the reward account's `reducible_balance` covers the full projected payout window (`rate * remaining_blocks`), or alternatively track a running "reserved liability" for the pool and require top-ups (similar in spirit to nomination pools' `current_balance` vs `pending_rewards` comparison) before allowing rate increases or further accrual. `harvest_rewards` should also persist the updated `pool_info` to storage on all paths (fixing the currently-missing `Pools::<T>::insert`) and should cap/pro-rate a staker's payout to the pool's actual balance (analogous to nomination-pools' `.min(transferable_balance(...))` pattern in `withdraw_unbonded`) rather than reverting outright, or explicitly track and expose a deficit for governance/admin remediation.

### Proof of Concept
1. `CreatePoolOrigin` (any account satisfying that origin, e.g., a permissioned/root-set origin) calls `create_pool` with `reward_asset_id = X`, `reward_rate_per_block = R`, `expiry_block = now + N`, but only funds `pool_info.account` with a small amount `B << R*N` of asset `X` (there is no enforcement tying deposit to rate/duration).
2. Staker A calls `stake` with some `staked_asset_id` amount.
3. Time advances several blocks; `reward_per_token` accrues based purely on `R` and elapsed blocks, independent of `B`. [1](#0-0) 
4. Staker A calls `harvest_rewards`; if accrued rewards exceed `B`, the internal `T::Assets::transfer(..., Preservation::Expendable)` fails and the whole extrinsic reverts, even though the pallet's own accounting shows Staker A "earned" that amount. [5](#0-4) 
5. If multiple stakers are involved and `B` is between the individual and combined accrued totals, the first harvester(s) succeed and drain the account, while later, equally-entitled stakers' `harvest_rewards` calls permanently fail as long as the pool is not manually re-topped-up (there being no protocol-level mechanism forcing or guaranteeing such a top-up).

		pub fn harvest_rewards(
			origin: OriginFor<T>,
			pool_id: PoolId,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool and staker rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info =
				PoolStakers::<T>::get(pool_id, &staker).ok_or(Error::<T>::NonExistentStaker)?;
			let (pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Transfer unclaimed rewards from the pool to the staker.
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&staker,
				staker_info.rewards,
				// Could kill the account, but only if the pool was already almost empty.
				Preservation::Expendable,
			)?;

			// Emit event.
			Self::deposit_event(Event::RewardsHarvested {
				caller,
				staker: staker.clone(),
				pool_id,
				amount: staker_info.rewards,
			});

			// Reset staker rewards.
			staker_info.rewards = 0u32.into();

			if staker_info.amount.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			Ok(())
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}

		/// Derives the amount of rewards earned by a staker.
		///
		/// This is a helper function for `update_pool_rewards` and should not be called directly.
		fn derive_rewards(
			staker_info: &PoolStakerInfo<T::Balance>,
			reward_per_token: &T::Balance,
		) -> Result<T::Balance, DispatchError> {
			Ok(staker_info
				.amount
				.ensure_mul(reward_per_token.ensure_sub(staker_info.reward_per_token_paid)?)?
				.ensure_div(PRECISION_SCALING_FACTOR.into())?
				.ensure_add(staker_info.rewards)?)
		}

	fn create_pool(
		creator: &T::AccountId,
		staked_asset_id: T::AssetId,
		reward_asset_id: T::AssetId,
		reward_rate_per_block: T::Balance,
		expiry: DispatchTime<BlockNumberFor<T>>,
		admin: &T::AccountId,
	) -> Result<PoolId, DispatchError> {
		// Ensure the assets exist.
		ensure!(T::Assets::asset_exists(staked_asset_id.clone()), Error::<T>::NonExistentAsset);
		ensure!(T::Assets::asset_exists(reward_asset_id.clone()), Error::<T>::NonExistentAsset);

		// Check the expiry block.
		let now = T::BlockNumberProvider::current_block_number();
		let expiry_block = expiry.evaluate(now);
		ensure!(expiry_block > now, Error::<T>::ExpiryBlockMustBeInTheFuture);

		let pool_id = NextPoolId::<T>::try_mutate(|id| -> Result<PoolId, DispatchError> {
			let current_id = *id;
			*id = id.ensure_add(1)?;
			Ok(current_id)
		})?;

		let footprint = Self::pool_creation_footprint();
		let cost = T::Consideration::new(creator, footprint)?;
		PoolCost::<T>::insert(pool_id, (creator.clone(), cost));

		// Create the pool.
		let pool = PoolInfoFor::<T> {
			staked_asset_id: staked_asset_id.clone(),
			reward_asset_id: reward_asset_id.clone(),
			reward_rate_per_block,
			total_tokens_staked: 0u32.into(),
			reward_per_token_stored: 0u32.into(),
			last_update_block: 0u32.into(),
			expiry_block,
			admin: admin.clone(),
			account: Self::pool_account_id(&pool_id),
		};

		// Insert it into storage.
		Pools::<T>::insert(pool_id, pool);

		// Emit created event.
		Self::deposit_event(Event::PoolCreated {
			creator: creator.clone(),
			pool_id,
			staked_asset_id,
			reward_asset_id,
			reward_rate_per_block,
			expiry_block,
			admin: admin.clone(),
		});

		Ok(pool_id)
	}

	fn set_pool_reward_rate_per_block(
		admin: &T::AccountId,
		pool_id: PoolId,
		new_reward_rate_per_block: T::Balance,
	) -> DispatchResult {
		let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
		ensure!(pool_info.admin == *admin, BadOrigin);
		ensure!(
			new_reward_rate_per_block > pool_info.reward_rate_per_block,
			Error::<T>::RewardRateCut
		);

		// Always start by updating the pool rewards.
		let rewards_per_token = Self::reward_per_token(&pool_info)?;
		let mut pool_info = Self::update_pool_rewards(&pool_info, rewards_per_token)?;

		pool_info.reward_rate_per_block = new_reward_rate_per_block;
		Pools::<T>::insert(pool_id, pool_info);

		Self::deposit_event(Event::PoolRewardRateModified { pool_id, new_reward_rate_per_block });

		Ok(())
	}
