## Title
`accrue()` treasury-LP mint can underflow/divide-by-zero when reserve-fee share of accrued interest reaches the vault's total assets, permanently DoS-ing deposit/redeem/borrow/repay - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
`accrue()` (and its preview counterpart `calc-treasury-lp-preview`) computes the treasury's share of newly accrued interest with `(mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc))`. This mirrors the WatchPug `Basket.handleFees()` pattern (`fee * BASE / (BASE - feePct)`): a subtraction of an unbounded, time/rate-dependent value from a bounded reference value, with no explicit ceiling check before the subtraction/division.

### Finding Description
`accrue()` is invoked at the top of every state-changing vault entry point (`deposit`, `redeem`, `system-borrow`, `system-repay`, etc.), via `(u (try! (accrue)))`. [1](#0-0) [2](#0-1) [3](#0-2) 

Inside `accrue`, `reserve-inc` is the treasury's share of the interest delta accrued since `last-update`, and it is used to compute `treasury-lp` via:
```
(treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0))
``` [4](#0-3) 

`total-assets-preview` is `current-assets + interest`, where `interest = debt-preview - total-borrowed`: [5](#0-4) 

`debt-preview` rounds up (`mul-div-up`) while the `new-debt`/`old-debt`/`debt-delta` computation inside `accrue`/`calc-treasury-lp-preview` rounds down (`mul-div-down`): [6](#0-5) 

Algebraically, `total-assets-preview − reserve-inc ≈ current-assets + debt-delta·(1 − fee-reserve/BPS)`. This stays positive under normal conditions, but degenerates to exactly `0` (division by zero, which aborts in Clarity) when:
- `current-assets == 0` (the vault is fully utilized — an entirely ordinary state reachable simply by borrowers borrowing out all available liquidity via `system-borrow`), and
- `fee-reserve == BPS` (100% reserve factor) — a valid, in-range DAO-set parameter (nothing in this file clamps `fee-reserve` below `BPS`), analogous to the original report's "publisher sets an extreme but syntactically valid `licenseFee`."

Just as in the WatchPug analog, no time-elapsed dormancy is even required to trip the same class of bug once the reserve factor is pushed toward the ceiling and the pool is fully borrowed; a longer `time-delta` (vault left unaccrued while paused, or simply infrequently touched) only makes `debt-delta`/`reserve-inc` proportionally larger relative to `total-assets-preview`, making the boundary condition easier to reach, exactly mirroring how `timeDiff` amplified `feePct` in `Basket.handleFees()`.

Once this triggers, `(- (total-assets-preview) reserve-inc)` divides by zero (or, in adjacent roundings, underflows), aborting the transaction. Because `accrue()` runs unconditionally inside every `deposit`, `redeem`, `system-borrow`, and `system-repay` call, the entire vault becomes permanently unusable until the DAO manually lowers `fee-reserve` (or `index`/`last-update` state is otherwise reset) — the exact "disruption of minting and burning until publisher updates the value" outcome described in the source report.

### Impact Explanation
This is a protocol-wide, self-inflicted denial of service on a single vault: no user can deposit, redeem, borrow, or repay because every one of those entry points calls `accrue()` first and `accrue()` reverts. Funds already supplied/borrowed become temporarily frozen (unclaimed yield/interest accrual is also frozen) until intervention, which lands in the in-scope **High — temporary freezing of funds** category.

### Likelihood Explanation
The trigger requires two conditions to coincide: full utilization of vault liquidity (`current-assets == 0`, a state ordinary borrowers can create through normal, permissionless `system-borrow` usage) and a reserve factor at or very near the `BPS` ceiling. The second condition is DAO-controlled, but setting an aggressive reserve factor is a normal governance action, not a compromise of the DAO — exactly like the original report's publisher setting an extreme (but valid) license fee. Given full utilization is common in lending markets during high-demand periods, likelihood is non-trivial once a high reserve factor is configured.

### Recommendation
Clamp `fee-reserve` strictly below `BPS` at the setter, and/or cap `reserve-inc` so that `reserve-inc < total-assets-preview` before performing the division in both `accrue()` and `calc-treasury-lp-preview` (e.g., `min(reserve-inc, total-assets-preview - 1)`), so a boundary/edge value can never zero-out or underflow the denominator.

### Proof of Concept
1. DAO (or protocol default) sets `fee-reserve` to `BPS` (10000, i.e. 100%) for a vault such as `v0-vault-stx.clar`.
2. Borrowers call `system-borrow` repeatedly until `current-assets` (idle liquidity, tracked by `assets` var) reaches `u0`, i.e., 100% utilization.
3. Time passes so that `next-index` computes `new-debt > old-debt` (any nonzero `debt-delta`) via `calc-multiplier-delta`.
4. Any subsequent call to `deposit`, `redeem`, `system-borrow`, or `system-repay` invokes `accrue()`, which computes `reserve-inc == total-assets-preview` (since `current-assets = 0` and `fee-reserve = BPS` make `total-assets-preview − reserve-inc = 0`), causing `(mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc))` to divide by zero and abort.
5. The vault is now unusable for all core operations until `fee-reserve` is lowered by the DAO.
