Based on my investigation, I've confirmed the analog vulnerability in the exchange trading mechanism.

### Title
Exchange creator can front-run `ExchangeTransactionContract` orders via `ExchangeInject`/`ExchangeWithdraw` to sandwich traders - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
The bancor-formula-based on-chain exchange (`ExchangeCreate`/`ExchangeInject`/`ExchangeWithdraw`/`ExchangeTransaction`) lets any account submit a trade against a token pool while only the exchange's `creatorAddress` is permitted to inject or withdraw liquidity. Because pool balances are mutable by the creator with no timelock or cooldown, and a trader's only protection is a loose minimum-received (`expected`) check, the creator can front-run a visible pending trade to shift the effective exchange rate in their favor before the trade executes, mirroring the Teller "market owner front-runs bid parameters with no timelock" bug class.

### Finding Description
`ExchangeTransactionActuator.execute`/`doValidate` computes the amount a trader receives purely from the pool's current `firstTokenBalance`/`secondTokenBalance` at execution time via `ExchangeCapsule.transaction()`, which calls the bancor-relay math in `ExchangeProcessor`/`SafeExchangeProcessor`. [1](#0-0) 
The only slippage protection is the trader-supplied `expected` minimum, checked against the amount computed from the pool state at the moment the transaction actually executes on-chain: [2](#0-1) 

Only the exchange's creator can call `ExchangeInjectContract`/`ExchangeWithdrawContract`, which directly mutate the pool's `firstTokenBalance`/`secondTokenBalance`: [3](#0-2) [4](#0-3) 

There is no timelock, cooldown, or block-delay restricting how often or how close to a pending trade the creator can inject/withdraw. A trader observing the current pool ratio, computing an `expected` value from it, and broadcasting `ExchangeTransactionContract` has no guarantee that ratio holds by the time their transaction lands, exactly analogous to the Teller borrower who submits a bid based on the currently-visible `paymentDefaultDuration` with no protection against the market owner changing it before inclusion. The pool balance mutation function used by both inject/withdraw and the trade itself is the shared state read at broadcast-time vs. execution-time: [5](#0-4) 

### Impact Explanation
The exchange creator, upon seeing a pending `ExchangeTransactionContract` in the mempool (or simply by controlling timing across blocks), can submit an `ExchangeWithdrawContract`/`ExchangeInjectContract` to skew the pool ratio immediately before the trader's transaction executes, then reverse it immediately after (classic sandwich attack), extracting value from the trader while still satisfying the trader's loosely-set `expected` floor. This results in unauthorized value extraction from an unprivileged trader's funds — a concrete theft-of-funds impact reachable purely through ordinary signed transactions (`ExchangeInject`/`ExchangeWithdraw`/`ExchangeTransaction`), with no special node privilege required beyond being the exchange's creator, which itself is attainable by anyone via `ExchangeCreateContract`.

### Likelihood Explanation
Likelihood is high: any account can become an exchange creator by calling `ExchangeCreateContract`, and once a creator, injecting/withdrawing before an incoming trade is a single additional low-cost transaction, ordered by the block producer within the same or an adjacent block. Because there is no minimum time between creator liquidity actions and trades, and traders commonly set loose slippage protection (or none beyond `expected=0`), this is straightforward to execute repeatedly on a live exchange pair, unlike the Teller scenario which required only a single opportunistic front-run.

### Recommendation
Enforce a minimum cooldown/timelock between an exchange creator's `ExchangeInject`/`ExchangeWithdraw` and any pool state used to execute a pending `ExchangeTransactionContract` (e.g., only allow liquidity changes to take effect after N blocks, or restrict same-block/same-creator inject+trade+withdraw sequences). Alternatively, tighten trader protections by requiring a maximum-allowed pool price deviation between the block the transaction was signed/broadcast and the block of execution, not merely a minimum-received check.

### Proof of Concept
1. Attacker calls `ExchangeCreateContract` to create a TRX/TokenX pool and becomes `creatorAddress`.
2. Victim observes the pool ratio and broadcasts `ExchangeTransactionContract` selling TRX for TokenX with `expected` computed from the current ratio (see `getExpected` validation in `ExchangeTransactionActuator.doValidate`, lines 217-221).
3. Before the victim's transaction is packed into a block, attacker (as `creatorAddress`) broadcasts `ExchangeWithdrawContract` removing TokenX liquidity, which is only permitted for the creator (`ExchangeWithdrawActuator.doValidate`, lines 181-183), skewing the ratio unfavorably for the victim while still keeping the victim's trade above their `expected` floor.
4. Victim's `ExchangeTransactionContract` executes at the worse rate, computed via `ExchangeCapsule.transaction()` (lines 124-169), receiving less TokenX than the fair rate implied when they signed.
5. Attacker calls `ExchangeInjectContract` to restore the pool ratio, having captured the spread at the victim's expense — same "no timelock on a privileged parameter mutable by the counterparty" pattern as the Teller report's `setPaymentDefaultDuration`.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
