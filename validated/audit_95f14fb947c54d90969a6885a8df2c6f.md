### Title
Out-of-bounds heap read when parsing a malicious ZIP/JAR central directory in ijar - (File: third_party/ijar/zip.cc)

### Summary
`ijar`, Bazel's interface-jar generator used whenever a Java jar (including third-party jars fetched via `http_jar`/`http_file`/`http_archive`/Maven-style rules) is processed into a `-ijar` for compilation, parses the ZIP central directory without validating that per-entry variable-length fields stay inside the memory-mapped input file. A crafted jar can drive the parsing cursor past the end of the mapped buffer, causing an out-of-bounds heap read, mirroring the out-of-bounds read class described in CVE-2025-1919.

### Finding Description
`FindZipCentralDirectory` validates only the aggregate central-directory region against the file length: [1](#0-0) 

But the per-entry parser `InputZipFile::ProcessCentralDirEntry`, which is called in a loop (`ProcessNext`, `CalculateOutputLength`) to walk every entry in that region, advances its cursor `p` by attacker-controlled 16-bit length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) with no bounds check against either the validated central-directory size or the mapped file length: [2](#0-1) 

The subsequent extra-field walk is similarly unchecked — `data_size` is fully attacker-controlled and `extra_p` is advanced by it with no comparison to the buffer end before the next `get_u2le`/`get_u8le` reads: [3](#0-2) 

By contrast, the local-file-header parser explicitly guards every read with `EnsureRemaining()`: [4](#0-3) [5](#0-4) 

No equivalent check exists in `ProcessCentralDirEntry`, so a single entry with an oversized `file_name_length`/`extra_field_length`/`file_comment_length` (up to `0xFFFF` each) can push `p` past `bytes + in_length`. The next loop iteration (`ProcessNext`/`CalculateOutputLength`) then calls `get_u4le(p)` on unmapped/out-of-range heap memory — an out-of-bounds read (CWE-125). The declared `sha256`/`integrity` checksum on the fetched jar does not stop this: the checksum only certifies that the bytes consumed match what a malicious publisher chose to serve; it does not constrain the ZIP structure inside those bytes.

### Impact Explanation
Any build that unpacks/processes an attacker-published jar (e.g., via `http_jar`, `http_file` + `java_import`, or transitively through Maven-derived rules) and lets Bazel run `ijar` on it (for interface-jar generation, a routine, automatic step for `java_library`/`java_import`) exposes the parser to attacker-controlled ZIP central-directory bytes. The out-of-bounds read can crash the `ijar` process (denial of the build) or, depending on heap layout, read adjacent heap memory into fields (`filename`, `attr`, size fields) that influence subsequent decisions and output content, risking information disclosure into the produced interface jar or build log.

### Likelihood Explanation
Reaching `ProcessCentralDirEntry` requires only that the attacker's file pass Bazel's basic EOCD-location logic in `FindZipCentralDirectory`, which is easy to satisfy in a crafted, otherwise-valid-looking jar the attacker fully controls. No credential, network position, or mocked path is needed; a build merely needs to depend on and unpack the attacker's jar, which is a standard operation for jars fetched via URL rules.

### Recommendation
Add bounds checks in `InputZipFile::ProcessCentralDirEntry` (and its callers) mirroring `EnsureRemaining()`: verify that `p + 46 + file_name_length + extra_field_length + file_comment_length` never exceeds `central_dir_ + central_dir_size` (and ultimately `bytes + in_length`) before dereferencing, and validate each extra-field `data_size` against remaining bytes in the extra-field block before advancing `extra_p`.

### Proof of Concept
Construct a minimal valid ZIP whose EOCD/central-directory-size checks pass `FindZipCentralDirectory`, but whose single central-directory entry sets `file_name_length = 0xFFFF` (or `extra_field_length = 0xFFFF`) while the physical file is only a few hundred bytes long. Feed this file to `ijar` (e.g., via a `ZipExtractor::Create`/`ProcessAll()`-based JUnit/C++ test in `third_party/ijar`) and observe that `p`/`extra_p` advance past `zipdata_in_ + input_file_->Length()`, causing `get_u4le`/`get_u2le` to dereference memory outside the mapped file (observable as a crash or ASan heap-buffer-overflow report on the next `ProcessNext()` iteration).

  // abort with an error message.  "state" is the name of the field
  // we're about to read, for diagnostics.
  int EnsureRemaining(size_t n, const char *state) {
    size_t in_offset = p - zipdata_in_;
    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "
                   "expected %zd more bytes but found %zd.\n",
                   in_offset, state, n, remaining);
    }
    return 0;
  }
