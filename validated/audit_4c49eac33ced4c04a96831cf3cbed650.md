### Title
Archive cache-key collision via unescaped comma-joined pathspecs allows cross-request cache poisoning - (File: internal/gitaly/service/repository/archive.go)

### Summary
`createArchiveCacheKey` builds the cache key by hashing `strings.Join(args, ",")` and `strings.Join(pathspecs, ",")` without escaping the `,` separator, and `ValidateRelativePath` does not reject commas in paths. Because Git allows arbitrary bytes (including commas) in tree entry names, two structurally different `exclude`/path lists can serialize to identical joined strings, producing the same SHA-256 cache key for different actual `git archive` invocations.

### Finding Description
`GetArchive` validates paths only via `storage.ValidateRelativePath` [1](#0-0)  and `storage.ValidateRelativePath` only checks path-escape via `filepath.Join`/`filepath.Rel`; it performs no character allow-listing, so commas are legal in a relative path [2](#0-1) . `handleArchive` builds `pathspecs` from `p.archivePath` and prefixed excludes (`":(exclude)"+exclude`) and computes the cache key by joining these lists with `,` and hashing the concatenation, with no length-prefixing or delimiter escaping between elements or between the `args` and `pathspecs` blocks [3](#0-2) . Because a single pathspec/exclude entry may itself legitimately contain a literal `,` (Git tree entries can have almost any byte in their names, reachable by an attacker who can construct a tree via low-level plumbing or a normal commit containing such a filename), a one-element list `["a,:(exclude)b"]` and a two-element list `["a", ":(exclude)b"]` (or comparable variants) can serialize to the exact same joined string, yielding an identical cache key computed from `s.archiveCache.Fetch(ctx, cacheKey, ...)` at line 245 despite representing different actual `git archive` `PostSepArgs`/`Args` passed to the real command at lines 246-251.

### Impact Explanation
This is a cache-key collision that lets a request for one archive configuration (path/excludes) be served the cached bytes generated by a different configuration. Because `createArchiveCacheKey` also folds in `repo.GetGlProjectPath()`, the collision is confined to requests against the *same* GitLab project, not across arbitrary projects/users the attacker doesn't already have repo access to. Within a shared project (e.g., multiple collaborators or CI jobs pulling `GetArchive` for the same repo), an attacker who can create colliding pathnames could prime the cache so that a legitimate caller (another user/CI job requesting a specific path/exclude set) receives archive content generated for a different, attacker-chosen set of excludes/paths — an integrity/cache-poisoning issue (wrong file content served for a given RPC request) rather than a strict cross-project confidentiality breach, since both requests are already scoped to the same repository the parties can already read.

### Likelihood Explanation
Exploitation requires: (1) the attacker controls or can create paths inside a shared/public project containing crafted commas, (2) another user or automated process requests `GetArchive` with parameters that happen to serialize into the same joined string, and (3) both requests hit the archive cache within its retention window. Constructing exact colliding pathspec strings (embedding literal `:(exclude)` text plus commas as real Git tree entry names) is non-trivial but feasible via low-level Git plumbing (`git mktree`, `git hash-object`) even though normal checkouts may reject such filenames. This makes the issue a genuine but narrow, project-scoped cache-poisoning primitive rather than a directly weaponizable cross-tenant read primitive.

### Recommendation
Use a collision-resistant, unambiguous serialization for the cache key — e.g., write each element's length before its bytes (length-prefixed encoding) or hash each argument/pathspec independently and combine the digests, instead of joining with a plain `,` separator. This removes any possibility of different lists collapsing to the same joined string.

### Proof of Concept
```go
func TestCreateArchiveCacheKeyCollision(t *testing.T) {
    keyA := createArchiveCacheKey("group/project",
        []string{"deadbeef"},
        []string{"a,:(exclude)b"}, // single pathspec containing a literal comma
    )
    keyB := createArchiveCacheKey("group/project",
        []string{"deadbeef"},
        []string{"a", ":(exclude)b"}, // two distinct pathspecs
    )
    require.Equal(t, keyA, keyB) // demonstrates the collision
}
```
This demonstrates that `createArchiveCacheKey` [3](#0-2)  produces identical keys for semantically different `pathspecs` inputs, which in a real `GetArchive` flow would be populated from attacker-controlled repository paths that pass `storage.ValidateRelativePath` unchanged.

```go
func createArchiveCacheKey(gitLabProjectPath string, args []string, pathspecs []string) string {
	cacheKeyHash := sha256.New()
	cacheKeyHash.Write([]byte(gitLabProjectPath))
	cacheKeyHash.Write([]byte(strings.Join(args, ",")))
	cacheKeyHash.Write([]byte(strings.Join(pathspecs, ",")))
	return hex.EncodeToString(cacheKeyHash.Sum(nil))
}
```

```go
func ValidateRelativePath(rootDir, relativePath string) (string, error) {
	absPath := filepath.Join(rootDir, relativePath)
	if rootDir != absPath && !strings.HasPrefix(absPath, rootDir+string(os.PathSeparator)) {
		return "", ErrRelativePathEscapesRoot
	}

	return filepath.Rel(rootDir, absPath)
}
```
