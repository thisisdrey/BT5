### Title
Ambiguous quarantine-detection heuristic in gRPC middleware allows crafted RPC fields to bypass transactional/quarantine gating and inject an attacker-controlled repository path - (File: internal/gitaly/storage/storagemgr/middleware.go)

### Summary
`beginTransactionForRepository` decides whether a repository-scoped RPC should run inside Gitaly's transaction/partition machinery by inferring "this request already carries a quarantine and is a Rails access-check loop-back" purely from the *presence* of the `GitObjectDirectory`/`GitAlternateObjectDirectories` fields on the target repository message. This single ambiguous signal is checked inconsistently for mutators versus accessors, exactly the class of bug described in the report (a single overloaded status/flag used to gate multiple, unrelated operations, checked differently in different code paths).

### Finding Description
In `beginTransactionForRepository`: [1](#0-0) 

the code treats a non-empty `GitObjectDirectory`/`GitAlternateObjectDirectories` on the *incoming request* as proof that "the request was already configured with a quarantine directory and is being looped back to Gitaly from Rails' authorization checks" and therefore skips starting a new transaction entirely. The function's own comment admits the heuristic is unsound: [2](#0-1) 

For `OpMutator` RPCs, this ambiguous signal is rejected with `ErrQuarantineConfiguredOnMutator`, but for `OpAccessor` RPCs the same signal instead routes the request through `restoreSnapshotRelativePath`, which unconditionally overwrites the target repository's `RelativePath` with an attacker/client-controlled gRPC metadata value (`MetadataKeySnapshotRelativePath`) and runs the RPC **outside of any transaction**, with none of the validation (`locator.ValidateRepository`, partition assignment, `storage.ValidateRelativePath`) that the normal transactional path performs: [3](#0-2) 

This is the same root-cause shape as the Drift `ExchangeStatus` bug: one field/flag is overloaded to represent two unrelated concepts ("does this repository have a quarantine configured" and "is this a legitimate Rails access-check loop-back"), and the two call sites (mutator branch vs. accessor branch) check it with different consequences instead of validating the actual claim (that the relative path/quarantine truly originated from the transaction that created it). The only downstream safety net is `ObjectDirectoryPath`'s prefix check tying an object directory to `QuarantineDirectoryPrefix(repo)`, but that prefix is itself derived from the same attacker-suppliable `RelativePath` field, so an attacker who controls both `GitObjectDirectory` and the `relative-path-bin` header can construct an internally-consistent pair that satisfies the prefix check for a *different* target than the one actually authorized by an in-flight transaction: [4](#0-3) [5](#0-4) 

### Impact Explanation
An accessor RPC whose request message exposes `GitObjectDirectory`/`GitAlternateObjectDirectories` fields (many `RepositoryService`/`CommitService`/`BlobService` accessor RPCs do, since Rails relies on this exact mechanism for access-check loop-backs) can be made to skip Gitaly's transaction/partition manager entirely and operate against a caller-supplied relative path taken from gRPC metadata rather than the path resolved and validated by the transaction manager. This breaks the guarantee that repository-scoped RPCs only ever read from a partition-manager-issued snapshot, and can result in an accessor reading objects/refs from a directory the caller specified rather than the one the surrounding access-check transaction actually authorized — a cross-repository/quarantine-boundary violation analogous to Drift's unintended unpausing of a different operation than the admin intended.

### Likelihood Explanation
Reaching this code path requires only a normal repository-scoped RPC request with the object-directory fields populated and a `relative-path-bin` metadata header — no privileged Gitaly/Praefect internals are required to construct the message, since these are ordinary fields on `gitalypb.Repository` in the request proto and ordinary gRPC metadata. The comment in the code explicitly documents that "tests... manually configure the object directory... allows circumventing the transaction management," confirming the maintainers are aware this signal is not authenticated/verified against the actual transaction state, only inferred from field presence.

### Recommendation
Do not infer "this is a legitimate access-check loop-back" from the mere presence of `GitObjectDirectory`/`GitAlternateObjectDirectories`. Instead, bind the quarantine/loop-back state to an authenticated, server-issued token (e.g., the actual transaction/snapshot ID) rather than a client-suppliable relative path, and apply the exact same verification (`locator.ValidateRepository`, path containment) to the accessor loop-back path that mutators/normal transactional requests receive. Consolidate the "is this request quarantine-configured / loop-back" determination into a single, consistently-checked representation instead of two different consequences (`ErrQuarantineConfiguredOnMutator` vs. silent path substitution) derived from the same ambiguous fields.

### Proof of Concept
Not independently executable from static analysis alone; the concrete PoC would require: (1) issuing an accessor RPC (e.g., a `CommitService`/`BlobService` call) directly against `gitaly-server` with `GitObjectDirectory` set to a crafted value and (2) the `relative-path-bin` metadata header set to a relative path different from the one legitimately in use by the in-flight transaction, then observing that `restoreSnapshotRelativePath` substitutes the caller-supplied path and the RPC executes non-transactionally against it, as described by the code comment at `internal/gitaly/storage/storagemgr/middleware.go:277-282`. Full confirmation would require running Gitaly locally and crafting such a request, which is outside the scope of this static analysis.

func restoreSnapshotRelativePath(ctx context.Context, methodInfo protoregistry.MethodInfo, req proto.Message) (proto.Message, error) {
	// Rails sends RPCs from its access checks with quarantine applied. The quarantine paths are relative to the
	// snapshot repository of the original transaction. While the relative path of the request is the original relative
	// path of the repository before snapshotting, Rails sends the snapshot repository's path in a header. For the
	// quarantine paths to apply correctly, we must thus rewrite the request to point to the snapshot repository here.
	snapshotRelativePath := metadata.GetValue(ctx, MetadataKeySnapshotRelativePath)
	if snapshotRelativePath == "" {
		return nil, ErrQuarantineWithoutSnapshotRelativePath
	}

	rewrittenReq, targetRepo, err := rewritableRequest(methodInfo, req)
	if err != nil {
		return nil, fmt.Errorf("rewritable request: %w", err)
	}

	targetRepo.RelativePath = snapshotRelativePath

	return rewrittenReq, nil
}

func QuarantineDirectoryPrefix(repo Repository) string {
	hash := [20]byte{}
	if repo != nil {
		hash = sha1.Sum([]byte(repo.GetRelativePath()))
	}
	return fmt.Sprintf("quarantine-%x-", hash[:8])
}
