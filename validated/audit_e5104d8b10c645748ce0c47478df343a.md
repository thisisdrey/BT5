### Title
Unprivileged caller can freeze victim's FA primary store via `migrate_coin_store_to_fungible_store` — (`aptos-move/framework/aptos-framework/sources/coin.move`)

### Summary
`migrate_coin_store_to_fungible_store` is a `public entry` function with **no signer parameter**. Any unprivileged account can call it with an arbitrary `vector<address>`. When a victim holds a frozen `CoinStore<CoinType>` (with non-zero balance) alongside a pre-existing unfrozen FA primary store, the migration unconditionally propagates the `frozen=true` flag to the FA store via `set_frozen_flag_internal`, bypassing the `TransferRef`-gated `set_frozen_flag` path that is the only authorized freeze mechanism for FA stores.

### Finding Description

**Entry point — no authorization:** [1](#0-0) 

`migrate_coin_store_to_fungible_store` accepts a raw `vector<address>` with no signer. Any account on mainnet can submit this transaction.

**Freeze propagation logic:** [2](#0-1) 

The code itself documents the behavior: if the CoinStore is frozen and the FA primary store is not, `set_frozen_flag_internal` is called with `frozen=true`. The condition `frozen != fungible_asset::is_frozen(store)` is satisfied whenever the two states differ, and there is no guard preventing an unprivileged caller from triggering this.

**`set_frozen_flag_internal` bypasses `TransferRef`:** [3](#0-2) 

The normal public API `set_frozen_flag` requires a `&TransferRef` held by the coin issuer. `set_frozen_flag_internal` is `public(friend)` and writes directly to `FungibleStore.frozen` with no capability check. `coin.move` is a declared friend of `fungible_asset.move`, so this call is permitted — but it is reachable here without any privilege.

**Contrast with the self-migration path:** [4](#0-3) 

`migrate_to_fungible_store` requires `account: &signer`, so only the account owner can trigger it for themselves. `migrate_coin_store_to_fungible_store` has no such constraint.

### Impact Explanation

**Preconditions (all reachable on mainnet):**
1. Coin issuer has frozen victim's `CoinStore<CoinType>` (non-zero balance) using `FreezeCapability`.
2. Victim independently holds a pre-existing, unfrozen FA primary store for the same coin type with additional balance (e.g., received via FA transfer before migration).

**Attack:**
- Attacker submits `migrate_coin_store_to_fungible_store<CoinType>([victim_addr])`.
- `maybe_convert_to_fungible_store` moves out the CoinStore (`frozen=true`, `coin.value > 0`), retrieves the existing FA primary store (unfrozen), detects the mismatch, and calls `set_frozen_flag_internal(store, true)`.
- Victim's FA primary store is now frozen. All FA balance — including the pre-existing unfrozen funds that were never subject to the CoinStore freeze — becomes unspendable.

**Victim impact:** Cannot withdraw or transfer any FA balance for that coin type. The victim holds no `TransferRef` and cannot unfreeze the store themselves. Only the coin issuer (holding the `TransferRef` stored in `PairedFungibleAssetRefs`) can reverse this, and they may be unaware the migration was externally triggered.

### Likelihood Explanation

The precondition (frozen CoinStore + pre-existing FA balance) is a realistic state during the Coin→FA migration period. The entry function is freely callable. An attacker who wants to harm a specific victim (e.g., a competitor, a protocol's treasury) only needs to know the victim's address and that their CoinStore is frozen.

### Recommendation

Add a signer requirement to `migrate_coin_store_to_fungible_store` so only the account owner (or an explicitly authorized party) can trigger migration for a given address, consistent with `migrate_to_fungible_store`. Alternatively, skip the `set_frozen_flag_internal` call when the FA primary store pre-existed and already had balance, or require the caller to be the coin issuer when the CoinStore is frozen.
