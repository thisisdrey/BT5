### Title
No `anotherTokenQuant` slippage bound in `ExchangeInjectContract` leaves liquidity providers with no control over the second-token amount deducted - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` lets a user inject a fixed `quant` of one token into a bancor-style TRX/TRC10 liquidity pool (`Exchange`), while the corresponding amount of the *other* token (`anotherTokenQuant`) is computed dynamically from the pool's current ratio at execution time and silently deducted from the same account. Unlike `ExchangeTransactionContract`, which carries an `expected` field enforced in validation, `ExchangeInjectContract` has no user-supplied bound on `anotherTokenQuant`, so users cannot protect themselves from unfavorable pool-ratio movement between transaction submission and inclusion.

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` [1](#0-0) . There is no `expected`/min/max field analogous to the one present on `ExchangeTransactionContract` [2](#0-1) .

In `ExchangeInjectActuator.doValidate()`, the amount of the second token the account must also give up (`anotherTokenQuant`) is derived purely from the exchange pool's *current* `firstTokenBalance`/`secondTokenBalance` at the moment the transaction is validated/executed on-chain — not from any value chosen by the submitter: [3](#0-2) 

The same computation is repeated in `execute()` using the pool state at execution time, and both `tokenQuant` and the freshly-computed `anotherTokenQuant` are deducted from the account's balance/assets: [4](#0-3) 

Because the exchange pool ratio changes as other participants trade against it via `ExchangeTransactionActuator` (which mutates `firstTokenBalance`/`secondTokenBalance` through the bancor `transaction()` method) [5](#0-4) , the ratio at the time an `ExchangeInjectContract` is broadcast can differ materially from the ratio at the time it is actually validated and applied to the chain. The submitter fixes only `quant` (the amount of one side), and has zero way to cap or bound how much of the other token they end up paying — this is the direct analog of the reported "no `minShares`/slippage parameter" issue, but here it manifests as no maximum bound on the *second* asset deducted from the injecting account.

By contrast, `ExchangeTransactionContract` explicitly protects the caller with a validated `expected` minimum-output check [6](#0-5) , and `ExchangeWithdrawContract` at least bounds the withdrawer to their own proportional share with a precision check [7](#0-6) . `ExchangeInjectContract` has no equivalent safeguard.

### Impact Explanation
A liquidity provider who broadcasts an `ExchangeInjectContract` intending to inject at a known ratio can have significantly more of the "other" asset deducted than anticipated if the pool ratio shifts unfavorably before the transaction is processed (e.g., due to a preceding large `ExchangeTransactionContract` trade, whether organic or deliberately front-run). Since both amounts are pulled straight from the account's TRX balance/TRC10 asset balance with no user-chosen ceiling, this can result in the account losing more value than intended in a single unauthorized-amount deduction — a concrete loss-of-funds condition for the transaction submitter.

### Likelihood Explanation
Any account can hold TRX/TRC10 balances and broadcast `ExchangeInjectContract` at will; no special privilege is required. The condition is reachable whenever the exchange's pool ratio moves between the time a user signs/broadcasts the inject transaction and the time it is included in a block — which is a normal, expected occurrence on an active exchange pool, and can be exacerbated by an adversary submitting a large trade against the same `exchange_id` beforehand.

### Recommendation
Add an optional bound field to `ExchangeInjectContract` (e.g., `max_another_token_quant` or `min_another_token_quant`, depending on the injected side), and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` similarly to how `expected` is enforced in `ExchangeTransactionActuator` [6](#0-5) , rejecting the transaction if the computed `anotherTokenQuant` exceeds the user-specified maximum.

### Proof of Concept
1. Attacker/other user observes an `Exchange` pool with `firstTokenBalance`/`secondTokenBalance` ratio R.
2. Victim signs and broadcasts `ExchangeInjectContract{token_id=A, quant=Q}` expecting to also pay `anotherTokenQuant ≈ Q * secondTokenBalance / firstTokenBalance` under ratio R, per [8](#0-7) .
3. Before the victim's transaction is included, another party executes a large `ExchangeTransactionContract` against the same `exchange_id`, shifting `firstTokenBalance`/`secondTokenBalance` via `ExchangeCapsule.transaction()` [5](#0-4) .
4. The victim's `ExchangeInjectContract` is then validated/executed against the new, worse ratio; `anotherTokenQuant` is recomputed higher than the victim expected and deducted from their account in `execute()` [9](#0-8) , with no validation check available to reject the unfavorable outcome, since `ExchangeInjectContract` carries no `expected`/bound field.

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
