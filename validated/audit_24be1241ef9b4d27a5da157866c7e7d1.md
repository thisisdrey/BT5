### Title
`NativeWithdraw` burns wNEAR balance with no refund/resolver if `receiver_id` does not exist, permanently freezing user funds - (File: `contracts/defuse/src/contract/tokens/nep141/native.rs`)

### Summary
The `NativeWithdraw` intent lets any account owner withdraw native NEAR by burning their internal wNEAR balance and sending a plain `Promise::new(receiver_id).transfer(amount)`. Unlike `FtWithdraw`/`MtWithdraw`, which schedule a `ft_resolve_withdraw`/`mt_resolve_withdraw` callback to detect a failed transfer and restore the user's internal balance, `do_native_withdraw` has no resolver at all. If `receiver_id` is a syntactically valid but non-existent named NEAR account (typo, or account not yet created), the `Transfer` action fails on-chain, NEAR refunds the attached balance to the *predecessor* of that failed receipt (the Defuse contract account itself, via `env::current_account_id()`), and the user's internal wNEAR balance has already been irreversibly decremented with no way to reclaim it.

### Finding Description
The withdrawal flow is:
1. `native_withdraw` in `contracts/defuse/src/contract/intents/state.rs` (lines 212-240) calls `self.withdraw(...)` to subtract the amount from the owner's internal wNEAR ledger balance, then calls `wnear.near_withdraw(...)`, and chains `.then(...do_native_withdraw(withdraw))`.
2. `do_native_withdraw` in `contracts/defuse/src/contract/tokens/nep141/native.rs` (lines 7-19) only checks that `near_withdraw` succeeded, then issues `Promise::new(withdraw.receiver_id).transfer(withdraw.amount)` with **no `.then()` resolver** attached to inspect the outcome of this final transfer.

Compare this to `FtWithdraw` (`contracts/defuse/src/contract/tokens/nep141/withdraw.rs`, lines 96-104), which always chains a `ft_resolve_withdraw` callback after the actual `ft_transfer`/`ft_transfer_call`, allowing the contract to detect failure and credit the balance back to the owner. `NativeWithdraw` has no equivalent safety net.

The documentation comment on the intent itself acknowledges the gap:
```
/// Withdraw native tokens (NEAR) from the intents contract to a given external account id (external being outside of intents).
/// This will subtract from the account's wNEAR balance, and will be sent to the account specified as native NEAR.
/// NOTE: the `wNEAR` will not be refunded in case of fail (e.g. `receiver_id`
/// account does not exist).
``` [1](#0-0) 

On NEAR, a plain `Transfer` action to a named account that does not yet exist fails with an account-not-created error at the protocol level (unlike implicit hex accounts, which are always considered to exist). When that receipt fails, the attached NEAR balance is refunded back to the *predecessor* of the failed receipt — here, the Defuse contract itself (since `do_native_withdraw` runs as a self-call, `env::current_account_id()`) — not to the withdrawing user. Meanwhile, the user's internal wNEAR balance was already burned via `self.withdraw(...)` and `near_withdraw(...)` before the outbound transfer was even attempted. [2](#0-1) [3](#0-2) 

This breaks the conservation binding described in the rules: `value debited == value delivered + value refunded`. Here, `value_debited (wNEAR burned from owner) > value_delivered (0, transfer failed) + value_refunded_to_owner (0)`. The refunded NEAR silently accrues to the Defuse contract's own account balance instead, with no ledger entry crediting anyone — it is not recoverable through any normal user or intent flow.

### Impact Explanation
This is Critical: user funds are permanently frozen due to a missing authorization/consistency check comparable in root cause to the referenced report — an externally supplied destination address is trusted without verifying it can actually receive the funds, and there is no resolver/refund path to reconcile ledger state with on-chain outcome (unlike the sibling `FtWithdraw`/`MtWithdraw`/`NftWithdraw` flows, which do have `*_resolve_withdraw` callbacks). Any single signer authorized to submit a `NativeWithdraw` intent for their own account (no relayer, DAO, or privileged role needed) can trigger this — either by accident (typo) or, more importantly, the vulnerability class itself represents an unrecoverable-funds bug reachable purely by normal intent execution.

### Likelihood Explanation
Likelihood is moderate-to-high: `receiver_id` is a fully attacker/user-controlled `AccountId` field on the `NativeWithdraw` intent with no existence check performed anywhere in the flow before the wNEAR balance is irreversibly burned. Any named NEAR account that has not been created (e.g., a fresh/misspelled subaccount) triggers this deterministically.

### Recommendation
Add a resolver callback analogous to `ft_resolve_withdraw`/`mt_resolve_withdraw` after the `Promise::new(receiver_id).transfer(amount)` call in `do_native_withdraw`, which checks `promise_result_checked_void` and, on failure, credits the withdrawn amount back to `owner_id`'s internal wNEAR balance (mirroring `internal_add_balance`). Alternatively/additionally, validate that `receiver_id` exists (e.g., via a preceding view call or requiring `storage_deposit`-style existence proof) before burning the internal balance.

### Proof of Concept
1. User `alice.near` has an internal wNEAR balance of `X` NEAR in Defuse.
2. `alice.near` signs and submits a `NativeWithdraw { receiver_id: "typo-nonexistent.near", amount: X }` intent.
3. `native_withdraw` (`contracts/defuse/src/contract/intents/state.rs:212-240`) subtracts `X` from `alice.near`'s internal wNEAR balance and calls `wnear.near_withdraw(X)`.
4. `do_native_withdraw` (`contracts/defuse/src/contract/tokens/nep141/native.rs:12-19`) issues `Promise::new("typo-nonexistent.near").transfer(X)`. Because the account does not exist, this receipt fails on-chain.
5. NEAR protocol refunds `X` back to the Defuse contract account (the predecessor of the failed receipt), not to `alice.near`.
6. No callback exists to detect the failure, so `alice.near`'s internal ledger balance remains debited by `X` with no compensating credit — the funds are permanently lost to `alice.near` and untracked within the contract's ledger.

    fn native_withdraw(&mut self, owner_id: &AccountIdRef, withdraw: NativeWithdraw) -> Result<()> {
        self.withdraw(
            owner_id,
            [(
                Nep141TokenId::new(self.wnear_id().into_owned()).into(),
                withdraw.amount.as_yoctonear(),
            )],
            Some("withdraw"),
            false,
        )?;

        ext_wnear::ext(self.wnear_id.clone())
            .with_attached_deposit(NearToken::from_yoctonear(1))
            .with_static_gas(NEAR_WITHDRAW_GAS)
            // do not distribute remaining gas here
            .with_unused_gas_weight(0)
            .near_withdraw(U128(withdraw.amount.as_yoctonear()))
            .then(
                // do_native_withdraw only after unwrapping NEAR
                Self::ext(env::current_account_id())
                    .with_static_gas(Self::DO_NATIVE_WITHDRAW_GAS)
                    // do not distribute remaining gas here
                    .with_unused_gas_weight(0)
                    .do_native_withdraw(withdraw),
            )
            .detach();

        Ok(())
    }

#[near]
impl Contract {
    pub(crate) const DO_NATIVE_WITHDRAW_GAS: Gas = Gas::from_tgas(12);

    #[private]
    pub fn do_native_withdraw(withdraw: NativeWithdraw) -> Promise {
        require!(
            promise_result_checked_void(0).is_ok(),
            "near_withdraw failed",
        );

        Promise::new(withdraw.receiver_id).transfer(withdraw.amount)
    }
