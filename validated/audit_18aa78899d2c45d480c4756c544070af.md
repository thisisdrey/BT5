### Title
Gas key nonce reseed on same-block DeleteKey+AddKey allows replay of an already-executed gas-key transaction - (File: runtime/runtime/src/access_keys.rs)

### Summary
`add_gas_key` reseeds every `nonce_index` in `0..num_nonces` to `initial_nonce_value(block_height)`, which depends only on the current block height, not on any nonce previously consumed under that public key. If a gas key is deleted and immediately re-added with the *same* `public_key` at the *same* `block_height` at which one of its nonce indices was already used, the reseed value equals the seed used when the key was first created at that height, which is lower than the already-consumed nonce. A previously signed and executed gas-key transaction for that index can then be resubmitted and re-executed.

### Finding Description
`add_gas_key` (runtime/runtime/src/access_keys.rs:194-228) sets every nonce slot with: [1](#0-0) 
using `initial_nonce_value(block_height)`: [2](#0-1) 
This function is purely a function of `block_height`, so re-adding the same `public_key` at the same block height reproduces the exact seed used when the key was originally created there.

`delete_gas_key` removes the access key and all its nonce rows (runtime/runtime/src/access_keys.rs:93-134) but only permits deletion when `gas_key_info.balance <= GasKeyInfo::MAX_BALANCE_TO_BURN` (line 103), so the balance must be drained close to zero before a delete+re-add can succeed. `action_add_key` only rejects an `AddKey` if the key still exists in the (in-progress) `TrieUpdate` (runtime/runtime/src/access_keys.rs:157-164); since `DeleteKey` and `AddKey` run sequentially against the same `TrieUpdate` within one receipt, `DeleteKey(pk)` followed by `AddKey(pk, GasKeyFullAccess)` in the same receipt succeeds and re-seeds the nonce array.

`verify_and_charge_gas_key_tx_ephemeral` (runtime/runtime/src/verifier.rs:370-478) validates a gas-key transaction's nonce against the value fetched fresh from state (`current_nonce`), combined with `pending.max_nonce`: [3](#0-2) 
There is no tracking of the historical high-water-mark nonce ever consumed for a given `(public_key, nonce_index)` beyond what is currently stored on-chain; once the stored value is reseeded to a lower number, an old, previously-valid, already-executed transaction with a nonce above the new seed but below/around it (or simply above the new lower seed) becomes valid again.

Exploit flow:
1. Attacker creates and funds a `GasKeyFullAccess` key at block height `H` (or earlier) and consumes `nonce_index = 0` with a transaction of nonce `X` at height `H`.
2. In the same block `H`, attacker submits a second receipt: `DeleteKey(pk)` (requires balance ≤ `MAX_BALANCE_TO_BURN`, so attacker first drains/spends the gas key balance) followed by `AddKey(pk, GasKeyFullAccess)` for the same `pk`. This resets every nonce index, including index 0, back to `initial_nonce_value(H)`, identical to the value used when the key was first seeded at `H`, i.e. below `X`.
3. Attacker re-funds the gas key via `TransferToGasKey`.
4. At a later block (within the transaction's `block_hash` validity window), attacker resubmits the exact previously-signed transaction with nonce `X` for `nonce_index = 0`. `verify_nonce(X, initial_nonce_value(H))` succeeds because `X > initial_nonce_value(H)`, so the transaction is accepted and its actions execute a second time.

No existing check (signature check, `AddKeyAlreadyExists`, `MAX_BALANCE_TO_BURN` burn gate, or `verify_nonce`) prevents this because none of them track nonces already consumed prior to a key's deletion/recreation.

### Impact Explanation
This breaks the "each signed transaction executes at most once" nonce-uniqueness invariant for gas-key transactions: a previously executed transaction can be re-executed by its own signer after a same-block delete/re-add of the gas key. This matches the "double-spend/replay" bounty category. The attacker must pay again for gas (refund the gas key balance) and for any attached deposit (deducted from the account balance again in `verify_and_charge_gas_key_tx_ephemeral`, lines 490-503), so there is no free minting of value purely from the runtime's perspective; however, replaying the identical signed transaction a second time can double-trigger the transaction's actions/side effects (e.g. a `FunctionCall` to a third-party contract, or a `Transfer`), which is a genuine violation of the expected at-most-once execution guarantee that other contracts and off-chain systems rely upon.

### Likelihood Explanation
This requires the attacker to control an account with a fully funded gas key, drive its balance down to at most `MAX_BALANCE_TO_BURN`, and get two of their own transactions (the original gas-key tx and the delete+add+re-fund receipt) included in the same block height, then resubmit the original signed bytes within the transaction validity window. This is a tight but achievable timing/ordering requirement for an unprivileged account acting only against its own key, with no validator or node privileges required.

### Recommendation
Track a monotonic high-water-mark nonce (or per-nonce-index high-water-mark) independent of `block_height` and independent of key deletion, so that re-adding a gas key (or a regular key) with the same `public_key` can never reseed the nonce below any value ever previously accepted for that `(account_id, public_key[, nonce_index])`. Alternatively, forbid `AddKey` from reusing a `public_key` that was ever previously registered on the account (not just currently registered), or persist the last-used nonce(s) for a deleted key until the transaction validity window has fully elapsed.

### Proof of Concept
Unit test in `runtime/runtime/src/access_keys.rs` (or an integration test in `runtime/runtime/src/tests/apply.rs` mirroring `test_gas_key_burn_not_reported_on_failed_receipt`):
1. At block height `H`, add a `GasKeyFullAccess` key with `num_nonces = 1`, fund it, and record `get_gas_key_nonce(index=0)` = seed `S0`.
2. Execute a gas-key transaction with `nonce_index = 0` and `nonce = S0 + 5`, asserting success and that `get_gas_key_nonce(index=0)` is now `S0 + 5`.
3. Drain the gas key balance to ≤ `GasKeyInfo::MAX_BALANCE_TO_BURN`, then apply a receipt at the same block height `H` containing `DeleteKey(pk)` followed by `AddKey(pk, GasKeyFullAccess)`.
4. Assert `get_gas_key_nonce(index=0)` after step 3 equals `S0` again (i.e. `<= S0 + 5`, the previously consumed value).
5. Re-fund the key and call `verify_and_charge_gas_key_tx_ephemeral` (or re-apply the transaction from step 2) with `nonce = S0 + 5` against the reseeded state, asserting it returns `TxVerdict::Success` (a `TxVerdict::Failed(InvalidNonce)` would indicate the bug is fixed).
