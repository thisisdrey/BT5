## Title
`socialize-debt` writes down the vault liquidity index using a stale, un-accrued interest snapshot, permanently losing/misallocating unclaimed yield - (File: `mainnet/contracts/vault/v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`)

### Summary
Every state-mutating vault entry point (`deposit`, `redeem`, `transfer`, `system-borrow`, `system-repay`, `flashloan`) begins with `(try! (accrue))` so that the interest index, liquidity index, and treasury LP mint are brought up to date *before* any balance change is applied. `socialize-debt` is the sole exception: it reads `index`, `total-borrowed`, `assets`, and `lindex` directly from storage without calling `accrue` first, then uses these stale values to compute `debt-reduction` and the new write-down `lindex`, before the caller (`market.clar`) invokes `accrue` in a subsequent, separate call. This mirrors the DERBY root cause: a value used for reward/accounting math (`savedTotalUnderlying` there, `lindex`/`total-assets` here) is computed and consumed across an operation boundary where interest/yield accrual should have happened first but didn't.

### Finding Description
`socialize-debt` computes: [1](#0-0) 

using `idx` = `(var-get index)` and `old-total-assets` = `(total-assets)`, both of which reflect the index as of the *last* `accrue` call (`last-update`), not the current block. `total-assets` explicitly depends on the stored `index`: [2](#0-1) 

By contrast, `next-index`/`total-assets-preview` (used everywhere else) accrue interest up to the current block: [3](#0-2) 

In `market.clar`/`v0-4-market.clar`, the bad-debt socialization flow calls `vault-socialize-debt` first, and only afterward calls `vault-accrue` to refresh the cached index — i.e., accrual happens *after* the write-down, not before: [4](#0-3) 

Because `socialize-debt` reduces `principal-scaled` before `accrue` runs, the subsequent `accrue` call computes `debt-delta`/`treasury-lp` off the *already-reduced* `principal-scaled`, so the reserve-fee interest that accrued on the written-off principal between `last-update` and the current block is never captured in the treasury LP mint (it is neither socialized as debt-reduction, which used the stale `idx`, nor accrued as treasury yield). Simultaneously, `lindex` (the value all depositor shares are priced against via `total-assets`) is written down using the stale `old-total-assets`, meaning the ratio applied to depositors' claims does not match the true value of vault assets at that block once the skipped interest is included later.

### Impact Explanation
This causes the accrued-but-uncollected reserve-fee interest (unclaimed protocol/treasury yield) spanning the gap between `last-update` and the block in which `socialize-debt` executes to be permanently lost from the treasury-LP mint calculation, and the depositor-facing `lindex` write-down ratio to be computed against a total-assets figure that omits currently-owed interest. This is a case of theft/permanent freezing of unclaimed yield (interest owed to the fee reserve/treasury), which falls under the in-scope High impact category ("theft of unclaimed yield or royalties, permanent freezing of unclaimed yield or royalties"). No principal deposits are placed at risk, but the miscalculated yield accounting is not "unprivileged principal attacker"-driven exploitation per se — the divergence occurs any time `socialize-debt` is invoked by governance/liquidation flow while time has elapsed since the last accrual, which happens on essentially every real socialization event given the two-week+ intervals typical for vault activity.

### Likelihood Explanation
`socialize-debt` is called during the liquidation/bad-debt write-off flow in `market.clar` whenever a liquidation leaves residual scaled debt that must be socialized across the vault's depositors. Since `accrue` is not called first, the mis-accounting occurs deterministically on every socialization event where `stacks-block-time` has advanced since `last-update` (i.e., in normal operating conditions, not merely a contrived edge case), so the likelihood of the bug being triggered is high whenever socialization actually occurs.

### Recommendation
Modify `socialize-debt` to call `(try! (accrue))` at the start (as all other state-mutating vault functions already do), so that `index`, `lindex`, and the treasury LP mint reflect interest accrued up to the current block before computing `debt-reduction` and the write-down `new-lindex`. Alternatively, in `market.clar`, invoke `vault-accrue` before `vault-socialize-debt` rather than after, ensuring accrual always precedes the balance mutation, consistent with the pattern used across `deposit`/`redeem`/`transfer`/`system-borrow`/`system-repay`/`flashloan`.

### Proof of Concept
1. At `T0`, a vault's `last-update` is set after some `accrue()` call; `index = idx0`, `lindex = L0`, `principal-scaled = P0`.
2. Time advances to `T1` without any accrual call (deposits/borrows may occur elsewhere but assume the vault under scrutiny is otherwise quiescent) — interest has economically accrued on `P0` but is not reflected in stored `index`.
3. A liquidation leaves a bad debt of `scaled-amount = S` on this vault. `market.clar`'s `socialize-debt-asset` calls `vault-socialize-debt` at `T1`: [1](#0-0) 
   `debt-reduction` and `old-total-assets` are both computed with the stale `idx0`, understating the true debt/assets at `T1`.
4. `principal-scaled` is reduced to `P0 - S_principal` and `lindex` is set to `new-lindex` based on the understated `old-total-assets`.
5. `market.clar` then calls `vault-accrue`, which computes `next-index` and `treasury-lp` using the *already-reduced* `principal-scaled`: [5](#0-4) 
   The interest that accrued on the `S_principal` portion between `T0` and `T1` (before it was written off) is never captured as `treasury-lp`, nor was it included in `debt-reduction` (which used stale `idx0`) — it is silently dropped from all accounting, permanently losing that slice of protocol/treasury yield and skewing the depositor `lindex` write-down ratio relative to what it should have been had accrual run first.

This root cause and impacted files were located and verified directly in-repo; I could not fully trace every downstream consumer of `lindex`/`total-assets-preview` across the full `market.clar` codebase within the available iterations, so the precise numeric magnitude of yield loss per socialization event is not quantified here and would need runtime simulation to bound.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))
