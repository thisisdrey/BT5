### Title
Network-wide resource pricing can be sandwiched via free freeze/unfreeze to grief or manipulate victims' energy/bandwidth limits - (File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceV2Actuator.java, actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java)

### Summary
Any account can call `FreezeBalanceV2Contract` to instantly increase the global `TotalEnergyWeight`/`TotalNetWeight` counters, then call `UnfreezeBalanceV2Contract` to instantly decrease them back, at essentially zero cost (both actuators have `calcFee() == 0`, and the frozen TRX is never spent — only the 14-day unstake period delays reclaiming the *principal*, not the weight bookkeeping). Any other account's resource entitlement (`EnergyProcessor.calculateGlobalEnergyLimit`, `BandwidthProcessor.calculateGlobalNetLimit`, and `RepositoryImpl.calculateGlobalEnergyLimit` used inside `VMActuator.getAccountEnergyLimitWithFloatRatio`) is computed as `accountFrozenBalance * totalLimit / totalWeight` at the exact moment their transaction executes, exactly mirroring the Kyber `Pool.burnRTokens` pattern where `deltaL` is derived from a shared, execution-time `totalSupply`.

### Finding Description
- `FreezeBalanceV2Actuator.execute` (lines 60-72) immediately calls `dynamicStore.addTotalEnergyWeight(...)`/`addTotalNetWeight(...)` when any account freezes TRX for ENERGY/BANDWIDTH. [1](#0-0) 
- `UnfreezeBalanceV2Actuator.updateTotalResourceWeight` immediately decrements the same global weight when unfreezing, while the actual balance return is deferred via `addUnfrozenV2List`/`calcUnfreezeExpireTime` (14-day `unfreezeDelayDays`), meaning the weight-dilution effect can be created and reverted within the same block without ever losing custody of the TRX. [2](#0-1) 
- Any account's usable energy limit derived from its own frozen balance is computed against this global, mutable denominator at read/execution time: [3](#0-2) 
- This same denominator also gates how much energy a caller can pull from `feeLimit` in `VMActuator.getAccountEnergyLimitWithFloatRatio`, which calls `rootRepository.calculateGlobalEnergyLimit(account)`. [4](#0-3) 
- The same pattern applies to bandwidth via `dynamicStore.getTotalNetWeight()`/`getTotalNetLimit()` in `BandwidthProcessor.calculateGlobalNetLimit`. [5](#0-4) 

Attack flow (analogous to the Kyber report's front-run mint / back-run burn):
1. Attacker observes a pending victim transaction (e.g. `TriggerSmartContract` or another `FreezeBalanceV2`/`DelegateResourceContract`) whose available energy/bandwidth depends on `TotalEnergyWeight`/`TotalNetWeight`.
2. Attacker front-runs with a large `FreezeBalanceV2Contract` (ENERGY or BANDWIDTH), instantly inflating the global weight and diluting the victim's proportional share of the fixed `TotalEnergyCurrentLimit`/`TotalNetLimit`.
3. The victim's transaction executes with less energy/bandwidth than it would have had without the front-run, potentially triggering an out-of-energy failure (fee still consumed) or forcing the victim to burn TRX balance for the shortfall.
4. Attacker back-runs with `UnfreezeBalanceV2Contract` for the same amount, immediately restoring `TotalEnergyWeight`/`TotalNetWeight` to its prior value — the attacker never actually loses the frozen TRX (only a 14-day illiquidity on funds they still fully control/vote with via `FreezeV2`), i.e. the attack is nearly free, matching the report's "costs zero tokens" characteristic.

### Impact Explanation
This lets an unprivileged, single-signer attacker manipulate a network-wide resource-pricing denominator read by other unrelated users' transactions within the same block, causing them to receive less energy/bandwidth than expected from their own frozen stake. Consequences include unexpected out-of-energy reverts (wasted transaction fees), forced consumption of TRX balance to cover the energy shortfall (`energyFromBalance` fallback in `VMActuator`), and unreliable resource accounting for contract callers/relayers that assume a stable `calculateGlobalEnergyLimit` result at submission time. This is a griefing/DoS-with-fund-loss primitive against arbitrary victims, reachable purely via broadcastable `FreezeBalanceV2Contract`/`UnfreezeBalanceV2Contract` transactions.

### Likelihood Explanation
Likelihood is limited by economic scale: to meaningfully move `TotalEnergyWeight`/`TotalNetWeight` (network-wide aggregates, typically very large), an attacker needs to freeze a correspondingly large amount of TRX, and the effect is proportional/dilutive rather than able to zero out a specific victim's share entirely. It also requires transaction ordering influence within the target block (front-running), which depends on the node/relay infrastructure java-tron uses (no explicit priority auction, but ordering by broadcast timing/fees is possible). This makes the attack technically feasible but requiring meaningful capital and timing precision, which is a materially different risk profile from the original Kyber report where a single sandwich directly stole LP value.

### Recommendation
Consider decoupling per-block resource-limit calculations from real-time freeze/unfreeze mutations of `TotalEnergyWeight`/`TotalNetWeight` — e.g., snapshot these totals once per block/maintenance cycle (similar to how `TotalEnergyCurrentLimit` is already only adjusted at maintenance boundaries) rather than allowing them to be mutated transaction-by-transaction and immediately consumed by other transactions in the same block. Alternatively, apply the unfreeze delay to the weight bookkeeping itself, not just to principal release, so that a freeze cannot be reversed until the same delay has elapsed.

### Proof of Concept
1. Attacker submits `FreezeBalanceV2Contract{resource: ENERGY, frozen_balance: LARGE_AMOUNT}` — `TotalEnergyWeight` increases immediately per `FreezeBalanceV2Actuator.execute` lines 67-71.
2. In the same block, victim's `TriggerSmartContract` executes; `getAccountEnergyLimitWithFloatRatio`/`EnergyProcessor.calculateGlobalEnergyLimit` computes a reduced energy allotment for the victim because `totalEnergyWeight` is now inflated, potentially causing an out-of-energy revert that still consumes the victim's paid fee.
3. Attacker submits `UnfreezeBalanceV2Contract{resource: ENERGY, unfreeze_balance: LARGE_AMOUNT}` — `UnfreezeBalanceV2Actuator.updateTotalResourceWeight` lines 285-289 immediately restores `TotalEnergyWeight` to its prior value; the attacker's TRX remains fully under their control (subject only to a 14-day unstake delay before withdrawal, not affecting their ability to have executed the sandwich).

Note: I was not able to fully verify within the available tool budget how transaction ordering/mempool prioritization works in java-tron (whether an attacker can reliably front-run/back-run within the same block via fee bidding or must rely on natural propagation timing), which affects the practical likelihood of this attack; a background Devin session with repo access could confirm ordering guarantees in the block-packing logic (`Manager`/`TransactionCapsule` processing order) if further precision is needed.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
