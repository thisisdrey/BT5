## Title
Out-of-bounds read / SEGV when ijar parses a malicious central directory in a downloaded jar/zip - (`third_party/ijar/zip.cc`)

### Summary
`ijar` (Bazel's interface-jar stripping tool, invoked whenever Bazel processes a `.jar` file, including third-party jars fetched via `http_jar`/`http_archive`/`http_file`/Maven rules) parses the ZIP central directory without any bounds checking on a per-entry basis. A crafted jar with a self-consistent overall length (so it passes the whole-file/central-directory-size sanity check) but bogus per-entry `file_name_length`/`extra_field_length`/`file_comment_length` fields can push the read cursor arbitrarily far past the end of the memory-mapped input file, causing an out-of-bounds read or SEGV, directly analogous to CVE-2024-0901 ("malformed packet with the correct length" causing OOB read/crash).

### Finding Description
`InputZipFile::Open` in [1](#0-0)  locates the central directory via `FindZipCentralDirectory`, which only validates that `cd.central_dir_offset + cd.central_dir_size <= in_length` — i.e., it validates the *overall* declared size of the central directory region against the file length [2](#0-1) .

However, iteration through individual entries in that central directory is done by `InputZipFile::ProcessCentralDirEntry`, which reads `compressed_size`, `uncompressed_size`, `file_name_length`, `extra_field_length`, `file_comment_length`, `attr`, and `offset` directly via `get_u4le`/`get_u2le` and then advances the cursor `p` by `file_name_length`, `extra_field_length`, and `file_comment_length` **without ever checking that these advances stay within the mapped buffer**: [3](#0-2) 

Notably, this function also `memcpy`s `file_name_length` bytes from `p` into a fixed `filename` buffer before validating that `p` still points into the mapped region: [4](#0-3) 

This is in stark contrast to the local-file-header parser, `InputZipFile::ProcessLocalFileEntry`, which calls `EnsureRemaining()` before every read/advance: [5](#0-4) 

The `EnsureRemaining` bounds-check helper exists in the class [6](#0-5)  but is never used in `ProcessCentralDirEntry`. The code comment claims "the central directory is always followed by another data structure that has a signature, so parsing it this way is safe" [7](#0-6) , but this assumption only holds for well-formed archives — a hostile archive can set oversized length fields to walk `p` far past the actual mapped file (a `mmap`'d region, per `MappedInputFile`), causing either garbage reads within the same/adjacent pages or a SIGSEGV when the mapping boundary is crossed.

`ProcessNext()` drives this loop repeatedly via `CalculateOutputLength()`/`ProcessAll()` [8](#0-7) [9](#0-8) , so the OOB pointer is dereferenced again on the very next iteration (`get_u4le(p)` for the next signature), compounding the read.

### Impact Explanation
An attacker who controls the content served at a jar/zip URL that a Bazel build depends on (e.g. a Maven artifact, `http_jar`, `http_archive`, or `http_file` target) can publish a malicious jar whose bytes match whatever `sha256`/`integrity` the victim declares (the attacker chooses both the content and, implicitly, its hash) — the checksum, therefore, is not a barrier to a malicious-but-self-consistent artifact. When Bazel invokes `ijar` to build an interface jar from this dependency (a routine step for `java_library`/`java_import` targets), the OOB pointer walk in `ProcessCentralDirEntry` can crash the build process (denial of service against the build machine) or leak adjacent process memory contents into the ijar's error output/behavior (out-of-bounds read).

### Likelihood Explanation
Any project consuming a third-party `.jar` dependency through Bazel's HTTP/registry-based repository rules is exposed. No special privileges or MITM access are needed; the attacker only needs control of the origin serving the jar (e.g., an open-source project or mirror the victim depends on). Because ijar is invoked automatically as part of ordinary Java build actions, exploitation requires no unusual build configuration.

### Recommendation
Add `EnsureRemaining()`-style bounds checks to `InputZipFile::ProcessCentralDirEntry` before every pointer read and before every `p +=` advance (including the extra-field sub-record loop), mirroring the guards already present in `ProcessLocalFileEntry`. Reject the entry with a proper error instead of continuing to dereference an unchecked pointer.

### Proof of Concept
Construct a minimal ZIP with:
1. One valid local file header + data.
2. A central directory entry whose `file_name_length` (or `extra_field_length`/`file_comment_length`) is set to a large value (e.g. `0xFFFF`) such that `p` advances past the end of the mapped file.
3. A valid End-Of-Central-Directory record positioned so that `cd.central_dir_offset + cd.central_dir_size <= in_length` still holds (satisfying `FindZipCentralDirectory`'s only check).

Running `ijar` (or any Bazel build step that invokes it, e.g. building a `java_import`/`java_library` target that depends on this jar) on this file triggers a read past the `mmap`'d region in `ProcessCentralDirEntry`, reproducible as a `BuildIntegrationTestCase`/`src/test/shell/bazel` test that fetches such a jar via `http_jar` and asserts the build does not crash with SIGSEGV.

```text
  u8 compressed, uncompressed;
```

```text
bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
```

```text
u8 InputZipFile::CalculateOutputLength() {
  const u1* current = central_dir_;

  u8 compressed_size = 0;
  u8 uncompressed_size = 0;
  u8 skipped_compressed_size = 0;
  u4 attr;
  u8 offset;
  char filename[PATH_MAX];

  while (true) {
    u8 file_compressed, file_uncompressed;
    if (!ProcessCentralDirEntry(current,
                                &file_compressed, &file_uncompressed,
                                filename, PATH_MAX, &attr, &offset)) {
      break;
    }

    if (processor->Accept(filename, attr)) {
      compressed_size += (u8) file_compressed;
      uncompressed_size += (u8) file_uncompressed;
    } else {
      skipped_compressed_size += file_compressed;
    }
  }

  // The worst case is when the output is simply the input uncompressed. The
  // metadata in the zip file will stay the same, so the file will grow by the
  // difference between the compressed and uncompressed sizes.
  return (u8) input_file_->Length() - skipped_compressed_size
      + (uncompressed_size - compressed_size);
}
```

```text
bool InputZipFile::Open() {
  MappedInputFile* input_file = new MappedInputFile(filename_);
  if (!input_file->Opened()) {
    snprintf(errmsg, sizeof(errmsg), "%s", input_file->Error());
    delete input_file;
    return false;
  }

  void *zipdata_in = input_file->Buffer();
  u8 central_dir_offset;
  const u1 *central_dir = NULL;

  if (!devtools_ijar::FindZipCentralDirectory(
          static_cast<const u1*>(zipdata_in), input_file->Length(),
          &central_dir_offset, &central_dir)) {
    errno = EIO;  // we don't really have a good error number
    error("Cannot find central directory");
    delete input_file;
    return false;
  }
  const u1 *zipdata_start = static_cast<const u1*>(zipdata_in);
  in_offset_ = - static_cast<off_t>(zipdata_start
                                    + central_dir_offset
                                    - central_dir);

  input_file_ = input_file;
  zipdata_in_ = zipdata_start;
  central_dir_ = central_dir;
  central_dir_current_ = central_dir;
  p = zipdata_in_ + in_offset_;
```
