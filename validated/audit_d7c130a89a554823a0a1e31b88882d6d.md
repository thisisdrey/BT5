Audit Report

## Title
Relayer reward paid on `submit_delivery_receipt` regardless of Ethereum dispatch outcome (`success` flag ignored) - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt` decoded from the Ethereum `InboundMessageDispatched` event carries a `success: bool` field indicating whether the message dispatch succeeded on Ethereum <cite repo="Loderfordw/polkadot-sdk--015" path="bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs" start="10-27" /> , but `Pallet::process_delivery_receipt` never inspects this field before paying the relayer reward and removing the `PendingOrder` [1](#0-0) . Any signed account can submit a valid receipt for a failed dispatch (`success: false`) via the public `submit_delivery_receipt` extrinsic and still collect the full relayer fee.

## Finding Description
The pallet's own doc-comment describes the intended flow: after "the message has been verified and executed," the relayer calls `submit_delivery_receipt` to fetch the pending order and pay the reward [2](#0-1) . The extrinsic verifies the Merkle/receipt proof via `T::Verifier::verify` and decodes the `DeliveryReceipt` from the log, then calls `process_delivery_receipt` [3](#0-2) . Inside `process_delivery_receipt`, the only checks performed are that `receipt.gateway` matches the configured gateway and that a `PendingOrder` exists for `receipt.nonce`; the function then unconditionally calls `T::RewardPayment::register_reward` whenever `order.fee > 0`, and removes the order [4](#0-3) . The decoded `receipt.success` field is never read in this function or anywhere else in the pallet — confirmed by an exhaustive search of the pallet source showing zero references to `success` outside the `DeliveryReceipt` struct definition. This means a `DeliveryReceipt` proving a failed Ethereum-side dispatch is treated identically to one proving success for payout purposes: proof validity and nonce presence are the only guards, not the semantic outcome of dispatch.

## Impact Explanation
Any account holding a valid proof of a genuine `InboundMessageDispatched` event with `success = false` can submit it through the permissionless, signed `submit_delivery_receipt` extrinsic and still receive the full relayer fee reserved when the message was queued via `do_process_message` [5](#0-4) . This is a payout-correctness defect: the pallet's settlement state (`PendingOrders` removal + `register_reward`) advances on a receipt whose decoded outcome explicitly signals failure, corrupting the intended "fee-for-successful-delivery" invariant and causing over-payment of `RewardPayment::register_reward` for dispatches that did not achieve their purpose. This matches the "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" pivot, and constitutes public underpriced/unbacked payout via a public entrypoint with no privileged actor required.

## Likelihood Explanation
High likelihood: `submit_delivery_receipt` is a plain signed extrinsic callable by any account [6](#0-5) , with no additional check tying reward eligibility to `receipt.success`. Any relayer whose dispatch fails on Ethereum (e.g., a reverted command, insufficient gas, or contract-side revert) can still submit that receipt and collect the reward — no admin, governance, or validator collusion is needed, and the exploit is directly reachable from attacker-controlled proof/message submission.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success` before calling `T::RewardPayment::register_reward`: only pay the fee when `success == true`; when `false`, settle/remove the `PendingOrder` without paying the reward (or route to a distinct failure-accounting path), so payout state advances only after execution is confirmed successful, matching the pallet's documented flow.

## Proof of Concept
1. A message is queued via `do_process_message`, inserting `PendingOrders::<T>::insert(nonce, PendingOrder { nonce, fee, block_number })` with `fee > 0` [7](#0-6) .
2. On Ethereum, the dispatch fails; the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer builds a valid receipt proof for this event and calls `submit_delivery_receipt` [3](#0-2) .
4. `T::Verifier::verify` succeeds (the event genuinely occurred), and `DeliveryReceipt::try_from` decodes `success: false` successfully [8](#0-7) .
5. `process_delivery_receipt` finds the `PendingOrder`, sees `order.fee > 0`, and calls `T::RewardPayment::register_reward` — paying the relayer despite `success == false` — then removes the order [9](#0-8) .

A unit test asserting `register_reward` is *not* invoked (or invoked with zero effect) when a mock `EventProof` decodes to `DeliveryReceipt { success: false, .. }` would reproduce this: currently no such assertion exists in the pallet's test suite, and the code path pays regardless of `success`.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
