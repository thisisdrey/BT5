Audit Report

## Title
Snowbridge relayer rewards are irrecoverably lost when the beneficiary cannot receive the asset on AssetHub, because reward accounting is settled on BridgeHub before remote XCM execution succeeds - ([File: bridges/modules/relayers/src/lib.rs], [File: bridges/snowbridge/primitives/core/src/reward.rs])

## Summary
`pallet-bridge-relayers::do_claim_rewards` deletes the relayer's accumulated reward entry and emits `RewardPaid` as soon as `T::PaymentProcedure::pay_reward` returns `Ok(())`. For Snowbridge, `pay_reward` (`PayAccountOnLocation::pay_reward`) only validates, charges delivery fees for, and hands the XCM off to `XcmSender::deliver` — it never confirms that the `DepositAsset` instruction actually succeeds on AssetHub, so a remote execution failure results in permanently trapped funds while BridgeHub's ledger already shows the reward as paid.

## Finding Description
`do_claim_rewards` in [1](#0-0)  uses `try_mutate_exists` to `take()` the stored reward, calls `T::PaymentProcedure::pay_reward(...)`, and treats any `Ok(())` result as final: it deletes the storage entry and emits `Event::RewardPaid`. The mutation is only rolled back if `pay_reward` itself returns `Err`.

For `BridgeReward::Snowbridge`, `pay_reward` resolves to `PayAccountOnLocation::pay_reward` in [2](#0-1) , which builds an XCM with `ReserveAssetDeposited` + `DepositAsset { assets: AllCounted(1).into(), beneficiary }`, calls `validate_send`, `XcmExecutor::charge_fees`, and `XcmSender::deliver(ticket)`. Once `deliver` succeeds, the function returns `Ok(())` — but successful delivery only means the message was accepted into the outbound queue; it says nothing about whether `DepositAsset` will actually succeed when the message executes on AssetHub.

Existing unit tests in the same file confirm that only synchronous failures (bad validation, fee-charging failure, delivery failure) are caught and preserved in the reward ledger — see `pay_reward_fails_on_xcm_validate_xcm`, `pay_reward_fails_on_charge_fees`, and `pay_reward_fails_on_delivery` at [3](#0-2) . There is no test or code path covering delivery-succeeds-but-remote-execution-fails, because no mechanism exists to detect or react to that case. If the beneficiary location cannot accept the deposited asset (e.g., insufficient existential deposit for a new foreign-asset account), the XCM executor traps the asset (`AssetsTrapped`) rather than causing the message to revert on BridgeHub, and BridgeHub has already deleted the reward record and reported success via `RewardPaid`.

This breaks the invariant that message/payout state should only advance after execution and settlement succeed atomically — settlement is committed on BridgeHub based purely on local delivery acceptance, not remote confirmation.

## Impact Explanation
A relayer's earned WETH reward can be permanently lost even under fully honest operation, whenever the AssetHub beneficiary location cannot successfully receive the deposited asset. BridgeHub's ledger reflects the reward as paid (`RewardPaid` emitted, entry removed), but the value never reaches a usable account and there is no direct-origin reclaim path since the trap-claim origin on AssetHub is the descended `InboundQueueLocation`/Ethereum universal origin, not one the relayer controls. This matches the "permanent user-fund lock" impact category for bridge reward accounting.

## Likelihood Explanation
The path is reachable via the public, unprivileged extrinsic `claim_rewards_to` at [4](#0-3)  with a `BridgeRewardBeneficiaries::AssetHubLocation` beneficiary. No governance, admin, or malicious-peer assumptions are required — only a beneficiary/asset state on AssetHub that causes `DepositAsset` to fail after message acceptance, which is a plausible operational condition (e.g., fresh account lacking ED for the WETH foreign asset).

## Recommendation
Do not treat successful XCM `deliver()` as final settlement for reward accounting. Options: (1) require confirmation of successful remote execution before clearing the reward ledger entry (e.g., an ack/receipt mechanism), (2) keep the reward re-claimable/restorable if a trap/failure signal is later observed rather than deleting it immediately, or (3) validate that the beneficiary location meets minimum-deposit/asset-sufficiency requirements before attempting settlement, rejecting the call if it cannot be proven to succeed.

## Proof of Concept
1. Relayer accrues a Snowbridge reward on BridgeHub via `register_reward`.
2. Relayer calls `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(beneficiary))` where `beneficiary` resolves to a fresh AccountId32 on AssetHub with a reward below the WETH foreign-asset sufficiency/ED requirement.
3. `PayAccountOnLocation::pay_reward` validates/charges fees/`deliver`s the XCM successfully and returns `Ok(())`.
4. `do_claim_rewards` commits: `RelayerRewards` entry removed, `RewardPaid` emitted on BridgeHub, as demonstrated by the passing flow in the integration test `claim_rewards_works` (`cumulus/parachains/integration-tests/emulated/tests/bridges/bridge-hub-westend/src/tests/snowbridge_v2_rewards.rs`).
5. On AssetHub, `DepositAsset` fails because the beneficiary cannot receive/hold the asset; the asset is trapped (`AssetsTrapped`) instead of the message failing outright.
6. Result: BridgeHub's ledger shows the reward as paid; the relayer never receives usable funds and has no direct-origin path to reclaim the trapped value.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
