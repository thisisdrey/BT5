## Analysis

The Algebra bug reduces to: **a pool's price/reserve state can be set for free by an unprivileged actor before the intended first liquidity provider acts, because the code treats "raw token balance held by the pool address" as authoritative reserve/price data with no invariant tying it to actual LP-token-backed liquidity.**

The direct analog in this repo is `pallet-asset-conversion`, the in-runtime constant-product AMM used on Asset Hub.

### The corrupted value

In `do_add_liquidity` (`substrate/frame/asset-conversion/src/lib.rs`), the "reserves" used to price a deposit are read directly from the pool account's live token balance, not from any liquidity-tracked storage: [1](#0-0) 

`reserve1`/`reserve2` come from `Self::get_balance(&pool_account, asset)` — i.e. whatever tokens currently sit at the deterministic `pool_account` address. That address is computed off-chain by `T::PoolLocator::address(&pool_id)` and is public and permissionless to send tokens to (a plain `Assets::transfer`/`Balances::transfer_allow_death`, no pallet call required).

`Pools::<T>::insert` in `do_create_pool` never seeds or checks reserves — the pool is "created" with an empty `PoolInfo { lp_token }`, exactly analogous to Algebra's pool being deployed without `initialize()` being called: [2](#0-1) 

### The exploitable branch

When `total_supply == 0` (no LP tokens minted yet, i.e. "actual liquidity zero," matching the report's precondition) but an attacker has *directly donated* nonzero amounts of both `asset1` and `asset2` to `pool_account` (not via `add_liquidity`, so no LP tokens were minted to the attacker), `reserve1` and `reserve2` are both nonzero. This makes `do_add_liquidity` skip the "first deposit, take amounts as-is" branch and instead execute the `quote()`-based branch, using the **attacker-chosen donation ratio** as the exchange rate the legitimate first LP is priced against: [3](#0-2) 

This is the exact structural equivalent of Algebra's unguarded price-setting: a party with no legitimate liquidity position dictates the price a real liquidity provider transacts at, at effectively zero cost (the donated dust is not reclaimed as LP shares since `calc_lp_amount_for_zero_supply` mints based on the *current* transaction's `amount1`/`amount2`, not the pre-existing dust).

The pallet's own test suite acknowledges a version of this griefing surface (`add_tiny_liquidity_directly_to_pool_address`, `cannot_block_pool_creation`), but those tests only cover a single-asset donation (which keeps one reserve at zero and thus stays on the "take as-is" branch) and never test the **two-asset donation with an attacker-controlled ratio**, which is the case that actually forces the `quote()` branch and manipulates price: [4](#0-3) [5](#0-4) 

Existing guards (`AssetTwoDepositDidNotMeetMinimum`, `AssetOneDepositDidNotMeetMinimum`, `AmountOneLessThanMinimal`/`AmountTwoLessThanMinimal`) only bound the deposit against the caller's own `amount_min` parameters — they do nothing to validate that `reserve1`/`reserve2` reflect genuine, LP-token-backed liquidity rather than attacker-donated balance. A caller who doesn't set tight enough `amount1_min`/`amount2_min` (or who reasonably assumes a freshly created, un-liquidated pool has no meaningful "market rate" to slip against) can be forced into depositing at an arbitrary ratio, exactly mirroring the LP loss scenario described in the Algebra report.

### Caveat

This does require the attacker to act on the pool address before the legitimate first `add_liquidity` succeeds (the pool being newly created and reserve-less is itself the window), which is structurally the same "no initialize() called → permissionless price-setting" primitive as the source report, not a generic "front-run a specific victim's already-broadcast transaction" MEV scenario — the attacker doesn't need to see or race any particular pending transaction; they only need to donate to a deterministic, publicly known address at any point after `create_pool` and before liquidity is added, which can be done proactively for any newly created pool.

### Recommendation (conceptual, not implemented here)

`do_add_liquidity` should not treat raw pool-account token balance as trusted reserve data when `total_supply(lp_token) == 0`. The "first deposit" branch should be gated on `total_supply.is_zero()` (as `setup_pool_from_genesis` already effectively assumes) rather than on `reserve1.is_zero() || reserve2.is_zero()`, and/or excess/untracked balance in the pool account should be swept or excluded from the quoted ratio until it has been properly attributed to minted LP shares. [6](#0-5)

#[test]
fn cannot_block_pool_creation() {
	new_test_ext().execute_with(|| {
		// User 1 is the pool creator
		let user = 1;
		// User 2 is the attacker
		let attacker = 2;

		let ed = get_native_ed();
		assert_ok!(Balances::force_set_balance(RuntimeOrigin::root(), attacker, 10000 + ed));

		// The target pool the user wants to create is Native <=> WithId(2)
		let token_1 = NativeOrWithId::Native;
		let token_2 = NativeOrWithId::WithId(2);

		// Attacker computes the still non-existing pool account for the target pair
		let pool_account =
			<Test as Config>::PoolLocator::address(&(token_1.clone(), token_2.clone())).unwrap();
		// And transfers the ED to that pool account
		assert_ok!(Balances::transfer_allow_death(
			RuntimeOrigin::signed(attacker),
			pool_account,
			ed
		));
		// Then, the attacker creates 14 tokens and sends one of each to the pool account
		for i in 10..25 {
			create_tokens(attacker, vec![NativeOrWithId::WithId(i)]);
			assert_ok!(Assets::mint(RuntimeOrigin::signed(attacker), i, attacker, 1000));
			assert_ok!(Assets::transfer(RuntimeOrigin::signed(attacker), i, pool_account, 1));
		}

		// User can still create the pool
		create_tokens(user, vec![token_2.clone()]);
		assert_ok!(AssetConversion::create_pool(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone())
		));

		// User has to transfer one WithId(2) token to the pool account (otherwise add_liquidity
		// will fail with `AssetTwoDepositDidNotMeetMinimum`)
		assert_ok!(Balances::force_set_balance(RuntimeOrigin::root(), user, 10000 + ed));
		assert_ok!(Assets::mint(RuntimeOrigin::signed(user), 2, user, 10000));
		assert_ok!(Assets::transfer(RuntimeOrigin::signed(user), 2, pool_account, 1));

		// add_liquidity shouldn't fail because of the number of consumers
		assert_ok!(AssetConversion::add_liquidity(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone()),
			10000,
			100,
			10000,
			10,
			user,
		));
	});
}
