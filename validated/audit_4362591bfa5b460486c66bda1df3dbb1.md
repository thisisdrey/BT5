### Title
Witness/voter rewards accrued during a zero-total-vote cycle are permanently lost instead of rolled over - (File: `chainbase/src/main/java/org/tron/core/store/DelegationStore.java`)

### Summary
The DPoS reward-per-share ("Vi", value-per-share) accumulation logic used to distribute voter rewards drops any reward that is credited to a super representative (SR) during a maintenance cycle in which the SR's total vote count is `0`. Unlike a proper reward-per-share scheme, the un-distributable reward for that cycle is neither carried forward nor merged into the reward pool of a later cycle when votes exist again — it is simply discarded, permanently freezing that portion of the block/standby/transaction-fee reward.

### Finding Description
Block rewards, transaction-fee rewards and standby-witness rewards are booked per-cycle via `MortgageService.payReward()`, which calls `delegationStore.addReward(cycle, witnessAddress, value)` [1](#0-0) . Critically, `payBlockReward()` is invoked unconditionally for the block-producing witness on every single block regardless of that witness's current vote total [2](#0-1) .

At each maintenance cycle, `MaintenanceManager.doMaintenance()` converts the per-cycle reward pool into a reward-per-share value ("Vi") by calling `delegationStore.accumulateWitnessVi(curCycle, witness, witness.getVoteCount())` for every witness [3](#0-2) .

The accumulation logic is:
```
public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      ...
    } else { // Accumulate delta vi
      ...
    }
}
``` [4](#0-3) 

When `voteCount == 0` for the cycle (i.e., every voter who had voted for that SR has withdrawn/unfrozen their votes while the SR remains active and keeps producing blocks between elections), the branch simply forwards the previous cycle's `Vi` unchanged — the `reward` value fetched via `getReward(cycle, address)` for that specific cycle is never incorporated into `Vi` and is never revisited afterward. `RewardViCalService.accumulateWitnessVi()` implements the same discard behavior for the historical batch-recalculation path [5](#0-4) .

Since voter reward withdrawal (`MortgageService.withdrawReward` / `VoteRewardUtil.withdrawReward`) only ever reads `Vi` deltas to compute payouts [6](#0-5) , and the brokerage portion of the reward was already paid to the SR at `payReward()` time, the residual (non-brokerage) reward accrued in a zero-vote cycle is credited to no one: not the SR, not any voter, and it is never merged into a subsequent cycle's reward pool the way the reported StakingRewards.sol bug describes for `notifyRewardAmount`.

### Impact Explanation
This results in permanent freezing/loss of protocol reward funds: TRX that was reserved from the block/transaction-fee reward budget for voter distribution becomes permanently unclaimable once a witness's vote total transitions through zero during an active reward cycle. This can happen without any special privilege — any set of ordinary token holders unfreezing/withdrawing their votes from a given witness (a normal, unprivileged account operation) can trigger a zero-vote cycle for that witness while it is still producing blocks, causing that cycle's reward to be silently dropped from the `Vi` accounting forever.

### Likelihood Explanation
Vote totals for an SR dropping to exactly zero mid-cycle while it continues to produce blocks is an edge case, but it is fully reachable through routine unprivileged operations (mass unvoting/unfreezing) with no attacker cooperation required from the SR itself, and it is more likely for lower-ranked active witnesses or witnesses right after replacing/losing most of their support. The condition requires no malicious insider, no consensus manipulation, and no special permission — only ordinary `VoteWitnessContract`/`UnfreezeBalanceContract` transactions from independent accounts.

### Recommendation
When `voteCount == 0` in `accumulateWitnessVi`, do not silently drop the fetched `reward`; instead carry it forward (e.g., accumulate it into the reward store entry for the next cycle via `addReward(cycle + 1, address, reward)`) so it is included once the SR again has non-zero votes, mirroring the recommended `(block.timestamp - startTime) * rewardRate` roll-forward fix in the referenced report. Apply the same fix consistently in both `DelegationStore.accumulateWitnessVi` and `RewardViCalService.accumulateWitnessVi`.

### Proof of Concept
1. SR `W` is active and producing blocks; at some point all accounts holding votes for `W` submit `UnfreezeBalanceContract`/vote-clearing transactions, driving `W.getVoteCount()` to `0`.
2. `W` continues to produce blocks during the current cycle; each block triggers `Manager.payReward()` → `MortgageService.payBlockReward()` → `delegationStore.addReward(cycle, W, value)`, accumulating a non-zero `reward` for `cycle` at `DelegationStore` [7](#0-6) .
3. At the next maintenance cycle boundary, `MaintenanceManager.doMaintenance()` calls `accumulateWitnessVi(cycle, W, 0)` because `W.getVoteCount()` is `0` at that point [3](#0-2) .
4. Inside `accumulateWitnessVi`, since `voteCount == 0`, the branch forwards `preVi` unchanged and the previously-added `reward` for `cycle` is never folded into `Vi` [4](#0-3) .
5. Even if voters later re-vote for `W` in a subsequent cycle, `computeReward`/`withdrawReward` only compute rewards from `Vi` deltas between `beginCycle` and `endCycle` [8](#0-7) ; the reward stored for the zero-vote cycle is never referenced again and is permanently unattributed/frozen.

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
