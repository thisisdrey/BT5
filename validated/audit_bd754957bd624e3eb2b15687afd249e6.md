### Title
Active-permission signer can be granted (and then exploit) the right to execute `AccountPermissionUpdateContract`, enabling full account takeover — ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
`AccountPermissionUpdateActuator.checkPermission()` validates the operations bitmap of a custom `Active` permission against `DynamicPropertiesStore.getAvailableContractType()` — the full set of *all* contract types the chain supports — instead of the restricted set that intentionally excludes account-administration contract types. As a result, an `Active` permission (a low-trust, delegated signer slot) can be configured to include the bit for `AccountPermissionUpdateContract` itself, which is the contract that rewrites Owner/Witness/Active permissions. Any holder of that Active key can then unilaterally overwrite the account's Owner permission and lock out or replace the true owner.

### Finding Description
When TRON's multi-sig model is used, an account's `Owner` permission is supposed to be the only permission capable of altering the account's own permission structure (`AccountPermissionUpdateContract`). The system enforces this intent when it builds the *default* Active permission: `AccountCapsule.createDefaultActivePermission()` seeds the active operations bitmap from `DynamicPropertiesStore.getActiveDefaultOperations()`, whose default value explicitly excludes `AccountPermissionUpdateContract`, `ClearABIContract`, and `UpdateBrokerageContract` bits (confirmed by the test `checkActiveDefaultOperationsCorrespondingToCode` at `framework/src/test/java/org/tron/core/actuator/AccountPermissionUpdateActuatorTest.java:951-977`, which explicitly skips those three contract types).

However, when a user submits a *custom* `Active` permission via `AccountPermissionUpdateContract` (i.e., changing/adding an active key's allowed operations), the actuator's own validation does not enforce that same exclusion: [1](#0-0) 

This loop only checks that each set bit corresponds to a contract type present in `getAvailableContractType()` — which, per the test `checkAvailableContractTypeCorrespondingToCode` (same test file, lines 919-948), *does* include `AccountPermissionUpdateContract`. Nothing else in the signature/permission-check pipeline special-cases `AccountPermissionUpdateContract` to require Owner-only execution: [2](#0-1) [3](#0-2) 

Both `checkPermission` (used when co-signing via `addSign`) and `checkPermissionOperations` (used in `TransactionUtil`/`WalletUtil`, reused by `Wallet.broadcastTransaction`/`getTransactionSignWeight`/`getTransactionApprovedList`) only verify that the signing permission is of type `Active` and that its operations bitmap has the bit for the contract type being executed — they never forbid the `AccountPermissionUpdateContract` bit specifically. So once an account's Owner (intentionally, by mistake, or via a compromised/malicious co-owner) creates or updates an `Active` permission whose operations include the `AccountPermissionUpdateContract` bit, any signer in that Active permission with enough weight to meet that permission's (potentially very low) threshold can subsequently broadcast a new `AccountPermissionUpdateContract` that overwrites the Owner permission entirely — removing the original owner key and inserting attacker-controlled keys.

### Impact Explanation
This breaks the fundamental privilege hierarchy of TRON's permission model: an `Active` permission is meant to be a restricted, delegated signer (e.g., only allowed to send transfers or vote), strictly subordinate to `Owner`. Because the actuator fails to explicitly and permanently forbid `AccountPermissionUpdateContract` (and similarly `ClearABIContract`/`UpdateBrokerageContract`) from being included in a custom Active permission's operations, an Active signer can escalate to full Owner-equivalent control. This directly enables:
- Permanent account takeover / lockout of the legitimate owner (permanent freezing of funds from the true owner's perspective).
- Theft of funds, since the attacker (as new Owner) can subsequently move all balances/assets/frozen stake controlled by the account.

This maps to the same bug class as CVE-2016-0767 (PL/Java): a principal holding a lesser privilege level (`USAGE`/`Active`) is able to perform an administrative action (altering the schema classpath/altering account permissions) that should be restricted to a higher privilege (`Owner`), because the enforcement point validates against too permissive a set.

### Likelihood Explanation
Exploitation requires that some account's Owner grant an Active permission the `AccountPermissionUpdateContract` operation bit — this is not blocked by validation and is not obviously flagged as dangerous to a wallet operator/UI, since the actuator happily accepts it (only the "default" auto-generated Active permission excludes it; hand-crafted ones do not). This is plausible in multi-sig setups (exchanges, custodians, DAOs) where operators grant broad "convenience" bitmaps to co-signers, or where a malicious co-owner intentionally sets this up during account configuration to later betray other co-signers. The actual takeover step is trivial once such a permission exists: just broadcast a signed `AccountPermissionUpdateContract` from any Active key meeting the threshold.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()`, explicitly reject setting the operations bit for `AccountPermissionUpdateContract` (and ideally `ClearABIContract`/`UpdateBrokerageContract`) on any `Active` permission, mirroring the exclusion already applied in `getActiveDefaultOperations()`. Additionally, enforce at the `TransactionCapsule`/`TransactionUtil`/`WalletUtil` `checkPermission`/`checkPermissionOperations` level that `AccountPermissionUpdateContract` can only ever be authorized via `permissionId == 0` (Owner), regardless of what an Active permission's operations bitmap contains, so a stray or maliciously-crafted bitmap cannot resurrect this escalation path.

### Proof of Concept
1. Owner of account `A` submits `AccountPermissionUpdateContract` creating an `Active` permission `P` with `threshold = 1`, one key `K` (weight 1), and `operations` bitmap with the bit for `AccountPermissionUpdateContract` set — this passes `AccountPermissionUpdateActuator.validate()`/`checkPermission()` because that contract type is present in `getAvailableContractType()`.
2. Holder of private key `K` crafts a new `AccountPermissionUpdateContract` for account `A`, sets `permission_id = P`'s id in the contract, and defines a new Owner permission containing only attacker-controlled keys.
3. Signs with `K` and broadcasts. `TransactionCapsule.checkPermission`/`WalletUtil.checkPermissionOperations` allow it because permission `P` is `Active` type and its operations bit for `AccountPermissionUpdateContract` is set; `checkWeight` succeeds since `K`'s weight (1) meets `P`'s threshold (1).
4. `AccountPermissionUpdateActuator.execute()` overwrites account `A`'s Owner permission with the attacker's keys, completing takeover.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException("operations size must be 32");
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
