### Title
`FetchRemote` can leave the reference-transaction lock held after `req.Timeout` expires during quarantine migration, blocking future pushes/fetches to the repository - ([File: internal/gitaly/service/repository/fetch_remote.go])

### Summary
`FetchRemote` splits a single user-controlled timeout budget (`req.GetTimeout()`) between the expensive `git-fetch(1)` dry-run and a subsequent multi-step commit sequence (`prunedUpdater.Prepare/Commit`, `refUpdater.Prepare`, `quarantineDir.Migrate`, `refUpdater.Commit`) that all run under the *same* context. This is structurally analogous to the LayerZero bug: a single resource budget (gas in the original report, the RPC deadline here) is consumed almost entirely by the "main" operation, leaving too little of that same budget for the "cleanup/finalization" step that must run afterward to leave the system in a consistent, unlocked state.

### Finding Description
`FetchRemote` derives its context from a caller-supplied timeout: [1](#0-0) 

That single `ctx` is then used for the entire multi-phase atomic-fetch sequence: the (potentially very large/slow) `git-fetch(1)` dry-run, followed by `prunedUpdater.Prepare()`/`Commit()`, `refUpdater.Prepare()`, `quarantineDir.Migrate(ctx)`, and finally `refUpdater.Commit()`: [2](#0-1) 

`refUpdater.Prepare()` locks the target references before Git considers the transaction ready to commit. If an ordinary, unprivileged caller of `FetchRemote` (any client that can invoke a mirror/fetch RPC with a `remote_params` pointing at a large or slow remote, or simply supplying a very small `timeout` value relative to the amount of data to fetch) causes the fetch phase to consume nearly the entire timeout budget, the remaining budget available for `quarantineDir.Migrate(ctx)` — which walks and moves potentially many pack/loose-object files — can be exhausted by the same deadline. When `ctx` expires mid-`Migrate`, `Migrate` returns an error and the function bails out via `return false, false, fmt.Errorf("migrating quarantined objects: %w", err)`, without ever calling `refUpdater.Commit()`.

The `refUpdater.Close()` deferred call is still expected to release the reference lock: [3](#0-2) . However, because `Close()` itself is invoked with a context that has already expired (the same `ctx` derived from the original timeout is used throughout — there is no independent, always-available context for unlock/cleanup, unlike the pattern used elsewhere in the codebase, e.g. `RepoReferenceWriteLockManager.unlock` which explicitly uses `context.Background()` with its own short timeout specifically to guarantee lock release regardless of the caller's context state: [4](#0-3) ), a Git process spawned to release the reference lock (`git-update-ref` in cancel mode) can itself fail or be killed due to the expired deadline, leaving the `.lock` files behind in `refs/`.

This mirrors the reported bug class precisely: the "main" operation (fetch) and the "recovery/cleanup" operation (migrate + lock release) share one resource budget (deadline instead of gas), and exhausting it during the main operation starves the cleanup path, producing a stuck/blocked state rather than a clean failure.

### Impact Explanation
If the reference lock is not released, subsequent `git-receive-pack`/`git-update-ref` operations on the same repository will fail to acquire the lock, effectively blocking pushes and further fetches to that repository until the stale `.lock` files are detected and removed by Gitaly's stale-lock housekeeping sweep (`FindStaleReferenceLocks`, gated by a grace period): [5](#0-4) . This is a availability/DoS impact on a specific repository's write path, reachable by any client permitted to call `FetchRemote` (a normal mirror/fetch operation, not a privileged administrative action).

### Likelihood Explanation
Medium. It requires the attacker to control (or cause) a `FetchRemote` call whose `timeout` value is tight relative to the volume of objects/refs being fetched (e.g., a large mirror update with a short configured timeout, or a deliberately slow/large remote), so that the fetch step consumes nearly all of the deadline before quarantine migration begins. This is a normal, unprivileged RPC path (no admin/DAO-owner-style privilege required), but it depends on timing/configuration (timeout value vs. data size), which is more probabilistic than a guaranteed trigger.

### Recommendation
Give the migration/lock-release/finalization phase of `fetchRemoteAtomic` its own independent context (e.g. `context.WithTimeout(context.Background(), fixedGracePeriod)`) instead of reusing the caller-supplied, already-nearly-expired `ctx`, similar to the pattern used in `RepoReferenceWriteLockManager.unlock`. At minimum, `quarantineDir.Migrate` and the deferred `refUpdater.Close()`/`prunedUpdater.Close()` calls should run with a context that is guaranteed to have enough remaining time to complete cleanup even if the primary fetch has consumed the original deadline, so an update-lock is never left behind.

### Proof of Concept
1. Configure a Gitaly repository and issue `FetchRemote` with a `remote_params.url` pointing at a remote with a very large number of refs/objects, and set `timeout` to a small value that is just barely enough for `git-fetch --dry-run` to complete but leaves almost no slack.
2. `git-fetch` dry-run consumes nearly the whole timeout window; `refUpdater.Prepare()` succeeds and locks the affected references.
3. `ctx` expires while `quarantineDir.Migrate(ctx)` is walking/copying the (large) quarantined object tree, causing `Migrate` to return an error and the function to return early without calling `refUpdater.Commit()`.
4. The deferred `refUpdater.Close()` runs with the already-expired `ctx`, so the underlying `git-update-ref` cancel-and-unlock invocation can itself fail/be killed, leaving `refs/heads/*.lock` files in place.
5. Verify subsequent pushes/fetches to the same repository fail until the stale-lock grace period elapses and housekeeping removes the lock files.

Note: I could not directly inspect `internal/git/updateref/updateref.go`'s `Close()` implementation (its content wasn't returned by search) to confirm whether it independently re-derives its own context for the underlying unlock/cancel Git invocation; this is the one point of uncertainty in the chain and would need to be confirmed by reading that file directly.

// FindStaleReferenceLocks provides a function which scans the refdb for stale locks
// and loose references against the provided grace period.
func FindStaleReferenceLocks(gracePeriod time.Duration) FindStaleFileFunc {
	return func(_ context.Context, repoPath string) ([]string, error) {
		var staleReferenceLocks []string

		if err := filepath.WalkDir(filepath.Join(repoPath, "refs"), func(path string, dirEntry fs.DirEntry, err error) error {
			if err != nil {
				if errors.Is(err, fs.ErrNotExist) || errors.Is(err, fs.ErrPermission) {
					return nil
				}

				return err
			}

			if dirEntry.IsDir() {
				return nil
			}

			if !strings.HasSuffix(dirEntry.Name(), ".lock") {
				return nil
			}

			fi, err := dirEntry.Info()
			if err != nil {
				if errors.Is(err, fs.ErrNotExist) {
					return nil
				}

				return fmt.Errorf("statting reference lock: %w", err)
			}

			if time.Since(fi.ModTime()) < gracePeriod {
				return nil
			}

			staleReferenceLocks = append(staleReferenceLocks, path)
			return nil
		}); err != nil {
			return nil, fmt.Errorf("walking refs: %w", err)
		}

		return staleReferenceLocks, nil
	}
}
