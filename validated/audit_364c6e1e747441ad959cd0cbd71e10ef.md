Based on my research, Go's standard library `encoding/xml` package does not implement DTD processing or external entity resolution at all, which is fundamentally different from the `untangle` XXE vulnerability pattern.

Looking at the decoder internals:
- `<!DOCTYPE ...>` and `<!ENTITY ...>` declarations are parsed only as opaque `Directive` tokens — the raw bytes are accumulated and returned as-is, without any semantic interpretation of `SYSTEM`/`PUBLIC` identifiers or entity expansion [1](#0-0) .
- Character/entity references (`&name;`) are resolved only through a hardcoded map of the five standard XML entities (`lt`, `gt`, `amp`, `apos`, `quot`) or through the caller-supplied `Decoder.Entity` map of string replacements — there is no mechanism to fetch content from a file path or URL [2](#0-1) [3](#0-2) .
- The `Decoder.Entity` field documentation confirms it only maps "non-standard entity names to string replacements" supplied directly by the program, not external resources [4](#0-3) .
- Test cases explicitly confirm `<!ENTITY rdf "http://...">` inside a `DOCTYPE` directive is preserved verbatim as text and never dereferenced [5](#0-4) .

Since there is no code path in `encoding/xml` that ever opens a file, socket, or URL in response to a `SYSTEM`/`PUBLIC` entity declaration, the XXE primitive from the `untangle` advisory (which relies on `xml.sax`/`libxml2`-style DTD resolution) has no analogous reachable sink in this codebase. This is intentional, long-standing Go design, not a missed fix.
