### Title
Attacker can permanently block a victim from adding new collateral/debt positions by force-filling their `MAX_TOKENS_PER_USER` slots via `deposit(amount_, onBehalfOf_)` - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`DepositToken.deposit` mints msdTOKEN to an arbitrary `onBehalfOf_` address with no opt-in or consent check, and `DepositToken._transfer` does the same for any recipient. Every first-time credit calls `Pool.addToDepositTokensOfAccount`, which reverts with `UserReachedMaxTokens` once the victim's combined deposit-token + debt-token count reaches `MAX_TOKENS_PER_USER`. An unprivileged attacker can dust-fill a victim's slots for near-zero cost, after which any operation that would add a new token to the victim's list reverts — a validation failure reachable before any health/solvency checks, analogous to the Squid CVE's "crafted input causes DoS before normal security checks".

### Finding Description
- `DepositToken.deposit(amount_, onBehalfOf_)` only validates `amount_ > 0` and `onBehalfOf_ != 0`; the beneficiary is fully attacker-chosen. [1](#0-0) 
- `_mint` credits `account_` and, when the prior balance is zero, calls `pool.addToDepositTokensOfAccount(account_)`. [2](#0-1) 
- `_transfer` does the same on behalf of any `recipient_`, so plain `transfer`/`transferFrom`/`seize` also add to the recipient's list. [3](#0-2) 
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` are gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER`. [4](#0-3) [5](#0-4) 
- Slots are only freed when a balance returns exactly to zero (`_burn`/sender-side removal). [6](#0-5) 

Attack path (all unprivileged): attacker calls `deposit(1 wei, victim)` on every registered `DepositToken` until the victim's `depositTokensOfAccount + debtTokensOfAccount` length hits `MAX_TOKENS_PER_USER`. There is no check anywhere that the recipient consented to occupy a slot.

### Impact Explanation
Once saturated, every code path that would add a new token to the victim reverts with `UserReachedMaxTokens`:
- `deposit` into any collateral type the victim doesn't already hold — the victim is permanently unable to open new collateral positions or new borrows (`DebtToken._mint` similarly calls `addToDebtTokensOfAccount`). [7](#0-6) 
- All inbound `transfer`/`transferFrom` of msdTOKEN types the victim doesn't hold revert.
- `DepositToken.seize` during `Pool.liquidate` reverts if the seized token type would be new for the liquidator — combined with the debt-token side, a saturated victim's positions become harder to liquidate.

The victim can only recover by fully zeroing a balance to free a slot; if they hold no positions at all yet are dust-filled, they cannot free slots themselves at all — the block is effectively permanent for new positions. This is a freezing/griefing DoS driven purely by incorrect input validation (unrestricted `onBehalfOf_`/recipient).

### Likelihood Explanation
- Fully permissionless: `deposit` is `whenNotPaused`, no role required, reachable directly or via `Operator.execute`. [8](#0-7) 
- Cost is only dust amounts of each underlying plus gas; no flash loan, oracle, or privileged actor needed.
- Caveat: effectiveness depends on the deployed `MAX_TOKENS_PER_USER` value and the number of registered deposit tokens (attacker can only fill slots up to the number of listed tokens, and cannot fill debt-token slots since `DebtToken` is non-transferable and `issue`/`mint` mint debt to `_msgSender`). If registered deposit tokens < `MAX_TOKENS_PER_USER`, the attacker alone cannot fully saturate the list — though they can still consume most of it, and combine with the victim's own positions. I did not confirm the constant's value or the deployed token count within this scan, so the permanent-freeze claim is strongest when registered collaterals ≥ `MAX_TOKENS_PER_USER`.

### Recommendation
- Do not add tokens to an account's list on `deposit(..., onBehalfOf_)`/incoming `transfer` without the recipient's control; alternatively make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` non-reverting on cap (silently skip tracking) — the per-account lists are only used for health iteration, so skipping an untracked token must be paired with iterating global token lists instead, or
- Restrict `onBehalfOf_ == msg.sender` for deposit (breaking the griefing vector), or
- Cap the griefing by requiring a minimum deposit amount and charging it to the beneficiary model (opt-in whitelist), and let any account trigger `removeFrom*` for tokens it doesn't hold.

### Proof of Concept
Hardhat sketch against a live deployment fork (pool with ≥ `MAX_TOKENS_PER_USER` registered deposit tokens):

```ts
// attacker = any EOA; victim = fresh EOA with no positions
for (const dt of depositTokens) {
  const underlying = await ethers.getContractAt('IERC20', await dt.underlying());
  await deal(underlying, attacker, 1n);          // dust
  await underlying.connect(attacker).approve(dt.address, 1n);
  await dt.connect(attacker).deposit(1n, victim.address); // fills victim's list
}
// victim's depositTokensOfAccount.length == MAX_TOKENS_PER_USER (combined with debt list)
// Any new-token operation for victim now reverts:
await expect(newDepositToken.connect(victim).deposit(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(msdToken.connect(holder).transfer(victim.address, 1n))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
// victim cannot free slots — they hold only dust balances they didn't choose;
// even fully withdrawing those still leaves them griefer-chosen set membership gone,
// but the victim must spend gas exiting positions they never opened.
```

Note: exact reproducibility depends on the deployed `MAX_TOKENS_PER_USER` (in `PoolStorage`) and the number of registered deposit/debt tokens on the target chain, which I could not fully verify in this pass; the revert path itself is deterministic from the cited code.
