### Title
Unbounded ref advertisement walk lets a pusher DoS every subsequent fetch/push - (File: `internal/gitaly/service/smarthttp/inforefs.go`)

### Summary
The external report describes a DoS pattern: an unprivileged actor (calling `incrementWindow()`) repeatedly grows an ever-increasing collection (`currentWindow`), and any subsequent call to a function that unconditionally iterates the *entire* collection (`claimForAllWindows()`) becomes prohibitively expensive and eventually unusable, with no server-side mechanism to bound or paginate the work. The same structural bug class exists in Gitaly's smart-HTTP ref advertisement path.

### Finding Description
`InfoRefsUploadPack` and `InfoRefsReceivePack` in `internal/gitaly/service/smarthttp/inforefs.go` invoke `handleInfoRefs`, which runs `git-upload-pack`/`git-receive-pack --stateless-rpc --advertise-refs` against the full repository with no ref-count limit, pattern filter, or pagination: [1](#0-0) 

This is exactly analogous to the `for (uint256 i = 0; i < currentWindow; i++)` loop in `claimForAllWindows()`: the amount of work is proportional to an attacker-growable collection (here, the total number of refs in the repository), and there is no way to request a subset.

The growable collection — the repository's reference set — can be inflated without bound by any user who can push, via `UpdateReferences`, which accepts an unbounded stream of ref-update batches with no limit on the number of updates per call or per repository: [2](#0-1) 

Once the ref count is large, **every** future `git fetch`, `git clone`, or `git push` against that repository triggers a fresh, full ref-advertisement walk:
- `InfoRefsReceivePack` (invoked on every push attempt, including by other, legitimate collaborators) is **never cached** — `handleInfoRefs` is called directly with no `tryCache` wrapper: [3](#0-2) 
- `InfoRefsUploadPack` does go through `infoRefCache.tryCache`, but the cache is bypassed entirely whenever the request carries `GitConfigOptions` or a `GitProtocol` value (both attacker-controllable per-request fields), forcing a full recomputation on every such request: [4](#0-3) 

Unlike other ref-listing RPCs in the same codebase (e.g. `ListRefs`/`GetReferences`, which support `Limit`/`Patterns`/pagination tokens), the info/refs advertisement path has no equivalent limiting mechanism, since the git wire protocol itself requires a full ref advertisement for negotiation: [5](#0-4) [6](#0-5) 

The codebase itself acknowledges the operational cost of very large ref counts — internal tooling explicitly warns about "stray" refs and batches cleanup/creation in chunks of up to 250k, and benchmarking scripts show that repositories with millions of refs are an expected, supported (if painful) scale point: [7](#0-6) [8](#0-7) 

### Impact Explanation
Any actor with push access to a repository (an "ordinary user's push" in scope) can create an unbounded number of refs via repeated `UpdateReferences` calls (or plain `git push` of many branches). Because `InfoRefsReceivePack` is executed uncached on every subsequent push attempt by any collaborator, and `InfoRefsUploadPack`'s cache can be trivially bypassed by supplying a `GitConfigOptions`/`GitProtocol` value, the ref advertisement becomes an expensive, unbounded operation executed repeatedly for the whole repository's population of users. This can render clone/fetch/push against the repository slow or effectively unusable for everyone (a repository-wide, gRPC handler resource-exhaustion DoS), mirroring the "any future call to `claimForAllWindows()` becomes unusable" outcome in the source report.

### Likelihood Explanation
Likelihood is moderate-to-high: creating a large number of refs requires only ordinary push/write access to the repository (no special privilege), and `UpdateReferences` places no explicit bound on the number of ref updates accepted per stream or over time. The only natural friction is the time/bandwidth cost of performing the pushes themselves, which is a one-time cost to the attacker versus a recurring cost imposed on every future accessor of the repository.

### Recommendation
- Add an explicit configurable ceiling on the total number of references permitted per repository (enforced in `UpdateReferences` and other ref-creation paths), rejecting updates that would exceed it, similar to how `ListRefs`/`GetReferences` already support `Limit`.
- Ensure `InfoRefsReceivePack` responses are cached the same way `InfoRefsUploadPack` responses are (or otherwise rate-limited/memoized) so that repeated push attempts against a huge-ref repository don't each re-trigger a full, uncached ref walk.
- Do not allow client-supplied `GitConfigOptions`/`GitProtocol` values to unconditionally defeat the `InfoRefsUploadPack` cache; normalize/validate these before using them as a cache-bypass signal, or key the cache on them instead of skipping the cache entirely.
- Consider tracking ref-count/packed-refs-size in `stats.RepositoryInfoForRepository`-style checks and proactively flagging or throttling repositories that cross a threshold, consistent with the existing "stray ref" sweeping tooling.

### Proof of Concept
1. As a user with push access to a repository, call `UpdateReferences` repeatedly (or run many `git push` operations) to create a very large number of refs (e.g. hundreds of thousands to millions), as already demonstrated feasible by the project's own benchmarking scripts, which create up to 250,000-ref batches per call: [9](#0-8) 
2. Any subsequent `git clone`/`git fetch` (via `InfoRefsUploadPack`) or `git push` (via `InfoRefsReceivePack`) against the same repository triggers `handleInfoRefs`, which runs `git-upload-pack`/`git-receive-pack --advertise-refs` over the full, now-huge ref set, with `InfoRefsReceivePack` never being cached: [3](#0-2) 
3. Repeat step 2 concurrently/from multiple clients (or simply supply `GitConfigOptions`/`GitProtocol` to bypass the `InfoRefsUploadPack` cache) to force repeated full-cost advertisement walks, degrading or exhausting server resources for all users of that repository.

// GetReferencesConfig is configuration that can be passed to GetReferences in order to change its default behaviour.
type GetReferencesConfig struct {
	// Patterns limits the returned references to only those which match the given pattern. If no patterns are given
	// then all references will be returned.
	Patterns []string
	// Limit limits
	Limit uint
}

// GetReferences enumerates references in the given repository. By default, it returns all references that exist in the
// repository. This behaviour can be tweaked via the `GetReferencesConfig`.
func GetReferences(ctx context.Context, repoExecutor RepositoryExecutor, cfg GetReferencesConfig) ([]git.Reference, error) {
	flags := []Option{Flag{Name: "--format=%(refname)%00%(objectname)%00%(symref)"}}
	if cfg.Limit > 0 {
		flags = append(flags, Flag{Name: fmt.Sprintf("--count=%d", cfg.Limit)})
	}

	cmd, err := repoExecutor.Exec(ctx, Command{
		Name:  "for-each-ref",
		Flags: flags,
		Args:  cfg.Patterns,
	}, WithSetupStdout())
