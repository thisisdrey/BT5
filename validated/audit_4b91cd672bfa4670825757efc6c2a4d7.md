## Title
Excessive memory allocation via unbounded array length in TVM precompiled-contract input parsing — (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytes32Array()` and `PrecompiledContracts.extractBytesArray()` read an array-length field directly from attacker-controlled `DataWord[]` input (the calldata passed to a TVM precompiled contract) and immediately allocate a Java array of that size, with no upper bound check against the amount of data actually available. This mirrors the libming `readBytes`/`parseSWF_DEFINEBITSJPEG2` pattern in CVE-2018-13251: a length value taken straight from untrusted input is used to size a memory allocation before validating that the input actually contains that much data.

### Finding Description
`extractBytes32Array` reads the length from `words[offset].intValueSafe()` and allocates `new byte[len][]` before any bytes are copied: [1](#0-0) 

Likewise, `extractBytesArray` takes `len` the same way and allocates `new byte[len][]` up front: [2](#0-1) 

`DataWord.intValueSafe()` only caps the value when the underlying 256-bit word occupies more than 4 bytes or decodes negative — for any 32-bit-representable positive value (up to `Integer.MAX_VALUE - 1`, since only overflow/negative triggers the `Integer.MAX_VALUE` clamp) it returns the value unmodified: [3](#0-2) 

So a caller can supply a calldata word whose value is, e.g., `0x7FFFFFFF` (fits in 4 bytes, positive), which `intValueSafe()` returns verbatim as `len`. The code then executes `new byte[len][]` — allocating an object-reference array of that length (8 bytes per reference on a 64-bit JVM with compressed oops off, or 4 bytes with compressed oops) — before ever checking whether the actual calldata (`data`, or `words` array) is large enough to back that many entries. This is conceptually identical to libming's flaw: the size field controls the allocation, but the data backing it is never bounds-checked before the allocation happens.

By contrast, other length-driven allocation paths in the same class do implement upper-bound checks before allocating — e.g., `VerifyTransferProof.execute()` explicitly bounds `spendCount`/`receiveCount` to `[1,2]` before sizing any arrays: [4](#0-3) 
and the RLP decoder in `RLP.java` calls `verifyLength()` to compare a supplied length against the actual remaining payload before allocating, and even has an explicit catch for `OutOfMemoryError` as defense-in-depth: [5](#0-4) 
`extractBytes32Array`/`extractBytesArray` have no equivalent guard on `len` before the `new byte[len][]` allocation.

### Impact Explanation
An unbounded allocation triggered from unauthenticated/unprivileged transaction data can force a large, single-shot heap allocation on the node processing the transaction/contract call. If reachable with an attacker-chosen large `len` (bounded only by 31-bit int range), this can exhaust available heap and throw `OutOfMemoryError`, which — depending on where it propagates and whether it's caught — can crash the executing node thread/process or destabilize the JVM, producing node crash/halt (denial of service) impact for a call that any unprivileged contract deployer/caller can trigger via a `TRIGGER_SMART_CONTRACT` invocation of the relevant precompiled contract address.

### Likelihood Explanation
Reachability depends on which precompiled contract(s) actually call `extractBytes32Array`/`extractBytesArray` and whether that precompile is enabled by chain configuration (`VMConfig` feature flags) at the target node. I was not able to fully confirm the specific caller within the available search iterations — the two helper methods exist in `PrecompiledContracts.java` alongside other precompile implementations (e.g., signature-array-based precompiles used with `SIG_LENGTH`), but I did not verify the exact call site or its feature-flag gating before running out of tool budget.

### Recommendation
Add explicit upper-bound validation of the decoded `len` in `extractBytes32Array` and `extractBytesArray` against the size of the actual backing `words`/`data` buffer (similar to `RLP.verifyLength()` or the bounding done for `spendCount`/`receiveCount` in `VerifyTransferProof`) before allocating `new byte[len][]`, rejecting the precompiled-contract call (returning a failure result) rather than allocating memory proportional to an untrusted length.

### Proof of Concept
Not fully constructible without confirming the exact precompiled-contract entry point that invokes `extractBytes32Array`/`extractBytesArray` and its enabling `VMConfig` flag — this could not be verified within the available search budget. Conceptually: craft a `TRIGGER_SMART_CONTRACT` transaction whose calldata targets the precompiled address using these helpers, with the length word at the expected offset set to a large 31-bit value (e.g. `0x7FFFFFFF`), which would cause `new byte[len][]` to attempt an allocation far exceeding available heap.

**Caveat:** Because the exact caller/reachability of `extractBytes32Array`/`extractBytesArray` was not confirmed, this finding should be treated as a candidate requiring verification of the calling precompiled-contract path and its feature-flag gating before being treated as fully proven exploitable.
