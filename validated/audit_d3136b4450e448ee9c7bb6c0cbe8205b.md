### Title
Unauthenticated non-broadcast block upload still triggers P2P relay, bypassing the auth gate - (File: stackslib/src/net/api/postblock_v3.rs)

### Summary
`RPCPostBlockRequestHandler::try_parse_request` only rejects unauthenticated requests when `broadcast=1` is explicitly requested, letting an unauthenticated caller post a block with `broadcast` defaulted to `false`. `try_handle_request` then relays any accepted block to the P2P network unconditionally, without checking `self.broadcast`, so the auth gate's intent (only broadcast when authenticated) is not enforced by the actual relay decision.

### Finding Description
The claimed equality is: *the set of blocks accepted into staging via the unauthenticated (non-broadcast) path must never trigger `node.set_relay_message(StacksMessageType::NakamotoBlocks(...))`.* Tracing the code:

- In `try_parse_request` (stackslib/src/net/api/postblock_v3.rs:99-122), `authenticated` is only set `true` if an `authorization` header matching `self.auth` is present; `broadcast` is parsed from the query string and defaults to `false`. The only enforcement is `if broadcast && !authenticated { return Err(401) }` — i.e., it is legal to omit both the header and `broadcast=1`.
- `self.broadcast = Some(broadcast)` is stored (`false` in the attack scenario), and the block is parsed and stored in `self.block`.
- In `try_handle_request` (lines 147-207), `Relayer::process_new_nakamoto_block_ext(...)` is called with `self.broadcast.unwrap_or(false)` as the last argument — this only affects internal validation/storage semantics, not the HTTP-level relay decision.
- Critically, at lines 197-202:
```
if data_resp.accepted {
    node.set_relay_message(StacksMessageType::NakamotoBlocks(NakamotoBlocksData {
        blocks: vec![block],
    }));
}
```
This check depends solely on `data_resp.accepted` (whether the block was validated/stored), **not** on `self.broadcast` or `authenticated`. So any block that passes chainstate validation — regardless of whether the request was authenticated or requested broadcast — is queued via `set_relay_message` for propagation to the node's P2P peers.

This means the `broadcast` query flag and the `authorization` header do not actually gate relay to the network; they are effectively decorative for this purpose. Any unauthenticated, non-broadcast POST of a validly-formed and chain-valid Nakamoto block is disseminated to the peer network exactly the same as an authenticated broadcast request.

### Impact Explanation
This allows an unauthenticated remote attacker to use a node as a relay/amplifier: any block they can get validated by `process_new_nakamoto_block_ext` (i.e., a legitimately-signed/valid Nakamoto block, e.g. one they obtained by other means or crafted with valid signer signatures they control if they are a legitimate miner/signer) is announced onward to the target's peers, regardless of the operator's intent to keep the auth-gated `/v3/blocks/upload/` endpoint from being usable as an open relay. Note that this does not forge invalid blocks — `process_new_nakamoto_block_ext` still enforces consensus validity (signatures, chaining, etc.), which is out of scope to bypass. The actual vulnerability is narrower than "forged data propagation": it is an authorization-bypass on the relay decision itself — the auth/broadcast gate is supposed to restrict who can cause the node to push relay traffic to the P2P network via this RPC endpoint, and that restriction does not hold. This matches the "auth bypass" / "unauthorized... network-wide propagation" category, but only for otherwise-valid blocks the attacker could not otherwise get relayed without already being a peer providing it through normal P2P gossip.

### Likelihood Explanation
Preconditions: the node must have `self.auth = Some(password)` configured (auth-gated deployment) and the attacker needs no credentials at all — they just omit the `Authorization` header and omit `broadcast=1` (or set it to something other than `1`). The endpoint `/v3/blocks/upload/` is a standard RPC route, remotely reachable by any unprivileged client that can reach the node's RPC port. The block itself still has to pass `Relayer::process_new_nakamoto_block_ext`'s consensus validation to be `accepted`, which limits attacker-supplied garbage but not attacker ability to relay a validly-obtained block through an operator-restricted endpoint. This is repeatable per valid block.

### Recommendation
Gate the relay decision on both `data_resp.accepted` and `self.broadcast` (and effectively the authentication state that produced it), e.g.:
```rust
if data_resp.accepted && self.broadcast.unwrap_or(false) {
    node.set_relay_message(...);
}
```
so that only requests that were both authenticated and explicitly requested broadcast actually cause `set_relay_message` to fire, matching the endpoint's documented/intended access control.
