### Title
Unprivileged attacker can fill a victim's per-account token list to `MAX_TOKENS_PER_USER` via dust `DepositToken.transfer`, permanently blocking the victim from depositing new collateral types or issuing new synthetics - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`fscrypt`'s bug class is "an unprivileged user can consume a shared/capped resource to deny service to others." The Metronome analog is the per-account token lists `depositTokensOfAccount` / `debtTokensOfAccount` in `Pool`, capped at `MAX_TOKENS_PER_USER = 30` [1](#0-0) . `DepositToken._transfer` adds the *recipient* to the list whenever their balance goes from 0 to non-zero, with no minimum amount and no consent [2](#0-1) . An attacker can dust-transfer 1 wei of each listed `DepositToken` to a victim, filling their list to the cap so that all subsequent first-time deposits and first-time debt mints for that account revert.

### Finding Description
`Pool.addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are guarded by `onlyIfAdditionWillNotReachMaxTokens`, which reverts with `UserReachedMaxTokens` once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [3](#0-2) . These functions are invoked from `DepositToken._mint` (line 487), `DepositToken._transfer` (line 519), and `DebtToken._mint` (line 599) whenever a balance transitions 0 → non-zero [4](#0-3) [5](#0-4) .

Attack path (all public, unprivileged entry points):
1. Attacker deposits dust into each of the pool's N listed collateral types via `DepositToken.deposit(1, attacker)` (no minimum; `amount_ > 0` suffices) [6](#0-5) .
2. Attacker calls `depositToken_i.transfer(victim, 1)` for each token. `transfer` only checks the *sender's* unlocked balance via `_revertIfLocked` [7](#0-6) , and `_transfer` pushes the token onto the victim's list [8](#0-7) .
3. Once the victim's combined list reaches 30, any `deposit`/`mint` into a collateral the victim doesn't already hold reverts inside `_mint → addToDepositTokensOfAccount`, and any `issue`/`mint`/`flashIssue`-triggered debt mint of a new synthetic reverts inside `DebtToken._mint → addToDebtTokensOfAccount`.

The same griefing also lands via `Pool.liquidate → DepositToken.seize → _transfer(attacker-chosen to_)` and `DebtToken.repay(onBehalfOf_)`-driven list changes, but plain `transfer` is the cleanest vector.

### Impact Explanation
Temporary freezing of funds / denial of service on position management. The victim cannot add any new collateral type or open debt in any new synthetic until they fully zero out an existing position (only `balance == 0` triggers `removeFromDepositTokensOfAccount`/`removeFromDebtTokensOfAccount`) [9](#0-8) . A victim who needs to deposit additional collateral to avoid liquidation, or who wants to migrate to a different collateral asset, is blocked. This is a griefing attack — cost to the attacker is ~N wei of dust plus gas, while the victim's only escape is fully exiting a position, which may be economically harmful or impossible if their remaining balances are locked against debt.

### Likelihood Explanation
Reachable by any EOA with no privileges. Constraints that reduce likelihood: the attacker can only fill the list with tokens the governor has actually listed (`addDepositToken`/`addDebtToken` are governor-only), so the attack requires enough listed deposit/debt token types to approach 30; on deployments with few collateral types the cap may be unreachable. The victim also has a (costly) recovery path — fully burning/withdrawing one position frees a slot. Because exploitation depends on deployment configuration, likelihood is medium-low, but the revert path is deterministic once the cap is hit and no modifier, pause flag, health check, or reentrancy guard prevents dust transfers to arbitrary recipients.

### Recommendation
- Add a minimum meaningful amount or require the recipient to opt in before pushing to `depositTokensOfAccount`/`debtTokensOfAccount` (e.g., only auto-add on `deposit`/`issue` where the caller specifies `onBehalfOf_`, not on plain ERC20 `transfer`), or
- Return early/skip list insertion for `transfer` recipients (transferred balances are still accounted in `depositOf` via `balanceOf`, so the list membership is the only thing lost — alternatively make `transfer` opt-in or restricted), or
- Treat `MAX_TOKENS_PER_USER` as a soft cap: revert only the *new* token's usability rather than blocking the whole operation, or allow the account to forcibly remove entries.

### Proof of Concept
Hardhat test against existing fixtures (pattern follows `test/Pool.test.ts` `addToDepositTokensOfAccount` tests at lines 1386-1416):

```ts
it('griefs victim by filling depositTokensOfAccount via dust transfers', async function () {
  const {pool, msdMET /* ...other listed deposit tokens */, user1, user2} = await loadFixture(fixture)

  const victim = user1.address
  const attacker = user2

  const depositTokens: DepositToken[] = [msdMET, msdVAUSDC, /* ... all listed collaterals */]

  // 1. Attacker deposits dust into each collateral and transfers 1 wei of msdTOKEN to the victim
  for (const dt of depositTokens) {
    const underlying = await ethers.getContractAt('ERC20Mock', await dt.underlying())
    await underlying.mint(attacker.address, 10)
    await underlying.connect(attacker).approve(dt.address, 10)
    await dt.connect(attacker).deposit(10, attacker.address)
    await dt.connect(attacker).transfer(victim, 1) // balance 0 -> 1: adds token to victim's list
  }

  // victim's list is now full of attacker-chosen tokens
  const len = (await pool.getDepositTokensOfAccount(victim)).length
            + (await pool.getDebtTokensOfAccount(victim)).length
  expect(len).to.eq(await pool.MAX_TOKENS_PER_USER())

  // 2. Victim tries to deposit a NEW collateral type they don't hold -> reverts
  const newUnderlying = await ethers.getContractAt('ERC20Mock', await msdNewCollateral.underlying())
  await newUnderlying.mint(victim, parseEther('100'))
  await newUnderlying.connect(user1).approve(msdNewCollateral.address, parseEther('100'))

  await expect(
    msdNewCollateral.connect(user1).deposit(parseEther('100'), victim)
  ).to.revertedWithCustomError(pool, 'UserReachedMaxTokens')

  // 3. Victim tries to issue a synthetic whose debt token isn't in their list -> reverts
  await expect(
    msXDebt.connect(user1).issue(parseEther('10'), victim)
  ).to.revertedWithCustomError(pool, 'UserReachedMaxTokens')
})
```

Key assertions demonstrated: `deposit` reverts inside `DepositToken._mint → Pool.addToDepositTokensOfAccount` (Pool.sol:144-146, DepositToken.sol:487), and `issue` reverts inside `DebtToken._mint → Pool.addToDebtTokensOfAccount` (DebtToken.sol:599), even though the victim's collateral position and health are otherwise valid.
