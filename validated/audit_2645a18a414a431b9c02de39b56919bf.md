### Title
Unbacked balance creation via repeated unfreeze of the same FreezeV2 balance in `UnfreezeBalanceV2Actuator` — ([File: actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java])

### Summary
`UnfreezeBalanceV2Actuator.execute()` never decrements the account's `FreezeV2` list balance when processing an unfreeze request, while `validate()` re-checks each new unfreeze request against that same, never-decremented `FreezeV2` amount. This mirrors the Thala class of bug: an isolated accounting flaw in the "farming"/staking withdrawal path let a user extract more value than they actually held because the contract failed to reduce the underlying deposited balance on withdrawal.

### Finding Description
`UnfreezeBalanceV2Actuator` defines `updateAccountFrozenInfo(ResourceCode, AccountCapsule, long)` specifically to subtract the unfrozen amount from the matching entry in `accountCapsule.getFrozenV2List()`: [1](#0-0) 

However, `execute()` never calls this method. It only calls `unfreezeExpire` (to settle previously matured unfreeze entries), `addUnfrozenV2List` (to enqueue the new unfreeze request), `updateTotalResourceWeight` (which only adjusts the chain-wide/dynamic-store resource weight counters via `addFrozenBalanceForBandwidthV2(-unfreezeBalance)` etc.), and `updateVote`: [2](#0-1) 

Meanwhile, `validate()`'s `checkUnfreezeBalance()` determines whether a given `unfreezeBalance` request is legal purely by comparing it against the current `FreezeV2` amount stored in `accountCapsule.getFrozenV2List()` for that resource type: [3](#0-2) 

Because `execute()` never calls `updateAccountFrozenInfo` to reduce that `FreezeV2` entry, the `FreezeV2` amount used by `checkUnfreezeBalance` in `validate()` is never reduced by prior unfreeze operations within the same account. An attacker who froze `X` TRX for a resource can therefore submit multiple `UnfreezeBalanceV2Contract` transactions, each unfreezing up to `X` (as long as `unfreezeBalance <= frozenAmount`, which stays at the original `X` since it's never decremented), up to `UNFREEZE_MAX_TIMES` (32) pending unfreeze entries: [4](#0-3) 

Each of these unfreeze requests is appended to `unfrozenV2List` via `accountCapsule.addUnfrozenV2List(freezeType, unfreezeBalance, expireTime)`. After the `unfreezeDelayDays` period, each entry is paid out as real TRX balance — either automatically the next time `unfreezeExpire`/`checkUnfreezeBalance` type flows run, or explicitly via `WithdrawExpireUnfreezeActuator`, which simply sums matured `UnFreezeV2` entries and credits the account's balance: [5](#0-4) 

This is the direct structural analog of Thala's incident: the vulnerable v1 farming contract update failed to properly decrement an internal deposit/stake accounting value on withdrawal, letting the exploiter repeatedly withdraw against the same collateral and drain the pool. Here, `FreezeV2.amount` is the analogous "deposit ledger" that should be decremented on each unfreeze but is not touched by `execute()`.

### Impact Explanation
If confirmed at runtime, this allows any account to unfreeze (and, after the delay period, withdraw as real TRX) many multiples of the TRX it actually has frozen, up to 32 pending unfreeze operations per resource type. This creates unbacked TRX balance out of the account's genuinely locked collateral — a direct, unauthorized minting of funds, which is Critical severity (theft/unbacked balance creation), consistent with the "unbacked balance" acceptance criterion.

### Likelihood Explanation
The path is reachable by any signed transaction from an unprivileged account: freeze once via `FreezeBalanceV2Contract`, then submit up to 32 `UnfreezeBalanceV2Contract` transactions against the same frozen amount, since `validate()`'s only safeguard (`checkUnfreezeBalance`) reads a value that `execute()` never mutates. No special privilege, contract deployment, or race condition is required — just repeated calls of a publicly available contract type.

### Recommendation
In `UnfreezeBalanceV2Actuator.execute()`, call `updateAccountFrozenInfo(freezeType, accountCapsule, unfreezeBalance)` (or equivalent) before/after `updateTotalResourceWeight`, so the `FreezeV2` list entry for the resource is decremented by `unfreezeBalance` on every successful unfreeze, keeping the per-account frozen ledger consistent with the amount actually still locked. Add regression tests that perform multiple sequential unfreeze calls against the same frozen balance and assert the second/subsequent calls fail once the tracked `FreezeV2` amount is exhausted.

### Proof of Concept
Note: I was unable to execute this end-to-end in a live environment (no code execution tools available in this session); the following is a structural PoC derived purely from reading the actuator code, and should be validated with a unit test similar to existing tests in `framework/src/test/java/org/tron/core/actuator/UnfreezeBalanceV2ActuatorTest.java`:

1. Account freezes `100_000_000` sun for `BANDWIDTH` via `FreezeBalanceV2Actuator`, populating one `FreezeV2{type=BANDWIDTH, amount=100_000_000}` entry.
2. Account submits `UnfreezeBalanceV2Contract{resource=BANDWIDTH, unfreezeBalance=100_000_000}` and calls `UnfreezeBalanceV2Actuator.validate()`/`execute()`. `checkUnfreezeBalance` passes (100M <= 100M). `execute()` enqueues an `UnFreezeV2` entry but does not reduce the `FreezeV2.amount`.
3. Account immediately submits the same `UnfreezeBalanceV2Contract{resource=BANDWIDTH, unfreezeBalance=100_000_000}` again. `checkUnfreezeBalance` still passes because `FreezeV2.amount` for BANDWIDTH is still `100_000_000` (unchanged by step 2). A second `UnFreezeV2` entry for 100M is enqueued.
4. Repeat up to `UNFREEZE_MAX_TIMES` (32) times, each adding another 100M-sun unfreeze entry.
5. After `unfreezeDelayDays` elapses, the account calls `WithdrawExpireUnfreezeActuator` (or triggers `unfreezeExpire`), which sums all matured `UnFreezeV2.unfreezeAmount` entries and adds them to `accountCapsule.balance` — i.e., the account receives up to 32×100M sun in real TRX balance despite having frozen only 100M sun once.   public boolean checkUnfreezeBalance(AccountCapsule accountCapsule,
                                      final UnfreezeBalanceV2Contract unfreezeBalanceV2Contract,
                                      ResourceCode freezeType) {
    boolean checkOk = false;

    long frozenAmount = 0L;
    List<FreezeV2> freezeV2List = accountCapsule.getFrozenV2List();
    for (FreezeV2 freezeV2 : freezeV2List) {
      if (freezeV2.getType().equals(freezeType)) {
        frozenAmount = freezeV2.getAmount();
        break;
      }
    }

    if (unfreezeBalanceV2Contract.getUnfreezeBalance() > 0
        && unfreezeBalanceV2Contract.getUnfreezeBalance() <= frozenAmount) {
      checkOk = true;
    }

    return checkOk;
  }

  public void updateAccountFrozenInfo(ResourceCode freezeType, AccountCapsule accountCapsule, long unfreezeBalance) {
    List<FreezeV2> freezeV2List = accountCapsule.getFrozenV2List();
    for (int i = 0; i < freezeV2List.size(); i++) {
      if (freezeV2List.get(i).getType().equals(freezeType)) {
        FreezeV2 freezeV2 = FreezeV2.newBuilder()
            .setAmount(freezeV2List.get(i).getAmount() - unfreezeBalance)
            .setType(freezeV2List.get(i).getType())
            .build();
        accountCapsule.updateFrozenV2List(i, freezeV2);
        break;
      }
    }
  }
