Based on my analysis, this codebase's StackerDB and P2P layers already enforce strong equality checks (chunk signatures verified against slot owners, wire lengths bounded by `MAX_MESSAGE_LEN`/`MAX_RELAYERS_LEN`, preamble/payload length checks in `stackslib/src/net/connection.rs` and `stackslib/src/net/codec.rs`). However, one genuine analog to the reported bug class exists in the `libsigner` transport layer.

### Title
Unauthenticated event-injection endpoint in `SignerEventReceiver` accepts forged node events with no source authentication - (File: `libsigner/src/events.rs`)

### Summary
The signer's HTTP event receiver (`SignerEventReceiver::next_event`) dispatches incoming POST requests to `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, and `/new_block` purely based on URL path, with no authentication, source-address check, or shared-secret validation of any kind.

### Finding Description
`SignerEventReceiver::bind` opens a plain `tiny_http::HttpServer` on the configured `endpoint` [1](#0-0) . `next_event` then reads the request body and routes it to `process_event::<T, ...>` solely by matching `request.url()` — there is no check of headers, an auth token, or the peer's identity anywhere in this function [2](#0-1) . `process_event` itself just JSON-deserializes the body and converts it into a `SignerEvent` [3](#0-2) . This is a different (and separately unauthenticated) channel from the node→signer block-proposal RPC path, which is gated by `auth_password`/`auth_token` per `docs/signing.md` [4](#0-3)  — no equivalent gate exists for this events listener anywhere in `libsigner/src/events.rs`.

Some payload types re-verify cryptographic authenticity downstream (e.g., `TryFrom<StackerDBChunksEvent>` recovers and checks a public key for `signers-*` contracts via `chunk.recover_pk()` [5](#0-4) ), but the `.miners` contract path (`SignerEvent::MinerMessages`) only deserializes the chunk bytes with no signature check at all [6](#0-5) . Likewise `BlockValidationResponse`, `NewBurnBlock`, and `NewBlock` events carry no cryptographic binding to the node at this transport layer — they are trusted purely because they arrived on this socket.

### Impact Explanation
Any remote, unprivileged party who can reach the signer's event-receiver port can POST a forged `StackerDBChunksEvent` (for `.miners`), `BlockValidateResponse`, `BurnBlockEvent`, or `StacksBlockEvent` and have it injected into the signer's event channel exactly as if the trusted node had sent it — `SignerEvent::MinerMessages` in particular is accepted with zero signature verification. This is a transport-level authentication-bypass: the equality "received from my node" vs. "received from anyone who can reach the socket" is never checked. Whether this rises to Critical severity depends on how far downstream logic (out of scope per the rules) further validates content, but the missing gate itself is a concrete, code-level defect in the in-scope `libsigner` transport file.

### Likelihood Explanation
Exploitability depends entirely on network reachability of the signer's event port, which is a deployment/config detail (out of scope per the rules excluding config files and "needing only traffic volume"/binding-related defaults). The code path itself, however, performs no authentication regardless of binding, so any reachable attacker (including from a compromised host on the same subnet, or misconfigured firewall/NAT) can exploit it with a single POST.

### Recommendation
Add an authentication mechanism to the `SignerEventReceiver` HTTP endpoint (e.g., a shared-secret header checked in `next_event`/`process_event`, analogous to the existing `auth_token`/`auth_password` scheme used for the node's block-proposal RPC), and/or require the `.miners` `StackerDBChunksEvent` path to validate `chunk` signatures before constructing `SignerEvent::MinerMessages`.

### Proof of Concept
1. Reach the signer's event-receiver socket (whatever address it is bound to).

Send: `POST /stackerdb_chunks HTTP/1.1` with a JSON-encoded `StackerDBChunksEvent` for the `.miners` boot contract containing an attacker-crafted, unsigned `StackerDBChunkData` payload (mirrors the test harness pattern in `libsigner/src/tests/mod.rs` lines 121-146, but omitting/forging `chunk.sign`).
3. Observe that `process_event` accepts and forwards this as `SignerEvent::MinerMessages` to the signer runloop with no signature check, as shown by the code path in `libsigner/src/events.rs:544-567`. [2](#0-1) [7](#0-6)
