I'll investigate whether gitaly has genuine analogous rate-limiting/gating mechanisms that could be "gamed" in a similar way, since that's the underlying bug class described (a per-request/per-transaction limit that doesn't prevent an actor from bypassing the overall protection by issuing many separate requests).### Title
Pack-objects concurrency limiter keys on a self-reported `remote_ip` field, allowing an ordinary client to bypass per-IP resource-exhaustion protection - (File: internal/gitaly/service/hook/pack_objects.go)

### Summary
Gitaly's `pack_objects_limiting` feature is documented as its primary "backpressure" defense against Gitaly being overwhelmed by concurrent `git-pack-objects` invocations, and by default limits concurrency "per remote IP" to prevent a surge of fetch/clone requests from exhausting server resources. However, the value used as the limiting key is not derived from any verified network-layer identity of the caller — it is a plain string field (`remote_ip`) carried end-to-end through gRPC metadata and the `HooksPayload`/`gitaly-hooks` subprocess chain, and is trusted at face value by `packObjectsHook`. This is the same failure pattern as the report's `maxRecordsPerTransaction` bug: a per-key admission control that an ordinary actor can trivially defeat by varying the key value across otherwise-identical requests, giving operators a false sense of DoS protection.

### Finding Description
`doc/backpressure.md` and the `PackObjectsHookWithSidechannelRequest.remote_ip` field comment both state the intent explicitly: [1](#0-0) [2](#0-1) 

In `packObjectsHook`, the server parses `req.GetRemoteIp()` as an IP and, if it is non-loopback, uses it as the concurrency-limiting key for `runPackObjectsLimited`: [3](#0-2) 

The `ConcurrencyLimiter.Limit` function then buckets concurrency purely by this string `limitingKey`, with no independent verification: [4](#0-3) 

The `remote_ip` value originates as a plain gRPC metadata value (`"remote_ip"`), which is attached to the outgoing hook-payload chain, e.g. via `WithPackObjectsHookEnv`/`WithReceivePackHooks`, and later re-emitted by `gitaly-hooks` as a request field with no cryptographic binding to the actual TCP peer of the eventual `PackObjectsHookWithSidechannel` call: [5](#0-4) [6](#0-5) [7](#0-6) 

Because `PackObjectsHookWithSidechannel` is invoked over Gitaly's internal socket by the `gitaly-hooks` subprocess (spawned locally for every `git-upload-pack`/pack-objects invocation), the gRPC peer address for that call is always local — there is no way for Gitaly to cross-check the claimed `remote_ip` against a real network-layer address at that point. The test suite itself documents that this string is fully attacker/caller-influenced and is used verbatim as the concurrency/cache-partitioning key ("requests from different remote IPs" test), confirming that varying this single field is sufficient to obtain a completely separate concurrency bucket: [8](#0-7) [9](#0-8) 

This mirrors the report's bug class exactly: a resource-protection mechanism (`maxRecordsPerTransaction` there, `pack_objects_limiting` keyed by IP here) that is enforced per self-reported/attacker-influenced key rather than per verified identity. An actor who can influence or forge multiple distinct `remote_ip` strings (e.g., a caller upstream of the trust boundary, or any code path where this value is not tightly pinned to a validated peer address) obtains one full concurrency allotment (default 200 concurrent `git-pack-objects` processes, `defaultPackObjectsLimitingConcurrency = 200`) per distinct string, defeating the intended global backpressure guarantee described in `doc/backpressure.md`.

### Impact Explanation
Medium: the specific mechanism advertised to protect Gitaly from resource exhaustion during pack-objects generation (CPU/memory-heavy `git-pack-objects` invocations) can be circumvented by varying a value that is not authenticated against the real network peer, allowing far more concurrent expensive git operations than the configured limit intends, i.e., resource exhaustion / degraded service for legitimate users — the exact class of "false sense of security" impact called out in the source report.

### Likelihood Explanation
Medium: the value is carried as ordinary metadata/string field over several hops (gRPC metadata → env-encoded `HooksPayload` → gRPC request field) with no signature or peer-verification step tying it to the actual originating connection, and this design is exercised by the codebase's own tests as a normal, supported input rather than as a defense mechanism against forgery.

### Recommendation
Document explicitly that `pack_objects_limiting`'s per-IP key is a soft/best-effort partition rather than a hard security boundary against DoS (similar to the report's own recommendation for `maxRecordsPerTransaction`). Where possible, prefer a limiting key anchored to verified request context (e.g., authenticated identity/token or the true peer of the *original* external gRPC connection captured once and passed through immutably) rather than an ordinary string field that is reconstructed at each hop.

### Proof of Concept
1. Issue N clone/fetch requests against the same repository in parallel to Gitaly (via SSH or SmartHTTP), driving `PostUploadPack`/`SSHUploadPackWithSidechannel`, each of which triggers the `pack-objects` hook.
2. As demonstrated by `packObjectsHook` and its unit tests, each invocation's concurrency bucket is selected solely by the `remote_ip` string carried in `PackObjectsHookWithSidechannelRequest`.
3. If this value can be made to differ per request (whether via legitimate multi-hop proxying or malformed/forged input upstream of Gitaly's trust boundary), the server treats each as a distinct key in `ConcurrencyLimiter.limitsByKey`, granting each request its own full concurrency/queue budget instead of sharing one bounded pool. [10](#0-9) 

Note: I was unable to fully trace, within the indexed portions of this repo, exactly how `remote_ip` metadata is first populated at the outermost gRPC entrypoint (e.g., whether SSH/SmartHTTP service handlers pin it to `peer.FromContext` or accept it from an upstream caller such as gitlab-shell/workhorse); that boundary lives partly outside Gitaly and could not be verified with certainty here.

// getConcurrencyLimit retrieves the concurrency limit for the given key. If no such limiter exists
// it will be lazily constructed.
func (c *ConcurrencyLimiter) getConcurrencyLimit(limitingKey string) *keyedConcurrencyLimiter {
	c.m.Lock()
	defer c.m.Unlock()

	if c.limitsByKey[limitingKey] == nil {
		// Set up the queue tokens in case a maximum queue length was requested. As the
		// queue tokens are kept during the whole lifetime of the concurrency-limited
		// function we add the concurrency tokens to the number of available token.
		var queueTokens semaphorer
		if c.maxQueueLength > 0 {
			queueTokens = c.createSemaphore(uint(c.currentLimit() + c.maxQueueLength))
		}

		c.limitsByKey[limitingKey] = &keyedConcurrencyLimiter{
			monitor:               c.monitor,
			maxQueueWait:          c.maxQueueWait,
			setWaitTimeoutContext: c.SetWaitTimeoutContext,
			concurrencyTokens:     c.createSemaphore(uint(c.currentLimit())),
			queueTokens:           queueTokens,
		}
	}

	c.limitsByKey[limitingKey].refcount++

	return c.limitsByKey[limitingKey]
}

// WithPackObjectsHookEnv provides metadata for gitaly-hooks so it can act as a pack-objects hook.
func WithPackObjectsHookEnv(objectHash git.ObjectHash, repo *gitalypb.Repository, protocol string) CmdOpt {
	return func(ctx context.Context, cfg config.Cfg, gitCmdFactory CommandFactory, cc *cmdCfg) error {
		if !cfg.PackObjectsCache.Enabled {
			return nil
		}

		if repo == nil {
			return fmt.Errorf("missing repo: %w", ErrInvalidArg)
		}

		userDetails := &UserDetails{
			Protocol: protocol,
			UserID:   metadata.GetValue(ctx, "user_id"),
			Username: metadata.GetValue(ctx, "username"),
			RemoteIP: metadata.GetValue(ctx, "remote_ip"),
		}

		if err := cc.configureHooks(
			ctx,
			cfg,
			objectHash,
			repo,
			gitCmdFactory,
			userDetails,
			PackObjectsHook,
		); err != nil {
			return fmt.Errorf("pack-objects hook configuration: %w", err)
		}

		cc.globals = append(cc.globals, ConfigPair{
			Key:   "uploadpack.packObjectsHook",
			Value: cfg.BinaryPath("gitaly-hooks"),
		})

		return nil
	}
}
