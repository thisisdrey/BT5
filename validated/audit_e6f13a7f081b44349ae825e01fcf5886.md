Based on my analysis of `extractTarToDirectory`, the vulnerability described is technically valid and reproducible.

### Title
Symlink path-confinement bypass via lexical (not filesystem-real) parent-directory computation in tar extraction - ([File: internal/gitaly/service/repository/replicate.go])

### Summary
`extractTarToDirectory` validates each `TypeSymlink` entry's target by computing `filepath.Join(filepath.Dir(targetPath), header.Linkname)` purely lexically and checking the result stays within `targetDir`. This validation assumes `filepath.Dir(targetPath)` reflects the real, on-disk parent directory of the symlink, but when an ancestor path component in `header.Name` is itself a symlink created earlier in the same tar stream, the OS resolves the actual parent directory to a different (typically shallower) real location than the code assumes, letting a subsequent relative `Linkname` escape `targetDir` once dereferenced.

### Finding Description
The confinement check for symlinks is: [1](#0-0) 

This check is purely textual/lexical: it uses `filepath.Dir(targetPath)`, where `targetPath = filepath.Join(targetDir, header.Name)`, as a stand-in for the symlink's real parent directory. It does not account for the possibility that an intermediate path component of `header.Name` is itself a symlink previously created by an earlier tar entry (also validated only against `targetDir`, per [2](#0-1) ). Because tar entries are processed sequentially with attacker-fully-controlled order and content (`s.extractSnapshot` streams the tar produced by the attacker's own repo via `GetSnapshot`, and `extractTarToDirectory` trusts it, see [3](#0-2) ), the attacker can:

1. Create directory `real` inside `targetDir` (via `TypeDir`).
2. Create symlink `a -> "."` (points back to `targetDir` root — passes the check since it resolves to `targetDir` itself).
3. Create nested entries under `a/b/...`. Because `MkdirAll`/`os.Symlink` follow the real filesystem when traversing `a` (a symlink), a directory/symlink declared as `a/b/link` is actually placed on disk at `targetDir/b/link` (one level shallower than the lexical name `a/b/link` suggests).
4. For this `TypeSymlink` entry with `header.Name = "a/b/link"` and `header.Linkname = "../../evil"`, the code computes `resolvedTarget` from the **lexical** `targetDir/a/b`, yielding `targetDir/evil` (inside `targetDir` — check passes). But the real on-disk symlink lives at `targetDir/b/link`, so when later dereferenced by the OS, `"../../evil"` resolves relative to `targetDir/b`, landing at `parent(targetDir)/evil` — outside the repository storage.
5. A subsequent `TypeReg` entry named `a/b/link/payload` (processed via `extractFile`, which calls `os.MkdirAll`/`os.OpenFile` without symlink-safety checks — see [4](#0-3) ) then writes through this symlink chain, landing the file outside `targetDir`.

Neither the top-level prefix check applied to every header [5](#0-4)  nor the symlink-specific check catches this because both operate on lexical `filepath.Join`/`filepath.Dir` computations of `header.Name`, never on the real, symlink-resolved filesystem path. `extractFile` and `os.MkdirAll` for `TypeDir` also perform no `O_NOFOLLOW`/realpath validation before writing.

### Impact Explanation
An attacker who controls a source repository (via fork/push, populating `GetSnapshot`'s tar stream) can, once that repository is replicated via `ReplicateRepository` (used in Praefect replication and repository creation/recovery flows), achieve arbitrary file write outside the target repository's storage directory on the receiving Gitaly node. This is a storage-path-escape / archive-extraction-escape vulnerability with potential for further compromise depending on what paths are writable on the host (e.g., other repositories' data, or files reachable by other services sharing the storage volume).

### Likelihood Explanation
The only precondition is that the attacker owns/controls a repository that will be replicated (a routine, unprivileged action — pushing content and triggering replication is a normal operation in a multi-node/Praefect GitLab deployment). No special role, secret, or misconfiguration is required. The exploit is fully deterministic: the tar stream is entirely attacker-crafted, and the sequential processing order in `extractTarToDirectory` is exactly as required (directory/symlink creation before consumption), making it reliably repeatable.

### Recommendation
Do not derive the "current real directory" for validation purposes from a lexical `filepath.Dir`/`filepath.Join` of the declared header name. Instead, resolve/track the real path incrementally as each entry is created (e.g., using `filepath.EvalSymlinks` on the already-created ancestor chain, or maintaining an internal map of created symlinks and resolving through it), and reject entries whose real resolved location is outside `targetDir`. Alternatively, disallow any tar entry (dir, file, symlink, hardlink) whose `header.Name` traverses a directory component that was created as a symlink earlier in the same archive — i.e., forbid symlinked directories as intermediate path components entirely (only allow symlinks as terminal/leaf entries), which removes the discrepancy between lexical and real resolution.

### Proof of Concept
```go
func TestExtractTarToDirectory_SymlinkDirChainEscape(t *testing.T) {
	targetDir := t.TempDir()
	outsideDir := filepath.Dir(targetDir) // parent of targetDir; simulates storage escape target

	var buf bytes.Buffer
	tw := tar.NewWriter(&buf)

	// 1. Create "real" dir (unused directly, just fills structure)
	require.NoError(t, tw.WriteHeader(&tar.Header{Name: "real", Typeflag: tar.TypeDir, Mode: 0o755}))

	// 2. "a" -> "." : symlink pointing back to targetDir root (passes lexical check)
	require.NoError(t, tw.WriteHeader(&tar.Header{Name: "a", Typeflag: tar.TypeSymlink, Linkname: ".", Mode: 0o777}))

	// 3. "a/b/link" -> "../../evil" : lexical Dir("targetDir/a/b") + "../../evil" = "targetDir/evil" (inside, passes)
	//    but real path is "targetDir/b/link" (since "a" resolves to targetDir), so real target is
	//    parent(targetDir)/evil once dereferenced.
	require.NoError(t, tw.WriteHeader(&tar.Header{Name: "a/b/link", Typeflag: tar.TypeSymlink, Linkname: "../../evil", Mode: 0o777}))

	// 4. Write through the symlink chain: "a/b/link/payload"
	payload := []byte("pwned")
	require.NoError(t, tw.WriteHeader(&tar.Header{
		Name: "a/b/link/payload", Typeflag: tar.TypeReg, Mode: 0o644, Size: int64(len(payload)),
	}))
	_, err := tw.Write(payload)
	require.NoError(t, err)
	require.NoError(t, tw.Close())

	s := &server{logger: testhelper.NewLogger(t)}
	err = s.extractTarToDirectory(context.Background(), &buf, targetDir)
	// Expect: either the extraction should fail with an escape error, or (demonstrating the bug)
	// the file lands outside targetDir:
	evilPath := filepath.Join(outsideDir, "evil", "payload")
	_, statErr := os.Lstat(evilPath)
	require.NoError(t, statErr, "file was written outside targetDir, confirming the escape")
}
```
This test demonstrates that `evil/payload` is created under `parent(targetDir)` rather than confined under `targetDir`, violating the "paths stay inside the storage" invariant.
