### Title
Unverified attachment content is persisted by `AttachmentsDownloader::run` without confirming it matches any queued `AttachmentInstance.content_hash` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
When `AttachmentsBatchStateMachine::Done` is reached, `AttachmentsDownloader::run` iterates over every downloaded `Attachment` and unconditionally calls `network.atlasdb.insert_instantiated_attachment(&attachment)`, regardless of whether `find_all_attachment_instances(&attachment.hash())` returned any confirmed on-chain commitment for that hash. A malicious/faulty peer selected to serve an `AttachmentRequest` can therefore return attacker-chosen content whose hash does not correspond to the content_hash that was actually requested, and that content gets permanently written into the node's `AtlasDB` `attachments` table.

### Finding Description
In `stackslib/src/net/atlas/download.rs`, `extend_with_attachments` decodes the HTTP response via `response.decode_atlas_get_attachment()` and inserts `response.attachment` into a `HashSet<Attachment>` with no verification that `response.attachment.hash()` equals the content_hash that was originally requested from that peer [1](#0-0) .

Later, in `AttachmentsDownloader::run`, the `Done` branch drains this set and, for each attachment, first queries `find_all_attachment_instances(&attachment.hash())` but then calls `insert_instantiated_attachment(&attachment)` unconditionally — the result of the lookup is only used afterward to build `resolved_attachments`, never to gate the `insert_instantiated_attachment` call itself: [2](#0-1) 

`insert_instantiated_attachment` performs an `INSERT OR REPLACE` into the `attachments` table with `was_instantiated = 1` unconditionally: [3](#0-2) 

Because the row is written with `was_instantiated = 1`, it is not even part of the "uninstantiated" bucket that `evict_expired_uninstantiated_attachments` and `count_uninstantiated_attachments` track (`WHERE was_instantiated = 0`) [4](#0-3) . So this write path is not merely missing the "confirmed commitment" check the question describes — it fully bypasses the "uninstantiated" pool/eviction bookkeeping entirely, persisting arbitrary attacker content indefinitely as if it were validated data.

The only place a "match" between attachment and instance is later established is `find_all_attachment_instances`, which does a straight hash lookup against `attachment_instances` rows already marked `Checked` [5](#0-4) . This lookup happening or not does not affect whether the bogus attachment gets stored.

### Impact Explanation
Any peer that a victim node selects as an outbound "atlas sync" peer for a legitimate `AttachmentRequest` (i.e., normal Atlas attachment-fetch flow driven by real on-chain BNS attachment events being queued) can respond with attacker-chosen bytes unrelated to the requested content_hash. This bytes blob gets committed to the victim's `AtlasDB` `attachments` table as `was_instantiated = 1`, permanently (it is not subject to the uninstantiated-eviction sweep), constituting an unauthenticated write of arbitrary content into node state with no relationship to any confirmed on-chain commitment. Repeated across many distinct `AttachmentRequest`s, this allows unbounded disk growth on the victim, matching the Critical category "unauthenticated write to state."

### Likelihood Explanation
The attacker must be selected by the victim as an outbound peer serving Atlas attachment downloads — achievable by simply running a normal peer node and being included in the victim's peer set, which requires no secret/privileged role. The victim must have at least one pending `AttachmentInstance` queued from real chain activity to trigger an `AttachmentRequest` to that peer, which is a routine occurrence on any node tracking BNS/Atlas attachments. The attacker's cost per exploited write is a single crafted HTTP response.

### Recommendation
In `AttachmentsDownloader::run`, only call `insert_instantiated_attachment` when `find_all_attachment_instances(&attachment.hash())` is non-empty (i.e., the attachment actually corresponds to a `Checked` on-chain instance), or otherwise verify `attachment.hash()` matches the content_hash that was requested from that specific peer before accepting/storing the response in `extend_with_attachments`.

### Proof of Concept
A Rust test in `stackslib/src/net/atlas/tests.rs` (or a new module) could:
1. Construct two `AtlasDB` instances and a `PeerNetwork`-like harness with a queued `AttachmentInstance` for hash `H1`.
2. Stub an `AttachmentRequest` peer response that returns an `Attachment{content: b"malicious"}` whose hash `H2 != H1`.
3. Drive `AttachmentsBatchStateMachine` to `Done` via `extend_with_attachments`, then call `AttachmentsDownloader::run`.
4. Assert `atlasdb.find_attachment(&H2).unwrap().is_some()` succeeds (bogus content persisted) while `atlasdb.find_all_attachment_instances(&H2).unwrap().is_empty()` (no confirmed commitment ever existed for `H2`), demonstrating the write proceeded despite zero on-chain corroboration.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    pub fn evict_expired_uninstantiated_attachments(&mut self) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let cut_off = now - self.atlas_config.uninstantiated_attachments_expire_after as i64;
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE was_instantiated = 0 AND created_at < ?",
            params![cut_off],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
