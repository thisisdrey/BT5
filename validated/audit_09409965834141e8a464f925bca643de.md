### Title
Insufficient validation of client-supplied `timeout` on `FetchRemote` allows unbounded RPC execution - (File: internal/gitaly/service/repository/fetch_remote.go)

### Summary
`FetchRemoteRequest.timeout` is an attacker/client-controlled `int32` field that is only honored when it is strictly greater than zero. A zero, negative, or omitted value silently disables any Gitaly-side time bound on the fetch operation, mirroring the "vesting `duration`/`halfLife` can be zero" class of bug where an unvalidated numeric constructor/config argument that should express a mandatory bound is instead allowed to take a degenerate value that disables the intended restriction entirely.

### Finding Description
In `FetchRemote`, the RPC handler only wraps the context with a deadline conditionally: [1](#0-0) 

```go
func (s *server) FetchRemote(ctx context.Context, req *gitalypb.FetchRemoteRequest) (*gitalypb.FetchRemoteResponse, error) {
	if err := s.validateFetchRemoteRequest(ctx, req); err != nil {
		return nil, err
	}

	if req.GetTimeout() > 0 {
		var cancel context.CancelFunc
		ctx, cancel = context.WithTimeout(ctx, time.Duration(req.GetTimeout())*time.Second)
		defer cancel()
	}
	...
```

The `timeout` field is declared as a plain, unbounded `int32` in the proto with no documented minimum/maximum and no server-side validation of the value before use: [2](#0-1) 

Because the check is `> 0`, both `timeout == 0` (the default/unset value) and any negative value skip the `context.WithTimeout` branch entirely, leaving the fetch bound only by whatever deadline (if any) the calling client set on the outer gRPC context. The subsequent `fetchRemoteAtomic` then performs a `git fetch` against an attacker/caller-controlled remote (`RemoteParams`), creates a quarantine directory, and holds open subprocesses, file descriptors, and quarantine storage for the duration of the fetch: [3](#0-2) 

If the remote endpoint is slow, hangs, or streams data indefinitely (an SSH/HTTP remote fully controlled by the caller via `remote_params`/`ssh_key`/`known_hosts`), and the caller/gRPC deadline is likewise unbounded or very large, the RPC handler, its `git-fetch` subprocess, and the quarantine directory remain alive with no Gitaly-enforced upper bound — this is a resource-exhaustion path directly analogous to the "zero duration bypasses restriction" bug class: the field that is supposed to impose a mandatory time bound can be nulled out by supplying a degenerate value (0 or negative), and there is no validation rejecting that input.

### Impact Explanation
This is a DoS vector against an RPC handler: an unbounded/slow fetch against a caller-supplied remote can hold a `git-fetch` subprocess, network connection, quarantine directory, and associated goroutines open indefinitely, consuming file descriptors, memory, and process slots on the Gitaly node. Because `FetchRemote` is a mutator RPC that legitimately accepts caller-supplied timeout, remote URL/params, SSH key, and known-hosts, a caller that intentionally supplies `timeout: 0` (or a negative value) together with a remote that never completes negotiation can extend resource consumption well beyond what the timeout field was designed to bound.

### Likelihood Explanation
Reaching this requires only calling the `FetchRemote` RPC with a crafted request (`timeout` unset/0/negative plus attacker-influenced `remote_params`), which is a standard, documented, reachable field of the RPC — no privileged Gitaly access is needed beyond whatever access is already required to invoke `FetchRemote` (a MUTATOR-classified RPC used e.g. for repository mirroring). No token leakage, MITM, or internal network access is required; the caller directly controls the vulnerable field.

### Recommendation
Validate `FetchRemoteRequest.timeout` in `validateFetchRemoteRequest` (or in `FetchRemote` itself) so that a value of `0` maps to a safe default timeout rather than "no timeout," reject negative values with `InvalidArgument`, and enforce a sane upper bound to prevent excessively long-running fetches. This mirrors adding "sensible lower and upper bounds" to the vesting contract's constructor arguments.

### Proof of Concept
1. Call `FetchRemoteRequest` with `timeout: 0` (or a negative integer) and `remote_params` pointing to an endpoint that accepts the connection but never completes the Git fetch negotiation (e.g., a TCP listener that stalls after the initial handshake).
2. Observe that `req.GetTimeout() > 0` evaluates false, so no `context.WithTimeout` is applied by `FetchRemote`.
3. The RPC handler's `git-fetch` subprocess and quarantine directory remain active until the underlying connection/subprocess is killed by some other mechanism (or indefinitely, if the caller's own gRPC deadline is also large/unset), consuming Gitaly server resources for the duration.

Note: I could not fully verify within the available searches whether an additional, independent gRPC-server-wide deadline (e.g., a global interceptor timeout) is enforced for all RPCs in this codebase, which would partially mitigate the impact; this would need to be confirmed by inspecting `internal/gitaly/server/` interceptor setup in a full session.
