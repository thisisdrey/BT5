### Title
Unbounded recursion in `debug/dwarf` type resolution causes stack overflow on malicious DWARF debug info - ([File: src/debug/dwarf/type.go])

### Summary
`Data.Type()` / `Data.readType()` in `debug/dwarf` recursively walks a DWARF type graph to resolve `AttrType` references (pointer, const/volatile/restrict qualifiers, arrays, typedefs, struct members, function parameters/return types) with no bound on recursion depth. The only safeguard is a `typeCache` that prevents infinite recursion on *cycles*, but it does nothing to limit the depth of a long, non-cyclic chain of distinct type DIEs (e.g., thousands of nested `DW_TAG_const_type`/`DW_TAG_pointer_type`/`DW_TAG_typedef` entries each pointing to the next). A crafted ELF/Mach-O/PE binary containing such a chain in its `.debug_info` section can drive `readType` into deep, unbounded Go-stack recursion, crashing the process with a stack overflow. This mirrors the pattern in the report: a recursive tree-walker over parser-produced, attacker-controlled structure with no depth guard.

### Finding Description
Attacker input is a crafted debug-info binary (ELF/Mach-O/PE with a `.debug_info`/`.debug_abbrev` section) consumed by a normal victim workflow that inspects binaries — e.g. symbolizers, profilers, `go tool objdump`/`nm`-style tools, or debuggers built on `debug/dwarf` and `debug/elf`.

- Entry point: `(*Data).Type(off Offset)` [1](#0-0) , which calls the internal `readType`.
- Core recursive function: `(*Data).readType` [2](#0-1) . For each qualifier/pointer/array/typedef/struct-member/function-parameter case, it calls the closure `typeOf`, which itself calls `d.readType(...)` again for the referenced `AttrType` offset [3](#0-2) .
- Failed check: the function only guards against **cycles** via `typeCache[off]` — a type is added to the cache *before* recursing into its children, so a DIE that eventually refers back to itself (directly or indirectly) short-circuits. But a long acyclic chain of unique offsets (e.g. `const→const→const→…→pointer→typedef→base`) each has a distinct offset, so the cache never intercepts it and `readType` recurses once per DIE in the chain, e.g. via the `TagConstType`/`TagVolatileType`/`TagRestrictType` [4](#0-3)  or `TagPointerType` [5](#0-4)  cases.
- Sink: unbounded native Go call-stack growth inside `readType`, eventually exceeding the goroutine stack limit and causing a runtime stack-overflow crash (fatal, unrecoverable panic), not merely a returned error.

This is structurally the same bug class as `SIccCalcOp::ArgsUsed()` in iccDEV: a tree-shaped, attacker-controlled intermediate representation is walked recursively by a "does this node's data need X" traversal, with cycle protection but no depth cap, so a sufficiently long (not necessarily cyclic) chain overflows the native stack.

### Impact Explanation
A successful crafted binary causes an unrecoverable runtime crash (SIGSEGV/stack overflow) of any Go process that calls `debug/dwarf.Type` (directly or via `debug/elf`, `debug/macho`, `debug/pe` DWARF helpers) on attacker-supplied binary/debug data — this is a availability/DoS impact (no C/I, matching the CVSS profile of the cited analog: `AV:L/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H`). Under Go's security-response taxonomy this would be evaluated on the PUBLIC track as a parser-crash/DoS in the standard library, since it is a plausible malicious-input parser panic in a package meant to safely parse untrusted debug information, not a build-execution or generic-resource-exhaustion issue.

### Likelihood Explanation
The victim workflow is any tool that parses untrusted or third-party binaries and extracts debug type info — e.g., binary analysis/security tooling, symbolizers, crash-report processors, or delve-like debuggers built on `debug/dwarf`. The attacker only needs to supply a binary (unauthenticated/normal file input); no privileged access, credentials, or malicious-server control is required. Building such a pathological chain of DWARF type DIEs is straightforward with any DWARF-writing tool or by hand-crafting `.debug_info`/`.debug_abbrev` bytes.

### Recommendation
Add an explicit recursion-depth counter (or an equivalent iterative/worklist-based rewrite) to `readType`, similar to the `maxNestingDepth`/`maxIgnoreNestingDepth`/`incNestLev` patterns already used elsewhere in the standard library (e.g. `encoding/json`, `encoding/gob`, `go/parser`, `regexp/syntax`), and return a `DecodeError` once a reasonable maximum chain length is exceeded instead of recursing unbounded.

### Proof of Concept
Because `debug/dwarf`'s DIE/abbrev encoding is internal, the PoC is expressed as a package-level (`package dwarf`) test that synthesizes a long acyclic chain of `TagConstType` DIEs, each pointing to the next, and calls `Type` on the outermost offset — analogous to the existing `TestTypedefCycle` test but using a long non-cyclic chain instead of a cycle:

```go
// file: src/debug/dwarf/type_stackoverflow_test.go (package dwarf)
func TestReadTypeDeepChainStackOverflow(t *testing.T) {
    const chainLen = 200000 // deep enough to exceed default goroutine stack

    // Build .debug_abbrev with a single abbrev code for DW_TAG_const_type
    // that has AttrType (form ref4) and no children.
    abbrev := buildConstTypeAbbrev(t)

    // Build .debug_info containing `chainLen` DW_TAG_const_type DIEs,
    // where DIE[i].AttrType == offset(DIE[i+1]), and the last DIE
    // references a DW_TAG_base_type DIE.
    info, headOff := buildLongConstChain(t, chainLen)

    d, err := New(abbrev, nil, nil, info, nil, nil, nil, nil)
    if err != nil {
        t.Fatal(err)
    }

    // Expected (buggy) behavior: this call recurses `chainLen` times inside
    // readType/typeOf and crashes the process with a stack overflow instead
    // of returning a bounded/graceful error.
    _, err = d.Type(headOff)
    if err != nil {
        t.Fatalf("expected either success or a graceful DecodeError, got crash risk instead: %v", err)
    }
}
```

Expected assertion after a fix: `d.Type(headOff)` should return a `DecodeError` such as `"type chain too deep"` (or succeed within a bounded stack) for arbitrarily long attacker-supplied chains, rather than crashing the process via unbounded native recursion.

**Note on verification limits:** I was not able to fully hand-encode a byte-accurate `.debug_abbrev`/`.debug_info` fixture within this analysis (helper functions `buildConstTypeAbbrev`/`buildLongConstChain` are illustrative placeholders for the DWARF byte encoding, which is intricate). The reachability and missing-depth-guard analysis of `readType`/`typeOf` in [6](#0-5)  is confirmed directly from source; a Devin session with file/terminal access would be needed to construct and run the exact byte-level DWARF fixture and observe the crash empirically.

// readType reads a type from r at off of name. It adds types to the
// type cache, appends new typedef types to typedefs, and computes the
// sizes of types. Callers should pass nil for typedefs; this is used
// for internal recursion.
func (d *Data) readType(name string, r typeReader, off Offset, typeCache map[Offset]Type, fixups *typeFixer) (Type, error) {
	if t, ok := typeCache[off]; ok {
		return t, nil
	}
	r.Seek(off)
	e, err := r.Next()
	if err != nil {
		return nil, err
	}
	addressSize := r.AddressSize()
	if e == nil || e.Offset != off {
		return nil, DecodeError{name, off, "no type at offset"}
	}

	// If this is the root of the recursion, prepare to resolve
	// typedef sizes and perform other fixups once the recursion is
	// done. This must be done after the type graph is constructed
	// because it may need to resolve cycles in a different order than
	// readType encounters them.
	if fixups == nil {
		var fixer typeFixer
		defer func() {
			fixer.apply()
		}()
		fixups = &fixer
	}

	// Parse type from Entry.
	// Must always set typeCache[off] before calling
	// d.readType recursively, to handle circular types correctly.
	var typ Type

	nextDepth := 0

	// Get next child; set err if error happens.
	next := func() *Entry {
		if !e.Children {
			return nil
		}
		// Only return direct children.
		// Skip over composite entries that happen to be nested
		// inside this one. Most DWARF generators wouldn't generate
		// such a thing, but clang does.
		// See golang.org/issue/6472.
		for {
			kid, err1 := r.Next()
			if err1 != nil {
				err = err1
				return nil
			}
			if kid == nil {
				err = DecodeError{name, r.offset(), "unexpected end of DWARF entries"}
				return nil
			}
			if kid.Tag == 0 {
				if nextDepth > 0 {
					nextDepth--
					continue
				}
				return nil
			}
			if kid.Children {
				nextDepth++
			}
			if nextDepth > 0 {
				continue
			}
			return kid
		}
	}

	// Get Type referred to by Entry's AttrType field.
	// Set err if error happens. Not having a type is an error.
	typeOf := func(e *Entry) Type {
		tval := e.Val(AttrType)
		var t Type
		switch toff := tval.(type) {
		case Offset:
			if t, err = d.readType(name, r.clone(), toff, typeCache, fixups); err != nil {
				return nil
			}
		case uint64:
			if t, err = d.sigToType(toff); err != nil {
				return nil
			}
		default:
			// It appears that no Type means "void".
			return new(VoidType)
		}
		return t
	}
