### Title
Meta-transaction griefing: a `SignedDelegateAction`'s nonce is consumed independent of relayer identity or inner-action success, allowing frontrunning of a user's `DelegateAction` - (File: runtime/runtime/src/actions.rs)

### Summary
NEAR's meta-transaction mechanism (NEP-366) has the same two-phase structure as the Permit2Proxy bug: a user signs an authorization (a `SignedDelegateAction`) that is later wrapped and submitted on-chain by a third party (a relayer). Just like `ERC20.permit`, the `SignedDelegateAction`'s signature does not bind to who submits it — any account can wrap the *exact same* signed payload in its own outer `SignedTransaction` and get it processed first. Because `nonce` consumption for the delegate action happens as its own independent, unconditionally-successful step (spawning the inner-action receipt), a frontrunner can consume the user's access-key/gas-key nonce ahead of the honest relayer, causing the honest relayer's identical resubmission to permanently fail with `DelegateActionInvalidNonce` — mirroring the "permit already used" griefing described in the report.

### Finding Description
A `DelegateAction` contains `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key`, but no field binding it to a particular relayer/outer signer: [1](#0-0) 

The relayer only wraps this pre-signed struct inside its own transaction and pays gas/deposit: [2](#0-1) 

On execution, `apply_delegate_action` verifies the signature, expiry, and sender match, then calls `validate_delegate_action_key`, which validates and **advances the nonce**, and finally spawns a brand-new receipt carrying the inner actions — this spawning step is unconditionally treated as the delegate-action's success, decoupled from whether the newly spawned receipt (the actual intended effect) ever succeeds: [3](#0-2) 

The nonce-consuming validation itself: [4](#0-3) [5](#0-4) 

The code's own comment acknowledges the asymmetry between nonce/fee commitment and eventual execution outcome: "Relayer prepaid all fees... If something goes wrong, deposit is refunded... Relayer should verify DelegateAction before submitting it": [6](#0-5) 

Because the signature does not commit to a specific relayer, any third party who observes a pending `SignedDelegateAction` (e.g., in the network's transaction pool while it is in flight to its intended relayer) can copy it verbatim and submit it wrapped in their own transaction. Once processed, this permanently advances the sender's nonce (or gas-key nonce), exactly as demonstrated by the existing replay test, which shows that replaying the same `SignedDelegateAction` after its nonce has been consumed once fails with `DelegateActionInvalidNonce`: [7](#0-6) 

If the honest, intended relayer's transaction (containing the identical `SignedDelegateAction`) was already broadcast and gets included after the attacker's copy, it will fail on-chain with `DelegateActionInvalidNonce`, after the relayer's outer transaction has already paid to purchase gas for it — the relayer loses the gas cost of a transaction that fails purely due to nonce invalidation, and the user's intended meta-transaction (as submitted to their chosen/trusted relayer) never has its inner actions executed via that relayer. This directly parallels the report's frontrunning pattern: the attacker copies "the permit information" (here, the `SignedDelegateAction`), submits it independently, and voids the victim's original, in-flight submission with no direct profit to the attacker beyond griefing.

### Impact Explanation
This is a griefing/denial-of-service vector, not a fund-theft vector: no tokens are stolen directly by the attack itself, and if the attacker submits the payload unmodified the sender's intended inner actions might still execute (paid for by the attacker instead). The concrete harm is:
- The user's chosen relayer's transaction is invalidated (`DelegateActionInvalidNonce`) after gas has already been purchased/burnt for it, imposing a monetary loss on that relayer.
- The user's authorized action becomes unusable via the intended relayer/pathway, requiring the user to re-sign a fresh `DelegateAction` with a new nonce — a repeatable denial-of-service against any specific relayer-user meta-transaction flow.
- If an attacker crafts scenarios where the inner receipt's execution is expected to fail for the sender at the time of the front-run submission (e.g., insufficient balance/allowance/state at that moment), the nonce is still permanently burned with no beneficial effect delivered to the sender, matching the report's "prevent the transaction from succeeding" scenario exactly.

This matches the report's stated low-risk griefing classification rather than direct fund theft.

### Likelihood Explanation
Exploitability requires only that an attacker can observe a pending `SignedDelegateAction` before it is included on-chain (e.g., via public mempool/relayer visibility or interception of the off-chain hand-off to the relayer) and have funds to cover the outer transaction's gas/deposit costs — no privileged access or validator/node compromise is required, consistent with the "unprivileged signer" analog constraints. This is a standard front-running race condition inherent to the current `DelegateAction` design, and the codebase's own comments and tests confirm the nonce-consumption/execution-decoupling behavior exists as documented, unmitigated behavior.

### Recommendation
Consider one or more of:
- Binding a `SignedDelegateAction` (optionally) to a specific relayer account or outer transaction signer, so only the intended relayer's submission is valid, preventing a third party from replaying a captured signed payload.
- Avoiding unconditional nonce advancement when the freshly spawned inner-action receipt is virtually guaranteed to fail for reasons known at admission time.
- Documenting/warning relayers and wallet SDKs that submitting a witnessed `SignedDelegateAction` from the mempool by a third party is possible, and encouraging short `max_block_height` windows to limit the exposure window.

### Proof of Concept
1. Alice signs a `DelegateAction{sender_id: alice, receiver_id: ft_contract, actions: [ft_transfer(john, 10)], nonce: N, max_block_height: H, public_key: pk}` and hands the resulting `SignedDelegateAction` off-chain to Relayer R.
2. R broadcasts an outer `SignedTransaction` wrapping this `SignedDelegateAction` (signer = R, receiver = alice).
3. Attacker A observes this pending transaction (e.g., via the tx pool) before it is included, copies the identical `SignedDelegateAction`, and broadcasts their own outer `SignedTransaction` (signer = A, receiver = alice) wrapping the same payload, with sufficient gas/priority to be included first.
4. A's transaction is processed: `apply_delegate_action`/`validate_delegate_action_key` (runtime/runtime/src/actions.rs:437-518, 558-730) validate signature/nonce and advance Alice's access-key nonce to N, spawning the inner `ft_transfer` receipt (which A paid for).
5. R's originally broadcast transaction, containing the same `SignedDelegateAction` (nonce N), is subsequently included and fails at `validate_delegate_action_key` with `DelegateActionInvalidNonce` (mirroring `test_gas_key_delegate_v2_meta_transaction`'s replay assertion at test-loop-tests/src/tests/gas_keys.rs:274-296), even though R already paid to purchase gas for this receipt.

struct DelegateAction {
    /// Signer of the delegated actions
    pub sender_id: AccountId,
    /// Receiver of the delegated actions.
    pub receiver_id: AccountId,
    /// List of actions to be executed.
    ///
    /// With the meta transactions MVP defined in NEP-366, nested
    /// DelegateActions are not allowed. A separate type is used to enforce it.
    pub actions: Vec<NonDelegateAction>,
    /// Nonce to ensure that the same delegate action is not sent twice by a
    /// relayer and should match for given account's `public_key`.
    /// After this action is processed it will increment.
    pub nonce: Nonce,
    /// The maximal height of the block in the blockchain below which the given DelegateAction is valid.
    pub max_block_height: BlockHeight,
    /// Public key used to sign this delegated action.
    pub public_key: PublicKey,
}

```markdown
With meta transactions, Alice can create a `DelegateAction`, which is very
similar to a transaction. It also contains a list of actions to execute and a
single receiver for those actions. She signs the `DelegateAction` and forwards
it (off-chain) to a relayer. The relayer wraps it in a transaction, of which the
relayer is the signer and therefore pays the gas costs. If the inner actions
have an attached token balance, this is also paid for by the relayer.

On chain, the `SignedDelegateAction` inside the transaction is converted to an
action receipt with the same `SignedDelegateAction` on the relayer's shard. The
receipt is forwarded to the account from `Alice`, which will unpacked the
`SignedDelegateAction` and verify that it is signed by Alice with a valid Nonce
etc. If all checks are successful, a new action receipt with the inner actions
as body is sent to `FT`. There, the `ft_transfer` call finally executes.

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }

    // Generate a new receipt from DelegateAction.
    let new_receipt = Receipt::V0(ReceiptV0 {
        predecessor_id: sender_id.clone(),
        receiver_id: delegate_action.receiver_id().clone(),
        receipt_id: CryptoHash::default(),

        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: action_receipt.signer_id().clone(),
            signer_public_key: action_receipt.signer_public_key().clone(),
            gas_price: action_receipt.gas_price(),
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: delegate_action.get_actions(),
        }),
    });

    // Note, Relayer prepaid all fees and all things required by actions: attached deposits and attached gas.
    // If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction.
    // Gas is refunded to the signer, this is Relayer.
    // Some contracts refund the deposit. Usually they refund the deposit to the predecessor and this is sender_id/Sender from DelegateAction.
    // Therefore Relayer should verify DelegateAction before submitting it because it spends the attached deposit.

    let prepaid_send_fees = total_prepaid_send_fees(&apply_state.config, action_receipt.actions())?;
    let required_cost = receipt_required_cost(apply_state, &new_receipt)?;
    // This gas will be burnt by the receiver of the created receipt.
    // Compute costs of that are not relevant at this point, the "used" gas is
    // only reserved for execution later, potentially on a different shard.
    result.gas_used = result.gas_used.checked_add_result(required_cost.gas)?;
    // This gas was prepaid on Relayer shard. Need to burn it because the receipt is going to be sent.
    // gas_used is incremented because otherwise the gas will be refunded. Refund function checks only gas_used.
    result.gas_used = result.gas_used.checked_add_result(prepaid_send_fees.gas)?;
    result.gas_burnt = result.gas_burnt.checked_add_result(prepaid_send_fees.gas)?;
    result.compute_usage = safe_add_compute(result.compute_usage, prepaid_send_fees.compute)?;
    result.new_receipts.push(new_receipt);

    Ok(())
```
