Based on my review of the Go standard library's HTTP client stack and the module-fetching code path, I don't find a reachable analog to this vulnerability class in `golang/go`.

Key findings:

1. **`net/http.Transport.roundTrip`** explicitly whitelists only `http`/`https` schemes before dispatching to a connection — any other scheme (including `file://`, `ftp://`, `data:`) is rejected with `"unsupported protocol scheme"` unless the caller has explicitly called `Transport.RegisterProtocol` to opt in. [1](#0-0)  This is the opposite of the reported PyJWT flaw — Go's default HTTP client already behaves like the "safe" libraries cited in the report (jose, keyfunc, IdentityModel, NimbusJwtDecoder), rejecting non-HTTP(S) schemes by default rather than silently accepting them.

2. `http.NewFileTransport` / `fileTransport` for the `file` protocol exists in the standard library, but it must be explicitly registered by the caller via `Transport.RegisterProtocol("file", ...)` — it is never wired in by default. [2](#0-1)  This is deliberate opt-in behavior, not an attacker-triggerable default.

3. The one place in this repository where `file://` URLs are accepted for fetching data is `cmd/go`'s module proxy resolution (`GOPROXY`), which explicitly documents and permits `file:///` proxy URLs as an intentional feature of the GOPROXY protocol. [3](#0-2) [4](#0-3)  However, `GOPROXY` is local environment/configuration under the victim's own control, not a value derived from unauthenticated, attacker-supplied network input (unlike the `jku` header in the PyJWT scenario). This falls outside the rules' attacker model, which excludes host/environment control as the premise.

No other JWK/JWT-fetching primitive exists in the Go standard library (Go has no bundled JWT/JWKS client), and I found no HTTP-client code path reachable from unauthenticated/attacker-supplied input that accepts non-HTTP(S) schemes for a trust decision.
