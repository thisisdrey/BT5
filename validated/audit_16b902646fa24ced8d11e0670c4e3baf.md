### Title
Deleting an account with a non-existent `beneficiary_id` permanently burns the account's remaining balance - (File: `runtime/runtime/src/actions.rs`)

### Summary
The `DeleteAccountAction` beneficiary field is only checked for account-ID **format** validity, never for account **existence**, before the runtime unconditionally schedules a balance-refund receipt to it. This is the same bug class as the reported Aave issue (no check that a target address is actually usable before sending value to it), and it results in silent, permanent loss of the deleted account's remaining NEAR balance.

### Finding Description
When a `DeleteAccount` action is validated, `validate_delete_action` only calls `validate_action_account_id(&action.beneficiary_id)`, which checks that the string is a syntactically valid `AccountId` — it does not check whether the account exists on-chain. [1](#0-0) 

During execution, `action_delete_account` takes the account's remaining balance and unconditionally pushes a `Receipt::new_balance_refund` addressed to `delete_account.beneficiary_id`, with no existence check on the beneficiary: [2](#0-1) 

Balance-refund receipts are special: they have `predecessor_id == "system"` and are marked `is_refund`. Crucially, implicit account creation (the only mechanism that lets a `Transfer` create a brand-new account) is explicitly disabled for refunds: [3](#0-2) 

The code comment documents this intentionally: "Refunds don't automatically create accounts... Account deletion with beneficiary creates a refund, so it'll not create a new account." [4](#0-3) 

Consequently, if `beneficiary_id` does not correspond to an existing account (including a hex-looking implicit-account ID that was never funded), `check_account_existence` on the refund `Transfer` action fails with `AccountDoesNotExist`. Because this failure occurs on a refund receipt, the deposit is not re-refunded anywhere — it is unconditionally burned: [5](#0-4) 

This is documented protocol behavior ("Refund receipts are free... a failed refund burns its deposit into `other_burnt_amount` rather than refunding"). [6](#0-5) 

### Impact Explanation
Any account owner (or any relayer/dApp constructing a `DeleteAccount` action via a promise, e.g. `promise_batch_action_delete_account`) can specify an arbitrary `beneficiary_id`. If that account does not exist at execution time — due to typo, a beneficiary that was itself deleted between construction and execution, or a not-yet-created implicit account — the entire remaining balance of the deleted account is permanently and irrecoverably burned rather than being transferred or bounced back to the signer. This is a real loss-of-funds bug class: unlike ordinary `Transfer` actions (which either succeed, create an implicit account, or fail the whole transaction with `AccountDoesNotExist` so the sender keeps their funds), `DeleteAccountAction` has no such safety net because the transfer happens via a post-hoc, "free" refund receipt whose failure mode is to burn value instead of reverting or returning it. [7](#0-6) 

### Likelihood Explanation
This path is reachable from an ordinary, unprivileged transaction — no special permissions are required to submit a `DeleteAccount` action, and no protocol invariant currently prevents choosing a nonexistent `beneficiary_id`. The only barrier is user/contract error (mistyped account, race with an account being deleted, or targeting an unfunded/unregistered implicit-style ID), making this plausible in practice, especially in automated flows (e.g., wallet/relayer contracts issuing `DeleteAccount` via Promise API on behalf of users) where the beneficiary is derived programmatically and could reference an account that no longer exists by execution time.

### Recommendation
Before scheduling the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` refers to an existing account (or is eligible for implicit-account creation via a normal, non-refund path). If it does not exist, either reject the `DeleteAccount` action outright (returning an execution error, similar to `AccountDoesNotExist`) or route the balance to a safe fallback (e.g., the predecessor/signer) instead of allowing it to be silently burned by the refund-failure path.

### Proof of Concept
1. Create account `alice.near` with a positive balance.
2. Submit a `DeleteAccount { beneficiary_id: "nonexistent123456".parse().unwrap() }` action on `alice.near`, where `nonexistent123456` is a syntactically valid but never-created account ID.
3. `validate_delete_action` accepts the action (format-only check) — [1](#0-0) .
4. `action_delete_account` deletes `alice.near` and schedules `Receipt::new_balance_refund(beneficiary_id, account_balance)` — [2](#0-1) .
5. When this refund receipt executes, `check_account_existence` fails because `beneficiary_id` doesn't exist and implicit-account creation is disabled for refunds — [3](#0-2) .
6. The failed refund's deposit is added to `other_burnt_amount`, i.e., permanently destroyed — [5](#0-4) .

Note: I was not able to execute this scenario in a live test environment (no sandbox/terminal access); the analysis is based on static tracing of the cited code paths and the project's own documentation of refund-failure burning semantics.
