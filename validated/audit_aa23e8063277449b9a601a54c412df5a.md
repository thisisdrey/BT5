### Title
Unbounded per-account asset map reconstruction (`importAllAsset`) enables denial-of-service via TRC10 token spam - (File: `chainbase/src/main/java/org/tron/core/capsule/utils/AssetUtil.java`)

### Summary
When TRC10 "asset optimization" is enabled, an account's TRC10 balances are stored per-token in a dedicated key-value store (`AccountAssetStore`, keyed by `address || tokenId`) instead of inside the `Account` protobuf. Whenever the full asset map for an account needs to be reconstructed (e.g. to serve it through an API), `AssetUtil.importAllAsset` reads and rebuilds a `Map<String, Long>` containing **every asset entry ever recorded for that address**, with no bound on the number of distinct tokens. [1](#0-0) 

### Finding Description
`importAllAsset(Account account)` calls `accountAssetStore.getAllAssets(account)`, which performs a full scan of all `address || tokenId` entries for the given address and materializes them into a `HashMap`, then rebuilds the `Account` protobuf's `AssetV2` map from that result. [1](#0-0) 

The number of distinct entries under a victim address is entirely attacker-controlled: TRC10 token issuance (`AssetIssueContract`) is permissionless (any account can issue a new token by paying the standard issuance fee), and `TransferAssetContract`/`TransferAssetActuator` lets anyone send an arbitrary self-issued token in any (even dust) amount to any target address, creating a brand-new `address || tokenId` entry in `AccountAssetStore` for the victim. [2](#0-1) 

By repeatedly issuing new tokens and transferring tiny amounts to the same target address, an attacker can grow that address's asset-entry count arbitrarily. Any subsequent call to `importAllAsset` for that address (used by account-query code paths, e.g. via `Wallet`) must iterate over the entire accumulated set in a single call, with cost proportional to the number of assets an attacker chose to spam — this is the same "unbounded loop over externally-growable list" pattern flagged in the source report (`_accumulateInternalRewards`/`_accumulateExternalRewards` looping over an unbounded reward-token array).

### Impact Explanation
Because `importAllAsset` is used to serve account balance data, an attacker can inflate the per-request cost of querying any address they choose to target (including their own address, or third-party addresses they can freely send dust TRC10 transfers to) by orders of magnitude. Since this reconstruction happens on the read/query path (not gated by a transaction's own energy/fee metering the way EVM execution would be), repeated or automated queries against an address with a bloated asset set can consume excessive CPU/memory on the node serving the request, degrading or denying that API's availability — a concrete "API the node can no longer serve" style impact.

### Likelihood Explanation
Likelihood is moderate-to-high: issuing a TRC10 token and sending a minimal amount to a target address are both ordinary, permissionless operations available to any account holder, requiring only the standard TRC10 issuance fee and bandwidth/fee for transfers, with no cap on how many distinct tokens can be sent to one address over time. An attacker with a comparatively modest amount of capital/time can incrementally build up a very large asset set for a target address before triggering (or waiting for others to trigger) the expensive read path.

### Recommendation
Bound or paginate `AccountAssetStore.getAllAssets`/`AssetUtil.importAllAsset`, e.g. by capping the number of distinct TRC10 asset entries an account may accumulate, or by avoiding full-map materialization in favor of streaming/paginated reads for query paths, and consider charging a fee or bandwidth cost proportional to the number of distinct assets held by the recipient in `TransferAssetActuator` when a new asset entry would be created for that account.

### Proof of Concept
1. Attacker issues N distinct TRC10 tokens via `AssetIssueContract`, each requiring only the standard issuance fee.
2. Attacker submits N `TransferAssetContract` transactions, sending a minimal (or zero-adjacent) amount of each distinct token to the same target address, each of which creates a new `address || tokenId` entry in `AccountAssetStore` through `TransferAssetActuator.execute` → `addAssetAmountV2` / `importAsset`. [3](#0-2) 
3. Any subsequent invocation of `AssetUtil.importAllAsset` for the target address (used to construct the full asset view of that account) must iterate over all N entries, with cost scaling linearly with attacker-chosen N. [1](#0-0) 

Note: I was able to confirm two call sites of `importAllAsset`/`importAsset` in `framework/src/main/java/org/tron/core/Wallet.java` via search, but the index did not return their exact contents/line numbers, so I could not directly confirm which specific query RPC(s) invoke the full-map reconstruction. Confirming that exact API entry point would require inspecting `Wallet.java` in full (e.g. via a Devin session with full filesystem access) to pin down the precise unauthenticated/low-privilege query path that triggers `importAllAsset`.

  public static Account importAllAsset(Account account) {
    if (!isAllowAssetOptimization()) {
      return account;
    }
    Map<String, Long> map = accountAssetStore.getAllAssets(account);
    return account.toBuilder().clearAssetV2().putAllAssetV2(map).build();
  }
