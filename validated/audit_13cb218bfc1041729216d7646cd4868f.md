### Title
Underflow in `CongestionInfo` gas/byte accounting escalates to a `panic!`, halting the shard's chunk apply - ([File: chain/chain/src/runtime/mod.rs])

### Summary
`CongestionInfo::remove_receipt_bytes` / `remove_buffered_receipt_gas` (`core/primitives/src/congestion_info.rs:256-321`) use `checked_sub` and return `Err(RuntimeError::UnexpectedIntegerOverflow(..))` on underflow, which is correctly propagated with `?` through `forward_from_buffer_to_shard` (`runtime/runtime/src/congestion_control.rs:368-369`) up through `Runtime::apply`. However, the caller in `chain/chain/src/runtime/mod.rs:360-373` explicitly converts this specific error variant into a hard `panic!("RuntimeError::UnexpectedIntegerOverflow {reason}")` rather than a recoverable `Error`. Any prior accounting under-add in this file (buffer/delayed-queue bookkeping) that later causes a `checked_sub` underflow therefore does not fail as a soft per-receipt error — it crashes the node process applying that chunk.

### Finding Description
`remove_receipt_bytes`/`remove_buffered_receipt_gas`/`remove_delayed_receipt_gas` in `core/primitives/src/congestion_info.rs:256-321` are the only accounting-removal primitives and all use `checked_sub().ok_or_else(|| RuntimeError::UnexpectedIntegerOverflow(...))?`. These are called from `ReceiptSinkV2::forward_from_buffer_to_shard` (`runtime/runtime/src/congestion_control.rs:367-369`) and other sites, and propagate as `Result<(), RuntimeError>` via `?` all the way out of `Runtime::apply` (`runtime/runtime/src/lib.rs:1781-1790` returns `Result<ApplyResult, RuntimeError>`).

Critically, `chain/chain/src/runtime/mod.rs:349-373` (the sole caller of `runtime.apply(...)` in the normal node runtime adapter) does:
```
RuntimeError::UnexpectedIntegerOverflow(reason) => {
    panic!("RuntimeError::UnexpectedIntegerOverflow {reason}")
}
```
This is annotated `// TODO(#2152): process gracefully`, confirming the maintainers are aware this is not graceful error handling but a deliberate crash-on-invariant-violation. So *if* an under-accounting bug elsewhere in `congestion_control.rs` (e.g. resharding buffer mismatch, `bootstrap_congestion_info`, `DelayedReceiptQueueWrapper`) causes `receipt_bytes`/`buffered_receipts_gas` to be smaller than what a later `forward_from_buffer_to_shard` or `apply_congestion_changes` call tries to subtract, the underflow does not degrade gracefully — it panics the validator/RPC process that is applying that chunk for that shard.

### Impact Explanation
This confirms the mechanical chain (`checked_sub` → `Err` → `?` propagation → `panic!` at the adapter boundary) exactly as hypothesized: it is a genuine hard crash, not a silent metric error, and would affect every node applying the chunk for that shard (all nodes run identical deterministic logic, so the same underflow occurs everywhere), which is a **liveness/shard-halting** condition — matching the NEP bounty category of a shard-halting panic — *if and only if the underflow precondition can actually be reached*.

### Likelihood Explanation
This finding is **conditional and not independently proven exploitable**. The question's own precondition states that "any of the other described accounting-mismatch scenarios ... has occurred at least once." I did not find, in the code inspected, a concrete unprivileged-attacker-reachable path that causes an under-add to `receipt_bytes`/`buffered_receipts_gas`/`delayed_receipts_gas` — `add_receipt_bytes`/`add_buffered_receipt_gas` are called symmetrically with `remove_*` at every push/pop site I traced (`buffer_receipt` at `congestion_control.rs:466-486`, `DelayedReceiptQueueWrapper` push/pop at `:838`/`:880`), and the spec notes an explicit invariant assertion (`forward_from_buffer`, `congestion_control.rs:282-284`: `assert_eq!(buffered_receipts_gas(), 0)` when all buffers are empty) that would itself trip before a silent drift went unnoticed. Without a demonstrated attacker-triggerable under-add bug (the "sibling accounting call" bug referenced is speculative, not identified), this is a **downstream consequence analysis of a hypothetical bug**, not a standalone vulnerability. Per the rules ("Reject speculative resource-hygiene claims with no reachable mainnet scenario" and "Require exact file/function support... for a concrete loss"), the missing link is a concrete, attacker-controlled input that produces the under-add in the first place.

### Recommendation
N/A as a standalone finding — no fix is proposed here since no concrete triggering bug was identified. If a genuine under-accounting bug is found elsewhere in `congestion_control.rs`, the panic-on-overflow policy at `chain/chain/src/runtime/mod.rs:366-368` (tracked as `TODO(#2152)`) would need to be revisited to fail the chunk gracefully instead of crashing the process, but that policy change is out of scope without an identified root-cause bug.

### Proof of Concept
Not provided — a valid PoC requires first identifying a concrete unprivileged-attacker transaction sequence that produces the under-add precondition (i.e., a real bug in `buffer_receipt`, `DelayedReceiptQueueWrapper`, or `bootstrap_congestion_info` that asymmetrically adds vs. removes). Absent that, a unit test merely constructing `CongestionInfo` with `receipt_bytes=0` and calling `remove_receipt_bytes(1)` only demonstrates the already-documented, intentional `checked_sub`/`panic!` design (`congestion_info.rs:256-265`, `chain/chain/src/runtime/mod.rs:366-368`) — it does not demonstrate attacker reachability.
