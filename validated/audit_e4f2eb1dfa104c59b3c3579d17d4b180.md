### Title
Anti-Replay Window Check-then-Update Race Allows Message Replay Bypass - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement Nebula's per-tunnel anti-replay protection using a `Bits` sliding-window tracker (`bits.go`). Both functions perform a **check** of the message counter, release the lock, do the (comparatively expensive) AEAD decrypt, then re-acquire the lock to **update** the window with that counter. Because the lock is dropped between `Check` and `Update`, two packets carrying the identical `messageCounter` that are processed concurrently by separate reader goroutines can both pass `window.Check()` before either one calls `window.Update()`, defeating the duplicate/replay rejection this window exists to enforce.

### Finding Description

The same check-unlock-decrypt-lock-update shape appears in `VerifyRelay`: [2](#0-1) 

`Bits.Check` only inspects whether the counter has already been marked; it does not itself mark the bit — only `Bits.Update` does that: [3](#0-2) [4](#0-3) 

`readOutsidePackets` (the inbound UDP handler) calls `hostinfo.ConnectionState.Decrypt(...)` on every packet, and multiple UDP reader routines run in parallel against the same `Interface`/`hostMap`, each capable of dispatching an inbound packet for the same `hostinfo`/`ConnectionState`: [5](#0-4) [6](#0-5) 

This means that if an attacker (who does not need to hold a CA-signed certificate, since a replayed packet is just previously-observed ciphertext captured on the wire) sends two copies of the same captured packet at nearly the same time, and they land on different reader goroutines, the following can occur:
1. Goroutine A: `Check(messageCounter)` → true (not yet marked)
2. Goroutine B: `Check(messageCounter)` → true (still not yet marked, A hasn't called `Update` yet)
3. Goroutine A: `DecryptDanger` succeeds, then `Update(messageCounter)` marks it seen
4. Goroutine B: `DecryptDanger` succeeds using the same counter/nonce, then `Update` returns false but the plaintext has already been produced and handed to the caller before the duplicate is detected

Both copies of the packet are decrypted and delivered into `readOutsidePackets`'s subsequent packet-type dispatch before rejection is enforced consistently — this is the same class of defect as the reported issue: a security-relevant value (the "already seen" state of the replay window) is computed under one lock scope, and a costly, non-atomic action (decryption/forwarding) is interposed before the same value is durably updated, so concurrent execution can make decisions against a window state that a competing, "in-flight" evaluation has already invalidated but not yet recorded.

### Impact Explanation
This breaks the confidentiality/integrity guarantee that the replay window is supposed to provide for the data plane: a captured ciphertext packet can be delivered to the tun device / relay-forwarding path more than once. For relay frames this was previously an entire missing-`Update` bug (see `TestRelayReplayProtection`), and while `Update` is now called on both the direct and relay decrypt paths, the lock-drop-and-reacquire pattern still leaves a same-counter race window on any code path where the same `ConnectionState` can be driven concurrently (multiple `listen.routines`/reader goroutines feeding the same tunnel). The net effect is duplicate delivery of already-processed traffic, undermining anti-replay assurances that firewall/conntrack and application logic may implicitly rely on.

### Likelihood Explanation
Exploitation requires only being able to observe/capture one legitimate ciphertext packet on the wire and resend it twice in quick succession while the target runs with more than one inbound UDP reader routine (`listen.routines`/`tun.routines` > 1, a supported and documented configuration) — no valid certificate or handshake participation is needed, only network position to replay bytes. The race window is narrow (a single `DecryptDanger` call) but is fully attacker-triggerable and repeatable, since replayed packets can be sent as many times as desired to win the race.

### Recommendation
Hold `decryptLock` across the entire `Check` → `Decrypt` → `Update` sequence (or otherwise make the check-and-mark atomic, e.g. by having a single call that reserves the counter before decrypting and rolls back the reservation only on decrypt failure) so that no second goroutine can observe an unmarked window state for a counter that is already being processed.

### Proof of Concept
1. Establish a tunnel between two Nebula nodes with `listen.routines` (or `tun.routines`) set to a value > 1 on the receiving node so multiple goroutines call `readOutsidePackets` concurrently.
2. Capture one legitimate encrypted `header.Message` packet sent by the peer (e.g., via `Control.GetFromUDP` in a test harness, mirroring `TestRelayReplayProtection` in `e2e/tunnels_test.go`).
3. Inject the identical captured packet bytes twice back-to-back into the receiver's UDP input (`InjectUDPPacket`) so that they are likely to be picked up by two different reader routines before either completes `ConnectionState.Update`.
4. Observe that under a sufficiently unlucky/forced schedule (e.g., inserting a delay in `DecryptDanger` for testing, or high iteration counts to hit the race), the same message counter is decrypted and delivered to the tun device/application twice, confirming the anti-replay window failed to reject the duplicate.

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
