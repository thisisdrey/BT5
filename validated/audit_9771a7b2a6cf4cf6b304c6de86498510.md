### Title
Missing ownership/authorization check in `LinkRepositoryToObjectPool` allows linking arbitrary repositories to any object pool, enabling cross-repository object disclosure - (File: `internal/gitaly/service/objectpool/link.go`)

### Summary
The external report describes `RewardDistributor.updateAccountReward`/`updateEpoch` as functions meant to be invoked only as an internal step of a larger, validated flow (`claimReward`), but which are exposed with public visibility and no access control, letting any caller invoke them directly and corrupt state that legitimate callers assumed was only reachable through the guarded flow. The analogous pattern in Gitaly is `LinkRepositoryToObjectPool`, an RPC meant to be used only as part of the fork-creation flow (where the object pool is derived from, and known to be authorized for, the specific repository), but which is exposed as a general-purpose RPC that performs no check that the caller-supplied `object_pool` is actually associated with the caller-supplied `repository`.

### Finding Description
`LinkRepositoryToObjectPool` accepts a `repository` and an independently-specified `object_pool` in the request, and both fields are only validated for basic well-formedness/existence: [1](#0-0) 

- `s.locator.ValidateRepository` only checks that `repository` is a valid, existing repository on the configured storage.
- `s.poolForRequest(ctx, req)` (backed by `objectpool.FromProto`) only checks that `object_pool` points to a valid pool-shaped repository: [2](#0-1) 

Neither check verifies any relationship between the two — e.g., that `repository` was forked from the source repository underlying `object_pool`, or that the caller is otherwise authorized to attach to that specific pool. The handler then unconditionally calls `pool.Link(ctx, repo)`, which writes the pool's object directory into `repository`'s `objects/info/alternates` file: [3](#0-2) 

Once linked, Git treats the pool's entire object database as an alternate for `repository`, so any object present in the pool (including objects contributed by other, unrelated forks/repositories that share that pool) becomes readable through `repository` via ordinary read RPCs (e.g. `CommitService`), as demonstrated by the existing `TestLink` test which fetches a pool-only commit through the newly-linked repository: [4](#0-3) 

This mirrors the reported bug class exactly: a state-mutating operation (`updateAccountReward`/`updateEpoch`, here `LinkRepositoryToObjectPool`) that is designed to be called only from within a controlled, invariant-preserving flow (`claimReward`, here fork creation) is instead exposed generally, and the handler itself performs no authorization/relationship check to ensure the caller is only linking pools it is entitled to link, i.e. "improper visibility and lack of access control" over an internal-flow-only mutator.

### Impact Explanation
An authenticated Gitaly client (any client with access to invoke gRPC operations against the storage, e.g. a compromised or malicious project/repository owner acting through GitLab's Gitaly access path) can call `LinkRepositoryToObjectPool` on a repository it controls, targeting any existing object pool on the same storage whose relative path it can supply. The victim pool need not be related to the attacker's repository at all. This grants the attacker's repository — and therefore the attacker, via standard read RPCs — access to all objects contained in that pool, which can include objects originating from other, unrelated fork-network members. This is a cross-repository object disclosure: private commits/blobs/trees stored only in the pool's alternate object store can be exfiltrated by pointing an unrelated repository's alternates at it.

### Likelihood Explanation
The RPC is reachable directly by any client authorized to make ordinary mutator Gitaly calls; it requires only a `repository` the attacker already has write access to (e.g., their own project) and knowledge/guessability of a target pool's relative path (pool paths are derived deterministically from repository/project identifiers in GitLab, e.g. `@pools/<hash>.git`), making this practically reachable without any special privilege beyond normal repository ownership.

### Recommendation
Add an authorization/relationship check inside `LinkRepositoryToObjectPool` (and any other objectpool-linking entry point) before calling `pool.Link`, verifying that the target `object_pool` is the pool that Rails/GitLab has legitimately associated with `repository` (e.g., by cross-checking against the recorded fork-network/pool relationship rather than trusting the caller-supplied `object_pool` field), or by making the pool-linking step internal-only and reachable solely from the fork-creation code path rather than as a freestanding externally callable RPC.

### Proof of Concept
1. Attacker creates/controls `repoA` (their own project) on a Gitaly storage.
2. Attacker learns or guesses the relative path of an existing object pool `pool.git` (e.g. belonging to a different, unrelated fork network containing private objects).
3. Attacker calls `LinkRepositoryToObjectPool` with `repository = repoA`, `object_pool = pool.git`.
4. The handler validates only that `repoA` and `pool.git` each independently exist/are valid (`ValidateRepository`, `FromProto`/`IsValid`), then writes `pool.git`'s object directory into `repoA/objects/info/alternates` via `objectpool.Link`.
5. Attacker now reads any object ID from `pool.git` through ordinary RPCs (e.g. `CommitService.GetCommit`) targeting `repoA`, as shown by the existing test pattern that fetches a pool-only commit through the linked repository (`internal/gitaly/service/objectpool/link_test.go:105-156`).

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}

// FromProto returns an object pool object from its Protobuf representation. This function verifies
// that the object pool exists and is a valid pool repository.
func FromProto(
	ctx context.Context,
	logger log.Logger,
	locator storage.Locator,
	gitCmdFactory gitcmd.CommandFactory,
	catfileCache catfile.Cache,
	txManager transaction.Manager,
	housekeepingManager housekeepingmgr.Manager,
	proto *gitalypb.ObjectPool,
) (*ObjectPool, error) {
	poolPath, err := locator.GetRepoPath(ctx, proto.GetRepository(), storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, err
	}

	if !storage.IsPoolRepository(proto.GetRepository()) {
		// When creating repositories in the ObjectPool service we will first create the
		// repository in a temporary directory. So we need to check whether the path we see
		// here is in such a temporary directory and let it pass.
		tempDir, err := locator.TempDir(proto.GetRepository().GetStorageName())
		if err != nil {
			return nil, fmt.Errorf("getting temporary storage directory: %w", err)
		}

		if !strings.HasPrefix(poolPath, tempDir) {
			return nil, ErrInvalidPoolDir
		}
	}

	pool := &ObjectPool{
		Repo:                localrepo.New(logger, locator, gitCmdFactory, catfileCache, proto.GetRepository()),
		logger:              logger,
		locator:             locator,
		gitCmdFactory:       gitCmdFactory,
		txManager:           txManager,
		housekeepingManager: housekeepingManager,
	}

	if !pool.IsValid(ctx) {
		return nil, ErrInvalidPoolRepository
	}

	return pool, nil
}

// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
