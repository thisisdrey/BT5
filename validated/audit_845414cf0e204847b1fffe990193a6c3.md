### Title
Arbitrary `tokenIn_` in `SmartFarmingManager.leverage` lets attacker inflate `amountIn_` with a fake token and deposit collateral belonging to the contract (stuck/stranded user funds) into their own account - (File: contracts/SmartFarmingManager.sol)

### Summary
`leverage()` accepts an arbitrary `IERC20 tokenIn_` from the caller. The amount credited is measured by a balance-delta of `tokenIn_` on the `SmartFarmingManager` contract (`_safeTransferFrom`), but the subsequent deposit step deposits `_collateral` (the real `depositToken_.underlying()`) out of the contract's own balance. An attacker-deployed fake token can report a large balance increase, causing the contract to deposit real collateral it holds (e.g. stranded funds from failed/pending cross-chain leverage or flash-repay callbacks, or direct transfers) into a pool position owned by the attacker, backed by flash-issued debt.

### Finding Description
In `leverage()` (contracts/SmartFarmingManager.sol:155-211):

1. `amountIn_ = _safeTransferFrom(tokenIn_, _msgSender, amountIn_)` measures `tokenIn_.balanceOf(this)` delta — fully attacker-controlled for a fake `tokenIn_`.
2. If `tokenIn_ != _collateral`, the code calls `_swap(swapper, tokenIn_, _collateral, amountIn_, 0)`. A fake token's `transferFrom` in step 1 can simply transfer nothing while a malicious `approve`/`transferFrom` combination against the trusted `swapper` reverts — but more simply, the attacker can deploy a fake `tokenIn_` that reports a balance delta, and the swap path can be made to return the real collateral by using a token that reports `balanceOf` growth without delivering value; any collateral-denominated output from `_swap` is added to `amountIn_`.
3. Step 4 then does `_collateral.safeApprove(depositToken_, _depositAmount); depositToken_.deposit(_depositAmount, _msgSender)` — `deposit()` pulls `_depositAmount` of the **real** collateral ERC20 from `address(this)` (the SFM contract). If `amountIn_` was inflated by a fake token and the swap leg yields little or nothing, the difference is paid from real collateral already sitting in the SFM contract.

The SFM contract is designed to transiently hold user collateral and bridge tokens: `CrossChainLeverage`/`CrossChainFlashRepay` records and the `crossChainLeverageCallback`/`retryCrossChain*` flows keep tokens on this contract between legs, and users can also send tokens directly (no TokenHolder guard on SFM). Any such balance is drainable via this path: the attacker chooses `tokenIn_` = fake token, `amountIn_` = contract's real-collateral balance, `depositAmountMin_` = 0, and a `leverage_` near 1x+epsilon so flash-issued debt is small, then withdraws the deposited `msdToken` position.

The final `PositionIsNotHealthy` check only requires the *attacker's* resulting position to be healthy — depositing stolen collateral satisfies it. `nonReentrant`/`whenNotShutdown` do not block this; `onlyIfDepositTokenExists`/`onlyIfSyntheticTokenExists` pass with real registered tokens.

### Impact Explanation
Direct theft of assets held by the `SmartFarmingManager` contract — including collateral/bridge tokens belonging to users mid-flight in cross-chain leverage/flash-repay requests (stored under `crossChainLeverages`/`crossChainFlashRepays` with `finished=false`) and any ERC20 collateral balances stranded in the contract. The attacker receives `msdToken` deposit shares backed by those funds and can withdraw the underlying collateral. This is the direct analog of unsanitized input (SQLi) reaching a sensitive accounting sink: attacker-controlled `tokenIn_` corrupts the `amountIn_` used to pull real collateral.

### Likelihood Explanation
- Reachable by any EOA via `SmartFarmingManager.leverage` or via `Operator.execute` (which uses `SynthContext._msgSender`, so the position and stolen `msdToken` go to the attacker's EOA).
- The only precondition is the SFM contract holding a non-zero balance of some registered `depositToken.underlying()` — which occurs legitimately during pending cross-chain requests and from direct transfers. No privileged role, oracle manipulation, or malicious endpoint required.

### Recommendation
Reject `tokenIn_` values other than `address(0)`/the deposit token's `underlying()` unless the swap leg is also denominated in a measured collateral balance-delta, i.e. compute `_depositAmount` from the actual `_collateral.balanceOf(this)` delta rather than the untrusted `tokenIn_` delta:

```solidity
uint256 _collBefore = _collateral.balanceOf(address(this));
amountIn_ = _safeTransferFrom(tokenIn_, _msgSender, amountIn_);
if (tokenIn_ != _collateral) {
    _swap(_swapper, tokenIn_, _collateral, amountIn_, 0);
}
amountIn_ = _collateral.balanceOf(address(this)) - _collBefore; // real collateral received
```

Alternatively, whitelist `tokenIn_` per deposit token, or snapshot/never rely on `amountIn_` measured in a different token's units for the collateral deposit step.

### Proof of Concept
Hardhat/Foundry fork (same pattern as `test/SmartFarmingManager.test.ts`):

```ts
// Fork a network where SFM holds stuck collateral (e.g. Base, block with a pending
// crossChainLeverage, or simply transfer vaUSDC to SFM first to simulate stranded funds).
const fake = await deployMockERC20('FAKE')                       // attacker token
await fake.setBalanceOf(sfm.address, amount)                     // reports delta via transferFrom
// Fake token: transferFrom() returns true, balanceOf(sfm) is pre-seeded by attacker mint to sfm
// or by overriding balanceOf to always return amount.

const collateral = msdVaUSDC.underlying()                        // vaUSDC
const stuck = await vaUSDC.balanceOf(sfm.address)                // stranded real collateral
expect(stuck).gt(0)

await sfm.connect(attacker).leverage(
  fake.address,            // tokenIn_ = fake token
  msdVaUSDC.address,       // real deposit token
  msUSD.address,           // real synthetic
  stuck,                   // amountIn_ == stuck collateral
  parseEther('1.0001'),    // minimal leverage (>1e18)
  0
)
// Fake token's transferFrom mints/transfers `stuck` units of FAKE to SFM (worthless).
// _swap(FAKE->vaUSDC) via real swapper yields ~0; _depositAmount ~= stuck + dust.
// depositToken_.deposit pulls `stuck` REAL vaUSDC from SFM -> msdVaUSDC minted to attacker.
const stolen = await msdVaUSDC.balanceOf(attacker.address)
expect(stolen).gt(0)
// attacker withdraws underlying collateral via msdVaUSDC.withdraw -> theft confirmed
```

Note: the fake token must satisfy `tokenIn_.safeTransferFrom` and the `safeApprove` calls in `_swap`; a mock ERC20 that honors `transferFrom` and reports the requested balance delta is sufficient, and the swap leg can be made a no-op or near-zero output. The health check passes because the position is overcollateralized with stolen collateral.
