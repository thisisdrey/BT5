### Title
Protocol fees on MT/IMT tokens can be fully bypassed by splitting a single large `TokenDiff` into many unit-sized `TokenDiff` intents - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::token_fee` (lines 206-217) exempts `TokenIdType::Nep245`/`TokenIdType::Imt` from fees only when the *per-intent* `amount <= 1`. Because `ExecutableIntent::execute_intent` (lines 41-104) computes and collects the fee independently for each `TokenDiff` intent rather than on the aggregate exposure a signer trades in a batch, an attacker can decompose any large MT/IMT trade into N separate unit-delta (`|delta| == 1`) `TokenDiff` intents inside one `MultiPayload`/intents list, paying zero fee on the whole notional instead of `fee_ceil(N)` that a single `{token: -N}` intent would incur.

### Finding Description
The broken binding is:
`fees_collected(token_id) == Self::token_fee(token_id, |Σ negative deltas on token_id in this signer's economic trade|, protocol_fee).fee_ceil(Σ|deltas|)`

but the code actually computes, per intent, per token entry:
`fee = Self::token_fee(token_id, |single_delta|, protocol_fee).fee_ceil(|single_delta|)` [1](#0-0) 

and `token_fee` explicitly zeroes the fee for `Nep245`/`Imt` whenever the evaluated `amount <= 1`: [2](#0-1) 

Because `intents.execute_intent(&signer_id, self, hash)` iterates the full list of intents in a signer's `DefuseIntents` message and calls `TokenDiff::execute_intent` once per `TokenDiff` struct [3](#0-2) , a signer can encode a trade of `N` units of an `Nep245`/`Imt` token as `N` separate `TokenDiff` intents each with `delta = -1` (matched by corresponding `+1` deposits elsewhere, e.g. from a counterparty or from the attacker's own second account), instead of one `TokenDiff{token: -N}`. Each of the `N` intents independently evaluates `amount = 1` and returns `Pips::ZERO`, so `fees_collected` accumulates to `0` for the whole batch, whereas a single intent moving the same total `N` units would have paid `token_fee(..., N, fee).fee_ceil(N) > 0`.

The global solvency invariant (`TransferMatcher::finalize`, `contracts/defuse/core/src/engine/state/deltas.rs` lines 267-283) still holds — all deltas across the batch net to zero and are correctly turned into `Transfers`, so the Verifier is never under-collateralized. The only value affected is the protocol fee, which is explicitly listed as a Critical-impact category ("protocol fees bypassed or over-collected"). None of the listed guards (`MultiPayload::verify`, nonce/salt checks, `TransferMatcher::finalize`, `checked_*` arithmetic) address this because they only protect balance conservation and signature/replay integrity, not the fee-exemption granularity, which is a design gap in `token_fee`'s per-intent, per-token-entry evaluation.

### Impact Explanation
The fee collector (`engine.state.fee_collector()`) receives strictly less than the protocol fee owed on any MT/IMT (`Nep245`/`Imt`) trade whose signer chooses to fragment it into unit-sized `TokenDiff` legs. This is repeatable indefinitely by any unprivileged account for any MT/IMT asset, on every trade, with no bound other than gas/transaction-size limits (explicitly out of scope as a constraint, not as a defense). It does not move funds without authorization and does not break solvency (`TransferMatcher::finalize` still balances to zero), but it directly under-collects the protocol fee for the affected token class, matching the "protocol fees bypassed" Critical category.

### Likelihood Explanation
No special privileges or roles are needed — any user constructing their own `MultiPayload`/`DefuseIntents` with multiple `TokenDiff` intents can trigger this. The attacker only needs a counterparty (which can be their own second account) willing to net the unit-sized deltas to zero, which is a normal part of legitimate trading via `TokenDiff`. The only cost is additional gas for more intents in the payload, and NEAR's per-transaction gas budget (~300 Tgas) permits many such unit-sized legs, making the fee bypass practically achievable for meaningfully large trades.

### Recommendation
Evaluate the MT/IMT fee exemption on the net exposure per `(signer, token_id)` across the whole batch/execution (e.g., accumulate deltas per token before computing `token_fee`, or track a running total similar to `TransferMatcher`), rather than on each individual `TokenDiff` intent's per-token delta in isolation. Alternatively, remove or shrink the "amount <= 1 is fee-free" exemption for `Nep245`/`Imt`, since these are not necessarily 1-of-1 NFTs and can represent arbitrary fungible quantities.

### Proof of Concept
```rust
// contracts/defuse/core/src/intents/token_diff.rs (new test)
#[test]
fn fee_bypass_via_unit_split() {
    let token_id = TokenId::from(Nep245TokenId::new(
        "mt.near".parse::<AccountId>().unwrap(), "sub_id".to_string(),
    ));
    let fee = Pips::ONE_PERCENT; // nonzero protocol fee

    // Single big TokenDiff intent: -1000 units -> fee should be > 0
    let big_fee = TokenDiff::token_fee(&token_id, 1000, fee).fee_ceil(1000);
    assert!(big_fee > 0);

    // N unit-sized intents summing to the same -1000 net delta -> cumulative fee is 0
    let mut cumulative_fee: u128 = 0;
    for _ in 0..1000 {
        let f = TokenDiff::token_fee(&token_id, 1, fee).fee_ceil(1);
        cumulative_fee += f;
    }
    assert_eq!(cumulative_fee, 0);
    assert_ne!(cumulative_fee, big_fee, "batch of unit-sized TokenDiff intents bypasses fee owed on aggregate delta");
}
```
This should be complemented with a `near-workspaces` sandbox test executing `execute_intents` with one `MultiPayload` containing 1000 `TokenDiff` intents (each `delta = -1` on the `Nep245` token, matched by a counterparty's `+1` deposits) and asserting the emitted `TokenDiffEvent::fees_collected` sums to `0`, while a single equivalent `TokenDiff{token: -1000}` intent produces `fees_collected > 0` for the same net amount traded.
