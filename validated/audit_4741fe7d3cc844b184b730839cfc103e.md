### Title
Predictable Quarantine Directory Prefix Used as Pseudo-Authorization Token for Client-Supplied Object Directories - (File: `internal/gitaly/storage/locator.go`)

### Summary
`QuarantineDirectoryPrefix()` derives the "proof" that a client-supplied `git_object_directory` belongs to a given repository's Git object quarantine from a **deterministic**, publicly-computable value — a truncated SHA1 hash of the repository's relative path — rather than from a cryptographically random, unguessable secret. This value is later used in `Repo.ObjectDirectoryPath()` as the sole criterion to accept an attacker/Rails-controlled `GitObjectDirectory`/`GitAlternateObjectDirectories` field that points *outside* the repository itself. This mirrors the reported bug class: using predictable, non-secret values where an unguessable random token is required for a security decision.

### Finding Description
`QuarantineDirectoryPrefix` computes: [1](#0-0) 

```go
func QuarantineDirectoryPrefix(repo Repository) string {
	hash := [20]byte{}
	if repo != nil {
		hash = sha1.Sum([]byte(repo.GetRelativePath()))
	}
	return fmt.Sprintf("quarantine-%x-", hash[:8])
}
```

This prefix is entirely deterministic from `RelativePath`, a value that is not secret (it is routinely known to, and often chosen/derivable by, the project owner or any actor who knows the project's path). No random or per-request secret component is mixed in.

This prefix is the mechanism `Repo.ObjectDirectoryPath()` relies on to authorize a `GitObjectDirectory` value supplied on the `Repository` protobuf message when that path does not resolve inside the repository itself: [2](#0-1) 

The `GitObjectDirectory` / `GitAlternateObjectDirectories` fields are populated by Gitaly during a legitimate quarantine (`quarantine.Apply`), but they are ordinary fields on the `gitalypb.Repository` message that travel over gRPC and are explicitly designed to be sent back to Gitaly from Rails during push access-check callbacks: [3](#0-2) 

The documented quarantine flow confirms this round-trip: Gitaly hands the quarantine object-directory information to the `pre-receive` hook → GitLab Rails → and Rails sends it back to Gitaly on subsequent RPCs to look at pushed-but-not-yet-committed objects. [4](#0-3) 

Because the "proof of ownership" for such an externally-supplied object directory is nothing more than a 64-bit, non-secret, deterministic hash of a typically-knowable string, any party able to compute `sha1(relative_path)[:8]` (trivial, since the algorithm and input are public) knows in advance the exact prefix Gitaly will accept for that repository. The security property that "only directories genuinely created by Gitaly's quarantine flow can pass this check" therefore rests on obscurity of a random path-suffix appended by `os.MkdirTemp`, not on the value that is actually being validated. This is architecturally the same flaw as the report: a value intended to gate an outcome (there: minted token index; here: acceptance of an externally supplied object directory) is derived from public/predictable inputs instead of a securely generated random secret.

### Impact Explanation
If an attacker can, through any path, cause a directory to exist under the storage's shared temporary root whose name begins with the attacker-precomputable string `quarantine-<sha1(relative_path)[:8]>-`, `ObjectDirectoryPath()` will treat it as a legitimate quarantine directory for that repository, and Gitaly will subsequently read (or run Git operations sourcing objects from) that directory as if it were the genuine object quarantine for the push in progress. Because access-check RPCs (e.g., ancestor/ref checks invoked from `pre-receive`) rely on the quarantine directory to see "objects pushed but not yet committed," acceptance of a directory that was not created by the real quarantine flow for that push undermines the integrity guarantee described in `doc/object_quarantine.md` and could be leveraged to influence push-acceptance decisions that depend on quarantine contents (e.g., ancestor/protected-branch checks), i.e., a hook/quarantine trust bypass.

### Likelihood Explanation
Exploitation requires an additional capability beyond predicting the prefix: an attacker must also be able to get some process to create a directory at the exact predicted path inside the storage's shared temp root (the trailing random suffix appended by `os.MkdirTemp` is otherwise unpredictable). This makes the issue Low-to-Medium likelihood on its own, but it removes what should be an independent, unguessable safety net: the check is effectively "does the name start with a public hash of a public string," not "is this name unguessable," so any future code path that lets an outside actor influence directory naming under the storage temp root (even partially) would immediately be exploitable for quarantine/authorization bypass with no additional secret to defeat.

### Recommendation
Do not rely on a deterministic hash of `relative_path` as the trust anchor for accepting externally supplied `GitObjectDirectory`/`GitAlternateObjectDirectories` values that point outside the repository. Instead, mint a cryptographically random, per-quarantine secret token (e.g., using `internal/helper/text.RandomHex`, already used elsewhere in the codebase for this purpose) at quarantine-creation time, embed it in the directory name, and validate it via constant-time comparison rather than a `strings.HasPrefix` check against a value re-derivable from public repository metadata.

### Proof of Concept
1. Compute `sha1(relative_path)[:8]` for any known/target repository's relative path (public/derivable information) to obtain the exact string Gitaly's `ObjectDirectoryPath()` will accept as a valid quarantine prefix: `quarantine-<hash>-`. [5](#0-4) 
2. Note that `ObjectDirectoryPath()` only checks `strings.HasPrefix(absoluteObjectDirectoryPath, expectedQuarantinePrefix)`, not that the directory was actually produced by `quarantine.New`/`tempdir.NewWithPrefix` for the current push. [6](#0-5) 
3. Any mechanism that allows a directory matching that exact predictable prefix to be created under the storage's shared temp root (`internal/tempdir/tempdir.go`) — e.g. abuse of another temp-directory-creating code path that can be steered by attacker input — would cause Gitaly to treat attacker-controlled object data as the legitimate quarantine for that repository's in-flight push, bypassing the intended object-quarantine trust boundary described in `doc/object_quarantine.md`.
