### Title
Missing trailing-data check in `unmarshalCertificateV2` allows attacker-appended bytes after a validly-signed cert to be silently accepted - ([File: cert/cert_v2.go])

### Summary
`unmarshalCertificateV2` reads the outer SEQUENCE, details, curve, public key and signature TLVs from `input`, but never calls `input.Empty()` after the final `ReadASN1(&rawSignature, TagCertSignature)` read. As a result, arbitrary trailing bytes placed inside the outer SEQUENCE after the signature TLV are never inspected and the function still returns a valid `*certificateV2` and `nil` error.

### Finding Description
In `cert/cert_v2.go`, `unmarshalCertificateV2` (starting at line 570) does: [1](#0-0) 
which opens the outer SEQUENCE and checks only that its *contents* are non-empty, not that the caller-provided buffer `b` was fully consumed by the TLV. It then sequentially reads `rawDetails`, an optional curve byte, an optional/derived public key, and finally the signature: [2](#0-1) 
After this read, the function proceeds directly to `unmarshalDetails`, builds the `certificateV2` struct, calls `c.validate()`, and returns success — at no point checking `input.Empty()`: [3](#0-2) 

Because `cryptobyte.String.ReadASN1` only consumes the specific tag it is asked to read and advances the cursor, any bytes remaining in `input` after the signature field (e.g., an attacker-injected extra ASN.1 element, or simply junk bytes appended inside the outer SEQUENCE's declared length) are left unread and unvalidated. The signature itself was computed only over `rawDetails + curve + publicKey` (see `marshalForSigning`, `cert/cert_v2.go:462-474`, and `CheckSignature`, lines 143-168), so appending extra bytes inside the SEQUENCE does not invalidate the signature — the cryptographic check still passes even though the wire encoding is not canonical/complete.

This same class of gap also exists at the outer envelope: `input.ReadASN1(&input, asn1.SEQUENCE)` overwrites `input` with the SEQUENCE contents, so bytes in `b` located after the entire outer SEQUENCE TLV are never even looked at by this function (no check like `!input.Empty()` against the original buffer after opening the envelope). The `unmarshalDetails` helper (`cert/cert_v2.go:641-745`) has an analogous issue: after reading `issuer` (the last field) at lines 730-733, it never verifies `b.Empty()`, so extra fields can also be smuggled inside the Details TLV.

### Impact Explanation
This breaks the "unknown/trailing fields must be rejected" invariant for certificate parsing. Two distinct byte sequences (one with trailing garbage/extra fields, one without) that share the same prefix up through a valid signature will both be treated as the same logical, validly-signed certificate — since `Fingerprint()` and `CheckSignature()` operate on `rawDetails`/`publicKey`/`signature` fields that were successfully extracted, not on the full/raw wire bytes with the trailing junk. This can lead to certificate/fingerprint ambiguity: a blocklisted-by-fingerprint certificate's underlying "logical" identity could be re-encoded with padding to produce a different fingerprint over the full byte string while still parsing to the same accepted `certificateV2` fields, or conversely could be used to probe/smuggle attacker-chosen bytes past cert parsing in contexts that hash/compare the raw blob. This does not, by itself, forge a valid signature or bypass CA verification, and does not appear to cause a crash — it is scoped to format/identity ambiguity in the certificate parser.

### Likelihood Explanation
No privileges are required. Any attacker who can present a certificate to a Nebula node — via handshake `Recombine` (`cert/cert.go` lines 128-159, whose doc explicitly states it unmarshals "a certificate received in a handshake") which dispatches to `unmarshalCertificateV2`, or via `UnmarshalCertificateFromPEM`/`unmarshalCertificateBlock` in `cert/pem.go` (lines 88-115) — can trivially append extra bytes after the signature TLV inside the outer SEQUENCE while keeping the SEQUENCE's declared length consistent, and keep the signature over the unaffected fields valid. This is fully attacker-controlled, deterministic, and repeatable.

### Recommendation
After the final field read in `unmarshalCertificateV2` (immediately following the `rawSignature` read at `cert/cert_v2.go:615`), add an explicit check `if !input.Empty() { return nil, ErrBadFormat }`. Similarly, add `if !b.Empty() { return detailsV2{}, ErrBadFormat }` at the end of `unmarshalDetails` (after the issuer read, `cert/cert_v2.go:731-733`) to ensure no trailing bytes remain unconsumed within either the outer certificate structure or the details structure.

### Proof of Concept
Unit test plan (place in `cert/cert_v2_test.go`):
1. Build a valid, correctly-signed v2 certificate using the existing test helpers (e.g., mirror `newTestCert`/similar used elsewhere in `cert_v2_test.go`) and `Marshal()` it to bytes `validBytes`.
2. Parse `validBytes` with `cryptobyte`, locate the outer SEQUENCE TLV, and construct a modified blob `tamperedBytes` by inserting extra bytes (e.g., a bogus context-specific TLV or random bytes) immediately after the signature TLV but still within the outer SEQUENCE's declared length (increase the SEQUENCE length field accordingly).
3. Call `unmarshalCertificateV2(tamperedBytes, nil, curve)` (or via `Recombine`) and assert:
   - Current (buggy) behavior: returns `(*certificateV2, nil)` with no error — parsing succeeds despite trailing bytes.
   - Expected (fixed) behavior: returns `(nil, ErrBadFormat)`.
4. Additionally assert that `unmarshalCertificateV2(tamperedBytes...)` and `unmarshalCertificateV2(validBytes...)` currently produce certs with identical `Fingerprint()`/field values despite different raw wire bytes, demonstrating the format/identity ambiguity, and that after the fix the tampered variant is rejected.
