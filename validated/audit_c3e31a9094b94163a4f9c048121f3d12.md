### Title
Uncaught unbounded array allocation in `ValidateMultiSign` precompile enables single-transaction node DoS - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` TVM precompiled contract (address `0x...09`, reachable from any `TriggerSmartContract` call) decodes an ABI-encoded signature array whose declared length is taken directly from attacker-controlled calldata via `DataWord.intValueSafe()` (which can return up to `Integer.MAX_VALUE`). When the `allowTvmSelfdestructRestriction` chain feature is not active, the code skips the `MAX_SIZE` bound check and passes the raw, unbounded length straight into `extractBytesArray`/`extractSigArray` → `extractBytes32Array`, which allocate `new byte[len][]`. This allocation happens **outside** the method's only `try`/`catch` block, so a resulting `OutOfMemoryError` (an `Error`, not a `RuntimeException`) is not caught by the precompile, and is not caught by the VM's generic exception handling in `VM.play`/`testSingleOperation`, which only catches `RuntimeException`, `StackOverflowError`, and TVM-specific timeout/stack exceptions — not `OutOfMemoryError`.

### Finding Description
`ValidateMultiSign.execute()` parses calldata into `DataWord[]` and, only if `VMConfig.allowTvmSelfdestructRestriction()` is enabled, checks `sigArraySize > MAX_SIZE` before extraction: [1](#0-0) 

If that feature is not active (e.g., on a chain/replay where the corresponding committee proposal has not yet been activated, or a private/consortium chain running this codebase with default parameters), the code falls straight to: [2](#0-1) 

which calls `extractBytesArray`, whose length comes from attacker data with no bound: [3](#0-2) 

`words[offset].intValueSafe()` can return `Integer.MAX_VALUE` for any word occupying more than 4 bytes or with a negative top bit, per: [4](#0-3) 

`new byte[len][]` with `len` near `Integer.MAX_VALUE` throws `OutOfMemoryError` (array header overhead alone exceeds heap for large `len`), or in a marginal case, allocates a huge amount of heap. This allocation occurs at line 1074, **before** the only `try { ... } catch (Throwable t) { ... }` block in the method, which starts later at line 1082: [5](#0-4) 

The test suite explicitly documents this as an acknowledged pre-activation gap: "before activation, malformed calldata reaches the legacy decoder... this precompile has no outer catch": [6](#0-5) 

Higher up the call stack, `VM.play`'s catch clauses do not include `OutOfMemoryError`: [7](#0-6) 
and `testSingleOperation` has the same gap: [8](#0-7) 

An uncaught `OutOfMemoryError` propagating out of transaction execution in `Manager`'s block-application path can crash or corrupt the node process (or leave heap in a state where subsequent GC/allocations fail across the node, including for unrelated transactions), producing a denial of service.

Note: the sibling precompile `BatchValidateSign` wraps its entire `doExecute` in `catch (Throwable t)` and is therefore not affected the same way: [9](#0-8) 

### Impact Explanation
This qualifies as node crash/halt DoS: an uncaught `Error` thrown during smart-contract execution triggered by a single unprivileged `TriggerSmartContract` transaction can escape all TVM error-containment layers, since `VM.play` and `testSingleOperation` only defend against `RuntimeException`/`StackOverflowError`, not `OutOfMemoryError`. This is directly analogous to the CVE's "crafted response causes DoS" bug class, mapped onto the TVM precompile input-parsing path reachable from any smart-contract call.

### Likelihood Explanation
Exploitability depends on the `allowTvmSelfdestructRestriction` feature flag being inactive for the executing node/chain (the guard added by that feature is the only bound check). On current TRON mainnet this proposal may already be permanently activated, which would mitigate the issue on mainnet specifically; however, the vulnerable code path remains present and reachable on any deployment (private/consortium chains, or historical block replay/sync before the activation height) where the flag is not yet set, and the precompile itself provides no compile-time or unconditional bound on the attacker-supplied array length. The bug requires nothing beyond a single signed transaction calling the precompile address with crafted calldata, from any account with enough energy to pay for the (attacker-cheap) `getEnergyForData` cost based on `data.length`, not on the huge decoded length.

### Recommendation
Move the `MAX_SIZE` (and general upper-bound sanity) check on the decoded array length so it is unconditional — not gated behind `allowTvmSelfdestructRestriction` — and perform it before calling `extractBytesArray`/`extractSigArray`/`extractBytes32Array`. Additionally, wrap the entire `execute()` body of `ValidateMultiSign` (and any other precompile using `extractBytes32Array`/`extractBytesArray` without a prior bound check) in a `catch (Throwable t)` similar to `BatchValidateSign`, so any decoding failure — parsing exception or allocation error — safely degrades to returning `(true, DATA_FALSE)` rather than propagating an uncaught `Error`.

### Proof of Concept
1. Craft calldata for `ValidateMultiSign(address,uint256,bytes,bytes[])` such that the dynamic offset word for the signatures array (`words[3]`) points to a header word whose value decodes (via `intValueSafe()`) to a very large length, e.g. `0x7FFFFFFF`, while providing minimal actual trailing bytes.
2. Deploy/trigger a contract (or call directly via `TriggerSmartContract`) that performs a `STATICCALL`/`CALL` to the `ValidateMultiSign` precompile address with this calldata, on a node/chain where `allowTvmSelfdestructRestriction` has not been activated (default/private chain, or pre-activation mainnet block height during replay).
3. `words[words[3].intValueSafe()/WORD_SIZE].intValueSafe()` returns the crafted huge length; `extractBytesArray` executes `new byte[0x7FFFFFFF][]`, which throws `OutOfMemoryError` before the method's `try` block is reached.
4. The `Error` propagates uncaught through `Program.callToPrecompiledAddress` → `VM.play` (whose catches only cover `RuntimeException`/`StackOverflowError`) up into transaction/block processing, crashing the node thread and potentially destabilizing the whole node process (heap exhaustion affecting concurrent processing).
