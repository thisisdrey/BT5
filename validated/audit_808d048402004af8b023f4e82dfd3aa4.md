### Title
Interest under-accrual due to division before multiplication in `interestRatePerSecond` — (File: contracts/DebtToken.sol)

### Summary
`DebtToken._calculateInterestAccrual` computes the interest to accrue as `interestRatePerSecond() * timeElapsed`, where `interestRatePerSecond()` performs `interestRate / SECONDS_PER_YEAR` first (DebtToken.sol:319-321, 560). Division happens in the middle of the calculation instead of at the end, truncating the per-second rate. Every accrual systematically understates both the accrued interest fee minted to `feeCollector` and the `debtIndex` growth applied to all borrowers' debt.

### Finding Description
In `DebtToken.sol`:

```solidity
function interestRatePerSecond() public view override returns (uint256) {
    return interestRate / SECONDS_PER_YEAR;          // division first
}

// _calculateInterestAccrual (lines 559-564)
uint256 _interestRateToAccrue = interestRatePerSecond() * (block.timestamp - _lastTimestampAccrued);
_interestAmountAccrued = _interestRateToAccrue.wadMul(totalSupply_);
_debtIndex += _interestRateToAccrue.wadMul(_debtIndex);
```

`interestRate / SECONDS_PER_YEAR` discards a remainder of up to `SECONDS_PER_YEAR - 1` (≈3.15e7) wei before the value is scaled back up by `timeElapsed`. The mathematically correct ordering is `(interestRate * timeElapsed) / SECONDS_PER_YEAR`. Because this truncated rate feeds both `_interestAmountAccrued` (minted to `pool.feeCollector()` in `accrueInterest`, lines 169-178) and the global `debtIndex` (which `balanceOf` uses to grow every borrower's debt, line 205), the protocol leaks value on every accrual.

### Impact Explanation
The protocol mints less interest to the fee collector than the configured `interestRate` implies, and all borrowers' debts grow slower than intended — a continuous, systematic value leak identical in class to the referenced finding (intermediate truncation of a fee/interest percentage that is then applied to supply). The relative error is bounded by `SECONDS_PER_YEAR / interestRate` (≈3e-9 for a 2e16 rate, larger for small rates), but it applies to the entire `totalSupply_` on every single accrual, across every DebtToken, forever.

### Likelihood Explanation
Certain — the truncation occurs deterministically on every `accrueInterest()` call, which is invoked at the top of `issue`, `repay`, `mint`, `flashIssue`, `liquidate`, etc. It is unprivileged and unavoidable in normal operation; no admin action is needed to trigger it.

### Recommendation
Reorder so multiplication precedes division. In `_calculateInterestAccrual`, compute the rate to accrue as:

```solidity
uint256 _interestRateToAccrue = interestRate * (block.timestamp - _lastTimestampAccrued) / SECONDS_PER_YEAR;
```

and remove or rework `interestRatePerSecond()`. `interestRate` is ≤ 1e18 and `timeElapsed` bounded, so the numerator cannot realistically overflow uint256.

### Proof of Concept
A Foundry/Hardhat test can compare the two formulas directly:

```solidity
uint256 rate = 0.02e18;                       // 2% APR
uint256 elapsed = 365.25 days;
uint256 current = (rate / SECONDS_PER_YEAR) * elapsed;   // 19999999999999872
uint256 correct = rate * elapsed / SECONDS_PER_YEAR;     // 20000000000000000
// lost = 128 wei of rate per year; multiplied by totalSupply_ each accrual.
```

The delta widens proportionally when `accrueInterest` is called in many short intervals, since the truncated remainder is lost on each call, and grows with `totalSupply_` and with smaller (non-multiple-of-SECONDS_PER_YEAR) `interestRate` configurations. [1](#0-0) [2](#0-1)
