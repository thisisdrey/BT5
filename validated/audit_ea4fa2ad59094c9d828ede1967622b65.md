## Analog identified

### Title
Out-of-bounds array read in TVM precompile ABI-array parsing (`extractSigArray`/`extractBytes32Array`/`extractBytesArray`) via unchecked attacker-controlled length - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The Linux `ipv6_find_tlv()` bug reads an `optlen` byte before verifying there is enough remaining buffer to hold it, causing an out-of-bounds read. The java-tron precompile helpers `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` exhibit the same bug class: they read an attacker-controlled length word from calldata and then index into the `words[]` array `len` times without ever validating that `offset + len` stays within `words.length`.

### Finding Description
`extractSigArray` and `extractBytes32Array` read `len` from a single `DataWord` supplied by the caller's calldata and then loop `i` from `0` to `len`, reading `words[offset + i + 1]` on every iteration: [1](#0-0) [2](#0-1) 

Only a bounds check on `offset` itself is performed (`if (offset > words.length - 1) return new byte[0][];`), but `len` (fully attacker-controlled via `intValueSafe()` of an ABI word) is never validated against `words.length - offset`. A caller can supply an array-length word far larger than the actual number of words passed in calldata, causing `words[offset + i + 1]` to run past the end of the `words` array — analogous to `ipv6_find_tlv()` fetching `optlen` without checking there is another byte to parse. `extractBytesArray` has the identical pattern at line 403-411.

These helpers are invoked from the multisignature-verification precompiled contracts (`ValidateMultiSign`/`BatchValidateSign`, confirmed present via `ValidateMultiSignContractTest.java` and `BatchValidateSignContractTest.java`), which are reachable by any contract that performs a `STATICCALL`/`CALL` to the corresponding precompile address as part of ordinary TVM execution — i.e., by any contract deployer or transaction sender invoking a deployed contract.

### Impact Explanation
An out-of-bounds array read inside `words[]` throws an unchecked `ArrayIndexOutOfBoundsException` inside precompiled-contract execution. Depending on how far up the call stack this propagates and whether it is caught by the TVM's opcode/precompile dispatch, this can crash node processing of the transaction (denial of service for that transaction) or, if not properly caught by the surrounding VM exception handling, propagate out of contract execution and disrupt block/transaction processing for the calling node. Because the exploit requires no privileged access — just crafting calldata for a contract call — every full node that executes the transaction is affected, giving it node/consensus-processing impact reachable from an ordinary transaction.

### Likelihood Explanation
High. Any account can deploy a contract (or use an existing one) that calls the `ValidateMultiSign`/`BatchValidateSign` precompile with malformed ABI-encoded array-length words. No special privileges, staking, or governance access are required — only crafting the `data` payload passed to the precompiled contract address.

### Recommendation
In `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate that `len >= 0` and that `offset + 1 + len` does not exceed `words.length` before entering the loop; return an empty/failure result (matching the existing `offset > words.length - 1` guard style) when the declared length would run past the available words, rather than trusting the attacker-supplied length unconditionally.

### Proof of Concept
Construct calldata for `ValidateMultiSign`/`BatchValidateSign` in which the ABI-encoded array-length word at the expected `offset` is set to a very large value (e.g., `0x7fffffff`) while the actual calldata (and hence the derived `words[]`) contains far fewer words. When the precompile's `execute()` calls `extractSigArray`/`extractBytes32Array`, the loop attempts to access `words[offset + i + 1]` for `i` up to the declared (fabricated) length, throwing `ArrayIndexOutOfBoundsException` well before reaching the real end of the array — confirming the unchecked-length read.

Note: I was not able to fully trace the exact exception-handling wrapper around precompile invocation in the TVM dispatcher within the indexed content, so the precise blast radius (transaction-local revert vs. broader node disruption) could not be fully confirmed from the available index; a Devin session with full repository access would be needed to trace `Program`/opcode dispatch around precompile calls to confirm whether this exception is caught and safely converted to a revert.
