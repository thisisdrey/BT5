### Title
Removed StackerDB Signer Retains Write Authorization When Config Reload Fails-Open to Empty Signer List - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`StackerDBs::create_or_reconfigure_stackerdbs` decides whether to update a replica's persisted slot→signer mapping by comparing the freshly-evaluated contract config to the previously stored one. If the fresh evaluation returns an empty signer list (which happens both for legitimate "no participation" states *and* for any error while querying/parsing the `.signers` contract), the function deliberately skips calling `reconfigure_stackerdb`, leaving the old (possibly stale) signer-to-slot bindings in the on-disk `chunks` table untouched. A signer who has since been removed from the authoritative signer set therefore keeps write authorization for their previously-owned slot as long as the node's periodic contract re-evaluation keeps returning (or is coerced into returning) an empty/failed result — an authentication check that silently fails open, analogous to a deleted account still being able to authenticate.

### Finding Description
`StackerDBChunkData`/`SlotMetadata` writes are authorized purely by comparing the signature to the `signer` value stored per-slot in the local `chunks` table (`get_slot_signer` / `get_slot_validation`, used by `validate_received_chunk` and `try_replace_chunk`) — see `stackslib/src/net/stackerdb/mod.rs:679-697` and `stackslib/src/net/stackerdb/db.rs:398-439` (`try_replace_chunk`) and `stackslib/src/net/stackerdb/db.rs:522-543` (`get_slot_signer`). This locally stored mapping is only refreshed by `reconfigure_stackerdb` (`stackslib/src/net/stackerdb/db.rs:302-351`), which is only invoked from `create_or_reconfigure_stackerdbs`: [1](#0-0) 

Specifically the reconfigure gate is:
```
} else if (new_config != stackerdb_config && !new_config.signers.is_empty())
    || (new_config == stackerdb_config
        && new_config.signers.len() != self.get_slot_versions(&stackerdb_contract_id)?.len())
{
    // only reconfigure if the config has changed
    ...
}
``` [2](#0-1) 

`new_config` is computed from `StackerDBConfig::from_smart_contract(...)`, and *any* failure of that evaluation (read-only call error, contract-analysis mismatch, parse error, overflow, etc.) is caught and mapped to `StackerDBConfig::noop()`, whose `signers` field is `vec![]`: [3](#0-2) [4](#0-3) 

Because `new_config.signers.is_empty()` is true in this fallback, the first disjunct of the `else if` (`new_config != stackerdb_config && !new_config.signers.is_empty()`) is false, and the second disjunct only fires if the slot *count* stays equal — normally true since nothing changed on disk. The net effect: whenever the fresh config evaluation is empty/erroring, the function silently keeps serving the OLD, in-memory `stackerdb_config` returned to callers **and** never calls `reconfigure_stackerdb`, so the physical replica's `chunks.signer` column is never updated to remove a signer who was dropped from the authoritative `.signers` contract state in the interim. Any chunk still signed by that now-unauthorized signer's key continues to pass `SlotMetadata::verify` (`libstackerdb/src/libstackerdb.rs:181-193`) against the stale stored address, and `try_replace_chunk`/`validate_received_chunk` accept it as legitimate — an equality break between "authenticated (per the real, current `.signers` state)" and "stored (per this node's stale replica)".

### Impact Explanation
This is a High-severity authorization equality break: a party correctly removed from the current signer set can continue writing/propagating StackerDB chunks (e.g., signer messages in the `.signers-N-M` contracts) on any node whose periodic reconfiguration transiently fails or observes an empty signer list, because the write authorization gate (`get_slot_signer`) checks locally-stored, stale state rather than being forced to re-derive authoritative state on every observed discrepancy. Chunks accepted on such a node will also be relayed/gossiped to other peers via normal StackerDB propagation, potentially causing the network to accept and propagate stale/forged signer messages beyond their intended validity window.

### Likelihood Explanation
The failure path is reached by any error in `StackerDBConfig::from_smart_contract` (read-only VM call failures, transient reorgs during evaluation, list/entry parsing edge cases) or when the true evaluated signer set is legitimately empty for one refresh cycle. Since this logic runs on every reward-cycle boundary / periodic reconfiguration pass, and the comment in the code (`#5142`) shows this exact fail-open handling has already needed patching once for a related shrink bug, the pattern is fragile and reachable without any special privilege — an attacker only needs to have once held a valid signer slot and continue broadcasting chunks after being removed.

### Recommendation
Do not conflate "config unchanged" with "config failed to load." Track evaluation failures explicitly (e.g., `Option<StackerDBConfig>`/`Result` rather than coercing to `noop()`), and only skip `reconfigure_stackerdb` when the evaluation genuinely succeeded and returned identical signers, never when it failed or returned an empty list due to an error. Additionally, `try_replace_chunk`/`validate_received_chunk` should independently confirm slot ownership is still consistent with the latest known-good on-chain state before accepting chunks from a signer whose slot presence has become ambiguous.

### Proof of Concept
1. A signer S is legitimately registered for reward cycle N and owns slot K in the `.signers` StackerDB (`chunks.signer = S`).
2. In reward cycle N+1, the `.signers` contract removes S from the signer set for its stackerdb (real `stackerdb-get-signer-slots` no longer lists S).
3. Trigger (or wait for) the node's `StackerDBConfig::from_smart_contract` evaluation to fail or race during the transition (e.g., during chain-tip flux at reward-cycle boundary) — `create_or_reconfigure_stackerdbs` then falls back to `StackerDBConfig::noop()`, whose `signers` is empty.
4. Because `new_config.signers.is_empty()`, the `else if` gate at `stackslib/src/net/stackerdb/mod.rs:414-428` does not call `reconfigure_stackerdb`; the node's `chunks` table keeps `signer = S` for slot K.
5. S (now removed) signs and pushes a new `StackerDBChunkData` for slot K with an incremented `slot_version`.
6. `validate_received_chunk`/`try_replace_chunk` verify the signature against the stale stored `S` and accept the write, and the node relays it to peers as valid StackerDB data.

    /// Config that does nothing
    pub fn noop() -> StackerDBConfig {

            // `noop()` is used as a fallback whenever a replica's real config can't be
            // loaded (see `create_or_reconfigure_stackerdbs`), and it can transiently
            // overwrite a good in-memory config on a failed refresh. Since the DB slots

            write_freq: 0,

            hint_replicas: vec![],
