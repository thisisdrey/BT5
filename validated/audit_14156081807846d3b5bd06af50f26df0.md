### Title
Integer overflow via unchecked `BigInteger.longValue()` truncation in witness voting-reward computation enables unbacked-balance creation - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
The vote-reward accumulation/withdrawal logic computes each voter's share of a witness's rewards as an unbounded `BigInteger` (`Vi`, scaled by `10^18`) but converts the final per-vote reward back to `long` using the narrowing, non-checked `BigInteger.longValue()` instead of `longValueExact()`. Every other resource/exchange arithmetic path in this codebase (`ResourceProcessor`, `RepositoryImpl`, `SafeExchangeProcessor`, `MarketUtils`) was deliberately hardened to use `addExact`/`multiplyExact`/`longValueExact` so that overflow throws `ArithmeticException` rather than silently wrapping — this reward path was missed, reproducing the classic "integer overflow leads to information disclosure/data tampering" bug class from CVE-2022-42265.

### Finding Description
`DelegationStore`/`RewardViCalService` accumulate a per-cycle "Vi" value for each witness as an unbounded `BigInteger`:
```
BigInteger deltaVi = BigInteger.valueOf(reward).multiply(DECIMAL_OF_VI_REWARD).divide(BigInteger.valueOf(voteCount));
``` [1](#0-0) 
There is no floor on `voteCount` (a witness can legitimately have very few votes in a cycle), so `Vi` for a low-vote witness can grow far beyond `Long.MAX_VALUE` after only a handful of cycles because it is stored purely as `BigInteger`.

When a user withdraws or queries their reward, this unbounded `Vi` delta is multiplied by the user's *current* vote count and divided back down, then narrowed to `long` with `.longValue()` (not `longValueExact()`):
```java
long userVote = vote.getVoteCount();
reward += deltaVi.multiply(BigInteger.valueOf(userVote))
    .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
``` [2](#0-1) 
The identical pattern exists in the legacy/native path: [3](#0-2) 
and in `RewardViCalService.getNewRewardAlgorithmReward`: [4](#0-3) 

`BigInteger.longValue()` silently truncates to the low 64 bits and can produce an arbitrary (including negative-then-added, or huge positive) `long` when the source value exceeds `Long.MAX_VALUE`/`Long.MIN_VALUE`, instead of throwing as `longValueExact()` would. The resulting `reward` value is then credited without any sanity bound via `adjustAllowance`, which directly increases `account.allowance` — the balance a user can withdraw as real TRX:
```java
account.setAllowance(allowance + amount);
``` [5](#0-4) 

This is the same bug class as the CVE: unchecked arithmetic on attacker-influenced inputs (vote count chosen by the caller, accumulated `Vi` shaped by which witness/cycle the attacker votes for) that overflows and silently wraps rather than failing safely, resulting in tampered/incorrect data — here, a corrupted reward amount credited to an account balance.

Contrast with the rest of the codebase, which was explicitly hardened against exactly this failure mode: [6](#0-5) [7](#0-6) 

### Impact Explanation
If `reward` overflows during `.longValue()` truncation, the wrapped value (which can be arbitrarily large and positive due to two's-complement truncation of a huge `BigInteger`) is added directly to `account.allowance` via `adjustAllowance`, which is later paid out as real TRX through `WithdrawBalanceContract` / the `WITHDRAWREWARD` TVM opcode. This constitutes creation of unbacked balance / potential theft of funds, matching the CVE's "information disclosure or data tampering" impact translated to this domain's asset-integrity guarantees.

### Likelihood Explanation
Reachable by any unprivileged account: an attacker only needs to (1) freeze TRX for voting power, (2) vote for a witness that (by chance or attacker collusion/self-witness) has an extremely low total vote count in some cycles so that `Vi` grows large relative to `Long.MAX_VALUE / 10^18` bound, and (3) call `WithdrawBalanceContract` or the `WITHDRAWREWARD` TVM opcode after enough cycles have accumulated. No special privilege, SR collusion, or network-level access is required — only ordinary vote/freeze/withdraw transactions, so this fits within the "asset issuer/order placer/stake delegator" reachable surface.

### Recommendation
Replace `.longValue()` with `.longValueExact()` (or otherwise explicitly bound/clamp the value with an `ArithmeticException`-based guard consistent with the `hardenCalculation()`/`StrictMathWrapper` pattern already used elsewhere) in:
- `actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java` (`computeReward`)
- `chainbase/src/main/java/org/tron/core/service/MortgageService.java` (`computeReward`)
- `chainbase/src/main/java/org/tron/core/service/RewardViCalService.java` (`getNewRewardAlgorithmReward`)

so that an overflow is rejected (and the transaction/withdrawal fails) instead of silently wrapping into a corrupted reward/allowance value.

### Proof of Concept
1. Attacker freezes TRX for `TRON_POWER` and votes for a witness `W` that has (or can be steered to have, e.g. by voting alone for `W` in an otherwise low-participation cycle) `voteCount = 1` for several cycles while `W` continues to earn block/standby rewards.
2. `DelegationStore.accumulateWitnessVi` accrues `deltaVi = reward * 10^18 / 1` per such cycle into the unbounded `BigInteger` `Vi` for `W`, quickly exceeding `Long.MAX_VALUE` in magnitude (e.g., after only a few cycles at typical block-reward levels).
3. Attacker then increases their own vote for `W` (still bounded by their own frozen TRX) and calls `WithdrawBalanceContract` (or invokes `WITHDRAWREWARD` from a smart contract).
4. `computeReward`/`getNewRewardAlgorithmReward` computes `deltaVi.multiply(userVote).divide(10^18)`, which can exceed `Long.MAX_VALUE`; `.longValue()` truncates this to an unpredictable 64-bit value instead of throwing.
5. The truncated value is added to the account's `allowance` and becomes withdrawable as TRX, independent of the reward pool actually collected — demonstrating unbacked-balance creation from the overflow.
