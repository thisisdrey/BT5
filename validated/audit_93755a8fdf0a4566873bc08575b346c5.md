### Title
Unbounded array allocation from attacker-controlled length field in ABI array decoding - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytesArray` and `PrecompiledContracts.extractSigArray` read a 32-byte length word straight out of the smart-contract call data and use it, unvalidated against the actual size of the supplied `data`, to allocate a `byte[][]` and to drive `System.arraycopy`/`Arrays.copyOfRange` calls. This mirrors the CVE-2018-20671 root cause: a size field taken from untrusted input is used directly for buffer sizing/copy operations without bounds checking against the real backing buffer.

### Finding Description
`extractBytesArray` at [1](#0-0)  does:
```
int len = words[offset].intValueSafe();
byte[][] bytesArray = new byte[len][];
for (int i = 0; i < len; i++) {
  int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
  int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
  bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, bytesLen);
}
```
`extractSigArray` at [2](#0-1)  has the same pattern with `len` and `bytesOffset` taken from the call data. Both `len` and `bytesLen`/`bytesOffset` are derived from `DataWord.intValueSafe()` on caller-supplied words, and `extractBytes` performs `Arrays.copyOfRange(data, offset, offset + len)` at [3](#0-2) . Neither `len` nor `offset`/`bytesLen` is validated against `data.length` before the array allocation and copy: a caller can supply a length word close to `Integer.MAX_VALUE` (e.g. `words[offset]`), which is used directly as the size of a `new byte[len][]` reference array, or as an `offset`/`length` pair to `Arrays.copyOfRange` that reads far past the actual `data` buffer.

These helpers are used by the `ValidateMultiSign`/`BatchValidateSign` precompiled contracts (confirmed by `framework/src/test/java/org/tron/common/runtime/vm/BatchValidateSignContractTest.java` and `ValidateMultiSignContractTest.java`), which are precompiled TVM addresses callable by any smart contract via a normal `CALL`/`STATICCALL` opcode from a transaction — i.e., reachable by any unprivileged contract deployer/caller.

### Impact Explanation
- `new byte[len][]` with `len` near `Integer.MAX_VALUE` allocates ~17 GB of reference slots, which will throw `OutOfMemoryError`. `OutOfMemoryError` is a JVM `Error`, not a checked/unchecked `Exception`; if the TVM's precompiled-contract invocation path does not specifically catch `Throwable`/`Error` around this call, this propagates up and can crash or destabilize the node process executing the transaction, i.e., a denial-of-service against block processing.
- Supplying an out-of-range `bytesOffset`/`bytesLen` also risks `ArrayIndexOutOfBoundsException` / `NegativeArraySizeException` from `extractBytes`'s `Arrays.copyOfRange`, which, depending on whether the calling code path only catches specific `Exception` subtypes, may likewise propagate unexpected runtime errors.

### Likelihood Explanation
Any account can trigger this by deploying or calling a contract that invokes the `ValidateMultiSign`/`BatchValidateSign` precompile with crafted call data — no special privilege is required, and it costs only the transaction's energy/fee.

### Recommendation
Validate `len`, `bytesOffset`, and `bytesLen` against the actual `words.length`/`data.length` before using them for allocation or copying in `extractBytesArray` and `extractSigArray`, returning an error/`Pair.of(false, ...)` result instead of allocating unbounded arrays, consistent with the existing `offset > words.length - 1` guard already present at the top of these methods.

### Proof of Concept
Craft ABI call data to the `ValidateMultiSign`/`BatchValidateSign` precompiled address where the array-length word (`words[offset]`) is set to a very large value (e.g. `0x7FFFFFFF`); invoking this precompile from a contract triggers `new byte[len][]` in `extractBytesArray`, causing an `OutOfMemoryError` during execution.

**Note on confidence**: I could not fully verify (due to tool iteration limits) whether the TVM's precompiled-contract call wrapper (in `Program.java`/`callToPrecompiledAddress`) catches `Throwable`/`Error` broadly enough to contain an `OutOfMemoryError` and simply revert the transaction rather than propagate a JVM-level crash. If it does catch broadly, the practical impact would be reduced to a reverted/failed transaction (low severity) rather than a node crash. This should be confirmed by examining the exception handling around precompiled contract invocation in `Program.callToPrecompiledAddress` before treating this as confirmed Medium-severity.
