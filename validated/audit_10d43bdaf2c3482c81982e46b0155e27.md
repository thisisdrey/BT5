### Title
Protocol fee bypass via unit-amount chunking of Nep245/Imt TokenDiff intents - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::token_fee` zero-rates any `Nep245`/`Imt`/`Nep171` leg with `amount <= 1`, and fee is computed per individual `TokenDiff` intent rather than over the aggregate batch. A signer can split a large NEP-245/IMT swap into N separate `TokenDiff{diff:{token,-1},...}` intents (batched in one or more signed `MultiPayload`s that still net to zero at `Deltas::finalize`), paying `Pips::ZERO` fee on every leg while an equivalent single `TokenDiff{token,-N}` intent on a fungible-valued NEP-245 asset would owe `fee.fee_ceil(N)` to the `fee_collector`.

### Finding Description
The binding claimed to hold is: `fees_collected_from(N legs of amount=1) == fees_collected_from(1 intent of amount=N)` for the same net token movement on a Nep245/Imt token. In `TokenDiff::execute_intent`, for each `(token_id, delta)` in **a single intent's** `self.diff`, the fee is `Self::token_fee(token_id, delta.unsigned_abs(), protocol_fee).fee_ceil(amount)` [4](#0-3) . `token_fee` explicitly returns `Pips::ZERO` whenever `TokenIdType::Nep245 | TokenIdType::Imt` and `amount <= 1` (and always for `Nep171`) [3](#0-2) . Since `amount` is scoped to the single intent's delta rather than the sum across a batch, an attacker (or a maker/taker pair fully controlled by the attacker) can express a trade of N units as N separate signed `TokenDiff` intents each with `delta = ±1`, submitted together in `execute_intents`/`simulate_intents`. `Engine::execute_signed_intents` processes each `MultiPayload` sequentially via `execute_signed_intent` → `execute_intent`, computing and crediting fees independently per intent, and only calls the batch-wide `TransferMatcher`/invariant check once at the very end via `finalize()` [1](#0-0) , [5](#0-4) . Nothing in `MultiPayload::verify`, nonce handling, or `TransferMatcher::finalize` aggregates deltas *before* fee calculation — `finalize` only checks that net deltas cancel to zero, it has no fee logic [6](#0-5) . Thus the aggregate fee collected (`0`) diverges from what a single-intent equivalent trade of the same total amount would owe (`fee.fee_ceil(N) > 0` when `protocol_fee > 0`).

### Impact Explanation
This directly matches the listed Critical category "protocol fees bypassed" — the `fee_collector` account under `internal_add_balance` receives strictly less than the protocol fee configuration entitles it to for the total volume traded [7](#0-6) . This applies to any NEP-245-wrapped or IMT-represented fungible-valued asset (e.g., a valuable wrapped fungible token issued under the multi-token standard) whenever a signer chooses to structure trades as repeated unit legs instead of one bulk `TokenDiff`. It is fully repeatable across accounts, tokens, and batch sizes, with no bound other than gas/transaction size limits, and requires no privileged role — any two ordinary accounts (potentially both attacker-controlled) can execute the pattern. The only funds "at risk" are protocol revenue (fee_collector's expected credit), not third-party principal, but this matches the enumerated Critical impact bucket for fee bypass explicitly.

### Likelihood Explanation
Preconditions are minimal: the attacker needs a nonzero `protocol_fee` (`engine.state.fee()`), a NEP-245/IMT token balance in Defuse, and either a counterparty or a second self-controlled account to match deltas to zero across the batch. Constructing N `TokenDiff` intents with unique nonces and correct counter-deltas is straightforward and requires no special privilege — cost scales only with the number of legs (gas/transaction size), which is explicitly out of scope as a "resource exhaustion" concern but does not prevent the exploit for moderate N. This is fully feasible today with normal `execute_intents`/`simulate_intents` calls.

### Recommendation
Compute `token_fee`'s NFT/MT carve-out based on the token's actual fungibility characteristics (e.g., whether the underlying NEP-245/IMT token is truly a unique, non-fungible unit) rather than solely on the per-intent `amount`, or aggregate the total abs-delta per token across the whole batch (all `TokenDiff` intents processed within one `execute_signed_intents` call) before applying the `amount <= 1` exemption, so that fee liability cannot be reduced by fragmenting a trade into unit-sized legs.

### Proof of Concept
- Set up `Env::builder().fee(Pips::ONE_PERCENT)`; create a NEP-245 token contract wrapping a valuable fungible-like asset (decimals=0, amount semantics) and deposit balance `N` (e.g. 1000) to `user1`, and a counter-asset balance to `user2`.
- Test A (baseline): sign one `TokenDiff{diff:{nep245_token: -N, other_token: X}}` for user1 and a matching `TokenDiff{diff:{nep245_token: N, other_token: -X}}` for user2 in one `MultiPayloadArgs`; execute via `env.defuse_execute_intents`; assert `fee_collector` balance for `nep245_token` increases by `Pips::ONE_PERCENT.fee_ceil(N) > 0`.
- Test B (exploit): construct N pairs of `TokenDiff` intents, each leg with `delta = ±1` on `nep245_token` (and correspondingly fractioned `other_token` deltas summing to the same net `X`), signed by user1/user2 with distinct nonces, batched into one call to `execute_intents`/`simulate_intents`; assert the batch passes `finalize()` (`invariant_violated` is `None`) with the same net balance changes as Test A, but assert `fee_collector` balance for `nep245_token` is unchanged (`delta == 0`), demonstrating `fees_collected(Test B) == 0 != fees_collected(Test A) == Pips::ONE_PERCENT.fee_ceil(N)` for equivalent net trades.
