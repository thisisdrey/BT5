## Title
Unsynchronized iteration over the revoking `Chainbase`/`SnapshotImpl` chain lets a `head`-derived `Iterator` escape the lock protecting the snapshot chain, exposing `ConcurrentModificationException` / inconsistent-state reads to any API caller during block application - (File: chainbase/src/main/java/org/tron/core/db2/core/Chainbase.java)

### Summary
`Chainbase.iterator()` is only `synchronized` for the duration of retrieving the `Iterator` object itself; the returned iterator (built by `SnapshotImpl.iterator()`) is a live, un-synchronized view chained via `Iterators.concat`/`Iterators.transform` over a `HashMap` snapshot ("all") plus `getRoot().iterator()`. Callers reachable from HTTP/gRPC/JSON-RPC (e.g. `WitnessStore.getAllWitnesses()`, `ProposalStore.getAllProposals()`, `ExchangeStore.getAllExchanges()`, `AssetIssueStore.getAllAssetIssues()`, `ContractStore.getTotalContracts()`, `TronStoreWithRevoking.size()`/`isNotEmpty()`/`iterator()`) then continue to consume that iterator entirely outside of any lock, while the block-application thread (`SnapshotManager.advance()/merge()/retreat()/refreshOne()` invoked from `Manager.pushBlock`) concurrently reassigns `Chainbase.head`, relinks the snapshot chain (`setPrevious`/`setNext`), and merges/mutates the underlying `HashDB` maps of the very snapshots being traversed. This is the same bug class as `dashmap` GHSA-mpg5-fvwp-42m2: a reference obtained under a lock is allowed to outlive that lock and is used while the guarded structure keeps mutating.

### Finding Description
`Chainbase.iterator()`:
```java
@Override
public synchronized Iterator<Map.Entry<byte[], byte[]>> iterator() {
  return head().iterator();
}
``` [1](#0-0) 

The `synchronized` block only protects the call to `head().iterator()`; it releases the lock immediately after the `Iterator` reference is returned. The iterator itself (from `SnapshotImpl.iterator()`) is built by walking the mutable snapshot linked list and copying entries into a plain (non-concurrent) `HashMap`, then chaining with the root's iterator:
```java
@Override
public Iterator<Map.Entry<byte[], byte[]>> iterator() {
  Map<WrappedByteArray, WrappedByteArray> all = new HashMap<>();
  collect(all);
  ...
  return Iterators.concat(
      Iterators.transform(all.entrySet().iterator(), ...),
      Iterators.filter(getRoot().iterator(), ...));
}
``` [2](#0-1) 

`collect()` walks `getRoot().getNext()` chain links (`WeakReference<Snapshot> next` in `AbstractSnapshot`, non-volatile, no synchronization) while a separate thread can be actively rewriting those links: [3](#0-2) [4](#0-3) 

Meanwhile, `Manager.pushBlock` (block application, one thread) calls into `SnapshotManager.advance()`, `merge()`, `retreat()`, and `refreshOne()`:
- `advance()` calls `db.setHead(db.getHead().advance())`, creating a brand-new `SnapshotImpl` and rewiring `next`/`previous` pointers.
- `refreshOne()` merges older snapshots into `root`, then rewrites `next.getNext().setPrevious(root)` / `root.setNext(next.getNext())`, unlinking nodes an in-flight iterator may still be walking. [5](#0-4) [6](#0-5) 

None of these mutation paths (`advance`, `merge`, `refreshOne`) hold `Chainbase`'s per-instance lock (only `commit()`, `revoke()`, `pop()`, `enable()`, `disable()` in `SnapshotManager` are `synchronized`, and even those synchronize on the `SnapshotManager` instance, not on the per-store `Chainbase` object whose `iterator()`/`put()`/`delete()` are `synchronized` on the `Chainbase` instance itself). Because `Chainbase.iterator()`'s `synchronized` scope ends the moment the `Iterator` is returned, any API-serving thread walking that iterator races unguarded against the block-application thread mutating `HashMap`s, `WeakReference` links, and merged snapshot contents underneath it - exactly the "reference outlives the lock" unsoundness pattern.

Query paths reachable by any unprivileged/anonymous client that trigger this:
- `WitnessStore.getAllWitnesses()` → `Streams.stream(iterator())` [7](#0-6) 
- `ProposalStore.getAllProposals()` / `getSpecifiedProposals()` [8](#0-7) 
- `ExchangeStore.getAllExchanges()` [9](#0-8) 
- `AssetIssueStore.getAllAssetIssues()` [10](#0-9) 
- `ContractStore.getTotalContracts()`, `AbiStore.getTotalABIs()` and the generic `TronStoreWithRevoking.iterator()/size()/isNotEmpty()` used across many stores. [11](#0-10) 

These are wired to HTTP/gRPC/JSON-RPC handlers in `Wallet`/`RpcApiService` (e.g. `listwitnesses`, `listproposals`, `listexchanges`, `getassetissuelist`), all callable by any anonymous client, and run concurrently with the node's ongoing block-processing thread.

### Impact Explanation
An unauthenticated API client can trigger a live iteration over an in-flux snapshot chain at any time by simply calling standard list-style RPC/HTTP endpoints (witnesses, proposals, exchanges, asset issues, contracts). Because the returned iterator's backing structures (`HashMap` built by `collect()`, and the `WeakReference`-linked snapshot chain) are mutated without synchronization by the concurrently running block-application thread, this can cause:
- `ConcurrentModificationException` thrown from the API-serving thread mid-iteration (denial of service for that request / potential unhandled exception paths).
- Silently incomplete or inconsistent result sets (missing/duplicated/stale entries) returned to the client because entries can be merged, unlinked (`refreshOne` rewiring `previous`/`next`), or garbage-collected (`WeakReference<Snapshot> next`) mid-traversal, producing incorrect application-facing state (e.g., stale exchange/proposal/witness lists) without any explicit error.
- Repeated triggering under sustained RPC load increases the chance of hitting the race window on every produced block (each block push calls `advance()`/`merge()`/possibly `refreshOne()` on every registered `Chainbase`), making the race practically reachable rather than purely theoretical.

This does not directly cause fund loss, but it can serve an inconsistent/incorrect node state via a network-facing query API and destabilize an otherwise available API surface (crash of the serving thread on unhandled `ConcurrentModificationException` in code paths that do not catch it), which matches the "API the node can no longer serve" / node instability class called out in scope.

### Likelihood Explanation
The race window opens on every block (`advance()` at minimum, and periodically `refreshOne()`/`merge()` per the `maxFlushCount`/`maxSize` thresholds in `SnapshotManager`), so any sustained polling of list-style read RPCs (a completely unprivileged, unauthenticated action) creates a continuous opportunity for interleaving with the block-processing thread. No special access or malicious validator/witness behavior is required — an ordinary API client repeatedly calling `listwitnesses`/`listproposals`/`listexchanges` is sufficient to probabilistically hit the window. The bug is a genuine missing-synchronization issue (the lock scope in `Chainbase.iterator()` structurally cannot cover the caller's later use of the iterator), not a hypothetical.

### Recommendation
- Do not return a live iterator from `Chainbase.iterator()`; instead, materialize the result set (e.g., a defensive copy/list) while holding the lock, and hand back an iterator/list over that immutable copy.
- Alternatively, make `SnapshotImpl.collect()`/`iterator()` fully snapshot-safe by acquiring the same lock used for `advance()`/`merge()`/`refreshOne()` for the full duration of the copy, and ensure all chain-mutating operations in `SnapshotManager` (`advance`, `merge`, `retreat`, `refreshOne`) synchronize on the corresponding `Chainbase` instance(s), not just on `SnapshotManager`.
- Audit all call sites in `TronStoreWithRevoking` and derived stores (`WitnessStore`, `ProposalStore`, `ExchangeStore`, `AssetIssueStore`, `ContractStore`, `AbiStore`) that stream/iterate `revokingDB.iterator()` outside any lock and route them through the corrected, snapshot-consistent API.

### Proof of Concept
1. Start a java-tron full node with normal block production active (background thread continuously calling `Manager.pushBlock` → `SnapshotManager.advance()/merge()/refreshOne()` on every `Chainbase` in `dbs`).
2. From an unauthenticated client, issue a tight loop of HTTP/gRPC calls to a list endpoint backed by `TronStoreWithRevoking.iterator()`, e.g. `listwitnesses` (`WitnessStore.getAllWitnesses()`) or `listproposals` (`ProposalStore.getAllProposals()`), at a rate comparable to or faster than block production.
3. Because `Chainbase.iterator()`'s lock is released before the caller consumes the `Iterator`, and `SnapshotManager.advance()`/`refreshOne()` mutate the same snapshot chain/`HashMap`s without coordinating with that lock, repeated concurrent calls will eventually race with an in-progress `advance()`/`refreshOne()` call during block application, producing either a `ConcurrentModificationException` in the RPC/HTTP thread or a result list reflecting a torn/inconsistent snapshot state.
4. Exact reproduction timing (thread interleaving) could not be fully verified without running the code; the described data-race conditions are established purely from source inspection of `Chainbase.java`, `SnapshotImpl.java`, `AbstractSnapshot.java`, and `SnapshotManager.java`, and should be confirmed with a concurrency stress test (similar in spirit to the existing `framework/src/test/java/org/tron/core/jsonrpc/ConcurrentHashMapTest.java`, which already demonstrates the project's awareness of concurrent-map hazards in adjacent code, but does not cover this particular `Chainbase`/`SnapshotImpl` iterator path).

  private void refreshOne(Chainbase db) {
    if (Snapshot.isRoot(db.getHead())) {
      return;
    }

    List<Snapshot> snapshots = new ArrayList<>();

    SnapshotRoot root = (SnapshotRoot) db.getHead().getRoot();
    Snapshot next = root;
    for (int i = 0; i < flushCount; ++i) {
      next = next.getNext();
      snapshots.add(next);
    }

    root.merge(snapshots);

    root.resetSolidity();
    if (db.getHead() == next) {
      db.setHead(root);
    } else {
      next.getNext().setPrevious(root);
      root.setNext(next.getNext());
    }
  }
