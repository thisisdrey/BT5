### Title
Stranded repository-creation lock file permanently blocks repository creation at that path - (File: internal/gitaly/repoutil/lock.go)

### Summary
`repoutil.Lock` (`internal/gitaly/repoutil/lock.go:22-55`) is Gitaly's mutual-exclusion mechanism used by `repoutil.Create` (`internal/gitaly/repoutil/create.go:191-243`) to guarantee that only one process can create a repository at a given path at a time. The lock is a plain `O_CREATE|O_EXCL` file at `<repoPath>.lock` and is only released by a Go `defer unlock()` in the calling goroutine — there is no external TTL, no lease/expiry, and no automatic sweep that reclaims it if the holder never runs its own cleanup code. If the Gitaly process is killed (OOM-kill, SIGKILL, host crash, forced pod eviction, `git clone` hang combined with process termination, etc.) while inside this critical section, the `.lock` file is left on disk forever. Because `Lock()` unconditionally returns `safe.ErrFileAlreadyLocked` whenever the file exists, every subsequent RPC that tries to create a repository at that exact relative path (`CreateRepository`, `CreateFork`, `CreateRepositoryFromURL`, `CreateRepositoryFromBundle`, `CreateRepositoryFromSnapshot`, `ReplicateRepository`, `CreateObjectPool` — see `repositoryCreatingRPCs` in `internal/gitaly/storage/storagemgr/middleware.go:64-72`) will permanently fail. This mirrors the reported governance bug class: a single required actor/lock, once stuck in a bad state, deadlocks all future legitimate state transitions with no automatic recovery path.

### Finding Description
`repoutil.Create` takes the repository-directory lock before performing any of the repository-creation work: [1](#0-0) 

The lock itself is implemented as a simple exclusive-create lock file with no expiry semantics: [2](#0-1) 

Release relies entirely on the calling Go routine executing `unlock()` via `defer`. If the Gitaly process terminates abnormally (OOM kill, SIGKILL, node crash, container eviction) at any point between `Lock()` succeeding and the deferred `unlock()` running — which spans the entire repository build, config sync, transactional voting, and atomic rename (`internal/gitaly/repoutil/create.go:196-243`) — the on-disk `<repoPath>.lock` file survives the process death. Nothing else in the codebase removes this specific lock file automatically:

- Gitaly's stale-data housekeeping (`internal/git/housekeeping/clean_stale_data.go`) only scans and cleans lock files **inside** an already-existing repository (e.g. `refs/**/*.lock`, `packed-refs.lock`, `reftable` locks — see `FindStaleReferenceLocks`, `FindPackedRefsLock`, `FindStaleReftableLock` at lines 448-512). The `<repoPath>.lock` sibling file used by `repoutil.Lock` sits next to (not inside) the target repository directory and is created before the repository exists, so it is outside the scope of any housekeeping job that operates on an existing repository.
- Praefect's PostgreSQL-backed write-lock manager (`internal/praefect/datastore/lock_manager.go`) has TTL/expiry and a background sweep (`doc/serialized_writes.md:271-287`), but that mechanism only governs the `reference-transaction` voting lock for writes to *existing* repositories — it is entirely separate from `repoutil.Lock`'s filesystem lock used for repository *creation*.

Consequently, once the lock file is orphaned, `repoutil.Lock` will return `safe.ErrFileAlreadyLocked` (verified by the existing test at `internal/gitaly/repoutil/create_test.go:196-213`) for every future attempt to create a repository at that path, indefinitely.

### Impact Explanation
This is a Denial-of-Service condition reachable through completely ordinary user actions — any operation that triggers repository creation (fork, project import, mirror creation, `ReplicateRepository` during replica repair) exercises this code path. A crash or forced termination of the Gitaly process during that window (which is not rare in practice: `CreateRepositoryFromURL` shells out to a potentially long-running `git clone`, `CreateRepositoryFromSnapshot`/`CreateRepositoryFromBundle` extract externally supplied, untrusted archive/bundle data, and Kubernetes-style deployments routinely OOM-kill or evict pods under memory or disk pressure) permanently and silently prevents recreation of that exact repository path — including retries by the same user/operation — until an operator manually finds and deletes the stray `.lock` file on disk. There is no automatic detection, alerting, or self-healing for this specific case, unlike Praefect's DB-backed lock, which is TTL-bound and self-repairing.

### Likelihood Explanation
Likelihood is moderate: it requires the Gitaly process to terminate abnormally specifically while holding this repository-creation lock, which is a comparatively narrow window relative to overall process uptime, but the trigger (an ordinary user-initiated create/fork/import/replicate RPC) is entirely unprivileged and the window includes externally-influenced, potentially slow operations (network clone, archive extraction). Given Gitaly nodes are commonly deployed under resource constraints where OOM-kills and forced restarts do occur, this is a realistic, repeatable DoS vector against specific repository paths rather than a purely theoretical one.

### Recommendation
- Replace the plain `O_CREATE|O_EXCL` lock file with a lock that carries either process liveness information (e.g., PID + `flock(2)` advisory lock, which the OS automatically releases if the holding process dies) or an explicit TTL/expiry similar to the Praefect `RepoReferenceWriteLockManager` pattern (`internal/praefect/datastore/lock_manager.go`), so a crashed holder cannot indefinitely block future creations.
- Alternatively, extend Gitaly's stale-data housekeeping / storage-level sweep to also detect and reclaim orphaned `<repoPath>.lock` files (i.e., a lock file present with no corresponding repository directory and older than a grace period), mirroring the treatment already given to `refs/**/*.lock`, `packed-refs.lock`, and reftable locks.
- Ensure repository-creation RPCs surface a distinguishable, actionable error (rather than a generic `AlreadyLocked`) when the stuck-lock condition is detected, so operators/automation can safely clear it without guessing.

### Proof of Concept
1. An unprivileged user triggers repository creation through any of the RPCs in `repositoryCreatingRPCs` (`internal/gitaly/storage/storagemgr/middleware.go:64-72`), e.g. `CreateRepositoryFromURL`, which internally calls `repoutil.Create` → `repoutil.Lock` (`internal/gitaly/repoutil/create.go:191`).
2. While Gitaly is inside the locked critical section (cloning, voting, or about to `os.Rename` the temp dir into place, `internal/gitaly/repoutil/create.go:196-228`), the Gitaly process is forcibly terminated (OOM-kill, SIGKILL, node/container crash) before the deferred `unlock()` at line 195 can execute.
3. The `<repoPath>.lock` file, created via `os.OpenFile(..., O_CREATE|O_EXCL, ...)` in `internal/safe`/`repoutil/lock.go:37-52`, remains on disk.
4. Any subsequent call to `CreateRepository`, `CreateFork`, `CreateRepositoryFromURL`, `CreateRepositoryFromBundle`, `CreateRepositoryFromSnapshot`, or `ReplicateRepository` targeting the same relative path fails with `structerr.NewInternal("creating repository: %w", ... safe.ErrFileAlreadyLocked)`, exactly as demonstrated by the existing unit test `internal/gitaly/repoutil/create_test.go:196-213` (which manually pre-creates the `.lock` file to reproduce this exact failure mode).
5. No component in the codebase (RPC handlers, housekeeping, or Praefect) automatically detects or removes this file; the repository path remains permanently uncreatable until manual operator intervention.

```go
	// over creation of the repository. So we:
	//
	// 1. Lock the repository path such that no other process can create it at the same
	//    time.
	// 2. Vote on the new repository's state.
	// 3. Move the repository into place.
	// 4. Do another confirmatory vote to signal that we performed the change.
	// 5. Unlock the repository again.
	//
	// This sequence guarantees that the change is atomic and can trivially be rolled
	// back in case we fail to either lock the repository or reach quorum in the initial
	// vote.

	if err != nil {
		return fmt.Errorf("locking repository: %w", err)
	}
	defer unlock()
```

```go
func Lock(ctx context.Context, logger log.Logger, locator storage.Locator, repository storage.Repository) (func(), error) {
	path, err := locator.GetRepoPath(ctx, repository, storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, err
	}

	// Create the parent directory in case it doesn't exist yet.
	if err := os.MkdirAll(filepath.Dir(path), mode.Directory); err != nil {
		return nil, structerr.NewInternal("create directories: %w", err)
	}

	// We're somewhat abusing this file writer given that we simply want to assert that
	// the target directory doesn't exist and isn't created while we want to move the
	// new repository into place. We thus only use the locking semantics of the writer,
	// but will never commit it.
	locker, err := safe.NewLockingFileWriter(path)
	if err != nil {
		return nil, err
	}

	unlock := func() {
		if err := locker.Close(); err != nil {
			logger.WithError(err).ErrorContext(ctx, "closing repository locker failed")
		}
	}

	if err := locker.Lock(); err != nil {
		unlock()

		return nil, err
	}

	return unlock, nil
}
```
