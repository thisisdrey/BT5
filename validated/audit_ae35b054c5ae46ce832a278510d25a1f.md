### Title
Unbounded array allocation from attacker-controlled length field in TVM precompiled-contract input decoding - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`extractBytesArray` and `extractSigArray` in `PrecompiledContracts.java` read a "count" word directly out of ABI-encoded calldata and immediately use it to size a Java array, with no upper bound check and no verification that the declared count is consistent with the actual size of `data`. This mirrors the Pillow ICNS bug class: a size/count field taken from untrusted, attacker-supplied container data is trusted to drive a memory allocation before the content is validated. [1](#0-0) 

### Finding Description
Both helper functions pull `len` straight from a `DataWord`:

```java
int len = words[offset].intValueSafe();
byte[][] bytesArray = new byte[len][];
```

`intValueSafe()` can return any value up to `Integer.MAX_VALUE`, and `len` is used to allocate a `byte[][]` array before any of the `len` iterations attempt to read from `data`. Unlike memory-touching opcodes such as `CODECOPY`/`EXTCODECOPY`/`MLOAD` (whose sizes are gated by `EnergyCost.calcMemEnergy` / `checkMemorySize`, which caps EVM memory at a 3 MB `MEM_LIMIT` before any `new byte[...]` is executed), [2](#0-1)  these precompiled-contract input-decoding helpers have no equivalent size cap tied to energy accounting. The declared "array length" is trusted the same way Pillow trusted the ICNS container's declared image size, without checking it against the real payload size (`data.length`) first.

`isValidAbiEncoding` exists elsewhere in the file to sanity-check ABI shape for other paths, but `extractBytesArray`/`extractSigArray` do not call it before allocating, and `len` is not clamped against `data.length` or any fixed maximum before the `new byte[len][]` allocation. [3](#0-2) 

### Impact Explanation
An unprivileged contract deployer/caller can invoke the precompiled contract that consumes these helpers (batch signature validation style precompile) with minimal, small calldata that encodes a header word with a huge integer count. The JVM will attempt to allocate a `byte[][]` of that size (each element itself a pointer, so a length near `Integer.MAX_VALUE` requests multi-gigabyte allocations), which can throw `OutOfMemoryError` or otherwise induce excessive GC pressure/memory exhaustion in the node process executing the transaction. Because this happens inside TVM execution reachable from ordinary transactions (and constant calls via the JSON-RPC/HTTP `TriggerConstantContract` path), it can be triggered repeatedly by any anonymous API client or transaction broadcaster, causing node instability/crash — a legitimate DoS impact.

### Likelihood Explanation
Reaching this code only requires crafting calldata for a `CALL`/static call to the relevant precompiled contract address with a manipulated header word — no special privileges, stake, or witness/SR status are needed. The cost model (`getEnergyForData`) for these precompiles is generally based on outer `data.length` (a small value can be supplied), not on the declared inner array length, so the attacker can trigger a huge internal allocation for negligible energy cost, and via constant/read-only calls potentially at no on-chain cost at all.

### Recommendation
Before allocating `bytesArray`/`sigArray` in `extractBytesArray` and `extractSigArray`, validate `len` against a sane upper bound and against the actual remaining size of `data` (similar to `isValidAbiEncoding`/`verifyLength` patterns already used elsewhere in the codebase, e.g. `RLP.verifyLength`), rejecting the call (returning `Pair.of(false, ...)`) instead of allocating when the declared count cannot be backed by the supplied `data`.

### Proof of Concept
1. Construct calldata for the affected precompiled contract such that the header word at the array-length offset decodes (via `intValueSafe()`) to a very large value (e.g., close to `Integer.MAX_VALUE`), while the rest of `data` remains minimal.
2. Submit this as a `TriggerConstantContract` call (or an on-chain transaction) invoking the corresponding TVM precompile address.
3. Observe the node attempt `new byte[len][]` during `extractBytesArray`/`extractSigArray` execution, resulting in excessive memory allocation and potential `OutOfMemoryError`/node instability.

*Note: I could not directly view the exact `execute()` method of the specific precompiled contract that calls `extractBytesArray`/`extractSigArray` (its energy-cost function specifically) within the available search results, so the precise energy amount required to reach this code path is not fully confirmed from the indexed content — this should be verified in a full read of `PrecompiledContracts.java` before remediation.*

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

    if (data == null || data.length % WORD_SIZE != 0) {
      return false;
    }
    long tail = subtractExact(data.length, multiplyExact(headerWords, WORD_SIZE));

  private static long calcMemEnergy(long oldMemSize, BigInteger newMemSize,
                             long copySize, int op) {
    long energyCost = 0;

    checkMemorySize(op, newMemSize);

    // memory SUN consume calc
    long memoryUsage = (newMemSize.longValueExact() + 31) / 32 * 32;
    if (memoryUsage > oldMemSize) {
      long memWords = (memoryUsage / 32);
      long memWordsOld = (oldMemSize / 32);
      long memEnergy = (MEMORY * memWords + memWords * memWords / 512)
          - (MEMORY * memWordsOld + memWordsOld * memWordsOld / 512);
      energyCost += memEnergy;
    }

    if (copySize > 0) {
      long copyEnergy = COPY_ENERGY * ((copySize + 31) / 32);
      energyCost += copyEnergy;
    }
    return energyCost;
  }

  private static void checkMemorySize(int op, BigInteger newMemSize) {
