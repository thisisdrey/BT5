### Title
Unauthenticated dust deposits/transfers fill a victim's token list and permanently lock them out of new collateral and debt positions - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The memos bug class is "missing authorization lets anyone write state into another user's account." The Metronome analog is the permissionless beneficiary parameter on `DepositToken.deposit(amount_, onBehalfOf_)` and the recipient-side list update inside `DepositToken._transfer`. Both paths call `Pool.addToDepositTokensOfAccount(victim)`, which enforces `MAX_TOKENS_PER_USER = 30` across the victim's combined deposit + debt token lists. An unprivileged attacker can push a victim's list to the cap with dust, after which every operation that would add a new token to the victim's list reverts with `UserReachedMaxTokens`.

### Finding Description
- `DepositToken.deposit` takes an arbitrary `onBehalfOf_` beneficiary and mints msdTOKEN to it with no consent check [1](#0-0) .
- `_mint` (and `_transfer`) add the token to the recipient's pool-level list whenever the recipient's balance was zero [2](#0-1) .
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` are guarded by `onlyIfAdditionWillNotReachMaxTokens`, reverting once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [3](#0-2) [4](#0-3) .
- Removal only happens when a balance returns to zero (`_burn`/`_transfer` → `removeFromDepositTokensOfAccount`) [5](#0-4) .

Attack: attacker calls `deposit(1 wei, victim)` once on each listed deposit token (the pool itself is capped at 30 deposit tokens, `addDepositToken` reverts at `MAX_TOKENS_PER_USER` [6](#0-5) ), or transfers 1 wei of msdTOKEN to the victim. If the victim already holds tokens, the attacker only needs to fill the remaining slots.

Consequences for the victim:
1. `deposit(...)` of any *new* collateral type reverts — its `_mint` hits `addToDepositTokensOfAccount` and rolls back.
2. `DebtToken._mint` for a *new* debt token reverts in `addToDebtTokensOfAccount` [7](#0-6) , blocking `issue` and `SmartFarmingManager.leverage`/`flashDeposit` flows that would create a new debt position.
3. Receiving msdTOKEN transfers of tokens they don't already hold reverts.
4. If the victim has outstanding debt, the dust msdTOKEN balances are locked by `_revertIfLocked`/`unlockedBalanceOf` [8](#0-7) , so the victim cannot transfer the dust away to free the slots while `issuableInUsd == 0` — the list entries are stuck until the victim repays debt.

No privileged role is needed; the only cost to the attacker is ~30 wei-denominated dust deposits (plus a deposit fee if configured).

### Impact Explanation
Temporary-to-persistent denial of collateral top-ups and new borrowing for the targeted account. A victim with an unhealthy or deteriorating position cannot deposit a new collateral type nor open a new debt/leverage position to manage it, and cannot evict the attacker-planted list entries while their balances are locked against debt — they can only repay existing debt or add more of already-held collateral. This qualifies as temporary freezing of funds/functionality, and in the locked-balance case persists until the victim repays debt.

### Likelihood Explanation
Fully permissionless, cheap (dust × number of tokens), repeatable against any account, and effective on the deployed configuration since `MAX_TOKENS_PER_USER` is a constant and the entry-point functions carry no per-recipient authorization. Partially self-limiting: victims with no debt can transfer dust out to free slots, and topping up *existing* collateral tokens is unaffected.

### Recommendation
- Only add a token to a recipient's account list on beneficiary-initiated paths (e.g., `deposit` to self), or make recipients opt in before `deposit onBehalfOf`/`transfer` can register new tokens on their account.
- Alternatively, exempt accounts at the cap gracefully: allow `deposit`/`issue` to succeed but skip list insertion when the set is full, tracking membership only for accounts below the cap.
- Allow locked dust positions to be removable (e.g., a `sweep` of zero-value list entries) so griefed slots can always be freed.

### Proof of Concept
Hardhat-style sketch (adapt to the existing fixture in `test/DepositToken.test.ts`):

```ts
// victim has no position; pool has >= 30 listed deposit tokens
for (const dt of depositTokens) {
  await underlying.mint(attacker.address, 1n);
  await underlying.connect(attacker).approve(dt.address, 1n);
  await dt.connect(attacker).deposit(1n, victim.address); // fills victim's list
}
// now any new-token action for victim reverts
await expect(
  newDepositToken.connect(victim).deposit(parseEther('1'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(
  newDebtToken.connect(victim).issue(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
// with victim debt + zero issuableInUsd, victim cannot transfer the dust out:
await expect(
  dustToken.connect(victim).transfer(attacker.address, 1n)
).to.be.revertedWithCustomError(dustToken, 'NotEnoughFreeBalance');
```

Caveat: I did not fully verify `SmartFarmingManager` leverage internals or whether a governance-facing mitigation (e.g., an allowlist on `onBehalfOf`) already exists elsewhere; the core deposit/transfer → `addTo*TokensOfAccount` → `UserReachedMaxTokens` path is confirmed in `DepositToken.sol`, `DebtToken.sol`, and `Pool.sol`.
