## Analysis

The reported bug class is: a validation check treats an "open"/ambiguous scope value as equal to a specific scope, so data authorized for one context (bridge) is silently accepted in a different context (a different bridge on the same network) because the signed/checked value never actually commits to which context it belongs to.

The same structural flaw exists in the StackerDB chunk-signing scheme.

### Root cause

`SlotMetadata::auth_digest()` in [1](#0-0)  computes the signed digest as `hash(slot_id || slot_version || data_hash)`. It never includes the target StackerDB's contract identifier ("which bridge/DB this signature is for"). `SlotMetadata::verify()` at [2](#0-1)  only checks that the recovered public key hash equals the caller-supplied `principal` — again with no contract binding.

Contract-scoping is instead enforced *only* by a side lookup: the node resolves "who owns slot X in contract C" and then checks the signature against that address:

- `try_replace_chunk` in [3](#0-2)  looks up `slot_validation.signer` for `(smart_contract, slot_desc.slot_id)` and calls `slot_desc.verify(&slot_validation.signer)`.
- `validate_received_chunk` (used for both sync downloads and unsolicited `StackerDBPushChunk`) in [4](#0-3)  does the identical thing via `self.stackerdbs.get_slot_signer(smart_contract_id, data.slot_id)`.

Because the digest itself carries no contract discriminator, **any signature that is valid for `(slot_id, slot_version, data_hash)` in contract A is equally valid for the same tuple in contract B**, provided the address assigned to `slot_id` happens to match in both contracts.

That precondition is not hypothetical — it is guaranteed by the signer-slot boot contracts. All per-message-type StackerDB contracts for a given signer set/page pull their slot assignment from the *same* underlying list:

- `signers-0-xxx.clar`: `(contract-call? .signers stackerdb-get-signer-slots-page u0)` [5](#0-4) 
- `signers-1-xxx.clar` analogously calls page `u1`.
- `MessageSlotID` enumerates `BlockResponse = 1`, `StateMachineUpdate = 2`, `BlockPreCommit = 3` [6](#0-5) , each materialized as a distinct contract (`.signers-0-1`, `.signers-0-2`, `.signers-0-3`), but all deriving slot ↔ signer assignment from the identical `stackerdb-signer-slots-0`/`-1` variable in `.signers` [7](#0-6) .

So for a fixed signer set/page, the same StacksAddress owns `slot_id = k` in the `BlockResponse`, `StateMachineUpdate`, and `BlockPreCommit` StackerDB contracts simultaneously.

### Title
Cross-contract StackerDB chunk signature replay due to missing contract discriminator in signed digest - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata`'s signed digest omits the StackerDB smart-contract identifier, so a chunk signature that is valid for one signer-message StackerDB (e.g. `.signers-0-1` / BlockResponse) is also valid for a different StackerDB contract that shares the same slot-to-signer mapping (e.g. `.signers-0-2` / StateMachineUpdate, `.signers-0-3` / BlockPreCommit), because both consult the same `.signers` slot-assignment table. This mirrors the reported bridge issue where a broadly-scoped discriminator let a snapshot authorized for "any bridge" be accepted by an unintended bridge.

### Finding Description
`auth_digest()` binds only `(slot_id, slot_version, data_hash)` [1](#0-0) . Contract scoping happens exclusively in the caller (`try_replace_chunk`, `validate_received_chunk`) via a DB lookup of `(smart_contract, slot_id) → signer`. Since the three per-message-type contracts for a given signer-set page (`signers-0-1/2/3` or `signers-1-1/2/3`) all copy their `(signer, slot_id)` list from the same `.signers` variable, an address's slot index is identical across those contracts. A chunk validly signed by signer S for contract A at `(slot_id, slot_version, data_hash)` therefore recovers to the exact same address when replayed into contract B at the same `(slot_id, slot_version, data_hash)`, passing `verify()` even though it was never produced for contract B.

### Impact Explanation
Any remote peer relaying gossip (e.g. via unsolicited `StackerDBPushChunk`, handled in `handle_unsolicited_StackerDBPushChunk`) can take a chunk it has observed on one signer-message StackerDB and rebroadcast it, unmodified, as if it were a legitimate chunk for a sibling StackerDB contract belonging to the same signer set/page. This is an unauthorized write of forged/misattributed data into a StackerDB that other signers and the miner (`stackerdb_listener.rs`) consume as authenticated signer-set state — network-wide propagation of forged data, without needing any private key.

### Likelihood Explanation
No secret material is required — only observation of one legitimately signed chunk (e.g. a slot with `slot_version=1` in `BlockResponse` where the signer happens to reuse identical bytes/version, or any deliberate cross-posting by the signer's own dry-run/test tooling, or the attacker controlling one message and choosing data that collides). The likelihood is bounded by needing a genuine chunk with matching `(slot_id, slot_version, data_hash)` observed for the sibling contract, but nothing in the protocol prevents or even detects such cross-contract replay; it is a structural design gap, not a probabilistic collision requirement, since an attacker who is also a legitimate signer (holding the signing key for their own slot) can trivially produce one signature and post identical `(slot_id, slot_version, data)` chunks to all three sibling contracts, each accepted as independently "authenticated" for that specific StackerDB even if the payload is nonsensical for that message type.

### Recommendation
Include the StackerDB's `QualifiedContractIdentifier` (or an equivalent unique discriminator) inside `SlotMetadata::auth_digest()` so that a signature is cryptographically bound to the specific contract it was created for, analogous to avoiding the overly-permissive `header.discriminator == allowedDiscriminator1` check in the referenced report.

### Proof of Concept
1. Signer S is assigned `slot_id = 0` in both `.signers-0-1` (BlockResponse) and `.signers-0-2` (StateMachineUpdate), per the shared `stackerdb-signer-slots-0` list.
2. S signs a `StackerDBChunkData { slot_id: 0, slot_version: 1, data: X }` intended for `.signers-0-1` — `chunk.sign(&S)` computes `auth_digest = hash(0 || 1 || sha512_256(X))`.
3. An observer (or S itself) submits the identical `(slot_id=0, slot_version=1, sig, data=X)` to `.signers-0-2` via `POST /stackerdb/.signers-0-2` or via P2P `StackerDBPushChunk`.
4. `validate_received_chunk`/`try_replace_chunk` for `.signers-0-2` looks up the signer for `slot_id=0` in that contract (same address S), calls `slot_metadata.verify(&S)`, which succeeds because the digest never referenced the contract — the chunk is accepted and stored as an authentic `StateMachineUpdate` message even though it was only ever authorized as a `BlockResponse` payload.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
