### Title
Out-of-bounds slice panic parsing an attacker-supplied `.a` archive symbol map in `cmd/link` - ([File: src/cmd/link/internal/ld/ar.go])

### Summary
`readArmap` in `cmd/link/internal/ld/ar.go` parses the archive symbol map (`armap`) of a host `.a` archive without validating that the declared entry size is large enough to hold the fixed-size word count/offset fields, or that the derived symbol count `c` is consistent with the remaining buffer length. A malicious module that bundles a corrupted/crafted `.a` archive (a legitimate, common cgo pattern via `#cgo LDFLAGS: -L. -lfoo`) can make `go build`/`go link` panic with an out-of-range slice access while resolving `undefs` from the archive's symbol table, crashing the build for anyone who builds the module. This is conceptually the same bug class as the Wasmtime report: an attacker-controlled size field is trusted to determine how much fixed-width data is read/consumed, and insufficient bounds validation lets the "load" run past the buffer.

### Finding Description
Attacker input: a module's package directory ships a hand-crafted static archive (e.g. `libb.a`) referenced by `#cgo LDFLAGS: -L. -lb` as documented in `src/cmd/cgo/doc.go:87-97` and exercised in `src/cmd/go/testdata/script/cgo_undef.txt:1-24`, so ordinary `go build` of the module invokes cgo/host-object linking.

Entry point: `cmd/link/internal/ld.hostArchive` (`src/cmd/link/internal/ld/ar.go:103-189`) opens the archive, reads the first header via `nextar`, and if it names `/` or `/SYM64/` calls `readArmap` (`src/cmd/link/internal/ld/ar.go:136-140, 196`).

Failed checks / sink: in `readArmap` (`src/cmd/link/internal/ld/ar.go:196-247`):
- `contents := make([]byte, atolwhex(arhdr.size))` sizes the buffer purely from the attacker-controlled `size` field in the archive header, with no minimum-size check (`src/cmd/link/internal/ld/ar.go:203-206`).
- `c = binary.BigEndian.Uint32(contents)` (or `Uint64` for `SYM64`) unconditionally reads 4/8 bytes from `contents` (`src/cmd/link/internal/ld/ar.go:208-213`); if `size` is smaller than `wordSize` this indexes past the slice.
- `contents = contents[wordSize:]` and later `names := contents[c*uint64(wordSize):]` (`src/cmd/link/internal/ld/ar.go:214,218`) use the untrusted symbol count `c` to slice `contents` with no bound check against `len(contents)`.
- The subsequent loop indexes `names[n]` while scanning for a NUL terminator (`src/cmd/link/internal/ld/ar.go:220-224`), again with no bounds validation.

Any of these can produce a Go runtime panic (`slice bounds out of range` / `index out of range`), which is unrecovered in `cmd/link`, terminating the linker process during the build.

### Impact Explanation
This causes a real, reproducible panic in `cmd/link` triggered purely by malformed input in a module's bundled archive - a denial of service against the build process for any victim who runs `go build` on such a module (a normal, unprivileged workflow: `go build`/`go get` of a published module that contains a native archive used via cgo). It does not grant memory disclosure or code execution beyond crashing the toolchain, so it aligns with a Go **PUBLIC** track DoS-class bug (crash-on-malformed-input during build), analogous to the "uncaught segfault"/DoS framing in the Wasmtime advisory (case 3) rather than to any arbitrary-read/write primitive.

### Likelihood Explanation
Victim workflow: any Go developer running `go build`/`go vet`/`go test` on a module that ships a cgo package with a `#cgo LDFLAGS` pointing at a locally-bundled static archive (a documented, supported feature, see `src/cmd/cgo/doc.go:87-97`) will have `cmd/link` parse that archive. An attacker only needs to publish such a module (or get a victim to build one), requiring no special privileges, matching the "published module/archive/source consumed by a normal victim workflow" premise. Reachability specifically requires `CGO_ENABLED=1` and the archive to reach the `armap` (`/` or `/SYM64/`) branch of `readArmap`, which is a normal part of `.a` archive processing, not a rare edge case.

### Recommendation
In `readArmap` (`src/cmd/link/internal/ld/ar.go`), validate that `len(contents) >= wordSize` before reading the initial count, and after computing `c`, validate that `c*wordSize <= uint64(len(contents))` (checking for overflow) before slicing `names := contents[c*uint64(wordSize):]`. Also bound the inner `for names[n] != 0 { n++ }` loop by `len(names)` and return a proper link-time error (e.g., via `Exitf`) instead of panicking when the archive's symbol table is malformed or truncated.

### Proof of Concept

```go
package ld

import "testing"

// Demonstrates that readArmap panics instead of returning
// a graceful error when the armap "size" field is smaller
// than wordSize (4 bytes for the 32-bit symbol table),
// or when count*wordSize exceeds len(contents).
func TestReadArmapMalformedSizePanics(t *testing.T) {
	defer func() {
		if r := recover(); r == nil {
			t.Fatal("expected panic from malformed archive symbol map, but readArmap succeeded silently")
		}
	}()

	// A truncated 32-bit armap: size=2 bytes, but Uint32
	// unconditionally reads 4 bytes from `contents`.
	arhdr := ArHdr{name: "/", size: "2"}
	f := openTestArchiveWithArmapPayload(t, []byte{0x00, 0x01}) // len=2 < wordSize(4)

	// Expected (fixed) behavior: readArmap returns/Exitf's a clean
	// "malformed archive" error rather than panicking with
	// "runtime error: slice bounds out of range" / "index out of range".
	readArmap("libmalicious.a", f, arhdr)
}
```
Note: `openTestArchiveWithArmapPayload` is a placeholder helper that would need to construct a minimal `!<arch>\n` archive with a `/` header whose declared `size` (2) is inconsistent with the amount of data actually needed by `binary.BigEndian.Uint32`; a background agent with filesystem/test access should implement this helper against the real `bio.Reader`/`nextar` machinery in `src/cmd/link/internal/ld/ar_test.go` to reproduce the panic end-to-end and confirm the exact panic message before landing the bounds-check fix.
