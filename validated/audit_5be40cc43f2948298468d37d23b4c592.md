### Title
Unbounded heap-buffer over-read parsing attacker-controlled ZIP extra-field records in ijar's central directory reader - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc`, invoked when Bazel's `ijar` tool builds an interface jar (`java_common.run_ijar`, `ijar.cc`) from any input `.jar`, parses the central directory of an attacker-supplied jar without any bounds checking, unlike `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` before every read.

### Finding Description
`ProcessCentralDirEntry` reads fixed-size fields (`get_u4le`/`get_u2le`) directly from the mmap'd input buffer and then walks the "extra fields" region using an attacker-controlled `extra_field_length`: [1](#0-0) 

Inside the extra-field loop, each iteration reads a 2-byte `header_id` and 2-byte `data_size` and advances `extra_p` by the attacker-supplied `data_size`, with no check that `extra_p + 4` or `extra_p + data_size` stays within the mapped region, and if the (possibly forged) `header_id` matches `ZIP64_EXTRA_FIELD_TAG`, it reads 8 more bytes via `get_u8le(extra)`: [2](#0-1) 

None of `get_u4le`, `get_u2le`, `get_u8le`, or the `memcpy` of the filename call `EnsureRemaining` (that helper is defined and used exclusively in `ProcessLocalFileEntry`/`SkipFile`/`ProcessFile`): [3](#0-2) 

A crafted central directory entry with an inflated `extra_field_length` and a chain of extra-field records whose `data_size` values keep pushing `extra_p` forward can walk past the true end of the extra fields, past the end of the central directory, and potentially past the end of the mmap'd file entirely, then interpret whatever bytes it lands on as a fake `ZIP64_EXTRA_FIELD_TAG` and issue an 8-byte `get_u8le` read beyond the mapping — the same "attacker-crafted variable-length field drives a fixed-width unchecked read past the buffer" pattern as the ImageMagick PSD/`PushShortPixel` bug cited in the report. The stale comment ("the central directory is always followed by another data structure that has a signature, so parsing it this way is safe") is the only justification offered, and it does not bound the inner extra-field-record walk at all.

### Impact Explanation
This is a heap/mmap out-of-bounds read triggered purely by the byte content of a `.jar`/`.aar`/`.zip` file, not by any network or credential compromise. `ijar` runs inside the Bazel server process (or as a standalone action) whenever `java_common.run_ijar` processes a jar for compile-classpath reduction; jars reaching this path routinely originate from external dependencies (`http_jar`, `http_archive`, Maven-resolved artifacts) that an untrusted upstream author or mirror operator controls. A successful over-read can crash the Bazel build (denial of service) or, depending on what unmapped/adjacent memory is read and echoed back (e.g., through the interpreted ZIP64 sizes used later for allocation/copy decisions), corrupt data or lead to further memory-safety issues in downstream jar-writing logic.

### Likelihood Explanation
Likelihood is limited by two factors: (1) the region immediately following the mmap'd file is not always immediately unmapped (page-aligned mmap means the over-read must cross a page boundary to fault, which requires either a file whose length lands near a page boundary or a sufficiently large `data_size` walk), and (2) many callers only use `run_ijar` on jars produced by the build itself rather than arbitrary third-party jars, though `http_jar`/`java_import`-style dependencies on externally-hosted jars are a realistic vector. This is a genuine reachable parsing bug, but triggering an actual out-of-bounds page fault (as opposed to reading further into the mapping/other mapped pages) requires a specific `extra_field_length`/`data_size` construction and file-size alignment, which was not verified experimentally here.

### Recommendation
Add explicit bounds checks in `ProcessCentralDirEntry` (mirroring `EnsureRemaining`) before every field read: verify `p`/`extra_p` never exceed `zipdata_in_ + input_file_->Length()` when reading the fixed header fields, when computing `extra_p bound = p (after += extra_field_length)`, and inside the extra-field loop before reading each `header_id`/`data_size` pair and before advancing `extra_p` by `data_size`. Reject the entry with an error instead of continuing to parse once a read would exceed the mapped file length.

### Proof of Concept
A reproducible JUnit/`shell` test would construct a minimal ZIP central directory entry with:
1. A valid `CENTRAL_FILE_HEADER_SIGNATURE`.
2. `extra_field_length` set to a small value that only partially fits the mapped buffer (e.g., ending exactly at `input_file_->Length()`).
3. Within that truncated extra-fields region, a fake extra-field record whose `data_size` (read from the last 2 bytes before EOF) is deliberately large enough that `extra_p += data_size` pushes past `p` (end of extra fields) and past `input_file_->Length()`, with the two bytes preceding EOF crafted so `header_id == 0x0001` (`ZIP64_EXTRA_FIELD_TAG`), causing `get_u8le(extra)` to read 8 bytes starting near/at EOF.
4. Feed this crafted `.jar` to `ijar`/`zipper` (e.g., via `ZipExtractor::Create(...)->ProcessNext()` in a `BuildIntegrationTestCase`, or `bazel build` on a target using `java_common.run_ijar` over a `java_import` pointing at the malicious jar) under ASan and confirm a heap-buffer-overflow (read) report at `zip.cc`'s `get_u8le`/`get_u2le` call sites inside `ProcessCentralDirEntry`.

This could not be fully validated in this session — building and running the crafted archive under ASan to confirm an actual out-of-bounds fault (versus reading harmless adjacent mapped bytes) was not performed.

  int EnsureRemaining(size_t n, const char *state) {
    size_t in_offset = p - zipdata_in_;
    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "
                   "expected %zd more bytes but found %zd.\n",
                   in_offset, state, n, remaining);
    }
    return 0;
  }
