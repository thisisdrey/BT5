## Title
Unbounded array allocation in TVM precompiled-contract input parsing enables node OOM/crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read an attacker-controlled 32-byte word from the smart-contract calldata and use it directly, without any upper bound, as the length of a Java array allocation (`new byte[len][]`), before any comparison against the actual size of the supplied calldata.

### Finding Description
`extractBytesArray`/`extractBytes32Array`/`extractSigArray` parse the calldata passed to a precompiled contract (invoked via the `CALL`/`STATICCALL` TVM opcode when the target address matches a precompile such as `BatchValidateSign` or `ValidateMultiSign`): [1](#0-0) [2](#0-1) [3](#0-2) 

`len` is derived from `words[offset].intValueSafe()`, i.e. a single 32-byte word taken from calldata that an attacker fully controls. There is no check that `len` is consistent with the actual size of `data`/`words` before `new byte[len][]` is executed — the loop that would eventually index out of bounds (and fail) runs *after* the allocation already occurred. `intValueSafe()` can return values up to `Integer.MAX_VALUE`, so an attacker can supply a small calldata payload (a few 32-byte words) that merely declares a huge array length in the length-prefix word, forcing the JVM to attempt to allocate an array of up to ~2^31 references (~16 GB on 64-bit JVMs) in a single instruction.

This is directly analogous to the reported PowerDNS bug class: a small, cheaply-crafted request field is trusted as an allocation size with no upper bound, causing unbounded memory allocation.

### Impact Explanation
Any account (no special privilege required) can broadcast a transaction, or make a `triggerconstantcontract`/`triggersmartcontract` call, that invokes the `BatchValidateSign` or `ValidateMultiSign` precompile with a crafted length word. When the transaction is executed as part of block application (`Manager`), every full node/witness that processes the block runs this same TVM execution path, so the allocation attempt happens on every node in the network. A sufficiently large declared length forces an `OutOfMemoryError` (or, on constrained heaps, kills the process), producing a synchronized denial-of-service across the network when the transaction is included in a block, or a targeted DoS against a single node via the `triggerconstantcontract`/`triggersmartcontract` HTTP/gRPC query APIs (constant calls do not require broadcasting and are directly reachable by any HTTP/gRPC client of `Wallet`).

### Likelihood Explanation
This requires no special node role or privileged key — any transaction broadcaster or JSON-RPC/HTTP client with contract-call access to a deployed contract that forwards calldata to these precompiles (or a directly crafted `triggerconstantcontract` call) can reach the vulnerable code path. Because the allocation size is decoupled from the actual submitted calldata length, the resource cost to the attacker (bandwidth/energy to submit a few words of calldata) is negligible compared to the potential ~16 GB allocation attempt on the victim node.

### Recommendation
Before allocating `bytes32Array`/`bytesArray`, validate that `len` is bounded both by a sane maximum (e.g., derived from `SIG_LENGTH`/expected signer counts already enforced elsewhere in `BatchValidateSign`/`ValidateMultiSign`) and by the actual size of `words`/`data` (i.e., `offset + len` must not exceed the available word count), rejecting the call (returning failure, not throwing) if the declared count is inconsistent with the supplied calldata length, mirroring the existing bounds check in `extractBytesArray`'s `offset > words.length - 1` guard but applied to `len` as well.

### Proof of Concept
I could not fully verify the exact `getEnergyForData()`/`execute()` wiring for `BatchValidateSign` and `ValidateMultiSign` within the available iterations (the class bodies for those two precompiles were not retrieved), so the following describes the reachable pattern based on confirmed code, but the precise minimal calldata layout that triggers each call site should be validated with a Devin session:

1. Deploy or call an existing contract that performs a low-level `staticcall`/`call` to the `BatchValidateSign` (address `0x66`) or `ValidateMultiSign` precompile address, OR invoke it directly via `triggerconstantcontract` with `contract_address` set to that precompile address.
2. Craft calldata whose header word (parsed by `words[offset].intValueSafe()`) declares a very large count (close to `Integer.MAX_VALUE`) while providing only a few actual data words after it.
3. Submit via `triggerconstantcontract` (HTTP/gRPC, no broadcast needed) or broadcast as a real transaction — `extractBytesArray`/`extractBytes32Array`/`extractSigArray` will attempt `new byte[len][]`, causing an immediate large allocation attempt independent of the small calldata actually transmitted.   private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
