### Title
Stale locally-cached StackerDB slot-signer authorization allows a deauthorized signer to keep writing/propagating chunks - (File: `stackslib/src/net/stackerdb/db.rs`)

### Summary
`try_replace_chunk` authenticates an incoming StackerDB chunk against the *locally stored* `slot_validation.signer` for that slot, not against the signer set currently defined on-chain by the controlling smart contract. That local table is only refreshed when `create_or_reconfigure_stackerdbs` → `reconfigure_stackerdb` runs, which itself only happens when a coordinator "stackerdb update" signal is consumed in `refresh_stackerdb()`. Between an on-chain signer-set change and that refresh, a party who was a legitimate signer before the change (but has since been removed/rotated out by the contract) can still successfully sign and write/push chunks to their old slot, and the network will accept and gossip that "stale-signer" data as valid.

### Finding Description
Chunk write authorization is decided purely from data cached in the node's own `chunks` table:

- `StackerDBTx::try_replace_chunk` looks up `slot_validation` (`self.get_slot_validation(...)`) and checks `slot_desc.verify(&slot_validation.signer)`, i.e. it verifies against whatever signer address is currently stored locally for that slot. [1](#0-0) 

- That stored `signer` column is only updated by `reconfigure_stackerdb`, which compares the new on-chain slot list against the existing local entries and rewrites a slot's signer only when it detects a change (`existing_validation.signer == *principal` short-circuits; otherwise it resets the slot). [2](#0-1) 

- `reconfigure_stackerdb` is only invoked from `create_or_reconfigure_stackerdbs`, which loads the *current* on-chain config via `StackerDBConfig::from_smart_contract` (which evaluates `stackerdb-get-signer-slots` against the canonical chain tip) and only actually calls `reconfigure_stackerdb` if the newly-loaded config differs from the config the node had cached in memory. [3](#0-2) 

- `create_or_reconfigure_stackerdbs` is not run continuously; it is only triggered from `PeerNetwork::refresh_stacker_db_configs`, which itself is only called from the node's main relayer loop in `refresh_stackerdb()`, gated behind a coordinator-set flag (`self.globals.coord_comms.need_stackerdb_update()`), and the flag is only cleared once handled. [4](#0-3) 

- Meanwhile, the HTTP write path (`POST /v2/stackerdb/...`) that accepts chunks from arbitrary remote peers calls straight into `try_replace_chunk` with no re-evaluation of the contract's current signer set — it only checks that the StackerDB itself exists (`tx.get_stackerdb_id`) before delegating authorization entirely to the stale local table. [5](#0-4) 

- The unsolicited push-chunk gossip path has the identical structural issue: `validate_received_chunk` authenticates against `self.stackerdbs.get_slot_signer(...)`, which reads the same locally cached `signer` column rather than consulting the current on-chain config. [6](#0-5) 

This is structurally identical to the reNFT `Guard.sol` bug class: the check that is supposed to authenticate "is this party currently authorized" is instead performed against *stored*, possibly-outdated state, with no cross-check against the authoritative, live source of truth (the on-chain contract / `Kernel.sol` active-policy list in reNFT's case; the on-chain StackerDB smart-contract signer list here). Any StackerDB smart contract that implements the `stackerdb-trait` (this is a general mechanism, not limited to boot contracts) can legitimately rotate its `stackerdb-get-signer-slots` result on-chain, but the deauthorized old signer's write privilege on this node is only revoked once `refresh_stacker_db_configs` happens to run and happens to detect the diff.

### Impact Explanation
A previously-authorized-but-now-revoked signer can continue to unilaterally write to (and, via `StackerDBChunkInv`/push-chunk gossip, propagate through the network) data for a slot they no longer control, because every node that hasn't yet run its periodic config refresh will accept their signature as valid. This lets stale/forged-relative-to-current-config data be served to peers as if it were authoritative for a contract whose ownership set has legitimately moved on — a "non-canonical served as canonical" condition (unauthorized write is accepted and relayed network-wide until each individual peer independently refreshes its config). This matches the High/Critical bucket for "network-wide propagation of forged data" / "unauthenticated/unauthorized write to state or StackerDB," since it undermines the very authorization guarantee that `try_replace_chunk`'s signature check is meant to provide.

### Likelihood Explanation
Likelihood is Medium: it requires (a) a StackerDB-controlling contract to legitimately update its signer set on-chain, and (b) the attacker to have been a previously valid signer for that slot (not an arbitrary unprivileged party). It does not require a secret key belonging to anyone else — the attacker signs with their own, previously-valid key. The exposure window is bounded by how promptly `refresh_stacker_db_configs` is invoked across the network (driven by the coordinator's stackerdb-update signal), and every peer in the gossip mesh that has not yet refreshed is independently vulnerable, so it is not merely a "your-own-node" issue.

### Recommendation
When authenticating a chunk (in `try_replace_chunk`, `validate_received_chunk`, and the unsolicited push-chunk handler), do not rely solely on the locally cached `slot_validation.signer`/`get_slot_signer` values. Either (a) force an immediate config re-evaluation against the current canonical chain tip before accepting/relaying a chunk whenever the cached config's "last refreshed" tip is behind the node's current view, or (b) have the coordinator signal a synchronous, blocking refresh of all affected StackerDB configs on every relevant chain-tip change (not a best-effort background flag) so that stale signer entries cannot be used to author accepted or gossiped chunks.

### Proof of Concept
1. Deploy (or use) a StackerDB-trait contract whose `stackerdb-get-signer-slots` returns `signer A` for slot 0.
2. Node `N` calls `create_or_reconfigure_stackerdbs`, and slot 0's local `slot_validation.signer` becomes `A`.
3. The contract owner rotates the signer set on-chain so slot 0 now belongs to `signer B` (e.g., a legitimate key-rotation transaction is mined). At this point the canonical, current-tip evaluation of `stackerdb-get-signer-slots` returns `B` for slot 0.
4. Before `N`'s coordinator sets `need_stackerdb_update` and `refresh_stackerdb()` runs `refresh_stacker_db_configs` (which is a background, throttled operation per `stacks-node/src/nakamoto_node/peer.rs:212-228`), `N`'s local `chunks.signer` for slot 0 still says `A`.
5. `A` (now deauthorized on-chain) signs and POSTs a new chunk to `N`'s `/v2/stackerdb/...` endpoint. `try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs:410-423` verifies against the stale local `A` and accepts it.
6. `N` advertises the new chunk inventory and/or pushes the chunk to peers; peers that likewise have not yet refreshed their config for this contract will pass it through `validate_received_chunk` (`stackslib/src/net/stackerdb/mod.rs:679-697`), which also checks against their own stale `get_slot_signer`, causing the deauthorized `A`'s write to propagate across the gossip network even though `A` is no longer a valid signer according to the contract's current, canonical state.
