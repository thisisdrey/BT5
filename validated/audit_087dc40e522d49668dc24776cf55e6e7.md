### Title
Unauthenticated attacker-controlled writes to `AtlasDB.attachments` via unchecked hash on attachment download - ([File: stackslib/src/net/atlas/db.rs], [File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsDownloader::run` inserts every `Attachment` returned by `extend_with_attachments`/`decode_atlas_get_attachment` into `AtlasDB` via `insert_instantiated_attachment` without ever checking that the returned content's hash matches the `content_hash` of the `AttachmentRequest` that solicited it. Because `insert_instantiated_attachment` computes and uses `attachment.hash()` (i.e., `Hash160::from_data(&self.content)`) as the SQL key, a malicious peer can answer any attachment fetch with arbitrary bytes and have them stored as a "known" attachment, unconnected to any on-chain `AttachmentInstance.content_hash` commitment.

### Finding Description
In `AttachmentsBatchStateContext::extend_with_attachments` [1](#0-0) , a successful HTTP response is decoded with `response.decode_atlas_get_attachment()` and the resulting `Attachment` is inserted directly into `self.attachments` (a `HashSet<Attachment>`) with no verification against the `AttachmentRequest.content_hash` that was used to issue the request.

Later, in `AttachmentsDownloader::run`, for every attachment collected this way:
```
for attachment in context.attachments.drain() {
    let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())?;
    network.atlasdb.insert_instantiated_attachment(&attachment)?;
    ...
}
``` [2](#0-1) 

`insert_instantiated_attachment` writes the row keyed by `attachment.hash()` (locally recomputed from `self.content`), independent of which `content_hash` the caller originally wanted to satisfy. This means an outbound peer, when asked (via `AttachmentRequest` built from a queued `AttachmentInstance.content_hash`) to serve content for hash `X`, can instead return arbitrary bytes `C` where `Hash160::from_data(C) != X`. The response is accepted (HTTP 200, successfully decoded), inserted into `context.attachments`, and unconditionally persisted into the `attachments` table keyed by `Hash160::from_data(C)` — a value with **zero** matching rows in `attachment_instances`, i.e., not committed by any on-chain transaction.

The subsequent `find_all_attachment_instances(&attachment.hash())` lookup will legitimately return an empty vector in this case (so no instance gets marked "resolved"), but the row is still written into the `attachments` table regardless, satisfying the exact equality violation from the question: content unrelated to any queued/`Checked` `AttachmentInstance.content_hash` is persisted as a "known" attachment.

### Impact Explanation
Any peer that a node queries for an attachment (via the atlas download pipeline) can cause arbitrary attacker-chosen bytes to be written into the victim's `AtlasDB` `attachments` table, with no relation to any actual on-chain BNS/Atlas commitment. This is an unauthenticated write to node state performed by an unprivileged peer, repeatable per attachment request/response cycle, and can be used to bloat the local Atlas database over time (storage exhaustion) since there is no check tying stored content back to a committed hash before persistence.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to run an ordinary outbound peer that the victim node queries for attachments (a normal, unprivileged role reachable over the P2P/HTTP attachment-fetch path). The attacker does not need any secret, admin role, or special network position — merely to respond to legitimate `AttachmentRequest`s issued by the victim's `AttachmentsDownloader`. Each malicious response yields one written row, and the attack is trivially repeatable by responding to further fetch requests or by controlling multiple identities/URLs the node might contact.

### Recommendation
In `extend_with_attachments` (or immediately after decoding, before adding to `self.attachments`), verify `attachment.hash() == request.content_hash` for the specific `AttachmentRequest` that produced the response; discard/blacklist responses that fail this check instead of inserting them. Only call `insert_instantiated_attachment` for attachments whose hash was confirmed to match the originally-requested `content_hash`.

### Proof of Concept
1. Construct an `AttachmentsBatchStateContext` with one `AttachmentRequest` whose `content_hash = X` (some `Hash160`), pointed at a mock HTTP server.
2. Have the mock server return an HTTP 200 with a `GetAttachmentResponse` whose `attachment.content` is arbitrary bytes `C` such that `Hash160::from_data(&C) != X`.
3. Drive `BatchedRequestsState::try_proceed` to completion so the response lands in `results.succeeded`, then call `extend_with_attachments(&mut results)`.
4. Call `AttachmentsDownloader::run` (or directly invoke the `Done` arm logic) so `insert_instantiated_attachment(&attachment)` is invoked.
5. Assert: `atlasdb.find_attachment(&Hash160::from_data(&C))` (i.e., `attachment.hash()`) now returns `Some(...)`, and `atlasdb.find_all_attachment_instances(&attachment.hash())` returns an empty vector — proving a row was persisted in `attachments` for content that is referenced by zero `AttachmentInstance` rows, i.e., not committed by any on-chain transaction and not equal to the originally requested hash `X`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
