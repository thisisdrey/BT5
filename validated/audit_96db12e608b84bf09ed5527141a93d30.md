## Analysis

The external report's core defect: an AMM swap has its `amountOutMinimum` hardcoded to a value that provides no real slippage protection, letting the swap execute at an arbitrarily bad price and letting an attacker drain value through pool manipulation.

The exact local analog is in `swap_and_burn` in the Snowbridge system-frontend pallet, reached from two public, unprivileged extrinsics (`register_token` and `add_tip`): [1](#0-0) 

The swap call explicitly passes `None` for `amount_out_min`, with a comment stating "No minimum amount required": [2](#0-1) 

The `Swap` trait used here is fulfilled by `pallet_asset_conversion`, a plain constant-product AMM without any oracle or TWAP protection, whose reserves can be freely manipulated within a single transaction: [3](#0-2) [4](#0-3) 

Compare this to the pallet itself, which does support and enforce a caller-provided `amount_out_min`/`ProvidedMinimumNotSufficientForSwap` guard when callers choose to use it — proving the guard exists but is deliberately bypassed in `swap_and_burn`: [5](#0-4) 

The dispatchables that invoke the unprotected swap are public and callable by any signed account: [6](#0-5) [7](#0-6) 

### Title
Missing slippage protection (`amount_out_min: None`) in Snowbridge `swap_and_burn` allows AMM-pool value extraction via self-contained price manipulation - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

### Summary
`Pallet::swap_and_burn` (invoked by the public extrinsics `register_token` and `add_tip`) calls `T::Swap::swap_exact_tokens_for_tokens` with `amount_out_min` hard-set to `None`, disabling the slippage floor that `pallet_asset_conversion` otherwise enforces. Since the swap price is derived from mutable, attacker-controllable AMM reserves with no oracle/TWAP, an unprivileged account can atomically manipulate the pool and then call `add_tip`/`register_token` in the same transaction to receive an inflated `ether_gained` amount, extracting real value from pool liquidity providers.

### Finding Description
`swap_and_burn` swaps a user-supplied "tip"/fee asset into Ether through `pallet_asset_conversion`'s constant-product pool and then burns/teleports the resulting Ether amount, recording it as the reward/tip for a bridge message (`add_tip`) or as the registration fee (`register_token`). The call explicitly disables the minimum-output guard:

```rust
let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
    who.clone(),
    swap_path,
    tip_amount,
    None, // No minimum amount required
    who,
    true,
)?;
```

`pallet_asset_conversion`'s pools are plain x*y=k constant-product pools whose reserves can be moved arbitrarily within a single block/transaction by any account with sufficient balance — there is no oracle, TWAP, or cooldown. Because `add_tip` and `register_token` are unprivileged, signed-origin extrinsics, an attacker can build one atomic transaction (e.g. via `utility.batch_all`) that:
1. Swaps a large amount into the pool to skew the reserve ratio in their favor,
2. Calls `add_tip`/`register_token` with a chosen `tip_amount`, which is swapped at the now-skewed price with **no** minimum-output check to reject a bad/attacker-favorable rate,
3. Reverses the initial swap to restore the pool, pocketing the difference extracted from the pool's liquidity.

The existing "guard" that should stop this — the `amount_out_min` check inside `do_swap_exact_tokens_for_tokens` (`Error::ProvidedMinimumNotSufficientForSwap`) — cannot fire because the caller of the trait explicitly passes `None`, bypassing the very protection the pallet itself provides for exactly this class of attack.

### Impact Explanation
The `ether_gained` value from the manipulated swap is burned/teleported and forwarded to BridgeHub as the amount used to fund relayer rewards (`add_tip`) or the registration fee (`register_token`). An attacker can obtain a large `ether_gained` for a comparatively small amount of tip asset by manipulating the shared AMM pool, at the expense of the pool's liquidity providers — this is a direct value-theft/underpriced-conversion vector against pooled funds reachable from a fully public, unprivileged extrinsic, matching the "theft… of value" and "bridge reward" impact categories.

### Likelihood Explanation
The attack requires only a single signed account, a batched/atomic transaction, and sufficient capital to temporarily move the pool's reserves — no malicious relayer, validator, collator, or governance actor is needed, and it does not depend on front-running another user's transaction since the attacker controls both legs of the manipulation within their own atomic call.

### Recommendation
Do not pass `None` for `amount_out_min` in `swap_and_burn`. Derive an expected output from a spot/quote check (e.g. `QuotePrice::quote_price_exact_tokens_for_tokens`) with a bounded tolerance, or expose a caller-supplied `amount_out_min` parameter on `add_tip`/`register_token` that is validated against a sane floor, so `pallet_asset_conversion`'s existing `ProvidedMinimumNotSufficientForSwap` protection is actually enforced.

### Proof of Concept
1. Attacker (single account) creates/uses an existing `pallet_asset_conversion` pool for `(tip_asset, ether_location)` with modest liquidity.
2. In one `utility.batch_all` transaction:
   a. `AssetConversion::swap_exact_tokens_for_tokens` — swap a large amount of `ether`-side asset into the pool to depress the ether price relative to the tip asset.
   b. `SnowbridgeSystemFrontend::add_tip(message_id, tip_asset_asset)` — this internally calls `swap_and_burn` with `amount_out_min = None`, executing at the manipulated rate and returning an inflated `ether_gained`.
   c. `AssetConversion::swap_exact_tokens_for_tokens` — swap back to restore the pool, realizing the extracted profit.
3. Because step (b) has no floor check, it executes even though the rate is far worse than fair market value, letting the attacker walk away with pool funds while restoring the pool state in the same transaction.

			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether
			let ether_asset = Asset::from((ether_location.clone(), ether_gained));

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}

		pub(crate) fn do_swap_exact_tokens_for_tokens(
			sender: T::AccountId,
			path: Vec<T::AssetKind>,
			amount_in: T::Balance,
			amount_out_min: Option<T::Balance>,
			send_to: T::AccountId,
			keep_alive: bool,
		) -> Result<T::Balance, DispatchError> {
			ensure!(amount_in > Zero::zero(), Error::<T>::ZeroAmount);
			if let Some(amount_out_min) = amount_out_min {
				ensure!(amount_out_min > Zero::zero(), Error::<T>::ZeroAmount);
			}

			Self::validate_swap_path(&path)?;
			let path = Self::balance_path_from_amount_in(amount_in, path)?;

			let amount_out = path.last().map(|(_, a)| *a).ok_or(Error::<T>::InvalidPath)?;
			if let Some(amount_out_min) = amount_out_min {
				ensure!(
					amount_out >= amount_out_min,
					Error::<T>::ProvidedMinimumNotSufficientForSwap
				);
			}
