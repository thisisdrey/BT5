### Title
Protocol is bricked on non-EIP-1153 chains (e.g. zkSync Era) because all `nonReentrant` functions and `Operator.execute` rely on TSTORE/TLOAD - (File: contracts/utils/ReentrancyGuardTransient.sol)

### Summary
The original report showed a protocol hard-bricked on zkSync because `computePoolAddress()` assumed EVM-equivalent CREATE2 semantics that zkSync does not provide. Metronome has the same bug class, but much deeper: nearly every state-changing function in the protocol flows through the `nonReentrant` modifier from `ReentrancyGuardTransient`, which is implemented with EIP-1153 transient-storage opcodes (`tstore`/`tload`). zkSync Era (and other zkEVM rollups at various protocol versions) does not implement EIP-1153 — TSTORE/TLOAD cause the transaction to revert, so every guarded function permanently reverts. The file itself acknowledges the limitation: "This variant only works on networks where EIP-1153 is available" (`contracts/utils/ReentrancyGuardTransient.sol:10`).

### Finding Description
- `ReentrancyGuardTransient._nonReentrantBefore()` executes `REENTRANCY_GUARD_STORAGE.asBoolean().tstore(true)` and `_reentrancyGuardEntered()` executes `.tload()` [1](#0-0) 
- All core contracts inherit it (`Pool`, `DepositToken`, `DebtToken`, `SmartFarmingManager`, `Treasury`, `NativeTokenGateway`, `VesperGateway`, `RewardsDistributor`, `RecurringAirdrop`, `Operator`), so deposits, withdrawals, swaps, issuance, repayments, liquidations, and reward claims all hit TSTORE/TLOAD on their first line.
- `Operator.execute` additionally stores the meta-sender in a transient slot via `setMsgSender`, and `SynthContext._msgSender` resolves the real caller through `getActualMsgSender()`, which `tload`s `MSG_SENDER_STORAGE` [2](#0-1) [3](#0-2) 
- The protocol is explicitly multi-chain — deployment artifacts exist for base, bsc, optimism, mainnet, hemi, plasma, and swell (`deployments/` directory) — so deployment to a zkSync-style chain is a plausible configuration, not a hypothetical one.

On a chain without EIP-1153 (zkSync Era prior to Gateway/protocol-v26, and other zkEVMs), `tstore`/`tload` are invalid opcodes; the EVM-equivalence layer reverts the entire transaction. Unlike a `computePoolAddress` mismatch (which could be patched with a single-address override), there is no fallback path here — `nonReentrant` is inlined into every entry point, and `Operator`'s sender-authentication mechanism has no non-transient alternative.

### Impact Explanation
Complete liveness failure on the affected chain. A user calling `pool.deposit(...)`, `depositToken.withdraw(...)`, `debtToken.repay(...)`, `pool.swap(...)`, `pool.liquidate(...)`, or `operator.execute(...)` reverts at the first TSTORE. Collateral already deposited is permanently frozen: withdrawals, repayments, and liquidations all require a `nonReentrant` call. This satisfies the "permanent freezing of funds" impact criterion.

### Likelihood Explanation
No attacker action is required — the failure is unconditional on deployment to a chain without EIP-1153. Likelihood is therefore a deployment-configuration question rather than an exploitation question, which is exactly the shape of the source finding (rated Medium there). The contracts hard-require `pragma solidity 0.8.24`/Cancun-target compilation, which itself signals EIP-1153 dependency, but nothing in the codebase gates deployment by chain capability. Note uncertainty: zkSync Era added TSTORE/TLOAD support in protocol v26, so the finding applies to older zkSync versions and other zkEVMs that still lack 1153; the protocol cannot distinguish these at runtime.

### Recommendation
- Gate deployment: maintain a per-chain capability check (e.g., attempt a self-call exercising TSTORE during initialization, reverting if unsupported) so a bad deployment fails atomically rather than after funds are deposited.
- Provide a storage-slot `ReentrancyGuard` variant for non-1153 chains (the repo already has `utils/ReentrancyGuardDeprecated.sol` as precedent), and a non-transient `MSG_SENDER` mechanism for `Operator` on those chains.
- Document supported-chain requirements alongside `pragma`/Cancun assumptions.

### Proof of Concept
Reproducible on a Foundry fork of a zkEVM chain without EIP-1153 (e.g., a zkSync Era fork pinned to a pre-v26 block, or Polygon zkEVM/Scroll versions lacking Cancun opcodes — the PoC uses `--evm-version paris` locally to simulate the missing opcodes):

```solidity
// test/foundry/NoEIP1153.t.sol
pragma solidity ^0.8.24;
import "forge-std/Test.sol";
import {Pool} from "contracts/Pool.sol";
import {Operator} from "contracts/Operator.sol";

contract NoEIP1153_Test is Test {
    // Compile/fork the target chain WITHOUT Cancun (e.g. forge test --evm-version paris)
    // so TSTORE/TLOAD are invalid opcodes, matching zkSync-era behavior.

    function test_deposit_reverts_onChainWithoutEIP1153() public {
        Operator operator = new Operator();
        vm.expectRevert(); // invalid opcode at tstore in _nonReentrantBefore/setMsgSender
        operator.execute{value: 0}(new IOperator.Call[](0));

        Pool pool = new Pool();
        // ...standard initialize with registry/tokens as in MultiPool_Test.setUp()...
        vm.expectRevert(); // any nonReentrant entry point reverts identically
        pool.swap(syntheticIn, syntheticOut, 1e18);
    }
}
```

Invariant broken: liveness — every state-changing entry point reverts unconditionally, freezing all deposited collateral on the chain.
