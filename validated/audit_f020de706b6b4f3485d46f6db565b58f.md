In the pre-`allowDelegateOptimization` (legacy) code path, `DelegatedResourceAccountIndexCapsule.getFromAccountsList()` / `getToAccountsList()` are plain protobuf-repeated fields that only ever grow via `addToAccount()` / `addFromAccount()` in `FreezeBalanceActuator.delegateResource()`, and are only shrunk by a linear `List.remove()` in `UnfreezeBalanceActuator`. An unprivileged account can call `FreezeBalanceContract` with a distinct, freshly generated `receiver_address` repeatedly (cost is only the frozen TRX + tx fee, no per-entry cap) to make its own index list grow without bound, exactly mirroring the `TimeLockPool.curve.push` growth pattern in the report.

### Title
Unbounded growth of `DelegatedResourceAccountIndex.toAccounts/fromAccounts` via repeated `FreezeBalanceContract` delegation enables O(n) list-processing DoS - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceActuator.delegateResource()` appends a new entry to the `DelegatedResourceAccountIndexCapsule` owner/receiver lists on every distinct delegation pair, with no upper bound on the number of distinct receivers/senders a single account can accumulate.

### Finding Description
When `supportAllowDelegateOptimization()` is false (legacy account-index model, still reachable when that fork is not active), `delegateResource()` reads the owner's `DelegatedResourceAccountIndexCapsule`, checks `toAccountsList.contains(...)`, and if absent calls `ownerIndexCapsule.addToAccount(...)`, then persists the whole capsule back to `DelegatedResourceAccountIndexStore` [1](#0-0) . The same happens symmetrically for the receiver's `fromAccounts` list. `addToAccount`/`addFromAccount` simply append to the underlying protobuf repeated field with no size cap [2](#0-1) . Because `FreezeBalanceContract` validation only checks that `frozenBalance >= 1 TRX` and `frozenCount` is 0/1 for the *owner's own* frozen entries (not the delegation index size) [3](#0-2) , an attacker can freeze the minimum 1 TRX and delegate it to a new, never-before-seen receiver address in each transaction, causing `toAccountsList`/`fromAccountsList` to grow by one entry per transaction indefinitely — the same "unbounded array growth via a public entry point with no cap" root cause flagged in `TimeLockPool.push`. Cleanup on `UnfreezeBalanceActuator` is also O(n): it copies the whole list into an `ArrayList`, does a linear `remove()`, and rewrites the entire capsule [4](#0-3) , so both write and read paths (`getIndex`/`getV2Index`, used by wallet/API queries such as delegated-resource-account-index RPCs) become increasingly expensive as the list grows, since the whole protobuf blob must be deserialized/reserialized on every touch.

### Impact Explanation
As the index list grows very large, every subsequent freeze/unfreeze/delegate transaction touching that account, and every API call that reads the account's delegated-resource index (e.g. `getDelegatedResourceAccountIndex`), must deserialize, scan, and reserialize an ever-larger protobuf message. This increases per-transaction processing time and memory footprint without a corresponding increase in fee/resource cost, degrading node performance and potentially causing timeouts on the query path or making the victim account's own freeze/unfreeze operations progressively more expensive/slow — an availability/DoS-class issue rather than direct fund loss.

### Likelihood Explanation
Exploitability depends on the legacy (`!supportAllowDelegateOptimization()`) delegation index code path still being active/reachable on the live chain; if `allowDelegateOptimization` has already been activated network-wide, new delegations use `delegatedResourceAccountIndexStore.delegate()` (separate per-pair keys, see `DelegatedResourceAccountIndexStore.java` lines 63-75), which does not exhibit this specific list-growth pattern, though the underlying legacy data and `convert()` migration path can still touch old unbounded lists. Given the uncertainty about which fork state is live on this deployment, likelihood is assessed as Medium pending confirmation of the active `allowDelegateOptimization` flag.

### Recommendation
Cap the number of distinct delegation-index entries per account (mirroring the `MAX_FROZEN_SUPPLY_NUMBER`/`MAX_VOTE_NUMBER` pattern already used elsewhere in this codebase, e.g. `DynamicPropertiesStore.getMaxFrozenSupplyNumber()`), or migrate all remaining legacy `DelegatedResourceAccountIndexCapsule` list-based indices to the already-implemented per-pair keyed model (`delegate`/`unDelegate` in `DelegatedResourceAccountIndexStore`) which avoids storing an unbounded list inside a single value.

### Proof of Concept
1. Ensure `allowDelegateOptimization` is not yet enabled (legacy path).
2. From a single funded account, submit N `FreezeBalanceContract` transactions, each freezing the minimum 1 TRX for `BANDWIDTH`, each specifying a distinct freshly-generated `receiver_address`.
3. Observe `DelegatedResourceAccountIndexStore.get(ownerAddress).getToAccountsList()` grows by one entry per transaction with no upper bound, as demonstrated in the existing test `testMultiFreezeDelegatedBalanceForBandwidth` [5](#0-4)  which already exercises 100+ growth without any validate()-time rejection.
4. Repeat at scale (thousands/millions of distinct receivers) to inflate the serialized capsule size and degrade read/write performance on that account's index.
