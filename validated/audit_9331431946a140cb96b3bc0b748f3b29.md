This confirms the reachability: `java_common.run_ijar` runs the ijar tool (backed by `InputZipFile` in `third_party/ijar/zip.cc`) on any jar file supplied to a Java rule, including precompiled/imported jars fetched from external sources (e.g. `java_import`, `http_jar`, or bzlmod/Maven registries). This is a legitimate, unprivileged-attacker-reachable surface: a malicious jar published at a dependency URL/registry, pinned by its own sha256 (which the attacker controls since they choose the bytes being hashed), still has full attacker control over its internal ZIP central-directory structure.

### Title
Missing bounds check in ZIP central-directory parsing causes heap out-of-bounds read in ijar - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in [1](#0-0)  reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from an attacker-controlled central directory entry and advances the cursor / copies memory according to these attacker-supplied lengths **without ever calling `EnsureRemaining`** to validate them against the actual mapped file size, unlike its sibling `ProcessLocalFileEntry`, which does call `EnsureRemaining` before every length-driven read [2](#0-1) .

### Finding Description
`EnsureRemaining` is the bounds-check helper defined for `InputZipFile` that is supposed to guard every length-driven read against the mmap'd file boundary [3](#0-2) . `ProcessLocalFileEntry` consistently calls it before reading `file_name_` and `extra_field_` [4](#0-3) , but `ProcessCentralDirEntry` — which is invoked for every entry by `ProcessNext` and `CalculateOutputLength` [5](#0-4) [6](#0-5)  — never calls it at all:

```
p += 16;  // skip to 'compressed size' field
*compressed_size = get_u4le(p);
*uncompressed_size = get_u4le(p);
u2 file_name_length = get_u2le(p);
u2 extra_field_length = get_u2le(p);
u2 file_comment_length = get_u2le(p);
...
memcpy(reinterpret_cast<void*>(filename), p, len);
...
p += file_name_length;
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  ...
  extra_p += data_size;
  ...
}
p += file_comment_length;
``` [7](#0-6) 

Because `file_name_length`, `extra_field_length`, and `file_comment_length` are 16-bit values fully controlled by the attacker who authored the jar, and because none of the pointer advances (`p += file_name_length`, `p += extra_field_length`, `extra_p += data_size`, `p += file_comment_length`) are checked against `input_file_->Length()` / the mmap'd region, a crafted jar can make `p`/`extra_p` walk past the end of the memory-mapped input file. This causes reads of heap memory adjacent to (or beyond) the mapping — a heap-based out-of-bounds read directly analogous to the missing length check in `JS_ReadString` from CVE-2025-46687. The `memcpy(filename, p, len)` call also copies from a `p` that has not been validated to still point within the mapped region, and while the destination is bounded by `filename_size`, the *source* range `[p, p+len)` is not validated.

### Impact Explanation
`ProcessCentralDirEntry` is reached automatically whenever ijar processes a jar — including via `java_common.run_ijar`/`stamp_jar` and the implicit ijar action Bazel schedules for any `java_import`/precompiled dependency jar (Maven artifact, `http_jar`, vendored jar, etc.) fetched from an untrusted origin. Since the attacker fully controls the jar's bytes (and thus the sha256 that is pinned against it), no checksum or lockfile mechanism prevents them from crafting a central-directory entry whose `file_name_length`/`extra_field_length`/`file_comment_length` exceed the remaining mapped-file size. The consequence is an out-of-bounds heap read in the `ijar` action executed as part of the build: at minimum a crash/SIGSEGV of the ijar subprocess (denial of the affected action), and at worst leakage of adjacent process heap memory into the generated interface jar's filenames/extra fields or error messages, which end up in build outputs/logs.

### Likelihood Explanation
Any consumer of a `java_import`-style precompiled jar, or of `java_common.run_ijar`/`stamp_jar`, that pulls the jar from an external/untrusted source (mirror, registry, `http_jar`) is affected. Producing the malformed central directory entry requires no special access — just crafting a ZIP file with an oversized `file_name_length`/`extra_field_length`/`comment_length` field near the end of the mapped region, then publishing it and letting the victim's build fetch and pin its own hash.

### Recommendation
Add `EnsureRemaining` checks in `ProcessCentralDirEntry` before every length-driven pointer advance and memory access — mirroring what `ProcessLocalFileEntry` already does — specifically before the `memcpy` of the file name, before advancing past `extra_field_length`, inside the `while (extra_p != p)` extra-field loop (to also guard against `data_size` overshooting `p`), and before advancing past `file_comment_length`.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` reproduction would:
1. Hand-craft a minimal ZIP/jar whose single central directory entry declares `file_name_length`/`extra_field_length` values that, when added to the entry's offset, exceed the actual file length (e.g., entry placed at the very end of the buffer with `extra_field_length = 0xFFFF`).
2. Feed this jar to the `ijar` binary directly (`third_party/ijar/zip_main.cc`) or via `java_common.run_ijar` in a Starlark rule, as already exercised by `third_party/ijar/test/ijar_test.sh` [8](#0-7) .
3. Observe a crash (SIGSEGV/ASan heap-buffer-overflow report) or leaked adjacent-heap bytes appearing in the output interface jar, instead of a graceful "Premature end of file" error that `EnsureRemaining` would have produced.

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
