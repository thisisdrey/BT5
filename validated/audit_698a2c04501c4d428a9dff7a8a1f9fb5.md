### Title
Firewall config reload desynchronizes conntrack timeout values from the retained TimerWheel's tick/duration parameters, causing silent timeout clamping and premature/inconsistent expiration - (File: firewall.go, timeout.go)

### Summary
This is the analog of the Symbiotic "epoch duration change breaks vault/slasher" bug class: a timing parameter (epoch duration / here, firewall conntrack timeout) is changed in config, but a dependent structure that was built once from the *old* duration (the vault/slasher epoch-length checks / here, the `TimerWheel`'s `tickDuration`/`wheelDuration`) is not rebuilt to match, so enforcement silently desynchronizes from the new configured value.

### Finding Description
`Interface.reloadFirewall` handles a `SIGHUP`/config reload by constructing an entirely new `Firewall` via `NewFirewallFromConfig`, which reads fresh `firewall.conntrack.tcp_timeout`, `firewall.conntrack.udp_timeout`, and `firewall.conntrack.default_timeout` values and calls `NewFirewall`, which in turn sizes a brand-new `FirewallConntrack.TimerWheel` via `NewTimerWheel(tmin, tmax)` based on those new values [1](#0-0) [2](#0-1) .

However, immediately after building this new firewall, `reloadFirewall` discards the freshly-sized `Conntrack` (and its correctly-dimensioned `TimerWheel`) and reuses the **old** `Firewall`'s `Conntrack` object (built for the *previous* timeout values) so existing connections aren't dropped:

```go
oldFw := f.firewall
conntrack := oldFw.Conntrack
...
fw.rulesVersion = oldFw.rulesVersion + 1
if fw.rulesVersion == 0 {
    // reset conntrack instead
} else {
    fw.Conntrack = conntrack   // <-- old TimerWheel, sized for OLD timeouts, is kept
}
f.firewall = fw
``` [3](#0-2) 

The new `Firewall.TCPTimeout` / `UDPTimeout` / `DefaultTimeout` fields *do* reflect the newly configured durations [4](#0-3) , but the `TimerWheel`'s `tickDuration` and `wheelDuration` — which determine both the minimum resolution and the *maximum trackable duration* — remain fixed at whatever `tmin`/`tmax` were computed from the timeouts in effect at the time the currently-live `Conntrack` was created (originally at startup, and never updated across any subsequent successful reload, since each reload keeps propagating the original wheel forward).

The consequence mirrors the report's root cause exactly: the runtime enforcement logic (`addConn`/`inConns` in `firewall.go`) sets each connection's absolute `Expires` field using the *new* `f.TCPTimeout`/`UDPTimeout`/`DefaultTimeout` values [5](#0-4) , but schedules the wheel-slot for eviction/re-checking via `conntrack.TimerWheel.Add(fp, timeout)` using the same new `timeout` value fed into `findWheel`, which **silently clamps** any timeout below `tickDuration` up to `tickDuration`, and any timeout above `wheelDuration` down to `wheelDuration`:

```go
func (tw *TimerWheel[T]) findWheel(timeout time.Duration) (i int) {
	if timeout < tw.tickDuration {
		timeout = tw.tickDuration
	} else if timeout > tw.wheelDuration {
		timeout = tw.wheelDuration
	}
	...
}
``` [6](#0-5) 

This "silent" clamping is explicitly documented as a known limitation of the wheel implementation itself ("The wheel rounds requested timeouts up to its tick resolution and clamps anything beyond its wheel duration; both are silent in this implementation") [7](#0-6) , and it is exactly the class of desynchronization the Symbiotic report describes: the security-relevant duration parameter (here, conntrack timeout, analogous to `epoch duration`) is updated in one place (`Firewall.TCPTimeout` et al., analogous to `EpochManager::setEpochDuration()`) while a structurally-baked-in dependent value (the wheel's `tickDuration`/`wheelDuration`, analogous to the vault/slasher's fixed epoch length) is left stale because it is inherited across reload instead of being rebuilt.

### Impact Explanation
If an operator raises `firewall.conntrack.tcp_timeout`/`udp_timeout`/`default_timeout` well beyond the originally-provisioned `wheelDuration` (e.g., the wheel was built at startup with small timeouts and later reloaded with much larger ones — a legitimate, unauthenticated-reachable path since firewall config reload is triggered by any config change), every subsequent connection's *actual* eviction slot in the wheel is silently capped at the old, smaller `wheelDuration`, even though `conn.Expires` (checked in `inConns`) reflects the new, larger timeout. Because `evict()` re-derives the real remaining time from `Expires` and re-adds to the wheel (`newT := t.Expires.Sub(time.Now()); ... TimerWheel.Add(p, newT)`, which again goes through the same clamping `findWheel`) [8](#0-7) , the entry keeps getting re-clamped and re-scheduled at the stale maximum on every wheel pass, rather than expiring per the newly configured timeout. This causes conntrack entries to be retained (or purged) at a cadence inconsistent with the administrator's configured firewall timeouts — a remote, config-adjacent desynchronization of a security-relevant timing control, matching the report's "epoch duration out of sync" impact class (stale enforcement window rather than the configured one). It does not cause a crash or memory corruption, but it is a genuine timing/enforcement desynchronization bug reachable by any config reload that changes conntrack timeouts, with no code path that ever rebuilds the wheel's ticks to match.

### Likelihood Explanation
Reachable whenever an operator issues a `SIGHUP`/SSH `reload` after changing `firewall.conntrack.*` timeout values in the config — a normal operational action, not requiring a malicious peer or attacker-controlled certificate. The bug is deterministic: any reload after a timeout change will retain the previous wheel dimensions since `reloadFirewall` unconditionally reuses `oldFw.Conntrack` whenever `rulesVersion` doesn't wrap.

### Recommendation
When conntrack timeout values change across a reload, rebuild (or at minimum resize) the `TimerWheel` to match the new `tmin`/`tmax`, migrating any already-tracked entries into the new wheel using their existing `Expires` timestamps, instead of blindly carrying forward the old `Conntrack.TimerWheel`. At minimum, detect a `tickDuration`/`wheelDuration` mismatch against the newly computed `tmin`/`tmax` in `reloadFirewall` and force a full conntrack reset in that case (as is already done for the `rulesVersion` overflow case), rather than silently continuing to clamp future `Add()`/`evict()` calls to the stale bounds.

### Proof of Concept
Not independently verifiable without running the code; the desynchronization is provable structurally from `reloadFirewall`'s unconditional `fw.Conntrack = conntrack` reuse (interface.go:423) combined with `findWheel`'s documented silent clamping (timeout.go:164-184), but no dynamic PoC was executed as part of this review.

func (f *Firewall) addConn(fp firewall.Packet, incoming bool) {
	var timeout time.Duration
	c := &conn{}

	switch fp.Protocol {
	case firewall.ProtoTCP:
		timeout = f.TCPTimeout
	case firewall.ProtoUDP:
		timeout = f.UDPTimeout
	default:
		timeout = f.DefaultTimeout
	}

	conntrack := f.Conntrack
	conntrack.Lock()
	if _, ok := conntrack.Conns[fp]; !ok {
		conntrack.TimerWheel.Advance(time.Now())
		conntrack.TimerWheel.Add(fp, timeout)
	}

	// Record which rulesVersion allowed this connection, so we can retest after
	// firewall reload
	c.incoming = incoming
	c.rulesVersion = f.rulesVersion
	c.Expires = time.Now().Add(timeout)
	conntrack.Conns[fp] = c
	conntrack.Unlock()

func (f *Firewall) evict(p firewall.Packet) {
	// Are we still tracking this conn?
	conntrack := f.Conntrack
	t, ok := conntrack.Conns[p]
	if !ok {
		return
	}

	newT := t.Expires.Sub(time.Now())

	// Timeout is in the future, re-add the timer
	if newT > 0 {
		conntrack.TimerWheel.Advance(time.Now())
		conntrack.TimerWheel.Add(p, newT)
		return
	}

func (f *Interface) reloadFirewall(c *config.C) {
	cs := f.pki.getCertState()
	curCert := cs.getCertificate(cert.Version2)
	if curCert == nil {
		curCert = cs.getCertificate(cert.Version1)
	}

	// The firewall builds its routableNetworks set from the certificate's UnsafeNetworks at construction.
	// Check to see if that set has changed, and if so, rebuild the firewall.
	certUnsafeChanged := curCert != nil && !slices.Equal(curCert.UnsafeNetworks(), f.firewall.unsafeNetworks)

	if !c.HasChanged("firewall") && !certUnsafeChanged {
		f.l.Debug("No firewall config change detected")
		return
	}

	fw, err := NewFirewallFromConfig(f.l, cs, c)
	if err != nil {
		f.l.Error("Error while creating firewall during reload", "error", err)
		return
	}

	oldFw := f.firewall
	conntrack := oldFw.Conntrack
	conntrack.Lock()
	defer conntrack.Unlock()

	fw.rulesVersion = oldFw.rulesVersion + 1
	// If rulesVersion is back to zero, we have wrapped all the way around. Be
	// safe and just reset conntrack in this case.
	if fw.rulesVersion == 0 {
		f.l.Warn("firewall rulesVersion has overflowed, resetting conntrack",
			"firewallHashes", fw.GetRuleHashes(),
			"oldFirewallHashes", oldFw.GetRuleHashes(),
			"rulesVersion", fw.rulesVersion,
		)
	} else {
		fw.Conntrack = conntrack
	}

	f.firewall = fw
```

func (tw *TimerWheel[T]) findWheel(timeout time.Duration) (i int) {
	if timeout < tw.tickDuration {
		// Can't track anything below the set resolution
		timeout = tw.tickDuration
	} else if timeout > tw.wheelDuration {
		// We aren't handling timeouts greater than the wheels duration
		timeout = tw.wheelDuration
	}

	// Find the next highest, rounding up
	tick := int(((timeout - 1) / tw.tickDuration) + 1)

	// Add another tick since the current tick may almost be over then map it to the wheel from our
	// current position
	tick += tw.current + 1
	if tick >= tw.wheelLen {
		tick -= tw.wheelLen
	}

	return tick
}
