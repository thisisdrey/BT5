### Title
Unbounded memory consumption when streaming oversized commit/tag messages via `GetCommitMessages` - (File: internal/git/catfile/commit.go, internal/gitaly/service/commit/commit_messages.go)

### Summary
`GetCommit`/`FindCommit` explicitly cap commit message bodies to `helper.MaxCommitOrTagMessageSize` (10 KiB) by truncating in `ParseCommit`, treating that field as a small, bounded-cost value (analogous to the assumption in `ERC165Checker` that `supportsInterface` returns a small, bounded response). However, the sibling code path used by `GetCommitMessages`, `catfile.GetCommitMessage` → `splitRawCommit`, applies no such cap: it calls `io.ReadAll(object)` on the raw commit object and returns the entire body verbatim, with no size limit enforced anywhere in the RPC handler.

### Finding Description
`catfile.GetCommitMessage` in [1](#0-0)  reads the *entire* raw git object into memory via `io.ReadAll(object)` in `splitRawCommit`, then returns the full body with no truncation. This contrasts with `ParseCommit` in [2](#0-1) , which explicitly truncates the body to `helper.MaxCommitOrTagMessageSize` (10 KiB, defined at [3](#0-2) ) — a size that is documented as the threshold "if exceeded then message is truncated and it's up to the client to request it in full separately."

The unbounded path is directly exposed via the `GetCommitMessages` RPC handler, which loops over caller-supplied `CommitIds` and calls `catfile.GetCommitMessage` for each one, then streams the full, untruncated message back to the client: [4](#0-3) . The handler performs no validation of commit-message size before or during the read, and the only "bound" (`io.Copy` in the streaming writer) is applied *after* the whole message has already been materialized in memory by `io.ReadAll`.

Git commit and tag messages have no protocol-enforced size ceiling; an ordinary git client can push a commit whose message body is many megabytes or gigabytes without violating the git object format. Because Gitaly's own regression test intentionally exercises this exact scenario — writing commit messages sized at `helper.MaxCommitOrTagMessageSize*2` and asserting the full, untruncated content is returned ( [5](#0-4) ) — the lack of any upper bound in this specific path is confirmed to be a real, exercised code path rather than a hypothetical.

### Impact Explanation
Any authenticated Gitaly client (e.g., GitLab Rails/Workhorse acting on behalf of an ordinary repository user) can push a commit with an arbitrarily large commit message via a normal `git push`, then invoke `GetCommitMessages` referencing that commit ID. Each invocation forces the Gitaly server to allocate memory proportional to the attacker-chosen message size (`io.ReadAll` over the whole object) per requested commit ID, and the request accepts a list of `CommitIds`, allowing amplification across multiple oversized commits in a single RPC call. Repeated or concurrent calls can drive significant server-side memory pressure, degrading or crashing the Gitaly process — a denial-of-service condition affecting all repositories served by that node, directly analogous to the unbounded-cost assumption violated in the ERC165Checker advisory (an operation assumed cheap/bounded becomes attacker-controlled and unbounded).

### Likelihood Explanation
Likelihood is limited by the fact that `GetCommitMessages` is typically invoked by GitLab's backend rather than being directly reachable from arbitrary anonymous input, and producing a very large commit message requires pushing correspondingly large pack data (bounded in practice by upload size/time limits enforced elsewhere in the stack, e.g. Workhorse/GitLab proxy limits). Still, within Gitaly's own trust boundary — where the RPC contract is "provide a commit ID, get its message" — no defense-in-depth limit exists, and the behavior is reachable purely through standard push + RPC-field flows without any privileged access, unlike the git hook or admin-configured code paths that are out of scope here.

### Recommendation
Apply the same `helper.MaxCommitOrTagMessageSize`-based truncation (or a configurable/streamed cap with an explicit "message truncated" indicator) to `catfile.GetCommitMessage`/`splitRawCommit` as is already applied in `ParseCommit`, or use a bounded `io.LimitReader` prior to `io.ReadAll` combined with an explicit size check before allocating the full buffer, so that oversized commit/tag message bodies cannot force unbounded memory allocation in a single RPC call.

### Proof of Concept
1. Create a repository and push a commit whose message body is several hundred MB (e.g., using `git commit --allow-empty -m "$(python3 -c 'print("A"*500_000_000)')"`).
2. Call the `GetCommitMessages` RPC with `CommitIds` containing that commit's OID (as exercised structurally by the existing test at [6](#0-5) , but scaled far beyond `MaxCommitOrTagMessageSize`).
3. Observe that `catfile.GetCommitMessage` → `splitRawCommit` ( [7](#0-6) ) buffers the entire message via `io.ReadAll` before any truncation or streaming occurs, causing memory usage proportional to the attacker-chosen message size.

// GetCommitMessage looks up a commit message and returns it in its entirety.
func GetCommitMessage(ctx context.Context, objectReader ObjectContentReader, repo storage.Repository, revision git.Revision) ([]byte, error) {
	obj, err := objectReader.Object(ctx, revision+"^{commit}")
	if err != nil {
		return nil, err
	}

	_, body, err := splitRawCommit(obj)
	if err != nil {
		return nil, err
	}
	return body, nil
}

func splitRawCommit(object git.Object) ([]byte, []byte, error) {
	raw, err := io.ReadAll(object)
	if err != nil {
		return nil, nil, err
	}

	header, body, _ := bytes.Cut(raw, []byte("\n\n"))

	return header, body, nil
}

func (s *server) getAndStreamCommitMessages(request *gitalypb.GetCommitMessagesRequest, stream gitalypb.CommitService_GetCommitMessagesServer) error {
	ctx := stream.Context()
	repo := s.localRepoFactory.Build(request.GetRepository())

	objectReader, cancel, err := s.catfileCache.ObjectReader(ctx, repo)
	if err != nil {
		return err
	}
	defer cancel()

	for _, commitID := range request.GetCommitIds() {
		msg, err := catfile.GetCommitMessage(ctx, objectReader, repo, git.Revision(commitID))
		if err != nil {
			return fmt.Errorf("failed to get commit message: %w", err)
		}
		msgReader := bytes.NewReader(msg)

		if err := stream.Send(&gitalypb.GetCommitMessagesResponse{CommitId: commitID}); err != nil {
			return err
		}
		sw := streamio.NewWriter(func(p []byte) error {
			return stream.Send(&gitalypb.GetCommitMessagesResponse{Message: p})
		})
		_, err = io.Copy(sw, msgReader)
		if err != nil {
			return fmt.Errorf("failed to send response: %w", err)
		}
	}
	return nil
}
