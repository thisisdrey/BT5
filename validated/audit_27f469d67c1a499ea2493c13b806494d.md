## Title
Reward/vote-weight distribution repeatedly floors per-account shares, causing allocated reward pools and delegated voting weight to be permanently under-distributed - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
The Code4rena finding describes a class of bug where a proportional share (`votingPower`) is computed independently for every participant using integer/floor division, so the sum of the individual shares is strictly less than the total that should be distributed — making a 100% (unanimous) outcome mathematically unreachable. java-tron contains the same rounding pattern in the reward-distribution and delegated-vote-adjustment code paths that are reachable by any staked/voting account, not just privileged roles.

### Finding Description
`MortgageService.payStandbyWitness()` computes a `double eachVotePay = (double) totalPay / voteSum` and then pays each standby witness `(long) (w.getVoteCount() * eachVotePay)`, truncating (flooring) the payout for every single witness independently: [1](#0-0) 

The same floor-per-recipient pattern is duplicated in `IncentiveManager.reward()`: [2](#0-1) 

Because every recipient's share is rounded down independently (as opposed to tracking a running remainder and giving it to the last recipient), the sum of all `pay` values paid out is always `<= totalPay`, and the residual (`totalPay - sum(pay)`) is never credited to any account and never carried forward to the next cycle — it is silently discarded.

The same rounding-down-for-every-share pattern also appears in the voter-reward computation, where the reward for each individual voter is computed with a floor division against the SR's total accumulated reward: [3](#0-2) [4](#0-3) 

This code is reached by any unprivileged account that stakes TRX and votes for witnesses (via `VoteWitnessContract`/`vote()` TVM native contract) and later calls `withdrawReward`/`WithdrawBalanceActuator`/`WithdrawRewardProcessor` — none of these require any special/SR privilege. Every voter who splits their vote across several SRs, and every standby-witness cycle, systematically loses a small amount of reward to floor rounding, and that lost amount is not accounted anywhere (not returned to the treasury, not carried to the next cycle, not left in an escrow balance) — it simply vanishes from total accounted balances.

A parallel instance of the exact bug pattern from the report (share of a fixed total computed independently per account, rounding down for every account) also exists in the delegated-vote re-proportioning logic executed whenever a user partially unfreezes stake that backs an active vote: [5](#0-4) 
Here `newVoteCount` is floored for every witness a user voted for, so the sum of a partially-unfrozen account's redistributed votes is always less than its actual entitled `ownedTronPower`, understating the account's real voting power after any partial unfreeze — directly analogous to the reported "votingPower always rounds down, sum never reaches the total" bug class.

### Impact Explanation
Reward/allowance amounts that are deducted from the pay-per-block/standby-allowance budget are not fully credited to voters/witnesses; the un-credited remainder is permanently lost rather than being tracked, refunded, or paid to any party — a form of permanent, unrecoverable loss of protocol-allocated funds. This occurs on every maintenance cycle for every witness/voter combination, so the aggregate leakage compounds continuously across the life of the chain. It also demonstrates that vote-weight accounting (used for SR election/governance) is not conservative: a user's real voting power can silently shrink after every partial `unfreezeBalanceV2` call beyond what their remaining stake would entitle them to.

### Likelihood Explanation
This is triggered under completely ordinary, unprivileged usage: any account that stakes TRX, votes for one or more SRs, and lets the maintenance cycle run (or withdraws rewards / partially unfreezes) will hit this rounding on every cycle. No attacker action, special permission, or malicious SR/validator behavior is required — it is a deterministic consequence of the current arithmetic and will occur on virtually every mainnet cycle where a voter's proportional share does not divide evenly.

### Recommendation
Replace the "round down independently for every recipient" pattern with an approach that preserves the invariant that the sum of distributed shares equals the total (e.g., track a running/cumulative remainder and let the last recipient absorb the leftover, or use exact integer arithmetic with an explicit "remainder carried to next payee" scheme) for `MortgageService.payStandbyWitness`, `IncentiveManager.reward`, `MortgageService.computeReward`, `VoteRewardUtil.computeReward`, and the vote re-proportioning logic in `UnfreezeBalanceV2Processor`/`UnfreezeBalanceActuator`.

### Proof of Concept
1. Create N standby witnesses whose vote counts do not evenly divide `totalPay` (e.g. votes = {1, 1, 1} and `totalPay` = 10, `voteSum` = 3).
2. Call `MortgageService.payStandbyWitness()` — `eachVotePay = 10/3 = 3.333...`; each witness receives `(long)(1 * 3.333) = 3`, total paid = 9, while `totalPay` was 10.
3. Observe that the 1 unit of reward is never credited to any account and is not reflected in any store (`DelegationStore`), constituting a silent, permanent loss repeated every cycle.
4. Similarly, freeze TRX, vote for two SRs with amounts that do not evenly divide the account's `ownedTronPower` after a partial `unfreezeBalanceV2`, and observe in `UnfreezeBalanceV2Processor.updateVote` that the recomputed vote sum is strictly less than the account's actual `ownedTronPower / TRX_PRECISION`.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
