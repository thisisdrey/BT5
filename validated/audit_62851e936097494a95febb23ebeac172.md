### Title
Unbounded array allocation from attacker-controlled length word in `BatchValidateSign`/`ValidateMultiSign` precompiles causes node OOM crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `BatchValidateSign` and `ValidateMultiSign` TVM precompiled contracts decode a "length" word directly from attacker-supplied calldata and pass it straight into `new byte[len][]` (via `extractBytesArray`/`extractBytes32Array`/`extractSigArray`) without first bounding `len` against the actual size of the remaining input. Energy for these precompiles is charged based on the physical size of the calldata buffer (`data.length`), not on the decoded length field, so a small, cheap transaction can embed a huge length word and force the node to attempt an allocation of up to `Integer.MAX_VALUE` array slots before any subsequent bounds check runs.

### Finding Description
`extractBytes32Array` and `extractBytesArray` read an attacker-controlled count directly from the calldata and allocate an array of that size before validating it against the actual payload: [1](#0-0) 

In `BatchValidateSign.doExecute`, the bound check (`MAX_SIZE`) on `addrArraySize`/`sigArraySize` is only performed when `VMConfig.allowTvmSelfdestructRestriction()` is true; `extractBytes32Array(words, words[2].intValueSafe() / WORD_SIZE)` for `addresses` is invoked unconditionally right after, regardless of that flag: [2](#0-1) 

Similarly, in `ValidateMultiSign.execute`, when `allowTvmSelfdestructRestriction()` is false, `extractBytesArray` is called directly with no prior `MAX_SIZE` check, unlike the `extractSigArray` branch that is gated by the size check: [3](#0-2) 

The energy charged for these precompiles is a function of `data.length` (physical bytes supplied), not the decoded internal length word: [4](#0-3) [5](#0-4) 

This is structurally analogous to CVE-2017-5335: a length field taken from untrusted input is used to drive memory allocation before the parser has validated that the declared length is consistent with the actual amount of available data, allowing an attacker to force an out-of-memory condition with a small crafted input.

I was not able to fully confirm, within the available search budget, whether `VMConfig.allowTvmSelfdestructRestriction()` is enabled by default on the currently deployed mainnet configuration (the corresponding `DynamicPropertiesStore` getter/default was not found in the indexed portion of the codebase). If this flag is already permanently activated on mainnet, the vulnerable `extractBytesArray`/unconditional `extractBytes32Array` call in `BatchValidateSign` (addresses path) is still reachable regardless of the flag, since that call is never guarded by the flag at all — only `signatures` extraction switches paths. This makes the `addresses` allocation in `BatchValidateSign` unconditionally exploitable irrespective of the fork flag's state.

### Impact Explanation
A contract call to the `BatchValidateSign` (or pre-fork `ValidateMultiSign`) precompiled contract with a crafted length word can cause the node executing the transaction to attempt to allocate an array with up to ~2^31 elements (each a pointer, i.e. up to ~16 GB on a 64-bit JVM for `byte[][]`), triggering `OutOfMemoryError`. Because precompiled contract execution happens during ordinary TVM contract calls that are part of consensus (every full node must execute the same transaction while applying/validating the block in `Manager`), this can crash or hang multiple/all full nodes processing the block, resulting in a chain halt or repeated node crash — a High severity, node-crash/DoS class impact reachable by any unprivileged contract deployer/caller.

### Likelihood Explanation
The precompiles are reachable via a plain `CALL`/`STATICCALL` from any smart contract to the fixed precompile addresses, requiring no special privilege — any account able to broadcast a `TriggerSmartContract` transaction can reach this code path. Energy cost scales with the physical calldata length, not the internal length field, so the attack is cheap: a small calldata buffer (just enough words to carry the manipulated length field) is sufficient to trigger a huge allocation attempt.

### Recommendation
- Validate the decoded `len`/count values in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` against a strict upper bound (e.g., `MAX_SIZE`) and against the actual remaining `data.length` *before* allocating any array, for all code paths (not just the `allowTvmSelfdestructRestriction()`-gated branch).
- Apply the `MAX_SIZE` bound check unconditionally in both `ValidateMultiSign` and `BatchValidateSign`, independent of `VMConfig.allowTvmSelfdestructRestriction()`.
- Consider charging energy proportional to the decoded array-size claims (not just physical calldata length) so that oversized length claims are economically penalized even if a size cap is bypassed.

### Proof of Concept
1. Craft a `TriggerSmartContract` transaction whose target contract issues a `STATICCALL`/`CALL` to the `BatchValidateSign` precompile address with calldata structured as:
   - `hash` (word 0)
   - `sigArray offset` word placed so that pre-`allowTvmSelfdestructRestriction` path is exercised, OR construct the `addresses` offset word (word 2) to point at a word whose value is `0x7FFFFFFF` (an enormous claimed array length), while keeping the physical `data` buffer small (just a few words) so `getEnergyForData` computes a low energy cost.
2. Submit the transaction with a modest `feeLimit`.
3. During execution, `extractBytes32Array(words, offset)` executes `int len = words[offset].intValueSafe();` yielding `0x7FFFFFFF`, then `new byte[len][]` attempts a multi-gigabyte allocation, throwing `OutOfMemoryError` inside TVM execution on every full node that processes/validates this transaction.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
