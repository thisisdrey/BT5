### Title
Relay control messages trust attacker-supplied `RelayFromAddr`/`RelayToAddr` without binding them to the sender's certificate-verified identity - ([File: relay_manager.go])

### Summary
`relayManager.handleCreateRelayRequest` and `handleCreateRelayResponse` in [1](#0-0)  derive the relay "from" and "to" addresses entirely from attacker-controlled protobuf fields (`RelayFromAddr`/`RelayToAddr`, or their deprecated v1 equivalents) inside the `NebulaControl` message body, and never check that the claimed `from` address matches the actual, certificate-verified `vpnAddrs` of `h`, the `HostInfo` of the peer that sent the message. This is structurally the same bug class as the reported analog: a value under the attacker's control (a message field playing the role of a "function selector") is dispatched into privileged state-changing logic (establishing/poisoning relay routing state) without validating that it actually corresponds to the entity that is cryptographically authenticated as the sender.

### Finding Description
`HandleControlMsg` unmarshals the control payload and only validates that `RelayFromAddr`/`RelayToAddr` are non-nil [2](#0-1) . It then dispatches to `handleCreateRelayRequest`/`handleCreateRelayResponse` [3](#0-2) .

Inside `handleCreateRelayRequest`, `from` and `target` are taken directly from the message content, and the only identity checks performed are whether `from`/`target` equal the local node's own address (`f.myVpnAddrsTable.Contains(from)` / `Contains(target)`) [4](#0-3) . There is no check tying `from` to `h.vpnAddrs`, i.e., to the identity that the sending peer actually proved via its certificate during the handshake that established `h`. Because `h` is only used to route the response and store relay state, an already-connected (but otherwise legitimate, certificate-holding) peer can send a `CreateRelayRequest` claiming `RelayFromAddr` = an arbitrary third-party victim's overlay IP, and the receiver will call `AddRelay(..., from, ...)` and populate `h.relayState` keyed on that victim address [5](#0-4) , associating relay routing state for the victim's IP with the attacker's authenticated tunnel `h`.

This mirrors the report's core bug class: content inside an authenticated channel is trusted to select/parametrize a privileged operation without cross-checking it against the verified identity of the party that produced it — analogous to a fallback handler selector matching a base-contract function whose privileged effect the caller didn't intend to expose.

### Impact Explanation
An authenticated (but hostile) peer can poison relay routing state on a victim-adjacent node, causing packets addressed to/from an arbitrary victim VPN IP to be associated with the attacker's own tunnel/index. Depending on how relay state is later consumed for forwarding decisions, this can enable traffic to be misdirected or laundered through the attacker as an ostensible relay for a peer it never actually relays for, i.e., remote state poisoning of the overlay's relay topology, without requiring a compromised CA-signed certificate for the victim's identity.

### Likelihood Explanation
The attacker only needs a valid certificate for themselves and an established, otherwise-normal tunnel to a node that uses relays — the standard, expected capability of any legitimate-but-malicious member of the mesh. No spoofed packets, no cryptographic breaks, and no lighthouse compromise are required; only crafting the `RelayFromAddr`/`RelayToAddr` fields of a `CreateRelayRequest` they are permitted to send.

### Recommendation
In `handleCreateRelayRequest` (and the response handler), validate that `RelayFromAddr` (and, where semantically required, `RelayToAddr`) is consistent with the sender's own certificate-verified `h.vpnAddrs` before creating or updating any `relayState`. Any relay-from/target address that does not correspond to an identity the sending `HostInfo` is authorized to represent should be rejected.

### Proof of Concept
1. Node A (attacker) establishes a normal, valid Nebula tunnel to node B, which participates as a relay.
2. A sends a `Control` message wrapping a `NebulaControl{Type: CreateRelayRequest, RelayFromAddr: <victim C's overlay IP>, RelayToAddr: <target D's overlay IP>}`.
3. B's `HandleControlMsg` → `handleCreateRelayRequest` only checks that `from` (C) and `target` (D) are not B's own address; it accepts the message and calls `AddRelay(..., from=C, ...)`, inserting relay state into B's hostmap keyed on C's address, tied to A's `HostInfo` [5](#0-4) .
4. B now has relay/routing state believing A is a valid relay path associated with victim C's address, despite A never having proven control of C's identity.

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}
