## Analysis

The external report's core broken invariant: a **shared, capacity-bounded action queue** is drained/refilled by one actor's benign-looking submit/withdraw cycle, permanently starving other users of the same shared slot.

The closest verified local analog is in `pallet-nomination-pools`: unlike `pallet-staking`'s plain `unbond`, where `MaxUnlockingChunks` is a **per-account** cap on that one staker's own ledger, in nomination pools **every member's unbond ultimately writes into one shared `StakingLedger`** — the pool's single `bonded_account()` — via `T::StakeAdapter::unbond(Pool::from(bonded_pool.bonded_account()), ...)`. [1](#0-0) 

### Title
Pool-wide unbonding-chunk exhaustion via cyclic partial `unbond` calls locks other members' exits - (File: `substrate/frame/nomination-pools/src/lib.rs`)

### Summary
`pallet-nomination-pools::Pallet::unbond` lets any pool member unbond their own points at will. Internally this calls into `pallet-staking`'s `do_unbond`, which enforces `MaxUnlockingChunks` on the **pool's single bonded stash account** — a resource shared by every member of the pool, not per-caller. [2](#0-1) 

### Finding Description
`do_unbond` first checks if the shared ledger's `unlocking` vector is already at `MaxUnlockingChunks`; if so it attempts an implicit `do_withdraw_unbonded` to free mature chunks, then re-checks `ensure!(ledger.unlocking.len() < T::MaxUnlockingChunks::get(), Error::NoMoreChunks)` before inserting a new chunk for the current unbonding era. [3](#0-2) 

Because chunks are keyed by era and merged only when the same era already has an entry, a member who calls `unbond` for a small amount **once per era** creates one *new* distinct chunk per era. `pallet-nomination-pools` itself documents this as the intended design: "If there are too many unlocking chunks to unbond with the pool account, `pool_withdraw_unbonded` can be called to try and minimize unlocking chunks... it may not be possible to release the current unlocking chunks, in which case, the result of this call will likely be the `NoMoreChunks` error." [4](#0-3) 

A pool member (attacker) who joined with the minimum bond can, each era, unbond a dust amount. Once mature chunks are auto-withdrawn (freeing exactly one slot) the attacker's own next-era unbond immediately consumes that freed slot again, keeping the shared ledger permanently at `MaxUnlockingChunks` capacity from the perspective of any other member who tries to `unbond` in the same era window. Existing guards — the `ok_to_unbond_with` checks (`PartialUnbondNotAllowedPermissionlessly`, `MinimumBondNotMet`) — only restrict *who* can unbond *whom*, not the rate at which one member can occupy shared unlocking slots, and `MaxUnbonding` in the pools pallet only bounds the *member's own* `unbonding_eras` map, it does nothing to protect the shared staking-ledger capacity from being monopolized by that same member. [5](#0-4) 

### Impact Explanation
Other legitimate pool members attempting `Call::unbond` (the only way to begin the exit/withdrawal process from a nomination pool) will repeatedly hit `pallet_staking::Error::NoMoreChunks`, exactly as demonstrated in the existing regression test `automatic_unbonding_pools`. [6](#0-5) 

If the attacker sustains one small unbond per era indefinitely (a negligible cost relative to bonding-duration cadence), other members can be denied the ability to initiate unbonding for as long as the attack continues — a fund-lock/denial-of-exit condition affecting unrelated users, matching the report's "disabling of the function for other users" pattern.

### Likelihood Explanation
This requires no privileged role, admin, governance, validator, or off-chain actor — any account that can afford `MinJoinBond` to join the target pool can execute the attack purely through the public, permissionless `unbond` extrinsic once per era. The relevant test (`partial_unbond_max_chunks`) already confirms `MaxUnbondingLimit`/`NoMoreChunks` triggers under exactly this repeated-partial-unbond pattern, showing the shared-capacity exhaustion is a reachable, unprivileged runtime condition rather than a hypothetical. [7](#0-6) 

### Recommendation
Decouple the shared staking-ledger unlocking-chunk capacity from per-member fairness in nomination pools: either rate-limit/queue a member's own repeated `unbond` calls against the shared bonded account (e.g., minimum interval or minimum unbond amount per member per era), or reserve/guarantee slot capacity so no single member can monopolize the shared `MaxUnlockingChunks` window; alternatively, decouple pool-level unbonding requests from the underlying single stash ledger's per-era chunk limit so other members' `unbond` calls do not fail due to another member's activity.

### Proof of Concept
1. Attacker joins Pool `P` with `MinJoinBond`.
2. Each era `e`, attacker calls `Pools::unbond(attacker, attacker, small_amount)`, which inserts a chunk at era `e + bonding_duration` into the pool's shared `bonded_account` ledger (as shown in `automatic_unbonding_pools`/`partial_unbond_max_chunks`).
3. Once the shared ledger's `unlocking.len() == MaxUnlockingChunks`, any other member `victim` calling `Pools::unbond(victim, victim, amount)` triggers `do_unbond`'s implicit `do_withdraw_unbonded`; if no chunk has matured yet in that block (attacker keeps refilling on cadence), `ensure!(ledger.unlocking.len() < MaxUnlockingChunks, NoMoreChunks)` fails and `victim`'s unbond reverts with `pallet_staking::Error::NoMoreChunks`, exactly reproducing lines 356-362 of `test-staking-e2e/src/lib.rs` but with an adversarial (not incidental) trigger repeated indefinitely across eras. [8](#0-7)
