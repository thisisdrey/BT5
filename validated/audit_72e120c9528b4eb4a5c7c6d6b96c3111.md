## Finding

### Title
HTTP Request Smuggling via Unvalidated `Transfer-Encoding` Header in `HttpRequestPreamble` - (File: `stackslib/src/net/http/request.rs`)

### Summary
`HttpRequestPreamble::consensus_deserialize` parses incoming HTTP requests to the Stacks RPC server but never inspects the `Transfer-Encoding` header at all. It only recognizes `host`, `content-type`, `content-length`, `connection`, and `set-cookie`; any other header, including `Transfer-Encoding`, falls into the generic catch-all branch and is stored as an opaque header string. `Content-Length` is parsed and trusted unconditionally, with no check for a conflicting `Transfer-Encoding: chunked`. This is the same bug class as the Netty HTTP/1.0 TE+CL coexistence flaw — the CL/TE equality that must hold between the framing method the edge/proxy uses and the framing method the Stacks node uses is not enforced.

### Finding Description
`HttpRequestPreamble::consensus_deserialize` [1](#0-0)  loops over all headers and dispatches only on `host`, `content-type`, `content-length`, `connection`, and `set-cookie` [2](#0-1) . There is no branch for `transfer-encoding`, so a request carrying both `Content-Length: N` and `Transfer-Encoding: chunked` parses successfully — `content_length` is set from the header value and `Transfer-Encoding` is silently absorbed into the generic `headers` map with no semantic effect and no error.

Contrast this with `HttpResponsePreamble::consensus_deserialize`, which explicitly tracks `chunked_encoding` and rejects the message outright if both `Content-Length` and `Transfer-Encoding: chunked` are present [3](#0-2) . The request path has no equivalent guard — this is precisely the asymmetry the Netty advisory describes (HTTP/1.1 path stripped the conflicting header, HTTP/1.0 path did not); here, the *response* path enforces CL/TE exclusivity while the *request* path does not enforce it at all, regardless of HTTP version.

Once parsed, the preamble's `Content-Length` becomes authoritative for framing: `ProtocolFamily::payload_len` for `StacksHttpPreamble::Request` returns `Some(http_request_preamble.get_content_length() as usize)` unconditionally [4](#0-3) , and the connection layer then reads exactly that many bytes as the message body [5](#0-4) . Any reverse proxy or load balancer sitting in front of the Stacks node's RPC interface that is TE-first (per RFC 7230 §3.3.3, TE should take precedence when both are present) will disagree with the node about where the request body ends. An attacker-controlled suffix of the "chunked" body — bytes the node ignores as body but the proxy treats as the start of a new request — can smuggle a second, attacker-chosen HTTP request that the proxy/other clients may see as originating from a trusted upstream connection.

### Impact Explanation
This breaks the request-framing equality between the edge proxy and the Stacks node's RPC server, enabling classic HTTP request smuggling: cache poisoning, bypassing authentication/IP-allowlisting on RPC endpoints, or injecting requests attributed to another client on a shared/pooled connection to the node. Per the scan rules this maps to the Critical bucket ("request smuggling or auth bypass").

### Likelihood Explanation
Reachable by any remote, unauthenticated client that can send an HTTP request to a Stacks node's RPC/API endpoint, with no special privileges or keys required — only a deployment where the node sits behind a proxy that honors `Transfer-Encoding` (common default in many proxies) is needed to complete the smuggling chain.

### Recommendation
In `HttpRequestPreamble::consensus_deserialize`, add explicit handling for the `transfer-encoding` header symmetric to the response parser: reject (or unambiguously resolve per RFC 7230 §3.3.3, preferring `Transfer-Encoding`) any request that carries both `Content-Length` and `Transfer-Encoding`, and reject any `Transfer-Encoding` value other than `chunked` (or reject chunked requests entirely if unsupported), mirroring the guard already present in `HttpResponsePreamble::consensus_deserialize` [3](#0-2) .

### Proof of Concept
Send the following to a Stacks node's RPC port (e.g. `20443`), either directly or through a TE-preferring reverse proxy:
```
POST /v2/transactions HTTP/1.1
Host: node:20443
Content-Type: application/octet-stream
Content-Length: 4
Transfer-Encoding: chunked

0

POST /v2/admin/leak HTTP/1.1
Host: node:20443
...
```
`HttpRequestPreamble::consensus_deserialize` accepts this (no error is raised for the conflicting headers), and `payload_len()` uses `Content-Length: 4`, consuming only `"0\r\n\r\n"`-worth of bytes as the body [4](#0-3) . A front-end proxy honoring `Transfer-Encoding: chunked` sees a zero-length chunked body terminating at `0\r\n\r\n`, then treats the remaining bytes (`POST /v2/admin/leak ...`) as a new, separate request — the two parties disagree on the message boundary.

                        return Err(CodecError::DeserializeError(
                            "Invalid HTTP request: header value is too big".to_string(),

                    }

                    let key = req_header.name.to_lowercase();

                    if seen_headers.contains(&key) {
                        return Err(CodecError::DeserializeError(format!(
                            "Invalid HTTP request: duplicate header \"{}\"",
                            key
                        )));
                    }

                    if key == "host" {
                        peerhost = match value.parse::<PeerHost>() {
                            Ok(ph) => Some(ph),
                            Err(_) => None,

                        seen_headers.insert(key);
                    } else if key == "content-type" {
                        // parse
                        let ctype = value.to_lowercase().parse::<HttpContentType>()?;
                        content_type = Some(ctype);
                        seen_headers.insert(key);
                    } else if key == "content-length" {
                        // parse

                            Ok(len) => Some(len),
                            Err(_) => None,
                        };
                        seen_headers.insert(key);

                        // parse
                        if value.to_lowercase() == "close" {
                            keep_alive = false;
                        } else if value.to_lowercase() == "keep-alive" {
                            keep_alive = true;
                        } else {
                            return Err(CodecError::DeserializeError(
                                "Inavlid HTTP request: invalid Connection: header".to_string(),
                            ));
                        }
                        seen_headers.insert(key);
                    } else if key == "set-cookie" {
                        set_cookie.push(value);

                            .and_modify(|entry| {
                                entry.push_str(", ");
                                entry.push_str(&value);
                            })
                            .or_insert(value);
                    }
                }

    /// Try and consume a payload from our internal buffer when the length of the payload is given
    /// in the preamble.
    fn consume_payload_known_length(
        &mut self,
        protocol: &mut P,
        preamble: &P::Preamble,
    ) -> Result<Option<P::Message>, net_error> {
        let payload_len_opt = protocol.payload_len(preamble);
        let payload_len = payload_len_opt.expect("BUG: payload length assumed to be known");
        let buf_bytes = self.buf.get(self.message_ptr..).ok_or_else(|| {
            net_error::RecvError(format!("Message ptr {} overran buffer", self.message_ptr))
        })?;

        // reading a payload of known length
        if buf_bytes.len() >= payload_len {
            // definitely have enough data to form a message
            if let Some(ref pubk) = self.public_key {
                protocol.verify_payload_bytes(pubk, preamble, buf_bytes)?;
            }

            // consume the message
            let message_opt = match protocol.read_payload(preamble, buf_bytes) {
                Ok((message, message_len)) => {
                    test_debug!("Got message of {} bytes with {:?}", message_len, preamble);
                    let next_message_ptr = self.message_ptr.checked_add(message_len).ok_or(
                        net_error::OverflowError("Overflowed buffer pointer".to_string()),
                    )?;

                    // begin parsing at the end of this message
                    let data = self.buf.get(next_message_ptr..).ok_or_else(|| {
                        net_error::RecvError(format!(
                            "Next message ptr {next_message_ptr} overran buffer"
                        ))
                    })?;

                    self.message_ptr = 0;
                    self.payload_ptr = 0;
                    self.buf = data.to_vec();

                    if !self.buf.is_empty() {
                        test_debug!(
                            "Buffer has {} bytes remaining: {:?}",
                            self.buf.len(),
                            &self.buf.to_vec()
                        );
                    }
                    Some(message)
                }
                Err(e) => {
                    // will never be valid, even if underflowed, since the preamble ought to have
                    // told us the message length
                    debug!(
                        "Invalid message payload: {:?}.  Preamble was {:?}",
                        &e, &preamble
                    );
                    return Err(net_error::InvalidMessage);
                }
            };
            Ok(message_opt)
        } else {
            // not enough data yet
            Ok(None)
        }
    }
