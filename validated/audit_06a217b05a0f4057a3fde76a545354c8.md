### Title
Unchecked `BigInteger.longValue()` truncation in TRX voting-reward computation can silently corrupt witness reward payouts - (`chainbase/src/main/java/org/tron/core/service/MortgageService.java`, `actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java`)

### Summary
The vote-reward ("Vi" algorithm) computation converts a `BigInteger` result to a `long` using the unchecked `.longValue()` method instead of the checked `.longValueExact()` (or an overflow-guarded path) that the rest of the codebase consistently uses for financial math. `BigInteger.longValue()` silently truncates/wraps values that exceed `Long.MIN_VALUE`/`Long.MAX_VALUE` rather than throwing, so if the intermediate `deltaVi * userVote` product (after dividing by `DECIMAL_OF_VI_REWARD`) exceeds a 64-bit signed long, the resulting reward is an arbitrary wrapped value instead of a rejected/clamped one.

### Finding Description
`DelegationStore.DECIMAL_OF_VI_REWARD = 10^18` is used as a fixed-point scaling factor for the per-cycle reward-per-vote accumulator ("Vi"), accumulated with unbounded `BigInteger` precision in `DelegationStore.accumulateWitnessVi` / `RewardViCalService.accumulateWitnessVi`: [1](#0-0) 

When a voter withdraws or queries their reward, the code re-materializes the reward as:
```
reward += deltaVi.multiply(BigInteger.valueOf(userVote))
    .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
```
This exact pattern appears in three call sites: [2](#0-1) [3](#0-2) [4](#0-3) 

`deltaVi` is the accumulated `Vi` delta across an arbitrary number of maintenance cycles (accumulated as unbounded `BigInteger`, so it never throws on overflow itself) and `userVote` is attacker-controlled (`vote.getVoteCount()`, driven directly by a signed `VoteWitnessContract`/`FreezeBalanceContract` from any account). Because `deltaVi` accumulates without any cap over the lifetime of a witness that has very low total vote weight relative to its rewards, `deltaVi * userVote / 10^18` can legitimately grow past `Long.MAX_VALUE` (~9.22 × 10^18) for a normal, unprivileged voter with a large frozen balance voting for a low-vote-weight witness over an extended, unbounded time horizon. `.longValue()` then silently wraps this to an arbitrary (possibly negative, possibly small-and-wrong, possibly huge-and-wrong) 64-bit value — exactly the "unchecked" financial-arithmetic risk flagged in the source report, where an unchecked numeric conversion in a fee/reward computation can corrupt contract state.

This is reachable from a fully unprivileged path:
`WithdrawBalanceActuator.execute()` → `MortgageService.withdrawReward()` → `computeReward()` (unchecked `.longValue()`): [5](#0-4) 
and equivalently via the TVM-vote native path `VoteRewardUtil.withdrawReward()`/`queryReward()` invoked from `WithdrawRewardProcessor`/vote-related TVM operations.

Notably, sibling reward/fee-sensitive computations elsewhere in this codebase (`ResourceProcessor`, `RepositoryImpl`, `AbstractExchangeActuator`, `TransferActuator`, etc.) have been explicitly hardened with `StrictMathWrapper`/`longValueExact()`/`hardenCalculation()` feature-flag gates to reject overflow with `ArithmeticException` rather than silently wrap: [6](#0-5) 
This confirms the general pattern the project follows for such calculations, and highlights that the vote-reward `.longValue()` call sites were left un-hardened, which is the concrete "unchecked" analog to the reported bug class.

### Impact Explanation
If the wrapped/truncated reward value is used to increase `AccountCapsule.allowance` (via `adjustAllowance`) and subsequently credited to the account balance in `WithdrawBalanceActuator.execute()`, this can either:
- silently under-pay a legitimate voter (permanent loss of the rightfully earned reward), or
- silently produce a wrapped value that is nonetheless positive and added to the account's spendable balance, creating an unbacked TRX credit not backed by the transaction-fee/block-reward pool (inflation / unbacked balance).

Either outcome is a concrete violation of accounting integrity in a core, frequently-used consensus/reward path (`Manager.payReward` → `MortgageService`), affecting any account that votes and withdraws rewards.

### Likelihood Explanation
Triggering requires a witness with sustained but comparatively small total vote weight (so `Vi` per cycle deltas are large) accumulating over many maintenance cycles combined with a voter placing a very large frozen-balance vote (`userVote`) on that witness right before withdrawal. This is a long-tail, but fully permissionless scenario reachable purely by freezing TRX, voting, and calling `WithdrawBalanceContract` — no privileged role or malicious SR/witness/peer behavior is required, satisfying the analog constraints. The magnitude of TRX total supply (~10^14 sun) times the 10^18 scaling factor is well within range to exceed `Long.MAX_VALUE` under adversarial vote/reward distribution, though exact triggering conditions (specific witness reward/vote ratios over specific numbers of cycles) were not fully modeled here and would need targeted numeric analysis/testing to pin down the minimal concrete exploit inputs.

### Recommendation
Replace `.longValue()` with `.longValueExact()` in all three reward-computation call sites (`VoteRewardUtil.computeReward`, `MortgageService.computeReward`, `RewardViCalService.getNewRewardAlgorithmReward`), or route the computation through the same `StrictMathWrapper`/hardened-BigInteger pattern already used in `ResourceProcessor`/`RepositoryImpl`, so that an overflowing reward computation throws `ArithmeticException` (caught and rejected) instead of silently wrapping. Consider also bounding per-cycle/per-witness `Vi` accumulation growth to avoid unbounded magnitude drift over time.

### Proof of Concept
Conceptual reproduction (exact numeric parameters require simulation against `RewardViCalService`/`DelegationStore` cycle accounting):
1. Freeze a very large TRX balance and vote for a witness `W` that otherwise receives comparatively small total vote weight from other accounts, so `W`'s per-cycle `Vi` delta (`reward * 10^18 / totalVoteCount`) is large relative to `totalVoteCount`.
2. Do not withdraw for many maintenance cycles, allowing the unbounded `BigInteger` `Vi` accumulator in `DelegationStore.accumulateWitnessVi` to grow.
3. Call `WithdrawBalanceContract` (`WithdrawBalanceActuator.execute`) to trigger `MortgageService.withdrawReward` → `computeReward`, where `deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD)` exceeds `Long.MAX_VALUE`.
4. Observe `.longValue()` return a wrapped (incorrect, possibly negative or bogus-large) value credited via `adjustAllowance` instead of an `ArithmeticException`, corrupting the account's `allowance`/balance state.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
