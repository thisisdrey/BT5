### Title
Housekeeping middleware leaves per-repository maintenance lock permanently stuck if the wrapped handler panics - ([File: internal/grpc/middleware/housekeeping/middleware.go])

### Summary
The Solana report describes a state-tracking value (the nonce) that is only advanced on the success path and never reset/advanced when the operation aborts, leaving the system permanently stuck. The `Middleware.UnaryServerInterceptor` in gitaly's housekeeping middleware exhibits the same class of bug for its `OpMaintenance` per-repository activity flag: the flag is set to `true` before invoking the handler and is only cleared by an explicit statement *after* the handler returns, with no `defer`/panic-recovery in between.

### Finding Description
For RPCs classified as `protoregistry.OpMaintenance`, the interceptor does: [1](#0-0) 

```go
case protoregistry.OpMaintenance:
    m.mu.Lock()
    if m.isActive(key) {
        m.mu.Unlock()
        return nil, structerr.NewAlreadyExists("housekeeping already executing for repository")
    }
    m.markHousekeepingActive(key)
    m.mu.Unlock()

    resp, err := handler(ctx, req)

    m.markHousekeepingInactive(key)

    return resp, err
```

`markHousekeepingActive`/`markHousekeepingInactive` toggle a per-repo boolean stored in `m.repoActivity[key]`: [2](#0-1) 

Unlike the scheduled/background housekeeping path (`scheduleHousekeeping`), which properly wraps its cleanup in a `defer` so `markHousekeepingInactive` always runs even on failure: [3](#0-2) 

...the synchronous `OpMaintenance` path calls `markHousekeepingInactive(key)` as a plain statement after `handler(ctx, req)` returns, not inside a `defer`. If `handler(ctx, req)` panics (e.g. an unrecovered panic somewhere deep in the maintenance RPC implementation, such as a nil-pointer dereference or index-out-of-range triggered by a crafted/edge-case request, or an OOM/stack-overflow condition), the goroutine unwinds past this call without ever clearing the `active` flag for that `repoKey`. Because `grpc-recovery` middleware (if configured) recovers the panic *outside* this interceptor frame and converts it into an `Internal` error response, the request appears to "fail" from the client's perspective, but `m.repoActivity[key].active` remains `true` forever — the in-memory equivalent of the nonce never being incremented back on failure in the Solana report.

Once stuck, every subsequent `OpMaintenance` RPC (e.g. `OptimizeRepository`) issued by an ordinary user against that same repository is permanently rejected with `AlreadyExists("housekeeping already executing for repository")`, because `isActive(key)` at line 162 will always be `true`: [4](#0-3) 

There is no timeout, TTL, or lease-expiry mechanism (unlike, for example, the `repository_reference_write_locks` mechanism in Praefect which has an explicit expiry sweep) to recover from this stuck state; the only recovery path is restarting the Gitaly process (which resets the in-memory `repoActivity` map).

### Impact Explanation
This is a permanent (until process restart) denial-of-service of the maintenance/housekeeping RPC surface for a specific repository, triggerable by an ordinary client sending a request that causes a panic in the handler chain for an `OpMaintenance`-classified RPC. Because the state is purely in-memory and keyed per `(storage, relativePath)`, a single crafted request against one repository can never legitimately run housekeeping RPCs (`OptimizeRepository`, etc.) again on that Gitaly node until restart, degrading repository health over time (no repacking/GC), without needing any privileged access.

### Likelihood Explanation
Likelihood depends on the ability to trigger a panic inside an `OpMaintenance` handler without the interceptor observing it — this requires an unrecovered panic in the RPC-specific code path, which is not something I could concretely verify occurs today at any specific `OpMaintenance` handler in this index (panics in Go RPC handlers are commonly guarded by a separate `grpc-recovery` interceptor at a different layer, and I could not confirm from this index whether that interceptor runs before or after `panic` unwinds through this housekeeping middleware frame, or whether any currently-known input can panic a maintenance RPC). The structural bug — the flag being cleared with a bare statement instead of a `defer` — is confirmed and reachable by design for any panic in this call chain, but I could not find a concrete existing panic-producing input in the indexed code, so likelihood should be treated as conditional on such a panic path existing/being found (or on some other early-exit path such as `runtime.Goexit` or fatal signal).

### Recommendation
Wrap the `markHousekeepingInactive(key)` call in a `defer` (mirroring the pattern already used in `scheduleHousekeeping`'s `finish` function) immediately after successfully marking the repo active, so the flag is always cleared regardless of whether `handler(ctx, req)` returns normally, returns an error, or panics:

```go
case protoregistry.OpMaintenance:
    m.mu.Lock()
    if m.isActive(key) {
        m.mu.Unlock()
        return nil, structerr.NewAlreadyExists("housekeeping already executing for repository")
    }
    m.markHousekeepingActive(key)
    m.mu.Unlock()
    defer m.markHousekeepingInactive(key)

    return handler(ctx, req)
```

Additionally, consider adding a lease/TTL-based expiry (similar to `repository_reference_write_locks`) as defense-in-depth against any other unrecovered path (e.g., `runtime.Goexit`, process signals) that could still leave the flag stuck.

### Proof of Concept
Not runnable within this index — proving the panic trigger requires identifying (or injecting) a concrete panicking input within an `OpMaintenance`-classified RPC handler, which was not confirmed here. The structural absence of `defer` around `markHousekeepingInactive` is directly observable in the cited source and is sufficient to demonstrate the stuck-state risk analogous to the reported nonce-not-incremented-on-failure bug class.

func (m *Middleware) markHousekeepingActive(key repoKey) {
	a, ok := m.repoActivity[key]
	if !ok {
		a = newActivity()
		m.repoActivity[key] = a
	}

	a.active = true
}

func (m *Middleware) markHousekeepingInactive(key repoKey) {
	m.mu.Lock()
	defer m.mu.Unlock()

	a, ok := m.repoActivity[key]
	if !ok {
		a = newActivity()
		m.repoActivity[key] = a
	}

	a.active = false
}
