### Title
Pingback handshake acceptance stores attacker-chosen `NeighborKey` address without verifying it against the address that authenticated the reply - ([File: stackslib/src/net/neighbors/walk.rs])

### Summary
`NeighborWalk::check_handshake_pubkey_hash` (stackslib/src/net/neighbors/walk.rs:1664) only verifies that `Hash160::from_node_public_key_buffer(&data.handshake.node_public_key)` equals `naddr.public_key_hash`; it never checks that `data.handshake.addrbytes`/`data.handshake.port` match `naddr` (the address the walk actually dialed for the pingback session). The unchecked, self-reported `data.handshake` struct is then forwarded verbatim to `NeighborDB::add_or_schedule_replace_neighbor` (stackslib/src/net/neighbors/walk.rs:1718-1724), which is used to construct/update the stored `PeerDB` neighbor record.

### Finding Description
In `pingback_handshakes_try_finish` (stackslib/src/net/neighbors/walk.rs:1683-1742), a reply is received over a TCP session that the local node itself initiated by connecting out to `naddr.addrbytes:naddr.port` (via `neighbor_session_begin` → `neighbor_connect_and_handshake` → `network.connect_peer`, in stackslib/src/net/neighbors/comms.rs:150-227,300-317). This does authenticate that *some* peer is reachable at `naddr`'s socket address, and `check_handshake_pubkey_hash` confirms that the peer's advertised public key hashes to the expected `naddr.public_key_hash` (walk.rs:1664-1680). However, the payload's self-declared `data.handshake.addrbytes`/`port` fields — which are attacker-controlled and can name any third-party address — are never checked against `naddr`. Those unchecked fields are passed straight into `self.neighbor_db.add_or_schedule_replace_neighbor(network, &message.preamble, &data.handshake, db_data, &mut self.neighbor_replacements)` (walk.rs:1718-1724), which uses `handshake.addrbytes`/`handshake.port` to build the `NeighborKey` written into `PeerDB`. This breaks the intended invariant that the stored neighbor address equals the address that was actually cryptographically/socket-authenticated during the pingback exchange — the peer only proved it controls the socket at `naddr` and holds the private key for `naddr.public_key_hash`; it proved nothing about `data.handshake.addrbytes/port`.

### Impact Explanation
An attacker who legitimately answers a pingback (i.e., is reachable at the address that triggered the pingback and controls the matching key) can cause the victim node to write an arbitrary, unverified `NeighborKey`/address pair into its own `PeerDB`. This is an unauthenticated write of unverified peer state which can subsequently be gossiped to other nodes via `GetNeighbors`/`Neighbors` exchanges, spreading unverified address claims into the wider peer-discovery graph. It does not directly cause a crash or fork, but it does inject forged peer-address associations into persistent state and is repeatable each time the attacker is chosen for a pingback.

### Likelihood Explanation
Preconditions are low-cost for a remote, unprivileged attacker: they must simply be reachable at the address that caused them to be scheduled for a pingback (e.g., via an inbound connection or a previously gossiped `NeighborAddress`) and must own a keypair whose Hash160 matches `naddr.public_key_hash` for that entry — which is trivially satisfiable if the attacker is the one who caused the pingback to be scheduled in the first place, since they simply reuse their own key. No secrets, admin roles, or privileged state are required, and the P2P port is remotely reachable by design.

### Recommendation
In `check_handshake_pubkey_hash` (or immediately before calling `add_or_schedule_replace_neighbor` in `pingback_handshakes_try_finish`), additionally assert that `data.handshake.addrbytes == naddr.addrbytes` and `data.handshake.port == naddr.port` (accounting for any legitimate NAT/self-reported-address semantics used elsewhere), rejecting/logging mismatches instead of proceeding to store the neighbor. Alternatively, construct the `NeighborKey` passed to `add_or_schedule_replace_neighbor` from the verified `naddr`/socket address rather than from the self-reported `data.handshake` fields.

### Proof of Concept
Rust test in `stackslib::net::neighbors::walk`:

    /// Does a given handshakedata represent an expected public key hash?
    fn check_handshake_pubkey_hash(
        nk: &NeighborKey,
        data: &HandshakeAcceptData,
        naddr: &NeighborAddress,
    ) -> bool {
        let neighbor_pubkey_hash =
            Hash160::from_node_public_key_buffer(&data.handshake.node_public_key);
        if neighbor_pubkey_hash != naddr.public_key_hash {
            debug!(
                "Neighbor {:?} had an unexpected pubkey hash: expected {:?} != {:?}",
                nk, &naddr.public_key_hash, &neighbor_pubkey_hash
            );
            return false;
        }

        true
    }
