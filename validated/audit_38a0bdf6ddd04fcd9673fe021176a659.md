### Title
RewardsDistributor grants `balance * INITIAL_INDEX` windfall to first claimer while token index is stuck at `INITIAL_INDEX` - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
The Sense bug class is: an externally triggered recomputation can produce a degenerate (zero / unchanged) stored value, which later breaks a validation check that assumed the value had advanced. In Metronome's `RewardsDistributor`, the reward index can stay exactly at `INITIAL_INDEX` (because the accrued `_ratio` rounds to 0, or because only the timestamp is updated), while `accountIndexOf[token][account]` remains `0` for a new account. `_calculateTokenDelta` only applies the `INITIAL_INDEX` fallback when `_tokenIndex > INITIAL_INDEX`, so a first-time claimant gets `_deltaIndex = INITIAL_INDEX - 0 = 1e18` and `tokensDelta = balance * 1e18`, draining the distributor's reward token balance.

### Finding Description
In `contracts/RewardsDistributor.sol`:

- `_updateTokenSpeed` initializes a new token state with `index = INITIAL_INDEX (1e18)` when a governor-set or keeper-synced speed first becomes `> 0` (`RewardsDistributor.sol:296-299`).
- `_calculateTokenIndex` computes `_ratio = _tokensAccrued.wadDiv(_totalSupply)`; if `_tokensAccrued < _totalSupply` (speed small relative to supply, or `syncTokenSpeed` setting a dust-level speed), `_ratio == 0` and `_newIndex` remains `INITIAL_INDEX`, while `_newTimestamp` advances (`RewardsDistributor.sol:200-212`). Note `syncTokenSpeed` computes `_speed = rewardRate * treasuryBalance / totalSupply`, which can legitimately be a tiny nonzero value.
- `_calculateTokenDelta` only back-fills `accountIndexOf` when `_accountIndex == 0 && _tokenIndex > INITIAL_INDEX`. If `_tokenIndex == INITIAL_INDEX` exactly, `_accountIndex` stays `0`, so `_deltaIndex = INITIAL_INDEX - 0 = 1e18` and `_tokensDelta = balanceOf(account) * 1e18` (`RewardsDistributor.sol:222-230`).
- `claimRewards` is permissionless for any `account_` and any registered `tokens_`; it calls `_updateTokenIndex` then `_updateTokensAccruedOf`, then `_transferRewardIfEnoughTokens`, which pays out `tokensAccruedOf[account]` whenever it is `<=` the distributor's reward token balance (`RewardsDistributor.sol:150-167`, `248-255`).

So an unprivileged attacker can: wait for (or help create, by keeping `token_.totalSupply()` large via deposits) a state where `index == INITIAL_INDEX` and their `accountIndexOf == 0`, deposit into the `DepositToken` (or hold `DebtToken`) to get a balance, then call `claimRewards(attacker, [token])` and receive `depositBalance * 1e18` reward tokens — capped only by the distributor's balance.

### Impact Explanation
Direct theft of unclaimed yield: `tokensAccruedOf[attacker]` is inflated by `balance * 1e18`, and `_transferRewardIfEnoughTokens` transfers the entire distributor `rewardToken` balance to the attacker, stealing rewards accrued for all legitimate suppliers/borrowers.

### Likelihood Explanation
- The attacker is fully unprivileged: `claimRewards` has no `only*` gating on the caller and accepts arbitrary `accounts_`/`tokens_`.
- Trigger condition `index == INITIAL_INDEX` is reachable whenever `_tokensAccrued < _totalSupply` in `_calculateTokenIndex`, i.e. for any nonzero but small speed (including `syncTokenSpeed` producing a tiny speed), or in the same block a token speed is first enabled before index growth.
- The attacker can force the condition deterministically by depositing a large amount into the `DepositToken` right after `updateTokenSpeed`/`syncTokenSpeed` activates the token, making `wadDiv` round `_ratio` to 0 for the remainder of that window, then claiming.
- No modifier stops it: `whenNotShutdown`, `nonReentrant`, and `onlyIfTokenExists` all pass on the deployed configuration.

### Recommendation
In `_calculateTokenDelta`, apply the `INITIAL_INDEX` fallback whenever `_accountIndex == 0` (not only when `_tokenIndex > INITIAL_INDEX`), i.e. treat a zero stored account index as "never interacted" and use `min(_tokenIndex, INITIAL_INDEX)` — equivalently: `if (_accountIndex == 0) _accountIndex = INITIAL_INDEX;` capped by `_tokenIndex`. Alternatively, in `_updateTokenSpeed`, set `accountIndexOf`/`tokenStates` such that the index is strictly greater than `INITIAL_INDEX` before any balance-bearing account can claim, or revert/disable claiming while `index <= INITIAL_INDEX`.

### Proof of Concept
Foundry test sketch (run against the repo's existing test fixtures, e.g. `test/foundry` pool/depositToken setup):

```solidity
// Assume: pool, depositToken (with underlying `underlying`), rewardsDistributor
// with rewardToken funded, and governor has called updateTokenSpeed(depositToken, speed)
// where speed is small (e.g. 1 wei/sec) and depositToken.totalSupply() is huge,
// or the attacker makes it huge.

address attacker = address(0xA11CE);

// 1. Attacker deposits a large amount so depositToken.totalSupply() >> speed * dt
uint256 deposit = 1_000_000e18;
underlying.mint(attacker, deposit);
vm.startPrank(attacker);
underlying.approve(address(depositToken), deposit);
depositToken.deposit(deposit, attacker);

// 2. Warp a bit — _calculateTokenIndex still returns index == INITIAL_INDEX
//    because _ratio = dt*speed / totalSupply rounds to 0
vm.warp(block.timestamp + 10);

// 3. Claim: accountIndexOf[attacker] == 0, index == INITIAL_INDEX (not >),
//    so deltaIndex = 1e18 and tokensDelta = deposit * 1e18
IERC20[] memory toks = new IERC20[](1);
toks[0] = IERC20(address(depositToken));
rewardsDistributor.claimRewards(attacker, toks);

// 4. Attacker receives the entire distributor rewardToken balance
assertEq(rewardToken.balanceOf(attacker), rewardToken.balanceOf(address(rewardsDistributor)) /* before */);
assertEq(rewardToken.balanceOf(address(rewardsDistributor)), 0);
vm.stopPrank();
