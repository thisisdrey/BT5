## No vulnerability found for this question.

**Analysis supporting this conclusion:**

The binding claimed to be broken is: `TokenId::from_str(s).variant == the type prefix that the string s truly should represent`. Tracing the parse path in `crates/primitives/token-id/src/lib.rs`, `TokenId::from_str` does `s.split_once(':')` **once**, obtaining `(typ, data)`, then dispatches on `typ.parse::<TokenIdType>()` before ever looking at `data`: [1](#0-0) 

For an attacker to smuggle a `nep245:` or `imt:` prefix "inside" what should be the Nep141 `contract_id` field and have it reclassify the token, the fake prefix would have to appear *before* the real type prefix, i.e., become the substring returned by the first `split_once(':')`. But `split_once` always returns the text before the **first** literal `:` in the whole string as `typ`. If the attacker writes something like `nep141:nep245:evil.near`, `typ` is `"nep141"` (correctly parsed as `TokenIdType::Nep141`), and `data` becomes `"nep245:evil.near"`, which is then handed to `Nep141TokenId::from_str`: [2](#0-1) 

That function requires `data.parse::<AccountId>()` to succeed for the *entire* remaining string. NEAR `AccountId` syntax disallows the `:` character, so `"nep245:evil.near"` fails to parse as a valid `AccountId` and the whole `TokenId::from_str` call returns an error — no misclassification occurs, it just fails.

The same holds in reverse: an attacker cannot make what should be a Nep245/Imt token parse as Nep141 by hiding a `:` in the `contract_id` portion, since `Nep245TokenId::from_str`/`ImtTokenId::from_str` split `data` once more into `(contract_id, token_id)` where `contract_id` must again be a valid, colon-free `AccountId`: [3](#0-2) [4](#0-3) 

Any extra colon can only land inside the trailing `mt_token_id`/`token_id` string field (which is not further reparsed), not the `contract_id`/`minter_id` field, since those are bounded by NEAR's account-id grammar.

Finally, `TokenDiff::token_fee`'s dispatch via `token_id.into(): TokenIdType` is not a second string-based classification step — it uses the `strum_discriminants`-generated enum discriminant of the already-constructed `TokenId` Rust enum value (backed by the `From<&Nep141TokenId> for TokenIdType` etc. impls), which was fixed at construction time by the successful `FromStr` parse: [5](#0-4) [6](#0-5) 

There is no re-parsing of the string form at the `token_fee` call site that could be fooled independently of the original `FromStr` result. Because NEAR `AccountId`s cannot contain `:`, `TokenId::to_string()`/`FromStr` round-trips exactly (as also asserted by the existing `display_from_str_roundtrip` tests), and no crafted string can cause `TokenId::from_str` to classify a Nep141 fungible token as Nep245/Imt (or vice versa). The premise of the question — that the parser can be fooled by an embedded `nep245:`/`imt:` substring inside a `contract_id` — does not hold given the NEAR account-id character restrictions enforced by `AccountId::from_str` at every field boundary.
