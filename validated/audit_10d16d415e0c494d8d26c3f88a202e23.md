### Title
Fee-on-transfer / non-standard SIP-010 tokens can desynchronize vault `assets`/shares accounting from real token balance - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
The Zest v2 vaults (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, and their `local-testing` counterparts) mint shares and increment the internal `assets` accumulator using the caller-supplied `amount` parameter directly, without verifying that the vault's underlying-token balance actually increased by that amount. This is the same root-cause class as WatchPug's WP-M17 finding against `Vault.sol#addValue()`: any deviation between the nominal transfer amount and the actually-received amount (fee-on-transfer, deflationary, or otherwise non-standard SIP-010 token behavior) causes the vault's share/asset accounting to diverge from real backing.

### Finding Description
In every vault's `deposit` function, shares are computed from the caller-supplied `amount` via `convert-to-shares-preview`, then the underlying token is pulled with `receive-underlying`, `zft` shares are minted for `inkind`, and `assets` is unconditionally incremented by the nominal `amount` — not by the token balance delta actually observed on the vault contract: [1](#0-0) 

```
(define-public (deposit (amount uint) (min-out uint) (recipient principal))
    (let (
      ...
      (inkind (convert-to-shares-preview amount)))
    ...
    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
    (var-set assets (+ current-assets amount))
```

The same pattern (`amount` trusted for shares math and `assets` bookkeeping instead of a before/after balance check) is duplicated across all six vault contracts [2](#0-1) [3](#0-2)  and in the market-layer collateral-add pathway, which similarly credits `add-user-collateral` with the nominal `amount` right after calling `receive-tokens`: [4](#0-3) .

If the underlying asset were ever a token with transfer-fee, rebasing, or blacklist/partial-transfer semantics, the vault would record `assets` and mint shares for the full nominal `amount` while its real SIP-010 balance only increased by `amount - fee`. Because `convert-to-shares-preview` and `convert-to-assets-preview` derive from `assets` (the internal ledger) rather than the token's true balance, this creates a permanent gap between claimed backing and actual backing, diluting redemption value for all depositors of that vault.

### Impact Explanation
This lands on temporary/permanent freezing of funds impact: once `assets` is inflated beyond the vault's real token balance, later `redeem` calls will fail `ERR-INSUFFICIENT-LIQUIDITY`/`ERR-INSUFFICIENT-ASSETS` checks for legitimate withdrawals, or the last redeemers are unable to withdraw their fair share of the underlying because it was never actually deposited — freezing a portion of depositors' funds. Since collateral valuation and debt health checks in `v0-4-market.clar` rely on the same `assets`/shares figures, the accounting error can also propagate into overstated collateral value, but the most direct and provable path is depositor fund freezing.

### Likelihood Explanation
Under the current deployed asset set (STX, sBTC, USDC, USDH, stSTX, stSTXbtc) this is not directly exploitable because none of those SIP-010 tokens currently charge transfer fees. However, the vault contracts themselves place no invariant check preventing a fee-bearing or non-standard SIP-010 token from being onboarded as a new vault asset, and the deposit/collateral-add code paths universally trust the nominal `amount` rather than measuring the actual balance delta — so the flaw is structural and would activate immediately upon listing any such asset, with no attacker action beyond a normal `deposit` or `supply-collateral-add` call needed to desynchronize the ledger.

### Recommendation
In each vault's `deposit` (and the market's `collateral-add`/`receive-tokens` flow), read the underlying/collateral token balance held by the vault/market contract immediately before and after the transfer call, and use the observed delta (rather than the caller-supplied `amount`) to compute `inkind` shares and to update `assets`/collateral bookkeeping.

### Proof of Concept
1. Suppose a future vault (e.g., `v0-vault-usdc.clar`) is configured for a hypothetical SIP-010 token that deducts a 1% fee on `transfer`.
2. User calls `deposit(amount: u1000, min-out: u0, recipient: user)`.
3. `receive-underlying` triggers a `transfer`/`transfer-from` of `1000`, but the vault contract's real token balance only increases by `990` due to the fee.
4. `inkind` (shares minted) is computed from `convert-to-shares-preview(1000)` and `assets` is set to `current-assets + 1000` — both based on the nominal, not the received, amount: [5](#0-4) .
5. The vault now believes it holds `10` more underlying tokens than it actually does; subsequent redeemers computing `convert-to-assets-preview` against the inflated `assets` value will be unable to fully withdraw, and the last redeemer(s) will hit `ERR-INSUFFICIENT-LIQUIDITY` since the real token balance is short.
