### Title
Signature malleability in `PrecompiledContracts.ValidateMultiSign` allows a single key's weight to be counted twice, bypassing multi-signature thresholds - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` TVM precompile, used by smart contracts to verify TRON account-permission (multisig) signatures, deduplicates signatures by comparing exact raw signature bytes rather than restricting the ECDSA `s` value to the canonical low-half of the curve order. Because ECDSA signatures are malleable (for any valid `(r, s)` there exists an equally valid `(r, N-s)` with flipped recovery id), an unprivileged caller who has one valid signature from a key can derive a second, bit-different, still-valid signature from the same key and submit both to `ValidateMultiSign`. The weight-accumulation logic only skips a signature when its **exact bytes** already appear in `executedSignList`; a malleated variant does not match, so the same signer's weight is added twice.

### Finding Description
`ECDSASignature.validateComponents()` in `crypto/src/main/java/org/tron/common/crypto/ECKey.java` only checks that `r` and `s` are within `[1, SECP256K1N)`; it does not enforce the BIP-62/EIP-2 canonical rule that `s` must be `<= HALF_CURVE_ORDER`: [1](#0-0) 

`ECDSASignature.toCanonicalised()` exists and is used when *signing* (`doSign`) to always emit a low-`s` signature: [2](#0-1) [3](#0-2) 

but nothing on the *verification* side rejects an attacker-supplied malleated signature `(r, N-s)`.

The `ValidateMultiSign` precompile (reachable from any smart contract, i.e., from an unprivileged transaction/contract-call), recovers a signer address per signature and deduplicates based on the exact signature bytes, not on the signer address alone with a canonicalized signature: [4](#0-3) 

Specifically:
```
byte[] recoveredAddr = recoverAddrBySign(sign, hash);
sign = merge(recoveredAddr, sign);
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
        continue;               // only skips exact-byte duplicates
    }
    MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```
If the address is already present but the raw signature bytes differ (which is trivially achievable by malleating `s` to `N-s` and flipping the recovery id), the `continue` is skipped and the same address's weight is added to `totalWeight` a second time.

This is the same bug class as the reported tbtc issue: a verifier accepts multiple distinct byte-encodings of what is cryptographically "the same" authorization from a single key, and code elsewhere relies on exact-byte-level uniqueness rather than on a canonicalized signature or on the recovered signer identity for anti-replay/anti-double-count logic.

### Impact Explanation
TRON's `Permission`/weighted-key multisig model (`account_permission`) is designed so that a threshold of *distinct* signer weights must be met before a permissioned operation (e.g., asset transfer, contract call) is authorized. `ValidateMultiSign` is the on-chain (TVM-reachable) primitive contracts use to check this. By feeding the precompile two byte-distinct but cryptographically equivalent signatures from the *same single key* (original + malleated `(r, N-s)`), an attacker who controls only one signer of a multi-key account can have that signer's weight counted twice, potentially reaching the threshold that was intended to require cooperation from multiple independent keys. This can permit unauthorized execution of the guarded operation (e.g., unauthorized transfer of funds guarded by a multisig contract relying on this precompile), i.e., theft/unauthorized account operation.

### Likelihood Explanation
The attack requires only:
1. One legitimate signature from any key in the target permission (obtainable by the attacker if they are one of the legitimate signers, or if a signature is otherwise exposed/leaked, e.g. through a prior transaction or off-chain approval flow), and
2. Simple arithmetic to compute the malleated `(r, N-s, v')` pair (standard, publicly known technique, no special access needed).

No special privileges, no waiting on other actors, and no network-level access beyond a normal smart-contract call are needed — any address able to invoke the precompile-consuming contract can attempt this. The complexity is low (well-documented ECDSA malleability transformation) but this specific double-counting requires that a contract exists which uses `ValidateMultiSign` under an assumption that recovered-signer weight can only be counted once per distinct key — a reasonable and expected assumption of an m-of-n scheme, making the flaw practically exploitable wherever this precompile underpins multisig-gated logic.

### Recommendation
1. In `ValidateMultiSign` (and any other signature-consuming verification path), deduplicate strictly by **recovered address**, not by raw signature bytes — i.e., once `recoveredAddr` is present in `executedSignList`, always `continue` (skip), regardless of whether the exact signature bytes match.
2. Additionally/alternatively, enforce canonical low-`s` signatures at the point of validation (mirroring `BondedECDSAKeep`'s check and `ECKey.ECDSASignature.toCanonicalised()`), by adding a low-`s` check inside `ECDSASignature.validateComponents()` or in the precompile's `recoverAddrBySign` path, so malleated high-`s` signatures are rejected outright before recovery.
3. Audit other signature-verification call sites (`TransactionCapsule.checkWeight`, `ECRecover` precompile usage in user contracts) for similar "unique-by-address" vs. "unique-by-signature-bytes" assumptions.

### Proof of Concept
1. Deploy/target a contract-guarded TRON account with `Permission` requiring threshold `T`, containing key `A` with weight `w_A < T` and other keys.
2. Obtain one valid signature `sig1 = (r, s, v)` from key `A` over the relevant hash (e.g., the attacker legitimately controls key `A` or a previously-authorized signature is available).
3. Compute the malleated signature `sig2 = (r, N - s, v XOR 1)` — still a valid ECDSA signature recoverable to the same address `A`.
4. Call the contract function that invokes `ValidateMultiSign` with `signatures = [sig1, sig2, ...]`.
5. In `execute()`, `recoverAddrBySign(sig1, hash)` and `recoverAddrBySign(sig2, hash)` both return address `A`. The first iteration adds `A`'s weight. On the second iteration, `matrixContains(executedSignList, recoveredAddr)` is true (address `A` already seen) but `matrixContains(executedSignList, sign)` is false (different raw bytes), so the `continue` is skipped and `A`'s weight is added again — `totalWeight` becomes `2 * w_A`, potentially reaching or exceeding threshold `T` with only one real key.
6. If `2 * w_A >= T`, `ValidateMultiSign` returns success (`dataOne()`), authorizing an operation that should have required cooperation from additional distinct signers. [4](#0-3)

    public ECDSASignature toCanonicalised() {
      if (s.compareTo(HALF_CURVE_ORDER) > 0) {
        // The order of the curve is the number of valid points that
        // exist on that curve. If S is in the upper
        // half of the number of valid points, then bring it back to
        // the lower half. Otherwise, imagine that
        //    N = 10
        //    s = 8, so (-8 % 10 == 2) thus both (r, 8) and (r, 2)
        // are valid solutions.
        //    10 - 8 == 2, giving us always the latter solution,
        // which is canonical.
        return new ECDSASignature(r, CURVE.getN().subtract(s));
      } else {
        return this;
      }
    }
