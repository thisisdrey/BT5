### Title
Panic-on-any-error in `PohRecorder::record()` result handling crashes the entire validator instead of treating `MaxHeightReached` as a benign, retryable condition — ([File: poh/src/poh_service.rs])

### Summary
`PohRecorder::record()` can legitimately return `PohRecorderError::MaxHeightReached` (a normal, expected, retryable condition that banking-stage code elsewhere treats gracefully) as well as other error variants. In `poh/src/poh_service.rs`, both call sites that consume this result treat every `Err` variant identically by unconditionally panicking the process, rather than special-casing the benign/expected error the way the rest of the codebase does.

### Finding Description
`PohRecorder::record()` returns `Err(PohRecorderError::MaxHeightReached)` whenever there is no working bank, or the working bank's id doesn't match the record's `bank_id` [1](#0-0) . This is treated as a normal, expected, retryable error elsewhere in banking stage code — e.g. `record_transactions()` explicitly maps sender-side failures to `PohRecorderError::MaxHeightReached` and callers such as `execute_and_commit_transactions_locked`/`process_and_record_transactions` handle it by returning the transaction for retry rather than crashing [2](#0-1) [3](#0-2) .

However, inside `poh_service.rs`, the code that actually calls `PohRecorder::record()` on the receiving side does not distinguish `MaxHeightReached` (or any other error) from a truly fatal condition — it matches only `Ok`, and any `Err` unconditionally panics the whole process:
```
Err(err) => {
    panic!("PohRecorder::record failed: {err:?}");
}
```
This appears identically in `read_record_receiver_and_process` and in `record_or_hash` [4](#0-3) [5](#0-4) .

The correctness of *not* hitting this panic in normal operation depends entirely on the lock-free `RecordSender`/`RecordReceiver` protocol in `record_channels.rs` correctly guaranteeing that any record admitted into the channel is for the currently active, non-exhausted working bank, via atomic CAS on a packed `bank_id`/`allowed_insertions` word [6](#0-5) . The module's own shuttle tests acknowledge this is a fragile invariant and explicitly document the exact failure mode: "If receiver/sender interaction is buggy there is a race where the receiver can receive a record after shutdown is called. This can cause PoH to panic because it may receive a record for a bank_id that has already been completed." [7](#0-6) 

This is structurally the same bug class as the GMX finding: a specific, plausible error condition (`MaxHeightReached`, analogous to the negative-price revert) is not distinguished from a truly unexpected/unrecoverable error and is instead treated as fatal — except here the consequence is not merely "cancel one order" but an unconditional `panic!()` that halts the entire validator process, which is strictly worse.

### Impact Explanation
If the `record_channels` bank-id/capacity invariant is ever violated (a race, an off-by-one in slot/tick bookkeeping, or any other bug that lets a stale/mismatched record reach `PohRecorder::record()` after the working bank has advanced), the leader's PoH service thread panics and crashes the validator process, rather than gracefully treating `MaxHeightReached` as retryable like the rest of the transaction-processing pipeline does. This is a full node crash, not a bounded, per-transaction failure — a strictly more severe outcome than the referenced report's "orders get canceled."

### Likelihood Explanation
The `record_channels` synchronization is intricate lock-free atomic-CAS bookkeeping specifically built (and shuttle-tested) to prevent exactly this race, so triggering it in the current code requires a latent concurrency bug rather than a straightforward external input. This keeps the likelihood lower than the original finding (which was reachable by naturally occurring negative asset prices), but the code path and blast radius (leader crash vs. one canceled order) are directly analogous and worth flagging: the error-handling design pattern of "assume error X can't happen so panic on any Err" is the same root-cause pattern the Sherlock report calls out.

### Recommendation
In `poh_service.rs`, explicitly match on `PohRecorderError::MaxHeightReached` (and any other error already known to be a legitimate, non-corruption condition) and handle it the same way the rest of the pipeline does — log/drop or retry without panicking — reserving `panic!` only for conditions that genuinely indicate unrecoverable state corruption (e.g., unexpected `SendError` types that indicate the channel itself is broken).

### Proof of Concept
Not independently reproduced; based on static analysis of the call sites and the codebase's own acknowledgment (in `record_channels.rs` shuttle tests) that a receiver/sender race "can cause PoH to panic" if the bank-id/capacity invariant is violated [7](#0-6) , combined with the unconditional `panic!` on any `Err` from `PohRecorder::record()` in `poh_service.rs` [8](#0-7) .
