### Title
Unverified `RelayFromAddr` Allows Certificate-Identity Impersonation in `relayManager.handleCreateRelayRequest()` - (File: relay_manager.go)

### Summary
`relayManager.handleCreateRelayRequest()` accepts the `RelayFromAddr` field from an incoming `NebulaControl` message and uses it directly as the claimed VPN identity of the sending peer, without ever verifying that this address is actually one of the addresses bound to the sender's certificate (`h.vpnAddrs`). This mirrors the `DaosLocker::collect(address dao)` bug: an authenticated caller supplies an arbitrary "identity" parameter, and the code trusts it instead of deriving the identity from the verified credential of the caller (the certificate-bound `h.vpnAddrs`, analogous to `msg.sender`).

### Finding Description
`handleCreateRelayRequest` is reached from `HandleControlMsg`, which is invoked for any properly-decrypted `Control` message from an already-handshaked (but otherwise arbitrary) peer `h`: [1](#0-0) 

Inside `handleCreateRelayRequest`, the "from" address is taken straight from the attacker-controlled `m.RelayFromAddr`/`m.OldRelayFromAddr` field: [2](#0-1) 

When the current host is the target (`f.myVpnAddrsTable.Contains(target)`), that unverified `from` value is used to key relay state and to register a new Relay entry associating `h` (the actual, certificate-authenticated peer) with the claimed identity `from`: [3](#0-2) 

Nowhere in this path is `from` checked against `h.GetCert().Certificate.Networks()` / `h.vpnAddrs` — the set of addresses the sender is actually authorized (by its CA-signed certificate) to claim. Any peer that has completed a legitimate handshake with a valid certificate for VPN address `X` can send a `CreateRelayRequest` claiming `RelayFromAddr = Y` for an arbitrary victim address `Y`, and the target will create/overwrite hostmap relay state (`AddRelay`, `h.relayState`) binding `h` as the relay endpoint for `Y`, exactly as `DaosLocker.collect()` trusted an attacker-supplied `dao` address without checking it against the caller's real identity.

### Impact Explanation
This allows a certificate-holding but otherwise unrelated peer to poison the target's relay hostmap state for a VPN address it does not own, by registering itself as the terminal relay contact for that address. This can be used to hijack or disrupt legitimate relay establishment for another host (denial-of-service / relay-state poisoning), consume scarce relay index slots (`hm.Relays`) under a victim's identity, and cause the target to send `CreateRelayResponse` control traffic that references a victim's VPN address to the attacker's tunnel — all without the attacker ever proving ownership of that address via its certificate. This falls squarely in the "remote state poisoning" / "hostmap trust" impact category, analogous to the fee-theft impact of trusting an unverified `dao` identity.

### Likelihood Explanation
Any peer that can complete a normal Noise handshake with a valid CA-signed certificate (i.e., any legitimate but non-privileged network member, or, in multi-tenant/interop scenarios, anyone able to obtain a cert from the same CA) can trigger this by sending a single crafted `CreateRelayRequest` control message with an arbitrary `RelayFromAddr`. No additional privilege beyond an authenticated tunnel to the target is required, making this straightforward to reach.

### Recommendation
In `handleCreateRelayRequest`, derive the relay-from identity from the sender's verified certificate (`h.vpnAddrs`/`h.GetCert().Certificate.Networks()`) rather than trusting the `RelayFromAddr`/`OldRelayFromAddr` field taken from the message body. If the message field is retained for compatibility, validate that it matches one of the addresses present in `h`'s CA-verified certificate before using it to create or update relay state, mirroring the recommendation to use `msg.sender` instead of an unchecked input parameter.

### Proof of Concept
1. Attacker completes a legitimate Nebula handshake with the target using its own valid certificate for VPN address `X`.
2. Attacker sends a `Control` message of type `NebulaControl_CreateRelayRequest` with `RelayFromAddr = Y` (a victim's VPN address it does not hold a certificate for) and `RelayToAddr` set to the target's own address.
3. `relayManager.HandleControlMsg` → `handleCreateRelayRequest` runs the `f.myVpnAddrsTable.Contains(target)` branch, calls `AddRelay(rm.l, h, f.hostMap, from, ...)` with `from = Y`, creating relay state that associates the attacker's hostinfo `h` with victim `Y`'s address, and replies to the attacker with a `CreateRelayResponse` referencing `Y` — all without any check that `h` is certified for `Y`. func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}
}

	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}
