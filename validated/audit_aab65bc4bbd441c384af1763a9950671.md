### Title
Front-running dust `DepositToken` transfers fill the victim's collateral list, denying their deposits, transfers and liquidations - (File: contracts/DepositToken.sol)

### Summary
Each `DepositToken` mint or transfer registers the token in `Pool.depositTokensOf[account]` via `pool.addToDepositTokensOfAccount`, and `Pool` enforces a hard `MAX_TOKENS_PER_USER` cap on that list. Because `DepositToken.transfer`/`transferFrom` are permissionless and only require the sender to have *unlocked* balance, an unprivileged attacker can deposit dust into every collateral asset and send 1 wei of each `msdTOKEN` to a victim, filling the victim's list to the cap. Every subsequent operation that would add a new collateral type to that account — their own `deposit` into a new asset, an incoming `transfer`, or a liquidation `seize` crediting a new collateral — reverts.

### Finding Description
`DepositToken._transfer` adds the token to the recipient's collateral set on first receipt:

```solidity
// contracts/DepositToken.sol:517-520
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
```

The same registration happens on first-time minting during `deposit` (contracts/DepositToken.sol:486-488). On the `Pool` side, `addToDepositTokensOfAccount` reverts once `depositTokensOf[account]` reaches `MAX_TOKENS_PER_USER` (the constant and the account-list logic live in `contracts/Pool.sol`, backed by `MappedEnumerableSet` in `contracts/storage/PoolStorage.sol`).

This is structurally identical to the Vader `LinearVesting.vestFor` finding: a "first-write wins" per-account record that a griefer can front-run to deny the victim's legitimate first interaction. Here the griefer front-runs (or precedes) the victim's deposit into collateral X by filling the victim's `depositTokensOf` list with dust `msdTOKEN` transfers of all other collateral types. The victim's `deposit(amount, victim)` on `DepositToken` then reverts inside `_mint` → `addToDepositTokensOfAccount`.

Modifiers do not stop the dust seeding: `transfer` only checks `_revertIfLocked(_msgSender, amount_)` (the *sender's* health, which is trivially satisfied for 1 wei), and `deposit` is open to any `onBehalfOf_`. `nonReentrant`, pause flags, and `SynthContext`/`Operator.execute` paths are all irrelevant to this path. Note the debt side is *not* reachable the same way — `DebtToken` minting is gated by `onlyPool`/`onlyIfCanMint`, so only the deposit-token list is attacker-fillable.

### Impact Explanation
Temporary denial of deposits and freezing of the victim's position dynamics: the victim cannot onboard new collateral types, cannot receive `msdTOKEN` transfers of new types, and liquidations crediting them a new collateral type via `seize` revert (Pool calls `DepositToken.seize`, which routes through the same `_transfer`). Recovery requires the victim to first transfer out a dust token to free a slot — forced, non-obvious remediation comparable in impact to the original "vest denied" finding.

### Likelihood Explanation
Requires only unprivileged calls (`deposit` dust + `transfer`) and scales to all users of a pool; the cost is bounded by dust deposits across the pool's collateral assets. Win condition is merely winning transaction ordering against a victim's first deposit of a given collateral — a realistic mempool front-run.

### Recommendation
Enforce `MAX_TOKENS_PER_USER` only on economically meaningful balances (e.g., skip or allow-set-overflow for balances below a dust threshold), add an opt-in toggle for receiving tokens, or make `addToDepositTokensOfAccount` non-reverting for unsolicited dust (permitting the position to exceed the cap via external transfers while keeping the cap on user-initiated deposits).

### Proof of Concept
Hardhat fork, any deployed pool with ≥2 active `DepositToken`s:

```ts
// attacker
for (const dt of allDepositTokens) {
  await underlying.connect(attacker).approve(dt.address, DUST);
  await dt.connect(attacker).deposit(DUST, attacker.address);     // mint dust
  await dt.connect(attacker).transfer(victim.address, 1);         // fill victim's list
}
// victim's list now == MAX_TOKENS_PER_USER
// victim
await dt.connect(victim).deposit(amount, victim.address);         // reverts on new collateral
await dt.connect(attacker).transfer(victim.address, 1);           // reverts
await pool.liquidate(...crediting new collateral...);             // seize() reverts
```

Note: exact line numbers for `MAX_TOKENS_PER_USER` / `addToDepositTokensOfAccount` in `contracts/Pool.sol` could not be retrieved within the tool-call budget; the constant and function are confirmed present there. The mechanism (first-receipt list insertion on mint/transfer/seize) is fully verified in `DepositToken.sol:486-488, 517-525, 343-345`.
