Found the closest analog: `calc-liq-factor-exp` in the market contracts performs an integer exponentiation via **sequential/chained integer division** (dividing before the final operation), the same root-cause pattern as the reported `boostPrice` bug (dividing a squared ratio before the final scaling division, losing precision when the intermediate ratio floors to a small integer).

### Title
Precision loss / underflow in `calc-liq-factor-exp` graduated liquidation curve due to chained integer division - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`calc-liq-factor-exp` computes `liq-factor^alpha` for the graduated liquidation curve using integer division of the exponent (`exp / BPS`) both as a power argument and, critically, inside a subtraction `(- (/ exp BPS) u1)` used as another exponent, and then performs a single final division of two `pow` results. When `exp` is between `BPS` and `2*BPS` (i.e., alpha between 1.0 and 2.0, expressed in BPS units), `(/ exp BPS)` floors to `1`, making `(- (/ exp BPS) u1)` evaluate to `0`, so the denominator `(pow BPS 0)` becomes `1`. Additionally, `factor` (a BPS-scaled fraction ≤ `10000`) raised to an integer power that has already been floored discards the fractional part of `alpha` entirely, causing large jumps/precision loss in the effective exponent applied — an integer-truncation analog to the reported bug where an intermediate integer division of a ratio close to the boundary rounds to a degenerate value (0 or 1) before it's used in further arithmetic. [1](#0-0) 

### Finding Description
The function:
```
(define-private (calc-liq-factor-exp (factor uint) (exp uint))
  (if (is-eq exp BPS) 
    factor
    (if (> exp BPS) 
        (/ (pow factor (/ exp BPS)) (pow BPS (- (/ exp BPS) u1)))
        (sqrti (* factor BPS))))) ;; assume factor^0.5
```
uses `exp / BPS` (integer division) to derive an integer exponent from a BPS-scaled fractional curve exponent (`curve-exponent`, configured by governance for graduated liquidation, per `calc-liquidation-params`). [2](#0-1) 

Any `curve-exponent` strictly between `BPS` (1.0) and `2*BPS` (2.0) — e.g. `1.5` represented as `15000` — floors `(/ exp BPS)` to `1`. This makes the numerator `(pow factor 1) = factor` and the denominator `(pow BPS (- 1 1)) = (pow BPS 0) = 1`, so the whole graduated-curve computation silently degenerates to `factor` itself (i.e., a linear liquidation factor), discarding the fractional exponent entirely — the same class of bug as the reported issue: an integer division performed on a ratio/exponent close to an integer boundary rounds away meaningful precision before being consumed by the rest of the formula, producing a materially wrong final result rather than a small rounding error.

This directly affects `calc-liquidation-params`, which is called from the public/permissionless `liquidate` entry point in the market contract to compute `liq-pct-scaled` and downstream `liq-penalty` and `max-debt-usd` for every liquidation. [3](#0-2) 

### Impact Explanation
Because `liq-pct-scaled` feeds directly into `calc-liq-factor-bound` (liquidation penalty) and `calc-liq-debt-repay` (max debt liquidatable), an incorrect exponent computation changes how much of a position can be liquidated and at what penalty for any borrower whose position falls in the graduated liquidation LTV band. If the configured curve exponent lands in the affected fractional range, liquidations execute using a wrong (linear rather than intended curved) liquidation percentage/penalty, causing either under-liquidation (protocol insolvency risk if bad debt isn't sufficiently covered) or over-penalization of borrowers (temporary freezing/incorrect seizure of collateral) — this falls into the in-scope "protocol insolvency" / "temporary freezing of funds" impact classes, since liquidation math directly determines fund flows for every position that becomes liquidatable.

### Likelihood Explanation
Likelihood depends entirely on the DAO-configured `curve-exponent` value stored per-market. If the DAO sets an exponent with a fractional BPS value between `10000` and `20000` (e.g. 1.5x), every liquidation that reaches the graduated (partial) LTV zone silently uses the wrong curve. This is a deterministic, reproducible computational bug (not requiring any attacker action) triggered purely by normal `liquidate()` calls once a qualifying exponent is configured — a plausible, not merely theoretical, configuration since exponents like 1.5 are natural design choices for liquidation curves.

### Recommendation
Replace integer-truncating division of the exponent with a fixed-point power implementation (e.g., `pow-fixed(factor_bps, exp_bps, BPS)` that internally uses `mul-div-down`/binary exponentiation on the BPS-scaled fraction without prematurely flooring `exp/BPS`), or restrict `curve-exponent` to whole multiples of `BPS` and validate this constraint on write, and add a specific unit test set covering `exp` values strictly between `BPS` and `2*BPS` to confirm the curve behaves as intended rather than collapsing to the linear factor.

### Proof of Concept
1. Governance/DAO sets a market's `curve-exponent = 15000` (i.e., alpha = 1.5) via the liquidation parameter setter that feeds `calc-liquidation-params`.
2. A borrower's LTV enters the partial-liquidation band such that `calc-liq-factor` returns, e.g., `factor = 6000` (60%, in BPS).
3. `calc-liq-factor-exp(6000, 15000)`:
   - `exp (15000) > BPS (10000)` → takes the `>` branch.
   - `(/ exp BPS) = (/ 15000 10000) = 1` (floor).
   - Numerator: `(pow 6000 1) = 6000`.
   - Denominator: `(pow BPS (- 1 1)) = (pow 10000 0) = 1`.
   - Result: `6000 / 1 = 6000` — identical to the *uncurved, linear* factor, even though the intended computation was `factor^1.5` (which should be smaller than `factor` since `factor < BPS`).
4. Any liquidator calling `liquidate()` on this position receives a materially different `liq-pct-scaled`/`liq-penalty`/`max-debt-usd` than the curve was designed to produce, exactly mirroring the reported bug's pattern of an intermediate division rounding to a degenerate integer and corrupting the final on-chain result used by a public entry point. [4](#0-3)

  (if (is-eq exp BPS) 
    factor
    (if (> exp BPS) 
        (/ (pow factor (/ exp BPS)) (pow BPS (- (/ exp BPS) u1)))

;; Scale penalty between min and max using liquidation factor
;; liq-penalty = liq-penalty-min + (liq-factor * (liq-penalty-max - liq-penalty-min) / BPS)
;; Capped at bound-max to handle cases where liq-factor > BPS
(define-private (calc-liq-factor-bound (liq-factor uint) (bound-min uint) (bound-max uint))
  (min bound-max (+ bound-min (mul-bps-down liq-factor (- bound-max bound-min)))))

;; Calculate debt to repay based on liquidation factor
;; debt-repay = liq-factor * debt / BPS
(define-private (calc-liq-debt-repay (debt uint) (liq-factor uint)) 
  (mul-bps-down liq-factor debt))

;; Calculate collateral to seize (includes liquidator bonus)
;; collateral-repay = debt-repay * (BPS + liq-penalty) / BPS
(define-private (calc-liq-collateral-repay (debt-repay uint) (liq-penalty uint)) 
  (mul-bps-down debt-repay (+ BPS liq-penalty)))

;; Calculate actual debt repayment when collateral is capped
;; debt-repay-real = (collateral-amount-usd * BPS) / (BPS + liq-penalty)
(define-private (calc-liq-debt-repay-real (collateral-amount-usd uint) (liq-penalty uint)) 
  (div-bps-down collateral-amount-usd (+ BPS liq-penalty)))

;; Graduated liquidation parameter calculation
;; Combines the 4-step liquidation factor calculation into a single helper

  (ltv-liq-full uint)

  (liq-penalty-max uint)

      liq-penalty: liq-penalty,
