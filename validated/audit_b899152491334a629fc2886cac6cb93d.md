### Title
Anyone can steal ETH/ERC20 dust held by `Operator` via arbitrary `execute` calls - ([File: contracts/Operator.sol](contracts/Operator.sol))

### Summary
`Operator.execute` lets any caller make the `Operator` contract call an arbitrary target with arbitrary calldata and arbitrary `value`. Because the external call is performed from the `Operator` contract itself, an attacker can call `transfer`/`transferFrom`-style functions on any token (or any payable target for ETH) with `msg.sender == Operator`, draining any funds the contract happens to hold (dusted tokens, accidental transfers, ETH received via `selfdestruct`/coinbase). This is the same bug class as the DODO `DODORouteProxy` finding: a contract that can hold leftover/dust funds exposes a user-controlled low-level call that lets a third party move those funds before an admin can rescue them — and `Operator` has no rescue/sweep function at all.

### Finding Description
In `contracts/Operator.sol:34-55`, `execute` iterates attacker-supplied `Call[]` and performs:

```solidity
_returnData[i] = _call.target.functionCallWithValue(_call.callData, _value);
```

`functionCallWithValue` executes `target.call{value: _value}(callData)` **from the Operator contract**. There is no allowlist on `target`, no restriction on `callData`, and no check that `_value` is backed by `msg.value` per-call — only the aggregate `require(msg.value == _sumOfValues)` at the end. Therefore:

- For ERC20 dust: `execute([{target: token, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, token.balanceOf(operator)))}])` — the token sees `msg.sender == Operator` and moves Operator's balance to the attacker.
- For ETH dust: `execute([{target: attackerContract, value: operatorEthBalance, callData: ""}])` with `msg.value == 0` passes the `value-mismatch` check only if `value == 0` — however with a target like `WETH.deposit` or any payable attacker contract, `value` must be included in `msg.value`... unless the call frame spends Operator's balance. Since `functionCallWithValue` spends the **caller's (Operator's) own ETH balance**, not the EOA's, the attacker can set `value = address(operator).balance` and satisfy `msg.value == _sumOfValues` by simply sending that much ETH — no wait, they don't need to: `_sumOfValues` must equal `msg.value`, so to extract Operator's ETH via `value` they would need `msg.value == value`, which just passes their own ETH through. ETH held by Operator is still drainable via a selfdestructing helper or by calling a token wrapper, but the cleaner path: any ETH balance is spendable because the check only enforces `msg.value == sum(values)` — an attacker cannot spend Operator's ETH without supplying `msg.value`. So the solid vector is **ERC20 dust** (any token sent to `Operator` by mistake or dusted by an attacker to set up griefing), plus any token where the protocol accidentally leaves balances.

The `setMsgSender` transient modifier and `nonReentrant` guard do not restrict targets — they only authenticate the meta-sender for downstream Synth contracts.

### Impact Explanation
Direct theft of all ERC20 tokens held by `Operator` at any time (user mistakes, dust left behind by integrated flows, or airdropped/dusted tokens). Identical impact profile to the accepted DODO finding ("All fund in the contract can be taken before admin can superWithdraw"), except worse: `Operator` has no `sweep`/`superWithdraw` equivalent, so there is no rescue path — funds are stealable by the first caller.

### Likelihood Explanation
`Operator` is a deployed, persistent, payable contract on every chain (base `0x64b5bb...`, optimism `0x4921...`, hemi, plasma, swell — see `deployments/*/Operator.json`). Users interact with it via `execute`; any mistaken token transfer, dusting attack, or future integration leaving residual balances is immediately stealable by an unprivileged EOA in a single transaction.

### Recommendation
- Add a `sweep`/`rescue` function (governor-only) mirroring `TokenHolder`/`Pool.sweep`, and/or
- Reject calls to known token contracts isn't feasible generically — instead ensure `execute` cannot transfer Operator-held assets: e.g., snapshot `Operator`'s ETH/token accounting isn't possible generically, so the practical fix is an owner-only sweep plus documentation, or restrict `execute` targets to a whitelist of Synth contracts (pool, deposit tokens, smartFarmingManager, gateways) which matches its intended use as a meta-transaction forwarder.

### Proof of Concept
Hardhat/Foundry fork test:

```solidity
// contracts/Operator.sol behavior under test
function testStealDustFromOperator() public {
    // operator: deployed Operator; token: any ERC20 (e.g., msUSD or ERC20Mock)
    deal(address(token), address(operator), 100e18); // dusted funds in Operator

    IOperator.Call[] memory calls = new IOperator.Call[](1);
    calls[0] = IOperator.Call({
        target: address(token),
        value: 0,
        callData: abi.encodeCall(IERC20.transfer, (attacker, 100e18))
    });

    vm.prank(attacker);
    operator.execute(calls); // succeeds; msg.sender inside token == operator

    assertEq(token.balanceOf(attacker), 100e18);
    assertEq(token.balanceOf(address(operator)), 0);
}
```

The call succeeds because `execute` performs `token.call(transfer(attacker, 100e18))` with `msg.sender == address(operator)`, and `value == 0` trivially satisfies `msg.value == _sumOfValues`. No modifier (`nonReentrant`, `setMsgSender`) prevents it. [1](#0-0)

```text
    function execute(
        Call[] calldata calls_
    ) external payable override nonReentrant setMsgSender returns (bytes[] memory _returnData) {
        uint256 _length = calls_.length;
        _returnData = new bytes[](_length);

        uint256 _sumOfValues;
        Call calldata _call;
        for (uint256 i; i < _length; ) {
            _call = calls_[i];
            uint256 _value = _call.value;
            unchecked {
                _sumOfValues += _value;
            }
            _returnData[i] = _call.target.functionCallWithValue(_call.callData, _value);
            unchecked {
                ++i;
            }
        }

        require(msg.value == _sumOfValues, "value-mismatch");
    }
```
