### Title
Missing bounds validation before buffer slice in TVM precompiled-contract signature parsing leads to attacker-controlled out-of-bounds read/DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The CVE-2017-9348 bug class is "a dissector reads past the end of a buffer because a size value taken from attacker-controlled input is not validated before being used to slice the buffer." The same pattern exists in java-tron's TVM precompiled-contract helpers `extractBytes`, `extractSigArray`, `extractBytesArray`, and `extractBytes32Array` in `PrecompiledContracts.java`, which are used to parse the raw calldata `byte[]` passed to the `ValidateMultiSign`/`BatchValidateSign` precompiles. Offsets and lengths are read directly from attacker-supplied calldata words and used to compute slice boundaries with no validation that the resulting range lies inside the actual data buffer.

### Finding Description
`extractBytes` performs a raw `Arrays.copyOfRange` using an offset and length that are never checked against the source array bounds: [1](#0-0) 

That offset is produced in `extractSigArray` by reading a word directly from `data` (attacker-controlled calldata) and dividing/multiplying it into a byte offset, with only a check on the *first* offset (`offset > words.length - 1`) — none of the intermediate `bytesOffset` values derived from `words[offset + i + 1]` are validated against `data.length`: [2](#0-1) 

The related helper `extractBytesArray`, used for ECDSA/argument decoding elsewhere in the same file, has the identical pattern: `len`, `bytesOffset`, and `bytesLen` are all taken straight from calldata words via `intValueSafe()` with no upper/lower bound check before being fed into `extractBytes`: [3](#0-2) 

Because `bytesOffset` is derived from an attacker-chosen 256-bit word (`intValueSafe()` clamps to `int` range but does not reject negative-producing arithmetic after the `* WORD_SIZE` multiplication), a crafted calldata value can make the computed `offset` in `extractBytes` negative or make `offset + len` overflow `int`. `Arrays.copyOfRange(data, offset, offset + len)` throws `ArrayIndexOutOfBoundsException` when `fromIndex < 0` or `fromIndex > original.length`; when `toIndex > original.length` it silently zero-pads instead of throwing. This mirrors the Wireshark DOF dissector bug: a length/offset value taken from untrusted input is used to index into a buffer without validating it is within range, with the crash/exception path being the concrete divergence from intended zero-padding behavior.

### Impact Explanation
This is reachable by any unprivileged account that calls the `BatchValidateSign` or `ValidateMultiSign` precompiled contracts (fixed TVM precompile addresses) with a crafted `data` payload — i.e., any contract-calling or transaction-broadcasting party, with no special privilege required. A crafted offset word can drive `extractBytes`/`extractSigArray`/`extractBytesArray` into throwing an uncaught `ArrayIndexOutOfBoundsException` (or, for `extractBytes32Array`/`extractBytesArray`, into allocating a `byte[len][]` array with an attacker-controlled `len` up to `Integer.MAX_VALUE`, which is a resource-exhaustion vector). Depending on how deep in the VM dispatch stack this exception is thrown and whether it is uniformly caught as `RuntimeException` by the operation-execution loop, this manifests at minimum as a way to reliably fail/burn energy on a specific transaction, and in the worst case (if any calling context doesn't wrap it, e.g. constant/view call paths through `Wallet`/`TronJsonRpcImpl` that invoke precompiled contracts directly for `triggerConstantContract`) as an uncaught exception that can crash node request-handling threads for that call path.

### Likelihood Explanation
High likelihood of triggering the faulty code path: the precompiled contracts are called with fully attacker-controlled `data`, requiring only a normal signed transaction or a constant/eth_call-style RPC request invoking the precompile address with crafted calldata — no compromised keys, no special permissions, and no race conditions needed.

### Recommendation
Add explicit bounds validation in `extractBytes`, `extractSigArray`, `extractBytesArray`, and `extractBytes32Array` before performing any slicing: verify `0 <= offset` and `offset + len <= data.length` (using overflow-safe arithmetic, e.g. `long` intermediate math) before calling `Arrays.copyOfRange`/`System.arraycopy`, and cap `len` derived from calldata words to a sane maximum before allocating `new byte[len][]`. Return an empty/zero result (or throw a `BytecodeExecutionException` that is deterministically handled by the VM's existing `RuntimeException` catch path) instead of letting `ArrayIndexOutOfBoundsException`/`OutOfMemoryError` propagate.

### Proof of Concept
1. Build calldata for `BatchValidateSign`/`ValidateMultiSign` such that the "signature count" word at `words[offset]` is a small positive integer (so the length-check `offset > words.length - 1` passes).
2. Set the corresponding per-signature offset word `words[offset + i + 1]` to a large value (e.g., close to `Integer.MAX_VALUE`) so that `bytesOffset = words[...].intValueSafe() / WORD_SIZE` combined with `(bytesOffset + offset + 2) * WORD_SIZE` in `extractSigArray`/`extractBytesArray` overflows `int` and becomes negative, or otherwise lands far outside `data.length`.
3. Submit this calldata via a `TriggerSmartContract` transaction (or a `triggerconstantcontract` HTTP/gRPC call through `Wallet`) targeting the precompile address.
4. Observe `extractBytes`'s `Arrays.copyOfRange(data, offset, offset+len)` throw `ArrayIndexOutOfBoundsException` from a negative `offset`, confirming the missing bounds check identified above.

Note: I was unable to fully trace, within the available tool budget, whether every call path into these precompiles (in particular the constant-call/RPC query path through `Wallet`/`TronJsonRpcImpl`) wraps this exception in a `try/catch` before it reaches request-handling code, versus the normal transaction-execution path which does catch `RuntimeException` in the VM's operation loop. This affects whether the ultimate impact is "transaction fails gracefully" (Medium) or "uncaught exception on a query path" (High); the root-cause missing-bounds-check itself is confirmed directly in the cited code.
