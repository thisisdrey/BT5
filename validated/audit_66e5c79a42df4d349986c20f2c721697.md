### Title
Handshake Retransmit Replay Enables Remote-Address Hijack via `preferred_ranges` - (File: `handshake_manager.go`)

### Summary
The bug class in the report is "a validated authorization artifact (a signature) is not bound to the requester, so an attacker can capture and resubmit it from a different origin before the legitimate flow completes, causing state to be applied on the attacker's behalf." In Nebula, the closest reachable analog (no CA-signed certificate required, purely a network-level replay) is the stage-1 handshake "already seen" path: a certificate-validated handshake packet is deduplicated by raw byte comparison only, and the *source address of the retransmit* — not any freshly-authenticated data — is trusted to update the peer's routable remote address when it falls in `preferred_ranges`.

### Finding Description
When a duplicate stage-0 (`msg1`) handshake packet arrives for an already-established `HostInfo`, `CheckAndComplete` matches it purely by byte-equality against the previously stored packet: [1](#0-0) 

On this match it returns `ErrAlreadySeen`, and `handleCheckAndCompleteError` reacts by calling `existing.SetRemoteIfPreferred(f.hostMap, via)` using the `via` of *this* packet, i.e. whatever UDP source address delivered the duplicate bytes: [2](#0-1) 

`SetRemoteIfPreferred` then unconditionally rewrites the HostInfo's routable remote address if the new source falls within `preferred_ranges` (or if there is currently no remote at all): [3](#0-2) 

The byte-for-byte match against `HandshakePacket[handshakePacketStage0]` proves only that the *content* of msg1 was authored by the legitimate peer (it was cert/signature verified once, when the original packet was first processed). It proves nothing about who is transmitting this particular UDP datagram right now. Because UDP source addresses are attacker-controlled and unauthenticated at this layer, and the plaintext-header/ciphertext handshake bytes travel in the clear on the wire, any attacker who observes (or is handed) one legitimate `msg1` capture can resend those exact same bytes from a spoofed or attacker-owned source address that happens to lie inside `preferred_ranges`. This is structurally the same flaw as the report: a validated artifact (the cert-checked handshake message) is reused by a third party without any binding (nonce/ownership check) to the party that is allowed to act on it, and the "front-run" delivery (attacker's copy arriving and being processed) causes state (the routable remote address) to be updated in the attacker's favor instead of the legitimate initiator's.

### Impact Explanation
`preferred_ranges` is a standard, commonly-deployed feature (e.g. to prefer LAN/internal addresses over WAN paths). Once triggered, `SetRemoteIfPreferred` becomes the responder's chosen "hot path" destination for future outgoing traffic to that peer (`HostInfo.remote`), so an attacker who can reach the responder from an address inside its `preferred_ranges` can redirect an already-established tunnel's outbound path toward themselves by replaying a captured, byte-identical handshake packet — a concrete remote state poisoning primitive that can be used to intercept traffic intended for the legitimate peer, without needing any certificate signed by the trusted CA.

### Likelihood Explanation
Requires the attacker to (a) obtain one copy of a legitimate `msg1` handshake packet (observable on the wire, since msg1 is not confidential to third parties — only the noise payload is es-encrypted, and the raw bytes are exactly what gets byte-compared) and (b) be able to deliver identical bytes from a source address within the victim's configured `preferred_ranges`. This is realistic in the deployment scenarios where `preferred_ranges` is used (shared/broadcast LAN segments, cloud VPC ranges) where source-address spoofing or co-location inside the preferred CIDR is plausible.

### Recommendation
Do not let an unauthenticated duplicate-packet delivery path (`ErrAlreadySeen`) drive `SetRemoteIfPreferred`. Bind the roam decision to something the current sender must prove, not just byte-equality of previously-validated content — e.g. require the duplicate to also produce a response the peer can decrypt/ack from the new path (as already happens for the "normal" roam path driven by real data-plane traffic), or gate `SetRemoteIfPreferred` here behind an additional freshness/challenge check so a mere capture-and-replay of the same handshake bytes from a new source cannot silently move the trusted remote.

### Proof of Concept
1. Victim (`me`) and peer (`them`) complete a normal IX handshake with `them` configured with `preferred_ranges` that includes a subnet the attacker can source packets from (e.g. `10.0.0.0/8`).
2. Attacker captures `me`'s stage-0 handshake packet (`msg1`) as it is sent to `them`'s current remote (analogous to `myControl.GetFromUDP` in `TestHandshakeRetransmitDuplicate`, `handshake_manager_test.go:52-62`).
3. Attacker resends the identical bytes to `them` with a spoofed/attacker source UDP address chosen from within `preferred_ranges`.
4. `them`'s `CheckAndComplete` matches the byte-identical packet against the existing `HostInfo`, returns `ErrAlreadySeen`; `handleCheckAndCompleteError` calls `existing.SetRemoteIfPreferred(f.hostMap, via)` with `via` pointing at the attacker's address.
5. Because the attacker's address is in `preferred_ranges`, `SetRemoteIfPreferred` treats it as a roaming event and rewrites `HostInfo.remote` to the attacker's address — `them`'s subsequent outbound encrypted traffic to `me` is now sent to the attacker-controlled endpoint. [4](#0-3) [5](#0-4)

// SetRemoteIfPreferred returns true if the remote was changed. The lastRoam
// time on the HostInfo will also be updated.
func (i *HostInfo) SetRemoteIfPreferred(hm *HostMap, via ViaSender) bool {
	if via.IsRelayed {
		return false
	}

	currentRemote := i.GetRemote()
	if !currentRemote.IsValid() {
		i.SetRemote(via.UdpAddr)
		return true
	}

	// NOTE: We do this loop here instead of calling `isPreferred` in
	// remote_list.go so that we only have to loop over preferredRanges once.
	newIsPreferred := false
	for _, l := range hm.GetPreferredRanges() {
		// return early if we are already on a preferred remote
		if l.Contains(currentRemote.Addr()) {
			return false
		}

		if l.Contains(via.UdpAddr.Addr()) {
			newIsPreferred = true
		}
	}

	if newIsPreferred {
		// Consider this a roaming event
		i.lastRoam = time.Now()
		i.lastRoamRemote = currentRemote

		i.SetRemote(via.UdpAddr)

		return true
	}

	return false
}
