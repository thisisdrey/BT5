### Title
Division by Zero (Uncaught `ArithmeticException`) in `EnergyProcessor.calculateGlobalEnergyLimit` via `assert` Instead of Real Guard - (File: `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java`)

### Summary
`EnergyProcessor.calculateGlobalEnergyLimit` relies on a Java `assert` statement to guard against a zero `totalEnergyWeight` before performing a `BigInteger` division. Since JVM assertions are disabled by default in production (no `-ea` flag), this guard is a no-op, and the method can reach `calculateGlobalLimitV1`, which divides by `totalEnergyWeight` with no zero-check, throwing an uncaught `ArithmeticException`.

### Finding Description
In `calculateGlobalEnergyLimit`: [1](#0-0) 

the zero-weight guard is only effective when `dynamicPropertiesStore.allowNewReward()` is `true`:
```java
if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
  return 0;
} else {
  assert totalEnergyWeight > 0;
}
if (hardenCalculation()) {
  return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
}
```
When `allowNewReward()` is `false`, the `else` branch executes `assert totalEnergyWeight > 0;`. Because assertions are disabled by default in production JVMs, this line performs no validation at runtime. Execution then falls through to `hardenCalculation()`, and if that flag is enabled, `calculateGlobalLimitV1` is invoked: [2](#0-1) 
```java
protected long calculateGlobalLimitV1(long frozeBalance,
    long totalLimit, long totalWeight) {
  long weight = frozeBalance / TRX_PRECISION;
  return BigInteger.valueOf(weight)
      .multiply(BigInteger.valueOf(totalLimit))
      .divide(BigInteger.valueOf(totalWeight))
      .longValueExact();
}
```
`BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException: BigInteger divide by zero`. This is functionally the same bug class described in the external report (unguarded division), except here the intended guard exists in source but is silently disabled at runtime because it is implemented with `assert` rather than an explicit conditional check.

The vulnerable path is reachable from ordinary contract execution: `EnergyProcessor.useEnergy` — invoked whenever a TVM contract consumes energy during transaction execution — calls `calculateGlobalEnergyLimit` unconditionally when the network has not yet enabled `supportUnfreezeDelay()`: [3](#0-2) 

so any signed transaction that triggers TVM energy accounting for an account with zero frozen-for-energy weight can hit this path once `allowHardenResourceCalculation` (hardenCalculation) is turned on but `allowNewReward` is not yet active (e.g. freshly bootstrapped chains/private networks, or transitional periods between hard-fork activations).

### Impact Explanation
An uncaught `ArithmeticException` thrown deep inside transaction/energy accounting during TVM execution is not caught by the surrounding energy-consumption logic in `EnergyProcessor`, and can propagate up through the actuator/VM execution path invoked during block application, causing transaction processing to fail unexpectedly or, depending on where the exception surfaces relative to try/catch boundaries in the calling actuator/`Manager`, halting normal block processing for the node. This matches the "node crash or halt" impact category.

### Likelihood Explanation
The trigger condition (`totalEnergyWeight == 0` while `allowNewReward()` is false and `hardenCalculation()` is true) requires a specific chain-configuration state — most likely on a freshly initialized private/test network before hard forks are fully activated, or during a transitional window where `allowHardenResourceCalculation` has been turned on ahead of `allowNewReward`. It is not trivially triggerable on current mainnet (where both flags are already active), which limits likelihood, but the underlying defect — a broken safety check that is silently disabled in production because it uses `assert` — is a genuine, concrete code correctness bug rather than a theoretical one.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` statement with an explicit runtime check (e.g., `if (totalEnergyWeight <= 0) { return 0; }`), independent of the `allowNewReward()` flag, so the zero/negative-weight case is always handled before any division is attempted, mirroring the existing explicit check already present in `calculateGlobalEnergyLimitV2` and in `BandwidthProcessor.calculateGlobalNetLimit`.

### Proof of Concept
1. Configure a chain (or use a test harness such as `CalculateGlobalLimitHardenTest`) with `allowNewReward = 0`, `supportUnfreezeDelay = 0`, and `allowHardenResourceCalculation = 1`.
2. Ensure `totalEnergyWeight` is `0` (e.g., no accounts have frozen balance for energy yet).
3. Submit any transaction that invokes `EnergyProcessor.useEnergy` (e.g., a smart contract call consuming energy) for an account whose `getAllFrozenBalanceForEnergy() >= TRX_PRECISION`.
4. `calculateGlobalEnergyLimit` reaches `calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, 0)`, and `BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException`, since assertions are disabled by default at runtime (`assert totalEnergyWeight > 0;` is a no-op).

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
