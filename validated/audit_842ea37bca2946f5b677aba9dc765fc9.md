### Title
Stale `PromiseYieldReceipt`/`PromiseYieldStatus`/`PromiseYieldTimeout` entries survive `DeleteAccount` and execute against a recreated account with a different owner - ([File: runtime/runtime/src/lib.rs, core/store/src/utils/mod.rs])

### Summary
`remove_account` (invoked by `action_delete_account`) deletes `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie entries for a deleted account, but never touches `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`/`DataIdToYieldId`, or the global `PromiseYieldTimeout` queue entry that references that account. If the account is recreated under the same name, the orphaned yield state is later resolved (automatically, via timeout) into an `apply_action_receipt` execution of actions chosen by the *old* account owner against the *new* account's current contract state.

### Finding Description
`promise_yield_create` stores a `PromiseYield` receipt keyed by `(receiver_id, data_id)` via `set_promise_yield_receipt` and enqueues a `PromiseYieldTimeout { account_id, data_id, expires_at }` entry in the global per-shard timeout queue (`runtime/runtime/src/function_call.rs:153-169`, `core/store/src/utils/mod.rs:181-198`). Both the receiver's `PromiseYieldReceipt`/`PromiseYieldStatus` keys (`core/primitives/src/trie_key.rs:244-247`, `561-566`) and the timeout queue entry are keyed by `account_id`/`data_id`, not by any account "generation" or nonce.

`remove_account` (`core/store/src/utils/mod.rs:504-575`), called from `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) on `DeleteAccount`, removes only `Account`, `ContractCode`, `AccessKey`/gas-key rows, and `ContractData`. It never scans or removes `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId` rows for that account, nor the global `PromiseYieldTimeout` queue entry. `action_delete_account`/`check_actor_permissions` (`runtime/runtime/src/actions.rs:761-776`) only check for zero locked stake; there is no check for pending yields.

An unprivileged attacker can:
1. Create account `A`, call `promise_yield_create` from `A`'s own contract execution, specifying a callback action (e.g. `FunctionCall(method_name, args)`) targeting `A` itself. This records the `data_id`/timeout the attacker already knows (they created it).
2. Send `DeleteAccount` for `A` before the yield times out. `remove_account` leaves the `PromiseYieldReceipt`/`PromiseYieldStatus`/`PromiseYieldTimeout` entries in the trie.
3. A third party (or the attacker) recreates account `A` (`CreateAccount`) and deploys a new contract exposing a method with the same name the attacker's stale receipt targets.
4. At `queue_entry.expires_at`, `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3104`) unconditionally checks `state_update.contains_key(&promise_yield_key)` for `(A, data_id)` — true, since it was never cleaned up — and synthesizes a `PromiseResume{data: None}` receipt for `A`, with no re-validation of account identity/ownership.
5. `process_receipt`'s `PromiseResume` branch (`runtime/runtime/src/lib.rs:1500-1568`) calls `get_promise_yield_receipt(state_update, account_id, data_id)`, finds the stale receipt, removes the bookkeeping keys, and calls `apply_action_receipt` on the stale `yield_receipt` — whose `receiver_id`/actions were fixed at creation time by the *old* account owner — against the *current* (new owner's) account and contract.

`check_account_existence` (`runtime/runtime/src/actions.rs:787-855`) only checks that account `A` exists at execution time (it does, since it was recreated) — it has no notion of "same account" vs "a different account that happens to have the same name," so the check passes trivially. This matches the invariant violation described: a data dependency (`data_id`) created by the old owner resolves into execution on a completely different, newly-controlled account state, entirely automatically (via timeout), without any action by the new owner.

### Impact Explanation
This is authorization escalation across accounts: the old account owner can force execution of an action (method call with attacker-chosen args, potentially with an attached deposit) against a contract deployed by a completely different, later owner of the same account name, without any consent or action from the new owner. Whether the callback in the stale receipt found a matching method on the new contract determines whether it silently no-ops (`MethodNotFound`) or actually executes attacker-chosen logic against the new owner's contract/storage — but the execution attempt itself, sourced entirely from stale state the new owner never created and cannot see or cancel, is the vulnerability. This falls under "authorization escalation across accounts or promises."

### Likelihood Explanation
- Fully attacker-controlled preconditions: the attacker creates the yield themselves (so they know `data_id`), then deletes their own account — no privileged access, leaked keys, or victim cooperation required.
- The only external dependency is that a third party later recreates the exact same account name and deploys a contract; this is a normal, permissionless operation (account names are recycled once deleted) and could even be self-orchestrated by the attacker in two steps if they later "sell"/hand off the account name, or simply demonstrated purely in a runtime/test-loop test without needing any third party at all.
- The exploit path is fully automatic via `resolve_promise_yield_timeouts`, requiring no interaction from the new owner's contract (unlike the resume-host-call path, which does require the new contract to call `promise_yield_resume` itself).
- Repeatable: any account can be used this way arbitrarily many times.

### Recommendation
When removing an account in `action_delete_account`/`remove_account`, also scan and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` entries for that `account_id` (similar to how access keys and contract data are scanned via prefix iteration), and/or invalidate/skip the corresponding `PromiseYieldTimeout` queue entries (e.g., by checking account existence/generation before honoring a stale yield in `process_receipt`'s `PromiseResume` branch and in `resolve_promise_yield_timeouts`). Alternatively, disallow `DeleteAccount` while the account still has any pending `PromiseYieldReceipt`, mirroring the existing zero-locked-stake precondition.

### Proof of Concept
Runtime integration test (extending patterns in `integration-tests/src/tests/runtime/test_yield_resume.rs` and `test-loop-tests/src/tests/yield_timeouts.rs`):
1. Deploy `rs_contract` to account `A`; call `call_promise` on `A` to invoke `promise_yield_create`, with the yielded callback action being `FunctionCall("victim_method", args, gas, deposit)` targeting `A`. Capture `data_id`.
2. In the next transaction, submit `DeleteAccount(beneficiary_id=other)` for `A` as the sole action from `A` itself (passes `check_actor_permissions` since `locked == 0`).
3. Submit `CreateAccount` + `DeployContract` for `A` with a new contract exposing `victim_method` that records a side effect (e.g., writes to contract storage / mutates balance) when called, distinct from the original attacker contract.
4. Advance blocks to `expires_at` (`yield_timeout_length_in_blocks`) without ever calling `promise_yield_resume`.
5. Assert: (a) `resolve_promise_yield_timeouts` still finds and processes the stale `PromiseYieldReceipt` for `(A, data_id)` (`assert_no_promise_yield_status_in_state` style check should fail/show consumption), and (b) the new contract's `victim_method` side effect (storage/balance mutation) is observed on account `A`, proving execution occurred against the recreated account without any action from its new deployer.
