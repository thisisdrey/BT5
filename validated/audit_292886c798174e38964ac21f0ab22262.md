### Title
Uninitialized `accountIndexOf` treated as index `0` instead of `INITIAL_INDEX` drains reward pool - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenDelta` reads `accountIndexOf[token_][account_]`, which is `0` for any account that has never had a rewards checkpoint on that token — an uninitialized storage read (the Solidity analog of CWE-908 uninitialized memory). A partial mitigation resets `0` to `INITIAL_INDEX` (1e18) only when the token index has already grown past `INITIAL_INDEX`. During the whole window where `tokenStates[token].index == INITIAL_INDEX` — which begins the moment the governor calls `updateTokenSpeed` and lasts until the accrued ratio first rounds to a non-zero wad — a holder with an uninitialized index gets `_deltaIndex = INITIAL_INDEX - 0 = 1e18`, crediting them `balanceOf(account)` reward tokens instantly. The public `claimRewards` then transfers up to the distributor's entire reward-token balance.

### Finding Description
In `RewardsDistributor.sol`, `_calculateTokenDelta` computes per-account reward delta as `balanceOf(account).wadMul(tokenIndex - accountIndex)`:

```solidity
// contracts/RewardsDistributor.sol:222-230
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

The guard only handles the case `_tokenIndex > INITIAL_INDEX`. When `_tokenIndex == INITIAL_INDEX` exactly, `_accountIndex` stays `0` and `_deltaIndex = 1e18`, so `_tokensDelta = balanceOf(account_)` — the full token balance is credited as claimable rewards.

The index is set to `INITIAL_INDEX` when a token is first added via `_updateTokenSpeed` (`contracts/RewardsDistributor.sol:298`). Afterwards, `_calculateTokenIndex` only advances the index by `_deltaTimestamps * _speed wadDiv _totalSupply` (`contracts/RewardsDistributor.sol:203-207`); for realistic speeds and supply this ratio rounds to `0` in wad terms for an extended period, so `index` remains exactly `INITIAL_INDEX`. The vulnerable window is therefore not just one block — it lasts until the first non-zero index increment.

Both `claimRewards` (`contracts/RewardsDistributor.sol:150-168`) and `updateBeforeMintOrBurn`/`updateBeforeTransfer` (`contracts/RewardsDistributor.sol:175-192`) reach `_updateTokensAccruedOf` → `_calculateTokenDelta` when `tokenStates[token_].index > 0`, which holds the moment the speed is set. `claimRewards` is permissionless and pays `tokensAccruedOf[account_]` to `account_` via `_transferRewardIfEnoughTokens` (`contracts/RewardsDistributor.sol:248-255`), capped only by the distributor's reward-token balance.

Attack path (all unprivileged):
1. Attacker deposits collateral through `DepositToken.deposit` before any reward speed exists (no index recorded since `tokenStates.index == 0` skips updates at line 176). A flash loan can supply the collateral.
2. Governor (normal protocol operation, not malicious) calls `updateTokenSpeed(msdX, speed)` → `tokenStates[msdX].index = INITIAL_INDEX`.
3. While `index == INITIAL_INDEX`, attacker calls `claimRewards(attacker, [msdX])`. `_updateTokensAccruedOf` credits `tokensAccruedOf[attacker] += attackerShareBalance` and `_transferRewardIfEnoughTokens` pays out, draining the distributor's reward-token balance up to the attacker's share balance.
4. Attacker withdraws the collateral via `DepositToken.withdraw`.

### Impact Explanation
Direct theft of unclaimed yield: the entire reward-token inventory of the `RewardsDistributor` can be drained by whichever account(s) with uninitialized indexes act inside the window. With flash-borrowed collateral the attacker can size `balanceOf` to cover the full contract balance in a single transaction. Even honest users' routine deposits/transfers during the window silently inflate their `tokensAccruedOf`, corrupting reward accounting for everyone.

### Likelihood Explanation
The trigger is a routine, expected governor action (`updateTokenSpeed`/`updateTokenSpeeds`), and the vulnerable window persists until `deltaTimestamps * speed / totalSupply` first reaches 1 wei of wad index — which can be many blocks for typical reward rates. No privileged malicious actor, oracle manipulation, or off-chain component is needed; the attacker only needs a pre-existing `DepositToken`/`DebtToken` balance and one public `claimRewards` call.

### Recommendation
In `_calculateTokenDelta`, treat `_accountIndex == 0` as `INITIAL_INDEX` unconditionally (whenever `_tokenIndex >= INITIAL_INDEX`), or set `accountIndexOf` to `INITIAL_INDEX` eagerly in `_updateTokenSpeed` for all future accounts by recording a "never initialized" sentinel. Corrected logic:

```solidity
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
```

Equivalently, subtract `INITIAL_INDEX` from the delta basis so an uninitialized account accrues `0`.

### Proof of Concept
Hardhat (fork) sketch:

```ts
// Fixture: pool, msdDAI DepositToken, RewardsDistributor funded with rewardToken (e.g., MET)
// 1) Attacker deposits BEFORE speed is set -> accountIndexOf stays 0
await dai.connect(attacker).approve(msdDAI.address, amount);
await msdDAI.connect(attacker).deposit(amount, attacker.address); // updateBeforeMintOrBurn no-ops (index == 0)

// 2) Governor enables rewards -> tokenStates[msdDAI].index = INITIAL_INDEX (1e18)
await rewardsDistributor.connect(governor).updateTokenSpeed(msdDAI.address, speed);

// 3) Before the index grows past 1e18 (same or later block while ratio rounds to 0),
//    attacker claims. _deltaIndex = 1e18 - 0 -> tokensDelta = share balance.
await rewardsDistributor.connect(attacker).claimRewards(attacker.address, [msdDAI.address]);

// rewardToken.balanceOf(attacker) == min(shareBalance, distributor reward balance)
```
