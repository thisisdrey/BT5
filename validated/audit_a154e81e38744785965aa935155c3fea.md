Audit Report

## Title
`EthereumSystemFrontend::add_tip` burns the user's tip asset before BridgeHub crediting is guaranteed, permanently locking funds in `LostTips` with no recovery path - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`EthereumSystemFrontend::add_tip` on AssetHub irreversibly swaps and burns the caller's tip asset via `swap_fee_asset_and_burn` → `swap_and_burn` → `burn_for_teleport` before any confirmation exists that the corresponding `EthereumSystemV2::add_tip` call on BridgeHub will succeed. If the referenced `nonce` (in `message_id`) has already been consumed by the time the XCM `Transact` lands on BridgeHub, the tip amount is only added to `LostTips`, a storage map with no withdrawal/recovery extrinsic anywhere in the codebase, resulting in a permanent, unbacked loss of the user's funds.

## Finding Description
The flow: `add_tip` (`bridges/snowbridge/pallets/system-frontend/src/lib.rs:261-273`) calls `swap_fee_asset_and_burn` (`:372-404`), which swaps the tip asset for Ether and unconditionally calls `burn_for_teleport::<T::AssetTransactor>` (`:313-314`) — destroying the asset on AssetHub — *before* sending the XCM `Transact` with `EthereumSystemCall::AddTip` to BridgeHub via `send_transact_call` (`:406-423`). [1](#0-0) [2](#0-1) 

On BridgeHub, `EthereumSystemV2::add_tip` (`bridges/snowbridge/pallets/system-v2/src/lib.rs:251-281`) dispatches to `InboundQueue::add_tip` or `OutboundQueue::add_tip`. If that call errors (e.g. nonce already consumed), the error is caught and only `LostTips::<T>::mutate(&sender, ...)` is bumped; the extrinsic still returns `Ok(())` and no compensating mint/credit occurs. [3](#0-2) 

`LostTips` is explicitly documented as a placeholder for a not-yet-implemented recovery mechanism: *"Capturing the lost tips here supports implementing a recovery method in the future."* [4](#0-3)  A repo-wide search confirms `LostTips` is only referenced in `system-v2/src/lib.rs`, its own test file, and the emulated integration test — there is no recovery/claim extrinsic implemented anywhere in this codebase. The inbound-queue's `add_tip` implementation explicitly returns `AddTipError::NonceConsumed` when the nonce has already been processed, confirming this failure path is real and reachable in normal, non-malicious operation (a relayer processing the nonce concurrently with the user's tip submission).

This matches the required invariant violation: the burn (custody/value conservation step) is not gated on successful settlement (the credit on BridgeHub), so value is destroyed without ever reaching the rightful beneficiary and with no path back to the original sender — an atomicity violation between burn and credit across the two chains.

## Impact Explanation
This falls under the "permanent user-fund or bridge-state lock" and "theft or unbacked mint/unlock" (here, unbacked burn — value removed from circulation without being credited anywhere) categories of the impact gate. Any unprivileged user who calls `add_tip` for a message whose nonce is consumed before/concurrently with their tip arriving on BridgeHub loses their swapped Ether permanently, with only an inert counter (`LostTips`) recording the loss and no extrinsic to reclaim it.

## Likelihood Explanation
No malicious actor, privileged role, or compromised relayer is required — an honest relayer processing a message just before or concurrently with the user's `add_tip` call is sufficient to trigger `AddTipError::NonceConsumed`. Given that tips are specifically meant to incentivize processing of under-priced/slow messages, this race condition is a normal, foreseeable operational occurrence, not an edge case requiring adversarial timing. The bug is fully self-contained within public extrinsics (`add_tip` on AssetHub and BridgeHub) and requires only ordinary user interaction.

## Recommendation
Do not perform the irreversible `burn_for_teleport` on AssetHub until success of the corresponding credit is confirmed on BridgeHub (e.g., via escrow/reservation released only on a delivery-receipt/ack), or alternatively implement the promised recovery extrinsic allowing a user to reclaim/re-mint the amount recorded in `LostTips` back to their account, and ensure that path is exercised whenever `EthereumSystemV2::add_tip` fails.

## Proof of Concept
The existing integration test `tip_to_invalid_nonce_is_added_to_lost_tips` demonstrates the full vulnerable path: it calls `SnowbridgeSystemFrontend::add_tip` on AssetHub with a real DOT asset for a nonce (`MessageId::Outbound(22)`) that does not exist, which triggers the swap-and-burn, and the subsequent BridgeHub-side `EthereumSystemV2::add_tip` call fails, emitting `TipProcessed { success: false }` and increasing `LostTips` for the sender with no compensating credit anywhere in the codebase. 			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether

			let who = T::AccountIdConverter::convert_location(&origin)

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}

		#[pallet::call_index(3)]
		#[pallet::weight(<T as pallet::Config>::WeightInfo::add_tip())]
		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}
