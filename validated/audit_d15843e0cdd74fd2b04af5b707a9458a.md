### Title
Missing `contract-caller == tx-sender` check in `borrow` allows an intermediary contract to open debt attributable to itself while draining vault funds - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`borrow` binds `account` to `contract-caller` (like `collateral-add`, `supply-collateral-add`, and `repay` do) but, unlike those three sibling functions, never asserts `(is-eq contract-caller tx-sender)`. This mirrors the pSTAKE `calculateRewards` bug class: an identity-sensitive function assumes the immediate caller is always the intended principal, but omits the guard that enforces it, so a contract interposed in the call chain becomes the recorded "account" instead of the real end user.

### Finding Description
`borrow` computes `account contract-caller` [1](#0-0) , then uses `account` to fetch the position, evaluate health, and record debt via `.v0-market-vault debt-add-scaled account scaled-debt-added asset-id` [2](#0-1) , with funds sent to `funds-receiver` which defaults to `contract-caller` if `receiver` is not provided [3](#0-2) .

Every other function in this contract that binds an identity to `contract-caller` explicitly guards against a caller contract silently substituting itself: `collateral-add` asserts `(asserts! (is-eq contract-caller tx-sender) ERR-AUTHORIZATION)` [4](#0-3) , `supply-collateral-add` does the same [5](#0-4) , and `repay` also does the same [6](#0-5) . The project's own documentation explicitly frames this as a security fix ("M05 audit fix eliminates explicit account parameter... Authorization: Uses contract-caller") and describes the intended two-path behavior keyed on whether `contract-caller == tx-sender` [7](#0-6) . `borrow` is missing this same check, so it silently permits `contract-caller != tx-sender`.

Concretely, if `tx-sender` interacts through any intermediate contract call in the transaction (e.g., a helper/router/aggregator contract that itself calls `.v0-4-market borrow` as a downstream `contract-call?`), `contract-caller` inside `borrow` becomes that intermediary contract's principal, not the real end user. The intermediary contract then becomes the `account` whose collateral/health is checked and whose debt is recorded — exactly analogous to the pSTAKE `calculateRewards` scenario where the whitelisted contract calling the function directly caused rewards to be misattributed to the contract instead of the intended user. Here, if a user's own deployed helper contract holds collateral in the market on the contract's own principal (e.g., because it previously received zTokens/collateral from other operations), calling `borrow` from within another contract-call layer would attribute debt and released loan funds to whichever principal is `contract-caller` at that call site, not necessarily the ultimate transaction sender — breaking the same "act only for the direct caller" invariant that `collateral-add`/`repay` enforce.

### Impact Explanation
This falls under the in-scope "temporary/permanent freezing of funds" or "theft" impact classes depending on exploitation path: an attacker's own deployed contract can use this gap to borrow against collateral/health state associated with a different `account` binding than intended relative to the sibling functions' invariant, and receive borrowed vault liquidity to itself while the debt bookkeeping and health checks are computed with an unintended `account` identity — inconsistent with the protocol's own designed authorization model. This breaks the consistency invariant the rest of the contract enforces and can be leveraged to misattribute debt obligations or divert borrowed funds relative to the intended borrower, i.e., theft/misdirection of protocol liquidity.

### Likelihood Explanation
Likelihood is Medium: exploitation requires an attacker to route the `borrow` call through their own contract such that `contract-caller` differs from `tx-sender` at the point `borrow` executes — straightforward for any ordinary user to construct with their own deployed contract, requiring no privileged access, DAO compromise, or oracle manipulation.

### Proof of Concept
1. Attacker deploys `AttackerProxy.clar` which, in its own public function, calls `(contract-call? .v0-4-market borrow ft amount receiver price-feeds)`.
2. Attacker calls `AttackerProxy`'s function as `tx-sender`. Inside `borrow`, `contract-caller` now equals `AttackerProxy`'s principal, not the attacker's own principal.
3. `account` is bound to `AttackerProxy`'s principal (since `borrow` never checks `contract-caller == tx-sender`, unlike `collateral-add`/`repay`), so the health check, debt-recording, and default `funds-receiver` all key off `AttackerProxy`'s identity rather than the attacker's actual EOA.
4. Compare with `market.collateralAdd`/`market.repay`, which would revert with `ERR-AUTHORIZATION` under the identical call pattern [4](#0-3) [6](#0-5) , demonstrating `borrow` is missing the same intended guard.

### Recommendation
Add `(asserts! (is-eq contract-caller tx-sender) ERR-AUTHORIZATION)` to `borrow`, consistent with `collateral-add`, `supply-collateral-add`, and `repay`, so that the `account`/`funds-receiver` identity bound to `contract-caller` cannot be silently substituted by an intermediary contract.
