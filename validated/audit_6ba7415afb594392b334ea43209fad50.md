### Title
Unbounded growth of `DelegatedResourceAccountIndex` entries enables an unauthenticated read API to trigger a costly, unbounded DB prefix scan - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
`DelegatedResourceAccountIndexStore.delegate()` writes a new, uniquely-keyed index entry (`FROM_PREFIX/TO_PREFIX + address + counterparty`) every time an account delegates resources to a *new* receiver address [1](#0-0) . Nothing bounds how many distinct counterparty entries an account can accumulate over time. The read path `getWithPrefix()` performs a full `prefixQuery` over all entries for the address and sorts them by timestamp on every call [2](#0-1) , and this is reachable from unauthenticated gRPC/HTTP/JSON query endpoints (`getDelegatedResourceAccountIndex`, `getDelegatedResourceAccountIndexV2`) that any anonymous API client can invoke with just an address [3](#0-2) , exposed via `RpcApiService` and the HTTP servlet [4](#0-3) .

### Finding Description
This mirrors the VUSD `processWithdrawals` bug class: an attacker-controlled, unbounded on-chain list is later iterated in full during a subsequent operation, and the attacker pays little relative to the cost imposed on whoever must process/read that list. Here, instead of governance paying gas to iterate withdrawals, any node serving read APIs must pay CPU/IO to iterate an attacker-inflated index every time the victim address (or the attacker's own address) is queried via `GetDelegatedResourceAccountIndex`/`V2`.

An attacker can call `DelegateResourceContract` (via `DelegateResourceActuator`) repeatedly, each time delegating a minimal amount of bandwidth/energy to a freshly generated receiver address. Each such transaction calls `delegate()`/`delegateV2()`, which appends a brand-new key under `FROM_PREFIX`/`TO_PREFIX` (or V2 equivalents) for the attacker's own address — these entries are never pruned unless the exact same (from,to) pair is later undelegated. There is no cap on the number of distinct counterparties, unlike the analogous `UnfreezeBalanceV2Actuator`, which explicitly caps concurrent unfreeze slots at `UNFREEZE_MAX_TIMES = 32` [5](#0-4) . No equivalent cap exists for delegated-resource counterparties recorded in `DelegatedResourceAccountIndexStore`.

Once the attacker has built up a very large number of index entries for their address, any client (including the attacker themselves, or anyone who queries that address, e.g., an exchange or explorer) triggers `getWithPrefix()`, which does a `prefixQuery` over the entire key range for that address and sorts the results by timestamp [2](#0-1) . This scan runs synchronously on the node's request-handling thread for every one of the unauthenticated `GetDelegatedResourceAccountIndex(V2)` RPC/HTTP calls.

### Impact Explanation
Because the query API is public/unauthenticated and reachable by any anonymous API client, an attacker can cheaply create a large backlog of index entries on their own address (paying only bandwidth/energy fees for many small delegate transactions), then repeatedly issue (or induce others to issue) `GetDelegatedResourceAccountIndex(V2)` calls against that address. Each call forces the node to perform a full prefix scan and sort operation, consuming CPU and disk I/O disproportionate to the fee paid to create the entries. Under heavy attacker-driven creation of entries combined with concurrent read queries, this can degrade the availability of the query API for all users of that node (denial of service on the query/API surface), which matches the "API the node can no longer serve" criterion. It does not directly cause fund loss or consensus divergence, so it is best characterized as a resource-exhaustion/availability issue on the read-API path rather than a chain-halting event.

### Likelihood Explanation
Likelihood is moderate: creating the entries requires only ordinary `DelegateResourceContract` transactions with distinct receiver addresses, each of negligible cost (small bandwidth/energy delegation), and no protocol-level bound prevents an account from delegating to an unbounded number of unique addresses over time. The trigger (calling the read API) requires no special privilege. However, the actual DoS severity depends on how large the attacker can grow the index before the marginal cost of transactions (bandwidth/energy consumption, account creation fees for new addresses) becomes prohibitive, and on how fast `prefixQuery`/sort execute in practice — this could not be fully confirmed without runtime/benchmarking access.

### Recommendation
- Cap the number of distinct delegated-resource counterparty entries recorded per address (similar to `UNFREEZE_MAX_TIMES` in `UnfreezeBalanceV2Actuator`), or validate/reject delegate calls once a per-account counterparty-count threshold is exceeded, in `DelegateResourceActuator`/`DelegateResourceContract` validation.
- Consider paginating `getWithPrefix()` / `GetDelegatedResourceAccountIndex(V2)` responses and query cost, rather than performing an unbounded prefix scan and full in-memory sort for every request.
- Rate-limit or apply stricter energy/bandwidth accounting to repeated small-value delegate operations that create new index keys.

### Proof of Concept
1. From a single attacker-controlled account, repeatedly broadcast `DelegateResourceContract` transactions, each delegating a minimal (near-zero) amount of BANDWIDTH or ENERGY to a newly generated, distinct receiver address.
2. Each transaction executes `DelegatedResourceAccountIndexStore.delegate()` (or `delegateV2()`), inserting a new `FROM_PREFIX+attacker+receiver` and `TO_PREFIX+receiver+attacker` key pair — these accumulate without limit since no cap on distinct counterparties exists.
3. After accumulating a very large number of such entries, call `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` (via gRPC, HTTP, or JSON-RPC-reachable Wallet API) for the attacker's address.
4. Observe that `getWithPrefix()` performs a full prefix scan and sort of all accumulated entries synchronously on the request thread, consuming disproportionate node resources relative to the low cost incurred to create them.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }

  public DelegatedResourceAccountIndex getDelegatedResourceAccountIndex(ByteString address) {
    if (address == null || address.size() != DecodeUtil.ADDRESS_SIZE / 2) {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
    DelegatedResourceAccountIndexCapsule accountIndexCapsule =
        chainBaseManager.getDelegatedResourceAccountIndexStore().getIndex(address.toByteArray());
    if (accountIndexCapsule != null) {
      return accountIndexCapsule.getInstance();
    } else {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
  }

  public DelegatedResourceAccountIndex getDelegatedResourceAccountIndexV2(ByteString address) {
    if (address == null || address.size() != DecodeUtil.ADDRESS_SIZE / 2) {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
    DelegatedResourceAccountIndexCapsule accountIndexCapsule = chainBaseManager
        .getDelegatedResourceAccountIndexStore().getV2Index(address.toByteArray());
    if (accountIndexCapsule != null) {
      return accountIndexCapsule.getInstance();
    } else {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
  }
