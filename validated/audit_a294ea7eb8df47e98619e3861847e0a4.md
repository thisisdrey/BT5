### Title
Unrecovered index-out-of-range panic on empty object-walk line crashes Gitaly process during transaction commit - ([File: internal/gitaly/storage/storagemgr/partition/transaction_manager.go])

### Summary
`TransactionManager.packObjects` parses the output of the object-walk (`git rev-list`-style) pipeline line-by-line and indexes the first byte of each line without checking that the line is non-empty. That parsing loop runs inside a bare `errgroup.Go` goroutine, which — unlike gRPC RPC handlers — is **not** wrapped by Gitaly's `panichandler` interceptor. A panic there is unrecovered and takes down the whole `gitaly` process, exactly mirroring the reported bug class (an uncaught panic on attacker-influenced input escaping a "should never happen" invariant and crashing the process rather than just failing gracefully).

### Finding Description
In the transaction-commit path, Gitaly pipes the output of `WalkObjects` into a scanner and processes each output line: [1](#0-0) 

```go
scanner := bufio.NewScanner(objectWalkReader)
...
for scanner.Scan() {
    objectLine := scanner.Text()
    if objectLine[0] == '?' {
        ...
```

`objectLine[0]` is indexed with no check that `len(objectLine) > 0`. `bufio.Scanner` with the default line-splitting function can legitimately yield an empty token when the underlying stream contains a blank line (e.g., `"\n\n"`). If the walk/rev-list-style command ever emits a stray blank line — through malformed quarantine object data, a crafted ref/tag whose formatted output degenerates to an empty line, or any other edge condition in `quarantineOnlySnapshotRepository.WalkObjects` output — `objectLine[0]` panics with "index out of range [0] with length 0".

Crucially, this code executes inside a goroutine spawned via `group.Go` (`golang.org/x/sync/errgroup`) at line 1457, not inside the RPC handler goroutine itself: [2](#0-1) 

`errgroup.Go` does not recover panics; an unrecovered panic in a goroutine started this way propagates and crashes the entire Go process, since Go's runtime terminates the whole program on an unrecovered goroutine panic. Gitaly's own developer guidance explicitly documents this exact class of risk: [3](#0-2) 

The gRPC-level `panichandler.UnaryPanicHandler`/`StreamPanicHandler` interceptors only catch panics that occur synchronously within the interceptor chain around the handler goroutine — they cannot catch panics raised in independently spawned goroutines like this one: [4](#0-3) 

Gitaly is aware of this exact hazard pattern elsewhere in the codebase — e.g. `internal/streamcache/cache.go`'s `runCreate` explicitly recovers panics with a comment stating "unlike RPC handlers, which are guarded by a panic catching middleware, an uncaught panic can crash the whole process" — but no equivalent recovery exists in `packObjects`.

### Impact Explanation
`packObjects` is invoked as part of the WAL-based transaction commit flow used by ordinary write RPCs (e.g., processing a push that creates a transaction, packs new objects, and commits them). Any transaction that goes through this code path is exposed. If the object-walk output can be coerced into producing an empty line, an ordinary authenticated Gitaly client (a normal `git push` or similar mutating RPC) can crash the entire `gitaly` process, terminating all in-flight RPCs for every repository served by that process — a full denial-of-service, not merely a failed single request. This matches the "Uncaught Exception" / process-abort DoS class of the reference advisory, where malformed-but-reachable input during a persistence/commit path defeats validation and reaches a fatal, unguarded runtime panic.

### Likelihood Explanation
This requires the object-walk/rev-list-style output to contain a blank line, which is not something honestly-formed Git output normally produces (`<oid> <path>` or `?<oid>` are the only documented formats). Reaching it likely requires either (a) a specific edge case in ref/path formatting that degenerates to an empty output line, or (b) another upstream bug that emits unexpected blank output into this pipe. Without being able to execute against a live Gitaly binary, I cannot definitively construct byte-for-byte input that reaches this exact empty-line condition through `WalkObjects`; this is a **plausible but unconfirmed reachability path** — the code path and missing panic-guard are concretely verified, but a concrete external trigger sequence was not proven end-to-end in the available static analysis.

### Recommendation
- Guard the loop with a length check before indexing: `if len(objectLine) == 0 { continue }` or treat an empty line as a scan error and abort the transaction with an error rather than panicking.
- Wrap the goroutine body in `packObjects` (and any other `group.Go` bodies parsing subprocess/pipe output) with a `recover()`-based guard (e.g. reuse the `dontpanic` package's pattern) so that unexpected parsing failures degrade to a transaction error instead of crashing the process.
- Audit other `bufio.Scanner`-based parsers running inside bare goroutines throughout `transaction_manager.go` and `gitpipe` for the same un-bounds-checked indexing pattern.

### Proof of Concept
Not independently reproduced against a running instance; based on static code review only. A reproduction would require: (1) triggering a mutating transaction (e.g., `git push`) whose quarantine object walk/`WalkObjects` output emits a blank line, and (2) observing that the `gitaly` process panics and exits rather than the RPC merely returning an error. Confirming a concrete Git-level trigger for the blank-line condition would need dynamic testing against `quarantineOnlySnapshotRepository.WalkObjects`, which was not available in this static analysis.

// UnaryPanicHandler creates a new unary server interceptor that handles panics.
func UnaryPanicHandler(logger log.Logger) grpc.UnaryServerInterceptor {
	return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (resp interface{}, err error) {
		defer handleCrash(logger, info.FullMethod, func(grpcMethodName string, r interface{}) {
			err = toPanicError(grpcMethodName, r)
		})

		return handler(ctx, req)
	}
}

	}
