### Title
Heap-buffer-overflow read in `InputZipFile::ProcessCentralDirEntry` ZIP64 extra-field parsing - (File: `third_party/ijar/zip.cc`)

### Summary
`ijar`'s central-directory-entry parser walks a ZIP64 "extra field" region using an attacker-controlled `data_size` without validating that enough bytes remain before dereferencing them, mirroring the class of bug in `CIccXmlArrayType<>::DumpArray()` (reading array/record data past the buffer that backs it based on an untrusted declared length).

### Finding Description
`InputZipFile::ProcessCentralDirEntry` reads the central-directory extra-field bytes for each ZIP/JAR entry directly out of the mmap'd input file: [1](#0-0) 

```
p += file_name_length;
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  if (header_id == ZIP64_EXTRA_FIELD_TAG) {
    if (*uncompressed_size == U4_MAX) {
      *uncompressed_size = get_u8le(extra);
    }
    ...
  }
}
```

No caller ever validates that `extra_field_length` bytes actually remain inside the mapped file/central directory region before this loop runs, and inside the loop:
- `get_u2le(extra_p)` twice (4 bytes total) is read with no check that at least 4 bytes remain before `p` (the declared end of the extra-fields region), so a truncated 1–3 byte trailing extra field already over-reads.
- When `header_id == ZIP64_EXTRA_FIELD_TAG`, `get_u8le(extra)` (and potentially two more `get_u8le` calls for compressed size / offset) unconditionally reads 8 bytes from `extra`, even though `data_size` for that record could be declared as 0–7. There is no check `data_size >= 8` (or `24` for the full triple) before reading.
- `extra_p += data_size` can also push `extra_p` past `p`, so the loop condition `extra_p != p` can be skipped entirely by crafting `data_size` such that `extra_p` overshoots `p`, but more importantly the very first read of a small/zero `data_size` ZIP64 record already triggers the out-of-bounds read before any length reconciliation happens.

Contrast with the fixed/careful pattern that exists elsewhere in the same codebase for the same ZIP extra-field concept, `third_party/singlejar`'s `ExtraField::find`, which explicitly bounds-checks each field against the buffer end before touching it: [2](#0-1) 

and `OutputJar::AppendToDirectoryBuffer` / `WriteEntry`, which validate `ef->size()` against the end pointer and abort with `diag_errx` on malformed extra fields (as exercised by the `MalformedExtraField` test): [3](#0-2) [4](#0-3) 

`third_party/ijar/zip.cc` has no equivalent bounds check for the extra-field loop it uses when reading a ZIP64 record's 8-byte payload, so it is the vulnerable analog: untrusted archive bytes (a maliciously crafted JAR/ZIP consumed by `ijar`, e.g. via `java_import`, a fetched `.jar` dependency, or any build rule that runs the input through ijar to produce an interface jar) drive a heap read past the mapped input buffer.

### Impact Explanation
The read is out-of-bounds relative to the mmap'd input file region; it can read adjacent heap/mapping memory into the tool's internal state (`*uncompressed_size`, `*compressed_size`, `*offset`) or crash the process (SIGSEGV on an unmapped page boundary) when ijar processes a hostile JAR supplied as a dependency. This matches the CVE's profile: low confidentiality impact via limited stray-memory disclosure and high availability impact via crash, with local, low-complexity, no-privilege, user-interaction-required exploitation (the victim's build must consume the crafted archive).

### Likelihood Explanation
`ijar` is invoked automatically by Bazel for any Java target whose interface jar needs generation, including jars obtained from external sources (e.g., `java_import`, `http_jar`/`http_file` derived jars, Maven-resolved artifacts). An attacker who controls the content served at such a URL (with no valid sha256 pin, or where the ICC/zip parsing happens before/regardless of hash verification of downloaded bytes) can supply a JAR with a truncated or short ZIP64 extra field to trigger this path with realistic likelihood whenever ijar decides to actually inspect that entry's central directory data.

### Recommendation
In `InputZipFile::ProcessCentralDirEntry` (`third_party/ijar/zip.cc`), before reading `header_id`/`data_size`, verify at least 4 bytes remain between `extra_p` and `p`; before dereferencing the ZIP64 payload with `get_u8le`, verify `data_size >= 8` (or `>= 24` when reading all three fields) and that `extra_p + data_size <= p`. Reject the entry (return `false`/emit an error) instead of reading past the declared extra-field length, matching the bounds-checked pattern already used in `src/tools/singlejar/zip_headers.h`'s `ExtraField::find`.

### Proof of Concept
A `BuildIntegrationTestCase`/shell-style PoC modeled on `src/tools/singlejar/output_jar_simple_test.cc`'s `CreateZipWithMalformedExtraField()`/`MalformedExtraField` test: [4](#0-3) 

1. Hand-craft a minimal ZIP/JAR whose central directory entry declares `extra_field_length = 2` and contains a ZIP64 extra-field record (`header_id = 0x0001`) with `data_size = 0` (i.e., only the 4-byte tag+size header fits, no payload bytes at all) and `uncompressed_size32 = 0xFFFFFFFF` (forcing the ZIP64 path to be taken).
2. Feed this file to `ijar` (`InputZipFile::Open()` + `ProcessNext()` → `ProcessCentralDirEntry`), e.g. via a small driver mirroring `third_party/ijar/ijar.cc`'s main entry point or a new `ZipReaderTest`.
3. Run under ASan; `get_u8le(extra)` at line 533/536/539 reads 8 bytes starting at `extra`, which is only 4 bytes before the end of the 2-byte-declared extra-field region and the end of the mmap'd input buffer, producing a heap-buffer-overflow read report analogous to the `CIccXmlArrayType<>::DumpArray()` finding.

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
