Based on the report's core bug class — a critical, security-relevant trust transition performed in a single, unconfirmed step (`_transferOwnership` immediately re-pointing ownership with no acceptance handshake) — the closest reachable analog in Nebula is the single-step re-pointing of a live tunnel's trusted underlay address (`HostInfo.remote`) via `SetRemoteIfPreferred`, triggered off a replayed handshake packet, with no round-trip re-verification that the new address actually controls the peer's key material.

### Title
Single-step, unconfirmed remote-address trust transfer on replayed handshake packets - (File: `handshake_manager.go`)

### Summary
When a responder receives a handshake packet it has already seen (`ErrAlreadySeen`), it calls `existing.SetRemoteIfPreferred(f.hostMap, via)` to instantly update the tunnel's trusted underlay address (`HostInfo.remote`) to the new source address, provided that address falls in a "preferred" CIDR range [1](#0-0) . This mirrors the audited flaw: a security-critical piece of state (here, "who owns this tunnel's live traffic destination") is transferred in one irreversible step, without a second, independent confirmation that the new address is actually held by the legitimate peer.

### Finding Description
`CheckAndComplete` detects a duplicate/replayed handshake by comparing raw handshake packet bytes against what is already stored for an existing hostinfo [2](#0-1) . On such a match, `ErrAlreadySeen` is returned and handled by simply calling `SetRemoteIfPreferred` with the *new* source (`via`) of the replayed packet [1](#0-0) .

`SetRemoteIfPreferred` performs the address swap in a single step: if the new source address lies in a configured preferred range, it immediately calls `SetRemote`, which overwrites the atomic `remote` pointer and calls `LearnRemote` on the `RemoteList` [3](#0-2) . There is no secondary step requiring the "new" address to independently prove possession of the peer's session/handshake keys before the swap is committed — the only gate is that the byte-for-byte handshake packet was seen before, which an on-path/replay-capable attacker can trivially satisfy by recording and replaying the same UDP payload with a different source.

`LearnRemote` further mutates the `RemoteList`'s cache unconditionally on this same signal [4](#0-3) , so this state feeds every subsequent traffic-routing decision for that tunnel.

### Impact Explanation
This allows a network-position attacker (able to observe/replay a captured handshake packet and spoof/originate traffic from an address inside the victim's preferred CIDR ranges, e.g. private LAN ranges commonly configured for `preferred_ranges`) to redirect where the victim sends encrypted overlay traffic for an established tunnel, in a single step with no additional proof of key possession — a form of remote state poisoning of the hostmap/tunnel routing state. Because the attacker does not obtain the session keys, this is not a decryption bypass, but it can misdirect/blackhole traffic and disrupt tunnel availability for the legitimate peer without any two-step (propose/accept) confirmation, exactly the risk class flagged in the report (irrevocable one-step critical state change).

### Likelihood Explanation
Exploitation requires the attacker to (1) capture one raw handshake packet exchanged between two nodes and (2) be able to send from (or spoof) a UDP source address inside the target's `preferred_ranges` (a config-dependent condition, but common for typical private-network preferred range setups). This is a plausible on-path/local-network attacker scenario, not requiring any valid certificate.

### Recommendation
Do not perform this trust-critical remote-address swap based solely on byte-equality of a replayed handshake packet plus a preferred-range membership check. Require the new address to independently complete (or re-confirm) a fresh authenticated round trip (e.g., a signed liveness/challenge exchange bound to the current session keys) before `SetRemoteIfPreferred`/`SetRemote` commit the new address as the tunnel's trusted remote, mirroring a propose/accept two-step pattern rather than a single implicit commit.

### Proof of Concept
1. Attacker observes (or is on-path for) the initial handshake stage0 UDP packet between node A and node B.
2. Attacker resends the identical packet bytes to A's listener, spoofing/originating from an address inside A's configured `preferred_ranges`.
3. `CheckAndComplete` finds the exact same `HandshakePacket[stage0]` bytes already stored and returns `ErrAlreadySeen` [5](#0-4) .
4. `handleCheckAndCompleteError` calls `existing.SetRemoteIfPreferred(f.hostMap, via)` with the attacker's `via` address [6](#0-5) .
5. Because the spoofed address is in a preferred range, `SetRemoteIfPreferred` immediately calls `SetRemote`, overwriting A's trusted `remote` for that tunnel in one step [7](#0-6) , redirecting subsequent encrypted traffic toward the attacker's address without any additional confirmation round trip.

// SetRemoteIfPreferred returns true if the remote was changed. The lastRoam
// time on the HostInfo will also be updated.
func (i *HostInfo) SetRemoteIfPreferred(hm *HostMap, via ViaSender) bool {
	if via.IsRelayed {
		return false
	}

	currentRemote := i.GetRemote()
	if !currentRemote.IsValid() {
		i.SetRemote(via.UdpAddr)
		return true
	}

	// NOTE: We do this loop here instead of calling `isPreferred` in
	// remote_list.go so that we only have to loop over preferredRanges once.
	newIsPreferred := false
	for _, l := range hm.GetPreferredRanges() {
		// return early if we are already on a preferred remote
		if l.Contains(currentRemote.Addr()) {
			return false
		}

		if l.Contains(via.UdpAddr.Addr()) {
			newIsPreferred = true
		}
	}

	if newIsPreferred {
		// Consider this a roaming event
		i.lastRoam = time.Now()
		i.lastRoamRemote = currentRemote

		i.SetRemote(via.UdpAddr)

		return true
	}

	return false
}

// LearnRemote locks and sets the learned slot for the owner vpn ip to the provided addr
// Currently this is only needed when HostInfo.SetRemote is called as that should cover both handshaking and roaming.
// It will mark the deduplicated address list as dirty, so do not call it unless new information is available
func (r *RemoteList) LearnRemote(ownerVpnIp netip.Addr, remote netip.AddrPort) {
	r.Lock()
	defer r.Unlock()
	if remote.Addr().Is4() {
		r.unlockedSetLearnedV4(ownerVpnIp, netAddrToProtoV4AddrPort(remote.Addr(), remote.Port()))
	} else {
		r.unlockedSetLearnedV6(ownerVpnIp, netAddrToProtoV6AddrPort(remote.Addr(), remote.Port()))
	}
}
