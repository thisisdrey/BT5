### Title
`add_tip` in `SnowbridgeSystemFrontend` bypasses the pause/halt guard, letting users burn real value while message export is supposed to be halted - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

### Summary
The Snowbridge system-frontend pallet implements a pause mechanism (`set_operating_mode` / `ExportOperatingMode`) intended to halt "all" Ethereum-export operations in an emergency, exactly like the `whenNotPaused` guard in the external report. However, only `register_token` checks this halt flag; the `add_tip` dispatchable performs its asset swap, ether burn, and cross-chain `Transact` dispatch without ever consulting `ExportOperatingMode`, so the guard is effectively dead for this entry point.

### Finding Description
`ExportOperatingMode<T>` is the pallet's single source of truth for whether Ethereum-bound export is halted, and `ExportPausedQuery::is_paused()` is implemented purely by reading it: [1](#0-0) 

`register_token` correctly gates on this flag before doing anything: [2](#0-1) 

But `add_tip` — a fully public, signed-origin dispatchable — never calls `Self::export_operating_mode().is_halted()` (or any equivalent check). It goes straight from `ensure_signed` into `swap_fee_asset_and_burn` (which swaps the tip asset for Ether via `T::Swap` and burns it via `burn_for_teleport`) and then dispatches a `Transact` to BridgeHub: [3](#0-2) 

Downstream, the BridgeHub-side `add_tip` in `snowbridge-pallet-system-v2` also performs no halt check — it simply forwards to `InboundQueue::add_tip` / `OutboundQueue::add_tip` and records a `LostTips` fallback on error, with no operating-mode gate at all: [4](#0-3) 

This is the same class of bug as the report: a pause primitive exists (`ExportOperatingMode` / `set_operating_mode`, analogous to `ERC20PausableUpgradeable`'s `_pause`/`whenNotPaused`) but one of the state-mutating, value-moving public entry points (`add_tip`, analogous to the missing `pause()`/`unpause()` wrappers making the modifier unreachable/ineffective) never consults it, so the "halt everything" invariant the pallet documentation implies ("Message export is halted" error, `Error::Halted`) is not actually enforced for this call.

### Impact Explanation
When operators halt Snowbridge (`ExportOperatingMode = Halted`) — e.g., during an incident with the Ethereum gateway, a compromised relayer, or a bridge exploit — an unprivileged, signed user can still call `add_tip`. This burns real backing asset value (Ether obtained via `pallet_asset_conversion::Swap` and `burn_for_teleport`) and dispatches a cross-chain XCM `Transact` toward BridgeHub while the bridge is supposed to be fully stopped. This violates the "public underpriced work degrades... stalls bridge processing" and "theft/unbacked burn while halted" impact classes: value is destroyed/committed on the Polkadot side even though the corresponding Ethereum-side processing is meant to be frozen, and it can also be used to keep injecting BridgeHub `Transact` traffic during an emergency halt that the pause was meant to prevent.

### Likelihood Explanation
High likelihood: `add_tip` is a normal signed extrinsic requiring no privilege, and the missing check is a simple code-path omission (present in the sibling `register_token` function but absent here), not requiring any race condition, governance action, or external actor. Any user can trigger it any time the pallet is halted.

### Recommendation
Add the same halt check to `add_tip` (and to the BridgeHub-side `snowbridge-pallet-system-v2::add_tip`) that `register_token` already performs:
```rust
pub fn add_tip(origin: OriginFor<T>, message_id: MessageId, asset: Asset) -> DispatchResult {
    ensure!(!Self::export_operating_mode().is_halted(), Error::<T>::Halted);
    let who = ensure_signed(origin)?;
    ...
}
```
Audit all other dispatchables in `snowbridge-pallet-system-frontend`, `snowbridge-pallet-system-v2`, `inbound-queue-v2`, and `outbound-queue-v2` to confirm every value-moving or message-forwarding path consults the relevant `OperatingMode`/`Halted` flag consistently, not just the ones that happen to check it today.

### Proof of Concept
1. Root/governance calls `SnowbridgeSystemFrontend::set_operating_mode(Halted)` on AssetHub, setting `ExportOperatingMode = Halted`.
2. An arbitrary signed user calls `SnowbridgeSystemFrontend::add_tip(origin, message_id, fee_asset)` with a valid tip asset.
3. `add_tip` proceeds without any halt check: `swap_fee_asset_and_burn` swaps and burns the asset for Ether, and `send_transact_call` dispatches an XCM `Transact` to BridgeHub's `EthereumSystemCall::AddTip`, exactly as if the pallet were not halted — contrasted with attempting `register_token` in the same state, which correctly fails with `Error::Halted`.
4. Observed result: asset burn and cross-chain dispatch succeed while `ExportOperatingMode::Halted` is active, confirming the pause is inaccessible/ineffective for this entry point.

		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}
