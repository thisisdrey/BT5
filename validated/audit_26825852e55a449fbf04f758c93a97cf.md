### Title
Witnesses can unilaterally raise their brokerage (commission) rate via `UpdateBrokerageContract`, retroactively cutting reward payouts already earned by locked voters - ([File: actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java])

### Summary
`UpdateBrokerageActuator` lets any account that is a registered witness change its `brokerage` (its cut of block/vote rewards, 0–100) at any time, with no rate-limit, cooldown, or per-cycle restriction on how often or how much it can change. [1](#0-0) 

### Finding Description
This mirrors the reported Cooler bug class: a counter-party (the SR/witness, analogous to the "lender") can unilaterally change an economic term (interest rate / commission) that a second party (the voter, analogous to the "borrower") has already committed capital to, and that second party cannot exit before being harmed.

Voters commit TRX (via freezing/voting) to a witness expecting a given reward split. `MortgageService.payReward()` reads the witness's current brokerage for the current cycle and deducts that percentage from the reward pool before crediting the rest to voters: [2](#0-1) 

`DelegationStore.setBrokerage(byte[] address, int brokerage)` stores the new value under a special "-1" (`REMARK`) slot with no history/versioning per cycle, no minimum change interval, and no cap on the frequency of updates: [3](#0-2) 

The actuator's `validate()` only checks that the address is a valid, existing witness/account and that `0 <= brokerage <= 100` — nothing checks how recently brokerage was last changed or limits the magnitude of the change: [4](#0-3) 

Because `UpdateBrokerageContract` requires only the witness's own signature (an unprivileged, self-signed transaction any registered witness can broadcast), a witness can:
1. Attract voters/delegators with a low brokerage (e.g., 0–5%).
2. Once voters have staked/voted TRX for it (locked for unfreeze periods), instantly call `updateBrokerage` to set brokerage to 100 right before/at reward distribution.
3. Reward computations for the *current cycle* immediately reflect the new rate — voters who already voted have no way to prevent the change and must wait out potentially long unfreeze/vote-withdrawal periods before they can redirect their stake elsewhere, during which they receive minimal or zero rewards.

This is directly analogous to the Cooler `rollLoan()` issue: a permissionless, single-party-controlled function changes agreed-upon economic terms after the counter-party has already committed value, with no floor/ceiling on the rate of change and no lock preventing abuse.

### Impact Explanation
Voters who have delegated/frozen TRX to a witness can have their expected staking rewards reduced to near zero at will by that witness, with no recourse until unfreeze/unvote is possible. This constitutes an unbacked expectation of reward yield and unauthorized diversion of reward funds from voters to the witness, satisfying "theft/permanent loss of funds" for affected delegators — reachable purely through a signed `UpdateBrokerageContract` transaction from the witness's own account.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to be a registered witness (a permissioned but broadly attainable role, not a privileged node role like SR/committee-only path) and requires voters to have already staked to that witness. Any witness can trigger this at will with a single transaction; no coordination or race condition needed.

### Recommendation
Introduce a cooldown/rate limit on `UpdateBrokerageContract` (e.g., limit to once per cycle, as is common in other TRON reward-model implementations) and/or cap the maximum brokerage delta per update, and apply new brokerage settings only starting from the *next* cycle rather than the current one, so voters have advance notice and time to react before the new rate affects already-locked stake.

### Proof of Concept
1. Witness `W` registers and sets brokerage to 0% via `UpdateBrokerageContract`.
2. Voter `V` votes/freezes TRX for `W`, expecting ~100% of the reward share (minus 0% commission).
3. Before the next `withdrawReward`/reward accrual for the current cycle, `W` calls `updateBrokerage` again setting brokerage to 100.
4. `MortgageService.payReward()` for the current cycle now computes `brokerageAmount = value` (100%) and sends the entire reward to `W`'s allowance, leaving `0` for the reward pool that voters draw from via `computeReward()`. [2](#0-1) 
5. `V` has no reward for that cycle despite having staked, and cannot recover funds already staked without waiting through the unfreeze/withdrawal delay.

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }
