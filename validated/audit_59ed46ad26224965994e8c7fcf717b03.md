Based on the evidence gathered, the strongest reachable analog to the "missing deadline" bug class is in the handshake initiation path: `Portal.sol`'s `convert()`/`buyPortalEnergy()`/`sellPortalEnergy()` had no deadline, allowing a stale mempool transaction to be executed later under changed conditions. In nebula, the analogous "pending transaction" is a stage-0 handshake initiation packet (`msg1`) sitting in the network/attacker's hands with no expiration, which can be replayed/delivered at an arbitrary later time and still be accepted to establish a full tunnel.

### Title
Stage-0 Handshake Initiation Packets Have No Expiration, Allowing Delayed/Replayed Handshakes To Establish Stale Tunnels - (File: handshake_manager.go)

### Summary
`HandshakeManager.beginHandshake` (the responder-side stage-0 handler) and the initiator's stage-0 build/retransmit path in `handleOutbound` do not attach or check any packet-level expiration/deadline to the handshake initiation message itself. The only "freshness" signal in the wire format is the optional `Time` field in `NebulaHandshakeDetails` (`handshake/handshake.proto`), which is decoded into `Payload.Time` / `HostInfo.lastHandshakeTime` [1](#0-0)  but is only used to compare *two competing handshakes for the same peer* in `CheckAndComplete`, never to reject a handshake packet that is simply "too old" relative to wall-clock time [2](#0-1) .

### Finding Description
The nebula "mempool" equivalent is any network path (attacker-controlled relay, delayed delivery, or a saved/exfiltrated UDP packet) that can hold and later replay a `header.Handshake` stage-0 packet. `e2e/handshake_manager_test.go`'s `TestHandshakeLateResponse` demonstrates this directly: the initiator's own local timeout expires and the pending hostinfo is deleted locally, but the exact same stale `msg1` — held out of band rather than dropped — is delivered to the responder afterward and the responder still processes it and creates a tunnel: [3](#0-2) 

The responder-side acceptance path (`beginHandshake` → `CheckAndComplete`) validates only the certificate's `NotBefore`/`NotAfter` against the *current* time via `certVerifier` (`hm.f.pki.GetCAPool().VerifyCertificate(time.Now(), c)` at `handshake_manager.go:1162-1166`) and the noise/HMAC cryptographic integrity of the message; it never checks how long the packet has been outstanding since creation. Because the only sender-supplied freshness field, `Payload.Time`, is used purely as a tie-breaker against an *existing* hostinfo entry (`existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime`) rather than validated against `time.Now()` with any bound, a stage-0 packet captured by an on-path relay or a malicious lighthouse/relay peer (both reachable without holding a CA-signed certificate for the target identity, since they merely forward or delay the initiator's own valid packet) can be replayed at an arbitrarily later time and still successfully complete a handshake, as confirmed by `TestHandshakeLateResponse`.

### Impact Explanation
An attacker positioned to intercept and delay UDP delivery (e.g., a malicious relay, NAT intermediary, or anyone able to buffer and later inject the packet) can force a tunnel establishment long after the initiator intended it, using stale conditions: e.g., a certificate that is nearing/near its expiry window and would not have been used to initiate a *fresh* handshake, or delivering the handshake to a stale/incorrect network path recorded in the lighthouse, causing state poisoning of `HostMap`/hostinfo (the tunnel now exists with keys/timing the initiator no longer controls or expects) or resource exhaustion via accumulation of long-delayed spurious handshakes. This mirrors the "unknowingly executed later" impact class in the source report, applied to session establishment rather than token pricing.

### Likelihood Explanation
Medium: the attacker does not need a CA-signed certificate — they only need the ability to delay delivery of a legitimately-sent stage-0 packet (achievable by a relay peer, a compromised intermediate router, or simple on-path buffering), and the responder's own local retry/timeout state (`hh.counter >= hm.config.retries` in `handleOutbound`) is irrelevant since it only governs the *initiator's* resend behavior, not the *responder's* acceptance criteria. The existing test `TestHandshakeLateResponse` (`e2e/handshake_manager_test.go:231-279`) empirically confirms the responder will accept and complete such a stale packet.

### Recommendation
Bind the handshake `Payload.Time` field to an enforced staleness window on the receiving side: reject stage-0 (and stage-2, if applicable) handshake packets whose `Time` differs from `time.Now()` by more than a small, configurable tolerance (analogous to adding a `deadline` check before `nonReentrant`-style execution in the referenced report). This should be validated in `handshake.Machine.processPayload` / `beginHandshake` before certificate validation and hostinfo creation, so a delayed or replayed initiation packet is dropped outright rather than allowed to complete a tunnel.

### Proof of Concept
`e2e/handshake_manager_test.go` (`TestHandshakeLateResponse`) is itself a working PoC of the vulnerable behavior for the responder side:
1. Initiator sends `msg1`; test intercepts it (`GetFromUDP`) without delivering it to the responder.
2. Initiator's local pending handshake times out and is deleted (`assert.Empty(t, myControl.ListHostmapHosts(true))`).
3. The withheld, now-stale `msg1` is injected into the responder well after the initiator gave up: `theirControl.InjectUDPPacket(msg1)`, and the responder replies with a valid stage-2 response (`resp := theirControl.GetFromUDP(true); assert.NotNil(t, resp)`), i.e., the responder created a tunnel from a stale, delayed packet [4](#0-3) .

This shows the responder applies no deadline/staleness check to the incoming stage-0 handshake packet independent of the initiator's own timeout, confirming the missing-deadline analog.
