### Title
Untrusted relayer can redirect Wallet Contract `AddKey`/`DeleteKey` actions to an account the user never authorized - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs)

### Summary
The `near-wallet-contract` (the eth-implicit account's on-chain wallet, invoked via `rlp_execute(target, tx_bytes_b64)`) validates that a relayer-supplied `target` account matches the signed Ethereum calldata's `receiver_id` for `FunctionCall` and `Transfer` actions, but performs **no equivalent check** for `AddKey`/`DeleteKey` actions. Since `target` is an ordinary, unsigned function-call argument controlled entirely by the (explicitly untrusted, "faulty relayer may be banned") relayer, a malicious or buggy relayer can redirect a user's signed `AddKey`/`DeleteKey` intent to an arbitrary NEAR account instead of the user's own eth-implicit account.

### Finding Description
`rlp_execute` takes `target: AccountId` directly as a contract-call argument, not as part of the Secp256k1-signed Ethereum transaction payload: [1](#0-0) 

Inside `parse_tx_data`, the `FUNCTION_CALL_SELECTOR` and `TRANSFER_SELECTOR` branches explicitly bind the action to `target` by checking it against the ABI-decoded `receiver_id`: [2](#0-1) 

But the `ADD_KEY_SELECTOR` and `DELETE_KEY_SELECTOR` branches decode only key material (`public_key`, permission fields) — there is no `receiver_id`/`target` field in the signed calldata at all, and no check binding the action to any particular account: [3](#0-2) 

These are classified as `ParsableTransactionKind::SelfNearNativeAction`. The only place this classification is used to reroute the action is when `target_kind == TargetKind::EthImplicit(_)` (i.e., `target` decodes to *another* eth-implicit address); in that case the action is overridden into a same-account `Transfer`. For `TargetKind::CurrentAccount` and, critically, `TargetKind::OtherNearAccount` (any named account that isn't an eth-implicit address), the original `AddKey`/`DeleteKey` action passes through unchanged: [4](#0-3) [5](#0-4) 

Finally, `inner_rlp_execute`'s default branch turns the action into a promise addressed at the relayer-chosen `target`, not `current_account_id`: [6](#0-5) [7](#0-6) 

The result: a user who signs a `DeleteKey(public_key)` Ethereum-style transaction — most plausibly to revoke a relayer's own `FunctionCall`-permission key from their eth-implicit account after the relayer becomes untrusted — has the transaction submitted through the very relayer whose access is being revoked. That relayer controls the unsigned `target` parameter and can substitute any other named `AccountId` for which the `DeleteKey`/`AddKey` action would be routed instead of the user's own account. Nothing in the signed payload constrains which account the action applies to; only `target` does, and `target` is relayer-controlled.

Docs confirm the intended trust boundary — the relayer is explicitly untrusted and is only supposed to pay gas / route the exact user-authorized action, with faulty behavior leading to being banned, not to being able to redirect security-sensitive actions: [8](#0-7) 

### Impact Explanation
By supplying a decoy `target` (any `OtherNearAccount`, or a `CurrentAccount` alias not equal to the true wallet account in edge configurations), a malicious/faulty relayer can:
- Cause a user's `DeleteKey` transaction — intended to revoke that very relayer's `FunctionCall` key from the user's eth-implicit account — to be misrouted to an unrelated account. If the specified public key does not exist on the decoy account the action fails, the nonce is nonetheless consumed (nonce increments on the `NearNativeAction` path before promise dispatch), and the signed transaction cannot be replayed, permanently defeating the user's ability to revoke that specific relayer/session key from their account.
- More generally, force the wallet contract to attempt `AddKey`/`DeleteKey` receipts against arbitrary receiver accounts chosen by the relayer instead of the account the user actually controls, breaking the invariant (documented and enforced for `FunctionCall`/`Transfer` but not for `AddKey`/`DeleteKey`) that a signed Ethereum transaction submitted through this contract only ever affects the signer's own eth-implicit account.

This is an authorization/scope-escalation bug analogous to the report's "overprivileged role": the relayer — meant to be an unprivileged, untrusted courier — gains unchecked control over which account a sensitive key-management action targets, undermining the account's key-revocation mechanism.

### Likelihood Explanation
Likelihood is moderate: it requires a malicious or compromised relayer (the standard threat actor this contract is explicitly designed to defend against for other action types), and does not require any cryptographic break — only omission of a `target == current_account_id` check on the two action variants (`AddKey`/`DeleteKey`) that the contract's own code and tests otherwise treat as strictly "self" actions (see the `SelfNearNativeAction` naming and the `test_cannot_add_full_access_key` test intent).

### Recommendation
In `parse_tx_data`'s `ADD_KEY_SELECTOR` and `DELETE_KEY_SELECTOR` branches, require `target == context.current_account_id` (mirroring the `target.as_str() != receiver_id.as_str()` check already used for `FUNCTION_CALL_SELECTOR`/`TRANSFER_SELECTOR`), rejecting the transaction with a `RelayerError::InvalidTarget` otherwise. Equivalently, since these are documented as "Self" actions, `parse_rlp_tx_to_action`'s `SelfNearNativeAction` handling should be widened to override/reject the action whenever `target_kind != TargetKind::CurrentAccount`, not just when it is `TargetKind::EthImplicit`.

### Proof of Concept
1. Alice owns eth-implicit account `alice_eth` and previously added relayer R's public key `pk_R` as a `FunctionCall` access key via `rlp_execute` (per `test_wallet_contract_interaction`, `AddKey` grants receiver `alice_eth`, methods `["rlp_execute"]`). [9](#0-8) 
2. Alice later wants to revoke R by signing an Ethereum-style `DeleteKey(pk_R)` transaction and asking relayer R (or any relayer) to submit it via `alice_eth.rlp_execute(target, tx_bytes_b64)`.
3. Because `DELETE_KEY_SELECTOR` calldata carries only `public_key_kind`/`public_key` (no receiver binding), and `target` is a plain unsigned call argument the relayer supplies, relayer R submits the call with `target = "some-other-account.near"` (a `TargetKind::OtherNearAccount`) instead of `target = "alice_eth"`.
4. `parse_rlp_tx_to_action` does not override the action (override only applies for `TargetKind::EthImplicit`), so the resulting `near_action::Action::DeleteKey` is dispatched via `action_to_promise("some-other-account.near", DeleteKey(pk_R))`, i.e., against an account Alice never intended, while her `alice_eth` nonce is still consumed. R's `FunctionCall` key on `alice_eth` remains untouched and Alice cannot resubmit the same signed transaction (nonce already advanced).

fn action_to_promise(target: AccountId, action: near_action::Action) -> Result<Promise, Error> {
    match action {
        near_action::Action::FunctionCall(action) => Ok(Promise::new(target).function_call(
            action.method_name,
            action.args,
            action.deposit,
            action.gas,
        )),
        near_action::Action::Transfer(action) => Ok(Promise::new(target).transfer(action.deposit)),
        near_action::Action::AddKey(action) => match action.access_key.permission {
            near_action::AccessKeyPermission::FullAccess => {
                Err(Error::User(UserError::UnsupportedAction(UnsupportedAction::AddFullAccessKey)))
            }
            near_action::AccessKeyPermission::FunctionCall(access) => Ok(Promise::new(target)
                .add_access_key_allowance_with_nonce(
                    action.public_key,
                    access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited),
                    access.receiver_id,
                    access.method_names.join(","),
                    action.access_key.nonce,
                )),
        },
        near_action::Action::DeleteKey(action) => {
            Ok(Promise::new(target).delete_key(action.public_key))
        }
    }

### Wallet Contract

The Wallet Contract (see [NEP-518](https://github.com/near/NEPs/issues/518) for more details) functions as a user account and is designed to receive, validate, and execute Ethereum-compatible transactions on the NEAR blockchain.

Without going into details, an Ethereum-compatible wallet user sends a transaction to an RPC endpoint, which wraps it and passes it to the Wallet Contract (on the target account) as an `rlp_execute(target: AccountId, tx_bytes_b64: Vec<u8>)` contract call.
Then, the contract parses `tx_bytes_b64` and verifies it is signed with the private key matching the target [ETH-implicit account ID](#eth-implicit-account-id) on which the contract is hosted.

Under the hood, the transaction encodes a NEAR-native action. Currently supported actions are:

- Transfer (from ETH-implicit account).
- Function call (call another contract).
- Add `AccessKey` with `FunctionCallPermission`. This allows adding a relayer's public key to an ETH-implicit account, enabling the relayer to pay the gas fee for transactions from this account. Still, each transaction has to be signed by the owner of the account (corresponding Secp256K1 private key).
- Delete `AccessKey`.
