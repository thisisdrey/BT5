### Title
Out-of-bounds Zip64 extra-field read from attacker-crafted archive metadata mismatch - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`singlejar`'s zip/jar parsing classes `CDH` (Central Directory Header) and `LH` (Local Header) compute the index into a `Zip64ExtraField`'s 64-bit attribute array purely from the 32-bit sentinel values (`0xFFFFFFFF`) of the *separate*, independently-attacker-controlled 32-bit size/offset fields, without ever checking that index against the Zip64 field's own declared `attr_count()`. A crafted zip/jar entry can set the 32-bit sentinels to request an attribute index that the actual (bounds-checked-only-for-itself) `Zip64ExtraField` never allocated, causing an out-of-bounds heap/mmap read.

### Finding Description
`CDH::compressed_file_size()` and `CDH::local_header_offset()` derive the array index passed to `Zip64ExtraField::attr64(index)` from unrelated fields: [1](#0-0) [2](#0-1) 

`Zip64ExtraField::attr64(int index)` performs no bounds checking against how many 8-byte attributes are actually present (`attr_count()`, derived from the field's own `payload_size()`): [3](#0-2) 

The only bounds check that exists is in `ExtraField::find`, which verifies that the *declared* Zip64 field (header + its own `payload_size`) fits inside the CDH's `extra_fields_length()` region — it says nothing about whether the number of attributes matches what the 32-bit sentinel bits imply: [4](#0-3) 

Per the ZIP64 spec, the extra field is supposed to contain exactly the attributes whose 32-bit counterpart is `0xFFFFFFFF`, in a fixed order (uncompressed, compressed, offset). Nothing in the parser enforces that this invariant actually holds between the two independently-supplied pieces of attacker-controlled metadata:
1. The 32-bit `uncompressed_file_size32_` / `compressed_file_size32_` / `local_header_offset32_` sentinel values in the fixed CDH/LH struct.
2. The Zip64 extra field's own `payload_size` (which determines `attr_count()`).

An attacker who controls the bytes of a `.zip`/`.jar` (e.g. one processed by `singlejar` — Bazel's jar-merging tool used to build `deploy.jar`/`java_binary` outputs, reachable via `InputJar::NextEntry`, `OutputJar::AddJar`, `output_jar.cc`, `combiners.cc`, `input_jar.cc`, all of which call these `zfield_has_ext64`-based accessors): [5](#0-4) 

can craft a CDH entry where:
- `uncompressed_file_size32_ = 0xFFFFFFFF` and `compressed_file_size32_ = 0xFFFFFFFF` (both request the 64-bit extension), but
- the accompanying `Zip64ExtraField`'s `payload_size` is only `8` (i.e. `attr_count() == 1`, holding a single attribute instead of the two the sentinels imply).

`compressed_file_size()` will then compute `index = zfield_has_ext64(uncompressed_file_size32()) == 1` and call `z64->attr64(1)`, reading 8 bytes starting at offset 12 from the `Zip64ExtraField` header — 8 bytes past the field's own allocated/declared payload. Because `ExtraField::find` only validated that the *declared* 12-byte field fits inside `extra_fields()`..`extra_fields()+extra_fields_length()`, the extra read at offset 12–19 can land past `extra_fields_length()` (i.e., past the CDH's own bounds) and, if this is the last central-directory entry, past the mmap'd input file region entirely — an out-of-bounds heap/mmap read. The analogous 3-attribute case in `local_header_offset()` (index up to `2`) makes the OOB window even larger.

This is the structural analog of the reported Solidity issue: a security-relevant numeric quantity (`id`/array index) is derived from one attacker-controlled field and used to index storage (`isSent` mapping / `attr_[]` array) sized according to a *different*, independently attacker-controlled field, with no cross-validation between the two, producing corrupted/out-of-range access.

### Impact Explanation
Processing a maliciously crafted zip/jar with `singlejar` (or any consumer of `zip_headers.h`, e.g. `output_jar.cc`, `input_jar.cc`, `combiners.cc`) can read memory outside the bounds of the mapped input file / central-directory buffer. This is a memory-safety violation (out-of-bounds read) in a native (C++) tool that is part of Bazel's Java build pipeline, and it is triggered purely by the *content* of an untrusted archive — a per-archive checksum on the whole downloaded file does not prevent this, since the checksum only guarantees byte-for-byte integrity of the download, not internal structural consistency of the ZIP64 metadata inside it. The read can crash the process (denial of service for the build) or, depending on adjacent memory layout, leak adjacent bytes into computed sizes/offsets that influence subsequent copies (`WriteBytes`, `memcpy` calls using `compressed_file_size()`/`uncompressed_file_size()`/`local_header_offset()`), which is a genuine "untrusted content stays data" containment violation, not merely a crash.

### Likelihood Explanation
Any consumer of an attacker-influenced `.jar`/`.zip` (e.g. a jar coming from a dependency published by an untrusted party, or a fixture bundled into a repository built by CI from an untrusted branch) that gets passed to `singlejar --sources` is affected. No special privileges are needed by the attacker beyond controlling the content of a jar/zip that ends up as a build input; crafting the specific mismatched sentinel/`payload_size` combination is straightforward with any hex editor once a standard "huge entry" Zip64 jar (as already exercised by `zip_headers_test.cc` / `zip64_huge_entry_test.sh`) is used as a base.

### Recommendation
In `Zip64ExtraField::attr64` (or at each call site in `CDH`/`LH`), validate `index < attr_count()` before dereferencing, and treat a mismatch between the 32-bit sentinel bits and the extra field's actual `attr_count()` as a corrupt/invalid archive, failing the parse instead of returning attacker/OOB-influenced data. This should mirror the existing bounds check already done in `ExtraField::find`, but applied to the *attribute count* implied by the 32-bit fields, not just the raw byte extent of the extra field.

### Proof of Concept
Extend `src/tools/singlejar/zip_headers_test.cc` (which already builds `Zip64ExtraField` byte arrays manually, e.g. lines 68-134 and 193-280) with a case that:
1. Sets `cdh->compressed_file_size32(0xFFFFFFFF)` and `cdh->uncompressed_file_size32(0xFFFFFFFF)`.
2. Attaches a `Zip64ExtraField` extra-fields blob with `payload_size = 8` (single attribute) sized to end exactly at `extra_fields_length()`, with a guard/poison byte immediately after the CDH's declared extra-fields region (as the existing tests use `kPoison` sentinel bytes, e.g. line 61/132).
3. Calls `cdh->compressed_file_size()` and observes that it reads `attr64(1)`, returning the poison/adjacent bytes located past the declared 12-byte Zip64 field / past `extra_fields_length()`, rather than failing or returning a defined error — demonstrating the out-of-bounds read (verifiable under ASan as a heap-buffer-overflow).

  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
