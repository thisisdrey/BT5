### Title
Missing Slippage Protection in `ExchangeWithdrawContract`/`ExchangeInjectContract` allows front-running the TRC10 Bancor-style Exchange — ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
The TRC10 built-in Exchange (Bancor-style constant-reserve AMM) exposes `ExchangeTransactionContract` with an explicit `expected` (minimum-received) field that is enforced at execution time, giving proper slippage protection for trades. However, the sibling operations `ExchangeInjectContract` (add liquidity) and `ExchangeWithdrawContract` (remove liquidity) carry no such minimum/maximum bound at all — the counter-token amount is always computed from whatever pool ratio exists at the moment the transaction actually executes, with zero tolerance parameter supplied by the caller. This is the same missing-slippage-protection class of bug flagged in the external Bancor report, but reachable purely on-chain via signed transactions rather than an external DEX integration.

### Finding Description
`ExchangeTransactionContract` protects the trader with a caller-supplied `expected` value, checked in `ExchangeTransactionActuator.doValidate`: [1](#0-0) 

By contrast, `ExchangeInjectContract` and `ExchangeWithdrawContract` only carry `owner_address`, `exchange_id`, `token_id`, `quant` — no expected/min/max field exists in the protobuf definitions: [2](#0-1) 

`ExchangeWithdrawActuator.doValidate`/`execute` recompute `anotherTokenQuant` strictly from the exchange's *current* on-chain `firstTokenBalance`/`secondTokenBalance` ratio at validation/execution time, with no comparison against any value the signer committed to when creating the transaction: [3](#0-2) [4](#0-3) 

The same pattern exists for injection — `anotherTokenQuant` is derived purely from the pool ratio present when the transaction lands, with no user-set bound on how much of the counter-token can be pulled from the caller's account: [5](#0-4) [6](#0-5) 

Because `ExchangeTransactionContract` is a public, unprivileged, broadcastable contract type that anyone can submit to move the pool ratio (subject only to `ContractValidateException` checks, not to permissioning tied to the exchange creator), an attacker can observe a pending `ExchangeWithdrawContract`/`ExchangeInjectContract` in the mempool and front-run it with one or more `ExchangeTransactionContract` trades to shift `firstTokenBalance`/`secondTokenBalance` before the withdraw/inject executes — exactly the front-running scenario described in the referenced Bancor/Uniswap report, except here there is no `expected`-style parameter at all to bound the damage (the Bancor report's issue was merely a fixed 1-wei bound; here the bound is completely absent).

### Impact Explanation
An exchange creator issuing `ExchangeWithdrawContract` can be forced to receive materially less of the counter-token than the pool ratio implied when they signed the transaction, or an `ExchangeInjectContract` can be forced to debit a larger amount of the counter-token than intended, both due to ratio manipulation via front-run `ExchangeTransactionContract` trades. This is a concrete case of unauthorized value extraction / economic loss for the exchange's liquidity provider, reachable purely from unprivileged, publicly-broadcastable transactions (no special SR/witness/committee access needed).

### Likelihood Explanation
Both the front-running primitive (`ExchangeTransactionContract`) and the victim operations (`ExchangeInjectContract`/`ExchangeWithdrawContract`) are ordinary user-facing contract types processed through the standard actuator pipeline; any account can observe pending transactions and race them within the same block window, so the precondition (an active TRC10 exchange plus a pending inject/withdraw) is the only real constraint.

### Recommendation
Add an explicit slippage-tolerance field (e.g., `expected`/`minAnotherTokenQuant` for withdraw, `maxAnotherTokenQuant` for inject) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce it in `ExchangeInjectActuator.doValidate`/`ExchangeWithdrawActuator.doValidate` analogous to the existing check in `ExchangeTransactionActuator.doValidate` (`anotherTokenQuant < tokenExpected`).

### Proof of Concept
1. Attacker monitors the mempool for a pending `ExchangeWithdrawContract` from the exchange creator on exchange `X` with `tokenId=A`, `quant=Q`.
2. Attacker broadcasts an `ExchangeTransactionContract` trade against the same exchange `X` that shifts `firstTokenBalance`/`secondTokenBalance` so that, when the creator's withdraw executes, the computed `anotherTokenQuant` in `ExchangeWithdrawActuator.execute` (lines 77-89) is significantly lower than what the ratio implied at signing time.
3. Because `ExchangeWithdrawContract` has no `expected`/minimum field to validate against (unlike `ExchangeTransactionContract`'s `tokenExpected` check at lines 217-221 of `ExchangeTransactionActuator.java`), the withdrawal proceeds and credits the creator with the reduced `anotherTokenQuant`, with no on-chain mechanism to reject the unfavorable outcome.
