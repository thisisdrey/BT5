## Title
Fee bypass on NEP-245/IMT token swaps via unit-delta decomposition — `TokenDiff::token_fee` (File: contracts/defuse/core/src/intents/token_diff.rs)

## Summary
`TokenDiff::execute_intent` charges the protocol fee only on a per-intent basis, and `TokenDiff::token_fee` hardcodes a fee exemption for NEP-245/IMT tokens whenever the *per-intent* delta magnitude is `<= 1`. Because a signer can submit an arbitrary number of independently-signed `TokenDiff` intents in a single `execute_intents`/`simulate_intents` call, a trade of any total size in a NEP-245 (or IMT) denominated asset can be decomposed into many unit-magnitude (`|delta| == 1`) legs, each of which is individually exempt from the protocol fee, while the batch as a whole still nets to zero and passes the invariant check.

## Finding Description
`TokenDiff::execute_intent` computes and collects protocol fees per-intent: [1](#0-0) 

The fee rate applied is determined by `TokenDiff::token_fee`, which hardcodes an assumption that NEP-245/IMT deltas of magnitude `<= 1` are NFT-like and therefore fee-exempt: [2](#0-1) 

This is the same bug class as the external report: a hardcoded parameter/threshold ("NFTs and MTs with `|delta| <= 1` don't pay fees") is baked into the swap-fee logic without accounting for the fact that NEP-245 `TokenId`s in this protocol are also used to represent **fungible** value (e.g. FT balances wrapped as `nep245:<contract>:<nep141-asset>` inside `intents.near`, as used throughout the escrow-swap and nested-defuse flows). For such tokens, `amount == 1` is not a special "one indivisible NFT" case — it is just the smallest unit of an arbitrarily-sized fungible balance.

Because the engine executes a whole `Vec<MultiPayload>` batch and only enforces global conservation (`sum of deltas == 0` after fee closures) at `finalize()`/invariant-check time, not per-token-per-signer aggregate fee computation, a signer (or coordinated signer set) can split what is economically a single large NEP-245/IMT trade into `N` separate signed `TokenDiff` intents, each with `delta == ±1` for the same `token_id`. Each individual intent hits the `amount <= 1` branch and is charged `Pips::ZERO`, even though the aggregate notional moved across the batch can be arbitrarily large.

This breaks the "fees owed versus fees collected" binding: the fee that *should* be owed on the net token flow moved by the signer is bypassed entirely by restructuring the same economic trade as many minimal legs, all settled atomically in one `execute_intents` call. [3](#0-2) 

## Impact Explanation
This falls under the Critical impact category "fees bypassed or over-collected." Any solver or user that routes NEP-245/IMT-denominated liquidity through this contract can avoid paying the protocol fee on such swaps by decomposing them into unit legs, directly reducing protocol/fee-collector revenue that the fee mechanism is intended to enforce. Since NEP-245 is used pervasively to represent wrapped fungible balances (not only genuine 1-of-1 NFTs), this is not a narrow edge case restricted to NFTs.

## Likelihood Explanation
Exploitation only requires the attacker to sign `N` extra `TokenDiff` intents with the same counterparty structure they would already need for a normal swap, and submit them together in one `execute_intents` call — no privileged role, no relayer key, and no protocol misconfiguration is required. The practical size of `N` is bounded by NEAR's per-transaction gas limit and signature-verification cost, which limits (but does not eliminate) the magnitude of fees that can be evaded per transaction; the attack can be repeated across multiple transactions to scale the bypassed fee amount.

## Recommendation
Do not gate the fee exemption on the per-intent delta magnitude for NEP-245/IMT tokens. Either:
- Remove the `amount <= 1` exemption for NEP-245/IMT entirely and instead exempt based on an explicit token-classification (e.g., a flag/metadata indicating "non-fungible" vs "fungible-wrapped"), or
- Aggregate deltas per `(signer_id, token_id)` across the whole intents batch before computing/charging the fee, so that splitting a trade into multiple legs cannot change the fee owed.

## Proof of Concept
1. A NEP-245 asset `T` wraps a fungible NEP-141 balance inside `intents.near` (as done for escrow-swap flows: `Nep245TokenId::new(verifier_contract, nep141_asset_id)`).
2. Attacker (as solver) wants to trade `10_000` units of `T` for token `T2` with a matching counterparty.
3. Instead of one `TokenDiff` intent with `diff = { T: -10_000, T2: +X }`, the attacker signs `10_000` separate `TokenDiff` intents, each `diff = { T: -1, T2: +x }` (`x = X/10_000`), matched by an equal number of counterparty intents.
4. All `20_000` signed intents are submitted together via `execute_intents`/`simulate_intents`.
5. `TokenDiff::token_fee` evaluates `amount == 1` for every leg on `T`, returning `Pips::ZERO` for each (per `contracts/defuse/core/src/intents/token_diff.rs:206-217`), so no protocol fee is ever collected on the `10_000`-unit trade, whereas a single non-decomposed intent of the same net size would have paid `protocol_fee.fee_ceil(10_000)`.
