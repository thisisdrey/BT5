## Analysis: NTFS reparse-point buffer parsing in `os`/`syscall` (Windows)

The Linux CVE fixes a missing bounds check on an attacker-influenced `next_entry_offset` field before it's used to index into an EA-entry buffer. The closest matching pattern in this Go repository is in the Windows reparse-point (symlink/junction) parsing code, which reads attacker-influenced `SubstituteNameOffset`/`SubstituteNameLength`/`PrintNameOffset`/`PrintNameLength` fields out of a kernel-returned `REPARSE_DATA_BUFFER` and uses them directly as slice indices into an oversized fixed-size array cast, without validating them against the actual returned buffer size.

### Finding Description

`os.Readlink`/`filepath.EvalSymlinks` on Windows call `readReparseLinkHandle`, which issues `FSCTL_GET_REPARSE_POINT` into a fixed `MAXIMUM_REPARSE_DATA_BUFFER_SIZE` (16384-byte) buffer and then dispatches on `rdb.ReparseTag` to `SymbolicLinkReparseBuffer.Path()` or `MountPointReparseBuffer.Path()`: [1](#0-0) 

Both `Path()` implementations compute byte offsets from the **untrusted, kernel/filesystem-supplied** `SubstituteNameOffset`/`SubstituteNameLength` fields and slice a pointer cast to a fixed `[0xffff]uint16` array — 8x larger than the actual 16384-byte allocation — with no check that the computed range fits inside the data actually returned (`bytesReturned`) or inside `ReparseDataLength`: [2](#0-1) [3](#0-2) 

The plain `syscall.Readlink` implementation has the identical unchecked pattern: [4](#0-3) 

In all three cases, `SubstituteNameOffset`/`SubstituteNameLength` (each `uint16`, max 65535) are taken straight from the reparse-point data on disk and used to build a slice range (`n1:n2`) against a *pretend* `[0xffff]uint16` array, with no validation that this range lies within the actual bytes returned by `DeviceIoControl`. This is the same bug class as the NTFS EA issue: an offset/length pair from an on-disk structure is trusted and used to index into adjacent data before checking it stays within the bounds of what was actually read.

### Impact Explanation

If a reparse point (directory junction/mount point, which does **not** require `SeCreateSymbolicLinkPrivilege`, or a symlink) is created with a `SubstituteNameOffset`/`SubstituteNameLength` inconsistent with the actual link-target bytes present in the reparse buffer, a victim later calling `os.Readlink`, `filepath.EvalSymlinks`, `os.Lstat`-based directory walks, or extracting an archive that materializes such a reparse point, will have Go read out-of-bounds heap memory adjacent to the 16KB `rdbbuf` and return it as part of the resolved "target" string — a heap information-disclosure primitive. Additionally, `SubstituteNameOffset+SubstituteNameLength` is computed in `uint16` arithmetic and can overflow/wrap, producing `n2 < n1`, which will panic with "slice bounds out of range" — a crash triggerable by a crafted reparse point consumed during an ordinary filesystem walk.

### Likelihood Explanation

The reachability depends on whether the NTFS/reparse filesystem driver itself validates `SubstituteNameOffset`/`SubstituteNameLength` consistency when a reparse point is *set* via `FSCTL_SET_REPARSE_POINT` (which Go's own `os.Symlink`/junction-creation paths always construct consistently, e.g. [5](#0-4) ). I could not confirm from this repository alone whether the Windows kernel enforces strict consistency for third-party-written reparse buffers (e.g., those written by non-Go tools, malicious archives that fabricate raw reparse data, or a crafted removable/network volume) versus only validating on the read/query path. Go's own parsing code performs no defensive validation regardless of what the kernel does, which is the analog to the missing-bounds-check fixed upstream in NTFS's EA handling.

### Recommendation

Before computing `n1`/`n2` in `SymbolicLinkReparseBuffer.Path()` / `MountPointReparseBuffer.Path()` and in `syscall.Readlink`, validate that `SubstituteNameOffset`, `SubstituteNameLength` (and `PrintNameOffset`/`PrintNameLength`) are non-overflowing and fall entirely within the number of bytes actually returned by `DeviceIoControl` (`bytesReturned`) and within `ReparseDataLength`, returning an error (e.g. wrapped `syscall.EINVAL`) otherwise, instead of trusting the on-disk header fields to index into the oversized `[0xffff]uint16` pointer cast.

### Proof of Concept

A minimal reproduction requires constructing a reparse point whose header declares `SubstituteNameOffset`/`SubstituteNameLength` inconsistent with the actual buffer contents (e.g. via raw `DeviceIoControl(FSCTL_SET_REPARSE_POINT, ...)` rather than Go's `os.Symlink`) and then calling:

```go
func TestReadlinkOOB(t *testing.T) {
    // link is a pre-crafted junction/symlink whose on-disk
    // REPARSE_DATA_BUFFER has SubstituteNameOffset/Length set beyond
    // the bytes actually returned by FSCTL_GET_REPARSE_POINT.
    _, err := os.Readlink(link)
    // Expect: no OOB read / disclosed heap bytes, or a bounds error —
    // not a panic and not attacker-influenced adjacent memory in the result.
    if err == nil {
        t.Fatal("expected bounds validation error, got success")
    }
}
```

I was unable to fully confirm within this index whether the Windows kernel itself rejects such inconsistent reparse buffers on write, which is required to establish end-to-end reachability by an unprivileged attacker. Given this open verification gap, I cannot assert this with full confidence as a proven vulnerability — it is presented as the strongest structural analog found, with the caveat above.

func readReparseLinkHandle(h syscall.Handle) (string, error) {
	rdbbuf := make([]byte, syscall.MAXIMUM_REPARSE_DATA_BUFFER_SIZE)
	var bytesReturned uint32
	err := syscall.DeviceIoControl(h, syscall.FSCTL_GET_REPARSE_POINT, nil, 0, &rdbbuf[0], uint32(len(rdbbuf)), &bytesReturned, nil)
	if err != nil {
		return "", err
	}

	rdb := (*windows.REPARSE_DATA_BUFFER)(unsafe.Pointer(&rdbbuf[0]))
	switch rdb.ReparseTag {
	case syscall.IO_REPARSE_TAG_SYMLINK:
		rb := (*windows.SymbolicLinkReparseBuffer)(unsafe.Pointer(&rdb.DUMMYUNIONNAME))
		s := rb.Path()
		if rb.Flags&windows.SYMLINK_FLAG_RELATIVE != 0 {
			return s, nil
		}
		return normaliseLinkPath(s)
	case windows.IO_REPARSE_TAG_MOUNT_POINT:
		return normaliseLinkPath((*windows.MountPointReparseBuffer)(unsafe.Pointer(&rdb.DUMMYUNIONNAME)).Path())
	default:
		// the path is not a symlink or junction but another type of reparse
		// point
		return "", syscall.ENOENT
	}

type SymbolicLinkReparseBuffer struct {
	// The integer that contains the offset, in bytes,
	// of the substitute name string in the PathBuffer array,
	// computed as an offset from byte 0 of PathBuffer. Note that
	// this offset must be divided by 2 to get the array index.
	SubstituteNameOffset uint16
	// The integer that contains the length, in bytes, of the
	// substitute name string. If this string is null-terminated,
	// SubstituteNameLength does not include the Unicode null character.
	SubstituteNameLength uint16
	// PrintNameOffset is similar to SubstituteNameOffset.
	PrintNameOffset uint16
	// PrintNameLength is similar to SubstituteNameLength.
	PrintNameLength uint16
	// Flags specifies whether the substitute name is a full path name or
	// a path name relative to the directory containing the symbolic link.
	Flags      uint32
	PathBuffer [1]uint16
}

// Path returns path stored in rb.
func (rb *SymbolicLinkReparseBuffer) Path() string {
	n1 := rb.SubstituteNameOffset / 2
	n2 := (rb.SubstituteNameOffset + rb.SubstituteNameLength) / 2
	return syscall.UTF16ToString((*[0xffff]uint16)(unsafe.Pointer(&rb.PathBuffer[0]))[n1:n2:n2])
