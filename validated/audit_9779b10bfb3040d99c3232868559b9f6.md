### Title
Unauthenticated `/shutdown` HTTP endpoint permanently halts signer event-receiver main loop - ([File: libsigner/src/events.rs])

### Summary
The signer's `SignerEventReceiver::next_event` handles `POST /shutdown` by unconditionally setting `stop_signal` to `true` and returning `EventError::Terminated`, with no authentication, secret, or origin check beyond matching the URL string. Any TCP peer that can reach the bound event port can send this single crafted HTTP request and permanently stop the signer's event-processing `main_loop`, which then exits and never restarts.

### Finding Description
The claimed equality — "who may terminate the receiver == the process's own `SignerStopSignaler`" — is broken. `SignerStopSignaler::send` legitimately triggers shutdown by connecting to `self.local_addr` and issuing `POST /shutdown` [1](#0-0) , but the receiving code makes no distinction between this internal signaler and an arbitrary external caller: in `next_event`, once the URL matches `/shutdown`, the handler stores `true` into `stop_signal` and returns `Err(EventError::Terminated)` unconditionally [2](#0-1) . There is no comparison against a secret, token, source IP/loopback check, or any credential — only a URL string equality test performed after a bare method check [3](#0-2) .

`main_loop` then observes `Err(EventError::Terminated)` and `break`s out of the loop permanently [4](#0-3) , and `is_stopped()` will return `true` from then on (checked before the next call to `next_event`) [5](#0-4) [6](#0-5) . There is no restart path in this loop — the signer's event-processing thread is dead until the whole process is restarted.

The attacker's exact message: a raw HTTP/1.1 request `POST /shutdown` with any body (even empty), sent to the bound TCP port. `tiny_http`'s `HttpServer::recv()` accepts and parses this like any other request; no header/token verification occurs before the URL comparison at line 443.

### Impact Explanation
A single unauthenticated HTTP POST permanently disables the signer's event ingestion loop (`main_loop`), meaning the signer stops receiving `StackerDB` chunk events, burn-block events, and block-validation responses from the node. This is a one-message, remotely-triggered denial of service against a signer, matching the "Critical - remote crash/unauthenticated DoS from few messages" category. It is trivially repeatable against every reachable signer instance.

### Likelihood Explanation
The only precondition is TCP reachability to the signer's event-receiver bind address/port. The severity of this depends entirely on whether that port is exposed beyond loopback/localhost in typical deployments — the question's own precondition states "only the local node is expected to be able to reach this port." I was not able to fully confirm in this pass how operators are expected to configure/firewall this bind address (e.g., whether `stacks-signer`'s config defaults to binding `127.0.0.1` or a routable interface), since the config lookup for the event-observer endpoint (`stacks-signer/src/config.rs`) was not fully inspected before the tool budget ran out. This is a meaningful gap: if the endpoint is only ever bound to loopback and firewalled, the "remote attacker" precondition required by the audit rules would not hold, and the finding would be out of scope. Given the code-level lack of any authentication check on `/shutdown` regardless of binding, and given that this port is explicitly designed to receive POSTs from the node process (implying it is a network-facing HTTP listener rather than a purely in-process construct), the vulnerability is real at the code level, but I cannot fully certify the network-reachability precondition without further review of deployment/config defaults.

### Recommendation
Require the `/shutdown` endpoint to authenticate the caller, e.g., by requiring a shared secret/token known only to the process (generated by the receiver at bind-time and included by `SignerStopSignaler::send`), or by binding the listener to loopback only and rejecting connections from non-loopback source addresses at the HTTP layer before matching the URL. At minimum, verify `request.remote_addr()` is loopback before honoring `/shutdown`.

### Proof of Concept
```rust
// libsigner/src/events.rs (test module)
use std::net::{TcpListener, TcpStream};
use std::io::Write;
use std::sync::atomic::Ordering;

#[test]
fn test_unauthenticated_remote_shutdown() {
    let mut receiver: SignerEventReceiver<StacksBlockEvent> = SignerEventReceiver::new(false);
    let addr = "127.0.0.1:0".parse().unwrap();
    let bound = receiver.bind(addr).unwrap();

    // Simulate an arbitrary remote peer (not the process's own SignerStopSignaler)
    let mut stream = TcpStream::connect(bound).unwrap();
    let body = "attacker-controlled";
    let req = format!(
        "POST /shutdown HTTP/1.1\r\nHost: {}\r\nConnection: close\r\nContent-Length: {}\r\n\r\n{}",
        bound, body.len(), body
    );
    stream.write_all(req.as_bytes()).unwrap();

    // Handler processes it exactly like the legitimate signaler would
    let result = receiver.next_event();
    assert!(matches!(result, Err(EventError::Terminated)));
    assert!(receiver.is_stopped());

    // Subsequent calls always short-circuit to Terminated -- main_loop is permanently halted
    let result2 = receiver.next_event();
    assert!(matches!(result2, Err(EventError::Terminated)));
}
```
This test opens a bare `TcpStream` (representing an arbitrary remote peer with no credentials) and issues the crafted `/shutdown` POST; the assertion confirms `stop_signal` was flipped and `main_loop` would `break` at [4](#0-3)  from the same code path exercised at [2](#0-1) .
