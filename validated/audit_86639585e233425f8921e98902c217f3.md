Audit Report

## Title
No slippage protection when swapping refunded weight fees back to the original asset - (File: `cumulus/primitives/utility/src/lib.rs`)

## Summary
`SwapFirstAssetTrader::refund_weight` swaps unused fee credit held in the `Target` asset back into the asset the user originally paid with, calling `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min` hardcoded to `None`, so the AMM's execution-time output is accepted unconditionally regardless of price movement [1](#0-0) . This is a real, verified gap: the codebase's own analogous refund path in `pallet-asset-conversion-tx-payment` quotes a price first and passes a computed `Some(refund_asset_amount)` as the floor, showing the missing-bound pattern here is inconsistent with the established safe pattern elsewhere in the repo.

## Finding Description
`SwapFirstAssetTrader::buy_weight` swaps a user's arbitrary payment asset into `Target` via `SwapCredit::swap_tokens_for_exact_tokens` and accumulates the `Target`-denominated proceeds in `self.total_fee` [2](#0-1) . When the XCM executor determines that less weight was consumed than was paid for, `refund_weight` extracts the corresponding portion of `total_fee` and swaps it back to the original asset:
```rust
let refund = self.total_fee.extract(refund_amount);
let refund = match SwapCredit::swap_exact_tokens_for_tokens(
    vec![Target::get(), refund_swap_asset],
    refund,
    None,
) {
``` [1](#0-0) 

`pallet-asset-conversion`'s `do_swap_exact_credit_tokens_for_tokens` only enforces `ProvidedMinimumNotSufficientForSwap` when `amount_out_min` is `Some`; with `None` the check is skipped entirely and whatever `amount_out` the pool curve produces at execution time is accepted. `quote_weight` in the same file does call `QuotePrice::quote_price_tokens_for_exact_tokens` before charging, but `refund_weight` never quotes an expected rate for the return leg, unlike the established safe pattern in `SwapAssetAdapter::correct_and_deposit_fee`, which calls `quote_price_exact_tokens_for_tokens` and passes the result as `Some(refund_asset_amount)` before executing the refund swap.

Because `buy_weight` and any instructions inside the same XCM message program execute between the fee charge and the refund, a message sender who controls the program's instructions (e.g., an `ExchangeAsset` or `Transact` call into the same pool) can move the `Target`/`refund_swap_asset` pool reserves within the same message execution, then have `refund_weight` execute the unbounded swap-back at the manipulated rate — extracting value from the pool's liquidity providers with no `ProvidedMinimumNotSufficientForSwap` protection possible, since no minimum was ever supplied.

## Impact Explanation
This is a concrete, named-value corruption: the `amount_out` returned by the refund-leg swap is not bound to any expected value, allowing the actual refunded balance in `refund_swap_asset` to be manipulated below (or, from the attacker's perspective, favorably above) the fair-value amount, silently draining value from the backing AMM pool's liquidity providers or from XCM message senders depending on price direction. This aligns with the "theft or unbacked ... unlock" / value-conservation class of impact for `cumulus-primitives-utility`, since a live-scope `WeightTrader` component that settles fee refunds through an AMM must conserve value on each swap leg and currently does not for the refund leg.

## Likelihood Explanation
Exploitability requires only a runtime that wires `SwapFirstAssetTrader` to a live `SwapCredit`/`QuotePrice` implementation (e.g., `pallet-asset-conversion`) as (part of) its `WeightTrader`, and an XCM message that overestimates weight, pays fees in a non-`Target` asset, and includes instructions that move the same pool's reserves before the refund executes — all achievable by an ordinary, unprivileged message sender with no relayer, validator, or off-chain component involved. The refund path runs on essentially every over-weighted XCM message using this trader, making repeated exploitation straightforward once such a chain configuration exists.

## Recommendation
Before calling `SwapCredit::swap_exact_tokens_for_tokens` in `refund_weight`, quote an expected output via `QuotePrice::quote_price_exact_tokens_for_tokens(Target::get(), refund_swap_asset, refund_amount, true)` and pass `Some(expected_amount)` (optionally tolerance-adjusted) as `amount_out_min`, mirroring `SwapAssetAdapter::correct_and_deposit_fee`. If the quote fails or the swap cannot meet the minimum, return the credit to `total_fee` and skip the refund rather than executing an unbounded-slippage swap.

## Proof of Concept
1. Configure a runtime with `SwapFirstAssetTrader<Target, AssetConversion, ...>` as the `WeightTrader`, backed by a live `pallet-asset-conversion` pool for `Target`/`AssetX`.
2. Craft an XCM message that pays fees in `AssetX` with overestimated weight (triggering `buy_weight` to swap `AssetX -> Target` and accumulate `total_fee`), includes an `ExchangeAsset` (or equivalent) instruction that trades against the same `Target`/`AssetX` pool to move its reserves unfavorably for the refund direction, then completes execution so `refund_weight` fires.
3. Observe `refund_weight` invoke `SwapCredit::swap_exact_tokens_for_tokens(vec![Target::get(), refund_swap_asset], refund, None)` at `cumulus/primitives/utility/src/lib.rs:540-544`, succeeding with a reduced or manipulated `refund` amount with no `ProvidedMinimumNotSufficientForSwap` error, since no `amount_out_min` was enforced.
