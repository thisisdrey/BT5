### Title
Unbounded heap growth of `Manager.ownerAddressSet` via repeated multi-sign transactions - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
`Manager` maintains an in-memory `Set<String> ownerAddressSet` that accumulates the hex-encoded owner address of every transaction that carries a non-default `permission_id` (a "multi-sign transaction"). Entries are added on every call to `processTransaction()` but the set has no bounded eviction policy tied to normal block processing, so an attacker who can broadcast transactions with a non-zero `permission_id` can grow this collection without limit, analogous to the libde265 bug where orphaned slice headers are attached to a long-lived object and never freed.

### Finding Description
The field is declared as an unbounded `HashSet`: [1](#0-0) 

Every time a transaction is processed (during `pushTransaction`, block generation, or block application via `processTransaction`), if the transaction is classified as a multi-sign transaction, its owner address is added to this set: [2](#0-1) 

This same set is also referenced in `getVerifyTxs` (building a working copy each time), confirming it is a persistent, growing, process-lifetime structure rather than a per-block scratch set: [3](#0-2) 

The classification `isMultiSignTransaction` is driven purely by the transaction carrying a non-default `permission_id` in its `Contract` — any account holder can enable this on their own account cheaply via a self-signed `AccountPermissionUpdateContract`, after which every subsequent transaction from that account (or from any freshly created account performing the same setup) that sets a non-zero `permission_id` inserts a new, effectively attacker-chosen string key into `ownerAddressSet`. Because account creation and permission updates are ordinary unprivileged operations, an attacker can mint unlimited distinct addresses and drive unlimited unique insertions into this set over the life of the node process, mirroring the "orphaned/never-freed retained state attached to a long-lived object" bug class described in the report.

### Impact Explanation
`ownerAddressSet` is a live field of the singleton `Manager` bean, held for the lifetime of the full node process. Continuous insertion of unique hex-address strings (40+ characters each, plus `HashSet` bucket overhead) causes steady, attacker-controlled heap growth that is never reclaimed during ordinary operation, eventually leading to increased GC pressure, degraded query/API performance, and potential OutOfMemoryError / node crash — a resource exhaustion condition reachable purely by an unprivileged transaction broadcaster.

### Likelihood Explanation
Likelihood is high for sustained, low-cost growth: creating new accounts and issuing self-signed `AccountPermissionUpdateContract` + a permissioned follow-up transaction are both ordinary, low-fee operations available to any transaction broadcaster, requiring no special privileges (SR, witness, or peer status). The only cost is standard bandwidth/energy consumption and minimal TRX for account activation, which is cheap relative to the sustained node-side memory cost per entry.

### Recommendation
Bound `ownerAddressSet` size (e.g., LRU/expiring cache similar to `transactionIdCache`), or scope it to per-block-generation lifetime rather than the full `Manager` lifetime, and add explicit pruning/removal when addresses are no longer relevant (e.g., after the corresponding pending/re-verify window closes).

### Proof of Concept
1. Attacker creates account A and broadcasts a self-signed `AccountPermissionUpdateContract` giving A an additional (e.g. `active`) permission with a low weight/threshold it can satisfy alone.
2. Attacker broadcasts a transaction from A with `permission_id` set to the new permission id (satisfies `isMultiSignTransaction`), causing `processTransaction` to insert A's hex address into `ownerAddressSet`. [4](#0-3) 
3. Attacker repeats steps 1–2 with N freshly created accounts (A1..AN), each insertion adding a unique, never-evicted entry to the process-wide set.
4. Over time N can be made arbitrarily large at attacker-controlled low cost, growing `ownerAddressSet` without bound for the lifetime of the node process.
