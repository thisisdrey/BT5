## Title
zToken oracle price (liquidity index) does not match actual redeemable share value (gross-interest pool + treasury dilution) - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
Zest's vaults value a depositor's redeemable share of the pool via `convert-to-assets-preview`, which divides `total-assets-preview` (pool assets grown by the **full/gross** accrued interest) by `total-supply-preview` (share supply diluted by newly-minted treasury shares that carve out the reserve-factor's portion of that gross interest). This is a correct, internally consistent formula for deposits/redeems. But the very same zTokens, when used as **collateral in the lending market**, are priced by an entirely separate mechanism — `resolve-ztoken` in `market.clar`/`v0-4-market.clar` — which multiplies the underlying asset's oracle price by the vault's `lindex` (liquidity index), a value that grows only at the **net-of-reserve-factor** rate. These two representations of "value per zToken share" are not proven to be equal, which mirrors the root cause of GMX H-14: a pool/share valuation formula that mixes in the wrong portion of the fee that is earmarked for the protocol's cut versus the LPs' cut. ### Finding Description
Each vault (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, etc.) computes:
- `total-assets(-preview)` = current underlying assets + (`total-debt` − `total-borrowed`), i.e. the **gross** interest accrued on debt, not reduced by the fee-reserve factor. [1](#0-0) 
- `calc-treasury-lp-preview` mints new `treasury-lp` shares to `dao-treasury`, sized so that exactly `reserve-inc` (=`debt-delta * fee-reserve / BPS`) worth of the gross interest is diverted to the treasury by dilution, while `total-supply-preview` = current supply + `treasury-lp`. [2](#0-1) 
- `convert-to-assets-preview`/`convert-to-shares-preview` use `total-assets-preview` and `total-supply-preview` together, so the LP-facing redemption price correctly nets out the reserve factor via share dilution. [4](#0-3) 

Separately, `accrue` advances `lindex` using `next-liquidity-index`, whose growth rate (`calc-liquidity-rate`) is computed from `(rate, utilization, fee-reserve)` — i.e., the liquidity index itself already excludes the reserve-factor share of interest by construction (an AAVE-style scaled-balance index). [5](#0-4) 

The market then prices a zToken purely from this `lindex`, independent of the share-dilution/treasury-minting mechanic:
```
(define-private (resolve-ztoken (p uint) (aid uint))
  (let ((cached (unwrap! (get-cached-indexes aid) ERR-ORACLE-CALLCODE))
        (cached-lindex (get lindex cached))
        (scaled (* p cached-lindex)))
    (ok (div-down scaled INDEX-PRECISION))))
``` [3](#0-2) 

This gives the market **two independent, non-reconciled formulas for "value of one zToken share"**:
1. The vault's own `convert-to-assets-preview` (gross-interest pool value / diluted supply-with-treasury-shares) — this is the value a holder actually receives upon `redeem`.
2. The market's oracle price via `resolve-ztoken` (base price × net-of-reserve liquidity index) — this is the value used to price zToken collateral for borrowing/health checks/liquidations.

Because the vault dilutes total supply with treasury-lp shares (an ERC-4626-style mechanism) *while separately* growing `lindex` at an already-net rate (an AAVE scaled-index mechanism), the codebase is running the reserve-factor accounting through two different, structurally incompatible models simultaneously. There is no code path visible that proves `resolve-ztoken`'s price ever converges to `convert-to-assets-preview`'s implied per-share value; they are computed from disjoint variables (`lindex` vs. `assets`/`total-borrowed`/`total-supply`/`treasury-lp`) and evolve under different discounting rules. This is directly analogous to the GMX H-14 root cause: a "pool value" calculation folding in the wrong portion of the fee split (fee-receiver's cut vs. the LPs' cut), producing a value used downstream for share pricing that diverges from the value LPs actually redeem.

### Impact Explanation
If the market's oracle-derived zToken collateral value (via `resolve-ztoken`/`lindex`) diverges from the true redeemable value implied by `convert-to-assets-preview`, then:
- If the oracle overvalues zTokens relative to true redemption value, a borrower can deposit zTokens as collateral and borrow more against them than they are actually worth, directly extracting real underlying assets (STX/sBTC/USDC/etc.) from other vaults — this is theft of principal funds at rest (Critical), directly analogous to GMX LPs "getting more than they should."
- If the oracle undervalues zTokens, honest zToken-collateral holders are pushed into unwarranted liquidations or under-borrowing, causing temporary freezing/loss of funds for those users (High).

Both outcomes match the impact class the report itself describes (principal losses from a pool/share valuation formula that includes the wrong fee portion).

### Likelihood Explanation
This is reachable by any ordinary principal: deposit into a vault (`deposit`) to receive zTokens, register/use them as market collateral (`collateral-add`), then borrow (`market.clar`/`v0-4-market.clar` borrow flow) using the oracle-resolved zToken price computed by `resolve-ztoken`. No privileged role or DAO action is required — it is purely a consequence of interest accruing over time (reserve-factor > 0 and utilization > 0), which happens continuously in normal operation, growing the discrepancy between the two valuation models.

### Recommendation
Unify the zToken valuation used by the oracle (`resolve-ztoken`) with the vault's actual redemption rate. Concretely, `resolve-ztoken` should call (or reproduce exactly) the vault's `convert-to-assets-preview(1_share)` — i.e., price = base_price × `total-assets-preview` / `total-supply-preview` — rather than an independently-evolving `lindex` that already excludes the reserve factor while `total-assets` grows on the gross amount and `total-supply` is diluted by `treasury-lp`. Alternatively, redesign the vault to use a single accounting model consistently (either pure ERC-4626 share dilution with gross assets, or pure AAVE-style net liquidity index with no treasury share dilution), and verify the market's oracle formula matches whichever model is chosen exactly at every accrual step.

### Proof of Concept
Concretely reachable via:
1. Vault accrues interest with `fee-reserve` > 0 and utilization > 0 over any nonzero time span — this happens automatically to `assets`, `total-debt`, `lindex`, and (upon `accrue()`) mints `treasury-lp` shares. [6](#0-5) 
2. A user calls `convert-to-assets` (read-only, uses `total-assets-preview`/`total-supply-preview`) to see their true redeemable value for N zSTX. [7](#0-6) 
3. The market, when evaluating the same N zSTX as collateral, independently calls `resolve-ztoken`/`price-resolve` with `CALLCODE-ZSTX`, computing a price from `lindex` alone. [8](#0-7) 
4. Because step 2's formula and step 3's formula are mathematically distinct (one dilutes supply by treasury shares against gross-interest assets, the other grows an index net of the reserve factor with no supply dilution), their outputs are not proven equal at any point after the first `treasury-lp` mint, i.e., after the very first accrual with non-zero `fee-reserve`.

I was not able to fully derive the exact numeric divergence (e.g., algebraically prove which formula is larger and by how much over time) because the concrete bodies of `calc-liquidity-rate`, `calc-index-next`, and `calc-cumulative-debt` were not returned by the search tools in this session — the grep only confirmed their existence in each vault file without surfacing their implementation. A background Devin session with full file access would be needed to pull those exact formulas and complete a numeric worked example, but the structural mismatch (two independent valuation paths for the same asset, one used for redemption and one used for collateral pricing) is confirmed from the code shown above.
