### Title
Dust deposit-token transfer fills victim's `depositTokensOfAccount` to `MAX_TOKENS_PER_USER`, permanently reverting new collateral deposits and debt positions (`UserReachedMaxTokens`) - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.addToDepositTokensOfAccount` and `Pool.addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once an account's combined token list reaches `MAX_TOKENS_PER_USER = 30` [1](#0-0) . Any EOA can add entries to an arbitrary victim's list simply by transferring dust amounts of every registered `DepositToken` to them, because `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance moves from 0 [2](#0-1) . The recipient never opted in and, while their position is at/over the collateral limit, cannot even remove the dust entries because `unlockedBalanceOf` returns 0 for all their deposit tokens when `_issuableInUsd == 0` [3](#0-2) .

### Finding Description
Attack flow:

1. Attacker deposits a dust amount (e.g. 1 wei) into each `DepositToken` registered in the pool (and/or sybil-registers positions so several pools' tokens exist — every token counts against the same per-account limit since `debtTokensOfAccount.length + depositTokensOfAccount.length` is summed [4](#0-3) ).
2. Attacker calls `depositToken.transfer(victim, 1)` for each token. `_revertIfLocked` only checks the *sender's* unlocked balance [5](#0-4) , and `_transfer` pushes each new token onto `victim`'s list via `pool.addToDepositTokensOfAccount(victim)` [2](#0-1) .
3. Once `victim`'s list hits 30, every subsequent operation that would add a new token reverts inside `onlyIfAdditionWillNotReachMaxTokens`:
   - `DepositToken.deposit(amount, victim)` for any collateral type the victim does not yet hold — `_mint` → `addToDepositTokensOfAccount` → revert [6](#0-5) .
   - `DebtToken.issue`/`mint` for a synth debt the victim does not yet hold.
   - `Pool.liquidate` where the seized `depositToken_` is not yet in the *liquidator's* list — `seize` → `_transfer` → `addToDepositTokensOfAccount(liquidator)` reverts [7](#0-6) ; the same applies to the second `seize` to `feeCollector` when `_fee > 0` and the fee collector's list is already at 30, which bricks fee-bearing liquidations pool-wide.
4. While the victim is at full utilization (`_issuableInUsd == 0`), `unlockedBalanceOf(victim)` is 0 for *every* deposit token including the dust [8](#0-7) , so the victim cannot transfer the dust out to free slots — `transfer`/`withdraw` revert with `NotEnoughFreeBalance` [9](#0-8) . The list entries are therefore stuck for as long as the position is unhealthy or fully utilized.

The invariant broken is liveness/availability: the per-account token cap, intended as a gas bound on `debtPositionOf` loops, becomes an attacker-controlled blocker that prevents a victim from depositing new collateral to restore health and prevents liquidators/fee collection from operating on tokens not already in their lists.

### Impact Explanation
- **Forced liquidation / temporary freezing of collateral recovery**: a victim whose health factor is degrading (or already unhealthy) cannot deposit a *new* collateral type — e.g. a fresh stablecoin deposit token — to recapitalize. Their existing collateral remains locked (`unlockedBalanceOf == 0`), dust entries cannot be removed, and the position is inevitably liquidated. The victim loses the liquidation penalty on the full position instead of recovering it.
- **Liquidation DoS via `feeCollector`**: `liquidate` performs a second `seize` to `_poolRegistry.feeCollector()` when `_fee > 0` [10](#0-9) . `feeCollector` is a protocol contract that cannot initiate `DepositToken.transfer` to clear entries. If the combined deposit-token count across pools reaches 30, an attacker fills the fee collector's list with dust; thereafter every liquidation whose seized collateral token is not already held by the fee collector reverts, halting liquidations for those collateral types and letting bad debt accrue.
- Severity is medium: mirrors the CVE class (availability/DoS). No direct theft, but positions become unrecoverable and liquidation liveness for specific collateral/fee paths can be permanently broken.

### Likelihood Explanation
- Cost is trivial: 1 wei dust deposits + `transfer` calls per token; no privileged role, oracle manipulation, or flash capital required. Everything uses public entry points (`deposit`, `transfer`) reachable by any EOA.
- Preconditions: the victim must hold a leveraged position near full utilization for the "cannot self-clean" property, and the pool must offer enough deposit-token varieties (across pools sharing the victim's accounting, or ≥ a few plus the victim's own debt tokens) to reach 30 combined entries. The fee-collector variant additionally requires the registry's total deposit-token count to approach `MAX_TOKENS_PER_USER`.
- Nothing in `SynthContext`, `nonReentrant`, pause flags, or caps prevents this: `transfer` is unprivileged, `addToDepositTokensOfAccount` has no per-caller allowlist, and `seize`/fee transfers hit the same cap for the fee collector.

### Recommendation
- Track per-account lists only for tokens the account intentionally deposited/minted: skip `addToDepositTokensOfAccount` for unsolicited `transfer`/`seize` recipients whose balance is pure dust, or better, only register tokens via `deposit()`/`issue()` and tolerate unlisted holdings in `depositOf`.
- Alternatively, provide a victim-initiated `removeFromDepositTokensOfAccount` escape (e.g. allow burning/transferring out a sub-threshold dust balance even when locked, since dust contributes ~0 collateral value anyway).
- Cap the revert path in `seize` fee collection: pre-register all deposit tokens into the fee collector at `addDepositToken` time, or let `addToDepositTokensOfAccount` be a no-op (emit/list lazily) rather than reverting when the recipient is `feeCollector`.

### Proof of Concept
Reproducible in the existing Hardhat suite (`test/Pool.test.ts`, `test/DepositToken.test.ts` already wire `pool`, `msdMET`, `msEthDebtToken`, `feeProvider`, `masterOracle`):

```ts
// assumes `pool`, `msdMET` (DepositToken), `met`, `msEth`, `msEthDebtToken`,
// `feeProvider`, and signers alice/victim/attacker/liquidator are set up as in test/Pool.test.ts

it('dust griefing fills account token list and blocks new collateral deposit', async () => {
  // Setup: victim deposits MET and mints msETH close to the CF limit
  await met.connect(alice).approve(msdMET.address, ethers.constants.MaxUint256)
  await msdMET.connect(alice).deposit(parseEther('6000'), alice.address)
  await msEthDebtToken.connect(alice).issue(parseEther('1'), alice.address)

  // Attacker deposits dust into every other registered DepositToken and transfers to victim.
  // (Deploy/register enough deposit tokens in the fixture so combined list reaches 30.)
  for (const dt of allDepositTokens) {
    await underlyingOf(dt).connect(attacker).approve(dt.address, ethers.constants.MaxUint256)
    await dt.connect(attacker).deposit(1, attacker.address)
    await dt.connect(attacker).transfer(alice.address, 1) // adds dt to alice's list
  }
  // alice's debtTokensOfAccount.length + depositTokensOfAccount.length == 30

  // 1. Victim cannot deposit a NEW collateral type to recapitalize
  const newDt = await deployNewDepositToken() // fresh collateral registered by governor
  await expect(newDt.connect(alice).deposit(parseEther('100'), alice.address))
    .revertedWithCustomError(pool, 'UserReachedMaxTokens')

  // 2. While unhealthy/fully utilized victim cannot even send the dust back
  await masterOracle.updatePrice(met.address, toUSD('0.95')) // _issuableInUsd -> 0
  await expect(allDepositTokens[0].connect(alice).transfer(attacker.address, 1))
    .revertedWithCustomError(allDepositTokens[0], 'NotEnoughFreeBalance')
  await expect(msdMET.connect(alice).withdraw(1, alice.address))
    .revertedWithCustomError(msdMET, 'NotEnoughFreeBalance')
})

it('fee collector at cap reverts fee-bearing liquidations', async () => {
  // Fill feeCollector's depositTokensOfAccount with dust transfers to reach 30,
  // then a liquidation with protocolLiquidationFee > 0 on a collateral the
  // feeCollector doesn't yet hold reverts inside the second `seize` call.
  await feeProvider.updateProtocolLiquidationFee(parseEther('0.01'))
  // ... fill feeCollector list via `dt.transfer(feeCollector, 1)` ...
  await masterOracle.updatePrice(met.address, toUSD('0.95'))
  await expect(
    pool.connect(liquidator).liquidate(msEth.address, alice.address, amountToRepay, newCollateralDt.address)
  ).revertedWithCustomError(pool, 'UserReachedMaxTokens')
})
```

Both cases trace cleanly through public entry points (`transfer`, `liquidate`) into `onlyIfAdditionWillNotReachMaxTokens` and are not blocked by any existing modifier, cap, or guard.
