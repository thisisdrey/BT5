### Title
Unauthenticated peer public-key overwrite via unverified re-key Handshake in `ConversationP2P::validate_handshake` / `handle_handshake` - (File: `stackslib/src/net/chat.rs`)

### Summary
`ConversationP2P::validate_handshake` only cryptographically verifies a `Handshake`'s signature against the claimed `node_public_key` when the conversation does **not** yet have a known public key (`self.connection.get_public_key() == None`). When a key is already known (the normal case for an established outbound peer), the `Some(_)` branch performs no signature check at all against the new claimed key—only an address/port sanity check for outbound peers. `handle_handshake` then unconditionally calls `update_from_handshake_data`, which overwrites the connection's public key whenever it differs from the old one, and if the conversation is outbound, persists that unverified key into `PeerDB` via `Neighbor::load_and_update`/`save_update`.

### Finding Description
The documented invariant in `handle_handshake`'s doc comment states: "A handshake will only be accepted if we do not yet know the public key of this remote peer, or if it is signed by the current public key" [1](#0-0) . This invariant is not actually enforced by `validate_handshake`:

```
match self.connection.get_public_key() {
    None => { message.verify_secp256k1(&handshake_data.node_public_key)... }
    Some(_) => { /* only checks outbound addr/port match */ }
};
``` [2](#0-1) 

When a key is already on file (the attacker's targeted scenario: an existing trusted `NeighborKey` with an old public key), the code never calls `verify_secp256k1` against the newly claimed `node_public_key`, and never checks whether the message was actually signed by that old key either (that check, if it happens, occurs upstream when deciding the `authenticated` flag passed into `handle_handshake`, which would fail for a message signed by a *different* new key and route it through `handle_unauthenticated_control_message`). The only remaining gates are: address/port match for outbound connections (trivially satisfiable by an attacker sending their own known address back) [3](#0-2) , and the "not stale" check `expire_block_height <= chain_view.burn_block_height` [4](#0-3) , satisfiable minimally with `burn_block_height + 1`.

After `validate_handshake` returns `Ok`, `update_from_handshake_data` unconditionally overwrites `self.connection`'s public key and sets `updated = true` whenever the new key differs from the old one, with no additional signature verification [5](#0-4) . Because the conversation is outbound, `handle_handshake` then persists this unverified key change straight into `PeerDB`:

```
if updated && self.stats.outbound {
    let tx = network.peerdb_tx_begin()...;
    let (mut neighbor, _) = Neighbor::load_and_update(&tx, ..., &handshake_data)?;
    neighbor.save_update(&tx, None)?;
    tx.commit()...;
}
``` [6](#0-5) 

`Neighbor::load_and_update` simply loads the existing PeerDB row (if any) and calls `handshake_update`, which sets `self.public_key = pubk` and `self.expire_block = handshake_data.expire_block_height` directly from attacker-supplied fields, with no cross-check that this key is cryptographically bound to the session [7](#0-6) . `save_update` then writes this straight to `PeerDB::update_peer` [8](#0-7) .

Thus the claimed equality is broken: the public key persisted into `PeerDB` for this `NeighborKey` is not required to equal a key that has been proven, via signature verification, to be held by the party sending the message.

### Impact Explanation
An attacker who already has an outbound P2P conversation with a node (i.e., the node dialed out to them and previously completed a handshake, so an old key is on file) can send a single crafted `Handshake` claiming an arbitrary `node_public_key` and `expire_block_height = burn_block_height + 1`. This message is written into `PeerDB`, silently replacing the trusted key record for that peer. Because this happens on the outbound-persistence path, it constitutes unauthenticated write to persistent local state (`PeerDB`), which downstream logic (neighbor walk, replacement logic, `NeighborAddress` key-hash matching) treats as authoritative. This matches the Critical category "unauthenticated/unauthorized write to state."

### Likelihood Explanation
Preconditions: the local node must already have an established outbound conversation to the attacker-controlled peer (attacker just needs to be listed/dialed as a neighbor, which is achievable by any remote party operating a peer that gets crawled/allowed). No secrets, admin role, or privileged access are required—only the ability to run a peer and respond to an outbound connection with a crafted Handshake. The attack is repeatable on every handshake/reconnect cycle at negligible cost (single message, no compute-intensive proof).

### Recommendation
In `validate_handshake`, when `self.connection.get_public_key()` is `Some(cur_pubk)`, explicitly verify the message signature against `cur_pubk` (rejecting if it doesn't verify) unless the caller has already confirmed `authenticated == true` via the same key; only allow acceptance of a *different* `node_public_key` (i.e., a genuine re-key) if it can be proven the sender controls the old key (e.g., signed by old key) or via some other authenticated re-key protocol, not merely because an unauthenticated message happened to pass the address/expiry checks. Pass and check the `authenticated` flag inside `validate_handshake`/`handle_handshake` before persisting any key change to `PeerDB`.

### Proof of Concept
Add a test in `stackslib/src/net/chat.rs` test module (or `net::chat` integration tests) that:
1. Establishes an outbound `ConversationP2P` with a `NeighborKey` and an initial trusted public key `pk_old`, and pre-populates `PeerDB` with that peer/key.
2. Crafts a `StacksMessage::Handshake` with `node_public_key = pk_new` (a fresh keypair unrelated to `pk_old`), `expire_block_height = chain_view.burn_block_height + 1`, and `addrbytes`/`port` copied from the conversation's known peer address, signed with `pk_new`'s private key (so it fails verification against `pk_old`, forcing `authenticated=false`).
3. Feeds this message into `handle_unauthenticated_control_message`/`handle_handshake` with `self.stats.outbound = true`.
4. Asserts that `PeerDB::get_peer(...)` for the `NeighborKey` now returns `public_key == pk_new` and `expire_block == burn_block_height + 1`, despite the message never being verified against `pk_old` or independently proven to be signed by `pk_new` in the `Some(_)` branch of `validate_handshake`—demonstrating the unauthenticated overwrite.

    pub fn update_from_handshake_data(
        &mut self,
        preamble: &Preamble,
        handshake_data: &HandshakeData,
    ) -> Result<bool, net_error> {
        let pubk = handshake_data
            .node_public_key
            .to_public_key()
            .map_err(|e| net_error::DeserializeError(e.into()))?;

        self.peer_version = preamble.peer_version;
        self.peer_network_id = preamble.network_id;
        self.peer_services = handshake_data.services;
        self.peer_expire_block_height = handshake_data.expire_block_height;
        self.handshake_addrbytes = handshake_data.addrbytes.clone();
        self.handshake_port = handshake_data.port;
        self.data_url = handshake_data.data_url.clone();

        let mut updated = false;
        let cur_pubk_opt = self.connection.get_public_key();
        if let Some(cur_pubk) = cur_pubk_opt {
            if pubk != cur_pubk {
                debug!(
                    "{:?}: Upgrade key {:?} to {:?} expires {:?}",
                    &self,
                    &to_hex(&cur_pubk.to_bytes_compressed()),
                    &to_hex(&pubk.to_bytes_compressed()),
                    self.peer_expire_block_height
                );
                updated = true;
            }
        }

        self.connection.set_public_key(Some(pubk.clone()));

        Ok(updated)
    }
