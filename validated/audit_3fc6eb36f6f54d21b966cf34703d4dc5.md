### Title
Oversized attachment content bypasses `AtlasConfig.attachments_max_size` on the peer-download path - ([File: stackslib/src/net/atlas/mod.rs])

### Summary
`GetAttachmentResponse::deserialize` hex-decodes an attachment body from a remote peer's `/v2/attachments/:hash` response with no size bound, and the download pipeline (`AttachmentsBatchStateContext::extend_with_attachments` → `AttachmentsDownloader::run` → `AtlasDB::insert_instantiated_attachment`) stores it verbatim. The size guard `AtlasDB::should_keep_attachment`, which checks `attachment.content.len() <= atlas_config.attachments_max_size`, is never called anywhere on this path.

### Finding Description
The invariant the codebase intends to hold is: every attachment persisted in `AtlasDB` satisfies `attachment.content.len() <= atlas_config.attachments_max_size`. This is enforced only inside `AtlasDB::should_keep_attachment` [1](#0-0) , and a `grep` across the repo shows `should_keep_attachment` is invoked only from `stackslib/src/net/api/posttransaction.rs` (the "attach content to a posted tx" path) and defined/tested in `db.rs`/`tests.rs`. It is not called from `stackslib/src/net/atlas/download.rs` at all.

The peer-download path is:
1. `RPCGetAttachmentRequestHandler::try_parse_response` / `StacksHttpResponse::decode_atlas_get_attachment` parses the JSON body into a `GetAttachmentResponse` via `GetAttachmentResponse::deserialize` [2](#0-1) . This function only hex-decodes the string; there is no length check against `attachments_max_size`.
2. `AttachmentsBatchStateContext::extend_with_attachments` calls `response.decode_atlas_get_attachment()` and inserts the resulting `Attachment` directly into `self.attachments` (a `HashSet<Attachment>`) with no size check [3](#0-2) .
3. `AttachmentsDownloader::run`, upon reaching `AttachmentsBatchStateMachine::Done`, drains `context.attachments` and calls `network.atlasdb.insert_instantiated_attachment(&attachment)` for each one, again with no size check [4](#0-3) .
4. `AtlasDB::insert_instantiated_attachment` writes `attachment.content` straight into the `attachments` SQLite table without validating its size [5](#0-4) .

Thus a malicious peer that a victim node queries for an attachment (a normal, unprivileged interaction that happens automatically as part of Atlas sync — the victim asks peers for attachments referenced by on-chain instances) can respond to `GET /v2/attachments/:hash` with an arbitrarily large hex-encoded `content` field. The victim's local HTTP response-body reading logic in `net/http/response.rs` bounds header sizes (`HTTP_PREAMBLE_MAX_ENCODED_SIZE`) but the body/content-length itself is only bounded by generic node-side buffering, not by `attachments_max_size`. There is no equivalent of `MAX_PAYLOAD_LEN` check enforced specifically for `GetAttachmentResponse` bodies (unlike `posttransaction.rs`, which explicitly checks `preamble.get_content_length() > MAX_PAYLOAD_LEN`). Because `should_keep_attachment` — the only place `attachments_max_size` is actually enforced — is never invoked in `download.rs`, the stored attachment can be arbitrarily large, breaking the intended invariant `attachment.content.len() <= atlas_config.attachments_max_size`.

Note: the hash returned by `Attachment::hash()` is computed over `content`, so the attachment does still have to match a `content_hash` referenced by some on-chain `AttachmentInstance` for it to be requested/paired at all (see `check_attachment_instances` in `download.rs`) — but nothing stops a peer that legitimately holds/serves that content from padding it beyond the max size, or from a malicious peer lying about content for a hash it doesn't actually own until it's rejected by hash mismatch. The scoped concern per the question is specifically that the size cap is bypassed for whatever content is accepted, regardless of hash-matching outcome elsewhere.

### Impact Explanation
Any peer serving attachment data to a victim node can cause the victim to store attachment blobs of unbounded size in its local Atlas SQLite database, exceeding the configured `attachments_max_size` (default minimum 1 MiB, `ATTACHMENTS_MAX_SIZE_MIN`). This is a bounded-but-repeatable storage-exhaustion vector against the read/sync path: each successful attachment fetch from a malicious/compromised peer can inject one oversized blob, and the process repeats for every attachment instance requested. This matches "attachment storage exhaustion via a single oversized attachment blob bypassing the configured attachments_max_size bound" (High category: bounded compute/storage DoS on a read/sync endpoint), since the operator-configured storage bound is silently ignored.

### Likelihood Explanation
- Attacker precondition: the attacker only needs to run a normal Stacks peer node that the victim connects to and downloads attachments from — this is part of ordinary outbound Atlas sync (`network.get_outbound_sync_peers()` in `download.rs`), requiring no privileged role, secret, or admin access.
- The attacker must be selected as a download source; this happens naturally via inventory advertisement (`GetAttachmentsInvResponse`) that the attacker peer can also control, or simply be reached opportunistically among any outbound peer set.
- Every subsequent attachment content hash the victim looks up from the malicious peer's URL can be exploited this way — fully repeatable.
- Remote reachability: requires only that the victim connects to the attacker's advertised P2P/data URL, well within the "unprivileged peer" threat model.

### Recommendation
Enforce `attachments_max_size` on the attachment-download path before it is stored: either bound-check the hex-decoded content length inside `GetAttachmentResponse::deserialize` (requires passing `AtlasConfig` into the deserializer context, or performing the check post-decode), or explicitly call `atlasdb.should_keep_attachment(...)`-equivalent size validation in `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs`) and/or immediately before `insert_instantiated_attachment` in `AttachmentsDownloader::run`, discarding/logging and bumping `report.bump_failed_requests()` for oversized responses instead of accepting them.

### Proof of Concept
```rust
// stackslib/src/net/atlas/tests.rs (new test)
#[test]
fn test_oversized_attachment_bypasses_max_size_on_download_path() {
    let atlas_config = AtlasConfig {
        contracts: HashSet::new(),
        attachments_max_size: 16, // tiny bound
        max_uninstantiated_attachments: 10,
        uninstantiated_attachments_expire_after: 10,
        unresolved_attachment_instances_expire_after: 10,
        genesis_attachments: None,
    };
    let mut atlas_db = AtlasDB::connect_memory(atlas_config.clone()).unwrap();

    // Simulate a GetAttachmentResponse decoded from a malicious peer's HTTP body,
    // with content far exceeding attachments_max_size.
    let oversized_content = vec![0xAB; 10 * atlas_config.attachments_max_size as usize];
    let attachment = Attachment::new(oversized_content.clone());

    // Confirm should_keep_attachment would reject it if it were called:
    let bns_contract_id = boot_code_id("bns", false);
    assert!(!atlas_db.should_keep_attachment(&bns_contract_id, &attachment));

    // But the download path (extend_with_attachments -> AttachmentsDownloader::run)
    // calls insert_instantiated_attachment directly, without should_keep_attachment:
    atlas_db.insert_instantiated_attachment(&attachment).unwrap();

    let stored = atlas_db.find_attachment(&attachment.hash()).unwrap().unwrap();
    assert_eq!(stored.content.len(), oversized_content.len());
    assert!(stored.content.len() as u32 > atlas_config.attachments_max_size); // invariant broken
}
```
A fuller end-to-end reproduction would construct a `GetAttachmentResponse` with an oversized `content`, feed it through `StacksHttpResponse::decode_atlas_get_attachment`, then through `AttachmentsBatchStateContext::extend_with_attachments` and `AttachmentsDownloader::run`, asserting `AtlasDB::insert_instantiated_attachment` is reached and persists the oversized blob without `should_keep_attachment` ever being invoked (verifiable via code coverage/instrumentation, since `should_keep_attachment` is not referenced in `download.rs`).

    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
