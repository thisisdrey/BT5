### Title
Missing post-trade balance validation in legacy (non-hardened) AMM path allows floating-point-driven negative exchange balances - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
The DODO/MEV-bot report describes a class of bug where an actor can repeatedly exploit an AMM's price/slippage math because the counterparty performs insufficient validation of the resulting trade amounts. The java-tron `ExchangeTransactionContract` path (an on-chain TRC10 AMM, "bancor"-style exchange) contains an analogous insufficient-validation defect: the legacy (`double`/`Math.pow`-based) curve calculation used by `ExchangeCapsule.transaction()` is allowed to update pool balances without any post-trade sanity check unless a currently-inactive hardening proposal (`allowHarden()`/`AllowHardenExchangeCalculation`) is enabled.

### Finding Description
`ExchangeCapsule.transaction()` selects one of two `Processor` implementations depending on the `hardenedCalc` flag: [1](#0-0) 

The resulting new pool balances are only checked for negativity when `hardenedCalc` is `true`: [2](#0-1) 

When `hardenedCalc` is `false` (the default/legacy path, used unless the `AllowHardenExchangeCalculation` chain parameter has been activated via governance proposal), the computed `newFirstTokenBalance`/`newSecondTokenBalance` are written back into the persisted `Exchange` capsule with **no bound check at all**. The legacy `ExchangeProcessor` performs the bancor-relay math using `double` arithmetic and `Math.pow` (as evidenced by the parallel `SafeExchangeProcessor`, which was clearly written to replace it with `BigDecimal`/`StrictMathWrapper` precision), so it is subject to floating-point rounding error. `ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(...)` and directly persists the capsule via `Commons.putExchangeCapsule(...)` without any independent verification that the resulting pool balances remain non-negative or internally consistent: [3](#0-2) 

The only guard present in `doValidate()` is a check that the *received* amount meets the caller's `tokenExpected` floor — it does not validate that the resulting pool state is sane: [4](#0-3) 

Because `ExchangeTransactionContract` is a normal signed transaction any account holding the traded token/TRX can broadcast, an attacker who can craft `quant`/`exchangeId` values that drive the legacy double-precision curve into rounding errors (e.g., very large or very small balances/quants near the edges of `double` precision, or repeated trades that compound rounding drift) can push the exchange's `firstTokenBalance`/`secondTokenBalance` negative or otherwise inconsistent with the actual underlying account holdings, since nothing prevents it on this code path.

### Impact Explanation
A negative or corrupted `firstTokenBalance`/`secondTokenBalance` in an `Exchange`/`ExchangeV2` capsule breaks the invariant that pool balances back real TRX/TRC10 holdings. This can result in an unbacked balance in the exchange (pool state diverges from actual token custody), and/or permanent freezing of the exchange (subsequent trades against a corrupted pool would fail or behave unpredictably, e.g., `Token balance in exchange is equal with 0` checks or arithmetic exceptions on later trades), effectively locking user funds already deposited into that exchange. This matches the "unbacked balance" / "permanent freezing of funds" acceptance criteria.

### Likelihood Explanation
Exploitability depends on finding trade sizes/pool balances where the legacy `double`-based curve rounding diverges enough to violate balance invariants; this is a data-dependent floating-point edge case rather than a universally reproducible one-shot bug, and only applies while `AllowHardenExchangeCalculation` (the proposal introducing `SafeExchangeProcessor`) is not yet active on the network. Given that a hardened replacement (`SafeExchangeProcessor`) was explicitly written to correct exactly this class of imprecision, this suggests the underlying floating-point AMM math has known precision issues that the missing bounds-check on the legacy path fails to catch.

### Recommendation
Apply the same non-negative balance validation performed for the hardened path (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0` in `ExchangeCapsule.transaction()`) unconditionally, regardless of the `hardenedCalc`/`allowHarden()` flag, so that the legacy `ExchangeProcessor` result is always sanity-checked before being persisted. Alternatively, force `hardenedCalc` to always be `true` in `ExchangeTransactionActuator`/`ExchangeCreateActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` independent of the governance proposal state.

### Proof of Concept

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
