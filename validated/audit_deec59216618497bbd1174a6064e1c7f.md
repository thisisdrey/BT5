### Title
Dust deposits can fill a victim's `MAX_TOKENS_PER_USER` slots and block collateral top-ups / new positions - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The Glance bug class is "resource exhaustion by creating many entries that are not properly cleaned up / bounded on the victim's side." The Metronome analog is the per-account token lists `depositTokensOfAccount` / `debtTokensOfAccount` in `Pool`, capped at `MAX_TOKENS_PER_USER = 30`. Any `DepositToken._transfer` or `_mint` that gives an account a nonzero balance calls `pool.addToDepositTokensOfAccount(account_)`, which reverts with `UserReachedMaxTokens` once the combined debt+deposit list reaches 30. Because `DepositToken.deposit(amount_, onBehalfOf_)` accepts an arbitrary beneficiary and `transfer`/`transferFrom` are permissionless, an unprivileged attacker can dust-deposit (or dust-transfer) every listed deposit token into a victim's account, occupying all remaining slots.

### Finding Description
- `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, which reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [1](#0-0) [2](#0-1) .
- `DepositToken._mint` and `_transfer` unconditionally add the token to the recipient's list whenever the recipient's prior balance was zero [3](#0-2) [4](#0-3) .
- `deposit` supports depositing to an arbitrary `onBehalfOf_` account (confirmed in tests using `deposit(toDeposit, bob.address)`), and `transfer`/`transferFrom` only check the *sender's* locked balance — the recipient never opts in [5](#0-4) .
- Attack: for each of the pool's listed deposit tokens, the attacker either (a) deposits 1 wei of underlying with `onBehalfOf_ = victim`, or (b) deposits to themselves and `transfer`s 1 wei to the victim. Each call appends one entry to `depositTokensOfAccount[victim]` until the cap is hit.
- Once the cap is reached, every subsequent action that would add a *new* token to the victim's list reverts: depositing a different collateral type, receiving msdToken transfers, and any liquidation/seize path that would credit a new deposit token (`seize` → `_transfer` → `addToDepositTokensOfAccount`).

### Impact Explanation
- The victim cannot add a new collateral type to their position. If the victim's debt position is drifting toward unhealthy and their remaining issuable capacity requires a *new* collateral token, they are temporarily unable to top up collateral, enabling forced liquidation of their existing position (direct loss of collateral via liquidation fee/seizure — temporary freezing of funds / liveness break of position management).
- Liquidators calling `Pool.liquidate` that would seize into an account whose list is full can have `seize`/`_transfer` revert, skewing liquidation execution.
- The victim can only recover by manually transferring each dust balance to zero (or having it seized), which costs gas and must race re-griefing; the dust itself may be partially locked when the victim has outstanding debt because `unlockedBalanceOf` gates transfers.

### Likelihood Explanation
- Cost is tiny: 1 wei of each underlying per deposit (or 1 wei of each msdToken per transfer), plus gas. No privileged role is needed; `addToDepositTokensOfAccount` is reached purely through public `deposit`/`transfer`.
- Feasibility depends on the deployed pool listing enough deposit tokens to fill the victim's remaining slots (the cap is shared across deposit + debt tokens, so a victim already holding several tokens needs fewer attacker deposits). Metronome pools (e.g., Hemi/Base deployments) list many collaterals; exact count per deployment should be confirmed.
- `whenNotShutdown`/`nonReentrant`/`onlyIfDepositTokenExists` do not mitigate this: dust deposits are legitimate calls in the deployed configuration.

### Recommendation
- Allow removal to be initiated more easily (e.g., a `pool`-level "clean my token list" that removes entries the account wants dropped, or auto-remove on any balance reaching zero including via seize).
- Raise/eliminate reliance on the fixed cap by bounding iteration differently, or exempt the victim's *own* deposits when the token being added is already collateral they hold.
- Alternatively, let `seize`/liquidation credit the liquidator directly so liquidation cannot be blocked by the victim's list state, and consider minimum-deposit dust thresholds.

### Proof of Concept
Hardhat sketch (fork against a deployed pool with ≥N deposit tokens):

```solidity
// victim already holds some tokens; attacker fills remaining slots up to 30
for (uint i; i < pool.getDepositTokens().length; ++i) {
    IDepositToken dt = IDepositToken(pool.getDepositTokens()[i]);
    IERC20 underlying = dt.underlying();
    deal(address(underlying), attacker, 1);
    vm.startPrank(attacker);
    underlying.approve(address(dt), 1);
    dt.deposit(1, victim);          // _mint -> addToDepositTokensOfAccount(victim)
    vm.stopPrank();
}
// victim's deposit+debt list is now at MAX_TOKENS_PER_USER
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
vm.prank(victim);
newCollateralDepositToken.deposit(amount, victim); // reverts: cannot top up new collateral
```

Uncertainty note: the attack requires the pool to list enough deposit tokens to reach the shared 30-slot cap on the victim (since debt tokens cannot be pushed to a third party — `DebtToken.issue` mints debt to `_msgSender`, not `to_`). If a deployed pool lists few collaterals and the victim holds few tokens, the cap may be unreachable; verify `pool.getDepositTokens().length` on the target chain.
