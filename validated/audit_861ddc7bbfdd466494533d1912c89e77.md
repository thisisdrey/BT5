### Explicit binding checked
`TokenId(A) == TokenId(B)` (as parsed `TokenId::from_str` string or Borsh bytes) `⟹ A == B` (same underlying `(contract_id, token_id)` pair). This must hold for the claimed exploit to be blocked; if two different `(contract, token)` pairs can produce equal `TokenId` representations, the binding is broken.

### Trace
- `TokenId::from_str` splits only on the *first* `:` to extract the type tag, then dispatches to the variant's own `FromStr`: [1](#0-0) .
- `Nep141TokenId::from_str` parses the remainder entirely as an `AccountId` (no further splitting): [2](#0-1) .
- `Nep245TokenId::from_str` / `Nep171TokenId::from_str` / `ImtTokenId::from_str` split the remainder on the first `:` into `(contract_id, token_id)`, with `contract_id` parsed strictly as `AccountId` and everything after the first colon (including any further colons) kept verbatim as `token_id`: [3](#0-2) .
- `AccountId` parsing (via `near_account_id`) only accepts the NEAR account-id charset (lowercase letters, digits, `.`, `-`, `_`); the character `:` is never a legal `AccountId` byte, so `AccountId::from_str` will reject any string containing a `:`. This guarantees the first `:` after the type tag unambiguously demarcates `contract_id` from the rest — there is no way to craft an `AccountId` string that itself contains a `:` to shift the split boundary.
- Consequently the encoding `type:contract_id[:token_id]` is injective: two different `(contract_id, token_id)` pairs cannot produce the same string, and this is exercised by the existing round-trip tests for each variant and for `TokenId` itself, both for `Display`/`FromStr` and for Borsh serialization: [4](#0-3) , [5](#0-4) .
- `Amounts<BTreeMap<_, DisplayFromStr>>` deserialization (used for `TokenDiff::diff` in `contracts/defuse/core/src/intents/token_diff.rs`) relies on exactly this `FromStr`/`Display` machinery, so a JSON `MultiPayload` cannot inject a colliding key: [6](#0-5) .
- Nested wrapping (e.g. a NEP-245 token whose `mt_token_id` is itself a full `TokenId` string of another asset, as exercised in `mt_transfer_call_circullar_deposit`) still round-trips correctly because the outer split only consumes the first colon, leaving the inner nested `TokenId` string intact: [7](#0-6) .

### Evaluation
Before and after: for any two distinct `(contract_id, token_id)` pairs belonging to different underlying assets, their `TokenId` string/Borsh representations remain distinct because `AccountId`'s restricted charset (excluding `:`) prevents any collision at the delimiter boundary. The binding holds. No divergence exists that would let a crafted `TokenId` in a `TokenDiff.diff` map be parsed as, or collide with, a different real `TokenId`.
