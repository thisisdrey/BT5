Found a confirmed analog: `BandwidthProcessor.updateUsage(AccountCapsule)` iterates over every asset an account holds via `accountCapsule.getAssetMapV2()`, and this function is called from `Wallet.getAccountResource` on every `getaccountresource` query, and indirectly during transaction processing for `TransferAssetContract`-related bandwidth calculation. `getAssetMapV2()` calls `importAllAsset()`, which for optimized accounts does a full LevelDB `prefixQuery` over all distinct token IDs the account holds via `AccountAssetStore.getAllAssets`.

### Title
Unbounded iteration over account's asset map in `BandwidthProcessor.updateUsage` enables gas/DoS via token-spam - (File: chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java)

### Summary
`BandwidthProcessor.updateUsage(AccountCapsule)` loops over the full set of distinct TRC10 token balances an account holds (`accountCapsule.getAssetMapV2()`), performing a `forEach` update for every token id present. [1](#0-0) 

### Finding Description
This is directly analogous to the Moloch `_ragequit` bug: an operation that should be O(1) per account instead becomes O(n) in the number of distinct tokens the account has ever received, and that count is fully attacker-controlled. Any address can issue a new TRC10 asset via `AssetIssueContract` and then send a tiny amount of it to a victim address using `TransferAssetContract`; the receiving account has no opt-in/whitelist and cannot refuse the asset. `getAssetMapV2()` calls `AccountCapsule.importAllAsset()`, which, when asset-storage optimization is enabled, performs a full LevelDB prefix scan of every asset entry keyed by the target account's address via `AccountAssetStore.getAllAssets`. [2](#0-1) [3](#0-2) [4](#0-3) 

`updateUsage(AccountCapsule)` is invoked from `Wallet.getAccountResource`, a public API path (`GetAccountResource` gRPC/HTTP query and JSON-RPC), meaning any unauthenticated client can trigger the full asset-map iteration for any address simply by requesting its resource info. [5](#0-4) 

There is no cap on the number of distinct token types an account can accumulate, unlike the bounded lists elsewhere in the codebase (e.g. `VoteWitnessProcessor` enforces `MAX_VOTE_NUMBER`, and `MarketSellAssetActuator` enforces `MAX_MATCH_NUM`). Nothing analogous bounds the asset map size.

### Impact Explanation
An attacker can cheaply issue many distinct TRC10 tokens (subject only to the `AssetIssueFee`) and airdrop 1 unit of each to a target account. Once the number of distinct assets held by the victim grows large enough, every subsequent `GetAccountResource` API call against that address becomes increasingly expensive for the serving node (unbounded LevelDB prefix scan plus a full map rebuild/forEach), degrading query-serving performance for that endpoint. Because bandwidth accounting also runs during actual transaction execution when the asset map is accessed (e.g., during block validation paths that call `updateUsage`), a bloated asset map can also slow down or, in aggregate across many spammed accounts, contribute to degraded block processing. This matches the "API the node can no longer serve" / node performance impact class.

### Likelihood Explanation
Likelihood is high given the low barrier to entry: any transaction broadcaster can issue TRC10 assets and freely send them to any recipient without the recipient's consent (`AssetIssueActuator` / `TransferAssetActuator` require no whitelist or opt-in from the receiver), and `GetAccountResource` is a completely unauthenticated, unprivileged query. No special privileges or SR/witness status are needed.

### Recommendation
Introduce a cap on the number of distinct asset ids an account can hold (an analog of `MAX_VOTE_NUMBER`), reject `TransferAssetContract`/asset-issuance operations that would push a recipient over that cap, and/or avoid recomputing the full asset map inside `updateUsage` (e.g., lazily update per-asset usage only for assets actually referenced by the transaction, similar to how `useAssetAccountNet` already only touches a single `tokenID`).

### Proof of Concept
1. Attacker calls `AssetIssueContract` repeatedly (paying the `AssetIssueFee` each time) to create N distinct TRC10 tokens. [6](#0-5) 
2. Attacker calls `TransferAssetContract` to send 1 unit of each of the N tokens to victim address V, which cannot refuse or opt out.
3. Any client calls `GetAccountResource(V)` (via gRPC/HTTP/JSON-RPC through `Wallet.getAccountResource`), which invokes `BandwidthProcessor.updateUsage(accountCapsule)`. [5](#0-4) 
4. `updateUsage` calls `accountCapsule.getAssetMapV2()` → `importAllAsset()` → `AccountAssetStore.getAllAssets` which performs an O(N) `prefixQuery` and forEach over all N assets, then a second forEach over the merged map to update per-asset net usage — cost scales linearly (unbounded) with N and is fully attacker-controlled. [7](#0-6)

        long latestAssetOperationTime = accountCapsule.getLatestAssetOperationTime(assetName);

  public Map<String, Long> getAllAssets(Protocol.Account account) {
    Map<String, Long> assets = new HashMap<>();
    if (account.getAssetOptimized()) {
      Map<WrappedByteArray, byte[]> map = prefixQuery(account.getAddress().toByteArray());
      map.forEach((k, v) -> {
        byte[] assetID = ByteArray.subArray(k.getBytes(),
                account.getAddress().toByteArray().length, k.getBytes().length);
        assets.put(ByteArray.toStr(assetID), Longs.fromByteArray(v));
      });
    }
    account.getAssetV2Map().forEach((k, v) -> assets.put(k, v));
    return assets;
  }
