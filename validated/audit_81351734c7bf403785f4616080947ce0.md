### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule` lets any account spam a victim's delegation index, causing amplified read/write costs and unbounded API responses - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceActuator` (and its native-contract equivalent) allow any account to freeze a small balance and delegate the resulting bandwidth/energy resource to an arbitrary `receiverAddress` it does not control. When the network has not yet activated `AllowDelegateOptimization` (`dynamicPropertiesStore.supportAllowDelegateOptimization()` false), each such delegation appends the `receiverAddress`/`ownerAddress` pair into a single, unbounded protobuf list stored under the *receiver's* key in `DelegatedResourceAccountIndexStore`, without the receiver's consent or any cap on the number of entries.

### Finding Description
`FreezeBalanceActuator.delegateResource()` unconditionally updates the victim's index entry whenever it receives a delegation, regardless of who initiates it: [1](#0-0) 

This mirrors the reported bug class: there is no access control preventing an attacker from unilaterally attaching data to a victim's on-chain state, and that state is later read/appended to as a whole. Each new attacker-controlled sender address (cheap to create) that delegates to the same victim `receiverAddress` causes `DelegatedResourceAccountIndexCapsule.addFromAccount` to append one more entry to the victim's `fromAccountsList`, which is persisted as a single serialized value: [2](#0-1) 

Every time any account (attacker or legitimate) delegates to or unfreezes from that victim address, the full list is deserialized, mutated, and rewritten: [3](#0-2) 

This same pattern is exercised (at small scale, 100 receivers) in `FreezeBalanceActuatorTest.testMultiFreezeDelegatedBalanceForBandwidth`, confirming the list grows linearly with the number of distinct delegation counterparts and is fully reloaded/rewritten on each new delegation: [4](#0-3) 

The unbounded index is also served directly via wallet/gRPC/HTTP query paths (`Wallet.getDelegatedResourceAccountIndex`, `GetDelegatedResourceAccountIndexServlet`, `RpcApiService`), meaning the full, attacker-inflated list is returned to any client querying that address, with no pagination or size limit enforced.

### Impact Explanation
An attacker can, at low cost (minimal freeze amount per throwaway sender account), continually grow the victim's `DelegatedResourceAccountIndexCapsule.fromAccountsList` indefinitely. This:
- Increases the serialized size of the victim's index record without bound, increasing DB read/rewrite cost for every future freeze/delegate/unfreeze operation touching that address (a legitimate operation, e.g., `UnfreezeBalanceActuator`, must also load and rewrite the whole growing list — see the same store usage in `UnfreezeBalanceActuator.java:156-192`).
- Makes API responses (`getDelegatedResourceAccountIndex` over gRPC/HTTP) unbounded in size, potentially large enough to degrade or crash the serving node process or make the query practically unusable for the victim address — an API the node can no longer meaningfully serve for that account.
- Could eventually push per-transaction processing time/energy for legitimate freeze/unfreeze operations on the victim account higher, degrading availability for that account (denial-of-service class impact), matching the reported bug's "unbounded growth causes gas/processing DoS on a victim" pattern.

This legacy code path is only reachable while `AllowDelegateOptimization` is not yet enabled network-wide; once enabled, the V2 index storage is prefix-keyed per pair rather than a single growing blob, which does not exhibit this issue. The severity therefore depends on whether this proposal has been activated on the target network — I could not fully verify current mainnet proposal state from the code alone.

### Likelihood Explanation
Likelihood is Medium: it requires network state where `AllowDelegateOptimization` has not been activated (a chain-committee-controlled proposal), and requires the attacker to fund many small freeze/delegate transactions to distinct throwaway addresses targeting one victim address. There is no capital requirement beyond minimal freeze amounts and standard transaction fees, and no special privilege is needed — any broadcastable `FreezeBalanceContract` reaches this path.

### Recommendation
- Cap the number of entries maintained in `DelegatedResourceAccountIndexCapsule.fromAccountsList`/`toAccountsList`, or migrate fully to the V2 prefix-keyed index scheme (already used when `supportAllowDelegateOptimization()` is true) for all delegation code paths, removing the legacy single-blob index growth path entirely.
- Enforce pagination or a maximum returned entry count in the `getDelegatedResourceAccountIndex` wallet/gRPC/HTTP handlers.
- Consider requiring receiver consent, a minimum delegation size, or rate-limiting new distinct delegation counterparts per address per time window to prevent low-cost list-inflation.

### Proof of Concept
1. On a network where `AllowDelegateOptimization` proposal is not yet enabled, create N throwaway funded accounts.
2. From each throwaway account, broadcast `FreezeBalanceContract` with `receiverAddress` set to a fixed victim address and a small `frozen_balance` (delegate flag), causing `FreezeBalanceActuator.delegateResource` to append to `DelegatedResourceAccountIndexStore` entry for the victim (`chainbase/.../DelegatedResourceAccountIndexCapsule.addFromAccount`).
3. Repeat with large N (analogous to the test's `RECEIVE_COUNT` but scaled far larger) to grow the victim's index list unbounded.
4. Query `Wallet.getDelegatedResourceAccountIndex(victimAddress)` via gRPC/HTTP and observe the unbounded response size/latency; observe increased cost of any subsequent freeze/unfreeze transaction touching the victim address due to full list read/rewrite in `FreezeBalanceActuator`/`UnfreezeBalanceActuator`.
