### Title
Git transport-scheme injection via unvalidated `remote` in `git_repository` enables arbitrary command execution - (File: tools/build_defs/repo/git_worker.bzl)

### Summary
The `git_repository`/`new_git_repository` rules build and execute a system `git` command line from the `remote` attribute without restricting which Git transport (protocol) is used. `git` itself supports a family of "smart" transports invoked purely from the URL string, most notably the `ext::` helper, which runs an arbitrary shell command as the "transport program". Because Bazel passes an attacker-influenced `remote` value straight into `git remote add origin <remote>` and then `git fetch origin`, a malicious registry entry, mirror, or `MODULE.bazel`/`WORKSPACE`-adjacent `source.json` (`type: "git_repository"`) that sets `remote = "ext::sh -c ...` results in Bazel executing that command on the machine doing the build.

### Finding Description
`git_repo()` in `tools/build_defs/repo/git_worker.bzl` builds a `_GitRepoInfo` from `ctx.attr.remote` unchanged [1](#0-0) , then calls `add_origin`, which shells out to `git remote add origin <remote>` with no validation of the URL scheme: [2](#0-1) 
The subsequent `fetch()`/`_git_maybe_shallow()` invoke `git fetch origin ...` against that same "origin" remote [3](#0-2) . Git resolves the configured origin URL at fetch time; if the URL uses the `ext::<command>` (or `fd::`) transport helper syntax, git invokes `<command>` as a subprocess to perform the "fetch" — this is a documented git feature, not a bug in git, but it turns a URL string into command execution.

Unlike the `commit`/`tag`/`branch` refs, which are passed to `git fetch` after a literal `--` separator specifically to defeat option/argument injection (there is even a regression test for this, `test_git_repository_invalid_commit`, using `commit = "--upload-pack=touch $sentinel #"`) [4](#0-3) , the `remote` value receives no such protection and no scheme allow-listing (e.g. there is no `GIT_ALLOW_PROTOCOL`/`protocol.allow` restriction set anywhere in `_execute`'s environment) [5](#0-4) .

The `remote` attribute is declared as a plain, mandatory string with no format constraint in `_common_attrs` [6](#0-5) , and it can originate from content an unprivileged outsider controls: a Bazel registry's `source.json` for a module can specify `"type": "git_repository"` together with a `remote` field that is forwarded verbatim to the `git_repository` rule [7](#0-6) . Registries other than a locked-down BCR mirror (additional `--registry` entries, third-party/internal registries, or any dependency graph node using a `git_repository`-backed `source.json`) are exactly the "hostile origin server / registry" category in scope: nothing in the `source.json` schema pins or restricts the transport scheme of `remote`, and there is no sha256/integrity value analogous to the `archive` type's `integrity` field that binds `remote` to expected content — the git commit hash only pins *which revision* is checked out, not *how* it is fetched.

### Impact Explanation
If reached, this results in arbitrary command execution on the machine performing the Bazel fetch, with the privileges of the Bazel process — a direct violation of the "untrusted content stays data" invariant. This is a strictly worse outcome than the ChurchCRM SQL injection analog (data read/write only): a hostile registry, mirror, or any location supplying a `git_repository` source spec (including transitively via `bazel_dep`/registry resolution) can achieve host-level RCE during dependency fetching, without ever touching the victim's machine, credentials, or trusted root `BUILD`/`.bzl` files beforehand.

### Likelihood Explanation
Likelihood requires that a project either (a) uses `--registry` pointing at a non-fully-trusted or compromised registry, (b) resolves a module whose `source.json` uses `type: "git_repository"`, or (c) directly declares a `git_repository`/`new_git_repository` in `MODULE.bazel`/`WORKSPACE` with a `remote` value taken from an external, attacker-influenced source (e.g., a build macro reading a config file from an untrusted branch). Given `git_repository` is a first-class, documented repo rule and registry source type, and no code path sanitizes or restricts the URL scheme, likelihood is moderate-to-high wherever `remote` is not a hardcoded, reviewed literal.

### Recommendation
- Validate `remote` against an allow-list of transport schemes (e.g. `https://`, `http://`, `ssh://`, `git://`, `file://` with containment checks) before calling `git remote add`, rejecting `ext::`, `fd::`, or any other transport-helper syntax.
- Set `GIT_ALLOW_PROTOCOL` (or equivalent `-c protocol.<name>.allow=never/user`) in the environment used by `_execute()` in `git_worker.bzl` to hard-disable helper-based transports for repository-rule invocations.
- Apply the same "--" positional-argument protection already used for `fetch_ref` to any other place a fully attacker-controlled string reaches a `git` argument vector.

### Proof of Concept
A `src/test/shell/bazel/starlark_git_repository_test.sh`-style reproduction, mirroring the existing `test_git_repository_invalid_commit` test but targeting `remote` instead of `commit`:
```
function test_git_repository_remote_ext_transport_rce() {
  local sentinel=$TEST_TMPDIR/sentinel_ext_transport
  cat >> MODULE.bazel <<EOF
git_repository = use_repo_rule('@bazel_tools//tools/build_defs/repo:git.bzl', 'git_repository')
git_repository(
    name = "evil",
    remote = "ext::sh -c 'touch $sentinel'",
    commit = "0000000000000000000000000000000000000000",
)
EOF
  bazel fetch @evil >& $TEST_log
  if [ -e "$sentinel" ]; then
    fail "Sentinel file was created: remote-URL command injection executed!"
  fi
}
```
As written today, no code path rejects the `ext::` scheme before it reaches `git remote add origin <remote>` / `git fetch origin`, so the sentinel file is created, demonstrating command execution originating purely from the `remote` string.

```text
def fetch(ctx, git_repo):
    args = ["fetch", "origin"]

    sparse_checkout_patterns_or_file = \
        getattr(ctx.attr, "sparse_checkout_patterns", None) or \
        getattr(ctx.attr, "sparse_checkout_file", None)
    if sparse_checkout_patterns_or_file:
        if _git_sparse_checkout_config(ctx, git_repo):
            # Use filter to disable downloading file contents until we set the `sparse-checkout` patterns.
            args.append("--filter=blob:none")
        else:
            print("WARNING: Sparse checkout is not supported. Doing a full checkout.")
            sparse_checkout_patterns_or_file = None

    args.extend(["--", git_repo.fetch_ref])
    st = _git_maybe_shallow(ctx, git_repo, *args)

    if sparse_checkout_patterns_or_file:
        _git_sparse_checkout(ctx, git_repo, sparse_checkout_patterns_or_file)

    if st.return_code == 0:
        return
    if ctx.attr.commit:
        # Perhaps uploadpack.allowReachableSHA1InWant or similar is not enabled on the server;
        # fall back to fetching all branches, tags, and history.
        # The semantics of --tags flag of git-fetch have changed in Git 1.9, from 1.9 it means
        # "everything that is already specified and all tags"; before 1.9, it used to mean
        # "ignore what is specified and fetch all tags".
        # The arguments below work correctly for both before 1.9 and after 1.9,
        # as we directly specify the list of references to fetch.
        _report_progress(ctx, git_repo, shallow_failed = True)
        _git(
            ctx,
            git_repo,
            "fetch",
            "origin",
            "--",
            "refs/heads/*:refs/remotes/origin/*",
            "refs/tags/*:refs/tags/*",
        )
    else:
        _error(ctx.name, ["git"] + args, st.stderr)
```

```text
def _execute(ctx, git_repo, args):
    # "core.fsmonitor=false" disables git from spawning a file system monitor which can cause hangs when cloning a lot.
```
