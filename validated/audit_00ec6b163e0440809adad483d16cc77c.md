### Title
Attachment content is stored without verifying `Hash160::from_data(&content) == request.content_hash` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` inserts the `Attachment` returned in a `GetAttachmentResponse` into `self.attachments` purely based on successful HTTP decoding, without ever checking that the returned content's hash matches the `content_hash` that was requested. This lets a malicious data-URL host answer an `AttachmentRequest{content_hash: H}` with arbitrary bytes that decode successfully but do not hash to `H`.

### Finding Description
The broken equality is: `response.attachment.hash() == request.content_hash`, which is never checked in `extend_with_attachments`: [1](#0-0) 
Here, `request` (which carries `content_hash`, the value that was solicited via `get_prioritized_attachments_requests`, see lines 404-478) is discarded after only being used to look up the peer's reliability report (`request.get_url()`), and the response's `attachment` field is inserted into `self.attachments` (a `HashSet<Attachment>`) as long as `decode_atlas_get_attachment()` succeeds — i.e., as long as the HTTP body parses as an `Attachment` at all, with no hash comparison.

Downstream, `AttachmentsDownloader::run` drains `context.attachments` and, for each attachment, calls `atlasdb.find_all_attachment_instances(&attachment.hash())` and `atlasdb.insert_instantiated_attachment(&attachment)`, then resolves `context.attachments_batch.resolve_attachment(&attachment.hash())`: [2](#0-1) 
Because the attachment is looked up/stored keyed by `attachment.hash()` (the hash of the *received* bytes B) rather than the *requested* `content_hash` H, a malicious peer can supply attacker-chosen bytes B where `Hash160::from_data(&B) != H`. The result: no `AttachmentInstance` row for H is ever resolved (since `find_all_attachment_instances(&attachment.hash())` looks up instances keyed by hash(B), not H), while attacker-controlled content is stored in the AtlasDB `attachments` table under `Hash160::from_data(&B)`.

Existing guards do not prevent this: the only checks performed are (1) HTTP 404 status (`response.preamble().status_code == 404` at line 901) and (2) successful decoding of the HTTP body into an `Attachment` struct (`decode_atlas_get_attachment()`), neither of which validates the cryptographic binding between requested hash and delivered content.

### Impact Explanation
This matches the "High - attachment/BNS mismatch" category explicitly named in scope. The on-chain commitment `H` (e.g., a BNS name-update `zonefile` hash) never resolves to real content because the correct `AttachmentInstance` row for H stays `is_available=0` forever — the node believes the attachment was processed but it wasn't matched to the correct hash. Simultaneously, attacker-supplied bytes are durably persisted in the node's AtlasDB `attachments` table, polluting local storage keyed under a hash the attacker chose (a minor secondary effect). This is repeatable per attachment request and requires no special peer privileges beyond being selected as a data-URL host, which is possible for any peer that another node peers with (an "outbound sync peer").

### Likelihood Explanation
Preconditions: the attacker's peer just needs to be among a victim node's outbound sync peers and be selected as a data-URL host with the queried attachment index (i.e., the attacker advertises via `GetAttachmentsInvResponse` that it has the attachment at the relevant page/index, which is self-reported and unauthenticated). The attacker does not need the node's RPC secret or admin role — it only needs to run its own node/peer and answer inbound attachment inventory/content requests, which is exactly the "unprivileged remote peer" model in scope. Cost is a single crafted HTTP response; the attack is trivially repeatable for every attachment request routed to the attacker's peer.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, after decoding the response, compute `Hash160::from_data(&response.attachment.content)` and compare it against `request.content_hash` before inserting into `self.attachments`; on mismatch, treat it as a failed request (`report.bump_failed_requests()`) and optionally mark the peer as faulty/blocked, mirroring the existing pattern used for decode failures.

### Proof of Concept

1. Construct an `AttachmentsBatchStateContext` with a single peer URL and an `AttachmentsBatch` such that `get_prioritized_attachments_requests()` yields one `AttachmentRequest { content_hash: Hash160::from_data(b"real"), .. }`.
2. Build a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map has that request keyed to `Some(response)`, where `response` is a `StacksHttpResponse` whose body decodes (via `decode_atlas_get_attachment`) to `Attachment { content: b"fake".to_vec() }` (so `Hash160::from_data(b"fake") != Hash160::from_data(b"real")`).
3. Call `context.extend_with_attachments(&mut results)`.
4. Assert that `context.attachments` contains the `Attachment{content: b"fake"}` entry (proving the mismatch was stored) — i.e., `assert!(context.attachments.iter().any(|a| a.hash() != request.content_hash))`, demonstrating the missing equality check.
5. (Optional integration extension) Continue into `AttachmentsDownloader::run`'s `Done` branch and assert that `network.atlasdb.find_attachment(&H)` (the originally requested hash) still returns `Ok(None)` after the run, while `network.atlasdb.find_attachment(&Hash160::from_data(b"fake"))` returns `Ok(Some(_))`, confirming the BNS-resolution-never-completes impact.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
