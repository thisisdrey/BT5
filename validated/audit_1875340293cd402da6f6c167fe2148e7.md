### Title
Bounty sub-account fund lock via fixed `RelevantAssets` list in `TransferAllFungibles::force_transfer_all_assets` - (File: substrate/frame/bounties/src/lib.rs)

### Summary
`pallet-bounties` exposes `Config::TransferAllAssets`, whose documented purpose is to sweep **all** assets out of a stale/closed bounty sub-account back to the treasury (`substrate/frame/bounties/src/lib.rs:391-395`). The multi-asset implementation, `TransferAllFungibles`, does not actually sweep "all" assets — it only iterates a compile-time, statically configured `RelevantAssets: Get<Vec<AssetId>>` list [1](#0-0) . Any asset id not present in that fixed list that ends up held by the bounty sub-account (e.g. a `pallet-assets` asset created/registered after runtime deployment, or any token sent to that derived account through a path other than the intended bounty currency) is silently skipped and never transferred out, exactly mirroring the `CVXStaker.rewardTokens[]` defect: a hardcoded token list that cannot track tokens introduced after the code was fixed in place.

### Finding Description
`TransferAllAssets` is the abstraction pallet-bounties uses to reclaim funds from a bounty's derived sub-account: [2](#0-1) 

For runtimes with more than one asset, the recommended implementation is `TransferAllFungibles`, which is generic over a `RelevantAssets: Get<Vec<...AssetId>>` parameter: [1](#0-0) 

`RelevantAssets` is a `frame_support::traits::Get` implementor, i.e. a value fixed by the runtime configuration at compile time (analogous to the constructor-supplied `rewardTokens[]` array in `CVXStaker.sol`). There is no extrinsic, governance call, or storage-backed mechanism in this pallet to add a newly-created asset id to `RelevantAssets` after deployment — updating it requires a runtime upgrade, exactly like `CVXStaker.sol` needed a code change to accept new `extraRewards`.

The `Config` trait documents the intended guarantee explicitly: [3](#0-2) 

"used for bounty closure to ensure that all assets are returned to the treasury" — but the loop only visits `RelevantAssets::get()`, so any asset outside that enumerated set is left behind in the bounty sub-account when the bounty is closed and the account is expected to be fully reaped.

This differs from `pallet-assets`' own `transfer_all` (`substrate/frame/assets/src/lib.rs:1895-1936`), which sweeps a single named asset per call — `TransferAllFungibles` is meant to be the "sweep everything" primitive specifically because a bounty account is anonymous/derived and the runtime cannot know in advance which assets could accumulate there. Restricting the sweep to a hardcoded list defeats that purpose whenever the parachain's asset registry grows (new `pallet-assets` ids, new foreign assets registered via XCM, etc.) after the `RelevantAssets` constant was set.

### Impact Explanation
Any balance of an asset not enumerated in `RelevantAssets` that resides in a bounty's derived sub-account becomes permanently unreachable through the bounty-closure sweep path — it is neither returned to the treasury nor recoverable by any other pallet extrinsic, since the sub-account is a keyless, derived `AccountId` with no owner able to sign a manual transfer. This is a "permanent user-fund/treasury-state lock" in the terms of the Required Impacts gate: value that should conserve and settle back to the treasury is stranded indefinitely once the enumerated fixed set diverges from the actual set of assets that can reach that account (which is guaranteed to happen as new assets are added to the chain over its lifetime, since `RelevantAssets` cannot be updated without a runtime upgrade).

### Likelihood Explanation
This does not require any privileged actor, governance abuse, or malicious relayer/validator — it is a direct consequence of a static configuration mismatch that will occur naturally as soon as the set of chain assets grows beyond what was enumerated when `RelevantAssets` was configured, which is expected and routine in a live Substrate/Asset-Hub-style deployment. No attacker action is even needed for the fund lock to manifest: it is triggered by the ordinary evolution of the asset registry combined with normal bounty-closure operation, satisfying the "public underpriced/false-safety work" and "permanent user-fund lock" bar without needing a malicious peer, node, or admin as root cause.

### Recommendation
Do not rely on a compile-time fixed asset list for a "sweep everything" primitive. Instead:
- Drive `TransferAllFungibles` from the live, on-chain registry of created assets (e.g. iterate `pallet_assets::Asset` storage or an on-chain `BoundedVec` maintained by the pallet that is updated whenever a new asset is created), or
- Provide a governance-gated or permissionless extrinsic to add/remove entries in `RelevantAssets`-equivalent runtime storage, analogous to the mitigation applied to `CVXStaker` (`setRewardTokens`), so the sweep set can track newly introduced assets without a runtime upgrade, or
- Change the semantics/documentation of `TransferAllFungibles` to explicitly disclaim the "all assets" guarantee and require operators to keep `RelevantAssets` in sync with the asset registry via a mandatory pre-close check.

### Proof of Concept
1. Configure a runtime with `pallet-bounties` using `TransferAllFungibles<AccountId, Assets, RelevantAssets>` where `RelevantAssets = [AssetA]` (as of genesis/runtime-build time).
2. After deployment, the runtime governance/users register a new `pallet-assets` asset `AssetB` (a normal, permissionless or governance action unrelated to bounties).
3. A bounty's derived sub-account accumulates a balance of `AssetB` (e.g., because a curator fee, ED top-up, or any transfer targets that account, which is a valid, non-privileged interaction since the sub-account address is derivable and receivable by anyone).
4. When the bounty is closed and `T::TransferAllAssets::force_transfer_all_assets` is invoked to reclaim `from` (the bounty sub-account) into `to` (the treasury), the loop in `TransferAllFungibles` only visits `RelevantAssets::get() = [AssetA]`; the `AssetB` balance is never checked or moved.
5. `AssetB` remains stranded in the now-closed, keyless bounty sub-account permanently, with no dispatchable in `pallet-bounties`, `pallet-treasury`, or `pallet-assets` capable of recovering it (the account has no controlling key to sign a manual `transfer`).

Note: I was not able to locate, within available tool iterations, the exact call site inside `close_bounty`/`claim_bounty` that invokes `T::TransferAllAssets::force_transfer_all_assets`, so the precise extrinsic name that triggers the sweep is inferred from the `Config::TransferAllAssets` doc comment (`substrate/frame/bounties/src/lib.rs:391-395`) rather than directly observed at the call site. Further verification of that call site is recommended before treating this as fully confirmed.

```rust
/// Transfer all `RelevantAssets` of the `Fungibles` from one account to another.
///
/// The native asset should be the first in the list of `RelevantAssets`, otherwise the transfers
/// of the other maybe fails.
pub struct TransferAllFungibles<AccountId, Fungibles, RelevantAssets>(
	core::marker::PhantomData<(AccountId, Fungibles, RelevantAssets)>,
);
impl<AccountId, Fungibles, RelevantAssets> TransferAllAssets<AccountId>
	for TransferAllFungibles<AccountId, Fungibles, RelevantAssets>
where
	Fungibles: FungiblesMutate<AccountId> + FungiblesCreate<AccountId>,
	RelevantAssets: Get<Vec<<Fungibles as FungiblesInspect<AccountId>>::AssetId>>,
	AccountId: Eq + Clone,
{
	fn force_transfer_all_assets(from: &AccountId, to: &AccountId) -> Result<bool, DispatchError> {
		// We iterate through all assets twice in case that the Native asset was not last in the
		// list and ED remained because of an insufficient asset at the end of the list.
		let assets_twice =
			RelevantAssets::get().into_iter().chain(RelevantAssets::get().into_iter());

		let mut transferred_any = false;
		for id in assets_twice {
			let balance = Fungibles::reducible_balance(
				id.clone(),
				from,
				Preservation::Expendable,
				Fortitude::Polite,
			);
			if balance.is_zero() {
				continue;
			}

			// Ignore errors since this can only fail if the receiver does not exist.
			if Fungibles::transfer(id, from, to, balance, Preservation::Expendable).is_ok() {
				transferred_any = true;
			}
		}
		Ok(transferred_any)
	}
```
