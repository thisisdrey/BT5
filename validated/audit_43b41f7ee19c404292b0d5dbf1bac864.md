### Title
Missing negative-clamp on `TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight` in TVM/precompile Freeze-Unfreeze path allows resource-weight accounting divergence - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
`DynamicPropertiesStore.addTotalNetWeight/addTotalEnergyWeight/addTotalTronPowerWeight` (the path used by ordinary account-level actuators such as `FreezeBalanceActuator`/`UnfreezeBalanceActuator`) clamps the resulting total weight to a floor of `0` when `allowNewReward()` is active. The equivalent methods in `RepositoryImpl` (the path used by TVM native/precompiled contracts such as `freeze`, `freezeBalanceV2`, `unfreezeBalanceV2`, delegate/undelegate) perform the identical accumulation but omit this clamp entirely.

### Finding Description
`DynamicPropertiesStore.addTotalNetWeight` in `chainbase/src/main/java/org/tron/core/store/DynamicPropertiesStore.java` guards the totals: [1](#0-0) 
The same pattern is repeated for `addTotalEnergyWeight` and `addTotalTronPowerWeight`: [2](#0-1) 

In contrast, `RepositoryImpl` — which is the `Repository` implementation used by every TVM-reachable native/precompiled staking operation (`FreezeBalanceProcessor`, `FreezeBalanceV2Processor`, `UnfreezeBalanceV2Processor`, `DelegateResourceProcessor`, `UnDelegateResourceProcessor`, invoked from `Program.freeze`/`Program.freezeBalanceV2`) — implements the same accumulation without any clamp: [3](#0-2) 

The TVM entry points that route through this unclamped path include `Program.freeze` and `Program.freezeBalanceV2`, which build a `Repository` child, run the `Processor`, then `repository.commit()`: [4](#0-3) [5](#0-4) 
The native processors themselves call `repo.addTotalNetWeight` / `repo.addTotalEnergyWeight` / `repo.addTotalTronPowerWeight` directly: [6](#0-5) [7](#0-6) 

This means the exact same on-chain resource state (`TOTAL_NET_WEIGHT`, `TOTAL_ENERGY_WEIGHT`, `TOTAL_TRON_POWER_WEIGHT`) can be mutated via two different code paths with inconsistent invariant enforcement, depending on whether the freeze/unfreeze is triggered by a normal transaction (`FreezeBalanceActuator`/`UnfreezeBalanceActuator`, which go through `DynamicPropertiesStore` and get the `max(0, …)` clamp) or by a smart-contract call to the freeze/unfreeze precompiles (which go through `RepositoryImpl` and skip the clamp).

### Impact Explanation
`TotalNetWeight`/`TotalEnergyWeight` are used directly in bandwidth/energy limit computation, e.g. `BandwidthProcessor.calculateGlobalNetLimit`, which explicitly special-cases `totalNetWeight <= 0` when `allowNewReward()` is on: [8](#0-7) 
If the unclamped TVM path can push the stored total below zero (or leave it inconsistent with what the clamped path would have produced), then bandwidth/energy limit calculations for all accounts and reward distribution based on total resource weight become skewed system-wide (invariant break), matching the "unbacked/incorrect accounting" class of impact cited in the analog report. This affects a chain-wide global counter, so it is not confined to a single account.

### Likelihood Explanation
Reaching this path requires only a normal contract call to the native freeze/unfreeze precompiles (`freeze`, `freezeBalanceV2`) exposed to any Solidity contract via `Program.freeze`/`Program.freezeBalanceV2` — reachable by any unprivileged deployer/caller issuing ordinary transactions, with no special privilege needed. However, I was not able to fully confirm from the available code whether a delegate/undelegate/unfreeze sequence via the TVM path can actually drive the total below zero in current production configurations (this would need to be validated with the exact sequencing/values in `DelegateResourceProcessor`/`UnDelegateResourceProcessor`/`UnfreezeBalanceV2Processor` and confirmed against fork-activation gating such as `supportUnfreezeDelay`/`allowNewReward`). This uncertainty affects confidence in likelihood, though the structural inconsistency (missing clamp in one of two parallel implementations of the same accounting function) is clearly present in the code.

### Recommendation
Route `RepositoryImpl.addTotalNetWeight`/`addTotalEnergyWeight`/`addTotalTronPowerWeight` through the same clamped logic as `DynamicPropertiesStore` (i.e., apply `max(0, total, disableJavaLangMath())` when `allowNewReward()` is enabled), or have `RepositoryImpl` delegate to `DynamicPropertiesStore`'s implementation instead of duplicating the arithmetic, so both the actuator path and the TVM/precompile path enforce identical invariants.

### Proof of Concept
Not independently reproduced; the finding is based on static comparison of the two duplicate-but-diverging implementations (`DynamicPropertiesStore.addTotalNetWeight` vs `RepositoryImpl.addTotalNetWeight`, and their `Energy`/`TronPower` counterparts) and their respective call graphs (`FreezeBalanceActuator`/`UnfreezeBalanceActuator` vs `FreezeBalanceV2Processor`/`UnfreezeBalanceV2Processor`/`Program.freeze`/`Program.freezeBalanceV2`). A concrete exploit sequence (e.g., freeze via TVM precompile, then unfreeze via TVM precompile enough times to drive the weight negative while `allowNewReward()` is set) would need to be constructed and tested against a running node to confirm exploitability, which was outside the scope of static code retrieval performed here.

  public long calculateGlobalNetLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForBandwidth();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalNetLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long totalNetLimit = chainBaseManager.getDynamicPropertiesStore().getTotalNetLimit();
    long totalNetWeight = chainBaseManager.getDynamicPropertiesStore().getTotalNetWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalNetWeight <= 0) {
      return 0;
    }
    if (totalNetWeight == 0) {
      return 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalNetLimit, totalNetWeight);
    }
    long netWeight = frozeBalance / TRX_PRECISION;
    return (long) (netWeight * ((double) totalNetLimit / totalNetWeight));
  }
