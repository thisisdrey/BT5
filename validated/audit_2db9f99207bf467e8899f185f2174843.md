### Title
Unvalidated attachment content-hash in `AttachmentsBatchStateContext::extend_with_attachments` lets a remote peer permanently pollute AtlasDB with unbound content - ([File: stackslib/src/net/atlas/download.rs])

### Summary
When the Atlas downloader fetches an attachment body from a peer to satisfy a pending `AttachmentInstance.content_hash`, the response's `Attachment` is accepted and stored without ever checking that `attachment.hash()` equals the `content_hash` that was actually requested. A malicious peer that is selected to serve an attachment can therefore return arbitrary bytes, which get permanently persisted via `insert_instantiated_attachment` even though `find_all_attachment_instances` finds zero matching `AttachmentInstance` rows.

### Finding Description
The equality the system is supposed to preserve is: every `Attachment` persisted via `insert_instantiated_attachment` should correspond to at least one `AttachmentInstance.content_hash` that was committed on-chain (i.e., `attachment.hash() == instance.content_hash` for some tracked instance).

The request/response flow is:
1. `get_prioritized_attachments_requests` (stackslib/src/net/atlas/download.rs:404-478) builds an `AttachmentRequest{ content_hash, sources, ... }` for each genuinely missing, on-chain-tracked `content_hash`.
2. The HTTP round trip happens in `BatchedRequestsState::try_proceed` (download.rs:819-943), which simply stores whatever `response` comes back keyed by the original `request` in `results.succeeded`.
3. `AttachmentsBatchStateContext::extend_with_attachments` (download.rs:530-558) then does:
```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
}
``` [1](#0-0) 
There is **no check that `response.attachment.hash() == request.content_hash`**. The request object (which carries the expected `content_hash`) is discarded after this point (`request` is dropped, only its URL/report are used).

4. In `AttachmentsDownloader::run`, the `Done` arm then does, for every attachment collected this way:
```
let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())?;
network.atlasdb.insert_instantiated_attachment(&attachment)?;
``` [2](#0-1) 

Because step 3 never validated the hash, an attacker-controlled peer can respond to a legitimate `AttachmentRequest` for hash `H` with a `GetAttachmentResponse` containing arbitrary bytes whose true hash is `H' != H`. `decode_atlas_get_attachment` only deserializes the HTTP body; it performs no cross-check against the request. This forged `Attachment` is inserted into `context.attachments` (a `HashSet<Attachment>`, deduped by full struct equality, not by hash). In `Done`, `find_all_attachment_instances(&attachment.hash())` looks up `H'`, which was never tracked by any batch (only `H` was), so it returns zero rows — yet `insert_instantiated_attachment(&attachment)` is called unconditionally regardless of that result. The bogus content is thus written to the AtlasDB `attachments` table permanently, with no corresponding `attachment_instances` row, and the original legitimate request for `H` is never resolved (`context.attachments_batch.resolve_attachment(&attachment.hash())` also resolves the wrong hash `H'`, leaving the real pending instance for `H` unresolved and subject to retry/re-enqueue forever).

`evict_expired_uninstantiated_attachments` and `evict_expired_unresolved_attachment_instances` (download.rs:174-181) only clean up the *uninstantiated* table and unresolved *instances*, not attachments that have already been marked instantiated — so the forged rows are never garbage-collected.

### Impact Explanation
A remote, unprivileged peer that a node selects as an outbound sync source for Atlas attachments (any peer with a data URL the node dialed) can cause the node to permanently store arbitrary attacker-chosen byte blobs in its local AtlasDB `attachments` table, decoupled from any committed name/BNS operation. This is an attachment/BNS-mismatch class issue: the node's AtlasDB no longer reflects "every stored attachment corresponds to a committed AttachmentInstance." Each `AttachmentRequest` round trip the attacker answers this way yields one more permanently-stored forged row, and this is repeatable across every attachment request the attacker's peer is asked to serve, giving unbounded storage growth over time and indefinitely stalling resolution of the real, legitimately requested attachments (since the original hash is never resolved and gets bumped/re-enqueued or eventually dropped after `max_attachment_retry_count`, but the forged data stays forever).

### Likelihood Explanation
Preconditions: the node must be in the process of syncing attachments and select the attacker's peer as one of the `sources` for a given `AttachmentRequest` (i.e., the attacker's peer must claim, via a normal attachments-inventory response, to have the requested attachment — no special privilege or secret required, just running a normal P2P peer that responds to `GetAttachmentsInv`/`GetAttachment` requests). This is a standard, unprivileged remote-peer capability explicitly in scope ("run their own peer... gossip messages"). Attacker cost is a single crafted HTTP response per targeted attachment request; the exploit is trivially repeatable for as many forged entries as the attacker's peer is asked to serve.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; drop/penalize (bump failed requests) any response whose attachment hash does not match. Additionally, in the `Done` arm of `AttachmentsDownloader::run`, only call `insert_instantiated_attachment` when `find_all_attachment_instances` returns at least one matching instance, and otherwise discard the attachment (or route it to the "uninstantiated" table subject to expiry) instead of persisting it into the permanent `attachments` table.

### Proof of Concept
Rust test plan (in `stackslib/src/net/atlas/tests.rs` or a new `download.rs` test module):
1. Seed an `AttachmentsBatchStateContext` with one legitimate `AttachmentInstance` whose `content_hash = H`, and an `AttachmentRequest{ content_hash: H, ... }` in the corresponding `BatchedRequestsResult::succeeded` map, but pair it with a `HttpResponse`/`GetAttachmentResponse` whose `Attachment` body content hashes to `H' != H` (i.e., craft bytes such that `Attachment::hash() == H'`).
2. Call `AttachmentsBatchStateContext::extend_with_attachments` with this result and assert `context.attachments` now contains the forged attachment (i.e., no rejection occurred) — this demonstrates the missing hash check at download.rs:547-552.
3. Drive `AttachmentsDownloader::run` to the `Done` branch (or directly replicate the `Done` arm logic in the test) and assert:
   - `atlasdb.find_all_attachment_instances(&H')` returns an empty vector,
   - `atlasdb.insert_instantiated_attachment` is called and a row for `H'` now exists in the `attachments` table (query via `atlasdb.find_attachment(&H')` returns `Some`),
   - the original instance for `H` remains unresolved (`attachments_batch.has_fully_succeed()` is false / instance for `H` still present in `attachments_instances`).
4. Repeat with N distinct forged attachments and assert the `attachments` table row count grows by N while the `attachment_instances` table gains zero rows for those hashes, confirming unbounded storage growth from unverified, attacker-controlled content.
