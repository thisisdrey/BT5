### Title
Unbounded mbox stream in `UserApplyPatch` allows attacker to exhaust shard disk/inode via `git mailsplit` file-bomb - ([File: internal/gitaly/service/operations/apply_patch_mbox.go])

### Summary
`splitMailbox` pipes the entire client-controlled `Patches` stream directly into `git mailsplit -o<workDir>` with no cap on total bytes, message count, or resulting file count, and the resulting files persist in `workDir` (under the storage shard's temp directory) for the full duration of parsing/applying all patches before being removed. An attacker with ordinary push/write access to a repository can stream gigabytes of mbox data or millions of trivially small `From `-separated messages to force `mailsplit` to materialize an unbounded number of files on the shared storage volume.

### Finding Description
`UserApplyPatch` accepts a streamed `Patches` field with no declared size limit in the proto and no application-level cap in the handler. `applyPatchesWithIndex` (internal/gitaly/service/operations/apply_patch.go:144-172) wraps the incoming stream in `streamio.NewReader` and feeds it as stdin to `splitMailbox` (internal/gitaly/service/operations/apply_patch_mbox.go:49-65), which invokes `git mailsplit -o<outDir>` with no message-count or size restriction. `git-mailsplit(1)` writes one file per detected message to `outDir`, so an attacker who streams millions of minimal `From `-delimited messages causes `mailsplit` to write millions of small files into `workDir`, a subdirectory of `repo.StorageTempDir()` — a directory shared by all repositories on that storage shard (internal/gitaly/service/operations/apply_patch.go:151-159).

Cleanup only happens via `defer os.RemoveAll(workDir)` once the whole RPC returns, meaning the files persist for the entire duration of mailbox splitting, per-message `mailinfo` parsing, and patch application, giving a sustained window of inode/disk pressure. `validateUserApplyPatchHeader` (internal/gitaly/service/operations/apply_patch.go:398-411) only validates the repository, user, and target branch — it performs no validation of an expected patch size or count. Gitaly's own backpressure model (doc/backpressure.md) explicitly relies on opt-in, non-default `[[concurrency]]` limits per RPC/repo rather than any per-request payload/message-count cap, so by default there is nothing bounding this handler's resource consumption.

### Impact Explanation
An unprivileged user with push/write access to any repository (including a fork or personal project) can call `UserApplyPatch` and stream an effectively unbounded mbox payload, causing `git mailsplit` to create an unbounded number of files/inodes in the shared per-storage temp directory. On shards where disk/inode capacity is finite and shared across tenants (the common Gitaly deployment model), this can exhaust inodes or disk space and degrade or break other repositories/tenants on the same storage, i.e., a DoS of the storage shard, not just the caller's own repository.

### Likelihood Explanation
Preconditions are minimal: any authenticated user who can open a `UserApplyPatch` client-streaming RPC (available to anyone who can push to a repo they control) can trigger this without special roles, secrets, or non-default configuration. It is fully repeatable and requires no interaction with other users. Default Gitaly configuration ships without a `[[concurrency]]` entry for `UserApplyPatch`, so the only mitigating control (concurrency queueing) is opt-in and not size/message-count aware in any case.

### Recommendation
Add explicit bounds in `apply_patch_mbox.go`/`apply_patch.go` before invoking `git mailsplit`: cap the total bytes read from the `Patches` stream (e.g., via `io.LimitReader`) and cap the number of resulting mailsplit files (fail fast if `len(entries)` exceeds a configurable maximum), returning a `structerr.NewResourceExhausted` or `InvalidArgument` error. Consider also configuring a default `[[concurrency]]` limit for `UserApplyPatch` and enforcing disk-quota checks before/while writing to the shared temp directory.

    require.NoError(t, err)

            Header: &gitalypb.UserApplyPatchRequest_Header{
                Repository:   repoProto,
                User:         gittest.TestUser,
                TargetBranch: []byte("branch"),
            },
        },
    }))

    // Stream N million minimal "From " separated messages to force mailsplit
    // to create N files in the shared storage temp dir.
    var buf bytes.Buffer
    for i := 0; i < 2_000_000; i++ {
        fmt.Fprintf(&buf, "From x Mon Sep 17 00:00:00 2001\nFrom: a <a@a.com>\nSubject: x\n\n---\n\n")
    }
    require.NoError(t, stream.Send(&gitalypb.UserApplyPatchRequest{
        UserApplyPatchRequestPayload: &gitalypb.UserApplyPatchRequest_Patches{Patches: buf.Bytes()},
    }))
    // Observe workDir inode/disk growth under repo.StorageTempDir() during the call,
    // and measure server responsiveness for concurrent requests to other repos on the shard.
    _, _ = stream.CloseAndRecv()
}
```
Expected assertion: without a byte/message cap, `workDir` inode count under the storage's temp directory grows proportionally to attacker-controlled input size with no ceiling, and CPU/disk I/O for other RPCs on the same shard is measurably degraded during the operation. func splitMailbox(ctx context.Context, repo *localrepo.Repo, mboxReader io.Reader, outDir string) ([]string, error) {
	var stdout, stderr bytes.Buffer
	if err := repo.ExecAndWait(ctx,
		gitcmd.Command{
			Name: "mailsplit",
			Flags: []gitcmd.Option{
				// This is a bit awkward, but we cannot use a ValueFlag
				// here because git-mailsplit(1) doesn't use parse-opts.
				gitcmd.Flag{Name: "-o" + outDir},
			},
		},
		gitcmd.WithStdin(mboxReader),
		gitcmd.WithStdout(&stdout),
		gitcmd.WithStderr(&stderr),
	); err != nil {
		return nil, fmt.Errorf("mailsplit: %w, stderr: %q", err, stderr.String())
	}

# Request limiting in Gitaly

In the GitLab ecosystem, Gitaly is the service that is at the bottom of the
stack for Git data access. This means that when there is a surge of
requests to retrieve or change a piece of Git data, the I/O happens in Gitaly.
This can lead to Gitaly being overwhelmed due to system resource exhaustion
because all Git access goes through Gitaly.

If there is a surge of traffic beyond what Gitaly can handle, Gitaly should
be able to push back on the client calling. Gitaly shouldn't subserviently agree
to process more than it can handle.

We employ concurrency limiting as our primary backpressure mechanism in Gitaly.

## Concurrency queue

Limit the number of concurrent RPCs that are in flight on each Gitaly node for each
repository per RPC using `[[concurrency]]` configuration:

```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
```
