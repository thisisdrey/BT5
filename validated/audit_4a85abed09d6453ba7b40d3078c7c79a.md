### Title
Unverified inventory bits let a lying peer be selected as sole source for an attachment, starving retries within a batch - (File: stackslib/src/net/atlas/download.rs)

### Summary
`get_prioritized_attachments_requests` builds `AttachmentRequest.sources` purely from the `has_attachment` bit reported in a remote peer's `GetAttachmentsInvResponse`, with no verification that the peer actually holds the content. `AttachmentRequest::get_url()` / `get_most_reliable_source()` then collapses this multi-peer source set down to a single peer chosen only by a locally-tracked `ReliabilityReport` score, so only one HTTP request is issued per `content_hash` per attempt even when honest peers are also present in `sources`.

### Finding Description
In `get_prioritized_attachments_requests` [1](#0-0) , for each peer's `GetAttachmentsInvResponse`, the code trusts `search_page.inventory.get(position_in_page)` at face value (`has_attachment`) and inserts the peer into `sources` with no content check whatsoever — a malicious peer can set `inventory[bit]=1` for content it never has. This produces an `AttachmentRequest` whose `sources` map may contain both a lying peer and one or more honest peers who actually have the data.

The bug is that despite `sources` containing multiple candidates, only one of them is ever contacted: `Requestable::get_url()` for `AttachmentRequest` calls `get_most_reliable_source()`, which picks the peer with the highest `ReliabilityReport::score()` [2](#0-1) . The `BatchedRequestsState` machine only issues one HTTP GET per `AttachmentRequest` (via `PeerNetwork::begin_request`, which uses this single `get_url()`), so if the lying peer wins the score comparison, the honest peers in the same `sources` set are never contacted in this attempt.

Compounding this, `ReliabilityReport::score()` is a weak metric: `score = floor(success/n) + n` [3](#0-2) . Since `success <= n`, the floor term is 0 unless the peer is 100% reliable, meaning score is dominated almost entirely by request volume `n`, not by actual honesty. An attacker peer that has answered many prior Atlas requests (of any kind, not necessarily this specific content) accumulates a high `n` and can out-rank an honest peer with fewer total interactions, even after being marked faulty for this one bad claim.

When the lying peer is chosen and returns 404, `state.faulty_peers.insert(event_id, peer_url)` is recorded [4](#0-3) , and the request is *not* retried against the other sources in `sources` within this attempt — the `AttachmentRequest`/content_hash is simply dropped from this batch. `AttachmentsBatchStateContext::extend_with_attachments` only records into `context.attachments` for `succeeded` requests [5](#0-4) , so the content_hash is never resolved. Since `resolve_attachment` is only called for hashes in `context.attachments` [6](#0-5) , `attachments_batch.has_fully_succeed()` stays false and the batch is re-enqueued via `bump_retry_count()` [7](#0-6) , until `retry_count >= max_attachment_retry_count`, at which point the batch is dropped entirely [8](#0-7) .

Note: on a re-enqueued retry, the FSM restarts from `Initialized`, so a completely fresh `AttachmentsBatchStateContext` and fresh `GetAttachmentsInvResponse` round is fetched from peers each time (inventories are not carried over across batch retries) — this does give a chance for a different peer to be selected on subsequent attempts if the malicious peer's score has degraded from the earlier failure. However, given the score formula's weak penalty for failed requests (dominated by `n`), an attacker with a large prior request history is not reliably demoted below honest peers after one or a few 404s, so it can plausibly keep winning selection across multiple retries until `max_attachment_retry_count` is exhausted.

### Impact Explanation
This causes a confirmed, honestly-served attachment (whose on-chain instance is legitimate — this is BNS zonefile/attachment data referenced by a confirmed transaction) to be treated as permanently unresolved once the retry budget in `ConnectionOptions::max_attachment_retry_count` is exhausted, even though at least one honest, reachable peer had the correct data the entire time. This matches the "attachment/BNS mismatch" High-impact category: BNS name resolution depending on that attachment (e.g., zonefile hash) will be denied or presented as absent by nodes that were otherwise capable of fetching it, purely due to an unprivileged remote peer lying in one field of an unauthenticated inventory response.

### Likelihood Explanation
The attacker only needs to run/control a peer that the victim node treats as an "outbound sync peer" (no special key, no StackerDB slot, no RPC secret required) and respond to `/v2/attachments/inv` requests with a crafted `GetAttachmentsInvResponse` setting an inventory bit it doesn't actually hold data for; this is a single unauthenticated HTTP response per page requested, trivially reproducible, and repeatable across every re-attempt as long as the attacker is willing to accept being marked faulty and can maintain a competitive `ReliabilityReport` score (achievable by answering enough of its other Atlas requests correctly). No cryptographic material, secrets, or privileged role is required.

### Recommendation
- When building `AttachmentRequest.sources` in `get_prioritized_attachments_requests`, do not collapse to a single "most reliable" peer for the actual download attempt; instead retry against the next-best source in `sources` within the same attempt if the top choice 404s or returns mismatched content, before falling back to a whole-batch retry.
- Verify the downloaded `Attachment`'s content hash equals `content_hash` before accepting it in `extend_with_attachments`, and treat a hash mismatch the same as a 404 (`bump_failed_requests` + try next source), closing the related "mismatched bytes never checked" gap referenced in the question.
- Penalize `ReliabilityReport::score()` more strongly for failures (e.g., use an actual success ratio rather than one dominated by total request count) so a single false inventory claim meaningfully demotes a peer relative to honest peers with fewer total interactions.

### Proof of Concept
Rust test plan in `stackslib/src/net/atlas/tests.rs` (or a new test module) exercising `download.rs` directly:
1. Construct an `AttachmentsBatchStateContext` with two peers: `peer_evil` (high `ReliabilityReport` score due to a large fabricated `total_requests_sent`/`total_requests_success` history) and `peer_honest` (fresh/low `ReliabilityReport::empty()`).
2. Populate `context.inventories` for a `(contract_id, pages, index_block_hash)` key with two `GetAttachmentsInvResponse`s: `peer_evil`'s page has `inventory[position]=1` for `content_hash H` (lie), `peer_honest`'s page also has `inventory[position]=1` (truth).
3. Call `context.get_prioritized_attachments_requests()` and assert the returned `AttachmentRequest` for `H` has `sources` containing both peers, but `get_url()` returns `peer_evil`'s URL (assert via `AttachmentRequest::get_most_reliable_source()`).
4. Simulate the HTTP layer returning `status_code == 404` for `peer_evil`'s request (mock via `BatchedRequestsResult` with `faulty_peers` populated) and feed into `context.extend_with_attachments(&mut results)`.
5. Assert `context.attachments` does NOT contain the attachment for `H`, and that `context.attachments_batch.has_fully_succeed()` is `false` even though `peer_honest` actually had the correct data and was never contacted.
6. Repeat through `bump_retry_count()` up to `connection_options.max_attachment_retry_count` and assert the batch is dropped (not re-pushed to `priority_queue`), confirming the attachment is permanently treated as unresolved despite an honest peer holding it.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

impl AttachmentRequest {
    pub fn get_most_reliable_source(&self) -> (&UrlString, &ReliabilityReport) {
        self.sources
            .iter()
            .max_by_key(|(_, v)| v.score())
            .expect("Atlas: trying to select an Url out of an empty set")
    }
}

impl Hash for AttachmentRequest {
    fn hash<H: Hasher>(&self, state: &mut H) {
        self.content_hash.hash(state)
    }
}

impl Ord for AttachmentRequest {
    fn cmp(&self, other: &AttachmentRequest) -> Ordering {
        other.sources.len().cmp(&self.sources.len()).then_with(|| {
            let (_, report) = self.get_most_reliable_source();
            let (_, other_report) = other.get_most_reliable_source();
            report.cmp(other_report)
        })
    }
}

impl PartialOrd for AttachmentRequest {
    fn partial_cmp(&self, other: &AttachmentRequest) -> Option<Ordering> {
        Some(self.cmp(other))
    }
}

impl Requestable for AttachmentRequest {
    fn get_url(&self) -> &UrlString {
        let (url, _) = self.get_most_reliable_source();
        url
    }
