### Title
Dust deposit-token transfers let an attacker fill a victim's per-account token list to `MAX_TOKENS_PER_USER`, permanently blocking all new deposits and borrows - (File: contracts/Pool.sol)

### Summary
`Pool` tracks every deposit token and debt token an account has ever held a nonzero balance of in two `MappedEnumerableSet` lists (`depositTokensOfAccount`, `debtTokensOfAccount`). Entries are added by `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount`, which are callable only from registered tokens but are triggered on *any* balance-increasing event, including third-party `transfer`, `transferFrom`, and `deposit(amount, onBehalfOf)`. Once the combined length reaches `MAX_TOKENS_PER_USER = 30`, `onlyIfAdditionWillNotReachMaxTokens` reverts every addition, and entries are only removed when the victim's balance in that token returns to exactly zero — a "leaked" list entry the victim cannot drop while the position is collateral-locked. This is the on-chain analog of CVE-2017-16672's session-object leak: objects (list entries) are created on behalf of a victim and are never destroyed, eventually exhausting the per-account resource limit and denying service.

### Finding Description
- `DepositToken._mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever `balanceOf[account_] == 0`, and `deposit(amount_, onBehalfOf_)` lets anyone mint shares to an arbitrary `onBehalfOf_` victim (contracts/DepositToken.sol:211-237, 469-489).
- `DepositToken._transfer` does the same for the recipient of a plain `transfer`/`transferFrom` (contracts/DepositToken.sol:498-526). `transfer` only checks `_revertIfLocked` on the *sender*, never on the recipient (contracts/DepositToken.sol:348-354).
- `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens(account_)`: revert when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (contracts/Pool.sol:143-148, 216-220).
- Removal (`removeFromDepositTokensOfAccount`) only happens inside `_burn`/`_transfer` when the victim's balance hits zero (contracts/Pool.sol:630-634; DepositToken.sol:459-463, 522-525). The victim cannot remove an entry by keeping a nonzero dust balance, and cannot transfer/withdraw the dust at all while `unlockedBalanceOf(victim) == 0` because every collateral is locked by an outstanding debt (`_revertIfLocked`, DepositToken.sol:181, 350).
- Consequence: every code path that would add a *new* token to the victim's lists reverts — `DepositToken.deposit` into any collateral not already in the list, inbound `transfer`/`transferFrom` of any new deposit token, and `DebtToken.issue`/`SmartFarmingManager.leverage` for any new synthetic (each new debt position triggers `addToDebtTokensOfAccount`, which enforces the same cap, contracts/Pool.sol:204-208). The revert is permanent until the victim unwinds debt to unlock the dust shares and pushes them out.

Attacker cost is `dust × N` where N is the number of slots to fill (victim's existing entries count toward the cap, so a user holding k positions only needs 30−k forced entries), bounded by the number of registered deposit tokens in the pool.

### Impact Explanation
Liveness violation / freezing of position management. A targeted user — including a SmartFarmingManager leverage position or any wallet holding k≥1 entries — can be capped so that:
- they cannot deposit into any new collateral type (denial of `deposit`, `NativeTokenGateway.deposit`, `VesperGateway` flows),
- they cannot open debt in any new synthetic (`issue`, `leverage`, `flashRepay` paths revert on `addToDebtTokensOfAccount`),
- the attacker's dust sits as extra collateral the victim cannot shed while locked.

The victim can recover only by repaying debt (unlocking balance) and manually transferring each dust share out — forced transactions the attacker can cheaply re-grief by re-dusting. During the window the victim is capped, they cannot add collateral of a *new* type to defend against liquidation (they may still top up already-held tokens and repay). Accepted impact class: temporary freezing of funds / denial of service on position management, matching the CVE class of resource-leak DoS.

### Likelihood Explanation
- Reachable entirely via unprivileged calls: `depositToken.deposit(dust, victim)` or `depositToken.transfer(victim, dust)`; no privileged role, oracle manipulation, or malicious endpoint needed.
- Precondition: the victim's combined list must reach 30, so the attack requires the pool to have enough registered deposit tokens (debt entries cannot be forced — `DebtToken` is non-transferable and `issue` records debt on the caller). Feasibility therefore depends on deployed pool composition; it is cheapest against users who already hold many positions.
- No existing guard prevents it: `onlyIfDepositTokenExists`, `nonReentrant`, and `_revertIfLocked` do not restrict recipient-side list growth, and `SynthContext._msgSender` resolves to the real caller only for access checks that dust transfers pass trivially.

### Recommendation
Do not add list entries for recipient-side balance changes the recipient did not initiate, or allow the account itself to purge entries. Options: (a) only call `addToDepositTokensOfAccount` from `deposit`-initiated mints where `account_ == _msgSender()`/operator-approved beneficiary, not from `_transfer` recipients; (b) add a `sweepDust`/`leaveToken` function letting any account force-remove a token whose balance is below a threshold; (c) count entries only above a minimum balance instead of any nonzero balance.

### Proof of Concept
Foundry fork test (pool = a deployed Pool with ≥ N registered DepositTokens; the test uses the real token contracts):

```solidity
function test_DustListFillBlocksVictim() public {
    IPool pool = IPool(POOL);
    address victim = makeAddr("victim");              // holds 0..k existing positions
    address[] memory dts = pool.getDepositTokens();   // registered deposit tokens

    uint256 max = pool.MAX_TOKENS_PER_USER();         // 30
    uint256 existing = pool.getDepositTokensOfAccount(victim).length
                     + pool.getDebtTokensOfAccount(victim).length;

    // Attacker pushes 1-wei dust shares of each registered deposit token to victim
    for (uint256 i; i < dts.length && existing + i < max; ++i) {
        IDepositToken dt = IDepositToken(dts[i]);
        IERC20 underlying = dt.underlying();
        deal(address(underlying), attacker, 1 ether);
        underlying.approve(address(dt), 1 ether);
        dt.deposit(1, victim);                        // or dt.transfer(victim, 1) after self-deposit
    }

    assertEq(
        pool.getDepositTokensOfAccount(victim).length
      + pool.getDebtTokensOfAccount(victim).length,
        max
    );

    // Victim cannot deposit a collateral type not already in its list
    IDepositToken newDt = IDepositToken(dts[dts.length - 1]); // one not dusted
    deal(address(newDt.underlying()), victim, 10 ether);
    vm.startPrank(victim);
    newDt.underlying().approve(address(newDt), 10 ether);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    newDt.deposit(1 ether, victim);

    // Victim cannot open a new synthetic debt position
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    IDebtToken(newDebtToken).issue(1, victim);
    vm.stopPrank();
}
```

Caveat: I could not fully verify the number of registered deposit tokens on each deployed pool within this session; the attack requires `registered deposit tokens + victim's own debt entries ≥ 30` (or fewer if the victim already holds positions). If a target deployment has materially fewer than 30 deposit tokens, the cap is unreachable and the finding degrades to griefing users who already hold many positions.
