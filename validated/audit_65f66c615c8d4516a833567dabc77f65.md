### Title
Client-supplied `submit_timestamp` is never bound-checked at the HOP RPC boundary, letting an unauthenticated caller stage arbitrarily stale or future-dated promotion payloads for later replay - (File: `substrate/client/hop/src/rpc.rs`, `substrate/client/hop/src/pool.rs`, `substrate/primitives/hop/src/lib.rs`)

### Summary
The external report's core broken invariant is: *a value that determines settlement outcome (price) is accepted from a caller-influenced report as long as it falls within a fixed drift window relative to a target time, but nothing enforces that the window is anchored to the intended instant, so an attacker/timing choice can steer which side "wins."* The local analog is the HOP (Hand-Off Protocol) submission/promotion pipeline: `hop_submit` lets an unauthenticated RPC caller supply an arbitrary `submit_timestamp` that is bound into the signed payload and persisted, with the *only* documented tolerance-window enforcement deferred entirely to a runtime pallet that does not exist anywhere in this repository.

### Finding Description
`HopApiServer::submit` in `substrate/client/hop/src/rpc.rs` accepts `submit_timestamp: u64` directly from the RPC caller and only uses it to build the domain-separated payload that is checked against the supplied signature: [1](#0-0) 

There is no check anywhere in `sc-hop` that `submit_timestamp` is close to the node's wall-clock time before it is accepted into the pool and persisted in `HopEntryMeta`: [2](#0-1) 

The design explicitly pushes the "reject promotions whose timestamp is outside a tolerance window" invariant onto whatever runtime implements `HopRuntimeApi`: [3](#0-2) 

But grepping the entire tree for an `impl HopRuntimeApi for Runtime` or any pallet enforcing this window turns up nothing — the primitives crate (`sp-hop`) and node service (`sc-hop`) exist, but per the introducing prdoc, "this PR introduces the crate only; it has no runtime or node consumers yet", i.e. the enforcing side of the invariant is absent from the repository: [4](#0-3) 

Compounding this, the maintenance task re-submits the *same, frozen* `submit_timestamp` on every retry over the entry's lifetime (up to `MAX_PROMOTION_ATTEMPTS` with exponential back-off, and up to `retention_secs`, default 24h) rather than re-timestamping at actual promotion time: [5](#0-4) 

This mirrors the `UpDown.sol` flaw precisely: a time-bound value (`priceTimestamp` there, `submit_timestamp` here) is embedded once, checked only for internal consistency (signature validity / `10 minutes` price-vs-block window there), and is trusted for a decision that happens much later — the pallet responsible for re-validating that the bound timestamp is still "the exact time it should be" is either widened, or in this repo's case, simply doesn't exist to be exploited or audited against widening in the first place. Any downstream runtime team wiring up `HopRuntimeApi` (as the doc instructs) has no reference implementation, no test, and no enforced bound in `sc-hop` itself to catch a caller supplying a `submit_timestamp` far in the past or future — the client-side code will happily accept it, sign-check it, store it, and keep re-submitting the unsigned extrinsic carrying that stale timestamp for up to a day.

### Impact Explanation
If/when a runtime wires `create_promotion_extrinsic` per the documented contract, the client-side pipeline that feeds it does not defend the tolerance window at all — an attacker-controlled `submit_timestamp` (bounded only by "must produce a valid signature over it", which the attacker trivially controls since they choose both the message and sign it with their own key) can be crafted to land just inside whatever window the runtime pallet enforces, at whatever wall-clock moment is most advantageous, exactly like the reported price-window abuse pattern. Because `sc-hop` provides no defense-in-depth check and no example runtime implementation exists to demonstrate correct enforcement, this is a live gap for any live-scope runtime that adopts `HopRuntimeApi` as directed — it can result in stale/replayed consent being accepted as fresh, i.e. false state acceptance of a promotion that should have been rejected.

### Likelihood Explanation
Medium-to-High for any team that follows the documented integration guide literally: the guide states the timestamp binding alone prevents indefinite replay, without providing or requiring an enforced window in the shipped code, and the retry logic actively resends the original (aging) timestamp for up to 24 hours by default, so the "few hours" tolerance suggested in the doc will already be violated by the tool's own default retry schedule in ordinary operation, indicating no working end-to-end example of this invariant exists in-tree to validate against.

### Recommendation
1. Enforce the tolerance window in `sc-hop` itself (not only rely on a future runtime), rejecting `submit_timestamp` values whose skew from the node's wall clock exceeds a documented bound.
2. Have `HopMaintenanceTask::tick` re-timestamp (and re-sign, if the sender pre-authorized re-signing, or otherwise fail closed) rather than resubmitting a frozen `submit_timestamp` across a multi-hour/day retry window.
3. Ship a reference `impl HopRuntimeApi` (even a minimal example pallet) inside this repository that concretely enforces the tolerance window, so integrators have a tested, correct anchor point instead of a prose requirement.

### Proof of Concept
1. Start a node with `--enable-hop --hop-retention-secs 86400 --hop-promotion-buffer-secs 7200`.
2. Call `hop_submit(data, recipients, signature, signer, submit_timestamp)` where `submit_timestamp` is computed and signed honestly at `T0`.
3. The entry sits in the pool; `HopMaintenanceTask::tick` only starts attempting promotion at `T0 + (retention_secs - buffer_secs)` ≈ `T0 + 22h`, still using the original `submit_timestamp` from `T0`.
4. If the runtime enforces a "few hours" tolerance window as `sp-hop` recommends, the promotion extrinsic is rejected as stale by design of the very tool meant to promote it — demonstrating the shipped default configuration and retry logic are inconsistent with the documented on-chain invariant, and that no code in this repository validates the window is honored correctly for either direction (too old or attacker-chosen freshness).
