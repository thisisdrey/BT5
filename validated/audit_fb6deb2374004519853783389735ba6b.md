Found a direct analog: `MarketCancelOrderActuator.calcFee()` and `MarketSellAssetActuator.calcFee()` both charge `dynamicStore.getMarketCancelFee()` / `dynamicStore.getMarketSellFee()` — the *current* global fee — at the moment the transaction executes, with no linkage to the fee that was in effect when the order was originally placed.

### Title
Committee can retroactively change market order fees applied at cancel/settlement time - (File: actuator/src/main/java/org/tron/core/actuator/MarketCancelOrderActuator.java)

### Summary
Same fee-timing bug class as the Sablier report: a fee parameter can be changed by governance at any time and is applied to an already-existing position (a resting order) based on the fee value in effect at the moment of the *later* action (cancel/match), not the fee value in effect when the order was created and funds were locked. Users placing orders have no guarantee of what fee they will ultimately pay to exit.

### Finding Description
`MARKET_SELL_FEE` and `MARKET_CANCEL_FEE` are global chain parameters stored in `DynamicPropertiesStore` and can be updated at any time by committee proposal via `ProposalService.process` (case `MARKET_SELL_FEE` / `MARKET_CANCEL_FEE`) with only range validation in `ProposalUtil.validator` [1](#0-0) . These proposals take effect at the next maintenance cycle with no linkage to any existing order.

`MarketOrderCapsule` orders can remain resting in the order book indefinitely (`MarketSellAssetActuator` places unmatched remainder into the book via `saveRemainOrder`). When the owner later cancels the order, `MarketCancelOrderActuator.execute()` charges `calcFee()`, which always reads the *current* value of `getMarketCancelFee()`: [2](#0-1) [3](#0-2) 

Likewise, `MarketSellAssetActuator.execute()` charges `calcFee()` = `dynamicStore.getMarketSellFee()` at the time the transaction is processed: [4](#0-3) [5](#0-4) 

No fee value is snapshotted into the `MarketOrderCapsule` at order-creation time; the fee is read fresh from `DynamicPropertiesStore` every time `calcFee()` executes. This is architecturally identical to the reported Sablier bug: the "debt/position" (the resting order and locked TRX/token) accrues under one fee regime, but a value-extracting action (cancel) charges whatever fee governance has decided is current, which can be increased (up to `10_000_000_000` sun per `MARKET_CANCEL_FEE`/`MARKET_SELL_FEE` bounds in `ProposalUtil`) after the user has already locked funds into the order, with no way for the user to have agreed to that fee in advance.

### Impact Explanation
An order placed while `MARKET_CANCEL_FEE` (or `MARKET_SELL_FEE`) is low or zero can later be charged a much higher fee purely because governance updated the parameter while the order was still resting in the book. Because `MarketCancelOrderActuator.execute()` deducts the fee from the trader's balance before returning the locked assets, the user's realizable value on exit is unexpectedly reduced (up to the maximum allowed parameter value) with no cap tied to what was agreed when the order was opened. This constitutes value extraction from users' locked funds via a governance-controlled parameter that they had no way to price in, matching the "steal via retroactive fee" impact class from the analog report — though bounded by chain-parameter governance rather than a single admin key, and limited to the market order module.

### Likelihood Explanation
Requires only that the committee approve a `MARKET_SELL_FEE`/`MARKET_CANCEL_FEE` proposal (a normal governance action already supported today) while unrelated users hold open orders; no special node compromise or malicious-SR collusion beyond the ordinary proposal process is needed, and any unprivileged user placing/cancelling market orders is affected. This is a design-level parameter-timing issue identical to the accepted (though "won't fix" by the analog vendor) report, rather than a new memory-safety or logic bug.

### Recommendation
Snapshot the applicable `MARKET_SELL_FEE` and `MARKET_CANCEL_FEE` values into `MarketOrderCapsule` at order-creation time and use that stored value in `MarketCancelOrderActuator.calcFee()` / at settlement, instead of re-reading the live `DynamicPropertiesStore` value, so a fee change only affects orders created after the change.

### Proof of Concept
1. With `MARKET_CANCEL_FEE = 0`, a user calls `MarketSellAssetContract` to place a resting sell order (`MarketSellAssetActuator.execute`), locking TRX/tokens into the order.
2. Committee approves a proposal raising `MARKET_CANCEL_FEE` to its maximum allowed value (`10_000_000_000` sun) via `ProposalService.process` (case `MARKET_CANCEL_FEE`).
3. The user calls `MarketCancelOrderContract` to cancel the still-resting order; `MarketCancelOrderActuator.execute()` computes `fee = calcFee()` which now returns the new, higher `MARKET_CANCEL_FEE`, deducting it from the user's balance before returning the locked funds — a fee the user never agreed to when the order was opened.
