### Title
Per-IP QUIC connection rate limiter can be bypassed via IPv6 address rotation within an attacker-controlled prefix, enabling per-actor QoS evasion of unstaked connection limits - ([File: streamer/src/nonblocking/connection_rate_limiter.rs])

### Summary
`ConnectionRateLimiter::is_allowed`/`register_connection` key the token bucket strictly by the literal `IpAddr` with no CIDR/prefix aggregation. An attacker who controls an IPv6 prefix (trivial to obtain from residential ISPs, cloud providers, or VPS hosts, which commonly hand out /64 or /56 blocks) can rotate the source address of each new QUIC connection to a distinct address within that prefix, so each connection is seen by `KeyedRateLimiter<IpAddr>` as a "new" key with a fresh token bucket, defeating the intended per-source throttle (`DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE`).

### Finding Description
`ConnectionRateLimiter` wraps a `KeyedRateLimiter<IpAddr>` and does all admission decisions purely on the raw `IpAddr` key: [1](#0-0) 

There is no normalization of the address to a subnet/prefix (e.g. truncating an IPv6 address to its /64 or /56 routing prefix) before it's used as the rate-limiter key. `is_allowed` and `register_connection` are invoked from the QUIC connection-establishment path in `streamer/src/nonblocking/quic.rs`, which is reachable directly by any unstaked/unprivileged remote peer opening a QUIC connection to the leader's public TPU port — no gossip membership, stake, or prior authentication is required to reach this check.

Because IPv6 gives a single actor an enormous, cheaply obtainable address space (a /64 alone provides 2^64 distinct addresses), the attacker can open successive connections from `::1`, `::2`, `::3`, ... (or any pseudo-random suffixes) drawn from the same prefix. Each address is a brand-new `IpAddr` key to `KeyedRateLimiter`, so each gets its own fresh `TokenBucket` starting at `max_burst` tokens, and the per-source limit (`DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE`) is never actually enforced against the real "actor" — only against the literal 128-bit address, which the attacker fully controls. This directly violates the stated invariant that "unstaked connection, stream, and per-IP limits are enforced per source and cannot be evaded by connection churn," since here the churn is exactly address rotation within a single controlled prefix, not distinct real sources.

The existing global unstaked-connection cap (`MAX_UNSTAKED_CONNECTIONS` and related counters in `streamer/src/nonblocking/quic.rs`) still bounds total simultaneous unstaked connections cluster-wide, so this is not an unbounded-resource/DoS bypass of every guard — but it is a bypass of the specific per-IP QoS mechanism, letting one actor consume a disproportionate share of the shared unstaked connection/stream budget that the per-IP limiter is meant to fairly ration among distinct sources.

### Impact Explanation
This is a QoS-evasion finding: a single unprivileged actor can capture a multiple of the intended per-source connection quota by rotating through IPv6 addresses in a prefix they control, starving other legitimate unstaked clients of their fair share of the leader's unstaked connection/stream budget and causing disproportionate resource consumption (connection setup, QUIC handshake, stream table entries) attributable to one actor while appearing as many distinct "sources" to the limiter. This matches the "QoS evasion" category explicitly listed as in-scope.

### Likelihood Explanation
Feasible and repeatable with only unprivileged network access: obtaining an IPv6 prefix (a /64 is standard from most consumer ISPs and cloud/VPS providers) and enumerating source addresses within it requires no stake, no validator control, and no special privileges — just a machine capable of binding to arbitrary addresses in its assigned prefix (or a provider that routes the whole prefix to the attacker). The exploit is a straightforward loop of QUIC connection attempts with rotating local IPv6 source addresses.

### Recommendation
Normalize/truncate IPv6 keys to a fixed prefix length (e.g., /64 or /56, matching typical allocation boundaries) before use as the `KeyedRateLimiter` key in `ConnectionRateLimiter`, so that all addresses within an attacker-controlled block share one token bucket. Consider making the prefix length configurable via the existing validator CLI options for per-IP limits.

### Proof of Concept
Rust unit test to add to `streamer/src/nonblocking/connection_rate_limiter.rs`:
```rust
#[tokio::test]
async fn test_ipv6_prefix_rotation_bypasses_rate_limiter() {
    use std::net::{IpAddr, Ipv6Addr};
    let limiter = ConnectionRateLimiter::new(3, 3, 4);
    let base: u128 = Ipv6Addr::new(0x2001, 0xdb8, 0, 0, 0, 0, 0, 0).into();
    let mut admitted = 0;
    // Same attacker-controlled /64 prefix, distinct low 64 bits each time.
    for i in 0..1000u128 {
        let ip = IpAddr::V6(Ipv6Addr::from(base + i));
        if limiter.register_connection(&ip) {
            admitted += 1;
        }
    }
    // Expected (desired) behavior: admitted should be bounded by the
    // per-actor/per-prefix budget (e.g. <= max_burst == 3).
    // Actual behavior with current code: admitted == 1000, showing the
    // per-IP limiter never throttles because each address is a new key.
    assert!(
        admitted <= 3,
        "per-prefix rate limit bypassed: {admitted} connections admitted from rotated IPv6 addresses in a single /64"
    );
}
```
Expected result on current code: assertion fails with `admitted == 1000`, demonstrating that address rotation within one IPv6 prefix defeats `DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE`.

        if self.limiter.consume_tokens(*ip, 1).is_ok() {
            debug!("Request from IP {ip:?} allowed");
            true // Request allowed
        } else {
            debug!("Request from IP {ip:?} blocked");

        }
    }
