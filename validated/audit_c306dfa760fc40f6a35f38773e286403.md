### Title
Attachment size cap `AtlasConfig::attachments_max_size` is not enforced on attachments fetched from peers via `GetAttachmentResponse` - ([File: stackslib/src/net/atlas/mod.rs])

### Summary
`GetAttachmentResponse::deserialize` decodes an arbitrary-length hex string into an `Attachment` with no length check [1](#0-0) . The only size-enforcement helper, `AtlasDB::should_keep_attachment`, checks `attachment.content.len() as u32 > self.atlas_config.attachments_max_size` [2](#0-1) , but the `AttachmentsDownloader` path that ingests peer-served attachments never calls it before storing the content.

### Finding Description
The claimed equality is: "attachment content length stored in `AtlasDB` <= configured `attachments_max_size`". This equality is broken for attachments obtained via peer-to-peer download.

The exploit path:
1. A remote peer implements the `/v2/attachments/<hash>` endpoint (or the attacker's own node responds when queried by a victim doing attachment sync) and returns a `GetAttachmentResponse` JSON body whose hex payload decodes to an oversized byte array.
2. `RPCGetAttachmentRequestHandler::try_parse_response` calls `parse_json` which deserializes into `GetAttachmentResponse`, invoking the custom `Deserialize` impl at `stackslib/src/net/atlas/mod.rs:69-77`. That impl does `hex_bytes(&hex_encoded)` and constructs `Attachment::new(bytes)` with **no length check against `attachments_max_size`**.
3. `StacksHttpResponse::decode_atlas_get_attachment` (`stackslib/src/net/api/getattachment.rs:158-165`) returns this oversized `GetAttachmentResponse` unchanged.
4. In the downloader, `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`) takes the decoded attachment and inserts it directly into `self.attachments: HashSet<Attachment>` with no size check at all.
5. `AttachmentsDownloader::run` (`stackslib/src/net/atlas/download.rs:152-169`) then iterates `context.attachments.drain()` and calls `network.atlasdb.insert_instantiated_attachment(&attachment)` directly, which unconditionally writes the content to the `attachments` SQLite table (`stackslib/src/net/atlas/db.rs:576-592`) — this method performs no size validation either.

The only place `attachments_max_size` is actually enforced is `AtlasDB::should_keep_attachment`, which is exclusively invoked from the locally-submitted-transaction attachment path (`stackslib/src/net/api/posttransaction.rs`) for attachments a client posts directly to the node's own RPC — not from the peer-download path (`download.rs`). This means the config-documented cap ("The values used in the example below are the minimum values which Atlas will accept") is silently bypassed for any attachment fetched from a remote peer during Atlas sync.

### Impact Explanation
Any remote peer that a victim node syncs attachments from (an outbound sync peer, discoverable simply by running a Stacks P2P/RPC-reachable node) can serve one or more oversized `Attachment` payloads in response to `GET /v2/attachments/<hash>` requests. Each such attachment is persisted into the victim's `AtlasDB` SQLite `attachments` table without any bound, regardless of the operator's configured `attachments_max_size` (default minimum 1 MiB, but operator-raisable — the point is the cap is simply not enforced at all in this path). Repeated across the (bounded) set of `AttachmentInstance`s the node is trying to resolve, this allows storage exhaustion far beyond the configured limit, matching the "High: bounded/unbounded storage exhaustion via a single class of oversized data bypassing the configured cap" category.

### Likelihood Explanation
- Attacker precondition: only needs to be an outbound-reachable peer that the victim's Atlas downloader queries for attachment content — no privileged role, no signature or secret needed.
- The victim must have at least one unresolved `AttachmentInstance` referencing content the attacker can serve (attacker can also relay BNS-name-registration-triggered attachment instances that reference their own served hash, since the hash is checked against `Attachment::hash()` == `Hash160::from_data(content)`, which an attacker fully controls by crafting oversized content matching the requested hash).
- Cost is a single crafted HTTP response per attachment instance; fully repeatable per instance and across nodes.

### Recommendation
Enforce `attachments_max_size` at the point attachments are ingested from the network:
- Add a size check inside `GetAttachmentResponse::deserialize` (`stackslib/src/net/atlas/mod.rs`) — though this struct doesn't have access to `AtlasConfig`, so the check is better placed immediately after decoding.
- More robustly, call `atlas_db.should_keep_attachment(...)`-equivalent logic (or a standalone size check against `atlas_config.attachments_max_size`) in `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`) before inserting into `self.attachments`, and/or in `AttachmentsDownloader::run` before calling `insert_instantiated_attachment` (`stackslib/src/net/atlas/download.rs:161`), discarding/penalizing peers that serve oversized attachments.

### Proof of Concept
```rust
// stackslib/src/net/atlas/download.rs (or a new test module)
#[test]
fn test_oversized_attachment_bypasses_max_size_via_extend_with_attachments() {
    let atlas_config = AtlasConfig {
        contracts: HashSet::new(),
        attachments_max_size: 1024, // 1KB cap
        max_uninstantiated_attachments: 100,
        uninstantiated_attachments_expire_after: 10,
        unresolved_attachment_instances_expire_after: 10,
        genesis_attachments: None,
    };
    let mut atlas_db = AtlasDB::connect_memory(atlas_config.clone()).unwrap();

    // Simulate an oversized attachment "served" by a malicious peer via GetAttachmentResponse
    let oversized_content = vec![0xAA; 10 * 1024 * 1024]; // 10MB, far > 1KB cap
    let oversized_attachment = Attachment::new(oversized_content);

    // should_keep_attachment correctly rejects it when checked directly
    assert!(!atlas_db.should_keep_attachment(&boot_code_id("bns", false), &oversized_attachment));

    // But the downloader path never calls should_keep_attachment:
    // extend_with_attachments just inserts into the HashSet unconditionally.
    let mut context = AttachmentsBatchStateContext::new(
        AttachmentsBatch::new(),
        HashMap::new(),
        &ConnectionOptions::default(),
    );
    context.attachments.insert(oversized_attachment.clone());

    // insert_instantiated_attachment stores it with no size check
    atlas_db.insert_instantiated_attachment(&oversized_attachment).unwrap();

    let stored = atlas_db.find_attachment(&oversized_attachment.hash()).unwrap().unwrap();
    assert_eq!(stored.content.len(), 10 * 1024 * 1024); // stored despite exceeding attachments_max_size=1024
}
```
This demonstrates that `insert_instantiated_attachment` (the call used by `AttachmentsDownloader::run`, `stackslib/src/net/atlas/download.rs:161`) stores content of arbitrary size, while the only enforcement function (`should_keep_attachment`) is bypassed entirely in that code path.

impl<'de> Deserialize<'de> for GetAttachmentResponse {
    fn deserialize<D: serde::Deserializer<'de>>(d: D) -> Result<GetAttachmentResponse, D::Error> {
        let payload = String::deserialize(d)?;
        let hex_encoded = payload.parse::<String>().map_err(de_Error::custom)?;
        let bytes = hex_bytes(&hex_encoded).map_err(de_Error::custom)?;
        let attachment = Attachment::new(bytes);
        Ok(GetAttachmentResponse { attachment })
    }
}

    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }
