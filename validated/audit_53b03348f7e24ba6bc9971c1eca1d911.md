## Analog Found

### Title
Anonymous/unauthenticated `getPaginatedNowWitnessList` API triggers full unpaginated scan of `VotesStore` and `WitnessStore` per request, enabling database/CPU resource exhaustion - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
The Nextcloud CVE lets a low-privileged, authenticated user send a cheap request (sharee recommendation) that internally triggers expensive, effectively unbounded database work through the Circles app. The java-tron analog is the `getPaginatedNowWitnessList` API: despite accepting an `offset`/`limit` pagination request, its implementation performs a full, unbounded scan (and destructive consumption) of the entire `VotesStore` and the entire `WitnessStore` on every single call, regardless of how small the requested page is.

### Finding Description
`Wallet.getPaginatedNowWitnessList(long offset, long limit)` caps `limit` to `WITNESS_COUNT_LIMIT_MAX`, but before any pagination is applied it:
1. Loads **all** witnesses via `chainBaseManager.getWitnessStore().getAllWitnesses()` [1](#0-0) 
2. Calls the private `countVote(votesStore)` helper, which iterates **every entry in `VotesStore`** — i.e., every account that has voted in the current epoch — accumulating `oldVotes`/`newVotes` deltas into a `HashMap` [2](#0-1) 
3. Applies the vote deltas to every witness, sorts the **entire** witness list, and only then applies `.skip(offset).limit(limit)` [3](#0-2) 

The cost of steps 1–3 is proportional to the total number of witnesses and the total number of voting accounts network-wide (potentially very large), not to the requested `limit`. A request for `limit=1` costs the same as a request for the maximum page size. This is exactly the CVE-2022-39330 bug class: a cheap/small request parameter drives disproportionate, uncapped backend work.

This endpoint is exposed with no signature/permission requirement — it is a pure read query reachable by any anonymous HTTP/gRPC client via:
- HTTP: `/wallet/getpaginatednowwitnesslist` served by `GetPaginatedNowWitnessListServlet` [4](#0-3) 
- gRPC: `WalletSolidity.getPaginatedNowWitnessList` in `RpcApiService` [5](#0-4) 
- Also mirrored on the FullNode wallet path, registered in `FullNodeHttpApiService` [6](#0-5) 

The only throttling in front of these handlers is the generic `RateLimiterServlet`, which is a per-API/global QPS limiter, not a cost-aware limiter — it does not account for the fact that this particular call is far more expensive per-invocation than most other endpoints, so a modest sustained request rate that passes the QPS limit can still repeatedly force full-store scans.

### Impact Explanation
Repeated calls to this single, unauthenticated, cheap-looking API force the node to repeatedly perform full linear scans over the `VotesStore` (bounded by the number of distinct voting accounts in the current epoch, potentially very large on a busy chain) and the `WitnessStore`, plus full in-memory sorting of the witness list, on every call. An attacker (or even an anonymous/uncredentialed client, since no signature is required — a lower bar than the Nextcloud CVE's "logged-in user" requirement) can drive sustained elevated CPU and I/O load on a full node or witness node by issuing many such requests, degrading the node's ability to serve other API/RPC/sync traffic — a node-level denial-of-service / API-availability impact consistent with the accepted impact class ("an API the node can no longer serve").

### Likelihood Explanation
The endpoint requires no authentication, no transaction fee, and no special permission — any network client that can reach the node's HTTP or gRPC listener can call it repeatedly. The only friction is the generic rate limiter, which limits request *count*, not request *cost*; because this handler's cost is decoupled from its `limit` parameter, an attacker gets maximal backend work per allowed request. This makes the analog straightforward to trigger at low cost, similar to the "AC:H" but ultimately practically exploitable nature of the original CVE.

### Recommendation
Change `countVote`/`getPaginatedNowWitnessList` to avoid a full unbounded scan of `VotesStore` on every paginated read — e.g., cache the computed vote-delta map per epoch/block and invalidate/recompute it only once per relevant state change, rather than recomputing it from a full store iteration on each API call. Alternatively, make the cost of this endpoint bounded and independent of total vote/witness counts, or apply a cost-weighted rate limit specific to this handler.

### Proof of Concept
1. On a live full node with many voting accounts (large `VotesStore`), repeatedly send:
   ```
   POST /wallet/getpaginatednowwitnesslist
   {"offset": 0, "limit": 1}
   ```
   or the gRPC equivalent `WalletSolidity.getPaginatedNowWitnessList` with `offset=0, limit=1`.
2. Each request causes the node to internally execute `Wallet.getPaginatedNowWitnessList` [7](#0-6) , which fully iterates `VotesStore` (via `countVote`) and `WitnessStore` (via `getAllWitnesses`) before returning just 1 witness.
3. Firing this request at the maximum rate allowed by `RateLimiterServlet` sustains repeated full-store scans, consuming CPU/I/O disproportionate to the trivial `limit=1` response, degrading node responsiveness for other clients.

```java
  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
```
