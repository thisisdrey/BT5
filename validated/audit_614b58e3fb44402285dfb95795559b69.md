### Title
`Treasury.claimFromVesper` permanently reverts when a reward token is a pool collateral, freezing all accrued Vesper rewards - (File: contracts/Treasury.sol)

### Summary
The analog of the AeraVault/MerkleOrchard issue ("contract entitled to external rewards but cannot collect them") is `Treasury.claimFromVesper`, the only code path by which the Treasury collects rewards earned by its Vesper vToken positions. The implementation exists but contains a broken accounting line that, whenever a Vesper reward token is also a Metronome deposit collateral, underflows and reverts. Because the subtraction sits inside a `for` loop over every reward token, one bad reward token bricks the whole claim call — meaning *all* reward tokens (not just the collateral one) become unclaimable while the condition holds. [1](#0-0) 

### Finding Description
`claimFromVesper` claims rewards into the Treasury, then iterates `_rewards.getRewardTokens()`:

```solidity
// contracts/Treasury.sol:87-99
for (uint256 i; i < _len; ++i) {
    IERC20 _token = IERC20(_rewardTokens[i]);
    uint256 _amount = _token.balanceOf(address(this));

    // Note: If the reward token is a collateral, transfer the surpass balance only
    IDepositToken _depositToken = _pool.depositTokenOf(_token);
    if (address(_depositToken) != address(0)) {
        _amount -= _depositToken.totalSupply();
    }

    if (_amount > 0) {
        _token.safeTransfer(to_, _amount);
    }
}
```

Two compounding defects:

1. **Underflow brick**: `_depositToken.totalSupply()` is denominated in *deposit-token shares* (which grow with accrued interest and are 18-decimals regardless of underlying), while `balanceOf` is in underlying units. Whenever `balanceOf(treasury) < depositToken.totalSupply()` — which is the normal steady state, since the Treasury only holds the *surplus* (fees/pull buffer), not the backing of all issued shares — the subtraction reverts with a panic underflow. The revert happens inside the loop, so the entire `claimFromVesper` call fails every time it is attempted, for every reward token. [2](#0-1) 
2. **Wrong surplus computation even when it doesn't revert**: comparing a token balance to a share supply compares two different units. Even when `balanceOf >= totalSupply`, the "surplus" transferred is computed against share count, not against the underlying actually owed to depositors, so the amount forwarded to `to_` can be wrong in either direction.

Vesper pool rewards are the yield the Treasury position earns — there is no other function in `Treasury.sol` that claims them, so a permanently reverting `claimFromVesper` replicates the original bug: rewards accrue in `PoolRewards` for the Treasury but can never be moved out. [3](#0-2) 

### Impact Explanation
Permanent freezing of unclaimed yield. Once a reward token that is also a pool collateral appears in `getRewardTokens()` and `rewardToken.balanceOf(treasury) < depositToken.totalSupply()`, every call to `claimFromVesper` reverts and all reward tokens earned by the Treasury's Vesper position are stuck. The RewardsDistributor's `syncTokenSpeed` path compounds the problem: it distributes rewards *to users* proportionally to `_vPool.balanceOf(treasury) / _vPool.totalSupply()` assuming the Treasury will actually collect those rewards via `claimFromVesper` — if claiming is bricked, the distributor promises `rewardToken` emissions it may never receive, so `claimRewards` payouts to depositors/borrowers can silently fail via `_transferRewardIfEnoughTokens` (insufficient `rewardToken` balance → no transfer, accrued amounts never paid out). [4](#0-3) [5](#0-4) 

### Likelihood Explanation
The trigger does not require any privileged misbehavior: it activates automatically if (a) a Vesper `PoolRewards` contract distributes a token that is also registered as a Metronome deposit collateral (e.g., underlying-denominated reward programs or reward tokens later added as collateral), and (b) `balanceOf(treasury) < depositToken.totalSupply()` for that token, which is the expected state since the Treasury deliberately holds only surplus. No reentrancy guard, pause flag, or `_msgSender` check mitigates it — the revert is an arithmetic underflow on an unrestricted code path reached by the governor's routine claim call. Likelihood depends on reward-token/collateral overlap in the deployed Vesper pools, which cannot be fully confirmed from the repo alone; if no reward token is ever a collateral, the bug is dormant but the unit-mismatch defect still produces an incorrect surplus amount whenever it is.

### Recommendation
Compute the surplus in underlying terms, not against share supply, and skip instead of reverting:

```solidity
uint256 _owed = _depositToken.totalSupply().wadMul(<underlying-per-share exchange rate or tracked backing>);
_amount = _amount > _owed ? _amount - _owed : 0;
```

At minimum, wrap the subtraction in a guarded check (`if (balance > required) _amount = balance - required; else _amount = 0;`) and process each reward token independently so one bad token cannot brick claims of the others. Alternatively, keep rewards in a dedicated balance slot/accounting counter so collateral backing and claimable surplus are never compared across units.

pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Treasury} from "../contracts/Treasury.sol";
import {IVPool} from "../contracts/interfaces/external/IVPool.sol";
import {IPoolRewards} from "../contracts/interfaces/external/IPoolRewards.sol";

/// @dev Demonstrates that claimFromVesper permanently reverts when a reward
/// token is a registered deposit collateral and the treasury's underlying
/// balance is below the deposit token's share supply (the normal state).
contract ClaimFromVesperStuckTest is Test {
    Treasury treasury;        // deployed behind proxy, initialize(pool)
    address constant GOV = address(0xG0V);

    function setUp() public {
        // 1. Deploy + initialize Treasury against the real Pool (fork).
        // 2. Mock/prepare Vesper poolRewards so getRewardTokens() returns
        //    [weth, op] where WETH is a pool collateral (depositTokenOf != 0).
        // 3. Give the treasury a small surplus: e.g. 10 WETH balance while
        //    msETH DepositToken totalSupply() == 1000e18 shares.
    }

    function test_claimBricksOnCollateralRewardToken() public {
        vm.prank(GOV);
        // _amount = balanceOf(treasury)=10e18; totalSupply=1000e18 -> underflow
        vm.expectRevert(); // arithmetic underflow inside the reward loop
        treasury.claimFromVesper(vPool, GOV);

        // Every subsequent call reverts identically: rewards are stuck forever,
        // including reward tokens listed *after* the collateral token.
    }
}
