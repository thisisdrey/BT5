### Title
Non-saturating `block_cost` subtraction in `CostTracker::sub_transaction_execution_cost` can wrap `SharedBlockCost` and stall block production - ([File: cost-model/src/cost_tracker.rs])

### Summary
`CostTracker` tracks aggregate execution cost for the current block in two places that are supposed to stay consistent: a per-account `HashMap<Pubkey, u64>` and a single shared `block_cost: SharedBlockCost` (an `AtomicU64`). When the tracker reduces cost after learning a transaction's *actual* execution cost, the per-account values are decremented with `saturating_sub`, but the block-level total is decremented with a plain, non-saturating `AtomicU64::fetch_sub`. This is the same accounting-drift/underflow pattern described in the reference report: a value is maintained as "recorded total minus a later adjustment" without guaranteeing the adjustment can never exceed the recorded total, and the reduction path does not use protected/saturating arithmetic consistently with the rest of the accounting.

### Finding Description
`CostTracker::try_add` publishes a transaction's estimated cost to both the per-account map and to `block_cost` via `self.block_cost.fetch_add(cost)`. [1](#0-0) 

When costs are later reduced (e.g. to reconcile an estimated cost against the actual execution cost, exercised by `test_adjust_transaction_execution_cost` and the dedicated `scheduler_cost_adjustment.rs` test), `sub_transaction_execution_cost` is used: [2](#0-1) 

Note the asymmetry inside this single function:
- Per-account costs: `account_cost.saturating_sub(adjustment)` — cannot underflow.
- Block-level cost: `self.block_cost.fetch_sub(adjustment)` — a raw `AtomicU64::fetch_sub`, which **wraps** (does not panic, does not saturate) if `adjustment` exceeds the current stored value.

`SharedBlockCost::fetch_sub` performs exactly this unprotected subtraction: [3](#0-2) 

`transaction_count`/other counters use `Saturating<u64>` wrappers elsewhere in the same struct, showing the codebase's own intended invariant is "never underflow these block-level counters" — the shared `block_cost` field alone breaks that invariant. [4](#0-3) 

This mirrors the reported bug class precisely: a cumulative-since-snapshot value (`block_cost`) is decremented by an "adjustment" computed from a separate, not-strictly-bounded source (actual vs. estimated per-transaction cost, computed in `runtime/src/transaction_execution.rs::get_transaction_costs` / `CostModel::calculate_cost_for_executed_transaction`), and the subtraction path does not defensively clamp to the tracked total the way the per-account map does. [5](#0-4) [6](#0-5) 

### Impact Explanation
`block_cost` gates every subsequent transaction admitted into the block: `try_add` rejects new transactions once `block_cost().saturating_add(cost) > limits.block_cost`. [7](#0-6) 
If `block_cost` ever wraps to a value near `u64::MAX` (from an underflowing `fetch_sub`), `saturating_add` immediately saturates to `u64::MAX`, so effectively every future `try_add` call in that bank fails with `WouldExceedBlockMaxLimit` for the remainder of the slot — i.e. the leader stops packing transactions into the block it is producing. This is a concrete, node-level denial-of-service on block production reachable purely through the ordinary banking-stage transaction execution/cost-tracking pipeline, without any validator/operator privilege.

### Likelihood Explanation
This requires the reduction path (`sub_transaction_execution_cost` / any adjustment based on actual-vs-estimated cost) to be invoked with an `adjustment` larger than what remains tracked for the block — e.g. through double-application of an adjustment, a stale/duplicate cost reconciliation, or any accounting path (analogous to the report's "outflows that don't refresh the snapshot") that consumes/reduces `block_cost` outside of the exact bookkeeping that added it. I was not able to fully trace, within the tool budget, the exact production call site that invokes `sub_transaction_execution_cost` (it only appears inside `cost-model/src/cost_tracker.rs` itself and its test module, plus the dedicated `core/tests/scheduler_cost_adjustment.rs` integration test, which confirms an "estimated vs. actual cost adjustment" feature exists and is exercised in tests). Without confirming the exact conditions under which `adjustment > current block_cost` can be triggered from a live banking-stage/scheduler code path, likelihood cannot be rated with full confidence — this is a structural/code-level flaw (proven by the source), but end-to-end unprivileged triggerability from network-supplied transactions is not fully verified from the available index.

### Recommendation
Make `SharedBlockCost`/`CostTracker::sub_transaction_execution_cost` consistent with the rest of the struct's underflow-safe design:
- Replace `self.block_cost.fetch_sub(adjustment)` with a saturating compare-and-swap loop (or store a `Saturating<u64>`/clamp-to-zero helper), mirroring the `saturating_sub` already used for the per-account map.
- Add an invariant/assert (in debug builds) that `adjustment <= block_cost()` before subtracting, to catch any caller-side miscalculation early instead of allowing a silent wraparound in production.
- Audit all call sites that compute the "adjustment" (estimated cost minus actual cost) to ensure it can never be applied more than once per transaction and is always bounded by what was actually added via `try_add` for that transaction.

### Proof of Concept
Constructing a full end-to-end PoC would require driving a real double-adjustment or duplicate-removal race against `CostTracker` from the banking stage, which I could not fully confirm within the available search budget (the exact caller of `sub_transaction_execution_cost` in production code was not located). At the unit level, the flaw itself is directly demonstrable by calling `sub_transaction_execution_cost` with an `adjustment` larger than the account's/block's current cost: the per-account entry correctly saturates to `0`, while `block_cost` (`SharedBlockCost::fetch_sub`) wraps to a value close to `u64::MAX`, as can be seen by extending `test_adjust_transaction_execution_cost` with an adjustment greater than the tracked `block_cost`. [8](#0-7)

        &mut self,

/// Wrapper around blockcost to allow fast sharing of the value without locking.
/// Value is read-only outside of cost-tracker.
#[derive(Debug, Clone)]
pub struct SharedBlockCost(Arc<AtomicU64>);

impl SharedBlockCost {
    pub fn new(value: u64) -> Self {
        Self(Arc::new(AtomicU64::new(value)))
    }

    fn fetch_add(&self, value: u64) -> u64 {
        self.0.fetch_add(value, Ordering::Release)
    }

    fn fetch_sub(&self, value: u64) -> u64 {
        self.0.fetch_sub(value, Ordering::Release)
    }

    pub fn load(&self) -> u64 {
        self.0.load(Ordering::Acquire)
    }
}

// Get actual transaction execution costs from transaction commit results
fn get_transaction_costs<'a, Tx: TransactionWithMeta>(
    bank: &Bank,
    commit_results: &[TransactionCommitResult],
    sanitized_transactions: &'a [Tx],
) -> Vec<Option<TransactionCost<'a, Tx>>> {
    assert_eq!(sanitized_transactions.len(), commit_results.len());

    commit_results
        .iter()
        .zip(sanitized_transactions)
        .map(|(commit_result, tx)| {
            if let Ok(committed_tx) = commit_result {
                Some(CostModel::calculate_cost_for_executed_transaction(
                    tx,
                    committed_tx.executed_units,
                    committed_tx.loaded_account_stats.loaded_accounts_data_size,
                    &bank.feature_set,
                ))
            } else {
                None
            }
        })
        .collect()
}
