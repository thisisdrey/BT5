### Title
Unhandled ststx-ratio external call revert in oracle callcode transform permanently freezes any position touching stSTX/zstSTX/zSTX-related mask entries - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`resolve-ststx` in `v0-4-market.clar` performs a direct external call to a hard-coded oracle contract (`SP4SZE494VC2YC5JYG7AYFQ44F5Q4PYV7DVMDPBG.block-info-nakamoto-ststx-ratio-v2`) via `call-ststx-ratio`, and `unwrap!`s the result with no fallback. Because every position-mutating entry point (`borrow`, `collateral-remove`, `liquidate`, etc.) must resolve prices for **all enabled assets in the user's mask** — not just the asset being touched — a single revert from this one external call cascades into an unconditional revert of every operation on any position that has stSTX or a zstSTX/zststxbtc-derived ztoken enabled in its collateral/debt mask, exactly mirroring the "unhandled external call revert blocks a critical state transition" bug class from the referenced report.

### Finding Description
`call-ststx-ratio` is a direct, non-defensive `contract-call?` to an external, DAO-uncontrolled principal: [1](#0-0) 

`resolve-ststx` `unwrap!`s that call with no `try/catch`-equivalent recovery path: [2](#0-1) 

`resolve-ztoken` for `CALLCODE-ZSTSTX` chains through `resolve-ststx` as well, so both the `stSTX` price and the `zstSTX` price transform depend on this single external call: [3](#0-2) 

`price-resolve` propagates any failure from `resolve-callcode` via `try!`, and `price-multi-resolve`/`iter-price-multi` propagate any single asset's failure into `ERR-ORACLE-MULTI`, aborting the entire batch: [4](#0-3) 

Critically, `get-assets` resolves prices for **every enabled asset present in the user's mask**, not only the asset being operated on: [5](#0-4) 

This function is called from `borrow`, `collateral-remove` (when the user has debt), and `liquidate`, all of which fetch the full-mask asset list before performing health checks: [6](#0-5) [7](#0-6) 

Consequently, if a user's position mask includes stSTX collateral, zstSTX collateral, or debt in any ztoken keyed off `resolve-ststx` (`zstSTX`, indirectly `zstSTXbtc`), then a persistent revert of the external `block-info-nakamoto-ststx-ratio-v2` contract call — whether from that contract being paused, deprecated, upgraded incompatibly, or simply reverting on some input — makes `resolve-ststx` fail every single time, which in turn makes `get-assets`/`price-multi-resolve` fail every time, which reverts `borrow`, `collateral-remove` (with debt), and `liquidate` for that account unconditionally.

### Impact Explanation
This is a **temporary freezing of funds** condition (in-scope impact): affected users cannot repay debt, cannot withdraw/remove any of their collateral (even non-stSTX collateral, since the health check requires resolving the *entire* mask), and — more severely — **liquidators cannot liquidate these positions either**, since `liquidate` also calls `get-assets`/`get-notional-evaluation` over the full mask before computing health and liquidation parameters. If the position becomes undercollateralized while the external oracle call is broken, bad debt cannot be created and socialized through the normal liquidation path, and the position is stuck. There is no admin/DAO bypass in `v0-4-market.clar` for this callcode failure mode (unlike the disabled-collateral price-failure path which has a distinct, still-unwrap-guarded branch). Since the failure is triggered by an ordinary external dependency (not by DAO misconfiguration or an accidental registry update), and blocks unprivileged users' own operations on their own positions, this is a reachable-by-anyone availability bug rather than a design decision.

### Likelihood Explanation
Likelihood is moderate: it requires the specific external `block-info-nakamoto-ststx-ratio-v2` contract to start reverting (e.g. due to it being paused/deprecated/buggy upstream, hitting an internal invariant, or being replaced without market.clar being upgraded in lockstep) while users still hold stSTX/zstSTX-tied positions. This is analogous to the referenced Salty DAO finding where an external dependency's revert permanently blocked a critical state transition (ballot finalization) — here the blocked transition is any collateral/debt state change (or liquidation) for affected accounts.

### Recommendation
Wrap the `call-ststx-ratio` external call in a recoverable path (Clarity's `match`/`unwrap!` already provide handling primitives, but currently there is no fallback value or "last known good ratio" cache), so that a stale/cached ratio (with staleness bound) or an explicit graceful-degradation path is used instead of unconditionally reverting every operation that touches any asset priced through `resolve-ststx`/`resolve-ztoken`. At minimum, provide a DAO-settable override/cached ratio and/or ensure the disabled-collateral-style price-failure branch pattern (isolating one asset's failure) is applied uniformly so a single upstream call failure cannot brick health checks across an entire position/mask, and specifically ensure liquidation remains reachable even if only the affected asset's price is unavailable.

### Proof of Concept
1. A user enables stSTX as collateral and borrows USDC against it, so their position mask has both `stSTX` collateral and `USDC` debt bits set.
2. The external contract `SP4SZE494VC2YC5JYG7AYFQ44F5Q4PYV7DVMDPBG.block-info-nakamoto-ststx-ratio-v2` begins reverting on `get-ststx-ratio-v3` (e.g., due to an unrelated upstream incident/upgrade/pause).
3. User calls `repay` (which similarly requires accruing/pricing the full mask through `get-assets`) or `collateral-remove` on their USDC-unrelated... actually to remove USDC debt they'd call repay/borrow paths — attempt `borrow` more USDC: `get-assets mask` → `price-multi-resolve` → `iter-price-multi` → `price-resolve` for the stSTX asset entry → `resolve-callcode` → `resolve-ststx` → `unwrap! (call-ststx-ratio) ...` reverts → the whole `borrow` call reverts with `ERR-ORACLE-CALLCODE`/`ERR-ORACLE-MULTI`.
4. A liquidator attempts `liquidate` on this now-undercollateralized position (e.g., after a market STX price drop). `liquidate` calls `get-full-position`, `accrue-user-collateral`, then `get-assets mask` → same `resolve-ststx` failure → `liquidate` reverts, so the position cannot be liquidated even though it should be.
5. The user's collateral remains locked and their debt remains outstanding/growing (interest still accrues in the vault via periodic `accrue`), with no path in `v0-4-market.clar` to unstick the position until the external `block-info-nakamoto-ststx-ratio-v2` contract call succeeds again.
