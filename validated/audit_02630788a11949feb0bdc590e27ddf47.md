### Title
Permanent denial-of-service / fund freeze in the ETH-implicit Wallet Contract via out-of-gas panic during `rlp_execute_callback`, permanently sticking `has_in_flight_tx = true` - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (the eth-implicit account contract deployed for every ETH-implicit account, see NEP-518) uses a `has_in_flight_tx` flag to serialize execution of Ethereum-emulated transactions [1](#0-0) . Just like the RubiconRouter contract that becomes the recorded `offer.owner` and provides no way to reverse that state if the offer is never filled, the `WalletContract` becomes the sole owner of the account's funds and access, and the only way to clear its in-flight lock is for one of its `#[private]` callback methods (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`, `ban_relayer`) to run to completion and commit `self.has_in_flight_tx = false` [2](#0-1) . If that callback receipt itself fails (e.g. runs out of gas) before finishing, NEAR's execution model discards *all* state writes performed during that function call, including the early `self.has_in_flight_tx = false` write, leaving the flag permanently stuck at `true` with no remaining code path capable of resetting it.

### Finding Description
`rlp_execute` immediately rejects any call while `has_in_flight_tx` is `true`, and only sets it back to `false` inside its callbacks [3](#0-2) .

For a generic action (`FunctionCall`, `Transfer`, etc.), the flow always resolves via `rlp_execute_callback`, which is scheduled with a fixed static gas amount `RLP_EXECUTE_CALLBACK_GAS = 5 Tgas`: [4](#0-3) 

That callback sets `self.has_in_flight_tx = false` as its first statement, then reads and re-serializes the promise result of the cross-contract call it made on the user's behalf: [2](#0-1) 

The `target` and the `FunctionCall` action's arguments/gas are attacker-influenced when the eth-implicit account owner (or its registered relayer) uses `rlp_execute` to call an arbitrary contract, per `action_to_promise` [5](#0-4) . A target contract can be crafted to return a very large successful value. Processing that value in `rlp_execute_callback` (reading `env::promise_result(0)` and constructing/serializing `ExecuteResponse` for the outer receipt return) consumes gas that is bounded only by the fixed, low `RLP_EXECUTE_CALLBACK_GAS` static allocation, not by the size of the returned payload. If that gas is exhausted, the callback function call fails (a WASM trap / out-of-gas), and per NEAR runtime semantics, **all state changes made by a function call that fails are rolled back** — including the `self.has_in_flight_tx = false` write that happened earlier in the same execution.

Because every path capable of resetting `has_in_flight_tx` is one of these same private callbacks, none of which can complete, the flag remains `true` in committed trie state forever. All subsequent `rlp_execute` calls are then immediately rejected at the top of the function [6](#0-5) , with no other mutating entry point exposed by the contract to clear the flag.

### Impact Explanation
This permanently freezes the ETH-implicit account: it can never again submit any NEAR-native action (transfers, function calls, key management) via `rlp_execute`, since every call is rejected by the stuck `has_in_flight_tx` guard. Any NEAR tokens or NEP-141 balances associated with that address, and any assets the account could otherwise move, become permanently inaccessible — matching the "permanent freezing of funds" impact class analogous to the Rubicon offers locked forever in `RubiconRouter` with no cancellation path.

### Likelihood Explanation
The account owner (or any relayer holding a `rlp_execute` function-call access key for that account) can trigger this simply by directing an `rlp_execute` call at a contract (which they fully control, e.g., their own malicious contract) that returns an oversized successful value on the targeted method, causing the fixed 5 Tgas callback budget to be exhausted. No privileged/validator/network access is required — it is reachable purely through ordinary transaction/receipt execution against a user-deployed contract used as the `target`.

### Recommendation
Do not gate the reset of `has_in_flight_tx` behind the same computation that can exhaust gas. Options include: (1) resetting `has_in_flight_tx = false` and persisting that state via a separate minimal-gas write/receipt before attempting to process/serialize the (potentially large) promise result, (2) bounding/truncating the size of `success_value` copied into `ExecuteResponse` and provisioning callback static gas proportional to the maximum possible promise-result size rather than a fixed constant, or (3) exposing a safe, permissionless "unstick" method that can reset `has_in_flight_tx` once it can be proven no promise is genuinely pending (e.g., by cross-checking block height/receipt state).

### Proof of Concept
1. Deploy a malicious contract `M` with a method `foo` that, on success, returns a value large enough that JSON-serializing it inside `ExecuteResponse` costs more than `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas) to process.
2. As the eth-implicit account owner, sign an Ethereum-style transaction encoding a `FunctionCall` action targeting `M::foo`, and submit it via `rlp_execute` (directly or through a registered relayer) — see `create_rlp_execute_tx`/`rlp_execute` flow [3](#0-2) .
3. `inner_rlp_execute` schedules the call to `M::foo` followed by `.then(ext.rlp_execute_callback(...))` with the fixed static gas [4](#0-3) .
4. `M::foo` succeeds and returns the oversized value; `rlp_execute_callback` runs out of gas while processing `env::promise_result(0)` / constructing the return value, so the receipt fails and the earlier `self.has_in_flight_tx = false` write is rolled back [7](#0-6) .
5. Any further call to `rlp_execute` on this account now always returns the "transaction already in progress" error [6](#0-5) , permanently freezing the account's funds and functionality.

Note: I was not able to execute this scenario in a live sandbox from this analysis environment; the conclusion is based on static analysis of the callback gas budgeting and NEAR's state-rollback-on-failure semantics as implemented in this file. If further confirmation of exact gas thresholds is needed, a Devin session with sandbox/test execution access would be required to reproduce empirically.

    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

fn action_to_promise(target: AccountId, action: near_action::Action) -> Result<Promise, Error> {
    match action {
        near_action::Action::FunctionCall(action) => Ok(Promise::new(target).function_call(
            action.method_name,
            action.args,
            action.deposit,
            action.gas,
        )),
        near_action::Action::Transfer(action) => Ok(Promise::new(target).transfer(action.deposit)),
        near_action::Action::AddKey(action) => match action.access_key.permission {
            near_action::AccessKeyPermission::FullAccess => {
                Err(Error::User(UserError::UnsupportedAction(UnsupportedAction::AddFullAccessKey)))
            }
            near_action::AccessKeyPermission::FunctionCall(access) => Ok(Promise::new(target)
                .add_access_key_allowance_with_nonce(
                    action.public_key,
                    access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited),
                    access.receiver_id,
                    access.method_names.join(","),
                    action.access_key.nonce,
                )),
        },
        near_action::Action::DeleteKey(action) => {
            Ok(Promise::new(target).delete_key(action.public_key))
        }
    }
}
