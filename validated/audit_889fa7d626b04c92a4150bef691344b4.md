Audit Report

## Title
Transaction-fee refund quoted from post-dispatch AMM reserves lets a dispatched call manipulate its own fee refund - (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

## Summary
`SwapAssetAdapter::withdraw_fee` quotes and swaps the fee-payment asset for the target asset before the wrapped `RuntimeCall` executes, using `S::quote_price_tokens_for_exact_tokens` against the pool's current reserves. `correct_and_deposit_fee`, which runs in `post_dispatch_details` *after* the call has fully executed, re-quotes the reverse conversion via `S::quote_price_exact_tokens_for_tokens(A::get(), asset_id, refund_amount, true)` against whatever the pool reserves are at that later point, allowing an attacker whose dispatched call moves the relevant pool's reserves to change the price used for their own fee refund.

## Finding Description
The transaction extension pipeline confirmed via `ChargeAssetTxPayment::prepare`/`post_dispatch_details` [1](#0-0)  shows `withdraw_fee` (which internally calls `SwapAssetAdapter::withdraw_fee`) executes in `prepare`, strictly before the wrapped call is dispatched, while `correct_and_deposit_fee` executes in `post_dispatch_details` [2](#0-1) , strictly after dispatch. This confirms the two pricing calls straddle the dispatched call's execution.

`withdraw_fee` quotes/swaps the fee asset for the target asset pre-dispatch: [3](#0-2) . `correct_and_deposit_fee` re-quotes the reverse conversion post-dispatch against current reserves: [4](#0-3) . The `QuotePrice` trait's own documentation states the guarantee holds "only ... if no other swaps are made after the price is quoted and before the target swap" [5](#0-4) , which is explicitly violated by the gap between pre-dispatch withdrawal and post-dispatch refund.

The reachability concern the original claim itself flagged — whether an attacker can get a pool-moving call executed inside the same extrinsic before `post_dispatch_details` runs — is addressed by `pallet_utility::batch`/`batch_all`/`force_batch`. These dispatch nested calls under the *same* signed origin with no restriction preventing an `AssetConversion::swap_exact_tokens_for_tokens` call from being included [6](#0-5) [7](#0-6) . The only nesting restriction found is that `batch_all` cannot recursively call `batch_all` [8](#0-7)  — it does not restrict calling `pallet_asset_conversion` extrinsics. Since `ChargeAssetTxPayment` and `pallet_utility` batch dispatch operate on the *outer* extrinsic's single call and its nested sub-calls respectively, a `utility.batch([asset_conversion.swap_exact_tokens_for_tokens(...), <attacker's real call>])` submitted as the extrinsic's `RuntimeCall`, paid for via `ChargeAssetTxPayment` with a non-native `asset_id`, executes the pool-skewing swap between the pre-dispatch fee withdrawal and the post-dispatch refund quote, all within one extrinsic.

The existing guard `can_deposit` only checks that the account can receive the computed `refund_asset_amount`, not that the amount reflects fair pricing relative to the original withdrawal rate [9](#0-8) . The subsequent `swap_exact_tokens_for_tokens` refund swap trusts the manipulated quote and only defensively logs on unexpected failure rather than checking value fairness [10](#0-9) .

## Impact Explanation
This is reachable by any ordinary signed account holding funds in the relevant fee asset and native asset, using only public extrinsics (`utility.batch` + `pallet_asset_conversion` swaps + `ChargeAssetTxPayment`), matching the "unprivileged external attacker" bar. It falls under the Balances/assets conservation-of-value pivot: the *fee-asset refund amount* credited to the caller is the exact value corrupted, since it is priced against attacker-manipulated post-dispatch reserves rather than the reserves in effect when the fee was actually withdrawn. Profitability is bounded by pool depth and swap fees, so this is a value-extraction issue against the pool/LPs rather than an unbounded mint, but it is a genuine, reproducible economic manipulation of a security-relevant on-chain price.

## Likelihood Explanation
No special privilege is required — only ordinary signed-extrinsic capability, funds to move the pool, and the ability to submit `utility.batch`, which is broadly available and not filtered against `pallet_asset_conversion` calls by any code found in this repository. The attack is fully self-contained within one transaction and repeatable each time the attacker can afford to move the pool and pay the associated swap fees, though profit shrinks with deeper pools/higher fees.

## Recommendation
Cache the pre-dispatch quote/rate (or a manipulation-resistant TWAP) and reuse it for the refund conversion instead of re-querying `quote_price_exact_tokens_for_tokens` against post-dispatch reserves, or bound the acceptable refund quote to be no more favorable to the payer than the pre-dispatch rate, rejecting/limiting refunds when reserves have moved beyond a tolerance since the initial withdrawal.

## Proof of Concept
1. Attacker holds asset `X` (`asset_id`) and native asset `A`, with a shallow `X`/`A` pool in `pallet-asset-conversion`.
2. Attacker submits an extrinsic with `ChargeAssetTxPayment` fee-asset = `X`, `RuntimeCall = Utility::batch([AssetConversion::swap_exact_tokens_for_tokens(path=[X,A], skewing reserves), <attacker's real call>])`.
3. `ChargeAssetTxPayment::prepare` → `withdraw_fee` quotes/withdraws `X` for the fee at the pre-manipulation rate [11](#0-10) .
4. The batched swap inside the dispatched call executes, shifting the `X`/`A` reserve ratio.
5. `ChargeAssetTxPayment::post_dispatch_details` → `correct_and_deposit_fee` quotes `refund_asset_amount` against the now-skewed reserves [4](#0-3) , yielding a refund priced at the manipulated rate rather than the rate at which the fee was originally withdrawn, extracting excess value from the pool within a single transaction. This can be reproduced as a unit test in `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/tests.rs` by inserting a reserve-shifting swap between `validate_and_prepare` and `post_dispatch_details` calls (mirroring the harness pattern already used in that file) and comparing the refund amount against the amount computed from the pre-swap reserves.

		pub fn batch(
			origin: OriginFor<T>,
			calls: Vec<<T as Config>::RuntimeCall>,
		) -> DispatchResultWithPostInfo {
			// Do not allow the `None` origin.
			if ensure_none(origin.clone()).is_ok() {
				return Err(BadOrigin.into());
			}

			let is_root = ensure_root(origin.clone()).is_ok();
			let calls_len = calls.len();
			ensure!(calls_len <= Self::batched_calls_limit() as usize, Error::<T>::TooManyCalls);

			// Track the actual weight of each of the batch calls.
			let mut weight = Weight::zero();
			for (index, call) in calls.into_iter().enumerate() {
				let info = call.get_dispatch_info();
				// If origin is root, don't apply any dispatch filters; root can call anything.
				let result = if is_root {
					call.dispatch_bypass_filter(origin.clone())
				} else {
					call.dispatch(origin.clone())
				};
				// Add the weight of this call.
				weight = weight.saturating_add(extract_actual_weight(&result, &info));
				if let Err(e) = result {
					Self::deposit_event(Event::BatchInterrupted {
						index: index as u32,
						error: e.error,
					});
					// Take the weight of this function itself into account.
					let base_weight = T::WeightInfo::batch(index.saturating_add(1) as u32);
					// Return the actual used weight + base_weight of this call.
					return Ok(Some(base_weight.saturating_add(weight)).into());
				}
				Self::deposit_event(Event::ItemCompleted);
			}
			Self::deposit_event(Event::BatchCompleted);
			let base_weight = T::WeightInfo::batch(calls_len as u32);
			Ok(Some(base_weight.saturating_add(weight)).into())
