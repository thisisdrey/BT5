### Title
False StackerDBChunkInv ack sent before chunk storage is committed via `try_replace_chunk` - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` patches the returned `StackerDBChunkInv.slot_versions[slot_id]` to the pushed chunk's version and immediately sends this ack back to the sending peer, but the actual write via `StackerDBTx::try_replace_chunk` happens later and asynchronously in the relayer thread (`Relayer::process_pushed_stacker_db_chunks` → `process_stacker_db_chunks`). If that later write fails (e.g. `StaleChunk` because a concurrent write already advanced the slot, or any other `try_replace_chunk` error), the chunk is silently dropped and no corrective message is ever sent to the peer that received the optimistic ack.

### Finding Description
In `stackslib/src/net/stackerdb/mod.rs`, `handle_unsolicited_StackerDBPushChunk` computes a reply via `make_StackerDBChunksInv_or_Nack`, then in the `StacksMessageType::StackerDBChunkInv(ref mut data)` branch calls `validate_received_chunk` (a pure read-only check: chunk size, slot signer, signature, version-vs-expected, max_writes) and, if it passes, directly mutates the outgoing inventory: [1](#0-0) 
This mutated inventory (claiming the chunk is now stored at the new version) is signed and sent back to the peer: [2](#0-1) 
Crucially, the function returns `(false, true)` — i.e. "don't buffer, but forward the raw chunk to the relayer for processing" — and never itself calls `try_replace_chunk`. The actual persistence happens later, out-of-band, in `Relayer::process_pushed_stacker_db_chunks`, which synthesizes a `StackerDBSyncResult` from the pushed chunk and calls `try_replace_chunk` in a separate DB transaction: [3](#0-2) 
`try_replace_chunk` itself re-checks slot ownership, signature, and — critically — re-checks the version against the *current* DB state (`slot_desc.slot_version <= slot_validation.version` → `Error::StaleChunk`): [4](#0-3) 
If this later check fails (most plausibly because a second, concurrently-arriving push for the same slot from a different peer/session wins the race and is committed first), the failure is only logged and the chunk is dropped: [5](#0-4) 
No follow-up NACK, correction, or downgraded inventory is ever sent to the peer that received the earlier optimistic `StackerDBChunkInv` ack. The equality claimed in the question — "version advertised in returned StackerDBChunkInv == version actually committed via `try_replace_chunk`" — is therefore not guaranteed; it can diverge whenever the deferred `try_replace_chunk` call fails after the ack has already gone out. This is not a theoretical corner case: the ack-send and the store are decoupled across the P2P thread and Relayer thread, with an explicit gap between `make_StackerDBChunksInv_or_Nack`'s optimistic patch and the actual commit, so any legitimate concurrent write (from another peer or another push targeting the same slot) racing the pushed chunk reproduces this divergence.

### Impact Explanation
A peer that receives this false ack believes the local node now holds the chunk at the acked version. In StackerDB's rarest-first/newest-first sync scheduling, this causes: (1) the acking node to be treated as "already up to date" for that slot/version by its neighbors, suppressing further replication attempts of that chunk from other paths toward this node, and (2) potential permanent non-convergence of the chunk across the replica set if no other push happens to re-trigger delivery. Because writes are ephemeral and slot-version-monotonic, a stale replica can be stuck believing it's caught up when it is not, which is a correctness violation of the eventual-consistency guarantee the StackerDB protocol is architected to provide. This matches the "false inventory causing sync non-convergence" class of impact described in the question. No consensus-critical block/chain data is affected (StackerDB is explicitly non-consensus-critical), so this is bounded to the StackerDB replication subsystem rather than chain-tip steering.

### Likelihood Explanation
Any remote peer that has established a P2P handshake (unprivileged capability per the threat model — no secret, no admin role needed) can push `StackerDBPushChunk` messages. The race is triggered whenever two writers push to the same slot at overlapping times — e.g. a legitimate signer publishing an update while, concurrently, this pushed chunk arrives from another peer relaying an older or same version, or vice versa — which is a routine, low-cost, easily reproducible condition in a busy StackerDB (e.g. `.signers` contract) rather than requiring privileged timing control. The attacker does not need to win every race; they only need to be one of the participants in a benign-looking chunk-push that loses the DB-side version race after the ack was already sent.

### Recommendation
Only construct/send the `StackerDBChunkInv` ack after the chunk has actually been committed via `try_replace_chunk` (or, if the ack must be sent eagerly for performance, roll back the advertised `slot_versions[slot_id]` to the DB's actual current version and re-notify the peer, e.g. via a follow-up chunk-inv correction, when the deferred `try_replace_chunk` in `process_stacker_db_chunks`/`process_pushed_stacker_db_chunks` fails).

### Proof of Concept
Rust test plan in `stackslib/src/net/stackerdb/tests/`:
1. Set up two connected `TestPeer`s replicating the same StackerDB contract/slot, both with an existing chunk at version `V`.
2. From the test harness, directly call `handle_unsolicited_StackerDBPushChunk` on peer A with a crafted, validly-signed `StackerDBPushChunkData` for slot `S` at version `V+1`.
3. Before letting the relayer process the pushed chunk (i.e. before `process_pushed_stacker_db_chunks`/`try_replace_chunk` runs), directly call `StackerDBTx::try_replace_chunk` on the same slot with a different, also-valid version `V+1` chunk (simulating a concurrent writer winning the race), and `commit()`.
4. Now let the relayer process the originally-pushed chunk via `process_pushed_stacker_db_chunks` — assert it returns `Err`/`StaleChunk` and the chunk is dropped (`chunks_to_store` never persisted).
5. Assert: the `StackerDBChunkInv` message that was sent back to the remote peer in step 2 advertised `slot_versions[S] == V+1`, while `StackerDBs::get_slot_versions` after step 4 shows the DB's actual value for slot `S` is the *other* committed chunk's version (potentially also `V+1` but different hash, or a different scenario where `try_replace_chunk` fails outright and the version remains `V`) — demonstrating the ack no longer matches the persisted state and no corrective message was ever sent.
