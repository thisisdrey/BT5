### Title
Stale Postponed ActionReceipt Retains Original `predecessor_id`, Enabling Self-Authorized Privileged Actions to Execute Against a Re-Created Account After `DeleteAccount` - (File: `runtime/runtime/src/lib.rs`, `runtime/runtime/src/actions.rs`, `core/store/src/utils/mod.rs`)

### Summary
`remove_account` (`core/store/src/utils/mod.rs:505-575`) clears `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` rows but never touches `TrieKey::PostponedReceipt`, `PostponedReceiptId`, or `PendingDataCount` rows, so a postponed `ActionReceipt` created before `DeleteAccountAction` survives account deletion. Because `apply_action_receipt` re-derives `actor_id` from the stored receipt's own `predecessor_id` field (`runtime/runtime/src/lib.rs:855`) and `check_actor_permissions` only compares `actor_id == account_id` by name (`runtime/runtime/src/actions.rs:739-785`), a self-authorized (`predecessor_id == receiver_id`) postponed receipt still passes privilege checks and executes its actions with full self-privilege against whatever account currently exists under that name, even if the account was deleted and re-created by an unrelated party in the meantime.

### Finding Description
1. Attacker deploys a contract on account `victim` (an account the attacker controls) and, via the promise API, creates a self-receipt (`predecessor_id == receiver_id == victim`) whose action list includes a privileged action such as `AddKey` (or `DeployContract`/`Stake`/`DeleteAccount`), gated behind a promise dependency (`input_data_ids`) that will not resolve immediately. `process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) finds `pending_data_count > 0`, writes `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, and `set_postponed_receipt` (`TrieKey::PostponedReceipt`) keyed by `receiver_id = victim` [1](#0-0) .
2. Attacker submits `DeleteAccountAction` on `victim` with `actor_id == victim` (self-delete). `action_delete_account` calls `remove_account`, which only removes `Account`, `ContractCode`, access/gas keys, and `ContractData` — the `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` rows for `victim` are left untouched [2](#0-1) [3](#0-2) .
3. The account name `victim` becomes available again (e.g. as a subaccount re-created by any parent, or reassigned by a service that provisions subaccounts to new customers). A new, unrelated owner creates `victim` fresh via `CreateAccountAction`.
4. When the outstanding `DataReceipt` for the original dependency finally arrives (a normal, attacker-triggerable event since the attacker controls the dependency chain), `process_receipt` finds the `PostponedReceiptId` entry still present, decrements `PendingDataCount` to 0, fetches the stored `Receipt` via `get_postponed_receipt`, and calls `apply_action_receipt` on it [4](#0-3) .
5. Inside `apply_action_receipt`, `actor_id` is initialized from the *stored* receipt's own `predecessor_id` field — `victim`, unchanged from creation time — not from any live authorization check [5](#0-4) . `check_actor_permissions` then only compares `actor_id != account_id` by name for privileged actions (`AddKey`, `DeleteKey`, `DeployContract`, `Stake`, `DeleteAccount`, etc.) [6](#0-5) . Since `actor_id == account_id == "victim"` still holds textually, the check passes and the privileged action (e.g. `AddKey` granting a full-access key, or another `DeleteAccount` draining the new balance to attacker-chosen beneficiary) executes against the *new* account's state and balance, without any signature or fresh authorization from the new owner.

This breaks the "authorization exactness" invariant: actions from a receipt created under the old account's context execute with privilege over an unrelated new account, purely because account-name identity is not versioned/epoch-tagged in the postponed-receipt bookkeeping or in `check_actor_permissions`.

### Impact Explanation
This is an authorization escalation across the account-name boundary (NEAR bounty category: authorization escalation / theft of user funds). A malicious former owner of an account name can plant a "time bomb" postponed receipt that, upon later account-name reuse by an unrelated party, silently grants the attacker full access (via `AddKey`) or redirects/drains funds (via a further `DeleteAccount`/`Transfer` inside the same batch) on the new owner's account — with no new signature, key, or consent from the new owner.

### Likelihood Explanation
Preconditions are fully within attacker capability: own a deletable subaccount, deploy a contract, use the standard promise API to create a self-receipt with a slow-resolving dependency, then self-delete. The only external dependency is that the vacated name gets reused (plausible for services that programmatically provision/reclaim subaccount names, e.g. `user123.exchange.near`). Cost is limited to normal gas/storage fees; the attack is fully repeatable per reclaimed name and requires no validator or privileged access.

### Recommendation
When deleting an account, `action_delete_account`/`remove_account` should also enumerate and purge (or otherwise invalidate) any `PostponedReceipt`, `PostponedReceiptId`, and `PendingDataCount` entries keyed to that `receiver_id` (failing the delete, or converting the postponed receipt into a refund, if any exist), and/or `check_actor_permissions`/`apply_action_receipt` should not trust a postponed receipt's stale `predecessor_id` as automatically self-authorized once the account has been deleted and recreated (e.g. by tracking an account "generation"/creation nonce and requiring it to match at execution time).

### Proof of Concept
Runtime/test-loop integration test:
1. Create subaccount `victim.parent` with a deployed contract; from `victim.parent` call `promise_batch_action_add_key` (via `promise_then` on a slow/cross-shard dependency) targeting itself, producing a postponed `ActionReceipt` with `predecessor_id == receiver_id == victim.parent` and an `AddKey` action for an attacker-chosen public key.
2. Assert `TrieKey::PostponedReceipt{receiver_id: "victim.parent", ..}` exists in state after this receipt is applied.
3. Submit `DeleteAccountAction` from `victim.parent` (self-delete, beneficiary = attacker); commit; assert account is gone but the `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` rows for `victim.parent` still exist.
4. From `parent`, submit `CreateAccountAction` + `Transfer` + `AddKey(new_owner_key)` to recreate `victim.parent` as a fresh account owned by a different key ("new owner").
5. Deliver the pending `DataReceipt` that satisfies the original dependency.
6. Assert the outcome for the originally postponed receipt is `SuccessValue`/success (not `StorageInconsistentState`), and that the attacker's public key now has a full-access `AccessKey` on the *new* `victim.parent` account — demonstrating privilege escalation onto the new owner's account.

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

pub(crate) fn check_actor_permissions(
    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {
    match action {
        Action::DeployContract(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
        }
        Action::DeleteAccount(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
            let account = account.as_ref().unwrap();
            if !account.locked().is_zero() {
                return Err(ActionErrorKind::DeleteAccountStaking {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
        Action::CreateAccount(_)
        | Action::FunctionCall(_)
        | Action::Transfer(_)
        | Action::TransferToGasKey(_) => (),
        Action::Delegate(_) | Action::DelegateV2(_) => (),
        Action::DeterministicStateInit(_) => (),
    };
    Ok(())
}
