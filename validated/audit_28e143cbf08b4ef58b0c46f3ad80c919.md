Based on directly retrieved source, the vulnerability described in the question is confirmed: `extend_with_attachments` performs no comparison between the returned attachment's actual content hash and the `AttachmentRequest.content_hash` that was requested.

### Title
Missing content-hash verification of downloaded attachment allows unprivileged peer to serve mismatched attachment content - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes an HTTP `GetAttachmentResponse` from a remote peer and unconditionally inserts `response.attachment` into `self.attachments` without ever checking that `response.attachment.hash()` equals the `request.content_hash` that was originally requested. Any peer listed as a source for an `AttachmentRequest` can therefore return arbitrary attachment bytes for a completely different content hash and have them accepted as a "successful" response.

### Finding Description

Specifically, the request/response handling loop: [2](#0-1) 

After `response.decode_atlas_get_attachment()` succeeds, the code goes straight to `self.attachments.insert(response.attachment)` and marks the report as a `bump_successful_requests()` — there is no equality check of the form `response.attachment.hash() == request.content_hash`, unlike the analogous inventory-handling path (`extend_with_inventories`) which at least validates the decoded response's structural correctness via `decode_atlas_attachments_inv_response()`. Because `AttachmentRequest.sources` is populated from any peer that merely claims (via its self-reported inventory bitmap) to have the attachment, and reliability reports are peer-supplied/observed but not a security boundary, a remote unprivileged peer that is queried for `GET /v2/attachments/<hash>` can return HTTP 200 with a `GetAttachmentResponse` whose `attachment.content` is arbitrary bytes that hash to a value different from the requested `content_hash`. This response would still be treated as a success and stored into `self.attachments`.

I was not able to fully trace, within the available tool budget, the exact downstream data structure and keying semantics of `self.attachments` (e.g., whether it is a `HashMap` keyed by the attachment's own computed hash vs. by the original request's `content_hash`, and how/where `insert_instantiated_attachment` associates a stored attachment with a specific `AttachmentInstance`/name commitment before `RPCGetAttachmentRequestHandler` serves it). That association step is critical to fully confirming the "serves it as resolution for a commitment it does not match" claim, and I could not verify it from the code retrieved.

### Impact Explanation
If the downstream storage/serving path resolves attachments by the originally-requested `content_hash` (as implied by `attachments_instances: HashMap<contract_id, (attachment_index -> content_hash)>` used to drive requests), then accepting an unverified attachment breaks the invariant that served attachment content matches its committed hash — this is a High-severity "attachment/BNS mismatch" per the stated impact categories, since a node could serve non-canonical attachment content as if it correctly resolved a given content hash / name commitment.

### Likelihood Explanation
Preconditions are modest and attacker-achievable without any privileged role: the attacker's node/peer must be listed in the peer inventory as claiming to have the attachment (self-reported, not verified) and the target node must have an outstanding `AttachmentInstance` for that `content_hash`. The attacker simply responds to the resulting GET request with a crafted `GetAttachmentResponse` — a single HTTP response is sufficient, and this is repeatable for every attachment the node requests from the malicious peer.

### Recommendation
In `extend_with_attachments`, after successfully decoding the response, explicitly verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; on mismatch, call `report.bump_failed_requests()` (and optionally penalize/deregister the peer) instead of treating it as success.

### Proof of Concept
Rust test plan (in `stackslib/src/net/atlas/download.rs` test module or a new test):
1. Construct an `AttachmentRequest` with a known `content_hash` (e.g., `Hash160::from_data(b"expected")`) and a `sources` map containing one peer URL with a `ReliabilityReport`.
2. Construct a `GetAttachmentResponse` whose `attachment.content` is different bytes (e.g., `b"malicious"`), so `Hash160::from_data(b"malicious") != content_hash`.
3. Build a `BatchedRequestsResult<AttachmentRequest>` with `succeeded` containing `(request, Some(crafted_response_as_StacksHttpResponse))`.
4. Call `AttachmentsBatchStateContext::extend_with_attachments(ctx, &mut results)`.
5. Assert that `ctx.attachments` now contains the malicious attachment (proving no hash check), and that `report.bump_successful_requests()` was invoked rather than `bump_failed_requests()` — demonstrating the missing `response.attachment.hash() == request.content_hash` guard at `download.rs:547-549`.

```rust
    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
```
