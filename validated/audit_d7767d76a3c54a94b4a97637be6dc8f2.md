### Title
Unvalidated multi-value ABI decoding in `ValidateMultiSign` precompile causes uncaught out-of-bounds exception on malformed calldata - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The Apache CVE describes an out-of-bounds read in `mod_headers`/`mod_mime` that occurs when the number of "multiple response languages" doesn't match the buffer the code allocated for them — i.e., a count/offset mismatch between an attacker-influenced multi-value field and the memory actually reserved for it. The same bug class exists in java-tron's `ValidateMultiSign` TVM precompile (address `0x0a`): the precompile decodes a self-reported count field from raw calldata and then uses attacker-controlled offsets/lengths to index into `DataWord[]` and `byte[]` arrays with no bounds validation prior to TIP-854/Osaka activation, and this codepath is reachable from any contract call.

### Finding Description
`PrecompiledContracts.ValidateMultiSign.execute()` parses the raw calldata into words with `DataWord.parseArray(rawData)` and then reads attacker-controlled header fields to compute offsets into that array: [1](#0-0) 

The `isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)` guard that rejects malformed calldata (mismatched word-count/tail shape) is only consulted when `VMConfig.allowTvmOsaka()` is enabled: [2](#0-1) 

Before that hard-fork switch is activated, calldata shorter than, or with a shape inconsistent with, the expected `(5 + 5*N)` word layout flows straight into `DataWord.parseArray`, `extractBytesArray`/`extractSigArray`, whose indexing (`words[offset + i + 1]`, `words[offset + bytesOffset + 1]`) is unchecked against the actual parsed-array length: [3](#0-2) 

This is exactly the "count vs. allocated-buffer mismatch causes out-of-bounds access" pattern in the CVE, except here it is a Java `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` thrown from inside a precompile that — per the project's own regression tests — has "no outer catch": [4](#0-3) 

### Impact Explanation
`ValidateMultiSign` is callable via a plain `CALL`/`STATICCALL` from any deployed smart contract, i.e., by any unprivileged transaction sender who deploys or invokes a contract that calls address `0x…0a` with crafted calldata. Because the exception thrown is a generic, uncaught `RuntimeException` rather than one of the TVM's expected `Program.Exception` subtypes, it is not guaranteed to be caught and neatly converted into a normal transaction revert/OOG result the way legitimate TVM faults are. If it escapes the transaction-execution try/catch during block application, it can abort processing of that block on every node executing the same transaction, producing a denial-of-service / potential halt for nodes that have not yet activated the Osaka/TIP-854 guard — a "node crash or halt" class impact called out as in-scope.

### Likelihood Explanation
Likelihood is high: the trigger is a single crafted transaction that calls the precompiled contract with a calldata length shorter than `(5+5)*32` bytes or otherwise mis-shaped (documented explicitly by `testTip854RejectsMalformedCalldata` as rejected post-activation but not pre-activation). No special privileges, staking, or governance access is required — any address that can broadcast a transaction invoking a contract that performs this `CALL` can trigger it, and the guard is gated behind a not-yet-universally-activated hard-fork flag (`VMConfig.allowTvmOsaka()`), meaning the vulnerable pre-activation path is the currently active one on networks/nodes where this proposal has not been switched on.

### Recommendation
Apply the `isValidAbiEncoding` (or equivalent bounds validation) check unconditionally in `ValidateMultiSign.execute()` (and the sibling `BatchValidateSign`) rather than gating it behind `VMConfig.allowTvmOsaka()`, and wrap the decode step in a try/catch that converts any `RuntimeException` into the standard `(true, DATA_FALSE)`/reject result instead of letting it propagate out of the precompile.

### Proof of Concept
Deploy a trivial contract that does `address(0x0a).call(data)` where `data` is calldata shorter than 320 bytes (`(5+1)*32`), e.g. mirroring the test: [5](#0-4) 
Broadcasting a transaction that invokes this call while `allowTvmOsaka` is not activated causes `ValidateMultiSign.execute()` to throw an uncaught out-of-bounds/array exception from `DataWord.parseArray`/`extractBytesArray` instead of returning a normal `(false, EMPTY_BYTE_ARRAY)` rejection.
