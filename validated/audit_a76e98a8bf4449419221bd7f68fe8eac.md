### Title
Dust deposits via `deposit(amount, onBehalfOf)` fill a victim's 30-slot account token list, permanently blocking them from depositing new collateral types or borrowing new synthetics - (File: contracts/Pool.sol)

### Summary
The `Pool` enforces `MAX_TOKENS_PER_USER = 30` across `debtTokensOfAccount` + `depositTokensOfAccount` [1](#0-0) . Any unprivileged attacker can add entries to a victim's list without consent: `DepositToken.deposit(amount_, onBehalfOf_)` lets anyone deposit dust on behalf of any address [2](#0-1) , and `_mint` registers the token with the pool on a 0→positive balance change [3](#0-2) . Once the cap is hit, `onlyIfAdditionWillNotReachMaxTokens` reverts with `UserReachedMaxTokens` inside `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` [4](#0-3) [5](#0-4) , reverting the entire deposit/mint transaction. This mirrors CVE-2020-25652: an unprivileged user exhausts a bounded resource (per-account token slots) to deny service to legitimate users.

### Finding Description
- `DepositToken.deposit` has no restriction on `onBehalfOf_` (only non-zero), so `deposit(1 wei, victim)` mints dust msdTOKEN to the victim [2](#0-1) .
- Alternatively, the attacker can `transfer(victim, dust)` since `transfer` only checks the *sender's* locked balance, never the recipient's list capacity [6](#0-5) .
- `Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` is invoked from `_mint`/`issue`; when the account already holds 30 distinct deposit+debt tokens it reverts, rolling back the whole user transaction [5](#0-4) .
- The victim cannot remove the dust: `withdraw`/`transfer` would burn their balance to 0 and call `removeFromDepositTokensOfAccount`, so griefing is *reversible* per token — but only if the victim spends gas iterating withdrawals, and the attacker can re-grief cheaply (the deposit-token balance and slot return on the next dust deposit). More importantly, the victim cannot deposit any *new* collateral type or mint any *new* synthetic while the list is full.

### Impact Explanation
Temporary freezing/DoS of user functionality: a victim with an open unhealthy position who needs to add a *different* collateral to regain health is blocked — every `deposit` of a not-yet-held token reverts — leaving them exposed to liquidation they cannot prevent. They also cannot open debt positions in synthetics they don't already hold (issue/mint would call `addToDebtTokensOfAccount` and revert). Withdrawals of already-held tokens still work, so this is availability loss rather than direct theft, matching the Medium/DoS severity of the source CVE.

### Likelihood Explanation
Requires the pool to list enough deposit tokens (or the victim to already hold most of 30 slots) for the attacker to reach the cap. Metronome pools list multiple collaterals (wstETH, WETH, WBTC, stablecoins, OP, etc.), and dust costs are negligible (1 wei per token plus deposit fee). No privileged role, oracle manipulation, or governance action is needed — only public `deposit`/`transfer` calls. Feasibility depends on the deployed token count per pool; where ~30 deposit+debt tokens exist, the attack is fully permissionless.

### Recommendation
- Do not let third parties add to an account's token list: restrict `deposit`'s `onBehalfOf_` and/or make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` silently no-op (or lazily handle in views) instead of reverting when the cap is reached, so only enumeration is affected, not the user's ability to transact.
- Alternatively, cap iterations in `depositOf`/`debtOf`/`debtPositionOf` directly and remove the per-account limit revert.

### Proof of Concept
Reproducible on a Hardhat fork against a deployed Pool (e.g., Base/Optimism deployments in `deployments/`):

```ts
// Attacker fills victim's slots with dust deposits on behalf of victim
for (const depositToken of allListedDepositTokens) { // up to MAX_TOKENS_PER_USER
  await underlying.connect(attacker).approve(depositToken.address, 1);
  await depositToken.connect(attacker).deposit(1, victim.address); // dust
}
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(30);

// Victim tries to deposit a collateral they don't yet hold -> reverts
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");
```

Attacker cost: ~30 dust deposits + gas. Note the caveat: validity is contingent on the target pool listing enough distinct deposit/debt tokens for the attacker to reach the 30-slot cap; on pools with few listed tokens the attacker can only reduce, not exhaust, capacity.

    function deposit(
        uint256 amount_,
        address onBehalfOf_
    ) external override whenNotPaused nonReentrant onlyIfDepositTokenExists returns (uint256 _deposited, uint256 _fee) {
        if (amount_ == 0) revert AmountIsZero();
        if (onBehalfOf_ == address(0)) revert BeneficiaryIsNull();

        IPool _pool = pool;
        IERC20 _underlying = underlying;
        address _msgSender = _msgSender();
        address _treasury = address(_pool.treasury());

        if (_msgSender == _treasury) revert TreasuryCanNotDeposit();

        uint256 _balanceBefore = _underlying.balanceOf(_treasury);
        _underlying.safeTransferFrom(_msgSender, _treasury, amount_);
        amount_ = _underlying.balanceOf(_treasury) - _balanceBefore;

        (_deposited, _fee) = quoteDepositOut(amount_);
        if (_fee > 0) {
            _mint(_pool.feeCollector(), _fee);
        }

        _mint(onBehalfOf_, _deposited);

        emit CollateralDeposited(_msgSender, onBehalfOf_, amount_, _deposited, _fee);
    }
