### Title
Unbounded `Attachment.content` size accepted and stored by `AttachmentsDownloader::run` / `AtlasDB::insert_instantiated_attachment` - (stackslib/src/net/atlas/download.rs, stackslib/src/net/atlas/mod.rs)

### Summary
`GetAttachmentResponse::deserialize` decodes an arbitrary-length hex string directly into `Attachment::new(bytes)` with no cap on the resulting `Vec<u8>` size. The downloader's completion path in `AttachmentsDownloader::run` then drains these attachments and calls `AtlasDB::insert_instantiated_attachment` without re-checking the content length against `AtlasConfig.attachments_max_size`, so a peer serving an oversized attachment body can cause the node to persist content larger than its configured/validated bound.

### Finding Description
`GetAttachmentResponse::deserialize` at `stackslib/src/net/atlas/mod.rs:69-77` parses the JSON string payload, hex-decodes it, and builds `Attachment::new(bytes)` with no length check whatsoever [1](#0-0) . `ATTACHMENTS_MAX_SIZE_MIN` (1 MiB) is only enforced in `AtlasConfig::validate`, which validates the *configuration value* itself, not incoming wire data [2](#0-1) [3](#0-2) .

Downstream, `AttachmentsDownloader::run` completes a batch and, for every attachment successfully retrieved from a peer, immediately calls `insert_instantiated_attachment` with no visible size gate in this code path [4](#0-3) .

However, it is important to note that `AttachmentInstance` records are content-addressed: attachments are only queued for download when a name/BNS operation on-chain committed to a specific `Hash160` for that content. This means an attacker cannot substitute arbitrary unrelated content for an existing hash (that would require a hash preimage break), but an attacker who is otherwise unprivileged can still act as a normal blockchain participant: they can submit their **own** BNS name operation committing to the hash of content they themselves control, including an oversized (e.g. multi-MB or larger) blob, and then run a peer that serves that oversized blob when queried via the Atlas attachment protocol. Because there is no size check at either the decode boundary (`GetAttachmentResponse::deserialize`) or immediately before the DB write (`insert_instantiated_attachment` call site in `download.rs`), the node will store content exceeding `attachments_max_size` for every victim node that syncs Atlas attachments from the attacker's peer.

### Impact Explanation
Each oversized attachment accepted causes unbounded disk/DB growth in the node's `AtlasDB`, in violation of the operator-configured `attachments_max_size` bound (minimum 1 MiB, but operators may raise it — the bound is still meant to be an enforced ceiling, not merely a config-validation floor). This is repeatable per attacment hash and can be repeated across many distinct BNS name operations/attachment hashes registered by the attacker, leading to storage exhaustion on any node that syncs Atlas attachments from the attacker-controlled peer — an unauthenticated write to node state matching the Critical category described.

### Likelihood Explanation
The attacker needs no privileged role: submitting a BNS name operation is a normal permissionless blockchain transaction, and serving Atlas attachment data over the P2P/RPC interface requires only running an ordinary peer that other nodes will sync from. The cost is limited to normal transaction fees for the name operations and bandwidth to serve the oversized payloads (repeatable, low cost per unit of stored bloat).

### Recommendation
Enforce `attachments_max_size` at the point of decode (reject/truncate in `GetAttachmentResponse::deserialize`) and again immediately before `insert_instantiated_attachment` is called in `AttachmentsDownloader::run`, rejecting (and penalizing/deregistering) any attachment whose `content.len()` exceeds `AtlasConfig.attachments_max_size` before it is written to the database.

### Proof of Concept

1. Construct a `GetAttachmentResponse` JSON payload whose hex-encoded `content` decodes to a `Vec<u8>` larger than `attachments_max_size` (e.g. `ATTACHMENTS_MAX_SIZE_MIN + 1` bytes).
2. Feed the payload through `GetAttachmentResponse::deserialize` and assert it currently succeeds (demonstrating no cap at decode time), per `stackslib/src/net/atlas/mod.rs:69-77`.
3. Drive an `AttachmentsDownloader` batch completion with this oversized attachment and assert that `AtlasDB::insert_instantiated_attachment` is invoked with content exceeding `attachments_max_size`, per the drain loop at `stackslib/src/net/atlas/download.rs:152-165`, instead of being rejected before the call.         let attachment = Attachment::new(bytes);

    }
