This confirms the storage layer already enforces slot-owner authentication before a chunk can ever be stored (and thus before it can appear in a `StackerDBChunksEvent`).

In `stackslib/src/net/stackerdb/db.rs`, `try_replace_chunk` looks up the registered signer for `slot_desc.slot_id` via `get_slot_validation`, and then calls `slot_desc.verify(&slot_validation.signer)`, rejecting the write with `net_error::BadSlotSigner` if the recovered public key's hash doesn't match the slot's registered owner: [1](#0-0) 

The same check applies to chunks arriving via P2P push (`validate_received_chunk`, which fetches the registered `addr` via `get_slot_signer` and calls `slot_metadata.verify(&addr)`): [2](#0-1) 

and via the HTTP POST‑chunk RPC handler (`RPCPostStackerDBChunkRequestHandler::try_handle_request`, which calls `tx.try_replace_chunk` and maps `BadSlotSigner`/`VerifyingError` to a rejection ack): [3](#0-2) 

`StackerDBChunksEvent`s are only ever constructed from chunks that were *already stored* (i.e., already passed one of these ownership checks) — see `process_stacker_db_chunks` in `relay.rs`, which only builds `all_events` for chunks that succeeded `tx.try_replace_chunk`, and `process_uploaded_stackerdb_chunks`, which only forwards chunks accepted by the RPC handler: [4](#0-3) 

So the attacker's premise — "attacker signs a chunk with key A but sets `chunk.slot_id` to victim slot B" — cannot reach `TryFrom<StackerDBChunksEvent>` at all: `try_replace_chunk`/`validate_received_chunk` would reject it with `BadSlotSigner`/`Ok(false)` before it is ever stored or dispatched as an event, since `slot_desc.verify(&slot_validation.signer)` (or `slot_metadata.verify(&addr)`) checks the recovered public key's hash against the on-chain-registered owner of that exact `slot_id`. `chunk.recover_pk()` in `libsigner/src/events.rs` itself indeed does not re-check slot ownership, but it doesn't need to — that invariant is already established and enforced at the point of storage/ingestion, before the event is ever emitted. This is consistent with the existing test coverage exercising `BadSlotSigner`: [5](#0-4)
