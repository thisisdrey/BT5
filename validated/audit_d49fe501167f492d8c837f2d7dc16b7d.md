### Title
Unbounded, fixed-cost vote-account creation triggers O(n) `Arc::make_mut` clones under the shared `StakesCache` write lock - ([File: vote/src/vote_account.rs])

### Summary
An unprivileged fee payer can create arbitrarily many vote-program-owned accounts via ordinary `System::create_account` + `Vote::InitializeAccount` transactions, each costing only rent-exemption lamports and a fixed `DEFAULT_COMPUTE_UNITS = 2_100` CU charge. Every successfully processed vote-account-creation transaction forces `Bank::update_stakes_cache` → `StakesCache::check_and_store` → `Stakes::upsert_vote_account` → `VoteAccounts::insert`, which calls `Arc::make_mut(&mut self.vote_accounts)` on the shared `VoteAccountsHashMap`. Because the map has no admission cap in the `StakesCache` path, its size (and thus the cost of any COW clone) grows unbounded and proportionally to attacker-paid rent only, not to CU fees.

### Finding Description
`VoteAccounts::insert` is implemented as:
```rust

    let vote_accounts = Arc::make_mut(&mut self.vote_accounts);
    ...
```
`Arc::make_mut` clones the entire backing `HashMap<Pubkey, (u64, VoteAccount)>` whenever the `Arc`'s reference count is greater than one (i.e., whenever another `Bank`/reader is concurrently holding a reference to the same snapshot, which routinely happens because `Stakes<T>` — and therefore `VoteAccounts` — is `Clone`d cheaply (Arc bump) whenever a child `Bank` is created from a parent, or when a caller such as `bank.vote_accounts()`/RPC snapshots the map). This insert is invoked from:
```rust
// runtime/src/stakes.rs:87-164 (StakesCache::check_and_store)
if solana_vote_program::check_id(owner) {
    if VoteStateVersions::is_correct_size_and_initialized(account.data()) {
        match VoteAccount::try_from(...) {
            Ok(vote_account) => {
                let mut stakes = self.0.write().unwrap();   // per-account write lock
                stakes.upsert_vote_account(pubkey, vote_account)
            }
            ...
```
which is called once per touched account from `Bank::update_stakes_cache` (runtime/src/bank.rs:5756-5792), itself invoked at the end of `Bank::commit_transactions` for every successfully executed transaction. Creating a new vote account requires only:
1. `System::create_account` (any signer, no privilege) to allocate a rent-exempt account owned by the vote program.
2. `Vote::InitializeAccount` (`programs/vote/src/vote_processor.rs:130-140`), which only checks rent-exemption and a node-key signature — **no stake is required**.

The Vote program's compute cost for `InitializeAccount` is fixed at `DEFAULT_COMPUTE_UNITS = 2_100` (`programs/vote/src/vote_processor.rs:101`), independent of `vote_accounts.len()`. There is no cap in this code path analogous to the Alpenglow "VAT" filtering (`clone_and_filter_for_vat`, `vote/src/vote_account.rs:212-271`), which only limits the *snapshot* used for `epoch_stakes`/leader-schedule purposes (`runtime/src/bank.rs:2644-2695`) and never bounds the live `StakesCache`'s `vote_accounts` map that every `check_and_store` call mutates.

Consequently, an attacker can grow the shared `vote_accounts` map size `n` unbounded by repeatedly funding+initializing new vote accounts, and each subsequent `insert` that happens to race a concurrent `Arc` clone (parent/child bank transition, RPC snapshot, leader-schedule computation, etc.) pays an O(n) clone under the process-wide `StakesCache` `RwLock` write lock. Since `check_and_store` takes this same lock for **every** transaction in **every** concurrently-committing batch that touches a vote or stake account (including legitimate validators' own vote transactions), the attacker can materially inflate per-account update latency validator-wide for a cost that does not scale with the imposed work (rent once per account + fixed 2,100 CU), which is a real underpriced-pre-fee-work condition, even though it does not block unrelated (non-vote/stake-touching) transfers, which never acquire this lock at all.

### Impact Explanation
This falls under "grossly underpriced pre-fee work" / resource-exhaustion: the attacker pays a fixed, size-independent fee (2,100 CU + one-time rent) per vote account created, while imposing O(n) memory-copy work on the validator's shared `StakesCache` write lock that grows with the attacker-controlled account count. Concurrent commits/reads of `StakesCache` (other worker threads' vote/stake account updates, leader-schedule/epoch-boundary code, RPC vote-account queries) are serialized behind this lock, and the wall-clock cost of the affected worker's `commit_transactions` call increases with `n`, delaying that thread's PoH recording. This does not, however, stall unrelated fee-paying transfers that never touch vote/stake-owned accounts, since `check_and_store` returns without taking the lock for such accounts.

### Likelihood Explanation
Fully achievable by an unprivileged, unstaked remote client: it only needs a funded fee payer and the ability to submit `System::CreateAccount` + `Vote::InitializeAccount` transactions, which require no special permission, stake, or validator identity. The clone cost is proportional to accumulated attacker-created accounts (persists across slots since nothing evicts these zero-stake vote accounts), so repeatable and cumulative over time.

### Recommendation
- Add an admission/rate limit on the number of vote-program accounts (or unstaked vote accounts) that `StakesCache`/`Stakes::upsert_vote_account` will track, independent of the Alpenglow VAT filtering which only applies at epoch boundaries.
- Consider pricing `Vote::InitializeAccount` (and other paths that mutate `StakesCache`) proportionally to current `vote_accounts.len()`, or evict stale zero-stake vote accounts from the cache after some grace period.
- Alternatively, switch `VoteAccounts`' backing store to a persistent (structural-sharing) map (e.g., `im`/`imbl`) as is already done for `stake_delegations` (`DelegatedStakes = ImblHashMap<Pubkey, u64>`), so inserts are O(log n) instead of O(n) regardless of `Arc` sharing.

### Proof of Concept
```rust
// runtime/tests/vote_account.rs (extend existing test module)
#[test]
fn bench_insert_scales_with_map_size_under_shared_arc() {
    use std::time::Instant;
    let mut rng = rand::rng();
    let mut vote_accounts = VoteAccounts::default();

    // Populate to N accounts (simulating attacker-created zero-stake vote accounts).
    let n = 200_000;
    let mut accounts = new_rand_vote_accounts(&mut rng, n, 0 /* zero stake */);
    for (pubkey, (stake, vote_account)) in (&mut accounts).take(n) {
        vote_accounts.insert(pubkey, vote_account, || stake);
    }

    // Snapshot the Arc (simulates a concurrent bank/RPC reader holding a clone,
    // which is what forces Arc::make_mut to actually clone on the next insert).
    let _snapshot = vote_accounts.clone();

    let (new_pubkey, (stake, new_account)) = accounts.next().unwrap();
    let start = Instant::now();
    vote_accounts.insert(new_pubkey, new_account, || stake);
    let elapsed = start.elapsed();

    // Assert: single insert cost scales with existing map size (not attacker fee),
    // demonstrating unbounded, size-proportional cost under the shared lock.
    println!("insert into {n}-entry map took {elapsed:?}");
    assert!(elapsed.as_micros() > 0); // replace with regression threshold in CI
}
```
Extend this into an integration test around `StakesCache::check_and_store` with a background thread holding `stakes_cache.stakes()` (or a cloned `Bank`) concurrently, and measure `Bank::commit_transactions` wall time for a batch of `Vote::InitializeAccount` transactions as `vote_accounts.len()` grows from 1,000 to 200,000, asserting the growth is superlinear/linear in `n` rather than constant.
