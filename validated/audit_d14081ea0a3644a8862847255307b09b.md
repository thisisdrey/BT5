### Title
Dust `DepositToken` transfers fill a victim's `MAX_TOKENS_PER_USER` slots, blocking deposits, borrows, and inbound transfers — (`contracts/Pool.sol`)

### Summary
An unprivileged attacker can permissionlessly add up to 30 entries to any account's `depositTokensOfAccount`/`debtTokensOfAccount` tracked sets by transferring 1-wei dust amounts of every `DepositToken` in the pool to the victim. Once the victim's combined per-account token count reaches `Pool.MAX_TOKENS_PER_USER` (30), `onlyIfAdditionWillNotReachMaxTokens` makes every subsequent `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` call revert. Because these calls are embedded in `DepositToken._mint`/`_transfer` and `DebtToken` issuance, the victim is DoS'd: they cannot deposit any new collateral type, cannot mint any new synthetic debt, and cannot even *receive* any deposit token they don't already hold — every such transaction reverts.

### Finding Description
The bug-class analog to the Nextcloud advisory (an unprivileged logged-in user forcing disproportionate state/resource growth on another user's account) is the per-account token list in `Pool`:

- `Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` enforce `onlyIfAdditionWillNotReachMaxTokens`, reverting with `UserReachedMaxTokens` once `debtTokensOfAccount + depositTokensOfAccount >= 30` (`contracts/Pool.sol:143-148`, `204-220`).
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is zero (`contracts/DepositToken.sol:517-520`), and `_mint` does the same (`contracts/DepositToken.sol:486-488`).
- `DebtToken` issuance calls `pool.addToDebtTokensOfAccount(account_)` when a user's debt balance goes from 0 to positive, so `Pool.issue`/mint paths revert as well once the cap is hit.

The critical flaw: **the victim has no control over entries added to their set**. Any holder of a `DepositToken` can `transfer()` dust to an arbitrary address, and each first-time token received consumes one of the victim's 30 slots. The removal path (`removeFromDepositTokensOfAccount`) only triggers inside `_transfer` when the *sender's* balance hits zero — i.e., the victim must actively send the dust away to reclaim slots.

Attack:
1. Attacker deposits small amounts into every `DepositToken` offered by the pool (bounded by `ReachedMaxDepositTokens` at ≤30, `contracts/Pool.sol:703`), and/or flash-borrows/distributes across them.
2. Attacker calls `depositToken_i.transfer(victim, 1)` for each token `i` (plus `DebtToken` slots cannot be pushed, but deposit tokens alone suffice to reach 30 on pools with few listed collaterals, since the cap is shared).
3. Victim's `depositTokensOfAccount.length` reaches 30.
4. Consequences until the victim manually sweeps each dust balance:
   - `pool.deposit(underlying_new, ...)` → `DepositToken._mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens` revert: victim cannot open a position in any collateral they don't already hold.
   - `pool.issue`/`mint` for a synthetic the victim doesn't already owe → `addToDebtTokensOfAccount` revert: victim cannot take on new debt, e.g., cannot leverage or borrow a different msAsset.
   - Any third party (or contract like `SmartFarmingManager.leverage`, `NativeTokenGateway`, a seizing liquidation paying `to_`) sending the victim a deposit token they don't hold reverts.

### Impact Explanation
Temporary freezing of funds / liveness denial per accepted impact: the victim's ability to deposit collateral, mint debt, and receive deposit tokens is fully blocked. In the worst scenario, a victim whose position is approaching liquidation and whose only viable rescue path is depositing a *different* collateral type (e.g., their existing collateral is crashing and they hold no more of it) cannot add it — forced liquidation and loss of the liquidation fee. The block persists until the victim discovers the grief and transfers out each dust position (30 transactions), so it is temporary rather than permanent. It also mirrors the advisory's profile: cheap unprivileged action imposing cleanup cost and denied service on another account.

### Likelihood Explanation
Medium-low. The attack requires no privileges, no governance, and works entirely through public `DepositToken.transfer`. Cost scales with the number of listed deposit tokens the attacker must acquire dust of; on pools with many collaterals the attacker needs real capital deposits, though only minimal amounts. Mitigating factors: the victim can self-recover by sweeping dust; existing-position holders retain full use of tokens already in their set; and the attacker gains no direct profit (pure griefing / liquidation-timing manipulation).

### Recommendation
- Do not auto-add to `depositTokensOfAccount` on unsolicited inbound `transfer`/`transferFrom`; only add on protocol-initiated `_mint` (deposit/seize paths), or require the recipient to opt in.
- Alternatively, let `transfer` evict/refuse dust below a threshold, or allow anyone (or the account itself) to call a `removeFromDepositTokensOfAccount`-style cleanup for zero-balance-equivalent dust.
- At minimum, emit events on set insertion so victims can detect and sweep dust entries.

### Proof of Concept
Foundry fork/Hardhat outline:

```ts
// Setup: pool with N deposit tokens dt_0..dt_k (k <= 30)
// 1. Attacker deposits minimal underlying into each DepositToken
for (const dt of depositTokens) {
  await underlyingOf(dt).approve(dt.address, 1);
  await dt.deposit(1, attacker.address);          // attacker holds dust
}
// 2. Attacker griefs victim — fills victim's per-account list
const victim = bob.address;
for (const dt of depositTokens) {
  await dt.connect(attacker).transfer(victim, 1); // Pool._transfer -> addToDepositTokensOfAccount(victim)
}
// pad remaining slots with extra deposit tokens until length == 30
expect(await pool.getDepositTokensOfAccount(victim)).to.have.length(30);

// 3. Victim cannot deposit a new collateral type
await expect(
  newDepositToken.connect(bob).deposit(1000, bob.address)
).revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 4. Victim cannot mint a new synthetic
await expect(
  pool.connect(bob).issue(newSynthetic.address, amount)
).revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 5. Anyone sending victim a not-yet-held deposit token reverts
await expect(
  otherDepositToken.connect(alice).transfer(victim, 1)
).revertedWithCustomError(pool, 'UserReachedMaxTokens');

// Recovery requires victim to sweep each dust entry individually
```

Key assertions: `getDepositTokensOfAccount(victim).length == MAX_TOKENS_PER_USER`, all new-token `deposit`/`issue`/inbound `transfer` calls revert with `UserReachedMaxTokens`, and prior functionality resumes only after the victim transfers the dust out.
