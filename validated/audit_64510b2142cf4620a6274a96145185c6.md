### Title
Unbounded array index derived from unvalidated call-data offset causes uncaught `ArrayIndexOutOfBoundsException` in `ValidateMultiSign`/`BatchValidateSign` TVM precompiles - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.ValidateMultiSign.execute()` and `PrecompiledContracts.BatchValidateSign.execute()` compute an array index into the `DataWord[] words` array directly from attacker-controlled call-data (`words[3]`/`words[1]`/`words[2]`, treated as an ABI offset) without checking that the resulting index is within `words.length`. This mirrors the CVE-2026-31558 bug class: a value that ultimately comes from external, attacker-controlled input is used as a raw array index without a bounds/negativity check before indexing a fixed-size array, causing an out-of-bounds access.

### Finding Description
In `ValidateMultiSign.execute()`:
```java
DataWord[] words = DataWord.parseArray(rawData);
...
if (VMConfig.allowTvmSelfdestructRestriction()) {
  int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
  ...
}
byte[][] signatures = ... extractSigArray(words, words[3].intValueSafe() / WORD_SIZE, rawData) : ...
``` [1](#0-0) 

and in `BatchValidateSign.doExecute()`:
```java
DataWord[] words = DataWord.parseArray(data);
...
int sigArraySize = words[words[1].intValueSafe() / WORD_SIZE].intValueSafe();
int addrArraySize = words[words[2].intValueSafe() / WORD_SIZE].intValueSafe();
``` [2](#0-1) 

`words[3]` (or `words[1]`/`words[2]`) is a raw 32-byte word taken directly from the smart-contract call data — an ABI "offset" field a caller fully controls. `DataWord.intValueSafe()` only clamps overflow/negative bit-patterns to `Integer.MAX_VALUE`; it never validates the value against the actual size of the `words` array:
```java
public int intValueSafe() {
  int bytesOccupied = bytesOccupied();
  int intValue = intValue();
  if (bytesOccupied > 4 || intValue < 0) {
    return Integer.MAX_VALUE;
  }
  return intValue;
}
``` [3](#0-2) 

Because `words` has a length bounded only by the (attacker-supplied) call-data size, while the offset field can independently be set to an arbitrary large value (e.g. `Integer.MAX_VALUE`), `words[3].intValueSafe() / WORD_SIZE` can trivially exceed `words.length - 1`, producing an `ArrayIndexOutOfBoundsException` when used to index `words[...]`. This indexing happens *before* the surrounding `try { ... } catch (Throwable t)` block that wraps only the signature-recovery/weight-calculation logic further down in `ValidateMultiSign`, and *before* any try/catch in `BatchValidateSign.doExecute()` (that method's outer `execute()` does catch `Throwable`, but the same unguarded pattern is directly analogous to the missing-bounds-check root cause described in the CVE — a numeric value from untrusted input used unchecked as an array subscript).

Contrast this with `extractBytesArray`/`extractSigArray`, which do at least guard the *offset* parameter (`if (offset > words.length - 1) return new byte[0][];`) before their own indexing loops — but the initial `words[words[3].intValueSafe() / WORD_SIZE]` dereference that computes `sigArraySize`/`addrArraySize` happens without any such guard. [4](#0-3) 

### Impact Explanation
An `ArrayIndexOutOfBoundsException` thrown from a precompiled-contract `execute()` call during TVM opcode execution is an uncontrolled runtime exception. Depending on how the surrounding `CALL`/`STATICCALL` dispatch in `Program`/`RuntimeImpl` handles it, this can propagate as an unexpected `RuntimeException` out of the normal VM exception-handling paths that are designed around `Program.Exception`/`ContractExeException` types, risking node-level instability (uncaught exception during block/transaction processing) rather than a clean revert. Any full node that executes a transaction calling this precompile (e.g., via `eth_call`, `triggercontract`, or block replay) is affected, making this reachable by any unprivileged transaction sender or JSON-RPC/gRPC caller invoking a contract that calls the `ValidateMultiSign` or `BatchValidateSign` precompiled address.

### Likelihood Explanation
High likelihood of reachability: both precompiles are reachable from ordinary contract calls (any account can deploy/call a contract that performs a `STATICCALL`/`CALL` to these fixed precompile addresses) and the offending offset words are taken straight from the transaction's call data with no validation prior to use as an array index divisor/index. No special privilege, feature flag beyond `allowTvmSelfdestructRestriction()`/default execution, or victim cooperation is required — a single malicious transaction suffices.

### Recommendation
Before using `words[3].intValueSafe() / WORD_SIZE]` (and the analogous `words[1]`/`words[2]` uses in `BatchValidateSign`) to index `words`, validate the computed index is within `[0, words.length)` and return the existing `Pair.of(true, DATA_FALSE)` failure result otherwise, mirroring the guard already present in `extractBytesArray`/`extractSigArray`. Apply the same bounds check consistently to every direct `words[...]` access derived from call-data-controlled offsets in `PrecompiledContracts.java`.

### Proof of Concept
1. Deploy a contract that performs a low-level call to the `ValidateMultiSign` precompiled contract address (or `BatchValidateSign`).
2. Craft the call data so that `words[3]` (offset word) encodes a very large value (e.g. `0xffffffff`), while the overall calldata is only long enough to contain the first few words (so `words.length` is small).
3. Trigger the contract call via a normal `TriggerSmartContract` transaction.
4. During execution, `words[words[3].intValueSafe() / WORD_SIZE]` computes an index far beyond `words.length`, throwing `ArrayIndexOutOfBoundsException` inside `PrecompiledContract.execute()`, which is not caught by the local exception-safety guards intended for this code path (verification of the exact exception propagation and its effect on node execution/JVM-level behavior in `Program`/`RuntimeImpl` would require dynamic testing, which was not performed here).
