### Title
`AttachmentsDownloader::run` Done-branch stores attacker-served attachment content unconditionally, without verifying it matches any confirmed on-chain `content_hash` - (File: stackslib/src/net/atlas/download.rs)

### Summary
When the Atlas attachment download state machine reaches `AttachmentsBatchStateMachine::Done`, every `Attachment` drained from `context.attachments` is persisted via `network.atlasdb.insert_instantiated_attachment(&attachment)` unconditionally, before/independently of whether `find_all_attachment_instances(&attachment.hash())` found any matching confirmed on-chain `AttachmentInstance`. A malicious outbound sync peer that is asked for a specific `content_hash` can instead return arbitrary bytes, and that arbitrary content gets written into the local `AtlasDB` "instantiated attachments" table and becomes servable by `find_attachment`, despite never having been committed to by any BNS name operation.

### Finding Description
The intended invariant is that an "instantiated" attachment stored in the Atlas DB corresponds to content that some on-chain `AttachmentInstance`/BNS name operation actually committed to (`stored_attachment.hash() == confirmed_name_op.content_hash`). The download pipeline is supposed to enforce this by requesting a specific `content_hash` (`AttachmentRequest.content_hash`) and only accepting attachment data that satisfies it.

Tracing the path:
1. `AttachmentsBatchStateContext::extend_with_attachments` decodes the HTTP GET-attachment response and does `self.attachments.insert(response.attachment)` with **no check** that `Hash160::from(&response.attachment.content) == request.content_hash` [1](#0-0) .
2. When the sub state machine finishes (`BatchedRequestsState::Done`), the top-level FSM transitions straight to `AttachmentsBatchStateMachine::Done` carrying whatever attachments were inserted in step 1 [2](#0-1) .
3. In `AttachmentsDownloader::run`, the `Done` branch drains `context.attachments` and, for each one, looks up `find_all_attachment_instances(&attachment.hash())` — but calls `insert_instantiated_attachment(&attachment)` **unconditionally**, regardless of whether that lookup returned any rows: [3](#0-2) .

Because `attachment.hash()` is computed from whatever bytes the malicious peer actually sent (not the originally requested `content_hash`), a peer can return content whose hash matches nothing in `attachment_instances`, and `insert_instantiated_attachment` still stores it. The equality `stored_attachment.hash() == some confirmed_name_op.content_hash` is therefore not enforced at the point of write — it's only checked incidentally afterward via `find_all_attachment_instances`, whose (empty) result is discarded rather than gating the insert.

No signature, length, or content-hash-vs-request check exists anywhere in this path to reject a mismatched body before persistence.

### Impact Explanation
Any peer selected via `network.get_outbound_sync_peers()` (an unprivileged remote node the victim dials out to, or that gossips/serves attachments) can, upon being asked for `content_hash = H`, return arbitrary bytes `D` where `hash(D) != H`. The victim node will:
- Persist `D` into its local `AtlasDB` "instantiated attachments" table under `hash(D)`, even though no BNS/name-related on-chain operation ever referenced `hash(D)`.
- Make `D` retrievable later via `AtlasDB::find_attachment(&hash(D))`, i.e., served from local storage without any canonical, on-chain backing.
- Leave the original requested instance for `H` unresolved (since resolution is keyed off `attachment.hash()`, not the original request's `content_hash`), causing it to be retried and eventually dropped after `max_attachment_retry_count`.

This is unauthenticated write of unverified data into node state and storage bloat with content that no confirmed BNS name operation committed to — matching the "attachment/BNS mismatch" High-severity category. It is repeatable per attachment request/response cycle and requires no privileged role, secret, or admin access — only that the node picks the attacker as an outbound sync peer or the attacker otherwise ends up serving the requested URL.

### Likelihood Explanation
- Precondition: the victim node must have a pending/unresolved `AttachmentInstance` (from a real, confirmed on-chain BNS operation) that it is trying to fetch, and the attacker must be reachable as one of the peers listed in the batch's inventory as having the attachment (`get_prioritized_attachments_requests` picks peers whose advertised inventory bit is set) [4](#0-3) .
- Attacker cost is trivial: run/advertise as a peer with the relevant inventory bit set, then answer the GET-attachment HTTP request with arbitrary bytes.
- No secret, signature, or privileged role is needed — full remote/network reachability via the P2P sync + HTTP data-plane used by Atlas.
- Repeatable per attachment fetch cycle, growing DB storage over time.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, verify `Hash160::from(&response.attachment.content) == request.content_hash` before inserting into `self.attachments`; drop/penalize the peer (bump failed requests) on mismatch instead of accepting the payload. Additionally, in the `Done` branch of `AttachmentsDownloader::run`, avoid calling `insert_instantiated_attachment` for attachments whose `find_all_attachment_instances` returned an empty set, unless the attachment is otherwise known-valid (e.g., matches the batch's requested `content_hash`).

### Proof of Concept
Rust test plan (in `stackslib/src/net/atlas/tests.rs` or a new test module), mirroring the question's proof idea:
```rust
#[test]
fn test_bogus_attachment_persisted_without_confirmed_instance() {
    let mut atlas_db = AtlasDB::connect_memory(AtlasConfig::default(true)).unwrap();

    // Craft an Attachment whose content/hash was never referenced by any
    // AttachmentInstance / BNS name op.
    let bogus_attachment = Attachment::new(vec![0xde, 0xad, 0xbe, 0xef]);
    let bogus_hash = bogus_attachment.hash();

    // Confirm no on-chain AttachmentInstance ever committed to this hash.
    let instances = atlas_db.find_all_attachment_instances(&bogus_hash).unwrap();
    assert!(instances.is_empty());

    // Directly exercise the unconditional insert performed in the Done branch
    // of AttachmentsDownloader::run (download.rs:159-162), regardless of the
    // empty `instances` result above.
    atlas_db.insert_instantiated_attachment(&bogus_attachment).unwrap();

    // The bogus content is now servable, despite zero confirmed BNS binding.
    let stored = atlas_db.find_attachment(&bogus_hash).unwrap();
    assert_eq!(stored, Some(bogus_attachment));
}
```
This demonstrates that `insert_instantiated_attachment` (and by extension the Done-branch loop at [3](#0-2) ) persists and later serves attachment content that has zero matching rows in `attachment_instances`, confirming the broken equality.
