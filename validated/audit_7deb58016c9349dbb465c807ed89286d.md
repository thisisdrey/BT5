### Title
Unvalidated section-length field in ARM ELF attributes parser causes linker panic on malformed input - ([File: src/cmd/link/internal/loadelf/ldelf.go])

### Summary
`parseArmAttributes` in the Go linker's ELF object loader reads attacker-controlled 32-bit length fields from a `.ARM.attributes` section and uses them directly to slice a byte buffer without any bounds checking, closely mirroring the underlying primitive of CVE-2018-8945 (`bfd_section_from_shdr`/attribute-section parsing in binutils causing a segfault on a malformed/oversized attribute section). A crafted ELF relocatable object containing a `SHT_ARM_ATTRIBUTES` (`.ARM.attributes`) section with a corrupted length can cause `go build`/`go tool link` to panic with an out-of-range slice/index instead of returning the intended `FormatError`-style error.

### Finding Description
Attacker input is a malicious ELF object file (e.g., a `.o`/`.syso` host object supplied as part of a Go package/module) that is linked in via the Go linker's host-object loading path (`cmd/link/internal/ld` invoking `cmd/link/internal/loadelf.Load`) [1](#0-0) . When `Load` encounters a section of type `SHT_ARM_ATTRIBUTES` named `.ARM.attributes`, it maps the section and calls `parseArmAttributes(e, sect.base[:sect.size])` [2](#0-1) .

Inside `parseArmAttributes`, the code:
- Indexes `data[0]` without checking `len(data) != 0` (panics if the section is empty), and
- Reads an attacker-controlled 32-bit `sectionlength` via `e.Uint32(data)`, which itself requires at least 4 bytes of `data` (panics if fewer remain), then slices `sectiondata := data[4:sectionlength]` and `data = data[sectionlength:]` with no check that `sectionlength >= 4` or `sectionlength <= len(data)` [3](#0-2) .

Any of these conditions (`sectionlength < 4` or `sectionlength > len(data)`, or a truncated buffer for the initial `Uint32` read) triggers a runtime panic ("slice bounds out of range" or "index out of range") rather than the graceful `FormatError` return path used elsewhere in `debug/elf` and other parts of `ldelf.go` (e.g., the section-header and shstrndx bounds checks in `Load`) [4](#0-3) . This is the same bug class as CVE-2018-8945: a length field taken from an "attribute section" of an ELF object is trusted without validation before being used to bound a buffer read, causing a crash while parsing the file.

### Impact Explanation
This causes a denial-of-service crash of the `go` toolchain (linker) while building a package that includes a malicious ELF host object (e.g., a `.syso` file bundled in a module, or a cgo-produced `.o` embedded/vendored by an attacker-controlled dependency). It does not lead to code execution or memory corruption (Go panics are safe, bounds-checked), so under Go's severity model this is a robustness/DoS bug in file parsing of untrusted binary data — likely a PUBLIC-track, low/medium-severity report (parser panic on malformed input), similar to previously-fixed panics in `debug/elf`/`cmd/link` object loaders. It is not equivalent in severity to the original memory-safety CVE (segfault/potential info leak in C) since Go's slice panics are recoverable and don't corrupt memory, but it is a real, reachable crash from attacker-supplied data during a normal build workflow.

### Likelihood Explanation
The victim scenario is: a developer runs `go build`/`go install` on a module or package that includes a host ELF object file (most plausibly a `.syso` resource file, which `go build` links in automatically without compiling it — no code execution is required from the attacker, just object-file inclusion) or a cgo-produced object that a malicious build step slipped in. No special privileges are needed; this matches the "published module/archive/source consumed by a normal victim workflow" premise. The `.ARM.attributes` section is not on the hot path for most builds (only exercised for ARM host-object cross-linking, and it is parsed unconditionally whenever a section of that type/name appears in a loaded ELF object) [5](#0-4) , so it requires the target architecture/toolchain path that loads external ELF objects containing this section, making the attack surface real but narrower than the general ELF section-header parsing in `debug/elf` (which already has explicit bounds checks, e.g. [6](#0-5) ).

### Recommendation
Add explicit bounds validation in `parseArmAttributes` before every slice/index operation: check `len(data) != 0` before `data[0]`, check `len(data) >= 4` before calling `e.Uint32(data)`, and validate `4 <= sectionlength && sectionlength <= uint32(len(data))` before computing `sectiondata := data[4:sectionlength]` and `data = data[sectionlength:]`; return the existing `fmt.Errorf(...)` malformed-file errors on any violation, matching the defensive style already used elsewhere in `Load` (e.g., the `shstrndx`/`symtab.link` range checks) [7](#0-6) .

### Proof of Concept
```go
package loadelf

import (
	"encoding/binary"
	"testing"
)

// Minimal reproduction of the out-of-bounds slice panic in parseArmAttributes
// when the .ARM.attributes section contains a corrupted/oversized length field.
func TestParseArmAttributesOOB(t *testing.T) {
	defer func() {
		if r := recover(); r == nil {
			t.Fatal("expected panic/graceful error on malformed .ARM.attributes section, got neither")
		}
	}()

	// "A" marker byte followed by a 4-byte little-endian section length
	// that is larger than the remaining data -- triggers
	// `sectiondata := data[4:sectionlength]` / `data = data[sectionlength:]`
	// slicing out of range.
	data := []byte{'A', 0xFF, 0xFF, 0xFF, 0xFF} // sectionlength = 0xFFFFFFFF, len(data)-1 = 4

	_, _, err := parseArmAttributes(binary.LittleEndian, data)
	if err == nil {
		t.Fatal("expected error, got nil (and no panic occurred)")
	}
}
```
Expected/actual behavior: instead of returning the intended `err` from `parseArmAttributes` (as the caller in `Load` expects and only logs via `log.Printf` [8](#0-7) ), the call panics with `slice bounds out of range [4:4294967295] with capacity 5`, crashing the linker process instead of surfacing a handled malformed-file error.
