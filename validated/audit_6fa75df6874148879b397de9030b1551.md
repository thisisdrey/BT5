Audit Report

## Title
Stale decimals snapshot lets external asset owner drain PSM reserve via `redeem` - (`substrate/frame/psm/src/lib.rs`)

## Summary
`pallet_psm::redeem` computes the external payout using the `ExternalAssetInfo.decimals` / `PsmInfo.internal_decimals` snapshot taken at `add_external_asset`/`create_psm` time, without re-validating it against the asset's current live decimals the way `mint` does via `ensure_decimals_match`. Since an external asset's decimals metadata is mutable at will by its `owner` (a normal, unprivileged `pallet-assets` capability, unrelated to PSM governance), the owner can change decimals after building up reserve via legitimate `mint`s, corrupting only the redeem-path scaling factor and causing the PSM to release far more external tokens than were actually deposited by that user.

## Finding Description
`add_external_asset` snapshots `T::Fungibles::decimals(external_asset)` into `ExternalAssetInfo::decimals`, and `create_psm` snapshots `internal_decimals` into `PsmInfo`. These are used to scale amounts between the internal stablecoin and external assets via `external_to_internal`/`internal_to_external`.

`mint()` guards against drift by calling `Self::ensure_decimals_match` before using the snapshot, which re-reads live decimals and errors with `DecimalsMismatch` on divergence.

`redeem()` has no equivalent guard: it reads `external.decimals` and `info.internal_decimals` directly from storage and uses them immediately in `internal_to_external` to compute `external_out`, transferred from the PSM reserve account to the caller.

Because raw balances in `pallet-assets` never rescale when the display `decimals` metadata changes, and `decimals` is mutable post-creation by the asset owner via `set_metadata`, an attacker who owns an approved external asset can: (1) get the asset approved with true decimals (e.g. 18); (2) use `mint()` legitimately to build real reserve at the correct rate; (3) call `set_metadata` to drop decimals (e.g. to 0) — this only blocks further `mint`s, not `redeem`s; (4) call `redeem()`, which reuses the stale 18-decimal exponent, multiplying the payout by `10^18` more than the true 0-decimal scale warrants, draining the pooled reserve of that external asset (contributed potentially by many users) far beyond what the attacker's own `internal_amount` legitimately backs.

## Impact Explanation
This breaks the "conserve value and settle exactly once to the rightful beneficiary and amount" invariant for the PSM reserve account (`psm_account`). It is a theft/unbacked-payout vulnerability: the corrupted value is the `external_out` amount computed in `redeem`, scaled by a stale `ExternalAssetInfo.decimals` value that no longer reflects the asset's true decimals, allowing withdrawal of far more of the reserve than the burned `internal_amount` backs.

## Likelihood Explanation
Requires the attacker's asset to first be approved via `add_external_asset` by the PSM's `full_admin`, a normal onboarding step that does not require the admin to act maliciously. The subsequent decimals mutation and redemption are entirely under the attacker's own control (they own the asset via `pallet-assets`, an unprivileged, permissionless capability) and require no special timing, collusion, or privileged access — fully repeatable once an asset is approved.

## Recommendation
Add the same `Self::ensure_decimals_match(&info, &internal_asset, &external_asset, &external)?` guard to `redeem()` before computing `external_out`, mirroring `mint()`. If unwinding pre-existing positions at the old rate is intentionally desired, halt `redeem` (not just `mint`) on drift until governance manually resolves/re-registers the pair with the corrected decimals and reconciled debt/reserve accounting.

## Proof of Concept
1. Attacker creates asset `X` via `pallet_assets::create` (permissionless) and sets `decimals = 18` via `set_metadata`.
2. PSM admin approves `X` via `add_external_asset`; `ExternalAssetInfo.decimals = 18` is snapshotted.
3. Attacker (or other users) calls `mint()` with a large `external_amount` of `X`, building real reserve of `X` in `psm_account`, computed correctly at 18 decimals.
4. Attacker calls `pallet_assets::set_metadata(X, decimals = 0)`.
5. Attacker calls `redeem(internal_asset, X, internal_amount, max_fee)`. `redeem` uses the stale `ext_decimals = 18` in `internal_to_external`, multiplying the payout by `10^18` relative to the true 0-decimal scale, transferring an inflated `external_out` of `X` out of `psm_account` to the attacker — as long as total reserve of `X` (from all depositors) covers it, exceeding what the attacker's `internal_amount` legitimately backs.
