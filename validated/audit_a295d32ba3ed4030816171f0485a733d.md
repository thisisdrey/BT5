### Title
`TrieUpdate::rollback()` does not undo `TrieRecorder::record_key_removal()` charges applied by `TrieUpdate::remove()`, permanently inflating `recorded_storage_size_upper_bound` for discarded state changes - (File: `core/store/src/trie/update.rs`)

### Summary
`TrieUpdate::remove()` unconditionally calls `recorder.record_key_removal()` (a flat 2000-byte surcharge added to `TrieRecorder::upper_bound_size`) *before* the removal is even placed into `prospective`. `TrieUpdate::rollback()` only clears `self.prospective` and calls `contract_storage.rollback_deploys()` — it never touches `self.trie.recorder`. Consequently, any `ContractData` removal performed by a contract call that is later reverted (rolled back) still leaves its 2000-byte accounting charge permanently baked into `upper_bound_size`/`removal_counter`, identical to what a committed removal would produce.

### Finding Description
`TrieUpdate::remove()` in [1](#0-0)  charges the recorder unconditionally for every `TrieKey::ContractData` removal:
```
if let Some(recorder) = &self.trie.recorder {
    if matches!(trie_key, TrieKey::ContractData { .. }) {
        recorder.record_key_removal();
    }
}
self.prospective.insert(...)
```
`record_key_removal()` adds 2000 bytes to `upper_bound_size` and bumps `removal_counter`, both `AtomicUsize` fields living on `TrieRecorder`, independent from `TrieUpdate::prospective`: [2](#0-1) .

`TrieUpdate::rollback()` only clears the prospective map and rolls back contract deploys — it never references `self.trie.recorder`: [3](#0-2) . By contrast, `commit()` moves `prospective` into `committed` but likewise never interacts with the recorder [4](#0-3) . This means the recorder-side "phantom charge" from a call to `remove()` is identical whether the surrounding `TrieUpdate` is ultimately committed or rolled back — the state change is discarded on rollback, but the accounting surcharge for it is not.

`recorded_storage_size_upper_bound()` (which reads `upper_bound_size`) is what the VM logic and runtime use to enforce the proof-size limit via `RuntimeExt::get_recorded_storage_size()` [5](#0-4)  and `TrieRecorder::check_proof_size_limit_exceed()` [6](#0-5) , and `RecordedStorageCounter::observe_size()` uses deltas of this same counter to raise `HostError::RecordedStorageExceeded` [7](#0-6) .

### Impact Explanation
This matches the "apply-path DoS/miscounted proof-limit enforcement" scoped impact explicitly called out in the question: an attacker-controlled contract can call `storage_remove` on `ContractData` keys inside a `FunctionCall` that is subsequently reverted (e.g. host-function panic, `env::panic`, insufficient gas mid-call, or any other failure path that triggers `state_update.rollback()`), and the 2000-byte-per-removal surcharge survives the rollback. Because the `TrieRecorder`/`upper_bound_size` is scoped to the shared `Trie` underlying the whole chunk-level `TrieUpdate` (not reset per-receipt — only the per-receipt *baseline* is snapshotted via `storage_proof_size_before_receipt`), phantom charges accumulated by one receipt's reverted removals persist in the trie-wide counter and can move the overall proof-size accounting closer to `check_proof_size_limit_exceed`'s threshold for subsequent, unrelated receipts processed against the same recorder within the same chunk.

The severity is bounded, however: the effect is deterministic and identical for every honest node re-executing the same receipts (no state-root divergence), and hitting `RecordedStorageExceeded` fails the offending function call gracefully rather than corrupting committed state. I was not able to fully verify, within the available tool budget, whether a `check_proof_size_limit_exceed`/`StorageError` triggered mid-apply for an *unrelated* receipt is always handled as a graceful `FunctionCallError` versus occasionally surfacing as an unrecoverable `StorageError` that could `panic!`/abort chunk application (which would elevate this to a shard-halting concern). Based on the code inspected, the mechanism is real and matches the described "cheap inflation of `recorded_storage_size_upper_bound` via calls that are ultimately rolled back," but I cannot confirm a concrete path to fund theft/freezing, consensus divergence, or a shard-halting panic from this alone.

### Likelihood Explanation
Trivial and cheap for any unprivileged account: deploy a contract that performs many `storage_remove` calls on `ContractData` keys and then deliberately panics/fails so the enclosing `TrieUpdate::rollback()` fires. Each remove costs only the fixed gas of a host `storage_remove` call, not proportional to the 2000-byte accounting surcharge, so the amplification ratio (gas paid vs. accounting bytes charged) favors the attacker. Repeatable in every chunk/receipt the attacker controls.

### Recommendation
Make the recorder-side removal accounting rollback-aware: either (a) defer `record_key_removal()` until `TrieUpdate::commit()` actually promotes the key from `prospective` to `committed` (mirroring the deferred nature of `contract_storage.commit_deploys()`), or (b) track pending removal charges per-`TrieUpdate` and explicitly reverse them (`upper_bound_size.fetch_sub(2000 * n)`, `removal_counter.fetch_sub(n)`) inside `TrieUpdate::rollback()` for exactly the `ContractData` removals present in the cleared `prospective` map.

### Proof of Concept
Rust unit test in `core/store/src/trie/update.rs`'s test module:
1. Build a `TrieUpdate` via `TestTriesBuilder`, ensure `trie.recording_reads_new_recorder()` is active so `trie.recorder` is `Some`.
2. Call `trie_update.remove(test_key(b"dog".to_vec()))` (a `ContractData` key).
3. Assert `trie_update.trie().recorded_storage_size_upper_bound() >= 2000`.
4. Call `trie_update.rollback()`.
5. Assert `trie_update.trie().recorded_storage_size_upper_bound()` is **unchanged** (still `>= 2000`), while `trie_update.prospective_len() == 0`, demonstrating the state change was discarded but the accounting charge was not.
6. Repeat steps 1-3 with `trie_update.commit(...)` instead of `rollback()` and show the recorded upper bound is identical to the rollback case, proving the recorder cannot distinguish committed vs. discarded removals.

```rust
    pub fn remove(&mut self, trie_key: TrieKey) {
        // We count removals performed by the contracts and charge extra for them.
        // A malicious contract could generate a lot of storage proof by a removal,
        // charging extra provides a safe upper bound. (https://github.com/near/nearcore/issues/10890)
        // This only applies to removals performed by the contracts. Removals performed
        // by the runtime are assumed to be non-malicious and we don't charge extra for them.
        if let Some(recorder) = &self.trie.recorder {
            if matches!(trie_key, TrieKey::ContractData { .. }) {
                recorder.record_key_removal();
            }
        }

        self.prospective.insert(trie_key.to_vec(), TrieKeyValueUpdate { trie_key, value: None });
    }
```

```rust
    pub fn commit(&mut self, event: StateChangeCause) {
        let prospective = std::mem::take(&mut self.prospective);
        for (raw_key, TrieKeyValueUpdate { trie_key, value }) in prospective {
            self.committed
                .entry(raw_key)
                .or_insert_with(|| RawStateChangesWithTrieKey { trie_key, changes: Vec::new() })
                .changes
                .push(RawStateChange { cause: event.clone(), data: value });
        }
        self.contract_storage.commit_deploys();
    }
```

```rust
    pub fn record_key_removal(&self) {
        // Charge 2000 bytes for every removal
        self.upper_bound_size.fetch_add(2000, Ordering::Release).checked_add(2000).unwrap();
        // No need to check for overflows here as the `upper_bound_size` would overflow sooner than
        // this if there was an overflow.
        self.removal_counter.fetch_add(1, Ordering::Relaxed);
    }
```

```rust
    /// Update the latest observed storage proof size and check if it exceeds the limit.
    /// Should be called after every trie operation.
    pub fn observe_size(&mut self, latest_storage_proof_size: usize) -> Result<(), VMLogicError> {
        self.last_observed_storage_size = latest_storage_proof_size;

        let current_size = self.get_storage_size()?;
        if current_size > self.size_limit {
            let limit_u64 = self.size_limit.try_into().map_err(|_| {
                VMLogicError::InconsistentStateError(InconsistentStateError::IntegerOverflow)
            })?;
            return Err(VMLogicError::HostError(HostError::RecordedStorageExceeded {
                limit: ByteSize::b(limit_u64),
            }));
        }

        Ok(())
    }
```
