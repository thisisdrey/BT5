### Title
Unbounded recursive descent in reference-tree WAL walker allows stack-exhaustion DoS from a crafted push - ([File: internal/gitaly/storage/wal/reftree/tree.go])

### Summary
The `Node.walk` method in `internal/gitaly/storage/wal/reftree/tree.go` recurses once per path segment of every reference tracked in the write-ahead-log's in-memory reference tree, with no maximum depth check analogous to the `MAX_TRIE_DEPTH` guard that was missing in the reported Scroll `walkTree` implementation. Since the reference tree is built from reference names supplied by an ordinary pushing client and is walked during every write transaction's commit path via `reference_recorder.go`, a specially crafted reference name with an extremely large number of `/`-separated components can drive the recursion to a depth controlled entirely by the pusher, which is a data-driven depth-limit omission of the same class as the reported finding.

### Finding Description
`Node.InsertNode`/`InsertReference` insert reference paths into an in-memory tree, one `Node` per path segment ( [1](#0-0) ). This tree is subsequently traversed by `WalkPreOrder`/`WalkPostOrder`, both of which delegate to the recursive helper `(*Node).walk`, which calls itself once per child for every directory level ( [2](#0-1) ). The recursion depth is therefore exactly the number of `/`-separated components in the deepest reference name that was inserted — a value that is fully attacker-controlled through the reference name supplied in a push, with no explicit maximum-depth check comparable to the `MAX_TRIE_DEPTH` (248) guard added for the Scroll `walkTree` bug. This walker is exercised through `internal/gitaly/storage/wal/reference_recorder.go`, which is invoked by `TransactionManager` as part of every write transaction that touches references (surfaced via `internal/gitaly/storage/storagemgr/partition/transaction_manager.go`, see the reference-recorder setup at commit time, and `transaction_manager_housekeeping.go`). Git's own `check-ref-format` rules constrain individual path components (no empty components, no leading `.`, etc.) but, unlike a fixed maximum trie depth, they do not cap the *number* of `/`-separated components in a reference name, so a reference name can in principle contain a very large number of segments and still pass Git's own validation.

### Impact Explanation
If a client can create (or attempt to create) a reference whose name contains a very large number of path segments, the depth-unbounded recursive walk in `Node.walk` will recurse proportionally, which can exhaust the goroutine stack and crash (or otherwise degrade) the Gitaly process handling the write transaction. Because this code path runs inside the transaction manager on every write to references, a single malicious push that manages to record such a reference could cause a denial of service for the affected partition/repository, impacting availability for legitimate operations against that storage.

### Likelihood Explanation
Likelihood is moderate rather than high: it depends on whether Git itself (or an earlier Gitaly-side reference-name validator) rejects reference names with an extremely large segment count before they ever reach `reference_recorder.go`/`reftree`. I was not able to conclusively verify, from the code reachable in this scan, a hard cap in Gitaly's reference-name validation (`internal/git/reference.go`) on the *number* of `/`-separated components (as opposed to per-component syntax rules), nor could I fully trace every caller of `WalkPreOrder`/`WalkPostOrder` in the time available. This uncertainty should be resolved by an engineer with full read access to `internal/git/reference.go`, `internal/gitaly/storage/wal/reference_recorder.go`, and the reftables/files reference-backend code paths to confirm whether an ordinary push can actually deliver a reference name with enough segments to threaten the goroutine stack.

### Recommendation
Add an explicit maximum path-segment depth check in `(*Node).walk` (and/or in `InsertNode`/`InsertReference`) mirroring the recommended `MAX_TRIE_DEPTH`-style guard from the reference report — reject or truncate processing of reference paths whose segment count exceeds a sane, documented maximum before recursing, and/or convert the recursive walk into an explicit-stack iterative walk (as is already done in `InsertNode`/`RemoveNode`/`Contains`) to remove the unbounded-recursion class of risk entirely.

### Proof of Concept
Not independently reproduced against a running Gitaly instance in this scan; the concern is derived from static analysis of the code paths cited above. A concrete PoC would involve pushing a reference name with a very large number of `/`-separated single-character components (e.g. `refs/heads/a/a/a/.../a` repeated many thousands of times) and observing whether it is accepted by the reference-name validation and, if so, whether the subsequent WAL commit path (`reference_recorder.go` → `reftree.Node.walk`) crashes or significantly degrades the `gitaly` process.

// InsertNode inserts a node into the tree at the given path optionally creating any
// missing parent directories.
func (n *Node) InsertNode(path string, createParents bool, isDirectory bool) error {
	var (
		pathPrefix string
		pathBase   = path
		node       = n
	)

	// Walk down the tree until we find the node.
	for {
		prefix, suffix, foundSeparator := strings.Cut(pathBase, "/")
		if !foundSeparator {
			// If there was no separator, then it means the current node
			// is the parent node of the inserted node.
			if node.children[pathBase] != nil {
				return errTargetAlreadyExists
			}

			targetNode := newFile()
			if isDirectory {
				targetNode = newDirectory()
			}

			node.children[pathBase] = targetNode

			return nil
		}

		// Since there was a separator, we still need to walk down the tree
		// to find parent node.
		child := node.children[prefix]
		if child == nil {
			if !createParents {
				return errParentNotFound
			}

			child = newDirectory()
			node.children[prefix] = child
		}

		if !child.isDirectory() {
			return errParentIsNotDirectory
		}

		node = child
		pathPrefix = filepath.Join(pathPrefix, prefix)
		pathBase = suffix
	}

func (n *Node) walk(path string, callback WalkCallback, preOrder bool) error {
	isDir := n.children != nil

	if preOrder {
		if err := callback(path, isDir); err != nil {
			return fmt.Errorf("pre-order callback: %w", err)
		}
	}

	type child struct {
		path string
		node *Node
	}

	sortedChildren := make([]child, 0, len(n.children))
	for path, childNode := range n.children {
		sortedChildren = append(sortedChildren, child{path: path, node: childNode})
	}

	// Walk the children in lexicographical order to produce deterministic ordering.
	sort.Slice(sortedChildren, func(i, j int) bool {
		return sortedChildren[i].path < sortedChildren[j].path
	})

	for _, child := range sortedChildren {
		if err := child.node.walk(filepath.Join(path, child.path), callback, preOrder); err != nil {
			return fmt.Errorf("walk: %w", err)
		}
	}
