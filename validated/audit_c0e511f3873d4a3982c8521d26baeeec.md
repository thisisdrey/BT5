Audit Report

## Title
`claim_rewards_to` benchmark returns `None` for bridge-hub-rococo relayer reward instances, poisoning the extrinsic's weight and permanently blocking alternative-beneficiary reward claims - ([File: cumulus/parachains/runtimes/bridge-hubs/bridge-hub-rococo/src/lib.rs])

## Summary
`pallet_bridge_relayers`'s benchmarking contract states that `prepare_rewards_account` returning `None` causes `claim_rewards_to` to be assigned `Weight::MAX`. On bridge-hub-rococo, both `RelayersForLegacyLaneIdsMessagesInstance` and `RelayersForPermissionlessLanesInstance` implementations of `prepare_rewards_account` unconditionally return `None`, and the committed autogenerated weight file confirms `claim_rewards_to()` is set to `Weight::from_parts(18_446_744_073_709_551_000, 0)` (i.e., `u64::MAX`, `Weight::MAX`'s ref_time). This makes the `claim_rewards_to` extrinsic permanently undispatchable for these two reward instances, since no block can accommodate a weight of `u64::MAX`.

## Finding Description
The benchmarking trait's documented contract is explicit: returning `None` from `prepare_rewards_account` causes `claim_rewards_to` to be assigned `Weight::MAX`. [1](#0-0) 

The `claim_rewards_to` benchmark implementation enforces this exactly: if `prepare_rewards_account` returns `None`, the benchmark result is overridden with `BenchmarkResult::from_weight(Weight::MAX)`. [2](#0-1) 

In `bridge-hub-rococo`'s runtime, both `BridgeRelayersConfig` implementations for `RelayersForLegacyLaneIdsMessagesInstance` and `RelayersForPermissionlessLanesInstance` explicitly return `None` from `prepare_rewards_account`, after depositing funds into the rewards account: [3](#0-2) [4](#0-3) 

This is directly reflected in the committed, autogenerated weight file for the legacy-lane instance, where `claim_rewards_to()` returns `Weight::from_parts(18_446_744_073_709_551_000, 0)` — i.e., `u64::MAX` ref_time — which is `Weight::MAX`'s ref-time component: [5](#0-4) 

Because the pallet's `claim_rewards_to` dispatchable is annotated with `#[pallet::weight(T::WeightInfo::claim_rewards_to())]`, this committed weight becomes the extrinsic's declared weight at runtime for these two configured instances. A weight of `u64::MAX` cannot fit within any realistic per-extrinsic or per-block weight limit, so any signed call to `claim_rewards_to` for these instances will be rejected by the runtime's weight-based validity checks before execution — it can never be included in a block.

This confirms the exact defect described in the claim, and matches a previously-fixed instance of the identical bug on bridge-hub-westend for the Snowbridge reward kind (fixed in `pr_10952.prdoc`), where `prepare_rewards_account` now returns `Some((...))` with a real beneficiary and funded relayer, instead of `None`.

## Impact Explanation
Relayers who have accumulated rewards under `RelayerRewards` for `RelayersForLegacyLaneIdsMessagesInstance` or `RelayersForPermissionlessLanesInstance` on bridge-hub-rococo cannot redirect their reward payout to an alternative beneficiary account via `claim_rewards_to`, because the extrinsic's committed weight (`u64::MAX`) makes it permanently undispatchable in any block. This is a permanent, protocol-level lock on a specific legitimate reward-routing capability — matching the "permanent user-fund ... lock" impact category, since affected relayers have no alternative in-protocol path to claim to a different account for these reward kinds. The basic `claim_rewards` extrinsic (claiming to `self`) is unaffected and still functions, limiting the impact strictly to the alternative-beneficiary claim path.

## Likelihood Explanation
This requires no privileged actor or malicious behavior — any ordinary relayer with an accumulated reward under either affected instance who calls the public `claim_rewards_to` extrinsic will trigger the fault deterministically, because the condition is baked into the already-committed weight tables generated from this exact benchmarking configuration. The identical failure mode has already been found and fixed for bridge-hub-westend's Snowbridge instance in this same repository, confirming the underlying defect pattern is real, reproducible, and was not consistently remediated across all bridge-hub runtimes sharing `pallet_bridge_relayers::benchmarking::Config`.

## Recommendation
Update `bridge-hub-rococo`'s `prepare_rewards_account` implementations for `RelayersForLegacyLaneIdsMessagesInstance` and `RelayersForPermissionlessLanesInstance` to return `Some((reward_kind, beneficiary))` with a properly funded, valid beneficiary, mirroring the westend fix, and regenerate/commit the corresponding weight files (`pallet_bridge_relayers_legacy.rs`, `pallet_bridge_relayers_permissionless_lanes.rs`) so `claim_rewards_to` receives a realistic, dispatchable weight for both instances. Add a CI check asserting no generated `WeightInfo` weight for a public extrinsic approaches `Weight::MAX`, to catch this benchmark-helper-returns-`None` pattern automatically.

## Proof of Concept
1. Inspect `cumulus/parachains/runtimes/bridge-hubs/bridge-hub-rococo/src/lib.rs` lines 1383-1403 and 1414-1428: both `prepare_rewards_account` implementations return `None`.
2. Per `bridges/modules/relayers/src/benchmarking.rs` lines 95-105, this causes the `claim_rewards_to` benchmark to be overridden with `BenchmarkResult::from_weight(Weight::MAX)`.
3. Confirm the committed weight file `cumulus/parachains/runtimes/bridge-hubs/bridge-hub-rococo/src/weights/pallet_bridge_relayers_legacy.rs` lines 69-76: `claim_rewards_to()` returns `Weight::from_parts(18_446_744_073_709_551_000, 0)` (`u64::MAX`).
4. At runtime, a relayer with a reward registered under `RelayerRewards` for `RelayersForLegacyLaneIdsMessagesInstance` (or the permissionless-lanes instance) submits `claim_rewards_to(reward_kind, alternative_beneficiary)`; because the extrinsic's declared weight is `u64::MAX`, the transaction is rejected by weight validity checks and can never be included in a block, permanently preventing the reward from being routed to an alternative beneficiary for these instances.
