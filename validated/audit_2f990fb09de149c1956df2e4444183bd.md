### Title
Global connection-slot starvation via pre-handshake QUIC connection churn - ([File: streamer/src/nonblocking/quic.rs])

### Summary
`run_server`'s accept loop reserves a `ClientConnectionTracker` slot (bounded by `qos.max_concurrent_connections()`) and increments `outstanding_incoming_connection_attempts` immediately after `incoming.accept()`, but only *consumes* `ConnectionRateLimiter`/`overall_connection_rate_limiter` tokens later in `setup_connection` after the QUIC handshake completes. Because the accept-loop checks (`overall_connection_rate_limiter.current_tokens() == 0` and `rate_limiter.is_allowed`) are non-mutating peeks that never deplete unless a handshake actually finishes, an attacker who opens connections and lets them idle/drop before completing the handshake can hold slots for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) each without ever tripping the consuming rate limiters, potentially pinning `open_connections` near `max_concurrent_connections()` and causing legitimate peers (including legitimate unstaked ones) to be refused via `incoming.refuse()`.

### Finding Description
In `run_server` [1](#0-0) , for every incoming connection the loop:
1. Peeks `overall_connection_rate_limiter.current_tokens() == 0` (non-consuming) and `rate_limiter.is_allowed(ip)` (non-consuming, and returns `true` unconditionally for any IP not previously *registered*, see `is_allowed` in `connection_rate_limiter.rs` [2](#0-1) ).
2. Calls `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())`, which increments `stats.open_connections` and enforces the *global* concurrency cap [3](#0-2) .
3. Increments `outstanding_incoming_connection_attempts` and spawns `setup_connection`, which awaits the handshake with a 2-second timeout before doing anything else [4](#0-3) .

Only inside `setup_connection`, *after* the handshake resolves, does the code actually consume tokens via `rate_limiter.register_connection(&from.ip())` and `overall_connection_rate_limiter.consume_tokens(1)` [5](#0-4) . The `ClientConnectionTracker` is only dropped (releasing the global slot) once `setup_connection` returns, i.e., after the handshake attempt times out or errors [6](#0-5) .

This means the accept-loop's rate-limiter checks (step 1) are peeks against buckets that are never drained by connection attempts that don't finish a handshake — so an attacker sending only Initial packets (or opening and immediately abandoning connections without completing the TLS/QUIC handshake) can pass both peek checks indefinitely (since `current_tokens()` never decreases and unseen/idle IPs are always `is_allowed`), while still consuming a `ClientConnectionTracker` slot and an `outstanding_incoming_connection_attempts` count for up to the full `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` window. By continuously rotating incomplete handshakes (across enough concurrent attempts, `num_shards`/source IPs to spread rate-limiter shard contention), the attacker can keep `stats.open_connections` pinned near `qos.max_concurrent_connections()`, causing `ClientConnectionTracker::new` to return `Err(())` for legitimate incoming connections, which are then refused via `incoming.refuse()` and counted in `stats.refused_connections_too_many_open_connections` [7](#0-6) .

Note: QUIC's amplification-limit/address-validation semantics require the attacker to actually be reachable at the source IP to make forward progress on the handshake at all, so pure IP spoofing without receiving return traffic will not occupy a slot for the full 2 seconds (the connecting future will typically fail fast on transport errors). This constrains, but does not eliminate, the attack: the attacker still needs real (but not large numbers of) reachable IPs/ports to sustain many concurrent partial handshakes.

### Impact Explanation
This is a remote DoS against the global QUIC accept path: the shared `open_connections` cap (`qos.max_concurrent_connections()`) gates *all* incoming connections, staked and unstaked alike, before peer classification occurs. Exhausting it denies legitimate unstaked (and even staked) peers a connection slot, matching the "remote DoS denying legitimate unstaked traffic" bounty category. It does not bypass sigverify, dedup, or execution — it is a resource-starvation issue on the pre-classification connection-admission path, not a verification bypass.

### Likelihood Explanation
Feasibility depends on how many concurrent, real, reachable source endpoints (IPs/ports) the attacker needs to sustain `max_concurrent_connections()` (default staked+unstaked totals ~4000, per `DEFAULT_MAX_STAKED_CONNECTIONS`/`DEFAULT_MAX_UNSTAKED_CONNECTIONS` = 2000 each) worth of simultaneous partial handshakes, refreshed every ~2 seconds (`QUIC_CONNECTION_HANDSHAKE_TIMEOUT`). This requires substantial but not staked/gossip-level resources (no stake, no keys, no validator identity needed) — a moderately resourced unstaked attacker with many source ports/IPs could sustain this. The per-IP/global token buckets, as currently wired, do not mitigate it because they are only debited on handshake completion, not on connection-attempt volume.

### Recommendation
Enforce rate limiting (or a lighter-weight per-source in-flight-attempt cap) at accept time before reserving a `ClientConnectionTracker` slot, rather than deferring all consumption to post-handshake. For example, maintain a separate bounded counter for "in-flight, not-yet-authenticated" connection attempts per IP (independent from the post-handshake `ConnectionRateLimiter`), and/or make the accept-loop peek checks also account for in-flight (not-yet-consumed) attempts so that a burst of never-completing handshakes cannot occupy an unbounded fraction of `max_concurrent_connections()` relative to genuinely completed connections.

### Proof of Concept
Rust integration test plan (in `streamer/src/nonblocking/quic.rs` test module, alongside `setup_quic_server`):
1. Start a test QUIC server via `setup_quic_server` with a small `max_concurrent_connections` (e.g., set staked+unstaked limits low, e.g. 4) so the test completes quickly.
2. Spawn `N` (> max_concurrent_connections) client tasks that each: create a `quinn::Endpoint`, initiate a connection (`endpoint.connect(...)`), and then immediately drop the endpoint/connecting future without ever completing the handshake response (or use a raw UDP socket to send only an Initial packet and then go silent), repeating this in a tight loop for the duration of the test.
3. Concurrently attempt one legitimate client connection (`make_client_endpoint`) that fully completes the handshake and sends a transaction.
4. Assert that `stats.refused_connections_too_many_open_connections` increases significantly during the churn, and assert whether the legitimate client's connection is delayed or refused (i.e., `count_received_packets_for` returns 0 or the connection is closed with `CONNECTION_CLOSE_CODE_TOO_MANY`/refused), demonstrating that legitimate traffic is starved despite the churn traffic never registering in `ConnectionRateLimiter` (assert `stats.connection_rate_limited_per_ipaddr` and `stats.connection_rate_limited_across_all` stay near 0 while `stats.open_connections` stays pinned at `max_concurrent_connections()`).

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
}
