## Analysis Summary

The Bunni bug's core broken invariant is: **a value-changing operation (rebalance) skips the same accounting hand-off that sibling operations (deposit/withdraw/swap) reliably perform**, so a component that consumes that data later cannot verify or trust it. The closest structural analog in `polkadot-sdk` is in the Snowbridge v2 queues, where the `AddTip` bookkeeping call mutates the exact value (`fee`/tip) that a sibling code path (`register_reward`) later pays out as real balance — but the mutation itself performs **no currency movement or backing check**, unlike every other reward-affecting write in these pallets. ### Title
Unbacked tip bookkeeping in Snowbridge v2 queues allows inflated relayer reward registration - (File: `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs`, `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
Both `pallet-inbound-queue-v2` and `pallet-outbound-queue-v2` implement the `AddTip` trait to let a tip be added to a pending message nonce. In both implementations, `add_tip` only performs a storage mutation — incrementing `Tips<T>[nonce]` (inbound) or `PendingOrders<T>[nonce].fee` (outbound) — with **no corresponding balance transfer, reservation, or hold** taken from any account inside the pallet. [3](#0-2) [4](#0-3) 

That mutated value is later trusted blindly at payout time: `process_message` (inbound) and `process_delivery_receipt` (outbound) read the tip/fee value and call `T::RewardPayment::register_reward(...)`, which ultimately becomes a real, claimable balance paid out of the bridge rewards pot via `pallet-bridge-relayers::claim_rewards`/`claim_rewards_to`. [5](#0-4) [6](#0-5) [7](#0-6) 

This mirrors the Bunni class of bug precisely: one code path (deposit/withdraw/swap reserve-change reporting, here the ordinary message fee attached at submission time via `Message.fee`/`relayer_fee`) is properly value-conserving, while a parallel path meant to augment the same accounting (`afterRebalance` in Bunni, `AddTip::add_tip` here) is not given/does not enforce the same value backing, letting downstream logic (Hooklet custom logic / `register_reward` payout) act on inconsistent, unverified data.

### Finding Description
- In `pallet-inbound-queue-v2`, `Tips<T>` is a plain `StorageMap<u64, u128>` mutated by `add_tip` with only an `amount > 0` and "nonce not yet consumed" check — no `Currency`/`fungible` withdrawal, hold, or reserve is taken from any caller. [8](#0-7) [3](#0-2) 
- At message processing time, this unbacked tip is simply added to `relayer_fee` and registered as a reward for whoever calls `submit`/`process_message`: [5](#0-4) 
- The outbound queue follows the identical pattern: `AddTip::add_tip` for `pallet-outbound-queue-v2` increments `PendingOrders<T>[nonce].fee` with no funds movement, and that field is later paid out verbatim via `register_reward` in `process_delivery_receipt`. [4](#0-3) [6](#0-5) 
- The actual DOT/asset payout happens later and separately, from a shared rewards-pot sovereign account, when the registered relayer calls `claim_rewards`/`claim_rewards_to` on `pallet-bridge-relayers`: [7](#0-6) 

Because neither queue pallet enforces that the numeric tip added via `AddTip::add_tip` is ever actually backed by a matching balance debit/lock in the same call, the correctness of the entire reward accounting depends entirely on whatever caller invokes `AddTip::add_tip` (e.g., a higher-level XCM/system-frontend handler) independently and correctly deducting real funds before calling this trait method. Within the queue pallets themselves — which are the pallets that ultimately convert this number into a real, claimable balance — there is no such guard, no event correlating the tip to an actual transfer, and no invariant check (e.g., total registered reward ≤ total funds received for that nonce).

### Impact Explanation
If the calling context that invokes `AddTip::add_tip` (outside these two pallets) does not itself perform an equal, atomic, and irreversible balance transfer/lock backing `amount`, an attacker can inflate `Tips`/`PendingOrders.fee` arbitrarily for a message they intend to relay, then relay/submit the receipt themselves and collect an unbacked reward via `register_reward`. Because the actual DOT payout later comes from a shared rewards-pot account (`PayRewardFromAccount`) or an XCM-driven asset mint (`PayAccountOnLocation`), this can drain the pot or forge reward-backed mints — i.e., theft/unbacked mint of bridge funds, which is squarely within the "theft or unbacked mint or unlock" and "duplicate settlement or payout" impact categories for this program.

### Likelihood Explanation
This finding is conditioned on how `AddTip::add_tip` is invoked in the runtime (e.g. via `pallet-system-frontend`, referenced in the grep results but not confirmed in this pass to correctly lock funds before calling the trait). If that calling site properly debits real funds atomically before invoking `add_tip`, the design is safe by composition; if it does not, the two queue pallets provide zero independent defense — there is no re-entrancy guard, no balance-conservation assertion, and no correlation between the recorded tip and any transferred value inside `inbound-queue-v2`/`outbound-queue-v2` themselves. Given the strict architectural separation (queue pallets vs. reward pallet vs. whatever front-end calls `AddTip`), and that this is the exact "missing accounting hand-off between sibling operations" pattern from the source report, this is flagged as the strongest local analog found, but full confirmation requires verifying the origin/funds-check in the `AddTip::add_tip` caller (e.g., `pallet-system-frontend`), which could not be completed within the available search budget.

### Recommendation
- Require `AddTip::add_tip` implementations in `pallet-inbound-queue-v2` and `pallet-outbound-queue-v2` to accept and validate a proof of funds transfer (or perform the debit themselves) atomically with the storage mutation, rather than trusting the caller.
- Add an invariant check at reward-registration time (`process_message`/`process_delivery_receipt`) that the total `relayer_fee + tip` registered for a nonce does not exceed value actually received/locked for that nonce.
- Emit an event linking each tip increment to the concrete transfer that funded it, to allow off-chain/governance auditing of reward-pot solvency.

### Proof of Concept
1. Confirm (or, if not yet confirmed, treat as the missing precondition) that the runtime's front-end pallet invoking `AddTip::add_tip` does not itself perform a matching, atomic balance debit/lock before calling `add_tip`.
2. Attacker observes an in-flight Ethereum→BridgeHub message with nonce `N` not yet consumed (`Nonce::<T>::get(N) == false`).
3. Attacker calls the exposed front-end extrinsic that maps to `AddTip::add_tip(N, huge_amount)` — this only mutates `Tips::<T>[N]` (or `PendingOrders::<T>[N].fee` on outbound) with no funds moving. [3](#0-2) 
4. Attacker submits the legitimate Ethereum event proof for nonce `N` themselves via `submit`/`submit_delivery_receipt`, becoming `relayer`.
5. `process_message`/`process_delivery_receipt` reads `Tips::<T>::take(N)` (or `PendingOrders[N].fee`) and calls `T::RewardPayment::register_reward(&attacker, kind, relayer_fee + huge_amount)`. [5](#0-4) 
6. Attacker later calls `pallet_bridge_relayers::claim_rewards_to` to redeem the inflated registered reward against the shared rewards-pot account, extracting real balance never actually deposited for this nonce. [7](#0-6)

	impl<T: Config> AddTip for Pallet<T> {
		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			// If the nonce is already processed, return an error
			ensure!(!Nonce::<T>::get(nonce.into()), AddTipError::NonceConsumed);
			// Otherwise add the tip.
			Tips::<T>::mutate(nonce, |tip| {
				*tip = Some(tip.unwrap_or_default().saturating_add(amount));
			});
			return Ok(());
		}
	}

	impl<T: Config> AddTip for Pallet<T> {
		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			PendingOrders::<T>::try_mutate_exists(nonce, |maybe_order| -> Result<(), AddTipError> {
				match maybe_order {
					Some(order) => {
						order.fee = order.fee.saturating_add(amount);
						Ok(())
					},
					None => Err(AddTipError::UnknownMessage),
				}
			})
		}
	}
