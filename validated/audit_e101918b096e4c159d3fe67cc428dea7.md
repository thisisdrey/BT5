Based on my research, I found a code pattern in the `liquidate-multi` batch-liquidation path that mirrors the reported bug class: a later validation step's rejection fires *after* earlier state has already been committed, and the rejection isn't properly propagated to undo that committed state — leaving the system in a permanently inconsistent, partially-applied state, analogous to `bad-blk-sigops` firing after body data is already accepted without setting `corruptionIn`.

### Title
Partial liquidation state (debt removal + collateral seizure) survives a failed bad-debt-socialization check in `liquidate-multi`, leaving unbacked debt on the books - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate-multi` batches liquidations via `(ok (map call-liquidate positions))` [1](#0-0) , where `call-liquidate` invokes the public function `liquidate` as a **plain in-contract call**, not via `contract-call?` [2](#0-1) . Inside `liquidate`, debt removal and collateral seizure are executed and committed via `contract-call? .v0-market-vault debt-remove-scaled/collateral-remove` *before* the bad-debt-socialization check, which only runs afterward and can fail with `ERR-BAD-DEBT-SOCIALIZATION-FAILED` [3](#0-2) .

### Finding Description
For a single external call to `liquidate`, this is safe: `liquidate` is the top-level transaction, so any later `asserts!` failure (e.g. `ERR-BAD-DEBT-SOCIALIZATION-FAILED`) reverts the entire transaction, including the earlier `debt-remove-scaled`/`collateral-remove` calls.

However, `liquidate-multi` calls `liquidate` directly (not through `contract-call?`) inside `map`, and does not `try!`/`unwrap!` the per-position result — it simply collects each `(response ...)` into the output list [4](#0-3) . This means:
1. `vault-system-repay`, `debt-remove-scaled`, and `collateral-remove` — each a distinct, individually-committing `contract-call?` — succeed and their effects persist as soon as they return `ok`.
2. Only afterward does the bad-debt socialization fold (`socialize-debt-asset`) run over any leftover unrepayable debt [5](#0-4) , and if any element in that fold fails (e.g., an inner `vault-socialize-debt`/`vault-accrue`/`debt-remove-scaled` sub-call errors), the outer `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` fails and `liquidate` returns `err`.
3. Because `liquidate` was invoked as a plain function call (no `contract-call?` savepoint) and `liquidate-multi` does not propagate that error via `try!`, the overall `liquidate-multi` transaction still commits successfully with `(ok (list ... (err ERR-BAD-DEBT-SOCIALIZATION-FAILED) ...))`.
4. The already-committed collateral seizure and debt removal for the "repayable" portion remain in place, but the leftover unpayable bad debt is never written off (no `lindex` write-down, no debt clearing) — leaving debt on the books with zero backing collateral.

This is structurally identical to the reported bug class: a later-stage rejection (bad-debt-socialization assert, playing the role of `bad-blk-sigops`) fires after earlier state has already been accepted (debt/collateral removal, playing the role of the committed block header), and the rejection path does not correctly signal that the whole operation must be undone (playing the role of `corruptionIn` defaulting to `false`), producing a permanently poisoned/inconsistent state. The single-call `liquidate` path is the "fixed" atomic entry point; `liquidate-multi` is the surviving alternate trigger path that bypasses the same protection.

### Impact Explanation
Debt left on a borrower's ledger with no backing collateral and no corresponding vault write-down inflates the vault's recorded `total-borrowed`/asset accounting relative to real backing, since the loss is never socialized into `lindex`. This constitutes protocol insolvency risk: LP share prices are computed against phantom, unrecoverable debt, meaning later depositors/withdrawers absorb a loss that was never properly recognized. This lands in the **Critical** impact bucket (protocol insolvency).

### Likelihood Explanation
Reachable by any unprivileged liquidator calling `liquidate-multi`, an ordinary permissionless market entry point — no DAO or privileged access needed. The likelihood depends on being able to trigger a failure inside `socialize-debt-asset`'s nested calls (`vault-socialize-debt`, `vault-accrue`, or `debt-remove-scaled`) for a specific debt asset while collateral has already been fully seized for the liquidated asset. I was not able to fully confirm, within available tool calls, the exact real-world conditions under which `vault-socialize-debt` fails for an ordinary caller (e.g., a zero-scaled debt entry edge case), so likelihood should be validated via local Clarinet-based test execution. Additionally, this finding rests on the assumption — standard in Clarity but not independently confirmed from in-repo documentation in this session — that only `contract-call?` invocations create rollback savepoints, while plain in-contract function calls (like `call-liquidate` → `liquidate`) do not. This should be verified with hands-on testing before treating the finding as fully proven.

### Recommendation
In `liquidate-multi`, either: (a) restructure so each per-position liquidation actually runs through a `contract-call?` boundary (e.g., `contract-call? .market liquidate ...`) so a failure rolls back exactly that position's partial state, or (b) move all irreversible state mutations (`debt-remove-scaled`, `collateral-remove`) to occur strictly *after* the bad-debt-socialization step succeeds, so no partial/committed state can survive a later failure.

### Proof of Concept
1. Attacker/liquidator identifies a borrower position with multiple debt assets where one debt asset's remaining balance, after this liquidation, is on a path that causes `socialize-debt-asset`'s nested call (e.g., `vault-socialize-debt`) to fail (exact triggering condition not fully confirmed here — requires Clarinet test exploration of `vault-socialize-debt`'s failure modes, such as a zero-scaled leftover entry or a vault-side guard).
2. Liquidator calls `liquidate-multi` with a single position matching that borrower/asset pair (or batches many, isolating this one).
3. `call-liquidate` → `liquidate` executes: `vault-system-repay`, `debt-remove-scaled`, `collateral-remove` all succeed and commit.
4. The bad-debt-socialization fold fails on the crafted debt entry; `liquidate` returns `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)`.
5. `liquidate-multi` still returns `(ok (list (err ERR-BAD-DEBT-SOCIALIZATION-FAILED)))` and the transaction commits.
6. Query the borrower's position afterward: collateral is fully removed, but the leftover bad debt entry is still present in `market-vault` with no lindex write-down having occurred — confirming the unbacked, unsocialized debt persists.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))

;; Liquidates multiple positions atomically
;; Each position can have different: borrower, collateral asset, debt asset, and debt amount
;; Prevents front-running attacks that prevent bad debt socialization
;; Note: price-feeds not supported in batch - update prices separately or use individual liquidate()
;; Returns list of responses - one per position (ok/err)
;; Failed liquidations return error codes but don't revert entire batch
(define-public (liquidate-multi
                (positions (list 64 { borrower: principal,
                                      collateral-ft: <ft-trait>,
                                      debt-ft: <ft-trait>,
                                      debt-amount: uint,
                                      min-collateral-expected: uint })))
  (ok (map call-liquidate positions)))
