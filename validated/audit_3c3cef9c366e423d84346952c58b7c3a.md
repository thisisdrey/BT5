### Title
`do_drop_history` silently discards the `charge` error while still emitting `HistoryDropped` and consuming the payout record - ([File: substrate/frame/broker/src/dispatchable_impls.rs])

### Summary
`Pallet::<T>::do_drop_history` in `pallet-broker` mirrors the exact bug class from the report: it calls a fallible operation (`Self::charge`) but discards the `Result` with `let _ = ...` instead of propagating the error, then proceeds to advance state and emit an event that claims the payout succeeded. [1](#0-0) 

### Finding Description
`do_drop_history` takes the `InstaPoolHistory` record for a timeslice out of storage first via `InstaPoolHistory::<T>::take(when)`, which unconditionally removes it. If the record has a `maybe_payout`, the code attempts to withdraw that amount from the pallet's own account and forward it to `T::OnRevenue` via `Self::charge`:

```rust
let record = InstaPoolHistory::<T>::take(when).ok_or(Error::<T>::NoHistory)?;
if let Some(payout) = record.maybe_payout {
    let _ = Self::charge(&Self::account_id(), payout);
}
let revenue = record.maybe_payout.unwrap_or_default();
Self::deposit_event(Event::HistoryDropped { when, revenue });
Ok(())
``` [2](#0-1) 

`Self::charge` is fallible — it does `T::Currency::withdraw(&who, amount, Exact, Expendable, Polite)?` before calling `T::OnRevenue::on_unbalanced(credit)`: [3](#0-2) 

Withdraw with `Exact` precision and `Polite` fortitude can fail (e.g., insufficient free/withdrawable balance in the pallet account, existential-deposit/consumer-reference constraints, or a `Frozen`/locked balance on the account). When `charge` fails, the error returned by `withdraw` is thrown away by `let _ = ...`. The function still: (1) has already irreversibly removed the `InstaPoolHistory` entry via `take`, (2) computes `revenue` from the same `maybe_payout` value regardless of whether the charge succeeded, and (3) emits `Event::HistoryDropped { when, revenue }` announcing that the payout of `revenue` occurred, and returns `Ok(())`.

This is the same invariant break as the report's `RemoveDelegateStake`: a fallible sub-operation's error is deliberately swallowed instead of bubbling up, so a caller/observer (and on-chain event log) is told an action succeeded (revenue distributed/history dropped cleanly) while the actual value transfer to `T::OnRevenue` never happened. Unlike `RemoveStake`'s correct pattern in the analogous report, there is no sibling function in this pallet enforcing the correct behavior for comparison, but the direct-fix comparison from the report applies identically: return the error instead of discarding it.

### Impact Explanation
This falls under "duplicate settlement or payout" / state advancing without the corresponding value movement succeeding, and under public underpriced/incorrect settlement flows called out in the required-impact gate ("Message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically"). Here the `InstaPoolHistory` record (the payout/settlement state) is destructively removed and a "dropped" event asserting the revenue amount is emitted even when the underlying `charge`/withdraw failed, permanently losing track of that revenue with no way to retry or recover it, since the source record is gone. This can also degrade the accounting used by `T::OnRevenue` recipients (typically a treasury/broker revenue split) — the beneficiary silently receives less than the chain believes it did.

### Likelihood Explanation
`do_drop_history` is reachable once the configured `contribution_timeout` has elapsed for a timeslice — the `ensure!(status.last_timeslice > when.saturating_add(config.contribution_timeout), Error::<T>::StillValid)` gate confirms this is a normal, expected, unprivileged/permissionless-style cleanup path rather than a rare edge case. [4](#0-3) 
The failure condition on `charge` (insufficient balance in the pallet's account when funds have already been spent/reserved elsewhere, or the withdrawal amount exceeding what's actually free) is plausible under normal operation without requiring a malicious peer, validator, or governance actor — it only requires the broker pallet's internal accounting to be transiently short, which the `let _ =` masking prevents anyone from detecting or reverting.

### Recommendation
Propagate the error from `Self::charge` instead of discarding it, and avoid destructively taking the `InstaPoolHistory` record (or otherwise ensure atomicity) until the charge has succeeded, e.g.:
```rust
if let Some(payout) = record.maybe_payout {
    Self::charge(&Self::account_id(), payout)?;
}
```
This restores the "advance state only after settlement succeeds" invariant, matching the corrected pattern shown by the external report (`RemoveStake` returning the error rather than swallowing it).

### Proof of Concept
1. Configure/observe a timeslice whose `InstaPoolHistory` entry has `maybe_payout = Some(payout)`.
2. Arrange (through normal pallet operation, e.g. a sequence of sales/renewals/on-demand purchases that draw down the broker pallet account's free balance) for the broker pallet's account (`Self::account_id()`) to have less free/withdrawable balance than `payout` at the time `contribution_timeout` elapses.
3. Call `drop_history(when)` (permissionless once `status.last_timeslice > when + contribution_timeout`).
4. `InstaPoolHistory::<T>::take(when)` removes the record unconditionally; `Self::charge` fails internally on the `withdraw` call, but the error is discarded by `let _ = ...`.
5. `Event::HistoryDropped { when, revenue: payout }` is emitted and the call returns `Ok(())`, even though `T::OnRevenue::on_unbalanced` was never invoked with the corresponding credit — the payout is lost and unrecoverable since the source record no longer exists.

I was unable to fully verify, within the remaining tool budget, the exact dispatchable wrapper/origin check for `drop_history` in `substrate/frame/broker/src/lib.rs` (i.e., whether it requires `ensure_signed` only or an additional origin filter) or the exact configured `T::OnRevenue`/`T::Currency` implementations in production runtimes, which would affect precisely how "polite" the withdraw failure mode is in practice. This should be confirmed by reading the `#[pallet::call]` definition of `drop_history` and the runtime's `Config` for `pallet-broker`.

	pub(crate) fn do_drop_history(when: Timeslice) -> DispatchResult {
		let config = Configuration::<T>::get().ok_or(Error::<T>::Uninitialized)?;
		let status = Status::<T>::get().ok_or(Error::<T>::Uninitialized)?;
		ensure!(
			status.last_timeslice > when.saturating_add(config.contribution_timeout),
			Error::<T>::StillValid
		);
		let record = InstaPoolHistory::<T>::take(when).ok_or(Error::<T>::NoHistory)?;
		if let Some(payout) = record.maybe_payout {
			let _ = Self::charge(&Self::account_id(), payout);
		}
		let revenue = record.maybe_payout.unwrap_or_default();
		Self::deposit_event(Event::HistoryDropped { when, revenue });
		Ok(())
	}
```

	pub(crate) fn charge(who: &T::AccountId, amount: BalanceOf<T>) -> DispatchResult {
