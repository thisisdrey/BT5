### Title
Unguarded division by `totalEnergyWeight` in TVM energy-limit calculation can throw an uncaught `ArithmeticException` (or silently return an unbounded energy limit) - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
The CVE describes a division-by-zero in `tif_dirread.c` caused by an unchecked divisor derived from attacker-controlled/edge-case input. The analogous pattern in java-tron is `calculateGlobalEnergyLimit()` in `RepositoryImpl` (and its sibling implementations in `EnergyProcessor`/`ResourceProcessor`), which divide by `totalEnergyWeight` while only protecting the divisor with a Java `assert` statement — a statement that is a compiled-in no-op unless the JVM is launched with `-ea`. No `-ea` flag is present in the project's run scripts, so the guard never actually executes in production.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit()` computes the account's global energy limit like this: [1](#0-0) 

```
long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();
assert totalEnergyWeight > 0;
if (hardenResourceCalculation()) {
  return BigInteger.valueOf(energyWeight)
      .multiply(BigInteger.valueOf(totalEnergyLimit))
      .divide(BigInteger.valueOf(totalEnergyWeight))
      .longValueExact();
}
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
```

- The only sanity check on `totalEnergyWeight` is `assert totalEnergyWeight > 0;`. Java assertions are disabled by default (no `-ea` is set anywhere in the launch scripts found), so this check compiles to nothing at runtime.
- If `totalEnergyWeight` is `0`:
  - In the **hardened** path (`VMConfig.allowHardenResourceCalculation()` enabled), `BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException: BigInteger divide by zero`. This method is called directly from the TVM `Repository` used during contract execution (energy metering), so an uncaught exception here propagates out of the normal VM opcode/energy-accounting path.
  - In the **non-hardened** (legacy) path, the same zero divisor does **not** throw, but computes `(double) totalEnergyLimit / 0.0 == Infinity`, so `energyWeight * Infinity` overflows to `Long.MAX_VALUE` when cast back to `long` — silently granting an unbounded/incorrect energy limit instead of failing safely.
- The same unguarded pattern (`assert totalEnergyWeight > 0`) is duplicated in `EnergyProcessor.calculateGlobalEnergyLimit()`, though that copy has a partial mitigating check (`if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) return 0;`) that is only exercised when `allowNewReward()` is enabled: [2](#0-1) 
- `ResourceProcessor.calculateGlobalLimitV1()` performs the same unguarded `BigInteger` divide by `totalWeight`: [3](#0-2) 

`totalEnergyWeight` is the sum of all frozen-for-energy balances chain-wide (`getTotalEnergyWeight`). It is normally non-zero on an established chain, but the divide is exercised on every energy-consuming transaction path (TVM contract calls/deploys, `DelegateResourceActuator`, `UnDelegateResourceActuator`, and the read-only `Wallet.calcCanDelegatedEnergyMaxSize` RPC), so any situation that drives it to zero (private/test networks at genesis, or after mass un-freezing enabled by FreezeV2's flexible/immediate unfreeze semantics) turns this into a live, remotely triggerable defect rather than a theoretical one.

### Impact Explanation
- Hardened path: an uncaught `ArithmeticException` thrown deep inside TVM energy accounting during ordinary contract execution can abort processing of a transaction/block in an unexpected way, which — depending on whether the calling frame (`VMActuator`) catches only specific exception types — can produce inconsistent handling across nodes (a chain-split risk) or an unhandled exception that halts processing of that transaction/block.
- Non-hardened path: silently computing `Long.MAX_VALUE` as an energy limit is a logic bug that effectively grants unbounded energy to an account, which is a resource-accounting integrity violation (analogous to an "unbacked" resource grant).
- Both are reachable purely by a transaction/contract call that exercises energy calculation once `totalEnergyWeight` is zero — no privileged role is required to trigger the divide itself (only the network-wide state of `totalEnergyWeight` needs to be zero).

### Likelihood Explanation
Low-to-moderate on a mature mainnet (a large amount of TRX would already be frozen for energy, making `totalEnergyWeight == 0` unlikely), but plausible on private/consortium chains, freshly bootstrapped test networks, or transient states enabled by FreezeV2's unfreeze mechanics. The underlying code defect — relying on a no-op `assert` as the only safety check before a division — exists unconditionally in production builds since assertions are not enabled.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` guards in `RepositoryImpl.calculateGlobalEnergyLimit`, `EnergyProcessor.calculateGlobalEnergyLimit`, and `ResourceProcessor.calculateGlobalLimitV1` with explicit runtime checks (`if (totalEnergyWeight <= 0) { return 0; }` or throw a handled exception) that execute regardless of JVM assertion settings, mirroring the equivalent bandwidth-side guards where present. Apply the same audit to any other `assert <denominator> > 0` patterns preceding integer/BigInteger division in the resource/energy code.

### Proof of Concept
1. Deploy/operate a java-tron network (or reach a state) where `DynamicPropertiesStore.getTotalEnergyWeight()` is `0` (e.g., fresh private chain before any account freezes energy, or after all previously frozen-for-energy balances are unfrozen).
2. Enable `allowHardenResourceCalculation` (hardened resource math), or use the non-hardened default.
3. Submit any TVM-triggering transaction (contract deployment/trigger) or call `Wallet.calcCanDelegatedEnergyMaxSize`/`DelegateResourceActuator` for an account with `getAllFrozenBalanceForEnergy() >= TRX_PRECISION`.
4. Observe:
   - Hardened path: `BigInteger.divide` throws `ArithmeticException: BigInteger divide by zero` inside energy-limit calculation.
   - Non-hardened path: the computed energy limit silently becomes `Long.MAX_VALUE` due to `double` division by zero producing `Infinity`.
