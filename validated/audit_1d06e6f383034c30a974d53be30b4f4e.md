### Title
Gas-key nonce watermark can be lowered below an already-consumed value via DeleteKey+AddKey in the same block, enabling exact transaction replay - ([File: runtime/runtime/src/access_keys.rs])

### Finding Description
`add_gas_key` reseeds every nonce row for a newly (re)created gas key to `initial_nonce_value(block_height) = (block_height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, unconditionally, with no knowledge of what nonce value was previously consumed at that index under a prior instance of the same public key. [1](#0-0) 

Gas-key nonce validation (both the regular gas-key path in `verify_and_charge_gas_key_tx_ephemeral`/`lib.rs` and the meta-transaction path `validate_delegate_action_key`) only checks the transaction/delegate nonce against the *currently stored* per-index nonce row and an upper bound `block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` computed from the *current* block: [2](#0-1) 

Because the reseed value only depends on the block height of the `AddKey` action and not on the prior high-water mark, the following sequence, all landing in the **same block** N, breaks monotonicity:
1. A `GasKeyNonce` transaction (nonce_index 0) with `nonce = X` close to the current upper bound `N*MULTIPLIER - 1` is applied, advancing nonce-row 0 to `X`.
2. `DeleteKey(K)` removes the access key and all nonce rows (`delete_gas_key`, `access_keys.rs:93-134`).
3. `AddKey(K, GasKeyFullAccess/...)` re-adds the same public key; `add_gas_key` reseeds nonce-row 0 to `(N-1)*MULTIPLIER`, which is strictly less than `X` (since `X` was chosen close to `N*MULTIPLIER-1`).

After this sequence, the stored nonce for index 0 is *lower* than a nonce that was already consumed by a previously-signed, previously-broadcast transaction from the same key (same public key, since it's re-added, not rotated). That old signed transaction (nonce=X, nonce_index=0) can be resubmitted: `X > (N-1)*MULTIPLIER` satisfies the monotonic check, and `X < P*MULTIPLIER` for any later block `P >= N` trivially satisfies the upper-bound check. No existing mechanism (nonce check, `UniqueChunkTransactions` per-chunk dedup, or `transaction_validity_period`) prevents this: the per-chunk dedup only rejects an identical tx hash within the *same* chunk, and `transaction_validity_period`/`block_hash` expiration bounds only how *old* a tx's reference block may be — it does not track whether a specific nonce value was already consumed. [3](#0-2) [4](#0-3) 

The attack requires the "high nonce" transaction and the `DeleteKey`+`AddKey` pair (signed by a full-access key on the same account) to be included in the *same* block height, which is required arithmetically (`M <= N`, and causal ordering forces `M = N`). This is not deterministic to arrange (block/chunk assembly and transaction ordering across different signing keys are not attacker-controlled), but it is not prevented by any protocol check either — an attacker fully controls timing/retries of their own transactions and can repeat the attempt until all three land together.

### Impact Explanation
This is a replay/double-spend of a specific signed transaction: the same `GasKeyNonce` transaction (same signature, same receipt-producing actions) can be applied twice against the same account/key. Depending on what the original transaction did (e.g., a `FunctionCall` withdrawing from an external contract, transferring tokens, or claiming a one-time reward via the gas key), this doubles the on-chain side effects of a single signed authorization — a core violation of the nonce-based replay-protection invariant (`NearBounty` category: double-spend/replay). Note that after the key is deleted and recreated, its `GasKeyInfo.balance` starts at 0 (verified `AddKeyAction` gas keys must have `balance == 0`, enforced in `validate_add_key_action` — `AddGasKeyWithNonZeroBalance`), so directly re-draining the *same* prepaid gas balance requires the attacker to also re-fund the new key via `TransferToGasKey`; the more general and reliably reachable impact is the replay of the transaction's receipt-producing actions themselves (a broken nonce-uniqueness guarantee), not necessarily a free-money creation bug. [5](#0-4) 

### Likelihood Explanation
Preconditions are fully within an unprivileged attacker's control: they need only their own account with a gas key (`num_nonces >= 2` is not actually required — even a single-index gas key reproduces the issue) and a full-access key to issue `DeleteKey`/`AddKey`. The hard part is getting all three actions (the high-nonce `GasKeyNonce` tx, `DeleteKey`, `AddKey`) into the exact same block/chunk, since block assembly ordering across independently-signed transactions is not controlled by the sender. This makes the attack probabilistic/repeatable rather than deterministic — the attacker can retry indefinitely at negligible cost until the timing aligns, but cannot guarantee success on a given attempt.

### Recommendation
When reseeding gas-key nonce rows in `add_gas_key`, do not use a value that depends only on `block_height`; either (a) prevent `AddKey` from reusing a public key that has ever existed on the account (track a "used public keys" set, at least for gas keys), or (b) make `initial_nonce_value` monotonically strictly greater than any nonce value the public key could have reached in this or an earlier block for this account — e.g., seed to `max((block_height-1)*MULTIPLIER, previous_high_water_mark + 1)` per index if such history could be recovered, or simply disallow deleting and re-adding the exact same public key within the same block (reject `AddKey` if the same public key appears in an already-applied `DeleteKey` earlier in the same receipt/block for that account).

### Proof of Concept
Runtime unit test plan in `runtime/runtime/src/access_keys.rs` (using existing helpers `create_apply_state`, `add_gas_key_to_account`, `get_gas_key_nonce`, `action_delete_key`, `action_add_key`):
1. At `block_height = N`, add a gas key `K` with `num_nonces = 2` via `action_add_key` (confirm nonce rows seeded to `(N-1)*MULTIPLIER`).
2. Directly call `set_gas_key_nonce(state_update, account_id, K, 0, N*MULTIPLIER - 1)` to simulate a `GasKeyNonce` transaction consuming index 0 at value `X = N*MULTIPLIER - 1` within block N (or drive it through `verify_and_charge_gas_key_tx_ephemeral`/`lib.rs` transaction-application path for a fuller integration test).
3. In the same `apply_state` (`block_height = N`), call `action_delete_key` for `K`, then `action_add_key` re-adding `K` as a fresh `GasKeyFullAccess` key.
4. Assert: `get_gas_key_nonce(state_update, account_id, K, 0) == (N-1)*MULTIPLIER`, which is `< X`.
5. Simulate replay: verify that a nonce value `X` (already used) again satisfies `X > (N-1)*MULTIPLIER` (monotonic check) and `X < N*MULTIPLIER` (upper-bound check) — i.e., call the nonce-check logic in `verify_and_charge_gas_key_tx_ephemeral` (or `validate_delegate_action_key`'s equivalent block for a `DelegateAction`) with `current_nonce = (N-1)*MULTIPLIER` and `tx_nonce = X`, and assert it returns `Ok` rather than `InvalidNonce`.

    let nonce = initial_nonce_value(block_height);
