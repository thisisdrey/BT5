Note: `ExchangeInjectContract` requires `!accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())` to throw — i.e. only the exchange creator can inject [1](#0-0) . This restricts inject to a privileged actor (the exchange creator), which falls outside the "unprivileged transaction broadcaster" scope the rules require, so it cannot be used to build a valid theft analog against an arbitrary victim.

The `ExchangeTransactionContract` path, by contrast, is reachable by any unprivileged account and does contain the reachable analog:

### Title
Exchange pool ratio can be sandwiched due to TOCTOU between `validate()` and `execute()` slippage check - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java)

### Summary
`ExchangeTransactionContract` lets any account swap tokens through a Bancor-style pool held in `ExchangeCapsule`. The only slippage protection is the `expected` field, checked against `exchangeCapsule.transaction(...)` inside `doValidate()` [2](#0-1) . `execute()` re-invokes `exchangeCapsule.transaction(...)` separately against the *current* on-chain state at execution time [3](#0-2) , not against the balances validated moments earlier. Because Tron block producers order transactions and a single block can contain multiple transactions touching the same `ExchangeCapsule`, an attacker can place a swap immediately before the victim's transaction (shifting `firstTokenBalance`/`secondTokenBalance`) and another swap immediately after (reverting the pool), extracting value from the victim's trade while the victim's `expected` bound - computed off a stale mental model of pool state - still nominally passes validation because validation is re-run against the *already-manipulated* state by the time it executes in the same block.

### Finding Description
The pool state (`firstTokenBalance`, `secondTokenBalance`) is a single shared mutable capsule keyed by `exchange_id`, exactly analogous to a vault's shared pricePerShare state in the ERC4626 report. `ExchangeCapsule.transaction()` computes output purely from current balances via the Bancor formula in `ExchangeProcessor`/`SafeExchangeProcessor` [4](#0-3) . A victim signs a transaction with a fixed `quant` and `expected` based on the pool ratio observed when they built the transaction, but the actual ratio used to compute their `anotherTokenQuant` is whatever the pool holds at the moment their transaction actually executes on-chain — which an attacker (or the block-producing witness itself) can shift by inserting swaps immediately before/after within the same block, since there is no commit-reveal, oracle, or TWAP protection and `expected` is just a minimum-output check, not a maximum-price/ratio bound tied to a specific pool state snapshot.

### Impact Explanation
An attacker who can order transactions within a block (including any user racing the mempool, or a witness constructing the block) can sandwich a victim's exchange swap: push the price against the victim before their trade executes, then reverse it after, extracting the price impact as profit from the victim's principal. This is a concrete theft-of-funds vector reachable by any unprivileged account issuing an `ExchangeTransactionContract`.

### Likelihood Explanation
Low-to-Medium. It requires (a) an exchange pool with shallow liquidity so the price impact is meaningful, and (b) the attacker to control ordering within the block (multiple transactions in the same block, or witness-level control), which is a general sandwich/front-run risk common to all constant-product/Bancor style AMMs, not specific to a broken accounting bug — TRON's Exchange feature is largely deprecated in favor of DEX-on-TVM in current mainnet usage, reducing real-world exposure.

### Recommendation
Add explicit pool-state binding to swap transactions (e.g., an optional expected pool ratio or block-height bound), and/or rely on TVM-based DEX contracts with proper minimum-output and deadline checks rather than the native Exchange actuators for any economically significant liquidity. Consider requiring `expected` to be computed and enforced against a ratio bound tighter than a bare minimum-output threshold, or introduce per-block price-impact limits on the native exchange.

### Proof of Concept
Not concretely demonstrable from static analysis alone — reproducing the sandwich requires controlling transaction ordering within a block (e.g., running a local node/testnet, submitting Swap A → Victim Swap → Swap B in the same block) which is outside what can be verified via code review; the mechanism (shared mutable pool state, minimum-output-only slippage check, `execute()` recomputing against live state) is confirmed directly in the cited files.

      boolean hardenedCalc) throws ContractValidateException {

    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);

          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
