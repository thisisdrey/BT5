### Title
Outgoing StackerDBChunkInv reply advertises a chunk version before/independent of it being durably stored - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` patches the outgoing `StackerDBChunkInv` ack's `slot_version` for the pushed slot immediately after `validate_received_chunk` succeeds, and sends this ack back to the peer in the same call. The actual persistence of the chunk into `self.stackerdbs` (via the DB-layer `try_replace_chunk`) does not happen in this function at all — it is deferred to the relayer, which processes it later from the `chunks_to_store`/`StackerDBSyncResult::from_pushed_chunk` path. This creates a window where the node's own advertised inventory claims a chunk version it has not yet (and may never) actually stored.

### Finding Description
`validate_received_chunk` (`stackslib/src/net/stackerdb/mod.rs:649`) is a purely stateless/read-only check: chunk size, expected version bounds, signer lookup, and signature verification against `SlotMetadata`. It performs no write and gives no guarantee of a subsequent successful store.

In `handle_unsolicited_StackerDBPushChunk` (`stackslib/src/net/stackerdb/mod.rs:742`), the `StackerDBChunkInv` branch (`mod.rs:768`) calls `validate_received_chunk` (`mod.rs:785`) and, on success, unconditionally patches the outgoing inventory:
```
*slot_version = chunk_data.chunk_data.slot_version;  // mod.rs:807
```
It then wakes the sync state machine (`mod.rs:810`) and, if `send_reply` is true, immediately signs and sends this patched `StackerDBChunkInv` back to the sender (`mod.rs:863-869`) — all within the same function call. Nowhere in this function is `self.stackerdbs`'s slot store (`StackerDBTx`/`try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs`) invoked or its result checked. The function's own doc comment at `mod.rs:735-741` confirms this design: it only decides whether to *buffer* and/or *forward to the relayer*; actual storage happens downstream in the relay path (`stackslib/src/net/relay.rs`, via `StackerDBSyncResult::from_pushed_chunk` and `chunks_to_store`).

Thus the equality the question is checking — "version advertised in the node's own outgoing `StackerDBChunkInv` == version committed in local StackerDB storage" — does not hold at the time the ack is sent. The ack is derived solely from the stateless validation, not from a confirmed write. If the deferred store in the relayer later fails (DB I/O error, write-frequency/max-writes race, contention, or any other rejection at `try_replace_chunk`), the node has already told the sending peer (and, via subsequent inventory gossip, other peers) that it possesses a chunk version it does not actually have.

### Impact Explanation
This is a state-divergence / phantom-advertisement bug: a remote peer that legitimately holds a StackerDB slot and pushes a valid-but-later-unstorable chunk can cause the receiving node to report a false inventory entry. Other peers doing rarest-first/newest-first StackerDB sync scheduling will attempt to fetch that "advertised" version from this node, receive a NACK or stale data, and have to fall back — this degrades replication behavior and can be triggered repeatedly by any StackerDB slot owner (an "unprivileged" party who legitimately owns a slot in a StackerDB they're a signer for). This matches the "state divergence / phantom advertisement" category, though it stops short of Critical since it is a best-effort, non-consensus-critical, ephemeral replication layer (`StackerDBSet` explicitly makes no strong consistency guarantees per the module doc at `mod.rs:30-34`), and does not itself constitute unauthenticated write, forged/propagated consensus data, or a crash. Realistically this is a **High-at-most / likely lower severity design gap** in a best-effort, eventually-consistent system, not a critical breach.

### Likelihood Explanation
Triggering the base "ack precedes/doesn't confirm store" ordering requires no special privilege beyond already-required StackerDB slot ownership (to pass `validate_received_chunk`'s signature check) — the attacker's own valid write could hypothetically race with a benign local storage failure. However, forcing the actual downstream store to *fail* after `validate_received_chunk` succeeds requires an independent local fault (DB error, disk issue, or a race/second write) on the *victim* node — this is not something a remote, unprivileged attacker can reliably induce through the P2P protocol alone. The `expected_versions`, `max_writes`, and signature checks in `validate_received_chunk` prevent naive replay or forged-signature attempts from reaching this window at all.

### Recommendation
Restructure the flow so the ack inventory is only patched/sent after `try_replace_chunk` (or equivalent) confirms a successful, durable write — i.e., perform storage synchronously within `handle_unsolicited_StackerDBPushChunk` (or delay building/sending the ack until the relayer confirms storage), rather than deriving the ack purely from `validate_received_chunk`.

### Proof of Concept
Not verified end-to-end: while the code confirms `validate_received_chunk` is stateless and the ack is built/sent before any call into `self.stackerdbs`'s write path in this function, I was unable to fully trace the exact point in `stackslib/src/net/relay.rs` where `chunks_to_store` entries are drained and passed to `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs`) within the available iterations, so I cannot confirm whether relay-layer logic re-validates/re-broadcasts a corrected inventory after a failed store, which would mitigate long-term divergence even if the initial ack is optimistic. A reproducible test would live in `stackslib/src/net/tests/relay/nakamoto.rs` (which already references `handle_unsolicited_StackerDBPushChunk`): inject a `StackerDBPushChunkData` with a valid signature/version, mock/force `try_replace_chunk` to return a DB error on the subsequent relay-driven store, and assert that the `StackerDBChunkInv` sent in reply (`mod.rs:863`) does not report the new `slot_version` for that slot — this assertion would fail against current code, since the ack is unconditionally patched at `mod.rs:807` before storage occurs.
