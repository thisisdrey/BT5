### Title
Heap-buffer over-read via unvalidated attacker-controlled field offsets in `VerifyTransferProof.execute` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`VerifyTransferProof.execute()`, the TVM precompile backing the shielded-TRC20 `verifyTransferProof` opcode-style contract call, parses "unfixed field offsets" (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`) directly out of attacker-supplied calldata with `parseInt(data, 0/32/64)` and then uses them, offset by attacker-controlled amounts, as the base for a sequence of `System.arraycopy` reads (`spendOffset + 320*i + ...`, `spendAuthSigOffset + 64*i`, `receiveOffset + 288*i + ...`) with no bounds check against `data.length`. This mirrors the CVE-2020-35655 bug class: a decoder trusts internal offset/length fields inside the payload instead of validating them against the buffer's actual size, producing an out-of-bounds read.

### Finding Description
The function only validates the overall length of `data` against a small fixed set of allowed sizes and validates `spendCount`/`receiveCount` ranges (1–2), but never validates that `spendOffset`, `spendAuthSigOffset`, or `receiveOffset` — each a raw 32-byte-derived `int` parsed straight from the transaction's precompile input — fall within `[0, data.length)`, nor that `offset + 32 + fieldSize*count` stays within `data.length`: [1](#0-0) 

Only `data.length` itself is checked against a fixed allow-list (`{2080, 2368, 2464, 2752}`), which bounds nothing about `spendOffset`/`spendAuthSigOffset`/`receiveOffset`: [2](#0-1) 

The subsequent copy loops use the unvalidated offsets as the base index for `System.arraycopy` reads that can run past the end of `data`: [3](#0-2) 

Since Java `System.arraycopy` throws `ArrayIndexOutOfBoundsException` rather than performing a true native OOB read, the direct memory-safety impact (raw heap over-read as in the Pillow CVE) does not exist in this managed-runtime context — but the analogous bug class (untrusted internal offset/length fields used unchecked to index a buffer) is present and reachable. The immediate consequence is an uncaught runtime exception. The surrounding `try { ... } catch (Throwable any) { ... }` block does catch this exception: [4](#0-3) 

I was not able to fully confirm within the available context whether the catch block that wraps this specific code path (visible starting at line 1472 with a `try`) actually terminates before line 1531, or whether the exception handling for this particular precompile ultimately returns `Pair.of(true, DataWord.ZERO().getData())` on failure (as `VerifyMintProof` does) — the full extent of the `catch` clause for `VerifyTransferProof` beyond line 1560 was not retrieved. This matters for severity: if exceptions are caught and mapped to a "false" precompile result, impact is limited to wasted computation/energy already charged; if any exception propagates uncaught out of the precompile dispatch into the VM's opcode execution path, it could crash/halt node processing of the transaction rather than being converted into a normal reverted-execution result.

### Impact Explanation
At minimum this is a robustness/DoS-class issue in a message-call-reachable precompiled contract: any account can invoke this precompile from a smart contract call (a "shielded TRC20" style transfer verification call) with crafted offsets designed to trigger out-of-bounds array indices during proof-data parsing. If the resulting exception is not safely caught and converted to a `false` verification (unlike `VerifyMintProof`'s explicit `Pair.of(true, DataWord.ZERO()...)` fallback pattern), it could destabilize the transaction/block-processing pipeline. This does not appear to be an exploit path to forge signatures or fabricate shielded value (the offsets only affect where bytes are read from within the same request buffer, not what cryptographic checks are performed), so it does not reach the "theft/unbacked balance" tier unless a node-crash/halt is confirmed via the missing catch-scope information.

### Likelihood Explanation
High reachability: this precompile is invoked whenever a contract call executes an opcode/precompile address corresponding to `VerifyTransferProof`, meaning any unprivileged transaction broadcaster or contract deployer can trigger it directly with fully attacker-controlled `data`. Crafting an out-of-range offset value (e.g., a large `int` from `parseInt(data, 0)`) is trivial and does not require passing any prior validation beyond the coarse length check.

### Recommendation
Add explicit bounds validation immediately after parsing `spendOffset`, `spendAuthSigOffset`, and `receiveOffset`, rejecting the call (returning `Pair.of(true, DataWord.ZERO().getData())`) if any offset (or `offset + requiredSize*count`) falls outside `[0, data.length]`, mirroring the pattern already used for RLP decoding's `verifyLength` check in `framework/src/main/java/org/tron/core/capsule/utils/RLP.java` (`verifyLength(suppliedLength, availableLength)`): [5](#0-4) 
Additionally, confirm/ensure the `catch (Throwable ...)` surrounding this method fully encloses the offset-based copy loops and always returns a safe `Pair.of(true, DataWord.ZERO().getData())` result rather than letting any `ArrayIndexOutOfBoundsException` propagate out of the precompile dispatcher.

### Proof of Concept
1. Construct calldata of exactly one of the allowed sizes (e.g., 2080 bytes) so the top-level `SIZE` check passes.
2. Set the first 32-byte word (`spendOffset` field, parsed via `parseInt(data, 0)`) to a large value such as `data.length - 4` (still parses as a small positive `int` but leaves almost no room for the subsequent `320*i`-strided reads).
3. Set `spendCount`/`spendAuthSigCount`/`receiveCount` (read via `parseInt(data, spendOffset)`, etc.) to values in the accepted `1–2` range by placing the right bytes at the attacker-chosen offset location (which is itself within `data` since offsets aren't bounds-checked against remaining length for the *count* fields either, only for `TREE_WIDTH`).
4. Submit this data to the `VerifyTransferProof` precompile via a contract call; the loop `System.arraycopy(data, spendOffset + 320*i + ..., ...)` at [6](#0-5)  reads past `data.length`, throwing `ArrayIndexOutOfBoundsException` inside the precompile — behavior beyond that point (silently swallowed vs. propagated) requires confirmation against the full `catch` block, which extends beyond the retrieved source range.
