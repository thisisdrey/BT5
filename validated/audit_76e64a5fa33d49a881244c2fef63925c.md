### Title
Unvalidated `block_id` in `GetAttachmentsInvResponse` allows attachment-inventory poisoning - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_inventories` stores a peer's `GetAttachmentsInvResponse` under the request's key `(contract_id, pages, index_block_hash)` without ever checking that `response.block_id` matches the `index_block_hash` that was actually queried. A malicious outbound sync peer can return an inventory response tagged with any `block_id` it wants (or none checked at all), which is then blindly treated as valid data for the queried block context when `get_prioritized_attachments_requests` later reads the page bitmap to decide whether the peer "has" a given attachment.

### Finding Description
The request is built with a specific `index_block_hash` in its query string via `make_request_type` [4](#0-3) , and the response is decoded and stored keyed by `request.key()`, which embeds that same `index_block_hash` [5](#0-4) . Nowhere in `extend_with_inventories` is `response.block_id` read or compared to `request.index_block_hash`. The consumer, `get_prioritized_attachments_requests`, iterates `self.inventories` and destructures the key as `(contract_id, pages, _)`, discarding the `StacksBlockId` component entirely, then uses `response.pages` bitmaps to decide whether a peer "has" a given attachment for that context [6](#0-5) . Because the block hash is never round-tripped/verified against `response.block_id`, a malicious peer's page-bitmap claims for an entirely unrelated block context get accepted and used to gate whether the node will attempt to fetch/consider an attachment as present for the batch's actual `index_block_hash`.

### Impact Explanation
An attacker-controlled outbound sync peer can cause the requesting node to accept/reject attachment presence decisions based on forged page bitmaps that were never actually attested for the queried block. This can suppress legitimate attachment fetches (peer falsely reports "does not have" leading to `sources.is_empty()` and the attachment never being fetched from this peer) or lead the node to trust a peer's inventory claims for content tied to a different block context than intended. This matches "attachment/BNS data mismatch / inventory poisoning" (High) since it can steer which attachments are considered available/committed for a given block context without validating the claim is actually about that context.

### Likelihood Explanation
Precondition is simply being a reachable outbound sync peer serving `/v2/attachments/inv` responses to the victim node — no privileged role, secret, or special access is required; this is achievable by any peer the node syncs Atlas attachments with. The attack is trivially repeatable per request/response cycle.

### Recommendation
In `extend_with_inventories`, after `response.decode_atlas_attachments_inv_response()` succeeds, compare `response.block_id` to `request.index_block_hash` and discard (treat as failed/faulty) any response where they don't match, before inserting into `self.inventories`.

### Proof of Concept
Construct an `AttachmentsInventoryRequest` for `index_block_hash = A`; build a `BatchedRequestsResult` whose `succeeded` map contains that request paired with an HTTP response decoding to `GetAttachmentsInvResponse { block_id: B (≠ A), pages: [...] }`; call `AttachmentsBatchStateContext::extend_with_inventories`; then assert `context.inventories.get(&(contract_id, pages, A))` is `Some` and contains the `B`-tagged response — demonstrating the response was accepted under key `A` despite claiming block `B`, matching the exact mechanism at `stackslib/src/net/atlas/download.rs` lines 490-522.
