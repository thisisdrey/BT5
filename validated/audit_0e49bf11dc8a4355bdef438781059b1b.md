### Title
Stale `TrieKey::PromiseYieldReceipt`/timeout state surviving `remove_account` enables privileged-action replay against a recreated account - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (`core/store/src/utils/mod.rs:504-575`) only removes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData`, but never removes `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::PromiseYieldTimeout`, `TrieKey::YieldIdToDataId`/`DataIdToYieldId`, or postponed-receipt state associated with the deleted account. [1](#0-0)  Because a self-targeted `PromiseYield` receipt (`predecessor_id == receiver_id == A`) with a stored callback action list (e.g. `AddKey`/`DeleteKey`) is keyed only by `receiver_id`/`data_id` and is not tied to any account-existence check when written or read, this leftover entry can later be resumed against a *different* account that happens to be recreated under the same `account_id`, at which point `check_actor_permissions` grants full self-authorization because `predecessor_id == receiver_id` trivially satisfies `actor_id == account_id`. [2](#0-1) 

### Finding Description
The exploit path:
1. Attacker deploys a contract on account `A` (any account they legitimately control — including a long, dot-free top-level name that anyone can create without registrar permission per `action_create_account`, since `CreateAccountOnlyByRegistrar` only applies to short top-level names). [3](#0-2) 
2. The contract calls the yield-create host function to schedule a self-targeted callback receipt containing `AddKey`/`DeleteKey` actions (predecessor_id == receiver_id == `A`). This is written to state via `set_promise_yield_receipt`, keyed by `TrieKey::PromiseYieldReceipt{receiver_id: A, data_id}`, plus an entry in the timeout queue (`TrieKey::PromiseYieldTimeout`). [4](#0-3) [5](#0-4) 
3. Attacker submits `DeleteAccount` on `A`. `check_actor_permissions` allows this because `actor_id == account_id`. `action_delete_account` invokes `remove_account`, which deletes the `Account`/keys/code/data records but **not** the `PromiseYieldReceipt`/`PromiseYieldTimeout`/`PromiseYieldStatus`/yield-id-mapping records. [6](#0-5) 
4. A victim later creates a new account with the identical `account_id` (e.g. the same long top-level name, plausible since creation of such names is open to anyone and not tied to the previous owner).
5. When the yield later resumes — either via the timeout queue firing (`resolve_promise_yield_timeouts`, which checks `contains_key(&promise_yield_key)` and unconditionally forwards a `PromiseResume` if the entry still exists, `runtime/runtime/src/lib.rs:3009-3105`) or via an explicit resume triggered by data delivery — the runtime looks up `get_promise_yield_receipt(state_update, account_id, data_id)`, finds the stale entry still present, and executes it via `apply_action_receipt` against whatever account currently exists under `account_id`. [7](#0-6) 
6. Inside that stale receipt, the embedded `AddKey`/`DeleteKey` actions have `predecessor_id == receiver_id == A` baked in from creation time, so `check_actor_permissions` treats `actor_id == account_id` as trivially true and executes them — granting the attacker's chosen public key on the victim's newly created account, with no verification that the current owner ever authorized it. [2](#0-1) 

The root cause is a missing invariant: account deletion does not purge yield/postponed-receipt state addressed by `account_id`, and resumption logic re-executes such stale receipts with no re-validation that the executing account is the same logical entity that scheduled the callback. `check_actor_permissions`'s `predecessor_id == receiver_id` shortcut assumes the receipt's identity binding remains valid for the lifetime of the receipt, which `remove_account` breaks.

### Impact Explanation
This is an authorization escalation across accounts (NEAR bounty category: authorization/privilege escalation): an unprivileged attacker can plant a dormant privileged callback that executes `AddKey`/`DeleteKey`/`DeployContract`/`Stake` against a completely different party's account once that account name is reused, without the new owner's consent. This can lead to full account takeover (attacker adds a full-access key) or contract redeployment, i.e., theft of any funds/assets held by the new account.

### Likelihood Explanation
The attack is cheap and fully attacker-controlled up to the point of requiring a name to be reused by an unrelated party. Costs: gas for the yield-create call, `DeleteAccount`, and waiting/timeout-management. The primary constraint is finding/engineering a scenario where a third party recreates the exact same `account_id` before the attacker permanently loses access to trigger resumption (or before the timeout naturally consumes the stale receipt against the still-nonexistent account, which happens if the timeout fires while the account is absent — that path is not exploitable because `remove_promise_yield_receipt`+`remove_promise_yield_status` occur before `apply_action_receipt`, consuming the entry). Exploitability therefore concentrates on scenarios where (a) the attacker controls the resume timing relative to account recreation (e.g., very long configured yield timeout, or an explicit resume triggered right after detecting recreation), and (b) an account-naming scheme allows a third party to legitimately claim the same `account_id` after deletion (feasible for long dot-free top-level names, which anyone may create). This is a real, reachable state-hygiene defect regardless of how easily the "victim recreates same name" precondition is met in practice.

### Recommendation
In `remove_account` (`core/store/src/utils/mod.rs`), also enumerate and remove all `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, `TrieKey::DataIdToYieldId`, `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, and `TrieKey::PendingDataCount` entries keyed by the deleted `account_id`, and/or scrub matching entries from the `PromiseYieldTimeout` queue (or mark them tombstoned) at deletion time. As defense in depth, `apply_action_receipt`/resume handling should re-check that the receiver account existed continuously since the receipt's creation (e.g., via a creation-epoch/account-nonce binding) before honoring the `predecessor_id == receiver_id` self-authorization shortcut for administrative actions.

### Proof of Concept
Integration test plan (test-loop / runtime integration test):
1. Deploy a contract on account `A` that calls yield-create with a callback action receipt to itself containing `AddKey(attacker_pubkey, FullAccess)`.
2. Submit `DeleteAccount` for `A`; assert `remove_account` result and directly query the trie for `TrieKey::PromiseYieldReceipt{receiver_id: A, data_id}` — assert it is **absent** (this assertion currently fails, proving the bug).
3. Recreate account `A` (e.g., `CreateAccount` + `Transfer`) from a different signer ("victim").
4. Trigger resumption (advance blocks past `expires_at` to fire the timeout queue, or submit an explicit resume receipt with the known `data_id`).
5. Assert that the new account `A`'s access key list does **not** contain `attacker_pubkey` — i.e., no action is executed against the account unless explicitly authorized by its current owner. Currently this assertion fails, confirming the escalation.

        VersionedReceiptEnum::PromiseYield(action_receipt) => {
            assert!(action_receipt.input_data_ids().len() == 1);
            let key = TrieKey::PromiseYieldReceipt {
                receiver_id: receipt.receiver_id().clone(),
                data_id: action_receipt.input_data_ids()[0],
            };
            set(state_update, key, receipt);
        }
        _ => unreachable!("Expected PromiseYield receipt"),
    }

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
