Confirmed vulnerability. The extension point `AttachmentsBatchStateContext::extend_with_attachments` deserializes the peer's HTTP response and inserts `response.attachment` into `self.attachments` (a `HashSet<Attachment>`) with **no check** that the returned attachment's hash matches the `content_hash` of the originating `AttachmentRequest`: [1](#0-0) 

Then, in `AttachmentsDownloader::run`'s `Done` branch, every attachment drained from `context.attachments` is unconditionally passed to `network.atlasdb.insert_instantiated_attachment(&attachment)`, regardless of whether `find_all_attachment_instances(&attachment.hash())` returned any matching, solicited `AttachmentInstance`: [2](#0-1) 

There is no check like `if !attachments_instances.is_empty() { insert_instantiated_attachment(...) }` — the insert happens even when the returned `Vec` is empty, i.e. even when no `AttachmentInstance` in the whole AtlasDB (not just the current batch) matches the delivered content's hash.

### Title
Unsolicited attachment content from a queried peer is permanently persisted with `was_instantiated=1` regardless of matching a requested `content_hash` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
When the Atlas downloader fetches attachments from remote peers, `extend_with_attachments` blindly trusts and stores whatever `Attachment` body a peer returns in a `GetAttachmentResponse`, without verifying it corresponds to the `content_hash` of the `AttachmentRequest` that was sent. The `Done` handler in `AttachmentsDownloader::run` then unconditionally calls `insert_instantiated_attachment` for every such attachment, even when zero `AttachmentInstance` rows reference its hash.

### Finding Description
The invariant that should hold is: for every `Attachment` a node stores as instantiated (`was_instantiated=1`), there must exist at least one `AttachmentInstance.content_hash` that matches it (i.e., the node actually asked for that content, per a canonical `AttachmentInstance` derived from chain state / gossiped index). This invariant is broken because:

1. `extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`) iterates `results.succeeded`, decodes the HTTP body via `decode_atlas_get_attachment()`, and calls `self.attachments.insert(response.attachment)` without comparing `response.attachment.hash()` to `request.content_hash`.
2. In the `Done` branch of `AttachmentsDownloader::run` (`stackslib/src/net/atlas/download.rs:153-169`), the code drains `context.attachments` and, for each one, calls `network.atlasdb.find_all_attachment_instances(&attachment.hash())` followed unconditionally by `network.atlasdb.insert_instantiated_attachment(&attachment)` — there is no guard skipping the insert when `attachments_instances` is empty.

Consequently, a malicious peer that a node queries for an `AttachmentRequest` (any outbound peer selected via `get_outbound_sync_peers`/reliability reports — no privileged role required, just being reachable and responsive to the request) can return a well-formed `GetAttachmentResponse` whose `attachment` field is arbitrary attacker-chosen bytes unrelated to the requested `content_hash`. The Atlas layer will compute the attacker-controlled data's own hash, find no matching instances, and still write it into the AtlasDB `attachments` table as `was_instantiated=1`. Because attachment instantiated storage doesn't share the size/count caps that apply to "uninstantiated" attachments (per `db.rs` comments describing separate handling of queued/uninstantiated attachments), this becomes a vector for unbounded storage growth from unsolicited data.

### Impact Explanation
This allows an unprivileged remote peer selected as an outbound sync target to write arbitrary attacker-chosen bytes into a victim node's persistent AtlasDB, unauthenticated and without matching any legitimate `AttachmentInstance`. Repeated requests (the batch retry logic re-enqueues unresolved batches, and new batches are continually processed) allow unbounded accumulation of forged/instantiated attachment rows, consuming disk space indefinitely — an unauthenticated write to state with no bound on volume, matching the "unauthenticated/unauthorized write to state" Critical category.

### Likelihood Explanation
The attacker only needs to run a peer that the victim node includes among its outbound Atlas sync peers (obtained via `network.get_outbound_sync_peers()`), and respond to `GetAttachmentRequest`s with a valid HTTP-shaped `GetAttachmentResponse` containing arbitrary bytes instead of the requested content. No secrets, admin roles, or special peer relationships are required — this is standard peer-to-peer Atlas attachment sync behavior. The attack is trivially repeatable for as long as the peer remains in the node's peer set.

### Recommendation
In `extend_with_attachments`, after decoding the response, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; reject (and count as a failed/faulty request, bumping `report.bump_failed_requests()`) any mismatched response. Additionally, as defense in depth, in the `Done` handler skip `insert_instantiated_attachment` when `find_all_attachment_instances` returns an empty list, since an attachment with no matching instance should never be persisted as instantiated.

### Proof of Concept
Rust net test in `stackslib/src/net/atlas/tests.rs` (or a new test module):
1. Set up an `AttachmentsBatchStateContext` / `AttachmentsBatchStateMachine` with a batch tracking a known `content_hash` H1 (from a legitimate `AttachmentInstance`).
2. Simulate `extend_with_attachments` (or directly construct the `Done` state) by inserting into `context.attachments` an `Attachment` whose bytes hash to H2, where H2 was never in the batch's tracked content hashes and has no corresponding `AttachmentInstance` in `AtlasDB`.
3. Invoke `AttachmentsBatchStateMachine::try_proceed`'s `Done`-branch logic (i.e., run `AttachmentsDownloader::run` through completion of the `DownloadingAttachment` state).
4. Assert: `network.atlasdb.find_all_attachment_instances(&H2)` returns an empty `Vec`, yet a subsequent query on `AtlasDB.attachments` for hash H2 shows a row with `was_instantiated=1` — proving unsolicited attacker data was persisted as instantiated despite no matching `AttachmentInstance`.
