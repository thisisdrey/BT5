### Title
Division by zero in `RepositoryImpl.calculateGlobalEnergyLimit()` due to unenforced `assert` invariant on `totalEnergyWeight` - ([File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java])

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit()`, which is invoked on the TVM energy-accounting data path for every `TriggerSmartContract`/`CreateSmartContract` transaction, relies on a bare Java `assert` to guarantee `totalEnergyWeight > 0` before dividing by it, instead of an explicit runtime check. Since JVM assertions are disabled by default in production (`-ea` is not set), this "should never happen" invariant is never actually enforced, mirroring the root cause of CVE-2021-47363: an internal state value that a code owner assumed could not be zero is allowed to reach a data-path division without a real guard.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit()`: [1](#0-0) 

reads `totalEnergyWeight` from `DynamicPropertiesStore` and only guards it with `assert totalEnergyWeight > 0;` before performing `BigInteger.divide(totalEnergyWeight)` (harden path) or a double division (legacy path). Compare this to the two sibling implementations of the same formula that DO have a real runtime guard:

- `EnergyProcessor.calculateGlobalEnergyLimit()` in the chainbase module checks `if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) { return 0; }` before falling through to the same `assert`. [2](#0-1) 
- `BandwidthProcessor.calculateGlobalNetLimit()` explicitly adds `if (totalNetWeight == 0) { return 0; }` in addition to the `allowNewReward()` check. [3](#0-2) 
- The V2 variants (`calculateGlobalEnergyLimitV2`, `calculateGlobalNetLimitV2`) both check `if (totalEnergyWeight == 0) return 0;` / `if (totalNetWeight == 0) return 0;`. [4](#0-3) 

`RepositoryImpl.calculateGlobalEnergyLimit()` in the `actuator` module is missing this explicit zero-check entirely — it is the only one of the four analogous implementations that depends solely on the assert. `totalEnergyWeight` is not re-derived on demand; it is a running counter maintained incrementally via `addTotalEnergyWeight(delta)` calls scattered across `FreezeBalanceActuator`, `UnfreezeBalanceActuator`, `FreezeBalanceProcessor`/`UnfreezeBalanceProcessor` (native TVM contracts), and their V2 counterparts, each computing a delta from `frozenBalance / TRX_PRECISION` differences: [5](#0-4) 

Because it is accumulated across independent, integer-truncated per-account weight deltas from many concurrent freeze/unfreeze operations network-wide rather than recomputed from the full account set, this counter can reach exactly zero (or go negative) while a specific caller/creator account still has a locally recorded non-zero `FrozenForEnergy` balance — precisely the "stub state visible to the data path before the real state is established" pattern from the kernel bug, just materialized through cross-account accounting drift instead of a group replace race.

This method is reached from `VMActuator.getAccountEnergyLimitWithFloatRatio()` whenever the calling/creating account has any V1 frozen-for-energy balance: [6](#0-5) 
which itself is called for every constant/normal `TriggerSmartContract` and `CreateSmartContract` execution via `getAccountEnergyLimitWithFixRatio`/`getAccountEnergyLimitWithFloatRatio` in `VMActuator.call()`/`create()`, i.e. directly reachable by any unprivileged contract caller or deployer.

### Impact Explanation
When `hardenResourceCalculation()` is enabled (the hardened accounting path used going forward), `BigInteger.valueOf(totalEnergyLimit).divide(BigInteger.valueOf(0))` throws an uncaught `ArithmeticException` inside the TVM energy-computation call chain for a normal transaction, which is not caught anywhere in `VMActuator`/`RepositoryImpl`. This can abort processing of an otherwise valid `TriggerSmartContract`/`CreateSmartContract` transaction during block application, i.e., node crash/halt of the transaction-processing path reachable from unprivileged users, analogous to the kernel's data-path divide-by-zero crash. On the legacy (non-hardened) double-division path, division by zero silently yields `Infinity`/`NaN`, which truncates to `Long.MAX_VALUE`/`0` and corrupts the derived energy limit, producing an incorrect resource accounting result instead of a crash — still a correctness/DoS issue for consensus-critical resource metering.

### Likelihood Explanation
Triggering requires the globally tracked `totalEnergyWeight` counter (maintained via incremental deltas across many independent freeze/unfreeze operations) to reach zero or go out of sync with the sum of individual frozen-for-energy balances, while at least one account retains a non-zero recorded `FrozenForEnergy` balance and issues a `TriggerSmartContract`/`CreateSmartContract` transaction. This is not directly attacker-controllable in a single transaction and depends on chain-wide accounting state, so likelihood is lower than a directly-triggerable bug, but the missing explicit guard (present in every sibling implementation of the same formula) is a clear defense-in-depth regression versus the rest of the codebase, and the `assert` provides zero protection in a production JVM.

### Recommendation
Add an explicit `if (totalEnergyWeight <= 0) { return 0; }` (or equivalent) check in `RepositoryImpl.calculateGlobalEnergyLimit()` before the division, mirroring the guards already present in `EnergyProcessor.calculateGlobalEnergyLimit()`/`calculateGlobalEnergyLimitV2()` and `BandwidthProcessor.calculateGlobalNetLimit()`/`calculateGlobalNetLimitV2()`, and remove reliance on `assert` for any invariant that affects consensus-critical division operations.

### Proof of Concept
1. Deploy or trigger a smart contract from an account that has a non-zero `FrozenForEnergy` (V1 freeze model) balance, ensuring `VMConfig.allowTvmFreezeV2()` is not yet active for that call path (`totalBalanceForEnergyFreeze != 0` branch in `VMActuator.getAccountEnergyLimitWithFloatRatio`).
2. Drive the network-wide `DynamicPropertiesStore.totalEnergyWeight` counter to `0` through a sequence of Freeze/UnfreezeBalance(V1) operations across multiple accounts whose incremental `addTotalEnergyWeight(newWeight - oldWeight)` deltas sum to exactly (or below) zero, while the triggering account's own frozen balance remains non-zero.
3. Submit the `TriggerSmartContract`/`CreateSmartContract` transaction; with `allowHardenResourceCalculation()` enabled, `RepositoryImpl.calculateGlobalEnergyLimit()` executes `BigInteger.valueOf(totalEnergyLimit).divide(BigInteger.valueOf(0))`, throwing an uncaught `ArithmeticException` during transaction/block processing.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
