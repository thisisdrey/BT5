### Title
Optimistic "canonical address" deployment in `HistoryBlockHashUtil.deploy` silently upgrades a pre-funded EOA into a contract, mirroring the OmniX peer-assumption bug class - ([File: framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java])

### Summary
`HistoryBlockHashUtil.deploy` installs the TIP‑2935 `BlockHashHistory` contract at a hardcoded canonical address [1](#0-0) . Because this address is fixed and known in advance (like a CREATE2/cross-chain "peer" address), any unprivileged account holder can pre-fund it as a normal EOA before the proposal activates. When activation later runs, the code optimistically assumes that whatever sits at that canonical address is either nothing, a genuine collision, or a "common case" EOA that should be silently converted in place into the contract's account, clearing its delegated-resource state [2](#0-1) [3](#0-2) . This is the same class of bug as the OmniX report: code trusts that an address will resolve to the intended, cooperating counterpart (a deployed peer contract / a benign unused EOA) without validating that assumption, and mutates account state/ownership based on that optimistic belief.

### Finding Description
`deploy()` only skips the write if `CodeStore`/`ContractStore` already has an entry at `HISTORY_STORAGE_ADDRESS` [4](#0-3) . It does **not** check whether the existing `AccountCapsule` at that address is a user-controlled account with real ownership expectations (e.g., delegated/frozen resources it manages, or funds it is actively using). Instead, if an account already exists there, the code unconditionally calls `account.updateAccountType(Protocol.AccountType.Contract)` and `account.clearDelegatedResource()` before overwriting the store entry [3](#0-2) .

Because `HISTORY_STORAGE_ADDRESS` is a fixed, publicly known 21-byte address before the TIP-2935 proposal is even active, any unprivileged transaction broadcaster can transfer TRX to it (turning it into a normal `AccountType.Normal` account with a balance and potentially with delegated resources acquired from other users, per the `DelegateResourceActuator` flow which requires the receiver to already exist as an account [5](#0-4) ). This mirrors the exact "optimistic peer assumption" pattern in the OmniX report: the destination address is not validated to actually be the intended contract-controlling entity, only that it is empty of contract code — so whatever pre-existing account/resource state a third party has built up at that address is silently repurposed (type flipped to Contract, delegated resources cleared) the moment the proposal activates, with no recourse for the account holder.

The code's own comments acknowledge this is the intended, expected common case ("A pre-existing non-contract account at the address is the common case (anyone can transfer TRX there to activate it as an EOA)") and treat it as equivalent to the CREATE2-collision branch — but a CREATE2 collision is deterministic per contract-deploy code, whereas here *any* end user's TRX transfer unconditionally establishes state at the canonical address, and the eventual maintenance-time conversion is asymmetric: the account's ownership semantics change (Normal → Contract) and any `delegatedResource` bookkeeping is wiped, without notifying or compensating the account holder or any counterparties who had delegated resources to that address.

### Impact Explanation
Once activated, the account at `HISTORY_STORAGE_ADDRESS` is forcibly converted to type `Contract` and its delegated-resource accounting is cleared (`clearDelegatedResource()`), while balance/asset amounts are preserved per the comment. Any resource-delegation relationships pointing at that address (from `DelegateResourceActuator`, which validates receiver existence but not receiver "intent" [6](#0-5) ) become orphaned bookkeeping (`DelegatedResourceStore`/`DelegatedResourceAccountIndexStore` entries not cleared in this flow), potentially leaving delegators unable to reconcile/undelegate correctly, and the account owner loses normal-account semantics (e.g., can no longer be a `TransferContract`/`VoteWitnessContract` participant as before) without consent. This is a one-time, network-wide (all full nodes) state mutation triggered by governance activation of a proposal, but the *precondition* — an ordinary user funding the canonical address — is reachable by any unprivileged TRX-transfer transaction broadcaster before that activation, exactly matching the "single signed transaction" reachability bar.

### Likelihood Explanation
Low-to-Medium likelihood: exploitation/collateral damage requires (a) TIP-2935 activation being a known, upcoming, deterministic address, and (b) a user (attacker or unaware party) sending TRX or delegating resources to `HISTORY_STORAGE_ADDRESS` before activation. Because the address is publicly hardcoded in source, a malicious actor could deliberately pre-fund it and delegate resources to it purely to have those resources cleared/frozen state altered at activation time, or an innocent user could stumble into this address. This matches the "high impact, low likelihood" profile called out in the original OmniX report.

### Recommendation
Before converting a pre-existing account at `HISTORY_STORAGE_ADDRESS` into a contract, explicitly validate that the account has no active delegated-resource relationships, no votes, and ideally no non-system-created state, and refuse (or safely settle) the conversion rather than unconditionally calling `clearDelegatedResource()`. Alternatively, reject/quarantine any account that already holds delegated resources or other stateful relationships at that address, and require explicit remediation instead of silently overwriting account-type semantics — following the recommended fix pattern from the reference report: fail closed on unverified/optimistic assumptions about what already occupies a "known" address, rather than proceeding with an implicit trust that whatever is there is safe to repurpose.

### Proof of Concept
1. Prior to the TIP-2935 proposal being activated (`saveAllowTvmPrague(1)` / `saveBlockHashHistoryInstalled`), an attacker broadcasts a `TransferContract` sending TRX to `HISTORY_STORAGE_ADDRESS` (`410000f90827f1c53a10cb7a02335b175320002935`), which is public in source. `TransferActuator.execute` creates a normal `AccountCapsule` there because it does not yet exist [7](#0-6) .
2. The attacker (or a third party) then issues a `DelegateResourceContract` transaction with `receiverAddress` = `HISTORY_STORAGE_ADDRESS`; validation succeeds because the account now exists and is `AccountType.Normal` [5](#0-4) , establishing delegated-resource bookkeeping pointing at that address.
3. When the TIP-2935 proposal activates at a later maintenance cycle, `HistoryBlockHashUtil.deploy(manager)` runs, sees the pre-existing account, and unconditionally executes `account.updateAccountType(Protocol.AccountType.Contract); account.clearDelegatedResource();` [8](#0-7) , wiping the delegated-resource accounting on that account and converting its type without any check of the delegation relationships previously established, leaving the delegator's `DelegatedResourceStore`/index entries orphaned relative to a receiver whose type/semantics just changed underneath them.

**Uncertainty note:** I was unable to fully trace whether `DelegatedResourceStore`/`DelegatedResourceAccountIndexStore` entries pointing at `HISTORY_STORAGE_ADDRESS` are cleaned up elsewhere (e.g., during maintenance) before or after `HistoryBlockHashUtil.deploy` runs, which would materially affect whether resources become truly stuck/unrecoverable versus merely inconsistent. This would require deeper tracing of `Manager.processBlock`/`ProposalService` ordering relative to `MaintenanceManager`, which I could not fully verify within the available index.
