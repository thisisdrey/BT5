### Title
Stale `PromiseYield` actions execute against a recreated account after `DeleteAccountAction`, allowing cross-account authorization escalation - (File: `runtime/runtime/src/lib.rs`)

### Summary
`promise_yield_create` parks an action receipt keyed only by `TrieKey::PromiseYieldReceipt{receiver_id, data_id}` and a `TrieKey::PromiseYieldTimeout` entry keyed only by index, both scoped by the plain `AccountId` string. `remove_account` (used by `action_delete_account`) never removes these two trie keys, so if the same account is deleted and later recreated (by anyone), the timeout mechanism will resurrect and execute the attacker's stale actions — including `AddKeyAction{FullAccess}` — against the new, unrelated account.

### Finding Description
`promise_yield_create` (`runtime/near-vm-runner/src/logic/logic.rs:3660`) creates a `PromiseYield` action receipt via `ext.create_promise_yield_receipt` [1](#0-0) . The attacker can further append an `AddKeyAction{FullAccess}` to the same receipt index using the standard `promise_batch_action_add_key_with_full_access` host call (backed by `append_action_add_key_with_full_access` in `runtime/runtime/src/receipt_manager.rs`), since batch actions are appended by promise/receipt index rather than being restricted to `FunctionCall` only.

When the receipt is first processed, `set_promise_yield_receipt` stores the whole `Receipt` (including all its actions) under `TrieKey::PromiseYieldReceipt{receiver_id: A, data_id}` [2](#0-1) , and `enqueue_promise_yield_timeout` stores a `TrieKey::PromiseYieldTimeout{index}` entry `{account_id: A, data_id, expires_at}` [3](#0-2) .

If the attacker (from A, self-call so `predecessor_id == receiver_id == A`) then submits `DeleteAccountAction` on A, `action_delete_account` calls `remove_account`, which removes only `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` entries for A [4](#0-3) . It does **not** touch `TrieKey::PromiseYieldReceipt` or `TrieKey::PromiseYieldTimeout`, so the parked receipt and its timeout entry survive account deletion.

A third party can then recreate account A (fresh `CreateAccount`/implicit transfer), fund it, and set up their own keys — this is a completely independent account instance sharing only the string `AccountId`.

At `queue_entry.expires_at`, `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009`) checks only `state_update.contains_key(&promise_yield_key, ...)` — i.e., whether a `PromiseYieldReceipt` entry still exists for `(A, data_id)` — with no check that A is "the same" account that created it [5](#0-4) . It synthesizes a `PromiseResume{data: None}` with `predecessor_id == receiver_id == A` and forwards it. When processed, `process_receipt` retrieves the stale stored yield receipt and executes it via `apply_action_receipt` [6](#0-5) .

Inside `apply_action_receipt`, the receiver account is fetched fresh from current state (`get_account(state_update, account_id)`) [7](#0-6)  — this resolves to the newly recreated, unrelated account. `check_account_existence` (`runtime/runtime/src/actions.rs:787`) only requires the account to *exist*, which it now does [8](#0-7) . `check_actor_permissions` for `AddKey` requires `actor_id == account_id` [9](#0-8) ; `actor_id` is seeded from `receipt.predecessor_id()` of the *original* yield receipt, which is A (self-call), and `account_id` is also A (same string) — so this check passes despite the account being a completely different, unrelated entity. `action_add_key` then executes, granting the attacker's `FullAccess` key on the new account.

### Impact Explanation
This is an authorization escalation across accounts: an attacker who once controlled account name `A` can plant a delayed, unconditional `AddKeyAction{FullAccess}` that fires against whoever later reclaims the `A` account id, without their consent, granting the attacker full control (and therefore access to all funds) of that unrelated account. This falls under NEAR's "authorization escalation across accounts or promises" bounty category and enables theft of funds from any victim who reuses a previously-deleted account name within the timeout window.

### Likelihood Explanation
Preconditions are fully within attacker's control and require no special privilege: fund account A, deploy a contract, call `promise_yield_create` plus a batch `AddKeyAction`, then call `DeleteAccountAction` on A — all via ordinary signed transactions to a public RPC. The only external dependency is that a third party (victim) recreates the exact same account id A before `TEST_CONFIG_YIELD_TIMEOUT_LENGTH`/`yield_timeout_length_in_blocks` blocks elapse — plausible for popular/short/attractive account names, sub-accounts programmatically recreated by dApps, or accounts recycled by automated systems. The attack is fully repeatable (attacker can pre-seed many account names with pending yields before deleting them, waiting for any of them to be reused).

### Recommendation
When deleting an account, also purge any pending `PromiseYieldReceipt` entries and their corresponding `PromiseYieldTimeout` queue entries for that account (or mark them invalidated), so a resumed/timed-out yield can never execute against a differently-owned account that later reuses the same id. Alternatively, `resolve_promise_yield_timeouts` should validate that the account state has not been deleted/recreated since the yield was created (e.g., by binding the yield to an account "incarnation" identifier) before applying the yield's actions.

### Proof of Concept
Test-loop integration test modeled on `test-loop-tests/src/tests/yield_timeouts.rs`:
1. Deploy a contract on account A that in one call performs `promise_yield_create` (self-callback) and appends `promise_batch_action_add_key_with_full_access(promise_idx, attacker_pubkey)` to the same promise.
2. In a subsequent transaction (same or next block), submit `DeleteAccountAction` on A with a valid beneficiary.
3. Have a different signer recreate account A (e.g. `CreateAccountAction` + `Transfer` funding) before `yield_timeout_height()`.
4. Advance the chain to `yield_timeout_height()` and one block after, mirroring `test_yield_timeout_resume_receipt_has_receipt_to_tx` [10](#0-9) .
5. Assert that the recreated account A now has an access key equal to `attacker_pubkey` with `FullAccess` permission, proving the stale `AddKeyAction` executed against the new account instance.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

fn test_yield_timeout_resume_receipt_has_receipt_to_tx() {

        env.validator_runner().run_until_head_height(block_height);
    }

    let resume_receipt_ids = find_promise_resume_receipt_ids_from_latest_block(&env);
