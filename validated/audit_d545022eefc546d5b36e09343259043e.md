### Title
Stale `PromiseYieldReceipt`/`PromiseYieldTimeout` entries survive `remove_account`, allowing planted actions to fire against a re-created account of the same name - (File: `core/store/src/utils/mod.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`remove_account` in `core/store/src/utils/mod.rs` deletes the `Account`, `ContractCode`, access keys/gas-key nonces, and contract data for an account, but never touches `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`/`DataIdToYieldId`, or the shard-global `TrieKey::PromiseYieldTimeout` queue entries that reference that account. `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009`) later only checks `state_update.contains_key(&TrieKey::PromiseYieldReceipt{receiver_id, data_id})` (line 3051) to decide whether to resolve a timed-out yield — it has no way to distinguish "the same account incarnation that created the yield" from "a brand-new account that happens to have been created with the same name."

### Finding Description
- `enqueue_promise_yield_timeout` stores queue entries keyed purely by a monotonically increasing shard-global `index` (`TrieKey::PromiseYieldTimeout{index}`), containing `account_id`, `data_id`, and `expires_at` (`core/store/src/utils/mod.rs:182-198`). This queue is never touched by account deletion.
- `set_promise_yield_receipt` stores the pending action receipt under `TrieKey::PromiseYieldReceipt{receiver_id, data_id}` (`core/store/src/utils/mod.rs:200-212`), which lives in the account's own trie subtree keyed by account name.
- `remove_account` (`core/store/src/utils/mod.rs:505-575`) removes `Account`, `ContractCode`, access keys/gas keys, and `ContractData`, but has no logic that iterates or removes `PromiseYieldReceipt`, `PromiseYieldStatus`, or the yield-id mapping keys for the account being deleted. [1](#0-0) 
- When the account is later re-created (`CreateAccount`), only a fresh `Account` object is written; the orphaned `PromiseYieldReceipt` (and its underlying stored action list) remains untouched in the trie at the same key.
- `resolve_promise_yield_timeouts` walks the global timeout queue and, for each entry whose `expires_at <= block_height`, checks only `contains_key(PromiseYieldReceipt{account_id, data_id})` — it never checks whether the account is the same one that existed when the yield was created. [2](#0-1)  If the key still exists (because deletion never cleared it), a `PromiseResume` receipt is synthesized and routed to `queue_entry.account_id` — i.e., to whatever account currently occupies that name.
- Because the stored `PromiseYieldReceipt` is the actual `ActionReceipt` (with its action list fixed at `promise_yield_create` time), resuming it causes its actions (e.g., `AddKey`) to execute against whichever account now holds that name, without any check that this is the same "incarnation" of the account that authorized/created the yield.

### Impact Explanation
This is an authorization-escalation / persistent-account-takeover primitive: an attacker can plant `AddKey(attacker_pubkey, FullAccess)` (rather than the described `DeleteKey`, since `DeleteKey` requires a fixed public key argument chosen at creation time and thus cannot target keys not yet known to exist) inside a yield's action list, delete the account, and have a subsequent, unrelated owner of the same account name unknowingly receive an unauthorized full-access key when the timeout matures — repeatable for as many `promise_yield_create` calls as the attacker plants before deletion, and across as many delete/recreate cycles as timeouts remain outstanding. This falls under the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
Preconditions are all within reach of an unprivileged attacker: any account owner can call `promise_yield_create` against their own account (no special privilege needed), can subsequently call `DeleteAccount` on their own account, and account-name reuse is possible whenever a new claimant (a different party) registers the freed name afterward (e.g., through the `near` top-level registrar contract's permissionless `create_account` flow, or a reused sub-account name). The remaining uncertainty is precisely how the eventual owner of the freed name comes to exist without noticing/objecting to residual state — this requires either coincidence, a marketplace/regrant scenario, or a victim intentionally reusing a name they don't realize was previously used maliciously. This constrains real-world likelihood but does not eliminate the underlying protocol defect: the code paths themselves provide no account-incarnation check.

### Recommendation
- Extend `remove_account` to also enumerate and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` entries whose keys are prefixed by the deleted `account_id` (analogous to how it already iterates access keys and contract data by prefix).
- Alternatively/additionally, bind `PromiseYieldTimeout` queue entries (and the `PromiseYieldReceipt` they reference) to an account "incarnation" identifier (e.g., account creation nonce/height) so `resolve_promise_yield_timeouts` can detect and discard stale entries belonging to a since-deleted-and-recreated account instead of trusting bare key presence.

### Proof of Concept
Integration test plan (test-loop / runtime `apply` test, analogous to existing tests in `runtime/runtime/src/tests/apply.rs` and `test-loop-tests/src/tests/yield_timeouts.rs`):
1. Deploy a contract on account `A` with a full-access owner key; from `A`, call `promise_yield_create` targeting `A` itself with an action list `[AddKey(attacker_pubkey, FullAccess)]` and a short `timeout_length_in_blocks`.
2. Submit `DeleteAccount` for `A` in the same or a subsequent block, before the timeout fires.
3. Submit `CreateAccount` recreating account `A` with a fresh, different owner key (simulating a new/unrelated owner claiming the same name).
4. Advance blocks past the original timeout's `expires_at`.
5. Assert: (a) `resolve_promise_yield_timeouts` still finds `contains_key(PromiseYieldReceipt{A, data_id})` true and emits a `PromiseResume` receipt (via `processed_yield_timeouts`/`outgoing_receipts`); (b) after processing, the recreated account `A`'s access-key set now contains `attacker_pubkey` with `FullAccess`, despite the new owner never consenting; (c) repeat with a second staggered yield to confirm the queue re-fires per surviving `PromiseYieldReceipt` regardless of the intervening delete/recreate cycle.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
