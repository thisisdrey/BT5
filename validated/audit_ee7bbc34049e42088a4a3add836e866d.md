### Title
Attacker-controlled `CertVersion` field lets an unauthenticated peer select a different certificate parser than the one that verifies it - (File: `handshake/machine.go`)

### Summary
`Machine.validateCert` parses the peer-supplied certificate bytes using an attacker-controlled `payload.CertVersion` field, then only afterward checks the parsed result's *own* `Version()` for negotiation purposes. There is no check that the declared `CertVersion` used to select the parser (`cert.Recombine`) is the version the resulting object actually claims to be, nor that it matches what the CA/verifier subsequently treats it as. This mirrors the `LimitOrderRegistry::cancelOrder` pattern: a caller-supplied selector (`direction` in the original bug, `CertVersion` here) is used to pick which code path validates an object, while the object's real, authoritative property (`order.direction` there, the cert's true wire-format/semantics here) is only consulted afterward — after the selection has already taken effect.

### Finding Description
During the Noise handshake, before any CA-signed identity has been established, the responder (or initiator processing the reply) calls `processPayload` → `validateCert`: [1](#0-0) 

`payload.CertVersion` comes straight off the wire (`handshake/payload.go`'s `unmarshalPayloadDetails`, `fieldCertVersion`) and is fully attacker-controlled — it is sent by a peer who has not yet been authenticated by any CA: [2](#0-1) 

That attacker-chosen version is passed directly into `cert.Recombine`, which uses it as a `switch` to decide whether to unmarshal `payload.Cert` as a V1 protobuf-encoded certificate or a V2 ASN.1-encoded certificate: [3](#0-2) 

Only *after* the bytes have already been parsed under the attacker-chosen format does the code inspect `rc.Version()` (the version the parser itself decided to stamp on the object) to do "version negotiation": [4](#0-3) 

This is structurally identical to the original report's flaw: `cancelOrder` let the caller pick `direction`, used that untrusted value to compute `(lower, upper)` and pass the OTM check, and only used the *real* `order.direction` after the gating check had already succeeded. Here, `CertVersion` is the untrusted selector that determines *which parser/verification semantics* apply to the raw bytes, and the "real" state (what the resulting object's own fields say, and how `CAPool.verify`/`CheckCAConstraints` subsequently treats a V1 vs V2 structure) is only reconciled after the selection has already been made. Because V1 and V2 certificates use different serialization formats (protobuf vs ASN.1) and different constraint-checking code paths (`cert/cert_v1.go` vs `cert/cert_v2.go`, `CheckCAConstraints`), a mismatch between the declared `CertVersion` and the actual byte format is a parser/format-confusion primitive that is reachable by any unauthenticated network peer initiating or completing a handshake, i.e., exactly the "packet/header/ASN.1 parsing" + "certificate verification" surface called out as in-scope.

### Impact Explanation
If the two format parsers (protobuf V1 vs ASN.1 V2) do not agree on which fields are authoritative, an attacker can potentially cause:
- A parsed `Certificate` object whose `Version()`, `Networks()`, `Groups()`, or other fields do not correspond to what was actually signed by the CA, because the signature/constraint check in `CAPool.verify`/`CheckCAConstraints` is applied to the object as parsed under the attacker's chosen format, not necessarily the format the signature was computed over.
- Certificate verification bypass or downgrade: the "version negotiation" step at line 365-368 blindly trusts `rc.Version()` (derived from attacker-supplied `CertVersion` and the parser it selected) to switch `m.myVersion`, potentially forcing the responder onto a weaker cert version/curve without any correlation to what the CA actually authorized.
- At minimum, a parser-confusion/DoS surface reachable pre-authentication (before any cert is verified), since the format-selection happens before `CheckSignature`/`CAPool.verify` run.

This falls under "certificate verification bypass" per the validation criteria.

### Likelihood Explanation
This is reachable by any network attacker with no CA-signed certificate at all: `HandleIncoming` → `beginHandshake` → `Machine.ProcessPacket` → `processPayload` → `validateCert` is invoked on the very first inbound handshake packet from an unauthenticated peer, before `m.verifier(rc)` (the CA-pool check) is ever called: [5](#0-4) 

No prior trust relationship, cert, or index is required to reach `validateCert` — only a well-formed stage-1/stage-2 handshake payload with a spoofed `CertVersion` field.

### Recommendation
Do not let the wire-supplied `CertVersion` unilaterally select the parser used to interpret `payload.Cert` and then separately trust the parser's own `Version()` output for negotiation. Instead:
- Validate that `payload.CertVersion` is one of the versions this node is actually willing to accept per `subtypeInfos`/negotiated handshake subtype before calling `cert.Recombine`.
- After parsing, cross-check that `rc.Version()` equals the `CertVersion` that was used to select the parser (reject on mismatch) so the two can never diverge.
- Ensure `m.myVersion` is only updated to a version for which a local `Credential` exists (already partially done) and re-verify all downstream CA/constraint logic operates on the object under a single, consistently-determined version rather than one implied by attacker input.

### Proof of Concept
A concrete end-to-end exploit (bytes that cause a real signature/constraint bypass) could not be constructed/verified within the scope of this review — this requires deeper knowledge of exact V1 protobuf vs V2 ASN.1 field-tag overlap to know whether crafted bytes parse successfully under the "wrong" `CertVersion` while still passing `CheckSignature`. What is demonstrable from the code alone (and stated with that caveat) is the control-flow primitive itself:

1. Attacker (no CA cert) initiates a handshake stage-1 message with `Payload{Cert: <raw bytes>, CertVersion: <attacker choice>}` (`handshake/payload.go` `fieldCertVersion`, tag 8).
2. `Machine.processPayload` → `validateCert` is invoked with the attacker-supplied `payload.CertVersion`, unconditionally selecting the V1 or V2 unmarshaler via `cert.Recombine(cert.Version(payload.CertVersion), payload.Cert, ...)` (`cert/cert.go:140-148`) before any CA/signature check occurs.
3. Only the resulting object's self-reported `rc.Version()` — itself a function of the attacker-chosen parser — is used for subsequent "version negotiation" and is what gets compared against the local `myVersion`/credential set (`handshake/machine.go:364-369`), with no assertion that this matches the declared `CertVersion` used to select the parser in step 2.

This confirms the structural analog to the reported bug (an attacker-supplied selector parameter is trusted to gate/steer a security-relevant code path, and the authoritative value is only checked afterward), but full confirmation of an exploitable signature/constraint bypass would require constructing a byte string that is valid under both the V1 protobuf and V2 ASN.1 decoders with divergent semantic content, which was not verified here.

func (m *Machine) validateCert(payload Payload) error {
	cred := m.getCred(m.myVersion)
	if cred == nil {
		m.failed = true
		return fmt.Errorf("%w: %v", ErrNoCredential, m.myVersion)
	}
	rc, err := cert.Recombine(
		cert.Version(payload.CertVersion),
		payload.Cert,
		m.hs.PeerStatic(),
		cred.Cert.Curve(),
	)
	if err != nil {
		m.failed = true
		return fmt.Errorf("recombine cert: %w", err)
	}

func Recombine(v Version, rawCertBytes, publicKey []byte, curve Curve) (Certificate, error) {
	if publicKey == nil {
		return nil, ErrNoPeerStaticKey
	}

	if rawCertBytes == nil {
		return nil, ErrNoPayload
	}

	var c Certificate
	var err error

	switch v {
	// Implementations must ensure the result is a valid cert!
	case VersionPre1, Version1:
		c, err = unmarshalCertificateV1(rawCertBytes, publicKey)
	case Version2:
		c, err = unmarshalCertificateV2(rawCertBytes, publicKey, curve)
	default:
		return nil, ErrUnknownVersion
	}

	if err != nil {
		return nil, err
	}

	if c.Curve() != curve {
		return nil, fmt.Errorf("certificate curve %s does not match expected %s", c.Curve().String(), curve.String())
	}

	return c, nil
}
