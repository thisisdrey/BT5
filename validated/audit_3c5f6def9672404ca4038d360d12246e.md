### Title
Non-atomic replay-window check-then-update in `ConnectionState.Decrypt`/`VerifyRelay` allows duplicate acceptance of replayed packets - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the anti-replay bookkeeping into two separate, independently-locked operations: `window.Check()` and `window.Update()`, with the AEAD decrypt performed *between* them while the lock is released. Because the "has this nonce been seen" check and the "mark this nonce as seen" commit are not atomic, two packets carrying the same message counter processed concurrently (e.g. on separate worker queues) can both pass `Check`, both get decrypted, and both be delivered to the tun device before either one calls `Update`. This mirrors the reported class of bug: an internal accounting/state value (the replay window) falls out of sync with the real-world outcome (how many times a given ciphertext was actually accepted and injected), permitting a value (here, a packet) to be "spent" more than once.

### Finding Description
`Decrypt` acquires `decryptLock`, calls `cs.window.Check(l, messageCounter)`, releases the lock, performs `cs.dKey.DecryptDanger(...)` unlocked, then reacquires the lock only to call `cs.window.Update(l, messageCounter)`: [1](#0-0) 

The same pattern is used in `VerifyRelay`: [2](#0-1) 

`Bits.Check` only inspects the current state (does not mark anything), and `Bits.Update` is the sole mutator that records a counter as seen: [3](#0-2) [4](#0-3) 

Because `Check` and `Update` are guarded by separate, short-lived lock sections rather than one atomic critical section spanning the whole decrypt, two goroutines processing the same captured ciphertext (same `h.MessageCounter`) concurrently can:
1. Goroutine A: `Check` → not seen → proceed, unlock.
2. Goroutine B: `Check` → not seen (A hasn't called `Update` yet) → proceed, unlock.
3. Both A and B independently AEAD-decrypt the packet with `DecryptDanger` (an AEAD decrypt does not itself track nonce state — it's a pure per-call operation), succeed.
4. Both A and B call `Update`; only one will observe the "duplicate" branch and be discarded, but at that point both have already decrypted the plaintext and it's about to be forwarded to `handleOutsideMessagePacket`/tun write.

`readOutsidePackets` is invoked per received UDP datagram, with a `q int` queue index indicating this is dispatched across multiple reader/worker routines, giving an attacker who simply captures and rapidly re-sends (replays) a legitimate ciphertext packet a realistic window to land two copies on different queues at nearly the same time: [5](#0-4) [6](#0-5) 

This attack requires only capturing/replaying wire ciphertext already exchanged between two legitimate certificate holders — the attacker performing the replay does not need any CA-signed certificate of their own; they only need to be on-path or otherwise able to capture and resend UDP datagrams.

### Impact Explanation
A successful race delivers the same application-layer packet twice to the tun interface (or, for `VerifyRelay`, processes the same relay/control frame twice). This is a data-plane replay/duplication bypass of the anti-replay mechanism the `Bits` window and `ReplayWindow` constant are explicitly designed to prevent. Depending on payload semantics this can cause duplicate packet delivery, state confusion in higher-level protocols riding over the tunnel, or repeated triggering of one-shot control actions carried over `header.Control`/relay frames.

### Likelihood Explanation
The race window depends on scheduling and the AEAD decrypt duration between the unlocked `Check` and the relocked `Update`, and requires the attacker to get two copies of the same captured ciphertext processed on different worker goroutines/queues close in time. This is plausible but not trivially reliable — likelihood is moderate, contingent on network conditions and internal queue dispatch timing, similar to the "disputed/medium" characterization in the original report.

### Recommendation
Make replay-window "check" and "mark-as-seen" atomic with respect to a single message: hold `decryptLock` (or an equivalent per-connection lock) across the entire `Check` → `DecryptDanger` → `Update` sequence for a given `messageCounter`, or restructure `Bits` to expose a single `CheckAndReserve`-style call that atomically tests-and-marks the counter before decryption begins, rejecting decrypt attempts for a counter that is already reserved by an in-flight decrypt.

### Proof of Concept
1. Establish a tunnel between two nebula nodes so a `ConnectionState` exists with `window = NewBits(ReplayWindow)`.
2. Capture one legitimate encrypted `header.Message` UDP datagram sent from peer A to peer B (e.g., via network capture).
3. Rapidly resend (replay) two copies of the identical captured datagram to peer B's UDP socket, timed so they are picked up by two different `f.readers[q]`-associated worker paths in `readOutsidePackets` (nebula dispatches inbound UDP reads across multiple queues).
4. Observe via instrumentation/logging that both invocations pass `cs.window.Check` (added debug logging around `connection_state.go` lines 63-66) and both successfully call `DecryptDanger`, before `Update` finally rejects the second one — by which point both decrypted payloads have already been forwarded toward `handleOutsideMessagePacket`/tun write.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	if err != nil {
		return nil, err
	}

	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
