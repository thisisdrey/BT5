#No vulnerability found for this question.

The bug class described in the Sturdy report—hardcoded slippage tolerance in a vault's own swap logic causing funds to be permanently locked—does not have a valid analog in marginfi-v2's unprivileged-user paths. Key differences:

1. **Orders/limit-order execution uses user-configurable slippage, not hardcoded**: `Order.max_slippage` is set by the user at order placement, capped at `MAX_ORDER_SLIPPAGE` (~10%), and enforced during `end_execute_order`. This is exactly the "let users determine max slippage" mitigation the original report recommended. [1](#0-0) [2](#0-1) [3](#0-2) 

2. **Receivership liquidation has no in-program swap/slippage exposure at all**: the swap is performed by the liquidator externally within the same tx (e.g., via Jupiter), and if no profitable route exists, the liquidator simply doesn't execute — there's no vault-side hardcoded exchange logic that could freeze funds. [4](#0-3) 

3. **Integration withdraws (JupLend, Drift) don't perform AMM/curve swaps with fixed slippage bounds**: they compute exact redeemable amounts from on-chain exchange rates (e.g., `token_exchange_price`) rather than routing through a swap pool subject to hardcoded min-out logic. [5](#0-4) 

There is no code path in marginfi-v2 where the protocol itself performs a token swap (e.g., stETH->ETH via Curve) with a hardcoded slippage tolerance baked into program logic that could cause user funds to become permanently stuck. The closest constructs (`Order.max_slippage`, `MAX_ORDER_SLIPPAGE`) are precisely the user-controlled design the original report recommended as the fix, not the vulnerability itself.
