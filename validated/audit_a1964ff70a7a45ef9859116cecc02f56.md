### Title
Unbounded/duplicate `commit_ids` in `GetCommitMessages` (and sibling RPCs) enables low-cost DoS amplification - (File: `internal/gitaly/service/commit/commit_messages.go`)

### Summary
The `GetCommitMessages` RPC (and the structurally identical `GetCommitSignatures` / `ListCommitsByOid` RPCs) accepts a `repeated string commit_ids` field with no upper bound on its length and no de-duplication, then iterates over every entry doing a full catfile lookup and, in the case of `GetCommitMessages`, streaming the entire commit message back to the client for each entry. This mirrors the reported liquidity-proxy bug class: an unvalidated vector whose length/duplication is not accounted for anywhere in resource limiting, letting a single request multiply backend work almost arbitrarily.

### Finding Description
`validateGetCommitMessagesRequest` only validates the repository, never the `CommitIds` slice: [1](#0-0) 

`getAndStreamCommitMessages` then loops over every element of `request.GetCommitIds()` unconditionally, performing a `catfile.GetCommitMessage` call and an `io.Copy` of the full message for each one: [2](#0-1) 

The proto definition declares `commit_ids` as an arbitrary-length repeated field with no documented or enforced maximum: [3](#0-2) 

The same pattern (no length/duplicate check, one catfile round-trip per entry) exists in `GetCommitSignatures`: [4](#0-3) 

and in `ListCommitsByOid`, which even records a metric of the request size but still performs no rejection or capping: [5](#0-4) 

By contrast, other RPCs in the same codebase do bound similarly-shaped inputs, e.g. `SearchFilesByName` explicitly rejects filters exceeding `searchFilesFilterMaxLength`, showing that per-field size validation is an established, expected pattern that these commit RPCs are missing: [6](#0-5) 

Gitaly's documented backpressure mechanism only limits the number of concurrent in-flight RPCs per repository — it does not account for the cost of a single oversized/duplicated request: [7](#0-6) 

Because a single gRPC message can carry hundreds of thousands of duplicated or distinct `commit_ids`, one request can force Gitaly to perform an equally large number of object lookups (and for `GetCommitMessages`, message streaming), each of which is only "one request" from the concurrency limiter's point of view — exactly the disconnect between request cost and request count that the external report flags for `selected_source_types`.

### Impact Explanation
A single unprivileged, authenticated caller able to invoke `GetCommitMessages`/`GetCommitSignatures`/`ListCommitsByOid` (these are reachable via GitLab Rails/Workhorse on behalf of ordinary users, e.g. commit-listing or diff-rendering features that batch multiple commit IDs) can submit a request with an extremely long or heavily duplicated `commit_ids`/`oid` list. Each entry drives a separate catfile object lookup and, for `GetCommitMessages`, a full message stream, so the CPU/IO cost of processing one gRPC request scales linearly with an attacker-controlled, effectively unbounded count. Because Gitaly's concurrency limiter counts requests, not per-request cost, an attacker can consume disproportionate CPU/catfile-process resources per request slot, degrading service for other repository operations — a denial-of-service condition consistent with the reported bug class.

### Likelihood Explanation
Likelihood is high for any environment where these RPCs are reachable with attacker-influenced repeated fields, since gRPC message size limits alone permit tens of thousands of short strings (commit SHAs are only 40 hex characters) in a single request, and no server-side code rejects long or duplicate lists.

### Recommendation
- Enforce a maximum size on `commit_ids`/`oid` repeated fields in `GetCommitMessages`, `GetCommitSignatures`, and `ListCommitsByOid` (mirroring the existing `searchFilesFilterMaxLength`-style pattern), returning `InvalidArgument` when exceeded.
- Reject or de-duplicate repeated identical entries before processing.
- Factor the length of these repeated fields into any weight/cost accounting used for concurrency limiting so that oversized requests are throttled proportionally to their actual cost, not counted as a single unit of work.
- Add regression tests asserting that requests with excessive or duplicate `commit_ids`/`oid` entries are rejected.

### Proof of Concept
1. As an authenticated ordinary user with read access to a repository, call `CommitService.GetCommitMessages` with a `CommitIds` list containing the same valid commit SHA repeated N times (e.g. N = 500,000), all fitting under the gRPC max message size (40-byte SHAs × 500k ≈ 20MB, adjustable to stay under default limits, or split across many smaller requests in parallel).
2. Observe that `getAndStreamCommitMessages` performs N sequential `catfile.GetCommitMessage` calls and N full message streams: [8](#0-7) 
3. Repeat the request concurrently from multiple low-privilege sessions; because Gitaly's concurrency limiter only counts request slots and not the size of `CommitIds`, CPU and catfile-process load scale with attacker-chosen N per accepted request, degrading Gitaly's responsiveness for the repository/node.

func (s *server) getAndStreamCommitMessages(request *gitalypb.GetCommitMessagesRequest, stream gitalypb.CommitService_GetCommitMessagesServer) error {
	ctx := stream.Context()
	repo := s.localRepoFactory.Build(request.GetRepository())

	objectReader, cancel, err := s.catfileCache.ObjectReader(ctx, repo)
	if err != nil {
		return err
	}
	defer cancel()

	for _, commitID := range request.GetCommitIds() {
		msg, err := catfile.GetCommitMessage(ctx, objectReader, repo, git.Revision(commitID))
		if err != nil {
			return fmt.Errorf("failed to get commit message: %w", err)
		}
		msgReader := bytes.NewReader(msg)

		if err := stream.Send(&gitalypb.GetCommitMessagesResponse{CommitId: commitID}); err != nil {
			return err
		}
		sw := streamio.NewWriter(func(p []byte) error {
			return stream.Send(&gitalypb.GetCommitMessagesResponse{Message: p})
		})
		_, err = io.Copy(sw, msgReader)
		if err != nil {
			return fmt.Errorf("failed to send response: %w", err)
		}
	}
	return nil
}

// GetCommitMessagesRequest is the request for the GetCommitMessages RPC.
message GetCommitMessagesRequest {
  // repository is the repository to retrieve the commits from.
  Repository repository = 1 [(target_repository)=true];
  // commit_ids is the list of commitish object IDs for whom we want to retrieve
  // the commit message.
  repeated string commit_ids = 2;
}

// GetCommitMessagesResponse is the response for the GetCommitMessages RPC.
message GetCommitMessagesResponse {
  // commit_id is the commit object ID. A response with commit_id set, will be followed with
  // response with the message field set with the commit message for that commit.
  string commit_id = 1;
  // message is the commit message for the commit.
  bytes message = 2;
}

func (s *server) ListCommitsByOid(in *gitalypb.ListCommitsByOidRequest, stream gitalypb.CommitService_ListCommitsByOidServer) error {
	ctx := stream.Context()
	repository := in.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}
	repo := s.localRepoFactory.Build(repository)

	objectReader, cancel, err := s.catfileCache.ObjectReader(ctx, repo)
	if err != nil {
		return err
	}
	defer cancel()

	sender := chunk.New(&commitsByOidSender{stream: stream})
	listCommitsbyOidHistogram.Observe(float64(len(in.GetOid())))

	for _, oid := range in.GetOid() {
		commit, err := catfile.GetCommit(ctx, objectReader, git.Revision(oid))
		if errors.As(err, &catfile.NotFoundError{}) {
			continue
		}
		if err != nil {
			return err
		}

		if err := sender.Send(commit.GitCommit); err != nil {
			return err
		}
	}

	return sender.Flush()
