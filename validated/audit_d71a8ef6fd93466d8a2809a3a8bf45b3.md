## Title
Unbacked-balance / lost-funds risk from unchecked floating-point fixed-point-power calculation in TRX/token bancor-style exchange (`ExchangeProcessor`) - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
The Chainflip report fixes a class of bugs where a fixed-point "nth power" function used to price pool orders could overflow and panic (later hardened to return `None`/use a safe binary-search nth-root instead of unguarded floating-point power). java-tron has a structurally analogous fixed-point power calculation in its legacy bancor-style `Exchange*` actuators (`ExchangeTransactionActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`), reachable from an unprivileged, signed transaction (`ExchangeTransactionContract`).

### Finding Description
`ExchangeCapsule.transaction()` [1](#0-0)  selects between a "hardened" `SafeExchangeProcessor` (BigDecimal-based, checked) and the legacy `ExchangeProcessor`, which computes token-out amounts using raw `double` fixed-point exponentiation: [2](#0-1) 

`exchangeToSupply`/`exchangeFromSupply` compute `Math.pow(1 + quant/newBalance, 0.0005)` and `Math.pow(1 + supplyQuant/supply, 2000)` entirely in `double` arithmetic with no overflow/NaN/Infinity checks, then cast the result directly to `long` via `(long) issuedSupply` / `(long) exchangeBalance`. This is the same bug class as the Chainflip report: an unchecked fixed-point power/root computation used to price an order-book/pool trade. If the floating-point computation produces `NaN`, `Infinity`, or a value outside `long` range (e.g. when `newBalance` or `supply` is very small/near-zero relative to `quant`, or due to accumulated floating error across repeated `ExchangeInject`/`ExchangeWithdraw`/`ExchangeTransaction` calls that legitimately shrink pool balances toward extreme ratios), the `(long)` cast silently truncates: `NaN`→`0`, `+Infinity`→`Long.MAX_VALUE`, `-Infinity`→`Long.MIN_VALUE`. Unlike the hardened path (`SafeExchangeProcessor`, guarded by `addExact`/`longValueExact()` and `allowHarden()`), the legacy path performs none of Java's checked-arithmetic guards, so no `ArithmeticException` is ever thrown to abort the trade.

The repository's own hardening work (`SafeExchangeProcessor`, `allowHardenExchangeCalculation` dynamic property, and the “hardened” test suite for `ExchangeInjectActuator`/`ExchangeTransactionActuator`/`ExchangeCreateActuator`) confirms that this exact code path was previously recognized as an arithmetic-safety gap and only closed when the toggle is enabled — the legacy, un-hardened `ExchangeProcessor` remains reachable whenever `allowHardenExchangeCalculation` is off (the historical/default configuration on chains that haven't activated it).

### Impact Explanation
An attacker able to submit `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions against a bancor-style exchange pool they control (or any public pool) can drive the pool balances toward ratios that push the floating-point power computation into overflow/underflow territory. Because the result is cast straight to `long` without any bounds or overflow check on the legacy path, this can yield:
- Minting an unbacked, arbitrarily large token amount (`Infinity` → `Long.MAX_VALUE`), effectively creating value not backed by the pool's actual reserves (theft/unbacked balance), or
- Returning `0` (`NaN`) tokens for a real, debited sell amount, causing permanent loss of the trader's deposited funds.

Either outcome is a concrete violation of exchange pool solvency invariants enforced elsewhere via `addExact`/balance checks, since those checks only validate the *pool balance* bookkeeping (`newFirstTokenBalance`/`newSecondTokenBalance >= 0`), not the correctness of the computed trade amount itself.

### Likelihood Explanation
Likelihood is limited by two factors that keep this from Critical: (1) the network can enable `allowHardenExchangeCalculation`, routing all traffic through the safe `SafeExchangeProcessor` path, which appears to be the currently-tested/expected configuration; and (2) reaching the precise floating-point edge case requires driving pool balances to extreme, attacker-crafted ratios via multiple `ExchangeInject`/`ExchangeWithdraw`/`ExchangeTransaction` calls, which is feasible for an unprivileged asset issuer/order placer who creates their own exchange pool (`ExchangeCreateContract`) but requires careful precision engineering rather than a single trivial call.

### Recommendation
Deprecate/remove the legacy `ExchangeProcessor` double-based path entirely (making the `SafeExchangeProcessor`/hardened BigDecimal path the only implementation, independent of the `allowHardenExchangeCalculation` toggle), or at minimum add explicit `Double.isFinite()`/range checks and reject the transaction with `ContractValidateException`/`ArithmeticException` before casting to `long`, matching the pattern already used by `SafeExchangeProcessor.exchangeFromSupply` (`BigDecimal...longValueExact()`).

### Proof of Concept
Not independently reproducible from static analysis alone: exploiting this requires computing the exact `firstTokenBalance`/`secondTokenBalance`/`sellTokenQuant` inputs that push `Math.pow(1 + quant/newBalance, 0.0005)` or `Math.pow(1 + supplyQuant/supply, 2000)` into `NaN`/`Infinity`/out-of-`long`-range territory across a sequence of `ExchangeCreate` → `ExchangeInject`/`ExchangeWithdraw` → `ExchangeTransaction` calls, then verifying whether `allowHardenExchangeCalculation` is disabled on the target network. This is best validated with a live/test node (unit test driving `ExchangeProcessor.exchange()` directly with crafted extreme balances to observe the `(long)` cast produce `0` or `Long.MAX_VALUE`).   private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
