### Title
`need_unconfirmed_tenures` false-positive via `.any()`-over-peers logic treating "peer doesn't know about tenure" as "tenure is processed" - ([File: stackslib/src/net/download/nakamoto/download_state_machine.rs])

### Summary
`NakamotoDownloadStateMachine::need_unconfirmed_tenures` computes `is_available_and_processed` for each `WantedTenure` by taking `.any()` over *all* peers' `AvailableTenures` maps, treating a peer's *absence* of an entry for that tenure as an implicit vote of `true` (line 979: `else { true }`). Because this uses OR semantics across peers, a single peer that never returns a `TenureStartEnd` for a given tenure (e.g. it lacks the subsequent tenure-start/tenure-end inventory bits, or reports a sparse/empty inventory for that reward cycle) can override every other, fully-informed peer's honest `processed: false` vote and make the overall predicate `true`, even though the tenure was never actually downloaded or locally processed.

### Finding Description
`is_available_and_processed` is computed as: [1](#0-0) 

`tenure_start_end.processed` is derived purely from the local node's `WantedTenure.processed` flag (set only via `has_processed_nakamoto_tenure` against local chainstate, see `inner_update_processed_wanted_tenures`), so an attacker cannot forge that value directly. However, the presence/absence of the entry in a given peer's `AvailableTenures` map is fully attacker-controlled: `TenureStartEnd::from_inventory` only inserts an entry for `wt` if the peer's inventory bit vector has both the tenure-start bit set and sufficient subsequent bits to resolve a start/end block pair. [2](#0-1) 

`find_tenure_block_ids` inserts one `AvailableTenures` map per peer into the global `tenure_block_ids` map that `need_unconfirmed_tenures` later scans with `.any()`: [3](#0-2) 

Attack: an attacker-controlled peer (any unprivileged p2p peer that responds to `GetNakamotoInvData`) can send a `NakamotoTenureInv` for the relevant reward cycle that is missing the bits needed to resolve a `TenureStartEnd` for the targeted `wt` (e.g. it advertises only a subset of `wanted_tenures`, or all-false bits for that cycle segment while still claiming to have inventory for the cycle). This peer's entry in `tenure_block_ids` then simply omits that `wt`'s consensus hash. Because `is_available_and_processed` is an `.any()` over *all* peers (including this one), the missing-key branch (`else { true }`) alone makes the predicate `true` for that `wt`, regardless of what every other honest, fully-synced peer reports (`processed: false`).

Separately (and matching the exact scenario in the question) a peer can also advertise the tenure-start bit and get included in `self.available_tenures` (used for scheduling, built by `find_available_tenures`), causing a `NakamotoTenureDownloaderSet` to be scheduled against it. If that peer then NACKs or serves garbage, the downloader for that tenure eventually exhausts its neighbor list and is dropped from the schedule (`stackslib/src/net/download/nakamoto/tenure_downloader_set.rs` lines 376-423), making `self.tenure_downloads` empty. At that point, if any other peer (colluding or merely out-of-date) causes `is_available_and_processed` to read `true` via the `else { true }` branch, `run_downloads` transitions `Confirmed -> Unconfirmed`: [4](#0-3) 

The confirmed tenure for the targeted `wt` is never actually fetched, but the state machine believes it has satisfied all wanted tenures and moves on to unconfirmed-tenure fetching.

### Impact Explanation
The affected node incorrectly concludes a confirmed tenure is "available and processed" without ever completing a `NakamotoTenureDownloader` for it, and transitions its download state machine to `Unconfirmed` prematurely. Since Nakamoto chain processing requires tenures in causal order, the node cannot advance its local Stacks tip past the missing tenure; it will oscillate between `Confirmed`/`Unconfirmed` (per the `run_downloads` transition logic) without ever completing the falsely-claimed tenure, stalling the node behind the canonical tip. This matches the "steering a node off the tip via false inventory" High-severity category — it is a remotely triggerable availability/liveness degradation caused entirely by unauthenticated inventory-gossip content, not by any privileged action.

### Likelihood Explanation
The attacker needs only to run an ordinary, unprivileged p2p peer that responds to standard Nakamoto inventory-sync requests (`GetNakamotoInvData`/`NakamotoInvData`) with a crafted or simply sparse bit vector for the targeted reward cycle — no secret, signature forgery, or privileged role is required, and this is fully within the "own peer, gossip messages" threat model. The bug is triggered as soon as one such peer's `AvailableTenures` map (built via `TenureStartEnd::from_inventory`) lacks an entry for the targeted `WantedTenure`, which is trivially achievable (e.g., by never advertising the necessary trailing tenure-start/tenure-end bits, or by advertising an all-zero/partial inventory for the cycle). It is repeatable on every `run_downloads` cycle as long as such a peer remains connected and the victim retains it in `network.inv_state_nakamoto.inventories`.

### Recommendation
Do not let the absence of a tenure entry in an arbitrary single peer's map vote `true` for `is_available_and_processed`. Instead:
- Base "processed" purely on the locally-known `wt.processed` flag (already available as a parameter to `need_unconfirmed_tenures`), rather than deriving it indirectly from a `.any()` scan over peer maps whose only signal for a missing entry is a hard-coded `true`.
- If peer-availability information should still gate the decision, require it via `.all()`-style logic: only treat a tenure as "resolved" if either it is genuinely processed locally, or *no* peer in `tenure_block_ids` reports it as available/known at all (rather than any single peer's silence being sufficient).

### Proof of Concept
Rust test plan in `stackslib/src/net/tests/download/nakamoto.rs` (or a new unit test near `test_tenure_start_end_from_inventory`):
1. Build `wanted_tenures`/`prev_wanted_tenures` with `processed: false` for all entries.
2. Construct two synthetic `NakamotoTenureInv`s: peer A with a full/correct bit vector (so `TenureStartEnd::from_inventory` returns an entry for every `wt` with `processed: false`); peer B with a bit vector for the same reward cycle that omits the trailing bits needed to resolve one specific `wt` (so `from_inventory` returns a map lacking that `wt`'s key).
3. Call `NakamotoDownloadStateMachine::find_tenure_block_ids` with both peers' inventories to build `tenure_block_ids`, and `find_available_tenures`/`find_unconfirmed_tenure_ids` for `available_tenures`.
4. Call `NakamotoDownloadStateMachine::need_unconfirmed_tenures(...)` with these maps and assert it returns `true`, even though the targeted `wt.processed == false` for every peer that does report it, demonstrating the false positive at `download_state_machine.rs` lines 975-981.
