### Title
Unbounded attacker-controlled `onBehalfOf_`/`to_` writes let anyone fill a victim's 30-slot token list and permanently block them from new collateral positions — (File: contracts/DepositToken.sol)

### Summary
Analogous to GitPython's `--separate-git-dir` allowing a caller-supplied parameter to redirect writes outside the intended destination, `DepositToken.deposit(uint256, address onBehalfOf_)` and `DepositToken.transfer(to_)`/`transferFrom` let any unprivileged EOA write entries into *any* account's `depositTokensOfAccount` / `debtTokensOfAccount` enumerable sets in `Pool`. `Pool.addToDepositTokensOfAccount` enforces `MAX_TOKENS_PER_USER = 30` and reverts once the combined list length hits the cap (`UserReachedMaxTokens`), but there is no opt-in, minimum amount, or victim-consent check before a new entry is appended. An attacker can pre-fill a victim's list with dust positions for collateral types the victim never wanted, permanently DoS-ing the victim's ability to deposit new collateral or receive deposit tokens.

### Finding Description
The write path:

1. `DepositToken.deposit(amount_, onBehalfOf_)` is permissionless (`whenNotPaused nonReentrant onlyIfDepositTokenExists`), takes the underlying only from `_msgSender()`, and mints msdTokens to arbitrary `onBehalfOf_` — the beneficiary never opts in (contracts/DepositToken.sol:211-237).
2. `_mint` calls `pool.addToDepositTokensOfAccount(account_)` on first receipt (contracts/DepositToken.sol:486-488).
3. `Pool.addToDepositTokensOfAccount` appends the token to `depositTokensOfAccount[account_]` under `onlyIfAdditionWillNotReachMaxTokens`, which reverts `UserReachedMaxTokens` once `debt + deposit` entries reach `MAX_TOKENS_PER_USER = 30` (contracts/Pool.sol:143-148, 216-220).
4. The same write happens in `_transfer` for `transfer`/`transferFrom`/`seize` recipients (contracts/DepositToken.sol:517-520), so dust transfers also fill the victim's list — and `transferFrom` works through `Operator.execute` meta-sender paths too.
5. Critically, every later `_mint` and `_transfer` targeting the victim re-executes `addToDepositTokensOfAccount`, which reverts for any *new* token type once the cap is reached. The victim cannot remove entries cheaply: an entry is only removed when that token's balance returns to zero (`_burn`/`_transfer` out, contracts/DepositToken.sol:460-462, 523-525), and for tokens seeded by `deposit(onBehalfOf)`, the position counts toward `depositOf()` and may be partially locked by `_revertIfLocked` if the victim has debt.

The attacker pays only dust amounts of each underlying (deposit fee + min amount) for up to `MAX_TOKENS_PER_USER` distinct DepositTokens in the victim's pool. No governance, keeper, or privileged role is needed — `deposit` is a public entry point and also reachable via `Operator.execute` through `SynthContext._msgSender()`.

### Impact Explanation
Temporary-to-permanent freezing of the victim's position functionality. Once the victim's combined token list hits 30 attacker-chosen entries:

- The victim cannot deposit any new collateral type (`deposit` → `_mint` → `addToDepositTokensOfAccount` reverts), blocking them from adding collateral to improve an unhealthy position — which can indirectly cause loss of funds via liquidation they could have prevented.
- The victim cannot receive airdropped/transferred deposit tokens of new types (all `_transfer` to them reverts), and `Pool.liquidate` still works against them.
- Clearing a slot requires driving an attacker-seeded balance to zero; if the victim has outstanding debt, `unlockedBalanceOf` returns less than `balanceOf`, so `_revertIfLocked` blocks the exact transfer needed to evict the dust entry — the victim must first repay debt or wait for liquidation, extending the freeze.

This breaks the liveness invariant that a user can always adjust collateralization, at the cost of dust amounts of the pool's supported underlying assets.

### Likelihood Explanation
High feasibility: `deposit()` requires only an ERC20 allowance of the attacker's own tokens, is unauthenticated beyond pause/active flags, and `onBehalfOf_` accepts any nonzero address. The pool supports up to `MAX_TOKENS_PER_USER` deposit tokens (`addDepositToken` caps offerings at the same 30, contracts/Pool.sol:703), so a pool with ~30 collateral types can have a victim's entire list filled by one attacker transaction batch. Cost is proportional to dust minimums only. The main constraint is that it requires enough distinct collateral offerings in the pool, and the victim can eventually clear slots by repaying debt / transferring unlocked dust out — making this a griefing/freeze rather than direct theft.

### Recommendation
- Only append to `depositTokensOfAccount`/`debtTokensOfAccount` when the account itself initiated the action (i.e., restrict `onBehalfOf_` minting to self-deposits, or gate list addition behind `account_ == _msgSender()`), so third parties cannot write into a victim's list.
- Alternatively, enforce a minimum first-deposit threshold per account before the token is added to the per-account list, or skip list insertion for transfers to accounts that already have a zero balance and never opted in.
- Consider allowing the account (or pool) to forcibly remove a token entry via a user-callable `removeFromDepositTokensOfAccount` path when balance is dust.

### Proof of Concept
Hardhat sketch (pool with ≥ N registered DepositTokens `d[i]` for distinct underlyings `u[i]`):

```ts
// attacker funds itself with dust of each underlying
for (let i = 0; i < N; i++) {
  await u[i].approve(d[i].address, DUST);
  // victim never consented; writes d[i] into victim's depositTokensOfAccount
  await d[i].connect(attacker).deposit(DUST, victim.address);
}
// repeat across pools' collateral list until:
expect(await pool.getDepositTokensOfAccount(victim.address))
  .to.have.lengthOf(30);

// victim's own deposit of a NEW collateral type now reverts inside _mint
await u_new.connect(victim).approve(d_new.address, amount);
await expect(
  d_new.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

// any transfer of a new deposit token to victim also reverts
await expect(
  d_new.connect(attacker).transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");
```

Key assertions: `depositTokensOfAccount.length(victim) + debtTokensOfAccount.length(victim) >= MAX_TOKENS_PER_USER` after attacker-only calls, and all subsequent `deposit`/`transfer` of unheld token types to `victim` revert at `Pool.addToDepositTokensOfAccount` (contracts/Pool.sol:143-148, 216-220).
