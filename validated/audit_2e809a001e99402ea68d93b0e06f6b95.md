### Title
StackerDB inventory reply falsely advertises a chunk as stored before it is actually persisted - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` builds a `StackerDBChunkInv` reply, validates the pushed chunk's signature/version/size against the *currently stored* inventory, and then optimistically patches the in-memory inventory (`data.slot_versions`) to reflect the new chunk version as already present, immediately sending that patched inventory back to the peer — all before the chunk is ever written to the `StackerDBs` sqlite store. Actual persistence only happens later, asynchronously, when the message is forwarded to the relayer and processed by `Relayer::process_stacker_db_chunks`, which calls `try_replace_chunk`. This breaks the equality between "advertised inventory state" and "actually committed storage state," analogous to the reported bug where a validator was removed from storage without properly tracking the pending, not-yet-completed operation.

### Finding Description
In `stackslib/src/net/stackerdb/mod.rs`, function `handle_unsolicited_StackerDBPushChunk`: [1](#0-0) 

The code validates the chunk with `validate_received_chunk` (signature, size, staleness) using the peer's *current* on-disk inventory (`data.slot_versions` built from `self.stackerdbs`), then directly overwrites the version entry:
```
*slot_version = chunk_data.chunk_data.slot_version;
```
and sends this patched inventory back as the immediate reply for this push (`Ok((false, true))` → sent via `send_p2p_message` at line 863-869) [2](#0-1) . The actual write to the database — `try_replace_chunk` — does not happen in this code path at all; it only happens later when the same message is separately forwarded to the relayer and processed by `Relayer::process_stacker_db_chunks`, which performs the real `tx.try_replace_chunk(&sc, &md, &chunk.data)` call and can fail (e.g., `StaleChunk`, DB error, config change) and simply drop/log the chunk without any correction to what was already advertised: [3](#0-2) .

This means the node tells its peer "I have version N of this slot" via the ack/inventory it just sent, while the underlying storage commit for that version may still fail or race with another concurrent write (e.g. a legitimate newer chunk arriving concurrently causing this one to be rejected as stale, or a transient DB error). There is no "pending" tracking of the optimistic patch, and no rollback of the advertised inventory if the later `try_replace_chunk` fails.

### Impact Explanation
This matches the "High — serving non-canonical state as canonical / steering a node off the tip via false inventory" category. A peer that receives this falsely-advertised inventory will believe this node already has the given chunk version and will therefore stop trying to push or serve it to this node (StackerDB sync logic prioritizes/filters by peer-reported version). If the chunk failed to actually persist, the node ends up silently missing StackerDB data (e.g. signer messages) that it will never proactively re-fetch, because its own advertised inventory (from its perspective, and as observed by neighbors) claims it is already current. This is a genuine advertised-vs-stored state mismatch that can propagate an inconsistent, non-canonical view of StackerDB inventory into the network.

### Likelihood Explanation
The precondition is only a race/failure between two `try_replace_chunk` calls (any legitimate concurrent chunk write, or a transient sqlite error) landing after the optimistic reply is computed but before/during relayer processing — this is a normal operational race, not something requiring privileged access, so it is remotely reachable by any peer that can push a `StackerDBPushChunk` message during normal sync traffic. It does not require forging signatures or bypassing authentication; it simply exploits the gap between "validated" and "actually committed."

### Recommendation
Do not patch and send the ack/inventory as if the chunk is stored until `try_replace_chunk` has actually succeeded. Either defer sending the `StackerDBChunkInv` reply until after the relayer has attempted and confirmed the write, or track this as an explicit "pending" write and only report the new slot version in inventory once persistence is confirmed, reverting/correcting the advertised version if the later write fails.

### Proof of Concept
Not independently exploitable purely from static review without live network reproduction; the race requires two `StackerDBPushChunk` messages for the same slot arriving close together (or a DB write failure) such that the version reported in the immediate reply from `handle_unsolicited_StackerDBPushChunk` does not match what `Relayer::process_stacker_db_chunks` ultimately commits. I was not able to fully trace every downstream consumer of the peer-visible inventory (e.g., exact sync-scheduling logic that consults a remote peer's advertised `slot_versions`) within the available iterations to confirm the full propagation path; this would need to be verified further, e.g. by starting a Devin session with full repo access to trace `StackerDBSync`'s consumption of `StackerDBChunkInv` from remote peers to confirm it actually skips slots reported as already at a given version.
