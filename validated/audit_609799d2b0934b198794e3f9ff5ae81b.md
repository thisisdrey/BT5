### Title
Non-deterministic floating-point Bancor pricing in the legacy Exchange (AMM) swap path can be exploited by a single trader to drain pool reserves / cause state divergence - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The AROS incident describes an attacker directly manipulating an AMM liquidity pool's pricing to drain the majority of its reserves. Java-tron ships its own on-chain AMM primitive — the TRX/TRC10 `Exchange` (Bancor-style two-token pool) — reachable by any unprivileged account via `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`. The default (non-hardened) swap-pricing engine, `ExchangeProcessor`, computes reserve changes using `double`-precision floating point math (`Math.pow`/`StrictMath.pow` via `Maths.pow`) rather than exact integer/BigDecimal arithmetic.

### Finding Description
`ExchangeCapsule.transaction()` selects the pricing engine based on the `hardenedCalc` flag: when `dynamicStore.allowHardenExchangeCalculation()` is false (the default, only flippable by a committee proposal), it instantiates the legacy `ExchangeProcessor`, which is used for every `ExchangeTransactionContract` swap: [1](#0-0) 

`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` perform the Bancor formula entirely in `double`: [2](#0-1) 

This is the exact code path invoked from `ExchangeTransactionActuator.execute()`/`doValidate()` for every trade against the pool, with the resulting `buyTokenQuant` directly credited to the caller's account and debited from the pool's on-chain reserve balances: [3](#0-2) 

Floating-point `pow`/division results are not bit-exact across all JIT/JVM/hardware combinations and are also sensitive to input ordering; the codebase itself acknowledges this by introducing a `StrictMathWrapper`-based `useStrictMath` toggle and, separately, a fully `BigDecimal`-based `SafeExchangeProcessor` "hardened" path that is explicitly gated behind a committee-controlled `allowHardenExchangeCalculation` flag: [4](#0-3) [5](#0-4) 

Because `ExchangeTransactionActuator` unconditionally calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` and `allowHarden()` defaults to `false` until a committee proposal changes it, an ordinary account can broadcast a sequence of `ExchangeTransactionContract` trades (of adversarially chosen `quant` sizes designed to land on double-precision rounding edges) against any TRX/TRC10 pool to extract systematically more tokens from the counter-side reserve than the exact Bancor invariant would allow, or to push different validating nodes (running different JVM/CPU combinations) to compute divergent `buyTokenQuant` values for the same transaction.

### Impact Explanation
Two distinct concrete harms map to the in-scope acceptance criteria:
- **Theft of funds / unbacked balance**: an attacker crafting `quant` values that exploit `double` rounding in `exchangeToSupply`/`exchangeFromSupply` can extract more of the counter-token than the pool's true invariant supports, directly draining the pool similar to how the AROS attacker drained the AROS/USDT pool.
- **Chain split**: since `pow`/division on `double` is not guaranteed bit-identical across all JVMs/CPUs in a heterogeneous validator set unless `allowStrictMath()` is also enabled, two honest full nodes could compute different `buyTokenQuant` for the same swap transaction, producing diverging account/exchange state and a consensus fork.

### Likelihood Explanation
Any account with sufficient TRX/TRC10 balance can create and broadcast `ExchangeTransactionContract` transactions against a public `Exchange` pool without any special permission — this matches the "order placer" role explicitly in scope. The default value of `allowHardenExchangeCalculation` is off (it requires a chain-wide committee proposal to enable the safer `SafeExchangeProcessor`/hardened arithmetic path), so the vulnerable `double`-based path is the one exercised on-chain today for any pool that has not had this proposal passed. Exploiting the rounding edge cases to reliably extract excess value requires careful trade-size crafting/testing but is a purely off-chain computation an attacker can iterate on before broadcasting.

### Recommendation
- Make `SafeExchangeProcessor` (or an equivalent deterministic, exact-integer/BigDecimal implementation) the mandatory pricing engine for all `Exchange` swaps, removing the `double`-based `ExchangeProcessor` from any code path reachable without a special flag, rather than gating it behind an opt-in committee proposal.
- Add invariant checks after every swap (e.g., verifying `firstTokenBalance * secondTokenBalance` does not decrease beyond the fee-adjusted expected bound) in `ExchangeTransactionActuator`/`ExchangeCapsule.transaction` to reject any trade whose output violates the underlying Bancor invariant.
- If `double` arithmetic must be retained for backward compatibility, unconditionally force `useStrictMath = true` on all nodes so the computation is required to be bit-reproducible.

### Proof of Concept
1. Create (or locate) an `Exchange` pool via `ExchangeCreateContract` with token balances chosen so that repeated small trades sit near `double` rounding boundaries in `exchangeToSupply`/`exchangeFromSupply` (`ExchangeProcessor.java` lines 17-39).
2. On a network where `allowHardenExchangeCalculation` has not been enabled by committee proposal (default state), broadcast a series of `ExchangeTransactionContract` transactions with `quant` values pre-computed offline (by replicating the exact `double` formula) to consistently round `buyTokenQuant` in the attacker's favor.
3. Observe that the sum of extracted counter-tokens over the trade sequence exceeds what the exact Bancor invariant (`firstTokenBalance * secondTokenBalance = constant`, adjusted for the 0.0005/2000 Bancor weight) would allow, progressively draining the pool's reserve — analogous to the AROS pool drain.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
