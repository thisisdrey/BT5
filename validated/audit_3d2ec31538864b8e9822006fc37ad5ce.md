### Title
FetchIntoObjectPool accepts arbitrary, unrelated `origin` repository, allowing griefing resource-exhaustion fetches against repositories the caller does not own - ([File: internal/gitaly/service/objectpool/fetch_into_object_pool.go])

### Summary
`FetchIntoObjectPool` only validates that `origin` and the target object pool share the same storage name; it never verifies that `origin` is actually linked to (a member of) the given pool, nor that the caller has any established relationship between the two repositories.

### Finding Description
`validateFetchIntoObjectPoolRequest` checks only that `req.GetOrigin()` and `req.GetObjectPool()` are non-nil and share a storage name: [1](#0-0) 

The handler then builds the `origin` repo directly from the request and calls `objectPool.FetchFromOrigin`, which performs a full `git fetch` from `origin` into the pool along with expensive housekeeping (pruning, repacking, dangling-ref rescue, fsck-adjacent work) as documented: [2](#0-1) [3](#0-2) 

`objectpool.FromProto` only validates that the target `ObjectPool` repository is a valid pool repository or lies in a temp dir — it does not check that `origin` is a member of it: [4](#0-3) 

This mirrors the flashloan-griefing pattern: an operation that is supposed to be performed "on behalf of" an approved/linked party (a pool fetching from its own member) instead accepts an arbitrary third-party target supplied purely as a request field, with no verification of the relationship, causing repeated resource-consuming operations to be forced onto that unrelated repository/storage.

### Impact Explanation
Because `origin` is taken verbatim from the request with only a same-storage-name check, a caller can repeatedly invoke `FetchIntoObjectPool` naming any repository on the same storage as `origin` and any pool they can reference as the target, forcing Gitaly to run `git fetch --atomic` reading all refs/objects out of that unrelated `origin` repository, followed by pruning/repacking/housekeeping on the pool. Repeated invocation drives CPU, disk I/O, and repository-lock contention against a repository the caller does not control, degrading service for its legitimate owner (a resource-exhaustion/griefing DoS), analogous to draining an unrelated approved account's balance by repeatedly invoking flashloans against it.

### Likelihood Explanation
Reachability depends on what actually gates access to the `ObjectPoolService` RPCs in production. In GitLab's deployment model, this RPC is normally invoked only by Rails after verifying a genuine fork/pool relationship, but nothing in the Gitaly-side handler itself enforces that `origin` is a member of the target pool — the check is purely storage-name equality. If any caller with valid Gitaly RPC access (e.g., a compromised/malicious internal caller, or a future direct-exposure regression) can freely choose `origin`, this is trivially and repeatedly exploitable. Because Gitaly's own code offers no cross-check between `origin` and pool membership, this should be treated as a defense-in-depth gap even if today's only caller is trusted Rails logic.

### Recommendation
Before performing the fetch, verify that `origin`'s `objects/info/alternates` actually points at the target object pool (i.e., `origin` is a genuine, already-linked pool member) rather than trusting the request field alone. Reject the RPC if the linkage isn't already established, and consider RPC-level rate limiting per (origin, pool) pair to bound the cost of repeated invocations.

### Proof of Concept
1. Attacker obtains valid Gitaly access (e.g. via a caller path where request fields aren't independently authorized against actual pool membership).
2. Attacker creates/controls `pool` (their own object pool) and repeatedly calls `FetchIntoObjectPool` with `object_pool = pool` and `origin = victimRepo` (any repository sharing the same storage name), which passes `validateFetchIntoObjectPoolRequest`'s only check.
3. Each call triggers `ObjectPool.FetchFromOrigin` — `git fetch --atomic` against `victimRepo`'s full ref/object set plus subsequent pruning/repacking/housekeeping — consuming disk and CPU tied to `victimRepo` without its owner's action, repeated at will to grief the shared storage/host.

```go
func (s *server) FetchIntoObjectPool(ctx context.Context, req *gitalypb.FetchIntoObjectPoolRequest) (*gitalypb.FetchIntoObjectPoolResponse, error) {
	if err := validateFetchIntoObjectPoolRequest(req); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	objectPool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		return nil, structerr.NewInvalidArgument("object pool invalid: %w", err)
	}

	origin := s.localRepoFactory.Build(req.GetOrigin())

	if err := objectPool.FetchFromOrigin(ctx, origin, func(repo *gitalypb.Repository) *localrepo.Repo {
		return s.localRepoFactory.Build(repo)
	}); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}
```

```go
func validateFetchIntoObjectPoolRequest(req *gitalypb.FetchIntoObjectPoolRequest) error {
	if req.GetOrigin() == nil {
		return errors.New("origin is empty")
	}

	if req.GetObjectPool() == nil {
		return errors.New("object pool is empty")
	}

	originRepository, poolRepository := req.GetOrigin(), req.GetObjectPool().GetRepository()

	if originRepository.GetStorageName() != poolRepository.GetStorageName() {
		return errors.New("origin has different storage than object pool")
	}

	return nil
```

```go
// FetchFromOrigin initializes the pool and fetches the objects from its origin repository
func (o *ObjectPool) FetchFromOrigin(ctx context.Context, origin *localrepo.Repo, newLocalRepo LocalRepoFactory) error {
	if !o.Exists(ctx) {
		return structerr.NewInvalidArgument("object pool does not exist")
	}

	originPath, err := origin.Path(ctx)
	if err != nil {
		return fmt.Errorf("computing origin repo's path: %w", err)
	}

	if err := o.housekeepingManager.CleanStaleData(ctx, o.Repo, housekeeping.DefaultStaleDataCleanup()); err != nil {
		return fmt.Errorf("cleaning stale data: %w", err)
	}

	if err := o.logStats(ctx, "before fetch"); err != nil {
		return fmt.Errorf("computing stats before fetch: %w", err)
	}

	// Ideally we wouldn't want to prune old references at all so that we can keep alive all
	// objects without having to create loads of dangling references. But unfortunately keeping
	// around old refs can lead to D/F conflicts between old references that have since
	// been deleted in the pool and new references that have been added in the pool member we're
	// fetching from. E.g. if we have the old reference `refs/heads/branch` and the pool member
	// has replaced that since with a new reference `refs/heads/branch/conflict` then
	// the fetch would now always fail because of that conflict.
	//
	// Due to the lack of an alternative to resolve that conflict we are thus forced to enable
	// pruning. This isn't too bad given that we know to keep alive the old objects via dangling
	// refs anyway, but I'd sleep easier if we didn't have to do this.
	//
	// Note that we need to perform the pruning separately from the fetch: if the fetch is using
	// `--atomic` and `--prune` together then it still wouldn't be able to recover from the D/F
	// conflict. So we first to a preliminary prune that only prunes refs without fetching
	// objects yet to avoid that scenario.
	if err := o.pruneReferences(ctx, origin); err != nil {
		return fmt.Errorf("pruning references: %w", err)
	}
```

```go
// FromProto returns an object pool object from its Protobuf representation. This function verifies
// that the object pool exists and is a valid pool repository.
func FromProto(
	ctx context.Context,
	logger log.Logger,
	locator storage.Locator,
	gitCmdFactory gitcmd.CommandFactory,
	catfileCache catfile.Cache,
	txManager transaction.Manager,
	housekeepingManager housekeepingmgr.Manager,
	proto *gitalypb.ObjectPool,
) (*ObjectPool, error) {
	poolPath, err := locator.GetRepoPath(ctx, proto.GetRepository(), storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, err
	}

	if !storage.IsPoolRepository(proto.GetRepository()) {
		// When creating repositories in the ObjectPool service we will first create the
		// repository in a temporary directory. So we need to check whether the path we see
		// here is in such a temporary directory and let it pass.
		tempDir, err := locator.TempDir(proto.GetRepository().GetStorageName())
		if err != nil {
			return nil, fmt.Errorf("getting temporary storage directory: %w", err)
		}

		if !strings.HasPrefix(poolPath, tempDir) {
			return nil, ErrInvalidPoolDir
		}
	}

	pool := &ObjectPool{
		Repo:                localrepo.New(logger, locator, gitCmdFactory, catfileCache, proto.GetRepository()),
		logger:              logger,
		locator:             locator,
		gitCmdFactory:       gitCmdFactory,
		txManager:           txManager,
		housekeepingManager: housekeepingManager,
	}

	if !pool.IsValid(ctx) {
		return nil, ErrInvalidPoolRepository
	}

	return pool, nil
}
```
