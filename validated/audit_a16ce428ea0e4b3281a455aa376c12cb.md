### Title
Missing pool-solvency check in default (non-hardened) Exchange swap math allows draining an Exchange pool beyond its actual balance - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
The Orion Protocol bug is a swap where an inconsistent/incorrectly-validated intermediate balance state during a token exchange lets the attacker extract more value than the pool actually backs. The closest reachable analog in java-tron is the on-chain bancor-style `Exchange*` feature: `ExchangeTransactionActuator` lets any account swap TRX/TRC10 through a bonding-curve pool, and the balance-consistency check that would stop a pool from being drained past its real balance is applied **only** when the hardened math path is active, not on the default/legacy path.

### Finding Description
`ExchangeCapsule.transaction()` computes the counter-token amount via `ExchangeProcessor` (legacy double/`Math.pow` math) or `SafeExchangeProcessor` (BigDecimal math), selected purely by the `hardenedCalc` flag: [1](#0-0) 

The invariant check `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) throw ...` is gated by `hardenedCalc`. When `hardenedCalc` is `false` (the legacy/default path), the resulting `newFirstTokenBalance`/`newSecondTokenBalance` are written into the capsule with **no non-negativity or solvency check at all**: [2](#0-1) 

Whether hardening is applied is controlled at runtime by `AbstractExchangeActuator.allowHarden()`, which just reads a dynamic property: [3](#0-2) 

`ExchangeTransactionActuator.doValidate()` only checks that the counter-amount returned meets the caller's minimum expectation (`tokenExpected`) — it never checks that the counter-amount does not exceed the pool's own balance of that token: [4](#0-3) 

`execute()` then unconditionally persists whatever balances `transaction()` produced, crediting the trader's account and writing the (possibly negative) pool state back to storage: [5](#0-4) 

The legacy `ExchangeProcessor` relies on `double`/`Math.pow` floating point arithmetic for a Bancor-style continuous relay computation: [6](#0-5) 

Because this arithmetic is done in double precision (not the BigDecimal path used by `SafeExchangeProcessor`), and because the actuator applies no post-computation sanity bound against the actual pool reserve on the legacy path, a caller who repeatedly submits `ExchangeTransactionContract` swaps against a pool with extreme/edge-case reserve ratios (very small counter-token balance relative to requested quant, or values near the boundaries that stress the `pow`/`exchangeToSupply`/`exchangeFromSupply` computations) can obtain a `buyTokenQuant` that exceeds the pool's real reserve of that token. Unlike the hardened path, nothing stops the resulting `secondTokenBalance` (or `firstTokenBalance`) from going negative, and nothing stops `execute()` from crediting the trader with tokens the pool never actually held.

### Impact Explanation
If the legacy math path can be driven to emit a counter-amount greater than the pool's actual reserve, the trader receives tokens (TRX or TRC10) that are not backed by the pool's real balance — this is a direct theft-of-funds / unbacked-balance condition against every other liquidity provider and trader of that Exchange pool, and the corrupted (negative) balance is then used as the baseline for all subsequent swaps against that exchange, compounding the damage and effectively permanently corrupting/freezing the pool's accounting.

### Likelihood Explanation
Any unprivileged account can call `ExchangeTransactionContract` directly (no special permission required) as long as an Exchange pool exists and hardening is not enabled (`allowHardenExchangeCalculation` is a chain-parameter feature flag, off unless explicitly activated via governance/proposal — the hardened, safer code path was clearly added later as a fix, implying the un-hardened path is the historically shipped/default behavior). Reaching a floating-point edge case requires carefully chosen exchange pool state and trade sizes (e.g., pools with very small reserves relative to trade size), which is feasible for an attacker who creates their own `ExchangeCreateContract` pool with small first/second token balances, then drives large trades against it. I could not fully verify from the available code excerpts the exact numeric conditions under which `ExchangeProcessor.exchange()` returns a value exceeding `buyTokenBalance` (this would require running/fuzzing the double-precision formula), so likelihood is assessed as Medium pending numeric verification.

### Recommendation
Apply the same non-negativity/solvency invariant check (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`, and ideally `buyTokenQuant <= buyTokenBalance`) unconditionally in `ExchangeCapsule.transaction()`, regardless of the `hardenedCalc` flag, and reject the transaction with `ContractValidateException` in `ExchangeTransactionActuator.doValidate()`/`execute()` if this invariant is violated, rather than gating the check behind a feature flag.

### Proof of Concept
Not independently confirmed by execution — this requires constructing an `ExchangeCreateContract` pool with small reserve values and then issuing `ExchangeTransactionContract` trades sized to push `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` (double-precision `Math.pow`) into a regime where `buyTokenQuant` computed in `ExchangeCapsule.transaction()` exceeds the actual `buyTokenBalance`, while `allowHardenExchangeCalculation` remains at its default (disabled) value, then calling `ExchangeTransactionActuator.execute()` to observe the pool's counter-token balance become negative in `ExchangeStore`/`ExchangeV2Store`. I was not able to execute this numerically within the scope of this review, so the exact trigger inputs are unverified.

    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)

package org.tron.core.capsule;

import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.Maths;

@Slf4j(topic = "capsule")
public class ExchangeProcessor implements ExchangeCapsule.Processor {

  private long supply;
  private final boolean useStrictMath;

  public ExchangeProcessor(long supply, boolean useStrictMath) {
    this.supply = supply;
    this.useStrictMath = useStrictMath;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
