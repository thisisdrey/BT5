### Title
Unbounded, attacker-inflatable LevelDB/RocksDB prefix scan in `DelegatedResourceAccountIndexStore.getWithPrefix` reachable from the public `GetDelegatedResourceAccountIndex(V2)` HTTP/gRPC API - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
`DelegatedResourceAccountIndexStore.getWithPrefix` (invoked via `getIndex`/`getV2Index`) performs a full key-space prefix scan with `prefixQuery` against the underlying LevelDB/RocksDB store for every call to the public, unauthenticated `getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` API, with no limit on the number of entries returned or scanned. Because an attacker fully controls how many delegation-index entries exist under their own address prefix (by repeatedly calling `DelegateResourceContract`/`DelegateResourceParam` with minimal frozen balances to many distinct receiver addresses), they can inflate the entry count for a chosen address arbitrarily, then repeatedly invoke the free read-only query API to force expensive linear scans, sorts, and full-object materialization on every full/solidity/PBFT node, unboundedly consuming CPU and memory — the same "unbounded recall of stored records into memory on each request" pattern described in the analog report.

### Finding Description
`DelegateResourceProcessor.execute` (and the corresponding `DelegateResourceActuator`) writes two `DelegatedResourceAccountIndexCapsule` records per delegation — one under the `V2_FROM_PREFIX + from + to` key and one under `V2_TO_PREFIX + to + from` key: [1](#0-0) 

There is no upper bound on how many distinct `receiverAddress` values a single owner can delegate to, and no cap on the total number of index records created for one address (each call only requires a nonzero `delegateBalance`, which can be minimal). The only cost to the attacker is transaction fees for issuing many small `DelegateResourceContract` transactions from a single controlled account to many different receiver addresses they also control.

When the index is later read, `DelegatedResourceAccountIndexStore.getV2Index`/`getIndex` calls `getWithPrefix`, which performs two unbounded `prefixQuery` calls per request: [2](#0-1) 

`prefixQuery` is implemented as a full iterator scan of the underlying store with no count/size limit — it iterates until the prefix no longer matches, materializing every matching key/value into a `HashMap`: [3](#0-2) [4](#0-3) 

The `Chainbase.prefixQuery` wrapper additionally merges this with an unbounded snapshot scan (`SnapshotImpl.collect(all, prefix)`), which linearly filters every uncommitted key in the snapshot chain: [5](#0-4) [6](#0-5) 

This is directly exposed to unauthenticated callers via `Wallet.getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2`: [7](#0-6) 

...and surfaced through HTTP servlets with no pagination: [8](#0-7) 

as well as gRPC (`RpcApiService`) and JSON-RPC-adjacent Wallet/WalletSolidity/WalletPBFT services, none of which impose a size cap on the result: [9](#0-8) 

The result list is then fully sorted and copied on every request: [10](#0-9) 

### Impact Explanation
Each query causes O(N) DB iteration, O(N log N) sorting, and O(N) protobuf materialization/serialization, where N is the number of delegation-index entries the attacker chose to create for the targeted address. Because the read endpoint is public, free (no fee, unauthenticated), and callable repeatedly at will (unlike the write path that costs a transaction fee once), the attacker pays a one-time, low cost to inflate N and then can trigger repeated, sustained CPU/memory/I-O consumption against every full node, solidity node, and PBFT node servicing this RPC — degrading node responsiveness for all other API clients (denial of service / resource consumption), matching CWE-400.

### Likelihood Explanation
Likelihood is moderate: creating many `DelegateResourceContract` transactions from attacker-controlled accounts is straightforward and requires only bandwidth/energy fees per transaction (no privileged role, no SR/witness/committee access, no p2p manipulation). The read API (`GetDelegatedResourceAccountIndex`/`V2`) is unauthenticated and reachable by any HTTP/gRPC client, satisfying the "unprivileged... anonymous API client" threat model in scope. However, the attacker must pay real fees to build up N entries, which somewhat limits attack economics compared to a purely free resource-consumption bug — this is the main mitigating factor.

### Recommendation
- Add a hard cap on the number of delegation-index entries `prefixQuery`/`getWithPrefix` will scan/return per query (e.g., stop iteration once a configurable maximum is reached), and/or paginate the `GetDelegatedResourceAccountIndex(V2)` API similarly to `GetPaginatedProposalList`/`GetPaginatedExchangeList`.
- Consider limiting the number of distinct delegation index records a single account can accumulate (e.g., cap distinct `to`/`from` counterparties per account) in `DelegateResourceProcessor`/`DelegateResourceActuator`.
- Enforce a minimum `delegateBalance` threshold high enough to make index-inflation attacks economically unattractive.

### Proof of Concept
1. From an attacker-controlled account `A`, repeatedly submit `DelegateResourceContract` transactions delegating a minimal `delegateBalance` of bandwidth/energy to a large number (e.g., tens of thousands) of distinct attacker-controlled receiver addresses `R1..Rn`. Each call goes through `DelegateResourceActuator`/`DelegateResourceProcessor.execute`, which writes a new `DelegatedResourceAccountIndexCapsule` under `V2_FROM_PREFIX + A + Ri` for every `i`.
2. Once N is large, repeatedly call the public HTTP endpoint `/wallet/getdelegatedresourceaccountindexv2` (or the gRPC `GetDelegatedResourceAccountIndexV2`) with `value = A`.
3. Each call triggers `Wallet.getDelegatedResourceAccountIndexV2` → `DelegatedResourceAccountIndexStore.getV2Index` → `getWithPrefix`, which performs unbounded `prefixQuery` scans and sorts, all in the RPC-handling thread, consuming CPU/memory proportional to N on every request — observed via increased node CPU load / response latency for concurrent RPC callers when repeated at volume.

        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));

    Map<WrappedByteArray, byte[]> result = prefixQueryRoot(key);
    Map<WrappedByteArray, byte[]>  snapshot = prefixQuerySnapshot(key);
    result.putAll(snapshot);
    result.entrySet().removeIf(e -> e.getValue() == null);
    return result;
  }

  private Map<WrappedByteArray, byte[]> prefixQueryRoot(byte[] key) {
    Map<WrappedByteArray, byte[]> result = new HashMap<>();
    if (((SnapshotRoot) head.getRoot()).db.getClass() == LevelDB.class) {
      result = ((LevelDB) ((SnapshotRoot) head.getRoot()).db).getDb().prefixQuery(key);
    } else if (((SnapshotRoot) head.getRoot()).db.getClass() == RocksDB.class) {
      result = ((RocksDB) ((SnapshotRoot) head.getRoot()).db).getDb().prefixQuery(key);
    }
    return result;
  }
