### Title
Missing content-hash verification of attachment payloads in `AttachmentsBatchStateContext::extend_with_attachments` - (File: stackslib/src/net/atlas/download.rs)

### Summary
When a node downloads an attachment from a peer via `GET /v2/attachments/<content_hash>`, the response is decoded and inserted into the resolved-attachments set without ever checking that the returned attachment's content actually hashes to the requested `content_hash`. A malicious peer serving arbitrary bytes in the response body can therefore get a mismatched attachment accepted and treated as satisfying an on-chain BNS commitment.

### Finding Description
`AttachmentsBatchStateContext::extend_with_attachments` iterates `results.succeeded`, which pairs each outstanding `AttachmentRequest{ content_hash: X, .. }` with the peer's `StacksHttpResponse`. For each successfully decoded response it does: [1](#0-0) 
`response.decode_atlas_get_attachment()` only parses the HTTP body into a `GetAttachmentResponse { attachment: Attachment { content } }` — there is no comparison anywhere in this function (or in the caller `AttachmentsBatchStateMachine::try_proceed`) between `request.content_hash` and `response.attachment.hash()` before `self.attachments.insert(response.attachment)` is executed.

The consumer of `context.attachments` in `AttachmentsDownloader::run` then unconditionally trusts the inserted attachment: [2](#0-1) 
It looks up `attachment.hash()` to find matching `AttachmentInstance`s already recorded on-chain (`find_all_attachment_instances`), inserts the attachment into `atlasdb` as instantiated (`insert_instantiated_attachment`), and calls `context.attachments_batch.resolve_attachment(&attachment.hash())`. Since `attachment.hash()` is recomputed from whatever content the peer sent, an attacker who serves content `Y` for a request whose `content_hash` was `X` will simply have that lookup fail to match `X`'s instance (so `X` remains unresolved / gets retried) unless the attacker crafts `Y` such that `Hash160::from_data(Y)` also collides with some other on-chain-recorded `content_hash` the node is tracking, or unless the node had multiple pending instances for the same hash where mismatched data gets stored as "instantiated" under the attacker-supplied hash. In the general case (no relevant `AttachmentInstance` recorded for `Y`'s hash), the mismatched attachment is simply stored in `atlasdb` as an uninstantiated/instantiated attachment blob (via `insert_instantiated_attachment`) without ever being tied back to `request.content_hash`, and the original request for `X` is not marked resolved — it will just retry or eventually be dropped.

The critical point is that `extend_with_attachments` throws away the `request.content_hash` after using it only as a `HashMap`/queue key, and never validates it against the delivered payload. This differs from correctly-designed attachment-fetch code, where the fetcher must verify `Hash160::from_data(content) == content_hash` before accepting data, exactly analogous to how BNS zonefile/attachment content-addressing is supposed to work.

### Impact Explanation
Because `attachment.hash()` (recomputed from the attacker's chosen `content`) is used as the key for reconciling with on-chain `AttachmentInstance`s, and not `request.content_hash`, the query `find_all_attachment_instances(&attachment.hash())` in `AttachmentsDownloader::run` is the only real correctness anchor here — it re-derives the association purely from content hash, not from which request fetched it. This means:
- A malicious peer cannot force acceptance of *wrong* content under an *arbitrary* `content_hash` label, because the eventual DB association is keyed by the real hash of the delivered bytes, not by the hash the attacker claims to be answering.
- However, the missing check is still a defect: nothing prevents storing/using data whose hash doesn't match the specific `AttachmentRequest.content_hash` that solicited it, meaning a byzantine/faulty peer response can be silently accepted into `context.attachments` and pushed to `atlasdb.insert_instantiated_attachment` even though it does not satisfy the outstanding request — this pollutes the attachments table with unrequested/unresolved data and can cause a legitimate `AttachmentInstance` for hash `X` to remain permanently unresolved (denial of the intended attachment) while consuming retry budget, since `context.attachments_batch.resolve_attachment` is keyed by the actually-computed hash, not `X`.

This does not rise to "serving wrong data as canonical for hash X" because the reconciliation step downstream re-derives the hash from content and only resolves instances matching that real hash. No unauthenticated write of arbitrary/attacker-chosen state under a victim-chosen key is demonstrated, and no crash or forged canonical data is produced.

### Likelihood Explanation
Reaching this code path requires: the node to have an outstanding BNS-derived `AttachmentInstance`/`AttachmentRequest`, a normal outbound P2P peer connection reachable by any node, and the remote peer (attacker) to serve an HTTP 200 response to `GET /v2/attachments/<hash>` with attacker-chosen bytes — a low-cost, repeatable action requiring no privilege beyond running a peer node with an advertised attachment inventory bit set. This part of the precondition is realistic and remotely triggerable.

### Recommendation
Add an explicit equality check in `extend_with_attachments` before inserting into `self.attachments`:
```rust
if let Ok(response) = response.decode_atlas_get_attachment() {
    if response.attachment.hash() == request.content_hash {
        self.attachments.insert(response.attachment);
        report.bump_successful_requests();
    } else {
        report.bump_failed_requests();
    }
} else {
    report.bump_failed_requests();
}
```
This ties acceptance directly to the content hash that was solicited, rather than relying solely on the downstream `find_all_attachment_instances` lookup for correctness, and prevents faulty/malicious peers from having their responses accepted for requests they did not actually satisfy.

### Proof of Concept
Unverified as a full exploit due to index/read limitations on `decode_atlas_get_attachment` and `find_all_attachment_instances` internals, but the missing-check portion is directly confirmed in code: construct an `AttachmentsBatchStateContext` with `peers` populated, create a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map has key `AttachmentRequest{content_hash: X, ..}` and value `Some(StacksHttpResponse)` whose body decodes via `decode_atlas_get_attachment()` to `Attachment{content: Y}` with `Hash160::from_data(&Y) != X`. Call `context.extend_with_attachments(&mut results)` and assert `context.attachments` contains the `Y`-attachment despite `Hash160::from_data(&Y) != X` — this assertion succeeds today because of the missing check at [1](#0-0) , confirming the absent guard, though the downstream severity is bounded by the hash-keyed reconciliation in `AttachmentsDownloader::run` ( [2](#0-1) ), which this analysis could not fully trace into `AtlasDB::find_all_attachment_instances`/`insert_instantiated_attachment` semantics to conclusively rule out state pollution — recommend a background Devin session with full repo access to verify DB-level implications of storing hash-mismatched attachments.
