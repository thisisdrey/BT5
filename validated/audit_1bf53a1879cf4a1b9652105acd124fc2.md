### Title
Hardcoded, immutable `UNDERLYING` token addresses in vault contracts cause permanent DOS/freezing if the underlying token contract is migrated - (File: mainnet/contracts/vault/v0-vault-usdh.clar, v0-vault-sbtc.clar, v0-vault-usdc.clar, v0-vault-ststx.clar, v0-vault-ststxbtc.clar)

### Summary
Each vault contract hardcodes the address of its underlying SIP-010 token as a `define-constant` and uses that literal principal directly in `contract-call?` for all deposits and withdrawals. There is no mechanism (not even a DAO-gated one) to update this address if the underlying token contract is redeployed/migrated, exactly analogous to the `noteAddress` issue in `asdRouter.sol` where a hardcoded external token address becomes permanently stale and DOSes protocol operations.

### Finding Description
`v0-vault-usdh.clar` defines `UNDERLYING` as a hardcoded principal pointing to `'SPN5AKG35QZSK2M8GAMR4AFX45659RJHDW353HSG.usdh-token-v1`: [1](#0-0) 

This same pattern of hardcoding an external token's exact contract address is repeated across the other vaults (`v0-vault-sbtc.clar`, `v0-vault-usdc.clar`), each embedding a specific versioned token address (e.g. `sbtc-token`, `usdcx`): [2](#0-1) 

Because Clarity's `contract-call?` requires a static, literal contract principal (unlike Solidity, which can dynamically resolve an address at runtime), these constants are baked into the contract's transfer logic in `receive-underlying`/`send-underlying`, which are invoked on every deposit and withdrawal path: [3](#0-2) 

The naming itself (`usdh-token-v1`, `ststxbtc-token-v2`) shows that these tokens are already versioned and have previously been migrated to new contract addresses, confirming that token redeployment is a realistic, recurring event in this ecosystem, not a hypothetical one — directly matching the underlying report's Canto `NOTE` migration scenario. Unlike `asdOFT.sol`'s corrected pattern of resolving the address dynamically via `cNoteToken.underlying()`, these vaults have no dynamic resolution and no admin/DAO setter to update the constant, since Clarity constants cannot be reassigned at all (there is no `var-set` equivalent for a `define-constant`).

### Impact Explanation
If any of these underlying token contracts (USDH, sBTC, USDC-equivalent, stSTX, stSTXbtc) is migrated/redeployed to a new address — as has already happened historically for these exact assets per the versioned naming — the vault's `receive-underlying`/`send-underlying` calls will target a stale, now-inert (or nonexistent) contract. This permanently breaks `deposit`, `withdraw`, `borrow`, `repay`, and liquidation flows for that vault, because the vault contract itself cannot be upgraded to point to the new token address (it is not a `define-data-var`, and even if the DAO tried to reconfigure it, there is no setter function exposed at all). Any user funds already deposited become permanently frozen in the vault since redemption also routes through the same hardcoded `send-underlying` call. This lands squarely in the in-scope **High** impact category: permanent freezing of funds.

### Likelihood Explanation
Likelihood is non-trivial: the existing constants already reference "v1"/"v2" suffixed token contracts, demonstrating that the referenced ecosystem tokens (USDH, stSTXbtc) have already undergone at least one migration to a new contract address. Any future migration of one of these tokens by their respective token teams (outside Zest's control) — the same class of event described in the external report for Canto's `NOTE` — would immediately and permanently trigger this DOS/freeze for the corresponding Zest vault, with no code-level path to remediate the affected vault instance.

### Recommendation
Store the underlying token's canonical identity behind a resolvable mechanism instead of a hardcoded literal principal: e.g., maintain the underlying address in a `define-data-var` settable only through DAO-gated logic (mirroring the pattern already used for other configurable protocol parameters via `dao-executor`), or use a trait-based dynamic dispatch parameter for the underlying token contract on every deposit/withdraw call so callers supply the currently valid contract reference, with a DAO-controlled or registry-verified allowlist to prevent malicious substitution.

### Proof of Concept
1. Assume `usdh-token-v1` at `'SPN5AKG35QZSK2M8GAMR4AFX45659RJHDW353HSG.usdh-token-v1` is deprecated by its maintainers and a new `usdh-token-v2` is deployed with fresh balances/allowances (as has already occurred for `ststxbtc-token-v2`).
2. `v0-vault-usdh.clar`'s `UNDERLYING` constant still points to the old v1 address; `receive-underlying`/`send-underlying` continue calling the stale contract. [3](#0-2) 
3. Any user attempting to `deposit` new v2-USDH tokens fails because the vault only recognizes/transfers via the v1 contract; any user attempting to withdraw existing balances triggers `send-underlying` against the v1 contract, which may hold no liquidity or be paused/deprecated by its maintainer, permanently freezing withdrawals.
4. No function in the vault contract exists to update `UNDERLYING`, so the vault instance is permanently DOSed for its core operations, with no way for the DAO to remediate short of redeploying the entire vault (and migrating all existing shares/state), which is not a valid severity mitigation per prior C4 precedent cited in the report.
