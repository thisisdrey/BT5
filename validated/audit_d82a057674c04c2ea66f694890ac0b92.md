### Title
Check-then-act race between replay-window `Check` and `Update` allows nonce reuse validation bypass - (File: connection_state.go)

### Summary
The external report's bug class is "a validation function whose result is only meaningful if the guarded operation happens in a fixed, uninterrupted order directly after it — any interleaving or developer error breaks the guarantee." In `checkSuccess()`, this manifested as a check that must immediately follow the external call it validates. The same anti-pattern exists in Nebula's `ConnectionState.Decrypt` / `VerifyRelay`, where the anti-replay `window.Check` and `window.Update` calls are split into two separately-locked critical sections with the actual AEAD decryption happening in between, unlocked.

### Finding Description
`ConnectionState.Decrypt` performs the replay check, releases the lock, decrypts, then re-acquires the lock to record the counter as seen: [1](#0-0) 

and `VerifyRelay` follows the identical pattern: [2](#0-1) 

`Bits.Check` only *reads* whether counter `i` has been seen; it does not mark it as seen — only `Bits.Update` mutates the bitmap: [3](#0-2) [4](#0-3) 

Because `Check` and `Update` are not atomic with respect to each other (the lock is dropped for the duration of the AEAD `Open`/decryption call), two packets carrying the **same** `messageCounter` that arrive concurrently (e.g., via multiple UDP reader goroutines/`q` indices feeding the same `HostInfo`) can both pass `window.Check` before either has called `window.Update`. Both then proceed to `dKey.DecryptDanger`, and if the attacker or a mangled network path delivers a duplicate/replayed ciphertext for that counter, the anti-replay guarantee — which depends on `Check` executing "directly next to" the state mutation it gates, exactly the ordering assumption the external report flags for `checkSuccess` — can be violated under concurrency. This is a check/act ordering bug of the same class as the reported one: the correctness of the guard is entirely dependent on an implicit, unenforced execution-order/atomicity contract between two calls that are not combined into a single atomic operation.

### Impact Explanation
If the race is won by an attacker-controlled duplicate/replayed packet, the sliding-window replay protection that Nebula relies on to prevent traffic replay is bypassed for that counter, permitting a replayed encrypted packet to be accepted and delivered to the TUN device (or, for `VerifyRelay`, accepted as a valid relay frame). This is a concrete replay/traffic-forgery impact within the intended nebula analog categories (replay handling).

### Likelihood Explanation
Exploitation requires winning a narrow timing window between `Check` and `Update` for the *same* counter, which requires the attacker to get two copies of the same encrypted packet (a legitimate one plus a replay) processed concurrently by the receiving node — plausible on a UDP transport where duplicate delivery (network duplication, or an on-path attacker resending) is expected and where multiple reader goroutines (`q`) can dispatch packets for the same `HostInfo` in parallel. This makes the difficulty low-to-moderate, consistent with the "Low" difficulty rating given to the analogous `checkSuccess` ordering bug in the source report.

### Recommendation
- **Short term:** Hold `decryptLock` across the entire check-decrypt-update sequence in both `Decrypt` and `VerifyRelay` so that `window.Check` and `window.Update` for a given counter are atomic with respect to concurrent decrypt attempts, eliminating the TOCTOU window.
- **Long term:** Refactor `Bits` to expose a single atomic `CheckAndReserve(i)`-style operation (reserve the slot before doing the expensive decrypt, and roll back on decrypt failure) so callers cannot decouple the check from the state mutation it protects, removing the developer-error-prone two-step contract entirely.

### Proof of Concept
Conceptual reproduction (concurrency-dependent, not a single deterministic packet):
1. Capture/replay a valid encrypted data packet `P` with `messageCounter = N` addressed to a live tunnel.
2. Send `P` twice in rapid succession over UDP so that the two reader paths call `ConnectionState.Decrypt(l, N, ...)` concurrently.
3. Both goroutines call `cs.window.Check(l, N)` under separate lock acquisitions before either has called `cs.window.Update(l, N)`; both observe `Check == true` because the bitmap bit for `N` has not yet been set.
4. Both goroutines proceed to `cs.dKey.DecryptDanger(...)`; since `P` is a valid ciphertext, both succeed, and the replayed copy of `P` is delivered a second time to the TUN interface (or accepted a second time as a relay frame in `VerifyRelay`), even though the anti-replay window is nominally supposed to reject exact duplicates. func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
