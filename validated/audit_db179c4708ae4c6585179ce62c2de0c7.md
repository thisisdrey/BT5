### Title
Unauthenticated `RecvError` teardown allows any off-path attacker to poison hostmap/tunnel state via UDP source-address spoofing - (File: `outside.go`)

### Summary
The reported bug class is about a state-mutating function that can be triggered by a party other than the legitimate owner, causing the system's tracked state to silently diverge from reality (rewards never added to the assets list) purely because the call site had no real authorization check tied to the actor who should be allowed to trigger it. The nebula analog is `handleRecvError` in `outside.go`, which tears down and deletes hostmap state for a tunnel in response to a `header.RecvError` packet type that is processed **before any cryptographic authentication** and whose only "authorization" check is a comparison against a value (the UDP source IP) that is fully attacker-controlled.

### Finding Description
`readOutsidePackets` dispatches `header.RecvError` packets straight to `f.handleRecvError(via.UdpAddr, h)` immediately after header parsing, with no certificate check, no handshake, and no AEAD/decrypt step: [1](#0-0) 

`handleRecvError` looks up the hostinfo purely from the plaintext `h.RemoteIndex` field carried in every unencrypted outer header (visible on the wire to any on/off-path observer), and its sole "spoofing" defense is comparing the packet's source `netip.AddrPort` to the currently known remote address of that hostinfo: [2](#0-1) 

Because UDP is connectionless and the source address in `via.UdpAddr` is taken from the packet's IP header (attacker-controlled on networks without egress/ingress filtering, or in general when the attacker is off-path but able to guess/observe the remote's known address+index), an attacker with **no CA-signed certificate and no established Noise session** can:
1. Observe or otherwise learn a target's `hostinfo.remoteIndexId`/`localIndexId` (transmitted in cleartext on every outer packet header for that tunnel), and
2. Spoof the source IP:port to match `hostinfo.GetRemote()`,

to produce a 1-byte-header UDP packet (`header.RecvError`) that passes the only guard in `handleRecvError` and triggers `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)` — i.e., unauthenticated, certificate-less remote state poisoning/teardown of the hostmap's tracked tunnel state, exactly mirroring the report's core defect: a state-affecting action gated by a check that doesn't actually verify the caller is who they claim, causing the system's tracked state to diverge from the real, intended state.

The maintainers' own `TestCloseTunnelAuthenticated` test explicitly validates that a spoofed `header.CloseTunnel` packet is *rejected* because that path requires successful AEAD decryption keyed to `hostinfo.ConnectionState`: [3](#0-2) 
`RecvError`, in contrast, is deliberately routed around decryption entirely (see the `switch h.Type` block that `return`s before reaching `hostinfo.ConnectionState.Decrypt`), so it has no equivalent authenticity guarantee.

### Impact Explanation
An attacker with no valid CA-signed certificate and no participation in any handshake can force any node to tear down and delete an active tunnel's tracked hostmap state at will, repeatedly, causing:
- Denial of service: continuous tunnel teardown/re-handshake churn between two legitimate peers.
- Remote state poisoning: the victim's tracked tunnel state (hostmap entries, pending indexes) is deleted/reset based on an unauthenticated trigger, which is the direct analog of the original report's "state not tracked properly" impact — the system's internal bookkeping no longer reflects the true state of the relationship between peers.

This matches the "remote state poisoning" / "firewall(-adjacent) enforcement bypass" impact categories called out as acceptable in the validation criteria.

### Likelihood Explanation
Reachability requires only: (a) knowledge of the target's current UDP remote address (observable from any packet exchange, lighthouse query, or simple traffic monitoring) and (b) the ability to spoof that source address on the wire (feasible on networks lacking BCP38/anti-spoofing egress filtering, or via reflection/off-path techniques), and (c) the `RemoteIndex`, which travels unencrypted in the header of every packet for that tunnel and is therefore trivially observable to anyone who can see traffic between the peers. No certificate, PSK, or Noise handshake participation is needed. The `listen.accept_recv_error` config can mitigate but defaults to `always`, and even the `private` mode only restricts by whether the *claimed* address is a private IP, not whether it's authentic.

### Recommendation
Do not let `RecvError` (or any other pre-authentication packet type) trigger destructive hostmap mutations based solely on comparing an attacker-controlled UDP source address to a previously-learned remote address. Options:
- Require `RecvError` handling to only reset lightweight timers/retry state, never call `closeTunnel`/`DeleteHostInfo`, unless corroborated by an authenticated signal (e.g., only accept it as a hint to retry the handshake, and let the encrypted handshake/dead-tunnel-detection logic make the actual teardown decision).
- If teardown-on-`RecvError` must be kept, bind acceptance to something an attacker can't forge, e.g. requiring the packet be delivered with a MAC/nonce derived from session state, or only honoring it from source addresses that are also currently rate-limited/validated via an existing conntrack-like mechanism.
- At minimum, harden `f.handleRecvError` so it treats an address match as weak evidence, not authorization, and rely on active tunnel testing (`connection_manager.go`) to confirm death before deleting state.

### Proof of Concept
1. Establish tunnel between `me` and `them`; note `me`'s `hostinfo.RemoteIndex` for the `them` tunnel and `them`'s current `CurrentRemote` UDP address (both learnable by any observer of traffic between the two, as `RemoteIndex` is sent in cleartext on every packet).
2. From an attacker-controlled host, craft a UDP datagram with header `Type = header.RecvError`, `RemoteIndex = <observed index>`, and send it to `me`'s listen address while spoofing the source `IP:port` to equal `them`'s `CurrentRemote` (same technique already demonstrated for `CloseTunnel` spoofing in `e2e/tunnels_test.go` lines 528-547, but targeting the `RecvError` type instead, which — unlike `CloseTunnel` — requires no valid `ConnectionState`/decryption to be accepted).
3. Observe `handleRecvError`'s only guard (`hr.IsValid() && hr != addr`) is satisfied because the spoofed source matches, causing `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` to run, with no certificate or Noise-session participation by the attacker at any point: [4](#0-3)

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```
