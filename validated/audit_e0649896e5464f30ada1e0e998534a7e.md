### Title
Attacker can fill the fee collector's per-account token list via dust `DepositToken` transfers, causing `UserReachedMaxTokens` reverts that DoS all fee-bearing liquidations - (File: contracts/Pool.sol)

### Summary
The CVE analog is a bounded accumulator that crashes the service once a hard size limit is reached. In Metronome, `Pool` keeps per-account `MappedEnumerableSet` lists (`depositTokensOfAccount`, `debtTokensOfAccount`) capped at `MAX_TOKENS_PER_USER = 30`. Every `DepositToken._transfer`/`_mint` for a first-time holder calls `pool.addToDepositTokensOfAccount`, which reverts with `UserReachedMaxTokens` when the recipient's combined list already holds 30 entries. Because `Pool.liquidate` transfers the protocol fee to the fixed `_poolRegistry.feeCollector()` via `depositToken_.seize(...)`, an attacker can dust-fill the fee collector's list so that every liquidation carrying a protocol fee reverts, blocking liquidation of that collateral until a slot is freed.

### Finding Description
- `onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (`Pool.sol:143-148`).
- `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` when the recipient's balance was zero (`DepositToken.sol:517-520`). `seize` routes through this same transfer path, so the check applies to liquidation proceeds too.
- `Pool.liquidate` performs two `seize` calls: one to the liquidator and, when `_fee > 0`, one to `feeCollector()` (`Pool.sol:589-593`). Either recipient having a full token list reverts the entire liquidation.
- Attack path (unprivileged EOA only): for each listed deposit token `i` (up to 30), the attacker deposits a dust amount of underlying via `DepositToken.deposit`, then calls `transfer(feeCollector, dust)`. Each first-time transfer appends to `depositTokensOfAccount[feeCollector]`. Once the list reaches 30 entries, any liquidation where `feeProvider.liquidationFees().protocolFee > 0` and the seized collateral is a token the collector doesn't already hold reverts — actually, once the list is full it reverts for *any* collateral whose balance at the collector is zero; for tokens already in the list the add is skipped, so the attacker must hold dust of *every* deposit token in the collector's list.
- The same griefing applies to an individual victim: filling a victim's list prevents them from receiving new deposit-token types (blocking `deposit` into a new collateral, e.g. to rescue a declining-health position) and prevents anyone transferring msdTOKENs to them.

### Impact Explanation
- Liquidation liveness: all liquidations with a nonzero protocol fee revert while the collector's list is full, allowing bad debt to accumulate — temporary freezing of a protocol-critical function and potential insolvency under fast price moves.
- User-level griefing: a victim cannot onboard new collateral types or receive deposit-token transfers; existing balances remain withdrawable, so funds are not permanently frozen.
- Mitigations: the fee collector can free a slot by zeroing a balance (transfer/withdraw triggers `removeFromDepositTokensOfAccount`), so the DoS is temporary and depends on the fee collector's ability to move tokens; effectiveness also requires the pool to list ~30 deposit tokens, which is a deployment-dependent precondition.

### Likelihood Explanation
Cost is roughly 30 dust deposits plus transfers across 30 listed collateral types — moderate but permissionless. The attack only works if the pool actually has ≥30 deposit tokens registered, and impact is capped because debt-token entries can't be pushed to a victim (debt is self-minted) and the collector/victim can always empty a slot. Conditional, medium-low likelihood.

### Recommendation
- Move the `MAX_TOKENS_PER_USER` check out of the transfer/mint path for protocol-internal recipients: skip `addToDepositTokensOfAccount` when `recipient_ == feeCollector()` (or track the collector's position value without the per-account set), and/or make `seize`'s fee leg not revert on a full list.
- Alternatively, bound-list overflow should degrade gracefully (e.g., `try/catch` around the add, or lazily track reward-relevant tokens only) rather than reverting state-changing operations like `liquidate` and `withdraw`.

### Proof of Concept
Foundry sketch (fork of a pool with ≥30 deposit tokens and `protocolFee > 0`):

```solidity
// contracts/DepositToken.sol: _transfer adds recipient to list
// contracts/Pool.sol: liquidate -> depositToken_.seize(account_, feeCollector, _fee)

function test_liquidationDos_feeCollectorListFull() public {
    // 1. Attacker deposits dust of each of the 30 deposit tokens and
    //    transfers it to the fee collector so its list is full.
    for (uint i; i < 30; ++i) {
        IDepositToken dt = pool.getDepositTokens()[i];
        deal(address(dt.underlying()), attacker, 1e6);
        IERC20(dt.underlying()).approve(address(dt), 1e6);
        dt.deposit(1);                       // mints msdToken to attacker
        dt.transfer(feeCollector, 1);        // pushes token i into collector's list
    }
    assertEq(pool.getDepositTokensOfAccount(feeCollector).length, 30);

    // 2. Make victim unhealthy (price drop via oracle or time/accrual).
    vm.mockCall(address(masterOracle), abi.encodeWithSelector(IMasterOracle.quoteTokenToUsd.selector), abi.encode(lowPrice));

    // 3. Any liquidation paying a protocol fee reverts.
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    pool.liquidate(msETH, victim, repayAmount, msdWETH);
}
```

Uncertainties I could not fully verify from the index: the exact body of `DepositToken.seize` (assumed to route through `_transfer`, consistent with `_withdraw`'s fee leg doing so at `DepositToken.sol:546-548`), the per-deployment count of registered deposit tokens, and whether the deployed `feeCollector` is a contract able to zero balances. If `seize` bypasses the per-account list bookkeeping or no deployment reaches 30 deposit tokens, the finding degrades to the weaker victim-side deposit/receive griefing only.
