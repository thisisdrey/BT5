## Title
Outbound bridge delivery receipts finalize relayer reward and close pending orders without checking dispatch `success`, permanently losing funds on failed Ethereum-side execution - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
`Pallet::process_delivery_receipt` in `snowbridge-pallet-outbound-queue-v2` decodes a `DeliveryReceipt` whose `success` field reflects whether the Ethereum Gateway actually dispatched the bridged command successfully, but the function never inspects that flag before paying the relayer's fee and permanently deleting the `PendingOrder` for the nonce. [1](#0-0)  This is confirmed by the `DeliveryReceipt` struct explicitly carrying `success: bool` decoded from the Ethereum `InboundMessageDispatched` event, yet `process_delivery_receipt` reads only `receipt.gateway`, `receipt.reward_address`, and `receipt.nonce`. <cite repo="Lauraivanka/polkadot-sdk--038" path="bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs" start="10-27" end="10-27" />

## Finding Description
The lifecycle is: `do_process_message` computes a static worst-case `gas` estimate per command via `T::GasMeter::maximum_dispatch_gas_used_at_most(&command)` and inserts a `PendingOrder{nonce, fee, block_number}` into `PendingOrders` storage. [2](#0-1)  The Ethereum Gateway later attempts to dispatch the command with at most this pre-computed gas; if the actual command execution reverts on Ethereum, the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`. <cite repo="Lauraivanka/polkadot-sdk--038" path="bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs" start="10-12" end="10-12" /> A relayer submits this truthful, verified event via `submit_delivery_receipt`, which verifies the proof, decodes the `DeliveryReceipt`, and calls `process_delivery_receipt`. [3](#0-2) 

`process_delivery_receipt` checks `T::GatewayAddress::get() == receipt.gateway`, resolves the reward account, fetches the `PendingOrder` by nonce, pays `order.fee` via `T::RewardPayment::register_reward`, and unconditionally calls `<PendingOrders<T>>::remove(nonce)` — without ever branching on `receipt.success`. [4](#0-3)  There is no other storage item in this pallet that records a failed dispatch for retry or refund; once `PendingOrders::remove(nonce)` executes, the message's fate is permanently sealed. The gas figures used for estimation are static, worst-case constants keyed only on command type (e.g., `UnlockNativeToken => 200_000`, `CallContract => gas_limit` from message data), which is exactly the class of heuristic estimate that can diverge from real Ethereum execution cost. [5](#0-4) 

Existing tests only exercise the `success: true` path (`assert_ok!(EthereumOutboundQueueV2::process_delivery_receipt(relayer, receipt))` with `success: true`), confirming no code path or test exists for `success: false` handling. [6](#0-5) 

## Impact Explanation
Assets bridged from AssetHub to Ethereum are withdrawn on the Polkadot side (`pallet_assets::Event::Withdrawn`) before Ethereum-side confirmation, and the message is queued with an assigned `PendingOrder`. [7](#0-6)  If the Ethereum Gateway dispatch of the corresponding command reverts (`success=false`) due to gas underestimation or a crafted payload, the pallet still pays the relayer and irreversibly deletes the `PendingOrder`, with no refund or retry path — a permanent loss of the bridged funds. This matches the "permanent user-fund or bridge-state lock" impact category in the accepted impact gate.

## Likelihood Explanation
No malicious relayer, admin, or governance action is required. The relayer is submitting a cryptographically verified, truthful proof of the real Ethereum-side event log. Any transaction whose real gas cost exceeds `maximum_dispatch_gas_used_at_most`'s static estimate (state-dependent SSTORE costs, EIP-150 63/64 gas forwarding on nested calls, or a payload/target crafted to consume more gas than the constant estimate) deterministically triggers this path once relayed.

## Recommendation
Branch on `receipt.success` in `process_delivery_receipt`. On failure, do not treat the corresponding `PendingOrder` as fully resolved — transition it to a distinct failed/retryable state or trigger a refund path crediting the original sender, so that already-withdrawn assets are not permanently stranded. Only pay the relayer reward and clear the order unconditionally when success is confirmed (or provide separate compensation for verification work regardless of dispatch outcome, without discarding the underlying settlement state).

## Proof of Concept
1. On AssetHub, initiate a transfer to Ethereum causing `snowbridge-pallet-outbound-queue-v2::do_process_message` to withdraw the asset and insert `PendingOrders[nonce]` with `gas` from `T::GasMeter::maximum_dispatch_gas_used_at_most`. [2](#0-1) 
2. Simulate/trigger an Ethereum Gateway dispatch that reverts due to gas underestimation, producing `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer calls `submit_delivery_receipt` with a valid proof of this event; `DeliveryReceipt::try_from` decodes `success: false` correctly. [8](#0-7) 
4. `process_delivery_receipt` still pays the relayer and removes `PendingOrders[nonce]`, identical to the passing `success: true` test flow. [9](#0-8) 
5. No storage state remains to reissue or refund the failed transfer — the withdrawn AssetHub funds are permanently unrecoverable.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

impl GasMeter for ConstantGasMeter {
	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64 {
		match command {
			Command::SetOperatingMode { .. } => 40_000,
			Command::Upgrade { initializer, .. } => {
				// total maximum gas must also include the gas used for updating the proxy before
				// the the initializer is called.
				50_000 + initializer.maximum_required_gas
			},
			Command::UnlockNativeToken { .. } => 200_000,
			Command::RegisterForeignToken { .. } => 1_200_000,
			Command::MintForeignToken { .. } => 100_000,
			Command::CallContract { gas: gas_limit, .. } => *gas_limit,
		}
	}
}

	type Error = DeliveryReceiptDecodeError;

		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
