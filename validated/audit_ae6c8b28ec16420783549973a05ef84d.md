### Title
Attacker can permanently lock an unhealthy account’s collateral slots with dust `DepositToken` transfers, blocking recovery deposits and new collateral positions - ([File: `contracts/Pool.sol`])

### Summary
Metronome limits each account to 30 combined debt and deposit-token positions. `DepositToken.transfer()` and `transferFrom()` allow any holder to send dust to a victim, and `_transfer()` adds that token to the victim’s account list. Once the list reaches `MAX_TOKENS_PER_USER`, `Pool.addToDepositTokensOfAccount()` reverts, causing first-time deposits of every other collateral token to revert. If the victim is already unhealthy, all collateral balances are locked by `_revertIfLocked()`, so the victim cannot remove the dust entries and cannot deposit a new collateral type to restore health.

### Finding Description
`Pool` enforces `MAX_TOKENS_PER_USER = 30` across `debtTokensOfAccount` and `depositTokensOfAccount`. [1](#0-0)  The `onlyIfAdditionWillNotReachMaxTokens` modifier reverts once the combined account lists reach that cap. [2](#0-1) 

An attacker can add entries to another account without that account’s consent by transferring dust. `DepositToken.transfer()` checks only the sender’s locked balance and then calls `_transfer()`. [3](#0-2)  `_transfer()` adds the deposit token to the recipient’s account list whenever the recipient previously had a zero balance. [4](#0-3) 

This normally does not permanently freeze a solvent account because the recipient can transfer the dust back out. However, when the account has debt and no excess issuable collateral, `unlockedBalanceOf()` returns zero, and `_revertIfLocked()` blocks any withdrawal or transfer. [5](#0-4) [6](#0-5) 

The account then cannot clear attacker-added collateral slots. `DepositToken.deposit()` succeeds for a new collateral only if `_mint()` can call `Pool.addToDepositTokensOfAccount()`, which now reverts with `UserReachedMaxTokens`. [7](#0-6) [8](#0-7)  Liquidation remains callable against the trapped position. [9](#0-8) 

### Impact Explanation
On a pool with enough listed deposit tokens to reach the account cap, an attacker can grief a leveraged account by filling every remaining account-list slot with dust before or while the position becomes unhealthy. The victim is then unable to deposit any previously unused collateral type to improve health, while liquidators can still liquidate the position.

This is a state-based availability violation rather than a gas exhaustion issue: a valid user action—depositing supported collateral to recover a position—is made impossible by unsolicited transfers. Existing collateral is already subject to protocol lock rules when unhealthy, but the attacker extends that lock to the recovery path by occupying the finite collateral-slot list.

### Likelihood Explanation
The attack requires the pool to expose enough distinct `DepositToken` contracts for the attacker to push the victim to 30 combined entries. `Pool.addDepositToken()` itself allows up to `MAX_TOKENS_PER_USER` deposit-token offerings. [10](#0-9) 

The attacker must own or obtain a dust balance of each targeted deposit token and must execute before the victim restores health. The attack is most reliable when timed around a liquidation, because an unhealthy victim cannot remove the dust entries. No privileged role, malicious oracle, governance action, or forged cross-chain message is required.

### Recommendation
Do not count unsolicited dust balances against `MAX_TOKENS_PER_USER`, or allow users to remove/forfeit dust positions even when collateral is locked. Prefer an opt-in collateral list, a minimum account-listing threshold tied to material value, or a dedicated account action that removes zero-value/dust entries after proving the amount does not affect health.

### Proof of Concept
Foundry-style sequence against a fork with 30 supported deposit tokens:

```solidity
function testDustFillsAccountSlotsAndBlocksRecovery() public {
    // Victim has debt and account list has N entries.
    // Attacker owns dust balances in every deposit token not held by victim.

    IDepositToken[] memory tokens = pool.getDepositTokens();

    for (uint256 i; i < tokens.length; ++i) {
        IDepositToken dt = tokens[i];
        if (dt.balanceOf(victim) == 0) {
            dt.transfer(victim, 1);
        }
        if (pool.getDepositTokensOfAccount(victim).length +
            pool.getDebtTokensOfAccount(victim).length == 30) {
            break;
        }
    }

    assertEq(
        pool.getDepositTokensOfAccount(victim).length +
            pool.getDebtTokensOfAccount(victim).length,
        30
    );

    // Move market/price condition or use an already unhealthy victim.
    // All deposit-token balances are now locked, so victim cannot remove dust.
    vm.startPrank(victim);
    vm.expectRevert(IDepositToken.NotEnoughFreeBalance.selector);
    tokens[0].transfer(attacker, 1);

    // First deposit of any collateral not already held reverts.
    IERC20 underlying = tokens[0].underlying();
    underlying.approve(address(tokens[0]), 1 ether);
    vm.expectRevert(IPool.UserReachedMaxTokens.selector);
    tokens[0].deposit(1 ether, victim);
    vm.stopPrank();

    // Liquidator can still call Pool.liquidate on the unhealthy victim.
}
```
