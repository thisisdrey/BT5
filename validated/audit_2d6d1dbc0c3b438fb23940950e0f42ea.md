### Title
Unbounded attacker-forced growth of a victim's per-account token list (dust `DepositToken` transfers) permanently blocks the victim's deposits/borrows - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
Analogous to the Next.js unbounded disk-cache report, Metronome lets an unprivileged attacker grow a *victim's* bounded resource — the `depositTokensOfAccount` / `debtTokensOfAccount` sets capped at `MAX_TOKENS_PER_USER = 30` — by sending dust `DepositToken` transfers to an arbitrary recipient. Once the set is full, every subsequent first-time receipt mints/transfers revert in `Pool.addToDepositTokensOfAccount`, so the victim cannot deposit any new collateral type or receive new deposit/debt tokens until they fully empty a slot, and `seize`/liquidation payouts to a targeted liquidator address can be selectively reverted.

### Finding Description
`DepositToken._transfer` adds the token to the recipient's per-account set whenever the recipient's balance goes `0 → >0`, with no opt-in and no minimum amount:

- `contracts/DepositToken.sol:518-520` — `if (_recipientBalanceBefore == 0 && amount_ > 0) pool.addToDepositTokensOfAccount(recipient_);`
- `contracts/DepositToken.sol:486-488` — same path via `_mint` (`deposit(...)` / `seize(...)`).
- `contracts/Pool.sol:143-148` — `onlyIfAdditionWillNotReachMaxTokens` reverts with `UserReachedMaxTokens` once `debtTokensOfAccount + depositTokensOfAccount == 30`.
- `contracts/Pool.sol:216-220` — `addToDepositTokensOfAccount` is callable by any registered `DepositToken`; the only check is the cap.
- `contracts/Pool.sol:204-208` — symmetric `addToDebtTokensOfAccount` gates `DebtToken.issue`, so a filled list also blocks the victim from borrowing a *new* synthetic asset.

Attack: for each registered `DepositToken` the attacker deposits a minimal amount (or uses `SmartFarmingManager`/gateway flows), then `transfer(victim, 1 wei)` per token. Each call pushes a distinct entry into `depositTokensOfAccount[victim]`. With N ≥ 30 deposit/debt tokens registered, the victim's list is saturated.

### Impact Explanation
Once saturated, `UserReachedMaxTokens` reverts inside `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`, which bubbles up through `DepositToken._transfer`/`_mint`. Consequences:

- The victim cannot deposit any collateral type they don't already hold (`deposit()` → `_mint` → revert), and cannot `issue` debt in a new synthetic asset — temporary freezing of protocol functionality for that account.
- `seize()` uses the same `_transfer` path, so an attacker can pre-fill a known liquidator bot's address; liquidation `seize` calls to that address revert for any deposit token the liquidator doesn't already hold, degrading liquidation liveness for targeted liquidators.
- The victim must spend gas (and possibly realize withdrawal fees / lock constraints via `_revertIfLocked`) to fully zero out a dust balance before regaining functionality — a forced griefing cost the victim never consented to, since inbound `transfer`/`transferFrom`/`seize`/`deposit onBehalfOf` cannot be refused.

### Likelihood Explanation
Cost is minimal: 1 wei of each deposit token plus transfer gas; the attacker can seed the positions themselves via `deposit()` (the dust stays locked in their own balance only if they have debt — they can use a fresh EOA per token or repaid accounts). Any EOA can execute it with no privileged role. Feasibility depends only on the pool having enough registered deposit/debt tokens to reach 30 combined entries against the victim's existing holdings; the mechanism itself is unconditional. The victim can recover by emptying a slot, so the freeze is temporary rather than permanent — but it can be re-applied continuously at low cost.

### Recommendation
- Whitelist additions: only push to `depositTokensOfAccount` on `deposit()`/`seize()` (protocol-initiated mints), not on peer `transfer`/`transferFrom`; or require recipient opt-in for unsolicited transfers.
- Alternatively, evict zero-value slots or make the cap check compare only *non-dust* entries, and/or make `seize`/`_mint` skip `addToDepositTokensOfAccount` revert (emit + track best-effort) so liquidation payouts cannot be bricked.
- If keeping the current design, at minimum add a recipient-side `sweep` helper that lets a user cheaply zero dust balances in one call.

### Proof of Concept
Foundry/Hardhat sketch (Hardhat, existing test harness style):

```ts
// Pool has >= 30 registered deposit tokens dT[0..29]; victim holds none.
for (let i = 0; i < 30; i++) {
  // attacker: deposit minimal underlying then dust-transfer to victim
  await underlying[i].approve(dT[i].address, 1);
  await dT[i].deposit(1, attacker.address);
  await dT[i].transfer(victim.address, 1); // _transfer -> addToDepositTokensOfAccount(victim)
}
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(30);

// victim tries to deposit a new collateral type (or receives any new deposit token)
await expect(dT_new.connect(victim).deposit(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim borrowing a new synthetic also reverts via addToDebtTokensOfAccount
await expect(debtToken.connect(victim).issue(1, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

The revert originates in `Pool.onlyIfAdditionWillNotReachMaxTokens` (`contracts/Pool.sol:143-148`) reached from `DepositToken._transfer` (`contracts/DepositToken.sol:518-520`) / `_mint` (`contracts/DepositToken.sol:486-488`) and `DebtToken.issue` → `addToDebtTokensOfAccount` (`contracts/Pool.sol:204-208`).
