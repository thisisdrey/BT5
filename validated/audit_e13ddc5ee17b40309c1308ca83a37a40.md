Exact-match order fill in `MarketSellAssetActuator` credits the taker with the maker's full remaining asset while a rounding-truncated payment can be zero, letting a taker drain a maker's resting order for free - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes the amount a taker must pay the maker (`makerBuyTokenQuantityReceive`) via integer division (`MarketUtils.multiplyAndDivide`), and the amount the taker unconditionally receives (`takerBuyTokenQuantityReceive`) as the maker's *entire* remaining sell quantity — exactly the same class of bug described in the external report, where an unvalidated/rounded fill amount can compute to zero while the taker still receives the full asset. The code base is aware of this exact failure mode: the sibling "taker > maker" branch explicitly checks `if (makerBuyTokenQuantityReceive == 0)` and refunds the maker instead of letting the trade proceed, but the "taker == maker" branch has no such check.

### Finding Description
In `matchSingleOrder` [1](#0-0) , after confirming `takerBuyTokenQuantityRemain != 0` [2](#0-1) , three branches handle the match. In the exact-match ("taker == maker") branch:

```
makerBuyTokenQuantityReceive = MarketUtils
    .multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...);
takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain();

long takerSellTokenLeft =
    takerOrderCapsule.getSellTokenQuantityRemain() - makerBuyTokenQuantityReceive;
takerOrderCapsule.setSellTokenQuantityRemain(takerSellTokenLeft);
makerOrderCapsule.setSellTokenQuantityRemain(0);
``` [3](#0-2) 

`makerBuyTokenQuantityReceive` is derived by `multiplyAndDivide`, which truncates fractional results to zero when `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity`. Unlike the "taker > maker" branch just below, which explicitly checks for this zero-result case and refunds the maker's remaining sell tokens instead of completing the trade [4](#0-3) , the "taker == maker" branch performs no such check. If `makerBuyTokenQuantityReceive` rounds to `0`:
- `makerOrderCapsule.setSellTokenQuantityRemain(0)` marks the maker's order as fully consumed.
- `takerOrderCapsule`'s remaining sell balance is reduced by `0` (i.e., unchanged) — the taker pays nothing.
- Both accounts are then credited via `addTrxOrToken`, giving the taker the maker's *entire* remaining sell-side asset while the maker receives `0` of the taker's asset: `addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, takerAccountCapsule); addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive);` [5](#0-4) 

This mirrors the reported issue's root cause precisely: an amount that can legitimately compute to zero (there, an unchecked callback return value; here, integer-division truncation) is used to move value in one direction while the other direction's transfer proceeds unconditionally for the full counter-asset amount.

### Impact Explanation
Any account can place a `MarketSellAssetContract` order (`fillDCA`-equivalent entry point is `MarketSellAssetActuator.execute`) that is sized to land on this exact-match branch against a resting maker order whose remaining quantity, multiplied by the price ratio, truncates to zero. The attacker (taker) receives the maker's full remaining asset balance for that order while paying zero counter-asset, and the maker's order is marked `INACTIVE`/fully consumed with no compensation. This is a direct theft of maker funds reachable by any unprivileged transaction broadcaster with no special privileges, matching "unauthorized account operation / theft of funds."

### Likelihood Explanation
Reaching the vulnerable state requires crafting a taker sell order whose `sellTokenQuantityRemain` yields (via `multiplyAndDivide` using the maker's sell/buy quantities) a `takerBuyTokenQuantityRemain` exactly equal to the maker's `sellTokenQuantityRemain`, while the reverse ratio computation (`makerBuyTokenQuantityReceive`) truncates to zero. Because market orders are user-controlled (arbitrary `sellTokenQuantity`/`buyTokenQuantity`/timing of partial fills), and TRON asset quantities can be arbitrarily large or small integers, an attacker can search the resting order book (public state) for a maker order whose remaining quantity satisfies this rounding condition, or can create their own two cooperating orders (self-matching) to deterministically construct the exact-match + zero-payment condition, making exploitation practical rather than theoretical.

### Recommendation
Add the same zero-result guard used in the "taker > maker" branch to the "taker == maker" branch: if `makerBuyTokenQuantityReceive == 0`, do not consume the maker's remaining sell balance; instead treat the match as too small, return the maker's remaining asset via `MarketUtils.returnSellTokenRemain` (or an equivalent per-side check), and prevent the unconditional `addTrxOrToken` credit to the taker in that scenario. More generally, before crediting either side in `matchSingleOrder`, both `takerBuyTokenQuantityReceive` and `makerBuyTokenQuantityReceive` should be validated to be non-zero (or the match rejected/adjusted), consistent with the fix pattern in the external report (`require curTakerFillAmount > 0`).

### Proof of Concept
Conceptual reproduction using `MarketSellAssetActuator`:
1. Maker places order: sell 100 of token A for 1 of token B (`sellTokenQuantity=100`, `buyTokenQuantity=1`), and it is partially filled by other trades so that `sellTokenQuantityRemain` becomes some small remainder R such that `R * 1 < 100` (e.g., R = 50) — this order sits in the book with `makerSellQuantity=100`, `makerBuyQuantity=1`, `makerSellRemainQuantity=50`.
2. Attacker (taker) submits a `MarketSellAssetContract` selling token B for token A with a `sellTokenQuantity` chosen so that `takerBuyTokenQuantityRemain = multiplyAndDivide(takerSellRemainQuantity, makerSellQuantity(100), makerBuyQuantity(1))` equals exactly `50` (the maker's remaining amount), driving execution into the "taker == maker" branch in `matchSingleOrder`.
3. In that branch, `makerBuyTokenQuantityReceive = multiplyAndDivide(50, 1, 100) = 0` (since `50*1 < 100`, truncated to zero), while `takerBuyTokenQuantityReceive = 50` (the maker's full remaining token A).
4. Execution proceeds: `makerOrderCapsule.setSellTokenQuantityRemain(0)` (maker order fully consumed), `takerOrderCapsule`'s remaining balance is reduced by `0` (attacker pays nothing), then `addTrxOrToken(takerOrderCapsule, 50, takerAccountCapsule)` credits the attacker 50 units of token A, and `addTrxOrToken(makerOrderCapsule, 0)` credits the maker nothing — the attacker has stolen the maker's 50 units of token A for zero cost.

Exact numeric values satisfying the equality constraint depend on `MarketUtils.multiplyAndDivide`'s rounding behavior for both directions and would need to be brute-forced or derived precisely against the live `MarketPairToPriceStore`/`MarketPairPriceToOrderStore` state, which requires runtime testing that could not be executed in this read-only analysis; the code-level root cause (missing zero-check in the exact-match branch, present in the sibling branch) is confirmed by direct code inspection.
