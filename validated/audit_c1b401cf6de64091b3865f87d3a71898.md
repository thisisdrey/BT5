### Title
Committee-controlled `ALLOW_MARKET_TRANSACTION` disable traps already-escrowed order funds (Catch-22 fund freeze) - ([File: actuator/src/main/java/org/tron/core/actuator/MarketCancelOrderActuator.java])

### Summary
The reported SafEth issue is a design flaw where disabling a broken component (a derivative) as a defensive measure permanently locks user funds that were already deposited into it, forcing operators to choose between early fund loss or indefinite downtime. The equivalent single-point-of-control gate in java-tron is the `ALLOW_MARKET_TRANSACTION` dynamic property, which is checked by both `MarketSellAssetActuator` (creating escrowed orders) and `MarketCancelOrderActuator` (returning escrowed funds). Both actuators gate on the exact same boolean flag, so toggling it off removes the *only* path by which already-placed orders can retrieve their locked assets.

### Finding Description
When a user places a market order via `MarketSellAssetContract`, their sell-token quantity is deducted from their account and held in escrow inside a `MarketOrderCapsule`, to be released either on a future match or on cancellation.

`MarketCancelOrderActuator.validate()` is the only path back to the user for an uncanceled/unmatched order's escrowed balance, and it unconditionally requires the market feature to still be enabled: [1](#0-0) 

The same gate exists in `MarketSellAssetActuator`, which is symmetric to the SfrxEth derivative-disable case — the flag is a single global switch shared by both the entry (deposit/escrow) and exit (withdraw/cancel) paths: [2](#0-1) 

The flag itself, `ALLOW_MARKET_TRANSACTION`, is a committee-governed dynamic property adjustable via proposal (as referenced in `ProposalUtil.java` and `DynamicPropertiesStore.java`), meaning a committee decision (e.g., to react to a bug discovered in the market matching logic, similar to how the SafEth owner would disable a misbehaving derivative) can flip this value from `1` to `0` at any time.

If the committee disables `ALLOW_MARKET_TRANSACTION` — for example in response to a discovered bug in order matching, price-key comparison, or overflow in `MarketUtils` — any order that is still `ACTIVE` and has escrowed tokens becomes **permanently unretrievable** by its owner: `MarketCancelOrderActuator.validate()` will always fail with "Not support Market Transaction, need to be opened by the committee" while the flag is off, and there is no other actuator path that releases escrowed order balances. This mirrors the SafEth catch-22 exactly: the committee must choose between (1) leaving the feature disabled — guaranteeing indefinite freezing of every open order's escrowed assets — or (2) re-enabling the feature despite the underlying issue that caused them to disable it, in order to let users cancel and reclaim funds.

I was not able to fully verify within the available iterations whether `ProposalUtil.java` enforces a one-way (0→1 only) transition for `ALLOW_MARKET_TRANSACTION` that might prevent this scenario; further review of that validation logic in `actuator/src/main/java/org/tron/core/utils/ProposalUtil.java` is recommended before treating this as a confirmed, unconditionally exploitable bug.

### Impact Explanation
Any TRX/TRC10 balances escrowed in active market orders at the time `ALLOW_MARKET_TRANSACTION` is disabled become frozen with no actuator-level mechanism to release them, other than re-enabling the exact feature that prompted the disable decision. This is a permanent freezing-of-funds risk contingent on a plausible, in-scope committee governance action rather than any attacker action, consistent with a Medium-severity finding.

### Likelihood Explanation
This requires a committee proposal to toggle `ALLOW_MARKET_TRANSACTION` off after users have open orders — a realistic operational scenario (e.g., responding to an incident in the market-matching code) rather than a contrived one, since the feature is explicitly designed to be committee-toggleable.

### Recommendation
Decouple order cancellation/fund-return from the `ALLOW_MARKET_TRANSACTION` gate in `MarketCancelOrderActuator.validate()`, so that even when new order creation (`MarketSellAssetActuator`) is disabled, users can still cancel existing orders and reclaim escrowed balances. Alternatively, if the market subsystem is disabled, add a migration/reconciliation mechanism that automatically releases or reverts all `ACTIVE` orders' `sellTokenQuantityRemain` back to owners rather than leaving them permanently gated behind the same disabled flag.

### Proof of Concept
1. User A calls `MarketSellAssetContract` while `ALLOW_MARKET_TRANSACTION = 1`; `sellTokenQuantity` is escrowed in a `MarketOrderCapsule` and removed from A's account balance.
2. Committee passes a proposal setting `ALLOW_MARKET_TRANSACTION = 0` (e.g., due to a discovered matching-logic bug).
3. User A submits `MarketCancelOrderContract` to reclaim the escrowed tokens; `MarketCancelOrderActuator.validate()` throws `"Not support Market Transaction, need to be opened by the committee"` [3](#0-2) .
4. As long as the committee keeps the feature disabled (to avoid the underlying bug), User A's escrowed funds remain permanently locked, with re-enabling the only exit — reproducing the SafEth catch-22 (fund loss vs. re-exposure to the disabled risk) in java-tron's market subsystem.
