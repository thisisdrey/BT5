### Title
Unbounded Array Allocation in TVM Precompiled Contract Signature-Batch Helpers Leads to Memory Exhaustion - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The helper functions `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` allocate Java arrays whose size is taken directly from a 256-bit word embedded in TVM call data, with no upper bound check before the allocation occurs. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
Each of these helper functions reads a "length" word from the ABI-encoded call data via `words[offset].intValueSafe()` and immediately uses it as the size of a newly allocated `byte[][]` array (e.g. `new byte[len][]`), before validating that `len` is within any sane bound relative to the actual size of the supplied `data`/`words` array: [1](#0-0) 

This mirrors the reported bug class (attacker-controlled size field drives unbounded memory allocation, e.g. a PSD header's declared dimensions/plane count driving buffer allocation before validating against the actual file size). Here, the "file" is the TVM call data of a precompiled-contract invocation, and the "size field" is a 256-bit word decoded via `intValueSafe()`, which can be attacker-chosen up to a large positive int value; the subsequent `for` loop then indexes `words[offset + i + 1]`, which would throw quickly on out-of-bounds access, but the array allocation itself (`new byte[len][]`) happens first and can already be large enough to pressure or exhaust heap memory before the bounds violation is detected.

### Impact Explanation
An unprivileged party can trigger this simply by deploying or calling a contract that invokes the affected TVM precompiled contract with a crafted call data, causing the node executing/validating that transaction (and every full node in the network, since TVM execution is deterministic and re-executed by all nodes during block validation) to attempt a very large array allocation. Repeated or well-tuned invocations can force `OutOfMemoryError` conditions, degrading or crashing node processes — a memory-exhaustion denial-of-service directly analogous to the Mattermost PSD report.

### Likelihood Explanation
Reachability is high in principle: precompiled contracts are invoked via ordinary `CALL`/`STATICCALL` from any deployed smart contract, meaning any transaction broadcaster can reach this code path. However, I was not able to fully confirm within the available tool budget (a) which specific precompiled contract(s) actually invoke `extractBytes32Array`/`extractBytesArray`/`extractSigArray` (my searches for call sites of these three methods did not return results, possibly due to index limitations), and (b) the exact semantics of `DataWord.intValueSafe()` (i.e., whether it already clamps the returned value to a small/safe bound). Both of these are necessary to confirm actual exploitability versus a merely theoretical code smell.

### Recommendation
Add an explicit upper-bound check on `len` immediately after decoding it in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` (e.g., bound it by `words.length - offset` or a fixed maximum item count) before performing the `new byte[len][]` allocation, so that malformed/oversized length fields are rejected before any large allocation occurs — analogous to the `verifyLength()` bounds check already used in `RLP.java`'s `fullTraverse`/`decode` methods. ### Proof of Concept
Conceptual: construct a transaction that calls a contract which in turn invokes the precompiled contract using `extractBytes32Array`/`extractBytesArray` (offset word set to a very large value, e.g. close to `Integer.MAX_VALUE`), causing an oversized `byte[len][]` allocation attempt during TVM execution/validation on every node re-executing the transaction. I was unable to fully verify the exact precompile entry point and `intValueSafe()` clamping behavior within the available investigation budget — a background Devin session with full repo access would be needed to trace the exact call sites and confirm the concrete exploit path with a runnable PoC.

**Note on confidence**: Because I could not verify the callers of these three helper methods nor the exact clamp bound of `intValueSafe()`, this finding should be treated as a plausible but not fully confirmed analog. If you want certainty, a follow-up investigation (or a Devin session with full-repo access, since the codebase index has size limits and may exclude some file contents) should trace all call sites of `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, and inspect `DataWord.intValueSafe()`'s implementation directly.
