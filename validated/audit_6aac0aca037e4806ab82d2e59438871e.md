### Title
Unauthenticated `RecvError` packets allow UDP source-spoofed remote attackers to force-close active tunnels between other authenticated peers - (File: outside.go)

### Summary
`handleRecvError` in `outside.go` processes the `header.RecvError` packet type completely outside of the Noise handshake / certificate-verification path. Any attacker who can send a raw UDP packet to a node's listener — with **no CA-signed certificate, no handshake, and no cryptographic authentication of the message itself** — can trigger `f.closeTunnel(hostinfo)`, tearing down a tunnel that belongs to two other, fully-authenticated peers, as long as the spoofed source UDP address matches the tunnel's current remote endpoint.

### Finding Description
`RecvError` is handled at the very top of `readOutsidePackets`, before any hostinfo lookup that would require a valid `ConnectionState`/certificate: [1](#0-0) 

The actual handler only checks a config toggle and a coarse address match — there is no MAC, no signature, no nonce tied to the sender's identity on this packet type: [2](#0-1) 

The only "authentication" performed is `hr.IsValid() && hr != addr` — i.e., it merely checks that the UDP source address of the (unauthenticated, unencrypted) `RecvError` packet equals the `HostInfo`'s currently recorded remote `netip.AddrPort`. Because UDP allows trivial source-address spoofing, an off-path attacker who can determine (or guess/observe) the `RemoteIndex` and the current UDP endpoint of a live tunnel can spoof that source address and index to pass this check, causing:
- `f.closeTunnel(hostinfo)` — destroying the tunnel for both legitimate peers.
- `f.handshakeManager.DeleteHostInfo(hostinfo)` — clearing the pending-handshake side, accelerating the disruption further.

This is functionally the same bug class as the report's `ServiceNft::updateImpact`: a state-mutating operation that is intended to be trustworthy/consensus-gated (in Nebula's case, "this peer told us they lost the tunnel") is instead reachable by an arbitrary network attacker with none of the expected authentication (no CA-signed certificate, no valid handshake), and it corrupts shared state (the tunnel/hostmap) that affects two other legitimate parties rather than only the attacker.

### Impact Explanation
An attacker with no certificate can repeatedly force-close arbitrary established tunnels between legitimate nodes by spoofing UDP source addresses and guessing/observing `RemoteIndex` values, causing persistent denial of service and forced re-handshakes across the mesh (`am_lighthouse` nodes and relays included). This is a remote, unauthenticated availability/state-poisoning impact reachable without holding any valid Nebula certificate, matching the "remote crash/state poisoning" acceptance criteria.

### Likelihood Explanation
The changelog shows this exact risk was already acknowledged by the project (`listen.send_recv_error` / `accept_recv_error` toggles, #670, #1569), but the toggle's default policy governs whether the *sender* emits `RecvError` messages and whether the *receiver* accepts them from a given policy set (e.g., "always")— the underlying validation performed in `handleRecvError` remains a same-source-address check on an unauthenticated packet type rather than a cryptographic proof of peer identity. `RemoteIndex` is a 32-bit value assigned at handshake time and is observable to any party that can see the wire traffic (e.g., a network intermediary, misrouted relay, or an on-path/near-path observer), making exploitation plausible for a targeted DoS, especially in environments without additional network-layer anti-spoofing (e.g., BCP38) protections.

### Recommendation
Do not allow an unauthenticated `RecvError` packet type to unilaterally cause `closeTunnel`/`DeleteHostInfo`. At minimum:
- Require the `RecvError` message to be authenticated (e.g., MAC'd with the tunnel's derived key, or sent as an encrypted `Message`/`Control` type over the established Noise session) rather than relying solely on UDP source-address comparison.
- If backward compatibility with the current wire format is required, treat unauthenticated `RecvError` as a soft hint only (e.g., trigger a re-verification handshake attempt) rather than an immediate, unilateral tunnel teardown.

### Proof of Concept
1. Node `A` and Node `B` establish an authenticated tunnel; attacker `E` observes network traffic (or otherwise learns) `B`'s current UDP endpoint and the `RemoteIndex` `A` uses for `B`'s tunnel (visible in cleartext packet headers on the wire since headers are unencrypted, per `header.H.Parse`).
2. `E` crafts a raw UDP packet with `header.RecvError` type and `RemoteIndex` set to the observed index, spoofing the source address to `B`'s UDP endpoint, and sends it to `A`.
3. `A`'s `handleRecvError` (outside.go:541) finds the hostinfo via `QueryReverseIndex`, sees `hr == addr` (spoofed to match), and calls `f.closeTunnel(hostinfo)` plus `DeleteHostInfo`, tearing down the legitimate tunnel between `A` and `B` — with `E` never having presented a CA-signed certificate or completed any handshake. func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
