### Title
Unsolicited StackerDB chunk handler advertises a chunk as stored in its inventory reply before the chunk is actually committed to the StackerDB - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` patches the `StackerDBChunkInv` slot-version entry to reflect the *incoming* pushed chunk's version and sends that inventory back to the peer as an acknowledgment/reply, before the chunk has actually been persisted via `StackerDBTx::try_replace_chunk`/`insert_chunk`. This is the same class of bug as the audited `unstake` finding: a derived/advertised value (the inventory entry) is computed and emitted based on an anticipated state change, while the actual state mutation (the DB write) happens later (and separately, in the relay pipeline) and can still fail or be skipped.

### Finding Description
In `handle_unsolicited_StackerDBPushChunk`, after `validate_received_chunk` succeeds (which only checks size, expected version, signature, and max-writes — explicitly **not** write frequency, per its own doc comment), the code does: [1](#0-0) 

i.e. it mutates `data.slot_versions[slot_id]` to the pushed chunk's version and treats the chunk as accepted, then wakes the sync state machine and — if `send_reply` is set — signs and sends this patched `StackerDBChunkInv` back to the remote peer as the acknowledgment: [2](#0-1) 

The function returns `(false, true)` meaning: don't buffer, but forward the chunk to the relayer for actual processing/storage. The chunk is never written to the `StackerDB` inside this function; the real write happens later via `try_replace_chunk`, which re-checks staleness/signature/max-writes: [3](#0-2) 

Because `validate_received_chunk` does not check write frequency (by its own documentation) and the actual commit is deferred to a separate relay-processing step, there is a window in which the node has already told the sender/network (via the signed inventory reply, and via any subsequent inventory gossip since the in-memory `data.slot_versions` entry may be reused for further `StackerDBChunkInv` construction) that it holds the chunk at the new version, while the on-disk state may not (or may never, if the later relay-triggered store fails, e.g., due to a write-frequency violation, a DB error, or the relay path dropping the message).

This breaks the same equality that the `unstake` bug broke: "advertised/derived state" vs. "actually committed state." Here, the exchange-rate analog is the inventory entry `data.slot_versions[slot_id]`, which is updated to the *new* value before the equivalent of `updateGlobalExchangeRate()`/actual storage (`try_replace_chunk`) has run.

### Impact Explanation
A peer that receives this optimistic inventory ack will believe the node has the chunk at the new version and will not re-request/re-push it, and may propagate this (false) inventory information further (StackerDB inventory gossip drives download scheduling in `stackerdb/sync.rs`). If the deferred store never completes (write-frequency check fails, or the relay pipeline drops/rejects the message for any reason), the network can end up believing a chunk is replicated when it is not, causing peers to skip downloading data that no replica actually holds — a "false inventory" condition that can stall StackerDB convergence for legitimate application data (e.g., signer messages relayed via StackerDB).

### Likelihood Explanation
This path is reachable by any peer that can open a P2P connection and send an unsolicited `StackerDBPushChunk` message — no authentication beyond an existing (unprivileged) P2P conversation is required. The write-frequency check is explicitly skipped in `validate_received_chunk`, so an attacker can trivially cause the deferred store to be rejected on write-frequency grounds after the inventory ack has already claimed acceptance, making the mismatch straightforward to trigger deliberately as well as occur organically under normal operation.

### Recommendation
Do not patch/report the slot as updated in the `StackerDBChunkInv` reply until the chunk has actually been durably stored (i.e., move the inventory patch to occur only after a successful `try_replace_chunk`/commit, mirroring the "update the source-of-truth state before deriving/advertising values from it" fix applied to the analogous `unstake` bug). If synchronous storage isn't feasible in this handler due to lock/ordering constraints, the reply should reflect only the previously-committed version until the relay path confirms the write succeeded.

### Proof of Concept
1. Attacker (a normal P2P peer with an existing connection, slot owner for `slot_id`) sends a validly signed `StackerDBPushChunk` for `slot_id` with `slot_version = N+1`, where the local write-frequency policy for that slot would reject a write this soon after the previous one (a check `validate_received_chunk` deliberately does not perform).
2. `handle_unsolicited_StackerDBPushChunk` calls `validate_received_chunk`, which returns `true` (write-frequency not checked here).
3. The handler patches `data.slot_versions[slot_id] = N+1` and, with `send_reply = true`, signs and sends this `StackerDBChunkInv` back to the attacker/peer, and separately marks the message `(false, true)` for relay-based processing.
4. The relay pipeline eventually attempts to actually store the chunk via `try_replace_chunk`; if write-frequency (checked elsewhere in the store/relay path, not in `validate_received_chunk`) or another commit-time condition fails, the chunk is never persisted.
5. The node has already advertised (via the signed reply, and consequently to any peer relying on that inventory) that it holds `slot_id` at version `N+1`, even though `get_slot_metadata`/`get_slot_versions` will still show the old version — a served-vs-committed mismatch. [4](#0-3)

    /// Validate chunk data either downloaded (with [`StackerDBSync::validate_downloaded_chunk`]), or
    /// pushed to us (with [`PeerNetwork::handle_unsolicited_StackerDBPushChunk`])
    ///
    /// NOTE: does not check write frequency, since the caller has different ways of doing this.
    /// Returns:
    /// - Ok(true) if the chunk is valid
    /// - Ok(false) if the chunk is invalid
    /// - Err(..) on DB error
    pub fn validate_received_chunk(
        &self,
        smart_contract_id: &QualifiedContractIdentifier,
        config: &StackerDBConfig,
        data: &StackerDBChunkData,
        expected_versions: &[u32],
    ) -> Result<bool, net_error> {
        // validate -- must not exceed this replica's configured chunk size.
        if (data.data.len() as u64) > config.chunk_size {
            info!(
                "Received StackerDBChunk for {} ID {}, which is oversized: {} bytes (max {} bytes)",
                smart_contract_id,
                data.slot_id,
                data.data.len(),
                config.chunk_size
            );
            return Ok(false);
        }

        // validate -- must be a valid chunk
        let Some(expected_version) = expected_versions.get(data.slot_id as usize) else {
            info!(
                "Received StackerDBChunk for {} ID {}, which is too big ({})",
                smart_contract_id,
                data.slot_id,
                expected_versions.len()
            );
            return Ok(false);
        };

        // validate -- must be signed by the expected author
        let addr = match self
            .stackerdbs
            .get_slot_signer(smart_contract_id, data.slot_id)?
        {
            Some(addr) => addr,
            None => {
                return Ok(false);
            }
        };

        let slot_metadata = data.get_slot_metadata();
        if !slot_metadata.verify(&addr)? {
            info!(
                "StackerDBChunk for {} ID {} is not signed by {}",
                smart_contract_id, data.slot_id, &addr
            );
            return Ok(false);
        }

        // validate -- must be the current or newer version
        if data.slot_version < *expected_version {
            info!(
                "Received StackerDBChunk for {} ID {} version {}, which is stale (expected {})",
                smart_contract_id, data.slot_id, data.slot_version, *expected_version
            );
            return Ok(false);
        }

        // validate -- must not exceed max writes
        if data.slot_version > config.max_writes {
            info!(
                "Write count exceeded for StackerDBChunk for {} ID {} version {} (max is {})",
                smart_contract_id, data.slot_id, data.slot_version, config.max_writes
            );
            return Ok(false);
        }

        Ok(true)
    }

        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });

            return Err(net_error::TooManySlotWrites {

                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
