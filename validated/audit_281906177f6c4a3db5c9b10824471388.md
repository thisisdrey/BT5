### Title
Relay-forwarding control message trusts attacker-supplied `RelayFromAddr` identity instead of the authenticated sender - (File: relay_manager.go)

### Summary
The external report's bug class is "an action is executed for/on behalf of an identity taken from unauthenticated request data instead of the identity that was actually verified/authenticated for the caller." In `handleCreateRelayRequest`, the relay-owner address used to create and key relay state is taken directly from the message payload (`m.RelayFromAddr`) rather than being checked against the authenticated identity of the `HostInfo` (`h`) that actually sent the control message.

### Finding Description
`relayManager.handleCreateRelayRequest` decodes `from := protoAddrToNetAddr(m.RelayFromAddr)` and `target := protoAddrToNetAddr(m.RelayToAddr)` straight out of the `NebulaControl` payload: [1](#0-0) 

It then uses `from` — an attacker-chosen field inside the control message, not the peer's certified VPN address — to install/complete/update relay state (`AddRelay`, `CompleteRelayByIP`, `UpdateRelayForByIpState`) and to answer with a `CreateRelayResponse`: [2](#0-1) 

Nowhere in this function is `from` checked against `h.vpnAddrs` (the certificate-verified identity of the peer that actually holds the authenticated tunnel `h`). The only identity checks present are that `from` is not one of *my* addresses and that `target` is/isn't me: [3](#0-2) 

This mirrors the TokTokNft pattern precisely: the function performs a state-changing operation (creating/mutating relay routing state, "claiming" a relay slot) using an identity argument supplied by the caller instead of validating that the caller *is* that identity. In TokTokNft, `tokenId` (owner-bound resource) was taken from the call arguments without checking `msg.sender == owner`; here, `RelayFromAddr` (an owner-bound relay slot keyed by VPN address) is taken from the message body without checking it against the sender's own certified `vpnAddrs`.

### Impact Explanation
A peer that has completed a handshake (and is thus a `HostInfo` known to `relayManager`) can send a `CreateRelayRequest` claiming `RelayFromAddr` = a victim's VPN address that is *not* the sender's own address. The terminal-relay branch will create/complete `Established`/`Requested` relay state under the victim's address on the responder, and reply with a `CreateRelayResponse` addressed as if it came from that victim. This lets one compromised/rogue tunnel member manipulate relay routing entries (poisoning which host is believed to be relayable and how) for an address it does not own, without any validation that it is entitled to speak "as" that address — a form of remote relay-state poisoning/spoofing analogous to the reported unauthorized "claim on behalf of another owner" bug.

### Likelihood Explanation
Reachability requires only that the calling node be a `HostInfo` in the peer's hostmap, i.e., that some handshake with that peer has completed at all (the function is invoked from `HandleControlMsg` for any established or in-progress `HostInfo`). No special privilege beyond having any tunnel to the target is needed, and the `RelayFromAddr`/`RelayToAddr` fields are fully attacker-controlled protobuf fields with no cross-check against the sender's own certified `vpnAddrs`, making exploitation straightforward for any peer able to reach the control channel.

### Recommendation
In `handleCreateRelayRequest` (and equivalently `handleCreateRelayResponse`), validate that the claimed `RelayFromAddr` corresponds to the certified VPN address(es) of the sending `HostInfo h` before using it to create or mutate relay state:
```go
if !slices.Contains(h.vpnAddrs, from) {
    logMsg.Error("RelayFromAddr does not match sender's certified vpnAddrs", "vpnAddrs", h.vpnAddrs, "claimedFrom", from)
    return
}
```
This mirrors the recommended fix in the source report — reject the operation unless the caller's authenticated identity matches the identity the operation is being performed for.

### Proof of Concept
1. Node `Evil` completes a normal handshake with node `Me` (so `Me` has a `HostInfo` for `Evil` with `Evil`'s certified `vpnAddrs = [10.0.0.5]`).
2. `Evil` sends `Me` a `Control` message of type `NebulaControl_CreateRelayRequest` with `RelayFromAddr = 10.0.0.9` (a victim's address, not `Evil`'s own) and `RelayToAddr = <Me's own address>`.
3. `Me` (being the relay target) runs `handleCreateRelayRequest`; since `f.myVpnAddrsTable.Contains(target)` is true, it calls `AddRelay(..., h, f.hostMap, from=10.0.0.9, ...)`, creating relay state keyed to `10.0.0.9` on `h` (which is really `Evil`), and sends a `CreateRelayResponse` claiming to be "from" `10.0.0.9`.
4. No check ever verifies `10.0.0.9 ∈ h.vpnAddrs` (`Evil`'s certified addresses), so relay routing state for the victim's address is created/poisoned by an unrelated peer. [4](#0-3)

func (rm *relayManager) handleCreateRelayRequest(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl) {
	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}

	// Is the target of the relay me?
	if f.myVpnAddrsTable.Contains(target) {
		existingRelay, ok := h.relayState.QueryRelayForByIp(from)
		if ok {
			switch existingRelay.State {
			case Requested:
				ok = h.relayState.CompleteRelayByIP(from, m.InitiatorRelayIndex)
				if !ok {
					logMsg.Error("Relay State not found")
					return
				}
			case Established:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
			case Disestablished:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
				// Mark the relay as 'Established' because it's safe to use again
				h.relayState.UpdateRelayForByIpState(from, Established)
			case PeerRequested:
				// I should never be in this state, because I am terminal, not forwarding.
				logMsg.Error("Unexpected Relay State found",
					"existingRemoteIndex", existingRelay.RemoteIndex,
					"state", existingRelay.State)
			}
		} else {
			_, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
			if err != nil {
				logMsg.Error("Failed to add relay", "error", err)
				return
			}
		}

		relay, ok := h.relayState.QueryRelayForByIp(from)
		if !ok {
			logMsg.Error("Relay State not found", "from", from)
			return
		}
