The structural analog exists in `DebtToken`. Let me confirm the math helpers.### Title
Interest accrual timestamp is advanced even when accrued interest rounds to zero, allowing a permissionless `accrueInterest()` caller to permanently erase debt interest — ([File: contracts/DebtToken.sol](contracts/DebtToken.sol))

### Summary
`DebtToken.accrueInterest()` is a public, unguarded function that always writes `lastTimestampAccrued = block.timestamp`, even when `_calculateInterestAccrual()` computes a zero interest amount due to `wadMul` rounding. This is the same bug class as Surge M-9: the accrual checkpoint moves forward without any interest being accumulated, so the interest for the elapsed window is lost permanently rather than deferred.

### Finding Description
In `DebtToken.sol`, `_calculateInterestAccrual()` computes `_interestRateToAccrue = interestRatePerSecond() * (block.timestamp - _lastTimestampAccrued)` where `interestRatePerSecond()` is the truncated division `interestRate / SECONDS_PER_YEAR` (line 319-321). If `_interestRateToAccrue > 0`, it then computes `_interestAmountAccrued = _interestRateToAccrue.wadMul(totalSupply_)` and `_debtIndex += _interestRateToAccrue.wadMul(_debtIndex)` (lines 559-565).

Two loss paths exist:

1. **`wadMul` rounds the interest amount to 0.** `wadMul` is `(a*b + 0.5e18) / 1e18` (WadRayMath.sol:30), so `_interestAmountAccrued` is 0 whenever `perSecondRate * dt * totalSupply_ < 0.5e18`. Because `accrueInterest()` sets `lastTimestampAccrued = block.timestamp` unconditionally (line 167) and only writes `totalSupply_`/`debtIndex` inside `if (_interestAmountAccrued > 0)` (lines 169-179), every call made while the rounding threshold is unmet discards the entire elapsed window's interest. Any EOA can call `accrueInterest()` once per block (it has no access control or reentrancy guard), keeping `dt` at ~1 block and perpetually zeroing accrual while `totalSupply_` stays below the threshold. For an 8-decimal synthetic asset such as msBTC (deployed `MsBTCDebt_Pool1`), with a 10% APR (`interestRate = 0.1e18`, per-second ≈ 3.17e9), the threshold supply is ≈ `0.5e18 / (3.17e9 * 12s) ≈ 1.3e7` units ≈ 0.13 msBTC — a non-dust debt amount paying zero interest for as long as the griefer keeps calling.
2. **`interestRatePerSecond()` truncates to 0.** If `interestRate < SECONDS_PER_YEAR` (~3.15e7), the per-second rate is permanently 0, `_interestRateToAccrue` is always 0, and timestamp still advances — although this requires an extremely small governor-set rate, so it is secondary.

Additionally, note that `_debtIndex` does get incremented inside `_calculateInterestAccrual` even when the amount rounds to 0 (since `wadMul(rate, ~1e18)` is nonzero), but `accrueInterest()` only persists `debtIndex` when `_interestAmountAccrued > 0`. So the index growth is also discarded while `lastTimestampAccrued` still moves, causing `balanceOf`/`totalSupply` to show accrued debt between calls and then snap back after an accrual — the lost interest is unrecoverable.

### Impact Explanation
Direct theft of yield / protocol insolvency vector: borrowers' debt stops growing while the attack runs, so they repay less than owed; the protocol `feeCollector` receives no interest-minted synthetic tokens. For low-decimals synthetic tokens the affected debt can be economically meaningful, and the lost interest is permanent (not just delayed) because the checkpoint is overwritten. The invariant "debt grows continuously with `interestRate`" is broken.

### Likelihood Explanation
`accrueInterest()` is `public` with no modifier; a borrower or any griefer can call it every block via an EOA or a contract. It only requires a debt token whose `totalSupply_` (in raw units) is below the rounding threshold — most easily satisfied for 8-decimal synths (msBTC/msDOGE) during low-debt periods, or for any newly created debt token. No privileged role, oracle manipulation, or flash loan is needed; the only cost is gas per call.

### Recommendation
Mirror the Surge fix: do not advance `lastTimestampAccrued` unless interest was actually accrued. In `accrueInterest()`, only write `lastTimestampAccrued = block.timestamp` when `_interestAmountAccrued > 0` (or when the computed state is persisted), so sub-rounding windows accumulate into the next accrual instead of being discarded. Alternatively, store `lastTimestampAccrued` with higher precision / accumulate `pendingInterestFee`-style sub-wei interest, and compute the per-second rate as `interestRate * dt / SECONDS_PER_YEAR` to avoid the pre-division truncation at line 320.

### Proof of Concept
Hardhat/Foundry fork sketch:

```solidity
// Assume msBTCDebt (8 decimals) with interestRate = 0.1e18 (10% APR)
// and totalSupply_ = 1e6 (0.01 msBTC) already issued.

// perSecondRate = 0.1e18 / 31557600 ≈ 3.168e9
// wadMul(perSecondRate * 12s, 1e6) = (3.8e10 * 1e6 + 0.5e18)/1e18 = 0  → rounds to 0

uint256 debtBefore = debtToken.totalSupply();

for (uint i; i < 365 days / 12; ++i) {
    vm.warp(block.timestamp + 12);          // one block
    debtToken.accrueInterest();              // permissionless call, attacker EOA
}

uint256 debtAfter = debtToken.totalSupply();
assertEq(debtAfter, debtBefore);             // zero interest accrued over a "year"
assertEq(debtToken.lastTimestampAccrued(), block.timestamp); // but checkpoint advanced
// Expected correct debt: debtBefore * 1.10
```
