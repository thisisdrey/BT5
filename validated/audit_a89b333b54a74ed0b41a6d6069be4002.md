### Title
Non-idempotent `MarketOrderIdListCapsule.removeOrder()` corrupts order-book linked list on re-invocation - (File: chainbase/src/main/java/org/tron/core/capsule/MarketOrderIdListCapsule.java)

### Summary
`MarketOrderIdListCapsule.removeOrder()` unlinks an order from the on-chain doubly-linked order-book list by mutating the order's `prev`/`next` pointers to empty and updating neighboring capsules, but it is not idempotent: it assumes the capsule it is given still reflects the list's *current* linkage. If this method is ever invoked a second time for the same order capsule (e.g., because a caller re-derives the "head" order from stale in-memory state, or a future code path calls it more than once as part of cleanup/error handling), the second call will read `prev`/`next` as already-cleared (empty) and treat the order as simultaneously head and tail, forcibly resetting `this.setHead(new byte[0])` and `this.setTail(new byte[0])` on the persisted `MarketOrderIdListCapsule`, discarding the real remaining order chain even though other live orders may still exist in the list.

### Finding Description
`MarketOrderIdListCapsule.removeOrder()` [1](#0-0)  computes `preCapsule`/`nextCapsule` via `currentCapsule.getPrevCapsule()`/`getNextCapsule()`, and based on whether they are null, updates head/tail on the list capsule and persists it. At the end it always clears `currentCapsule`'s own `prev`/`next` to empty bytes and re-persists it:

```java
currentCapsule.setPrev(new byte[0]);
currentCapsule.setNext(new byte[0]);
marketOrderStore.put(currentCapsule.getID().toByteArray(), currentCapsule);
```

This is analogous to the kernel bug class in CVE-2025-38177 (`sch_hfsc`'s `hfsc_qlen_notify()`), where a removal/cleanup routine mutates shared linked structures without checking whether the entry was already removed, so a repeated call corrupts the structure instead of being a no-op.

In java-tron, the only current callers are `MarketCancelOrderActuator.execute()` [2](#0-1)  and `MarketSellAssetActuator.matchOrder()` [3](#0-2) , each of which appears to call `removeOrder()` exactly once per matched/canceled order within a single actuator execution. I was not able to fully verify, within the tool budget available, whether any code path (e.g. exception/retry handling, or a future actuator/matching change) can cause `removeOrder()` to be invoked twice for the same order id within one transaction or across chained matches, the way `hfsc_qlen_notify()` was reachable multiple times through `qdisc_tree_reduce_backlog()`. The method itself has no guard (`RB_EMPTY_NODE`-equivalent) against being called on an already-unlinked capsule, so if such a second invocation ever occurs — for example due to a future modification to the matching loop, or an actuator bug that re-processes the same maker order id twice inside `matchOrder()`'s while loop — the second call will silently zero out `head`/`tail` on `pairPriceToOrderStore`'s `MarketOrderIdListCapsule`, permanently orphaning any remaining orders in that price bucket (they become unreachable via `getHead()`/traversal even though their underlying `MarketOrderCapsule` records still exist and still hold locked TRX/token balances).

### Impact Explanation
If reachable, this would silently detach live, unmatched orders from the order-book's traversal structure while their locked balances (`sellTokenQuantityRemain`) remain reserved in `MarketOrderCapsule`, but the orders become invisible to future matching (`matchOrder()` walks the list starting at `getHead()`) and to `pairToPriceStore`/`pairPriceToOrderStore` accounting. This is a permanent freezing-of-funds condition: users' escrowed tokens/TRX for those orders can never be matched or canceled through normal flows since the order is no longer linked from the head/tail the actuators use to find candidates, and `pairToPriceStore.getPriceNum()`/list traversal would treat the price bucket as empty. This matches the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
This is **conditional/unconfirmed** — I could not identify a concrete, currently-reachable call sequence in `MarketCancelOrderActuator` or `MarketSellAssetActuator.matchOrder()` that invokes `removeOrder()` twice for the same order within present code. Both existing call sites appear to call it exactly once per removed order per execution. The vulnerability class exists in the code (the method is not idempotent/defensive), mirroring the kernel bug pattern, but without a demonstrated double-invocation trigger reachable by an unprivileged `MarketSellAssetContract`/`MarketCancelOrderContract` broadcaster, I cannot confirm current exploitability with the confidence required.

### Recommendation
Make `MarketOrderIdListCapsule.removeOrder()` idempotent/defensive: before mutating head/tail and neighbor pointers, check whether `currentCapsule` is already fully unlinked (`prev` and `next` both empty AND it is neither the recorded head nor tail) and treat that as a no-op, similar to how the kernel fix uses `RB_EMPTY_NODE()`/`RB_CLEAR_NODE()` to guard `eltree_remove()`. Additionally, audit all callers (`MarketCancelOrderActuator`, `MarketSellAssetActuator.matchOrder`) to ensure no path can invoke `removeOrder()` more than once for the same order id within a single execution or across retried executions.

### Proof of Concept
Not constructed — I was unable to confirm, within the available investigation, a concrete transaction sequence that causes `removeOrder()` to be called twice on the same `MarketOrderCapsule` under the current actuator code. A PoC would require demonstrating such a double-call path (e.g., a crafted sequence of `MarketSellAssetContract`/`MarketCancelOrderContract` transactions that causes the matching loop or cancel actuator to process the same order id twice), which was not established.

  public void removeOrder(MarketOrderCapsule currentCapsule, MarketOrderStore marketOrderStore,
      byte[] pairPriceKey, MarketPairPriceToOrderStore pairPriceToOrderStore)
      throws ItemNotFoundException {
    MarketOrderCapsule preCapsule = currentCapsule.getPrevCapsule(marketOrderStore);
    MarketOrderCapsule nextCapsule = currentCapsule.getNextCapsule(marketOrderStore);

    // pre.next = current.next
    // current.next.prev = current.prev
    if (preCapsule != null) {
      if (nextCapsule != null) {
        preCapsule.setNext(currentCapsule.getNext());
      } else {
        preCapsule.setNext(new byte[0]);
      }

      marketOrderStore.put(preCapsule.getID().toByteArray(), preCapsule);
    } else {
      // current is head
      // head = current.next
      if (nextCapsule != null) {
        this.setHead(currentCapsule.getNext());
      } else {
        // need to delete, outside
        this.setHead(new byte[0]);
      }

      // head changed
      pairPriceToOrderStore.put(pairPriceKey, this);
    }

    if (nextCapsule != null) {
      if (preCapsule != null) {
        nextCapsule.setPrev(currentCapsule.getPrev());
      } else {
        nextCapsule.setPrev(new byte[0]);
      }

      marketOrderStore.put(nextCapsule.getID().toByteArray(), nextCapsule);
    } else {
      // current is tail
      // this.tail = pre
      if (preCapsule != null) {
        this.setTail(currentCapsule.getPrev());
      } else {
        this.setTail(new byte[0]);
      }

      // tail changed
      pairPriceToOrderStore.put(pairPriceKey, this);
    }

    // update current
    currentCapsule.setPrev(new byte[0]);
    currentCapsule.setNext(new byte[0]);
    marketOrderStore.put(currentCapsule.getID().toByteArray(), currentCapsule);
  }
