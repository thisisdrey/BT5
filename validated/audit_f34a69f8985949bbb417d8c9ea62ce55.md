### Title
Client-supplied quarantine fields bypass Gitaly's transaction/partition gating for repository-scoped RPCs - ([File: internal/gitaly/storage/storagemgr/middleware.go])

### Summary
`beginTransactionForRepository` decides whether an incoming repository-scoped RPC should be run inside Gitaly's transactional storage engine (WAL-backed partition transaction) by checking whether the target `Repository` message's `GitObjectDirectory` / `GitAlternateObjectDirectories` fields are non-empty, treating a non-empty value as proof that "the request was already configured with a quarantine directory ... looped back to Gitaly from Rails' authorization checks" and is therefore already running inside a transaction. In reality these fields are ordinary, unauthenticated proto3 fields on `gitalypb.Repository` that any RPC caller can set directly on an accessor request, with no verification that the value actually originated from a legitimate Rails access-check callback.

### Finding Description
The bug mirrors the reported `BaseGauge::earned()` flaw: an eligibility/gating decision is made from a proxy signal that is trivially controllable by the caller instead of verifying the real precondition it is supposed to represent.

In `earned()`, "has staked" was inferred from veRAAC balance/weight — a value the caller fully controls without ever staking. Here, "already running inside a Rails-driven quarantine/access-check transaction" is inferred from whether `GitObjectDirectory`/`GitAlternateObjectDirectories` are set on the request: [1](#0-0) 

The code comment explicitly acknowledges the gap: setting either field "allows for circumventing the transaction management," and the author states "We'll leave this unaddressed for now and later address this by removing the options to configure object directories and alternates in a request." For mutators this is blocked (`ErrQuarantineConfiguredOnMutator`), but for accessor RPCs the request is simply passed through as `nonTransactionalRequest`, after being rewritten via `restoreSnapshotRelativePath`, entirely skipping `PartitionManager`/`TransactionManager` scoping.

The two fields being checked are plain, always-writable fields of the shared `Repository` proto message, not something restricted to internal/Rails-only callers: [2](#0-1) 

Under the legitimate design (documented in `doc/object_quarantine.md`), these fields are meant to be populated only by Gitaly itself during `git receive-pack` quarantine, or echoed back by Rails' `/internal/allowed` callback using data Gitaly gave it — never supplied directly by an ordinary client on an arbitrary accessor RPC: [3](#0-2) 

Because `beginTransactionForRepository` trusts these fields as a boolean "already inside transaction" signal rather than validating that the request is actually part of a legitimate quarantine/access-check flow (e.g., via the transaction/quarantine context, not client-supplied proto fields), any unprivileged caller of a repository-scoped accessor RPC can set a non-empty `git_object_directory` to force Gitaly to skip the transactional storage engine for that call.

### Impact Explanation
Skipping the transaction/partition boundary means the accessor RPC no longer runs against a consistent, isolated snapshot managed by `TransactionManager`/`PartitionManager`; it executes non-transactionally against the live repository. This breaks the isolation and consistency guarantees that the transactional storage engine is designed to provide for concurrent readers/writers, analogous to how the `BaseGauge` bug let an attacker skip the "stake" precondition and still receive the protected resource (a consistent, correctly-gated view). This is reachable from ordinary, unprivileged RPC callers (no special credentials needed) simply by crafting the `Repository` message field on any accessor call, matching the "hook/quarantine gating bypass" analog class.

### Likelihood Explanation
High likelihood of triggering: `GitObjectDirectory`/`GitAlternateObjectDirectories` are ordinary proto fields with no server-side authorization guarding who may set them, and the code path is explicitly documented as vulnerable by the author's own comment. Any client capable of invoking a repository-scoped accessor RPC (`protoregistry.ScopeRepository`, `OpAccessor`) can supply these fields directly in the request.

### Recommendation
Do not use client-supplied `GitObjectDirectory`/`GitAlternateObjectDirectories` values as a signal for "this request already runs under quarantine/transaction management." Instead, gate this decision on trusted, non-client-controlled request context — e.g., an internal marker set by Gitaly itself when it constructs the quarantine repository for the Rails callback loop (such as verifying `MetadataKeySnapshotRelativePath`/transaction context originates from Gitaly-issued state, not merely "field is non-empty"). Reject or ignore attacker-supplied object-directory fields on requests that do not carry Gitaly's own transaction/quarantine provenance, consistent with the code's own stated intent to eventually "remove the options to configure object directories and alternates in a request."

### Proof of Concept
Not directly reproducible from static analysis alone (root cause is confirmed by the code and its own explanatory comment, but exercising it end-to-end requires a running Gitaly + gRPC client). Conceptually: invoke any repository-scoped accessor RPC (e.g., `RepositoryService.RepositoryExists` or a `CommitService` read RPC) while populating the `Repository.git_object_directory` (and/or `git_alternate_object_directories`) field with an arbitrary non-empty value not derived from any real quarantine/pre-receive flow. Per `beginTransactionForRepository`, this causes Gitaly to treat the request as already transactional/quarantined and route it through `nonTransactionalRequest`, bypassing `PartitionManager`/`TransactionManager` scoping for that call — confirmable by observing (via tracing/logging) that no partition transaction is begun for the request, unlike identical requests without the field set. Full confirmation of the reachable downstream impact (e.g., which specific read/consistency guarantee is violated for a given RPC) would require running Gitaly's test suite (`middleware_test.go` already contains related test scaffolding referencing `ErrQuarantineConfiguredOnMutator`) or live testing in a Devin session with the actual gRPC server.

		// The object directories should only be configured on a repository coming from a request that
		// was already configured with a quarantine directory and is being looped back to Gitaly from Rails'
		// authorization checks. If that's the case, the request should already be running in scope of a
		// transaction and the repository rewritten to point to the snapshot repository. We thus don't start
		// a new transaction if we encounter this.
		//
		// This property is violated in tests which manually configure the object directory or the alternate
		// object directory. This allows for circumventing the transaction management by configuring the either
		// of the object directories. We'll leave this unaddressed for now and later address this by removing
		// the options to configure object directories and alternates in a request.

		if methodInfo.Operation == protoregistry.OpMutator {
			// Accessor requests may come with quarantine configured from Rails' access checks. Since the
			// RPC that triggered these access checks would already run in a transaction and target a
			// snapshot, we won't start another one. Mutators however are rejected to prevent writes
			// unintentionally targeting the main repository.
			return transactionalizedRequest{}, ErrQuarantineConfiguredOnMutator
		}

		rewrittenReq, err := restoreSnapshotRelativePath(ctx, methodInfo, req)
		if err != nil {
			return transactionalizedRequest{}, fmt.Errorf("restore snapshot relative path: %w", err)
		}

		return nonTransactionalRequest(ctx, rewrittenReq), nil
	}
