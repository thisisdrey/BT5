## Analysis

The GMX report centers on a hardcoded `minOutputAmount = 0` in `LiquidationUtils.createLiquidationOrder()`, which strips out slippage protection and lets MEV bots sandwich the resulting swap to steal value from the position owner. The closest analog in java-tron's actuator layer is the exchange (AMM-style token pair) actuators.

java-tron's `ExchangeTransactionActuator` (the actual swap/order-placement path) is **not** vulnerable — its `ExchangeTransactionContract` includes an `expected` field, and validation explicitly enforces `anotherTokenQuant >= tokenExpected`: [1](#0-0) 

However, `ExchangeInjectContract` and `ExchangeWithdrawContract` — which mutate the same AMM pool used for pricing swaps — carry **no** user-specified minimum/maximum bound on the computed `anotherTokenQuant` (the counterpart token amount debited on inject, or credited on withdraw). This is the same bug class as the GMX report: a monetary amount that depends on live pool state is computed with **zero caller-supplied bound**, making it exploitable via front-running/sandwiching.

### Title
Missing slippage/bound protection in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` allows sandwich-attack fund loss - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` compute the counterpart token amount (`anotherTokenQuant`) purely from the exchange pool's live balances at execution time, with no caller-supplied minimum/maximum tolerance field in the protobuf contract, unlike `ExchangeTransactionContract`, which has an `expected` field that is validated against the computed output.

### Finding Description
For `ExchangeInjectActuator`, the amount of the "other" token that is deducted from the exchange creator's balance is computed proportionally to the current pool ratio, with no user-specified cap: [2](#0-1) 

For `ExchangeWithdrawActuator`, the amount of the "other" token credited back to the creator is likewise computed purely from the live pool ratio, with only a "precision" sanity check (not a slippage bound): [3](#0-2) 

The protobuf contracts confirm neither message carries an `expected`/min-output-style field, in contrast to `ExchangeTransactionContract`: [4](#0-3) 

Because the pool ratio (`firstTokenBalance`/`secondTokenBalance`) can be shifted arbitrarily by any unprivileged account broadcasting an `ExchangeTransactionContract` swap against the same `exchange_id` immediately before the inject/withdraw transaction is packed into a block, an attacker can manipulate the ratio the moment before the victim's inject/withdraw executes, forcing the victim to (a) pay far more of the counterpart token than they intended when injecting liquidity, or (b) receive far less of the counterpart token than expected when withdrawing liquidity — then restore the ratio afterward, pocketing the difference. This mirrors the GMX finding exactly: an on-chain amount computed at execution time with no caller-enforced bound, exploitable by transaction ordering/sandwiching.

### Impact Explanation
An exchange creator broadcasting `ExchangeInjectContract`/`ExchangeWithdrawContract` can lose funds (excess token spent on inject, or reduced token received on withdraw) to a sandwiching attacker who only needs to submit `ExchangeTransactionContract` transactions around the victim's transaction. This is a concrete unauthorized value transfer/theft of funds reachable by any account that has created (or knows the id of) a token exchange pair, satisfying the "asset issuer" role permitted by scope.

### Likelihood Explanation
Likelihood is moderate: only the exchange creator can call inject/withdraw (`accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())` check), but any other account can freely submit `ExchangeTransactionContract` against the same exchange to manipulate its ratio ahead of the creator's transaction, since block producers order transactions and mempool visibility allows front-running. No special privilege beyond normal transaction broadcasting is required by the attacker.

### Recommendation
Add a caller-specified bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (e.g., `expected_another_token_max`/`expected_another_token_min`), and validate the computed `anotherTokenQuant` against it in `ExchangeInjectActuator.doValidate()` / `ExchangeWithdrawActuator.doValidate()`, analogous to the existing `tokenExpected` check in `ExchangeTransactionActuator`.

### Proof of Concept
1. Exchange creator prepares an `ExchangeInjectContract` intending to inject `tokenQuant` of token A, expecting to pay `X` of token B based on the current pool ratio.
2. Attacker observes the pending transaction (or predicts it) and broadcasts an `ExchangeTransactionContract` swap that shifts the pool ratio unfavorably for the creator, executed in the same or an earlier block.
3. The creator's `ExchangeInjectContract` executes using the now-skewed ratio in `ExchangeInjectActuator.execute()` (lines 71-83), causing the creator to pay significantly more of token B than intended, with no on-chain check preventing this since no minimum/maximum field exists in the contract.
4. Attacker reverses their swap afterward, capturing the difference.
