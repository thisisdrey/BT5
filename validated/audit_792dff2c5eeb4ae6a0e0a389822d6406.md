### Title
Pack-objects concurrency limiter keys solely on client-supplied `remote_ip`, allowing per-key limit reset/bypass analogous to identity-swap vote reuse - (File: internal/gitaly/service/hook/pack_objects.go)

### Summary
The upstream report describes a DAO vote-counting bug where a "spent" voting credential (staked SALT) can be freed and reattached to a new identity, letting the same underlying resource be recounted against a quorum/limit check that was designed to be one-shot per identity. The closest concrete analog reachable by an ordinary Gitaly client is the pack-objects RPC concurrency limiter, whose "identity" key is a single client-controlled field (`remote_ip`) rather than a value that Gitaly can verify is stable/unique per real client. Because the concurrency limiter is instantiated per unique key value with an independent semaphore, and the key is not bound to anything Gitaly itself derives from the TCP connection, a large or varying set of `remote_ip` values lets a client's concurrent `git-upload-pack`/pack-objects fetches be spread across many independent limiter buckets, defeating the intended per-client concurrency cap.

### Finding Description
`packObjectsHook` derives the concurrency-limiting key exclusively from `req.GetRemoteIp()`: [1](#0-0) 

This is the only input used to build `limitkey`, which is then passed to `runPackObjectsLimited` and ultimately to `ConcurrencyLimiter.Limit`: [2](#0-1) 

The `ConcurrencyLimiter` maintains one independent, lazily-created `keyedConcurrencyLimiter` (with its own semaphore/token pool) per distinct key string, and entries are evicted once refcount drops to zero: [3](#0-2) 

Documentation and code comments describe this limiter as being "scoped by remote IPs," intended to bound how many concurrent pack-objects processes a single client/IP can trigger: [4](#0-3) 

The `RemoteIp` field, however, is just a string field on the `PackObjectsHookWithSidechannelRequest` proto populated by the calling layer (`gitaly-hooks`/hooks payload), and is documented purely as "the original IP of the initiator of the fetch": [5](#0-4) 

Because the limiter treats each distinct string value of this field as a brand-new, independent quota bucket (exactly like the DAO's `_lastUserVoteForBallot[ballotID][msg.sender]` being keyed on a mutable/attacker-controllable identity — the staking account), any mechanism that lets the value vary between otherwise-identical concurrent fetches (e.g., a value derived from an X-Forwarded-For-style header, IPv6 address rotation among a `/64` block the client controls, or multiple source addresses behind the same logical client/tenant) causes each new key to get a fresh semaphore with the full configured allotment, just as unstaking-and-transferring SALT to a new account resets the "already voted" state and lets the same voting power be recounted. The invalid/loopback address path (`runPackObjects` with no key at all, i.e. unlimited) shown in the same function further underscores that the limiter can be fully skipped, and any value that legitimately parses as a non-loopback IP but differs per-request participates as a "new voter" with a fresh quota.

### Impact Explanation
If the per-key concurrency limiter can be effectively reset by varying the client-supplied identity value used as its key, the configured `pack_objects_limiting` protection against resource exhaustion from a single abusive client is bypassed. `git-pack-objects` is CPU- and memory-intensive; the entire purpose of this limiter (per `doc/backpressure.md`) is to prevent Gitaly from being overwhelmed by concurrent, expensive pack-objects invocations from one client. Bypassing it allows a single client to launch many more concurrent pack-objects processes than intended, leading to CPU/memory exhaustion and degraded service for other tenants sharing the Gitaly node — a DoS of the RPC handler's resource-limiting mechanism, in the same spirit as the original report's "quorum/limit that can be endlessly re-triggered by resetting the identity used for the check."

### Likelihood Explanation
Reachability requires only ordinary, unprivileged fetch/clone traffic that exercises the `PackObjectsHook`/`PackObjectsHookWithSidechannel` path — no special privileges, malicious peer, or MITM position are needed. The main uncertainty (not fully resolvable from the indexed code alone) is exactly how trustworthy/attacker-influenceable the `remote_ip` value is by the time it reaches this RPC in a given deployment (e.g., whether it is derived from a trusted proxy hop or can be influenced by request headers under attacker control). This uncertainty affects likelihood but does not change the underlying design gap: the concurrency limiter's uniqueness guarantee rests entirely on the assumption that this single string field is a stable, attacker-unspoofable per-client identity, which is a fragile trust assumption directly analogous to relying on a mutable on-chain balance/account as a one-time voting credential.

### Recommendation
- Do not rely solely on a single externally-supplied string (`remote_ip`) as the sole concurrency-limiting key; combine it with additional server-verified context (e.g., authenticated user identity, repository, and/or the actual peer address as observed by Gitaly's transport layer) similar to how the `TypePackObjects` limiter is documented to key on `RemoteIP/Repository/User` combined.
- Ensure the value used for `remote_ip` is derived from a source Gitaly can trust (verified proxy chain) rather than a value that traversed multiple hops without re-validation, mirroring the recommended fix in the original report of snapshotting a trusted, non-replayable state (like `ERC20Votes`) instead of a live, attacker-manipulable balance.
- Consider capping the total number of distinct concurrency-limiter keys or applying a secondary, coarser-grained (e.g., per-storage or global) concurrency ceiling so that key proliferation cannot fully bypass the intended backpressure.

### Proof of Concept
Conceptual, matching the structure of the original PoC (repeated "unstake → transfer → re-stake → re-vote" cycle mapped onto repeated "issue fetch with a new remote_ip value → get a fresh concurrency quota"):
1. Configure Gitaly with `pack_objects_limiting` `max_per_repo`/concurrency = 1 for a given actor.
2. Issue a fetch/clone whose resulting `PackObjectsHookWithSidechannelRequest.RemoteIp` is `A`; this consumes the single concurrency slot for key `A` in `ConcurrencyLimiter.limitsByKey["A"]` (`internal/limiter/concurrency_limiter.go:245-270`).
3. While that request is still in flight, issue a second, concurrent fetch that results in `RemoteIp` value `B` (differing only in this field, e.g., a different value derived from a client-influenceable source).
4. Because `getConcurrencyLimit` creates and tracks limiter state independently per key string, the second request is admitted immediately into its own new semaphore instead of being queued/rejected, demonstrating that varying the identity field defeats the single-client quota — analogous to `votesCastForBallot(ballotID)` doubling after the SALT unstake/transfer/re-vote cycle in the original report.

func (s *server) runPackObjectsLimited(
	ctx context.Context,
	w io.Writer,
	limitkey string,
	req *gitalypb.PackObjectsHookWithSidechannelRequest,
	args *packObjectsArgs,
	stdin io.ReadCloser,
	key string,
) error {
	ctx = context.WithoutCancel(ctx)

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	defer stdin.Close()

	if _, err := s.packObjectsLimiter.Limit(
		ctx,
		limitkey,
		func() (interface{}, error) {
			return nil,
				s.runPackObjectsFn(
					ctx,
					s.gitCmdFactory,
					w,
					req,
					args,
					stdin,
					key,
				)
		},
	); err != nil {
		return err
	}

// getConcurrencyLimit retrieves the concurrency limit for the given key. If no such limiter exists
// it will be lazily constructed.
func (c *ConcurrencyLimiter) getConcurrencyLimit(limitingKey string) *keyedConcurrencyLimiter {
	c.m.Lock()
	defer c.m.Unlock()

	if c.limitsByKey[limitingKey] == nil {
		// Set up the queue tokens in case a maximum queue length was requested. As the
		// queue tokens are kept during the whole lifetime of the concurrency-limited
		// function we add the concurrency tokens to the number of available token.
		var queueTokens semaphorer
		if c.maxQueueLength > 0 {
			queueTokens = c.createSemaphore(uint(c.currentLimit() + c.maxQueueLength))
		}

		c.limitsByKey[limitingKey] = &keyedConcurrencyLimiter{
			monitor:               c.monitor,
			maxQueueWait:          c.maxQueueWait,
			setWaitTimeoutContext: c.SetWaitTimeoutContext,
			concurrencyTokens:     c.createSemaphore(uint(c.currentLimit())),
			queueTokens:           queueTokens,
		}
	}

	c.limitsByKey[limitingKey].refcount++

	return c.limitsByKey[limitingKey]
}
