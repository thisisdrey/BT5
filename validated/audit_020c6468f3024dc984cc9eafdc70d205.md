This confirms the claim exactly as stated. The code fully matches the report:

1. `DeliveryReceipt` decodes the Ethereum `InboundMessageDispatched` event including the `success: bool` field <cite repo="Kohvert/polkadot-sdk--001" path="bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs" start="10-12" end="48" />, but `success` is never read afterward.

Audit Report

## Title
Relayer reward is paid out on `submit_delivery_receipt` regardless of the Ethereum-side delivery `success` flag - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
The Snowbridge outbound-queue-v2 pallet's `process_delivery_receipt` pays the relayer reward and permanently removes the `PendingOrder` for a nonce based solely on a verified `InboundMessageDispatched` event log existing, without ever checking the `success` boolean the event carries. A genuine but failed Ethereum-side dispatch (`success == false`) is thus treated identically to a successful one, and the pallet still pays the full fee and deletes the order.

## Finding Description
The Ethereum `Gateway` emits `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)`, decoded into `DeliveryReceipt { gateway, nonce, topic, success, reward_address }` [3](#0-2) . The `TryFrom<&Log>` impl correctly populates `success` from the decoded event [4](#0-3) .

`submit_delivery_receipt` verifies the proof via `T::Verifier::verify`, decodes the log into `DeliveryReceipt`, and forwards it to `process_delivery_receipt` [1](#0-0) . Inside `process_delivery_receipt`, the only checks performed are: (1) `receipt.gateway` matches `T::GatewayAddress`, and (2) the `PendingOrder` exists for `receipt.nonce`. If `order.fee > 0`, `T::RewardPayment::register_reward` is called unconditionally, the order is removed, and `MessageDelivered` is emitted — `receipt.success` is never read [2](#0-1) .

Proof verification only attests that the event genuinely occurred on a finalized Ethereum block; it says nothing about the dispatch outcome the event's `success` field is specifically designed to convey. By ignoring `success`, the pallet authorizes payout on the mere occurrence of the event rather than on the actual settlement outcome.

## Impact Explanation
Any account can call the permissionless `submit_delivery_receipt` with a valid proof for a genuine event whose `success` is `false` (destination dispatch reverted/ran out of gas, etc.) and still cause the pallet to (1) pay the relayer reward from `T::RewardPayment`, and (2) permanently delete the `PendingOrder`, foreclosing any reprocessing/accounting recovery for that nonce. This violates one-time, outcome-correct settlement of bridge reward funds — the exact `PendingOrder.fee` amount is paid to `reward_account` even though the corresponding message delivery did not actually succeed, and the `PendingOrders` payout-state marker advances (is removed) without a successful execution/settlement outcome, which the Polkadot SDK Pivots explicitly require ("Message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically").

## Likelihood Explanation
No privileged access, malicious relayer, or leaked keys are required. Ethereum-side dispatch failures (insufficient gas, reverting destination commands) are expected to occur during normal bridge operation, and the resulting event/receipt proof is public data that any signed account can submit via `submit_delivery_receipt`. The bug fires deterministically on every occurrence of a `success == false` receipt, making it fully repeatable, not merely theoretical.

## Recommendation
Add a check in `process_delivery_receipt`, e.g. `ensure!(receipt.success, Error::<T>::DeliveryFailed)` before calling `T::RewardPayment::register_reward`, or otherwise branch payout logic explicitly on `receipt.success`. Decide and implement an explicit, bounded policy for failed deliveries (e.g., no reward, partial reward, or retry) rather than treating them identically to successful ones. Avoid unconditionally removing `PendingOrders` when `success == false` unless the chosen policy intends to finalize failed nonces.

## Proof of Concept
1. A `v2_sendMessage`-originated command is dispatched by the Gateway on Ethereum but destination execution reverts, causing the Gateway to emit `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
2. Any account constructs an `EventProof` from this genuine, finalized event and its valid receipt proof.
3. It calls `EthereumOutboundQueueV2::submit_delivery_receipt(origin, Box::new(event))` [5](#0-4) .
4. `T::Verifier::verify` succeeds since the event/proof is real.
5. `process_delivery_receipt` finds the `PendingOrder`, sees `order.fee > 0`, calls `T::RewardPayment::register_reward` unconditionally, removes the order, and emits `MessageDelivered` [6](#0-5)  — despite `receipt.success == false`.
