### Title
Out-of-bounds heap read via unvalidated Central Directory `local_header_offset` in ijar's `InputZipFile` - (File: `third_party/ijar/zip.cc`)

### Summary
`ijar` (the `third_party/ijar/zip.cc` tool used by Bazel to derive interface jars from ordinary `.jar` files) trusts the attacker-controlled `local_header_offset` field from a ZIP Central Directory Header to seek within the mapped input file, and then relies on an unsigned-integer bounds check that silently underflows for out-of-range offsets, allowing the parser to read process memory beyond the mapped file and copy it into the produced interface jar.

### Finding Description
`InputZipFile::ProcessCentralDirEntry` reads the 32-bit `offset` field directly from the Central Directory Header with no range validation: [1](#0-0) 

`InputZipFile::ProcessNext` then uses this attacker-controlled `offset` to compute a raw pointer into the memory-mapped input file: [2](#0-1) 

The subsequent bounds check, `EnsureRemaining`, computes `remaining` as an unsigned subtraction of the file length and the current offset: [3](#0-2) 

Because `in_offset = p - zipdata_in_` (which embeds the attacker-supplied `offset`) can legitimately exceed `input_file_->Length()`, `input_file_->Length() - in_offset` underflows to a huge `size_t` value. The check `n > remaining` then always evaluates false, so `EnsureRemaining` incorrectly reports success even though `p` already points outside the mapped region. Parsing proceeds to read the (fake) local file header fields and then the file's raw bytes via `p` in `ProcessFile`: [4](#0-3) 

The data read from this out-of-bounds pointer is handed directly to `processor->Process(filename, attr, file_data, uncompressed_size_)`, which for ijar writes the (attacker-influenced) bytes into the generated interface jar output. This breaks the invariant that only bytes belonging to the mapped input archive are ever read and materialized — the parser instead reads and re-emits arbitrary adjacent process memory.

This is directly analogous to the reported CVE-2026-48684 class: an attacker-controlled length/offset field drives a read loop with no check that `pointer + read_size` stays within the buffer, and the bounds-check arithmetic itself is defective (unsigned wraparound here, vs. missing bounds check in the NetFlow case), causing reads past the end of the legitimate buffer.

### Impact Explanation
A malicious `.jar` file (e.g., served as a `http_jar`/`http_archive`/Maven dependency whose declared sha256 matches this exact malicious content — the checksum only pins bytes, it does not vet them for safety) can trigger `ijar`, invoked automatically by Bazel's Java rules to build interface jars, to read out-of-bounds process memory and copy some of it into the resulting `-ijar.jar` artifact stored in the output tree/action cache. This is a genuine confidentiality impact (C:L, matching the CVSS profile of the analog CVE): heap/stack contents of the Bazel build process can leak into build outputs that are persisted and potentially consumed or inspected by other parts of the build or other users sharing the cache/output base. Depending on placement, an out-of-range read can also crash the process (worker A:L), matching the analog CVSS vector.

### Likelihood Explanation
`ijar` runs on every ordinary-jar-to-interface-jar conversion, an extremely common, largely automatic action for Java targets, and requires no special build configuration to reach. Producing a crafted ZIP Central Directory entry with an out-of-range `local_header_offset` value is trivial and entirely within a single unprivileged actor's control (they need only publish a jar with the malicious bytes and a matching checksum, or place it on a branch that CI builds). No credentials, sandbox escape, or trusted BUILD file access is required.

### Recommendation
- In `InputZipFile::ProcessCentralDirEntry`/`ProcessNext`, validate `offset` (and the zip64-derived 64-bit offset) against `input_file_->Length()` before using it to compute `p`, rejecting the entry if `offset >= Length()`.
- Fix `EnsureRemaining` to avoid unsigned underflow, e.g. by first checking `in_offset > input_file_->Length()` and failing immediately, rather than relying on the subtraction result.
- Apply the same offset/length validation to the extra-field parsing loop in `ProcessCentralDirEntry` (lines 526–542), which similarly advances `extra_p` by an attacker-controlled `data_size` without checking `extra_p + data_size <= p`.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` style reproduction:
1. Construct a minimal valid ZIP file with one Central Directory Header whose `local_header_offset` field is set to a very large value (e.g., `0xFFFFFFF0`, deliberately not the ZIP64 sentinel `0xFFFFFFFF`) while the physical file is only a few hundred bytes.
2. Register this jar as an input to a Java rule (`java_import`) so that `ijar` is invoked on it during the build.
3. Observe that `ijar`/`singlejar` either crashes (SIGSEGV from reading unmapped memory) or produces an output interface jar containing bytes that do not correspond to any content of the original archive (memory-disclosure), demonstrating the read occurs outside the bounds of the mapped input file.

    }
  } else {
    // In this case, compressed_size_ == uncompressed_size_ (since the file is

      return -1;
    }
    file_data = p;
    p += compressed_size_;
  }

  return 0;
}
