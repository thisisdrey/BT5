### Title
Access-key reseed after DeleteKey+AddKey enables nonce replay of a previously-executed transaction, causing double execution — ([File: runtime/runtime/src/access_keys.rs], [File: runtime/runtime/src/verifier.rs])

### Summary
The question's file reference (`core/primitives/src/chunk_apply_stats.rs`) does not contain `add_regular_key` or `verify_nonce`; those functions actually live in `runtime/runtime/src/access_keys.rs` and `runtime/runtime/src/verifier.rs`. The underlying logic they describe is real, however: `add_regular_key` reseeds a recreated access key's nonce to `(block_height-1) * 1_000_000` regardless of any nonce that was already consumed by a prior incarnation of the same public key, and `verify_nonce` only compares against this stored value with no persistent replay-protection set. If a signer used a nonce close to the per-height upper bound and then deletes+re-adds the same public key, the reseeded nonce can be lower than the old, already-consumed nonce, allowing the identical previously-executed `SignedTransaction` to pass nonce validation a second time.

### Finding Description
`initial_nonce_value` seeds a freshly (re)created regular key to: [1](#0-0) 
which is written into the trie by `add_regular_key`: [2](#0-1) 

`verify_nonce` validates a transaction's nonce purely against the currently stored access-key nonce plus an upper bound of `block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`: [3](#0-2) 

Exploit flow:
1. At chunk height `H`, attacker signs and submits `tx_A` = `Transfer` from key `K`, choosing `nonce = X` just below the upper bound for height `H` (i.e. `X` close to but less than `H * 1_000_000`). This is valid and, on acceptance, the transaction-processing phase bumps the on-trie `access_key.nonce` to `X` (via `AccessKeyUpdate::Regular { nonce: tx_nonce, .. }` in `verify_and_charge_tx_ephemeral`), and a `Transfer` receipt is queued. [4](#0-3) 
2. In the same or a subsequent chunk, attacker submits `tx_reset` = `[DeleteKey(K), AddKey(K)]` with `nonce = X+1` (self-directed, so the resulting action receipt is processed locally). This passes `verify_nonce` (`X+1 > X`). When its receipt executes, `action_delete_key`/`action_add_key` run, and `add_regular_key` reseeds `K`'s nonce to `(block_height-1) * 1_000_000` — using the receipt's *processing* block height, not `H`. Because `X` was chosen close to `H * 1_000_000`, this reseeded value can be lower than `X`.
3. Attacker resubmits the byte-identical `tx_A` (same nonce `X`, same signature) as a new mempool entry after the reset has actually executed. `verify_nonce` sees `current_nonce = (block_height-1)*1_000_000 < X`, satisfying the `Monotonic` requirement `tx_nonce > current_nonce`, and the upper-bound check `X < current_height * 1_000_000` also holds trivially. The transaction is accepted and re-executed, producing a second balance debit and a second `Transfer` receipt to the same recipient.

The check that would normally prevent replay — the monotonic nonce comparison — is defeated because the code has no persistent high-water-mark independent of key deletion/recreation; deleting and re-adding the same public key resets the comparison baseline to a value dependent only on block height, not on any nonce previously consumed by that key.

### Impact Explanation
This is a double-spend / replay vulnerability: an ordinary account holder can cause their own previously-executed `Transfer` (or any other action, including contract calls with a deposit) to be executed twice by combining it with a same-key delete+recreate. While this "steals" from the attacker's own account rather than another user's, it breaks the value-conservation invariant (double receipt/double execution from a single signed message) and could be leveraged against any workflow that trusts "one signature = one execution" (e.g., a custodial/relay service crediting a receiver once per unique signed transaction, matching NEAR's replay/double-spend bounty category). Because the resubmitted transaction is byte-identical to one already applied, any downstream indexer/exchange logic keyed only on "nonce advanced monotonically ⇒ tx cannot recur" is violated.

### Likelihood Explanation
- Requires no privileged access: an ordinary funded account, its own keys, and standard RPC transaction submission.
- Requires precise but easily computable timing: attacker must pick `X` close to the height-based upper bound and control when the delete+recreate is processed, both of which are attacker-observable via public RPC (`status`/nonce queries).
- Requires the DeleteKey+AddKey receipt (self-directed) to execute before the resubmitted transaction is validated, which is the normal local-receipt execution order for same-account, same-shard actions.
- Fully repeatable and does not require racing validators or network manipulation — only sequencing of the attacker's own transactions across blocks.

### Recommendation
Do not let `AddKey` for a previously-existing public key reset the nonce baseline below any nonce ever used by that (account, public_key) pair. Options: (a) track a persistent per-`(account_id, public_key)` monotonic high-water-mark nonce that survives `DeleteKey`/`AddKey` cycles and use `max(high_water_mark, initial_nonce_value(block_height))` when seeding; or (b) forbid re-adding a public key value that was deleted from the same account (or from the account's DeleteKey history) within some tracked window; or (c) always seed to `max(current_height, previous_height_when_deleted+1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` so the new baseline can never fall below a nonce that could have been valid under the old key's upper bound.

### Proof of Concept
Runtime integration test (e.g. alongside `chain/chain/src/runtime/tests.rs` or `runtime/runtime/src/tests/apply.rs`) using `TestEnv`:
1. Create account `alice` with `FullAccess` key `K`, fund `bob`.
2. At height `H`, submit `tx_A = Transfer(K, nonce = H*1_000_000 - 1, amount=1_NEAR)` to `bob`; assert it applies and `bob`'s balance increases by 1 NEAR; assert stored `access_key.nonce == H*1_000_000 - 1`.
3. In the same or next block, submit `tx_reset = [DeleteKey(K), AddKey(K, FullAccess)]` with `nonce = H*1_000_000` (or higher, valid); let its (local) receipt execute; assert stored `access_key.nonce == (block_height-1)*1_000_000`, and assert this value is `< X` from step 2.
4. Resubmit the exact same signed bytes from `tx_A` (same nonce, same signature) in a subsequent block; assert `ProcessTxResponse` is *not* `InvalidTx(InvalidNonce)` and that it is applied.
5. Assert `bob`'s balance increased by 2 NEAR total (not 1), proving double execution/replay of a single signed transaction.

fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,

    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    );
    Ok(())
}

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}
