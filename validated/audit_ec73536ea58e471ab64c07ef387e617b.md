The reported issue is specific to **Waitress**, a Python WSGI server, and its custom (and at the time non-compliant) parsing of the `Transfer-Encoding` header, which caused it to fall back to `Content-Length` for values like `gzip, chunked`. java-tron's HTTP/JSON-RPC API layer does not use Waitress or any custom HTTP request-line/header parser — it is built entirely on Jetty (`org.eclipse.jetty.server.Server`), which is instantiated and configured in [1](#0-0)  and used by all wallet/JSON-RPC HTTP services such as [2](#0-1)  and [3](#0-2) .

Jetty's HTTP/1.1 request parsing (header/`Transfer-Encoding` handling, chunked decoding, request smuggling defenses) is implemented internally by the Jetty library itself, not by application code in this repository, and modern Jetty already rejects ambiguous/multiple `Transfer-Encoding` values per RFC 7230 §3.3.3. There is no analogous hand-rolled `Transfer-Encoding` parser in java-tron's HTTP stack that could fall through to `Content-Length` the way vulnerable Waitress did — the existing test suite around body-size handling (`SizeLimitHandlerTest`, `JsonrpcServiceTest#testJsonRpcSizeLimitIntegration`) exercises Jetty's chunked-transfer behavior but shows no custom smuggling-prone logic [4](#0-3) [5](#0-4) .

Per the scan rules, this is a dependency-only concern about a third-party library (Waitress) that is not part of java-tron's dependency stack at all (java-tron uses Jetty), so no valid in-scope analog exists.
