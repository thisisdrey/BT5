### Title
Unbounded resource consumption in `DiffBlobs` RPC when `patch_bytes_limit` is left at zero - (File: `internal/gitaly/service/diff/diff_blobs.go`)

### Summary
The external report describes a bug class where a numeric parameter that is expected to gate an economic calculation (`price`) can be left/set at zero, silently disabling the safety check that should protect against loss. The analogous pattern in Gitaly is the `patch_bytes_limit` field of `DiffBlobsRequest`: it is an ordinary, client-supplied RPC field that is documented to *disable* patch-size enforcement entirely when left at its zero value, and the server-side code implements exactly that behavior with no independent server-side ceiling.

### Finding Description
`DiffBlobsRequest.patch_bytes_limit` is described as: "the max size in bytes of a single patch generated from a pair of blobs... If set to zero, no limit is enforced." [1](#0-0)  Because protobuf's default value for an unset `int32` is `0`, any ordinary, unprivileged client calling `DiffBlobs` — whether or not they intend to — gets an unlimited patch size unless they explicitly opt into a limit.

In `diffBlobs`, the limit is only wired into the diff parser when it is strictly greater than zero: [2](#0-1) 
When `request.GetPatchBytesLimit()` is `0` (or negative), `limits.EnforceLimits` and `limits.PatchLimitsOnly` are never set to `true`, so the `diff.Limits` structure passed to `diffBlob`/`diff.NewDiffParser` carries no byte-size cap at all. There is no fallback default or upper bound enforced by Gitaly itself in this code path — unlike other diff endpoints where a configured `Limits` struct with upper bounds (`maxPatchBytesUpperBound`, etc.) is supplied by the caller service. This differs from the general `Limits` struct guarded by constants such as `maxPatchBytesUpperBound = 512000` [3](#0-2) , which are simply never applied here because `EnforceLimits`/`PatchLimitsOnly` remain `false`.

The resulting unbounded diff is then parsed fully into memory by `diff.NewDiffParser` and streamed back chunk-by-chunk via `sendDiff`, which only limits the *response message* size (`s.MsgSizeThreshold`), not the *total* amount of data buffered/generated per blob pair: [4](#0-3) 

This mirrors the report's root cause exactly: a caller-controlled numeric field whose zero value silently switches off an intended protective calculation/limit, with no independent server-side floor to fall back on.

### Impact Explanation
Any client authorized to call `DiffService.DiffBlobs` (an ordinary read-access RPC, not requiring any elevated/administrative role) can request diffs of many large blob pairs (e.g. large binary or text blobs already present in the repository) while leaving `patch_bytes_limit` unset. Because no limit is enforced server-side, Gitaly will generate and buffer the full, unbounded patch for each pair, driving up memory and CPU usage on the Gitaly node handling the RPC. Repeated or concurrent such requests can degrade or exhaust node resources, resulting in a denial of service for the RPC handler and potentially other tenants co-located on the same Gitaly node (repository/storage shard).

### Likelihood Explanation
Likelihood is high: `patch_bytes_limit=0` is the *default* protobuf value, so no special crafting is required beyond simply not setting the field (or setting it explicitly to 0), and the request only needs ordinary read access to existing large blobs in a repository the caller can already reach. No privileged role, leaked token, or malicious peer is needed — this is purely an unprivileged client interacting with a normal RPC field.

### Recommendation
- Enforce a mandatory, server-configured upper bound on patch size for `DiffBlobs` regardless of the client-supplied `patch_bytes_limit`, analogous to the `maxPatchBytesUpperBound` constant already used elsewhere in the diff package.
- Treat `patch_bytes_limit <= 0` as "use the server's default/maximum limit" rather than "no limit at all," or explicitly clamp the effective limit to a safe upper bound when the field is zero or negative.
- Ensure the same safeguard is applied consistently between `diffBlobs` (blob-pair) and `diffPairs` (raw-info) code paths, since `diffPairs` passes `request.GetPatchBytesLimit()` directly into `NewPatchParser` with the same zero-disables-limit semantics [5](#0-4) .

### Proof of Concept
1. Create or identify a repository containing one or more very large blobs (e.g., multi-hundred-MB text/binary content) accessible to a low-privilege/read-only client.
2. Call `DiffService.DiffBlobs` with `blob_pairs` referencing two large, sufficiently different blobs, and omit `patch_bytes_limit` (leaving it at its default `0`) as shown in the request schema [6](#0-5) .
3. Observe that `diffBlobs` skips enabling `EnforceLimits`/`PatchLimitsOnly` since `request.GetPatchBytesLimit() > 0` is false [2](#0-1) , causing the full patch to be generated and streamed without any byte cap, and repeat the call concurrently/at scale to observe elevated memory/CPU consumption on the Gitaly node.

```go
func (s *server) sendDiff(stream gitalypb.DiffService_DiffBlobsServer, diff *diff.Diff) error {
	response := &gitalypb.DiffBlobsResponse{
		LeftBlobId:          diff.FromID,
		RightBlobId:         diff.ToID,
		Binary:              diff.Binary,
		OverPatchBytesLimit: diff.TooLarge,
		PatchSize:           diff.PatchSize,
		LinesAdded:          diff.LinesAdded,
		LinesRemoved:        diff.LinesRemoved,
	}

	for {
		if len(diff.Patch) > s.MsgSizeThreshold {
			response.Patch = diff.Patch[:s.MsgSizeThreshold]
			diff.Patch = diff.Patch[s.MsgSizeThreshold:]
		} else {
			response.Patch = diff.Patch
			response.Status = gitalypb.DiffBlobsResponse_STATUS_END_OF_PATCH
			diff.Patch = nil
		}

		if err := stream.Send(response); err != nil {
			return fmt.Errorf("send: %w", err)
		}

		if len(diff.Patch) == 0 {
			break
		}

		response = &gitalypb.DiffBlobsResponse{}
	}

	return nil
}
```
