## Analog Vulnerability Found

### Title
Contract owner can instantly change `consume_user_resource_percent` via `UpdateSettingContract` to defraud callers of frozen-energy fee-splitting — ([File: actuator/src/main/java/org/tron/core/actuator/UpdateSettingContractActuator.java])

### Summary
The reported Set Protocol issue is that a SetToken manager can add/remove modules (e.g. `StreamingFeeModule`) with no time delay, letting them bypass a fee limit that users previously agreed to. The direct java-tron analog is the `UpdateSettingContract`/`UpdateSettingContractActuator`, which lets a smart-contract's `origin_address` (deployer) instantly change `consume_user_resource_percent` — the split ratio that determines how much of a caller's TRX vs. the contract owner's frozen energy pays for a `TriggerSmartContract` call — with zero delay, zero cooldown, and zero on-chain notice period.

### Finding Description
`UpdateSettingContractActuator.execute()` unconditionally overwrites the deployed contract's `consume_user_resource_percent` field the moment the transaction is included in a block: [1](#0-0) 

`validate()` only checks that the percent is within `[0, 100]` and that the caller is the contract's `origin_address` — there is no timelock, no minimum interval between changes, and no requirement that the change only take effect after a delay: [2](#0-1) 

This percent directly controls how energy cost is split between the contract "origin" (deployer) and the calling account in `VMActuator.getTotalEnergyLimitWithFixRatio`/`getTotalEnergyLimitWithFloatRatio`, and ultimately in `ReceiptCapsule.payEnergyBill`, which computes `originUsage = energyUsageTotal * percent / 100` and charges the remainder to the caller: [3](#0-2) [4](#0-3) 

The test `twiceUpdateSettingContract` even demonstrates the actuator successfully allowing two sequential updates in immediate succession (10% → 30% → 90%), confirming no rate-limiting or delay exists in the current implementation: [5](#0-4) 

The same lack-of-delay pattern exists for `UpdateEnergyLimitContract`, which changes `origin_energy_limit` (the cap on how much of the contract owner's frozen energy can subsidize callers) instantly and without restriction: [6](#0-5) 

### Impact Explanation
Users interacting with a smart contract (e.g., a dApp) typically observe/expect a given `consume_user_resource_percent` (how much of the call's energy cost the contract owner absorbs via frozen energy vs. how much the caller pays). A malicious contract owner can, in a single unprivileged transaction with `calcFee() == 0` (free to submit), instantly raise the caller-paid percentage right before/at the same time users call the contract — silently shifting energy cost burden onto callers who did not consent to the new ratio, directly draining TRX/bandwidth from unsuspecting callers without any notice period to opt out. This is a concrete unauthorized-fee/theft-of-funds analog to the reported streaming-fee bypass.

### Likelihood Explanation
Any account that deployed (or is recorded as `origin_address` of) a smart contract can trigger this at will, at zero fee, at any time, with no cooldown — making this trivially and repeatedly reachable by an unprivileged contract deployer to exploit ordinary callers.

### Recommendation
Introduce a time delay (or block-height/epoch based cooldown) before a new `consume_user_resource_percent` (and `origin_energy_limit`) value takes effect, analogous to the report's suggestion of a PENDING→INITIALIZED delay, so that callers have advance notice and an opportunity to avoid interacting with the contract under materially changed fee-split terms. Alternatively, cap the frequency/magnitude of changes within a rolling window.

### Proof of Concept
1. Deploy a smart contract with `consume_user_resource_percent = 0` (owner subsidizes all energy) via `CreateSmartContract`.
2. Wait for users/dApp integrators to interact with the contract expecting the advertised 0% caller cost.
3. As `origin_address`, broadcast `UpdateSettingContract` setting `consume_user_resource_percent = 100` (fee-free per `UpdateSettingContractActuator.calcFee()`), which is validated and applied atomically in the same block per `UpdateSettingContractActuator.execute()`.
4. Any caller's subsequent `TriggerSmartContract` transaction in the same or a later block is now billed via `ReceiptCapsule.payEnergyBill` at the new 100% caller-pays ratio, with no warning, confirming unauthorized shifting of energy cost onto the caller.

  @Override
  public boolean execute(Object object) throws ContractExeException {
    TransactionResultCapsule ret = (TransactionResultCapsule) object;
    if (Objects.isNull(ret)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    long fee = calcFee();
    ContractStore contractStore = chainBaseManager.getContractStore();
    try {
      UpdateEnergyLimitContract usContract = any.unpack(UpdateEnergyLimitContract.class);
      long newOriginEnergyLimit = usContract.getOriginEnergyLimit();
      byte[] contractAddress = usContract.getContractAddress().toByteArray();
      ContractCapsule deployedContract = contractStore.get(contractAddress);

      contractStore.put(contractAddress, new ContractCapsule(
          deployedContract.getInstance().toBuilder().setOriginEnergyLimit(newOriginEnergyLimit)
              .build()));
      RepositoryImpl.removeLruCache(contractAddress);

      ret.setStatus(fee, code.SUCESS);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      ret.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }
    return true;
