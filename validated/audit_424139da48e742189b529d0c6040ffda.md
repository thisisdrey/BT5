### Title
Unbounded growth of `nonces_in_use` via orphaned entries inserted after eviction race in `set_nonce_transaction_priority_id` - (File: `core/src/banking_stage/transaction_scheduler/transaction_state_container.rs`)

### Summary
`TransactionStateContainer::set_nonce_transaction_priority_id` unconditionally inserts into `nonces_in_use: HashMap<Pubkey, TransactionPriorityId>` before checking whether the corresponding `TransactionState` still exists in `id_to_transaction_state`. If the transaction was already capacity-evicted by `push_ids_into_queue` (which calls `remove_state`) before `set_nonce_transaction_priority_id` runs, the lookup fails, the `debug_assert!(false, "transaction must exist")` is a no-op in release builds, and the newly-inserted `nonces_in_use` entry becomes permanently orphaned — no `TransactionState` exists anymore to ever trigger its removal through `remove_state`.

### Finding Description
The container's bounded structures are `priority_queue` (`BTreeSet`) and `id_to_transaction_state` (`Slab`, capacity `capacity + EXTRA_CAPACITY`) [1](#0-0) . `nonces_in_use` is a separate `HashMap<Pubkey, TransactionPriorityId>` keyed by nonce address with no capacity bound of its own [2](#0-1) .

When a nonce transaction is buffered, the flow inserts the state and pushes it into the priority queue via `push_ids_into_queue`, which may immediately evict the lowest-priority entries (including the one just inserted, if it is now the lowest priority and the map is at capacity) by calling `remove_state` [3](#0-2) . Only afterwards is `set_nonce_transaction_priority_id` called to record the nonce address's owning priority id:

```rust
fn set_nonce_transaction_priority_id(
    &mut self,
    nonce_address: &Pubkey,
    priority_id: TransactionPriorityId,
) {
    self.nonces_in_use.insert(*nonce_address, priority_id);
    if let Some(state) = self.id_to_transaction_state.get_mut(priority_id.id) {
        state.set_nonce_address(Some(*nonce_address))
    } else {
        debug_assert!(false, "transaction must exist");
    }
}
``` [4](#0-3) 

The `self.nonces_in_use.insert(...)` on line 256 happens unconditionally, *before* the existence check. If the transaction's slot was already reaped by the earlier `push_ids_into_queue`/`remove_state` call, the `else` branch is taken — but `debug_assert!` compiles to nothing in release builds, so the missing-state condition is silently ignored and the newly-written `nonces_in_use` entry is never attached to any `TransactionState.nonce_address`.

Compare with `remove_state`, the only place that ever removes from `nonces_in_use`:
```rust
fn remove_state(&mut self, id: TransactionId) -> TransactionPriorityId {
    let state = self.id_to_transaction_state.remove(id);
    let priority_id = TransactionPriorityId::new(state.priority(), id);
    if let Some(nonce_address) = state.nonce_address()
        && let Entry::Occupied(entry) = self.nonces_in_use.entry(*nonce_address)
        && *entry.get() == priority_id
    {
        entry.remove();
    }
    priority_id
}
``` [5](#0-4) 

This removal path is only reachable through a live `TransactionState` whose `nonce_address` field was actually set. Because the orphaned entry created above never had `TransactionState::set_nonce_address` invoked on any surviving state, there is no future call to `remove_state` that will ever target and clean up that `nonces_in_use[nonce_address]` entry — it is permanently leaked.

An unstaked attacker who submits many nonce transactions, each using a distinct/never-before-seen nonce account and a low priority (e.g., zero compute-unit price), while the container is at or near capacity, causes each transaction to be inserted and then immediately evicted by `push_ids_into_queue`'s capacity-trim loop before `set_nonce_transaction_priority_id` is invoked for it. Each such transaction leaves one permanently-orphaned entry keyed by a unique attacker-chosen `Pubkey` in `nonces_in_use`, with no bound tied to `capacity`.

### Impact Explanation
`nonces_in_use` growth is decoupled from the bounded `priority_queue`/`id_to_transaction_state` capacity enforcement, allowing cheap, unstaked, low-priority traffic to drive unbounded heap growth in the banking stage's transaction scheduler (each entry is a `Pubkey` + `TransactionPriorityId`, ~48 bytes, but with no bound the memory is limited only by attacker-sent volume of distinct nonce addresses). This matches the Agave bounty category of unbounded resource consumption / memory growth from unauthenticated, low-cost network input directed at the leader's ingress path.

### Likelihood Explanation
Reaching this condition requires no special privileges — only crafting valid nonce transactions with distinct `nonce_address` values (any account can be referenced; the address does not need to be staked or owned by the attacker in any privileged sense) at low compute-unit price, sent to the TPU while the scheduler's buffer is at capacity (a state easily inducible with sustained low-value traffic). This is a plain sequential ordering bug (insert into queue/possible eviction happens before nonce bookkeeping is recorded), not a genuine multi-thread race, making it deterministically reproducible in a single-threaded unit test of `TransactionStateContainer`.

### Recommendation
In `set_nonce_transaction_priority_id`, check `id_to_transaction_state.get_mut(priority_id.id)` first; only insert into `nonces_in_use` if the state exists and successfully has its `nonce_address` set. If the state does not exist (already evicted), skip the insertion entirely instead of relying on a `debug_assert!` that is compiled out in release builds. Consider also bounding `nonces_in_use` by proactively evicting the oldest entries or deriving membership strictly from live `TransactionState.nonce_address()` values rather than maintaining a separately-populated map.

### Proof of Concept
Add an integration test to `core/src/banking_stage/transaction_scheduler/transaction_state_container.rs`:
```rust
#[test]
fn test_nonces_in_use_orphaned_entry_on_race() {
    let mut container = TransactionStateContainer::with_capacity(1);

    // Insert and immediately evict a low-priority transaction (simulates the
    // capacity-eviction happening before nonce bookkeeping is attached).
    let (transaction, max_age, priority, cost) = test_transaction(0);
    let id = container.insert_map_only(TransactionState::new(transaction, max_age, priority, cost));
    let priority_id = TransactionPriorityId::new(priority, id);

    // Fill capacity with a higher-priority transaction so the low-priority one is evicted.
    let (transaction2, max_age2, priority2, cost2) = test_transaction(10);
    let id2 = container.insert_map_only(TransactionState::new(transaction2, max_age2, priority2, cost2));
    let priority_id2 = TransactionPriorityId::new(priority2, id2);
    container.push_ids_into_queue([priority_id2, priority_id].into_iter());
    // `id` (priority 0) is now evicted from id_to_transaction_state.
    assert!(container.get_transaction(id).is_none());

    // Nonce bookkeeping call arrives "late", after eviction.
    let nonce_address = solana_pubkey::new_rand();
    container.set_nonce_transaction_priority_id(&nonce_address, priority_id);

    // Entry is inserted into nonces_in_use despite the state no longer existing,
    // and there is no live state to ever trigger its removal.
    assert!(container.get_nonce_transaction_priority_id(&nonce_address).is_some());

    // Even after fully draining the container, the orphaned entry remains.
    container.pop(); // removes priority_id2 from queue only
    container.remove_by_id(id2);
    assert!(container.is_empty());
    assert!(
        container.get_nonce_transaction_priority_id(&nonce_address).is_some(),
        "nonces_in_use entry leaked despite container being empty"
    );
}
```
Expected assertion failure/success demonstrates that `nonces_in_use.len()` can exceed the number of live entries in `id_to_transaction_state`, growing without bound as distinct `nonce_address` values are supplied under this eviction ordering, independent of `capacity`.

    fn push_ids_into_queue(
        &mut self,
        priority_ids: impl Iterator<Item = TransactionPriorityId>,
    ) -> usize {
        for id in priority_ids {
            self.priority_queue.insert(id);
        }

        // The number of items in the `id_to_transaction_state` map is
        // greater than or equal to the number of elements in the queue.
        // To avoid the map going over capacity, we use the length of the
        // map here instead of the queue.
        let num_dropped = self
            .id_to_transaction_state
            .len()
            .saturating_sub(self.capacity);

        for _ in 0..num_dropped {
            let priority_id = self.priority_queue.pop_first().expect("queue is not empty");
            self.remove_state(priority_id.id);
        }

        num_dropped
    }
