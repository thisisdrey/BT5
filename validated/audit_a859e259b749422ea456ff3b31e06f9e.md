### Title
Dust-transfer account-list stuffing lets an attacker temporarily block a victim from adding new collateral/debt tokens - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`DepositToken._transfer` unconditionally registers the recipient in the pool's per-account token list (`Pool.addToDepositTokensOfAccount`) whenever the recipient's balance was zero. The pool enforces a hard cap (`MAX_TOKENS_PER_USER`) on `debtTokensOfAccount.length + depositTokensOfAccount.length`. An unprivileged attacker can transfer 1 wei of every registered `DepositToken` to a victim to fill the victim's list, causing `onlyIfAdditionWillNotReachMaxTokens` to revert for any subsequent operation that would add a new token to the victim's list.

### Finding Description
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` when `_recipientBalanceBefore == 0`, with no minimum amount and no opt-in by the recipient [1](#0-0) .
- `transfer`/`transferFrom` are public entry points; the only check is that the *sender's* balance is unlocked (`_revertIfLocked` on the sender, not the recipient) [2](#0-1) .
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` when the combined list length reaches `MAX_TOKENS_PER_USER` [3](#0-2) [4](#0-3) .
- `DepositToken._mint` (invoked by `deposit`, `seize`/liquidation, and fee mints) also calls `addToDepositTokensOfAccount` on a first balance [5](#0-4) , so a victim at the cap cannot deposit a collateral type they don't already hold, and — critically — cannot receive seized collateral in `DepositToken.seize` during `Pool.liquidate` for a deposit token not already in their list [6](#0-5) .

Attacker path: `msdTOKEN_i.transfer(victim, 1)` for each registered deposit token the victim doesn't hold. Cost is a few wei of collateral per token plus gas.

### Impact Explanation
- Temporary freezing / liveness break: a victim whose position needs an additional collateral type (e.g., to add a new deposit token to restore health, or to take on a new debt token) is blocked until they self-clean. For an account near liquidation, inability to add a new collateral type can lead to liquidation losses that would otherwise be avoidable.
- Liquidation griefing amplification: `Pool.liquidate` lets the liquidator choose `depositTokenToSeize_`; seizing reverts inside `_transfer → addToDepositTokensOfAccount` if the *liquidator's* list is full — but this harms the liquidator, not the victim, so it is not an attack vector against the victim. The main impact is the blocked-deposit DoS on the victim.
- The break is in liveness (temporary freezing of the ability to open new token positions), matching the CVE-2022-36351 class of unauthenticated input-validation DoS. No identity, solvency, or accounting invariant is broken.

### Likelihood Explanation
- Fully permissionless: any EOA holding a dust amount of each msdTOKEN can execute it; obtaining dust requires only depositing small amounts or receiving transfers.
- Repeatable: the attacker can monitor and re-stuff the victim's list after each cleanup, though each round costs the attacker a transaction per token.
- Mitigating factors reducing severity: recovery is self-service — the victim transfers each dust token out, and because their balance goes to zero, `pool.removeFromDepositTokensOfAccount` frees the slot [7](#0-6) . Impact is therefore *temporary* freezing, not permanent loss, and the victim's existing tokens remain usable (the cap only gates additions).
- The exact value of `MAX_TOKENS_PER_USER` could not be confirmed in the available index context; a small constant makes this cheap to trigger, a large one increases attacker gas cost proportionally.

### Recommendation
- Only add the recipient to the account list on mints (deposits/seizes) initiated through the pool, not on ordinary ERC-20 transfers; or require a minimum non-dust amount (e.g., a per-token `minTransferThreshold`) before list registration.
- Alternatively, make list membership lazy: compute held tokens from balances at read time, or allow `addToDepositTokensOfAccount` to silently no-op instead of reverting when called via transfer paths.
- At minimum, let users remove foreign dust via a permissionless `Pool.removeFromDepositTokensOfAccount`-style cleanup that doesn't require a full token transfer.

### Proof of Concept
Hardhat sketch (requires fork/test deployment; `MAX_TOKENS_PER_USER` read from `Pool`):

```ts
// attacker deposits dust in every DepositToken they don't have, then:
for (const dt of allDepositTokens) {
  if ((await dt.balanceOf(victim.address)).eq(0)) {
    await dt.connect(attacker).transfer(victim.address, 1); // fills victim's list
  }
}
// victim's list length is now MAX_TOKENS_PER_USER
const newMsdToken = /* a DepositToken the victim never held */;
await expect(
  newMsdToken.connect(victim).deposit(parseUnits('1', 18), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim recovers by sweeping each dust token out (balance -> 0 removes it)
await dustToken.connect(victim).transfer(attacker.address, 1);
```

Note: recovery-by-transfer makes this a temporary (griefing-class) DoS rather than a permanent freeze; severity should be rated accordingly.
