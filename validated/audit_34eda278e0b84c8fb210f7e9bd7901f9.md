### Title
`PeerNetwork::lookup_peer` returns known peers under inverted expiry check, causing stale/unauthenticated public-key state to seed new inbound connections - (File: stackslib/src/net/p2p.rs)

### Summary
`PeerNetwork::lookup_peer` is documented as returning "the neighbor if we know of it and its public key is unexpired," but its implementation does the opposite: it returns `Some(neighbor)` only when the stored key has **already expired**, and `Ok(None)` when the key is still valid/unexpired. [1](#0-0) 

### Finding Description
`lookup_peer` looks up a `PeerDB` entry by socket address and is meant to gate whether we already have a trustworthy, unexpired public key on file for that address. The check is inverted:

```
if neighbor.expire_block < cur_block_height {
    Ok(Some(neighbor))   // key already expired -> still returned as "known"
} else {
    Ok(None)             // key is still valid -> treated as unknown
}
``` [2](#0-1) 

This function is consumed directly in `register_peer`, which is invoked whenever a new inbound TCP connection is accepted:

```
let neighbor_opt = match self.lookup_peer(self.chain_view.burn_block_height, &client_addr) { ... };
let (pubkey_opt, neighbor_key) = match neighbor_opt {
    Some(neighbor) => (Some(neighbor.public_key.clone()), neighbor.addr),
    None => (None, NeighborKey::from_socketaddr(...)),
};
...
new_convo.set_public_key(pubkey_opt);
``` [3](#0-2) 

Because of the inversion:
- When a peer address in the DB has a **still-valid** (unexpired) public key on record, `register_peer` treats the new inbound socket as fully unknown (`pubkey_opt = None`), discarding the legitimately-known key.
- When a peer address in the DB has an **expired/stale** key, `register_peer` incorrectly seeds the new connection's `ConversationP2P` with that stale key via `set_public_key(Some(neighbor.public_key))`.

This directly parallels the reported bug class: an identity-linking decision (which public key to trust/associate with an incoming connection) is made on the wrong side of a validity flag (`expire_block` vs. current height), exactly as Budibase linked accounts by `email` while ignoring `email_verified`. Downstream, `ConversationP2P::validate_handshake` branches its trust model on whether `self.connection.get_public_key()` is already `Some(..)`:

```
match self.connection.get_public_key() {
    None => {
        // must self-verify: newly claimed pubkey must match the message signature
        message.verify_secp256k1(&handshake_data.node_public_key)...
    }
    Some(_) => {
        // outbound-only: just check reported IP/port matches
    }
};
``` [4](#0-3) 

Any code path (including message dispatch/authentication elsewhere in `chat.rs` that trusts `self.connection.get_public_key()` as an anchor for signature checks) will now be operating on a public key that was seeded from a **stale/expired** DB record rather than either (a) nothing, or (b) a currently-valid key — inverted from the documented and intended behavior.

### Impact Explanation
This breaks the equality "peer public key on file is currently valid" vs. "peer public key on file has expired," which the rest of the P2P authentication logic (`validate_handshake`, message verification against `connection.get_public_key()`) depends on to decide whether to (re)verify a claimed identity from scratch. An unauthenticated remote party that connects from (or is relayed through) an address associated with a peer whose key has expired inherits stale key material bound to the connection before any handshake is validated, while addresses with legitimately fresh keys are wrongly stripped of that knowledge on new inbound connections. This is a state/identity-confusion bug reachable by any remote, unauthenticated peer simply by opening a TCP connection to the node — no attacker-controlled secret or privileged role is required to trigger the faulty branch itself.

### Likelihood Explanation
The faulty branch executes unconditionally on every inbound peer registration (`register_peer` → `lookup_peer`), so it is triggered by ordinary connection churn (peer key rotation/expiry, NAT reassignment, or IP reuse across nodes) without any special crafting. Reaching it requires no authentication and no secret material — only that a new inbound socket lands on an address the local `PeerDB` has previously recorded, which is a routine occurrence in the P2P network's peer-churn/reconnect behavior.

### Recommendation
Fix the comparison to match the documented intent: return `Some(neighbor)` when the key is still valid, i.e. flip the condition to `neighbor.expire_block >= cur_block_height` (or `>` depending on the exact boundary semantics elsewhere in the codebase, e.g. `Neighbor::load_by_address`'s `peer.expire_block < block_height => None`), so that only unexpired keys are propagated into `register_peer`'s `pubkey_opt`, and expired ones are treated as unknown, forcing a fresh handshake/signature validation.

### Proof of Concept
1. Node A has a `PeerDB` entry for `1.2.3.4:20444` with `expire_block = 100`.
2. Chain tip advances so `cur_block_height = 150` (key expired).
3. A remote party connects inbound from `1.2.3.4:20444`.
4. `register_peer` calls `lookup_peer(150, 1.2.3.4:20444)`; since `100 < 150`, it returns `Some(neighbor)` with the **expired** key.
5. `new_convo.set_public_key(Some(stale_pubkey))` seeds the new conversation with a public key that should have been discarded as expired, before any handshake signature has been verified for this connection — inverted from the intended "unexpired-only" semantics documented at line 1798. [3](#0-2)

    /// Get the neighbor if we know of it and it's public key is unexpired.
    fn lookup_peer(
        &self,
        cur_block_height: u64,
        peer_addr: &SocketAddr,
    ) -> Result<Option<Neighbor>, net_error> {
        let conn = self.peerdb.conn();
        let addrbytes = PeerAddress::from_socketaddr(peer_addr);
        let neighbor_opt = PeerDB::get_peer(
            conn,
            self.local_peer.network_id,
            &addrbytes,
            peer_addr.port(),
        )
        .map_err(net_error::DBError)?;

        match neighbor_opt {
            None => Ok(None),
            Some(neighbor) => {
                if neighbor.expire_block < cur_block_height {
                    Ok(Some(neighbor))
                } else {
                    Ok(None)
                }
            }
        }
    }
