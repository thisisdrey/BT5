## Title
Unbounded array-length and offset fields in TVM precompiled-contract signature/bytes extraction can trigger out-of-bounds array access from untrusted calldata - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

## Summary
The libxls report describes a buffer overflow in `xls_parseWorkBook` caused by trusting attacker-controlled length/offset fields inside a crafted binary file without validating them against the buffer bounds before copying data. The equivalent bug class exists in java-tron's TVM precompiled-contract helpers `extractBytesArray` and `extractSigArray`, which decode ABI-encoded arrays from raw contract calldata (`DataWord[] words` / `byte[] data`) using attacker-supplied length and offset words with insufficient bounds checking before indexing and copying.

## Finding Description
`extractBytesArray` reads an array length directly from calldata and then walks additional calldata words using that length, without ever checking that the derived indices stay inside `words`: [1](#0-0) 

The only guard is on the initial `offset` (`offset > words.length - 1`), not on `offset + i + 1` or `offset + bytesOffset + 1`, which are all derived from attacker-controlled words. A crafted `len` or `bytesOffset` value causes `words[...]` to be indexed past the end of the array.

The sibling helper `extractSigArray`, used by the batch-signature-validation precompile, has the identical pattern — it reads `len` from `words[offset]` and then loops `words[offset + i + 1]` with no upper bound check against `words.length`: [2](#0-1) 

Both helpers finish by calling `extractBytes`, which performs an unchecked `Arrays.copyOfRange(data, offset, offset + len)`: [3](#0-2) 

If `offset` is negative or `offset + len` exceeds `data.length` (both fully attacker-controlled through the ABI-encoded calldata to the precompile), this throws `ArrayIndexOutOfBoundsException` or `NegativeArraySizeException`. This mirrors the root cause of JLSEC-2026-1297: a length/offset field taken from untrusted input is used to size or index a buffer/array without validating it against the actual buffer size, the classic CWE-125/CWE-787 pattern, just manifesting in Java as an uncaught runtime exception rather than raw memory corruption.

## Impact Explanation
This code runs inside precompiled-contract execution (`Identity`/batch-signature-validation-style precompiles) invoked via a normal `CALL`/`STATICCALL` from any smart contract, i.e. reachable by any unprivileged contract deployer or caller who can construct calldata to the precompile address. A crafted `len`/`offset` word can force an out-of-bounds array access during TVM execution of a broadcast transaction. Depending on how far up the call stack the resulting `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` is caught, this can at minimum cause transaction execution to fail unpredictably (denial of service for the calling contract/transaction), and if the exception is not fully contained by the TVM's precompiled-call dispatch, it risks propagating as an unhandled error during block application. I was not able to fully trace the exact call site and exception-handling wrapper around `PrecompiledContract.execute()` in `Program`/`VM` in the remaining time, so the exact blast radius (transaction-scoped revert vs. broader node-level failure) is unconfirmed and should be verified directly against `Program.callToPrecompiledAddress` (or equivalent) before treating this as node-crashing.

## Likelihood Explanation
High reachability: any account can submit a transaction that triggers a `CALL` to the affected precompile with crafted calldata; no special privilege, stake, or witness/committee role is required. The vulnerable arithmetic (`offset + i + 1`, `bytesOffset + offset + 2`) is purely a function of attacker-supplied ABI words, so triggering the out-of-bounds condition requires no more than choosing large `len`/`offset` values in the transaction data.

## Recommendation
Add explicit bounds validation in `extractBytesArray` and `extractSigArray` before using `len`, `bytesOffset`, and `bytesLen` to index `words` or slice `data` — reject (return empty / throw a handled `ContractValidateException`-style error) whenever `offset + i + 1 >= words.length`, `bytesOffset` is negative, or `bytesOffset + offset + 2` combined with `bytesLen`/`SIG_LENGTH` would exceed `data.length`, analogous to the existing bounds check already present at the top of `extractBytesArray` for the initial `offset`. Ensure `extractBytes` validates `offset >= 0` and `offset + len <= data.length` before calling `Arrays.copyOfRange`, mirroring the pattern already used in `ContractEventParser.subBytes` (`framework/src/main/java/org/tron/common/logsfilter/ContractEventParser.java:80-91`).

## Proof of Concept
1. Deploy or call an existing contract that forwards attacker-supplied calldata to the batch-signature-validation precompile address via `CALL`/`STATICCALL`.
2. Craft calldata such that the ABI-encoded array-length word at `words[offset]` (as consumed by `extractSigArray`/`extractBytesArray`) is set to a large value (e.g. `0x7fffffff`) or such that a nested offset word (`words[offset + i + 1]`) points beyond the actual number of words present in `data`.
3. Submit the transaction; `extractSigArray`/`extractBytesArray` will index `words[offset + i + 1]` past the array bound, throwing `ArrayIndexOutOfBoundsException` (or `NegativeArraySizeException`/`OutOfMemoryError` for huge `len` in `new byte[len][]`) during TVM execution of the precompiled call.
4. Observe whether this exception is caught and safely reverted by the surrounding TVM call-dispatch logic or propagates further; either way, unbounded, attacker-controlled indexing into `words`/`data` from calldata is proven, matching the crafted-length/offset-driven out-of-bounds read pattern reported in JLSEC-2026-1297.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
