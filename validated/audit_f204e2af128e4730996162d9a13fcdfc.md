### Title
Unbounded heap read in ijar ZIP central-directory parsing on attacker-supplied jar/zip content - ([File: third_party/ijar/zip.cc])

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses the ZIP central directory (filename, extra-field entries, comment length) without any `EnsureRemaining`-style bounds check against the mapped input file's length, unlike its sibling `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` before every variable-length read. [1](#0-0) 

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from attacker-controlled bytes and then advances the cursor `p` by those lengths and copies `file_name_length` bytes with `memcpy` — with no check that `p + file_name_length`, `p + extra_field_length`, or the ZIP64 extra-field sub-record (`header_id`/`data_size` loop at lines 526-542) stay within the bounds of the memory-mapped ZIP file (`zipdata_in_` / `input_file_->Length()`). [2](#0-1) 

The extra-field walking loop is especially dangerous: it advances `extra_p` by an attacker-controlled `data_size` field with only `extra_p != p` as the loop exit condition, and reads `header_id`/`data_size` (and, for the ZIP64 tag, 8-byte size/offset fields) from `extra_p` on every iteration with no validation that `extra_p` remains inside `[p_start, p_end)`. [3](#0-2) 

Contrast this with `ProcessLocalFileEntry`, which is defensive and calls `EnsureRemaining()` before reading `file_name`/`extra_field`: [4](#0-3) 

This asymmetry means a JAR/ZIP file (the same class of untrusted, attacker-served content addressed by the CVE — a specially crafted image/archive triggering an OOB heap read) processed by the `ijar`/`singlejar` tooling (used by Bazel to build interface jars from `.jar` inputs, including those originating from external dependencies fetched over HTTP) can drive `p`/`extra_p` past the end of the mmap'd input buffer. Reads via `get_u2le`/`get_u4le`/`get_u8le` beyond the mapped region are out-of-bounds heap/mapped-memory reads, and the resulting garbage values (`uncompressed_size`, `offset`, filename bytes copied via `memcpy`) are then used to drive subsequent decisions (`Accept`, `ProcessFile`, output length calculations), potentially leaking adjacent heap memory into filenames or file contents of the generated interface jar / extracted output.

### Impact Explanation
An attacker who can supply a malformed `.jar`/`.zip` (e.g., a malicious dependency artifact) causes out-of-bounds reads in `ijar`'s central-directory parser, an information-disclosure class analogous to CVE-2018-3838 (heap OOB read in image parsing due to missing bounds checks). No write outside the process occurs and no direct code execution is implied; impact is heap memory disclosure and/or corrupted output, and in the worst case a crash (denial of service via segfault when reading unmapped pages past the mmap).

### Likelihood Explanation
Reachability requires attacker-controlled bytes to reach `ProcessCentralDirEntry` via `ijar`/`zip_main.cc`'s `extract()`/`ProcessAll()` path or `singlejar`'s use of the shared `zip.cc` central-directory reader, which is invoked whenever Bazel processes a `.jar` file (e.g., to build an interface jar or during `singlejar` packaging). This is a routine, automatic step for jar-typed dependencies, so likelihood of the vulnerable code path being exercised on attacker-controlled content is meaningfully high whenever an untrusted `.jar` is compiled against.

### Recommendation
Add the same `EnsureRemaining`-style bounds validation used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry`: validate that `p + 46` (fixed central-directory header size), `p + file_name_length`, `p + extra_field_length`, and `p + file_comment_length` never exceed `zipdata_in_ + input_file_->Length()` before dereferencing, and bound the extra-field walk loop (`header_id`/`data_size`) so `extra_p + 4 + data_size` never exceeds the declared `extra_field_length` boundary.

                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;

    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
