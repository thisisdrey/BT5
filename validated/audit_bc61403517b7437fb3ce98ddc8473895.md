## Title
Stale `PromiseYieldReceipt` state survives `DeleteAccount`, letting a recreated account be impersonated via automatic timeout-driven `PromiseResume` execution - ([File: core/store/src/utils/mod.rs])

## Summary
`remove_account` in `core/store/src/utils/mod.rs` only deletes `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` trie entries for a deleted account, but never removes `TrieKey::PromiseYieldReceipt`, `PromiseYieldStatus`, `PromiseYieldTimeout`, `YieldIdToDataId`/`DataIdToYieldId`, `PostponedReceipt`, `PostponedReceiptId`, or `PendingDataCount` entries keyed to that account. `action_delete_account` (`runtime/runtime/src/actions.rs:314`) never checks for such pending state before allowing deletion. If a contract on account `A` calls `promise_yield_create` and then `A` is deleted and recreated, the orphaned yield receipt and its timeout entry remain addressed to `A` and will be automatically executed against the new account once the timeout fires.

## Finding Description
`promise_yield_create` (`runtime/runtime/src/ext.rs:353`, via `runtime/near-vm-runner/src/logic/logic.rs:3660`) stores an `ActionReceipt` (with attacker-chosen `method_name`/`arguments`, `receiver_id = current_account_id = A`) under `TrieKey::PromiseYieldReceipt{receiver_id: A, data_id}` (`core/store/src/utils/mod.rs:200`), and separately enqueues a `TrieKey::PromiseYieldTimeout{account_id: A, data_id, expires_at}` entry (`core/store/src/utils/mod.rs:182`).

An attacker who controls `A` can then submit a `DeleteAccount` action. `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) only validates storage usage and gas-key burn amount, then calls `remove_account` (`core/store/src/utils/mod.rs:505-575`), which removes `Account`, `ContractCode`, access/gas keys, and `ContractData`, but explicitly does **not** touch `PromiseYieldReceipt`, `PromiseYieldStatus`, `PromiseYieldTimeout`, `YieldIdToDataId`/`DataIdToYieldId`, `PostponedReceipt`, `PostponedReceiptId`, or `PendingDataCount` rows. `TrieKey::Account{account_id}` is the only thing gating "does this account exist," so nothing prevents recreating `A` immediately afterward with new access keys and a new contract.

Once `A` is recreated, the dangling `PromiseYieldTimeout` entry is processed automatically at `expires_at` in `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3105`), with **no ownership/ownership-generation check** — it only checks `state_update.contains_key(&promise_yield_key)` (`lib.rs:3051`), which is still true. It synthesizes and forwards a `PromiseResume` receipt with `predecessor_id = receiver_id = A`, `data: None` (`lib.rs:3060-3068`).

That `PromiseResume` receipt is processed in `process_receipt`'s `VersionedReceiptEnum::PromiseResume` branch (`runtime/runtime/src/lib.rs:1500-1568`): it finds the stale `get_promise_yield_receipt(state_update, account_id=A, data_id)` (still present, since `remove_promise_yield_receipt` was never called during deletion), removes it, writes `ReceivedData`, and calls `apply_action_receipt` on the **original, attacker-authored** action receipt — with `predecessor_id == receiver_id == A`. This executes attacker-chosen `FunctionCall` actions (method name/arguments fixed at the time of `promise_yield_create`, before deletion) against the **new** contract deployed at `A`, under the trusted "self-call" identity (`predecessor_account_id() == current_account_id()`), which many contracts (e.g. `#[private]` in near-sdk) use as an authorization guard for privileged operations.

No existing check stops this: deletion doesn't require the storage-staking/size check to inspect yield/postponed state, account recreation doesn't scan for leftover yield rows, and the timeout resolution has no way to detect that the account behind `A` has been swapped out.

## Impact Explanation
This is an authorization-escalation bug: an attacker can pre-plant a self-authorized `FunctionCall` (with `predecessor==current_account_id`) that fires automatically after account recreation, days-or-blocks later, on whatever code is later deployed to that account name. Depending on the victim's new contract, this could be used to call privileged self-only methods (e.g., withdraw funds, change owner/keys, mint/burn tokens) — resulting in theft or loss of user funds and cross-account authorization escalation via a manipulated promise. This maps to the NEAR bounty categories of "authorization escalation across accounts or promises" and potentially "theft of user funds," depending on the specific victim contract logic that trusts self-calls.

## Likelihood Explanation
The attacker only needs: (1) a contract deployment on an account they control, (2) a call to `promise_yield_create`, (3) a `DeleteAccount` action — all ordinary, unprivileged transactions costing only gas and the account's storage-staking deposit. The remaining precondition — that someone else (or the same attacker for staging purposes) recreates the same account name and deploys a contract that trusts self-calls before the yield timeout (`yield_timeout_length_in_blocks`, on the order of ~200 blocks) elapses — is plausible in scenarios of account-name reuse/marketplaces, or an attacker deliberately targeting their own account name being reused by a future tenant, or an attacker deleting and recreating their own account as a "time bomb" targeting their own future deployment mistakes. It is fully repeatable and does not require any node/validator/network compromise.

## Recommendation
`remove_account` should also purge yield/postponed-receipt-related trie entries scoped to the account being deleted: iterate and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`, `PostponedReceipt`, `PostponedReceiptId`, and `PendingDataCount` rows keyed by `receiver_id == account_id` (and correspondingly invalidate/skip matching `PromiseYieldTimeout` queue entries, e.g. by checking during `resolve_promise_yield_timeouts` whether the account was deleted/recreated since the yield was created, or by tracking an account "generation"/incarnation counter that must match). Alternatively, `action_delete_account` should reject deletion (similar to the existing storage-usage and gas-key-balance checks) if the account still has any pending `PromiseYieldReceipt` or postponed receipts.

## Proof of Concept
Test-loop integration test plan:
1. Create account `A`, deploy a contract exposing a method that calls `promise_yield_create("victim_admin_method", attacker_args, gas_weight=1)` and returns/logs the resulting `data_id`.
2. Call this method from `A`; capture `data_id` and note `yield_timeout_length_in_blocks` from `RuntimeConfig::test()`.
3. Submit `DeleteAccount{beneficiary_id: attacker}` from `A`; run one block; assert `A`'s `Account` trie entry is gone (`get_account` returns `None`) but the raw trie still contains `TrieKey::PromiseYieldReceipt{receiver_id: A, data_id}` (query via `col::PROMISE_YIELD_RECEIPT` prefix iteration as in `test-loop-tests/src/tests/yield_timeouts.rs::get_yield_data_ids_in_state`).
4. Submit `CreateAccount` + `AddKey` + `DeployContract` for `A` with a *different*, "victim" contract exposing `victim_admin_method` guarded by `assert_eq!(env::predecessor_account_id(), env::current_account_id())` (a private/self-only method, e.g. one that transfers the account's balance to an attacker-controlled address).
5. Advance blocks until `yield_timeout_length_in_blocks` after step 2 elapses.
6. Assert: a `PromiseResume` receipt with the original `data_id` and `receiver_id = A` is produced and executed; the victim contract's `victim_admin_method` is invoked with `predecessor_id == A` (self-call), and its effect (e.g. balance drain) is observed on the *new* account state — demonstrating that a receipt scoped to the old incarnation of `A` executed with elevated trust against the new incarnation's code.
7. Expected (fixed) behavior: either the `DeleteAccount` action should be rejected while a `PromiseYieldReceipt`/timeout exists for `A`, or the stale entries should be purged on deletion so that no `PromiseResume`/execution occurs after recreation.
