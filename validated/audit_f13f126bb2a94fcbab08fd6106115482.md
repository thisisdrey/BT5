### Title
Stale-version chunk acceptance due to missing request/response version binding in `getchunks_try_finish` - ([File: stackslib/src/net/stackerdb/sync.rs])

### Summary
`StackerDBSync` records `expected_versions` as the node's own local slot versions for the entire sync round, not the specific version it requested for each in-flight `StackerDBGetChunkData`. `validate_downloaded_chunk` only checks the returned chunk's version against this stale local-version array, so a malicious replica can answer a request for version `V` with any older-but-still-newer-than-local, validly-signed chunk and have it accepted.

### Finding Description
The equality that should hold is: `data.slot_version == chunk_request.slot_version` (the version actually requested for that in-flight `StackerDBGetChunkData`). Instead, the code only enforces `data.slot_version > expected_versions[slot_id]`, where `expected_versions` is the requester's own local DB version snapshot taken once per round.

Trace:
1. In `getchunksinv_try_finish`, after receiving inventories, the schedule is built via `make_chunk_request_schedule` and `expected_versions` is set once to the node's local versions: [1](#0-0) 
This is the array used for validation for the *entire* fetch round, independent of which specific `slot_version` was placed into each individual `StackerDBGetChunkData` request built in `make_chunk_request_schedule` (which picks the *remote peer's advertised* newest version, e.g. `V=5`): [2](#0-1) 

2. `getchunks_begin` sends this specific-version request (`chunk_request.slot_version`) to the selected neighbor: [3](#0-2) 

3. When the reply arrives, `getchunks_try_finish` calls `validate_downloaded_chunk`, which only forwards `&self.expected_versions` (the flat, request-independent, local-version snapshot) — never the specific `chunk_request.slot_version` that was actually asked for: [4](#0-3) [5](#0-4) 

4. Accepted chunks are stored via `add_downloaded_chunk` and later returned in `StackerDBSyncResult.chunks_to_store` for persistence: [6](#0-5) [7](#0-6) 

Root cause: nothing in this path ties the response's `slot_version` back to the specific version number requested for that outstanding request. The only bound is against `expected_versions[i]`, a value computed once at the start of the round from the requester's own pre-sync local state, and never refreshed or matched per in-flight request. A malicious replica — which the node has already chosen to sync with and which legitimately/previously held an older, validly-signed chunk for that slot (e.g., version 3, signed by the real slot owner at some earlier point) — can reply to a request for version 5 with that stale version-3 chunk. Since 3 > local version 2 (the only comparison performed), it passes `validate_downloaded_chunk` and gets accepted and stored, even though it is not the version that was requested and not the latest available.

### Impact Explanation
A malicious/adversarial replica (an already-connected sync peer the node chose to talk to, holding a validly-signed but stale chunk) can force a requesting node to accept and persist an older-than-latest, though newer-than-local, version of a StackerDB slot instead of the true latest version. Because the requester's own bookkeeping (`expected_versions`) is only refreshed once per sync round from local DB state, the same attacker can repeat this "drip-feed the next oldest signed version" strategy across successive sync rounds, indefinitely delaying (stalling) convergence of the requester to the actual canonical/latest chunk for that slot, as long as it holds intermediate signed versions. This matches the "serving non-canonical (stale) state as canonical/accepted" category — High severity — since it is stale data accepted and durably stored as if canonical, without ever binding it to the specific version the node asked for.

### Likelihood Explanation
Preconditions are modest and within the specified unprivileged attacker model: the attacker only needs to be one of the chosen replica peers for a StackerDB contract (any remote party can become this by advertising itself as a replica and getting picked in `make_chunk_request_schedule`/`getchunksinv_begin`), and it needs to actually possess (or have observed via prior legitimate gossip) an older, validly-signed chunk for the targeted slot — no secret key forgery required. This is fully remotely triggerable over the p2p StackerDB sync protocol, requires no admin/secret access, and is repeatable each sync round as long as the attacker has additional stale-but-locally-newer versions to feed.

### Recommendation
Bind each response to the specific request it answers: when validating a `StackerDBChunk` reply in `getchunks_try_finish`, compare `data.slot_version` (and `data.slot_id`) against the `slot_version` recorded in the specific `StackerDBGetChunkData` that was actually sent for that in-flight request (e.g., track per-outstanding-request expected `(slot_id, slot_version)` pairs alongside `chunk_fetch_priorities`/inflight tracking), rejecting any reply whose version does not exactly match what was requested, rather than only checking it against the round-stale `expected_versions` local-version snapshot.

### Proof of Concept
Rust test plan in `stackslib/src/net/stackerdb/tests/sync.rs`:
1. Set up a `StackerDBSync` instance with local slot version for slot 0 = 2.
2. Populate `chunk_invs` for a mock malicious replica advertising slot 0 version = 5, causing `make_chunk_request_schedule` to build a `StackerDBGetChunkData{slot_id:0, slot_version:5}` request.
3. Run `getchunksinv_try_finish` so `expected_versions = [2, ...]` (local versions) is set, and `getchunks_begin` sends the version-5 request to the malicious replica.
4. Have the mock replica respond with a `StackerDBChunkData{slot_id:0, slot_version:3, ...}` chunk, validly signed by the real slot-owner key (simulate with a legitimately signed older chunk fixture).
5. Call `getchunks_try_finish`; assert that `validate_downloaded_chunk` (and thus the overall call) returns `Ok(true)` and that `add_downloaded_chunk`/`downloaded_chunks` now contains the version-3 chunk — despite the outstanding request having asked for version 5. This demonstrates acceptance of a non-matching, stale-but-locally-newer chunk version, confirming the missing request/response version binding.

        let slot_id = data.slot_id;
        let _slot_version = data.slot_version;

        if let Some(data_list) = self.downloaded_chunks.get_mut(&naddr) {
            data_list.push(data);
        } else {
            self.downloaded_chunks.insert(naddr.clone(), vec![data]);
        }

        self.chunk_fetch_priorities
            .retain(|(chunk, ..)| chunk.slot_id != slot_id);

        if !self.chunk_fetch_priorities.is_empty() {
            let next_chunk_fetch_priority =
                self.next_chunk_fetch_priority % self.chunk_fetch_priorities.len();
            self.next_chunk_fetch_priority = next_chunk_fetch_priority;
        }

        self.total_stored += 1;
    }
