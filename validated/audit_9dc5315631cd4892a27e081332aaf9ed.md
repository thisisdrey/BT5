### Title
Missing revalidation of version/size/instruction-count sanitization checks in `resanitize_transaction_minimally` bypasses `Bank::verify_transaction`'s gates for aged banking-stage transactions - (File: `runtime/src/bank.rs`)

### Summary
The external report's bug class is: a validation check is enforced on the "create/register" code path but is missing from an equivalent "re-validate/rotate" code path that mutates the same state, letting an attacker route around the check via the second path. The same structural pattern exists in agave's banking-stage transaction validation: `Bank::verify_transaction_with_serialized_message` enforces the transaction-version gate, max wire-size check, and instruction-count limit, but the parallel re-validation entry point, `Bank::resanitize_transaction_minimally`, which is invoked for "aged" transactions sitting in the banking-stage queue across an epoch boundary, does not repeat those same checks.

### Finding Description
`Bank::verify_transaction_with_serialized_message` performs several checks before a transaction is admitted: [1](#0-0) 

These include: (1) rejecting `TransactionVersion::Number(1)` unless `enable_tx_v1` is active, (2) enforcing `max_transaction_size` (which is different/larger for v1 once the feature is active vs. `PACKET_DATA_SIZE` otherwise), and (3) the SIMD-0160 instruction-count limit (`MAX_INSTRUCTION_TRACE_LENGTH`) checked "before signature verification." The code contains an explicit maintainer warning that these checks must be mirrored elsewhere: [2](#0-1) 

The mirrored function, `Bank::resanitize_transaction_minimally`, is the code path that re-validates a transaction that was sanitized earlier (in a prior bank/epoch) before it is locked and executed. It only re-checks vote-only-bank status, reserved keys, `MAX_ACCOUNTS_PER_INSTRUCTION` (and only when the epoch actually changed), and ALT expiration — it does **not** re-check the `enable_tx_v1` version gate, the wire-size limit, or the instruction-count (SIMD-0160) limit: [3](#0-2) 

This function is called from the banking stage's "aged transaction" processing path, which handles transactions that were parsed/buffered against a previous bank and are now being locked/executed against a newer bank: [4](#0-3) 

This is structurally identical to the reported bug class: the "registration" check (`verify_transaction_with_serialized_message`) enforces the invariant, but the "rotate"/re-admit equivalent (`resanitize_transaction_minimally`) does not, so a transaction that ages across the relevant epoch/feature boundary in the banking-stage queue is not re-subjected to the same gates.

### Impact Explanation
If any of the three checks in `verify_transaction_with_serialized_message` were ever meant to change behavior across an epoch boundary (as the maintainer comment implies for "pending features"), a transaction sitting in the unprivileged banking-stage queue could be executed with rules from its original sanitization epoch instead of the current bank's rules, bypassing the invariant the check was meant to enforce network-wide at the new epoch/feature-activation slot.

### Likelihood Explanation
Likelihood is bounded by how likely it is that a transaction ages across the specific epoch boundary at which one of these checks would newly matter (e.g., the epoch where `enable_tx_v1` toggles). This is a normal, attacker-triggerable condition (submit near the epoch boundary and let it sit in the buffered queue), not a validator/operator action, and does not require special privileges. I could not fully confirm from static review alone whether `translate_to_runtime_view`/`SanitizedTransactionView` parsing independently re-derives and blocks the version/size/instruction-count invariants at execution time through some other choke point, which would reduce or eliminate the practical impact; this uncertainty should be resolved by tracing the full execution path from `prepare_sanitized_batch_with_results` (called immediately after `resanitize_transaction_minimally`) through to `load_and_execute_transactions`.

### Recommendation
Audit `Bank::resanitize_transaction_minimally` and ensure it re-applies the same invariants enforced in `Bank::verify_transaction_with_serialized_message` (version gate, size limit, instruction-count limit), consistent with the existing inline warning at `runtime/src/bank.rs:5542-5543`, so that transactions which age across an epoch/feature boundary in banking stage cannot skip checks that were tightened or added between the transaction's original sanitization and its actual execution.

### Proof of Concept
Not independently reproduced; based on static code analysis only. A concrete PoC would require identifying a specific feature/limit whose activation slot can be straddled by a transaction sitting in the `TransactionViewStateContainer` queue long enough to be processed via `process_and_record_aged_transactions` in a bank from a later epoch than it was sanitized against, and confirming no other code path (e.g., `load_and_execute_transactions`) re-derives the missing check.

    pub fn resanitize_transaction_minimally(
        &self,
        transaction: &impl TransactionWithMeta,
        sanitized_epoch: Epoch,
        alt_invalidation_slot: Slot,
    ) -> Result<()> {
        if self.vote_only_bank() && !vote_parser::is_valid_vote_only_transaction(transaction) {
            return Err(TransactionError::SanitizeFailure);
        }

        // If the transaction was sanitized before this bank's epoch,
        // additional checks are necessary.
        if self.epoch() != sanitized_epoch {
            // Reserved key set may have changed, so we must verify that
            // no writable keys are reserved.
            self.check_reserved_keys(transaction)?;

            for instr in transaction.instructions_iter() {
                if instr.accounts.len() > solana_transaction_context::MAX_ACCOUNTS_PER_INSTRUCTION {
                    return Err(solana_transaction_error::TransactionError::SanitizeFailure);
                }
            }
        }

        if self.slot() > alt_invalidation_slot {
            // The address table lookup **may** have expired, but the
            // expiration is not guaranteed since there may have been
            // skipped slot.
            // If the addresses still resolve here, then the transaction is still
            // valid, and we can continue with processing.
            // If they do not, then the ATL has expired and the transaction
            // can be dropped.
            let (_addresses, _deactivation_slot) =
                self.load_addresses_from_ref(transaction.message_address_table_lookups())?;
        }

        Ok(())
    }
