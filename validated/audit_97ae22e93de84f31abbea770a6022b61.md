Audit Report

## Title
`process_delivery_receipt` ignores the Ethereum `success` flag and pays relayer reward / settles pending order regardless of delivery outcome - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`Pallet::process_delivery_receipt` decodes and unconditionally accepts a `DeliveryReceipt` containing a `success: bool` field from the Ethereum `InboundMessageDispatched` event, but never inspects that field before paying the relayer reward via `T::RewardPayment::register_reward` and removing the `PendingOrder`. This treats a failed/reverted message dispatch on Ethereum identically to a successful one, causing unbacked reward payout and permanent loss of the order's failure-tracking state.

## Finding Description
The `DeliveryReceipt` struct explicitly carries a `success` field decoded straight from the Gateway's `InboundMessageDispatched(nonce, topic, success, reward_address)` event log [1](#0-0) , and populated faithfully during decode [2](#0-1) .

The public, unprivileged extrinsic `submit_delivery_receipt` only verifies proof authenticity via `T::Verifier::verify`, decodes the receipt, and forwards it to `process_delivery_receipt` [3](#0-2) . `process_delivery_receipt` then checks only `receipt.gateway`, resolves the reward account, fetches the `PendingOrder`, unconditionally pays `order.fee` as a relayer reward, and removes the order from storage — `receipt.success` is never read or branched on anywhere in this function [4](#0-3) .

`T::Verifier::verify` only authenticates that the log genuinely originates from the Gateway and was included in a finalized Ethereum block — it makes no assertion about the semantic `success` outcome encoded in the log's data. Consequently, a legitimately verified event with `success == false` (i.e., the dispatched command reverted/failed on Ethereum) is processed identically to a successful delivery.

## Impact Explanation
This results in an unbacked/incorrect payout — the relayer reward (`order.fee`) is paid via `T::RewardPayment::register_reward` even when Ethereum reports the dispatch failed, which is a theft-of-value/incorrect-payout condition against the intended reward semantics. Additionally, the `PendingOrder` entry — the sole state tracking the nonce's outstanding fee/relay obligation — is unconditionally removed via `<PendingOrders<T>>::remove(nonce)` regardless of outcome, permanently discarding the ability to retry, reconcile, or correctly settle a failed dispatch. This matches the "duplicate settlement or payout" / "permanent bridge-state lock" impact categories: the corrupted values are the relayer's reward payout amount and the `PendingOrders` storage entry for `nonce`, both settled/finalized incorrectly based on a wrong (ignored) `success` flag.

## Likelihood Explanation
Any command relayed through the outbound-queue-v2 pallet can legitimately fail on Ethereum for reasons independent of relayer honesty (insufficient gas budgeted via `GasMeter::maximum_dispatch_gas_used_at_most`, downstream revert, agent/channel issues, etc.). Every such failure emits a real `InboundMessageDispatched` event with `success=false`, and any relayer — with no special privilege beyond obtaining a standard inclusion proof — can call the public `submit_delivery_receipt` extrinsic with that authentic log to claim the reward. No additional gate exists in `process_delivery_receipt` to prevent this, making the flaw trivially and repeatedly reachable during normal bridge operation, not merely a theoretical edge case.

## Recommendation
In `Pallet::process_delivery_receipt`, branch on `receipt.success`: on `true`, retain current behavior (pay reward, remove/settle the order as delivered); on `false`, withhold or reduce the relayer reward and transition the `PendingOrder` into a distinct failure/retry state (or emit a dedicated failure event) instead of deleting it, so that fee and order bookkeeping accurately reflect the real dispatch outcome reported by Ethereum.

## Proof of Concept
1. A message with non-zero `fee` is enqueued via `do_process_message`, creating a `PendingOrder { nonce, fee, .. }` [5](#0-4) .
2. The Gateway contract on Ethereum dispatches the corresponding command but the execution reverts (e.g., due to insufficient allotted gas), emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a valid inclusion proof for this genuine event log and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (log is authentic/included); `DeliveryReceipt::try_from` correctly decodes `success = false`.
5. `process_delivery_receipt` proceeds to call `T::RewardPayment::register_reward(&reward_account, .., order.fee)` and removes `PendingOrders::<T>::remove(nonce)` exactly as for a successful delivery, despite the on-chain fact that dispatch failed.
6. Observable result: `Event::MessageDelivered { nonce }` fires and the relayer is rewarded even though the message never executed successfully on Ethereum, and the `PendingOrder` state that could track/retry the failure is permanently gone.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
