### Title
`OutboundQueue::calculate_fee` can round the remote (Ethereum) fee component to zero, letting messages be sent to Snowbridge underpriced - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

### Summary
`Pallet::calculate_fee` (used by `SendMessage::validate` to price every outbound message sent to Ethereum) performs several chained integer divisions to convert the ETH-denominated gas cost into native currency. With valid, non-zero `PricingParameters`, the computed remote fee can round down to `0`, exactly mirroring the `curvePriceWad` rounding-to-zero bug in the external report: a legitimate, non-degenerate input state produces an under/zero-priced output that is accepted and used downstream without a minimum-value check.

### Finding Description
`calculate_fee` computes the remote (Ethereum-side) fee as: [1](#0-0) 

The remote fee (`fee_per_gas * gas_used + reward`) is scaled by `multiplier`, divided by `exchange_rate` via `FixedU128::checked_div`, and finally passed through `convert_from_ether_decimals`, which divides by `10^(18 - Decimals)` (`10^8` for DOT, `10^6` for KSM): [2](#0-1) 

None of these divisions guard against the final result rounding to zero. This is not a hypothetical: the pallet's own test suite demonstrates it happening with entirely valid, non-zero pricing parameters (`exchange_rate = 1`, `fee_per_gas = 1`, `reward = 1`, `multiplier = 1`): [3](#0-2) 

The test comment itself acknowledges this is a bug ("the remote fee calculated here is invalid which should be avoided") but no fix/guard exists in the code — unlike `pallet-asset-conversion`, where the analogous rounding-to-zero issue was hardened (see `prdoc/stable2606/pr_11795.prdoc`, which added explicit zero-output checks to `quote_price_exact_tokens_for_tokens`/`quote_price_tokens_for_exact_tokens`).

`calculate_fee`'s output is consumed directly and unconditionally by the public `validate` entrypoint that every outbound message (e.g., XCM `ExportMessage` for asset transfers to Ethereum) goes through: [4](#0-3) 

The resulting `Fee { local, remote }` is what callers (XCM executors, `pallet-xcm`, bridge exporters) charge the sender before enqueuing the message via `deliver`. There is no check anywhere in `validate` or `calculate_fee` that `fee.remote > 0`.

### Impact Explanation
Because `fee.remote` is not floor-bounded, an ordinary unprivileged user can construct/trigger a message-send scenario where the collected remote fee is `0` even though the message still requires real ETH gas to be dispatched and relayed on Ethereum (each `Command` has a nonzero `maximum_dispatch_gas_used_at_most`, e.g., `UnlockNativeToken` = 200_000 gas). This is "public underpriced work": the sender pays no fee to cover the Ethereum-side execution/reward, yet the message is still queued, committed into the Merkle root, and expected to be relayed and executed on the Ethereum Gateway. Relayers who are supposed to be reimbursed via `reward`/`fee_per_gas` embedded in the committed message do not actually get compensated by user-paid fees, degrading relayer incentives and stalling bridge message processing (backlog of undercompensated messages) — matching the "public underpriced work that degrades block production or stalls bridge processing" impact category for Snowbridge.

### Likelihood Explanation
The specific numeric example in the test requires specific parameter combinations that governance sets via `set_pricing_parameters` (the divisor chain depends on `exchange_rate`, `multiplier`, `fee_per_gas`, `reward`, and the `Decimals` scaling constant of 10^6/10^8). While governance chooses these parameters, the rounding-to-zero condition is a function of ordinary/valid parameter magnitudes relative to `gas_used_at_most` for cheap commands, not of any malicious or out-of-range configuration — the pallet's own unit test reproduces it with "valid" parameters. Any user who can construct a low-gas message under prevailing pricing parameters can trigger the zero-fee path without needing a malicious peer, relayer, or governance actor.

### Recommendation
Add an explicit floor check in `calculate_fee` (or in `validate`) rejecting/erroring when the computed `remote` fee rounds to zero for a message with nonzero expected gas usage, analogous to the fix applied to `pallet-asset-conversion`'s quote functions:
```rust
let fee = Fee::from((Self::calculate_local_fee(), fee));
ensure!(gas_used_at_most == 0 || !fee.remote.is_zero(), Error::<T>::InvalidPricingParameters);
```
Additionally consider using round-up division (analogous to `get_amount_in`'s `+1` rounding) instead of round-down/truncating division in `checked_div`/`convert_from_ether_decimals`, so any non-zero cost never resolves to `Some(0)`.

### Proof of Concept
The existing test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` is itself the PoC: [3](#0-2) 
With `gas_used_at_most = 250000`, `exchange_rate = 1/1`, `fee_per_gas = 1`, `reward = 1`, `multiplier = 1/1`, `calculate_fee` returns `fee.remote == 0` while `fee.local == 698000000`. Any message routed through `SendMessage::validate` under these (or similarly structured) `PricingParameters` will be enqueued and delivered while the sender is charged zero for the Ethereum-side cost/reward component.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {
		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
			exchange_rate: FixedU128::from_rational(1, 1),
			fee_per_gas: 1_u32.into(),
			rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});
}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}
