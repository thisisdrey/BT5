### Title
`mt_resolve_withdraw` treats a wrong-length `mt_batch_transfer_call` response as "nothing used", fully refunding tokens that were already irrevocably delivered - ([File: `contracts/defuse/src/contract/tokens/nep245/withdraw.rs`])

### Summary
`mt_resolve_withdraw` parses the promise result of `mt_batch_transfer_call` with `promise_result_checked_json_with_len::<Vec<U128>>`, and any successfully-deserialized but wrong-length response falls into the `Ok(_) => vec![U128(0); amounts.len()]` branch, which is interpreted as "zero tokens were used" and triggers a full internal re-credit via `self.deposit`. Because the external token contract that received the transfer is fully attacker-controlled, the attacker can make delivery unconditional while returning a malformed-length response, causing Defuse to credit back the withdrawn amount even though it already treated the transfer as delivered externally.

### Finding Description
The broken binding: `balance_debited_by_withdraw (1000)` should equal `assets_delivered_externally (1000)` OR `amount_recredited_internally (1000)` — never both. The code path:

1. `internal_mt_withdraw` (`contracts/defuse/src/contract/tokens/nep245/withdraw.rs:60-125`) subtracts 1000 from `owner_id`'s `token_balances` for `TokenId::Nep245(attacker_mt_contract, "id1")` via `self.withdraw(...)`, then schedules `do_mt_withdraw` → `mt_batch_transfer_call` on `withdraw.token` (the attacker's own deployed contract), followed by `mt_resolve_withdraw` as the resolving callback.
2. `do_mt_withdraw` (lines 154-197) issues `ext_mt_core::ext_on(p).mt_batch_transfer_call(receiver_id, token_ids, amounts, ..., msg)` against `withdraw.token`, an account the attacker fully controls and can implement arbitrarily (permitted per the attacker profile: "deploy and control their own ... MT ... contracts").
3. In `mt_resolve_withdraw` (lines 200-257):
   ```rust
   let mut used = if is_call {
       match promise_result_checked_json_with_len::<Vec<U128>>(0, amounts.len()) {
           Ok(Ok(used)) if used.len() == amounts.len() => used,
           Ok(_) => vec![U128(0); amounts.len()],   // <-- wrong-length or unexpected shape
           Err(_) => amounts.clone(),
       }
   } ...
   self.deposit(sender_id, ..., refund = amount - used, ...)
   ```
   The attacker's `mt_batch_transfer_call` implementation can unconditionally mark the tokens as delivered to `receiver_id` (the attacker) in its own contract storage — an irreversible external state change — while returning a JSON value that parses as `Vec<U128>` but has the wrong length (e.g., `vec![]` for a 1-element request). This lands in `Ok(_) => vec![U128(0); amounts.len()]`, so `used.0.min(amount.0) = 0`, making `refund = amount.0 = 1000`, and `self.deposit` re-credits the full 1000 back to the attacker's `token_balances` inside the Verifier.
4. No existing guard prevents this: `promise_result_checked_json_with_len` only validates deserializability and byte-length bounds, not semantic correctness of the vector's length; the length check `used.len() == amounts.len()` explicitly routes any mismatch into the "treat as zero used" branch rather than the conservative `amounts.clone()` (as-used) fallback used for the `Err(_)` (promise failure) branch.

Result: the attacker ends up with 1000 units marked delivered on their own external contract AND 1000 units re-credited inside Defuse's `token_balances` — for a single debit of 1000 — breaking the conservation invariant that a resolver's re-credit must match exactly what failed to settle. ### Impact Explanation
The credited/duplicated value is confined to the `TokenId` namespace `nep245:<attacker's own contract>:<token_id>`, which the attacker already fully controls end-to-end (both the Defuse-side signer and the external contract implementation). The bug is a genuine internal-accounting/conservation violation inside the Verifier's `token_balances` matching the listed Critical category "a refund or resolver credit that does not match what failed to settle": Defuse's own state ends up crediting tokens it already regarded as successfully transferred out. It is repeatable per withdraw call and does not require any privileged role, relayer key, or victim key — only a signed `MtWithdraw` intent and a deployed callee contract that the attacker controls.

### Likelihood Explanation
Preconditions are minimal and entirely attacker-controlled: deploy an NEP-245-style contract, obtain internal Defuse balance for a self-namespaced `TokenId` (trivially obtainable for free by calling `mt_on_transfer` directly, since Defuse trusts the caller's self-reported deposit as noted in the existing test comment in `mt_transfer_resolve_gas.rs`), then sign an `MtWithdraw` for that token targeting the attacker's own contract with a `msg` (forcing `is_call = true`), and implement `mt_batch_transfer_call` to mark delivery while returning a wrong-length `Vec<U128>`. No relayer key, DAO role, or victim signature is needed; the attack is fully reproducible in a `near-workspaces` sandbox test.
