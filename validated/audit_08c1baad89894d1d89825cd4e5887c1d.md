### Title
Missing freshness/replay check on initiator-owned tunnels lets a replayed stage-1 handshake overwrite an active session (persistent DoS) - (File: `handshake_manager.go`)

### Summary
`HandshakeManager.CheckAndComplete` is the function that decides whether an inbound handshake attempt is allowed to replace an existing, fully-established tunnel in `mainHostMap`. It uses the initiator-supplied `Time` field (`hostinfo.lastHandshakeTime`, sourced from `handshake.Result.HandshakeTime`, which in turn comes straight from the unauthenticated-freshness `payload.Time` field of the peer's handshake message) to decide if the incoming handshake is "newer" than the one currently established. However, the freshness comparison is skipped entirely whenever the *existing* tunnel is one that the local node itself initiated, allowing any previously captured, cryptographically valid (but arbitrarily old) handshake message from that same peer to unconditionally displace the live tunnel.

### Finding Description
The relevant logic is:

```go
// Is this a newer handshake?
if existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime && !existingHostInfo.ConnectionState.initiator {
    return existingHostInfo, ErrExistingHostInfo
}

existingHostInfo.logger(hm.l).Info("Taking new handshake")
``` [1](#0-0) 

This is reached from `beginHandshake`, which is invoked for every inbound stage-1 (`MessageCounter == 1`) handshake packet regardless of whether a completed tunnel already exists for that peer: [2](#0-1) 

`beginHandshake` builds a brand-new responder `Machine` for *any* stage-1 packet, processes it, and if it completes (which the 2-message IX pattern does on the first packet), builds a fresh `HostInfo`/`ConnectionState` and calls `CheckAndComplete`: [3](#0-2) [4](#0-3) [5](#0-4) 

The staleness field `lastHandshakeTime` is populated directly from the wire-supplied, self-reported `Time` field inside the handshake payload — a value the sender fully controls and which is not bound to any replay window, nonce, or session identifier: [6](#0-5) [7](#0-6) 

The protocol's dedicated anti-replay/anti-DoS field was never implemented, which is explicitly called out in the wire-format documentation: [8](#0-7) 

Putting this together: if my node previously **initiated** a handshake to a peer (so `existingHostInfo.ConnectionState.initiator == true`), then the `!existingHostInfo.ConnectionState.initiator` guard is always `false`, and the entire staleness check is bypassed — *no matter how old or already-superseded* the incoming handshake's `Time` value is. Any attacker who has ever observed a single valid stage-1 packet sent by that peer to me (a completely passive, off-path capability — no CA-issued certificate or private key is needed) can replay it at will. Because IX completes on the first message from the responder's point of view, `beginHandshake` will complete the (replayed) handshake locally, `CheckAndComplete` will unconditionally accept it as "newer," and `unlockedAddHostInfo` will make the stale, freshly-built `HostInfo` the new primary entry for that VPN address: [9](#0-8) 

The live tunnel's connection state is thereby replaced by dead, unusable ephemeral keys that the real peer never derived, breaking outbound data-plane traffic for that VPN address until a fresh handshake eventually recovers it — at which point the attacker can simply replay the captured packet again.

### Impact Explanation
This is a remote, unauthenticated, off-path denial-of-service against any established Nebula tunnel where the local node is the handshake initiator. No knowledge of private keys or the CA is required — only observation of a single genuine, historical handshake packet from the peer (obtainable via network capture, since UDP handshake packets traverse the network and are not otherwise protected against replay). The attacker can repeatedly and indefinitely disrupt/reset the tunnel, denying legitimate traffic — directly analogous to the referenced report's "session-agnostic storage accepts stale-but-valid material, causing persistent DoS against session-bound state," except here the "session" is the Noise handshake/tunnel state rather than a guardian share.

### Likelihood Explanation
Likelihood is realistic: passively capturing one legitimate stage-1 UDP packet between two Nebula nodes (e.g., from a shared network segment, a relay, or logs) is sufficient, and the replay can be repeated indefinitely at low cost with no interaction from either legitimate peer, and no signed certificate of the attacker's own is required.

### Recommendation
Bind the "is this handshake newer" decision to real replay protection rather than trusting the peer-supplied `Time` value asymmetrically:
- Remove (or heavily restrict) the `!existingHostInfo.ConnectionState.initiator` carve-out in `CheckAndComplete`, and instead always require `hostinfo.lastHandshakeTime` to be strictly greater than `existingHostInfo.lastHandshakeTime` before an established main-hostmap tunnel can be replaced, regardless of which side initiated the existing tunnel.
- Consider incorporating a monotonic, locally-tracked "last seen" counter or a proper nonce/session binding for the handshake exchange (the reserved-but-unimplemented `Cookie` anti-DoS field could be revisited here) so stale-but-valid captured handshake messages cannot be replayed to legitimately complete a new handshake and hijack an active tunnel slot.
- If the "responder always wins on simultaneous handshake" behavior is intentionally retained for race resolution (see `TestStage1Race`), it should only apply to genuinely concurrent, in-flight handshake attempts (correlated by a fresh nonce/challenge issued by this node), not to arbitrary replays of old completed handshakes.

### Proof of Concept
1. Node A initiates a handshake to Node B and a tunnel is established; A's `HostInfo.ConnectionState.initiator == true` for this tunnel.
2. An attacker passively captures the original stage-1 packet A→B (or B→A depending on direction) at the time it was sent.
3. At any later time, the attacker resends that exact captured stage-1 packet to A (spoofing/relaying it as if from B's UDP address, or simply replaying it if source-address filtering is not enforced upstream).
4. `HandleIncoming` → `beginHandshake` on A processes it as a new, self-completing IX handshake and calls `CheckAndComplete`.
5. Because A's existing tunnel with B was initiator-owned, the staleness check `existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime && !existingHostInfo.ConnectionState.initiator` evaluates to `false` regardless of the old packet's `Time` value, so the replay is accepted ("Taking new handshake") and becomes the new primary `HostInfo` for B's VPN address.
6. A's data plane now encrypts/decrypts using stale keys B never derived for this instant; legitimate traffic between A and B fails until a new real handshake is completed — which the attacker can immediately disrupt again by repeating step 3.

func (hm *HandshakeManager) beginHandshake(via ViaSender, packet []byte, h *header.H) {
	f := hm.f
	cs := f.pki.getCertState()

	v := cs.DefaultVersion()
	if cs.GetCredential(v) == nil {
		f.l.Error("Unable to handshake with host because no certificate is available",
			"from", via, "certVersion", v)
		return
	}

	machine, err := handshake.NewMachine(
		v, cs.GetCredential,
		hm.certVerifier(), func() (uint32, error) { return generateIndex(f.l) },
		false, header.HandshakeIXPSK0,
	)
	if err != nil {
		f.l.Error("Failed to create handshake machine", "from", via, "error", err)
		return
	}

	response, result, err := machine.ProcessPacket(nil, packet)
	if err != nil {
		f.l.Error("Failed to process handshake packet", "from", via, "error", err)
		return
	}
