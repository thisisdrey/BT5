### Title
`RewardsDistributor._calculateTokenDelta` treats an uninitialized `accountIndexOf` (zero value) as a valid index, minting `balance` reward tokens to pre-existing holders — ([File: contracts/RewardsDistributor.sol])

### Summary
Analogous to `SegQueue`/`mem::zeroed()` producing a zero value of a type where zero is invalid, `RewardsDistributor` reads `accountIndexOf[token_][account_]` which defaults to `0` for any account that was never updated. The zero index is supposed to mean "uninitialized — fall back to `INITIAL_INDEX`", but the fallback only applies when the global index is strictly greater than `INITIAL_INDEX`. When the global `tokenStates[token_].index` is exactly `INITIAL_INDEX` (1e18) — i.e., the window right after a reward token is activated — `_deltaIndex = 1e18 - 0 = 1e18`, and the account is credited `balanceOf(account).wadMul(1e18) = balance` reward tokens for free.

### Finding Description
In `contracts/RewardsDistributor.sol`:

```solidity
// contracts/RewardsDistributor.sol:222-230
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

While `tokenStates[token_].index == 0` (token not yet registered for rewards), `updateBeforeMintOrBurn`/`updateBeforeTransfer`/`claimRewards` all skip updates (lines 156, 176, 187), so every holder keeps `accountIndexOf == 0` even with a positive balance.

When the governor first enables rewards, `_updateTokenSpeed` sets `tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: now})` (line 298). As long as the index remains exactly `INITIAL_INDEX` (`_deltaTimestamps == 0` in the same block, or `totalSupply == 0`), a call to `claimRewards(account, [token])` or the public `updateBeforeMintOrBurn` hits the vulnerable path: `_tokenIndex == INITIAL_INDEX` fails the `> INITIAL_INDEX` fallback check, `_accountIndex` stays `0`, and `_tokensDelta = balance * 1`. This is stored into `tokensAccruedOf[account]` (line 264) and paid out by `_transferRewardIfEnoughTokens` (lines 248-255) up to the distributor's `rewardToken` balance.

### Impact Explanation
Any account holding a `DepositToken` or `DebtToken` balance at the moment rewards are activated for that token can claim reward tokens equal to their full token balance, draining the `RewardsDistributor`'s `rewardToken` reserves — direct theft of unclaimed yield belonging to all users. An attacker can pre-position by depositing collateral (or issuing debt) before a reward token is enabled, then back-run the governor's `updateTokenSpeed`/`syncTokenSpeed` transaction in the same block (index still `INITIAL_INDEX` because `deltaTimestamps == 0`) to claim the inflated accrual. The same code path is reachable permissionlessly via `updateBeforeMintOrBurn`, which "may be called by anyone" (line 173).

### Likelihood Explanation
The preconditions are mild and occur naturally: a user only needs a non-zero deposit/debt balance recorded before the token is registered in the distributor — which is the default state, since all index updates are skipped while `tokenStates[token_].index == 0`. The trigger is calling `claimRewards`/`updateBeforeMintOrBurn` while `index == INITIAL_INDEX`, which holds in the activation block and anytime the speed is 0 or supply is 0 afterward. The exploit is one-shot per account (the call writes `accountIndexOf = INITIAL_INDEX`), but attacker-controlled contracts can each hold a balance before activation, and the payout scales linearly with deposited balance, so a single large deposit is sufficient to drain the reward pool.

### Recommendation
Treat `accountIndexOf == 0` as "unset" whenever the token index is at or above `INITIAL_INDEX`, i.e., change the fallback to `if (_accountIndex == 0) { _accountIndex = INITIAL_INDEX; }` when `_tokenIndex >= INITIAL_INDEX` (or `>=`/`> 0`), so that a zero account index never participates in `_tokenIndex - _accountIndex` as a real value — mirroring the upstream fix of replacing `mem::zeroed()` with `MaybeUninit` semantics.

### Proof of Concept
Foundry-style test against deployed mainnet `Pool`/`DepositToken`/`RewardsDistributor` (addresses from `deployments/mainnet/`):

```solidity
function testZeroAccountIndexFreeRewards() public {
    // Setup: attacker deposits collateral -> holds depositToken balance B.
    // Token not yet reward-enabled: tokenStates[depositToken].index == 0,
    // so deposit mint path leaves accountIndexOf == 0.
    uint256 B = depositToken.balanceOf(attacker);
    assertGt(B, 0);
    assertEq(distributor.accountIndexOf(depositToken, attacker), 0);

    // Governor enables rewards in the same block (index == INITIAL_INDEX).
    vm.prank(governor);
    distributor.updateTokenSpeed(depositToken, speed);

    // Attacker back-runs in the same block (deltaTimestamps == 0).
    IERC20[] memory toks = new IERC20[](1);
    toks[0] = depositToken;
    uint256 balBefore = rewardToken.balanceOf(attacker);
    distributor.claimRewards(attacker, toks);

    // tokensDelta == B * wadMul(1e18) == B paid out in rewardToken.
    assertEq(rewardToken.balanceOf(attacker), balBefore + B);
}
```
