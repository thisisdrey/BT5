### Title
StackerDB write-frequency (`write_freq`) rate limit is never enforced on chunk writes, allowing unlimited-rate authenticated writes and network-wide propagation flooding - (File: stackslib/src/net/stackerdb/db.rs)

### Summary
`StackerDBConfig::write_freq` is documented as "the minimum wall-clock time between writes to the same slot" [1](#0-0)  and the protocol even defines a dedicated `net_error::TooFrequentSlotWrites` error for rejecting chunks that violate it [2](#0-1) . However, the actual chunk-acceptance path, `StackerDBTx::try_replace_chunk`, never checks `write_freq`/`write_time` at all — it only validates chunk size, signer, staleness, and `max_writes` [3](#0-2) . This is analogous to the Nouns DAO bug class: a configured guardrail parameter (`write_freq`, like `forkPeriod`) exists and is advertised/trusted by the protocol, but the code path that should enforce it silently accepts writes that violate the configured invariant, breaking the equality between "configured policy" and "enforced policy."

### Finding Description
`write_freq` is only consulted in the StackerDB *pull/sync* path, where it's used to decide whether to *fetch* a chunk from a peer [4](#0-3) . It is never consulted when a node *accepts and stores* a chunk. Both remote write entry points funnel into `try_replace_chunk`:
- The unauthenticated-facing HTTP endpoint `POST /v2/stackerdb/:contract/chunks`, which calls `tx.try_replace_chunk(...)` directly [5](#0-4) , and on success re-broadcasts the chunk to the whole p2p network [6](#0-5) .
- The p2p unsolicited-push path, which also stores accepted uploaded chunks and unconditionally re-broadcasts them to all neighbors via `process_uploaded_stackerdb_chunks` [7](#0-6) .

Because `try_replace_chunk` never checks `slot_validation.write_time + config.write_freq > now`, any remote party holding a valid slot signing key (any registered StackerDB signer — not an admin, and requiring no special privilege beyond being one of the configured signers for that replica, e.g. a Nakamoto miner slot or a `.signers-XX-YY` participant) can submit new chunk versions as fast as the network/API allows, completely ignoring the configured `write_freq`. The only remaining throttle is `max_writes` (a total version-count cap, not a rate cap) [8](#0-7) , which does not bound the *rate* of writes at all — an attacker can burn through the entire `max_writes` budget in as many requests as the HTTP/relay layer will process, and legitimate replicas/miner configs even set `write_freq: 0` / `max_writes: u32::MAX` for signer databases [9](#0-8) , but crucially for contracts that *do* configure a nonzero `write_freq` intending to throttle writes, that intention is silently unenforced.

`TooFrequentSlotWrites` is defined and has a `Display` impl [10](#0-9)  but is never constructed/returned anywhere in the write path — confirming this is dead/unreachable protection, not an intentional design choice.

### Impact Explanation
Each accepted chunk write triggers a SQLite `UPDATE` on every replicating node's local StackerDB copy and a broadcast/relay of the chunk to that node's peers [11](#0-10) . Without rate enforcement, a single authenticated slot owner can force unbounded disk-write and network-propagation load across every node hosting that StackerDB replica — a bounded-compute/storage DoS driven by a small number of authenticated, low-cost requests, not merely raw traffic volume, since it exploits amplification through legitimate gossip/relay of "valid" but policy-violating writes to the entire replica set. This directly undermines the write-frequency guarantee that downstream contract designers rely on (e.g. throttling how often signers post block votes/signatures), similar in class to how an unenforced `forkPeriod` guardrail let a malicious actor bypass an intended protection.

### Likelihood Explanation
Low complexity, no special privilege required beyond already being a registered slot signer for a target StackerDB contract (a normal, expected participant, e.g., a signer in `.signers-XX-YY`). No collusion or majority vote is needed — a single signer can trigger it at will by posting chunks back-to-back through the standard HTTP or p2p relay path.

### Recommendation
Enforce `config.write_freq` in `StackerDBTx::try_replace_chunk` (stackslib/src/net/stackerdb/db.rs) by comparing `slot_validation.write_time + config.write_freq` against the current wall-clock time before accepting a new chunk version, returning `net_error::TooFrequentSlotWrites` (already defined) when violated — mirroring the check already present in the read/sync path (`sync.rs`).

### Proof of Concept
1. Configure a StackerDB contract with `write-freq: u60` (intending at most one write per slot per minute).
2. As a registered signer for a slot, repeatedly `POST /v2/stackerdb/<contract>/chunks` with strictly increasing `slot_version` values, each properly signed.
3. Observe that every request is accepted (`try_replace_chunk` only checks size/signature/staleness/`max_writes`), each acceptance triggers a `StackerDBPushChunk` broadcast to all peers, and the configured 60-second interval is never enforced, contrary to the contract's declared policy and the existence of the unused `TooFrequentSlotWrites` error code.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }

    /// Process HTTP-uploaded stackerdb chunks.
    /// They're already stored by the RPC handler, so all we have to do
    /// is forward events for them and rebroadcast them (i.e. the fact that we stored them and got
    /// this far at all means that they were novel, and thus potentially novel to our neighbors).
    pub fn process_uploaded_stackerdb_chunks(
        &mut self,
        rc_consensus_hash: &ConsensusHash,
        uploaded_chunks: Vec<StackerDBPushChunkData>,
        event_observer: Option<&dyn StackerDBEventDispatcher>,
    ) {
        let mut all_events: HashMap<QualifiedContractIdentifier, Vec<StackerDBChunkData>> =
            HashMap::new();
        for chunk in uploaded_chunks.into_iter() {
            // Always forward the event to ensure the local signer receives it.
            if event_observer.is_some() {
                if let Some(events) = all_events.get_mut(&chunk.contract_id) {
                    events.push(chunk.chunk_data.clone());
                } else {
                    all_events.insert(chunk.contract_id.clone(), vec![chunk.chunk_data.clone()]);
                }
            }

            if chunk.rc_consensus_hash != *rc_consensus_hash {
                debug!("Not rebroadcasting stale uploaded StackerDB chunk";
                           "stackerdb_contract_id" => %chunk.contract_id,
                           "slot_id" => chunk.chunk_data.slot_id,
                           "slot_version" => chunk.chunk_data.slot_version,
                           "chunk.rc_consensus_hash" => %chunk.rc_consensus_hash,
                           "network.rc_consensus_hash" => %rc_consensus_hash);
                continue;
            }

            debug!("Got uploaded StackerDB chunk"; "stackerdb_contract_id" => %chunk.contract_id, "slot_id" => chunk.chunk_data.slot_id, "slot_version" => chunk.chunk_data.slot_version);

            let msg = StacksMessageType::StackerDBPushChunk(chunk);
            if let Err(e) = self.p2p.broadcast_message(vec![], msg) {
                warn!("Failed to broadcast StackerDB chunk: {e:?}");
            }
        }
