### Title
Unstaked-peer connection limit can be multiplied via low-stake identity churn because ConnectionTableKey is keyed by pubkey (not source IP) whenever a recognized-but-negligible-stake pubkey is presented - (File: streamer/src/nonblocking/swqos.rs)

### Summary
`SwQos::build_connection_context` downgrades any staked pubkey whose `stake_ratio` is below `min_stake_ratio` to `ConnectionPeerType::Unstaked`, but it still keeps the recognized `remote_pubkey` in the resulting context. `cache_new_connection` then builds the connection-table key from `(ip, remote_pubkey)`, which resolves to a per-pubkey key whenever a pubkey is present, instead of the per-IP key used for truly anonymous unstaked clients. This lets an attacker who controls many distinct negligible-stake identities obtain a separate `max_connections_per_unstaked_peer` allotment per identity from a single source IP, rather than being capped once per IP like a genuinely stakeless client.

### Finding Description
`build_connection_context` classifies a peer as `ConnectionPeerType::Unstaked` in two distinct situations:
1. The pubkey is not found in `staked_nodes` at all → `remote_pubkey = None`.
2. The pubkey is found with stake below `min_stake_ratio` (`stake_ratio < min_stake_ratio`) → `remote_pubkey = Some(pubkey)`, but `peer_type = Unstaked`. [1](#0-0) 

`cache_new_connection` then does:
```rust
let max_connections_per_peer = match conn_context.peer_type() {
    ConnectionPeerType::Unstaked => self.config.max_connections_per_unstaked_peer,
    ConnectionPeerType::Staked(_) => self.config.max_connections_per_staked_peer,
};
connection_table_l.try_add_connection(
    ConnectionTableKey::new(remote_addr.ip(), conn_context.remote_pubkey),
    ...
    max_connections_per_peer,
    ...
)
``` [2](#0-1) 

`ConnectionTableKey::new(ip, maybe_pubkey)` resolves to a `Pubkey`-keyed entry whenever `maybe_pubkey` is `Some`, and only falls back to an `IP`-keyed entry when no pubkey is present. This means: for a genuinely anonymous/zero-stake client (case 1 above), all connections from one source IP collapse into a single table key and are limited once by `max_connections_per_unstaked_peer`. But for a recognized pubkey whose stake is merely below `min_stake_ratio` (case 2), each distinct pubkey gets its own table key even though it is classified `Unstaked` and shares the same `unstaked_connection_table`. An attacker controlling `N` distinct low-stake pubkeys from a single IP therefore obtains up to `N * max_connections_per_unstaked_peer` connection slots (bounded only by the global `max_unstaked_connections` capacity of the shared unstaked table), instead of the single per-IP allotment intended for unstaked traffic.

No existing guard collapses this: the per-peer cap is applied against the table key, not against `remote_addr.ip()` directly, and there is no separate IP-level accounting layered on top of the pubkey-keyed slots for this "recognized-but-below-threshold" bucket.

### Impact Explanation
This is a QoS-evasion bug: an unprivileged/negligibly-staked attacker can consume a disproportionate share of the shared unstaked connection pool from a single source IP by rotating through many negligible-stake identities, each of which is granted its own `max_connections_per_unstaked_peer` slots rather than being aggregated per-IP as intended for unstaked/anonymous traffic. This degrades service for other legitimate unstaked/low-stake clients sharing the same `max_unstaked_connections` pool and stream-throttling budget, though the blast radius is still bounded by the global `max_unstaked_connections` cap (this is not unbounded memory growth, but a QoS-fairness bypass/amplification within the existing bounty category for QoS evasion).

### Likelihood Explanation
Feasible for any attacker who can obtain several distinct pubkeys each delegated a tiny, non-zero stake (delegation amounts well under `min_stake_ratio * total_stake`), which does not require validator/leader/peer/gossip control—only ordinary stake delegation. The attacker only needs to open one QUIC connection per identity from the same IP; no privileged actions, mocked paths, or config changes are required, making this readily repeatable.

### Recommendation
When downgrading a recognized pubkey to `ConnectionPeerType::Unstaked` due to `stake_ratio < min_stake_ratio`, either (a) clear `remote_pubkey` so the connection is keyed by IP like a genuinely anonymous unstaked client, or (b) apply an additional per-IP aggregate cap across all `Unstaked`-classified connections (regardless of key type) before admitting into `unstaked_connection_table`.

### Proof of Concept
Integration test in `streamer/src/nonblocking/swqos.rs` test module:
1. Populate `staked_nodes` with `N` distinct pubkeys, each with stake set just below `min_stake_ratio * total_stake` (e.g., `total_stake` large, each identity stake = 1 lamport), and one large-stake node to keep `total_stake` high.
2. For each of the `N` pubkeys, open a QUIC connection to `SwQos` from the same source IP (varying only the client keypair/pubkey), calling `build_connection_context` then `try_add_connection`.
3. Assert `conn_context.peer_type()` is `ConnectionPeerType::Unstaked` for all `N` connections (confirms downgrade).
4. Assert that all `N * max_connections_per_unstaked_peer` connections are admitted into `unstaked_connection_table` (up to `max_unstaked_connections`), i.e., `unstaked_connection_table.total_size` exceeds `max_connections_per_unstaked_peer` even though every connection originates from the same IP—demonstrating the per-IP cap does NOT dominate, contradicting the intended invariant that unstaked per-source limits cannot be multiplied by identity churn.

impl QosController<SwQosConnectionContext> for SwQos {
    fn build_connection_context(&self, connection: &Connection) -> SwQosConnectionContext {
        let remote_address = connection.remote_address();
        get_connection_stake(connection, &self.staked_nodes).map_or(
            SwQosConnectionContext {
                peer_type: ConnectionPeerType::Unstaked,
                total_stake: 0,
                remote_pubkey: None,
                in_staked_table: false,
                remote_address,
                stream_counter: None,
                last_update: Arc::new(AtomicU64::new(timing::timestamp())),
            },
            |(pubkey, stake, total_stake)| {
                // The heuristic is that the stake should be large enough to have 1 stream pass through within one throttle
                // interval during which we allow max (MAX_STREAMS_PER_MS * STREAM_THROTTLING_INTERVAL_MS) streams.

                let peer_type = {
                    let max_streams_per_ms = self.staked_stream_load_ema.max_streams_per_ms();
                    let min_stake_ratio =
                        1_f64 / (max_streams_per_ms * STREAM_THROTTLING_INTERVAL_MS) as f64;
                    let stake_ratio = stake as f64 / total_stake as f64;
                    if stake_ratio < min_stake_ratio {
                        // If it is a staked connection with ultra low stake ratio, treat it as unstaked.
                        ConnectionPeerType::Unstaked
                    } else {
                        ConnectionPeerType::Staked(stake)
                    }
                };
