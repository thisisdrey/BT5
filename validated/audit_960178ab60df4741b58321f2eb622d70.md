### Title
DelegateAction nonce replay via DeleteKey+AddKey(same public key) resetting `access_key.nonce` below previously consumed delegate nonce - (File: runtime/runtime/src/actions.rs, runtime/runtime/src/access_keys.rs)

### Summary
`verify_and_charge_delegate_action`'s nonce check at `runtime/runtime/src/actions.rs:632` compares a `DelegateAction`'s nonce only against the *current* on-chain `access_key.nonce`. Because `add_regular_key` in `runtime/runtime/src/access_keys.rs:230-255` unconditionally resets a re-created access key's nonce to `initial_nonce_value(block_height) = (block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` instead of preserving the deleted key's prior nonce (as the design comment in `docs/DataStructures/AccessKey.md` and `core/primitives-core/src/account.rs:732-734` says it should), an attacker who deletes and re-adds the *same* public key in the same block height as a previously-executed `DelegateAction` can drive `current_nonce` below the already-consumed `delegate_nonce`, allowing the identical `DelegateAction` to be resubmitted and executed twice.

### Finding Description
Delegate-action nonce validation and persistence: [1](#0-0) [2](#0-1) 

After a `DelegateAction` with nonce `N1` executes successfully, `access_key.nonce` is set to `N1` and persisted. The upper bound check uses the *execution-time* block height: [3](#0-2) 

Key re-creation with the same public key does not preserve the prior nonce — it always derives a fresh floor from the current block height: [4](#0-3) [5](#0-4) 

This directly contradicts the stated design intent recorded in the data-structure documentation and the field comment on `AccessKey`, both of which say a re-created key with the same public key must retain the old key's nonce specifically "to avoid replaying old transactions again": [6](#0-5) [7](#0-6) 

Exploit flow:
1. Attacker's account (delegate-action signer) has a `DelegateAction #1` with `delegate_nonce = N1` forwarded by any relayer R1. Because signer (relayer) ≠ receiver (attacker), this executes as an *incoming* receipt at some block height `H1`, setting `access_key.nonce = N1` (`actions.rs:715`) where `N1 < H1 * 1_000_000` (from the upper-bound check).
2. The attacker separately submits, from their own account (`signer_id == receiver_id`, so it is a *local receipt* executed in the very same block it is included in — confirmed by `docs/RuntimeSpec/ApplyingChunk.md:39,51-62` and `runtime/runtime/AGENTS.md:27`), a transaction with `[DeleteKey(same pubkey), AddKey(same pubkey)]`.
3. If this local transaction lands in the exact same block height `H1` as step 1, `add_regular_key` resets `access_key.nonce = (H1-1) * 1_000_000`, which is below `N1` for essentially the entire valid nonce range at height `H1` (any nonce chosen close to the natural block-height-derived nonce, not just extreme edge values, satisfies `N1 > (H1-1)*1_000_000`).
4. The attacker (or relayer) resubmits the identical `DelegateAction #1` (same signature, same `N1`). The check at `actions.rs:632` now passes because `current_nonce = (H1-1)*1_000_000 < N1`, and the upper-bound check at the new execution height `H3 ≥ H1` also passes since `N1 < H1*1_000_000 ≤ H3*1_000_000`. The delegated actions (e.g. a `Transfer` or `FunctionCall`) execute a second time.

No existing check (signature, access-key permission, gas metering, storage staking) blocks this: the signature is genuine (same key material redeployed under the same public key), and the *only* replay defense — the monotonic nonce comparison — is defeated by the block-height-based reset that discards the key's prior nonce state instead of carrying it forward.

### Impact Explanation
Double execution of a delegated action is a direct fund-theft / double-spend primitive: a delegated `Transfer`, `FunctionCall` performing a withdrawal, or any state-mutating relayed action executes twice for the cost of one authorization, matching NEAR's "double-spend/replay" and "theft of user funds" bounty categories. The attacker acts entirely against their own account's key material and a permissionless relayer, requiring no validator or node privilege.

### Likelihood Explanation
Preconditions: attacker must own the account signing the `DelegateAction`, control timing of their own `DeleteKey+AddKey` local transaction, and land it in the same block height as their relayed `DelegateAction` receipt's execution. Since incoming-receipt latency after a cross-account transaction is deterministic (one block after the originating transaction is included, absent congestion/delay queues), and local transactions execute in the same block they're included in, the attacker can predict the target height and retry the local `DeleteKey+AddKey` transaction across consecutive blocks (using their independent, unrelated transaction nonce) until the alignment succeeds — cheap and repeatable, bounded only by gas fees for a few retried local transactions.

### Recommendation
Preserve the deleted access key's nonce when a key with the same public key is re-added (`add_regular_key` in `runtime/runtime/src/access_keys.rs`), e.g., track the highest nonce ever used per `(account_id, public_key)` independent of key deletion, or fall back to `max(initial_nonce_value(block_height), last_known_nonce_for_this_pubkey)`. Alternatively, tie `DelegateAction` nonce validation to a monotonically increasing per-account or per-key "generation" identifier that cannot be reset by delete/re-add, so a stale `DelegateAction` can never satisfy the nonce check again regardless of key churn.

### Proof of Concept
Runtime/test-loop integration test:
1. Set up account `attacker` with full-access key `K`.
2. At block height `H1`, submit a relayed transaction from `relayer` containing `SignedDelegateAction` with `nonce = N1` targeting `attacker` → succeeds, mutates `access_key(attacker, K).nonce = N1`.
3. In the same block height `H1`, submit a local transaction from `attacker` (`signer_id == receiver_id == attacker`) with actions `[DeleteKey(K), AddKey(K, full_access)]`.
4. Assert `get_access_key(attacker, K).nonce == (H1-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER < N1`.
5. Resubmit the identical `SignedDelegateAction` from step 2 (same `N1`) via any relayer at height `H3 ≥ H1`.
   - Expected (bug present): receipt succeeds and executes the delegated action a second time (e.g., transferred balance moves twice, or `DelegateActionInvalidNonce` is NOT raised).
6. Control test: repeat steps 2-5 but force the `DeleteKey`/`AddKey` transaction into block height `H1+1` instead of `H1`; assert the resubmitted `DelegateAction` now correctly fails with `ActionErrorKind::DelegateActionInvalidNonce { delegate_nonce: N1, ak_nonce: H1*1_000_000 }`, demonstrating the vulnerability is specifically the same-block-height alignment case.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
