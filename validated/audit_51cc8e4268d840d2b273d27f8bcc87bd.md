The off-by-one bug is real and self-documented by the code's own comment. Let me lay out the exact analysis.

---

### Title
Off-by-One Index in `aggregate_and_update_total_supply` Commits Wrong `total_supply` to State for Every Sharded Transaction — (`aptos-move/aptos-vm/src/sharded_block_executor/sharded_aggregator_service.rs`)

---

### Summary

`aggregate_and_update_total_supply` builds a cumulative delta array starting at index 1, but the application loop reads from index `round * num_shards + shard_id` (0-based), which is always one slot behind the correct entry. The code's own comment on line 207 explicitly states the correct index is `round * num_shards + shard_id + 1`. Every shard therefore applies the preceding shard's cumulative delta, and the first shard of the first round always applies the zero-default. The global shard is unaffected because it reads the last element, which happens to be correct.

---

### Finding Description

**Population phase** (`aggr_ts_idx` starts at 1):

| Slot | Content |
|------|---------|
| 0 | `DeltaU128::default()` (zero) |
| 1 | cumulative delta for (round=0, shard=0) |
| 2 | cumulative delta for (round=0, shard=1) |
| … | … |
| `r*S + s + 1` | cumulative delta for (round=r, shard=s) | [1](#0-0) 

**Application phase** reads `aggr_total_supply_delta_ref[round * num_shards + shard_id]` — missing the `+1`: [2](#0-1) 

The code's own comment directly contradicts the implementation:

> `// The 'delta' for the shard/round is in aggr_total_supply_delta[round * num_shards + shard_id + 1]` [3](#0-2) 

**Concrete trace — 2 shards, 2 rounds:**

| (round, shard) | Correct index | Index actually read | Value read |
|---|---|---|---|
| (0, 0) | 1 | 0 | zero default |
| (0, 1) | 2 | 1 | delta of (0,0) |
| (1, 0) | 3 | 2 | delta of (0,1) |
| (1, 1) | 4 | 3 | delta of (1,0) |
| global | 4 | 4 | ✓ correct |

Every `TransactionOutput` in every non-global shard has `update_total_supply` called with a wrong value, which overwrites the `TOTAL_SUPPLY_STATE_KEY` write-set entry with an incorrect `u128`. [4](#0-3) 

The write-set update is unconditional once a `total_supply` entry exists: [5](#0-4) 

---

### Impact Explanation

Every `TransactionOutput` produced by a sharded shard carries a stale or zero cumulative delta for `TOTAL_SUPPLY_STATE_KEY`. When these outputs are committed to the Aptos state store, the on-chain total APT supply is written with an incorrect value for every sharded block. This is an **invalid state commitment** — the committed total supply diverges from the true sum of all minted/burned APT across shards. Depending on the direction of the error, this can silently over- or under-report the circulating supply, corrupting a core chain invariant.

---

### Likelihood Explanation

The bug fires unconditionally whenever `LocalExecutorClient::execute_block` is called with more than one shard. It requires no special transaction crafting — any ordinary user transaction included in a sharded block triggers the wrong delta assignment. The only prerequisite is that sharded execution is enabled on the validator, which is a deployment-level configuration, not an attacker-controlled input. If sharded execution is live on any mainnet validator set, every block processed through it silently corrupts `total_supply`.

---

### Recommendation

Change line 224 from:

```rust
aggr_total_supply_delta_ref[round * num_shards + shard_id]
```

to:

```rust
aggr_total_supply_delta_ref[round * num_shards + shard_id + 1]
```

This aligns the read index with the population index (`aggr_ts_idx` starting at 1) and matches the existing comment on line 207.

```rust
// Shard 0 produces total_supply = BASE + 10
// Shard 1 produces total_supply = BASE + 25

//   aggr_total_supply_delta[1] = delta(+10)   <- for shard 0
//   aggr_total_supply_delta[2] = delta(+25)   <- cumulative for shard 1
//
// Application (buggy):
//   shard 0 reads index 0 -> delta = 0  -> total_supply = BASE_VAL + 0  (WRONG, should be BASE_VAL + 10)
//   shard 1 reads index 1 -> delta = +10 -> total_supply = BASE_VAL + 10 (WRONG, should be BASE_VAL + 25)
//
// Assert: shard 0 output carries BASE_VAL + 10  -> FAILS (carries BASE_VAL + 0)
// Assert: shard 1 output carries BASE_VAL + 25  -> FAILS (carries BASE_VAL + 10)
```

The fix (`+1`) makes both assertions pass.
