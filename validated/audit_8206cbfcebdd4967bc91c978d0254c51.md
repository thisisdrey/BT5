### Title
Operator.execute leaks the authenticated `msg.sender` context to arbitrary embedded calls, allowing any contract invoked in the batch to act as the user - (File: contracts/Operator.sol)

### Summary
Like CVE-2019-11739 — where encrypted (protected) content leaks as plaintext when embedded into a different message context (HTML reply/forward) — `Operator.execute` writes the batch initiator's address into transient storage (`MSG_SENDER_STORAGE`) for the entire duration of the batch. Every nested call made from `execute` is performed with `msg.sender == Operator`, and `SynthContext._msgSender()` resolves any such call back to the stored user address. Consequently, any contract that gains execution inside the batch (an attacker-deployed ERC20 transfer hook, a malicious `tokenIn_` passed to `SmartFarmingManager.leverage`, or any target that reenters) can call privileged-by-identity functions on `SyntheticToken`, `DepositToken`, and `Pool` and be authenticated as the victim. The protected sender context "leaks" into embedded third-party code.

### Finding Description
`Operator.execute` stores `msg.sender` in a transient slot, executes an arbitrary list of user-supplied `Call{target,value,callData}` via `functionCallWithValue`, and clears the slot only after all calls finish [1](#0-0) . `SynthContext._msgSender()` returns `getActualMsgSender()` whenever `msg.sender == operator` [2](#0-1) . `getActualMsgSender()` only reverts when the slot is zero — it has no notion of *which* sub-call is executing [3](#0-2) .

`nonReentrant` on `execute` is a per-contract transient guard: it blocks reentering `execute` itself but does nothing to stop an embedded target from calling *other* Metronome contracts mid-batch. Functions like `SyntheticToken.transfer`, `SyntheticToken.approve`, and `SyntheticToken.transferFrom` authenticate solely via `_msgSender()` [4](#0-3) . `SmartFarmingManager.leverage` explicitly accepts an arbitrary `tokenIn_` and calls `token_.safeTransferFrom(...)` on it, which invokes attacker-controlled code while the sender slot still holds the victim [5](#0-4) ; `leverage` itself resolves the account via `_msgSender()` [6](#0-5) .

Attack path (victim batches `approve(maliciousToken)` + `leverage(maliciousToken, ...)` or any swap touching a hooked token):

1. Victim calls `Operator.execute([...])`; `MSG_SENDER = victim`.
2. One call reaches `MaliciousToken.transferFrom` (via `leverage`'s `_safeTransferFrom` or a DEX router call in the batch).
3. `MaliciousToken` calls `msUSD.transfer(attacker, victimMsUsdBalance)` — `msg.sender == Operator`, `SynthContext` returns `victim` → transfer succeeds.
4. Same callback can call `DepositToken.transfer`, `Pool.swap`, `DebtToken.mint`/`issue` (if the victim's position is healthy), or grant `approve(attacker, type(uint256).max)` on all synthetic tokens — all as `victim`.

### Impact Explanation
Direct theft of user funds: the attacker's embedded code can drain the victim's entire `SyntheticToken` balance, unlocked `DepositToken` collateral shares, grant unlimited allowances, and even mint new debt on a healthy victim position and transfer the proceeds. This breaks the identity/authentication invariant of the meta-sender pattern — the exact analog of an encrypted part leaking plaintext when forwarded into an untrusted context. No modifier stops it: `onlyIfCanMint`/`onlyIfCanSeize` checks evaluate the *resolved* sender against registered pools/debt tokens only for mint/seize paths, while plain `transfer`/`approve`/pool user actions are intentionally open to the resolved sender; `whenNotShutdown`/pause flags are config-dependent and normally off.

### Likelihood Explanation
Requires user interaction (the victim must batch a call that reaches attacker-controlled code), matching the CVE's `UI:R` profile. This is realistic: the Operator multicall exists precisely to compose `approve` + `deposit`/`leverage`/`swap` flows, and `leverage` explicitly accepts a user-chosen `tokenIn_` — a malicious token whose `transferFrom` hook reenters is sufficient. Any ERC20 with transfer hooks, or a compromised/malicious swap router target in the batch, exposes the victim's whole position, not just the intended call's funds — the leaked context is global to the transaction, which is what makes this more dangerous than an ordinary "don't call untrusted contracts" footgun.

### Recommendation
Do not keep a global transaction-scoped sender. Scope the trusted context to the specific intended callee, e.g.:
- Pass the sender as an explicit immutable parameter per call (or store a `{sender, expectedTarget}` pair and have `SynthContext` verify `msg.sender == operator` only for calls where Operator forwards to a whitelisted target).
- Alternatively, have `execute` clear/restore the slot around each `Call` and require targets to be registered Metronome contracts, or implement ERC-2771-style trusted-forwarder semantics where only designated protocol contracts honor the forwarded sender.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Operator, IOperator} from "contracts/Operator.sol";
import {IERC20} from "contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract EvilToken {
    ISyntheticTokenLike msUsd; address attacker;
    constructor(address msUsd_, address attacker_) { msUsd = ISyntheticTokenLike(msUsd_); attacker = attacker_; }
    function balanceOf(address) external view returns (uint256) { return 0; }
    function transferFrom(address, address, uint256) external returns (bool) {
        // Reenter Metronome while Operator's MSG_SENDER slot = victim
        uint256 bal = msUsd.balanceOf(address(this)); // placeholder; query victim via pool
        msUsd.transfer(attacker, /* victim balance */ bal);
        return true;
    }
}
interface ISyntheticTokenLike { function balanceOf(address) external view returns (uint256); function transfer(address,uint256) external returns (bool); }

contract SenderLeakTest is Test {
    Operator operator; address victim = address(0xVIC); address attacker = address(0xBAD);
    function test_senderLeaksIntoEmbeddedCall() public {
        // victim batches: approve(evil) + sfm.leverage(evil, depositToken, msUSD, ...)
        vm.prank(victim);
        IOperator.Call[] memory calls = new IOperator.Call[](1);
        calls[0] = IOperator.Call({target: address(sfm), value: 0,
            callData: abi.encodeCall(sfm.leverage, (IERC20(address(evil)), depositToken, msUsd, 1e18, 2e18, 0))});
        operator.execute(calls);
        assertEq(msUsd.balanceOf(victim), 0);          // drained
        assertGt(msUsd.balanceOf(attacker), 0);
    }
}
```
The `MaliciousToken.transferFrom` hook executes while `MSG_SENDER == victim`; its call to `msUsd.transfer` resolves `_msgSender()` to the victim and moves their full balance. (PoC assumes a deployed-fork fixture where the victim holds an msUSD balance and invokes `leverage` with the malicious `tokenIn_`; the same primitive works via any hooked token in the batch.)
