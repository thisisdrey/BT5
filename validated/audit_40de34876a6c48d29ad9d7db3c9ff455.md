### Title
Per-account token-list entries are pinned for passive recipients (e.g. `feeCollector`) and can be attacker-filled, permanently DoSing deposits/withdrawals - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
Analogous to the qibfs dentry leak — a pin acquired on a lookup that the cleanup path never releases — every `_transfer`/`_mint` of a `DepositToken` pins an entry in the recipient's `depositTokensOfAccount` set, while only the holder itself can release it by moving tokens out. The pool `feeCollector` is a permanently accumulating sink for these pins, and any account can be force-pinned via dust `transfer`s. Once an account's combined `debtTokensOfAccount + depositTokensOfAccount` reaches `MAX_TOKENS_PER_USER` (30), `addToDepositTokensOfAccount` reverts, which bricks every fee-bearing deposit/withdraw into `feeCollector` and any `transfer`/`seize` to a pinned victim.

### Finding Description
`Pool.addToDepositTokensOfAccount` enforces a hard cap via `onlyIfAdditionWillNotReachMaxTokens`:

```solidity
// contracts/Pool.sol:143-148
if (debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER) {
    revert UserReachedMaxTokens();
}
```

Entries are added automatically — without recipient consent — on every balance-from-zero transition:

```solidity
// contracts/DepositToken.sol:517-525 (_transfer)
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
if (amount_ > 0 && balanceOf[sender_] == 0) {
    pool.removeFromDepositTokensOfAccount(sender_);
}
```

and identically in `_mint` (lines 485-488). The leak: a recipient that never transfers out can never release the pin. `feeCollector` receives msd-token fees via `_mint` in `deposit()` (line 231) and via `_transfer` in `_withdraw` (line 547), so each new deposit token irrevocably occupies a slot in `feeCollector`'s set — it is a protocol-managed address that will never call `transfer`/`withdraw` to drop entries.

Attack path (unprivileged EOA only):
1. For each of the pool's registered deposit tokens, attacker calls `deposit(dust, attacker)` then `transfer(feeCollector, 1)` (or relies on natural fee accrual). Each transfer appends a permanent entry to `feeCollector`'s list — the "leaked dentry" that is never `dput`-ed.
2. Once `depositTokensOfAccount.length(feeCollector) == 30` (attacker can also dust-transfer to fill slots directly), every subsequent `deposit()` with `depositFee > 0` reverts inside `_mint` → `addToDepositTokensOfAccount`, and every `withdraw()` with `withdrawFee > 0` reverts inside `_transfer` to `feeCollector`.
3. Additionally, `Pool.liquidate` → `DepositToken.seize` → `_transfer(from, liquidator, amount)` reverts for any liquidator whose list is full, which an attacker can induce on its own liquidator competitors, though the primary victim is `feeCollector`.

### Impact Explanation
Permanent liveness failure on core pool functions: all fee-bearing deposits and withdrawals revert pool-wide once `feeCollector`'s set saturates — user collateral becomes frozen (withdraw path bricked) and new deposits are impossible. Since `_transfer`/`_mint` revert atomically, there is no bypass short of governance changing `feeCollector` or the feeCollector contract itself transferring tokens out (it is a plain address constant in `PoolRegistry`, not an executable contract with a sweep function for msd tokens in the standard config). This is a direct analog of the dentry leak: resources (set slots) are acquired on every fee event and never released.

### Likelihood Explanation
Reachable entirely by unprivileged calls (`deposit`, `transfer`). Cost is dust deposits across registered deposit tokens. The gating factor is that the attack requires the pool to register enough deposit tokens to fill 30 slots (feeCollector accrues no debt tokens on its own); on pools with fewer collaterals the natural-fee path still leaks slots permanently but saturates slower/not at all. No privileged role, oracle manipulation, or governance action is required by the attacker; the revert path is not guarded by pause flags, reentrancy locks, or `SynthContext`.

### Recommendation
Do not auto-add recipients to `depositTokensOfAccount` for `feeCollector`/`treasury` sinks, or decouple `MAX_TOKENS_PER_USER` enforcement from `addToDepositTokensOfAccount` so the cap reverts only for the initiating user rather than inside shared code paths (`_mint`/`_transfer`/`seize`). Alternatively, mint/transfer fees in the underlying or a dedicated fee token that does not maintain a per-account pool set, or let `addToDepositTokensOfAccount` silently succeed/fail without reverting the parent transfer.

### Proof of Concept
Hardhat test sketch against deployed pool fixtures:

```typescript
// Fill feeCollector's deposit-token list, then show deposit/withdraw bricked
const feeCollector = await poolRegistry.feeCollector();
const max = (await pool.MAX_TOKENS_PER_USER()).toNumber(); // 30

// 1. Attacker dust-deposits and transfers 1 wei of each msd token to feeCollector
for (const msd of depositTokens) {
  await underlying.connect(attacker).approve(msd.address, DUST);
  await msd.connect(attacker).deposit(DUST, attacker.address);
  await msd.connect(attacker).transfer(feeCollector, 1); // pins entry
}
expect(await pool.getDepositTokensOfAccount(feeCollector)).to.have.length(max);

// 2. Any fee-bearing deposit now reverts (UserReachedMaxTokens inside _mint)
await feeProvider.connect(governor).updateDepositFee(parseEther('0.01'));
await expect(msd.connect(alice).deposit(parseEther('1'), alice.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 3. Any fee-bearing withdraw reverts (_transfer to feeCollector reverts)
await feeProvider.connect(governor).updateWithdrawFee(parseEther('0.01'));
await expect(msd.connect(bob).withdraw(bobBalance, bob.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Caveat: if a given deployment's pool registers fewer than ~30 deposit tokens, the saturation step needs the natural fee-accrual path to also pin remaining slots, which still leaks but may not reach the cap; the severity then reduces to a slow resource leak with no bounded cleanup — same defect class as the referenced dentry leak.
