### Title
Solend withdraw path omits `ACCOUNT_IN_ORDER_EXECUTION` when deciding whether to enforce the health check - ([File: programs/marginfi/src/instructions/solend/withdraw.rs])

### Summary
`_handleExecuteLiquidity()`-style bug class: a code path checks one "defer/override" flag but omits a sibling flag that all analogous paths check together. In marginfi-v2, every standard/external-protocol withdraw handler is supposed to defer the account health check until the end of a receivership liquidation *or* an order-execution transaction, by testing `ACCOUNT_IN_RECEIVERSHIP | ACCOUNT_IN_ORDER_EXECUTION` together. The Solend withdraw handler only tests `ACCOUNT_IN_RECEIVERSHIP`, omitting `ACCOUNT_IN_ORDER_EXECUTION`.

### Finding Description
The standard withdraw instruction, the Kamino withdraw instruction, and the JupLend withdraw instruction all compute a combined flag before deciding whether to run `check_account_init_health` immediately or defer it: [1](#0-0) [2](#0-1) [3](#0-2) 

These all guard the immediate health check with `!marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP | ACCOUNT_IN_ORDER_EXECUTION)`, consistent with the documented invariant that "during liquidation/deleverage or order execution, we skip health checks until the end of the transaction."

The Solend withdraw handler, by contrast, only checks `ACCOUNT_IN_RECEIVERSHIP`: [4](#0-3) 

A `grep` across the codebase for `ACCOUNT_IN_ORDER_EXECUTION` confirms `programs/marginfi/src/instructions/solend/withdraw.rs` is the only withdraw-family file that does not reference this flag, while `marginfi_account/withdraw.rs`, `kamino/withdraw.rs`, `juplend/withdraw.rs`, and `drift/withdraw.rs` all do.

This is structurally the same bug class as the Connext report: one flag (`receiveLocal`/`ACCOUNT_IN_RECEIVERSHIP`) is checked, but a related override/exception flag (`receiveLocalOverrides`/`ACCOUNT_IN_ORDER_EXECUTION`) that is checked in the equivalent branch elsewhere is missing here.

### Impact Explanation
Because `end_execute_order` in `programs/marginfi/src/instructions/marginfi_account/order.rs` defers all health enforcement to the final slippage/max-fee check performed at order end [5](#0-4) , a Solend withdraw invoked mid-order-execution would instead run `check_account_init_health` immediately, using intermediate (possibly transiently unhealthy) account state. This diverges from the documented and implemented behavior for every other supported asset/protocol type in the same withdraw family.

I was not able to fully verify, within the available tooling, whether Solend withdraw is actually included in the permitted-instruction whitelist validated via transaction introspection during order execution (`validate_instructions`/`ix_discriminators` in `order.rs`), nor could I confirm the accounts-level constraints on `LendingAccountWithdraw` (Solend variant) explicitly forbid or allow use during `ACCOUNT_IN_ORDER_EXECUTION`. If Solend withdraw is not reachable from the order-execution flow at all, this inconsistency is dead code with no exploitable impact (a hardening/robustness issue only). If it is reachable, the most likely consequence is a spurious transaction failure/DoS on legitimate order executions involving Solend positions (an unintended stricter check), rather than a bypass that enables theft or bad debt — the opposite direction from the original Connext bug (which caused *bypassed* protections). I could not confirm a concrete theft, insolvency, or unauthorized-transfer outcome from this discrepancy with certainty.

### Likelihood Explanation
Low-to-moderate. The bug requires a user/keeper to combine a Solend-integrated marginfi account with the order/limit-order feature and attempt an order execution sequence that withdraws Solend collateral before the account returns to a maintenance-healthy state — a legitimate and expected pattern per the order-execution design (defer health check to the end). Whether this is actually reachable depends on whitelist/CPI restrictions not fully confirmed here.

### Recommendation
Align `programs/marginfi/src/instructions/solend/withdraw.rs` with the other withdraw handlers by testing `ACCOUNT_IN_RECEIVERSHIP | ACCOUNT_IN_ORDER_EXECUTION` together (as done in `marginfi_account/withdraw.rs`, `kamino/withdraw.rs`, and `juplend/withdraw.rs`), and add a test analogous to the existing receivership/order-execution parity tests to prevent regression. A background engineer should also confirm whether Solend withdraw is currently permitted inside order-execution transactions at all, to determine if this is exploitable/reachable or purely a latent consistency bug.

### Proof of Concept
Not able to construct a full end-to-end PoC without confirming reachability of Solend withdraw inside the order-execution instruction whitelist (unverified within available tool access — recommend a Devin session with full repo/test access to check `ix_discriminators` used by `StartExecuteOrder`/`EndExecuteOrder` validation and the Solend withdraw account constraints).

```rust
    check!(
        order_liab_count.eq(&0), // All order liabilities should be closed
        MarginfiError::OrderLiabilityNotClosed
    );

    let net = order_assets_in_equity;

    // The user slippage constraint we want to enforce is:
    // net >= (1 - slippage) * (tp or sl)
    // where slippage is encoded as a u32 percent (0..100% mapped to 0..u32::MAX).

    // For the TP case another constraint(the max fee constraint) we want to enforce is:
    // net >= (1 - max_fee) * (start health)
    // It may be possible that the value (1 - max_fee) * (start health) is less than the
    // min allowed value based on the user's slippage constraint alone, in that case
    // we clamp it to the slippage, allowing for that much.
    // In the case where the value was greater we use (1 - max_fee) * (start health) instead.

    // Check that the liquidator did not over-withdraw.

    let slippage_frac = {
        let slippage = marginfi_type_crate::types::u32_to_centi(order.max_slippage);
        I80F48::ONE
            .checked_sub(slippage)
            .ok_or_else(math_error!())?
    };

    let max_fee_frac = {
        let max_fee: I80F48 = fee_state.order_execution_max_fee.into();
        I80F48::ONE.checked_sub(max_fee).ok_or_else(math_error!())?
    };

    let start_health = || -> I80F48 { execute_record.order_start_health.into() };

    match order.trigger {
        OrderTriggerType::StopLoss => {
            let sl: I80F48 = order.stop_loss.into();
            let allowed_sl = sl.checked_mul(slippage_frac).ok_or_else(math_error!())?;

            check!(
                net >= allowed_sl,
                MarginfiError::OrderExecutionOverWithdrawal
            );
        }
        OrderTriggerType::TakeProfit => {
            let tp: I80F48 = order.take_profit.into();
            let allowed_tp = tp.checked_mul(slippage_frac).ok_or_else(math_error!())?;

            let allowed_diff = (start_health)()
                .checked_mul(max_fee_frac)
                .ok_or_else(math_error!())?;

            check!(
                net >= allowed_diff && net >= allowed_tp,
                MarginfiError::OrderExecutionOverWithdrawal
            );
```
