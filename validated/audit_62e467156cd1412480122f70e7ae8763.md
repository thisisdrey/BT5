### Title
Single-step, unvalidated marginfi account authority transfer causes permanent loss of account control - ([File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs])

### Summary
`transfer_to_new_account` and `transfer_to_new_account_pda` migrate a user's entire position (`lending_account`) to a brand-new `MarginfiAccount` under a caller-supplied `new_authority`, in a single irreversible on-chain step with no validation of that authority and no two-step "propose/accept" pattern.

### Finding Description
The `TransferToNewAccount` accounts struct defines `new_authority` as a completely unchecked account: [1](#0-0) 

The handler unconditionally uses this value as the authority of the freshly initialized account and permanently disables the old one, with no acceptance step from `new_authority` and no on-chain check that it is non-default/valid: [2](#0-1) [3](#0-2) 

A guard prevents any account from being migrated a second time, so the operation is strictly one-shot and irrecoverable once executed: [4](#0-3) 

This is exactly the bug class from the external report ("single-step process for critical ownership transfer... irrecoverable from any mistakes"), applied to an unprivileged-user-reachable path instead of an admin path: any `MarginfiAccount` authority can accidentally (or via a malicious front-end/dApp/CPI integrator) set `new_authority` to a wrong, unrecoverable, or `Pubkey::default()` address, permanently losing control of all migrated collateral/debt positions. The only zero-address safeguard that exists is client-side, in the CLI helper, and is not enforced by the program: [5](#0-4) 

The test suite explicitly acknowledges the unrestricted nature of this instruction: "Here the user moves authority to some new wallet. WARN: User picks the new authority with no restrictions!" [6](#0-5) 

The `TransferToNewAccountPda` variant has the identical unchecked pattern: [7](#0-6) 

### Impact Explanation
If `new_authority` is set incorrectly (typo, wrong keypair whose private key is unknown, or `Pubkey::default()`), the old account is disabled and its `lending_account` is zeroed/moved to the new account in the same instruction, and that new account can never be re-migrated (`AccountAlreadyMigrated` check blocks any retry). Since `is_signer_authorized` requires a matching signer for the stored `authority`, no one can ever sign for an incorrect/default authority, permanently freezing all deposited collateral and outstanding debt positions tied to that account. This matches the accepted impact class: permanent lock/freeze of user funds due to an irrecoverable, unvalidated critical state transition.

### Likelihood Explanation
This is directly reachable by any unprivileged user or any third-party integrator/dApp building instructions against this program (the account requires only the current authority's signature, no privileged role). Given `new_authority` is a raw `UncheckedAccount` with zero on-chain validation, a single client-side bug, UI bug, or fat-fingered input by an end user is sufficient to trigger permanent loss — the CLI's zero-address guard does not protect users interacting through other clients, SDKs, or direct instruction construction.

### Recommendation
Enforce on-chain that `new_authority.key() != Pubkey::default()` (and ideally exclude the program ID / other clearly invalid values) as a `constraint` on the `TransferToNewAccount`/`TransferToNewAccountPda` accounts structs. Consider adopting a two-step migration: initialize the new account in a "pending" state and require a signed acceptance transaction from `new_authority` before disabling the old account and finalizing the migration, mirroring the recommended propose/accept ownership-transfer pattern from the external report.

### Proof of Concept
1. User calls `transfer_to_new_account(ctx)` with `new_authority = Pubkey::default()` (or any keypair whose private key is unknown/lost).
2. `initialize_migrated_account` sets `new_account.authority = new_authority` unconditionally. [8](#0-7) 
3. `finalize_migrated_old_account` disables the old account and zeroes its `lending_account`, and sets `migrated_to`, blocking any retry via the `AccountAlreadyMigrated` check. [2](#0-1) 
4. All previously deposited collateral/debt positions are now under a `MarginfiAccount` whose `authority` cannot produce a valid signature, permanently locking the funds with no recovery path.

fn finalize_migrated_old_account(
    old_account: &mut MarginfiAccount,
    new_account_key: Pubkey,
