### Title
StackerDB unsolicited-push handler advertises a chunk as accepted in its `StackerDBChunkInv` reply before the chunk is actually committed to storage - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
The InitCapital finding is a class of bug where a value is validated/committed against state observed at one point in time, but the actual state-changing effect happens later, after the underlying state may have moved — producing a mismatch between what was "approved"/advertised and what is actually settled. The direct network analog in this repo is `PeerNetwork::handle_unsolicited_StackerDBPushChunk`, which validates an incoming chunk against the *current* slot versions and then immediately patches and signs a `StackerDBChunkInvData` reply telling the sending peer "I now have version X of this chunk" — before the chunk has actually been written to the StackerDB (`try_replace_chunk`). The real write happens later, asynchronously, in the relayer thread. If that deferred write fails or a different chunk wins the race, the peer has already told the network it possesses data it never actually stored, i.e. the *served inventory* is out of sync with the *committed* database state.

### Finding Description
`validate_received_chunk` ( [1](#0-0) ) checks a pushed chunk's signature, freshness, and size against `expected_versions`, a snapshot of `get_slot_versions()` taken moments earlier via `make_StackerDBChunksInv_or_Nack` ( [2](#0-1) ).

Once validation passes, `handle_unsolicited_StackerDBPushChunk` immediately mutates the *reply* inventory to declare the chunk accepted: [3](#0-2) 

Note the comment "patch inventory -- we'll accept this chunk" — this update happens purely in-memory on the outgoing `StackerDBChunkInvData`, not after a successful DB write. The function then either buffers the reply for the relayer or, if `send_reply` is true, signs and sends this patched inventory straight back to the peer: [4](#0-3) 

The actual persistence of the chunk data happens later and separately, in the relayer's `process_pushed_stacker_db_chunks` → `process_stacker_db_chunks`, which calls `try_replace_chunk` against whatever the DB's *current* state is by the time the relayer gets around to it: [5](#0-4) 

`try_replace_chunk` re-validates signer, staleness (`slot_version <= stored_version`), and `max_writes` against the live DB row at write time ( [6](#0-5) ). Because the P2P thread's optimistic inventory patch and the relayer thread's actual write are two separate steps operating on two different snapshots of state (exactly the "approval time" vs "settlement time" split in the InitCapital bug), a remote, unprivileged neighbor can trigger a case where:
1. The node receives and validates a pushed chunk at version `V` for slot `S` (current stored version `V-1`).
2. The node immediately advertises via `StackerDBChunkInv` that slot `S` is now at version `V`.
3. Before the relayer commits it, another (or the same) neighbor races another valid write to slot `S` (e.g. a legitimately newer version `V+1` from a normal sync, or simply the relayer processing a batch out of order), so `try_replace_chunk` returns `StaleChunk`/`TooManySlotWrites`/`BadSlotSigner` and the store of version `V` is silently dropped (`process_stacker_db_chunks` just logs and `continue`s — [7](#0-6) ).
4. The node has already told the network it holds version `V`, but its actual on-disk state never reflects that write; the served inventory permanently diverges from committed state (until a future overwrite happens to line up again).

This mirrors the acknowledged historical instance of exactly this failure mode in this codebase — the fix note for HTTP-uploaded chunks explicitly describes a chunk being "stored and acknowledged but never announced," which "could stall consensus indefinitely when the lost chunk was a signer's block pre-commit" [8](#0-7) . That fix addressed the HTTP-upload path's event-loss variant; the P2P unsolicited-push path still has the analogous "advertise-before-commit" ordering.

### Impact Explanation
Because `StackerDBChunkInvData` drives the rarest/newest-first download scheduling in `StackerDBSync` ( [9](#0-8) : `if local_version <= remote_version { continue; }`), a peer that falsely believes this node already has version `V` will stop trying to push/backfill that data to it. If the node's actual write never lands, the chunk (potentially a signer's block pre-commit or DKG message) never actually gets replicated to this node, and this node in turn cannot serve it to others, degrading StackerDB-dependent consensus signaling. This matches the "High: steering a node off the tip via false inventory" impact bucket — the falsely-advertised inventory misleads peers about replication state.

### Likelihood Explanation
Any P2P-connected, unauthenticated neighbor can send a `StackerDBPushChunk` message; the send-reply/patch-inventory-before-commit sequence is deterministic and unconditional on the "accept" path, so triggering the race only requires ordinary conditions already anticipated by the design (concurrent writers to the same slot, or relayer processing lag under load — both explicitly acknowledged in the code's own comments about buffering/racing "GetChunk ... TODO: this is racey" at `chat.rs:1974`). No secret keys or privileged roles are required.

### Recommendation
Do not patch/send the optimistic `StackerDBChunkInv` reply until the chunk has actually been durably stored (i.e., move the reply generation to occur after `try_replace_chunk` succeeds in the relayer, or make the P2P handler perform the actual store synchronously before replying, similar to how the HTTP POST handler commits before acknowledging in `poststackerdbchunk.rs`). Alternatively, track slot versions from a authoritative post-commit query rather than mutating an in-flight message speculatively.

### Proof of Concept
Not independently reproduced with a running test harness in this session (no execution environment available); the finding is based on static analysis of the control flow between `handle_unsolicited_StackerDBPushChunk`'s inventory patch (`mod.rs:793-814`, `858-871`) and the deferred, independently-validated write in `Relayer::process_stacker_db_chunks` (`relay.rs:2406-2437`) / `StackerDBTx::try_replace_chunk` (`db.rs:400-438`). A concrete PoC would involve two peers concurrently pushing conflicting valid updates to the same slot to the target node and observing that the target's subsequently-advertised `StackerDBChunkInv` reports a version that `get_slot_versions`/on-disk state does not actually contain after relayer processing completes.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
