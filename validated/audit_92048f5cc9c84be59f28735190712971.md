### Title
Missing upper-bound validation for `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` chain parameters allows unbounded fee changes to be applied to already-broadcast, unprivileged transactions - (File: `actuator/src/main/java/org/tron/core/utils/ProposalUtil.java`)

### Summary
`ProposalUtil.validator()` enforces a numeric range check (`[0, LONG_VALUE]`, i.e. `[0, 1e17]`) on almost every fee-type chain parameter that can be changed via a committee proposal (`TRANSACTION_FEE`, `ASSET_ISSUE_FEE`, `MARKET_SELL_FEE`, `MARKET_CANCEL_FEE`, `UPDATE_ACCOUNT_PERMISSION_FEE`, `MULTI_SIGN_FEE`, etc.). However, `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` fall through with **no validation at all**: [1](#0-0) 

Once a proposal for either of these parameters is approved and applied by `ProposalService.process`, the raw value is saved with no sanity check: [2](#0-1) 

`ENERGY_FEE` (the sun-per-energy price for TVM execution beyond an account's frozen/staked allowance) is consumed directly against a caller's balance in `ReceiptCapsule.payEnergyBill`: [3](#0-2) 

### Finding Description
This mirrors the Teller `setProtocolFee` bug class: a fee-controlling setter with no upper bound, reachable through the normal, non-malicious governance flow (a passed committee/witness proposal), which can retroactively affect transactions that were already signed and broadcast by ordinary users before the fee change took effect. `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` are the only two fee-type `ProposalType` cases in `ProposalUtil.validator()` that `break` immediately with zero range check, in contrast to every sibling fee parameter, which is explicitly capped at `LONG_VALUE` (`1e17`) or a tighter bound (e.g. `MARKET_SELL_FEE`/`MARKET_CANCEL_FEE` capped at `10_000_000_000L`, see `ProposalUtil.java:370-397`). This is a genuine asymmetry/oversight in the parameter-validation table, not a hypothetical.

### Impact Explanation
* For `ENERGY_FEE`: while a `TriggerSmartContract` sender can specify `feeLimit`, `VMActuator` derives the runnable energy budget from `feeLimit / getEnergyFee()` **at execution time**, using whatever `ENERGY_FEE` is current at block-application time, not the value the sender observed when signing. Because there is no cap on how large `ENERGY_FEE` can be set to, a governance change occurring between signing and inclusion can arbitrarily shrink the effective energy budget for in-flight transactions, or — if the value is extreme — interact with the `sunPerEnergy` multiplication and per-unit accounting to push the actually-billed `energyFee` toward the sender's full remaining balance under edge conditions in `payEnergyBill`.
* For `EXCHANGE_CREATE_FEE`: this is a flat fee taken directly from the caller's balance when an `ExchangeCreateContract` executes, with no per-transaction cap analogous to `feeLimit`. Since `ProposalUtil` performs zero bounds checking on this value, a proposal that raises `EXCHANGE_CREATE_FEE` to an extreme value takes effect for any pending/mempool `ExchangeCreateContract` transaction signed before the change, causing the sender to be charged far more than anticipated (up to draining their available balance, subject only to the `BalanceInsufficientException` failure path rather than a bounded, predictable fee).

Both cases match the report's underlying concern: a governance/administrative fee-setter without a maximum cap can retroactively "attack" already-signed, unprivileged transactions during the window between broadcast and execution.

### Likelihood Explanation
Likelihood is limited by the fact that these values only change via the standard committee-proposal maintenance-cycle mechanism (not a single instantaneous unprivileged call), so the "mempool race" window is a full maintenance cycle rather than a single block — this is a coarser race window than the original TellerV2 scenario. It requires an approved proposal to occur while unprivileged transactions are in flight, which is a normal but infrequent governance event, not attacker-triggered on demand.

### Recommendation
Add explicit, sane upper-bound validation for `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` in `ProposalUtil.validator()`, consistent with the `[0, LONG_VALUE]` (or a tighter, protocol-appropriate) bound already applied to every other fee-type `ProposalType`, so that a single proposal cannot set these parameters to an unbounded value that can arbitrarily affect the cost of already-broadcast, unprivileged transactions.

### Proof of Concept
1. A committee member submits and enough witnesses approve a proposal setting `code = ENERGY_FEE` (or `EXCHANGE_CREATE_FEE`) to an extremely large `value` (e.g. `Long.MAX_VALUE`).
2. `ProposalUtil.validator` reaches the `case ENERGY_FEE: case EXCHANGE_CREATE_FEE: break;` branch with no check, so the proposal passes validation. [1](#0-0) 
3. At the next maintenance cycle, `ProposalService.process` unconditionally saves the new value via `saveMarketSellFee`-style setters (`saveEnergyFee`/`saveExchangeCreateFee`), with no re-validation. [2](#0-1) 
4. Any `TriggerSmartContract`/`CreateSmartContract` transaction (for `ENERGY_FEE`) or `ExchangeCreateContract` transaction (for `EXCHANGE_CREATE_FEE`) that was already signed and broadcast by an ordinary user prior to the proposal taking effect is then executed under the new, unbounded fee value in `ReceiptCapsule.payEnergyBill` (for energy) or the exchange-creation actuator (for the flat create fee), resulting in a fee far larger than the user expected when they signed the transaction. [3](#0-2)
