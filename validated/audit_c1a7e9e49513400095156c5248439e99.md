### Title
Self-inflated AMM reserve ratio lets a signed account underpay `pallet-asset-conversion-tx-payment` transaction fees at will - (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

### Summary
The Salty report's core broken invariant is: an AMM's instantaneous reserve ratio is trusted as a price oracle for a critical economic decision (collateral valuation), even though any unprivileged actor can move that ratio with a single swap, and the deviation is not bounded by any TWAP/oracle check. The local analog is `pallet-asset-conversion`'s Uniswap-V2-style pool [1](#0-0)  being used as the price source for `SwapAssetAdapter::withdraw_fee`, which decides — from the pool's live reserves — exactly how much of a non-native asset a signed account must pay to cover a transaction fee, and then immediately executes the swap for that exact quoted amount [2](#0-1) .

### Finding Description
`quote_price_tokens_for_exact_tokens` derives its answer purely from `Self::get_reserves(asset1, asset2)`, i.e. the raw token balances currently held by the pool account, with no oracle, no TWAP, and no bound on how much the ratio has moved since the pool's creation [3](#0-2) . Any signed account can create a pool (paying only `PoolSetupFee`) and swap in it without any privileged origin [4](#0-3) .

`SwapAssetAdapter::withdraw_fee`, used by `ChargeAssetTxPayment` when a transaction opts to pay fees in a non-native asset, calls this same live-reserve quote function to compute `asset_fee` — the amount of `asset_id` the signer must give up for the native-denominated `fee` — and then swaps exactly that amount through the pool in the very same call [5](#0-4) .

Because the reserve ratio is a spot price with no manipulation resistance, a signer can, across ordered extrinsics in the same block (same account, sequential nonces, fully under their own control — no relayer, validator, or third party required):
1. Submit a large swap that skews the pool so that `asset_id` becomes artificially "expensive" relative to the native asset (shrinking `asset_id`'s reserve relative to native).
2. Submit any number of further extrinsics whose `ChargeAssetTxPayment` extension is configured to pay fees in that same `asset_id`. Because the pool is skewed, `quote_price_tokens_for_exact_tokens` will return an artificially small `asset_fee` for the same native-denominated `fee`, so each of these extrinsics pays far less real value than the fee schedule intends.
3. Submit a final swap to undo the skew, recovering nearly all of the value spent in step 1 minus only the constant-product LP fee (`pool_fee_for`, e.g. 0.3%) on the round trip.

This is the direct analog of the Salty report's mechanism: the manipulator "loses" money on the skewing trade in isolation, but the loss is small and recoverable because it is reversed within the same window, while the gain (here: systematically underpriced tx fees across many extrinsics) scales with how many fee-paying extrinsics are squeezed into the manipulated window. The existing guard `quote_price_tokens_for_exact_tokens`'s `reducible_balance(Preserve, Polite)` check only prevents *pool starvation*, not *ratio manipulation* — it does nothing to stop the ratio itself from being pushed to any value up to the withdrawable limit [6](#0-5) .

### Impact Explanation
Transaction fees paid via `pallet-asset-conversion-tx-payment` are meant to reflect the real economic cost of block weight/length so that block production is correctly priced and spam-resistant. A signer who can cheaply and repeatably manipulate the fee-asset's pool ratio can pay a fraction of the intended fee for a burst of extrinsics, i.e. "public underpriced work that degrades block production," one of the explicitly in-scope impacts. This does not require a malicious validator/collator/relayer/prover, a leaked key, or any privileged origin — only ordinary signed transactions and a thinly-liquiditized pool for the chosen fee asset, matching the report's escalation path (attacker profit scales with pool thinness and volume of fee-paying calls squeezed into the manipulated window, cost is bounded by the round-trip LP fee).

### Likelihood Explanation
Requires: (a) a runtime that includes `pallet-asset-conversion-tx-payment`'s `SwapAssetAdapter`/`OnChargeAssetTransaction` configured over `pallet-asset-conversion` pools, and (b) at least one asset-fee-eligible pool with limited liquidity relative to the fees the attacker wants to discount. Both are ordinary, permissionless runtime configurations already exercised in this repo's test suite (`setup_lp`, `transaction_payment_in_asset_possible`, etc.) [7](#0-6) . As in the original report, the severity/likelihood scales with "external requirements" — the cost of moving the pool must be smaller than the aggregate fee savings, so this is a Medium-class, arbitrage-competition-dependent issue rather than a guaranteed drain, consistent with how the analogous Salty finding was judged.

### Recommendation
Do not use the raw instantaneous pool reserves as the price source for a security/economic-critical computation such as fee conversion. Use a manipulation-resistant price (e.g., a time-weighted average price over multiple blocks, or a price bounded by a maximum per-block deviation) before calling `get_amount_in`/`get_amount_out` inside `quote_price_tokens_for_exact_tokens`/`quote_price_exact_tokens_for_tokens`, or cap how much a single quote is allowed to deviate from a recent moving-average reserve ratio, mirroring the report's own recommendation to value AMM positions "as if the ratio was at the correct ratio" rather than trusting the current spot ratio.

### Proof of Concept
1. Attacker deploys or uses an existing thin `AssetX`/`Native` pool via `AssetConversion::create_pool` + `add_liquidity` (both permissionless, signed-origin calls) [4](#0-3) .
2. In block N, nonce 0: attacker swaps a large amount of `Native` into the pool for `AssetX`, sharply reducing `AssetX`'s reserve relative to `Native` (standard `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens`, no special privilege needed).
3. Nonces 1..k: attacker submits k signed extrinsics whose `ChargeAssetTxPayment` extension pays fees in `AssetX`. Each call's `withdraw_fee` re-quotes `quote_price_tokens_for_exact_tokens(AssetX, Native, fee, true)` against the now-skewed reserves [8](#0-7) , returning an artificially low `asset_fee`.
4. Nonce k+1: attacker swaps back `AssetX` for `Native` to restore the ratio, recovering the bulk of the step-2 outlay minus the round-trip LP fee.
5. Net effect: k extrinsics were charged fees far below their intended native-denominated cost, while the attacker's total capital cost is bounded by ~2×`LPFee`×(swap size), demonstrable directly against the existing test harness's `setup_lp`/`quote_price_tokens_for_exact_tokens` calls used in `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/tests.rs`.

	fn withdraw_fee(
		who: &T::AccountId,
		_call: &T::RuntimeCall,
		_dispatch_info: &DispatchInfoOf<<T>::RuntimeCall>,
		asset_id: Self::AssetId,
		fee: Self::Balance,
		_tip: Self::Balance,
	) -> Result<Self::LiquidityInfo, TransactionValidityError> {
		if asset_id == A::get() {
			// The `asset_id` is the target asset, we do not need to swap.
			let fee_credit = F::withdraw(
				asset_id.clone(),
				who,
				fee,
				Precision::Exact,
				Preservation::Preserve,
				Fortitude::Polite,
			)
			.map_err(|_| InvalidTransaction::Payment)?;

			return Ok((fee_credit, fee));
		}

		// Quote the amount of the `asset_id` needed to pay the fee in the asset `A`.
		let asset_fee =
			S::quote_price_tokens_for_exact_tokens(asset_id.clone(), A::get(), fee, true)
				.filter(|asset_fee| !asset_fee.is_zero())
				.ok_or(InvalidTransaction::Payment)?;

		// Withdraw the `asset_id` credit for the swap.
		let asset_fee_credit = F::withdraw(
			asset_id.clone(),
			who,
			asset_fee,
			Precision::Exact,
			Preservation::Preserve,
			Fortitude::Polite,
		)
		.map_err(|_| InvalidTransaction::Payment)?;

		let (fee_credit, change) = match S::swap_tokens_for_exact_tokens(
			vec![asset_id, A::get()],
			asset_fee_credit,
			fee,
		) {
			Ok((fee_credit, change)) => (fee_credit, change),
			Err((credit_in, _)) => {
				defensive!("Fee swap should pass for the quoted amount");
				let _ = F::resolve(who, credit_in).defensive_proof("Should resolve the credit");
				return Err(InvalidTransaction::Payment.into());
			},
		};

		// Since the exact price for `fee` has been quoted, the change should be zero.
		ensure!(change.peek().is_zero(), InvalidTransaction::Payment);

		Ok((fee_credit, asset_fee))
	}

				T::Assets::touch(asset1.clone(), &pool_account, creator)?
			};

				T::Assets::touch(asset2.clone(), &pool_account, creator)?
			};

			let lp_token = NextPoolAssetId::<T>::get()
				.or(T::PoolAssetId::initial_value())

		pub fn quote_price_tokens_for_exact_tokens(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount: T::Balance,
			include_fee: bool,
		) -> Option<T::Balance> {
			// Swaps reject zero amounts, match that behavior.
			if amount.is_zero() {
				return None;
			}
			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2).ok()?;

			let (balance1, balance2) = Self::get_reserves(asset1.clone(), asset2.clone()).ok()?;

			if balance1.is_zero() {
				return None;
			}

			// Swap withdrawals from pools use `keep_alive=true` (Preserve). Use the same
			// preservation level to determine the actual withdrawable amount.
			let max_output =
				T::Assets::reducible_balance(asset2.clone(), &pool_account, Preserve, Polite);
			if amount > max_output {
				return None;
			}

			if include_fee {
				let fee = Self::pool_fee_for(&asset1, &asset2).ok()?;
				Self::get_amount_in(fee, &amount, &balance1, &balance2).ok()
			} else {
				Self::quote(&amount, &balance2, &balance1).ok()
			}
		}

				42,   // owner

				min_balance

			// mint into the caller account

				NativeOrWithId::Native,
				fee_in_native,
				true,

			let fee_in_asset = input_quote.unwrap();
