Based on my investigation, I found a legitimate analog in the StackerDB write path that matches the bug class of the OATHAuth advisory (rate limiting enforced on one path but not the other, allowing bypass via a different route).

### Title
StackerDB `write_freq` rate limit is never enforced on the `POST /v2/stackerdb/.../chunks` write path - (File: stackslib/src/net/stackerdb/db.rs)

### Summary
`StackerDBConfig::write_freq` is meant to throttle how often a given slot may be rewritten, but the only code that actually consults `write_freq` is the *pull/sync scheduler* in `stackslib/src/net/stackerdb/sync.rs`, which uses it merely to decide whether to bother *downloading* a chunk from a peer. The function that actually commits a write to a slot, `StackerDBTx::try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs`, never checks `write_freq` or the slot's `write_time` at all.

### Finding Description
`try_replace_chunk` performs: chunk-size check, signer/signature check, staleness check (`slot_version <= slot_validation.version`), and `max_writes` check, then calls `insert_chunk`. [1](#0-0) 
None of these checks reference `write_freq` or `SlotValidation.write_time`, even though `write_time` is tracked and stored on every insert. [2](#0-1) [3](#0-2) 

This function is invoked directly by the unauthenticated public HTTP endpoint `RPCPostStackerDBChunkRequestHandler::try_handle_request` in `stackslib/src/net/api/poststackerdbchunk.rs`, which calls `tx.try_replace_chunk(...)` with no additional throttling. [4](#0-3) 

The only place `write_freq` is honored is `StackerDBSync::make_chunk_request_schedule`, which skips scheduling a *download* of a chunk if it was written too recently — this only limits pull-based propagation, not direct writes. [5](#0-4) 

There is even a dedicated error variant, `net_error::TooFrequentSlotWrites`, defined for this purpose in `stackslib/src/net/mod.rs`, but it is never constructed/returned anywhere in the codebase (confirmed by a global grep — only its 3 definition/Display-impl occurrences exist, no call sites that raise it in db.rs or elsewhere). [6](#0-5) 

Equality/invariant broken: the intended invariant is "a slot write is only accepted if `now - last_write_time >= write_freq`" for *every* write path, but this equality is checked on the read/sync scheduling path only, not on the authoritative write path (`try_replace_chunk`). A remote, unprivileged client possessing a valid slot signer key (any StackerDB participant, e.g. a signer or miner) can bypass the intended write-frequency throttle entirely simply by using the direct `POST /v2/stackerdb/:address/:contract/chunks` RPC instead of relying on P2P gossip/sync, exactly analogous to OATHAuth's per-site (vs. cluster-wide) rate limit being bypassable by hitting a different site/path.

### Impact Explanation
This does not authorize an unauthorized write (the caller must already hold a valid signer key for the slot — signature and `max_writes` checks are still enforced), so it is not a full auth-bypass. However, it defeats an intended anti-spam/DoS control: `write_freq` exists specifically to bound how fast a legitimate slot owner (or someone possessing that key) can churn the StackerDB, controlling propagation/storage load across the network. Since a signed chunk with an unenforced write_freq is stored and then relayed via `node.set_relay_message(StacksMessageType::StackerDBPushChunk(...))`, a signer can flood their own slot at unlimited frequency, which becomes network-wide propagation load on every replica. [7](#0-6) 
This is a bounded-compute/DoS-style impact rather than critical unauthorized state corruption, since only holders of legitimate slot-signing keys (signers/miners) can exploit it — not a fully unauthenticated attacker.

### Likelihood Explanation
High likelihood of being reachable: any of the fixed set of registered StackerDB signers (e.g. a Nakamoto signer or miner participating in a `.signers-*`/`.miners` StackerDB) can trivially invoke this HTTP endpoint directly instead of going through the gossip/sync path, with no additional privilege needed beyond the key they are already provisioned with.

### Recommendation
Enforce `write_freq` inside `StackerDBTx::try_replace_chunk` (or immediately before calling it in the RPC handler) by loading `SlotValidation.write_time` and rejecting the write with `net_error::TooFrequentSlotWrites` if `now < write_time + config.write_freq`, mirroring the same check already implemented in `StackerDBSync::make_chunk_request_schedule`. Add a corresponding `StackerDBErrorCodes` entry (e.g. `TooFrequentWrites`) so `poststackerdbchunk.rs` returns a well-formed rejection ack instead of silently accepting.

### Proof of Concept
1. Configure a StackerDB contract with `write-freq > 0` (e.g. 300 seconds) and a signer key `sk` owning slot 0.
2. Sign and `POST` a `StackerDBChunkData` to `/v2/stackerdb/<addr>/<contract>/chunks` with `slot_version = 1`; observe `accepted: true`.
3. Immediately sign and `POST` another chunk with `slot_version = 2` (still within the `write_freq` window). Per `try_replace_chunk`'s logic, this passes size/signature/staleness/max_writes checks and is accepted — `write_freq` is never consulted, so unlimited rapid rewrites succeed contrary to the DB's configured throttle.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
