### Title
Multisig weight double-counting via ECDSA signature malleability in `ValidateMultiSign` precompile - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` TVM precompile (address `0x64` gated by `validateMultiSignAddr`, exposed to any contract call as `validatemultisign(address,uint256,bytes32,bytes[])`) is meant to let a smart contract check whether a set of ECDSA signatures reach a permission's weight threshold. Its "already-used" dedup check keys off the full raw signature bytes concatenated with the recovered address, rather than the recovered address alone. Because ECDSA signatures are malleable (flipping `s -> n - s` and `v` yields a second valid signature for the same message and key without knowing the private key), an attacker can submit the same signer's approval twice — once in original form and once in its malleated form — and have both counted toward `totalWeight`.

The loop only `continue`s (skips adding weight) when the *exact byte-for-byte* `sign` (address + raw signature bytes) was already seen. If the recovered address was already seen but the raw signature bytes differ, the code does **not** skip — it falls through, looks up the weight again with `TransactionCapsule.getWeight`, and adds it to `totalWeight` a second time.

This design is the exact analog of the certificate-controller bug in the report: instead of tracking a canonical identifier of "who approved" (the recovered address, or a canonicalized signature), the code tracks the *raw signature bytes*. Because ECDSA allows a second, syntactically distinct `(r, n-s, flipped-v)` signature that recovers to the identical address (`recoverAddrBySign` in the same file, lines 371-388, calls `signature.validateComponents()` which does not enforce low-S canonicalization — see `ECDSASignature.validateComponents` in crypto/src/main/java/org/tron/common/crypto/ECKey.java:923-941, which has no low-S check, only bounds checks), an attacker can trivially derive a second valid signature from any signature they observe (e.g. one legitimately collected signature from a co-signer, or their own signature) and submit both in the `bytes[]` array to `validatemultisign`. [2](#0-1) [3](#0-2) 

The existing unit test `testDifferentCase` in `ValidateMultiSignContractTest` even demonstrates the intended "signed twice" rejection using an *identical* duplicated signature (`signs.add(Hex.toHexString(key1.sign(toSign).toByteArray())); signs.add(Hex.toHexString(key1.sign(toSign).toByteArray()));`), but ECDSA signing with a random `k` per call already produces different `(r,s)` for repeated signs in most implementations, and a deliberately-constructed malleated signature (same `r`, flipped `s`/`v`) is the deterministic way to guarantee a byte-distinct duplicate that still passes `matrixContains` as "new." [4](#0-3) 

### Impact Explanation
Any smart contract can call `validatemultisign` to gate privileged actions (fund release, contract admin operations, etc.) based on multisig threshold approval. Because a single signer's weight can be counted twice (or, with more colluding/observed signatures, an attacker can inflate `totalWeight` using fewer distinct real approvers than the permission's `threshold` requires), an attacker who controls or has observed only a subset of the required signers' signatures can satisfy the weight threshold and unlock actions that should require full quorum. This is a broken-access-control / unauthorized-account-operation bug reachable from ordinary contract calls, which can lead to unauthorized fund transfers or account operations gated by on-chain multisig logic built on top of `ValidateMultiSign`.

### Likelihood Explanation
The attack requires no special privileges — any address can deploy or call a contract that invokes the `validatemultisign` precompile with a crafted `bytes[]` signature array. Deriving the ECDSA malleable counterpart of a known signature (`s' = n - s`, flip `v`) is a well-known, deterministic, zero-cost operation requiring only the signature itself, not the private key. The precompile is reachable via ordinary TVM `CALL`/`STATICCALL` from any contract, gated only by `VMConfig.allowTvmSolidity059()` being enabled (a mainnet-active feature).

### Recommendation
Change the dedup key in `ValidateMultiSign.execute` from the concatenation of `recoveredAddr + rawSignatureBytes` to the recovered address alone (which is already what `matrixContains(executedSignList, recoveredAddr)` checks for presence). Once an address has been counted once, any further signature recovering to that same address — malleated or not — must be skipped (`continue`), never counted again. Additionally, enforce canonical (low-S) signature form in `recoverAddrBySign`/`ECDSASignature.validateComponents` for this codepath, rejecting non-canonical signatures outright, consistent with the general SWC-117 remediation of not trusting raw signature-byte equality for uniqueness.

### Proof of Concept
1. Set up an account with `Active` permission: threshold = 2, two keys `key1` (weight 1) and `key2` (weight 1) — same setup as `ValidateMultiSignContractTest.testDifferentCase`.
2. Obtain a single valid signature `sig1 = key1.sign(hash)` from `key1` only (attacker does not control `key2`).
3. Compute the malleated counterpart `sig1' = (r, n-s, flip(v))` from `sig1` — no private key needed.
4. Call `validatemultisign(address, permissionId, hash, [sig1, sig1'])`.
5. In `ValidateMultiSign.execute`, iteration 1 processes `sig1`, recovers `key1`'s address, adds weight 1 (`totalWeight=1`). Iteration 2 processes `sig1'`; `recoverAddrBySign` again yields `key1`'s address; `matrixContains(executedSignList, recoveredAddr)` is true, but `matrixContains(executedSignList, merge(recoveredAddr, sig1'))` is false (different raw bytes) — so the loop does **not** `continue`; it adds weight 1 again (`totalWeight=2`).
6. `totalWeight (2) >= threshold (2)` → the precompile returns `DATA_ONE` (success), even though only one real signer (`key1`) actually participated, bypassing the 2-of-2 multisig requirement.

      logger.info("ECRecover error", any.getMessage());

    return out;
  }
