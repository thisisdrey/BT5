## Analysis

The Trader Joe bug's core invariant break is: **a permissionless "register-by-identifier" entrypoint lets an attacker claim a unique key (keyed off an external asset the attacker does not control) for negligible, refundable cost, permanently denying the rightful owner the ability to register that same key**, because the pallet enforces "id must not already be in use" with no origin check tying the id to its legitimate owner.

The direct local analog is `pallet_assets::Pallet::create` in `substrate/frame/assets/src/lib.rs`.

### Title
Permissionless, attacker-chosen `AssetId` squatting via `pallet_assets::create` permanently blocks the legitimate issuer - (File: `substrate/frame/assets/src/lib.rs`)

### Summary
`pallet-assets` exposes a permissionless `create` extrinsic that lets any signed account choose an arbitrary, currently-unused `AssetId` and register it against a nominal, fully-refundable deposit [1](#0-0) . When a runtime's `Config::AssetIdAllocator` is set to `()` (the pallet's own documented default), `create` accepts *any* unused id, not one dictated by an allocation policy [2](#0-1) . This is structurally the same primitive as `createRJLaunchEvent()`: a public function that claims a scarce identifier tied to someone else's asset/token, with the only "cost" being a deposit the attacker later reclaims.

### Finding Description
`create` is gated only by `T::CreateOrigin` (typically `AsEnsureOriginWithArg<EnsureSigned<AccountId>>`, i.e. any signed account) and checks solely that `id` is not currently in `Asset::<T,I>`: [3](#0-2) . There is no check that the caller is the legitimate/expected issuer for that particular `id`. Once inserted, `Error::<T,I>::InUse` unconditionally rejects any later `create` for the same `id` by anyone else [4](#0-3) [5](#0-4) .

This is the pallet's documented, intended "permissionless" mode: *"Issue new assets in a permissionless or permissioned way, if permissionless, then with a deposit required."* [6](#0-5)  The mitigation the pallet ships for id-squatting is opt-in: `Config::AssetIdAllocator`, with `AutoIncAssetId` forcing sequential, caller-uncontrolled ids [7](#0-6) . Several production-adjacent configs in this repo still leave `AssetIdAllocator = ()` while using an open `EnsureSigned` `CreateOrigin`, e.g. the Substrate node-template runtime's `pallet_assets::Config<Instance1>` [8](#0-7) , and `pallet-assets`' own `TestDefaultConfig`/generic default which any downstream chain can inherit unmodified [9](#0-8) . Asset Hub only closed this specific gap for its `TrustBackedAssetsInstance` by switching to `AutoIncAssetId` [10](#0-9) , confirming the underlying pattern was recognized as a real griefing vector worth fixing — but the fix is per-instance and per-runtime, not enforced by the pallet itself.

The attacker's cost is `T::AssetDeposit`, which is fully returned via `start_destroy`/`finish_destroy`, so the attack is essentially free and repeatable [11](#0-10) ; the analog of "1 Wei" in the report is "a temporarily-reserved, fully-refundable deposit."

### Impact Explanation
Any runtime that instantiates `pallet-assets` with an unconstrained `AssetIdAllocator` and an open `CreateOrigin` (a configuration the pallet itself defaults to and still ships in this repo, e.g. `substrate/bin/node/runtime`) allows an unprivileged attacker to permanently squat a specific `AssetId` intended for a legitimate project/token before that project can register it, blocking their asset launch indefinitely (`Error::InUse`) unless the squatter voluntarily destroys the asset. This is exactly the impact class flagged in the seed report: public underpriced work / unauthorized state-claiming that denies the rightful party normal on-chain functionality.

### Likelihood Explanation
Likelihood is high wherever `AssetIdAllocator = ()` is paired with an open `EnsureSigned`-style `CreateOrigin` — this is the pallet's documented default behavior, requires no special access, no governance action, and no malicious peer/validator/relayer (all of which are out of scope). The attacker only needs a signed account and the deposit amount, which is refunded.

### Recommendation
- Make `AssetIdAllocator` non-optional (or default to an allocator that prevents arbitrary id choice) whenever `CreateOrigin` permits open/self-selecting signed origins, so `create` cannot accept attacker-chosen ids for permissionless asset classes.
- For runtimes that must support caller-chosen ids (e.g. `Location`-derived foreign asset ids), restrict `CreateOrigin` to a provably-bound origin (as already done for `ForeignAssetsInstance`'s `ForeignCreators`) rather than `EnsureSigned`.
- Audit all in-repo `pallet_assets::Config` instances (and downstream template runtimes) for the `AssetIdAllocator = () + EnsureSigned CreateOrigin` combination and migrate them to `AutoIncAssetId` or an equivalent binding allocator, mirroring the fix already applied to Asset Hub's trust-backed assets.

### Proof of Concept
1. Deploy/observe a runtime with `pallet_assets::Config` where `CreateOrigin = AsEnsureOriginWithArg<EnsureSigned<AccountId>>` and `AssetIdAllocator = ()` (e.g. `substrate/bin/node/runtime/src/lib.rs`, `Instance1`).
2. Attacker account `A` (unprivileged, unrelated to the token) observes that project `P` intends to launch asset id `X` (e.g. announced publicly, or a well-known convention id).
3. `A` calls `Assets::create(origin=A, id=X, admin=A, min_balance=1)`. This succeeds: `Asset::<T,I>::contains_key(X)` is `false`, `AssetIdAllocator::next()` returns `None` so no id constraint is enforced [12](#0-11) , and only `AssetDeposit` is reserved from `A`.
4. Project `P` later calls `Assets::create(origin=P, id=X, ...)` and receives `Error::<T,I>::InUse` [4](#0-3) , permanently unable to use id `X`.
5. `A` may optionally call `start_destroy`/`finish_destroy` on `X` to reclaim the full deposit and repeat the griefing against another target id [11](#0-10) .

/// Allocates asset ids by auto-incrementing the [`NextAssetId`].
///
/// This has no effect while the [`NextAssetId`] value is not present.
pub struct AutoIncAssetId<T, I = ()>(PhantomData<(T, I)>);
impl<T: Config<I>, I: 'static> AssetIdAllocator<T::AssetId> for AutoIncAssetId<T, I>
where
	T::AssetId: Incrementable + PartialOrd,
{
	fn next() -> Option<T::AssetId> {
		NextAssetId::<T, I>::get()
	}

	fn advance() -> Result<(), ()> {
		let Some(next_id) = NextAssetId::<T, I>::get() else {
			// Auto increment for the asset id is not active.
			return Ok(());
		};
		let next_id = next_id.increment().ok_or(())?;
		NextAssetId::<T, I>::put(next_id);
		Ok(())
	}

	fn advance_from(id: &T::AssetId) -> Result<(), ()> {
		let Some(next_id) = NextAssetId::<T, I>::get() else {
			// Auto increment for the asset id is not active.
			return Ok(());
		};
		// Only advance when the forced id is at or beyond the sequence; ids below `next_id` belong
		// to a range that can be reserved for deliberate, forced assignment.
		if *id >= next_id {
			let next_id = id.increment().ok_or(())?;
			NextAssetId::<T, I>::put(next_id);
		}
		Ok(())
	}
}
