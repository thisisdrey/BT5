## Title
Deleting and re-adding an access key within the same chunk can roll back its nonce floor below an already-used nonce, enabling replay of a stale transaction - ([File: runtime/runtime/src/access_keys.rs])

## Summary
`initial_nonce_value`/`add_regular_key` unconditionally reseeds a re-created key's nonce to `(block_height-1)*ACCESS_KEY_NONCE_RANGE_MULTIPLIER` with no regard for the highest nonce that public key has already consumed. Because a transaction's nonce only needs to satisfy `tx_nonce < block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` (not a lower bound tied to the *current* block height, and `NonceMode::Monotonic` allows any jump above the stored value), an attacker can choose a nonce close to the current upper bound, then delete and re-add the same public key **within the same chunk**, dropping the on-chain nonce back below that already-consumed value. A previously signed but superseded transaction with a nonce in that reopened window can later be resubmitted and accepted.

## Finding Description
`initial_nonce_value` (`runtime/runtime/src/access_keys.rs:46`) computes the seed purely from `block_height`, and `add_regular_key` (`:230`-`:241`) writes it unconditionally, overwriting whatever nonce state existed for that key before deletion: [1](#0-0) [2](#0-1) 

`verify_nonce` (`runtime/runtime/src/verifier.rs:211`-`237`) only enforces `tx_nonce > current_nonce` (Monotonic) and `tx_nonce < block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`; there is no lower bound relating `tx_nonce` to `block_height`: [3](#0-2) 

Within one `Runtime::apply` call, `apply_state.block_height` is a single fixed value shared by both transaction verification (step 2) and local-receipt execution (step 3), per the documented apply pipeline: [4](#0-3) 

Exploit flow (attacker's own account, two of their own FullAccess keys K1, K2):
1. Attacker submits `TxA`, signed by K1, with `nonce = H*1_000_000 - k` for small `k` (legal because `NonceMode::Monotonic` permits any nonce increase, not just +1), where `H` is the chunk's block height. `TxA` succeeds; K1's stored nonce becomes `N = H*1_000_000 - k`.
2. In the *same chunk*, attacker submits `TxB`, signed by K2, with actions `[DeleteKey(K1), AddKey(K1, FullAccess)]`, `receiver_id == signer_id` (a local receipt executed in step 3 of the *same* `apply` call, same `H`).
3. `action_add_key` re-seeds K1's nonce to `(H-1)*1_000_000`, which is `k` less than `N`.
4. In any later chunk, attacker (re-)submits a stale, previously-signed transaction using K1 with a nonce in `((H-1)*1_000_000, N]` — including possibly `TxA` itself, or another transaction they held back. `verify_nonce` now sees `current_nonce = (H-1)*1_000_000 < tx_nonce`, so it passes, and the upper-bound check trivially passes since the later chunk's height is far larger.

This defeats the "transaction executes at most once" guarantee that the `(block_height-1)*ACCESS_KEY_NONCE_RANGE_MULTIPLIER` seeding was explicitly designed to preserve across key re-creation (see the referenced issue in the code comment), because the mitigation only accounts for `block_height` growth, not for the fact that a delete+re-add local receipt can land at the *identical* `block_height` as the transaction that advanced the nonce.

## Impact Explanation
This breaks nonce monotonicity / replay-prevention, the exact invariant called out in the question. Any action the attacker signed once (e.g. a `FunctionCall` withdrawing/claiming from an external contract that trusts NEAR's single-execution guarantee, or a `Transfer` used as a one-time payment authorization handed to a counterparty) can be made valid again after the key delete/recreate trick, allowing it to be executed a second time. This matches the "double-spend/replay of a stale transaction" bounty category.

## Likelihood Explanation
- Fully reachable by an unprivileged account: only requires the attacker's own two FullAccess keys and the ability to choose an arbitrary (non-sequential) nonce, which `NonceMode::Monotonic` (the default for V0/legacy transactions) explicitly allows.
- Requires `TxA` and `TxB` (DeleteKey+AddKey, with `receiver_id == signer_id` so it's a local receipt) to land in the same chunk — fully controllable by submitting both together and retrying if a chunk boundary splits them; no validator or network privilege needed.
- Repeatable at will since the attacker fully controls key creation/deletion and nonce choice on their own account.

## Recommendation
Do not reseed a re-created regular/gas key's nonce purely from `block_height`. Preserve or take the maximum of the previous nonce (or a per-account/per-pubkey historical high-water mark) and the block-height-derived seed in `add_regular_key`/`add_gas_key`, e.g. `access_key.nonce = max(initial_nonce_value(block_height), previous_nonce_if_any)`, or persist a per-(account, public key) monotonic nonce floor that survives `DeleteKey` and is consulted by `add_regular_key`.

## Proof of Concept
Integration/unit test in `runtime/runtime/src/tests/apply.rs` style, using `Runtime::apply` directly (mirrors `runtime_group_tools`):
1. Create account with two FullAccess keys, K1 and K2.
2. Build a chunk at height `H` containing:
   - `TxA`: signed by K1, `nonce = H*1_000_000 - 5`, e.g. a `Transfer` action to a third account, asserted to succeed.
   - `TxB`: signed by K2, `receiver_id == signer_id`, actions `[DeleteKey(K1), AddKey(K1, FullAccess)]`.
   - Apply this chunk; assert both `TxA`'s and `TxB`'s local receipts execute in the same `apply` call (same `block_height`), and that K1's stored nonce afterward equals `(H-1)*1_000_000`.
3. Apply a subsequent chunk at height `H+1` (or later) containing `TxA2`: identical signed bytes/content to `TxA` (same nonce `H*1_000_000 - 5`, same signature) re-submitted.
4. Assert `TxA2` is **accepted and re-executed** (e.g., the `Transfer` fires a second time, doubling the recipient's balance increase) rather than being rejected with `InvalidNonce`, demonstrating the replay.

```rust
/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}
```

```markdown
### Ordered phases of `apply`

`Runtime::apply` (`runtime/runtime/src/lib.rs:1717`) runs conceptually as: (1) validator accounts, (2) transactions, (3) receipts, (4) finalize. Concretely, in order:

1. **Prefetch** transaction data (best-effort) (`runtime/runtime/src/lib.rs:1746`).
2. **Update validator accounts** if a `ValidatorAccountsUpdate` is supplied (`runtime/runtime/src/lib.rs:1752` → `update_validator_accounts` `:1599`). This happens first so reward/stake changes land before any tx/receipt reads balances, and it commits with `StateChangeCause::ValidatorAccountsUpdate` (`runtime/runtime/src/lib.rs:1692`).
3. **Load the delayed receipt queue** (`runtime/runtime/src/lib.rs:1759`).
4. **Run the bandwidth scheduler** — for every chunk including missing ones (`runtime/runtime/src/lib.rs:1767` — `run_bandwidth_scheduler`).
5. **Missing-chunk short-circuit**: if `!apply_state.is_new_chunk`, finalize immediately and return without processing any receipts (`runtime/runtime/src/lib.rs:1775` → `missing_chunk_apply_result` `:2937`), carrying congestion info and bandwidth requests forward unchanged.
6. **Build the `ReceiptSink`** from own congestion info + scheduler output, then **forward buffered receipts** from prior chunks first (`runtime/runtime/src/lib.rs:1787`, `:1795`). See [cross-shard congestion](cross-shard-congestion.md).
7. **Process transactions** → local receipts / forwarded receipts (`runtime/runtime/src/lib.rs:1798` — `process_transactions`).
8. **Process receipts** in the order local → delayed → incoming, then resolve promise-yield timeouts (`runtime/runtime/src/lib.rs:1801` — `process_receipts` `:2658`).
9. **Finalize**: `validate_apply_state_update` (`runtime/runtime/src/lib.rs:1813` / `:2723`) — persist promise-yield indices, finalize congestion (choose allowed shard), generate bandwidth requests, apply the sandbox state patch, run `state_update.finalize()`, dedup validator proposals (keeping the last per account, reversed) (`runtime/runtime/src/lib.rs:2816`), and assemble `ApplyResult`.

The local → delayed → incoming order matters: local receipts (from this chunk's transactions) and the delayed backlog are drained before new incoming cross-shard receipts, so backlog is preferred over new work and gas-limit exhaustion pushes the newest work to the delayed queue (`runtime/runtime/src/lib.rs:2670`-`2692`).
```
