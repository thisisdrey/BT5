### Title
Uncontrolled memory allocation from unvalidated length fields in TVM precompiled-contract ABI decoding helpers - (`File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.java` contains helper routines (`extractBytesArray`, `extractBytes32Array`, `extractSigArray`) that read an attacker-controlled length word directly from the raw call-data words array and immediately use it to size a Java object array (`new byte[len][]`), with no upper bound check on `len` before the allocation is performed. [1](#0-0) 

This is the same bug class as CVE-2018-5783: a size value taken from untrusted, attacker-supplied input (there, a PDF object count; here, a `DataWord` decoded from contract call-data) is passed straight into an allocation routine (`PdfVecObjects::Reserve` there, a `new T[len]` here) without bounding it against a sane maximum or the actual remaining input size.

### Finding Description
`extractBytes32Array` and `extractBytesArray` take the `len` value directly from `words[offset].intValueSafe()` — a `DataWord` decoded from the raw smart-contract call-data supplied by the caller of the precompiled contract — and use it unchecked to allocate a two-dimensional byte array: [2](#0-1) 

`intValueSafe()` clamps a `DataWord`'s `BigInteger` value into the `int` range, meaning an attacker can set the length word to values up to `Integer.MAX_VALUE` (2^31-1) while only supplying a small amount of actual call-data. There is no check that `len` is consistent with `data.length` or with the number of remaining `words`, unlike, for example, the sapling-proof precompile in the same file which explicitly bounds `spendCount`/`receiveCount` to `[1,2]` before allocating arrays: [3](#0-2) 

By contrast, `extractBytesArray`/`extractBytes32Array`/`extractSigArray` perform `new byte[len][]` (or `new byte[len][32]`) purely from the decoded length word, with `len` bounded only by `int` range, not by any energy-related or data-size-related sanity check. Allocating an object array with billions of elements (each a reference, 4–8 bytes) can immediately exhaust the JVM heap, triggering an `OutOfMemoryError` inside the node process handling the contract call.

### Impact Explanation
Any unprivileged account can construct and broadcast a smart-contract transaction that invokes the precompiled contract using these helpers, supplying a crafted length word. This can force every full node that validates/executes the transaction (and every node that re-executes it during block application) to attempt a multi-gigabyte array allocation, causing an `OutOfMemoryError` and a node crash or halt. Because block execution is deterministic and mandatory for consensus, this can be triggered against the entire network, resulting in a chain-wide denial of service — matching the "node crash or halt" impact category explicitly accepted by this scan's validation rules.

### Likelihood Explanation
Likelihood is high for an attacker with basic knowledge of the ABI encoding used by this precompile: the trigger is a single, unprivileged, signed transaction with crafted call-data (no special permissions, staking, or contract deployment access required), and the allocation happens deterministically during `execute()`, prior to any downstream energy exhaustion check that might otherwise limit the attack.

### Recommendation
Add explicit bounds checking on `len` in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` before allocation — e.g., reject the call (return `Pair.of(true, DataWord.ZERO().getData())` or throw a VM exception) if `len` exceeds a small sane maximum (consistent with `words.length` and the already-validated `isValidAbiEncoding` bounds), mirroring the explicit `spendCount`/`receiveCount` bound checks already used elsewhere in `PrecompiledContracts.java`.

### Proof of Concept
1. Craft a transaction invoking the precompiled contract that internally calls `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, with `data` such that `words[offset]` decodes (via `intValueSafe()`) to a very large integer (e.g., close to `Integer.MAX_VALUE`) while `words` itself has few real elements after `offset`.
2. Broadcast the transaction to the network.
3. On execution, the helper allocates `new byte[len][...]`, causing the JVM to attempt a multi-gigabyte allocation and throw `OutOfMemoryError` within the TVM execution path in every node that processes the transaction/block.

Note: due to index size limits, I could not confirm from the available index the exact precompiled contract class (address/name) whose `execute()` method calls these three helper functions — only their definitions within `PrecompiledContracts.java` were retrievable. A full-repository session (e.g., a Devin run with complete file access) is recommended to identify the exact call site(s) and confirm the concrete calldata layout needed to reach these helpers, and to verify whether any wrapping precompiled-contract class performs additional bounds checks before calling them.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
