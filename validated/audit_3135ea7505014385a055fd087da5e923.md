Based on my investigation, I found that `handleCreateRelayRequest` in `relay_manager.go` does not verify that the `from` address in a `CreateRelayRequest` control message actually belongs to the sending peer `h`. This is structurally analogous to the reported bug: an already-authenticated actor (`h`, who has a valid handshake and certificate) supplies a claimed identity (`from`, taken directly from the message body) that the code trusts implicitly and installs relay state for, without checking that `from` is one of `h.vpnAddrs`.

### Title
Relay state can be poisoned for an arbitrary victim VPN address via unverified `RelayFromAddr` in `CreateRelayRequest` - (File: relay_manager.go)

### Summary
`handleCreateRelayRequest` derives `from` directly from the attacker-controlled `NebulaControl.RelayFromAddr`/`OldRelayFromAddr` field and uses it, unverified against `h.vpnAddrs`, to install relay state (`AddRelay`) and to answer with a `CreateRelayResponse` claiming to be relaying traffic on behalf of `from`.

### Finding Description
`handleCreateRelayRequest` extracts `from := protoAddrToNetAddr(m.RelayFromAddr)` [1](#0-0)  and only checks that `from` is not one of the local node's own addresses [2](#0-1) . It never checks that `from` is contained in `h.vpnAddrs` — the set of addresses actually certified for the handshaken peer `h` that sent the control message. It then proceeds to call `AddRelay(...)` and reply with a `CreateRelayResponse` keyed on that unverified `from` address [3](#0-2) .

This mirrors the report's root cause: an authenticated party (the Solana signer / here, the handshaken peer `h`) supplies an identity claim (the seat owner / here, `RelayFromAddr`) that is trusted without validating it actually belongs to the party making the request.

### Impact Explanation
A fully-authenticated (but otherwise unprivileged) peer can send a `CreateRelayRequest` claiming `RelayFromAddr` equal to any victim VPN address it does not own. This causes the target node to install relay routing state (`AddRelay`, terminal/established relay entries) associating the attacker's own hostinfo `h` as a relay path "from" the victim's address, and to answer with a `CreateRelayResponse` for that address. This is remote state poisoning of the relay subsystem for an address the attacker doesn't control, potentially misdirecting or disrupting relay traffic intended for the legitimate victim, without the CA-signed certificate of the victim ever being presented.

### Likelihood Explanation
Any peer that has completed a normal (legitimate) handshake with a target node — i.e., any node with a valid certificate signed by the same CA, which is the baseline trust level for any Nebula mesh member — can send this control message; no special privilege beyond a completed handshake is required, and the relay code path is reached in `f.relayManager.HandleControlMsg` for every `header.Control` message [4](#0-3) .

### Recommendation
In `handleCreateRelayRequest` (and the analogous `handleCreateRelayResponse`), verify that `from` (`m.RelayFromAddr`/`m.OldRelayFromAddr`) is contained within `h.vpnAddrs` before installing or updating any relay state, rejecting the request/response otherwise — mirroring the self-address check already performed for `f.myVpnAddrsTable.Contains(from)`.

### Proof of Concept
1. Attacker node `A` completes a normal handshake with target node `T` (any CA-signed cert is sufficient — no elevated privilege needed).
2. `A` sends `T` a `header.Control` message of type `NebulaControl_CreateRelayRequest` with `RelayFromAddr` set to victim `V`'s VPN address (a node `A` has never handshaken with) and `RelayToAddr` set to `T`'s own address.
3. `T`'s `relayManager.HandleControlMsg` routes this to `handleCreateRelayRequest`, which only rejects if `from == T`'s own address; since `from == V ≠ T`, the check passes.
4. `T` calls `AddRelay(..., h, ..., from=V, ..., TerminalType, Established)` on `A`'s hostinfo `h`, installing relay state that claims `A` is a valid relay path "from" `V`, and replies with a `CreateRelayResponse` for `V` — all without `V`'s certificate or consent ever being verified.

**Note:** I was not able to fully trace how this poisoned relay entry is subsequently consumed by the data-plane relay-selection logic (e.g., whether `T` would actually route real traffic destined to/from `V` through `A` as a result), since that would require deeper analysis of `hostmap.go`'s relay query paths and the e2e relay test suite than the indexed context allowed. I recommend a Devin session with full repository access to confirm the exploitability chain end-to-end (specifically whether this poisoned state can be leveraged to intercept or misdirect a victim's actual traffic) before treating this as a confirmed high-severity finding.
