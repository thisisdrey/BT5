### Title
Attacker-controlled array-count words in TVM signature precompiles allow multi-gigabyte allocation before validation - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts parse an attacker-supplied ABI word as an array length and immediately allocate a Java array of that size (`new byte[len][]`) before the length is bounds-checked against `MAX_SIZE`. This is the same bug class as CVE-2026-58060 (HSS public-key level count unbounded, enabling huge allocation on verify): an untrusted count field is trusted to size an allocation before validation.

### Finding Description
`extractBytesArray`, `extractSigArray`, and `extractBytes32Array` read `len` directly from a caller-controlled `DataWord` via `intValueSafe()` and unconditionally allocate `new byte[len][]`: [1](#0-0) 

`intValueSafe()` clamps only overflow to `Integer.MAX_VALUE`, it does not enforce any semantic bound related to the precompile's `MAX_SIZE`: [2](#0-1) 

In `ValidateMultiSign.execute` and `BatchValidateSign.doExecute`, the `MAX_SIZE` bound check on the array-size word is only performed when the `allowTvmSelfdestructRestriction` hard-fork flag is enabled — the check is skipped entirely otherwise, and even when it runs it is a separate, ad-hoc re-computation of the offset/size rather than a check enforced inside the extraction helpers themselves: [3](#0-2) [4](#0-3) 

Because `extractBytesArray`/`extractSigArray`/`extractBytes32Array` are the same low-level helpers reused across call sites, and the bound check is bolted on externally and flag-gated rather than being intrinsic to the allocation, any code path (current or future) that reaches these helpers without first re-implementing the identical `MAX_SIZE` guard will allocate an array sized directly from attacker data, up to `Integer.MAX_VALUE` (2,147,483,647) elements — an 8–16 GB object-array allocation attempt on a 64-bit JVM.

### Impact Explanation
A crafted call to the `ValidateMultiSign`/`BatchValidateSign` precompiled contracts (reachable from any smart contract via `CALL`/`STATICCALL`, and thus from any unprivileged, unpermissioned transaction broadcaster) can force a full node — including nodes still applying blocks without `allowTvmSelfdestructRestriction` active, or reached via `extractBytes32Array`'s unguarded second path — to attempt an allocation on the order of gigabytes for a single `byte[][]` array. Depending on JVM heap configuration this throws `OutOfMemoryError`, which is uncaught by the narrow `try/catch (Throwable t)` scoping in some paths and can abort transaction execution/block application, causing node instability, degraded availability, or a crash that halts block production/serving on affected nodes — matching the "node crash or halt" impact bar.

### Likelihood Explanation
The precompiles are reachable by any account able to submit a `TriggerSmartContract` transaction, requiring no special permission, stake, or witness/committee role — the same low-privilege trigger class the CVE targets (unauthenticated/low-privilege input feeding an unbounded verify-time allocation). Exploitability is conditioned on the specific hard-fork flag state (`allowTvmSelfdestructRestriction`) for the `signatures`/`addresses` count words in the guarded call sites, but the underlying helper functions themselves contain no intrinsic bound, so the risk is structural rather than incidental.

### Recommendation
Move the `MAX_SIZE` (or equivalent sane upper bound, e.g. `DataWord.WORD_SIZE`-derived and gas-metered) validation inside `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` themselves — reject before allocating when `len` exceeds the bound or when `len * elementSize` would exceed the remaining `data`/`words` length — instead of relying on call-site, flag-gated pre-checks that can be bypassed or omitted.

### Proof of Concept
Craft ABI-encoded calldata to `BatchValidateSign` (or `ValidateMultiSign`) where the array-length word at the `addresses` (or `signatures`) offset is set to a large value such as `0x7fffffff`, with the actual payload truncated/short. On a node/network state where `allowTvmSelfdestructRestriction` is not active (or via the `extractBytes32Array` call which is invoked unconditionally in `BatchValidateSign.doExecute`), this drives execution into: [5](#0-4) 
which calls `extractBytes32Array(words, offset)` with `len = 0x7fffffff`, triggering `new byte[2147483647][]` and an `OutOfMemoryError`/multi-GB allocation attempt during transaction execution.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];

    return bytes32Array;

          bytesLen);
    }
    return bytesArray;
  }

  /**
   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()
   */
  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
    return intValue;
  }
