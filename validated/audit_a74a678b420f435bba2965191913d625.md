### Title
Protocol liquidation fee is seized to `feeCollector` even on underwater positions, worsening bad debt instead of covering the deficit - (File: contracts/Pool.sol)

### Summary
`Pool.liquidate` always skims `protocolLiquidationFee` from the seized collateral and sends it to `feeCollector`, even when the liquidated account is insolvent (collateral < debt) and the entire collateral balance is being seized. In that scenario every wei routed to `feeCollector` is collateral that is no longer available to repay debt, directly increasing the pool's unbacked debt — the same bug class as the Symmetrical finding where the protocol keeps user funds during liquidation instead of using them to reduce the deficit.

### Finding Description
In `Pool.liquidate` (contracts/Pool.sol:581-593), the seizure amount is computed by `quoteLiquidateOut`, which splits the seized collateral into `_toLiquidator` (debt repayment + `liquidatorIncentive`) and `_fee` (`protocolFee` to the protocol):

```solidity
// contracts/Pool.sol:462-471
(uint128 _liquidatorIncentive, uint128 _protocolFee) = feeProvider.liquidationFees();
if (_protocolFee > 0) {
    _fee = _toLiquidator.wadMul(_protocolFee);
}
if (_liquidatorIncentive > 0) {
    _toLiquidator += _toLiquidator.wadMul(_liquidatorIncentive);
}
_totalToSeize = _fee + _toLiquidator;
```

Then `liquidate` executes:

```solidity
// contracts/Pool.sol:587-593
syntheticToken_.burn(_msgSender, amountToRepay_);
_debtToken.burn(account_, amountToRepay_);
depositToken_.seize(account_, _msgSender, _toLiquidator);
if (_fee > 0) {
    depositToken_.seize(account_, _poolRegistry.feeCollector(), _fee);
}
```

When the position is underwater (`_depositInUsd < _debtInUsd`), `quoteLiquidateMax` caps `amountToRepay` at what the full collateral balance can buy via `quoteLiquidateIn` (contracts/Pool.sol:429-438), meaning the user's *entire* collateral is seized while debt remains outstanding. Yet `quoteLiquidateIn` still carves out `_fee = _repayAmountInCollateral.wadMul(_protocolFee)` (contracts/Pool.sol:402-404) from that collateral, so `1/(1+totalFees)` less debt is repaid than the collateral could cover. The protocol mints deposit tokens to `feeCollector` — withdrawable for real Treasury underlying via `withdraw`/`Treasury.pull` — while the liquidated account's `DebtToken` balance stays > 0 with zero collateral backing it.

This mirrors the referenced Symmetrical issue: funds that are in the protocol's hands during liquidation and could pay down the deficit are instead diverted to the fee collector.

### Impact Explanation
Protocol insolvency. For every underwater liquidation while `protocolLiquidationFee > 0`, the protocol transfers `collateral * protocolFee/(1+totalFees)` worth of value to `feeCollector` instead of burning that value of debt. The residual debt becomes permanently unbacked bad debt borne by the pool/other depositors. The existing test `should liquidate by repaying max possible amount (liquidateFee > 0)` (test/Pool.test.ts:821-871) already demonstrates the end state: `msdMET` balance of the account ≈ 0, `msEthDebtToken` balance > 0, and `fee` units of collateral sitting with `feeCollector`. The attacker/liquidator needs no privilege — this happens on every ordinary `liquidate` call on an insolvent account.

### Likelihood Explanation
Requires only: (1) `feeProvider.liquidationFees().protocolFee > 0` (a supported, tested configuration), and (2) any account going underwater, which is exactly the market condition where preserving collateral for debt repayment matters most. No privileged action, oracle manipulation, or attacker sophistication is needed; a normal liquidator calling `liquidate` with `quoteLiquidateMax` triggers it.

### Recommendation
In `Pool.liquidate`/`quoteLiquidateOut`, skip the `protocolFee` (and arguably cap `liquidatorIncentive`) when the account's post-seizure collateral is exhausted while debt remains — e.g., detect that `_totalSeized >= depositToken_.balanceOf(account_)` and the position is insolvent, and in that case set `_fee = 0` so the full collateral value repays debt via `quoteLiquidateIn`-style accounting. At minimum, do not divert collateral to `feeCollector` when the liquidation leaves residual unbacked debt.

### Proof of Concept
Hardhat sketch based on the existing `Pool.test.ts` insolvency scenario (`newMetPrice = toUSD('0.50')`):

```ts
// given: alice deposited MET and minted msETH; MET price halves so debt > collateral
await feeProvider.updateProtocolLiquidationFee(parseEther('0.01')) // 1%
await masterOracle.updatePrice(met.address, toUSD('0.50'))
const depositBefore = await msdMET.balanceOf(alice.address)
const debtBefore = await msEthDebtToken.balanceOf(alice.address)

// when: liquidator repays the max, which seizes ~all collateral
const amountToRepay = await pool.quoteLiquidateMax(msEth.address, alice.address, msdMET.address)
const tx = await pool.connect(liquidator)
  .liquidate(msEth.address, alice.address, amountToRepay, msdMET.address)
const ev = (await tx.wait()).events!.find(e => e.event === 'PositionLiquidated')
const fee = ev.args![5]

// then: protocol took a fee while debt is left unbacked
const debtAfter = await msEthDebtToken.balanceOf(alice.address)
expect(await msdMET.balanceOf(alice.address)).to.be.closeTo(0, 6000)
expect(debtAfter).to.be.gt(0)                 // residual bad debt
expect(await msdMET.balanceOf(poolRegistryMock.feeCollector())).to.eq(fee)
expect(fee).to.be.gt(0)

// the seized `fee` could have repaid additional debt instead:
const extraDebtCoverable = await masterOracle.quote(met.address, msEth.address, fee)
// extraDebtCoverable of debt stays unbacked purely because feeCollector was paid
```

To make the divergence explicit, run the same scenario with `updateProtocolLiquidationFee(0)` and compare `debtAfter` — it is strictly lower when no fee is skimmed, proving the fee diverts collateral from deficit coverage to the protocol.
