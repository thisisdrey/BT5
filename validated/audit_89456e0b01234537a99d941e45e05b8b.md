### Title
Unbounded growth of `unfrozen_v2` list via expired-but-uncleared unfreeze entries causes DoS-level slowdown in `CancelAllUnfreezeV2Actuator` and `WithdrawExpireUnfreezeActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/CancelAllUnfreezeV2Actuator.java`)

### Summary
`UnfreezeBalanceV2Actuator.validate()` limits the number of *unexpired* unfreeze entries per account to `UNFREEZE_MAX_TIMES = 32` by calling `AccountCapsule.getUnfreezingV2Count(now)`, which only counts entries whose `getUnfreezeExpireTime() > now`. Entries whose expire time has already passed are never counted, and consequently are never bounded, and they only get physically removed from the account's `unfrozen_v2` list when an actuator that reads/clears the list runs (`WithdrawExpireUnfreezeActuator`, `UnfreezeBalanceV2Actuator.unfreezeExpire`, or `CancelAllUnfreezeV2Actuator`). If a user never triggers one of those cleanup paths (or triggers `CancelAllUnfreezeV2` before expiry so the list is repeatedly regrown), stale but still-listed `UnFreezeV2` records can accumulate in the underlying account protobuf.

### Finding Description
The check that bounds the size of `unfrozen_v2` is: [1](#0-0) 

```java
public int getUnfreezingV2Count(long now) {
    int count = 0;
    List<UnFreezeV2> unFreezeV2List = account.getUnfrozenV2List();
    for (UnFreezeV2 item : unFreezeV2List) {
      if (item.getUnfreezeExpireTime() > now) {
        count++;
      }
    }
    return count;
}
```

`UnfreezeBalanceV2Actuator.validate()` enforces `UNFREEZE_MAX_TIMES <= unfreezingCount` using this count only, so the check is bypassable if the attacker keeps the unexpired count under 32 while never removing already-expired-but-still-present entries. Since `now` is the block timestamp — attacker-uncontrollable but strictly increasing — entries the attacker chooses with a very short `unfreeze_delay_days` window (configurable via `getUnfreezeDelayDays()`, minimum could be small depending on committee configuration) expire quickly, freeing "room" under the 32-count cap for the attacker to add more `UnfreezeBalanceV2` transactions, while the already-expired items stay in the protobuf list until a withdrawal-type actuator runs and clears them.

Every actuator that must process this list — `CancelAllUnfreezeV2Actuator.execute()`, `WithdrawExpireUnfreezeActuator.execute()`/`getTotalWithdrawList`/`getRemainWithdrawList`, and `UnfreezeBalanceV2Actuator.unfreezeExpire()` — iterates the *entire* `unfrozen_v2` list every single time they are invoked: [3](#0-2) [4](#0-3) 

None of these loops have any size cap independent from `getUnfreezingV2Count`, so if an account manages to accumulate a very large number of stale entries (e.g., by repeatedly issuing `UnfreezeBalanceV2` right after each previous batch expires, without ever calling a clearing actuator, or via any race/edge condition where the count check and list growth diverge), any subsequent transaction referencing that account through `CancelAllUnfreezeV2Contract`, `WithdrawExpireUnfreezeContract`, or another `UnfreezeBalanceV2Contract` must iterate over the full, unbounded list of `UnFreezeV2` protobuf entries during block application inside `Manager`/actuator execution — a synchronous, non-gas-metered code path that every full node must execute identically to reach consensus.

### Impact Explanation
Because these actuators run during deterministic block application (not inside the gas-metered TVM), there is no per-operation energy/bandwidth throttling comparable to TVM opcodes. An attacker who can grow one account's `unfrozen_v2` list to a very large size can craft transactions (`CancelAllUnfreezeV2Contract`, `WithdrawExpireUnfreezeContract`) that all validating/producing nodes must process by iterating the full list, increasing block processing time for every node in the network. In the worst case this can slow block production/propagation across the network (a network-wide processing-time DoS), which corresponds to the "node crash or halt" / degraded availability impact class.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to repeatedly submit `UnfreezeBalanceV2Contract` transactions timed so that entries expire and are re-counted as "not unfreezing" by `getUnfreezingV2Count` while the raw list keeps growing because no cleanup actuator is invoked in between. This is entirely achievable by a single account issuing many low-value freeze/unfreeze cycles over time (bounded only by transaction fees/bandwidth cost per transaction, not by the 32-entry cap), so it is reachable by any ordinary signed-transaction sender without needing SR/witness privileges.

### Recommendation
- Enforce a hard cap on the total size of `unfrozen_v2` (including expired-but-unprocessed entries), not just the count of unexpired ones, in `AccountCapsule.getUnfreezingV2Count` / `UnfreezeBalanceV2Actuator.validate()`.
- Alternatively, force expired entries to be purged from the account's `unfrozen_v2` list at the point `addUnfrozenV2List` is called (i.e., always call `unfreezeExpire`-equivalent cleanup before adding a new entry), so the list can never grow beyond `UNFREEZE_MAX_TIMES` regardless of expiry timing.
- Add a cumulative iteration/size limit check in `CancelAllUnfreezeV2Actuator.execute`, `WithdrawExpireUnfreezeActuator.execute`, and `UnfreezeBalanceV2Actuator.unfreezeExpire` before iterating, to fail fast rather than perform unbounded work.

### Proof of Concept
1. Set `unfreeze_delay_days` (via `saveUnfreezeDelayDays`) to a small value so unfreeze entries expire quickly.
2. Repeatedly (over many blocks) submit `UnfreezeBalanceV2Contract` transactions from the same account, each unfreezing a minimal, valid amount. As earlier entries pass their `unfreeze_expire_time`, `getUnfreezingV2Count(now)` in `AccountCapsule.java` (lines 679-688) stops counting them, allowing the check `UNFREEZE_MAX_TIMES <= unfreezingCount` in `UnfreezeBalanceV2Actuator.validate` (lines 179-182) to keep passing, while `addUnfrozenV2List` (line 86) keeps appending new `UnFreezeV2` entries to the underlying protobuf list — never triggering a withdrawal/cancel actuator in between so the list is never cleared.
3. After accumulating a very large number of entries in `unfrozen_v2`, submit a `CancelAllUnfreezeV2Contract` (or `WithdrawExpireUnfreezeContract`) transaction referencing the same account.
4. Observe that `CancelAllUnfreezeV2Actuator.execute` (lines 57-74) must iterate the full, unbounded `unfrozenV2List` synchronously during block application, increasing processing time for every node that applies this transaction, proportional to the number of accumulated entries.
