The vulnerability claim is valid. Here is the complete analysis:

---

### Title
`CrossShardCommitSender::send_remote_update_for_success` Silently Drops Dependent-Edge Notifications for Aborted Transactions, Permanently Deadlocking Dependent Shards — (`aptos-move/aptos-vm/src/sharded_block_executor/cross_shard_client.rs`)

---

### Summary

`on_transaction_committed` is invoked for every committed transaction — including those that abort with a Move error or gas exhaustion. `send_remote_update_for_success` only iterates over the actual write set of the output. For an aborted transaction the write set contains only gas-charge entries; any key K that appears in `dependent_edges` but was never written is silently skipped. The dependent shard's `RemoteStateValue` for K was initialized in `Waiting` and has no timeout; `get_value()` blocks forever, permanently deadlocking the dependent shard's execution thread and halting block processing.

---

### Finding Description

**Step 1 — Hook is called unconditionally for aborted transactions.**

`record_finalized_output` in `executor.rs` calls the commit hook for every finalized transaction regardless of execution status:

```rust
if let Some(hook) = &self.transaction_commit_hook {
    hook.on_transaction_committed(txn_idx, &committed_output);
}
``` [1](#0-0) 

**Step 2 — `on_transaction_committed` unconditionally calls `send_remote_update_for_success`.**

There is no status check; any transaction whose global index appears in `dependent_edges` triggers the send path:

```rust
fn on_transaction_committed(&self, txn_idx: TxnIndex, txn_output: &TransactionOutput) {
    let global_txn_idx = txn_idx + self.index_offset;
    if self.dependent_edges.contains_key(&global_txn_idx) {
        self.send_remote_update_for_success(global_txn_idx, txn_output);
    }
}
``` [2](#0-1) 

**Step 3 — `send_remote_update_for_success` only iterates the write set.**

The function sends a `RemoteTxnWriteMsg` only for keys that appear in both the write set and `dependent_edges`. For an aborted transaction, the write set contains only gas-charge entries; key K is absent:

```rust
fn send_remote_update_for_success(&self, txn_idx: TxnIndex, txn_output: &TransactionOutput) {
    let edges = self.dependent_edges.get(&txn_idx).unwrap();
    for (state_key, write_op) in txn_output.write_set().expect_write_op_iter() {
        if let Some(dependent_shard_ids) = edges.get(state_key) {
            // ... sends message only if state_key is in write set
        }
    }
    // Keys in edges but NOT in write_set → no message sent, ever.
}
``` [3](#0-2) 

**Step 4 — `CrossShardStateView` initializes K in `Waiting` with no fallback.**

Every key declared as a cross-shard required edge is inserted as `RemoteStateValue::waiting()`:

```rust
for key in cross_shard_keys {
    cross_shard_data.insert(key, RemoteStateValue::waiting());
}
``` [4](#0-3) 

**Step 5 — `get_value()` blocks indefinitely with no timeout.**

```rust
pub fn get_value(&self) -> Option<StateValue> {
    let (lock, cvar) = &*self.value_condition;
    let mut status = lock.lock().unwrap();
    while let RemoteValueStatus::Waiting = *status {
        status = cvar.wait(status).unwrap();  // infinite wait
    }
    ...
}
``` [5](#0-4) 

When shard-1's transaction reads K via `CrossShardStateView::get_state_value`, it calls `get_value()` and blocks forever because no `RemoteTxnWriteMsg` for K was ever sent. [6](#0-5) 

**No compensating guard exists.** The `TransactionCommitHook` trait has only `on_transaction_committed`; there is no `on_execution_aborted` or equivalent path that would send `None` for unwritten dependent keys. [7](#0-6) 

---

### Impact Explanation

The dependent shard's execution thread blocks permanently inside `cvar.wait`. Because `execute_transactions_with_dependencies` uses a `rayon::scope` that waits for all spawned tasks to complete, the entire sub-block execution for that shard never returns. The coordinator never receives a result, and block execution for the entire block halts — a material chain availability failure. [8](#0-7) 

---

### Likelihood Explanation

Any aborted transaction (Move abort, gas exhaustion, arithmetic overflow, assertion failure) that the partitioner assigns cross-shard dependent edges to will trigger this. An unprivileged user can reliably cause an abort by submitting a transaction that calls `abort 0` or transfers more tokens than their balance. The partitioner's assignment of dependent edges is deterministic and observable from on-chain state, so an attacker can craft a transaction that is guaranteed to be partitioned with cross-shard dependencies and then abort it.

---

### Recommendation

After the write-set loop in `send_remote_update_for_success`, iterate over all keys in `edges` that were **not** covered by the write set and send a `RemoteTxnWriteMsg` with `write_op = None` for each:

```rust
fn send_remote_update_for_success(&self, txn_idx: TxnIndex, txn_output: &TransactionOutput) {
    let edges = self.dependent_edges.get(&txn_idx).unwrap();
    let mut notified_keys = HashSet::new();

    for (state_key, write_op) in txn_output.write_set().expect_write_op_iter() {
        if let Some(dependent_shard_ids) = edges.get(state_key) {
            notified_keys.insert(state_key.clone());
            for (dependent_shard_id, round_id) in dependent_shard_ids.iter() {
                // ... existing send logic ...
            }
        }
    }

    // Send None for every dependent key not present in the write set (aborted txn).
    for (state_key, dependent_shard_ids) in edges {
        if !notified_keys.contains(state_key) {
            for (dependent_shard_id, round_id) in dependent_shard_ids.iter() {
                let message = RemoteTxnWriteMsg(RemoteTxnWrite::new(state_key.clone(), None));
                // ... send logic ...
            }
        }
    }
}
```

The `RemoteTxnWrite` struct already supports `write_op: None` to signal an aborted write, and `CrossShardCommitReceiver` already handles it correctly via `write_op.and_then(|w| w.as_state_value())`. [9](#0-8) [10](#0-9)

### Proof of Concept

```rust
// Shard-0: transaction T declares dependent edge for key K to shard-1,
// but aborts before writing K (write set = {gas_key}).
//
// Expected: shard-1 receives RemoteTxnWriteMsg(K, None)
// Actual:   shard-1 receives nothing for K → get_value() blocks forever

#[test]
fn test_aborted_txn_deadlocks_dependent_shard() {
    // Build a CrossShardStateView for shard-1 with K as a required cross-shard key.
    let state_key_k = StateKey::raw(b"fungible_asset_balance_K");
    let mut keys = HashSet::new();
    keys.insert(state_key_k.clone());
    let view = Arc::new(CrossShardStateView::new(keys, &EmptyView));
    let view_clone = view.clone();

    // Spawn a thread simulating shard-1 reading K (will block forever without the fix).
    let handle = std::thread::spawn(move || {
        view_clone.get_state_value(&state_key_k) // blocks indefinitely
    });

    // Simulate shard-0 committing T with abort (no write for K).
    // With the bug: no RemoteTxnWriteMsg is sent for K.
    // handle.join() never returns → deadlock confirmed.
    assert!(handle.join().is_err(), "Expected deadlock");
}
```
