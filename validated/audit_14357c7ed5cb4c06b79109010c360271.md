### Title
Fsck validation is disabled when importing repositories from Git bundles, allowing malicious/corrupt objects to bypass integrity checks - ([File: internal/git/localrepo/bundle.go])

### Summary
The `CreateRepositoryFromBundle` and `FetchBundle` RPCs let a client import repository contents from an arbitrary, user-supplied Git bundle. Both code paths explicitly disable `transfer.fsckObjects` before invoking `git-clone`/`git-fetch`, meaning none of Gitaly's normal object-validation checks are applied to bundle-sourced objects, unlike every other ingestion path (`git-receive-pack`, `git-fetch-pack`) which always run fsck with `transfer.fsckObjects=true`.

### Finding Description
Gitaly configures fsck to run by default for all untrusted object ingestion. `templateFsckConfiguration` explicitly documents this rationale: "When receiving objects from an untrusted source, we want to always assert that all objects are valid," and sets `transfer.fsckObjects=true` for both `git-receive-pack(1)` and `git-fetch-pack(1)`. [1](#0-0) 

However, `Repo.CloneBundle` and `Repo.FetchBundle` — used exclusively for ingesting user-supplied bundle data — explicitly override this default and set `transfer.fsckObjects=false`: [2](#0-1) [3](#0-2) 

These functions are invoked directly from the `CreateRepositoryFromBundle` gRPC RPC, which streams arbitrary attacker/client-controlled bundle bytes and clones them without further validation: [4](#0-3) 

Both RPCs are registered as `op: MUTATOR` in the proto definition, meaning any client permitted to issue mutating RPCs against Gitaly (e.g., any authenticated GitLab user performing a project import from a bundle, or a repository mirror/fetch-bundle operation) can trigger this path: [5](#0-4) 

This mirrors the bug class in the report exactly: a validation step that is supposed to gate acceptance of externally supplied content (fsck ≈ ProcessProposal's block/tx verification) is unconditionally downgraded to a no-op ("non-fatal"/disabled) rather than rejecting the operation, so corrupt or malicious objects are unconditionally accepted and persisted into the repository's real object store (there is no quarantine step for bundle imports — objects go straight into the destination repository via `git clone`/`git fetch`).

### Impact Explanation
Fsck is Gitaly's primary defense against malformed or maliciously crafted Git objects (duplicate tree entries, degenerate/pathological trees, malformed `.gitmodules`, zero-padded filemodes exploited for other checks, etc.). By disabling `transfer.fsckObjects` for bundle-based imports, Gitaly permits objects that would be rejected on every other ingestion path (push, fetch) to be permanently written into a repository's object database. This corrupted/malicious state can then propagate to every consumer of the repository (other services, forks, object pools, or downstream fetches), potentially enabling further attacks that specifically rely on such objects passing fsck elsewhere, or causing downstream tooling (which assumes previously-fsck'd repositories) to mishandle malformed trees/commits. It is also a straightforward denial-of-service vector: repeated import of corrupt bundles reliably plants broken objects that other RPCs (e.g., `Fsck`, `CreateFork` from this repo) will then surface as broken, and which can degrade or break repository operations that assume fsck-clean content.

### Likelihood Explanation
This is reachable by an ordinary, unprivileged flow: any user- or automation-triggered "import repository from bundle" or bundle-based fetch/mirror action results in Gitaly calling `CreateRepositoryFromBundle`/`FetchBundle` with fully attacker-controlled bundle bytes, no special/administrative access to Gitaly internals is required beyond normal RPC access already needed to import projects, matching the "ordinary user's push/fetch/import" reachability bar. The disabling of fsck is unconditional (not merely a fallback for a rare edge case), so any bundle exploiting an fsck check will succeed every time.

### Recommendation
Do not blanket-disable `transfer.fsckObjects` for bundle imports. Instead:
- Re-enable fsck by default for `CloneBundle`/`FetchBundle`, matching the behavior of `git-receive-pack`/`git-fetch-pack`.
- If the Git 2.46 bundle-fsck severity-config limitation described in the code comments must be worked around, use a more targeted mitigation (e.g., perform the clone into a quarantine/pool location and run a separate explicit `git fsck` pass before migrating objects into the destination repository, similar to how push quarantine already isolates objects before they are accepted).
- Ensure any relaxed/ignored fsck message IDs are scoped as narrowly as the documented Git limitation requires, rather than disabling fsck entirely.

### Proof of Concept
1. Craft a Git bundle containing a tree object with duplicate entries (as already demonstrated to be fsck-detectable in this codebase's own tests, see `TestCreateFork_fsck`, which shows `git fsck` reports `duplicateEntries: contains duplicate file entries`). [6](#0-5) 
2. Call `CreateRepositoryFromBundle` (or `FetchBundle` against an existing repository) with this bundle as the streamed payload.
3. Observe the RPC succeeds without error because `transfer.fsckObjects=false` is force-set for the underlying `git clone`/`git fetch`, confirmed by the existing test comment: "bundle contains fsck error" / "fsck checks are ignored" for `CloneBundle`/`FetchBundle`. [7](#0-6) 
4. Subsequently calling `Fsck` on the newly created/updated repository reveals the broken object is now permanently stored, proving fsck validation was bypassed on ingestion.

// templateFsckConfiguration generates our fsck configuration, including ignored checks.
// The prefix must either be "fsck", "receive.fsck" or "fetch.fsck" and indicates whether
// it should apply to git-fsck(1), git-receive-pack(1) or to git-fetch-pack(1).
func templateFsckConfiguration(_ context.Context, prefix string) []GlobalOption {
	configPairs := []GlobalOption{
		// When receiving objects from an untrusted source, we want to always assert that
		// all objects are valid. When fetch.fsckObjects or receive.fsckObjects are not set,
		// the value of transfer.fsckObjects is used instead. Since the fsck configuration
		// of git-fetch-pack(1) and git-receive-pack(1) is coupled, transfer.fsckObjects can
		// be used for both.
		ConfigPair{Key: "transfer.fsckObjects", Value: "true"},
	}
