Audit Report

## Title
Unchecked `DeliveryReceipt.success` flag allows relayer reward payout for failed message execution - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
`process_delivery_receipt` decodes a `DeliveryReceipt` via `DeliveryReceipt::try_from`, which includes a `success: bool` field reporting whether the corresponding message actually executed successfully on Ethereum. The pallet verifies only the cryptographic proof of the event log via `T::Verifier::verify`, but never inspects `receipt.success` before paying the pending relayer reward and deleting the `PendingOrders` entry, so proofs of failed executions are treated identically to proofs of successful ones for reward purposes.

## Finding Description
The `submit_delivery_receipt` extrinsic verifies event-log authenticity, decodes the log into a `DeliveryReceipt` struct (which carries `success: bool` populated straight from the Ethereum `InboundMessageDispatched` event), and calls `process_delivery_receipt`. That function checks only `receipt.gateway` against `T::GatewayAddress::get()` and looks up `PendingOrders` by `receipt.nonce`; it then pays `order.fee` via `T::RewardPayment::register_reward` and unconditionally removes the order whenever those two checks pass. The decoded `receipt.success` value is never read anywhere in this function or elsewhere in the pallet's reward-payout logic, so the semantic execution outcome is silently discarded despite being available and cryptographically authenticated. [2](#0-1) [3](#0-2) 

## Impact Explanation
Because Ethereum-side execution status is never validated, a relayer can submit a legitimate proof for a real `InboundMessageDispatched` event with `success=false` — i.e., a message whose execution on Ethereum genuinely failed or reverted — and still collect the full `order.fee` reward, with the `PendingOrders` entry deleted as if delivery had succeeded. This is a duplicate/unbacked settlement: reward funds are paid out for work that did not achieve the intended outcome, and the deleted order removes any associated fee tracking for legitimate re-delivery or reconciliation of the failed message. This matches the "bridge rewards ... must conserve value and settle exactly once to the rightful beneficiary and amount" / "duplicate settlement or payout" impact category.

## Likelihood Explanation
No privileged role is required. Any unpermissioned, signed account can call `submit_delivery_receipt` with a genuinely valid inclusion proof for a `success=false` event, which naturally occurs whenever the destination-side Gateway call reverts on Ethereum (e.g., gas griefing, execution errors). No relayer/validator/prover collusion or key compromise is needed — the attacker only needs to submit a truthful proof of a failed delivery to claim the reward anyway, making this fully reachable via the public extrinsic.

## Recommendation
In `process_delivery_receipt`, explicitly branch on `receipt.success`: only pay `order.fee` and settle the order when `success == true`; for `success == false`, withhold the reward and either requeue/allow re-relay or otherwise avoid deleting the `PendingOrders` entry as if delivery had succeeded.

## Proof of Concept
1. A message is queued via `do_process_message`, creating a `PendingOrder { nonce, fee, .. }` with `fee > 0` [4](#0-3) .
2. On Ethereum, the corresponding Gateway call executes but reverts, so the emitted `InboundMessageDispatched` event has `success = false`.
3. Any signed relayer submits `submit_delivery_receipt` with a valid inclusion proof of that event.
4. `T::Verifier::verify` succeeds (proof is genuine), `DeliveryReceipt::try_from` decodes `success = false` into the struct, but `process_delivery_receipt` never inspects it — the reward is paid via `T::RewardPayment::register_reward` and the order removed, exactly as the unconditional flow shown at lines 466-475 executes regardless of `success`.

				);
