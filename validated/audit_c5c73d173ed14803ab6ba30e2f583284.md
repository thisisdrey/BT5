### Title
Priority-floor pre-verify filter is trivially evaded because packet priority is a self-declared, unfunded value, allowing unstaked senders to force full `ed25519_verify_serial` work under scheduler saturation - (File: core/src/sigverify.rs)

### Summary
The scheduler-published `SchedulerPriorityFloor` is meant to let sigverify cheaply drop packets that would immediately be evicted by a saturated banking-stage container, bounding wasted `ed25519_verify_serial` work. Because the "priority" compared against the floor is computed purely from attacker-controlled bytes (declared compute-unit price) with no signature or funds verification at that point, an unstaked attacker can always craft packets whose priority sits at `floor + 1` (or simply set an arbitrarily high compute-unit price), guaranteeing every packet clears the floor check and forces full ed25519 verification, even though the transaction will later fail (e.g., due to lack of real funds/fee-payer balance) once it reaches banking-stage checks.

### Finding Description
`apply_priority_floor_to_batch` in `core/src/sigverify.rs` drops a packet only if `calculate_priority_from_bytes(bank, data) <= floor`: [1](#0-0) 

`calculate_priority_from_bytes` (in `core/src/transaction_priority.rs`) computes priority purely from the serialized message contents — cost model + declared `compute_unit_price` — without any signature verification or account-balance/fee-payer check: [2](#0-1) 

The floor check happens in `run_transaction_task` *before* `ed25519_verify_serial` is invoked, and only after cheap `dedup_packets_and_count_discards`: [3](#0-2) 

The floor value itself is derived by the scheduler from the retained buffer's current minimum priority under saturation: [4](#0-3) 

Because `compute_unit_price` in a `ComputeBudgetInstruction` is entirely attacker-chosen and free to set (there is no requirement that the fee payer actually hold funds to back the claimed price at this stage — that is checked far downstream in banking-stage/bank execution, not in sigverify or the priority calculation), an attacker does not need to "probe" anything: they can simply set an arbitrarily large `compute_unit_price` (e.g., `u64::MAX`) on every crafted packet, guaranteeing `priority > floor` for essentially any floor value the scheduler could publish. Each such packet still needs a validly-signed transaction (cheap for the attacker to produce with a throwaway keypair, since Ed25519 signing is inexpensive client-side), but every one of them forces the leader to perform the expensive `ed25519_verify_serial` call in `run_transaction_task`, at line 327-331, defeating the purpose of the floor.

The floor's doc comment explicitly frames its purpose as bounding sigverify work under saturation ("drop at-or-below-floor arrivals... ahead of signature verification"), but the check compares against a value with no economic backing, so the "floor" only filters out senders who declare a *lower* price than an attacker willing to declare an unlimited price for free — it does not verify the declared price is collectible.

### Impact Explanation
This falls under the stated scope: "An unprivileged attacker can cheaply force sigverify, dedup, scheduling, or buffering work that vastly exceeds the fees ever collected, degrading the leader below true cost." Since priority is unauthenticated and costless to inflate, the floor provides no effective backpressure against a determined attacker: sustained CPU is spent in `ed25519_verify_serial` on packets whose real fee-paying ability is nil, even while the scheduler container is saturated and the transactions are ultimately dropped/rejected downstream. This matches the "grossly underpriced pre-fee work" bounty category, scoped to sigverify CPU waste under saturation.

### Likelihood Explanation
High feasibility: the attacker needs only an unstaked QUIC/UDP connection to the leader's TPU, the ability to generate throwaway keypairs, and knowledge of the public `ComputeBudgetInstruction::set_compute_unit_price` format — no probing of the actual floor value is even required if the attacker simply sets the maximum possible `compute_unit_price`, since `priority` scales monotonically with declared price per `calculate_priority_and_cost`. This is trivially repeatable and sustainable at line rate against the TPU sigverify workers.

### Recommendation
Do not let a pre-verify floor rely solely on a self-declared, unauthenticated priority value. Options: (1) require that packets passing the floor also pass a cheap fee-payer plausibility check (e.g., verify claimed fee against a minimum stake/balance heuristic) before committing to full sigverify; (2) rate-limit/dedup based on (fee-payer pubkey, declared price) tuples so an attacker can't cheaply mint unlimited distinct "high priority" packets from unfunded accounts; (3) move floor-based rejection to occur after a lightweight balance/existence check on the declared fee payer, or cross-reference against known-funded accounts, rather than trusting instruction-declared compute-unit price alone.

```rust
#[test]
fn floor_hugging_defeats_priority_floor_with_unfunded_sender() {
    let (bank, _mint) = test_bank_with_lamports_per_signature(5_000);
    // Attacker uses a throwaway, unfunded keypair.
    let attacker = Keypair::new();
    let published_floor = 100u64; // scheduler currently publishes this floor

    // Attacker crafts a validly-signed tx with maximal compute_unit_price,
    // requiring no real funds to construct.
    let bytes = make_tx_bytes(&attacker, bank.last_blockhash(), u64::MAX);
    let priority = calculate_priority_from_bytes(&bank, &bytes).unwrap();

    // Priority always clears the floor regardless of its published value.
    assert!(priority > published_floor);

    // apply_priority_floor_to_batch will therefore never discard this packet,
    // forcing it through to ed25519_verify_serial even though the attacker
    // account holds no funds and the tx will fail later (insufficient balance).
    let mut batch = to_single_packet_batch(&bytes);
    let (dropped, all_below) = apply_priority_floor_to_batch(&mut batch, published_floor, &bank);
    assert_eq!(dropped, 0);
    assert!(!all_below);
}
```
Expected assertion outcome: the packet from a zero-balance attacker is never dropped by `apply_priority_floor_to_batch` regardless of the published floor, confirming the floor cannot bound sigverify work against unfunded, priority-inflated spam.

```rust
fn apply_priority_floor_to_batch(
    batch: &mut PacketBatch,
    floor: u64,
    bank: &Bank,
) -> (usize, bool) {
    let mut dropped: usize = 0;
    let mut any_kept = false;
    for mut packet in batch.iter_mut() {
        if packet.meta().discard() {
            continue;
        }
        let Some(data) = packet.data(..) else {
            // Zero-length or otherwise unreadable: leave to downstream
            // stages to reject.
            any_kept = true;
            continue;
        };
        // Unparseable packets are kept and left for downstream rejection.
        match calculate_priority_from_bytes(bank, data) {
            Some(priority) if priority <= floor => {
                packet.meta_mut().set_discard(true);
                dropped = dropped.saturating_add(1);
            }
            _ => any_kept = true,
        }
    }
    (dropped, !any_kept)
```

```rust
    let view = SanitizedTransactionView::try_new_sanitized(data, &sanitize_config()).ok()?;
    let runtime_tx = RuntimeTransaction::<SanitizedTransactionView<_>>::try_new(
        view,
        MessageHash::Compute,
        None,
    )
    .ok()?;
    let transaction_configuration = runtime_tx
        .transaction_configuration(&bank.feature_set)
        .ok()?;
    let (priority, _cost) =
        calculate_priority_and_cost(bank, &runtime_tx, &transaction_configuration);

    Some(priority)
}
```
