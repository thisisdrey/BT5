### Title
Unbounded array-length field in `ValidateMultiSign`/`BatchValidateSign` precompiled contracts causes uncaught OOM DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts (addresses `0x9` and `0xa`) decode an attacker-supplied ABI-encoded `bytes[]` array by reading a "length" word directly out of the caller-controlled calldata and using it to allocate a Java array (`new byte[len][]`) before any bound check is performed. This mirrors the CVE-2017-14056 pattern: a count/size field taken from untrusted input is used to drive an allocation/loop without verifying it against the actual size of the backing data, allowing a single malicious call to request an enormous allocation.

### Finding Description
`extractBytesArray` (the legacy decode path, used whenever `VMConfig.allowTvmSelfdestructRestriction()` is `false`) has no upper bound check on `len` before allocating: [1](#0-0) 

`extractBytes32Array` (used for the `addresses` array in `BatchValidateSign`) is even weaker — it does not check `offset` against `words.length` at all, and computes `len` unconditionally from attacker data: [2](#0-1) 

In `ValidateMultiSign.execute`, when `allowTvmSelfdestructRestriction()` is not active, `extractBytesArray` is invoked *before* the `MAX_SIZE` sanity check on `signatures.length`, and the call is **not wrapped in any try/catch**: [3](#0-2) 

`BatchValidateSign.doExecute` has the same shape: the `MAX_SIZE` guard on `sigArraySize`/`addrArraySize` is only performed `if (VMConfig.allowTvmSelfdestructRestriction())`; when that flag is off, `extractBytesArray`/`extractBytes32Array` run first with a fully attacker-controlled `len`: [4](#0-3) 

The `isValidAbiEncoding` check that gates these functions (only active post-`allowTvmOsaka`) only validates the overall calldata length is `header + n*item` words — it does not constrain the *value* of the length word embedded inside the calldata, so an attacker can still set that word to an arbitrarily large 256-bit value while keeping the overall calldata shape "valid": [5](#0-4) 

There is no framework-level catch of `java.lang.OutOfMemoryError` around precompiled-contract invocation (`Program.callToPrecompiledAddress`); the only "OutOfMemory" handling in the codebase is the unrelated custom `OutOfMemoryException` used for TVM memory-expansion metering, which is not triggered by a raw `new byte[len][]` allocation inside a precompile.

### Impact Explanation
Any unprivileged account can deploy a trivial contract that performs a `STATICCALL`/`CALL` to precompile address `0x9` (`batchValidateSign`) or `0xa` (`validateMultiSign`) with crafted calldata encoding a huge `bytes[]`/`address[]` length word. When `allowTvmSelfdestructRestriction` is not yet activated on a given chain (default state prior to that specific TVM proposal being voted in, e.g. on a freshly deployed private/consortium chain or a network that has not yet passed that proposal), this triggers an unguarded, uncaught allocation attempt of an oversized array on the node process executing the transaction. This can throw a real `java.lang.OutOfMemoryError` that is not contained by any precompile-level try/catch (clearly so for `ValidateMultiSign`), propagating up through transaction execution and potentially destabilizing or crashing the JVM process for every full node that processes/validates the block — a much stronger outcome than ordinary excess energy consumption, since it is not properly energy-metered against the true cost of the allocation.

### Likelihood Explanation
Reachable directly from any single signed `TriggerSmartContract` transaction issued by any unprivileged account; no special permission, staking, or witness/SR status is required — it only requires a deployed contract that calls the precompile with malicious calldata. The gating condition is the on-chain state of the `allowTvmSelfdestructRestriction` hard-fork switch; on networks (or points in time / testnets / private deployments) where this switch has not been enabled, the bug is fully unguarded and trivially triggerable.

### Recommendation
- Add an explicit, unconditional bound check (e.g., against `MAX_SIZE` and/or `words.length`) inside `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` themselves, before allocating `new byte[len][]`, rather than relying on an external, hard-fork-gated caller-side check.
- Remove the dependency on `VMConfig.allowTvmSelfdestructRestriction()` for this specific protection so the fix applies unconditionally regardless of the proposal's activation status.
- Wrap precompiled-contract decode/execute paths in a try/catch that treats resource-allocation failures as a controlled contract revert rather than letting them propagate as raw `OutOfMemoryError`.

### Proof of Concept
1. On a java-tron network/chain where `allowTvmSelfdestructRestriction` has not been activated, deploy a minimal contract that issues a `STATICCALL` to address `0x000000000000000000000000000000000000000a` (`validateMultiSign`) or `...09` (`batchValidateSign`).
2. Craft the calldata as ABI-encoded `validateMultiSign(address,uint256,bytes,bytes[])` where the offset/length word for the `bytes[]` parameter is set to a very large value (e.g., close to `Integer.MAX_VALUE`), while keeping the overall calldata length consistent with `isValidAbiEncoding`'s header/tail arithmetic (or simply invoke pre-`allowTvmOsaka`, where that guard is entirely absent).
3. Broadcast a `TriggerSmartContract` transaction invoking this contract from any funded account.
4. Observe `extractBytesArray`/`extractBytes32Array` attempting `new byte[len][]` with `len` derived from the crafted word, causing a large/failing allocation on every node that executes/validates the transaction.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
