### Title
Fixed-window stream throttling in `ConnectionStreamCounter` permits near-2x burst at STREAM_THROTTLING_INTERVAL boundary - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Summary
`ConnectionStreamCounter::reset_throttling_params_if_needed` implements a fixed (non-sliding) window rate limiter: it zeroes `stream_count` only when more than `STREAM_THROTTLING_INTERVAL` (100ms) has elapsed since the last reset. An attacker who times stream opens to straddle a reset boundary can be admitted up to `max_streams_per_throttling_interval` streams just before the reset and another full quota immediately after, receiving close to 2x the intended per-interval cap within a short real-time window.

### Finding Description
`throttle_stream` in `streamer/src/nonblocking/stream_throttle.rs` (lines 233-271) calls `stream_counter.reset_throttling_params_if_needed()` and only sleeps/throttles when `streams_read_in_throttle_interval >= max_streams_per_throttling_interval`. The reset logic in `ConnectionStreamCounter::reset_throttling_params_if_needed` (lines 213-230) resets `stream_count` to 0 and moves `last_throttling_instant` forward only when the elapsed time since the last reset exceeds `STREAM_THROTTLING_INTERVAL_MS` (100ms) [1](#0-0) . This is a fixed-window counter, not a sliding window or token bucket: it has no memory of *when within the window* the previous streams were consumed, so a burst can occur at the very end of window N and another full burst at the very start of window N+1, producing up to ~2x `max_streams_per_throttling_interval` admitted streams in a period much shorter than `STREAM_THROTTLING_INTERVAL_MS`. This limiter is invoked from `SwQos::on_new_stream` (`streamer/src/nonblocking/swqos.rs` lines 496-516) which is awaited per new QUIC uni-stream before packets are read in `handle_connection` (`streamer/src/nonblocking/quic.rs` lines 610-628), meaning the attacker fully controls the timing of stream opens against `remote_address`/`peer_type` to align with the reset boundary. No other independent smoothing mechanism (e.g., a per-ms sub-limit or a rolling window) enforces the cap tighter than the 100ms fixed window; `StakedStreamLoadEMA` throttles staked load only in aggregate across all staked connections, not per-connection burst alignment.

### Impact Explanation
This is a QoS/fairness evasion (BOUNDED_RESOURCES category): a single attacker connection can obtain roughly double its allotted `max_streams_per_throttling_interval` stream-open capacity in a narrow time window by exploiting the fixed-window reset boundary, at the expense of other senders sharing the same throttling budget (unstaked pool or staked-stake-proportional share). The effect is bounded — capacity is at most ~2x, not unbounded — but it does defeat the intended per-interval cap invariant and can be repeated every window, giving a sustained ~2x effective throughput advantage over honest, evenly-paced senders for TPU stream ingress.

### Likelihood Explanation
Fully reachable by an unprivileged remote client (unstaked or low-stake) that has an already-admitted QUIC connection to the TPU port; no special stake, keys, or peer control is required. Exploitation only requires accurately timing stream opens relative to `last_throttling_instant`, which is observable indirectly via `throttled_streams`/backpressure behavior (sleep triggered once the cap is hit) and can be approximated by opening a max-quota burst, waiting slightly over 100ms, then bursting again — this is straightforward and repeatable every ~100ms cycle.

### Recommendation
Replace the fixed-window reset with a sliding-window or token-bucket algorithm (e.g., decay `stream_count` proportionally to elapsed time each check, or use `solana_net_utils::token_bucket::TokenBucket`, already used elsewhere in `simple_qos.rs`) so that the maximum number of streams admitted in any rolling `STREAM_THROTTLING_INTERVAL_MS` window — not just within a fixed-boundary window — never exceeds `max_streams_per_throttling_interval`.

### Proof of Concept
Rust unit test in `streamer/src/nonblocking/stream_throttle.rs` test module, timing-fuzz style:

```rust
#[tokio::test(start_paused = true)]
async fn test_fixed_window_boundary_burst_evasion() {
    let stats = Arc::new(StreamerStats::default());
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max_streams: u64 = 10;

    // Burst 1: consume full quota just before window ends.
    for _ in 0..max_streams {
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }
    // Confirm next call would throttle within same window.
    let start = counter.reset_throttling_params_if_needed();
    assert!(counter.stream_count.load(Ordering::Relaxed) >= max_streams);

    // Advance time just past STREAM_THROTTLING_INTERVAL to trigger reset.
    tokio::time::advance(STREAM_THROTTLING_INTERVAL + Duration::from_millis(1)).await;

    // Burst 2: immediately consume another full quota right after reset.
    throttle_stream(&stats, ConnectionPeerType::Unstaked, "127.0.0.1:0".parse().unwrap(), &counter, max_streams).await;
    for _ in 0..max_streams {
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }

    // Total streams admitted across the two bursts within a span
    // barely over STREAM_THROTTLING_INTERVAL is ~2x max_streams,
    // violating the intended per-interval cap invariant.
    let total_admitted = max_streams + counter.stream_count.load(Ordering::Relaxed);
    assert!(
        total_admitted <= max_streams,
        "expected per-interval cap {} but observed {} streams admitted across boundary straddle",
        max_streams, total_admitted
    );
}
```
Expected result: the assertion fails on current code (demonstrating ~2x admission), confirming the fixed-window boundary evasion; a corrected sliding-window/token-bucket implementation should make this assertion pass.

    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }
