### Title
Unprivileged dust deposits/transfers fill an account's token list to `MAX_TOKENS_PER_USER`, DoS-ing new deposits and fee-bearing mints - (File: contracts/Pool.sol)

### Summary
The Discourse report class is "unprivileged user submits a crafted payload that degrades service availability." The Metronome analog: `Pool` tracks per-account `depositTokensOfAccount`/`debtTokensOfAccount` lists and enforces a combined cap of `MAX_TOKENS_PER_USER = 30`. Because `DepositToken.deposit(amount_, onBehalfOf_)` and `DepositToken.transfer/transferFrom` add the token to the *recipient's* list (not the caller's), an attacker can cheaply fill a victim's — or the global `feeCollector`'s — list with dust balances, causing every subsequent `_mint`/`_transfer` of a new token type to that account to revert with `UserReachedMaxTokens()`. This is a liveness/availability failure driven purely by attacker-chosen arguments.

### Finding Description
`Pool.addToDepositTokensOfAccount` is guarded by `onlyIfAdditionWillNotReachMaxTokens`, which reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [1](#0-0) . The lists live in `PoolStorageV1` as `MappedEnumerableSet.AddressSet` per account [2](#0-1) .

Two public, unprivileged paths grow another account's list:

1. `DepositToken.deposit(amount_, onBehalfOf_)` accepts an arbitrary beneficiary and calls `_mint(onBehalfOf_, _deposited)` [3](#0-2) . `_mint` adds the token to `account_`'s list when its prior balance is zero [4](#0-3) .
2. `DepositToken.transfer/transferFrom` call `_transfer`, which likewise adds the token to the recipient's list on first receipt [5](#0-4) .

The most damaging target is the pool's `feeCollector()`: both `deposit` (`_mint(_pool.feeCollector(), _fee)` [6](#0-5) ) and `_withdraw` (`_transfer(account_, _pool.feeCollector(), _fee)` [7](#0-6) ) mint/transfer fee balances to it. If the attacker fills `feeCollector`'s list to 30, every deposit or withdrawal that produces `fee > 0` for a deposit token the collector doesn't already hold reverts — a protocol-wide DoS of that token's deposit/withdraw path. For an ordinary victim, the same trick blocks them from depositing a new collateral type or issuing a new synthetic (issue requires a collateral deposit/list insert).

### Impact Explanation
Invariant broken: liveness/availability. Attacker-forced list entries cause `UserReachedMaxTokens` reverts, temporarily freezing (a) a victim's ability to onboard new collateral/debt positions and (b) fee-bearing `deposit`/`withdraw` for any token the `feeCollector` doesn't already hold — griefing all users of those tokens. Funds are not stolen and the block is temporary (the victim/collector can transfer or withdraw a dust balance to free a slot), matching the accepted "temporary freezing of funds / reduced availability" impact.

### Likelihood Explanation
Fully unprivileged: only public `DepositToken.deposit`/`transfer` calls with dust amounts and attacker-chosen `onBehalfOf_`/recipient are needed — no governor, keeper, oracle, or LayerZero involvement. Cost is dust collateral across the pool's listed deposit tokens. Reachability caveat: filling 30 slots requires enough distinct listed `DepositToken`s (debt tokens can't be added to a third party's list without their collateral); where the pool lists fewer than 30 deposit tokens, the attack can still brick the feeCollector path for tokens the collector doesn't yet hold, but may not reach the cap for an arbitrary victim. `nonReentrant` and `whenNotPaused` do not prevent it; SynthContext/`getActualMsgSender` faithfully forwards the real sender but the beneficiary is attacker-chosen anyway.

### Recommendation
Do not let a sender dictate list membership of a third party. Options: (a) in `deposit`, revert unless `onBehalfOf_ == _msgSender()` or the beneficiary already holds the token; (b) exempt the `feeCollector` and `treasury` from `MAX_TOKENS_PER_USER` enforcement; (c) treat "recipient has zero balance of this token" transfers to accounts already at the cap by skipping list insertion only when the sender is the account itself — i.e., check the cap against the caller, not the recipient, for unsolicited inbound transfers.

### Proof of Concept
Reproducible Hardhat sketch (using the existing fixture in `test/Pool.test.ts` which already demonstrates `UserReachedMaxTokens` via `addToDepositTokensOfAccount`):

```ts
// given: pool with >= 30 listed deposit tokens, depositFee > 0,
// feeCollector has zero balance of msTokenX
const feeCollector = await poolRegistry.feeCollector()

// attacker dust-fills feeCollector's account list
for (const dt of depositTokens.slice(0, 30)) {
  await underlying.approve(dt.address, dust)
  await dt.deposit(dust, feeCollector) // adds dt to feeCollector's list
}

// any user deposit into a token feeCollector doesn't hold now reverts
await expect(
  msTokenX.deposit(amount, alice.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
// because _mint(feeCollector, fee) -> addToDepositTokensOfAccount(feeCollector) reverts

// same for an arbitrary victim: attacker blocks new collateral onboarding
await expect(victimDepositOfNewToken).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

The existing test at `test/Pool.test.ts:1386-1416` already proves the revert path once the cap is hit; the PoC demonstrates the unprivileged attacker (not a token contract, but a plain EOA via `deposit(..., onBehalfOf_)`/`transfer`) can force that state on someone else.
