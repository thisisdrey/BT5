Audit Report

## Title
Spot-traffic multiplier collapses to the floor price instead of decaying gradually, enabling underpriced on-demand coretime purchases - (File: `polkadot/runtime/parachains/src/on_demand/mod.rs`)

## Summary
`Pallet::calculate_spot_traffic` computes the on-demand coretime "traffic" multiplier used to derive the spot price for on-demand core purchases via `spot_price = new_traffic * on_demand_base_fee` in `update_spot_traffic`. In the negative branch (queue utilization below target), the implementation computes `queue_util_diff.saturating_sub(div_by_two).saturating_mul(traffic)` and returns that directly as the new traffic value, omitting the `1 -` term that the documented Taylor-approximation model requires, so the result is dominated by the (typically small) `diff` fraction rather than decaying gradually from `traffic`.

## Finding Description
In `calculate_spot_traffic` [1](#0-0) , the `positive` branch correctly implements `traffic * (1 + diff + div_by_two)` by adding `One::one()` before the multiplication. The `else` branch computes `queue_util_diff.saturating_sub(div_by_two).saturating_mul(traffic)` and returns it directly — this is mathematically `traffic * diff`, not the intended `traffic * (1 - diff + div_by_two)`. Since `diff` is generally a small Perbill-scale fraction of the queue capacity, multiplying it directly by `traffic` collapses the result to a small fraction of the prior multiplier on essentially any block where utilization dips slightly below target, after which the `.max(TrafficDefaultValue::get())` clamp typically snaps the value straight to the pallet floor. This structurally matches the intended-model deviation described in the claim: the delta term is conflated with the new value instead of being subtracted from the previous value, unlike the positive branch and unlike the analogous `pallet-transaction-payment` `TargetedFeeAdjustment::convert` decaying-branch pattern (`previous.saturating_sub(negative)`).

## Impact Explanation
`update_spot_traffic` [2](#0-1)  uses the returned `new_traffic` to directly compute `spot_price`, so this bug causes the on-demand coretime spot price to be mispriced (underpriced) whenever queue utilization is at or slightly below target, regardless of how elevated `traffic` had become from sustained prior demand. This is a public, unprivileged, underpriced-work condition affecting the Coretime marketplace / on-demand blockspace pricing mechanism, matching the "public underpriced work that degrades block production" impact category permitted by the gate.

## Likelihood Explanation
No privileged actor is required — queue utilization naturally fluctuates below target on most non-congested blocks, and any account interacting with the public on-demand order-placement extrinsic can trigger `update_spot_traffic`. The condition (`queue_util_ratio < target_queue_utilisation`, i.e., `positive == false`) is the common case rather than an edge case, making the mispricing readily and repeatedly triggerable under normal usage, not merely adversarial conditions.

## Recommendation
Fix the negative branch to mirror the correct decaying formula: compute `negative_term = queue_util_diff.saturating_sub(div_by_two).saturating_mul(traffic)`, then return `traffic.saturating_sub(negative_term).max(TrafficDefaultValue::get())`, so the multiplier decays proportionally from its previous value analogous to `pallet-transaction-payment`'s `TargetedFeeAdjustment::convert`.

## Proof of Concept
1. Set `TrafficDefaultValue = 1.0`, `on_demand_target_queue_utilization = 25%`, and let `traffic = 10.0` from sustained prior demand.
2. Have queue utilization drop to 24% for one block, so `positive = false` and `queue_util_diff ≈ 0.01` (with `div_by_two` negligible).
3. Current code (`calculate_spot_traffic`, lines 661-663 in `mod.rs`) returns `new_traffic = (0.01 - ~0) * 10.0 = 0.1`, clamped by `.max(1.0)` to `1.0`.
4. The mathematically intended formula `traffic * (1 - diff + div_by_two) ≈ 9.9` would leave traffic nearly unchanged.
5. As a result, `spot_price = new_traffic * on_demand_base_fee` collapses to the floor price (`1.0 * on_demand_base_fee`) instead of `~9.9 * on_demand_base_fee`, letting any caller purchase on-demand coretime near the minimum price after only a 1% dip in queue utilization — reproducible as a Rust unit test directly calling `Pallet::<T>::calculate_spot_traffic` with the parameters above and asserting the returned value against the two formulas.
