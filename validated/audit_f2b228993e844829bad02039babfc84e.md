### Title
Archive cache key collision via unescaped pathspec concatenation allows cross-request archive content confusion - ([File: internal/gitaly/service/repository/archive.go])

### Summary
`GetArchive`'s cache key generator, `createArchiveCacheKey`, builds a SHA256 digest by concatenating raw, attacker-influenced strings (`args` and `pathspecs`, which are derived directly from user-supplied `Path`/`Exclude`/`ElidePath` fields) without any length-prefixing or unambiguous delimiter. This mirrors the report's root cause — two logically distinct inputs are hashed into an identical key because the encoding scheme used to combine sub-fields is not injective. [1](#0-0) 

### Finding Description
`GetArchive` builds `args` and `pathspecs` from the caller-controlled `Path`, `Exclude`, and `ElidePath` request fields: [2](#0-1) 

These are then combined into a cache key using naive `strings.Join(..., ",")` calls concatenated together, with no length prefix or unambiguous separator between the `args` segment and the `pathspecs` segment, and no escaping of the `,` and `:` characters that are themselves used as pathspec/exclude/elide separators: [3](#0-2) [4](#0-3) 

This is exactly the ambiguous-concatenation flaw the codebase itself explicitly documents and defends against elsewhere: the disk-cache key builder `compositeKeyHashHex` calls `prefixLen` on every component specifically "to reduce the risk of collisions due to different combinations of concatenated strings producing the same content" (e.g. `f+oobar` vs `foo+bar`): [5](#0-4) 

`createArchiveCacheKey` was not built with this same protection. Because `ElidePath` toggles whether the path is folded into `args[0]` (as `commitID:path`) versus appended as a separate `pathspecs` entry, and because `Path`/`Exclude` are user-controlled strings that can contain `,` and `:` characters (subject only to `storage.ValidateRelativePath`, which does not forbid these characters), a crafted `GetArchiveRequest` combination (different `CommitId`/`Path`/`Exclude`/`ElidePath`) can be engineered to produce identical byte concatenations before hashing, i.e., identical `cacheKey`.

The `cacheKey` is used to fetch/store the archive contents in `s.archiveCache`, a shared cache not further scoped per-repository beyond the digest itself (`GlProjectPath` is only the first hashed field, and it is also unlength-prefixed, so it too participates in the same ambiguity): [6](#0-5) 

### Impact Explanation
If a colliding key is produced, one caller's `GetArchive` request can be served the cached tar/zip stream generated for a different, unrelated request — potentially from a different commit, a different sub-`path`, or a different `exclude` set, and (depending on how the `GlProjectPath` string participates in the ambiguity) potentially cross-repository. Because `Path`/`Exclude` are frequently used by callers to scope an archive download to a specific subdirectory (excluding sensitive paths), a collision can cause disclosure of content that the specific request intended to exclude, or cause a requester to receive an archive belonging to a different commit/repository context than requested. This is a concrete cross-request object/content confusion in an RPC that any authenticated repository user can invoke by crafting the `Path`/`Exclude`/`ElidePath` fields of `GetArchive`.

### Likelihood Explanation
Reaching this code path requires only calling the `GetArchive` RPC — accessible to any client with read access to a repository — with attacker-chosen `Path`, `Exclude`, and `ElidePath` fields, which are only checked for path traversal/existence via `storage.ValidateRelativePath` and `validateGetArchivePrecondition`/`findGetArchivePath`, not for exclusion of the delimiter characters (`,`, `:`) used in `createArchiveCacheKey`. Constructing a specific concrete two-request collision requires careful string engineering (finding a `(CommitId, Path, Exclude, ElidePath)` pair that reproduces another request's raw byte concatenation) but is deterministic once found, since it is a preimage/format-string ambiguity, not a cryptographic hash collision. The overall likelihood is best characterized as moderate: no cryptographic break is needed, but the message-format collision must be deliberately engineered by the attacker for a specific target request.

### Recommendation
Rework `createArchiveCacheKey` to hash length-prefixed or otherwise unambiguously delimited fields, exactly like `compositeKeyHashHex`/`prefixLen` in `internal/cache/keyer.go`, ensuring `gitLabProjectPath`, each `args` element, and each `pathspecs` element (including the `ElidePath` boolean state) are encoded so that no two distinct `(args, pathspecs, elidePath)` tuples can serialize to the same byte stream before hashing.

### Proof of Concept
Root-cause code path (not independently executed, but concretely supported by file/line references above):
1. Two `GetArchiveRequest`s differ in `ElidePath` and how `Path` is placed (`commitID:path` folded into `args[0]` vs. `path` appended as a separate `pathspecs` element) — see `handleArchive` branch logic at `internal/gitaly/service/repository/archive.go:198-212`.
2. `createArchiveCacheKey` (`internal/gitaly/service/repository/archive.go:290-296`) joins `args` and `pathspecs` with `,` and writes them to the hash back-to-back with no boundary marker between the `args` segment and the `pathspecs` segment.
3. By choosing `CommitId`/`Path`/`Exclude` values containing `,`/`:` characters (permitted by `storage.ValidateRelativePath`), an attacker can construct a second request whose `args`+`pathspecs` raw concatenation is byte-identical to a first, unrelated request's concatenation, yielding the same SHA256 `cacheKey` despite the two requests targeting different content, causing `s.archiveCache.Fetch` to return the wrong cached archive to the second caller.

// createArchiveCacheKey creates a cache key using the GitLab project's path, the `git archive`
// command arguments and the pathspecs. The goal is to create a key that is unique not only
// across repository, but also across the content of each archive within the same repository.
func createArchiveCacheKey(gitLabProjectPath string, args []string, pathspecs []string) string {
	cacheKeyHash := sha256.New()
	cacheKeyHash.Write([]byte(gitLabProjectPath))
	cacheKeyHash.Write([]byte(strings.Join(args, ",")))
	cacheKeyHash.Write([]byte(strings.Join(pathspecs, ",")))
	return hex.EncodeToString(cacheKeyHash.Sum(nil))
}

// compositeKeyHashHex returns a hex encoded string that is a SHA256 hash sum of
// the composite key made up of the following properties: Gitaly version, gRPC
// method, repo cache current generation ID, protobuf request, and enabled
// feature flags.
func compositeKeyHashHex(ctx context.Context, genID string, req proto.Message) (string, error) {
	method, ok := grpc.Method(ctx)
	if !ok {
		return "", ErrCtxMethodMissing
	}

	reqSum, err := proto.Marshal(req)
	if err != nil {
		return "", err
	}

	h := sha256.New()

	var flagsWithValue []string
	for flag, enabled := range featureflag.FromContext(ctx) {
		flagsWithValue = append(flagsWithValue, flag.FormatWithValue(enabled))
	}
	sort.Strings(flagsWithValue)

	for _, i := range []string{
		version.GetVersion(),
		method,
		genID,
		string(reqSum),
		strings.Join(flagsWithValue, " "),
	} {
		_, err := h.Write(prefixLen(i))
		if err != nil {
			return "", err
		}
	}

	return hex.EncodeToString(h.Sum(nil)), nil
}

// prefixLen reduces the risk of collisions due to different combinations of
// concatenated strings producing the same content.
// e.g. f+oobar and foo+bar concatenate to the same thing: foobar
func prefixLen(s string) []byte {
	return []byte(fmt.Sprintf("%08x%s", len(s), s))
}
