Audit Report

## Title
Relayer reward paid out regardless of Ethereum delivery outcome, ignoring `DeliveryReceipt.success` - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`Pallet::process_delivery_receipt`, invoked from the public `submit_delivery_receipt` extrinsic, decodes a `DeliveryReceipt` containing a `success: bool` field reflecting whether the relayed message dispatch actually succeeded on Ethereum, but never reads or checks this field before paying out the relayer reward and clearing the `PendingOrder`. This decouples bridge reward payout from actual message delivery outcome, allowing any relayer to collect the full fee for a message whose Ethereum-side dispatch failed.

## Finding Description
`DeliveryReceipt` is decoded from the real `InboundMessageDispatched(nonce, topic, success, reward_address)` Ethereum event log emitted by the Gateway contract, explicitly carrying a `success` field describing whether the relayed message actually executed successfully on Ethereum. [1](#0-0) 

The public, unprivileged extrinsic `submit_delivery_receipt` verifies the proof and decodes the log into a `DeliveryReceipt`, then hands off to `process_delivery_receipt`: [2](#0-1) 

`process_delivery_receipt` only validates the gateway address and looks up the `PendingOrder` by nonce, then unconditionally registers the reward whenever `order.fee > 0` and removes the order — `receipt.success` is never referenced: [3](#0-2) 

A repository-wide search confirms `receipt.success`/`DeliveryReceipt.success` is set exactly once (at decode time in `delivery_receipt.rs`) and read nowhere else in the codebase — no downstream logic, including the `RewardLedger::register_reward` implementation, ever consults it. The pallet also defines no `DeliveryFailed`-style error variant, confirming the outcome was never intended to be branched on in the current implementation. The only existing guards (`GatewayAddress` match, `PendingOrders` lookup by nonce) bind gateway identity and nonce validity, not delivery outcome, so they do not mitigate this gap.

## Impact Explanation
This is reachable via the public, unprivileged `submit_delivery_receipt` extrinsic and results in bridge reward payout (`T::RewardPayment::register_reward`) and settlement-state advancement (`PendingOrders::remove`) that is not conditioned on the underlying Ethereum-side execution actually succeeding. This falls under "duplicate settlement or payout" / "public underpriced work that ... stalls bridge processing" impact categories, since the fee economics are fully decoupled from real message delivery success, and it violates the pivot requirement that bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically.

## Likelihood Explanation
The triggering condition — a real Ethereum event with `success:false` — occurs naturally whenever a dispatched `Command` reverts on the Ethereum side (e.g., insufficient gas, contract-side revert), which is a normal occurrence rather than an attacker-crafted artifact. Any signed, unprivileged relayer who possesses a valid Merkle/receipt proof for such an event can submit it via `submit_delivery_receipt` and receive the full reward, requiring no malicious peer, admin, governance, or validator collusion, and is fully repeatable for every failed dispatch.

## Recommendation
Add an explicit check such as `ensure!(receipt.success, Error::<T>::DeliveryFailed)` in `process_delivery_receipt` before registering the reward (or define distinct handling, e.g. no reward or a reduced reward, for failed deliveries), so the `success` flag actually gates settlement rather than being silently discarded after decode.

## Proof of Concept
1. A message is committed via `do_process_message`, creating `PendingOrder { nonce, fee, .. }` in storage. [4](#0-3) 
2. The message is delivered to the real Gateway contract on Ethereum, but the dispatched command reverts (e.g. insufficient gas at destination), causing the Gateway to emit `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. Any relayer calls `submit_delivery_receipt` with a valid proof of this real event; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success=false` correctly.
4. `process_delivery_receipt` passes the `GatewayAddress` check and the `PendingOrders` lookup, then — since `receipt.success` is never inspected — calls `T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee)` and removes the `PendingOrder`, paying the full fee despite the failed delivery. 			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward

					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });
