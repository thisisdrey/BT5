### Title
Denial of Service via unbounded growth of `TransactionManager.committedEntries`, fully re-walked under a global partition mutex on every commit - ([File: internal/gitaly/storage/storagemgr/partition/transaction_manager.go])

### Summary
An object pool's partition maintains a single, shared, append-only in-memory list (`committedEntries`) of every committed transaction for **all repositories in that partition** (the pool plus all its fork/member repositories). Any ordinary user with push access to just one member repository can force this list to grow unbounded by combining (a) a burst of cheap write transactions and (b) a long-lived read snapshot that blocks eviction. Every subsequent commit anywhere in the partition — including commits made by completely unrelated users to other forks of the same pool — must then fully walk this list under the manager's single mutex, degrading or blocking transaction processing for the whole partition. This mirrors the `createOrder`/`pendingOrderIds` pattern in the reference report: cheap, attacker-controlled entries appended to a shared array that every subsequent operation must fully scan.

### Finding Description
Gitaly places an object pool and all repositories connected to it (including forks) in the **same partition**, sharing one `TransactionManager` instance and one write-ahead log [1](#0-0) .

`TransactionManager` tracks committed log entries in an in-memory linked list `committedEntries`, incremented on every commit via `updateCommittedEntry` and only pruned from the front once there are no more transactions reading at an older snapshot: [2](#0-1) [3](#0-2) 

Every commit calls `walkCommittedEntries`, which iterates the **entire** `committedEntries` list (filtering by `relativePath`, but only after visiting every node) while holding `mgr.mutex` — the same mutex that serializes all transaction commit/Begin processing for the whole partition: [4](#0-3) 

This walk is invoked on essentially every commit path, both for key-value conflict checks and for housekeeping conflict checks: [5](#0-4) [6](#0-5) 

An unprivileged user who can push to only one repository connected to a pool can:
1. Start (or keep open) a read transaction at an old snapshot LSN (e.g., any slow/streaming RPC, or repeatedly opening reads faster than they close), which increments `snapshotReaders` on the oldest `committedEntry` and prevents `cleanCommittedEntry` from ever pruning the front of the list.
2. Concurrently flood the same repository with a large number of trivial, cheap write transactions (analogous to "0 amount" orders — e.g., minimal single-byte ref/commit changes), each of which calls `updateCommittedEntry`/`appendLogEntry` and appends a new, unprunable node to `committedEntries`.

Because the list is never bounded by size or age — only by reader liveness — it grows without limit as long as condition (1) holds, and every other transaction touching **any** repository in the pool (including other users' unrelated forks) pays an ever-increasing `O(n)` cost in `walkCommittedEntries` while holding the partition-wide mutex.

### Impact Explanation
This is a Denial-of-Service of a partition-scoped RPC handler resource limit: an ordinary user with write access to a single fork inside an object pool can degrade or stall commit throughput for every other repository sharing that pool's partition, because the conflict-check walk and the mutex it runs under are shared, unbounded, and not repository-scoped in cost.

### Likelihood Explanation
Moderate to high. It only requires standard push/fetch access to one repository that is (or will become) part of an object-pool partition (a routine setup for GitLab forks), plus the ability to issue a burst of cheap writes and hold open a slow/streaming read — both ordinary client capabilities, no privileged actor or malicious peer needed.

### Recommendation
- Bound `committedEntries` independent of reader liveness (e.g., cap total entries/age and abort/evict overly long-lived snapshot readers, similar to the `max_queue_size`/`max_queue_wait` mechanism already used for RPC concurrency limiting [7](#0-6) ).
- Index committed entries by `relativePath` so `walkCommittedEntries` only scans entries relevant to the transaction's target repository instead of every entry in the partition.
- Avoid performing the full walk while holding the manager-wide `mgr.mutex`, or at minimum make the walk cost independent of unrelated repositories' commit volume.

### Proof of Concept
1. Set up an object pool with two independent forks, `fork-A` (attacker-controlled) and `fork-B` (victim), both assigned to the same partition per the pool/fork partitioning rule [1](#0-0) .
2. Attacker opens a long-lived/slow read RPC against `fork-A` that begins a transaction and holds its snapshot open (e.g., a slow streaming RPC), pinning `snapshotReaders` on the current head of `committedEntries`.
3. Attacker concurrently issues a rapid burst of trivial write RPCs against `fork-A` (minimal ref/content changes), each committing via `TransactionManager` and appending an entry to `committedEntries` via `updateCommittedEntry` [2](#0-1) .
4. Because the reader from step 2 keeps `snapshotReaders > 0` on the oldest entry, `cleanCommittedEntry` cannot prune any node from the front of the list [3](#0-2) , so `committedEntries` grows unbounded with the attacker's write volume.
5. A victim user pushing to `fork-B` (same partition) triggers a commit that calls `verifyHousekeeping`/`verifyKeyValueOperations`, both of which invoke `walkCommittedEntries`, now iterating the attacker-inflated list under the shared `mgr.mutex` [4](#0-3) , causing increasing latency/timeouts for the victim's unrelated push.

```go
// them in the log entry. The conflict checking ensures serializability. Transaction is considered to
// conflict if it read a key a concurrently committed transaction set or deleted. Iterated key prefixes
// are predicate locked.
func (mgr *TransactionManager) verifyKeyValueOperations(ctx context.Context, tx *Transaction) error {
	defer trace.StartRegion(ctx, "verifyKeyValueOperations").End()

	if readSet := tx.recordingReadWriter.ReadSet(); len(readSet) > 0 {
		if err := mgr.walkCommittedEntries(tx, func(entry *gitalypb.LogEntry, _ map[git.ObjectID]struct{}) error {
			for _, op := range entry.GetOperations() {
				var key []byte
				switch op := op.GetOperation().(type) {
				case *gitalypb.LogEntry_Operation_SetKey_:
					key = op.SetKey.GetKey()
				case *gitalypb.LogEntry_Operation_DeleteKey_:
					key = op.DeleteKey.GetKey()
				}

				stringKey := string(key)
				if _, ok := readSet[stringKey]; ok {
					return newConflictingKeyValueOperationError(stringKey)
				}

				for prefix := range tx.recordingReadWriter.PrefixesRead() {
					if bytes.HasPrefix(key, []byte(prefix)) {
						return newConflictingKeyValueOperationError(stringKey)
					}
				}
			}

			return nil
		}); err != nil {
			return fmt.Errorf("walking committed entries: %w", err)
		}
	}

	return nil
}
```

```go
// updateCommittedEntry updates the reader counter of the committed entry of the snapshot that this transaction depends on.
func (mgr *TransactionManager) updateCommittedEntry(snapshotLSN storage.LSN) *committedEntry {
	// Since the goroutine doing this is holding the lock, the snapshotLSN shouldn't change and no new transactions
	// can be committed or added. That should guarantee .Back() is always the latest transaction and the one we're
	// using to base our snapshot on.
	if elm := mgr.committedEntries.Back(); elm != nil {
		entry := elm.Value.(*committedEntry)
		entry.snapshotReaders++
		return entry
	}

	entry := &committedEntry{
		lsn:             snapshotLSN,
		snapshotReaders: 1,
	}

	mgr.committedEntries.PushBack(entry)

	return entry
}
```

```go
// walkCommittedEntries walks all committed entries after input transaction's snapshot LSN. It loads the content of the
// entry from disk and triggers the callback with entry content.
func (mgr *TransactionManager) walkCommittedEntries(transaction *Transaction, callback func(*gitalypb.LogEntry, map[git.ObjectID]struct{}) error) error {
	mgr.mutex.Lock()
	defer mgr.mutex.Unlock()

	for elm := mgr.committedEntries.Front(); elm != nil; elm = elm.Next() {
		committed := elm.Value.(*committedEntry)
		if committed.lsn <= transaction.snapshotLSN {
			continue
		}

		if committed.entry == nil {
			return errCommittedEntryGone
		}
		// Transaction manager works on the partition level, including a repository and all of its pool
		// member repositories (if any). We need to filter log entries of the repository this
		// transaction targets.
		if committed.entry.GetRelativePath() != transaction.relativePath {
			continue
		}
		if err := callback(committed.entry, committed.objectDependencies); err != nil {
			return fmt.Errorf("callback: %w", err)
		}
	}
	return nil
}
```

```go
// cleanCommittedEntry reduces the snapshot readers counter of the committed entry. It also removes entries with no more
// readers at the head of the list.
func (mgr *TransactionManager) cleanCommittedEntry(entry *committedEntry) bool {
	entry.snapshotReaders--

	removedAnyEntry := false
	elm := mgr.committedEntries.Front()
	for elm != nil {
		front := elm.Value.(*committedEntry)
		if front.snapshotReaders > 0 {
			// If the first entry had still some snapshot readers, that means
			// our transaction was not the oldest reader. We can't remove any entries
			// as they'll still be needed for conflict checking the older transactions.
			return removedAnyEntry
		}

		mgr.committedEntries.Remove(elm)

		// It's safe to drop the transaction from the conflict detection history as there are no transactions
		// reading at an older snapshot. Since the changes are already in the transaction's snapshot, it would
		// already base its changes on them.
		mgr.conflictMgr.EvictLSN(mgr.ctx, front.lsn)
		mgr.fsHistory.EvictLSN(front.lsn)

		removedAnyEntry = true
		elm = mgr.committedEntries.Front()
	}
	return removedAnyEntry
}
```

```go
func (mgr *TransactionManager) verifyHousekeeping(ctx context.Context, transaction *Transaction, refBackend git.ReferenceBackend, zeroOID git.ObjectID) (*gitalypb.LogEntry_Housekeeping, error) {
	defer trace.StartRegion(ctx, "verifyHousekeeping").End()

	span, ctx := tracing.StartSpanIfHasParent(ctx, "transaction.verifyHousekeeping", nil)
	defer span.End()

	finishTimer := mgr.metrics.housekeeping.ReportTaskLatency("total", "verify")
	defer finishTimer()

	// Check for any concurrent housekeeping between this transaction's snapshot LSN and the latest appended LSN.
	if err := mgr.walkCommittedEntries(transaction, func(entry *gitalypb.LogEntry, objectDependencies map[git.ObjectID]struct{}) error {
		if entry.GetHousekeeping() != nil {
			return errHousekeepingConflictConcurrent
		}
		if entry.GetRepositoryDeletion() != nil {
			return errConflictRepositoryDeletion
		}

		// Applying a repacking operation prunes all loose objects on application. If loose objects were concurrently introduced
		// in the repository with the repacking operation, this could lead to corruption if we prune a loose object that is needed.
		// Transactions in general only introduce packs, not loose objects. The only exception to this currently is alternate
		// unlinking operations where the objects of the alternate are hard linked into the member repository. This can technically
		// still introduce loose objects into the repository and trigger this problem as the pools could still have loose objects
		// in them until the first repack.
		//
		// Check if the repository was unlinked from an alternate concurrently.
		for _, op := range entry.GetOperations() {
			switch op := op.GetOperation().(type) {
			case *gitalypb.LogEntry_Operation_RemoveDirectoryEntry_:
				if string(op.RemoveDirectoryEntry.GetPath()) == stats.AlternatesFilePath(transaction.relativePath) {
					return errConcurrentAlternateUnlink
				}
			}
		}

		return nil
	}); err != nil {
		return nil, fmt.Errorf("walking committed entries: %w", err)
	}
```

```markdown
An in-memory queue of requests can build up in Gitaly that are waiting their turn. Because
this is a potential vector for a memory leak, two other values in the `[[concurrency]]`
configuration can prevent an unbounded in-memory queue of requests:

- `max_queue_wait` is the maximum amount of time a request can wait in the
  concurrency queue. When a request waits longer than this time, it returns
  an error to the client.
- `max_queue_size` is the maximum size the concurrency queue can grow for a
  given RPC. If a concurrency queue is at its maximum, subsequent requests
  return with an error. The queue size is per repository.
```
