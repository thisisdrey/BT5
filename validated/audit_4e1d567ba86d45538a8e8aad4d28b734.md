### Title
Access key deletion + re-addition resets `access_key.nonce` below previously-consumed nonces, enabling replay of already-executed transactions - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`add_regular_key` seeds a newly (re-)added access key's nonce purely from the current block height via `initial_nonce_value(block_height)`, with no awareness of the nonce that the same public key previously reached before being deleted. If an account performs `DeleteKey(K)` followed by `AddKey(K)` for the same public key within the same block height, the freshly stored nonce `(H-1)*1_000_000` can be far lower than the nonce `V` already consumed by prior transactions signed with `K`. Any previously signed-and-broadcast (or archived) `SignedTransaction` with a nonce in `(initial_nonce_value(H), V]` will then pass the nonce freshness check again, allowing it to be re-applied.

### Finding Description
`action_delete_key` fully removes the access key entry from the trie via `remove_access_key` (called from `delete_regular_key`) with no record kept of the nonce it last held: [1](#0-0) 

`action_add_key` → `add_regular_key` then creates a brand-new `AccessKey` entry and unconditionally sets its nonce using only the current block height, independent of what nonce the same public key previously reached: [2](#0-1) 

The seeding function itself is purely a function of `block_height`: [3](#0-2) 

Both `action_delete_key` and `action_add_key` are invoked with the same `apply_state.block_height` when processing sequential actions inside one receipt/transaction, so a signer can put `DeleteKey(K)` and `AddKey(K, ...)` into the same transaction (or two chained receipts confirmed at the same height H): [4](#0-3) 

The design assumption behind `initial_nonce_value` (referencing near/nearcore#3779) is that block height only increases, so height-derived nonce ranges for *newly created* keys will always exceed nonces used so far. That assumption is only valid if all nonces ever used by a key are bounded by the height-derived range. In practice, regular (non-meta) `SignedTransaction` nonces are **not** bounded to any block-height-derived ceiling — a user can freely choose an arbitrarily large nonce value (up to `u64::MAX`) when signing a transaction with a full-access key, since regular nonce validation only requires the new nonce to be strictly greater than the currently stored nonce. Once such a large nonce `V` (e.g., `V >> (H-1)*1_000_000` for any realistic `H`) has been consumed, deleting and re-adding the same public key at height `H` resets the stored nonce back down to `(H-1)*1_000_000 < V`. Any old, previously-valid, already-broadcast `SignedTransaction` signed by `K` with nonce in `((H-1)*1_000_000, V]` will again satisfy the "nonce greater than stored nonce" freshness check and be accepted for execution a second time, even though it was already executed once and should be permanently invalidated.

### Impact Explanation
This breaks the nonce-based replay-prevention invariant for access keys: a transaction that has already been executed once (e.g., a `Transfer`, a withdrawal call, a one-time authorization to a counterparty/service, or a batch of pre-signed transactions held by a third party) can be re-submitted and re-applied after the signer performs a routine-looking `DeleteKey`+`AddKey` sequence on that same key at a given block height. Concrete impact: double-spend/replay of value-moving or state-changing actions authorized under the affected key — matching the "double-spend/replay" bounty category. The impact is scoped to the affected account/key and whoever relies on the one-time nature of a previously signed transaction associated with that key (e.g., a payee that already banked a transfer being paid again by the same replayed tx, or a contract that already processed a one-time call being tricked into processing it twice).

### Likelihood Explanation
- No privileged access is required: any account owner can submit `DeleteKey`+`AddKey` for the same public key using a full-access key they already control, at zero special cost beyond gas.
- The precondition (an old nonce `V` far exceeding the height-derived floor for some future height `H`) is easy to satisfy because ordinary transaction nonces are unbounded relative to block height; a user can simply choose a very large nonce when originally signing a transaction.
- The action sequence is deterministic and fully reproducible: apply `DeleteKey(K)` then `AddKey(K)` in the same block, then replay any old transaction with nonce in the gap.
- Repeatable for any account/key pair meeting the precondition.

### Recommendation
When adding an access key with the same public key that previously existed on the account (or more generally, when seeding any new key's nonce), ensure the new nonce is never lower than the highest nonce ever used by that exact public key on that account. Options:
- Track a per-account/public-key "last used nonce" watermark that persists across delete/re-add cycles (not just while the access key entry exists), and seed new keys as `max(initial_nonce_value(block_height), last_known_nonce + 1)`.
- Alternatively, forbid immediate re-use of a deleted public key for `AddKey` within the same account without an explicit height-independent nonce floor, or store a tombstone nonce marker when a key is deleted.

### Proof of Concept
Unit test in `runtime/runtime/src/access_keys.rs` (or `runtime/runtime/src/tests/apply.rs`):
1. At block height `H0`, call `action_add_key` for public key `K`, confirm stored nonce is `initial_nonce_value(H0)`.
2. Simulate consumption of a large nonce `V` (e.g. `V = 10 * initial_nonce_value(H0 + 1000)`), directly via `set_access_key` (or via `verify_and_charge_tx_ephemeral` with a `SignedTransaction` using nonce `V`), confirming the transaction succeeds and the access key nonce becomes `V`.
3. At a block height `H` such that `initial_nonce_value(H) < V` (any `H` not astronomically large satisfies this), apply `action_delete_key` for `K` then `action_add_key` for `K` again with the same public key.
4. Assert `get_access_key(...).nonce == initial_nonce_value(H)` and that `initial_nonce_value(H) < V`.
5. Construct/reuse a `SignedTransaction` signed by `K` with nonce `N` where `initial_nonce_value(H) < N <= V` (e.g., the same nonce `V` used in step 2, or any value in that range) and feed it into `verify_and_charge_tx_ephemeral`; assert it is wrongly accepted (returns `Ok`) instead of `InvalidTxError::InvalidNonce`, demonstrating replay of an already-consumed nonce range.

```rust
pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}
```

```rust
pub(crate) fn action_add_key(
    apply_state: &ApplyState,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    add_key: &AddKeyAction,
) -> Result<(), StorageError> {
    if get_access_key(state_update, account_id, &add_key.public_key)?.is_some() {
        result.result = Err(ActionErrorKind::AddKeyAlreadyExists {
            account_id: account_id.to_owned(),
            public_key: add_key.public_key.clone().into(),
        }
        .into());
        return Ok(());
    }

    let fee_config = &apply_state.config.fees;

    if let Some(gas_key_info) = add_key.access_key.gas_key_info() {
        add_gas_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            gas_key_info,
            apply_state.block_height,
        )?;
    } else {
        add_regular_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            apply_state.block_height,
        )?;
    }

    Ok(())
}
```

```rust
fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
```
