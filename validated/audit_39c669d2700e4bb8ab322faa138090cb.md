### Title
Missing upper bound on client-supplied `FetchRemoteRequest.timeout` allows indefinite resource hold during `FetchRemote` - (File: internal/gitaly/service/repository/fetch_remote.go)

### Summary
The `FetchRemote` RPC lets a caller supply a `Timeout` value (seconds) that gates how long the underlying `git fetch` and reference-update work may run. This value is fully attacker/caller-controlled and is never validated against any maximum (or minimum), so a caller can set it to zero or to an extremely large value, letting the operation - and the quarantine directory, locks, and subprocess it holds open - run effectively unbounded, mirroring the "no upper limit on a duration parameter that gates release of a locked resource" root cause from the reference report.

### Finding Description
`FetchRemote` reads the caller-supplied `Timeout` field and, only if it is greater than zero, derives a bounded context from it: [1](#0-0) 

There is no upper bound (nor sanity check) placed on `req.GetTimeout()`. `validateFetchRemoteRequest` only checks that the repository is valid and that remote params/URL are present — it never inspects `Timeout` at all: [2](#0-1) 

As a result, a caller can either:
- Omit `Timeout` (defaults to `0`), which skips the `context.WithTimeout` branch entirely and lets the fetch run bound only by whatever (possibly very long or absent) deadline the parent gRPC context carries, or
- Supply an arbitrarily large `int32` value (up to ~2^31-1 seconds, i.e. decades) which is accepted uncritically and converted into a `context.WithTimeout` deadline that is functionally unbounded.

While the timeout context is in effect, `fetchRemoteAtomic` creates an on-disk quarantine directory, spawns `git fetch`, and opens two `updateref.Updater` reference-transaction sessions against the repository, all of which stay open for the duration of the call: [3](#0-2) [4](#0-3) 

This is directly analogous to the reported bug class: a duration/window value that gates how long a resource (there: buyer funds; here: quarantine directory, git subprocess, in-flight reference-transaction handles) stays locked/held is accepted from the caller without any upper-bound validation.

### Impact Explanation
An unbounded or excessively long `Timeout` combined with a slow/stalled/malicious remote (the `RemoteParams.Url` is also caller-supplied) allows a single `FetchRemote` invocation to hold a quarantine directory and reference-transaction state open for a very long time, tying up a Gitaly worker slot, git subprocess, and repository-scoped resources. Repeated or concurrent such calls can exhaust worker/concurrency limits and degrade or deny service for other RPCs against the same repository, since reference updates and quarantine merges are serialized per repository.

### Likelihood Explanation
`FetchRemote` is a standard mutator RPC that GitLab uses for pull mirroring and similar workflows; the `Timeout` and `RemoteParams` fields are populated by the calling application layer, not restricted by Gitaly itself. Any caller with access to invoke `FetchRemote` (an ordinary authenticated RPC caller, not a privileged admin) can set this field to an extreme value or omit it, making the condition trivially reachable without any special privilege.

### Recommendation
Enforce a sane maximum (and possibly a minimum) on `req.GetTimeout()` inside `validateFetchRemoteRequest`, rejecting or clamping values outside an acceptable range (e.g., a fixed maximum such as Git's typical fetch timeout ceiling), and apply a server-side default/maximum context deadline even when the caller supplies `Timeout == 0`, so that quarantine directories and reference-transaction resources cannot be held indefinitely by a single RPC.

### Proof of Concept
1. Call `FetchRemote` with `RemoteParams.Url` pointing to a remote that accepts the connection but stalls the fetch (e.g., a slow-loris style Git server), and either:
   - omit `Timeout` (leaving it at `0`), or
   - set `Timeout` to a very large value (e.g., `2147483647`).
2. Observe that `FetchRemote` does not apply any effective bound: the quarantine directory under the repository's storage remains open, and the `git fetch` subprocess plus the two `updateref.Updater` sessions stay alive for the entire stall duration.
3. Issue multiple such requests concurrently against the same or different repositories to observe accumulation of long-lived quarantine directories and held subprocess/reference-transaction resources, degrading throughput for legitimate `FetchRemote`/mutator RPCs on the affected repositories.

func (s *server) FetchRemote(ctx context.Context, req *gitalypb.FetchRemoteRequest) (*gitalypb.FetchRemoteResponse, error) {
	if err := s.validateFetchRemoteRequest(ctx, req); err != nil {
		return nil, err
	}

	if req.GetTimeout() > 0 {
		var cancel context.CancelFunc
		ctx, cancel = context.WithTimeout(ctx, time.Duration(req.GetTimeout())*time.Second)
		defer cancel()
	}

func (s *server) validateFetchRemoteRequest(ctx context.Context, req *gitalypb.FetchRemoteRequest) error {
	if err := s.locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}

	if req.GetRemoteParams() == nil {
		return structerr.NewInvalidArgument("missing remote params")
	}

	if req.GetRemoteParams().GetUrl() == "" {
		return structerr.NewInvalidArgument("blank or empty remote URL")
	}

	return nil
}
