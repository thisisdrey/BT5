Confirmed: `DeleteKey` requires `actor_id == account_id` [1](#0-0) , and `check_account_existence` for `DeleteKey` only requires the account to currently exist (`account.is_some()`), with no check that it's the "same" account instance that existed when the receipt was created [2](#0-1) . `remove_account` (invoked by `action_delete_account`) only removes `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie entries for the account — it does **not** touch `PostponedReceipt`, `PostponedReceiptId`, or `PendingDataCount` entries keyed by that `receiver_id` [3](#0-2) . These postponed-receipt bookkeeping keys are purely `(receiver_id, receipt_id/data_id)`-keyed and outlive account deletion/recreation [4](#0-3) .

When the awaited `DataReceipt` eventually arrives, `process_receipt` looks up the postponed receipt purely by `receiver_id`/`data_id` and re-executes it via `apply_action_receipt`, unconditionally, against whatever account currently occupies that `account_id` [5](#0-4) . There is no "generation"/epoch check binding the postponed receipt to the account incarnation that existed at postponement time.

### Title
Stale postponed DeleteKeyAction survives DeleteAccount and can strip the recreated account's new FullAccess key - (File: runtime/runtime/src/lib.rs, core/store/src/utils/mod.rs)

### Summary
A self-targeted `DeleteKey` action receipt can be postponed (awaiting an `input_data_id`) on account X; the same owner (only entity with `actor_id == account_id` permission to issue this) then deletes X. `remove_account` clears the account/keys/contract but never clears the account's `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` trie entries, so the stale receipt survives. If X is later recreated (e.g. a NEAR-implicit/deterministic account whose access key is derived from the account id, or any subaccount re-created and given the same pubkey) and the withheld `DataReceipt` is finally delivered, the runtime blindly re-executes the postponed `DeleteKey(pubkey)` against the new account, deleting the new owner's key.

### Finding Description
`DeleteKey`/`DeleteAccount` actor-permission checks only allow the account itself (`actor_id == account_id`) to issue these actions [6](#0-5) . An account X (attacker-controlled while owned) can, via a self-call `FunctionCall` (so `predecessor_id == account_id == actor_id`), emit an outgoing `ActionReceipt{receiver_id: X, input_data_ids: [D], actions: [DeleteKey(pk)]}` targeting a `pk` it expects the eventual re-owner of X to use. Because `D` hasn't arrived, `process_action_receipt` stores it as a `PostponedReceipt` plus a `PostponedReceiptId{X, D} -> receipt_id` and `PendingDataCount{X, receipt_id} = 1` [7](#0-6) .

X then executes `DeleteAccount`. `action_delete_account` calls `remove_account`, which deletes `Account`, `ContractCode`, all `AccessKey`/gas-key entries, and `ContractData`, but leaves the `PostponedReceipt`, `PostponedReceiptId`, and `PendingDataCount` trie records intact [8](#0-7) [3](#0-2) .

Someone (the "new owner") later creates account X again (via `CreateAccount`, implicit-account `Transfer`, or `DeterministicStateInit`) and adds an access key with public key `pk` — this passes `check_account_existence`'s `CreateAccount`/`AddKey` checks unconditionally, since nothing references the old, stale postponed receipt. Finally, the withheld `D` `DataReceipt` (which the attacker/predecessor fully controls the timing of, since it originates from the attacker's own prior self-call chain) is delivered. `process_receipt`'s `Data` branch decrements `PendingDataCount` to 0, fetches the stored `ready_receipt` by `(X, receipt_id)`, and calls `apply_action_receipt` against the current (recreated) account state [9](#0-8) . `apply_action` then runs `check_account_existence`/`check_actor_permissions` for `DeleteKey`, both of which pass trivially because the account now exists and the stored receipt's `actor_id` derivation only cares about identity match at execution time, not "is this the same account generation" [2](#0-1) . `action_delete_key` then finds `pk` present (the new owner's key) and deletes it [10](#0-9) .

No existing check (signature/nonce is irrelevant — this is receipt-level, not tx-level; access-key permission checks pass because the actor is the account itself; storage-staking and size limits are unrelated) stops this, because the postponed-receipt mechanism was designed assuming accounts are immutable identities across the receipt's lifetime, and account deletion does not invalidate outstanding postponed receipts addressed to that account id.

### Impact Explanation
Permanent freezing of the new owner's funds/access: their sole (or all) FullAccess key(s) on the recreated account get silently deleted by a receipt they never sent and had no way to prevent, matching the "permanent freezing of user funds" bounty category. This is most severe for NEAR-implicit or deterministic accounts, where the access key is cryptographically bound to (derivable from) the account id, making the target key 100% predictable to the original (attacker) owner before the account is even recreated.

### Likelihood Explanation
Preconditions are attacker-affordable and unprivileged: the attacker only needs to (1) own account X, (2) send itself a receipt with an artificial unresolved `input_data_id` carrying `DeleteKey(pk)` where `pk` is the deterministic/derivable key of X's future incarnation, (3) call `DeleteAccount`, and (4) at a time of its choosing, resolve the pending data dependency (since it, as predecessor, controls that promise chain) once it observes via public RPC that the new owner has recreated X with the expected key. This requires no validator/node privilege, only ordinary transactions and monitoring of public chain state — fully repeatable for any account whose reuse the attacker can predict (trivially true for NEAR-implicit/deterministic accounts).

### Recommendation
When an account is deleted (`remove_account`), also purge any outstanding `PostponedReceipt`, `PostponedReceiptId`, and `PendingDataCount` entries keyed by that `receiver_id` (iterate/remove all such trie keys under the account's postponed-receipt prefixes, mirroring the access-key/contract-data cleanup already done), so that stale postponed action receipts cannot be resurrected against a subsequently recreated account with the same id.

### Proof of Concept
Integration/apply-path test (mirroring existing tests in `runtime/runtime/src/tests/apply.rs` for postponed-receipt cleanup, e.g. `test_promise_input_size_limit_exceeded_fails_and_cleans_up`):
1. Set up account `X` (or a NEAR-implicit account id) with FullAccess key `K_old`.
2. Apply a self-receipt from `X` to `X` with `input_data_ids: [D]`, `actions: [DeleteKey(pk_target)]` (unresolved `D`) — assert it is stored as `PostponedReceipt`/`PendingDataCount`.
3. Apply a self-receipt from `X`: `DeleteAccount{beneficiary}` — assert account/keys are gone but `get_postponed_receipt(state, X, receipt_id)` still returns `Some`.
4. Apply a `CreateAccount` + `AddKey(pk_target, FullAccess)` receipt recreating `X` (or, for implicit accounts, a `Transfer` receipt) — assert `pk_target` access key now exists.
5. Deliver the `DataReceipt{receiver_id: X, data_id: D}` — assert the postponed `DeleteKey(pk_target)` executes and `get_access_key(state, X, pk_target)` returns `None` afterward, i.e., the new owner's key was removed by a receipt from before the account's recreation.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
