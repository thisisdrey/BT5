### Title
Unauthenticated smart-contract call to `BatchValidateSign` precompile can trigger an out-of-bounds array read/`ArrayIndexOutOfBoundsException` in `extractBytes32Array` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE describes an out-of-bounds read in a parser (`spvxml_parse_attributes`) that fails to validate that offsets/lengths derived from attacker-controlled input actually stay within the bounds of the underlying buffer when there is "extra content" past what the parser expects. The same bug class — deriving array offsets/lengths from untrusted input words without a bounds check before indexing — exists in the TVM `BatchValidateSign` precompiled contract's helper `extractBytes32Array`.

### Finding Description
`PrecompiledContracts.extractBytes32Array` reads an attacker-controlled offset from the `words` array and then indexes into it without any bounds validation: [1](#0-0) 

Compare this to the sibling helpers `extractBytesArray` and `extractSigArray`, which both explicitly guard against `offset > words.length - 1` before dereferencing: [2](#0-1) 

`extractBytes32Array` is called from `BatchValidateSign.doExecute` with an offset computed directly from calldata (`words[2].intValueSafe() / WORD_SIZE`), which any account can control by invoking the precompile with crafted ABI-encoded calldata via a smart contract call: [3](#0-2) 

If the offset (or `offset + i + 1` for a large declared array length `len`) exceeds `words.length - 1`, the missing bounds check causes `words[offset]` (or the subsequent indexed reads inside the loop) to throw `ArrayIndexOutOfBoundsException`, mirroring the "extra/insufficient content vs. declared length" root cause in the CVE.

Note: When `VMConfig.allowTvmOsaka()` is active, `isValidAbiEncoding` performs a coarse length/modulo check on the overall calldata, but this only validates total length alignment against `ABI_HEADER_WORDS`/`ABI_ITEM_WORDS` — it does not validate that the offset word (`words[2]`) itself points within the array bounds, nor that the declared array length is consistent with the buffer, since the offset value is fully attacker-controlled and independent from the coarse alignment check.

### Impact Explanation
An uncaught `ArrayIndexOutOfBoundsException` thrown from a precompiled contract during TVM execution is a `Throwable`. `BatchValidateSign.execute` does wrap `doExecute` in a `try/catch (Throwable t)` and falls back to returning `Pair.of(true, new byte[WORD_SIZE])` on any exception: [4](#0-3) 

Because this specific precompile already catches `Throwable`, the immediate effect is likely just an incorrect (all-zero) result rather than a node crash — this substantially limits the severity of this particular call site compared to the CVE's "read out of bounds" impact. However, this establishes that the bug-class (offset used without prior bounds validation in `extractBytes32Array`) exists in the codebase; if this helper is reused elsewhere in the future without an equivalent catch-all wrapper, it would produce a genuine crash/DoS. As currently wired, the worst observed outcome is energy consumption for a call that deterministically returns a false/zero signature-validation result, which is a **low-impact, self-contained exception path already defended by a catch-all** rather than a node-halting or fund-theft condition.

### Likelihood Explanation
Trivial to trigger: any unprivileged account can invoke the precompiled contract at the `BatchValidateSign` address via a normal TVM `CALL`/`STATICCALL` with crafted calldata setting `words[2]` to an out-of-range word offset. No special privileges are required.

### Recommendation
Add the same `offset > words.length - 1` (and per-iteration `offset + i + 1 > words.length - 1`) bounds check to `extractBytes32Array` that already exists in `extractBytesArray` and `extractSigArray`, returning an empty array instead of relying on downstream `catch (Throwable)` handling. This closes the code-level bug class even though the current call site is already defensively wrapped.

### Proof of Concept
Not independently confirmed by execution (no test harness run); reasoning is based on static code review of `extractBytes32Array` versus its sibling helpers and the `BatchValidateSign.doExecute` call site shown above. A concrete PoC would be a Solidity contract calling the `batchvalidatesign` precompile address with ABI-encoded calldata where the third word (`addrArrayOffset`) is set to a very large offset value (e.g., `0xFFFFFFFF / WORD_SIZE`), which is then used unchecked as an index into the `words` array in `extractBytes32Array`, raising `ArrayIndexOutOfBoundsException` — caught by the existing `try/catch(Throwable)` in `execute`. Verifying the exact runtime behavior end-to-end (deployment, calldata encoding, and confirming exception is indeed raised rather than optimized away) would require running the actual TVM in a test environment, which was not performed here.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
