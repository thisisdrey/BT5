### Title
Dust-transfer griefing fills a victim's per-account token list (`depositTokensOfAccount`), permanently DoS-ing deposits/issuance of new tokens - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Metronome tracks, per account, the set of `DepositToken`s and `DebtToken`s with nonzero balance in `MappedEnumerableSet` lists inside `Pool`. Any addition reverts once `debtTokensOfAccount.length(account) + depositTokensOfAccount.length(account) >= MAX_TOKENS_PER_USER`. Because `msdTOKEN` deposit tokens are freely transferable and every first-time receipt pushes the token onto the recipient's list, an unprivileged attacker can dust-transfer 1 wei of every deposit token to a victim and fill the victim's list up to the cap. From then on, the victim cannot deposit into any collateral type they don't already hold, cannot receive any new `msdTOKEN`, and cannot issue any new synthetic asset — every such path reverts inside `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` with `UserReachedMaxTokens`.

### Finding Description
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance moves from 0 to nonzero, with no consent or opt-out ([contracts/DepositToken.sol:517-520](contracts/DepositToken.sol)). The same happens in `DepositToken._mint` for `deposit(amount, onBehalfOf_)` where `onBehalfOf_` is attacker-chosen ([contracts/DepositToken.sol:485-488](contracts/DepositToken.sol)).
- `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, reverting with `UserReachedMaxTokens` once the combined deposit+debt token count hits `MAX_TOKENS_PER_USER` ([contracts/Pool.sol:143-148, 216-219](contracts/Pool.sol)).
- Removal only happens when a balance returns to zero; the victim can only clear entries one token at a time by transferring each dust balance away.
- Debt tokens are added via `DebtToken` mint/issue paths through `addToDebtTokensOfAccount`, which is guarded by the same cap — so issuing any *new* synthetic also reverts.

This mirrors CVE-2019-9371's class: missing input validation (no bound/consent on who may append entries to a bounded per-account resource) enables resource exhaustion and denial of service, reachable by any EOA with ordinary token transfers.

### Impact Explanation
- The victim is blocked from depositing any collateral type not already in their list and from minting any synthetic not already held — a temporary freeze of the account's core protocol operations.
- Concretely harmful follow-on: a victim with an unhealthy position who needs to add a *new* collateral type to avoid liquidation cannot do so and is liquidated; a user mid-way through a leverage/unwind flow involving a new token is bricked until they manually clear entries.
- Recovery is possible (transfer dust out), so funds are not permanently frozen, matching "temporary freezing of funds" impact class.

### Likelihood Explanation
- Attacker needs only a dust balance of each `msdTOKEN` (obtainable by depositing a tiny amount of each underlying, or buying on a DEX) and one cheap `transfer` per token per victim. Cost scales linearly with the number of listed deposit tokens, which is small.
- No privileged role, oracle manipulation, or victim interaction is required; `transfer` only checks the *sender's* unlocked balance (`_revertIfLocked` on `sender_`), never the recipient's list state.
- Nothing in `whenNotPaused`, `nonReentrant`, `SynthContext._msgSender`, or supply caps prevents this on the deployed configuration.

### Recommendation
- Make list membership opt-in: only add the recipient in `_transfer` if the recipient already holds the token or explicitly accepts it (e.g., track deposits separately from unsolicited transfers, or require `deposit`/`issue` paths to add while plain `transfer` does not).
- Alternatively, charge/whitelist: require a minimum amount (`amount_ > dustThreshold`) before adding to the per-account list, or let any account purge tokens below a dust threshold from its own list via a public `removeFromDepositTokensOfAccount`-style cleanup callable by the account owner.

### Proof of Concept
Hardhat (fork not strictly required; runs against deployed-style `Pool`/`DepositToken` mocks or a mainnet/base fork):

```ts
// setup: pool with N registered DepositTokens; attacker + victim EOAs
const max = (await pool.MAX_TOKENS_PER_USER()).toNumber();

// attacker obtains dust of each deposit token and sends 1 wei to victim
for (const dt of depositTokens) {
  await underlying.connect(attacker).approve(dt.address, 1);
  await dt.connect(attacker).deposit(1, attacker.address);       // or buy dust on DEX
  await dt.connect(attacker).transfer(victim.address, 1);        // adds dt to victim's list
}
// ... repeat until getDepositTokensOfAccount(victim) + getDebtTokensOfAccount(victim) == max

// victim can no longer deposit into a collateral they don't already hold
await expect(newDepositToken.connect(victim).deposit(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim cannot issue a new synthetic either (DebtToken._mint -> addToDebtTokensOfAccount)
await expect(newDebtTokenIssueFrom(victim))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Caveats: the per-victim impact is denial of new deposits/issuance (not theft of existing balances), and cleanup by the victim is possible but costs one transaction per stuffed token — severity is bounded, consistent with the Medium (6.5) rating of the reference CVE.
