### Title
Unbounded attacker-controlled attachment content persisted via `insert_instantiated_attachment` with no `attachments_max_size` check - (File: stackslib/src/net/atlas/db.rs / stackslib/src/net/atlas/download.rs)

### Summary
When the `AttachmentsDownloader` state machine finishes downloading attachments from a peer, it unconditionally calls `AtlasDB::insert_instantiated_attachment` on every `Attachment` decoded from a peer's `GetAttachmentResponse`, without ever calling `should_keep_attachment` (the function that enforces `AtlasConfig.attachments_max_size`). This is unlike the `posttransaction.rs` path, which does gate `insert_uninstantiated_attachment` behind `should_keep_attachment`.

### Finding Description
`should_keep_attachment` is the only place in `db.rs` that compares an attachment's content length against `self.atlas_config.attachments_max_size`: [1](#0-0) 

It is called before `insert_uninstantiated_attachment` in the HTTP POST-transaction path: [2](#0-1) 

However, the peer-download path never calls it. `AttachmentsDownloader::run`, when the batch state machine reaches `Done`, iterates every decoded `Attachment` and calls `insert_instantiated_attachment` directly with no size gate and no verification that the attachment's `hash()` matches any originally-requested `content_hash`: [3](#0-2) 

The attachments are populated in `extend_with_attachments`, which decodes the raw HTTP response via `decode_atlas_get_attachment()` (a hex string parsed into `Attachment::new(bytes)` with no length bound) and simply inserts it into a `HashSet<Attachment>` — again with no size check and no hash-equality check against the request that was sent: [4](#0-3) [5](#0-4) 

`insert_instantiated_attachment` itself performs no size validation before persisting the content verbatim into the SQLite BLOB column: [6](#0-5) 

Because `find_all_attachment_instances(&attachment.hash())` is looked up *after* already deciding to insert (and insertion happens regardless of whether any matching instance is found), a malicious peer answering an `AttachmentsInventoryRequest`/`AttachmentRequest` can return an oversized, unrelated blob as the "attachment" content; it will be hashed via `Attachment::hash()` (which calls `Hash160::from_data` over the full buffer) and persisted into the node's `attachments` table, regardless of `attachments_max_size`.

### Impact Explanation
An attacker running (or otherwise controlling) a peer that a victim node syncs Atlas attachments from can cause the victim to allocate, hash, and durably store an arbitrarily large attacker-chosen buffer in its local `AtlasDB`, bypassing the only size-enforcement mechanism (`should_keep_attachment`) that exists elsewhere in the same file for the same table. This is a remote, unauthenticated write of attacker-controlled data into node state/storage, repeatable per attachments-batch download cycle. This matches the "unauthenticated/unauthorized write to state" Critical category.

### Likelihood Explanation
Preconditions: the victim node must have Atlas attachment instances to resolve (normal operation for BNS-enabled nodes) and must select the attacker's node as one of its `outbound_sync_peers` for that batch — no special privilege, secret, or role is required, only running a reachable peer that offers attachment data. Attacker cost is low (serve one crafted HTTP response per attachment/inventory request); reachable via the standard Atlas download HTTP client path used for `/v2/attachments/inv` and `/v2/attachments/{hash}`.

### Recommendation
Call `should_keep_attachment` (or an equivalent length check against `atlas_config.attachments_max_size`) before inserting any attachment received from a peer, both in `AttachmentsDownloader::extend_with_attachments`/`run`'s `Done` branch and in `check_attachment_instances`'s inboxed-attachment branch, and additionally verify that `attachment.hash()` equals the `content_hash` that was actually requested before accepting/storing the peer's response.

### Proof of Concept
Rust test plan (stackslib/src/net/atlas/download.rs or db.rs test module):
1. Construct an `AtlasConfig` with a small `attachments_max_size` (e.g. 1_048_576).
2. Construct an `Attachment` whose `content` exceeds `attachments_max_size` (e.g. 10 MB of bytes).
3. Simulate the downloader path by directly invoking `AtlasDB::insert_instantiated_attachment(&oversized_attachment)` (bypassing `should_keep_attachment`), and assert it succeeds (`Ok(())`) and that `find_attachment(&oversized_attachment.hash())` returns `Some(...)` with the full oversized content — demonstrating no size enforcement exists on this path, contrasted with `should_keep_attachment` returning `false` for the same content when checked.
4. Optionally, drive the full `AttachmentsBatchStateMachine`/`AttachmentsDownloader::run` with a mocked peer HTTP response containing an oversized `GetAttachmentResponse` for a requested `content_hash`, and assert the resulting attachment stored has a `hash()` differing from the originally requested `content_hash`, proving the store proceeds without hash/size validation.

    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

impl<'de> Deserialize<'de> for GetAttachmentResponse {
    fn deserialize<D: serde::Deserializer<'de>>(d: D) -> Result<GetAttachmentResponse, D::Error> {
        let payload = String::deserialize(d)?;
        let hex_encoded = payload.parse::<String>().map_err(de_Error::custom)?;
        let bytes = hex_bytes(&hex_encoded).map_err(de_Error::custom)?;
        let attachment = Attachment::new(bytes);
        Ok(GetAttachmentResponse { attachment })
    }
