## Title
Zero-fee TRX/TRC10 Bancor Exchange enables costless sandwich/DoS of user swaps - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
Java-tron implements a permissionless, on-chain Bancor-formula asset exchange (`ExchangeCreateContract`/`ExchangeTransactionContract`) that lets any account swap TRX/TRC10 tokens against a shared reserve pool. Like the Well AMM in the referenced report, this built-in exchange charges **zero trading fee** and enforces slippage protection purely through a client-supplied `expected` (minimum-output) parameter checked at validation time. This combination reproduces the exact preconditions the external report identifies as enabling a costless sandwich/denial-of-service attack: no fee to make attacks costly, instantaneous price movement via a deterministic bonding-curve formula, and a mempool-visible minimum-output parameter that an attacker can straddle.

### Finding Description
`ExchangeTransactionActuator.calcFee()` unconditionally returns `0`, meaning swaps through the built-in exchange incur no protocol fee beyond ordinary bandwidth/energy consumption: [1](#0-0) 

The only user-supplied slippage protection is the `expected` field, validated against the Bancor-curve output computed by `ExchangeCapsule.transaction()`: [2](#0-1) 

The underlying reserve update follows a deterministic, instantaneously-priced bonding curve (Bancor relay-token formula) implemented in `ExchangeCapsule.transaction()` and `ExchangeProcessor.exchange()`: [3](#0-2) [4](#0-3) 

Because a victim's swap transaction and its `expected` (minimum-output) value are visible in the mempool before confirmation, an attacker can:
1. Submit a swap in the same direction as the victim to push the exchange's price/reserves so that the victim's `anotherTokenQuant` will fall below `tokenExpected`, causing `ExchangeTransactionActuator` to throw `"token required must greater than expected"` and the victim's transaction to fail.
2. Let the victim's transaction fail (revert, no fee credited to the exchange because `calcFee()==0`).
3. Submit a reverse swap to restore the reserve ratio, recovering nearly all previously swapped tokens (aside from small precision losses in the truncating Bancor math), since no fee is extracted from the pool at any step.

This is structurally identical to the Well DOS: a swap venue with (a) no fee, (b) instantaneous deterministic pricing, and (c) an on-chain minimum-output check that any observer can read and target.

### Impact Explanation
An attacker can repeatedly and near-costlessly force any TRX/TRC10 exchange swap to fail by manipulating the shared bonding-curve reserves around the victim's `expected` threshold, at only the cost of TRON bandwidth/energy for the bracketing transactions (which can be largely covered by free bandwidth/energy quotas for many accounts). This denies service to the built-in on-chain exchange, degrading the user experience of a core `Wallet`/actuator-reachable financial feature and pressuring users toward less transparent workarounds (higher slippage tolerance, which in turn increases their exposure to value extraction by the same attacker), analogous to the Medium-severity impact accepted in the original report.

### Likelihood Explanation
The attack requires only the ability to observe pending `ExchangeTransactionContract` transactions and to submit ordinary signed transactions - both available to any unprivileged network participant with TRX for bandwidth/energy. The `ExchangeTransactionActuator` and its zero-fee, deterministic-curve dependencies (`ExchangeCapsule`, `ExchangeProcessor`, `SafeExchangeProcessor`) are always reachable via broadcastable transactions, requiring no special privilege or witness/SR role.

### Recommendation
Introduce a nonzero protocol fee in `ExchangeTransactionActuator.calcFee()` (or an equivalent spread taken from the exchange reserves during `ExchangeCapsule.transaction()`), so that repeatedly bracketing a victim swap costs the attacker real value rather than being fee-neutral. Alternatively/additionally, consider commit-reveal or minimum block-inclusion delay semantics for exchange swaps to reduce the effectiveness of same-block sandwiching.

### Proof of Concept
1. Attacker observes a pending `ExchangeTransactionContract` from victim specifying `exchangeId`, `tokenId`, `quant`, and `expected` (see fields validated in `doValidate()`), lines [5](#0-4) .
2. Attacker submits a same-direction swap transaction first, shifting `firstTokenBalance`/`secondTokenBalance` in `ExchangeCapsule` via `transaction()` [6](#0-5)  so that the Bancor-formula output for the victim's swap now computes below `tokenExpected`.
3. Victim's transaction executes `doValidate()` and throws `"token required must greater than expected"`, failing at zero exchange-fee cost [7](#0-6) .
4. Attacker submits an opposite-direction swap of matching size, restoring reserves and recovering essentially all funds because `calcFee()` returns `0` [1](#0-0) , repeatable at will to deny service to any exchange participant.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
