### Title
WFP interface PERMIT filter has no protocol/port/remote condition, exposing the tun adapter to all inbound traffic bypassing Windows Defender Firewall - ([File: wfp/wfp_windows.go])

### Summary
`addInterfaceFilter` builds a single-condition `fwpmFilterCondition0` that only matches `fwpmConditionIPLocalInterface` (the tun LUID), with no `IP_PROTOCOL`, port, or remote-address condition, and installs it as a terminating PERMIT with `fwpmFilterFlagFlagClearActionRight` at a sublayer weighted `0xFFFF` above WDF's sublayer. This means once `PermitInterface` runs, ALL inbound traffic on the wintun adapter—any protocol, not just the nebula UDP overlay—is unconditionally permitted at `FWPM_LAYER_ALE_AUTH_RECV_ACCEPT_V4/V6` regardless of any Windows Defender Firewall block rules configured for that interface/protocol.

### Finding Description
`PermitInterface` (wfp/wfp_windows.go:201-216) calls `newSession` to create a dynamic session and a sublayer weighted `0xFFFF` (`registerSublayer`, wfp/wfp_windows.go:266-290), then calls `addInterfaceFilter` for both the IPv4 and IPv6 ALE_AUTH_RECV_ACCEPT layers. In `addInterfaceFilter` (wfp/wfp_windows.go:292-329) the filter's only condition is:
```go
cond := fwpmFilterCondition0{
    fieldKey:  fwpmConditionIPLocalInterface,
    matchType: fwpMatchEqual,
    conditionValue: fwpValue0{type_: fwpUint64, value: uintptr(unsafe.Pointer(&luid))},
}
```
with `numFilterConditions: 1` and `flags: fwpmFilterFlagClearActionRight`, unlike `addUDPPortFilter` (wfp/wfp_windows.go:333-377) which adds an additional `IP_PROTOCOL == UDP` condition. Because the filter matches solely on local interface LUID, and the sublayer weight (0xFFFF) plus `FWPM_FILTER_FLAG_CLEAR_ACTION_RIGHT` is explicitly designed (per the file's own comment at wfp/wfp_windows.go:76-79) to override lower-weight WDF block rules in the `MPSSVC_WF` sublayer, any inbound packet of any IP protocol destined to the nebula tun adapter's LUID is unconditionally PERMITted at the ALE_AUTH_RECV_ACCEPT layer, before WDF's own rules can block it. This is wired in via `installInterfaceBypass` (overlay/tun_bypass_windows.go:15-23), which calls `wfp.PermitInterface(luid)` with the wintun adapter's LUID when `listen.windows_bypass_wdf` is enabled.

### Impact Explanation
Any traffic (TCP, ICMP, or any other IP protocol, not only the nebula UDP control/data channel) that reaches the tun adapter's LUID—e.g. via routing, port forwarding, or any other mechanism that can direct packets at that interface—is delivered to the OS network stack regardless of Windows Defender Firewall rules scoped to that adapter or protocol. This is a firewall enforcement bypass: the invariant that WDF policy governs inbound traffic to the interface is violated for the entire interface, not just for the nebula UDP listener port that the feature is meant to permit. This matches the "firewall bypass" bounty category.

### Likelihood Explanation
Requires `listen.windows_bypass_wdf` to be enabled (an opt-in config feature) and the host running as the process with permission to install WFP filters (this is by design of the feature, not additional attacker privilege). Given that precondition, the bypass filter is installed automatically on every nebula start via `installInterfaceBypass`/`PermitInterface`, and it applies universally to any inbound traffic hitting the LUID—so exploitation is deterministic and requires no attacker interaction with the nebula certificate/handshake system at all; it is a configuration-triggered firewall-scope defect rather than a network-input-triggered one.

### Recommendation
Add the missing `IP_PROTOCOL == UDP` (and ideally `IP_LOCAL_PORT == <listen port>`) condition to `addInterfaceFilter`, mirroring `addUDPPortFilter`, so the interface-scoped PERMIT filter is narrowed to exactly the nebula UDP listener traffic instead of blanket-permitting all protocols on the LUID. Alternatively, replace `addInterfaceFilter`'s interface-only condition set with a combined condition array `{IP_LOCAL_INTERFACE == luid, IP_PROTOCOL == UDP, IP_LOCAL_PORT == port}` and drop the separate `PermitUDPPort`/`addUDPPortFilter` if redundant.

### Proof of Concept
Integration test (Windows-only, requires admin):
1. Configure a Windows Defender Firewall inbound block rule for TCP (or ICMP) scoped to the wintun adapter's interface alias/LUID.
2. Call `wfp.PermitInterface(luid)` with that LUID.
3. From a remote/loopback host, send a non-UDP packet (e.g., a TCP SYN or ICMP echo) targeting an IP bound to the tun adapter.
4. Assert that the packet is delivered to the interface (e.g., observed via a raw socket/packet capture bound to the tun adapter, or a listening TCP socket receiving the SYN) despite the WDF block rule — expected (buggy) result: delivered; expected (fixed) result: dropped by WDF because the WFP filter no longer matches non-UDP traffic.
