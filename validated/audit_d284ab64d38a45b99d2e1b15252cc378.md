I'll investigate whether there's a genuine analog in Gitaly's codebase — specifically around unvalidated URL handling in remote/import paths, since that's the closest legitimate parallel to "unvalidated external URLs" in a Git server context.### Title
Unvalidated Remote URL Scheme in Gitaly's URL-Based Git RPCs Enables `ext::` Transport Command Execution - (File: `internal/gitaly/service/repository/create_repository_from_url.go`, `internal/gitaly/service/repository/fetch_remote.go`)

### Summary
`CreateRepositoryFromURL`, `FetchRemote`, `UpdateRemoteMirror`, `FindRemoteRepository`, and `FindRemoteRootRef` all accept an attacker/caller-controlled `url` string that is passed to `git clone`/`git fetch`/`git ls-remote` with no scheme allowlist. Git supports the `ext::<command>` remote helper transport, which spawns an arbitrary shell command as the "remote helper" for the operation. Because Gitaly never restricts allowed protocols (no `protocol.ext.allow=never`, no `GIT_ALLOW_PROTOCOL` env var, no scheme allowlist in Go code), a URL value of the form `ext::sh -c '<command>'` reaching any of these RPCs results in command execution on the Gitaly host under the `git` process user.

### Finding Description
`cloneFromURLCommand` in [1](#0-0)  only performs `url.Parse(repoURL)` to extract user/credentials, and `validateCreateRepositoryFromURLRequest` only checks that the URL is non-empty [2](#0-1) . The resulting string is passed straight through as a positional argument to `git clone` [3](#0-2) .

Similarly, `FetchRemote`'s `buildCommandOpts` takes `req.GetRemoteParams().GetUrl()` and only rejects an empty string in `validateFetchRemoteRequest` [4](#0-3) , then sets it as `remote.inmemory.url` for `git fetch` [5](#0-4) .

The only URL-related hardening present in the codebase is:
- DNS-rebinding protection via the optional `resolved_address` field / `http.curloptResolve`, implemented in `GetURLAndResolveConfig` [6](#0-5) .
- Disabling `transfer.bundleURI` specifically to close a prior bundle-URI SSRF vector [7](#0-6) , confirmed as a past fix in the changelog [8](#0-7) .

Neither mechanism restricts the URL **scheme**. There is no `protocol.<name>.allow` configuration, no `GIT_ALLOW_PROTOCOL` environment variable, and no scheme allowlist anywhere in `internal/git/gitcmd` (searched `command_factory.go`, `command_description.go`, `protocol.go`) — confirmed by exhaustive grep across the repository showing zero matches for `protocol.ext`, `protocol.file`, `GIT_ALLOW_PROTOCOL`, or `ext::` handling in the git command layer. Git's global configuration set up in `GlobalConfiguration` hardens unrelated settings (`core.useReplaceRefs`, `gc.auto`, fsync behavior, etc.) but never touches `protocol.*.allow` [9](#0-8) .

Because the URL is supplied directly as a git command-line argument (equivalent to a user typing `git clone <url>` themselves, not a URL discovered indirectly such as a submodule URL), Git's `GIT_PROTOCOL_FROM_USER` defaults to enabled, meaning Git's "user" default policy for `protocol.ext.allow` permits the `ext::` remote helper to run. A URL such as:
```
ext::sh -c "id > /tmp/pwned; sh 0<&1"
```
would cause `git clone`/`git fetch`/`git ls-remote` to invoke the given shell command as its "remote helper," executing it as the Gitaly process.

### Impact Explanation
Successful exploitation results in arbitrary command execution on the Gitaly node, running as the user that runs the `git`/Gitaly process. This is a full compromise of the Gitaly host: read/write access to every repository on that storage, ability to pivot to other internal services, and potential compromise of the entire GitLab installation depending on network segmentation. This significantly exceeds the impact described in the original frontend report (client-side XSS/spoofing) because it grants server-side RCE instead of a browser-confined issue.

### Likelihood Explanation
Likelihood depends on whether any caller of these RPCs (`CreateRepositoryFromURL`, `FetchRemote`, `UpdateRemoteMirror`, `FindRemoteRepository`, `FindRemoteRootRef`) forwards an unsanitized, user-supplied URL. These RPCs back GitLab-facing features such as "import project by URL," "pull mirroring," and "fetch remote," where the URL is directly provided by the requesting user/project owner through the Rails/API layer and forwarded to Gitaly. If the upstream caller (e.g., GitLab Rails' `Gitlab::UrlBlocker`) does not strip/validate `ext::`-prefixed values before forwarding to Gitaly, this is directly reachable by any user with import/mirror privileges — an "ordinary user" action, matching the required threat model. Gitaly itself provides no defense-in-depth against this at the RPC boundary, so if the caller's validation is bypassed or incomplete (as has repeatedly happened historically — see the multiple "Import via git protocol allows to bypass checks on repository" security fixes in the changelog, e.g. [10](#0-9)  and [11](#0-10) ), this becomes trivially exploitable.

### Recommendation
- Enforce `protocol.ext.allow=never` (and disallow `file://` unless explicitly needed) as part of the global Git configuration used for all URL-based clone/fetch/ls-remote invocations in `GlobalConfiguration` (`internal/git/gitcmd/command_factory.go`) or via `GIT_ALLOW_PROTOCOL`/`GIT_PROTOCOL_FROM_USER=0` environment variables set on these specific commands.
- Add an explicit scheme allowlist (e.g., `http`, `https`, `git`, `ssh`) in `validateCreateRepositoryFromURLRequest` and `validateFetchRemoteRequest`, rejecting any other scheme (including `ext`, `fd`, and, unless intentionally supported, `file`) before constructing the Git command.
- Apply the same validation uniformly to `UpdateRemoteMirror`, `FindRemoteRepository`, and `FindRemoteRootRef`, since they share the same unrestricted `url`/`remote` fields.
- Do not rely solely on upstream (Rails/API) URL validation as the sole control; Gitaly should treat all RPC-supplied URLs as untrusted input given its multi-consumer, multi-tenant deployment model.

### Proof of Concept
1. Issue a `CreateRepositoryFromURL` gRPC request (or the equivalent `FetchRemote`/`UpdateRemoteMirror` request) with:
   ```
   url: "ext::sh -c \"touch /tmp/gitaly_pwned\""
   ```
2. `cloneFromURLCommand` parses this with `url.Parse`, finds no issues since only user/password extraction is attempted, and passes the string unchanged to `git clone ... "ext::sh -c \"touch /tmp/gitaly_pwned\""` [12](#0-11) .
3. Because no `protocol.ext.allow` restriction is configured anywhere in Gitaly's Git command layer, Git's `ext::` remote helper executes `sh -c "touch /tmp/gitaly_pwned"` on the Gitaly host, confirming arbitrary command execution.

**Note on verification limits:** I was not able to execute Git directly to confirm the exact parsing behavior of Go's `net/url.Parse` on `ext::`-style URLs (whether it errors out on certain characters like spaces) or to confirm Git's exact default `protocol.ext.allow` policy version-for-version. This assessment is based on static analysis of the Gitaly codebase (confirmed absence of any protocol/scheme restriction) combined with documented Git `ext::` transport semantics. If a background Devin session with code execution capability is available, this PoC should be validated end-to-end against a running Gitaly instance to eliminate any remaining uncertainty before considering this exploit confirmed.

func GetURLAndResolveConfig(remoteURL string, resolvedAddress string) (string, []ConfigPair, error) {
	if remoteURL == "" {
		return "", nil, fmt.Errorf("URL is empty")
	}

	if resolvedAddress == "" {
		return "", nil, fmt.Errorf("resolved address is empty")
	}

	resolvedIP := net.ParseIP(resolvedAddress)
	if resolvedIP == nil {
		return "", nil, fmt.Errorf("resolved address has invalid IPv4/IPv6 address")
	}

	switch {
	case strings.HasPrefix(remoteURL, "http://"), strings.HasPrefix(remoteURL, "https://"), strings.HasPrefix(remoteURL, "git://"):
		return getURLAndResolveConfigForURL(remoteURL, resolvedAddress)
	case strings.HasPrefix(remoteURL, "ssh://"):
		return getURLAndResolveConfigForSSH(remoteURL, resolvedAddress)
	default:
		return getURLAndResolveConfigForSCP(remoteURL, resolvedAddress)
	}
}
