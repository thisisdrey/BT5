### Title
Unstaked attackers can churn QUIC handshakes indefinitely because rate-limiter tokens are only consumed on *successful* handshake completion, not on attempt - ([File: streamer/src/nonblocking/quic.rs])

### Summary
Both the global (`overall_connection_rate_limiter`) and per-IP (`ConnectionRateLimiter`) checks performed in `run_server` before `incoming.accept()` are non-mutating "peek" checks; the actual token consumption (`consume_tokens`/`register_connection`) only happens later in `setup_connection`, and only if the QUIC handshake succeeds. An attacker who opens connection attempts and lets them fail or time out before completing the handshake never drains either bucket, so the pre-accept gates never fire and the attacker can repeatedly trigger `ClientConnectionTracker` allocation and QUIC handshake crypto work at a rate bounded only by the concurrency cap and handshake timeout, not by the named rate limiters.

### Finding Description
In `run_server`, for every incoming attempt the code performs two pre-accept checks that only *read* limiter state: [1](#0-0) 

- `overall_connection_rate_limiter.current_tokens() == 0` merely peeks at the bucket.
- `rate_limiter.is_allowed(&ip)` in `ConnectionRateLimiter` also only peeks: [2](#0-1) 

Neither of these calls decrements any token. The only places that actually consume tokens are `rate_limiter.register_connection(&from.ip())` and `overall_connection_rate_limiter.consume_tokens(1)`, both of which are reached exclusively on the `Ok(new_connection)` branch of `setup_connection`, i.e. only after the QUIC handshake has *successfully completed* within `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`: [3](#0-2) 

If the handshake instead errors or times out, execution goes to `handle_connection_error` or the `connection_setup_timeout` branch — neither of which touches either limiter: [4](#0-3) 

Consequently, an attacker who deliberately aborts the QUIC handshake before it completes (e.g. drop the socket right after the Initial packet, or never send further handshake flight) can generate an unbounded number of connection attempts per unit time without ever draining either the global or per-IP token bucket, because the buckets are never charged for failed/incomplete attempts. Every such attempt still costs the leader:
1. A `ClientConnectionTracker::new` allocation/accounting update (bounded only by `qos.max_concurrent_connections()`), gated purely by the never-decrementing peek checks: [5](#0-4) 
2. A spawned `setup_connection` task that drives the `Connecting` future through TLS/QUIC handshake crypto (server-side certificate/key operations) before the `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting)` expires: [6](#0-5) 

Because slots are freed the moment the attacker's connection fails/times out and there is no cost recorded against either rate limiter for a failed attempt, the sustainable attack throughput is `max_concurrent_connections / effective_slot_hold_time`, entirely decoupled from `MAX_CONNECTION_BURST`/`TOTAL_CONNECTIONS_PER_SECOND` and `max_connections_per_ipaddr_per_min`. This directly contradicts the invariant that unstaked connection/stream limits are enforced per source and cannot be evaded by connection churn — the counters `connection_rate_limited_across_all` and `connection_rate_limited_per_ipaddr` will not increment for this attack pattern because the buckets never empty.

### Impact Explanation
This is cheap-packet-forces-disproportionate-accept/handshake-work: a single unstaked, unprivileged remote client reachable via the public TPU QUIC port can force the leader to repeatedly perform QUIC/TLS server-side handshake crypto and connection-table bookkeeping at a rate that the documented rate-limiting mechanism (`overall_connection_rate_limiter`, `ConnectionRateLimiter`) is supposed to bound but does not, because these limiters are only charged on handshake success. This degrades leader CPU availability below the cost the attacker actually pays (near-zero, since a client-side dropped/incomplete handshake is cheap), matching the "grossly underpriced pre-fee work" / resource-exhaustion category referenced in the question's scoped impact.

### Likelihood Explanation
No stake, gossip participation, or special network position is required — only that the leader's TPU QUIC endpoint is reachable, which is a normal precondition for transaction submission. The attack requires only opening TCP/UDP QUIC connections and aborting the handshake before completion, which is trivial to automate from many ephemeral local ports of a single source IP (or multiple IPs to also bypass the per-IP concurrency accounting spread across `open_connections`). This is fully repeatable and does not depend on timing races beyond normal network conditions.

### Recommendation
Charge (consume) both the global and per-IP rate limiter tokens at attempt time (before or at `incoming.accept()`), not only after successful handshake completion. If a lighter pre-handshake charge is desired to avoid punishing legitimate retries, consider a separate, smaller "attempt" bucket that is consumed on every accept attempt (successful or not), in addition to the existing "success" bucket, so that repeated failed/aborted handshakes from the same IP or in aggregate are still throttled.

### Proof of Concept
Integration test plan (using existing `setup_quic_server` test harness in `streamer/src/nonblocking/quic.rs` test module):
1. Spawn a test QUIC server via `setup_quic_server` with a small `max_connections_per_ipaddr_per_min` and small `MAX_CONNECTION_BURST`.
2. From a single source IP, open N `Connecting` attempts (N > burst limits) that immediately drop the socket/connection before completing the TLS handshake (e.g., send only the QUIC Initial packet and close the UDP socket, or use a client endpoint but abort before `Connecting` resolves).
3. Repeat this churn loop many times within `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`-sized windows for a sustained period.
4. Assert that `stats.connection_rate_limited_per_ipaddr` and `stats.connection_rate_limited_across_all` remain at 0 (or far below the number of attempts) despite far exceeding the configured `max_connections_per_ipaddr_per_min` and `TOTAL_CONNECTIONS_PER_SECOND`, while `stats.total_incoming_connection_attempts` and `stats.outstanding_incoming_connection_attempts` grow proportionally with attack volume — demonstrating that accepted/handshake work is not bounded by attempt volume as the invariant requires.

    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \

            );
            return Err(());
        }

        Ok(Self { stats })
    }
