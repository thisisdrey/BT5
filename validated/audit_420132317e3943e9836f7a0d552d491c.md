### Title
`mt_resolve_withdraw` treats a mismatched-length promise result identically to "nothing used", causing a full refund despite real token delivery - ([File: contracts/defuse/src/contract/tokens/nep245/withdraw.rs])

### Summary
`mt_resolve_withdraw` only trusts the deserialized `used` vector from the `mt_batch_transfer_call` promise result when its length exactly equals `amounts.len()`; any other successful-but-malformed length (`Ok(_)`) is silently mapped to `vec![U128(0); amounts.len()]`, i.e. "zero used, refund everything." An attacker who deploys and fully controls the withdrawn token contract can make its final resolve step return a JSON array of the wrong length while the underlying tokens have genuinely already moved to the receiver, causing the Verifier to re-credit the full withdrawn amount on top of the real transfer.

### Finding Description
The broken binding is: `debited == delivered + recredited`, per token.

- `debited`: `self.withdraw(&owner_id, ...)` subtracts `1000` from the owner's internal balance for `Nep245TokenId(attacker_mt, "a")` and `"b"` at intent-execution time. [1](#0-0) 
- `delivered`: the real cross-contract `mt_batch_transfer_call` to `attacker_mt`, transferring the tokens to `attacker_receiver`. Since the attacker deploys `attacker_mt`, they fully control what "delivered" means on that ledger and can make it genuinely `1000` per token while still forging the outer promise's final return value. [2](#0-1) 
- `recredited`: in the callback, `promise_result_checked_json_with_len::<Vec<U128>>(0, amounts.len())` is matched with `Ok(Ok(used)) if used.len() == amounts.len() => used`, but any other `Ok(_)` (including a JSON array parsed successfully but with the wrong length) falls into `vec![U128(0); amounts.len()]`, i.e. "assume none used". This drives `refund = amount.saturating_sub(0) = amount` for every token, and `self.deposit(...)` re-credits the full `1000` per token back to `sender_id`. [3](#0-2) 

For each token: `debited(1000) == delivered(1000) + recredited(1000)` is `1000 == 2000`, false — the internal ledger now claims to hold `1000` more of `Nep245TokenId(attacker_mt, "a"/"b")` per token than it actually possesses, since the real tokens already left to `attacker_receiver`.

Root cause: the `Ok(_)` catch-all branch conflates "response length didn't match" with "the whole batch failed/nothing was used" — the same conservative fallback is used elsewhere for genuine errors (`Err(_) => amounts.clone()`, documented as a deliberate NEP-141-style safety net) but here it is silently applied to any malformed-but-successful response too, without distinguishing an honest receiver bug from a malicious token deliberately forging its own resolve output.

This requires the attacker to own/deploy the withdrawn token contract itself (`token` field of `MtWithdraw`), since only a contract the attacker fully controls can make its `mt_resolve_transfer`/equivalent return an intentionally wrong-length array while still having genuinely delivered the tokens internally. A well-behaved third-party NEP-245 implementation (including the Verifier's own `mt_resolve_transfer`, seen at `contracts/defuse/src/contract/tokens/nep245/resolver.rs:32-36,121`) always returns a fixed-length array matching `amounts.len()`, so it cannot trigger this branch — confirming the exploit is confined to token contracts the attacker controls.

### Impact Explanation
The immediate effect is ledger-integrity corruption for the specific `Nep245TokenId(attacker_mt, token_id)` type: the Verifier's internal balance for that token type exceeds what it actually custodies on the external contract, matching the "Verifier owes more than it custodies" / "refund or resolver credit that does not match what failed to settle" Critical category. Because the attacker deploys and controls `attacker_mt` and `attacker_receiver`, only balances of that self-issued token type are directly inflated in this step; there is no guard preventing the attacker from later using this inflated internal balance in swap intents against other counterparties' genuinely deposited assets, at which point real value could be extracted. The bug is repeatable per withdrawal and per token count in the batch.

### Likelihood Explanation
The attacker needs only to deploy their own MT contract and a receiver contract (both fully attacker-controlled, no special roles or victim keys required), deposit some amount of their self-issued token into the Verifier to build an internal balance, then sign an `MtWithdraw` with `msg: Some(...)` to trigger the `mt_batch_transfer_call` path, and have their own contract deliberately return a wrong-length JSON on resolution. This is inexpensive and fully reproducible by the attacker at will; it does not require any other party's cooperation to trigger the ledger divergence itself.

### Recommendation
In `mt_resolve_withdraw`, do not collapse a malformed/mismatched-length `Ok(_)` response to "zero used, full refund." Instead treat any `Ok` result whose length doesn't match `amounts.len()` the same as a hard error condition that should not credit a refund at all (or panic), since a successfully-parsed-but-wrong-length response cannot be trusted to represent "nothing was transferred." At minimum, distinguish this case from genuine promise failures documented for the NEP-141 gas-exhaustion workaround, and require exact-length validation before assuming any refund amount.

### Proof of Concept
`cargo test` (near-workspaces sandbox) plan:
1. Deploy a malicious MT contract `attacker_mt` whose `mt_batch_transfer_call`/internal resolve step: (a) genuinely records `attacker_receiver` as owning `1000` of `"a"` and `"b"` (real transfer completes), and (b) returns a final JSON value that deserializes as `Vec<U128>` of length `1` (e.g. `[U128(0)]`) instead of length `2`.
2. In the Verifier: deposit `1000` of `Nep245TokenId(attacker_mt, "a")` and `1000` of `Nep245TokenId(attacker_mt, "b")` to attacker's account via `mt_on_transfer`.
3. Sign and execute `MtWithdraw { token: attacker_mt, receiver_id: attacker_receiver, token_ids: ["a","b"], amounts: [1000,1000], msg: Some("x") }` through `execute_intents`.
4. Assert on both sides of the binding: query `attacker_mt`'s real balance of `attacker_receiver` for `"a"`/`"b"` (expect `1000` each — real delivery happened), and query the Verifier's `mt_balance_of` for the attacker's `Nep245TokenId(attacker_mt, "a"/"b")` balance post-withdrawal (expect it returns to `1000` each instead of `0`), demonstrating `debited(1000) != delivered(1000) + recredited(1000)` and a net doubling of attacker-controlled value versus the Verifier's actual custodied amount (`0`).
