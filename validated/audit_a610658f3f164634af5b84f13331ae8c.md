### Title
Unbounded array allocation from unchecked length word in TVM precompiled contract input parsing leads to OOM / node crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read a length value directly from attacker-supplied EVM/TVM call data (a 32-byte word interpreted via `DataWord.intValueSafe()`) and immediately allocate a Java array sized by that value, without validating it against the actual size of the call data buffer. This mirrors the Apache Ant CVE-2021-36374 bug class (CWE-130, "Improper Handling of Length Parameter Inconsistency"): a length field taken from untrusted input is trusted to size a memory allocation before the parser has confirmed enough real data backs it, letting a small, cheap input trigger a disproportionately large allocation.

### Finding Description
`extractBytes32Array` and `extractBytesArray`/`extractSigArray` compute `len` from `words[offset].intValueSafe()` and then do: [1](#0-0) 

`intValueSafe()` only clamps to `Integer.MAX_VALUE` when the word occupies more than 4 bytes or is negative; any value that fits in 4 bytes (up to `0x7FFFFFFF`, ~2.14 billion) is returned unmodified: [2](#0-1) 

The `len` value is then used directly to allocate `new byte[len][]` (an object-reference array, ~8–16 bytes per empty slot on a 64-bit JVM) before any per-element bounds check occurs. Only the starting `offset` is checked against `words.length`; the declared count `len` is never checked against the number of words actually available in the call data: [3](#0-2) 

This is the same root cause pattern as the Ant advisory: a length field embedded in the payload (ZIP entry size / here, an ABI-style count word) is used to size an allocation before the parser has verified the declared length is consistent with the actual amount of backing data supplied. A contract's call data is bounded by the transaction/message size limits, but the *declared* array length embedded inside that call data is fully attacker-controlled and independent of the real backing bytes, so a tiny transaction can request a huge allocation.

### Impact Explanation
An attacker can craft call data to a precompiled contract (e.g. the batch-signature-validation precompile that uses these extraction helpers) with a length word set to a large value (up to ~2^31-1) while supplying only a few real bytes of call data. This forces the executing full node to attempt allocating a very large array (potentially billions of reference slots), which will throw `OutOfMemoryError` or cause severe GC pressure/thrashing on the node processing the transaction. Because contract execution in `PrecompiledContracts`/TVM runs inside the block-processing/validation path in `Manager`, this can disrupt transaction execution for any node that processes or re-executes the malicious transaction (including during block validation by all nodes on the network), amounting to a low-cost, broadly reachable node-crash/DoS vector triggerable by any unprivileged transaction sender.

### Likelihood Explanation
High reachability: any account can deploy or call a contract that invokes the vulnerable precompiled contract with attacker-chosen call data; no special privilege, staking, or witness/SR role is required. The only constraint is normal transaction/energy limits, but the cost of supplying the crafted length word is trivial (32 bytes) compared to the allocation it triggers, so the attack is cheap relative to its effect.

### Recommendation
In `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate that the declared `len` is consistent with the actual remaining `words`/`data` length (analogous to the `verifyLength` checks already used in `RLP.java`) before allocating any array, and reject/throw if the declared count exceeds what the supplied call data can actually back.

### Proof of Concept
1. Deploy or call any contract that invokes the batch-signature-validation precompiled contract path in `PrecompiledContracts.java`.
2. Construct the ABI-encoded call data so the "array length" word at the offset consumed by `extractBytesArray`/`extractSigArray`/`extractBytes32Array` is set to a large value (e.g. `0x7FFFFFFF`) while providing only the minimal number of real trailing words.
3. Send the transaction; on execution, `new byte[len][]` (or `new byte[len]`) is invoked with `len` derived from the attacker-controlled word, causing the executing node to attempt an oversized allocation and throw `OutOfMemoryError`, disrupting further processing on that node.
