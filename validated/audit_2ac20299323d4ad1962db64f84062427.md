## Analysis

The external report's core broken invariant: a public/permissionless "create the resource" action can pre-empt and permanently block a privileged/governance-gated "create the resource with special parameters" action, because both check the same "does not yet exist" precondition on the same identifier.

I found a direct structural analog in `pallet-asset-conversion`.

`create_pool` is a fully permissionless, `ensure_signed` extrinsic (call index 0) that creates a liquidity pool for any `(asset1, asset2)` pair via `do_create_pool`, which only guards against re-creation with `ensure!(!Pools::<T>::contains_key(&pool_id), Error::<T>::PoolExists)`. [1](#0-0) [2](#0-1) 

`create_pool_with_fee` is the privileged counterpart, gated by `T::AdminOrigin` (governance/root), intended to atomically create a pool for a given `creator` account with a custom initial `Permill` fee that overrides the global `LPFee`. It calls the exact same `do_create_pool` and hits the exact same `PoolExists` guard on the exact same `pool_id`. [3](#0-2) 

Because `pool_id` is derived deterministically from the unordered `(asset1, asset2)` pair via `T::PoolLocator::pool_id`, any unprivileged account can call the permissionless `create_pool` for that pair (in either asset order) before governance's `create_pool_with_fee` extrinsic executes, causing the privileged call to fail with `PoolExists` — exactly mirroring the griefer calling `JoeFactory.createPair(WAVAX, _token)` ahead of `LaunchEvent.createPair`.

### Title
Permissionless `create_pool` can pre-empt and deny the privileged `create_pool_with_fee` for the same asset pair - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`pallet-asset-conversion::create_pool` (any signed account, no privilege) and `pallet-asset-conversion::create_pool_with_fee` (`T::AdminOrigin` only) both funnel into `do_create_pool`, which enforces a single global "pool must not already exist for this `pool_id`" invariant. An unprivileged attacker can observe an admin's intent (e.g. via a pending governance proposal/scheduled call, or simply race any anticipated new-asset listing) and call the permissionless `create_pool` first, causing the subsequent privileged `create_pool_with_fee` to always revert with `Error::PoolExists`.

### Finding Description
`do_create_pool` is shared by both extrinsics: [4](#0-3) 

- `create_pool` (call index 0) requires only `ensure_signed`, i.e. it is fully public.
- `create_pool_with_fee` (call index 6) requires `T::AdminOrigin::ensure_origin`, and takes a `creator` account plus an initial `fee: Permill` intended to override the pallet's default `LPFee` for that specific pool.

Both resolve the same `pool_id = T::PoolLocator::pool_id(&asset1, &asset2)` (order-independent for a given pair) and both check `ensure!(!Pools::<T>::contains_key(&pool_id), Error::<T>::PoolExists)`. There is no reservation, no "governance intends to configure this pair" flag, and no way for `create_pool_with_fee` to take over/overwrite an already-existing pool. A regular `create_pool` call for the same pair, submitted before the privileged transaction is included, permanently forecloses the privileged path — the pool will exist forever with the pallet's default `LPFee` (unless subsequently patched via `set_pool_fee`), and the `creator` account chosen by governance is bypassed for deposit/fee payment and event attribution.

This is structurally identical to the Trader Joe finding: `LaunchEvent.createPair` (privileged, phase-gated) required `factory.getPair(...) == address(0)`, but `factory.createPair` itself was permissionless, so a griefer front-ran the privileged path and blocked it, since pool/pair creation itself is designed to be open.

### Impact Explanation
This degrades intended runtime behavior: a chain's governance-configured LP fee schedule for a newly listed asset pair can be silently overridden/blocked by any user, and the deterministic `pool_id`/`lp_token` allocation intended for a controlled listing is instead consumed by an arbitrary actor. While `set_pool_fee` (also `AdminOrigin`-gated) can retroactively fix the fee on an already-created pool, the `creator`-scoped deposit/fee-payment semantics of `create_pool_with_fee` and the atomicity of "pool + fee set together" (`PoolCreated` + `PoolFeeSet` emitted together) are lost, and any batched/atomic governance operation relying on `create_pool_with_fee` succeeding will revert with `PoolExists`, silently failing an on-chain governance action. This falls under "runtime bugs that compromise intended behavior" for the pallet.

### Likelihood Explanation
High likelihood: `create_pool` has no cost barrier beyond the fixed `PoolSetupFee`/deposits, no whitelist, and any observer of a pending governance proposal (all on-chain proposals are public before execution) referencing `create_pool_with_fee` for a specific pair can trivially front-run it in an earlier block/extrinsic.

### Recommendation
Do not rely on a shared "pool must not exist" precondition for both a permissionless and a privileged creation path targeting the same `pool_id`. Options:
- Allow `create_pool_with_fee` to also succeed when the pool already exists, applying the requested fee via `set_pool_fee` semantics instead of unconditionally failing.
- Alternatively, gate `create_pool` itself so it cannot be used to squat on pairs that governance has reserved (e.g. an allow/denylist of asset kinds, or a "reserved pair" registry checked by `do_create_pool`).
- At minimum, document/handle the race by having governance always call `create_pool_with_fee` and, on `PoolExists`, fall back to `set_pool_fee` in the same batch/proposal so the intended fee is applied regardless of which path created the pool.

### Proof of Concept
1. Governance drafts (and it becomes publicly visible, e.g. in the transaction pool or a scheduled/preimage'd proposal) a call to `AssetConversion::create_pool_with_fee(AdminOrigin, creator=Treasury, asset1=Native, asset2=NewAsset, fee=0.05%)`.
2. Attacker observes this and, before it executes, submits `AssetConversion::create_pool(RuntimeOrigin::signed(attacker), Native, NewAsset)`, paying only the standard `PoolSetupFee`. [5](#0-4) 
3. `Pools::<T>::contains_key(&pool_id)` is now `true` for `(Native, NewAsset)`.
4. Governance's `create_pool_with_fee` call executes and returns `Error::<T>::PoolExists`, as shown by the existing test `create_same_pool_twice_should_fail` demonstrating the same-pair collision behavior of `do_create_pool`.
5. The pool now permanently exists with `attacker` as `creator` and the pallet's default `LPFee`, and `Pools`/`PoolFees` cannot be re-created; governance must issue a separate `set_pool_fee` call to correct the fee, breaking the intended atomic "create with custom fee" operation.

		pub(crate) fn do_create_pool(
			creator: &T::AccountId,
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			initial_fee: Option<Permill>,
		) -> Result<T::PoolId, DispatchError> {
			ensure!(asset1 != asset2, Error::<T>::InvalidAssetPair);
			if let Some(fee) = initial_fee {
				ensure!(fee <= T::MaxSwapFee::get(), Error::<T>::FeeTooHigh);
			}

			// prepare pool_id
			let pool_id = T::PoolLocator::pool_id(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;
			ensure!(!Pools::<T>::contains_key(&pool_id), Error::<T>::PoolExists);

			let pool_account =
				T::PoolLocator::address(&pool_id).map_err(|_| Error::<T>::InvalidAssetPair)?;

#[test]
fn create_same_pool_twice_should_fail() {
	new_test_ext().execute_with(|| {
		let user = 1;
		let token_1 = NativeOrWithId::Native;
		let token_2 = NativeOrWithId::WithId(2);

		create_tokens(user, vec![token_2.clone()]);

		let lp_token = AssetConversion::get_next_pool_asset_id();
		assert_ok!(AssetConversion::create_pool(
			RuntimeOrigin::signed(user),
			Box::new(token_2.clone()),
			Box::new(token_1.clone())
		));
		let expected_free = lp_token + 1;
		assert_eq!(expected_free, AssetConversion::get_next_pool_asset_id());

		assert_noop!(
			AssetConversion::create_pool(
				RuntimeOrigin::signed(user),
				Box::new(token_2.clone()),
				Box::new(token_1.clone())
			),
			Error::<Test>::PoolExists
		);
		assert_eq!(expected_free, AssetConversion::get_next_pool_asset_id());

		// Try switching the same tokens around:
		assert_noop!(
			AssetConversion::create_pool(
				RuntimeOrigin::signed(user),
				Box::new(token_1.clone()),
				Box::new(token_2.clone())
			),
			Error::<Test>::PoolExists
		);
		assert_eq!(expected_free, AssetConversion::get_next_pool_asset_id());
