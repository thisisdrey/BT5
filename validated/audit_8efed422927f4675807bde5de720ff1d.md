I reviewed the StackerDB write paths in the specified scope (`stackslib/src/net/stackerdb/**`, `stackslib/src/net/api/poststackerdbchunk.rs`, `stackslib/src/net/relay.rs`, `libstackerdb/**`) for the specific bug class you described (unauthenticated/unauthorized StackerDB writes, forged gossip relay, or auth checks failing open). I did not find a valid analog — every write path enforces signature verification before storage or relay:

- **HTTP POST path** (`RPCPostStackerDBChunkRequestHandler::try_handle_request`) delegates directly to `StackerDBTx::try_replace_chunk`, which is the sole gate for persisting a chunk. [1](#0-0) 

- **Core validation** in `try_replace_chunk` checks chunk size, looks up the slot's registered signer, and rejects with `BadSlotSigner` if `slot_desc.verify(&slot_validation.signer)` fails, before checking staleness or write-count limits. [2](#0-1) 

- **Gossip/sync path** (`StackerDBSync::validate_received_chunk`, used both for downloaded chunks and unsolicited pushes) independently re-derives the expected signer via `get_slot_signer` and calls `slot_metadata.verify(&addr)` before accepting the chunk as valid, prior to any relay/broadcast. [3](#0-2) 

- **Relay of newly-stored chunks** (`Relayer::process_stacker_db_chunks`) only broadcasts a chunk after `tx.try_replace_chunk` (same signature-checked gate) succeeds; failures (including bad signer) are dropped with a `continue`, not relayed. [4](#0-3) 

- The signature check itself (`SlotMetadata::verify`) recovers the pubkey from the signature over `(slot_id, slot_version, data_hash)` and compares its hash to the registered owner address, so mismatched signer, corrupted data hash, or unrecoverable/forged signatures all fail closed (return `Ok(false)`/`Err`, never silently accepted). [5](#0-4) 

- Test coverage explicitly confirms this fail-closed behavior for wrong-signer signatures, unverifiable/malformed signatures, and forged empty signatures, including on the "FutureView" buffering branch that could otherwise have been an interesting place for a validation bypass. [6](#0-5) [7](#0-6) 

I did not find a case in this scope where a chunk is stored or relayed without a valid owner signature, nor an auth gate that fails open. Given the external report is about CI/build-pipeline hygiene (unrelated to this repo's runtime code paths), and my own review of the actual StackerDB write/gossip code shows consistent signature enforcement at every layer, there is no valid analog vulnerability to report here.
