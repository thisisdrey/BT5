### Title
Unbounded array allocation from attacker-controlled length in `ValidateMultiSign` precompile leads to node crash via uncaught exception - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The FFmpeg report describes an integer-overflow when a length/size value taken from untrusted, attacker-crafted input is used to compute a buffer size in `g729_parse()`, causing out-of-bounds memory access. The closest reachable analog in java-tron is the `ValidateMultiSign` TVM precompiled contract, where attacker-controlled 32-byte words from the smart-contract call data (`rawData`) are converted with `intValueSafe()` and used directly as array lengths/offsets without bounds validation before array allocation, in `extractBytesArray`/`extractSigArray`/`extractBytes32Array` [1](#0-0) .

### Finding Description
`ValidateMultiSign.execute()` parses the raw call data into 32-byte `DataWord` words via `DataWord.parseArray(rawData)`, then reads header fields such as `words[3]` directly as an array index without checking that `words[3].intValueSafe() / WORD_SIZE` is within the bounds of `words` [2](#0-1) . This index and the subsequent calls into `extractSigArray`/`extractBytesArray` happen **before** the try/catch block that wraps only the signature-weight computation loop, so any exception thrown while resolving the header offset or building the signature array (e.g. `ArrayIndexOutOfBoundsException`, `NegativeArraySizeException`, or `OutOfMemoryError`) is not caught by that inner `try { ... } catch (Throwable t)` block [3](#0-2) .

Inside `extractBytesArray`, the `len` value comes straight from `words[offset].intValueSafe()`, which returns up to `Integer.MAX_VALUE` for any DataWord that fits in 4 bytes, and is used unchecked to allocate `new byte[len][]` [4](#0-3) . The only mitigation (`MAX_SIZE` check on `sigArraySize`) is applied *after* array construction has already occurred and only guards the `allowTvmSelfdestructRestriction()`-enabled path via `extractSigArray`; when that feature flag is disabled the legacy `extractBytesArray` path performs no size cap at all before allocation [5](#0-4) . `extractBytes` then performs `Arrays.copyOfRange(data, offset, offset + len)` with attacker-controlled, unchecked `offset`/`len` values derived from further arithmetic (`(bytesOffset + offset + 2) * WORD_SIZE`), which can integer-overflow or exceed array bounds and throw an uncaught `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` [6](#0-5) .

### Impact Explanation
Any account can trigger the `ValidateMultiSign` precompile by invoking a smart contract that calls the corresponding precompiled address with crafted call data. A crafted `words[3]` header offset or huge length word can cause a `new byte[Integer.MAX_VALUE][]` allocation attempt (`OutOfMemoryError`) or an out-of-bounds array index (`ArrayIndexOutOfBoundsException`) inside `PrecompiledContracts.execute`. Because this failure path lies outside the local try/catch, the exception propagates up through the TVM execution stack. Depending on how the outer VM/transaction executor handles unexpected runtime exceptions versus the TVM's own checked exception hierarchy, this can manifest as a full node crash (unhandled Error/RuntimeException) rather than a graceful contract revert, which is a node-crash/halt condition — a category explicitly in scope per the validation rules.

### Likelihood Explanation
The precompile is reachable from any unprivileged account by simply crafting and sending a transaction that triggers a contract call to the `ValidateMultiSign` precompiled contract address with malformed call data; no special privileges or state are required. This makes exploitation straightforward for any transaction broadcaster.

### Recommendation
Add explicit bounds validation immediately after decoding `words[3]`/header offsets (verify the computed index is `< words.length`) and clamp/validate `len` in `extractBytesArray`/`extractBytes32Array`/`extractSigArray` against a sane `MAX_SIZE` **before** allocating any array, mirroring the check already applied to `extractSigArray`'s `MAX_SIZE` guard. Wrap the entire `ValidateMultiSign.execute()` body (not just the inner weight-computation loop) in a broad `catch (Throwable)` that safely returns `Pair.of(true, DATA_FALSE)` on any parsing failure, consistent with the safety pattern used elsewhere in `PrecompiledContracts`.

### Proof of Concept
1. Deploy or use any contract that performs a `staticcall`/`call` to the `ValidateMultiSign` precompiled address (as documented in `PrecompiledContracts.getContractForAddress`).
2. Craft `rawData` such that `words[3]` encodes an offset whose `/WORD_SIZE` index exceeds `words.length`, or such that the word at the resolved offset (`len`) is a large value like `0x7FFFFFFF`.
3. Submit the transaction; `execute()` computes `words[words[3].intValueSafe() / WORD_SIZE]` (out-of-bounds read) or calls `extractBytesArray`/`extractSigArray`, which allocates `new byte[len][]` with `len` near `Integer.MAX_VALUE`, outside of any local exception handling [5](#0-4) .
4. Observe uncaught `ArrayIndexOutOfBoundsException`/`OutOfMemoryError` propagating out of the precompile execution path.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
