### Title
Unbounded reserve-ratio dependency in `ExchangeInjectContract` / `ExchangeWithdrawContract` allows front-run of double-sided liquidity operations - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` (and analogously `ExchangeWithdrawActuator`) computes the counter-asset amount (`anotherTokenQuant`) purely from the exchange pool's *current* `firstTokenBalance`/`secondTokenBalance` ratio at execution time, and then unconditionally debits/credits that computed amount from the user's account, with no user-supplied bound on the derived amount. [1](#0-0) 

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected`/min-or-max bound field, unlike `ExchangeTransactionContract` which explicitly carries an `expected` field for slippage protection. [2](#0-1) 

In `ExchangeInjectActuator.execute()`, the counter-token amount is derived directly from the live pool ratio (`secondTokenBalance * tokenQuant / firstTokenBalance` or the symmetric case) and then that exact `anotherTokenQuant` is deducted from the caller's balance/asset, with the pool balances updated to the new ratio: [3](#0-2) 

The same pattern (`bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)`) is used again in validation, still based on whatever the pool ratio is at validation/execution time: [4](#0-3) 

`ExchangeWithdrawActuator` has the identical structure — deriving `anotherTokenQuant` from the live ratio and crediting it back to the user without any bound check: [5](#0-4) 

By contrast, `ExchangeTransactionActuator` (a swap, not a double-sided deposit) *does* protect the caller: it reads `contract.getExpected()` from `ExchangeTransactionContract` and enforces it against the AMM-computed output. [6](#0-5) [7](#0-6) 

This is exactly the bug class in the DODO report: an operation that mints/settles an amount based on the pool's instantaneous reserve ratio, without a slippage bound supplied by the caller, is reachable by an anonymous account. An attacker can submit `ExchangeTransactionContract` (a normal, unprivileged swap) transactions to shift `firstTokenBalance`/`secondTokenBalance` immediately before a victim's `ExchangeInjectContract` (or `ExchangeWithdrawContract`) lands in the same block, causing the victim's fixed `quant` of `token_id` to be matched against a manipulated `anotherTokenQuant` for the paired asset — forcing the victim to pay materially more of the second asset than intended (inject) or receive materially less back (withdraw), with the difference captured by the pool/attacker.

### Impact Explanation
A victim who submits `ExchangeInjectContract`/`ExchangeWithdrawContract` has no way to bound the derived counter-asset amount. An attacker who front-runs with `ExchangeTransactionContract` swaps can force the victim to lose value on injection (overpay the second asset relative to fair value) or on withdrawal (receive less than fair value), directly transferring value from the victim to whoever benefits from the skewed post-transaction pool state (attacker unwinding the swap afterward). This is an unauthorized loss of user funds reachable purely through unprivileged, broadcastable transactions (`ExchangeTransactionContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`), matching the Medium severity of the original finding.

### Likelihood Explanation
`ExchangeCreate`/`Inject`/`Withdraw`/`Transaction` contracts are all standard, permission-less transaction types processed by ordinary actuators; anyone can create an exchange pair and anyone can trade against or inject/withdraw from it. Front-running via transaction ordering within a block (or across adjacent blocks by a witness/relayer, though not required — any user racing to be included first suffices) is a standard MEV-style attack pattern, making this practically exploitable whenever a bot monitors the mempool for pending `ExchangeInjectContract`/`ExchangeWithdrawContract` transactions.

### Recommendation
Add a caller-specified bound (e.g., `expected`/`min_another_token_quant` for inject, `max_another_token_quant` or a `min` for withdraw) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, mirroring the `expected` field already present on `ExchangeTransactionContract`, and enforce it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` validate/execute before mutating balances.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` from victim specifying `token_id = firstTokenID`, `quant = Q`.
2. Attacker submits an `ExchangeTransactionContract` swap that shifts `firstTokenBalance`/`secondTokenBalance` so the ratio `secondTokenBalance/firstTokenBalance` increases, and gets it included first (via fee/ordering or same-block placement).
3. Victim's `ExchangeInjectActuator.execute()` now computes `anotherTokenQuant = floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)` against the post-swap, attacker-manipulated balances (lines 73-74 of `ExchangeInjectActuator.java`), forcing the victim to deduct a larger amount of the second asset than they would have at the pre-manipulation ratio — with no `expected`/bound field in `ExchangeInjectContract` to reject this outcome.
4. Attacker reverses their swap afterward, extracting the difference as profit while the victim's deposit settles at an unfavorable ratio. [8](#0-7)
