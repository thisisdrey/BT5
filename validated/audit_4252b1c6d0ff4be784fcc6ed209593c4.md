### Title
Attacker fills victim's per-account token set to `MAX_TOKENS_PER_USER` via dust deposits, blocking new collateral deposits, transfers and debt issuance - (`contracts/DepositToken.sol` / `contracts/Pool.sol`)

### Summary
`Pool.addToDepositTokensOfAccount` enforces a combined cap of `MAX_TOKENS_PER_USER = 30` across `depositTokensOfAccount` + `debtTokensOfAccount` and reverts with `UserReachedMaxTokens` once reached. Because `DepositToken.deposit(amount_, onBehalfOf_)` and `DepositToken.transfer`/`transferFrom` are permissionless and add the recipient to the set whenever the recipient's balance goes from `0` to non-zero, an unprivileged attacker can stuff a victim's set with dust positions in every registered collateral, permanently (until the victim manually unwinds each dust position) preventing the victim from acquiring any *new* deposit or debt token.

### Finding Description
- `DepositToken.deposit` accepts an arbitrary `onBehalfOf_` beneficiary and mints deposit tokens to it (`_mint`), which calls `pool.addToDepositTokensOfAccount(account_)` on first receipt. [1](#0-0) 
- `_mint` adds the token to the per-account list only when `_balanceBefore == 0`. [2](#0-1) 
- `Pool.addToDepositTokensOfAccount` is guarded by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts `UserReachedMaxTokens` when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`. [3](#0-2) [4](#0-3) 
- The same revert path is hit by `DepositToken._transfer`/`transferFrom` (deposit tokens sent to the victim) and by `DebtToken` issuance (`addToDebtTokensOfAccount`), since the cap is shared. [5](#0-4) [6](#0-5) 

Attack path (fully unprivileged):
1. For each registered deposit token `d_i`, attacker calls `d_i.deposit(1 wei of underlying, victim)` — requires only dust of each underlying collateral, paid once per token.
2. `depositTokensOfAccount[victim]` grows by one entry per token until the combined length hits 30.
3. Thereafter, any action that would add a *new* token to the victim's set reverts: deposits into a collateral type the victim doesn't hold yet, incoming `transfer`/`transferFrom`/`seize` of a new deposit token, and issuance of a new debt token (`DebtToken.issue`/`mint` → `addToDebtTokensOfAccount`).

### Impact Explanation
The victim is blocked from adding collateral of a type they do not already hold and from taking new debt-token positions. If the victim's position becomes unhealthy (price move or interest accrual) and their existing collateral types are insufficient, they cannot top up with a different collateral — `debtPositionOf`-driven liquidations proceed while rescue deposits revert — leading to forced liquidation and loss of collateral value. The dust positions can be unwound by the victim (`withdraw` burns the dust and removes the entry via `removeFromDepositTokensOfAccount`), but each removal costs a transaction and the attacker can re-stuff emptied slots, making this a persistent griefing / temporary freezing of the victim's ability to manage their position. This is the on-chain analog of the CVE's class: repeated cheap writes grow a bounded resource until all dependent operations fail (denial of service via resource exhaustion).

### Likelihood Explanation
- Entry point is permissionless: `deposit` has only `whenNotPaused nonReentrant onlyIfDepositTokenExists` and explicitly accepts an arbitrary `onBehalfOf_`. No role, allowance, or `SynthContext` restriction applies to the beneficiary. [7](#0-6) 
- Cost is bounded: attacker needs a 1-wei deposit per distinct deposit token; feasibility requires the pool to have enough registered deposit tokens (+ existing debt tokens) to reach 30. If the deployed pool has fewer than 30 total tokens, the attack cannot saturate the cap — this is the main constraint and depends on deployment configuration.
- No modifier stops it: `onlyIfAdditionWillNotReachMaxTokens` checks the *victim's* count, not the sender's; the victim has no way to opt out of receiving deposit tokens.

### Recommendation
- Let the owner of a position remove entries without holding a balance, or allow a "sweep" entry point (`removeFromDepositTokensOfAccount` gated to the account itself for zero-balance tokens) so recovery is one batched call.
- Alternatively, exempt `onBehalfOf_ != msg.sender` first-deposit paths, or require a minimum first deposit amount to make stuffing economically non-viable.
- Consider decoupling the shared cap (separate limits for deposit vs. debt tokens) so dust in one list cannot block the other.

### Proof of Concept
```solidity
// Foundry, fork of a deployed Pool with N registered DepositTokens
function test_fillVictimTokenSet() public {
    address victim = makeAddr("victim");
    address[] memory dtokens = pool.getDepositTokens();

    // Victim starts with one normal position
    dealUnderlyingAndDeposit(victim); // depositTokensOfAccount[victim].length == 1

    // Attacker dust-deposits every other collateral on behalf of victim
    for (uint i = 0; i < dtokens.length && pool.getDepositTokensOfAccount(victim).length < 30; i++) {
        IERC20 underlying = dt[i].underlying();
        deal(address(underlying), attacker, 1);
        underlying.approve(address(dt[i]), 1);
        vm.prank(attacker);
        dt[i].deposit(1, victim); // mints dust, addToDepositTokensOfAccount(victim)
    }

    // Victim can no longer deposit a new collateral type
    vm.prank(victim);
    vm.expectRevert(UserReachedMaxTokens.selector);
    newCollateralToken.deposit(100e18, victim);

    // Victim can no longer receive a new deposit token
    vm.prank(holder);
    vm.expectRevert(UserReachedMaxTokens.selector);
    someDepositToken.transfer(victim, 1);

    // Victim can no longer issue a new debt type
    vm.prank(victim);
    vm.expectRevert(UserReachedMaxTokens.selector);
    newDebtToken.issue(1e18, victim);
}
```
Reproduction requires the pool to have enough registered deposit/debt tokens for the attacker's deposits plus the victim's existing tokens to reach `MAX_TOKENS_PER_USER = 30`; on deployments with fewer registered tokens the cap cannot be saturated and the finding does not apply.
