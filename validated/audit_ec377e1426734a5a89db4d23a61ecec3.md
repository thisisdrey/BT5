Based on the investigation, I found a legitimate analog to the "poisoning state before the entity exists" bug class in java-tron's CREATE2 contract-creation / resource-delegation interaction. I was not able to fully verify every downstream consequence (I ran out of tool budget before reading `AccountCapsule.clearDelegatedResource()` and `UnDelegateResourceActuator` in full), so I flag that gap explicitly below.

### Title
CREATE2 deployment onto a pre-funded address only clears legacy (FreezeV1) delegated-resource state, leaving FreezeV2 delegation records poisoned - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
Any address in TRON can be turned into an `AccountCapsule` before a contract is ever deployed there, simply by sending it TRX or by delegating TRON Power/resources to it (as long as the address is not yet typed `Contract`). An attacker can predict a `CREATE2` target address and "pre-poison" it with FreezeV2 resource-delegation state before the legitimate contract is deployed. When the real `CREATE2` deployment later lands on that address, `Program.createContractImpl` upgrades the account to `AccountType.Contract` and calls `AccountCapsule.clearDelegatedResource()` — but this only clears the legacy (FreezeV1) delegation fields, not the FreezeV2 "acquired delegated" balances or the off-account `DelegatedResourceStore` / `DelegatedResourceAccountIndexStore` records that reference the same address.

### Finding Description
`DelegateResourceActuator.validate()` requires the `receiverAddress` to already exist in `AccountStore` and to not be of type `Contract`: [1](#0-0) [2](#0-1) 

This means an attacker can (a) create a `Normal` account at a predicted `CREATE2` address by sending it TRX (implicit account creation is a documented, reachable path via `TransferActuator`): [3](#0-2) 

and then (b) delegate FreezeV2 bandwidth/energy resources to that Normal account, since it exists and is not yet a contract, populating `receiverCapsule.addAcquiredDelegatedFrozenV2BalanceFor...` on the account and writing a `DelegatedResourceCapsule`/`DelegatedResourceAccountIndexStore` entry keyed to that address: [4](#0-3) 

The project's own test suite (`FreezeTest.testFreezeAndUnfreezeToCreate2Contract`) demonstrates that the legacy FreezeV1 opcode path allows exactly this pattern — delegating/freezing to a `CREATE2`-predicted address before deployment — and that the mitigation applied in `Program.createContractImpl` for the collision is to call `existingAccount.clearDelegatedResource()` when upgrading the account to `Contract` type: [5](#0-4) [6](#0-5) 

However, `clearDelegatedResource()` is the legacy (V1) clearing routine. Separately, `Program.freezeV2Check()` explicitly treats `delegatedFrozenV2BalanceForBandwidth/Energy` and the `unfrozenV2` list as distinct state that must independently be checked/cleared (it is used to gate `suicide`, not `CREATE2` landing): [7](#0-6) 

There is no equivalent FreezeV2 check or clearing step invoked in `createContractImpl` when a pre-existing account is converted into a contract via `CREATE2`. This mirrors the Teller `commitCollateral` bug class: state (here, resource delegation) is attached to an identifier (an address) before the "real" entity (the deployed contract) exists, and the entity creation path fails to invalidate/clear that pre-existing state for the resource model that was actually left unguarded (FreezeV2), even though the developers clearly intended to guard against this class of collision (as shown by the V1 clearing code and dedicated `Create2Test`/`FreezeTest` cases).

### Impact Explanation
If FreezeV2 delegation records survive a `CREATE2` collision:
- The deployed contract inherits phantom "acquired delegated" bandwidth/energy balances it never legitimately received, corrupting the resource/energy accounting used for `TriggerSmartContract` execution and energy metering for that contract.
- The stale `DelegatedResourceStore`/`DelegatedResourceAccountIndexStore` entries still list the attacker as the delegating owner toward the (now-)contract address, potentially letting the attacker later invoke `UnDelegateResourceContract` against the contract's resource state, since the actuator keys off the owner/receiver address pair rather than account type at delegation time.
- This can manifest as an availability/DoS impact on the contract (its effective energy/bandwidth limit is influenced by attacker-controlled, uncleared delegation records) or resource-accounting corruption that a malicious deployer/attacker can manipulate — falling under "unbacked" resource state and potential unauthorized account operation.

### Likelihood Explanation
Reachability is straightforward and requires only unprivileged, signed transactions: a `TransferContract` (or `TransferAssetContract`) to implicitly create the account at the predicted address, followed by a `DelegateResourceContract` (FreezeV2) to that address, both processed through the normal actuator/API path. No special privilege is required. The main mitigating factor is that `CREATE2` addresses must be predicted in advance (deterministic from sender + salt + init-code hash), and the attacker/deployer relationship (who controls the factory salt) determines whether this is self-inflicted or exploitable against a victim's factory pattern (e.g. deterministic-address wallet factories, counterfactual deployments), which is a common pattern in production dApps.

### Recommendation
In `Program.createContractImpl` (and any other code path that upgrades a pre-existing `AccountCapsule` to `AccountType.Contract`, e.g. `HistoryBlockHashUtil.deploy`), when `existingAccount != null` and it is being converted to a contract, also:
- Clear `delegatedFrozenV2BalanceForBandwidth` / `delegatedFrozenV2BalanceForEnergy` and `acquiredDelegatedFrozenV2Balance*` fields on the account, and clear `unfrozenV2List`.
- Purge or invalidate any `DelegatedResourceStore` / `DelegatedResourceAccountIndexStore` entries associated with that address (as owner or receiver) as part of the same atomic upgrade, or explicitly forbid `CREATE2` from landing on an address that has any outstanding FreezeV2 delegation records (analogous to disallowing delegation to `Contract`-type accounts in `DelegateResourceActuator`).

### Proof of Concept
1. Attacker/deployer computes the deterministic `CREATE2` address for a planned contract deployment (factory address + salt + init code hash), as done in `Create2Test`/`FreezeTest.getCreate2Addr`.
2. Attacker sends a `TransferContract` transaction of a small TRX amount to the predicted address, causing `TransferActuator` to implicitly create a `Normal` `AccountCapsule` there (`actuator/src/main/java/org/tron/core/actuator/TransferActuator.java:48-58`).
3. Attacker (having frozen TRX for FreezeV2 resources) submits a `DelegateResourceContract` transaction with `receiverAddress` = predicted address; `DelegateResourceActuator.validate()` accepts it since the receiver exists and is `Normal` type, and `execute()` writes `acquiredDelegatedFrozenV2Balance*` on the receiver plus `DelegatedResourceStore`/`DelegatedResourceAccountIndexStore` entries (`actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java:313-325`).
4. The victim (or attacker) deploys the real contract via `CREATE2` to that same address. `Program.createContractImpl` finds `existingAccount != null`, upgrades it to `AccountType.Contract`, and calls only `existingAccount.clearDelegatedResource()` (`actuator/src/main/java/org/tron/core/vm/program/Program.java:844-852`) — the V2 delegation fields and store entries from step 3 are not cleared.
5. The resulting contract now carries attacker-influenced FreezeV2 delegation state, and the stale `DelegatedResourceStore` entry still allows the attacker to submit `UnDelegateResourceContract` referencing the contract address as receiver.

**Confidence caveat:** I was unable to inspect the full body of `AccountCapsule.clearDelegatedResource()` or `UnDelegateResourceActuator.validate()`/`execute()` before the session ended, so the exact downstream exploitation mechanics of the leftover `DelegatedResourceStore` entry (e.g., whether `UnDelegateResourceActuator` also independently blocks contract-type receivers) are not fully confirmed. This should be verified in a follow-up session to determine the precise severity (whether it is purely an accounting/availability bug or enables actual fund/resource extraction).

  private boolean freezeV2Check(AccountCapsule accountCapsule) {
    if (!VMConfig.allowTvmFreezeV2()) {
      return true;
    }
    long now = getContractState().getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();

    boolean isDelegatedResourceEmpty =
        accountCapsule.getDelegatedFrozenV2BalanceForBandwidth() == 0
            && accountCapsule.getDelegatedFrozenV2BalanceForEnergy() == 0;
    boolean isUnFrozenV2ListEmpty =
        CollectionUtils.isEmpty(
            accountCapsule.getUnfrozenV2List().stream()
                .filter(unFreezeV2 -> unFreezeV2.getUnfreezeExpireTime() > now)
                .collect(Collectors.toList()));

    return isDelegatedResourceEmpty && isUnFrozenV2ListEmpty;
  }
