### Title
Unbounded certificate detail lists parsed and allocated before signature/CA verification during handshake - (File: `cert/cert_v2.go`)

### Summary
An attacker who does not hold a valid CA-signed certificate can send a handshake message whose embedded certificate contains an oversized `networks`, `unsafeNetworks`, or `groups` list. `unmarshalDetails` in `cert/cert_v2.go` parses every entry in these lists into heap-allocated slices/strings and runs `netip.Prefix.UnmarshalBinary` on each one, all before the certificate signature is verified against the CA pool. This mirrors the Berachain finding: extra/unvalidated items are iterated over and processed (allocating memory, doing computation) even though they will ultimately be rejected, wasting CPU and memory on every recipient that processes the handshake.

### Finding Description
`unmarshalCertificateV2` bounds only the overall encoded certificate to `MaxCertificateSize` (65536 bytes) [1](#0-0) , but it delegates detail parsing to `unmarshalDetails`, which loops over the `TagDetailsNetworks`, `TagDetailsUnsafeNetworks`, and `TagDetailsGroups` sub-fields with no cap on the *number* of entries — only a per-entry length cap (`MaxNetworkLength`) is enforced [2](#0-1) . Because each network/group entry can be as small as a couple of bytes, an attacker can pack thousands of entries into a single ~64KB certificate, each of which is appended to a slice and, for networks, run through `netip.Prefix.UnmarshalBinary`.

This certificate unmarshal path is reachable from an unauthenticated handshake: `Machine.processPayload` calls `validateCert` on the payload's `Cert` field before the peer has been authenticated (`handshake/machine.go` lines 285-337, calling `m.validateCert(payload)` at the `expectsCert` branch) [3](#0-2) . The actual signature check against the CA pool happens later, so all of this list-parsing and allocation work is paid for by the recipient regardless of whether the certificate is ultimately rejected as untrusted — directly analogous to the BeaconBlock report where "ignored" extra transactions are still iterated over and their results computed before being discarded.

### Impact Explanation
**Medium** - Any external attacker with no valid certificate can send crafted handshake stage-1/continuation packets carrying certificates packed with many small network/group entries. Every node that processes an inbound handshake (including lighthouses, which by design accept handshakes from unknown addresses) pays CPU and memory cost proportional to the entry count before rejecting the certificate at verification time. Repeated or parallel handshake attempts from spoofed sources amplify the effect since UDP handshake packets are cheap for an attacker to generate but costly for the responder to parse.

### Likelihood Explanation
**Medium** - No credentials, prior trust relationship, or successful handshake are required; the parsing occurs during the very first message exchange (`beginHandshake` → `Machine.ProcessPacket` → `processPayload` → `validateCert` → `unmarshalCertificateV2`) [4](#0-3) . An attacker only needs network reachability to a nebula node's UDP listener.

### Recommendation
Enforce explicit maximum counts (not just per-entry byte length) on `networks`, `unsafeNetworks`, and `groups` during `unmarshalDetails`, rejecting the certificate immediately once a reasonable count threshold is exceeded, before any further allocation or `netip.Prefix` parsing is attempted.

### Proof of Concept
Construct a certificate whose ASN.1 `TagDetailsGroups` sequence contains, e.g., 30,000 minimal 1-byte UTF8String entries (well within the 65536-byte `MaxCertificateSize` cap), embed it as the `Cert` field of a stage-1 handshake payload, and send it to a nebula listener. `unmarshalDetails`'s groups loop [5](#0-4)  allocates a slice entry and a Go string for each of the 30,000 entries before the certificate is ever checked against the CA pool, causing measurable per-packet CPU/memory cost that scales with attacker-chosen entry count rather than a fixed handshake cost.
