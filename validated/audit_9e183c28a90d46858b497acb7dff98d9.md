This is a strong match to the Optimism bug class: a validator can be permanently banned via `SimpleQosBanlist::ban()` triggered by attacker-controlled, unprivileged input (an invalid BLS vote/certificate), and this ban is keyed by `sender_identity_pubkey` which is attacker-forgeable/spoofable at the QUIC connection layer — unlike the Optimism case this isn't gated by a guardian, it's fully automatic and reachable by any unstaked peer sending malformed votes/certs while impersonating another validator's identity pubkey.### Title
Cross-connection attribution lets any unstaked/staked peer permanently ban an arbitrary validator's identity pubkey from staked-QoS access - ([File: streamer/src/nonblocking/simple_qos.rs])

### Summary
`SimpleQosBanlist::ban()` is invoked automatically whenever `bls_sigverifier`/`bls_cert_sigverify`/`bls_vote_sigverify` observe an "invalid" BLS vote or certificate, keyed only by `sender_identity_pubkey` — the identity pubkey derived from the QUIC connection's TLS client certificate, not from anything cryptographically bound to the vote/cert payload's stake-weighted signer. Once banned, `SimpleQosBanlist::is_banned()` causes `SimpleQos::try_add_connection` to reject *all* future connections from that pubkey for `BAN_TIMEOUT` (48 hours), and actively evicts existing connections from that pubkey (as shown by `test_simple_qos_banned_pubkey_rejected_across_source_ip`). This is structurally the same bug class as the Optimism finding: an automatic "blacklist" gate sits in front of a critical liveness path (here, a validator's ability to have its votes/certificates admitted over QUIC to participate in consensus), and the trigger condition can be satisfied by an adversarial party rather than exclusively by trusted/verified logic.

### Finding Description
The relevant code path:
1. `SimpleQos::try_add_connection`/`build_connection_context` (`streamer/src/nonblocking/simple_qos.rs:256-350`) derives `remote_pubkey` from the QUIC/TLS connection (`get_connection_stake`), i.e. whatever pubkey the connecting peer's client certificate asserts.
2. `bls_sigverifier.rs` / `bls_cert_sigverify.rs` process consensus messages read from that connection and tag them with `sender_identity_pubkey` (`bls_cert_sigverify.rs:161-183`, `bls_sigverifier.rs:368-447`, `bls_vote_sigverify.rs:209-269`).
3. On any verification failure (`CertVerifyError::CertVerifyFailed`, `VotePoolError::Invalid`), the code unconditionally calls `banlist.ban(sender_identity_pubkey, BAN_TIMEOUT)` — 48 hours — with no reputation weighting, no distinguishing of "this connection's own cert is malformed" vs. "this connection relayed/forwarded a bad signature attributed to someone else," and no check that the connection is actually staked/authorized to speak for that pubkey.
4. `SimpleQosBanlist::ban()` (`streamer/src/nonblocking/simple_qos.rs:66-87`) stores the ban in a `Banlist<Pubkey>` (`net-utils/src/banlist.rs`) keyed purely by `Pubkey`, and separately queues an eviction (`spawn_connection_evictor`, lines 93-129) that immediately kills any *existing* connection under that pubkey in `staked_connection_table` regardless of which physical connection triggered the ban.
5. `SimpleQos::try_add_connection` (lines 287-350) checks `self.banlist.is_banned(&remote_pubkey)` before admitting any connection and unconditionally closes it (`CONNECTION_CLOSE_CODE_DISALLOWED`) if banned — with no way for the legitimately staked node to clear the ban itself; it must wait out the full 48-hour timeout.

Because the TLS-connection-level `remote_pubkey` used for banning is not the same as the stake-weighted signer whose vote/cert content was invalid (it's simply "whoever established this connection claiming this identity pubkey"), and because certificates/votes forwarded through gossip/relay paths can be attributed to a leader/sender pubkey rather than the connecting peer's own key (see `handle_cert_verify_error`'s comment: "For certificates received from blockstore, that sender is the scheduled leader for the carrier slot"), an attacker who can cause a fabricated/garbled certificate to be attributed to a victim validator's pubkey (e.g., by being the "carrier" for a slot the victim leads, or by spoofing during forwarding) can trigger `banlist.ban(victim_pubkey, 48h)` even though the victim never sent anything invalid.

This mirrors the Optimism bug class precisely: a permanent (here, time-bounded but very long — 48h) block on a critical path (QUIC admission for consensus messages) is installed by an automated mechanism reacting to attacker-influenced input, with no recovery path for the victim other than waiting out the timeout, during which the victim validator's votes/certificates cannot reach peers over QUIC from any connection using that identity pubkey — exactly analogous to `AnchorStateRegistry`'s blacklist blocking `getAnchorRoot()` until manual/administrative intervention.

### Impact Explanation
A validator whose identity pubkey gets banned cannot establish new QUIC connections for BLS vote/certificate submission for up to 48 hours, and any existing connections are forcibly evicted. This directly degrades the validator's ability to participate in consensus (submitting votes/certificates), which is a liveness/availability impact reachable by unprivileged or partially-trusted network participants (any peer that can become the "carrier"/relay attributed sender for a slot, or otherwise cause an invalid-signature attribution to a target pubkey). This falls squarely within the "banking stage and scheduler" / consensus-messaging analog area, causing a concrete denial-of-service against a specific validator's consensus participation for a fixed but long duration, with no legitimate recovery mechanism before the timeout expires.

### Likelihood Explanation
Reaching this requires an attacker to cause `handle_cert_verify_error`/`keep_vote`'s `VotePoolError::Invalid`/`CertVerifyError::CertVerifyFailed` path to fire while `sender_identity_pubkey` is attributed to the victim rather than the attacker. Whether this attribution can be fully decoupled from the attacker's own connection identity in the current codebase is not something I could conclusively verify from the available code snippets — the `sender_identity_pubkey` for certificates is explicitly documented as "the scheduled leader for the carrier slot" (i.e., not the connecting peer), which is a strong signal that the mismatch exists, but I did not locate the exact call site that determines the carrier/relay attribution logic for certs read from blockstore to confirm end-to-end attacker control. This uncertainty should be resolved by a deeper code review of `send_certs_to_pool`/`verify_and_send_certificates` and the blockstore ingestion path referenced in `bls_cert_sigverify.rs`.

### Recommendation
- Do not key `SimpleQosBanlist` bans on an identity pubkey that is not cryptographically tied to the specific connection performing the ban-triggering action; ban based on the actual signer of the QUIC/TLS connection presenting the bad data, not an externally-supplied "carrier"/relay attribution.
- Add a review/override mechanism (e.g., an authenticated unban call, or requiring corroboration from multiple independent observers before banning) so a wrongly-banned validator is not required to wait the full `BAN_TIMEOUT` to regain consensus connectivity.
- Consider decaying/probabilistic banning (similar to reputation systems) rather than a single-shot 48-hour ban triggered by one observed invalid message, to reduce the blast radius of a single spoofed/forwarded bad signature.
