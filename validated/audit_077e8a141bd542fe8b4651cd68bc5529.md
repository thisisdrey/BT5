### Title
Unauthenticated `RecvError` packet lets an attacker with no valid certificate tear down an arbitrary victim tunnel by guessing/replaying its `RemoteIndex` - (File: outside.go)

### Summary
The [M-03] Yieldy finding is a case of a privileged action (`burn`) being callable against an *arbitrary target* with no restriction to "self," because the only gate on the action is a role check rather than a check tying the action to the caller's own identity. The analogous pattern in nebula is `Interface.handleRecvError`, which acts on an arbitrary hostinfo identified purely by a 32-bit `RemoteIndex` taken from an unauthenticated, unencrypted UDP packet, with no certificate/HMAC verification and only a weak source-address check.

### Finding Description
`header.RecvError` messages are handled before any Noise/AEAD decryption and before any certificate is consulted. In `readOutsidePackets` (outside.go), packet dispatch for authenticated types happens only after `hostinfo.ConnectionState.Decrypt` succeeds [1](#0-0) , but `RecvError` is handled separately/upstream via `handleRecvError`, which never calls `Decrypt` or touches `ConnectionState` at all:

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	...
	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil { return }

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?", ...)
		return
	}

	f.closeTunnel(hostinfo)
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
``` [2](#0-1) 

The only "authentication" performed is comparing the UDP source address of the packet to the hostinfo's cached remote address (`hr != addr`) — and that check is skipped entirely (`hr.IsValid()` is false) whenever the target hostinfo has no remote set yet (e.g., a pending/roaming/relay-only tunnel). The lookup key, `h.RemoteIndex`, is a plain 32-bit value taken directly from the cleartext wire header of *every* nebula packet, so it is trivially observable/inferable by anyone who can see or brute-force traffic to the target, without ever presenting a CA-signed certificate. This mirrors the Yieldy pattern precisely: an action ("close/destroy state") that should only be triggerable by the entity that legitimately owns that state (i.e., a peer that has actually completed a verified handshake and is the "self" for that tunnel) can instead be triggered by anyone supplying the right index, because the code checks "is this index known" rather than "is this the specific authenticated party this tunnel belongs to."

`acceptRecvErrorConfig` further defaults to `recvErrorAlways`, meaning by default there is no restriction based on whether the sender's address is private/trusted either [3](#0-2) .

### Impact Explanation
An attacker with no CA-signed certificate — someone who is not a member of the mesh at all — can force-close another peer's tunnel(s) by sending a bare, unauthenticated `RecvError` header with a matching `RemoteIndex`. This is a remote state-poisoning / denial-of-service primitive: it deletes the hostinfo from both the main and pending hostmaps (`f.closeTunnel(hostinfo)` and `hm.DeleteHostInfo(hostinfo)`), destroying an established, cryptographically-authenticated tunnel state using a packet that carries zero authentication of its own. This is the direct network-protocol analog of "burn any amount of tokens from an arbitrary address" — an unrestricted third party can destroy state belonging to another verified party.

### Likelihood Explanation
Exploitability depends on the attacker learning a valid `RemoteIndex` for the target tunnel and (for tunnels that already have `GetRemote()` set) either being able to spoof the victim's real remote UDP source address or hitting a tunnel that has no remote set yet (common right after a handshake starts, for relay-only paths, or while roaming). Since `RemoteIndex` is transmitted in cleartext in every packet on that tunnel, any on-path observer (or a brute-force attempt over the 32-bit space, which is not rate-limited here) can obtain it without ever authenticating. The `recv_error` feature is enabled by default (`always`), maximizing exposure.

### Recommendation
Do not allow an unauthenticated packet to unilaterally tear down established state. At minimum:
- Require `RecvError` messages to be authenticated (e.g., HMAC'd/keyed using the tunnel's established symmetric keys) rather than accepted based solely on `RemoteIndex` + best-effort source-address matching.
- Tighten the source check so it is a strict, non-bypassable requirement (never skip when `hr` is not yet valid), and consider requiring corroborating evidence tied to the current handshake/session before deleting hostinfo.
- Consider defaulting `listen.accept_recv_error` to `private` or `never` rather than `always`, and/or rate-limiting recv_error processing per source.

### Proof of Concept
This mirrors the existing `TestCloseTunnelAuthenticated` e2e test pattern (which shows a bogus authenticated-type packet, `CloseTunnel`, is correctly rejected because that path requires successful AEAD decryption under `hostinfo.ConnectionState`) [4](#0-3) . `RecvError`, by contrast, has no such decryption gate:
1. Attacker (no certificate, not part of the mesh) observes or brute-forces a victim's `RemoteIndex` (visible in cleartext on any packet to/from that tunnel, or guessable since it's just a `uint32`).
2. Attacker crafts a bare header: `header.Encode(buf, header.Version, header.RecvError, 0, guessedRemoteIndex, 0)` and sends it via UDP to the victim's listen port, spoofing the victim's expected remote UDP address if `GetRemote()` is already set (or simply targeting a hostinfo where it is not yet set).
3. `handleRecvError` finds the hostinfo via `QueryReverseIndex`, the `hr != addr` check passes or is skipped, and `f.closeTunnel(hostinfo)` + `hm.DeleteHostInfo(hostinfo)` destroy the victim's authenticated tunnel state — with the attacker never having presented a valid certificate.

I was not able to fully verify from the index how strongly `h.RemoteIndex` values are exposed/guessable in all deployment scenarios (e.g., exact entropy versus other mitigations elsewhere in the reader/dispatch path), since the top of `outside.go` (packet-type dispatch before line ~86) and `header/header.go`'s exact field-validation logic were not fully retrieved before the tool budget ended; a Devin session with full repo access would be needed to confirm there is no additional gate (e.g., minimum-length or version checks) that meaningfully narrows this attack surface.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
