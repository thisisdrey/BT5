## Analysis

The strongest local analog to the "unchecked ERC20 return value" bug is in `ERC20Transactor`, the XCM `TransactAsset` implementation that bridges XCM asset accounting to real ERC20 balances via `pallet-revive`. Unlike the naive SafeERC20 bug, this code *does* decode-validate the boolean return value with `abi_decode_returns_validate` — but the on-chain, irreversible token movement is executed via `bare_call` *before* that validation, and a decode/validation failure only produces an `XcmError` while leaving the caller-visible `AssetsInHolding` credit ("what"/newly created `Erc20Credit`) intact for the XCM executor to trap and later re-issue via `ClaimAsset`. The `smart_contract_does_not_return_bool_fails` test confirms the exact analog scenario from the report — a token contract (`MyTokenFake`) whose `transfer` performs the real balance mutation but returns a non-boolean value instead of `true`/`false`: [3](#0-2)  The test only asserts the overall XCM message errors out; it does not assert that the underlying ERC20 balance change was reverted or that no `AssetsTrapped` double-credit occurred: [4](#0-3) 

The trap/claim mechanism (`DropAssets`/`ClaimAssets`) is generic accounting: whatever ends up in `AssetsInHolding` after an instruction errors gets trapped and can later be claimed by the relevant origin via `ClaimAsset`, minting a fresh credit back into holding: [5](#0-4) [6](#0-5) 

### Title
Non-atomic ERC20 return-value validation in `ERC20Transactor` allows real token transfer to execute while XCM asset accounting is rolled back, enabling double-credit via asset trap/claim - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` invoke `pallet_revive::Pallet::bare_call` to perform a real, state-mutating ERC20 `transfer()` call *before* validating the returned boolean via `IERC20::transferCall::abi_decode_returns_validate`. If that post-hoc validation fails (non-bool return data, or a token that returns `false`/malformed data despite having actually moved balances), the transactor function returns `Err`, but the underlying ERC20 contract state (`_balances` mapping) has already been permanently mutated. The `AssetsInHolding` credit/asset that the XCM executor associates with that same value is not rolled back to reflect the real chain state — it is either dropped as a failed instruction (in `withdraw`) or returned as `unspent` and subsequently trapped by `Config::AssetTrap::drop_assets` (in `deposit`), where it becomes claimable again later via `ClaimAsset`.

### Finding Description
- In `withdraw_asset_with_surplus`, `bare_call` sends `checking_address` a real ERC20 transfer from the user's contract-token balance. If the call succeeds on-chain but `abi_decode_returns_validate` fails to parse a valid `bool` (line 191-194) or reads `false` (line 204-207), the function returns `Err(XcmError::FailedToTransactAsset(..))`. The tokens are now sitting in the checking account with **no compensating `AssetsInHolding` credit ever created** — this is a permanent fund lock for the user, since the whole XCM program aborts and no further instruction can produce a credit for value that was never added to holding.
- In `deposit_asset_with_surplus`, `bare_call` transfers real ERC20 balance from the checking account to the beneficiary's mapped H160 address *before* the return is validated (lines 253-266, 276-298). If validation fails, the function returns `Err((what, XcmError::FailedToTransactAsset(..)))`, handing the *original* `AssetsInHolding` (`what`) — still representing the same amount — back to the XCM executor. The executor's `post_process` traps any non-empty holding via `Config::AssetTrap::drop_assets`, and that trapped value can be recovered later by executing `ClaimAsset`, which calls `AssetTransactor::mint_asset` and re-subsumes the credit into a fresh holding register.
- Because the checking account's real ERC20 balance already decreased and the beneficiary's real ERC20 balance already increased in this branch, but the abstract `AssetsInHolding` unit for the *same* value is preserved/trapped/reclaimable, the system can end up crediiting the same value twice: once via the real, irreversible on-chain ERC20 transfer, and once via the trapped/claimed `AssetsInHolding` unit that a claimant can later deposit somewhere else (e.g., back to the checking account or another beneficiary), effectively duplicating settlement for a single physical transfer.
- Existing guards (`abi_decode_returns_validate`, `did_revert()` check) only stop the *accounting layer* from crediting on the happy path; they do not make the physical ERC20 transfer conditional on that validation, so the invariant "advance state only after decode+dispatch+settlement succeed atomically" (per the Pivots section) is violated: the state mutation (`bare_call`) precedes and is decoupled from settlement validation (`abi_decode_returns_validate`).

### Impact Explanation
This is a public, unprivileged-attacker-reachable path: any account can deploy a custom ERC20-style contract on `pallet-revive` (permissionless contract deployment) whose `transfer()` performs the real balance update but returns malformed/incorrect data, then register that contract's location as an XCM asset and drive a `withdraw_asset`/`deposit_asset` sequence through `pallet_xcm::execute`. Depending on which leg fails:
- Withdraw path: user funds are permanently moved into `TransfersCheckingAccount` with no compensating credit — a fund lock affecting the *victim* (self-inflicted or attacker-crafted token, but the checking account holds unbacked value that no longer corresponds to any tracked `AssetsInHolding`).
- Deposit path: value is both physically transferred and left recoverable as a trapped/claimable XCM asset, letting an attacker/claimant reclaim the same value amount a second time via `ClaimAsset`, which is a duplicate-settlement / theft-adjacent bug matching the "duplicate settlement or payout" and "theft or unbacked mint" impact categories.

### Likelihood Explanation
Likelihood is high for the deposit-side double-credit scenario because: (1) contract deployment on `pallet-revive` is permissionless, (2) the checking-account architecture requires only that a "fake" ERC20-like contract be registered as the asset's backing contract via the existing `Matcher`/asset registration flow used by asset-hub for ERC20 assets, and (3) the codebase already contains a fixture (`MyTokenFake.sol`) and test demonstrating exactly this non-boolean-return scenario, confirming the code path is reachable and exercised, though the existing test only checks that the overall XCM errors, not that value wasn't duplicated or that state changes were reverted.

### Recommendation
Wrap the `bare_call` and the return-value validation in the same atomic/transactional boundary (e.g., using `with_transaction`, as already done for the ED-transfer path in `substrate/frame/revive/src/exec.rs`), so that if `abi_decode_returns_validate` fails or returns `false`, the underlying ERC20 storage mutation performed by `bare_call` is rolled back together with the XCM-level failure. Alternatively, perform a dry-run/state-reverting call first to validate the return value before committing the real transfer, or ensure the transactional processor guarantees rollback of `pallet_revive` storage changes whenever `ERC20Transactor` returns an `Err`.

### Proof of Concept
1. Deploy `MyTokenFake` (or any similar contract that mutates balances in `transfer()` but returns non-bool/`false` data) via `pallet_revive` — permissionless.
2. Register it as a matched ERC20 asset for `ERC20Transactor` (using the existing `Matcher`/`AccountKey20` location convention used in `asset-hub-westend` tests).
3. Execute an XCM program: `WithdrawAsset` (ERC20 asset) → `DepositAsset` to a beneficiary, following the pattern in `smart_contract_does_not_return_bool_fails`.
4. Observe: the real `MyTokenFake` balance moves in `_balances` (verifiable via `balanceOf`), while `deposit_asset_with_surplus` returns `Err` with `what` unspent, causing the XCM executor to trap that same value; a subsequent `ClaimAsset` (or `pallet_xcm::claim_assets`) extrinsic recovers an equivalent `AssetsInHolding` credit that can be deposited again — net effect: value transferred once on the real ERC20 ledger and credited a second time through the XCM asset-trap/claim mechanism.

*Note:* I was not able to fully trace whether the specific `Matcher`/asset registration used in production `asset-hub-westend` runtime config would allow an attacker-supplied ERC20 contract address to be dynamically matched without governance action (this may require the asset to already be registered as a foreign asset). This constrains real-world exploitability and could not be verified within the available tool budget — a Devin session with full repo access would be needed to confirm whether arbitrary/attacker-controlled contract addresses can satisfy `Matcher::matches_fungibles` without a privileged registration step.

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}

						))
					},
				}

			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.

		}

impl<T: Config> ClaimAssets for Pallet<T> {
	fn claim_assets(
		origin: &Location,
		ticket: &Location,
		assets: &Assets,
		context: &XcmContext,
	) -> Option<AssetsInHolding> {
		let mut versioned = VersionedAssets::from(assets.clone());
		match ticket.unpack() {
			(0, [GeneralIndex(i)]) => {
				versioned = match versioned.into_version(*i as u32) {
					Ok(v) => v,
					Err(()) => return None,
				}
			},
			(0, []) => (),
			_ => return None,
		};
		let hash = BlakeTwo256::hash_of(&(origin.clone(), versioned.clone()));
		match AssetTraps::<T>::get(hash) {
			0 => return None,
			1 => AssetTraps::<T>::remove(hash),
			n => AssetTraps::<T>::insert(hash, n - 1),
		}
		let mut claimed = AssetsInHolding::new();
		for asset in assets.inner() {
			match <T::XcmExecutor as XcmAssetTransfers>::AssetTransactor::mint_asset(asset, context)
			{
				Ok(minted) => {
					// SAFETY: Any fungible imbalances are now effectively duplicated because they
					// were not resolved when the asset was trapped (so total issuance tracks
					// trapped assets too), and now a duplicate asset was just minted.
					// To balance the system and keep total issuance constant, we drop and resolve
					// one of the duplicates. As a result, total issuance doesn't change.
					//
					// Note: This may emit Burned/Minted events even though the net issuance change
					// is zero. The mint creates a +X imbalance, and dropping the clone resolves -X,
					// resulting in no net change but potentially two events. This is an acceptable
					// tradeoff for the asset trap/claim mechanism.
					minted.fungible.iter().for_each(|(_, imbalance)| {
						let to_resolve = imbalance.unsafe_clone();
						core::mem::drop(to_resolve);
					});
					claimed.subsume_assets(minted)
				},
				Err(error) => tracing::debug!(
					target: "xcm::pallet_xcm::claim_assets",
					?asset, ?error, "Asset claimed from trap but unable to mint."
				),
			}
		}
		Self::deposit_event(Event::AssetsClaimed {
			hash,
			origin: origin.clone(),
			assets: versioned,
		});
		Some(claimed)
	}

	/// This includes refunding surplus weight, trapping extra holding funds, and returning any

	pub fn post_process(mut self, xcm_weight: Weight) -> Outcome {
		// We silently drop any error from our attempt to refund the surplus as it's a charitable
		// thing so best-effort is all we will do.
		let _ = self.refund_surplus();
		drop(self.trader);

		let mut weight_used = xcm_weight.saturating_sub(self.total_surplus);

		if !self.holding.is_empty() {
			tracing::trace!(
				target: "xcm::post_process",
				holding_register = ?self.holding,
				context = ?self.context,
				original_origin = ?self.original_origin,
				"Trapping assets in holding register",
			);
			let claimer = self
				.asset_claimer
				.as_ref()
				.or(self.context.origin.as_ref())
				.unwrap_or(&self.original_origin);
			let trap_weight = Config::AssetTrap::drop_assets(claimer, self.holding, &self.context);
			weight_used.saturating_accrue(trap_weight);
		};
