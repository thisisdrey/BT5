Confirmed — any account can create an exchange (`ExchangeCreateActuator`) with only a minimal `ExchangeCreateFee`, becoming its `creatorAddress` [1](#0-0) . Any other unprivileged account can then trade against that pool via `ExchangeTransactionContract`, which deposits their tokens into the shared pool and pays out the counter-token from the pool balance [2](#0-1) . ### Title
Exchange pool creator can instantly drain trader-contributed funds via unrestricted `ExchangeWithdrawContract` - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Any unprivileged account can become the `creatorAddress` of a bancor-style token-swap pool via `ExchangeCreateContract`, seeded with only their own initial tokens. Other unprivileged accounts subsequently deposit real value into that pool by trading against it with `ExchangeTransactionContract`. Because `ExchangeWithdrawActuator` only checks that the caller equals `exchangeCapsule.getCreatorAddress()` and that the requested `tokenQuant` does not exceed the *current pool balance* — not the creator's original contribution — the creator can withdraw the entire pool (including all funds deposited by other traders) in a single transaction at any time, with no timelock, cooldown, or governance check.

### Finding Description
`ExchangeCreateActuator.execute` lets any account create an exchange by depositing arbitrary starting balances of two tokens and become its permanent `creatorAddress` [1](#0-0) .

`ExchangeTransactionActuator.execute` allows any other account to swap tokens against the pool: the trader's sold token is added to the pool and the bought token is subtracted from the pool via `exchangeCapsule.transaction(...)`, growing the pool with externally-contributed value [4](#0-3) .

`ExchangeWithdrawActuator.doValidate` only verifies that the caller is the `creatorAddress` and that `tokenQuant`/`anotherTokenQuant` do not exceed the exchange's *current* `firstTokenBalance`/`secondTokenBalance` [3](#0-2) . There is no check limiting withdrawal to the creator's proportional share, no lock period, and no requirement of prior notice — mirroring the reported bug class where a privileged role can instantly redirect commingled funds to itself, with no registry/timelock safeguard as recommended in the external report.

### Impact Explanation
A pool creator can trade a small amount into their own pool to legitimately attract liquidity/volume from other users (or simply wait for organic trades), then call `ExchangeWithdrawContract` to withdraw up to 100% of both token balances, effectively stealing funds that other traders deposited into the pool through legitimate `ExchangeTransactionContract` calls. This is concrete unauthorized-account-operation-style theft of funds reachable purely through normal signed transactions from an unprivileged trader/creator — no SR, witness, committee, or node compromise is required.

### Likelihood Explanation
High. Creating an exchange costs only the `ExchangeCreateFee`, and any account can immediately act as its `creatorAddress`. No special permission, resource, or privileged role is required beyond being first to create the pool for a given token pair — an action any anonymous API client/transaction broadcaster can perform.

### Recommendation
Track each liquidity provider's proportional share of the pool (e.g., LP-share accounting) instead of allowing the raw `creatorAddress` to withdraw arbitrary amounts up to the full current balance. Alternatively, restrict `ExchangeWithdrawContract` withdrawals to amounts not exceeding the creator's own net-injected balance, or require a timelock/queued withdrawal mechanism so other participants can react before funds are drained.

### Proof of Concept
1. Account A calls `ExchangeCreateContract` with a small `firstTokenBalance`/`secondTokenBalance`, becoming `creatorAddress` of exchange `id` [5](#0-4) .
2. Account B (unprivileged trader) calls `ExchangeTransactionContract` repeatedly, depositing real tokens into the pool and increasing `firstTokenBalance`/`secondTokenBalance` [6](#0-5) .
3. Account A calls `ExchangeWithdrawContract` requesting `tokenQuant` equal to the full current `firstTokenBalance` (and correspondingly derives `anotherTokenQuant` from `secondTokenBalance`); `doValidate` only checks `firstTokenBalance < tokenQuant` etc., which passes since A is requesting exactly the full balance [7](#0-6) .
4. `execute` credits Account A's account with both token amounts and zeroes/reduces the exchange balances, transferring Account B's deposited funds to Account A [8](#0-7) .
