Based on my investigation, the strongest structural analog to the HoneyLocker bug is the version-negotiation step inside `handshake.Machine.validateCert`, in `handshake/machine.go`.

### Title
Handshake state machine locks in an attacker-chosen certificate version before the certificate is verified as trusted - ([File: handshake/machine.go])

### Summary
The HoneyLocker bug lets an owner authorize a "migration" based on a coarse identity check (contract codehash) and then trust the *new* target's runtime configuration without re-verifying it matches the security invariants of the source. In `handshake.Machine.validateCert`, the local `Machine`'s protocol configuration (`m.myVersion`, which selects the credential/cert version used for all subsequent local outgoing messages) is mutated based on the *peer-supplied, not-yet-verified* certificate's version field, before `m.verifier(rc)` (the CA-trust check) has run.

### Finding Description
In `handshake/machine.go`, `validateCert` recombines the peer's raw handshake certificate bytes into a `Certificate` object and checks the embedded public key matches the Noise static key: [1](#0-0) 

Immediately after that check, but *before* calling the `CertVerifier` (`m.verifier`) that performs CA trust/expiry/policy validation, the code performs "version negotiation": [2](#0-1) 

`rc.Version()` comes directly from the attacker-controlled `payload.CertVersion` field passed into `cert.Recombine` — data that has not yet been authenticated by any CA. If `m.getCred(rc.Version())` returns non-nil (i.e., we simply *possess* a credential for that other version, regardless of whether the peer's claimed version cert will ultimately verify), `m.myVersion` is switched. This mutates persistent Machine state that governs which locally-held credential is used to build all subsequent outgoing handshake messages (`marshalOutgoing` at line 407 reads `cred := m.getCred(m.myVersion)`). This is the same root-cause shape as the HoneyLocker bug: a decision that should be gated on a fully-verified identity/config match is instead made using state supplied by the not-yet-trusted party, and that decision persists in mutable local state.

### Impact Explanation
If the verifier subsequently rejects the certificate, `m.failed = true` and the Machine is abandoned, so the mutated `m.myVersion` has no further effect in that instance — this limits the severity considerably. The residual exploitable surface is narrower than the original finding: an unauthenticated peer can force a responder that holds both V1 and V2 credentials to switch its `myVersion` prior to verifying the initiator's certificate, but because a fresh `Machine` is allocated per handshake attempt (`beginHandshake` creates a new `Machine`), there is no cross-handshake persistence of the tainted decision, and a failed verification aborts that Machine outright.

### Likelihood Explanation
Likelihood is low. Reaching this code path only requires sending a first-stage handshake packet with an arbitrary `CertVersion` field and a self-signed (or garbage) certificate blob — no CA-signed certificate is needed to reach `validateCert`, satisfying the "no CA-signed certificate" reachability requirement. However, exploiting it beyond triggering the credential switch requires the verifier to still succeed with a legitimately-issued certificate of the *other* version, which is a narrow, config-dependent condition (dual-CA / dual-version deployments), and even then the observable effect is a version choice, not an authentication or confidentiality bypass.

### Recommendation
Move the version-negotiation switch (`m.myVersion = rc.Version()`) to occur only *after* `m.verifier(rc)` succeeds, so that untrusted, unauthenticated certificate data can never influence local protocol/credential state before the certificate has been proven trustworthy by the CA pool.

### Proof of Concept
Not independently reproduced in this session — the CheckAndComplete/HostInfo migration paths and additional e2e rehandshake tests I inspected (`e2e/handshakes_test.go`, `handshake_manager.go` lines 794-990) did not reveal a more directly exploitable analog within the scope constraints (they require an already-authenticated peer, which the rules explicitly reject). The PoC would require: (1) initiate a v1/v2 dual-credential responder, (2) send a stage-1 packet with `CertVersion` set to the version the responder also holds credentials for but with a certificate that fails final verification, (3) observe `m.myVersion` change before the verifier call — confirmable by unit-testing `validateCert` directly with a mocked failing verifier and asserting `m.myVersion` was already switched at the point of the verifier call. func (m *Machine) validateCert(payload Payload) error {
```go
	cred := m.getCred(m.myVersion)
	if cred == nil {
		m.failed = true
		return fmt.Errorf("%w: %v", ErrNoCredential, m.myVersion)
	}
	rc, err := cert.Recombine(
		cert.Version(payload.CertVersion),
		payload.Cert,
		m.hs.PeerStatic(),
		cred.Cert.Curve(),
	)
	if err != nil {
		m.failed = true
		return fmt.Errorf("recombine cert: %w", err)
	}

	if !bytes.Equal(rc.PublicKey(), m.hs.PeerStatic()) {
		m.failed = true
		return ErrPublicKeyMismatch
	}
```
