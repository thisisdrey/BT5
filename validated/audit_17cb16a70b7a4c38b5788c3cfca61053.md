## Analysis

The reported bug class — a user-supplied `salt` that is exposed in the mempool before confirmation, allowing an attacker to front-run and replicate the request, causing the original caller's request to permanently fail (DOS) — has a direct analog in java-tron's TVM `CREATE2` implementation.

### Title
CREATE2 salt front-running causes permanent DOS of legitimate contract deployment - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
The TVM `CREATE2` opcode derives the deployed contract address deterministically from `(senderAddress, salt, keccak256(code))` via `WalletUtil.generateContractAddress2`. Both `code` and `salt` are supplied as calldata by whoever calls the deploying (factory) contract, and this calldata is visible in the mempool prior to confirmation, exactly analogous to the `OrderProcessor.requestOrder()` salt exposure described in the external report.

### Finding Description
`Program.createContract2()` computes the new contract address as: [1](#0-0) 

using `WalletUtil.generateContractAddress2`: [2](#0-1) 

Because `senderAddress` is the calling (factory) contract's own address (constant for a given factory), the resulting deployment address is fully determined by the attacker-observable `salt` and `code` parameters passed in the triggering transaction's calldata. Any account can watch the mempool for a pending `TriggerSmartContract` transaction invoking a factory's `deploy(bytes,uint256)`-style function, extract the exact `(code, salt)` arguments, and resubmit an identical call (with higher energy/priority) to have it mined first.

When the legitimate transaction is later executed, `createContractImpl()` detects that the address is already occupied: [3](#0-2) 

and further down sets a `BytecodeExecutionException`: [4](#0-3) 

This reverts the legitimate user's create call while consuming their submitted energy/fee, permanently preventing them from deploying at their intended, pre-committed address — this is the identical “salt exposed in mempool → front-run → original request permanently fails” pattern flagged in the `OrderProcessor.requestOrder()` report. The test suite's own commented-out `create2AddressTest` explicitly demonstrates a second caller reusing the same `(code, salt)` and the original deployer's attempt failing with an `OutOfEnergyException`: [5](#0-4) 

### Impact Explanation
Any unprivileged contract-deploying transaction that relies on `CREATE2` with a caller-supplied or predictable `salt`/`code` pair (a common and recommended pattern for deterministic multi-chain deployments, counterfactual wallets, etc.) can be permanently blocked by a third party who merely copies the pending transaction's calldata into their own transaction. The legitimate deployer's transaction reverts and their intended contract address becomes permanently unusable for their code+salt combination, since `contractAlreadyExists` is a durable on-chain state, not a transient condition. This is a denial-of-service on a core, broadly-used TVM primitive reachable by any contract deployer, with no privileged access required.

### Likelihood Explanation
Exploitation requires only observing pending transactions in the mempool (or via full node broadcast) and resubmitting an equivalent transaction with sufficient fee/energy to be included first — the same trivial capability assumed in the original `OrderProcessor` report. No special permissions, staking, or SR/witness collusion are needed; only a standard signed transaction from any account.

### Recommendation
Where practical, application-level factory contracts deployed on TRON should avoid relying purely on a caller-controlled `salt` value without binding it to `msg.sender`/`tx.origin` (e.g., `salt = keccak256(abi.encodePacked(sender, userSalt))`), so a griefing party cannot cheaply reproduce another user's exact `CREATE2` call. At the protocol/documentation level, java-tron could highlight this front-running risk for `CREATE2` users, similar to well-known EVM guidance, since the underlying opcode semantics (`createContract2` / `generateContractAddress2`) are unchanged from standard EVM behavior and inherit the same front-running characteristics.

### Proof of Concept
1. Deploy a `Factory` contract exposing `deploy(bytes code, uint256 salt)` that internally calls `CREATE2` (as in `Create2Test.testCreate2`) — [6](#0-5) .
2. Victim broadcasts a `TriggerSmartContract` transaction calling `factory.deploy(testCode, salt=100)`.
3. Attacker observes the pending transaction, extracts `(testCode, 100)`, and broadcasts an identical call to the same factory with higher energy price, getting it confirmed first — deploying to the deterministic address computed by `generateContractAddress2(factoryAddress, salt, code)`.
4. When the victim's original transaction executes, `createContractImpl()` finds `contractAlreadyExists == true` and throws `BytecodeExecutionException("Trying to create a contract with existing contract address...")`, permanently failing the victim's deployment at that address while consuming their fee — mirrored by the exception path shown at [4](#0-3)  and the equivalent front-run test scenario at [7](#0-6) .

  public static byte[] generateContractAddress2(byte[] address, byte[] salt, byte[] code) {
