### Title
Broken/inconsistent `Comparator` in `ExchangeStore.getAllExchanges()` can throw `IllegalArgumentException` and crash any node serving `listExchanges` - ([File: chainbase/src/main/java/org/tron/core/store/ExchangeStore.java])

### Summary
`ExchangeStore.getAllExchanges()` sorts all `ExchangeCapsule` entries using a lambda comparator that violates the `Comparator` contract required by Java's `Collections.sort`/`List.sort` (TimSort). Any unprivileged client calling the `listExchanges` API on a full node, solidity node, or PBFT node reaches this code path with attacker-influenceable data (exchange `createTime` values, which are set from `dynamicStore.getLatestBlockHeaderTimestamp()` at the time `ExchangeCreateContract` transactions are broadcast by *any* account).

### Finding Description
The comparator is defined as: [1](#0-0) 

```java
.sorted(
    (ExchangeCapsule a, ExchangeCapsule b) -> a.getCreateTime() <= b.getCreateTime() ? 1
        : -1)
```

This comparator never returns `0` for equal elements, and critically it is not antisymmetric: for two capsules `a` and `b` with equal `createTime`, `compare(a,b)` returns `1` and `compare(b,a)` also returns `1` (should be `-1` by contract, since `compare(a,b) == -compare(b,a)` is required). This is exactly the "inconsistent comparator" bug class referenced in the analog report (CVE-2025-1932, an inconsistent comparator in `txNodeSorter` causing OOB access) — Java's `TimSort`, used internally by `Stream.sorted()`, detects contract violations for arrays/lists of length ≥ 32 (`TimSort.MIN_GALLOP`/merge-collapse invariant checks) and throws `IllegalArgumentException("Comparison method violates its general contract!")` rather than silently corrupting memory (Java's managed runtime prevents true OOB access, but the invariant violation is structurally the same root cause as the Firefox bug).

Any account can create an `Exchange` object via `ExchangeCreateContract`, handled by `ExchangeCreateActuator.execute()`, which persists a new `ExchangeCapsule` with `createTime = dynamicStore.getLatestBlockHeaderTimestamp()`: [2](#0-1) 

Because `createTime` is quantized to block header timestamp, many exchanges created within the same block (or even across many blocks if timestamps repeat/tie under certain sequencing) will have equal `createTime` values, producing the exact tie condition that breaks the comparator's contract once the list of exchanges reaches TimSort's merge-sort threshold (32 elements).

### Impact Explanation
Once the number of on-chain `Exchange` objects with colliding/near-colliding `createTime` values crosses TimSort's contract-check threshold, any call to the `listExchanges` HTTP/gRPC API (served by `Wallet.getExchangeList()`/related RPC handlers going through `ExchangeStore.getAllExchanges()`) throws an uncaught `IllegalArgumentException`. If this exception is not caught inside the API handler and propagates, the corresponding query endpoint becomes permanently unable to serve that request for any node exposing it (full node, solidity node, PBFT node) — a concrete "API the node can no longer serve" condition as called out in the analysis rules. Because `Exchange` records are permanent (there is no removal of `Exchange` objects, only trading via `ExchangeTransaction`), this is a persistent denial of service once triggered, not merely transient.

### Likelihood Explanation
Likelihood is high: creating enough `ExchangeCreateContract` transactions is cheap (bounded only by the configured `exchangeCreateFee` and token balances) and fully attacker-controlled by an unprivileged account; no special permission or witness/SR privilege is required — only the ability to submit signed transactions and have small token/TRX balances to pay creation fees for ~32+ exchange pairs, several of which are created within the same block (sharing identical `createTime`).

### Recommendation
Replace the comparator with a contract-compliant one, e.g. `Comparator.comparingLong(ExchangeCapsule::getCreateTime).reversed()`, matching the safe pattern already used elsewhere in the codebase (e.g. `WitnessStore.sortWitnesses` at [3](#0-2) ), and add defensive exception handling around the `listExchanges` query path so a future comparator regression cannot crash the query service.

### Proof of Concept
1. From an unprivileged account, broadcast ≥32 `ExchangeCreateContract` transactions (paying the exchange-create fee each time) such that multiple exchanges are created inside the same block, giving them identical `createTime` via `ExchangeCreateActuator.execute()`.
2. Call the `listExchanges` HTTP or gRPC/JSON-RPC endpoint on the node.
3. `ExchangeStore.getAllExchanges()` invokes `Stream.sorted()` with the broken comparator; once the collection size reaches the TimSort contract-check size (32 elements) with ties, `java.util.TimSort` detects the violated invariant and throws `IllegalArgumentException: Comparison method violates its general contract!`, causing the `listExchanges` query to fail for every subsequent caller on that node.
