### Title
Dust deposit-token griefing fills `MAX_TOKENS_PER_USER` and blocks a victim from adding collateral or minting new debt - (`contracts/Pool.sol`)

### Summary
`Pool` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` combined deposit+debt token entries per account via `onlyIfAdditionWillNotReachMaxTokens`. Both `DepositToken._mint` and `DepositToken._transfer` unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` whenever a balance moves from 0 to nonzero, and `deposit(amount_, onBehalfOf_)` accepts an arbitrary beneficiary. An unprivileged attacker can therefore push 1-wei dust of every supported deposit token onto any victim's per-account list, saturating the cap. From then on, any first-time mint/transfer/seize of a new deposit-token type to that victim reverts with `UserReachedMaxTokens`, and `DebtToken` issuance of a synthetic the victim doesn't already hold reverts the same way via `addToDebtTokensOfAccount`.

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert once `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30` (`contracts/Pool.sol:143-148, 216-220`).
- `DepositToken._mint` adds the token to `account_`'s list whenever `_balanceBefore == 0 && amount_ > 0` (`contracts/DepositToken.sol:485-488`); `deposit` lets the caller pick `onBehalfOf_` freely (`contracts/DepositToken.sol:211-237`).
- `DepositToken._transfer` does the same for recipients (`contracts/DepositToken.sol:517-520`), and `transfer`/`transferFrom` are public and only require the sender's balance to be unlocked (`contracts/DepositToken.sol:348-376`, `_revertIfLocked` only checks the *sender*).
- Attack sequence: attacker deposits dust underlying for each enabled deposit token (or transfers 1 wei after depositing), targeting the victim as recipient. Each transfer adds one entry to `depositTokensOfAccount[victim]`. After at most `30 - currentCount` dust transfers, every subsequent `deposit`, `transfer`, `seize` (liquidation payout to a victim that is a smart-farming/keeper position), or `DebtToken.mint`/`issue` of a not-yet-held token to that victim reverts inside `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`.
- The DoS analog to the Micrometer report (crafted inputs causing resource-exhaustion/liveness failure, CWE-400/CWE-770) holds: the attacker exhausts a bounded per-account resource using public entry points at negligible cost.

### Impact Explanation
- A victim whose position is deteriorating cannot deposit a *new* collateral type to restore health — `deposit` → `_mint` → `addToDepositTokensOfAccount` reverts — forcing liquidation they could otherwise avoid (loss via liquidation penalty/bad health).
- The victim cannot mint/issue any synthetic whose debt token they don't already hold, and cannot receive transfers or liquidation-seized collateral of a new type (`seize` → `_transfer` reverts, which can also revert `Pool.liquidate` when the seized token isn't already in the liquidator's list — a liquidator who is themselves dusted becomes unable to liquidate).
- Removing entries requires the victim to withdraw each dusted token fully (balance → 0 triggers `removeFromDepositTokensOfAccount`), i.e., the attacker imposes up to ~30 forced transactions on the victim with dust cost only — temporary freezing of collateral-management functionality plus a gas griefing asymmetry.

### Likelihood Explanation
- Fully permissionless: any EOA can call `DepositToken.deposit`/`transfer`; no privileged role, oracle manipulation, or flash capital needed beyond dust of each underlying.
- Effectiveness scales with the number of enabled deposit/debt tokens in a pool; Metronome deployments list multiple deposit and debt tokens, so saturating the 30-slot cap is cheap.
- No mitigating check exists: `_msgSender`/SynthContext modifiers only verify the token contracts, pause flags don't block transfers, and the recipient is never consulted.
- Cleanup is possible (victim withdraws dust), so the impact is a temporary freeze and forced-liquidation window rather than permanent loss — consistent with a Medium-High DoS severity.

### Recommendation
- Make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` idempotent-by-saturation-safe, or have the cap only count tokens with economically meaningful balance (e.g., a minimum dust threshold in USD) rather than any nonzero balance.
- Alternatively, allow the recipient to opt out: only add on `deposit` when `onBehalfOf_ == _msgSender()` or via an explicit enable, and let `removeFromDepositTokensOfAccount` be callable for dust balances cheaply/batched.
- Cap gas griefing by bounding the number of tokens counted in `debtPositionOf` regardless of entries (already bounded by 30, but keep), and consider removing entries for balances below a minimum.

### Proof of Concept
Hardhat (repository uses Hardhat + smock; runnable in `test/`):

```ts
import {expect} from 'chai'
import {ethers} from 'hardhat'
import {parseEther} from 'ethers/lib/utils'

// Assumes `pool` deployed with >= N deposit tokens (msdToken0..msdTokenN-1)
// and `alice` = victim holding none of them yet (or holding k < 30).

it('dust griefing fills MAX_TOKENS_PER_USER and blocks victim deposits', async () => {
  const max = (await pool.MAX_TOKENS_PER_USER()).toNumber() // 30
  const victim = alice.address
  const attacker = bob // attacker EOA with dust underlying

  // Victim's current list size (debt + deposit)
  const current =
    (await pool.getDepositTokensOfAccount(victim)).length +
    (await pool.getDebtTokensOfAccount(victim)).length

  // Attacker pushes 1-wei dust of deposit tokens the victim doesn't hold
  for (let i = 0; i < max - current; i++) {
    // attacker already holds msdToken[i] via deposit(1 wei underlying, attacker)
    await msdTokens[i].connect(attacker).transfer(victim, 1)
  }

  expect((await pool.getDepositTokensOfAccount(victim)).length +
         (await pool.getDebtTokensOfAccount(victim)).length).to.eq(max)

  // 1) Victim can no longer deposit a NEW collateral type -> reverts
  await underlying.connect(victim).approve(msdNewToken.address, parseEther('1'))
  await expect(
    msdNewToken.connect(victim).deposit(parseEther('1'), victim)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

  // 2) Victim can no longer receive/transfer a new deposit token type
  await expect(
    msdNewToken.connect(attacker).transfer(victim, 1)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

  // 3) Victim cannot issue a synthetic whose DebtToken is not already in their list
  await expect(
    msSynthDebtToken // via Pool.mint/swap path issuing a new debt token type
  ).to.be.reverted // UserReachedMaxTokens inside addToDebtTokensOfAccount
})
```

Fork variant: point at a deployed `Pool` (e.g., `deployments/mainnet/Pool.json`), impersonate an EOA, acquire dust of each listed `DepositToken` via `deposit`, and `transfer(1)` to the victim; subsequent first-time `deposit`/`seize`/`issue` reverts until the victim withdraws each dust token to a zero balance.
