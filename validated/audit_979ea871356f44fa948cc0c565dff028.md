### Title
Protocol fee on NEP-245/IMT token transfers bypassed by splitting a `TokenDiff` delta into many `|delta|==1` intents - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::token_fee` waives fees for `Nep245`/`Imt` tokens whenever the *individual intent's* `|delta| <= 1`, but the check is applied per `TokenDiff` intent rather than on the aggregate amount moved by a signer for a token in the batch. An unprivileged signer can therefore split a `k`-unit transfer of a `Nep245TokenId` into `k` separate `TokenDiff` intents (each `{token_id: -1}`, matched with corresponding `+1` deposits from a counterparty), collecting `Pips::ZERO` fee each time, whereas a single `TokenDiff` with `delta=-k` would owe `Pips::fee_ceil(k)`.

### Finding Description
The broken binding: fee owed for moving `k` units of a `Nep245TokenId` in one economically equivalent transfer, `Pips::fee_ceil(k)` (as computed when expressed as a single `TokenDiff{token_id: -k}`), should equal the fee actually collected when the same `k` units move via `k` separate `TokenDiff` intents each `{token_id: -1}`. They do not.

Code path: for each `Intent::TokenDiff` in `DefuseIntents.intents`, `Intent::execute_intent` dispatches independently to `TokenDiff::execute_intent` [2](#0-1) 
which, for each negative delta, computes `Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount)` using only that single intent's `amount = delta.unsigned_abs()`: [3](#0-2) 
`token_fee` explicitly zeroes the fee whenever `amount <= 1` for `TokenIdType::Nep245`/`Imt`: [4](#0-3) 
There is no per-signer/per-token aggregation across the multiple `TokenDiff` intents in the batch before this threshold check runs — each intent is fee-evaluated in isolation.

Exploit flow: the attacker (fee-paying side, i.e., the negative-delta "giver") signs one `MultiPayload` containing `k` `Intent::TokenDiff` entries, each `{diff: {T: -1}}` where `T` is a `Nep245TokenId`. A cooperating counterparty (could be the attacker's own second account) supplies matching `k` `TokenDiff` intents `{T: +1}` (or other tokens completing the swap). Each of the `k` calls to `Self::token_fee(T, 1, protocol_fee)` hits the `amount <= 1` branch and returns `Pips::ZERO`, so `fees_collected` stays empty across all `k` intents; the batch-level `TransferMatcher::finalize` still nets to zero because withdrawals (`k` from the giver) exactly match deposits (`k` to the receiver, with zero routed to `fee_collector`). Had the attacker submitted a single `TokenDiff{T: -k}` instead, `token_fee` would return `protocol_fee` (amount `k > 1`), yielding `fee_ceil(k) > 0` deposited into `fee_collector`, forcing the receiving counterparty's compensating delta to be discounted by that fee for `finalize` to balance (per `TokenDiff::closure_delta`/`supply_delta`). No existing guard (`MultiPayload::verify`, nonce checks, `TransferMatcher::finalize`) detects or prevents this, since `finalize` only enforces net-zero balancing per token across the batch, not fee correctness relative to aggregate amount.

### Impact Explanation
The `fee_collector` account under-collects protocol fees on all NEP-245/IMT (and, via the `TokenIdType::Imt` branch, in-memory-token) transfers whenever the transacting parties choose to structure the transfer as many unit-size `TokenDiff` legs instead of one large-magnitude delta. This directly matches the listed Critical category "protocol fees bypassed or over-collected." The attack is fully repeatable across any account and any `Nep245TokenId`/`Imt` token, and scales linearly with the number of intents included in a single signed payload (bounded only by payload/gas size, which is explicitly out of scope to consider as a mitigating factor). No third party's funds are stolen directly — the diverted value is the fee that `fee_collector` is otherwise entitled to receive.

### Likelihood Explanation
Preconditions are simple: a signer with a `Nep245`/`Imt` token balance ≥ `k`, `protocol_fee > 0`, and a willing (or self-controlled) counterparty to provide matching positive deltas. No special role, relayer key, or upgrade access is required — this is directly reachable via `execute_intents` with a normal signed `MultiPayload` containing multiple `TokenDiff` intents, which is standard unprivileged usage. Cost to the attacker is only the intents/gas needed to submit `k` small legs instead of one, which is attacker-controlled and can be minimized by choosing `k` just large enough to matter economically while avoiding gas limits.

### Recommendation
Compute the NEP-245/IMT fee-exemption threshold on the aggregate `|delta|` moved by a given signer for a given `token_id` across the whole batch (e.g., accumulate per-`(signer, token_id)` totals before evaluating `token_fee`'s `amount <= 1` guard), not on each individual `TokenDiff` intent's isolated delta. Alternatively, remove or redesign the `amount <= 1` fee exemption so it cannot be trivially satisfied by unit-splitting (e.g., base the exemption on the token's own semantics, such as a per-`token_id` supply cap of 1, rather than on the transaction's requested delta).

### Proof of Concept
`cargo test` (workspaces sandbox) plan, comparable to the existing unit tests in `contracts/defuse/core/src/intents/token_diff.rs`'s `#[cfg(test)] mod tests`:
1. Set `protocol_fee = Pips::ONE_PERCENT` (or any `> 0`), deploy defuse contract, mint/deposit `k` units (e.g. `k = 10`) of a `Nep245TokenId` MT to account `A`, and register `fee_collector`.
2. Path 1 ("aggregated"): submit one signed `MultiPayload` with `Intent::TokenDiff{A: {T: -k}}` matched by `B`'s `Intent::TokenDiff{B: {T: +(k - fee_ceil(k))}}` (using `TokenDiff::closure_delta` to compute the correct discounted counter-delta). Assert `fee_collector`'s balance of `T` after execution equals `Pips::fee_ceil(k)` (`> 0`).
3. Path 2 ("split"): reset state; submit one signed `MultiPayload` containing `k` `Intent::TokenDiff{A: {T: -1}}` entries matched by `k` `Intent::TokenDiff{B: {T: +1}}` entries. Assert `fee_collector`'s balance of `T` after execution equals `0`, while `A`'s balance of `T` decreased by `k` and `B`'s increased by `k` (full amount, no fee discount).
4. Assert the two `fee_collector` balances differ (`0 != fee_ceil(k)`), demonstrating the fee-bypass binding is broken.
