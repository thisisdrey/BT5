### Title
Rewards accrued while a DepositToken/DebtToken `totalSupply` is zero are permanently locked — first-depositor restart gap silently burns unclaimed yield - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenIndex` drops all reward accrual for any period where the tracked token's `totalSupply()` is `0`. When a token's supply later restarts from zero, the rewards emitted during the zero-supply window are never credited to any index, so they become permanently unclaimable in the distributor contract — the same "supply hits zero while obligations outstanding" edge as the slashed-vault bug class.

### Finding Description
In `contracts/RewardsDistributor.sol`:

```solidity
uint256 _totalSupply = token_.totalSupply();
uint256 _tokensAccrued = _deltaTimestamps * _speed;
uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
_newIndex = (_supplyState.index + _ratio).toUint224();
``` [1](#0-0) 

When `_totalSupply == 0`, `_ratio` is forced to `0`, but `_newTimestamp` is still advanced to `block.timestamp`. The `_tokensAccrued` for that interval are therefore permanently discarded — the index resumes accumulating from the new timestamp and the skipped emissions can never be re-attributed, since `claimRewards` only pays out `tokensAccruedOf` deltas derived from index movement.

The analog to the vault bug: `DepositToken.deposit` mints shares 1:1 (`_mint(onBehalfOf_, _deposited)`) [2](#0-1)  and `withdraw` burns them 1:1 against treasury underlying, so supply can legitimately reach `0` while `tokenSpeeds[token_]` remains positive. Any emission occurring in that window is lost, and the first redepositor cannot capture it either — it is locked in the contract forever, not donated to prior holders. The loss accrues to all future legitimate reward claimants because `_transferRewardIfEnoughTokens` only transfers strictly-accrued amounts.

### Impact Explanation
Permanent freezing/loss of unclaimed yield: reward tokens emitted (per `tokenSpeeds`) during every zero-supply interval are neither distributed nor reclaimable; they sit as a surplus balance in `RewardsDistributor` that no claim path can reach. On long-running pools where a deposit token can be fully redeemed (attacker or organic full exit), all emissions during the gap are destroyed. Repeated zero-supply cycles compound the loss.

### Likelihood Explanation
Reachable by an unprivileged user: any holder can fully `withdraw`/`repay` their position, and if they are (or coordinate to be) the sole holder, `totalSupply` hits `0` while `tokenSpeeds` stays nonzero (speeds are governor-set and independent of supply). The loss then occurs with no further action and is permanent — no pause flag, cap, or reentrancy check intervenes, since `_updateTokenIndex` runs on every mint/burn/transfer/claim.

### Recommendation
When `_totalSupply == 0`, do not advance `_supplyState.timestamp` (or roll the skipped accrual forward into a "pending rewards" bucket credited to the next non-zero index update), so emissions are deferred rather than silently discarded.

### Proof of Concept
Hardhat/Foundry sketch:

```solidity
// setup: distributor registered, rewardToken funded, governor sets speed>0 on msdToken
// 1. attacker deposits X -> sole holder of msdToken
depositToken.deposit(X, attacker);
// 2. attacker withdraws all -> totalSupply() == 0, speed still > 0
depositToken.withdraw(X, attacker);
// 3. warp T seconds; accrued = T * speed is dropped because _totalSupply == 0
vm.warp(block.timestamp + T);
// 4. attacker redeposits X
depositToken.deposit(X, attacker);
// 5. warp another T and claim: attacker only receives rewards for the second window
vm.warp(block.timestamp + T);
distributor.claimRewards(attacker);
// assert: attacker claimed ~T*speed, while ~T*speed of rewardToken remains
// locked in the distributor with no index path to claim it
assertGt(rewardToken.balanceOf(address(distributor)), tokensAccruedDuringGap);
```
