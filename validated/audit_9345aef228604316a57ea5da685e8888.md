Audit Report

## Title
Unattributed reward-token deposits into a zero-stake pool are permanently lost to the pool admin - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`deposit_reward_tokens` is a public, unprivileged extrinsic that lets any signed account transfer reward-asset tokens into a pool's holding account with no check on `total_tokens_staked` [1](#0-0) . Reward accrual is computed by `reward_per_token`, which explicitly returns the stale `reward_per_token_stored` and skips any update when `total_tokens_staked` is zero, so such deposits are never folded into the accumulator that would let a staker claim them [2](#0-1) . Since `cleanup_pool` only checks that `PoolStakers` is empty and then transfers the pot's *entire* `reducible_balance` to `pool_info.admin`, it does not distinguish admin-funded emission balance from third-party deposits made via `deposit_reward_tokens`, letting the admin capture funds it never contributed [3](#0-2) .

## Finding Description
The root cause is a mismatch between two independent pieces of state: (1) the pool's actual token balance held at `pool_info.account`, which any signed account can top up via `deposit_reward_tokens` with no precondition on stake, and (2) the reward accounting state `reward_per_token_stored`, which is driven purely by `reward_rate_per_block * elapsed_blocks` and is never advanced while `total_tokens_staked.is_zero()` [2](#0-1) . Because reward emission to stakers is computed from `reward_per_token_stored`/`reward_rate_per_block`, not from the pot's literal balance, any tokens deposited while `total_tokens_staked == 0` are never bound to any staker's claimable rewards, no matter how long the pool subsequently operates.

`cleanup_pool`'s only guard is that `PoolStakers` be empty (`stakers.is_none()`) — a condition that trivially holds immediately after `create_pool` or after all stakers fully `unstake` [4](#0-3) . It then reads `reducible_balance` of the pool account and transfers the full amount to `pool_info.admin`, with no accounting of how much of that balance was contributed by the admin's original funding versus a third-party's `deposit_reward_tokens` call [5](#0-4) . This lets the admin capture value deposited by an unrelated, unprivileged depositor, with the depositor's contribution never having been credited anywhere in `reward_per_token_stored` or any staker's `PoolStakerInfo`.

## Impact Explanation
This is a value-conservation violation: reward-asset tokens transferred by an unprivileged depositor via the public `deposit_reward_tokens` extrinsic are never attributed to the intended beneficiaries (stakers) and can be redirected entirely to the pool admin via `cleanup_pool`, without the depositor's consent and with no corresponding entry ever recorded in the pool's reward accumulator. This matches the required impact category of failing to conserve and settle value to the rightful beneficiary in a balances/assets pallet.

## Likelihood Explanation
The exploit path requires only ordinary, unprivileged actions: (1) any signed account calling the public `deposit_reward_tokens` extrinsic while a pool has zero staked tokens — a state that is trivially reached right after `create_pool` or transiently whenever all stakers `unstake` — and (2) the pool admin subsequently calling `cleanup_pool` once `PoolStakers` is empty, which is a normal, documented use of that call rather than an abuse of elevated privilege. No governance action, validator power, or compromised infrastructure is needed, and the root-cause defect (missing zero-stake guard on deposits, and no source-tracking in `cleanup_pool`) is purely a code-level gap in `pallet-asset-rewards`.

## Recommendation
- Reject deposits in `deposit_reward_tokens` when `pool_info.total_tokens_staked.is_zero()`, or immediately fold the deposited amount into `reward_per_token_stored`/staker accounting so it is properly attributable.
- In `cleanup_pool`, track and only return to the admin the balance attributable to the admin's own funding/emission schedule (e.g., via a dedicated accounting field), rather than sweeping the pool account's entire `reducible_balance`, which may include third-party deposits.

## Proof of Concept
1. `CreatePoolOrigin` creates a pool via `create_pool`; `total_tokens_staked == 0` and `PoolStakers` is empty.
2. Any signed account calls `deposit_reward_tokens(pool_id, amount)`, transferring `amount` of the reward asset into `pool_info.account` — this succeeds because there is no stake-based guard.
3. Because `PoolStakers::iter_key_prefix(pool_id).next()` is still `None`, the admin calls `cleanup_pool(pool_id)`.
4. `cleanup_pool` reads `reducible_balance` of `pool_info.account` (now including the third party's `amount`) and transfers the full balance to `pool_info.admin`.
5. `reward_per_token_stored` was never updated to reflect the deposit (since `reward_per_token` short-circuited on `total_tokens_staked.is_zero()`), so the depositor has no recorded claim anywhere in the pallet's storage; the funds are fully and permanently captured by the admin instead of the depositor.

		pub fn cleanup_pool(origin: OriginFor<T>, pool_id: PoolId) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			ensure!(pool_info.admin == who, BadOrigin);

			let stakers = PoolStakers::<T>::iter_key_prefix(pool_id).next();
			ensure!(stakers.is_none(), Error::<T>::NonEmptyPool);

			let pool_balance = T::Assets::reducible_balance(
				pool_info.reward_asset_id.clone(),
				&pool_info.account,
				Preservation::Expendable,
				Fortitude::Polite,
			);
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&pool_info.admin,
				pool_balance,
				Preservation::Expendable,
			)?;
