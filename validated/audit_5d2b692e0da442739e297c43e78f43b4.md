### Title
Blind-signing / cross-domain signature confusion enables theft via `TransactionCapsule` raw-hash signing and the `ValidateMultiSign`/`BatchValidateSign` TVM precompiles - (File: `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java`, `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The reported issue is a classic "blind signing" bug class: a wallet signs an opaque hash/message supplied by an untrusted party, and because the signing primitive has no domain separation, the resulting signature can be replayed to authorize a completely different, attacker-chosen operation (e.g., a fund transfer). java-tron's own signature stack exhibits the same root cause: a real TRON transaction is authorized by simply signing the raw SHA-256 hash of the serialized `Transaction.raw` bytes with no protocol tag/prefix distinguishing it from any other "please sign this 32-byte hash" request [1](#0-0) . At the same time, java-tron ships TVM precompiles (`ValidateMultiSign`, `BatchValidateSign`) that let any deployed contract ask an account holder to produce a raw-hash ECDSA signature over attacker-supplied data and recover/verify it on-chain [2](#0-1) . Because signing itself (via `sign(hash)`/`ECKey.sign`) is a generic raw-hash ECDSA operation with no format tag [3](#0-2) , a signature a user believes they are producing for an off-chain "authentication"/"permit" challenge is cryptographically indistinguishable from a signature over an actual `Transaction.raw` hash. This mirrors TOB-TEZORI-008: the callback/prompt data controls what gets signed and how the signature is later used, with no on-chain or on-wallet enforcement that a "message" hash cannot double as a transaction id.

### Finding Description
- Transaction authorization in java-tron is performed by signing `getTransactionId()`, which is simply `Sha256Hash.of(rawData.toByteArray())` — a bare hash with no version/domain prefix [4](#0-3) .
- Signature verification for broadcast (`validatePubSignature`/`validateSignature`) recovers the signer's address from that same bare hash and checks it against the owner/permission, with no distinguishing tag proving the signed hash was actually meant as a transaction id rather than an arbitrary message [5](#0-4) .
- Separately, the `ValidateMultiSign` and `BatchValidateSign` TVM precompiles are reachable by any contract deployer/caller and are explicitly designed to have a user sign an attacker/contract-supplied hash off-chain and have it verified on-chain against account permissions [6](#0-5)  and [7](#0-6) .
- `BatchValidateSign` in particular consumes `hash = words[0].getData()` directly from calldata with zero domain separation of any kind before invoking `recoverAddrBySign` [8](#0-7) .
- Because both flows (transaction signing and precompile-driven "message" signing) use the same primitive (`ECKey.sign(byte[] messageHash)` on a bare 32-byte SHA-256 value with no protocol/version tag) [9](#0-8) , there is no cryptographic or protocol guarantee that a hash a user is asked to sign "for authentication" via a dApp/off-chain flow cannot simultaneously be crafted so its bytes are (or are trivially made to be) the SHA-256 hash of a real, fully-formed, attacker-benefiting `Transaction.raw` (e.g., a `TransferContract` draining the victim's account). Once the victim signs that hash under the belief it's an innocuous challenge, the attacker attaches the very same signature to the prebuilt transaction and submits it to `/wallet/broadcasttransaction` (validated purely by `validatePubSignature`), and the node accepts and executes it as a fully authorized transfer.

### Impact Explanation
If a user can be induced to sign an arbitrary 32-byte hash (e.g., through an off-chain "permit"/authentication flow built around `ValidateMultiSign`/`BatchValidateSign`, or any external tool prompting "sign this hash"), the resulting signature is fully reusable as the signature for any transaction whose raw-data hash equals that value. This is a direct unauthorized-account-operation / theft-of-funds primitive: the attacker obtains a validly verifiable transaction signature for a transfer the victim never consciously approved, and the node's `validatePubSignature` path has no mechanism to reject it as "not really meant as a transaction signature." This satisfies the "concrete unauthorized account operation / theft of funds" bar.

### Likelihood Explanation
Exploitation requires a social-engineering component (tricking the victim into signing a hash whose meaning is disguised) plus infrastructure that presents such a "sign this hash" prompt, which is analogous to the external report's `galleon://` handler enticing users to authenticate. Within java-tron the mechanism enabling reuse is entirely protocol-level (no domain separation between transaction-id hashes and generic message hashes), so likelihood depends on the existence/adoption of dApp flows using `ValidateMultiSign`/`BatchValidateSign` for off-chain signature-based authorization — these precompiles are shipped and reachable by any contract, making the enabling condition present today, though it is not automatically exploitable without a companion "blind-signing" front-end.

### Recommendation
- Introduce domain separation for transaction signing: prefix the bytes hashed/signed for a `Transaction.raw` (e.g., with a fixed, sufficiently long constant not usable as a valid protobuf-encoded contract) so a transaction-id hash can never be confused with — or engineered to equal — a hash produced for an unrelated purpose.
- Apply the same domain separation to the hashes consumed by `ValidateMultiSign`/`BatchValidateSign` (they already partially do this for `ValidateMultiSign` by combining `address || permissionId || data`, but `BatchValidateSign` accepts a raw, uncombined hash directly) so that signatures produced for these precompiles cannot be reinterpreted as transaction signatures.
- Document and warn dApp/contract developers that any flow asking a user to "sign a hash" off-chain for use with these precompiles must never present the user with a hash that could plausibly also serve as (or be crafted to equal) an unsigned transaction's id.

### Proof of Concept
1. Attacker builds a real, fully valid but unsigned `Transaction.raw` (e.g., `TransferContract` from the victim's address to the attacker's address) and computes `H = SHA256(rawData.toByteArray())` — exactly what `TransactionCapsule.getTransactionId()` computes [1](#0-0) .
2. Attacker deploys/uses a contract exposing a "permit"/"login" style call that invokes `BatchValidateSign` (or `ValidateMultiSign`) and presents `H` to the victim as an innocuous "authentication challenge hash" to sign with their wallet, framed as harmless off-chain verification, similar to the `req.prompt` value in the external report.
3. Victim signs `H` with their private key using the ordinary raw-hash ECDSA signing primitive [9](#0-8) , producing signature `S`.
4. Attacker attaches `S` to the prebuilt `Transaction` from step 1 and submits it via the broadcast API; `validatePubSignature`/`validateSignature` recomputes `H` from the raw data and recovers the victim's address from `S`, and — since they match — accepts the transaction as validly signed [5](#0-4) .
5. The transfer executes, moving the victim's funds to the attacker, even though the victim never intended to authorize a transaction — only to "sign a hash" for authentication.

Note: this analysis is limited to what is indexed/available in the code search; exact wallet/HTTP broadcast entry-point wiring (`Wallet.broadcastTransaction`) was not fully re-verified line-by-line in this session, though its use of `TransactionCapsule.validateSignature` is well established elsewhere in the codebase.

  /**
   * Takes the keccak hash (32 bytes) of data and returns the ECDSA signature
   *
   * @param messageHash -
   * @return -
   * @throws IllegalStateException if this ECKey does not have the private part.
   */
  public ECDSASignature sign(byte[] messageHash) {
    ECDSASignature sig = doSign(messageHash);
    // Now we have to work backwards to figure out the recId needed to
    // recover the signature.
    int recId = -1;
    byte[] thisKey = this.pub.getEncoded(/* compressed */ false);
    for (int i = 0; i < 4; i++) {
      byte[] k = ECKey.recoverPubBytesFromSignature(i, sig, messageHash);
      if (k != null && Arrays.equals(k, thisKey)) {
        recId = i;
        break;
      }
    }
    if (recId == -1) {
      throw new RuntimeException("Could not construct a recoverable key" +
          ". This should never happen.");
    }
    sig.v = (byte) (recId + 27);
    return sig;
  }
