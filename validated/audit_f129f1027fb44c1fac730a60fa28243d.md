### Title
Fee bypass by splitting `TokenDiff` deltas into unit-amount legs for `Nep245`/`Imt` tokens - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::token_fee` treats any `Nep245`/`Imt` leg with `amount <= 1` as fee-exempt (`Pips::ZERO`), because it assumes such legs represent atomic NFT-like transfers. Since `Nep245TokenId` is also used to represent bridged fungible balances (e.g. an FT wrapped as an MT balance across Defuse deployments, confirmed by tests such as `tests/src/tests/defuse/tokens/nep245/mod.rs` and `simulate_mt_withdraw_intent`), a signer can split one economically fungible `-N` delta into `N` separate `TokenDiff` intents each carrying `diff = {token_id: -1}`, and each leg's fee computation independently hits the `amount <= 1` exemption branch.

### Finding Description
The broken binding: `sum(fee for token_id across the batch) == Pips::fee_ceil(protocol_fee, total_negative_delta_for_token_id)`.

In `TokenDiff::execute_intent` (contracts/defuse/core/src/intents/token_diff.rs:59-79), the fee for each negative delta is computed independently per intent leg:
```
let fee = Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount);
```
`token_fee` (lines 206-217) contains this logic:
```rust
match token_id {
    TokenIdType::Nep141 => {}
    TokenIdType::Nep245 | TokenIdType::Imt if amount > 1 => {}
    TokenIdType::Nep171 | TokenIdType::Nep245 | TokenIdType::Imt => return Pips::ZERO,
}
```
For `Nep245`/`Imt` token IDs, if the per-leg `amount` is exactly `1`, `Pips::ZERO` is returned unconditionally, regardless of `protocol_fee`, and no accumulation of fees across legs of the same token occurs — each `TokenDiff` intent (and even each leg within one intent's `diff` map) is fee-assessed in isolation.

`DefuseIntents` (contracts/defuse/core/src/intents/mod.rs:97-113) allows an arbitrary `Vec<Intent>` to be executed from a single signed payload, so an attacker's single `MultiPayload` signature can contain e.g. 1000 `TokenDiff` intents (or one `TokenDiff` whose `diff` includes 1000 different `token_id`s each with `delta = -1`, but crucially the *same* `token_id` can also be split across multiple sequential `TokenDiff` intents in the same signed message, since `token_fee` is evaluated once per `(token_id, delta)` pair with no cross-leg or cross-intent aggregation). Each `-1` leg needs a matching `+1` deposit elsewhere in the batch to satisfy `TransferMatcher::finalize` (contracts/defuse/core/src/engine/state/deltas.rs:267-283) — this can be satisfied by a genuine counterparty in a real Nep245-based swap (e.g., the underlying MT balance is a bridged, fungible FT position), so the split is fully compatible with a legitimate economic trade.

Existing guards do not prevent this: `MultiPayload::verify`, nonce checks, and `TransferMatcher::finalize` only enforce that deltas net to zero across the batch — they enforce balance conservation, not fee correctness. No code aggregates `amount` per `token_id` across multiple `TokenDiff` legs/intents before calling `token_fee`.

### Impact Explanation
This under-collects protocol fees credited to `engine.state.fee_collector()` via `internal_add_balance` (token_diff.rs:96-101). Any signer trading `Nep245`/`Imt`-classified balances (which include cross-deployment bridged fungible tokens, per the Nep245 token-id round-tripping tests) can reduce the *entire* fee due on that leg to zero simply by structuring their signed payload as many unit-amount `TokenDiff` intents/legs instead of one aggregate delta, while achieving the identical net balance change. This is repeatable for every trade and every account, systemically bypassing the protocol fee, matching the "protocol fees bypassed" Critical category.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs (a) a non-zero `protocol_fee`, (b) at least one `Nep245`/`Imt`-classified `TokenId` involved in a trade (readily available since bridged FT-as-MT balances are a normal path in this codebase), and (c) a counterparty (which can be themselves via a second signed intent, or a genuine solver) providing the matching `+1` deposits to satisfy the zero-sum invariant. No special role or privilege is required — this is exactly the "unprivileged signer calling `execute_intents` with a crafted `MultiPayload` batch" scenario described in the question. The only cost is a linear increase in intents/legs (gas), which is explicitly out of scope to consider as a mitigating factor per the rules (DoS/gas concerns are excluded, but gas cost as an economic deterrent is not a security control).

### Recommendation
Aggregate the total negative delta for a given `token_id` across all legs of the batch (or at least across all `TokenDiff` intents signed within the same `DefusePayload`) before computing `token_fee`, rather than evaluating `amount <= 1` per individual leg. Alternatively, restrict the `amount <= 1` fee exemption to token IDs that are provably non-fungible (e.g., only `Nep171`, and only `Nep245`/`Imt` IDs explicitly flagged as NFT-like), rather than blanket-applying it to any `Nep245`/`Imt` balance regardless of whether it represents a fungible position.

### Proof of Concept
Using a `near-workspaces`/sandbox test analogous to existing `tests/src/tests/defuse/intents/token_diff.rs`:
1. Set up a Defuse contract with `protocol_fee = Pips::ONE_PERCENT` (or any non-zero fee) and a Nep245-classified fungible token (e.g., bridge an FT into a second Defuse deployment as an MT balance, as in `simulate_mt_withdraw_intent`, so the resulting `TokenId::Nep245` represents 1000 fungible units held by the signer and a counterparty).
2. Baseline: construct one signed `TokenDiff` intent with `diff = {nep245_token_id: -1000, other_token_id: +X}` matched by a counterparty intent with `{nep245_token_id: +1000, other_token_id: -X}`. Execute via `execute_intents`, then assert `fee_collector`'s balance for `nep245_token_id` (via `mt_balance_of`) equals `Pips::ONE_PERCENT.fee_ceil(1000) > 0`.
3. Exploit: construct 1000 signed `TokenDiff` intents (or 1000 legs across a small number of intents in one signed payload), each `diff = {nep245_token_id: -1}`, matched by corresponding `+1` legs from a counterparty. Execute via `execute_intents`.
4. Assert: `fee_collector`'s balance for `nep245_token_id` after step 3 equals `0`, in contrast to the non-zero value from step 2, despite both moving the same net `1000` units — demonstrating `sum(fees_collected) == 0 != Pips::fee_ceil(protocol_fee, 1000)`.
