### Title
Missing duplicate-witness check in `VoteWitnessActuator.validate()` allows duplicate vote entries per witness - ([File: actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java])

### Summary
The reported Velocimeter bug is a class of "missing duplicate-entry validation" issue: `addFactory()`/`replaceFactory()` fail to check whether an entry is already present before pushing it into an array, allowing duplicates that later break invariants and cause a DoS when the array is iterated (`createGauge()`). The closest reachable analog in java-tron is `VoteWitnessActuator.validate()`, which accepts a `VoteWitnessContract` containing a list of `Vote{voteAddress, voteCount}` entries directly from an unprivileged, self-signed transaction, but never checks whether the same `voteAddress` appears more than once in the list.

### Finding Description
`VoteWitnessActuator.validate()` iterates over `contract.getVotesList()` and validates each vote's address and count individually, summing `voteCount` to compare against the voter's `tronPower`, but performs no distinct/duplicate check on `vote.getVoteAddress()`: [1](#0-0) 

Compare this to `AccountPermissionUpdateActuator`, where the analogous list of `Key` entries is explicitly deduplicated with `.distinct()` and a size check before being accepted, precisely the kind of validation missing in `Voter.addFactory()` per the report: [2](#0-1) 

In `countVoteAccount()` (the execute path), each `Vote` entry in the contract is applied independently via `votesCapsule.addNewVotes(...)` and `accountCapsule.addVotes(...)` inside a `forEach`, with no merging of duplicate witness addresses: [3](#0-2) 

Notably, the newer TVM-native equivalent, `VoteWitnessProcessor` (used by the `voteWitness` precompile path), already fixes this exact class of bug by merging votes for the same witness into a `Map<ByteString, Long>` (`voteMap`) before applying them: [4](#0-3) [5](#0-4) 

This asymmetry confirms that the legacy `VoteWitnessActuator` (reachable directly from a standard signed `VoteWitnessContract` transaction) lacks the duplicate-address safeguard that its TVM-native counterpart has, mirroring the "missing validation before array push" pattern from the Solidity report.

### Impact Explanation
A voter can submit a single `VoteWitnessContract` with multiple `Vote` entries pointing to the same witness address (up to `MAX_VOTE_NUMBER` entries, since that check only limits the number of `Vote` objects, not distinct witnesses). Because `accountCapsule.addVotes()`/`votesCapsule.addNewVotes()` are called per-entry without merging, the account's persisted votes list (`AccountCapsule`/`VotesCapsule`) can end up with several separate entries for the same witness. This breaks the implicit "one witness per vote" invariant maintained everywhere else in the codebase, and downstream consumers of `getVotesList()`/`getNewVotesList()` (e.g., maintenance/reward and vote-tally logic in `MaintenanceManager`) that assume unique witness keys can be affected by inflated list sizes or inconsistent per-witness aggregation. I was not able to fully verify from the available index whether `MaintenanceManager`'s vote-tally logic aggregates by witness key (which would neutralize the duplicate-entry impact) or iterates the raw list assuming uniqueness (which would not) — I was unable to retrieve the exact tally logic content within the tool budget.

### Likelihood Explanation
Trivially reachable: any account can construct a `VoteWitnessContract` with repeated `voteAddress` entries and broadcast it as a normal signed transaction. No special privileges are required, and the existing checks (`MAX_VOTE_NUMBER`, per-vote count > 0, sum ≤ tronPower) do not prevent duplicate addresses.

### Recommendation
In `VoteWitnessActuator.validate()`, add a distinct-address check on `contract.getVotesList()` (mirroring the `.distinct()` pattern already used in `AccountPermissionUpdateActuator.checkPermission()`), rejecting the transaction if any `voteAddress` appears more than once. Alternatively, port the `voteMap` merging approach from `VoteWitnessProcessor.execute()` into `VoteWitnessActuator.countVoteAccount()` so duplicate witness entries are consolidated before being written to `AccountCapsule`/`VotesCapsule`.

### Proof of Concept
1. Freeze balance to obtain `tronPower` on `OWNER_ADDRESS`.
2. Construct a `VoteWitnessContract` for `OWNER_ADDRESS` containing N `Vote` entries all with `voteAddress = WITNESS_ADDRESS` and small `voteCount` values summing to ≤ `tronPower` (test helper `getRepeateContract` in the existing test suite already builds exactly this shape): [6](#0-5) 
3. Call `VoteWitnessActuator.validate()` then `execute()` — validation passes because no duplicate-address check exists, and `countVoteAccount()` writes N separate vote entries for the same witness into `AccountCapsule`/`VotesCapsule` instead of one merged entry.
