### Title
Unbounded delay of `resolve_promise_yield_timeouts` via compute-limit saturation freezes yielded-promise deposits past their protocol-guaranteed timeout - (File: `runtime/runtime/src/lib.rs:2681-2737, 3009-3116`)

### Summary
`process_receipts` runs `resolve_promise_yield_timeouts` strictly last, after local, delayed, and incoming receipts have already consumed the shard's per-chunk `compute_limit`, and the function immediately breaks the moment `total.compute >= compute_limit` with no reserved compute budget of its own. An account that keeps its own local receipts saturating `compute_limit` every chunk can therefore indefinitely prevent the timeout queue from being drained, defeating the hard bound promised by `yield_timeout_length_in_blocks`.

### Finding Description
`process_receipts` (`runtime/runtime/src/lib.rs:2681-2719`) processes, in order: local receipts (`process_local_receipts`, :2694), delayed receipts (`process_delayed_receipts`, :2702), incoming receipts (`process_incoming_receipts`, :2710), and only then calls `resolve_promise_yield_timeouts` (:2719). Each of the first three phases loops `while` (or `for`) checking `processing_state.total.compute >= compute_limit` and pushes remaining work to the delayed queue once the budget is exhausted [1](#0-0) , but they do not reserve any portion of `compute_limit` for the timeout phase.

`resolve_promise_yield_timeouts` walks the shard-wide `PromiseYieldTimeout` FIFO queue (keyed only by a global running index via `TrieKey::PromiseYieldIndices` / `TrieKey::PromiseYieldTimeout { index }`, not partitioned per account) and breaks out of the loop as soon as `total.compute >= compute_limit`, before even checking whether the head entry's `expires_at` has passed [2](#0-1) . Because `total.compute` is a single cumulative counter for the whole chunk (`TotalResourceGuard`, reset to 0 at the start of `apply`) [3](#0-2) , and it is filled first by local/delayed/incoming receipt processing, an account that submits enough max-gas `FunctionCall` transactions each block to keep `total.compute` at or above `compute_limit` prevents the timeout-resolution loop from making any progress at all in that chunk — it exits on the very first iteration.

Since this queue is shard-global rather than per-account, this doesn't just delay the attacker's own yields: it stalls the `PromiseYieldTimeout` FIFO for every account with a pending yield on that shard, because entries are drained strictly in `expires_at`/queue order and the loop breaks unconditionally on compute exhaustion regardless of whose entry is next.

`process_incoming_receipts`/`process_delayed_receipts`/`process_local_receipts` correctly defer excess work to the delayed queue when the budget runs out, but there is no analogous "reserve" mechanism ensuring `resolve_promise_yield_timeouts` gets at least some guaranteed compute each chunk. No existing gas-metering, storage-staking, or size-limit check addresses this because the attacker's individual transactions are all valid, correctly charged, and within normal gas/compute limits — the issue is purely about scheduling priority within `process_receipts`.

### Impact Explanation
Any `PromiseYield` receipt with a deposit attached to its parked callback `FunctionCall` (e.g., an escrow/oracle-style contract using `promise_yield_create`) has that deposit effectively locked in state until the parked receipt executes — either via a real resume or via the timeout-generated `PromiseResume` produced by `resolve_promise_yield_timeouts` (:3059-3097). If this phase never runs because compute is perpetually saturated, those deposits remain frozen indefinitely, well past the protocol's `yield_timeout_length_in_blocks` bound. This is a liveness violation — freezing of user funds (not just the attacker's own) belonging to any account with a pending yield on the affected shard, matching a "freezing of user funds" bounty category.

### Likelihood Explanation
The attacker needs only an ordinary funded account: no validator, protocol, or privileged access is required. They must continuously submit enough local `FunctionCall` transactions each chunk to keep `total.compute` at `compute_limit` on the target shard. This is costly (attacker pays gas for every receipt, and NEAR's dynamic gas-price adjustment will raise costs as chunks stay full), but it is self-funded, repeatable, and requires no special conditions beyond sustained spending — fully within reach of an unprivileged attacker willing to pay for it. The attack is deterministic: as long as compute stays saturated, the timeout-resolution loop is guaranteed to break at the very first check (:3026), before evaluating any queue entry.

### Recommendation
Reserve a minimum compute/gas budget specifically for `resolve_promise_yield_timeouts` (e.g., process it before local/incoming receipts, or carve out a fixed fraction of `compute_limit` that only the timeout-resolution phase may spend) so that expired yield timeouts are guaranteed to be dequeued within a bounded number of chunks regardless of how full the rest of the chunk is.

### Proof of Concept
Test-loop integration test:
1. Deploy a contract on account `A` that calls `promise_yield_create` with a callback `FunctionCall` carrying a nonzero deposit, capturing `expires_at = block_height + yield_timeout_length_in_blocks`.
2. From the same or a different account `B` on the same shard, submit local `FunctionCall` transactions with max attached gas every block such that `total.compute` in `process_receipts` reaches `compute_limit` before `resolve_promise_yield_timeouts` runs.
3. Advance the chain past `expires_at` while continuing to submit max-gas transactions from `B` every block.
4. Assert that the timeout `PromiseResume` for `A`'s yield is *not* produced and the deposit remains locked well beyond `yield_timeout_length_in_blocks` blocks past `expires_at` (demonstrating the freeze), contrasted with a control run without the flooding transactions where the timeout resolves within one block of `expires_at`.
