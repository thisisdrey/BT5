### Title
Unstaked connection eviction based on stale `last_update` timestamps allows attacker-driven pruning of legitimate actively-streaming connections - ([File: streamer/src/nonblocking/swqos.rs])

### Summary
`SwQos::prune_unstaked_connection_table` evicts unstaked connections down to 90% capacity via `ConnectionTable::prune_oldest`, which relies on each connection's `last_update` timestamp as its "age" signal. That timestamp is only refreshed in `on_stream_finished` when a stream fully completes, not while a stream is actively in-flight, so a legitimate connection with a long-running, not-yet-finished stream can be judged "older" than an attacker's brand-new flood connections and evicted.

### Finding Description
`SwQosConnectionContext::last_update` is initialized to the connection's creation time in `build_connection_context` [1](#0-0) [2](#0-1) , and is only updated afterward in `on_stream_finished`, which stores the current timestamp when a stream is finished (i.e., closed/completed) [3](#0-2) . There is no update path that refreshes `last_update` while a stream is actively receiving data but not yet finished.

`prune_unstaked_connection_table` triggers `ConnectionTable::prune_oldest(max_connections)` whenever `unstaked_connection_table.total_size >= max_unstaked_connections`, unconditionally pruning down to 90% capacity [4](#0-3) . This is invoked for every new unstaked connection attempt via `prune_unstaked_connections_and_add_new_connection`, which is called on the `ConnectionPeerType::Unstaked` path of `try_add_connection` for every incoming unstaked connection [5](#0-4) .

Because eviction ordering is driven by `last_update` (an age-since-last-completed-stream signal) rather than any measure of current in-flight activity, an attacker who repeatedly opens brand-new unstaked connections (each starting with a fresh `last_update` at connection-build time) can outrank a legitimate connection that is mid-way through a long-lived, not-yet-finished stream (whose `last_update` is stale from before that stream started). The unstaffed connection table has no other invariant protecting connections with active un-flushed streams, so `prune_oldest` can select and evict the legitimate connection while its stream is still in flight, closing the connection and dropping that data.

I was unable to directly view the internal sort logic of `ConnectionTable::prune_oldest` in `streamer/src/nonblocking/quic.rs` (tool access exhausted before retrieval), so the exact comparator used is not independently confirmed; this finding assumes it operates on the `last_update` field passed into `try_add_connection`, per the field's name and its exclusive use as connection recency for `on_stream_finished` and `remove_connection`/`update_open_connections_stat` bookkeeping in this file.

### Impact Explanation
This is a QoS-evasion/fairness violation: an unprivileged unstaked attacker can flood the leader's unstaked connection slots to force legitimate unstaked senders' active connections to be closed mid-stream, causing data loss/aborted transaction submission and unfair starvation, contrary to the intended "prune truly idle connections first" design implied by the `last_update`/`on_stream_finished` mechanism.

### Likelihood Explanation
Feasibility depends on precise timing: the attacker needs the victim's stream to remain unfinished (e.g., large payload, throttled by `throttle_stream`/`max_streams_per_throttling_interval`) while flooding enough new unstaked connections to push `total_size` at/above `max_unstaked_connections` repeatedly. This is achievable by any unstaked remote client since `max_connections_per_unstaked_peer` and `max_unstaked_connections` are public defaults, but requires sustained connection churn and is only exploitable within the window before the victim's stream completes and refreshes `last_update`. This makes it feasible but timing-sensitive.

### Recommendation
Track and refresh connection recency on stream activity (not just completion) — e.g., have `on_stream_accepted`/periodic byte-received callbacks bump `last_update`, or add an explicit "has active un-flushed stream" flag that `prune_oldest` treats as unevictable, so `ConnectionTable::prune_oldest` cannot select connections with genuinely in-flight, actively-progressing streams.

### Proof of Concept
Integration test plan for `streamer/src/nonblocking/swqos.rs`:
1. Configure `SwQosConfig` with a small `max_unstaked_connections` (e.g., 10) and `default_for_tests()`-style single-connection-per-peer limits.
2. Establish one legitimate unstaked QUIC connection and open a long stream that sends data slowly (simulating in-flight, un-flushed data) without finishing it, so `on_stream_finished` is never called for it.
3. Spawn attacker tasks that repeatedly open new unstaked connections (from distinct source IPs/ports) until `total_size` crosses `max_unstaked_connections` multiple times, triggering `prune_unstaked_connection_table` repeatedly.
4. Assert that the legitimate connection's `CancellationToken`/connection handle is never cancelled/closed by `prune_oldest` while its stream is still open and un-finished, and that its stream data is eventually received.
5. Expected current (failing) behavior: the legitimate connection is evicted (cancellation token fires / `remove_connection` count increments for it) despite having active un-flushed data, demonstrating the starvation.

    fn prune_unstaked_connection_table(
        &self,
        unstaked_connection_table: &mut ConnectionTable<ConnectionStreamCounter>,
        max_unstaked_connections: usize,
        stats: Arc<StreamerStats>,
    ) {
        if unstaked_connection_table.total_size >= max_unstaked_connections {
            // Prune the connection table down to 90% capacity
            const PRUNE_TABLE_RATIO: f64 = 0.90;
            let max_connections = (PRUNE_TABLE_RATIO * (max_unstaked_connections as f64)) as usize;
            let num_pruned = unstaked_connection_table.prune_oldest(max_connections);
            stats
                .num_evictions_unstaked
                .fetch_add(num_pruned, Ordering::Relaxed);
        }
    }
