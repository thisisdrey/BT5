### Title
Optional/omittable price-feed updates let any caller choose a stale-but-valid Pyth price to their advantage in `liquidate`/`borrow`/`collateral-remove` - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar`'s hot-path entry points (`liquidate`, `borrow`, `collateral-add`, `collateral-remove`) take an *optional* `price-feeds` parameter that lets the caller push a fresh Pyth VAA on-chain before the health/liquidation math runs. If the caller passes `none`, no update happens and the market simply reads whatever price is currently cached in `pyth-storage-v4`, accepting it as long as it is within a fixed `max-staleness` window. Because updating is optional and entirely at the caller's discretion, any unprivileged liquidator or borrower can pick whichever of the "already-published (possibly stale)" price or a "fresh, off-chain-known" price is most favorable to them, exactly like the Flatmoney keeper bug where `priceUpdateData` could be passed as an empty array.

### Finding Description
The `write-feeds` helper is a no-op when `price-feeds` is `none`: [1](#0-0) 

Every hot-path function calls it and then proceeds to resolve prices unconditionally regardless of whether an update happened: [2](#0-1) [3](#0-2) 

Price acceptance is governed solely by a staleness/monotonicity check, not by requiring that the caller submitted the newest available data: [4](#0-3) [5](#0-4) 

`check-confidence` only bounds Pyth's self-reported confidence interval relative to the chosen price - it does not bound how far the chosen (possibly stale) price can diverge from the true current market price: [6](#0-5) 

This is structurally identical to the Flatmoney H-6 root cause: the requirement to push the latest off-chain price is *not enforced*; the caller can bypass it by omitting `price-feeds` (analogous to passing an empty `priceUpdateData` array), and as long as the resulting price passes a staleness/deviation check that isn't tight enough to catch meaningful moves, the caller effectively gets to choose between two valid prices depending on which benefits them.

Concretely, an ordinary principal can exploit this in two directions:
- **Liquidator picks the stale price.** In `liquidate`, if the *previously* on-chain-cached Pyth price for the collateral (still within `max-staleness`) makes a position look unhealthier than it truly is right now, a liquidator submits `price-feeds: none` and liquidates a position that is not actually eligible under the current true price, seizing collateral plus the liquidation penalty - direct theft of the borrower's collateral.
- **Borrower/self-liquidator picks the stale price.** In `borrow` or `collateral-remove`, the position owner (`contract-caller`) similarly omits `price-feeds` and borrows against, or withdraws collateral valued at, a stale favorable price that is still within the staleness bound but no longer reflects the true market price, extracting more debt/collateral than the position can safely support and leaving the protocol with under-collateralized debt.

Because these functions are all "hot path" entry points reachable by any unprivileged caller/position owner via `contract-caller`, this is a first-class, permissionless manipulation vector, not a DAO or privileged-actor issue.

### Impact Explanation
- Unfairly liquidating a currently-healthy position based on a stale valid price results in direct theft of the borrower's collateral at rest (Critical).
- Borrowing/withdrawing against a stale favorable price that overstates collateral value creates instantly under-collateralized debt, directly threatening protocol insolvency (Critical) since the difference is not covered by real collateral value.

### Likelihood Explanation
`price-feeds` is optional on every relevant call and there is no requirement that the submitted or cached price be the *latest* available Pythnet update — only that it be within `max-staleness` and monotonically non-decreasing versus the last recorded timestamp. Any liquidator bot or borrower already monitoring off-chain Pyth prices (a completely realistic and expected actor in this design, per the docs' own description of `price-feeds` as an opportunistic "hot path" convenience) can trivially decide whether to submit an update based on which of the two valid prices benefits them, with no additional cost beyond a normal transaction.

### Recommendation
Do not allow the choice of "update vs. don't update" to be made unilaterally by the caller when their action depends on price freshness for an adversarial outcome (borrowing, collateral removal, liquidation). Options: tighten `max-staleness` substantially and/or require that `price-feeds` always be submitted (reject `none`) for `liquidate`/`borrow`/`collateral-remove` when the cached price is older than a much smaller freshness bound relative to expected off-chain price update cadence; additionally, bound how far a "stale-but-accepted" price may diverge from a second independent oracle (e.g., DIA) rather than relying only on Pyth's self-reported confidence interval.

### Proof of Concept
1. Attacker observes off-chain (Hermes) that BTC price has just moved meaningfully away from the last price stored in `pyth-storage-v4` for the BTC feed, while the stored (stale) price is still within the configured `max-staleness` window relative to `stacks-block-time`.
2. Attacker calls `market.liquidate(borrower, sbtc-ft, usdc-ft, debt-amount, min-collateral-expected, none, none)` (passing `none` for `price-feeds`) — see call signature at [7](#0-6) .
3. `write-feeds` is a no-op ( [1](#0-0) ), so `price-resolve` reads the stale-but-still-fresh price from `pyth-storage-v4` ( [5](#0-4) ) and computes an LTV using that stale price that exceeds `LTV-LIQ-PARTIAL`, even though the true current price would keep the position healthy.
4. Liquidation executes, transferring the borrower's collateral plus penalty to the attacker, even though under the true current price the position was not liquidatable.
5. Symmetrically, a borrower can call `borrow`/`collateral-remove` with `price-feeds: none` while the stale cached collateral price is inflated relative to the true price, extracting debt/collateral in excess of what the true collateral value supports ( [8](#0-7) ).

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
