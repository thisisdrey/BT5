### Title
Unbounded `read_to_string` in `process_event` allows unauthenticated memory-exhaustion DoS against the signer event-receiver - (File: libsigner/src/events.rs)

### Summary
`process_event` in `libsigner/src/events.rs` reads the entire HTTP body of any POST to `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, or `/new_block` into a `String` via `read_to_string` with no size cap. Any TCP client that can reach the signer's bound event-receiver port can send a POST with an arbitrarily large `Content-Length` (or chunked body) and force the signer process to buffer that entire attacker-chosen size in memory before any validation occurs.

### Finding Description
`SignerEventReceiver::next_event` accepts an HTTP request via `tiny_http`'s `HttpServer::recv()` and dispatches based on URL to `process_event::<T, E>(request)`: [1](#0-0) 

Inside `process_event`, the body is read unconditionally with no upper bound before any JSON parsing, authentication, or codec-length validation: [2](#0-1) 

Unlike the `StacksMessageCodec` deserializers elsewhere in the codebase (e.g., `BlockProposalData::consensus_deserialize` at lines 179-203, which caps the inner payload with `read_next_at_most(fd, BLOCK_RESPONSE_DATA_MAX_SIZE)`), there is no analogous `MAX_MESSAGE_LEN`-style cap applied to the raw HTTP body in `events.rs`. `tiny_http`'s `Request::as_reader()` returns a reader that streams exactly `Content-Length` bytes (or the full dechunked body for chunked transfer-encoding), and `Read::read_to_string` will keep growing the `String` buffer until that declared length is exhausted or the process runs out of memory. The bound relied upon is therefore whatever limits exist inside `tiny_http` itself (if any) — not anything enforced by this crate's own code. Since none of the four dispatched routes require any secret, signature, or session state before `process_event` is invoked, an attacker with plain TCP connectivity to the bound address can trigger this with a single crafted request.

### Impact Explanation
A single unauthenticated POST with an oversized `Content-Length` (e.g., tens of gigabytes) causes the signer process to attempt to allocate and fill a buffer of that size in `body: String`, exhausting available memory and crashing or hanging the signer node. This is repeatable per TCP connection and requires no signer key, no valid StackerDB slot, and no prior handshake — matching the "Critical: remote crash/unauthenticated DoS from few messages" category, since it takes only one malicious request per connection to attempt the exhaustion.

### Likelihood Explanation
The only precondition is TCP reachability to the signer's event-receiver HTTP port (bound via `SignerEventReceiver::bind`, `libsigner/src/events.rs` lines 404-408, at whatever address is configured for the signer's event-observer endpoint). No signer key, StackerDB slot ownership, RPC secret, or admin role is required — the four routes (`/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block`) are dispatched purely on method+URL before `process_event` runs. Cost to the attacker is a single crafted HTTP request; the attack is trivially repeatable across reconnects.

### Recommendation
Impose a hard ceiling on the body size before calling `read_to_string`, e.g. reject requests whose `Content-Length` exceeds a `MAX_MESSAGE_LEN`-style constant, and/or wrap `request.as_reader()` in a `Read::take(MAX_MESSAGE_LEN)` adaptor so that even chunked or misreported bodies cannot cause unbounded allocation. This should be enforced in `process_event` (and any other body-reading dispatch path in `libsigner/src/events.rs`) prior to buffering.

### Proof of Concept
1. Start a `SignerEventReceiver::<T>::bind` on a test address (as used in `libsigner`'s existing tests for this struct).
2. Open a raw `TcpStream` to that address and write:
   `POST /new_block HTTP/1.1\r\nHost: x\r\nContent-Length: <N>\r\n\r\n` followed by `N` bytes of filler (e.g., `N` = several GB, or use chunked transfer-encoding to stream indefinitely without pre-declaring a header value that some client library might refuse).
3. Observe process memory (RSS) growth in the signer process proportional to `N`, with no rejection or early abort in `process_event` (`libsigner/src/events.rs` lines 519-533) before the read completes or the process OOMs.
4. Assert that memory usage tracks `N` unboundedly, demonstrating the missing cap — contrast with a fixed-size control request to show the code path is otherwise functional.
