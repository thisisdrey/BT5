### Title
Permissionless cross-repository object-pool linking enables cross-repository object disclosure - (File: internal/gitaly/service/objectpool/link.go, internal/git/objectpool/pool.go)

### Summary
`LinkRepositoryToObjectPool` lets a caller name an arbitrary `ObjectPool` repository (any relative path on the same storage) to link as an alternate object store for a `repository` the caller controls, with Gitaly performing only existence/well-formedness checks on the pool path, not an ownership/association check tying the pool to the target repository's project or fork network. This is analogous to the reported `route()` bug: a permissionless, unvalidated "linking" operation lets an attacker point one object at another attacker-chosen persistent object with no validation of relationship, creating unintended access to a resource (funds/objects) that was not meant to be reachable.

### Finding Description
`LinkRepositoryToObjectPool` resolves the caller-specified object pool via `poolForRequest` → `objectpool.FromProto`, which only checks that the pool path exists, resides on a valid storage, and is either a "pool repository" (by naming convention/`storage.IsPoolRepository`) or located in the storage's temp directory: [1](#0-0) 

No check is performed that the object pool actually belongs to the same project/fork network as the `repository` field being linked, i.e. there is no assertion that the target repository is (or should be) a legitimate member of that specific pool. The actual `Link` operation then simply writes the pool's relative path into the target repository's `objects/info/alternates` file: [2](#0-1) 

The RPC handler itself only validates that `repository` is a well-formed, existing repository and that the pool resolves; it does not verify authorization linking these two specific repositories: [3](#0-2) 

Once linked via the alternates file, all of the pool's objects become readable through the linked repository (`git cat-file`, `ls-tree`, clone, etc., since Git transparently resolves objects via alternates)—this is the entire purpose of the object-pool/alternates mechanism, but it assumes only rightful pool members are ever linked. Because the check that would establish "is this repository allowed to be a member of this particular pool" is not present at the Gitaly layer, if this RPC (or an equivalent path such as `FetchIntoObjectPool`/`DisconnectGitAlternates` interplay) is reachable with attacker-influenced parameters, the analog to `route()`'s permissionless-state-creation flaw applies directly: unvalidated input (`object_pool` relative path) creates persistent state (the alternates link) that grants access to assets (objects) the caller was never authorized to see, mirroring the "steal service tokens by creating a route with a known preimage" scenario, except here the "asset" is the pool's git objects rather than tokens.

### Impact Explanation
If reachable with an attacker-chosen pool path, an attacker-controlled repository could be linked to an arbitrary private object pool on the same storage, exposing the pool's full object graph (blobs, commits, trees) to the attacker's repository — a direct cross-repository object disclosure. This matches the explicitly accepted bug class "cross-repository object access." It also mirrors the DoS angle from the report: `DeleteObjectPool` documentation states "there are no safety checks in place, so if any repository is still using this object pool it will become corrupted," so an attacker who links their own accessible repository to a pool they don't legitimately belong to could also indirectly cause corruption/DoS scenarios for legitimate pool members depending on how deletion/disconnection is orchestrated.

### Likelihood Explanation
`LinkRepositoryToObjectPool`, like all Gitaly RPCs, is intended to be called only by trusted internal callers (GitLab Rails) which are expected to enforce that the object pool and target repository belong to the same fork network before invoking this RPC — Gitaly itself does not enforce this business relationship. The likelihood that this is independently, remotely exploitable by an "ordinary user" purely through Gitaly's gRPC surface without help from a compromised/buggy caller is uncertain from the code alone; the analog is valid as a structural gap ("permissionless" at the Gitaly layer because validation is pushed entirely to the RPC caller) but I could not confirm from the indexed code whether any additional authorization gate exists between an end user's action (fork creation, push) and this RPC being invoked with attacker-influenced pool paths. This should be treated as moderate-likelihood, contingent on caller-side authorization guarantees that are outside Gitaly's codebase.

### Recommendation
- Add a Gitaly-side check that verifies the object pool referenced in `LinkRepositoryToObjectPoolRequest` (and `FetchIntoObjectPoolRequest`) is legitimately associated with the target/origin repository (e.g., verify the pool's expected relative path against a derivation from the repository, similar to how `objectpool.FromRepo`/`getRelativeObjectPath` computes an expected relationship) rather than trusting the caller-supplied pool path unconditionally.
- Bound/validate all Gitaly RPC input fields that create persistent linking state to ensure they cannot reference resources outside of the caller's own trust boundary, consistent with existing validations such as `storage.ValidateRelativePath`, `alternateOutsideStorageError`, and `linkedToRepository`'s check against "different object pool."
- Document and enforce (ideally with tests) that `LinkRepositoryToObjectPool` rejects pools it cannot prove are associated with the given repository's fork network/project, closing the gap between "the pool exists and is valid" and "the pool is the correct pool for this repository."

### Proof of Concept
Not independently verifiable from the indexed code alone — reachability depends on whether an unprivileged/ordinary end-user action can drive `object_pool` field content in `LinkRepositoryToObjectPoolRequest`/`FetchIntoObjectPoolRequest` to point at a pool the caller does not legitimately own; this requires either a bug in GitLab Rails' authorization for object-pool association or an alternate internal caller path not present in this repository's index. Structurally, the exploit sequence per the code is:
1. Caller invokes `LinkRepositoryToObjectPool` with `repository` = attacker-accessible repo, `object_pool` = victim's private pool relative path (same storage). [3](#0-2) 
2. `poolForRequest`/`FromProto` only checks the pool exists and is a valid repository — not that it belongs to the same fork network as `repository`. [4](#0-3) 
3. `Link` writes the victim pool's path into the attacker repo's `objects/info/alternates`, making the pool's objects readable from the attacker's repository going forward. [5](#0-4)

// FromProto returns an object pool object from its Protobuf representation. This function verifies
// that the object pool exists and is a valid pool repository.
func FromProto(
	ctx context.Context,
	logger log.Logger,
	locator storage.Locator,
	gitCmdFactory gitcmd.CommandFactory,
	catfileCache catfile.Cache,
	txManager transaction.Manager,
	housekeepingManager housekeepingmgr.Manager,
	proto *gitalypb.ObjectPool,
) (*ObjectPool, error) {
	poolPath, err := locator.GetRepoPath(ctx, proto.GetRepository(), storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, err
	}

	if !storage.IsPoolRepository(proto.GetRepository()) {
		// When creating repositories in the ObjectPool service we will first create the
		// repository in a temporary directory. So we need to check whether the path we see
		// here is in such a temporary directory and let it pass.
		tempDir, err := locator.TempDir(proto.GetRepository().GetStorageName())
		if err != nil {
			return nil, fmt.Errorf("getting temporary storage directory: %w", err)
		}

		if !strings.HasPrefix(poolPath, tempDir) {
			return nil, ErrInvalidPoolDir
		}
	}

	pool := &ObjectPool{
		Repo:                localrepo.New(logger, locator, gitCmdFactory, catfileCache, proto.GetRepository()),
		logger:              logger,
		locator:             locator,
		gitCmdFactory:       gitCmdFactory,
		txManager:           txManager,
		housekeepingManager: housekeepingManager,
	}

	if !pool.IsValid(ctx) {
		return nil, ErrInvalidPoolRepository
	}

	return pool, nil
}

// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}
