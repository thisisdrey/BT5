### Title
Unauthenticated QUIC half-open connection churn exhausts global `max_concurrent_connections` slot before per-IP/global rate limiters ever engage - (File: streamer/src/nonblocking/quic.rs)

### Summary
In `run_server`, `ClientConnectionTracker::new` reserves a slot against the global `qos.max_concurrent_connections()` cap and `incoming.accept()` is called *before* any peer identity or IP-based state is established. The per-IP `ConnectionRateLimiter::is_allowed` check is a non-consuming peek, and both per-IP `register_connection` and the `overall_connection_rate_limiter.consume_tokens` calls only execute in `setup_connection` after a *successful* handshake. An attacker who opens connections and aborts before the handshake completes never triggers those consuming checks, letting it repeatedly occupy the shared concurrency slots for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) each, denying legitimate stakers.

### Finding Description
The accept loop in `run_server` processes each `Incoming` connection as follows:
- `overall_connection_rate_limiter.current_tokens() == 0` is only a peek (`TokenBucket::current_tokens`) that does not consume tokens [1](#0-0) .
- `rate_limiter.is_allowed(&incoming.remote_address().ip())` is also non-mutating: for an IP never seen before, or one that has never completed a handshake, it always returns `true` because `is_allowed` only reads existing token-bucket state via `current_tokens`, returning `true` when `None` (no record exists) [2](#0-1) .
- `ClientConnectionTracker::new(stats, qos.max_concurrent_connections())` then reserves one of a *shared, unauthenticated* global capacity of open connections — before the handshake, and before peer/stake identification, occurs [3](#0-2) ; [4](#0-3) .
- `incoming.accept()` is invoked and `setup_connection` is spawned with a `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` of 2 seconds [5](#0-4) ; [6](#0-5) .
- Only *after* the handshake completes does `setup_connection` call `rate_limiter.register_connection(&from.ip())` (which consumes a per-IP token) and `overall_connection_rate_limiter.consume_tokens(1)` (which consumes the global token) [7](#0-6) .
- If the attacker drops the connection or otherwise causes the handshake future to error/timeout, `setup_connection` returns via `handle_connection_error` or the timeout branch, and the `client_connection_tracker` is dropped, decrementing `open_connections` — but neither `register_connection` nor `overall_connection_rate_limiter.consume_tokens` was ever invoked [8](#0-7) ; [9](#0-8) .

Consequently, an attacker never needs to pass `ConnectionRateLimiter::register_connection` at all. By repeatedly opening a connection and aborting before/at the handshake, they can keep the shared `open_connections` counter pinned near `qos.max_concurrent_connections()` indefinitely (bounded only by the 2-second handshake timeout window per attempt), because:
1. The per-IP limiter never "sees" this IP as having a real completed connection (so `is_allowed` keeps returning `true` for that IP forever).
2. The global `overall_connection_rate_limiter`'s pre-accept peek check (`current_tokens() == 0`) is never depleted by churned/aborted connections since consumption only happens post-handshake.
3. `ClientConnectionTracker` is the only real gate, and it is a purely global, unauthenticated-reachable counter with no reservation for stake or per-peer fairness at this stage of the pipeline.

The code comment in `run_server` itself acknowledges the intentional design tradeoff ("shed fast and bound resource consumption... before a peer has asserted control over their ip address") [10](#0-9) , but this tradeoff still leaves the shared `max_concurrent_connections` slot pool contestable by unauthenticated churn without any per-source accounting, since neither rate limiter constrains pre-handshake churn from a single (or many) IP(s).

### Impact Explanation
This causes legitimate connections (staked or unstaked) to receive `ClientConnectionTracker::new` failures and be refused via `stats.refused_connections_too_many_open_connections`, since `open_connections >= max_concurrent_connections` is a purely FIFO/first-come race with no reservation by stake [11](#0-10) . This matches the "ingress unboundedly consumes `qos.max_concurrent_connections()` capacity, denying legitimate connections" category — a QoS evasion / DoS on TPU ingress capacity, falling under the ingress/QoS denial-of-service impact category described in the question's scope.

### Likelihood Explanation
The attack requires only unprivileged network reachability to the TPU QUIC port; no stake, keys, or gossip participation is required. An attacker can trivially open a QUIC `Connecting` handle and drop it (or intentionally stall the handshake) in a tight loop from many concurrent tasks/sockets, since `is_allowed` never blocks an IP that has not completed a handshake, and the global bucket's pre-accept check is a peek that is unaffected by churn. The only natural throttle is the 2-second `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`, which bounds per-attempt slot occupation but does not bound the number of concurrent attempts an attacker can sustain across many sockets/ports.

### Recommendation
Introduce a pre-handshake, IP-keyed admission counter/limiter (separate from `open_connections`) that consumes a token when an unauthenticated `Incoming` is accepted (not merely peeked), so a single or few source IPs cannot monopolize the shared `max_concurrent_connections` pool via handshake churn. Alternatively, reserve a portion of `max_concurrent_connections` capacity exclusively for connections that have completed handshake/registered stake, and/or make the per-IP `ConnectionRateLimiter` consume a token on accept (before handshake) rather than only on completed-handshake `register_connection`, refunding it if warranted after successful/failed handshake.

### Proof of Concept
Integration test plan (extending existing quic.rs test harness, e.g. `setup_quic_server`):
```rust
#[tokio::test(flavor = "multi_thread")]
async fn test_half_open_connection_churn_starves_legit_clients() {
    let SpawnTestServerResult { server_address, stats, cancel, join_handle, .. } =
        setup_quic_server(
            None,
            QuicStreamerConfig::default_for_tests(),
            SwQosConfig { max_unstaked_connections: 4, ..SwQosConfig::default() }, // small cap for test
        );

    // Attacker: repeatedly connect and drop before handshake completes.
    let attacker_task = tokio::spawn({
        let addr = server_address;
        async move {
            for _ in 0..1000 {
                if let Ok(endpoint) = make_client_endpoint(&addr, None).await_partial_handshake() {
                    drop(endpoint); // abort before handshake finishes
                }
            }
        }
    });

    tokio::time::sleep(Duration::from_millis(500)).await;

    // Legit client tries to connect while attacker churns.
    let legit_conn_result = make_client_endpoint(&server_address, None).await;

    // Expect: refused_connections_too_many_open_connections is nonzero,
    // and open_connections never exceeds max_concurrent_connections (bounded, but legit client starved).
    assert!(stats.refused_connections_too_many_open_connections.load(Ordering::Relaxed) > 0);
    assert!(stats.open_connections.load(Ordering::Relaxed) <= 4);
    // legit_conn_result should show refusal/timeout under sustained churn
    attacker_task.abort();
    cancel.cancel();
    join_handle.await.unwrap();
}
```
Expected assertions: `stats.refused_connections_too_many_open_connections` increases while `stats.connection_rate_limited_per_ipaddr` and `stats.connection_rate_limited_across_all` remain at (or near) zero for the churn traffic, proving the churn bypasses both rate limiters and only the shared, unreserved `max_concurrent_connections` gate is hit — demonstrating legitimate-client starvation without ever calling `ConnectionRateLimiter::register_connection`.
