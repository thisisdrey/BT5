**Rationale**: CVE-2018-7537 stems from Python's backtracking regex engine (`re` module) used by Django's `Truncator.chars()`/`words()` with `html=True`, where crafted HTML input caused catastrophic backtracking. Go's `regexp` package is fundamentally different — it is RE2-based and explicitly guarantees linear-time execution regardless of input, as documented directly in the package: "The regexp implementation provided by this package is guaranteed to run in time linear in the size of the input... This is a property not guaranteed by most open source implementations of regular expressions" [1](#0-0) .

Even the internal `backtrack.go` engine (used only for small regexes/inputs as a fast-path optimization) bounds its work with a visited-bit vector sized `len(prog.Inst) * (end+1)`, capped by `maxBacktrackProg` (500 instructions) and `maxBacktrackVector` (256KiB bits), explicitly to keep runtime linear and prevent exponential blowup [2](#0-1) [3](#0-2) .

In `html/template`, the escaping functions that use `regexp` (`specialScriptTagRE`, `scriptTagRe`) use simple, fixed, non-nested-quantifier patterns like `(?i)<(script|/script|!--)` and `(?i)<(/?)script` [4](#0-3) [5](#0-4) , which pose no backtracking risk even in engines that do backtrack, and in Go's case run through the linear-time RE2 automaton regardless. There is no code path in this repository analogous to Django's `html=True` truncation using an unsafe backtracking regex against attacker-controlled HTML/text — the architecture that enabled CVE-2018-7537 does not exist in Go's `regexp` or `html/template` packages by design.

// maxBitStateLen returns the maximum length of a string to search with
// the backtracker using prog.
func maxBitStateLen(prog *syntax.Prog) int {
	if !shouldBacktrack(prog) {
		return 0
	}
	return maxBacktrackVector / len(prog.Inst)
}

// shouldBacktrack reports whether the program is too
// long for the backtracker to run.
func shouldBacktrack(prog *syntax.Prog) bool {
	return len(prog.Inst) <= maxBacktrackProg
}
