### Title
Unbounded memory allocation via uncapped `Content-Length`/chunked body in `process_event` - (File: `libsigner/src/events.rs`)

### Summary
`process_event::<T,E>` reads the entire HTTP request body into a `String` using `request.as_reader().read_to_string(&mut body)` with no maximum body size check anywhere in the call path. Any TCP client that can reach the signer's event-receiver port can send a POST to `/stackerdb_chunks` (or `/proposal_response`, `/new_burn_block`, `/new_block`) with an attacker-controlled `Content-Length` (or chunked-encoded body) of arbitrary size, forcing the process to allocate memory proportional to the attacker-declared/streamed body size before any JSON parsing or validation occurs.

### Finding Description
`SignerEventReceiver::bind` starts a `tiny_http::Server` [1](#0-0) . `next_event` calls `http_server.recv()`, dispatches based on `request.url()`, and for `/stackerdb_chunks` calls `process_event::<T, StackerDBChunksEvent>(request)` [2](#0-1) .

Inside `process_event`, the body is read like this:
```rust
let mut body = String::new();
if let Err(e) = request.as_reader().read_to_string(&mut body) { ... }
``` [3](#0-2) 

`tiny_http`'s reader for a request will read exactly as many bytes as declared by `Content-Length` (or will decode a chunked body if `Transfer-Encoding: chunked` is used), but neither `tiny_http` nor this code enforces any upper bound on that value before allocating the `String`. A grep across `libsigner` for any size-limiting mechanism (`max_body`, `max_size`, `set_max`, `limits`) found none [3](#0-2) . Only after the full body has been buffered does the code call `serde_json::from_slice` to attempt to parse it into `E` [4](#0-3) , so any size cap that might exist inside the deserialization step is reached only after the unbounded allocation has already occurred.

Because there is no cap between the socket read and `read_to_string`, an attacker can declare (or stream, via chunked transfer) an arbitrarily large body, causing the receiving process to attempt to allocate that much memory in one `String` buffer, which can exhaust available memory or trigger an allocator abort, crashing the process. This differs from a "volumetric" DDoS because a single connection with a single crafted HTTP header/body can trigger the failure — it does not require sustained high-bandwidth traffic, just one large-Content-Length or long-chunked request.

### Impact Explanation
A single crafted request against `/stackerdb_chunks` (or the sibling endpoints `/proposal_response`, `/new_burn_block`, `/new_block`, all of which route through the same `process_event`) can cause the signer's event-receiver process to attempt an unbounded allocation, resulting in an out-of-memory crash or severe service degradation of the stacks-signer process listening on that port. This is a remote, unauthenticated crash/DoS triggerable with a handful of bytes (headers only, for the `Content-Length` variant) plus a body the attacker chooses whether to actually transmit in full — even a declared `Content-Length` alone can be enough depending on how the reader/allocator behaves, and a slow/chunked body multiplies the effect while keeping bandwidth low. This matches the Critical category: "remote crash/unauthenticated DoS from few messages."

### Likelihood Explanation
- No signer secret, StackerDB slot ownership, or any privileged role is required — the attacker only needs TCP reachability to the bound event-receiver port.
- The event-receiver's bind address is configuration-dependent (`stacks-signer` config), and no code path in `libsigner/src/events.rs` restricts the peer or validates any credential before `process_event` runs; the request is only checked for URL and HTTP method, not for size or origin.
- The attack is trivially repeatable per-connection, and cost to the attacker is a single crafted HTTP request.

### Recommendation
Enforce an explicit maximum content length before reading the body in `process_event`: inspect the `Content-Length` header (if present) and reject/close the connection if it exceeds a defined `MAX_PAYLOAD_LEN`/`MAX_MESSAGE_LEN`-style constant before calling `read_to_string`; additionally, use a bounded reader (e.g., `Read::take(max_len)`) so that chunked or unheadered bodies cannot exceed the cap regardless of declared size, and treat truncation/overflow as `EventError::MalformedRequest`.

### Proof of Concept
```rust
// libsigner test: drive a raw TcpStream against a bound SignerEventReceiver
// and send a POST to /stackerdb_chunks with an oversized (or chunked, unbounded)
// Content-Length, asserting the process either rejects it early (bug fixed)
// or attempts the full allocation (bug reproduced) before reaching serde_json::from_slice.

let mut receiver: SignerEventReceiver<SomeMsgType> = SignerEventReceiver::new(false);
let addr = receiver.bind("127.0.0.1:0".parse().unwrap()).unwrap();
// spawn receiver.next_event() in a thread

let mut stream = TcpStream::connect(addr).unwrap();
let huge_len: u64 = 10 * 1024 * 1024 * 1024; // 10 GiB declared length
let header = format!(
    "POST /stackerdb_chunks HTTP/1.1\r\nHost: {}\r\nContent-Length: {}\r\nContent-Type: application/json\r\n\r\n",
    addr, huge_len
);
stream.write_all(header.as_bytes()).unwrap();
// Optionally stream a small prefix of body bytes and observe process memory grow
// unbounded as `read_to_string` blocks trying to fill `body: String` to `huge_len`,
// well before `serde_json::from_slice` (events.rs:536) is ever reached.
```
Expected (buggy) behavior: process memory usage climbs toward the attacker-declared length with no rejection; expected (fixed) behavior: the request is rejected with `EventError::MalformedRequest` as soon as `Content-Length` exceeds a defined cap, without buffering the oversized body.
