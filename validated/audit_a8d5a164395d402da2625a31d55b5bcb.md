### Title
Unenforced precondition on `totalEnergyWeight > 0` causes energy-limit division to rely on a disabled `assert` - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit()` computes a contract-call energy limit by dividing by `totalEnergyWeight`, but the only guard against `totalEnergyWeight == 0` is a Java `assert` statement, which is compiled out and disabled by default (JVMs run without `-ea`). This mirrors the Basin `GeoEmaAndCumSmaPump` pattern: the code *comments/asserts* an invariant ("each caller must ensure reserve/weight is non-zero") instead of actually enforcing it with a runtime check, so if the precondition is ever violated the downstream arithmetic silently misbehaves or throws an uncaught exception.

### Finding Description
`calculateGlobalEnergyLimit` is used to convert an account's frozen-for-energy balance into an energy limit proportional to `totalEnergyLimit / totalEnergyWeight`: [1](#0-0) 

The `assert totalEnergyWeight > 0;` line is the *only* safeguard for the denominator. Unlike `chainbase/.../EnergyProcessor.calculateGlobalEnergyLimit`, which has an explicit runtime guard (`if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) { return 0; } else { assert totalEnergyWeight > 0; }`), [2](#0-1)  the `RepositoryImpl` copy used by the TVM path has no such conditional check when the "new reward" feature flag is off — it falls straight to the assert and then divides.

This function is reached from `VMActuator.getAccountEnergyLimitWithFloatRatio` while computing the energy limit for every smart-contract call transaction (`TriggerSmartContract`), i.e. from an ordinary unprivileged transaction: [3](#0-2) 

If `totalEnergyWeight` (the sum of all accounts' frozen-for-energy balances, a chain-wide dynamic property) is ever `0` — e.g. right after a resource-model migration, on a fresh/private network before anyone has frozen for energy, or after mass unfreezing under the new Freeze V2 model — any account that still has `frozeBalance >= TRX_PRECISION` will trigger this code path. With assertions disabled (the default), `assert totalEnergyWeight > 0;` is a no-op, and execution proceeds to:
- `hardenResourceCalculation()==true`: `BigInteger.divide(BigInteger.ZERO)` → `ArithmeticException`, uncaught by this method, propagating up through transaction execution.
- `hardenResourceCalculation()==false` (legacy floating path): `(double) totalEnergyLimit / 0` → `Infinity`, and `(long) (energyWeight * Infinity)` → `Long.MAX_VALUE`, silently granting an unbounded/incorrect energy limit for that call, an unbacked-resource condition analogous to the pump being fed a distorted value instead of reverting.

This is exactly the bug class in the report: a component's safety property ("total weight must be non-zero") is documented/expected but is not actually enforced by any caller or by the function itself under all configurations — reliance on a disabled `assert` is functionally equivalent to Basin's non-enforced "Each Well is responsible for ensuring…" comment.

### Impact Explanation
Depending on the arithmetic branch taken:
- Hardened path: an uncaught `ArithmeticException` inside contract-call energy accounting for a normal `TriggerSmartContract` transaction can propagate out of the intended execution flow, risking abnormal transaction processing / node crash during block application if not wrapped by a catch-all elsewhere.
- Legacy (non-hardened) path: silently produces `Long.MAX_VALUE`/an incorrect energy limit, letting a caller bypass the intended energy-fee/resource accounting — an unbacked resource grant that could be used to execute arbitrarily expensive contract calls without paying for them (a "unbacked balance"/DoS-adjacent resource abuse), which is a Medium/High-severity resource-accounting integrity issue.

### Likelihood Explanation
The precondition (`totalEnergyWeight > 0`) is not always true by construction; it is a dynamic, chain-state-dependent value that legitimately can drop to zero (e.g., a private/test network before anyone freezes for energy, or after protocol/state transitions around Freeze V2 rollout). Because assertions are disabled by default in production JVM deployments, the only protection is an inert `assert`. Any single `TriggerSmartContract` transaction from an account with a non-zero frozen-for-energy balance triggers the vulnerable calculation — no special privileges are required.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit` with an explicit runtime guard (matching the pattern already used in `EnergyProcessor.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2`): if `totalEnergyWeight <= 0`, return `0` (or another safe default) instead of falling through to division. This closes the gap between the documented invariant and the code that actually enforces it.

### Proof of Concept
1. Bring `totalEnergyWeight` (dynamic property `TOTAL_ENERGY_WEIGHT`) to `0` on a network — for instance on a fresh chain/private testnet before any account performs `FreezeBalanceV2`/energy delegation, or after all energy-frozen balances are withdrawn.
2. Have any account with `getAllFrozenBalanceForEnergy() >= TRX_PRECISION` (a residual/legacy frozen amount can exist even if `totalEnergyWeight` reporting is 0 due to a state-transition edge case) send a normal `TriggerSmartContract` transaction.
3. Execution reaches `VMActuator.getAccountEnergyLimitWithFloatRatio` → `RepositoryImpl.calculateGlobalEnergyLimit(creator)`.
4. Because JVMs run without `-ea` by default, `assert totalEnergyWeight > 0;` does not throw.
5. Division by zero occurs: `BigInteger` path throws `ArithmeticException` (hardened), or the double path yields `Infinity`/`Long.MAX_VALUE` for `creatorEnergyLimit` (non-hardened), corrupting the expected energy-limit accounting for that transaction.

Note: I was not able to execute this scenario in an actual node/testnet within this analysis; the finding is based on static code review of the guard logic and call graph. A background Devin session with test/runtime access would be needed to confirm the exact exception propagation behavior and whether any outer catch prevents a crash in `VMActuator`/block application.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  private long getAccountEnergyLimitWithFloatRatio(AccountCapsule account, long feeLimit,
      long callValue) {

    long sunPerEnergy = VMConstant.SUN_PER_ENERGY;
    if (rootRepository.getDynamicPropertiesStore().getEnergyFee() > 0) {
      sunPerEnergy = rootRepository.getDynamicPropertiesStore().getEnergyFee();
    }
    // can change the calc way
    long leftEnergyFromFreeze = rootRepository.getAccountLeftEnergyFromFreeze(account);
    callValue = max(callValue, 0, VMConfig.disableJavaLangMath());
    long energyFromBalance = floorDiv(max(
        account.getBalance() - callValue, 0, VMConfig.disableJavaLangMath()), sunPerEnergy,
        VMConfig.disableJavaLangMath());

    long energyFromFeeLimit;
    long totalBalanceForEnergyFreeze = account.getAllFrozenBalanceForEnergy();
    if (0 == totalBalanceForEnergyFreeze) {
      energyFromFeeLimit =
          feeLimit / sunPerEnergy;
    } else {
      long totalEnergyFromFreeze = rootRepository
          .calculateGlobalEnergyLimit(account);
      long leftBalanceForEnergyFreeze = getEnergyFee(totalBalanceForEnergyFreeze,
          leftEnergyFromFreeze,
          totalEnergyFromFreeze);

      if (leftBalanceForEnergyFreeze >= feeLimit) {
        energyFromFeeLimit = BigInteger.valueOf(totalEnergyFromFreeze)
            .multiply(BigInteger.valueOf(feeLimit))
            .divide(BigInteger.valueOf(totalBalanceForEnergyFreeze)).longValueExact();
      } else {
        energyFromFeeLimit = addExact(
            leftEnergyFromFreeze, (feeLimit - leftBalanceForEnergyFreeze) / sunPerEnergy,
            VMConfig.disableJavaLangMath());
      }
    }

    return min(addExact(leftEnergyFromFreeze, energyFromBalance,
            VMConfig.disableJavaLangMath()), energyFromFeeLimit, VMConfig.disableJavaLangMath());
  }
