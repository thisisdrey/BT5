### Title
Unbounded prefix-scan DoS via attacker-inflatable `DelegatedResourceAccountIndex` (V2) entries - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
The number of `DelegatedResourceAccountIndex` (V2) key/value entries associated with any account address is entirely controlled by unprivileged callers who invoke `DelegateResourceContract`/`FreezeBalance`+delegate operations. There is no upper bound on how many distinct delegator/receiver pairs can point at the same address. The public read-only query path `getDelegatedResourceAccountIndexV2`, exposed over gRPC/HTTP/JSON-RPC, then performs an unbounded `prefixQuery` scan and full in-memory sort over all matching entries, which grows linearly with attacker-inflated data — the same "loop over an attacker-controlled unbounded collection" bug class as the referenced Carapace `protectionInfos` DDOS finding.

### Finding Description
`DelegateResourceProcessor.delegateResource` (and the legacy `FreezeBalanceActuator.delegateResource`) write two new keys per delegation using the receiver/owner addresses as key suffixes: [1](#0-0) 

Because the key includes both addresses (`V2_FROM_PREFIX/ownerAddress/receiverAddress` and `V2_TO_PREFIX/receiverAddress/ownerAddress`), any attacker who freezes trivial amounts of TRX from many disposable accounts and delegates to a single target address creates one new persistent DB entry per transaction, with no cap on the count of such entries per target address: [2](#0-1) 

When any client queries that address via the public API, `getV2Index`/`getIndex` call `getWithPrefix`, which performs a `prefixQuery` for both the "to" and "from" prefixes, materializes **all** matching entries into a `List`, and sorts the full list by timestamp before returning: [3](#0-2) 

`TronStoreWithRevoking.prefixQuery` performs the underlying scan with no size limit, converting the entire matched key range into an in-memory `Map`: [4](#0-3) 

This query is directly reachable by any anonymous API client through gRPC (`RpcApiService.getDelegatedResourceAccountIndex`/`V2`), HTTP servlets (`GetDelegatedResourceAccountIndexServlet`/`V2Servlet`), and the PBFT/Solidity read-only node services — none of which require authentication or apply rate/size limiting on the number of entries scanned: [5](#0-4) 

Additionally, the legacy non-optimized code path stores the same unbounded list directly inside a single protobuf capsule (`toAccountsList`/`fromAccountsList`), and when the `AllowDelegateOptimization` feature is toggled on, `DelegatedResourceAccountIndexStore.convert()` iterates the *entire* accumulated list for that address inside a normal transaction-processing actuator call, re-writing two new DB keys per historical entry: [6](#0-5) [7](#0-6) 

A production test even demonstrates the unbounded growth pattern (100+ receivers appended to a single owner's index) without any cap enforcement: [8](#0-7) 

### Impact Explanation
An attacker can, at negligible cost (minimum freeze amount + normal transaction fee, using disposable freshly-generated addresses), inflate the delegation index of an arbitrary target address to an unbounded size. Any subsequent read of that target's delegated-resource index via gRPC/HTTP/JSON-RPC forces the node to perform an unbounded `prefixQuery` scan plus a full sort of all matched entries, consuming CPU and memory proportional to attacker-controlled input size. Repeated queries (from the attacker or from legitimate third parties such as exchanges/wallets that routinely check delegation state for arbitrary addresses) can degrade or stall the node's query-serving capability, and — in the legacy/optimization-migration code path — can inflate the cost and latency of an ordinary `FreezeBalanceContract`/`convert()` execution embedded inside normal block/transaction processing. This matches the reported bug class: attacker-controlled unbounded collection iterated in a reachable code path leading to sustained resource exhaustion of the affected service.

### Likelihood Explanation
High feasibility: creating many funded throwaway accounts and issuing minimal `FreezeBalanceContract`/`DelegateResourceContract` transactions targeting one address is cheap and requires no special privileges — it is exactly analogous to the referenced report's buyer spamming `buyProtection` to grow `protectionInfos`. The query APIs that trigger the expensive scan are public, unauthenticated, and commonly invoked by wallets/exchanges, making exploitation straightforward and the resulting degradation broadly impactful.

### Recommendation
- Cap the number of delegation index entries scanned/returned per query (pagination with a hard maximum), or replace the current `prefixQuery`-then-sort-all approach with a bounded, indexed/paginated retrieval.
- Enforce/maintain a minimum-delegation-amount or a maximum count of distinct delegator/receiver relationships per address to make large-scale spamming economically costly.
- Bound the legacy `convert()` migration loop (or execute it out-of-band/incrementally rather than fully inline within a single actuator execution) so a single transaction cannot be forced to process an attacker-inflated historical list.

### Proof of Concept
1. Generate N disposable accounts, each funded with the minimum TRX needed to freeze/delegate (e.g., 1 TRX equivalent, `TRX_PRECISION` sized amounts).
2. From each disposable account, issue a `FreezeBalanceContract` (with `receiver_address = victim`) or `DelegateResourceContract` transaction delegating BANDWIDTH/ENERGY to a single victim address, as in `DelegateResourceProcessor.delegateResource` / `FreezeBalanceActuator.delegateResource`.
3. Each transaction persists new `V2_FROM_PREFIX`/`V2_TO_PREFIX` keyed entries keyed by the (owner, receiver) pair — no code path limits N.
4. Repeat until N is large (e.g., tens/hundreds of thousands of entries pointing at the victim address) — cost scales only with the minimal freeze amount and normal tx fees.
5. Call the public `getDelegatedResourceAccountIndexV2`/`GetDelegatedResourceAccountIndexV2Servlet` API for the victim address; observe the node performing an unbounded `prefixQuery` (`DelegatedResourceAccountIndexStore.getWithPrefix`) that materializes and sorts all N entries, consuming CPU/memory proportional to attacker-inflated N and degrading the node's ability to answer this and other requests.

    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
