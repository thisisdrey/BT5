Based on the investigation, there is a genuine analog of the KinoAccountProxy "hijacked initialize selector" bug class in the ETH-implicit Wallet Contract's 4-byte function-selector dispatch logic.

### Title
Reserved 4-byte function-selector collision in the ETH-implicit Wallet Contract misroutes calls into a native `AddKey`/`DeleteKey` action against an attacker-chosen `target` account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

### Summary
The Wallet Contract (NEP-518) dispatches incoming Ethereum-style call data purely on the first 4 bytes (`tx.data[0..4]`), exactly like a non-transparent proxy dispatching on a function selector. If that 4-byte prefix happens to match one of four hard-coded "reserved" selectors (`FUNCTION_CALL_SELECTOR`, `TRANSFER_SELECTOR`, `ADD_KEY_SELECTOR`, `DELETE_KEY_SELECTOR`), the call is diverted away from generic ERC-20/contract emulation and interpreted as a native NEAR action - the same "reserved function shadows arbitrary implementation calls" bug class described in the KinoAccountProxy report, just implemented via a 4-byte prefix match instead of Solidity's built-in selector dispatch.

### Finding Description
`parse_tx_data` matches `tx.data[0..4]` against four constants before falling back to ERC-20 emulation: [1](#0-0) 

`ADD_KEY_SELECTOR`/`DELETE_KEY_SELECTOR` are returned as `ParsableTransactionKind::SelfNearNativeAction`, meaning the design intent is that these only ever apply to the wallet's own account. But the caller (`parse_rlp_tx_to_action`) only special-cases the situation where `target_kind` is `TargetKind::EthImplicit` (redirecting to a harmless base-token transfer); for any other `target_kind` (`TargetKind::OtherNearAccount` or `TargetKind::CurrentAccount`) it falls straight through as `TransactionKind::NearNativeAction`: [2](#0-1) 

The resulting action is then converted into a `Promise` sent to `target` - not to `current_account_id` - via `action_to_promise`: [3](#0-2) 

`target` is a parameter supplied by the untrusted relayer (`rlp_execute(target, tx_bytes_b64)`), only loosely constrained by `validate_tx_relayer_data` to satisfy `to == account_id_to_address(target)`, where `to` is the address field of the user's signed Ethereum transaction: [4](#0-3) 

Because `AddKey`/`DeleteKey` never validate `target` against `receiver_id` (unlike the `FUNCTION_CALL_SELECTOR`/`TRANSFER_SELECTOR` arms, which explicitly check `target.as_str() != receiver_id.as_str()`), a "self-only" action can be redirected to any Named account the relayer/attacker names as `target`, as long as they can also present a plausible `to` address for the user to sign against.

Separately, `AddKeyAction::AccessKeyPermission::FunctionCall` with `is_limited_allowance = false` yields `Allowance::Unlimited`: [5](#0-4) [6](#0-5) 

### Impact Explanation
An attacker who deploys a malicious contract whose function signature's keccak selector collides with `ADD_KEY_SELECTOR` (`0x753ce5ab`) or `DELETE_KEY_SELECTOR` (`0x3fc6d404`) - a searchable vanity-selector problem, exactly the "1 in 2^32" collision the original KinoAccountProxy report calls out, and fully brute-forceable offline since the attacker controls the function name/parameter types - can get a victim to sign what looks like an ordinary Ethereum contract interaction. If routed with `target` set to something other than the wallet's own eth-implicit account (which the relayer chooses), the wallet contract will emit a native `AddKey` (with attacker-supplied public key, `receiver_id`, `method_names`, and `Allowance::Unlimited`) or `DeleteKey` action directed at `target` instead of confining it to the signer's own wallet. This can grant an attacker-controlled key with unlimited gas allowance on an unintended account, or delete keys on an account the user never authorized, both of which correspond to authorization escalation across accounts.

### Likelihood Explanation
Exploitation requires (1) finding a colliding function selector via brute force (feasible, similar cost class to vanity-address generation), (2) social-engineering a victim into signing a transaction against the malicious contract, and (3) a relayer (which the protocol treats as fully untrusted/unprivileged in this design) supplying a `target` that is not the wallet's own account. Because relayers are explicitly assumed untrusted in this design (the contract's own comments describe banning "faulty" relayers), an attacker acting as relayer can freely choose `target`, making this a realistically reachable path rather than a purely theoretical one. I was not able to fully verify within available tool calls whether NEAR's action-application layer places any additional restriction on `AddKey`/`DeleteKey` receipts where predecessor != receiver; this could not be confirmed with certainty from the indexed files inspected (`runtime/runtime/src/access_keys.rs`, `actions.rs`), so the exact blast radius against arbitrary third-party accounts remains partially unconfirmed.

### Recommendation
For `ADD_KEY_SELECTOR`/`DELETE_KEY_SELECTOR` (and any other `SelfNearNativeAction`), enforce that the resulting action is only ever converted to a promise targeting `context.current_account_id`, regardless of `target_kind`, rather than only handling the `EthImplicit` case specially. Reject (or force a safe fallback for) any `SelfNearNativeAction` where `target_kind` is `OtherNearAccount` unless `target == current_account_id`, mirroring the explicit `target == receiver_id` checks already present for `FUNCTION_CALL_SELECTOR`/`TRANSFER_SELECTOR`.

### Proof of Concept
Conceptual PoC (could not be executed within this session, no filesystem/test-runner access):
1. Brute-force a function name/parameter tuple matching `ADD_KEY_SIGNATURE` types whose keccak selector equals `0x753ce5ab`. [7](#0-6) 
2. Deploy a contract exposing that function at a chosen Near account `evil.near`; compute `to = account_id_to_address("evil.near")`.
3. Get a victim to sign an Ethereum transaction with `to` set to that address and the crafted calldata (looks like a normal dApp interaction in a wallet UI).
4. Submit via `rlp_execute(target="evil.near", tx_bytes_b64=...)`. Since `target_kind` resolves to `TargetKind::OtherNearAccount`, the AddKey action is emitted as `TransactionKind::NearNativeAction` and sent as a promise to `evil.near` rather than being confined to the victim's own wallet account. fn validate_tx_relayer_data<'a>(
    tx: &NormalizedEthTransaction,
    target: &'a AccountId,
    context: &ExecutionContext,
    expected_nonce: u64,
) -> Result<TargetKind<'a>, Error> {
    if tx.address.raw() != context.current_address {
        return Err(Error::Relayer(RelayerError::InvalidSender));
    }

    if tx.chain_id != Some(CHAIN_ID) {
        return Err(Error::Relayer(RelayerError::InvalidChainId));
    }

    let to = tx.to.ok_or(Error::User(UserError::EvmDeployDisallowed))?.raw();

    let target_kind = parse_target(target, context.current_address);

    // valid targets satisfy `to == target` or `to == hash(target)`
    let is_valid_target = match target_kind {
        TargetKind::CurrentAccount if to == context.current_address => {
            target == &context.current_account_id
        }
        TargetKind::EthImplicit(address) if to == address => {
            target.as_str()
                == format!("0x{}{}", hex::encode(address), context.current_account_suffix())
        }
        _ => to == account_id_to_address(target),
    };

    if !is_valid_target {
        return Err(Error::Relayer(RelayerError::InvalidTarget));
    }

fn action_to_promise(target: AccountId, action: near_action::Action) -> Result<Promise, Error> {
    match action {
        near_action::Action::FunctionCall(action) => Ok(Promise::new(target).function_call(
            action.method_name,
            action.args,
            action.deposit,
            action.gas,
        )),
        near_action::Action::Transfer(action) => Ok(Promise::new(target).transfer(action.deposit)),
        near_action::Action::AddKey(action) => match action.access_key.permission {
            near_action::AccessKeyPermission::FullAccess => {
                Err(Error::User(UserError::UnsupportedAction(UnsupportedAction::AddFullAccessKey)))
            }
            near_action::AccessKeyPermission::FunctionCall(access) => Ok(Promise::new(target)
                .add_access_key_allowance_with_nonce(
                    action.public_key,
                    access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited),
                    access.receiver_id,
                    access.method_names.join(","),
                    action.access_key.nonce,
                )),
        },
        near_action::Action::DeleteKey(action) => {
            Ok(Promise::new(target).delete_key(action.public_key))
        }
    }
