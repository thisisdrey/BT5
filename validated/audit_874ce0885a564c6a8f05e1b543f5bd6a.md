### Title
`CreateAccountActuator` never validates the caller-supplied `type`/`typeValue` field, letting an unprivileged account impersonate an `AccountType.Contract` identity - ([File: actuator/src/main/java/org/tron/core/actuator/CreateAccountActuator.java])

### Summary
`AccountCreateContract` carries a `type` (and mirrored `typeValue`) field that determines the resulting account's `AccountType` (`Normal`, `AssetIssue`, `Contract`). `CreateAccountActuator.validate()` explicitly skips validating this field — the only check that ever existed is commented out — and `execute()` builds the persisted `AccountCapsule` directly from the attacker-controlled `contract.getType()`/`getTypeValue()`. This is analogous to the LXD bug: a caller-controlled "type" field that should be constrained/derived by the system is instead persisted verbatim, letting a normal, unprivileged transaction sender mint an account that is indistinguishable (by `AccountType`) from a real smart-contract account.

### Finding Description
In `CreateAccountActuator.validate()` the only reference to the `type` field is commented out: [1](#0-0) 
No other check anywhere in `validate()` restricts `contract.getType()`/`getTypeValue()`.

In `execute()`, the capsule is constructed straight from the attacker-supplied contract: [2](#0-1) 

And the `AccountCapsule` constructor used copies both `type` and `typeValue` verbatim from the contract with no server-side derivation or clamping: [3](#0-2) 

This mirrors the LXD root cause exactly: a privileged/identity-determining field (`Type` in LXD certificates, `type`/`typeValue` here) is supposed to be system-controlled (contract accounts are normally only ever created as a side effect of `CreateSmartContract`, never directly chosen by the caller), but the update/create path fails to reset or reject a caller-supplied value for that field, so it persists unchecked.

### Impact Explanation
Several downstream checks trust `AccountCapsule.getType() == AccountType.Contract` as a strong signal that the address holds deployed bytecode and therefore should be treated differently from an EOA, e.g.: [4](#0-3) 
Here, `TransferActuator` uses `toAccount.getType() == AccountType.Contract` to decide whether TRX transfers must be blocked (`ForbidTransferToContract`) or must go through TVM version compatibility checks, and even looks up `ContractStore` assuming a contract entry must exist for such accounts, throwing an internal "can not happen" error path when it does not — because a `Contract`-typed account created via `CreateAccountActuator` never actually has a `ContractCapsule` in `ContractStore`. Other consumers of `AccountType` (`BandwidthProcessor`, `DelegateResourceActuator`, `FreezeBalanceActuator`, `TransferAssetActuator`) similarly branch on account type for resource/permission semantics. An attacker who can label an arbitrary key-controlled address as `AccountType.Contract` can spoof "smart contract" identity to bypass or corrupt logic that assumes contract accounts are governed by TVM/`ContractStore` invariants, or manipulate downstream bandwidth/resource accounting and API classification (e.g., JSON-RPC/explorer logic that treats `AccountType.Contract` addresses as contracts) — all reachable via a single unprivileged `AccountCreateContract` transaction broadcast, with no special permission required.

### Likelihood Explanation
`AccountCreateContract` is broadcastable by any account with enough balance to pay `getCreateNewAccountFeeInSystemContract()`; no committee/witness/admin privilege is needed. The vulnerable code path is hit on every account creation, and the missing check is visible as dead/commented-out code, confirming it was intentionally checked once and then disabled/forgotten, an easily reachable and highly reproducible condition.

### Recommendation
In `CreateAccountActuator.validate()`, reject any `AccountCreateContract` where `type`/`typeValue` is anything other than the allowed caller-creatable types (i.e., disallow `AccountType.Contract`, which must only ever be set internally by `CreateSmartContractActuator`). Alternatively, ignore the caller-supplied `type` entirely in `execute()` and always construct new accounts with `AccountType.Normal` (or `AssetIssue` only through the dedicated asset-issue flow), mirroring the LXD fix pattern of re-deriving the sensitive field from trusted server-side state rather than trusting client input.

### Proof of Concept
1. Craft and sign an `AccountCreateContract` from any funded account, setting:
   - `owner_address` = attacker's funded account
   - `account_address` = a fresh address the attacker controls the private key for
   - `type` = `Contract` (enum value 2)
2. Broadcast the transaction; `CreateAccountActuator.validate()` performs no check on `type`, and `execute()` persists an `AccountCapsule` with `AccountType.Contract` for `account_address`, even though `ContractStore` has no entry for it.
3. Query `account_address` via `Wallet`/HTTP `getaccount` — it reports `type: "Contract"` despite being a plain EOA with no bytecode, and any logic branching on `AccountType.Contract` (e.g., `TransferActuator`'s `ForbidTransferToContract`/`AllowTvmCompatibleEvm` checks) treats it accordingly, diverging from actual contract semantics.

  public AccountCapsule(final AccountCreateContract contract, long createTime,
      boolean withDefaultPermission, DynamicPropertiesStore dynamicPropertiesStore) {
    if (withDefaultPermission) {
      Permission owner = createDefaultOwnerPermission(contract.getAccountAddress());
      Permission active = createDefaultActivePermission(contract.getAccountAddress(),
          dynamicPropertiesStore);

      this.account = Account.newBuilder()
          .setType(contract.getType())
          .setAddress(contract.getAccountAddress())
          .setTypeValue(contract.getTypeValue())
          .setCreateTime(createTime)
          .setOwnerPermission(owner)
          .addActivePermission(active)
          .build();
    } else {
      this.account = Account.newBuilder()
          .setType(contract.getType())
          .setAddress(contract.getAccountAddress())
          .setTypeValue(contract.getTypeValue())
          .setCreateTime(createTime)
          .build();
    }
  }
