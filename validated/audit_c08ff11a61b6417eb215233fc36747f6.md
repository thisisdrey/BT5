### Title
Disabled-API Config Bypass via JSON-RPC — Sensitive Account/Contract Data Remains Exposed When Equivalent Wallet APIs Are Disabled - (File: framework/src/main/java/org/tron/core/services/filter/HttpApiAccessFilter.java)

### Summary
java-tron lets operators hide sensitive Wallet APIs (`getaccount`, `triggerconstantcontract`, `getcontract`, `getnodeinfo`, etc.) from the public by adding their names to `node.disabledApi`. This control is enforced by `HttpApiAccessFilter.isDisabled()` [1](#0-0)  for HTTP/Solidity/PBFT servlets and by `RpcApiAccessInterceptor.isDisabled()` [2](#0-1)  for gRPC. However, the JSON-RPC (Ethereum-compatible) surface exposed by `TronJsonRpcImpl`/`JsonRpcServlet` is explicitly excluded from this control, as documented directly in the shipped config: "Disabled API list (works for http, rpc and pbft, not jsonrpc)" [3](#0-2) . This is structurally identical to the Directus bug: an administrator sets a restriction expecting a class of information to be hidden (`GRAPHQL_INTROSPECTION=false` / `disabledApi=[...]`), but an alternate, functionally-equivalent endpoint (`server_specs_graphql` SDL / JSON-RPC `eth_*` methods) returns the same information without being subject to the restriction.

### Finding Description
`disabledApi` is documented and intended as the mechanism to hide specific Wallet API operations from unauthenticated/unwanted callers [4](#0-3) . It is enforced only in the HTTP filter and gRPC interceptor:
- `HttpApiAccessFilter.isDisabled` matches on `endpoint.split("/")[2]` for `/wallet/*`, `/walletsolidity/*`, PBFT paths, plus a few manually-added extra paths (`/net/listnodes`, `/monitor/getstatsinfo`, `/monitor/getnodeinfo`) [5](#0-4) .
- `RpcApiAccessInterceptor.isDisabled` matches on the gRPC full method name [6](#0-5) .

Neither of these interceptors, nor any equivalent, is registered on the JSON-RPC servlet chain. The only interceptor present there is `MetricInterceptor`, which is purely for metrics, not access control. Yet `TronJsonRpcImpl` (`framework/src/main/java/org/tron/core/services/jsonrpc/TronJsonRpcImpl.java`) implements Ethereum-style RPC methods (`eth_getBalance`, `eth_call`, `eth_getCode`, `eth_getTransactionByHash`, etc.) that return the exact same underlying account/contract state as the Wallet APIs an operator may have disabled (`getaccount`, `triggerconstantcontract`, `getcontract`). Because `node.disabledApi` is documented as not applying to JSON-RPC, disabling a sensitive Wallet endpoint gives operators a false sense of security: the equivalent account balance, contract bytecode, or constant-call state remains fully queryable by any unauthenticated client through the JSON-RPC endpoint (`node.jsonrpc.httpFullNodeEnable`), which is enabled independently of `disabledApi`.

### Impact Explanation
An operator who disables sensitive read APIs via `disabledApi` (e.g., to hide account balances, contract bytecode, or constant-call results for privacy/compliance reasons on a node they run) is silently bypassed: any anonymous client reachable over `node.jsonrpc` can retrieve equivalent account and contract state via `eth_getBalance`/`eth_call`/`eth_getCode`, exactly mirroring the CWE-200 pattern in the reference report — a restriction meant to hide information from unauthenticated/unauthorized parties is only enforced on one interface while an equivalent interface leaks the same data. This satisfies "unauthorized ... information disclosure" impact criteria at Medium severity, matching the referenced advisory's own CVSS (C:L/I:N/A:N).

### Likelihood Explanation
High likelihood of exposure: `node.jsonrpc.httpFullNodeEnable` is a standard feature many FullNodes enable for Ethereum tooling compatibility, requires no authentication, and the bypass requires no crafted payload — simply calling the standard JSON-RPC method achieves the same result the operator believed was blocked.

### Recommendation
Extend the `disabledApi` enforcement (or an equivalent allow/deny mechanism) to the JSON-RPC dispatch path in `TronJsonRpcImpl`/`JsonRpcServlet`, mapping JSON-RPC method names to the same underlying operation categories used by `HttpApiAccessFilter`/`RpcApiAccessInterceptor`, so that disabling an operation blocks it consistently across HTTP, gRPC, and JSON-RPC. At minimum, update documentation to make the JSON-RPC gap explicit and provide a `node.jsonrpc.disabledApi`-equivalent control.

### Proof of Concept
1. Configure a node with `node.disabledApi = ["getaccount"]` and `node.jsonrpc.httpFullNodeEnable = true`.
2. Confirm `POST /wallet/getaccount` now returns `{"Error":"this API is unavailable due to config"}` per `HttpApiAccessFilter`.
3. Call the JSON-RPC endpoint with `{"jsonrpc":"2.0","method":"eth_getBalance","params":["0x...","latest"],"id":1}` against `node.jsonrpc.httpFullNodePort` — the balance for the same account is still returned, unaffected by `disabledApi`, confirming the bypass documented at [3](#0-2) .

  private boolean isDisabled(String endpoint) {
    boolean disabled = false;

    try {
      endpoint = URI.create(endpoint).normalize().toString();
      List<String> disabledApiList = CommonParameter.getInstance().getDisabledApiList();
      if (!disabledApiList.isEmpty()) {
        disabled = disabledApiList.contains(endpoint.split("/")[2].toLowerCase(Locale.ROOT));
      }
    } catch (Exception e) {
      logger.warn("check isDisabled except, endpoint={}, {}", endpoint, e.getMessage());
    }

    return disabled;
  }
