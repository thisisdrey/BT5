### Title
Fee-on-accrual rounds to zero when `accrue()` is spammed in small time increments, permanently denying `dao-treasury` its reserve-factor revenue - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
The vault's public `accrue()` function computes the protocol's reserve-factor cut of new interest with `mul-div-down`, which truncates towards zero. Any unprivileged caller can invoke `accrue()` directly, and by doing so every block (instead of letting interest build up across many blocks before someone calls it), the computed `debt-delta` per call becomes small enough that `reserve-inc` rounds down to `0` on every single call — this is the exact "buy in chunks to zero the fee" pattern from the referenced report, applied to the interest-reserve fee instead of a token-sale fee.

### Finding Description
`accrue()` is `define-public` with no caller restriction beyond the pause flag, so it is reachable by any ordinary principal (or their own contract) directly: [1](#0-0) 

Inside it, the protocol fee owed to `dao-treasury` is computed as:
```
old-debt     = mul-div-down scaled-principal idx INDEX-PRECISION
new-debt     = mul-div-down scaled-principal next INDEX-PRECISION
debt-delta   = new-debt - old-debt
reserve-inc  = mul-div-down debt-delta fee-reserve BPS
treasury-lp  = if reserve-inc > 0 then mul-div-down reserve-inc total-supply (total-assets-preview - reserve-inc) else 0
```
`mul-div-down` is a plain floor division: `(/ (* x y) z)`, exactly the same rounding-down primitive used in the external report's `ownerShare` computation: [2](#0-1) 

Because `treasury-lp` (and thus the `ft-mint?` to `.dao-treasury`) is only executed `if (> treasury-lp u0)`, whenever `debt-delta * fee-reserve < BPS` (i.e. `< 10000`), the entire fee for that accrual window is silently dropped — the interest itself is still reflected in `total-assets`/`index`, but the DAO's cut of it disappears: [3](#0-2) 

This is directly analogous to the report's exploit: rather than buying in tiny chunks to zero the owner's percentage fee, an attacker calls `accrue()` (or triggers it via any market/vault entry point) every single block so that each `debt-delta` slice is kept below the rounding threshold, whereas letting interest accumulate over a longer natural interval before an organic call would have produced a non-zero `reserve-inc`. The bug is most exploitable for the lower precision / lower utilization periods (small `debt-delta` relative to `BPS=10000` combined with a modest `fee-reserve`), and is present identically across all vaults using this same accrual pattern.

Note that within the same block, a second `accrue()` call is a no-op (`idx == next`), so the attack's leverage comes from maximizing call frequency across blocks (once per block) rather than within a block — same "fragmentation" idea as the original report, just applied at the granularity the protocol allows.

### Impact Explanation
Every time `reserve-inc` truncates to zero, the reserve-factor revenue that should have been minted as `zft` shares to `.dao-treasury` is permanently lost for that accrual window — the interest still accrues to depositors/`total-assets`, but the DAO's carve-out of it never gets minted. Because a bot can force this every block, it results in permanent freezing/loss of the protocol's unclaimed yield (reserve-factor revenue) with essentially zero cost to the attacker, matching the in-scope impact class "theft/permanent freezing of unclaimed yield."

### Likelihood Explanation
Likelihood is high: `accrue()` has no access control, costs only a standard transaction, and any bot/contract can call it once per block indefinitely on any of the six vaults (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`) that share this identical accrual code. It's most effective while `debt-delta` per block is small relative to `BPS` — e.g., low-utilization periods, or vaults with smaller principal, or with a low `fee-reserve` setting.

### Recommendation
Track and carry forward truncated/undistributed reserve remainder across accrual calls (e.g., accumulate a running "dust" counter of pre-truncation reserve-inc and only mint whole zft units once accumulated dust crosses a share-unit threshold), instead of dropping the sub-unit remainder on every call. Alternatively, revert with a minimum-elapsed-time guard so `accrue()`'s reserve calculation is only executed when `debt-delta * fee-reserve >= BPS`, deferring dust accrual to a later, larger call rather than silently discarding it forever.

### Proof of Concept
1. Deploy/observe a vault (e.g. `v0-vault-usdc.clar`) with `fee-reserve` set (e.g. `u1000` = 10%) and normal utilization/rate such that per-block interest accrues but is a modest amount.
2. An attacker (any principal, no auth needed) calls `(contract-call? .vault-usdc accrue)` in every single Stacks block.
3. Each call computes `debt-delta` for just that ~10-minute interval; if `debt-delta * fee-reserve < 10000`, `reserve-inc` floors to `0`, and the `if (> reserve-inc u0) (ft-mint? zft treasury-lp .dao-treasury)` branch never executes for that call.
4. Compare against the counterfactual where `accrue()` is called only once after the same total elapsed time (e.g. once per day): the aggregated `debt-delta` there is large enough that `reserve-inc > 0`, and `dao-treasury` receives its due `zft` shares.
5. Repeating step 2 indefinitely permanently denies `dao-treasury` the reserve-factor revenue it would otherwise have earned, at no cost beyond gas to the attacker.
