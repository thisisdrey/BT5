### Title
Unbounded array allocation from attacker-controlled ABI length in TVM precompile helpers can crash a node - (`File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytes32Array` and `PrecompiledContracts.extractBytesArray` read an array-length field directly out of the calldata passed to a precompiled contract and use it, unbounded, to allocate a Java array before any sanity check is performed. This mirrors the CVE-2020-20658 bug class: an oversized, attacker-supplied length value is passed straight into an allocation routine (there, `calloc`; here, `new byte[len][]`), producing a denial-of-service instead of a controlled failure.

### Finding Description
`extractBytes32Array` takes `len` from `words[offset].intValueSafe()` and immediately allocates `new byte[len][]` with no upper bound check: [1](#0-0) 

`extractBytesArray` has the same pattern — `len` comes straight from calldata, and a `byte[len][]` array is allocated before any validation of `len` against the actual data size: [2](#0-1) 

Both helpers are internal to `PrecompiledContracts`, which is the TVM precompile dispatch class reachable from any smart-contract `CALL`/`STATICCALL` a transaction sender can trigger through `Program`/opcode execution. `DataWord.intValueSafe()` is designed to clamp out-of-range 256-bit words to `Integer.MAX_VALUE` rather than throwing, so a crafted word (e.g. `0xFF...FF`) in the "array length" slot of the ABI-encoded input yields `len = Integer.MAX_VALUE`, and the subsequent `new byte[Integer.MAX_VALUE][]` (or `new byte[len][]`) allocation attempt throws `OutOfMemoryError`. Because this happens inside TVM opcode execution rather than inside a `try/catch` boundary that gracefully reverts, an `OutOfMemoryError` thrown mid-execution can propagate up through the block-application path and destabilize the node process, unlike normal reverts which are safely caught by `Program`/`VM` exception handling for `Exception`-derived types.

### Impact Explanation
An unprivileged transaction sender who deploys or calls a contract invoking the affected precompile with a crafted length field can force the node to attempt an outsized heap allocation. Depending on JVM heap configuration this can trigger `OutOfMemoryError`, which is an unchecked `Error` (not caught by the `Exception`-based revert handling used throughout `Program`), risking a node crash/halt when the block containing the malicious transaction is validated by every full node and SR — a broadly reachable, block-processing denial-of-service.

### Likelihood Explanation
Likelihood is high for reach (any account can broadcast a contract call that exercises this precompile path with attacker-chosen calldata) but is bounded by whether the specific precompile(s) that call `extractBytes32Array`/`extractBytesArray` additionally validate array length against the actual `data.length` before or shortly after these helpers execute — I was not able to fully enumerate every call site and surrounding guard within the remaining tool budget, so this should be independently confirmed by inspecting each precompile `execute()` method that references these two helpers before treating this as fully proven end-to-end exploitable.

### Recommendation
Validate `len` against a sane upper bound and against the actual remaining `data.length` before allocating, in both `extractBytes32Array` and `extractBytesArray` (and any other precompile helper using `intValueSafe()`-derived lengths for allocation sizing), returning a revert/false result instead of allocating when the declared length is inconsistent with the supplied calldata size.

### Proof of Concept
1. Deploy a contract that performs a `STATICCALL`/`CALL` to the precompiled address whose implementation invokes `extractBytesArray`/`extractBytes32Array`.
2. Encode the ABI array-length word at the expected `offset` as `0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF` (or any value whose `intValueSafe()` clamps to `Integer.MAX_VALUE`).
3. Broadcast the transaction; the resulting `new byte[Integer.MAX_VALUE][]` allocation attempt throws `OutOfMemoryError` during opcode execution in `PrecompiledContracts`. [3](#0-2)

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
