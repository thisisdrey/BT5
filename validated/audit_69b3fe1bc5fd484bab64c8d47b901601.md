### Title
Legacy `FreezeBalanceContract`/`UnfreezeBalanceContract` remain fully active after `ALLOW_NEW_RESOURCE_MODEL`/`UNFREEZE_DELAY_DAYS` upgrade, letting users bypass the intended unfreeze-delay lock - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`, `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java`, `framework/src/main/java/org/tron/core/consensus/ProposalService.java`)

### Summary
The reported zAuction issue is a class of bug where an "upgrade" only adds a new code path (`zAuctionAccountant` pointing to a new `zAuction`), without disabling the old path, so both remain simultaneously reachable and produce inconsistent/parallel state. java-tron has the same structural pattern with its staking/resource system: the "old" freeze/vote model (`FreezeBalanceContract`/`UnfreezeBalanceContract`) and the "new" model (`FreezeBalanceV2Contract`/`UnfreezeBalanceV2Contract`, gated by `ALLOW_NEW_RESOURCE_MODEL` / `UNFREEZE_DELAY_DAYS`) are never mutually exclusive at the actuator level.

### Finding Description
When the committee approves the `ALLOW_NEW_RESOURCE_MODEL` / `UNFREEZE_DELAY_DAYS` proposals, `ProposalService.process` simply flips a dynamic property and grants permission for the new contract types; it never revokes permission for the legacy `FreezeBalanceContract`/`UnfreezeBalanceContract` types [1](#0-0) [2](#0-1) .

`FreezeBalanceActuator.validate()` still accepts `BANDWIDTH`/`ENERGY` freeze requests unconditionally regardless of whether the new resource model/unfreeze-delay upgrade is active [3](#0-2) , and `UnfreezeBalanceActuator.validate()`/`execute()` likewise still process legacy unfreeze requests with the old fixed-duration unlock semantics — no unfreeze delay, no unfreezing-queue, no cap on unfreeze count — even after `supportUnfreezeDelay()`/`supportAllowNewResourceModel()` is turned on [4](#0-3) .

This mirrors the zAuction bug: the "old" auction/staking mechanism keeps accepting transactions in parallel with the "new" one after the admin/committee "upgrades" the system, and the two mechanisms interact through shared global state (`TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight`, vote-clearing logic, and `oldTronPower`/`FrozenV2` bookkeeping) that was designed assuming a single active model.

### Impact Explanation
The entire purpose of `UNFREEZE_DELAY_DAYS`/`FreezeBalanceV2` is to introduce a mandatory unfreeze delay (anti flash-freeze/vote-manipulation protection) for staking and voting weight. Because the legacy `FreezeBalanceContract`/`UnfreezeBalanceContract` actuators remain fully enabled and unrestricted after the upgrade, any account can continue to freeze and unfreeze TRX instantly via the old contract type, completely bypassing the delay that the new model was meant to enforce. This undermines the stake/voting economic security model (rapid freeze-vote-unfreeze cycles), and the coexistence of two parallel accounting paths (old `Frozen`/`TronPower` fields vs. new `FrozenV2` lists, with `oldTronPower`/`invalidateOldTronPower()` bridging logic) creates room for double-counted or inconsistent total resource weights, which affects consensus-relevant bandwidth/energy/vote accounting network-wide.

### Likelihood Explanation
No special privilege is required — any ordinary TRX holder can submit a `FreezeBalanceContract`/`UnfreezeBalanceContract` transaction at any time, before or after the committee-driven upgrade, since neither actuator's `validate()` checks whether the new model has superseded the old one. The only "trigger" needed is a normal governance proposal being approved (something that already happens on mainnet historically for `UNFREEZE_DELAY_DAYS`), after which the parallel-path condition exists indefinitely.

### Recommendation
When `ALLOW_NEW_RESOURCE_MODEL`/`UNFREEZE_DELAY_DAYS` is activated, `FreezeBalanceActuator`/`UnfreezeBalanceActuator` (and the corresponding `FreezeBalanceContract`/`UnfreezeBalanceContract` native-contract paths) should be disabled (e.g., via `addSystemContractAndSetPermission` removal or an explicit `validate()` check rejecting the contract type once the new model is supported), analogous to how `FreezeBalanceV2Actuator.validate()` already rejects V2 freezes when `supportUnfreezeDelay()` is false. This ensures only one staking/unfreeze model is ever active, eliminating the parallel-path inconsistency, matching the general recommendation from the source report to avoid keeping multiple versions of the same mechanism simultaneously active.

### Proof of Concept
1. Committee approves `UNFREEZE_DELAY_DAYS`/`ALLOW_NEW_RESOURCE_MODEL` proposal via `ProposalService.process`, which sets `dynamicStore.saveUnfreezeDelayDays(...)`/`saveAllowNewResourceModel(...)` and grants permission for `FreezeBalanceV2Contract` etc., but leaves `FreezeBalanceContract`/`UnfreezeBalanceContract` permissions untouched [2](#0-1) .
2. Any account submits a legacy `FreezeBalanceContract` (BANDWIDTH/ENERGY) transaction — `FreezeBalanceActuator.validate()` accepts it with no gating on the new model [5](#0-4) .
3. The account votes using the resulting weight, then immediately submits a legacy `UnfreezeBalanceContract` once `expireTime` passes — using the old, non-delayed unlock path (`UnfreezeBalanceActuator.execute`, `case BANDWIDTH/ENERGY` branch) [6](#0-5)  — receiving funds back instantly, without ever going through the new `FreezeBalanceV2`/`UnfreezeBalanceV2` delay/unfreezing-queue mechanism that governance intended to enforce chain-wide.

Note: I was not able to fully trace every downstream interaction between `oldTronPower`/`FrozenV2` weight accounting across both actuators within the available exploration; a Devin session with full repo/test access could confirm whether this discrepancy can be pushed further into a total-weight double-count or vote-manipulation exploit with concrete numeric PoC.
