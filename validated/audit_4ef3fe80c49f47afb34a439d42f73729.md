### Title
Replay window check/update race in `ConnectionState.Decrypt` allows duplicate packet processing - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt()` splits the anti-replay check into two separately-locked phases (`window.Check` then decrypt then `window.Update`) instead of holding the lock across the entire check-decrypt-mark sequence. This mirrors the reported bug class: a protective state check is performed against a value that can still change (or, here, race) before the corresponding state update actually takes effect, so a second operation can slip through against the stale "not yet seen" state.

### Finding Description
`Decrypt` in `connection_state.go` works in three steps: acquire `decryptLock`, call `cs.window.Check(l, messageCounter)`, release the lock; decrypt the ciphertext without holding any lock; then re-acquire `decryptLock` and call `cs.window.Update(l, messageCounter)` to actually mark the counter as consumed. [3](#0-2) 

Because the lock is dropped between `Check` and `Update`, the "has this counter already been seen" state used to gate processing is checked once but not committed until later — exactly the "outdated/stale check" pattern in the report, where a decision is made from a value that is not atomically tied to the subsequent state mutation. If Nebula is run with `f.routines > 1` (multiqueue), packets are dispatched to independent reader goroutines that each call `readOutsidePackets` → `ConnectionState.Decrypt` for the same `hostinfo`/`ConnectionState` without any per-connection serialization. [4](#0-3) [2](#0-1) 

An attacker with no CA-signed certificate — a pure network-position/on-path observer — can capture one legitimate ciphertext packet exchanged between two already-tunneled peers and retransmit ("replay") an exact duplicate of it back at the receiving host. If the duplicate arrives while the original is still mid-flight through `Decrypt` (between the `Check` and `Update` calls, e.g. landing on a different reader routine), the duplicate's `Check` call also observes the counter as unseen (since `Update` for the original hasn't run yet), and both copies proceed to decrypt and process the same plaintext application payload. This directly undermines the purpose of `Bits`/`ReplayWindow`, which is designed specifically to reject duplicate counters. [5](#0-4) 

### Impact Explanation
A successful race delivers the same already-authenticated tunnel payload twice into `handleOutsideMessagePacket`/TUN write, i.e., a genuine packet-processing duplication/replay despite the anti-replay window explicitly existing to prevent this. Depending on payload semantics this can duplicate application-level side effects (e.g., idempotency-sensitive operations, duplicate transaction replays over the tunnel) purely by an on-path attacker duplicating one observed ciphertext, without ever needing key material, a certificate, or any authentication.

### Likelihood Explanation
Exploitation requires: (1) `routines > 1` (multiqueue enabled, a supported and documented configuration), and (2) precise timing to land the duplicate packet in the narrow window between `Check` and `Update` on a different worker goroutine — narrower than the balance-staleness window in the original report, but still non-zero and remotely triggerable by simple UDP packet duplication (which is trivial for any network path attacker, no cryptographic material needed to synthesize the duplicate). Likelihood is Medium given the deterministic, reachable race window and the fact that packet duplication is a normal capability of an unauthenticated network attacker.

### Recommendation
Hold `decryptLock` for the entire duration of the check-decrypt-mark sequence (or otherwise reserve the counter slot atomically before releasing the lock for decryption, then roll back/free the reservation on decrypt failure) so that a second packet with the same `messageCounter` cannot pass `Check` until the first packet's outcome (success or failure) has been committed to the window state.

### Proof of Concept
1. Configure a Nebula host with `routines: 2` (or more) so `f.routines > 1`, enabling concurrent UDP reader goroutines. [6](#0-5) 
2. Establish a tunnel between two hosts and observe one legitimate encrypted `header.Message` packet with counter `N` in transit (as any on-path attacker can, since ciphertext is visible on the wire).
3. Duplicate the captured UDP datagram and send it to the receiver's listener a second time, timed so it lands on a different reader goroutine than the original while the original's `Decrypt` call is between its `Check` and `Update` phases. [3](#0-2) 
4. Both copies pass `window.Check` (since `window.Update` for the first has not yet executed), both successfully `DecryptDanger`, and both are forwarded on for further processing — demonstrating the same tunnel message being accepted and processed twice, contrary to the replay-window's guarantee.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
