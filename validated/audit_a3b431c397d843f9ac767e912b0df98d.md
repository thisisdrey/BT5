### Title
Unreliable `assert totalEnergyWeight > 0` guard makes `RepositoryImpl.calculateGlobalEnergyLimit` divide by zero on every TVM call once `TotalEnergyWeight` is 0, reverting/freezing all subsequent contract-triggering transactions - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit()` is the exact analog of the ZeroLend `rewardPerToken()` bug: a value (`derivedSupply` / `totalEnergyWeight`) is assumed non-zero and only "checked" via a mechanism that does not actually enforce the invariant at runtime (`if (totalSupply==0)` guarding the wrong denominator vs. `assert totalEnergyWeight > 0` which is compiled out in production JVMs), and is then used unconditionally as a division denominator that any unprivileged user's transaction can trigger.

### Finding Description
`calculateGlobalEnergyLimit(AccountCapsule accountCapsule)` computes an account's energy limit from its frozen-for-energy balance and the network-wide `TotalEnergyLimit`/`TotalEnergyWeight` ratio: [1](#0-0) 

The only "guard" against `totalEnergyWeight == 0` is a Java `assert` statement, which is a no-op unless the JVM is started with `-ea` (assertions are disabled by default in production JVMs, including java-tron's standard startup scripts). If `totalEnergyWeight` is 0 when this method is reached:
- In the hardened path (`hardenResourceCalculation()==true`), `BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException`.
- In the legacy `double` path, `totalEnergyLimit / totalEnergyWeight` produces `Infinity`, and the subsequent cast `(long)` silently produces a corrupted, effectively unlimited energy limit rather than a clean revert — an "unbacked" resource value.

This is precisely analogous to the GaugeIncentiveController bug: `rewardPerToken()` checks `totalSupply == 0` but divides by a *different* variable, `derivedSupply`, that is not covered by that check and can independently be zero, causing a real division-by-zero revert. Here, the code even documents the invariant it relies on (`assert totalEnergyWeight > 0`) but does not actually enforce it at runtime, so if that invariant is ever violated, the division proceeds unguarded.

By contrast, the sibling implementation `EnergyProcessor.calculateGlobalEnergyLimit()` in the chain-level accounting path *does* have a real runtime guard for one code path (`if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) return 0;`) but falls through to the same unenforced `assert` when `allowNewReward()` is false, showing the guard is incomplete/config-dependent rather than universal: [2](#0-1) 

`RepositoryImpl.calculateGlobalEnergyLimit()` is reached from `VMActuator.getTotalEnergyLimitWithFixRatio()`, which is invoked on **every** smart-contract-triggering transaction to compute the contract creator's available energy from frozen balance: [3](#0-2) 

This is one of the most heavily-used code paths in the actuator — any unprivileged user submitting a `TriggerSmartContractContract` transaction will invoke it.

### Impact Explanation
If `TotalEnergyWeight` (a chain-wide dynamic property, decremented/incremented by freeze/unfreeze-for-energy operations) ever reaches zero — e.g., right after the last energy-frozen account fully unfreezes and before any new freeze — then:
1. Every subsequent `TriggerSmartContract` transaction from any account that goes through `getTotalEnergyLimitWithFixRatio` → `calculateGlobalEnergyLimit` will hit the unguarded division.
2. With hardened resource calculation enabled, this throws an uncaught `ArithmeticException`, which would either revert the actuator execution unexpectedly or, if not caught by the surrounding actuator dispatch, could crash the node process handling the transaction — freezing all smart-contract execution on the network (temporary freezing of funds/functionality) until `TotalEnergyWeight` becomes non-zero again.
3. With hardened calculation disabled, the legacy double-division silently yields an unbounded/corrupted energy limit (`Infinity` cast to `long`), letting a contract creator consume energy far beyond their legitimately frozen backing — an unbacked-resource condition analogous to "theft of unclaimed yield" in the original report (here, theft of network energy resources without payment).

### Likelihood Explanation
`TotalEnergyWeight` reaching exactly zero requires all currently energy-frozen TRX across the entire network to be unfrozen simultaneously, which is unlikely on an established mainnet with many participants, but is plausible on new networks, private/consortium chains, low-participation testnets, or immediately after protocol-level resource-model migrations (e.g., v1→v2 unfreeze transitions) where frozen-for-energy balances can transiently go to zero. The reliance on an `assert` (rather than an explicit runtime check as done conditionally in `EnergyProcessor`) means this is a real code-quality/robustness gap: the invariant the developers intended to enforce is not actually enforced in a standard production deployment (assertions disabled by default).

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit()` with an explicit runtime check (mirroring the guard already present in `EnergyProcessor.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2`, i.e., `if (totalEnergyWeight <= 0) return 0;`) unconditionally, regardless of `allowNewReward()`/feature-flag state, so the code never relies on JVM assertions for a security-relevant invariant. Apply the same explicit-check pattern to `calculateGlobalNetLimit`-family code paths that share `totalNetWeight`/`totalEnergyWeight` denominators.

### Proof of Concept
Not independently reproducible from static analysis alone — a live/local java-tron network would be needed to drive `TotalEnergyWeight` to zero (e.g., freeze a small amount for energy, then fully unfreeze it, ensuring no other account holds energy-frozen balance) and then submit a `TriggerSmartContractContract` transaction from an account with `allFrozenBalanceForEnergy >= TRX_PRECISION`, observing the `ArithmeticException` (hardened path) or corrupted energy-limit value (legacy double path) inside `RepositoryImpl.calculateGlobalEnergyLimit`. This mirrors the reported PoC pattern (drive the denominator to 0, then trigger the guarded function via a normal user action) but requires a running node/testnet to execute, which is outside the scope of this static code review.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
