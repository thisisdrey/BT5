## Title
Permanent DoS in `pallet-asset-rewards`: `reward_per_token` overflow reverts `stake`/`unstake`/`harvest_rewards` for all stakers - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards`'s `reward_per_token` computes `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked` using two sequential `ensure_mul` calls before a single `ensure_div`, exactly the pattern flagged in the referenced Locke.sol finding (multiply-then-divide overflow, with the divide-back never reached). Any DispatchError from this checked arithmetic bubbles straight up through `update_pool_and_staker_rewards`, which is called at the very start of `stake`, `unstake`, and `harvest_rewards`. Because the corrupted computation depends on pool-level state (`reward_rate_per_block`, elapsed blocks, `total_tokens_staked`) rather than being reset per call, once the intermediate product exceeds `T::Balance::MAX` the failure recurs on every future call for every staker in that pool, not just the account that caused it.

### Finding Description
`reward_per_token` is defined as: [1](#0-0) 

```rust
let rewardable_blocks_elapsed: u32 = ...;
Ok(pool_info.reward_per_token_stored.ensure_add(
    pool_info
        .reward_rate_per_block
        .ensure_mul(rewardable_blocks_elapsed.into())?
        .ensure_mul(PRECISION_SCALING_FACTOR.into())?
        .ensure_div(pool_info.total_tokens_staked)?,
)?)
```

This is the same multiply-multiply-divide overflow shape as `Locke.sol#L229`: the code multiplies `reward_rate_per_block` by both `rewardable_blocks_elapsed` and `PRECISION_SCALING_FACTOR` *before* dividing by `total_tokens_staked`. If the true mathematical result (after division) would fit comfortably in `T::Balance`, but the intermediate product does not, `ensure_mul` returns `Err` (an `ArithmeticError`) instead of the correct scaled value — exactly the "reverts due to overflow for higher values, but strictly less than the type's max" bug class from the report.

`update_pool_and_staker_rewards` — invoked unconditionally as the first step of `stake`, `unstake`, and `harvest_rewards` — propagates this error with `?`: [2](#0-1) [3](#0-2) [4](#0-3) 

Because `reward_rate_per_block` can only be *increased* by the admin (`set_pool_reward_rate_per_block` enforces `new_reward_rate_per_block > pool_info.reward_rate_per_block`, see `Error::RewardRateCut`), and `rewardable_blocks_elapsed` grows every block that `update_pool_rewards` isn't called, the product `reward_rate_per_block * rewardable_blocks_elapsed * PRECISION_SCALING_FACTOR` grows monotonically for a stale/low-activity pool. Once this product exceeds `T::Balance::MAX` for a pool's configured `reward_rate_per_block`, **every subsequent call to `stake`, `unstake`, or `harvest_rewards` for that pool by any staker fails**, because `reward_per_token` is called before any other logic in each of those extrinsics and there is no fallback or two-step scaling as recommended in the original report.

### Impact Explanation
This is a public, unprivileged-triggerable, permanent denial of service on user funds: stakers with tokens frozen (`AssetsFreezer::increase_frozen`) in the pool would be permanently unable to call `unstake` to unfreeze and withdraw their staked assets, and unable to `harvest_rewards`, once the pool enters this overflow state — mirroring the "user will not able to withdraw funds permanently" impact in the source report. Because `total_tokens_staked` sits in the denominator, pools with a large `reward_rate_per_block` relative to `total_tokens_staked`, or pools where updates are infrequent (elapsed blocks accumulate), are particularly exposed; an admin increasing `reward_rate_per_block` (a legitimate, expected admin action, not privileged abuse of the bug) or simply blocks passing without anyone calling `stake`/`unstake`/`harvest_rewards` can push the intermediate product past the overflow threshold with no way to walk it back once stuck, since there's no operation that reduces `reward_rate_per_block` or forcibly resets `last_update_block` independent of this same code path.

### Likelihood Explanation
No malicious peer/validator/relayer/admin-abuse is required — any account can call `stake` to seed a pool's `total_tokens_staked`, and normal admin usage of the intentionally allowed `set_pool_reward_rate_per_block` increase, or the mere passage of blocks without pool interaction, drives `rewardable_blocks_elapsed` upward. Given `T::Balance` is typically `u128` in production runtimes, actually reaching overflow requires large `reward_rate_per_block * PRECISION_SCALING_FACTOR` products, but the report explicitly calls out that this class of bug triggers well below `type(uint112).max` (i.e., far below the type's true maximum) purely due to the multiply-before-divide ordering, so the threshold is much lower than `T::Balance::MAX` and reachable via ordinary pool configuration and normal elapsed-time growth rather than needing an intentionally malicious value.

### Recommendation
Reorder the arithmetic to divide earlier or use a wider intermediate type before narrowing back to `T::Balance`, per the original report's mitigation: e.g. compute the numerator in `u256`/a wider type, or divide `PRECISION_SCALING_FACTOR` into `total_tokens_staked` first where safe, or clamp `reward_per_token` growth. Concretely, in `reward_per_token` (`substrate/frame/asset-rewards/src/lib.rs`), perform the multiplication step-wise with intermediate division, or upcast `reward_rate_per_block`, `rewardable_blocks_elapsed`, and `PRECISION_SCALING_FACTOR` to `u256`-equivalent arithmetic before dividing by `total_tokens_staked` and downcasting, ensuring the final result fits `T::Balance` without ever requiring the un-divided intermediate product to fit.

### Proof of Concept
1. Admin calls `create_pool` with a `reward_rate_per_block` set near a value where `reward_rate_per_block * PRECISION_SCALING_FACTOR` is a sizeable fraction of `T::Balance::MAX` (see constant used at [5](#0-4) ).
2. A staker calls `stake` once to set `total_tokens_staked` to a small nonzero value, then no one interacts with the pool for many blocks so `rewardable_blocks_elapsed` in `reward_per_token` grows large — see the computation at lines 794-809 of the same file: `reward_rate_per_block.ensure_mul(rewardable_blocks_elapsed.into())?.ensure_mul(PRECISION_SCALING_FACTOR.into())?`.
3. Once `reward_rate_per_block * rewardable_blocks_elapsed * PRECISION_SCALING_FACTOR` exceeds `T::Balance::MAX`, the first `ensure_mul` (or second) returns `Err(ArithmeticError::Overflow)`.
4. Any subsequent call to `stake`, `unstake`, or `harvest_rewards` for this pool — by any staker, including one trying to withdraw their entire stake — calls `update_pool_and_staker_rewards` → `reward_per_token`, hits the same overflow, and the whole extrinsic reverts with `DispatchError`, permanently freezing all stakers' assets in that pool (frozen via `AssetsFreezer::increase_frozen` at line 482-487) with no code path to reset `reward_rate_per_block` downward or bypass this calculation.
