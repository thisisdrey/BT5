### Title
Unbounded reference processing in `ObjectPool.FetchFromOrigin` allows resource-exhaustion DoS via ref-bomb origin repository - ([File: internal/git/objectpool/fetch.go])

### Summary
`FetchIntoObjectPool` invokes `ObjectPool.FetchFromOrigin`, which calls `pruneReferences` and `rescueDanglingObjects`. Both functions stream the full output of `git remote prune --dry-run` and `git fsck --connectivity-only --dangling` line-by-line into an in-process `updateref.Updater` transaction with no cap on the number of refs, no timeout, and no backpressure. A repository with an extremely large number of unique refs (attacker-controlled content, since the attacker owns/controls the origin repository) will cause a single RPC invocation to build an enormous single reference-transaction (unbounded memory for queued updates, unbounded git-update-ref stdin, and unbounded vote-hash computation over every deleted/dangling ref), consuming CPU/memory/disk proportional to attacker-chosen ref count.

### Finding Description
`server.FetchIntoObjectPool` (`internal/gitaly/service/objectpool/fetch_into_object_pool.go:16-57`) only validates that origin and pool repositories share a storage name [1](#0-0) ; it does not bound the size or ref-count of the origin repository before calling `objectPool.FetchFromOrigin`.

Inside `FetchFromOrigin` (`internal/git/objectpool/fetch.go:31-142`), `o.pruneReferences(ctx, origin)` is called before the fetch. `pruneReferences` spawns `git remote prune --dry-run`, then reads its output with a `bufio.Scanner` in a loop, queuing every "would prune" line into an `updateref.Updater` and updating a `voting.VoteHash` per line, with no maximum ref count and no context deadline enforced at this layer [2](#0-1) . Similarly, `rescueDanglingObjects` streams `git fsck --connectivity-only --dangling` output and queues an `updater.Create` call for every dangling object line, again with no cap [3](#0-2) . Both updaters are ultimately committed in a single call (`updater.Commit()`), meaning the entire batch of ref operations must be held and processed as one unit [4](#0-3) [5](#0-4) .

Since an attacker fully controls the content of a repository they own (via push/fork), they can create millions of divergent, non-shared-history refs. When that repository is fetched into an object pool it's linked to, the resulting scan and update-ref transaction size scales linearly (or worse) with the attacker-chosen ref count, with no configured upper bound visible in this code path.

### Impact Explanation
This causes unbounded CPU, memory, and disk I/O consumption on the Gitaly node hosting the shared storage for the duration of a single RPC, since the entire ref list must be scanned and staged before any commit happens. Because object pools are shared infrastructure serving multiple projects/forks on the same Gitaly storage, sustained resource exhaustion from one attacker-controlled repository can degrade or deny service to other tenants co-located on that storage — matching a DoS-of-handler impact class.

### Likelihood Explanation
The attacker only needs standard, unprivileged push/fork capability to create a large-ref repository; no admin role, secret, or non-default configuration is required. The remaining precondition is that this repository must be (or become) an origin fetched into an object pool — this normally happens automatically as part of GitLab's fork-network/object-pool housekeeping, which is triggered by ordinary usage (forking, pushing) rather than by privileged action, and recurs periodically, making repeated exploitation feasible. The RPC itself (`FetchIntoObjectPoolRequest`) is only invoked by GitLab Rails/internal callers rather than being directly reachable by an external gRPC client, but the attacker fully controls the triggering condition (ref-bomb content) and this call recurs as part of normal object-pool maintenance.

### Recommendation
Enforce bounds before/while processing prune and fsck output in `internal/git/objectpool/fetch.go`: cap the number of refs processed per `pruneReferences`/`rescueDanglingObjects` invocation (batching updater commits instead of one giant transaction), add a context-based deadline/cancellation check inside the scanner loops, and consider rejecting or flagging origin repositories whose ref count exceeds a configurable threshold before attempting `FetchFromOrigin`.

    const N = 500000

    start := time.Now()

    require.NoError(t, err)

    runtime.ReadMemStats(&memAfter)
    t.Logf("elapsed=%s allocDelta=%dMB", time.Since(start),

    // Expect: wall-clock time and allocated memory scale roughly linearly
    // with N and are unbounded by any handler-imposed cap.

Running this with increasing `N` (10^5 → 10^6) is expected to show unbounded linear-or-worse growth in wall-clock time and memory for a single `FetchIntoObjectPool`/`FetchFromOrigin` call, confirming the absence of any enforced cap in `pruneReferences` and `rescueDanglingObjects`.

		// worth it given that the output is comparatively simple and given that the pruned

			continue

			continue
		case bytes.HasPrefix(line, []byte(" * [would prune] ")):

		}
