### Title
Global (unscoped) `http.extraHeader` config in `cloneFromURLCommand` leaks credentials to redirected/attacker-controlled hosts and DNS-pinning (`resolvedAddress`) does not cover redirect targets, enabling SSRF and header disclosure - (File: `internal/gitaly/service/repository/create_repository_from_url.go`)

### Summary
`cloneFromURLCommand` builds the git-config used for `git clone` from the caller-supplied `Url`/`HttpAuthorizationHeader`, and — unlike the equivalent code paths in `fetch_remote.go`'s `buildCommandOpts` and `remote/find_remote_root_ref.go` — sets a **global** `http.extraHeader` instead of a URL-scoped `http.<url>.extraHeader`. Combined with Git's default `http.followRedirects=initial` behavior and the fact that `resolvedAddress`/`curloptResolve` pinning only applies to the *original* host, a malicious remote can redirect the initial request to a different, attacker-chosen host and both receive the `Authorization` header and cause Gitaly to fetch from an unresolved/unpinned destination.

### Finding Description
In `cloneFromURLCommand` (`internal/gitaly/service/repository/create_repository_from_url.go:41-58`), the authorization header is attached with an unscoped key: [1](#0-0) 

By contrast, the sibling implementations for `FetchRemote` and `FindRemoteRootRef` scope the header to the exact remote URL via `http.<url>.extraHeader`, which Git only attaches to requests matching that URL: [2](#0-1) [3](#0-2) 

Because `cloneFromURLCommand` instead sets the plain `http.extraHeader` key, the header applies to **every** HTTP request Git makes for that invocation — including requests to a host reached via an HTTP redirect from the original URL. Git's default `http.followRedirects` setting is `initial`, meaning Git will follow a redirect on the first ref-discovery request and then treat the redirected URL as the new base for the rest of the session. The anti-SSRF/DNS-rebinding defense implemented via `resolvedAddress` → `gitcmd.GetURLAndResolveConfig` (`internal/git/gitcmd/command_resolve.go:81-105`) only pins the IP for the *original* hostname:port pair (`http.curloptResolve`); it does nothing for a different host reached through a redirect, so that second host undergoes normal, unpinned DNS resolution. [4](#0-3) 

Combining these two facts: an attacker who owns/controls the source server for `CreateRepositoryFromURL` (a repo owner importing their own project from an attacker-hosted URL) can have that server issue a redirect during the initial fetch to an internal address (e.g. cloud metadata endpoint or an internal-only Gitaly/GitLab service) that was never validated or IP-pinned, and the outbound request will still carry the `Authorization` header meant only for the original host. Note the code explicitly disables `transfer.bundleURI` for exactly this class of SSRF risk (line 72-75), showing the maintainers are aware of and mitigate the bundle-URI vector but did not scope `http.extraHeader` the same way the fetch/mirror code paths do. [5](#0-4) 

### Impact Explanation
- **SSRF**: The redirect target is not subject to the `resolvedAddress` DNS-pinning validation that GitLab Rails/Gitaly rely on to stop DNS-rebinding/SSRF for the primary host, so Gitaly can be made to issue outbound HTTP requests to internal-only endpoints chosen entirely by the attacker's own server via a redirect.
- **Credential/auth-header disclosure**: Because `http.extraHeader` is global rather than URL-scoped, any `Authorization` header configured for the request (whether embedded basic-auth from the URL or a caller-supplied `HttpAuthorizationHeader`/`authorizationToken`) is also sent to the redirect target host, which in scenarios where the token is a real secret unknown to the attacker (e.g. GitLab-issued import tokens) constitutes credential disclosure to an attacker-controlled host.

Both map to the target's cited GitLab HackerOne impact classes (SSRF to internal endpoint / credential-header disclosure to attacker host).

### Likelihood Explanation
An unprivileged GitLab user with "import project from URL" capability fully controls the `Url` field and can host the malicious server themselves (no special role or infra access needed beyond running a small HTTP server that returns a 3xx redirect). This requires no MITM, no privileged Gitaly configuration change, and is reproducible on any default Gitaly install since `http.followRedirects` defaults to `initial` in stock Git and Gitaly does not override it in `cloneFromURLCommand`.

### Recommendation
Scope the header exactly as the other call sites do: use `http.<url>.extraHeader` (keyed off the pre-redirect URL) instead of the bare `http.extraHeader` key in `cloneFromURLCommand`, and additionally set `http.followRedirects=false` (or validate/re-pin any redirect target against the same SSRF allow-list/DNS-pinning logic used for the original host) before performing the clone.

### Proof of Concept
```go
// Pseudo Go test sketch for create_repository_from_url_test.go
func TestCreateRepositoryFromURL_RedirectLeaksAuthHeader(t *testing.T) {
    var capturedAuthOnRedirectTarget string

    // attacker-controlled "redirect target" server records incoming Authorization header
    redirectTarget := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        capturedAuthOnRedirectTarget = r.Header.Get("Authorization")
        w.WriteHeader(http.StatusNotFound)
    }))
    defer redirectTarget.Close()

    // attacker-controlled "source" server issues a 301 to redirectTarget on the initial info/refs request
    source := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        http.Redirect(w, r, redirectTarget.URL+r.URL.Path, http.StatusMovedPermanently)
    }))
    defer source.Close()

    _, err := client.CreateRepositoryFromURL(ctx, &gitalypb.CreateRepositoryFromURLRequest{
        Repository:              repoProto,
        Url:                     source.URL + "/some/repo.git",
        HttpAuthorizationHeader: "Bearer super-secret-token",
    })
    // clone will fail (404) but the assertion of interest is:
    require.NotEmpty(t, capturedAuthOnRedirectTarget, "Authorization header leaked to redirect target host")
}
```
Expected result on the vulnerable code: `capturedAuthOnRedirectTarget` is non-empty, proving the header configured for `source` leaked to the unrelated `redirectTarget` host. After scoping the config key to `http.<source-url>.extraHeader` and/or disabling redirects, the header should not reach `redirectTarget`.

```go
func getURLAndResolveConfigForURL(remoteURL, resolvedAddress string) (string, []ConfigPair, error) {
	u, err := url.ParseRequestURI(remoteURL)
	if err != nil {
		return "", nil, fmt.Errorf("couldn't parse remoteURL: %w", err)
	}

	port := u.Port()

	if port == "" {
		switch u.Scheme {
		case "http":
			port = "80"
		case "https":
			port = "443"
		case "git":
			port = "9418"
		default:
			return "", nil, fmt.Errorf("unknown schema provided: %s", u.Scheme)
		}
	}

	return remoteURL, []ConfigPair{
		{Key: "http.curloptResolve", Value: fmt.Sprintf("%s:%s:%s", u.Hostname(), port, resolvedAddress)},
	}, nil
}
```
