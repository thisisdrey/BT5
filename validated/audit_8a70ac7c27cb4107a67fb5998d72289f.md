## Analog Vulnerability Confirmed

### Title
Missing slippage/minimum-output protection in `ExchangeWithdrawContract` and `ExchangeInjectContract` enables sandwich-attack fund loss - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
The TRC10 bancor-style exchange module has three trade-affecting broadcastable contracts: `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract`. Only `ExchangeTransactionContract` carries a user-supplied `expected` (minimum output) field that is checked before execution. [1](#0-0)  `ExchangeInjectContract` and `ExchangeWithdrawContract` have no equivalent slippage-limit field. [2](#0-1)  Their counterparty amount is computed purely from the pool's live reserve ratio at execution time, exactly the class of bug described in the report ("no user-specified minimum amount... no check for withdrawnAmount0 and amount0OutMin").

### Finding Description
In `ExchangeWithdrawActuator.doValidate()` / `execute()`, the amount of the "other" token returned to the caller (`anotherTokenQuant`) is derived solely from the current pool reserves (`firstTokenBalance`, `secondTokenBalance`) and the requested `tokenQuant`, with no caller-supplied lower bound: [3](#0-2) 

The same pattern occurs in `ExchangeInjectActuator`, where `anotherTokenQuant` (the amount deducted from the caller for the paired token) is computed from the live ratio with no caller-supplied upper bound: [4](#0-3) 

By contrast, `ExchangeTransactionActuator` explicitly validates the computed output against a user-specified `expected` field and reverts otherwise: [5](#0-4) 

This asymmetry means the developers already recognized and mitigated the slippage risk for `ExchangeTransactionContract`, but left `ExchangeWithdrawContract`/`ExchangeInjectContract` unprotected. Any account can create a TRC10 exchange pool via `ExchangeCreateContract` and become its `creatorAddress`, which is the only permission needed to later call `ExchangeWithdrawContract` (checked at `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())`), and any account whatsoever can call `ExchangeInjectContract`. [6](#0-5)  Because the reserve ratio can be moved by any third party broadcasting an ordinary `ExchangeTransactionContract` trade against the same pool (an unprivileged, permissionless operation) in a preceding transaction of the same block or an earlier block, a withdraw/inject transaction that was signed based on one ratio can be executed against a manipulated ratio, with no way for the signer to bound their loss.

### Impact Explanation
This is a concrete, unauthorized value-extraction path (theft of funds) reachable by any unprivileged account: an attacker can watch the pending-transaction pool for a target's `ExchangeWithdrawContract` (which withdraws LP-style dual-token liquidity) or `ExchangeInjectContract`, then submit a large `ExchangeTransactionContract` swap against the same exchange to skew `firstTokenBalance`/`secondTokenBalance` immediately before the target transaction executes, and reverse the skew afterward (classic sandwich). Because there is no `expected`/minimum-output (withdraw) or maximum-input (inject) bound, the victim's transaction executes at the manipulated ratio, causing them to receive far less value on withdraw, or pay far more on inject, than intended — with the difference captured by the attacker. This directly matches the Sherlock report's "Medium" impact class: value loss under sandwich attacks due to missing slippage parameters.

### Likelihood Explanation
Both `ExchangeWithdrawContract` and `ExchangeInjectContract` are ordinary broadcastable transactions reachable by any signed account through the standard wallet/HTTP APIs (e.g. `/wallet/exchangewithdraw`, `/wallet/exchangeinject`), requiring no special privilege beyond having created or being a participant of the exchange. TRC10 exchanges are a long-standing, permissionless java-tron feature (`ExchangeCreateContract` can be called by anyone), so exploitation only requires normal transaction broadcasting and does not depend on malicious SRs, witnesses, or peers.

### Recommendation
Add slippage-guard fields to `ExchangeInjectContract` and `ExchangeWithdrawContract` (e.g., `expected`/minimum `anotherTokenQuant` for withdraw, and a maximum `anotherTokenQuant` cap for inject), and enforce them in `ExchangeWithdrawActuator.doValidate()` / `ExchangeInjectActuator.doValidate()` the same way `ExchangeTransactionActuator` already validates `tokenExpected` against the computed `anotherTokenQuant`.

### Proof of Concept
1. Attacker or arbitrary user creates a TRC10 exchange pool P(A,B) via `ExchangeCreateContract`, or targets an existing pool.
2. Victim (the pool creator/owner) broadcasts `ExchangeWithdrawContract{exchangeId, tokenId=A, quant=X}` expecting to receive `Y = reserveB * X / reserveA` of token B, based on the ratio observed when signing.
3. Before the victim's transaction executes, an attacker broadcasts an `ExchangeTransactionContract` trade against the same `exchangeId` that shifts `reserveA`/`reserveB` substantially (this is fully permissionless via the same actuator class shown at `ExchangeTransactionActuator`).
4. The victim's withdraw executes against the shifted reserves in `ExchangeWithdrawActuator.execute()`, computing a much smaller `anotherTokenQuant` than the victim expected, with no `expected`/minimum check to abort the transaction. [7](#0-6) 
5. Attacker reverses their swap in a follow-up transaction, restoring the ratio and pocketing the value difference extracted from the victim's withdrawal.
