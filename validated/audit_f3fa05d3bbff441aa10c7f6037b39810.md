Based on tracing the full forwarding path, the two clamps work together consistently and there is no divergence causing permanent freezing.

Key trace:
- `try_forward` (`runtime/runtime/src/congestion_control.rs:403-463`) receives the *real* receipt `size` as an owned parameter and only mutates its own local copy for the size-limit comparison (`if size > max_receipt_size { size = max_receipt_size; }`, lines 418-426). The comparison at line 451 (`forward_limit.size >= size`) uses this clamped value, so once the bandwidth scheduler grants `forward_limit.size >= max_receipt_size` on that link, the oversized receipt passes the check and is pushed to `outgoing_receipts` in full (the actual, unclamped receipt object). [1](#0-0) [2](#0-1) 

- The caller `forward_from_buffer_to_shard` computes `size` via `receipt_size(&receipt)?` (the true, uncapped size) *before* calling `try_forward`; because Rust passes `size` by value, `try_forward`'s internal clamp does not mutate the caller's `size` variable. After a successful forward, the caller uses this same true `size` to decrement `own_congestion_info.remove_receipt_bytes(size)` and to update `outgoing_metadatas_updates`/`ReceiptGroupsQueue` via `update_on_receipt_popped`. [3](#0-2) 

- `ReceiptGroupsQueue::update_on_receipt_pushed`/`update_on_receipt_popped` both add/subtract the same real `receipt_size` (`ByteSize`), so `total_size` stays exactly consistent with the buffer contents at push and pop time — there is no divergence introduced by the request-generation clamp. [4](#0-3) 

- The request-generation clamp in `generate_bandwidth_request` (`congestion_control.rs:556-562`) only affects what value is *requested* from the scheduler — it caps the requested bitmap value at `max_receipt_size` so the scheduler doesn't try to satisfy an unfulfillable value. Combined with `BandwidthSchedulerParams::max_single_grant` being documented as "at least as big as `max_receipt_size`" (`core/primitives/src/bandwidth_scheduler.rs:293-295`), the scheduler can and eventually will grant at least `max_receipt_size` bandwidth on that link once requested, satisfying the clamped comparison inside `try_forward`. [5](#0-4) [6](#0-5) 

So the oversized receipt does not permanently stall: once the granted bandwidth for that link reaches `max_receipt_size` (guaranteed to eventually happen because the request asks for exactly that, clamped, value), `try_forward`'s own independent clamp (already present before the request-generation clamp was added, itself referencing issue #12606) lets the comparison succeed and the full, real-sized receipt is forwarded and correctly deducted everywhere (`own_congestion_info`, `ReceiptGroupsQueue.total_size`). The two clamps are two independent instances of the same intentional workaround, not competing/divergent logic, and they jointly preserve liveness for oversized receipts. There is consequently no unbounded, indefinite re-scan cost either — the entry is removed from the buffer as soon as sufficient bandwidth accumulates, same as any other buffered receipt.

    pub fn update_on_receipt_pushed(
        &mut self,
        receipt_size: ByteSize,
        receipt_gas: Gas,
        state_update: &mut TrieUpdate,
        groups_config: &ReceiptGroupsConfig,
    ) -> Result<(), StorageError> {
        add_size_checked(&mut self.data.total_size, receipt_size);
        add_gas_checked(&mut self.data.total_gas, receipt_gas);
        self.data.total_receipts_num = self
            .data
            .total_receipts_num
            .checked_add(1)
            .expect("Overflow! - Number of receipts doesn't fit into u64!");

        // Take out the last group from the queue and inspect it.
        match self.pop_back(state_update)? {
            Some(mut last_group) => {
                if groups_config.should_start_new_group(&last_group, receipt_size, receipt_gas) {
                    // Adding the new receipt to the last group would make the group too large.
                    // Start a new group for the receipt.
                    self.push_back(state_update, &last_group).expect("Integer overflow on push");
                    self.push_back(state_update, &ReceiptGroup::new(receipt_size, receipt_gas))
                        .expect("Integer overflow on push");
                } else {
                    // It's okay to add the new receipt to the last group, do it.
                    add_size_checked(last_group.size_mut(), receipt_size);
                    add_gas_checked(last_group.gas_mut(), receipt_gas);
                    self.push_back(state_update, &last_group).expect("Integer overflow on push");
                }
            }
            None => {
                // No groups in the queue, start a new group which contains the new receipt.
                self.push_back(state_update, &ReceiptGroup::new(receipt_size, receipt_gas))
                    .expect("Integer overflow on push");
            }
        }

        Ok(())
    }

    pub fn update_on_receipt_popped(
        &mut self,
        receipt_size: ByteSize,
        receipt_gas: Gas,
        state_update: &mut TrieUpdate,
    ) -> Result<(), StorageError> {
        subtract_size_checked(&mut self.data.total_size, receipt_size);
        subtract_gas_checked(&mut self.data.total_gas, receipt_gas);

        self.data.total_receipts_num = self
            .data
            .total_receipts_num
            .checked_sub(1)
            .expect("Underflow! - More receipts were popped than pushed!");

        assert!(self.data.indices.len() > 0, "No receipt groups to pop from!");

        self.modify_first(state_update, |mut first_group| {
            subtract_size_checked(first_group.size_mut(), receipt_size);
            subtract_gas_checked(first_group.gas_mut(), receipt_gas);
            if first_group.is_empty() {
                // No more receipts in the first group, remove it.
                None
            } else {
                // Still some receipts in the group. Save the updated group.
                Some(first_group)
            }
        })
    }
