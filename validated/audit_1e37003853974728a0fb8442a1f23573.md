### Title
Dust-transfer griefing permanently consumes a victim's bounded per-account token slots, blocking new deposits and new debt positions - ([File: contracts/Pool.sol](contracts/Pool.sol), [File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The kernel bug (CVE-2019-19071) leaks an allocation on every failure of `rsi_prepare_beacon()`, so repeated attacker-triggered failures exhaust a finite resource. The direct Metronome analog is the per-account token bookkeeping: every time an account's balance of a `DepositToken` goes from 0 to non-zero, `Pool.addToDepositTokensOfAccount()` allocates a permanent slot in `depositTokensOfAccount`, and `Pool.addToDebtTokensOfAccount()` does the same for `debtTokensOfAccount`. Both are gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts with `UserReachedMaxTokens` once the combined count hits `MAX_TOKENS_PER_USER`. An unprivileged attacker can "leak" these bounded slots in a victim's account by dust-transferring every whitelisted deposit token to them, after which any first-time receipt of an additional deposit or debt token reverts.

### Finding Description
- `DepositToken._transfer()` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever `_recipientBalanceBefore == 0 && amount_ > 0` (`contracts/DepositToken.sol:517-520`). There is no opt-in: any holder of any whitelisted ms-token can force a slot allocation onto any address by sending `amount_ = 1 wei`.
- `Pool.addToDepositTokensOfAccount()` enforces `onlyIfAdditionWillNotReachMaxTokens(account_)`, reverting once `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` (`contracts/Pool.sol:143-148`, `contracts/Pool.sol:216-220`).
- The identical guard sits on `addToDebtTokensOfAccount()` (`contracts/Pool.sol:204-208`), which `DebtToken` calls when an account mints/issues a synthetic asset for the first time. Once the list is full, the victim cannot mint any *new* synthetic token type, and cannot receive any *new* deposit token type — `transfer`, `transferFrom`, `deposit(amount, onBehalfOf)`, `leverage` deposits, liquidation `seize` fee transfers to a fresh `feeCollector`-style recipient, and `NativeTokenGateway`/`VesperGateway` deposits all route through `addToDepositTokensOfAccount` and revert.
- Entries are only freed by `removeFromDepositTokensOfAccount`/`removeFromDebtTokensOfAccount` when the balance returns exactly to zero (`contracts/DepositToken.sol:522-525`), mirroring the leak-only-on-failure-then-never-freed pattern of the CVE: each dust transfer allocates a slot that persists until someone pays to clear it.

### Impact Explanation
Temporary freezing of funds and denial of service of core protocol actions for the victim:
- The victim cannot open a debt position in a synthetic token they have not used before (`issue`/`mint` reverts inside `addToDebtTokensOfAccount`), even with healthy collateral.
- Nobody — including the victim — can deposit a collateral type the victim does not already hold; `deposit()` to their account reverts.
- Because `liquidate` seizes via `DepositToken.seize`/transfer to the liquidator, positions are unaffected there, but the victim's ability to deleverage by adding new collateral types is blocked at the exact moment they may need it.
Recovery is possible only by the victim locating each dusted token and transferring the dust out (or having the balance zeroed), which costs gas per token and requires the victim to know the attack happened — analogous to the memory consumption DoS, where the only fix is explicit cleanup.

### Likelihood Explanation
- Fully unprivileged: the attacker only needs dust balances of each whitelisted `DepositToken`, obtainable by depositing a few wei of each underlying through `DepositToken.deposit()` or buying the ms-tokens on the open market. No governor, keeper, oracle, or malicious LayerZero endpoint is involved.
- Cost scales linearly with `MAX_TOKENS_PER_USER` and the number of whitelisted deposit tokens (bounded set), one cheap ERC-20-style transfer each.
- No modifier stops it: `addToDepositTokensOfAccount` is permissionless for any registered deposit token, `whenNotPaused`/`nonReentrant` do not apply, and the health/lock checks (`_revertIfLocked`) only restrict the sender's balance, not the recipient's list growth.

### Recommendation
- Let the recipient control list growth: skip `addToDepositTokensOfAccount` on plain `transfer`/`transferFrom` and only register the token on `deposit`/mint paths, or add an opt-in/allowlist flag per account.
- Alternatively, make slot reclamation automatic and permissionless: allow anyone to call a `sweepDustToken(account, token)`-style cleanup that force-returns sub-dust balances, or auto-remove entries for balances below a threshold during `debtPositionOf`/`depositOf` iteration.
- If neither is feasible, document the griefing vector and raise `MAX_TOKENS_PER_USER` plus monitor `DepositToken` transfers for dust patterns.

### Proof of Concept
Hardhat-style reproduction (against a live `Pool` deployment with `N` whitelisted deposit tokens, `MAX_TOKENS_PER_USER = M`):

```ts
// attacker holds >= 1 wei of each whitelisted msd token
for (const dt of whitelistedDepositTokens) {
  await dt.connect(attacker).transfer(victim.address, 1); // allocates slot
}
// victim's combined token count is now >= MAX_TOKENS_PER_USER
expect(await pool.debtPositionOf(victim.address)); // still works (view)

// 1. New collateral deposit to victim reverts
const newDepositToken = /* any whitelisted token victim doesn't hold */;
await underlying.connect(attacker).approve(newDepositToken.address, amount);
await expect(
  newDepositToken.connect(attacker).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

// 2. Victim cannot mint a synthetic asset they haven't used before
await expect(
  newDebtToken.connect(victim).issue(amount)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");
```

Note: full confirmation of the exact `MAX_TOKENS_PER_USER` constant value and the `DebtToken.issue` call path into `addToDebtTokensOfAccount` was not completed within the search budget, but the modifier ordering at `contracts/Pool.sol:143-148` and `204-220` confirms both entry points share the same bounded-list guard.
