### Title
Protocol Fee Bypass via NEP-245/IMT Amount-≤1 Fee Exemption in `TokenDiff` - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::execute_intent` charges the protocol fee only on negative deltas ("token_in"), and delegates the fee rate to `TokenDiff::token_fee`, which unconditionally returns `Pips::ZERO` whenever the token is `Nep245` or `Imt` and `|delta| <= 1`. The intent behind this carve-out is to avoid charging a percentage fee on NFT-like transfers of a single indivisible unit. However, NEP-245 ("Multi Token") is explicitly a *semi-fungible* standard — nothing prevents a token whose single unit represents an arbitrary, attacker-chosen quantity of value. Because any account can register brand-new NEP-245 token IDs inside Defuse simply by calling `mt_on_transfer` from its own contract as `predecessor_account_id`, an attacker can deposit/trade a custom multi-token where `amount = 1` denotes the entire value being moved, permanently exempting that leg of every `TokenDiff` trade from the protocol fee.

### Finding Description
`token_fee()` decides the fee rate purely from the token's type discriminant and the raw numeric `amount`, not from any real value or from whether the token is actually non-fungible: [1](#0-0) 

The comment states the intent — "do not take fees on NFTs and MTs with `|delta| <= 1`" — but the code has no way to verify that a given `Nep245`/`Imt` token ID is actually non-fungible; it trusts the numeric amount alone as a proxy for "this is an NFT."

`execute_intent` uses this rate directly to compute `fees_collected`, which is what actually gets credited to the fee collector: [2](#0-1) 

Any unprivileged account can mint an arbitrary NEP-245 token ID scoped to its own contract simply by calling `mt_on_transfer` directly against Defuse — the token identity is derived from `predecessor_account_id`, so the caller fully controls both the token contract identity and the semantics of what one "unit" represents: [3](#0-2) [4](#0-3) 

This confirms the token-registration path used for the bypass is not privileged or DAO-gated — it is the ordinary deposit path any user already uses to bring MT assets into Defuse.

### Impact Explanation
The binding broken is *fees owed versus fees collected*: the protocol fee schedule (`engine.state.fee()`) is defined as a percentage that should apply to the value moved on every `token_in` leg of a `TokenDiff`, but `token_fee()` silently zeroes it whenever the attacker structures that leg as a `Nep245`/`Imt` transfer of `amount == 1`. By depositing/using a self-controlled semi-fungible token where a single unit stands in for the full notional value of a trade, an attacker (or attacker-controlled solver) can route the "token_in" side of swaps through that unit and permanently avoid paying the fee that is supposed to be collected on it, directly reducing protocol fee revenue with no counterparty needing special privileges. This matches the Critical criterion "fees bypassed or over-collected."

### Likelihood Explanation
High. Registering a new NEP-245 token ID under an attacker-controlled predecessor account is a normal, permissionless operation already exercised in the test suite (`mt_on_transfer` from an arbitrary "author" contract). No admin role, relayer key, or upgrade is required — a single unprivileged EOA/contract pair can create the token and repeatedly use it as one leg of `TokenDiff` intents to evade the fee indefinitely.

### Recommendation
Do not infer "NFT-like, fee-exempt" status from the numeric transfer amount. Either: (a) remove the amount-based exemption for `Nep245`/`Imt` entirely and charge the standard fee on all fungible-style deltas, or (b) require an explicit, protocol-controlled classification of which `Nep245` token IDs are genuinely non-fungible (e.g., a registered NFT-semantics flag) before exempting them from fees, rather than trusting `|delta| <= 1` as a proxy.

### Proof of Concept
1. Attacker deploys a minimal contract `evil.near` and calls `evil.near`'s own logic to invoke `defuse.mt_on_transfer(sender_id=attacker, previous_owner_ids=[attacker], token_ids=["1"], amounts=[1], msg=...)` directly as `predecessor_account_id = evil.near`, depositing 1 unit of `nep245:evil.near:1` credited to the attacker's Defuse balance (per `contracts/defuse/src/contract/tokens/nep245/deposit.rs:46-73`).
2. Attacker treats this single unit as representing, say, 10,000 USDT worth of value (purely by mutual off-chain/solver agreement with a counterparty willing to trade against it).
3. Attacker signs a `TokenDiff` with `diff = { nep245:evil.near:1: -1, <real_token>: +N }`. In `execute_intent`, since `delta == -1` and the token type is `Nep245`, `token_fee` returns `Pips::ZERO` (`contracts/defuse/core/src/intents/token_diff.rs:206-217`), so `fees_collected` for this leg is `0` regardless of `protocol_fee`.
4. The counterparty's matching `TokenDiff` supplies the real, valuable token; because fee is only assessed per-signer on that signer's own negative deltas, the attacker's outgoing leg (nominally worth 10,000 USDT by mutual agreement) never contributes to `fees_collected`, while a normal `Nep141` swap of equivalent value would have paid `protocol_fee * amount`.
5. Repeating this pattern lets the attacker (or an attacker-run solver) systematically avoid protocol fees on the "token_in" side of trades routed through self-issued NEP-245 units, causing the fee collector to under-collect versus what the fee schedule is designed to charge.

    #[inline]
    pub fn token_fee(token_id: impl Into<TokenIdType>, amount: u128, fee: Pips) -> Pips {
        let token_id = token_id.into();
        match token_id {
            TokenIdType::Nep141 => {}
            TokenIdType::Nep245 | TokenIdType::Imt if amount > 1 => {}
            // do not take fees on NFTs and MTs with |delta| <= 1
            TokenIdType::Nep171 | TokenIdType::Nep245 | TokenIdType::Imt => return Pips::ZERO,
        }
        fee
    }
