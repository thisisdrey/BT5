### Title
Out-of-bounds heap read via unchecked Zip64 extra-field attribute index in `singlejar` - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`Zip64ExtraField::attr64(int index)` and its callers in `LH`/`CDH` (`compressed_file_size()`, `uncompressed_file_size()`, `local_header_offset()`) compute the index of the 64-bit attribute to read from flags in the *32-bit* size/offset fields, but never check that index against `attr_count()` (which is derived from the attacker-controlled `payload_size` of the extra field itself). A crafted jar/zip entry can set the 32-bit sentinel fields to `0xFFFFFFFF` while supplying a Zip64 extra field with fewer attributes than the code expects, causing `attr64()` to read 64-bit words past the end of the extra field's actual payload — into adjacent bytes of the memory-mapped input file/heap buffer.

### Finding Description
`Zip64ExtraField::attr_count()` is `payload_size() / sizeof(uint64_t)`, and `payload_size()` comes directly from bytes in the untrusted archive: [1](#0-0) 

`attr64(index)` performs `attr_[index]` with no bounds check against `attr_count()`: [2](#0-1) 

Both `LH` (local file header) and `CDH` (central directory header) call `attr64()` at an index derived purely from whether the corresponding 32-bit size/offset field equals the `0xFFFFFFFF` sentinel — a condition fully controlled by the archive author, independent of the true size of the Zip64 extra field payload:

- `LH::compressed_file_size()` / `uncompressed_file_size()` read `attr64(1)` / `attr64(0)` whenever the 32-bit field is `0xFFFFFFFF`: [3](#0-2) 

- `CDH::compressed_file_size()` and `CDH::local_header_offset()` compute an index (`0`, `1`, or `2`) from combinations of the 32-bit fields and pass it straight to `attr64()`: [4](#0-3) [5](#0-4) 

An attacker who crafts an archive entry can, for example:
- set `uncompressed_file_size32 = 0xFFFFFFFF` and `compressed_file_size32 = 0xFFFFFFFF` (forcing `attr_no = 2` for `local_header_offset()`), while
- attaching a Zip64 extra field whose `payload_size` only covers 0 or 1 attribute (`attr_count() < 3`).

`attr64(2)` then reads 8 (or 16) bytes past the end of the extra field's real payload. Because `Zip64ExtraField::find()` only validates that the field's declared `size()` fits within the enclosing `extra_fields`/`extra_fields_length()` span, it cannot prevent an over-read that is triggered by a mismatch between the *declared attribute count* and the *index the caller assumes*; the over-read walks into whatever bytes follow in the memory-mapped input jar (or, at the tail of the file, past the mapping entirely).

This mirrors the reported bug class precisely: a fixed-shape record (`attr_[]`) is indexed using a caller-computed offset that is bounded against the wrong quantity (the *type flags* the archive claims) rather than the record's own declared/actual capacity (`attr_count()`), so attacker-controlled framing fields cause a read outside the intended object.

`singlejar` is Bazel's own tool for merging/repackaging jar files (used for `deploy_jar`, Java rule output packaging, etc.), and it parses `CDH`/`LH` structures directly out of memory-mapped **input jars**, which routinely originate from external dependencies (e.g., `http_jar`, `http_archive` extracting jars, Maven artifacts fetched via `rules_jvm_external`, etc.) — content published by a third party and consumed as part of the build. `output_jar.cc` walks `CDH`/`LH` records of input jars and calls the size/offset accessors (`compressed_file_size()`, `uncompressed_file_size()`, `local_header_offset()`) while copying entries into the output jar.

Neither `sha256`/`integrity` verification of the archive nor the existing `ExtraField::find()` bounds check on the extra field's own end-of-array position addresses this: those checks validate that the *hash matches* and that the "next field" pointer doesn't run off the `extra_fields` buffer, not that the number of 64-bit attributes actually present matches what the accessor logic assumes to index. A bit-for-bit-verified, checksum-valid, but structurally malicious jar can still trigger the read.

### Impact Explanation
The bug is an out-of-bounds heap/mmap read (CWE-125) triggered purely by content of an externally supplied jar/zip file processed by Bazel's `singlejar` tool during ordinary Java build actions. Depending on layout, the read can pull adjacent heap or (for the last mapped page of the file) unmapped memory into a `size_t`/`uint64_t` value that is subsequently used as a claimed file size / header offset while copying archive entry bytes into the merged output jar — this can leak bytes of process memory into build outputs or crash the build process (segfault at an unmapped page boundary). It does not, by itself, grant memory writes or code execution, but it is a genuine information-disclosure / reliability issue reachable purely from attacker-supplied archive content that has already passed Bazel's normal integrity checks.

### Likelihood Explanation
Reaching this code only requires convincing a build to process a crafted jar as an input to `singlejar` (i.e., any Java build target with dependencies from an external, attacker-influenced source — a common scenario for unpinned/mutable jar dependencies or a compromised host serving jar artifacts). No sandbox escape, no credential access, and no cooperation from Bazel's checksum machinery is needed since the crafted bytes can be exactly what is hashed/pinned; the malformation is purely in the zip64 extra-field structure, which integrity checks do not semantically validate.

### Recommendation
In `Zip64ExtraField::attr64()`, bound `index` against `attr_count()` before indexing, and have `LH`/`CDH` accessors treat a missing/undersized Zip64 extra field the same way they already treat a `nullptr` result from `zip64_extra_field()` (return an explicit "invalid" sentinel or fail the parse) rather than trusting the caller-computed index derived from the 32-bit sentinel fields.

### Proof of Concept
A reproducible unit test can be added alongside `src/tools/singlejar/zip_headers_test.cc` (which already exercises `Zip64ExtraField`/`CDH` accessors) that:
1. Allocates a `CDH` in a fixed-size backing buffer (as existing tests do), with poison bytes immediately following the buffer's logical end.
2. Sets `uncompressed_file_size32(0xFFFFFFFF)` and `compressed_file_size32(0xFFFFFFFF)` to force `attr_no == 2` in `local_header_offset()`.
3. Attaches a Zip64 extra field with `payload_size` covering only 1 attribute (`attr_count() == 1`, 8 bytes of payload) via `cdh->extra_fields(...)`.
4. Calls `cdh->local_header_offset()` and observes that `attr64(2)` reads past the crafted extra-field payload — verified by placing a sentinel/poison pattern right after the payload and asserting the returned value reflects those sentinel bytes rather than a defined value or an error, demonstrating the unchecked over-read of `attr_[]`.
