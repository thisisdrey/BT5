### Title
Missing content-hash verification on downloaded Attachment responses allows storage of unbacked attachments - (File: stackslib/src/net/atlas/download.rs, stackslib/src/net/atlas/db.rs)

### Summary
When the `AttachmentsDownloader` fetches an attachment from a peer, it never checks that the returned `Attachment`'s hash equals the `content_hash` of the `AttachmentRequest` that was sent. Any peer that is selected as a source for an in-flight, legitimately-queued content request can instead return arbitrary bytes; the node computes its own hash of that payload and permanently stores it via `AtlasDB::insert_instantiated_attachment`, regardless of whether any confirmed on-chain `AttachmentInstance`/`tx_id` ever committed to that hash.

### Finding Description
`AttachmentsBatchStateContext::extend_with_attachments` in `stackslib/src/net/atlas/download.rs` (lines 530-558) processes successful HTTP responses to `AttachmentRequest`s: [1](#0-0) 
It decodes the JSON body via `decode_atlas_get_attachment` and does `self.attachments.insert(response.attachment)` — there is no comparison of `response.attachment.hash()` against `request.content_hash`. `decode_atlas_get_attachment` itself performs no hash validation either: [2](#0-1) 

Later, in `AttachmentsDownloader::run`, every attachment collected this way is unconditionally persisted: [3](#0-2) 

`AtlasDB::insert_instantiated_attachment` writes the row keyed by the attacker-controlled content's own hash, and only *attempts* to update matching `attachment_instances` rows — a zero-row `UPDATE` is not an error and does not block the `INSERT`: [4](#0-3) 

Root cause: the equality the system is supposed to enforce — "every stored `attachments` row's hash corresponds to a `content_hash` referenced by some confirmed `AttachmentInstance`" — is broken. The code only ever computes the hash of whatever bytes the peer returned; it never checks that this equals the `content_hash` that was actually requested (which is the value tied to a real on-chain commitment). Because `resolve_attachment` (called via `context.attachments_batch.resolve_attachment(&attachment.hash())`) also matches by hash, a wrong-hash response fails to resolve the original queued item — the batch keeps retrying (up to `max_attachment_retry_count`) and the attacker can serve a *different* fabricated payload on each retry, producing a distinct row each time. There is no size cap or eviction policy on the `was_instantiated = 1` (instantiated) portion of the `attachments` table — eviction/cap logic (`max_uninstantiated_attachments`, `evict_expired_uninstantiated_attachments`) only applies to `was_instantiated = 0` rows.

Attacker exploit flow:
1. Wait for (or induce, via the forged-inventory precondition) a real, on-chain-queued `AttachmentInstance` content_hash request to be issued by the victim node (this requires the attacker to be selected as a `source` in `get_prioritized_attachments_requests`, which requires advertising an inventory bit — covered by the companion inventory-forgery question).
2. When the victim sends `GET /v2/attachments/<content_hash>` to the attacker's peer/data URL, respond with a `GetAttachmentResponse` JSON body containing arbitrary bytes `C` unrelated to `content_hash`.
3. The victim decodes it, computes `hash(C)`, and calls `insert_instantiated_attachment`, storing a permanent row `(hash(C), C, was_instantiated=1)` in `AtlasDB`'s `attachments` table — with no `AttachmentInstance`/`tx_id` ever having committed to `hash(C)`.
4. Because the original `content_hash` was never matched, the batch retries the same slot up to `max_attachment_retry_count` times, and the attacker can supply a different `C` each time to generate additional distinct rows.

### Impact Explanation
This lets a remote, unprivileged peer (who only needs to be selected as a legitimate-looking data source for outstanding attachment fetches) cause the victim node to permanently store attacker-chosen content under attacker-chosen hashes in its Atlas attachment store — content that no confirmed BNS/name operation ever committed to. This is a genuine break of the "attachment must be backed by a confirmed on-chain commitment" invariant, and results in storage bloat of `AtlasDB`'s `attachments` table (unbounded by any cap for instantiated rows) with garbage/non-canonical data served up over `GET /v2/attachments/<hash>` by that node to any client who happens to ask for that garbage hash later. This matches the "High — storing content no on-chain name operation ever committed to" / attachment-BNS mismatch category.

### Likelihood Explanation
Preconditions: the attacker must be selected as a reliable source for an outstanding `AttachmentRequest` (achievable per the companion inventory-forgery finding, or simply by being a legitimate peer that is a real data source for some real BNS zonefile fetch and choosing to lie in the response). No RPC secret or privileged role is required — this is exercised purely over the ordinary P2P/HTTP Atlas attachment-fetch protocol. It is fully repeatable across retries (bounded per-batch by `max_attachment_retry_count`, but unbounded across the continual stream of new legitimate `AttachmentInstance` events the node processes over its lifetime).

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (stackslib/src/net/atlas/download.rs), after decoding a response, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; discard/penalize (bump_failed_requests) mismatched responses instead of accepting them. Additionally, consider guarding `AtlasDB::insert_instantiated_attachment` to only persist attachments whose hash matches at least one existing `attachment_instances` row (queued or checked), rejecting unsolicited/unmatched content outright.

### Proof of Concept
Rust test plan (in `stackslib/src/net/atlas/tests.rs` or a new integration test):
1. Construct an `AttachmentsBatchStateContext` with one `AttachmentRequest { content_hash: H_real, .. }` sourced from a fake peer URL.
2. Build a `BatchedRequestsResult` whose `succeeded` map associates that request with an `StacksHttpResponse` whose body is a `GetAttachmentResponse { attachment: Attachment { content: b"malicious-unrelated-bytes".to_vec() } }` (hash `H_evil != H_real`).
3. Call `context.extend_with_attachments(&mut results)` and assert `context.attachments` contains the attachment with hash `H_evil`.
4. Drive `AttachmentsDownloader::run` to completion (or call `atlasdb.insert_instantiated_attachment(&attachment)` directly as done in existing tests, e.g. mirroring the pattern in `stackslib/src/net/api/tests/mod.rs:749-769`), then assert via `SELECT * FROM attachments WHERE hash = ?` that the row for `H_evil` exists, while `SELECT * FROM attachment_instances WHERE content_hash = ?` for `H_evil` returns no rows — proving the stored attachment has no backing `AttachmentInstance`/`tx_id` commitment.
5. Repeat with several different malicious contents to demonstrate `attachments` table growth uncorrelated to any real on-chain commitment.

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
