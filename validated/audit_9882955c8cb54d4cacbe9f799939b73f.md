### Title
Unbounded body read in `process_event` allows unauthenticated memory-exhaustion DoS via `/stackerdb_chunks` - (File: libsigner/src/events.rs)

### Summary
`process_event` reads the entire HTTP request body into a `String` via `request.as_reader().read_to_string(&mut body)` with no length cap comparable to `MAX_MESSAGE_LEN`/`MAX_PAYLOAD_LEN` used elsewhere in the codebase (e.g. stackslib HTTP endpoints). Any remote party able to reach the signer's event-receiver port can POST to `/stackerdb_chunks` (or `/new_block`, `/new_burn_block`, `/proposal_response`, which share this same code path) with an oversized or endlessly-streamed body, causing unbounded memory allocation in the signer process before any authentication, signature, or deserialization check runs.

### Finding Description
`next_event` dispatches any POST to `/stackerdb_chunks` directly into `process_event::<T, StackerDBChunksEvent>(request)` [1](#0-0) . Inside `process_event`, the code does:
```rust
let mut body = String::new();
if let Err(e) = request.as_reader().read_to_string(&mut body) { ... }
``` [2](#0-1) 

This read happens before any validation of the payload: no length check against a constant like `MAX_MESSAGE_LEN`, no auth-gate, and no signature/consensus check — those only occur later, deep inside `TryFrom<StackerDBChunksEvent>` when iterating `event.modified_slots` and calling `chunk.recover_pk()` [3](#0-2) . By the time any per-chunk validation occurs, the entire body has already been buffered into memory by `read_to_string`.

Unlike the RPC HTTP layer in `stackslib` (`stackslib/src/net/http/request.rs`, `stackslib/src/net/httpcore.rs`), which enforces `MAX_MESSAGE_LEN`/`MAX_PAYLOAD_LEN`-style caps on request bodies before buffering, the signer's `libsigner` event-receiver (built on `tiny_http`, referenced here as `HttpServer`/`HttpRequest`) has no analogous cap in this file. The event-receiver socket is reachable by any process that can connect to the signer's configured event-receiver bind address — this is not the node's authenticated RPC or P2P handshake path; it is a bare local HTTP listener that the node's event dispatcher POSTs to, but nothing in `process_event` restricts the sender to only the node.

### Impact Explanation
An attacker who can open a TCP connection to the signer's event-receiver bind address can send a POST to `/stackerdb_chunks` with a very large or streamed (chunked/no Content-Length) body. `read_to_string` will keep allocating and appending to the `String` until the connection is closed or memory is exhausted, with no configured ceiling in this code path. This can crash or OOM the signer process (`stacks-signer`) from a small number of requests, matching the "Critical – remote crash/unauthenticated DoS from few messages" category, since it requires no valid signature, no known StackerDB slot ownership, and no admin secret.

### Likelihood Explanation
Preconditions: attacker must be able to reach the signer's event-receiver HTTP port. In default deployments this listener is often bound to a local/private interface for communication from the co-located Stacks node, but the code itself does not enforce any peer-source restriction, TLS, or auth token check before reading the body — reachability is purely a network/deployment-topology question, not a code-enforced guarantee. Given reachability, exploitation is trivial (a single crafted HTTP POST), cheap, and repeatable indefinitely.

### Recommendation
Impose a hard cap on the body size before/while reading in `process_event`, e.g. wrap the reader with `Read::take(MAX_PAYLOAD_LEN)` (mirroring the caps used in `stackslib/src/net/httpcore.rs`), reject/close the connection if `Content-Length` exceeds the cap or is absent/chunked without an enforced upper bound, and only pass through auth or ensure the event-receiver socket is not exposed beyond a trusted loopback/localhost interface. Applying the same fix pattern used by `stackslib`'s HTTP request handling (`MAX_MESSAGE_LEN`/`MAX_PAYLOAD_LEN`) to `libsigner/src/events.rs::process_event` closes this gap for all four dispatched routes (`/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block`).

### Proof of Concept
Rust test plan (net-level, in `libsigner` test harness):
1. Bind an `EventReceiver` instance on `127.0.0.1:0` as in existing `libsigner` tests.
2. Open a raw `TcpStream` to the bound address and send:
   `POST /stackerdb_chunks HTTP/1.1\r\nHost: x\r\nTransfer-Encoding: chunked\r\n\r\n` followed by an unbounded stream of chunked data (e.g. loop writing `1000\r\n<1000 bytes>\r\n` many times, e.g. hundreds of MB) without ever sending the terminating `0\r\n\r\n`.
3. Observe process RSS growth via `/proc/self/status` (or a memory-tracking allocator) on the signer/event-receiver thread, asserting that memory usage grows unbounded / exceeds a small threshold (e.g. beyond `MAX_PAYLOAD_LEN`) without the connection being rejected.
4. Assert failure: `read_to_string` at `libsigner/src/events.rs:526` never returns before memory exceeds a sane cap (e.g. 100MB), demonstrating the missing bound; a fixed version should reject the request (return `EventError::MalformedRequest` for oversized body) well before that threshold.
