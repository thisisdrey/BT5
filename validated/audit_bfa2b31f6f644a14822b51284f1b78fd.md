### Title
Pre-receive hook silently drops quarantine object-directory info when only one of `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` is present, letting the GitLab `Allowed` access check operate blind to pushed objects - (File: internal/gitaly/hook/prereceive.go)

### Summary
`preReceiveHook()` only updates the `gitalypb.Repository`'s `GitObjectDirectory`/`GitAlternateObjectDirectories` fields (which are subsequently sent to GitLab Rails' `Allowed` internal API and used to build the custom-hooks environment) when **both** `GIT_OBJECT_DIRECTORY` and `GIT_ALTERNATE_OBJECT_DIRECTORIES` are simultaneously non-empty in the hook's environment. This is analogous to the Curve `canRemoveLiquidity()` bug, where a per-item conditional check (`amounts[i] > 0`) was used to decide inclusion in a list that is later relied upon for a security decision, even though the underlying invariant does not guarantee the condition holds for every relevant item together.

There is no invariant enforced anywhere that these two fields on `gitalypb.Repository` must always be set together, so it's structurally possible for a repository object to have `GitObjectDirectory` set without `GitAlternateObjectDirectories` (or vice versa) when it reaches `preReceiveHook`. In that state, the AND-gated `if` at line 108 fails, and the repository proto keeps whatever stale/empty quarantine information it had, even though `git` is actually operating with the object directory override in effect for this push. That stale repository information is what's sent as `GitObjectDirectory`/`GitAlternateObjectDirectories` in `gitlab.AllowedParams` to the GitLab Rails `Allowed` internal API: [3](#0-2) 

Gitaly's own documentation confirms the exact consequence class of desynchronized quarantine information: [4](#0-3) 
> "During the POST, the internal GitLab API makes Gitaly calls back into the repo to examine the objects being pushed... because that commit is in quarantine, the RPC will fail because the commit cannot be found."

### Impact Explanation
If Rails' pre-receive policy checks (e.g., protected-branch/force-push detection, secret/large-file scanning, LFS pointer inspection) rely on being able to see the incoming, not-yet-committed objects via the quarantine object directory, and the quarantine directory information silently fails to propagate due to this AND-gated check, those checks operate against the wrong (or missing) object database. Depending on how Rails' `Allowed` implementation handles "object not found" during such checks (fail-open vs fail-closed), this can result in a push being incorrectly approved that should have been rejected — an authorization/hook-gating bypass reachable purely from an ordinary user's `git push`.

### Likelihood Explanation
Exploitability hinges on finding a code path that produces a `gitalypb.Repository`/environment with only one of the two variables set. Under Gitaly's own quarantine helper (`internal/git/quarantine/quarantine.go`), both fields are always populated together, so the default push flow driven purely by Gitaly-managed quarantine is not affected. However, `alternates.Env()` (used broadly whenever `ExecCommandFactory` spawns a git subprocess for *any* `storage.Repository`, including RPC-supplied `gitalypb.Repository` messages) treats the two fields completely independently, so any code path that constructs or forwards a `Repository` with an object-directory override but no alternates (or vice versa) would trigger the desync. This makes likelihood moderate rather than certain — it depends on there being a reachable path that decouples these two normally-paired fields before the hook executes.

### Recommendation
Update `preReceiveHook()` to update `repo.GitObjectDirectory`/`repo.GitAlternateObjectDirectories` whenever *either* `GIT_OBJECT_DIRECTORY` or `GIT_ALTERNATE_OBJECT_DIRECTORIES` is present in the environment, rather than requiring both simultaneously — mirroring the same fix pattern as the referenced report (stop gating inclusion on a partial per-item/per-field condition and instead always propagate all available quarantine information). Additionally, consider asserting the invariant that these two fields are always set/unset together wherever `gitalypb.Repository` quarantine fields are constructed, to eliminate the possibility of desynchronized state entirely.

### Proof of Concept
1. Identify or introduce a code path where a `gitalypb.Repository` used to spawn a `git-receive-pack`/hook-invoking subprocess has `GitObjectDirectory` set but `GitAlternateObjectDirectories` empty (or the reverse) — e.g., by crafting an internal RPC/request flow that supplies only one of these repository fields before `configureHooks`/`alternates.Env` builds the subprocess environment.
2. Push a change including a new object that only exists in the quarantine object directory.
3. Observe that in `preReceiveHook`, `env.ExtractValue(envs, "GIT_ALTERNATE_OBJECT_DIRECTORIES")` (or `GIT_OBJECT_DIRECTORY`) is empty, so the `if` at line 108 is skipped and `repo.GitObjectDirectory`/`GitAlternateObjectDirectories` are not updated.
4. Observe that the `gitlab.AllowedParams` sent to Rails' `Allowed` API lacks the correct quarantine path, so any Gitaly-backed inspection of the new object (e.g., `IsAncestor`, file content checks) fails to locate it — verifying the same "object invisible to the accounting/decision list" condition described in the source report.

```go
// Env returns the alternate object directory environment variables.
func Env(repoPath, objectDirectory string, alternateObjectDirectories []string) []string {
	var env []string
	if objectDirectory != "" {
		env = append(env, fmt.Sprintf("GIT_OBJECT_DIRECTORY=%s", filepath.Join(repoPath, objectDirectory)))
	}

	if len(alternateObjectDirectories) > 0 {
		var dirsList []string

		for _, dir := range alternateObjectDirectories {
			dirsList = append(dirsList, filepath.Join(repoPath, dir))
		}

		env = append(env, fmt.Sprintf("GIT_ALTERNATE_OBJECT_DIRECTORIES=%s", strings.Join(dirsList, ":")))
	}

	return env
}
```
