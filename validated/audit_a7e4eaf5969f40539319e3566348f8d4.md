## Title
Silent fund-lock in `close_child_bounty`: native balance transfer failure is only `debug_assert!`-checked, permanently stranding funds after storage removal - (File: substrate/frame/child-bounties/src/lib.rs)

## Summary
`impl_close_child_bounty` sweeps the child-bounty account's balance back to the parent bounty account via `T::Currency::transfer(&child_bounty_account, &parent_bounty_account, balance, AllowDeath)`, but only verifies success with `debug_assert!`, which is compiled out in release/production runtime builds. Immediately after, the code unconditionally executes `*maybe_child_bounty = None;`, deleting the only on-chain bookkeeping for that account regardless of whether the transfer actually succeeded.

## Finding Description
The vulnerable code path is confirmed in `impl_close_child_bounty`: [1](#0-0) . The `child_bounty_account` is deterministically derived via `Self::child_bounty_account_id`, computed as `T::PalletId::get().into_sub_account_truncating(("cb", parent_bounty_id, child_bounty_id))` [2](#0-1) , making it publicly predictable by any unprivileged party before the account is even funded.

`close_child_bounty` is reachable by either the parent curator (a permissioned but non-privileged, non-governance actor) or `T::RejectOrigin` [3](#0-2) . It calls `impl_close_child_bounty`, which performs the balance sweep and checks the result only via `debug_assert!(transfer_result.is_ok())` — a no-op in release builds — before unconditionally clearing the storage entry with `*maybe_child_bounty = None;`.

This mirrors a previously-fixed defect in the sibling `pallet-bounties::close_bounty`, where account references (via `sufficients`/`consumers`/`providers`, e.g., from asset transfers to the bounty pot) could block a native balance transfer or full reap of the pot account, as demonstrated by `close_bounty_with_random_references_works` [4](#0-3)  and the insufficient-asset case [5](#0-4) . That issue was addressed for `pallet-bounties` by hardening `close_bounty` to reap assets before reaping balance and by adding the permissionless `reclaim_bounty_funds` recovery extrinsic [6](#0-5) , per `prdoc/pr_11045.prdoc` [7](#0-6) . Critically, `prdoc/stable2603/pr_10729.prdoc` explicitly lists `pallet-child-bounties` as a crate affected by the related change, but no `TransferAllAssets`-equivalent sweep, hardened ordering, or `reclaim_bounty_funds`-equivalent recovery call exists in `pallet-child-bounties` itself. There is no dispatchable in `pallet-child-bounties` to reclaim funds from an orphaned child-bounty account once the `ChildBounties` storage entry backing it is removed.

## Impact Explanation
This is a permanent user-fund lock: treasury-derived funds allocated to a child bounty can become permanently stranded in a deterministically-derivable account with no bookkeeping and no recovery path once `close_child_bounty` removes the storage entry despite a failed transfer. This falls squarely within the accepted impact class "permanent user-fund or bridge-state lock" and violates the invariant that treasury/bounty-held value must conserve and settle exactly once.

## Likelihood Explanation
An unprivileged attacker can, with a single ordinary signed extrinsic (e.g., an asset transfer via `pallet-assets` or another fungible/NFT pallet configured in the runtime), send a "sufficient" asset to the publicly-computable `child_bounty_account_id(parent_bounty_id, child_bounty_id)` prior to the curator's `close_child_bounty` call, creating account references that can cause `T::Currency::transfer(..., AllowDeath)` to fail. No governance, validator, or privileged access is required for the setup step; the only privileged-but-not-malicious action is the curator/`RejectOrigin` calling `close_child_bounty` in the normal course of pallet operation. This is directly analogous to the `close_bounty_with_additional_assets_works` scenario for parent bounties, and is repeatable for every child bounty in the system.

## Recommendation
- Replace the `debug_assert!(transfer_result.is_ok())` with a real error propagation (`transfer_result?`) so that `close_child_bounty` fails and preserves the storage entry when the sweep cannot complete.
- Before transferring native balance, sweep or account for any non-native asset balances/references on the child-bounty account, mirroring the `TransferAllAssets` mechanism added to `pallet-bounties`.
- Add a permissionless recovery extrinsic analogous to `pallet-bounties::reclaim_bounty_funds` scoped to orphaned child-bounty accounts, so funds are not unrecoverable if a transfer failure does occur.

## Proof of Concept
1. Create and fund a parent bounty; propose and accept a parent curator; add and accept a child bounty, funding `ChildBounties::child_bounty_account_id(0, 0)` with native balance.
2. As an unprivileged third party, transfer a "sufficient" asset via `pallet-assets::transfer` (or an equivalent configured fungible/NFT pallet) directly to `ChildBounties::child_bounty_account_id(0, 0)`, creating an account reference that can block a clean balance transfer/reap, analogous to `close_bounty_with_additional_assets_works`.
3. Call `close_child_bounty(origin, 0, 0)` as the parent curator. In a release build, if `T::Currency::transfer(..., AllowDeath)` fails due to the account reference, the failure is swallowed by the compiled-out `debug_assert!`, and `*maybe_child_bounty = None;` still executes, deleting `ChildBounties` storage for that entry.
4. Observe that the child-bounty storage entry no longer exists, but the native balance remains stranded in `child_bounty_account_id(0, 0)`, with no extrinsic in `pallet-child-bounties` available to recover it.

		///
		/// Permissionless. Moves all remaining assets from a closed bounty's account back to the
		/// treasury in a single call. Which assets are swept depends on the `TransferAllAssets`
		/// configuration.
		///
		/// The call is free if funds were reclaimed and paid otherwise, so no-op calls cannot be
		/// used to grief the network. Emits `BountyFundsReclaimed` on success.
		///
		/// ## Complexity
		/// - O(A) where A is the number of relevant assets configured in `TransferAllAssets`.
		#[pallet::call_index(11)]
		#[pallet::weight(<T as Config<I>>::WeightInfo::reclaim_bounty_funds())]
		pub fn reclaim_bounty_funds(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
		) -> DispatchResultWithPostInfo {
			ensure_signed(origin)?;

			// A live bounty still manages its account, so leave it untouched.
			ensure!(!Bounties::<T, I>::contains_key(bounty_id), Error::<T, I>::BountyStillActive);

			debug_assert!(
				T::ChildBountyManager::child_bounties_count(bounty_id) == 0,
				"child bounties should not exist for a closed bounty"
			);

			let bounty_account = Self::bounty_account_id(bounty_id);
			let treasury_account = Self::account_id();

			let transferred = T::TransferAllAssets::force_transfer_all_assets(
				&bounty_account,
				&treasury_account,
			)?;

			// Free only if something moved, otherwise paid to prevent griefing.
			if !transferred {
				return Ok(Pays::Yes.into());
			}

			Self::deposit_event(Event::<T, I>::BountyFundsReclaimed { bounty_id });

			Ok(Pays::No.into())
		}
