Audit Report

## Title
Snowbridge relayer reward is paid out even when the delivery receipt reports `success == false` - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`OutboundQueue::process_delivery_receipt` decodes an Ethereum `InboundMessageDispatched` event into a `DeliveryReceipt` carrying an explicit `success: bool` field, but pays the relayer reward from `order.fee` unconditionally whenever `order.fee > 0`, without ever checking `receipt.success`. This lets a relayer who causes/observes a failed inbound dispatch on Ethereum still collect the full protocol-held fee on BridgeHub.

## Finding Description
`DeliveryReceipt` is derived from the `InboundMessageDispatched(nonce, topic, success, reward_address)` Solidity event and decoded via `TryFrom<&Log>`, explicitly preserving `success: event.success` ( [4](#0-3) ). The public extrinsic `submit_delivery_receipt` is callable by any `ensure_signed` origin; it verifies the event log/proof via `T::Verifier::verify`, decodes the receipt, and calls `Self::process_delivery_receipt(relayer, receipt)` ( [2](#0-1) ).

Inside `process_delivery_receipt`, the gateway address is checked, the reward destination is resolved from `receipt.reward_address` (attacker-controlled, or defaulting to the calling relayer), the pending order is fetched by `receipt.nonce`, and the reward is paid via `T::RewardPayment::register_reward` purely based on `order.fee > 0` — `receipt.success` is never read ( [5](#0-4) ). The `PendingOrder` is then unconditionally removed and `MessageDelivered` is emitted regardless of delivery outcome. This breaks the invariant that payout state must only advance after execution actually succeeds.

## Impact Explanation
Because reward registration is gated only on `order.fee > 0`, an attacker can obtain a valid Ethereum transaction receipt/log proving `InboundMessageDispatched` fired with `success: false` (a state the Gateway contract is designed to emit on failed dispatch) and submit it through the fully public `submit_delivery_receipt` extrinsic to drain the pre-registered fee for a message that was never successfully delivered. This is a theft/unbacked payout of bridge fee funds via `T::RewardPayment::register_reward`, matching the "duplicate settlement or payout" / "theft or unbacked... unlock" impact categories, since the exact corrupted value is the reward payout being decoupled from the `receipt.success` field that is supposed to gate it.

## Likelihood Explanation
The exploit requires only a normal signed account submitting a legitimate, verifier-accepted proof for an event log that already contains `success: false` — no privileged role, governance action, or compromised relayer/validator assumption is needed beyond ordinary permissionless relaying that the protocol already supports. This is a reachable, repeatable path for any external, unprivileged caller of the public `submit_delivery_receipt` extrinsic.

## Recommendation
Gate the call to `T::RewardPayment::register_reward` on `receipt.success == true`. When `success` is `false`, withhold the reward (or apply a distinct, reduced "delivery-attempt" reward explicitly separate from the full success reward), and emit a distinct event such as `MessageDeliveryFailed` rather than `MessageDelivered`, so failed deliveries cannot drain the fee pot as if they had succeeded.

## Proof of Concept
1. A message is queued via `do_process_message`, creating a `PendingOrder { nonce, fee, .. }` with `fee > 0` ( [6](#0-5) ).
2. The message is relayed to the Ethereum Gateway such that the inner dispatch fails while the outer transaction still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address=<attacker>)`.
3. Any signed account submits this log/proof via `submit_delivery_receipt`; `T::Verifier::verify` accepts the valid proof, `DeliveryReceipt::try_from` decodes `success: false` faithfully, and `process_delivery_receipt` pays `order.fee` to `reward_account` because only `order.fee > 0` is checked ( [7](#0-6) ).
4. Result: the reward is paid and `PendingOrders` is cleared for a message whose delivery explicitly failed, confirmable by a unit test that constructs a `DeliveryReceipt { success: false, .. }`, calls `process_delivery_receipt`, and observes `T::RewardPayment::register_reward` still invoked.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
