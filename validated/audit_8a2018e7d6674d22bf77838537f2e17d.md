### Title
Malicious eth-wallet-contract relayer can collect the transaction fee before target-address validation completes, letting it pocket payment without ever executing the user's transfer - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The eth-implicit `WalletContract::rlp_execute` flow pays the relayer's compensation fee (`fee` field derived from the Ethereum transaction's `max_fee_per_gas * gas_limit`) via an unconditional, fire-and-forget `Promise` transfer immediately after parsing the RLP transaction, before the contract has validated whether the requested action will actually be performed. For `EthEmulationKind::EOABaseTokenTransfer`/`ERC20Transfer` transaction kinds that route through the address-registrar check (`address_check: Some(address)`), the fee transfer is dispatched in `inner_rlp_execute` up front, but the registrar lookup and the resulting "faulty relayer" determination happen later, asynchronously, in `address_check_callback`. If the callback determines the relayer used the wrong target (i.e., the eth-implicit target actually has a registered named account), the relayer is simply "banned" and the user's real action is never executed (and the nonce is deliberately *not* incremented so a different relayer can retry) — but the fee has already been irreversibly transferred to the (now-banned) relayer.

### Finding Description
`inner_rlp_execute` unconditionally schedules the relayer's fee transfer as soon as RLP parsing succeeds and the transaction kind is `EOABaseTokenTransfer`/`ERC20Transfer` with non-zero `fee`: [1](#0-0) 

This fee `Promise` is created via `env::promise_batch_create`/`env::promise_batch_action_transfer` and is **not** chained after, or contingent on, the outcome of the actual requested action's promise. The actual action promise (constructed afterwards in the same function) is a completely separate promise chain: [2](#0-1) 

For the `address_check: Some(address)` branch (used when `target` is an eth-implicit account but might actually correspond to a registered named account), the contract only discovers *after* the fee has already been sent whether the relayer picked a faulty target: [3](#0-2) 

If the registrar lookup returns `Some(account_id)` (i.e., a named account is in fact registered for that address), the relayer is deemed faulty; if it authenticated with an access key it is banned, otherwise the call simply returns an `ExecuteResponse::success = false` with the nonce left un-incremented so the transaction can be retried by another relayer. In both outcomes, the intended user transfer never executes in this attempt — yet the fee `Promise` fired at the top of `inner_rlp_execute` already unconditionally transferred NEAR from the wallet contract's own balance to the relayer's account.

This is the direct analog of the reported Sudoswap issue: a value transfer intended to compensate a service-provider party (relayer fee ≈ router-collected protocol fee/royalty) is dispatched without any check that the corresponding "sale"/action actually completed, and the flow is documented as trusting the relayer/user to self-police ("Relayers should also verify the fee before sending... Users should always verify the fee before signing"), mirroring Sudorandom Labs' decision to accept this trade-off rather than add extra balance/outcome checks.

### Impact Explanation
Because any account can act as an unpermissioned relayer for an eth-implicit wallet contract (that is the design goal, per the code comment "this allows any relayer to safely serve base token transfers from any wallet without additional on-boarding"), a malicious relayer can deliberately submit a validly-signed user transaction using an eth-implicit `target` it knows resolves to a registered named account (learnable via a prior read-only call to the address registrar), triggering the `address_check: Some` path. It collects the fee immediately, then lets the callback ban/error out — receiving payment while performing zero useful work and without the user's requested transfer ever completing in that attempt. This is a direct, repeatable loss of NEAR funds (theft) from the wallet account to an attacker-controlled relayer account, independent of the user's own mistakes, since the target ambiguity condition is inherent to how eth-implicit accounts and the address registrar interact, not something a signer necessarily controls.

### Likelihood Explanation
This requires only that: (1) the target address of the emulated transfer corresponds to both an eth-implicit account and a registered named account (a state that can exist for many real accounts, and which any observer can query via the public address registrar before choosing to act maliciously as a relayer), and (2) the fee field of the emulated transaction is non-zero (the normal/expected case, since fee incentivizes relayers to act at all). No special privileges beyond acting as a plain transaction relayer are needed, making this practically exploitable by any actor willing to monitor mempool/user-submitted RLP transactions and act first as a malicious relayer.

### Recommendation
Do not dispatch the relayer fee transfer until the target/address validation (registrar lookup) is fully resolved and the contract is certain that the relayer selected a legitimate target. Concretely, move the fee-transfer promise creation into `address_check_callback`'s success branch (after confirming `maybe_account_id.is_none()`), or chain the fee transfer as a subsequent step after the action promise resolves successfully, so the relayer is compensated only once it is established that the relayer did not present a faulty target.

### Proof of Concept
1. Attacker (as relayer) monitors the eth-wallet-contract's on-chain address registrar or otherwise learns that an eth-implicit target address `0xabc...` also has a registered named account `alice.near`.
2. Attacker obtains (or is handed, per the wallet's trust model) a validly-signed user RLP transaction with `to = 0xabc...` and non-zero `fee`.
3. Attacker submits `rlp_execute(target = 0xabc...(eth-implicit form), tx_bytes_b64)` instead of `target = alice.near`.
4. `parse_rlp_tx_to_action` computes `TargetKind::EthImplicit`, sets `address_check: Some(address)`, and `inner_rlp_execute` immediately fires the fee `Promise` to the attacker's account (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:381-384`).
5. The registrar lookup + `address_check_callback` subsequently determine `maybe_account_id = Some("alice.near")`, causing either a relayer ban (if using an access key) or a plain failure response (if not) — the user's action is not executed and, in the non-access-key case, the nonce is left unchanged so it can be retried.
6. The attacker has already received the fee `Promise` payout in step 4, with no requirement to ever deliver the requested action.
