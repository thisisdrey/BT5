## Title
Bazel's `git_repository`/`git_override` submodule fetch force-enables `protocol.file.allow=always`, permitting attacker-controlled `.gitmodules` to clone arbitrary local paths into the output base — (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`update_submodules()` in `tools/build_defs/repo/git_worker.bzl` invokes `git submodule update --init [--recursive] --checkout --force` with the flag `-c protocol.file.allow=always` unconditionally whenever `init_submodules`/`recursive_init_submodules` is set on `git_repository`/`new_git_repository`/`git_override`. [1](#0-0)  This flag re-enables the `file://` transport for submodule cloning, which upstream Git disabled by default starting from the fixes for the local-clone submodule attack class (Git ≥2.38.1). The Bazel code comment explicitly acknowledges this is done to work around that same Git hardening ("necessary for Git 2.38.1 and associated backport versions", referencing bazelbuild/bazel#17040).

### Finding Description
`git_repo()` drives the full clone/update flow: `init` → `add_origin` → `fetch` → `reset` → `clean` → (optionally) `update_submodules`. [2](#0-1)  The `remote`, `commit`/`tag`/`branch` values come from the repository rule's declared attributes, but the *content* that is checked out — including the `.gitmodules` file that specifies each submodule's `url` — is fetched from whatever git host/branch/commit is referenced. If that source is attacker-influenced (a compromised upstream, an untrusted fork/branch/PR that a CI pipeline builds, or any host the attacker can push to), the attacker fully controls `.gitmodules`.

Normally, Git's own default configuration (`protocol.file.allow=user`) blocks a submodule's declared `url` from using `file://` to clone an arbitrary local directory — this was Git's fix for exactly this abuse pattern (an attacker-supplied `.gitmodules` pointing `url = file:///absolute/path/on/build/host`, causing the victim's `git submodule update` to copy an arbitrary local directory's contents into the submodule checkout path). Bazel's `update_submodules()` explicitly overrides that protection with `-c protocol.file.allow=always` for every submodule update it performs, with no verification that the resulting submodule content stays within any expected boundary.

### Impact Explanation
Because `protocol.file.allow` is forced back to `always`, any attacker who can influence the content of a fetched git ref (branch, tag, or commit target of `git_repository`/`git_override`, or a nested submodule's own `.gitmodules`) can declare a submodule `url` of `file:///path/to/sensitive/or/arbitrary/directory` on the build machine. `git submodule update --init` will then locally clone that directory's contents into the external repository's checkout path inside Bazel's output base — a read outside the intended repository boundary, with the copied files subsequently available to be embedded in build outputs, uploaded to caches, or otherwise exfiltrated through the build. This satisfies the "write or read outside the repository / exec root / output base" impact category.

### Likelihood Explanation
Any project (or CI configuration) using `git_repository`/`new_git_repository`/`git_override` with `init_submodules = True` or `recursive_init_submodules = True` is affected by default, with no flag to opt back into Git's safer behavior — the override is unconditional in the Starlark code. The only requirement is that the attacker control (directly or via supply-chain compromise / untrusted branch) the `.gitmodules` content of some ref that gets checked out, which is a realistic scenario for dependencies pinned to branches/tags rather than immutable commits, or for CI systems that build untrusted contributor branches.

### Recommendation
Do not unconditionally force `protocol.file.allow=always`. At minimum, scope the override to the specific submodule paths/URLs Bazel already knows are safe (e.g., only for submodules whose URL is relative to the already-trusted `origin`), or validate that any `file://` submodule URL resolves within the already-checked-out repository tree before allowing the clone, restoring the containment Git's default was designed to provide.

### Proof of Concept
Set up a git repository controlled by the attacker (or an untrusted branch of a legitimately-referenced repo) containing a `.gitmodules` entry such as:
```
[submodule "leak"]
    path = leaked
    url = file:///etc
```
Reference that branch/commit from a `git_repository`/`git_override` rule with `init_submodules = True`. Running `bazel fetch`/`bazel build` will execute `git -c protocol.file.allow=always submodule update --init --checkout --force`, causing Git to locally clone `/etc` into the `leaked` subdirectory of the external repository under the output base — content from outside the intended repository now materialized as build inputs. A `src/test/shell/bazel/starlark_git_repository_test.sh`-style integration test can assert this by creating such a `.gitmodules`-bearing test fixture (mirroring the existing submodule test setup) and checking for the presence of unexpected host files under `bazel info output_base`/external/.../leaked.
