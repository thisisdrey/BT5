### Title
Dust-transfer griefing fills `feeCollector`'s token list, permanently reverting fee-bearing deposits and withdrawals - (File: contracts/DepositToken.sol)

### Summary
Every fee-bearing `_transfer` inside `DepositToken` calls `pool.addToDepositTokensOfAccount(recipient)`, which reverts with `UserReachedMaxTokens` once the recipient holds 30 distinct deposit/debt tokens (`MAX_TOKENS_PER_USER`). Because withdrawal fees and deposit fees are sent to the fixed `feeCollector` address via `_transfer(account_, _pool.feeCollector(), _fee)`, an unprivileged attacker can dust-transfer tiny amounts of each `DepositToken` share to `feeCollector` until its per-account list is full. From that point, every `deposit()` / `withdraw()` that charges a non-zero fee reverts, freezing user collateral in the pool.

### Finding Description
- `Pool.addToDepositTokensOfAccount` is guarded by `onlyIfAdditionWillNotReachMaxTokens`, which reverts once `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30` (`contracts/Pool.sol:143-147`, `216-220`).
- `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` when the recipient's prior balance is zero (`contracts/DepositToken.sol:517-520`). `transfer()` is a public entry point; the only check is `_revertIfLocked` on the *sender* (`DepositToken.sol:348-354`), so anyone with an unlocked balance can push dust shares to any address.
- `DepositToken._withdraw` routes the fee through `_transfer(account_, _pool.feeCollector(), _fee)` before burning (`DepositToken.sol:545-551`), and the deposit path does the same for the deposit fee. `feeCollector` is a single protocol-wide address that users cannot alter per-call.
- Attack steps (fully unprivileged, no privileged role needed):
  1. Deposit a minimal amount into each active `DepositToken` in the pool (or use flash-borrowed funds; shares only need to remain unlocked — attacker keeps zero debt).
  2. Call `depositToken.transfer(feeCollector, dust)` for each distinct deposit token until `depositTokensOfAccount.length(feeCollector) + debtTokensOfAccount.length(feeCollector) == 30`. If the pool lists fewer than 30 collaterals, repeat across additional listed deposit tokens and, if needed, front-run / combine with a second pool's deployments where `feeCollector` is shared. The deployed pools list multiple deposit tokens and new collateral additions over time only reduce the attacker's cost.
  3. Once `feeCollector`'s list is full, any user calling `depositToken.withdraw(...)` or `deposit(...)` while the corresponding fee is non-zero reverts inside `_transfer` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`.

The invariant that breaks is liveness: users cannot exit positions because the fee leg of every withdrawal reverts.

### Impact Explanation
Temporary freezing of user funds. All fee-bearing deposits and withdrawals on the affected pool revert for every user until `feeCollector` (a multisig/EOA) transfers shares out to shrink its list below 30. Users who are underwater cannot even withdraw unlocked collateral in the meantime, and liquidations that route seized shares to a `feeCollector`-saturated or full recipient list can also revert (`seize` → `_transfer` → `addToDepositTokensOfAccount`). The attacker only forfeits dust collateral.

### Likelihood Explanation
Moderate. Requires the pool to list enough deposit tokens to fill the cap (cost scales with the number of listed collaterals and their minimum deposit sizes) and requires a non-zero deposit/withdraw fee, which is a governance-set but commonly enabled configuration. No privileged action or oracle manipulation is needed; the only mitigation is `feeCollector` proactively clearing its list, which requires noticing the attack and spending gas on transfers.

### Recommendation
- Do not add `feeCollector` (and other protocol-internal fee recipients) to `depositTokensOfAccount`: in `DepositToken._transfer`, skip `pool.addToDepositTokensOfAccount(recipient_)` when `recipient_ == pool.feeCollector()`, and symmetrically skip `removeFromDepositTokensOfAccount` for that address, or track fee balances separately since `debtPositionOf(feeCollector)` is never needed for risk accounting.
- Alternatively, make `addToDepositTokensOfAccount` non-reverting for protocol fee recipients (cap check only applied for user accounts that can hold debt).

### Proof of Concept
Foundry fork (pool with ≥ N listed deposit tokens and `withdrawFee > 0`):

```solidity
function testFeeCollectorDosFreeze() public {
    address victim = makeAddr("victim");
    address[] memory dts = pool.getDepositTokens();        // listed DepositTokens
    IPool _pool = pool;
    address feeCollector = _pool.feeCollector();

    // 1) Attacker dust-fills feeCollector's list
    for (uint256 i; i < dts.length; ++i) {
        DepositToken dt = DepositToken(dts[i]);
        IERC20 underlying = dt.underlying();
        deal(address(underlying), attacker, 1e18);
        vm.startPrank(attacker);
        underlying.approve(address(dt), 1e18);
        dt.deposit(1e18);                  // attacker mints shares (zero debt => unlocked)
        if (dt.balanceOf(feeCollector) == 0) dt.transfer(feeCollector, 1);
        vm.stopPrank();
    }
    // Optionally also dust debt-token slots are not needed; once count hits 30:
    assertGe(
        _pool.getDepositTokensOfAccount(feeCollector).length +
        _pool.getDebtTokensOfAccount(feeCollector).length,
        _pool.MAX_TOKENS_PER_USER()
    );

    // 2) Any user's withdrawal now reverts inside the fee transfer
    DepositToken dt0 = DepositToken(dts[0]);
    deal(address(dt0.underlying()), victim, 100e18);
    vm.startPrank(victim);
    dt0.underlying().approve(address(dt0), 100e18);
    dt0.deposit(100e18);
    vm.expectRevert(IPool.UserReachedMaxTokens.selector);
    dt0.withdraw(50e18, victim);           // reverts: fee leg -> addToDepositTokensOfAccount(feeCollector)
    vm.stopPrank();
}
```
