### Title
Non-deterministic `StackOverflowError` handling in the TVM interpreter can desynchronize nodes and halt the chain - ([File: actuator/src/main/java/org/tron/core/vm/VM.java])

### Summary
The Cosmos `packet-forward-middleware` advisory describes a chain-halt caused by *error non-determinism*: different validators could reach different error/panic outcomes for the same input, causing consensus divergence. java-tron's TVM interpreter has an analogous pattern: it relies on catching a native JVM `StackOverflowError` as a *runtime* safety net for excessive call/recursion depth, rather than relying solely on a deterministic, protocol-enforced limit. Whether this native error actually fires for a given contract call depends on JVM/OS configuration (thread stack size, JVM vendor, JIT inlining) which is **not** part of consensus and can differ between honest full nodes, so the same transaction can legitimately produce different `contractResult` values on different nodes.

### Finding Description
`VM.play()` wraps opcode execution and explicitly catches the JVM's native `StackOverflowError`, converting it into a `Program.JVMStackOverFlowException`: [1](#0-0) 

That exception is a first-class TVM result code, mapped deterministically by name in `RuntimeImpl.setResultCode`: [2](#0-1) 

and in `VMActuator.execute`, catching it spends all remaining energy and sets `contractResult.JVM_STACK_OVER_FLOW` as the transaction outcome: [3](#0-2) 

The resulting `contractResult` is not merely informational — it is embedded by the block producer into the transaction's `Result.contractRet` field (part of the signed/broadcast `Transaction`), and every other node that later applies the block must reproduce the *same* result code or the block is rejected: [4](#0-3) 

`ReceiptCheckErrException` thrown here propagates directly out of `Manager.processBlock`, which is invoked while applying every block: [5](#0-4) 

The problem: whether a given deeply-recursive/deeply-nested-CALL transaction actually triggers a native `StackOverflowError` depends on the JVM thread's configured native stack size (`-Xss`), JVM vendor/version stack-frame layout, and JIT inlining decisions — none of which are part of the TRON consensus rules. The code even acknowledges this class of JVM-version-dependent non-determinism elsewhere for exception messages (`NullPointerException` handling references JEP-358's "helpful NPE" messages varying by JDK version): [6](#0-5) 

If a transaction's recursion/call depth sits near the boundary where one honest node (with a smaller configured/default stack, or a JVM build with larger per-frame overhead) throws `StackOverflowError` while another node (larger stack, different JVM build) completes the same call successfully, the two nodes will compute different `contractResult` values for the identical, deterministic input. The node whose result disagrees with the block producer's embedded `contractRet` will throw `ReceiptCheckErrException` inside `processBlock` and fail to apply the block, effectively desynchronizing/halting that node from the rest of the network — the same class of impact ("chain-halt due to error non-determinism") described in the referenced advisory.

### Impact Explanation
This is reachable by any unprivileged account that can broadcast a `TriggerSmartContract`/`CreateSmartContract` transaction invoking a contract with deep call/recursion nesting tuned to be near a node's native stack limit. Because the divergence manifests as a hard consensus-check failure (`ReceiptCheckErrException`) inside block application rather than a graceful fallback, affected nodes stop processing blocks — a node crash/halt and potential chain split between nodes running different JVM configurations (different `-Xss`, JVM vendor, or JDK version), which matches the "High" severity class of the referenced advisory (chain-halt via non-deterministic error path).

### Likelihood Explanation
Exploitability depends on the attacker being able to reliably trigger divergent behavior across real-world node deployments, which requires knowledge of/variance in operators' JVM stack configuration and versions. java-tron nodes are not required to run identical `-Xss`/JVM builds, so this variance plausibly exists across the live network, but crafting a transaction that reliably straddles the boundary for a meaningful fraction of nodes is nontrivial and would likely need empirical tuning. This lowers likelihood relative to the reachability of the code path itself.

### Recommendation
Replace reliance on catching the native `StackOverflowError` with a strictly deterministic, energy/gas-metered call-and-recursion depth counter enforced identically regardless of JVM stack configuration (i.e., reject/revert once a fixed logical depth constant is exceeded, before the native stack is ever at risk), so that `JVMStackOverFlowException`/`StackOverflowError` can never legitimately occur during normal execution and is purely a last-resort abort with a canonicalized, deterministic result rather than being reachable via crafted inputs that depend on host JVM configuration.

### Proof of Concept
Not independently reproduced (would require running two java-tron nodes with different `-Xss`/JVM configurations and a specially depth-tuned recursive/self-calling smart contract to empirically find a call depth where outcomes diverge). Root cause is demonstrated via the code paths cited above: `VM.java`'s catch of native `StackOverflowError`, its mapping to `contractResult.JVM_STACK_OVER_FLOW`, and `TransactionTrace.check()`/`Manager.processBlock` enforcing exact-match consensus on that result code.
