### Title
DebtToken rewards accrue on the interest-inflated `balanceOf` retroactively, overpaying passive borrowers at the expense of active ones - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
This is the same bug class as the referenced finding: reward distribution is computed on an index-growing *balance* rather than on a stable *share/principal* unit. In `RewardsDistributor._calculateTokenDelta`, a user's accrued rewards are computed as `token_.balanceOf(account_).wadMul(_deltaIndex)`, i.e. the balance **at update time** multiplied by the **entire** index delta accumulated since their last update (`contracts/RewardsDistributor.sol:229-230`). For `DebtToken`, `balanceOf` is not a static share - it is `principalOf[account_] * _debtIndex / debtIndexOf[account_]`, which grows continuously as interest accrues (`contracts/DebtToken.sol:196-206`). Because the reward index deltas were computed against a *smaller* `totalSupply()` in the past, applying today's interest-inflated balance to historical index deltas retroactively credits users for debt they did not yet have. Users who update less often receive strictly more rewards per unit of principal than users who update often.

### Finding Description
- `_updateTokensAccruedOf` → `_calculateTokenDelta` reads `token_.balanceOf(account_)` at the moment of update and multiplies it by `tokenIndex - accountIndexOf` (`contracts/RewardsDistributor.sol:217-231`).
- For `DebtToken`, both `balanceOf` and `totalSupply` grow proportionally to `debtIndex` (`contracts/DebtToken.sol:196-206`, `contracts/DebtToken.sol:500-503`, `contracts/DebtToken.sol:551-566`).
- The fair accrual for a constant principal is `principal_share × Σ speed_t·Δt`, since `balance_t / totalSupply_t` is constant. Instead the contract computes `balance_now × Σ(speed_t·Δt / totalSupply_t)`, which equals the fair amount times the average of `debtIndex_now / debtIndex_t` over the elapsed window — always ≥ 1, and > 1 whenever interest accrues between updates.
- `_burn` and `_mint` wrap `updateRewardsBeforeMintOrBurn` (`contracts/DebtToken.sol:525`, `contracts/DebtToken.sol:577`), so a user who repays/mints frequently checkpoints at smaller balances and accumulates less total rewards than an identical passive debtor. `updateBeforeMintOrBurn` is also permissionlessly callable (`contracts/RewardsDistributor.sol:175-180`), but only updates the *caller-specified* account's accrual with the same inflated balance — it does not fix the over-accrual, it just commits it.
- This mirrors the referenced report: the protocol accrues rewards on an index-scaled asset balance instead of on a fixed share (`principalOf`), making distribution depend on update timing rather than actual contribution.

### Impact Explanation
Theft/redistribution of unclaimed yield: a fixed reward emission (`tokenSpeeds × Δt`) is divided among reward-token holders via the index. A passive debtor's over-accrual dilutes and reduces the claimable rewards of every other holder of that DebtToken (the reward token balance paid out by `_transferRewardIfEnoughTokens` is finite). The distortion grows with the DebtToken `interestRate` and the elapsed time since each account's last `updateBeforeMintOrBurn`. It is reachable purely via public entry points — simply holding debt (acquired via `DebtToken.issue`) and calling `claimRewards(account_)` once, versus updating via dust `repay` calls — no privileged role required.

### Likelihood Explanation
Requires two config conditions: `interestRate > 0` on a DebtToken and a nonzero `tokenSpeeds` for that DebtToken in a `RewardsDistributor`. Both are governance-set deployment parameters commonly enabled to incentivize borrowing. The effect per epoch is bounded by the interest growth factor between account updates, so individual loss magnitude is moderate and depends on other users' update frequency — consistent with a medium-severity accounting flaw rather than a direct drain.

### Recommendation
Accrue rewards on the stable principal unit rather than the interest-growing balance. For DebtToken, base the delta on `principalOf[account_]` (and the index on the principal-scaled supply, e.g. `totalSupply_ / debtIndex`), or snapshot the user's principal in the distributor at `updateBeforeMintOrBurn`/`updateBeforeTransfer` time. Alternatively, normalize `balanceOf` by `debtIndex` inside `_calculateTokenDelta` for interest-bearing reward tokens.

### Proof of Concept
Reproducible in the existing Hardhat setup (see `test/RewardDistributor.test.ts`):

```ts
// U1 and U2 each issue 100e18 of the same debt token (same principal).
// RewardsDistributor has tokenSpeeds[debtToken] > 0; debtToken.interestRate > 0.

// t=0: U1 and U2 issue debt (updateBeforeMintOrBurn checkpoints both).
// Time passes: debtIndex grows, both balances grow 100 -> 150.

// U2 makes a dust repay (repay(U2, 1 wei)) -> updateBeforeMintOrBurn accrues
//    U2's delta using balanceOf(U2) ~= 150 at this midpoint index.

// More time passes: balances grow 150 -> 200.
// U1 never interacts.

// At end: claimRewards for both.
//   U1 delta = 200 * (index_end - index_0)
//   U2 delta = 150 * (index_mid - index_0) + 200 * (index_end - index_mid)
// U1.accrued > U2.accrued despite identical principal history.
// Assert: tokensAccruedOf[U1] > tokensAccruedOf[U2].
```

Invariant broken: reward accrual is a function of checkpoint timing, not of principal contribution — identical positions earn different rewards based solely on how often the user touches the protocol.

Uncertain aspects: I did not fully verify `DepositToken`'s reward path (it appears to be a plain non-rebasing ERC20, so the deposit side is likely unaffected); the finding is specific to interest-bearing `DebtToken` reward distribution. Deployed `interestRate`/`tokenSpeeds` values were not confirmed from this index.
