### Title
Value transferred to a precompiled contract is permanently lost (not refunded to sender) when the precompiled call fails - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
`Program.callToPrecompiledAddress()` mirrors the `elections_master` bug class: on a failed sub-call, TRX/TRC10 value that has already been moved is not returned to the sender, so it is misallocated/stranded on failure instead of being safely reverted.

### Finding Description
When a contract makes a value-carrying `CALL`/`CALLCODE`/`DELEGATECALL` to a precompiled contract address, `callToPrecompiledAddress()` transfers the endowment from the caller to the target **before** invoking `contract.execute(data)`: [1](#0-0) 

The comment explicitly states the charge "is not reversible by rollback." The transfer is performed on the `deposit` child repository via `MUtil.transfer()` / `deposit.addTokenBalance()`: [2](#0-1) 

After the transfer, the precompiled contract is executed. If it fails (`out.getLeft() == false`), the code only refunds energy and pushes zero onto the stack — it never reverses the balance change made moments earlier: [3](#0-2) 

This is structurally identical to the reported `elections_master.on_bounce()` flaw: a value transfer is committed as part of a multi-step action, the subsequent step of that same action fails, and the fund-movement is not correctly reconciled with the failure — funds end up somewhere other than where the protocol intends (in this case, stuck at the precompiled contract address / sender balance not restored), rather than being cleanly rolled back to the caller as callers of EVM/TVM `CALL` semantics expect (a failed call is supposed to look like `deposit.commit()` was never invoked).

### Impact Explanation
A caller contract that sends TRX/TRC10 value together with a call to a precompiled contract address that subsequently fails (e.g., insufficient energy inside `contract.execute()`, malformed input causing internal failure, or any precompiled contract returning `false`) permanently loses that value — it is not refunded to the sender and the call is reported as failed (stack pushes `0`), so the calling contract's logic believes no state change occurred, while in fact a balance transfer has already taken effect. This produces an unbacked-balance/fund-freezing condition: the sender's balance is decremented and the destination address's balance is incremented despite the operation as a whole "failing," breaking the atomicity guarantee that Solidity/TVM developers rely on for `call{value: x}(...)` semantics.

### Likelihood Explanation
Reachable by any anonymous account that deploys or triggers a smart contract making a value-carrying call to a precompiled contract address that can be made to fail (e.g., by supplying insufficient energy so `requiredEnergy` check still passes but internal precompiled logic errors out, or by constructing input that causes the specific precompiled contract's `execute()` to return `false`). No special privileges are needed — a single `TriggerSmartContract` transaction from any account can exercise this path.

### Recommendation
Move the endowment transfer to occur only after `contract.execute()` succeeds, or make the transfer part of the same `deposit` repository transaction that is discarded (not committed) on failure so that a failing precompiled call fully reverts, consistent with the atomicity semantics of `CALL`. If the "not reversible by rollback" behavior is intentional for specific precompiles (e.g., legacy compatibility), that intent should be explicitly validated against downstream precompiled contracts and clearly documented, and a mechanism to return stranded funds to the original sender should be added.

### Proof of Concept
1. Deploy a contract `A` that calls a precompiled contract address with `value > 0`, e.g. via `staticcall`/`call` opcode targeting an address handled by `PrecompiledContracts.getContractForAddress()`.
2. Craft the call data such that `contract.execute(data)` inside the precompiled contract implementation returns `Pair.of(false, ...)` (many precompiles return `false` on certain invalid inputs) while `requiredEnergy <= msg.getEnergy()` still holds so the transfer branch is entered first.
3. Observe: `MUtil.transfer()` moves `endowment` sun from `senderAddress` to `contextAddress` before `contract.execute()` runs.
4. `contract.execute()` returns `false`; `callToPrecompiledAddress()` takes the `else` branch, pushes `0`, and returns — the earlier balance transfer is never undone.
5. Verify via account balance queries (`Wallet`/`TronJsonRpcImpl` `eth_getBalance` or `GetAccount`) that `senderAddress` lost `endowment` sun and `contextAddress` gained it, despite the call reporting failure to the caller contract.
