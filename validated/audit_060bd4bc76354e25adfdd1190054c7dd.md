### Title
Anti-replay window check-then-act race in `ConnectionState.Decrypt`/`VerifyRelay` allows the same captured packet to be replayed twice - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the anti-replay check and the anti-replay commit into two separate, unlocked critical sections with an expensive AEAD decryption operation in between. This mirrors the M-2 pattern (`Utilization rate check can be bypassed depositing additional loan tokens and withdrawing them in the same transaction`): a decision is made against a stale snapshot of shared state, and the state is only updated after other work has completed, leaving a window in which the same input can pass the guard twice.

### Finding Description
`ConnectionState.Decrypt` performs the anti-replay check and the anti-replay commit as two independently locked operations: [1](#0-0) 

and `VerifyRelay` has the identical pattern for relay frames: [2](#0-1) 

`cs.window.Check()` is called under `decryptLock`, then the lock is released, then `DecryptDanger` (an AEAD decrypt) runs unlocked, and only afterward does `cs.window.Update()` re-acquire the lock to actually mark the counter as consumed: [3](#0-2) [4](#0-3) 

This `ConnectionState` (and its `Bits` replay window) is shared across the interface's multiple concurrent UDP-reader goroutines. `Interface.run` launches `f.routines` goroutines that each independently call `listenOut` → `readOutsidePackets` → `ConnectionState.Decrypt`/`VerifyRelay` for whatever hostinfo the packet resolves to: [5](#0-4) [6](#0-5) 

Because `Check` and `Update` are not performed atomically as a single critical section, if two copies of the same ciphertext (same `MessageCounter`) are delivered to two different reader queues at close to the same time, both can call `Check()` and both observe "not yet seen" before either has called `Update()`. Both then proceed to decrypt and process the packet, so the same message counter is accepted twice — the replay-window guarantee ("no duplicate `MessageCounter` is ever delivered") is violated. This is exactly the same class of bug as the referenced report: a security-critical invariant is checked against a snapshot of mutable state, but the actual state mutation that would make the check meaningful is deferred past other work, creating a TOCTOU window an external actor can exploit by supplying duplicate/parallel inputs.

An attacker does not need a CA-signed certificate or valid peer identity to trigger this: they only need to capture one legitimate encrypted UDP packet on the wire (an on-path or off-path spoofing/duplicating attacker) and re-inject duplicate copies of it toward the victim's UDP socket at (near-)the same time, timed to land on different reader goroutines.

### Impact Explanation
Successful exploitation causes:
- Duplicate delivery of a captured/replayed packet into the plaintext path — `f.handleOutsideMessagePacket` writing the same decrypted payload to the TUN device twice, or `handleOutsideRelayPacket` forwarding the same relay frame twice — even though the anti-replay window is specifically designed to guarantee "at most once" delivery per message counter.
- This is a concrete traffic-replay/decryption-integrity bypass: it defeats the core security property the sliding-window `Bits` anti-replay mechanism (`ReplayWindow = 1024`, `connection_state.go:15`) exists to provide, for both direct-tunnel data and relay-forwarded frames.
- For relay-forwarded traffic in particular, duplicated forwarding wastes relay bandwidth/CPU and can be used to amplify attacker traffic through a relay node.

### Likelihood Explanation
The window between `Check()` unlocking and `Update()` re-locking spans a full AEAD decrypt, which is a nontrivial, schedulable amount of work, and it is entirely feasible for an attacker who can duplicate a captured UDP datagram to land two copies on two different reader goroutines within that window, especially when `f.routines > 1` (multiple UDP listener queues, a common performance configuration). No cryptographic material or valid certificate is required — only the ability to capture and resend ciphertext.

### Recommendation
Perform the replay-window check-and-mark as a single atomic operation instead of two independently-locked steps, e.g. hold `decryptLock` across a `CheckAndReserve`-style call that marks the counter as "in-flight/consumed" before releasing the lock for the actual decrypt, and roll back the reservation only if decryption subsequently fails. This removes the TOCTOU gap between the check and the commit, analogous to how the referenced fix closed the loan-token gap by disallowing state to be exploited within the same window as the check.

### Proof of Concept
1. Establish a legitimate tunnel between two nebula nodes, with the responder configured with `f.routines > 1` (multiple UDP reader queues / `SO_REUSEPORT`).
2. Capture one legitimate encrypted `header.Message` UDP packet sent to the responder (e.g. via a network tap or on-path position); no decryption of its contents is needed.
3. Simultaneously re-inject two (or more) copies of the exact same captured ciphertext toward the responder's UDP port, timed so they are likely to be picked up by different `listenOut` reader goroutines at close to the same wall-clock time.
4. Because `cs.window.Check()` and `cs.window.Update()` in `ConnectionState.Decrypt` (connection_state.go:61-82) are not atomic, both copies can pass `Check()` before either calls `Update()`; both are decrypted and delivered to the TUN device (or forwarded again if it is a relay frame), instead of the second copy being rejected as `ErrAlreadySeen`.

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
