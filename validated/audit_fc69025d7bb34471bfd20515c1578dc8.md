## Title
Unchecked `u64` multiplication overflow in `estimate_tx_fee_from_cost_and_length` via attacker-controlled `estimated_len` - (File: stackslib/src/net/api/postfeerate.rs)

## Summary
The `POST /v2/fees/transaction` handler accepts an attacker-supplied `estimated_len` field of type `Option<u64>` from the JSON body, bounds only the raw HTTP body byte length via `content_len < MAX_PAYLOAD_LEN`, and never validates the numeric magnitude of `estimated_len` itself. This value flows unchanged into `minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE`, an unchecked multiplication that overflows for large `estimated_len` values.

## Finding Description
In `RPCPostFeeRateRequestHandler::try_parse_request` [1](#0-0) , `content_len` (the HTTP `Content-Length`) is bound-checked against `MAX_PAYLOAD_LEN`, but this only limits how many raw bytes the body can contain — it says nothing about the numeric value encoded in the small JSON field `estimated_len`. A tiny JSON body such as `{"estimated_len": 18446744073709551615, "transaction_payload": "0x..."}` easily fits under `MAX_PAYLOAD_LEN` while still deserializing `estimated_len` as `u64::MAX` via `serde_json::from_slice` into `FeeRateEstimateRequestBody.estimated_len: Option<u64>` [2](#0-1) .

The parsed value is combined with `max(body.estimated_len, payload_data.len())` and stored unchanged in `self.estimated_len` [3](#0-2) . It is then passed into `estimate_tx_fee_from_cost_and_length`, where:

```rust
let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;
``` [4](#0-3) 

This is a plain `*` operator on `u64`, not `checked_mul`/`saturating_mul`. With `estimated_len = u64::MAX` and any non-zero `MINIMUM_TX_FEE_RATE_PER_BYTE` (a nonzero constant defined in `stackslib/src/chainstate/stacks/db/blocks.rs`), the multiplication overflows.

There is no authentication gate on this endpoint visible in the handler — `try_parse_request`/`try_handle_request` perform no secret/token check, so any remote peer able to reach the RPC port can send this request.

- In debug builds, Rust's default overflow checks cause this to **panic** (`attempt to multiply with overflow`), which — depending on how the HTTP worker thread panic is handled — can crash or hang the request-handling thread/task for that connection.
- In release builds, the multiplication silently wraps, producing an incorrect (and unpredictable, attacker-influenced) `minimum_fee` that is used to clamp `estimate.fee` in the response `RPCFeeEstimateResponse`, corrupting the returned fee estimate that a wallet/bridge might trust.

## Impact Explanation
This affects the read-endpoint `/v2/fees/transaction`. The impact is bounded to: (a) a possible panic in the handling thread on debug/overflow-checked builds triggered by a single small HTTP request, and (b) in release builds, a corrupted/wrapped `minimum_fee` value silently returned to callers, misleading fee-estimation clients (wallets, bridges) that trust the response. This is a bounded-compute/logic-correctness issue on a single read-only RPC endpoint, not a state-write, consensus, or network-propagation issue — it does not forge data, does not affect chain state, and does not require any privileged role. This aligns with the "bounded compute DoS/incorrect data on a read endpoint" category rather than the more severe "remote crash from a single message causing broader denial of service" categories, since impact is scoped to the single request/thread handling that endpoint (unless the panic escapes and takes down the whole RPC server, which was not established in the reachable code paths I could inspect).

## Likelihood Explanation
No preconditions are required beyond the attacker being able to reach the node's RPC port (`/v2/fees/transaction`), which requires no secret, peer key, or StackerDB slot. The attack is a single crafted small HTTP POST, trivially repeatable at will and at negligible attacker cost.

## Recommendation
Replace the raw multiplication with a checked/saturating operation, e.g.:
```rust
let minimum_fee = estimated_len.saturating_mul(MINIMUM_TX_FEE_RATE_PER_BYTE);
```
Additionally, validate `estimated_len` against a sane upper bound (e.g., `MAX_PAYLOAD_LEN` or the max block size) in `try_parse_request` before accepting it, rejecting the request with a `DecodeError` if it is unreasonably large, rather than only relying on `content_len < MAX_PAYLOAD_LEN` which bounds bytes, not the numeric field value.

## Proof of Concept
Rust test plan (in `stackslib/src/net/api/postfeerate.rs` test module or `stackslib/src/net/api/tests/postfeerate.rs`):
1. Construct a `FeeRateEstimateRequestBody { estimated_len: Some(u64::MAX), transaction_payload: "0x<small valid token-transfer payload hex>".to_string() }`.
2. Serialize to JSON, confirm body byte length `< MAX_PAYLOAD_LEN`.
3. Call `RPCPostFeeRateRequestHandler::try_parse_request` with a preamble whose `Content-Length` matches the small body — assert it succeeds and sets `self.estimated_len == Some(u64::MAX)`.
4. Call `RPCPostFeeRateRequestHandler::estimate_tx_fee_from_cost_and_length` (or the full `try_handle_request` via a configured `fee_estimator`) with `estimated_len = u64::MAX`.
5. Assert: in a debug/overflow-checked build, this call panics with "attempt to multiply with overflow" at `let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;` (postfeerate.rs:112); or, running with overflow checks disabled, assert the returned `minimum_fee`/`estimate.fee` equals the wrapped value `(u64::MAX).wrapping_mul(MINIMUM_TX_FEE_RATE_PER_BYTE)` rather than the mathematically unbounded expected fee, demonstrating corrupted output.
