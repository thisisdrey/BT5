## Analysis

Nebula's relay control protocol contains an authorization gap analogous to the SKALE `linkNodeAddress`/`unlinkNodeAddress` bug: a message field that identifies "whose state this is about" is trusted from an attacker-controlled payload rather than tied to the cryptographically authenticated sender.

### Title
Relay control messages let an authenticated peer forge relay state ("RelayFromAddr") for a third-party VPN address it does not own - (File: `relay_manager.go`)

### Summary
`relayManager.handleCreateRelayRequest` derives the identity of the relay-requesting peer (`from`) directly from the `RelayFromAddr`/`OldRelayFromAddr` field inside the `NebulaControl` message body, rather than from the authenticated `HostInfo` (`h`) that decrypted/verified the packet. There is no check that `from == h.vpnAddrs[0]`.

### Finding Description
In `relayManager.HandleControlMsg`, `h` is the already-authenticated `*HostInfo` for the tunnel that decrypted the incoming `Control` packet [1](#0-0) . The message payload `msg` is then unmarshalled and dispatched to `handleCreateRelayRequest(v, h, f, msg)` [2](#0-1) .

Inside `handleCreateRelayRequest`, the "from" (relay initiator) address used for all subsequent relay bookkeeping is taken from the message body (`m.RelayFromAddr`/`m.OldRelayFromAddr`), not from `h.vpnAddrs`: [3](#0-2) 

The only checks performed are whether `from` or `target` happen to be *my own* address; there is no check that `from` equals the actual authenticated peer identity (`h.vpnAddrs[0]`). When I am the target, the code creates/updates relay state keyed by this attacker-supplied `from` value: [4](#0-3) 

`AddRelay` is called with `h` (the real, authenticated hostinfo for the connection) but `from` (the claimed, unauthenticated address) as the `vpnIp`/`PeerAddr` key: [5](#0-4) 

This is structurally the same class of bug as the SKALE report: a party that holds a legitimate, authenticated relationship (a validator-linked node / an established Nebula tunnel) is trusted to assert an identity/ownership claim (`nodeAddress` / `RelayFromAddr`) about a *different* principal, and the receiving code performs the sensitive state mutation (`unlinkNodeAddress` / `AddRelay`+relay state table update) keyed on that unverified claim instead of the verified caller identity.

### Impact Explanation
An authenticated Nebula peer `A` that has any real tunnel to node `T` can send a `CreateRelayRequest` to `T` with `RelayFromAddr` set to victim `B`'s VPN address (any address in the network, including one `A` has never actually handshaked with). `T` will install relay/forwarding state that associates `B`'s VPN address with the tunnel to `A`, and will reply with a `CreateRelayResponse` addressed back to `A` (`f.SendMessageToHostInfo(header.Control, 0, h, ...)` where `h` is still `A`'s hostinfo) [6](#0-5) . This lets `A` poison `T`'s relay routing table for `B`'s address and potentially position itself in the path for traffic `T` believes it is relaying to/from `B` — a remote state-poisoning / traffic-redirection primitive reachable by any peer that has a live authenticated tunnel, without needing to possess `B`'s certificate or private key.

### Likelihood Explanation
Reachable by any Nebula node holding a valid certificate signed by a trusted CA and an established tunnel to the target — no possession of the victim's key material is required, and no special configuration (e.g., `am_relay`) is needed for the terminal-side code path (`f.myVpnAddrsTable.Contains(target)` branch) to execute. The attack only requires sending one crafted `Control`/`CreateRelayRequest` message over an existing tunnel.

### Recommendation
In `handleCreateRelayRequest` (and `handleCreateRelayResponse`), validate that `from` (`RelayFromAddr`/`OldRelayFromAddr`) matches the authenticated sender's own vpn address (`h.vpnAddrs`), analogous to the existing check already done for lighthouse `HostUpdateNotification` (`!slices.Contains(fromVpnAddrs, detailsVpnAddr)`) [7](#0-6) . Reject/drop CreateRelayRequest messages where the claimed `RelayFromAddr` does not belong to the authenticated peer that sent the control message.

### Proof of Concept
Conceptual (not executed, since I have read-only access):
1. Node `A` establishes a normal authenticated tunnel to node `T`.
2. `A` crafts a `NebulaControl` message with `Type = CreateRelayRequest`, `RelayFromAddr = B` (any other VPN address on the network, not `A`'s own), `RelayToAddr = T`'s address, and a chosen `InitiatorRelayIndex`.
3. `A` sends this as a `header.Control` packet over its own encrypted tunnel to `T`.
4. `T`'s `relayManager.HandleControlMsg` decrypts the packet using the authenticated `HostInfo` for `A`, but `handleCreateRelayRequest` uses the forged `RelayFromAddr = B` to install relay state as if `B` were relayed through `A`'s tunnel, and sends a `CreateRelayResponse` back to `A`.
5. `T` now has relay-routing state binding `B`'s vpn address to `A`'s tunnel, without `A` ever proving control of `B`'s certificate/key.

Note: full exploitation impact (e.g., whether this can be leveraged to intercept/redirect live traffic destined for `B`, versus merely poisoning bookkeeping state that a legitimate handshake would later overwrite) was not fully traced through `QueryVpnAddrsRelayFor`/`handleOutsideRelayPacket` forwarding logic within the available investigation budget; a Devin session with the ability to run the e2e test harness (`e2e/handshakes_test.go`, `e2e/tunnels_test.go`) would be needed to confirm the exact blast radius experimentally.

func AddRelay(l *slog.Logger, relayHostInfo *HostInfo, hm *HostMap, vpnIp netip.Addr, remoteIdx *uint32, relayType int, state int) (uint32, error) {
	hm.Lock()
	defer hm.Unlock()
	for range 32 {
		index, err := generateIndex(l)
		if err != nil {
			return 0, err
		}

		_, inRelays := hm.Relays[index]
		if !inRelays {
			// Avoid standing up a relay that can't be used since only the primary hostinfo
			// will be pointed to by the relay logic
			//TODO: if there was an existing primary and it had relay state, should we merge?
			if !hm.unlockedMakePrimary(relayHostInfo) {
				// The tunnel was torn down after the caller grabbed relayHostInfo. A relay standing
				// on an unlinked hostinfo would never carry traffic, and its Relays entry could
				// never be reclaimed since the delete-time cleanup has already run.
				return 0, errors.New("relay hostinfo is no longer in the hostmap")
			}

			hm.Relays[index] = relayHostInfo
			newRelay := Relay{
				Type:       relayType,
				State:      state,
				LocalIndex: index,
				PeerAddr:   vpnIp,
			}

			if remoteIdx != nil {
				newRelay.RemoteIndex = *remoteIdx
			}
			relayHostInfo.relayState.InsertRelay(vpnIp, index, &newRelay)

			return index, nil
		}
	}

	return 0, errors.New("failed to generate unique localIndexId")
}

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}

		"relayTo", target,
