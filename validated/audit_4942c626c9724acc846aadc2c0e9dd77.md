## Analysis

This maps cleanly to the CXF bug class: **an entire response payload is fully materialized in memory with no size bound before any size check is applied**, exactly mirroring CXF's "read the whole file into memory before it should have streamed/limited it."

### Title
JSON-RPC batch handler buffers each sub-response fully and unboundedly in memory before enforcing the response-size limit, enabling an OOM DoS - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/JsonRpcServlet.java`)

### Summary
`JsonRpcServlet.handleBatch` protects the *aggregate* batch response with `maxResponseSize`, but each individual sub-request's result is generated into an **unbounded** `ByteArrayOutputStream` before that check is ever applied, allowing a single large JSON-RPC call embedded in a batch to force the node to buffer an arbitrarily large result in memory.

### Finding Description
In the single-request path, `handleSingle` wraps the response in `BufferedResponseWrapper` constructed with `maxResponseSize`, which enforces the byte cap incrementally on every `write()` call, discarding bytes once the limit is exceeded [1](#0-0) , backed by `BufferedResponseWrapper`'s streaming overflow check [2](#0-1) .

In the batch path, however, each sub-request is dispatched with a plain, unbounded `ByteArrayOutputStream`: [3](#0-2) 

`rpcServer.handleRequest(...)` runs the entire JSON-RPC method (e.g. any method exposed via `TronJsonRpcImpl`/`TronJsonRpc`) to completion and writes its full serialized result into `subOutput` with no size ceiling. Only *after* `responseBytes.length` is fully known does the code check it against `maxResponseSize`: [4](#0-3) 

The `jsonRpcMaxBatchSize` check earlier only limits the *number* of sub-requests in a batch [5](#0-4) , it does nothing to bound the size of any single sub-request's result. An attacker can send a batch containing as few as one JSON-RPC call to a data-heavy, unbounded method (e.g. a wide-range `eth_getLogs`, a large block/trace query, etc. exposed through `TronJsonRpcImpl`) and the full result will be built and serialized in memory before the size check has any chance to react.

### Impact Explanation
Because there is no bound during generation, the node can be forced to allocate memory proportional to the underlying query result size (multiplied by concurrent requests), which can exhaust heap and crash or hang the full node — a Denial of Service against the JSON-RPC API, reachable by any anonymous API client with no authentication or special privileges, matching CWE-400 the same way as CVE-2025-48795.

### Likelihood Explanation
The JSON-RPC HTTP endpoint is a standard externally reachable interface (no signed transaction or special permission required). An attacker only needs to craft one JSON-RPC batch array containing a single sub-request to an unbounded data-returning method; this is a trivial, repeatable, low-cost attack.

### Recommendation
Wrap each batch sub-request's output stream with the same bounded mechanism used in `handleSingle` (e.g. reuse `BufferedResponseWrapper`-style incremental limit enforcement, or a size-capped `OutputStream` that aborts/truncates once `maxResponseSize` is exceeded) so oversized individual results are rejected during generation rather than after they are fully buffered.

### Proof of Concept
1. Configure/keep default `jsonRpcMaxResponseSize` at a normal small-to-moderate value.
2. Send a JSON-RPC batch request with a single element calling a data-heavy method known to return unboundedly large results based on attacker-controlled range parameters (e.g. `eth_getLogs` with a huge `fromBlock`/`toBlock` span) via `handleBatch` at [6](#0-5) .
3. Observe that `rpcServer.handleRequest` fully computes and serializes the (huge) result into an unbounded `ByteArrayOutputStream` before the `maxResponseSize` comparison at line 233 is ever reached, causing large, uncontrolled memory allocation regardless of the configured response-size limit.

  private void handleBatch(HttpServletResponse resp, JsonNode rootNode, int maxResponseSize)
      throws IOException {

    ArrayNode batchResult = MAPPER.createArrayNode();
    int accumulatedSize = 2; // "[]"
    boolean overflow = false;

    for (int i = 0; i < rootNode.size(); i++) {
      JsonNode subRequest = rootNode.get(i);

      if (overflow) {
        if (!subRequest.isObject()) {
          batchResult.add(buildErrorNode(JsonRpcError.INVALID_REQUEST, "Invalid Request", null));
        } else if (subRequest.has("id")) {
          // Notifications (no "id") do not get a response even on overflow.
          batchResult.add(buildErrorNode(JsonRpcError.RESPONSE_TOO_LARGE,
              "Response exceeds the limit of " + maxResponseSize + " bytes",
              subRequest.get("id")));
        }
        continue;
      }

      if (!subRequest.isObject()) {
        ObjectNode errNode = buildErrorNode(JsonRpcError.INVALID_REQUEST, "Invalid Request", null);
        byte[] errBytes = MAPPER.writeValueAsBytes(errNode);
        int addition = errBytes.length + (!batchResult.isEmpty() ? 1 : 0);
        if (maxResponseSize > 0 && accumulatedSize + addition > maxResponseSize) {
          overflow = true;
        } else {
          accumulatedSize += addition;
        }
        batchResult.add(errNode);
        continue;
      }

      byte[] subBody;
      try {
        subBody = MAPPER.writeValueAsBytes(subRequest);
      } catch (JsonProcessingException e) {
        writeJsonRpcError(resp, JsonRpcError.INTERNAL_ERROR, "Internal error", null, true);
        return;
      }

      ByteArrayOutputStream subOutput = new ByteArrayOutputStream();
      try {
        rpcServer.handleRequest(new ByteArrayInputStream(subBody), subOutput);
      } catch (RuntimeException e) {
        logger.error("RPC execution failed for batch sub-request {}", i, e);
        writeJsonRpcError(resp, JsonRpcError.INTERNAL_ERROR, "Internal error", null, true);
        return;
      }

      byte[] responseBytes = subOutput.toByteArray();
