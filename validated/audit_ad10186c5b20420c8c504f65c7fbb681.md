### Title
Unbounded array allocation from attacker-controlled length in `ValidateMultiSign` precompile before hard-fork guards activate - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`ValidateMultiSign.execute()` decodes an attacker-supplied signature-array length directly from calldata and allocates a Java array sized by that length, with no upper bound, whenever both `VMConfig.allowTvmOsaka()` and `VMConfig.allowTvmSelfdestructRestriction()` are `false` for the executing chain configuration.

### Finding Description
`ValidateMultiSign.execute()` first checks `isValidAbiEncoding` only when `allowTvmOsaka()` is enabled [3](#0-2) . It then reads `permissionId`/`data` and computes a SHA-256 `hash` [4](#0-3) . The `MAX_SIZE` (5) bound on the signature-array length is only enforced when `VMConfig.allowTvmSelfdestructRestriction()` is true [5](#0-4) . When that flag is off, the code calls `extractBytesArray(words, words[3].intValueSafe() / WORD_SIZE, rawData)` unconditionally [6](#0-5) , which does `int len = words[offset].intValueSafe(); byte[][] bytesArray = new byte[len][];` [7](#0-6)  — `len` is fully attacker-controlled (up to `Integer.MAX_VALUE` via `intValueSafe()`), and the `MAX_SIZE` check on `signatures.length` only happens *after* this allocation already executed [8](#0-7) . Only the address-recovery/weight-checking loop that follows is wrapped in `try { ... } catch (Throwable t)` [9](#0-8)  — the array allocation itself is outside that guard. A `new byte[Integer.MAX_VALUE][]` reference-array allocation (~16GB of pointers on a 64-bit JVM) or a large `extractBytes`/`Arrays.copyOfRange` call inside the loop can throw `OutOfMemoryError`, which is an uncaught `Error` at that point in the method, structurally analogous to the reported Node.js WebCrypto bug where an oversized/boundary input size crashes the process instead of being rejected.

### Impact Explanation
If the `OutOfMemoryError`/`NegativeArraySizeException` thrown from the unguarded allocation propagates past the TVM's precompile dispatch without being caught (this final step of the call chain, `Program.callToPrecompiledAddress`, was not verified in this session), it can crash or destabilize the node process that executes the transaction, which every full node in the network would replay — potentially producing a network-wide denial of service triggered by a single crafted transaction calling the `validatemultisign` precompile address. Even if caught at a higher layer, the massive transient allocation attempt itself is a resource-exhaustion vector on affected nodes.

### Likelihood Explanation
This path is reachable by any unprivileged account: `ValidateMultiSign` is a public precompiled contract callable via a `CALL`/`STATICCALL` from any smart contract, meaning any user who can broadcast a contract-triggering transaction can construct calldata that sets `words[3]`'s pointed-to length word to a very large value. The trigger condition depends on chain configuration: it requires `allowTvmSelfdestructRestriction()` (and, to skip ABI-shape validation, `allowTvmOsaka()`) to be disabled — i.e., this is exploitable on chains/networks where these newer hard-fork toggles have not yet been activated (private/test networks, or a mainnet window before the corresponding proposal is turned on).

### Recommendation
Move the `MAX_SIZE` bound check on the signature-array length to run unconditionally before calling `extractBytesArray`/`extractSigArray`, independent of the `allowTvmSelfdestructRestriction()` flag, and add the same `if (offset > words.length - 1)` bounds guard used in `extractBytesArray`/`extractSigArray` to `extractBytes32Array`. Additionally, verify that `Program.callToPrecompiledAddress` wraps all precompiled-contract `execute()` invocations in a `catch (Throwable)`/`catch (OutOfMemoryError)` boundary so that any future unguarded precompile cannot crash the node process.

### Proof of Concept
1. Deploy a contract that issues a `CALL` to the `validatemultisign` precompile address with calldata encoding: `address` (word0), `permissionId` (word1), `data` offset/word (word2), and a signature-array offset (word3) that points to a length word set to a large value (e.g., `0x7FFFFFFF`).
2. On a chain configuration where `allowTvmSelfdestructRestriction` (and `allowTvmOsaka`) are disabled, invoke this contract via a normal triggersmartcontract transaction.
3. Observe `ValidateMultiSign.execute()` attempt `new byte[0x7FFFFFFF][]` at `extractBytesArray` (`PrecompiledContracts.java:404`), triggering an `OutOfMemoryError` outside any local `try/catch`, and monitor node behavior for crash/instability.
