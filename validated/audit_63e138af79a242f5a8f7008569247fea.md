### Title
Unprivileged attacker can fill a victim's per-account token list via dust `deposit(onBehalfOf)`/`transfer`, blocking all new deposits and borrows (DoS) - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to the Tumblr cookie-injection DoS — where an attacker forcibly writes attacker-chosen state into the victim's account context (`oa-consumer_key`/`oa_consumer_secret` cookies) to break account functionality until the victim manually cleans up — `Pool` keeps a per-account set of deposit/debt tokens capped at `MAX_TOKENS_PER_USER = 30`. Any EOA can add entries to a *victim's* set without the victim's consent, either by calling `DepositToken.deposit(amount_, onBehalfOf_ = victim)` with dust, or by `transfer()`ing dust deposit-token balances to the victim. Once the victim's combined `depositTokensOfAccount + debtTokensOfAccount` reaches 30, every subsequent mint/transfer-in/borrow for that account reverts with `UserReachedMaxTokens`, denying service until the victim manually transfers the dust positions away.

### Finding Description
`Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` enforce `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts once the account holds 30 distinct token entries [1](#0-0) [2](#0-1) . Entries are added by `DepositToken._mint` and `DepositToken._transfer` whenever the recipient's balance moves from 0 to >0 [3](#0-2) [4](#0-3) . Both reachable paths are permissionless with respect to the *recipient*: `deposit(amount_, onBehalfOf_)` mints to an arbitrary `onBehalfOf_` with no consent check [5](#0-4) , and `transfer(to_, amount_)` only checks the *sender's* unlocked balance via `_revertIfLocked(_msgSender, amount_)` [6](#0-5) . Since the pool-level deposit token list is itself capped at 30 [7](#0-6) , an attacker holding dust of each listed collateral can saturate a victim's slots entirely.

Concretely: attacker deposits/buys 1 wei of underlying for each of the pool's deposit tokens, then calls `deposit(1, victim)` (or `transfer(victim, 1)`) for each until `depositTokensOfAccount.length(victim) + debtTokensOfAccount.length(victim) == 30`. From then on, the victim's `deposit()` of any *new* collateral type reverts inside `_mint → addToDepositTokensOfAccount`, any incoming deposit-token transfer reverts, and `DebtToken` issuance of a synthetic the victim doesn't already hold reverts the same way.

### Impact Explanation
This is a victim-targeted denial of service matching the report's "cookies must be manually deleted to restore the account" shape: the victim's funds are not stolen, but they cannot onboard new collateral or new debt until they spend gas transferring out the injected dust positions. The critical case is liveness under duress — a victim whose position is approaching liquidation cannot deposit a *new* collateral type to restore health (they can only top up collateral types already in their set), and cannot mint a new synthetic type to repay/refinance. If all their existing slots are exhausted, they are exposed to liquidation loss they cannot prevent. Recovery requires the victim to discover and clear the dust positions, exactly paralleling "the victim needs to delete all cookies to restore the account."

### Likelihood Explanation
Fully unprivileged and reproducible: `deposit` is `whenNotPaused nonReentrant` with no restriction on `onBehalfOf_` [8](#0-7) , and `transfer` has no recipient-consent or recipient-cap check beyond the Pool revert itself [6](#0-5) . Cost is bounded: at most 30 dust deposits/transfers plus acquiring dust of each listed underlying. Limitations: the attacker can only fill slots with tokens that actually exist (≤30 deposit tokens), and the victim retains an escape hatch (transfer the dust out), so it is temporary rather than permanent freezing — consistent with a Medium-severity DoS rather than a critical loss.

### Recommendation
Make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` additions consent-based rather than forced: e.g., skip adding recipient entries on `transfer`/`deposit(onBehalfOf)` unless the recipient opted in, or drop the hard `MAX_TOKENS_PER_USER` revert in favor of lazily tracking positions. At minimum, do not revert the whole `_mint`/`_transfer` when the cap is hit — treat list bookkeeping as best-effort so balance transfers are never blocked by set membership.

### Proof of Concept
```solidity
// Fork test (Hardhat) against deployed Pool + DepositTokens
// Assumes pool lists N deposit tokens; attacker holds dust of each underlying.

async function run(victim: string) {
  const pool = await ethers.getContractAt("Pool", POOL);
  const n = (await pool.MAX_TOKENS_PER_USER()).toNumber();
  const tokens = await pool.getDepositTokens(); // up to 30

  for (let i = 0; i < Math.min(n, tokens.length); i++) {
    const dt = await ethers.getContractAt("DepositToken", tokens[i]);
    const underlying = await ethers.getContractAt("IERC20", await dt.underlying());
    // attacker acquires 1 wei of underlying (swap/dust), approves treasury pull
    await underlying.connect(attacker).approve(dt.address, 1);
    // forcibly adds tokens[i] to victim's depositTokensOfAccount
    await dt.connect(attacker).deposit(1, victim);
    // alternative: await dt.connect(attacker).transfer(victim, 1);
  }

  expect(await pool.getDepositTokensOfAccount(victim)).to.have.lengthOf(
    Math.min(n, tokens.length)
  );

  // victim can no longer deposit a collateral type they don't already hold,
  // nor receive deposit-token transfers, nor mint a new debt token:
  await expect(
    someOtherDepositToken.connect(victim).deposit(amount, victim)
  ).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

  // recovery: victim must manually transfer each dust position out
  // (the "delete all cookies" step) before functionality is restored.
}
```

Key mechanics verified in code: recipient-side list insertion on `_mint`/`_transfer` [9](#0-8) , the shared 30-token cap that reverts `UserReachedMaxTokens` [10](#0-9) [1](#0-0) , and consentless `onBehalfOf_` deposits [5](#0-4) .
