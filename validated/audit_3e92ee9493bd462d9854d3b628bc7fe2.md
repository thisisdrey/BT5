### Title
Unauthenticated POST to `/v3/blocks/upload/` triggers unconditional P2P relay via `set_relay_message`, bypassing the `broadcast`+auth gate - ([File: stackslib/src/net/api/postblock_v3.rs])

### Summary
`RPCPostBlockRequestHandler::try_parse_request` only requires authentication when `broadcast=1` is explicitly requested; an omitted auth header with no `broadcast` param passes with `authenticated=false`, `broadcast=false`. In `try_handle_request`, `node.set_relay_message(...)` is invoked solely based on `data_resp.accepted`, never checking `self.broadcast`, so the query-string/auth "broadcast" gate has no effect on whether the block is queued for P2P propagation.

### Finding Description
The claimed equality — "set of blocks reaching `set_relay_message` == blocks explicitly authorized via `broadcast=1`+secret" — is broken by inspection of the code:

- In `try_parse_request` (`stackslib/src/net/api/postblock_v3.rs:99-122`), the only enforcement point is: `if broadcast && !authenticated { return Err(401) }`. If the attacker sends no `Authorization` header and no `broadcast=1`, both `authenticated` and `broadcast` stay `false`, and the request proceeds; `self.broadcast = Some(false)` is stored [1](#0-0) .
- In `try_handle_request`, `Relayer::process_new_nakamoto_block_ext` is called with `self.broadcast.unwrap_or(false)` [2](#0-1) , and — critically — the relay-queuing decision at the end of the function checks only `data_resp.accepted`, not `self.broadcast` or authentication state: `if data_resp.accepted { node.set_relay_message(StacksMessageType::NakamotoBlocks(...)) }` [3](#0-2) .
- `node.take_relay_message()` in `ConversationHttp::handle_request` (`stackslib/src/net/rpc.rs:214-245`) returns this as `Option<StacksMessageType>` which callers forward to the P2P layer for network-wide broadcast (per the doc comment: "it's Some(...) if we need to forward a message to the peer network") [4](#0-3) .

So the "broadcast" flag as implemented in `postblock_v3.rs` gates nothing about whether the block is queued for relay — it only affects the internal `broadcast` boolean argument passed into `Relayer::process_new_nakamoto_block_ext` (in `stackslib/src/net/relay.rs`), whose exact internal effect could not be fully confirmed in this pass, but it is *not* consulted at the `set_relay_message` call site.

However, note that `process_new_nakamoto_block_ext` is the node's standard Nakamoto block-acceptance path, which performs full consensus validation (signer signatures, tenure/sortition checks, chain-extension rules) before returning `Accepted`. An attacker without the tenure's/signers' keys cannot cause an invalid or forged block to be "accepted" — only a legitimately-signed block (one that a legitimate miner/signer set already produced) can reach `data_resp.accepted == true`. This mirrors the equivalent epoch2x endpoint `RPCPostBlockRequestHandler` in `postblock.rs`, which has no auth/broadcast gate at all and always relays on acceptance [5](#0-4) , indicating "relay any block the node itself validates and accepts" is consistent, longstanding behavior across both block-upload endpoints.

### Impact Explanation
An unauthenticated remote party can POST any well-formed, cryptographically valid Nakamoto block (one they observed elsewhere, e.g., via legitimate gossip, or one produced by a colluding/legitimate signer set) to `/v3/blocks/upload/` with no `Authorization` header and no `broadcast=1`, and if the node's own consensus validation accepts it, the node will unconditionally queue it via `set_relay_message` and forward it to its P2P peers — exactly as if the caller had supplied `broadcast=1` and the correct secret. This defeats the intended authorization boundary between "just have the node validate/store this block" and "have the node act as an authorized relay/announcer for this block to the wider network," letting any anonymous caller turn a node into an unauthorized broadcast relay. It does not, however, allow propagation of a forged/invalid block, since `process_new_nakamoto_block_ext` performs full validation before acceptance.

### Likelihood Explanation
Trivial to trigger: the RPC port must be reachable (no special peer state, secret, or role needed), and the attacker only needs a syntactically valid, previously/independently-signed Nakamoto block that the node's chainstate would accept (e.g., a block already broadcast but not yet delivered to this specific node, or a block from a signer they have visibility into but no authority over). Repeatable per block. No secret or privileged role is required to exercise the code path itself, though the attacker cannot forge block content.

### Recommendation
Make the relay decision in `postblock_v3.rs` consult `self.broadcast` (and thus the authentication gate) explicitly, e.g.:
```rust
if data_resp.accepted && self.broadcast.unwrap_or(false) {
    node.set_relay_message(...);
}
```
so that `set_relay_message` is only invoked when the caller both authenticated and requested `broadcast=1`, matching the documented intent of the endpoint. If the intent is instead that any accepted, validly-signed block should always be relayed (consistent with `postblock.rs`), then the `auth`/`broadcast` mechanism should be documented as controlling only some other internal behavior (e.g., relay priority or obtain-method bookkeeping) rather than being described as an authorization gate on network propagation, to avoid confusion and inconsistent expectations.

### Proof of Concept
In `stackslib/src/net/api/tests/postblock_v3.rs`, extend the request-handling test to:
1. Set up a `TestPeer`/`StacksNodeState` with a sortition/chainstate such that a crafted, properly-signed `NakamotoBlock` will be `Accepted` by `Relayer::process_new_nakamoto_block_ext`.
2. Build the HTTP request via `StacksHttpRequest::new_post_block_v3` (no `broadcast=1`, no `Authorization` header) — as opposed to `new_post_block_v3_broadcast`.
3. Drive it through `RPCPostBlockRequestHandler::try_parse_request` then `try_handle_request`.
4. Assert `handler.broadcast == Some(false)` and that the response's `data_resp.accepted == true`.
5. Assert that `node.take_relay_message()` returns `Some(StacksMessageType::NakamotoBlocks(...))` despite `broadcast=false`/no auth header — proving relay occurs unconditionally on acceptance, independent of the broadcast/auth gate.
