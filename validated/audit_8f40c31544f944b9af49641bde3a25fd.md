### Title
`deploy_deterministic_account` bypasses the per-receipt storage-proof size cap because it isn't covered by `RecordedStorageCounter` or the (still-nightly) `EnforceStorageProofLimitForAllActions` check - (`runtime/runtime/src/deterministic_account_id.rs`)

### Summary
`deploy_deterministic_account` writes every `(key, value)` pair from a `DeterministicStateInitAction`'s `state_init.data()` directly into the trie via `state_update.set(trie_key, value.clone())` without any bound on the storage proof it generates. The only mechanism that enforces `per_receipt_storage_proof_size_limit` on non-`FunctionCall` actions, `ProtocolFeature::EnforceStorageProofLimitForAllActions`, is gated behind a check in `runtime/runtime/src/lib.rs` that is a no-op unless that feature is enabled, and it is documented as still nightly (not yet the stable/active protocol feature in this codebase, whose highest stable storage-proof feature is `EnforcePerReceiptStorageProofLimit`).

### Finding Description
`action_deterministic_state_init` -> `deploy_deterministic_account` iterates `state_init.data()` and calls `state_update.set(trie_key, value.clone())` for each entry [1](#0-0) , with cost accounted only via the fixed `action_deterministic_state_init_per_byte`-style fee, not the WASM storage-write gas schedule that drives `RecordedStorageCounter`.

`RecordedStorageCounter` (`runtime/near-vm-runner/src/logic/recorded_storage_counter.rs`) is invoked from inside the VM logic and only bounds trie operations issued by a `FunctionCall`'s host calls; it has no visibility into native runtime actions such as `DeterministicStateInitAction`.

The generic, action-kind-agnostic enforcement lives in the receipt-execution loop in `runtime/runtime/src/lib.rs`: after each action, it computes `recorded_by_receipt = trie.recorded_storage_size_upper_bound() - size_before` and compares it against `per_receipt_storage_proof_size_limit`, but only when `storage_proof_limit_for_all_actions` is `Some(_)`, which itself requires `ProtocolFeature::EnforceStorageProofLimitForAllActions.enabled(...)` [2](#0-1) . The feature comment explicitly documents the exact gap being probed: "The `RecordedStorageCounter` only runs inside the VM, so it bounds `FunctionCall` actions alone; other actions in the same receipt could record proof past the limit" [3](#0-2) . Per the codebase's own protocol-model documentation, at this baseline's active/stable protocol version the highest enabled storage-proof feature is `EnforcePerReceiptStorageProofLimit`, and `EnforceStorageProofLimitForAllActions` is not yet the live/stable feature [4](#0-3) . Consequently, while that feature is inactive, the closure in `lib.rs` returns `None` and the per-action `ReceiptStorageProofSizeExceeded` check for non-`FunctionCall` actions never fires.

An attacker (unprivileged, ordinary account) can submit a transaction/meta-transaction containing a `DeterministicStateInitAction` whose `state_init.data()` contains many small, sparsely-distributed key/value entries. Individually each key/value passes any per-entry size limits, but collectively the writes touch many distinct trie paths, generating branch/extension node proof material well beyond the raw byte payload — the same amplification effect demonstrated for reads/writes in `test_add_keys_after_large_read_exceed_receipt_storage_proof_limit` [5](#0-4) . Because this write path is not covered by `RecordedStorageCounter` (not a `FunctionCall`) and the generic per-action guard is inactive for the current protocol version, this receipt's recorded proof can exceed `per_receipt_storage_proof_size_limit`/`main_storage_proof_size_soft_limit` with no rejection.

### Impact Explanation
Uncapped storage-proof accumulation for a single receipt undermines the state-witness size budget that stateless validation depends on (documented target ~21MiB total, with `per_receipt_storage_proof_size_limit` intended as a hard 4MB-per-receipt backstop) [6](#0-5) . A chunk producer that includes such a receipt can produce a witness that overshoots the intended limits; if this pushes the witness past the compile-time hard caps (`MAX_UNCOMPRESSED_STATE_WITNESS_SIZE`/`MAX_COMPRESSED_STATE_WITNESS_SIZE`) or otherwise causes chunk-application/validation costs to spike disproportionately to the gas actually charged (since the write is billed at a fixed per-byte fee unrelated to proof-generation cost), this is a shard-level availability/DoS risk: chunk producers/validators can be stalled or forced to reject chunks, which maps to the "shard-halting" bounty category rather than direct fund theft.

### Likelihood Explanation
Preconditions are minimal: any funded account can submit a `DeterministicStateInitAction` to derive/deploy a NEP-616 deterministic account with an attacker-chosen `state_init.data()` payload; no special privileges, validator access, or leaked keys are required. The cost to the attacker is only the fixed `action_deterministic_state_init_per_byte` gas fee for the (still transaction/receipt-size-bounded, e.g. `max_receipt_size` ~4MiB) payload, not the amplified trie-proof cost, making the attack cheap and repeatable across chunks/shards as long as the vulnerable protocol-version window (feature `EnforceStorageProofLimitForAllActions` not yet active) is in effect.

### Recommendation
Extend `EnforceStorageProofLimitForAllActions`-style enforcement (or equivalently, activate/backport it) so the per-action storage-proof check in `runtime/runtime/src/lib.rs` also applies unconditionally to `DeterministicStateInitAction`/`deploy_deterministic_account`, independent of the feature-gate timing relative to NEP-616 activation. Concretely, either (a) ensure `DeterministicStateInitAction` cannot activate on a protocol version where `EnforceStorageProofLimitForAllActions` is disabled, or (b) add an explicit, always-on check inside `deploy_deterministic_account`/`action_deterministic_state_init` that aborts with `ActionErrorKind::ReceiptStorageProofSizeExceeded` once the accumulated `state_update.trie.recorded_storage_size_upper_bound()` for the receipt exceeds `per_receipt_storage_proof_size_limit`, mirroring the guard already present for `FunctionCall` receipts.

### Proof of Concept
Add an apply-path integration test in `runtime/runtime/src/tests/apply.rs` (or `test-loop-tests/src/tests/deterministic_account_id.rs`) modeled on `test_per_receipt_storage_proof_size_limit`/`test_add_keys_after_large_read_exceed_receipt_storage_proof_limit`:
1. Set up an account and construct a `DeterministicStateInitAction` whose `state_init.data()` contains a large number (e.g. thousands) of small key/value pairs chosen to maximize distinct trie-node touches (e.g. keys with divergent high-order nibbles) while keeping total payload under `max_receipt_size`.
2. Apply the receipt at the current `PROTOCOL_VERSION` and assert on `state_update.trie.recorded_storage_size_upper_bound()` after execution.
3. Assert the receipt fails with `ActionErrorKind::ReceiptStorageProofSizeExceeded { limit: per_receipt_storage_proof_size_limit }` (expected/fixed behavior) rather than succeeding with a recorded proof size greater than `per_receipt_storage_proof_size_limit` (current/vulnerable behavior), confirming today's build allows unbounded proof accumulation on this path while `FunctionCall`-based writes of equivalent trie shape are already rejected by `RecordedStorageCounter`.

**File:** docs/misc/state_witness_size_limits.md (L27-31)
```markdown
* `per_receipt_storage_proof_size_limit - 4 MB`
  * Executing a receipt generates storage proof. A single receipt is allowed to generate at most 4MB of storage proof. This is a hard limit, receipts which generate more than that will fail.
* `main_storage_proof_size_soft_limit - 4 MB`
  * This is a limit on the total size of storage proof generated by receipts in one chunk. Once receipts generate more storage proof than this limit, the chunk producer stops processing receipts and moves the rest to the delayed queue.
  * It's a soft limit, which means that the total size of storage proof could reach 8 MB (3.99MB + one receipt which generates 4MB of storage proof)
```
