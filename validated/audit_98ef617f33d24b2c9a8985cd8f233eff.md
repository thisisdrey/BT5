Based on my investigation, I found a viable analog in the Zest v2 vault contracts. The Hyperdrive bug's core pattern — a state-accrual step that performs an unchecked scaling division whose denominator can be driven toward the numerator (or below it) by ordinary user actions, causing a permanent revert of a core accounting entry point — maps to `calc-treasury-lp-preview` in Zest's vault contracts.

### Title
Treasury-LP preview division can underflow/permanently brick `accrue`, `system-borrow`, `system-repay`, `redeem` and all downstream market operations - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and identical logic in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`)

### Summary
`calc-treasury-lp-preview` computes the treasury's LP-fee share using `(mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc))` [1](#0-0) . Clarity's `-` operator on `uint` aborts the transaction if the subtraction underflows. Because `ta-preview` (`total-assets-preview`) and `reserve-inc` (this period's reserve-fee cut of newly accrued interest) are computed via independent code paths that are not proven to always satisfy `ta-preview >= reserve-inc`, a state where `available assets ≈ 0` (vault fully utilized/borrowed out) combined with freshly-reset accrued interest can make `reserve-inc` equal to or exceed `ta-preview`, causing the subtraction — and therefore every call to `accrue()` — to revert permanently for that vault.

### Finding Description
`total-assets-preview` is `current-assets + max(debt-preview - total-borrowed, 0)` [2](#0-1) , i.e. it is the sum of idle underlying sitting in the vault plus the *cumulative* uncollected interest since the last time `total-borrowed`/`assets` were reconciled. `reserve-inc` is only this *single accrual step's* portion of newly accrued interest that goes to the treasury: `mul-div-down debt-delta fee-reserve BPS` [3](#0-2) .

`calc-treasury-lp-preview` then does:
```
(if (> reserve-inc u0)
    (mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc))
    u0)
``` [4](#0-3) 

This is invoked from `accrue()`, which is itself invoked at the top of every state-mutating vault entry point: `system-borrow`, `system-repay`, `socialize-debt` (via caller path), `deposit`/`redeem`, etc. [5](#0-4)  — this mirrors exactly how Hyperdrive's `applyCheckpoint` is invoked at the top of every trade, making a revert here system-wide and not isolated to one caller.

The vulnerable window is: when `current-assets` (idle liquidity) is `0` because the vault is fully borrowed out, and the accrued-interest carry-over (`debt-preview - total-borrowed`) from prior periods has just been "reset" to near-zero by a `system-repay` that fully repays outstanding debt (which zeroes `principal-scaled` and brings `total-borrowed` back in line with `debt`), followed immediately by a fresh `system-borrow` that re-inflates `principal-scaled`/`total-borrowed` to the same magnitude. On the very next `accrue()` (even a 1-second time delta), `debt-delta` (interest accrued since re-borrow) can make up effectively all of `ta-preview`, since `current-assets` is `0` and there is no other historical unclaimed-interest buffer left. If `fee-reserve` (the reserve/treasury cut, in BPS) is high enough, `reserve-inc` (derived from `debt-delta`) can equal or exceed `ta-preview`, since both are computed via the same rounding-down `mul-div-down` chain but through slightly different intermediate roundings (`debt-preview` via `next-index`/`calc-index-next` vs. `debt-delta`/`fee-reserve` multiplication) — this is analogous to the Hyperdrive case where the ratio factor blows up because the "denominator" side of the computation was driven to near-zero by ordinary trading (open-short) activity, and a subsequent state update (mature-short) tries to scale by that ratio and reverts on the safe-cast.

This is unprivileged and reachable: any borrower can trigger full repay + immediate re-borrow (this is normal `system-repay`/`system-borrow` usage reachable from `market.clar`'s `repay`/`borrow` entry points, which any principal can call for their own position), and the subsequent `accrue()` call (triggered by literally any user action touching that vault, including their own next transaction) permanently reverts once the underflow condition is hit, since the state that produced it (fee-reserve config, idle-assets-at-zero) does not self-correct.

### Impact Explanation
Once `accrue()` reverts unconditionally for a vault, every function that begins with `(try! (accrue))` — `system-borrow`, `system-repay`, and consequently `market.clar`'s `borrow`, `repay`, `liquidate` flows that route through this vault for that asset — become permanently unusable. Lenders' supplied assets and borrowers' collateral/repay capability for that asset become frozen with no operational path to unwind, matching the in-scope impact class of **temporary/permanent freezing of funds** (assets are locked and cannot be withdrawn, borrowed, or repaid for that vault going forward).

### Likelihood Explanation
The precise numerical alignment needed to make `reserve-inc >= ta-preview` requires a specific but not impossible combination: idle assets at 0 (achievable via a max-utilization borrow), and the fee-reserve/rounding arithmetic aligning such that the treasury-fee cut of this period's interest accrual meets or exceeds the total previewed assets base at that instant. This requires careful sequencing (repay-then-reborrow to reset the interest carryover, then trigger accrual) but does not require any privileged role, oracle manipulation, or DAO action — it is achievable purely through ordinary borrow/repay calls by a single unprivileged account, similar to how the Hyperdrive PoC only required opening and maturing shorts.

### Recommendation
Clamp the subtraction defensively, e.g. `(if (> ta-preview reserve-inc) (mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc)) u0)`, mirroring the `(if (> a b) (- a b) u0)` defensive pattern already used elsewhere in the same file (e.g., `total-assets-preview`'s `interest` computation and `socialize-debt`'s reductions) [6](#0-5) . More fundamentally, treasury-LP minting math should not depend on scaling by a denominator that can be driven to zero or below the numerator by ordinary utilization/repay/borrow cycles.

### Proof of Concept
I could not construct or run an on-chain/Clarinet PoC within this session to empirically confirm the exact numeric conditions (whether Clarity's rounding in `next-index`/`calc-index-next` vs. `mul-div-down debt-delta fee-reserve BPS` can actually produce `reserve-inc >= ta-preview` in practice, and under what `fee-reserve` values). This should be verified with a Clarinet unit test that: (1) deploys a vault with a high `fee-reserve` BPS, (2) drives `current-assets` to `0` via `system-borrow` up to `available-assets`, (3) fully repays via `system-repay` to reset `principal-scaled`≈`total-borrowed`, (4) immediately re-borrows the same amount, (5) advances time by a minimal delta, and (6) calls any function that triggers `accrue()` to observe whether the subtraction underflows and aborts.
