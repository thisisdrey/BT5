### Title
Attacker can fill a victim's `MAX_TOKENS_PER_USER` slots via dust DepositToken transfers, blocking new deposits and debt issuance - (File: contracts/Pool.sol)

### Summary
`Pool` tracks each account's deposit and debt tokens in `MappedEnumerableSet` lists capped by `MAX_TOKENS_PER_USER = 30` (counted jointly). Whenever a `DepositToken` balance goes from 0 to >0 — including via an ordinary permissionless `transfer`/`transferFrom` — `DepositToken` calls `Pool.addToDepositTokensOfAccount`, which reverts with `UserReachedMaxTokens` once the combined count reaches 30. An unprivileged attacker can dust-transfer tiny amounts of many distinct deposit tokens to a victim, filling all 30 slots and causing every subsequent deposit of a new collateral type (and any new debt issuance, which calls `addToDebtTokensOfAccount` under the same cap) to revert.

### Finding Description
- `Pool.sol:79` sets `MAX_TOKENS_PER_USER = 30`, shared between `depositTokensOfAccount` and `debtTokensOfAccount` (`onlyIfAdditionWillNotReachMaxTokens` checks the sum).
- `Pool.addToDepositTokensOfAccount` (`Pool.sol:216`) and `Pool.addToDebtTokensOfAccount` (`Pool.sol:204`) are invoked by the token contracts whenever an account balance transitions from zero; they revert once the cap is reached.
- `DepositToken` transfers are permissionless ERC20-like transfers callable by any EOA via public entry points. The attacker mints/deposits 1 wei of underlying into each deposit token (or receives them via `Pool.swap`), then transfers 1 wei of each token to the victim. Each dust transfer permanently occupies one slot in `depositTokensOfAccount[victim]` until the victim transfers it back out.
- Once saturated, `deposit()`/`mint()` of any new collateral for the victim reverts inside the token hook, and `DebtToken.issue`/`mint` reverts on `addToDebtTokensOfAccount` for any new synthetic asset.
- The victim can remove slots only by transferring the dust tokens away ( costs gas per token), so this is a temporary freeze; critically, if the victim is near liquidation and needs a new collateral type to restore health, the forced revert makes liquidation inevitable — converting the freeze into direct loss of collateral to a liquidator.

### Impact Explanation
Temporary freezing of user funds and, for underwater/near-threshold positions, forced liquidation: the victim cannot deposit a new collateral type or open debt in a new synthetic while the 30 slots are occupied. Invariant broken: liveness/liquidation bounds — a position that could have been saved by topping up collateral is liquidatable.

### Likelihood Explanation
Fully unprivileged: needs only public `DepositToken.transfer` calls with dust amounts; the cost is bounded by the number of registered deposit/debt tokens in the pool (cap 30). No governor, keeper, oracle, or bridge trust assumptions required. Effectiveness depends on the pool having enough distinct registered deposit/debt tokens to fill the cap; the victim can recover by spending gas to shed dust tokens, so impact is temporary unless it coincides with a liquidation window.

### Recommendation
Count only "meaningful" balances (e.g., only add to the per-account list on deposits/mints, not inbound transfers), or raise/decouple the cap, or let accounts opt out of auto-adding on inbound transfers so dust cannot consume slots.

### Proof of Concept
Hardhat/fork sketch:
1. Fork a chain with a deployed `Pool` (e.g., optimism deployment) having N deposit tokens `dT[i]`.
2. Attacker calls `dT[i].deposit(1)` (or `deposit` then `transfer`) to obtain dust, then `dT[i].transfer(victim, 1)` for each `i` until `getDepositTokensOfAccount(victim).length + getDebtTokensOfAccount(victim).length == 30`.
3. `dT_new.deposit`/`mint` to victim reverts with `UserReachedMaxTokens`; `debtToken.issue(victim, x)` for a new synthetic reverts.
4. Drop collateral price via oracle update (or use an existing unhealthy-approaching position) and show `Pool.liquidate` succeeds while the victim's recapitalizing `deposit` still reverts.
