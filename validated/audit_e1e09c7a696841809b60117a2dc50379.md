### Title
Liquidity index accrual can be permanently starved by frequent borrow/repay while the borrow index keeps ticking, freezing supplier yield - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
The vault's `accrue` function only resets `last-update` when either the borrow index (`index`) or the liquidity index (`lindex`) actually changes value [1](#0-0) . Because the two indexes are driven by different rates (`interest-rate` for the borrow index vs. a discounted `calc-liquidity-rate` for the liquidity index) but share the *same* `last-update` timestamp, a borrow-index change alone resets the elapsed-time base used to compute the liquidity index's rounding threshold. This reproduces the reported ERC20Rewards rounding class: `rewardsPerToken_.accumulated` (here, `lindex`) can stay constant while the timer governing it (`last-update`) keeps being reset, permanently starving depositor yield.

### Finding Description
`next-index` and `next-liquidity-index` both compute a multiplier via `calc-multiplier-delta`, which uses `mul-div-down` and therefore rounds to zero whenever `rate * time-delta * INDEX-PRECISION < SECONDS-PER-YEAR-BPS` [2](#0-1) . When the rounded multiplier equals `INDEX-PRECISION`, `calc-index-next` returns the index unchanged [3](#0-2) .

The liquidity rate is always `<=` the borrow rate, since `calc-liquidity-rate` scales the borrow rate down by both utilization and the reserve factor [4](#0-3) . This means the liquidity index's zero-rounding threshold in elapsed time is met far more easily (needs a much larger `time-delta`) than the borrow index's threshold.

`accrue` computes both `next` (borrow index) and `nliq` (liquidity index) using the *same* `time-delta = stacks-block-time - last-update`, then commits `last-update` to `stacks-block-time` if **either** index changed:
```
(if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
    (var-set last-update stacks-block-time)
    false)
``` [1](#0-0) 

If a user (via `system-borrow`/`system-repay`, which themselves call `accrue` first [5](#0-4) ) triggers `accrue` at intervals that are large enough for the borrow-index rounding threshold to be crossed but small enough to remain under the (much larger) liquidity-index threshold, then on every call `idx != next` while `lidx == nliq`. The `last-update` timer resets each time purely because of the borrow-side change, discarding the elapsed time that would eventually have accumulated toward the liquidity index's threshold. `lindex` (and thus `total-assets`/`total-assets-preview`, which drive redemption value for depositors) never advances, even though `principal-scaled`/`total-debt` keeps growing via the borrow index [6](#0-5) .

### Impact Explanation
Interest actually accruing on the debt side (paid for by borrowers) is never reflected in the liquidity index that depositors redeem against, so the yield owed to suppliers is effectively frozen/lost while debt keeps compounding. This is theft/permanent freezing of unclaimed yield owed to liquidity providers, matching the in-scope High impact category (theft or permanent/temporary freezing of unclaimed yield).

### Likelihood Explanation
This requires no privileged access and no DAO/oracle compromise — any address able to reach `system-borrow`/`system-repay` through the market's ordinary borrow/repay entry points can trigger `accrue` at will by issuing small, frequent borrow/repay actions. Because normal market usage already calls `accrue` on every borrow/repay, this condition can also arise unintentionally under sustained transaction activity at low utilization/low reserve-factor configurations, similar to how the original ERC20Rewards report noted that ordinary `transfer` calls could trigger the issue without a deliberate attacker.

### Recommendation
Track elapsed time (or an equivalent rounding remainder) independently for the borrow index and the liquidity index, or only advance `last-update` after both `next-index` and `next-liquidity-index` have been evaluated and only when the accumulated time credited to *each* respective calculation has actually been consumed (e.g., keep separate `last-update-borrow` / `last-update-liquidity` timestamps, or carry forward unconsumed time instead of resetting to `stacks-block-time`).

### Proof of Concept
1. Configure a vault (e.g. `v0-vault-usdc.clar`) with a reserve factor and utilization such that `liquidity-rate << interest-rate` (normal/expected configuration).
2. Repeatedly call the market's borrow/repay flow (which internally calls the vault's `system-borrow`/`system-repay`, each invoking `accrue` first) at time intervals `Δt` chosen so that:
   - `interest-rate * Δt * INDEX-PRECISION ≥ SECONDS-PER-YEAR-BPS` (borrow index moves), but
   - `liquidity-rate * Δt * INDEX-PRECISION < SECONDS-PER-YEAR-BPS` (liquidity index rounds to no change).
3. Observe that on every call `idx != next`, so `last-update` is reset to `stacks-block-time` each time, while `lindex` never changes across the whole sequence — depositor-redeemable assets (`total-assets`, driven off `lindex`) never grow despite debt (`total-debt`, driven off `index`) increasing continuously.

This should be verified directly if further confirmation is needed.*
