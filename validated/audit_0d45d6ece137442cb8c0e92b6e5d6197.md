### Title
Partial state mutation in `MarketSellAssetActuator.execute` before an unvalidated matching-limit check can revert the transaction, wasting resources and leaving order-book state inconsistent - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator` mirrors the Vault/AlchemistV2 bug pattern: an amount-dependent limit (`MAX_MATCH_NUM`) is checked deep inside a helper (`matchOrder`) instead of being validated up-front in `validate()`, after several other state mutations (fee deduction, balance/asset transfer, order creation) have already been applied in the same `execute()` call.

### Finding Description
`validate()` only checks `MAX_ACTIVE_ORDER_NUM` and token/balance sufficiency; it never checks how many maker orders a taker order could match against (`MAX_MATCH_NUM`). [1](#0-0) 

In `execute()`, the actuator: deducts the fee, transfers the sell balance/asset out of the account, creates and persists the order via `orderStore.put(...)`/`marketAccountStore.put(...)`, and only then calls `matchOrder`, which can throw `ContractValidateException("Too many matches...")` once `matchOrderCount` exceeds `MAX_MATCH_NUM`. [2](#0-1) [3](#0-2) 

This is functionally identical to the reported bug class: a size/limit check that depends on the actual computed workload (matches needed) is performed only deep inside execution, after the balance has already been debited and store writes (`orderStore.put`, `marketAccountStore.put`) issued inside `createAndSaveOrder`, instead of being predicted/validated before any state change is made. [4](#0-3) 

The thrown `ContractValidateException` is caught in `execute()`'s catch block and rewrapped into a `ContractExeException`. [5](#0-4) 

### Impact Explanation
I was unable to fully verify, within the remaining tool budget, whether `TransactionTrace`/`Manager` wraps every actuator's `execute()` call in a database session that is fully reverted (rolled back) when `ContractExeException` propagates. If such a snapshot/rollback exists (as it does for `SnapshotManager.Session.revoke()` seen for VM execution paths), the impact is limited to a failed transaction (fee/bandwidth loss for the sender) with no permanent freezing of funds - i.e., low/no impact and out of scope per the rules given. If no such per-transaction session rollback wraps native (non-VM) actuator execution and any of the store writes performed before the exception (`orderStore.put`, `marketAccountStore.put`, or the account balance already mutated in local `AccountCapsule` object which is only persisted via `accountStore.put()` at the end of `execute()` and thus not actually written on early exception) are durably committed, this could result in permanently lost sell-side assets/TRX without a corresponding order or match, i.e. an unbacked-balance/fund-loss condition.

Because I could not confirm the actual rollback semantics of native actuator execution in this codebase within the current session, I cannot assert with confidence that this reaches the required "concrete unauthorized account operation, theft or permanent freezing of funds" bar. This is a genuine architectural analog (limit check performed after state-changing side effects, deep in execution, instead of during validation) but the actual on-chain impact depends on transaction-level atomicity guarantees that I was not able to verify with the tools available in this session.

### Likelihood Explanation
Reachable by any unprivileged account broadcasting a single `MarketSellAssetContract` transaction with parameters engineered to match against more than `MAX_MATCH_NUM` (20) existing maker orders at the best price level — no special privileges required, as demonstrated by the existing test `exceedMaxMatchNumLimit`. [6](#0-5) 

### Recommendation
Move the match-count-limit prediction into `validate()` (e.g., by scanning `pairPriceToOrderStore`/`pairToPriceStore` and estimating whether more than `MAX_MATCH_NUM` orders would need to be consumed) before any balance transfer or order persistence occurs in `execute()`, and confirm/enforce that a failed `execute()` call for this actuator is always executed within a fully revocable snapshot so no partial state (fee burn, asset transfer, order-book write) survives the failure.

### Proof of Concept
Not independently reproduced; relies on the existing test `MarketSellAssetActuatorTest.exceedMaxMatchNumLimit`, which sets up more than `MAX_MATCH_NUM` maker orders at the best price and shows `execute()` throwing `ContractExeException("Too many matches...")` only after `transferBalanceOrToken` and `createAndSaveOrder` have already mutated `accountCapsule` and the order stores. [7](#0-6)

  private MarketOrderCapsule createAndSaveOrder(AccountCapsule accountCapsule,
      MarketSellAssetContract contract) {
    MarketAccountOrderCapsule marketAccountOrderCapsule = marketAccountStore
        .getUnchecked(contract.getOwnerAddress().toByteArray());
    if (marketAccountOrderCapsule == null) {
      marketAccountOrderCapsule = new MarketAccountOrderCapsule(contract.getOwnerAddress());
    }

    // note: here use total_count
    byte[] orderId = MarketUtils
        .calculateOrderId(contract.getOwnerAddress(), sellTokenID, buyTokenID,
            marketAccountOrderCapsule.getTotalCount());
    MarketOrderCapsule orderCapsule = new MarketOrderCapsule(orderId, contract);

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    orderCapsule.setCreateTime(now);

    marketAccountOrderCapsule.addOrders(orderCapsule.getID());
    marketAccountOrderCapsule.setCount(marketAccountOrderCapsule.getCount() + 1);
    marketAccountOrderCapsule.setTotalCount(marketAccountOrderCapsule.getTotalCount() + 1);
    marketAccountStore.put(accountCapsule.createDbKey(), marketAccountOrderCapsule);
    orderStore.put(orderId, orderCapsule);

    return orderCapsule;
  }

  @Test
  public void exceedMaxMatchNumLimit() throws Exception {

    InitAsset();

    int start = 10;
    int limit = MarketSellAssetActuator.getMAX_MATCH_NUM();
    int step = 1;
    int end = start + step * limit;

    //(sell id_1  and buy id_2)
    String sellTokenId = TOKEN_ID_ONE;
    String buyTokenId = TOKEN_ID_TWO;
    long buyTokenQuant = 400L;
    long sellTokenQuant = buyTokenQuant * (end / start + 1);

    byte[] ownerAddress = ByteArray.fromHexString(OWNER_ADDRESS_FIRST);
    AccountCapsule accountCapsule = dbManager.getAccountStore().get(ownerAddress);
    accountCapsule.addAssetAmountV2(sellTokenId.getBytes(), sellTokenQuant,
        dbManager.getDynamicPropertiesStore(), dbManager.getAssetIssueStore());
    dbManager.getAccountStore().put(ownerAddress, accountCapsule);
    Assert.assertEquals(sellTokenQuant,
            (long) accountCapsule.getAssetV2MapForTest().get(sellTokenId));

    // Initialize the order book

    // at least limit+1 times
    for (int i = start; i <= end; i += step) {
      addOrder(buyTokenId, (long) start, sellTokenId, i, OWNER_ADDRESS_SECOND);
    }

    // this order(taker) need to match 21 times
    MarketSellAssetActuator actuator = new MarketSellAssetActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
        OWNER_ADDRESS_FIRST, sellTokenId, sellTokenQuant, buyTokenId, buyTokenQuant));

    String errorMessage =
        "Too many matches. MAX_MATCH_NUM = " + MarketSellAssetActuator.getMAX_MATCH_NUM();
    try {
      TransactionResultCapsule ret = new TransactionResultCapsule();
      actuator.validate();
      actuator.execute(ret);
      fail(errorMessage);
    } catch (ContractExeException e) {
      Assert.assertEquals(errorMessage, e.getMessage());
    } catch (Exception e) {
      Assert.assertTrue(false);
    }
  }
