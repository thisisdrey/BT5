### Title
Burned synthetic tokens cannot be recovered when the destination-side mint in `ProxyOFT._creditTo` fails deterministically — no cancel/refund path exists - ([File: contracts/ProxyOFT.sol](contracts/ProxyOFT.sol))

### Summary
Metronome's `ProxyOFT` burns the user's `SyntheticToken` supply on the source chain in `_debitFrom` and relies entirely on the destination chain's `_creditTo` → `syntheticToken.mint` succeeding. The LayerZero nonblocking wrapper stores a failed message for `retryMessage`, but there is no API to cancel an in-flight message and refund/re-mint the burned tokens on the source chain. If the destination mint reverts deterministically (e.g., bridging pause flag, mint disabled, supply cap), the stored message can never be retried successfully and the user's tokens are permanently frozen — analogous to the missing `cancelL1toL2Message` in the Kakarot finding.

### Finding Description
`ProxyOFT.sendFrom` → `_send` → `_debitFrom` calls `syntheticToken.burn(from_, amount_)` before dispatching the LayerZero message [1](#0-0) . On the destination, `NonblockingLzAppUpgradeable._blockingLzReceive` try/catches the receive and stores `failedMessages[srcChainId][srcAddress][nonce]` on failure [2](#0-1) . Recovery relies on permissionless `retryMessage`, which re-executes `_nonblockingLzReceive` and reverts if the inner call reverts [3](#0-2) . On the destination ProxyOFT, `_creditTo` unconditionally calls `syntheticToken.mint(toAddress_, amount_)` [4](#0-3) . `SyntheticToken.mint` is gated by pause/cap checks (per `SyntheticToken.sol` and `PoolRegistry.isBridgingActive`), so if the destination synthetic token is paused or its bridged-in cap is exhausted, `mint` reverts deterministically. Every `retryMessage` reverts, `failedMessages` is never cleared, and there is no `cancelMessage`/refund entry point anywhere in `ProxyOFT` — the source-chain tokens stay burned forever. Note `sendAndCall` is disabled via `SendAndCallNotAllowed`, so the `failedOFTReceivedMessages` path in `_safeCallOnOFTReceived` is unreachable; the exposure is purely the PT_SEND mint path [5](#0-4) .

### Impact Explanation
Permanent freezing of user funds: the user's tokens are burned on the source chain and can never be minted on the destination chain, breaking bridge conservation. Unlike the composable path where tokens are credited before the failing receiver call [6](#0-5) , a failing `_creditTo` mint leaves the user with nothing on either chain.

### Likelihood Explanation
Triggering requires the destination `SyntheticToken.mint` to revert — e.g., bridging paused or a bridged-in cap reached at delivery time. These are normal operational states (bridging can be toggled via `isBridgingActive`), and a message sent just before a pause lands in exactly this state. Any unprivileged user bridging hits this; no attacker action is required to cause the lock, and the user has no self-service recovery. Caveat: a governance unpause or cap increase would eventually let `retryMessage` succeed, so "permanent" depends on the deterministic-failure window — but for a permanently capped/paused token or a deprecated route, the loss is unrecoverable by design since no cancel API exists.

### Recommendation
Add a cancellation/recovery path: e.g., a `cancelMessage(srcChainId, srcAddress, nonce, payload)`-style function that, after a timeout, allows the original sender to reclaim funds (re-mint on the source chain via a trusted cross-chain refund message, or a governor-attested refund). Alternatively, catch mint failures inside `_creditTo` and credit a withdrawable balance on the destination instead of failing the whole message.

### Proof of Concept
Foundry fork outline (mainnet fork for source `ProxyOFT`/`SyntheticToken` + simulated destination):

1. Deploy/fork `ProxyOFT` + `SyntheticToken` on chain A and chain B with a mock LZ endpoint that delivers payloads synchronously, and set trusted remotes.
2. User calls `proxyOFTA.sendFrom(user, chainB, user, amount)` — tokens are burned on A.
3. On B, pause bridging / set the synthetic token bridged-in cap below `amount` so `syntheticToken.mint` reverts inside `_creditTo`.
4. Deliver the LZ packet: `_blockingLzReceive` catches the revert and stores `failedMessages[chainA][srcAddr][nonce]`.
5. Call `proxyOFTB.retryMessage(chainA, srcAddr, nonce, payload)` — it reverts every time because `mint` still reverts.
6. Assert: `syntheticTokenA.balanceOf(user) == 0`, `syntheticTokenB.balanceOf(user) == 0`, and no function on either contract allows the user to reclaim. Funds are locked indefinitely.

```text
    function retryMessage(uint16 _srcChainId, bytes calldata _srcAddress, uint64 _nonce, bytes calldata _payload) public payable virtual {
        // assert there is message to retry
        bytes32 payloadHash = failedMessages[_srcChainId][_srcAddress][_nonce];
        require(payloadHash != bytes32(0), "NonblockingLzApp: no stored message");
        require(keccak256(_payload) == payloadHash, "NonblockingLzApp: invalid payload");
        // clear the stored message
        failedMessages[_srcChainId][_srcAddress][_nonce] = bytes32(0);
        // execute the message. revert if it fails again
        _nonblockingLzReceive(_srcChainId, _srcAddress, _nonce, _payload);
        emit RetryMessageSuccess(_srcChainId, _srcAddress, _nonce, payloadHash);
```
