### Title
Unauthenticated `postblock_v3` upload triggers network-wide relay regardless of `broadcast` flag - ([File: stackslib/src/net/api/postblock_v3.rs])

### Summary
`try_handle_request` gates the `node.set_relay_message(...)` call solely on `data_resp.accepted`, not on `self.broadcast`. Since a request with `broadcast` unset (or `false`) requires no authentication at all, an unauthenticated attacker whose block passes local chain-state validation can still have their block queued for network-wide relay.

### Finding Description
In `try_parse_request` <cite repo="Kohvert/stacks-core--025" path="stackslib/src/net/api/postblock_v3.rs" start="99,120,133,134" end="122" />, authentication is only enforced `if broadcast && !authenticated`. When the query has no `broadcast=1` (or it is absent), `broadcast` stays `false` and the handler proceeds with `authenticated = false`. `self.broadcast` is then set to `Some(false)` unconditionally.

In `try_handle_request`, `self.broadcast.unwrap_or(false)` is passed only as the `force_broadcast` parameter to `Relayer::process_new_nakamoto_block_ext` [1](#0-0) . That parameter, per `process_new_nakamoto_block_ext`'s doc and body, only affects whether an *already-stored* block is reported as `Accepted` again (to force re-broadcast of a duplicate) [2](#0-1) . It does not affect the relay decision downstream in the HTTP handler.

The actual relay trigger is:
```
if data_resp.accepted {
    node.set_relay_message(StacksMessageType::NakamotoBlocks(NakamotoBlocksData { blocks: vec![block] }));
}
``` [3](#0-2) 

This check depends only on whether the block was newly and validly accepted into staging (signature, tenure well-formedness, stacker signatures, burnchain consistency, etc., verified inside `NakamotoChainState::accept_block` / `process_new_nakamoto_block_ext`), and has no dependency on `self.broadcast` or `authenticated`. So the claimed equality in the question — "network-wide propagation == `self.broadcast == Some(true) AND authenticated == true`" — does **not** hold in the code; propagation is actually gated only on `data_resp.accepted`.

### Impact Explanation
Any unauthenticated remote peer that can reach the node's RPC endpoint `/v3/blocks/upload/` and submit a **validly-signed** Nakamoto block (i.e., one that passes `NakamotoChainState::accept_block`'s well-formedness/signature/tenure checks) will have that block queued via `node.set_relay_message`, which causes the node to relay/gossip the block to its peers. This matches the "network-wide propagation of forged data" Critical category — except note the block must still pass the substantive chain-state acceptance checks (signature and stacker signing checks are enforced by `accept_block`), so this is not a bypass of block validity itself, only a bypass of the intended broadcast-authorization gate that the API's own comment ("if broadcast=1 is set, then the requester must be authenticated") implies should exist.

### Likelihood Explanation
- The `/v3/blocks/upload/` RPC endpoint is remotely reachable by design (it's how blocks are pushed to bootstrap/API nodes).
- No RPC secret/auth header is required as long as the attacker omits `broadcast=1` in the query string.
- The attacker still needs a validly signed Nakamoto block (correct miner and stacker signatures for a real, current tenure/sortition) — this limits attacker-chosen content, but any actor with a legitimately-produced or replayed valid block (e.g. a block from a different node's local mempool, or a block the attacker legitimately mined/observed) can trigger relay through this endpoint without providing the RPC password.
- This is repeatable per distinct valid block.

### Recommendation
Gate `node.set_relay_message(...)` on `self.broadcast.unwrap_or(false)` (and by extension the enforced `authenticated` requirement) in addition to `data_resp.accepted`, i.e. only relay when the caller explicitly requested `broadcast=1` and was authenticated, matching the documented intent of the `broadcast` query parameter and the 401 gate in `try_parse_request`.

### Proof of Concept
Rust net test plan (in `stackslib/src/net/api/tests/postblock_v3.rs` or similar):
1. Configure `RPCPostBlockRequestHandler::new(Some("secret".into()))` on a `StacksNodeState` test harness with an authorization secret set.
2. Construct a validly-signed Nakamoto block for the current tip/tenure (reuse test helpers from `chainstate::nakamoto::tests::node`).
3. Send a POST to `/v3/blocks/upload/` with **no** `broadcast` query parameter and **no** `authorization` header, with the block bytes as the body.
4. Assert the response is `200 OK` with `StacksBlockAcceptedData { accepted: true, .. }` (block passed `accept_block`).
5. Assert (failure expected under current code) that `node.set_relay_message` was **not** invoked — e.g. by inspecting `StacksNodeState`'s pending relay message field/queue after the call. Under the current implementation this assertion fails because `data_resp.accepted == true` unconditionally triggers `set_relay_message` regardless of `self.broadcast` or the missing `authorization` header.

    /// Insert a staging Nakamoto block that got relayed to us somehow -- e.g. uploaded via http,
    /// downloaded by us, or pushed via p2p.
    /// Return Ok(true) if we should broadcast the block.  If force_broadcast is true, then this
    /// function will return Ok(true) even if we already have the block.
    /// Return Ok(false) if we should not broadcast it (e.g. we already have it, it was invalid,
    /// etc.)
    /// Return Err(..) in the following cases, beyond DB errors:
    /// * If the block is from a tenure we don't recognize
    /// * If we're not in the Nakamoto epoch
    /// * If the reward cycle info could not be determined
    /// * If there was an unrecognized signer
    /// * If the coordinator is closed, and `coord_comms` is Some(..)
    pub fn process_new_nakamoto_block_ext(
        burnchain: &Burnchain,
        sortdb: &SortitionDB,
        sort_handle: &mut SortitionHandleConn,
        chainstate: &mut StacksChainState,
        stacks_tip: &StacksBlockId,
        block: &NakamotoBlock,
        coord_comms: Option<&CoordinatorChannels>,
        obtained_method: NakamotoBlockObtainMethod,
        force_broadcast: bool,
    ) -> Result<BlockAcceptResponse, chainstate_error> {
        info!(
            "Handle incoming Nakamoto block {}/{} obtained via {}",
            &block.header.consensus_hash,
            &block.header.block_hash(),
            &obtained_method;
            "block_id" => %block.header.block_id(),
        );
        if block.is_shadow_block() {
            // drop, since we can get these from ourselves when downloading a tenure that ends in
            // a shadow block.
            return Ok(BlockAcceptResponse::AlreadyStored);
        }

        if fault_injection::ignore_block(block.header.chain_length, &burnchain.working_dir) {
            return Ok(BlockAcceptResponse::Rejected(
                "Fault injection: ignoring block".into(),
            ));
        }

        // do we have this block?  don't lock the DB needlessly if so.
        if chainstate
            .nakamoto_blocks_db()
            .has_nakamoto_block_with_index_hash(&block.header.block_id())
            .inspect_err(|e| {
                warn!(
                    "Failed to determine if we have Nakamoto block {}/{}: {e:?}",
                    &block.header.consensus_hash,
                    &block.header.block_hash()
                );
            })?
        {
            if force_broadcast {
                // it's possible that the signer sent this block to us, in which case, we should
                // broadcast it
                debug!(
                    "Already have Nakamoto block {}, but treating a new anyway so we can broadcast it",
                    &block.header.block_id()
                );
                return Ok(BlockAcceptResponse::Accepted);
            } else {
                debug!("Already have Nakamoto block {}", &block.header.block_id());
                return Ok(BlockAcceptResponse::AlreadyStored);
            }
