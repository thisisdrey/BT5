### Title
Positions with debt between `debtFloorInUsd` and `debtFloorInUsd / maxLiquidable` can never be liquidated — permanent bad-debt DoS - ([File: contracts/Pool.sol])

### Summary
`Pool.liquidate` enforces two conflicting constraints: (1) a single call may repay at most `maxLiquidable` (default 50%) of the position's debt, and (2) the post-repayment remaining debt must be either zero or ≥ `debtFloorInUsd`. When `debtFloorInUsd > 0` and `maxLiquidable < 1e18`, any position whose debt `D` satisfies `D·(1 − maxLiquidable) < debtFloorInUsd ≤ D` is permanently unliquidatable: every partial repayment leaves a remainder below the floor (reverts `RemainingDebtIsLowerThanTheFloor`), and a full repayment exceeds `maxLiquidable` (reverts `AmountGreaterThanMaxLiquidable`). This is the direct on-chain analog of the MySQL optimizer hang/crash class: a liveness failure of the liquidation path reachable purely by unprivileged users, producing protocol insolvency.

### Finding Description
In `Pool.liquidate`: [1](#0-0) 

```solidity
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}

if (debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(
        address(syntheticToken_),
        _debtTokenBalance - amountToRepay_
    );
    if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
        revert RemainingDebtIsLowerThanTheFloor();
    }
}
```

`maxLiquidable` is initialized to `0.5e18` in `initialize` [2](#0-1)  and `debtFloorInUsd` is a governed parameter set via `updateDebtFloor` [3](#0-2) . The floor feature exists precisely to prevent dust debt, but combined with the per-call liquidation cap it creates a dead zone:

- Full repay (`amountToRepay_ = debt`) → `wadDiv` returns `1e18 > 0.5e18` → `AmountGreaterThanMaxLiquidable`.
- Any repay leaving `0 < remaining < debtFloorInUsd` → `RemainingDebtIsLowerThanTheFloor`.
- A repay leaving `remaining ≥ debtFloorInUsd` is only possible while `debt − repaid ≥ floor`; once remaining debt falls below `floor / (1 − maxLiquidable)` the next call is stuck on both branches — the leftover can never be cleared.

Concretely, with `debtFloorInUsd = 100` USD and `maxLiquidable = 50%`: a position with `$150` of debt repays `$50` (leaves `$100`, allowed), then the remaining `$100` can never be repaid — 50% leaves `$50 < floor`, 100% exceeds `maxLiquidable`. Worse, positions opened with debt already `< 2·floor` are unliquidatable from the first call.

There is no alternative recovery path: `liquidate` is the only function that reduces another account's debt and seizes collateral, and `depositToken_.seize`/`debtToken.burn` are callable only from `Pool`.

### Impact Explanation
Permanent freezing of collateral and permanent accrual of unliquidatable bad debt, leading to protocol insolvency. An unprivileged attacker can deliberately open many positions sized into the dead zone (debt in `(debtFloorInUsd·(1−maxLiquidable), debtFloorInUsd]` initially, or `≤ debtFloorInUsd/(1−maxLiquidable)` after partial repayments), let them go unhealthy via normal price movement, and no liquidator — permissionless actor — can ever clear them. The synth supply stays backed by insufficient collateral. This matches the accepted impact classes (protocol insolvency / permanent freezing — the borrower's collateral is locked forever since withdrawal requires a healthy/full position resolution).

### Likelihood Explanation
Medium. Requires only: (a) `debtFloorInUsd > 0` configured (the feature exists and `updateDebtFloor` is a live governor function; deployed `Pool` artifacts reference `debtFloorInUsd`), and (b) a position becoming unhealthy, which happens naturally via market moves or can be forced by the attacker choosing the riskiest listed collateral and max borrowing. No privileged role, oracle failure, or governance mistake beyond enabling the floor is needed — the flaw is in the arithmetic itself. Reachable entirely through public `DebtToken.issue` and `Pool.liquidate` entry points.

### Recommendation
Inside `liquidate`, treat a full clear as legal regardless of `maxLiquidable` when the remaining debt would otherwise fall below the floor — e.g., clamp `amountToRepay_` up to the full balance when `quoteTokenToUsd(synthetic, balance − amountToRepay_) < debtFloorInUsd`, or exempt the "repay-to-zero" case from the `maxLiquidable` check. Alternatively, enforce the floor at issuance time (`issue` must leave debt `≥ floor` or `0`) and drop the floor check in `liquidate` for full repayments.

### Proof of Concept
Hardhat fork sketch against the deployed `Pool` (assumes `debtFloorInUsd = 100e18`, `maxLiquidable = 0.5e18`):

```ts
// 1. Attacker deposits collateral and issues ~$150 of msUSD debt
await depositToken.deposit(collateralAmount, attacker.address);
await debtToken.issue(msUSD.address, parseEther('150'));

// 2. Price moves (or attacker used max CF + volatile collateral);
//    position is now unhealthy
expect((await pool.debtPositionOf(attacker.address)).isHealthy).to.be.false;

// 3. Liquidator repays 50% ($75) -> leaves $75 < floor -> REVERTS
await expect(
  pool.liquidate(msUSD.address, attacker.address, parseEther('75'), depositToken.address)
).to.be.revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor');

// 4. Full repay ($150) -> 1e18 > 0.5e18 maxLiquidable -> REVERTS
await expect(
  pool.liquidate(msUSD.address, attacker.address, parseEther('150'), depositToken.address)
).to.be.revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');

// 5. Repay $50 leaves $100 (== floor, allowed); remaining $100 is now
//    permanently unliquidatable by both branches above.
```

Uncertainty note: the deployed on-chain value of `debtFloorInUsd` was not verifiable from the indexed repo (it lives in proxy storage, not the JSON artifacts). If it is `0` on all live pools, the dead zone does not exist today, but the code path remains broken the moment the governor enables the feature — the check is unconditional on the parameter being non-zero rather than being compatible with `maxLiquidable`.
