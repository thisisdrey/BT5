### Title
Missing slippage protection in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` enables front-run asset loss - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java, actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
The TRON Bancor-style AMM `Exchange` computes the counter-asset amount (`anotherTokenQuant`) for inject/withdraw operations purely from the exchange's current on-chain pool ratio at execution time, with no user-supplied bound. Unlike `ExchangeTransactionContract`, which carries an `expected` field enforced in validation, `ExchangeInjectContract` and `ExchangeWithdrawContract` have no equivalent protection field.

### Finding Description
`ExchangeWithdrawActuator.doValidate()`/`execute()` computes `anotherTokenQuant = bigSecondTokenBalance * bigTokenQuant / bigFirstTokenBalance` (or the symmetric branch) directly from the exchange pool's live `firstTokenBalance`/`secondTokenBalance` at the moment the transaction is processed [2](#0-1) . The same pattern exists in `ExchangeInjectActuator.execute()`, which computes `anotherTokenQuant` from `firstTokenBalance`/`secondTokenBalance` with no user-specified bound at all [3](#0-2) . Both `ExchangeInjectContract` and `ExchangeWithdrawContract` in the protobuf schema only carry `owner_address`, `exchange_id`, `token_id`, and `quant` — no `expected`/min-output field [4](#0-3) . By contrast, `ExchangeTransactionContract` explicitly adds an `expected` field [5](#0-4) , and `ExchangeTransactionActuator.doValidate()` enforces it: `if (anotherTokenQuant < tokenExpected) throw new ContractValidateException(...)` [1](#0-0) . This shows the protocol designers recognized the need for slippage protection for trades but omitted it for inject/withdraw, mirroring the Ulysses report's core issue: a value computed against a live, mutable pricing state (pool ratio / vault weights) is used to settle a transaction without any user-enforced bound, so any state change between quote-time and execution-time (e.g., another account's `ExchangeTransactionContract` trade against the same pool executed earlier in the block, or a preceding `ExchangeInjectContract`/`ExchangeWithdrawContract`) silently changes the counter-asset amount the caller receives or must pay.

### Impact Explanation
A pool creator (any unprivileged account that created an `Exchange` and is authorized under `exchangeCapsule.getCreatorAddress()` check at [6](#0-5) ) who submits an inject or withdraw transaction can receive/pay a materially different `anotherTokenQuant` than what they computed off-chain, because the ratio is read fresh from mutable on-chain state at execution and there is no way to cap the deviation. On withdrawal this can mean receiving far less of the counter asset than intended for the amount of the first asset withdrawn, i.e., a permanent, unrecoverable loss of assets that were rightfully theirs, since the pool balance is decremented for good and the withdrawn counterpart amount cannot be topped up post-hoc. On inject, the account can be forced to lock in more of the counter asset than intended for the same target injection, causing an unintended over-contribution.

### Likelihood Explanation
It requires ordinary transaction ordering within a single block or across nearby blocks (any other trade or inject/withdraw against the same exchange pool between the time the caller queries the pool ratio and when their own transaction is packed), which is a standard occurrence for any actively traded AMM pool and does not require any privileged role — any account can send an `ExchangeTransactionContract` against the pool to shift the ratio before the victim's inject/withdraw lands.

### Recommendation
Add an `expected`/minimum-output (or maximum-cost, for inject) field to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and validate the computed `anotherTokenQuant` against it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`, mirroring the existing check in `ExchangeTransactionActuator.doValidate()`.

### Proof of Concept
1. Account `A` creates/owns `Exchange` pool `P` with `firstTokenBalance = F`, `secondTokenBalance = S`.
2. `A` queries the current ratio and computes the `anotherTokenQuant` they expect for withdrawing `Q` of `firstToken` via `ExchangeWithdrawContract` (as in `ExchangeWithdrawActuator.doValidate()` [7](#0-6) ), off-chain, and broadcasts the withdraw transaction.
3. Before `A`'s transaction is packed, another unprivileged account `B` submits an `ExchangeTransactionContract` trade against the same pool `P`, shifting `firstTokenBalance`/`secondTokenBalance`.
4. `A`'s withdraw transaction executes against the now-shifted balances in `ExchangeWithdrawActuator.execute()` [2](#0-1) , yielding an `anotherTokenQuant` far lower than `A` expected, with no validation to reject or bound the deviation, permanently reducing `A`'s withdrawn assets.
