### Title
Missing path validation on `BackupId` in `RestoreRepository` allows path-traversal into another repository's backup manifest/bundle - ([File: internal/gitaly/service/repository/restore_repository.go])

### Summary
`validateRestoreRepositoryRequest` validates `PathPrefix` via `backup.ValidatePathPrefix`, but never validates `BackupId`. `BackupId` is used verbatim as a filesystem path component when the `ManifestLocator` builds manifest/bundle/ref/custom-hooks paths, so an attacker restoring their own (validated) repository can smuggle `../` sequences in `BackupId` to make the backup manager read a different repository's manifest/backup artifacts.

### Finding Description
`RestoreRepository` (`internal/gitaly/service/repository/restore_repository.go:14-52`) validates `Repository`, `VanityRepository` (via `s.locator.ValidateRepository`), and `PathPrefix` (via `backup.ValidatePathPrefix`, `restore_repository.go:67`), but performs **no validation whatsoever on `in.GetBackupId()`** before passing it into `backup.RestoreRequest.BackupID` and on to `manager.Restore`.

`backup.ValidatePathPrefix` (`internal/backup/backup.go:176-196`) is thorough — it rejects absolute paths, `..` components, empty/`.`-only components, and trailing/double slashes, as confirmed by the extensive `TestValidatePathPrefix` table (`internal/backup/backup_test.go:1477-1580`). This closes off the `PathPrefix` vector described in the question.

However, `Manager.Restore` (`internal/backup/backup.go:388-454`) calls `mgr.locator.Find(ctx, req.VanityRepository, req.BackupID, locatorOpts...)`, and `ManifestLocator.Find`/`BeginFull`/`BeginIncremental` (`internal/backup/locator.go:30-147`) build manifest and artifact paths with raw `filepath.Join` calls such as:
```go
filepath.Join(cfg.pathPrefix, storageName, relativePath, backupID, "001.bundle")
```
`backupID` is concatenated directly as a path segment with no character/traversal restriction. Because `Repository`/`VanityRepository` are the attacker's own, already-validated repository, `storageName`/`relativePath` are safe, but a crafted `BackupId` such as `../../<other-storage>/<other-relative-path>/<their-backup-id>` collapses via `filepath.Clean` inside `filepath.Join` to point at another tenant's manifest/bundle/custom-hooks directory instead of the attacker's own backup tree.

The resulting manifest (read from the victim's backup tree) contains `bundle_path`/`ref_path`/`custom_hooks_path` values that are then fetched from the shared backup sink and restored — via `restoreFromBundle`/`restoreCustomHooks` — into the attacker's own repository (since `repositoryFactory` is built from `req.Repository`, which is the attacker's repo). This lets the attacker exfiltrate another project's Git history/refs and custom hooks by observing the resulting state of their own repository after a crafted `RestoreRepository` call.

### Impact Explanation
This allows cross-tenant confidentiality compromise: an unprivileged user who can invoke `RestoreRepository` for their own repository can cause Gitaly to load another repository's backup manifest and bundle data and materialize it into their own (accessible) repository, disclosing that other repository's git objects, refs, and custom hooks. This matches "cross-repository object access" / disclosure of another repository's objects and metadata.

### Likelihood Explanation
Requires server-side backups configured (`s.backupSink`/`s.backupLocator` set, a supported but non-default deployment) and the attacker must know or guess the target's storage name, relative path (e.g. `@hashed/...`), and a valid `BackupId` for that repository — none of which are secret values requiring privileged access, but which do require some reconnaissance (hashed paths and backup IDs, e.g. timestamps, may be guessable or leaked). Given those, the RPC is directly reachable by any user permitted to trigger repository restore/import flows for their own project.

### Recommendation
Validate `BackupId` the same way `PathPrefix` is validated — reject empty, absolute, `..`-containing, or otherwise unclean path components (e.g. reuse/extend `backup.ValidatePathPrefix` or add a dedicated `ValidateBackupID` check) in `validateRestoreRepositoryRequest`, and apply the same validation in `ManifestLocator.Find`/`BeginFull`/`BeginIncremental` before using `backupID` in any `filepath.Join`.

### Proof of Concept
```go
// internal/gitaly/service/repository/restore_repository_test.go (new case)
resp, err := client.RestoreRepository(ctx, &gitalypb.RestoreRepositoryRequest{
    Repository:       attackerRepo,       // attacker's own, validated repo
    VanityRepository: attackerRepo,
    BackupId:         "../../" + victimStorage + "/" + victimRelativePath + "/" + victimBackupID,
})
// Expected (secure) behavior: structerr.NewInvalidArgument("restore repository: invalid backup id")
// Actual (vulnerable) behavior: err == nil, and attackerRepo now contains victim's
// git history/refs/custom hooks fetched from victim's backup path.
require.Error(t, err) // currently fails because no BackupId validation exists
```
