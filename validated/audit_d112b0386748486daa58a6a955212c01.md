### Title
Missing Trailing-Bytes Check in Derivable Account Abstraction Deserialization Allows Non-Canonical Authentication Data — (`aptos-move/framework/aptos-framework/sources/account/common_account_abstractions/ethereum_derivable_account.move`, `solana_derivable_account.move`)

---

### Summary

The `ethereum_derivable_account` and `solana_derivable_account` modules, both registered as mainnet derivable authentication functions, deserialize BCS-encoded `abstract_public_key` and `abstract_signature` blobs without checking that all bytes were consumed. Any trailing bytes are silently ignored and the authentication proceeds as if the input were well-formed. The `sui_derivable_account` module — which handles the same authentication pattern — explicitly guards against this with `assert!(!bcs_stream::has_remaining(&mut stream), EMALFORMED_DATA)`. The root cause is identical to the Optimism M-1 bug: a mandatory field (or the end-of-input sentinel) is not enforced, so a structurally incomplete or padded binary blob is accepted as valid.

---

---

### Impact Explanation

**Transaction malleability via `abstract_signature` trailing bytes.** An observer who sees a valid Ethereum-DAA or Solana-DAA transaction in the mempool can append arbitrary trailing bytes to the `abstract_signature` field and rebroadcast it. The mutated transaction has a different hash but the same sender, sequence number, and payload. Both the original and the mutated form pass authentication. Only one executes (sequence number is consumed), but off-chain systems (explorers, indexers, wallets) that track transactions by hash can be confused or deceived.

**Non-canonical encoding accepted for `abstract_public_key`.** The account address for a derivable-AA account is derived from the raw `abstract_public_key` bytes via `derive_account_address(func_info, signing_data.derivable_abstract_public_key())`. Because trailing bytes are silently dropped during parsing, two byte strings that differ only in trailing garbage parse to the same `(ethereum_address, domain)` pair but produce different account addresses. This means the same Ethereum key can authenticate to multiple distinct Aptos accounts (one per distinct trailing-byte suffix), all of which pass signature verification. While this does not allow impersonating an existing account, it violates the canonical-encoding invariant that BCS requires and that `sui_derivable_account` enforces.

**Inconsistent rejection across authentication modules.** The Sui DAA module rejects trailing bytes with `EMALFORMED_DATA`; the Ethereum and Solana DAA modules silently accept them. Any future logic that relies on the invariant "a well-formed abstract_public_key uniquely identifies an account" is broken for Ethereum/Solana DAA accounts.

---

### Likelihood Explanation

The trigger is unprivileged: any party who can observe a pending Ethereum-DAA or Solana-DAA transaction (i.e., anyone watching the mempool) can construct the malleated form. No special keys or permissions are required. The modules are registered at genesis and active on mainnet.

---

### Recommendation

Add `assert!(!bcs_stream::has_remaining(&mut stream), EMALFORMED_DATA)` (or an equivalent error code) immediately before the return value in every branch of `deserialize_abstract_public_key` and `deserialize_abstract_signature` in both `ethereum_derivable_account.move` and `solana_derivable_account.move`, mirroring the pattern already present in `sui_derivable_account.move`.

For `ethereum_derivable_account.move`:
```move
fun deserialize_abstract_public_key(abstract_public_key: &vector<u8>): SIWEAbstractPublicKey {
    let stream = bcs_stream::new(*abstract_public_key);
    let ethereum_address = bcs_stream::deserialize_vector<u8>(&mut stream, |x| deserialize_u8(x));
    let domain = bcs_stream::deserialize_vector<u8>(&mut stream, |x| deserialize_u8(x));
    assert!(!bcs_stream::has_remaining(&mut stream), EMALFORMED_DATA); // add this
    SIWEAbstractPublicKey { ethereum_address, domain }
}
```

And similarly for each branch of `deserialize_abstract_signature`, and for both functions in `solana_derivable_account.move`.

### Proof of Concept

The `sui_derivable_account` test suite already demonstrates the expected behavior and the exploit pattern:

```move
#[test]
#[expected_failure(abort_code = EMALFORMED_DATA)]
fun test_deserialize_abstract_signature_with_trailing_bytes() {
    // valid signature bytes ...
    let abstract_signature = create_raw_signature(signature_bytes);
    abstract_signature.push_back(0xDE);
    abstract_signature.push_back(0xAD);
    // This correctly aborts for sui_derivable_account ...
    deserialize_abstract_signature(&abstract_signature);
}
``` [8](#0-7) 

The identical test applied to `ethereum_derivable_account::deserialize_abstract_signature` or `solana_derivable_account::deserialize_abstract_signature` would **pass** (no abort) because neither function checks for remaining bytes. An analogous test for `deserialize_abstract_public_key` in both modules would also pass, confirming that trailing bytes are silently accepted in both the signature and public-key deserialization paths.
