Audit Report

## Title
Reward pool state (`stake`/`unstake`/`harvest_rewards`) permanently DoS'd when a non-monotonic `BlockNumberProvider` regresses, locking staked funds and unclaimed rewards - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards` computes reward-per-token accrual using `ensure_sub` on the delta between the current block number (sourced from a generic `T::BlockNumberProvider`) and the stored `last_update_block`. Because the pallet explicitly supports non-local, relay-chain-derived block number providers whose documentation states they are not guaranteed to be monotonically increasing, a single regression causes `ensure_sub` to underflow and return a hard error, which propagates out of every state-mutating extrinsic (`stake`, `unstake`, `harvest_rewards`) for that pool permanently, since no subsequent call can ever succeed to advance `last_update_block` again.

## Finding Description
`reward_per_token` computes elapsed blocks via `Self::last_block_reward_applicable(pool_info.expiry_block).ensure_sub(pool_info.last_update_block)?` [1](#0-0) , where `last_block_reward_applicable` returns `min(now, expiry_block)` and `now = T::BlockNumberProvider::current_block_number()` [2](#0-1) . `update_pool_rewards` unconditionally stores `now` as the new `last_update_block` on every successful call [3](#0-2) . This function is invoked from `stake`, `unstake`, and `harvest_rewards` via `update_pool_and_staker_rewards` before any other pool/staker mutation occurs [4](#0-3) [5](#0-4) [6](#0-5) . The pallet's `BlockNumberFor<T>` type is explicitly derived from `T::Config::BlockNumberProvider` [7](#0-6) , and the changelog documents this generalization was made specifically to support relay-chain-sourced block numbers on parachains, listing `asset-hub-rococo-runtime`, `asset-hub-westend-runtime`, and `pallet-staking-async-parachain-runtime` as consumers.

I was unable to inspect the actual `impl pallet_asset_rewards::Config for Runtime` blocks in `asset-hub-rococo`/`asset-hub-westend` in this session (tool access ran out before reading the concrete `type BlockNumberProvider = ...` assignment), so I cannot directly confirm from this repo snapshot whether the deployed runtimes wire in a relay-chain-backed, non-monotonic provider (e.g. `RelaychainDataProvider`) versus the safe default `frame_system::Pallet<Self>`. This is a material gap: the claim's core exploit precondition (a non-monotonic provider actually configured) is asserted from the prdoc changelog intent, not verified against the live runtime configuration in this snapshot.

Regardless of that gap, the code-level defect is real and verifiable within the pallet itself: `ensure_sub` is used instead of `saturating_sub`, so if `now < last_update_block` ever occurs for any configured provider, the underflow is unrecoverable — `last_update_block` cannot be advanced without a successful call, and a successful call requires `now >= last_update_block`, creating a permanent deadlock for that pool. This mirrors the acknowledged pattern in `pallet-vesting`'s `locked_at`, which deliberately uses `saturating_sub` to tolerate `n < starting_block` [8](#0-7) , and the `pallet-society` fix for non-monotonic block providers described in `prdoc/stable2509/pr_9497.prdoc`, confirming this class of issue is a recognized real occurrence for non-local `BlockNumberProvider`s in this codebase, for which `pallet-asset-rewards` has no equivalent hardening.

## Impact Explanation
If triggered, `unstake` and `harvest_rewards` fail deterministically and permanently for the affected pool, since both unconditionally call the failing `update_pool_and_staker_rewards` before any other logic. This locks stakers' frozen staking-asset tokens and unclaimed reward-asset balances in the pool account with no recovery path (no saturating fallback, no admin bypass), matching the "permanent user-fund lock" impact category.

## Likelihood Explanation
Triggering this requires the runtime to configure `pallet_asset_rewards::Config::BlockNumberProvider` to a provider whose block number is not guaranteed monotonic (e.g., a relay-chain-backed provider), and for that provider to actually regress at least once after a pool has been updated. The prdoc changelog in this snapshot indicates this generalization was added for parachain runtimes including asset-hub-rococo/westend, and `RelaychainStateProvider::current_relay_chain_state` in `cumulus/pallets/parachain-system/src/lib.rs` documents relay parents are "not guaranteed to be monotonically increasing" [9](#0-8) . However, I was not able to confirm in this session that any currently deployed runtime in this repository snapshot actually wires `pallet-asset-rewards` to such a non-monotonic provider rather than the default `frame_system::Pallet<Self>` (which is monotonic by construction and would not trigger this bug at all). Without that confirmation, likelihood cannot be fully established from verified in-repo configuration; the pallet-level code defect exists, but whether it is presently reachable in production configuration is unverified with the available evidence.

## Recommendation
Replace `ensure_sub` with `saturating_sub` (clamping to zero) in `reward_per_token`'s elapsed-blocks computation, mirroring `pallet-vesting::locked_at`. Additionally, `update_pool_rewards` should avoid regressing `last_update_block` backward when `now < last_update_block`, to prevent silently reversing reward accounting once/if the provider's value catches back up.

## Proof of Concept
1. Configure a runtime's `pallet_asset_rewards::Config::BlockNumberProvider` to a non-monotonic provider (e.g., a relay-chain block number provider).
2. Create a pool and call `stake`, which sets `Pools::<T>::get(pool_id).last_update_block = N` via `update_pool_rewards`.
3. Have the configured provider's `current_block_number()` return a value less than `N` on a subsequent call.
4. Call `unstake` or `harvest_rewards` for that pool; `reward_per_token`'s `ensure_sub` underflows and returns `Error::<T>::...` via `?`, aborting the extrinsic.
5. Repeat step 4 indefinitely — the call fails every time since `last_update_block` can never be reduced or advanced past the regression without a successful update, permanently locking staked funds and rewards for that pool.

	pub fn locked_at<BlockNumberToBalance: Convert<BlockNumber, Balance>>(
		&self,
		n: BlockNumber,
	) -> Balance {
		// Number of blocks that count toward vesting;
		// saturating to 0 when n < starting_block.
		let vested_block_count = n.saturating_sub(self.starting_block);
		let vested_block_count = BlockNumberToBalance::convert(vested_block_count);
		// Return amount that is still locked in vesting.
		vested_block_count
			.checked_mul(&self.per_block()) // `per_block` accessor guarantees at least 1.
			.map(|to_unlock| self.locked.saturating_sub(to_unlock))
			.unwrap_or(Zero::zero())
	}
