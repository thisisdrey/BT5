### Title
Missing permission-level restriction on `AccountPermissionUpdateContract` allows a restricted "active" key to self-escalate to full account (owner) control - ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
The FOSSBilling bug is a missing "you cannot grant yourself elevated rights through a permission scoped for something else" check on the `permissions_update` endpoint. The closest reachable analog in java-tron is `AccountPermissionUpdateActuator`, the actuator that lets an account holder rewrite its own `owner`/`witness`/`active` permission sets. Nothing in the actuator, nor in the generic transaction-signature verification path, enforces that this specific, power-granting contract type may only be authorized by the account's `owner` permission (`permission_id == 0`). Any `active` permission (id 2-9) whose `operations` bitmap happens to include `AccountPermissionUpdateContract` (bit 46) is fully sufficient to execute it, letting a deliberately-scoped, lower-privilege key rewrite the entire permission structure of the account — including its own weight/threshold and the owner permission — exactly the "narrow permission escalates to full control over the same principal" pattern described in the CVE.

### Finding Description
Transaction-level permission enforcement is generic and contract-type agnostic. `TransactionCapsule.checkPermission` only asserts that a non-owner permission is of type `Active` and that its `operations` bitmap allows the requested `ContractType`: [1](#0-0) 

`validateSignature`/`addSign` resolve the permission purely from `contract.getPermissionId()` on the account, with no special-casing for `AccountPermissionUpdateContract`: [2](#0-1) 

`AccountPermissionUpdateActuator.validate()` similarly performs only structural validation of the new `owner`/`witness`/`actives` permissions (key counts, thresholds, distinct addresses, operation-bitmap sanity) — it never inspects which permission level was used to authorize the transaction, nor rejects the case where the acting permission is a scoped `active` permission rather than `owner`: [3](#0-2) 

`execute()` then unconditionally overwrites the account's owner, witness, and active permission sets with the attacker-supplied values via `AccountCapsule.updatePermissions`: [4](#0-3) [5](#0-4) 

Because `operations` is a raw 256-bit bitmap over `ContractType` values (with `AccountPermissionUpdateContract = 46`) and `AccountPermissionUpdateActuator.checkPermission` only checks the bitmap against `getAvailableContractType()` (i.e., "is this a valid/enabled contract type at all"), it does not forbid granting bit 46 to an `active` permission: [6](#0-5) 

Consequently, once any `active` permission on an account is configured (by the account owner, or inherited from a template/tool that sets broad default operations) to include `AccountPermissionUpdateContract`, the holder of just that `active` key — which was meant to be limited to a specific, narrower set of contract types — can unilaterally submit a new `AccountPermissionUpdateContract` that rewrites the `owner` permission (e.g., adding itself as the sole owner key with threshold 1) and all `active`/`witness` permissions, fully seizing control of the account. This is structurally identical to the FOSSBilling flaw: a permission granted for one narrow purpose (`staff.create_and_edit_staff` / a scoped `active` key) is abused via a permission-management endpoint (`permissions_update` / `AccountPermissionUpdateContract`) to grant the caller arbitrary elevated permissions on the very same principal, with no dedicated boundary check preventing self-escalation.

### Impact Explanation
Successful exploitation gives the attacker permanent, unauthorized control over the victim account: it can rewrite the `owner` permission to itself (locking out the original owner), change `active`/`witness` permissions arbitrarily, and thereby control all subsequent asset transfers, voting, contract deployment/calls, and resource operations gated by that account's permissions. This is a concrete unauthorized-account-takeover / persistent privilege-escalation impact matching the "Validate" criteria (unauthorized account operation, theft/freezing of funds under attacker's post-escalation control).

### Likelihood Explanation
Exploitation requires that some `active` permission on the target account already includes (or can be made to include, e.g. via multisig setup tooling/wallets that grant broad default operation bitmaps, or a previous legitimate but overly-broad grant) the `AccountPermissionUpdateContract` bit, and that the attacker controls or colludes with a keyholder meeting that active permission's threshold. This is a realistic scenario for multisig-enabled TRON accounts where operators commonly grant broad "active" operation sets to delegated keys for convenience, not realizing that bit 46 effectively equals owner-level power. No special network position, SR/witness status, or additional privileges beyond an existing active-permission key are required — only a single signed `AccountPermissionUpdateContract` transaction.

### Recommendation
In `AccountPermissionUpdateActuator.validate()` (and/or in the shared `TransactionCapsule.checkPermission`/`checkPermissionOperations` path), explicitly reject any attempt to authorize `AccountPermissionUpdateContract` using a non-owner (`permission_id != 0`) permission, regardless of what its `operations` bitmap allows. This restores the intended trust boundary: only the account's `owner` permission should be able to redefine the account's permission structure, closing the self-escalation path analogous to the FOSSBilling `permissions_update` fix.

### Proof of Concept
1. Account `A` has default `owner` permission (threshold 1, key `A`) and an `active` permission (id 2) with threshold 1, key set `{K}`, and an `operations` bitmap that includes bit 46 (`AccountPermissionUpdateContract`) — a configuration an operator could plausibly create believing it only grants `K` narrow operational rights.
2. Holder of `K` builds an `AccountPermissionUpdateContract` for owner address `A`, setting:
   - `owner` = new Permission{type=Owner, threshold=1, keys=[K:1]}
   - `actives` = new broad Active permission also controlled by `K`
3. `K` signs the transaction using `permission_id = 2` (its existing active permission).
4. `TransactionCapsule.checkPermission` (lines 635-645) passes because permission type is `Active` and bit 46 is set in its operations.
5. `AccountPermissionUpdateActuator.validate()` (lines 148-229) passes because it only checks structural validity of the new permission set, not who authorized the change.
6. `execute()` calls `AccountCapsule.updatePermissions`, overwriting `A`'s owner permission to be controlled solely by `K` — full account takeover from what was intended to be a scoped `active` key.

  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
  }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
