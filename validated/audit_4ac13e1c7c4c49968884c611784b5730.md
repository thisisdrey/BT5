### Title
net/http Client Forwards Authorization/Cookie Headers on HTTPS→HTTP Downgrade Redirect to Same Host - ([File: src/net/http/client.go])

### Summary
`Client.do` decides whether to strip sensitive headers (`Authorization`, `Cookie`, `Proxy-Authorization`, etc.) on a redirect solely by comparing hostnames via `shouldCopyHeaderOnRedirect`, without ever comparing URL schemes. As a result, a redirect from `https://example.com` to `http://example.com` (a classic TLS-to-plaintext downgrade) is treated identically to a same-scheme redirect, and credentials configured on the initial request are re-sent over an unencrypted channel — mirroring the exact primitive in GHSA-pfc9-2cqg-9wq6 (Reactor Netty leaking credentials on protocol-downgrade redirect).

### Finding Description
Entry point: `(*Client).do` processes a 3xx response and builds the next hop request in the redirect loop at [1](#0-0) . Before copying headers it computes `stripSensitiveHeaders` using `shouldCopyHeaderOnRedirect(reqs[0].URL, req.URL)` only when the **hosts** differ [2](#0-1) . That helper, `shouldCopyHeaderOnRedirect`, punycode-normalizes and lower-cases only the hostnames and calls `isDomainOrSubdomain`; it never inspects `initial.Scheme` or `dest.Scheme` [3](#0-2) . The actual copy is performed by the closure built in `makeHeadersCopier`, which forwards `Authorization`, `Www-Authenticate`, `Cookie`, `Cookie2`, `Proxy-Authorization`, and `Proxy-Authenticate` headers unless `stripSensitiveHeaders` is true [4](#0-3) . Because the strip decision is host-based only, a same-host `https→http` redirect leaves `stripSensitiveHeaders == false`, so these secrets are placed on the plaintext follow-up request. Notably, the package is aware that scheme downgrade matters for the `Referer` header specifically — `refererForURL` explicitly special-cases https→http to omit the Referer [5](#0-4)  — but no equivalent scheme check exists for the sensitive-header stripping path, which is the exact asymmetry exploited in the reactor-netty advisory.

### Impact Explanation
An attacker who can trigger or influence a same-host redirect from HTTPS to HTTP (e.g., a compromised/misconfigured downstream server issuing a `Location: http://same-host/...` 3xx, or a network attacker performing SSL-stripping style redirection while keeping the host constant) causes the Go HTTP client to transmit `Authorization`/`Cookie`/`Proxy-Authorization` values in cleartext, allowing passive network interception of credentials (confidentiality impact matching CWE-522, similar to the CVSS vector in the advisory: AC:L/PR:N/C:L). This is PUBLIC-track material since it's directly observable via a documented, testable code path in the standard library `net/http` package used by effectively all Go HTTP clients that set `CheckRedirect`-following behavior (the default).

### Likelihood Explanation
Any Go program using `http.Client` (default behavior follows redirects unless `CheckRedirect` returns an error) that sets `Authorization` or `Cookie` headers directly on the request and is redirected by a same-origin server (or an on-path attacker spoofing a same-host redirect) will hit this path with no special privileges needed — the attacker only needs to control or influence the `Location` header of a response, a standard unauthenticated capability for a malicious/compromised server or MITM performing scheme downgrade.

### Recommendation
Update `shouldCopyHeaderOnRedirect` (or its caller in `Client.do`) to also require `initial.Scheme == dest.Scheme`, or at minimum treat an `https`→`http` scheme downgrade as always triggering `stripSensitiveHeaders = true`, regardless of host match, analogous to the existing scheme check already applied for the `Referer` header in `refererForURL`.

### Proof of Concept
```go
package http

import "net/url"

func TestShouldCopyHeaderOnRedirect_SchemeDowngrade(t *testing.T) {
	initial, _ := url.Parse("https://example.com/")
	dest, _ := url.Parse("http://example.com/") // same host, downgraded scheme
	got := shouldCopyHeaderOnRedirect(initial, dest)
	if got {
		t.Fatalf("shouldCopyHeaderOnRedirect returned true for https->http downgrade on same host; "+
			"sensitive headers (Authorization/Cookie) will be sent over plaintext")
	}
}
```
Expected (current, vulnerable) behavior: the test fails because `shouldCopyHeaderOnRedirect` returns `true` (same/subdomain host, scheme ignored), confirming that `Authorization`/`Cookie` will be forwarded to the downgraded plaintext endpoint via `makeHeadersCopier`'s `sensitive && !stripSensitiveHeaders` copy path.

func shouldCopyHeaderOnRedirect(initial, dest *url.URL) bool {
	// Permit sending auth/cookie headers from "foo.com"
	// to "sub.foo.com".

	// Note that we don't send all cookies to subdomains
	// automatically. This function is only used for
	// Cookies set explicitly on the initial outgoing
	// client request. Cookies automatically added via the
	// CookieJar mechanism continue to follow each
	// cookie's scope as set by Set-Cookie. But for
	// outgoing requests with the Cookie header set
	// directly, we don't know their scope, so we assume
	// it's for *.domain.com.

	ihost, err1 := httpguts.PunycodeHostPort(initial.Hostname())
	dhost, err2 := httpguts.PunycodeHostPort(dest.Hostname())
	if err1 != nil || err2 != nil {
		return false
	}
	ihost, ok1 := ascii.ToLower(ihost)
	dhost, ok2 := ascii.ToLower(dhost)
	return ok1 && ok2 && isDomainOrSubdomain(dhost, ihost)
}
