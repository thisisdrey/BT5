Audit Report

## Title
Outbound Queue V2 accepts and permanently commits messages with a zero (or arbitrarily low) fee, allowing free/underpriced spam of bridge state - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/send_message_impl.rs`, `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`SendMessage::validate` for the V2 outbound queue only checks the payload size and never inspects `Message::fee`, and `do_process_message` unconditionally commits every dequeued message into `Messages`/`MessageLeaves`, advances the global `Nonce`, and inserts a `PendingOrder` regardless of whether `fee == 0`. The upstream XCM-to-`Message` converter (`XcmConverter::extract_remote_fee`) also never rejects a zero fee amount, only checking that the withdrawn asset amount is `>=` the declared `PayFees` amount, so an ordinary XCM sender can drive `fee_amount = 0` end-to-end with no privileged access.

## Finding Description
`Pallet::validate` in `send_message_impl.rs` performs only a payload-size check before returning `Ok(message.clone())`, with no assertion on `message.fee`. [1](#0-0) 

`deliver()` then enqueues the ticket via `T::MessageQueue::enqueue_message` unconditionally. [2](#0-1) 

Once dequeued, `do_process_message` decodes the `Message` (including `fee`) and unconditionally appends the converted `OutboundMessage` to `Messages`, appends its hash to `MessageLeaves`, allocates the next `Nonce`, and inserts a `PendingOrder { nonce, fee, block_number }` into `PendingOrders` — none of this is gated on `fee > 0`. [3](#0-2) 

The only place a zero-value guard exists in this pallet is the unrelated `AddTip::add_tip` path, which explicitly rejects `amount == 0`, confirming the authors recognized the hazard but did not apply it to the primary acceptance path. [4](#0-3) 

`process_delivery_receipt` only pays a relayer reward `if order.fee > 0`, otherwise it simply removes the pending order with no reward, confirming `fee == 0` is an anticipated, unrejected state. [5](#0-4) 

Critically, the upstream XCM-to-`Message` converter used by `SnowbridgeMessageExporter`/`ExportMessage` also fails to enforce a nonzero fee: `extract_remote_fee` only checks that the fee asset is Ether and that `reserved_fee_amount >= fee_amount`, with no `ensure!(fee_amount > 0)`. An attacker can submit `WithdrawAsset`/`PayFees` with amount `0` and satisfy `0 >= 0`, producing a `Message` with `fee: 0` that flows straight into `validate`/`deliver`/`do_process_message`. [6](#0-5) [7](#0-6) 

This is distinct from the general XCM local-execution weight fee (which is charged separately by the XCM executor for buying weight on the local chain); the `Message.fee` field is specifically the reward earmarked for the Ethereum-side relayer, and no component in the reviewed code path enforces it be nonzero or cover any minimum processing/relay cost.

## Impact Explanation
Any unprivileged XCM sender able to route an `ExportMessage` through `SnowbridgeMessageExporter` to this exporter can submit arbitrary numbers of zero-fee messages. Each one consumes a `MaxMessagesPerBlock` slot and Merkle-leaf/PoV space every block, permanently advances the global `Nonce`, and creates a `PendingOrder` entry that lingers in storage indefinitely since no relayer is incentivized to submit a delivery receipt for zero reward. This matches the accepted impact class of "public underpriced work that degrades block production or stalls bridge processing" — unpriced state is committed on-chain and grows persistently without requiring any privileged actor, compromised relayer, or validator.

## Likelihood Explanation
High. No signed extrinsic or special permission is required beyond constructing a standard XCM program with `ExportMessage`; the fee-consistency check in `extract_remote_fee` is satisfiable with `fee_amount = 0` at no capital cost, and none of `validate`, `deliver`, or `do_process_message` in the outbound-queue-v2 pallet enforce a fee floor. The attack is trivially repeatable and only costs the attacker the local XCM dispatch/weight fee, not the bridge relay fee.

## Recommendation
Enforce a minimum, nonzero fee in `SendMessage::validate` (and/or `do_process_message`) for the V2 outbound queue, mirroring the V1 pallet's `calculate_fee`/pricing-parameter model, and additionally reject `fee_amount == 0` (or any amount below a configured floor) in `XcmConverter::extract_remote_fee`. Do not allow `PendingOrders` to be created for messages that have not paid for their own inclusion/relay.

## Proof of Concept
1. Construct an XCM program matching the expected `ExportMessage` syntax with `WithdrawAsset` and `PayFees` both specifying amount `0` for the Ether fee asset, followed by a valid `AliasOrigin`/`DepositAsset`/commands/`SetTopic` sequence.
2. `XcmConverter::convert` succeeds because `extract_remote_fee` only checks `reserved_fee_amount >= fee_amount` (0 >= 0), producing `Message { fee: 0, .. }`.
3. `Pallet::<T>::validate(&message)` succeeds because only payload size is checked.
4. `Pallet::<T>::deliver(ticket)` enqueues the message via `T::MessageQueue::enqueue_message`.
5. On processing, `do_process_message` commits the message into `Messages`/`MessageLeaves`, increments `Nonce`, and inserts `PendingOrder { nonce, fee: 0, .. }` into `PendingOrders` — with no economic cost beyond local dispatch weight, and no relayer incentive to ever clear the resulting entry.

	fn extract_remote_fee(&mut self) -> Result<u128, XcmConverterError> {
		use XcmConverterError::*;
		let reserved_fee_assets = match_expression!(self.next()?, WithdrawAsset(fee), fee)
			.ok_or(WithdrawAssetExpected)?;
		ensure!(reserved_fee_assets.len() == 1, AssetResolutionFailed);
		let reserved_fee_asset =
			reserved_fee_assets.inner().first().cloned().ok_or(AssetResolutionFailed)?;
		let (reserved_fee_asset_id, reserved_fee_amount) = match reserved_fee_asset {
			Asset { id: asset_id, fun: Fungible(amount) } => Ok((asset_id, amount)),
			_ => Err(AssetResolutionFailed),
		}?;
		let fee_asset =
			match_expression!(self.next()?, PayFees { asset: fee }, fee).ok_or(InvalidFeeAsset)?;
		let (fee_asset_id, fee_amount) = match fee_asset {
			Asset { id: asset_id, fun: Fungible(amount) } => Ok((asset_id, *amount)),
			_ => Err(AssetResolutionFailed),
		}?;
		// Check the fee asset is Ether (XCM is evaluated in Ethereum context).
		ensure!(fee_asset_id.0 == Here.into(), InvalidFeeAsset);
		ensure!(reserved_fee_asset_id.0 == Here.into(), InvalidFeeAsset);
		ensure!(reserved_fee_amount >= fee_amount, InvalidFeeAsset);
		Ok(fee_amount)
	}
