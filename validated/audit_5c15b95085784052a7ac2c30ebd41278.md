## Finding: `pallet-revive` lacks the `MigrationInProgress` guard that `pallet-contracts` enforces

### Summary
`pallet-revive` runs multi-block storage migrations (`v1`→`v4`) that change the on-disk shape of contract accounting data — including the deposit-currency switch in `v4` (native currency → `PGAS`) — but, unlike its sibling `pallet-contracts`, it has no per-pallet guard that blocks `call`/`instantiate`/`upload_code`/`remove_code`/`set_code` while a migration is mid-flight.

### Finding Description
`pallet-contracts` explicitly documents and enforces a pause during migrations: [1](#0-0) 

This is implemented via the `MigrationInProgress` storage item and the `ensure_no_migration_in_progress!` macro, which short-circuits `bare_call`/`bare_instantiate` (and, per the `migration_in_progress_works` test, the extrinsic-facing `call`, `instantiate`, `instantiate_with_code`, `upload_code`, `remove_code`, `set_code` calls) with `Error::MigrationInProgress` whenever `Migration::<T>::in_progress()` is true: [2](#0-1) [3](#0-2) [4](#0-3) 

`pallet-revive`, which is the newer EVM/PolkaVM contracts pallet, uses a different, generic Multi-Block-Migration module (`frame/migrations`) instead of a self-contained cursor+guard pattern: [5](#0-4) 

A repository-wide search for `MigrationInProgress`, `migration::in_progress`, or `ensure_no_migration` inside `substrate/frame/revive/**` returned **zero matches**, meaning there is no local, pallet-level check inside `pallet-revive`'s `call`, `instantiate`, `upload_code`, `remove_code`, or `set_code` dispatchables that rejects execution while `v1`→`v4` (e.g. `AccountInfoOf`/`CodeInfoOf` restructuring, or the `v4` deposit-currency migration from native currency to `PGAS`) is only partially applied.

The generic `frame/migrations` pallet's own documentation confirms that pausing transactions during an ongoing MBM is *not automatic* — it is left to upstream integrators: [6](#0-5) [7](#0-6) 

That is, `MultiStepMigrator::ongoing()` merely exposes a flag; whether user transactions are actually paused depends on whether the runtime wires up `SafeMode`/`TxPause` around `pallet-revive`'s calls. `pallet-contracts` does not rely on this external wiring — it enforces the block itself, in-pallet, unconditionally. `pallet-revive` has no equivalent in-pallet safeguard, so if a runtime integrator does not separately configure `TxPause`/`SafeMode` to cover `pallet_revive::Call::*`, user calls can execute against a storage layout that is only half-migrated (e.g. mixed `ContractInfoOf`/`AccountInfoOf` records, or accounts whose deposits have been moved to `PGAS` while others have not), corrupting deposit/balance accounting for contract accounts touched during the migration window.

### Impact Explanation
A half-migrated storage state read or written by `call`/`instantiate` during `v1`–`v4` can cause incorrect deposit or balance bookkeeping for contract accounts (e.g., stale `ContractInfoOf` vs. new `AccountInfoOf`, or deposits recorded in the wrong currency during the `v4` migration), leading to under/over-charged storage deposits, inconsistent account state, or fund-accounting corruption for end users interacting with contracts mid-upgrade. This matches the "runtime bug that compromises intended behavior" / "permanent user-fund... lock" impact classes in the gate.

### Likelihood Explanation
Likelihood is moderate and conditional: it only manifests during the multi-block window while a runtime is actively running a `pallet-revive` storage migration, and only if that runtime does not separately pause the `pallet_revive` calls via `TxPause`/`SafeMode` (which the `frame/migrations` docs explicitly call out as the integrator's responsibility, not something the pallet itself guarantees). Because `pallet-contracts` treats this as important enough to hard-code in-pallet, and `pallet-revive` provides no equivalent, this is a real regression in defense-in-depth for a pallet actively shipping new migrations (`v1`–`v4`).

### Recommendation
Add an in-pallet guard to `pallet-revive`, analogous to `ensure_no_migration_in_progress!` in `pallet-contracts`, that checks `T::Migrations`/the MBM cursor status (e.g. via `pallet_migrations::Pallet::<T>::ongoing_status()` or a dedicated local flag) and rejects `call`, `instantiate`, `upload_code`, `remove_code`, and `set_code` with a `MigrationInProgress`-style error whenever a `pallet-revive` migration is active, instead of relying solely on runtime-level `TxPause`/`SafeMode` configuration.

### Proof of Concept
1. Deploy a runtime with `pallet-revive` configured with `Migrations = (v1::Migration<T>, v2::Migration<T>, v3::Migration<T>, v4::Migration<T>)` but without wiring `TxPause`/`SafeMode` around `pallet_revive::Call::*`.
2. Trigger a runtime upgrade so the MBM cursor becomes `Active` for, e.g., the `v4` (deposit currency) migration.
3. While `pallet_migrations::Cursor` is still `Active` for `pallet-revive`'s migration ID (`PALLET_MIGRATIONS_ID = "pallet-revive-mbm"`), submit ordinary `pallet_revive::Call::call`/`instantiate` extrinsics against contract accounts that have not yet been migrated.
4. Observe that, unlike `pallet-contracts` (which would reject the call with `Error::MigrationInProgress` per `substrate/frame/contracts/src/tests.rs:655-690`), `pallet-revive` executes the call against the not-yet-migrated storage layout/deposit currency, producing inconsistent deposit/balance state for that account relative to accounts processed after migration completes.

macro_rules! ensure_no_migration_in_progress {
	() => {
		if Migration::<T>::in_progress() {
			return ContractResult {
				gas_consumed: Zero::zero(),
				gas_required: Zero::zero(),
				storage_deposit: Default::default(),
				debug_message: Vec::new(),
				result: Err(Error::<T>::MigrationInProgress.into()),
				events: None,

		}
	};

#[test]
fn migration_in_progress_works() {
	let (wasm, code_hash) = compile_module::<Test>("dummy").unwrap();

	ExtBuilder::default().existential_deposit(1).build().execute_with(|| {
		let _ = <Test as Config>::Currency::set_balance(&ALICE, 1_000_000);
		MigrationInProgress::<Test>::set(Some(Default::default()));

		assert_err!(
			Contracts::upload_code(
				RuntimeOrigin::signed(ALICE),
				vec![],
				None,
				Determinism::Enforced
			),
			Error::<Test>::MigrationInProgress,
		);
		assert_err!(
			Contracts::remove_code(RuntimeOrigin::signed(ALICE), code_hash),
			Error::<Test>::MigrationInProgress,
		);
		assert_err!(
			Contracts::set_code(RuntimeOrigin::signed(ALICE), BOB.clone(), code_hash),
			Error::<Test>::MigrationInProgress,
		);
		assert_err_ignore_postinfo!(builder::call(BOB).build(), Error::<Test>::MigrationInProgress);
		assert_err_ignore_postinfo!(
			builder::instantiate_with_code(wasm).value(100_000).build(),
			Error::<Test>::MigrationInProgress,
		);
		assert_err_ignore_postinfo!(
			builder::instantiate(code_hash).value(100_000).build(),
			Error::<Test>::MigrationInProgress,
		);
	});
}
