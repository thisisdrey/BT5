Confirmed: `deposit` in the vault contracts lacks a `(> inkind u0)` check, unlike `redeem` which explicitly checks `ERR-OUTPUT-ZERO`. This is a genuine rounding-to-zero analog to the reported bug class.

### Title
Deposit into vault can mint zero shares while assets are debited, causing permanent loss of a user's deposit - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
The `deposit` function in each vault contract (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) computes shares to mint via `convert-to-shares-preview`, which performs a truncating division (`mul-div-down`). Unlike the `redeem` function in the same contracts, which explicitly guards against a zero output with `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`, the `deposit` function has no equivalent check. When `min-out` is `0` (the default a caller may pass, or a naive frontend), a deposit whose computed share amount rounds down to `0` will still succeed: the user's underlying tokens are transferred into the vault (`receive-underlying`), `assets` is incremented, but `(ft-mint? zft inkind recipient)` mints `0` shares to the depositor.

### Finding Description
`convert-to-shares-preview` is defined identically across all vault contracts: [1](#0-0) 
```
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```
`mul-div-down` truncates: `(/ (* x y) z)` [2](#0-1) . Once the vault has accrued interest (via the liquidity index), the share price (`ta`/`ts`) exceeds `1.0`. For any deposit `amount` smaller than the current price-per-share (in the underlying token's smallest unit), `amount * ts / ta` truncates to `0`.

The `deposit` function then proceeds: [3](#0-2) 
```
(define-public (deposit (amount uint) (min-out uint) (recipient principal))
    (let (
      ...
      (inkind (convert-to-shares-preview amount)))
    (asserts! (not (get deposit states)) ERR-PAUSED)
    (asserts! (var-get initialized) ERR-INIT)
    (asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (>= inkind min-out) ERR-SLIPPAGE)
    (asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)

    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
    (var-set assets (+ current-assets amount))
    ...
    (ok inkind)))
```
There is no `(asserts! (> inkind u0) ...)` guard. Compare to `redeem` in the same contract, which does have this exact check: [4](#0-3) 
```
(asserts! (> amount u0) ERR-AMOUNT-ZERO)
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
(asserts! (>= inkind min-out) ERR-SLIPPAGE)
```
This asymmetry confirms the omission is a bug, not an intentional design choice — the same defensive check exists on the withdrawal path but is missing on the deposit path where it is equally necessary. If `min-out` is `0`, `(>= inkind min-out)` (i.e. `0 >= 0`) is satisfied, so the transaction proceeds: the depositor's underlying tokens are pulled in and the vault's `assets` var increases, but the depositor receives `0` zTokens and therefore has no claim on the deposited value. The deposited funds are effectively donated to existing zToken holders, permanently frozen from the depositor's perspective.

This mirrors the root cause described in the external report: an integer division (`volume / price` there, `amount * ts / ta` here) that truncates to zero when the numerator is smaller than the denominator's effective unit, silently consuming the caller's principal instead of reverting.

### Impact Explanation
This falls under "High – temporary freezing of funds" / effectively permanent loss of the depositor's principal for that specific deposit transaction, since the underlying is transferred and irrecoverable by the depositor (no shares were minted to redeem against). This lands squarely within the explicitly in-scope category of "vault share math and interest accrual."

### Likelihood Explanation
Medium. It requires: (1) the vault to have accrued at least some interest so `ta/ts > 1`, which happens naturally over time; and (2) the depositor (or an integrating frontend/contract) to submit `min-out = 0` (or a `min-out` that is itself below the rounding threshold) and an `amount` below the current price-per-share. For low base-unit deposits (e.g. dust amounts, or scripts/contracts computing deposit amounts programmatically) this is easily triggered, especially as the vault price-per-share grows with cumulative interest.

### Recommendation
Add the same zero-output guard used in `redeem` to `deposit` in every vault contract:
```
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed alongside the other assertions in `deposit`, before `receive-underlying`/`ft-mint?` execute.

### Proof of Concept
1. Deploy/initialize `v0-vault-usdc` and let it accrue interest via `borrow`/`accrue` cycles until `total-assets-preview / total-supply-preview` (price-per-share) is greater than `1` unit of the smallest USDC denomination times some factor N (e.g., price-per-share = 1.5 base units).
2. Caller calls `deposit(amount=1, min-out=0, recipient=caller)` where `amount < price-per-share` in base units such that `convert-to-shares-preview(1)` truncates to `0`.
3. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes because `0 >= 0`.
4. `receive-underlying` transfers `1` unit of USDC from caller into the vault; `(ft-mint? zft 0 recipient)` mints zero zUSDC to caller.
5. Caller has permanently lost `1` unit of USDC with no corresponding zToken claim, while `var-set assets` increases, effectively distributing that value to other zToken holders.
