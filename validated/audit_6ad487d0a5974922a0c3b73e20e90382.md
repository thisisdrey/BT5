### Title
Reconfigure-trigger check compares signer-tuple count instead of total slot count, letting stale slots outlive their config - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`StackerDBs::create_or_reconfigure_stackerdbs` decides whether to re-apply a StackerDB configuration to the on-disk replica by comparing the *number of signer entries* against the *number of persisted slots*, instead of comparing the *total slot count* against the persisted slot count. This is the same class of bug as the Pupnik report: a quantity that should track "how many units currently exist/are authorized" is computed from the wrong variable, so a decision that depends on that equality can silently fail, leaving the on-disk StackerDB permanently out of sync with the smart-contract-derived configuration.

### Finding Description
The reconfiguration gate is: [1](#0-0) 

```rust
} else if (new_config != stackerdb_config && !new_config.signers.is_empty())
    || (new_config == stackerdb_config
        && new_config.signers.len()
            != self.get_slot_versions(&stackerdb_contract_id)?.len())
{

    // (that second check on the length is needed in case the node is a victim of
    // #5142, which was a bug whereby a stackerdb could never shrink)
    if let Err(e) = self.reconfigure_stackerdb(&stackerdb_contract_id, &new_config) {
```

`new_config.signers` is `Vec<(StacksAddress, u32)>` — one entry per *signer*, where the `u32` is that signer's *slot count*. The correct total slot count is `new_config.num_slots()`: [2](#0-1) 

```rust
pub fn num_slots(&self) -> u32 {
    self.signers.iter().fold(0, |acc, s| acc + s.1)
}
```

`get_slot_versions` returns one entry per actual slot in the DB (i.e., the true total slot count), confirmed by the round-trip test that asserts `versions.len() == total slot count` after `create_stackerdb`/`reconfigure_stackerdb`: [3](#0-2) 

The comment explicitly says this second check exists specifically to catch the case where the config is unchanged (`new_config == stackerdb_config`) but the persisted slot count has drifted from what it should be (the previously-fixed "#5142" shrink bug). But the check compares `signers.len()` (count of signer *entries*) to the persisted slot count, not `num_slots()` (sum of each signer's slot count) to the persisted slot count. Whenever any signer has `slot_count != 1` — which is normal; e.g., the `.miners` StackerDB config assigns multiple slots per signer via `MINER_SLOT_COUNT`, as seen in: [4](#0-3) 

— `signers.len()` (e.g. `2`) will almost never equal the true persisted slot count (e.g. `2 * MINER_SLOT_COUNT`). The intended detection of "stuck/mismatched slot count" therefore never fires in the normal multi-slot-per-signer case, and the DB never gets reconfigured to correct any pre-existing over-allocation.

### Impact Explanation
If a replica's persisted slot table ever grows larger than the number of slots the current legitimate config calls for (e.g. due to a prior reconfiguration bug, a version skew during upgrade, or any state where `get_slot_versions().len() > new_config.num_slots()`), this broken equality check means `reconfigure_stackerdb` (which calls `shrink_stackerdb` to delete slots at/above the new total) will not be invoked as long as `new_config == stackerdb_config` — the node keeps serving/accepting writes to "phantom" slots that are no longer part of the intended signer set. Because `try_replace_chunk`/`validate_received_chunk` authorize writes purely against the DB's stored `SlotValidation.signer` for a given `slot_id` (not against the live `StackerDBConfig`), a signer who legitimately owned one of those now-out-of-range slots under an older/stale config can continue writing to it, and other peers can continue serving that stale slot's contents in inventory/chunk responses — non-canonical StackerDB state (i.e., a slot no longer authorized by the current signer set/config) being served as canonical to the rest of the network. This does not require any secret key or privileged role beyond an already-provisioned signer key for that stale slot.

### Likelihood Explanation
Medium. It requires a prior state where the persisted slot count exceeds the *desired* total slot count (the exact scenario the code comment references as "#5142"), which realistically occurs across signer-set/config transitions (e.g., reward-cycle rotations, `.miners` config changes) — precisely the multi-slot-per-signer configurations where this check is broken. The condition doesn't need attacker action to arise; it's a systemic latent bug that resurfaces the very class of issue the comment claims was already fixed.

### Recommendation
Change the drift-detection comparison to use total slot counts consistently:
```rust
new_config.num_slots() as usize != self.get_slot_versions(&stackerdb_contract_id)?.len()
```
instead of comparing `new_config.signers.len()`. Add a regression test with a config where at least one signer has `slot_count > 1` to ensure the shrink/reconfigure path is exercised correctly for multi-slot signers.

### Proof of Concept
1. Configure a StackerDB (e.g., `.miners`) whose `signers` vector has 2 entries, each with `slot_count = MINER_SLOT_COUNT` (>1), so `signers.len() == 2` but `num_slots() == 2 * MINER_SLOT_COUNT`.
2. Suppose the on-disk replica currently has more slots than `num_slots()` calls for (simulating drift, e.g. from an old config or the previously-fixed shrink bug).
3. On the next call to `create_or_reconfigure_stackerdbs` with `new_config == stackerdb_config` (no change), the check evaluates `new_config.signers.len() (2) != get_slot_versions().len() (> 2*MINER_SLOT_COUNT)` — this is coincidentally true here since 2 is unlikely to equal the actual slot count, so in this particular direction it *would* trigger — but the inverse failure mode is: if the persisted count happens to equal `signers.len()` by coincidence (e.g., 2 stale slots left over) while the true desired count is `2*MINER_SLOT_COUNT`, the check incorrectly reports "no mismatch" and skips reconfiguration entirely, leaving the extra/stale slots (or too few slots) unresolved. Because the two quantities being compared are never the same kind of count except in the degenerate 1-slot-per-signer case, the check's behavior is effectively arbitrary/incorrect for any real multi-slot-per-signer configuration, defeating its intended purpose as demonstrated by unit test coverage of `reconfigure_stackerdb`/`num_slots()` in [5](#0-4)  which only ever exercises the 1-slot-per-signer case and never triggers this exact branch under drift.
