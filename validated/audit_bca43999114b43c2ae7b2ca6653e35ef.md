Confirmed: `MAX-ASSETS` is `u64`, so the collateral bitmap (bits 0-63) and debt bitmap (bits 64-127) can each carry up to 64 registered assets [1](#0-0) . Any user can build their own position's collateral/debt lists up to `(list 64 ...)` for each side by depositing/borrowing dust amounts of every registered asset, and `find-collateral-amount`/`find-debt-scaled` are called once per asset inside `calculate-asset-notional-value`, which itself is `fold`ed over the full `assets` list inside `get-notional-evaluation` [2](#0-1) , making the liquidation-path valuation cost scale roughly quadratically (up to ~64×64 collateral lookups and ~64×64 debt lookups) with the number of assets a borrower chooses to hold.

### Title
Self-inflated position asset lists let a borrower price liquidation out of Stacks' read/write cost limits - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate()` (and every other health-checked entry point) must call `get-notional-evaluation`, which folds over the position's entire `assets` list and, for every asset, re-scans the *full* collateral and debt lists via `find-collateral-amount`/`find-debt-scaled` [3](#0-2) . Because `MAX-ASSETS` is 64 [4](#0-3)  and a user's collateral/debt lists are each sized `(list 64 ...)`, an ordinary borrower can, at essentially no cost to themselves, deposit a trivial amount of every registered asset as collateral and borrow a trivial amount of every registered debt asset, maximizing the population of their own position mask. This is directly analogous to the tBTC finding: a fixed per-block/per-transaction resource ceiling (there, Ethereum gas; here, Stacks' Clarity runtime read/write cost limits) is exceeded by a transaction whose size is influenced by an actor who benefits from the failure — except here the "attacker" is the very borrower whose position a liquidator is trying to act on.

### Impact Explanation
If the accumulated read/write cost of `liquidate()` (accrual over up to 64 debt + 64 collateral entries via `accrue-user-debts`/`accrue-user-collateral`, oracle price resolution for every enabled asset in `get-assets`, and the O(N²)-ish notional evaluation) exceeds the Stacks block cost limits, the transaction cannot be mined. A borrower who is underwater can pad their own position mask to make `liquidate` permanently unexecutable, keeping their under-collateralized position alive indefinitely. This blocks legitimate liquidation of bad debt, which the protocol otherwise handles through `socialize-debt-asset` [5](#0-4) . Uncollectable, un-liquidatable bad debt is a path to protocol insolvency (lenders unable to recover the funds backing the position), which lands squarely in the in-scope "protocol insolvency" Critical impact category.

### Likelihood Explanation
Exploitation requires no privileged access — an ordinary user simply calls `collateral-add`/`borrow` repeatedly with dust amounts of every listed asset. The main open question (which the report itself calls out as unavoidable) is whether the current fixed asset count (~12 assets live at the time of this repo's inspection: STX, sBTC, stSTX, USDC, USDH, stSTXbtc and their zToken variants) already pushes real transactions close to Stacks cost limits, and whether the DAO could grow the registry toward the `MAX-ASSETS` ceiling of 64. Precise measurement requires runtime cost benchmarking of `liquidate()` under a maximally-populated position, which is not obtainable from static code review alone.

### Recommendation
- Cap the number of *distinct* collateral/debt assets a single position may simultaneously hold to a small bound well below `MAX-ASSETS`, enforced in `collateral-add`/`borrow` at the point where `future-raw-mask`/`future-mask` is computed [6](#0-5) .
- Benchmark the Clarity runtime cost of `liquidate()`/`liquidate-multi` as a function of the number of distinct assets in a position, and document a safe maximum.
- Consider an alternative liquidation path that does not require evaluating the entire position notional in one transaction (e.g., a per-asset liquidation step that liquidators can call repeatedly, since a position's asset count is now attacker (borrower)-controlled rather than fixed.

### Proof of Concept
1. Borrower deposits `u1` of collateral for every one of the (up to 64) registered collateral-enabled assets via repeated `collateral-add` calls, and borrows `u1` of every debt-enabled asset via repeated `borrow` calls, each of which is a small enough transaction to pass validation individually.
2. Borrower's stored `mask` in `market-vault` now spans the maximum population across both the collateral (bits 0-63) and debt (bits 64-127) halves.
3. Borrower manipulates price exposure (or simply waits for market movement) so their position becomes liquidatable.
4. Any liquidator's call to `liquidate()` must now execute `get-liquidation-position`, `get-full-position`, `accrue-user-debts`, `accrue-user-collateral`, `get-assets` (oracle resolution for every enabled asset), and `get-notional-evaluation` (fold with nested `find-collateral-amount`/`find-debt-scaled` scans) over the full, maximized asset list — at a runtime cost that, if it approaches or exceeds Stacks' per-transaction/per-block cost limits, causes the transaction to be rejected, leaving the position permanently un-liquidatable.

              id: uint, addr: principal, decimals: uint,
              oracle: { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint },
              collateral: bool, debt: bool, price: uint })
          (acc { clist: (list 64 { aid: uint, amount: uint }),

                  coll-total: uint,
                  debt-total: uint }))

        (price (get price asset-entry))
        (decimals (get decimals asset-entry))
        (collateral-list (get clist acc))
        (debt-list (get dlist acc))
        (coll-amount (find-collateral-amount collateral-list asset-id))
        (coll-notional (if (> coll-amount u0)

                             (normalize (* actual price) decimals true))
                           u0)))

    { clist: collateral-list,
      dlist: debt-list,
      coll-total: (+ (get coll-total acc) coll-notional),
      debt-total: (+ (get debt-total acc) debt-notional) }))
