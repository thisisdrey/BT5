### Title
Lockfile merge tool silently overwrites trusted `facts` entries with attacker-supplied values from an untrusted merged-in `MODULE.bazel.lock` - (File: scripts/bazel-lockfile-merge.jq)

### Summary
Bazel's `module_ctx.facts` mechanism lets a module extension record data (e.g. checksums of an "immutable" artifact) that Bazel persists verbatim in `MODULE.bazel.lock` and hands back to the extension on later evaluations *without re-verification*, explicitly as a substitute for a download checksum. The `scripts/bazel-lockfile-merge.jq` helper — the shipped tool for reconciling `MODULE.bazel.lock` files across branches/PRs in CI — merges `facts` from multiple lockfiles with silent last-wins semantics, with no detection of value conflicts for the same key. An attacker who controls the content of one of the lockfiles being merged (e.g. a PR branch lockfile that CI merges against the trusted base) can inject a `facts` entry that overwrites a previously-recorded trusted fact (such as a checksum mapping), and this corrupted value becomes the "trusted" state consumed by the extension on subsequent evaluations, bypassing the very checksum-substitute guarantee `facts` was designed to provide.

### Finding Description
`docs/external/extension.mdx` documents that `facts` is meant to record "effectively immutable data obtained from outside the build... most commonly from the network, but you don't have a checksum available to guard the download" — e.g. "a mapping from version numbers of some SDK to ... download URL and checksum." [1](#0-0)  Facts are "always persisted in the lockfile," survive extension code changes, and Bazel "assumes that two different `facts` dicts produced by two different evaluations of the same extension can be shallowly merged... as if by using the `|` operator," documented as only "partially enforced" because `module_ctx.facts` doesn't support enumeration. [2](#0-1) 

The repository ships `scripts/bazel-lockfile-merge.jq`, a jq script explicitly designed to merge an arbitrary number of `MODULE.bazel.lock` files (as arise from concurrent PRs/branches in CI) into one. Its `shallow_merge` helper uniquifies values across the input lockfiles and then does an `add` (i.e. last-wins dict merge) with no check that colliding keys carry identical values: [3](#0-2) 

This last-wins merge is applied directly to `facts` per extension ID: entries are grouped by extension ID and their value maps are shallow-merged with the same last-wins logic, after only filtering by `factsVersion` (schema version), not by content agreement: [4](#0-3) 

Because facts entries "uniquely determine the value" only as a documented expectation on well-behaved extensions — not something the merge tool verifies — a malicious/compromised branch lockfile merged in this pipeline can carry a `facts` entry with the same key as a legitimate one already recorded (e.g. `"1.26.1": {"hash": "hello"}` as seen in the test fixtures) but a different, attacker-chosen value, and depending on ordering in the merged array it silently overrides the previously-trusted value: [5](#0-4) 

Once merged into the checked-in `MODULE.bazel.lock`, this corrupted fact is fed straight back to the extension via `module_ctx.facts` on the next evaluation, without any network fetch or checksum validation — that is the entire point of the `facts` feature. [6](#0-5) 

### Impact Explanation
An extension author using `facts` to cache a checksum/URL mapping in lieu of a per-download hash (the exact use case the docs recommend) can be tricked, via CI-side lockfile merging, into trusting an attacker-supplied checksum/URL pair for a version key that previously mapped to a legitimate value. Since the whole purpose of `facts` is to avoid re-verifying content over the network, once the poisoned fact lands in the merged, trusted `MODULE.bazel.lock`, it is silently propagated to every subsequent build that consumes that lockfile — a lockfile/cache-poisoning outcome that defeats the pinned-checksum-equivalent guarantee `facts` is documented to provide, matching the "reset without removing/validating prior state" bug class from the report (stale trusted state is blindly overwritten rather than reconciled).

### Likelihood Explanation
Requires a CI/merge workflow that actually invokes `bazel-lockfile-merge.jq` across lockfiles originating from different trust levels (e.g. merging a fork/PR branch's lockfile against main) — which is precisely the tool's documented purpose. No access to the victim's machine, credentials, or root-repo BUILD/.bzl files is needed; only the ability to submit a branch/PR whose `MODULE.bazel.lock` contains an attacker-chosen `facts` value for an existing key.

### Recommendation
The merge script should reject (rather than silently pick a winner for) conflicting `facts` values for the same key across input lockfiles, since the documented invariant is that "the key uniquely determines the value." At minimum, it should fail loudly on such conflicts (similar to how it already discards facts on `factsVersion` mismatch) so a human must resolve the discrepancy rather than the tool silently trusting the last file in the merge order.

### Proof of Concept
Given three lockfiles merged via `jq -s -f scripts/bazel-lockfile-merge.jq base.lock attacker.lock`, where:
- `base.lock` contains `"facts": {"//:extension.bzl%ext": {"1.26.1": {"hash": "legit_hash"}}}`
- `attacker.lock` (from an untrusted branch) contains `"facts": {"//:extension.bzl%ext": {"1.26.1": {"hash": "malicious_hash"}}}`

the merge in `shallow_merge` at [7](#0-6)  produces `"1.26.1": {"hash": "malicious_hash"}` in the output lockfile with no error or warning, since `stable_unique | add` simply lets the later occurrence win. This corrupted lockfile, once committed, is consumed by `module_ctx.facts` on the next extension evaluation, per the documented `facts` field of `module_ctx` [6](#0-5) , silently substituting the attacker's value wherever the extension trusted the cached hash to skip verification.

```text
# Given an array of objects, shallowly merges the result of applying f to each
# object into a single object, with a few special properties:
# 1. Values are uniquified before merging and then merged with last-wins
#    semantics. Assuming that the first value is the base, this ensures that
#    later occurrences of the base value do not override other values. For
#    example, when this is called with B A1 A2 and A1 contains changes to a
#    field but A2 does not (compared to B), the changes in A1 will be preserved.
# 2. Object keys on the top level are sorted lexicographically after merging,
#    but are additionally split on ":". This ensures that module extension IDs,
#    which start with labels, sort as strings in the same way as they due as
#    structured objects in Bazel (that is, //python/extensions:python.bzl
#    sorts before //python/extensions/private:internal_deps.bzl).
def shallow_merge(f):
  map(f) | stable_unique | add | to_entries | sort_by(.key | split(":")) | from_entries;
```
