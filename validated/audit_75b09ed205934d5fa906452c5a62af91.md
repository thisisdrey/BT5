### Title
Missing boundary check in `RewardsDistributor._calculateTokenDelta` lets an account accrue rewards equal to its full token balance when the token index is exactly `INITIAL_INDEX` - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenDelta` uses a stored `accountIndexOf[token][account]` as the lower bound when computing accrued rewards. When the stored index is `0` (account never touched the token), the code falls back to `INITIAL_INDEX` — but only if `_tokenIndex > INITIAL_INDEX`. When the global token index is still exactly `INITIAL_INDEX` (i.e. the first block after a reward token is activated, before `deltaTimestamps > 0`), the fallback is skipped, `_deltaIndex` becomes `1e18`, and the account is credited `balance * 1.0` reward tokens instantly. This is the same bug class as CVE-2024-53147: a cached/index hint (`accountIndexOf == 0`) resolves to an invalid position (index `0` instead of `INITIAL_INDEX`) because a boundary value (`_tokenIndex == INITIAL_INDEX`) is not treated as an "empty/not-yet-accrued" state.

### Finding Description [1](#0-0) 

```solidity
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

When `_tokenIndex == INITIAL_INDEX` exactly, a fresh account gets `_accountIndex = 0`, so `_deltaIndex = 1e18` and `wadMul(balance, 1e18) = balance`. The window exists because `_updateTokenSpeed` sets `tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` [2](#0-1) , and `_calculateTokenIndex` returns `(0,0)` when `deltaTimestamps == 0`, leaving the index pinned at `INITIAL_INDEX` for the rest of that timestamp [3](#0-2) .

`updateBeforeMintOrBurn(token_, account_)` is permissionless ("may be called by anyone to update stored indexes") and triggers `_updateTokensAccruedOf` whenever `index > 0` [4](#0-3) . `claimRewards(accounts, tokens)` is also permissionless and pays out `tokensAccruedOf` [5](#0-4) . No modifier, health check, pause flag, or reentrancy guard stops the path (the `nonReentrant` guard is irrelevant to a single-call claim).

### Impact Explanation
Direct theft of unclaimed yield / reward funds. An attacker with a large `DepositToken` (or `DebtToken`) balance calls `updateBeforeMintOrBurn(token, attacker)` in the same block that the governor activates reward speed for that token, accrues `tokensAccruedOf[attacker] += depositTokenBalance`, then calls `claimRewards` to drain the distributor's reward-token balance up to that amount. With a large deposit (which also earns boosted balances through leverage), the entire `rewardToken` balance of the distributor can be extracted in two calls.

### Likelihood Explanation
- The exploit window is one timestamp per newly activated reward token (or per `tokens.push` activation where `index` was previously `0`).
- `updateTokenSpeed`/`updateTokenSpeeds` governor transactions are publicly observable; the attacker only needs to land `updateBeforeMintOrBurn` in the same block (backrun). On L2 deployments (Base/Optimism in `deployments/`) ordering a tx immediately after a known governor tx is feasible.
- The attacker must hold a deposit/debt token balance beforehand — a normal, unprivileged action — and can size it arbitrarily via a regular `deposit` or SmartFarming leverage.
- No privileged/compromised role, oracle manipulation, or external precondition beyond the routine governance activation of a reward token is required.

### Recommendation
Treat the uninitialized-account case by comparison against the token's *activation* index rather than the hardcoded constant, or clamp at zero:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex > INITIAL_INDEX ? INITIAL_INDEX : _tokenIndex;
}
```

Equivalently, record each token's initial index in `TokenState` and use `if (_accountIndex == 0) _accountIndex = _initialIndex;`, or default missing `accountIndexOf` to `INITIAL_INDEX` unconditionally (`if (_accountIndex == 0) _accountIndex = INITIAL_INDEX;`) — since a real `_tokenIndex` below `INITIAL_INDEX` is impossible, `_tokenIndex - INITIAL_INDEX` would then correctly be `0` at the boundary.

### Proof of Concept
Hardhat sketch (fork or local deployment of `Pool`, `DepositToken`, `RewardsDistributor`, reward `IERC20`):

```ts
// Setup: pool, depositToken (vX), rewardsDistributor funded with rewardToken
await depositToken.connect(attacker).deposit(largeAmount); // attacker holds balance B

// Governor activates reward speed for the deposit token
await distributor.connect(governor).updateTokenSpeed(depositToken.address, speed);

// Same block / same timestamp: index is still INITIAL_INDEX
await distributor.connect(attacker).updateBeforeMintOrBurn(depositToken.address, attacker.address);

// tokensAccruedOf[attacker] == B (balance * wadMul(1e18))
expect(await distributor.tokensAccruedOf(attacker.address)).to.equal(B);

await distributor.connect(attacker).claimRewards(attacker.address);
// attacker received min(B, rewardTokenBalance) reward tokens for zero elapsed time
```

Deterministic reproduction: in Foundry, `vm.warp` is not needed — placing the `updateTokenSpeed` call and the `updateBeforeMintOrBurn` call in the same block (or same `vm.prank` sequence without time advance) guarantees `deltaTimestamps == 0` and `index == INITIAL_INDEX`, so `_calculateTokenDelta` returns `balance` as the delta.
