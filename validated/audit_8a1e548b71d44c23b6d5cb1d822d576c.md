Based on my research, I found a solid protocol-level analog to the "predictable price hash" bug class in nearcore's promise-yield/resume mechanism (NEP-536-style asynchronous callbacks).

### Title
Predictable `data_id` allows front-running/impersonation of promise-yield callback resumption - ([File: runtime/runtime/src/ext.rs])

### Summary
NEAR's yield/resume host-function mechanism (`promise_yield_create` / `promise_yield_resume`) generates a `data_id` that acts as the sole capability token gating who can resume a suspended promise with data. This `data_id` is derived entirely from deterministic, publicly-known inputs (transaction hash, block height, and a monotonic counter) with no unpredictable, per-instance secret entropy, mirroring the audited bug where `keccak256(price)` was fully guessable because it lacked salt.

### Finding Description
`generate_data_id` computes the data_id as: [1](#0-0) 
which calls `create_receipt_id_from_action_hash(action_hash, block_height, data_count)`, itself built on `create_hash_index`: [2](#0-1) [3](#0-2) 

`create_hash_index` (line 353 onward) hashes only `base` (a transaction/receipt/action hash), `block_height`, and an incrementing `salt` counter — no chain randomness (e.g. VRF `random_value`) or any secret is mixed in. Every one of these inputs (`tx_hash`, `block_height`, `receipt_index`, `action_index`, `data_count`) is either known before submission (the signer computes the transaction hash off-chain) or becomes public the moment the transaction/receipt is included in a chunk, well before the corresponding `PromiseYield` receipt is actually processed by the receiving shard.

`create_promise_yield_receipt` in `RuntimeExt` returns this same predictable `data_id` to the contract and simultaneously writes to trie a "yielded" marker keyed on `(receiver_id, data_id)`: [4](#0-3) 

`submit_promise_resume_data` — the implementation backing the `promise_yield_resume` host function that any contract execution can invoke — only checks that a pending yield exists for the given `(account_id, data_id)` pair; it performs no check that the caller is the intended data provider, relying implicitly on `data_id` being an unguessable secret: [5](#0-4) 

Because `data_id` is fully computable from public chain data ahead of time (just like the un-salted `keccak256(price)` hash in the report), the secrecy the design implicitly relies on to gate `submit_promise_resume_data` does not exist. Any party who can trigger the resuming contract's public method (a common "oracle callback" contract pattern built on this primitive) can precompute the exact `data_id` for a target yield receipt without ever being told it, and race the legitimate resolver to submit forged resume data.

### Impact Explanation
Contracts built on the yield/resume primitive (e.g., oracle/price-feed patterns, cross-contract "wait for external answer" flows) depend on `data_id` being an unpredictable capability token analogous to the audited "hidden price hash." Since it is fully predictable, an attacker can front-run the legitimate resumer and inject attacker-controlled data into the resumed promise. Depending on what the resumed contract logic does with that data (e.g., release funds, mint/settle based on the "trusted" callback value), this enables authorization bypass / state manipulation and potential theft or loss of funds mediated by that contract — the same class of exploitation the report describes (recovering/spoofing values meant to be secret until reveal).

### Likelihood Explanation
Exploitation only requires deriving the deterministic `data_id` formula (public, no secret material) and calling the resuming account's exposed method before the legitimate provider does — no protocol-level authorization bypass or special access is needed at the runtime/host-function level, only that a target contract's callback-resume entry point does not itself add caller authentication (a common gap for contracts that assume `data_id` secrecy is enough, exactly the assumption this design invites).

### Recommendation
Mix protocol-level or receipt-level unpredictable entropy that isn't known before receipt processing into `data_id` generation (e.g., include the destination shard's per-block randomness/VRF output, analogous to `get_receipts_shuffle_salt`'s use of `prev_hash`, rather than only `action_hash`/`block_height`/counter), and/or document and enforce that host-implemented yield/resume must not be treated as capability-secure without caller identity checks performed by the contract.

### Proof of Concept
1. Observe or predict a transaction from account `A` calling a contract method that internally invokes `promise_yield_create`. Because `create_hash_index` inputs (`tx_hash`, `block_height`, `receipt_index`/`action_index`, `data_count`) are all derivable from the signed transaction bytes and the block height at which it will execute, precompute `data_id = create_receipt_id_from_action_hash(action_hash, block_height, data_count)` off-chain, matching [1](#0-0) .
2. Before the legitimate off-chain oracle/service responds, submit a transaction calling the target contract's public "resume/fulfill" method with the precomputed `data_id` and attacker-chosen payload, triggering `submit_promise_resume_data`, whose only check is state existence of the yield marker written in step 0's [5](#0-4) , not caller identity.
3. The forged data resumes the promise; the resuming contract logic proceeds on attacker-controlled input instead of the genuine provider's.

Note: I could not fully verify within available context whether any in-tree "reference" oracle/yield-consumer contract exists that lacks its own caller authentication on the resume entry point — that would need to be confirmed to fully weaponize this at the application layer; the protocol-level predictability of `data_id` itself is confirmed from the cited runtime code.

        let has_yield_status_in_state =
            has_promise_yield_status(self.trie_update, &self.account_id, data_id)
                .map_err(wrap_storage_error)?;

        if has_yield_receipt_in_state || has_yield_status_in_state {
            self.receipt_manager.create_promise_resume_receipt(data_id, data);
            set_promise_yield_status(
                &mut self.trie_update,
                &self.account_id,
                data_id,
                PromiseYieldStatus::ResumeInitiated,
            );
            return Ok(true);
        }

        Ok(false)
    }

/// Creates a new action_hash based on original receipt id.
pub fn create_action_hash_from_receipt_id(
    receipt_id: &CryptoHash,
    block_height: BlockHeight,
    action_index: usize,
) -> CryptoHash {
    // Action hash uses the same input as a new receipt ID, so to avoid hash conflicts we use the
    // salt starting from the `u64` going backward.
    let salt = u64::MAX.wrapping_sub(action_index as u64);
    create_hash_index(receipt_id, block_height, salt)
}

) -> CryptoHash {

}

pub fn create_random_seed(action_hash: CryptoHash, random_seed: CryptoHash) -> Vec<u8> {
    // Generates random seed from random_seed and action_hash.
    // Since every action hash is unique, the seed will be unique per receipt and even
    // per action within a receipt.
    const BYTES_LEN: usize = size_of::<CryptoHash>() + size_of::<CryptoHash>();
    let mut bytes: Vec<u8> = Vec::with_capacity(BYTES_LEN);
    bytes.extend_from_slice(action_hash.as_ref());
    bytes.extend_from_slice(random_seed.as_ref());
    let res = hash(&bytes);
    res.as_ref().to_vec()
}
