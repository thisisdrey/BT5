### Title
Attachment gossip response is not verified against its requested content hash - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts any `Attachment` returned in a `GetAttachmentResponse` as long as it decodes successfully, without checking that `response.attachment.hash() == request.content_hash`. A malicious peer answering a `GET /v2/attachments/<hash>` request can return arbitrary content, which gets inserted into `context.attachments` regardless of whether it matches the requested hash.

### Finding Description
In `extend_with_attachments` [1](#0-0) , for each `(request, response)` pair in `results.succeeded`, the code only checks that `response.decode_atlas_get_attachment()` succeeds before doing `self.attachments.insert(response.attachment)`. There is no comparison between `response.attachment.hash()` and `request.content_hash`, the value that was actually requested (set from `content_hash: content_hash.clone()` when the request was built in `get_prioritized_attachments_requests` [2](#0-1) ). Any remote peer that is a source for a given attachment request can therefore respond with unrelated bytes that decode into a valid `Attachment` structure but hash to a different `Hash160`, and that mismatched attachment is unconditionally inserted into the batch's `attachments` set, while the report is marked as a "successful request" — silently accepted rather than rejected.

Downstream, attachment resolution is keyed by the *actual* content hash of what was stored (via lookups keyed on `attachment.hash()`), so the originally requested `content_hash` is never satisfied. This means the request for that specific piece of content remains perpetually unresolved (since the peer's malicious response consumed the "successful" download slot for that request round), while attacker-controlled content sits in the local attachments store under its own (different) hash.

### Impact Explanation
This matches the "attachment/BNS data mismatch" High-severity category: a node can be made to store/relay attacker-supplied blob content that was never the content committed to canonically for the hash that was actually requested, and the correct attachment for the originally-requested hash is never fetched (denial of resolution for that specific attachment/BNS zonefile). This is repeatable per attachment request and requires only that the attacker's peer be listed as a source (i.e., that it advertised having the attachment in its inventory), which is attacker-controlled gossip data with no privileged role needed.

### Likelihood Explanation
The attacker just needs to run an ordinary P2P peer that (a) advertises in its `AttachmentsInventory` response that it has the attachment at the relevant page/index, and (b) responds to the subsequent `GET /v2/attachments/<hash>` with a well-formed `GetAttachmentResponse` containing different content. No secret, admin role, or privileged access is required — this is purely a gossip/RPC response with no cross-check to what was requested.

### Recommendation
In `extend_with_attachments`, after `decode_atlas_get_attachment()` succeeds, explicitly verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; if the hash doesn't match, treat it as a failed request (`report.bump_failed_requests()`) and optionally penalize/blacklist the peer for serving mismatched content.

### Proof of Concept
Rust test in `stackslib::net::atlas::download`:
1. Build an `AttachmentRequest` with a known `content_hash` (e.g., hash of `b"expected"`).
2. Construct a fake `HttpResponse`/`GetAttachmentResponse` whose `attachment.content = b"attacker-controlled"` (a different hash) but which still parses successfully via `decode_atlas_get_attachment()`.
3. Insert `(request, Some(response))` into `results.succeeded` and call `AttachmentsBatchStateContext::extend_with_attachments`.
4. Assert that `context.attachments` contains the attacker's `Attachment` (whose `.hash() != request.content_hash`), and that `report.bump_successful_requests()` was called for that peer — proving the mismatch is accepted rather than rejected. [3](#0-2)

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
