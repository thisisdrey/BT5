## Title
Replay-window check/update race in `ConnectionState.Decrypt`/`VerifyRelay` allows duplicate acceptance of the same message counter - (File: connection_state.go)

## Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` validate a message counter against the replay window with `window.Check`, release the lock, perform the (comparatively expensive) AEAD decrypt, and only afterward re-acquire the lock to call `window.Update`, which is what actually marks the counter as seen. [1](#0-0) [2](#0-1) 

## Finding Description
This mirrors the UMA `resolveProposal` bug class: a state-changing action is gated by a read of prior state (`resolved` / "already seen"), but the actual state mutation that prevents recurrence (marking `resolved` / marking the counter received) happens later and is not atomic with the check. In `Proposer.resolveProposal`, checking "has the oracle resolved" without flagging the proposal as paid let the same proposal be resolved (and paid) repeatedly. In `ConnectionState.Decrypt`/`VerifyRelay`, `window.Check` reads "has this counter been seen" and `window.Update` is what marks it seen, but between the two calls the `decryptLock` is dropped:

```go
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)
cs.decryptLock.Unlock()
if !result {
    return nil, ErrAlreadySeen
}
out, err = cs.dKey.DecryptDanger(...)
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)
cs.decryptLock.Unlock()
``` [1](#0-0) 

If two packets carrying the same `messageCounter` (or a duplicated/replayed on-wire packet delivered twice before the first `Update` completes) are processed concurrently by the code path that calls `Decrypt`/`VerifyRelay`, both can pass `window.Check` (since neither has called `Update` yet), both proceed to `DecryptDanger`, and both would report success up the stack — the second `Update` call would then correctly return `false`/`ErrAlreadySeen`, but only after the duplicate ciphertext has already been decrypted and (depending on caller) potentially delivered once already accepted as valid before the late rejection. This is the same "check without atomically committing state" flaw as the `resolveProposal` bug: the guard exists, but the window between check and mark-as-done is exploitable.

`Bits.Check` (read-only) and `Bits.Update` (the actual mutating anti-replay bookkeeping) are explicitly separate operations by design [3](#0-2) [4](#0-3) , and `ConnectionState.Decrypt`/`VerifyRelay` is the only place in the codebase pairing them together, and it does so non-atomically across an unlocked AEAD operation.

## Impact Explanation
If this race is reachable (i.e., if the caller of `Decrypt`/`VerifyRelay` can invoke it concurrently for the same `ConnectionState`/counter, e.g. via relay forwarding paths or multiple UDP-read workers feeding the same tunnel), an attacker who can inject a duplicate on-wire packet (a captured, previously-seen ciphertext for a still-valid session) could cause the anti-replay window's "seen" guarantee to be bypassed for a brief window, resulting in duplicate acceptance/processing of a replayed encrypted frame — a traffic-replay class impact.

## Likelihood Explanation
This requires two invocations of `Decrypt`/`VerifyRelay` for the same `ConnectionState` to race in a way that both pass `Check` before either calls `Update`; I was not able to confirm from static reading of the code whether the codebase currently dispatches inbound UDP packets for a single tunnel across multiple concurrent goroutines that could call `Decrypt` in parallel for the same hostinfo (this would need runtime/architecture verification of `readOutsidePackets`/the receive loop, which I could not fully trace before running out of investigation budget). Without confirmed concurrent dispatch onto the same `ConnectionState`, the practical likelihood is uncertain/low; the code pattern itself is nonetheless a real check/update TOCTOU gap.

## Recommendation
Make the anti-replay check-and-mark atomic: hold `decryptLock` (or perform an atomic compare-and-set on the bitmap) across both the `Check` and `Update` operations, or better, merge them into a single `CheckAndReserve`-style call executed under one lock acquisition before doing the AEAD decrypt, only finalizing (or rolling back) the reservation based on decrypt success. This removes the window in which two callers can both observe "not yet seen" for the same counter.

## Proof of Concept
Not independently verified against a live build in this session — the theoretical PoC would be: hold two goroutines both calling `ConnectionState.Decrypt(l, N, ...)` with the same `messageCounter=N` for the same `ConnectionState`, timed so goroutine B calls `window.Check` after goroutine A's `Check` but before A's `Update`; both then proceed into `DecryptDanger`. Confirming real-world exploitability requires establishing whether the interface's packet-receive path can dispatch two packets for the same hostinfo onto separate goroutines concurrently, which I could not confirm within the available investigation.

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
