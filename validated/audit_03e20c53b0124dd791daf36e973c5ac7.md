## Analysis: Unbounded Cycle-Iteration Reward Computation in `MortgageService`/Legacy Reward Path

Unlike the Sherlock report's example, java-tron's actuators generally cap unbounded loops explicitly (`MAX_VOTE_NUMBER=30` in `VoteWitnessActuator`, `MAX_MATCH_NUM=20` in `MarketSellAssetActuator`, `UNFREEZE_MAX_TIMES=32` in `UnfreezeBalanceV2Actuator`, `MAX_SIZE` limits in the `BatchValidateSign`/`ValidateMultiSign` precompiles, and the 8-active/5-key caps in `AccountPermissionUpdateActuator`). However, one legacy reward-computation path lacks any such cap.

### Title
Unbounded per-cycle reward computation loop in legacy `getOldReward` path reachable from ordinary vote/freeze/unfreeze/withdraw transactions - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Finding Description
`MortgageService.withdrawReward(byte[] address)` is invoked by ordinary, unprivileged transactions any time an account votes, freezes, or unfreezes balance, or explicitly withdraws rewards (e.g. `VoteWitnessActuator`, `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, `WithdrawBalanceActuator`, and the corresponding TVM native-contract processors via `VoteRewardUtil.withdrawReward`). [1](#0-0) 

Internally this calls `computeReward(beginCycle, endCycle, accountCapsule)`, which — when `beginCycle` is still below `getNewRewardAlgorithmEffectiveCycle()` — falls back to `getOldReward`: [2](#0-1) 

```java
private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
  if (dynamicPropertiesStore.allowOldRewardOpt()) {
    return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
  }
  long reward = 0;
  for (long cycle = begin; cycle < end; cycle++) {
    reward += computeReward(cycle, votes);
  }
  return reward;
}
```

When the `allowOldRewardOpt` chain parameter is not enabled, this loop iterates once per maintenance cycle between the account's `beginCycle` (last time it interacted/withdrew) and the `endCycle` (current cycle), and for every cycle it calls `computeReward(cycle, votes)` which itself iterates over every SR the account voted for: [3](#0-2) 

This is directly analogous to `claimWithdrawalsForManyEpochs` iterating an unbounded, caller-influenced range of "epochs": here the range is the number of maintenance cycles (roughly one every 6 hours by default) that have elapsed since the account last interacted with the chain, multiplied by the number of SR votes cast — with no `MAX_*` cap comparable to `MAX_VOTE_NUMBER`/`MAX_MATCH_NUM`/`UNFREEZE_MAX_TIMES` elsewhere in the codebase.

The identical unbounded pattern also exists in the TVM-facing `VoteRewardUtil`/native-contract path used by contract calls, though that path funnels through `computeReward` in `Repository`-based form rather than `getOldReward` directly — the risk is concentrated in the direct actuator path shown above.

### Impact Explanation
Any account that accumulates a large gap between `beginCycle` and the current cycle (simply by not interacting for a long period, which requires no special privilege and costs nothing) will trigger an O(cycles × votes) computation the next time it votes, freezes, unfreezes, or withdraws — all ordinary, permissionless transaction types. Because this computation runs during `Manager` block application inside the actuator's `execute()`/`validate()` path (not inside the TVM), it is **not metered by CPU/energy checks** the way TVM opcodes are; it runs to completion as native Java code during block processing. A sufficiently large cycle gap (attainable simply by waiting, or amplified by many long-dormant accounts interacting in the same block) can materially slow block application, creating a risk of processing delays across the network — a resource-exhaustion condition on block-producing/verifying nodes rather than a mere reverted transaction.

### Likelihood Explanation
The path is reached by extremely common, everyday transaction types (vote, freeze, unfreeze, withdraw) with no special conditions other than elapsed cycles since last interaction, which occurs naturally and can also be induced by an attacker who simply refrains from interacting with a controlled account for an extended period before finally triggering the computation. The guard (`allowOldRewardOpt`) is a committee-controlled chain parameter, so the severity of this path depends on whether that optimization has been activated on the target network.

### Recommendation
Cap the number of cycles processed per call (similar to `UNFREEZE_MAX_TIMES`/`MAX_VOTE_NUMBER`), or force incremental/periodic settlement of rewards (e.g., during `Manager`'s per-cycle maintenance) so `beginCycle`/`endCycle` gaps cannot grow unbounded before a user-triggered transaction has to walk them. Alternatively, ensure `allowOldRewardOpt` (which switches to the O(votes) `RewardViCalService` algorithm) is always active before mainnet exposure, and add a defensive maximum cycle-gap check with an explicit `ContractValidateException` similar to other bounded actuators in the codebase.

### Proof of Concept
1. Freeze balance and vote for one or more SRs from a fresh account so `beginCycle`/`endCycle` are initialized.
2. Do not interact with the account for a long period so that `currentCycle` (advanced every maintenance cycle globally) grows far past the account's `beginCycle`.
3. Send any ordinary transaction that triggers `mortgageService.withdrawReward(address)` (e.g., `VoteWitnessContract`, `UnfreezeBalanceContract`, `UnfreezeBalanceV2Contract`, or `WithdrawBalanceContract`).
4. If `allowOldRewardOpt` is not enabled, `getOldReward` executes a loop over every elapsed cycle multiplied by every voted SR with `BigInteger`/floating-point work per iteration, all inside actuator execution during block application, with no upper bound check comparable to the caps found elsewhere in the codebase (`MAX_VOTE_NUMBER`, `MAX_MATCH_NUM`, `UNFREEZE_MAX_TIMES`).

```java
  public void withdrawReward(byte[] address) {
    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return;
    }
    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;
        logger.info("Latest cycle reward {}, {}.", beginCycle, account.getVotesList());
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      delegationStore.setBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
      adjustAllowance(address, reward);
    }
    delegationStore.setBeginCycle(address, endCycle);
    delegationStore.setEndCycle(address, endCycle + 1);
    delegationStore.setAccountVote(endCycle, address, accountCapsule);
    logger.info("Adjust {} allowance {}, now currentCycle {}, beginCycle {}, endCycle {}, "
            + "account vote {}.", Hex.toHexString(address), reward, currentCycle,
        beginCycle, endCycle, accountCapsule.getVotesList());
  }
```

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```
