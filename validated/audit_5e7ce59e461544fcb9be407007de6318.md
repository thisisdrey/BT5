### Title
Legacy floating-point Bancor exchange math can be exploited to drain AMM pool reserves - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The Yearn/Euler report describes indirect fund loss caused by a bug-class in another protocol's value-accounting math that let an attacker extract more value than was deposited (donation/precision-based insolvency). The closest reachable analog in java-tron is the TRX/token AMM exchange (`ExchangeTransactionActuator` / `ExchangeInjectActuator` / `ExchangeWithdrawActuator`), whose pricing math is delegated to `ExchangeCapsule.transaction()`, which by default uses `ExchangeProcessor` — a `double`-based Bancor-formula implementation — instead of the newer `SafeExchangeProcessor` (`BigDecimal`-based) unless the `allowHardenExchangeCalculation` chain parameter has been switched on.

### Finding Description
`ExchangeCapsule.transaction()` selects the math engine based on the `hardenedCalc` flag: [1](#0-0)  If `hardenedCalc` is `false` (i.e. `allowHardenExchangeCalculation()` returns `false`, which is the legacy/default state before the corresponding proposal is activated by SRs), pricing is computed by `ExchangeProcessor`, which performs the Bancor relay-token conversion using `double` arithmetic and `Math.pow`: [2](#0-1)  This is precisely the kind of floating-point/rounding weakness that historically enabled precision-manipulation and value-extraction bugs in AMM-style pools (the same bug class DeFi protocols like Euler/associated vaults were exposed to via donation/rounding attacks). By contrast, the project's own `SafeExchangeProcessor` was written specifically to replace this with `BigDecimal` fixed-point math and explicit overflow/negative-balance checks, which strongly signals that the double-based path was recognized internally as the risky legacy implementation: [3](#0-2)  Both `ExchangeTransactionActuator.execute()` and `ExchangeInjectActuator` are directly reachable by any unprivileged account issuing a signed `ExchangeTransactionContract` / `ExchangeInjectContract`, since the actuator only performs balance/limit checks before calling `exchangeCapsule.transaction(...)`: [4](#0-3) 

### Impact Explanation
An attacker able to control the pool's token balances and repeatedly perform small, structured trades (a classic sequence of tiny inject/sell/buy operations against the double-precision relay math) can accumulate systematic rounding bias in their favor across the two-step `exchangeToSupply` → `exchangeFromSupply` calculation, extracting more value from the counter-token reserve than deposited. Because the pool balances are the sole backing for other users' TRX/TRC10 holdings inside that exchange, this constitutes a theft-of-funds / unbacked-balance condition for other liquidity participants in that exchange pair — directly matching the "unbacked balance" and "theft of funds" acceptance criteria.

### Likelihood Explanation
Exploitability is contingent on `allowHardenExchangeCalculation` (and `allowStrictMath`) not being enabled on the target chain/proposal state. I was unable to confirm from the index the exact default value stored in `DynamicPropertiesStore` for this proposal parameter (searches for `allowHardenExchangeCalculation`/`ALLOW_STRICT_MATH` inside `DynamicPropertiesStore.java` returned no results, likely due to index truncation), so I cannot state with certainty whether this legacy path is still active on current mainnet or is now permanently hardened via committee proposal. This uncertainty limits my confidence in classifying this as a live, currently-exploitable High/Critical issue versus a historical, now-mitigated one.

### Recommendation
Given the unresolved uncertainty about the current default/activation state of `allowHardenExchangeCalculation`, I cannot confirm this is presently exploitable without inspecting the full `DynamicPropertiesStore.java` and the relevant hard-fork/committee proposal activation records, which the current index does not fully surface. A Devin session with full filesystem access should be used to check: (1) the default value of `allowHardenExchangeCalculation` in `DynamicPropertiesStore`, (2) whether it has already been activated via a committee proposal on mainnet, and (3) whether `ExchangeProcessor` (double-based) remains reachable at all after that activation, before treating this as an active, unmitigated vulnerability.

### Proof of Concept
Not constructible with confidence from the available index alone, since exploitability depends on the unresolved `allowHardenExchangeCalculation` default noted above; a concrete PoC would require confirming the flag's live value and iterating `ExchangeInjectActuator`/`ExchangeTransactionActuator` calls against a test pool to quantify the double-precision rounding bias in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
