### Title
Non-atomic replay-window check-then-update in `ConnectionState.Decrypt()` / `VerifyRelay()` permits duplicate processing of replayed packets - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt()` and `ConnectionState.VerifyRelay()` in `connection_state.go` release `decryptLock` between checking the replay window (`window.Check`) and committing it (`window.Update`), performing the AEAD decrypt operation in between while unlocked. This is the network-protocol analog of the reported reentrancy class: a piece of "external" work (decryption) is interleaved between a state check and its finalization, so a second concurrent invocation can observe the pre-update state and be treated as valid before the first invocation commits.

### Finding Description
`Decrypt()` locks `decryptLock`, calls `cs.window.Check(l, messageCounter)`, unlocks, performs `cs.dKey.DecryptDanger(...)` (unlocked), then re-locks to call `cs.window.Update(l, messageCounter)`, and unlocks again: [1](#0-0) 

`VerifyRelay()` has the identical pattern: [2](#0-1) 

`Bits.Check()` only inspects the window without mutating it; only `Bits.Update()` marks a counter as seen: [3](#0-2) 

Because `Check` and `Update` are two separate lock/unlock critical sections rather than one atomic operation, two goroutines racing on the same `ConnectionState` with the same (replayed) `messageCounter` can both pass `Check` (neither has marked it seen yet), both proceed to decrypt the same ciphertext, and only afterward serialize on `Update` — at which point one succeeds and the other returns `ErrAlreadySeen`, but the decrypt (and any of its side effects up to that point) already happened for both. This is directly reachable by a remote peer with no forged certificate needed: a replayed data-plane or relay frame is enough, since replay handling is exactly the class this report flags as needing atomic/reentrancy-safe state transitions.

Concurrent invocation on the same `ConnectionState` is realistic because Nebula can run multiple UDP reader goroutines (`routines`/`listen.routines` > 1) that each independently call into the shared per-hostinfo `ConnectionState`: [4](#0-3) [5](#0-4) 

On Linux, `SupportsMultipleReaders()` returns true, enabling this multi-routine configuration in production: [6](#0-5) 

The CHANGELOG shows the project has previously had to specifically patch replay-window races ("Lock replay window updates so concurrent readers can't corrupt it"), and separately had to fix relays that authenticated frames but never advanced the replay window — both indicate this exact check/update boundary has been a recurring source of replay-related races: [7](#0-6) 

The existing test suite explicitly targets the relay-replay scenario, confirming replay handling here is a scrutinized security property, but it does not exercise the concurrent racing case described above: [8](#0-7) 

### Impact Explanation
A successfully-decrypted packet is passed on to further processing (roaming update, connection-manager liveness update, and dispatch to the message/lighthouse/test/control handlers) before the caller learns whether `Update` ultimately rejected it as already-seen: [9](#0-8) 

For the data-plane, a replayed packet raced this way could be delivered twice to the handler that follows (state-affecting side effects such as roaming/keepalive bookkeeping execute for the duplicate before the after-the-fact `ErrAlreadySeen` is observed on the losing goroutine). For `VerifyRelay`, a relay could authenticate and act on a replayed relay frame twice under race, which is the same bug class the project's own relay-replay fix (#1751) targeted for the non-concurrent case. This maps to the "traffic replay" / "remote state poisoning" categories the analog rules require.

### Likelihood Explanation
The race window requires: (1) the attacker to capture/replay one previously-observed valid encrypted frame (no CA-signed certificate needed — the frame's authenticity was already established by a prior legitimate transmission), and (2) two receiver goroutines to process the duplicate at nearly the same time, which is only possible when `routines`/`listen.routines` is configured > 1 (a supported, documented multi-queue configuration on Linux). This makes exploitation environment-dependent (multi-routine deployments) but requires no privileged position and no valid credential — only capture-and-replay of a single legitimate frame plus favorable scheduling.

### Recommendation
Make the check-and-commit of the replay window atomic under a single lock acquisition per packet, i.e., hold `decryptLock` (or an equivalent per-`messageCounter` reservation) across the entire "check, decrypt, commit" sequence, or reserve the counter (mark it provisionally consumed) before releasing the lock to perform the decrypt, rolling back only on decrypt failure. This removes the unlocked window in which two concurrent handlers can both observe the counter as unseen.

### Proof of Concept
1. Configure a receiving Nebula node with `routines` (or `listen.routines`) > 1 on Linux (SO_REUSEPORT multi-queue), so multiple goroutines independently invoke `readOutsidePackets` → `hostinfo.ConnectionState.Decrypt`.
2. Capture one legitimate data-plane (or relay) frame with counter `N` destined to that node.
3. Send two (or more) copies of the exact same captured frame to the node in rapid succession, timed so they land on different reader queues.
4. Both goroutines call `cs.window.Check(l, N)` before either calls `cs.window.Update(l, N)`; both pass `Check`, both execute `DecryptDanger`, and both proceed to the post-decrypt logic (roaming/connection-manager update, handler dispatch) before the second `Update` call observes and rejects the duplicate — demonstrating duplicate processing of a replayed frame, as the existing `TestRelayReplayProtection` test structure could be adapted to assert against by injecting concurrently rather than sequentially: [10](#0-9)

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

	return false
