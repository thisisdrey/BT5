### Title
Dust-transfer griefing fills `depositTokensOfAccount` to `MAX_TOKENS_PER_USER`, DoS-ing victim's deposits and debt issuance - (File: contracts/Pool.sol)

### Summary
`Pool` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` on the combined length of an account's `depositTokensOfAccount` and `debtTokensOfAccount` lists. `DepositToken._transfer` adds the token to the recipient's list on any non-zero transfer, and `DepositToken` shares are freely transferable via `transfer`/`transferFrom` with only the sender's locked-balance check. An unprivileged attacker can deposit dust amounts of every listed collateral and transfer 1 wei of each `msdToken` to a victim, filling the victim's list to 30. From then on, every call path that would add a new token entry for the victim reverts with `UserReachedMaxTokens`: depositing any new collateral (`DepositToken._mint` → `pool.addToDepositTokensOfAccount`) and issuing/minting any new synthetic asset (`DebtToken._mint` → `pool.addToDebtTokensOfAccount`). This is a direct availability analog of the CVE class (low-privilege attacker causes repeatable crash/DoS of the victim's operations).

### Finding Description
- `Pool.sol:79` sets `MAX_TOKENS_PER_USER = 30`.
- `Pool.sol:143-148` `onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30`.
- `Pool.sol:216-220` `addToDepositTokensOfAccount` is callable only by registered deposit tokens, but is triggered on behalf of any recipient.
- `DepositToken.sol:498-525` `_transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance was 0 — no opt-in, no minimum amount, no way to reject incoming shares.
- `DepositToken.sol:348-354` `transfer` only checks `_revertIfLocked(_msgSender, amount_)`, so any holder can push dust to anyone.
- `DepositToken.sol:469-489` `_mint` (deposit path) also adds the account, so a victim at the cap cannot deposit a new collateral type.
- `DebtToken.sol:590-600` `_mint` calls `pool.addToDebtTokensOfAccount(account_)`, so a victim at the cap cannot open a debt position in a new synthetic — even against already-deposited collateral.

Attack trace (all public, unprivileged):
1. For each registered deposit token `msdX` (up to 30 distinct ones across the pool's offerings): attacker calls `msdX.deposit(dust)` then `msdX.transfer(victim, 1)`.
2. Each transfer adds `msdX` to `depositTokensOfAccount[victim]`.
3. Once the combined count hits 30, `victim.deposit(newCollateral)` reverts in `addToDepositTokensOfAccount`, and `debtToken.issue(...)`/`mint` reverts in `addToDebtTokensOfAccount` with `UserReachedMaxTokens`.
4. This persists until the victim manually empties each dust position (transfer full balance or withdraw each token) — a forced cleanup burden the victim never opted into.

### Impact Explanation
The victim is denied service for the core protocol functions: they cannot deposit additional collateral types and cannot mint/issue debt in any synthetic token they don't already hold — i.e., collateral already in the pool becomes unusable for borrowing while the list is saturated. For a SmartFarming position or a leveraged flow that must mint into a fresh debt token, this is a temporary freeze of the position's functionality. Severity is capped because the victim can recover by zeroing out each dust balance (the dust shares were gifted, so the attack costs the attacker real underlying), and existing positions remain withdrawable/liquidatable — hence Medium, matching the report's availability-only impact.

### Likelihood Explanation
- Fully unprivileged: only needs ERC20 collateral + public `deposit`/`transfer`.
- No privileged roles, oracle manipulation, or timing assumptions needed; works on deployed configuration since `MAX_TOKENS_PER_USER` is a constant.
- Cost scales with the number of distinct deposit tokens the pool lists (gas + permanently gifted dust per token); on a pool with few collateral types the attack may be infeasible, and repeatability after victim cleanup requires re-spending — this limits likelihood.

### Recommendation
- Add a per-account opt-out/allowlist or make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` no-op (skip) rather than revert when at cap, and have `debtPositionOf`/`depositOf` handle unlisted tokens — or
- enforce a minimum transfer/mint amount before list insertion, or
- exempt the liquidator/`seize` path so receiving tokens via liquidation can't push an account over the cap, and let users self-remove dust entries by allowing forced `removeFrom*` on zero-balance tokens.

### Proof of Concept

// attacker deposits dust of each listed collateral and gifts 1 wei of each msdToken
for (const msd of allDepositTokens) {
