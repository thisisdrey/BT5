### Title
Unsanitized tar extraction into repository directory via `CreateRepositoryFromSnapshot`'s `HttpUrl` field enables archive-based path traversal - ([File: internal/gitaly/service/repository/create_repository_from_snapshot.go])

### Summary
The `CreateRepositoryFromSnapshot` RPC downloads an archive from a caller-supplied `HttpUrl` and pipes it directly into the system `tar` command with no path/entry validation, unlike the hardened tar-extraction path used elsewhere in the codebase (`extractTarToDirectory` in `replicate.go`). This mirrors the ingress-nginx bug class: an untrusted/attacker-influenced input (here, the archive contents pulled from an RPC-controlled URL) is fed into a file-extraction/config-construction step without sanitization, allowing it to escape the intended target directory.

### Finding Description
`untar` builds and runs the extraction command as: [1](#0-0) 

The HTTP response body is streamed directly as stdin to `tar -C <path> -xvf -` with no restrictions on tar headers (no rejection of `../` entries, absolute paths, or symlinks). This is a plain system `tar` extraction, not the safer `extractTarToDirectory` implementation Gitaly maintains elsewhere, which explicitly validates against directory traversal and symlink escape: [2](#0-1) 

The code's own comment acknowledges this is a known trust boundary weakness: [3](#0-2) 

The extraction target `path` is the newly created repository directory obtained via `repoutil.Create`/`GetRepoPath`: [4](#0-3) 

Because the `HttpUrl`, `HttpAuth`, and `ResolvedAddress` fields of `CreateRepositoryFromSnapshotRequest` are attacker/caller-controlled RPC fields, a malicious or compromised source (e.g., a rogue replication peer, or any caller able to invoke this RPC with a crafted URL) can serve a tar archive containing entries with `../` path components or absolute paths. Since GNU `tar` by default has some (but not complete) protections against absolute-path entries, and none against crafted relative-path traversal combined with symlinks depending on version/flags used here (no `--anchored`/`-P` denial, no explicit `-` component checking), files can be written outside the intended repository directory on the Gitaly storage.

### Impact Explanation
Successful exploitation allows writing arbitrary files outside the newly-created repository's directory on the Gitaly node's filesystem — a storage escape. Depending on what paths are reachable (e.g., other repositories' `hooks`/`custom_hooks` directories, or Gitaly's own binaries/config under the storage root), this could lead to cross-repository file tampering, custom-hook injection into other repositories (leading to code execution during subsequent Git operations), or corruption of Gitaly state. This matches the "concrete storage escape" / "extraction escape" impact class called out in the validation rules.

### Likelihood Explanation
The `untar` function is reachable directly through the `CreateRepositoryFromSnapshot` gRPC RPC, which per its own in-code caveat is explicitly documented as untrusted-input-sensitive ("The received archive is trusted *a lot*... it should undergo a lot of hardening"). Exploitation only requires the ability to invoke this RPC with a URL serving a crafted tar file — no privileged Gitaly-internal access or leaked token is required beyond what's needed to call the RPC itself (an ordinary crafted RPC field, per the report's bug class). The repo's test suite exercises the happy path and HTTP redirect/auth handling but does not appear to test path-traversal/symlink-escape resilience of `untar` (unlike the `extractTarToDirectory` test suite which explicitly covers symlink escape scenarios), supporting that this path lacks the same hardening.

### Recommendation
Replace the raw `tar -xvf -` system-command extraction in `untar` with the same hardened, Go-native extraction routine already used by `extractTarToDirectory` in `replicate.go`, which validates each entry's resolved path stays within the target directory and rejects absolute/traversing symlinks and hard links. Alternatively, reuse a single shared, audited extraction helper for all tar-ingestion RPCs so that traversal protections aren't duplicated (and potentially missed) across code paths.

### Proof of Concept
1. Stand up an HTTP server serving a tar archive containing an entry such as `../../../../other-repo/custom_hooks/pre-receive` (or a `TypeSymlink`/`TypeLink` entry pointing outside the target) with executable content.
2. Call `CreateRepositoryFromSnapshot` with `HttpUrl` pointing at this server, and a `Repository` target on a Gitaly storage.
3. Observe `untar`'s `tar -C <path> -xvf -` invocation extracts the malicious entry, writing/overwriting a file outside the intended repository path (e.g., into another repository's `custom_hooks` directory), which will be executed on that other repository's next push, achieving code execution or state corruption outside the caller's intended scope — consistent with the "extraction escape" impact class validated above.

func (s *server) CreateRepositoryFromSnapshot(ctx context.Context, in *gitalypb.CreateRepositoryFromSnapshotRequest) (*gitalypb.CreateRepositoryFromSnapshotResponse, error) {
	repository := in.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository, storage.WithSkipRepositoryExistenceCheck()); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	if err := repoutil.Create(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.repositoryCounter, repository, func(repo *gitalypb.Repository) error {
		path, err := s.locator.GetRepoPath(ctx, repo, storage.WithRepositoryVerificationSkipped())
		if err != nil {
			return structerr.NewInternal("getting repo path: %w", err)
		}

		// The archive contains a partial git repository, missing a config file and
		// other important items. Initializing a new bare one and extracting the
		// archive on top of it ensures the created git repository has everything
		// it needs (especially, the config file and hooks directory).
		//
		// NOTE: The received archive is trusted *a lot*. Before pointing this RPC
		// at endpoints not under our control, it should undergo a lot of hardening.
		if err := s.untar(ctx, path, in); err != nil {
			return structerr.NewInternal("extracting snapshot: %w", err)
		}

		return nil
	}); err != nil {
		return nil, structerr.NewInternal("creating repository: %w", err)
	}
