### Title
Unbounded `DelegatedResourceAccountIndexStore` growth via `DelegateResourceContract` causes DoS on `GetDelegatedResourceAccountIndex(V2)` query APIs - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
`DelegateResourceActuator` lets any funded account create an unbounded number of distinct delegate relationships (one per unique receiver address) with only a minimal 1 TRX resource commitment per relationship, and does not deduplicate or cap them. Each relationship is stored as a separate key-value entry (`V2_FROM_PREFIX/V2_TO_PREFIX` + owner/receiver) in `DelegatedResourceAccountIndexStore`. The public read APIs `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` reconstruct the full list for an address via an unbounded `prefixQuery`, load every matching row into memory, sort it, and serialize it into a single protobuf response with no pagination — mirroring the reported `getUsers()` bug class where an attacker-inflatable on-chain list becomes unreadable/unsafe to enumerate.

### Finding Description
`DelegateResourceActuator.delegateResource()` calls `delegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress, ...)` for every `DelegateResourceContract` execution: [1](#0-0) 

`delegateV2` unconditionally writes two new rows keyed by `V2_FROM_PREFIX+from+to` and `V2_TO_PREFIX+to+from` — a brand-new key for every distinct receiver address, with no limit on how many distinct receivers an owner can accumulate: [2](#0-1) 

`DelegateResourceActuator.validate()` only requires `delegateBalance >= 1 TRX` and that the receiver account exists (any non-contract account, including one just newly activated by a tiny transfer) — there is no cap on the number of unique receivers per owner: [3](#0-2) [4](#0-3) 

When the index is queried, `getV2Index`/`getWithPrefix` performs an unbounded `prefixQuery` over all rows for that address, materializes them into an `ArrayList`, sorts them, and builds a single `DelegatedResourceAccountIndex` capsule containing every entry: [5](#0-4) 

This unbounded result is returned directly, without any pagination, by `Wallet.getDelegatedResourceAccountIndexV2`, which is exposed via both gRPC (`GetDelegatedResourceAccountIndexV2`) and the public HTTP endpoint `/wallet/getdelegatedresourceaccountindexv2` (also mirrored on PBFT/Solidity nodes): [6](#0-5) [7](#0-6) 

### Impact Explanation
An unprivileged transaction sender can repeatedly broadcast `DelegateResourceContract` transactions to a large number of distinct, minimally-funded receiver addresses (each requiring only ~1 TRX committed resource and a cheaply-activated receiver account), continually growing the owner's row-set in `DelegatedResourceAccountIndexStore`. Any subsequent call to `getdelegatedresourceaccountindexv2` (or the legacy `getdelegatedresourceaccountindex`, whose `getWithPrefix` path is used identically once the account has been `convert()`-ed) for that address forces the full node, solidity node, or PBFT node to load, sort, and serialize the entire unbounded row-set in a single query — degrading or crashing the node process (excessive heap allocation/OOM, long GC pauses) and rendering this public read API path unusable for that address, a concrete node-availability DoS reachable purely through normal broadcastable transactions and a subsequent unauthenticated API call.

### Likelihood Explanation
High. `DelegateResourceContract` is a normal user-facing transaction requiring no special privileges, and 1 TRX per relationship (plus trivial account-activation cost for receivers) is inexpensive relative to the number of distinct entries needed to make a query response large enough to strain node memory/serialization. The query endpoints are unauthenticated HTTP/gRPC calls reachable by any client.

### Recommendation
Add pagination to `DelegatedResourceAccountIndexStore.getWithPrefix`/`getV2Index` (and the corresponding `Wallet`/gRPC/HTTP methods), or cap the number of distinct delegate relationships an owner/receiver can hold, similar to the recommendation in the referenced report (paginated `getUsers(start, stop)`-style API instead of returning the full unbounded set in one response).

### Proof of Concept
1. Fund an owner account and freeze a small resource balance (V2 freeze).
2. For `i` in `1..N` (N large, e.g. tens of thousands): activate a fresh receiver address with a minimal TRX transfer, then submit `DelegateResourceContract{owner, receiver_i, balance=1 TRX}` — each call adds a new `V2_FROM_PREFIX+owner+receiver_i` / `V2_TO_PREFIX+receiver_i+owner` row via `DelegatedResourceAccountIndexStore.delegateV2` (`chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java:77-89`), never undelegating so the rows persist.
3. Call `GET /wallet/getdelegatedresourceaccountindexv2?value=<owner>` (or the gRPC equivalent). `getV2Index` executes `prefixQuery` over all N rows, builds and sorts an `ArrayList` of size N, and serializes the full list into one protobuf response (`DelegatedResourceAccountIndexStore.java:114-138`), causing excessive memory/CPU usage or failure of that query path on the serving node.

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
