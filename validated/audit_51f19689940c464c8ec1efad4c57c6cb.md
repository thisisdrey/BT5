### Title
Stale `TrieKey::YieldIdToDataId` / `TrieKey::DataIdToYieldId` (and related promise-yield state) survive `remove_account`, enabling cross-account-recreation state collision - (File: `core/store/src/utils/mod.rs`)

### Summary
`remove_account` in `core/store/src/utils/mod.rs` deletes only the `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData` trie entries for a deleted account; it never touches `TrieKey::YieldIdToDataId`, `TrieKey::DataIdToYieldId`, `TrieKey::PromiseYieldStatus`, or `TrieKey::PromiseYieldReceipt` entries scoped to that `receiver_id`. If the same account name is later re-registered, these leftover promise-yield trie entries remain live and can interact with new calls to `promise_yield_create_with_id`/`promise_yield_resume` made by the new account owner.

### Finding Description
`set_yield_id_mapping` writes two entries keyed by `receiver_id`: `TrieKey::YieldIdToDataId{receiver_id, yield_id}` and `TrieKey::DataIdToYieldId{receiver_id, data_id}` (`core/store/src/utils/mod.rs:281-297`). The only place these mappings are ever cleared is `remove_yield_id_mappings` (`core/store/src/utils/mod.rs:326-334`), which is invoked from the runtime's own yield-resume/timeout completion path — not from account deletion.

`remove_account` (`core/store/src/utils/mod.rs:505-575`) removes:
- `TrieKey::Account`
- `TrieKey::ContractCode`
- access keys and gas-key nonces (via prefix iteration)
- `TrieKey::ContractData` (via prefix iteration)

It does **not** iterate or remove `TrieKey::YieldIdToDataId`, `TrieKey::DataIdToYieldId`, `TrieKey::PromiseYieldStatus`, or `TrieKey::PromiseYieldReceipt` for the account, all of which are also `receiver_id`-scoped keys per `core/primitives/src/trie_key.rs`. This is a confirmed, exact code-level gap: the account-teardown routine does not have any handling for the promise-yield namespace at all.

However, I was not able to fully trace the exact "duplicate detection" semantics inside `promise_yield_create_with_id` / `promise_yield_resume` (in `runtime/near-vm-runner/src/logic/logic.rs` and `runtime/runtime/src/ext.rs`) within the available tool budget to confirm the precise consequence of a stale mapping surviving into a recreated account:
- If yield creation rejects on an existing `YieldIdToDataId` entry ("duplicate" check), the stale entry would cause the *new* owner's `promise_yield_create_with_id(Y)` call to fail (a griefing/DoS on that specific `yield_id`), not an authorization bypass benefiting the attacker.
- If yield creation instead overwrites the entry, the old `DataIdToYieldId(old_data_id) -> Y` mapping and any un-cleaned `PromiseYieldReceipt`/`PromiseYieldStatus` entries under the old `data_id` would remain dangling. This could permit whoever holds the original `data_id` (the original attacker, who chose it or observed it) to later invoke resume-completion logic against state now owned by an unrelated account — but I could not confirm from the code I reviewed that `promise_yield_resume` allows a caller other than the account itself (or that resulting execution crosses any privilege boundary that leads to fund theft rather than a no-op/error).

Because the specific "resume targets the wrong (attacker-authored) receipt" causal chain described in the question depends on exact logic in `promise_yield_create_with_id`'s duplicate-check and `promise_yield_resume`'s receipt-lookup that I could not fully verify, I can confirm the root-cause code gap (missing cleanup in `remove_account`) but cannot confirm the full exploit chain to the described impact (authorization escalation / receipt hijack) with certainty.

### Impact Explanation
Confirmed: dangling promise-yield trie state (`YieldIdToDataId`, `DataIdToYieldId`, `PromiseYieldStatus`, `PromiseYieldReceipt`) persists across account deletion and can collide with a subsequently recreated account of the same name. This is a genuine state-hygiene defect. Whether it rises to "authorization escalation / receipt hijack" (funds theft, wrong receipt execution) depends on unverified duplicate-detection/resume logic that I did not have budget to fully trace.

### Likelihood Explanation
Preconditions require: (1) an account name that can be deleted and re-registered by an unrelated party (feasible for named accounts under a registrar, not for implicit accounts), (2) the original owner deliberately leaving a yield pending before deleting the account, and (3) the new owner independently choosing a colliding attacker-supplied `yield_id` value in `promise_yield_create_with_id` — the last of which requires either guessing or the attacker convincing the new owner to use a specific value, which is not naturally "independent" as the question frames it. Given these constraints and unverified downstream mechanics, likelihood of full fund-theft exploitation is speculative rather than confirmed.

### Recommendation
Extend `remove_account` in `core/store/src/utils/mod.rs` to also iterate and remove `TrieKey::YieldIdToDataId`, `TrieKey::DataIdToYieldId`, `TrieKey::PromiseYieldStatus`, and `TrieKey::PromiseYieldReceipt` entries scoped to the deleted `account_id`, mirroring the existing access-key/contract-data prefix-iteration-and-remove pattern.

### Proof of Concept
1. Unit test in `core/store/src/utils/mod.rs` (or a new test module): call `set_yield_id_mapping(update, &account_id, yield_id, data_id)`, then `set_promise_yield_status`/`set_promise_yield_receipt` for the same `(account_id, data_id)`; call `remove_account(update, &account_id)`; assert via `get_data_id_for_yield_id`, `get_yield_id_for_data_id`, `get_promise_yield_status`, `get_promise_yield_receipt` that entries are cleared (expected to currently FAIL, proving the gap).

Integration/runtime test (extending `integration-tests/src/tests/runtime/test_yield_resume.rs`): create account A, call `promise_yield_create_with_id(Y)`, delete account A, re-create account A, call `promise_yield_create_with_id(Y)` again as new owner, and assert whether the call is unexpectedly rejected (duplicate) or whether stale `data_id`/`PromiseYieldReceipt` state is observable/exploitable via `promise_yield_resume`. This second test is needed to conclusively establish (or rule out) the fund-impact chain, which was not verifiable from static code review alone. [1](#0-0) [2](#0-1)

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
