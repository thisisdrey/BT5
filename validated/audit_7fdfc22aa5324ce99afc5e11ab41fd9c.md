### Title
Malformed WAL entry causes permanent write-lockout of an entire partition (repeating fatal apply failure blocks all repositories sharing the partition) - (File: internal/gitaly/storage/storagemgr/partition/transaction_manager.go)

### Summary
`TransactionManager.Run()` is the single writer for a partition (which can contain an object pool and all of its fork members). It processes committed WAL entries strictly in order via `applyLogEntry`. If applying a given LSN ever fails (e.g. due to a partially-written pack file, a filesystem error, a stat/rename failure, or any bug in `applyOperations`), `run()` returns the error and the whole goroutine terminates, causing every other pending/future transaction against that partition to fail with `storage.ErrTransactionProcessingStopped`. Because the failing entry was already durably appended to the WAL (`appendLogEntry`), it cannot be skipped: on every restart, `run()`'s recovery loop re-reads `appliedLSN` and unconditionally reapplies the same failing LSN before admitting any new transaction, reproducing the exact same fatal error and terminating again.

### Finding Description
The relevant control flow:
1. `appendLogEntry` (`transaction_manager.go:2150-2169`) durably commits a transaction's WAL entry via `mgr.logManager.AppendLogEntry`. Once this succeeds, the entry is considered committed and *must* eventually be applied — there is no mechanism to discard or skip a bad entry.
2. `run()` (`transaction_manager.go:1699-1740`) loops: if `mgr.appliedLSN < mgr.logManager.AppendedLSN()`, it calls `applyLogEntry(ctx, mgr.appliedLSN+1)` and, on error, `return fmt.Errorf("apply log entry: %w", err)` — terminating the entire manager goroutine for that partition.
3. `applyLogEntry` (`transaction_manager.go:2171-2223`) calls `applyOperations(...)` inside `mgr.db.Update`, and any error there aborts the whole `Run()`.
4. On restart, `initialize()` reads `appliedLSN` from the KV store and the same `for` loop in `run()` will again attempt `applyLogEntry` at the same LSN before any new `Begin`/`Commit` is admitted (`admissionQueue`) — reproducing the crash deterministically if the on-disk cause of the failure persists (e.g., a stale/corrupted temp file, missing target path, permission issue introduced by the same failed operation).
5. This is explicitly acknowledged as an unrecoverable, human-intervention-required state in the recovery tooling: `internal/cli/gitaly/subcmd_recovery_replay.go:156-166` states "If a log entry cannot be applied for any reason (broken, wrong bucket, etc.), the user will find out, but it requires an in-depth investigation... that partition is always in a broken state. There is nothing this tool can do to resolve the situation automatically."

This mirrors the LimboDAO pattern precisely: a single "current" unit of work (WAL LSN, analogous to "current proposal") is accepted (durably logged) but cannot be executed (`applyOperations` fails), and its un-skippable, ordered nature blocks the single writer from processing anything else — including for every other repository/fork sharing the same partition — until manual intervention (deleting/replacing the malformed log entry, as the recovery CLI itself does via `ptn.GetLogWriter().DeleteLogEntry(nextLSN)`).

### Impact Explanation
Because pools and all their fork members share a single partition (`doc/transactions.md:56-60`, `internal/gitaly/storage/storagemgr/partition/transaction_manager.go:889-891` "TransactionManager is responsible for transaction management of a single repository... it is the repository's single-writer"), a single bad transaction that succeeds at the append/verification stage but fails during apply (e.g. an edge case in `applyOperations`, filesystem/quota error, symlink/rename race, or a crafted set of reference/quarantine operations that pass validation but fail on `os.Rename`/`os.Link` at apply time) causes a denial-of-service: no repository in that partition can process any write (and on Gitaly's model, likely no new transaction can even `Begin`) until an administrator manually identifies and deletes/patches the offending WAL entry — an operation that itself risks data loss. This is a DoS of a core write handler reachable in principle from ordinary push/fetch/fork activity that triggers WAL-logged mutator RPCs (reference updates, repository creation/deletion, custom hooks updates, housekeeping).

### Likelihood Explanation
Moderate/uncertain. The verification step at commit time (reference/pack checks) is designed to catch most invalid states before appending to the WAL, and I could not find in the available index a concrete, presently-exploitable case where a request an *ordinary* unprivileged user fully controls (via push/fetch/fork RPC fields) is guaranteed to pass verification/append but deterministically fail at apply on every future run. This would require identifying a specific operation type in `applyOperations` (e.g. filesystem races, disk full at apply-but-not-at-verify time, or a pack file quarantine edge case) that is non-idempotent or racy relative to the environment. The design explicitly documents this failure mode as an operational risk requiring manual recovery (see the CLI comment cited above and the extensive `simulateCrashHook`/`errSimulatedCrash` test scaffolding throughout `transaction_manager_hook_test.go` and `transaction_manager_repo_test.go`, which shows the team is aware `applyLogEntry` failures halt and must be recovered), but I was not able to pin down within this index a specific untrusted-input trigger that survives verification yet fails apply repeatably. This should be treated as a structural/architectural risk rather than a confirmed, immediately reproducible exploit from the evidence gathered.

### Recommendation
- Ensure that anything which can cause `applyOperations` to fail is validated during the pre-append verification/reference-verification phase, so that a WAL entry is never durably appended unless it is guaranteed to be applicable.
- Make `applyLogEntry` failures distinguish between transient (retryable) and permanent (structurally invalid) errors; for permanent errors, consider marking only the specific relative paths/transaction as failed (poisoning just that repository) rather than halting the entire partition's single writer, if partition-wide halting isn't strictly required for correctness.
- Provide automated (not purely manual-CLI) detection and quarantine of a malformed WAL entry so that partitions can self-recover without requiring an operator to run `gitaly recovery replay`/manually delete log entries, reducing the blast radius of the "stuck partition" condition to the smallest possible scope.

### Proof of Concept
No standalone exploit could be constructed from the available index; this is inferred purely from control-flow analysis of the cited production code (`transaction_manager.go` `run`/`applyLogEntry`/`appendLogEntry`) plus the project's own test suite, which explicitly simulates this exact scenario via `BeforeApplyLogEntry: simulateCrashHook()` (e.g. `internal/gitaly/storage/storagemgr/partition/transaction_manager_hook_test.go:514-547`, `internal/gitaly/storage/storagemgr/partition/transaction_manager_repo_test.go:880-921`) and the recovery tooling's own acknowledgment that a failed-to-apply log entry leaves "that partition ... always in a broken state" (`internal/cli/gitaly/subcmd_recovery_replay.go:156-166`). Demonstrating an end-to-end unprivileged trigger (a specific RPC/field combination that passes commit-time verification but fails at apply) was not achievable within the scope and tooling available in this investigation.
