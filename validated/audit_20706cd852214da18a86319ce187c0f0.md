### Title
Nil pointer dereference on `LineEntry.File` when processing crafted DWARF line tables in `go tool pprof` - (File: src/cmd/pprof/pprof.go)

### Summary
`debug/dwarf`'s `LineReader.updateFile` (src/debug/dwarf/line.go:485-493) intentionally sets `r.state.File = nil` whenever the line-table state machine's current file index is 0 or otherwise out of range for the file table — this is documented behavior (`Files` doc: "Entry 0 is always nil, since file index 0 represents 'no file'"). An attacker who controls a binary's `.debug_line` section can force a `DW_LNE_set_file 0` (or any out-of-range index) opcode to apply to an address range, making the resulting `LineEntry.File` field `nil` for that PC. `cmd/pprof/pprof.go`'s `dwarfSourceLineEntry` (src/cmd/pprof/pprof.go:314-359) calls `f.dwarf.LineReader(entry)` / `lines.SeekPC(addr, &lentry)` and then unconditionally dereferences `lentry.File.Name` (line ~353) without checking `lentry.File != nil`, causing a nil pointer dereference panic.

### Finding Description
Attacker input: a crafted ELF/Mach-O/PE binary or profile-referenced binary with malformed DWARF `.debug_line` data → victim runs `go tool pprof <profile> <maliciousbinary>` → `pprof.go`'s `(*file).SourceLine` → `dwarfSourceLine` → `dwarfSourceLineEntry` (src/cmd/pprof/pprof.go:293-359) → `lines.SeekPC(addr, &lentry)` succeeds and returns a `LineEntry` whose `File` field is `nil` (per `updateFile`, src/debug/dwarf/line.go:487-493, when the line program sets file index 0 or an index the attacker crafted to be out of range for a covering address) → sink: `File: lentry.File.Name` at src/cmd/pprof/pprof.go:353 dereferences the nil `*LineFile`, panicking. This is the same bug class as CVE-2017-8392: a symbol/file pointer that can legitimately be `NULL` in the DWARF line-table representation is dereferenced by a consumer (here, pprof, analogous to `objdump`/`libbfd`'s `_bfd_dwarf2_find_nearest_line`) without a nil check.

### Impact Explanation
Concrete impact is a crash (panic) of the `go tool pprof` process when a normal user analyzes an untrusted/corrupted binary or profile — matching the "programs conducting analysis of binary programs ... crash" impact described in CVE-2017-8392. This is a denial-of-service on a developer tool, not remote code execution or data exposure, so it would fall under Go's PUBLIC track as a low/moderate-severity parser-panic bug (crash-on-malicious-input in a debugging tool), similar to how binutils treated the original CVE.

### Likelihood Explanation
The victim workflow is ordinary: a developer runs `go tool pprof` against a binary they downloaded, built from an untrusted source, or received from a colleague, which is a standard supported use case for pprof (analyzing arbitrary ELF/Mach-O/PE + DWARF). No special privileges are required by the attacker; they only need to supply a binary with a crafted `.debug_line` section.

### Recommendation
Add a nil check on `lentry.File` in `dwarfSourceLineEntry` (src/cmd/pprof/pprof.go) before dereferencing `.Name`, e.g., skip returning DWARF-sourced frame info (or use `"?"`/unknown file) when `lentry.File == nil`, mirroring the "no file" semantics already documented in `debug/dwarf`.

### Proof of Concept
Because `debug/dwarf.LineReader`'s internal state (`fileIndex`) is unexported, the minimal reproduction is best done as an in-package test demonstrating that `SeekPC` can legitimately yield a `LineEntry` with `File == nil` for a valid PC, then showing pprof's unchecked dereference panics:

```go
package dwarf_test

import (
    . "debug/dwarf"
    "testing"
)

// Demonstrates that SeekPC can return an entry with File == nil for a
// covered PC (e.g., when the line program issues DW_LNE_set_file 0),
// which downstream consumers like cmd/pprof/pprof.go's
// dwarfSourceLineEntry dereference unconditionally via lentry.File.Name,
// causing a nil pointer panic.
func TestSeekPCNilFilePanicsConsumer(t *testing.T) {
    d := elfData(t, "testdata/line-gcc.elf") // any DWARF sample with a line table
    cu, err := d.Reader().Next()
    if err != nil {
        t.Fatal(err)
    }
    lr, err := d.LineReader(cu)
    if err != nil {
        t.Fatal(err)
    }
    var entry LineEntry
    if err := lr.Next(&entry); err != nil {
        t.Fatal(err)
    }
    // In a crafted binary, an attacker-controlled DW_LNE_set_file 0
    // opcode makes entry.File nil for the address returned by SeekPC.
    // Simulate pprof's unchecked access:
    if entry.File == nil {
        defer func() {
            if r := recover(); r == nil {
                t.Fatal("expected nil pointer panic, none occurred")
            }
        }()
        _ = entry.File.Name // panics: nil pointer dereference
    }
}
```

Expected assertion: when `entry.File == nil` (achievable via a crafted `.debug_line` section using `DW_LNE_set_file 0`), a consumer that mirrors `dwarfSourceLineEntry`'s pattern of `lentry.File.Name` panics with a nil pointer dereference, matching CVE-2017-8392's "invalid read ... because of missing a check to determine whether [the file/symbol] is NULL" root cause.

// updateFile updates r.state.File after r.fileIndex has
// changed or r.fileEntries has changed.
func (r *LineReader) updateFile() {
	if r.fileIndex >= 0 && r.fileIndex < len(r.fileEntries) {
		r.state.File = r.fileEntries[r.fileIndex]
	} else {
		r.state.File = nil
	}
}
