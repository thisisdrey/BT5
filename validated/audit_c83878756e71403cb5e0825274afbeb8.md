### Title
Missing sender-identity binding in `handleCreateRelayRequest` allows relay-state poisoning for arbitrary victim VPN addresses — (File: `relay_manager.go`)

### Summary
`relayManager.handleCreateRelayRequest` (and the response/request switch in `HandleControlMsg`) trusts the `RelayFromAddr` field carried inside an authenticated peer's `NebulaControl` payload without ever checking it against the sender's own authenticated identity (`h.vpnAddrs`, derived from the certificate verified during the handshake). Any already-handshaked peer can put an arbitrary victim VPN address in `RelayFromAddr` and get relay state created/mutated on behalf of that victim, exactly mirroring the reported `VestedZeroNFT.split()` bug where the function checked only that the referenced object exists, not that the caller owns/controls it.

### Finding Description
`HostInfo`/certificate verification in nebula's handshake path (`handshake/machine.go` `validateCert`, `handshake_manager.go` `beginHandshake`/`continueHandshake`) cryptographically proves who the remote peer `h` is and binds `h.vpnAddrs` to that identity. [1](#0-0) 

However, `relayManager.HandleControlMsg` only validates that `RelayFromAddr`/`RelayToAddr` are non-nil — it never checks that `RelayFromAddr` equals one of the addresses in the authenticated `h.vpnAddrs` of the peer that actually sent the control message: [2](#0-1) 

That unchecked value (`from`) is then used directly to key relay state:
- In the "target is me" branch, `from` is used to look up/insert `h.relayState` (the relay bookkeeping kept on the *sender's* `HostInfo` from the local node's perspective), and a brand-new relay entry is created via `AddRelay(..., from, &m.InitiatorRelayIndex, TerminalType, Established)` if none exists — with `Established` state and the attacker-chosen `InitiatorRelayIndex`, with no verification that `from` is actually an address the peer `h` is authorized to represent. [3](#0-2) 

- In the "target is not me" branch, the same attacker-controlled `from` is used to install relay state on the *target's* `HostInfo` object (`peer.relayState.QueryRelayForByIp(from)` / `AddRelay(..., peer, ..., from, ...)`), and a `CreateRelayRequest` naming `from` as the relay origin is forwarded on to that target peer. [4](#0-3) 

Under the intended protocol, `RelayFromAddr` is only ever supposed to be set to `f.myVpnAddrs[0]` — i.e. the sender's own address — by legitimate callers such as `StartRelays`: [5](#0-4) 

But nothing on the receiving side enforces that invariant. This is the same class of bug as the `VestedZeroNFT.split()` report: the check present (`_requireOwned(tokenId)` there; certificate/handshake authentication of `h` here) only proves *some* valid entity exists/is authenticated, not that the caller is authorized to act on the specific referenced identity/token embedded in the request (`tokenId` there; `RelayFromAddr` here).

### Impact Explanation
An authenticated-but-malicious peer can poison relay/hostmap trust state for a victim VPN address it does not own:
- It can force a relay-capable node to record itself as an `Established` terminal relay for an arbitrary victim address with an attacker-chosen local index, without that victim ever requesting or consenting to it.
- It can cause a third-party target host to install `Requested`/`Established` relay-forwarding state believing an arbitrary victim address is being relayed through the attacker-controlled relay peer, influencing which peer future relayed traffic toward/from that victim address gets routed through.

This is remote state poisoning of the hostmap/relay/lighthouse trust structures reachable by any peer that has completed a normal handshake (no special privilege, no valid certificate for the victim required) — squarely within the in-scope categories of hostmap/lighthouse/relay address trust and remote state poisoning.

### Likelihood Explanation
Exploitation only requires being an authenticated Nebula peer able to send a `header.Control` message of type `NebulaControl_CreateRelayRequest` to any node that is a relay candidate or is directly reachable, with a forged `RelayFromAddr`. No CA-signed certificate for the victim address is needed, and no race or timing constraints beyond normal message delivery are required, making this readily reachable.

### Recommendation
When processing `NebulaControl_CreateRelayRequest`/`CreateRelayResponse`, verify that `RelayFromAddr` (for requests where the sender claims to be the origin) matches one of the authenticated `h.vpnAddrs` for the `HostInfo` that delivered the control message, and reject/log-drop the message otherwise, before calling `AddRelay` or mutating any `relayState`.

### Proof of Concept
1. Node `A` (attacker) completes a normal handshake with relay-capable node `R` and with target node `T`, obtaining valid `HostInfo` objects the same as any legitimate peer.
2. `A` crafts a `NebulaControl{Type: CreateRelayRequest, RelayFromAddr: <victim V's vpn addr>, RelayToAddr: <T's vpn addr>, InitiatorRelayIndex: <arbitrary>}` and sends it to `R` over the `A`↔`R` tunnel.
3. `R.handleCreateRelayRequest` executes the "target is not me" branch (since `T != R`), calls `AddRelay(..., peer=T's HostInfo on R, from=V, ...)`, and forwards a `CreateRelayRequest` naming `RelayFromAddr=V` to `T`.
4. `T.handleCreateRelayRequest` executes the "target is me" branch (since `T`'s own address matches), and — because it has no prior relay entry for `V` on `R`'s `HostInfo` — calls `AddRelay(..., h=R's HostInfo on T, from=V, ..., Established)`, installing `Established` relay state for victim `V` that `T` never requested, keyed by attacker-chosen `InitiatorRelayIndex`.
5. No step above checks that `V` corresponds to any address the sender (`A`, then `R` on `A`'s behalf) is certified for, demonstrating the missing identity/ownership binding.

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}
}
