### Title
Access-key nonce is not preserved on same-pubkey re-creation, enabling stale-transaction replay - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
The external report's bug class is: a counter (`nextQuestionId`) restarts from a low/overlapping value for a "new instance" while a mapping keyed by that counter is shared with the "old instance," letting stale/old state collide with new state and be replayed or misused. The nearest reachable analog in nearcore is `AccessKey.nonce`: when an access key is deleted and a new key is added under the *same* `public_key`, the nonce "instance" is not continued from the old key's high-water mark — it is reset to a value derived only from the current block height, which can be lower than the nonce the old key had already reached.

### Finding Description
`docs/DataStructures/AccessKey.md` documents the intended invariant explicitly: [1](#0-0) 

i.e., if a public key is reused after being deleted, the new key's nonce **must** start at least as high as the old key's nonce, specifically "to avoid replaying old transactions again."

The actual implementation does not enforce this. `action_add_key` (`runtime/runtime/src/access_keys.rs:149`) only rejects the add if a key **currently** exists for that public key (`AddKeyAlreadyExists`); once a key has been deleted, `get_access_key` returns `None` and the historical nonce is gone: [2](#0-1) 

`add_regular_key` then seeds the new key's nonce purely from the current block height, with no knowledge of the deleted key's nonce: [3](#0-2) 

using: [4](#0-3) 

Nonce validation (`verify_nonce`, described in `protocol-model/spec/accounts-keys.md:55`) only bounds a signed transaction's nonce by `tx_nonce <= block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` (`NonceTooLarge`, `core/primitives/src/errors.rs:238`) — there is no *lower* bound tied to previous usage of that specific public key besides the currently-stored `AccessKey.nonce`. Because `NonceMode::Monotonic` only requires `tx_nonce > current_nonce` with no meaningful upper constraint other than the block-height-derived ceiling, an account owner (or anyone who obtains a validly signed but unsubmitted transaction for that key) can, in a single transaction, drive the key's `nonce` value close to `block_height * 1_000_000`. If that same public key is subsequently deleted and re-added (e.g., during a key-rotation or permission-reset flow performed by a wallet/dApp) within the same or a nearby block, the new key's seeded nonce (`(block_height-1) * 1_000_000`) can be **lower** than the nonce the old key had already reached. Any previously signed-but-unsubmitted (or intentionally withheld/"cancelled") transaction whose nonce falls in the gap between the new seed and the old high-water mark becomes valid again against the recreated key and can be replayed.

This exactly mirrors the report's root cause: a per-"instance" counter is not carried forward when a new instance is created under an identity that is shared with the old instance, and the mapping/validation logic (here, nonce monotonicity checking) does not account for previously-consumed identifiers from the prior instance, allowing old state to be reintroduced.

### Impact Explanation
An account holder or a party in possession of an old, revoked/cancelled signed transaction can replay it after the intended key rotation, executing an action the signer believed was invalidated (e.g., a `FunctionCall` action with an allowance, a `Transfer`, or a `DeleteKey`/`AddKey` sequence). This is a nonce-based replay of a previously authorized action, which falls in the double-spend/replay category: funds or permissions that were meant to be revoked or spent only once can be re-executed.

### Likelihood Explanation
The likelihood is limited by the precondition that the *same* public key must be deleted and then re-added (an unusual but not disallowed pattern — nothing in `action_add_key`/`action_delete_key` prevents it), and that the old key's nonce must have already been advanced close to `block_height * 1_000_000` before deletion (achievable in a single self-signed transaction since `Monotonic` nonce mode has no restrictive lower bound tied to actual transaction count). This requires specific, deliberate sequencing rather than being triggered by ordinary usage, so exploitation is plausible primarily in adversarial key-rotation/relayer workflows rather than as an everyday occurrence.

### Recommendation
When re-adding an access key under a public key that previously existed on the account (even if currently deleted), the new key's nonce should never be permitted to be lower than the highest nonce ever observed for that `(account_id, public_key)` pair. This requires either (a) retaining a tombstone/high-water-mark record for deleted keys' nonces until it is provably safe to reuse the public key, or (b) rejecting `AddKey` for a public key that was recently deleted within the nonce's validity window, consistent with the invariant already documented in `docs/DataStructures/AccessKey.md`.

### Proof of Concept
1. Account `alice.near` has `FullAccess` key `K` with a low nonce.
2. Alice signs transaction `T_old` (e.g., transferring funds or calling a sensitive method) with `K` and nonce `N_high`, chosen close to `current_block_height * 1_000_000`, but does not submit it (or the relayer holds it without submitting).
3. Alice submits a transaction that advances `K`'s stored nonce to `N_high` via any monotonic-nonce transaction — this is a single valid transaction under `NonceMode::Monotonic`, requiring only `tx_nonce > current_nonce` and `tx_nonce <= block_height * 1_000_000`.
4. In a subsequent (or same-block) transaction, Alice (or a relayer with a `FullAccess`/`FunctionCall` key) issues `DeleteKey(K)` followed by `AddKey(K, ...)` reusing the identical public key. Per `add_regular_key` (`access_keys.rs:230-241`), the new key's nonce is seeded to `(block_height-1) * 1_000_000`, independent of the fact that `K` previously reached `N_high`.
5. If `N_high > (block_height-1) * 1_000_000` at the time of recreation, `T_old` (with `nonce = N_high`) is now valid again against the recreated key and can be broadcast/executed — replaying an action the account owner believed was cancelled or superseded.

Note: I was not able to execute this scenario in a live nearcore test environment; this is derived from static analysis of `runtime/runtime/src/access_keys.rs`, `runtime/runtime/src/verifier.rs`, and `core/primitives/src/errors.rs`, and the documented invariant in `docs/DataStructures/AccessKey.md`. A Devin session with full repo/test access would be needed to write and run an integration test (e.g., under `integration-tests/src/tests/features/`) to concretely confirm the replay executes end-to-end under current protocol logic.

```rust
pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}
```

```rust
pub(crate) fn action_add_key(
    apply_state: &ApplyState,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    add_key: &AddKeyAction,
) -> Result<(), StorageError> {
    if get_access_key(state_update, account_id, &add_key.public_key)?.is_some() {
        result.result = Err(ActionErrorKind::AddKeyAlreadyExists {
            account_id: account_id.to_owned(),
            public_key: add_key.public_key.clone().into(),
        }
        .into());
        return Ok(());
    }
```
