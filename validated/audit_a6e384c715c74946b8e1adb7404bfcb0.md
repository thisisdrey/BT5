### Title
Users cannot withdraw collateral when the oracle price is stale or reverts, even with zero debt - (File: contracts/DepositToken.sol)

### Summary

`DepositToken.withdraw`, `withdrawFrom`, `transfer`, and `transferFrom` all gate on `_revertIfLocked`, which internally calls `unlockedBalanceOf`. `unlockedBalanceOf` unconditionally calls `Pool.debtPositionOf(account_)`, which calls `Pool.depositOf` — a loop that invokes `masterOracle.quoteTokenToUsd` on the collateral's `underlying` for every deposit token the account holds. If the oracle returns a stale/disabled price, `quoteTokenToUsd` reverts, so the lock check itself reverts before it can even determine the user has no debt. The zero-debt early return at `DepositToken.sol:388` (`if (_debtInUsd == 0) return balanceOf[account_]`) is unreachable because `debtPositionOf` reverts first — the oracle quote for the collateral happens inside `depositOf`, not lazily.

### Finding Description

Trace:

1. `DepositToken.withdraw(amount_, to_)` calls `_revertIfLocked(_msgSender(), amount_)` at `contracts/DepositToken.sol:409`. [1](#0-0) 
2. `_revertIfLocked` checks `amount_ > unlockedBalanceOf(account)`, and `unlockedBalanceOf` calls `pool.debtPositionOf(account_)` at `contracts/DepositToken.sol:386`. [2](#0-1) 
3. `Pool.debtPositionOf` calls `depositOf(account_)` at `contracts/Pool.sol:263`, which loops over `depositTokensOfAccount` and calls `masterOracle.quoteTokenToUsd(address(_depositToken.underlying()), ...)` at `contracts/Pool.sol:281-283`. [3](#0-2) 
4. When the underlying's oracle feed is stale or the price provider is disabled, `quoteTokenToUsd` reverts, reverting the entire `withdraw`. This is demonstrated in the repo's own test: after `time.increase` past the pull-oracle expiration, `msdUSDC.withdraw(...)` reverts with `'price-expired'` (`test/Operator.test.ts:121-126`), even though the test user's debt is zero (`debtPositionOf` returned `_debtInUsd = 0` at `test/Operator.test.ts:110-118`). [4](#0-3) 

The same oracle dependency freezes `transfer`/`transferFrom` of msdTokens (`contracts/DepositToken.sol:350, 362`) and `SmartFarmingManager.flashRepay`/`withdrawFrom` paths, which also end at `debtPositionOf` (`contracts/SmartFarmingManager.sol:140`).

### Impact Explanation

Users with fully repaid debt — or users who never borrowed — cannot withdraw or transfer their deposited collateral while the oracle for that collateral (or for any synthetic token in their `debtTokensOfAccount` list, via `debtOf` at `contracts/Pool.sol:230-236`) is stale, disabled, or reverting. Collateral is user property, not protocol property; a zero-debt position has no solvency invariant that requires a price. The breakage is a temporary freezing of funds lasting as long as the oracle outage — which, for a disabled/decommissioned feed, can become effectively permanent until governance swaps the oracle. This is the exact bug class of the referenced BaseVault finding (health check requiring a valid oracle blocking collateral exit for a debt-free user), expressed through Metronome's `debtPositionOf`-based lock check rather than a `_checkAccountHealth` call.

### Likelihood Explanation

The trigger is external (oracle staleness), not attacker-controlled, so per the rules this is a liveness/DoS-of-funds class issue rather than an actively exploitable theft. Stale-price conditions occur naturally: Chainlink heartbeat lapses, pull-oracle providers (RedStone on Hemi deployment, per `test/E2E.hemi.pullOracle.test.ts`) failing to update, or a provider being deprecated. The repo's own Operator tests exist precisely because expired prices block `debtPositionOf` and `withdraw`, and the intended workaround is `Operator.execute` batching a price update with the withdrawal — which only helps for pull-style oracles anyone can update, not for a disabled push feed. Severity is medium: real impact, conditioned on oracle failure.

### Recommendation

Avoid the oracle call when it cannot affect the outcome. Two options:

1. In `unlockedBalanceOf`, short-circuit when the account holds no debt tokens: check `pool.debtTokensOfAccount.length(account_) == 0` (or a cheap non-priced debt check such as summing raw `DebtToken.balanceOf`) before calling `debtPositionOf`, and return `balanceOf[account_]` directly.
2. Alternatively, add a priced or unpriced variant to `Pool` — e.g., `debtOf` over raw balances already avoids pricing synthetic tokens the user doesn't hold; the residual problem is `depositOf` quoting the collateral price even when `_debtInUsd == 0`, so `debtPositionOf` could skip `depositOf` entirely once debt is known to be zero.

```solidity
// DepositToken.unlockedBalanceOf — sketch
if (_pool.debtTokensOfAccount.length(account_) == 0) {
    return balanceOf[account_];
}
(, , uint256 _debtInUsd, , uint256 _issuableInUsd) = _pool.debtPositionOf(account_);
...
```

A caveat: raw `DebtToken` balances alone don't prove zero USD debt if a user holds debt in a synth whose oracle is stale — but `debtTokensOfAccount` length is a safe gate since an account with no debt-token positions has provably zero debt.

### Proof of Concept

Reproducible in Hardhat (the repo already contains the essential test at `test/Operator.test.ts:78-144`):

```typescript
// test — user deposits, has NO debt, oracle expires, withdraw reverts
await pullOracle.setExpirationPeriod(time.duration.hours(1))
await pullOracle.updatePrice(usdc.address, parseEther('1'))
await usdc.connect(alice).approve(msdUSDC.address, MaxUint256)
await msdUSDC.connect(alice).deposit(parseUnits('100', 6), alice.address)

// alice has zero debt — never called debtToken.issue
const { _debtInUsd } = await pool.debtPositionOf(alice.address)
expect(_debtInUsd).eq(0)

// oracle price expires
await time.increase(time.duration.hours(2))

// withdraw of ANY amount reverts inside unlockedBalanceOf -> debtPositionOf -> quoteTokenToUsd
await expect(
  msdUSDC.connect(alice).withdraw(parseUnits('1', 6), alice.address)
).to.revertedWith('price-expired')

// transfers are equally frozen
await expect(
  msdUSDC.connect(alice).transfer(bob.address, 1)
).to.revertedWith('price-expired')
```

The existing test at `test/Operator.test.ts:121-126` already asserts this revert, confirming the behavior on the deployed code path. The oracle-dependent lock also cannot be bypassed via `Operator.execute` unless the oracle is a permissionless pull oracle — for a disabled push feed there is no unprivileged recovery path, so the freeze persists until governance intervention.
