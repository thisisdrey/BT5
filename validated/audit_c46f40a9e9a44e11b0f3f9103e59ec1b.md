Audit Report

## Title
Unbounded slippage in `SwapFirstAssetTrader::refund_weight` lets an attacker sandwich XCM fee refunds and drain refunded value via the AssetConversion pool - (File: cumulus/primitives/utility/src/lib.rs)

## Summary
`SwapFirstAssetTrader::refund_weight` swaps unused `Target` fee credit back into the user's original payment asset via `SwapCredit::swap_exact_tokens_for_tokens(vec![Target::get(), refund_swap_asset], refund, None)`, passing `None` as `amount_out_min` and thus accepting any output amount from the public AssetConversion pool. This contrasts with `buy_weight`, which requests an exact output amount, and with `SwapAssetAdapter::correct_and_deposit_fee`, which always quotes and passes `Some(refund_asset_amount)` before swapping a refund. The type is wired as the XCM `Trader` in Asset Hub Rococo, Asset Hub Westend, Penpal, and the staking-async parachain runtime.

## Finding Description
`buy_weight` withdraws the user's non-target payment asset and swaps it for the `Target` asset via `SwapCredit::swap_tokens_for_exact_tokens`, requesting an exact `fee` amount out. [1](#0-0)  `refund_weight` extracts the unused portion of `total_fee` (in `Target` asset) and swaps it back into `refund_swap_asset` using `swap_exact_tokens_for_tokens` with `amount_out_min` hardcoded to `None`. [2](#0-1) 

`pallet_asset_conversion`'s swap logic only enforces the minimum-output check when `amount_out_min` is `Some(...)`; when `None`, the `ProvidedMinimumNotSufficientForSwap` guard is skipped entirely. [3](#0-2)  The pool used is the same public, permissionlessly tradable `AssetConversion` pool exposed via dispatchables like `swap_exact_tokens_for_tokens`. [4](#0-3)  This trader type is used as the configured `Trader` in Asset Hub Rococo, Asset Hub Westend, Penpal, and the staking-async parachain runtime `xcm_config.rs` files, confirming it is live, in-repo, reachable code, not test-only. [5](#0-4) 

By contrast, `SwapAssetAdapter::correct_and_deposit_fee` in the transaction-payment asset-conversion pallet always quotes a minimum via `QuotePrice::quote_price_exact_tokens_for_tokens` and passes `Some(refund_asset_amount)` into the swap-back, demonstrating that the codebase's own established pattern for refund swaps is to bound slippage — a pattern `refund_weight` fails to follow. [6](#0-5) 

## Impact Explanation
The corrupted value is the amount of the original fee-payment asset credited back to the XCM message's fee payer during `refund_weight`. An attacker who manipulates the pool's reserves immediately before this swap executes can force `swap_exact_tokens_for_tokens` to accept an arbitrarily unfavorable output, extracting the spread as the pool price is restored afterward. This matches the "public underpriced work" impact category: fee-refund settlement against a public AMM pool loses value non-conservation guarantees without requiring any privileged actor.

## Likelihood Explanation
Exploitation only requires an unprivileged attacker able to submit ordinary swap transactions against the same public `AssetConversion` pool (via `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` dispatchables) before and after an XCM message that triggers a fee refund executes. Since XCM fee estimation is typically conservative, weight overpayment and consequent `refund_weight` invocations with nontrivial `refund_amount` are routine, giving the attacker predictable, repeatable opportunities. No validator, collator, or governance privilege is needed — only transaction timing/ordering within or across adjacent blocks.

## Recommendation
Before calling `SwapCredit::swap_exact_tokens_for_tokens` in `refund_weight`, compute a minimum acceptable output via `QuotePrice::quote_price_exact_tokens_for_tokens(Target::get(), refund_swap_asset, refund_amount, true)` and pass `Some(quoted_min)` (with a small tolerance) instead of `None`, mirroring the approach already used in `SwapAssetAdapter::correct_and_deposit_fee`. If the swap would fail the minimum check, retain the credit in `total_fee` using the existing error-branch fallback rather than accepting an unbounded-slippage swap.

## Proof of Concept
1. Configure a runtime using `SwapFirstAssetTrader` as the XCM `Trader` (as in `asset-hub-rococo`, `asset-hub-westend`, `penpal`, or the staking-async parachain runtime `xcm_config.rs`), with an `AssetConversion` pool between `Target` and a foreign/local asset.
2. An attacker observes an incoming XCM message that overpays fees in the foreign asset (common due to conservative fee estimation), which will trigger `buy_weight` followed by a `refund_weight` call with nonzero `refund_amount`.
3. Immediately before the message executes, the attacker calls the public `swap_tokens_for_exact_tokens`/`swap_exact_tokens_for_tokens` dispatchable to skew the `Target`/foreign-asset pool reserves unfavorably for a `Target -> foreign` conversion.
4. The XCM message executes; `refund_weight` calls `SwapCredit::swap_exact_tokens_for_tokens(vec![Target, foreign], refund, None)`, accepting the skewed, unfavorable output with no minimum enforced. [7](#0-6) 
5. The attacker reverses their initial swap, restoring the pool price and capturing the spread extracted from the undervalued refund.
