### Title
Unchecked attacker-controlled array-length allocation in TVM precompile ABI decoding may throw uncaught `Error`/`RuntimeException` outside protective try-catch - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.extractBytesArray()` and `extractBytes32Array()` allocate Java arrays (`new byte[len][]`) whose size `len` is taken directly from attacker-supplied calldata (`words[offset].intValueSafe()`), with no upper-bound validation before the allocation call in the legacy (pre-feature-flag) code path of `ValidateMultiSign.execute()`. This mirrors the CVE-2024-34030 bug class: an allocation-size value derived from external input is used without checking either the request or the allocation result, risking unchecked-failure crashes.

### Finding Description
`extractBytesArray` and `extractBytes32Array` read a length word straight from the raw contract calldata and immediately allocate an array of that many elements: [1](#0-0) 

In `ValidateMultiSign.execute()`, when `VMConfig.allowTvmSelfdestructRestriction()` is not active, the code calls `extractBytesArray` directly, skipping the `sigArraySize > MAX_SIZE` bound check that is only performed in the `allowTvmSelfdestructRestriction()`-guarded branch: [2](#0-1) 

This call to `extractBytesArray`/`extractSigArray` occurs **before** the surrounding `try { ... } catch (Throwable t) { ... }` block that wraps the rest of the precompile logic, meaning any exception thrown while allocating `bytesArray` (e.g., `NegativeArraySizeException` from a corrupted/huge length, or `OutOfMemoryError` from an extremely large but positive length) propagates uncaught out of the precompile.

Precompile execution happens inside TVM opcode dispatch (`VM.play()`), whose exception handling only catches `RuntimeException` and `StackOverflowError`, not arbitrary `Error` types like `OutOfMemoryError`: [3](#0-2) 

A similar unchecked-length-to-allocation pattern also exists in `BatchValidateSign.doExecute()`, guarded the same way by `allowTvmSelfdestructRestriction()`: [4](#0-3) 

### Impact Explanation
If the vulnerable legacy branch (`allowTvmSelfdestructRestriction()` disabled) is reachable, any account can call the `validateMultiSign`/`BatchValidateSign` precompile with a crafted `int_map`-like length field to trigger a large or negative array allocation. `OutOfMemoryError` is not a `RuntimeException` and is not caught by `VM.play()`'s catch block, so it can propagate up through block/transaction execution, which — depending on how the Manager/actuator execution wraps this — could crash the node processing the block (all full nodes and SRs replay every transaction), leading to a chain-wide halt. This matches the "node crash or halt" impact bucket.

### Likelihood Explanation
Likelihood is **uncertain** because I was unable to confirm within the available tool budget whether `VMConfig.allowTvmSelfdestructRestriction()` is already permanently enabled on production networks (in which case the unguarded legacy branch is dead code and unreachable by new transactions) or whether it remains a live, deactivatable/optional path. I also could not fully verify `DataWord.intValueSafe()`'s value-clamping behavior, which affects whether `len` can actually reach an extreme value capable of triggering `OutOfMemoryError` versus being safely bounded to `Integer.MAX_VALUE`-class values that would merely throw a catchable `NegativeArraySizeException`/`OutOfMemoryError` still outside the try block. This should be validated with a live Devin session that can trace `VMConfig.allowTvmSelfdestructRestriction()` activation status and `intValueSafe()` semantics precisely.

### Recommendation
- Add explicit bounds validation on `len` in `extractBytesArray`/`extractBytes32Array`/`extractSigArray` (e.g., reject if `len < 0` or `len > MAX_SIZE`) regardless of the `allowTvmSelfdestructRestriction()` flag, before performing any allocation.
- Move the array-extraction calls inside the existing `try { ... } catch (Throwable t) { ... }` block in `ValidateMultiSign.execute()` and `BatchValidateSign.doExecute()` so that allocation failures are handled gracefully and returned as a normal precompile failure (`Pair.of(true, DATA_FALSE)`) instead of propagating as an uncaught `Error`.
- Audit `VM.play()`'s exception handling to also catch `OutOfMemoryError`/`Error` at the VM dispatch boundary so that a single malicious contract call cannot destabilize node execution.

### Proof of Concept
Not executable without confirming the current activation state of `allowTvmSelfdestructRestriction()`; conceptually: craft a `validateMultiSign(address, permissionId, bytes32 hash, bytes[] signatures)` call where the ABI-encoded dynamic-array length word at the `signatures` offset is set to a very large value (e.g., `0x7FFFFFFF`), while `allowTvmSelfdestructRestriction()` is inactive so the `sigArraySize` pre-check is skipped, forcing `extractBytesArray` to attempt `new byte[0x7FFFFFFF][]`.
