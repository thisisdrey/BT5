### Title
Cross-StackerDB / cross-reward-cycle chunk signature replay due to missing contract binding in `SlotMetadata::auth_digest` - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
The external report's bug class is "a node signs/accepts a payload whose authenticated digest omits fields the caller actually relies on, letting an attacker splice a validly-signed blob into a different context." The exact analog in this repo is the StackerDB chunk authentication scheme: the signature only commits to `(slot_id, slot_version, data_hash)` and never to the target contract/DB identity. Because the Nakamoto signer set reuses the *same slot assignment* (signer address ↔ slot index) across every `.signers-{set}-{message_id}` sub-database and across reward cycles when the same signer re-registers, a chunk legitimately signed for one StackerDB replica is also a valid signature for a different StackerDB replica, as long as slot_id/version/data-hash line up. Any unauthenticated network peer that can observe a gossiped chunk (or simply POST it) can replay it into a different contract's slot.

### Finding Description
`SlotMetadata::auth_digest()` computes the signed digest solely from `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

`SlotMetadata::verify()` recovers the public key from this digest and only checks that it hashes to the caller-supplied `principal` — it has no notion of *which* StackerDB/contract the signature was meant for: [2](#0-1) 

The contract/DB identity is supplied out-of-band by the *caller*, not bound into what's actually signed. In `try_replace_chunk`, the expected signer address is looked up per `(smart_contract, slot_id)`, and then `slot_desc.verify(&slot_validation.signer)` is called — the contract never enters the cryptographic check: [3](#0-2) 

The public HTTP write path (`POST /v2/stackerdb/:principal/:contract/chunks`) takes an attacker-controlled `contract_identifier` from the URL and an attacker-controlled `StackerDBChunkData` (slot_id, slot_version, sig, data) from the body, with no requirement that the signer intended this contract: [4](#0-3) [5](#0-4) 

The same fault path exists on the gossip/relay side: `validate_received_chunk` calls `get_slot_signer(smart_contract_id, data.slot_id)` and then `slot_metadata.verify(&addr)`, again never mixing the contract id into the signed digest: [6](#0-5) 

Crucially, the Nakamoto signer-set design guarantees slot-index collisions across sibling databases: every message-type sub-contract for a given signer set (`.signers-0-X` / `.signers-1-X`) is built from the exact same slot ordering, fetched from the single shared `stackerdb-get-signer-slots-page`: [7](#0-6) 

and `MessageSlotID` enumerates several sibling contracts (`BlockResponse`, `StateMachineUpdate`, `BlockPreCommit`) that all key off the *same* per-signer slot index within a reward cycle: [8](#0-7) 

This is confirmed directly by the test asserting identical slot assignment is shared by every `signers-{set}-{message_id}` contract: [9](#0-8) 

Consequently, a signer S occupying slot `k` in `.signers-0-2` (StateMachineUpdate) occupies the same slot `k` in `.signers-0-1` (BlockResponse) and `.signers-0-3` (BlockPreCommit) for that reward-cycle parity. Any chunk `{slot_id=k, slot_version=v, sig, data}` that S validly signs for one of these DBs is *also* a valid, verifiable chunk for the sibling DB at the same `(k, v, hash(data))` triple, because the signature check only ever recomputes `H(k, v, hash(data))` and recovers to S's address — it never checks "was this signed for contract X". An attacker who observes any gossiped/pushed chunk (StackerDB traffic is not access-controlled; anyone can read it via p2p or by re-querying `GET /v2/stackerdb/...`) can resubmit the identical bytes to a sibling contract's `POST /v2/stackerdb/:principal/:other-contract/chunks` endpoint, as an unprivileged network participant, and the write will be accepted as if S had signed it for that other DB (subject only to the freshness/version and slot/size checks in `try_replace_chunk`, none of which reference contract identity in the signature).

The same construction also lets an attacker replay a chunk *across reward cycles*: if S occupies slot `k` again in a later cycle for the same message type (common when signer sets persist), a stale, previously-authentic chunk from an old cycle can be reinjected into the current cycle's StackerDB as if freshly signed — because reward cycle is likewise absent from the digest, and only affects the destination contract identifier, not the cryptography.

### Impact Explanation
This breaks the intended equality "signed-for-contract-X == authenticated-for-contract-X": a signature legitimately produced for one StackerDB replica is accepted as authoritative for a *different* replica or a *stale* cycle, entirely via unauthenticated write. Concretely:
- Unauthorized/forged write into a `.signers-*` StackerDB slot the true signer never intended for that contract (matches the "Critical: unauthenticated/unauthorized write to state or StackerDB" category).
- Sibling-message-type payloads that happen to decode compatibly, or stale historical state re-served as fresh, can pollute state consumed for block-acceptance bookkeeping (e.g., `GlobalStateEvaluator`/`StackerDBListener`, which reads "latest chunks" per slot and treats them as authoritative current signer state): [10](#0-9) 
This is at minimum a High-impact "serving non-canonical (stale/foreign-context) state as canonical," and can rise to Critical (unauthorized write / forged-data propagation) since accepted chunks are subsequently re-gossiped to peers by the node that stored them, propagating the forged/foreign-context data network-wide via the normal chunk-inventory/push relay path.

### Likelihood Explanation
No special privilege is required: the write endpoint is a plain unauthenticated HTTP POST, and legitimately signed chunks are freely observable (StackerDB gossip and the read endpoint are public by design). The only preconditions — same signer occupying the same slot index across sibling message-type contracts, or across a later reward cycle — are guaranteed by the signer-set contract design shown above, not by chance. The remaining checks in `try_replace_chunk` (chunk size, version freshness, max-writes) are ordinary bookkeeping and do not defend against cross-contract replay.

### Recommendation
Bind the destination namespace into what is actually signed: include the `QualifiedContractIdentifier` (and ideally the reward cycle) in `SlotMetadata::auth_digest()` alongside `slot_id`, `slot_version`, and `data_hash`, and thread that context through `StackerDBChunkData::sign`/`verify`, `try_replace_chunk`, and `validate_received_chunk`. This is a wire-format/signing-scheme change and requires careful compatibility handling across the network.

### Proof of Concept
Conceptual (cannot be executed from static analysis; concrete field/byte layout must be confirmed against `NakamotoSigners::make_signers_db_contract_id` and `SignerMessage` encoding, which were not fully retrieved in this session):
1. A legitimate signer S is registered in reward cycle N, occupying slot index `k` in signer-set page `p`. Per `signers.clar`/`signers_tests.rs`, S occupies slot `k` identically in every `.signers-{p}-{message_id}` sub-contract for that cycle.
2. S sends a normal, validly signed `StateMachineUpdate` chunk to `.signers-{p}-2` at `(slot_id=k, slot_version=v)`. An attacker observes this chunk (via p2p gossip or `GET /v2/stackerdb/{addr}/signers-{p}-2/chunks/{k}`).
3. The attacker takes the identical `(slot_id, slot_version, sig, data)` tuple and issues `POST /v2/stackerdb/{addr}/signers-{p}-1/chunks` (the sibling `BlockResponse` contract), where slot `k` is still fresh (version 0/1 unused).
4. `try_replace_chunk` looks up the expected signer for `(signers-{p}-1, k)` — which is the *same* address S — and `SlotMetadata::verify` succeeds because the digest never referenced the contract, only `(k, v, hash(data))`. The forged chunk is accepted and stored as though S had signed a `BlockResponse` message, then re-gossiped to peers.

Note: I was not able to fully verify from the indexed content whether `SignerMessage` type-prefix bytes would cause immediate downstream deserialization failure for genuinely cross-type payloads (this would limit — but not eliminate — impact to stale/garbage-slot pollution and re-gossip of forged data, rather than semantic message confusion). Confirming this, and the exact reward-cycle contract-naming scheme (`make_signers_db_contract_id`), would require reading `stackslib/src/chainstate/nakamoto/signer_set.rs` and `SignerMessage`'s codec implementation in full, which exceeded the remaining search budget in this session.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
