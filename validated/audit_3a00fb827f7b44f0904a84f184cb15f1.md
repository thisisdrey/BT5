Based on my investigation, the fee-refund promise to the relayer in the ETH-implicit Wallet Contract is dispatched unconditionally at parse time, *before* the underlying user-intended action (base-token transfer or ERC-20/NEP-141 transfer) is known to succeed, and the two promises are not chained together.

### Title
Relayer fee refund is paid unconditionally before the underlying transfer succeeds, allowing fee extraction without service - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
In `inner_rlp_execute`, when an Ethereum transaction is parsed as an `EOABaseTokenTransfer` or `ERC20Transfer` with a non-zero `fee`, a separate `Transfer` promise refunding the relayer is created and dispatched immediately, independent of the promise that performs the user's requested action.

### Finding Description
`internal::parse_rlp_tx_to_action` computes `tx_fee` from the signed Ethereum transaction and `inner_rlp_execute` fires a standalone refund promise to the relayer as soon as parsing succeeds: [1](#0-0) 
This refund promise (`env::promise_batch_create` + `env::promise_batch_action_transfer`) is not `.then()`-chained to the promise that actually performs the requested transfer/`ft_transfer` (built later in the same function via `action_to_promise(...)` or the NEP-141 registration flow), which is only invoked afterward and independently: [2](#0-1) 
Because NEAR receipts execute as independent, asynchronous units, the relayer's refund receipt does not depend on, and is not rolled back by, a later failure of the `storage_balance_of` → `storage_deposit` → `ft_transfer` chain (handled in `nep_141_storage_balance_callback`) or of the base-token/action promise (handled in `rlp_execute_callback`). If that downstream chain fails — e.g., the token contract panics, is paused, or the receiver's `ft_transfer` call is rejected for insufficient balance — `rlp_execute_callback` only refunds the *`caller_deposit`* (the 1 yoctoNEAR the wallet function attaches to itself), never the relayer fee that was already sent out: [3](#0-2) 
This is the same root-cause pattern as the Slingshot bug: an amount-bearing check/commitment ("the relayer will be compensated for successfully relaying this transfer") is settled *before* the actual operation it is meant to compensate is confirmed to succeed, so the outcome can diverge from what was promised — here, the wallet owner pays the fee even when the requested value transfer never lands.

### Impact Explanation
A user's ETH-implicit wallet balance is permanently decremented (the relayer refund) with no completed corresponding transfer to their intended recipient when the downstream action fails. Since the wallet does not verify that the action succeeded prior to disbursing the fee, and does not refund the fee on failure (only the 1-yocto caller deposit is refunded), this is a permanent loss of user funds to any relayer that submits (or a token contract that reliably causes failure of) a transaction whose main action fails. A relayer could deliberately target a token/contract known to revert `ft_transfer` (e.g., paused, blacklisted receiver, or a malicious/broken token) to repeatedly collect fees while never performing the underlying transfer, though only up to the fee specified by the user's signed transaction (bounded by `max_fee_per_gas * gas_limit`).

### Likelihood Explanation
The condition triggers whenever `fee` is non-zero and `predecessor_account_id != current_account_id` (i.e., an external relayer is used, which is the primary design use case for gas-sponsored relaying), combined with any failure of the wrapped action (token contract rejects the call, insufficient token balance, `storage_deposit`/`ft_transfer` batch failure, network-adversarial token, etc.). This is a normal operational path (not requiring privileged access), reachable by any unprivileged relayer or by natural contract failures, making likelihood moderate-to-high in production use of ERC-20/NEP-141 emulation through relayers.

### Recommendation
Chain the relayer refund transfer to only execute after the wrapped action promise resolves successfully (e.g., dispatch the refund from within `rlp_execute_callback`/`nep_141_storage_balance_callback` conditioned on `PromiseResult::Successful`), or hold the fee and refund it to the relayer only in the success branch, symmetric to how `caller_deposit` is already refunded on failure. Alternatively, use `Promise::and`/sequential `.then()` chaining so the fee-refund action is part of the same batch that must succeed together with the target action, rather than an independent parallel promise.

### Proof of Concept
1. Relayer submits an RLP-encoded Ethereum transaction representing an ERC-20 `transfer` call to a NEP-141 token contract, with `max_fee_per_gas * gas_limit` computing to a non-zero `tx_fee`.
2. `inner_rlp_execute` parses this as `EthEmulationKind::ERC20Transfer { fee, .. }` and immediately schedules a `Transfer` promise refunding `fee` to the relayer [1](#0-0) .
3. Separately, the wallet schedules `storage_balance_of` → (optionally `storage_deposit`) → `ft_transfer` on the token contract [2](#0-1) .
4. If the token contract's `ft_transfer` panics (e.g., insufficient balance, paused contract), `rlp_execute_callback` reports `success: false` and refunds only the `caller_deposit` (1 yoctoNEAR), not the already-paid relayer fee [4](#0-3) .
5. Result: the wallet owner's balance is reduced by `fee`, the relayer is paid, but no tokens were transferred — a permanent, unrecoverable loss of the fee amount without the corresponding service.
