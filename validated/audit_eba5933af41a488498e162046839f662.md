This confirms the analog: partition assignments (`relativePath → partitionID` mapping) are permanent once created and are never deleted, even after the repository at that relative path is removed via `RemoveRepository`/`repoutil.Remove`, as documented in `doc/transactions.md:70` and reflected in the implementation at `internal/gitaly/storage/storagemgr/partition_assigner.go:151-190` and `internal/gitaly/storage/storagemgr/partition_manager.go:344-363`. `repoutil.remove` (`internal/gitaly/repoutil/remove.go:39-67`) deletes the repository's on-disk data and its `RepositoryKey` KV entry, but never touches the `partition_assignment/<relative_path>` record, so a subsequent repository (or object pool) created at the same relative path is silently placed into the old partition alongside whatever unrelated repository/pool previously occupied it.

### Title
Stale partition assignments persist after repository deletion, causing repositories recreated at a reused relative path to be silently comingled into an unrelated partition - ([File: internal/gitaly/storage/storagemgr/partition_assigner.go])

### Summary
Gitaly assigns every repository relative path to a storage partition via a permanent key-value mapping (`partition_assignment/<relative_path> -> partition_id`). This mapping is created eagerly — even before the repository exists — but is never removed, including when the repository is deleted. If a relative path is later reused for a new, unrelated repository (e.g. after a project/fork/pool is deleted and a new one created at the same path), the new repository is automatically assigned to the stale partition ID instead of a fresh one, comingling it with whatever repositories/object pools were previously colocated there.

### Finding Description
`partitionAssigner.getPartitionIDRecursive` (`internal/gitaly/storage/storagemgr/partition_assigner.go:234-288`) first checks `partitionAssignmentTable.getPartitionID(relativePath)`; if an assignment already exists it is returned unconditionally, without verifying that the repository currently at that path is the same repository the assignment was originally made for.

`repoutil.remove` (`internal/gitaly/repoutil/remove.go:52-67`) only deletes the on-disk repository and its `storage.RepositoryKey` KV entry inside the transaction; it never calls into the `partitionAssignmentTable` to remove the `partition_assignment/<relative_path>` record. This is explicitly acknowledged in `doc/transactions.md:70`:

> "The assignment handling is fairly crude at the moment. The assignments are created before the repository is even created, and assignments are not deleted even if the repository is deleted."

This is structurally the same bug class as the reported `StabilityPool` issue: a resource identifier (collateral index / relative path) is reused for a new logical entity without clearing the accounting/assignment state tied to the old entity, so the new entity inherits stale state that was never meant for it.

Because partitions are the unit of transactional isolation and colocate object pools with all their members (`doc/transactions.md:56-60`), a repository silently landing in a stale partition means it is now sharing a write-ahead log, KV keyspace, and (via the pool-member alternate mechanism) potentially objects with a completely different set of repositories that the current owner/actor has no relationship to.

### Impact Explanation
A newly created repository or object pool that happens to reuse a relative path previously used and deleted is placed into the partition of the old, unrelated repository(ies)/pool instead of a fresh partition. This breaks the partitioning system's isolation guarantees (`doc/transactions.md:52`, "Transactions always operate against a single partition... Transactional guarantees only apply within a partition"), and can lead to unexpected cross-repository comingling of KV state and, in object-pool scenarios, colocated objects intended for a different set of members — a partition/isolation-escape rather than mere cosmetic bookkeeping.

### Likelihood Explanation
Reaching this requires only ordinary repository lifecycle operations — deleting a repository/pool via `RemoveRepository` and later creating a new repository at the same relative path — both of which are triggerable through standard, unprivileged Gitaly RPCs (`CreateRepository`, `CreateFork`, `CreateObjectPool`, `ReplicateRepository`, etc.). The relative-path reuse window depends on deployment specifics (e.g. `@hashed` paths are normally unique, but pools, wikis, snippets, and other repository kinds can have more predictable or reusable relative paths), and the maintainers already flag this as a known, unresolved gap (issue referenced at `internal/gitaly/storage/storagemgr/middleware.go:363-370`), which increases confidence this is a real, currently-open weakness rather than a hypothetical.

### Recommendation
When a repository is deleted (`repoutil.Remove` / `internal/gitaly/repoutil/remove.go`), remove or invalidate its `partition_assignment/<relative_path>` entry as part of the same transaction that deletes the repository and its `RepositoryKey`, so a relative path can only be re-assigned to a fresh partition ID (or is re-validated against the identity of the repository being created) rather than silently inheriting a stale assignment. Alternatively, make partition assignment/repository creation atomic as tracked in the referenced issue, and add a check that a partition assignment is only honored if the KV store still has a live `RepositoryKey` for that path.

### Proof of Concept
Conceptual reproduction (matches the pattern in `internal/gitaly/storage/storagemgr/partition_assigner_test.go` and `partition_manager_test.go`):
1. Create repository/pool `A` at relative path `P` (or a fork chain relying on `P`). It gets assigned `partition_assignment/P -> partitionID=N` (`partition_assigner.go:151-190`).
2. Write data / link members into `N`'s partition.
3. Delete `A` via `RemoveRepository` (`internal/gitaly/service/repository/remove.go:12-29` → `repoutil.Remove`). The on-disk repo and `RepositoryKey` are removed, but `partition_assignment/P` remains (`repoutil/remove.go:52-67`).
4. Create a brand-new, unrelated repository `B` at the same relative path `P` (e.g. via `CreateRepository`).
5. `partitionAssigner.getPartitionIDRecursive` finds the pre-existing `partition_assignment/P -> N` entry and returns `N` unchanged (`partition_assigner.go:236-264`), so `B` is started in partition `N` — the same partition previously used by unrelated repository `A` and any of its pool members — instead of a fresh partition. func (pa *partitionAssigner) getPartitionIDRecursive(ctx context.Context, relativePath string, recursiveCall bool, partitionHint storage.PartitionID, isRepositoryCreation bool) (storage.PartitionID, error) {
	// Check first whether the repository is already assigned into a partition. If so, just return the assignment.
	ptnID, err := pa.partitionAssignmentTable.getPartitionID(relativePath)
	if err != nil {
		if !errors.Is(err, storage.ErrPartitionAssignmentNotFound) {
			return 0, fmt.Errorf("get partition: %w", err)
		}

		// Repository wasn't yet assigned into a partition. This is the slow path. Requests attempting
		// to get or assign a partition ID concurrently are serialized.

		releaseLock, err := pa.acquireRepositoryLock(ctx, relativePath)
		if err != nil {
			return 0, fmt.Errorf("acquire repository lock: %w", err)
		}

		defer releaseLock()

		// With the repository locked, check first whether someone else assigned it into a partition
		// while we weren't holding the lock between the first failed attempt getting the assignment
		// and locking the repository.
		ptnID, err = pa.partitionAssignmentTable.getPartitionID(relativePath)
		if !errors.Is(err, storage.ErrPartitionAssignmentNotFound) {
			if err != nil {
				return 0, fmt.Errorf("recheck partition: %w", err)
			}

			// Some other goroutine assigned a partition between the failed attempt and locking the
			// repository.
			return ptnID, nil
		}
