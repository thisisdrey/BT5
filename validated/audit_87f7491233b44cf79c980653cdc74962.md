### Title
Stranded funds in closed `pallet-child-bounties` accounts have no reclaim path, unlike parent bounties - (File: `substrate/frame/child-bounties/src/lib.rs`)

### Summary
`pallet-bounties` was fixed to add a permissionless `reclaim_bounty_funds` extrinsic that sweeps any native/asset balance stranded in a closed bounty's sub-account back to the treasury [1](#0-0) , addressing the exact "funds sent to an account with no withdrawal path get stuck" bug class described in the external report. The sibling pallet, `pallet-child-bounties`, manages an analogous per-child-bounty sub-account (`child_bounty_account_id`) that is credited with native funds and drained via plain `Currency::transfer` calls in `claim_child_bounty` and `impl_close_child_bounty` [2](#0-1) [3](#0-2) , but it has **no equivalent sweep/reclaim dispatchable**. When a child bounty is closed or claimed, its storage record is removed [4](#0-3) [5](#0-4) , yet the deterministic `child_bounty_account_id(parent, child)` keeps existing and remains a valid destination for transfers. Any balance sent to it afterward (accidental transfer, dust, locked/held funds that a plain `transfer` doesn't move) is permanently stranded, with no dispatchable in `pallet-child-bounties` analogous to `reclaim_bounty_funds` to move it out.

### Finding Description
- `child_bounty_account_id` derives a stable, guessable sub-account for every `(parent_bounty_id, child_bounty_id)` pair [6](#0-5) .
- On `claim_child_bounty`, only `curator_fee` and `payout` (derived from `free_balance` at call time) are moved out via `Currency::transfer`, and the child-bounty record is deleted right after [7](#0-6) .
- On `impl_close_child_bounty` (used by `close_child_bounty`), the whole `free_balance` is transferred to the parent bounty account and the record is deleted [8](#0-7) .
- In both paths, once the storage record (`ChildBounties`) is removed, there is no code path in `pallet-child-bounties` that ever looks at this specific sub-account again, and `pallet-bounties`' own `reclaim_bounty_funds` only operates on parent bounty accounts (`Self::bounty_account_id(bounty_id)`), not child-bounty accounts [9](#0-8) .
- This is precisely the pattern that was identified and fixed for the parent-bounty pallet (issue #10996, PR "add `reclaim_bounty_funds`" and PR "Bounties return balance and assets on close") — closed bounty accounts could retain stray/leftover balance with nothing to reclaim it. The child-bounty pallet received only a `patch` bump in that same PR bundle [10](#0-9) , indicating no equivalent fix was carried over, and no `reclaim_bounty_funds`-style call exists anywhere in `pallet-child-bounties` (confirmed by the absence of any such extrinsic in `lib.rs`, `weights.rs`, or `benchmarking.rs` for this pallet).
- Existing guards do not stop this: nothing prevents a third party from transferring balance directly to `child_bounty_account_id(parent, child)` after the child bounty has been claimed/closed (the account is a normal `AccountId`, reachable by any `balances::transfer`). Once sent, there is no signed, root, or permissionless extrinsic in the child-bounties pallet that reads or moves balance out of an account not tracked by a live `ChildBounties` entry.

### Impact Explanation
Funds transferred to a stale/closed child-bounty sub-account become permanently locked with no on-chain path to recovery short of a runtime migration, matching the "permanent user-fund lock" impact category. While this is not a runtime-crashing or origin-escalation bug, it is a public, unprivileged-triggerable fund-loss condition: any account can create this state (deliberately or accidentally) by sending tokens to a deterministic, computable address, and neither the child-bounty holder, the parent curator, `RejectOrigin`, nor treasury can currently reclaim it via the exposed dispatchables. It is directly analogous in class and impact to the resolved `MPROVesting.sol` issue (ether permanently stuck because no withdrawal path existed).

### Likelihood Explanation
Likelihood is moderate: this requires either an accidental transfer to the sub-account after closure/claim, or a slightly-early transfer that lands after the balance sweep executes (e.g., a transfer racing the block in which `claim_child_bounty`/`close_child_bounty` executes, or funds sent to reference the account post-closure since the address remains computable and stable indefinitely). No malicious peer/validator/relayer/admin action is required — it is purely a self-inflicted or third-party transfer to a known deterministic account, satisfying the "unprivileged attacker" and "public entrypoint" criteria (ordinary `balances.transfer`).

### Recommendation
Add a `pallet-child-bounties` extrinsic mirroring `pallet-bounties::reclaim_bounty_funds`: a permissionless call that, for a `(parent_bounty_id, child_bounty_id)` no longer present in `ChildBounties` storage, sweeps any remaining native (and configured asset) balance from `child_bounty_account_id(parent_bounty_id, child_bounty_id)` to the parent bounty account (or treasury), following the same `Pays::No`-on-success/`Pays::Yes`-on-no-op pattern used in `pallet-bounties` to avoid griefing.

### Proof of Concept
1. Create and fund a parent bounty; add and accept a child bounty curator; note `child_acct = ChildBounties::child_bounty_account_id(parent_id, child_id)`.
2. Complete the normal flow: `award_child_bounty` → `claim_child_bounty`. The `ChildBounties` storage entry for `(parent_id, child_id)` is now removed [4](#0-3) , but `child_acct` still exists as a valid account.
3. Any account calls `Balances::transfer(child_acct, X)` (accidentally, or the same transfer pattern demonstrated for the parent-bounty analog in `reclaim_bounty_funds_works_after_accidental_refund` [11](#0-10) ).
4. There is no extrinsic in `pallet-child-bounties` that can move `X` out of `child_acct`: `add_child_bounty` for the same `(parent_id, child_id)` index cannot be re-issued to reuse the account meaningfully, `close_child_bounty`/`claim_child_bounty` require a live `ChildBounties` entry (`InvalidIndex` otherwise), and `pallet-bounties::reclaim_bounty_funds` only targets `bounty_account_id(parent_id)`, not `child_bounty_account_id`. `X` remains permanently stuck in `child_acct`.

		///
		/// Permissionless. Moves all remaining assets from a closed bounty's account back to the
		/// treasury in a single call. Which assets are swept depends on the `TransferAllAssets`
		/// configuration.
		///
		/// The call is free if funds were reclaimed and paid otherwise, so no-op calls cannot be
		/// used to grief the network. Emits `BountyFundsReclaimed` on success.
		///
		/// ## Complexity
		/// - O(A) where A is the number of relevant assets configured in `TransferAllAssets`.
		#[pallet::call_index(11)]
		#[pallet::weight(<T as Config<I>>::WeightInfo::reclaim_bounty_funds())]
		pub fn reclaim_bounty_funds(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
		) -> DispatchResultWithPostInfo {
			ensure_signed(origin)?;

			// A live bounty still manages its account, so leave it untouched.
			ensure!(!Bounties::<T, I>::contains_key(bounty_id), Error::<T, I>::BountyStillActive);

			debug_assert!(
				T::ChildBountyManager::child_bounties_count(bounty_id) == 0,
				"child bounties should not exist for a closed bounty"
			);

			let bounty_account = Self::bounty_account_id(bounty_id);
			let treasury_account = Self::account_id();

			let transferred = T::TransferAllAssets::force_transfer_all_assets(
				&bounty_account,
				&treasury_account,
			)?;

			// Free only if something moved, otherwise paid to prevent griefing.
			if !transferred {
				return Ok(Pays::Yes.into());
			}

			Self::deposit_event(Event::<T, I>::BountyFundsReclaimed { bounty_id });

			Ok(Pays::No.into())
		}

#[test]
fn reclaim_bounty_funds_works_after_accidental_refund() {
	ExtBuilder::default().build_and_execute(|| {
		Balances::make_free_balance_be(&Treasury::account_id(), 101);

		// Full lifecycle: propose → approve → fund → curator → award → claim
		assert_ok!(Bounties::propose_bounty(RuntimeOrigin::signed(0), 50, b"12345".to_vec()));
		assert_ok!(Bounties::approve_bounty(RuntimeOrigin::root(), 0));
		go_to_block(2);

		let fee = 4;
		Balances::make_free_balance_be(&4, 10);
		assert_ok!(Bounties::propose_curator(RuntimeOrigin::root(), 0, 4, fee));
		assert_ok!(Bounties::accept_curator(RuntimeOrigin::signed(4), 0));
		assert_ok!(Bounties::award_bounty(RuntimeOrigin::signed(4), 0, 3));
		go_to_block(5);
		assert_ok!(Bounties::claim_bounty(RuntimeOrigin::signed(1), 0));

		// Bounty is now fully closed; verify it is gone from storage.
		assert!(pallet_bounties::Bounties::<Test>::get(0).is_none());

		let bounty_account = Bounties::bounty_account_id(0);
		// Account should already be empty after claim.
		assert_eq!(Balances::free_balance(&bounty_account), 0);

		// Simulate someone accidentally sending funds to the closed bounty account.
		Balances::make_free_balance_be(&bounty_account, 25);
		assert_eq!(Balances::free_balance(&bounty_account), 25);

		let treasury_before = Treasury::pot();

		// Dust the account.
		assert_ok!(Bounties::reclaim_bounty_funds(RuntimeOrigin::signed(99), 0));
		assert_eq!(last_event(), BountiesEvent::BountyFundsReclaimed { bounty_id: 0 },);

		assert_eq!(Balances::free_balance(&bounty_account), 0);
		assert!(Treasury::pot() > treasury_before);
	});
}
