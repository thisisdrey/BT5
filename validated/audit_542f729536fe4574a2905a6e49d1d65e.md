### Title
Heap buffer over-read via missing bounds checks in ijar's ZIP central directory parser - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar's ZIP reader parses each Central Directory Header (CDH) entry using attacker-controlled length fields (`file_name_length`, `extra_field_length`, `file_comment_length`, and the Zip64 extra-field `data_size`) without ever validating that the cursor `p`/`extra_p` stays within the bounds of the memory-mapped input file.

### Finding Description
Unlike `InputZipFile::ProcessLocalFileEntry`, which calls `EnsureRemaining()` before every variable-length read [1](#0-0) , `ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from the untrusted CDH and advances `p`/`extra_p` by those attacker-supplied amounts with no `EnsureRemaining`-style check against `input_file_->Length()`: [2](#0-1) 

The `memcpy(filename, p, len)` call bounds the *destination* write to `PATH_MAX` via `filename_size`, but the *source* pointer `p` can already point far past the end of the mmap'd file, so this is an out-of-bounds heap read on the mapped input file whenever `file_name_length`/`extra_field_length`/`file_comment_length`/Zip64 `data_size` values exceed the remaining file bytes. The Zip64 extra-field loop `extra_p += data_size` similarly walks past the mapped region using an attacker-controlled 16-bit value, and `get_u8le(extra)` in the Zip64 branch reads 8 bytes from that unchecked location. This function is invoked in a loop from `CalculateOutputLength()` [3](#0-2)  and drives the two-pass ijar processing (size calculation, then actual copy) that runs on every `.jar` file ijar/`stamp_jar` touches, per `java_common.run_ijar` / the ijar tool entry point [4](#0-3) .

The comment above the function asserts "the central directory is always followed by another data structure that has a signature, so parsing it this way is safe" — but this assumption only holds for well-formed archives; a crafted jar can set arbitrarily large length fields that walk `p` past the end of the mapped region well before any subsequent signature check is reached.

### Impact Explanation
ijar operates on `.jar` files supplied as build inputs — e.g., prebuilt jars fetched from an external Maven/HTTP repository (`http_jar`, `maven_install`) whose bytes are entirely attacker-controlled even when the download's sha256/integrity check passes (the checksum only certifies transport integrity of the bytes the attacker chose to publish, not their internal structural well-formedness). Because ijar mmaps the file and never bounds-checks CDH-derived offsets, an attacker-crafted jar with oversized `file_name_length`/`extra_field_length`/`file_comment_length`/Zip64 fields causes ijar to read adjacent heap/mmap-region memory out of bounds. Depending on layout this manifests as a crash (denial of the build action) or, more concerningly, as inclusion of adjacent-memory bytes into the emitted filename buffer/copied metadata that then gets written into the resulting interface jar and central-directory records — a heap over-read into build outputs.

### Likelihood Explanation
High reachability: any target depending on an externally-supplied `.jar` (common for Java rules using `http_jar`/`maven_install`) runs it through ijar/`stamp_jar` as part of ordinary compilation, with default flags. No opt-in or unusual configuration is required — the vulnerable path is on the default `run_ijar` action used to generate compile-time interface jars from dependencies. The attacker only needs to publish the malicious jar at the URL declared in the dependency (matching whatever checksum they choose), which is squarely within the unprivileged-attacker-publishing-content threat model.

### Recommendation
Add the same `EnsureRemaining`-style bounds validation used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry`: before consuming `file_name_length`, `extra_field_length`, `file_comment_length` bytes (and before each Zip64/extra-field `data_size` advance), verify the remaining distance from `p`/`extra_p` to the end of the mapped input (or to `central_dir_` bounds) and fail closed (as `EnsureRemaining` already does for local headers) rather than trusting attacker-declared lengths.

### Proof of Concept
A `BuildIntegrationTestCase`/shell test analogous to the existing `MalformedExtraField` singlejar test [5](#0-4)  should be added for ijar: craft a minimal ZIP with a valid EOCD pointing at a single CDH whose `file_name_length` (or `extra_field_length`/`file_comment_length`) is set to a value exceeding the actual remaining bytes in the file (e.g., `0xFFFF`), pass it to the `ijar` binary via `OpenFilesAndProcessJar`, and run under ASan/Valgrind to demonstrate the heap-buffer-overflow (over-read) reported by the sanitizer when `ProcessCentralDirEntry` walks `p`/`extra_p` past the mapped file's end — mirroring how `third_party/ijar/test/ijar_test.sh` already drives the `ijar` binary end-to-end on crafted jars.

u8 InputZipFile::CalculateOutputLength() {
  const u1* current = central_dir_;

  u8 compressed_size = 0;
  u8 uncompressed_size = 0;
  u8 skipped_compressed_size = 0;
  u4 attr;
  u8 offset;
  char filename[PATH_MAX];

  while (true) {
    u8 file_compressed, file_uncompressed;
    if (!ProcessCentralDirEntry(current,
                                &file_compressed, &file_uncompressed,
                                filename, PATH_MAX, &attr, &offset)) {
      break;
    }

    if (processor->Accept(filename, attr)) {
      compressed_size += (u8) file_compressed;
      uncompressed_size += (u8) file_uncompressed;
    } else {
      skipped_compressed_size += file_compressed;
    }
  }

  // The worst case is when the output is simply the input uncompressed. The
  // metadata in the zip file will stay the same, so the file will grow by the
  // difference between the compressed and uncompressed sizes.
  return (u8) input_file_->Length() - skipped_compressed_size
      + (uncompressed_size - compressed_size);
}

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
