### Title
Unbounded in-memory read of attacker-controlled Git commit messages in `GetCommitMessage`/`GetCommitMessages` RPC - ([File: internal/git/catfile/commit.go])

### Summary
`GetCommitMessages` streams commit messages by calling `catfile.GetCommitMessage`, which unconditionally slurps the entire commit body into memory via `io.ReadAll(object)` with no size limit, unlike other Gitaly code paths (`ReadObjectWithLimit`) that were specifically hardened against this.

Git does not impose any inherent limit on commit message size, so an ordinary user who can push a commit (or fork/import a repository containing one) can create a commit whose message is arbitrarily large (many gigabytes), and any subsequent `GetCommitMessages` (or `GetCommitWithTrailers`/`GetCommit` consumers relying on `splitRawCommit`) call against that commit will attempt to allocate the full message in memory in a single `io.ReadAll` before any data is streamed back to the client.

### Impact Explanation
Because the read is fully synchronous and unbounded, a small, cheap, attacker-authored commit (a git commit object with a multi-gigabyte message) can force the Gitaly process to allocate memory proportional to the attacker-chosen size on every retrieval. Repeated or parallel requests targeting the same or different such commits can be used to grief the server's memory, causing increased GC pressure, latency spikes for co-located tenants, or process OOM — a resource-exhaustion analog of the "gas griefing" pattern described in the report, where the caller unconditionally pays the cost of copying attacker-controlled data into memory.

### Likelihood Explanation
Creating an oversized commit message requires no special privilege — any user capable of pushing commits, or providing an import/mirror source that Gitaly fetches, can craft such an object. Triggering the vulnerable code path only requires calling the already-existing `GetCommitMessages` RPC (or paths that use `GetCommitWithTrailers`) against the crafted commit, which is a standard, unauthenticated-at-this-layer, ordinary-user-reachable operation.

### Recommendation
Apply the same defensive pattern already used in `internal/git/localrepo/objects.go`'s `ReadObjectWithLimit`: wrap the object reader in `io.LimitReader` with a configurable maximum size before calling `io.ReadAll` in `splitRawCommit`, and return a clear error (or truncate with a flag, consistent with how `PatchParser` handles oversized diffs via `patchLimit`/`TooLarge`) when the object exceeds the limit, rather than allocating unboundedly.

### Proof of Concept
1. Create a repository and push a commit whose message body is several gigabytes of arbitrary bytes (Git does not restrict commit message length).
2. Call the `GetCommitMessages` RPC with that commit's OID.
3. Observe that `catfile.GetCommitMessage` → `splitRawCommit` performs `io.ReadAll(object)` on the full object before any streaming response is produced, causing a single large memory allocation proportional to the attacker-chosen commit size; repeating this concurrently amplifies memory pressure on the Gitaly server.

Note: I was not able to fully trace every consumer of `catfile.GetCommit`/`GetCommitWithTrailers` (used across `internal/git/localrepo/commit.go`, `internal/gitaly/service/operations/*.go`, etc.) within the available search budget, so there may be additional reachable call sites beyond `GetCommitMessages` that are similarly affected; a full audit of `splitRawCommit` callers would be needed to size the complete blast radius.

func splitRawCommit(object git.Object) ([]byte, []byte, error) {
	raw, err := io.ReadAll(object)
	if err != nil {
		return nil, nil, err
	}

	header, body, _ := bytes.Cut(raw, []byte("\n\n"))

	return header, body, nil
}
