### Title
Unbounded array-length field in precompiled contract call-data allocation causes node memory exhaustion - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytesArray`, `extractBytes32Array`, and `extractSigArray` read an attacker-controlled 32-byte word from TVM call data and use it directly as an array length to allocate a Java array, with no upper bound check, unlike the neighboring `ModExp` precompile which explicitly enforces `UPPER_BOUND` on its length fields.

### Finding Description
`extractBytesArray`/`extractBytes32Array`/`extractSigArray` take `len = words[offset].intValueSafe()` straight from the calldata word and immediately allocate `new byte[len][]` before any content is validated: [1](#0-0) [2](#0-1) [3](#0-2) 

`intValueSafe()` clamps the DataWord to an `int`, so `len` can be driven up to `Integer.MAX_VALUE` by simply crafting the corresponding calldata word to a large value, with no dependency on how much actual calldata was supplied. This is analogous to the referenced CVE, where the MFI `sglist` size field from guest-controlled input is used to size an allocation without an upper-bound check, leading to unconstrained host memory consumption. Here, the analogous “size field” is the ABI length word inside TVM precompile input data, and the allocation happens inside the java-tron node process itself (not inside a sandboxed VM), so a large `new byte[Integer.MAX_VALUE][]` allocation attempt directly stresses/exhausts the node’s heap.

This is contrasted with `ModExp`, which was hardened with an explicit `UPPER_BOUND = 1024` check on `baseLen`, `expLen`, `modLen` before doing any further processing: [4](#0-3) 
No equivalent bound exists for the array-length fields consumed by `extractBytesArray`/`extractBytes32Array`/`extractSigArray`.

### Impact Explanation
A crafted contract call reaching a precompiled contract that uses these helper methods (multi-signature / batch signature validation precompiles) can force the node to attempt allocation of an oversized `byte[][]` array. This can throw `OutOfMemoryError` or otherwise cause severe GC pressure/heap exhaustion on the validating/executing node, potentially crashing the node process or making it unresponsive to further transaction processing — a denial-of-service impact consistent with the "host memory consumption" impact of the referenced CVE.

### Likelihood Explanation
I was unable to fully confirm, within the available tool budget, the exact energy-cost function (`getEnergyForData`) charged for the precompiled contract(s) that call these three helper methods, nor definitively confirm whether an earlier length/energy check elsewhere in the call chain bounds `len` before these methods execute. Without that confirmation, I cannot certify that this path is reachable at low/bounded cost by an ordinary unprivileged caller, so likelihood is uncertain and should be validated by inspecting the full `ValidateMultiSign`/`BatchValidateSign`-style precompile classes' `getEnergyForData` and `execute` implementations plus any upstream validation of the ABI-encoded array length before it reaches `extractBytesArray`/`extractBytes32Array`/`extractSigArray`.

### Recommendation
Add an explicit upper bound (mirroring `ModExp.UPPER_BOUND`) on `len` in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` before allocating `new byte[len][]`, and/or make the energy cost for these precompiles scale with the declared array length so oversized inputs are rejected or heavily charged before allocation occurs.

### Proof of Concept
Not fully verified — a concrete PoC transaction requires confirming which precompiled contract(s) invoke `extractBytesArray`/`extractBytes32Array`/`extractSigArray` and their exact energy cost formula, which I could not complete within the tool-call budget. Conceptually: craft TVM call data for the corresponding precompile such that the length word at the parsed offset is set to a very large value (e.g., close to `Integer.MAX_VALUE`), triggering the allocation in the cited methods.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
