### Title
Unbounded reference-array allocation in TVM `BatchValidateSign`/`ValidateMultiSign` precompiles allows attacker-triggered OOM DoS - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The precompiled contracts `ValidateMultiSign` and `BatchValidateSign` decode ABI arrays from raw TVM call data by reading a length word directly out of attacker-controlled calldata and immediately allocating a Java array of that length, *before* validating that the length is bounded or that the underlying data actually contains that many elements. This mirrors the CVE-2025-55647 pattern in GPAC (`mp4_mux_cenc_insert_pssh`), where an attacker-controlled size/count field from a crafted input is used to pre-allocate memory without validation, causing an out-of-memory denial of service.

### Finding Description
`extractBytes32Array` reads the array length straight from a `DataWord` and allocates a reference array of that size with no bound check: [1](#0-0) 

`extractBytesArray`/`extractSigArray` do the same: [2](#0-1) 

In `BatchValidateSign.doExecute`, a length/size check (`sigArraySize`/`addrArraySize > MAX_SIZE`) is only performed when the chain-parameter-gated feature `VMConfig.allowTvmSelfdestructRestriction()` is enabled. The `addresses` extraction via `extractBytes32Array` is invoked **unconditionally**, outside that gate: [3](#0-2) 

Similarly, in `ValidateMultiSign.execute`, the `MAX_SIZE` bound check on `sigArraySize` and the safer `extractSigArray` path (which reads a fixed 65-byte signature per item rather than trusting a per-item length) are only used when `allowTvmSelfdestructRestriction()` is true; otherwise `extractBytesArray` is invoked with the raw, unchecked `len`: [4](#0-3) 

`words[offset].intValueSafe()` can return any value up to `Integer.MAX_VALUE` for a maliciously crafted 32-byte word, independent of how much actual calldata was submitted: [5](#0-4) 

Because `new byte[len][]` (or `new byte[len]` in `extractBytesArray`/`extractSigArray`) allocates the array eagerly, a single small transaction can force the JVM to attempt allocating gigabytes of memory for a reference array, before any subsequent bounds-checked access to `words[...]` would throw and abort. This is functionally the same root cause as the GPAC CVE: trusting an attacker-supplied length/count field to size a memory allocation without validating it against the real payload size or an upper bound first.

### Impact Explanation
Any account can call a smart contract that in turn calls the `ValidateMultiSign` (address `0x66...`, invoked from a `TVM` contract) or `BatchValidateSign` precompile with crafted call data, or directly submit a `TriggerSmartContract` transaction targeting a contract that performs this call. If `allowTvmSelfdestructRestriction()` is not (yet) active on the target network — the feature is toggled by a chain parameter/proposal, meaning it may be off on custom, private, or not-fully-upgraded java-tron deployments — the unchecked path is taken and a single malicious value can trigger an attempted huge array allocation, resulting in `OutOfMemoryError` and node crash/halt (denial of service for block production/validation). This matches the "node crash or halt" impact class allowed by scope.

### Likelihood Explanation
Likelihood is *conditional*: on networks where `allowTvmSelfdestructRestriction` has already been activated via governance, the length checks (`sigArraySize`/`addrArraySize > MAX_SIZE`) mitigate `ValidateMultiSign`'s vulnerable path but the `addresses` extraction in `BatchValidateSign` (`extractBytes32Array`) remains **unconditionally unchecked before allocation**, since that code path is not wrapped by the feature gate at all. Exploitation requires only crafting call data with a large 32-byte word for the array-length field; no special privileges, signatures, or high fees are needed beyond the cost of a `TriggerSmartContract` call, which is inexpensive relative to potential impact.

### Recommendation
- Move the `MAX_SIZE` bound check for `addrArraySize` (and any other extracted lengths) so it happens before *every* call to `extractBytes32Array`/`extractBytesArray`/`extractSigArray`, regardless of `allowTvmSelfdestructRestriction()`.
- In `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` themselves, validate `len` against a hard maximum (e.g., `MAX_SIZE`) and against the actual bound implied by `words.length`/`data.length` before allocating any array.
- Consider making these array-length sanity checks unconditional baseline behavior rather than gated behind a governance-controlled fork flag, since the underlying allocation-before-validation bug should not depend on chain configuration.

### Proof of Concept
1. Build a `TriggerSmartContract` transaction that calls a helper contract (or calls the precompile address directly via low-level `staticcall`/`call`) targeting the `BatchValidateSign` precompile address.
2. Construct call data per the ABI header layout expected by `BatchValidateSign.doExecute` (`hash`, offset to signatures array, offset to addresses array) such that the word at the "addresses" length position (`words[words[2].intValueSafe() / WORD_SIZE]`) encodes a very large value, e.g. `0x000000000000000000000000000000000000000000000000000000FFFFFFF0` (interpreted by `intValueSafe()` as `Integer.MAX_VALUE`-scale).
3. Submit this transaction on a network where `allowTvmSelfdestructRestriction()` is not active (default/un-upgraded chain configuration).
4. `extractBytes32Array` executes `new byte[len][]` with `len` ~2^31, causing the executing/validating node to attempt an enormous heap allocation, throwing `OutOfMemoryError` and potentially crashing or hanging the TVM execution thread/node during block validation.

**Uncertainty note:** I could not fully verify from the index whether `allowTvmSelfdestructRestriction()` is currently activated (default `1`) on the production TRON mainnet chain state, since the runtime dynamic-properties default value wasn't found in the indexed portion of `DynamicPropertiesStore.java`. If it is already permanently active on mainnet with the associated `MAX_SIZE` checks always applied for all fields, only the `BatchValidateSign` "addresses" path (`extractBytes32Array`, unconditionally unguarded) remains exploitable; the `ValidateMultiSign`/`signatures` path would be considered mitigated by governance. A Devin session with full repo/file access could confirm the exact default and any hardfork activation status.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
