### Title
Bazel `git_repository`/`new_git_repository` re-enables `file://` submodule protocol, allowing attacker-controlled `.gitmodules` to escape the checkout and read/execute arbitrary local host content - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
Analogous to CVE-2021-43286 (GoCD executing attacker-supplied Git URL content without restriction), Bazel's `git_repository`/`new_git_repository` repo rules downgrade a Git security control (`protocol.file.allow`) that upstream Git deliberately defaults to a restricted value for content originating from a fetched repository (`.gitmodules`), rather than from the trusted invoking user.

### Finding Description
When `init_submodules` or `recursive_init_submodules` is set, `update_submodules` in `git_worker.bzl` runs `git submodule update --init [--recursive] --checkout --force` with `-c protocol.file.allow=always` hard-coded: [1](#0-0) 

This override was added to work around a Git compatibility bug in local submodule setups (bazelbuild/bazel#17040), per the inline comment: [2](#0-1) 

Upstream Git deliberately restricts `protocol.file.allow` for submodule URLs sourced from a fetched repository's `.gitmodules` file (untrusted content the remote author controls), because that file is data pulled from the network, not something the invoking user typed. Bazel's blanket `protocol.file.allow=always` removes that restriction for every `git_repository`/`new_git_repository` invocation with submodules enabled, regardless of whether `remote` is pinned by immutable `commit` or by a mutable `tag`/`branch`.

The `.gitmodules` file lives inside the fetched tree and is therefore entirely attacker-controlled whenever the `remote`/`tag`/`branch` combination is not content-addressed: `git_repository` documents that only the `commit` attribute yields a reproducible fetch, while `tag`/`branch` fetch whatever content the origin currently serves for that ref. A hostile or compromised origin (or one that force-pushes/moves a tag) can therefore serve a `.gitmodules` referencing a submodule URL like `file:///absolute/path/on/build/host` (e.g., pointing at another already-cloned Bazel external repository, a user's home directory checked out as a git repo, or an internal path containing a `.git` with hooks). With `protocol.file.allow=always` forced, `git submodule update --init --recursive` follows this URL and clones/checks out that local path into the submodule's target directory inside the current repository's working tree — content that Bazel then treats as ordinary fetched repository content and packages into the external repo consumed by the build.

Note that Bazel already implements explicit anti-escape logic for `strip_prefix` and `add_prefix` in `git.bzl` (checking `.realpath` stays under the checkout root): [3](#0-2) 
but no equivalent check exists for submodule paths/targets brought in via `.gitmodules`, so the containment invariant enforced elsewhere in the same file is absent for submodule content.

### Impact Explanation
This allows a hostile/compromised git origin (or a moved tag/branch) to make Bazel read/copy arbitrary local filesystem content reachable to the build user (as a `file://` repository) into the workspace of a project using `git_repository`/`new_git_repository` with `init_submodules`/`recursive_init_submodules` — a read outside the intended external-repository boundary. If the referenced local path is itself a Git repository containing configured hooks or an `.git/hooks` directory reachable during clone/checkout, this can extend to local code execution on the build machine, matching the "execute arbitrary code via a crafted Git-related input" bug class in the GoCD analog.

### Likelihood Explanation
Requires: (1) a `git_repository`/`new_git_repository` usage with `init_submodules`/`recursive_init_submodules` enabled and a `remote`/`tag`/`branch` (not solely a pinned `commit`) that an attacker can influence — e.g., a mutable branch/tag on a third-party or compromised host, matching the threat model of "an outsider who publishes content a victim's build consumes." No credentials, sandbox breakout, or local machine access is needed by the attacker; only control over content served for that Git ref.

### Recommendation
Do not globally force `protocol.file.allow=always` for submodule updates. Restrict the override to cases where it's actually needed (e.g., only when the submodule URL is same-origin/local-testing), or scope it via `submodule.<name>.active`/URL allow-listing, or default to Git's safer `protocol.file.allow=user` and only broaden it under an explicit, documented opt-in attribute for repositories known to be trusted (e.g., only when `commit` is pinned and the remote is a trusted, non-network origin).

### Proof of Concept
1. Create a git repo `evil` under `origin_dir` with a `.gitmodules` entry: `[submodule "x"] path = x url = file:///home/victim/.ssh` (or any sensitive local directory that is a valid git-ish tree, e.g., another Bazel external repo checkout).
2. In `MODULE.bazel`, use `git_repository(name="dep", remote=origin_dir, branch="main", recursive_init_submodules=True)`.
3. Run `bazel fetch @dep`. Because `git_worker.bzl`'s `update_submodules` runs with `-c protocol.file.allow=always`, the `x` submodule is cloned from the local `file://` path into the external repo directory, exfiltrating/copying local filesystem content that should not be reachable from `evil`'s declared remote.
4. This can be encoded as a `src/test/shell/bazel/starlark_git_repository_test.sh` case analogous to the existing `test_git_repository_invalid_commit` (lines 913–927) which already demonstrates the test harness pattern for asserting that untrusted git ref/URL-derived content does not escape into unintended execution/read paths: [4](#0-3)

def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
