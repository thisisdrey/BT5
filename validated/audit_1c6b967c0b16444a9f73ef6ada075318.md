### Title
Missing `write_freq` throttle enforcement in `try_replace_chunk`/`insert_chunk` allows unlimited-rate authenticated writes via RPC POST - ([File: stackslib/src/net/stackerdb/db.rs])

### Summary
`try_replace_chunk` (db.rs:400-438) enforces chunk-size, signature, monotonic version, and `max_writes` bounds, but never checks `config.write_freq` before calling `insert_chunk` (db.rs:374-396). Since the RPC endpoint `POST /v2/stackerdb/:principal/:contract/chunks` calls `try_replace_chunk` directly (poststackerdbchunk.rs:197), a legitimate owner of a slot can submit strictly-increasing-version chunks (including empty `data`) back-to-back with no wall-clock delay, violating the documented `write_time`-since-last-write ≥ `write_freq` invariant.

### Finding Description
`write_freq` is loaded from the controlling smart contract into `StackerDBConfig` (`config.rs:496-503`) and is only consumed in `StackerDBSync::make_chunk_request_schedule` (`sync.rs:340`), where it merely suppresses *fetching* from peers whose last-write timestamp is too recent — it is a sync-scheduling heuristic, not a write admission-control check. The actual write path, `try_replace_chunk` → `insert_chunk` (db.rs:400-438, 374-396), never reads `write_time` from `slot_validation` to compare against `write_freq`; it unconditionally executes the `UPDATE ... SET write_time = ?5` statement using the current wall-clock time. The RPC POST handler validates content-length and JSON shape, then calls `try_replace_chunk` on every request with no additional per-request throttle, so each valid, strictly-incrementing, correctly-signed chunk (even with `data.len()==0`) is accepted and its `write_time` bumped to "now," regardless of how recently the previous write occurred.

One real bound does exist: `slot_desc.slot_version > self.config.max_writes` is rejected (db.rs:430-436), so the *total* number of writes to a given slot over its lifetime is capped by `max_writes` from the controlling contract — the churn is not literally infinite, but it is unthrottled in time, i.e., all `max_writes` writes can be submitted back-to-back with no `write_freq` delay.

### Impact Explanation
A slot owner can, within their `max_writes` budget, submit chunks at whatever rate the RPC server can process instead of the rate the contract's `write-freq` dictates. Each accepted write also triggers a relay broadcast of `StackerDBPushChunkData` to the p2p network (poststackerdbchunk.rs:315-324), so the write also causes gossip fan-out to peers at unthrottled frequency. This is a bounded compute/relay-amplification issue (bounded by `max_writes`) rather than an unauthenticated write or forged-data propagation — the writer is a legitimate slot owner with a valid signature, and each write is genuinely authorized. Severity is limited by the `max_writes` cap and by the fact this requires the attacker to already legitimately hold a slot (own signing key).

### Likelihood Explanation
Precondition: attacker must legitimately own a StackerDB slot (has a valid signer key for it), which is within the allowed threat model. No secret, admin role, or other party's key is needed. The RPC port must be reachable, which it normally is. The attacker can then trivially script `max_writes` rapid POSTs with strictly increasing `slot_version` and empty `data`.

### Recommendation
Enforce `config.write_freq` inside `try_replace_chunk` by comparing the candidate write's timestamp against `slot_validation.write_time` (already fetched) and rejecting with a new `net_error` (e.g. `TooFrequentWrite`) if `now < slot_validation.write_time + config.write_freq`, mirroring the check currently only done heuristically in `sync.rs:340`. This closes the gap for both the RPC path and any other direct caller of `try_replace_chunk`.

### Proof of Concept
Rust test in `stackslib/src/net/stackerdb/tests/db.rs`-style harness:
1. Instantiate a `StackerDBs` with a config where `write_freq = 60` and `max_writes` ≥ 5.
2. Construct a slot owner keypair, sign 5 `StackerDBChunkData` messages with `data = vec![]` and `slot_version = 1..=5`.
3. Call `tx.try_replace_chunk(...)` for each in a tight loop with no `sleep`, and assert all 5 calls return `Ok(())` (i.e., `try_replace_chunk` never returns an error attributable to timing) — confirming that the wall-clock throttle from `write_freq` is absent at this layer, in contrast to `sync.rs:340`'s explicit `write_ts + self.write_freq > now` check.     pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
