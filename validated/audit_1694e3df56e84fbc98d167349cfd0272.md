Investigation notes: Go's `net/textproto.readMIMEHeader` (used by `net/http` for both client and server) actually *does* implement RFC 7230 §3.2.4 obs-fold header continuation via `readContinuedLineSlice`/`skipSpace`, which treats any line beginning with a space or tab as a continuation of the previous header line [1](#0-0) . This is the opposite condition from the reported httpd bug (which never implements obs-fold at all), and it's long-standing, documented, RFC-compliant behavior — not an undiscovered bug [2](#0-1) . Since both `net/http`'s client and server (and `httputil.ReverseProxy`, which is built on the same `net/http` stack) use this identical parser, there is no front-end/back-end parser disagreement within the Go standard library itself to construct a smuggling primitive analogous to the httpd CVE. Producing an actual smuggling scenario would require pairing this with a *different* HTTP implementation that disagrees on obs-fold handling, which is outside the scope of the Go repository's own production code.
