### Title
Out-of-bounds read when parsing a crafted ZIP/JAR central directory entry - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` reads a central-directory record's `file_name_length`, `extra_field_length`, and `file_comment_length` fields and immediately advances the cursor `p` and performs `memcpy`/`get_u4le`/`get_u2le` reads based on those attacker-controlled lengths, without ever verifying that `p` stays within the bounds of the memory-mapped input file.

### Finding Description
Compare `ProcessLocalFileEntry` (third_party/ijar/zip.cc:332-418), which calls `EnsureRemaining()` before every read of a variable-length or fixed-size field, to `ProcessCentralDirEntry` (third_party/ijar/zip.cc:493-545), which contains **no** `EnsureRemaining()` calls at all: [1](#0-0) 

The function reads `file_name_length`, `extra_field_length`, and `file_comment_length` as raw `u2` values (up to 65535 each) directly from the mmap'd buffer, then:
- `memcpy`s `file_name_length` bytes from `p` into a fixed `filename[PATH_MAX]` buffer (bounded copy length via `filename_size`, but the *source* `p` is not checked to be in-bounds) [2](#0-1) 
- advances `p` by `file_name_length`, then walks an "extra field" loop reading `header_id`/`data_size` `u2` values and advancing `extra_p` by attacker-controlled `data_size`, and for the ZIP64 tag calls `get_u8le(extra)` — none of these reads are bounds-checked against the mapped file end [3](#0-2) 
- finally advances `p` by `file_comment_length` with no check [4](#0-3) 

The comment at lines 490-492 asserts "the central directory is always followed by another data structure that has a signature, so parsing it this way is safe" — but that assumption only holds for a *well-formed* zip; it does not protect against a crafted file where these length fields intentionally push `p`/`extra_p` past the end of the `mmap`'d region.

`ProcessCentralDirEntry` is invoked once per entry from `InputZipFile::ProcessNext` (third_party/ijar/zip.cc:302-330), which is the entry point used both by `ijar` (interface-jar stripping of dependency jars) and `singlejar`'s `InputJar` path, both of which mmap and parse jar files that can originate from external/third-party dependencies (e.g., `java_import`/`http_jar`-fetched artifacts) as part of a normal build. `MappedInputFile` memory-maps the file, so reading or dereferencing past `mapped_file_.end()` is an out-of-bounds read of process memory, which can crash the build process (SIGSEGV) or leak adjacent heap/mapped memory contents into `filename`/`attr`/`offset` fields that get propagated to `processor->Accept()`/`Process()`.

This class of bug — a parser that trusts internal length fields inside a binary container format without validating them against the actual buffer bounds — is the same bug class as CVE-2022-1304 (e2fsprogs trusting on-disk filesystem structure fields without validating bounds, leading to OOB read/write and possible segfault/code execution). Just as a "specially crafted filesystem" is the attack vector for e2fsprogs, a specially crafted ZIP/JAR central directory record is the attack vector here — no checksum or hash pinned on the archive (e.g., `sha256`/`integrity` on an `http_archive`/`http_jar`) would prevent this, because the vulnerability is inherent in parsing attacker-controlled *content*, not in tampering with content in transit.

### Impact Explanation
Successful exploitation causes an out-of-bounds read while `ijar`/`singlejar` (native C++ tools invoked during ordinary Java build actions) parse a malicious jar/zip. This can crash the tool (denial of service for that action) or leak bytes of adjacent mapped memory into filenames/attributes that then influence subsequent path/content decisions (e.g., `processor->Accept(filename, attr)`), which the report class describes as segmentation fault and "possibly arbitrary code execution via a specially crafted" input structure.

### Likelihood Explanation
`ijar`/`singlejar` are executed automatically as part of normal Bazel Java build actions on any jar reachable as a dependency (including externally-fetched jars via `http_jar`, `maven_install`, etc.). An unprivileged attacker who controls the origin of such a jar (a hostile registry/mirror or the file itself as published) can trivially craft the length fields in a central directory record; no special privileges on the victim's machine are required.

### Recommendation
Add explicit bounds checks (analogous to `EnsureRemaining()` in `ProcessLocalFileEntry`) in `ProcessCentralDirEntry` before every fixed-size and variable-length read (`p += 16`, `file_name_length`, `extra_field_length`, `file_comment_length`, the extra-field loop's `data_size`), verifying that `p`/`extra_p` never advance past `mapped_file_.end()` (or `zipdata_in_ + input_file_->Length()`), and abort with a diagnostic (as `EnsureRemaining` does) instead of proceeding.

### Proof of Concept
I could not execute code in this environment to build a runnable JUnit/shell reproduction. Conceptually, a proof of concept would:
1. Construct a minimal valid ZIP EOCD + one central directory header record.
2. Set `file_name_length` (or `extra_field_length`/`file_comment_length`) to a large value (e.g., `0xFFFF`) such that `p + file_name_length` exceeds the actual mapped file length, while keeping the file small so the mapped region ends shortly after the header.
3. Run `ijar` (or a `singlejar`-based build action) against this crafted `.jar`/`.zip` and observe a segmentation fault or ASAN-reported heap/mmap out-of-bounds read inside `InputZipFile::ProcessCentralDirEntry`, analogous to `third_party/ijar/test/zip_test.sh`'s existing `test_corrupt_eocd_zip` pattern [5](#0-4)  but targeting the central directory entry length fields rather than the EOCD record.

**Note on completeness**: This codebase's index is docs/native-tools heavy for this query; I was unable to locate the Java-based `ZipDecompressor`/`TarFunction`/`ArFunction` classes used in Bazel's `http_archive`/`repository_ctx.extract()` fetch path (they did not appear in the indexed content), so I could not verify whether an equivalent unchecked-length-field issue exists there.
