## Finding [1](#0-0) [2](#0-1) 

### Title
`ERC20Transactor` performs unconditional external ERC-20 `transfer()` calls without a zero-amount guard, letting a revert-on-zero-value token DoS XCM asset withdrawal/deposit - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` extract `amount` straight from the XCM `Asset`/`AssetsInHolding` via `Matcher::matches_fungibles` and immediately build an `IERC20::transferCall { value: EU256::from(amount), .. }` that is executed via `pallet_revive::Pallet::<T>::bare_call` [3](#0-2) [4](#0-3) . Neither function checks `amount == 0` before making the call, unlike every native FRAME transfer path in this codebase (`Balances`, `Assets`, `pallet-revive::exec::transfer`, `transfer_with_dust`, `Vesting`), which all short-circuit with `if value.is_zero() { return Ok(()) }` before touching storage or making a transfer.

### Finding Description
This is the direct on-chain analog of the reported Backstop.sol bug: an unconditional `safeTransfer`/`transfer()` call to an externally-controlled asset contract with an amount that can legitimately be zero, and no guard skipping the call when `amount == 0`.

In `ERC20Transactor`, the "asset" being transacted is an arbitrary ERC-20 contract reachable through `pallet-revive` (used for ERC20/foreign-asset-backed tokens on Asset Hub / Bridge Hub, including tokens bridged in via Snowbridge). Some real-world ERC-20 implementations explicitly `require(value > 0)` and revert on a zero-value `transfer`. Because the transactor does not special-case `amount == 0`:

- `withdraw_asset_with_surplus` will call `transfer(checking_account, 0)` whenever an XCM program executes `WithdrawAsset`/`TransferAsset` for a `Fungible(0)` instance of that asset (an attacker-controlled sender, e.g. via an Ethereum-origin Snowbridge message with a `Transact`/`Payload::Raw` XCM, or via `PayFees`/`RefundSurplus` residue legs, can trivially craft such a leg).
- `deposit_asset_with_surplus` will call `transfer(beneficiary, 0)` whenever a `DepositAsset` instruction is executed on a holding entry that ends up at zero (e.g. after fee/weight buying leaves a zero-value fungible instance still present for that asset id).

For a revert-on-zero token, both calls come back with `did_revert() == true`, so the function returns `Err(XcmError::FailedToTransactAsset(...))`. That failure propagates up through the XCM executor: on `withdraw_asset_with_surplus` failure the whole XCM program fails before any assets are ever pulled into holding; on `deposit_asset_with_surplus` failure the already-withdrawn/holding assets (which may include unrelated, non-zero assets bundled in the same `DepositAsset`/multi-asset transfer, e.g. the leftover ETH fee alongside WETH in the Snowbridge V2 flow) are trapped via `AssetsTrapped` instead of reaching the intended beneficiary [5](#0-4) .

Existing guards do not stop this path:
- `Matcher::matches_fungibles` performs asset-id/type matching, not amount validation, so `amount = 0` passes through untouched.
- The codebase already recognizes zero-amount transfers as a hazard and explicitly rejects them elsewhere (`XcmConverterError::ZeroAssetTransfer` in the Snowbridge outbound-queue converter) [6](#0-5) , but no equivalent `if amount.is_zero() { return Ok(...) }` short-circuit exists in `ERC20Transactor`, unlike `pallet-revive`'s own internal `transfer` helper, which is explicitly documented as "a no-op for zero `value`, avoiding events to be emitted for zero balance transfers" [7](#0-6) .

### Impact Explanation
This falls under "public underpriced work that degrades block production or stalls bridge processing" and "permanent user-fund ... lock": a permissionless message sender (any Ethereum-side originator through Snowbridge, or any XCM sender able to route through `ERC20Transactor`) can force `FailedToTransactAsset` on any XCM leg touching a revert-on-zero ERC-20 asset, causing:
- Legitimate transfers bundled with a zero-value leg of the same asset to fail entirely and have their non-zero assets trapped (`AssetsTrapped`) rather than delivered to the rightful beneficiary, breaking the "settle exactly once to the rightful beneficiary" invariant.
- Repeatable griefing against specific ERC20-backed asset flows without needing a malicious relayer, validator, or governance actor — an ordinary user crafting the XCM payload is sufficient.

### Likelihood Explanation
Likelihood depends on at least one ERC20 asset registered/reachable via `ERC20Transactor` reverting on `transfer(_, 0)`, which is a documented, non-exotic pattern among real ERC-20 tokens. Given `pallet-assets` precompiles' own tests explicitly document zero-value transfer/allowance edge cases as a first-class concern (`pr_11227.prdoc`, `pr_12196.prdoc`), and the transactor is wired directly into the Asset Hub / Bridge Hub XCM executor config for ERC20/foreign assets, the attack surface is directly exposed to externally-triggerable XCM execution.

### Recommendation
Add an explicit zero-amount short-circuit in both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, mirroring the pattern already used throughout the codebase (`Balances::transfer`, `pallet-revive::exec::transfer`, `Vesting::vested_transfer`):
```rust
if amount == 0 {
    return Ok((AssetsInHolding::new(), Weight::zero())); // withdraw
}
if amount == 0 {
    return Ok(Weight::zero()); // deposit
}
```
skipping the `bare_call` to the external ERC20 contract entirely when `amount.is_zero()`.

### Proof of Concept
1. Register an ERC-20 contract via `pallet-revive` whose `transfer` function includes `require(value > 0, "zero amount")` (a legal, spec-compliant ERC-20 implementation) as a foreign/bridged asset matched by `ERC20Transactor`'s `Matcher`.
2. Construct an XCM program (e.g. via a Snowbridge inbound `Payload::Raw` message or any XCM entry point using this transactor) that includes a `WithdrawAsset`/`DepositAsset` instruction with `Fungible(0)` for that asset — trivially achievable by a permissionless sender picking dust/leftover amounts, or directly specifying `Fungible(0)`.
3. Observe `ERC20Transactor::withdraw_asset_with_surplus` (or `deposit_asset_with_surplus`) invoke `bare_call` → `transfer(_, 0)` → contract reverts → `XcmError::FailedToTransactAsset("ERC20 contract reverted")` is returned, failing the XCM program and, in the deposit case, trapping any other non-zero assets bundled in the same holding via `AssetsTrapped` instead of delivering them to the beneficiary.

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}

	fn deposit_asset_with_surplus(
		what: AssetsInHolding,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<Weight, (AssetsInHolding, XcmError)> {
		tracing::trace!(
			target: "xcm::transactor::erc20::deposit",
			?what, ?who,
		);
		defensive_assert!(what.len() == 1, "Trying to deposit more than one asset!");
		// Check we handle this asset.
		let maybe = what
			.fungible_assets_iter()
			.next()
			.and_then(|asset| Matcher::matches_fungibles(&asset).ok());
		let (asset_contract_id, amount) = match maybe {
			Some(inner) => inner,
			None => return Err((what, MatchError::AssetNotHandled.into())),
		};
		let who = match AccountIdConverter::convert_location(who) {
			Some(inner) => inner,
			None => return Err((what, MatchError::AccountIdConversionFailed.into())),
		};
		// We need to map the 32 byte beneficiary account to a 20 byte account.
		let eth_address = T::AddressMapper::to_address(&who);
		let address = Address::from(Into::<[u8; 20]>::into(eth_address));
		// To deposit, we actually transfer from the checking account to the beneficiary.
		// We do this using the solidity ERC20 interface.
		let data = IERC20::transferCall { to: address, value: EU256::from(amount) }.abi_encode();
		let weight_limit = WeightLimit::get();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(TransfersCheckingAccount::get()),
				asset_contract_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::deposit", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::deposit", ?return_value, "Return value");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::deposit", "Contract reverted");
				Err((what, XcmError::FailedToTransactAsset("ERC20 contract reverted")))
			} else {
				match IERC20::transferCall::abi_decode_returns_validate(&return_value.data) {
					Ok(true) => {
						tracing::trace!(target: "xcm::transactor::erc20::deposit", "ERC20 contract was successful");
						Ok(surplus)
					},
					Ok(false) => {
						tracing::debug!(target: "xcm::transactor::erc20::deposit", "contract transfer failed");
						Err((
							what,
							XcmError::FailedToTransactAsset("ERC20 contract transfer failed"),
						))
					},
					Err(error) => {
						tracing::debug!(target: "xcm::transactor::erc20::deposit", ?error, "ERC20 contract result couldn't decode");
						Err((
							what,
							XcmError::FailedToTransactAsset(
								"ERC20 contract result couldn't decode",
							),
						))
					},
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::deposit", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err((what, XcmError::FailedToTransactAsset("ERC20 contract execution errored")))
		}
	}

	/// Transfer some funds from `from` to `to`.
	///
	/// This is a no-op for zero `value`, avoiding events to be emitted for zero balance transfers.
	///
	/// If the destination account does not exist, it is pulled into existence by transferring the
	/// ED from `origin` to the new account. The total amount transferred to `to` will be ED +
	/// `value`. This makes the ED fully transparent for contracts.
	/// The ED transfer is executed atomically with the actual transfer, avoiding the possibility of
	/// the ED transfer succeeding but the actual transfer failing. In other words, if the `to` does
	/// not exist, the transfer does fail and nothing will be sent to `to` if either `origin` can
	/// not provide the ED or transferring `value` from `from` to `to` fails.
	/// Note: This will also fail if `origin` is root.
	fn transfer<S: State>(
		origin: &Origin<T>,
		from: &T::AccountId,
		to: &T::AccountId,
		value: U256,
		preservation: Preservation,
		meter: &mut ResourceMeter<T, S>,
		exec_config: &ExecConfig<T>,
	) -> DispatchResult {
		let value = BalanceWithDust::<BalanceOf<T>>::from_value::<T>(value)
			.map_err(|_| Error::<T>::BalanceConversionFailed)?;
		if value.is_zero() {
			return Ok(());
		}
