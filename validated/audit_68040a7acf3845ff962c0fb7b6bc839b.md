### Title
Unbounded, non-prioritized Praefect replication queue lets ordinary users delay replication convergence for unrelated repositories - ([File: internal/praefect/datastore/queue.go])

### Summary
Every mutating RPC that Praefect routes to a secondary enqueues a `ReplicationEvent` via `Coordinator.newRequestFinalizer` [1](#0-0) . These events are consumed strictly in `created_at` order per target storage by `PostgresReplicationEventQueue.Dequeue`, with a fixed `LIMIT $3` batch size and no cost- or size-based prioritization [2](#0-1) . An ordinary, unprivileged user who can push cheap/trivial writes to many repositories on the same physical Gitaly storage node can flood this FIFO queue with low-cost replication jobs, delaying the processing (and therefore the on-disk convergence) of legitimately important replication jobs for other repositories sharing that storage — directly analogous to the reported "small deposits clog `batchRelease()` queue" bug class.

### Finding Description
`Coordinator.newRequestFinalizer` enqueues one `ReplicationEvent` per outdated secondary for every mutator RPC (e.g. any push), regardless of how trivial the change is [3](#0-2) . There is no minimum-cost gate, size threshold, or per-user/per-repository rate limit before an event is admitted into `replication_queue`.

`PostgresReplicationEventQueue.Dequeue` selects candidate jobs ordered strictly by `created_at`, one candidate per `(lock_id, change)` partition, and takes only `LIMIT $3` (the configured `dequeueBatchSize`) per call to `ReplMgr.handleNode` [2](#0-1) [4](#0-3) . Because the ordering is purely FIFO by creation time across the whole target storage (not scoped to a specific repository nor weighted by job cost), jobs for many distinct repositories created earlier will always be pulled ahead of a job created later for a repository someone else cares about, even if the earlier jobs are for near-empty/trivial repositories and the later job is large or urgent.

The in-memory implementation exhibits the same unbounded/no-priority behavior: `memoryReplicationEventQueue.Dequeue` performs a linear scan honoring insertion order (`s.queued` is append-only, consumed by index) with no cost weighting [5](#0-4) .

Unlike the escrow example (where `bridgeOut()` was cheap but `send()` was expensive per item), here *creating* a replication job is cheap for the attacker (a trivial ref push), while *processing* each dequeued job is comparatively expensive — it requires an actual gRPC-driven replication (fetch/copy of objects) between Gitaly nodes, executed sequentially by the fixed-size worker pool per virtual storage (`r.parallelStorageProcessingWorkers` / `handleNode`) [6](#0-5) . No mechanism exists to skip ahead in the queue or to release/replicate a specific pending job out of order, mirroring the report's recommendation gap ("expose a function that releases the deposit of a specific queue index").

### Impact Explanation
Because replication jobs for all repositories hosted on a shared target storage compete in a single global FIFO ordered by `created_at`, an attacker who controls (or has push access to) many repositories on that storage can generate a large volume of trivial replication events. This backlog must be drained, one `dequeueBatchSize`-sized batch at a time, before newer, unrelated replication jobs are picked up. The practical effect is:
- Delayed convergence of secondaries for legitimate repositories, meaning reads served from those secondaries or replicas considered by the read-distribution/failover logic remain stale longer.
- Increased time before a repository becomes eligible for reconciliation/failover promotion, since generation numbers only get updated once the corresponding replication job is processed.
- A cost-asymmetric DoS: the attacker's per-event cost (a cheap push) is far lower than the aggregate processing cost imposed on the replication manager (actual data replication RPCs), and no minimum-size or per-source throttle exists to prevent it.

This does not corrupt data or bypass authorization; it is a liveness/availability degradation of the replication subsystem, reachable via the ordinary "push" path with no privileged access required.

### Likelihood Explanation
Likelihood is limited by:
- The attacker needs push access to enough repositories/branches on the same virtual storage/target node to generate meaningful queue depth relative to `dequeueBatchSize`.
- Praefect includes a "worker per virtual storage" loop that continually redrains the queue when there's backlog and healthy nodes exist, so absolute starvation is unlikely, but proportional delay scales with attacker-controlled queue depth.
- Coalescing logic in `Acknowledge` reduces duplicate/no-op jobs for the *same* repository+change+source combination, but does not help across distinct repositories or distinct change types, which is the primary attack vector described here.

Overall likelihood is moderate: it requires an attacker with a moderate number of repositories/push privileges on a shared storage node, which is realistic for a multi-tenant GitLab instance (e.g., a user with many personal projects on the same storage shard).

### Recommendation
- Introduce fairness/prioritization in `PostgresReplicationEventQueue.Dequeue` (and the in-memory equivalent), e.g. round-robin or weighted-fair dequeuing across `lock_id` (repository) rather than pure `created_at` FIFO across the whole target storage.
- Add per-source (user/project) rate limiting or a maximum outstanding-replication-events-per-repository quota to bound how much a single actor can inflate the shared queue.
- Consider a "cost hint" or size-based weighting similar to the size-aware admission discussed in `doc/load-management-architecture.md` for the concurrency limiter, applied to the replication queue as well.
- Expose an operational mechanism (as the original report also recommends) to expedite/skip specific pending events, e.g. prioritizing based on repository importance/urgency signals.

### Proof of Concept
Conceptual (matches the reachable push path, not a literal exploit script since this is a design/queueing issue):
1. Attacker creates or owns N repositories hosted on the same Gitaly storage node behind Praefect.
2. Attacker performs N trivial pushes (e.g., updating a single lightweight ref) in quick succession across these repositories. Each push causes `Coordinator.newRequestFinalizer` to call `c.queue.Enqueue` for every outdated secondary [7](#0-6) .
3. Meanwhile, Alice pushes a legitimate, larger/urgent change to a different repository on the same target storage, generating her own replication event with a later `created_at`.
4. `ReplMgr.handleNode` repeatedly calls `queue.Dequeue(ctx, virtualStorage, target.Storage, dequeueBatchSize)`, which — per the `ORDER BY created_at LIMIT $3` query — returns the attacker's earlier-queued events first [2](#0-1) .
5. Alice's replication job is only processed once all of the attacker's earlier trivial jobs across N repositories have been dequeued and processed in batches of `dequeueBatchSize`, delaying convergence/failover-eligibility of her repository proportionally to N / dequeueBatchSize.

Note: I was not able to determine the exact configured default of `dequeueBatchSize` from the indexed files (only its usages in `replicator.go` were found, not the numeric default in `config.go`), so the concrete magnitude of delay per attacker-controlled repository count is not verified here. Confirming the exact default/configurable value would require examining `internal/praefect/config/config.go` in full, which is best done in a Devin session with full repository access.

func (rq PostgresReplicationEventQueue) Dequeue(ctx context.Context, virtualStorage, nodeStorage string, count int) ([]ReplicationEvent, error) {
	query := `
	WITH candidates AS (
		SELECT DISTINCT FIRST_VALUE(id) OVER (PARTITION BY lock_id, job->>'change' ORDER BY created_at) AS id, lock_id, created_at
		FROM (
		    SELECT queue.id, queue.lock_id, queue.job, queue.created_at
			FROM replication_queue AS queue
			JOIN replication_queue_lock AS lock ON queue.lock_id = lock.id
			WHERE queue.state IN ('ready', 'failed' )
			AND NOT EXISTS (SELECT 1 FROM replication_queue_job_lock WHERE lock_id = queue.lock_id)
			AND lock.id LIKE ($1 || '|' || $2 || '|%') AND NOT acquired
			FOR UPDATE SKIP LOCKED
		) AS s
		ORDER BY created_at
		LIMIT $3
	)
	-- Set the jobs as 'in-progress'
	, job AS (
		UPDATE replication_queue AS queue
		SET attempt = CASE WHEN job->>'change' = 'delete_replica' THEN queue.attempt ELSE queue.attempt - 1 END,
	    		state = 'in_progress',
	    		updated_at = NOW() AT TIME ZONE 'UTC'
		FROM candidates
		WHERE queue.id = candidates.id
		RETURNING queue.id, queue.state, queue.created_at, queue.updated_at, queue.lock_id, queue.attempt, queue.job, queue.meta
	)
	-- Add jobs to the replication_queue_job_lock table for tracking
	, track_job_lock AS (
		INSERT INTO replication_queue_job_lock (job_id, lock_id, triggered_at)
		SELECT job.id, job.lock_id, NOW() AT TIME ZONE 'UTC'
		FROM job
		RETURNING lock_id
	)
	-- Acquire the locks for each jobs
	, acquire_lock AS (
		UPDATE replication_queue_lock
		SET acquired = TRUE
		FROM candidates
		WHERE replication_queue_lock.id = candidates.lock_id
	)
	SELECT id, state, created_at, updated_at, lock_id, attempt, job, meta
	FROM job
	ORDER BY id`

func (r ReplMgr) handleNode(ctx context.Context, virtualStorage string, target Node) int {
	logger := r.log.WithFields(log.Fields{logWithVirtualStorage: virtualStorage, logWithReplTarget: target.Storage})

	events, err := r.queue.Dequeue(ctx, virtualStorage, target.Storage, int(r.dequeueBatchSize))
	if err != nil {
		logger.WithError(err).Error("failed to dequeue replication events")
		return 0
	}

	if len(events) == 0 {
		return 0
	}

func (s *memoryReplicationEventQueue) Dequeue(_ context.Context, virtualStorage, nodeStorage string, count int) ([]ReplicationEvent, error) {
	s.Lock()
	defer s.Unlock()

	var result []ReplicationEvent
	uniqueJob := make(map[string]struct{})

	for i := 0; i < len(s.queued); i++ {
		event := s.queued[i]

		isForVirtualStorage := event.Job.VirtualStorage == virtualStorage
		isForTargetStorage := event.Job.TargetNodeStorage == nodeStorage
		isReadyOrFailed := event.State == JobStateReady || event.State == JobStateFailed

		if isForVirtualStorage && isForTargetStorage && isReadyOrFailed {
			jobData, err := json.Marshal(event.Job)
			if err != nil {
				return nil, err
			}

			if _, found := uniqueJob[string(jobData)]; found {
				continue
			}

			uniqueJob[string(jobData)] = struct{}{}

			updatedAt := time.Now().UTC()
			event.Attempt--
			event.State = JobStateInProgress
			event.UpdatedAt = &updatedAt

			s.queued[i] = event
			s.dequeued[event.ID] = struct{}{}
			eventDest := s.defineDest(event)
			if last, found := s.lastEventByDest[eventDest]; found && last.ID == event.ID {
				s.lastEventByDest[eventDest] = event
			}
			result = append(result, event)

			if len(result) >= count {
				break
			}
		}
	}

	return result, nil
}
