### Title
Bazel's `git_repository`/`new_git_repository` submodule fetching forces `protocol.file.allow=always`, allowing attacker-controlled `.gitmodules` content to trigger local `file://` clones outside the repository — ([File: tools/build_defs/repo/git_worker.bzl])

### Summary
`update_submodules()` in `tools/build_defs/repo/git_worker.bzl` unconditionally passes `-c protocol.file.allow=always` to `git submodule update --init [--recursive] --checkout --force` for every `git_repository`/`new_git_repository` invocation that initializes submodules. [1](#0-0) 

### Finding Description
Git ships with `protocol.file.allow` defaulting to a restricted setting so that `file://` (local filesystem) transport is not used implicitly during automated, repository-content-driven operations such as recursive `git submodule update`. This restriction exists specifically because submodule URLs are read from `.gitmodules`, a file whose content is fully controlled by whoever authored the fetched repository/commit — i.e., by content the victim's build merely *consumes*, not content the victim wrote. Historical Git CVEs (e.g. GHSA/CVE-2022-39253) showed that local `file://` clones of attacker-chosen paths can leverage hardlink-based local clone optimizations to read files that should not be reachable from the fetched project.

Bazel's `git_worker.bzl` deliberately overrides this protection for *every* submodule fetch, citing a workaround for a compatibility issue in Git 2.38.1 (`bazelbuild/bazel#17040`), but the override is unconditional rather than scoped to the narrow compatibility case it was meant to address. [1](#0-0) 

`update_submodules` is invoked as part of the normal `_update` flow used by `git_repo()`, which every `git_repository`/`new_git_repository` fetch runs to satisfy `init_submodules`/`recursive_init_submodules` attributes. [2](#0-1) 

All `git` invocations are made through `ctx.execute()` with explicit argv lists (not a shell string), so this is not a literal CWE-78 shell-metacharacter injection like Mercurial's SSH hostname issue. However, it is the closest analog reachable in this codebase: an externally-supplied, attacker-controlled value (the submodule `url=` entries inside `.gitmodules`, which are part of the fetched repository content, not the WORKSPACE/MODULE.bazel a victim authored) is allowed to drive a security-sensitive transport decision that Git itself intentionally locks down by default, because Bazel forces `protocol.file.allow=always` before Git ever parses `.gitmodules`. [3](#0-2) 

### Impact Explanation
Because `protocol.file.allow=always` is force-set, a `.gitmodules` file inside a fetched repository can declare a submodule `url = file:///absolute/path/on/build/host`. Git will honor the local-clone path, potentially using hardlinks/local-clone optimizations, which historically permitted the checked-out submodule tree to end up containing hardlinked (or otherwise exposed) file contents from arbitrary filesystem locations outside the intended repository checkout — i.e., a read outside the repository/output base, and a mechanism to smuggle host filesystem contents into the resulting Bazel workspace tree where they can be consumed by subsequent build steps (BUILD files, genrules, etc.).

### Likelihood Explanation
Exploitation only requires that the git content Bazel fetches (a specific commit, tag, or branch reachable through `git_repository`/`new_git_repository`) contain a crafted `.gitmodules`. This matches the described attacker model: an outsider who controls or later compromises the fetched git origin, a fork on an untrusted branch that CI builds, or a newly published tag/commit the victim upgrades to. No commit-hash integrity check inspects `.gitmodules` semantics or the transport implications of the URLs it contains — pinning to a commit only guarantees *that* content is used, not that Bazel's forced `protocol.file.allow=always` is safe for it.

### Recommendation
- Do not force `protocol.file.allow=always` unconditionally. Scope the override narrowly to the specific Git 2.38.1 compatibility case referenced in `bazelbuild/bazel#17040` (e.g., only for local, same-machine relative submodule paths that Bazel itself controls), or detect the affected Git versions and apply the override only then.
- For `git submodule update`, prefer explicit `-c protocol.file.allow=user` (or leave Git's default) and, where the 17040 workaround is required, restrict it to submodule URLs that are relative paths resolved within the already-cloned repository tree rather than arbitrary absolute `file://` targets.
- Add a regression test that fetches a repository containing a `.gitmodules` submodule URL of `file:///<outside path>` and asserts the fetch fails (or does not exfiltrate content from outside the checkout).

### Proof of Concept
1. Attacker publishes/serves a git repository (or a tag/commit a victim later depends on via `git_repository`) whose `.gitmodules` contains:
   ```
   [submodule "evil"]
       path = evil
       url = file:///etc
   ```
2. Victim's `MODULE.bazel`/`WORKSPACE` uses:
   ```python
   git_repository(
       name = "dep",
       remote = "https://attacker-controlled-or-later-compromised-origin/repo.git",
       commit = "<pinned commit containing the malicious .gitmodules>",
       recursive_init_submodules = True,
   )
   ```
3. During fetch, Bazel runs (via `update_submodules`):
   `git -c core.fsmonitor=false -c protocol.file.allow=always submodule update --init --recursive --checkout --force` [1](#0-0) 
4. Because `protocol.file.allow=always` is forced, Git performs a local clone of `file:///etc` into the `evil` submodule directory inside the Bazel-managed repository checkout, using Git's local-clone (potentially hardlink-based) fast path — bringing host filesystem content into the fetched repo tree outside of what the repository/tag's declared dependency graph should allow.

**Note on confidence**: I could not execute Git itself in this environment to reproduce the hardlink-disclosure mechanics of CVE-2022-39253 against this exact code path, so the concrete file-disclosure outcome is based on documented Git behavior for `file://` submodule clones rather than a runtime-verified PoC in this repo. If this analysis needs to be validated end-to-end, a Devin session with shell/Git access would be needed to build and run the JUnit/`src/test/shell/bazel` reproduction described above.

```text
def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
```

```text
def _execute(ctx, git_repo, args):
    # "core.fsmonitor=false" disables git from spawning a file system monitor which can cause hangs when cloning a lot.
    # See https://github.com/bazelbuild/bazel/issues/21438
    start = ["git", "-c", "core.fsmonitor=false"]
    return ctx.execute(
        start + args,
        environment = ctx.os.environ | _GIT_LOCAL_ENV_VARS,
        working_directory = str(git_repo.directory),
    )
```
