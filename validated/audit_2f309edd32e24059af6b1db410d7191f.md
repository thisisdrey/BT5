### Title
Responder handshake index allocation skips collision check against pending/main hostmap indexes - (File: handshake_manager.go)

### Summary
`HandshakeManager.beginHandshake`, the code path that processes an unauthenticated stage-1 handshake packet from any remote sender (no CA-signed certificate required to reach this code), allocates the local index for the new responder `Machine` using a raw `generateIndex()` call instead of the collision-checked `HandshakeManager.allocateIndex()` used by the initiator path. This mirrors the reported NFTX bug class: an operation that adds a new keyed entry (here, a `localIndexId` used as a map key in `hm.indexes` / `hm.mainHostMap.Indexes`) without first verifying the key doesn't already exist, allowing a duplicate/colliding entry to be introduced.

### Finding Description
`HandleIncoming` dispatches any stage-1 packet (`h.MessageCounter == 1`, `h.RemoteIndex == 0`) straight to `beginHandshake` before any certificate has been validated [4](#0-3) . Inside `beginHandshake`, the responder `Machine` is constructed with:

```go
machine, err := handshake.NewMachine(
    v, cs.GetCredential,
    hm.certVerifier(), func() (uint32, error) { return generateIndex(f.l) },
    false, header.HandshakeIXPSK0,
)
``` [2](#0-1) 

`generateIndex` only guarantees the returned value is non-zero; it performs no lookup against any existing map [3](#0-2) . This value becomes `result.LocalIndex`, which is used to populate `hostinfo.localIndexId` and is later inserted into `hm.mainHostMap.Indexes` via `unlockedAddHostInfo`/`CheckAndComplete` [5](#0-4) [6](#0-5) .

By contrast, the initiator side deliberately avoids this exact problem: `buildStage0Packet` wires the allocator to `hm.allocateIndex(hh)`, which loops up to 32 times, checking both `hm.indexes` (pending) and `hm.mainHostMap.Indexes` (established) before accepting a candidate index [7](#0-6) [1](#0-0) . The existence of this dedicated, collision-checked allocator for one code path but not the other is the direct root cause — analogous to `NFTXSimpleFeeDistributor#addReceiver` adding an entry to a list without checking whether it already exists, while presumably other code paths in that contract do check.

`CheckAndComplete` does defend against index collisions to some degree (`ErrLocalIndexCollision`) when the *new* index happens to already exist in `hm.mainHostMap.Indexes` or `hm.indexes` for a *different* hostinfo, and it also tolerates `RemoteIndexes` collisions by just logging [8](#0-7) . However, this only reduces (does not eliminate) the impact of an uncollision-checked allocation for `localIndexId`, and it does nothing for the case where the generated index only collides transiently with another *pending* responder machine created concurrently by other stage-1 floods, since `beginHandshake` never registers into `hm.indexes` at all for the (currently unsupported) multi-message case, and even for the completed IX case the check happens only once, after the machine has already fully processed the packet and produced key material.

### Impact Explanation
An attacker who can send raw UDP stage-1 handshake packets — requiring no valid CA-signed certificate — can repeatedly trigger `beginHandshake`. Because the responder-side local index is generated without any uniqueness check at allocation time, a remote index can be produced that happens to already be in use by another established or pending `HostInfo`, is remote-triggerable, and is completely outside attacker control to predict but easy to consistently attempt/collide with a small (32-bit) space against a busy lighthouse or gateway node handling many concurrent handshakes. The registration into `hm.mainHostMap.Indexes` / `RemoteIndexes` happens after the fact only inside `CheckAndComplete`, and while that function does detect certain local-index collisions with a *different* hostinfo and rejects them (`ErrLocalIndexCollision`), it treats a colliding `RemoteIndexes` entry as a benign, log-only condition ("this can happen since we can't control the remote ID") [9](#0-8) , meaning a remote-index collision from an unauthenticated responder-generated index can silently shadow/redirect traffic intended for an existing tunnel to a different `HostInfo`. This is a remote state-poisoning risk in the handshake/hostmap bookkeeping, triggerable purely by an attacker without possessing a CA-signed certificate.

### Likelihood Explanation
Likelihood is low-to-moderate: the collision window is on a 32-bit random index space, so a *specific* collision is statistically rare on any single busy node, but the code path is reachable by any unauthenticated packet sender at essentially unlimited rate (bounded only by the `RemoteAllowList` check on the source IP) [10](#0-9) , so on a high-traffic lighthouse/relay node processing many concurrent handshakes the aggregate probability of colliding with a live index rises, and there is no application-level rate limiting of stage-1 packets shown in this path.

### Recommendation
Route the responder-side `IndexAllocator` in `beginHandshake` through the same collision-checked allocation used by the initiator (i.e., an analog of `hm.allocateIndex` that checks `hm.indexes` and `hm.mainHostMap.Indexes` before accepting the candidate index), and register the responder's pending `HandshakeHostInfo` into `hm.indexes` under lock atomically with the allocation, mirroring the initiator's `allocateIndex` semantics. Additionally, treat a `RemoteIndexes` collision on `CheckAndComplete` less permissively than a pure log statement, since it currently permits one hostinfo to shadow another's remote index without any explicit remediation.

### Proof of Concept
Not runnable without a live two-node nebula deployment and a way to force `generateIndex()` to return a colliding 32-bit value (e.g., via a custom build hooking `crypto/rand` or via exhaustive/parallel stage-1 flood against a node already juggling many concurrent handshakes/tunnels to raise collision probability). Conceptually:
1. Attacker (holding no CA-signed cert, or an entirely separate/unrelated CA) sends a spoofed UDP packet with `header.Handshake`, `Subtype = HandshakeIXPSK0`, `MessageCounter = 1`, `RemoteIndex = 0` to the victim node.
2. `HandleIncoming` routes it to `beginHandshake` before any certificate has been checked [11](#0-10) .
3. `beginHandshake`'s `IndexAllocator` calls bare `generateIndex()` with no uniqueness verification [2](#0-1) .
4. If the noise handshake subsequently fails cert verification, `beginHandshake` returns early — but the underlying issue is that nothing at allocation time prevented picking an index already live in `hm.mainHostMap.Indexes`/`RemoteIndexes`; a colliding index reaching `CheckAndComplete` for a *successful* handshake (from a differently-signed but still-verifying certificate under a misconfigured/multi-CA trust pool, or via the log-only `RemoteIndexes` collision path) can shadow an existing tunnel's remote index bookkeeping.

// allocateIndex generates a unique localIndexId for this HostInfo
// and adds it to the pendingHostMap. Will error if we are unable to generate
// a unique localIndexId
func (hm *HandshakeManager) allocateIndex(hh *HandshakeHostInfo) (uint32, error) {
	hm.mainHostMap.RLock()
	defer hm.mainHostMap.RUnlock()
	hm.Lock()
	defer hm.Unlock()

	for range 32 {
		index, err := generateIndex(hm.l)
		if err != nil {
			return 0, err
		}

		_, inPending := hm.indexes[index]
		_, inMain := hm.mainHostMap.Indexes[index]

		if !inMain && !inPending {
			hh.hostinfo.localIndexId = index
			hm.indexes[index] = hh
			return index, nil
		}
	}

	return 0, errors.New("failed to generate unique localIndexId")
```

func generateIndex(l *slog.Logger) (uint32, error) {
	b := make([]byte, 4)

	// Let zero mean we don't know the ID, so don't generate zero
	var index uint32
	for index == 0 {
		_, err := rand.Read(b)
		if err != nil {
			l.Error("Failed to generate index", "error", err)
			return 0, err
		}

		index = binary.BigEndian.Uint32(b)
	}

	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("Generated index", "index", index)
	}
	return index, nil
}
