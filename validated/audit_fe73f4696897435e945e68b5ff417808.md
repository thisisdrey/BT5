### Title
Division-before-multiplication using double-precision floats causes reward miscalculation in witness/voter payout math - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`, `consensus/src/main/java/org/tron/consensus/dpos/IncentiveManager.java`)

### Summary
The GMX report describes `getNextFundingAmountPerSize()` truncating `cache.sizeOfLargerSide / Precision.FLOAT_PRECISION` before multiplying, discarding precision when the numerator is small relative to the divisor. The same "divide-then-multiply" anti-pattern exists in java-tron's DPoS reward-distribution math, except the truncation is masked by an intermediate `double` cast rather than integer division. For financial quantities that exceed `2^53` (TRX amounts are denominated in SUN, so values well beyond `2^53` are common for large `totalPay`/`voteSum`/`value` figures), the `double` representation itself loses integer precision, and the division-first ordering compounds the truncation before it is multiplied back up — producing systematically incorrect reward payouts, exactly analogous to the reported bug class.

### Finding Description
Three call sites compute a per-unit rate by dividing first (as a `double`) and only then multiplying by the raw vote/brokerage count, instead of multiplying first and dividing last:

1. `MortgageService.payStandbyWitness()`: [1](#0-0) 
computes `eachVotePay = (double) totalPay / voteSum` first, then `pay = (long) (w.getVoteCount() * eachVotePay)`.

2. `MortgageService.payReward()`: [2](#0-1) 
computes `brokerageRate = (double) brokerage / 100` first, then `brokerageAmount = (long) (brokerageRate * value)`.

3. `IncentiveManager.reward()`: [3](#0-2) 
computes `(double) totalPay / voteSum` first, then multiplies by each witness's `getVoteCount()`.

This is the same "division before multiplication" ordering flagged in the GMX report, just implemented with `double` instead of fixed-point integers. It is significant in java-tron because:
- `payReward()` is invoked on every single block via `payBlockReward()`/`payTransactionFeeReward()`, which are called from `MortgageService` during `Manager` block application for every produced block — reachable indirectly by any account whose transactions generate fees, since transaction-fee rewards flow through this exact code path.
- The codebase itself acknowledges that this class of arithmetic is unsafe at scale: `RepositoryImpl.calculateGlobalEnergyLimit()` explicitly retains the legacy `(long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight))` formula as the *unhardened*, known-imprecise fallback, and replaces it with `BigInteger`-based multiply-then-divide when `allowHardenResourceCalculation()` is enabled: [4](#0-3) 
The same class of double-based, division-first math in `MortgageService`/`IncentiveManager` has never received an equivalent hardened/BigInteger replacement, even though it directly affects on-chain balances (`AccountCapsule.setAllowance`, `delegationStore.addReward`) rather than transient resource limits.

### Impact Explanation
Reward and brokerage amounts distributed to standby witnesses, block-producing witnesses, and their voters can be silently and permanently understated (or, less commonly, overstated by rounding) for every block and every maintenance cycle. Because `payReward` is called once per produced block network-wide, the aggregate drift accumulates over the life of the chain, resulting in a persistent discrepancy between the funds that should be credited to accounts (`delegationStore.addReward`, `AccountCapsule.allowance`) and what is actually credited — a form of fund miscalculation/permanent loss of expected rewards for affected stakeholders, matching the "incorrect funding amount" class in the source report.

### Likelihood Explanation
This code executes unconditionally on the hot path of block reward distribution (`payBlockReward`/`payTransactionFeeReward` on every block, `payStandbyWitness`/`IncentiveManager.reward` on every maintenance cycle), so the precision drift is deterministic and guaranteed to occur whenever `totalPay`/`value`/`voteSum` combinations produce a non-exact rational quotient (i.e., essentially always), not dependent on any attacker action beyond normal network operation.

### Recommendation
Replace the `double`-based divide-then-multiply pattern with integer/`BigInteger` multiply-then-divide, mirroring the pattern already adopted in `ResourceProcessor.calculateGlobalLimitV2()` and the hardened branch of `RepositoryImpl.calculateGlobalEnergyLimit()`:
```java
long pay = BigInteger.valueOf(voteCount)
    .multiply(BigInteger.valueOf(totalPay))
    .divide(BigInteger.valueOf(voteSum))
    .longValueExact();
```
Apply the same transformation to `brokerageAmount` in `payReward()` and to the per-witness `pay` computation in `IncentiveManager.reward()`.

### Proof of Concept
Consider `IncentiveManager.reward()` with `totalPay = 1_000_000_000_000_017L` (SUN, > 2^53 ≈ 9.007e15) and `voteSum = 3`:
- Correct (multiply-first) result for a witness with `voteCount = 1`: `1_000_000_000_000_017 * 1 / 3 = 333,333,333,333,339` (integer division).
- Current code: `(double) totalPay / voteSum` first rounds `totalPay` to the nearest representable double (losing the low-order bits beyond 2^53), then multiplies by `voteCount`, yielding a value that diverges from the exact integer result by a nontrivial, non-zero amount — the discrepancy is credited (or denied) to `accountCapsule.setAllowance(...)` every time this code runs, for every standby witness, every maintenance cycle, and every block reward paid via `payReward()`.
