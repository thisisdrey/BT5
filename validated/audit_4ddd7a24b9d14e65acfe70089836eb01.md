## Analog Found

### Title
Uncaught `ArithmeticException` from `BigInteger.longValueExact()` in energy-limit calculation can crash nodes during transaction processing - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
The reported bug is about a downcast helper that can silently fail/halt the chain when a value read from contract state exceeds the target integer type's range. The same class of bug exists in java-tron's TVM energy accounting code, where `BigInteger.longValueExact()` is used to convert intermediate `BigInteger` products/quotients (derived from account frozen balances, total energy weight/limit, and usage window sizes) back to `long`, without any safety fallback like `longValueSafe()`. If the operands make the intermediate value exceed `Long.MAX_VALUE`, an unchecked `ArithmeticException` is thrown.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit()` computes a node's global energy limit for a `TriggerSmartContract`/`CreateSmartContract` call using account-controlled state (frozen balance) combined with global dynamic properties: [1](#0-0) 

When `hardenResourceCalculation()` is enabled, the result is computed via `BigInteger` multiplication/division and then unwrapped with `longValueExact()`, which throws `ArithmeticException` if the value doesn't fit into a `long`: [2](#0-1) 

The same unguarded pattern (`longValueExact()` with no try/catch) appears in the related `getUsage()` and `divideCeilExact()` helpers used for resource usage accounting, all of which sit in the hot path of every smart-contract-calling transaction: [3](#0-2) 

Unlike `DataWord.longValueSafe()`/`intValueSafe()` elsewhere in the codebase, which explicitly clamp to `Long.MAX_VALUE`/`Integer.MAX_VALUE` on overflow instead of throwing: [4](#0-3) 
these energy-accounting helpers have no such clamping and instead propagate a raw `ArithmeticException`. This is functionally the same root cause as the reported `downcast_uint256()` issue: a numeric-range downcast that fails hard on overflow instead of degrading gracefully, in code that consumes attacker/user-influenced numeric inputs (frozen balances, energy usage, window sizes) that accumulate over time via ordinary freeze/vote/resource-consumption transactions.

I was not able to fully confirm, within the available context, whether every call site up the stack (e.g., `VMActuator.getTotalEnergyLimitWithFixRatio()`, which also performs its own unguarded `longValueExact()` on a `BigInteger` division) wraps this in a try/catch that converts it into a normal `ContractExeException`/`ContractValidateException` versus letting it escape as an uncaught runtime exception during block application: [5](#0-4) 
The existing test suite only validates that `ArithmeticException` is thrown for extreme, artificially-large synthetic inputs when hardening is enabled — it does not demonstrate the exception being caught and converted into a transaction failure at the actuator boundary: [6](#0-5) 

### Impact Explanation
If the `ArithmeticException` produced by `longValueExact()` in this deterministic, consensus-relevant code path is not caught before reaching block-application logic, it would cause an uncaught runtime exception during processing of an otherwise valid transaction. Because the overflow condition depends only on deterministic on-chain state (frozen balances, `totalEnergyWeight`, `totalEnergyLimit` — all of which grow over time and are influenced by ordinary freeze/stake transactions from any account), every node processing the same block would hit the identical exception, resulting in a deterministic node crash/halt across the network rather than a chain split — directly analogous to the "downcasting can freeze the chain" bug class in the report.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires the product of `frozeBalance`/`energyWeight`/`totalEnergyLimit` etc. to exceed `Long.MAX_VALUE`, which is far above realistic TRX supply figures today, similar to the original report's own "Low" likelihood rating for the analogous bridge nonce overflow. However, as network-wide staked TRX and cumulative counters grow over long time horizons, or if a specific combination of dynamic-property values is set (e.g., via governance proposals adjusting `totalEnergyWeight`/`totalEnergyLimit`), the overflow condition becomes reachable without any single actor needing privileged access — a normal `TriggerSmartContract` transaction from any unprivileged account exercises this code path.

### Recommendation
Replace the unguarded `longValueExact()` calls in `RepositoryImpl.calculateGlobalEnergyLimit()`, `divideCeilExact()`, and `getUsage()` (and the analogous call in `VMActuator.getTotalEnergyLimitWithFixRatio()`) with a safe conversion that clamps to `Long.MAX_VALUE`/`Long.MIN_VALUE` on overflow (mirroring `DataWord.longValueSafe()`), or explicitly catch `ArithmeticException` at these call sites and convert it into a `ContractValidateException`/`ContractExeException` so a single malformed/extreme value fails only the offending transaction instead of crashing the node process.

### Proof of Concept
Not independently reproducible from static analysis alone since it requires driving `frozeBalance * totalEnergyLimit` (or `usage * windowSize`) past `Long.MAX_VALUE`, which is outside currently realistic on-chain magnitudes; the existing unit test demonstrates the throw behavior with synthetic large values: [7](#0-6) 
A full confirmation of end-to-end unhandled propagation into block-application/consensus code would require tracing every caller of `calculateGlobalEnergyLimit()`/`getAccountEnergyLimitWithFixRatio()` through `TransactionTrace`/`Runtime`, which I could not fully complete with the available tool budget.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

   * In case of long overflow returns Long.MAX_VALUE otherwise works as #longValue()

  public long longValueSafe() {
    int bytesOccupied = bytesOccupied();
    long longValue = longValue();
    if (bytesOccupied > 8 || longValue < 0) {
      return Long.MAX_VALUE;
    }
    return longValue;
  }
