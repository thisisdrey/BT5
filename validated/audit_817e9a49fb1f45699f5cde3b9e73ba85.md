### Title
Interest rate curve defaults to `{util: u0, rate: u0}` before DAO configuration, allowing zero-interest borrowing analogous to the unset-price-config bug - ([File: local-testing/contracts/vault/vault-stx.clar])

### Summary
The external report describes a class of bug where a pricing/config struct that has not been explicitly set defaults to Solidity/Clarity's zero-value initialization, and that zero value is used directly in a financial calculation without a "config is set" guard, letting users transact for free. The same root-cause pattern exists in Zest's vault interest-rate mechanism: the `points-ir` data-var, which stores the packed utilization/rate curve used to price borrowing, is declared with a hardcoded zero default and is consumed by `interest-rate` with no check that the DAO has ever called `set-points-util`/`set-points-rate`.

### Finding Description
Each vault (`vault-stx.clar`, `vault-sbtc.clar`, `vault-ststx.clar`, `vault-usdc.clar`, `vault-usdh.clar`, `vault-ststxbtc.clar`, and their mainnet `v0-*` counterparts) declares: [1](#0-0) 

```
(define-data-var points-ir
  {util: uint, rate: uint}
  {util: u0, rate: u0})
```

This is exactly the "default-initialized struct" pattern the report warns about: `util` and `rate` are packed words that, until `set-points-util`/`set-points-rate` are called by the DAO, unpack to eight zero utilization breakpoints and eight zero interest rates via `unpack-u16`: [2](#0-1) 

The borrow-rate lookup path never validates that this curve has actually been configured — it simply unpacks whatever is stored and interpolates: [3](#0-2) 

```
(define-private (interest-rate)
  (let ((points-data (var-get points-ir))
        (uword (get util points-data))
        (rword (get rate points-data))
        (utils (unpack-u16 uword))
        (rates (unpack-u16 rword)))
    (interpolate-rate (utilization) utils rates)))
```

With all eight utilization points at `u0` and all eight rate points at `u0`, `resolve-and-interpolate`/`resolve-interpolation-points` will match the very first point (`target >= 0` is always true) and return `rate = u0` for any utilization level: [4](#0-3) 

That zero rate then feeds directly into index accrual (`next-index`/`next-liquidity-index`), meaning borrowers accrue **no interest** and suppliers earn **no yield** for as long as the curve remains unset: [5](#0-4) 

This mirrors the ZNS bug precisely: a struct (`PriceConfig`/`CurvePriceConfig` there, `points-ir` here) that is zero by default is consumed by a pricing function (`getPrice()` there, `interest-rate()` here) with no `isSet`/`isConfigSet`-style guard, so the absence of explicit configuration silently produces a "free" outcome (free domain registration there, 0% borrow rate here) instead of reverting.

### Impact Explanation
If a vault becomes reachable by ordinary borrowers (deposit/borrow enabled in `assets.clar` and the market authorized in the vault) while `points-ir` is still at its zero default — e.g., during initial protocol bring-up before the DAO's rate-setting call executes, or during onboarding of a new vault where enablement and rate-curve configuration are not atomic — any user can borrow at 0% interest. This is theft of unclaimed yield: lenders/treasury permanently lose the interest they should have earned on debt outstanding during that window, which falls under the in-scope "High — theft of unclaimed yield ... or temporary freezing of funds" impact class for "vault share math and interest accrual."

### Likelihood Explanation
Exploitability depends entirely on whether there is any window, however narrow, in which a vault's borrow path is reachable by an ordinary principal before `set-points-util`/`set-points-rate` have been called. In the reviewed mainnet deployment proposal (`v0-init.clar`) and the newer `proposal-protocol-init.clar`, asset enablement, market authorization, and interest-curve configuration are issued as sequential `try!` calls inside a single DAO proposal `execute()` function, which is atomic in Clarity — so no external transaction can be interleaved between "vault becomes borrowable" and "rate curve is set" during a single proposal execution. This significantly reduces likelihood for the *known* initialization flow. However, the underlying code-level guarantee is missing: nothing in `vault-*.clar` itself prevents `borrow`/`accrue` from operating over a zero curve, so any future onboarding flow, script, or manual multi-transaction DAO rollout that separates "enable asset for borrowing" from "call set-points-rate" (as the standalone `proposal-set-stx-interest-rates.clar` update pattern demonstrates is an accepted operational pattern) would reopen this window. I could not fully verify, within the available search results, whether the vault's `deposit`/`borrow` entry points contain any independent check that `points-ir` is non-zero or "initialized" — none was found — so this remains a code-level defect even though current atomic proposal execution mitigates it today.

### Recommendation
Add an explicit "curve is set" invariant to the vault interest-rate path, mirroring the fix applied to `ZNSCurvePricer`/`ZNSFixedPricer`: track whether `set-points-util` and `set-points-rate` have both been called at least once (e.g., a boolean flag alongside `points-ir`), and have `interest-rate`/`accrue`/`borrow` assert on that flag (or otherwise refuse to accrue debt/allow borrowing) until the curve is confirmed non-default. This removes any reliance on proposal-execution atomicity as the sole safeguard against a zero-rate borrowing window.

### Proof of Concept
Conceptual reproduction (contingent on a vault being borrow-enabled prior to curve configuration):
1. Deploy a vault (e.g., `vault-usdc.clar`) with default `points-ir = {util: u0, rate: u0}`.
2. Have the DAO enable the corresponding asset for collateral/debt in `assets.clar` and authorize the market in the vault, but do not yet call `set-points-util`/`set-points-rate` (e.g., a multi-step/non-atomic rollout, or a bug in ordering).
3. An ordinary user deposits collateral and calls `market.borrow` on the affected asset.
4. `interest-rate()` unpacks all-zero `util`/`rate` points, `interpolate-rate` returns `u0` for any utilization, and `next-index`/`next-liquidity-index` compute a multiplier of `INDEX-PRECISION` (no growth) via `calc-multiplier-delta rate ...` with `rate = 0`.
5. The user's debt accrues zero interest indefinitely until the DAO calls `set-points-rate`, at which point all interest accrued during the window is permanently unrecoverable — theft of yield that should have accrued to the vault/treasury.

(define-private (unpack-u16-at (word uint) (pos uint))
  (let ((offset (* pos BIT-U16))
        (div (pow u2 offset))
        (shiftr (/ word div)))
    (mod shiftr MASK-U16)))

(define-private (iter-unpack-u16 (pos uint) (acc {word: uint, fields: (list 8 uint)}))
