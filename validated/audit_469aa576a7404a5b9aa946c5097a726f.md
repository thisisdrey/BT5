### Title
Missing Zero-Address Validation in `set_beneficiary_for_operator` Causes Permanent Loss or Freeze of Staking Commission Rewards — (`File: aptos-move/framework/aptos-framework/sources/staking_contract.move` and `aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

---

### Summary

Both `staking_contract::set_beneficiary_for_operator` and `delegation_pool::set_beneficiary_for_operator` accept an arbitrary `new_beneficiary: address` with no validation that the address is non-zero or non-reserved. An operator who (by mistake or maliciously) passes `@0x0` (`@vm_reserved`) as the beneficiary will cause all future commission distributions to be routed to the uncontrolled VM-reserved address, permanently burning the commission APT. If the deposit to `@0x0` aborts (because no account exists there), every subsequent call to `distribute_internal` — which is invoked on every `unlock_stake`, `switch_operator`, and `distribute` path — will revert, permanently freezing the staker's funds in the stake pool.

---

### Finding Description

**Root cause — `staking_contract.move`:**

```move
public entry fun set_beneficiary_for_operator(
    operator: &signer, new_beneficiary: address
) acquires BeneficiaryForOperator {
    assert!(
        features::operator_beneficiary_change_enabled(),
        std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
    );
    let operator_addr = signer::address_of(operator);
    let old_beneficiary = beneficiary_for_operator(operator_addr);
    if (exists<BeneficiaryForOperator>(operator_addr)) {
        borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
            new_beneficiary;   // ← no zero/reserved-address check
    } else {
        move_to(operator, BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary });
    };
    ...
}

Neither function validates `new_beneficiary`. Compare this to `vesting::create_vesting_contract`, which correctly guards its `withdrawal_address` parameter:

```move

    !system_addresses::is_reserved_address(withdrawal_address),

);

``` [3](#0-2) 

**Propagation path — `distribute_internal`:**

When `distribute_internal` runs, it redirects the operator's share to `beneficiary_for_operator(operator)`:

```move
if (recipient == operator) {
    recipient = beneficiary_for_operator(operator);
};
aptos_account::deposit_coins(
    recipient, coin::extract(&mut coins, amount_to_distribute)
);
``` [4](#0-3) 

If `recipient` is `@0x0`:

- **Scenario A — `@0x0` has an account on mainnet** (the VM-reserved address is initialized at genesis): `aptos_account::deposit_coins(@0x0, coins)` succeeds and the commission APT is permanently deposited at an address no one controls — direct, irreversible burn of APT.
- **Scenario B — `@0x0` has no account**: `deposit_coins` calls `create_account(@0x0)`, which aborts because `@vm_reserved` is blocked by `account::create_account`. The entire `distribute_internal` transaction reverts. Since `distribute_internal` is called inside `unlock_stake`, `switch_operator`, and `distribute`, every one of those entry points permanently aborts, freezing the staker's principal in the stake pool. [5](#0-4) 

`@vm_reserved = @0x0` is confirmed by `system_addresses::is_vm_address`:

```move
public fun is_vm_address(addr: address): bool {
    addr == @vm_reserved
}
``` [6](#0-5) 

---

### Impact Explanation

- **Scenario A**: Commission APT is permanently sent to `@0x0` and irrecoverable — direct theft/burning of on-chain APT assets.
- **Scenario B**: Every call to `distribute_internal` aborts, permanently freezing the staker's entire principal in the stake pool. The staker cannot unlock, switch operators, or withdraw — permanent freeze of user-controlled staking balances.

Both outcomes are within the Aptos allowed impact gate (direct burning of APT / permanent freezing of staking balances caused by an unprivileged transaction).

---

### Likelihood Explanation

- `set_beneficiary_for_operator` is a public entry function callable by any operator with no privilege beyond holding the operator signer.
- An operator can trigger this by mistake (e.g., passing a zero-initialized address variable) or deliberately as a griefing attack against a staker.
- The feature flag `operator_beneficiary_change_enabled` is the only gate in `staking_contract.move`; once enabled on mainnet, the path is fully open. `delegation_pool.move` has no feature flag at all.
- The `vesting` module already demonstrates the correct pattern, confirming the omission is unintentional.

---

### Recommendation

Add a reserved-address and zero-address guard in both `set_beneficiary_for_operator` functions, mirroring the pattern already used in `vesting::create_vesting_contract`:

```move
assert!(
    !system_addresses::is_reserved_address(new_beneficiary),
    error::invalid_argument(EINVALID_BENEFICIARY_ADDRESS)
);
assert_account_is_registered_for_apt(new_beneficiary);
``` [3](#0-2) 

---

### Proof of Concept

```
1. Operator calls:
       staking_contract::set_beneficiary_for_operator(operator_signer, @0x0)
   → Succeeds. BeneficiaryForOperator { beneficiary_for_operator: @0x0 } is stored.

2. Staker calls:
       staking_contract::unlock_stake(staker_signer, operator_addr, amount)
   → Internally calls distribute_internal(staker, operator, staking_contract)
   → distribute_internal calls beneficiary_for_operator(operator) → @0x0
   → aptos_account::deposit_coins(@0x0, commission_coins) is called

   Scenario A: @0x0 account exists → coins deposited at @0x0, permanently lost.
   Scenario B: @0x0 account absent → create_account(@0x0) aborts (vm_reserved blocked)
               → entire unlock_stake reverts → staker's funds permanently frozen.

3. Staker cannot call unlock_stake, switch_operator, or distribute ever again
   as long as beneficiary_for_operator(operator) == @0x0.
```

    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
