### Title
A debtor can front-run liquidation and repay dust debt to force `Pool.liquidate()` to revert - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate()` reverts when the caller-requested `amountToRepay_` exceeds `maxLiquidable` multiplied by the debtor’s current `DebtToken` balance. An unhealthy debtor can observe a liquidation transaction, front-run it with a dust repayment through `DebtToken.repay()`, reduce the denominator in the liquidation-bound check, and make the previously valid `amountToRepay_` revert with `AmountGreaterThanMaxLiquidable`. [1](#0-0) [2](#0-1) 

### Finding Description
`Pool.liquidate()` is a public, non-reentrant liquidation entry point that accrues interest, verifies that the target position is unhealthy, reads the current debt-token balance, and rejects the request when `amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable`. [3](#0-2) 

If a liquidator submits `amountToRepay_ = D * maxLiquidable`, the debtor can repay any nonzero debt amount `r` before the liquidation executes. The new ratio is:

```text
(D * maxLiquidable) / (D - r) > maxLiquidable
```

Consequently, a request that was valid when quoted or submitted becomes invalid solely because the debtor repaid dust, without restoring the position to health. The position-health check only determines whether liquidation may occur; it does not prevent an unhealthy debtor from changing the debt balance between transaction submission and execution. [4](#0-3) 

`DebtToken.repay()` is callable by an unprivileged account and accepts an arbitrary beneficiary through `onBehalfOf_`; the caller only needs enough synthetic tokens to cover the repaid amount and fee. A debtor therefore can repay its own position with a minimal synthetic-token amount. [5](#0-4) 

The same stale-bound problem exists at the collateral check: `_totalSeized` is calculated from the submitted repayment amount and then compared with the debtor’s current `depositToken_` balance, reverting instead of clamping the request to the currently liquidatable amount. [6](#0-5) 

### Impact Explanation
An unhealthy debtor can repeatedly invalidate liquidation transactions with negligible repayment cost while leaving the position below the collateral-factor limit. Liquidators can resubmit with a lower amount, but the debtor can repeat the dust repayment and force another revert, temporarily delaying liquidation and imposing transaction costs on liquidators.

This breaks liquidation liveness rather than directly stealing collateral or causing protocol insolvency. The impact is bounded by the debtor’s ability to obtain enough synthetic tokens for dust repayments and by the liquidator’s ability to recalculate and resubmit.

### Likelihood Explanation
The attack requires only the public `DebtToken.repay()` function, a small amount of the synthetic token, and ordinary front-running. Issuing debt mints the corresponding synthetic token to the debtor, so an existing borrower commonly has the asset needed for the repayment. [7](#0-6) [8](#0-7) 

The deployed initialization sets `maxLiquidable` to 50%, so maximum-size liquidation requests are especially sensitive: reducing debt by even one unit makes a requested repayment equal to 50% of the old debt exceed 50% of the new debt. [9](#0-8) 

### Recommendation
Do not revert solely because `amountToRepay_` exceeds the currently allowed liquidation amount. Clamp the amount to the current maximum before calculating collateral to seize:

```solidity
uint256 maxAmountToRepay = _debtToken.balanceOf(account_).wadMul(maxLiquidable);
if (amountToRepay_ > maxAmountToRepay) {
    amountToRepay_ = maxAmountToRepay;
}
```

Also account for the selected collateral’s available balance, equivalent to `quoteLiquidateMax()`, and only revert if the resulting amount is zero or another invariant such as the debt floor cannot be satisfied. The existing `quoteLiquidateMax()` already models the desired minimum of the debt fraction and collateral-limited repayment amount. [10](#0-9) 

### Proof of Concept
The following Hardhat test can be added inside the existing unhealthy-position `liquidate` test context in `test/Pool.test.ts`. It demonstrates that a dust repayment makes a previously valid 50% repayment request revert:

```typescript
it('allows debtor to invalidate liquidation with dust repayment', async function () {
  await pool.updateMaxLiquidable(parseEther('0.5'))

  const debtBefore = await msEthDebtToken.balanceOf(alice.address)
  const amountToRepay = debtBefore.div(2)

  expect(amountToRepay.wadDiv(debtBefore)).lte(parseEther('0.5'))

  // Net repayment is exactly 1 debt unit even if a repay fee exists.
  const {_amount: dustGrossAmount} = await msEthDebtToken.quoteRepayIn(1)
  await msEthDebtToken.connect(alice).repay(alice.address, dustGrossAmount)

  const {_isHealthy} = await pool.debtPositionOf(alice.address)
  expect(_isHealthy).false

  const tx = pool
    .connect(liquidator)
    .liquidate(msEth.address, alice.address, amountToRepay, msdMET.address)

  await expect(tx).revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable')
})
```

The test relies on the existing setup where Alice has minted `msETH`, the liquidator holds `msETH`, and the position is made unhealthy by lowering the MET price. [11](#0-10) [12](#0-11)
