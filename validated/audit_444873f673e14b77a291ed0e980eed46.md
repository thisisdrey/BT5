### Title
Out-of-bounds read of Zip64 extra-field attribute array via attacker-controlled index in singlejar's `CDH` accessors - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`CDH::compressed_file_size()` and `CDH::local_header_offset()` compute an index into the Zip64 extra field's `attr_[]` array from attacker-controlled 32-bit header fields, then use that index to read `attr64(index)` without validating it against the extra field's actual `attr_count()`. This mirrors CVE-2018-19985's bug class: a value read from untrusted input is used unchecked as an array index, producing an out-of-bounds read.

### Finding Description
`singlejar` (`InputJar`, `src/tools/singlejar/input_jar.h`) memory-maps an untrusted jar/zip supplied to a Bazel action and walks Central Directory Header (`CDH`) entries via `NextEntry()`. [1](#0-0) 

For each `CDH`, `local_header_offset()` computes the local-header offset. When the 32-bit `local_header_offset32_` field equals `0xFFFFFFFF` (attacker sets this), the real 64-bit value is looked up in the Zip64 extra field, at an index (`attr_no`) computed purely from whether the attacker-controlled `uncompressed_file_size32_`/`compressed_file_size32_` fields are also `0xFFFFFFFF`: [2](#0-1) 

Similarly, `compressed_file_size()` computes an index from `uncompressed_file_size32()`'s "has-ext64" flag: [3](#0-2) 

`Zip64ExtraField::attr64(index)` performs a raw, unchecked array access: [4](#0-3) 

`attr_count()` (derived from the extra field's own `payload_size()`, which is also attacker-controlled and independent of the 32-bit flags) is defined but never consulted before indexing. An attacker who crafts the CDH entry so that all three 32-bit fields (`uncompressed_file_size32_`, `compressed_file_size32_`, `local_header_offset32_`) equal `0xFFFFFFFF` forces `attr_no = 2` in `local_header_offset()`, while supplying a Zip64 extra field whose `payload_size()` only covers 0 or 1 `uint64_t` entries (`attr_count() < 2`). The resulting `attr64(2)` read is out of the bounds of the extra field's declared payload, into adjacent header/comment bytes or, if the extra field is placed at the very end of the mapped file region, into memory beyond the mapping — an out-of-bounds read directly analogous to `hso_get_config_data`'s unchecked `if_num` indexing in the reported CVE.

`ExtraField::find()` only validates that the field the attacker declares fits within the surrounding `extra_fields_length()` window, it does not (and cannot) know how many `attr64` entries the *consumer* will later assume are present: [5](#0-4) 

### Impact Explanation
This affects `singlejar`, the tool Bazel uses to merge/repackage jars during Java builds, which processes zip/jar inputs (including build outputs and potentially third-party jars fed as `srcs`/`deps`) via `InputJar`. An out-of-bounds read here can leak adjacent process memory content into computed offsets used for subsequent parsing (e.g., `LocalHeader()` dereferences `local_header_offset()` to compute a pointer into the mapped file: `mapped_file_.address(cdh->local_header_offset() + preamble_size_)`), potentially causing further OOB reads or crashes, and in principle could leak bytes of adjacent heap/mmap content back into the build. This is a memory-safety violation in native C++ code processing untrusted archive content. [6](#0-5) 

### Likelihood Explanation
Likelihood is limited: `singlejar` is a native binary invoked as part of the Java build action, and the crafted jar must be consumed as an input to a singlejar action (an unprivileged dependency author who controls a jar's bytes — e.g., an untrusted-branch CI build or a maliciously crafted downloaded jar — can trigger this). No credentials, MITM, or trusted-repo Starlark are needed; only crafted, syntactically-plausible zip metadata (a legal-looking CDH with a short Zip64 extra field). This is a plain data-parsing bug in a fixed binary format, independent of any integrity/hash verification (checksums verify the *download*, not the internal structural consistency of the archive's own headers), so no existing Bazel checksum/lockfile/containment mechanism defends against it.

### Recommendation
In `Zip64ExtraField::attr64()`/`CDH::compressed_file_size()`/`CDH::local_header_offset()` (and analogous `LH` accessors), validate `attr_no < attr_count()` before dereferencing `attr_[index]`, and treat an out-of-range index the same as `z64 == nullptr` (return an error/sentinel value or fail the read) rather than performing the raw indexed load. Add fuzz/unit coverage in `zip_headers_test.cc` for malformed Zip64 extra fields whose declared `payload_size()` is smaller than what the 32-bit "has-ext64" flags imply is needed.

### Proof of Concept
A `BuildIntegrationTestCase`/`zip_headers_test.cc`-style unit test can construct a raw `CDH` buffer with:
- `uncompressed_file_size32_ = 0xFFFFFFFF`
- `compressed_file_size32_ = 0xFFFFFFFF`
- `local_header_offset32_ = 0xFFFFFFFF`
- an appended Zip64 extra field (tag `0x0001`) with `payload_size = 8` (i.e., only one `uint64_t`, `attr_count() == 1`)

and call `cdh->local_header_offset()`, which computes `attr_no = 1 + 1 = 2` and calls `z64->attr64(2)`, reading 16 bytes past the start of the single-entry `attr_[]` array — outside the field's declared payload — demonstrable under AddressSanitizer as a heap/mmap out-of-bounds read.

class ExtraField {
 public:
  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
