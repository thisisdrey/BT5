## Title
Self-matching orders in `MarketSellAssetActuator` allows an unbacked balance / permanent loss of matched proceeds due to a stale in-memory `AccountCapsule` overwrite - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
The external report describes an owner-bypass pattern (self-bidding/self-offering) that is trivially reachable via a second address and is only "mitigated," not eliminated, because Sybil resistance cannot be enforced on-chain. The same structural weakness exists in java-tron's on-chain TRC10 order-book market: `MarketSellAssetActuator.validate()` contains no check preventing a taker order from matching against a resting maker order owned by the very same account address [1](#0-0) . Unlike `ParticipateAssetIssueActuator`, which explicitly rejects self-dealing with `"Cannot participate asset Issue yourself!"` [2](#0-1) , and `VMUtils.validateForSmartContract`, which rejects `ownerAddress == toAddress` transfers [3](#0-2) , `MarketSellAssetActuator` has no equivalent guard. Existing unit tests even demonstrate the exact same address matching its own resting orders as a normal, accepted flow (`hasBuyAddFirstSellOrderNotMatch1`, `noBuyAddMultiSellOrder1`, etc.) [4](#0-3) .

### Finding Description
Beyond simply enabling a "fake supply/demand" illusion (the report's core concern), allowing self-matching in `MarketSellAssetActuator` triggers a real accounting bug because of how account state is persisted during matching:

1. In `execute()`, the taker's `AccountCapsule` is loaded once into a local variable `accountCapsule`, mutated in-memory (fee, sell-token debit, and later buy-token credit from `addTrxOrToken(takerOrderCapsule, ..., takerAccountCapsule)`), and only written back to `accountStore` at the very end of the method [5](#0-4) .
2. During matching, the maker side of each fill is credited through the *other* overload of `addTrxOrToken(MarketOrderCapsule, long)`, which independently re-reads the maker's account from `accountStore`, adds the buy-token proceeds, and immediately `put()`s it back mid-execution [6](#0-5) .
3. When the maker order's owner address equals the taker's address (self-match, which `validate()` never forbids), step 2's immediate write is a *stale, independent copy* of the same account. The final `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` in `execute()` (line 148) unconditionally overwrites the account state again using the taker's in-memory object, which never observed the maker-side credit applied in step 2. That maker-side proceeds credit is silently discarded.

Net effect for a self-matched trade: the sell-side tokens are deducted (via `transferBalanceOrToken` for the taker leg and via the maker order's earlier reservation), but the corresponding buy-side credit for the maker leg of the trade is lost when the two divergent in-memory account snapshots for the same address are written back in sequence, with the taker's stale snapshot winning last.

### Impact Explanation
This results in an unbacked/inconsistent balance: tokens are removed from circulation on the sell side of the self-trade without ever being credited back, effectively permanently freezing/burning a user's own funds through normal, permissionless use of the on-chain market feature (`MarketSellAssetContract`). Because the market actuator directly manipulates `AccountCapsule` balances and TRC10 asset amounts that back the chain's ledger of value, silently dropping a credited leg is a concrete "permanent freezing of funds" / "unbacked balance" condition, not merely a cosmetic supply/demand illusion.

### Likelihood Explanation
Any account can trivially trigger this: place a maker order (e.g., sell asset A for asset B) with `MarketSellAssetContract`, let it rest in the order book, then place an opposing taker order (sell asset B for asset A) from the same address so that it matches the resting order. No special privilege, committee approval, or additional signer is needed beyond `dynamicStore.supportAllowMarketTransaction()` being enabled, which is a normal committee-controlled market feature flag, not an attacker-controlled gate. The existing test suite already exercises same-account order matching as a supported path, confirming the code allows it without restriction [7](#0-6) .

### Recommendation
- Add an explicit validation in `MarketSellAssetActuator.validate()` (mirroring `ParticipateAssetIssueActuator`) to reject matching if the maker order's owner address equals the taker's address, or more robustly:
- Fix the underlying persistence bug regardless of self-matching: route all account balance mutations for a single transaction through one consistent in-memory map/cache keyed by address, so the maker-credit path (`addTrxOrToken(MarketOrderCapsule, long)`) and the taker-credit path operate on the same object when addresses coincide, and only a single, final write per address occurs in `execute()`.

### Proof of Concept
1. Account `A` calls `MarketSellAssetContract` selling `sellTokenQuantity` of token `X` for `buyTokenQuantity` of token `Y`; order rests in the book (no match yet) — analogous to `addOrder(...)` calls in `MarketSellAssetActuatorTest` [8](#0-7) .
2. Same account `A` then calls `MarketSellAssetContract` selling token `Y` for token `X` at a matching price, causing `matchOrder`/`matchSingleOrder` to match against its own resting order from step 1 [9](#0-8) .
3. Inside `matchSingleOrder`, the maker-side credit is applied via `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` which reads/writes `accountStore` immediately for address `A` [6](#0-5) .
4. After matching completes, `execute()` performs `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` using the stale taker-side in-memory copy of account `A`, overwriting the update from step 3 and discarding the maker-side credit [10](#0-9) .
5. Final on-chain balance of account `A` for token `X`/`Y` is short by the amount that should have been credited on the maker leg, demonstrating a reproducible fund loss for any self-matched market order.

    byte[] makerSellTokenID = buyTokenID;
    byte[] makerBuyTokenID = sellTokenID;
    byte[] makerPair = MarketUtils.createPairKey(makerSellTokenID, makerBuyTokenID);

    // makerPair not exists
    long makerPriceNumber = pairToPriceStore.getPriceNum(makerPair);
    if (makerPriceNumber == 0) {
      return;
    }
    long remainCount = makerPriceNumber;

    // get maker price list
    List<byte[]> priceKeysList = pairPriceToOrderStore
        .getPriceKeysList(MarketUtils.getPairPriceHeadKey(makerSellTokenID, makerBuyTokenID),
            (long) (MAX_MATCH_NUM + 1), makerPriceNumber, true);

    int matchOrderCount = 0;
    // match different price
    while (takerCapsule.getSellTokenQuantityRemain() != 0) {
      // get lowest ordersList
      MarketPrice makerPrice = hasMatch(priceKeysList, takerPrice);
      if (makerPrice == null) {
        return;
      }

      byte[] pairPriceKey = priceKeysList.get(0);

      // if not exists
      MarketOrderIdListCapsule orderIdListCapsule = pairPriceToOrderStore.get(pairPriceKey);

      // match different orders which have the same price
