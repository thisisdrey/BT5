### Title
Unbounded, instantaneous `UpdateSettingContractActuator` percent change lets a contract owner retroactively grief users/delegators who already committed resources - ([File: actuator/src/main/java/org/tron/core/actuator/UpdateSettingContractActuator.java])

### Summary
The external report flags `setCoolDownInSecs()` for allowing an owner to change a critical economic parameter to an arbitrary value with no bound and no protection for participants who already committed funds under the previous value. The directly analogous pattern in java-tron is `UpdateSettingContractActuator`, which lets any smart-contract owner (an unprivileged, ordinary "contract deployer" account, not a witness/committee) instantly change `consume_user_resource_percent` for a deployed contract at any time, with the only bound being a static `[0,100]` range check and no protection for callers/resource-delegators who already relied on the prior percentage.

### Finding Description
`UpdateSettingContractActuator.validate()` only checks that the new percent is within `[0, 100]` and that the caller is the contract's origin address [1](#0-0) . There is no rate limit, timelock, minimum notice period, or "one-directional" constraint (e.g., only allowed to decrease, or requiring pending delegations to settle) as recommended for `setCoolDownInSecs()` in the external report. `execute()` writes the new percent straight into the `ContractCapsule` and immediately evicts the LRU cache so the new value is live for the very next contract invocation [2](#0-1) .

This percentage is read live, at TVM-execution time, by `VMActuator.getTotalEnergyLimitWithFixRatio()` to split energy costs between the contract owner ("creator") and the caller: when `consumeUserResourcePercent` is low, the owner's frozen energy pays most of the bill; when it is raised (up to 100), the caller must cover a correspondingly larger share [3](#0-2) . Because the update takes effect immediately (no cooldown/timelock and no "commit-then-apply-later" semantics), any user who delegated resources or built a transaction/feeLimit under the assumption of the previous percent can have that assumption invalidated by the very next block, exactly mirroring the report's scenario: "user A locks under cooldown T1, owner changes it to T2, and T2 (not T1) applies to A's operation."

`UpdateEnergyLimitContractActuator` exhibits the identical pattern for `origin_energy_limit`: only a `> 0` check is enforced, with no bound, timelock, or protection for in-flight/expected resource commitments [4](#0-3) , and this value is also consumed live by the same energy-split formula [5](#0-4) .

### Impact Explanation
A contract owner can flip `consume_user_resource_percent` from 0 (owner pays) to 100 (caller pays) or vice versa immediately before/after users interact with the contract, without any advance notice, bound tightening, or delay. Callers relying on delegated energy (via `DelegateResourceActuator`, which explicitly supports locking resources to a specific address for a committed period [6](#0-5) ) can suddenly be forced to burn their own frozen/free energy or TRX fee (`feeLimit`) that they did not budget for, causing unexpected fee loss or transaction failure (OUT_OF_ENERGY reverts still consuming resources already delegated/locked). This is a fairness/DoS-style griefing vector against unsuspecting callers, matching Medium severity per the original finding.

### Likelihood Explanation
Any account that owns/deployed a smart contract (an ordinary, non-privileged actor per the in-scope actor list) can broadcast an `UpdateSettingContract` or `UpdateEnergyLimitContract` transaction at will, with no cooldown or multi-step approval, making this trivially and repeatedly reachable.

### Recommendation
Apply the same mitigations the external report recommends for `setCoolDownInSecs()`: (1) restrict how much/how often the percent or energy limit may change per unit time, (2) add a timelock/notice period before a change takes effect so in-flight resource delegations/transactions are unaffected, and (3) preserve the previously-committed percent for delegations that were made under the old setting rather than always reading the live value.

### Proof of Concept
1. Contract owner deploys `C` with `consume_user_resource_percent = 0` and delegates resources so that callers expect to pay $0 energy.
2. User `U` freezes/delegates energy to interact with `C`, and/or submits a transaction with `feeLimit` sized for a 0% caller-pay ratio.
3. Before `U`'s transaction lands, owner broadcasts `UpdateSettingContract` setting `consume_user_resource_percent = 100` — accepted immediately by `UpdateSettingContractActuator.validate()`/`execute()` [7](#0-6) .
4. `U`'s transaction executes under the new 100% ratio via `VMActuator.getTotalEnergyLimitWithFixRatio()` [8](#0-7) , consuming `U`'s own energy/TRX unexpectedly or failing with OUT_OF_ENERGY despite `U`'s prior expectation and resource commitment.

  @Override
  public boolean execute(Object object) throws ContractExeException {
    TransactionResultCapsule ret = (TransactionResultCapsule) object;
    if (Objects.isNull(ret)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    long fee = calcFee();
    ContractStore contractStore = chainBaseManager.getContractStore();
    try {
      UpdateSettingContract usContract = any.unpack(UpdateSettingContract.class);
      long newPercent = usContract.getConsumeUserResourcePercent();
      byte[] contractAddress = usContract.getContractAddress().toByteArray();
      ContractCapsule deployedContract = contractStore.get(contractAddress);

      contractStore.put(contractAddress, new ContractCapsule(
          deployedContract.getInstance().toBuilder().setConsumeUserResourcePercent(newPercent)
              .build()));
      RepositoryImpl.removeLruCache(contractAddress);

      ret.setStatus(fee, code.SUCESS);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      ret.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }
    return true;
  }
