### Title
Fixed-window (non-sliding) per-connection stream throttling allows boundary-straddling bursts to double effective TPU stream throughput - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Summary
`ConnectionStreamCounter::reset_throttling_params_if_needed` resets `stream_count` to 0 only when wall-clock elapsed time since `last_throttling_instant` exceeds `STREAM_THROTTLING_INTERVAL` (100ms), implementing a fixed (tumbling) window rather than a sliding window. `throttle_stream` only sleeps a caller once `streams_read_in_throttle_interval >= max_streams_per_throttling_interval` within the current window, so an attacker can send `max_streams_per_throttling_interval` streams just before a window boundary and another full burst just after it, resulting in nearly `2x max_streams_per_throttling_interval` streams accepted within a ~100ms real-time span.

### Finding Description
`reset_throttling_params_if_needed` (`streamer/src/nonblocking/stream_throttle.rs:213-230`) tracks `last_throttling_instant` and resets `stream_count` to 0 only after more than `STREAM_THROTTLING_INTERVAL` (100ms) has elapsed since the last reset: [1](#0-0) 

`throttle_stream` (`streamer/src/nonblocking/stream_throttle.rs:233-271`) checks the counter against `max_streams_per_throttling_interval` and only sleeps the connection task once that threshold is reached within the *current* fixed window: [2](#0-1) 

Because the window boundary is anchored to `last_throttling_instant` (set once per reset) rather than continuously sliding, an attacker who times stream opens to straddle the boundary — e.g., `max_streams_per_throttling_interval` streams at t=99ms (counted in window A ending near t≈X) followed immediately by another `max_streams_per_throttling_interval` streams at t=101ms (counted in freshly-reset window B) — is not throttled for either burst, since each burst individually stays under the per-window cap. This is inherent to any fixed/tumbling-window counter and is not mitigated elsewhere in the visible code (`available_load_capacity_in_throttling_duration` in the same file computes only per-window caps, not a sliding computation).

I was not able to fully trace the call sites in `streamer/src/nonblocking/quic.rs` where `throttle_stream` and `ConnectionStreamCounter` are invoked per-stream (the grep only located matches in `streamer/src/nonblocking/swqos.rs`, and I could not retrieve the exact surrounding logic due to index limitations), so I cannot confirm with certainty whether there is an additional outer-layer smoothing/limiting mechanism (e.g. the `StakedStreamLoadEMA`, connection-level concurrent-stream caps enforced by quinn, or per-connection total throughput caps) that would dampen or eliminate this effect in practice for a single connection's stream count. The `StakedStreamLoadEMA` EMA-based load smoothing exists for *staked* aggregate load only and does not affect the per-connection fixed-window reset logic that gates individual stream admission via `ConnectionStreamCounter`.

### Impact Explanation
If confirmed reachable exactly as described, the impact is a QoS/fairness evasion: an unstaked or low-stake sender could obtain up to ~2x its intended `max_streams_per_throttling_interval` allotment across a ~2ms window straddling a 100ms boundary, at the expense of fair-share bandwidth for other unstaked/low-stake connections contending for the same aggregate unstaked stream budget (`max_unstaked_load_in_throttling_window`). This is a rate-limit/QoS evasion, not a panic, memory-safety, consensus, or verification-bypass issue.

### Likelihood Explanation
This requires only an unprivileged client precisely timing stream opens around a per-connection window boundary, which is plausible given `Instant::now()` boundaries are observable/inferable by an attacker via response timing (e.g. by watching that streams begin being throttled/sleeping, indicating a fresh window just started). It is a well-known limitation of fixed-window rate limiters generally, so the effect is real but bounded in magnitude to roughly one extra window's worth of streams, not sustained/repeated amplification, and the gain is capped at approximately double for a single window transition, not compoundable across most subsequent windows without repeatedly hitting exact millisecond-level timing.

### Recommendation
Replace the fixed reset-based counter with a sliding-window or token-bucket algorithm for `ConnectionStreamCounter` (e.g., track timestamps of the last `max_streams_per_throttling_interval` stream opens and require the interval between the current stream and the one `max_streams_per_throttling_interval` streams prior to exceed `STREAM_THROTTLING_INTERVAL`), or use a leaky-bucket/token-refill approach so no window boundary allows a full extra burst.

### Proof of Concept
Unit test plan for `streamer/src/nonblocking/stream_throttle.rs`:
```rust
#[tokio::test]
async fn test_boundary_straddle_doubles_throughput() {
    let stats = StreamerStats::default();
    let stream_counter = Arc::new(ConnectionStreamCounter::new());
    let max_streams: u64 = 10;

    // Simulate burst A: consume max_streams right before window boundary.
    for _ in 0..max_streams {
        stream_counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }
    // Sleep until just past STREAM_THROTTLING_INTERVAL to trigger reset.
    tokio::time::sleep(STREAM_THROTTLING_INTERVAL + Duration::from_millis(1)).await;

    // Burst B: reset_throttling_params_if_needed() will zero the counter here.
    let mut accepted_in_burst_b = 0;
    for _ in 0..max_streams {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, "127.0.0.1:0".parse().unwrap(), &stream_counter, max_streams).await;
        accepted_in_burst_b += 1;
    }

    // Assert burst B was not throttled at all, i.e. total streams accepted across
    // the ~1-2ms boundary window (burst A + burst B) is 2 * max_streams,
    // exceeding the intended single-window cap of max_streams.
    assert_eq!(accepted_in_burst_b, max_streams);
    assert_eq!(stats.throttled_streams.load(Ordering::Relaxed), 0);
}
```
Expected result: the test shows `2 * max_streams_per_throttling_interval` streams accepted with zero throttling events recorded within a time span barely exceeding `STREAM_THROTTLING_INTERVAL`, confirming the fixed-window boundary evasion.

    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }
