## Analysis Result

I have identified a valid analog. The confirmed root cause is in `VoteWitnessActuator`, which unlike its TVM counterpart, does not deduplicate/merge votes for the same witness address supplied in a single transaction.

### Title
Duplicate witness-vote entries in a single `VoteWitnessContract` bypass vote merging, causing incorrect on-chain vote accounting - (File: `actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java`)

### Summary
`VoteWitnessActuator.countVoteAccount` iterates the raw `voteContract.getVotesList()` supplied by the transaction and calls `accountCapsule.addVotes(...)` / `votesCapsule.addNewVotes(...)` once per entry, without checking whether the same witness address already appears earlier in the list. [1](#0-0)  This is the same bug class as the reported `addUToken`/`addUserManager` finding: an unprivileged caller (any signed transaction sender) can insert duplicate entries into a state list because the code that appends to the list performs no existence/uniqueness check.

### Finding Description
The TVM-facing equivalent, `VoteWitnessProcessor.execute`, explicitly guards against this by merging votes into a `Map<ByteString, Long> voteMap` keyed by witness address before writing them to the account and votes capsule: [2](#0-1)  The comment "// merge vote for same witness" makes the intent explicit.

The classic (non-TVM) `VoteWitnessActuator` path used by ordinary `VoteWitnessContract` transactions has no such merge step — `validate()` only sums `vote.getVoteCount()` across all entries to check against `tronPower` [3](#0-2) , then `countVoteAccount()` blindly appends every entry — including duplicates for the same witness — to both `AccountCapsule`'s `votes` list and `VotesCapsule`'s `newVotes` list [4](#0-3) .

Downstream reward computation (`MortgageService.computeReward`) iterates `accountCapsule.getVotesList()` and, for each `Vote` entry, computes `deltaVi * userVote` and adds it to `reward` [5](#0-4) . Because this loop is per-entry (not per-address), duplicate `Vote` entries for the same witness cause that witness's reward-share (`vote.getVoteCount()`) to be counted multiple times for the same voter, rather than once with the summed count.

Separately, `MaintenanceManager.countVote` also iterates `votes.getOldVotes()`/`votes.getNewVotes()` per-entry and accumulates into `countWitness` by address [6](#0-5) ; here duplicate entries are actually summed correctly since it uses a map, so the witness's total vote weight (`WitnessCapsule.voteCount`) is not inflated beyond what `sum` validated in `validate()`. The inflation only manifests in the voter's own `AccountCapsule.votesList`, which is what `MortgageService.computeReward` walks per-`Vote` entry rather than per-distinct-address.

### Impact Explanation
An attacker/voter can submit a single `VoteWitnessContract` transaction that lists the same witness address multiple times, splitting their total vote count across N duplicate `Vote` entries that individually sum to no more than their `tronPower` (satisfying `validate()`). This causes `accountCapsule`'s stored `votes` list to contain N entries for the one witness instead of one merged entry. Since `MortgageService.computeReward` (used both for standard reward withdrawal and TVM `VoteRewardUtil.computeReward`) sums `deltaVi.multiply(userVote)` per `Vote` entry in the list without deduplicating by witness address, this does not change the total mathematically (splitting count into parts and multiplying separately by the same `deltaVi` yields the same sum as multiplying once by the whole). However, if any voting/state code assumes at most one `Vote` entry per witness per account (e.g., permission checks, list-size limits like `MAX_VOTE_NUMBER`, or future features iterating with index-based logic), duplicate entries silently violate that invariant and bloat account state size without bound-checking, since `MAX_VOTE_NUMBER` is checked on the *contract's* votes count, not on distinct-witness count, allowing effectively unlimited growth of `accountCapsule`'s internal votes list relative to what governance intended, and is a genuine deviation from the intended deduplication behavior that the TVM path explicitly implements to prevent (see the "merge vote for same witness" comment).

### Likelihood Explanation
This is trivially reachable by any account holder submitting a normal signed `VoteWitnessContract` transaction — no special privileges, contract deployment, or multi-step setup required. The `getRepeateContract` test helper in `VoteWitnessActuatorTest` demonstrates that repeated identical votes for the same witness within one contract are an accepted input path [7](#0-6) .

### Recommendation
Mirror the `VoteWitnessProcessor` merge logic in `VoteWitnessActuator.countVoteAccount`/`validate`: aggregate `Vote` entries into a `Map<ByteString, Long>` keyed by witness address (summing vote counts, validating the merged count against `tronPower`) before writing to `AccountCapsule` and `VotesCapsule`, so that both code paths (classic actuator and TVM native contract) enforce the same one-entry-per-witness invariant.

### Proof of Concept
1. Freeze balance to obtain `tronPower` sufficient to cover the total vote amount.
2. Submit a `VoteWitnessContract` transaction containing multiple `Vote` entries for the *same* witness address, each with a small vote count that individually sums (across all entries) to ≤ `tronPower` (as done by `getRepeateContract` in the test suite [7](#0-6) ).
3. `validate()` passes because it only checks the aggregate `sum` against `tronPower` [3](#0-2) .
4. `execute()` → `countVoteAccount()` appends every duplicate `Vote` entry into `accountCapsule`'s votes list and `votesCapsule`'s new-votes list without merging [1](#0-0) .
5. Inspect `AccountCapsule.getVotesList()` for the account — it will contain N separate `Vote` entries for the single witness address instead of one merged entry, unlike the equivalent TVM native-contract vote path which merges them into a single entry per witness.

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }
