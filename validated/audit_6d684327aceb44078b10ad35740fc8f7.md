## #Vulnerability found

### Title
Non‑atomic replay‑window check‑then‑update in `ConnectionState.Decrypt`/`VerifyRelay` allows message‑counter replay bypass - (File: `connection_state.go`)

### Summary
The external report's bug class is a helper routine that performs a sensitive state‑changing operation but is reachable without the validation/locking guarantees its callers normally provide, letting an attacker retrigger it and get a result more than once. The Nebula analog is `ConnectionState.Decrypt` and `ConnectionState.VerifyRelay`, which release and re‑acquire `decryptLock` between the anti‑replay `window.Check` and the anti‑replay `window.Update` calls, creating a window in which the same message counter can pass the replay check twice.

### Finding Description
`ConnectionState.Decrypt` is the data‑plane decryption path invoked for every incoming UDP packet on an established tunnel. It is supposed to guarantee that a given `messageCounter` is decrypted (accepted) at most once, using the `Bits` replay window (`window.Check` / `window.Update`). [1](#0-0) 

The check and the update are performed as two separate, independently locked critical sections:

```go
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)
cs.decryptLock.Unlock()
...
out, err = cs.dKey.DecryptDanger(...)
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)
cs.decryptLock.Unlock()
``` [2](#0-1) 

Because the lock is dropped between `Check` and the later `Update`, and `DecryptDanger` itself does not consult or mutate the replay window (it only performs AEAD open with the raw counter as nonce, with no de‑duplication logic), the actual duplicate‑suppression rests entirely on the `Bits.Check`/`Bits.Update` pair being observed atomically. `Bits.Check` only inspects state and returns a boolean, it does not mark the counter seen; `Bits.Update` is the only call that mutates the bitmap. [3](#0-2) [4](#0-3) 

`VerifyRelay`, used for relay‑frame authentication, has the exact same pattern. [5](#0-4) 

If two goroutines call `Decrypt` (or `VerifyRelay`) concurrently with an identical captured/replayed ciphertext and counter — e.g. a UDP receive worker processing a duplicated wire packet delivered twice in quick succession — both can pass `window.Check` before either has called `window.Update`, because the lock is released after `Check` and only re‑acquired afterward. Both calls then proceed to `DecryptDanger`, which has no replay awareness of its own, and both succeed, with the window's `Update` step (whichever runs first) marking the counter seen only after the fact. This mirrors the reported bug class exactly: a sensitive operation (`_repayCredit`/here, "consume and decrypt a message counter") that is supposed to be gated by validation performed by its caller (`repayCredit`/`liquidate`, here "check replay window") but can be invoked in a way that bypasses the atomicity of that validation, allowing the same protected resource (a fresh AEAD nonce/counter) to be consumed more than once.

### Impact Explanation
An attacker who can duplicate wire delivery of a captured Nebula data packet (trivial on UDP — simply send the same encrypted packet bytes twice, no valid certificate or key material required beyond what a normal peer already possesses on the wire) can potentially cause the same message counter to be accepted and decrypted twice by the receiver before the replay window is updated. This subverts Nebula's anti‑replay guarantee, which is a core security property of the transport (equivalent to defeating IPsec/WireGuard-style replay protection). Depending on the higher layers consuming the decrypted plaintext, a successfully replayed packet could cause duplicate processing of tunneled traffic (e.g., duplicate application‑layer commands relayed over the tunnel), and for `VerifyRelay` a duplicated relay frame could similarly be re‑authenticated and forwarded twice.

### Likelihood Explanation
Exploitation requires only capturing a single valid encrypted Nebula packet from the wire and re‑injecting it in a very tight timing window against a receiver processing packets from more than one goroutine (or otherwise re‑entrant call to `Decrypt`), which is consistent with the "no CA‑signed certificate" reachable path since no cryptographic material needs to be attacker‑controlled — only replay of already‑observed ciphertext is needed. The race window is narrow (must land the second copy between the first's `Check` and `Update`), so likelihood is moderate rather than trivial, but the bug is a genuine correctness defect in the replay‑protection code path, not a theoretical concern.

### Recommendation
Make the check‑and‑mark operation atomic: hold `decryptLock` across both the `window.Check` and `window.Update` calls (or better, fold them into a single locked "reserve" operation performed *before* decryption, analogous to `Bits.Update`'s combined semantics), so no other caller can observe the counter as "not yet seen" between the two steps. Concretely, `Decrypt`/`VerifyRelay` should reserve the counter slot (mark it tentatively consumed) under one lock acquisition prior to calling `DecryptDanger`, and only roll back the reservation if decryption fails, rather than checking, unlocking, decrypting, and re‑locking to update.

### Proof of Concept
1. Establish a Nebula tunnel between two nodes and capture one legitimate encrypted data packet (ciphertext + header) sent from peer A to peer B.
2. Rapidly re‑inject (send) the identical UDP packet twice back‑to‑back to peer B's listening socket (feasible from an on‑path/off‑path attacker able to spoof/duplicate UDP datagrams, or by a compromised peer replaying its own earlier legitimate traffic).
3. If peer B processes inbound packets on more than one goroutine/queue (see `interface.go`'s multiple `listenOut` workers) or otherwise re‑enters `ConnectionState.Decrypt` concurrently for the same `ConnectionState`, both copies can pass `cs.window.Check(l, messageCounter)` in `connection_state.go:64` before either reaches `cs.window.Update(l, messageCounter)` at `connection_state.go:76`, because `decryptLock` is released in between (`connection_state.go:65`) and re‑acquired independently by each call. Both invocations then successfully call `cs.dKey.DecryptDanger(...)` at `connection_state.go:70`, i.e. the replayed packet is decrypted twice instead of being rejected as `ErrAlreadySeen`. [1](#0-0)

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

// updateSlow handles jumps, in-window backfill, dupes, and out-of-window.
func (b *Bits) updateSlow(l *slog.Logger, i uint64) bool {
	// If i is a jump, adjust the window, record lost, update current, and return true
	if i > b.current {
		end := i
		if end > b.current+b.length {
			end = b.current + b.length
		}
		count := end - b.current
		startPos := (b.current + 1) & b.lengthMask

		var lost int64
		if b.current >= b.length {
			// Steady state: every cleared slot is past warmup, so any unset
			// bit we evict is a lost packet from the previous cycle.
			wasSet := b.clearRange(startPos, count)
			lost = int64(count) - int64(wasSet)
		} else {
			// Warmup (the very first window). Some cleared slots represent
			// packets <= length where eviction is not "lost" in the usual
			// sense. This branch is taken at most once per connection so we
			// don't bother optimizing it.
			for n := b.current + 1; n <= end; n++ {
				if !b.get(n) && n > b.length {
					lost++
				}
			}
			b.clearRange(startPos, count)
		}

		// Anything past the new window can never be backfilled, so it's lost.
		if i > b.current+b.length {
			lost += int64(i - b.current - b.length)
		}
		b.lostCounter.Inc(lost)

		b.set(i)
		b.current = i
		return true
	}
