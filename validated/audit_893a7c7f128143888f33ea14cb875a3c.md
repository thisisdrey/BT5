### Title
Dust-transfer griefing fills `depositTokensOfAccount` to `MAX_TOKENS_PER_USER`, blocking victims from receiving new collateral types and enabling forced liquidations - (File: contracts/Pool.sol)

### Summary
`Pool` maintains a per-account enumerable set of deposit tokens (`depositTokensOfAccount`) capped by `MAX_TOKENS_PER_USER`. Because `DepositToken` shares are transferable and every non-zero receipt registers the token in the recipient's set via `Pool.addToDepositTokensOfAccount`, an unprivileged attacker can dust-transfer small amounts of each registered deposit token to a victim, filling all slots. The victim can then no longer receive (or deposit into) any *new* deposit token type, mirroring CVE-2020-8619's pattern: an attacker who can "write" a marker into shared state creates a crafted record (here, dust share entries — the analog of the empty non-terminal `*` node) that causes a persistent operational failure for the target rather than for the attacker.

### Finding Description
`Pool` tracks each account's deposit tokens in a `MappedEnumerableSet` and enforces a cap: `addDepositToken` reverts with `ReachedMaxDepositTokens` once `depositTokens.length() >= MAX_TOKENS_PER_USER` (contracts/Pool.sol:703), and symmetric per-account registration happens through `addToDepositTokensOfAccount` / `removeFromDepositTokensOfAccount` callbacks invoked by `DepositToken` whenever balances cross zero (contracts/Pool.sol:625-634). `DepositToken` balances are ERC-20 shares; an attacker holding shares of every listed collateral (cheaply obtainable by depositing minimal amounts of each underlying) can transfer 1 wei of each token to a victim address. Each dust transfer inserts the token into the victim's `depositTokensOfAccount` set until the cap is reached. Any subsequent attempt by the victim to deposit a *different* collateral type — or to receive shares of one — reverts when the set insertion hits the cap. Notably, this also blocks liquidation rescue: a victim whose position is deteriorating cannot add a new collateral type to restore health, and `Pool.liquidate` (contracts/Pool.sol:537-596) can then be executed against them. The removal path (`removeFromDepositTokensOfAccount`) only frees a slot when a balance goes to exactly zero, so the attacker can re-dust at negligible cost if the victim exits a position.

### Impact Explanation
Permanent (as long as the attacker maintains the dust) denial of deposits into new collateral types for targeted accounts, and forced liquidations: a victim approaching the liquidation threshold who would normally deposit a healthier collateral is prevented from doing so, directly enabling seizure of their collateral by liquidators. This qualifies as temporary freezing of funds / blocked liveness of a core user flow caused solely by an unprivileged attacker's normal ERC-20 transfers — no privileged role, oracle manipulation, or governance change required.

### Likelihood Explanation
Likelihood is moderate-to-high for targeted attacks: it requires the attacker to hold dust of each listed deposit token (bounded by `MAX_TOKENS_PER_USER` and the number of listed collaterals) and to front-run or sandwich the victim's deposit/liquidation-rescue transactions. Cost is low (dust amounts plus gas); benefit is the liquidation incentive on the victim's position, matching `liquidate`'s `_toLiquidator` share in contracts/Pool.sol:581-589. Likelihood is limited to victims holding fewer than the max token types and needing a new collateral type.

### Recommendation
Track "deposit tokens of account" separately for accounting/health purposes without coupling ERC-20 share transfers to the capped set — e.g., revert-free insertions where overflow entries are ignored for rewards but still counted in `depositOf`, or decouple the cap from unsolicited transfers by only registering tokens on explicit `deposit()` calls initiated by the account itself. Alternatively, allow victims to force-remove entries via a user-callable `removeFromDepositTokensOfAccount`-style escape hatch, and exempt pure inbound transfers from the cap so dust griefing cannot block deposits.

### Proof of Concept
Reproducible on a Foundry fork per `test/foundry/MultiPool.t.sol` setup: (1) attacker deposits 1 wei-equivalent of each listed underlying into each `DepositToken` and transfers 1 wei of each share to the victim until the victim's `depositTokensOfAccount` length equals `MAX_TOKENS_PER_USER`; (2) victim calls `DepositToken.deposit(amount, victim)` for a collateral type not yet in their set — the call reverts inside `Pool.addToDepositTokensOfAccount` with `ReachedMaxDepositTokens`; (3) with collateral price moved down via the mock `MasterOracle` (same-transaction oracle moves per test harness), `Pool.liquidate(msAsset, victim, amount, depositToken)` succeeds while any rescue deposit of a new collateral type remains impossible.

*Uncertainty note:* index access to `DepositToken.sol` transfer internals was limited in this session; the analog relies on `Pool.addToDepositTokensOfAccount` being invoked on inbound share transfers (the inverse of the zero-balance removal hook shown at contracts/Pool.sol:625-634). If inbound transfers bypass set registration, the vector weakens to deposits-only blocking.
