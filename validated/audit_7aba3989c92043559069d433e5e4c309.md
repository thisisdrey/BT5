## Title
Shared per-repository concurrency queue in `limithandler` allows any unauthenticated caller to exhaust `max_queue_size`/`max_per_repo` and deny legitimate fetches/clones of the same repository - (File: `internal/grpc/middleware/limithandler/middleware.go`)

### Summary
Gitaly implements a backpressure mechanism that limits in-flight and queued RPCs **per repository** using a single shared key derived from the repository's relative path [1](#0-0) . When a repository hits its configured `max_per_repo` concurrency and `max_queue_size` queue limit, any additional caller targeting that same repository is rejected with a `ResourceExhausted`/`LimitError`, regardless of who they are [2](#0-1) . This mirrors the reported bug class: a protective resource limit (`maxContractBalance` in the treasury) that is keyed on a single shared counter can be deliberately driven to its ceiling by any actor, denying legitimate participants (deposits) from succeeding.

### Finding Description
The concurrency limiter's lock/queue key is computed purely from the target repository's relative path, with no distinction between the caller who is filling the queue and other, unrelated callers [1](#0-0) . The queue enforces two hard ceilings that reject additional callers once reached:
- `maxQueueLength`/`max_queue_size`: once the number of queued callers for the key reaches this value, subsequent callers are rejected immediately with `ErrMaxQueueSize` [3](#0-2) [4](#0-3) .
- `max_per_repo`: the number of concurrently in-flight calls for the key [5](#0-4) .

Because the key is only the repository path (not caller identity), any ordinary, even unauthenticated, client that can reach a rate-limited RPC for a given repository (e.g. `PostUploadPackWithSidechannel` for `git clone`/`git fetch` as recommended in the example config) [5](#0-4)  can flood that single repository with concurrent requests to saturate both the in-flight slots and the queue. This is directly analogous to the whale/flashbundle abusing the shared `maxContractBalance` counter to block other depositors: a single, coarse, shared limit is exposed to manipulation by any party that shares the same key, denying service to all other legitimate users of that key.

The `WithConcurrencyLimiters` setup further shows this is opt-in but explicitly recommended for exactly the kind of public, unauthenticated-reachable RPCs (clone/fetch) that would be most attractive to abuse [6](#0-5) , and an unauthenticated-specific limiter variant exists precisely because unauthenticated traffic is expected on these paths [7](#0-6) .

### Impact Explanation
An attacker (unauthenticated or a low-privilege ordinary client) can target one repository and burst enough concurrent RPC calls (e.g., clone/fetch requests) to fill `max_per_repo` and then `max_queue_size` for that repository's key. Every legitimate user attempting to fetch/clone/access the same repository during this window is denied with a `ResourceExhausted` `LimitError` [2](#0-1) . By continuously repeating the burst (analogous to the whale re-depositing after withdrawing), the attacker can sustain a denial-of-service against all other users of a targeted repository, without needing any elevated privilege, purely by exploiting the shared per-repo limit gate that the RPC-handler resource-limiting feature exposes.

### Likelihood Explanation
The concurrency-limiting feature is explicitly documented and recommended for the exact RPCs (e.g. `PostUploadPackWithSidechannel`) that are reachable by ordinary/unauthenticated fetch and clone operations [8](#0-7) . Any client capable of issuing multiple concurrent RPCs against a target repository (a trivial capability for any Git client) can trigger this condition; no race-condition timing or privileged access is required, only concurrency, making this readily reproducible whenever an operator has configured per-repo concurrency limits as recommended.

### Recommendation
- Incorporate caller/session identity (or at minimum separate authenticated vs. unauthenticated traffic more granularly, and per-source-IP/token sub-limits) into the queue key so that one caller cannot monopolize the entire per-repository queue and starve unrelated legitimate callers.
- Consider fair-queuing or per-caller sub-limits within the per-repository bucket instead of one global FIFO queue keyed solely by repository path.
- Ensure `max_queue_size`/`max_per_repo` guidance documents this shared-resource abuse risk so operators can size limits and combine them with per-IP/per-token throttling at the edge (e.g., Workhorse/Rails) to prevent a single actor from exhausting a repository's queue.

### Proof of Concept
1. Operator configures, per the documented example, a concurrency limit on a public/unauthenticated-reachable RPC:
   ```toml
   [[concurrency]]
   rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
   max_per_repo = 1
   max_queue_wait = "1m"
   max_queue_size = 5
   ```
   as shown in [9](#0-8) .
2. Attacker issues `max_per_repo + max_queue_size` (here, 6) concurrent clone/fetch requests against the same public repository, all of which enter the shared queue keyed by `LimitConcurrencyByRepo` [1](#0-0) .
3. Any legitimate 7th caller attempting to clone/fetch the same repository is immediately rejected with `ErrMaxQueueSize`/`ResourceExhausted`, as demonstrated by the existing test harness pattern [10](#0-9) .
4. Attacker repeats the burst indefinitely (or holds connections open), sustaining denial of clone/fetch access to the targeted repository for all other users.

// WithConcurrencyLimiters sets up middleware to limit the concurrency of
// requests based on RPC and repository
func WithConcurrencyLimiters(cfg config.Cfg) (map[string]*limiter.AdaptiveLimit, map[string]*limiter.AdaptiveLimit, SetupFunc) {
	perRPCLimits := map[string]*limiter.AdaptiveLimit{}
	perRPCLimitsUnauthenticated := map[string]*limiter.AdaptiveLimit{}

	for _, concurrency := range cfg.Concurrency {
		// Create authenticated limiter
		limitName := fmt.Sprintf("perRPC%s", concurrency.RPC)
		if concurrency.Adaptive {
			perRPCLimits[concurrency.RPC] = limiter.NewAdaptiveLimit(limitName, limiter.AdaptiveSetting{
				Initial:       concurrency.InitialLimit,
				Max:           concurrency.MaxLimit,
				Min:           concurrency.MinLimit,
				BackoffFactor: limiter.DefaultBackoffFactor,
			})
		} else {
			perRPCLimits[concurrency.RPC] = limiter.NewAdaptiveLimit(limitName, limiter.AdaptiveSetting{
				Initial: concurrency.Concurrency(),
			})
		}

		// Create unauthenticated limiter if configured
		unauthLimits := concurrency.Unauthenticated
		if unauthLimits.IsSet() {
			limitNameUnauth := fmt.Sprintf("perRPC%s-unauthenticated", concurrency.RPC)
			if unauthLimits.Adaptive {
				perRPCLimitsUnauthenticated[concurrency.RPC] = limiter.NewAdaptiveLimit(limitNameUnauth, limiter.AdaptiveSetting{
					Initial:       unauthLimits.InitialLimit,
					Max:           unauthLimits.MaxLimit,
					Min:           unauthLimits.MinLimit,
					BackoffFactor: limiter.DefaultBackoffFactor,
				})
			} else if unauthLimits.Concurrency() > 0 {
				perRPCLimitsUnauthenticated[concurrency.RPC] = limiter.NewAdaptiveLimit(limitNameUnauth, limiter.AdaptiveSetting{
					Initial: unauthLimits.Concurrency(),
				})
			}
		}
	}

```markdown
Limit the number of concurrent RPCs that are in flight on each Gitaly node for each
repository per RPC using `[[concurrency]]` configuration:

```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
```

For example:

- One clone request comes in for repository "A" (a largish repository).
- While this RPC is executing, another request comes in for repository "A". Because
  `max_per_repo` is 1 in this case, the second request blocks until the first request
  is finished.

An in-memory queue of requests can build up in Gitaly that are waiting their turn. Because
this is a potential vector for a memory leak, two other values in the `[[concurrency]]`
configuration can prevent an unbounded in-memory queue of requests:

- `max_queue_wait` is the maximum amount of time a request can wait in the
  concurrency queue. When a request waits longer than this time, it returns
  an error to the client.
- `max_queue_size` is the maximum size the concurrency queue can grow for a
  given RPC. If a concurrency queue is at its maximum, subsequent requests
  return with an error. The queue size is per repository.

For example:

```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
max_queue_wait = "1m"
max_queue_size = 5
```

func TestUnaryLimitHandler_queueing(t *testing.T) {
	t.Parallel()
	ctx := testhelper.Context(t)
	t.Run("simple timeout", func(t *testing.T) {
		cfg := config.Cfg{
			Concurrency: []config.Concurrency{
				{
					RPC: "/grpc.testing.TestService/UnaryCall",
					ConcurrencyLimits: config.ConcurrencyLimits{
						MaxPerRepo:   1,
						MaxQueueSize: 1,
						// This test setups two requests:
						// - The first one is eligible. It enters the handler and blocks the queue.
						// - The second request is blocked until timeout.
						// Both of them shares this timeout. Internally, the limiter creates a context
						// deadline to reject timed out requests. If it's set too low, there's a tiny
						// possibility that the context reaches the deadline when the limiter checks the
						// request. Thus, setting a reasonable timeout here and adding some retry
						// attempts below make the test stable.
						// Another approach is to implement a hooking mechanism that allows us to
						// override context deadline setup. However, that approach exposes the internal
						// implementation of the limiter. It also adds unnecessarily logics.
						// Congiuring the timeout is more straight-forward and close to the expected
						// behavior.
						MaxQueueWait: duration.Duration(100 * time.Millisecond),
					},
				},
			},
		}
		_, _, setupPerRPCConcurrencyLimiters := limithandler.WithConcurrencyLimiters(cfg)
		lh := limithandler.New(cfg, fixedLockKey, setupPerRPCConcurrencyLimiters)

		s := &queueTestServer{
			server: server{
				blockCh: make(chan struct{}),
			},
			reqArrivedCh: make(chan struct{}),
		}

		srv, serverSocketPath := runServer(t, s, grpc.UnaryInterceptor(lh.UnaryInterceptor()))
		defer srv.Stop()

		client, conn := newClient(t, serverSocketPath)
		defer conn.Close()

		// Spawn an RPC call that blocks so that the subsequent call will be put into the
		// request queue and wait for the request to arrive.
		var wg sync.WaitGroup
		wg.Add(1)
		go func() {
			defer wg.Done()
			// Retry a couple of time, just in case the test runs on a very slow machine that invalidates
			// the test. If the limiter still cannot permit the request after 3 times, something must go
			// wrong horribly.
			for i := 0; i < 3; i++ {
				if _, err := client.UnaryCall(ctx, &grpc_testing.SimpleRequest{}); err == nil {
					return
				}
			}
			require.FailNow(t, "the first request is supposed to enter the test server's handler")
		}()
		<-s.reqArrivedCh

		// Now we spawn a second RPC call. As the concurrency limit is satisfied we'll be
		// put into queue and will eventually return with an error.
		_, err := client.UnaryCall(ctx, &grpc_testing.SimpleRequest{})
		testhelper.RequireGrpcError(t, structerr.NewResourceExhausted("%w", limiter.ErrMaxQueueTime).WithDetail(
			&gitalypb.LimitError{
				ErrorMessage: "maximum time in concurrency queue reached",
				RetryAfter:   durationpb.New(0),
			},
		), err)

		// Unblock the concurrent RPC call and wait for the Goroutine to finish so that it
		// does not leak.
		close(s.blockCh)
		wg.Wait()
	})
