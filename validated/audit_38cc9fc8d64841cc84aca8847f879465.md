Audit Report

## Title
Idle-period rewards in `pallet-asset-rewards` are permanently discarded and become unrecoverable once a new staker joins - (File: substrate/frame/asset-rewards/src/lib.rs)

## Summary
`pallet-asset-rewards` computes reward accrual via `reward_per_token()`, which intentionally skips accruing `reward_per_token_stored` while `total_tokens_staked` is zero [1](#0-0) , but the paired `update_pool_rewards()` unconditionally advances `last_update_block` to the current block regardless of whether any stake existed during the elapsed window [2](#0-1) . This causes any reward emission notionally due during a zero-stake gap to be silently and permanently dropped once a new staker calls `stake()`.

## Finding Description
`update_pool_and_staker_rewards()` calls `reward_per_token()` then `update_pool_rewards()` together on every `stake()` and `unstake()` call [3](#0-2) . When `total_tokens_staked` is zero, `reward_per_token()` returns the unchanged stored value [4](#0-3) , but `update_pool_rewards()` still moves `last_update_block` forward to `now` [5](#0-4) . Consequently, when `total_tokens_staked` returns to non-zero on the next call, `rewardable_blocks_elapsed` is computed from the new (advanced) `last_update_block`, so blocks that elapsed during the zero-stake window are excluded from any future accrual — the reward budget for that window is never applied to `reward_per_token_stored` and can never be claimed via `harvest_rewards()`.

Because a staker's `PoolStakers` entry is only removed when both `amount` and `rewards` are zero [6](#0-5) , a full unstake by all participants can indeed empty `PoolStakers`, driving `total_tokens_staked` to zero. Any subsequent unprivileged call to `stake()` [7](#0-6)  re-populates `PoolStakers`, which permanently blocks the admin's only recovery mechanism, `cleanup_pool()`, since it requires `stakers.is_none()` [8](#0-7) . The reward tokens pre-funded into the pool account for that idle window thus remain stuck in the pool's account indefinitely, unattributable to any staker and unreclaimable by the admin.

## Impact Explanation
This matches the "permanent user-fund or bridge-state lock" impact category: reward-asset funds transferred into a pool's dedicated account become permanently unattributable and unrecoverable once a zero-stake gap is followed by any new stake, and `cleanup_pool` is simultaneously foreclosed. No privileged action is required to trigger the loss — it results from ordinary usage flow (full unstake followed by any restake).

## Likelihood Explanation
The trigger requires only two unprivileged, ordinary extrinsic calls — `unstake()` by all current stakers (reducing `total_tokens_staked` to zero) followed by any `stake()` call by any account. No malicious relayer, validator, governance, or privileged role is needed. Pools nearing expiry, low-TVL pools, or pools with coordinated/complete unstaking are realistically exposed to this condition, and the bug is deterministically reproducible.

## Recommendation
When `total_tokens_staked` is zero, `update_pool_rewards()` should not advance `last_update_block` past the point where staking last went to zero (preserving the un-emitted window so it applies once a staker returns), or the reward-rate calculation should explicitly exclude idle blocks from `rewardable_blocks_elapsed` rather than let `last_update_block` silently consume them. Additionally, `cleanup_pool` (or an equivalent sweep mechanism) should allow reclaiming reward-asset surplus not accounted for in `reward_per_token_stored`, even when `PoolStakers` is non-empty.

## Proof of Concept
1. `create_pool` with a fixed `reward_rate_per_block = R` and far-future `expiry_block`.
2. Fund the pool account via `deposit_reward_tokens` for `R * N` blocks worth of rewards.
3. Staker A calls `stake(pool_id, X)`, then `unstake(pool_id, X, None)` — `total_tokens_staked` becomes `0` and the `PoolStakers` entry is removed (assuming `rewards == 0`).
4. Advance the chain by `M` blocks with no calls to the pool.
5. Any account calls `stake(pool_id, Y)` — `reward_per_token()` returns the unchanged stored value, but `update_pool_rewards` still sets `last_update_block = now`, discarding `R * M` of reward emission.
6. Admin calls `cleanup_pool(pool_id)` — fails with `Error::NonEmptyPool` because the new staker's entry exists.
7. Result: `R * M` reward tokens remain stranded in the pool account, unclaimable via `harvest_rewards` and unreclaimable via `cleanup_pool`.
