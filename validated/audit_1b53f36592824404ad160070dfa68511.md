### Title
`AddressRegistrar::register` permanently keeps any deposit overpayment on successful registration instead of refunding the excess - ([File: runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs])

### Summary
The external report describes Solidity `payable` functions that mishandle attached protocol-fee value, causing users to overpay or fail transactions. The closest reachable analog in nearcore is the `#[payable]` `register` method of the eth-implicit-wallet ecosystem's `AddressRegistrar` contract, which accepts an `attached_deposit` to cover storage cost but only refunds it on the "collision" path — never refunds any excess over the exact required storage cost on the successful "insert" path.

### Finding Description
`AddressRegistrar::register` is a `#[payable]` method that computes an exact `required_deposit` for the storage bytes needed (`20 + account_id.len()`), and panics if `given_deposit < required_deposit`. [1](#0-0)  If the deposit is sufficient and the address slot is a collision (`Entry::Occupied`), the code explicitly refunds the entire `given_deposit` back to the predecessor via a transfer promise. [2](#0-1)  However, on the successful insertion path (`Entry::Vacant`), the code inserts the new mapping and returns the address string without any refund logic for the difference between `given_deposit` and `required_deposit`. [3](#0-2)  Any excess deposit attached beyond the exact storage cost is silently absorbed into the contract's account balance with no code path that returns it to the caller.

This function is reachable directly by any ordinary NEAR account issuing a `FunctionCall` action with a `deposit`, since `AddressRegistrar` is a normal deployed contract (not access-restricted), and is also reachable indirectly via the ETH-implicit Wallet Contract's relayer flow that looks up/updates address registrations. [4](#0-3) 

### Impact Explanation
Any caller (an unprivileged signer) who attaches more yoctoNEAR than the exact computed storage cost when calling `register` on a fresh address permanently loses the excess amount — it is neither returned nor recoverable through any other method exposed by the contract (`lookup`, `get_address` are both read-only). This constitutes a permanent freezing/loss of user funds, matching the accepted impact bar (permanent freezing of funds), analogous to the "wasted funds due to incorrect deposit handling" root cause identified in the source report, though the concrete mechanism here is a missing refund rather than a missing `payable` qualifier.

### Likelihood Explanation
Likelihood is moderate: any caller who does not compute the exact storage byte cost precisely (e.g., attaching a round/rough deposit, or a relayer/dApp integration that over-provisions the deposit for safety) will trigger the loss on every successful (non-colliding) registration call. There is no economic incentive for an attacker; this is primarily a self-inflicted-loss bug for ordinary users interacting with the eth-implicit account tooling, but it is trivially and repeatably triggerable.

### Recommendation
In the `Entry::Vacant` branch of `register`, compute the excess deposit (`given_deposit.saturating_sub(required_deposit)`) and refund it to `env::predecessor_account_id()` via a transfer promise, mirroring the refund logic already present in the `Entry::Occupied` branch.

### Proof of Concept
1. Deploy `AddressRegistrar` (as done in wallet-contract tests, e.g. `TestContext::new()` in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs`). [5](#0-4) 
2. Call `register(account_id)` with an `AccountId` not previously registered, attaching a deposit strictly greater than `storage_byte_cost() * (20 + account_id.len())`.
3. Observe: the call succeeds (`Entry::Vacant` path), the mapping is stored, and the full excess deposit remains on the `AddressRegistrar` contract's balance — no promise is created to return it to the caller, unlike the `Entry::Occupied` branch which explicitly issues `promise_batch_action_transfer(refund_promise, given_deposit)`. [6](#0-5)
