Based on the investigation, the strongest matching analog to the OneFlow `arange()` DoS (missing bound validation on a user-supplied "count/length" parameter leading to uncontrolled resource allocation) is in the TVM's batch-signature precompiled contract logic.

### Title
Unbounded array allocation from unchecked signature-count field in precompile signature array extraction causes node DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractSigArray()` reads a length value directly from attacker-controlled TVM precompile call data and immediately allocates a Java array of that size, with no upper bound check against the actual size of the supplied `data` buffer or any energy-based cap, mirroring the OneFlow `arange()` pattern where a crafted size argument drives unchecked allocation.

### Finding Description
`extractSigArray` takes the `len` field straight from the caller-supplied word array without validating it against `data.length` or any sane ceiling: [1](#0-0) 

`words[offset].intValueSafe()` can return values up to `Integer.MAX_VALUE` since `DataWord.intValueSafe()` only caps overflow to `Integer.MAX_VALUE`, it does not bound the value to anything related to the actual call-data size: [2](#0-1) 

Once `len` is attacker-controlled and unchecked, `new byte[len][]` attempts to allocate an object-reference array proportional to `len` (each element up to 8 bytes on 64-bit JVMs plus per-object overhead once populated in the loop), so a caller can request an allocation of gigabytes from a single 32-byte word in the call data. This is directly analogous to `flow.arange()` failing to validate a size argument before allocating memory. This code path is reached whenever any unprivileged account/contract calls the corresponding TVM precompiled contract (a batch-signature verification precompile) with crafted `data`, i.e. from a normal `TriggerSmartContract` transaction — no special privilege is required.

### Impact Explanation
A crafted `TriggerSmartContract` call into this precompile can force the node to attempt an extremely large heap allocation. This can throw an `OutOfMemoryError` in the transaction-execution thread; depending on JVM state this can degrade or crash the full node process, since `OutOfMemoryError` is unpredictable and not reliably caught/contained everywhere in the VM execution path (unlike the explicit `MEM_LIMIT`/`checkMemorySize` guard rails present for ordinary VM memory opcodes such as `CODECOPY`/`EXTCODECOPY`, see `EnergyCost.calcMemEnergy`/`checkMemorySize` at `actuator/src/main/java/org/tron/core/vm/EnergyCost.java:549-576`). This qualifies as a node crash/halt DoS reachable by any transaction broadcaster.

### Likelihood Explanation
High: reachable via a single unsigned-permission, unprivileged smart-contract call (`TriggerSmartContract`) that targets the fixed precompile address and supplies a single crafted 32-byte word as the "count" field — no special account state, stake, or witness/SR privileges are needed.

### Recommendation
Bound `len` in `extractSigArray` (and any other precompile that reads count/length fields from `DataWord`) to a value consistent with `data.length` (e.g., `len <= (data.length - expectedHeaderBytes) / expectedItemSize`) before allocating `bytesArray`, and reject with a normal precompile failure (`Pair.of(false, ...)`) instead of allocating. Apply the same MEM_LIMIT-style validation already used in `EnergyCost.checkMemorySize` to any array-size parameter taken from untrusted call data before allocation.

### Proof of Concept
1. Deploy or call an existing contract that invokes the batch-signature-verification precompile address with `TriggerSmartContract`.
2. Craft the `data` payload such that the count word at the expected offset (`words[offset]`) is set to a very large value (e.g., `0xFFFFFFFF`), while the rest of `data` is arbitrarily short.
3. Submit the transaction to a full node; `extractSigArray` executes `new byte[len][]` with `len` near `Integer.MAX_VALUE`, triggering a large allocation attempt and potential `OutOfMemoryError` in the node's execution thread.

Note: I was not able to fully trace, within the available tool budget, whether `OperationRegistry`/`VM.java`'s energy pre-check for this specific precompile computes and validates energy cost (`getEnergyForData`) using the same unbounded `len` before `execute()` is invoked, which would determine whether an energy-based revert occurs before or only after the allocation attempt. This should be confirmed by reviewing `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`'s enclosing precompile class (the one containing `extractSigArray`) and its `getEnergyForData` implementation.
