### Title
Unprivileged clients can set `git_object_directory`/`git_alternate_object_directories` on accessor RPCs to bypass Gitaly's transactional snapshot isolation - ([File: internal/gitaly/storage/storagemgr/middleware.go])

### Summary
Gitaly's `Repository` protobuf message exposes two fields, `git_object_directory` and `git_alternate_object_directories`, that are meant to be set only when Rails "loops back" a quarantine-configured request during access checks after a legitimate `pre-receive` quarantine has been established. However, nothing in the RPC/interceptor layer verifies that the caller who sets these fields actually went through that trusted round trip. Any accessor RPC request can carry these fields directly, and the transaction interceptor treats their mere presence as proof of a pre-established quarantine, causing it to skip the transaction manager entirely and hand the request straight to the RPC handler.

### Finding Description
The transaction interceptor's `beginTransactionForRepository` function decides whether to open a transaction for a `ScopeRepository` RPC based solely on whether `GetGitObjectDirectory()`/`GetGitAlternateObjectDirectories()` are non-empty on the target repository message: [1](#0-0) 

The code comment explicitly documents the unenforced invariant this relies on: object directories "should only be configured on a repository coming from a request that was already configured with a quarantine directory and is being looped back to Gitaly from Rails' authorization checks," and admits "this property is violated ... This allows for circumventing the transaction management by configuring either of the object directories." This is functionally identical to the Aave bug class: a security-relevant flag (`_useAsCollateral` there; "is this repository legitimately quarantined and already inside a transaction" here) is supposed to be set only as a side effect of a prior privileged/trusted step, but a downstream ordinary caller can set the flag directly on their own request and skip the check the flag was meant to gate.

When these fields are present on an **accessor** RPC, `beginTransactionForRepository` calls `restoreSnapshotRelativePath` and then `nonTransactionalRequest`, which returns a no-op `finishTransaction` and runs the handler directly, bypassing:
- Partition assignment and the `PartitionManager`'s repository validation (`locator.ValidateRepository`) that normally runs for transactional requests, seen a few lines below in the same function.
- Snapshot isolation guarantees described in `doc/transactions.md`, where "RPC handlers always operate on a snapshot of a repository, never the canonical repository." [2](#0-1) 

The companion `MetadataKeySnapshotRelativePath` header, used by `restoreSnapshotRelativePath` to recover the real relative path, is itself just gRPC metadata attached by the caller — an ordinary client sending an accessor RPC (e.g. `FindCommits`, `ObjectFormat`, `GetObjectDirectorySize`) can supply an arbitrary `relative_path` via this header together with a non-empty `git_object_directory`/`git_alternate_object_directories`, entirely outside of any real quarantine context. Existing tests corroborate that this path is reachable purely by shaping the request/metadata, without any actual quarantine directory existing on disk: [3](#0-2) 

### Impact Explanation
An unprivileged client that can reach Gitaly's gRPC accessor endpoints (e.g., through the standard GitLab-to-Gitaly RPC path, or any component/service forwarding requests with attacker-influenced repository fields) can force an accessor RPC to run non-transactionally against a caller-specified relative path plus a crafted object/alternate-object directory. This circumvents transactional/partition-based isolation guarantees the rest of the system relies on for repository access consistency, and can be combined with the object-directory path validation in `ObjectDirectoryPath` (which accepts any directory that resolves inside the repository tree, not only genuine quarantine paths) to read objects through directories the caller should not be able to designate on their own, all without ever having gone through Rails' legitimate quarantine handshake.

### Likelihood Explanation
The comment in the code acknowledges this is a known, currently-unaddressed weakness ("We'll leave this unaddressed for now"), and there is no server-side cryptographic or provenance check binding the `git_object_directory`/`git_alternate_object_directories`/snapshot-relative-path metadata to an actual, previously-established quarantine transaction. Any caller capable of crafting the RPC message fields and metadata (which are ordinary, non-privileged protobuf/gRPC constructs) can trigger the bypass, making this readily reachable from a normal RPC-issuing client.

### Recommendation
Do not infer "already inside a trusted quarantine transaction" purely from the presence of `git_object_directory`/`git_alternate_object_directories` on the incoming request. Instead, bind quarantine/snapshot state to a value that only Gitaly itself generates and can verify (e.g., a signed or server-tracked transaction/quarantine token), and reject accessor requests that present object-directory fields without a verifiable, matching quarantine transaction context. As the comment suggests, consider removing the ability to set object directories directly on the wire, moving that state into an internal-only linkage between the transaction and the request.

### Proof of Concept
1. As a normal RPC client, send any accessor RPC (e.g., `ObjectFormat`, `FindCommits`, `GetObjectDirectorySize`) whose `Repository` field sets `git_object_directory` (or `git_alternate_object_directories`) to a non-empty value, without having actually gone through the `pre-receive`/Rails quarantine flow.
2. Attach the `relative-path-bin` (`MetadataKeySnapshotRelativePath`) gRPC metadata header with an arbitrary relative path value of the caller's choosing.
3. Observe (as shown in `middleware_test.go`'s "does not start a transaction" cases) that the interceptor takes the `nonTransactionalRequest` path and invokes the handler directly with the caller-supplied `RelativePath` and object directory fields, bypassing partition validation and transactional snapshot isolation entirely.
