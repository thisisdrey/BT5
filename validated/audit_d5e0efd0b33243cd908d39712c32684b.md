### Title
Unbounded half-open QUIC connection slot exhaustion via stalled handshakes bypasses pre-handshake rate limiting - ([File: streamer/src/nonblocking/quic.rs])

### Summary
`run_server` allocates a `ClientConnectionTracker` slot (bounded by `qos.max_concurrent_connections()`) for every incoming QUIC `Initial` packet *before* the handshake completes, while the only rate-limiting checks performed at that point (`overall_connection_rate_limiter.current_tokens() == 0` and `rate_limiter.is_allowed(ip)`) are non-mutating peeks that never debit tokens. Actual token consumption (`rate_limiter.register_connection`, `overall_connection_rate_limiter.consume_tokens`) only happens in `setup_connection` after a successful handshake, so an attacker who never completes the handshake can occupy connection slots essentially for free, repeatedly, exhausting the shared global connection budget before either limiter ever triggers.

### Finding Description
In `run_server` (`streamer/src/nonblocking/quic.rs:331-379`), for every accepted `Incoming`, the code:
1. Peeks `overall_connection_rate_limiter.current_tokens() == 0` [1](#0-0) 
2. Peeks `rate_limiter.is_allowed(&ip)` [2](#0-1) 
3. Then calls `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())`, which increments the global `open_connections` counter and errors out (refusing the connection) only once that global limit is hit [3](#0-2) , [4](#0-3) 

Crucially, `ConnectionRateLimiter::is_allowed` is documented and implemented as a **non-mutating** check ("just checking should not mutate state") that only reads `current_tokens`; it does not consume any token budget [5](#0-4) . The actual token debit (`register_connection` → `consume_tokens`) and the overall limiter's `consume_tokens(1)` only happen in `setup_connection` *after* the QUIC handshake resolves successfully [6](#0-5) .

The handshake itself is bounded by `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` = 2 seconds [7](#0-6) , enforced via `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting).await` in `setup_connection` [8](#0-7) . So a stalled/never-completed handshake only holds a `ClientConnectionTracker` slot for up to 2 seconds before `Drop` releases it [9](#0-8) , but this window is sufficient: because neither the overall nor per-IP limiter is debited by incomplete handshakes, the attacker faces **no throttling penalty** for repeatedly opening new half-open connections (even from a single unconfirmed source IP), and can therefore continuously refill slot occupancy above `qos.max_concurrent_connections()` by sustaining a submission rate of roughly `max_concurrent_connections / QUIC_CONNECTION_HANDSHAKE_TIMEOUT` stalled Initial packets per second — a trivially low, unauthenticated cost since crafting a QUIC Initial packet requires no stake or prior state.

Once the slot budget is saturated, legitimate connection attempts (staked or unstaked — the tracker limit is shared and checked before peer type is even known, since `qos.build_connection_context` only runs after handshake success at line 512) are refused via `refused_connections_too_many_open_connections` [3](#0-2) .

### Impact Explanation
This is a QoS/BOUNDED_RESOURCES-violation-class TPU denial-of-service: an unstaked, unprivileged remote attacker can starve the leader's public TPU QUIC handshake slots, causing legitimate senders (including staked validators/RPC forwarders) to be refused with `refused_connections_too_many_open_connections`, degrading transaction ingestion for the entire cluster during the affected leader slot(s). This matches the scoped impact stated in the question: "TPU handshake-slot starvation denying legitimate connections."

### Likelihood Explanation
Feasible and repeatable with only unprivileged UDP access to the public TPU QUIC port: the attacker needs no stake, no valid TLS completion, and no IP diversity (since per-IP limiting is bypassed pre-handshake). The only per-attempt cost is sending a QUIC Initial packet; sustaining a modest rate below `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` expiry (2s) is trivial via simple socket scripting, requiring no IP spoofing.

### Recommendation
Debit (or at least reserve) rate-limiter tokens (both per-IP and overall) at the time the `ClientConnectionTracker` slot is granted (pre-handshake), not only after successful handshake completion; alternatively, apply a separate, tightly-bounded per-IP concurrent "pending handshake" slot cap independent of the confirmed-connection tables, so a single unconfirmed source cannot occupy an unbounded share of `qos.max_concurrent_connections()`.

### Proof of Concept
Integration test plan (extending existing `streamer/src/quic.rs` test harness, e.g. `setup_swqos_quic_server`):
1. Configure server with a small `max_concurrent_connections` (e.g., via `SwQosConfig::max_staked_connections`/`max_unstaked_connections` yielding a small `qos.max_concurrent_connections()`).
2. Spawn N attacker tasks that open raw UDP sockets to the server's QUIC port and send a single valid-looking QUIC Initial packet each (or use a quinn `Endpoint::connect` future that is dropped/never polled to completion before ACKing Finished), at a rate exceeding `max_concurrent_connections / QUIC_CONNECTION_HANDSHAKE_TIMEOUT`, and never advance the handshake.
3. Concurrently, attempt a legitimate `make_client_endpoint(&server_address, ...)` full handshake from a "legitimate" client.
4. Assert that `stats.refused_connections_too_many_open_connections` increments for the legitimate client's attempt, or that `stats.open_connections` reaches `max_concurrent_connections` sustained over multiple 2-second timeout windows purely from attacker traffic, and that `stats.connection_rate_limited_across_all` / `connection_rate_limited_per_ipaddr` remain at 0 (proving the limiters were never debited) while legitimate handshake success rate drops to 0.
