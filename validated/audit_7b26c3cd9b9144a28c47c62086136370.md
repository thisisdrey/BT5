### Title
Malicious ShieldedTRC20 contract deployer can spoof `scalingFactor()` per-call to desynchronize shielded note values from real TRC20 transfer amounts - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.checkPublicAmount` performs an external constant call to an attacker-controllable contract's `scalingFactor()` function and trusts the raw return value to convert a user-supplied `fromAmount`/`toAmount` into the internal `scaledFromAmount`/`scaledToAmount` used to build the zk-SNARK note commitments for shielded mint/burn operations. This mirrors the reported bug class: an external, attacker-deployed contract's numeric parameter is queried live and fed directly into a fund-affecting calculation with no consistency check across calls.

### Finding Description
`createShieldedContractParameters` (and its `WithoutAsk` sibling), reachable via the gRPC/HTTP Wallet API used to build shielded-TRC20 mint/transfer/burn transaction parameters, calls: [1](#0-0) 

which invokes `checkPublicAmount`: [2](#0-1) 

`checkPublicAmount` retrieves the scaling factor via a live TVM constant call to the *attacker-supplied contract address*: [3](#0-2) 

`getShieldedContractScalingFactor` executes a `TriggerSmartContract` constant call against `scalingFactor()` on `contractAddress`, which is fully controlled by whoever deployed the shielded contract (`shieldedTRC20ContractAddress` is a caller-supplied field of `PrivateShieldedTRC20Parameters`/`PrivateShieldedTRC20ParametersWithoutAsk`). Nothing in `checkPublicAmount` or its caller pins the scaling factor to a value fixed at deployment time, cross-checks it against a value used in a prior call, or otherwise prevents the contract's `scalingFactor()` implementation from returning different values on different invocations (e.g., based on `msg.sender`, call count, or arbitrary contract state the deployer controls).

The unscaled `fromAmount`/`toAmount` supplied by the RPC caller is divided by this externally-supplied `scalingFactor` to produce `scaledFromAmount`/`scaledToAmount`, which then become the shielded note `value` fields used to build the mint/burn zk-proof and the trigger-contract input (`mintParamsToHexString`, `burnParamsToHexString`, etc.) — i.e., the value that is cryptographically committed into the shielded pool's Merkle tree and later spendable via burn: [4](#0-3) 

Because the scaling factor is re-queried from the deployer-controlled contract on every call to `createShieldedContractParameters` (mint) and independently on every burn, a malicious deployer can implement `scalingFactor()` to return a small value when a victim mints (so `scaledFromAmount = fromAmount/scalingFactor` is inflated relative to the TRC20 amount actually collected by the contract's `mint` logic) and a different value when funds are later withdrawn via burn, desynchronizing the shielded note accounting from the contract's real token balance/allocation logic — the same "attacker-controlled external numeric parameter queried per-call and trusted without pinning" pattern as the Sherlock report's `payoutToken.decimals()` issue.

### Impact Explanation
If exploited, notes minted under a manipulated (small) scaling factor could represent shielded value inconsistent with the TRC20 tokens the contract actually escrowed, and subsequent burns computed under a different (also manipulated) scaling factor could let the deployer extract more TRC20 tokens than were ever deposited for that shielded balance, or credit other users' notes with amounts that don't correspond to real backing. This is a fund-accounting integrity issue inside the java-tron node's trusted shielded-TRC20 parameter-building path (exposed over gRPC/HTTP `Wallet` API), which other users of the same shielded pool rely on to correctly represent value — analogous to the drained collateral pool in the original report.

### Likelihood Explanation
Exploitation only requires deploying a shielded TRC20 contract with a malicious `scalingFactor()` implementation and inducing victims (or the attacker's own sequence of calls) to interact with it through the standard `createShieldedContractParameters`/`getTriggerInputForShieldedTRC20Contract` RPC flow — no special privileges, consensus role, or node compromise needed. This is reachable purely as an API client / contract deployer, matching the allowed threat model.

### Recommendation
Do not trust a live, re-queryable `scalingFactor()` value across independent calls without pinning. Cache the scaling factor once (e.g., at first use per contract address, or read via a fixed immutable field/constant lookup) and validate it is consistent across mint/transfer/burn parameter-building calls for the same shielded contract instance; alternatively, require the scaling factor to be supplied by the RPC caller and independently verified once against the contract's immutable bytecode/state rather than freshly executed via TVM call on every invocation.

### Proof of Concept
1. Deploy a `ShieldedTRC20`-compatible contract whose `scalingFactor()` view function returns `1` on the Nth call and `1000000` on the (N+1)th call (e.g., toggling based on an internal counter incremented on every call, which the attacker fully controls since it is their own contract).
2. Call `Wallet.createShieldedContractParameters` (via gRPC) to mint shielded notes with a small `fromAmount`; because `scalingFactor()` returns `1` at this point, `scaledFromAmount = fromAmount` is computed at full value in `checkPublicAmount` (`framework/src/main/java/org/tron/core/Wallet.java:4223-4254`), producing a shielded note with inflated value relative to what the contract's own `mint()` TVM logic actually escrows for that `fromAmount`.
3. Later, call `createShieldedContractParameters` for a `burn` with a `toAmount` chosen so that, with `scalingFactor()` now returning `1000000`, `scaledToAmount` matches the previously over-inflated note value, allowing the attacker to redeem more TRC20 tokens than were ever deposited to back that note.

  private long[] checkPublicAmount(byte[] address, BigInteger fromAmount, BigInteger toAmount)
      throws ContractExeException, ContractValidateException {
    checkBigIntegerRange(fromAmount);
    checkBigIntegerRange(toAmount);

    BigInteger scalingFactor;
    try {
      byte[] scalingFactorBytes = getShieldedContractScalingFactor(address);
      scalingFactor = ByteUtil.bytesToBigInteger(scalingFactorBytes);
    } catch (ContractExeException e) {
      throw new ContractExeException("Get shielded contract scalingFactor failed");
    }
    if (scalingFactor.compareTo(BigInteger.ZERO) <= 0) {
      throw new ContractValidateException("scalingFactor must be positive");
    }

    // fromAmount and toAmount must be a multiple of scalingFactor
    if (!(fromAmount.mod(scalingFactor).equals(BigInteger.ZERO)
        && toAmount.mod(scalingFactor).equals(BigInteger.ZERO))) {
      throw new ContractValidateException("fromAmount or toAmount invalid");
    }

    long[] ret = new long[2];
    try {
      ret[0] = fromAmount.divide(scalingFactor).longValueExact();
      ret[1] = toAmount.divide(scalingFactor).longValueExact();
    } catch (ArithmeticException e) {
      throw new ContractValidateException("fromAmount or toAmount invalid");
    }

    return ret;
  }

  public byte[] getShieldedContractScalingFactor(byte[] contractAddress)
      throws ContractExeException {
    String methodSign = "scalingFactor()";
    byte[] selector = new byte[4];
    System.arraycopy(Hash.sha3(methodSign.getBytes()), 0, selector, 0, 4);

    TriggerSmartContract.Builder triggerBuilder = TriggerSmartContract.newBuilder();
    triggerBuilder.setContractAddress(ByteString.copyFrom(contractAddress));
    triggerBuilder.setData(ByteString.copyFrom(selector));
    TriggerSmartContract trigger = triggerBuilder.build();

    TransactionExtention.Builder trxExtBuilder = TransactionExtention.newBuilder();
    Return.Builder retBuilder = Return.newBuilder();
    TransactionExtention trxExt;

    try {
      TransactionCapsule trxCap = createTransactionCapsule(trigger,
          ContractType.TriggerSmartContract);
      Transaction trx = triggerConstantContract(trigger, trxCap, trxExtBuilder, retBuilder);

      retBuilder.setResult(true).setCode(response_code.SUCCESS);
      trxExtBuilder.setTransaction(trx);
      trxExtBuilder.setTxid(trxCap.getTransactionId().getByteString());
      trxExtBuilder.setResult(retBuilder);
    } catch (ContractValidateException | VMIllegalException e) {
      retBuilder.setResult(false).setCode(response_code.CONTRACT_VALIDATE_ERROR)
          .setMessage(ByteString.copyFromUtf8(CONTRACT_VALIDATE_ERROR + e.getMessage()));
      trxExtBuilder.setResult(retBuilder);
      logger.warn(CONTRACT_VALIDATE_EXCEPTION, e.getMessage());
    } catch (RuntimeException e) {
      retBuilder.setResult(false).setCode(response_code.CONTRACT_EXE_ERROR)
          .setMessage(ByteString.copyFromUtf8(e.getClass() + " : " + e.getMessage()));
      trxExtBuilder.setResult(retBuilder);
      logger.warn("When run constant call in VM, failed for reason: " + e.getMessage());
    } catch (Exception e) {
      retBuilder.setResult(false).setCode(response_code.OTHER_ERROR)
          .setMessage(ByteString.copyFromUtf8(e.getClass() + " : " + e.getMessage()));
      trxExtBuilder.setResult(retBuilder);
      logger.warn("Unknown exception caught: " + e.getMessage(), e);
    } finally {
      trxExt = trxExtBuilder.build();
    }

    String code = trxExt.getResult().getCode().toString();
    if ("SUCCESS".equals(code)) {
      List<ByteString> list = trxExt.getConstantResultList();
      byte[] listBytes = new byte[0];
      for (ByteString bs : list) {
        listBytes = ByteUtil.merge(listBytes, bs.toByteArray());
      }
      return listBytes;
    } else {
      throw new ContractExeException("trigger contract to get scaling factor error.");
    }
  }
