### Title
Missing zero-address check on `new_authority` in `transfer_to_new_account` / `transfer_to_new_account_pda` permanently freezes migrated account funds - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
The reported Nouns Builder bug class is: an unprivileged user can set an ownership/delegation field to `address(0)`, which has no controlling key, permanently burning/losing the associated value. In marginfi-v2, the account-authority migration instructions accept a completely unchecked `new_authority` account and never reject `Pubkey::default()` (Solana's zero-address analog), allowing a user to permanently freeze their own migrated marginfi account and all the collateral/debt positions it holds.

### Finding Description
`transfer_to_new_account` and `transfer_to_new_account_pda` let the current account authority migrate all lending positions from an `old_marginfi_account` to a brand-new `new_marginfi_account`, setting its authority to an arbitrary `new_authority` pubkey supplied by the caller [1](#0-0) . The `new_authority` account is explicitly documented as unchecked: [2](#0-1) 

The same unchecked pattern exists for the PDA variant [3](#0-2) .

`initialize_migrated_account` copies the old account's full `lending_account` (all deposit/borrow balances), `emissions_destination_account`, and flags into the new account and sets its `authority` field to whatever `new_authority` was passed, with no validation against `Pubkey::default()` [4](#0-3) . The old account is then irreversibly disabled and marked as migrated [5](#0-4) , and repeated migration of the same source account is blocked [6](#0-5) .

By contrast, the off-chain CLI helper does perform this check client-side (`if new_authority == Pubkey::default() { bail!(...) }`) [7](#0-6) , but this is not enforced on-chain, so any direct instruction call (bypassing the CLI) or a malicious/careless integrator can still set `new_authority = Pubkey::default()`.

This is the direct analog of the reported bug: just as delegating to `address(0)` in `ERC721Votes._delegate` permanently loses/misallocates voting power because no one controls `address(0)`, migrating a marginfi account's authority to `Pubkey::default()` permanently locks the new account (and all its lending positions) because no private key exists for the default pubkey and no signer can ever be produced for it.

### Impact Explanation
If a user (or any integrator building on top of `transfer_to_new_account`/`transfer_to_new_account_pda`) sets `new_authority = Pubkey::default()`, the following happens:
- The old account is disabled and marked migrated, with `migrated_to` pointing at the new account — this step is irreversible (`AccountAlreadyMigrated` blocks retry) [8](#0-7) .
- The new account, holding all the migrated `lending_account` balances (deposits and borrows), now has `authority = Pubkey::default()`.
- Since no wallet can ever sign as `Pubkey::default()`, no subsequent instruction requiring the account authority's signature (withdraw, repay, close, re-migrate, etc.) can ever be executed against the new account.

This results in permanent lock/freeze of all collateral and outstanding positions in the migrated account — funds become permanently inaccessible, which is a valid impact category (permanent lock/freeze) under the given rules.

### Likelihood Explanation
The action is entirely user-triggered and requires no admin or validator privilege — the account authority (an ordinary user) simply supplies `Pubkey::default()` as `new_authority` when calling `transfer_to_new_account`/`transfer_to_new_account_pda`. This can happen from a client-side bug (e.g., an uninitialized/never-set `new_authority` variable defaulting to the zero pubkey), a UI defect, or a malicious integrator's misuse. The presence of an explicit client-side guard against this exact input in `p0-cli` [7](#0-6)  indicates the marginfi team is already aware zero-address `new_authority` is a foreseeable failure mode, but the protection is missing from the on-chain instruction itself, so any caller that doesn't go through that specific CLI path is unprotected.

### Recommendation
Add an on-chain check in both `transfer_to_new_account` and `transfer_to_new_account_pda` (in `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`) that rejects `new_authority == Pubkey::default()` before finalizing the migration, mirroring the existing client-side check in `p0-cli/src/processor/account.rs`. This prevents an irrecoverable freeze of migrated lending positions.

### Proof of Concept
1. User creates a `MarginfiAccount` and deposits/borrows against one or more banks.
2. User (or an integrator on their behalf) calls `transfer_to_new_account` with `new_authority = Pubkey::default()`, `old_marginfi_account` = their existing account, and a fresh `new_marginfi_account` keypair.
3. `initialize_migrated_account` sets `new_account.authority = Pubkey::default()` while copying over the full `lending_account` state [9](#0-8) .
4. `finalize_migrated_old_account` disables the old account and marks it migrated, so it can never be used or re-migrated again [5](#0-4) .
5. Any subsequent instruction targeting the new account (withdraw, repay, re-migrate, close) requires a signature from `authority` = `Pubkey::default()`, which is unattainable — the account and its assets are permanently frozen.

fn finalize_migrated_old_account(
    old_account: &mut MarginfiAccount,
    new_account_key: Pubkey,
    current_timestamp: u64,
) {
    old_account.migrated_to = new_account_key;
    old_account.last_update = current_timestamp;
    old_account.lending_account = LendingAccount::zeroed();
    old_account.set_flag(ACCOUNT_DISABLED, true);
    old_account.sync_indexer_flags();
}
