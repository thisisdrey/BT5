## Title
Unauthenticated `/shutdown` HTTP request permanently terminates the signer's event receiver - ([File: libsigner/src/events.rs])

### Summary
`SignerEventReceiver::next_event` handles the `/shutdown` URL by unconditionally setting `stop_signal` to `true` and returning `EventError::Terminated`, with no authentication, secret, or origin check of any kind. Any TCP client able to reach the bound event-receiver socket can send a raw `POST /shutdown HTTP/1.1` request and permanently stop the signer's event loop.

### Finding Description
The intended invariant is that only the node process (or the signer's own internal `SignerStopSignaler::send`) can trigger a shutdown of the event receiver, since `SignerStopSignaler::send` [1](#0-0)  constructs and sends the exact same unauthenticated `POST /shutdown` request that any external client could send. In `next_event`, the dispatch logic checks `request.url() == "/shutdown"` and immediately does:
```
event_receiver.stop_signal.store(true, Ordering::SeqCst);
Err(EventError::Terminated)
``` [2](#0-1) 
There is no verification of a shared secret, signature, peer identity, or any other credential before this branch executes — unlike `process_event` for other event types, which at least requires a JSON body deserializable into a known event type, the `/shutdown` path requires nothing but the correct HTTP method and URL string. Once `stop_signal` is `true`, `is_stopped()` returns `true` [3](#0-2) , causing `main_loop` to break out of its loop on the very next iteration [4](#0-3) , and `next_event` returns `Err(EventError::Terminated)` even before reaching `http_server.recv()` [5](#0-4) . There is no reset path — once fired, the signer's event stream is permanently dead until process restart.

### Impact Explanation
Any remote client that can open a TCP connection to the signer's event-receiver bound address can send a single crafted `POST /shutdown` HTTP request and permanently stop the signer from receiving further node-forwarded events (`/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block`, `/status`). This is a one-message, repeatable, unauthenticated denial of service against a core signer subsystem, matching the "Critical — remote crash/unauthenticated DoS from few messages" category. Whether this is remotely exploitable by the threat model in scope depends entirely on whether the event-receiver socket is bound to a loopback address only or to a network-reachable interface.

### Likelihood Explanation
Exploitability hinges on network reachability of the event-receiver bind address, which is operator/config-controlled (`stacks-signer` config sets the endpoint the node event-observer POSTs to, and the signer binds an `HttpServer` to that same address). I was not able to fully confirm from the indexed code whether this endpoint defaults to or is commonly configured to a non-loopback address in this repo's config handling (my `stacks-signer/src/config.rs` search did not return readable snippets due to index limits). If the endpoint is bound to `127.0.0.1` (loopback-only, as is typical for node-to-signer event forwarding), this is not remotely reachable by an unprivileged external attacker and would be out of scope per the threat model (no privileged/local access). If it is bound to `0.0.0.0` or a routable interface, the attack is trivially reachable, cheap (one raw HTTP POST, no crypto or slot ownership needed), and fully repeatable.

### Recommendation
Require some form of authentication for the `/shutdown` endpoint — e.g., restrict the shutdown trigger to an internal-only mechanism (in-process channel/shared `Arc<AtomicBool>` call from `SignerStopSignaler::send` without going over the network), or require a shared secret/token in the request that only the node/signer process knows, rather than trusting the bare URL path over an unauthenticated HTTP request.

### Proof of Concept
```rust
// libsigner/src/events.rs (test module) or a separate integration test
use std::net::{TcpListener, TcpStream};
use std::io::Write;
use libsigner::events::{SignerEventReceiver, EventReceiver};

#[test]
fn test_unauthenticated_shutdown() {
    let mut receiver: SignerEventReceiver<SomeSignerMessageType> = SignerEventReceiver::new(false);
    let addr = "127.0.0.1:0".parse().unwrap();
    let bound = receiver.bind(addr).unwrap();

    // Attacker: no credentials, just a raw TCP connection to the bound address
    let mut stream = TcpStream::connect(bound).unwrap();
    let body = "attacker-controlled";
    let req = format!(
        "POST /shutdown HTTP/1.1\r\nHost: {}\r\nConnection: close\r\nContent-Length: {}\r\n\r\n{}",
        bound, body.len(), body
    );
    stream.write_all(req.as_bytes()).unwrap();

    // Drive one iteration of next_event to process the request
    let _ = receiver.next_event(); // returns Err(EventError::Terminated)

    assert!(receiver.is_stopped()); // stop_signal now permanently true
    // Any subsequent legitimate node event POSTs will be dropped because
    // next_event() short-circuits with EventError::Terminated at the top,
    // never reaching http_server.recv().
}
```

**Caveat:** This finding is valid for the code path itself — the `/shutdown` branch performs no authentication check whatsoever, mirroring exactly the request format used by the legitimate `SignerStopSignaler::send`. However, whether it constitutes an in-scope, remotely-reachable Critical vulnerability under this task's threat model depends on the event-receiver's bind address configuration, which I could not fully verify from the available indexed contents of `stacks-signer/src/config.rs` due to index limits. If this endpoint is loopback-only by design/default, the finding would be out of scope (requires local access); if it can be bound to a network-reachable interface, the finding is valid as Critical. I recommend starting a full Devin session to inspect `stacks-signer/src/config.rs` and the node's event-observer configuration to confirm the actual bind/connect address used in deployments before treating this as conclusively in-scope.
