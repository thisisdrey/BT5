### Title
Arbitrary object pool linking allows cross-repository object disclosure via `LinkRepositoryToObjectPool` - (File: internal/gitaly/service/objectpool/link.go)

### Summary
`LinkRepositoryToObjectPool` links a caller-controlled `Repository` (the `target_repository`) to a caller-supplied `ObjectPool` (the `additional_repository`) by writing the pool's path into the repository's `objects/info/alternates` file. The only validation performed on the supplied pool is that it is a structurally valid pool directory — there is no check that the pool actually "belongs" to the target repository or that the caller has any pre-existing relationship to it. This mirrors the ERC721 bug pattern: the function validates the *state* of the referenced resource (is it a legitimate pool?) but not the *authorization relationship* between the caller/target and that resource (should this particular repository be allowed to read this particular pool's objects?).

### Finding Description
`LinkRepositoryToObjectPool` resolves the `object_pool` field purely via `poolForRequest` → `objectpool.FromProto`, which only checks:
1. That the path resolves to a repository (`locator.GetRepoPath`), and
2. That it satisfies `storage.IsPoolRepository` (a naming/location convention check) or lives in the storage's temp dir, and
3. That `pool.IsValid(ctx)` succeeds (a structural git-validity check). [1](#0-0) [2](#0-1) 

None of these checks verify that the pool was actually created from, or is otherwise associated with, the target repository being linked. The RPC handler itself performs no additional authorization tying `repository` and `object_pool` together: [3](#0-2) 

The underlying `Link` function then unconditionally writes the resolved pool's object directory into the repository's alternates file (after only checking whether an alternates file already exists, to avoid clobbering unrelated content): [4](#0-3) 

Once linked, `git` will consult the pool's object store as an alternate for every read against the member repository, meaning **all objects present in the foreign pool become readable through the linked repository** (e.g. via clone/fetch of the member repo). This is analogous to `supplyERC721FromNToken`, which validated only that the ERC721 asset was owned by the `NToken` contract (a state check) but never verified that the caller/`onBehalfOf` address was actually entitled to claim that specific asset — allowing an unrelated party to attach themselves to assets they didn't put there.

The proto annotations confirm the field roles: `object_pool` is marked `additional_repository` and `repository` is the `target_repository`, and access-control enforcement for gRPC calls in GitLab's model is expected to be driven by permission checks against the repositories referenced in the request — but Gitaly itself performs no relationship check between the two repositories here, only structural validity of the pool: [5](#0-4) 

### Impact Explanation
Any actor capable of invoking `LinkRepositoryToObjectPool` for a repository they control (e.g., a project they can push/administer) can point that repository's alternates at any other object pool on the same storage, as long as they know or can guess its relative path (pool paths follow a predictable, hashed-but-discoverable convention under `@pools/`). Successfully linking grants the attacker's repository — and thus the attacker via a subsequent clone/fetch — read access to every object contained in the victim pool, i.e., cross-repository object disclosure of potentially private commits/blobs/trees that were never intended to be shared with the attacker's project. This is a confidentiality break across repository/project boundaries.

### Likelihood Explanation
Exploitability depends on the attacker being able to name or discover the relative path of another, unrelated object pool on the same Gitaly storage (pool directories are deterministically placed, e.g., under `@pools/<hash>`), and on the higher-level GitLab authorization layer failing to gate this specific action beyond ordinary repository-mutator permission checks. Within Gitaly itself, there is no defense-in-depth check verifying the pool-to-repository relationship, so if the authorization boundary above Gitaly does not independently verify that the caller has legitimate access to the *pool's* origin project, the attack succeeds. This makes likelihood dependent on external access-control layers rather than any check in Gitaly, which is itself the weakness being reported (lack of defense-in-depth analogous to the ERC721 report's recommendation for additional access controls).

### Recommendation
Add a Gitaly-side check in `LinkRepositoryToObjectPool` (and `objectpool.Link`) that verifies the target repository has a legitimate association with the requested pool before writing the alternates file — for example, requiring that the pool was created from (or previously provably related to) the target repository, or requiring an explicit, auditable metadata record binding pools to their permitted member repositories, rather than relying solely on path-naming validity (`IsPoolRepository`) and structural validity (`IsValid`). This mirrors the ERC721 report's long-term recommendation to add access controls and track legitimate ownership rather than trusting only positional/state validation.

### Proof of Concept
1. Attacker controls `repoA` (any repository they can call repository-mutator RPCs against).
2. Attacker discovers or guesses the relative path of `poolB`, an object pool created from a private, unrelated `repoB` (pool paths are deterministic under the storage's `@pools/` hashing scheme).
3. Attacker calls:
```
LinkRepositoryToObjectPool(
  Repository:  repoA,
  ObjectPool:  { Repository: { StorageName: <same storage>, RelativePath: <poolB path> } }
)
```
4. `poolForRequest`/`objectpool.FromProto` accepts `poolB` because it passes `IsPoolRepository` and `IsValid` checks, without any tie to `repoA`. [6](#0-5) 
5. `pool.Link(ctx, repoA)` writes `poolB`'s object directory into `repoA/objects/info/alternates`. [4](#0-3) 
6. Attacker clones/fetches `repoA`; Git transparently resolves objects via the alternate, exposing `repoB`'s (and other pool members') objects to the attacker.

func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil

// FromProto returns an object pool object from its Protobuf representation. This function verifies
// that the object pool exists and is a valid pool repository.
func FromProto(
	ctx context.Context,
	logger log.Logger,
	locator storage.Locator,
	gitCmdFactory gitcmd.CommandFactory,
	catfileCache catfile.Cache,
	txManager transaction.Manager,
	housekeepingManager housekeepingmgr.Manager,
	proto *gitalypb.ObjectPool,
) (*ObjectPool, error) {
	poolPath, err := locator.GetRepoPath(ctx, proto.GetRepository(), storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, err
	}

	if !storage.IsPoolRepository(proto.GetRepository()) {
		// When creating repositories in the ObjectPool service we will first create the
		// repository in a temporary directory. So we need to check whether the path we see
		// here is in such a temporary directory and let it pass.
		tempDir, err := locator.TempDir(proto.GetRepository().GetStorageName())
		if err != nil {
			return nil, fmt.Errorf("getting temporary storage directory: %w", err)
		}

		if !strings.HasPrefix(poolPath, tempDir) {
			return nil, ErrInvalidPoolDir
		}
	}

	pool := &ObjectPool{
		Repo:                localrepo.New(logger, locator, gitCmdFactory, catfileCache, proto.GetRepository()),
		logger:              logger,
		locator:             locator,
		gitCmdFactory:       gitCmdFactory,
		txManager:           txManager,
		housekeepingManager: housekeepingManager,
	}

	if !pool.IsValid(ctx) {
		return nil, ErrInvalidPoolRepository
	}

	return pool, nil
}

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}

// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}
