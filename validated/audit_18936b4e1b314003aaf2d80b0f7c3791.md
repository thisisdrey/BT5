Audit Report

## Title
Permissionless asset creator can freeze an AMM pool account in `pallet-asset-conversion`, permanently locking LP funds - (File: `substrate/frame/asset-conversion/src/lib.rs`)

## Summary
`pallet-asset-conversion::do_create_pool` accepts any `T::AssetKind` into a pool without checking who controls the freezer/admin role of that asset. Since `pallet-assets::create` is a public dispatchable where the caller becomes `owner`/`issuer`/`admin`/`freezer` of the newly created asset, an attacker can create a token, pool it against a valuable asset, wait for a victim LP to deposit, then call `pallet-assets::freeze` on the pool account to permanently block withdrawal of both sides of the pool.

## Finding Description
`Pallet::create` in `substrate/frame/assets/src/lib.rs` assigns `owner`/`issuer`/`admin`/`freezer` all to the calling account, confirmed at lines 863-879 where `AssetDetails { owner, issuer, admin: admin.clone(), freezer: admin.clone(), ... }` is inserted with no restriction on who `admin` can be.

`do_create_pool` (`substrate/frame/asset-conversion/src/lib.rs`, lines 729-788) creates a pool for arbitrary `asset1`/`asset2` of `T::AssetKind` and calls `T::Assets::touch` to establish an `Account` entry for the pool account for both assets (lines 753-759), with no check on the freezer/admin role of either asset.

The `freeze` extrinsic (`substrate/frame/assets/src/lib.rs`, lines 1192-1217) only requires `origin == d.freezer` — confirmed in the code I read — and sets the target account's `status` to `AccountStatus::Frozen`. Since the attacker is `freezer` of their own created asset, they can freeze the pool account once it has a live `Account` entry (created via `touch` during `do_create_pool`/`do_add_liquidity`).

Any subsequent `T::Assets::transfer(asset, &pool_account, ...)` — used in `do_remove_liquidity` at lines 951-952 and in swap paths — is checked by `can_decrease` in `substrate/frame/assets/src/functions.rs`. I confirmed at lines 190-192 that `details.status == AssetStatus::Frozen` returns `Frozen`, and separately at lines 203-205 that `account.status.is_frozen()` also returns `Frozen`. `reducible_balance` (lines 247-256) applies the same account-level frozen check. Both paths reject the withdrawal deterministically before any transfer executes.

`thaw` (`substrate/frame/assets/src/lib.rs`, lines 1230-1251) requires `origin == details.admin` — confirmed in the code read — and the attacker is also the `admin`, so only the attacker can reverse the freeze.

I was unable to fully verify within the given iterations whether `asset-hub-rococo`'s `pallet_asset_conversion::Config` restricts `AssetKind` to a curated enum (e.g., `NativeOrWithId`) that might implicitly limit which assets can be paired, since the grep for `impl pallet_asset_conversion::Config for Runtime` and `type AssetKind` in that runtime returned matches but I did not get to read their content before the iteration limit. However, the core pallet logic in `pallet-asset-conversion` itself — which is the scope of the claim — imposes no such restriction; `do_create_pool` is generic over `T::AssetKind` and performs no freezer/admin check regardless of runtime configuration. The vulnerability is in the pallet's design, not merely a specific runtime instantiation, and the previously-cited `TrustBackedAssetsInstance` config with `CreateOrigin = AsEnsureOriginWithArg<EnsureSigned<AccountId>>` demonstrates a realistic permissionless configuration exists in-repo.

## Impact Explanation
This matches the "permanent user-fund lock" impact class: a victim LP's deposited assets (including a potentially valuable counterpart asset like the native token) become irreversibly locked in the pool account, recoverable only at the attacker's discretion since the attacker holds sole `admin` control to `thaw`. It also constitutes a DoS on that trading pair since all liquidity removal and swaps touching the frozen asset fail with `Error::<T>::Frozen`.

## Likelihood Explanation
High feasibility for any runtime that configures asset creation with a permissionless `CreateOrigin` (as `TrustBackedAssetsInstance` does in asset-hub-rococo) and allows `pallet-asset-conversion` pools to be created for any `T::AssetKind` including such assets. The attack requires only two public extrinsics (`create`, `create_pool`/`add_liquidity`) plus `freeze`, and luring one victim LP — no governance, validator, or off-chain privileged access needed.

## Recommendation
- Restrict poolable assets in `pallet-asset-conversion` to those with no externally-controlled freezer, or require the freezer/admin role be renounced/burned before pooling.
- Have the pool account be exempted from third-party freezing, e.g., by pallet-asset-conversion implementing/registering its own `FrozenBalance` hook for pool accounts, or by rejecting `do_create_pool`/`do_add_liquidity` when the asset's freezer is not itself governance-controlled or the pallet.
- Alternatively, gate which `AssetKind`s are poolable via a runtime-configurable allowlist (`ForceOrigin`-vetted assets only).

## Proof of Concept
1. Attacker calls `pallet_assets::create(id=X, admin=attacker, min_balance=1)`; attacker becomes `admin`/`freezer` of `X` per `AssetDetails` insertion at `substrate/frame/assets/src/lib.rs:863-879`.
2. Attacker calls `pallet_asset_conversion::create_pool(Native, X)`, triggering `do_create_pool` (`substrate/frame/asset-conversion/src/lib.rs:729-788`), which `touch`es the pool account for both assets.
3. Attacker adds minimal seed liquidity.
4. Victim calls `add_liquidity(Native, X, ...)`, transferring native tokens into `pool_account` (`substrate/frame/asset-conversion/src/lib.rs:855-856`).
5. Attacker calls `pallet_assets::freeze(id=X, who=pool_account)` (`substrate/frame/assets/src/lib.rs:1192-1217`), succeeding because `origin == d.freezer`.
6. Any `remove_liquidity` or swap touching `X` from `pool_account` fails with `Error::<T>::Frozen` via `can_decrease` (`substrate/frame/assets/src/functions.rs:190-205`), permanently locking the victim's native-token liquidity unless the attacker (sole `admin`) chooses to `thaw`.
