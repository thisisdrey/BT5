### Title
Fixed-duration write-lock lease in Praefect's serialized-writes lock manager is stolen based on wall-clock expiry rather than actual completion of the in-flight transaction, allowing concurrent, un-serialized ref writes to the same repository - ([File: internal/praefect/datastore/lock_manager.go])

### Summary
The Praefect "serialized writes" feature guards against a documented Git deadlock by making sure only one reference-transaction can be past the `PREPARING` phase for a given repository at a time [1](#0-0) . The guarantee is implemented as a PostgreSQL row with a fixed `expired_at` deadline that is granted once at `PREPARING_PHASE` and renewed exactly once at `PREPARED_PHASE` [2](#0-1) . The deadline is a blind wall-clock offset (`NOW() + renewInterval`, hard-coded to 20 seconds) that is never re-validated against whether the holder has actually progressed or finished — exactly the same class of flaw as the referenced report's use of `block.timestamp` as an AMM deadline: the check is valid "whenever" it happens to be evaluated, regardless of the real state of the guarded operation.

### Finding Description
`RepoReferenceWriteLockManager.tryLock` grants (or steals) the lock via a single UPSERT that only checks `expired_at < NOW()` [3](#0-2) . The lease length is a fixed constant:

```go
lockRenewInterval := 20 * time.Second
``` [4](#0-3) 

`lockRepoForTransaction` renews this lease **once**, when the `PREPARED_PHASE` vote is cast, and never again while the holder is actually performing the on-disk ref locking and writing between `PREPARED` and `COMMITTED`:

```go
case gitalypb.VoteTransactionRequest_PREPARED_PHASE, gitalypb.VoteTransactionRequest_COMMITTED_PHASE:
    ...
    lock := v.(datastore.RepoLock)
    if err := lock.Renew(ctx); err != nil {
        return err
    }
``` [5](#0-4) 

If the real-world time between the `PREPARED` vote and the `COMMITTED` vote exceeds the fixed 20-second lease — for any reason: a slow disk, contention on `packed-refs` (which the codebase's own Git configuration comments say is common enough that Gitaly raises Git's own lock timeout from 1s to 10s [6](#0-5) ), a large push touching many refs, quorum voting latency across multiple nodes, or a node experiencing a stall — a second, unrelated transaction can steal the lock row via the exact same UPSERT and proceed into its own `PREPARED`/on-disk-locking phase while the first transaction is still mid-flight. The repository's own test suite demonstrates this mechanically: `TestPraefectWriteSerialization_HangAfterPrepared` shows that once `expired_at` has passed (there simulated by back-dating the row), a second transaction's `PREPARING_PHASE` vote succeeds and steals the lock even though the first transaction is still holding it and has not voted `COMMITTED` [7](#0-6) . In production this same condition is reached purely by the wall clock outrunning a legitimately slow operation — no crash, no explicit `StopTransaction`/`cancelTransaction` call, and no malicious peer is required.

Once stolen, two transactions can be concurrently past `PREPARING_PHASE` for the same repository, exactly the deadlock/race scenario the whole feature exists to prevent [8](#0-7) , because on-disk ref locks taken by the two nodes' Git processes are no longer guaranteed to be acquired in a globally consistent order.

### Impact Explanation
This defeats the correctness guarantee of the serialized-writes feature for an ordinary, unprivileged user's push: a sufficiently large or slow push (many refs, packed-refs rewrite, or degraded I/O/network conditions that the codebase itself acknowledges as realistic) can outlast the fixed lease and let a second transaction race onto the same repository. The result is loss of the "only one transaction can be past PREPARING at a time" invariant, reintroducing the cross-node ref-lock deadlock the feature was built to eliminate, and/or interleaved ref writes that can corrupt repository state or silently drop updates from one of the two racing transactions.

### Likelihood Explanation
No privileged access, leaked token, or malicious peer is needed. An attacker (or even an accidental legitimate user) only needs to issue a push that legitimately takes longer than 20 seconds between the `PREPARED` and `COMMITTED` votes — e.g. a push with a very large number of ref updates that forces a `packed-refs` rewrite, or timed to coincide with I/O contention, both of which the codebase's own comments describe as observed in practice [9](#0-8) . Because the renewal happens only once (at `PREPARED_PHASE`) rather than periodically for the duration of the actual write, the safety margin is fixed and easy to exceed deliberately.

### Recommendation
Do not rely on a single fixed-duration lease granted once at `PREPARED_PHASE`. Instead, either (a) renew the lease periodically (heartbeat) for as long as the holder is actively working between `PREPARED` and `COMMITTED`, tying the deadline to actual liveness rather than to a static wall-clock offset chosen once; or (b) require the stealer to verify the previous holder's transaction is actually dead (e.g. via the transaction manager's in-memory state or a liveness check) before taking over the row, rather than trusting `expired_at < NOW()` alone. This mirrors the AMM fix of not trusting `block.timestamp`/a blind timestamp check but instead tying validity to the real state of the operation being protected.

### Proof of Concept
The repository's own test demonstrates the underlying primitive: [7](#0-6) 
1. Txn1 casts `PREPARING_PHASE` then `PREPARED_PHASE` votes (lock acquired, renewed once) and then "hangs" (does not cast `COMMITTED_PHASE`) — modeling a slow write.
2. Once `expired_at` has passed (in the test, simulated by back-dating; in production, simply by the real operation taking >20s), Txn2 successfully casts `PREPARING_PHASE` and steals the lock while Txn1 is still logically in-flight.
3. Both transactions can now proceed to take on-disk ref locks and write concurrently to the same repository, exactly the deadlock/race condition the serialized-writes feature was designed to prevent [10](#0-9) .

# Praefect Serialized Writes

Praefect coordinates writes to a repository across multiple Gitaly nodes using a
voting protocol driven by the Git `reference-transaction` hook. This document
describes why writes must be serialized at the repository level, how the
serialization is implemented, what upstream Git change it depends on, and how to
turn the feature on.

## Why Serialize Writes

The voting protocol relies on Git's `reference-transaction` hook to vote on a
ref update at each phase of the transaction. The phases Git historically
exposed are:

- `prepared` — references have been locked on disk
- `committed` — updates have been persisted
- `aborted` — the transaction was rolled back

Praefect collects votes from all Gitaly nodes participating in the transaction
and only allows the write to proceed when quorum is reached.

The problem is that at the `prepared` phase, **on-disk ref locks have already
been taken**. With two concurrent transactions T1 and T2 updating overlapping
refs A and B:

1. Node 1: T1 locks A, T2 locks B
1. Node 2: T2 locks A, T1 locks B

Each transaction is now waiting for the other to release a lock, and neither
can release until quorum is reached for its own lock. The cluster is
deadlocked.

The fix is to serialize transactions **before** any node has taken an on-disk
ref lock. If only one transaction per repository can advance past this point at
a time, lock acquisition order is globally consistent and the deadlock above
cannot occur.
```

```markdown
### Flow for one write

1. Client calls a write RPC against Praefect.
1. Praefect forwards the RPC to each Gitaly node in the replica set.
1. Each Gitaly node, in `UpdateReference` (or the equivalent write path),
   casts a `Preparing` vote **before** locking refs locally. The hook RPC
   reaches Praefect, which calls `lockRepoForTransaction(PREPARING_PHASE)`:
   `WriteLockManager.Lock` blocks until the per-repository lock is free.
1. Both nodes return from `Preparing` together (quorum reached).
1. Each Gitaly node locks refs on disk and votes `Prepared`. Praefect renews
   the lock.
1. Each Gitaly node writes the update and votes `Committed`. Praefect releases
   the lock.

Because step 3 is exclusive per repository, no two transactions can be in
steps 4-6 at the same time for the same repo, so on-disk locks are always
taken in a consistent order.
```

	case gitalypb.VoteTransactionRequest_PREPARING_PHASE:
		lock, err := mgr.repoWriteLockMgr.Lock(ctx, storageName, repoRelativePath, transactionID)

			// No Preparing was cast for this transaction. This happens when Git itself drives
			// the reference-transaction hook on a Git build that doesn't emit "preparing"
			// (i.e. pre-2.54). Skip lock work; serialization is dormant for this path
			// until GIT_VERSION_PREV is bumped past 60d8c1e9.
			mgr.logger.WithFields(log.Fields{
				"transaction.id": transactionID,
				"phase":          phase.String(),
			}).DebugContext(ctx, "skipping lock check: no preparing phase recorded")
			return nil
		}
		lock := v.(datastore.RepoLock)
		if err := lock.Renew(ctx); err != nil {
			return err
		}
	}

func TestPraefectWriteSerialization_HangAfterPrepared(t *testing.T) {
	t.Parallel()
	db := testdb.New(t)
	ctx := testhelper.Context(t)
	logger := testhelper.SharedLogger(t)
	repoWriteLockMgr := datastore.NewRepoReferenceWriteLockManager(ctx, db, testdb.GetConfig(t, db.Name), logger)

	storageName := "mock"
	relativePath := "hang/after/prepared.git"
	voters := []transactions.Voter{{Name: "primary", Votes: 1}}
	threshold := uint(1)

	cc, txMgr, cleanup := runPraefectServerAndTxMgrAndLockMgr(t, ctx, repoWriteLockMgr)
	defer cleanup()
	client := gitalypb.NewRefTransactionClient(cc)

	// Txn1: PREPARING + PREPARED, then "hang" (no COMMITTED)
	txn1, _, err := txMgr.RegisterTransaction(ctx, voters, threshold)
	require.NoError(t, err)
	hash1 := sha1.Sum([]byte("txn1"))

	for _, phase := range []gitalypb.VoteTransactionRequest_Phase{
		gitalypb.VoteTransactionRequest_PREPARING_PHASE,
		gitalypb.VoteTransactionRequest_PREPARED_PHASE,
	} {
		_, err := client.VoteTransaction(ctx, &gitalypb.VoteTransactionRequest{
			TransactionId:        txn1.ID(),
			Repository:           &gitalypb.Repository{StorageName: storageName, RelativePath: relativePath},
			Node:                 voters[0].Name,
			ReferenceUpdatesHash: hash1[:],
			Phase:                phase,
		})
		require.NoError(t, err)
	}
	// Intentionally skip COMMITTED phase to simulate a stuck client.

	// Simulate lock expiry by back-dating the row
	_, err = db.ExecContext(ctx, `
          UPDATE repository_reference_write_locks
          SET expired_at = NOW() - INTERVAL '1 second'
          WHERE lock_id = $1`, storageName+"|"+relativePath)
	require.NoError(t, err)

	// Txn2: PREPARING should succeed (steals the expired lock)
	txn2, cancel2, err := txMgr.RegisterTransaction(ctx, voters, threshold)
	require.NoError(t, err)
	defer func() { require.NoError(t, cancel2()) }()
	hash2 := sha1.Sum([]byte("txn2"))

	_, err = client.VoteTransaction(ctx, &gitalypb.VoteTransactionRequest{
		TransactionId:        txn2.ID(),
		Repository:           &gitalypb.Repository{StorageName: storageName, RelativePath: relativePath},
		Node:                 voters[0].Name,
		ReferenceUpdatesHash: hash2[:],
		Phase:                gitalypb.VoteTransactionRequest_PREPARING_PHASE,
	})
	require.NoError(t, err)
}
