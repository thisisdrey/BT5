### Title
Unauthenticated mid-session public-key swap via re-handshake with no signature proof-of-possession check - (File: `stackslib/src/net/chat.rs`)

### Finding Description
`ConversationP2P::validate_handshake` branches on `self.connection.get_public_key()`. Only in the `None` case does it verify that the incoming `Handshake` is actually signed by the claimed key: [1](#0-0) 

In the `Some(_)` case (i.e. this conversation already has a bound public key, learned from an earlier handshake on the same TCP session), the code performs **no `verify_secp256k1` call at all** — it only checks, and only for outbound conversations, that the self-reported address matches the socket address: [2](#0-1) 

For inbound conversations (the attacker's case — they connect to the node), that address check is skipped entirely (`self.stats.outbound` is `false`), so the `Some(_)` branch degenerates into just a public-key-format check, an expiry check, and a "not our own key" check: [3](#0-2) 

None of these checks prove the sender possesses the private key for the newly claimed `node_public_key`, nor do they require any relationship between the previously-bound key and the newly-claimed key. `validate_handshake` returning `Ok(())` then leads `update_from_handshake_data` to unconditionally overwrite the bound identity: [4](#0-3) 

Dispatch confirms this path is reachable even when the second handshake fails the connection's normal per-message authentication check against the *previously* bound key: `handle_unauthenticated_control_message` still routes any `Handshake` payload into `handle_handshake` with `authenticated=false`, and `handle_handshake` calls `validate_handshake`/`update_from_handshake_data` regardless of that flag: [5](#0-4) [6](#0-5) 

Exploit flow: attacker connects inbound, sends `Handshake(pubkeyA)` self-signed by A (passes the `None`-branch `verify_secp256k1` check, binding the convo to A). Attacker then sends a second `Handshake(pubkeyB)` — this message can be signed with an arbitrary/garbage signature (it need not even be signed by B), because the `Some(_)` branch never calls `verify_secp256k1` against either the old key A or the new key B. `update_from_handshake_data` sees `pubk(B) != cur_pubk(A)`, sets `updated = true`, and unconditionally calls `self.connection.set_public_key(Some(B))`, silently flipping the conversation's authenticated identity with no proof of possession of B's private key at all.

### Impact Explanation
The in-memory identity bound to an established TCP conversation can be swapped to an arbitrary attacker-chosen key without any cryptographic proof of possession. This corrupts `to_neighbor_address()` (used when this conversation is gossiped to other peers via GetNeighbors/Neighbors replies), since the reported `public_key_hash` for that IP:port will reflect the forged key B: [7](#0-6) 
This is network-wide propagation of forged peer-identity data (an IP:port pair falsely bound to a public key its owner never proved control of), which other nodes may relay onward as inventory of peers — matching the Critical "network-wide propagation of forged data" category. For outbound conversations, the PeerDB is also updated via `Neighbor::load_and_update`/`save_update`, persisting the unauthenticated re-key into local state: [8](#0-7) 

### Likelihood Explanation
The attacker only needs to open a normal inbound P2P TCP connection — no privileged role, no secret, no prior trust relationship — and send two `Handshake` messages with different self-claimed public keys. The action is fully repeatable per-connection and costs nothing beyond opening a socket and crafting two small p2p messages. The remote P2P port is reachable by any unprivileged peer by design.

### Recommendation
In the `Some(_)` branch of `validate_handshake`, require that the incoming `Handshake` be verified with `message.verify_secp256k1(&handshake_data.node_public_key)` exactly as the `None` branch does, so a proof-of-possession check for the *new* key is always enforced. Additionally, consider requiring that a key upgrade on an already-authenticated conversation either (a) be signed by the previously-bound key as well (co-signature) or (b) be treated identically to a brand-new connection (drop/reset conversation state) rather than silently mutating the bound identity in place.
