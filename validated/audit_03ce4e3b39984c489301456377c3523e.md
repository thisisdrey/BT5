### Title
Attacker can saturate a victim's `MAX_TOKENS_PER_USER` quota via unsolicited dust deposits/transfers, DoS-ing new collateral and debt positions - (File: contracts/Pool.sol)

### Summary
`Pool` enforces a shared cap of `MAX_TOKENS_PER_USER = 30` on the combined length of `debtTokensOfAccount` and `depositTokensOfAccount` (contracts/Pool.sol:79,143-148). Entries are added without the account's consent: `DepositToken._mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever a recipient's balance goes 0→positive (contracts/DepositToken.sol:486-488), and `DepositToken.deposit(amount_, onBehalfOf_)` lets any caller mint msdTOKEN to an arbitrary `onBehalfOf_` address (contracts/DepositToken.sol:211-237). `_transfer` does the same on plain ERC20 `transfer`/`transferFrom` (contracts/DepositToken.sol:517-520). An attacker can therefore fill a victim's token list with unwanted deposit-token slots, causing every subsequent `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` for that account to revert with `UserReachedMaxTokens` (contracts/Pool.sol:143-148). This is the same bug class as the Ammplify M-3 (unconsented recipient quota filling under a shared global cap).

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` are gated only by `onlyIfAdditionWillNotReachMaxTokens(account_)` and by the caller being a registered token (contracts/Pool.sol:204-220). There is no opt-in from `account_`.
- `DepositToken.deposit` is permissionless and takes an arbitrary `onBehalfOf_` beneficiary; `_mint` adds the token to the beneficiary's list (contracts/DepositToken.sol:234, 486-488).
- `DepositToken.transfer`/`transferFrom` are public; `_transfer` adds the token to any recipient with a zero prior balance (contracts/DepositToken.sol:348-376, 517-520).
- `DebtToken._mint` similarly adds debt tokens on 0→positive balance, but debt issuance requires the position owner to call `issue`, so the attacker-controlled vector is the deposit-token side (contracts/DebtToken.sol:598-600).

Attack path: for every `DepositToken` registered in the victim's `Pool`, the attacker calls `depositToken.deposit(dust, victim)` (or deposits to itself and `transfer`s dust). Once `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) == 30`, any action that would add a new token to the victim's list reverts: depositing a collateral type the victim doesn't yet hold (`deposit` → `_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`), issuing a synthetic asset whose DebtToken isn't yet in the list (`issue` → `_mint` → `addToDebtTokensOfAccount` → revert), receiving an msdTOKEN transfer, and SmartFarmingManager leverage flows that mint new deposit/debt tokens (`DebtToken.mint`, `DepositToken` mints via `flashWithdraw`/leverage paths).

### Impact Explanation
Denial of service on core protocol functionality for the victim: they cannot open positions in any collateral or synthetic they don't already hold, cannot receive msdTOKEN transfers or `seize` proceeds from liquidation of others, and cannot use leverage routes that add new tokens. The freeze is temporary rather than permanent — a victim with no debt has fully unlocked balances and can self-recover by `transfer`ing each dust token away (which triggers `removeFromDepositTokensOfAccount`, contracts/DepositToken.sol:523-525) or `withdraw`ing it. However, cleanup requires per-token transactions and can be re-griefed; if the victim does hold debt, locked balances may make some slots unremovable until their position changes. This matches the "temporary freezing of funds / blocked core functionality" acceptance bound and mirrors the confirmed Ammplify M-3 impact.

### Likelihood Explanation
Cost is low and automatable: one dust `deposit` (or `transfer`) per registered `DepositToken`. The limiting factor is that the attacker can only add slots for tokens that actually exist in the victim's pool — the number of slots fillable equals the count of registered `DepositToken`s (bounded by the pool's `ReachedMaxDepositTokens` cap) plus any debt tokens the attacker can induce (effectively none, since `issue` mints debt to `msg.sender`). Therefore the attack fully blocks the victim only when `registeredDepositTokens + victimExistingDebtTokens ≥ 30`; with fewer registered tokens it partially reduces the victim's free slots. Feasibility depends on the deployed pool's token count and should be verified on the target fork.

### Recommendation
- Require recipient consent before adding a token to an account's list: e.g., restrict `deposit`'s `onBehalfOf_` to `msg.sender`, or implement a two-step claim/acceptance for unsolicited msdTOKEN balances.
- Alternatively, exempt unsolicited incoming transfers from the cap by only counting tokens the account deposited itself, or add a permissionless "cleanup" function letting an account remove a token from its own list (burning/transferring the residual balance).

### Proof of Concept
Hardhat sketch (adapt to repo's fixture in `test/Pool.test.ts`):

```ts
// attacker deposits dust into every DepositToken of the pool, onBehalfOf = victim
for (const dt of poolDepositTokens) {
  await underlying(dt).connect(attacker).approve(dt.address, DUST);
  await dt.connect(attacker).deposit(DUST, victim.address); // adds dt to victim's list
}

// once depositTokensOfAccount(victim) + debtTokensOfAccount(victim) == 30:
await expect(
  someOtherDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

await expect(
  debtToken.connect(victim).issue(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

The repository's own test at `test/Pool.test.ts:1386-1416` already demonstrates that `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once 30 slots are filled, confirming the revert behavior; the PoC above only needs to substitute the smock fakes with real `DepositToken.deposit(dust, victim)` calls on a fork.
