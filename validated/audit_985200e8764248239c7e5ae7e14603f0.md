### Title
Stale `YieldIdToDataId`/`DataIdToYieldId` mappings survive `DeleteAccount` and permanently freeze a recreated account's `promise_yield_create_with_id` calls - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` in `core/store/src/utils/mod.rs` deletes the `Account`, `ContractCode`, access/gas keys, and `ContractData` entries, but never removes `TrieKey::YieldIdToDataId`, `TrieKey::DataIdToYieldId`, `TrieKey::PromiseYieldStatus`, or `TrieKey::PromiseYieldReceipt` entries for that account. Because `has_yield_id_mapping` (checked in `create_promise_yield_receipt_with_id`) only looks at trie presence rather than account liveness, a stale mapping left behind by a deleted account causes a legitimate future `promise_yield_create_with_id(Y)` call after the account is recreated to be silently treated as a duplicate.

### Finding Description
`create_promise_yield_receipt_with_id` (`runtime/runtime/src/ext.rs:371-400`) checks `has_yield_id_mapping(self.trie_update, &receiver_id, user_yield_id)` before creating a new yield receipt, and if the mapping already exists in the trie it returns `Ok(None)` (surfaced to the contract as the `u64::MAX` sentinel per host-function contract), without creating any `PromiseYieldReceipt`. [1](#0-0) 

The `YieldIdToDataId`/`DataIdToYieldId` bidirectional mapping is written by `set_yield_id_mapping`, keyed only by `receiver_id` and the user-supplied `yield_id`: [2](#0-1) 

`remove_account`, invoked when an account is deleted via `DeleteAccount`, cleans up `Account`, `ContractCode`, access keys/gas key nonces, and `ContractData`, but has no logic that touches `YieldIdToDataId`, `DataIdToYieldId`, `PromiseYieldStatus`, or `PromiseYieldReceipt` keys: [3](#0-2) 

Exploit flow:
1. Attacker deploys a contract to `x.a.near` and calls `promise_yield_create_with_id` with attacker-chosen `Y`, writing `YieldIdToDataId{x.a.near, Y}` and `DataIdToYieldId{x.a.near, data_id}` via `set_yield_id_mapping`.
2. Attacker abandons the yield (never resolves it) and submits a `DeleteAccount` action for `x.a.near`. `remove_account` runs and deletes the account/keys/code/contract-data, but the yield-id mapping keys remain in the trie since they are never enumerated or removed.
3. Attacker (or anyone, since account names are first-come-first-served once deleted) recreates `x.a.near` and the victim deploys a new contract there that, as part of a documented idempotency pattern, calls `promise_yield_create_with_id(Y)`.
4. `has_yield_id_mapping` finds the stale `YieldIdToDataId{x.a.near, Y}` key still present and reports true, so `create_promise_yield_receipt_with_id` returns `None`/sentinel instead of creating the intended `PromiseYieldReceipt`. No error is raised, no receipt is created — the call silently no-ops.

No existing check (signature, nonce, access-key permission, gas metering, storage staking) prevents this because the vulnerability is a pure state-cleanup omission at the trie level, not an authorization or resource-limit issue. `DeleteAccount` action validation only concerns balance/state cleanup for standard state, not this yield-id namespace.

### Impact Explanation
This is a liveness/freezing bug, not a fund-drain bug directly, but it can cause the victim contract to believe a `promise_yield_create_with_id` call succeeded when in fact no yield receipt/PromiseYieldReceipt was ever created for `data_id`. Any deposit/logic gated behind that yield's resolution (e.g., escrowed funds waiting on a callback via `submit_promise_resume_data_with_yield_id`) can never resolve through the normal path, matching the "permanent freezing of user funds" bounty category. The practical severity depends on how a real contract's idempotency logic reacts to the sentinel return value — if it does not have a fallback/retry with a different `Y`, the flow is stuck permanently.

### Likelihood Explanation
Preconditions are attacker-controlled and cheap: the attacker needs to own account `x.a.near` (a sub-account they created, or any account they control) and issue a normal `FunctionCall` + `DeleteAccount` transaction sequence, all achievable by an ordinary unprivileged user. The attack additionally requires the victim's contract to (a) be deployed to that exact recreated account name and (b) call `promise_yield_create_with_id` with an attacker-predictable `yield_id` `Y` — this second requirement (predicting/colliding on the same `Y` value the victim will use, and the victim reusing a poisoned account name) meaningfully limits real-world applicability, since `yield_id` values are typically contract-chosen/unique (e.g. derived from request state) rather than attacker-guessable, and the victim would have to deploy onto an attacker-previously-owned account name. The underlying storage bug (stale trie keys after `DeleteAccount`) is unconditionally reproducible, but turning it into a victim-impacting exploit requires these additional coincidences.

### Recommendation
Extend `remove_account` (`core/store/src/utils/mod.rs`) to also enumerate and remove all `YieldIdToDataId`, `DataIdToYieldId`, `PromiseYieldStatus`, and `PromiseYieldReceipt` trie entries scoped to the account being deleted, mirroring the existing access-key/contract-data cleanup loops (using appropriate `trie_key_parsers` prefix iteration for these key types, adding such parsers if they don't exist).

### Proof of Concept
Integration/runtime test-loop plan:
1. Create account `x.a.near`, deploy a contract exposing a wrapper for `promise_yield_create_with_id(Y)`.
2. Call the wrapper with a fixed `Y`; assert `YieldIdToDataId{x.a.near, Y}` and `DataIdToYieldId{x.a.near, data_id}` exist in trie via `get_data_id_for_yield_id`/`get_yield_id_for_data_id`.
3. Submit `DeleteAccount` for `x.a.near`; assert `get_account(x.a.near)` is `None` but `has_yield_id_mapping(trie, x.a.near, Y)` is still `true`.
4. Recreate `x.a.near`, deploy a (possibly different) contract, call the wrapper again with the same `Y`.
5. Assert the call returns the `u64::MAX` sentinel (via `create_promise_yield_receipt_with_id` returning `None`) and that no new `PromiseYieldReceipt` exists for the new call's expected `data_id`/receipt count, confirming the yield silently failed to be created.

    yield_id: YieldId,
    data_id: CryptoHash,

    set(
        state_update,
        TrieKey::YieldIdToDataId { receiver_id: receiver_id.clone(), yield_id },

    );

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
