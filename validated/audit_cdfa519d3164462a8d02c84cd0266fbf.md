# No vulnerability found for this question.

**Analysis of the claimed binding**

The question claims that `RequestMessage` replay is possible when the nonce bitmap rotates `current` → `old` → dropped while the message's "validity window outlives the bitmap retention." Tracing `Nonces::commit` and `Nonces::check_cleanup` shows this is prevented by design with margin:

1. **Message validity window is clamped to the contract's `timeout`, not the message's own `timeout`.** In `Nonces::commit`, the check is:
```
if !(now - self.timeout.min(timeout) <= created_at && created_at <= now)
``` [1](#0-0) 
Since `self.timeout.min(timeout)` can never exceed `self.timeout`, a message can only be accepted while `now <= created_at + self.timeout`, regardless of the attacker/signer-supplied `msg.timeout` field [2](#0-1) .

2. **Nonce bitmap retention is `2 * self.timeout`**, and rotation is monotonic: `current`→`old` requires a gap of at least `self.timeout` since the last rotation, and `old` is only wiped once a further `self.timeout` has elapsed on top of that:
```
if self.last_cleaned_at < last_valid_nonce_at {          // rotate current -> old
    self.old = std::mem::take(&mut self.current);
    if self.last_cleaned_at < last_valid_nonce_at - self.timeout {  // wipe old
        self.old = BitMap::new(BTreeMap::new());
    }
    self.last_cleaned_at = now;
}
``` [3](#0-2) 
Because a nonce is only committed to `current` after `check_cleanup()` runs (at commit time `Tc >= created_at`), the earliest a nonce can be dropped from both bitmaps is `Tc + 2*self.timeout >= created_at + 2*self.timeout`. This is strictly greater than the message's own expiry at `created_at + self.timeout`.

**Conclusion**

There is always a full extra `self.timeout` safety margin between when a signed `RequestMessage` becomes permanently invalid (via the `created_at`/`min(self.timeout, msg.timeout)` check) and when its nonce could possibly be forgotten by the `old`/`current` bitmap rotation. Consequently, the scenario in the "Fast validation" section (resubmitting a "still-valid" request after `2 * timeout`) is self-contradictory: any request still valid per `Nonces::commit`'s deadline check cannot be older than `self.timeout`, so it can never reach the `2*timeout` bitmap-forgetting point. The lazy, call-triggered nature of `check_cleanup` (as opposed to automatic time-based expiry) can only *delay* forgetting further (an over-retention/storage concern, explicitly out of scope), never cause premature forgetting relative to a still-valid message. No replay of a signed `RequestMessage` is achievable through this path.
