### Title
Unprivileged attacker pollutes a victim's per-account token registry via dust DepositToken transfers, blocking new collateral deposits - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The prototype-pollution bug class (attacker-controlled keys injected into a shared object later trusted by the protocol) maps onto Metronome's per-account token registries `depositTokensOfAccount` / `debtTokensOfAccount`, which are keyed by the victim's address but written to by token contracts whenever a balance transitions from zero. Because `DepositToken` balances are freely transferable, any EOA can "pollute" a victim's registry with attacker-chosen keys by transferring dust amounts of every listed `DepositToken` to the victim, forcing the account up against `MAX_TOKENS_PER_USER` (30). Once the cap is hit, `onlyIfAdditionWillNotReachMaxTokens` reverts `UserReachedMaxTokens` for every *new* token type, so the victim cannot deposit additional collateral to restore health and can be liquidated.

### Finding Description
`Pool.addToDepositTokensOfAccount` is callable only by registered `DepositToken` contracts, but it is invoked from the token's transfer/mint hook for whatever `account_` (recipient) the *sender* chooses — there is no opt-in from the recipient. [1](#0-0) [2](#0-1) 

Each new `DepositToken` the victim touches (as recipient) consumes one slot in `MappedEnumerableSet.AddressSet` keyed by `victim`, and entries are only removed when the balance returns to exactly zero. [3](#0-2) [4](#0-3) 

Since deposit tokens are standard ERC-20-like shares, an attacker can transfer a 1-wei amount of each of the pool's deposit tokens to any victim address. After `MAX_TOKENS_PER_USER - (existing debt tokens)` such transfers, the victim's registry is full and any subsequent deposit into a *not-yet-held* `DepositToken` reverts at `addToDepositTokensOfAccount`.

### Impact Explanation
Temporary freezing of funds and forced liquidations:

- A victim whose position is approaching the liquidation threshold cannot add a *new* collateral type to heal the position — `deposit()` on a new `DepositToken` mints shares to the victim, triggering `addToDepositTokensOfAccount`, which reverts with `UserReachedMaxTokens`.
- The victim is then liquidatable via `Pool.liquidate`, losing collateral plus the liquidation incentive.
- The victim can only recover by transferring the dust tokens back out (reducing each polluting balance to zero so `removeFromDepositTokensOfAccount` runs), which the attacker can contest by re-dusting — a liveness/freeze asymmetry where the victim pays gas to clean entries the attacker created for free. [5](#0-4) 

Note on confidence: I could not re-read `DepositToken.sol`'s transfer hook in the remaining iterations, but the existence of `addToDepositTokensOfAccount`/`removeFromDepositTokensOfAccount` with `onlyIfAdditionWillNotReachMaxTokens` confirms the write path is driven by balance changes on the token side; the assumption is that `transfer`/`transferFrom` trigger it for the recipient, which is the standard Metronome pattern. If the hook only fires on `deposit()`/`mint()` to `msg.sender`, the vector narrows but still applies to any recipient parameter the token exposes.

### Likelihood Explanation
- Attacker requirements: hold dust of up to ~29 deposit tokens (cheap — they are vault shares obtainable by depositing a few wei of each underlying), then make ~29 `transfer` calls. No privileged role, flash loan, oracle manipulation, or governance action needed.
- Works on the deployed configuration: `MAX_TOKENS_PER_USER` is a hardcoded constant, the cap check is unconditional, and deposit tokens are permissionlessly transferable by design.
- Partially mitigated only if the pool lists few deposit tokens or the victim already holds all of them.

### Recommendation
- Make per-account list additions opt-in: gate `addToDepositTokensOfAccount` behind a flag set when the account itself calls `deposit()` (e.g., only register on mint where `to == operator` or on explicit `deposit` calls through the Pool, not on raw `transfer`/`transferFrom`).
- Alternatively, count only tokens with a balance above a dust threshold, or remove the `MAX_TOKENS_PER_USER` revert in favor of bounding iteration elsewhere.
- At minimum, skip `add`/`remove` bookkeeping for transfers that don't originate from `deposit()`/`withdraw()` flows.

### Proof of Concept
Hardhat sketch against a deployed/forked `Pool`:

```ts
// attacker holds dust of every listed deposit token
const depositTokens = await pool.getDepositTokens();
for (const dt of depositTokens) {
  const token = await ethers.getContractAt("DepositToken", dt);
  // skip tokens the victim already holds; each transfer adds a registry key
  if (await token.balanceOf(victim) === 0n) {
    await token.connect(attacker).transfer(victim, 1n); // pollutes depositTokensOfAccount[victim]
  }
}
// victim's position now at MAX_TOKENS_PER_USER
await expect(
  newDepositToken.connect(victim).deposit(collateralAmount)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");
// price move makes victim unhealthy; liquidator seizes collateral
await pool.connect(liquidator).liquidate(msUsd, victim, repayAmount, victimDepositToken);
```

Expected outcome: the victim cannot deposit any new collateral type while polluted, and the liquidation succeeds — a temporarily frozen position turned into a forced loss, driven entirely by unprivileged transfers of attacker-chosen registry keys.
