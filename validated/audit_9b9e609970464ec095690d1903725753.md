## No vulnerability found for this question.

The premise of the question is factually incorrect. The `rc_consensus_hash` field is not attacker-controlled: the wire body decoded by `try_parse_request` is a `StackerDBChunkData` containing only `slot_id`, `slot_version`, `sig`, and `data` — there is no `rc_consensus_hash` field in the client payload at all. [1](#0-0) 

The `rc_consensus_hash` attached to the `StackerDBPushChunkData` used for re-broadcast is populated by the node itself, immediately after storage, from its own current chain view — not from anything the remote peer sent: [2](#0-1) 

Consequently, the comparison in `process_uploaded_stackerdb_chunks` (`chunk.rc_consensus_hash != *rc_consensus_hash`) can only diverge if the node's own chain view changes between the moment the RPC handler snapshots it and the moment the relay loop processes the queued chunk — an internal timing artifact of the node's own state, not something an attacker can inject or control. [3](#0-2) 

The code comment explicitly documents the intended design: chunks are validated for authenticity (signer, slot ownership, version) by `try_replace_chunk`, and storage success alone implies novelty; the `rc_consensus_hash` check only gates whether to re-broadcast to avoid pointless propagation, not whether the data is valid or "canonical." [4](#0-3) 

StackerDB chunk data is off-chain, signer-authenticated pub/sub state, not chain-consensus state gated by a canonical tip; there is no equality violated by an attacker here, since the attacker cannot supply or forge the `rc_consensus_hash` value used in the comparison. This does not meet the "serving non-canonical state as canonical" High-impact category because there is no attacker-controllable divergence — the described scenario cannot be triggered by remote bytes.

    /// Process HTTP-uploaded stackerdb chunks.
    /// They're already stored by the RPC handler, so all we have to do
    /// is forward events for them and rebroadcast them (i.e. the fact that we stored them and got
    /// this far at all means that they were novel, and thus potentially novel to our neighbors).
    pub fn process_uploaded_stackerdb_chunks(
        &mut self,
        rc_consensus_hash: &ConsensusHash,
        uploaded_chunks: Vec<StackerDBPushChunkData>,
        event_observer: Option<&dyn StackerDBEventDispatcher>,
    ) {
        let mut all_events: HashMap<QualifiedContractIdentifier, Vec<StackerDBChunkData>> =
            HashMap::new();
        for chunk in uploaded_chunks.into_iter() {
            // Always forward the event to ensure the local signer receives it.
            if event_observer.is_some() {
                if let Some(events) = all_events.get_mut(&chunk.contract_id) {
                    events.push(chunk.chunk_data.clone());
                } else {
                    all_events.insert(chunk.contract_id.clone(), vec![chunk.chunk_data.clone()]);
                }
            }

            if chunk.rc_consensus_hash != *rc_consensus_hash {
                debug!("Not rebroadcasting stale uploaded StackerDB chunk";
                           "stackerdb_contract_id" => %chunk.contract_id,
                           "slot_id" => chunk.chunk_data.slot_id,
                           "slot_version" => chunk.chunk_data.slot_version,
                           "chunk.rc_consensus_hash" => %chunk.rc_consensus_hash,
                           "network.rc_consensus_hash" => %rc_consensus_hash);
                continue;
            }

            debug!("Got uploaded StackerDB chunk"; "stackerdb_contract_id" => %chunk.contract_id, "slot_id" => chunk.chunk_data.slot_id, "slot_version" => chunk.chunk_data.slot_version);

            let msg = StacksMessageType::StackerDBPushChunk(chunk);
            if let Err(e) = self.p2p.broadcast_message(vec![], msg) {
                warn!("Failed to broadcast StackerDB chunk: {e:?}");
            }
        }
