### Title
Standby witness reward distribution loses funds to floating-point truncation - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.payStandbyWitness()` and the legacy `computeReward(long, List)` path split a fixed reward pool among multiple Super Representatives (SRs) in proportion to their vote counts using floating-point division and `(long)` truncation, exactly like the Nouns Builder `Token.sol` founder-allocation bug where an integer-division-based schedule caused participants to receive less than their entitled share. Because the per-recipient share is computed with `double` arithmetic and then truncated, the sum of amounts actually paid out is generally less than the pool that was supposed to be distributed, and specific vote-count ratios cause a larger, systematic shortfall for individual SRs, exactly mirroring the `(100/pct1) - (100/pct2) == 1` coincidence described in the report.

### Finding Description
In `payStandbyWitness()`: [1](#0-0) 

```java
long voteSum = witnessStandbys.stream().mapToLong(WitnessCapsule::getVoteCount).sum();
...
long totalPay = dynamicPropertiesStore.getWitness127PayPerBlock();
double eachVotePay = (double) totalPay / voteSum;
for (WitnessCapsule w : witnessStandbys) {
  long pay = (long) (w.getVoteCount() * eachVotePay);
  payReward(w.getAddress().toByteArray(), pay);
}
```

`eachVotePay` is computed once as a `double`, and each witness's `pay` is `(long) (voteCount * eachVotePay)`. Every multiplication/truncation independently rounds *down*, so `Σ pay(w)` for all witnesses is virtually always strictly less than `totalPay`. The undistributed remainder is not tracked, reconciled, or carried forward anywhere — it is silently and permanently lost (it is never added back to any account, pool, or black hole in a way that is verifiable/traceable), unlike the deliberate `blackhole`/`transactionFeePool` handling used elsewhere in the codebase (e.g. `consumeFeeForBandwidth`) [2](#0-1) .

The same root-cause pattern (percentage share computed via `double` division then truncated to `long`) also appears in the legacy vote-reward computation used by `withdrawReward`: [3](#0-2) 

```java
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
```

and in the brokerage split for block/transaction-fee rewards: [4](#0-3) 

```java
double brokerageRate = (double) brokerage / 100;
long brokerageAmount = (long) (brokerageRate * value);
value -= brokerageAmount;
```

In all three cases, unlike the hardened arithmetic patterns that were introduced elsewhere in the codebase specifically to avoid this class of bug (e.g. `RepositoryImpl.calculateGlobalLimitV2` and `ResourceProcessor.divideCeilExact`, which use `BigInteger` and ceiling-division to preserve exact proportional shares) [5](#0-4) , the reward-distribution paths in `MortgageService` still use raw `double` truncation, so participants systematically receive less than their exact entitled percentage of the reward pool, and the difference is permanently unaccounted for.

### Impact Explanation
This causes SRs and voters/stakers to permanently receive fewer rewards than their vote-weighted entitlement on every maintenance cycle that pays standby witnesses, and on every reward withdrawal that uses the legacy vote-rate computation. Because this runs automatically for every SR/voter on every cycle (not a one-off edge case), the aggregate value lost across the network over time is real economic loss to legitimate stakeholders — a permanent, protocol-level loss of funds analogous to the founders' "less tokens than expected" issue in the referenced report.

### Likelihood Explanation
This is not a hypothetical or attacker-triggered issue — it fires automatically and deterministically on every maintenance-period standby-witness payout (`payStandbyWitness()`) and on every reward withdrawal computed under the old reward algorithm (`computeReward`), for any combination of vote counts where `totalPay % voteSum != 0` (i.e., essentially always). No malicious input or special privilege is required; it occurs under completely normal on-chain voting/reward operation.

### Recommendation
Replace the `double`-based proportional split with exact integer arithmetic that either (a) uses `BigInteger`/`Math.multiplyHigh`-safe fixed-point math and distributes any remainder deterministically (e.g., to the largest-remainder recipients or into a tracked pool), mirroring the `divideCeilExact`/`calculateGlobalLimitV2` hardening pattern already used in `ResourceProcessor` and `RepositoryImpl`, or (b) accumulate the leftover remainder explicitly (e.g., carry it into the next cycle's `totalPay`, or route it to `blackhole`/`transactionFeePool` the same way transaction fees are handled) so that the reward pool is fully and traceably accounted for instead of being silently lost.

### Proof of Concept
For any `voteSum` and per-witness `voteCount` values that do not divide `totalPay` evenly, `eachVotePay = (double) totalPay / voteSum` and `pay = (long)(voteCount * eachVotePay)` will truncate every witness's share downward. Example: `totalPay = 100`, three witnesses with `voteCount = 33, 33, 34` (`voteSum = 100`): `eachVotePay = 1.0`, so each gets `33, 33, 34` = `100` total (exact in this case), but with `totalPay = 100`, `voteSum = 101` and votes `33, 33, 35`: `eachVotePay ≈ 0.990099`; `pay` values become `32, 32, 34` = `98`, i.e., `2` units (2% of the pool) are permanently lost every single cycle this distribution occurs — this compounds indefinitely across the life of the chain, exactly as `testMEP_M1_2` demonstrated the law-of-large-numbers loss in the original Nouns Builder report.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
