### Title
Refund-time recomputation of `prepaid_exec_gas`/`prepaid_send_fee` from live `RuntimeConfig` can diverge from the amount actually debited at tx-conversion time for receipts that cross a protocol-version boundary - (File: `runtime/runtime/src/config.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`calculate_tx_cost` (which determines how much balance is debited from the signer, including `gas_remaining = prepaid_gas + prepaid_send_fee.gas + receipt_cost.gas + prepaid_exec_fee.gas`) and `refund_unspent_gas_and_deposits` (which determines how much gas gets refunded when the resulting `ActionReceipt` is actually executed) both independently recompute the send/exec fee components from a `RuntimeConfig` argument, rather than from a value stored on the receipt itself. If the fee schedule (`config.fees`/`wasm_config`) used at these two moments differs, the two computations of the "total gas budget" for the same receipt are not guaranteed to be equal.

### Finding Description
`calculate_tx_cost` in `runtime/runtime/src/config.rs` computes, at the moment a `Transaction` is converted into a receipt: [1](#0-0) 
using the `RuntimeConfig` in force at that block/protocol version. This `gas_remaining` figure is exactly what is priced (`remaining_gas_amount = gas_remaining * receipt_gas_price`) and deducted from the signer's account.

Later, when the produced `ActionReceipt` is actually applied (potentially on a different shard, potentially after being placed in the delayed-receipt queue due to congestion), `refund_unspent_gas_and_deposits` in `runtime/runtime/src/lib.rs` reconstructs the same conceptual budget from scratch: [2](#0-1) 
Algebraically, `prepaid_gas(refund) + prepaid_exec_gas(refund)` reduces to the same formula as `gas_remaining` in `calculate_tx_cost` **only if the same `config` (same fee schedule) is used in both calls**. `refund_unspent_gas_and_deposits` receives `config` as a parameter reflecting the config in effect for the current apply call (i.e. the protocol version at execution time), not the protocol version/config that was active when the transaction was converted and the balance was debited.

The code's own doc comment acknowledges that NEP-536 deliberately pins the **gas price** across the receipt's lifetime so that price fluctuations don't affect refunds: [3](#0-2) 
but it does not similarly pin the **fee amounts** (`total_prepaid_send_fees`, `total_prepaid_exec_fees`, `ActionCosts::new_action_receipt` exec fee) to the config version in effect when the receipt was created. If a protocol upgrade changes any of the action send/exec cost parameters between receipt creation and receipt application, the refund-time reconstruction of the "purchased" gas budget will not match the amount that was actually debited from the signer at conversion time.

### Impact Explanation
If a protocol upgrade increases the relevant send/exec fee parameters between receipt creation and execution, `refund_unspent_gas_and_deposits` will compute a larger `gross_gas_refund` than what was actually purchased, over-refunding the signer/predecessor account — a token-inflation bug (value creation). If fees decrease, the refund will be smaller than what was purchased, silently destroying user funds without any corresponding burn accounting, which is loss of user funds. Either direction violates the value-conservation invariant that "the same prepaid_gas figure must be used for debit and refund."

### Likelihood Explanation
Exploiting this requires (a) a receipt (e.g. from a `FunctionCall` transaction) to be delayed past a protocol-version/epoch boundary — achievable by an ordinary user via congestion on the receiving shard, which is a normal, unprivileged, and repeatable action (submit transactions that push the shard's delayed-receipt queue), and (b) an actual protocol upgrade landing in that window that changes the relevant fee tables (`ActionCosts` send/exec fees, `wasm_config` parameters feeding `total_prepaid_send_fees`/`total_prepaid_exec_fees`). Condition (b) is outside attacker control and depends on validator/governance-driven protocol upgrades; I was not able to confirm, within the available context, a specific currently-shipping protocol feature that changes these exact fee-table entries (e.g. `ExecutionMetadataV4` as inspected only changes execution-outcome metadata format, not the fee tables, and I did not have context to fully verify `FixAccessKeyAllowanceCharging`'s effect on `total_prepaid_exec_fees`/`total_prepaid_send_fees`). This is therefore a structural/architectural weakness confirmed at the code level, but concrete exploitability depends on external, non-attacker-controlled events (protocol upgrades actually changing these specific parameters) that I could not fully verify in this pass.

### Recommendation
Persist the fee-relevant quantities computed at tx-conversion time (e.g. `prepaid_send_fee.gas`, `prepaid_exec_fee.gas`, or the full `gas_remaining`) on the `ActionReceipt`/`Receipt` itself (alongside the already-pinned `gas_price`), and have `refund_unspent_gas_and_deposits` use those stored values instead of recomputing them from the (possibly newer) `RuntimeConfig` at execution time. Alternatively, ensure `RuntimeConfig` fee parameters relevant to `total_prepaid_send_fees`/`total_prepaid_exec_fees`/`ActionCosts::new_action_receipt` are guaranteed immutable across protocol versions (an explicit protocol invariant), and add an assertion/test that fails CI if a future protocol upgrade changes any of these parameters without a corresponding receipt-versioning migration.

### Proof of Concept
Integration/test-loop plan (in `runtime/runtime/src/tests/apply.rs` or `test-loop-tests`):
1. Construct a `RuntimeConfigStore` with two protocol versions, V1 and V2, where V2 changes one of `fees.fee(ActionCosts::new_action_receipt)`'s exec fee, or a `total_prepaid_exec_fees`/`total_prepaid_send_fees` input parameter, relative to V1.
2. Submit a `FunctionCall` transaction under protocol version V1; call `tx_cost`/`calculate_tx_cost` directly to record `gas_remaining_v1` and the resulting debited `total_cost`.
3. Force the resulting `ActionReceipt` into the delayed-receipt queue (simulate chunk congestion), then bump `apply_state.current_protocol_version` to V2 before the receipt is applied.
4. Apply the receipt and capture the refund produced by `refund_unspent_gas_and_deposits`.
5. Assert that `prepaid_gas(refund) + prepaid_exec_gas(refund)` (computed under V2) equals `gas_remaining_v1` (computed under V1) exactly. Expect the assertion to fail whenever V1/V2 fee tables differ for the relevant parameters, demonstrating that refund total diverges from what was actually purchased at tx-conversion time.
