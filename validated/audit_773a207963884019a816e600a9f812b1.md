### Title
Missing hash verification of downloaded `Attachment` content against requested `Hash160` in `AttachmentsBatchStateContext::extend_with_attachments` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts any `Attachment` returned by a peer for a `GET /v2/attachments/{content_hash}` request and stores it via `self.attachments.insert(response.attachment)` without ever checking that `Attachment::hash()` (i.e. `Hash160::from_data(&content)`) equals the `Hash160` `content_hash` that was actually requested. Because the request is driven by a confirmed on-chain `AttachmentInstance` (BNS/name operation), a malicious source peer can substitute arbitrary bytes for the attachment content the chain committed to.

### Finding Description
The request is built from a queued `AttachmentInstance.content_hash` in `get_prioritized_attachments_requests` and dispatched via `AttachmentRequest::make_request_type` as `GET /v2/attachments/{content_hash}` (download.rs:1110-1118). Any peer listed as a source (an unprivileged remote peer that merely advertised an attachment inventory bit) can answer this GET with a `StacksHttpResponse` whose JSON body decodes into an `Attachment { content: <attacker bytes> }`.

In `extend_with_attachments` (download.rs:530-558), the response is decoded with `response.decode_atlas_get_attachment()` and, on success, immediately stored:
```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
} else {
    report.bump_failed_requests();
}
``` [1](#0-0) 

There is no comparison of `request.content_hash` (the hash that was actually requested, held by the loop variable `request`) against `Hash160::from_data(&response.attachment.content)` before insertion. The equality `Attachment::hash() == AttachmentInstance.content_hash` — the invariant that is supposed to bind the served bytes to the on-chain commitment — is never enforced at this point in the pipeline. Any attacker-controlled source peer answering the download request therefore gets its payload accepted into `self.attachments` purely because the JSON decoded successfully, regardless of whether the bytes match the hash committed to by the confirmed BNS/name contract call.

### Impact Explanation
An unprivileged remote peer that is (a) listed as a source in the inventory results for a given `content_hash`, and (b) able to answer the subsequent `GET /v2/attachments/{content_hash}` request, can supply arbitrary bytes as the "attachment" for a hash that a confirmed on-chain BNS operation legitimately committed to. If this mismatched `Attachment` is subsequently persisted/served by the node's Atlas subsystem, remote clients querying that node for the attachment tied to a specific name/zonefile hash would receive attacker-chosen data rather than the data whose hash was actually recorded on-chain — a BNS/attachment mismatch matching the "High" severity category (serving non-canonical state as canonical).

### Likelihood Explanation
The precondition is modest: the node must have a queued `AttachmentInstance` from a confirmed BNS/name transaction (a routine, easily triggered situation), and the attacker must control (or race to be selected as) one of the reachable inventory sources for that hash — something any peer that gossips an attachment inventory bit for that page/index can attempt. No secret, admin role, or privileged position is required; the attacker only needs to run a peer that responds to the Atlas HTTP GET. The check that is missing is purely at the application layer in `extend_with_attachments`; no lower-layer guard (HTTP auth, message length caps, etc.) provides equivalent protection for this specific field.

### Recommendation
In `extend_with_attachments`, before inserting, verify `response.attachment.hash() == request.content_hash` (i.e., recompute `Hash160::from_data(&response.attachment.content)` and compare to the request's `content_hash`); on mismatch, treat it as a failed request (`report.bump_failed_requests()`) and discard the attachment, mirroring how `AttachmentInstance` hashes are validated elsewhere in the Atlas pipeline.

### Proof of Concept
Add a unit test in `stackslib::net::atlas::download` that:
1. Constructs an `AttachmentRequest` with a known `content_hash` H (e.g., hash of `b"expected"`).
2. Builds a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map contains `(request, Some(response))`, where `response` is a `StacksHttpResponse` whose JSON body decodes (via `decode_atlas_get_attachment`) to `Attachment { content: b"attacker-controlled".to_vec() }` (so `Hash160::from_data(content) != H`).
3. Calls `AttachmentsBatchStateContext::extend_with_attachments(ctx, &mut results)`.
4. Asserts that `ctx.attachments` contains the mismatched attachment — demonstrating that `self.attachments.insert(response.attachment)` at download.rs:548 accepts it unconditionally, with no assertion failure or rejection based on `request.content_hash`.

Note: full confirmation that this mismatched attachment becomes resolvable end-to-end via `AtlasDB::find_attachment` would require tracing the downstream persistence code in `stackslib/src/net/atlas/db.rs` (e.g., whether `insert_uninstantiated_attachment` re-keys/validates by content-derived hash), which could not be fully verified within the available investigation; this should be checked to determine whether the missing check in `extend_with_attachments` is fully exploitable end-to-end or only partially mitigated by downstream hash-keyed storage.
