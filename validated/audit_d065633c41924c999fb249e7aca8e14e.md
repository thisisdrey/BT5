### Title
Wallet Contract pays the relayer fee unconditionally, independent of whether the emulated action succeeds, causing permanent user fund loss - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The reported ERC-4337 bug is a case where a "prefund"/fee payment is deducted unconditionally from funds that are supposed to be preserved for a specific purpose, without being contingent on the outcome of the operation it is meant to pay for — leading to the user losing funds they should have kept. The NEAR analog is the `near-wallet-contract`'s (NEP-518) `inner_rlp_execute` function, which issues the relayer's fee transfer as an independent promise, disconnected from the promise that performs the user's actual intended action.

### Finding Description
When a relayer submits an RLP-encoded Ethereum transaction that is parsed as an emulated base-token transfer or ERC-20 transfer, the Wallet Contract computes a `tx_fee` from the user-signed `max_fee_per_gas * gas_limit` [1](#0-0) , then unconditionally fires a **separate** promise batch to pay that fee to the relayer (`context.predecessor_account_id`) as soon as the transaction kind is determined to carry a non-zero fee: [2](#0-1) 

This fee-payment promise (`env::promise_batch_create` / `env::promise_batch_action_transfer`) is created and scheduled independently of the `promise` variable that actually carries out the user's intended action (transfer, ERC-20 transfer via NEP-141, etc.), which is built later in the same function and only resolved via `rlp_execute_callback` [3](#0-2) . The account's nonce is also incremented immediately in the same code path (before either promise is known to succeed) [4](#0-3) , permanently consuming the user's signed intent.

Because the fee promise and the action promise are unrelated, sibling promises originating from the same receipt rather than a single atomic chain, there is no guarantee that funding is available for both. If the wallet's account balance (which must also cover NEAR storage staking, per `check_storage_stake`) is only sufficient to cover one of the two transfers, one promise can succeed while the other fails — most critically, the relayer's fee can be paid out even though the user's actual intended action (the base-token or ERC-20 transfer) fails. Unlike the `rlp_execute_callback` failure path, which refunds `caller_deposit` (the NEAR attached by the caller) on failure [5](#0-4) , there is no such refund mechanism for the relayer fee — it is never reclaimed if the paired action fails.

### Impact Explanation
A user whose Wallet Contract account balance is tight (e.g. near the zero-balance/storage-stake threshold) can have the relayer fee deducted from their account while the transfer/ERC-20 action they intended fails, and since the nonce has already advanced, the transaction cannot be replayed. This is a permanent, non-recoverable loss of funds for the eth-implicit account owner, mirroring the reported issue's core defect: an unconditional "prefund"-style payment carved out of funds that should otherwise be reserved intact for the user's operation.

### Likelihood Explanation
This requires the wallet's NEAR balance to be low enough that it can cover the fee but not the full action (or vice versa), and a relayer (honest or not) submitting a transaction under those conditions. Because eth-implicit accounts are explicitly designed to support zero/low-balance operation (NEP-448 zero-balance accounts) and fees are computed independently of the wallet's actual liquid balance, this scenario is plausible in normal operation rather than requiring privileged access — any relayer can trigger it, intentionally or not.

### Recommendation
Chain the relayer-fee transfer to the same promise as the main action (e.g. attach it as part of the same promise batch, or gate the fee transfer behind success of the main action via a callback), so that the fee is only paid out when the user's underlying action actually succeeds. Alternatively, verify upfront that the wallet's spendable balance (excluding storage-stake requirements) can cover both the fee and the action's cost before scheduling either promise.

### Proof of Concept
1. Fund an ETH-implicit Wallet Contract account with a balance just above the storage-stake/zero-balance threshold, sufficient to pay `tx_fee` but not the intended `tx.value` transfer amount.
2. Have a relayer submit an RLP-encoded emulated base-token transfer with a non-zero `max_fee_per_gas * gas_limit` fee and a `value` that, combined with the fee, exceeds the wallet's spendable balance.
3. Observe: the fee promise (`env::promise_batch_action_transfer(refund_promise, *fee)`) succeeds and pays the relayer, while the main transfer promise fails due to insufficient balance for both storage stake and the deposit.
4. The wallet's nonce has already been incremented, so the user cannot resubmit; the fee amount is permanently lost with no corresponding action performed.
