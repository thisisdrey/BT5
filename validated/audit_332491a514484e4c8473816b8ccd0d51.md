### Title
Uncontrolled Resource Consumption via Unbounded Array Allocation in `ValidateMultiSign` Precompile — ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` precompiled contract (TVM precompile at a fixed address, reachable from any smart contract call) decodes an attacker-controlled ABI "signature array length" and allocates a Java array sized directly from that value before any bound check is applied, when the chain parameter `allowTvmSelfdestructRestriction` is not yet enabled. This mirrors the Tika PSDParser bug class (CWE-400): a maliciously crafted length field triggers an oversized memory allocation attempt with negligible attacker cost.

### Finding Description
`ValidateMultiSign.execute` reads the signature-array length from caller-supplied `rawData` and, depending on a feature flag, either bounds-checks it first or does not: [1](#0-0) 

When `VMConfig.allowTvmSelfdestructRestriction()` is `false`, the code calls `extractBytesArray` directly, with **no upper bound check on `len`** before allocating the array: [2](#0-1) 

`len` comes from `words[offset].intValueSafe()`, which decodes an attacker-supplied 32-byte ABI word from the call-data of `ValidateMultiSign` (`intValueSafe()` clamps to `Integer.MAX_VALUE`/`MIN_VALUE` but does not reject large positive values). The very next line, `byte[][] bytesArray = new byte[len][];`, attempts to allocate up to ~2^31 object-array slots *before* the subsequent `signatures.length > MAX_SIZE` guard has any chance to run: [3](#0-2) 

The energy charged for this precompile call is derived only from `rawData.length` (`cnt = (data.length / WORD_SIZE - 5) / 5`), which is small and unrelated to the value embedded in the length word: [4](#0-3) 

This decouples the actual memory-allocation cost from the energy paid — an attacker can supply a small call-data buffer (cheap energy) that encodes a huge `len` value, causing a disproportionate allocation attempt, exactly the "input length vs. resource cost" mismatch pattern behind CVE-2020-1950.

### Impact Explanation
An attempted allocation of a very large `byte[][]` inside the TVM execution thread throws `OutOfMemoryError` or forces the JVM into significant GC pressure, which can crash or stall the node process handling the transaction (including validating full nodes and SR nodes that must re-execute the same transaction while producing/confirming blocks). Because this executes inside block/transaction processing (`Manager` → actuator → TVM → precompile), a successful trigger can affect availability of the node, which the scope classifies as node crash/halt impact.

### Likelihood Explanation
Exploitability is gated entirely by the dynamic parameter `allowTvmSelfdestructRestriction`, controlled via `ProposalUtil`/`DynamicPropertiesStore` and toggled by an SR committee proposal (`ProposalService`): [5](#0-4) 
On any network where this proposal has not been activated (e.g., private/test chains, forks, or a mainnet prior to activation), the vulnerable `extractBytesArray` path is live and reachable from a single, ordinary, unprivileged smart-contract call with no special privileges — only a `TriggerSmartContract`/`TriggerConstantContract` invoking the `ValidateMultiSign` precompile address with crafted call data.

### Recommendation
Move the `sigArraySize > MAX_SIZE` bound check so it is evaluated unconditionally before any array is allocated in `extractBytesArray` (and `extractBytes32Array`), regardless of the `allowTvmSelfdestructRestriction` flag, and clamp/validate `len` against `MAX_SIZE` (or a sane hard cap) inside `extractBytesArray`/`extractBytes32Array` themselves rather than relying on the caller to pre-check. Additionally, make the energy cost for `ValidateMultiSign` scale with the decoded array length rather than only `rawData.length`, so the cost model cannot be bypassed with a small call-data buffer.

### Proof of Concept
1. Deploy/interact with a contract that performs a `STATICCALL`/`CALL` to the `ValidateMultiSign` precompiled contract address on a network/chain state where `allowTvmSelfdestructRestriction` is disabled (default `0` until the corresponding SR proposal is activated).
2. Craft `rawData` such that:
   - `words[0]` = target address, `words[1]` = permission id, `words[2]` = data.
   - `words[3]` = an offset pointing to a controlled word.
   - The word at that offset (`len`) is set to a very large value (e.g., `0x7FFFFFFF`), while the rest of `rawData` is minimal so `getEnergyForData` reports a small energy cost.
3. Submit the transaction with modest energy; execution reaches `extractBytesArray(words, offset, rawData)`, which executes `new byte[len][]` with `len` ≈ `Integer.MAX_VALUE`, causing an immediate large allocation attempt / `OutOfMemoryError` in the node's TVM execution thread before the `signatures.length > MAX_SIZE` check is ever reached.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
