Based on the investigation, `FetchIntoObjectPool` validates only that `Origin` and `ObjectPool` share the same storage name, but never verifies that `Origin` is actually a legitimate member/source of that specific object pool before fetching all of its refs and objects into the pool.

### Title
Cross-repository object disclosure via unverified origin-to-pool binding in `FetchIntoObjectPool` - (File: internal/gitaly/service/objectpool/fetch_into_object_pool.go)

### Summary
`FetchIntoObjectPool` accepts any `origin` repository and any `object_pool` as long as they share the same storage name, then fetches all references and objects from `origin` into the pool. There is no check that `origin` is the pool's actual seed/source repository or an authorized member of the pool, analogous to the reported bug class where a signed record is accepted without checking that the signer's declared identity actually corresponds to the key/record being modified.

### Finding Description
`validateFetchIntoObjectPoolRequest` only checks that the request has an `Origin` and `ObjectPool`, and that they share the same `StorageName`: [1](#0-0) . It never confirms that `Origin` is the object pool's originating/seed repository or that it is linked to it. `FetchIntoObjectPool` then directly calls `objectPool.FetchFromOrigin(ctx, origin, ...)` [2](#0-1) , which performs `git fetch +refs/*:refs/remotes/origin/*` from `origin` into the pool repository, per the documented behavior of housekeeping fetches [3](#0-2) .

The object pool identity itself is only checked for structural validity (`FromProto` verifies the pool path is a well-formed pool directory and exists) [4](#0-3) , not that the caller-supplied `Origin` is the one true source repository that was used to originally seed that pool (via `CreateObjectPool`) or that it is a `LinkRepositoryToObjectPool` member. Because objects fetched into a pool become readable by every repository that has an "alternates" link to that pool (any repo linked via `Link`/`linkedToRepository` in `internal/git/objectpool/link.go` [5](#0-4) ), an attacker who can reach this RPC with an arbitrary `origin` repository on the same storage (but a pool they don't legitimately seed) can inject that origin's refs/objects into the pool. Any other repository already linked to that pool can then read the injected objects through the alternates mechanism, achieving cross-repository object disclosure — the same "any combination is accepted" failure pattern as the CVE, but applied to the origin↔pool binding instead of key↔peer-ID binding.

### Impact Explanation
Successful exploitation permits copying objects (blobs, commits, potentially secrets committed to a private repository) from one repository into an object pool shared with unrelated repositories, exposing them to any repository/member with alternates access to that pool. This is a concrete cross-repository object access/information-disclosure vector.

### Likelihood Explanation
The RPC is a normal `ObjectPoolService` mutator RPC reachable through Gitaly's gRPC interface (and routed by Praefect, as shown by `TestStreamDirectorMutator`'s "target and additional repository" case) [6](#0-5) . Exploitability in production depends on whether GitLab Rails' internal-API authorization layer independently enforces that the caller has permission to reference the given `Origin` repository as a pool source before invoking this RPC — that authorization logic lives outside this repository (in GitLab Rails / gitlab-shell), so it cannot be confirmed or ruled out from the Gitaly codebase alone. Within Gitaly itself, no such binding check exists, which is the root cause aligned with the reported bug class.

### Recommendation
Before fetching, verify that `Origin` is actually associated with the target object pool — e.g., require it to already be linked to the pool (via the same check used by `linkedToRepository`) or to match metadata recorded when the pool was created via `CreateObjectPool`, and reject the request otherwise.

### Proof of Concept
Conceptual (cannot be executed here, no filesystem/terminal access):
1. Create object pool `P` seeded from repository `A` (`CreateObjectPool` with origin `A`) on storage `default`.
2. Link a second repository `B` (public/shared) to pool `P` via `LinkRepositoryToObjectPool`.
3. Call `FetchIntoObjectPool` with `ObjectPool = P`, `Origin = C` — an unrelated private repository on the same storage that the caller can reference but that was never linked to `P`.
4. Because `validateFetchIntoObjectPoolRequest` only checks storage-name equality, the RPC succeeds and all refs/objects from `C` are fetched into `P`.
5. Any client with access to `B` (linked via alternates to `P`) can now read `C`'s objects, e.g. via `git cat-file` against `B`'s alternates, since `P`'s objects directory is readable through `B`.

func validateFetchIntoObjectPoolRequest(req *gitalypb.FetchIntoObjectPoolRequest) error {
	if req.GetOrigin() == nil {
		return errors.New("origin is empty")
	}

	if req.GetObjectPool() == nil {
		return errors.New("object pool is empty")
	}

	originRepository, poolRepository := req.GetOrigin(), req.GetObjectPool().GetRepository()

	if originRepository.GetStorageName() != poolRepository.GetStorageName() {
		return errors.New("origin has different storage than object pool")
	}

	return nil
}

// FromProto returns an object pool object from its Protobuf representation. This function verifies
// that the object pool exists and is a valid pool repository.
func FromProto(
	ctx context.Context,
	logger log.Logger,
	locator storage.Locator,
	gitCmdFactory gitcmd.CommandFactory,
	catfileCache catfile.Cache,
	txManager transaction.Manager,
	housekeepingManager housekeepingmgr.Manager,
	proto *gitalypb.ObjectPool,
) (*ObjectPool, error) {
	poolPath, err := locator.GetRepoPath(ctx, proto.GetRepository(), storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, err
	}

	if !storage.IsPoolRepository(proto.GetRepository()) {
		// When creating repositories in the ObjectPool service we will first create the
		// repository in a temporary directory. So we need to check whether the path we see
		// here is in such a temporary directory and let it pass.
		tempDir, err := locator.TempDir(proto.GetRepository().GetStorageName())
		if err != nil {
			return nil, fmt.Errorf("getting temporary storage directory: %w", err)
		}

		if !strings.HasPrefix(poolPath, tempDir) {
			return nil, ErrInvalidPoolDir
		}
	}

	pool := &ObjectPool{
		Repo:                localrepo.New(logger, locator, gitCmdFactory, catfileCache, proto.GetRepository()),
		logger:              logger,
		locator:             locator,
		gitCmdFactory:       gitCmdFactory,
		txManager:           txManager,
		housekeepingManager: housekeepingManager,
	}

	if !pool.IsValid(ctx) {
		return nil, ErrInvalidPoolRepository
	}

	return pool, nil
}

// linkedToRepository tests if a repository is linked to an object pool
func linkedToRepository(ctx context.Context, pool, repo *localrepo.Repo) (bool, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting repo path: %w", err)
	}

	altInfo, err := stats.AlternatesInfoForRepository(repoPath)
	if err != nil {
		return false, fmt.Errorf("getting alternates info: %w", err)
	}

	if !altInfo.Exists || len(altInfo.ObjectDirectories) == 0 {
		return false, nil
	}

	relPath := altInfo.ObjectDirectories[0]
	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return false, err
	}

	if relPath == expectedRelPath {
		return true, nil
	}

	if filepath.Clean(relPath) != filepath.Join(poolPath, "objects") {
		return false, fmt.Errorf("unexpected alternates content: %q", relPath)
	}

	return false, nil
}
