### Title
Missing slippage protection in `ExchangeWithdrawActuator` allows MEV sandwich theft of exchange-pool funds - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawContract`/`ExchangeWithdrawActuator` lets the pool creator withdraw one side of a bancor-curve exchange pool and computes the counterpart token amount from the *current* pool ratio at execution time, with no caller-specified minimum-output parameter, analogous to Orca's hard-coded `token_min_a = token_min_b = 0` in `decreaseLiquidity`.

### Finding Description
`ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id` and `quant` — there is no `expected`/minimum field, unlike `ExchangeTransactionContract` which explicitly has `expected` and enforces it (`token required must greater than expected`) in `ExchangeTransactionActuator`. [1](#0-0) [2](#0-1) 

In `ExchangeWithdrawActuator.execute`, the counterpart amount (`anotherTokenQuant`) is derived purely from the *live* `firstTokenBalance`/`secondTokenBalance` ratio of the pool at execution time via `BigInteger` multiplication/division, with no comparison against any caller-supplied minimum: [3](#0-2) 

`doValidate()` only checks that `tokenQuant > 0`, that pool balances are non-zero, and a "Not precise enough" rounding-consistency check — it never validates the ratio/price against a caller-chosen bound, so any value of `anotherTokenQuant`, however small relative to what the withdrawer expected, passes validation: [4](#0-3) 

Because `ExchangeTransactionActuator` lets any unprivileged account trade against the same pool and instantly moves `firstTokenBalance`/`secondTokenBalance` in `ExchangeCapsule` (`ExchangeCapsule.transaction`, then `Commons.putExchangeCapsule`), an attacker can broadcast a large trade immediately before the victim's `ExchangeWithdraw` transaction to skew the pool ratio, let the victim's withdraw execute at that skewed ratio (since it has no minimum-output floor), and then broadcast a reversing trade immediately after to restore the ratio and capture the difference. This is functionally the same missing-slippage-protection class as the reported Orca `decreaseLiquidity` bug, just built with TRON's TRC10 exchange trio (`ExchangeTransactionActuator`, `ExchangeWithdrawActuator`, `ExchangeInjectActuator`) instead of Whirlpool's `decreaseLiquidity`.

### Impact Explanation
An MEV searcher (an ordinary, unprivileged transaction broadcaster) can sandwich a legitimate `ExchangeWithdraw` transaction to force it to redeem an unfavorable split of the pool's two assets, extracting value from the withdrawer without their consent — a concrete theft-of-funds impact reachable from a single pair of signed transactions around the victim's transaction.

### Likelihood Explanation
Exploitation requires only ordinary `ExchangeTransaction` calls (fully unprivileged, open to any account holding TRX/the relevant TRC10 asset) sandwiched around the victim's `ExchangeWithdraw` transaction within the same block or adjacent blocks, which any block producer or well-positioned broadcaster can arrange; no special permissions, committee approval, or malicious-SR behavior is needed.

### Recommendation
Add a `min_expected_another_token_quant` (or similar) field to `ExchangeWithdrawContract`, propagate it into `ExchangeWithdrawActuator.execute`/`doValidate`, and reject the transaction if the computed `anotherTokenQuant` is below the caller-specified minimum, mirroring the `expected` check already present in `ExchangeTransactionActuator`.

### Proof of Concept
1. Exchange pool P holds token A and token B with balances `Af`, `Bf`.
2. Victim broadcasts `ExchangeWithdraw(tokenId=A, quant=q)` expecting `anotherTokenQuant ≈ Bf*q/Af`.
3. Attacker front-runs with `ExchangeTransaction` trading a large amount of A into the pool for B, shifting `Af`↑, `Bf`↓ (via `ExchangeTransactionActuator.execute`, updating `ExchangeCapsule` balances). [5](#0-4) 
4. Victim's withdraw executes against the now-skewed ratio, computing a much smaller `anotherTokenQuant` than intended, with `doValidate` raising no error since there is no minimum-output check. [6](#0-5) 
5. Attacker back-runs with the reverse `ExchangeTransaction`, restoring the pool ratio and pocketing the difference extracted from the victim's withdrawal.
