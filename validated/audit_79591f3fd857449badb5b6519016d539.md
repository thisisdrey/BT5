## Title
Missing slippage/minimum-received protection in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` enables sandwich-attack value extraction - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The reported bug class is a missing "expected price" check that lets a mutable, externally-changeable exchange rate be applied to a user's trade without the user being able to bound the outcome. In java-tron's Bancor-style TRC10 `Exchange`, this exact protection exists for `ExchangeTransactionContract` (a `getExpected()` bound is enforced) but is completely absent from the sibling contracts `ExchangeInjectContract` and `ExchangeWithdrawContract`, which compute the counter-token amount from the live pool ratio at execution time with no caller-supplied bound.

### Finding Description
`ExchangeTransactionActuator.doValidate()` requires callers to supply a minimum expected return and reverts if the computed `anotherTokenQuant` is less than it: [1](#0-0) 

In contrast, `ExchangeInjectActuator.doValidate()`/`execute()` compute `anotherTokenQuant` purely from the exchange's `firstTokenBalance`/`secondTokenBalance` ratio at execution time, with no analogous "expected" field on the contract to bound how much the creator pays: [2](#0-1) 

Likewise, `ExchangeWithdrawActuator.doValidate()`/`execute()` computes the counter-token amount the creator receives purely from the live pool ratio, again with no minimum-received parameter: [3](#0-2) 

Both actuators are restricted to the exchange's creator address (`accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())`), but that restriction only checks *who* may submit the inject/withdraw — it does nothing to prevent an unrelated, unprivileged transaction broadcaster from moving the pool ratio immediately before (and after) the creator's transaction is packed into a block. Any account can submit `ExchangeTransactionContract` trades that shift `firstTokenBalance`/`secondTokenBalance` — this is the exact same "value changed between when the user forms the tx and when it executes" root cause described in the report for `KnightingRound.buy`/`setTokenOutPrice`, just realized through ordinary trades on the AMM pool instead of an admin-set price.

### Impact Explanation
An attacker can sandwich the creator's `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction: trade against the pool to skew the ratio just before it executes, let the creator's inject/withdraw settle at the skewed ratio, then trade back afterward to restore the ratio and capture the spread. Because neither actuator lets the creator bound the amount paid (inject) or received (withdraw), this results in the creator overpaying or under-receiving TRX/TRC10 assets — a concrete transfer of value (theft) from the exchange creator/pool to the attacker, achievable purely from broadcastable, unprivileged transactions.

### Likelihood Explanation
Both `ExchangeInjectContract` and `ExchangeWithdrawContract` are ordinary broadcastable transactions processed through the standard actuator validate/execute path; an attacker only needs the ability to submit `ExchangeTransactionContract` trades against the same exchange ID and to observe/predict the creator's pending inject/withdraw transaction (e.g., via mempool visibility), which is a realistic MEV-style setup already acknowledged as a risk class for the sibling `ExchangeTransactionContract` (hence its `expected` field).

### Recommendation
Add an `expected` (minimum-received or maximum-paid) field to `ExchangeInjectContract` and `ExchangeWithdrawContract`, mirroring the check already present in `ExchangeTransactionActuator` at [1](#0-0) , so `ExchangeInjectActuator`/`ExchangeWithdrawActuator` validation rejects the transaction if the computed `anotherTokenQuant` deviates unfavorably beyond the caller's specified bound.

### Proof of Concept
1. Exchange creator prepares an `ExchangeWithdrawContract` to withdraw `tokenQuant` of `firstTokenID`, expecting `anotherTokenQuant` of `secondTokenID` based on the currently observed pool ratio at [4](#0-3) .
2. Attacker observes this pending transaction and submits an `ExchangeTransactionContract` trade beforehand that shifts `firstTokenBalance`/`secondTokenBalance` in their favor, processed via `ExchangeTransactionActuator.execute()` at [5](#0-4) .
3. The creator's withdraw executes against the now-skewed ratio at [6](#0-5) , since there is no minimum-received check to abort it.
4. Attacker submits a reverse trade to restore the ratio and pocket the difference, with no on-chain protection preventing steps 2–4 because `ExchangeWithdrawContract` (and `ExchangeInjectContract`) never validate against a caller-supplied expected value, unlike `ExchangeTransactionContract`.
