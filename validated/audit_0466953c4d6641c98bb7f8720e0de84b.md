## Title
StackerDB replica skips reconfiguration when a signer's authorization is fully revoked, letting a previously-authorized signer continue to write chunks to slots the DB owner intended to disable - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::create_or_reconfigure_stackerdbs` refreshes each StackerDB's configuration from its controlling smart contract every reward cycle, but only calls `reconfigure_stackerdb` (which rewrites the persisted per-slot `signer` column in the on-disk `chunks`/slot-validation table) when the *new* config is non-empty. If the contract update disables/empties the signer set (the StackerDB analog of an admin disabling an IdP), the on-disk slot-validation record is never updated, and the previous signer's key remains bound to slots in the persistence layer used by `try_replace_chunk`/`validate_received_chunk`.

Note the guard `!new_config.signers.is_empty()`: it explicitly *skips* calling `reconfigure_stackerdb` whenever the freshly-loaded config has an empty signer list. This is the exact case that occurs when the controlling contract revokes/disables all previously-authorized writers (analogous to an admin disabling an IdP in the Keycloak advisory). Despite skipping the on-disk reconfiguration, the function still records the empty-signers `new_config` in the in-memory map it returns: [2](#0-1) 

The actual chunk-validation authority, however, is not the in-memory config but the on-disk `SlotValidation` record read via `get_slot_validation`/`get_slot_signer`, which was populated by the *last successful* `reconfigure_stackerdb`/`create_stackerdb` call: [3](#0-2) 

```

    .get_slot_validation(smart_contract, slot_desc.slot_id)?
    .ok_or(net_error::NoSuchSlot(...))?;
if !slot_desc.verify(&slot_validation.signer)? {
```

and similarly in the p2p push-chunk path (`validate_received_chunk`), which calls `self.stackerdbs.get_slot_signer(...)` directly against the persisted table: [4](#0-3) 

Because the guard prevents the DB from ever being told "this slot's signer is now revoked," the stale `signer` value from the last non-empty configuration persists in the SQLite `chunks` table (via `reconfigure_stackerdb` → `tx.reconfigure_stackerdb`). Consequently, a signer whose write authorization was fully revoked by the controlling contract can still produce a validly-signed `StackerDBChunkData`/`SlotMetadata` (they still hold their private key) that will pass both the HTTP POST endpoint's check (`try_replace_chunk`) and the p2p push-chunk check (`validate_received_chunk`), because both check against the stale, un-reconfigured `signer` column rather than the current (empty) contract-derived authorization list.

This breaks the equality that "chunk write authority == the signer set currently returned by the controlling smart contract" — the node instead enforces "chunk write authority == the last signer set for which the signers list was non-empty."

### Impact Explanation
This is an unauthorized-write vulnerability against StackerDB state: a remote peer whose write privileges were revoked by the smart-contract-based access control (the mechanism operators use to disable a signer, analogous to disabling an IdP in the report) can continue writing/propagating chunks under their old, revoked authorization. Since StackerDB chunks are pushed and gossiped between peers (`handle_unsolicited_StackerDBPushChunk`), this stale write can be relayed network-wide as "currently-authorized" data, i.e., unauthorized write to network state and propagation of data that should be considered forged/no-longer-authorized.

### Likelihood Explanation
The condition is reached whenever a StackerDB-controlling contract transitions from having signers to having none (e.g., emptying the signer set to disable the DB or a bad-actor signer) — a legitimate, foreseeable administrative action, not a corner case requiring a compromised key. The attacker only needs to retain the (now supposedly revoked) private key they were issued earlier, and continue sending previously-valid signed chunks; no privileged access or secret of another party is required.

### Recommendation
Remove the `!new_config.signers.is_empty()` exemption from the reconfiguration guard in `create_or_reconfigure_stackerdbs`, so that transitioning to an empty signer set still triggers `reconfigure_stackerdb` (updating/clearing persisted `signer` bindings), or explicitly special-case "signers now empty" to wipe/disable the slots rather than silently skip reconfiguration.

### Proof of Concept
1. Deploy/operate a StackerDB-controlling contract with one signer `A` owning slot 0.
2. Node loads config via `StackerDBConfig::from_smart_contract`, `create_stackerdb` is called, and slot 0's `signer` column is set to `A`.
3. Admin updates the contract so `stackerdb-get-signer-slots` now returns an empty list (fully revoking `A`).
4. On the next `create_or_reconfigure_stackerdbs` pass, `new_config.signers` is empty, so `!new_config.signers.is_empty()` is false, and `reconfigure_stackerdb` is *not* called — the on-disk `signer` column for slot 0 remains `A`.
5. `A` (still holding their private key) signs and submits/pushes a `StackerDBChunkData` for slot 0 with an incremented `slot_version`.
6. `try_replace_chunk` (HTTP POST) / `validate_received_chunk` (p2p push) both check against the stale on-disk `SlotValidation{signer: A}` and accept the write despite `A` no longer being an authorized signer per the current contract state.

**Caveat:** I was not able to fully trace `tx.reconfigure_stackerdb`'s SQL behavior (whether it clears rows for removed signers or only adds new ones) within the available index; this affects only the exact mechanics of how stale rows persist, not the core finding that the guard clause skips reconfiguration entirely on an empty new signer set.
