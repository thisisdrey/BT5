Based on my investigation, I've confirmed the strongest reachable java-tron analog: the top-level `CreateSmartContract` deployment path in `VMActuator.create()`.

### Title
Front-runnable, deterministic top-level contract address enables permanent griefing/DOS of `CreateSmartContract` deployment - (File: `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
The Sherlock finding's root cause is: (1) a deployment's target address is publicly computable before the deployment lands on-chain, and (2) the deployment actuator hard-reverts if any account/state already exists at that address. java-tron's own top-level smart-contract creation path (`CreateSmartContract` transaction type, executed by `VMActuator.create()`) has the exact same structural weakness, and unlike the Sherlock report's "expensive minimum shares" degradation, java-tron's version causes an outright, unconditional revert of the deployer's transaction.

### Finding Description
When a user broadcasts a `CreateSmartContract` transaction, its target contract address is computed deterministically as `sha3(txRawDataHash || ownerAddress)`: [1](#0-0) 

This transaction ID (`txRawDataHash`) is fixed the moment the transaction is signed, and it is fully public as soon as the transaction is broadcast to the P2P network / sits in a node's pending pool — well before it is packed into a block. Any observer can therefore compute the exact resulting `contractAddress` ahead of time and race a plain TRX (or asset) transfer to that address into an earlier position in the same or an earlier block (e.g. via a higher-fee/priority transaction).

`VMActuator.create()` then performs an unconditional existence check on that address and throws if anything is already there: [2](#0-1) 

Because `rootRepository.getAccount(contractAddress)` returns non-null the moment *any* account object exists at that address (a plain TRX transfer creates an `AccountCapsule`), a single low-value transfer to the predicted address is sufficient to make the legitimate `CreateSmartContract` transaction throw `ContractValidateException("Trying to create a contract with existing contract address...")`, causing the whole deployment transaction to fail. This differs from the `CREATE2`/internal `createContractImpl` path, where `isContractExist()` gates on actual code/contract metadata (Constantinople hardening) rather than mere account existence: [3](#0-2) 

The top-level path has no such nuance — any pre-existing `AccountCapsule`, even a bare EOA with a dust balance, blocks creation outright.

### Impact Explanation
This breaks the core "deploy a smart contract" functionality for a targeted victim transaction: for the cost of one minimal TRX transfer (bandwidth/energy fee only), a griefer can force a specific `CreateSmartContract` transaction to fail deterministically, every single time it is resubmitted with the same raw data (same `txId` ⇒ same address). Because the address depends solely on `txRawDataHash` and `ownerAddress` — not on any nonce that would change on failure — the victim cannot simply resend the identical transaction; they must construct an entirely new transaction (different `ref_block`/`expiration`/timestamp fields) to get a new `txId`/address, and the griefer can repeat the attack against the new address just as cheaply. This matches the Sherlock M-3 "breaks core contract functionality, rendering the contract useless" DOS class, and is arguably more severe since java-tron's outcome is an outright revert rather than merely inflated cost.

### Likelihood Explanation
Low cost, no special privileges, and full public visibility of `txId` once broadcast make this trivially exploitable by any unprivileged network participant able to observe the mempool and submit a competing transaction with higher priority/fee. No malicious-SR/witness/consensus involvement is required — this is reachable purely from broadcastable, ordinary user transactions (a `TransferContract` and a `CreateSmartContract`).

### Recommendation
Do not hard-fail top-level contract creation merely because an `AccountCapsule` already exists at the target address. Mirror the internal `CREATE`/`CREATE2` handling in `Program.createContractImpl` (`actuator/src/main/java/org/tron/core/vm/program/Program.java`): only reject when actual contract code/metadata (`isContractExist`) is present, and otherwise upgrade the pre-existing account in place (preserving its balance), as already done for `HistoryBlockHashUtil.deploy` (`framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java`) which explicitly handles "anyone can transfer TRX to the canonical address before deploy" by upgrading the account type rather than reverting.

### Proof of Concept
1. Attacker monitors the P2P network for pending `CreateSmartContract` transactions (or is told the transaction bytes directly, e.g. through wallet/dApp integration flows).
2. From the pending transaction bytes, attacker computes `txId = sha256(raw_data)` and then `contractAddress = sha3omit12(txId || ownerAddress)` exactly as in `WalletUtil.generateContractAddress`.
3. Attacker broadcasts a minimal `TransferContract` sending 1 SUN to `contractAddress`, with sufficient fee/priority to be included before the victim's `CreateSmartContract` transaction.
4. When the victim's transaction executes, `VMActuator.create()` finds `rootRepository.getAccount(contractAddress) != null` and throws `ContractValidateException`, failing the deployment; the victim's fee for bandwidth/energy consumed up to that point is still spent.
5. Victim must build a brand-new transaction (changing `expiration`/`ref_block` fields) to get a different `txId`/address; attacker can repeat step 3 against the new address for the same trivial cost. [2](#0-1)

  public static byte[] generateContractAddress(Transaction trx) {

    CreateSmartContract contract = ContractCapsule.getSmartContractFromTransaction(trx);
    byte[] ownerAddress = contract.getOwnerAddress().toByteArray();
    TransactionCapsule trxCap = new TransactionCapsule(trx);
    byte[] txRawDataHash = trxCap.getTransactionId().getBytes();

    byte[] combined = new byte[txRawDataHash.length + ownerAddress.length];
    System.arraycopy(txRawDataHash, 0, combined, 0, txRawDataHash.length);
    System.arraycopy(ownerAddress, 0, combined, txRawDataHash.length, ownerAddress.length);

    return Hash.sha3omit12(combined);

  }
