## Title
Vault `redeem` allows self-referential `recipient` (the vault contract itself), causing user's redeemed underlying to be silently absorbed by the vault instead of delivered - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and equivalent sibling vaults)

### Summary
The Zest v2 tokenized vault contracts (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) expose a `redeem` function that lets the caller freely choose an arbitrary `recipient` principal to receive the withdrawn underlying asset, with no check preventing that `recipient` from being the vault contract's own address (`current-contract`). This is the exact analog of the external report's `PrimitiveEngine.withdraw` bug class: a recipient-controlled withdrawal path with no validation against the contract's own address.

### Finding Description
`redeem` burns the caller's zTokens and calls `send-underlying` to move the corresponding underlying asset to the caller-supplied `recipient`: [1](#0-0) 

`send-underlying` performs the transfer via a direct SIP-010 call from `current-contract` to `account` (the `recipient`): [2](#0-1) 

Critically, the vault's own `transfer` function (for the zToken itself) *does* explicitly guard against the destination being the vault contract: [3](#0-2) 

using `ERR-TOKENIZED-VAULT-PRECONDITIONS` to reject `to == current-contract`. That same guard is conspicuously **absent** from `redeem`'s handling of `recipient`, and equally absent from `deposit`'s handling of `recipient` (which mints shares to an arbitrary principal without checking it isn't the vault itself). This asymmetry - protecting the internal zToken ledger from self-transfers but not protecting the underlying-asset withdrawal path from the same mistake - is precisely the missing-validation pattern described in the report for `PrimitiveEngine.withdraw`.

When `recipient == current-contract` in `redeem`:
- The caller's zTokens are burned via `ft-burn? zft amount account`.
- The vault's internal accounting variable `assets` is decremented by `inkind`.
- The underlying-token transfer is a self-transfer (vault to itself), so the redeemer never actually receives any underlying tokens - the value they redeemed is effectively lost to them while remaining trapped inside the vault's balance, mirroring the "funds stuck in the contract" outcome from the original report.

This same pattern repeats identically across all sibling vault contracts: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

### Impact Explanation
An ordinary depositor who calls `redeem` and mistakenly (or via a wallet/integration bug) supplies the vault's own contract principal as `recipient` burns their zTokens but never receives the underlying asset - the value is permanently unrecoverable through the normal redeem path, since their shares are already destroyed and the underlying stays commingled in the vault's balance without being credited back to them. This is a **permanent freezing/loss of user funds at rest**, matching the Critical/High impact classes in scope ("permanent freezing of funds").

### Likelihood Explanation
This requires only an ordinary, unprivileged user calling the public `redeem` entry point with a self-inflicted (or client-bug-induced) bad `recipient` argument - no privileged role, DAO action, or flashloan is required, and it is directly reachable from a normal principal's call, exactly like the original report's exploit scenario for `PrimitiveEngine.withdraw`.

### Recommendation
Add an explicit check in `redeem` (and `deposit`) in all vault contracts mirroring the one already present in `transfer`:
```clarity
(asserts! (not (is-eq current-contract recipient)) ERR-TOKENIZED-VAULT-PRECONDITIONS)
```
This should be enforced before burning shares/transferring underlying so that a user cannot direct withdrawn assets back into the vault contract itself.

### Proof of Concept
1. Alice deposits underlying asset into `v0-vault-usdc` and receives `zft` shares.
2. Alice calls `(redeem amount min-out .v0-vault-usdc)` — i.e., passing the vault's own contract principal as `recipient`.
3. `redeem` burns Alice's shares via `ft-burn? zft amount account` and decrements `assets` by `inkind`.
4. `send-underlying` executes a transfer from `current-contract` to `current-contract` (self-transfer) — no tokens are actually delivered to Alice.
5. Alice's shares are gone; she received nothing; the underlying asset remains in the vault's balance, unattributed to her.

```text
(define-public (redeem (amount uint) (min-out uint) (recipient principal))
  (let (
    (states (var-get pause-states))
    (u (try! (accrue)))
    (account contract-caller)
    (current-assets (var-get assets))
    (balance (get-balance-internal account))
    (balance-check (asserts! (>= balance amount) ERR-INSUFFICIENT-BALANCE))
    (available-assets (get-available-assets))
    (inkind (convert-to-assets-preview amount)))

  (asserts! (>= current-assets inkind) ERR-INSUFFICIENT-ASSETS)
  (asserts! (not (get redeem states)) ERR-PAUSED)
  (asserts! (> amount u0) ERR-AMOUNT-ZERO)
  (asserts! (> inkind u0) ERR-OUTPUT-ZERO)
  (asserts! (>= inkind min-out) ERR-SLIPPAGE)
  (asserts! (>= available-assets inkind) ERR-INSUFFICIENT-LIQUIDITY)

  (try! (ft-burn? zft amount account))
  (try! (send-underlying inkind recipient))
  (var-set assets (- current-assets inkind))

  (print {
    action: "redeem",
    caller: contract-caller,
```
