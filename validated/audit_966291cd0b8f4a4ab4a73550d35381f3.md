Audit Report

## Title
Per-recipient staking reward transfer failures are silently swallowed, permanently losing nominator payouts while the era page is marked as paid - (File: `substrate/frame/staking-async/src/pallet/impls.rs`)

## Summary
`do_payout_stakers_by_page` calls `Eras::<T>::set_rewards_as_claimed(era, &stash, page)` at [1](#0-0)  before the actual reward transfers are attempted later in the function via `payout_from_provider` → `make_payout_from_provider`. If `T::Currency::transfer` from the era's `staker_rewards_pot` to a recipient's `payout_account` fails, `make_payout_from_provider` only logs the error and returns `None` at [2](#0-1) , and the caller treats that identically to a zero reward, silently skipping the recipient with no event and no compensating storage update at [3](#0-2) .

## Finding Description
The claimed-page bookkeeping is irreversible: `set_rewards_as_claimed` is invoked unconditionally before the per-nominator payout loop runs, and there is no subsequent path that unwinds it if a transfer fails [4](#0-3) . Later, `Self::payout_from_provider(...)` is invoked from within the same extrinsic handler and iterates over all nominators in the page, calling `make_payout_from_provider` per recipient [5](#0-4) . Inside `make_payout_from_provider`, a failed `T::Currency::transfer` is caught, logged, and converted into `None` with no error propagation [6](#0-5) . The caller `payout_from_provider` treats this `None` exactly like a zero-value reward — it simply omits the `Rewarded` event and moves to the next nominator, without incrementing any failure counter or recording the unpaid amount anywhere [7](#0-6) . Since `do_payout_stakers_by_page` still returns `Ok(...)` regardless of how many individual `make_payout_from_provider` calls returned `None` [8](#0-7) , and the page is already recorded as claimed, there is no way to re-attempt payment for that nominator through the normal flow — `AlreadyClaimed` will be returned on any retry attempt for that (era, stash, page) via the `is_rewards_claimed` check [9](#0-8) .

## Impact Explanation
This breaks the required invariant that "payout state must only advance after ... settlement succeed atomically." A transfer failure for any individual nominator results in funds remaining in the era's `staker_rewards_pot` (never transferred) while the page's claimed cursor has permanently advanced, making that nominator's reward unrecoverable through the standard `payout_stakers`/`payout_stakers_by_page` flow. This is an unbacked-value/permanent-fund-lock condition reachable through ordinary use of a public extrinsic.

## Likelihood Explanation
Any unprivileged account can call `payout_stakers`/`payout_stakers_by_page`, and the code path already anticipates and handles a fallible `T::Currency::transfer` result (it has a dedicated error-logging branch), demonstrating the failure mode is a recognized possibility in this position rather than a purely theoretical one. `Preservation::Expendable` transfers can still fail (e.g. `TokenError::FundsUnavailable`, frozen/locked balances on the recipient, or other fungible-trait-specific fallible conditions), and the vulnerable code performs no verification that the pot balance or the destination account state guarantees success before advancing the claimed-page cursor.

## Recommendation
Do not advance the claimed-page state for a page until every payout within it succeeds or is deterministically deferred to a re-claimable record. Concretely: propagate `T::Currency::transfer` errors so the whole extrinsic can fail atomically before `set_rewards_as_claimed` takes effect, or move the `set_rewards_as_claimed` call to occur only after all transfers in the page have been attempted, with individually-unpaid amounts recorded in a dedicated retryable storage item.

## Proof of Concept
1. Configure a nominator whose `payout_account` (via `RewardDestination::Account`) is in a state that causes `T::Currency::transfer(&staker_rewards_pot, &payout_account, amount, Preservation::Expendable)` to return `Err` (e.g., `TokenError::FundsUnavailable` due to frozen/locked balance on the destination, or another fungible-trait fallible condition for that account).
2. Call `payout_stakers`/`payout_stakers_by_page` for the era/validator/page containing this nominator as any unprivileged signed account.
3. Observe the extrinsic returns `Ok(...)`; `PayoutStarted` fires; `Eras::<T>::set_rewards_as_claimed` has already marked the page claimed; no `Rewarded` event is emitted for the failing nominator and their balance is unchanged.
4. Attempt to reclaim the same era/page for that nominator — it is rejected with `Error::<T>::AlreadyClaimed`, permanently losing that nominator's share of the era reward while the funds remain stuck in `staker_rewards_pot`.
