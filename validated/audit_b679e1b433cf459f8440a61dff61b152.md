### Title
Unprivileged repository DoS via shared per-repository concurrency queue exhaustion - ([File: internal/grpc/middleware/limithandler/middleware.go])

### Summary
Gitaly's RPC concurrency limiter, the mechanism the bug-report's "cheap repeated action fills a bounded per-target resource, denying other legitimate users" pattern maps onto, keys its admission queue purely by **RPC name + repository path**, not by caller identity. Any client with ordinary access to a shared repository (fetch/clone or a mutator RPC) can flood that queue with minimal-cost requests until `max_queue_size` is reached, after which *every other* caller targeting the same repository — regardless of their own privileges — is rejected with a `ResourceExhausted`/`LimitError` response until the attacker's requests drain.

### Finding Description
The concurrency limiter is configured per `[[concurrency]] rpc = "..."` entry and is scoped to a repository via `LimitConcurrencyByRepo`, which derives the limiting key solely from the request's target repository relative path: [1](#0-0) 

This key is used to build a `keyedConcurrencyLimiter` with a bounded `queueTokens` semaphore sized by `MaxQueueSize`. Once the queue is full, subsequent callers — with no distinction for who is calling — are rejected immediately: [2](#0-1) [3](#0-2) 

The documentation explicitly confirms the queue is shared "per repository" and that filling it causes an error for *all* subsequent requesters: [4](#0-3) 

Because the admission key has no caller/session/user dimension, an attacker who merely has read (fetch/clone) access to a repository that is also used by other legitimate users (a shared/public/forked repository, or one accessed concurrently by CI, mirroring, or multiple collaborators) can hold `max_per_repo` slots busy and fill the `max_queue_size` backlog with trivially cheap requests (e.g., a `PostUploadPackWithSidechannel` invocation that is deliberately slow-read/kept open) — this is structurally analogous to the reported `create_lock_for()` abuse: a cheap, repeatable, unprivileged action that consumes a bounded per-target resource slot on behalf of/affecting a specific victim-shared target, causing that target's legitimate operations to fail with a hard error the victim cannot resolve on their own.

Test coverage confirms the "queue full ⇒ reject subsequent caller" behavior independent of caller identity: [5](#0-4) 

### Impact Explanation
Any RPC configured with `[[concurrency]]` (e.g. `PostUploadPackWithSidechannel` used for clone/fetch, or `OptimizeRepository`) can be denial-of-serviced for all other users of the same shared repository by an attacker who only needs the same-or-lesser privilege level required to invoke that RPC (e.g., read/fetch access). This can block legitimate pushes, fetches, or CI/mirroring jobs against that repository for as long as the attacker sustains the flood, and — because `max_queue_wait`/`max_queue_size` are node-wide static configuration — the victim has no way to self-remediate other than waiting out the attacker or an admin intervening, which parallels the original report's "victim cannot resolve it themselves, must wait" characteristic.

### Likelihood Explanation
Likelihood is medium: it requires only ordinary, already-granted access to a repository shared by multiple actors (a very common scenario — public repos, forks pointing at the same physical relative path via object pools, or team repos with several collaborators/CI jobs), and requires no privilege escalation, no leaked token, and no MITM/malicious-peer position. It is limited to environments where `[[concurrency]]` limits are configured with a bounded `max_queue_size` (as recommended by Gitaly's own documentation), which is expected in production deployments per `doc/backpressure.md`.

### Recommendation
- Scope concurrency-limiting keys to include caller/session identity (or at minimum rate-limit per originating identity within the per-repository queue) so that a single caller cannot monopolize the entire per-repository queue budget.
- Consider a per-caller sub-limit (e.g., fraction of `max_queue_size`) within `ConcurrencyLimits` so no single client can starve the queue for all other legitimate callers of the same repository.
- Emit metrics/alerts (already partially present via `gitaly_requests_dropped_total`) keyed by caller identity where available, to detect and rate-limit abusive single-source flooding distinctly from genuine load spikes.

### Proof of Concept
1. Configure a tight queue for a shared repository operation:
```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
max_queue_size = 5
```
2. Attacker (holding only fetch access to the shared repository) opens `max_per_repo + max_queue_size` (here, 6) concurrent slow/blocking fetch requests against that repository, keeping each one open (e.g., by reading the response slowly).
3. A legitimate, unrelated user with proper access to the same repository issues a normal `git fetch`/`git clone`; the request is rejected immediately with:
```
rpc error: code = ResourceExhausted desc = maximum queue size reached
```
as demonstrated by the existing unit test pattern: [6](#0-5) 

This confirms an unprivileged, low-cost, repeatable action by one caller can deny a shared, bounded per-repository resource to other legitimate callers of the exact same repository.

```go
// acquire tries to acquire the semaphore. It may fail if the admission queue is full or if the max
// queue-time ticker ticks before acquiring a concurrency token.
func (sem *keyedConcurrencyLimiter) acquire(ctx context.Context, limitingKey string) (returnedErr error) {
	if sem.queueTokens != nil {
		// Try to acquire the queueing token. The queueing token is used to control how many
		// callers may wait for the concurrency token at the same time. If there are no more
		// queueing tokens then this indicates that the queue is full and we thus return an
		// error immediately.
		if err := sem.queueTokens.TryAcquire(); err != nil {
			return err
		}
```

**File:** doc/backpressure.md (L26-42)
```markdown
For example:

- One clone request comes in for repository "A" (a largish repository).
- While this RPC is executing, another request comes in for repository "A". Because
  `max_per_repo` is 1 in this case, the second request blocks until the first request
  is finished.

An in-memory queue of requests can build up in Gitaly that are waiting their turn. Because
this is a potential vector for a memory leak, two other values in the `[[concurrency]]`
configuration can prevent an unbounded in-memory queue of requests:

- `max_queue_wait` is the maximum amount of time a request can wait in the
  concurrency queue. When a request waits longer than this time, it returns
  an error to the client.
- `max_queue_size` is the maximum size the concurrency queue can grow for a
  given RPC. If a concurrency queue is at its maximum, subsequent requests
  return with an error. The queue size is per repository.
```

```go
func TestConcurrencyLimiter_queueLimit(t *testing.T) {
	queueLimit := 10
	ctx := testhelper.Context(t)
	monitorCh := make(chan struct{})
	monitor := &blockingQueueCounter{queuedCh: monitorCh}
	ch := make(chan struct{})
	limiter := NewConcurrencyLimiter(NewAdaptiveLimit("staticLimit", AdaptiveSetting{Initial: 1}), queueLimit, 0, monitor)

	// occupied with one live request that takes a long time to complete
	go func() {
		_, err := limiter.Limit(ctx, "key", func() (interface{}, error) {
			ch <- struct{}{}
			<-ch
			return nil, nil
		})
		require.NoError(t, err)
	}()

	<-monitorCh
	<-ch

	var wg sync.WaitGroup
	// fill up the queue
	for i := 0; i < queueLimit; i++ {
		wg.Add(1)
		go func() {
			_, err := limiter.Limit(ctx, "key", func() (interface{}, error) {
				return nil, nil
			})
			require.NoError(t, err)
			wg.Done()
		}()
	}

	var queued int
	for range monitorCh {
		queued++
		if queued == queueLimit {
			break
		}
	}

	errChan := make(chan error, 1)
	go func() {
		_, err := limiter.Limit(ctx, "key", func() (interface{}, error) {
			return nil, nil
		})
		errChan <- err
	}()

	err := <-errChan
	assert.Error(t, err)
```
