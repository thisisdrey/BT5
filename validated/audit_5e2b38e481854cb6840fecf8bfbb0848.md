Audit Report

## Title
Missing duplicate-registration guard in Snowbridge `register_token` allows repeated `RegisterForeignToken` bridge commands for an already-registered asset - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`, `bridges/snowbridge/pallets/system/src/lib.rs`)

## Summary
`do_register_token` and the v2 `register_token` extrinsic compute a `token_id` and only conditionally skip the `ForeignToNativeId` storage insert when the token is already known, but unconditionally proceed to build and send `Command::RegisterForeignToken` and emit `Event::RegisterToken` regardless of prior registration state. Because the v2 path is reachable by any unprivileged asset owner through `snowbridge-pallet-system-frontend::register_token`, an already-registered asset's owner can repeatedly trigger fresh `RegisterForeignToken` commands to the Ethereum Gateway with arbitrarily different metadata.

## Finding Description
In `bridges/snowbridge/pallets/system/src/lib.rs`, `do_register_token` (lines 476-509) computes `token_id` via `TokenIdOf::convert_location` and checks `if !ForeignToNativeId::<T>::contains_key(token_id)` only to guard the storage `insert` call [1](#0-0) . There is no `ensure!`/early return tied to that check — execution unconditionally continues to build `Command::RegisterForeignToken` and call `Self::send(...)`, then deposits `Event::RegisterToken` [2](#0-1) .

The identical pattern exists in `bridges/snowbridge/pallets/system-v2/src/lib.rs`'s `register_token` extrinsic (lines 211-249): the same `contains_key` check only guards the storage insert, and the function unconditionally sends `Command::RegisterForeignToken` and emits `RegisterToken` [3](#0-2) .

This v2 entrypoint is reachable from an unprivileged, ordinary user via `snowbridge-pallet-system-frontend`'s `register_token` extrinsic, gated by `T::RegisterTokenOrigin::ensure_origin(origin, &asset_location)` [4](#0-3) . On Asset Hub Westend, `RegisterTokenOrigin` is configured as `EitherOf<EitherOf<LocalAssetOwner<...>, ForeignAssetOwner<...>>, EnsureRootWithSuccess<...>>` [5](#0-4) , meaning any account that is the owner of the asset (local or foreign) — not just root/governance — can satisfy this origin check and call `register_token` on an already-registered asset repeatedly, paying only the fee-asset swap/burn each time.

The `contains_key` guard is therefore purely cosmetic with respect to the state-changing bridge action: the outbound message stream to the Ethereum Gateway and the emitted events diverge from the on-chain "already registered" state, allowing repeat calls with independently-chosen `metadata` (name/symbol/decimals) for the same `token_id`.

## Impact Explanation
This violates the intended one-time-registration invariant for `RegisterForeignToken` commands. The pallet's storage-level idempotency check (`ForeignToNativeId`) creates a false sense of protection while the actual bridge-affecting side effect — dispatching `Command::RegisterForeignToken` to the Ethereum Gateway — is not deduplicated. Because metadata is attacker-supplied on each call, an asset owner can repeatedly send differing name/symbol/decimals for the same already-registered `token_id`, causing the Ethereum-side Gateway/token contract logic (which likely assumes registration is a one-time event) to process duplicate or inconsistent registration commands. This matches the "message queues, bridge markers, receipts... must only advance after decode, dispatch, execution, and settlement succeed atomically" pivot — registration state and the outbound command stream diverge.

## Likelihood Explanation
High for reachability: any account satisfying `LocalAssetOwner`/`ForeignAssetOwner` for an asset it owns can call `register_token` again at will with no root or governance action required, as shown by the `RegisterTokenOrigin` configuration in `bridge_to_ethereum_config.rs`. The only cost is the standard fee-asset swap/burn, a normal paid action, not underpriced spam, but sufficient to repeatedly trigger the "already registered" branch and prove the guard is non-blocking for the message-send path.

## Recommendation
Add an explicit guard that turns "already registered" into a hard error before building/sending the command, in both `do_register_token` (`bridges/snowbridge/pallets/system/src/lib.rs`) and `register_token` (`bridges/snowbridge/pallets/system-v2/src/lib.rs`):
```rust
ensure!(!ForeignToNativeId::<T>::contains_key(token_id), Error::<T>::TokenAlreadyRegistered);
ForeignToNativeId::<T>::insert(token_id, location.clone());
```
so `Command::RegisterForeignToken` is dispatched and `RegisterToken` is emitted only on first registration, matching the storage-level dedup intent.

## Proof of Concept
1. Asset owner `A` calls `system-frontend::register_token(asset_id = X, metadata = M1, fee_asset = F)`, satisfying `RegisterTokenOrigin` as owner of `X`. This transacts into `system-v2::register_token`, which sets `ForeignToNativeId[token_id(X)]` and sends `Command::RegisterForeignToken{token_id, name: M1.name, ...}` to Ethereum.
2. `A` calls the same extrinsic again with `metadata = M2` (still owning `X`). `T::RegisterTokenOrigin::ensure_origin` succeeds again (owner check only, no "already registered" check). In `system-v2::register_token`, `ForeignToNativeId::contains_key(token_id)` is `true` so the insert is skipped, but the function still builds and sends `Command::RegisterForeignToken{token_id, name: M2.name, ...}` and emits `RegisterToken` again, burning fee `F` a second time.
3. Repeating step 2 produces an unbounded number of `RegisterForeignToken` commands for the same `token_id` with independently chosen metadata, delivered to the Ethereum Gateway despite the asset already being registered on-chain.
