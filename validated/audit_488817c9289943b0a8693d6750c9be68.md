## Title
Unbounded `AssetIssueStore`/`ExchangeStore` growth via cheap unprivileged transactions enables DOS of unpaginated list APIs - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
Any unprivileged account can call `AssetIssueContract` (asset issuance) or `ExchangeCreateContract` (exchange creation) transactions to keep appending entries into `AssetIssueStore`/`ExchangeV2Store` and `ExchangeStore` with no cap on the total number of assets/exchanges a chain (or single account, subject only to a fixed cost) can create. These stores are exposed through non-paginated wallet query APIs — `Wallet.getAssetIssueList()` and `Wallet.getExchangeList()` — that unconditionally load, and in the exchange case sort, the *entire* store into memory on every call.

### Finding Description
`Wallet.getAssetIssueList()` iterates and materializes the full `AssetIssueStore`/`AssetIssueV2Store` contents with no offset/limit, unlike its paginated counterpart: [1](#0-0) 

`Wallet.getExchangeList()` similarly loads and sorts (`ExchangeStore.getAllExchanges()` sorts by creation time) the entire exchange store with no bound: [2](#0-1) [3](#0-2) 

Both entry points are reachable anonymously via HTTP (`/wallet/getassetissuelist`, `/wallet/listexchanges`) and gRPC (`GetAssetIssueList`, `ListExchanges`): [4](#0-3) [5](#0-4) 

Meanwhile, the backing stores can be grown without limit by any account issuing `AssetIssueCreateContract` or `ExchangeCreateContract` transactions: [6](#0-5) 

The `ExchangeCreateActuator` only validates token balances and a fixed `calcFee()`, and `AssetIssueActuator` similarly requires only a name/parameter validation and a fixed issuance fee — neither imposes any bound on the total number of exchanges/assets in the store. This is directly analogous to the reported `Factory.deploySurgePool()` issue: an externally callable, unprivileged function repeatedly appends to a globally-shared unbounded array/store, and a later, non-privileged read path (`pools` array iteration analog = `getAllAssetIssues()`/`getAllExchanges()`) must scan the entire, attacker-inflatable collection.

This contrasts with the codebase's own established mitigation pattern seen elsewhere (e.g. `MarketSellAssetActuator.MAX_ACTIVE_ORDER_NUM`, `AssetIssueActuator`'s frozen-supply-list-length check, and `AssetIssueStore.getAssetIssuesPaginated()`'s `ASSET_ISSUE_COUNT_LIMIT_MAX`/`EXCHANGE_COUNT_LIMIT_MAX` caps used by the *paginated* query variants) — showing the project is aware unbounded growth/iteration is a problem, but the un-paginated `getAssetIssueList()`/`getExchangeList()` (and their gRPC/HTTP wrappers) were left without the same protection.

### Impact Explanation
An attacker can drive `AssetIssueStore`/`ExchangeStore` to a very large size over time by issuing many cheap creation transactions. Every subsequent unauthenticated call to `getassetissuelist`/`listexchanges` (HTTP), or `GetAssetIssueList`/`ListExchanges` (gRPC), forces the node to iterate, deserialize, and (for exchanges) sort the entire store on every single request. This is a query-path resource-exhaustion issue: repeated/concurrent calls to these unbounded endpoints can consume excessive CPU/memory on full nodes serving these APIs, potentially degrading or crashing the node's API-serving capability — matching the "API the node can no longer serve" acceptance criterion.

### Likelihood Explanation
Likelihood is Medium: creating an asset or exchange has a real but bounded TRX cost, so an attacker must spend some capital to inflate the collection size, and this happens over an extended period rather than instantly. However, once the store is large (which can happen organically over the chain's life, or be accelerated by a well-funded attacker), every unauthenticated caller of the un-paginated endpoints repeatedly pays the full iteration/sort cost, so the DOS surface persists indefinitely regardless of how the size was reached.

### Recommendation
- Enforce the same limit used in the paginated variants (`ASSET_ISSUE_COUNT_LIMIT_MAX` / `EXCHANGE_COUNT_LIMIT_MAX`) on `getAssetIssueList()`/`getExchangeList()`, or deprecate/remove the un-paginated APIs in favor of the paginated ones with enforced default/maximum page sizes.
- Consider maintaining an incrementally sorted structure for exchanges instead of re-sorting the whole `ExchangeStore` on every `getAllExchanges()` call.
- Consider adding an overall cap (or steeply increasing marginal cost) on the number of assets/exchanges creatable, similar to `MAX_ACTIVE_ORDER_NUM` in `MarketSellAssetActuator`.

### Proof of Concept
1. Repeatedly submit `AssetIssueContract` (or `ExchangeCreateContract`) transactions from one or more accounts, each paying the fixed issuance/creation fee, to grow `AssetIssueStore`/`ExchangeStore` to a very large number of entries.
2. Call the unauthenticated HTTP endpoint `GET /wallet/getassetissuelist` (backed by `Wallet.getAssetIssueList()`, [1](#0-0) ) or `GET /wallet/listexchanges` (backed by `Wallet.getExchangeList()`/`ExchangeStore.getAllExchanges()`, [7](#0-6) ) repeatedly/concurrently.
3. Observe that each call scans (and for exchanges, sorts) the full store, with cost proportional to the attacker-inflated collection size, degrading the node's ability to serve this and other API requests.

        .map(Map.Entry::getValue)
        .sorted(
            (ExchangeCapsule a, ExchangeCapsule b) -> a.getCreateTime() <= b.getCreateTime() ? 1
                : -1)
