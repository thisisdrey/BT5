### Title
Unprivileged attacker can permanently fill a victim's per-account token lists via dust `deposit`/`transfer`, DoS-ing new collateral deposits, new borrows, and token receipts (File: contracts/Pool.sol)

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` on the combined per-account lists `depositTokensOfAccount` + `debtTokensOfAccount`. Any first-time balance of a deposit token (mint via `deposit`, or receipt via `transfer`/`seize`) calls `Pool.addToDepositTokensOfAccount(recipient)` which reverts `UserReachedMaxTokens()` when the list is full. Because `DepositToken.deposit(uint256, onBehalfOf_)` and `DepositToken.transfer` are permissionless and the recipient is arbitrary, an attacker can cheaply stuff a victim's list with dust positions the victim never asked for, after which every operation that would add a new token type to that account reverts. [1](#0-0) [2](#0-1) 

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens()` when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` before adding a new entry. [3](#0-2) 
- `DepositToken._mint` registers the token for `account_` whenever prior balance is `0` and `amount_ > 0`; `deposit()` accepts an arbitrary `onBehalfOf_` beneficiary, so the attacker can mint dust deposit tokens directly onto any victim. [4](#0-3) [5](#0-4) 
- `DepositToken._transfer` does the same registration for any recipient of a plain `transfer`, `transferFrom`, or pool-driven `seize`. [6](#0-5) 
- `DebtToken._mint` calls `pool.addToDebtTokensOfAccount(account_)` on first borrow; `issue()` and `mint()` therefore revert for the victim once the shared list is full, even though the victim has ample unlocked collateral. [7](#0-6) [8](#0-7) 
- The attacker pays only dust amounts of underlying (each `deposit(amount_, victim)` pulls `amount_` of underlying from the attacker to the Treasury and mints the victim 1 wei of msdToken). Repeating this across every registered deposit token — plus any debt tokens the victim already holds — pushes the victim to the cap.

### Impact Explanation
Once the victim's combined list reaches 30 entries:
- `deposit(amount, victim)` for any deposit token the victim doesn't already hold reverts — third parties (zaps, gateways like `NativeTokenGateway`/`VesperGateway` flows that deposit on behalf, or donors) cannot credit the victim.
- `transfer`/`transferFrom`/`seize` of any deposit token the victim doesn't hold reverts — the victim cannot receive collateral tokens, including seized collateral routed to them.
- `DebtToken.issue`/`mint` for any new synthetic reverts — the victim cannot open new borrowing positions or complete `SmartFarmingManager.leverage` flows that mint a new debt token type to the position account.
- The DoS persists until the victim fully withdraws a dust position (balance → 0 removes the entry), which requires the victim to spend gas clearing up to 30 attacker-planted dust entries before resuming normal protocol use — temporary freezing of protocol functionality/funds proportional to attack cost that is entirely borne by the victim. [9](#0-8) 

### Likelihood Explanation
- Fully unprivileged: `DepositToken.deposit` requires only underlying balance + approval; `transfer` requires only unlocked msdToken balance. No privileged role, oracle manipulation, or governance action is involved.
- Cost is dust-level (e.g., `1` wei of each underlying per deposit, minus deposit fees) times the number of registered deposit tokens; deployments list ~10–30 deposit tokens per pool (e.g., mainnet `Pool1`/`Pool2` have USDC, DAI, FRAX, sfrxETH, vaETH, vaCBETH, etc.).
- No existing defense stops it: `onlyIfAdditionWillNotReachMaxTokens` protects the list integrity but not the victim; there is no opt-in, minimum-amount, or sender-consent check on `onBehalfOf_` deposits or token receipts, and `_revertIfLocked` only constrains the sender's balance, not the recipient. [10](#0-9) 
- Caveat: if a pool has fewer than 30 total deposit+debt tokens, the attacker must combine dust deposits with tokens the victim legitimately acquires; the attack is strongest on pools near the cap or against victims who already hold many token types.

### Recommendation
- Track a real position threshold: only register a token in `depositTokensOfAccount`/`debtTokensOfAccount` once the balance exceeds a meaningful minimum (e.g., a USD floor via the oracle), or keep dust balances out of the accounting list.
- Alternatively, add an opt-in/whitelist mechanism for `onBehalfOf_` deposits and inbound transfers, or auto-sweep dust deposits below a floor to the caller.
- Alternatively, raise/relax `MAX_TOKENS_PER_USER` semantics so that forced additions beyond the cap fail only for the *attacker's* action — e.g., let `seize` and `issue` succeed by auto-removing the smallest dust entry or by crediting via an internal balance not requiring list registration.

### Proof of Concept
Hardhat fork sketch against a deployed `Pool` + its `DepositToken`s (e.g., mainnet `Pool1`):

```ts
// 1. Impersonate/whale-fund attacker with tiny amounts of each underlying.
for (const dt of depositTokens) {
  const underlying = await ethers.getContractAt("IERC20", await dt.underlying());
  await underlying.connect(attacker).approve(dt.address, 1);
  // pushes `dt` onto victim's depositTokensOfAccount for 1 wei of underlying
  await dt.connect(attacker).deposit(1, victim.address);
}
// victim's list is now full of attacker-planted dust entries.

// 2. Any new collateral receipt to victim reverts:
await expect(
  someOtherDepositToken.connect(holder).transfer(victim.address, amount)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

// 3. Victim cannot issue a new synthetic (first-time debt token):
await expect(
  newDebtToken.connect(victim).issue(amount, victim.address)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

// 4. Victim cannot receive deposit-on-behalf of a new collateral:
await expect(
  newDepositToken.connect(donor).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

// 5. Recovery requires victim to fully withdraw each dusted collateral
//    (burning balance to 0 removes the list entry), paying gas per entry.
```

The invariant broken is liveness/availability of core flows (deposit, transfer, seize, issue) for a targeted account, mirroring the CVE's availability-impact class: a low-privilege network attacker causes a repeatable, reverted-state "hang" of the victim's position management at dust-level cost.
