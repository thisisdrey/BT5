### Title
Dust transfer fills victim's `depositTokensOfAccount` list, permanently DoS-ing new deposits and collateralization recovery - (File: contracts/DepositToken.sol)

### Summary
`DepositToken._transfer` unconditionally registers the recipient in the pool's per-account deposit-token list via `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient previously held a zero balance. The list is bounded by `MAX_TOKENS_PER_USER` because `Pool.debtPositionOf` iterates it. An unprivileged attacker can therefore "poison" a victim's slot budget by transferring 1 wei of many different `msdTOKEN`s to the victim, causing every subsequent `deposit`, `transfer`/`transferFrom`, `seize`, or `_mint` that would add a *new* deposit token for the victim to revert — analogous to the Xen bug where a local, unprivileged actor injects a fault (async abort) that crashes the host's ability to process further work.

### Finding Description
In `DepositToken._transfer` and `DepositToken._mint`, the code adds the token to the recipient's account list on first receipt:

```solidity
// contracts/DepositToken.sol
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
...
if (_balanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(account_);
}
```

`addToDepositTokensOfAccount` enforces `MAX_TOKENS_PER_USER` (the cap that bounds the loop inside `Pool.debtPositionOf`/`depositOf`) and reverts once the account's list is full. Key properties that make this attacker-reachable:

- `transfer`/`transferFrom` only require the *sender's* unlocked balance (`_revertIfLocked(sender_, amount_)`); there is no consent from the recipient and no minimum amount — 1 wei of each deposit token suffices.
- `deposit` accepts an arbitrary `onBehalfOf_`, so even minting dust directly to a victim works the same way.
- Removal only happens when the recipient's balance of that specific token returns to zero, so the attacker controls fill-up and the victim must actively spend gas to evict entries.

### Impact Explanation
Once the victim's list is saturated:

- `deposit(newCollateral, victim)` reverts inside `_mint` → `addToDepositTokensOfAccount`, so the victim cannot add new collateral types. For a borrower near the liquidation threshold this blocks the standard deleveraging/recapitalization path and can force an otherwise avoidable liquidation — an availability fault induced by an unprivileged party, matching the "local user panics the host" bug class.
- Any `transfer`/`transferFrom`/`seize` sending the victim a deposit token they don't already hold reverts, breaking integrations (zaps, SmartFarmingManager flows, liquidation payouts routed to the account).
- The DoS is griefing-cheap: the attacker's only cost is dust amounts of already-listed collateral (deposited once, then distributed).

Victim recovery requires manually transferring the dust tokens away (or depositing/withdrawing to zero them), so the freeze is temporary and bounded by the victim's willingness to pay gas — qualifying as temporary freezing/blocking of protocol functionality rather than permanent loss.

### Likelihood Explanation
- Fully permissionless: only needs a normal deposit + ERC-20 transfers; no governor, keeper, oracle, or bridge role.
- Cost scales with the number of distinct deposit tokens needed to reach `MAX_TOKENS_PER_USER`; on pools with few listed collaterals the attack is impractical, which lowers likelihood on current deployments but does not fix the code-level flaw (new collaterals are added over time, and the cap also applies to victims holding many tokens already).
- Rules exclusion check: this is not a gas/unbounded-loop DoS — the loop is bounded precisely *because* the cap exists; the fault is injected by a crafted input (dust transfer), which is the intended analog.

### Recommendation
- Make `addToDepositTokensOfAccount` overflow fail-soft for non-minting paths, or require a minimum transfer amount / recipient opt-in for list registration.
- Alternatively, let `debtPositionOf` skip zero-or-dust balances so the cap can't be consumed by worthless entries, or cap by USD value rather than token count.
