### Title
Unauthenticated `RecvError` packets allow remote tunnel state poisoning / DoS - ([File: outside.go])

### Summary
The external report describes `mint_stable_coin` performing a privileged, state-changing operation (minting coins) without verifying that the caller is the entity authorized to trigger it (the target collateral contract). The equivalent bug class in this codebase is `Interface.handleRecvError`, which performs a privileged, state-changing operation (tearing down an established tunnel and deleting its handshake/host-map state) based only on a cleartext, unauthenticated header field and a spoofable UDP source address — never on a certificate, handshake completion, or any cryptographic proof of sender identity.

### Finding Description
In `outside.go`, `readOutsidePackets` dispatches `header.RecvError` packets straight to `f.handleRecvError` before any certificate/hostinfo/decrypt checks are performed: [1](#0-0) 

`handleRecvError` then looks up the hostinfo purely by `h.RemoteIndex` (a 32-bit index that travels in the cleartext header of every packet on the wire, and is therefore visible to any on-path observer or recoverable by simple probing) and "authenticates" the sender only by comparing the packet's source UDP address to the hostinfo's currently known remote address: [2](#0-1) 

If the (guessable/observable) index matches and the source IP:port matches the peer's last-known address, the code unconditionally calls `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` — no certificate is checked, no handshake is required, and no cryptographic signature or MAC binds the packet to the claimed sender. `closeTunnel` deletes the host-map entry and, if it's the last tunnel for that peer, clears lighthouse state: [3](#0-2) 

This mirrors the report's root cause exactly: a state-mutating entry point (`mint_stable_coin` there, `handleRecvError`/`closeTunnel` here) that lacks any check that the caller is the party actually entitled to invoke it (the collateral contract there; the genuine, certificate-holding tunnel peer here). UDP source addresses are trivially spoofable (no TCP-style 3-way handshake, no cert binding to the underlay address at this stage), and `RemoteIndex` is not a secret — it appears in cleartext in every packet exchanged on that tunnel, including ordinary traffic an attacker can observe on-path or infer.

### Impact Explanation
An attacker who does not hold a CA-signed certificate — and thus can never complete a legitimate Nebula handshake — can still terminate any two peers' established, encrypted tunnel and wipe the host-map/handshake state for it, by:
1. Observing (or otherwise obtaining) the target's `RemoteIndex` and its peer's current UDP `addr:port` from any packet on that tunnel that crosses a network segment the attacker can see, or by off-path guessing on a small enough index space, and
2. Spoofing a UDP packet with `header.RecvError` type, that `RemoteIndex`, and a forged source address equal to the currently known genuine peer address.

This is a remote, unauthenticated state-poisoning/denial-of-service primitive: it forces immediate tunnel teardown (matching the original report's BVSS vector `D:C` — Denial of Service: Complete, `AC:L`/`AX:L` — low complexity, low access, `AO:A` — adjacent attacker, no valid credential required). While it does not by itself grant confidentiality/integrity compromise, forcing repeated teardown/rehandshake also creates a window during which a wrong-responder or evil-lighthouse race can be re-attempted, and is a persistent, cheap disruption of any Nebula overlay reachable to a spoof-capable attacker.

### Likelihood Explanation
Likelihood is moderate-to-high on networks where UDP source-address spoofing is possible (many networks do not enforce BCP38/ingress filtering) and where the attacker has visibility into cleartext header traffic (LAN segments, some cloud/NAT topologies, or simply by being a previously-blocked/evicted former peer who still remembers the index and address). No certificate, PSK, or successful handshake of any kind is required to send the forged packet — only knowledge of the RemoteIndex, which is not protected as a secret in the protocol.

### Recommendation
Do not allow `RecvError` (or any other unencrypted/pre-handshake message type) to trigger destructive state changes based solely on an index match plus a spoofable UDP source-address comparison. At minimum:
- Require some proof tied to the current cryptographic session (e.g., a MAC keyed by the established session key, or requiring the RecvError to be carried inside the encrypted channel where feasible) before acting on it.
- Rate-limit / cool down repeated `RecvError`-triggered teardowns per remote address and per index to blunt spoofed floods.
- Consider treating an out-of-session `RecvError` as advisory only (e.g., trigger a re-handshake attempt) rather than an immediate authoritative `closeTunnel` + `DeleteHostInfo`.

### Proof of Concept
1. Establish (or observe) a Nebula tunnel between hosts A and B; sniff/derive B's `RemoteIndex` (as known by A) and B's current UDP `addr:port` from any header on the wire (cleartext).
2. Attacker (holding no certificate, unable to complete any Nebula handshake) crafts a UDP packet with `header.Version = header.Version`, `header.Type = header.RecvError`, `RemoteIndex` = B's observed index, and source address spoofed to match B's known `addr:port`, and sends it to A.
3. A's `readOutsidePackets` routes it directly to `handleRecvError` (outside.go:82) before any decryption/cert check.
4. `handleRecvError` finds the hostinfo via `QueryReverseIndex`, sees `hr == addr` (spoofed match), and calls `f.closeTunnel(hostinfo)` plus `handshakeManager.DeleteHostInfo(hostinfo)` — tearing down A's legitimate tunnel to B without B's or any certificate holder's involvement.

Note: exhaustive confirmation of `QueryReverseIndex`'s exact index semantics (i.e., whether it is scoped per-remote or globally unique) and of `acceptRecvErrorConfig.ShouldRecvError`'s default rate-limiting behavior could not be fully verified within the available index snippets; a Devin session with full repository access should confirm these details (`hostmap.go`'s `QueryReverseIndex` and `interface.go`'s `RecvErrorConfig`) before finalizing a fix.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
