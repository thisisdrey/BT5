### Title
Whale can grief all inbound cross-chain transfers by saturating `maxBridgedInSupply` - ([File: contracts/SyntheticToken.sol](contracts/SyntheticToken.sol))

### Summary
`SyntheticToken` enforces a global `maxBridgedInSupply` cap on tokens minted via the LayerZero `ProxyOFT`. An unprivileged whale can bridge tokens in until `bridgedInSupply() == maxBridgedInSupply`, after which every subsequent inbound bridge message reverts inside `mint()` → `_mint()` with `SurpassMaxBridgingSupply`. Other users' inbound transfers are parked as failed LayerZero messages until the attacker backs off or the governor raises the cap — a temporary freezing of bridged funds / liveness DoS, the same bug class as the Axelar flow-limit report.

### Finding Description
Inbound bridging path: `ProxyOFT.sendFrom` (source chain) → LayerZero → `_creditTo` → `syntheticToken.mint(toAddress_, amount_)` [1](#0-0) . `mint` reaches `_mint`, which increments `totalBridgedIn` when the caller is the `proxyOFT` and reverts if `bridgedInSupply() > maxBridgedInSupply` [2](#0-1) .

The caps are global and shared across all users (`totalBridgedIn`, `totalBridgedOut`, `maxBridgedInSupply`, `maxBridgedOutSupply` in `contracts/storage/SyntheticTokenStorage.sol:64-79`), with no per-account or per-epoch limit. The docs acknowledge the intended liveness trade-off: "When reach this value, bridging in will only be possible after some bridging out" (`docs/emergency-flags.md:27`). An attacker who holds a large synth balance on a supported source chain calls `sendFrom` repeatedly until the cap is saturated [3](#0-2) . From that point, all victims' inbound `_creditTo` calls revert.

Because `LzApp` (inherited via `ComposableOFTCoreUpgradeable`) stores reverted payloads as failed messages, victims' tokens are neither delivered nor lost — they sit in `failedMessages` and can only be retried after capacity frees. So the invariant broken is liveness/bridge conservation in the temporary sense: user funds are frozen in the LZ queue while the attacker occupies the entire cap. The attacker can re-saturate each time capacity frees (bridging out then back in), sustaining the DoS cheaply — only LayerZero messaging fees on cheap L2s, since the bridged tokens are recoverable.

`SenderIsNotTheOwner`, `BridgingIsPaused`, and `DestinationChainNotAllowed` checks in `_debitFrom` do not stop this [4](#0-3) . Governor can mitigate by calling `updateMaxBridgedInSupply`, but that is reactive, not preventive.

### Impact Explanation
Temporary freezing of funds / temporary unavailability of the bridging feature for all users of a given `SyntheticToken`. Affected users' bridged assets remain stuck as failed LZ messages until the attacker releases cap space or governance intervenes — matching the "function of the protocol or its availability could be impacted" criterion.

### Likelihood Explanation
Requires only an unprivileged EOA holding a large synth position on one supported chain plus LZ native fees. Cheap on L2s; the position itself is recoverable by bridging back (which also frees `bridgedOut` headroom on the source). Likelihood is bounded by the cap size relative to attacker holdings, so it's a whale-only griefing vector.

### Recommendation
- Add a per-account (or per-message-size-aware) inbound quota, or a decaying/epoch-based flow limit so a single actor cannot hold the entire capacity.
- Alternatively, charge a bps fee on bridge-in volume that scales with cap utilization, making sustained saturation expensive.
- At minimum, emit monitoring events and document that operators must actively raise `maxBridgedInSupply`/`maxBridgedOutSupply` during saturation events.

### Proof of Concept
Hardhat fork sketch (Base, where msUSD `SyntheticToken` + `ProxyOFT` are deployed):

```ts
// Fork Base mainnet; attacker holds >= (maxBridgedInSupply - bridgedInSupply) msUSD on Optimism.
const synth = await ethers.getContractAt("SyntheticToken", SYNTH_ADDR);
const oft   = await ethers.getContractAt("ProxyOFT", OFT_ADDR);

const gap = (await synth.maxBridgedInSupply()).sub(await synth.bridgedInSupply());

// 1) On source chain, attacker calls sendFrom until inbound supply hits cap
await oft.sendFrom(attacker.address, BASE_LZ_ID, attacker.address, gap, { value: fee });

// 2) Deliver LZ message on destination -> mint succeeds, bridgedInSupply == cap

// 3) Victim bridges any amount in; destination _creditTo -> _mint reverts
//    with SurpassMaxBridgingSupply; message lands in failedMessages (LzApp)
await expect(retryVictimMessage()).to.be.revertedWithCustomError(synth, "SurpassMaxBridgingSupply");

// 4) Attacker can keep re-saturating: bridge out (burns, raises headroom), then in again.
```

The repo's own tests confirm the revert surface: `test/E2E.base.test.ts:603-644` shows bridging reverts with `SurpassMaxBridgingSupply` once the cap is reached.
