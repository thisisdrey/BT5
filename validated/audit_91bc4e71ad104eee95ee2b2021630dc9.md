## Title
Snowbridge relayer rewards are irrevocably deleted on mere XCM dispatch, before the cross-chain deposit is confirmed, permanently losing relayer funds on remote execution failure - (File: `bridges/snowbridge/primitives/core/src/reward.rs`)

## Summary
`PayAccountOnLocation::pay_reward` builds an XCM program performing `ReserveAssetDeposited` + `DepositAsset` on AssetHub and returns `Ok(())` as soon as `XcmSender::deliver(ticket)` succeeds — i.e., once the message is queued for delivery, not once AssetHub has actually credited the beneficiary. `pallet_bridge_relayers::do_claim_rewards` treats this `Ok(())` as final settlement, permanently deleting the `RelayerRewards` ledger entry via `maybe_reward.take()` and emitting `RewardPaid` before any confirmation that the remote `DepositAsset` succeeded.

## Finding Description
`PayAccountOnLocation::pay_reward` [1](#0-0)  constructs an XCM program (`UnpaidExecution`, `DescendOrigin`, `UniversalOrigin`, `ReserveAssetDeposited`, `DepositAsset{AllCounted(1), beneficiary}`) and only checks `validate_send`, `charge_fees`, and `deliver` — all local, pre-execution steps. No `SetAssetClaimer` instruction is included, and there is no feedback path from AssetHub back to BridgeHub confirming that `DepositAsset` actually credited `beneficiary`.

`do_claim_rewards` in `pallet-bridge-relayers` [2](#0-1)  calls `T::PaymentProcedure::pay_reward(...)` inside `try_mutate_exists`; on `Ok(())` — which occurs purely on successful local dispatch — the reward entry is permanently removed via `maybe_reward.take()` and `RewardPaid` is emitted. This is confirmed to be the actual wiring for the Snowbridge reward path via `BridgeRewardPayer::pay_reward` in `bridge_common_config.rs`, which routes `BridgeReward::Snowbridge` claims directly to `PayAccountOnLocation::pay_reward` [3](#0-2) .

If the remote `DepositAsset` later fails on AssetHub (e.g., beneficiary below existential deposit, non-routable location, or transient execution-time conditions unrelated to the sender), the reserve-deposited assets are trapped with no explicit claimer set by the program. Meanwhile, on BridgeHub, the `RelayerRewards` entry is already gone and `RewardPaid` has already fired — there is no reconciliation, retry, or re-claim mechanism in the codebase for this scenario.

I confirmed this is the intended integration flow: the emulated test `claim_rewards_works` in `snowbridge_v2_rewards.rs` [4](#0-3)  shows `RewardPaid` is emitted on BridgeHub immediately upon `claim_rewards_to` returning `Ok`, and the actual `ForeignAssets::Deposited` event on AssetHub is only checked afterward as a separate, decoupled step — with no code tying the two together or allowing recovery if the AssetHub-side deposit fails.

## Impact Explanation
An honest relayer who has a `RelayerRewards` entry can lose the reward permanently if `DepositAsset` fails on AssetHub for any reason unrelated to the sender (beneficiary below ED, congestion, or other transient execution failure) after the BridgeHub-side message was validly dispatched. Since the ledger entry is deleted before remote settlement is confirmed, this falls under "permanent user-fund or bridge-state lock" for bridge relayer compensation on Snowbridge/BridgeHub code.

## Likelihood Explanation
No privileged actor or malicious peer is required. Any relayer calling the public `claim_rewards_to` extrinsic with a `BridgeRewardBeneficiaries::AssetHubLocation` whose resolved account cannot receive the deposit (e.g., below ED) triggers this path unconditionally, since `do_claim_rewards` finalizes settlement purely based on local dispatch success for all `BridgeReward::Snowbridge` claims.

## Recommendation
Do not delete the `RelayerRewards` entry based solely on `XcmSender::deliver` succeeding. Either add an explicit `SetAssetClaimer` to the reward-payment XCM program so trapped assets remain recoverable and add a reconciliation/retry mechanism tied to confirmed remote execution before final ledger removal, or retain a "pending settlement" marker until execution is confirmed so the relayer can re-claim if the remote deposit does not land.

## Proof of Concept
1. Relayer accrues a Snowbridge reward via `register_reward`.
2. Relayer calls `claim_rewards_to(BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(loc))` where `loc` resolves to an account that cannot receive the deposit on AssetHub (e.g., below existential deposit).
3. `BridgeRewardPayer::pay_reward` → `PayAccountOnLocation::pay_reward` succeeds locally (`validate_send`, `charge_fees`, `deliver` all `Ok`), so `do_claim_rewards` deletes the `RelayerRewards` entry and emits `RewardPaid`.
4. On AssetHub, `DepositAsset` fails at execution time; the reserve-deposited asset is trapped with no explicit claimer.
5. Result: `RelayerRewards` entry is gone on BridgeHub with no re-claim path, and funds are trapped/unrecoverable on AssetHub — permanent loss despite the local `RewardPaid` success signal.

		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,

		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![

			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),

		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
