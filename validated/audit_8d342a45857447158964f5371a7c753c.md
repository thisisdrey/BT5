### Title
Unbounded per-filter result queue in JSON-RPC log/block filters allows memory-exhaustion DoS - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/filters/FilterResult.java`)

### Summary
The CVE describes curl auto-acknowledging WebSocket PING frames into an unbounded buffer, letting a peer exhaust memory because there is no cap on unacknowledged-frame storage. The analogous pattern in java-tron is the JSON-RPC `eth_newFilter` / `eth_newBlockFilter` filter-tracking mechanism: each filter accumulates matched blocks/logs into a plain `LinkedBlockingQueue` with no capacity bound, and the queue is only drained when the client calls `eth_getFilterChanges`. An anonymous JSON-RPC client can create such a filter and simply never poll it while the chain (or the attacker's own contract activity) keeps appending elements, growing the queue without limit until the process runs out of memory.

### Finding Description
`FilterResult` is the base class backing both block and log filters and stores results in an unbounded `BlockingQueue`: [1](#0-0) 

`BlockFilterAndResult` and `LogFilterAndResult` both instantiate this field as a plain `LinkedBlockingQueue<>()`, which has no maximum capacity: [2](#0-1) [3](#0-2) 

The only guard is on the *number of filter objects* that can be created, not on the size of each filter's internal result queue: [4](#0-3) 

Every processed block triggers `postBlockFilter`/`postLogsFilter` in `Manager`, which push into `filterCapsuleQueue`, subsequently drained by `filterProcessLoop` calling `tronJsonRpcImpl.handleLogsFilter`/`handleBLockFilter`: [5](#0-4) [6](#0-5) 

`handleLogsFilter` then iterates all open (non-expired) filters and unconditionally appends every matched log element into the filter's queue, with no bound check other than an entry TTL expiry that is only refreshed when the client actually reads results: [7](#0-6) [8](#0-7) 

Because a filter's expiry timer is only reset on `getFilterResult`/`popAll`, an attacker who never calls `eth_getFilterChanges` (or a filter that matches broadly, e.g., an empty/all-address log filter) accumulates every matching log element for the remainder of the filter's lifetime with no per-queue upper bound, and can additionally amplify growth by deploying a contract that emits many `LOG*` events per transaction (still governed only by normal energy limits, which permit large log volumes per block).

### Impact Explanation
Sustained, unbounded growth of the log/block filter result queues consumes heap memory tied to matched chain data with no cap, independent of how many bytes the client has actually consumed. On a JSON-RPC-enabled full/solidity node (`jsonrpc.httpFullNodeEnable` / `jsonrpc.httpSolidityNodeEnable`), an anonymous client can open a broad filter and withhold polling while driving log-generating transactions, causing the JVM heap to grow until the node experiences GC pressure, OOM, or crash — denying the JSON-RPC API (and potentially the whole node process) to all users. This matches the "API the node can no longer serve" / "node crash" acceptance criteria.

### Likelihood Explanation
Reaching this path requires only a JSON-RPC-enabled node and no special privileges: any anonymous client can call `eth_newFilter`/`eth_newBlockFilter` and then simply stop polling. Amplifying it further by generating heavy log volume only requires deploying and calling a smart contract, which is available to any unprivileged contract deployer. The bug requires no witness/validator compromise and no p2p manipulation, making it directly reachable from the public JSON-RPC surface.

### Recommendation
Add a hard maximum size to the per-filter `BlockingQueue` in `FilterResult`/`BlockFilterAndResult`/`LogFilterAndResult` (e.g., bounded `LinkedBlockingQueue<>(MAX_FILTER_RESULT_SIZE)`), and drop/expire the filter (or stop accepting new matches, logging a warning) once the bound is hit, mirroring the pattern already used for the filter-count limit in `newBlockFilter`.

### Proof of Concept
1. Enable JSON-RPC on a full node (`jsonrpc.httpFullNodeEnable = true`).
2. As an anonymous client, call `eth_newFilter` with a broad filter (no `address`/`topics` restriction, wide `fromBlock`/`toBlock`) to obtain a `filterId`.
3. Never call `eth_getFilterChanges` for that `filterId`.
4. As an unprivileged contract deployer, deploy and repeatedly invoke a contract that emits many `LOG4` events per call to maximize per-block matched entries.
5. Observe that `LogFilterAndResult.result` for the open filter (via `handleLogsFilter` → `processLogFilterEntry` → `logFilterAndResult.getResult().addAll(...)`) grows without bound across blocks until the process exhausts memory, since nothing caps queue size and the filter only expires if left completely unpolled beyond `EXPIRE_SECONDS` — trivially avoided by periodically issuing a cheap poll that resets the timer while the queue keeps growing.

public abstract class FilterResult<T> {

  private long expireTimeStamp;

  @Getter
  protected BlockingQueue<T> result;

  public void updateExpireTime() {
    expireTimeStamp = System.currentTimeMillis() + TronJsonRpcImpl.EXPIRE_SECONDS * 1000;
  }

  public boolean isExpire() {
    return expireTimeStamp < System.currentTimeMillis();
  }

  public abstract void add(T t);

  public abstract List<T> popAll();
}
