### Title
Non-atomic check-then-put on Sapling nullifier allows shielded double-spend via concurrent transaction execution - (File: actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java)

### Summary
`ShieldedTransferActuator.executeShielded()` enforces single-use consumption of a Sapling spend nullifier using a non-atomic "check-then-act" pattern: it calls `nullifierStore.has(...)` and, if absent, later calls `nullifierStore.put(...)` in a separate step, with proof verification and other work happening in between (in `validate()`/`checkProof()`). This mirrors the reported Mattermost bug class (CWE-367, TOCTOU) where a single-use token is not atomically consumed, allowing it to be redeemed multiple times through concurrent requests.

### Finding Description
The nullifier is the mechanism that prevents a shielded note from being spent twice, analogous to a single-use "magic link" token. The check and the consumption are two separate, non-atomic operations: [1](#0-0) 

```java
for (SpendDescription spend : spends) {
  if (nullifierStore.has(
      new BytesCapsule(spend.getNullifier().toByteArray()).getData())) {
    ret.setStatus(fee, code.FAILED);
    ret.setShieldedTransactionFee(fee);
    throw new ContractExeException("double spend");
  }
  nullifierStore.put(new BytesCapsule(spend.getNullifier().toByteArray()));
}
```

The `validate()` path performs an equivalent `has()` check before `execute()` is ever invoked, and additionally records/caches zk-proof verification results keyed by transaction id rather than by nullifier: [2](#0-1) 

Two different transactions carrying spend descriptions with the *same* nullifier (e.g., two transactions built from the same shielded note, submitted concurrently) each independently:
1. Pass `validate()` because `nullifierStore.has()` still returns false for both (neither has committed yet).
2. Reach `executeShielded()`.

Whether this can actually race to a successful double-spend depends on whether the two independent `TransactionTrace.exec()`/actuator `execute()` invocations for the two transactions can interleave without serialization around this store access. Within `Manager.pushTransaction()`, execution is wrapped in a `synchronized(this)` block, and `processTransaction()` is invoked while holding that lock, which reduces (but does not eliminate) the exposure surface. It was not possible to fully verify from static analysis alone whether all invocation paths into `TransactionTrace.exec()` (e.g., block re-validation/retry paths in `Manager.processTransaction()`, or trace execution triggered from multiple pending pushes queued before the lock is acquired) are uniformly serialized with respect to `NullifierStore` reads/writes, or whether the underlying store (LevelDB/RocksDB-backed `NullifierStore`) provides any atomic compare-and-set semantics for `has()`+`put()`. This uncertainty is the central open question for full exploitability confirmation.

### Impact Explanation
If the check-then-act window can be raced (e.g., through the transient/uncommitted revoking-store session state during concurrent `pushTransaction` calls, or through retry logic in `Manager.processTransaction()` re-executing a trace), an attacker could get a shielded note's value credited twice to different shielded/transparent recipients while only spending the note once — an unbacked-balance / double-spend of value, directly corresponding to "theft or permanent freezing of funds / unbacked balance" in the acceptance criteria.

### Likelihood Explanation
Exploitation requires an attacker who controls a valid shielded spend (their own note) and crafts two transactions spending it to different outputs, then attempts to get both processed concurrently by broadcasting to multiple full nodes near-simultaneously, or by exploiting any node-local execution path where `validate()`/`execute()` for two transactions with the same nullifier are not serialized. Because normal `pushTransaction` flow appears to funnel through a `synchronized(this)` critical section, exploiting this on a single node's mempool intake is likely mitigated in the common path; the realistic risk surface would be transaction re-validation/retry logic in `processTransaction()` or divergent nodes each independently accepting one of the two conflicting transactions into their own mempools before block inclusion resolves the conflict at the chain level (which is expected/normal blockchain behavior, not a vulnerability by itself). Given this, likelihood is uncertain and depends on code paths not fully confirmed in this pass.

### Recommendation
Make nullifier consumption atomic with the existence check, ideally via a single atomic `putIfAbsent`-style store operation (or an explicit lock scoped to the nullifier) so that "check" and "commit" cannot be observed or interleaved by two concurrent execution paths. Additionally, ensure `executeShielded()` cannot be invoked for two transactions sharing a nullifier without both mutations to `NullifierStore` being covered by the same synchronization domain that guards state transitions in `Manager`, and confirm that block-application/retry code paths (`trace.checkNeedRetry()` in `Manager.processTransaction()`) cannot double-invoke `execute()` for the same spend without an intervening authoritative check.

### Proof of Concept
Conceptual reproduction (not fully verified as end-to-end exploitable given open questions above):
1. Build two `ShieldedTransferContract` transactions, `txA` and `txB`, each spending the same note (same `SpendDescription.nullifier`) to different outputs — this is straightforward given `ZenTransactionBuilder`/`ShieldedTransferActuator.validate()` only rejects duplicate nullifiers *within a single transaction*, not across transactions, as shown by the existing test: [3](#0-2) 
(this test demonstrates the check is store-based and only trips once a nullifier is already persisted).
2. Submit `txA` and `txB` concurrently (e.g., via two simultaneous `broadcastTransaction` gRPC/HTTP calls to the same or to peer nodes) before either commits its nullifier to the `NullifierStore`.
3. If the underlying execution paths are not fully serialized around the nullifier check-and-put, both transactions can pass `nullifierStore.has()` as false and both proceed to spend the same note, resulting in double the value being paid out from a single note.

Given the incomplete verification of concurrency guarantees across all `processTransaction` invocation paths, this should be validated further (e.g., with a targeted concurrency test invoking `Manager.processTransaction()` on two conflicting shielded transactions from separate threads) before treating it as confirmed rather than a plausible analog.
