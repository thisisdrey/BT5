## Title
Front-runnable Liquidity Ratio in `ExchangeInjectContract` Allows Sandwich Theft from Liquidity Providers - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectContract`, which lets any account (the exchange creator) add liquidity to a TRX/TRC10 bancor-style exchange pair, computes the counter-token amount (`anotherTokenQuant`) strictly from the pool's live `firstTokenBalance`/`secondTokenBalance` ratio at execution time, with no caller-supplied bound on that ratio or on `anotherTokenQuant`. This mirrors the KyberSwap `mint` issue where liquidity math is derived from state that can shift between submission and execution.

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no "expected"/minimum-out or ratio-bound field, unlike its sibling `ExchangeTransactionContract`, which explicitly has an `expected` field used to reject unfavorable trades. [1](#0-0) 

In `doValidate()`/`execute()` of `ExchangeInjectActuator`, `anotherTokenQuant` is derived purely from the current on-chain `firstTokenBalance`/`secondTokenBalance` ratio at the moment the transaction is processed, and the only sanity check is `anotherTokenQuant > 0` plus the global `balanceLimit`: [2](#0-1) [3](#0-2) 

There is no mechanism analogous to `ticksPrevious` validation or a minimum/maximum ratio bound supplied by the caller, so the exact "counter-asset" amount required is fully determined by whatever the pool ratio happens to be when the block producer includes the transaction — a value the liquidity provider cannot pin down when signing.

### Impact Explanation
Because `ExchangeTransactionContract` (trades) can be freely broadcast by anyone and directly move `firstTokenBalance`/`secondTokenBalance` via `ExchangeCapsule.transaction()`, an attacker who observes a pending `ExchangeInjectContract` in the mempool can submit a trade beforehand (front-run) that skews the pool ratio, then optionally reverse it afterward (sandwich) via another trade. This forces the victim's inject transaction to lock in far more of `anotherTokenID` than the fair-value ratio implied, or to receive a much worse deposit ratio than intended, transferring value from the LP to the attacker — a concrete, exploitable fund-loss scenario for any account performing `ExchangeInjectContract` (analogous to the reported KyberSwap `mint` tick-range manipulation).

### Likelihood Explanation
Any unprivileged account can submit `ExchangeTransactionContract` transactions against the same `exchange_id`, and transaction ordering within a block is controlled by the block-producing witness/relayers, making the attack straightforward to execute whenever a sizeable `ExchangeInjectContract` is visible in the mempool. The precondition (existence of the target Bancor-style exchange pair with sufficient liquidity to move the ratio meaningfully) is common for actively used TRC10/TRX pairs.

### Recommendation
Add caller-supplied slippage protection to `ExchangeInjectContract`, e.g., a minimum/maximum bound on `anotherTokenQuant` (or an acceptable ratio range), analogous to the `expected` field already present in `ExchangeTransactionContract`, and reject the injection in `doValidate()`/`execute()` if the computed `anotherTokenQuant` falls outside the caller's specified bound.

### Proof of Concept
1. LP builds and signs `ExchangeInjectContract{exchange_id=X, token_id=A, quant=Q}` expecting to deposit roughly `Q * balB/balA` of token B based on the ratio observed when signing.
2. Attacker observes this pending transaction and submits `ExchangeTransactionContract` trades against exchange `X` to shift `balA`/`balB` favorably for themselves before the LP's transaction is packed.
3. Block producer includes attacker's trade(s) first, then the LP's `ExchangeInjectContract`; `ExchangeInjectActuator.execute()` computes `anotherTokenQuant` from the now-skewed ratio via `floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)` (or the symmetric branch), causing the LP to deposit a disadvantageous amount of token B relative to the market price they expected. [3](#0-2) 
4. Attacker reverses their trade afterward (sandwich) to restore the ratio and extract the value transferred from the LP's unfavorable deposit.
