**Reasoning:** The premise of this question — that a "resolved price reflects a gated feed whose inputs the caller cannot move in the same transaction" — does not apply to the `repay` path at all. Examining `repay` in `mainnet/contracts/market/v0-4-market.clar:1316-1378`, the function never calls `write-feeds` or resolves any oracle price. It computes `max-repay-tokens` purely from `account-scaled-debt` and `borrow-index` (from `get-cached-indexes`, populated via `accrue-user-debts`), with no price-feed dependency: [1](#0-0) .

`debt-remove-scaled` in `mainnet/contracts/market/v0-market-vault.clar:473-503` clears the debt bit only when `remaining` (post-subtraction scaled debt) is exactly zero — this is the intended, standard "fully repaid" bookkeeping, not a bound satisfied with an unintended value: [2](#0-1) . It is also gated by `check-impl-auth`, restricting direct calls to the market contract itself, so it's only reachable via `repay`/`borrow` as designed: [3](#0-2) .

Repaying debt on behalf of a third party (`on-behalf-of`) reduces that account's debt using safe capping logic (`min amount max-repay-tokens`, `min account-scaled-debt scaled-debt-repayment`) and requires the attacker to actually transfer real tokens via `vault-system-repay`: [4](#0-3) . This is beneficial to the named account (their debt shrinks or clears), not a theft vector — there is no mechanism by which an attacker paying down someone else's debt results in stealing that person's collateral. No oracle, price feed, or gated invariant is touched or bypassed in this code path, so the described exploit mechanism does not exist here.
