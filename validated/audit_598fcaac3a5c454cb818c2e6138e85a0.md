### Title
StackerDB chunk signatures omit the target contract identifier, enabling cross-StackerDB replay of validly-signed chunks - (`libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata`/`StackerDBChunkData` signatures authenticate only `(slot_id, slot_version, data_hash)` — never the StackerDB's `smart_contract_id` (nor any network/chain discriminator). Because chunk-write endpoints accept chunks from anyone (no session/auth beyond the embedded signature) and because the same signer key legitimately occupies the same `slot_id` across multiple distinct StackerDB contracts, a signature that was validly produced and broadcast for one StackerDB instance can be replayed verbatim into a different StackerDB instance and be accepted as authentic there too. This mirrors the reported bug class: a signed message lacking a domain/context binding (EIP-712 domain separator equivalent) is captured off one context and successfully replayed into another context where it was never intended to be valid.

### Finding Description
The signing digest is computed as: [1](#0-0) 

This digest — and thus the signature `sig`/`signature` — commits to `slot_id`, `slot_version`, and `data_hash` only. It never includes the `smart_contract_id` (the specific StackerDB/contract instance), nor `rc_consensus_hash`/chain identifier, even though those values are transmitted alongside the chunk in `StackerDBPushChunkData` and the HTTP POST route: [2](#0-1) 

Verification of a received/pushed chunk is likewise scoped only to (a) whether the given address owns that `slot_id` *in the contract the verifier is currently processing*, and (b) whether the digest above validates against that address — the contract identity is checked as metadata around the signature, not as part of what is signed: [3](#0-2) 

Writing a chunk is unauthenticated beyond this signature check — "Anyone may call this function for anyone else... it's just a question of who provides the proof and pays the gas" is the exact StackerDB design model quoted in the external report, and it applies here too: `handle_unsolicited_StackerDBPushChunk` and the `POST /v2/stackerdb/.../chunks` handler accept any properly-signed chunk from any peer, with no session tied to the original broadcaster.

Because a StacksAddress's `(slot_id, addr)` mapping is reused verbatim across independently maintained StackerDB contract instances (e.g., the `.signers-0-*`/`.signers-1-*` two-replica DBs referenced in `stackslib/src/chainstate/stacks/boot/signers-0-xxx.clar` / `signers-1-xxx.clar`, and analogous miner/signer slot assignments across reward cycles via `boot_code_id(SIGNERS_NAME, is_mainnet)` in `stackslib/src/chainstate/nakamoto/signer_set.rs`), the same private key can end up owning slot `N` in two different contracts simultaneously. If both contracts also happen to accept the same `slot_version` (e.g., both freshly initialized at version 0/1, a common state right after a reward-cycle rollover or a new replica DB's creation), then `auth_digest()` for a chunk of a given `(slot_id, slot_version, data_hash)` is byte-identical in both contracts. An attacker who observes a legitimately signed chunk broadcast for contract A can resubmit the *exact same* `StackerDBChunkData` (unmodified signature) against contract B's write endpoint, and `validate_received_chunk`/`try_replace_chunk` will accept it as validly signed by that address for contract B, even though the owner never intended nor signed anything for contract B.

### Impact Explanation
This breaks the "authenticated per-instance write" invariant: a chunk accepted as valid for contract B was never actually authorized by its signer for contract B — it is a forged/replayed write into a StackerDB the attacker does not control the keys for. This is an unauthenticated write of attacker-replayed (non-canonical for that context) data into a StackerDB slot, and because chunks are gossiped to the whole network (`handle_unsolicited_StackerDBPushChunk`, inventory sync), the forged write propagates network-wide as if it were freshly and correctly authored for that specific contract, which downstream consumers (signer message pipelines reading `.signers-*` DBs, miner message pipelines reading `.miners-*` DBs) treat as authentic per-slot state for that contract.

### Likelihood Explanation
Exploitation requires only passively observing one legitimately broadcast, validly signed chunk (trivial — StackerDB chunk pushes are broadcast in the clear to the whole P2P network) and then re-submitting the identical bytes to a different StackerDB contract endpoint where the same signer occupies the same slot at a compatible version — a condition that recurs naturally at multi-replica DB initialization and reward-cycle rollovers. No cryptographic material or privileged access is required, matching the "remote, unprivileged" and "unauthenticated write to state" bar.

### Recommendation
Bind the `smart_contract_id` (and ideally a chain/network discriminator, e.g. `is_mainnet`/chain-id) into `SlotMetadata::auth_digest()` so that a chunk signature is only valid for the specific StackerDB contract it was created for. This requires a version bump/migration since it changes the wire-verifiable digest that all existing signers compute.

### Proof of Concept
1. Signer key `K` is registered as the owner of `slot_id = 3` in both `.signers-0-XXXX` and `.signers-1-XXXX` (a real two-replica configuration pattern) — see `signers-0-xxx.clar` / `signers-1-xxx.clar` and `NakamotoSigners::update_signers` in `stackslib/src/chainstate/nakamoto/signer_set.rs`, which writes an identical `stackerdb-set-signer-slots` list for the signer set.
2. `K` legitimately signs and broadcasts a `StackerDBChunkData{slot_id: 3, slot_version: 1, sig, data}` to `.signers-0-XXXX` via `send_message_bytes_with_retry` (`stacks-signer/src/client/stackerdb.rs:158-257`); this is relayed network-wide by `handle_unsolicited_StackerDBPushChunk`.
3. An attacker observes this chunk on the wire (no encryption/binding to contract) and resubmits the identical `StackerDBChunkData` bytes to `.signers-1-XXXX`'s `POST /v2/stackerdb/.../chunks` (or a P2P push), while `.signers-1-XXXX` slot 3 is also at version ≤1 and still owned by `K`.
4. `validate_received_chunk` (`stackslib/src/net/stackerdb/mod.rs:649-718`) calls `get_slot_signer(&.signers-1-XXXX, 3)` → returns `K`'s address, then `slot_metadata.verify(&addr)` succeeds because `auth_digest()` never included the contract id, so the forged write to `.signers-1-XXXX` is accepted and propagated as if `K` had authored it there.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }
