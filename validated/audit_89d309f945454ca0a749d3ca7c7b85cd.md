### Title
Prefix-only `tempDir` check in `FromProto` allows pool path confusion with sibling directories - ([File: internal/git/objectpool/pool.go])

### Summary
`FromProto` falls back to `strings.HasPrefix(poolPath, tempDir)` to allow pools that are still being created in the temporary directory, but this check does not verify a path-separator boundary. A `RelativePath` such as `+gitaly/tmp-evil/objects.git` produces a `poolPath` that is a raw string-prefix match of `tempDir` (`.../+gitaly/tmp`) without actually being a subdirectory of it.

### Finding Description
`FromProto` computes `poolPath` via `locator.GetRepoPath(...)` [1](#0-0) , and then, if the repository does not look like a canonical pool path (`storage.IsPoolRepository`), falls back to checking whether `poolPath` sits inside the storage's temp dir:

```go
if !strings.HasPrefix(poolPath, tempDir) {
    return nil, ErrInvalidPoolDir
}
``` [2](#0-1) 

`tempDir` is `filepath.Join(storagePath, "+gitaly/tmp")` [3](#0-2) [4](#0-3) , and `poolPath` is `filepath.Join(storagePath, relativePath)` after `ValidateRelativePath` confirms it stays within `storagePath` (no `..` traversal) [5](#0-4) [6](#0-5) . Notably, elsewhere in the codebase the exact same class of bug is guarded against correctly by appending the path separator to the prefix check: `strings.HasPrefix(absPath, rootDir+string(os.PathSeparator))` [7](#0-6) . The `FromProto` check in `pool.go` does not do this, so any relative path whose last path component of `tempDir`'s basename is a *string* prefix of a sibling directory name (e.g. `tmp-evil` vs `tmp`) will pass `strings.HasPrefix`, even though `tmp-evil` is not inside `tmp` on disk.

Since `RelativePath` is fully attacker-controlled through the `ObjectPool.Repository` field of `CreateObjectPool`/related object-pool RPCs, and there is no explicit reservation/denylist preventing a user-supplied relative path from starting with `+gitaly/tmp-<anything>` before it reaches `FromProto`, an attacker can supply a `RelativePath` engineered to string-match the temp-dir prefix without being contained in it.

### Impact Explanation
If exploited, this would let `FromProto` treat a path outside the temp-dir sandbox as though it were "still under construction" in the temp area, bypassing the pool-confinement invariant that only genuine pool repositories (`storage.IsPoolRepository`) or paths truly inside the storage temp directory are accepted. The scoped impact is limited to `FromProto`'s directory confinement gate — subsequent validation still runs `pool.IsValid(ctx)`, which calls `locator.ValidateRepository`, requiring the target path to be an actual valid git directory (`objects`, `refs`, `HEAD` present) [8](#0-7) [9](#0-8) . This substantially narrows real-world exploitability: the attacker would still need a pre-existing, valid git repository at the crafted sibling path within the same storage to pass `IsValid`, and `RelativePath` traversal outside the storage root is already blocked by `ValidateRelativePath`. Without a further primitive that lets an attacker write/create a git repo at an arbitrary storage-relative location and reuse it as a pool, this does not by itself yield cross-repository object disclosure or storage escape.

### Likelihood Explanation
Exploiting the prefix defect alone is feasible for an attacker who controls `RelativePath` in `ObjectPool.Repository` (available to any user who can invoke object-pool-related RPCs on their own project), but achieving concrete impact requires an additional condition — a genuine valid git repository already existing at the crafted "confused" path within the same storage — which is not demonstrated to be attacker-reachable from the code inspected. This significantly limits standalone exploitability.

### Recommendation
Fix the prefix check to require a path-separator boundary, consistent with `storage.ValidateRelativePath`:
```go
if poolPath != tempDir && !strings.HasPrefix(poolPath, tempDir+string(os.PathSeparator)) {
    return nil, ErrInvalidPoolDir
}
```

### Proof of Concept
```go
func TestFromProto_TempDirPrefixConfusion(t *testing.T) {
    // Construct a locator where TempDir("default") == "<storage>/+gitaly/tmp"
    // and RelativePath == "+gitaly/tmp-evil/objects.git", so that:
    //   poolPath == "<storage>/+gitaly/tmp-evil/objects.git"
    // strings.HasPrefix(poolPath, tempDir) is true, even though poolPath
    // is NOT inside tempDir (sibling directory "tmp-evil" vs "tmp").
    //
    // Expected (fixed) behavior: FromProto returns ErrInvalidPoolDir.
    // Observed (buggy) behavior: the temp-dir gate is passed, and only
    // pool.IsValid(ctx) (i.e., presence of a real git dir at that path)
    // determines acceptance/rejection.
}
```
Because full exploitation depends on additional preconditions (an existing valid git repository at the confused sibling path) that could not be confirmed as attacker-reachable from the available code, this should be treated as a defense-in-depth/logic flaw in the confinement check rather than a demonstrated storage-escape vulnerability.
