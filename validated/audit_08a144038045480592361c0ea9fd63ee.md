### Title
Heap buffer over-read via unchecked `local_header_offset` in `InputJar::LocalHeader` - ([File: src/tools/singlejar/input_jar.h])

### Summary
`singlejar`'s zip/jar reader computes the address of a per-entry Local Header directly from an attacker-supplied Central Directory Header field, without validating that the resulting pointer lies inside the mapped file, mirroring the elfutils `check_sysv_hash` class of bug where an untrusted offset/index field is trusted to compute a memory location that is then dereferenced.

### Finding Description
`InputJar::NextEntry` walks the Central Directory using `CDH::size()`, and does check that the *next CDH* pointer is inside the mapped region via `mapped_file_.mapped(new_cdr)` [4](#0-3) . However, for locating each entry's Local Header it calls:

```
const LH* LocalHeader(const CDH* cdh) const {
    return reinterpret_cast<const LH*>(
        mapped_file_.address(cdh->local_header_offset() + preamble_size_));
}
``` [3](#0-2) 

`cdh->local_header_offset()` is read straight from the (attacker-controlled) CDH bytes — either the raw 32-bit field or, if it is `0xFFFFFFFF`, from an equally attacker-controlled 64-bit Zip64 extra-field attribute [5](#0-4) . `MappedFile::address()` performs no range check — it just does pointer arithmetic on `mapped_start_` [1](#0-0) , in contrast to `MappedFile::mapped()`, which does bound the address between `mapped_start_` and `mapped_end_` [2](#0-1)  but is never invoked for the `LocalHeader()` result before it is dereferenced as an `LH*` by callers such as `OutputJar::AddJar` (used to compute `copy_from`/`num_bytes` and to `memcpy` data derived from `lh`) [6](#0-5) .

An arbitrary/huge or negative `local_header_offset` therefore produces a pointer far outside the mapped jar buffer; subsequent reads of `lh->size()`, `lh->compressed_file_size()`, etc. constitute an out-of-bounds heap read exactly analogous to `check_sysv_hash` in elfutils computing an out-of-range bucket/chain index from a crafted ELF hash table and reading past the mapped section.

### Impact Explanation
`singlejar` is invoked by Bazel's Java/Android build rules to merge jars, several of which can come from external, less-trusted sources (e.g., third-party `.jar` dependencies fetched via `http_jar`/`http_archive` or included in a build graph on an untrusted branch). A maliciously crafted jar with a corrupted/out-of-range `local_header_offset` in a Central Directory Header can cause `singlejar` to read out-of-bounds heap memory, leading to a crash (denial of service for that build action) or, depending on adjacent heap contents, potential information disclosure through error messages/derived output. This matches the Medium severity, local (single build worker), no-privilege class of the analog CVE.

### Likelihood Explanation
Reaching this code path only requires supplying a jar/zip file with an out-of-range `local_header_offset` field in one CDH entry (or a bogus Zip64 extra-field attribute) as input to `singlejar` (e.g., as a `srcs`/`deploy_jar` input). No credentials or special access are required beyond controlling the content of a jar consumed by the build (e.g., a jar dependency on an untrusted branch or fetched from an origin the victim's build merges without further vetting). The existing check in `NextEntry` only protects walking through the Central Directory, not deriving the Local Header address, so nothing currently stops this.

### Recommendation
Before dereferencing the result of `LocalHeader()`, validate it with `mapped_file_.mapped(...)` (and check that `lh + sizeof(LH)`, plus the file-name/extra-field/comment lengths, also stay within bounds), failing fast (`diag_errx`) as is already done for the Central Directory walk in `NextEntry`.

### Proof of Concept
A `BuildIntegrationTestCase`/shell test analogous to `src/tools/singlejar/input_jar_random_jars_test.cc` should:
1. Build a minimal valid zip/jar with one entry.
2. Patch the entry's CDH `local_header_offset32` field to a large out-of-range value (e.g., `0x7FFFFFFF` or a Zip64 extra field with an absurd 64-bit offset).
3. Run `InputJar::Open` + `NextEntry` (or invoke `singlejar` on this file) and observe the process crash/ASan heap-buffer-overflow (read) instead of a clean "corrupt jar" diagnostic, confirming the unchecked out-of-bounds read in `InputJar::LocalHeader`.
