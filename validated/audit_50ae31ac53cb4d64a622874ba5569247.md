## Finding

### Title
Missing G2 subgroup check in `alt_bn128_pairing_check` allows forged pairing proofs to authorize unauthorized token minting - (File: `runtime/near-vm-runner/src/logic/alt_bn128.rs`)

### Summary
`alt_bn128_pairing_check` documents that it rejects G2 points that are "not in the subgroup" with `AltBn128InvalidInput`, but the actual decoding path only checks that the point satisfies the twist curve equation, never that it lies in the prime-order `r`-torsion subgroup. This lets any caller submit a G2 element that is on-curve but outside the correct subgroup, which can make `bn::pairing_batch` return `Gt::one()` for pairs that do not correspond to a valid cryptographic proof, defeating any contract-level authorization logic gated on this host function's true/false result.

### Finding Description
`pairing_check` decodes each element via `decode_g1`/`decode_g2` and then checks `bn::pairing_batch(&elements) == bn::Gt::one()`: [1](#0-0) 

`decode_g2` only validates that the point satisfies the twist curve equation via `bn::AffineG2::new(x, y)`; it performs no order/subgroup check: [2](#0-1) 

This contradicts the documented contract of the host function, which explicitly states that non-subgroup points must be rejected: [3](#0-2) 

The asymmetry with the parallel BLS12-381 implementation is instructive: for BLS12-381, `bls12381_pairing_check` explicitly performs `blst_p1_affine_in_g1` and `blst_p2_affine_in_g2` subgroup membership checks on every point before running the Miller loop: [4](#0-3) 

No equivalent check (`is_in_correct_subgroup_assuming_on_curve` / cofactor clearing) exists anywhere in `alt_bn128.rs` for the G2 element used in `pairing_check`. Because BN254's twist G2 has a non-trivial cofactor, "on-curve" does not imply "in the r-order subgroup." An attacker who crafts a G2 point in a small-order subgroup of the twist (co-prime to `r`) that is still curve-valid can produce inputs where `bn::pairing_batch` collapses to the identity in `Gt` without the caller possessing any valid witness/signature — i.e., a forged pairing "proof."

Reachability: any contract that gates security-relevant logic (e.g., BLS/Groth16-style proof verification, bridge mint-on-deposit attestations) on the return value of `alt_bn128_pairing_check` inherits this weakened guarantee. An ordinary, unprivileged NEAR account can deploy such a contract (or interact with an existing one using this pattern) and call it with `FunctionCall` actions containing a crafted `value` byte buffer; there is no signature, nonce, access-key, or gas check in `near-vm-runner` that inspects the semantic validity of G2 points — validation of curve membership passes (`decode_g2` succeeds) and gas is charged normally, so the call proceeds to the contract's minting/authorization branch.

### Impact Explanation
Any NEAR contract using `alt_bn128_pairing_check` as a boolean authorization primitive (bridge deposit attestations, zk-proof verifiers, BLS-style multisig/threshold verification) can be tricked into treating a forged, witness-less proof as valid, because the host function's documented subgroup enforcement is not actually implemented for G2. In a mint-on-proof contract pattern, this maps to unauthorized token inflation/minting of that contract's internally tracked balances without a corresponding real deposit — matching the "token inflation" bounty category. The vulnerability lives in the shared host-function implementation, so its blast radius extends to every contract (not just synthetic ones) that relies on this primitive for cryptographic authorization.

### Likelihood Explanation
The attacker needs no special privilege: fund an account, deploy or call a contract, and submit a `FunctionCall` with crafted byte input — well within the stated "ordinary client" threat model. Crafting a curve-valid, non-subgroup G2 point is a standard elliptic-curve construction (pick any point satisfying the twist equation and multiply by the cofactor's complementary factor, or use small-subgroup generators), requiring no secrets. The attack is fully repeatable and deterministic once such a point is derived offline.

### Recommendation
Add an explicit subgroup membership check for decoded G2 (and, for defense in depth, G1) points in `decode_g2`/`decode_g1` in `runtime/near-vm-runner/src/logic/alt_bn128.rs`, e.g. by multiplying the decoded point by the group order `r` and asserting the result is the identity, mirroring the explicit `blst_p2_affine_in_g2` check already used in `bls12381.rs`. Update/verify this is versioned behind a protocol feature to avoid consensus-breaking behavior changes on existing deployed contracts.

### Proof of Concept
1. In `runtime/near-vm-runner/src/logic/tests/alt_bn128.rs`, construct a G2 point `(x2, y2)` satisfying the twist curve equation `y^2 = x^3 + 3/(9+i)` but verified (via an independent scalar multiplication by `r`) to be outside the order-`r` subgroup.
2. Call `logic.alt_bn128_pairing_check` with a single `(g1, g2)` pair using an arbitrary G1 generator and the crafted non-subgroup G2 point, chosen such that `pairing_batch` returns `Gt::one()`.
3. Assert the host function returns `1` (pairing holds) despite the G2 element not being in the subgroup — demonstrating the documented `AltBn128InvalidInput` rejection never fires.
4. As an integration-level extension, implement a minimal "mint-on-proof" test contract that calls `alt_bn128_pairing_check` and credits an internal token balance when it returns true; submit the forged proof via a `FunctionCall` action in a test-loop runtime test and assert the balance increased with no corresponding deposit receipt.

pub(crate) fn pairing_check(
    elements: &[[u8; PAIRING_CHECK_ELEMENT_SIZE]],
) -> Result<bool, InvalidInput> {
    let elements: Vec<(bn::G1, bn::G2)> = elements
        .iter()
        .map(|chunk| {
            let (g1, g2) = stdx::split_array(chunk);
            let g1 = decode_g1(g1)?;
            let g2 = decode_g2(g2)?;
            Ok((g1, g2))
        })
        .collect::<Result<Vec<_>, InvalidInput>>()?;

    let res = bn::pairing_batch(&elements) == bn::Gt::one();

    Ok(res)
}

fn decode_g2(raw: &[u8; 2 * POINT_SIZE]) -> Result<bn::G2, InvalidInput> {
    let (x, y) = stdx::split_array(raw);
    let x = decode_fq2(x)?;
    let y = decode_fq2(y)?;
    if x.is_zero() && y.is_zero() {
        Ok(bn::G2::zero())
    } else {
        bn::AffineG2::new(x, y)
            .map_err(|_err| InvalidInput::new("invalid g2", raw))
            .map(bn::G2::from)
    }
}
