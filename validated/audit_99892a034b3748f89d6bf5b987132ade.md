Based on my investigation, I found a concrete, structurally identical analog in `substrate/frame/psm`.

### Title
PSM `redeem()` burns the internal asset via `Fungibles::burn_from`, bypassing the internal asset's own frozen/pause enforcement that governs ordinary transfers - ([File: substrate/frame/psm/src/lib.rs])

### Summary
The reported bug is that `PSM._redeem()` burns `yzUSD` directly instead of going through `syzUSD.redeem()`, which is the only path that runs `maxRedeem()` (pause + redeem-restriction checks). The local `pallet-psm` in this repo reproduces the same shape: `Pallet::redeem()` [1](#0-0)  only validates the **external**-asset's `CircuitBreakerLevel::allows_redemption()`, then unconditionally burns the **internal** asset with `T::Fungibles::burn_from(...)` [2](#0-1) . Nothing in `redeem()` checks whether the internal asset itself is frozen/paused for that specific account.

### Finding Description
`redeem()` gates on the **external** asset's per-instance circuit breaker only: [3](#0-2) 
It never queries the internal asset's own account-level freeze/hold state before calling `burn_from`. `T::Fungibles` is a generic trait (`FungiblesMutate`), and `burn_from` is a privileged, unauthenticated-by-holder debit operation - unlike a `transfer()` initiated by the holder, which in `pallet-assets` is gated through `can_withdraw`-style consequence checks. The pallet's own `ensure_account_can_die` helper shows that freezes are tracked via a separate `T::Freezer` abstraction (`T::Freezer::frozen_balance`), which is checked only in narrow paths like account death, not in `do_burn`'s core debit logic: [4](#0-3)  and the `do_burn` function itself only validates asset *status* (Live/Frozen at the asset level, not per-account freezes) before debiting: [5](#0-4) .

This mirrors the Solidity report exactly: the checked, user-facing entry point (`yzUSD.redeem()` / here, a hypothetical direct `Assets::transfer`/hold-based restriction on the internal asset) enforces pause and eligibility, but the PSM's privileged internal call (`burn_from`, analogous to `IERC20Burnable.burn`) skips it because it operates through an admin/issuer-level primitive rather than the holder-consent transfer primitive that the restriction logic is attached to.

### Impact Explanation
If a runtime integrator freezes or restricts redemption of the internal asset (e.g., during an incident, via `pallet-assets`' per-account freeze extension, or a custom `Freezer`/pause layer intended to block redemptions for a specific account or globally) expecting that to stop all outflows of that asset, PSM's `redeem()` still lets holders exchange the "frozen" internal asset for hard external collateral, draining PSM reserves and defeating the frozen/pause control. This is a "public underpriced work" / uncontrolled-fund-egress class issue: an unprivileged, signed-only caller (`ensure_signed(origin)?`) can extract real backing assets that the runtime operator believed were locked.

### Likelihood Explanation
Likelihood is Medium: it requires a runtime configuration where the internal asset has some frozen/restricted state mechanism (via `pallet-assets` freezer trait or a custom pause layer) that is expected to block redemption but is not itself checked inside `pallet-psm::redeem()`. Since `pallet-psm` is generic over `T::Fungibles` and doesn't hard-code any pause/freeze awareness for the internal asset, any runtime wiring a freeze-capable backend without duplicating the check at the PSM call site is exposed. This exactly parallels the "Note" in the original report that the bypass is conditional on the underlying asset's pause mechanism existing and not being separately enforced.

### Recommendation
Apply the internal asset's frozen/pause and redemption-eligibility checks explicitly inside `Pallet::redeem()` before calling `burn_from`/`transfer` on the internal asset - e.g., query `T::Freezer::frozen_balance` (or an equivalent `CanRedeem`/pause hook) for `(internal_asset, who)` and reject the swap if it would violate that state, mirroring the recommendation to enforce checks consistently at all entry points that debit the internal asset.

### Proof of Concept
1. Runtime configures `pallet-psm::Config::Fungibles` = `pallet-assets`, and separately wires a `Freezer`/pause extension on the internal asset intended to block redemption for a flagged account (e.g., sanctioned or under investigation).
2. The freeze/pause is applied to account `who` on the internal asset via the freezer mechanism, with the expectation that `who` cannot move/redeem that asset.
3. `who` calls `Psm::redeem(origin, internal_asset, external_asset, internal_amount, max_fee)`.
4. `redeem()` only checks `external.status.allows_redemption()` [3](#0-2)  - unrelated to `who`'s freeze on the internal asset - and proceeds to `T::Fungibles::burn_from(internal_asset, &who, ...)` [2](#0-1) , which succeeds because `do_burn`/`decrease_balance` in `pallet-assets` does not consult the freezer for burns the way holder-initiated transfers would.
5. `who` receives external collateral out of the PSM reserve despite being frozen/paused on the internal asset, confirming the bypass.

**Caveat on confidence**: I was not able to fully trace whether `pallet-assets::functions::decrease_balance` (the low-level debit routine invoked by `do_burn`) consults `T::Freezer` for reducible-balance calculations in this specific commit - my search only confirmed that `ensure_account_can_die` and asset-level `status` are checked, not that per-account freeze balances are excluded from `do_burn`'s underflow guard. A Devin session with full file access should verify `decrease_balance`'s implementation end-to-end (including whether it calls `reducible_balance`/`Freezer::frozen_balance`) before treating this as fully confirmed rather than a strong structural analog.
