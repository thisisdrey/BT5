## Analog Vulnerability Found

### Title
Reference updates via `RefService.UpdateReferences` bypass Gitaly's pre-receive/update access-check hooks - (File: internal/gitaly/service/ref/update_references.go)

### Summary
The external report describes a bug class where a critical protective check (ZRC20 pause enforcement) is implemented only in a side-channel "hook" mechanism, and a code path exists that writes state directly while skipping the hook invocation, thereby bypassing the check. In Gitaly, the equivalent protective mechanism is the `pre-receive`/`update` hook chain, which is responsible for calling into GitLab Rails' `/internal/allowed` access-control endpoint and for running any repository-specific access checks before a reference update takes effect. The `RefService.UpdateReferences` RPC updates references directly through the low-level `updateref.New` git updater, never going through `updateref.UpdaterWithHooks`, so the access-check hook chain is never invoked for these updates.

### Finding Description
Gitaly's documented security model for reference updates says explicitly that "most RPCs in the `OperationService` that write objects into the repository manually invoke [pre-receive/update/reference-transaction] hooks using the `updateref.UpdaterWithHooks` structure" [1](#0-0) . `UpdaterWithHooks.UpdateReference` implements this by running `PreReceiveHook` (which posts to Rails' `/internal/allowed` and executes custom `pre-receive` hooks) and `UpdateHook` before ever calling the low-level ref updater to commit the change [2](#0-1) .

By contrast, `RefService.UpdateReferences` builds a bare `updateref.New(ctx, repo)` updater directly, queues the caller-supplied reference updates, and commits them — with no call into `hookManager.PreReceiveHook`, `UpdateHook`, or any GitLab access-check integration at all [3](#0-2) [4](#0-3) . The only validation performed is reference-name format and object-ID hex validation; there is no invocation of the hook mechanism that carries GitLab's push authorization/protected-branch/access-control logic. This directly mirrors the external report's finding: a state-mutating path exists in the system that is not "below"/"after" the point where the hook-based protection is applied, so callers of this path can update refs (e.g., overwrite `refs/heads/*`, create/move tags, or write refs used by other subsystems) without passing through the same access-check gate that `UserUpdateBranch` and other `OperationService` RPCs enforce via `UpdaterWithHooks` [5](#0-4) .

### Impact Explanation
Any caller with gRPC access to `RefService.UpdateReferences` can force-update, create, or delete references in a repository while completely bypassing:
- GitLab's `/internal/allowed` push authorization check (protected branches, permission checks, license/feature gating),
- Custom `pre-receive`/`update` hooks that enforce repository-specific policy,
- The reference counter used to track in-flight pushes.

This is analogous to the ZRC20 case where a code path that mutates protected state runs below the point the hook-based check is applied, letting an attacker "circumvent" logic that administrators or the platform assume is always enforced. Since Gitaly hosts the source of truth for Git references, an unauthorized/unchecked ref update can be used to bypass branch-protection policies or push arbitrary history into protected refs.

### Likelihood Explanation
This is a real, unconditional code-path gap rather than a hypothetical timing issue: `UpdateReferences` never touches `hookManager` at all, whereas every comparable OperationService mutator RPC funnels through `UpdaterWithHooks`. The likelihood hinges entirely on whether `RefService.UpdateReferences` is reachable by ordinary/less-privileged callers (vs. being restricted to internal/administrative use, e.g., only used by backup-restore code as seen in `internal/backup/repository.go`). Whether GitLab Rails / gitlab-shell actually exposes this RPC to end-user push flows, or gates it behind an internal-only credential, could not be fully confirmed from the available index; this determines whether the gap is exploitable by an "ordinary user" as required by the validation rules, or is only reachable by an already-privileged internal actor (which would fall under the excluded "privileged-actor" analog category).

### Recommendation
Either (a) route `UpdateReferences` through `updateref.UpdaterWithHooks` so that pre-receive/update access-check hooks are always invoked before any reference mutation is committed, or (b) explicitly restrict/authenticate this RPC so it can only be invoked by trusted internal callers (e.g., Praefect-only or backup/restore internal paths) that have already performed equivalent authorization checks, and document/enforce this restriction at the RPC/service-config level (e.g., via existing internal-only RPC annotations) so it cannot be reached by ordinary push/fetch/import flows.

### Proof of Concept
Because this requires live gRPC access and cannot be fully validated without running Gitaly, the concrete proof of concept is:
1. Start a `RefService.UpdateReferences` bidirectional stream against a repository with a protected branch (e.g., `refs/heads/main`) that would normally reject a force-push via `git push` (rejected by `pre-receive` calling GitLab's `/internal/allowed`).
2. Send an `UpdateReferencesRequest` with `Repository` set, and an update entry setting `reference: "refs/heads/main"`, `old_object_id: <current-tip>`, `new_object_id: <arbitrary-existing-commit>`.
3. Close the stream and observe that `UpdateReferencesResponse` succeeds and `refs/heads/main` is updated to the new object, with no call ever made to GitLab's `/internal/allowed` endpoint and no `pre-receive`/`update` custom hook executed — confirmed by code inspection showing `updateref.New` (not `UpdaterWithHooks`) is used in `update_references.go`.

**Uncertainty note:** I was unable to confirm from the indexed code whether `RefService.UpdateReferences` is exposed to standard, less-privileged Gitaly clients (e.g., via gitlab-shell/Workhorse on ordinary pushes) or is restricted to internal callers such as the backup/restore subsystem (`internal/backup/repository.go` is a known caller). This distinction is decisive for whether the finding qualifies as an unprivileged-reachable analog per the task's validation rules. Confirming the RPC's authorization/exposure surface would require inspecting `internal/gitaly/server/auth.go` and Rails/gitlab-shell integration code, which was not fully retrievable given index limits — a full Devin session with repository access would be needed to trace all gRPC client callers of `UpdateReferences` end-to-end.
