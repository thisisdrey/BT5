### Title
Module extension `facts` are persisted to the lockfile without checksum verification, letting a first-evaluation network response permanently poison all subsequent builds - (File: `src/main/java/com/google/devtools/build/lib/bazel/bzlmod/*` — `SingleExtensionEvalFunction` / `ModuleExtensionMetadata` / `BazelLockFileValue`, documented in `docs/external/extension.mdx:244-288`)

### Summary
Bzlmod's `facts` mechanism lets a non-checksum-guarded module extension record data it fetched over the network on its first evaluation, which Bazel writes into `MODULE.bazel.lock` and blindly trusts on all future evaluations, forever, without any hash pinning of the data itself [1](#0-0) . This is a direct trust-on-first-use analog of the "first depositor sets a baseline that is then trusted" bug class: whatever content an attacker-controlled server returns during the *first* fetch for an entry becomes the permanent "fact" baked into the lockfile, silently reused by every subsequent build, bypassing re-fetch and re-verification even after the extension's own code changes.

### Finding Description
The `extension_metadata()` Starlark builtin accepts a `facts` dict that is explicitly intended for extensions that "rely on effectively immutable data obtained from outside the build...but don't have a checksum available to guard the download" [2](#0-1) . On the *first* evaluation of the extension, whatever facts the extension implementation function returns (e.g., a URL→hash mapping fetched from the network) are persisted verbatim into `MODULE.bazel.lock`'s `facts` field [3](#0-2) , and are exposed to all future evaluations via `module_ctx.facts` [4](#0-3) .

Critically:
- Facts are **not invalidated when the extension code changes** — the documentation itself states this explicitly [5](#0-4) .
- Facts from **different evaluations get shallow-merged** (`dict.update()`/`|` semantics), so a value written once for a given key persists across schema/version drift unless the extension bumps `facts_version` [6](#0-5) .
- The whole mechanism exists specifically **because there is no checksum available to guard the download** — i.e., it is designed for exactly the situation where integrity verification is absent, and the "trust" boundary is "first observed value wins."
- Regression tests confirm facts persist across `bazel shutdown`, `bazel clean --expunge`, and lockfile deletion via the hidden lockfile, and are only regenerated if a key is fully absent [7](#0-6) , and partial-deletion/regeneration semantics are keyed purely by dict-key presence, not by content verification [8](#0-7) .

An attacker who controls the network resource that a `facts`-recording extension fetches from during a victim's *first* build (e.g., a compromised mirror, a registry endpoint not yet pinned by a checksum, or a not-yet-cached "immutable artifact" URL) can return malicious/inflated metadata (e.g., a bogus artifact hash, URL, or version mapping) at that first-use moment. Bazel then commits that value into `facts` in the lockfile as ground truth. Every subsequent evaluation — on this machine, and on any machine/CI that checks in or reuses that `MODULE.bazel.lock` — reuses the poisoned value without re-contacting the network or re-verifying it, because the entire point of `facts` is to let the extension "avoid the network requests" on later evaluations [9](#0-8) . This mirrors the report's core defect: a value established during an unguarded "first" interaction becomes the trusted baseline for all later accounting, with no mechanism analogous to a pinned checksum to reject a bad first value.

### Impact Explanation
Because `facts` is explicitly the recommended pattern for extensions to persist "hashes of artifacts in an immutable repository" when no checksum is otherwise available [10](#0-9) , a poisoned first-fetch value can propagate a wrong hash/URL into every repository built by that extension for the lifetime of the checked-in lockfile. This is analogous to the "share value inflation" impact: a single attacker-controlled response at the moment before a pin exists corrupts the trusted state for every future consumer, and — matching the report's "prohibitively expensive" angle — is difficult to detect or roll back because `facts` are not invalidated by extension code changes and are merged across versions rather than replaced. This affects reproducibility and, when facts encode download hashes/URLs used by a `repository_rule`, can result in unauthenticated content flowing into all future builds' external repositories, i.e., untrusted content escaping into what should be integrity-checked build inputs.

### Likelihood Explanation
Likelihood is constrained: the attacker must control (or MITM at a level analogous to a "hostile origin server counted only where a declared integrity check should stop it") the exact network response an extension fetches during the very first, not-yet-lockfile-pinned evaluation on a victim's machine or CI. This is realistic for module extensions that fetch from mirrors/registries without a pinned hash for that specific fact key (which is precisely the scenario the `facts` API is designed to serve, per Bazel's own docs), and for CI configurations that regenerate `MODULE.bazel.lock` from scratch (e.g., `bazel clean --expunge` + no checked-in lock, or a rollback that drops facts for that key as shown in the regression test) [11](#0-10) .

### Recommendation
Require the `facts` dict itself to carry, or be constrained by, a Bazel-verified checksum (e.g., allow `facts` entries to declare an expected `sha256`/integrity that Bazel validates against the actual downloaded bytes before persisting or reusing the fact), rather than trusting whatever the extension implementation returned on the first, un-pinned evaluation. At minimum, surface a loud diagnostic/warning whenever a `facts` entry is being *created* for the first time (not merely when it changes) so that first-run provenance can be audited, and consider tying `facts` reuse to the same `--lockfile_mode=error` guarantees used for other lockfile content so `error` mode can refuse silently-first-established facts in CI.

### Proof of Concept
Not independently reproduced against live Bazel due to ask-only/index limitations (no access to the Java implementation of `SingleExtensionEvalFunction`/lockfile facts-merging logic in this index — only docs and Python integration tests were available). A concrete JUnit/`bazel_lockfile_test.py`-style PoC would:
1. Define a module extension whose impl calls a fake "fetch metadata from the internet" helper (as in `testFactsInReproducibleExtension` [12](#0-11) ) but backed by a real HTTP endpoint under attacker control.
2. On the victim's first build (no `MODULE.bazel.lock` present), have the attacker-controlled endpoint return a malicious hash/URL, which is confirmed to be written into `lockfile['facts'][extension_id]` (mirroring the assertion pattern used at [13](#0-12) ).
3. Fix the endpoint to now serve the legitimate value and show that subsequent builds (even with `--lockfile_mode=error`, even after `bazel clean --expunge`) still use the attacker's original value because it is served from the persisted `facts`, never re-verified or re-fetched.

If your extension relies on effectively immutable data obtained from outside
the build, most commonly from the network, but you don't have a checksum
available to guard the download, consider using the `facts` parameter of
[`extension_metadata`](/rules/lib/builtins/module_ctx#extension_metadata) to
persistently record such data and thus allow your extension to become
reproducible. `facts` is expected to be a dictionary with string keys and
arbitrary JSON-like Starlark values that is always persisted in the lockfile and
available to future evaluations of the extension via the
[`facts`](/rules/lib/builtins/module_ctx#facts) field of `module_ctx`.

`facts` are not invalidated even when the code of your module extension changes,
so be prepared to handle the case where the structure of `facts` changes.
Bazel also assumes that two different `facts` dicts produced by two different
evaluations of the same extension can be shallowly merged (i.e., as if by using
the `|` operator on two dicts). This is partially enforced by `module_ctx.facts`
not supporting enumeration of its entries, just lookups by key.

An example of using `facts` would be to record a mapping from version numbers of
some SDK to the an object containing the download URL and checksum of that
version. The first time the extension is evaluated, it can fetch this mapping
from the network, but on later evaluations it can use the mapping from `facts`
to avoid the network requests.

If you need to make a backwards-incompatible change to the schema of the values
your extension stores in `facts`, set the
[`facts_version`](/rules/lib/globals/bzl#module_extension.facts_version)
parameter on `module_extension` to a higher integer than its previous value.
Bazel persists `facts_version` in the lockfile alongside the facts and discards
any persisted facts when the recorded version differs from the current one,
making sure your extension only ever observes facts produced by the same schema.

  def testFactsWithLockfileModeErrorAfterRollback(self):
    """Test that ERROR mode doesn't fail when rolling back to a version without facts.

    Regression test for https://github.com/bazelbuild/bazel/issues/28717

    Simulates the scenario:
    1. Build with extension that produces facts (e.g., rules_go 0.60.0)
    2. Rollback to older version without facts (e.g., rules_go 0.50.1)
    3. Build with --lockfile_mode=error should succeed, not fail with
       "extension has changed its facts" error
    """
    self.ScratchFile(
        'MODULE.bazel',
        [
            'lockfile_ext = use_extension("extension.bzl", "lockfile_ext")',
            'use_repo(lockfile_ext, "hello")',
        ],
    )
    self.ScratchFile('BUILD.bazel')
    self.ScratchFile(
        'extension.bzl',
        [
            'def impl(ctx):',
            '    ctx.file("BUILD", "filegroup(name=\\"lala\\")")',
            'repo_rule = repository_rule(',
            '    implementation = impl,',
            '    attrs = {"hash": attr.string()},',
            ')',
            'def _mod_ext_impl(ctx):',
            '    print("Extension with facts")',
            '    metadata = {"hello": {"hash": "olleh"}}',
            '    repo_rule(',
            '        name = "hello",',
            '        hash = metadata["hello"]["hash"],',
            '    )',
            '    return ctx.extension_metadata(',
            '        reproducible = True,',
            '        facts = metadata,',
            '    )',
            'lockfile_ext = module_extension(implementation = _mod_ext_impl)',
        ],
    )

    # Initial build with facts - creates both workspace and hidden lockfiles
    self.RunBazel(['build', '@hello//:all', '--lockfile_mode=update'])

    # Verify facts are in the lockfile
    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    self.assertIn('facts', lockfile)
    extension_id = '//:extension.bzl%lockfile_ext'
    self.assertIn(extension_id, lockfile['facts'])

    # Verify ERROR mode works with facts present
    self.RunBazel(['build', '@hello//:all', '--lockfile_mode=error'])

    # Simulate rollback: change extension to not produce facts
    self.ScratchFile(
        'extension.bzl',
        [
            'def impl(ctx):',
            '    ctx.file("BUILD", "filegroup(name=\\"lala\\")")',
            'repo_rule = repository_rule(',
            '    implementation = impl,',
            '    attrs = {"hash": attr.string()},',
            ')',
            'def _mod_ext_impl(ctx):',
            '    print("Extension without facts")',
            '    repo_rule(',
            '        name = "hello",',
            '        hash = "olleh",',
            '    )',
            '    return ctx.extension_metadata(',
            '        reproducible = True,',
            '    )',
            'lockfile_ext = module_extension(implementation = _mod_ext_impl)',
        ],
    )

    # Simulate rollback: manually remove facts from workspace lockfile
    # (as would happen when checking out an older commit)
    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    if extension_id in lockfile['facts']:
      del lockfile['facts'][extension_id]
    with open(self.Path('MODULE.bazel.lock'), 'w') as f:
      json.dump(lockfile, f, indent=2)

    # This should succeed without "has changed its facts" error
    # Before the fix, this would fail because the hidden lockfile still has
    # facts from the previous build, causing a false-positive validation error
    exit_code, stdout, stderr = self.RunBazel(
        ['build', '@hello//:all', '--lockfile_mode=error'], allow_failure=True
    )
    stderr = ''.join(stderr)
    # Should succeed (exit code 0)
    self.AssertExitCode(exit_code, 0, stderr, stdout)
    # Should not have "has changed its facts" error
    self.assertNotIn('has changed its facts', stderr)
