## Analog Found

### Title
Unbounded full-table scan in `Wallet.getAssetIssueByAccount` / `getAssetIssueListByName` allows a single external API request to exhaust node resources - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
The reported Blueberry bug is an unbounded `for` loop over a globally-growing counter (`nextPositionId`) that is reachable by any external caller and whose cost grows without limit as usage of the protocol increases. The same bug class exists in java-tron's asset-issue query path: `Wallet.getAssetIssueByAccount` and `Wallet.getAssetIssueListByName` load the entire asset-issue table into memory and linearly scan/filter it for every single call, with no pagination, no cap, and no owner-address index.

### Finding Description
`Wallet.getAssetIssueByAccount` fetches **all** asset issues via `getAllAssetIssues()` and then does an in-memory linear filter by owner address: [1](#0-0) 

The same unbounded pattern repeats in `getAssetIssueListByName`, which also loads the complete list and filters by name in memory instead of using an index: [2](#0-1) 

Both rely on `AssetIssueStore.getAllAssetIssues()`, which streams the *entire* underlying key-value store into a `List`: [3](#0-2) 

Unlike `getAssetIssueList(offset, limit)`, which correctly paginates via `getAssetIssuesPaginated` and caps `limit` at `ASSET_ISSUE_COUNT_LIMIT_MAX`: [4](#0-3) 

`getAssetIssueByAccount` and `getAssetIssueListByName` have **no pagination and no size cap** — they always do `O(N)` work where `N` is the total number of asset issues ever created on chain, a quantity that only grows and is directly controllable by any user willing to pay the token-issuance fee (there is no protocol-level maximum on the number of asset issues, confirmed by the absence of any such limit in `AssetIssueActuator`/`Commons`). This mirrors the audit finding precisely: the loop bound (`nextPositionId` there, total asset-issue count here) is an ever-increasing global counter driven by ordinary user activity, not a bounded per-caller value.

This function is reachable directly from unauthenticated, unprivileged callers via multiple entry points:
- HTTP: `GetAssetIssueByAccountServlet` / `GetAssetIssueListByNameServlet`, mounted on the full node, PBFT, and solidity HTTP API services. [5](#0-4) 
- gRPC: `RpcApiService.getAssetIssueByAccount` / `getAssetIssueListByName`, also mirrored on PBFT/solidity gRPC services. [6](#0-5) 

### Impact Explanation
As the total number of asset issues on chain grows over the lifespan of the network, every call to `getAssetIssueByAccount`/`getAssetIssueListByName` becomes progressively more expensive: it must materialize the full asset-issue table (each entry deserialized into an `AssetIssueCapsule`) and run a `BandwidthProcessor.updateUsage` side-effect call plus a filter over the whole list. Because these endpoints are unauthenticated and exposed on the node's HTTP/gRPC API surface (full node, solidity node, and PBFT services), a remote caller can repeatedly invoke them to force the node to repeatedly do large memory allocations and CPU-bound scans, degrading or blocking the API service thread pool and slowing down the node's ability to serve other legitimate API requests — matching the "API the node can no longer serve" impact category.

### Likelihood Explanation
The endpoints require no special privileges — any HTTP or gRPC client can call `/wallet/getassetissuebyaccount` or `GetAssetIssueByAccount`/`GetAssetIssueListByName` with an arbitrary address/name. The cost of triggering the worst case scales with the total number of asset issues ever created, which any account can increase by issuing new tokens (subject only to the issuance fee, not a hard cap), meaning an attacker can also amplify the attack over time by pre-seeding many asset issues.

### Recommendation
Add pagination (offset/limit with a hard maximum, consistent with `getAssetIssuesPaginated`) to `getAssetIssueByAccount` and `getAssetIssueListByName`, or better, maintain a secondary index (owner-address → asset-issue IDs, name → asset-issue IDs) similar to `DelegatedResourceAccountIndexStore`'s prefix-based indexing, so lookups are O(matches) instead of O(total asset issues).

### Proof of Concept
1. Over time (or by an attacker pre-issuing many tokens from many accounts, each paying the issuance fee), the total asset-issue count `N` grows large.
2. An anonymous client sends repeated HTTP requests to `GET /wallet/getassetissuebyaccount?address=<any>` (or the equivalent gRPC `getAssetIssueByAccount` / `getAssetIssueListByName` call).
3. Each request forces `Wallet.getAssetIssueByAccount` to call `getAllAssetIssues()` and deserialize/scan all `N` entries plus run `BandwidthProcessor.updateUsage` for each filtered match, consuming CPU/memory proportional to `N` per single request, with no pagination or cap to bound the work.
4. Repeated concurrent calls exhaust HTTP/gRPC worker threads, degrading the node's ability to serve other API requests.

    if (accountAddress == null || accountAddress.isEmpty()) {

    AssetIssueList.Builder builder = AssetIssueList.newBuilder();
    assetIssueCapsuleList.stream()
        .filter(assetIssueCapsule -> assetIssueCapsule.getOwnerAddress().equals(accountAddress))
        .forEach(
            issueCapsule -> {
              processor.updateUsage(issueCapsule);
              builder.addAssetIssue(issueCapsule.getInstance());
            });

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
    return getAssetIssuesPaginated(getAllAssetIssues(), offset, limit);
  }

@Component
@Slf4j(topic = "API")
public class GetAssetIssueByAccountServlet extends RateLimiterServlet {

  @Autowired
  private Wallet wallet;

  protected void doGet(HttpServletRequest request, HttpServletResponse response) {
    try {
      boolean visible = Util.getVisible(request);
      String address = request.getParameter("address");
      if (visible) {
        address = Util.getHexAddress(address);
      }
      fillResponse(visible, ByteString.copyFrom(ByteArray.fromHexString(address)), response);
    } catch (Exception e) {
      Util.processError(e, response);
    }
  }

  protected void doPost(HttpServletRequest request, HttpServletResponse response) {
    try {
      PostParams params = PostParams.getPostParams(request);
      Account.Builder build = Account.newBuilder();
      JsonFormat.merge(params.getParams(), build, params.isVisible());
      fillResponse(params.isVisible(), build.getAddress(), response);
    } catch (Exception e) {
      Util.processError(e, response);
    }
  }

  private void fillResponse(boolean visible, ByteString address, HttpServletResponse response)
      throws Exception {
    AssetIssueList reply = wallet.getAssetIssueByAccount(address);
    if (reply != null) {
      response.getWriter().println(JsonFormat.printToString(reply, visible));
    } else {
      response.getWriter().println("{}");
    }
  }
