### Title
Relay control messages let a peer register relay state under a VPN address it does not own - ([File: relay_manager.go])

### Summary
`handleCreateRelayRequest` and `handleCreateRelayResponse` in `relay_manager.go` derive the "from" VPN address for relay bookkeeping directly from attacker-controlled protobuf fields (`m.RelayFromAddr` / `m.OldRelayFromAddr`) inside a `NebulaControl` message, without ever checking that this claimed address matches the certificate-authenticated `vpnAddrs` of the `HostInfo` (`h`) that actually sent the message.

### Finding Description
`handleCreateRelayRequest` is invoked with `h *HostInfo`, which is the already-authenticated tunnel peer that sent the `CreateRelayRequest` control message [1](#0-0) . Inside it, the function extracts `from` and `target` purely from message fields supplied by the peer:

```go
from := protoAddrToNetAddr(m.RelayFromAddr)
target := protoAddrToNetAddr(m.RelayToAddr)
``` [2](#0-1) 

The only sanity check performed is that `from` is not one of *my own* addresses [3](#0-2) . There is no check anywhere in this function (nor in `handleCreateRelayResponse`) that `from == h.vpnAddrs[0]`, i.e. that the claimed relay-origin address actually belongs to the certificate that `h` presented during its own handshake. Given that, when the target is me, the code proceeds to install relay state keyed by the attacker-supplied `from` on the authenticated `HostInfo` of the connecting peer:

```go
_, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
``` [4](#0-3) 

And in the "target is not me" branch, the peer being asked to forward is looked up purely by the attacker-supplied `target`, and relay state is installed for the attacker-supplied `from` on that unrelated peer's `HostInfo`:

```go
peer := rm.hostmap.QueryVpnAddr(target)
...
index, err = AddRelay(rm.l, peer, f.hostMap, from, nil, ForwardingType, Requested)
...
peer.relayState.UpdateRelayForByIpState(from, Requested)
``` [5](#0-4) 

This is the mesh-VPN analog of the reported bug class: the protocol implicitly assumes that a VPN address named in a cross-node message ("RelayFromAddr") is controlled by the party asserting it, the same faulty assumption the external report flags for cross-chain messages that assume the same address is controlled by the same party on both ends. Here, any peer that has completed a normal handshake with `h` (i.e., any legitimately-provisioned but non-privileged node) can name an arbitrary victim VPN address as its own `RelayFromAddr` and get relay/forwarding state created that associates that victim address with a connection it does not control.

### Impact Explanation
The immediate effect is remote hostmap/relay-state poisoning: an authenticated but otherwise unprivileged peer can inject fabricated `Relay` entries (keyed by an arbitrary victim `vpnAddr`) into the relay tables of both the terminal node and any intermediate relay node, without owning a certificate for that address. Because relay control messages (unlike data packets) are processed based solely on the caller-supplied address fields rather than on the actual certificate bound to `h`, this breaks the assumption elsewhere in the codebase (e.g. in `handshake_manager.go`'s explicit self/consistency checks) that VPN-address-to-identity binding is always certificate-verified. At minimum this enables relay-table corruption and denial-of-service against the true owner of the victim address (repeatedly creating/overwriting `Disestablished`/`Requested` relay entries for it, interfering with legitimate relay negotiation for that address); depending on how forwarding state is later consumed by the data path, it also creates confusion about which connection is authorized to relay traffic "from" a given VPN address.

### Likelihood Explanation
Likelihood is Medium: the attack requires only a normal, valid certificate-holding node capable of establishing an ordinary tunnel and sending a `Control`/`CreateRelayRequest` message — no lighthouse compromise, no invalid certificate, and no privileged position is required. The `am_relay` flag is only required for the "not-target-is-me" forwarding branch; the "target is me" branch (poisoning my own relay state for an arbitrary `from` address) requires no special peer configuration at all.

### Recommendation
In `handleCreateRelayRequest` (and the analogous path in `handleCreateRelayResponse`), reject the message unless the claimed `RelayFromAddr`/`OldRelayFromAddr` equals one of `h.vpnAddrs` (the certificate-verified addresses of the sending `HostInfo`). Only the sender's own authenticated VPN address(es) should ever be usable as the "from" identity for relay state that gets attributed to that sender's connection.

### Proof of Concept
Conceptual PoC (not executed, given index-only access):
1. Attacker node `A` (valid cert for `10.0.0.5`) establishes a normal tunnel to victim/terminal node `T`.
2. `A` sends a `NebulaControl{Type: CreateRelayRequest, RelayFromAddr: <victim V's address, e.g. 10.0.0.9>, RelayToAddr: <T's own address>}` over its authenticated tunnel to `T`.
3. In `handleCreateRelayRequest`, since `target == T`'s own address, `T` executes `AddRelay(rm.l, h, f.hostMap, from=10.0.0.9, ..., TerminalType, Established)`, associating `A`'s `HostInfo` with relay state for `10.0.0.9` — an address `A` never proved ownership of via certificate.
4. `T` responds with `CreateRelayResponse` believing `A` is now a valid relay/terminal for `10.0.0.9`, corrupting `T`'s relay bookkeeping for the real owner of `10.0.0.9` and potentially disrupting/blocking genuine relay establishment for that address.

Note: I was unable to fully trace how `Relay.PeerAddr`/`relayForByAddr` state is subsequently consumed in the hot data-forwarding path (`outside.go`'s `handleOutsideRelayPacket`) to determine whether this can be escalated beyond state-poisoning/DoS to actual traffic redirection, since that requires deeper tracing of `RelayState`/`AddRelay` internals in `hostmap.go` that weren't fully retrievable through the index in this session. A Devin session with full repository access would be needed to confirm the exact downstream blast radius.
