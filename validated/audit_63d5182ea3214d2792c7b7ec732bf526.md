Confirmed: `receipt.success` is never referenced anywhere in the outbound-queue-v2 pallet code. The claim is fully verified against the repository.

Audit Report

## Title
Snowbridge `submit_delivery_receipt` pays relayer rewards and settles the order regardless of on-chain delivery `success` status - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`Pallet::process_delivery_receipt` fetches the `PendingOrder` for a nonce, unconditionally pays out `order.fee` as a relayer reward, and removes the order from storage — without ever checking `receipt.success`, even though `DeliveryReceipt` explicitly carries this field decoded from the Ethereum `InboundMessageDispatched` event log. [1](#0-0) [2](#0-1) 

## Finding Description
The `DeliveryReceipt` struct decoded from the Ethereum gateway's `InboundMessageDispatched` event contains an explicit `success` field, populated directly from the emitted event's `success` value during `TryFrom<&Log>`. [3](#0-2) 

`submit_delivery_receipt` verifies the cryptographic proof of the event log, decodes it into a `DeliveryReceipt`, and calls `process_delivery_receipt`. [4](#0-3) 

Inside `process_delivery_receipt`, the gateway address is checked, the pending order is looked up by nonce via `<PendingOrders<T>>::get(nonce).ok_or(...)`, and if `order.fee > 0` the reward is unconditionally registered via `T::RewardPayment::register_reward`, after which the order is removed from `PendingOrders` and a `MessageDelivered` event is emitted. [5](#0-4)  At no point is `receipt.success` read or branched on — a repo-wide search within the outbound-queue-v2 pallet for `success` returns no matches, confirming the field is fully unused there.

The existing guards (gateway address check, pending-order existence check) verify authenticity and outstanding status, but neither guard inspects whether the message was actually executed successfully on Ethereum. This matches the reported bug class exactly: settlement advances based on the *existence* of a record, not the *status flag* that should gate the payout.

## Impact Explanation
A relayer can submit a genuine, correctly-signed proof for an `InboundMessageDispatched` event where `success == false` (command execution failed/reverted on the Ethereum Gateway contract) and still receive the full relayer fee via `T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee)`, while the `PendingOrder` is permanently deleted from `PendingOrders` as if delivery had fully succeeded. This is an unbacked reward payout for work that did not succeed, and since the order is removed there is no path to retry or correct the accounting — a duplicate-settlement/underpriced-work condition in Snowbridge BridgeHub reward accounting, matching the "theft or unbacked mint or unlock, duplicate settlement or payout" impact category.

## Likelihood Explanation
This is reachable by any unprivileged relayer through the public `submit_delivery_receipt` extrinsic once a legitimate (verifier-passing) event proof exists showing `success: false`. No malicious peer, validator, or governance action is required — a normal failed dispatch on the Ethereum side (e.g., an underfunded or reverting command) naturally produces such an event, and the relayer merely submits it as-is.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success` before registering the reward: only call `T::RewardPayment::register_reward` when `receipt.success` is `true`; if `false`, still remove/settle the `PendingOrder` (to avoid unbounded growth) but emit a distinct event (e.g., `MessageDeliveryFailed`) and skip the reward payment, or apply a reduced/alternate compensation policy consistent with bridge design intent.

## Proof of Concept
1. A message is queued via `do_process_message`, creating `PendingOrders[nonce] = { nonce, fee: F, block_number }`. [6](#0-5) 
2. On Ethereum, the Gateway contract attempts dispatch but the command fails/reverts, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a valid Merkle/receipt proof for this event and calls `submit_delivery_receipt(event)`.
4. `T::Verifier::verify` succeeds (proof is legitimate), `DeliveryReceipt::try_from` decodes `success: false` correctly.
5. `process_delivery_receipt` never reads `receipt.success`; because `order.fee > 0`, it calls `T::RewardPayment::register_reward(&reward_account, ..., order.fee)`, removes `PendingOrders[nonce]`, and emits `MessageDelivered { nonce }` exactly as it would for a genuinely successful delivery.
6. The relayer is paid for a message that failed to execute on Ethereum; existing tests (e.g., `submit_delivery_receipt_succeeds_after_unhalt`) only exercise the `success: true` path, confirming the `false` branch is untested and unguarded. [7](#0-6)

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
