### Title
Missing pre-decode size gate on JSON-RPC transaction deserialization enables borsh-length-driven memory-allocation DoS - (File: `chain/jsonrpc/src/api/transactions.rs`)

### Summary
The nearcore team has already recognized and mitigated this exact bug class (crafted length-prefixed input forcing a large allocation before the actual bytes are validated) on the P2P network path, but the equivalent public JSON-RPC transaction-submission path has no such gate.

### Finding Description
`decode_signed_transaction` in the JSON-RPC layer takes a base64 string supplied directly by an RPC caller, decodes it, and immediately calls `SignedTransaction::try_from_slice(&bytes)` with no pre-decode size/shape validation: [1](#0-0) 

This function backs `broadcast_tx_async`, `broadcast_tx_commit`, `send_tx`, and `RpcTransactionStatusRequest` (`tx`) — all reachable by any unauthenticated caller against the public JSON-RPC port (default 3030): [2](#0-1) 

The only guard in front of this decode is the HTTP body-size middleware, `RequestBodyLimitLayer::new(limits_config.json_payload_max_size)` (10 MiB by default): [3](#0-2) [4](#0-3) 

That limit bounds the *bytes actually sent*, but it does not bound the *length values a borsh-encoded structure can claim*. `SignedTransaction`/`Transaction` contains nested `Vec` fields (e.g. the `actions: Vec<Action>` list, and `FunctionCallAction.args: Vec<u8>` inside it) whose borsh encoding is a 4-byte little-endian length prefix followed by that many elements. A small (well under 10 MiB) payload can declare a length prefix near `u32::MAX`, causing the deserializer to attempt to allocate space for billions of elements before it has confirmed that many bytes/elements actually exist in the buffer — the same "allocate first, validate later" pattern described in the reported gnark advisory.

Critically, nearcore's own network-protocol layer treats this as a real, exploitable threat and was hardened specifically against it: `chain/network/.../proto_conv/peer_message.rs` enforces `MAX_TRANSACTION_SIZE_BYTES`/`MAX_ROUTED_MESSAGE_SIZE_BYTES` *before* calling into borsh decoding, with comments explicitly stating the purpose is to stop "a maliciously inflated transaction exhausting node memory at decode time": [5](#0-4) 
and a reusable helper, `try_from_slice_with_limit`, was added for exactly this purpose: [6](#0-5) 

The reed-solomon chunk-decode path received the analogous fix (`MAX_ENCODED_LENGTH` check before allocation): [7](#0-6) 

No equivalent bound was applied to `decode_signed_transaction` in the JSON-RPC API, meaning the exact bug class that was fixed for peer-supplied transactions was left open for RPC-client-supplied transactions — an even more directly reachable, fully public entry point (no P2P handshake or peer trust required).

### Impact Explanation
An unauthenticated RPC caller can submit a crafted, small base64 blob decoding to a `SignedTransaction` with a manipulated borsh length prefix in a nested `Vec` field. If the borsh decoder (as the codebase's own hardening comments confirm for the same data type elsewhere) attempts to size/allocate a buffer proportional to the claimed length before validating remaining input, this can trigger an out-of-memory abort of the RPC-serving node process — a denial of service against any node exposing its JSON-RPC endpoint (which includes most public RPC providers and validator nodes' RPC listeners). This does not enable theft, replay, or state-root divergence, but it is a shard/node-halting-class panic reachable purely through an ordinary client submission, which the "Validate" criteria explicitly count as in-scope ("a shard-halting panic").

### Likelihood Explanation
High reachability: the endpoint is public and requires no authentication, no funds, and no prior state — a single crafted `broadcast_tx_async`/`send_tx`/`tx` call is sufficient. The only mitigating factor is the 10 MiB body-size cap, which limits how much attacker-controlled body content exists, but as reasoned above this does not limit the magnitude of the length field itself, only the actual bytes transmitted.

### Recommendation
Apply the same pre-decode defense used in `chain/network`'s `proto_conv` layer to the JSON-RPC transaction decode path: bound `decode_signed_transaction` (and any other RPC-facing borsh decode of client-controlled bytes, e.g. transaction/receipt status lookups) with an explicit maximum encoded-size check (reusing or mirroring `try_from_slice_with_limit`) prior to calling `SignedTransaction::try_from_slice`, sized to the largest legitimate transaction (consistent with `MAX_TRANSACTION_SIZE_BYTES` used on the network path). Additionally, verify/patch the underlying borsh `Vec<T>` deserialization behavior (if not already fixed in the pinned borsh version) to validate a length prefix against remaining reader bytes before allocating, independent of call site.

### Proof of Concept
Not independently reproduced against a live node in this analysis (would require compiling nearcore against the exact borsh version pinned in `Cargo.lock`, which is outside the scope of static code review). The claim rests on: (1) the code's own documented threat model in `chain/network/.../peer_message.rs` and `.../reed_solomon.rs`, which explicitly identify "maliciously inflated" borsh length fields on this same `SignedTransaction`/action-vector data as a memory-exhaustion vector, and (2) the absence of the analogous guard on the `chain/jsonrpc` decode path (`decode_signed_transaction`), confirmed by direct code inspection. Concretely, a PoC would: construct a `TransactionV0`-shaped byte buffer with a valid short prefix, then overwrite the 4-byte little-endian length prefix of the `actions` `Vec<Action>` field (or an inner `Vec<u8>`/`Vec<Action>` field) with a large value (e.g., `0xFFFFFFFE`) while keeping total payload under 10 MiB, base64-encode it, and POST it to `broadcast_tx_async` via the JSON-RPC endpoint.

/// Borsh-deserializes `T` from `bytes`, rejecting inputs larger than `limit`
/// before decoding so a maliciously inflated peer payload cannot force a large
/// allocation at decode time. Use this for any peer-supplied borsh blob whose
/// decoded form can be much larger than its wire size; `limit` must sit above
/// the largest legitimate encoding of `T` and well below the peer-frame cap.
/// Returns `io::Error` so it composes with the borsh-based proto decode sites.
pub fn try_from_slice_with_limit<T: BorshDeserialize>(bytes: &[u8], limit: usize) -> io::Result<T> {
    if bytes.len() > limit {
        return Err(io::Error::new(
            io::ErrorKind::InvalidData,
            format!("encoded size {} exceeds the limit of {limit} bytes", bytes.len()),
        ));
    }
    T::try_from_slice(bytes)
}
