### Title
Explicit re-enable of the `file://` submodule transport in `git_repository`/`new_git_repository` submodule fetching allows a malicious repository to make Bazel read local files outside the intended checkout - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_repository`/`new_git_repository` support `init_submodules`/`recursive_init_submodules`, which run `git submodule update --init` inside the freshly cloned, attacker-published repository. To work around upstream Git's own hardening, Bazel explicitly re-enables the `file` transport for this step with `-c protocol.file.allow=always`, which is exactly the setting Git added in response to a submodule-based local information-disclosure vulnerability (the class fixed for CVE-2022-39253). Because `.gitmodules` content is part of the untrusted repository being fetched (a dependency URL an attacker publishes, or an untrusted branch that CI builds), the attacker fully controls the submodule URLs that get passed to git with this restriction disabled.

### Finding Description
`update_submodules()` always invokes submodule update with the file protocol explicitly allowed: [1](#0-0) 

The comment right above it acknowledges this is a deliberate re-enabling of a capability Git restricts by default: [1](#0-0) 

The submodule URLs themselves come from `.gitmodules`, a file that lives inside the repository content being fetched by `git_repo()`/`fetch()`/`reset()` — i.e., content the attacker (the publisher of the `remote` repo, or whoever controls an untrusted branch that CI checks out) fully controls: [2](#0-1) 

Git's own default (since the fix for the local-clone/`file://` submodule disclosure issue) is to require `protocol.file.allow` to be something other than `always` for automatically-triggered transports like submodule recursion, precisely because a hostile repository's `.gitmodules` can point a submodule at `file://<local path>` and trigger Git's local-clone hardlink/object-sharing optimization against arbitrary paths readable by the invoking user. By hard-coding `-c protocol.file.allow=always` for every `submodule update --init` call (both the non-recursive and recursive variants), Bazel unconditionally strips this protection for every `git_repository`/`new_git_repository` invocation that sets `init_submodules`/`recursive_init_submodules`, regardless of whether the `remote` is trusted.

The `_execute` wrapper does not sandbox or restrict the working directory beyond `working_directory = str(git_repo.directory)`, and no containment check is applied to the resolved submodule paths before/after the update: [3](#0-2) 

### Impact Explanation
An attacker who controls the content of a `git_repository`/`new_git_repository` target's `remote` (e.g. any external dependency hosted at a URL the attacker controls, or a repository/branch built by CI where the attacker can land a PR/branch) can embed a `.gitmodules` entry pointing a submodule at a `file://` path on the build host. With `protocol.file.allow=always` forced on, Git will perform its local-clone object-sharing/hardlinking behavior against that local path during `submodule update --init`, which is the exact primitive Git restricted by default to stop information disclosure of files/objects outside the intended repository boundary. This lets attacker-published content pull data from elsewhere on the build machine's filesystem into the fetched repository tree, which then becomes an input to the build (and can be exfiltrated further via build outputs, logs, or a later network-accessible artifact) — a read outside the intended repository boundary driven entirely by untrusted, attacker-supplied content.

### Likelihood Explanation
Any consumer of `git_repository`/`new_git_repository` with `init_submodules = True` or `recursive_init_submodules = True` pointed at a third-party or otherwise untrusted `remote` (a very common bzlmod/WORKSPACE pattern for fetching external dependencies) is affected by default — there is no opt-out flag exposed by the rule, and the dangerous flag is unconditional in `update_submodules()`. No special network position is required beyond being able to host/serve the `remote` repository content (or land it on a branch that CI builds), matching the attacker model of the underlying Registrator.jl-class bug: hostile content served at a URL the victim's build fetches, reaching an argument/flag-sensitive code path.

### Recommendation
Do not force `protocol.file.allow=always` for submodule operations. Instead, only allow the `file` protocol when required and scope it, or default to Git's safer restricted behavior, letting users opt in explicitly per-repository (documenting the risk) instead of Bazel silently overriding Git's hardening for every `git_repository` invocation that has submodules enabled.

### Proof of Concept
Using Bazel's existing git repository shell test harness (e.g. `src/test/shell/bazel/git_repository_test.sh`) as the scaffold:
1. Create `outer-repo`, a bare git repo that will be used as `remote` for a `git_repository(..., init_submodules = True)` target.
2. Inside `outer-repo`, add a `.gitmodules` entry: `url = file:///<absolute path to a sensitive local directory/repo on the build host>` for a submodule.
3. Add a `WORKSPACE`/`MODULE.bazel` entry: `git_repository(name = "outer", remote = "<outer-repo path>", init_submodules = True, ...)`.
4. Run `bazel fetch //external:outer` (or a target depending on `@outer`) and observe `git -c core.fsmonitor=false -c protocol.file.allow=always submodule update --init --checkout --force` executing against the attacker-chosen `file://` path, exercising Git's local-clone object-sharing behavior against a path outside `outer-repo`'s own tree, in the same class of local-repository content disclosure that upstream Git's `protocol.file.allow` restriction (post CVE-2022-39253) was designed to prevent.

def git_repo(ctx, directory):
    """ Fetches data from git repository and checks out file tree.

    Called by git_repository rule.

    Args:
        ctx: Context of the calling rules, for reading the attributes.
        Please refer to the git_repository rule for the description.
        directory: Directory where to check out the file tree.
    Returns:
        The struct with the following fields:
        commit: Actual HEAD commit of the checked out data.
        shallow_since: Actual date and time of the HEAD commit of the checked out data.
    """
    if ctx.attr.shallow_since:
        if ctx.attr.tag:
            fail("shallow_since not allowed if a tag is specified; --depth=1 will be used for tags")
        if ctx.attr.branch:
            fail("shallow_since not allowed if a branch is specified; --depth=1 will be used for branches")

    # Use shallow-since if given
    if ctx.attr.shallow_since:
        shallow = "--shallow-since=%s" % ctx.attr.shallow_since
    else:
        shallow = "--depth=1"

    reset_ref = ""
    fetch_ref = ""
    if ctx.attr.commit:
        reset_ref = ctx.attr.commit
        fetch_ref = ctx.attr.commit
    elif ctx.attr.tag:
        reset_ref = "tags/" + ctx.attr.tag
        fetch_ref = "tags/" + ctx.attr.tag + ":tags/" + ctx.attr.tag
    elif ctx.attr.branch:
        reset_ref = "origin/" + ctx.attr.branch
        fetch_ref = ctx.attr.branch + ":origin/" + ctx.attr.branch
    else:
        reset_ref = "origin/HEAD"
        fetch_ref = "HEAD:refs/remotes/origin/HEAD"

    git_repo = _GitRepoInfo(
        directory = ctx.path(directory),
        shallow = shallow,
        reset_ref = reset_ref,
        fetch_ref = fetch_ref,
        remote = str(ctx.attr.remote),
        init_submodules = ctx.attr.init_submodules,
        recursive_init_submodules = ctx.attr.recursive_init_submodules,
    )

def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")

def _execute(ctx, git_repo, args):
    # "core.fsmonitor=false" disables git from spawning a file system monitor which can cause hangs when cloning a lot.
    # See https://github.com/bazelbuild/bazel/issues/21438
    start = ["git", "-c", "core.fsmonitor=false"]
    return ctx.execute(
        start + args,
        environment = ctx.os.environ | _GIT_LOCAL_ENV_VARS,
        working_directory = str(git_repo.directory),
    )
