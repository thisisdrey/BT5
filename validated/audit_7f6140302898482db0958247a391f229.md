### Title
Unbounded `sock.read_to_end(&mut buf)` in `run_http_request` allows a malicious StackerDB host to force unbounded memory growth on the signer - ([File: libsigner/src/http.rs])

### Summary
`run_http_request` reads an HTTP response into `buf` via `sock.read_to_end(&mut buf)` with no byte cap of any kind, before `decode_http_response` or any `MAX_MESSAGE_LEN`-style check is applied. A StackerDB host the signer connects to (attacker-controlled host, or a MITM of that plaintext connection) can trickle bytes slowly enough to avoid the per-`read()` socket timeout while never sending EOF, growing `buf` without bound and consuming memory/CPU on the signer.

### Finding Description
In `libsigner/src/http.rs`, `run_http_request` does: [1](#0-0) 
`sock.write_all(req_txt.as_bytes())?; sock.write_all(payload)?; let mut buf = vec![]; sock.read_to_end(&mut buf)?;` — only after this unbounded read completes (i.e., after the socket returns EOF or an error) is `decode_http_response(&buf)` called at line 253. There is no `MAX_MESSAGE_LEN` or any other length cap applied to `buf` while it's being filled, unlike `decode_http_body`, which does bound its chunked-decoding via `HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into())` (`libsigner/src/http.rs:207`).

The only mitigating control present is a per-operation socket read timeout set via `sock.set_read_timeout(Some(self.socket_timeout))` in `StackerDBSession::connect_or_reconnect` (`libsigner/src/session.rs:132`). This timeout bounds the maximum *idle gap* between successful reads on the underlying `TcpStream`, but `read_to_end` loops calling `read()` repeatedly and keeps appending to `buf` as long as each individual `read()` call returns data before its own timeout elapses. A malicious/MITM host can drip-feed bytes (e.g., one byte every `socket_timeout - ε`) indefinitely, so the total bytes read into `buf`, and the total wall-clock time of the call, are both unbounded by any protocol-declared length or session-level cap. Only the OS/process memory limit or an external caller-imposed timeout (none exists in this call path) would eventually stop it.

The call chain is: `StackerDBSession::rpc_request` (`libsigner/src/session.rs:162-172`) → `run_http_request` (`libsigner/src/http.rs:221-262`) → unbounded `sock.read_to_end` → `decode_http_response`. `rpc_request` is used by `list_chunks`, `get_chunks`, `get_latest_chunks`, and `put_chunk` in `StackerDBSession` (`libsigner/src/session.rs:188-273`), all of which are invoked by the signer when it queries/pushes chunks to the StackerDB host it's configured against.

### Impact Explanation
A malicious or MITM'd StackerDB host can force the signer process to allocate unbounded memory in a single RPC response (per rpc_request call), causing a bounded-per-connection compute/memory DoS on the signer's outbound RPC parsing path. This matches the "High - bounded compute DoS on a read endpoint" category since it's not simple traffic-volume flooding — no length cap exists to stop the buffer from growing regardless of connection duration, only the socket idle-timeout, which the drip-feed technique circumvents.

### Likelihood Explanation
Preconditions: the signer must be configured to talk to (or be MITM'd while talking to) a StackerDB host that is attacker-controlled — this is exactly the threat model named in the question (malicious StackerDB host or a MITM of the plaintext session). No secret, privileged role, or additional access is required beyond controlling that endpoint; the attacker only needs to accept the signer's TCP connection and respond deliberately slowly with unterminated data. The attack is repeatable on every RPC call the signer makes to that host (`list_chunks`/`get_chunks`/`put_chunk` etc.), so it can be sustained indefinitely.

### Recommendation
Bound the response read with an explicit cap (e.g. `MAX_MESSAGE_LEN`) using a size-limited reader (e.g., `Read::take(MAX_MESSAGE_LEN as u64)` combined with checking for truncation, or a manual loop that reads in a bounded buffer and errors out once total bytes read exceeds the cap) instead of unconditional `sock.read_to_end(&mut buf)`, mirroring the bound already applied in `decode_http_body`'s `HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into())`.

### Proof of Concept
```rust
// libsigner/src/http.rs (test module)
use std::io::{Read, Write};
use std::net::{TcpListener, TcpStream};
use std::thread;
use std::time::Duration;

#[test]
fn run_http_request_unbounded_read_dos() {
    let listener = TcpListener::bind("127.0.0.1:0").unwrap();
    let addr = listener.local_addr().unwrap();

    thread::spawn(move || {
        if let Ok((mut stream, _)) = listener.accept() {
            let mut req_buf = [0u8; 4096];
            let _ = stream.read(&mut req_buf); // consume request
            stream.write_all(b"HTTP/1.1 200 OK\r\n\r\n").unwrap();
            // Drip-feed bytes forever, each write spaced under any reasonable
            // per-read timeout, and never close the connection (no EOF).
            loop {
                if stream.write_all(&[b'A'; 1024]).is_err() {
                    break;
                }
                thread::sleep(Duration::from_millis(50));
            }
        }
    });

    let mut sock = TcpStream::connect(addr).unwrap();
    sock.set_read_timeout(Some(Duration::from_secs(2))).unwrap();
    sock.set_write_timeout(Some(Duration::from_secs(2))).unwrap();

    // Expect run_http_request to enforce a cap (e.g. MAX_MESSAGE_LEN) and
    // return an error once that cap is exceeded, rather than hanging/growing
    // buf without bound. Currently this call never returns (or grows buf
    // unbounded) because read_to_end has no size cap.
    let result = libsigner::http::run_http_request(&mut sock, "test", "GET", "/", None, &[]);
    assert!(result.is_err(), "expected a bounded-length error, got unbounded read");
}
```
This test demonstrates that `run_http_request`/`sock.read_to_end` has no enforced maximum, since the drip-fed connection (never sending EOF) causes the call to block/grow `buf` indefinitely rather than erroring out at a validated cap.
