### Title
Rewards emitted while a tracked token has zero supply are permanently lost because the index timestamp still advances - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenIndex` advances `tokenStates[token_].timestamp` even when `totalSupply == 0`, so `speed * deltaTimestamp` worth of reward emission for that period is discarded rather than deferred — the same bug class as the LiquidityMining finding, where a boundary condition in accrual bookkeeping causes a period's accrued rewards to be skipped and never recoverable.

### Finding Description
In `accrueConcentratedPositionTimeWeightedLiquidity`, an equality edge case (`exitTimestamp == nextWeek`) failed to advance `tickTrackingIndex`, permanently losing a tick period's accrual. The Metronome analog is the "zero-supply" edge of the reward index: [1](#0-0) 

When `tokenSpeeds[token_] > 0` and `_deltaTimestamps > 0`, the code computes `_ratio = 0` when `token_.totalSupply() == 0`, but still returns `_newTimestamp = block.timestamp`. `_updateTokenIndex` then persists that timestamp: [2](#0-1) 

Every block/second elapsed while the tracked `DepositToken`/`DebtToken` has zero supply emits `speed` tokens that are credited to no index — they are gone from the accrual schedule forever (there is no catch-up or sweep path; `tokensAccruedOf` is the only claim route [3](#0-2) ).

Reachability: any EOA can force this state. Withdrawing the last deposit via `Pool.withdraw` (which calls `DepositToken.burn` after `updateBeforeMintOrBurn` [4](#0-3) ) or repaying the last debt brings `totalSupply` to 0 while `tokenSpeeds` remains > 0, since speeds are only zeroed by governor/keeper calls (`updateTokenSpeed`, `syncTokenSpeed` [5](#0-4) ). No modifier, pause flag, or reentrancy guard prevents the last holder from exiting while speed is non-zero.

### Impact Explanation
Invariant broken: reward accrual conservation — emitted `speed * dt` rewards should be attributable to some index/account. Instead, the entire zero-supply interval's emission is silently dropped, permanently reducing distributable yield. The stranded reward tokens remain in the contract with no claim path, amounting to permanent freezing of unclaimed yield.

### Likelihood Explanation
Requires a tracked token with `speed > 0` to reach `totalSupply == 0` and remain there while time passes — plausible at pool launch (speed set before first deposit), during full exits/deleveraging, or between Vesper `syncTokenSpeed` updates. Likelihood is moderate but the loss compounds linearly with the zero-supply duration.

### Recommendation
Do not advance `timestamp` (or pause effective accrual) when `totalSupply == 0` and `_speed > 0`, so the unallocated emission either accrues into the next non-zero-supply index update or is explicitly deferred. E.g., in `_calculateTokenIndex`, return `_newTimestamp = _supplyState.timestamp` when `_totalSupply == 0`, or treat zero supply like zero speed for timestamp purposes only after recording the gap.

### Proof of Concept
```solidity
// Foundry fork-style PoC
// 1. Governor sets speed: rd.updateTokenSpeed(depositToken, 1e18)
// 2. Alice deposits => depositToken.totalSupply() > 0; index accrues normally.
// 3. Alice withdraws all => totalSupply() == 0.
// 4. vm.warp(block.timestamp + 1 days); mine a block.
// 5. Anyone calls rd.updateBeforeMintOrBurn(depositToken, alice) (permissionless)
//    or any mint/burn triggers it via updateRewardsBeforeMintOrBurn.
// 6. Assert: tokenStates[depositToken].timestamp == block.timestamp
//           && tokenStates[depositToken].index == INITIAL_INDEX
//    => 86400 * 1e18 reward emission permanently dropped; no account can ever
//       claim it, and future depositors' index starts from the new timestamp.
```
Note: I could not fully verify `_calculateInterestAccrual` in `DebtToken.sol` (its body was outside the indexed range), so a second potential analog — `accrueInterest` writing `lastTimestampAccrued = block.timestamp` unconditionally (line 167) even if the calculation capped accrual at an earlier time — remains unconfirmed.

    function _calculateTokenIndex(
        TokenState memory _supplyState,
        IERC20 token_
    ) private view returns (uint224 _newIndex, uint32 _newTimestamp) {
        uint256 _speed = tokenSpeeds[token_];
        uint256 _deltaTimestamps = block.timestamp - uint256(_supplyState.timestamp);
        if (_deltaTimestamps > 0 && _speed > 0) {
            uint256 _totalSupply = token_.totalSupply();
            uint256 _tokensAccrued = _deltaTimestamps * _speed;
            uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
            _newIndex = (_supplyState.index + _ratio).toUint224();
            _newTimestamp = block.timestamp.toUint32();
        } else if (_deltaTimestamps > 0 && _supplyState.index > 0) {
            _newTimestamp = block.timestamp.toUint32();
        }
    }

        TokenState storage _supplyState = tokenStates[token_];
        (uint224 _newIndex, uint32 _newTimestamp) = _calculateTokenIndex(_supplyState, token_);
        if (_newIndex > 0 && _newTimestamp > 0) {
