### Title
Unchecked `new_authority` allows account migration to the zero address, permanently locking migrated funds - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
The `transfer_to_new_account` / `transfer_to_new_account_pda` instructions let an account authority migrate their `MarginfiAccount` (with all its lending balances) to a new account under a caller-supplied `new_authority` pubkey. That pubkey is accepted as a raw `UncheckedAccount` with no validation that it is non-default, mirroring the class of bug described in the external report (an `onBehalfOf`/beneficiary-style parameter accepted without a zero-address check).

### Finding Description
`TransferToNewAccount` and `TransferToNewAccountPda` declare: [1](#0-0) [2](#0-1) 

The doc comment itself flags this as "completely unchecked." The value is then written directly into the new account as its `authority` with no zero-address (or any other) validation: [3](#0-2) [4](#0-3) 

The migration path zeroes out the old account's lending state and marks it disabled/migrated, so the old account can never again be used to access those balances — funds now live exclusively on the new account: [5](#0-4) 

If the caller (the current, legitimate authority) sets `new_authority` to `Pubkey::default()` (the zero/all-zero key), the newly created `MarginfiAccount.authority` becomes the zero address. All subsequent account-authority-gated instructions require a `Signer<'info>` whose key matches `MarginfiAccount.authority` (see e.g. `MarginfiAccountUpdateEmissionsDestinationAccount`, which constrains `authority` to `address = marginfi_account.load()?.authority`): [6](#0-5) 

Because nobody can produce a valid Ed25519 signature for the all-zero public key on Solana (there is no discoverable/derivable private key for `Pubkey::default()`), any instruction requiring the account authority to sign becomes permanently unreachable for that account. This differs from the account-creation path (`MarginfiAccountInitialize`/`MarginfiAccountInitializePda`), where `authority` is itself a `Signer`, so the creator must already be able to sign as that key — making a zero-address authority effectively unreachable there. The migration path breaks that invariant because `new_authority` is supplied as data, not as a signer, allowing a value to be set that no signer can ever satisfy.

### Impact Explanation
This is a genuine unprivileged-user-triggerable, concrete permanent lock/freeze of funds: an account authority (rug/self-inflicted) or, more importantly, any code path that programmatically drives migration with an unchecked/attacker-influenced destination could brick the migrated balances by setting `new_authority = 0x00..00`. Once migrated, the account's lending balances (assets and liabilities) are stuck: no instruction can act on the account since none of `is_signer_authorized`/authority-address constraints can ever be satisfied by a signer of the zero pubkey, and the old account has already been zeroed and disabled, so there is no rollback path. This matches the "permanent lock/freeze" acceptance criterion.

### Likelihood Explanation
The instruction is permissionless from the perspective of the account owner (no special privilege needed — the current authority alone can invoke it), and the vulnerable field (`new_authority`) is a plain unchecked account with no on-chain guard, no CPI restriction relevant to it, and no client-side enforcement that is authoritative (client-side checks are not a security boundary). The only precondition is that the caller/authority chooses (or is tricked/automated into passing) the zero address as the destination authority — a single missing `require!(new_authority.key() != Pubkey::default())` check.

### Recommendation
Add an explicit check in both `transfer_to_new_account` and `transfer_to_new_account_pda` that `ctx.accounts.new_authority.key() != Pubkey::default()` (and ideally also reject the marginfi program ID or other known sentinel/system addresses) before writing it into `new_account.authority`, returning a dedicated error (e.g. `MarginfiError::InvalidAuthority`) otherwise.

### Proof of Concept
1. Create a `MarginfiAccount` and deposit funds into a bank via the normal user flow.
2. Call `transfer_to_new_account` (or `transfer_to_new_account_pda`), supplying:
   - `old_marginfi_account`: the existing account (authority signs)
   - `new_marginfi_account`: a fresh account/PDA to initialize
   - `new_authority`: `Pubkey::default()` (all-zero key), passed as the `UncheckedAccount`
3. Instruction succeeds because there is no validation on `new_authority`: [7](#0-6) 
4. `old_account` is now disabled/zeroed and `new_account.authority == Pubkey::default()`.
5. Attempt any authority-gated instruction on `new_account` (e.g. `marginfi_account_update_emissions_destination_account`, `lending_account_withdraw`, etc.) — none can be signed because no keypair can produce a valid signature for the zero pubkey, permanently locking the migrated balances.
