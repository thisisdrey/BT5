### Title
Front-runnable deterministic Safe address squatting can permanently block `SmartAccountFactory.deploySmartAccount` for a given (deployer, nonce) - (File: `tare-io__tare-contracts/contracts/SmartAccountFactory.sol`)

### Summary
`SmartAccountFactory.deploySmartAccount` computes a fully deterministic CREATE2 salt from `msg.sender`, an auto-incrementing per-deployer nonce, and a hash of the exact Safe initializer parameters, then calls the permissionless `SafeProxyFactory.createProxyWithNonce` with that salt [1](#0-0) . Because `SafeProxyFactory` is a standard, permissionless, external contract that anyone can call directly, an attacker who observes a pending `deploySmartAccount` transaction in the mempool can extract its exact parameters and race it by calling `SafeProxyFactory.createProxyWithNonce` directly with the same `singleton`, `initializer`, and `saltNonce`. This deploys a Safe proxy at the exact address the victim's transaction was going to produce, causing the victim's subsequent `createProxyWithNonce` call inside `deploySmartAccount` to revert on the CREATE2 address collision.

### Finding Description
The salt used for the Safe's CREATE2 deployment is `keccak256(keccak256(initializer), saltNonce)`, where `saltNonce = keccak256(msg.sender, nonces[msg.sender])` [2](#0-1) . Both `nonces[deployer]` and the intended initializer parameters (delegates, currencies, nftCollections, trustedRecipients, validUntil, owners, threshold) are either public (`nonces` is a public mapping, see `ISmartAccountFactory.nonces`) or trivially readable from the pending transaction's calldata in the mempool.

Because `SafeProxyFactory` is a standard, publicly callable contract (not access-restricted to `SmartAccountFactory`), any address can pre-empt the deployment by calling `createProxyWithNonce(SAFE_SINGLETON, initializer, saltNonce)` directly with the exact same arguments, deploying a Safe proxy to the identical CREATE2 address before the victim's transaction lands.

When the victim's `deploySmartAccount` transaction then executes, `SAFE_PROXY_FACTORY.createProxyWithNonce` will revert because the CREATE2 target address already has code ("Create2 call failed" in the underlying Safe factory). This reverts the entire `deploySmartAccount` call, including the `nonces[msg.sender]++` state change performed earlier in the same function [3](#0-2) . Since the nonce increment is rolled back on revert, a naive retry with identical parameters recomputes the exact same `saltNonce`/salt and fails again — this is structurally the same root cause as the reported bug class: a public, unrestricted contract call lets an attacker occupy a deterministic address that the legitimate factory depends on, before the factory itself can use it, forcing the factory's calls for that slot to permanently revert unless the caller changes some input that shifts the salt.

The `isDeployedSmartAccount` provenance mapping — used by integrators/other contracts to verify a Safe was deployed via this factory — is only ever set to `true` inside a successful `deploySmartAccount` call [4](#0-3) , so a squatted Safe address (even though deployed with the victim's intended owners/threshold via the raw `SafeProxyFactory` call) will never be recognized as a legitimate Tare-deployed smart account.

### Impact Explanation
An attacker monitoring the mempool can repeatedly block a specific deployer's `deploySmartAccount` calls for a given nonce/parameter combination, since the nonce does not advance on revert. This can be used to grief onboarding of protocol-critical role accounts (e.g. originator, investor, borrower, servicer Safes provisioned via `create-role-accounts`/`create-smart-account` CLI flows) that ops scripts deploy with fixed, predictable parameters, delaying or blocking funding/disbursement setup that depends on those Safes existing and being recognized via `isDeployedSmartAccount`.

### Likelihood Explanation
The likelihood is limited by two factors: (1) the attacker must actively front-run a specific pending transaction with correctly extracted calldata and pay gas each time; and (2) the deployer can trivially escape the block by varying any parameter that changes the initializer hash (e.g. adding/removing a delegate or currency), which changes the salt. This makes the DoS a griefing/annoyance vector rather than an unconditional permanent lock, but it is a real, unprivileged, reachable path that a background agent should evaluate for hardening (e.g. restricting or wrapping the underlying `SafeProxyFactory` interaction, or making `deploySmartAccount` resilient to pre-existing code at the predicted address).

### Recommendation
Consider one or more of:
- Detect the "already deployed at predicted address" case and, instead of reverting, check whether the deployed Safe matches the intended configuration and register it in `isDeployedSmartAccount` if so.
- Incorporate an unpredictable/private component into the salt (e.g., a commit-reveal scheme, or requiring a fresh random salt supplied off-chain right before submission) so attackers cannot pre-compute the exact salt from mempool-visible data.
- Advance `nonces[msg.sender]` even on the specific "address collision" failure path so a stuck nonce doesn't block all future attempts indefinitely, e.g. catch the collision and auto-retry with the next nonce internally.

### Proof of Concept
1. Deployer submits `deploySmartAccount(delegates, currencies, nftCollections, trustedRecipients, validUntil, owners, threshold)` from address `D`. This is visible in the mempool with `nonces[D] = n`.
2. Attacker computes `saltNonce = keccak256(abi.encodePacked(D, n))` and rebuilds the identical `initializer` bytes from the visible calldata.
3. Attacker calls `SAFE_PROXY_FACTORY.createProxyWithNonce(SAFE_SINGLETON, initializer, saltNonce)` directly with higher gas price, landing before the deployer's transaction.
4. Deployer's `deploySmartAccount` transaction executes: `SAFE_PROXY_FACTORY.createProxyWithNonce` reverts due to CREATE2 address collision; the whole call reverts, `nonces[D]` remains `n`.
5. Any retry by `D` using the same parameters recomputes the identical salt/address and reverts again, until `D` changes some initializer-affecting parameter.
