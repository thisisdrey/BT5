### Title
Missing bounds validation in ZIP central directory entry parsing leads to out-of-bounds read - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar's ZIP reader parses the length-prefixed `file_name`, `extra_field`, and `file_comment` fields of a central directory entry and advances the cursor `p` by these attacker-controlled 16-bit lengths without ever checking that the resulting reads stay inside the input file, unlike its sibling `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` before every variable-length field read.

### Finding Description
`FindZipCentralDirectory` validates only that the *aggregate* central directory (`central_dir_offset + central_dir_size`) fits within the mapped input file: [1](#0-0) 

Once that coarse check passes, individual entries inside the central directory are parsed by `ProcessCentralDirEntry`, which reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from attacker-controlled bytes and blindly advances `p` and `extra_p` by those values, including inside the ZIP64 extra-field loop: [2](#0-1) 

There is no call to `EnsureRemaining()` anywhere in this function, in contrast to `ProcessLocalFileEntry`, which validates every variable-length read against the file bounds before dereferencing: [3](#0-2) 

Because `file_name_length`, `extra_field_length`, and `file_comment_length` are each 16-bit values fully controlled by the crafted ZIP/JAR, an entry near the end of the (validly-bounded) central directory block can declare lengths that push `p`/`extra_p` past the end of the mmap'd file, or past the legitimate central-directory boundary while still landing on mapped memory belonging to other file sections, producing an out-of-bounds read (crash via `SIGSEGV`, or exposure of adjacent memory content, e.g., through the copied `filename` buffer at line 520 or the ZIP64 field parsing at 526–541) analogous to the missing length-check in ImageMagick's `Get8BIMProperty`.

### Impact Explanation
An attacker who serves or publishes a JAR/ZIP (e.g., a maven/http_jar/http_archive artifact consumed by java rules, whose interface jar is generated by invoking ijar on the artifact at build time) can craft a central directory entry with an oversized `file_name_length`/`extra_field_length`/`file_comment_length` to trigger reads outside the file's mapped/validated region. This can crash the ijar tool (denial of service for that build action) or leak adjacent process memory content into build outputs/error messages, matching the out-of-bounds read/memory leak class of ALPINE-CVE-2016-6491. A valid sha256/integrity check on the downloaded jar does not prevent this, since the attacker controls the exact bytes that are hashed — the checksum only proves the bytes weren't altered in transit, not that the internal ZIP structure is well-formed.

### Likelihood Explanation
Any build that processes a jar via ijar (virtually all `java_library`/`java_import` targets, including those sourced from external repositories or a compromised mirror/registry) reaches this code path automatically without any explicit opt-in, making the reachable surface large. Crafting a malicious central directory entry only requires basic ZIP format knowledge, no privileged access.

### Recommendation
Add `EnsureRemaining()` (or equivalent bounds checks against the validated central directory bounds and overall file length) before every variable-length read in `ProcessCentralDirEntry`, mirroring the checks already present in `ProcessLocalFileEntry`, and validate that `extra_p + data_size` does not exceed `p` in the ZIP64 extra-field parsing loop.

### Proof of Concept
Construct a minimal ZIP file whose EOCD/central-directory-size fields satisfy `FindZipCentralDirectory`'s aggregate bound check, but whose single central directory entry declares `file_name_length = 0xFFFF` (or `extra_field_length`/`file_comment_length` similarly oversized) such that `central_dir_ + entry_offset + fixed_header_size + file_name_length` exceeds the mmap'd file length. Feed this file to the `ijar` binary (`third_party/ijar/ijar.cc` driver invoking `ZipExtractor::Create`/`ProcessAll`) and observe a crash or out-of-bounds read reported by ASan, which a `BuildIntegrationTestCase`/shell test invoking `bazel build` on a `java_library` depending on this crafted jar can capture as the reproduction harness.
