### Title
Incomplete `remove_account` state teardown lets postponed/received-data/promise-yield rows survive `DeleteAccount` and execute against a later account of the same name - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` only deletes the `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` rows for an account, but the account-scoped column list in `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` also includes `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId`. None of these are cleaned up on `DeleteAccount`, so any pending cross-contract-call state (postponed action receipts, unresolved promise yields) outlives the account and is keyed only by the bare `AccountId` string with no generation/liveness marker.

### Finding Description
`remove_account` (`core/store/src/utils/mod.rs:505-575`) removes only `TrieKey::Account`, `TrieKey::ContractCode`, access keys/gas-key nonces (via `get_raw_prefix_for_access_keys`), and `TrieKey::ContractData` (via `get_raw_prefix_for_contract_data`): [1](#0-0) [2](#0-1) 

The authoritative list of every column that is keyed by `account_id`, `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY`, additionally lists `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId`: [3](#0-2) 

None of these are touched by `remove_account`, and `RemoveAccountResult` only tracks `gas_key_nonce_count`/`gas_key_nonce_total_key_bytes`, confirming the omission was not accounted for: [4](#0-3) 

The receipt-processing code that later reads/executes these rows does so purely by `account_id` (the receiver of the receipt), with no check that the account instance is the same one that created the postponed state. In `process_receipt` (`runtime/runtime/src/lib.rs`), an incoming `Data` receipt looks up `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` solely keyed by `receiver_id` and, once complete, calls `apply_action_receipt` against whatever account currently exists at that id: [5](#0-4) 

Similarly, `PromiseResume` receipts resolve `PromiseYieldReceipt`/`PromiseYieldStatus`/yield-id mappings by `account_id` only and execute the parked receipt against the current account: [6](#0-5) 

Exploit flow: an account `X` issues an outgoing async call to itself (or another party) creating a `PostponedReceipt`/`PromiseYieldReceipt` awaiting a data dependency (e.g., a cross-contract callback, or a `promise_yield_create` self-call). Before the dependency is delivered, `X` submits `DeleteAccount`, freeing the account name while the postponed rows remain in the trie under key `X`. Because NEAR permits any account name to be re-registered once deleted, an unrelated party can later create a brand-new account also named `X` and deploy its own contract there. When the original dependent `Data`/`PromiseResume` receipt is finally delivered (its delivery timing is controlled by whenever the attacker/predecessor chooses to resolve it, or automatically via the promise-yield timeout queue), the runtime finds the stale `PostponedReceipt`/`PromiseYieldReceipt` for account `X` and executes it in the context of the *new* account `X`, using the new account's live state, storage, and code. Since receiver_id/predecessor_id are plain strings, any self-only ("private") method check in the new contract (`predecessor_account_id() == current_account_id()`) is satisfied purely by the recycled name match, letting the stale receipt invoke privileged self-only entry points on a contract it was never authorized against.

None of the existing checks catch this: `DeleteAccount` has no requirement that pending postponed/promise-yield state be empty, account re-creation has no generation counter, and `check_account_existence`/access-key checks only validate that an account named `X` exists — they cannot distinguish "the same `X`" from "a different `X` that reused the name."

### Impact Explanation
This is authorization escalation across accounts/promises: an attacker can arrange for privileged, self-scoped receipt execution (originally authorized only for the deleted account) to run against a different, later, unrelated contract deployment under the same account name, matching the "authorization escalation across accounts or promises" bounty category. Depending on what actions/methods the stale postponed or promise-yield receipt invokes, this can be leveraged to call assert_self-gated logic on the new deployment, corrupt its state, or trigger unintended fund movement tied to the recycled name.

### Likelihood Explanation
Preconditions: the attacker must (1) control an account `X` with a pending postponed/received-data/promise-yield row (trivial — any cross-contract async call or `promise_yield_create` self-call creates one), (2) delete `X` via ordinary `DeleteAccount`, and (3) wait for/arrange for the account name `X` to be reused by another party. Steps 1–2 are fully within an ordinary unprivileged user's control and cost only normal gas fees. Step 3 (someone else registering the exact same name) is the main constraint on real-world exploitability — it requires either social engineering of a specific vanity name or targeting well-known recycled/short names, so likelihood is moderate rather than trivially high, but the underlying state-teardown bug is fully attacker-triggerable and repeatable at will.

### Recommendation
Extend `remove_account` to also purge, under the account's prefix, `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` rows (iterating and removing exactly like the existing access-key/contract-data loops), and extend `RemoveAccountResult` to reflect the additional keys removed for compute-cost accounting. Alternatively/additionally, disallow `DeleteAccount` while any postponed/promise-yield state exists for the account, or incorporate an account "generation" component into these trie keys so that stale postponed state can never be picked up by a differently-generation account of the same name.

### Proof of Concept
Unit test in `core/store/src/utils/mod.rs` (or a runtime integration test):
1. Build a `TrieUpdate`, and for account `X` write one row of each of: `ReceivedData`, `PostponedReceiptId` (via `set`), `PendingDataCount`, `PostponedReceipt` (`set_postponed_receipt`), `PromiseYieldReceipt` (`set_promise_yield_receipt`), `PromiseYieldStatus` (`set_promise_yield_status`), `YieldIdToDataId`/`DataIdToYieldId` (`set_yield_id_mapping`), plus `Account`, `AccessKey`, `ContractData` for control.
2. Call `remove_account(&mut state_update, &X)`.
3. For each raw prefix in `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY`, use `state_update.locked_iter` to count remaining rows under account `X`.
4. Assert `Account`, `AccessKey`, `ContractData` prefixes are empty (already correct) but assert non-emptiness (bug reproduction) for `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`.
5. (Runtime-level escalation PoC) In a `runtime/runtime` integration test: create account `X` with a self-targeted `promise_yield_create` pending, `DeleteAccount(X)`, `CreateAccount(X)` + deploy a new contract with an `assert_self`-gated method, then deliver the original `PromiseResume`/`Data` receipt and assert that the gated method executes successfully despite the new deployment never having authorized it.
