### Title
Active (non-Owner) multi-sig permission holders can fully overwrite the Owner permission via `AccountPermissionUpdateContract`, enabling account takeover outside their granted scope - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
CVE-2017-7505 describes an authorization flaw where a scoped, limited administrative permission (user-management, restricted to certain organizations) could be used to perform operations on resources entirely outside its intended scope (global admin accounts). The java-tron multi-sig permission system has an analogous structural flaw: an `Active` permission — meant to be a scoped, lower-privilege permission restricted to a whitelisted set of contract types via its `operations` bitmap — can, if that bitmap includes the `AccountPermissionUpdateContract` type, be used to unilaterally rewrite the account's `Owner` permission, i.e., escalate itself to full account control, with no additional check that ties the acting permission's privilege level to the privilege level of the permission structure it is allowed to write.

### Finding Description
`AccountPermissionUpdateActuator.execute()` unconditionally overwrites the account's `Owner`, `Witness`, and `Active` permission set from the contract payload: [1](#0-0) 

The only authorization gate for whether a given signer (using a particular `permission_id`) may submit this contract type is `TransactionCapsule.checkPermission`, which merely checks that the signer's permission is of type `Active` and that the `AccountPermissionUpdateContract` bit is set in that permission's `operations` bitmap: [2](#0-1) 

`AccountPermissionUpdateActuator.checkPermission()` (called from `validate()`) only checks that the `operations` bitmap bits correspond to *some* valid `ContractType`, not that the contract type being authorized (`AccountPermissionUpdateContract`, type 46) is safe to grant to a non-Owner permission: [3](#0-2) 

There is no check anywhere in `validate()` or `execute()` that ensures the `Owner` permission's key set is unchanged, or that the signer invoking the update via a non-zero `permission_id` (i.e., an `Active` permission) is restricted from altering `Owner`-level authority. As a result, once an account owner (knowingly or via a compromised/malicious dApp request) grants an `Active` permission that includes bit 46 in its `operations` field, any key holder of that `Active` permission can submit a single `AccountPermissionUpdateContract` transaction that sets an entirely attacker-controlled `Owner` permission, removing the original owner's keys and gaining full, permanent control of the account — going far beyond the scope the `Active` permission was intended to grant.

### Impact Explanation
This allows a holder of a deliberately-scoped, limited permission to perform an out-of-scope privileged operation (rewriting `Owner`-level authority), resulting in complete and permanent account takeover: the attacker can lock out the legitimate owner, then drain all TRX/TRC-10/TRC-20 balances, vote/freeze/delegate resources, or reconfigure the account arbitrarily using the new Owner key. This matches the "unauthorized account operation" and "theft or permanent freezing of funds" impact bar.

### Likelihood Explanation
Exploitation requires that the victim account previously created an `Active` permission whose `operations` bitmap includes the `AccountPermissionUpdateContract` bit (46) — a configuration a user could set up intentionally (e.g., for automated permission rotation) or be tricked into approving via a malicious dApp/wallet integration requesting overly broad active-permission scope. Once that grant exists, exploitation is a single signed transaction with no further authorization needed, making likelihood dependent on real-world prevalence of such overly-broad grants rather than any additional protocol-level barrier.

### Recommendation
Add an explicit invariant in `AccountPermissionUpdateActuator.validate()`/`execute()` (and/or `TransactionCapsule.checkPermission`) preventing a transaction authorized via a non-zero (`Active`) `permission_id` from modifying the `Owner` permission's keys/threshold, or from including `AccountPermissionUpdateContract` in an `Active` permission's allowed operations bitmap at all — analogous to disallowing scope-escalating operations for restricted-scope permissions in the Foreman fix.

### Proof of Concept
1. Account `A` (owner key `K_owner`) creates an `Active` permission `P2` with `operations` bitmap that includes bit 46 (`AccountPermissionUpdateContract`) and assigns key `K_attacker` to `P2` (this can be done unintentionally via a dApp request asking for broad "active" scope).
2. Attacker, holding `K_attacker`, builds an `AccountPermissionUpdateContract` for account `A`, setting a new `Owner` permission whose only key is `K_attacker2` (attacker-controlled), signs it with `permission_id = 2` using `K_attacker`.
3. `TransactionCapsule.validateSignature`/`checkPermission` only verifies bit 46 is set in `P2.operations` and the signature weight meets `P2`'s threshold — this passes.
4. `AccountPermissionUpdateActuator.execute()` overwrites `A`'s `Owner` permission with the attacker's key, per [1](#0-0) .
5. Attacker now controls `A`'s `Owner` permission exclusively and can transfer out all funds/resources, permanently locking out the legitimate owner.
