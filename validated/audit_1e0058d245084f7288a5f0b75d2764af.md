### Title
HTTP request framing desync via bare-LF header parsing tolerated by vendored `httparse` vs. strict CRLF-only preamble reader - ([File: stacks-common/src/deps_common/httparse/mod.rs])

### Summary
The vendored, hand-modified `httparse` parser used to decode Stacks HTTP request/response preambles accepts a bare `\n` as a valid line/header terminator, not just `\r\n`, in direct violation of RFC 7230 §3 — the exact bug class in CVE-2022-32214 (llhttp). This parser is paired with a strict, CRLF-only "end of preamble" scanner (`read_to_crlf2`), and the two components disagree about where the HTTP preamble ends when a request/response uses bare-LF line endings, producing an equality break between "bytes consumed from the socket" and "bytes the parser says constitute the preamble."

### Finding Description
`stacks-common/src/deps_common/httparse/mod.rs` implements the request/response line and header parsing logic. The `newline!` macro and `skip_empty_lines`/`parse_headers_iter` functions explicitly treat a lone `b'\n'` as a valid terminator, identical in effect to `\r\n`: [1](#0-0) [2](#0-1) 

This parser is invoked from `stackslib/src/net/http/request.rs` and `response.rs` to decode `HttpRequestPreamble`/`HttpResponsePreamble` from the raw bytes read off the wire, and separately from `libsigner/src/http.rs` (`decode_http_request`/`decode_http_response`) for the signer event/RPC transport: [3](#0-2) [4](#0-3) 

Crucially, the byte-buffer that is handed to this LF-tolerant parser is produced by `read_to_crlf2`, which reads byte-by-byte from the stream and only stops once it observes the strict 4-byte sequence `\r\n\r\n`: [5](#0-4) 

Because the reader requires a strict CRLFCRLF terminator but the parser will happily terminate headers on a bare LF, an attacker-controlled request/response using LF-only header termination causes:
- `read_to_crlf2` to keep consuming bytes from the socket past the point the parser considers the "end of preamble" (since it never sees `\r\n\r\n`, it keeps reading up to `HTTP_PREAMBLE_MAX_ENCODED_SIZE`), while
- `req.parse(&buf_read)` / `resp.parse(&buf_read)` returns `Status::Complete(len)` with `len` far shorter than `buf_read.len()` once it hits the bare-LF-terminated header block.

This mismatch is a direct analog of the CVE-2022-32214 bug class ("LF alone is sufficient to delimit header fields... according to RFC7230 §3, only CRLF should delimit"): the framing boundary computed by the strict CRLF-based reader and the framing boundary computed by the lenient LF-tolerant parser are not equal, breaking the "bytes consumed == bytes parsed as preamble" invariant that every downstream body/next-message reader relies on to stay in sync with the peer's request/response stream.

### Impact Explanation
Any bytes pulled into `buf_read` beyond what `req.parse`/`resp.parse` reports as consumed (`len`) are silently discarded — they are never handed to the body reader nor re-examined as the start of a pipelined follow-up message. On a keep-alive HTTP connection (the RPC/API and signer-event HTTP transports both support `Connection: keep-alive`), this desync means the node's view of "where this message ends and the next one begins" no longer matches what a strict front-end (reverse proxy, load balancer, or another compliant HTTP client library, all of which enforce true CRLF framing per RFC 7230) believes. That is the textbook precondition for HTTP request/response smuggling: an attacker can craft a preamble whose true termination point (per RFC 7230, CRLFCRLF) differs from what this node's parser accepts (bare LF), causing this node to desynchronize its position in a pipelined/keep-alive stream. Depending on deployment topology (e.g., a proxy in front of the RPC server), this can let an attacker split or smuggle a second, attacker-chosen request past the proxy's inspection into the node's connection, or corrupt response parsing on the client side of `libsigner`/RPC HTTP client paths.

### Likelihood Explanation
The vulnerable code paths are reached without authentication — any TCP client that can complete the HTTP handshake with the node's RPC endpoint, or any HTTP peer being decoded on the signer event side, exercises this parser. Constructing a request/response with `\n`-only header lines (no `\r`) is trivial and requires no special privileges or races. The main uncertainty is exploitation depth: I was not able to fully trace the exact `ProtocolFamily`/non-blocking incremental read path in `stackslib/src/net/httpcore.rs` (the tool budget ran out before locating `read_preamble`/`read_payload` implementations for the socket-driven, non-blocking path used in production, as opposed to the blocking `Read`-based `read_to_crlf2` path used by `consensus_deserialize`). It is possible the non-blocking path re-implements its own boundary detection independently of `read_to_crlf2`, which would need to be checked to confirm whether this exact discrepancy is reachable on the live P2P/RPC listener versus only on the `libsigner`/test-harness code paths that call `consensus_deserialize` directly.

### Recommendation
Make the vendored `httparse` strictly reject bare `\n` as a header/line terminator (require `\r\n` only), matching the upstream `httparse`/`llhttp` fix for CVE-2022-32214, so that the lenient parser and the strict `read_to_crlf2` boundary detector agree on framing. Alternatively, replace the custom byte-by-byte `read_to_crlf2` scan with a parser-driven incremental read loop that trusts only the `Status::Complete(len)` returned by `req.parse`/`resp.parse` to determine how many bytes were consumed, so there is a single source of truth for message boundaries.

### Proof of Concept
```
POST /v2/transactions HTTP/1.1\n
Host: victim-node:20443\n
Content-Length: 5\n
\n
AAAAA
```
Send this over a persistent (keep-alive) connection to the node's HTTP RPC listener (or feed it into `HttpRequestPreamble::consensus_deserialize`/`decode_http_request`). `read_to_crlf2` will not find the literal 4-byte sequence `\r\n\r\n` and will keep consuming subsequent bytes (including bytes belonging to what should be treated as body/next request) up to `HTTP_PREAMBLE_MAX_ENCODED_SIZE`, while `httparse::Request::parse` will report `Status::Complete` at the position right after the bare-LF-terminated blank line — i.e., far earlier than the actual number of bytes already consumed from the socket, demonstrating the byte-accounting mismatch that enables desync/smuggling on a persistent connection.

pub fn read_to_crlf2<R: Read>(fd: &mut R) -> Result<Vec<u8>, CodecError> {
    let mut ret = Vec::with_capacity(HTTP_PREAMBLE_MAX_ENCODED_SIZE as usize);
    while ret.len() < HTTP_PREAMBLE_MAX_ENCODED_SIZE as usize {
        let mut b = [0u8];
        fd.read_exact(&mut b).map_err(CodecError::ReadError)?;
        ret.push(b[0]);

        if let Some(last_4) = ret.last_chunk::<4>() {
            // '\r\n\r\n' is [0x0d, 0x0a, 0x0d, 0x0a]
            if last_4 == &[0x0d, 0x0a, 0x0d, 0x0a] {
                break;
            }
        }
    }
    Ok(ret)
}
