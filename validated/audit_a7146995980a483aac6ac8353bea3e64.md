### Title
Signer's wNEAR spent on `storage_deposit` is not re-credited when the withdraw promise chain fails entirely - (File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs)

### Summary
`internal_ft_withdraw` (and the analogous `internal_mt_withdraw`/`internal_nft_withdraw`) debits the signer's primary token **and** their wNEAR `storage_deposit` amount in a single `self.withdraw(...)` call, then unwraps that wNEAR into real NEAR via `near_withdraw` and forwards it as an attached deposit to the target token contract's `storage_deposit` call before chaining `ft_transfer`/`ft_transfer_call`. If the whole downstream promise chain fails (e.g. the attacker's own token contract panics or lacks the callee method), the resolver only refunds the primary withdrawn amount, never the wNEAR spent on `storage_deposit`, because the raw NEAR that bounced off the failed external call is returned by the NEAR protocol to the contract's own account balance, not credited back to the signer's internal ledger.

### Finding Description
The binding that must hold is: `wnear_debited_for_storage_deposit == wnear_re-credited_if_storage_deposit_action_never_lands`. Trace:

1. `internal_ft_withdraw` calls `self.withdraw(&owner_id, [primary_token_delta, wnear_storage_deposit_delta], ...)`, atomically debiting both the primary token and `Nep141TokenId::new(self.wnear_id())` from `owner_id`'s `token_balances`. [1](#0-0) 
2. It then schedules `near_withdraw(storage_deposit)` on wNEAR, chained into `do_ft_withdraw`, which itself requires `near_withdraw` to have succeeded before forwarding the unwrapped NEAR as an attached deposit into `ext_storage_management::storage_deposit(...)` on the (attacker-controlled) `token` contract, followed by `ft_transfer`/`ft_transfer_call`. [2](#0-1) 
3. The whole chain is wrapped in a final `.then(... ft_resolve_withdraw(...))` callback that, per the standard NEP-141 withdraw-resolver pattern used throughout this contract, only knows about and refunds the **primary** token amount — it has no parameter or bookkeeping for the `storage_deposit` amount. [3](#0-2) 

If the target `token` contract's `storage_deposit` (or the following transfer) fails at the action/receipt level — e.g., the account doesn't implement the method, or panics — the NEAR protocol refunds the unused attached deposit to the *predecessor* (the Defuse contract's own account), not to any specific internal ledger entry. Since `ft_resolve_withdraw` was only ever given the primary token/amount to re-credit, the signer's debited wNEAR balance is never restored, while the corresponding real NEAR silently accrues to the contract's own account with no on-chain record tying it back to the signer.

### Impact Explanation
The signer's internal wNEAR balance (`token_balances[owner_id][Nep141TokenId(wnear_id)]`) is permanently debited with no corresponding credit anywhere reachable by the signer — value leaves the ledger without being delivered to the receiver or refunded to the signer, violating the settlement invariant (debited == delivered + re-credited). This matches the Critical category "user funds permanently frozen." It is repeatable across any `FtWithdraw`/`MtWithdraw`/`NftWithdraw` intent that includes `storage_deposit: Some(...)` and targets a receiver token contract that fails to consume the attached deposit.

### Likelihood Explanation
The precondition is that the signer must sign an intent with `storage_deposit: Some(NearToken)` targeting a `token` contract whose `storage_deposit` call (or subsequent transfer) fails entirely at the promise level. An attacker can trivially deploy such a malicious/broken token contract and induce (or trick) a signer into withdrawing to it, or exploit it against their own account to demonstrate frozen-funds impact. No privileged role is required.

### Recommendation
`ft_resolve_withdraw`/`mt_resolve_withdraw`/`nft_resolve_withdraw` should also track and conditionally re-credit the `storage_deposit` wNEAR amount to the owner whenever the downstream transfer/storage_deposit promise fails, mirroring the existing primary-token refund path, so that a failed chain fully reverses all debits made in `self.withdraw(...)`.

### Proof of Concept
```
cargo test -p defuse --test ft_withdraw -- storage_deposit_wnear_lost_on_failed_chain
```
Plan: deploy a malicious FT contract without a `storage_deposit` method (or one that panics unconditionally); fund the signer with wNEAR; sign an `FtWithdraw` intent with `storage_deposit: Some(amount)` targeting the malicious contract; call `execute_intents`; assert the downstream promise chain fails; then assert:
- signer's wNEAR internal balance is `pre_balance - amount` (not restored) — the "never re-credited" side, and
- no transfer of `amount` wNEAR appears anywhere delivered to the signer or receiver — the "never delivered" side,
confirming the invariant `debited == delivered + re-credited` is broken.

    #[private]
    pub fn do_ft_withdraw(withdraw: FtWithdraw) -> Promise {
        let min_gas = withdraw.min_gas();
        let p = if let Some(storage_deposit) = withdraw.storage_deposit {
            require!(
                promise_result_checked_void(0).is_ok(),
                "near_withdraw failed",
            );

            ext_storage_management::ext(withdraw.token)
                .with_attached_deposit(storage_deposit)
                .with_static_gas(STORAGE_DEPOSIT_GAS)
                // do not distribute remaining gas here
                .with_unused_gas_weight(0)
                .storage_deposit(Some(withdraw.receiver_id.clone()), None)
        } else {
            Promise::new(withdraw.token)
        };

        let p = ext_ft_core::ext_on(p)
            .with_attached_deposit(NearToken::from_yoctonear(1))
            .with_static_gas(min_gas)
            // distribute remaining gas here
            .with_unused_gas_weight(1);
        if let Some(msg) = withdraw.msg {
            p.ft_transfer_call(
                withdraw.receiver_id,
                withdraw.amount.into(),
                withdraw.memo,
                msg,
            )
        } else {
            p.ft_transfer(withdraw.receiver_id, withdraw.amount.into(), withdraw.memo)
        }
    }
