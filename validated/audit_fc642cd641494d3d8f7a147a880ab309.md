### Title
Unauthenticated UDP source-address spoofing can hijack a tunnel's trusted remote address via the `ErrAlreadySeen`/`SetRemoteIfPreferred` path - (File: `handshake_manager.go`, `hostmap.go`)

### Summary
The external report's bug class is a missing bound/validation check on a state-changing operation triggered by an actor who is not a fully-authorized party, allowing race/replay-based manipulation of trusted state for attacker benefit. The closest reachable analog in this codebase is in the handshake retransmit ("already seen") path: when a byte-for-byte duplicate of a previously-received handshake packet is delivered, the responder calls `HostInfo.SetRemoteIfPreferred`, which switches the tunnel's trusted `remote` address to whatever UDP source address the packet arrived from, gated only by whether that source IP falls in the locally configured `preferred_ranges` — not by any cryptographic proof that the peer is actually reachable at that address.

### Finding Description
When a handshake stage-1 packet is received and matches an existing hostinfo's stored `HandshakePacket` bytes exactly, `CheckAndComplete` returns `ErrAlreadySeen`: [1](#0-0) 

The error handler then calls `SetRemoteIfPreferred`, which unconditionally updates the hostinfo's `remote` (the address all future data traffic will be sent to) if the packet's source address is inside a preferred range and no existing remote is already inside a preferred range: [2](#0-1) [3](#0-2) 

`SetRemoteIfPreferred` only checks `via.IsRelayed` and range membership of `via.UdpAddr.Addr()` — it performs no verification that the sender at that UDP source is the actual noise-cryptographically-authenticated peer. The `ErrAlreadySeen` branch is reachable purely by delivering an exact copy of previously-observed ciphertext (the raw handshake packet bytes stored in `hostinfo.HandshakePacket[handshakePacketStage0]`), which requires no possession of any private key or CA-signed certificate — only the ability to capture (sniff/replay) that packet and resend it over UDP with a forged source address, since UDP source addresses are attacker-controlled on any network path where spoofing isn't filtered.

This mirrors the AMM.sol root cause: a state-mutating action (choosing the trusted "price"/here "trusted remote address") is executed based on an unauthenticated signal, with only a coarse, non-cryptographic guard (a CIDR range check) rather than a bound tied to the actual authenticated party, letting a third party who is not the legitimate counterpart manipulate settled state for their own benefit (traffic redirection instead of financial profit).

### Impact Explanation
If an attacker can (a) observe/replay a legitimate stage-1 handshake packet between two Nebula nodes, and (b) send a UDP packet with a spoofed source address that lands inside the victim's configured `preferred_ranges` (commonly private/LAN CIDRs such as `10.0.0.0/8` or `192.168.0.0/16`), the attacker can redirect the trusted "remote" address `hostinfo.remote` used for all future outbound overlay traffic. Because `remote` is the destination used by `sendNoMetrics`/`send` for subsequent packets, an attacker positioned to also receive UDP traffic on the spoofed source range (e.g. via ARP spoofing on the same LAN, or a routing manipulation on the local segment) can redirect a portion of the encrypted tunnel traffic toward themselves, causing denial of service or facilitating further on-path attacks against the tunnel — this is "remote state poisoning" of hostmap/remote-address trust, which the task's validation criteria explicitly accepts as in-scope impact.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to be able to (1) capture a legitimate handshake packet — feasible for any on-path/local-network observer since UDP handshake packets are sent in the clear on the wire, and (2) spoof a UDP source address that lands within the victim's `preferred_ranges` — feasible on networks where source-address filtering (BCP38/uRPF) is not enforced, which is common in LAN/shared-network scenarios that `preferred_ranges` is specifically designed to detect. The `try_interval`/retry logic in the handshake manager also naturally produces retransmits of the same stage-1 bytes, giving the attacker ample capture opportunity.

### Recommendation
Do not let `SetRemoteIfPreferred` mutate the trusted remote solely on a CIDR match of the packet's UDP source address. Instead require:
- The remote-address update from `ErrAlreadySeen` only take effect after the resent stage-2 response completes a fresh liveness/challenge round-trip authenticated to the new source (rather than trusting the bare metadata of the duplicate stage-1 packet), or
- Track a nonce/challenge tied to the specific source address and require the peer's continued participation in the Noise session (data proving key possession) before updating `remote`, similar to how `handleHostRoaming` requires actual traffic decrypted successfully under the session key before roaming (see `outside.go` `handleHostRoaming`, which only roams once decrypted application traffic is confirmed from the new address) — the `ErrAlreadySeen` fast-path should be made to require the same guarantee rather than relying on a coarse range check on unauthenticated packet metadata.

### Proof of Concept
1. Node A and Node B complete a handshake; A's `HandshakePacket[handshakePacketStage0]` and B's hostinfo are established, with B configured with `preferred_ranges` including the local LAN CIDR.
2. Attacker M, on the shared LAN, captures A's stage-1 handshake packet bytes in transit to B (or waits for a natural retransmit).
3. M resends the identical packet bytes to B, spoofing the UDP source address to one inside B's `preferred_ranges` (e.g., a different LAN IP that M also controls or can intercept traffic for, such as via ARP spoofing).
4. B's `CheckAndComplete` finds an exact byte match against the stored packet and returns `ErrAlreadySeen`; `handleCheckAndCompleteError` calls `existing.SetRemoteIfPreferred(f.hostMap, via)`, which succeeds because the spoofed address is in `preferred_ranges`, changing `hostinfo.remote` on B to the attacker-controlled address.
5. Subsequent traffic B intends to send to A is now sent to the spoofed address, which M can intercept (given the LAN-level spoofing/ARP capability that made the source-address forgery possible in the first place). [2](#0-1) [3](#0-2)

// SetRemoteIfPreferred returns true if the remote was changed. The lastRoam
// time on the HostInfo will also be updated.
func (i *HostInfo) SetRemoteIfPreferred(hm *HostMap, via ViaSender) bool {
	if via.IsRelayed {
		return false
	}

	currentRemote := i.GetRemote()
	if !currentRemote.IsValid() {
		i.SetRemote(via.UdpAddr)
		return true
	}

	// NOTE: We do this loop here instead of calling `isPreferred` in
	// remote_list.go so that we only have to loop over preferredRanges once.
	newIsPreferred := false
	for _, l := range hm.GetPreferredRanges() {
		// return early if we are already on a preferred remote
		if l.Contains(currentRemote.Addr()) {
			return false
		}

		if l.Contains(via.UdpAddr.Addr()) {
			newIsPreferred = true
		}
	}

	if newIsPreferred {
		// Consider this a roaming event
		i.lastRoam = time.Now()
		i.lastRoamRemote = currentRemote

		i.SetRemote(via.UdpAddr)

		return true
	}

	return false
}
