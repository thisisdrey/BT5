### Title
`core.hooksPath` override via attacker-controlled `git_config_options` bypasses Gitaly's pre-receive/update/post-receive hook enforcement - (File: internal/gitaly/service/ssh/receive_pack.go)

### Summary
`SSHReceivePack` builds the `git-receive-pack` command with `gitcmd.WithReceivePackHooks(...)` (which sets the legitimate `core.hooksPath`) *before* `gitcmd.WithConfig(config...)`, where `config` is derived unfiltered from the attacker-supplied `git_config_options` field via `gitcmd.ConvertConfigOptions`. Because Git honors the last `-c key=value` occurrence on the command line for single-valued keys, an attacker can submit `core.hooksPath=<attacker path>` to override Gitaly's real hooks directory, effectively disabling git's invocation of Gitaly's pre-receive/update/post-receive hook wrappers.

### Finding Description
`gitcmd.ConvertConfigOptions` (`internal/git/gitcmd/command_options.go:118-131`) converts attacker-controlled `git_config_options` strings into `ConfigPair`s with only syntactic validation performed later by `ConfigPair.Validate()` (`internal/gitaly/config/config.go:437-470`) — it only checks that the key contains a `.`, has no `=`, doesn't start/end with `.`, and matches a generic regex. There is no allow-list or deny-list rejecting dangerous keys such as `core.hooksPath`, `uploadpack.packObjectsHook`, `uploadpack.allowFilter`, etc. [1](#0-0) 

In `sshReceivePack` (`internal/gitaly/service/ssh/receive_pack.go:96-99,160-167`), the config derived from the request is passed to `repo.Exec` via `gitcmd.WithConfig(config...)`, and the `CmdOpt`s are applied in this literal order:
```
gitcmd.WithReceivePackHooks(objectHash, req, "ssh", transactionsEnabled),
gitcmd.WithGitProtocol(s.logger, req),
gitcmd.WithConfig(config...),
``` [2](#0-1) 

`WithReceivePackHooks` invokes `configureHooks`, which appends the legitimate `core.hooksPath=<gitCmdFactory.HooksPath(ctx)>` to `cc.globals`: [3](#0-2) 

Because `WithConfig(config...)` (which contains the attacker's `git_config_options`) runs *after* `WithReceivePackHooks`, the attacker's entries are appended to `cc.globals` later than the legitimate `core.hooksPath` entry. `combineArgs` (`internal/git/gitcmd/command_factory.go:597-645`) emits `cc.globals` in that same order as `-c key=value` flags on the final `git receive-pack` command line: [4](#0-3) 

Git applies later `-c` occurrences of the same single-valued key as authoritative, so a request with `git_config_options = ["core.hooksPath=/tmp/attacker-controlled"]` results in git-receive-pack looking for `pre-receive`/`update`/`post-receive` scripts in the attacker-specified directory rather than Gitaly's real hooks path. If that directory does not contain matching executables (the common case for an attacker without filesystem write access), git silently skips hook execution entirely, since git treats a missing hook executable as "no hook to run." This is functionally equivalent to disabling pre-receive/update/post-receive hook execution for that push, bypassing whatever server-side push checks GitLab implements via those hooks (protected branch enforcement, push rules, etc., all wired through Gitaly's `HooksPayload`/`gitaly-hooks` mechanism).

No `storage.ValidateRelativePath`, `git.ValidateRevision`, or command/description allow-list in `gitcmd` currently blocks or filters config keys supplied through `GitConfigOptions`; validation is purely syntactic.

### Impact Explanation
An unprivileged authenticated user who can push to a repository they have access to can neutralize Gitaly's hook execution for that push by supplying `core.hooksPath` in `git_config_options`, since the option ordering lets the attacker's `-c` flag win over Gitaly's own hook wiring. This maps to the "hook or quarantine bypass" impact class, and depending on what GitLab enforces purely through pre-receive/update hooks (branch protection, LFS/size limits, custom push rules processed by the hook mechanism), it could allow rule bypass on a push that should otherwise be rejected.

### Likelihood Explanation
The preconditions are minimal: the attacker only needs push access to any repository (their own fork is sufficient) and control over the `GitConfigOptions` field forwarded by GitLab Shell from SSH client `-o` capabilities into `SSHReceivePackRequest.git_config_options`. No special role, secret, or bug in git itself is required — this is a straightforward, repeatable ordering flaw in how `CmdOpt`s are composed in `internal/gitaly/service/ssh/receive_pack.go`.

### Recommendation
Deny-list (or otherwise reject) security-sensitive keys such as `core.hooksPath`, `uploadpack.packObjectsHook`, `uploadpack.allowFilter`, `receive.procReceiveRefs`, etc. in `gitcmd.ConvertConfigOptions` or in `ConfigPair.Validate()`, since these must remain exclusively under Gitaly's control. Additionally, apply `WithConfig(config...)` (attacker-supplied globals) *before* `WithReceivePackHooks`/`WithPackObjectsHookEnv` in the `CmdOpt` ordering so that Gitaly-controlled config entries are always emitted last and win regardless of allow-list gaps.

A minimal Go unit test on `gitcmd.ExecCommandFactory` can also assert the final argv order: build a command with `WithReceivePackHooks(...)` then `WithConfig([]ConfigPair{{Key:"core.hooksPath", Value:"/tmp/x"}})` and confirm the resulting args contain `-c core.hooksPath=/tmp/x` positioned after `-c core.hooksPath=<real hooks path>`, proving the attacker value is the one git will honor.

// ConvertConfigOptions converts `<key>=<value>` config entries into `ConfigPairs`.
func ConvertConfigOptions(options []string) ([]ConfigPair, error) {
	configPairs := make([]ConfigPair, len(options))

	for i, option := range options {
		configPair := strings.SplitN(option, "=", 2)
		if len(configPair) != 2 {
			return nil, fmt.Errorf("cannot convert invalid config key: %q", option)
		}

		configPairs[i] = ConfigPair{Key: configPair[0], Value: configPair[1]}
	}

	return configPairs, nil
}
