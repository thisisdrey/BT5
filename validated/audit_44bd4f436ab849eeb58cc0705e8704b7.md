### Title
Unauthenticated remote shutdown of signer event-receiver via `POST /shutdown` - ([File: libsigner/src/events.rs])

### Summary
`SignerEventReceiver::next_event` handles the `/shutdown` URL by unconditionally setting `stop_signal` to `true` and returning `EventError::Terminated`, with no signature, secret, or peer-identity check on the request. Any TCP client able to reach the signer's event-observer HTTP listener can send a bare `POST /shutdown` and terminate the signer's event-receiver main loop.

### Finding Description
In `next_event`, the request dispatch chain checks `request.url()` against several fixed paths [1](#0-0) . For `/shutdown`, the handler does not verify a body, header, secret, or peer identity — it directly does `event_receiver.stop_signal.store(true, Ordering::SeqCst); Err(EventError::Terminated)` [2](#0-1) . This mirrors exactly what the legitimate in-process `SignerStopSignaler::send` does internally to wake the blocking `recv()` call, by connecting to `self.local_addr` and issuing a crafted `POST /shutdown` request over plain TCP with no auth material [3](#0-2) . Once `stop_signal` is true, `is_stopped()` returns true and the check at the top of `next_event` returns `Err(EventError::Terminated)` on the next call [4](#0-3) , and `main_loop` breaks out of its loop entirely on seeing `EventError::Terminated` [5](#0-4) , ending the signer's event-receiver thread. This HTTP listener is the same port bound via `bind()` [6](#0-5)  that the node's `event_observer` configuration is pointed at to deliver StackerDB chunks, burn-block events, and block-validation responses — i.e., it is the signer's externally-facing event ingestion port, not an internal-only loopback IPC channel enforced by the code itself. Nothing in this dispatch path checks the source IP, a shared secret, or any StackerDB/peer signature before honoring `/shutdown`.

### Impact Explanation
Any remote party that can open a TCP connection to the signer's bound event-receiver address can permanently stop that signer's event processing loop with a single unauthenticated HTTP request, since after `stop_signal` is set the loop exits and is never restarted automatically. This is a remote unauthenticated denial-of-service against the signer process's ability to receive new block proposals, StackerDB chunk events, and burn-block/new-block notifications, effectively knocking a signer offline from participating in block signing until manually restarted. This matches the Critical category of "remote crash/unauthenticated DoS from few messages."

### Likelihood Explanation
The only precondition is TCP reachability to the signer's event listener socket, which is the same address/port that node operators point their node's `event_observer` at (per the question's own framing) — no signer key, RPC secret, StackerDB slot ownership, or any privileged role is required. The attack is a single crafted HTTP POST with no body-content requirement, trivially repeatable, and reachable by any unprivileged network client.

### Recommendation
Restrict `/shutdown` handling to a local-only/loopback binding (or a dedicated control socket not exposed on the network), or require the request to carry proof of local origin/authorization (e.g., a per-process random shutdown token embedded by `SignerStopSignaler` and validated in `next_event`) before honoring the stop request. Do not treat `/shutdown` as reachable from the same externally-facing socket used for the node's `event_observer` callbacks.
