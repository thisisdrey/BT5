### Title
Dust transfers permanently fill a victim's per-account token list (`MAX_TOKENS_PER_USER`), blocking all new deposits and borrows - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`Pool` maintains per-account sets `depositTokensOfAccount` and `debtTokensOfAccount`, capped at `MAX_TOKENS_PER_USER = 30` entries combined. Any first-time receipt of a `DepositToken` balance — including an unsolicited dust `transfer` — calls `Pool.addToDepositTokensOfAccount(recipient)`, which reverts with `UserReachedMaxTokens` once the combined count reaches 30. Since the set of deposit tokens is itself capped at 30, an unprivileged attacker can deposit dust amounts of every supported collateral once and then `transfer` 1 wei of each deposit token to any victim, completely filling their list. From that point, every `deposit` of a new collateral type and every first `issue`/mint of a new debt token for that victim reverts — a permissionless, cheap liveness attack analogous to unauthenticated registration spam: one actor can mass-grief unlimited accounts with no captcha-like cost beyond gas.

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` enforce `onlyIfAdditionWillNotReachMaxTokens`, reverting once `debt + deposit tokens >= 30` (`contracts/Pool.sol:143-148`, `204-220`). [1](#0-0) 
- `DepositToken._transfer` unconditionally adds the token to the recipient's list when the recipient's balance was zero — there is no opt-in, minimum amount, or dust threshold (`contracts/DepositToken.sol:517-525`). [2](#0-1) 
- `DepositToken.transfer` is not paused-gated and only checks the sender's unlocked balance (`_revertIfLocked`), so dust is always sendable (`contracts/DepositToken.sol:348-354`). [3](#0-2) 
- The same list insertion happens via `deposit(amount_, onBehalfOf_)` → `_mint` (`contracts/DepositToken.sol:485-488`), and the debt side via `DebtToken._mint` → `pool.addToDebtTokensOfAccount(account_)` (`contracts/DebtToken.sol:597-600`), so both axes a user needs to open a position are gated by the same counter. [4](#0-3) 
- Governor-side `addDepositToken` caps total deposit tokens at 30 (`contracts/Pool.sol:703`), meaning a single attacker pass can occupy *every* possible slot — no legitimate collateral can ever be added by the victim once full. [5](#0-4) 

### Impact Explanation
Once a victim's combined list reaches 30:
- `deposit()` for any collateral the victim does not already hold reverts inside `_mint` → `addToDepositTokensOfAccount`.
- `DebtToken.issue`/`mint`/`flashIssue` and `Pool.swap`/`SmartFarmingManager.leverage` flows that would mint a *new* debt token revert inside `_mint` → `addToDebtTokensOfAccount`.

The victim cannot open any new position or collateral type until they manually clear slots by transferring or withdrawing dust entries to zero. For EOAs this is a recoverable DoS plus gas/UX cost; for contracts or integrated flows (wallets, leverage/zap routers, automated strategies) that only expose `deposit`/`issue` and cannot perform arbitrary `transfer`s of msd tokens, the freeze is effectively permanent — new funds routed through them can never enter the pool. This satisfies the liveness/temporary-freeze impact class for the "account list / freeze griefing" surface, which is reachable purely by an unprivileged EOA paying gas — the on-chain analog of uncapped, unauthenticated registration spam.

### Likelihood Explanation
High: the attack needs no privileges, no flash loans, no price manipulation, and no victim interaction. Cost is one dust deposit per deposit token (recoverable) plus ~30 cheap `transfer` calls per victim, and it can be scripted against arbitrary many accounts exactly like the rotating-proxy registration spam in the report. Nothing in the deployed configuration (pausability, reentrancy guards, `SynthContext`, fees) prevents or prices it.

### Recommendation
- Remove accounts' entries on the recipient side only when balances are meaningful: require a minimum (e.g., oracle-priced) threshold before adding to `depositTokensOfAccount`, or let `addToDepositTokensOfAccount` silently skip/revert-free when the cap is hit instead of reverting the whole transfer/deposit.
- Alternatively, exempt the recipient-side add from the revert path and only enforce `MAX_TOKENS_PER_USER` on user-initiated actions (`deposit`, `issue`), or allow eviction: provide a function to forcibly remove entries, or drop the cap in favor of a bounded-iteration design.
- At minimum, make `transfer`-triggered additions not consume the cap (only count positions created via `deposit`/mint).

### Proof of Concept
Hardhat test sketch against the deployed `Pool`/`DepositToken` set (existing test scaffolding already fakes deposit/debt tokens and proves the revert — see `test/Pool.test.ts:1386-1416`):

```ts
// attacker deposits dust of each listed deposit token, then:
for (const dt of await pool.getDepositTokens()) {
  const token = await ethers.getContractAt('DepositToken', dt)
  await token.connect(attacker).deposit(DUST, attacker.address)      // 1 wei underlying
  await token.connect(attacker).transfer(victim.address, 1)          // adds dt to victim list
}
// victim.depositTokensOfAccount.length + debtTokensOfAccount.length == MAX_TOKENS_PER_USER

// victim can no longer:
await expect(depositToken.connect(victim).deposit(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
await expect(msUSDDebt.connect(victim).issue(amount))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

Key reproducible facts: `_transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` for any first-time nonzero receipt (`contracts/DepositToken.sol:518-519`), `addToDepositTokensOfAccount` reverts at the cap (`contracts/Pool.sol:143-146`, `216-220`), and `DebtToken._mint` reverts through the same counter (`contracts/DebtToken.sol:598-599`).
