Based on the investigation, the strongest analog to CVE-2018-12108 (a malformed/edge-case input causing an uncaught arithmetic crash, SIGFPE) in java-tron is a missing zero-check guard in `RepositoryImpl.calculateGlobalEnergyLimit`, which is reachable from any `TriggerSmartContract` transaction.

### Title
Uncaught `ArithmeticException` (division by zero) in `RepositoryImpl.calculateGlobalEnergyLimit` when `totalEnergyWeight` is 0 - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit(AccountCapsule)` guards against a zero `totalEnergyWeight` only with a Java `assert` statement, which is a no-op unless the JVM is started with `-ea` (not default in production). Sibling implementations of the same logic elsewhere in the codebase explicitly check and short-circuit on this condition, showing the maintainers are aware this value can legitimately be zero.

### Finding Description [1](#0-0) 

The method computes:
```java
long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();
assert totalEnergyWeight > 0;
if (hardenResourceCalculation()) {
  return BigInteger.valueOf(energyWeight)
      .multiply(BigInteger.valueOf(totalEnergyLimit))
      .divide(BigInteger.valueOf(totalEnergyWeight))   // divide-by-zero if weight==0
      .longValueExact();
}
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
```
Compare this to the equivalent, correctly-guarded logic in `EnergyProcessor.calculateGlobalEnergyLimit` and `BandwidthProcessor.calculateGlobalNetLimit`/`calculateGlobalNetLimitV2`, both of which explicitly return `0` when the weight is `<= 0`: [2](#0-1) [3](#0-2) 

`RepositoryImpl.calculateGlobalEnergyLimit` lacks this explicit `totalEnergyWeight <= 0` short-circuit; it only relies on the disabled-by-default `assert`. When `VMConfig.allowHardenResourceCalculation()` is enabled and `totalEnergyWeight` is `0` (e.g. if all SR/user energy stake is unfrozen network-wide, which is a state the code elsewhere explicitly anticipates as reachable), `BigInteger.divide(BigInteger.ZERO)` throws an unguarded `ArithmeticException` — the same bug class as the CVE's SIGFPE from a division/modulo by zero on malformed/edge-case input.

### Impact Explanation
This function is invoked from the TVM energy-limit calculation path used during contract execution (`ContractState`/`VMActuator`), which is reached on every `TriggerSmartContract`/`CreateSmartContract` transaction — a fully unprivileged, broadcastable action. An uncaught `ArithmeticException` at this point in transaction/block processing could propagate up through actuator execution and potentially into block application, causing transaction processing failures or a node crash/halt depending on where it is (or is not) caught further up the call stack.

### Likelihood Explanation
Exploitability depends entirely on `totalEnergyWeight` reaching `0` and `allowHardenResourceCalculation` being enabled — both are network-wide dynamic parameters, not something a single unprivileged caller can force directly. On a live mainnet with substantial existing energy stake this is unlikely to occur under normal operation, but the maintainers' own tests (`CalculateGlobalLimitHardenTest`, `RepositoryImplHardenTest`) demonstrate the sibling functions explicitly treat `totalEnergyWeight <= 0`/`== 0` as a reachable state that must be defended against — this specific `RepositoryImpl` copy of the logic was not updated with the same defense.

### Recommendation
Add an explicit `if (totalEnergyWeight <= 0) { return 0; }` guard in `RepositoryImpl.calculateGlobalEnergyLimit`, mirroring `EnergyProcessor.calculateGlobalEnergyLimit`, instead of relying on the compiled-out `assert`.

### Proof of Concept
Not independently verifiable within the scope of this review — I was unable to confirm within the available iterations (a) whether an uncaught `ArithmeticException` from this specific call path is caught by an outer exception handler in `VMActuator`/`Runtime` before reaching block application in `Manager`, and (b) the exact live-network conditions under which `totalEnergyWeight` could reach `0` with `allowHardenResourceCalculation` enabled.
