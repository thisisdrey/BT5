### Title
Dust deposit-token griefing fills `depositTokensOfAccount` to `MAX_TOKENS_PER_USER`, DoS-ing victim deposits, mints and transfers - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` on the combined size of an account's `debtTokensOfAccount` and `depositTokensOfAccount` lists. Any new entry beyond the cap reverts with `UserReachedMaxTokens()`. Because `DepositToken.deposit(amount_, onBehalfOf_)` and `DepositToken.transfer`/`transferFrom` unconditionally call `Pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance was zero, an unprivileged attacker can permissionlessly push dust balances of every registered deposit token into a victim's list — at dust cost — and permanently/griefingly block every victim action that would add a new token entry: depositing a new collateral type, minting a new synthetic (which adds a debt-token entry), receiving any deposit-token transfer or liquidation `seize` payout, and leveraging via `SmartFarmingManager`. This mirrors the CVE-2025-43430 bug class: a state-management flaw that turns a normal operation into an unexpected crash/revert.

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert once `debtTokensOfAccount.length(account) + depositTokensOfAccount.length(account) >= 30` via `onlyIfAdditionWillNotReachMaxTokens` [1](#0-0) [2](#0-1) .
- `DepositToken._mint` adds the token to the recipient's list whenever the pre-balance is zero — and `deposit()` mints to an attacker-chosen `onBehalfOf_`, so no victim interaction is needed [3](#0-2) [4](#0-3) .
- `DepositToken._transfer` does the same on plain transfers, and the only check on the sender side is `_revertIfLocked(sender, amount)` (unlocked-balance check) — a dust `amount` is always unlocked for an account with no/low debt [5](#0-4) [6](#0-5) .
- There is no opt-in/allowlist for receiving a new deposit-token entry, no minimum-amount threshold, and no way for the recipient to refuse the list insertion. Removal (`removeFromDepositTokensOfAccount`) only happens when the victim's balance of that token goes to exactly zero — and if the victim has debt, the dust may be locked (`unlockedBalanceOf` uses `debtPositionOf` health), preventing self-cleaning [7](#0-6) [8](#0-7) .

Once the victim is at the cap:
- `deposit` of any new collateral reverts inside `_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`, so the victim cannot add collateral of a new type (relevant when an existing collateral's CF is cut or price falls and they must post a different asset).
- `DebtToken.issue/mint/flashIssue` for a synthetic the victim doesn't already hold reverts (new debt-token entry), so the victim cannot open new borrow positions.
- Any `transfer`/`transferFrom`/`seize` of a deposit token the victim doesn't hold reverts, breaking liquidation payouts to a fresh liquidator address and ordinary token receipt.
- `SmartFarmingManager.leverage` reverts for positions requiring new token entries.

### Impact Explanation
Temporary freezing of funds and liveness failure for targeted accounts: the victim's ability to deposit, borrow, or receive position tokens crashes (reverts) until slots are freed — and freeing them requires zeroing balances, which is impossible for locked collateral and requires individually sweeping each dust token. If the victim's position is near the liquidation boundary and the needed collateral type isn't already in their list, they cannot rescue the position and it becomes liquidatable; combined with liquidators whose lists are also fillable, liquidation itself can be griefed. All reachable by any EOA with dust capital; no privileged role, oracle manipulation, or trusted-party failure required.

### Likelihood Explanation
The attack cost is bounded by acquiring/depositing minimal amounts of each registered deposit token (plus transaction gas). Its effectiveness scales with the number of deposit + debt tokens configured in the pool: the cap counts their sum, so pools with many listed tokens make filling 30 slots cheap, and the victim's own existing positions count toward the cap, reducing the entries the attacker must force. Since `deposit(amount, victim)` requires no approval or cooperation, the attack is fully permissionless and repeatable against any account at any time.

### Recommendation
- Make list membership opt-in or lazy: don't auto-add deposit tokens on `transfer`/`deposit` when `onBehalfOf_ != _msgSender()`, or only count entries above a meaningful balance threshold.
- Alternatively, allow `debtOf`/`depositOf`/`debtPositionOf` and mint/burn paths to iterate only over tokens with nonzero balance (drop the cap), or let anyone call `removeFromDepositTokensOfAccount(account, token)`-style cleanup for zero/dust balances.
- At minimum, exempt the cap check for entries the account already holds and skip adding when `amount` is below a dust floor.

### Proof of Concept
```solidity
// Hardhat/Foundry fork, per-pool setup
// victim: fresh EOA holding nothing
// attacker: EOA

for each depositToken_i registered in pool (doesDepositTokenExist / getDepositTokens):
    underlying_i = depositToken_i.underlying();
    deal(underlying_i, attacker, 1);
    IERC20(underlying_i).approve(depositToken_i, 1);
    // onBehalfOf = victim inserts depositToken_i into victim's list
    depositToken_i.deposit(1, victim);

// repeat across pools/tokens until:
assertEq(pool.debtTokensOfAccount.length(victim)
       + pool.depositTokensOfAccount.length(victim), 30);

// Now every victim action that adds a new entry reverts:
vm.prank(victim);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newDepositToken.deposit(amount, victim);        // cannot add new collateral

vm.expectRevert(Pool.UserReachedMaxTokens.selector);
debtToken.issue(victim, amount);                // cannot mint a new synthetic

vm.expectRevert(Pool.UserReachedMaxTokens.selector);
someDepositToken.transfer(victim, amount);      // incoming transfers / seize revert
```
The revert path is `DepositToken._mint/_transfer → Pool.addToDepositTokensOfAccount → onlyIfAdditionWillNotReachMaxTokens → UserReachedMaxTokens` (Pool.sol:143-148, 216-220; DepositToken.sol:486-488, 517-520).
