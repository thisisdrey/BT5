### Title
Non-atomic replay-window Check/Update allows a concurrent replay of a captured packet to be re-decrypted and re-accepted before the window is updated - (File: `connection_state.go`)

### Summary
The reported bug class is "a state-changing operation can be invoked repeatedly without an idempotency guard, and the guard that exists checks the wrong thing (time instead of one-time-use), enabling a network attacker to exploit the gap for repeated unauthorized effect." The closest reachable analog in Nebula that fits the required categories (replay handling, decryption, no CA-signed cert required) is `ConnectionState.Decrypt`, which splits the anti-replay "have we seen this counter" check and the "mark this counter as seen" update into two separate, separately-locked critical sections with a full AEAD decrypt operation in between.

### Finding Description
`ConnectionState.Decrypt` in [1](#0-0)  performs:
1. Lock `decryptLock`, call `cs.window.Check(l, messageCounter)`, unlock.
2. Perform `cs.dKey.DecryptDanger(...)` (the actual AEAD decryption) **outside** the lock.
3. Lock `decryptLock` again, call `cs.window.Update(l, messageCounter)`, unlock.

Because the "already seen" check and the "mark seen" mutation are not performed atomically under a single critical section that also encompasses the decrypt, two goroutines processing two copies of the same captured ciphertext (e.g., a genuine UDP retransmission race or an attacker duplicating/relaying a captured packet at the exact right moment on a multi-routine listener) can both pass `Check` (both see the counter as not-yet-seen), both successfully decrypt the same valid ciphertext, and only the second `Update` call will discover the duplicate and reject it — but by then the first copy has already been fully decrypted and handed off to `handleOutsideMessagePacket`/firewall processing. The `Bits` sliding window (`bits.go`, lines 118-263) itself provides no built-in atomicity; it is the caller's responsibility to make Check+Decrypt+Update atomic, and `Decrypt` deliberately releases the lock between the two.

This is structurally identical to the reported bug class: a "one-time" gate (`Check`) is enforced, but the action it gates (`Decrypt`, i.e., accepting/consuming the packet) is not tied atomically to the gate, and the "already consumed" flag (`Update`) is only recorded after the sensitive operation has already run to completion — mirroring how `withdrawFee()` performed the transfer with only a time-based guard and no atomic "already withdrawn" flag.

### Impact Explanation
If exploitable, this allows an off-path or on-path attacker (who does not need a CA-signed certificate — they only need to capture/duplicate ciphertext bytes traveling over the UDP transport) to cause a single legitimate encrypted packet to be processed twice by the receiving node under concurrent packet-processing routines (`routines > 1`), rather than being deduplicated by the anti-replay window as designed. Depending on payload contents this could cause duplicate delivery of application data to the TUN device, double-processing of control messages (e.g., `header.Test`, `header.LightHouse`, `header.Control`), or duplicate firewall/conntrack side effects — a violation of the anti-replay guarantee the window is meant to provide.

### Likelihood Explanation
Exploitability depends on timing: the attacker needs two copies of an identical, previously observed ciphertext to be processed concurrently by two of Nebula's UDP reader routines before the first `Update` call commits. This is only meaningfully possible when `routines > 1` (multiple concurrent readers/decryptors), and the window of exploitation is a very narrow race between the `DecryptDanger` return and the second `decryptLock` acquisition. This narrows likelihood considerably compared to the original finding (which required no race at all), but the underlying design defect — check-then-act split across two independently-locked sections around an unlocked decrypt — is real and present in the current code.

### Recommendation
Hold a single lock (or otherwise make atomic) across `window.Check`, `DecryptDanger`, and `window.Update` for a given `ConnectionState`, or use a combined "test-and-set" primitive on the `Bits` window so that a given message counter can only pass the gate once, with the decryption and the window update inseparable from the check. Alternatively, perform `Update` unconditionally before attempting decryption (reserving the slot first) and roll back only the reservation (not silently permit reuse) if decryption subsequently fails.

### Proof of Concept
Not concretely demonstrated here — the race requires `routines > 1` and precise concurrent delivery of two copies of one captured ciphertext to `Interface.readOutsidePackets` → `ConnectionState.Decrypt`, which cannot be constructed without live test-harness access in this analysis session. This is flagged as a design-level defect (Check/Decrypt/Update not atomic) rather than a fully validated exploit; a background engineering session with test-harness access (e.g., the existing `e2e/tunnels_test.go` `TestRelayReplayProtection` pattern, which already demonstrates replay-window testing for the relay path) would be needed to confirm whether the multi-routine dispatch path can actually schedule two `Decrypt` calls for the same counter concurrently.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
