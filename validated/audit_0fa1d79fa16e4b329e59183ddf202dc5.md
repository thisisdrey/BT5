Audit Report

## Title
Bounty payout silently fails below the existential deposit, permanently stranding funds in the bounty sub-account - (File: `substrate/frame/bounties/src/lib.rs`)

## Summary
`Pallet::claim_bounty` transfers the curator fee and beneficiary payout via `T::Currency::transfer(..., AllowDeath)` but only checks the result with `debug_assert!(res.is_ok())`, which compiles to a no-op in release builds. The bounty storage entry is then unconditionally deleted (`*maybe_bounty = None;`) regardless of transfer outcome, so a payout below the chain's `ExistentialDeposit` to a fresh beneficiary account fails silently while the bounty record — the only pointer to the escrowed funds — is destroyed. The identical pattern exists in `claim_child_bounty` in `substrate/frame/child-bounties/src/lib.rs`.

## Finding Description
`claim_bounty` computes `payout = balance.saturating_sub(fee)` and transfers it to `beneficiary` with `AllowDeath` preservation, guarding the result only with `debug_assert!`: [1](#0-0) 

Immediately after, regardless of whether either `transfer` call succeeded, the bounty entry is deleted and its description removed: [2](#0-1) 

Since `debug_assert!` is stripped in release/production builds (the profile used for real chains), an `Err(TokenError::BelowMinimum)` returned by `pallet_balances::transfer` — which occurs whenever a transfer to a not-yet-existing account is below `ExistentialDeposit` — is discarded instead of aborting the extrinsic. `ensure_signed(origin)?` shows any signed account, not just the beneficiary or curator, can invoke this call once the bounty is `PendingPayout`: [3](#0-2) 

The identical unguarded pattern (`debug_assert!(fee_transfer_result.is_ok())` / `debug_assert!(payout_transfer_result.is_ok())`) appears in `claim_child_bounty`: [4](#0-3) 

There is no floor applied to `payout` or `final_fee` against `ExistentialDeposit`, and no check that `award_bounty` rejects a `beneficiary`/fee split that would produce a sub-ED payout to a fresh account in the reachable code. The storage deletion is unconditional on the transfer outcome, so once the extrinsic executes, the only on-chain reference to the escrowed balance in `bounty_account` is gone while the balance itself remains stuck there.

## Impact Explanation
This is a permanent user-fund lock: the payout balance in the derived `bounty_account` (a `PalletId`-keyed sub-account) becomes irrecoverable because the storage record needed to re-attempt or reroute the payout is deleted unconditionally in the same transaction as the failed transfer. No privileged action, governance, or malicious node/validator behavior is required — the call is a plain permissionless extrinsic (`ensure_signed`), and the failure is a deterministic consequence of ordinary bounty value/fee arithmetic combined with `pallet_balances`'s existential-deposit rule.

## Likelihood Explanation
The bug is triggered purely by chain-parameter and workflow conditions that are plausible in production: a bounty reaching `PendingPayout` whose computed `payout` (or `final_fee`) is below `ExistentialDeposit` for a beneficiary/curator account with no prior existence on-chain. Because `claim_bounty`/`claim_child_bounty` are callable by any signed account (not restricted to the beneficiary), any observer who notices such a bounty can trigger the fund-losing claim. This does not require malicious governance, leaked keys, or privileged access — only ordinary permissionless extrinsic usage — so it satisfies the unprivileged-external-attacker requirement.

## Recommendation
Propagate the `DispatchResult` of both `T::Currency::transfer` calls with `?` instead of relying on `debug_assert!`, and only clear the bounty/child-bounty storage entries after both transfers actually succeed. Alternatively, floor `payout`/`final_fee` at `ExistentialDeposit` or reject bounty configurations (in `propose_bounty`/`award_bounty`) that would produce a sub-ED payout to a possibly-nonexistent beneficiary/curator account, and consider adopting the `PayoutAttempted`/retry pattern already used in `pallet-multi-asset-bounties` for this pallet and `child-bounties`.

## Proof of Concept
1. Deploy a chain/mock with a non-trivial `ExistentialDeposit = ED`.
2. Propose and fund a bounty (`propose_bounty`, `approve_bounty`) whose `value` and `fee` are sized so that `payout = value - fee < ED`.
3. Assign a curator (`propose_curator`/`accept_curator`) and call `award_bounty` with `beneficiary` set to a brand-new account with zero balance.
4. Advance past `unlock_at`.
5. Call `claim_bounty(bounty_id)` from any signed account in a release-profile build (where `debug_assert!` is compiled out).
6. Observe that `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` returns `Err(TokenError::BelowMinimum)` (per `pallet_balances` ED enforcement), which is discarded, while `*maybe_bounty = None;` and `BountyDescriptions::remove(bounty_id)` execute unconditionally, permanently stranding `payout` in `bounty_account` with no remaining on-chain state referencing it.
