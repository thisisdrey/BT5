### Title
`ExchangeInjectContract` (and `ExchangeWithdrawContract`) execution has no user-supplied slippage protection, allowing sandwich attacks against liquidity providers - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` computes the counter-token amount to be pulled from (or, on withdraw, paid to) an account purely from the *current* on-chain pool ratio at execution time, with no user-specified minimum/maximum bound analogous to the `expected` field that `ExchangeTransactionContract` provides for swaps. This is the same root cause described in the external report for `TrufPartner.pay`: a liquidity-provisioning operation is executed at whatever ratio exists in the pool at inclusion time, with zero protection against ratio manipulation, so it can be sandwiched by TRX/token swaps against the exchange (`ExchangeTransactionContract`) placed immediately before and after it in the same block.

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — no expected/minimum output field exists in the protobuf message. [1](#0-0) 

In `ExchangeInjectActuator.execute`, the amount of the "other" token pulled from the caller's account (`anotherTokenQuant`) is derived directly from the exchange pool's live balances at the moment the transaction is packed into a block: [2](#0-1) 

The same pattern (deriving `anotherTokenQuant` purely from live pool ratios, without any caller-supplied bound) exists in `ExchangeWithdrawActuator.execute`: [3](#0-2) 

By contrast, `ExchangeTransactionContract` (a swap, not a liquidity op) explicitly has an `expected` field used to enforce a minimum received amount: [4](#0-3) 

This asymmetry means that whenever an account calls `ExchangeInjectContract` to add liquidity proportionally to an existing `Exchange` pair, or `ExchangeWithdrawContract` to redeem its share, any attacker who can also broadcast `ExchangeTransactionContract` transactions can manipulate `firstTokenBalance`/`secondTokenBalance` immediately before the inject/withdraw is packed, forcing the injector to deposit (or the withdrawer to receive) tokens at a distorted ratio, then reverse the swap afterward to restore the ratio and capture the difference — the same classic sandwich pattern described for `TrufPartner.pay`'s zero-minOut `addLiquidity` call.

### Impact Explanation
A block producer (or any user who can time transactions within the same block/ordering window) can extract value from any account calling `ExchangeInjectContract`/`ExchangeWithdrawContract` by sandwiching it with two `ExchangeTransactionContract` swaps. This results in unauthorized transfer of value: the victim ends up contributing/receiving tokens at an unfavorable ratio while the attacker profits risk-free, which is a concrete theft-of-funds impact on TRX/TRC10 balances held in `Exchange` pools.

### Likelihood Explanation
All three contract types (`ExchangeTransactionContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`) are ordinary signed transactions broadcastable by any account, requiring no special privilege — only having the target exchange pair active with balances (`firstTokenBalance != 0`, `secondTokenBalance != 0`). Because there is no field in the protobuf or actuator logic to bound the counter-token amount for inject/withdraw, exploitation requires no contract bug beyond normal transaction ordering control, making this readily reachable by any transaction broadcaster who can influence transaction ordering (e.g., an SR producing the block, or via front-running in the mempool/relay).

### Recommendation
Add a caller-supplied minimum/maximum bound (analogous to `expected` in `ExchangeTransactionContract`) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and validate the computed `anotherTokenQuant` against it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` before mutating balances, reverting if the live pool ratio deviates beyond the caller's tolerance.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` transaction from Victim targeting exchange pair `id`, injecting `tokenQuant` of `firstTokenID`.
2. Attacker submits an `ExchangeTransactionContract` swap that sells a large amount of `secondTokenID` for `firstTokenID` in the same pair, shifting `firstTokenBalance`/`secondTokenBalance` heavily (per `ExchangeCapsule.transaction`, see `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java` lines 124-168), ordered before Victim's transaction.
3. Victim's `ExchangeInjectContract` executes using the now-skewed ratio; `anotherTokenQuant = floorDiv(secondTokenBalance * tokenQuant, firstTokenBalance)` (`ExchangeInjectActuator.java` lines 73-76) causes Victim to be debited far more/less of `secondTokenID` than intended, with no check to prevent this.
4. Attacker submits a second `ExchangeTransactionContract` reversing the initial swap, restoring the pool ratio and pocketing the difference extracted from Victim's injected liquidity.
