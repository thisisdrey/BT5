### Title
Dust transfers/deposits fill a victim's per-account token lists (`MAX_TOKENS_PER_USER`), DoS-ing deposits, mints and collateral top-ups - ([File: contracts/Pool.sol])

### Summary
The CVE describes a resource-amplification DoS: a cheap attacker input (a resumption ClientHello with mismatched parameters) forces the victim into an expensive/abusive path (full DTLS handshake, message amplification, CPU burn). The Metronome analog is the per-account token-list accounting in `Pool.sol`: any unprivileged attacker can cheaply force entries into a victim's `depositTokensOfAccount`/`debtTokensOfAccount` sets via `DepositToken.transfer` dust (or `deposit(amount, onBehalfOf_)`), and once the combined list reaches `MAX_TOKENS_PER_USER = 30`, every subsequent `Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` reverts with `UserReachedMaxTokens` (contracts/Pool.sol:143-148). Because the revert happens inside `_mint`, the victim can no longer deposit any *new* collateral type or take on any *new* debt position - a griefing DoS directly proportional to how many distinct tokens the protocol lists.

### Finding Description
- `Pool.addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are guarded by `onlyIfAdditionWillNotReachMaxTokens`, which reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (contracts/Pool.sol:79,143-148,204-220).
- `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is 0 and `amount_ > 0` (contracts/DepositToken.sol:517-520). There is no minimum amount, no opt-in, and no check that the recipient wants the position.
- `DepositToken._mint` does the same on `deposit(amount_, onBehalfOf_)` where `onBehalfOf_` is attacker-chosen (contracts/DepositToken.sol:211-236,486-488).
- Attack flow: attacker deposits 1 wei of underlying into each of the pool's `N` deposit tokens under their own address (or uses `deposit(1, victim)` directly where a fee doesn't round the mint to 0), then calls `msdToken_i.transfer(victim, 1)` for each token. Each transfer pushes a new entry into `depositTokensOfAccount[victim]`. If the victim already holds `k` deposit/debt tokens, only `30 - k` dust transfers are needed to brick the slot.
- Once full, `victim`'s calls to `deposit()` for any *new* collateral, and any `DebtToken.issue/mint` that would add a new debt token, revert - the victim cannot open new positions or top up with a different collateral.
- Consequences on liquidation: a victim whose position drifts toward `debtPositionOf()._isHealthy == false` normally rescues it by depositing additional collateral of *any* listed type. If the attacker has filled the list (and the victim's existing collateral types are insufficient or illiquid), the rescue deposit reverts, enabling a forced liquidation of a position that should have been salvageable - i.e., the DoS is not merely a gas/loop nuisance but converts into direct loss of user funds through liquidatable-but-unrescuable positions.
- The victim can recover slots by transferring away dust (which triggers `removeFromDepositTokensOfAccount` at balance 0), but this costs the victim transactions per token, must be raced against the attacker re-dusting in the same block via `transfer`/front-running, and requires the dust to be *unlocked* (`_revertIfLocked` only gates the sender's transfer; a liquidator seizing or a busy position complicates this). This mirrors the CVE's "temporary but attacker-renewable" liveness degradation.

### Impact Explanation
Cheap, repeatable griefing that (a) permanently blocks a victim from using new collateral types / new synth debt (denial of service of core protocol functions for that account) and (b) can be timed to prevent an unhealthy account from adding collateral, forcing an otherwise-avoidable liquidation - i.e., direct theft of user funds via forced liquidation, plus temporary freezing of the account's ability to interact with the pool. Cost to the attacker is bounded by dust amounts of underlying + gas for `<=30` transfers.

### Likelihood Explanation
- Fully unprivileged: `transfer` and `deposit(_, onBehalfOf_)` are public entry points; no governor/keeper/oracle involvement.
- Cheap and atomic: the attacker can batch all dust transfers in one tx, and re-fill slots faster than the victim can clear them (front-running the victim's clearing transfers).
- Requires the pool to list enough deposit tokens that `30 - (victim's existing tokens)` is reachable; on pools with ≥30 listed collaterals+debt tokens it is always achievable. The attack cannot push a victim *over* the cap on its own (each add reverts at the cap), so it degrades to "fill exactly to the cap" - still sufficient to block all new-token operations.
- Not stopped by `nonReentrant`, `whenNotPaused`, `SynthContext`, or supply caps; the only mitigation is the victim manually emptying dust balances, which the attacker can re-pollute.

### Recommendation
- Make list membership opt-in or privileged: e.g., in `DepositToken._transfer`, only add the recipient to `depositTokensOfAccount` via an explicit `deposit`/claim flow, or keep a `recipient`-set threshold (`MIN_LISTED_BALANCE`) so sub-dust balances are ignored.
- Alternatively, index list membership on *underlying minted via deposit* rather than raw token balance, and have `debtPositionOf`/`depositOf` skip tokens below a dust threshold so unsolicited transfers cannot occupy a slot.
- Provide a public `sweepDust()`/self-removal path that lets an account cheaply purge entries without paying per-token transfer gas in a raceable way.

### Proof of Concept
(Hardhat, against an existing pool with `N >= 30` listed deposit tokens; abbreviated.)

```ts
// victim holds some collateral already => victim's list has k entries
const victim = alice.address

// 1) attacker acquires dust of each msdTOKEN
for (const d of depositTokens) {              // ~30-k iterations
  const under = await d.underlying()
  await ERC20(under).mint(attacker, 1)        // faucet/mock or buy dust on AMM
  await ERC20(under).connect(attacker).approve(d.address, 1)
  await d.connect(attacker).deposit(1, attacker)          // or deposit(1, victim)
  await d.connect(attacker).transfer(victim, 1)           // adds entry to victim's list
}

// now: depositTokensOfAccount[victim].length + debtTokensOfAccount[victim].length == 30
expect(await pool.getDepositTokensOfAccount(victim)).length
  .to.equal(30 - (await pool.getDebtTokensOfAccount(victim)).length)

// 2) victim tries to add NEW collateral -> reverts inside _mint -> addToDepositTokensOfAccount
const newDt = depositTokens[0] // a token victim has 0 balance of (all were filled)
await expect(newDt.connect(alice).deposit(parseEther('1'), victim))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// 3) victim's position drifts unhealthy; rescue deposit of a new collateral reverts
//    -> liquidator seizes collateral via Pool.liquidate for pure profit
await oracle.setPrice(/* drop collateral price */)
await expect(pool.liquidate(synth, victim, msdCollateral.address, payAmount))
  .to.emit(pool, 'PositionLiquidated') // position liquidated although victim could have topped up
```

The PoC is reproducible on a mainnet/Base fork: enumerate `pool.getDepositTokens()`, fund dust via the underlying's AMM/faucet, run the loop above against a fresh victim account with an open leveraged position, then demonstrate the `UserReachedMaxTokens` revert blocking a rescue deposit followed by a successful `Pool.liquidate`.
