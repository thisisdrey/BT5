### Title
`ValidateMultiSign` TVM precompile builds its signed-message hash without a calling-contract/chain domain separator, enabling cross-contract and cross-chain signature replay - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` precompiled contract (TVM address `0x…0a`) lets any Solidity contract verify off-chain, EOA-produced signatures against a TRON account's on-chain multisig `Permission`. The hash that signers actually sign is constructed only from the target account address, the permission id, and caller-supplied `data`. It contains no reference to the calling/verifying contract address, the chain id, or any other execution-context value, so it is not an EIP-712-style domain-separated message. Any contract on the same or a different chain that reconstructs the identical `(address, permissionId, data)` tuple will accept the exact same signature, exactly the replay-attack pattern described in the report.

### Finding Description
`ValidateMultiSign.execute()` builds the signed hash like this: [1](#0-0) 

```
DataWord[] words = DataWord.parseArray(rawData);
byte[] address = words[0].toTronAddress();      // TRON account whose permission is checked
int permissionId = words[1].intValueSafe();
byte[] data = words[2].getData();                // arbitrary caller-supplied payload

byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
byte[] hash = Sha256Hash.hash(CommonParameter.getInstance().isECKeyCryptoEngine(), combine);
```

The recovered signer addresses are then weighed against the account's `Permission` (obtained purely from on-chain state, via `TransactionCapsule.getWeight`): [2](#0-1) 

The signed hash is entirely independent of:
- the address of the *calling* smart contract (the "verifying contract" in EIP-712 terms) — the precompile never reads `msg.sender`/caller address of the invoking contract into the hash,
- the chain id — the hash has no reference to any chain-specific value; `address` and `permissionId` are pure account state that is typically identical across TRON mainnet and every testnet that shares the same key/permission setup,
- a nonce or purpose tag beyond whatever the calling dApp chooses to embed in `data`.

This is functionally the same defect described in the external report for `KinoAccountMinterUpgradable.mintBySignature`: the message that gets signed lacks a domain separator (verifying contract + chain id), so a valid signature produced for one consumer of the primitive can be replayed verbatim by any other consumer that reconstructs the same `(address, permissionId, data)` triple — whether that consumer is a different contract on the same chain, or the identical contract/account/permission replicated on a different TRON network (mainnet/Nile/Shasta, or any private chain forked from the same state).

The general test suite for this precompile (`ValidateMultiSignContractTest`) confirms the exact hash construction and shows it never varies with caller/contract identity or chain: the test signs `sha256(address || permissionId || data)` directly and feeds it to the precompile with no domain-tagging step. [3](#0-2) 

Contrast this with `TransactionCapsule.validateSignature` used for on-chain broadcast transactions, whose signed hash is the full transaction id (`ref_block_hash`, `ref_block_num`, `expiration`, contract payload, etc.), which is intrinsically bound to a specific chain because `ref_block_hash` must correspond to a real recent block on the target chain: [4](#0-3) 
That natural protection does **not** apply to `ValidateMultiSign`, because its "message" is an arbitrary, contract-defined blob, not a transaction — it is designed precisely so dApp developers can build off-chain-signed authorization flows (meta-transactions, gasless approvals, multisig gating for arbitrary contract actions) on top of TRON's native multisig permission system. Any dApp that follows the documented usage pattern (sign `sha256(account || permissionId || data)` off-chain and submit it later) inherits the replay vulnerability unless it manually adds its own domain separation inside `data` — which is not enforced or even suggested by the precompile itself.

### Impact Explanation
Any contract built on `ValidateMultiSign` for off-chain-signed authorization (e.g., "approve transfer of N tokens", "authorize action X") can have its signatures replayed:
- **Cross-contract replay on the same chain**: if two different deployed contracts both call `ValidateMultiSign` with the same target account/permission id and coincidentally (or through predictable encoding schemes) reconstruct the same `data`, a signature authorized for contract A's action can be accepted by contract B, causing an unauthorized state change/asset movement in a context the signer never intended.
- **Cross-chain replay**: since `address` and `permissionId` are TRON account/permission identifiers rather than chain-bound values, and account permissions are frequently mirrored (deliberately or coincidentally) across TRON mainnet and its public testnets or forks, a signature captured on one network can be replayed on another network that has an identically configured account/permission, letting an attacker action be authorized without the signer's chain-B intent.

This is a genuine "unauthorized account operation" vector reachable by any unprivileged contract deployer or dApp-integrating attacker who can extract a broadcasted/mempool-visible signature, matching the Medium/High severity criteria for unauthorized operations or asset movement.

### Likelihood Explanation
Likelihood is Medium: exploitation requires that a specific consuming dApp's design pattern for `data` is either predictable or reused verbatim between two different verifying contexts (two contracts, or the same contract instance mirrored on two chains). This is common practice, because the precompile's own test/reference usage encodes `data` as a plain content hash with no contract or chain binding, so developers copying the documented pattern are directly steered into the vulnerable construction. No special privileges are needed — any transaction broadcaster who observes a signature (mempool, block explorer, or the party who was given the signature) can immediately replay it against another consumer of the primitive.

### Recommendation
Add mandatory domain separation to the hash computed by `ValidateMultiSign` (and equivalently document/enforce it for `BatchValidateSign`), incorporating at minimum:
- the invoking/verifying contract's address (obtainable from the VM execution context, e.g. via `Program`/`Repository` caller info already threaded through the precompile framework),
- the chain id (already available through `CommonParameter`/genesis block info),
- optionally a monotonically increasing nonce per `(account, permissionId)` tracked in state, to prevent same-chain/same-contract replay of the identical authorization.

Update `combine = ByteUtil.merge(chainId, verifyingContractAddress, address, ByteArray.fromInt(permissionId), nonce, data)` (or an EIP-712-style typed hash) before hashing, and bump the TVM feature flag so this becomes the required hashing scheme going forward, with clear documentation warning dApp developers that raw `data` alone is not sufficient for replay protection.

### Proof of Concept
1. Account `A` sets an `Active` permission with `permissionId=2`, threshold 2, keys `K1, K2` (weight 1 each) — identical account/permission configuration exists on TRON mainnet and on a public testnet (or is mirrored by a malicious operator running a private fork), as shown in the setup used by `ValidateMultiSignContractTest.testDifferentCase`: [5](#0-4) 
2. Off-chain, `K1` and `K2` sign `hash = sha256(A || 2 || data)` where `data` encodes "authorize transfer of 1000 TRC20 tokens to Bob" for **contract X** on chain A, following the exact construction in the test: [6](#0-5) 
3. Contract X (chain A) calls precompile `0x…0a` with `(A, 2, data, [sig1, sig2])`, the weight check passes (`totalWeight >= threshold`), and the authorized action executes: [7](#0-6) 
4. An attacker who observed `sig1`/`sig2` (e.g., from the broadcast transaction or from data shared with contract X) submits the identical `(A, 2, data, [sig1, sig2])` tuple to **contract Y**, deployed either on the same chain or on a different TRON network where account `A`'s permission is identically configured. Because the hash never included contract X's address or a chain id, contract Y's call to `ValidateMultiSign` also returns success, letting the attacker trigger contract Y's gated action using a signature the signers only intended for contract X.
