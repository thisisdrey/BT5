### Title
Exchange Inject/Withdraw compute paired-token amounts from instantaneous spot balances, enabling same-block price-manipulation to drain AMM reserves - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
The `ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the paired ("another") token amount for a liquidity operation strictly from the *current* on-chain balances of the two reserve tokens held by the `ExchangeCapsule` (`firstTokenBalance` / `secondTokenBalance`). Because `ExchangeTransactionActuator` (a normal, unprivileged swap open to any signed transaction) can move these same balances arbitrarily far from their equilibrium via the Bancor-style bonding curve in a preceding transaction of the same block/transaction group, the exchange creator can manipulate the spot ratio immediately before calling withdraw/inject and reverse it immediately after, extracting a disproportionate share of the reserve token pair — the exact "spot-price/flash-loan" pattern described in the referenced Synth `realise()` report.

### Finding Description
`ExchangeWithdrawActuator.execute()`/`doValidate()` derives `anotherTokenQuant` as a pure linear ratio of the current balances: [1](#0-0) 

`ExchangeInjectActuator` does the same on the inject side: [2](#0-1) 

These are simple spot-ratio ("proportional deposit/withdraw", Uniswap-V2-style) computations, with no fee, no bonding-curve slippage, and no TWAP or historical price reference. In contrast, ordinary swaps go through `ExchangeCapsule.transaction()`, which applies the Bancor bonding curve (`ExchangeProcessor`/`SafeExchangeProcessor`) and therefore can shift `firstTokenBalance`/`secondTokenBalance` significantly for a single large trade: [3](#0-2) [4](#0-3) 

`ExchangeTransactionActuator` (the swap actuator) is callable by any account with no restriction: [5](#0-4) 

While `ExchangeWithdrawActuator`/`ExchangeInjectActuator` are restricted to the exchange's `creatorAddress`: [6](#0-5) [7](#0-6) 

`ExchangeCreateActuator` allows any unprivileged account to create an exchange and become its creator, so the "creator" role is itself permissionless and reachable by a single signed transaction: [8](#0-7) 

Because the same account controls both the (permissionless) swap path and the (creator-only) withdraw/inject path, it can, within the same block (multiple transactions from the same account are all executed in `Manager`'s block application in order, with no cooldown or delay enforced between an `ExchangeTransactionContract` and a subsequent `ExchangeWithdrawContract`/`ExchangeInjectContract` against the same exchange):
1. Swap a large amount of token A into the pool, shifting `firstTokenBalance`/`secondTokenBalance` far from the price other traders transacted at.
2. Call `ExchangeWithdrawActuator` to withdraw at the now-skewed spot ratio, receiving a disproportionately large amount of the now-scarce token relative to what was actually deposited earlier by the creator (or `ExchangeInjectActuator` to inject a disproportionately small amount and later withdraw favorably).
3. Reverse the initial swap to restore the original ratio, paying only the round-trip bonding-curve slippage.

Since the exchange reserve is the sole collateral used by `ExchangeProcessor`/`SafeExchangeProcessor` to price every subsequent trade for *all* other users of that exchange, draining/skewing it via this technique degrades the invariant backing future swaps and lets the manipulating account extract value that rightfully belongs to the pool (and, transitively, to counterparties of future trades), all while the code performs no TWAP, no oracle, and no manipulation-resistant ("anti-flash-loan") formula — the exact root cause flagged in the Synth report.

### Impact Explanation
An account that both creates an exchange and actively manipulates its own pool's spot balances via unrestricted swap transactions can systematically extract more value than deposited from the exchange's reserves on withdraw, or deposit less than fair value on inject, at the expense of the shared reserve pool that other users rely on for correctly priced swaps. Repeated exploitation drains/distorts the AMM reserve, degrading pricing integrity for all subsequent traders of that exchange and constituting theft of pooled/reserve value — a Medium/High severity fund-safety issue analogous to the reported LP `realise()` flash-loan attack.

### Likelihood Explanation
The attack requires no special privilege beyond creating one's own exchange (a fully permissionless `ExchangeCreateContract`) and issuing ordinary `ExchangeTransactionContract`/`ExchangeWithdrawContract`/`ExchangeInjectContract` transactions from a single account — all reachable from a single unprivileged transaction broadcaster. No flash loan primitive is even required within java-tron's exchange model since the attacker fully controls both the swap and the creator-only inject/withdraw calls sequentially.

### Recommendation
- Do not compute inject/withdraw paired-token amounts from the mutable, single-block spot balance; instead track proportional "shares" contributed historically (LP-share accounting) rather than re-deriving ratios from current balances at withdrawal time.
- Alternatively, require inject/withdraw amounts to be validated against a manipulation-resistant reference (e.g., a moving average of `firstTokenBalance`/`secondTokenBalance` over multiple blocks) rather than the instantaneous values read directly from `ExchangeCapsule`.
- Add a minimum delay/cooldown between a swap and a subsequent inject/withdraw on the same exchange by the same creator, or disallow both actions within the same block.

### Proof of Concept
1. Attacker calls `ExchangeCreateActuator` to create Exchange `E` with tokens A/B, becoming `creatorAddress`.
2. Other users trade against `E` via `ExchangeTransactionActuator`, growing/adjusting `firstTokenBalance`/`secondTokenBalance` per the Bancor curve in `ExchangeCapsule.transaction()`.
3. Attacker submits a large `ExchangeTransactionContract` swap of A→B, sharply lowering `secondTokenBalance` relative to `firstTokenBalance`.
4. Attacker immediately submits `ExchangeWithdrawContract` for token A; `anotherTokenQuant` in `ExchangeWithdrawActuator.execute()` (`bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)`) is computed off the now-skewed ratio, yielding a smaller-than-fair `secondTokenBalance` decrease for a given A withdrawal, effectively letting attacker keep more B in the pool while removing A, or the inverse depending on direction chosen.
5. Attacker reverses the swap (B→A) to restore balances, paying only bonding-curve round-trip cost, having net-extracted value from the manipulated withdraw/inject relative to true reserve value.

          : firstTokenBalance + sellTokenQuant;

          : firstTokenBalance - buyTokenQuant;
