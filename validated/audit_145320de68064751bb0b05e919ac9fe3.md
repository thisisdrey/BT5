### Title
Uninitialized reward account index over-credits claimable rewards equal to full token balance — (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenDelta()` confuses "account never checkpointed" (`accountIndexOf == 0`) with "account checkpointed at index 0" whenever the global token index is equal to or below `INITIAL_INDEX` (`1e18`). The fallback at line 225 only kicks in when `_tokenIndex > INITIAL_INDEX`; right after a reward token is activated, the index is exactly `INITIAL_INDEX`, so a 0-valued account index produces `_deltaIndex = 1e18` and credits the user `balance * 1e18` (i.e., their full token balance) of reward tokens. This is the same bug class as the GLib advisory: a state-confusion error in index accounting producing an unsigned-arithmetic over-read/over-credit.

### Finding Description [1](#0-0) 

The account index stored in `accountIndexOf[token_][account_]` is only ever written inside `_updateTokensAccruedOf()` (line 263). For any account that has never been touched by a rewards update, it is `0`. The code attempts to handle this via:

```solidity
if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
uint256 _deltaIndex = _tokenIndex - _accountIndex;
```

But `_updateTokenSpeed()` initializes a new reward token with `TokenState({index: INITIAL_INDEX, ...})` — i.e., `index == 1e18`, not `> 1e18`: [2](#0-1) 

Consequently, in the window between token activation and the first index increase (and permanently if `speed` is later set to a nonzero value in the same block or accrued deltas round down), `_tokenIndex - _accountIndex = 1e18 - 0 = 1e18`, and `_tokensDelta = token_.balanceOf(account_).wadMul(1e18)` equals the account's entire DepositToken/DebtToken balance, denominated in the reward token.

`updateBeforeMintOrBurn` and `updateBeforeTransfer` are permissionless and called automatically by `DepositToken`/`DebtToken` hooks (`updateRewardsBeforeMintOrBurn`, lines 124-131 of `DepositToken.sol`), and `claimRewards(account_)` is callable by anyone for any account: [3](#0-2) 

An unprivileged attacker can therefore, the moment a reward token is activated, deposit collateral (or have debt), then call `claimRewards(attacker)` (or simply trigger any transfer/mint hook that runs `_updateTokensAccruedOf`) and drain the distributor's reward-token balance up to `_rewardToken.balanceOf(this)` via `_transferRewardIfEnoughTokens`.

### Impact Explanation
Direct theft of unclaimed yield: the attacker siphons the entire `rewardToken` balance of the `RewardsDistributor` (rewards accrued for all legitimate users) in a single transaction, proportional only to their deposit/debt balance which flash-loaned or freshly-deposited collateral can supply. The same state-confusion also silently corrupts `tokensAccruedOf`, so even partial claims permanently misattribute the reward pool. No privileged role, oracle manipulation, or external protocol misbehavior is required — only the ordinary administrative action of enabling a reward token, plus a public `claimRewards` call.

### Likelihood Explanation
Triggering requires a reward token whose `tokenStates[token].index` equals `INITIAL_INDEX` while some account has `accountIndexOf == 0` — this is guaranteed to be true for every account at the instant any token's speed is first enabled, and again whenever a second token is added (existing holders have no index for the new token). `claimRewards` is permissionless, `nonReentrant` does not help (no reentrancy needed), and no health/pause checks gate it. The only precondition is a routine governor `updateTokenSpeed(s)` call — normal operations, not a malicious parameter choice.

### Recommendation
Treat a zero `accountIndexOf` as "checkpoint at current token index" unconditionally, not only when `_tokenIndex > INITIAL_INDEX`:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex; // or INITIAL_INDEX semantics that never yield delta for index == INITIAL_INDEX
}
```

Alternatively, set `accountIndexOf` to `INITIAL_INDEX` lazily whenever `_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX`, and additionally skip delta computation entirely when `_tokenIndex == _accountIndex`. Also consider recording per-token "has been updated" flags instead of overloading the zero index.

### Proof of Concept
Hardhat test against the existing suite (`test/` uses hardhat + ethers):

```ts
it('drains rewards via uninitialized account index', async () => {
  // given: alice holds msdMET before reward token activation
  // governor enables reward speed on msdMET for the first time
  await rewardsDistributor.connect(governor).updateTokenSpeed(msdMET.address, parseEther('0.01'))

  // fund the distributor with reward tokens
  await rewardToken.mint(rewardsDistributor.address, parseEther('1000'))

  // when: attacker (any EOA, e.g. bob with a deposit) claims in the same block
  // tokenStates.index == INITIAL_INDEX, accountIndexOf[bob] == 0
  const tx = rewardsDistributor.claimRewards(bob.address)
  await expect(tx).to.emit(rewardsDistributor, 'RewardClaimed')

  // then: bob is credited ~his full msdMET balance in rewardToken,
  // despite zero elapsed accrual time
  expect(await rewardToken.balanceOf(bob.address)).to.be.gt(0)
})
```

Expected: `_deltaIndex == 1e18`, `_tokensDelta == msdMET.balanceOf(bob)`, transferred out of the distributor. Note: this analysis is based on the indexed source of `RewardsDistributor.sol`; a fork-mode run against deployed addresses in `deployments/` would confirm distributor balance and which tokens currently sit at `INITIAL_INDEX`.
