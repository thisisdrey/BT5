### Title
Account deletion leaves dangling account-scoped receipt/yield state (`ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`) that gets delivered to a recreated account - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (`core/store/src/utils/mod.rs:505-575`), invoked by `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`), only removes `TrieKey::Account`, `TrieKey::ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` entries for the deleted account. It does not remove `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId` entries keyed by that same `account_id`/`receiver_id`, even though these are all written by `set()`/`set_postponed_receipt`/`set_received_data`/`set_promise_yield_receipt` calls that key solely on the account id. Because these entries survive account deletion, and the account name becomes free for anyone (including the deleting party) to recreate, a stale postponed/yield receipt can later be delivered and executed against whatever account now occupies that name.

### Finding Description
Enumerating the write sites that key state solely by `account_id`/`receiver_id`:
- `set_received_data` → `TrieKey::ReceivedData` [1](#0-0) 
- `process_action_receipt` → `TrieKey::PostponedReceiptId` and `TrieKey::PendingDataCount`, then `set_postponed_receipt` → `TrieKey::PostponedReceipt` [2](#0-1) 
- `set_promise_yield_receipt` → `TrieKey::PromiseYieldReceipt` [3](#0-2) 
- `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId` are keyed the same way (all carry `receiver_id`) [4](#0-3) 

Against this, `remove_account` only issues `state_update.remove(...)` for `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData`: [5](#0-4) 

`action_delete_account` calls `remove_account` unconditionally as long as storage usage and gas-key-balance limits are satisfied and locked stake is zero — there is no check for outstanding postponed/yield state for the account being deleted: [6](#0-5) [7](#0-6) 

Later, when the missing `DataReceipt`/`PromiseResume` finally arrives, the runtime looks up `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` (or `PromiseYieldReceipt`/`PromiseYieldStatus`) purely by `account_id`, with no check that the account still exists or is "the same" account as when the entry was created, and then executes the resolved `ActionReceipt` via `apply_action_receipt` against whatever `Account` currently occupies that id: [8](#0-7) [9](#0-8) 

Attacker flow (fully unprivileged):
1. Attacker owns `victim.attacker.near`, deploys an honest-looking contract that performs a cross-contract call creating a postponed `ActionReceipt` targeting `victim.attacker.near` awaiting a `data_id` the attacker fully controls (i.e., a callback that is never actually resolved on schedule). At this point `PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` are all stored keyed by `victim.attacker.near`.
2. An unsuspecting counterparty's transaction/receipt chain deposits funds/attaches gas into that pending `ActionReceipt` destined for `victim.attacker.near` (e.g., expecting escrow release, a swap completion, or an NFT transfer once the callback resolves).
3. Attacker submits `DeleteAccount` on `victim.attacker.near` (permitted: actor is the account itself, zero locked stake, storage usage under the deletion cap). `remove_account` wipes the `Account`/keys/contract/data rows but leaves the postponed-receipt bookkeeping rows untouched.
4. Attacker recreates `victim.attacker.near` (a `CreateAccount` action is always valid once the name is free) and deploys a new, malicious contract.
5. Attacker triggers delivery of the previously withheld `Data`/`PromiseResume` receipt. The runtime finds the still-present `PostponedReceiptId`/`PendingDataCount`, fetches the still-present `PostponedReceipt`, and executes its actions (including the deposit/`FunctionCall` originally destined for the honest contract) against the newly-deployed malicious contract, since `apply_action_receipt` simply does `get_account(state_update, account_id)` on the current state with no linkage back to the account incarnation the receipt was originally queued for.

No existing check (signature, nonce, access key, storage-staking, or account-existence validation in `check_account_existence`/`check_actor_permissions`) prevents deleting an account that still has account-scoped postponed/yield state, and no check prevents recreating that account name afterward.

### Impact Explanation
This enables theft of funds/assets that were attached to a pending cross-contract callback: a legitimate deposit or promise result destined for one contract incarnation of an account is instead delivered to an attacker-controlled contract deployed after the account was deleted and recreated. This matches the "theft of user funds" bounty category. It can also corrupt protocol invariants (e.g., a `PromiseYieldStatus`/`YieldIdToDataId` entry surviving into a differently-owned recreated account, causing a resumed yield/callback to execute with the wrong contract logic/state).

### Likelihood Explanation
The attacker only needs to control one subaccount (trivial, no privileges required), orchestrate a self-timed postponed receipt (fully within their control), delete their own account (a normal, self-authorized action), and recreate it before/while triggering delivery of the deferred data. All of the steps use ordinary transactions available to any funded account; no validator/node/protocol-level access is needed, and the attack is repeatable at will.

### Recommendation
In `remove_account` (`core/store/src/utils/mod.rs`), additionally enumerate and remove all `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` entries scoped to the account being deleted (mirroring the existing access-key/contract-data iteration pattern), or alternatively reject `DeleteAccount` while any such entries exist for the account (similar to the existing locked-stake/storage-usage checks in `check_actor_permissions`/`action_delete_account`).

### Proof of Concept
Unit test plan (Rust, `core/store` or `runtime/runtime` test suite):
1. Build a `TrieUpdate` and call `set_postponed_receipt`, `set(TrieKey::PendingDataCount{...})`, `set(TrieKey::PostponedReceiptId{...})`, `set_received_data`, `set_promise_yield_receipt`, `set(TrieKey::PromiseYieldStatus{...})`, `set(TrieKey::YieldIdToDataId{...})`, `set(TrieKey::DataIdToYieldId{...})` for a fixed `account_id = "victim.near"`.
2. Call `remove_account(&mut state_update, &account_id)`.
3. Assert that `get_postponed_receipt`, `get(TrieKey::PendingDataCount{...})`, `get(TrieKey::PostponedReceiptId{...})`, `get_received_data`, `get_promise_yield_receipt`, `get_promise_yield_status`, and the yield-id mapping getters still return `Some(..)` after `remove_account` — demonstrating the asymmetry (`set(written_trie_key_variants) != set(cleared_trie_key_variants)`).
4. Integration/test-loop reproduction: deploy a contract at a subaccount, have it issue a cross-contract call creating a postponed receipt targeting itself with deposit/gas attached, call `DeleteAccount` on itself, recreate the account with a different contract, then deliver the deferred `Data`/`PromiseResume` receipt and assert that the new contract's `FunctionCall`/`Transfer` actions from the stale postponed receipt execute against the recreated account (e.g., balance increase visible to the new, attacker-controlled contract instead of failing or being dropped).

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
