### Title
Missing account-balance deduction in `action_transfer_to_gas_key` mints NEAR via `TransferToGasKey`/`WithdrawFromGasKey` round-trip — ([File: runtime/runtime/src/access_keys.rs])

### Summary
`action_transfer_to_gas_key` credits a gas key's internal `GasKeyInfo.balance` "reserve" with the `deposit` amount but never debits the owning account's `Account.amount`. Its counterpart, `action_withdraw_from_gas_key`, correctly performs the symmetric operation (decrements the gas-key balance and *credits* the account). The asymmetry lets a signer mint NEAR out of thin air by transferring into a gas key and withdrawing it back, exactly the "reserve vs. actual balance" desync pattern in the external report (an internal accounting ledger is bumped without a matching movement of the backing asset).

### Finding Description
Compare the two action handlers in `runtime/runtime/src/access_keys.rs`: [1](#0-0) 

`action_transfer_to_gas_key` only does:
```
gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit)?;
set_access_key(...)
```
There is no `account.set_amount(account.amount().checked_sub(action.deposit)?)` anywhere in this function, nor in its caller.

`action_withdraw_from_gas_key` performs the full symmetric transfer: [2](#0-1) 
It subtracts from `gas_key_info.balance` (line 315-325) **and** adds to `account.amount()` (line 328-333).

The dispatcher in `apply_action` passes the mutable `Account` to `action_withdraw_from_gas_key` (so it can update `account.amount()`), but for `Action::TransferToGasKey` it only passes `state_update`/`account_id`, not the mutable account — because the function never touches account balance: [3](#0-2) 

The existing unit test for the success path only asserts that `gas_key_info.balance` increased; it never checks that the account balance decreased, which is consistent with (and would have caught) this omission: [4](#0-3) 

Because `GasKeyInfo.balance` lives inside the `AccessKey` trie record rather than the `Account` record, and the runtime's balance-checker invariant is defined over "sum of the final accounts' balance for all affected accounts" (i.e., `Account.amount`/`locked`), a bump to a gas key's balance that is not mirrored by an `Account.amount` decrease is not caught by that invariant: [5](#0-4) 

The result: `TransferToGasKeyAction { public_key, deposit }` (available both as a transaction action and via the `promise_batch_action_transfer_to_gas_key` host function) increases the target gas key's spendable balance without any funds leaving the account, and that credited balance can subsequently be spent directly on gas-key transactions or withdrawn back to the account balance via `WithdrawFromGasKeyAction`, which does perform the real credit.

### Impact Explanation
This is unconditional token inflation reachable by any ordinary signer possessing (or creating, since `AddKey` can add a gas key) a gas key on their own account:
1. Add a gas key (`AddKey` with `AccessKey::gas_key_full_access`).
2. Call `TransferToGasKeyAction { deposit: X }` — the account is not charged, but the gas key balance is credited by `X`.
3. Call `WithdrawFromGasKeyAction { amount: X }` — the account balance is credited by `X` (from `action_withdraw_from_gas_key`).

Net effect: the account gains `X` NEAR (minus only the ordinary tx gas fees for the two cheap actions) with no offsetting debit anywhere in the system — inflating total token supply, which the rules classify as directly in-scope impact ("token inflation or loss").

### Likelihood Explanation
Both actions (`TransferToGasKey`, `WithdrawFromGasKey`) are ordinary, unprivileged transaction actions available to any signer that controls an access key on the target account, and are also reachable from within a contract via `promise_batch_action_transfer_to_gas_key` host function: [6](#0-5) 
No privileged role, mocked path, or node/network compromise is required — a single self-signed transaction sequence suffices. This makes the likelihood very high if the described code path is indeed missing the debit (see caveat below).

### Recommendation
In `action_transfer_to_gas_key` (`runtime/runtime/src/access_keys.rs:257`), deduct `action.deposit` from the account's balance (analogous to `action_withdraw_from_gas_key`'s symmetric credit), returning `LackBalanceForState`/insufficient-balance error if the account cannot afford it, and update the `apply_action` dispatcher in `runtime/runtime/src/lib.rs:749-757` to pass the mutable `Account` into `action_transfer_to_gas_key` so it can perform `account.set_amount(account.amount().checked_sub(action.deposit)...)`. Add a regression test mirroring `test_withdraw_from_gas_key_success` (`runtime/runtime/src/access_keys.rs:1070`) that asserts the account balance decreases by exactly `deposit` after `TransferToGasKeyAction`.

### Proof of Concept
1. Create/own an account `alice` with a full-access key.
2. Submit `AddKey(gas_key_pub, AccessKey::gas_key_full_access(n))` on `alice`.
3. Submit `TransferToGasKeyAction { public_key: gas_key_pub, deposit: 1000 NEAR }` from `alice`.
   - Expected (buggy) result: `alice.amount()` unchanged; gas key's `GasKeyInfo.balance == 1000 NEAR` (see `test_transfer_to_gas_key_success`, `runtime/runtime/src/access_keys.rs:996-1020`, which only checks the gas-key side).
4. Submit `WithdrawFromGasKeyAction { public_key: gas_key_pub, amount: 1000 NEAR }` from `alice`.
   - Result: `alice.amount()` increases by 1000 NEAR (per `action_withdraw_from_gas_key`, `runtime/runtime/src/access_keys.rs:328-333`), and gas key balance returns to 0.
5. Net: `alice` gained 1000 NEAR that was never debited from any account — repeatable indefinitely, minting unlimited NEAR.

**Caveat:** I could not find any additional debit of `account.amount` for `TransferToGasKeyAction` elsewhere in the reachable code (e.g., in `verifier.rs`'s `total_deposit`/tx-cost calculations, which appear to only affect refund bookkeeping for failed receipts, not a live balance debit). Given index-size limits, I was not able to fully rule out a debit occurring in a location outside what the index returned (e.g. inside `config.rs`'s fee tables which only cover gas costs, not the deposit itself). If such an omitted debit is confirmed by a full code read (recommended via a Devin session with complete repo access), this would be a critical, generally-applicable token-inflation vulnerability in the gas-key mechanism.

```rust
pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
```

```rust
pub(crate) fn action_withdraw_from_gas_key(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &WithdrawFromGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    let Some(updated_balance) = gas_key_info.balance.checked_sub(action.amount) else {
        result.result = Err(ActionErrorKind::InsufficientGasKeyBalance {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
            balance: gas_key_info.balance,
            required: action.amount,
        }
        .into());
        return Ok(());
    };
    gas_key_info.balance = updated_balance;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);

    let new_account_balance = account.amount().checked_add(action.amount).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "Account balance integer overflow".to_string(),
        ))
    })?;
    account.set_amount(new_account_balance);
    Ok(())
}
```

```markdown
## Balance checker

Balance checker computes the total incoming balance and the total outgoing balance.

The total incoming balance consists of the following:

- Incoming validator rewards from validator accounts update.
- Sum of the initial accounts balances for all affected accounts. We compute it using the snapshot of the initial state.
- Incoming receipts balances. The prepaid fees and gas multiplied their gas prices with the attached balances from transfers and function calls.
  Refunds are considered to be free of charge for fees, but still has attached deposits.
- Balances for the processed delayed receipts.
- Initial balances for the postponed receipts. Postponed receipts are receipts from the previous blocks that were processed, but were not executed.
  They are action receipts with some expected incoming data. Usually for a callback on top of awaited promise.
  When the expected data arrives later than the action receipt, then the action receipt is postponed.
  Note, the data receipts are 0 cost, because they are completely prepaid when issued.

The total outgoing balance consists of the following:

- Sum of the final accounts balance for all affected accounts.
- Outgoing receipts balances.
- New delayed receipts. Local and incoming receipts that were not processed this time.
- Final balances for the postponed receipts.
- Total rent paid by all affected accounts.
- Total new validator rewards. It's computed from total gas burnt rewards.
- Total balance burnt. In case the balance is burnt for some reason (e.g. account was deleted during the refund), it's accounted there.
- Total balance slashed. In case a validator is slashed for some reason, the balance is account here.

When you sum up incoming balances and outgoing balances, they should match.
If they don't match, we throw an error.
```

```rust
pub fn promise_batch_action_transfer_to_gas_key(
    ctx: &mut Ctx,
    memory: &mut [u8],
    promise_idx: u64,
    public_key_len: u64,
    public_key_ptr: u64,
    amount_ptr: u64,
) -> Result<()> {
    ctx.result_state.gas_counter.pay_base(base)?;
    if ctx.context.is_view() {
        return Err(HostError::ProhibitedInView {
            method_name: "promise_batch_action_transfer_to_gas_key".to_string(),
        }
        .into());
    }
    let public_key_buf = get_public_key(
        &mut ctx.result_state.gas_counter,
        memory,
        &ctx.registers,
        public_key_ptr,
        public_key_len,
        ctx.ext.post_quantum_keys_enabled(),
    )?;
    let public_key_res = public_key_buf.decode();
    let pk_len = public_key_res.as_ref().map_or(0, |pk| pk.len());
    let amount =
        Balance::from_yoctonear(get_u128(&mut ctx.result_state.gas_counter, memory, amount_ptr)?);
    let (receipt_idx, sir) = promise_idx_to_receipt_idx_with_sir(ctx, promise_idx)?;
    let receiver_id = ctx.ext.get_receipt_receiver(receipt_idx);
    let send = gas_key_transfer_send_fee(&ctx.fees_config, sir, pk_len);
    let exec_pk_len = gas_key_exec_pk_len(&public_key_res, &ctx.config, pk_len);
    let exec = gas_key_transfer_exec_fee(&ctx.fees_config, receiver_id.len(), exec_pk_len);
    let burn_base = send.base;
    let use_base = burn_base.gas.checked_add(exec.base.gas).ok_or(HostError::IntegerOverflow)?;
    ctx.result_state.gas_counter.pay_action_accumulated(
        burn_base,
        use_base,
        ActionCosts::gas_key_transfer_base,
    )?;
    let burn_byte = send.per_byte;
    let use_byte =
        burn_byte.gas.checked_add(exec.per_byte.gas).ok_or(HostError::IntegerOverflow)?;
    ctx.result_state.gas_counter.pay_action_accumulated(
        burn_byte,
        use_byte,
        ActionCosts::gas_key_byte,
    )?;
    ctx.result_state.deduct_balance(amount)?;
    ctx.ext.append_action_transfer_to_gas_key(receipt_idx, public_key_res?, amount);
```
