### Title
Gateways do not verify the DepositToken exists, permanently locking user funds - ([File: contracts/VesperGateway.sol](contracts/VesperGateway.sol), [File: contracts/NativeTokenGateway.sol](contracts/NativeTokenGateway.sol))

### Summary
Analogous to `AuctionHouse.createBid()` acting on a non-existent auction and losing the user's ETH, `VesperGateway.deposit()` and `NativeTokenGateway.deposit()` only check that the `pool_` is registered — they never verify that `pool_.depositTokenOf(vToken_)` / `pool_.depositTokenOf(nativeToken)` actually exists (non-zero). When the deposit token doesn't exist, the call chain silently succeeds while the user's assets end up stuck inside the gateway contract, minting nothing.

### Finding Description
In `VesperGateway.deposit()` the only validation is `isPoolRegistered(pool_)`. The function then (1) pulls `amount_` of `underlying` from the caller, (2) deposits it into the user-chosen `vToken_` (`vToken_.deposit(amount_)`), and (3) looks up the corresponding `IDepositToken` and calls `_depositToken.deposit(_vTokenAmount, _msgSender)`:

- `VesperGateway.sol:45` `if (!_poolRegistry.isPoolRegistered(address(pool_))) revert UnregisteredPool();`
- `VesperGateway.sol:51` `_underlying.safeTransferFrom(_msgSender, address(this), amount_);`
- `VesperGateway.sol:57` `vToken_.deposit(amount_);`
- `VesperGateway.sol:61` `IDepositToken _depositToken = pool_.depositTokenOf(vToken_);`
- `VesperGateway.sol:64` `_depositToken.deposit(_vTokenAmount, _msgSender);`

If the pool does not list `vToken_` as collateral, `depositTokenOf` returns `address(0)`. Solidity high-level calls to an address with no code succeed, so `_depositToken.deposit(...)` is a silent no-op. `vToken_.safeApprove(address(0), ...)` also succeeds because `approve` is executed on the real vToken contract. Result: the user's underlying was converted into vTokens now held by the gateway, and no `msdToken` was ever minted to the user. The same shape exists in `NativeTokenGateway.deposit()` (`NativeTokenGateway.sol:46-54`): `msg.value` ETH is wrapped into WETH, approved to `address(0)`, and the final `deposit` no-ops — the ETH is lost to the gateway.

The stuck tokens sit in the contract and can only be recovered through the governor-gated `TokenHolder.sweep()` (`TokenHolder.sol:37-45`); the unprivileged caller has no way to reclaim them.

### Impact Explanation
Direct loss of user funds: any caller invoking `VesperGateway.deposit()` (or payable `NativeTokenGateway.deposit()`) on a registered pool that lacks a `DepositToken` for that vToken/native token loses their entire input amount. Funds are frozen in the gateway (permanently, unless governance intervenes via `sweep`) — identical bug class and impact to the original "createBid on non-existent auction → lost ETH" report.

### Likelihood Explanation
Reachable by any EOA with no privileges. `VesperGateway.deposit` accepts an arbitrary `vToken_` and any registered `pool_`, so any Vesper vToken not yet onboarded to a given pool (or a pool that supports some vTokens but not others) triggers it. `NativeTokenGateway.deposit` triggers whenever a registered pool does not list the native token as a `DepositToken`. No reentrancy guard, pause flag, or SynthContext check prevents it — the only guard (`UnregisteredPool`) passes because the pool itself is valid.

### Recommendation
Check that the deposit token exists before pulling/wrapping user funds, and revert otherwise:

```solidity
// VesperGateway.deposit / withdraw
IDepositToken _depositToken = pool_.depositTokenOf(vToken_);
if (address(_depositToken) == address(0)) revert DepositTokenDoesNotExist();

// NativeTokenGateway.deposit
IDepositToken _depositToken = pool_.depositTokenOf(nativeToken);
if (address(_depositToken) == address(0)) revert DepositTokenDoesNotExist();
```

Note `pool_.isDepositTokenExists()` may not exist on `IPool`; checking `depositTokenOf(...) != address(0)` (or adding a registry-level `isDepositTokenExists`) is sufficient.

### Proof of Concept
```solidity
// Hardhat fork test
// Setup: `pool` is a registered Pool that does NOT list `someVToken` (vaUSDC, etc.)
//        or that lacks a DepositToken for WETH.

// VesperGateway variant
await underlying.connect(user).approve(vesperGateway.address, amount);
const before = await underlying.balanceOf(user.address);
await vesperGateway.connect(user).deposit(pool.address, vToken.address, amount);
// tx does NOT revert
expect(await underlying.balanceOf(user.address)).to.eq(before.sub(amount)); // user paid
expect(await vToken.balanceOf(vesperGateway.address)).to.be.gt(0);          // stuck in gateway
expect(await depositToken.balanceOf(user.address)).to.eq(0);                // nothing minted
// only governor.sweep(vToken, ...) can recover the funds

// NativeTokenGateway variant (pool without msdWETH)
await nativeTokenGateway.connect(user).deposit(pool.address, {value: parseEther('1')});
// tx does NOT revert; WETH balance of gateway increased, user received no msdToken
```

Caveat: I could not fully confirm `Pool.depositTokenOf` returns `address(0)` rather than reverting for unlisted underlyings within the tool-call budget — the mapping-style accessor in `PoolStorage.sol`/`IPool.sol` should be checked; if it reverts, this path still reverts but with an opaque error and the finding degrades to a UX issue.
