Confirmed: a single signed `DefusePayload` message can carry a `Vec<Intent>` (`DefuseIntents.intents`) executed under one signature [1](#0-0) , and each `Intent::TokenDiff` is executed independently, each computing its own fee via `TokenDiff::token_fee` based solely on that single intent's per-token `delta.unsigned_abs()` [2](#0-1) . `token_fee` explicitly returns `Pips::ZERO` for `Nep245`/`Imt`/`Nep171` token types when `amount <= 1` [3](#0-2) . Fees are never recomputed on an aggregated, cross-intent, or cross-batch basis — `execute_signed_intent` simply iterates and executes each `Intent` in sequence, applying deltas and, on the negative side, `fee_ceil` independently for each `TokenDiff` [4](#0-3) . Settlement correctness (i.e., that the batch balances) is enforced only by `TransferMatcher::finalize`, which matches deposits/withdrawals across the whole `MultiPayload` batch regardless of how they were split into individual intents or how many signers contributed them [5](#0-4) ; it does not re-derive or re-charge fees.

This confirms the premise: an unprivileged signer can split what would be one `TokenDiff{delta: -1000}` (which would incur `fee_ceil(protocol_fee, 1000)`) into 1000 `TokenDiff{delta: -1}` intents inside a single signed `DefuseIntents` message, each below the `amount <= 1` exemption threshold, paying `Pips::ZERO` per leg, while a matching counterparty (even the same attacker's second account, or a genuine liquidity counterparty) supplies the offsetting `+1000` (positive deltas never incur fees regardless of size) so the batch nets to zero and passes `TransferMatcher::finalize` [6](#0-5) .

### Title
Protocol fee bypass on NEP-245/IMT token diffs via micro-delta splitting - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::token_fee` exempts NEP-245/IMT/NEP-171 legs from fees whenever the per-intent `|delta| <= 1`, but fee computation is scoped strictly to a single `TokenDiff` intent rather than to the net aggregate delta of a token across the whole `MultiPayload` batch. An unprivileged signer can pack any number of `TokenDiff` intents, each moving `1` unit of the same `Nep245TokenId`, into one signed `DefuseIntents` message (paired with an offsetting counterparty deposit elsewhere in the batch), settling an arbitrarily large net negative delta of that token while paying zero protocol fee.

### Finding Description
The broken binding is: `fee_collector.balance_delta(T) == Pips::fee_ceil(protocol_fee, |net_negative_delta(T)|)` for the batch. Actual code enforces per-intent fee: for each `TokenDiff` intent, `fee = TokenDiff::token_fee(token_id, delta.unsigned_abs(), protocol_fee).fee_ceil(amount)` [6](#0-5) , and `token_fee` zeroes the fee for `Nep245`/`Imt` when `amount <= 1` [3](#0-2) . Since `DefuseIntents` allows an arbitrary `Vec<Intent>` under one signature, and `Intent::TokenDiff` execution is fully independent per entry [7](#0-6) , the signer_id can include 1000 `TokenDiff{diff: {T: -1}}` intents; each pays `Pips::ZERO`, but the aggregate withdrawal from `signer_id` for `T` is 1000 units. `TransferMatcher::finalize` only checks that deposits and withdrawals net to zero across the whole batch, with no fee re-derivation [5](#0-4) , so as long as another party (or another intent from the same signer/colluding account) contributes a matching `+1000` deposit of `T` (itself fee-free since fees are only taken on negative deltas, line 70 of token_diff.rs), the batch settles successfully with `fee_collector` receiving `0` instead of `Pips::fee_ceil(protocol_fee, 1000)`.

### Impact Explanation
This directly under-collects protocol fees on any real NEP-245/IMT trade that the attacker structures as many 1-unit legs instead of one large-amount leg, matching the rubric's explicit Critical category "protocol fees bypassed or over-collected." The `fee_collector` account is denied funds it is otherwise entitled to; the blast radius is any MT/IMT trade route through `TokenDiff`, repeatable indefinitely and across any `Nep245TokenId`/`ImtTokenId` and any batch size, at the cost of only extra intents (not extra fees or signatures, since one signature covers the whole `DefuseIntents` list).

### Likelihood Explanation
Preconditions: attacker only needs their own signing key, their own real balance of the NEP-245/IMT token being traded (real withdrawal, real matching deposit from a counterparty in the same batch), and the ability to submit a `MultiPayload`/`execute_intents` call — all within the unprivileged capabilities defined by the rules. No role, relayer key, or victim key is required. Cost is negligible (bytes for extra `TokenDiff` JSON entries in one signed message); feasibility is high and fully repeatable per trade/batch.

### Recommendation
Compute the NEP-245/IMT fee exemption against the net aggregate delta per `TokenId` across the entire `DefuseIntents`/batch (e.g., pre-aggregate all `TokenDiff` deltas per token before evaluating `amount <= 1`), or remove/tighten the per-leg exemption so it cannot be trivially defeated by splitting a single trade into many 1-unit `TokenDiff` intents.

### Proof of Concept
`cargo test` (near-workspaces sandbox) plan:
1. Create two users `attacker` and `counterparty`, deploy an MT contract, mint `1000` units of `Nep245TokenId` to `attacker`'s Defuse balance.
2. Set `protocol_fee` to a non-zero `Pips` value (e.g. `Pips::ONE_PERCENT`).
3. Build one `DefuseIntents` message signed once by `attacker` containing 1000 `Intent::TokenDiff` entries, each `{diff: {T: -1}}`.
4. Build a second signed `DefuseIntents` (by `counterparty`, or by `attacker`'s second controlled account) with one `Intent::TokenDiff {diff: {T: +1000}}` to balance the batch.
5. Call `execute_intents` with both signed payloads as one `MultiPayload` batch.
6. Assert: `fee_collector` `token_balances` for `T` after execution `== 0`, versus the expected `Pips::fee_ceil(protocol_fee, 1000)` that a single `TokenDiff{diff: {T: -1000}}` intent would have produced — demonstrating the binding `fee_collector.balance_delta(T) == Pips::fee_ceil(protocol_fee, 1000)` is violated (actual `0`).

    // Finalizes all transfers, or returns unmatched deltas.
    // If unmatched deltas overflow, then Err(None) is returned.
    pub fn finalize(self) -> Result<Transfers, InvariantViolated> {
        let mut transfers = Transfers::default();
        let mut deltas = TokenDeltas::default();
        for (token_id, transfer_matcher) in self.0 {
            if let Err(unmatched) = transfer_matcher.finalize_into(&token_id, &mut transfers)
                && (unmatched == 0 || deltas.apply_delta(token_id, unmatched).is_none())
            {
                return Err(InvariantViolated::Overflow);
            }
        }
        if !deltas.is_empty() {
            return Err(InvariantViolated::UnmatchedDeltas {
                unmatched_deltas: deltas,
            });
        }
        Ok(transfers)
    }
}
