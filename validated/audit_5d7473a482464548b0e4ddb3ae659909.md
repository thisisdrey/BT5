### Title
Hash Collision in `createArchiveCacheKey` Enables Archive Cache Cross-Request Content Disclosure - ([File: internal/gitaly/service/repository/archive.go])

### Summary
`createArchiveCacheKey` in `internal/gitaly/service/repository/archive.go` builds the `GetArchive` stream-cache key by writing three variable-length, attacker-influenced strings (`GlProjectPath`, joined `args`, joined `pathspecs`) directly into a SHA-256 hash with no length prefixing or delimiter between them, mirroring the `abi.encodePacked` ambiguous-concatenation issue in the referenced Solidity report.

### Finding Description
`createArchiveCacheKey` hashes the concatenation of three fields without any separator or length prefix: [1](#0-0) 

The inputs are `repo.GetGlProjectPath()` and the `args`/`pathspecs` slices, which are built directly from RPC-supplied fields (`CommitId`, `Path`, `Exclude`, `ElidePath`) in `handleArchive`: [2](#0-1) 

Because `strings.Join` output for `args` is written immediately followed by the `pathspecs` join with no delimiter, two semantically different `GetArchive` requests can produce byte-identical concatenations (e.g. `args=["abc"], pathspecs=["def"]` vs. `args=["ab"], pathspecs=["cdef"]` both yield `"...abcdef"`), causing the same SHA-256 cache key. This key is then used to look up or populate the shared `streamcache.Cache`: [3](#0-2) 

The cache's `Fetch`/`getStream` implementation trusts the key as a unique identifier and serves whatever content is already indexed under a colliding key without re-validating the request parameters: [4](#0-3) 

Notably, Gitaly's own `internal/cache/keyer.go` demonstrates the correct fix pattern for this exact class of bug — it length-prefixes each component before hashing specifically "to reduce the risk of collisions due to different combinations of concatenated strings producing the same content": [5](#0-4) 

`createArchiveCacheKey` does not apply this same mitigation, leaving the archive cache key construction vulnerable to the analogous collision.

### Impact Explanation
If a caller can influence `CommitId`, `Path`, `Exclude`, or `ElidePath` (fields that end up composing `args`/`pathspecs`) to engineer a matching concatenation with a previously cached (or subsequently requested) archive, the streamcache may return archive content generated for a different commit/path/exclude combination — and potentially a different repository/project, since `GlProjectPath` is one of the concatenated, non-delimited fields. This is a concrete cross-request cache poisoning / content-disclosure primitive within the shared archive cache used by `GetArchive`.

### Likelihood Explanation
`GetArchive` is reachable by any caller permitted to invoke the RPC with attacker/user-influenced `commit_id`, `path`, and `exclude` values, which GitLab typically forwards for user-initiated partial/full repository archive downloads. Constructing a colliding request only requires knowledge of another request's parameter lengths (which are often predictable, e.g., default archive requests with no path/exclude), so the likelihood of a practical collision is non-trivial though it requires some coordination of string lengths.

### Recommendation
Apply the same length-prefixing scheme already used in `internal/cache/keyer.go` (`prefixLen`) — or an unambiguous delimiter/encoding such as writing each field's length before its bytes — when hashing `gitLabProjectPath`, `args`, and `pathspecs` in `createArchiveCacheKey`, so that no combination of these fields can produce colliding byte concatenations.

### Proof of Concept
1. Trigger `GetArchive` with `Repository.GlProjectPath="proj"`, no path, `CommitId="abc"` such that `args=["abc"]`, `pathspecs=["def-equivalent-pathspec"]`, causing `createArchiveCacheKey` to hash `"proj" + "abc" + "def"`.
2. Trigger a second `GetArchive` request with `GlProjectPath="proja"`, `CommitId="bc"`, and an `Exclude`/`Path` combination that produces `pathspecs=["def"]`, causing the hash input to be `"proja" + "bc" + "def"` — identical bytes to step 1.
3. Both requests hash to the same SHA-256 key, so the second requester receives the cached archive content generated for the first (different) request via `s.archiveCache.Fetch(ctx, cacheKey, ...)` at [3](#0-2) , without re-executing `git archive` for its own parameters.

func createArchiveCacheKey(gitLabProjectPath string, args []string, pathspecs []string) string {
	cacheKeyHash := sha256.New()
	cacheKeyHash.Write([]byte(gitLabProjectPath))
	cacheKeyHash.Write([]byte(strings.Join(args, ",")))
	cacheKeyHash.Write([]byte(strings.Join(pathspecs, ",")))
	return hex.EncodeToString(cacheKeyHash.Sum(nil))
}

func (c *cache) getStream(key string, create func(io.Writer) error) (_ io.ReadCloser, _ *waiter, created bool, err error) {
	c.m.Lock()
	defer c.m.Unlock()

	if e := c.index[key]; e != nil {
		if r, err := e.pipe.OpenReader(); err == nil {
			return r, e.waiter, false, nil
		}

		// In this case err != nil. That is allowed to happen, for instance if
		// the *filestore cleanup goroutine deleted the file already. But let's
		// remove the key from the cache to save the next caller the effort of
		// trying to open this entry.
		c.delete(key)
	}

	r, e, err := c.newEntry(key, create)
	if err != nil {
		return nil, nil, false, err
	}

	c.index[key] = e
	c.setIndexSize()

	return r, e.waiter, true, nil
}

// prefixLen reduces the risk of collisions due to different combinations of
// concatenated strings producing the same content.
// e.g. f+oobar and foo+bar concatenate to the same thing: foobar
func prefixLen(s string) []byte {
	return []byte(fmt.Sprintf("%08x%s", len(s), s))
}
