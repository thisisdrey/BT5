## Title
Enabling `allowHardenExchangeCalculation` re-introduces the previously deprecated bancor-style `ExchangeTransactionContract` and its spot-price arbitrage/manipulation vulnerability - (File: framework/src/main/java/org/tron/core/db/Manager.java)

## Summary
Mainline java-tron permanently disabled the on-chain bancor-relay `ExchangeTransactionContract` at fork `VERSION_4_8_0_1` because its price is a single, instantaneous bonding-curve spot price computed purely from the two token reserves in the pool, with no TWAP or other manipulation resistance — the same bug class described in GLOBAL-4 (spot price used directly for execution enabling arbitrage/manipulation). In this codebase, a new dynamic property `allowHardenExchangeCalculation` was added that, when turned on, causes `Manager.isExchangeTransaction()` to always return `false`, which silently disables both the mempool rejection of `ExchangeTransactionContract` and the block-level `rejectExchangeTransaction` check, fully re-enabling execution of the exchange contract's price-manipulable bonding-curve trade path for any ordinary transaction sender.

## Finding Description
The upstream fix for the exchange arbitrage issue is implemented as three interlocking guards in `Manager.java`:
- `pushTransaction()` rejects any `ExchangeTransactionContract` from entering the mempool: [1](#0-0) 
- `generateBlock()` skips packing any pending `ExchangeTransactionContract` into a new block: [2](#0-1) 
- `processBlock()` calls `rejectExchangeTransaction()` for every transaction in an already-produced block, throwing if the fork is past `VERSION_4_8_0_1`: [3](#0-2) 

All three guards funnel through the same predicate: [4](#0-3) 

Because `isExchangeTransaction()` short-circuits to `false` whenever `allowHardenExchangeCalculation()` is enabled, turning that flag on unconditionally reactivates `ExchangeTransactionContract` processing across all three checkpoints simultaneously — mempool admission, block packing, and block validation.

The re-enabled contract executes `ExchangeCapsule.transaction()`, which computes the trade output entirely from the current instantaneous reserves of the two-token bonding-curve pool via a bancor-style formula: [5](#0-4) , delegating the price math to `ExchangeProcessor.exchange()`: [6](#0-5)  (or the "hardened" `SafeExchangeProcessor`, which only fixes overflow/rounding, not manipulability: [7](#0-6) ).

Neither processor incorporates a time-weighted average, external reference price, per-block trade-size cap, or any other manipulation-resistance mechanism — it is exactly the "spot price used directly for execution" pattern flagged in GLOBAL-4. Any account can call `ExchangeTransactionActuator` (validated/executed via `AbstractExchangeActuator`, whose only "hardening" is overflow-checked arithmetic, not price-manipulation resistance: [8](#0-7) ) to shift the pool's reserve ratio in one transaction and then trade against the shifted price in a following transaction within the same block, or sandwich a third party's exchange transaction, extracting value with no economic disincentive.

## Impact Explanation
Once `allowHardenExchangeCalculation` is enabled, unprivileged transaction senders can freely submit `ExchangeTransactionContract` transactions again. Since the underlying price-discovery mechanism (`ExchangeCapsule.transaction`/`ExchangeProcessor`) uses only the pool's own instantaneous reserves as the price oracle, an attacker can manipulate the exchange rate within a single block (self-trade to skew reserves, then trade back, or sandwich a victim's `ExchangeTransactionContract`) to extract funds from other participants of the same exchange pool or from arbitrage against external markets — a theft-of-funds impact via unauthorized value extraction, matching exactly the class of issue upstream java-tron eliminated by permanently rejecting this contract type.

## Likelihood Explanation
The gating flag is a standard on-chain dynamic property, toggled through ordinary committee-proposal governance (the normal mechanism used for numerous other consensus parameters in java-tron) rather than any malicious/compromised-SR action. Once toggled, exploitation requires no special privilege: any address holding TRX/TRC10 balances in an `ExchangeV2Store` pool can submit ordinary signed `ExchangeTransactionContract` transactions to manipulate and arbitrage the pool, exactly as before the upstream deprecation.

## Recommendation
Do not tie the mempool/block-level exchange-transaction guard (`isExchangeTransaction`) to `allowHardenExchangeCalculation`. The overflow/precision hardening in `SafeExchangeProcessor` and `AbstractExchangeActuator` should remain independent of whether `ExchangeTransactionContract` execution is permitted at all. If reactivating the on-chain exchange feature is intended, add manipulation-resistance mechanisms (TWAP pricing, per-block trade caps, minimum trade intervals) before removing the `rejectExchangeTransaction`/`isExchangeTransaction` protections that upstream added specifically to close this class of bug.

## Proof of Concept
1. A committee proposal sets `ALLOW_HARDEN_EXCHANGE_CALCULATION = 1`, calling `DynamicPropertiesStore.saveAllowHardenExchangeCalculation(1)`.
2. `Manager.isExchangeTransaction()` now always returns `false` (per `Manager.java` lines 1809-1821), so:
   - `pushTransaction()` no longer throws `ContractValidateException("ExchangeTransactionContract is rejected")`.
   - `generateBlock()` no longer `continue`s past pending exchange transactions — they get packed into blocks.
   - `processBlock()`'s `rejectExchangeTransaction()` no longer rejects them even past fork `VERSION_4_8_0_1`.
3. An attacker with balance in both tokens of an `ExchangeV2Store` pool submits an `ExchangeTransactionContract` selling a large amount of token A to skew the pool ratio (`ExchangeCapsule.transaction`), then within the same block submits a second `ExchangeTransactionContract` (or sandwiches a victim's trade) exchanging back at the now-favorable rate, extracting value from the pool/victim — verified functionally by the existing test `hardenedSuccessExchangeTransaction` in `ExchangeTransactionActuatorTest.java`, which shows the actuator executes successfully end-to-end once hardened mode is enabled, and `isExchangeTransactionBypassedWhenHardenedEnabled` in `ManagerTest.java`, which directly confirms the guard is bypassed.

  private boolean isExchangeTransaction(Transaction transaction) {
    if (getDynamicPropertiesStore().allowHardenExchangeCalculation()) {
      return false;
    }
    Contract contract = transaction.getRawData().getContract(0);
    switch (contract.getType()) {
      case ExchangeTransactionContract: {
        return true;
      }
      default:
        return false;
    }
  }

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
