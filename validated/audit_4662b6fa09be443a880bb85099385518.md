### Title
Cross-StackerDB signature replay due to missing contract binding in `SlotMetadata` authentication digest - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` — the digest that authenticates every StackerDB chunk write — commits only to `slot_id`, `slot_version`, and `data_hash`. It never binds the signature to the specific StackerDB replica (smart contract) the chunk is destined for. Because Nakamoto signer-set StackerDBs assign the *same* `slot_id → signer address` mapping to multiple sibling contracts sharing the same reward-cycle parity (e.g. `signers-0-1` for `BlockResponse`, `signers-0-2` for `StateMachineUpdate`, `signers-0-3` for `BlockPreCommit`), a validly-signed chunk gossiped for one of these contracts can be replayed, unmodified, by any unprivileged network peer into a different sibling contract and will pass signature verification there as well — resulting in unauthorized data being accepted and stored as if it had been authored for that replica.

### Finding Description
The signed digest is computed here: [1](#0-0) 

and verification only checks this digest against the resolved signer address for the target slot: [2](#0-1) 

Neither the digest nor `verify()` incorporates the `QualifiedContractIdentifier` (`smart_contract`) of the StackerDB replica being written to. The contract is only used *externally* to look up which `StacksAddress` owns a given `slot_id` — both on write: [3](#0-2) 

and on validation of chunks pushed over the network: [4](#0-3) 

which is reachable from an unauthenticated/unsolicited network push: [5](#0-4) 

The equality the system relies on is: *"a signature that verifies for (slot_id, slot_version, data_hash) authorizes storing this chunk in the specific StackerDB replica the signer intended."* This equality is broken because the digest is contract-agnostic — it only proves the signer authorized *some* chunk at that slot/version/hash, not that they authorized it *for this particular replica*.

This is directly exploitable because Nakamoto's signer-set StackerDBs are deliberately structured so that several sibling contracts for the same reward-cycle parity share an identical `slot_id`-to-signer-address assignment, since they all delegate to the same underlying page in `.signers`: [6](#0-5) [7](#0-6) 

and the message-type contracts are enumerated via `MessageSlotID` (`BlockResponse=1`, `StateMachineUpdate=2`, `BlockPreCommit=3`), each mapping to its own contract via the same reward-cycle/page scheme: [8](#0-7) 

Since all these sibling contracts (`signers-0-1`, `signers-0-2`, `signers-0-3`, …) assign slot 0 to the same signer address for a given reward-cycle parity, a chunk validly signed by that signer for one contract (e.g., a `BlockResponse` chunk posted to `signers-0-1`) verifies successfully if replayed — with the `contract_id` field simply swapped — into a different sibling contract (e.g. `signers-0-2`, which stores `StateMachineUpdate` payloads) as long as the replayed `slot_version` is not lower than the version already stored in the target contract's slot.

### Impact Explanation
This allows any remote, unauthenticated network peer that has observed a legitimately signed StackerDB chunk (chunks are broadcast/gossiped and thus easy to observe) to inject that data into a *different* StackerDB replica without possessing the signer's private key. Consumers of these StackerDBs (the signer runloop, `StackerDBListener`, and the global state evaluator used for Nakamoto miner/signer coordination) will treat the injected data as authentically originating from that signer for that message type, e.g. feeding a replayed `BlockResponse`-typed payload's bytes into the `StateMachineUpdate` slot or vice versa. Depending on how the consumer deserializes/interprets the payload, this can corrupt or desynchronize signer state-machine coordination data used in block-signing consensus — an unauthorized write to state accepted as authentic, which maps to the Critical category ("unauthenticated/unauthorized write to state or StackerDB").

### Likelihood Explanation
Exploitation requires only: (1) observing one legitimately signed, broadcast StackerDBChunkData for any of the sibling `signers-{parity}-{message_id}` contracts (trivial, since data propagates over the p2p StackerDB gossip protocol to any connected peer), and (2) resending it — via the unsolicited `StackerDBPushChunk` P2P message with the `contract_id` field changed to a sibling contract sharing the same signer/slot assignment — to a victim node, with a `slot_version` at least as high as the target's currently stored version. No cryptographic material, admin role, or special timing is needed, making this a straightforward network-reachable replay.

### Recommendation
Bind the authentication digest to the target StackerDB replica by including the `smart_contract`/`QualifiedContractIdentifier` (and ideally the network/consensus context) in `SlotMetadata::auth_digest()`, so a signature computed for one StackerDB contract cannot be replayed into another. This mirrors the general recommendation in the referenced bitcoin-spv report of not letting an under-constrained input (there, `_outpoint` length; here, missing contract binding) allow a value computed in one context to be reinterpreted/reused in a different, unintended context.

### Proof of Concept
1. Signer `S` legitimately signs and pushes `StackerDBChunkData { slot_id: 0, slot_version: 5, sig, data: D }` to `signers-0-1` (`BlockResponse`), which is broadcast over the p2p network.
2. An attacker (any connected peer) captures this chunk from the gossip stream.
3. The attacker crafts `StackerDBPushChunkData { contract_id: signers-0-2 ("StateMachineUpdate"), rc_consensus_hash: <current>, chunk_data: StackerDBChunkData { slot_id: 0, slot_version: 5, sig, data: D } }` — identical `slot_id`/`slot_version`/`sig`/`data`, only `contract_id` changed — and sends it as an unsolicited `StackerDBPushChunk` message to a victim node.
4. On the victim, `handle_unsolicited_StackerDBPushChunk` → `validate_received_chunk` resolves the slot-0 signer for `signers-0-2` (the same address `S`, per the shared signer-slot page in `.signers`), calls `slot_metadata.verify(&addr)`, which succeeds because the digest never included the contract identifier.
5. Provided version 5 exceeds `signers-0-2`'s currently stored version for slot 0, the forged-context chunk is accepted and stored under `signers-0-2`, even though `S` never signed anything intended for that contract.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

    pub fn validate_received_chunk(
        &self,
        smart_contract_id: &QualifiedContractIdentifier,
        config: &StackerDBConfig,
        data: &StackerDBChunkData,
        expected_versions: &[u32],
    ) -> Result<bool, net_error> {
        // validate -- must not exceed this replica's configured chunk size.
        if (data.data.len() as u64) > config.chunk_size {
            info!(
                "Received StackerDBChunk for {} ID {}, which is oversized: {} bytes (max {} bytes)",
                smart_contract_id,
                data.slot_id,
                data.data.len(),
                config.chunk_size
            );
            return Ok(false);
        }

        // validate -- must be a valid chunk
        let Some(expected_version) = expected_versions.get(data.slot_id as usize) else {
            info!(
                "Received StackerDBChunk for {} ID {}, which is too big ({})",
                smart_contract_id,
                data.slot_id,
                expected_versions.len()
            );
            return Ok(false);
        };

        // validate -- must be signed by the expected author
        let addr = match self
            .stackerdbs
            .get_slot_signer(smart_contract_id, data.slot_id)?
        {
            Some(addr) => addr,
            None => {
                return Ok(false);
            }
        };

        let slot_metadata = data.get_slot_metadata();
        if !slot_metadata.verify(&addr)? {
            info!(
                "StackerDBChunk for {} ID {} is not signed by {}",
                smart_contract_id, data.slot_id, &addr
            );
            return Ok(false);
        }
