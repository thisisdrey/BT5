### Title
Airdrop claim at exact lock expiry boundary locks MET into esMET instead of transferring it freely - (File: contracts/MetAirdrop.sol)

### Summary
`MetAirdrop._transferReward` uses a strict `<` comparison when checking whether the esMET lock window has expired. At the boundary `updatedAt + lockPeriod == block.timestamp`, the lock period has already elapsed but the code still routes the claimed MET into `ESMET.lockFor`, locking the user's reward for `MINIMUM_LOCK_PERIOD + 1` instead of transferring it freely. This is the same boundary-comparison bug class as the Isomorph circuit-breaker finding (`<` should be `<=`).

### Finding Description
In `MetAirdrop._transferReward`, the expiry check is:

```solidity
// contracts/MetAirdrop.sol:31-47
uint256 _end = updatedAt + lockPeriod;

if (_end < block.timestamp) {
    MET.safeTransfer(to_, amount_);
    return;
}

uint256 _min = ESMET.MINIMUM_LOCK_PERIOD() + 1;
uint256 _max = ESMET.MAXIMUM_LOCK_PERIOD();

// Ensures valid lock period
uint256 _remainLockPeriod = Math.min(Math.max(_end - block.timestamp, _min), _max);

token.safeApprove(address(ESMET), 0);
token.safeApprove(address(ESMET), amount_);
ESMET.lockFor(to_, amount_, _remainLockPeriod);
```

When `block.timestamp == _end`, the elapsed lock time is exactly `lockPeriod`, so the reward should be unlocked. Instead, `_end < block.timestamp` is false, the free-transfer branch is skipped, `_end - block.timestamp == 0` is clamped up to `MINIMUM_LOCK_PERIOD + 1` via `Math.max`, and `ESMET.lockFor` locks the full claimed amount for a fresh minimum lock period. The intended semantic — "once `lockPeriod` has fully elapsed since `updatedAt`, the reward is liquid" — is violated at the exact boundary.

### Impact Explanation
Any user whose `claim` transaction lands in the block where `block.timestamp == updatedAt + lockPeriod` has their entire claimable MET balance locked into esMET for `MINIMUM_LOCK_PERIOD + 1` seconds rather than received as liquid MET. This is temporary freezing of user (unclaimed yield) funds: the tokens are not stolen, but the user cannot access them for the duration of the freshly imposed lock, which is not what the protocol intends at or past expiry. The misbehavior is fully permissionless to trigger — `RecurringAirdrop.claim` is a public entry point and the caller controls only timing, not parameters.

### Likelihood Explanation
The window is a single block timestamp (`block.timestamp == _end`), so the likelihood is low and largely incidental — a claim must land in exactly that block. However, on chains with 2-second block times the boundary is still reachable without any privileged action, and nothing in the code or deployment configuration prevents it. The impact on an affected claim scales with the full claimable amount, not a rounding dust quantity, because `Math.max(..., _min)` forces the entire `amount_` into a minimum-length lock.

### Recommendation
Change the strict inequality to a non-strict one so the boundary is treated as expired:

```solidity
if (_end <= block.timestamp) {
    MET.safeTransfer(to_, amount_);
    return;
}
```

Foundry-style test (place in `test/foundry/`, forking a chain where `ESMET` and `MET` addresses resolve, or mocking `IESMET`/`IERC20`):

```solidity
pragma solidity 0.8.24;

import {Test} from "forge-std/Test.sol";
import {MetAirdrop} from "contracts/MetAirdrop.sol";

contract MetAirdropBoundaryTest is Test {
    MetAirdrop airdrop;
    address alice = address(0xA11CE);

    function setUp() public {
        airdrop = new MetAirdrop();
        // governor sets a merkle root containing leaf (alice, amount)
        // and funds the contract with MET (setup elided)
    }

    function test_claimAtExactExpiryLocksInsteadOfTransferring() public {
        uint256 amount = 100e18;
        bytes32[] memory proof = _proofFor(alice, amount); // valid proof

        // Warp to the exact boundary: updatedAt + lockPeriod == block.timestamp
        uint256 end = airdrop.updatedAt() + airdrop.lockPeriod();
        vm.warp(end);

        vm.prank(alice);
        airdrop.claim(amount, proof);

        // EXPECTED (with fix): alice holds `amount` MET, zero esMET lock
        // ACTUAL (buggy): ESMET.lockFor(alice, amount, MINIMUM_LOCK_PERIOD + 1)
        //   was called; alice received no liquid MET.
        // Assert observable outcome:
        assertEq(airdrop.MET().balanceOf(alice), amount, "boundary claim must be unlocked");
    }
}
```

Concrete reproduction path: after `updateMerkleRoot` records `updatedAt`, a user submits `RecurringAirdrop.claim` so it executes in the block with `timestamp == updatedAt + lockPeriod`. The free-transfer branch is skipped and `ESMET.lockFor` is invoked with `_remainLockPeriod = MINIMUM_LOCK_PERIOD + 1`, temporarily freezing the reward.
