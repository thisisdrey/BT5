### Title
Unbounded Array-Length Field in TVM Precompile Calldata Decoders Allows Attacker-Controlled `OutOfMemoryError` DoS - (`File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts decode caller-supplied calldata using helper methods `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`. These helpers read an array-length ("count") word directly from attacker-controlled calldata and immediately allocate a Java array of that size — `new byte[len][]` — before any bound check is applied against the actual amount of data present. This mirrors the Go `archive/zip` bug class in BIT-golang-2021-39293/CVE-2021-39293, where a crafted header field falsely claiming a large file count caused an unchecked, oversized allocation/panic before validation.

### Finding Description
`extractBytes32Array` reads the length purely from the word at `offset` with no upper bound: [1](#0-0) 

`extractBytesArray` and `extractSigArray` behave the same way — `len` is taken from `words[offset].intValueSafe()` and used to size the array before the loop that would otherwise throw an index-out-of-bounds exception on a bogus offset: [2](#0-1) 

Both consuming precompiles only bound this length when the feature switch `VMConfig.allowTvmSelfdestructRestriction()` is active: [3](#0-2) [4](#0-3) 

When that switch is not enabled, `extractBytesArray`/`extractSigArray`/`extractBytes32Array` are called directly with no size cap at all. Even when the newer `isValidAbiEncoding` shape check (gated separately by `VMConfig.allowTvmOsaka()`) is active, it only validates that the *overall* calldata length is a multiple of the expected item width; it does not cross-validate that the length word actually read at the attacker-chosen `offset` matches the number of items implied by the calldata size: [5](#0-4) 

Because the `len`/count word is read from an arbitrary position inside the small, attacker-supplied calldata (the offset itself, e.g. `words[3]`, is also attacker-controlled and only needs to reference a position that exists in the parsed `words` array), a caller can supply a tiny calldata blob whose "count" word value is set to `0x7FFFFFFF`. The allocation `new byte[len][]` (an array of `len` object references) is attempted before the subsequent loop that copies actual bytes — meaning the OOM condition is triggered purely from the declared count, independent of how much real data backs it, exactly analogous to the zip `NewReader`/`OpenReader` panic caused by a falsely large file-count header.

### Impact Explanation
Any account can deploy a contract that performs a `CALL`/`STATICCALL` to the `ValidateMultiSign` (address `0x66`) or `BatchValidateSign` precompile address with crafted calldata. Because TVM execution is deterministic and re-executed by every full node/SR validating the block, a single cheaply-broadcast transaction can force every validating node to attempt a multi-gigabyte array allocation simultaneously, throwing `OutOfMemoryError` inside the JVM. Depending on GC/heap state this can crash the node process or destabilize it network-wide, producing a chain halt / node-crash DoS — satisfying the "node crash or halt" impact bar.

### Likelihood Explanation
Exploitability requires only: (1) the target network not having activated `allowTvmSelfdestructRestriction` (or, for `BatchValidateSign`/`ValidateMultiSign`, crafting an offset/count combination that reads a count word from within the bounds-checked array but that check catches only the `MAX_SIZE` bound scenario in the gated path — the ungated legacy path has no bound at all), and (2) energy cost for the call, which is computed from actual calldata length via `getEnergyForData`, not from the fabricated `len` value, so the attack is inexpensive to broadcast. This makes the bug trivially reachable by any unprivileged contract caller/deployer with minimal fee cost, on any deployment where the hardening switch is not yet enabled.

### Recommendation
- Bound the `len` value read in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` unconditionally (not only under `allowTvmSelfdestructRestriction`) to a small, fixed `MAX_SIZE` before allocating any array.
- Cross-validate that the length word matches the number of items actually derivable from the calldata size (as computed by `isValidAbiEncoding`) rather than trusting an independently-read word.
- Apply the same validation regardless of feature-switch activation state so older/non-upgraded networks are not exposed.

### Proof of Concept
1. Craft calldata for a `CALL` to precompile address `0x66` (`ValidateMultiSign`) with the standard 5-word header (`address`, `permissionId`, `data hash`, `sigArrayOffset`, padding) followed by only one additional 32-byte word.
2. Set `sigArrayOffset` (`words[3]`) to point at that trailing word's index within the parsed `words` array (a valid, in-bounds index).
3. Set the value of that trailing word to `0x7FFFFFFF` (interpreted as `intValueSafe()`), representing the fabricated signature-array length.
4. On any deployment where `VMConfig.allowTvmSelfdestructRestriction()` is not active, `extractBytesArray`/`extractSigArray` executes `new byte[0x7FFFFFFF][]`, immediately throwing `OutOfMemoryError` inside every node that processes/validates the transaction.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
