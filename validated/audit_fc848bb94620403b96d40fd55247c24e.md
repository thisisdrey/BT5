### Title
Optimistic StackerDB chunk-inventory patch advertises unstored chunk versions before storage succeeds - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` validates a pushed `StackerDBChunkPushData` and, on success, immediately patches the `slot_versions` field of the `StackerDBChunkInvData` reply it signs and sends back to the peer — *before* the chunk has actually been committed to the local StackerDB. The actual write only happens later, out-of-band, when the message is forwarded to the relayer. If that later write fails for any reason, the node has already told the peer (in a signed protocol message) that it possesses a chunk version it does not actually have.

### Finding Description
In `stackslib/src/net/stackerdb/mod.rs`: [1](#0-0) 

`validate_received_chunk` only checks size, slot existence, signature correctness, staleness against the *inventory snapshot passed in* (`data.slot_versions`, taken from `make_StackerDBChunksInv_or_Nack`), and the max-writes bound — it performs **no database write**. Immediately after this check passes, the code does:
```rust
*slot_version = chunk_data.chunk_data.slot_version;
```
mutating the outgoing `StackerDBChunkInvData` reply to claim the new version is now stored. The function's own doc-comment confirms storage is deferred: [2](#0-1) 

The signed reply is sent unconditionally right after the patch: [3](#0-2) 

Actual persistence happens separately, only if the caller forwards the message to the relayer (the `(false, true)` return value), which eventually calls `try_replace_chunk`, the function that performs the real authenticated compare-and-swap against `slot_validation.version`: [4](#0-3) 

Because two independent connections/event IDs can concurrently receive pushes for the *same* slot (e.g., the same chunk gossiped via multiple neighbors, or a signer re-publishing in quick succession), both `handle_unsolicited_StackerDBPushChunk` invocations read the same pre-write inventory, both pass `validate_received_chunk`, and **both** sign and send replies claiming the new version — yet at the actual-storage step only one `try_replace_chunk` call can succeed; the other fails with `net_error::StaleChunk` (or any other DB error) and is silently dropped, as seen in the analogous sync-side handling in `relay.rs`: [5](#0-4) 

The result is a node that has told at least one peer, in a signed p2p reply, that it now stores a specific chunk version, while its actual on-disk `slot_validation.version` for that slot remains at the old value. This breaks the "served vs. stored" invariant the sync protocol depends on (`StackerDBChunkInvData` is meant to be the ground truth of what a replica has, per the sync algorithm's design doc): [6](#0-5) 

### Impact Explanation
Peers that receive this optimistic inventory reply will believe the local node already has the newest chunk version and will deprioritize or skip requesting it from this node, while a subsequent `GetChunk` request to this node for that version returns stale data (or a mismatch), stalling replication of that StackerDB slot until another write eventually corrects the local version. Because StackerDB is used for signer message dissemination and other real-time coordination data, this is a High-severity "serving non-canonical state as canonical" / false-inventory issue reachable by any remote, unauthenticated peer capable of sending ordinary `StackerDBPushChunk` messages — no signing key, admin role, or privileged access is required to trigger the race (the attacker just needs to cause/observe two concurrent pushes of the same valid, properly-signed chunk to the same slot).

### Likelihood Explanation
Triggering the race does not require unusual timing precision from an attacker with two open connections to the same node: simply pushing the same (or a rapid update to the same) valid `StackerDBChunkData` slot over two simultaneous connections, or relying on natural network duplication/gossip re-delivery, is enough to create the two concurrent `handle_unsolicited_StackerDBPushChunk` calls needed. Because each call independently derives its own copy of `slot_versions` from a fresh DB read at request time and the storage step is deferred and asynchronous relative to the reply, the window for the mismatch is not merely theoretical.

### Recommendation
Do not patch and sign the `StackerDBChunkInvData` reply based on validation alone. Either (a) defer sending the chunk-accept reply until the storage of the chunk is confirmed successful, or (b) send only a provisional acknowledgment, and repair the inventory (re-derive `slot_versions` from the DB) after the relayer processes the chunk, rather than trusting the pre-write patched value.

### Proof of Concept
1. Establish two separate p2p connections (`event_id_1`, `event_id_2`) to a target node for the same StackerDB contract/slot.
2. Craft a validly signed `StackerDBPushChunkData` for slot `S`, version `V` (current stored version `< V`).
3. Send this message (or two chunks both valid at version `V`, e.g. duplicate delivery via gossip) nearly simultaneously over both connections.
4. Both invocations of `handle_unsolicited_StackerDBPushChunk` read the same on-disk version (`< V`), pass `validate_received_chunk`, patch their respective outgoing `StackerDBChunkInvData.slot_versions[S] = V`, and sign+send replies claiming version `V` back to each peer.
5. Both messages are forwarded to the relayer; only the first `try_replace_chunk` call actually persists version `V`. The second raises `NetError::StaleChunk` and is dropped.
6. Regardless of which peer received the "losing" reply, the *responding node's own local storage* is at version `V` only via one write — but if instead the *storage attempt itself fails outright* (e.g., DB transaction error, disk failure, or the second push arriving with a bad signature after re-validation timing skew), the reply already sent claims version `V` while the local slot never advances past its prior version, leaving the advertised inventory permanently out of sync with actual storage until the next legitimate write to that slot.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
