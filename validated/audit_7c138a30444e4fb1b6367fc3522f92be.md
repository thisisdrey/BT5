### Title
Unbounded growth of `DelegatedResourceAccountIndex.toAccounts`/`fromAccounts` via repeated legacy `FreezeBalanceContract` delegations causes DoS of index queries and reward/index maintenance - ([File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java])

### Summary
The legacy (non-optimized) resource-delegation path in `FreezeBalanceActuator.delegateResource()` appends a new entry to `DelegatedResourceAccountIndexCapsule.toAccounts`/`fromAccounts` every time an account delegates BANDWIDTH/ENERGY to a *new* receiver address, with no upper bound on the list size. Any account holder can call `FreezeBalanceContract` (with `receiverAddress` set) repeatedly, using minimal frozen TRX amounts (e.g. 1 TRX per call) and a fresh receiver address each time, growing their own `DelegatedResourceAccountIndex.toAccounts` (and the corresponding `fromAccounts` on each victim receiver) without limit. This directly parallels the reported `LockingPositionService.lockExtensions` bug class: an actor-controlled, monotonically growing list attached to an account/asset that other code paths must fully load and iterate/serialize.

### Finding Description
In `FreezeBalanceActuator.delegateResource()` [1](#0-0) , when `!dynamicPropertiesStore.supportAllowDelegateOptimization()`, the code fetches (or creates) a `DelegatedResourceAccountIndexCapsule` for both the owner and receiver and unconditionally calls `addToAccount`/`addFromAccount` for any receiver not already present in the list:

```
List<ByteString> toAccountsList = ownerIndexCapsule.getToAccountsList();
if (!toAccountsList.contains(ByteString.copyFrom(receiverAddress))) {
  ownerIndexCapsule.addToAccount(ByteString.copyFrom(receiverAddress));
}
```

There is no cap on the number of distinct receiver/owner addresses that can be added to `toAccounts`/`fromAccounts`. `FreezeBalanceContract` only requires `frozenBalance >= 1 TRX` [2](#0-1) , so a single account can broadcast many low-cost transactions, each delegating 1 TRX to a distinct newly generated receiver address, appending one entry per transaction to its own `toAccounts` list and one entry to each victim receiver's `fromAccounts` list. A test in the repo (`testMultiFreezeDelegatedBalanceForBandwidth`) already demonstrates 100 sequential delegations growing the index list linearly with no validation rejecting it [3](#0-2) .

This capsule is fully deserialized and returned by `Wallet.getDelegatedResourceAccountIndex()` [4](#0-3) , which is directly reachable from unauthenticated HTTP/gRPC query endpoints: `GetDelegatedResourceAccountIndexServlet` [5](#0-4)  and the gRPC `GetDelegatedResourceAccountIndex` RPC [6](#0-5) . Because the entire list is loaded into a single protobuf message and serialized/printed on every query, an attacker-inflated list forces the node to do unbounded work (memory allocation, JSON/String serialization via `JsonFormat.printToString`) on every read of that address's index — for any client querying it, not just the attacker.

The same growth also occurs transitively during `unDelegateResource`/legacy `UnfreezeBalanceActuator`, which must load, search (`contains`), and rewrite these lists on every unfreeze operation [7](#0-6) , meaning normal state-changing transactions on the victim's account become progressively more expensive as the attacker keeps inflating the list, mirroring the original report's DoS mechanic where a poisoned array degrades an otherwise-legitimate counterparty's transaction.

### Impact Explanation
While this doesn't directly cause fund loss (the receiver's balances/weights update correctly per resource key, not per index entry), it does create:
- A queryable, unauthenticated API (`GetDelegatedResourceAccountIndex`/V2, both HTTP and gRPC) whose response size and processing time an attacker fully controls and can grow unbounded for their own address or for any address they choose to send even a 1 TRX delegation to (poisoning victims who never opted in).
- Degraded/blocked read availability for that API path for legitimate callers (explorers, wallets) once the list is large enough, satisfying the "API the node can no longer serve" criterion.
- Increased processing cost embedded in the owner's/receiver's account state that subsequent `FreezeBalanceContract`/`UnfreezeBalanceContract` transactions must pay (linear `contains()` scan and rewrite of the whole list), which can push affected transactions toward resource/time limits, though this is bounded by the same actor's own transaction fee/bandwidth cost unless directed at an innocent third-party receiver.

### Likelihood Explanation
Reaching this requires only unprivileged, low-value `FreezeBalanceContract` transactions with a `receiverAddress` set to a fresh keypair for each call — no special privileges, and cheap (1 TRX minimum + standard fee) per entry. This path exists only when `!dynamicPropertiesStore.supportAllowDelegateOptimization()`; if the delegate-optimization dynamic parameter is enabled on the live chain, the optimized path (`convert`/`delegate`) is used instead, which stores individual keyed entries rather than growing a single list, and would not exhibit this bug. Confirming whether `AllowDelegateOptimization` is enabled on current mainnet was not possible from the available code/index; this materially affects likelihood and should be verified before treating this as currently exploitable in production.

### Recommendation
- Enforce a maximum size (e.g. a `MAX_DELEGATE_INDEX_SIZE` dynamic parameter, analogous to `MAX_FROZEN_SUPPLY_NUMBER`/`MAX_VOTE_NUMBER`) on `DelegatedResourceAccountIndexCapsule.toAccounts`/`fromAccounts` in the legacy path, rejecting further `addToAccount`/`addFromAccount` once the cap is reached.
- Prefer routing all resource delegation through the already-existing optimized key-per-pair scheme (`supportAllowDelegateOptimization`) and consider deprecating/hard-capping the legacy list-based index entirely.
- Add pagination to `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` so that response construction and serialization cost is bounded regardless of stored list size.

### Proof of Concept
1. Ensure `supportAllowDelegateOptimization()` is false (or find a network snapshot before that feature was enabled).
2. From an attacker account with sufficient TRX for many 1 TRX freezes + fees, generate N fresh receiver keypairs.
3. For each receiver, broadcast a `FreezeBalanceContract` with `frozen_balance = 1_000_000` (1 TRX) and `receiver_address` = the fresh address, resource = BANDWIDTH or ENERGY.
4. Each transaction appends one entry to the attacker's `DelegatedResourceAccountIndex.toAccounts` and one entry to the corresponding receiver's `fromAccounts` (per `FreezeBalanceActuator.delegateResource`, lines 319-345, cited above).
5. Repeat for a large N (e.g., tens of thousands); query `GetDelegatedResourceAccountIndex` for the attacker's address via HTTP or gRPC and observe growing response size/latency, demonstrating unbounded resource consumption on a public read API.

  public void removeFromAccount(ByteString fromAccount) {
    if (getFromAccountsList().contains(fromAccount)) {
      List<ByteString> fromList = new ArrayList<>(getFromAccountsList());
      fromList.remove(fromAccount);
      setAllFromAccounts(fromList);
    }
  }

  public List<ByteString> getToAccountsList() {
    return this.delegatedResourceAccountIndex.getToAccountsList();
  }

  public void setAllToAccounts(List<ByteString> toAccounts) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .clearToAccounts()
        .addAllToAccounts(toAccounts)
        .build();
  }

  public void addToAccount(ByteString toAccount) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .addToAccounts(toAccount)
        .build();
  }

  public void removeToAccount(ByteString toAccount) {
    if (getToAccountsList().contains(toAccount)) {
      List<ByteString> toList = new ArrayList<>(getToAccountsList());
      toList.remove(toAccount);
      setAllToAccounts(toList);
    }
  }
