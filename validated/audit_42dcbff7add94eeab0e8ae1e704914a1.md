### Title
Postponed receipts and pending-data-count links for a deleted account are not cleared, allowing an attacker's scheduled callback (e.g. `AddKey`) to execute against a same-named account recreated later - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (`core/store/src/utils/mod.rs:504-575`) deletes the `Account`, `ContractCode`, access keys, gas-key nonces, and `ContractData` entries, but never removes `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, or `TrieKey::PendingDataCount` entries associated with that `account_id`. If a self-targeted action receipt (e.g. containing an `AddKey`) was postponed while waiting on unmet `input_data_ids` (created via `promise_and`) and the account is then deleted via `DeleteAccountAction`, the postponed receipt and its pending-data links survive in state, keyed only by the plain `account_id` string. If a *different* actor later creates a brand-new account with the exact same name and the two pending data dependencies are eventually satisfied, `process_receipt`'s data-arrival path (`runtime/runtime/src/lib.rs:1367-1455`) fetches and executes the stale postponed receipt — including its `AddKey` action — against the newly created account.

### Finding Description
- `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` and then sets `*account = None`, but has no check for outstanding postponed receipts tied to the account it is deleting.
- `remove_account` (`core/store/src/utils/mod.rs:504-575`) only clears `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData`. It does not iterate or clear `PostponedReceipt`, `PostponedReceiptId`, or `PendingDataCount` trie entries for the account.
- `process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) is what created these entries in the first place: when a receiver's action receipt (here, the attacker's self-callback with `AddKey`, produced via `.then()` on a `promise_and` of two dependency promises) has unmet `input_data_ids`, it stores `PendingDataCount` and calls `set_postponed_receipt`, keyed purely by `(receiver_id, receipt_id)` where `receiver_id` is the account-id string "a.near" — not any unique account instance/generation identifier.
- When the two dependency `Data` receipts eventually arrive, `process_receipt`'s `VersionedReceiptEnum::Data` branch (`runtime/runtime/src/lib.rs:1367-1455`) decrements `PendingDataCount`; when it hits zero it fetches the postponed receipt via `get_postponed_receipt(state_update, account_id, receipt_id)` and executes it via `apply_action_receipt` — purely by account-id string lookup, with no verification that the account existing now is the same account that originally scheduled the receipt.
- Action-level guards do not catch this: `check_account_existence` (`runtime/runtime/src/actions.rs:787-855`) only checks that *some* account currently exists at `account_id` for `AddKey`; `check_actor_permissions` (`runtime/runtime/src/actions.rs:739-785`) only checks `actor_id == account_id`. Since the postponed receipt's predecessor/receiver is the same literal string ("a.near"), and the actor_id assigned for a self-receipt is that same string, both checks pass trivially against the newly recreated account.
- Net effect: an attacker can plant a time-delayed `AddKey` (or other authorization-changing action) that fires on whoever recreates the same short account name later, without that new owner's authorization.

### Impact Explanation
This is an authorization escalation / account-takeover primitive: a completely unrelated party's brand-new "a.near" account can end up with an access key (or other administrative action) installed by a former, unrelated account holder, without ever having authorized it. This falls under the NEAR bounty category of authorization escalation across accounts, matching the accepted finding this test is meant to reproduce end-to-end.

### Likelihood Explanation
- Preconditions: attacker needs to (1) fund and control a short account name likely to be desirable/recreated, (2) deploy a trivial contract, (3) schedule a self-callback gated by two unresolved dependencies before deleting the account, (4) wait for someone else to recreate the exact same account name and for the dependencies to later resolve.
- Cost to attacker is minimal: normal transaction/gas fees plus funding the throwaway account; no privileged access, validator, or node control needed — purely client-side transactions to a public RPC endpoint, consistent with the "ordinary client" threat model.
- Feasibility/repeatability: fully deterministic given control over when the two dependency receipts are satisfied (attacker can hold one of the two dependencies open indefinitely, e.g., a yet-unresolved cross-contract call to itself, then trigger it only after observing the account recreated). Reproducible in a test-loop deterministically since the attacker also controls the timing of dependency satisfaction.

### Recommendation
When an account is deleted, `remove_account` (or `action_delete_account`) should also purge any state entries under that `account_id` related to receipt postponement: iterate and remove all `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, and `TrieKey::PendingDataCount` entries for that account (as the existing "removing access keys"/"removing contract data" loops already do for other prefixed key kinds), so no callback scheduled before deletion can execute after account recreation. Alternatively, tag postponed receipts/pending-data links with an account "generation"/nonce that changes on `CreateAccount`, and validate that generation matches at data-arrival time before executing.

### Proof of Concept
Test-loop integration test outline (`test-loop-tests`):
1. Fund attacker account `attacker.near` and create short account `a.near` (attacker-controlled key) with `TestLoopBuilder`/`tx_create_account` helpers as in `test-loop-tests/src/utils/node.rs:326-359`.
2. Deploy `near_test_contracts::rs_contract()` (or a minimal custom contract) to `a.near`. On an "init" call, have the contract build a batch promise on `env::current_account_id()` (`a.near`) with a `FunctionCall` action, `.then()`-chained, whose action list is `[AddKey(attacker_public_key, FullAccess)]`, and make the callback's execution conditional on `promise_and` of two independent promises (e.g., two cross-contract calls to helper accounts that don't resolve immediately) — mirroring the `test_create_account_add_key_call_delete_key_delete_account`-style `call_promise` batch construction (`runtime/runtime/tests/test_async_calls.rs:911-996`), but leaving the two dependency promises unresolved when the top-level call returns.
3. Submit a signed `DeleteAccount` transaction from `a.near` to itself with `beneficiary_id = attacker.near` (using `tx_delete_account`-style helper, `test-loop-tests/src/utils/node.rs:344-358`), and advance the test loop N blocks, confirming via `env.rpc_node()` that `a.near` no longer exists (`QueryError::UnknownAccount`) while the postponed receipt for the `AddKey` callback remains in state (can be checked via `state-viewer`'s `PostponedReceipt`/`PendingDataCount` record types, `tools/state-viewer/src/cli.rs:942-983`).
4. Have a separate, unrelated signer (`victim.near`) submit a `CreateAccount` + `Transfer` transaction re-creating `a.near` with a victim-controlled key, and confirm success.
5. Trigger the two outstanding dependency promises so both underlying `Data` receipts are delivered to `a.near`'s pending postponed receipt, causing `PendingDataCount` to reach zero and the runtime to execute the stale `AddKey` action.
6. Assert: `env.rpc_node().view_access_keys(&"a.near")` (or equivalent query) contains **only** the victim's key that `victim.near` actually authorized in step 4, and does **not** contain the attacker's public key or any attacker-authorized action. If the attacker's key is present, this is a confirmed authorization-escalation exploit demonstrating that `remove_account` fails to purge postponed-receipt state on deletion.
