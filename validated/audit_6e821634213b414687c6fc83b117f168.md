## Analog Vulnerability Confirmed

### Title
Missing slippage protection in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` enables sandwich-attack fund loss during Bancor-style TRC10 exchange liquidity operations - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
Java-tron's Bancor-curve TRC10 exchange (`ExchangeCreateContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`, `ExchangeTransactionContract`) computes the counter-asset amount for liquidity inject/withdraw purely from the exchange pool's *current* on-chain balances at execution time, with no user-supplied minimum/maximum bound. `ExchangeTransactionActuator` (the trade/swap path) deliberately includes an `expected` field that is checked against the computed output [1](#0-0) , but the liquidity `Inject` and `Withdraw` paths have no equivalent protection at all.

### Finding Description
`ExchangeInjectActuator.execute`/`doValidate` and `ExchangeWithdrawActuator.execute`/`doValidate` compute the counter-token amount as a simple ratio of the pool's `firstTokenBalance`/`secondTokenBalance` read at execution time: [2](#0-1) 

Unlike `ExchangeTransactionContract`, which carries an `expected` (minimum received) field enforced in `doValidate` [1](#0-0) , the `ExchangeInjectContract` and `ExchangeWithdrawContract` protobuf messages carry only `owner_address`, `exchange_id`, `token_id`, and `quant` — no expected/limit field exists at all [3](#0-2) . The only sanity checks present are a "not precise enough" rounding check and a positive-amount check [4](#0-3)  — neither of which bounds the counter-token amount relative to a fair/expected price.

This mirrors the root cause of the HydraDX report: a liquidity-affecting operation (there, `remove_liquidity`/`add_liquidity`; here, `ExchangeInject`/`ExchangeWithdraw`) is executed against a pool price that can be freely manipulated immediately beforehand by an unprivileged actor, and the operation itself provides the victim no mechanism to reject an unfavorable execution price. In java-tron, `ExchangeTransactionContract` is fully permissionless and callable by any account to swap against the same pool, so an attacker can:
1. Submit a large `ExchangeTransactionContract` swap that skews `firstTokenBalance`/`secondTokenBalance` in the pool just before the victim's `ExchangeWithdrawContract` (or `ExchangeInjectContract`) is packed into the same block (transaction ordering within a block is determined by the packing node, and a user can also broadcast in rapid succession to attempt to precede the victim tx).
2. The victim's withdraw/inject executes at the skewed ratio, receiving/depositing counter-token amounts far from fair value, with no `expected`-style guard to abort.
3. The attacker reverses the swap afterward, extracting the difference (classic sandwich).

### Impact Explanation
The exchange creator (any account that created a Bancor-style exchange via `ExchangeCreateContract`) can lose a significant portion of the value of their injected/withdrawn liquidity to a sandwiching attacker, with no way to bound the loss on-chain — directly analogous to the "no slippage parameter... transaction will not revert" root cause described in the report. This is a concrete loss-of-funds vector reachable by any unprivileged transaction broadcaster.

### Likelihood Explanation
`ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` are all ordinary, permissionless actuators requiring only a signed transaction from any account (subject to being the exchange creator for inject/withdraw, which is a normal, non-privileged status obtained simply by creating an exchange). No committee/witness/administrative action is required to trigger the sandwich; only ordinary swap transactions against the target pool are needed.

### Recommendation
Add an `expected`/limit-style field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`) allowing the caller to specify an acceptable minimum/maximum counter-token amount, and enforce it in `ExchangeInjectActuator.doValidate`/`ExchangeWithdrawActuator.doValidate` before executing the transfer, rejecting the transaction if the computed `anotherTokenQuant` falls outside the caller-specified bound.

### Proof of Concept
1. Attacker observes a pending `ExchangeWithdrawContract` (or `ExchangeInjectContract`) from the pool creator for exchange `X`.
2. Attacker broadcasts an `ExchangeTransactionContract` swap of a large `tokenQuant` against exchange `X`, shifting `firstTokenBalance`/`secondTokenBalance` far from the pre-manipulation ratio — this is fully permitted since `ExchangeTransactionActuator` only requires balance sufficiency and `expected` set by the attacker themself [1](#0-0) .
3. In the same or immediately following block, the victim's `ExchangeWithdrawContract` executes, computing `anotherTokenQuant` from the now-skewed balances [5](#0-4)  with no minimum-output check to reject the unfavorable result.
4. Attacker submits a reverse `ExchangeTransactionContract` to restore the pool ratio and capture the extracted value.
