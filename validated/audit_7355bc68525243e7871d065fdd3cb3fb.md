### Title
Intra-batch write-lock conflicts bypass `AccountLocks::try_lock_transaction_batch`, allowing two conflicting write locks to be granted simultaneously - ([File: accounts-db/src/account_locks.rs])

### Summary
`AccountLocks::try_lock_transaction_batch` performs its conflict check (`can_lock_accounts`) for every transaction in the batch **before** applying any of the resulting locks (`lock_accounts`). Because the check pass never mutates `self`, two transactions in the *same* batch that both write to the same previously-unlocked `Pubkey` will both pass the check, and both will subsequently be granted a write lock in the mutate pass, defeating the mutual-exclusion invariant the lock system exists to enforce.

### Finding Description
`try_lock_transaction_batch` is implemented as two separate passes over `validated_batch_keys`: [1](#0-0) 

Pass 1 (lines 28-34) calls `self.can_lock_accounts(keys.clone())` — an immutable `&self` read (lines 56-71) — for every transaction in the batch, in order, but crucially the lock state `self.write_locks` / `self.readonly_locks` is **not updated** between iterations of this loop.

Pass 2 (lines 36-39) then maps every transaction that was `Ok` after pass 1 through `self.lock_accounts(keys)` (lines 73-81), which mutates the lock maps by incrementing the write/read counters for each key (`lock_write`/`lock_readonly`, lines 103-109).

Because pass 1 evaluates every transaction against the *pre-batch* lock state rather than incrementally against sibling transactions already validated in the same batch, two (or more) transactions within a single batch that write to the same account key — which was not write/read locked before the batch began — will both see `can_write_lock(key) == true` and both be marked `Ok`. Pass 2 then locks that key twice, incrementing `write_locks[key]` to 2. The batch-level API reports both transactions as successfully and exclusively locked for writing the same account, even though `can_write_lock`'s invariant ("no key is write-locked more than once, and never concurrently with a read lock") is meant to prevent exactly this.

This does not require duplicate keys within a single transaction (which is already blocked by `has_duplicates`/`validate_account_locks`, lines 143-182); it only requires two *distinct* sanitized transactions in the same lock batch that share a writable account key, which is entirely legal at the transaction level and trivially producible by an attacker submitting ordinary transactions that write to the same account (e.g., two transfers debiting/crediting the same account) into the leader's transaction ingestion pipeline.

### Impact Explanation
Successful exploitation causes the account-lock subsystem — the mechanism relied upon throughout Agave to guarantee no two conflicting transactions execute concurrently within a batch/entry — to report two write-conflicting transactions as both locked. Any caller that trusts the `Ok`/`Err` result of `try_lock_transaction_batch` to build a serialized/parallel-safe scheduling batch would allow the two conflicting transactions to be scheduled or executed together, since the lock manager falsely certifies non-overlap. This maps to the "invalid recorded block / state mismatch from concurrent conflicting execution" category, matching the scoped impact described in the question.

### Likelihood Explanation
This requires no privileged access: an unstaked client only needs to submit two ordinary, individually valid transactions (no duplicate keys within either transaction, so `validate_account_locks` does not reject them) that share a writable account key, such that both end up passed into the same call to `try_lock_transaction_batch` while that key is not already locked. This is a straightforward, deterministic, and 100%-repeatable code-level defect (not probabilistic), reproducible directly against the `AccountLocks` struct in a unit test without any network or timing dependency.

### Recommendation
Merge the check-and-lock passes so that the check for each transaction in the batch is evaluated against the lock state as it exists **after** applying the locks of all previously-processed transactions in the same batch, e.g., by checking-and-locking each transaction's keys in a single pass (rolling back locks acquired so far for that transaction if a conflict is hit partway through), instead of splitting `can_lock_accounts` (read-only, pre-batch state) and `lock_accounts` (mutate) into two independent loops over the whole batch.

### Proof of Concept
```rust
// accounts-db/src/account_locks.rs (test module)
#[test]
fn test_try_lock_transaction_batch_intra_batch_write_conflict() {
    let mut locks = AccountLocks::default();
    let key = Pubkey::new_unique();

    // Two distinct "transactions" both writing the SAME key.
    let tx1_keys: Vec<(&Pubkey, bool)> = vec![(&key, true)];
    let tx2_keys: Vec<(&Pubkey, bool)> = vec![(&key, true)];

    let batch: Vec<TransactionResult<_>> = vec![
        Ok(tx1_keys.into_iter()),
        Ok(tx2_keys.into_iter()),
    ];

    let results = locks.try_lock_transaction_batch(batch);

    // BUG: both transactions are reported as successfully locked,
    // even though they both hold a write lock on the same key.
    assert!(results[0].is_ok());
    assert!(results[1].is_ok()); // should be Err(AccountInUse) but passes

    // Demonstrates the invariant violation directly:
    // write lock count for `key` is 2, i.e. two concurrent
    // exclusive write locks are held simultaneously.
    assert!(locks.is_locked_write(&key));
    // (Add a pub(crate) accessor or use dev-context-only-utils
    // qualifiers to inspect write_locks[key] == 2 directly.)
}
```
Expected (correct) behavior: the second transaction should receive `Err(TransactionError::AccountInUse)` because the first transaction in the same batch already claims a write lock on `key`. The current implementation instead returns `Ok(())` for both, proving the bypass.

```rust
    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }
```
