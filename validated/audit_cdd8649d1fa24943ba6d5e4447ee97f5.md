The reported VTVL bug class — internal ledger accounting drifting from actual custodied token balance for non-standard ERC20/NEP-141 tokens — has a genuine analog in this codebase's NEP-141 deposit path.

### Title
Fungible-token deposits are credited by the `ft_on_transfer` amount argument with no verification against actual custodied balance, allowing non-standard tokens to desynchronize internal ledger from real holdings and permanently lock withdrawals - (File: `contracts/defuse/src/contract/tokens/nep141/deposit.rs`)

### Summary
`Contract::ft_on_transfer` credits the depositor's internal multi-token balance using the `amount` value supplied in the `ft_transfer_call` callback arguments, never checking that the contract's real NEP-141 `balanceOf` increased by the same amount. For any token whose transfer semantics can deliver less (or more, in different combinations) than the nominal `amount` — fee-on-transfer tokens, deflationary/rebasing-down tokens, or a malicious/non-compliant token contract — the sum of internally credited balances (`total_supplies` for that `TokenId`) can exceed the token actually held by the Defuse contract.

### Finding Description [1](#0-0) 
`ft_on_transfer` takes the `amount: U128` parameter — a value declared by the calling token contract as part of the `ft_transfer_call` payload — and passes it straight into `self.deposit(receiver_id, [(token_id, amount.0)], ...)`, minting that exact amount of internal accounting balance for the token. There is no `balanceOf(current_account_id)` diff check before vs. after the transfer, unlike the balance-diff pattern recommended for handling non-compliant tokens.

The corresponding withdrawal path debits the same internal ledger and then issues an outbound `ft_transfer` for the full internal amount: [2](#0-1) [3](#0-2) 

The binding that should hold is: `total_supplies[token_id]` (sum of all users' internally credited balances) `== balanceOf(defuse_contract, token_id)` (actual custody). Because deposit crediting trusts the caller-declared `amount` rather than a measured balance delta, this equality can be broken the moment a token's real transfer semantics diverge from the declared `amount` (fee-on-transfer skimming, rebase-down between call and settlement, or a malicious FT contract that calls `ft_on_transfer` with an inflated `amount` while transferring less or nothing).

### Impact Explanation
Once `total_supplies[token_id] > balanceOf(defuse_contract, token_id)`, the contract is insolvent for that token: whichever user withdraws last (or attempts to withdraw an amount that exceeds the remaining real balance) has their `ft_withdraw`/`FtWithdraw` intent fail because the outbound `ft_transfer` in the token contract will revert for insufficient balance, and there is no fallback path to recover the shortfall — the contract's own accounting says the funds exist, but they don't. This satisfies the "funds permanently frozen" Critical impact category: legitimate token holders per the internal ledger cannot fully redeem their claimed balances, and earlier withdrawers effectively drain real liquidity from later ones.

### Likelihood Explanation
This requires an attacker (or protocol operator) to onboard a non-standard NEP-141 token — e.g. a token whose `ft_transfer_call`/`ft_on_transfer` declared `amount` doesn't match what actually lands in the Defuse contract's balance (fee-on-transfer, deflationary, or intentionally malicious token contracts). Given Defuse is a generic multi-token intents settlement layer intended to custody arbitrary NEP-141 tokens (evidenced by the fully generic `Nep141TokenId`/`TokenId` machinery with no token allowlist visible in the deposit path), any token not behaving as a strict 1:1 transferer can trigger this. This mirrors the VTVL finding's judged Medium/analogous-Critical-here severity: the exploit requires a specific token type but no privileged role, DAO action, or off-chain compromise.

### Recommendation
Verify actual balance delta on deposit instead of trusting the `amount` argument: record `balanceOf(current_account_id)` before invoking any external call is impossible within `ft_on_transfer` itself (the transfer already happened by the time the callback runs), so instead compare the contract's token balance immediately inside `ft_on_transfer` against a previously cached/expected total, or maintain a strict per-token invariant check (`total_supplies[token_id] <= actual_balance`) that is enforced via a periodic reconciliation, and/or restrict which NEP-141 contracts can be deposited to only those on the PoA factory / an explicit safe-list known to be full-amount compliant, similar to `contracts/poa/factory` deployments. At minimum, document and enforce that only standards-compliant, non-fee, non-rebasing NEP-141 tokens are accepted, since the current deposit crediting logic silently trusts caller-declared amounts.

### Proof of Concept
1. Deploy a NEP-141 token `evilft` whose `ft_transfer_call` implementation deducts a 10% fee from the receiving contract's actual balance increase, but still invokes `ft_on_transfer(sender_id, amount, msg)` on Defuse with the full pre-fee `amount`.
2. User calls `evilft.ft_transfer_call(defuse, amount=1000, msg="")`. Defuse's real balance of `evilft` only increases by 900, but `ft_on_transfer` in `contracts/defuse/src/contract/tokens/nep141/deposit.rs` calls `self.deposit(receiver_id, [(token_id, 1000)], ...)`, crediting the user 1000 internally.
3. `total_supplies[evilft]` is now 1000 while `evilft.ft_balance_of(defuse)` is 900.
4. User calls `ft_withdraw` for 1000 (matching internal balance). `internal_ft_withdraw` decrements the internal ledger to 0 and issues `ext_ft_core::ft_transfer(receiver_id, 1000)` — [4](#0-3)  — which reverts on the token side because Defuse only holds 900, permanently locking 100 units of value and leaving the withdrawal in a failed/refund state that cannot fully settle the credited claim.

    fn ft_on_transfer(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        msg: String,
    ) -> PromiseOrValue<U128> {
        require!(amount.0 > 0, "zero amount");

        let token_id = TokenId::Nep141(Nep141TokenId::new(env::predecessor_account_id()));

        let DepositMessage {
            receiver_id,
            action,
        } = if msg.is_empty() {
            DepositMessage::new(sender_id.clone())
        } else {
            msg.parse().unwrap_or_else(|e| panic!("{e}"))
        };

        self.deposit(
            receiver_id.clone(),
            [(token_id.clone(), amount.0)],
            Some("deposit"),
        )
        .unwrap_or_else(|err| err.panic());

            .get_mut_maybe_forced(force)
            .ok_or_else(|| DefuseError::AccountLocked(owner_id.to_owned()))?;

        let mut burn_event = MtBurnEvent {
            owner_id: Cow::Owned(owner_id.to_owned()),
            authorized_id: None,
            token_ids: Vec::new().into(),
            amounts: Vec::new().into(),
            memo: memo.map(Into::into).map(Into::into),
        };

        for (token_id, amount) in token_amounts {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);

            burn_event.token_ids.to_mut().push(token_id.to_string());
            burn_event.amounts.to_mut().push(amount);

                .token_balances
                .sub(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;

            self.storage
                .state
                .total_supplies
                .sub(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
