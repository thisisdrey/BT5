### Title
Unauthenticated handshake flooding causes DoS due to missing anti-DoS cookie mechanism - (File: handshake_manager.go, handshake/machine.go, handshake/handshake.proto)

### Summary
Nebula's handshake path performs a full Noise `ReadMessage` (DH + AEAD decrypt of the certificate payload) for every inbound stage-1 packet before any certificate/CA validation occurs, and the protocol's own anti-DoS mitigation (a `Cookie` field) was never implemented. This is directly analogous to the reported PSM rate-limit exhaustion bug: a shared, limited resource (here, CPU/crypto cycles and pending-handshake state) can be exhausted by an unauthenticated party, denying service to legitimate peers — except here there isn't even the mitigating time-window reset that the original report discusses.

### Finding Description
`HandshakeManager.HandleIncoming` accepts any UDP packet claiming to be a stage-1 handshake (`h.MessageCounter == 1`, `h.RemoteIndex == 0`) from any source that passes only an IP-based `remote_allow_list` check — no certificate or CA trust is required at this point: [1](#0-0) 

For each such packet, `beginHandshake` builds a brand-new `handshake.Machine` and calls `machine.ProcessPacket`, which performs `noise.HandshakeState.ReadMessage` (asymmetric Diffie-Hellman + AEAD decrypt) and payload processing *before* the peer certificate is ever checked against the CA pool: [2](#0-1) [3](#0-2) 

Certificate validation (`CertVerifier`) is only invoked as part of `processPayload`, i.e., after the expensive Noise DH/decrypt operations have already been executed: [4](#0-3) 

The protocol explicitly documents that an anti-DoS mitigation for this exact scenario was designed but never built: [5](#0-4) 

This mirrors the reported bug class (a rate/resource-limiting control meant to bound abuse is either absent or ineffective, letting one attacker exhaust a shared resource and block legitimate users). WireGuard-style protocols mitigate exactly this with a lightweight MAC1/cookie check that is validated *before* any DH is performed; Nebula has no equivalent enforcement despite reserving a field for it.

### Impact Explanation
An attacker with no CA-signed certificate and no established tunnel can send a flood of forged stage-1 handshake packets (valid header, arbitrary/garbage or replayed Noise message bytes) to a Nebula node's UDP listener. Each such packet forces the responder to allocate a `handshake.Machine`, run Noise's asymmetric cryptographic handshake step, and only then discover the peer certificate is untrusted. Because the responder is a single-threaded packet loop reading from the socket, sustained flooding directly translates into CPU exhaustion and inbound packet processing latency, denying handshake service to legitimate peers — a remote, unauthenticated DoS condition, matching the "impact" bar of remote crash/state poisoning DoS.

### Likelihood Explanation
Likelihood is high: no certificate, prior handshake, or firewall rule is needed — only knowledge of the target's UDP listen port (which is inherently exposed for a mesh VPN) and passing the (often permissive, default-allow) `remote_allow_list`. Unlike the PSM report's attacker (who must pay a redemption fee to consume the rate limit), a Nebula attacker pays essentially nothing (a raw UDP packet) to force expensive server-side crypto work, making the attack cheap to repeat at scale.

### Recommendation
- **Short term**: Implement the reserved `Cookie` mechanism (or an equivalent lightweight, unforgeable MAC-based challenge) so that unauthenticated stage-1 packets are rejected with a cheap check before any Noise `ReadMessage`/DH operation is performed, mirroring WireGuard's cookie/MAC1 anti-flood defense. Add per-source-IP or global rate limiting on stage-1 handshake processing distinct from the retry/backoff logic already present for outbound handshakes.
- **Long term**: Add metrics/alerting on handshake failure rates and pending-handshake churn to detect flooding in production, and document/enforce a documented incident-response process for handshake-flood events, consistent with the original report's long-term recommendation for off-chain/out-of-band monitoring.

### Proof of Concept
1. Attacker (no CA-issued certificate, no established tunnel) crafts a UDP packet with a Nebula header: `Type=Handshake`, `Subtype=HandshakeIXPSK0`, `RemoteIndex=0`, `MessageCounter=1`, and a syntactically valid but bogus Noise ciphertext body (e.g., a valid-looking ephemeral public key plus arbitrary encrypted payload bytes), as constructed in test helpers such as `makeHandshakePacket`: [6](#0-5) 
2. Attacker sends a high volume of such packets, each with a unique fake ephemeral key, from spoofed or many source addresses (or one allowed address) to the target's listen port.
3. `HandleIncoming` → `beginHandshake` is invoked for every packet passing the IP allow-list; `handshake.NewMachine` + `machine.ProcessPacket` run full Noise DH/AEAD work per packet before the (only-then-checked) `CertVerifier` rejects the forged certificate: [7](#0-6) 
4. Repeated at volume, this consumes CPU cycles on the responder proportional to attacker-controlled packet rate, with no cookie/MAC gate to cheaply reject bogus attempts first, degrading or denying handshake processing for legitimate peers.

Note: I was not able to fully trace `processPayload`'s exact internal call sequence for `CertVerifier` invocation (file not fully retrieved in this session), so the precise line-level location of the CA verification step within `handshake/machine.go` could not be pinned down further; this is inferred from the `CertVerifier` doc comment and `requireComplete`/`completed` flow shown above.

func (hm *HandshakeManager) beginHandshake(via ViaSender, packet []byte, h *header.H) {
	f := hm.f
	cs := f.pki.getCertState()

	v := cs.DefaultVersion()
	if cs.GetCredential(v) == nil {
		f.l.Error("Unable to handshake with host because no certificate is available",
			"from", via, "certVersion", v)
		return
	}

	machine, err := handshake.NewMachine(
		v, cs.GetCredential,
		hm.certVerifier(), func() (uint32, error) { return generateIndex(f.l) },
		false, header.HandshakeIXPSK0,
	)
	if err != nil {
		f.l.Error("Failed to create handshake machine", "from", via, "error", err)
		return
	}

	response, result, err := machine.ProcessPacket(nil, packet)
	if err != nil {
		f.l.Error("Failed to process handshake packet", "from", via, "error", err)
		return
	}
```

func (m *Machine) ProcessPacket(out, packet []byte) ([]byte, *Result, error) {
	if m.failed {
		return nil, nil, ErrMachineFailed
	}
	if len(packet) < header.Len {
		return nil, nil, ErrPacketTooShort
	}
	// Reject packets whose subtype doesn't match the one this Machine was
	// built for. A pending handshake that suddenly receives a different
	// subtype on its index is either a stray packet that matched by chance
	// or a peer protocol violation; drop it without failing the Machine so
	// the legitimate retransmit can still complete.
	if header.MessageSubType(packet[1]) != m.subtype {
		return nil, nil, ErrSubtypeMismatch
	}
	if m.result.Initiator && m.hs.MessageIndex() == 0 {
		m.failed = true
		return nil, nil, ErrInitiateNotCalled
	}

	// The (eKey, dKey) ordering here is correct for IX, where the initiator
	// completes the handshake by reading the responder's stage-2 message.
	// noise returns (cs1, cs2) where cs1 is the initiator->responder cipher.
	// For 3-message patterns where a responder finishes by reading the final
	// message, this ordering would be wrong; revisit when XX/pqIX lands.
	msg, eKey, dKey, err := m.hs.ReadMessage(nil, packet[header.Len:])
	if err != nil {
		// Noise ReadMessage failed. The noise library checkpoints and rolls back
		// on failure, so the Machine is still alive. The caller can retry with
		// a different packet.
		return nil, nil, fmt.Errorf("noise ReadMessage: %w", err)
	}

	// From here on, noise state has advanced. Any error is fatal.
	flags := m.peerMsgFlags()

	if err := m.processPayload(msg, flags); err != nil {
		return nil, nil, err
	}
```

// makeHandshakePacket creates a handshake packet with the given parameters.
func makeHandshakePacket(from, to netip.AddrPort, subtype header.MessageSubType, remoteIndex uint32, counter uint64) *udp.Packet {
	data := make([]byte, 200)
	header.Encode(data, header.Version, header.Handshake, subtype, remoteIndex, counter)
	for i := header.Len; i < len(data); i++ {
		data[i] = byte(i)
	}
	return &udp.Packet{To: to, From: from, Data: data}
}
