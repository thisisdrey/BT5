I now have enough evidence to conclude the analysis. Confirming the flow: `HandleIncoming` in `handshake_manager.go` dispatches every stage-1 packet from any unauthenticated remote directly to `beginHandshake`, which builds a fresh Noise `Machine` and calls `ProcessPacket` — performing an X25519 Diffie-Hellman computation, cert reconstruction/parsing, and cert-chain verification against the CA pool — with no per-source-IP or per-packet rate limiting anywhere on this path.

### Title
Unauthenticated flood of handshake stage-1 packets causes unbounded ECDH/cert-verification CPU exhaustion (DoS) - (handshake_manager.go)

### Summary
Nebula's `HandshakeManager.HandleIncoming` accepts UDP handshake packets from any address that passes only a coarse, optional "remote allow list" check, then unconditionally invokes `beginHandshake` for every stage-1 packet. There is no rate limiting, cookie/proof-of-work challenge, or per-source throttle before the expensive Noise `ProcessPacket` call (ECDH + certificate parsing/verification) runs. An attacker who can reach the UDP listen port — even with no valid CA-signed certificate of their own — can flood arbitrarily many spoofed stage-1 packets to force the node to perform a full elliptic-curve DH operation and certificate-chain verification per packet, exhausting CPU.

### Finding Description
`HandleIncoming` gates only on subtype and a zero `RemoteIndex` for new handshakes; the only "attacker filter" before allocating a full `handshake.Machine` and running Noise is `AllowUnknownVpnAddr`, an IP/CIDR allow/deny list which is off by default and does not throttle rate. The code comment even acknowledges the deliberate absence of an anti-DoS mechanism ("Cookie was reserved for an anti-DoS mechanism that was never implemented"). [1](#0-0) 
For every stage-1 packet with `RemoteIndex == 0`, `beginHandshake` is called unconditionally: [2](#0-1) 
`beginHandshake` allocates a new `handshake.Machine` and calls `ProcessPacket`, which performs `m.hs.ReadMessage` (an X25519 ECDH computation as part of Noise_IX) before any certificate validity is known: [3](#0-2) [4](#0-3) 
Because a stage-1 packet carries `RemoteIndex == 0` by protocol convention, and the check at line 178 only rejects non-zero indexes, a flood of well-formed stage-1 packets (real or garbage-but-well-formed noise ciphertext with distinct ephemeral keys) each reaches the DH computation. Every distinct malformed packet requires its own DH computation before Noise/cert failure is detected, since there's no state that lets the server recognize and cheaply reject a flood before paying the cryptographic cost. This differs from the malformed-header/garbage cases which are dropped cheaply elsewhere; those hit `ErrPacketTooShort` or subtype mismatch, but any packet crafted with a valid Noise ephemeral key and IXPSK0 subtype will run the DH and payload-unmarshal path regardless of whether it ultimately produces a valid certificate.

### Impact Explanation
This is a remote, unauthenticated CPU-exhaustion / denial-of-service vector reachable by any network peer that can reach the node's UDP port, without possessing a certificate signed by the network's CA. Sustained flooding of crafted stage-1 packets forces continuous ECDH computation and certificate-parsing work on the responder, starving legitimate handshake processing and potentially the whole single-threaded UDP-listener/handshake path, denying service to the rest of the mesh.

### Likelihood Explanation
Likelihood is high: the attack requires no credentials, no valid certificate, and no prior handshake state — only the ability to send UDP packets to the listen port. The remote allow list defaults to allow-all unless explicitly configured, and even when configured, it filters by static IP/CIDR rather than rate, so a single allowed source (or a spoofed one, since UDP source addresses are not authenticated) can still flood without limit.

### Recommendation
- Add a lightweight, stateless anti-DoS check (e.g., a cookie/puzzle mechanism, as originally reserved but never implemented in the handshake payload) before committing to the DH computation in `beginHandshake`.
- Add a per-source-address rate limiter (token bucket) in `HandleIncoming` ahead of the `beginHandshake` call, independent of the `remote_allow_list` feature.
- Track error/handshake-failure rates per source address and impose backoff or temporary blocking.

### Proof of Concept
1. Craft repeated valid-format stage-1 UDP packets (`header.Handshake`, `header.HandshakeIXPSK0` subtype, `RemoteIndex=0`, `MessageCounter=1`), each with a fresh random Noise ephemeral public key, at high rate to the target node's listen port.
2. Each packet reaches `HandshakeManager.HandleIncoming` → `beginHandshake` → `handshake.NewMachine` → `ProcessPacket` → `m.hs.ReadMessage`, performing a full X25519 DH operation per packet before any failure is detected.
3. Because there is no rate limit or cheap pre-filter, sending packets faster than the responder's DH throughput drives CPU to saturation, degrading or denying handshake service to legitimate peers.

func (hm *HandshakeManager) beginHandshake(via ViaSender, packet []byte, h *header.H) {
	f := hm.f
	cs := f.pki.getCertState()

	v := cs.DefaultVersion()
	if cs.GetCredential(v) == nil {
		f.l.Error("Unable to handshake with host because no certificate is available",
			"from", via, "certVersion", v)
		return
	}

	machine, err := handshake.NewMachine(
		v, cs.GetCredential,
		hm.certVerifier(), func() (uint32, error) { return generateIndex(f.l) },
		false, header.HandshakeIXPSK0,
	)
	if err != nil {
		f.l.Error("Failed to create handshake machine", "from", via, "error", err)
		return
	}

	response, result, err := machine.ProcessPacket(nil, packet)
	if err != nil {
		f.l.Error("Failed to process handshake packet", "from", via, "error", err)
		return
	}

func (m *Machine) ProcessPacket(out, packet []byte) ([]byte, *Result, error) {
	if m.failed {
		return nil, nil, ErrMachineFailed
	}
	if len(packet) < header.Len {
		return nil, nil, ErrPacketTooShort
	}
	// Reject packets whose subtype doesn't match the one this Machine was
	// built for. A pending handshake that suddenly receives a different
	// subtype on its index is either a stray packet that matched by chance
	// or a peer protocol violation; drop it without failing the Machine so
	// the legitimate retransmit can still complete.
	if header.MessageSubType(packet[1]) != m.subtype {
		return nil, nil, ErrSubtypeMismatch
	}
	if m.result.Initiator && m.hs.MessageIndex() == 0 {
		m.failed = true
		return nil, nil, ErrInitiateNotCalled
	}

	// The (eKey, dKey) ordering here is correct for IX, where the initiator
	// completes the handshake by reading the responder's stage-2 message.
	// noise returns (cs1, cs2) where cs1 is the initiator->responder cipher.
	// For 3-message patterns where a responder finishes by reading the final
	// message, this ordering would be wrong; revisit when XX/pqIX lands.
	msg, eKey, dKey, err := m.hs.ReadMessage(nil, packet[header.Len:])
	if err != nil {
		// Noise ReadMessage failed. The noise library checkpoints and rolls back
		// on failure, so the Machine is still alive. The caller can retry with
		// a different packet.
		return nil, nil, fmt.Errorf("noise ReadMessage: %w", err)
	}
