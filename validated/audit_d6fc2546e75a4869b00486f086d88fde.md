### Title
Missing `chain_id` in `SignerCapabilityOfferProofChallengeV2` Enables Cross-Chain Signature Replay to Hijack Signer Capability — (`File: aptos-move/framework/aptos-framework/sources/account/account.move`)

---

### Summary

`SignerCapabilityOfferProofChallengeV2`, the struct signed off-chain to authorize `offer_signer_capability`, omits `chain_id` from its fields. The structurally identical `RotationCapabilityOfferProofChallengeV2` explicitly includes `chain_id` and its comment states this was added specifically to prevent cross-chain replay. Because `chain_id` is absent from the signer-capability challenge, a signature produced on one Aptos network (e.g., testnet) is valid on any other network (e.g., mainnet) where the same account address exists at the same sequence number. An attacker who obtains such a signature can call `offer_signer_capability` on mainnet, granting themselves or a colluding party a `SignerCapability` over the victim's mainnet account, enabling full account takeover and asset theft.

---

### Finding Description

`RotationCapabilityOfferProofChallengeV2` and `SignerCapabilityOfferProofChallengeV2` are parallel proof-of-intent structs used to authorize off-chain-signed capability delegation. The rotation variant was explicitly upgraded to include `chain_id`:

```move
/// This V2 struct adds the `chain_id` and `source_address` to the challenge message,
/// which prevents replaying the challenge message.
struct RotationCapabilityOfferProofChallengeV2 has drop {
    chain_id: u8,
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
```

The signer-capability variant, however, was never given the same treatment:

```move
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
```

`offer_signer_capability` constructs this struct and verifies the caller's off-chain signature against it:

```move
let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
    sequence_number: get_sequence_number(source_address),
    source_address,
    recipient_address,
};
verify_signed_message(
    source_address, account_scheme, account_public_key_bytes,
    signer_capability_sig_bytes, proof_challenge);
```

Because `chain_id` is absent, the BCS-serialized challenge is identical across all Aptos networks for any account that shares the same address and sequence number. A valid signature produced on testnet is therefore also valid on mainnet. [1](#0-0) [2](#0-1) 

---

### Impact Explanation

`SignerCapability` is the most powerful delegation primitive in the Aptos account model. A holder calls `create_authorized_signer` to obtain a full `signer` for the victim's account and can then execute arbitrary transactions on their behalf — transferring APT, fungible assets, rotating auth keys, or publishing modules. Replaying a testnet signer-capability offer on mainnet therefore constitutes **unauthorized transaction execution and direct theft of user-controlled on-chain assets**, both of which are in scope. [3](#0-2) 

---

### Likelihood Explanation

The precondition is that the victim's account exists on both networks with the same sequence number at the time of the replay. This is common for:

- Newly created accounts (sequence number 0 on both networks).
- Accounts that have executed the same number of transactions on both networks.
- Testnet accounts created by developers who mirror their mainnet setup.

The attacker only needs to observe the victim's testnet `offer_signer_capability` transaction (publicly visible on-chain), extract the `signer_capability_sig_bytes`, and submit it to mainnet before the victim's mainnet sequence number advances past the matching value. No privileged access is required; the attack is fully unprivileged. [4](#0-3) 

---

### Recommendation

Add `chain_id: u8` to `SignerCapabilityOfferProofChallengeV2` and populate it from `chain_id::get()` inside `offer_signer_capability`, exactly as `RotationCapabilityOfferProofChallengeV2` does. This is a breaking change to the signed struct layout, so any off-chain tooling that constructs this challenge must be updated in lockstep.

```move
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    chain_id: u8,          // <-- add this
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
```

```move
let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
    chain_id: chain_id::get(),  // <-- populate
    sequence_number: get_sequence_number(source_address),
    source_address,
    recipient_address,
};
``` [5](#0-4) 

---

### Proof of Concept

1. **Setup**: Alice has address `0xALICE` on both testnet (chain_id=2) and mainnet (chain_id=1). Both accounts are freshly created (sequence number = 0). Bob is the attacker with address `0xBOB`.

2. **Testnet action**: Alice legitimately calls `offer_signer_capability` on testnet, signing:
   ```
   SignerCapabilityOfferProofChallengeV2 {
       sequence_number: 0,
       source_address: 0xALICE,
       recipient_address: 0xBOB,
   }
   ```
   The resulting `signer_capability_sig_bytes` is recorded on-chain in the testnet transaction.

3. **Replay on mainnet**: Bob submits a mainnet transaction calling:
   ```move
   offer_signer_capability(
       &alice_signer_placeholder,   // Bob supplies Alice's address as sender
       signer_capability_sig_bytes, // copied verbatim from testnet
       ED25519_SCHEME,
       alice_public_key_bytes,
       0xBOB
   )
   ```
   The challenge reconstructed on mainnet is byte-for-byte identical to the testnet challenge (same `sequence_number=0`, same `source_address`, same `recipient_address`, no `chain_id`). `verify_signed_message` passes.

4. **Outcome**: `Account[0xALICE].signer_capability_offer.for` is now set to `0xBOB` on mainnet. Bob calls `create_authorized_signer(&bob, 0xALICE)` to obtain Alice's mainnet signer and drains her APT and fungible asset balances. [6](#0-5) [7](#0-6) [8](#0-7)

    /// Offers signer capability on behalf of `account` to the account at address `recipient_address`.
    /// An account can delegate its signer capability to only one other address at one time.
    /// `signer_capability_key_bytes` is the `SignerCapabilityOfferProofChallengeV2` signed by the account owner's key
    /// `account_scheme` is the scheme of the account (ed25519 or multi_ed25519).
    /// `account_public_key_bytes` is the public key of the account owner.
    /// `recipient_address` is the address of the recipient of the signer capability - note that if there's an existing
    /// `recipient_address` in the account owner's `SignerCapabilityOffer`, this will replace the
    /// previous `recipient_address` upon successful verification (the previous recipient will no longer have access
    /// to the account owner's signer capability).
    public entry fun offer_signer_capability(
        account: &signer,
        signer_capability_sig_bytes: vector<u8>,
        account_scheme: u8,
        account_public_key_bytes: vector<u8>,
        recipient_address: address
    ) acquires Account {
        let source_address = signer::address_of(account);
        ensure_resource_exists(source_address);
        assert!(exists_at(recipient_address), error::not_found(EACCOUNT_DOES_NOT_EXIST));

        // Proof that this account intends to delegate its signer capability to another account.
        let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
            sequence_number: get_sequence_number(source_address),
            source_address,
            recipient_address,
        };
        verify_signed_message(
            source_address, account_scheme, account_public_key_bytes, signer_capability_sig_bytes, proof_challenge);

        // Update the existing signer capability offer or put in a new signer capability offer for the recipient.
        let account_resource = &mut Account[source_address];
        account_resource.signer_capability_offer.for.swap_or_fill(recipient_address);
    }

    public fun verify_signed_message<T: drop>(
        account: address,
        account_scheme: u8,
        account_public_key: vector<u8>,
        signed_message_bytes: vector<u8>,
        message: T,
    ) acquires Account {
        let auth_key = get_authentication_key(account);
        // Verify that the `SignerCapabilityOfferProofChallengeV2` has the right information and is signed by the account owner's key
        if (account_scheme == ED25519_SCHEME) {
            let pubkey = ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else if (account_scheme == MULTI_ED25519_SCHEME) {
            let pubkey = multi_ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = multi_ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                multi_ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };
    }
