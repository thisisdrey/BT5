This confirms Go's `net/http` package already defends against exactly this bug class. `Header.write` (via `writeSubset`, `src/net/http/header.go:139`) uses `headerNewlineToSpace = strings.NewReplacer("\n", " ", "\r", " ")` to strip CR/LF from header values before writing them onto the wire, which is exactly demonstrated by the existing test `TestRequestBadUserAgent` where `"evil\r\nX-Evil: evil"` gets sanitized to `"evil  X-Evil: evil"` in the actual output rather than being split into an injected header line.

Additionally, `net/http.Transport.roundTrip` calls `validateHeaders` (`src/net/http/transport.go:592-606`), which rejects any outgoing header field name/value that fails `httpguts.ValidHeaderFieldValue`/`ValidHeaderFieldName` before the request is ever sent, returning an error like `net/http: invalid header value for %q` rather than smuggling a second request. [1](#0-0) [2](#0-1) [3](#0-2) 

This is the exact opposite of RestSharp's `HttpHeaders.TryAddWithoutValidation`, which performs no validation at all. Go's standard `net/http` client/server stack already sanitizes/rejects CR/LF in header values at both the write layer and the transport validation layer, so the reported bug class does not reproduce here — it's a case of an already-defended/fixed pattern, not a live vulnerability.

func validateHeaders(hdrs Header) string {
	for k, vv := range hdrs {
		if !httpguts.ValidHeaderFieldName(k) {
			return fmt.Sprintf("field name %q", k)
		}
		for _, v := range vv {
			if !httpguts.ValidHeaderFieldValue(v) {
				// Don't include the value in the error,
				// because it may be sensitive.
				return fmt.Sprintf("field value for %q", k)
			}
		}
	}
	return ""
}
