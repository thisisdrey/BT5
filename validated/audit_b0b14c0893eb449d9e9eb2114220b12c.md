### Title
Broadcast auth-gate is bypassed because relay is unconditional on `accepted`, not on `self.broadcast`/auth — (`File: stackslib/src/net/api/postblock_v3.rs`)

### Summary
`try_parse_request` allows an unauthenticated, non-broadcast POST (`self.auth=Some(password)`, no `authorization` header, no `broadcast=1`) to fall through to `Self::parse_postblock_octets(body)`, deserializing a fully attacker-controlled buffer into a `NakamotoBlock`. If that block is accepted by `Relayer::process_new_nakamoto_block_ext`, `try_handle_request` unconditionally calls `node.set_relay_message(...)` based solely on `data_resp.accepted`, never checking `self.broadcast`/whether the uploader was authenticated. This means the "broadcast requires auth" access control the code appears to implement is not actually what gates network relay.

### Finding Description
The intended equality is: *"a block gets relayed to the network only if the uploader was authenticated or explicitly requested broadcast=1 with the correct password."* Tracing the code:

- `try_parse_request` (`stackslib/src/net/api/postblock_v3.rs:99-129`) only errors on missing/bad auth when `broadcast=true` (`if broadcast && !authenticated { return Err(...) }`, line 120). If `broadcast` is left unset (`false`) and no `authorization` header is sent at all, `authenticated` stays `false` and no error is raised — the request proceeds to content-type check and then to `Self::parse_postblock_octets(body)` (line 131), running `NakamotoBlock::consensus_deserialize` on a fully attacker-controlled byte buffer [1](#0-0) .
- In `try_handle_request`, the decoded block is passed to `Relayer::process_new_nakamoto_block_ext` with `self.broadcast.unwrap_or(false)` as a hint parameter [2](#0-1) . Crucially, whether the block is relayed onward to the P2P network is decided purely by `data_resp.accepted` — i.e., whether chainstate validation (internal signature/tenure checks) accepted it — and **not** by `self.broadcast` or by whether the uploader was authenticated: `if data_resp.accepted { node.set_relay_message(...) }` [3](#0-2) .

Root cause: the `broadcast`/`authenticated` gate in `try_parse_request` only prevents the HTTP request from being rejected early; it does not actually control the relay decision in `try_handle_request`. As long as the posted bytes decode into a `NakamotoBlock` that independently passes `process_new_nakamoto_block_ext`'s internal chainstate acceptance checks (e.g., it's a validly-signed block for a real, already-broadcast tenure — which an attacker can obtain simply by observing it on the wire once), any unauthenticated, non-broadcast upload triggers the same `node.set_relay_message` relay as an authenticated broadcast upload would.

### Impact Explanation
An unauthenticated remote party who has merely observed a validly signed Nakamoto block on the wire (or via any RPC) can re-POST that exact block to `/v3/blocks/upload/` with no `authorization` header and no `broadcast=1`, and cause the target node to re-relay it to its peers via `node.set_relay_message`. This circumvents the node operator's configured access control (`self.auth=Some(password)`) which is intended to require credentials for network propagation via this endpoint. The data relayed is not forged (it must pass internal signature/tenure validation), so this is not arbitrary state corruption, but it is an authorization-bypass on the intended "authenticated-broadcast-only" relay control, allowing repeatable, cost-free triggering of network-wide gossip re-propagation of blocks the node already possesses, from any remote unauthenticated peer.

### Likelihood Explanation
Preconditions: the node has `self.auth=Some(password)` configured (intending only authenticated/broadcast uploads to cause relay), the attacker has observed at least one validly-signed Nakamoto block for a real, already-active tenure (trivial — any node broadcasts/serves blocks). Attacker cost is a single unauthenticated HTTP POST with no special access; the port (`/v3/blocks/upload/`) is a standard remotely-reachable RPC endpoint. The action is fully repeatable for every block the attacker can obtain.

### Recommendation
In `try_handle_request` (`stackslib/src/net/api/postblock_v3.rs`), gate the `node.set_relay_message` call on `self.broadcast.unwrap_or(false)` (and thus on the authentication check already performed in `try_parse_request`) in addition to `data_resp.accepted`, so that relay only occurs when the uploader was actually authorized to request broadcast, matching the intended semantics of the `broadcast`/`authorization` parameters.

### Proof of Concept
Add a test in `stackslib::net::api::tests::postblock_v3`:
1. Construct a `RPCPostBlockRequestHandler` with `auth = Some("secret".into())`.
2. Using a running `TestPeer`, obtain a real, validly-signed `NakamotoBlock` for the peer's current (already broadcast) tenure.
3. Build a raw HTTP POST to `/v3/blocks/upload/` with `Content-Type: application/octet-stream`, the block's serialized bytes as body, **no `authorization` header**, and **no `broadcast` query parameter**.
4. Call `try_parse_request` then `try_handle_request` against `StacksNodeState`, ensuring `process_new_nakamoto_block_ext` accepts the block (already-known, validly signed tenure).
5. Assert: current behavior shows `node.set_relay_message` IS invoked (relay occurs) despite `authenticated=false` and `broadcast=false`, violating the expected invariant that relay only occurs for authenticated/broadcast=1 uploads.
