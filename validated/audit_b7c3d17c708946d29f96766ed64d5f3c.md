### Title
Unbounded GetFileAttributesRequest paths/attributes cause resource exhaustion in GetFileAttributes - (File: internal/gitaly/service/repository/file_attributes.go)

### Summary
`validateGetFileAttributesRequest` only checks that `Paths`, `Attributes`, and `Revision` are non-empty, with no upper bound on the number of entries. An attacker-controlled unary `GetFileAttributesRequest` with millions of path/attribute entries drives `GetFileAttributes` into a large, unbounded loop over `git check-attr`, consuming CPU, memory, and process/goroutine time proportional to attacker input.

### Finding Description
`validateGetFileAttributesRequest` (internal/gitaly/service/repository/file_attributes.go:44-61) enforces only `len(...) == 0` checks on `in.GetPaths()` and `in.GetAttributes()` — there is no maximum count or aggregate size limit. `GetFileAttributes` (lines 14-42) passes `in.GetAttributes()` directly as `Args` to `git check-attr` via `gitattributes.CheckAttr` (internal/git/gitattributes/check_attr.go:30-60), and then iterates `in.GetPaths()` calling `checkAttrCmd.Check(path)` once per path (file_attributes.go:30-39). Each `Check` call writes the path to the command's stdin pipe and synchronously blocks reading `c.count` NUL-delimited tokens back from stdout (check_attr.go:63-106) before returning to the loop, appending results into an ever-growing `attrValues` slice held entirely in memory until the response is returned.

With millions of paths, this results in millions of sequential synchronous pipe round-trips within a single RPC handler invocation, and unbounded growth of the `attrValues` slice in memory. With millions of attribute names, the `git check-attr` subprocess is invoked with a correspondingly huge argument list, consuming memory/CPU in the exec'd process and validation of each name.

There is no per-request cap in this handler, and no visible gRPC-level `MaxRecvMsgSize` override for this service found in the repo. This is a real resource-consumption path directly reachable via a single unauthenticated-role (but authenticated-token) RPC, using data fully controlled by the caller (request fields).

### Impact Explanation
An attacker with normal repo access can send a single `GetFileAttributesRequest` with a very large `Paths`/`Attributes` list, causing the handling goroutine to run for an extended period and to allocate memory proportional to the (attacker-controlled) input and result set, and can drive the `git check-attr` child process to do the same. On a multi-tenant Gitaly node this can degrade or exhaust resources (memory, CPU, held goroutine) shared with other tenants, matching a DoS-of-RPC-handler impact class.

### Likelihood Explanation
This requires only an unprivileged, already-authorized caller of the Gitaly RPC (any GitLab user is normally proxied through Rails/Workhorse to reach this call with a request they can shape) — no special role, no admin/config bypass, no secret. The gRPC transport's default max message size (grpc-go default 4MB for receive unless overridden) is the practical bound on how many paths/attributes fit in one request; no override was found configured for this Gitaly server in the codebase search performed, so the achievable size is bounded by the standard gRPC default, which still permits tens of thousands of short path/attribute strings per request — enough to cause a measurably expensive, repeatable synchronous loop. This is repeatable and does not require special timing or race conditions.

### Recommendation
Add explicit upper bounds in `validateGetFileAttributesRequest` on `len(in.GetPaths())` and `len(in.GetAttributes())` (e.g., matching limits used by comparable Gitaly RPCs, or based on a configurable maximum), rejecting requests over the limit with `InvalidArgument`. Consider also capping total request size/argument length before invoking `git check-attr`, and enforcing a bound on the resulting `attrValues` size or streaming results instead of buffering the entire response in memory.

### Proof of Concept
```go
func TestGetFileAttributes_LargePathsDoS(t *testing.T) {
    // Construct a GetFileAttributesRequest with N=10^5–10^6 unique short paths
    // and/or attributes (bounded only by default gRPC 4MB max message size),
    // e.g. paths := make([]string, 1_000_000); for i := range paths { paths[i] = fmt.Sprintf("f%d", i) }
    req := &gitalypb.GetFileAttributesRequest{
        Repository: repo,
        Revision:   []byte("HEAD"),
        Paths:      paths,
        Attributes: []string{"text"},
    }
    start := time.Now()
    _, err := client.GetFileAttributes(ctx, req)
    // Expected: no InvalidArgument rejection occurs regardless of len(paths);
    // measure elapsed time and memory (pprof) to show handler runs unbounded
    // proportional to N with no server-side cap.
    require.NoError(t, err)
    t.Logf("elapsed: %s", time.Since(start))
}
```
Run with increasing `N` and observe roughly linear (or worse) growth in handler latency/memory with no enforced ceiling, confirming absence of a request-size/count limit in `validateGetFileAttributesRequest`.
