### Title
Unsolicited StackerDB chunk handler advertises a chunk version in its inventory reply before the chunk is durably stored, allowing an advertised-vs-actual-state mismatch - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` validates an unsolicited chunk cryptographically/structurally and then immediately patches and transmits a `StackerDBChunkInv` reply claiming the new (higher) `slot_version` is now held locally, before the chunk has actually been durably written to the StackerDB via `try_replace_chunk`. The write itself only happens later, out-of-band, when the message is forwarded to the relayer. This mirrors the external report's root cause pattern: an equality/consistency assumption (here, "advertised slot inventory == actually stored chunk") is asserted on data that has not yet been finalized, and can be observed/acted upon by other peers before the underlying state actually matches.

### Finding Description
`validate_received_chunk` (stackslib/src/net/stackerdb/mod.rs:649-718) performs signature, freshness, size, and write-count checks on an incoming `StackerDBChunkData`, but does not store anything — storage is exclusively the job of `StackerDBs::try_replace_chunk` (stackslib/src/net/stackerdb/db.rs:400-438), which is invoked later via the Relayer pipeline, not inside the unsolicited-message handler itself.

Inside `handle_unsolicited_StackerDBPushChunk` (stackslib/src/net/stackerdb/mod.rs:742-871): [1](#0-0) 
the code calls `validate_received_chunk`, and on success, immediately mutates the in-memory `StackerDBChunkInvData` reply object to record the *new* slot version as if it were already stored: [2](#0-1) 
If `send_reply` is true, this patched inventory is signed and sent back to the peer right away — before the chunk is committed to the on-disk StackerDB by the relayer. The function then returns `(false, true)`, meaning "don't buffer, but do forward to relayer for actual processing/storage" — i.e., the storage step is deferred and decoupled from the inventory-advertisement step.

This breaks the equality that the report's bug class targets: "advertised/served state == committed/stored state." Between the moment the inventory reply is sent (claiming version N is present) and the moment the relayer actually performs `try_replace_chunk`, the local StackerDB does not yet contain that chunk. Any peer that receives this advertisement and immediately issues a `StackerDBGetChunk` request for that version can encounter a window where the local node cannot serve it (stale/absent), and other peers that use inventory information to prioritize sync (as described in the "rarest-first" download scheduling per stackslib/src/net/stackerdb/mod.rs:85-96) may make forwarding/priority decisions based on inventory that does not yet reflect real, durable state.

### Impact Explanation
This falls under the High-impact category of "steering a node off the tip via false inventory" — the StackerDB inventory (`StackerDBChunkInvData`) is the mechanism peers use to decide what to fetch and from whom, and the sync state machine (stackslib/src/net/stackerdb/sync.rs) prioritizes chunks by version from these inventories. Advertising a chunk version before it is durably persisted allows an attacker (any connected, even semi-authenticated peer capable of pushing a validly-signed chunk for a slot it does not own the write-lock for — note the signature check still binds to the correct slot owner, so this is not an auth-bypass, but a state-consistency/ordering flaw) to cause the network's view of "who has what" to diverge from ground truth, degrading replication reliability and enabling wasted round-trips or missed availability, particularly if the deferred relayer-side write fails, races with a concurrent write, or the connection to the peer is severed before the async store completes.

### Likelihood Explanation
Likelihood is moderate: it requires only a normally-formed, validly-signed `StackerDBPushChunkData` message and a slow/blocked relayer at the moment the reply is generated, which is achievable by any peer pushing chunks at the moment its neighbor is under load, or by triggering many pushes back-to-back to widen the race window. No privileged key or admin role is needed beyond a legitimately-signing StackerDB slot signer (a normal DB participant), and the message path is fully reachable over the standard P2P protocol in-scope (`stackslib/src/net/stackerdb/**`, excluded from epoch2x/neon).

### Recommendation
Do not patch/emit the `StackerDBChunkInv` version bump until the corresponding chunk has actually been durably committed via `StackerDBs::try_replace_chunk`. Either perform the store synchronously within `handle_unsolicited_StackerDBPushChunk` before constructing the reply, or defer sending the `StackerDBChunkInv` reply until the relayer confirms successful storage, ensuring the advertised inventory never runs ahead of the actual persisted state.

### Proof of Concept
Conceptual PoC (based on code paths, not independently executed in this analysis):
1. An attacker or slow neighbor connects as an authenticated peer and possesses a valid signing key for a StackerDB slot (a normal, legitimate DB participant capability).
2. It sends a `StackerDBPushChunkData` with an incremented `slot_version` and a valid signature/hash.
3. `handle_unsolicited_StackerDBPushChunk` runs `validate_received_chunk`, which succeeds, patches `data.slot_versions[slot_id] = new_version` in the outgoing `StackerDBChunkInv`, and (if `send_reply`) immediately signs and transmits this inventory to the requesting peer — all before the relayer has invoked `try_replace_chunk` to actually persist the chunk.
4. A third-party peer receiving this inventory (or the same peer, immediately after) issues a `StackerDBGetChunk` for that new version; if it arrives before the deferred relayer store completes (or if the store never completes, e.g., due to a race/error), the node cannot serve the advertised chunk, demonstrating the advertised-vs-actual mismatch.

Note: I was unable to execute this scenario against a live/test harness within this analysis; the finding is derived from static review of `stackslib/src/net/stackerdb/mod.rs`, `stackslib/src/net/stackerdb/db.rs`, and `stackslib/src/net/unsolicited.rs`, which shows the code paths described above, confirming the storage step is decoupled from and deferred relative to the inventory-advertisement step.
