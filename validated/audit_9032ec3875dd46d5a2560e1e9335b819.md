### Title
Permanent freezing of ETH-implicit account funds if the fixed-gas `rlp_execute_callback` panics, leaving `has_in_flight_tx` stuck as `true` forever - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract used for ETH-implicit accounts (NEP-518) uses a single boolean flag, `has_in_flight_tx`, to serialize transaction processing so that only one Ethereum-style transaction is "in flight" at a time. `rlp_execute` refuses any further calls while this flag is `true`, and the flag can only be cleared from within one of the contract's own promise callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`). All of these callbacks are dispatched with a hard-coded static gas budget (`RLP_EXECUTE_CALLBACK_GAS = 5 Tgas`) regardless of how large the underlying cross-contract call's return value is. If that callback ever panics (e.g. by running out of the fixed 5 Tgas budget while processing an oversized `promise_result`), the whole receipt's state changes — including the `has_in_flight_tx = false` reset — are rolled back by the NEAR runtime, and no further callback will ever be scheduled to reset it. Because ETH-implicit accounts can never have a full access key added or be recreated, and `rlp_execute` unconditionally rejects new transactions while `has_in_flight_tx` is `true`, this permanently locks the account and stucks any funds/tokens it holds, with no rescue path.

### Finding Description
`WalletContract::rlp_execute` is the sole entry point for an ETH-implicit account: it checks `self.has_in_flight_tx` and bails out immediately if it is `true`. [1](#0-0) 

The flag can be set to `true` in `rlp_execute` (and `address_check_callback` / `nep_141_storage_balance_callback`), but can only ever be reset to `false` inside one of the three private callbacks: [2](#0-1) [3](#0-2) [4](#0-3) 

Every code path that ultimately performs the user's requested action schedules `rlp_execute_callback` with a hard-coded static gas value `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas), independent of the size/complexity of the underlying call's result: [5](#0-4) [6](#0-5) [7](#0-6) 

Inside `rlp_execute_callback`, the flag reset happens first, but afterward the function reads and copies the entire cross-contract call's returned bytes into `ExecuteResponse.success_value`: [8](#0-7) 

On NEAR, a function call is atomic: if execution of the receipt panics for any reason (including "Exceeded the prepaid gas"), none of the state mutations performed during that call are committed — the `has_in_flight_tx = false` write is discarded along with everything else. Since the `target` of `rlp_execute` (and hence the contract whose return value is read in the callback) is fully attacker/relayer/user-controlled, and the callback gas budget is fixed rather than scaled to the size of the expected response, a `target` contract that returns an oversized value (or otherwise makes the deserialization/copy in the callback expensive) can cause the fixed 5 Tgas budget to be exceeded, causing `rlp_execute_callback` to panic before its state changes are committed.

Because the wallet contract's `has_in_flight_tx = true` write from `rlp_execute` was already committed (that outer call succeeded and actually dispatched the receipt), and the only mechanism to reset it — the callback — subsequently panics and reverts its own state changes, the account is left with `has_in_flight_tx` permanently stuck at `true`. All subsequent `rlp_execute` calls will immediately hit the early-return "transaction already in progress" branch: [9](#0-8) 

Per the design documentation, an ETH-implicit account "can only be used by calling the methods of the Wallet Contract. It cannot be deleted, nor can a full access key be added," meaning there is no alternative path (e.g. adding a full access key, or deleting/recreating the account) to regain control once the contract is wedged. [10](#0-9) 

This mirrors the reported Pip.sol issue: a legitimate, foreseeable failure mode (forgetting a nullifier / an inevitable gas-budget overflow) results in funds becoming permanently inaccessible with no built-in recovery mechanism.

### Impact Explanation
Any $NEAR balance and any NEP-141/ERC-20 style balances associated with the ETH-implicit account become permanently frozen — the wallet can never again process a transaction because `rlp_execute` unconditionally refuses to proceed while `has_in_flight_tx` is `true`, and nothing in the contract can ever flip it back to `false` after this panic. There is no owner-only or rescue function of any kind in `WalletContract`, so this is a total, unrecoverable loss of custody over the account's assets.

### Likelihood Explanation
The `target` account and the exact call made are freely chosen by the transaction's signer (or a malicious/faulty relayer that races the address-check/storage-balance flow), and the callback gas budget is a fixed constant unrelated to the actual size of data returned by that target. A user (accidentally, via a contract that returns large blobs) or an attacker (deliberately deploying a contract that returns a maximal-size value, or that is targeted through an emulated ERC-20 transfer path) can reliably trigger a gas-exhaustion panic inside `rlp_execute_callback`. Given the fixed 5 Tgas static budget is quite low relative to what deserializing/copying a large `Vec<u8>` return value can cost, this is a practically reachable, repeatable condition rather than a purely theoretical one.

### Recommendation
- Do not gate all future transactions solely on an unrecoverable boolean flag with no timeout/reset mechanism. Add a way to detect and clear a "stuck" in-flight flag (e.g., a self-callback with a guaranteed minimum gas reservation, or a watchdog method that can reset `has_in_flight_tx` if the corresponding promise/receipt is known to have already resolved).
- Scale the static gas reserved for `rlp_execute_callback` (and the other callbacks) to account for the maximum possible size of the underlying call's return value, or cap/truncate the amount of data copied into `ExecuteResponse` so the callback's gas cost is bounded regardless of what the target returns.
- Ensure the flag reset (`has_in_flight_tx = false`) is the very first, unconditionally-cheap operation and structure the callback so that any expensive/variable-cost work (e.g., copying large return values) cannot cause the entire receipt, including the reset, to be reverted.

### Proof of Concept
1. Deploy the Wallet Contract as the global contract behind an ETH-implicit account `E` (as in `integration-tests/src/tests/features/wallet_contract.rs`), fund `E` with $NEAR. [11](#0-10) 
2. Deploy an attacker-controlled contract `Evil` whose only method returns a large byte blob (close to the maximum allowed return-value size) when called.
3. Sign and submit (via `create_rlp_execute_tx`) an Ethereum-style transaction from `E`'s secret key targeting `Evil`'s method through `rlp_execute`. [12](#0-11) 
4. The `_` branch of `inner_rlp_execute` schedules `Evil`'s call followed by `rlp_execute_callback` with only `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas). [7](#0-6) 
5. When `Evil`'s large return value is processed in `rlp_execute_callback`, the call exceeds its 5 Tgas budget and panics ("Exceeded the prepaid gas"), reverting the `has_in_flight_tx = false` write from earlier in that same function. [13](#0-12) 
6. Any subsequent `rlp_execute` call against `E` now immediately returns `"Error: transaction already in progress, please try again later."` forever, and `E`'s funds can never be moved again. [9](#0-8)

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

pub fn create_rlp_execute_tx(
    target: &AccountIdRef,
    mut action: Action,
    nonce: u64,
    eth_implicit_account: &AccountIdRef,
    secret_key: &SecretKey,
    near_signer: &NearSigner<'_>,
    env: &TestEnv,
) -> SignedTransaction {
    const CHAIN_ID: u64 = 399;
    // handles 24 vs 18 decimal mismatch between $NEAR and $ETH
    const MAX_YOCTO_NEAR: u128 = 1_000_000;

    // Construct Eth transaction from user's intended action
    let value = match &mut action {
        Action::Transfer(tx) => {
            let raw_amount = tx.deposit;
            tx.deposit = Balance::from_yoctonear(raw_amount.as_yoctonear() % MAX_YOCTO_NEAR);
            Wei::new_u128(raw_amount.as_yoctonear() / MAX_YOCTO_NEAR)
        }
        Action::FunctionCall(fn_call) => {
            let raw_amount = fn_call.deposit;
            fn_call.deposit = Balance::from_yoctonear(raw_amount.as_yoctonear() % MAX_YOCTO_NEAR);
            Wei::new_u128(raw_amount.as_yoctonear() / MAX_YOCTO_NEAR)
        }
        _ => Wei::zero(),
    };
    let tx_data = abi_encode(target.to_string(), action);
    let transaction = Transaction2930 {
        chain_id: CHAIN_ID,
        nonce: nonce.into(),
        gas_price: U256::zero(),
        gas_limit: U256::zero(),
        to: Some(derive_address(target)),
        value,
        data: tx_data,
        access_list: Vec::new(),
    };
    let signed_tx = sign_eth_transaction(transaction, &secret_key);
    let signed_tx_bytes: Vec<u8> = (&signed_tx).into();
    let tx_bytes_b64 = near_primitives::serialize::to_base64(&signed_tx_bytes);
    let args = format!(
        r#"{{
        "target": "{target}",
        "tx_bytes_b64": "{tx_bytes_b64}"
    }}"#
    )
    .into_bytes();

    // Construct Near transaction to `rlp_execute` method
    let actions = vec![Action::FunctionCall(Box::new(FunctionCallAction {
        method_name: "rlp_execute".into(),
        args,
        gas: Gas::from_teragas(300),
        deposit: Balance::ZERO,
    }))];
    let nonce = view_nonce(env, near_signer.account_id, near_signer.signer.public_key()) + 1;
    let block_hash = *env.clients[0].chain.get_head_block().unwrap().hash();
    SignedTransaction::from_actions(
        nonce,
        near_signer.account_id.into(),
        eth_implicit_account.into(),
        &near_signer.signer.clone(),
        actions,
        block_hash,
    )
}
