## Finding

### Title
`TransferToNewAccount`/`TransferToNewAccountPda` never validate `new_authority`, allowing a migrated account to be permanently bricked by setting authority to the zero Pubkey - ([File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs])

### Summary
The Compound Open Oracle bug is that `put()` never checks that the address recovered from a signature is non-zero before trusting it and writing it into state. The analogous pattern in marginfi-v2 is `transfer_to_new_account` / `transfer_to_new_account_pda`: the `new_authority` account is taken as a completely unchecked `UncheckedAccount` and is written directly into the new `MarginfiAccount.authority` field — with no check that it is non-default (or otherwise sane) — while the old account is simultaneously disabled and permanently marked as migrated.

### Finding Description
`TransferToNewAccount` and `TransferToNewAccountPda` both declare: [1](#0-0) [2](#0-1) 

The comment itself acknowledges "New authority is completely unchecked." The handler `transfer_to_new_account` (and the PDA variant) takes `ctx.accounts.new_authority.key()` and writes it directly into the freshly-initialized account via `initialize_migrated_account`, without any `require!`/`check!` that it is not `Pubkey::default()`: [3](#0-2) 

Immediately after, the old account is disabled and permanently marked migrated so it can never be used again: [4](#0-3) 

Only the off-chain CLI helper enforces a zero-address check (`if new_authority == Pubkey::default() { bail!(...) }`), which is purely client-side and not enforced by the on-chain program: [5](#0-4) 

Because `Pubkey::default()` (the all-zero key) has no corresponding private key, no transaction can ever be signed as that authority. If the new account's `authority` field ends up as `Pubkey::default()` — whether from a user/client mistake, a malicious or buggy front-end/relayer building the transaction, or third-party CPI callers of `TransferToNewAccountPda` — every subsequent operation gated by `is_signer_authorized`/`Signer<'info>` checks against that authority becomes unsatisfiable, since the check compares against the actual transaction signer, which can never equal the zero key.

### Impact Explanation
Once migration completes:
- The old `MarginfiAccount` is unconditionally disabled (`ACCOUNT_DISABLED` flag set, `lending_account` zeroed) and its `migrated_to` field permanently points at the new account — this path is one-way and guarded against re-entry via `check_eq!(old_account.migrated_to, Pubkey::default(), ...)`.
- The new `MarginfiAccount` holds the migrated `lending_account` (i.e., all deposits/borrows) but has `authority = Pubkey::default()`.
- No wallet can ever sign transactions as `Pubkey::default()`, so no further deposit/withdraw/borrow/repay/close/transfer instruction gated by authority checks can be executed on the new account.

This results in permanent lock/freeze of the migrated funds, satisfying the accepted impact category ("permanent lock/freeze"). This is reachable by any unprivileged marginfi account owner (or anyone building the transaction on their behalf) calling a completely permissionless, non-admin instruction.

### Likelihood Explanation
`transfer_to_new_account`/`transfer_to_new_account_pda` are unprivileged, user-initiated instructions (only the account's own `authority` must sign). The vulnerable field, `new_authority`, is fully attacker/user-controlled input with zero on-chain validation. The bug is trivially triggered by passing the system program ID, the zero pubkey, or any other address the caller doesn't/can't control as `new_authority` — this requires no special preconditions beyond owning a marginfi account and submitting one transaction.

### Recommendation
Add an explicit on-chain check in both `transfer_to_new_account` and `transfer_to_new_account_pda` that `ctx.accounts.new_authority.key() != Pubkey::default()` (and consider disallowing well-known non-signable addresses such as native program IDs) before finalizing the migration, returning an error (e.g., `MarginfiError::InvalidAuthority`) if this check fails — mirroring the check that currently exists only in the CLI.

### Proof of Concept
1. Attacker/careless user owns `marginfi_account_A` with active deposits/borrows.
2. They call `transfer_to_new_account` (or `transfer_to_new_account_pda`), signing as the current `authority`, but set `new_authority = Pubkey::default()` (or any address without a known private key) in the account list.
3. The instruction succeeds: `old_account` is disabled and its `migrated_to` set; `new_account.authority` is set to `Pubkey::default()`, and it now holds all the migrated lending positions.
4. No subsequent transaction can satisfy `Signer<'info>`/`is_signer_authorized` checks for `authority = Pubkey::default()`, since Solana cannot produce a valid signature for the all-zero key.
5. All value in `new_account` (deposits and any residual borrow positions) is permanently unreachable — a permanent freeze of user funds with no admin/emergency recovery path evident in this instruction.
