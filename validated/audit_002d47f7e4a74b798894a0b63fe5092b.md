### Title
Per-block index-cache in the market can desync from a vault's live liquidity index within the same block - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
The market caches vault liquidity indexes (`index`, `lindex`) per `(timestamp, aid)` in `index-cache` and, once a cache entry exists for the current `stacks-block-time`, all subsequent debt/collateral accruals and oracle price resolutions for that asset within the same block reuse the cached value instead of re-querying the vault [1](#0-0) . This mirrors the reported bug class: a value is snapshotted/cached at one point while a different, "always fresh" authority (the vault contract itself) can move on independently, producing a desync between the cached figure the market relies on and the vault's true current state.

### Finding Description
`accrue-and-cache` is the market's single gateway for reading a vault's up-to-date liquidity index: on a cache miss it calls `vault-accrue`, which invokes the vault's own `accrue` entrypoint and returns fresh indexes, then stores them keyed by `{ timestamp: stacks-block-time, aid }` [2](#0-1) [1](#0-0) . On a cache hit, it trusts the previously stored tuple for the remainder of the block without re-checking the vault.

Vault-mutating operations such as `vault-deposit` and `vault-redeem` call the vault contracts directly (`.v0-vault-stx deposit`, etc.) rather than going through `accrue-and-cache` [3](#0-2) . Each vault contract maintains its own interest-rate state (`points-ir`, `assets`, `total-borrowed`, `principal-scaled`, per the vault data vars) and is expected to accrue on state-changing calls to keep its share-price/index consistent, independent of whether the market's `index-cache` has already been populated for that block. If a vault's index is advanced by a deposit/redeem/borrow/repay call that happens after the market has already cached that vault's index for the current `stacks-block-time`, every subsequent call in the same block that hits the cache (health checks, `accrue-user-debts`/`accrue-user-collateral`, and ztoken price resolution via the callcode path) will keep using the now-stale cached `index`/`lindex` instead of the vault's true current value — exactly the "bank caches feeManager while HardVault always reads config.feeManager fresh" pattern from the reference report, just applied to the per-block index cache instead of a fee manager address.

### Impact Explanation
Debt scaling, collateral scaling, and ztoken price resolution (via `resolve-ztoken`'s callcode transform, which is gated behind the cached index) all depend on this index being an accurate, live reflection of the vault's true accrual state. A stale cached index used by health-check math or ztoken pricing can misstate a position's real collateral value or real debt value within the same block, which can let a user's position appear healthier than it is or let ztoken collateral be over/under-priced relative to its true backing. Depending on direction, this can be leveraged to borrow against overstated collateral or evade a true unhealthy state, which falls under theft of user funds / protocol insolvency risk.

### Likelihood Explanation
Reaching this requires only ordinary, unprivileged actions available to any principal: multiple market operations touching the same asset within a single block (e.g., a deposit/redeem followed by a borrow, repay, or liquidation call, or an oracle-price-dependent action) — no DAO action, oracle-publisher compromise, or flashloan trickery is needed. The desync window is bounded to one block, but Stacks blocks can contain several unprivileged transactions, so the precondition is realistic though narrow.

### Recommendation
Do not treat the `index-cache` hit as universally safe for all callers within a block. Either (a) invalidate/refresh the cache entry for an asset whenever any market-mediated vault-mutating call (`vault-deposit`, `vault-redeem`, `vault-system-borrow`, `vault-system-repay`, `vault-socialize-debt`) touches that asset in the same block, or (b) route all vault-mutating calls through `accrue-and-cache`/`vault-accrue` first so the cached value is always refreshed immediately before any state-changing operation, guaranteeing later cache hits in the same block reflect the vault's latest accrual.

### Proof of Concept
1. In block N, an unprivileged user (or a bot on behalf of one) triggers any market operation that calls `accrue-and-cache` for asset `aid` (e.g., a health check as part of a borrow), populating `index-cache` with `{timestamp: stacks-block-time, aid}` → `{index, lindex}` from the vault's state at that moment [1](#0-0) .
2. Still within block N, a second unprivileged transaction calls `vault-deposit`/`vault-redeem` directly on the same `aid`'s vault, which internally accrues and advances the vault's true index/lindex, bypassing `accrue-and-cache` [3](#0-2) .
3. A third transaction in block N (borrow, repay, or a ztoken-collateral valuation) calls `accrue-and-cache` for the same `aid`; because a cache entry already exists for `{stacks-block-time, aid}`, it returns the stale pre-step-2 index instead of the vault's now-current index [4](#0-3) .
4. Debt/collateral valuation for that third transaction is computed against the stale index, mispricing the position relative to the vault's true state for the rest of block N.

Note: I could not, within the available tool budget, directly confirm the exact internal accrual trigger inside the vault contracts (e.g., `v0-vault-stx`) on every `deposit`/`redeem`/`borrow`/`repay` call — this is inferred from the vault's interest-rate/index data vars (`points-ir`, `total-borrowed`, `principal-scaled`) observed in the vault contracts and the general vault design pattern. Confirming this precisely would require reading the vault contract bodies in full.

```text
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```
