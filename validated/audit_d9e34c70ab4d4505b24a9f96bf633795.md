### Title
Nep245/Imt protocol fee bypassed by fragmenting a diff into 1-unit `TokenDiff` intents - ([File: contracts/defuse/core/src/intents/token_diff.rs])

### Summary
`TokenDiff::token_fee` waives the protocol fee whenever the `amount` parameter it receives is `<= 1` for `Nep171`, `Nep245`, and `Imt` token types. Because the fee is computed per-`TokenDiff` intent (using only that single intent's `delta`), an unprivileged signer can split one large `Nep245`/`Imt` position (e.g. 1000 units) into many separate `TokenDiff` intents inside a single signed `MultiPayload`, each moving exactly 1 unit, forcing every fee computation to hit the `amount <= 1` waiver arm and driving total collected fees to zero.

### Finding Description
The binding that should hold is: `fees_collected[T] == Pips::fee_ceil(protocol_fee, sum(|negative deltas of T executed by the signer in the batch|))`.

The actual code computes fees strictly per intent, per call to `TokenDiff::execute_intent`: [1](#0-0) 

and the fee-rate function itself: [2](#0-1) 

For a single `TokenDiff` intent with `diff = {T: -1000}` on a `Nep245`/`Imt` token, `token_fee(T, 1000, fee)` falls into the `amount > 1` arm and returns `fee`, so `fee.fee_ceil(1000) > 0` when `fee != Pips::ZERO`. If the same signer instead submits 1000 `TokenDiff` intents inside one `DefuseIntents`/`MultiPayload`, each with `diff = {T: -1}`, then each call is `token_fee(T, 1, fee)`, which matches the `TokenIdType::Nep171 | TokenIdType::Nep245 | TokenIdType::Imt` arm and returns `Pips::ZERO` unconditionally — regardless of `fee`. Summed over 1000 such intents, `fees_collected[T] == 0`, not `fee.fee_ceil(1000)`.

`DefuseIntents` executes an arbitrary `Vec<Intent>` sequentially under one signature/nonce, so an attacker fully controls how many `TokenDiff` intents to include and how to split deltas across them: [3](#0-2) 

No aggregation across intents (by token, by signer, or by batch) is performed anywhere in `execute_intent`; each `TokenDiff` independently debits `signer_id`'s own balance via `internal_apply_deltas` and independently computes and credits its own fee share to `fee_collector`. None of the listed guards (`MultiPayload::verify`, nonce checks, `Lock`, `TransferMatcher::finalize`, `assert_one_yocto`, role guards) constrain the granularity of `TokenDiff.diff` map entries or the number of `TokenDiff` intents in a batch, so nothing prevents this fragmentation.

### Impact Explanation
`fee_collector`'s expected fee revenue on `Nep245`/`Imt` trades can be reduced to zero by any signer simply by splitting their trade into unit-sized `TokenDiff` legs inside one signed payload, instead of one one aggregate diff. This is a direct instance of the "protocol fees bypassed" Critical category: value (fee revenue) that should be credited to `fee_collector` is never collected, for every batch the attacker constructs this way. It is fully repeatable across accounts, across any `Nep245`/`Imt` token, and across every batch the attacker submits — there is no per-account or per-token limit on how many times this can be exploited.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's control: hold any positive `Nep245`/`Imt` balance in the Verifier, and a nonzero protocol `fee` (the deployment default). The attacker needs no special role, only the ability to construct and sign a `MultiPayload` containing many `TokenDiff` intents (all under one signature/nonce as permitted by `DefuseIntents.intents: Vec<Intent>`). The only cost is proportionally larger payload/gas for more intents, which is explicitly out of scope as a DoS/gas concern but does not prevent the fee bypass itself from occurring at smaller scales (e.g., splitting a 100-unit balance into 100 legs is trivial). This is deterministic and reproducible on every call, not probabilistic.

### Recommendation
Compute the `Nep245`/`Imt`/`Nep171` fee-waiver decision on the aggregate magnitude of same-token negative deltas across the whole `DefuseIntents`/batch (or at minimum across the full `TokenDiff.diff` map when multiple entries target the same `token_id`), rather than per individual `TokenDiff` intent invocation. Alternatively, restrict the `amount <= 1` waiver so it only applies when the token id's underlying standard is confirmed non-fungible (i.e., true `Nep171` NFTs, or `Nep245`/`Imt` ids that are provably NFT-semantic, e.g. registered max-supply-1), rather than allowing any `Nep245`/`Imt` balance (which can be fungible) to always qualify by fragmenting deltas to size 1.

### Proof of Concept
```rust
// contracts/defuse/core/src/intents/token_diff.rs (additional #[cfg(test)] test)
#[test]
fn fee_bypass_via_fragmentation() {
    let token_id: TokenId = Nep245TokenId::new(
        "mt.near".parse::<AccountId>().unwrap(),
        "ft1".to_string(),
    ).into();
    let fee = Pips::ONE_PERCENT; // nonzero protocol fee

    // Single aggregated diff of -1000 on the same Nep245 token
    let aggregated_fee = TokenDiff::token_fee(&token_id, 1000, fee).fee_ceil(1000);
    assert!(aggregated_fee > 0, "aggregated fee must be > 0 for nonzero protocol fee");

    // Fragmented into 1000 legs of -1 each (as would happen across 1000 TokenDiff
    // intents in a single signed MultiPayload / DefuseIntents.intents)
    let fragmented_fee: u128 = (0..1000)
        .map(|_| TokenDiff::token_fee(&token_id, 1, fee).fee_ceil(1))
        .sum();

    // Binding broken: total fee collected across the batch should equal
    // fee.fee_ceil(1000), but it is 0.
    assert_eq!(fragmented_fee, 0);
    assert_ne!(fragmented_fee, aggregated_fee);
}
```
This directly exercises `TokenDiff::token_fee`/`fee_ceil` as invoked from `TokenDiff::execute_intent`'s fee-collection loop and demonstrates `fees_collected` diverging from `Pips::fee_ceil` over the full negative delta when the same economic trade is split into 1-unit legs. A full end-to-end confirmation (via `near-workspaces` sandbox asserting `fee_collector`'s on-chain balance after `execute_intents` with 1000 `TokenDiff` intents vs. one) would additionally validate `internal_add_balance` behavior, but is not required to prove the fee-rate divergence, which is deterministic and lives entirely in `token_fee`.
