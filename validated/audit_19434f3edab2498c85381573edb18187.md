### Title
`pallet-assets::finish_destroy` permanently locks the asset owner's reserved deposit if the configured `CallbackHandle::destroyed` hook fails - ([File: substrate/frame/assets/src/functions.rs])

### Summary
`pallet-assets` gates the return of a reserved `AssetDeposit` (and metadata deposit) on an external hook, `T::CallbackHandle::destroyed(&id)`. If that hook is broken or misconfigured (returns an error unconditionally, panics-avoided but consistently errors, or has a latent bug), `finish_destroy` can never succeed, and the owner's reserved balance is locked forever with no bypass or emergency-exit path. This mirrors the reported class of bug: closing a position/destroying an asset depends on an external hook, and a broken hook blocks users from recovering funds they are otherwise entitled to.

### Finding Description
`do_finish_destroy` unconditionally requires the configured callback to succeed before it will unreserve the owner's deposit: [1](#0-0) 

```
pub(super) fn do_finish_destroy(id: T::AssetId) -> DispatchResult {
    Asset::<T, I>::try_mutate_exists(id.clone(), |maybe_details| -> Result<(), DispatchError> {
        let details = maybe_details.take().ok_or(Error::<T, I>::Unknown)?;
        ensure!(details.status == AssetStatus::Destroying, Error::<T, I>::IncorrectStatus);
        ensure!(details.accounts == 0, Error::<T, I>::InUse);
        ensure!(details.approvals == 0, Error::<T, I>::InUse);
        ensure!(T::CallbackHandle::destroyed(&id).is_ok(), Error::<T, I>::CallbackFailed);

        let metadata = Metadata::<T, I>::take(&id);
        T::Currency::unreserve(
            &details.owner,
            details.deposit.saturating_add(metadata.deposit),
        );
        ...
```

The `ensure!(... .is_ok() ..., CallbackFailed)` line means the deposit unreserve logic that follows is unreachable unless the external `CallbackHandle::destroyed` implementation returns `Ok(())`. This is confirmed directly by the pallet's own test suite: [2](#0-1) 

The test explicitly shows that once `AssetsCallbackHandle::set_return_error()` is active, `start_destroy`, `destroy_accounts`, and `destroy_approvals` all succeed (draining accounts/approvals) but `finish_destroy` fails permanently with `CallbackFailed` — leaving the asset stuck in the `Destroying` state and the owner's `AssetDeposit` + metadata deposit permanently reserved, with no other call path in the pallet to reclaim it.

This differs structurally from the "callback failure on `create`" case (which is fully reversible via the enclosing transaction because nothing has been committed yet) — `finish_destroy`'s failure occurs *after* `start_destroy`, `destroy_accounts`, and `destroy_approvals` have already been dispatched as separate, already-committed extrinsics. There is no way to unwind those prior steps or bypass the hook; the only path forward requires the hook to eventually return `Ok(())`.

`T::CallbackHandle` is a runtime-supplied associated type (configured per-runtime, e.g. in asset-hub runtimes and other production configs found via `CallbackHandle` bindings across `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs`, `asset-hub-rococo/src/lib.rs`, `substrate/bin/node/runtime/src/lib.rs`, etc.). This is an ordinary runtime-integration surface, not a privileged/governance actor — if the hook implementation has a bug (e.g., an integration with `nft-fractionalization` or a foreign-asset precompile registry that reverts under certain state, or simply an implementation defect), any user who has legitimately reserved a deposit for an asset class has no recourse to reclaim those funds.

### Impact Explanation
This is a permanent user-fund lock: the `AssetDeposit` (and any metadata deposit) reserved by the asset owner is un-refundable as long as the external hook fails, with no governance/root override, no forced-unreserve extrinsic, and no alternate call path in `pallet-assets` to complete `finish_destroy` without the hook succeeding. This matches the "permanent user-fund … lock" criterion in the impact gate — value that should conserve and settle back to the rightful beneficiary (the asset owner reclaiming their own deposit) is instead permanently stuck due to reliance on an external hook with no emergency exit, exactly the failure mode described in the external report.

### Likelihood Explanation
Likelihood depends on the correctness of the runtime-configured `CallbackHandle` implementation, which is out of `pallet-assets`'s control. Any regression, panic-avoidance bug, or unhandled edge case in that hook (used across multiple production runtimes) would trigger this condition deterministically and irreversibly for every asset going through destruction at that time. Because `CallbackHandle` is a general extension point intended to be implemented by arbitrary pallets/runtimes (as evidenced by its use across many mock and runtime configs), the surface for an eventual broken implementation is non-trivial, and the pallet itself provides no defensive fallback.

### Recommendation
Add an unreserve/emergency-exit path in `pallet-assets` that does not depend on `CallbackHandle::destroyed` succeeding — for example, allow `finish_destroy` (or a dedicated privileged/no-permission-required call) to unreserve the owner's deposit and clean up storage after all accounts/approvals are destroyed even if the callback fails, while still emitting a distinct event/warning about the callback failure so integrators can detect and fix the hook out-of-band. Alternatively, decouple the callback invocation from the deposit-refund critical path entirely (e.g., emit best-effort callback notification without gating fund release on its result).

### Proof of Concept
Based on the existing test `asset_create_and_destroy_is_reverted_if_callback_fails` in `substrate/frame/assets/src/tests.rs` (lines 2092-2116):
1. Configure `AssetsCallbackHandle::set_return_ok()`; call `Assets::create` — asset created, deposit reserved.
2. Configure `AssetsCallbackHandle::set_return_error()` (simulating a broken hook in a real runtime).
3. Call `Assets::start_destroy`, `Assets::destroy_accounts`, `Assets::destroy_approvals` — all succeed, fully draining the asset's accounts/approvals.
4. Call `Assets::finish_destroy` — fails with `Error::<Test>::CallbackFailed`.
5. Because the hook remains broken (by hypothesis, indefinitely), step 4 can never succeed: `Asset::<T,I>` storage entry remains in `Destroying` state forever, and the owner's `AssetDeposit`/metadata deposit remains reserved/locked with no other extrinsic capable of releasing it. [2](#0-1)

#[test]
fn asset_create_and_destroy_is_reverted_if_callback_fails() {
	build_and_execute(|| {
		// Asset creation fails due to callback failure
		AssetsCallbackHandle::set_return_error();
		Balances::make_free_balance_be(&1, 100);
		assert_noop!(
			Assets::create(RuntimeOrigin::signed(1), 0, 1, 1),
			Error::<Test>::CallbackFailed
		);

		// Callback succeeds, so asset creation succeeds
		AssetsCallbackHandle::set_return_ok();
		assert_ok!(Assets::create(RuntimeOrigin::signed(1), 0, 1, 1));

		// Asset destroy should fail due to callback failure
		AssetsCallbackHandle::set_return_error();
		assert_ok!(Assets::start_destroy(RuntimeOrigin::signed(1), 0));
		assert_ok!(Assets::destroy_accounts(RuntimeOrigin::signed(1), 0));
		assert_ok!(Assets::destroy_approvals(RuntimeOrigin::signed(1), 0));
		assert_noop!(
			Assets::finish_destroy(RuntimeOrigin::signed(1), 0),
			Error::<Test>::CallbackFailed
		);
	});
