### Title
`VesperGateway.deposit` bricked for vTokens whose underlying reverts on zero-value approvals - (File: contracts/VesperGateway.sol)

### Summary
`VesperGateway.deposit` unconditionally calls `safeApprove(spender, 0)` before setting the real allowance for both the vToken's underlying asset and the vToken itself. For ERC-20 tokens that revert inside `approve` when `value == 0` (e.g. BNB `0xB8c77482e45F1F44dE1745F52C74426C631bDD52`), every call to `deposit` reverts, permanently blocking that collateral path.

### Finding Description
`deposit(IPool pool_, IVPool vToken_, uint256 amount_)` is a public, unprivileged entry point gated only by `_poolRegistry.isPoolRegistered`. After pulling the underlying via `safeTransferFrom`, it executes:

```solidity
_underlying.safeApprove(address(vToken_), 0);
_underlying.safeApprove(address(vToken_), amount_);
```

at `contracts/VesperGateway.sol:54-55`, and again for the vToken at lines 62-63. `safeApprove` in `contracts/dependencies/openzeppelin/token/ERC20/utils/SafeERC20.sol:44-57` forwards to `token.approve(spender, 0)` via `_callOptionalReturn`, which propagates any revert from the token. Therefore, if the vToken's underlying (or the vToken itself) is a "revert-on-zero-approval" token, `deposit` always reverts before `vToken_.deposit(amount_)` is reached.

The zero-approval reset is unnecessary here: the gateway does not retain a standing allowance between calls in the deposit path (allowance is set to exactly `amount_` and consumed by `vToken_.deposit`), so `safeApprove(spender, 0)` adds no safety for these tokens — it only guarantees the revert.

### Impact Explanation
Liveness break: for any registered Pool collateralized by a vToken whose underlying reverts on zero approvals (BNB and other tokens listed in the weird-erc20 "revert on zero value approvals" class), `VesperGateway.deposit` is permanently unusable. Users cannot onboard that collateral through the gateway at all — a permanent freezing/unavailability of the deposit path for that asset, matching the accepted impact class of the source finding.

### Likelihood Explanation
Likelihood depends on whether governance registers a Pool whose vToken wraps such a token; no attacker action is required to trigger it — any user calling `deposit` hits the revert deterministically. Vesper pools exist for a wide range of underlyings, and BNB is a canonical example. No modifier, reentrancy guard, or SynthContext check prevents the revert; it occurs inside the plain `safeApprove` call.

### Recommendation
Skip the zero-approval reset and use `safeIncreaseAllowance`, or set the allowance once with `safeApprove(spender, amount_)` since prior allowance is always zero after a successful `vToken_.deposit`. Alternatively use `forceApprove`-style logic that tolerates tokens reverting on `approve(0)`.

### Proof of Concept
On a Hardhat/Foundry mainnet fork:

1. Deploy a mock ERC-20 that reverts when `approve(spender, 0)` is called (replicating BNB's `require(_value > 0)` in approve), or use the real BNB token at `0xB8c77482e45F1F44dE1745F52C74426C631bDD52`.
2. Deploy a minimal `VPool`-compatible mock (`vToken_.token()` returns that ERC-20; `deposit` pulls allowance via `transferFrom`), and register a Pool in `PoolRegistry` whose `depositTokenOf(vToken)` returns a `DepositToken`.
3. Call `vesperGateway.deposit(pool, vToken, amount)` after `approve`ing the gateway.
4. The call reverts at `VesperGateway.sol:54` inside `safeApprove(vToken, 0)` before `vToken_.deposit` executes — reproducible on every invocation.
