### Title
ExtractHooks() delegates custom_hooks tar extraction to the external `tar` binary with no symlink-escape validation, unlike Gitaly's own symlink-aware tar walker used elsewhere - (File: internal/gitaly/repoutil/custom_hooks.go)

### Summary
`ExtractHooks()` extracts attacker-supplied tar data (from `SetCustomHooks`/`RestoreCustomHooks`) by shelling out to the system `tar` binary with no post-extraction validation of symlink targets, hard links, or path traversal. This is inconsistent with `extractTarToDirectory` in `internal/gitaly/service/repository/replicate.go`, which implements explicit symlink/hard-link boundary checks against exactly this class of attack (a symlink entry followed by a data entry written "through" it).

### Finding Description
`ExtractHooks` builds the command `tar -xf - -C <path> --strip-components N custom_hooks` and pipes attacker-controlled tar bytes directly to it, relying entirely on whatever `tar` binary is installed on the host/container to safely handle the archive contents: [1](#0-0) 

There is no inspection of tar headers (no `tar.TypeSymlink` check, no `Linkname` validation, no rejection of absolute or `..`-escaping targets) before or after invoking the external binary. Compare this to `extractTarToDirectory`, which uses Go's own `archive/tar` reader and explicitly validates that both symlink and hard-link targets resolve within the target directory before creating them, rejecting absolute symlinks and any relative target that escapes the extraction root: [2](#0-1) 

That dedicated safeguard (and its test `TestExtractTarToDirectory_SymlinkValidation`) demonstrates the Gitaly team is aware of the "symlink entry followed by data-through-symlink" escape pattern (the exact scenario historically tracked as CVE-2016-6321 in libarchive/bsdtar, and previously present in older GNU tar releases before their fix). `ExtractHooks`, however, has no equivalent protection and no test coverage for symlink entries at all — the existing `TestExtractHooks` table only exercises regular files/directories, and `TestGetCustomHooks_symlink` only checks that `GetCustomHooks` (creation side) preserves a symlink for the `custom_hooks` directory itself, not extraction-time defenses: [3](#0-2) 

The attacker fully controls the tar stream via `SetCustomHooks`/`RestoreCustomHooks` RPCs (or `CreateRepositoryFromBundle`/import flows that call `SetCustomHooks`), so they can craft: (1) a `tar.TypeSymlink` entry named `custom_hooks/evil` with `Linkname` pointing outside the extraction root (absolute path or `../..` escape), followed by (2) a regular-file entry named `custom_hooks/evil/payload`. Whether this succeeds in escaping is entirely dependent on the semantics of whatever `tar` binary happens to be installed in the Gitaly runtime environment — behavior that Gitaly itself does not control, verify, or pin.

### Impact Explanation
If the deployed `tar` implementation does not defend against symlink-directory-component escapes (as was historically true for libarchive/bsdtar prior to its CVE-2016-6321 fix, and could recur in minimal/alternative container base images), an attacker-controlled hooks tarball can write files outside the intended temporary extraction directory. Since `SetCustomHooks` later performs `os.Rename` of `custom_hooks` into the target repository and votes/writes based on directory contents, and the extraction directory itself is a fresh Gitaly-controlled tempdir, the practical escape target is limited to wherever the crafted symlink points on the host filesystem the `tar` process can write to — potentially another repository's `custom_hooks` directory or other Gitaly-writable paths — leading to arbitrary hook file planting and RCE via subsequent hook execution on push. This matches the GitLab bounty impact class of "archive extraction escape" / cross-repository object access / RCE via hook execution.

### Likelihood Explanation
Exploitability is entirely conditional on the specific `tar` binary resolved on `$PATH` in the Gitaly runtime supporting (or failing to block) the symlink-follow-through pattern; GNU tar as shipped in GitLab's default Debian/Ubuntu-based Omnibus and container images has included this specific protection since 2007 (post CVE-2007-4131), making default GitLab deployments unlikely to be exploitable today. The risk is real only under non-default/alternate tar implementations (e.g., minimal Alpine/busybox images or libarchive-based `tar` prior to its own fix), which falls outside "default configuration" as scoped by the audit rules, and no code in this repository demonstrates a currently-installed vulnerable tar version.

### Recommendation
Replace the external `tar` binary invocation in `ExtractHooks` with the same Go-native, symlink-aware extraction logic already implemented in `extractTarToDirectory` (or a shared helper), performing explicit `tar.TypeSymlink`/`tar.TypeLink` target-boundary validation before writing, independent of the host's `tar` binary behavior. At minimum, reject any symlink entries within `custom_hooks/` outright, since custom hooks tarballs are not expected to legitimately contain symlinks pointing outside the archive.

### Proof of Concept
```go
func TestExtractHooks_SymlinkEscape(t *testing.T) {
    ctx := testhelper.Context(t)
    tmpDir := t.TempDir()
    outsideDir := t.TempDir() // simulates a location outside the extraction root

    var buf bytes.Buffer
    w := tar.NewWriter(&buf)
    // 1. Symlink escaping the extraction root
    require.NoError(t, w.WriteHeader(&tar.Header{
        Name:     "custom_hooks/evil",
        Typeflag: tar.TypeSymlink,
        Linkname: outsideDir, // or "../../../../tmp" for a relative escape
    }))
    // 2. Regular file written "through" the symlink
    content := []byte("planted-payload")
    require.NoError(t, w.WriteHeader(&tar.Header{
        Name: "custom_hooks/evil/payload", Size: int64(len(content)), Mode: 0o755,
    }))
    _, err := w.Write(content)
    require.NoError(t, err)
    require.NoError(t, w.Close())

    err = ExtractHooks(ctx, testhelper.NewLogger(t), &buf, tmpDir, false)
    require.NoError(t, err)

    // Assertion: on a symlink-vulnerable tar implementation, this file
    // would land in outsideDir rather than under tmpDir.
    _, statErr := os.Lstat(filepath.Join(outsideDir, "payload"))
    require.True(t, os.IsNotExist(statErr), "payload must not escape extraction root")
}
```
Run this test against Gitaly's configured `tar` binary in the target deployment environment (varying between GNU tar and BSD/libarchive tar) to confirm whether the escape succeeds, since the outcome is determined by the external binary rather than by any check in `ExtractHooks` itself.

func ExtractHooks(ctx context.Context, logger log.Logger, reader io.Reader, path string, stripPrefix bool) error {
	// GNU tar does not accept an empty file as a valid tar archive and produces
	// an error. Since an empty hooks tar is symbolic of a repository having no
	// hooks, the reader is peeked to check if there is any data present.
	buf := bufio.NewReader(reader)
	if _, err := buf.Peek(1); errors.Is(err, io.EOF) {
		return nil
	}

	stripComponents := "0"
	if stripPrefix {
		stripComponents = "1"
	}

	cmdArgs := []string{"-xf", "-", "-C", path, "--strip-components", stripComponents, CustomHooksDir}

	var stderrBuilder strings.Builder
	cmd, err := command.New(ctx, logger, append([]string{"tar"}, cmdArgs...),
		command.WithStdin(buf),
		command.WithStderr(&stderrBuilder))
	if err != nil {
		return fmt.Errorf("executing tar command: %w", err)
	}
