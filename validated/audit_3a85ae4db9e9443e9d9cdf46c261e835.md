### Title
`try_forward` admits oversized receipts via clamped `admission_gas` but debits the full unclamped `gas`, allowing head-of-line starvation of the `allowed_shard_outgoing_gas` budget - (File: runtime/runtime/src/congestion_control.rs)

### Finding Description
When a shard is fully congested (`congestion_level == 1.0`), `CongestionControl::outgoing_gas_limit` grants only the deterministically-chosen `allowed_shard` a small forwarding budget, `self.config.allowed_shard_outgoing_gas`, while all other shards get `Gas::ZERO`: [1](#0-0) 

This budget is used to seed `forward_limit.gas` in the `outgoing_limit` map consumed by `ReceiptSinkV2::try_forward`. In `try_forward`, when `ProtocolFeature::ClampOutgoingGasAdmission` is enabled, the *admission check* uses a clamped value: [2](#0-1) 

but the actual budget decrement after admission uses the full, unclamped `gas` of the receipt: [3](#0-2) 

Because the admission test is `forward_limit.gas >= admission_gas` and `admission_gas = gas.min(allowed_shard_outgoing_gas)`, any receipt with `gas > allowed_shard_outgoing_gas` is treated identically to one with `gas == allowed_shard_outgoing_gas` for admission purposes — both produce `admission_gas == allowed_shard_outgoing_gas`, which passes as long as `forward_limit.gas >= allowed_shard_outgoing_gas` (true at the start of the round). However, the subsequent `forward_limit.gas.saturating_sub(gas)` subtracts the receipt's *real* congestion gas, which can be many times larger than `allowed_shard_outgoing_gas`, saturating `forward_limit.gas` to zero in one step.

`forward_from_buffer_to_shard` iterates the buffer in FIFO order and `break`s on the first `NotForwarded` result: [4](#0-3) 

so once the budget is zeroed by one oversized receipt, every subsequent receipt in that shard's buffer — regardless of how small — is denied forwarding for the rest of the chunk (and, since the buffer is FIFO with no reordering, for as many subsequent chunks as it takes to drain).

An attacker whose account happens to reside in the deterministically-computed `allowed_shard` for a given block height can submit a single `FunctionCall` receipt with attached gas far exceeding `allowed_shard_outgoing_gas` (e.g., near `max_total_prepaid_gas`, ~300 Tgas, versus a much smaller `allowed_shard_outgoing_gas`), targeting the fully-congested receiver shard, and consume the entire round's forwarding allowance for that shard pair while only being "charged" `allowed_shard_outgoing_gas` worth of admission credit.

None of the existing checks (signature, nonce, access key, gas metering, size limits) prevent this: the receipt is a normal, valid `FunctionCall` receipt with legitimately attached gas; the flaw is purely in the accounting logic that separates admission-gas from debited-gas.

### Impact Explanation
This degrades liveness/fairness of cross-shard receipt forwarding during full congestion: legitimate users whose receipts are queued behind the attacker's oversized receipt in the same shard-to-shard buffer are denied forwarding for that chunk, and due to FIFO head-of-line blocking, potentially for further chunks if the attacker repeats the attack each round they occupy the allowed shard. This is a liveness/DoS-style impact (temporary receipt-forwarding starvation) rather than fund theft or consensus divergence — it does not corrupt state, but it can indefinitely delay execution of otherwise-valid receipts to a congested shard, which falls under a liveness/availability degradation category.

### Likelihood Explanation
Preconditions are non-trivial: the target shard must be fully congested (`congestion_level == 1.0`), and the attacker's account must be located in the specific shard chosen as `allowed_shard` for that block height, which changes over time. Given that, the attack cost is a single normal transaction (funding a large attached-gas `FunctionCall`); it is easily repeatable whenever the attacker controls (or can deploy) an account in whatever shard becomes the allowed shard next, and the target shard remains fully congested (an attacker can plausibly help sustain congestion). This is feasible for any unprivileged user, no special access required, but is gated by the congestion + allowed-shard-membership precondition.

### Recommendation
Make the debited gas amount consistent with the admitted amount, or admit based on the real cost. Specifically, in `try_forward`, either (a) use the same clamped value for both the admission check and the decrement (i.e., cap the actual gas debited per receipt at `allowed_shard_outgoing_gas`, and correspondingly account for the "excess" gas elsewhere, e.g. by borrowing against future rounds), or (b) require `forward_limit.gas >= gas` (the real gas) rather than `>= admission_gas` when clamping is enabled, so an oversized receipt is not admitted at all unless the full budget covers it. Additionally, consider not `break`-ing the FIFO loop unconditionally on `NotForwarded`, or bounding the maximum per-receipt gas that can be forwarded via the allowed-shard channel, to avoid a single receipt's gas monopolizing the round budget and blocking the queue.

### Proof of Concept
1. In `runtime/runtime/src/tests/apply.rs` (or a dedicated unit test alongside `try_forward`), construct an `ApplyState` with `ProtocolFeature::ClampOutgoingGasAdmission` enabled and `congestion_control_config.allowed_shard_outgoing_gas` set to a small value (e.g., 1 Tgas).
2. Seed `outgoing_limit` for the target shard with `OutgoingLimit { gas: allowed_shard_outgoing_gas, size: <large> }` (simulating `CongestionControl::outgoing_gas_limit` output for the allowed shard under full congestion).
3. Call `ReceiptSinkV2::try_forward` (or exercise `forward_from_buffer_to_shard` with a buffer containing two receipts) with:
   - Receipt A: congestion gas = 300 Tgas (>> allowed_shard_outgoing_gas), targeting the congested shard.
   - Receipt B: congestion gas = 0.5 Tgas (comfortably under `allowed_shard_outgoing_gas` alone), also targeting the congested shard, placed after A in FIFO order.
4. Assert Receipt A returns `ReceiptForwarding::Forwarded` and that `forward_limit.gas == Gas::ZERO` afterward (via `saturating_sub` underflow-to-zero).
5. Assert Receipt B (processed next in `forward_from_buffer_to_shard`) returns `ReceiptForwarding::NotForwarded`, despite `0.5 Tgas < allowed_shard_outgoing_gas`, demonstrating starvation caused solely by Receipt A's oversized real gas cost combined with the clamped admission check.
