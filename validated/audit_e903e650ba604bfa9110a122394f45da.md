### Title
Stale object-pool membership metadata not cleared on `DisconnectGitAlternates`, enabling cross-repository pool-object exposure - ([File: internal/gitaly/service/objectpool/alternates.go])

### Summary
`DisconnectGitAlternates` is the Gitaly RPC that severs a repository ("pool member") from an object pool — the functional analog of Hats Protocol's `unlinkTopHatFromTree()`. Gitaly maintains a separate, persistent bookkeeping table of pool membership (`pool_members`/`pools` in the `relational.PoolStore`, exposed through `relational.ObjectPoolStateManager`) with an explicit `NotifyUnlinkRepository` hook whose sole purpose is to delete a member's membership record when it disconnects. However, the actual `DisconnectGitAlternates` handler never calls it, so the persisted membership record survives the unlink, exactly mirroring the H-9 pattern of a stale, unrevoked state record surviving a "disconnect" operation.

### Finding Description
The `ObjectPoolStateManager` interface defines the intended lifecycle hooks for the pool-membership store: [1](#0-0) 

`NotifyUnlinkRepository` deletes the corresponding row from the `pool_members` table via `PoolStore.RemoveMember`: [2](#0-1) 

This `objectPoolStateManager` is wired into the `ObjectPoolService` server struct as a dependency, implying it is meant to be consulted/updated during pool lifecycle RPCs: [3](#0-2) 

But `DisconnectGitAlternates` — the RPC that actually performs the unlink (hard-linking pool objects into the member and removing `objects/info/alternates`) — never references `objectPoolStateManager` at all: [4](#0-3) 

A repository-wide search confirms `NotifyLinkRepository`/`NotifyUnlinkRepository` are referenced only in `state_manager.go`, its test file, `dependencies.go`, and `serve.go`/`server.go` (dependency wiring) — never inside `link.go`, `create.go`, `delete.go`, or `alternates.go`, the files that implement the actual `LinkRepositoryToObjectPool`, `CreateObjectPool`, `DeleteObjectPool`, and `DisconnectGitAlternates` RPC handlers. This means the membership store is populated entirely by an out-of-band disk-scanning tool (`gitaly pool`/`praefect pool` CLI subcommands, see `internal/cli/gitaly/subcmd_pool_test.go` and `internal/cli/praefect/subcmd_pool.go`) rather than being kept consistent with the live RPC-driven object-pool lifecycle: [5](#0-4) 

Because a real disconnect via `DisconnectGitAlternates` performs no corresponding `RemoveMember`/`NotifyUnlinkRepository` call, a repository that has been fully and successfully unlinked from its pool (alternates file removed, `fsck` verified) can still show up as a pool member in `GetPoolForMember`/`ListPoolMembers` queries until the next full storage rescan runs. Any consumer (the `praefect pool`/`gitaly pool` reconciliation tooling, or a GitLab-side authorization check built on `ListPoolUpstreams`/`GetPoolForMember`) that trusts this metadata to determine object-sharing/visibility relationships between repositories will operate on a stale link — the same "unlink doesn't clear stored permission/relationship state" defect as H-9, just at the pool-membership layer instead of the Hats tree layer.

### Impact Explanation
A repository owner who disconnects from an object pool (e.g., because the fork became private, or its objects should no longer be considered part of a shared pool) reasonably expects that Gitaly's authoritative record of that relationship is gone. Instead, the stale `pool_members` row persists until an administrator re-runs the pool-scan reconciliation tool. Any downstream logic — access checks, `ListPoolUpstreams` consumers on the Rails side, or the `praefect pool` reconciler itself — that treats this table as ground truth for "is `X` part of pool `Y`" can make an authorization or object-visibility decision based on a relationship the target repository already terminated. This is a cross-repository metadata integrity issue: a formerly-shared repository can remain treated as linked to (and thus potentially exposed to or through) a pool it explicitly disconnected from.

### Likelihood Explanation
`DisconnectGitAlternates` is a mutator RPC reachable by any actor authorized to call RPCs against a repository (e.g., via ordinary GitLab project-visibility-change workflows that trigger a fork's disconnection from its pool). No special privilege beyond normal repository-mutator access is required to trigger the unlink; the omission is unconditional and 100% reproducible — the handler simply never touches `objectPoolStateManager`, so the stale record is guaranteed to persist until the periodic/administrator-invoked scan re-syncs the table.

### Recommendation
Call `s.objectPoolStateManager.NotifyUnlinkRepository(ctx, poolDiskPath, memberDiskPath)` from `DisconnectGitAlternates` (and, symmetrically, `NotifyLinkRepository`/`NotifyCreatePool`/`NotifyDeletePool` from `LinkRepositoryToObjectPool`, `CreateObjectPool`, and `DeleteObjectPool`) immediately after the on-disk operation succeeds, so the `pool_members` bookkeeping table stays consistent with the actual, live alternates-linkage state instead of relying solely on periodic disk scans.

### Proof of Concept
1. Create an object pool and link a member repository via `LinkRepositoryToObjectPool` (or the disk-scan tool records the relationship in `pool_members` after a `pool` CLI scan).
2. Confirm `GetPoolForMember(member)` returns the pool's disk path.
3. Call `DisconnectGitAlternates` on the member repository — the RPC succeeds, `objects/info/alternates` is removed, and `git fsck` passes, per the flow in [4](#0-3)  and [6](#0-5) .
4. Query `GetPoolForMember(member)` again (or run `ListPoolUpstreams`/`ListPoolMembers`) — it still returns the now-severed pool, because no `NotifyUnlinkRepository`/`RemoveMember` call was ever made, as confirmed by the absence of any such call in `alternates.go` and by the grep results showing these lifecycle notifications are never invoked from the RPC handler files (`link.go`, `create.go`, `delete.go`, `alternates.go`).

func (m *objectPoolStateManager) NotifyUnlinkRepository(ctx context.Context, poolDiskPath, memberDiskPath string) error {
	if m.poolStore == nil {
		return nil
	}

	m.mu.Lock()
	defer m.mu.Unlock()

	return m.poolStore.RemoveMember(ctx, poolDiskPath, memberDiskPath)
}

func (s *server) DisconnectGitAlternates(ctx context.Context, req *gitalypb.DisconnectGitAlternatesRequest) (*gitalypb.DisconnectGitAlternatesResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	repo := s.localRepoFactory.Build(repository)

	storageRoot, err := s.locator.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return nil, fmt.Errorf("storage by name: %w", err)
	}

	f := storage.NewNoopFS(storageRoot)
	if tx := storage.ExtractTransaction(ctx); tx != nil {
		f = tx.FS()
	}

	if err := objectpool.Disconnect(ctx, f, repo, s.logger, s.txManager); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.DisconnectGitAlternatesResponse{}, nil
}

// Disconnect disconnects the specified repository from its object pool. If the repository does not
// utilize an alternate object database, no error is returned. For repositories that depend on
// alternate objects, the following steps are performed:
//   - Alternate objects are hard-linked to the main repository.
//   - The repository's Git alternates file is backed up and object pool disconnected.
//   - A connectivity check is performed to ensure the repository is complete. If this check fails,
//     the repository is reconnected to the object pool via the backup and an error returned.
//
// This operation carries some risk. If the repository is in a broken state, it will not be restored
// until after the connectivity check completes. If Gitaly crashes before the backup is restored,
// the repository may be in a broken state until an administrator intervenes and restores the backed
// up copy of objects/info/alternates.
func Disconnect(ctx context.Context, f storage.FS, repo *localrepo.Repo, logger log.Logger, txManager transaction.Manager) error {
	repoPath, err := repo.Path(ctx)
	if err != nil {
		return err
	}

	altInfo, err := stats.AlternatesInfoForRepository(repoPath)
	if err != nil {
		return err
	}

	// If the repository does not have an alternates file or if alternate file does not contain
	// object directories, there is not an object pool repository to disconnect from and no need to
	// continue.
	if !altInfo.Exists || len(altInfo.ObjectDirectories) == 0 {
		// When a repository is not linked to any alternates, ensure the repository is consistent
		// with other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("no alternates")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on missing alternates: %w", err)
		}

		return nil
	}
