### Title
Unbounded array allocation from attacker-controlled length word in `BatchValidateSign` precompile causes uncontrolled memory allocation (`OutOfMemoryError`) - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `BatchValidateSign` precompiled contract (address reachable from any TVM `CALL`/`STATICCALL`) decodes its calldata into `DataWord[]` and then reads an attacker-controlled 32-byte word as an array *length*, immediately allocating a Java array of that size — `byte[][] bytesArray = new byte[len][]` / `byte[][] bytes32Array = new byte[len][]` — before validating that `len` is bounded or that the referenced words actually exist inside the supplied `data`. On chains/paths where the `allowTvmSelfdestructRestriction` guard is not exercised (the only place a `MAX_SIZE` bound is enforced), a single small calldata blob whose length-word is set to a large 32-bit value causes the JVM to attempt an outsized allocation, mirroring the SoundTouch `acceptNewOverlapLength` bug class from CVE-2017-9259 (untrusted length field driving an unchecked allocation that crashes the process).

### Finding Description
`extractBytesArray` and `extractBytes32Array` in `PrecompiledContracts.java` read a length directly from calldata-derived `DataWord`s and allocate arrays sized by that value with no upper bound check against `MAX_SIZE` or against the actual size of `words`: [1](#0-0) 

`BatchValidateSign.doExecute` only enforces a `MAX_SIZE` (16) cap on the `sigArraySize`/`addrArraySize` words when `VMConfig.allowTvmSelfdestructRestriction()` is active; the actual extraction calls (`extractSigArray`, `extractBytesArray`, `extractBytes32Array`) are otherwise unguarded and are invoked unconditionally for the `addresses` array regardless of that flag: [2](#0-1) 

Because `len` comes straight from `words[offset].intValueSafe()` — an attacker-fully-controlled 32-byte word in the transaction/contract-call input — a caller can craft a tiny calldata payload (few words, so `getEnergyForData` charges almost nothing) while setting the length field to a huge value (e.g. `0x7FFFFFFF`). The `new byte[len][]` allocation attempt (~16 GB for a max `int` reference array) happens *before* any bounds check against `words.length`, so the OutOfMemoryError is thrown at allocation time, not after a cheap bounds check. This is functionally identical to the SoundTouch bug: a length field taken from untrusted input drives a memory allocation with no sanity check on its magnitude.

### Impact Explanation
Although `BatchValidateSign.execute` wraps `doExecute` in a `catch (Throwable t)` so the immediate call does not propagate the error, the array allocation itself forces the JVM heap allocator to attempt a very large contiguous allocation. This can trigger `OutOfMemoryError` for the whole FullNode/SR JVM process (shared heap), induce major GC pauses, or destabilize concurrently executing transactions/threads in the same node — a transaction-triggered node-wide denial of service. Because `BatchValidateSign` is reachable by any deployed contract via `STATICCALL`, an unprivileged contract deployer/caller can repeatedly trigger this cheaply (cost is bound to `data.length`, not to the forged length field), making this a low-cost, repeatable DoS vector against block-producing/serving nodes.

### Likelihood Explanation
Likelihood is high for any contract call path where `VMConfig.allowTvmSelfdestructRestriction()` is not yet active (e.g., prior to the corresponding hard fork activation on a given network, or any deployment/test/private network running an older feature-flag state) since no other guard exists before the allocation. Even where the flag is active, the guard only checks `sigArraySize`/`addrArraySize`; it does not fully validate `offset` bounds before those checks run, so a crafted `words[1]`/`words[2]` offset could still index out of the actual `words` array on the guard-check line itself (`words[words[1].intValueSafe() / WORD_SIZE]`), which throws an `ArrayIndexOutOfBoundsException` rather than the huge-allocation OOM — this is a separate, lower-severity failure mode. The primary allocation-DoS finding requires only that the restriction flag be inactive, which is a realistic historical/deployment state for this feature-gated code path.

### Recommendation
- Validate `len` in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` against a hard maximum (e.g., `MAX_SIZE`) and against the actual bounds of `words` *before* allocating any array, unconditionally (not gated behind `allowTvmSelfdestructRestriction`).
- Reject with `Pair.of(false, EMPTY_BYTE_ARRAY)` (or `DATA_FALSE`) as soon as `len < 0 || len > MAX_SIZE || offset + len >= words.length`.
- Make the `MAX_SIZE` bound check unconditional (drop the feature-flag gate) so all networks/configurations are protected regardless of hard-fork activation state.

### Proof of Concept
1. Construct calldata for `BatchValidateSign` (or any precompile relying on `extractBytesArray`/`extractBytes32Array`) with only the minimal ABI header words required to pass `getEnergyForData` cheaply.
2. Set the word at the position referenced as the array-length field (`words[2]` pointer target, used for `addresses = extractBytes32Array(words, words[2].intValueSafe()/32)`) to `0x7FFFFFFF`.
3. Deploy a trivial contract that performs a `STATICCALL`/`CALL` to the `BatchValidateSign` precompiled address with this crafted calldata and submit the triggering transaction.
4. Observe the executing node attempt `new byte[0x7FFFFFFF][]`, causing `OutOfMemoryError` and degraded/failed processing on the node handling the call (repeat to amplify effect across nodes serving RPC/energy-cheap calls).

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
