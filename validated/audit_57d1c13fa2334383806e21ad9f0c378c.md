### Title
`Wallet.getMarketOrderById` throws instead of returning null/empty on missing order, breaking the API's expected "not-found" contract - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
Analogous to the `UniswapAnchoredView.getUnderlyingPrice` bug (an interface that should degrade gracefully to a default/zero value on missing data but instead reverts), `Wallet.getMarketOrderById` in java-tron deviates from the established query-API convention of returning `null`/empty on a missing record, and instead throws an unchecked `IllegalStateException` that propagates to callers as a hard error.

### Finding Description
Every other Wallet market-lookup method follows a "return null when not found" contract that HTTP/gRPC handlers rely on to render an empty response (`{}` or an empty message) rather than an error, e.g. `getExchangeById` [1](#0-0)  and `getMarketOrderByAccount`'s outer null-check [2](#0-1) .

`getMarketOrderById`, however, catches the internal `ItemNotFoundException` and rethrows it as an unchecked `IllegalStateException("order not found in store")` instead of returning `null`: [3](#0-2) 

The same anti-pattern also exists inside the per-order lambda of `getMarketOrderByAccount`, which throws `IllegalStateException` from within a `forEach` when any order id referenced by the account capsule cannot be found in the order store: [4](#0-3) 

This is reachable directly by any anonymous API client through both the HTTP and gRPC query surfaces:
- HTTP: `GetMarketOrderByIdServlet.doGet`/`doPost` call `wallet.getMarketOrderById(...)` expecting either a non-null `MarketOrder` or `null` (to print `"{}"`), but instead receive an exception that is turned into an HTTP error response via `Util.processError` [5](#0-4) 
- gRPC: `RpcApiService.getMarketOrderById` and `getMarketOrderByAccount` wrap the call in try/catch and call `responseObserver.onError(getRunTimeException(e))` [6](#0-5) 

### Impact Explanation
Although both HTTP and gRPC layers catch the exception (preventing a full node crash), the deviation means:
1. The public query API returns an error status for a routine "not found" condition instead of the empty/`null` response that every other lookup endpoint in the same API family returns for identical semantics (record absent). This is an interface/contract violation identical in nature to the reported Compound bug — the caller cannot distinguish "order id malformed", "internal store corruption", and "order simply doesn't exist" because all surface as generic error responses instead of the documented empty result.
2. Any external service, wallet, or exchange integration that calls `getMarketOrderById`/`getMarketOrderByAccount` and expects a benign empty response (as it would from `getExchangeById`, `getMarketPriceByPair`, etc.) will instead receive unhandled error responses, which can break automated integrations built against this API's otherwise-consistent "null/empty on missing" convention, and could be leveraged to probe internal error message strings ("order not found in store") not normally exposed by other endpoints.

This does not meet the higher bar of theft of funds, unauthorized account operation, or node crash — the impact is confined to API contract inconsistency and information/error leakage on the query path, which is comparable in severity to the original Compound finding.

### Likelihood Explanation
Trivial to trigger: any anonymous client can query `/wallet/getmarketorderbyid` or the gRPC `getMarketOrderById`/`getMarketOrderByAccount` methods with a non-existent (but well-formed) order ID or account address, since these are unauthenticated, unprivileged read-only query endpoints.

### Recommendation
Modify `Wallet.getMarketOrderById` and the per-order loop in `getMarketOrderByAccount` to catch `ItemNotFoundException` and return `null` (or skip the missing entry) rather than rethrowing as `IllegalStateException`, matching the convention used by `getExchangeById` and other Wallet query methods. Add unit tests (in `WalletMockTest`/`HttpServletTest`) verifying that querying with a non-existent order ID returns an empty/`null` result rather than an error.

### Proof of Concept
1. Start a full node with the HTTP API enabled.
2. Send `GET /wallet/getmarketorderbyid?value=<hex of a well-formed but non-existent 32-byte order id>`.
3. Observe that instead of an HTTP 200 response with body `{}` (the pattern used by `/wallet/getexchangebyid` for a missing exchange), the servlet returns an error response produced from `IllegalStateException("order not found in store")`, confirmed by the code path in `Wallet.getMarketOrderById` [7](#0-6)  and `GetMarketOrderByIdServlet` [8](#0-7) .
