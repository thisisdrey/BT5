### Title
Division-before-multiplication precision loss in `MortgageService.computeReward` can zero out small stakers' vote rewards - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes each staker's share of a witness's cycle reward by first dividing `userVote` by `totalVote` and only then multiplying by `totalReward`, mirroring exactly the `Maths.wdiv(interestEarned_, totalInterestEarnedInPeriod)` then `wmul(..., totalBurnedInPeriod)` pattern flagged in the referenced Ajna report.

### Finding Description
In the legacy ("old") reward algorithm path used for cycles prior to `newRewardAlgorithmEffectiveCycle`, rewards are computed as: [1](#0-0) 

```java
private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
  long reward = 0;
  for (Pair<byte[], Long> vote : votes) {
    ...
    long userVote = vote.getValue();
    double voteRate = (double) userVote / totalVote;
    reward += voteRate * totalReward;
  }
  return reward;
}
```

The order of operations divides first (`userVote / totalVote`), producing a fractional `voteRate`, and only afterward multiplies by `totalReward`. This is the same class of bug as the Ajna finding: dividing a small numerator by a large denominator before multiplying by a scaling factor can under-represent (or, in the worst case with sufficiently disparate magnitudes, truncate) the true proportional share, instead of first multiplying `userVote * totalReward` and dividing by `totalVote` once at the end (as the newer VI-based algorithm correctly does, see below).

This is invoked from `MortgageService.queryReward(byte[])` and `MortgageService.withdrawReward(byte[])`: [2](#0-1) 

which are reachable indirectly by any account's own reward query/withdrawal for cycles predating `newRewardAlgorithmEffectiveCycle` (`getOldReward`), and structurally analogous copies of this exact pattern also exist in `RewardViCalService`/`DelegationStore`/`VoteRewardUtil` reward math that use the correct multiply-then-divide order with `BigInteger`: [3](#0-2) 

Notably, this same class of bug was already identified and fixed elsewhere in this codebase for resource/energy-limit math (`ResourceProcessor`/`RepositoryImpl`), where a `hardenResourceCalculation()`/`allowHardenResourceCalculation()` feature flag replaces a legacy double-based divide-then-multiply formula with a correct BigInteger multiply-then-divide formula, with an explicit code comment documenting the fix: [4](#0-3) 

This confirms the project's own developers recognize divide-before-multiply as a real precision bug class — but the fix was not applied to `MortgageService.computeReward`'s legacy vote-reward path.

### Impact Explanation
Because Java `double` has ~15-17 significant decimal digits of precision (unlike Solidity's fixed-point integer math, which truncates to exactly 0 when the intermediate division underflows the integer domain), the practical precision loss here is far smaller than the classic Solidity truncation-to-zero case. A genuine reward loss to zero would require `userVote` to be many orders of magnitude (roughly 10^15+) smaller than `totalVote`, which is an extreme edge case given `long` vote counts. Thus, while the code exhibits the same anti-pattern (division before multiplication) as the referenced report, the actual monetary impact in java-tron is limited to minor rounding-level reward discrepancies for legacy-cycle rewards rather than a full loss of funds, and only affects the pre-`newRewardAlgorithmEffectiveCycle` computation path, which is a narrow, mostly historical code path.

### Likelihood Explanation
Low-to-moderate. The vulnerable path only executes for cycles before `newRewardAlgorithmEffectiveCycle` (a one-time, already-passed cutover on mainnet), and even then, floating point division rarely truncates enough to fully zero rewards. There is no way for an unprivileged caller to force fresh executions of this vulnerable path going forward since new cycles use the corrected `BigInteger`-based VI algorithm.

### Recommendation
For consistency and defense-in-depth, refactor `MortgageService.computeReward(long, List<Pair<byte[], Long>>)` to compute `userVote * totalReward / totalVote` using `BigInteger` (or in the same manner as `calculateGlobalLimitV2`'s hardened fix) rather than `(double) userVote / totalVote * totalReward`, eliminating the divide-before-multiply pattern entirely, matching the already-corrected VI-based reward algorithm and the hardened resource-limit calculations elsewhere in the codebase.

### Proof of Concept
Given `totalReward = 100`, `totalVote = 3`, and three voters each with `userVote = 1`:
- Correct (multiply first): `1 * 100 / 3 = 33` for each voter, summing to `99` (acceptable rounding loss of `1`).
- Current double-based order: `voteRate = 1.0/3.0 = 0.333333...`; `reward = 0.333333... * 100 = 33.333...` truncated to `long` = `33` per voter — in this scale the discrepancy is negligible, but as the ratio `userVote/totalVote` shrinks toward the limits of double precision, the compounding rounding error grows relative to the correct multiply-first-divide-last result, deviating from the exact proportional share that `computeReward`'s newer `BigInteger`-based sibling methods correctly compute.

   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with

   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the

   * yield the same proportional result as the double-arithmetic path.

  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
