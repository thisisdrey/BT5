### Title
Stale postponed receipts and pending data counts survive `DeleteAccount`, allowing privileged self-call execution against a re-created account - ([File: runtime/runtime/src/actions.rs::action_delete_account, core/store/src/utils/mod.rs::remove_account])

### Summary
`remove_account` in `core/store/src/utils/mod.rs` deletes only the `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie entries for a deleted account, but never removes `TrieKey::PostponedReceipt` or `TrieKey::PendingDataCount` entries keyed by that account as receiver. If a multi-input cross-contract call (`promise_and`) targeting the account was parked (postponed) before deletion, the postponed receipt row remains in the trie after the account is deleted.

### Finding Description
`remove_account` [1](#0-0)  iterates and removes `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData` rows for the target account, but contains no logic that touches `TrieKey::PostponedReceipt` or `TrieKey::PendingDataCount` for that account. Meanwhile, the store-level helpers `set_postponed_receipt`/`remove_postponed_receipt` explicitly key postponed receipts by `receiver_id` and `receipt_id` [2](#0-1) , showing that these rows are a separate, independently-addressed part of account state that `remove_account` never visits.

Exploit flow:
1. Attacker creates account `X` and deploys a contract that, when called, issues an outgoing receipt to itself (`X`) depending on two input data ids (via `promise_and`), causing the runtime to write a `PostponedReceipt{receiver_id:X,...}` row and a `PendingDataCount{receiver_id:X,...}` counter set to 2.
2. One of the two dependent data callbacks resolves, decrementing `PendingDataCount` to 1 (receipt stays parked).
3. Attacker submits `DeleteAccount(X)` with itself as beneficiary. `action_delete_account` calls `remove_account`, which deletes `Account`, `ContractCode`, `AccessKey`, `ContractData` for `X`, but leaves the `PostponedReceipt` and `PendingDataCount` rows intact in the trie.
4. Account `X` is later re-created (by the same or a different party, depending on naming/namespace rules) with new contract code, new access keys, and new state.
5. The second, previously-pending data dependency arrives and resolves, driving `PendingDataCount` to 0. The runtime's receipt-resumption logic in `runtime/runtime/src/lib.rs` reads back the still-present `PostponedReceipt` entry and re-executes its actions with `predecessor_id == receiver_id == X`.
6. Action authorization in `runtime/runtime/src/actions.rs`'s `check_actor_permissions` grants owner-level privilege whenever `predecessor_id == receiver_id` (the "self-call" trust model used for internal continuation receipts), so the resumed postponed actions execute with full self/owner privilege against the account that currently occupies `X` — even though that account may be an entirely different incarnation with a different owner, contract, and keys than the one that scheduled the receipt.

This is a genuine gap in `remove_account`'s cleanup: an account's postponed cross-shard state (receipts pending completion of their non-arrived input data) is not enumerated or purged on deletion, unlike every other per-account trie namespace it does clean up.

### Impact Explanation
This is an authorization-escalation bug: actions originally authorized only in the context of the deleted account's contract/owner are later executed with privileged "self-call" trust against a re-created account that never scheduled or approved them. Depending on what actions were queued in the postponed receipt (e.g., `DeployContract`, `AddKey`, `DeleteKey`, `Transfer`, `FunctionCall` with elevated trust), this can result in unauthorized state mutation, key/permission takeover, or fund movement on the newly re-created account — mapping to the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
The precondition requires: (a) attacker fully controls account `X` and its contract to construct a 2-input `promise_and` self-targeted receipt and resolve exactly one input before deletion, (b) attacker (or object account owner) issues `DeleteAccount(X)`, and (c) `X` is subsequently re-created before the remaining input data resolves. Steps (a) and (b) are entirely within an ordinary unprivileged user's control (self-owned account, contract deployment, and standard receipt/promise mechanics) and cost only the normal gas/storage of a few transactions. Step (c), re-creation of the exact same account id by a distinct/unexpected owner, is constrained by NEAR's account-naming rules (sub-account creation requires the immediate parent as predecessor; top-level account creation is registrar-gated) — this narrows, but does not eliminate, real-world scenarios (e.g., subaccounts under a shared/registrar-controlled parent, or the attacker itself re-creating `X` and being surprised by execution of stale privileged self-calls against its fresh state). Even without a change of "owner" the residual postponed-receipt execution against a fresh account incarnation is an unexpected and unaudited interaction.

### Recommendation
When executing `action_delete_account` / `remove_account`, enumerate and remove all `TrieKey::PostponedReceipt` and `TrieKey::PendingDataCount` entries for which the deleted account is the `receiver_id` (analogous to how access keys and contract data are enumerated via prefix iteration), and account for their storage/refund appropriately. Alternatively, disallow `DeleteAccount` while any postponed receipts are pending for that account, similar to existing checks that block deletion when the account still holds locked/staked balance.

### Proof of Concept
Integration test plan (in `runtime/runtime/src/tests/apply.rs`, following the pattern of existing postponed-receipt tests):
1. Create account `X`, deploy a contract exposing a method that issues a self-targeted `ActionReceipt` depending on two input data ids via `promise_and`.
2. Trigger the call so that a `PostponedReceipt{receiver_id: X, ...}` and `PendingDataCount{receiver_id: X} = 2` are written; resolve one of the two data dependencies, confirming `PendingDataCount` decrements to 1 and the receipt remains parked (assert via `get_postponed_receipt`/trie key presence).
3. Submit `DeleteAccount(X)` (beneficiary = self) and apply it; assert `get_account(X)` returns `None`, but `get_postponed_receipt(trie, X, receipt_id)` still returns `Some(..)` and the `PendingDataCount` key is still present.
4. Re-create account `X` via `CreateAccount` (new owner/keys/contract).
5. Resolve the second, previously-outstanding input data id; apply the resulting `ReceivedData` receipt and assert that the parked receipt's actions execute against the new `X`, with `predecessor_id == receiver_id == X` granting owner-level actor permission via `check_actor_permissions`, and that this happens despite the new `X` never having authorized or generated that receipt (assert account/actor mismatch, e.g. by checking the new account's state was mutated by an action it never approved).

pub fn set_postponed_receipt(state_update: &mut TrieUpdate, receipt: &Receipt) {
    assert!(matches!(receipt.versioned_receipt(), VersionedReceiptEnum::Action(_)));
    let key = TrieKey::PostponedReceipt {
        receiver_id: receipt.receiver_id().clone(),
        receipt_id: *receipt.receipt_id(),
    };
    set(state_update, key, receipt);
}

pub fn remove_postponed_receipt(
    state_update: &mut TrieUpdate,
    receiver_id: &AccountId,
    receipt_id: CryptoHash,
) {
    state_update.remove(TrieKey::PostponedReceipt { receiver_id: receiver_id.clone(), receipt_id });
}

pub fn get_postponed_receipt(

    receipt_id: CryptoHash,
) -> Result<Option<Receipt>, StorageError> {

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
