## Analog Found

### Title
Account Permission Update Actuator Allows a Delegated Active-Level Key to Overwrite Owner/Active Permissions and Seize Full Control of an Account - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator` lets any transaction whose signer satisfies a non-Owner (`Active`) permission that has the `AccountPermissionUpdateContract` bit set in its `operations` bitmap fully rewrite the account's `Owner` permission, `Witness` permission and all `Active` permissions in a single call. `validate()` never checks that the signer actually holds Owner-level authority (`permission_id == 0`) before allowing the new Owner keys/threshold to be substituted; it only checks structural well-formedness of the new permission set. This is the same bug class as CVE-2024-6908: a lower-privileged principal (an Active/"admin" key) can use a normal, crafted request to write itself into the highest-privilege role ("SuperAdmin"/Owner), because the endpoint that performs privilege changes does not verify that the caller's *existing* privilege level is sufficient for the privilege being granted.

### Finding Description
Multisig accounts in java-tron have three permission tiers: `Owner` (`id=0`), `Witness` (`id=1`) and up to 8 `Active` permissions (`id>=2`), defined in `protocol/src/main/protos/core/Tron.proto:261-274`. A transaction is authorized against one of these tiers via `Transaction.Contract.Permission_id`; for `permission_id != 0` the code only requires that the referenced permission is of type `Active` and that its `operations` bitmap has the bit for the contract's `ContractType` set: [1](#0-0) 

That means any account owner can create an `Active` permission whose `operations` bitmap includes bit 46 (`AccountPermissionUpdateContract`) — by default this bit is excluded from the "default" active permission template, as shown by `AccountCapsule.createDefaultActivePermission` and the corresponding unit test that explicitly excludes `ContractType.AccountPermissionUpdateContract` from `getActiveDefaultOperations`: [2](#0-1) [3](#0-2) 

But nothing in `AccountPermissionUpdateActuator` prevents that bit from being granted to an `Active` permission (the actuator's `checkPermission()` validates operations only against the full `getAvailableContractType()` set, i.e. "any valid contract type is allowed here"): [4](#0-3) 

Once any `Active` permission is granted bit 46 (which is a normal, supported configuration for delegated "admin" management, e.g. exchange/custodian back-office keys), a transaction signed under that `Active` permission passes `validate()`'s only checks — permission type/threshold/weight/name/operations well-formedness of the **new** permissions being set — with no verification that the signer's own permission tier (`Active`, not `Owner`) is authorized to modify the `Owner` tier: [5](#0-4) 

`execute()` then unconditionally applies the attacker-supplied `Owner`, `Witness`, and `Active` permission lists to the account, replacing the previous owner key set entirely: [6](#0-5) [7](#0-6) 

### Impact Explanation
An account that has delegated an `Active` permission with the `AccountPermissionUpdateContract` right (a legitimate administrative delegation pattern — e.g. granting a co-signer or automation key rights to manage account settings) effectively grants that key holder the ability to unilaterally seize the `Owner` role: it can set a brand-new `Owner` permission (its own key, threshold 1), replace all `Active` permissions, and remove the original owner's keys entirely. This permanently locks the legitimate owner out of the account and gives the former Active-tier key full, unrestricted control (including future transfers, resource freezing, and further permission changes) — a concrete unauthorized-account-takeover / permanent-loss-of-funds-control scenario reachable purely from a single crafted, signed transaction.

### Likelihood Explanation
Exploitation requires that an account owner has, at some point, granted an `Active` permission the right to submit `AccountPermissionUpdateContract` (contract type 46) — a configuration outside the framework's default template but fully permitted by `checkPermission()`, which validates against the entire universe of valid contract types rather than restricting sensitive contract types to the Owner tier. Given this is a real, documented capability of the multisig system (delegation of account/permission management to non-owner keys), and no additional server-side guard enforces "only Owner can modify Owner," any environment using this delegation pattern (exchanges, custody services, DAOs using TRON multisig) is directly exposed. This matches the CVSS profile of the referenced CVE (PR:H — attacker needs a privileged-but-not-highest role to begin with).

### Recommendation
In `AccountPermissionUpdateActuator.validate()`, require that transactions modifying the `Owner` permission (and ideally `Witness`/other `Active` permissions) be authorized specifically under `permission_id == 0` (the Owner tier), regardless of what the `operations` bitmap of an `Active` permission allows. Alternatively/additionally, disallow `AccountPermissionUpdateContract`'s bit from ever being set in any `Active` permission's `operations` bitmap during `checkPermission()`, closing the escalation path at permission-creation time rather than relying on convention.

### Proof of Concept
1. Account `A` (Owner key `K_owner`) creates an `Active` permission (`id=2`) for key `K_admin` with `operations` bitmap including bit 46 (`AccountPermissionUpdateContract`), intending `K_admin` to manage minor account settings.
2. `K_admin` crafts and signs an `AccountPermissionUpdateContract` transaction with `permission_id=2`, setting:
   - `owner` = new `Permission{type=Owner, threshold=1, keys=[K_admin]}`
   - `actives` = `[Permission{type=Active, threshold=1, keys=[K_admin], operations=<all-contract-types>}]`
3. Because `permission_id != 0` only requires `checkPermissionOperations` to pass (bit 46 set) per `TransactionCapsule.checkPermission` at lines 635-645, and `AccountPermissionUpdateActuator.validate()` performs no check that the signer holds Owner authority, the transaction is accepted.
4. `execute()` calls `AccountCapsule.updatePermissions(owner, witness, actives)`, overwriting the account's Owner permission to `K_admin` alone; `K_owner` is permanently removed from all permission tiers, giving `K_admin` full unilateral control of account `A`.

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
  }
