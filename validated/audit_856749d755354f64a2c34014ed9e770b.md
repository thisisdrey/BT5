### Title
Slice-bounds-out-of-range panic parsing malicious Mach-O load commands - (File: src/cmd/link/internal/loadmacho/ldmacho.go)

### Summary
The linker's Mach-O host-object reader (`loadmacho.Load`) advances through the load-command table using an attacker-controlled 32-bit length field without validating it against the remaining buffer size, similar in spirit to the unchecked-length copy that caused CVE-2022-1240 in radare2's `mach0.c`. A crafted `.o`/host object with an oversized `cmdsize` field causes a Go runtime slice-bounds panic instead of a native heap overflow, but the root cause — trusting an attacker-supplied length field to slice a buffer — is the same primitive.

### Finding Description
`cmd/link` calls `loadmacho.Load` (`src/cmd/link/internal/loadmacho/ldmacho.go`) to parse Mach-O host object files supplied to the linker (e.g. via cgo `.o` files or external linking inputs) [1](#0-0) . Inside the load-command loop, each command's `type` and `size` are read directly from attacker-controlled file bytes and the cursor is advanced by `cmdp = cmdp[sz:]` with no check that `sz <= len(cmdp)`: [2](#0-1) 
`unpackcmd` does validate `sz` against fixed minimums for known command types (e.g. `sz < 56` for `LC_SEGMENT`), but those checks bound only the *minimum* size, not the *maximum*, and they do not protect the outer loop's `cmdp[sz:]` slicing operation. If `sz` (a raw `uint32` taken from the file) exceeds the remaining length of `cmdp`, the slice expression panics with "slice bounds out of range" [3](#0-2) . Additionally, for `LC_SEGMENT`/`LC_SEGMENT_64`, `nsect` (also attacker-controlled `uint32`) is multiplied by a fixed per-section size (`c.seg.nsect*68` or `*80`) when checking `sz`; this multiplication can overflow `uint32`, potentially bypassing the size check before the section-array slicing that follows [4](#0-3) .

### Impact Explanation
The effect in Go is a runtime panic (denial of service) rather than memory corruption, because Go's slicing is bounds-checked — unlike the C `r_str_ncpy` overflow in the original radare2 report. This would only be reachable during `go build`/`go link` when the toolchain is asked to link in an attacker-supplied Mach-O host object (e.g., a cgo consumer building a package that ships a malicious precompiled `.o`/archive). Per Go's security policy, this is arguably a build-time parser crash on malicious input, which is a lower-severity, PUBLIC-track class of issue (denial of service via panic), not code execution or data corruption.

### Likelihood Explanation
Requires a victim to run `go build`/`go link` against a project or dependency that supplies a crafted Mach-O object file (common in cgo-heavy modules bundling prebuilt `.o`/`.a` files). The attacker doesn't need any special privilege beyond getting their malicious object linked, but this is a narrow and unusual workflow.

### Recommendation
In `unpackcmd`/`Load`, validate that `sz >= 8` and `sz <= len(cmdp)` before slicing `cmdp[sz:]`, and use overflow-safe arithmetic (e.g. `uint64`) when checking `56+nsect*68` / `72+nsect*80` bounds so a large `nsect` cannot wrap around and defeat the size check.

### Proof of Concept
