### Title
Quarantine objects are packed and committed into the repository without object validity checks - ([File: internal/gitaly/storage/storagemgr/partition/transaction_manager.go])

### Summary
`TransactionManager.packObjects` walks the objects a client wrote into the push/fetch quarantine directory and commits them into the repository's object store as part of the WAL transaction, but the objects themselves are never validated for well-formedness before being packed and later applied. The only "check" performed is that referenced-but-missing objects (dependencies) are later verified to *exist*; the objects that *are* present in the quarantine are trusted as-is and staged directly into the pack that becomes part of the committed state.

### Finding Description
`packObjects` walks new reference tips and the quarantine directory contents, and any object found in the quarantine is written straight into a packfile that gets staged for the transaction and eventually merged into the repository's real object directory: [1](#0-0) 

The function's own documentation is explicit about the gap: "The packed objects are not yet checked for validity," linking to the still-open issue https://gitlab.com/gitlab-org/gitaly/-/issues/5779, and the code only records objects that are *missing* from quarantine as "dependencies" to be checked for existence later — it never fscks or otherwise validates the objects that are actually walked and packed: [2](#0-1) [3](#0-2) 

This is structurally analogous to the ELFI bug class: an action (opening a position / committing a push's objects) is executed and the resulting state is only sanity-checked for a narrow condition (liquidation-safety / dependency-existence) while the deeper validity of what is actually being committed (position solvency / object well-formedness) is left unchecked. Here, quarantine directories are the Gitaly analog of "keeper-executed positions" — an ordinary user's `git push` (or `FetchRemote`, which also routes fetched objects through the same quarantine-then-migrate flow, see `fetchRemoteAtomic`) supplies arbitrary object content, and once accepted for packing, that content is written into the durable repository state without a corruption/consistency check gate. [4](#0-3) 

### Impact Explanation
Because object validity isn't checked before the pack becomes part of the transaction's committed WAL entry, a client (an ordinary pusher, or a remote peer in the `FetchRemote` flow) can get malformed, truncated, or otherwise corrupt objects merged into the shared object store. Since this pack becomes indistinguishable from legitimately-verified history once committed, it can silently corrupt the repository (bad blobs/trees/commits reachable from real refs), cause later Git operations (fsck, repack, replication, object-pool linking) to fail or behave inconsistently, and can propagate corruption to replicas/pools via `internal/git/objectpool` linking and Praefect replication, since those paths trust that objects already accepted into a repository's transaction log are structurally sound.

### Likelihood Explanation
This path is reachable from wholly unprivileged, ordinary Git client operations — every push (and `FetchRemote`) that uses the WAL/partition transaction manager runs through `packObjects`, and the code comment itself documents that the missing-validity check is a known, currently-unaddressed gap (tracked but still open per the linked issue). No malicious peer, leaked token, or privileged actor is required — a normal `git push` supplying deliberately malformed loose objects/pack content in the client-controlled quarantine directory is sufficient to reach this code path.

### Recommendation
Before staging the packfile produced by `packObjects` for commit, validate the objects walked out of the quarantine directory (e.g., run `git index-pack --strict`/`git fsck`-equivalent checks or leverage `git-index-pack`'s validation options) and reject the transaction if any object fails structural/content validation, consistent with the remediation already tracked in gitlab-org/gitaly#5779.

Not independently reproducible from static analysis alone — this repository is source-only, and I did not have execution/build access to construct a live `git push`/`FetchRemote` test proving corrupt-object acceptance.
