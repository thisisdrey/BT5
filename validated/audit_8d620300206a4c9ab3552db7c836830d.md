### Title
Fold-based bad-debt socialization fails atomically, allowing a borrower to block full liquidation of a multi-asset debt position - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate` calls `socialize-debt-asset` inside a `fold` over the borrower's full debt list once collateral is exhausted. Because that fold treats *any* single-asset socialization failure as a hard stop that reverts the whole liquidation via `asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED`, a borrower who deliberately opens debt in more than one asset can turn a single failing leg of the socialization loop into a full revert of the liquidator's transaction, exactly the "external call in a loop, one revert kills everything" pattern the referenced report describes.

### Finding Description
`liquidate` builds `fresh-debt-list` (the borrower's remaining scaled debts across every debt asset they used) and, when `no-collateral-left` is true, folds `socialize-debt-asset` over that list: [1](#0-0) 

`socialize-debt-asset` performs three chained external/cross-contract calls per debt asset entry (`vault-socialize-debt`, cache refresh via `vault-accrue`, and `.v0-market-vault debt-remove-scaled`), each guarded with `unwrap!`, and short-circuits subsequent iterations once one fails, but the aggregate result is only checked at the very end with a single `asserts!`: [2](#0-1) 

This is structurally identical to the SWC-113 pattern: several external calls executed in a loop where a revert (or `unwrap!` failure) on any single element aborts the entire batch, even though the batch is otherwise legitimate and partially succeeds. Because the debt list being iterated is derived from the *borrower's own* chosen set of debt assets (not a fixed, curated list), the borrower fully controls how many and which debt-asset legs participate in the fold at liquidation time, and can shape their position (e.g., by holding a small residual debt in an additional, low-liquidity/edge-case asset alongside their primary debt) to make one leg of the socialization fold fail deterministically.

### Impact Explanation
If any single leg of the socialization fold reverts, the entire `liquidate` call reverts, meaning:
- The liquidator's transaction fails and the collateral seizure / debt repayment that already succeeded up to that point (`vault-system-repay`, `debt-remove-scaled`, `collateral-remove`) is rolled back with it, since `liquidate` is one atomic call.
- The borrower's clearly-undercollateralized position (which is what triggers `no-collateral-left` / bad-debt socialization in the first place) becomes effectively un-liquidatable through the normal `liquidate` path, letting bad debt accumulate and remain unresolved on-chain.

This lands on the in-scope **temporary freezing of funds** impact class (liquidators cannot execute liquidation/repayment against the position, and unclaimed yield/collateral tied up in that position remains stuck) and contributes toward protocol insolvency risk if bad debt cannot be socialized because the very mechanism meant to write it off is the one that reverts.

### Likelihood Explanation
Likelihood is speculative rather than proven: I could not identify, within the reachable code, a concrete unprivileged path that deterministically forces one leg of `socialize-debt-asset` (`vault-socialize-debt`, `vault-accrue`, or `debt-remove-scaled`) to fail while the position is otherwise eligible for full liquidation — the scaled amounts folded in are computed directly from the position's own stored state, so the `ERR-INSUFFICIENT-DEBT` check in `remove-user-scaled-debt` and the guarded divisions in `socialize-debt` are not obviously triggerable by a normal borrower without an additional bug (e.g., a paused vault, which is DAO-gated and out of scope) or an oracle/arithmetic edge case elsewhere in the flow. The fold's fail-fast design is nonetheless a genuine deviation from the "always assume external calls can fail, handle failures gracefully" recommendation and is a plausible amplifier for any yet-unknown revert condition in the vault contracts.

### Recommendation
Change `socialize-debt-asset`/the surrounding fold so a failure on one debt-asset leg does not abort the others: process each asset independently (catching/skipping failures rather than propagating them into a global `success: false` short-circuit), and only revert the overall `liquidate` transaction if no leg at all can be socialized, or better, decouple debt-list socialization retries from the collateral-seizure step so partial socialization failures don't undo already-completed liquidator repayment/collateral transfer.

### Proof of Concept
Not constructible from static review alone: reproducing the DoS requires identifying a concrete on-chain state (e.g., a specific debt-asset combination or vault state reachable by an ordinary borrower) that causes `vault-socialize-debt`, `vault-accrue`, or `.v0-market-vault debt-remove-scaled` to fail for one asset while the position is otherwise fully liquidatable — this precondition was not confirmed in the available code and would need to be validated with a live/test-network reproduction (e.g., a Devin session running the Clarinet/Clarigen test suite in `local-testing/`) before this can be escalated beyond a structural/code-pattern concern.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
