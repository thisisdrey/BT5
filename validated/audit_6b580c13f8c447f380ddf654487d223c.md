Found a concrete stuck-funds analog: in `address_check_callback` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:134-192`), when the registrar lookup returns `PromiseResult::Failed` (line 142-148) or an unexpected/malformed response (line 149-158), the function returns `ExecuteResponse{success:false,...}` **without ever refunding `caller_deposit`**. Every other failure branch in this contract (`rlp_execute_callback` at lines 296-317, `nep_141_storage_balance_callback` at lines 203-220) explicitly issues a `promise_batch_action_transfer` refund to `caller_deposit.account_id` before returning failure — but these two early-return branches in `address_check_callback` drop `caller_deposit` on the floor.

### Title
Attached deposit permanently lost (not refunded) when the Wallet Contract's registrar-lookup callback fails or returns malformed data - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The eth-implicit Wallet Contract's `rlp_execute` flow tracks an external caller's attached deposit via `CallerDeposit` so it can be refunded if the downstream cross-contract call ultimately fails [1](#0-0) . This refund pattern is correctly implemented in `rlp_execute_callback` [2](#0-1)  and in `nep_141_storage_balance_callback`'s failure branch [3](#0-2) . However, `address_check_callback` — which runs for `EOABaseTokenTransfer` transactions that need an address-registrar lookup before proceeding — takes `caller_deposit: Option<CallerDeposit>` as a parameter but silently drops it in its two failure paths [4](#0-3) .

### Finding Description
`inner_rlp_execute` computes `caller_deposit = CallerDeposit::new(&context)` from the attached deposit whenever the predecessor differs from the wallet's own account id [5](#0-4) , and for the `EOABaseTokenTransfer{address_check: Some(_)}` path it forwards `caller_deposit` into the `address_check_callback` scheduled via `.then(...)` [6](#0-5) .

Inside `address_check_callback`:
- If the registrar cross-contract call fails (`PromiseResult::Failed`), the function immediately returns an `ExecuteResponse{success:false}` without touching `caller_deposit` [7](#0-6) .
- If the registrar call succeeds but returns data that fails to deserialize into `Option<AccountId>`, the function again returns failure without refunding `caller_deposit` [8](#0-7) .

In both cases the attached NEAR that the external caller sent with their `rlp_execute` call (via `#[payable]` at line 88) remains on the Wallet Contract account with no code path to return it to the caller — it is not burned, not sent anywhere, and there is no user-facing way to reclaim it since the nonce/nonce nonincrement branch permits the transaction to potentially be resubmitted, but the previously attached deposit for the failed attempt is simply absorbed into the contract's balance.

This matches the report's root-cause pattern: a value-transfer flow with an intermediate off-band/asynchronous step (waiting for a cross-contract callback) whose failure/rejection branches were not all wired to return the collateral/deposit, so funds that were already transferred into the contract for a pending operation become stuck when that operation is aborted.

### Impact Explanation
Funds (attached $NEAR deposit) sent by an ordinary, unprivileged user calling `rlp_execute` on their own eth-implicit wallet contract can become permanently stuck in the contract whenever the registrar lookup either reverts (e.g., registrar contract paused, not deployed, out of gas) or returns a response the wallet contract cannot parse. This is a genuine, reachable path from a normal external call — no privileged role is required, and the loss is deterministic given the described conditions (any transient failure of the registrar call). This constitutes permanent freezing/loss of user funds, satisfying the required impact bar.

### Likelihood Explanation
Likelihood is moderate: it requires the caller to route through the `EOABaseTokenTransfer{address_check: Some(_)}` branch (i.e., sending a base-token transfer whose destination is another eth-implicit address, triggering the registrar lookup) and the registrar call to fail or return unparseable data. Since the registrar is a separate cross-contract call subject to normal failure modes (gas exhaustion, receiver not deployed/misconfigured, unexpected response schema changes), this is a realistic occurrence, not a contrived edge case, and can also be intentionally triggered by an attacker who deploys/controls or targets a malfunctioning registrar response to grief victims' deposits.

### Recommendation
In both failure branches of `address_check_callback` (`PromiseResult::Failed` and JSON deserialization failure), issue the same refund pattern used elsewhere in the contract: if `caller_deposit` is `Some`, create a `promise_batch_action_transfer` back to `caller_deposit.account_id` for `caller_deposit.yocto_near` before returning the failure `ExecuteResponse`, mirroring the logic already present in `rlp_execute_callback` [2](#0-1) .

### Proof of Concept
1. Deploy the Wallet Contract as the global contract for an eth-implicit account, as in `test_wallet_contract_interaction` [9](#0-8) .
2. Have an external caller invoke `rlp_execute` with an RLP-encoded Ethereum transaction representing an `EOABaseTokenTransfer` whose `to` address requires an address-registrar lookup (i.e., `address_check: Some(address)`), attaching a nonzero deposit, similar to `test_caller_refunds`'s pattern of attaching `deposit_amount` [10](#0-9)  and `test_relayer_invalid_address_target`'s registrar-lookup setup [11](#0-10) .
3. Cause the address-registrar's `lookup` call to fail (e.g., point `target` at an account without a deployed/functioning registrar, or one that returns malformed JSON).
4. Observe `address_check_callback` returns `success:false` while the caller's account balance does not recover the attached deposit — unlike the analogous failure paths in `rlp_execute_callback`, no transfer-back promise is created, so the deposit remains on the wallet contract's balance permanently (verifiable by comparing pre/post caller balance the way `test_caller_refunds` does at lines 208-213, but for the address-check-lookup-failure path instead of the inner-cross-contract-call-failure path).

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
