Audit Report

## Title
Missing zero-address validation on ENA/PNA recipient in Snowbridge outbound XCM-to-Ethereum converter causes permanent fund loss - (File: `bridges/snowbridge/primitives/outbound-queue/src/v1/converter/mod.rs`, `bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs`)

## Summary
The Snowbridge outbound-queue XCM converters extract `recipient: H160` from the `DepositAsset { beneficiary, .. }` XCM instruction's `AccountKey20` junction without ever validating it is non-zero, in both v1 (`XcmConverter::make_unlock_native_token_command`) and v2 (`XcmConverter::convert`, `extract_ethereum_native_assets`, `extract_polkadot_native_assets`). This allows an unprivileged XCM sender to craft a message that produces `Command::UnlockNativeToken`/`MintForeignToken` with `recipient = H160::zero()`, which, once relayed to the Ethereum Gateway, results in permanent loss of the transferred value.

## Finding Description
In v1, the beneficiary is extracted purely via pattern match requiring `AccountKey20` at depth 0 with matching network, with no zero check: [1](#0-0) 
This `recipient` is fed directly into `Command::UnlockNativeToken { agent_id: self.agent_id, token, recipient, amount }`: [2](#0-1) 

In v2, the identical unguarded extraction occurs in `XcmConverter::convert`: [3](#0-2) 
and is passed unchanged into both `extract_ethereum_native_assets` (producing `Command::UnlockNativeToken { token, recipient, amount }`) and `extract_polkadot_native_assets` (producing `Command::MintForeignToken { token_id, recipient, amount }`): [4](#0-3) [5](#0-4) 

I searched the entire outbound-queue primitive and pallet code (`bridges/snowbridge/primitives/outbound-queue/**`, `bridges/snowbridge/pallets/outbound-queue*/**`) for any `is_zero`/`H160::zero()` guard applied to the recipient/beneficiary, and found none in production code — the only matches for zero-address checks in that scope are in test files (`tests.rs`, `test.rs`, `mock.rs`, `benchmarking.rs`). By contrast, the inbound-queue v2 converter (`bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs`, Ethereum-to-Polkadot direction) does contain multiple zero-address checks, confirming this class of validation is a recognized necessity elsewhere in the same bridge codebase but is absent specifically in the outbound (Polkadot-to-Ethereum) direction.

## Impact Explanation
An unprivileged user can construct an XCM ending in `DepositAsset { beneficiary: AccountKey20 { key: [0u8;20], network: None }, .. }` from a parachain such as AssetHub. This passes `EthereumBlobExporter::validate` → `XcmConverter::convert` unchallenged (no `BeneficiaryResolutionFailed` or equivalent error), gets queued via `OutboundQueue::validate`/`deliver`, and is eventually relayed to the Ethereum Gateway contract as `UnlockNativeToken`/`MintForeignToken` addressed to `0x0`. Sending/minting value to the zero address on Ethereum is generally an unrecoverable operation, resulting in permanent loss of the bridged asset — this matches the "permanent user-fund or bridge-state lock" impact category, since value that leaves Polkadot-side custody is not recoverable once committed to the outbound message.

## Likelihood Explanation
The exploit path requires only a normal, unprivileged XCM send from a parachain (e.g., AssetHub) targeting the Ethereum bridge with a crafted `beneficiary`. No governance, validator, or relayer misbehavior is needed — it is a pure public-entrypoint/message-construction defect reachable by any account that can execute XCM sends, and it is fully reproducible/deterministic.

## Recommendation
Add an explicit zero-address check immediately after extracting `recipient` in both `make_unlock_native_token_command` (v1, `mod.rs:260`) and `convert` (v2, `convert.rs:272`), e.g. `ensure!(recipient != H160::zero(), XcmConverterError::BeneficiaryResolutionFailed)`, mirroring the checks already present in the inbound-queue v2 converter.

## Proof of Concept
1. Construct an XCM program ending in `DepositAsset { assets: Wild(All), beneficiary: AccountKey20 { network: None, key: [0u8; 20] }.into() }` alongside a valid `WithdrawAsset`/`ReserveAssetDeposited` and `SetTopic`.
2. Send it via `pallet_xcm::send`/`transfer_assets` from AssetHub targeting the Ethereum bridge, triggering `EthereumBlobExporter::validate`.
3. `XcmConverter::convert` in both v1 (`bridges/snowbridge/primitives/outbound-queue/src/v1/converter/mod.rs:253-260`) and v2 (`bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs:265-272`) successfully extracts `recipient = H160([0;20])` with no error raised.
4. The resulting `Command::UnlockNativeToken`/`MintForeignToken { recipient: H160::zero(), .. }` is accepted by `OutboundQueue::validate`/`deliver` and committed for relay.
5. Add a unit test in `bridges/snowbridge/primitives/outbound-queue/src/v1/converter/tests.rs` (and v2 equivalent) asserting that a `beneficiary` with `key: [0u8;20]` currently succeeds (demonstrating the missing guard) — confirming the fix requirement is that it should instead return `Err(XcmConverterError::BeneficiaryResolutionFailed)`.

	/// Extract ethereum native assets
	fn extract_ethereum_native_assets(
		&mut self,
		enas: &Assets,
		deposit_assets: &AssetFilter,
		recipient: H160,
	) -> Result<Vec<Command>, XcmConverterError> {
		let mut commands: Vec<Command> = Vec::new();
		for ena in enas.clone().into_inner().into_iter() {
			// Check the the deposit asset filter matches what was reserved.
			if !deposit_assets.matches(&ena) {
				return Err(FilterDoesNotConsumeAllAssets);
			}

			// only fungible asset is allowed
			let (token, amount) = match ena {
				Asset { id: AssetId(inner_location), fun: Fungible(amount) } => {
					match inner_location.unpack() {
						(0, [AccountKey20 { network, key }]) if self.network_matches(network) => {
							Ok((H160(*key), amount))
						},
						// To allow ether
						(0, []) => Ok((H160([0; 20]), amount)),
						_ => Err(AssetResolutionFailed),
					}
				},
				_ => Err(AssetResolutionFailed),
			}?;

			// transfer amount must be greater than 0.
			ensure!(amount > 0, ZeroAssetTransfer);

			commands.push(Command::UnlockNativeToken { token, recipient, amount });
		}
		Ok(commands)
	}

	/// Extract polkadot native assets
	fn extract_polkadot_native_assets(
		&mut self,
		pnas: &Assets,
		deposit_assets: &AssetFilter,
		recipient: H160,
	) -> Result<Vec<Command>, XcmConverterError> {
		let mut commands: Vec<Command> = Vec::new();
		ensure!(pnas.len() > 0, NoReserveAssets);
		for pna in pnas.clone().into_inner().into_iter() {
			if !deposit_assets.matches(&pna) {
				return Err(FilterDoesNotConsumeAllAssets);
			}

			// Only fungible is allowed
			let Asset { id: AssetId(asset_id), fun: Fungible(amount) } = pna else {
				return Err(AssetResolutionFailed);
			};

			// transfer amount must be greater than 0.
			ensure!(amount > 0, ZeroAssetTransfer);

			// Ensure PNA already registered
			let token_id = TokenIdOf::convert_location(&asset_id).ok_or(InvalidAsset)?;
			let expected_asset_id = ConvertAssetId::maybe_convert(token_id).ok_or(InvalidAsset)?;
			ensure!(asset_id == expected_asset_id, InvalidAsset);

			commands.push(Command::MintForeignToken { token_id, recipient, amount });
		}
		Ok(commands)
	}
