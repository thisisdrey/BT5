### Title
Quarantine object-directory prefix check lacks path-separator boundary, allowing sibling-directory escape - ([File: internal/git/localrepo/paths.go])

### Summary
`ObjectDirectoryPath()` validates the client-supplied `GitObjectDirectory` field of a `Repository` message against an "expected quarantine prefix" using a raw `strings.HasPrefix()` comparison instead of a boundary-aware comparison. This is the same class of bug described in the external report: a variable, attacker-influenced parameter (`GitObjectDirectory`) is checked with an insufficiently strict rule (`StartsWith`-style prefix match) that does not guarantee the value is actually *inside* the expected directory, only that its string representation begins with the expected string.

### Finding Description
`Repo.ObjectDirectoryPath` in [1](#0-0)  resolves the object directory for a repository based on the client-supplied `GitObjectDirectory` field. When the object directory does not fall within the repository itself, the code falls back to checking whether it is a valid "manual" quarantine directory located in the storage's temp directory: [2](#0-1) 

The check computes `expectedQuarantinePrefix := filepath.Join(tempDir, storage.QuarantineDirectoryPrefix(repo))` and then does:
```go
if !strings.HasPrefix(absoluteObjectDirectoryPath, expectedQuarantinePrefix) {
    return "", structerr.NewInvalidArgument("not a valid relative path: %w", origError)
}
```
This is a pure string-prefix comparison with no path-separator boundary enforcement. Contrast this with the codebase's own correct pattern in `storage.ValidateRelativePath`, which explicitly appends `os.PathSeparator` before doing the prefix check to avoid exactly this class of bug: [3](#0-2) 

Because `QuarantineDirectoryPrefix(repo)` is deterministic and derived only from repository identity (not from any per-request random component), any client that can compute this prefix for a given repository can construct a `GitObjectDirectory` value naming a different, sibling directory under the storage's temp directory whose name merely begins with the same prefix string (e.g. `<prefix>-something-else/../<other-repo-quarantine>/...`), and the check will incorrectly treat it as belonging to the repository's legitimate quarantine.

### Impact Explanation
If exploitable, this allows a client to make Gitaly treat an arbitrary directory under the storage's temp directory as the object directory for a target repository, bypassing the intended "this quarantine directory must belong to this repo" guarantee. That is a violation of the "hook or quarantine bypass" / "cross-repository object access" categories: it could let object reads/writes for one repository be redirected into another repository's temporary quarantine directory, or into an attacker-influenced directory that merely shares a string prefix with the legitimate one.

### Likelihood Explanation
Exploitability requires: (1) the storage's temp directory to contain, at request time, another directory whose name begins with the exact same deterministic prefix but is not the actual quarantine directory belonging to the repo, and (2) the requester's ability to set an arbitrary `GitObjectDirectory` value in the `Repository` proto sent to an RPC. Reaching this path requires bypassing the "no GitObjectDirectoryPath validated inside the repo itself" branch first (i.e., an object directory that is not inside the repo but still matches the temp-dir-prefix heuristic), which is a narrower reachable condition than an ordinary push. I could not fully verify, within the available index, how `QuarantineDirectoryPrefix` is computed (its collision resistance/uniqueness) or what siblings can realistically exist with matching prefixes at the moment of the request, so I cannot confirm concrete end-to-end exploitability — only that the validation primitive itself is structurally unsound (missing boundary check) compared to the safe pattern used elsewhere in the same codebase.

### Recommendation
Change the check to require a path-separator boundary after the prefix, mirroring `storage.ValidateRelativePath`:
```go
if absoluteObjectDirectoryPath != expectedQuarantinePrefix &&
    !strings.HasPrefix(absoluteObjectDirectoryPath, expectedQuarantinePrefix+string(os.PathSeparator)) {
    return "", structerr.NewInvalidArgument("not a valid relative path: %w", origError)
}
```
More generally, replace ad-hoc `strings.HasPrefix` path checks throughout the codebase with the existing `storage.ValidateRelativePath` helper (or an equivalent boundary-safe comparison) wherever a directory containment check is performed against attacker/client-influenced path values.

### Proof of Concept
Not fully constructible from the indexed code alone: exploitation depends on the exact output format of `storage.QuarantineDirectoryPrefix(repo)` and on timing/existence of a sibling directory under the storage temp dir whose name shares that prefix without a following separator. A concrete PoC would need to be developed by an engineer with full repo access, by (1) inspecting `QuarantineDirectoryPrefix`'s implementation, (2) crafting a `Repository.GitObjectDirectory` value under the storage temp dir that is a sibling to the real quarantine dir and shares its exact prefix (e.g. `<prefix>x/...`), and (3) issuing a repository RPC that calls `ObjectDirectoryPath` (e.g. `GetObjectDirectorySize`) with that crafted value to confirm the check is bypassed.

func ValidateRelativePath(rootDir, relativePath string) (string, error) {
	absPath := filepath.Join(rootDir, relativePath)
	if rootDir != absPath && !strings.HasPrefix(absPath, rootDir+string(os.PathSeparator)) {
		return "", ErrRelativePathEscapesRoot
	}

	return filepath.Rel(rootDir, absPath)
}
