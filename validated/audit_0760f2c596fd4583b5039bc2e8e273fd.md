### Title
Front-runnable global oracle `last-update` monotonic timestamp allows any user to DoS price-dependent market operations (borrow, collateral-add, repay, liquidate) - ([File: mainnet/contracts/market/v0-4-market.clar])

### Finding Description
`price-resolve` maintains a single **global, per-feed** state map, `last-update`, keyed only by `{type, ident}` (the oracle feed identifier), not by user or position: [1](#0-0) 

Every unprivileged public entry point that needs a price (`collateral-add`, `borrow`, `repay`, `liquidate`, etc., via `get-asset-value`/`get-assets`/`process-collateral-asset`) calls `price-resolve`, which enforces a monotonic-timestamp freshness check and then unconditionally advances the shared `last-update` value to whatever timestamp the *caller-supplied* price feed carries: [2](#0-1) 

Because `oracle-timestamp-fresh` requires `(>= ts prev)`, and `prev` is the shared `last-update` value written by the **most recent caller of any account**, one unprivileged actor can advance `last-update` for a feed ahead of what another pending/mempool transaction is using. This is directly analogous to the `checkTransaction` issue in the external report: a state variable that gates admission of a legitimate call (the cooldown/monotonic timestamp) is writable as a side effect of a publicly-callable function, letting any actor manipulate it and cause other legitimate calls relying on an equal-or-older (but still valid/fresh) price timestamp to revert with `ERR-ORACLE-INVARIANT`.

Concretely: prices are supplied to the market by callers via the optional `price-feeds` argument, decoded/verified by `write-feed`/`write-feeds` (Pyth verification) before being consumed by `price-resolve`. Since Stacks transactions are visible in the mempool before confirmation, an attacker observing a victim's pending transaction (which embeds a signed Pyth update with publish-time `T`) can extract the same Pyth payload and submit their own transaction with a higher-fee/priority using that same or a marginally newer already-published Pyth update (`T' >= T`) first. Once mined, `last-update` for that feed advances to `T'`. If the victim's original transaction is then included afterward and its embedded feed's publish-time is `< T'` (which is the case whenever the attacker used a slightly fresher, but still real, price update than the one the victim had when they built/broadcast their transaction), the victim's call fails the `(>= ts prev)` monotonic check inside `price-resolve` and reverts with `ERR-ORACLE-INVARIANT`, even though the victim's supplied price is legitimately fresh (within `max-staleness`).

### Impact Explanation
This is a **temporary freezing of funds** vector: an attacker can repeatedly front-run and invalidate any user's `borrow`, `repay`, `collateral-remove`, or `liquidate` transaction that depends on the affected asset's price feed, by resubmitting a fresher legitimate Pyth/DIA update just ahead of the victim's transaction. Since the check is purely about relative ordering of the global `last-update` value vs. the caller's embedded timestamp, a persistent attacker (even at negligible cost, since Pyth updates are freely republishable and don't require special permission) can indefinitely block a targeted user's transactions on a given feed/asset, most critically **blocking timely self-repayment or collateral top-up right before a user would otherwise become liquidatable, or blocking liquidators from liquidating an undercollateralized position** — both are forms of temporary freezing of funds for the affected principals.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to observe a target's pending transaction in the mempool (standard MEV/front-running assumption on this chain) and race a resubmission of a valid Pyth update ahead of it. No special privileges, flashloans, or DAO compromise are needed — any unprivileged principal can call the public market entry points with fresh price feeds. The bug is a direct structural analog of the reported class: a state variable meant to gate legitimate execution is globally shared and mutated as a side effect of any unprivileged call.

### Recommendation
Do not use a single global monotonic `last-update` per feed to gate correctness of concurrent, unrelated callers' transactions. Options:
- Track freshness only via the caller-supplied timestamp compared against `stacks-block-time` and the asset's `max-staleness`, without requiring `ts >= prev` against a shared, publicly-advanceable state.
- If monotonicity must be preserved (e.g., to prevent replay of stale/older price data being fed intentionally), decouple it from cross-user blocking effects, or allow a caller's own transaction to succeed as long as its `ts` is within `max-staleness` of `stacks-block-time`, regardless of a globally-advanced `last-update` set by another party in the same block window.

### Proof of Concept
1. Victim builds transaction `borrow`/`repay`/`liquidate` referencing asset A with a legitimate signed Pyth update `feedV` (`publish-time = T`), and broadcasts it.
2. Attacker observes the pending transaction, obtains a newer legitimate Pyth update for the same feed (`publish-time = T' > T`, still within Pyth's normal cadence), and submits their own transaction (e.g., a trivial `collateral-add` with 0/negligible amount, or any function that triggers `price-resolve` for that feed) with higher priority/fee.
3. Attacker's transaction confirms first; `price-resolve` executes the `(> timestamp last-update-time)` branch and sets `last-update` for the feed key to `T'`: [3](#0-2) 
4. Victim's transaction confirms next; `oracle-timestamp-fresh` now evaluates `(>= T T')` as `false` since `T < T'`, causing `price-resolve` to `asserts!` fail with `ERR-ORACLE-INVARIANT`, reverting the victim's `borrow`/`repay`/`liquidate` call: [4](#0-3) 
5. Attacker repeats this each time the victim resubmits, indefinitely delaying the victim's ability to repay/top-up collateral or a liquidator's ability to liquidate.

```text
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
```
