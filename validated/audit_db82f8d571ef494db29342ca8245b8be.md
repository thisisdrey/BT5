### Title
Anti-replay window check-then-act race allows a duplicate/replayed packet to be decrypted concurrently with a legitimate one - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` release `decryptLock` between the anti-replay `window.Check` call and the later `window.Update` call that actually marks the counter as consumed. This check-then-act gap is structurally the same bug class as the LlamaLocker report: a piece of per-message "lock" state (the replay-window bit for a given counter) is read, acted upon (decryption), and only cleared/marked afterward — with no atomicity guaranteeing the check and the mark happen as one operation. In LlamaLocker this let an attacker unlock the same NFT twice and corrupt a global counter; in Nebula the same pattern creates a window where two goroutines processing the same or overlapping counters can both pass `Check` before either calls `Update`.

### Finding Description
`Decrypt` (and `VerifyRelay`) in `connection_state.go` do:
```go
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)
cs.decryptLock.Unlock()          // <-- lock released here
...
out, err = cs.dKey.DecryptDanger(...)   // AEAD decrypt happens unlocked
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)   // state is only "cleared"/marked here
cs.decryptLock.Unlock()
``` [1](#0-0) 

`Bits.Check` only reads the sliding-window bitmap and `Bits.Update` is what actually marks/clears bits for the counter [2](#0-1) . Because the lock is dropped between these two calls, the replay-window state for a given counter is not atomically checked-and-marked, mirroring the `locks[tokenId]` clearing gap in the reported bug: the "is this replay/lock slot already consumed" check and the actual state mutation are two separate critical sections that a concurrent second processor of the same packet can interleave with.

This is reachable without a CA-signed certificate by a network attacker who can capture/replay a UDP packet that was already observed on the wire (nonce/replay handling category), since Nebula supports multiple concurrent UDP reader routines via `routines`/`listen.routines`, each independently invoking `readOutsidePackets` → `Decrypt` for packets that resolve to the same `HostInfo`/`ConnectionState` [3](#0-2) [4](#0-3) . A duplicated on-wire packet distributed via `SO_REUSEPORT` across routines can therefore be picked up by two goroutines simultaneously, both passing the unlocked `Check`, both entering `DecryptDanger`, and racing on `Update`.

The CHANGELOG's own history confirms this exact code path is fragile: "Lock replay window updates so concurrent readers can't corrupt it" (#1802) and "Advance the replay window on relayed packets so a relay drops replayed frames instead of re-forwarding them" (#1751) [5](#0-4) , and a dedicated relay-replay regression test now exists specifically because the replay window previously wasn't advanced/locked correctly on some paths [6](#0-5) . This shows the project already treats "replay window state not being updated atomically with the check" as a real, previously-exploited bug class in this exact subsystem, and the current `Check`-then-unlock-then-`Update` structure in `Decrypt`/`VerifyRelay` retains that same shape of race.

### Impact Explanation
If two goroutines race through `Check` before either calls `Update`, both will perform a full AEAD decrypt of the duplicated packet before the replay window state is finalized. While the AEAD decryption itself is deterministic and only one goroutine's `Update` call will ultimately succeed (the loser gets `ErrAlreadySeen`), the check-and-mark operation is not atomic, which means the correctness of the anti-replay window depends on undocumented interleaving rather than an enforced invariant. This is exactly the kind of "forgot to atomically clear/mark the consumed state" defect the reported bug class targets, and it weakens the guarantee that a given message counter is processed at most once, which is the core security property replay windows exist to provide.

### Likelihood Explanation
Exploitability depends on an attacker being able to get a duplicate/replayed UDP datagram delivered to two different reader routines close enough in time to race the unlocked window between the two lock sections — feasible when `routines > 1` (a supported, documented configuration) and the underlying socket uses `SO_REUSEPORT`, letting an attacker-controlled duplicate packet land on two queues nearly simultaneously.

### Recommendation
Hold `decryptLock` across the entire check-decrypt-mark sequence in `Decrypt` and `VerifyRelay` (or otherwise make the "check window bit" and "mark window bit" operations atomic with respect to concurrent callers for the same `ConnectionState`), rather than releasing and reacquiring the lock between `Check` and `Update`.

### Proof of Concept
Not independently reproduced against a running instance in this investigation — this analysis is based on static code reading of `connection_state.go` (the unlock between `Check` and `Update`) combined with the multi-routine UDP dispatch path in `interface.go`, and the project's own CHANGELOG entries documenting prior concurrency bugs in exactly this replay-window code. I could not fully confirm within the available tool budget whether the second (losing) goroutine's already-decrypted plaintext is ever forwarded to the tun device before `Update` rejects it, which would be needed to prove concrete double-delivery impact rather than a benign race that self-corrects at the `Update` step. A background Devin session with the full repo and a test harness would be needed to write a concurrent-goroutine reproduction against `ConnectionState.Decrypt` to determine definitively whether this race has observable security impact beyond redundant decryption work.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

func (b *Bits) strictlyWithinWindow(i uint64) bool {
	// Handle the case where the window hasn't slid yet. This avoids u64 underflow.
	inWarmup := b.current < b.length
	if i < b.length && inWarmup {
		return true
	}

	// Next, if the packet is in-window, see if we've seen it before
	if i > b.current-b.length {
		return true
	}
	return false //not within window!
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

// Update has three branches:
//   - i == b.current+1: fast path; advance the cursor by one and lose-count
//     the slot we just stomped (only past warmup; see the i > b.length guard
//     below).
//   - i  >  b.current+1: jump path; clear all slots between current and i
//     (or up to a full window's worth, whichever is smaller) via clearRange,
//     then mark i. Two arms here: a warmup arm that handles the very first
//     window before the cursor has slid, and a steady-state arm that treats
//     every cleared empty slot as a lost packet.
//   - i  <= b.current: in-window check for duplicates; out-of-window otherwise.
//
// NewBits seeds bits[0]=1 so counter 0 looks "received" — Update never
// clears that marker during warmup (clearRange skips position 0 when
// startPos=1), and once b.current >= b.length the marker is no longer
// consulted. The marker prevents a fictitious "lost" hit on the first real
// counter.
func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}

func (f *Interface) listenOut(i int) {
	var li udp.Conn
	if i > 0 {
		li = f.writers[i]
	} else {
		li = f.outside
	}

	ctCache := firewall.NewConntrackCacheTicker(f.ctx, f.l, f.conntrackCacheTimeout)
	lhh := f.lightHouse.NewRequestHandler()
	plaintext := make([]byte, udp.MTU)
	h := &header.H{}
	fwPacket := &firewall.Packet{}
	nb := make([]byte, 12, 12)

	err := li.ListenOut(func(fromUdpAddr netip.AddrPort, payload []byte) {
		f.readOutsidePackets(ViaSender{UdpAddr: fromUdpAddr}, plaintext[:0], payload, h, fwPacket, lhh, nb, i, ctCache.Get())
	})

	// An error after teardown began is shutdown noise, the closed flag covers resources
	// Close releases itself and the cancelled ctx covers ones torn down by their owners
	// reacting to it, like the user device pipes
	if err != nil && !f.closed.Load() && f.ctx.Err() == nil {
		f.l.Error("Error while reading inbound packet, closing", "error", err)
		f.onFatal(err)
	}

	f.l.Debug("underlay reader is done", "reader", i)
}
