### Title
Non-constant-time HTTP auth-token comparison enables timing-based secret recovery and downstream unauthorized writes - (File: `stackslib/src/net/api/postblock_v3.rs`, `postblock_proposal.rs`, `blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, `txsimulate.rs`)

### Summary
Every HTTP RPC handler that gates a privileged endpoint behind the node's `auth_token` compares the client-supplied `Authorization` header to the configured secret using a plain, short-circuiting string comparison (`auth_header != password`) rather than a constant-time comparison. This is the same bug class as CVE-2024-26268 (timing-based secret/credential inference): a remote, unauthenticated attacker can use response-time differences to incrementally recover the secret one byte at a time, then use the recovered token to reach write-capable endpoints.

### Finding Description
The following handlers all perform the identical pattern in `try_parse_request`: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

In each case, `auth_header != password` uses Rust's default `PartialEq` for `String`/`&str`, which is implemented via byte-slice comparison (`memcmp`-style, first-byte-mismatch-short-circuits). This is not a constant-time comparison. An attacker who can measure round-trip latency with enough precision (repeated sampling averages out network jitter) can distinguish "matched N bytes then failed" from "matched N+1 bytes then failed," recovering the `auth_token` byte-by-byte — structurally identical to the Liferay timing-based user-enumeration bug (CWE-203), just applied to a shared secret comparison instead of a username-existence check.

This matters because `auth_token` gates security-relevant surface: it authorizes `broadcast=1` writes on `POST /v2/blocks` (`postblock_v3.rs`, which sets `authenticated` before allowing the block broadcast), and it also gates `/v3/block_proposal`, `/v3/blocks/replay/*`, `/v3/blocks/simulate/*`, `/v3/transactions/simulate`, and `/v3/contracts/fast-call-read/*`. The config docs confirm this token "secures the communication channel between this node and a connected `stacks-signer` instance" and gates block-broadcast and block-proposal endpoints: [6](#0-5) 

### Impact Explanation
If an attacker can recover `auth_token` via timing analysis, they gain the ability to make authenticated requests to endpoints that would otherwise be closed to unauthenticated network peers, including forcing broadcast of a block via `POST /v2/blocks?broadcast=1` (an unauthorized write path) as shown in `postblock_v3.rs`'s `authenticated` gate: [7](#0-6) 

This matches the "unauthenticated/unauthorized write to state" Critical impact bucket, since the auth gate is the sole control standing between an unauthenticated remote peer and a privileged write/administrative endpoint.

### Likelihood Explanation
Exploiting this requires a large number of precisely-timed requests and a low-noise network path to the target node, which is a nontrivial but realistic prerequisite for timing side-channel attacks over HTTP (well documented against services running behind minimal network jitter, e.g. same-datacenter or local attacks). This is consistent with the original CVE's own threat model, which is also purely timing-based over the network. It is not a volumetric/DDoS attack — it's a targeted, low-bandwidth oracle abuse of a specific equality check.

### Recommendation
Replace the direct `!=`/`==` string comparisons against `auth_token` in `postblock_v3.rs`, `postblock_proposal.rs`, `blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, and `txsimulate.rs` with a constant-time comparison (e.g., `subtle::ConstantTimeEq`) applied to the byte representations of the header value and the configured secret, ensuring equal-length inputs are compared over their full length regardless of where the first mismatch occurs, and reject unequal-length inputs without leaking length information (compare against a fixed-size digest, e.g., HMAC of both sides, instead of raw string length).

### Proof of Concept
1. Configure a node with `connection_options.auth_token` set.
2. Send repeated `POST /v3/block_proposal` (or `/v2/blocks?broadcast=1`, `/v3/blocks/simulate/...`, etc.) requests with `Authorization` headers that are correct up to a prefix of length `k` and differ at byte `k`.
3. Measure response latency for many trials at each candidate byte value for position `k`; the correct byte value will (on average, after averaging out jitter) show a measurably different timing profile from incorrect ones at the comparison call site (`auth_header != password`), because the comparison exits earlier for mismatches at smaller `k`.
4. Repeat incrementally for each byte position to reconstruct the full `auth_token`, then replay it to reach the authenticated write endpoint.

        let mut broadcast = false;

        // look for authorization header
        if let Some(password) = &self.auth {
            if let Some(auth_header) = preamble.headers.get("authorization") {
                if auth_header != password {
                    return Err(Error::Http(401, "Unauthorized".into()));
                }
                authenticated = true;
            }
        }

        // see if broadcast=1 is set
        for (key, value) in form_urlencoded::parse(query.as_ref().unwrap_or(&"").as_bytes()) {
            if key == "broadcast" {
                broadcast = broadcast || value == "1";
            }
        }

        if broadcast && !authenticated {
            return Err(Error::Http(401, "Unauthorized".into()));
        }
