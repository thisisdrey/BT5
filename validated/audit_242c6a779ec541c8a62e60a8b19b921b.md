### Title
Unbounded memory allocation from attacker-controlled length field in `BatchValidateSign`/`ValidateMultiSign` precompiles — analog to CVE-2022-32206 "malloc bomb" - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
CVE-2022-32206 describes curl trusting a server-declared "decompressed length" and blindly allocating memory to match it, letting a tiny compressed payload trigger unbounded heap growth. The analogous pattern in java-tron is `PrecompiledContracts.extractBytes32Array`, which reads an attacker-supplied 32-byte word as an array length and immediately allocates a Java array of that size — before any size cap or gas-proportional check is applied — when a transaction calls the `batchvalidatesign` TVM precompile.

### Finding Description
`extractBytes32Array` is: [1](#0-0) 
It takes `len` directly from a caller-controlled `DataWord` (`words[offset].intValueSafe()`) and allocates `new byte[len][]` unconditionally, with no upper bound check before the allocation.

In `BatchValidateSign.doExecute`, this method is called **unconditionally**, unlike the sibling call to `extractBytesArray`/`extractSigArray`, which is only pre-guarded by a `MAX_SIZE` (16) check when the `allowTvmSelfdestructRestriction` feature is enabled: [2](#0-1) 

Note that the `sigArraySize`/`addrArraySize` bound in the `if (VMConfig.allowTvmSelfdestructRestriction())` block only guards the `extractSigArray`/`extractBytesArray` selection — the very next line, `extractBytes32Array(words, words[2].intValueSafe() / WORD_SIZE)`, is invoked regardless of that feature flag or the size check, so the addresses-array length is never bounded before the allocation happens.

The energy/gas cost for this precompile is computed purely from the **actual calldata length**, not from the attacker-declared array-length field: [3](#0-2) 
This means a tiny calldata payload (a few hundred bytes) can encode a length word close to `Integer.MAX_VALUE` at the `words[2]`-referenced offset, costing minimal energy, while `extractBytes32Array` attempts to allocate an array with billions of `byte[]` slots — a multi-gigabyte allocation attempt sized entirely by the attacker, decoupled from the metered/paid-for resource.

`ValidateMultiSign.execute` has a similar structure and is worse: the call to `extractBytesArray`/`extractSigArray` for the `signatures` array sits **outside any try/catch**, so an `OutOfMemoryError`/`NegativeArraySizeException` thrown during allocation propagates directly out of `execute()`: [4](#0-3) 

### Impact Explanation
Any account can trigger this by deploying a small contract that calls `batchvalidatesign(bytes32,bytes[],address[])` (address gated only by `VMConfig.allowTvmSolidity059()`, a standard already-activated TIP) with crafted calldata where the addresses-array length word is set to a very large value while the actual buffer is tiny. This forces the executing node — every full node/witness node that must replay the transaction to validate/apply the block — to attempt a huge heap allocation for negligible energy cost. Depending on JVM heap headroom this can:
- Trigger `OutOfMemoryError` under memory pressure, and in `ValidateMultiSign` this error is not locally caught, so it propagates out of the precompile and up through VM opcode dispatch, risking abnormal termination of block/transaction processing on the node.
- Cause severe GC pressure / latency spikes across all nodes that must independently re-execute the same transaction while syncing/validating a block, which is a node-availability impact reachable purely by an anonymous unprivileged contract caller (no special SR/witness/committee privilege required) — a Medium-severity DoS analog to the curl "malloc bomb".

### Likelihood Explanation
High reachability: `batchvalidatesign` is exposed to any TVM contract call and reachable from a plain `TriggerSmartContract` transaction. Crafting the malicious ABI payload requires only setting a 32-byte length word arbitrarily; no signature validity or account state is required to reach the vulnerable allocation, since the length/allocation happens before any of the downstream signature/address correctness checks.

### Recommendation
- In `extractBytes32Array` (and `extractBytesArray`/`extractSigArray`), validate `len` against a hard cap (e.g., `MAX_SIZE`) and against the actual remaining bytes in `data`/`words` **before** allocating the array, mirroring the existing `isValidAbiEncoding` bound check already used elsewhere in the file.
- In `BatchValidateSign.doExecute`, make the `addrArraySize`/`sigArraySize` bound check unconditional (not gated behind `allowTvmSelfdestructRestriction`), and perform it before calling `extractBytes32Array`.
- Wrap precompile array-extraction logic (in `ValidateMultiSign.execute` in particular) in a try/catch consistent with `BatchValidateSign.execute`, so an oversized/malformed length cannot escape as an uncaught `Error`.
- Charge energy proportional to the attacker-declared array length (not just calldata length) prior to allocation, consistent with EVM/TVM's gas-for-resource design.

### Proof of Concept
1. Deploy a minimal contract exposing a passthrough call to precompile `0x66` (BatchValidateSign address) or directly encode a `TriggerSmartContract` calldata for `batchvalidatesign(bytes32,bytes[],address[])`.
2. ABI-encode calldata so that:
   - word[0] = arbitrary 32-byte hash
   - word[1] = offset pointing to a `signatures` array with a small, valid length (e.g., 1)
   - word[2] = offset pointing to the `addresses` array
   - at the `addresses` offset, set the length word to `0x7FFFFFFF` (or another very large value near `Integer.MAX_VALUE`) while providing far fewer actual trailing words.
3. Submit as a `TriggerSmartContract` (or `TriggerConstantContract` for a cheaper constant-call probe) transaction with sufficient `fee_limit`.
4. Observe that `extractBytes32Array` attempts `new byte[0x7FFFFFFF][]`, causing a multi-gigabyte allocation attempt / `OutOfMemoryError` on the executing node, disproportionate to the small calldata size and its computed energy cost.

Note: I was unable to fully trace the exact call path from `Program`/opcode dispatch into `PrecompiledContract.execute()` (e.g., whether a generic `catch (Throwable)` wraps precompile invocation at the VM level) due to index truncation of `OperationActions.java`/`Program.java`; a Devin session with full repo access would be needed to confirm whether the uncaught `Error` path in `ValidateMultiSign` can actually propagate past the VM's top-level exception handling, which affects whether the impact is "energy metering bypass + heap pressure only" versus "node crash."

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }
