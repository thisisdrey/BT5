### Title
Remote stack-overflow crash via deeply-nested JSON in `try_parse_error_response` - ([File: stackslib/src/net/http/error.rs])

### Summary
`try_parse_error_response` decodes an HTTP error body with `Content-Type: application/json` by piping a `BoundReader` (capped at `MAX_MESSAGE_LEN` bytes) into `serde_json::from_reader`. Byte-length bounding does not bound JSON nesting depth: `serde_json`'s default `Value` deserializer recurses once per array/object nesting level with no depth guard, so a small, well-under-cap payload consisting of hundreds of thousands of nested `[` characters can exhaust the stack before the byte cap is ever reached.

### Finding Description
The code assumes that because the reader is bounded to `MAX_MESSAGE_LEN` bytes [1](#0-0) , decoding is safe. That equality ("bounded bytes" ⇒ "bounded stack usage") does not hold for `serde_json::from_reader` when deserializing into `serde_json::Value` (used implicitly here since `json_val` is returned as `HttpResponsePayload::JSON`): each nested array/object token invokes another level of recursive descent in the parser with no built-in recursion-depth limit. A body like `"[[[[[[[[..."` repeated N times costs only N bytes but N stack frames. With N in the low hundreds of thousands (well within `MAX_MESSAGE_LEN`, which is tens of megabytes), the parser recurses past the thread's stack size and the process aborts (SIGSEGV/stack overflow), not returning `Err`.

This function is reachable whenever this node acts as an HTTP client and receives an error status (400–599) with `Content-Type: application/json` from any remote HTTP peer it queries, via every `HttpErrorResponse::try_parse_response` implementation (`HttpBadRequest`, `HttpUnauthorized`, `HttpNotFound`, `HttpServerError`, etc.), all of which forward directly to `try_parse_error_response` [2](#0-1) [3](#0-2) . Any remote, unprivileged peer running its own HTTP server that this node connects to for outbound RPC (block/inventory/mempool fetches, etc.) can trigger this by simply returning a 500/400/etc. response with a crafted JSON error body — no authentication, secret, or privileged role is required, only that the target node initiate an HTTP request to the attacker-controlled peer.

Notably, the codebase is aware of this exact vulnerability class elsewhere — Clarity has a dedicated `stack_depth_checker.rs` guard specifically to prevent stack overflow from deeply nested parsed structures — but no equivalent depth-limiting guard exists for the JSON error-response decoding path in `net/http`.

### Impact Explanation
A single crafted HTTP error response from a malicious/compromised remote peer that the victim node happens to make an outbound RPC request to (which is routine, unauthenticated behavior during normal peer networking) crashes the querying node's process via stack overflow. This is a remote, unauthenticated crash from a single message — matching the "Critical: remote crash/unauthenticated DoS from few messages" category. It is trivially repeatable against any Stacks node that connects to the attacker's endpoint.

### Likelihood Explanation
- Attacker needs only to run an HTTP server (or man-in-the-middle a plaintext HTTP RPC connection) that the victim node will query and to answer with a 4xx/5xx status and `Content-Type: application/json`.
- No secret, signature, or privileged peer/slot role is required.
- Cost is trivial: constructing the payload (`"[".repeat(N)`) is cheap, and the response size (hundreds of KB to a few MB) is well under `MAX_MESSAGE_LEN`.
- The exact stack size needed depends on the runtime thread's stack size, but nesting depth is fully attacker-controlled and unbounded by any existing guard in this path, so the attacker can trivially exceed any reasonable default thread stack size.

### Recommendation
Do not rely solely on byte-length bounding for JSON safety. Use a JSON deserializer configuration that limits recursion/nesting depth (e.g., `serde_json::Deserializer::from_reader(..).disable_recursion_limit()` should NOT be used — instead impose an explicit low maximum nesting depth check before/while parsing, or use a non-recursive JSON parser/streaming validator for untrusted input, or run the parse on a dedicated thread with `stacker`/`psm`-style stack growth guards, mirroring the approach already used for Clarity's `stack_depth_checker.rs`). At minimum, reject error-response bodies whose bracket/brace nesting exceeds a small fixed limit (e.g., 128) before calling `serde_json::from_reader`.

### Proof of Concept
```rust
// stackslib/src/net/http/error.rs (test module)
#[test]
fn test_deeply_nested_json_error_response_stack_overflow() {
    use crate::net::http::error::try_parse_error_response;
    use crate::net::http::HttpContentType;

    let depth = 500_000usize;
    let mut body = Vec::with_capacity(depth);
    body.extend(std::iter::repeat(b'[').take(depth));
    // No matching closes needed to trigger recursion during parse of '['

    // Expectation under SAFETY invariant: should return Err(Error::DecodeError(..))
    // Actual: process aborts with stack overflow before returning.
    let result = try_parse_error_response(500, HttpContentType::JSON, &body);
    assert!(result.is_err());
}
```
Run under a constrained stack (e.g., spawn in a thread with a small stack size, or run natively — default OS thread stacks of 2–8MB are already often insufficient for depths in the hundreds of thousands) to observe the abort instead of a graceful `Err`.
