## Finding [1](#0-0) [2](#0-1) 

### Title
`reward_per_token` integer division with an under-scaled precision constant permanently zeroes reward accrual for all pool stakers - (File: substrate/frame/asset-rewards/src/lib.rs)

### Summary
The `asset-rewards` pallet computes the incremental reward-per-token value with a fixed `PRECISION_SCALING_FACTOR` of only `4096` (2^12), instead of a WAD-style (10^18) fixed-point scale used elsewhere in the codebase (e.g. nomination-pools `RewardCounter: FixedU128`). Any unprivileged staker can call the public `stake` extrinsic to inflate `total_tokens_staked` for a pool. Once `reward_rate_per_block * blocks_elapsed * 4096` becomes smaller than `total_tokens_staked`, the integer division in `reward_per_token` truncates to zero every block, permanently stalling reward accrual for that pool — this is the same broken invariant described in the external report (`rate * time / weight` rounding to zero because the numerator's precision multiplier is far smaller than the growth of the denominator).

### Finding Description
`reward_per_token` computes:
```rust
Ok(pool_info.reward_per_token_stored.ensure_add(
    pool_info
        .reward_rate_per_block
        .ensure_mul(rewardable_blocks_elapsed.into())?
        .ensure_mul(PRECISION_SCALING_FACTOR.into())?
        .ensure_div(pool_info.total_tokens_staked)?,
)?)
``` [2](#0-1) 

`PRECISION_SCALING_FACTOR` is defined as `pub(crate) const PRECISION_SCALING_FACTOR: u16 = 4096;` [1](#0-0) . This mirrors the Synthetix `StakingRewards.sol` pattern noted in the pallet's own doc comment [3](#0-2) , but Solidity uses `1e18` precision while this pallet uses `4096` — a difference of roughly 14 orders of magnitude for assets with typical 10-18 decimal balances.

`ensure_div` performs standard integer division (no rounding-up, no checked non-zero result), so whenever `reward_rate_per_block * rewardable_blocks_elapsed * 4096 < total_tokens_staked`, the added term truncates to `0`, and `reward_per_token_stored` does not advance for that period. `derive_rewards` then computes each staker's owed amount as `staker.amount * (reward_per_token - staker.reward_per_token_paid) / PRECISION_SCALING_FACTOR` [4](#0-3) , which is also zero for that window since the delta is zero.

Crucially, `total_tokens_staked` is fully user-controlled: any account can call the public, unprivileged `stake` extrinsic with an arbitrarily large amount of the staked asset [5](#0-4) . There is no minimum-stake floor relative to `reward_rate_per_block`, and `reward_rate_per_block` can only be increased by the admin, not decreased, once a pool has already been created and joined by other stakers [6](#0-5) , so an existing pool cannot self-correct once griefed. Because rewards are computed just-in-time and windows are never retroactively recomputed after the fact, once a block window truncates to zero the rewards for that entire window are permanently lost for every staker in the pool, not just the attacker.

### Impact Explanation
This breaks the "runtime bugs that compromise intended behavior" and "permanent user-fund lock" impact categories: legitimate stakers who have deposited real assets under a `RewardsPool` (a live pallet reachable from any runtime that includes `pallet-asset-rewards`) can have their expected, already-configured reward stream permanently and silently halted by any other unprivileged user, with no way for the pool admin to recover the lost accrual window (only future increases to `reward_rate_per_block` can partially compensate future blocks, and cannot recover the zeroed history). This is a direct denial of intended reward economics for the pool, not a griefing side-effect requiring an admin, validator, or privileged actor.

### Likelihood Explanation
The precision gap (4096 vs 10^18) is large enough that this triggers under completely ordinary usage patterns, not just adversarial ones: any pool configured with a modest `reward_rate_per_block` (measured in a token with typical 10-18 decimals) will hit the zero-truncation the moment enough total value is staked, which is the pool's expected steady-state as it grows successful. An attacker doesn't need any special capability — just enough balance of the staked asset to call `stake` — to deliberately trigger or worsen this for any target pool.

### Recommendation
Replace the fixed `u16` `PRECISION_SCALING_FACTOR` with a full fixed-point representation (e.g., `FixedU128`/WAD-style 10^18 scaling, matching the precision used by `nomination-pools`' `RewardCounter`), or otherwise use `multiply_by_rational_with_rounding`/`Perquintill`-style helpers that preserve precision independent of `total_tokens_staked` growth, exactly as recommended by the external report's `divWadDown`/`mulWadDown` fix.

### Proof of Concept
1. Admin creates a pool with `reward_rate_per_block = 1_000` (in an asset with 12 decimals) via `create_pool`.
2. Staker A stakes a normal amount, e.g. `1_000_000_000_000` (1 unit).
3. Attacker (any unprivileged account holding the staked asset) calls `stake` with a very large amount, e.g. `10_000_000_000_000_000` (10,000,000 units) — nothing prevents this since `stake` has no upper bound relative to `reward_rate_per_block`.
4. From this point, for any `rewardable_blocks_elapsed` where `reward_rate_per_block * rewardable_blocks_elapsed * 4096 < total_tokens_staked` (true here: `1_000 * 4096 = 4_096_000 << 10_000_000_000_000_000`), `reward_per_token` in `substrate/frame/asset-rewards/src/lib.rs` lines 786-810 returns the previous `reward_per_token_stored` unchanged.
5. Any call to `stake`, `unstake`, `harvest_rewards`, or `claim` triggers `update_pool_and_staker_rewards` → `reward_per_token`, confirming Staker A (and any other participant) accrues zero additional rewards for all elapsed blocks, despite the pool continuing to emit its configured `reward_rate_per_block`.

			let staker = ensure_signed(origin)?;

			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;

				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.
			pool_info.total_tokens_staked.ensure_add_assign(amount)?;

			Pools::<T>::insert(pool_id, pool_info);

			// Update PoolStakers.
			staker_info.amount.ensure_add_assign(amount)?;
			PoolStakers::<T>::insert(pool_id, &staker, staker_info);

			// Emit event.
			Self::deposit_event(Event::Staked { staker, pool_id, amount });

			Ok(())
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}

	fn set_pool_reward_rate_per_block(
		admin: &T::AccountId,
		pool_id: PoolId,
		new_reward_rate_per_block: T::Balance,
	) -> DispatchResult {
		let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
		ensure!(pool_info.admin == *admin, BadOrigin);
		ensure!(
			new_reward_rate_per_block > pool_info.reward_rate_per_block,
			Error::<T>::RewardRateCut
		);

		// Always start by updating the pool rewards.
		let rewards_per_token = Self::reward_per_token(&pool_info)?;
		let mut pool_info = Self::update_pool_rewards(&pool_info, rewards_per_token)?;

		pool_info.reward_rate_per_block = new_reward_rate_per_block;
		Pools::<T>::insert(pool_id, pool_info);

		Self::deposit_event(Event::PoolRewardRateModified { pool_id, new_reward_rate_per_block });

		Ok(())
	}
