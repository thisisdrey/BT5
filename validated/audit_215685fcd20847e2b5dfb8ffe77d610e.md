### Title
Stale `PromiseYieldReceipt`/`PromiseYieldTimeout` entries survive `DeleteAccount` and are delivered/executed against a subsequently recreated account of the same name - ([File: `core/store/src/utils/mod.rs`, `runtime/runtime/src/lib.rs`])

### Summary
`remove_account` (called on `DeleteAccount`) purges `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` rows, but never touches `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, or the account-agnostic `TrieKey::PromiseYieldTimeout` queue. `resolve_promise_yield_timeouts` only checks for the existence of the `PromiseYieldReceipt` row (not account existence or incarnation) before synthesizing and delivering a `PromiseResume` receipt to `queue_entry.account_id`. If the account was deleted and a new, unrelated account is created under the same name before the timeout height, the leftover receipt (including any escrowed deposit attached via `promise_yield_create_with_id`) is executed against the new account.

### Finding Description
`promise_yield_create`/`promise_yield_create_with_id` always set `receiver_id = current_account_id` (self-callback) and persist three account-keyed rows: `PromiseYieldReceipt{receiver_id, data_id}`, `PromiseYieldStatus{receiver_id, data_id}`, and a global-queue `PromiseYieldTimeout{index, account_id, data_id, expires_at}` [1](#0-0) .

`remove_account`, the primitive invoked when an account is deleted, removes `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData`, but contains no call to `remove_promise_yield_receipt`, `remove_promise_yield_status`, or any logic to purge matching `PromiseYieldTimeout` queue entries: [2](#0-1) . Note that `PROMISE_YIELD_RECEIPT` and `PROMISE_YIELD_STATUS` are explicitly listed as "columns with account ID in key" [3](#0-2) , yet `remove_account` does not iterate/clean them.

`resolve_promise_yield_timeouts`, run at the end of each chunk's receipt processing, walks the timeout queue in `expires_at` order and, for each expired entry, checks only `state_update.contains_key(&PromiseYieldReceipt{account_id, data_id})` — not whether the account still exists or is the same incarnation — before synthesizing a `PromiseResume{data: None}` receipt destined for `queue_entry.account_id`: [4](#0-3) .

When that resume receipt is processed, `process_receipt`'s `PromiseResume` branch looks up `get_promise_yield_receipt(state_update, account_id, data_receipt.data_id)` (still present because it was never cleaned up), removes it, and immediately executes it via `apply_action_receipt` — with no check that the account is the same incarnation that created the yield: [5](#0-4) .

Exploit flow:
1. `victim.near` calls `promise_yield_create_with_id` with a long `expires_at`, attaching a non-zero `amount` deposit to the callback `FunctionCall` action (the deposit is deducted from `victim.near`'s balance at creation time and embedded in the stored receipt) [6](#0-5) .
2. `victim.near`'s own contract logic (e.g. an exit/migration flow) issues `DeleteAccount` before the timeout fires. `remove_account` clears the account/code/keys but leaves `PromiseYieldReceipt`, `PromiseYieldStatus`, and the queued `PromiseYieldTimeout` entry untouched.
3. An unprivileged attacker, who can observe the pending queue entry's `account_id`, `data_id`, `method_name`, and `expires_at` via public state (the queue/receipt rows are readable via RPC `view_state`), submits an ordinary `CreateAccount` transaction recreating `victim.near` before the timeout height, optionally deploying a contract implementing the observed callback `method_name`.
4. At `expires_at`, `resolve_promise_yield_timeouts` finds the `PromiseYieldReceipt` still present and forwards a `PromiseResume` to `victim.near` (now attacker-owned).
5. `process_receipt` finds the stale `PromiseYieldReceipt`, removes the bookkeeping rows, and executes the embedded `FunctionCall` action — including crediting/using the escrowed deposit — against the attacker's freshly created account, with `predecessor_id == receiver_id` (self-call / `sir=true` trust), which many contracts use to gate privileged internal logic.

No existing check (signature, nonce, access-key, or account-identity/incarnation validation) prevents this because the resolution path is keyed purely by `(account_id, data_id)` string/hash equality, with no incarnation nonce or account-creation-height binding.

### Impact Explanation
This breaks the invariant that a receipt/escrowed value created for one account incarnation must resolve only against that same incarnation. Concretely it enables: (a) misdirection of an escrowed deposit (from `promise_yield_create_with_id`) to a party that did not own the account when the yield was created — a fund-theft/fund-misdirection scenario — and (b) delivery of a self-trusted (`predecessor_id == receiver_id`) function call, with attacker-chosen contract code, that many applications treat as an internally-authorized callback. This falls under the "theft of user funds" and "authorization escalation across accounts/promises" bounty categories.

### Likelihood Explanation
Preconditions are narrow but realistic and require no privileged access: a victim contract must (1) use `promise_yield_create_with_id` with an attached deposit and a long timeout, and (2) support self-deletion (`DeleteAccount`) while such a yield is still outstanding — a pattern plausible in escrow/marketplace/DAO-style contracts with exit/migration flows. The attacker's only actions are standard, publicly-available operations: reading state via RPC and submitting a `CreateAccount` (and optional `DeployContract`) transaction before the timeout height — well within the "ordinary funded client" threat model. Cost to the attacker is minimal (storage staking for the new account) and the attack is repeatable whenever such a sequence occurs.

### Recommendation
When executing `DeleteAccount`, iterate and remove any `PromiseYieldReceipt`/`PromiseYieldStatus` rows keyed to the deleted `account_id`, and mark/skip corresponding entries in the `PromiseYieldTimeout` queue (e.g., tombstone by index or bind timeout entries to an account "incarnation" nonce that is checked in `resolve_promise_yield_timeouts` and in `process_receipt`'s `PromiseResume` handling) so a resume can never be delivered to, or executed against, an account incarnation different from the one that created the yield.

### Proof of Concept
Test-loop integration test:
1. Deploy a contract on `victim.near` exposing: a method that calls `promise_yield_create_with_id` with a nonzero attached `amount` and a long `yield_timeout_length_in_blocks`, and a `DeleteAccount` action to self-destruct.
2. Submit a transaction invoking the yield-create method, then in a following transaction issue `DeleteAccount` for `victim.near` before the timeout height, before the yield is resumed.
3. As a separate signer (simulating the attacker), submit `CreateAccount`/`DeployContract` recreating `victim.near` with a contract implementing the same callback `method_name`, before `expires_at`.
4. Advance the test-loop environment to the timeout block height and assert:
   - Before fix: the resume receipt is delivered and the callback executes against the recreated account (state mutation/deposit observed on the new account, verified via `assert_no_promise_yield_status_in_state`-style helpers plus balance/state inspection of the new incarnation), demonstrating cross-incarnation execution.
   - After fix: the resume errors out / is silently dropped because the queue entry or receipt was invalidated at `DeleteAccount` time, and no execution/deposit crediting occurs against the new account.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
