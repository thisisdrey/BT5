### Title
Cross-StackerDB slot signature replay due to missing contract-ID binding in `SlotMetadata::auth_digest` - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata`/`StackerDBChunkData` signatures authenticate only `(slot_id, slot_version, data_hash)`, never the identity of the StackerDB (`QualifiedContractIdentifier`) the chunk is being written to. All the downstream checks (`StackerDBTx::try_replace_chunk`, `PeerNetwork::validate_received_chunk`, `StackerDBSync::validate_downloaded_chunk`, and the `poststackerdbchunk` RPC handler) verify that signature only against the *slot owner recorded for that particular contract's slot table* — but nothing in the signed digest itself ties the signature to that contract. This breaks the intended equality "a chunk signature is valid only for the specific StackerDB/slot it was produced for" and instead makes it valid for *any* StackerDB where the same address happens to own the same `slot_id`, as long as the version requirement is satisfied.

### Finding Description
The digest that gets signed is computed purely from local, contract-independent fields: [1](#0-0) 

```
fn auth_digest(&self) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
``` [2](#0-1) 

`verify()` recovers the public key from this same context-free digest and compares its `Hash160` against a caller-supplied `principal: &StacksAddress`. The *contract binding* only happens one layer up, where the caller looks up which address is supposed to own `slot_id` in a specific contract's slot table and passes that address in: [3](#0-2) 

```
let slot_validation = self
    .get_slot_validation(smart_contract, slot_desc.slot_id)?
    .ok_or(net_error::NoSuchSlot(...))?;

if !slot_desc.verify(&slot_validation.signer)? {
    return Err(net_error::BadSlotSigner(...));
}
```

Because the signed bytes carry no contract identifier, any valid, previously-observed signature for `(slot_id, slot_version, data_hash)` produced by signer `S` for StackerDB **A** will *also* pass `verify()` against StackerDB **B**, provided `S` is also the recorded owner of the same `slot_id` in **B**'s slot table (`get_slot_validation`/`get_slot_signer` per `smart_contract`) and `slot_version` exceeds B's currently stored version. The same context-free digest is used identically in the sync-validation path: [4](#0-3) 

and in the unsolicited-push validation path exercised by `PeerNetwork::handle_unsolicited_StackerDBPushChunk` (confirmed by the existing test `test_handle_unsolicited_stackerdb_push_chunk_future_view_validation`, which only checks slot-id/signer/version, never contract identity, against the digest): [5](#0-4) 

An attacker does not need any private key — they only need to *capture* (from network traffic, or by simply requesting the chunk over the public StackerDB read API) a legitimately-signed chunk that a signer produced for one StackerDB contract, and rebroadcast/`POST` it (via `poststackerdbchunk.rs`, or as a `StackerDBPushChunkData`/`StackerDBChunkInv` p2p message) to a *different* StackerDB contract where that address occupies the same slot index and where the local `slot_version` is currently lower than the replayed chunk's version. Because storage success triggers re-broadcast (`process_stacker_db_chunks` in `relay.rs` unconditionally rebroadcasts anything successfully stored), a successful replay causes network-wide propagation of data that was authenticated for a different context, being accepted and gossiped as canonical, current data for the target StackerDB/slot. [6](#0-5) 

This is a direct analog of the reported bug class: values/identities that are supposed to be *consistent and bound together* (here: "signature commits to a specific slot in a specific StackerDB") are in fact decoupled — the signature commits to slot_id/version/hash only, while the "which StackerDB" component is enforced solely at the caller side via an unauthenticated lookup, allowing the equality to be broken by an attacker who controls only which contract endpoint they submit an already-valid signed chunk to.

### Impact Explanation
This falls under "network-wide propagation of forged[-context] data" / unauthorized write to StackerDB state without possessing the target-context signing capability the protocol intends. Concretely, an unprivileged remote party can, without holding any secret key, get attacker-chosen-context data (a legitimately signed chunk meant for StackerDB A) accepted and stored under a different StackerDB B's slot, and rebroadcast to the whole network as if it were fresh, valid data for B. Depending on which StackerDBs happen to reuse the same signer set/slot layout (e.g., signer message StackerDBs that share the same underlying reward-cycle signer ordering across different message-type contracts, or across successive reward cycles where set membership/ordering coincidentally repeats), this can pollute a StackerDB with stale/misattributed content, or be used to disrupt consensus-adjacent signer communication (e.g., causing followers/miners to observe an out-of-context `SignerMessage` under a slot where fresh, correctly-scoped data was expected). Given the write occurs without the corresponding signer's participation for that specific context, and the effect propagates node-wide via `broadcast_message`, this meets the High/Critical impact bar for "unauthenticated/unauthorized write to StackerDB" and "network-wide propagation of forged data."

### Likelihood Explanation
Exploitability depends on whether a given signer's slot index (as assigned by `get_slot_validation`/`create_stackerdb`'s ordering) coincides across two distinct StackerDB contracts that the node also configures/replicates. Because slot assignment is derived deterministically from the (typically small, PoX-based) reward-cycle signer set ordering, and there are multiple StackerDB contracts sharing the *same* signer-set ordering per reward cycle (e.g., different message-slot StackerDBs for the same signer cohort), same-address/same-slot_id collisions across contracts are plausible without any attacker control over signer selection — only the incidental configuration of the network. This is not a purely theoretical concern; it is a structural property of the signing scheme (context omitted from the signed bytes) rather than a narrow edge case, and no code path was found (in `libstackerdb`, `stackslib/src/net/stackerdb/**`, or the RPC handler) that re-introduces the missing contract binding.

### Recommendation
Include the `QualifiedContractIdentifier` (or a canonical hash of it) of the target StackerDB inside `SlotMetadata::auth_digest()`, so that the signed digest binds slot_id, slot_version, data_hash, *and* the specific StackerDB it is destined for. This requires plumbing the contract identifier into `SlotMetadata::sign`/`verify` (and therefore into `StackerDBChunkData::sign`/`verify`/`recover_pk`), and updating every call site (`try_replace_chunk`, `validate_received_chunk`, `validate_downloaded_chunk`, the `poststackerdbchunk` RPC handler, and `libsigner`'s chunk-signing helpers) to pass the contract identifier through. This is a wire/serialization-format change and needs careful version-gating to avoid breaking existing deployed signers.

### Proof of Concept
Conceptual PoC (cannot be executed without a live testnet, but derivable directly from the code paths cited):
1. Configure/observe two StackerDB contracts, A and B, that share the same PoX signer-set ordering for a given reward cycle (e.g., two message-type StackerDBs for the same signer cohort, or note that `get_slot_validation` assigns slot IDs purely by iteration order of the configured `(StacksAddress, slot_count)` list — see `reconfigure_stackerdb`/`create_stackerdb`).
2. Passively observe (via the public StackerDB chunk read API, or p2p `StackerDBChunkInv`/`StackerDBGetChunkData` exchange) a legitimately-signed `StackerDBChunkData` for contract A, slot `S`, version `V`, produced by signer address `X`, where `X` also owns slot `S` in contract B.
3. Submit that identical `StackerDBChunkData` (same `slot_id`, `slot_version`, `sig`, `data`) to contract B via `POST /v2/stackerdb/.../chunks` (handled by `RPCPostStackerDBChunkRequestHandler::try_handle_request`), or inject it as a `StacksMessageType::StackerDBPushChunk` p2p message.
4. `try_replace_chunk`/`validate_received_chunk` will call `slot_desc.verify(&slot_validation.signer)`, which succeeds because the signature only commits to `(slot_id, slot_version, data_hash)` — none of which differ between A and B — and B's recorded owner for slot `S` is also `X`.
5. If B's current stored version for slot `S` is `< V`, the chunk is accepted, stored, and (per `process_stacker_db_chunks`) rebroadcast to the network as authentic data for contract B's slot `S`, even though `X` never signed anything intending it for B.

    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
