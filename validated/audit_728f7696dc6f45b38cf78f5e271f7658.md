## Analysis: Missing `chain_id` binding in `DefusePayload`/`MultiPayload`

### Finding

The `defuse` intents engine binds a signed `MultiPayload` only to `verifying_contract` (a NEAR `AccountId`) — it never checks a chain/network identifier, unlike the sibling `wallet` contract in the same repo, which explicitly signs and verifies a `chain_id` field.

### Title
Missing `chain_id`/network binding in `DefusePayload` allows a signed `MultiPayload` to settle more than once across chain instances sharing the same `verifying_contract` `AccountId` - (File: `contracts/defuse/core/src/payload/mod.rs`)

### Summary
`DefusePayload` (the payload signed by users for `defuse` intents, wrapped in `MultiPayload`) binds validity only to `signer_id`, `verifying_contract` (an `AccountId`), `deadline`, and `nonce`. Unlike the `wallet` contract in the same repository — which explicitly signs and checks a `chain_id` field via `RequestMessage`/`OffchainMessage` — the `defuse` intents engine (`Engine::execute_signed_intent`) has no analogous check. A signature is therefore valid on any NEAR-protocol-compatible network instance where an account with the identical `AccountId` (`verifying_contract`) and identical public key/nonce state exists, e.g. after a chain split/fork or on a parallel deployment sharing the same contract account name and account/nonce state.

### Finding Description
`Engine::execute_signed_intent` verifies the signature, checks `verifying_contract != *self.state.verifying_contract()`, checks the deadline, checks the signer's public key, and commits the nonce — but the entire binding to "this network" rests solely on the `AccountId` string equality of `verifying_contract`, with `verifying_contract` itself just being `env::current_account_id()` at execution time [7](#0-6) [3](#0-2) .

`AccountId` alone carries no chain/genesis/network identity — it is only unique within a single running network instance. If a hard fork or chain split occurs (the exact scenario in the original report) — or if a second network instance is deployed/bootstrapped with the same account naming and account state (e.g. same contract account id, same public keys registered, same nonce bitmap state) — a signature valid on one instance remains fully valid on the other, because nothing in `DefusePayload` or the engine's checks differentiates the two networks.

This is a genuine gap relative to the rest of the codebase: the `wallet` module's signed `RequestMessage`/`OffchainMessage` explicitly includes `chain_id` and the verifying contract explicitly rejects a mismatched `chain_id` [8](#0-7) , and NEP-641's `OffchainMessage` schema documents this as a mandatory field for any verifying contract implementing the standard [9](#0-8) . The `defuse` core payload/engine simply omits the equivalent binding.

### Impact Explanation
This breaks the equality that should hold: *"the number of times a signed `MultiPayload` settles" == 1*. If the same `verifying_contract` `AccountId` and account/nonce state exist concurrently on two live chain instances (post-fork or parallel deployment), an attacker (or any third party in possession of the signed payload, since these payloads are typically broadcast/relayed) can replay the exact same signed `MultiPayload` on the second instance, executing the same intent (e.g. a `Transfer`/`FtWithdraw`/`TokenDiff`) a second time and moving/crediting/withdrawing tokens without a second valid authorisation from the signer on that instance. This matches the Critical impact category: "one signed payload settling more than once."

### Likelihood Explanation
Exploitation requires a scenario external to this specific contract's control — a network split or a second live deployment matching account state — which is lower likelihood than an on-chain-only bug, but it is the precise scenario the original report describes and is structurally always possible because the schema and engine provide *no* defense-in-depth against it, whereas the sibling `wallet` module in the same codebase does defend against exactly this by checking `chain_id`.

### Recommendation
Add a network/chain identifier field to `DefusePayload` (and the underlying `Nep413DefuseMessage`/other `MultiPayload` variants), analogous to `chain_id` in `contracts/wallet`/`nep641::OffchainMessage`, and have `Engine::execute_signed_intent` reject any signed payload whose `chain_id` does not match the current network, exactly as `WalletImpl::resolve_auth` already does for `msg.chain_id != env::chain_id()`.

### Proof of Concept
1. User signs a `MultiPayload` (`Nep413`) authorising a `Transfer`/`FtWithdraw` intent against `verifying_contract = "intents.near"`, with a given `nonce`/`deadline`, per `contracts/defuse/core/src/payload/nep413.rs`.
2. A network split occurs, or a second live NEAR-protocol-compatible network instance exists where an account named `intents.near` has been deployed with matching account/public-key/nonce state (mirroring genesis at the fork point, as in the original report's exploit scenario).
3. `Engine::execute_signed_intent` on the second instance validates the same signature (public key/signature checks pass, unrelated to network), confirms `verifying_contract == "intents.near"` (true on both instances), confirms the `nonce` is unused there, and executes the intent — settling the same signed authorisation a second time.

```rust
    fn execute_signed_intent(&mut self, signed: MultiPayload) -> Result<()> {
        // verify signed payload and get public key
        let public_key = signed.verify().ok_or(DefuseError::InvalidSignature)?;

        // calculate intent hash
        let hash = signed.hash();

        // extract NEP-413 payload
        let DefusePayload::<DefuseIntents> {
            signer_id,
            verifying_contract,
            deadline,
            nonce,
            message: intents,
        } = signed.extract_defuse_payload()?;

        // check recipient
        if verifying_contract != *self.state.verifying_contract() {
            return Err(DefuseError::WrongVerifyingContract);
        }

        self.inspector.on_deadline(deadline);

        // make sure message is still valid
        if deadline < Timestamp::now() {
            return Err(DefuseError::DeadlineExpired);
        }

        // make sure the account has this public key
        if !self.state.has_public_key(&signer_id, &public_key) {
            return Err(DefuseError::PublicKeyNotExist(signer_id, public_key));
        }

        // commit nonce
        self.verify_intent_nonce(nonce, deadline)?;
        self.state.commit_nonce(signer_id.clone(), nonce)?;
```
