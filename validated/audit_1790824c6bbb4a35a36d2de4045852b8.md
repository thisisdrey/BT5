### Title
Unfreeze​BalanceV2 never decrements the account's `FreezeV2` ledger, allowing double/triple unfreezing of the same collateral - (File: `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java`)

### Summary
`UnfreezeBalanceV2Actuator.execute()` credits an unfreeze request into `accountCapsule`'s `unfrozenV2List` (which is later paid out as real TRX) and reduces the *global* resource-weight counters, but it never calls the actuator's own `updateAccountFrozenInfo()` method to reduce the *per-account* `FreezeV2.amount` that backs that unfreeze. Because validation only checks against this never-decremented value, the same frozen collateral can be "unfrozen" repeatedly (up to `UNFREEZE_MAX_TIMES = 32` times) by one owner, minting unbacked TRX credit — the same class of bug as the reported `ReachAffiliateDistribution.swapEth()` issue: an amount is subtracted/consumed in one part of the accounting flow (weight reduction, `unfrozenV2List` credit) while a related ledger entry that should mirror it (`FreezeV2.amount`) is left stale, producing an inconsistent, exploitable balance sheet.

### Finding Description
In `execute()`:
```java
accountCapsule.addUnfrozenV2List(freezeType, unfreezeBalance, expireTime);
this.updateTotalResourceWeight(accountCapsule, unfreezeBalanceV2Contract, unfreezeBalance);
this.updateVote(accountCapsule, unfreezeBalanceV2Contract, ownerAddress);
``` [1](#0-0) 

The actuator defines `updateAccountFrozenInfo(ResourceCode freezeType, AccountCapsule accountCapsule, long unfreezeBalance)`, whose entire purpose is to subtract `unfreezeBalance` from the matching entry in `accountCapsule.getFrozenV2List()`: [2](#0-1) 

That method is never invoked anywhere in `execute()`. Meanwhile `validate()`'s `checkUnfreezeBalance()` authorizes the request purely by comparing the requested `unfreezeBalance` against the (never-decremented) `FreezeV2.amount`: [3](#0-2) 

So the flow is: `updateTotalResourceWeight` (global weight, using `accountCapsule.getFrozenV2BalanceWithDelegated`) is decremented, and a payable `unfrozenV2List` entry is added — both of these represent that collateral has left the "frozen" pool — but the actual `FreezeV2` record used to gate the *next* unfreeze request is untouched. A user can therefore submit the same `UnfreezeBalanceV2Contract` (same resource, same or lesser amount) repeatedly; each call passes `checkUnfreezeBalance` because `frozenAmount` never shrinks, and each call adds another `unfrozenV2List` entry that will later be paid out via `WithdrawExpireUnfreezeActuator`/`unfreezeExpire()`/`CancelAllUnfreezeV2Actuator`, all of which simply sum `unfreezeAmount` from `unfrozenV2List` and credit `accountCapsule.balance`: [4](#0-3) [5](#0-4) 

This mirrors the external report's pattern exactly: one part of the code consumes/moves an amount (weight reduction + payable-list credit) while a companion ledger entry that should be kept in sync (the frozen-balance record backing future validation) is left stale — enabling an "amount" to be effectively double counted.

### Impact Explanation
An account can repeat `UnfreezeBalanceV2Contract` up to 32 times (bounded only by `UNFREEZE_MAX_TIMES` and per-call validation against the stale `frozenAmount`), each time queuing a payable unfreeze entry for the full originally-frozen amount. After the unfreeze delay elapses, all of these entries are redeemable via `WithdrawExpireUnfreezeContract`/`UnfreezeBalanceV2` cancel flows, crediting `accountCapsule.balance` far beyond the TRX that was actually locked as collateral. This is an unbacked-balance/inflation bug: TRX is minted out of thin air for the attacker, and simultaneously the global `TotalNetWeight`/`TotalEnergyWeight` accounting becomes permanently incorrect (repeatedly decremented for collateral that was only frozen once), corrupting bandwidth/energy issuance economics chain-wide.

### Likelihood Explanation
Reachable directly by any unprivileged TRX holder broadcasting an ordinary `UnfreezeBalanceV2Contract` transaction multiple times (no special permissions required, purely account-owner signed). The only friction is the `UNFREEZE_MAX_TIMES` cap and the unfreeze delay before funds are actually withdrawable, but neither of these prevents the fundamental accounting mismatch — an attacker simply needs to wait out the delay (or use `CancelAllUnfreezeV2`) to realize the unbacked TRX. This makes the likelihood high and the exploit trivially repeatable per freeze position.

### Recommendation
Call `updateAccountFrozenInfo(freezeType, accountCapsule, unfreezeBalance)` inside `execute()` (and in the TVM-callable twin, `UnfreezeBalanceV2Processor.execute()`) immediately after adding to `unfrozenV2List`, so the per-account `FreezeV2.amount` is properly decremented in lock-step with the weight reduction and payable-list credit, exactly like `checkUnfreezeBalance` assumes it will be.

### Proof of Concept
1. Freeze `1,000,000` sun for `BANDWIDTH` via `FreezeBalanceV2Contract` (creates one `FreezeV2{type=BANDWIDTH, amount=1,000,000}` entry).
2. Submit `UnfreezeBalanceV2Contract{resource=BANDWIDTH, unfreeze_balance=1,000,000}`.
   - `validate()`'s `checkUnfreezeBalance` passes because `1,000,000 <= frozenAmount(1,000,000)`.
   - `execute()` adds an `UnFreezeV2{amount=1,000,000, expire=now+delay}` entry, reduces global net weight, but leaves `FreezeV2.amount` at `1,000,000` (unchanged) because `updateAccountFrozenInfo` is never called.
3. Repeat step 2 up to `UNFREEZE_MAX_TIMES - 1` more times (bounded by `getUnfreezingV2Count`); each call still passes validation since `frozenAmount` never decreases, queuing another `1,000,000`-sun payable entry.
4. After `unfreezeDelayDays` elapse, call `WithdrawExpireUnfreezeContract` (or `CancelAllUnfreezeV2Contract`): `getTotalWithdrawUnfreeze()` sums all queued `unfreezeAmount` entries and credits the owner's balance with the full sum (e.g., `N × 1,000,000` sun) even though only `1,000,000` sun was ever actually frozen — producing unbacked TRX.

  public boolean checkUnfreezeBalance(AccountCapsule accountCapsule,
                                      final UnfreezeBalanceV2Contract unfreezeBalanceV2Contract,
                                      ResourceCode freezeType) {
    boolean checkOk = false;

    long frozenAmount = 0L;
    List<FreezeV2> freezeV2List = accountCapsule.getFrozenV2List();
    for (FreezeV2 freezeV2 : freezeV2List) {
      if (freezeV2.getType().equals(freezeType)) {
        frozenAmount = freezeV2.getAmount();
        break;
      }
    }

    if (unfreezeBalanceV2Contract.getUnfreezeBalance() > 0
        && unfreezeBalanceV2Contract.getUnfreezeBalance() <= frozenAmount) {
      checkOk = true;
    }

    return checkOk;
  }

  public void updateAccountFrozenInfo(ResourceCode freezeType, AccountCapsule accountCapsule, long unfreezeBalance) {
    List<FreezeV2> freezeV2List = accountCapsule.getFrozenV2List();
    for (int i = 0; i < freezeV2List.size(); i++) {
      if (freezeV2List.get(i).getType().equals(freezeType)) {
        FreezeV2 freezeV2 = FreezeV2.newBuilder()
            .setAmount(freezeV2List.get(i).getAmount() - unfreezeBalance)
            .setType(freezeV2List.get(i).getType())
            .build();
        accountCapsule.updateFrozenV2List(i, freezeV2);
        break;
      }
    }
  }

  public long unfreezeExpire(AccountCapsule accountCapsule, long now) {
    long unfreezeBalance = 0L;

    List<UnFreezeV2> unFrozenV2List = Lists.newArrayList();
    unFrozenV2List.addAll(accountCapsule.getUnfrozenV2List());
    Iterator<UnFreezeV2> iterator = unFrozenV2List.iterator();

    while (iterator.hasNext()) {
      UnFreezeV2 next = iterator.next();
      if (next.getUnfreezeExpireTime() <= now) {
        unfreezeBalance += next.getUnfreezeAmount();
        iterator.remove();
      }
    }

    accountCapsule.setInstance(
        accountCapsule.getInstance().toBuilder()
            .setBalance(accountCapsule.getBalance() + unfreezeBalance)
            .clearUnfrozenV2()
            .addAllUnfrozenV2(unFrozenV2List).build()
    );
    return unfreezeBalance;
  }
