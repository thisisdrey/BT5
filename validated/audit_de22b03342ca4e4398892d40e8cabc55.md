## Finding [1](#0-0) 

### Title
Missing overflow check on `frozenDuration` when computing `expireTime` in `FreezeBalanceProcessor` (TVM `freezeBalance` native contract) - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java)

### Summary
The reported NounsBuilder bug is about `startTime + duration` being cast to a narrower type without a safe-cast/overflow check, letting `endTime` wrap and become smaller than `block.timestamp`. The closest reachable analog in java-tron is `FreezeBalanceProcessor.execute`, which computes `expireTime = nowInMs + param.getFrozenDuration() * FROZEN_PERIOD` with plain `long` arithmetic and no overflow guard, unlike the AssetIssueActuator's `startTime + frozenDays * FROZEN_PERIOD`, which the project explicitly hardened with `StrictMathWrapper.addExact` after the fork `VERSION_4_8_1` specifically to prevent this exact overflow class.

### Finding Description
`FreezeBalanceProcessor` is the native-contract implementation backing the TVM `freezeBalance` opcode (reachable from any deployed smart contract via `Program.java`, i.e. from an unprivileged transaction that triggers a smart contract call). Its `validate()` method checks `frozenBalance` bounds, `frozenCount`, `resourceType`, and receiver-account constraints, but performs **no bound check on `param.getFrozenDuration()`** before it flows into:

```java
long expireTime = nowInMs + param.getFrozenDuration() * FROZEN_PERIOD;
``` [2](#0-1) 

If a contract supplies a sufficiently large `frozenDuration`, the multiplication `param.getFrozenDuration() * FROZEN_PERIOD` (or the subsequent addition with `nowInMs`) can silently overflow `long`, producing an `expireTime` that is arbitrary — including a value smaller than `nowInMs` (i.e., already "expired"), or a large negative number.

This mirrors the exact bug class in the report: an unchecked arithmetic widening/combination of a "start time" and a "duration" value that is then relied upon as an expiry boundary for a time-based state machine, without any `SafeCast`-equivalent (`Math.addExact`/`StrictMathWrapper.addExact`) protection. The codebase itself demonstrates awareness of this precise defect: `AssetIssueActuator.validate()` wraps the analogous computation (`assetIssueContract.getStartTime() + next.getFrozenDays() * FROZEN_PERIOD`) in `StrictMathWrapper.addExact`, throwing `"Start time and frozen days would cause expire time overflow"` if it would overflow: [3](#0-2) 

That guard is missing entirely in `FreezeBalanceProcessor` (and similarly absent in `UnfreezeBalanceV2Processor.calcUnfreezeExpireTime` / `UnfreezeBalanceV2Actuator.calcUnfreezeExpireTime`, which compute `now + unfreezeDelayDays * FROZEN_PERIOD` unchecked) [4](#0-3) [5](#0-4) 
— but in these two the multiplicand (`unfreezeDelayDays`) is a chain-configured constant, not directly attacker-supplied, so they are lower risk. `FreezeBalanceProcessor.getFrozenDuration()` is the value most directly under the caller's/contract's control among the candidates found.

### Impact Explanation
If `expireTime` overflows to a value `<= nowInMs` (or negative), the frozen balance/delegated resource created by the freeze is treated as already expired by downstream logic that compares `expireTime` against `now` (e.g. resource-unfreeze checks, delegated-resource expiry checks). This can let a contract-controlled freeze/delegate operation immediately unlock or misrepresent frozen TRX/resource state, corrupting the resource-accounting invariants (`total net/energy weight`) that the freeze/delegate mechanism is supposed to maintain, and potentially allowing resource or balance state to be manipulated in ways not intended by the freeze/lock design.

### Likelihood Explanation
I was not able to fully confirm, within the available tool calls, whether `param.getFrozenDuration()` is bounded elsewhere (e.g., in `Program.java` before the `FreezeBalanceParam` is constructed) before reaching `FreezeBalanceProcessor.execute`. The non-VM broadcastable path (`FreezeBalanceActuator`) does reference `FrozenDuration` five times, suggesting it applies min/max duration validation there, but `FreezeBalanceProcessor.validate()` — the code path used by the TVM opcode — has no equivalent check in the code I reviewed. This is the key uncertainty: if the TVM opcode wrapper in `Program.java` independently clamps/validates the duration before calling into the processor, this issue would not be exploitable. I could not verify that wrapper within the given iterations.

### Recommendation
Add an explicit overflow-safe computation (e.g. `Math.multiplyExact`/`Math.addExact` or `StrictMathWrapper`, consistent with the existing `AssetIssueActuator` pattern) when computing `expireTime` in `FreezeBalanceProcessor.execute`, and add explicit bounds validation on `param.getFrozenDuration()` in `FreezeBalanceProcessor.validate()`, mirroring the min/max frozen-duration checks already present for `FreezeBalanceActuator`. Apply the same overflow-safe pattern to `UnfreezeBalanceV2Processor.calcUnfreezeExpireTime` and `UnfreezeBalanceV2Actuator.calcUnfreezeExpireTime` for defense in depth.

### Proof of Concept
Conceptual (not fully verified due to inability to trace the exact caller path from `Program.java` in the final iteration):
1. Deploy a contract that invokes the TVM `freezeBalance` opcode with a very large `frozenDuration` value (attempting to make `frozenDuration * FROZEN_PERIOD` overflow `long`, or `nowInMs + (that product)` overflow).
2. If `FreezeBalanceParam.getFrozenDuration()` is not clamped upstream, `FreezeBalanceProcessor.execute` computes a wrapped/negative `expireTime`.
3. Downstream resource/delegation-expiry checks (`expireTime <= now`) would treat the freeze as already expired, undermining the freeze/delegate lock guarantee.

Because I could not confirm the absence of upstream bounds-checking on `frozenDuration` in the `Program.java` opcode handler within the allotted tool calls, this should be validated further (start a Devin session with full repository access) before treating it as a confirmed exploitable issue rather than a code-quality gap.

  public void validate(FreezeBalanceParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    // validate arg @frozenBalance
    byte[] ownerAddress = param.getOwnerAddress();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long frozenBalance = param.getFrozenBalance();
    if (frozenBalance <= 0) {
      throw new ContractValidateException("FrozenBalance must be positive");
    } else if (frozenBalance < TRX_PRECISION) {
      throw new ContractValidateException("FrozenBalance must be greater than or equal to 1 TRX");
    } else if (frozenBalance > ownerCapsule.getBalance()) {
      throw new ContractValidateException("FrozenBalance must be less than or equal to accountBalance");
    }

    // validate frozen count of owner account
    int frozenCount = ownerCapsule.getFrozenCount();
    if (frozenCount != 0 && frozenCount != 1) {
      throw new ContractValidateException("FrozenCount must be 0 or 1");
    }

    // validate arg @resourceType
    switch (param.getResourceType()) {
      case BANDWIDTH:
      case ENERGY:
        break;
      default:
        throw new ContractValidateException(
            "Unknown ResourceCode, valid ResourceCode[BANDWIDTH、ENERGY]");
    }

    // validate for delegating resource
    byte[] receiverAddress = param.getReceiverAddress();
    if (!FastByteComparisons.isEqual(ownerAddress, receiverAddress)) {
      param.setDelegating(true);

      // check if receiver account exists. if not, then create a new account
      AccountCapsule receiverCapsule = repo.getAccount(receiverAddress);
      if (receiverCapsule == null) {
        receiverCapsule = repo.createNormalAccount(receiverAddress);
      }

      // forbid delegating resource to contract account
      if (receiverCapsule.getType() == Protocol.AccountType.Contract) {
        throw new ContractValidateException(
            "Do not allow delegate resources to contract addresses");
      }
    }
  }
