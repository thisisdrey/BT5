### Title
Cross-repository object exfiltration via unauthenticated `TargetRepository` in `ResolveConflicts` - (File: internal/gitaly/service/conflicts/resolve_conflicts.go)

### Summary
`ResolveConflicts` accepts two repository identifiers in `ResolveConflictsRequestHeader`: `Repository` (the repo the caller is authorized to write to) and `TargetRepository` (an arbitrary "their" repository used only to resolve a branch name). Validation and quarantine/authorization machinery is applied to `Repository`, but `TargetRepository` is barely validated and is used to fetch arbitrary objects that get merged and committed into `Repository`. This mirrors the `Borrowing::redeemYields` bug class: one identifier is checked/authorized while a second, less-trusted identifier supplies the actual privileged data that ends up materialized under the authorized identity.

### Finding Description
In `validateResolveConflictsHeader`, `header.GetRepository()` is passed through `locator.ValidateRepository`, which performs storage/path validation and participates in Gitaly's usual repository-scoped access-control path. [1](#0-0) 

By contrast, `header.GetTargetRepository()` is only checked for non-nilness — there is no `ValidateRepository` call, and it is never subjected to the same access-controlled path resolution that `Repository` goes through: [2](#0-1) 

`resolveConflicts` then builds a `remoterepo.Repo` directly from this weakly-validated `TargetRepository` and calls `repoWithBranchCommit`, passing the quarantined (authorized) `sourceRepo` and the caller-controlled `targetRepo`: [3](#0-2) 

Inside `repoWithBranchCommit`, the target branch is resolved on the arbitrary `targetRepo`, and if the resulting commit is not already present in the source repo, it is pulled in via `sourceRepo.FetchInternal(ctx, targetRepo.Repository, ...)`: [4](#0-3) 

The fetched object is then merged with the "ours" commit and written as a new commit inside the caller's own (authorized) repository via `resolveConflictsWithGit`, and finally landed with `UpdateReference` on `header.GetRepository()`: [5](#0-4) 

Exactly like the Solidity bug — where `abond.userStates(user)` data (belonging to the unauthorized identifier) is used to compute and transfer value while the debit is applied to a different, insufficiently-checked identifier (`msg.sender`) — here the RPC uses the *weakly validated* identifier (`TargetRepository`) to source privileged content (git objects/branch tips) while the *authorized* identifier (`Repository`) is the one that actually gets mutated/committed to. The caller only needs write access to `Repository`; they can name any `TargetRepository` (any storage/relative-path pair they can guess or enumerate) and the RPC will happily fetch and merge its commit content into their own repository history, then durably persist it via the normal receive-hook/reference-update path.

### Impact Explanation
An attacker with legitimate write access to some `Repository` (their own project) can supply an arbitrary `TargetRepository` (a private/internal repository they otherwise have no read access to, as long as they can identify its `storage_name`/`relative_path`) as the "their" side of a conflict resolution. `FetchInternal` will pull the tip commit (and reachable tree/blob objects) of that repository's branch into the attacker's own repo, and the merge/commit logic will materialize that content as a real, readable commit in the attacker-controlled repository, from which the attacker can freely read it (e.g., via any read RPC or over standard `git fetch`/`clone`). This is a cross-repository content-disclosure / authorization-bypass vector: it exposes objects from repositories the caller was never authorized to read, using an RPC intended only to resolve merge conflicts within a repository the caller does control.

### Likelihood Explanation
Reachability requires only: (1) write access to one repository to drive the `ResolveConflicts` RPC, and (2) knowledge of the target repository's `storage_name` and `relative_path` (both of which are often predictable/enumerable, e.g., sequential/deterministic replica paths as seen elsewhere in the codebase, such as `storage.DeriveReplicaPath`). No special privilege, leaked token, malicious peer, or MITM is required — it is exploitable from an ordinary authenticated user's crafted RPC field, matching the required unprivileged-actor threat model.

### Recommendation
Apply the same authorization/validation to `TargetRepository` as is applied to `Repository` before using it as a fetch source: call `locator.ValidateRepository` on it, and additionally require that the caller be authorized to *read* `TargetRepository` (equivalent to the "enforce msg.sender == user" mitigation in the original report — here, enforce that the RPC's authorization context legitimately covers both repositories involved, not just the one being written to). At minimum, reject `ResolveConflicts` requests where `TargetRepository` has not passed the same existence/ownership validation gate as `Repository`.

### Proof of Concept
1. Attacker has push/write access to `RepoA` (their own project) and knows the `storage_name`/`relative_path` of `RepoB` (a private repository they cannot otherwise read).
2. Attacker calls `ResolveConflicts` with `Repository = RepoA`, `TargetRepository = RepoB`, `TargetBranch` pointing at a branch in `RepoB`, and a valid `OurCommitOid` from `RepoA`.
3. `validateResolveConflictsHeader` accepts the request since `TargetRepository` is only checked for non-nilness.
4. `repoWithBranchCommit` resolves `RepoB`'s branch tip and, since it's absent from `RepoA`, fetches it into `RepoA`'s quarantine via `sourceRepo.FetchInternal`.
5. The conflict-resolution merge commit (containing `RepoB`'s tree/blob content) is written and landed into `RepoA` via `UpdateReference`.
6. Attacker reads the new commit from `RepoA` (which they have full access to), obtaining content originally confined to `RepoB`.

func validateResolveConflictsHeader(ctx context.Context, locator storage.Locator, header *gitalypb.ResolveConflictsRequestHeader) error {
	if header.GetOurCommitOid() == "" {
		return errors.New("empty OurCommitOid")
	}
	if err := locator.ValidateRepository(ctx, header.GetRepository()); err != nil {
		return err
	}
	if header.GetTargetRepository() == nil {
		return errors.New("empty TargetRepository")
	}

func (s *server) repoWithBranchCommit(ctx context.Context, sourceRepo *localrepo.Repo, targetRepo *remoterepo.Repo, targetBranch []byte) error {
	const peelCommit = "^{commit}"

	targetRevision := "refs/heads/" + git.Revision(string(targetBranch)) + peelCommit

	if sameRepo(sourceRepo, targetRepo) {
		_, err := sourceRepo.ResolveRevision(ctx, targetRevision)
		return err
	}

	oid, err := targetRepo.ResolveRevision(ctx, targetRevision)
	if err != nil {
		return fmt.Errorf("could not resolve target revision %q: %w", targetRevision, err)
	}

	ok, err := sourceRepo.HasRevision(ctx, git.Revision(oid)+peelCommit)
	if err != nil {
		return err
	}
	if ok {
		// target branch commit already exists in source repo; nothing
		// to do
		return nil
	}

	if err := sourceRepo.FetchInternal(
		ctx,
		targetRepo.Repository,
		[]string{oid.String()},
		localrepo.FetchOpts{Tags: localrepo.FetchOptsTagsNone},
	); err != nil {
		return fmt.Errorf("could not fetch target commit: %w", err)
	}

	return nil
}
