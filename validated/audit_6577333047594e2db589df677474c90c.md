### Title
XML Injection via unescaped element/attribute names in `encoding/xml` Marshal - ([File: src/encoding/xml/marshal.go])

### Summary
`encoding/xml`'s marshaler writes attacker-influenced `Name.Local` values for both elements and attributes directly into the output stream without validating or escaping XML metacharacters. When an application builds a `xml.Name` (via a dynamic `XMLName` field, `MarshalXML`, or `MarshalXMLAttr`) from untrusted input and marshals it, the untrusted string can inject new elements/attributes into the produced document — the same CWE-91 XML Injection primitive described in the dom4j `addElement`/`addAttribute` advisory.

### Finding Description
Attacker input flows into a program that dynamically sets an `xml.Name.Local` (e.g. a request-derived tag or attribute name) and then calls `xml.Marshal`/`Encoder.Encode`. In `marshalValue`, the resulting `StartElement` is passed to `printer.writeStart`, which writes `start.Name.Local` with a raw `p.WriteString(start.Name.Local)` [1](#0-0) , and attribute names are written the same way, `p.WriteString(name.Local)`, with only the attribute *value* passed through `p.EscapeString` — the attribute *name* is never escaped or validated [2](#0-1) . The matching `writeEnd` also writes `name.Local` unescaped [3](#0-2) . Unlike `EncodeToken`, which explicitly validates `Comment` (rejects `--`), `ProcInst` (`isNameString`/`?>` check), and `Directive` (`isValidDirective`) to prevent markup injection [4](#0-3) , no equivalent check (`isName`, quote/angle-bracket rejection) exists for `Name.Local` used in `writeStart`/`writeEnd`, so a value containing `"`, `<`, `>`, or whitespace is emitted verbatim, letting an attacker close the current tag/attribute early and splice in new elements or attributes.

### Impact Explanation
An attacker who controls a value used to build an `xml.Name` (dynamic tag/attribute naming is a documented, supported feature — "the value of the XMLName field of type Name") can inject arbitrary sibling elements or attributes into the serialized XML consumed by a downstream parser, e.g. smuggling extra fields, spoofing attributes that affect authorization/config parsing on the consuming side, or corrupting document structure (CWE-91, matching the CVSS C:N/I:H/A:N profile of the dom4j advisory). This is a data-integrity/injection issue on the PUBLIC track class of bugs, not memory-safety.

### Likelihood Explanation
Requires the ordinary, documented workflow of unmarshaling/deriving an `xml.Name` from untrusted data (e.g., a field name or attribute key coming from user input) and re-marshaling it — a plausible pattern in generic XML-rewriting/proxy code. No privileged access or malicious server/peer control is needed; only that the application passes attacker-influenced strings into `Name.Local`.

### Recommendation
Validate `Name.Local`/`Name.Space` against the XML `Name` production (as already done via `isName` for entity-decoder), or escape/reject characters like `<`, `>`, `"`, `'`, `&`, and whitespace in `writeStart`/`writeEnd` before writing them, mirroring the checks already applied to `Comment`, `ProcInst`, and `Directive` in `EncodeToken`.

### Proof of Concept
```go
package xml_test

import (
	"encoding/xml"
	"strings"
	"testing"
)

type Envelope struct {
	XMLName xml.Name
	Body    string
}

func TestElementNameInjection(t *testing.T) {
	e := Envelope{
		XMLName: xml.Name{Local: `foo><injected attr="pwned"`},
		Body:    "data",
	}
	out, err := xml.Marshal(e)
	if err != nil {
		t.Fatalf("marshal error: %v", err)
	}
	got := string(out)
	// Expect a well-formed <foo ...>...</foo>; instead the injected
	// characters are emitted raw, splicing in a new element/attribute.
	if strings.Contains(got, `<injected attr="pwned">`) {
		t.Fatalf("XML injection succeeded, got malformed output: %s", got)
	}
}
```
