## Finding

### Title
Active-permission key holders can silently overwrite the Owner (and Witness) permission via `AccountPermissionUpdateContract`, enabling privilege escalation within multi-sig accounts - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
The CVE describes Apache Ranger allowing a lower-privileged "keyadmin" role to change credentials belonging to the higher-privileged "admin" role because the privilege hierarchy was not enforced on the password-change action. The analogous flaw in java-tron's multi-sig permission model is that `AccountPermissionUpdateActuator`, which processes `AccountPermissionUpdateContract`, never checks which permission tier authorized the transaction relative to what it is allowed to modify. Any key holder whose `Active` permission has the `AccountPermissionUpdateContract` operation bit enabled can submit a transaction that fully replaces the account's `Owner` permission (and `Witness` permission), seizing complete control of the account — a strictly higher privilege than the "Active" tier that authorized the call.

### Finding Description
Signature/authority checks for a broadcast transaction are performed generically in `TransactionCapsule.checkPermission` / `WalletUtil.checkPermissionOperations`: for any `permissionId != 0` (i.e., a non-Owner, "Active" key), the only requirement is that the permission is of type `Active` and that its 32-byte `operations` bitmap has the bit set for the contract type being executed. [1](#0-0) 

This generic check is reused for *every* contract type, including `AccountPermissionUpdateContract`. Once that bit is set (nothing in `checkPermission`/`checkAvailableContractType` in the actuator excludes it — the validity check only verifies the bit corresponds to *some* known `ContractType`), an Active key is fully authorized to invoke the actuator: [2](#0-1) 

`AccountPermissionUpdateActuator.validate()` mandates that a new `Owner` permission always be supplied (`hasOwner()`), and `execute()` unconditionally overwrites the account's Owner permission (and Witness permission, if applicable) with whatever was submitted in the contract — with no check tying the caller's authorizing permission tier to the scope of what may be changed: [3](#0-2) [4](#0-3) 

`AccountCapsule.updatePermissions` blindly replaces `owner_permission`, `witness_permission`, and `active_permission` fields as instructed by the contract, with no protection preventing an Active-tier caller from redefining Owner keys to addresses it controls (excluding the real owner) or lowering thresholds: [5](#0-4) 

Thus, the only gate standing between an "Active" (delegate/child) key and full ownership takeover is a single operations bit in the Active permission's bitmap — which the account owner may set for entirely unrelated reasons (e.g., wanting a delegate to be able to rotate *other* Active keys) — with no structural separation preventing that same bit from being used to overwrite Owner/Witness. This mirrors the Ranger flaw: the system fails to enforce that a lower-privileged principal cannot alter the credentials of a higher-privileged principal, relying only on a coarse capability flag instead of a proper privilege hierarchy check.

### Impact Explanation
An attacker who obtains (or is granted) an Active key with the `AccountPermissionUpdateContract` bit set can broadcast a single `AccountPermissionUpdateContract` transaction that replaces the account's `Owner` permission with attacker-controlled keys and thresholds, and can similarly overwrite the `Witness` permission if the account is a witness. This is an unauthorized account takeover: the true owner permanently loses control of their account/funds/witness role, since subsequent Owner-authorized operations (e.g., re-granting Owner control, unfreezing balance, voting, withdrawing rewards) require signatures that only the attacker now controls. This satisfies the "unauthorized account operation / permanent loss of funds or control" bar.

### Likelihood Explanation
Exploitation requires that the account owner has, at some point, granted an Active permission with the `AccountPermissionUpdateContract` operation bit enabled (this bit is excluded from the framework's own default Active-permission template, per `checkActiveDefaultOperations`/`checkAvailableContractTypeCorrespondingToCode` tests, meaning it is off by default and only set when an owner explicitly customizes permissions to delegate permission management). This makes the issue conditional on owner configuration rather than universally exploitable, but it is a realistic misconfiguration for any multi-sig setup that wants to delegate "manage keys" duties without granting full Owner rights — since the actuator provides no way to scope that delegation, any such grant is equivalent to granting full Owner control. [6](#0-5) 

### Recommendation
Enforce a privilege hierarchy in `AccountPermissionUpdateActuator.validate()`/`execute()`: reject (or restrict) `AccountPermissionUpdateContract` transactions signed via a non-Owner (`permissionId != 0`) permission when the submitted contract attempts to modify the `Owner` permission (or the `Witness` permission) relative to its current value. At minimum, require that any change to `owner_permission` or `witness_permission` be authorized specifically by the current Owner permission (`permissionId == 0`), independent of whatever bits are present in an Active permission's operations bitmap.

### Proof of Concept
1. Owner account `A` sets up a custom Active permission (id ≥ 2) for delegate key `D`, intending to allow `D` only to rotate other Active keys, and sets the `AccountPermissionUpdateContract` bit in that Active permission's operations bitmap (this is the only way to invoke this contract type from a non-Owner permission).
2. `D` crafts an `AccountPermissionUpdateContract` for account `A` with `owner_permission` set to a permission whose sole key is `D`'s own address and threshold 1, keeping `active_permission`/`witness_permission` as desired.
3. `D` signs the transaction using `permission_id` referencing its Active permission and broadcasts it.
4. `TransactionCapsule.checkPermission` / `WalletUtil.checkPermissionOperations` pass because `D`'s Active permission has the `AccountPermissionUpdateContract` bit set and sufficient weight.
5. `AccountPermissionUpdateActuator.validate()`/`execute()` accept the contract without checking that the caller's permission tier (Active) should not be authorized to change `Owner` permission, and `AccountCapsule.updatePermissions` overwrites `owner_permission` to `D`'s new permission.
6. `D` now solely controls account `A`'s Owner permission; the original owner is permanently locked out.

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
