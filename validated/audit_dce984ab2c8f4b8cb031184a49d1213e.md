### Title
Inconsistent `AllowTvmCompatibleEvm` version-1 contract guard between `TransferActuator` and `TransferAssetActuator` allows TRC10 assets to be sent to version-1 smart contracts - (File: actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java)

### Summary
`TransferActuator.validate()` enforces two independent guards before crediting a smart-contract address: `ForbidTransferToContract` and, when `AllowTvmCompatibleEvm` is active, a specific block on sending TRX to a "version 1" (EVM-compatible) smart contract, directing callers to use `TriggerSmartContract` instead [1](#0-0) . `TransferAssetActuator.validate()`, which performs the analogous "credit" operation for TRC10 assets, only enforces the `ForbidTransferToContract` check and never checks `AllowTvmCompatibleEvm`/`getContractVersion()` [2](#0-1) . This is the same bug class as the reported `_credit` issue: an emergency/consistency gate applied to one crediting code path is silently omitted from a parallel, functionally equivalent code path.

### Finding Description
Both `TransferActuator` (TRX transfers) and `TransferAssetActuator` (TRC10 asset transfers) allow an unprivileged sender to move value directly into a smart-contract account outside of `TriggerSmartContract`, i.e. without executing the contract's code/fallback logic. The committee-controlled `AllowTvmCompatibleEvm` proposal was introduced specifically to block this for "version 1" contracts, because such contracts may not have code paths designed to handle unsolicited external transfers (their fallback/receive semantics differ under the EVM-compatible TVM mode), and the recommended path is `TriggerSmartContract`. `TransferActuator.validate()` implements this: when `getAllowTvmCompatibleEvm() == 1` and the destination account is a `Contract` whose `ContractCapsule.getContractVersion() == 1`, it rejects the transaction [3](#0-2) .

`TransferAssetActuator.validate()`, which handles the structurally identical operation for TRC10 tokens, only replicates the `ForbidTransferToContract` check and has no equivalent check against `AllowTvmCompatibleEvm`/`getContractVersion()` [2](#0-1) . `TransferAssetActuator.execute()` then unconditionally credits the asset balance to the destination contract via `addAssetAmountV2` [4](#0-3) . As a result, once `AllowTvmCompatibleEvm` is enabled by the committee, TRC10 tokens can still be pushed into version-1 contracts by a single signed `TransferAssetContract` transaction from any unprivileged account broadcaster, even though the network intended to close that exact path for such contracts.

### Impact Explanation
Version-1 contracts are the ones the `AllowTvmCompatibleEvm` guard was designed to protect against unsolicited value credits (the guard's very purpose, per the code comment, is that these contracts should only receive value via `TriggerSmartContract`). Bypassing it for TRC10 assets can result in assets being locked/stranded inside contracts that have no code path to move or account for them, i.e. permanent freezing of user funds for any depositor who (knowingly or via UI/tooling) sends an asset transfer to such a contract address. It also creates an inconsistent enforcement state across two parity actuators for the same underlying safety mechanism, which is exactly the "some operations blocked while others continue" pattern described in the original report.

### Likelihood Explanation
Reachable by a single unprivileged `TransferAssetContract` transaction broadcast against any known version-1 contract address (the destination address, its type, and its `contractVersion` are all public on-chain data), with no witness/committee/peer collusion required, only requiring the (already-activated) `AllowTvmCompatibleEvm` chain parameter.

### Recommendation
Add the same `AllowTvmCompatibleEvm`/`getContractVersion() == 1` guard to `TransferAssetActuator.validate()` that already exists in `TransferActuator.validate()`, rejecting `TransferAssetContract` transactions whose `toAccount` is a `Contract` with `contractVersion == 1` when `dynamicStore.getAllowTvmCompatibleEvm() == 1`, mirroring lines 141-156 of `TransferActuator.java`.

### Proof of Concept
1. Committee activates `AllowTvmCompatibleEvm` (`saveAllowTvmCompatibleEvm(1)`), as covered by `AllowTvmCompatibleEvmTest` [5](#0-4) .
2. Attacker deploys or targets an existing version-1 contract address (`ContractCapsule.getContractVersion() == 1`).
3. Attacker (or any account) broadcasts a `TransferAssetContract` sending a TRC10 asset to that contract address.
4. `TransferAssetActuator.validate()` only checks `ForbidTransferToContract`, not `AllowTvmCompatibleEvm`/version, so the transaction passes validation (compare with `TransferActuator`'s equivalent path, which is exercised in `TransferActuatorTest.transferToSmartContractAddress` for the TRX case) [6](#0-5) .
5. `TransferAssetActuator.execute()` credits the asset into the contract's balance via `addAssetAmountV2`, as exercised (without the version-1 restriction) in `TransferAssetActuatorTest.transferToContractAddress` [7](#0-6) , demonstrating the asset lands in the contract despite the guard meant to prevent exactly this for version-1 contracts.
