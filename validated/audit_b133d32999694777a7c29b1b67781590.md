### Title
`extend_with_attachments` bumps peer reliability on successful parse, not on content-hash correctness - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` increments a peer's reliability score whenever `decode_atlas_get_attachment()` succeeds, without ever comparing the returned `Attachment`'s hash to the `content_hash` that was actually requested. A malicious source in `AttachmentRequest.sources` can therefore inflate its `ReliabilityReport` by returning well-formed but wrong-content attachments, causing it to be preferred over honest peers in subsequent rounds.

### Finding Description
In `extend_with_attachments`: [1](#0-0) 
for each successfully-received response, the code only checks that `decode_atlas_get_attachment()` parses without error before calling `report.bump_successful_requests()`; it never checks `response.attachment.hash() == request.content_hash`. This is the exact equality break identified: "request succeeded" (i.e., the HTTP body decoded into a well-formed attachment struct) is treated as equivalent to "content matches the hash X this request was actually for."

Because `self.peers` (and hence `self.reliability_reports` in `AttachmentsDownloader::run`, lines 182-185) persist across batches, a malicious peer who is one of several `sources: HashMap<UrlString, ReliabilityReport>` for a given `content_hash` can respond with any parseable-but-wrong attachment payload to accumulate successful-request credit, while an honest peer serving the correct payload is bumped by the exact same amount for actually providing the correct data. Over repeated rounds, an attacker returning wrong content on every request accrues the same or a comparable reliability score as (or, if it responds faster/more often, a higher score than) honest peers, since nothing in this function penalizes hash mismatch — only outright decode failure or connection failure is penalized (`report.bump_failed_requests()` at lines 543 and 551).

Separately, the mis-hashed attachment returned by the attacker is inserted into `self.attachments` (line 548) using the attachment's own actual (wrong) hash; later, in `AttachmentsDownloader::run`, `context.attachments_batch.resolve_attachment(&attachment.hash())` is called using that same wrong hash, so the originally-requested `content_hash` is never marked resolved. This means the specific attachment instance keeps getting re-queued/retried up to `max_attachment_retry_count`, all the while the malicious peer's reliability score is inflated for these bogus round-trips.

### Impact Explanation
Because peer selection for future rounds is influenced by these reliability scores (higher score peers are preferred, per the question's description of `AttachmentRequest::get_most_reliable_source`/`Ord`/`score()`), an attacker who is one of several `sources` for a requested attachment can cause the malicious source to be chosen preferentially over honest sources across retries. Combined with the finite `max_attachment_retry_count`, this can exhaust the retry budget on the malicious peer's junk responses before an honest peer is ever selected, causing the batch to be dropped ("Atlas: dropping batch ... retries count exceeded"). The net effect is that a legitimately on-chain-committed attachment is never fetched — a form of attachment starvation/mismatch DoS on the Atlas subsystem, matching the "attachment/BNS mismatch" High-impact category.

### Likelihood Explanation
Preconditions: the attacker must run/control at least one peer that is discovered as an outbound sync peer and whose data URL ends up in `sources` for some attachment request (i.e., its `GetAttachmentsInvResponse` inventory claims to have the attachment) — no privileged role, secret, or special peer status is required beyond normal P2P participation, which is within the unprivileged attacker model. The attacker only needs to answer `GET /attachments/<hash>`-style HTTP requests from the victim node with any well-formed-but-wrong-content attachment payload, repeatable indefinitely and at low cost (a single crafted HTTP response per round).

### Recommendation
In `extend_with_attachments`, after `decode_atlas_get_attachment()` succeeds, verify `response.attachment.hash() == request.content_hash` before calling `report.bump_successful_requests()`; treat a hash mismatch the same as a failed request (`report.bump_failed_requests()`), and do not insert the mismatched attachment into `self.attachments`.

### Proof of Concept
Rust unit test in `stackslib/src/net/atlas/tests.rs` (or a new test module) plan:
1. Construct two `UrlString`s, `honest_url` and `evil_url`, each with a fresh `ReliabilityReport::empty()`.
2. Build an `AttachmentRequest` with `content_hash = X` and `sources` containing both peers with equal initial scores.
3. Simulate the `evil_url` peer returning an HTTP response whose body decodes successfully via `decode_atlas_get_attachment()` into an `Attachment` whose `hash()` != `X` (wrong content), and `honest_url` returning the correct attachment.
4. Feed both through `AttachmentsBatchStateContext::extend_with_attachments` with a `BatchedRequestsResult` containing both in `succeeded`.
5. Assert `self.peers.get(&evil_url).unwrap().bump_successful_requests()` was invoked (score increased) despite the wrong hash — i.e., `report.score()` for `evil_url` increased identically to `honest_url`'s, even though only `honest_url` returned the requested content.
6. Assert (as the question proposes) that after this update, `AttachmentRequest::get_most_reliable_source` (or equivalent `sources` sorting by `report.score()`) can return `evil_url` as preferred, demonstrating the broken equality between "successful decode" and "correct content."

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
