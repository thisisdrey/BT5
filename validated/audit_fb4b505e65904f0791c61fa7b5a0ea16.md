### Title
Ignored AEAD Encryption Return Code in Shielded Note Encapsulation Leaks Sensitive Plaintext to API Callers - ([File: framework/src/main/java/org/tron/core/zen/note/NoteEncryption.java])

### Summary
`NoteEncryption.encryptToRecipient()` and `NoteEncryption.encryptToOurselves()` call `JLibsodium.cryptoAeadChacha20Poly1305IetfEncrypt(...)` but discard the returned status code instead of checking it for failure, exactly the RSASVE encapsulation bug class described in CVE‑2026‑31790 (checking success without validating the underlying cryptographic primitive's return value). If the AEAD encryption call ever fails, the code unconditionally proceeds to package the (unencrypted-or-partial) buffer as if it were valid ciphertext, and this buffer is placed directly into on-chain/returned shielded-transaction fields (`cEnc`, `cOut`) that are handed back to an untrusted API caller and ultimately broadcast to the network.

### Finding Description
`NoteEncryption.encryptToRecipient` computes the shared secret, derives `kEnc`, then calls the native AEAD encrypt function and ignores its return value: [1](#0-0) 

```java
byte[] dhsecret = new byte[32];
if (!JLibrustzcash.librustzcashKaAgree(new KaAgreeParams(pkD, esk, dhsecret))) {
  return Optional.empty();
}
byte[] kEnc = new byte[NOTEENCRYPTION_CIPHER_KEYSIZE];
Encryption.kdfSapling(kEnc, dhsecret, epk);
byte[] cipherNonce = new byte[CRYPTO_AEAD_CHACHA20POLY1305_IETF_NPUBBYTES];
EncCiphertext ciphertext = new EncCiphertext();
JLibsodium.cryptoAeadChacha20Poly1305IetfEncrypt(new Chacha20Poly1305IetfEncryptParams(
    ciphertext.data, null, message.data,
    ZenChainParams.ZC_ENCPLAINTEXT_SIZE, null, 0, null, cipherNonce, kEnc));
alreadyEncryptedEnc = true;
return Optional.of(ciphertext);
```

Note the earlier call `librustzcashKaAgree` in the very same method IS checked (`if (!...)`), confirming the codebase's own convention is to validate native crypto return codes — the AEAD encrypt call is the one exception. The sibling method `encryptToOurselves` has the identical omission: [2](#0-1) 

By contrast, other call sites in the very same file (`attemptEncDecryption`, `attemptOutDecryption`, `encryptBurnMessageByOvk`) correctly check `!= 0` and return `Optional.empty()` on failure: [3](#0-2) 

This asymmetry (decrypt paths check the return code; the two encrypt paths used for constructing outgoing shielded notes do not) is the exact same failure-handling defect class as the reported OpenSSL RSASVE bug: "the affected code tests only whether the return value is non-zero" is *not even attempted* here — the return value isn't inspected at all.

The resulting `ciphertext`/`OutCiphertext` objects are placed straight into the `ReceiveDescriptionCapsule` (`cEnc`, `cOut` fields) which is:
1. Committed into the `ShieldedTransferContract`/shielded TRC20 parameters and eventually broadcast on-chain, and
2. Returned directly to the RPC/HTTP caller by `Wallet.createShieldedTransaction` / `Wallet.createShieldedContractParameters`-style flows, reachable via `CreateShieldedTransactionServlet`, `CreateShieldedContractParametersServlet`, and their gRPC equivalents in `RpcApiService`. [4](#0-3) [5](#0-4) 

### Impact Explanation
If the AEAD encrypt primitive silently fails (invalid parameters, JNI/native-linkage error, buffer-size edge case, memory error under load, etc.), the caller currently has no way to know encryption did not succeed. The produced "ciphertext" fields (`cEnc`/`cOut`) — which are supposed to hide the note's plaintext value, memo, diversifier, and outgoing viewing data — would instead contain either the pre-set zero buffer or stale/partial contents, and this data:
- Is returned by the node directly to the requesting API caller (an anonymous contract-parameter builder), and
- Is embedded into a broadcastable `ShieldedTransferContract`, becoming permanently, publicly recorded on-chain.

This can result in disclosure of the shielded note's secret contents (value, memo, recipient key material derived data) to anyone observing the API response or the chain, and/or produce a permanently unusable/undecryptable shielded output (since a legitimate recipient cannot recover a note whose `cEnc` was never really encrypted), which is a form of fund-loss/freezing for the note's value. This matches the required impact bar: sensitive data leakage and permanent freezing of funds via a defective shielded output.

### Likelihood Explanation
Exploitability is bounded by how often `crypto_aead_chacha20poly1305_ietf_encrypt` can actually fail for the tightly-controlled, fixed-size internal buffers used here (`ZC_ENCPLAINTEXT_SIZE`, `ZC_OUTPLAINTEXT_SIZE`); under normal conditions with library-managed inputs, the native call rarely returns non-zero. However, the code path is reachable by any unprivileged caller of the shielded transaction/contract-parameter construction API (`CreateShieldedTransactionServlet`, `CreateShieldedContractParametersServlet`, and gRPC equivalents), and the missing check means the defect is silent and would not be caught by any existing test or validation layer — there is no downstream verification that `cEnc`/`cOut` correspond to a successful encryption before they are returned to the client or included in a transaction. I could not find any additional validation elsewhere in the codebase (e.g., in `TransactionCapsule` or actuator validation) that cross-checks these ciphertext fields for a "failed encryption" marker, so likelihood is Medium given it depends on a rare underlying native failure, but severity if triggered is High.

### Recommendation
Check the return value of `JLibsodium.cryptoAeadChacha20Poly1305IetfEncrypt` in both `NoteEncryption.encryptToRecipient` and `NoteEncryption.encryptToOurselves`, mirroring the existing pattern used for `librustzcashKaAgree` and the decrypt/`encryptBurnMessageByOvk` methods: if the return code is non-zero, return `Optional.empty()` (or throw `ZksnarkException`) instead of proceeding to package and return the ciphertext buffer.

### Proof of Concept
Conceptual (root-cause) PoC, since the native call practically never fails under normal conditions in this environment:
1. An attacker (or fault-injection scenario) causes `JLibsodium.cryptoAeadChacha20Poly1305IetfEncrypt` to return a non-zero status when invoked from `encryptToRecipient`/`encryptToOurselves` (e.g., via a modified/patched native library, or a future libsodium version that adds stricter parameter validation and starts rejecting an edge-case input previously accepted).
2. `encryptToRecipient` ignores the failure and returns `Optional.of(ciphertext)` where `ciphertext.data` is the pre-allocated (all-zero) buffer, not a real ciphertext.
3. `Note.encrypt()` treats this as success, and `ZenTransactionBuilder.generateOutputProof` / `ShieldedTRC20ParametersBuilder.generateOutputProof` embed this bogus `cEnc` into a `ReceiveDescriptionCapsule`. [6](#0-5) 
4. The resulting shielded transaction parameters are returned to the calling API client via `CreateShieldedTransactionServlet`/`CreateShieldedContractParametersServlet` and can be broadcast, permanently recording an unencrypted/garbage note payload on-chain that legitimate recipients cannot use, while the caller sees the raw buffer contents in the API response.
