### Title
Unauthenticated address-keyed public-key rebinding in `PeerDB` allows hijacking of "always-allowed" walk-seed identity - ([File: stackslib/src/net/neighbors/db.rs])

### Summary
`PeerDB` binds a `Neighbor` row (and its `public_key`) purely by `(network_id, addrbytes, port)`, and every code path that persists handshake data (`Neighbor::load_and_update` → `handshake_update` → `save_update`/`update_peer`) overwrites `public_key` for that address unconditionally, without verifying that the new key matches any previously-known key for that address. Because the `addrbytes`/`port` fields inside `HandshakeData` are self-reported by the remote party and are only cross-checked against the observed socket address for *outbound* connections, an attacker who is contacted as part of a neighbor-of-neighbor crawl or pingback can claim to be the operator's pre-configured "always-allowed" peer and get their own public key bound to that trusted address in the PeerDB, which is later returned verbatim by `PeerDB::get_always_allowed_peers` and consumed by `get_initial_walk_neighbors`/`instantiate_walk_to_always_allowed`.

### Finding Description
The broken equality: the code assumes `public_key bound to an always-allowed NeighborKey == operator-configured trusted key`, but nothing enforces this — the first (or any subsequent) handshake claiming that `addrbytes`/`port` wins the binding.

Trace:
1. `PeerDB::get_always_allowed_peers` (`stackslib/src/net/db.rs:1043-1059`) simply selects rows `WHERE allowed < 0 AND network_id = ?1` from the `frontier` table and returns them as-is — it trusts whatever `public_key` is currently stored for that address/port.
2. `PeerDBNeighborWalk::get_initial_walk_neighbors` (`stackslib/src/net/neighbors/db.rs:428-444`) calls this directly in the non-IBD branch, and `NeighborWalk::instantiate_walk_to_always_allowed` (`stackslib/src/net/neighbors/walk.rs:290-333`) picks the first non-self entry as the walk seed.
3. The binding is written by `Neighbor::load_and_update` (`stackslib/src/net/chat.rs:475-516`), which looks up an existing peer strictly by `(network_id, handshake.addrbytes, handshake.port)` — fields taken directly from the remote party's self-reported `HandshakeData` — and then calls `handshake_update` (`chat.rs:438-465`), which unconditionally does `self.public_key = pubk` from the handshake, regardless of what key (if any) was previously bound to that address.
4. `PeerDBNeighborWalk::add_or_schedule_replace_neighbor` (`stackslib/src/net/neighbors/db.rs:368-426`): if the address `was_present` (e.g., a pre-seeded always-allowed row with `allowed = -1`), it calls `neighbor_from_handshake.save_update(...)`, which calls `PeerDB::update_peer` (`stackslib/src/net/db.rs:1285-1334`). That SQL `UPDATE` is keyed only by `network_id, addrbytes, port` and blindly writes the new `public_key` — there is no comparison against the previous key before allowing the overwrite; a key mismatch is only used afterward to decide whether to drop cached StackerDB replication state.
5. `validate_handshake` (`stackslib/src/net/chat.rs:1047-1092`) only enforces that `handshake_data.addrbytes/port` match the observed socket address when `self.stats.outbound` is true and a public key is already cached for the connection. For inbound connections, and for connections where no key is yet known, the self-reported address is accepted unchecked. The Secp256k1 signature on the handshake only proves the sender controls the private key matching `node_public_key` inside the message — it proves nothing about the `addrbytes`/`port` fields also inside that same signed payload.
6. Critically, `handle_neighbor_handshake_accept` (`stackslib/src/net/neighbors/walk.rs:1092-1124`), used while our node is walking to "neighbors of our neighbor," calls `add_or_schedule_replace_neighbor(network, preamble, &data.handshake, ...)` directly, with **no check** that `data.handshake.addrbytes/port` corresponds to the `naddr` we actually contacted. So any peer we crawl to (including addresses we only learned about from third-party gossip) can, in its `HandshakeAccept`, claim an arbitrary `addrbytes/port` — including the trusted always-allowed seed's address — and have its own key durably bound to that address.

Exploit flow: attacker gets themselves contacted by the victim node during any ordinary walk step (e.g., by being advertised as a neighbor by any peer, or via pingback), and in its signed `HandshakeAccept`/`Handshake` reply sets `handshake.addrbytes`/`handshake.port` to the operator's known always-allowed bootstrap address. `add_or_schedule_replace_neighbor` treats that address as already-present (assuming it was pre-seeded, e.g. via config/bootstrap peers) and overwrites its `public_key` with the attacker's key. Any subsequent walk in the non-IBD branch then treats the attacker as the trusted seed.

### Impact Explanation
This is an unauthenticated write to `PeerDB` state that corrupts which identity the node trusts as its bootstrap/seed peer for future walks (`get_initial_walk_neighbors`/`instantiate_walk_to_always_allowed`), matching the "unauthenticated/unauthorized write to state" Critical category. It is repeatable (any future re-handshake can re-hijack the binding) and requires only that the attacker be reachable as an ordinary, unprivileged peer during a routine crawl step — no secrets, signatures over another key, or privileged role are needed.

### Likelihood Explanation
Preconditions: the operator's `network_id` and always-allowed `addrbytes`/`port` are typically public (bootstrap node lists are usually publicly documented), and the row must already exist in the frontier as "present" for the `update_peer` overwrite path to trigger (this is the normal state for a pre-configured always-allowed seed). The attacker cost is low: they just need to be crawled by the victim (e.g., be gossiped as a neighbor, or answer a pingback) and reply with a self-signed handshake carrying forged `addrbytes`/`port` fields. This uses only the ordinary P2P handshake path, requires no privileged role, and is fully remote.

### Recommendation
Never let a handshake's self-reported `addrbytes`/`port` silently rebind an existing peer's `public_key` in `PeerDB::update_peer`/`Neighbor::handshake_update`. Before overwriting `public_key` for an address that is already marked `allowed < 0` (or more generally any existing row), require that the new key match the previously stored key, or require out-of-band re-authorization for always-allowed entries. Additionally, in `handle_neighbor_handshake_accept` and `pingback_handshakes_try_finish`, verify that `data.handshake.addrbytes`/`port` match the `naddr`/`nk` that was actually contacted before calling `add_or_schedule_replace_neighbor`, mirroring the pubkey-hash check already present in `check_handshake_pubkey_hash`.

### Proof of Concept
Rust test in `stackslib::net::neighbors` (or `db.rs` test module):
1. Create a `PeerDB` and pre-insert (via `PeerDB::insert_or_replace_peer`/`try_insert_peer`) a `Neighbor` row for `network_id = N`, `addrbytes = TRUSTED_ADDR`, `port = TRUSTED_PORT`, `allowed = -1`, with some legitimate `public_key = trusted_pubkey`.
2. Construct an attacker `HandshakeData` with `addrbytes = TRUSTED_ADDR`, `port = TRUSTED_PORT`, `node_public_key = attacker_pubkey` (attacker's own keypair, self-signed correctly), and a valid `Preamble` for `network_id = N`.
3. Call `PeerDBNeighborWalk::add_or_schedule_replace_neighbor(&mut network, &preamble, &attacker_handshake, None, &mut NeighborReplacements::new())` directly (simulating what `handle_neighbor_handshake_accept` does with an unchecked `data.handshake`).
4. Assert the returned `Neighbor.public_key == attacker_pubkey` (not `trusted_pubkey`), and that `PeerDB::get_peer(conn, N, &TRUSTED_ADDR, TRUSTED_PORT)` now shows `public_key == attacker_pubkey`.
5. Call `PeerDBNeighborWalk.get_initial_walk_neighbors(&network, /*ibd=*/false)` and assert the returned `Neighbor` for `TRUSTED_ADDR:TRUSTED_PORT` has `public_key == attacker_pubkey`, demonstrating the walk seed is now attacker-controlled.
