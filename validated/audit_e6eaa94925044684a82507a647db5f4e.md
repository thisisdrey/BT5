### Title
Transactions silently dropped (never packed, never re-queued) during block packing when they collide on multi-sign owner, oversized block, or exchange/shielded limits, causing delayed/lost execution of legitimate transactions - (File: framework/src/main/java/org/tron/core/db/Manager.java)

### Summary
`Manager.generateBlock()` builds a block by draining `pendingTransactions`/`rePushTransactions` with `poll()`, then applying several eligibility filters (block-size limit, shielded-transaction cap, multi-sign owner de-duplication, exchange-transaction rejection). When a transaction fails one of these filters, the code executes a bare `continue;` — but the transaction has already been removed from the queue by the preceding `poll()` and is never re-added to `pendingTransactions`, `rePushTransactions`, or `poppedTransactions`. As a result the transaction is discarded from this node's local mempool state entirely, rather than being retried in a subsequent block. [1](#0-0) [2](#0-1) 

### Finding Description
This is directly analogous to the FarmEOS "transaction congestion attack": the attacker does not need any special privilege — they broadcast ordinary signed transactions (multi-sign transactions from a chosen owner address, or transactions sized/typed to trip the block-size, shielded, or exchange filters) that a block producer's `Manager` will pull out of its pending queue via `pendingTransactions.poll()` / `rePushTransactions.poll()` at lines 1670-1691, and then reject with a plain `continue` at:
- block-size overflow: `postponedTrxCount++; continue;` (lines 1710-1714)
- shielded-transaction cap exceeded: `continue;` (lines 1717-1720)
- multi-sign owner already seen in this block: `continue;` (lines 1722-1730)
- exchange-transaction type: `continue;` (lines 1732-1734)

In every one of these branches the transaction was already dequeued before the check, and none of these branches re-inserts the transaction into any tracked collection (`toBePacked`, `pendingTransactions`, `rePushTransactions`, `poppedTransactions`). The variable name `postponedTrxCount` implies the transaction is only delayed, but the code does not actually postpone it anywhere — it is simply lost from the node's local queues. Unlike `PendingManager.close()`, which moves the *remaining* entries of `pendingTransactions`/`poppedTransactions` into `rePushTransactions` for retry, transactions removed mid-loop by `poll()` are outside the scope of that recovery mechanism.

This mirrors the FarmEOS bug class: an attacker submits crafted/duplicate-owner or otherwise-filtered transactions that get processed by the block producer's packing loop and end up discarding legitimate victim transactions in the same batch/category from further inclusion, effectively delaying or permanently preventing execution of pending user transactions.

### Impact Explanation
A user's legitimately-broadcast, signed, and fee-paid-for transaction can be silently dropped by a witness's block-packing logic and never included in any block, without an explicit failure being surfaced to the client beyond eventual mempool-timeout. For time-sensitive contract flows (e.g., lottery draws, auctions, order settlement) this causes denial of expected on-chain execution/delay analogous to the FarmEOS incident. Because the trigger conditions (multi-sign owner collision, exchange-contract type, shielded-transaction over-cap, block-size overflow) can be induced by an unprivileged transaction broadcaster crafting or submitting transactions in the same category as a victim's pending transaction, this is reachable purely through the public broadcast API path (`Wallet.broadcastTransaction` → `Manager.pushTransaction` → `Manager.generateBlock`). [3](#0-2) 

### Likelihood Explanation
Triggering the multi-sign-owner and exchange/shielded-limit branches requires no special permission — any account can send a multi-sign transaction, and any client can flood shielded/exchange transaction types to the mempool. The block-size branch is reachable by anyone submitting maximal-size transactions to fill the block ahead of others. The likelihood of an attacker exploiting this to specifically silence a known victim's transaction (e.g., delaying a lottery-style draw call) is moderate — it requires timing the malicious transaction so both land in the same producer's pending/rePush queue during the same block-generation window and belong to the same filtering category (same owner + multi-sign flag, or contending for tail-end block space).

### Recommendation
When a transaction is skipped due to block-size overflow, shielded-cap, multi-sign owner collision, or exchange-transaction rejection, re-insert it into `rePushTransactions` (or a dedicated retry queue) instead of leaving it dequeued and unreferenced, so it is retried on the next block-generation cycle rather than permanently lost from local state. At minimum, the size-overflow branch should preserve the transaction for a future, smaller block rather than dropping it after incrementing `postponedTrxCount`.

### Proof of Concept
1. Attacker (owner address A) submits a multi-sign transaction T1 and it enters the pending queue.
2. Victim (also owner address A, e.g., because A is a shared multi-sig account, or the attacker specifically targets an account they can front-run into the same block) has a pending multi-sign transaction T2 queued after T1.
3. During `generateBlock`, T1 is polled, matches `isMultiSignTransaction`, and `ownerAddress` A is added to `accountSet` (lines 1721-1730).
4. T2 is subsequently polled; because `accountSet.contains(ownerAddress)` is true, the loop hits `continue;` at line 1725 — T2 has already been removed from `pendingTransactions` by the `poll()` at line 1670/1691, and is never re-added anywhere.
5. T2 never appears in `toBePacked`, `pendingTransactions`, or `rePushTransactions`; it is discarded from the node's tracked state and will not be retried, delaying/losing its intended execution (e.g., a lottery draw call) analogous to the FarmEOS incident. [4](#0-3)
