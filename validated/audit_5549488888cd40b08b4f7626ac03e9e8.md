### Title
Stale postponed self-receipt survives `remove_account`/`CreateAccount` cycle and later executes privileged actions (Stake) against the re-created account - ([File: core/store/src/utils/mod.rs:504-575])

### Summary
`remove_account` (`core/store/src/utils/mod.rs:504-575`), invoked by `action_delete_account` (`runtime/runtime/src/actions.rs:314-389`) on `DeleteAccount`, deletes `TrieKey::Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` entries, but never removes `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceipt` for that `receiver_id`. A self-addressed `ActionReceipt` (predecessor==receiver==A) postponed via `process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) before `A` was deleted therefore survives the deletion, and once `A` is re-created (e.g. via `CreateAccount` from its parent account, which the same attacker controls for sub-accounts) and the outstanding data dependency finally arrives, the stale receipt is executed against the fresh account.

### Finding Description
`Runtime::process_action_receipt` persists a postponed action receipt keyed only by `(receiver_id, receipt_id)`/`(receiver_id, data_id)` — see `TrieKey::PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt` (`core/primitives/src/trie_key.rs:203-219`) and the writes at `runtime/runtime/src/lib.rs:1608-1655`. These keys carry no notion of "account incarnation" — they are indexed purely by the `AccountId` string.

`action_delete_account` calls `remove_account(state_update, account_id)` (`runtime/runtime/src/actions.rs:371`), which only clears `Account`, `ContractCode`, `AccessKey`/gas-key nonces, and `ContractData` (`core/store/src/utils/mod.rs:504-575`). It does not scan or remove any `PostponedReceiptId`, `PendingDataCount`, or `PostponedReceipt` rows for the deleted account.

When the account is later re-created (`Action::CreateAccount`, `runtime/runtime/src/actions.rs`), and a `Data` receipt matching the still-registered `PostponedReceiptId` arrives (`process_receipt`, `runtime/runtime/src/lib.rs:1386-1474`), the pending count is decremented, and once it hits 0 the stale receipt is fetched via `get_postponed_receipt` and executed with `apply_action_receipt` (`runtime/runtime/src/lib.rs:1442-1455`).

Inside `apply_action_receipt`, `actor_id` is initialized purely from the stored receipt's `predecessor_id` (`runtime/runtime/src/lib.rs:855`), and `check_actor_permissions` (`runtime/runtime/src/actions.rs:739-785`) authorizes privileged actions (`Stake`, `AddKey`, `DeleteKey`, `DeployContract`, …) solely via string equality `actor_id == account_id` — with no check that the account is the same "incarnation" that originally created the postponed receipt. Since the stale receipt was crafted with `predecessor_id == receiver_id == A`, this check trivially passes against the re-created `A`, regardless of who now owns/funds it. `action_stake` (`runtime/runtime/src/actions.rs:59-110`) then moves the account's *current* balance into `locked` under the public key embedded in the original (pre-deletion) `StakeAction`, and pushes a `ValidatorStake` proposal, using funds that may have been deposited by whoever refunded/re-funded the re-created account.

No existing check invalidates postponed-receipt bookkeeping on account deletion, and no check ties the postponed receipt's authorization to a specific account "generation" (e.g., a creation nonce or incarnation counter). Account re-creation of `A` is achievable by the same attacker for a subaccount (`sub.attacker.near`, created by/deleted by predecessor `attacker.near` which the attacker fully controls, as already exercised by the existing test `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`, `runtime/runtime/src/tests/apply.rs:4877-4954`). A normal cross-contract-callback pattern (`promise_then`) naturally produces exactly the receipt shape needed: an ActionReceipt to self with unmet `input_data_ids` and a `Stake` action in its batch.

### Impact Explanation
This is an authorization-exactness violation: a promise created before an account's deletion retains full self-authority over a functionally distinct account instance created later under the same name, letting an attacker plant a "time bomb" `Stake` action that fires automatically once triggered, staking whatever balance the re-created account holds under a validator public key chosen by the original (deleting) party. Matches "authorization escalation across accounts/promises" and unauthorized staking on a re-created account category in the bounty scope.

### Likelihood Explanation
Preconditions are all attacker-controlled and require no privileged access: a self-addressed callback-style `ActionReceipt` with an unmet `input_data_id` and a `Stake` action, followed by `DeleteAccount` on the same account, then `CreateAccount` recreating it (feasible for sub-accounts the attacker itself parents), and finally delivery of the outstanding `Data` receipt. The main practical constraint is that the attacker (or a party colluding with them) must control account re-creation, since sub-account creation requires the immediate parent as predecessor — this narrows exploitation mostly to self-targeted "time bomb" staking scenarios rather than attacking an arbitrary unrelated victim's newly created account, but it remains a genuine and reproducible protocol-level state-management bug (stale trie rows surviving `remove_account`).

### Recommendation
When `remove_account` deletes an account, also purge any outstanding `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceipt` rows keyed by that `receiver_id` (mirroring the access-key/contract-data cleanup pattern already used for iteration+removal in `core/store/src/utils/mod.rs:504-575`), so that no stale postponed receipt can survive across an account's deletion and re-creation. Alternatively, refund/burn or explicitly fail any pending postponed receipts for the account being deleted before completing `DeleteAccount`.

### Proof of Concept
Unit/integration test plan (runtime apply-level, similar in style to `runtime/runtime/src/tests/apply.rs:5038` and `runtime/runtime/src/tests/apply.rs:4882`):
1. Set up an account `A` (e.g., `child.alice.near`) with balance sufficient for minimum stake.
2. Build a self-addressed `ActionReceipt` R1: `predecessor_id == receiver_id == A`, `input_data_ids = [data_id]` (unmet), `actions = [Stake { stake, public_key: attacker_key }]`.
3. Apply R1: assert `TrieKey::PostponedReceiptId{A,data_id}`, `TrieKey::PendingDataCount{A,receipt_id}`, and `TrieKey::PostponedReceipt{A,receipt_id}` are present in the trie (use `get_postponed_receipt`/direct trie reads).
4. Apply a second receipt: `DeleteAccount{beneficiary}` from `A` to itself (predecessor==receiver==A, locked==0).
5. Assert `TrieKey::Account{A}` is gone, but the three `Postponed*` rows for `A` from step 3 are STILL present (proving the bug) — enumerate via prefix iteration on `col::POSTPONED_RECEIPT_ID`/`POSTPONED_RECEIPT`/`PENDING_DATA_COUNT`.
6. Apply `CreateAccount` for `A` (from its parent, e.g. `alice.near`) with a fresh balance/new key, funded by a "new owner" transfer.
7. Deliver the outstanding `Data` receipt for `data_id` targeting `A`.
8. Assert: the `Stake` action from the original stale receipt executes successfully (`ValidatorStake` proposal appears in `apply_result.validator_proposals` with `attacker_key`), and `A`'s `locked` balance increases — despite `A` having been deleted and recreated in between, with no signature/access-key from the new owner authorizing the stake.
