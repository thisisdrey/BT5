## Title
Self-trading on the Market DEX permanently burns the maker-side proceeds - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator` matches a newly submitted order (the taker) against pre-existing orders in the order book (the makers) with no restriction preventing a single account from matching its own resting order. When that happens, the maker-side credit is applied directly to the `AccountStore` in the middle of `execute()`, and is then silently clobbered by the stale in-memory taker account object that gets persisted at the very end of `execute()`. This is analogous to the reported Dex `consume_events` bug: special-cased / overlapping handling for the "same account is both sides of the trade" scenario is missing, causing the account's balance update to be dropped and funds to be permanently lost.

### Finding Description
`execute()` loads the taker's account once at the start of the transaction and keeps a single in-memory `AccountCapsule` (`accountCapsule`) for the whole call: [1](#0-0) [1](#0-0) 

That same in-memory object is mutated for the taker side throughout matching and finally flushed back with `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` at the very end of `execute()`.

During matching, `matchSingleOrder` credits the maker side with a *separate*, freshly re-read account object, and persists it immediately: [2](#0-1) [3](#0-2) 

The maker-crediting overload of `addTrxOrToken` does its own `accountStore.get(...)`, adds `makerBuyTokenQuantityReceive`, and immediately writes it back to `accountStore`. This is independent of the top-level `accountCapsule` used for the taker.

If the account that owns the *new* (taker) order is the same account that owns the pre-existing (maker) order being matched — i.e. a self-trade — both the taker-side and maker-side updates target the same underlying account record, but through two different, out-of-sync in-memory copies:

1. The maker-side write (inside `matchSingleOrder`) reads the account, adds the maker proceeds, and writes it to `accountStore` immediately.
2. At the end of `execute()`, the top-level `accountCapsule` — which was loaded *before* step 1 and only reflects taker-side changes — is written to `accountStore`, overwriting the maker-side credit applied in step 1.

There is no check anywhere in `matchOrder`/`matchSingleOrder`/`execute()` that the maker order's owner (`makerOrderCapsule.getOwnerAddress()`) differs from the taker's address, and no logic that merges the two updates when they coincide. This mirrors the reported Dex issue where special-case logic (or, here, the *lack* of unified logic) around identical maker/taker identities drops a balance credit.

### Impact Explanation
When a user's new order matches one of their own resting orders:
- The tokens/TRX for the maker side of the trade (`makerBuyTokenQuantityReceive`) were already deducted from the market (the seller's asset was deducted from the account when the original maker order was created, via `transferBalanceOrToken`), but the corresponding proceeds credited back to the account in `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` are silently discarded by the final `accountStore.put` in `execute()`.
- This is a genuine, unbacked loss of funds: assets are removed from the account (at order placement) and never come back (at match), permanently destroying value with no compensating credit anywhere. This satisfies "unbacked balance / permanent freezing/loss of funds."

### Likelihood Explanation
Any account can trivially trigger this by placing two opposite-side orders for the same trading pair at prices that cross (e.g., place a sell order, then place a matching buy order from the same account). No special privileges, no multi-party cooperation, and no chain configuration change are required — it is reachable by any transaction broadcaster using `MarketSellAssetContract`.

### Recommendation
Detect when the maker order's owner address equals the taker's owner address in `matchSingleOrder`/`matchOrder` and route the maker-side credit through the same in-memory `AccountCapsule` used for the taker (instead of re-reading/re-writing `accountStore` independently), so a single account's combined taker+maker updates are computed and persisted consistently in `execute()`. Alternatively, always reload the maker account from the taker's in-memory object when addresses match before applying/persisting the maker-side update.

### Proof of Concept
1. Account `X` places a sell order (e.g., sell 100 of asset A for 200 of asset B) via `MarketSellAssetContract`. This deducts 100 A from `X`'s balance and stores the maker order.
2. Account `X` places a second order that fully matches the resting order from step 1 (e.g., sell B for A at the matching price), submitted as a new `MarketSellAssetContract` from the same address `X`.
3. In `execute()`, `accountCapsule` for `X` is loaded once at the top (already missing the settlement from step 2's maker match).
4. `matchSingleOrder` calls `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` (no-`accountCapsule` overload), which reads `X`'s account from `accountStore`, adds the `B` proceeds owed to `X` as maker, and writes it back immediately.
5. At the end of `execute()`, `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` writes the original taker-only in-memory copy of `X`'s account back to the store, overwriting the maker credit applied in step 4.
6. Result: `X` loses the 100 A permanently — deducted at order placement, never credited back — with no other account receiving it. [4](#0-3)

  private void matchSingleOrder(MarketOrderCapsule takerOrderCapsule,
      MarketOrderCapsule makerOrderCapsule, TransactionResultCapsule ret,
      AccountCapsule takerAccountCapsule)
      throws ItemNotFoundException {

    long takerSellRemainQuantity = takerOrderCapsule.getSellTokenQuantityRemain();
    long makerSellQuantity = makerOrderCapsule.getSellTokenQuantity();
    long makerBuyQuantity = makerOrderCapsule.getBuyTokenQuantity();
    long makerSellRemainQuantity = makerOrderCapsule.getSellTokenQuantityRemain();

    // according to the price of maker, calculate the quantity of taker can buy
    // for makerPrice,sellToken is A,buyToken is TRX.
    // for takerPrice,buyToken is A,sellToken is TRX.

    // makerSellTokenQuantity_A/makerBuyTokenQuantity_TRX =
    //   takerBuyTokenQuantityCurrent_A/takerSellTokenQuantityRemain_TRX
    // => takerBuyTokenQuantityCurrent_A = takerSellTokenQuantityRemain_TRX *
    //   makerSellTokenQuantity_A/makerBuyTokenQuantity_TRX

    long takerBuyTokenQuantityRemain = MarketUtils
        .multiplyAndDivide(takerSellRemainQuantity, makerSellQuantity, makerBuyQuantity,
            this.disableJavaLangMath());

    if (takerBuyTokenQuantityRemain == 0) {
      // quantity too small, return sellToken to user
      takerOrderCapsule.setSellTokenQuantityReturn();
      MarketUtils.returnSellTokenRemain(takerOrderCapsule, takerAccountCapsule,
          dynamicStore, assetIssueStore);
      MarketUtils.updateOrderState(takerOrderCapsule, State.INACTIVE, marketAccountStore);
      return;
    }

    long takerBuyTokenQuantityReceive; // In this match, the token obtained by taker
    long makerBuyTokenQuantityReceive; // the token obtained by maker

    if (takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()) {
      // taker == maker

      // makerSellTokenQuantityRemain_A/makerBuyTokenQuantityCurrent_TRX =
      //   makerSellTokenQuantity_A/makerBuyTokenQuantity_TRX
      // => makerBuyTokenQuantityCurrent_TRX = makerSellTokenQuantityRemain_A *
      //   makerBuyTokenQuantity_TRX / makerSellTokenQuantity_A

      makerBuyTokenQuantityReceive = MarketUtils
          .multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity,
              this.disableJavaLangMath());
      takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain();

      long takerSellTokenLeft =
          takerOrderCapsule.getSellTokenQuantityRemain() - makerBuyTokenQuantityReceive;
      takerOrderCapsule.setSellTokenQuantityRemain(takerSellTokenLeft);
      makerOrderCapsule.setSellTokenQuantityRemain(0);

      if (takerSellTokenLeft == 0) {
        MarketUtils.updateOrderState(takerOrderCapsule, State.INACTIVE, marketAccountStore);
      }
      MarketUtils.updateOrderState(makerOrderCapsule, State.INACTIVE, marketAccountStore);
    } else if (takerBuyTokenQuantityRemain < makerOrderCapsule.getSellTokenQuantityRemain()) {
      // taker < maker
      // if the quantity of taker want to buy is smaller than the remain of maker want to sell,
      // consume the order of the taker

      takerBuyTokenQuantityReceive = takerBuyTokenQuantityRemain;
      makerBuyTokenQuantityReceive = takerOrderCapsule.getSellTokenQuantityRemain();

      takerOrderCapsule.setSellTokenQuantityRemain(0);
      MarketUtils.updateOrderState(takerOrderCapsule, State.INACTIVE, marketAccountStore);

      makerOrderCapsule.setSellTokenQuantityRemain(subtractExact(
          makerOrderCapsule.getSellTokenQuantityRemain(), takerBuyTokenQuantityRemain));
    } else {
      // taker > maker
      takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain();

      // if the quantity of taker want to buy is bigger than the remain of maker want to sell,
      // consume the order of maker
      // makerSellTokenQuantityRemain_A/makerBuyTokenQuantityCurrent_TRX =
      //   makerSellTokenQuantity_A/makerBuyTokenQuantity_TRX
      makerBuyTokenQuantityReceive = MarketUtils
          .multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity,
              this.disableJavaLangMath());

      MarketUtils.updateOrderState(makerOrderCapsule, State.INACTIVE, marketAccountStore);
      if (makerBuyTokenQuantityReceive == 0) {
        // the quantity is too small, return the remain of sellToken to maker
        // it would not happen here
        // for the maker, when sellQuantity < buyQuantity, it will get at least one buyToken
        // even when sellRemain = 1.
        // so if sellQuantity=200，buyQuantity=100, when sellRemain=1, it needs to be satisfied
        // the following conditions:
        // makerOrderCapsule.getSellTokenQuantityRemain() - takerBuyTokenQuantityRemain = 1
        // 200 - 200/100 * X = 1 ===> X = 199/2，and this comports with the fact that X is integer.
        makerOrderCapsule.setSellTokenQuantityReturn();
        returnSellTokenRemain(makerOrderCapsule);
        return;
      } else {
        makerOrderCapsule.setSellTokenQuantityRemain(0);
        takerOrderCapsule.setSellTokenQuantityRemain(subtractExact(
            takerOrderCapsule.getSellTokenQuantityRemain(), makerBuyTokenQuantityReceive));
      }
    }

    // save makerOrderCapsule
    orderStore.put(makerOrderCapsule.getID().toByteArray(), makerOrderCapsule);

    // add token into account
    addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, takerAccountCapsule);
    addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive);

    MarketOrderDetail orderDetail = MarketOrderDetail.newBuilder()
        .setMakerOrderId(makerOrderCapsule.getID())
        .setTakerOrderId(takerOrderCapsule.getID())
        .setFillSellQuantity(makerBuyTokenQuantityReceive)
        .setFillBuyQuantity(takerBuyTokenQuantityReceive)
        .build();
    ret.addOrderDetails(orderDetail);
  }

  private void addTrxOrToken(MarketOrderCapsule orderCapsule, long num) {
    AccountCapsule accountCapsule = accountStore
        .get(orderCapsule.getOwnerAddress().toByteArray());

    byte[] buyTokenId = orderCapsule.getBuyTokenId();
    if (Arrays.equals(buyTokenId, "_".getBytes())) {
      accountCapsule.setBalance(addExact(accountCapsule.getBalance(), num));
    } else {
      accountCapsule
          .addAssetAmountV2(buyTokenId, num, dynamicStore, assetIssueStore);
    }
    accountStore.put(orderCapsule.getOwnerAddress().toByteArray(), accountCapsule);
  }
