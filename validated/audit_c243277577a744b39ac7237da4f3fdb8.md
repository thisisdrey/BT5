### Title
RPC cost-accounting bypass for sidechannel RPCs undermines resource-limit enforcement signal - (File: internal/grpc/middleware/costhandler/costhandler.go)

### Summary
`costhandler.computeCost` derives the `x-gitaly-cost` trailer — the signal that external layers (Rails/Workhorse/Cloudflare) use to budget and rate-limit clients — from a fixed static per-RPC-type weight plus a dynamic component computed as `totalBytes / byteCostDivisor` where `byteCostDivisor` is a hardcoded `1 MiB` constant [1](#0-0) . The dynamic term is sourced exclusively from `grpcstats.PayloadBytesStatsFromContext`, i.e. bytes seen inside the gRPC message stream itself [2](#0-1) . This mirrors the reported bug class: a single fixed scaling constant (`Common.DECIMALS`/`byteCostDivisor`) is applied uniformly to a value whose true "unit size" varies by RPC, and for the RPCs that actually carry the largest resource cost, the constant is applied to the wrong (near-zero) quantity, producing a wildly under-scaled result relative to real consumption.

### Finding Description
`staticCostOverrides` explicitly flags `PostUploadPackWithSidechannel`, `SSHUploadPackWithSidechannel`, `SSHReceivePack`, `SSHUploadPack`, and `PostReceivePack` as the RPCs that "transfer large amounts of data" [3](#0-2) . By Gitaly's own sidechannel design, the actual pack/object payload for the `*WithSidechannel` RPCs (and, depending on transport, `SSH*` RPCs) is **not** carried inside the gRPC message stream at all — it flows over an out-of-band Unix/TCP sidechannel connection established alongside the gRPC call, precisely so that large blobs avoid gRPC framing overhead. Because `dynamicCostFromContext` only reads `stats.InPayloadBytes + stats.OutPayloadBytes` from `grpcstats.PayloadBytesStatsFromContext(ctx)` [4](#0-3) , and that stats handler can only observe bytes that pass through the gRPC stream, all sidechannel-transferred bytes are invisible to the cost calculation. The result: an RPC that pushes or fetches gigabytes of pack data through the sidechannel is scored with only the fixed static weight (`10`), identical to a request that transferred a few kilobytes over the same RPC. The per-byte "haircut" conversion (`bytes / 1 MiB`) is silently skipped for exactly the class of request it was designed to price, the same failure mode as applying a token-agnostic `1e18` divisor to a 6-decimal balance: the unit assumption baked into the constant does not hold for the dominant contributor to real resource cost.

### Impact Explanation
The `x-gitaly-cost` trailer is the sole mechanism by which downstream systems (Rails, Workhorse, Cloudflare via the `X-Score` header) throttle or budget expensive Git operations per actor, as documented in the package's own comment block [5](#0-4) . An ordinary authenticated user issuing repeated large `PostUploadPackWithSidechannel`/`SSHUploadPackWithSidechannel` fetches (or `PostReceivePack`/`SSHReceivePack` pushes) of multi-gigabyte packfiles will always be billed the small fixed static cost, never the dynamic byte-based cost. This lets such a user consume disproportionate Gitaly CPU/disk/network resources while appearing "cheap" to the external rate-limit budget, defeating the very DoS-mitigation control the cost signal exists to drive — directly analogous to draining a collateral pool with a value that is scaled down by orders of magnitude relative to its true size.

### Likelihood Explanation
High. No special privilege is needed: any client that can call the existing, normal fetch/push RPCs (`PostUploadPackWithSidechannel`, `SSHUploadPackWithSidechannel`, `PostReceivePack`, `SSHReceivePack`, `SSHUploadPack`) triggers this path by design, since sidechannel data transfer is the standard, documented transport for large pack data in these RPCs. The static cost overrides list itself calls these RPCs out as "large amounts of data" transfers, confirming they are treated as bulk paths yet are the ones whose bulk bytes never reach `grpcstats`.

### Recommendation
Do not rely solely on `grpcstats.PayloadBytesStatsFromContext` (in-band gRPC message bytes) to compute the dynamic cost term for RPCs that use sidechannel transport. Instead, source byte counts for `*WithSidechannel` (and SSH-transport) RPCs from the actual sidechannel/packfile byte counters (e.g., pack size counters already tracked by `internal/git/stats` / sidechannel readers), and add them into `dynamicCostFromContext` so `byteCostDivisor` is applied to the real transferred size rather than only the gRPC-visible portion. Alternatively, raise the static cost for these RPCs to a value calibrated against typical/maximum sidechannel payload sizes so the omission of the dynamic term cannot be used to mask outsized resource consumption.

### Proof of Concept
1. As an ordinary authenticated Gitaly client, issue an `SSHUploadPackWithSidechannel` (or `PostUploadPackWithSidechannel`) request that clones/fetches a repository containing multi-gigabyte packfiles; the bulk pack bytes are sent over the sidechannel connection, not the gRPC stream.
2. Repeat step 1 in a tight loop.
3. Observe the `x-gitaly-cost` trailer returned for each call: it will consistently equal the fixed static override (`10`) from `staticCostOverrides` [6](#0-5) , because `dynamicCostFromContext` derives its byte count only from in-gRPC-stream payload stats [7](#0-6) , regardless of how many gigabytes were actually moved via the sidechannel.
4. Compare against an equivalent-sized transfer forced through a non-sidechannel path (if available): the cost trailer for that path scales with `totalBytes / (1<<20)`, while the sidechannel path's cost stays flat — demonstrating the scaling-factor blind spot that lets a client extract disproportionate resource usage per unit of reported "cost."

Note: I was unable to inspect the full contents of `internal/grpc/grpcstats/stats.go` (only file metadata was retrievable, not its source) to confirm with certainty whether it has any partial instrumentation for sidechannel byte counts; this analysis is based on the documented behavior of Gitaly's sidechannel transport model plus the observable logic in `costhandler.go`. A Devin session with full repository access should verify `grpcstats.PayloadBytesStatsFromContext`'s exact instrumentation points to confirm whether sidechannel bytes are captured anywhere in that struct before treating this as fully confirmed.

```go
// dynamicCostFromContext computes the dynamic cost contribution from payload
// bytes tracked by the grpcstats.PayloadBytes stats handler.
func dynamicCostFromContext(ctx context.Context) int {
	stats := grpcstats.PayloadBytesStatsFromContext(ctx)
	if stats == nil {
		return 0
	}
	totalBytes := stats.InPayloadBytes + stats.OutPayloadBytes

	return int(math.Ceil(float64(totalBytes) / float64(byteCostDivisor)))
```
