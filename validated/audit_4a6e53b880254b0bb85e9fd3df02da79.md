### Title
Time-of-check/time-of-use gap between replay-window `Check` and `Update` allows a duplicate/replayed data-plane packet to be accepted - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` validate an inbound message counter against the anti-replay window (`window.Check`), release the lock, perform the (comparatively expensive) AEAD decrypt, then re-acquire the lock and commit the counter into the window (`window.Update`). Because the "is this counter allowed" check and the "commit this counter as seen" mutation are not atomic, this mirrors the root cause of the referenced Solidity finding: a state check is performed against a value that can be invalidated by an outstanding/pending operation before the corresponding commit happens.

### Finding Description
`Decrypt` in `connection_state.go` does: [1](#0-0) 

The sequence is: lock → `window.Check` → unlock → `DecryptDanger` (no lock held) → lock → `window.Update` → unlock. `VerifyRelay` (used for relayed frames, i.e. reachable without holding the target host's own certificate — an intermediate relay node just forwards ciphertext) follows the identical pattern: [2](#0-1) 

Nebula's routing/reader design supports multiple concurrent reader/worker routines processing inbound UDP packets (`routines` config, multiple `f.readers`/writers) per `interface.go`: [3](#0-2) [4](#0-3) 

`Bits.Check` only inspects the current window state and does not itself mutate anything; the actual anti-replay guarantee is only established once `Bits.Update` runs and marks the bit: [5](#0-4) [6](#0-5) 

Because the lock is dropped between `Check` and `Update`, and the AEAD `DecryptDanger` call happens with no lock held at all, two calls to `Decrypt`/`VerifyRelay` for the *same* message counter (e.g., an attacker replaying a captured ciphertext packet multiple times in quick succession toward a target being serviced by multiple reader goroutines) can both pass `Check` before either has called `Update`. Both then proceed to decrypt the same ciphertext (AES-GCM/ChaCha20-Poly1305 decryption is deterministic for a given key/nonce/ciphertext and does not itself detect nonce reuse), and only afterward does the "commit" (`Update`) actually enforce single-use — at which point one of the two duplicate deliveries has already produced valid plaintext and would be handed to the routing/tun layer.

This is directly analogous to the referenced HERMES `updatePeriod()` bug: a guard condition (`balanceOf < _required` / `window.Check`) is evaluated against a snapshot of state that ignores an outstanding, not-yet-settled quantity (`weekly` not yet withdrawn / the concurrent decrypt-in-flight for the same counter that hasn't yet updated the window), so the subsequent action (mint / decrypt-and-deliver) proceeds on stale information and the intended invariant ("exactly one message per counter is ever delivered") can be violated.

### Impact Explanation
A successful race allows a previously observed/captured encrypted data-plane (or relay) packet to be decrypted and delivered a second time to the tun device or relay-forward path, even though the anti-replay window is specifically designed to reject exactly this. This is a concrete traffic-replay/anti-replay-bypass impact in the category explicitly permitted by scope rules ("nonce/replay handling"). The severity is bounded (only genuinely captured ciphertext for an already-established session can be replayed — it does not grant new authentication or key material, and the underlying AEAD tag still must verify), but it undermines the confidentiality/integrity guarantee that Nebula's replay window is supposed to provide, and could be leveraged to duplicate-inject a single legitimate frame (e.g., re-triggering an application-level side effect carried once inside the tunnel) by racing packet delivery through multiple reader routines (`routines > 1`).

### Likelihood Explanation
Requires: (1) the deployment to run with more than one reader routine (`listen.routines`/`punchy` config commonly recommends `routines > 1` for throughput, and multiple `writers`/`readers` are explicitly supported), and (2) the attacker to be able to capture one ciphertext packet on the wire and resend copies of it in a tight race window aimed at the same host. Both conditions are realistic for a network-position/on-path attacker without needing a CA-signed certificate — this is exactly the kind of "rare edge case, still in-scope for Medium" reasoning the judge applied to the original HERMES finding.

### Recommendation
Make the check-then-commit sequence atomic with respect to the message counter: hold `decryptLock` (or use a per-counter reservation) across the `Check` step and an immediate provisional `Update`/reservation before doing the AEAD decrypt, only rolling back the reservation if decryption fails. Equivalently, merge `Check`+`Update` into a single locked "reserve-and-verify" primitive so no other caller can observe the pre-update window state for the same counter while a decrypt is in flight, then perform the AEAD operation outside the lock using the already-reserved slot.

### Proof of Concept
1. Establish a tunnel between two Nebula nodes with `listen.routines` set to a value > 1 (or otherwise arrange for two goroutines to call `Interface.readOutsidePackets`/`ConnectionState.Decrypt` concurrently for the same `HostInfo`).
2. Capture one legitimate data-plane (or relay, `header.MessageRelay`) UDP packet destined for a node.
3. Fire two (or more) copies of that exact captured packet at the target essentially simultaneously so that they land on different reader routines.
4. Both goroutines call `cs.window.Check` before either calls `cs.window.Update` (lock is dropped in between and `DecryptDanger` — the most expensive step — happens with no lock held), so both `Check` calls return `true`.
5. Both goroutines successfully decrypt the same ciphertext and only one is later rejected by `Update`; the other has already produced and (absent further contention) delivered plaintext a second time, despite the anti-replay window's contract.

Note: I could not fully verify from the indexed code whether a downstream de-duplication step exists elsewhere in the tun-delivery path that might additionally mitigate double-delivery after `Decrypt` returns successfully twice; confirming end-to-end exploitability (vs. just the TOCTOU in the anti-replay primitive itself) would require tracing the full caller chain in `outside.go` beyond what was indexed, and is best validated with a live/instrumented Devin session rather than static reading given index size limits.

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

// Update has three branches:
//   - i == b.current+1: fast path; advance the cursor by one and lose-count
//     the slot we just stomped (only past warmup; see the i > b.length guard
//     below).
//   - i  >  b.current+1: jump path; clear all slots between current and i
//     (or up to a full window's worth, whichever is smaller) via clearRange,
//     then mark i. Two arms here: a warmup arm that handles the very first
//     window before the cursor has slid, and a steady-state arm that treats
//     every cleared empty slot as a lost packet.
//   - i  <= b.current: in-window check for duplicates; out-of-window otherwise.
//
// NewBits seeds bits[0]=1 so counter 0 looks "received" — Update never
// clears that marker during warmup (clearRange skips position 0 when
// startPos=1), and once b.current >= b.length the marker is no longer
// consulted. The marker prevents a fictitious "lost" hit on the first real
// counter.
func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
