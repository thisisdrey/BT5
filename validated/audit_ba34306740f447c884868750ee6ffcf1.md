### Title
Dust deposit griefing permanently saturates a victim's `MAX_TOKENS_PER_USER` slots, DoS-ing deposits and debt issuance - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` tracks every deposit/debt token an account has ever touched in `depositTokensOfAccount` / `debtTokensOfAccount`, capped at `MAX_TOKENS_PER_USER = 30`. `DepositToken.deposit(amount_, onBehalfOf_)` is permissionless and mints to an arbitrary `onBehalfOf_`, and `DepositToken.transfer` lets anyone push dust to any address. Both paths call `Pool.addToDepositTokensOfAccount`, which reverts with `UserReachedMaxTokens` once the combined list length hits 30. An unprivileged attacker can fill all 30 slots of any victim with 1-wei dust positions, after which every `deposit`, `DebtToken.issue`/`mint`, and `DepositToken.transfer` involving a *new* token type reverts for that victim.

### Finding Description
`addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` apply `onlyIfAdditionWillNotReachMaxTokens`, reverting when `debtTokens + depositTokens >= 30` ( [1](#0-0) , [2](#0-1) ). Entries are added whenever a recipient's balance goes 0→positive via `_mint`/`_transfer` ( [3](#0-2) , [4](#0-3) ) and only removed when the victim's balance returns to exactly 0. `deposit()` accepts any `onBehalfOf_` with no consent check ( [5](#0-4) ). For a victim holding debt whose collateral is fully locked, `_revertIfLocked` (via `unlockedBalanceOf`, which returns 0 when `_issuableInUsd == 0`) prevents the victim from even transferring the dust back out to free slots ( [6](#0-5) , [7](#0-6) ).

### Impact Explanation
Availability loss mirroring the CVE's DoS class: the victim is unable to (a) deposit any collateral type not already in their list, (b) open debt positions in new synthetic assets (`issue` mints a new debt token → `addToDebtTokensOfAccount` reverts), and (c) receive msdTOKEN transfers. For a leveraged victim approaching liquidation, this blocks the primary self-rescue path (depositing a *different* collateral), and while locked slots cannot be cleared, the griefing persists as long as the position stays fully utilized. Cost to attacker is 30 dust deposits; no privileged role, oracle manipulation, or governance involvement is needed.

### Likelihood Explanation
Requires a pool offering enough distinct deposit/debt tokens to reach 30 combined slots and a victim with a position. On deployments like mainnet/optimism with multiple collaterals and synths this is reachable. It is a griefing (attacker gains nothing directly), and the victim can eventually recover by repaying debt to unlock and shed tokens, so it is temporary rather than permanent freezing — matching a Medium-severity availability analog.

### Recommendation
- Only add to `depositTokensOfAccount` when the account itself initiates (i.e., in `deposit` add for `onBehalfOf_` only if `onBehalfOf_ == _msgSender()` or via an opt-in), or
- Add a `sweep`/`removeToken` escape hatch letting an account forcibly remove a token from its list when its balance is below a dust threshold, and/or
- Do not count tokens whose account balance is zero-valued dust toward `MAX_TOKENS_PER_USER`, or allow entries to be pruned permissionlessly when `balanceOf` is below a minimum.

### Proof of Concept
```ts
// Hardhat, fork of a deployed Pool with >= 30 listed deposit tokens (or mix of deposit+debt tokens)
it('griefs victim token slots', async () => {
  const victim = bob.address
  const depositTokens = await pool.getDepositTokens() // e.g. 30 collaterals

  for (const dt of depositTokens.slice(0, 30)) {
    const token = await ethers.getContractAt('DepositToken', dt)
    const underlying = await ethers.getContractAt('IERC20', await token.underlying())
    await setBalance(underlying.address, attacker.address, 10) // dust
    await underlying.connect(attacker).approve(token.address, 10)
    // permissionless deposit on behalf of victim -> registers token on victim's account
    await token.connect(attacker).deposit(1, victim)
  }

  expect((await pool.getDepositTokensOfAccount(victim)).length).to.eq(30)

  // Victim can no longer deposit a new collateral type, mint a new synth, or receive new msdTOKENs
  const newToken = await ethers.getContractAt('DepositToken', someOtherDepositToken)
  await expect(newToken.connect(victim).deposit(parseEther('1'), victim))
    .revertedWithCustomError(pool, 'UserReachedMaxTokens')
  await expect(debtToken.connect(victim).issue(1, victim))
    .revertedWithCustomError(pool, 'UserReachedMaxTokens')

  // If victim is fully levered, dust is locked: transfer-out reverts, slots cannot be freed
  await expect(token.connect(victim).transfer(attacker.address, 1))
    .revertedWithCustomError(token, 'NotEnoughFreeBalance')
})
```
