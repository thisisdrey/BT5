### Title
`init_global_fee_state` has no deployer/authority check, allowing any unprivileged signer to front-run initialization and seize the global `global_fee_admin` role - (File: programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs)

### Summary
The `init_global_fee_state` instruction initializes the program-wide singleton `FeeState` PDA and lets the caller-supplied `admin_key` argument become `global_fee_admin` with no verification that the caller is the program's deployer/upgrade authority or any other privileged party.

### Finding Description
`init_global_fee_state` derives the `fee_state` account solely from the constant seed `FEE_STATE_SEED` (a global singleton, not per-group), and the `InitFeeState` account context only requires an arbitrary `payer: Signer<'info>` — there is no `has_one`, `address =`, or other constraint tying the call to a privileged key: [1](#0-0) 

The handler sets `global_fee_admin`, `global_fee_wallet`, and all fee parameters directly from caller-supplied instruction arguments with no validation of who is calling: [2](#0-1) 

The corresponding entrypoint in `lib.rs` documents this as "(Runs once per program)" but enforces nothing programmatically to restrict who runs it first: [3](#0-2) 

Because Anchor's `init` constraint only prevents *re*-initialization (it fails if the PDA already has data), it provides no protection against a *race* to be first. Any unprivileged user who observes the deployed program (before the legitimate operator submits their `init_global_fee_state` transaction) can submit their own transaction with `admin_key = <attacker>` and win the race, since Solana transaction ordering is not FIFO-guaranteed and mempool-less networks like Solana still allow competing transactions targeting the same not-yet-created PDA. This is the direct analog of the reported "missing lock on initializer" bug class: the initializer itself is the only gate, and it has no ownership check, so whoever calls it first — not necessarily the intended privileged party — permanently claims control.

Once `global_fee_admin` is set to the attacker's key, they gain full control of `EditFeeState`, which is gated only by `has_one = global_fee_admin`: [4](#0-3) 

This lets the attacker rewrite `global_fee_wallet` (redirecting all protocol fee flows to themselves), fee rates/fees across bank creation, liquidation, and order execution, and set the `pause_delegate_admin`, and per the docs the `global_fee_admin` can also invoke `panic_pause`, which affects the entire protocol's pause state: [5](#0-4) 

### Impact Explanation
This directly matches the "unauthorized state change" / privilege-escalation category and touches the fee path explicitly called out as in-scope. Capturing `global_fee_admin` lets the attacker redirect all `global_fee_wallet` proceeds (fees from bank creation, liquidations, order execution, and the protocol fee rate/fixed fee applied across every group) to an attacker-controlled wallet, and gives them unilateral pause control over the entire protocol via `panic_pause`. This is a concrete theft/unauthorized-transfer and unauthorized-state-change vector, not merely theoretical, since the state written is exactly the privileged-role field used to gate all subsequent fee/pause administration.

### Likelihood Explanation
Likelihood is high in the narrow window between program deployment and the legitimate first call to `init_global_fee_state`. Since the PDA seed (`FEE_STATE_SEED`) and account layout are public (compiled into the IDL/program), any observer monitoring the newly deployed program ID can construct and submit the exact same instruction with attacker-controlled arguments before the legitimate operator's transaction lands. No special privileges, leaked keys, or governance access are required — only being an unprivileged actor racing a public, permissionless instruction, which is why this is not excluded as a "privileged-address" issue per the project's exclusion list.

### Recommendation
Add an explicit authority check to `InitFeeState`/`initialize_fee_state` (e.g., require the payer/admin to equal a hardcoded pubkey or the program's upgrade authority fetched via the `bpf_loader_upgradeable` `ProgramData` account, as marginfi's `admin_close_account`/critical instructions do elsewhere), so the singleton `FeeState` cannot be claimed by an arbitrary first caller. This mirrors the general "lock the initializer" recommendation, but adapted to Solana: gate the once-only instruction by validated authority rather than relying solely on `init`'s one-time-creation semantics.

### Proof of Concept
1. Observe the marginfi program deployment transaction/program ID on-chain before the operator's `init_global_fee_state` call is confirmed.
2. Derive the `fee_state` PDA using `Pubkey::find_program_address(&[FEE_STATE_SEED.as_bytes()], &marginfi::ID)` (public constant/seed), as done in tests: [6](#0-5) 
3. Submit `init_global_fee_state(admin = <attacker_pubkey>, fee_wallet = <attacker_wallet>, ...)` with the attacker as `payer`/signer, racing the legitimate operator's transaction.
4. If the attacker's transaction lands first, `fee_state.global_fee_admin` and `fee_state.global_fee_wallet` are permanently set to attacker-controlled keys (the account cannot be re-initialized due to `init`).
5. The attacker now passes the `has_one = global_fee_admin` check in `EditFeeState` and can redirect fees / control pausing indefinitely: [7](#0-6)

pub fn initialize_fee_state(
    ctx: Context<InitFeeState>,
    admin_key: Pubkey,
    fee_wallet: Pubkey,
    bank_init_flat_sol_fee: u32,
    liquidation_flat_sol_fee: u32,
    order_init_flat_sol_fee: u32,
    program_fee_fixed: WrappedI80F48,
    program_fee_rate: WrappedI80F48,
    liquidation_max_fee: WrappedI80F48,
    order_execution_max_fee: WrappedI80F48,
) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_init()?;
    fee_state.global_fee_admin = admin_key;
    fee_state.global_fee_wallet = fee_wallet;
    fee_state.key = ctx.accounts.fee_state.key();
    fee_state.bank_init_flat_sol_fee = bank_init_flat_sol_fee;
    fee_state.bump_seed = ctx.bumps.fee_state;
    fee_state.program_fee_fixed = program_fee_fixed;
    fee_state.program_fee_rate = program_fee_rate;
    fee_state.liquidation_max_fee = liquidation_max_fee;
    fee_state.liquidation_flat_sol_fee = liquidation_flat_sol_fee;
    fee_state.order_execution_max_fee = order_execution_max_fee;
    fee_state.order_init_flat_sol_fee = order_init_flat_sol_fee;

    Ok(())
}
