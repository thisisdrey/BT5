### Title
Shielded-Transaction HTTP GET Endpoints Accept Private Key Material as Query-String Parameters, Exposing Secrets via Logs/History — (File: `framework/src/main/java/org/tron/core/services/http/GetSpendingKeyServlet.java`, `GetExpandedSpendingKeyServlet.java`, `GetAkFromAskServlet.java`, `GetIncomingViewingKeyServlet.java`, `ScanNoteByOvkServlet.java`, `ScanAndMarkNoteByIvkServlet.java`)

### Summary
The CVE-2013-2633 report concerns Piwik logging sensitive parameters because they were accepted via the wrong HTTP method (breaking the expected GET/POST semantics that determine what gets recorded/exposed). In java-tron's Wallet HTTP API, multiple shielded-transaction servlets accept raw private key material — spending keys, `ak`/`nk`/`ivk`/`ovk` viewing/nullifier keys — as `doGet` query-string parameters via `request.getParameter(...)`, in addition to POST. Query-string parameters are routinely captured by web/reverse-proxy access logs, browser history, referrer headers, and shell history (when curl'd), unlike POST JSON bodies. The node's own configuration comments acknowledge this class of API is dangerous to expose.

### Finding Description
`GetSpendingKeyServlet.doGet` returns a fresh diversifier-based shielded spending key with no secret input, but sibling servlets take user-supplied secrets on GET:
- `GetExpandedSpendingKeyServlet.doGet` reads a raw spending key from `request.getParameter("value")` [1](#0-0) 
- `GetAkFromAskServlet.doGet` reads the spend authorizing key `ask` via `request.getParameter("value")` [2](#0-1) 
- `GetIncomingViewingKeyServlet.doGet` reads `ak`/`nk` via query parameters [3](#0-2) 
- `ScanNoteByOvkServlet.doGet` reads the outgoing viewing key `ovk` via query parameter [4](#0-3) 
- `ScanAndMarkNoteByIvkServlet.doGet` and `ScanShieldedTRC20NotesByIvkServlet.doGet` read `ivk`, `ak`, `nk` via query parameters [5](#0-4) [6](#0-5) 

The project's own configuration explicitly documents the danger of this API class: [7](#0-6)  — "Some shielded transaction APIs require sending private keys as parameters. Calling these APIs on untrusted or remote nodes may leak your private keys." Despite this warning being attached to the `allowShieldedTransactionApi` gate, the servlets still expose a **GET** code path that places the same secrets in the URL query string, which is fundamentally more exposure-prone than a POST body: it is captured by default in Jetty/nginx/Apache/reverse-proxy access logs, browser/CLI history, and Referer headers sent to third parties on any embedded links — mirroring exactly the CVE-2013-2633 bug class of "input accepted via the wrong request channel leading to logging of sensitive parameters."

### Impact Explanation
If any of these endpoints are reachable (locally exposed for development, behind a reverse proxy with default access logging, or a full node operator forgets to restrict `walletExtensionApi`/binds HTTP externally), spend authorizing keys (`ask`), spending keys, and viewing keys (`ivk`, `ovk`, `ak`+`nk`) used for shielded transactions get written into access logs, proxy logs, and potentially browser history. Possession of a spending key allows an attacker to spend shielded funds; possession of `ask` allows deriving spend authority; `ivk`/`ovk` allow decrypting and tracking a user's shielded transaction history — i.e., key disclosure leading to potential theft of shielded funds.

### Likelihood Explanation
Exploitability depends on operational exposure: the node config comment already flags this as a known risk pattern for the "shielded transaction API" family, indicating the maintainers are aware secrets can leak via these HTTP paths. GET-based leakage is strictly easier to trigger unintentionally (curl scripts, browser testing, monitoring tools that log full URLs) than POST-body leakage, and no additional authentication separates GET vs POST handling in these servlets.

### Recommendation
Remove or reject `doGet` handling for all shielded-key-bearing endpoints (`GetExpandedSpendingKeyServlet`, `GetAkFromAskServlet`, `GetIncomingViewingKeyServlet`, `ScanNoteByOvkServlet`, `ScanAndMarkNoteByIvkServlet`, `ScanShieldedTRC20NotesByIvkServlet`, `ScanShieldedTRC20NotesByOvkServlet`, and any other servlet taking `ask`/`ivk`/`ovk`/`nk`/spending-key values), forcing POST-only submission of secret parameters, and ensure these endpoints are hard-gated behind `allowShieldedTransactionApi` (default false) with documentation reinforcing local-only use.

### Proof of Concept
```
curl "http://<full-node>:8090/wallet/getakfromask?value=<ASK_HEX>&visible=true"
curl "http://<full-node>:8090/wallet/getincomingviewingkey?ak=<AK_HEX>&nk=<NK_HEX>"
curl "http://<full-node>:8090/wallet/scannotebyovk?start_block_index=0&end_block_index=100&ovk=<OVK_HEX>"
```
Each request places the secret key material directly in the URL, which will be captured verbatim by any intermediary reverse proxy or load balancer access log (e.g., nginx default `log_format` includes `$request`), by the requester's shell history, and by browser history if triggered from a UI — satisfying the CVE-2013-2633 analog of sensitive parameter logging.
