### Title
Global `max_concurrent_connections` slot budget can be exhausted by abandoned QUIC handshakes before per-IP/staked checks ever engage - ([File: streamer/src/nonblocking/quic.rs])

### Summary
`run_server` reserves a slot from the shared, global `max_concurrent_connections` pool via `ClientConnectionTracker::new` *before* the QUIC handshake completes, and only releases it when the tracker is dropped — either on successful setup or after `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) expires. Because this check sits downstream of the overall and per-IP token-bucket rate limiters but is a pure concurrency cap (not a rate cap), an attacker using multiple source IPs can sustain a connection-attempt rate that never trips `overall_connection_rate_limiter` or `rate_limiter.is_allowed`, yet still keep enough Initial handshakes in flight simultaneously to fill the entire `max_concurrent_connections` slot pool, starving legitimate unstaked/staked peers with `refused_connections_too_many_open_connections`.

### Finding Description
In `run_server` [1](#0-0) , incoming connections pass through three gates in order:
1. `overall_connection_rate_limiter.current_tokens() == 0` — a global token bucket (`TOTAL_CONNECTIONS_PER_SECOND = 2500`, burst `MAX_CONNECTION_BURST = 1000`) [2](#0-1) .
2. `rate_limiter.is_allowed(&incoming.remote_address().ip())` — a per-IP limiter keyed strictly by source IP [3](#0-2) .
3. `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())` — a single global counter (`stats.open_connections`) shared across *all* peers regardless of stake, checked against `max_concurrent_connections` [4](#0-3) .

Gate 3 is purely a concurrency cap, not a token-refill rate cap. The `ClientConnectionTracker` slot is acquired immediately once an Initial packet is accepted, and is only released via `Drop` — either when `setup_connection` finishes normally or when the handshake exceeds `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2 seconds) as documented at [5](#0-4) . Since gates 1 and 2 only bound the *admission rate* of new attempts (per-IP and globally), an attacker spread over multiple source IPs, each individually staying under `max_connections_per_ipaddr_per_min`, and keeping the aggregate admission rate under `TOTAL_CONNECTIONS_PER_SECOND`, can still admit enough Initial packets during any 2-second window to drive `stats.open_connections` up to `max_concurrent_connections`. Every abandoned handshake occupies its slot for up to the full 2-second timeout before `Drop` runs, so sustained-but-modest attempt rates accumulate into a large "in-flight" pool that starves legitimate callers, who are refused at line 371-379 via `refused_connections_too_many_open_connections` — with no visibility into stake or IP reputation at that gate.

### Impact Explanation
This is a resource-starvation / QoS-evasion issue on the leader's TPU QUIC ingress: legitimate staked and unstaked senders can be refused connections (`refused_connections_too_many_open_connections`) purely due to attacker-controlled abandoned handshakes, without the attacker ever being rate-limited by the existing per-IP or global admission limiters. This falls under the "starves legitimate senders of TPU capacity" / availability-DoS bounty category rather than a consensus or fund-safety bug.

### Likelihood Explanation
Feasible with only unprivileged network access and multiple source IPs (real or spoofable, since QUIC Initial packets are UDP and pre-handshake spoofing is inherent to QUIC's connectionless start). No stake, keys, or special config are required. The attack is repeatable indefinitely as long as the attacker can rotate/spread source IPs faster than the per-IP limiter's window while keeping per-IP request rates low enough to avoid `rate_limiter.is_allowed` rejection, which is a mild but realistic constraint (botnets, cloud IP pools, or spoofed UDP source addresses at Initial time satisfy this).

### Recommendation
Decouple the handshake-in-progress slot budget from the fully-established connection budget, and/or shrink the exposure window: reduce `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` for the "hold-a-slot" phase, reserve a distinct (smaller) pool specifically for `outstanding_incoming_connection_attempts` separate from `max_concurrent_connections`, and/or make the in-flight handshake slot cap itself rate-limited per-IP so that many distinct IPs sending low but sustained handshake attempts cannot collectively saturate the shared pool. Additionally, consider weighting slot admission by stake earlier (before `ClientConnectionTracker::new`) so unstaked churn cannot compete for the same budget as staked peers.

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
}
