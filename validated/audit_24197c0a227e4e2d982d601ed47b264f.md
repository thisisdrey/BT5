### Title
Unhardened `ExchangeProcessor` bonding-curve math permits reserve-draining rounding exploitation in TRC10 Exchange trades - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
Like Mango Markets, where an attacker exploited a thinly-collateralized, low-liquidity market's price-calculation mechanism to extract far more value than was ever actually deposited, java-tron's on-chain TRC10 `Exchange` (a Bancor-style bonding-curve AMM reachable by any signed `ExchangeTransactionContract`) computes swap outputs using raw IEEE-754 `double` arithmetic by default. This non-hardened path (`ExchangeProcessor`) can produce rounding results that do not exactly conserve the pool invariant, and the codebase's own introduction of a `SafeExchangeProcessor`/`allowHardenExchangeCalculation` toggle (defaulting to legacy/off) confirms this was a recognized correctness gap in the default execution path.

### Finding Description
`ExchangeCapsule.transaction()` selects between two calculation engines based on the `allowHardenExchangeCalculation` chain parameter, defaulting to the legacy `ExchangeProcessor`, which performs the Bancor relay-token math entirely in `double`: [1](#0-0) 

The core computation uses `Math.pow`-based floating point operations and truncating casts to `long`, with no invariant check that the resulting swap preserves `k = firstTokenBalance * secondTokenBalance` (or any bound relative to it): [2](#0-1) 

Any account can create such a pool with attacker-chosen, arbitrarily small reserves via `ExchangeCreateActuator` (both sides funded solely by the creator, no minimum liquidity enforced): [3](#0-2) 

and any account (not just the creator) can then trade against it via `ExchangeTransactionActuator`, which delegates entirely to the possibly-imprecise processor and directly credits/debits account balances based on its output with no independent invariant check in the actuator itself: [4](#0-3) 

The project's own regression tests demonstrate that the legacy (non-hardened) `ExchangeProcessor` and the newer `SafeExchangeProcessor` (BigDecimal-based) produce *different* results for identical inputs — proving the default math is imprecise relative to the "correct" hardened computation: [5](#0-4) 

This mirrors the Mango Markets root cause at a structural level: a price/valuation mechanism for a market that any unprivileged party can create and manipulate, whose calculation model does not strictly enforce that value extracted from the pool is bounded by value deposited, allowing accumulated rounding/precision drift across repeated trades to be exploited for profit that is not backed by real reserves.

### Impact Explanation
If an attacker can find (or brute-force offline) sequences of buy/sell trade sizes against a self-created, low-liquidity pool where the `double`-based `exchangeToSupply`/`exchangeFromSupply` rounding consistently favors the trader over many repeated round-trip trades, they can extract more of the "another token" (including TRX) than they deposited, at the expense of counterparties/liquidity previously injected into that specific pool by the creator (who is also potentially the attacker, but if a *victim* creator had injected additional liquidity via `ExchangeInjectActuator`, that liquidity becomes at risk). This is an unbacked-balance / theft-of-funds class impact confined to whichever `Exchange` object is targeted, since the value moved is not backed by an equivalent decrease elsewhere — directly analogous to Mango's bad-debt creation, though scoped to a single pool's reserves rather than the whole platform.

### Likelihood Explanation
Exploitation requires: (1) creating a pool with minimal reserves (cheap, one signed `ExchangeCreateContract`), and (2) discovering trade-size sequences where `double` rounding is systematically favorable — this requires numerical analysis/fuzzing of `Maths.pow` behavior, similar in spirit to Mango's exploit requiring capital and price-manipulation know-how but here requiring exploit-engineering effort instead of capital. The presence of `allowHardenExchangeCalculation`, `SafeExchangeProcessor`, and extensive hardening tests in the codebase strongly suggests this exact risk was previously identified and partially remediated, but the remediation appears to be a governance-gated feature flag rather than the default — meaning any deployment that has not activated the hardened calculation proposal remains exposed to the legacy floating-point path.

### Recommendation
Make hardened (`SafeExchangeProcessor`, BigDecimal-based) exchange math mandatory rather than opt-in via `allowHardenExchangeCalculation`, or otherwise enforce an invariant check in `ExchangeCapsule.transaction()` for the legacy path (e.g., verifying `newFirstTokenBalance * newSecondTokenBalance >= firstTokenBalance * secondTokenBalance` using integer/BigInteger arithmetic) before committing balance changes, regardless of which processor computed the swap.

### Proof of Concept
Exact numeric inputs required to trigger a favorable-rounding exploit chain were not identified in this review (would require offline fuzzing of `ExchangeProcessor.exchange()` across many small-reserve pool states and repeated trade sequences to find a profitable divergence pattern); however, the codebase's own test `testStrictMath` in `ExchangeProcessorTest.java` already empirically demonstrates that `ExchangeProcessor` (legacy) and `SafeExchangeProcessor` (hardened) diverge on identical inputs, confirming the underlying imprecision that a targeted PoC would exploit: [6](#0-5)

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
