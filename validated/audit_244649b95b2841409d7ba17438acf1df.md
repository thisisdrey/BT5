### Title
`ValidateMultiSign`/`BatchValidateSign` TVM precompiles omit caller-contract binding, enabling cross-contract signature replay - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The external report describes a bridge contract that authorizes a withdrawal using a "discriminator" that is either open (any bridge on the network) or scoped (a specific bridge contract), and warns that using the open form lets a signed authorization intended for one bridge be replayed against another bridge on the same network because the check never binds the authorization to the specific contract instance performing the check. The same root cause — an authorization primitive that hashes/validates a payload without binding it to the identity of the contract requesting the validation — exists in java-tron's `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts.

### Finding Description
`ValidateMultiSign.execute()` builds the message that signatures are checked against purely from caller-supplied parameters — `(address, permissionId, data)` — with no binding to the identity of the calling smart contract (no `msg.sender`/`this` of the invoking contract, no chain/contract discriminator): [1](#0-0) 

The recovered signer addresses are then checked purely against the `Permission` of the target `address` account: [2](#0-1) 

`BatchValidateSign.doExecute()` has the same structural gap — it recovers signer addresses from a raw `hash` word supplied directly by the caller, with no scoping to the calling contract: [3](#0-2) 

This is the exact analog of the reported bug class: the external report's `allowedDiscriminator1` accepts a withdrawal signed/authorized for "any bridge contract on the network," letting one specific bridge's valid credential be replayed against a different bridge that performs the identical `header.discriminator == allowedDiscriminator1` check. Here, any two (or more) Solidity contracts deployed on java-tron that both call `ValidateMultiSign`/`BatchValidateSign` to authorize an action (e.g., "release funds if a multisig committee has approved this exact `data`/`hash` for account `address`") will accept the *same* off-chain-collected signature set, because the precompile hash never incorporates which contract is asking. If two different bridge/vault contracts (or two versions/instances of the same audited bridge template) are deployed on the same java-tron network and both use this pattern to gate a withdrawal keyed on `(address, permissionId, data)`, a signature set collected to authorize a withdrawal in contract A is valid input to satisfy the identical check in contract B.

### Impact Explanation
Any dApp on java-tron using `ValidateMultiSign`/`BatchValidateSign` as an off-chain multisig-approval gate for a state-changing action (fund release, mint, unlock) is exposed to cross-contract replay of an approval that was only intended for one specific deployed instance. Since the precompile is a core, always-available TVM primitive (not sidechain-only), this generalizes the reported bridge vulnerability to *any* pair of deployed contracts sharing this authorization pattern on mainnet or any java-tron-based network, resulting in unauthorized execution of privileged actions/fund withdrawal in a second contract using signatures never intended for it.

### Likelihood Explanation
Exploitation requires only a standard `TriggerSmartContract` transaction from any unprivileged account to a contract that uses this precompile pattern with data/parameters overlapping another live contract (e.g., identical `permissionId`, `data` structure, and multisig committee address across a template deployed multiple times, as commonly happens with vault/bridge factories). No special privileges, node compromise, or consensus manipulation is needed — only knowledge of a previously broadcast signature set (which is often published on-chain or observable in mempool/logs).

### Recommendation
Include the calling/target contract's address (and ideally a purpose-specific domain tag) inside the hash that `ValidateMultiSign` and `BatchValidateSign` sign over, e.g. `combine = merge(callingContractAddress, address, permissionId, data)`, so that a valid signature is cryptographically bound to the specific contract instance intended to consume it, mirroring the recommendation to avoid the network-wide "open" discriminator and instead always require `header.discriminator == allowedDiscriminator2` (bound to `address(this)`).

### Proof of Concept
1. Deploy two independent Solidity contracts `VaultA` and `VaultB` on java-tron, each implementing: `function withdraw(address acct, uint256 permissionId, bytes data, bytes[] sigs) { require(validateMultiSign(acct, permissionId, data, sigs)); pay(...); }` calling the `ValidateMultiSign` precompile as in [4](#0-3) .
2. Off-chain multisig committee for `acct` signs `hash = SHA256(acct || permissionId || data)` to authorize a withdrawal in `VaultA`.
3. An attacker observes this signature set (e.g., from `VaultA`'s successful transaction) and submits the identical `(acct, permissionId, data, sigs)` tuple to `VaultB.withdraw(...)`.
4. Because the precompile hash in `PrecompiledContracts.ValidateMultiSign.execute()` never included any reference to `VaultA` vs `VaultB`, `recoverAddrBySign` and the weight/threshold check in [5](#0-4)  succeed identically in `VaultB`, allowing the attacker to trigger an unauthorized withdrawal in `VaultB` using an approval that was only meant for `VaultA`.
