### Title
Uncaught out-of-bounds/negative-length array construction in TVM precompile ABI array extraction - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE describes an integer-underflow in size checking during MakerNote array/offset decoding in libexif, which lets attacker-controlled length/offset fields drive out-of-bounds reads before validation. The closest reachable analog in java-tron is the ABI array-extraction helpers used by the `validatemultisign`/`batchvalidatesign` TVM precompiled contracts, which derive array lengths and offsets directly from attacker-supplied call data words without validating them before allocating arrays or copying bytes.

### Finding Description
`extractBytesArray`, `extractSigArray`, and `extractBytes32Array` in `PrecompiledContracts.java` take an `offset` into a `DataWord[]` parsed from the raw precompile call data and read a `len`/`bytesOffset`/`bytesLen` value straight from attacker-controlled words via `intValueSafe()`: [1](#0-0) 

`len` and the derived `bytesOffset`/`bytesLen` are used unchecked to size a new array (`new byte[len][]`) and to index into `words[offset + i + 1]` / `words[offset + bytesOffset + 1]`, and ultimately into `extractBytes`, which does `Arrays.copyOfRange(data, offset, offset + len)`: [2](#0-1) 

Because `len`/`bytesLen` come straight from `intValueSafe()` on a 256-bit word, a crafted value can be negative (triggering `NegativeArraySizeException`) or can push `offset + i + 1` / `bytesOffset + offset + 2) * WORD_SIZE` beyond the bounds of `words`/`data` (triggering `ArrayIndexOutOfBoundsException`). This mirrors the libexif bug class: a length/offset value used in size arithmetic is not range-checked before it drives array construction and copying.

Critically, in `ValidateMultiSign.execute()`, the call to `extractSigArray`/`extractBytesArray` happens **before** the `try { ... } catch (Throwable t) { ... }` block that wraps the rest of the logic: [3](#0-2) 

Any `RuntimeException` thrown while extracting the signature/bytes array (negative length, out-of-range offset, etc.) is therefore not caught by this local handler and propagates out of `execute()`.

### Impact Explanation
`ValidateMultiSign` (and `BatchValidateSign`, which also calls `extractBytesArray`) are TVM precompiled contracts reachable by any account through a normal smart-contract call (`TriggerSmartContract`) that invokes the precompile address with crafted call data. An attacker can construct call data whose header word (`words[offset]`) or nested offset/length words decode to a negative or out-of-range value, causing an unhandled `NegativeArraySizeException` or `ArrayIndexOutOfBoundsException` to propagate out of the precompiled contract's `execute()` method during transaction execution. Depending on how the VM/`Program` layer surrounding precompile invocation handles unexpected `RuntimeException`s, this can manifest as an aborted/failed transaction at best, or an unexpected exception path in block/transaction processing at worst — the latter being the class of impact (node crash/halt) targeted by this scan. This is reachable from a single unprivileged, signed transaction with no special permissions.

### Likelihood Explanation
Likelihood is high for triggering the exception path itself: constructing the calldata to make `words[offset].intValueSafe()` negative, or to make `offset + i + 1` exceed `words.length`, requires only crafting the ABI-encoded call data for the precompile call, which any transaction broadcaster or contract deployer can do without any privileged state. The `VMConfig.allowTvmOsaka()`-gated `isValidAbiEncoding` check only validates overall data length/word alignment, not the per-item offset/length fields consumed by `extractBytesArray`/`extractSigArray`, so it does not close this gap.

### Recommendation
Validate `len`, `bytesOffset`, and `bytesLen` in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` against `words.length`/`data.length` (rejecting negative or out-of-range values) before using them to size or index arrays, and move the `extractSigArray`/`extractBytesArray` calls inside `ValidateMultiSign.execute()`'s existing `try/catch (Throwable t)` block (or add an equivalent guard) so any malformed-input exception is converted to a normal `DATA_FALSE` result instead of propagating.

### Proof of Concept
Craft a `TriggerSmartContract` call to the `validatemultisign` precompile address whose ABI-encoded `data` sets the signature-array header word (the word at `words[3].intValueSafe() / WORD_SIZE]`) to a value that, when read as `len` in `extractSigArray`/`extractBytesArray`, is negative (e.g., a word with the high bit set that survives `intValueSafe()` as negative) — this makes `new byte[len][]` throw `NegativeArraySizeException` before the surrounding `try` block in `ValidateMultiSign.execute()` at line 1082, which is uncaught by that method.
