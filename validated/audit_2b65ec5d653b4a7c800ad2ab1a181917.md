### Title
StackerDB chunk signatures do not bind the target contract, enabling cross-lane chunk replay into `.signers-X-Y` StackerDBs - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest` — the digest that authenticates every StackerDB chunk — is computed only from `slot_id`, `slot_version`, and `data_hash`, and never includes the identity of the StackerDB smart contract the chunk is destined for. Because the Nakamoto signer-message StackerDBs (`.signers-<cycle%2>-1`, `.signers-<cycle%2>-2`, `.signers-<cycle%2>-3`, one per `MessageSlotID` "lane") all share the exact same `slot_id → signer address` mapping for a given reward cycle, a chunk validly signed by a signer for one lane (e.g. `BlockResponse`) is also a validly-signed chunk for any other lane at the same slot (e.g. `StateMachineUpdate` or `BlockPreCommit`). This is the same class of bug as the Casdoor report: the cryptographic artifact never encodes/validates its intended "audience" (here, the target contract), so it is accepted outside its intended scope.

### Finding Description
`SlotMetadata::auth_digest` in `libstackerdb/src/libstackerdb.rs` hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 
`SlotMetadata::verify` recovers the public key from this digest and compares its hash160 to the caller-supplied `principal` — it takes no `QualifiedContractIdentifier` at all: [2](#0-1) 

The network-facing acceptance paths call this same signature check without ever mixing the contract identity into the signed data:
- `PeerNetwork::validate_received_chunk` looks up the expected signer for `(smart_contract_id, slot_id)` and then verifies the chunk's `SlotMetadata` against that address, but the signature itself says nothing about which contract it was meant for: [3](#0-2) 
- `StackerDBTx::try_replace_chunk` (the RPC/local storage write path used by `POST /v2/stackerdb/...`) performs the identical address-only check: [4](#0-3) 

Crucially, for the Nakamoto signer set, the *same* `slot_id → signer address` ordering is shared across multiple distinct StackerDB contracts for a given `signer_set` (reward-cycle parity): the `.signers` boot contract stores one shared slot list (`stackerdb-signer-slots-0`/`-1`) which is read by every `.signers-<set>-<message_id>` contract: [5](#0-4) 
This is exercised in tests, confirming that `signers-<set>-1`, `signers-<set>-2`, `signers-<set>-3` (for `BlockResponse`, `StateMachineUpdate`, `BlockPreCommit` respectively — see `MessageSlotID`) all return the identical signer list for a given signer_set: [6](#0-5) [7](#0-6) 

Because the chunk signature never binds to which of these three lanes it was signed for, a chunk that a signer legitimately signed and pushed to `.signers-0-1` (BlockResponse) is *also* a valid, correctly-signed chunk for the identical slot in `.signers-0-2` (StateMachineUpdate) or `.signers-0-3` (BlockPreCommit), as long as the replayed chunk's `slot_version` is not stale for the target lane. Any unprivileged network relay (not the signer, not requiring any private key) that observes a broadcast `StackerDBPushChunkData` can simply re-wrap the same `chunk_data` (unchanged `slot_id`/`slot_version`/`sig`/`data`) with a different target `contract_id` and push it as unsolicited gossip; the receiving node's `handle_unsolicited_StackerDBPushChunk` → `validate_received_chunk` path (and the `FutureView`-buffering path) accepts and stores it, then relays it onward to its own peers, propagating the mismatched chunk network-wide.

I was unable to confirm within the indexed portion of the repo whether `signer_message_payload_matches_lane` (`libsigner/src/events.rs`) is actually invoked anywhere in the StackerDB write path or the `StackerDBChunksEvent`→`SignerEvent` conversion that stacks-signer/stacks-node use to interpret already-stored chunks; the only usages I could locate were its definition and its unit tests. If it is not wired into the chunk-acceptance code path (only into event *interpretation*, after the chunk has already been accepted, signed, stored, and rebroadcast by the network layer), it does not prevent the propagation itself, only possibly the consumer's later misinterpretation.

### Impact Explanation
This breaks the equality "chunk authenticated for lane/contract L" vs "chunk stored/served as belonging to lane/contract L′". A relay-only, unprivileged attacker can cause forged/misattributed signer messages to be stored in and propagated across the StackerDB replication network for a lane the original signer never targeted (e.g. taking a genuine `BlockResponse` chunk and re-announcing it under the `StateMachineUpdate` or `BlockPreCommit` contract at the matching slot), corrupting the state seen by all other stacks-node/stacks-signer instances that rely on that lane and potentially causing state-machine confusion for the affected signer's slot in the mis-targeted lane. This matches the "network-wide propagation of forged data" / "unauthorized write to StackerDB state" impact tier.

### Likelihood Explanation
The prerequisite content (a validly signed `StackerDBChunkData` in a given lane) is broadcast in the clear over the p2p network by design, so any peer participating in gossip can capture it. No signer private key or elevated privilege is required by the attacker — only relaying an already-observed, legitimately signed chunk under a different `contract_id`. The only constraint is that the target lane's current slot version for that slot_id must be lower than the replayed `slot_version` (easily satisfied for less-active lanes such as `BlockPreCommit`/`StateMachineUpdate`).

### Recommendation
Include the target StackerDB contract identifier (`QualifiedContractIdentifier`) in `SlotMetadata::auth_digest` (and thus in the signed hash), so a chunk signature is only valid for the specific contract/lane it was generated for. This requires plumbing the contract ID into `SlotMetadata::sign`/`verify`/`auth_digest`, `StackerDBChunkData::sign`/`verify`, and updating all call sites (`try_replace_chunk`, `validate_received_chunk`, RPC handlers) accordingly, with appropriate versioning/back-compat handling for existing StackerDB replicas.

### Proof of Concept
1. Observe a `StackerDBPushChunkData { contract_id: signers-0-1, chunk_data: { slot_id: 3, slot_version: 5, sig, data } }` broadcast on the p2p network (any relay node can see this).
2. Construct a new `StackerDBPushChunkData { contract_id: signers-0-2, chunk_data: <identical chunk_data> }` and push it, unsolicited, to a Stacks node that replicates both `.signers-0-1` and `.signers-0-2`.
3. The receiving node calls `validate_received_chunk` for contract `signers-0-2`: it fetches the signer address for `(signers-0-2, slot_id=3)` — the same address as in `signers-0-1` because both share the `.signers` slot list [5](#0-4)  — verifies `SlotMetadata::verify` against that address (succeeds, since the digest never included `signers-0-1` vs `signers-0-2`) [2](#0-1) , and accepts/stores the chunk if `slot_version` (5) exceeds the current version for `signers-0-2` slot 3.
4. The node relays this now-stored chunk to its own DB neighbors, propagating data signed for the `BlockResponse` lane as if it were valid `StateMachineUpdate` data.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
