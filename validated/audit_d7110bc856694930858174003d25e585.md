### Title
Cross-lane StackerDB chunk-signature replay due to missing contract binding in the signed digest — ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` in [1](#0-0)  computes the signed digest for a StackerDB chunk write from only `slot_id`, `slot_version`, and `data_hash`. It never binds the signature to the target StackerDB smart-contract identity (`contract_id`). This is the exact analog of the external report's missing-`chainID` bug: a signature schema that omits its "domain" (here, the destination StackerDB contract) can be replayed verbatim into any other context where the same signer occupies the same slot.

### Finding Description
For the Nakamoto signer set, all lane contracts for a given `signer_set` (`signers-0-1` for `BlockResponse`, `signers-0-2` for `StateMachineUpdate`, `signers-0-3` for `BlockPreCommit`, etc.) read the *same* signer→slot assignment from `.signers`, as shown in [2](#0-1)  (`stackerdb-get-signer-slots-page`) and the delegating call in [3](#0-2) . Consequently, a given signer address owns the identical `slot_id` in every one of the `signers-{set}-{message_id}` contracts (confirmed structurally in `MessageSlotID::stacker_db_contract` at [4](#0-3) , which derives each lane's contract purely from `(reward_cycle, message_id)` while the underlying slot list is shared).

Because the signed digest only covers `(slot_id, slot_version, data_hash)` — see `verify()` in [5](#0-4)  — a chunk validly signed by a signer for one lane (e.g. `StateMachineUpdate`) recovers to the exact same public key when checked against any other lane (`BlockResponse`, `BlockPreCommit`) at the same `slot_id`. The storage/validation path never re-derives or checks the target `contract_id` as part of the signature: `PeerNetwork::validate_received_chunk` in [6](#0-5)  only looks up the owner address for the *target* contract's slot and calls `slot_metadata.verify(&addr)`, which cannot distinguish which contract the chunk was actually authorized for. The same gap exists in the direct storage path, `StackerDBTx::try_replace_chunk`, exercised in [7](#0-6) .

This means any network peer that has observed a legitimately-signed chunk broadcast on lane A (StackerDB chunks are public, gossiped data — no attacker key is needed) can re-submit that exact `StackerDBChunkData` (same `sig`, same `data`) to a different lane B's `contract_id`, as long as: (1) the signer is also the owner of the same `slot_id` in lane B (guaranteed by the shared `.signers` slot-assignment page), and (2) the target lane's current slot version is not ahead of the replayed version (trivially true right after a reward-cycle rollover, or whenever the target lane is otherwise behind). The write succeeds and is accepted as valid, and is then propagated network-wide through the normal StackerDB push/broadcast mechanism, corrupting the target lane's slot with data that was never authorized for that lane and was never checked against `contract_id` at the signature level.

### Impact Explanation
This is an unauthenticated (attacker needs no private key), unauthorized write into StackerDB state: it plants replayed, out-of-context data (bearing another lane's serialized `SignerMessage`) into a slot of a StackerDB contract the original signer never intended to write. This satisfies the "Critical" bar — unauthenticated/unauthorized write to StackerDB plus network-wide propagation of forged/misrouted data, since accepted chunks are re-broadcast to StackerDB replication peers just like legitimate writes.

### Likelihood Explanation
High. No secret key or admin role is required — only observation of one publicly-broadcast, validly signed chunk from any target signer, and a version number at the destination lane that is not ahead of the replayed chunk's version (commonly true, e.g., right after a lane's slot has not yet been written in the current cycle). The cross-lane slot-sharing behavior is a hard structural property of `.signers`/`signers-{0,1}-{message_id}` contracts, not a probabilistic condition.

### Recommendation
Bind the StackerDB signature to the destination contract identity: include the `QualifiedContractIdentifier` (and ideally a chain-id/network-id and/or reward-cycle) in `SlotMetadata::auth_digest()` (`libstackerdb/src/libstackerdb.rs`), and thread the `contract_id` through `StackerDBChunkData::sign`/`verify`/`recover_pk`. Update all callers (`PeerNetwork::validate_received_chunk`, `StackerDBTx::try_replace_chunk`, the `poststackerdbchunk` HTTP handler, and `SignerCoordinator::send_miners_message`) to pass and check the contract-bound digest, and bump any wire/schema version needed for backward compatibility.

### Proof of Concept
1. Observe (via normal StackerDB replication) a validly signed `StackerDBChunkData` `C` written by signer `S` to `slot_id = k` on contract `signers-0-2` (`StateMachineUpdate` lane), version `v`.
2. Confirm `S` also owns `slot_id = k` on `signers-0-3` (`BlockPreCommit` lane) — guaranteed, since both lanes read the identical `stackerdb-signer-slots-0` list from `.signers` (`stackerdb-get-signer-slots-page`).
3. Submit `C` unmodified (same `slot_id`, `slot_version`, `sig`, `data`) as a `PostStackerDBChunk`/`StackerDBPushChunk` targeting `signers-0-3`'s `contract_id`, with the current slot version at that lane `<= v`.
4. `validate_received_chunk`/`try_replace_chunk` accepts it: `get_slot_signer` for `signers-0-3` returns `S`, and `slot_metadata.verify(&S)` succeeds because the digest never referenced `signers-0-2`. The chunk is stored and re-broadcast — an unauthorized cross-lane write has been propagated network-wide without the attacker possessing `S`'s private key.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
