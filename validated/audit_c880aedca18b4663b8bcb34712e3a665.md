### Title
Deposit accounting trusts self-reported `amount` from NEP-141 tokens, breaking internal-ledger backing for fee-on-transfer/deflationary tokens - (File: contracts/defuse/src/contract/tokens/nep141/deposit.rs)

### Summary
`ft_on_transfer` credits a user's internal Defuse balance with the full `amount` parameter reported by the calling token contract, without any check that the contract's real NEP-141 balance actually increased by that amount. For a deflationary/fee-on-transfer NEP-141 token, this mints internal ledger units ("phantom" balance) that are not backed by real tokens held by the contract.

### Finding Description
`ft_on_transfer` takes `amount: U128` as supplied by the predecessor token contract and immediately calls `self.deposit(receiver_id, [(token_id, amount.0)], ...)`, which increments both `total_supplies` and the user's `token_balances` by that exact value: [1](#0-0) 

The `deposit` helper performs no independent verification (e.g. `ft_balance_of` before/after) of how much of the token the contract's own account actually received; it simply adds the reported `amount` to `total_supplies` and to the owner's `token_balances`: [2](#0-1) 

The invariant this breaks is: `total_supplies[token_id]` (and the sum of all users' `token_balances[token_id]`) should equal the actual NEP-141 balance the contract holds in the underlying token contract. For a standard-compliant, non-fee token this holds because `ft_transfer_call` credits the receiver's real balance by exactly `amount` before invoking `ft_on_transfer`. But a deflationary/fee-on-transfer NEP-141 token can implement its own `ft_transfer_call`/`internal_transfer` so that the contract's real balance increases by `amount - fee`, while still invoking `ft_on_transfer(sender_id, amount, msg)` with the full nominal `amount`. Nothing in the receiver's logic (`ft_on_transfer`/`deposit`) distinguishes "amount claimed" from "amount actually received."

The withdrawal path attempts to reconcile actual vs. requested only for the outbound leg (via `ft_resolve_withdraw`, using the returned "used" amount from `ft_transfer_call`), but on the inbound/deposit leg there is no equivalent reconciliation: [3](#0-2) 

### Impact Explanation
This breaks the conservation-of-value binding between "value debited versus value delivered": the internal MT ledger (`total_supplies`/`token_balances`) for a given `Nep141TokenId` can be inflated beyond the real token backing held by the contract. Once inflated, the over-credited internal balance is a fully fungible, tradeable Defuse asset — it can be transferred via `mt_transfer`, used in signed `Transfer`/swap intents, or withdrawn via `FtWithdraw`. An attacker who deposits such a deflationary token receives internal credit for more than they actually contributed, and can then exchange that credit (through intents with other counterparties, or by being first to withdraw) for genuinely-backed assets, extracting value at the expense of other depositors/holders of that token_id, or leaving the pool insolvent (later legitimate withdrawals of that token_id fail because the real token balance is short). This matches the "TokenId names an asset that doesn't match the asset actually moved" / value-conservation class called out as Critical.

### Likelihood Explanation
Reaching this path requires nothing beyond depositing an NEP-141 token that applies a transfer fee/deflationary mechanism while still reporting the pre-fee amount to `ft_on_transfer` — no privileged role, relayer, or DAO action is needed; any account can call `ft_transfer_call` against any NEP-141 contract, including one the attacker deploys and controls, targeting the Defuse contract. The likelihood of the specific token type existing on mainnet against intents.near's exact allow-list is uncertain (I could not find any documented restriction in `contracts/defuse/README.md` or elsewhere in the in-scope code that excludes non-standard/fee-on-transfer NEP-141 tokens), so this is a plausible but token-dependent path rather than one that is unconditionally exploitable against any deposited asset.

### Recommendation
Either (a) explicitly restrict/allow-list NEP-141 tokens usable with `ft_on_transfer` to those verified as standard-compliant (no transfer fee, 1:1 balance semantics), or (b) verify actual received balance by querying `ft_balance_of(current_account_id())` before and after crediting, and only credit the delta actually received, mirroring the reconciliation already done on the withdrawal path in `ft_resolve_withdraw`.

### Proof of Concept
1. Attacker deploys a NEP-141 token contract `evltoken.near` whose `ft_transfer_call` deducts a 50% fee: it internally credits the receiver only `amount/2` real balance, but still invokes `ft_on_transfer(sender_id, amount, msg)` with the full requested `amount`.
2. Attacker calls `evltoken.near::ft_transfer_call(defuse.near, 1_000_000, None, msg)`.
3. Inside `defuse.near`, `ft_on_transfer` receives `amount = 1_000_000` and calls `self.deposit(attacker, [(Nep141TokenId(evltoken.near), 1_000_000)], ...)`, crediting the attacker 1,000,000 internal units, even though `defuse.near`'s real `evltoken.near` balance only increased by 500,000. [4](#0-3) 
4. Attacker signs a `Transfer`/swap intent moving the 1,000,000 internally-credited `evltoken.near` units to another account in exchange for a fully-backed asset (e.g. USDC), or attempts to `FtWithdraw` the 1,000,000 units — the second withdrawal from this token_id pool by any other holder will fail or drain funds that were never actually deposited, because the real `evltoken.near` balance held by `defuse.near` is only 500,000.

Because I could not fully confirm whether intents.near restricts deposits to a specific vetted set of NEP-141 tokens via off-chain/DAO governance configuration (which is out of scope for on-chain code review), the practical exploitability depends on whether such an allow-list is enforced outside the reviewed contracts.

    fn ft_on_transfer(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        msg: String,
    ) -> PromiseOrValue<U128> {
        require!(amount.0 > 0, "zero amount");

        let token_id = TokenId::Nep141(Nep141TokenId::new(env::predecessor_account_id()));

        let DepositMessage {
            receiver_id,
            action,
        } = if msg.is_empty() {
            DepositMessage::new(sender_id.clone())
        } else {
            msg.parse().unwrap_or_else(|e| panic!("{e}"))
        };

        self.deposit(
            receiver_id.clone(),
            [(token_id.clone(), amount.0)],
            Some("deposit"),
        )
        .unwrap_or_else(|err| err.panic());

    pub(crate) fn deposit(
        &mut self,
        owner_id: AccountId,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
        memo: Option<&str>,
    ) -> Result<()> {
        let owner = self
            .storage
            .accounts
            .get_or_create(owner_id.clone())
            // deposits are allowed for locked accounts
            .as_inner_unchecked_mut();

        let mut mint_event = MtMintEvent {
            owner_id: owner_id.into(),
            token_ids: Vec::new().into(),
            amounts: Vec::new().into(),
            memo: memo.map(Into::into),
        };

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            mint_event.token_ids.to_mut().push(token_id.to_string());
            mint_event.amounts.to_mut().push(amount);

            let total_supply = self
                .storage
                .state
                .total_supplies
                .add(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;
            match token_id {
                TokenId::Nep171(ref tid) => {
                    if total_supply > 1 {
                        return Err(DefuseError::NftAlreadyDeposited(tid.clone()));
                    }
                }
                TokenId::Nep141(_) | TokenId::Nep245(_) | TokenId::Imt(_) => {}
            }

            owner
                .token_balances
                .add(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

        if !mint_event.amounts.is_empty() {
            MtEvent::MtMint([mint_event].as_slice().into())
                .check_refund()?
                .emit();
        }

        Ok(())
    }

#[near]
impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
