### Title
Fee bypass on NEP-245/IMT `TokenDiff` swaps by splitting `delta` into `|delta| ≤ 1` chunks - (File: `contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee` computes the protocol fee per individual `TokenDiff` intent using only that intent's own `|delta|`, exempting `Nep245`/`Imt` tokens whenever `amount ≤ 1`. Because the `TransferMatcher` nets withdrawals and deposits across *all* intents in the whole `execute_signed_intents` batch (not per-intent), an attacker can split one large NEP-245 withdrawal into many `delta = -1` `TokenDiff` intents, each fee-exempt, while the aggregate `-N` amount is still netted against a counterparty's `+N` deposit — fully bypassing the fee that a single `delta = -N` intent would have paid.

### Finding Description
The broken binding: for a token `T`, `fees_collected(T)` credited to `fee_collector` should equal the fee owed on the true executed amount, i.e. `Pips::fee_ceil(token_fee(T, |Σdelta_T|, protocol_fee), |Σdelta_T|)`. Instead, the contract computes and collects fee **per intent**: [1](#0-0) 

using `Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount)` where `amount = delta.unsigned_abs()` is the delta of that single `TokenDiff` intent, not the sum across the batch. `token_fee` explicitly exempts NFT/MT tokens when the per-intent amount is `≤ 1`: [2](#0-1) 

Meanwhile, `DefuseIntents` executes an arbitrary list of intents in one signed payload sequentially, each independently invoking `TokenDiff::execute_intent`: [3](#0-2) 

and `execute_signed_intents` accumulates deltas from *all* signed payloads/intents in the call into a single shared `TransferMatcher` state, only finalizing (netting deposits vs withdrawals) once at the very end: [4](#0-3) 

`internal_add_balance`/`internal_sub_balance` feed every withdrawal/deposit — regardless of which intent produced it — into the same `TransferMatcher`: [5](#0-4) 

**Exploit**: attacker signs (or has a payload constructed with) `N` separate `TokenDiff` intents, each `{diff: {token_id_nep245: -1}}`, plus one intent crediting the offsetting token(s) they want out. A counterparty (self-controlled second account, or colluding solver) submits a matching `+N` deposit for the same NEP-245 token in the same `execute_intents`/`simulate_intents` call. Each of the `N` intents independently hits the `amount = 1` branch of `token_fee`, returning `Pips::ZERO`, so `fees_collected` for that intent is `0`. The `TransferMatcher::finalize` nets the aggregate `-N` withdrawal against the `+N` deposit exactly as if it were one honest swap of size `N`, but the fee actually collected is `0` instead of `Pips::fee_ceil(protocol_fee, N)`. No existing guard (`verify`, nonce, `assert_one_yocto`, `#[pause]`, `checked_*` arithmetic) prevents this since it does not violate signature, nonce, or balance-conservation checks — it only affects fee accounting, which is computed strictly locally to each intent.

### Impact Explanation
The protocol systematically under-collects fees on any NEP-245/IMT-denominated flow whenever the withdrawing party structures it as many `delta = -1` intents instead of one large delta. This directly breaks the invariant that fees credited to `fee_collector` match the fees owed on the executed deltas — an explicit "protocol fees bypassed" case, which the rules classify as Critical. The attacker keeps the full swapped value (no NFT/MT fee at all) while the intended fee revenue never reaches `fee_collector`; this is repeatable across any account, any NEP-245/IMT token, and any batch size (bounded only by gas/payload size, which is out of scope but does not prevent feasibility for moderately large `N`).

### Likelihood Explanation
No privileged role is required. The attacker only needs: (1) a Verifier balance of the NEP-245/IMT token they want to swap, (2) the ability to sign one (or several) `MultiPayload`s containing `N` `TokenDiff` intents with `delta = -1` each, and (3) a counterparty (which can be a second account they also control) willing to supply the offsetting `+N` deposit within the same `execute_intents`/`simulate_intents` call. This requires no special timing, no race condition, and works deterministically every time — it is purely a structuring trick around the fee-exemption threshold.

### Recommendation
Compute `token_fee` based on the *aggregate* signed net delta per token across the whole batch (or per signer across intents) rather than per individual `TokenDiff` intent — e.g., accumulate deltas per `(signer_id, token_id)` before applying `token_fee`/`fee_ceil`, mirroring how `TransferMatcher` nets globally. Alternatively, remove/restrict the `amount ≤ 1` exemption to a per-account-per-token cumulative counter that persists across a batch, so splitting into unit deltas cannot zero out the fee.

### Proof of Concept
`cargo test` (near-workspaces sandbox), extending `tests/src/tests/defuse/intents/token_diff.rs`:
1. Set `protocol_fee = Pips::ONE_PERCENT` via `Env::builder().fee(fee)`.
2. Deposit an attacker with `N = 100` units of a `Nep245` token, and a counterparty with the offsetting output token, willing to give `+N` of the NEP-245 token back (or receive it).
3. Build payload A: attacker signs `N` separate `TokenDiff` intents, each `{diff: {nep245_token: -1, other_token: +closure_delta_i}}` such that the sum of `other_token` legs equals what a single big swap would produce.
4. Build payload B: counterparty signs a single `TokenDiff` with `{nep245_token: +N, other_token: -Σclosure_delta_i}`.
5. Call `execute_intents([payload_A_intents..., payload_B])` and read the `TokenDiffEvent::fees_collected` logs / final `mt_balance_of(fee_collector, nep245_token)`.
6. Assert `fee_collector` balance delta for `nep245_token` `== 0`.
7. Compare against `TokenDiff::token_fee(nep245_token, N, protocol_fee).fee_ceil(N)`, which is `> 0` since `N > 1` — demonstrating the fee owed on the aggregate amount was bypassed entirely by the per-intent `amount ≤ 1` exemption.
