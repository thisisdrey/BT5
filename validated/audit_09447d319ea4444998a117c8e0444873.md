### Title
Stale cached `tokenSpeeds` distributes rewards after Vesper `periodFinish` - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor.syncTokenSpeed()` snapshots Vesper’s `rewardRates`, treasury pool share, and `periodFinish` into `tokenSpeeds`, but reward accrual later uses the cached speed without independently checking whether the external reward period has ended or whether the rate/share changed. [1](#0-0)  Once `periodFinish` passes, `_calculateTokenIndex()` continues multiplying elapsed time by the stale positive speed. [2](#0-1) 

### Finding Description
The only production refresh path computes the current Vesper-derived speed and sets it to zero when `block.timestamp >= periodFinish`, but it is restricted to `tokenSpeedKeeper`. [1](#0-0)  Between syncs, `tokenSpeeds[token]` remains fixed even if Vesper’s reward rate, treasury share, pool supply, or reward period changes. [3](#0-2)  Every user-facing accrual path then applies that stale value for the full elapsed interval through `_updateTokenIndex()`. [4](#0-3) 

The issue is reachable through ordinary deposit-token or debt-token activity because those contracts invoke `updateBeforeMintOrBurn()` or `updateBeforeTransfer()` before balance changes. [5](#0-4)  An unprivileged holder can also directly call `claimRewards(attacker)` after waiting past `periodFinish`; the function updates the stale index, accrues the attacker’s delta, and transfers up to the distributor’s actual reward-token balance. [6](#0-5) 

### Impact Explanation
After the external reward period ends, users continue accruing protocol rewards at the old speed even though no additional Vesper rewards should be attributed to that period. If accrued entitlements exceed the distributor’s balance, the first claimants can receive funds that should not have accrued, while later claimants receive nothing because `_transferRewardIfEnoughTokens()` silently skips underfunded payouts. [7](#0-6)  This breaks reward-accrual correctness and can cause theft or permanent loss of unclaimed yield for later entitled users.

### Likelihood Explanation
No privileged attacker action is required: a user only needs a rewarded deposit/debt balance and a public claim after a normal Vesper reward-rate change or `periodFinish` boundary occurs before the next keeper synchronization. `nonReentrant` protects the claim call but does not validate that the stored speed still reflects the external reward state. [8](#0-7) 

### Recommendation
Do not cache the Vesper-derived speed across reward accrual. Recalculate `rewardRates * treasuryVPoolBalance / vPoolTotalSupply` and check `periodFinish` inside `_calculateTokenIndex()` or a common index-refresh path. At minimum, store the Vesper `periodFinish` alongside `tokenSpeeds` and clamp accrual to `min(block.timestamp, periodFinish)`, then automatically set the effective speed to zero after expiry.

### Proof of Concept
On a mainnet fork using a deployed `RewardsDistributor` with a configured positive `tokenSpeed` for a Vesper-backed `DepositToken`:

```ts
// Hardhat fork test outline
const now = await time.latest();
const finish = await vesperPoolRewards.periodFinish(await distributor.rewardToken());

// Warp from an active reward period to after its finish without calling syncTokenSpeed().
await time.increaseTo(finish + 3600);

// The stored speed remains positive even though the external period ended.
expect(await distributor.tokenSpeeds(depositToken)).to.be.gt(0);

// Rewards continue accruing against the stale cached speed.
const before = await distributor.claimable(attacker.address);
await time.increase(3600);
const after = await distributor.claimable(attacker.address);
expect(after).to.be.gt(before);

// An unprivileged user claims first and receives stale-speed rewards.
await distributor.connect(attacker).claimRewards(attacker.address);
expect(await rewardToken.balanceOf(attacker.address)).to.be.gt(attackerBalanceBefore);

// Once the distributor is depleted, another user's accrued claim transfers nothing.
await distributor.connect(victim).claimRewards(victim.address);
expect(await rewardToken.balanceOf(victim.address)).to.eq(victimBalanceBefore);
```
