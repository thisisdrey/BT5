The report concerns npm's `timespan` package using a vulnerable regular expression to parse dates/durations, causing catastrophic backtracking (ReDoS). Searching the Go standard library repository for the closest analogous code — duration/date parsing — turns up `time.ParseDuration` in [1](#0-0)  and `parseDurationISO8601` in [2](#0-1) . Both of these parse duration/date strings using hand-written, linear-time character-by-character scanning (`leadingInt`, `leadingFraction`, `cutBytes`, explicit loops) rather than `regexp`, with explicit overflow and bounds checks throughout [3](#0-2) [4](#0-3) . There is no use of `regexp.MustCompile` or any backtracking regex engine in these date/duration parsing paths — the `regexp.MustCompile` matches found across the repo are all confined to test files, tooling scripts (`cover`, `vet`, `simdgen`, etc.), and unrelated code, not to any production duration/date/time parsing logic.

Since Go's duration and ISO 8601 date parsers use bounded, linear-time manual parsing instead of a backtracking regex engine, the ReDoS primitive from the `timespan` advisory does not have a matching analog in this codebase.
