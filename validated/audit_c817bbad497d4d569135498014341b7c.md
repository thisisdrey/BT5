Audit Report

## Title
`claim_rewards_to()` commits reward removal on BridgeHub before the cross-chain payout to AssetHub is guaranteed to succeed, permanently destroying relayer rewards below the destination minimum balance - (File: `bridges/modules/relayers/src/lib.rs`, `bridges/snowbridge/primitives/core/src/reward.rs`)

## Summary
`Pallet::do_claim_rewards` deletes the relayer's `RelayerRewards` entry and emits `Event::RewardPaid` as soon as `T::PaymentProcedure::pay_reward` returns `Ok(())`, but for Snowbridge, `pay_reward` (`PayAccountOnLocation`) only validates, charges fees for, and dispatches a fire-and-forget `UnpaidExecution` XCM to AssetHub — it never confirms that the `DepositAsset` instruction actually executes successfully there. Rewards below the destination asset's minimum balance are rejected by `pallet_assets` on AssetHub execution, after the BridgeHub-side accounting has already been irreversibly committed, causing a permanent, unrecoverable loss of the relayer's reward.

## Finding Description
In `do_claim_rewards` (`bridges/modules/relayers/src/lib.rs` L263-302), `RelayerRewards::<T, I>::try_mutate_exists` takes the reward balance out of storage inside the closure, calls `T::PaymentProcedure::pay_reward(...)`, and if it returns `Ok(())`, commits the removal and emits `Event::RewardPaid` [1](#0-0) .

For Snowbridge, `T::PaymentProcedure` is `PayAccountOnLocation` (`bridges/snowbridge/primitives/core/src/reward.rs` L127-151). Its `pay_reward` builds an `UnpaidExecution` XCM containing `ReserveAssetDeposited` + `DepositAsset` targeting AssetHub, and returns `Ok(())` as soon as `validate_send`, `charge_fees`, and `XcmSender::deliver` succeed — all of which happen entirely on BridgeHub [2](#0-1) . There is no XCM query/response or execution-confirmation mechanism; success on BridgeHub only means the message was dispatched, not that it executed successfully on AssetHub.

No minimum-reward guard exists anywhere in the reachable code path: a repo-wide search confirms there is no `MinimumClaimableReward` or `RewardBelowMinimum` check in `do_claim_rewards`, `RelayerRewards`, or `PayAccountOnLocation::pay_reward`. If the claimed `reward_balance` is below the destination foreign asset's minimum balance (referenced as `ETHER_MIN_BALANCE` in the test suite), the `DepositAsset` instruction is rejected by `pallet_assets`/`ForeignAssets` on AssetHub execution, and the reserve-deposited asset is trapped/burnt there — while on BridgeHub the reward entry is already deleted and `RewardPaid` already emitted, with no error surfaced and no retry path.

## Impact Explanation
This matches the explicitly in-scope "permanent user-fund or bridge-state lock" category and violates the pivot requiring that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." The corrupted state is the `RelayerRewards` double-map entry: it is deleted (settlement "succeeds") on BridgeHub despite the corresponding AssetHub-side asset deposit failing, resulting in permanent, unrecoverable loss of the relayer's reward balance with no compensating record or retry mechanism.

## Likelihood Explanation
`claim_rewards_to` is a public, unprivileged, signed extrinsic reachable by any relayer holding any nonzero `RelayerRewards` entry [3](#0-2) . Small reward accumulations are plausible in practice (e.g., a single low-fee message, or accumulated dust from partial reward registrations via `register_reward` in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`), and nothing in the codebase enforces a minimum threshold before the claim proceeds. No malicious peer, relayer collusion, or privileged action is required — this is a straightforward, always-reachable path for any relayer whose accrued reward happens to fall under the destination minimum balance.

## Recommendation
- Add an explicit `ensure!(reward_balance >= T::MinimumClaimableReward::get(), Error::<T, I>::RewardBelowMinimum)` guard in `do_claim_rewards` before invoking `PaymentProcedure::pay_reward`, using the known destination-chain minimum balance as the threshold.
- Alternatively, make the payment procedure genuinely atomic with respect to destination-chain execution — e.g., use an XCM query/response pattern to confirm successful execution on AssetHub before removing the `RelayerRewards` entry and emitting `RewardPaid`, or restore the entry upon receipt of an execution failure notification.

## Proof of Concept
1. A relayer accrues a small reward via `register_reward`, e.g., `reward_balance` set below `ETHER_MIN_BALANCE` (see reward registration in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` L464-473).
2. The relayer calls `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(...))`.
3. `do_claim_rewards` takes the reward from storage and calls `PayAccountOnLocation::pay_reward`, which validates/charges fees/delivers the XCM and returns `Ok(())` on BridgeHub; the `RelayerRewards` entry is deleted and `RewardPaid` is emitted.
4. On AssetHub, `DepositAsset` executes with an amount below the foreign asset's minimum balance; `pallet_assets` rejects the deposit and the reserve-deposited asset is trapped/burnt.
5. The relayer's `RelayerRewards` entry no longer exists (deleted in step 3), and no funds land in the relayer's AssetHub account — a permanent loss with no error ever surfaced on BridgeHub, since `pay_reward` already returned `Ok`. This scenario is not covered by existing tests (`claim_snowbridge_rewards_to_local_account_fails` uses a rejected beneficiary variant before any XCM is built; `claim_rewards_works` deliberately sets `reward_amount = ETHER_MIN_BALANCE * 2` to avoid triggering the bug), confirming the gap is untested.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
