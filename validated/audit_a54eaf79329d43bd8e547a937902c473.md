### Title
Permissionless `init_global_fee_state` allows front-running to seize global fee admin / fee wallet - (File: `programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs`)

### Summary
`init_global_fee_state` is a "run once per program" instruction that creates the singleton `FeeState` PDA and sets its `global_fee_admin` and `global_fee_wallet` from caller-supplied arguments, with no access control restricting who may call it [1](#0-0) . This is the same bug class as the Velodrome `setGauge` finding: a critical, one-time "constructor-like" setter that is meant to be called atomically as part of deployment, but is actually callable by anyone, and once called successfully (`init` constraint on the PDA) it can never be re-run.

### Finding Description
The `InitFeeState` accounts struct only requires `payer` to be a signer paying rent for the PDA; there is no check that `payer` is the intended deployer/admin, nor any other authorization gate: [2](#0-1) 

The handler blindly trusts the `admin_key` and `fee_wallet` parameters passed by the caller and writes them into the newly created `FeeState` account: [1](#0-0) 

Because the `fee_state` account is a PDA derived solely from `FEE_STATE_SEED` (no signer-specific seed) and uses Anchor's `init` constraint, it can only be created once, by whoever's transaction lands first: [3](#0-2) 

The PDA address is fully deterministic and computable off-chain before deployment. Any unprivileged actor monitoring the network for the marginfi program's deployment/upgrade can race the legitimate deployer's initialization transaction (front-run it), supplying their own `admin_key`/`fee_wallet` and any other fee parameters. This mirrors the report's root cause: a permissionless "set once" call (`setGauge`/here, `init_global_fee_state`) that is supposed to run atomically with a constructor-like deployment step but is not enforced to do so on-chain.

The `global_fee_admin` role is highly privileged downstream: per `guides/ADMIN/PERMISSIONS_AND_ROLES.md`, it controls global fee state edits, setting the pause-delegate admin, and panic-pause/unpause of the entire protocol [4](#0-3) . `MarginfiGroupInitialize` also reads from this same `fee_state` PDA to seed each new group's `fee_state_cache` (global fee wallet/fees), so a hijacked `FeeState` would propagate the attacker-controlled fee wallet/fee rates into every group created afterward [5](#0-4) .

### Impact Explanation
If exploited, an unprivileged attacker becomes the permanent `global_fee_admin`/`global_fee_wallet` for the entire protocol, since the `FeeState` PDA is `init`-once and cannot be re-created or reset through any exposed instruction found in the reviewed code. This is a permanent unauthorized state change requiring a redeploy (new program ID or new seed) to recover — directly analogous to the "Bribe redeployment" remediation in the source report. Downstream consequences include attacker control over protocol fee routing/fee wallet and pause/unpause authority delegation, i.e., unauthorized privileged-state takeover, not merely a griefing DoS.

### Likelihood Explanation
Exploitation requires only that the attacker observe the (public) program deployment and beat the legitimate deployer's `init_global_fee_state` call into a subsequent block/slot — a standard front-running/race condition on a public, permissionless instruction with no atomicity guarantee with program deployment. This requires no special privileges, and Solana's public mempool/leader schedule makes such races practically executable by any well-resourced or vigilant attacker at deployment time.

### Recommendation
Restrict `init_global_fee_state` (and `init_global_fee_state_v2`) to a trusted, hardcoded/known authority (e.g., require `payer` to match a fixed pubkey baked into the program, or gate it via an `#[account(constraint = ...)]` check, or fold it into the program's `Initialize`/upgrade authority verification). Alternatively, bundle fee-state initialization atomically with program deployment/upgrade (e.g., call it in the same transaction as the deploy, or use a program-derived signer that only the upgrade authority can invoke) so no window exists for an unprivileged actor to front-run it.

### Proof of Concept
1. Attacker monitors the network for the marginfi program's deployment (program ID becomes known/executable).
2. Attacker computes the deterministic `FeeState` PDA using `FEE_STATE_SEED` and the known program ID.
3. Before the legitimate deployer submits their `init_global_fee_state` transaction, the attacker submits their own transaction calling `init_global_fee_state(admin_key = attacker_pubkey, fee_wallet = attacker_wallet, ...)`, paying the minor rent cost themselves as `payer` — no other signer/authorization is required per the `InitFeeState` accounts struct.
4. Because `fee_state` uses Anchor's `init` constraint keyed only by the seed, the attacker's transaction succeeds first and permanently sets `global_fee_admin`/`global_fee_wallet` to attacker-controlled values.
5. The legitimate deployer's subsequent `init_global_fee_state` call fails (`already in use`), and there is no instruction in the reviewed codebase to reset/recreate this singleton PDA, permanently freezing the intended admin out of the fee-admin role.

pub struct InitFeeState<'info> {

}
