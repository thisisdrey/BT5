### Title
Non-Constant-Time Comparison of the RPC `auth_token` Enables Timing Side-Channel Secret Recovery - (File: stackslib/src/net/api/postblock_proposal.rs)

### Summary
The `/v3/block_proposal`, `/v3/blocks/simulate/*`, `/v3/blocks/replay/*`, and `/v2/blocks?broadcast=1` RPC endpoints authenticate the caller by comparing the client-supplied `authorization` header against the node's configured secret (`connection_options.auth_token`) using a plain, non-constant-time equality check (`auth_header != password`). This mirrors the bug class behind CVE-2015-7503 (Zend Framework): a security-critical secret comparison performed without timing-side-channel protection, allowing a remote, unauthenticated attacker to incrementally recover the secret by observing response-timing differences byte-by-byte, rather than being forced to guess the whole token at once.

### Finding Description
Every handler that gates access with `auth_token` performs the check the same way: [1](#0-0) 

```rust
let Some(password) = &self.auth else {
    return Err(Error::Http(400, "Bad Request.".into()));
};
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```

The identical pattern is repeated in: [2](#0-1) [3](#0-2) [4](#0-3) 

`&str`/`String` equality in Rust (`PartialEq` for `str`) is implemented as a length check followed by a byte-wise `memcmp`-style comparison that returns as soon as a mismatching byte is found. This means the time taken by `auth_header != password` is a function of how many leading bytes of the guessed token match the real secret — the exact same class of flaw that made CVE-2015-7503's crypto comparison exploitable to leak private-key material: an equality test over a secret that isn't computed in constant time.

This breaks the intended equality guarantee "attacker-supplied credential == stored secret must be indistinguishable in timing," which is explicitly one of the equality classes in scope for this analysis. Any of these RPC handlers are reachable by an unauthenticated remote peer (the whole point of the check is to gate otherwise-unauthenticated HTTP requests), so an attacker can issue a large number of guesses and use timing statistics to reconstruct `auth_token` one byte at a time, drastically reducing the brute-force search space from `O(basecount)^token_length` to `O(basecount * token_length)`.

Once `auth_token` is recovered, the attacker gains legitimate access to sensitive/privileged endpoints protected by this exact same secret:
- `/v3/block_proposal` — submit block proposals directly to a miner/signer's validation pipeline.
- `/v2/blocks?broadcast=1` — force-broadcast Stacks blocks.
- `/v3/blocks/simulate/*`, `/v3/blocks/replay/*` — invoke potentially compute-heavy debug/replay endpoints.

### Impact Explanation
Successful timing-based recovery of the shared `auth_token` results in unauthorized access to endpoints intended to be gated behind signer/node coordination secrets — effectively an auth bypass for the node/signer communication channel. This falls under the "auth bypass" Critical-impact category, since the recovered secret is precisely the credential these endpoints use to distinguish trusted signer traffic from arbitrary remote requests.

### Likelihood Explanation
The likelihood is constrained by real-world timing-attack noise (network jitter, statistical averaging requirements), so this is a lower-confidence, higher-effort attack path rather than a single-request exploit. It requires many repeated requests and statistical timing analysis, but no privileges, no prior secrets, and is reachable purely over the network against any node/miner that has `auth_token` configured (which is required for signer-node coordination per `docs/signing.md`). The vulnerability is deterministic in code (the same non-constant-time pattern is repeated in four separate handlers), so remediation is a small, well-understood fix (constant-time comparison, e.g. `subtle::ConstantTimeEq`), consistent with a class of finding auditors flag even when full network exploitation requires many samples.

### Recommendation
Replace the `auth_header != password` checks in `postblock_proposal.rs`, `postblock_v3.rs`, `blockreplay.rs`, and `blocksimulate.rs` with a constant-time comparison (e.g., using the `subtle` crate's `ConstantTimeEq`, or a manual XOR-accumulate comparison over the full byte length regardless of early mismatches) so that the secret `auth_token` cannot be inferred via response-timing analysis.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"`.
2. Issue repeated POST requests to `/v3/block_proposal` with `authorization` headers guessing successive prefixes of the token (e.g. `"a"`, `"aa"`, `"ab"`, ...), measuring response latency for each guess via high-resolution timers averaged over many trials to filter network noise.
3. Because `auth_header != password` short-circuits at the first mismatching byte, correct-prefix guesses take measurably (statistically) longer than incorrect ones, allowing incremental byte-by-byte recovery of `auth_token` without ever needing to guess the full secret at once.
4. Once recovered, use the token to submit forged/privileged requests to `/v3/block_proposal` or `/v2/blocks?broadcast=1`.
