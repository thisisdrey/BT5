### Title
Shielded-transaction spend authorizing keys (`ask`/`nsk`/`ovk`, sapling ephemeral secrets) are never explicit-zeroed after use, leaving raw spend keys recoverable from freed JVM heap - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
The HTTP/gRPC endpoint `wallet/createshieldedtransaction` (`Wallet.createShieldedTransaction`) accepts a client's raw Sapling `ask` (spend authorizing key), `nsk` (proof authorizing key) and `ovk` (outgoing viewing key) directly in the request body so the node can build the zk-SNARK spend proof on the caller's behalf. These byte arrays are wrapped into an `ExpandedSpendingKey` and threaded through `ZenTransactionBuilder`/`SpendDescriptionInfo`, `NoteEncryption` (ephemeral secret `esk`), and native `librustzcash`/`libsodium` calls, then simply dropped and left for GC — none of the intermediate `byte[]` buffers are cleared with `Arrays.fill(..., (byte) 0)` before becoming unreachable.

### Finding Description
`Wallet.createShieldedTransaction` extracts the caller-supplied secret material directly from the wire request: [1](#0-0) 

These bytes are wrapped in `ExpandedSpendingKey` and passed to `ZenTransactionBuilder.addSpend`, which stores them in a `SpendDescriptionInfo`: [2](#0-1) [3](#0-2) 

`ExpandedSpendingKey` itself is a plain holder for `ask`/`nsk`/`ovk` with no destroy/wipe method: [4](#0-3) 

Similarly, `SpendingKey.PRF.prfExpand` and `NoteEncryption.fromDiversifier`/`encryptToRecipient` generate and hold ephemeral secret scalars (`esk`, `dhsecret`, `kEnc`, `ock`) as transient `byte[]` that are handed to native code and then discarded without zeroing: [5](#0-4) [6](#0-5) 

A search across `org.tron.core.zen` confirms no `Arrays.fill`/explicit-zeroing pattern exists on any of these spend-key/ephemeral-key code paths (only `ShieldedTRC20ParametersBuilder.java` and `NoteEncryption.java` contain unrelated "clear"/"zero" hits that are not key-wiping). Once the request completes, these arrays (containing the caller's raw spend authorizing key — equivalent in sensitivity to a private key, since possession of `ask`/`nsk` lets an attacker spend the shielded note) become garbage but their contents remain byte-for-byte in the heap until overwritten by chance, exactly the bug class described in CVE-2026-48984 (freeing sensitive buffers without `explicit_bzero`).

### Impact Explanation
Unlike a typical private-key parameter that a client would keep local, this design already requires the node to receive the raw Sapling spend key over the network per-request; a heap-inspection primitive on the node (e.g., via a native-library crash dump, a debugger/JMX endpoint, memory-mapped swap, or a co-located vulnerability that permits arbitrary heap reads) could recover a shielded spend authorizing key from a completed but not-yet-GC'd request, allowing unauthorized spending of the corresponding shielded note (theft of funds). This is a defence-in-depth gap rather than a directly remotely triggerable RCE, but it strengthens exploitation of any adjacent memory-disclosure bug against a node that serves the shielded transaction API.

### Likelihood Explanation
Exploitation requires an additional heap-read/inspection capability (e.g., a JVM heap dump, a native crash core, or an unrelated info-leak) — it is not a standalone remote-exploit primitive. However, the shielded-transaction API is reachable by any anonymous client that can build the appropriate gRPC/HTTP payload (subject to `checkAllowShieldedTransactionApi()` and the parameter allowing this API to be enabled), and the number of long-lived arrays carrying this material (`ask`, `nsk`, `ovk`, `esk`, `dhsecret`, `kEnc`, `ock`) is large, widening the window during which the secret persists uncleared in heap.

### Recommendation
- After native proof/signature generation completes (`generateSpendProof`, `createSpendAuth`, `NoteEncryption.encryptToRecipient/encryptToOurselves`, `SpendingKey.PRF.prfExpand`), explicitly zero the transient key-material buffers (`ask`, `nsk`, `ovk`, `esk`, `dhsecret`, `kEnc`, `ock`, `tmp`, `blob`) via `Arrays.fill(buf, (byte) 0)` in a `finally` block, mirroring the pattern already used for password/keystore buffers in `KeystoreCliUtils`.
- Consider adding a `destroy()`/`wipe()` method on `ExpandedSpendingKey` and `SpendingKey` invoked once the transaction/proof build finishes (success or failure) in `Wallet.createShieldedTransaction`, `Wallet.createShieldedTransactionWithoutSpendAuthSig`, and `ZenTransactionBuilder`.
- Where feasible, avoid transporting raw `ask`/`nsk` to the node at all in favor of client-side proof generation, which removes the exposure entirely; this is a broader design change beyond the immediate memory-hygiene fix.

### Proof of Concept
1. Enable the shielded transaction API (`allowShieldedTransaction=1`) on a node.
2. Send a `wallet/createshieldedtransaction` request containing a valid `ask`/`nsk`/`ovk` (as demonstrated in `HttpMethed.sendShieldCoin`, which builds exactly this payload) so `Wallet.createShieldedTransaction` executes lines 2283–2350 of `Wallet.java`. [7](#0-6) 
3. On a JVM where a heap-dump/inspection capability exists (e.g., triggering a native `librustzcash`/`libsodium` crash, or using `jmap`/`jcmd` if locally reachable, or via any co-located memory-disclosure bug), search the dumped heap for the 32-byte `ask`/`nsk` values supplied in step 2 — they will still be present verbatim because no `Arrays.fill` zeroing occurs anywhere along the `ExpandedSpendingKey` → `SpendDescriptionInfo` → proof-generation path before the arrays become unreachable.

    private static byte[] prfExpand(byte[] sk, byte t) throws ZksnarkException {
      byte[] res = new byte[64];
      byte[] blob = new byte[33];
      System.arraycopy(sk, 0, blob, 0, 32);
      blob[32] = t;
      long state = JLibsodium.initState();
      try {
        JLibsodium.cryptoGenerichashBlake2bInitSaltPersonal(new Blake2bInitSaltPersonalParams(
            state, null, 0, 64, null,
            Constant.ZTRON_EXPANDSEED_PERSONALIZATION));
        JLibsodium.cryptoGenerichashBlake2bUpdate(new Blake2bUpdateParams(state, blob, 33));
        JLibsodium.cryptoGenerichashBlake2bFinal(new Blake2bFinalParams(state, res, 64));
      } finally {
        JLibsodium.freeState(state);
      }
      return res;
    }
