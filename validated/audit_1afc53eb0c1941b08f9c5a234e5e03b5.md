### Title
SlotMetadata signature omits the StackerDB contract identity, enabling cross-contract chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the digest that a StackerDB signer signs over — but, exactly like the `CalculateRequestHash` bug in the external report (which hashes everything except `QuorumIDs`), it omits a field that should scope the signature to a specific context. Here, the omitted field is the StackerDB's `smart_contract_id`. The signature only binds `(slot_id, slot_version, data_hash)`, never the identity of the StackerDB instance the chunk is meant for.

### Finding Description
`SlotMetadata::auth_digest()` builds the message that gets signed/verified for every StackerDB chunk: [1](#0-0) 

Note it hashes only `slot_id`, `slot_version`, and `data_hash` — never the `QualifiedContractIdentifier` (`smart_contract_id`) of the StackerDB the chunk belongs to. `sign()`/`verify()` operate purely over this digest: [2](#0-1) 

On the receiving/validating side, `StackerDBs::validate_received_chunk` resolves the expected signer *per-contract* via `get_slot_signer(smart_contract_id, slot_id)`, then verifies the chunk's signature against that address: [3](#0-2) 

Because the signed digest never includes `smart_contract_id`, if the same signer address is registered to own the same `slot_id` in two *different* StackerDB contracts (e.g., the per-message-lane signer contracts named `signer-<reward-cycle>-<message_id>`, which are derived from the same reward-cycle signer set and commonly preserve the same slot ordering — see the lane-dispatch logic in `libsigner/src/events.rs`), a validly-signed chunk broadcast for contract A will also pass signature verification for contract B at the same slot, because verification only checks "does this address own this slot_id in the target contract," not "was this chunk signed for this contract." [4](#0-3) 

An attacker does not need to forge anything or hold any private key — they only need to relay/replay an authentic chunk (data + signature exactly as broadcast by its legitimate signer) into a different contract's chunk-push/upload path. `process_stacker_db_chunks` / `handle_unsolicited_StackerDBPushChunk` will accept and store it, then rebroadcast it network-wide: [5](#0-4) [6](#0-5) 

### Impact Explanation
This lets an unprivileged remote peer cause a signer's legitimately-signed data intended for one StackerDB "lane"/contract (e.g., a block-response message) to be accepted, stored, and network-wide propagated as if it were data for a *different* contract/lane (e.g., a DKG/vote-message contract) that the same signer also owns a slot in. This is a cross-contract chunk-injection / type-confusion write into StackerDB replicas that is then propagated network-wide — matching the report's "Critical: unauthenticated/unauthorized write to state or StackerDB; network-wide propagation of forged (i.e., mis-scoped) data" category, since downstream consumers (e.g., `libsigner`'s `SignerEvent` decoding, which trusts the contract/lane to determine payload semantics) may misinterpret the payload for the wrong purpose.

### Likelihood Explanation
Likelihood depends on whether slot ownership assignment actually collides on `slot_id` across two live StackerDB contracts for the same signer set — which is plausible given the `signer-<rc>-<message_id>` naming/lane scheme sharing the same underlying reward-cycle signer set — but I could not fully confirm the exact slot-assignment algorithm used per-lane within the tool budget available. The root cause (digest omitting `smart_contract_id`) is proven directly from the code; the practical blast radius depends on this unverified precondition.

### Recommendation
Include the StackerDB's `smart_contract_id` (and ideally a chain/network domain separator) in `SlotMetadata::auth_digest()` so that a signature is cryptographically bound to the specific StackerDB instance it was created for, preventing cross-contract chunk replay even when the same signer address is authorized for the same slot index in multiple StackerDB contracts.

### Proof of Concept
1. Configure/observe two StackerDB contracts, A and B, where address `X` is the assigned signer for `slot_id = 5` in both (plausible for sibling `signer-<rc>-<msg_id>` contracts sharing one reward-cycle signer set).
2. `X` signs and pushes a chunk (`data`, `sig`) for slot 5 in contract A via the normal signer flow; this propagates via `StackerDBPushChunk`.
3. A malicious/observing peer resends the identical `StackerDBChunkData { slot_id: 5, slot_version, sig, data }` unmodified but wrapped in a `StackerDBPushChunkData { contract_id: B, ... }`.
4. The recipient's `validate_received_chunk` calls `get_slot_signer(B, 5)` → `X`, and `slot_metadata.verify(&X)` succeeds because the digest never included `A` or `B` — the chunk is accepted and stored under contract B's slot 5, then rebroadcast network-wide via `process_stacker_db_chunks`.     fn auth_digest(&self) -> Sha512Trunc256Sum {

        hasher.update(self.slot_version.to_be_bytes());

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
