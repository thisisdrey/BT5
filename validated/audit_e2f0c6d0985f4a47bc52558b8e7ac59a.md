### Title
Vault `deposit` mints zero shares for a nonzero underlying payment when the caller passes `min-out u0`, silently transferring the deposited value to existing shareholders - (File: mainnet/contracts/vault/v0-vault-sbtc.clar, mainnet/contracts/vault/v0-vault-stx.clar, mainnet/contracts/vault/v0-vault-usdc.clar, mainnet/contracts/vault/v0-vault-usdh.clar, mainnet/contracts/vault/v0-vault-ststx.clar, mainnet/contracts/vault/v0-vault-ststxbtc.clar)

### Summary
The Zest vault share-math has the same "round-to-zero-shares" root cause flagged in the Napier report (`_stake()` reverting when 0 shares are minted). In Zest, however, the effect is the inverse but equally damaging: `deposit` never checks that the computed share amount (`inkind`) is greater than zero before accepting the underlying and minting `zft`. `redeem` explicitly guards against this (`ERR-OUTPUT-ZERO`), but `deposit` does not.

### Finding Description
Every vault's `deposit` function computes shares via `convert-to-shares-preview`, which does `mul-div-down amount ts ta` once the pool is non-empty, and can round down to `u0` for a small enough `amount` relative to the accrued `total-assets`/`total-supply` ratio: [1](#0-0) 

`deposit` then only checks `amount > u0`, `inkind >= min-out`, and the supply cap - there is no `inkind > u0` guard analogous to the `ERR-OUTPUT-ZERO` check present in `redeem`: [2](#0-1) [3](#0-2) 

If `inkind` resolves to `u0` and the caller supplies `min-out u0` (the natural default when a caller doesn't yet know the correct minimum, or when an integrating contract - such as `supply-collateral-add` in `v0-4-market.clar`, which forwards a caller-supplied `min-shares` straight into `vault-deposit` - passes `u0`), the deposit proceeds: `receive-underlying` pulls the real underlying tokens from the depositor, `ft-mint? zft inkind recipient` mints zero `zft`, and `assets` is increased by the full deposited `amount`: [4](#0-3) 

The net effect is that the depositor's underlying tokens are absorbed into the vault's `assets` accounting and become claimable by *existing* `zft` holders (since `total-assets` rises while `total-supply` does not), while the depositor receives nothing in return.

### Impact Explanation
This is a direct, permanent loss of the depositor's funds with no compensating share issuance - the deposited principal is transferred to other, pre-existing vault shareholders as an involuntary donation. This falls under "theft of user funds at rest" for the depositing principal (their funds are irrecoverably redistributed to others via a share-math rounding bug, not merely frozen).

### Likelihood Explanation
Likelihood grows as a vault's `total-assets`/`total-supply` ratio (share price) increases over time via interest accrual (`accrue`), which is the vault's normal intended behavior — so the window for a small deposit to round to zero shares widens naturally as the vault matures. The only precondition is that the caller (or an integrating contract path such as `supply-collateral-add`) submits `min-out`/`min-shares` as `u0`, which is a common default for a caller who has not pre-computed an exact slippage bound.

### Recommendation
Add an explicit `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` check in every vault's `deposit` function, mirroring the existing check already present in `redeem`, so that a deposit that would mint zero shares reverts instead of silently consuming the depositor's funds.

### Proof of Concept
1. Let a vault reach a state where `total-assets-preview` / `total-supply-preview` > 1 (normal after interest accrual).
2. Depositor calls `deposit` with `amount` small enough that `convert-to-shares-preview(amount)` = `mul-div-down amount ts ta` rounds down to `u0`, and `min-out` = `u0`.
3. `deposit` succeeds: `receive-underlying` pulls `amount` of the real token from the depositor, `ft-mint? zft u0 recipient` mints nothing, and `(var-set assets (+ current-assets amount))` credits the pool.
4. The depositor's `zft` balance is unchanged (0 shares) while their underlying tokens now inflate the redeemable value for all other `zft` holders — a silent, irreversible loss for the depositor. [2](#0-1)
