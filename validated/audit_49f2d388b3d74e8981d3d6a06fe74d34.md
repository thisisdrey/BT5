### Title
StackerDB unsolicited-push handler signs and returns a `StackerDBChunkInv` acknowledging a chunk version before that chunk is actually committed to the database - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` optimistically patches and signs an outgoing `StackerDBChunkInv` reply to claim possession of a pushed chunk's slot version *before* the chunk has been written to the StackerDB, deferring the actual persistence to the asynchronous relayer path. If that deferred write later fails (e.g. a race on the same slot), the signed inventory claim is never corrected, so the node ends up asserting (with its own signature) that it holds data it does not actually store — an authenticated-but-not-stored mismatch analogous to the WJLP report's failure to keep internal accounting synchronized with the real underlying state change.

### Finding Description
In `handle_unsolicited_StackerDBPushChunk`, the node builds a base inventory/NACK via `make_StackerDBChunksInv_or_Nack`, then in the `StackerDBChunkInv` branch calls `validate_received_chunk`, which only checks signature validity, size, staleness, and max-write count — purely in-memory checks that perform no database write. [1](#0-0) 

Immediately after this in-memory validation passes, the code patches the outgoing inventory to declare that the local slot now holds the *incoming* chunk's version, and wakes the sync state machine — all without any call into `StackerDBTx::try_replace_chunk`/`insert_chunk`: [2](#0-1) 

If `send_reply` is set, this patched inventory is then signed and sent straight back to the peer as an authenticated `StackerDBChunkInv` reply, and the function separately returns `(false, true)` so the *actual* storage attempt is deferred to the relayer: [3](#0-2) 

The real, authoritative write only happens later, out-of-band, in `PeerNetwork::process_stacker_db_chunks`, which calls `try_replace_chunk` per chunk and, on failure (including a `StaleChunk` race against another concurrently-received push for the same slot), simply logs and drops the chunk — with no mechanism to retract or correct the inventory claim that was already signed and sent out: [4](#0-3) 

`try_replace_chunk` itself shows exactly the class of race that can invalidate the earlier optimistic claim: it enforces signer verification and monotonic slot-version ordering at commit time, which can reject a chunk that was already optimistically acknowledged moments earlier by a different, concurrently-processed unsolicited push for the same slot: [5](#0-4) 

This breaks the eventually-consistent replication design that StackerDB relies on, where nodes use each other's inventories to decide which peers already have a given chunk version (rarest-first / already-replicated peer selection): [6](#0-5) 

### Impact Explanation
A remote, unprivileged peer can receive a cryptographically signed `StackerDBChunkInv` from a node claiming it possesses a given (contract, slot, version) chunk that the node in fact never persisted (because the deferred write silently failed). Other nodes making replication decisions based on this signed-but-false inventory (e.g. concluding the data has already propagated to this replica and skipping further retries or deprioritizing that chunk in rarest-first scheduling) can cause a legitimate write to be permanently dropped from the network's replicated state, even though the network appears (via signed inventory) to have already converged on it. This is a "non-canonical state served as canonical" condition on a StackerDB replica.

### Likelihood Explanation
This requires no special privileges — any two ordinary StackerDB writers/pushers (or a single writer whose push is retried/re-relayed) sending pushes for the same (contract, slot_id) close together, which is a normal occurrence in the described store-and-forward replication design and fully reachable over the unauthenticated p2p push path (`StacksMessageType::StackerDBPushChunk` handled in `handle_unsolicited_stacks_message`, `stackslib/src/net/unsolicited.rs:547-574`). No attacker key, admin role, or unusual traffic volume is needed.

### Recommendation
Do not sign/send the inventory acknowledgment until the chunk has actually been committed. Either:
1. Perform the `try_replace_chunk` write inline (synchronously) before constructing/signing the `StackerDBChunkInv` reply in `handle_unsolicited_StackerDBPushChunk`, so the ack reflects true DB state, or
2. If storage must remain deferred to the relayer, do not patch/sign the optimistic inventory at push-receipt time; instead, only advertise the new slot version after `process_stacker_db_chunks` confirms the write succeeded, and issue a corrective (or simply accurate) inventory afterward.

### Proof of Concept
1. Node `N` is a StackerDB replica participating with signer key `S` for slot `k`.
2. Peers `A` and `B` are both connected to `N` and, in quick succession (or via re-broadcast/relaying), each send an unsolicited `StackerDBPushChunk` for the same `(contract_id, slot k)`, both validly signed by `S`, but for the same/overlapping `slot_version` (e.g. version `v`).
3. `N`'s event loop processes both pushes through `handle_unsolicited_StackerDBPushChunk` before either has gone through the relayer's `process_stacker_db_chunks`; each call independently patches its own copy of the inventory reply to say "slot k = version v" and signs/sends this reply back to its respective sender.
4. When the relayer later calls `process_stacker_db_chunks` for both, only the first `try_replace_chunk` call succeeds; the second returns `StaleChunk` (per `stackslib/src/net/stackerdb/db.rs:424-429`) and is silently dropped (`stackslib/src/net/relay.rs:2412-2434`).
5. The peer that received the second (dropped) chunk's acknowledgment now holds a validly signed `StackerDBChunkInv` from `N` asserting `N` has stored slot k at version v, even though `N` never actually committed that particular write — an authenticated claim that does not match `N`'s real, persisted StackerDB state.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
