### Title
Attacker can DoS a user's new deposits and borrows by dust-filling their `MAX_TOKENS_PER_USER` slots - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Metronome tracks, per user and per pool, a bounded list of held deposit tokens and debt tokens capped at `MAX_TOKENS_PER_USER = 30`. Any caller can force a token into a victim's list — via `DepositToken.transfer`, `DepositToken.transferFrom`, `DepositToken.deposit(..., onBehalfOf_ = victim)`, or `Pool.seize` — because `_mint`/`_transfer` unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` when the recipient's prior balance is zero. Once the combined list reaches 30, `onlyIfAdditionWillNotReachMaxTokens` reverts with `UserReachedMaxTokens`, blocking the victim from depositing any collateral type they don't already hold and from issuing any synthetic whose `DebtToken` is not already in their list. This is the same bug class as the OpenQ report: filling a fixed-size allowance list with attacker-chosen entries to DoS the legitimate user's ability to fund/use the feature.

### Finding Description [1](#0-0) 

The cap is enforced in `onlyIfAdditionWillNotReachMaxTokens`, used by `addToDepositTokensOfAccount` (Pool.sol:216) and `addToDebtTokensOfAccount` (Pool.sol:204). Those functions are called from `DepositToken`: [2](#0-1) [3](#0-2) 

Attack path:

1. Attacker deposits dust amounts of every listed collateral into `DepositToken` for themselves (or uses `deposit(amount, victim)` directly to mint dust to the victim — `onBehalfOf_` is attacker-chosen, DepositToken.sol:211-237).
2. Each first-time dust balance adds that token to `victim`'s `depositTokensOfAccount` list with no opt-in or whitelist check.
3. When `debtTokensOfAccount.length + depositTokensOfAccount.length == 30`, any subsequent `_mint` or `_transfer` to the victim for a token they don't already hold reverts inside `addToDepositTokensOfAccount`, reverting the whole deposit/transfer/seize transaction.
4. Symmetrically, once at cap, `DebtToken` issuance of a new synthetic reverts via `addToDebtTokensOfAccount`, so the victim cannot open new borrow positions.

The victim can clear a slot by transferring a dusted token back to zero (which triggers `removeFromDepositTokensOfAccount`, DepositToken.sol:523-525), but clearing and depositing are separate transactions, so an attacker watching the mempool can re-dust the cleared slot before the victim's deposit executes, sustaining the DoS.

### Impact Explanation
Liveness/DoS impact identical to the OpenQ finding: the victim cannot fund their position with a new collateral type or open a new borrow while the attacker persists the grief. Existing deposits of already-held tokens, withdrawals, and repayments still work (they don't trigger list additions). On top of blocking deposits, a liquidator account at the cap cannot receive `seize`d tokens for a collateral it doesn't hold (`seize` → `_transfer` → `addToDepositTokensOfAccount` reverts), so the griefing can also transiently block a specific liquidation path until the liquidator uses another account. Impact is temporary freezing of user functionality rather than theft or insolvency.

### Likelihood Explanation
Constrained by the number of distinct collateral types: the attacker can only push one slot per existing `DepositToken`, so the combined cap of 30 is only reachable if the victim already holds several debt/deposit tokens and the pool lists enough collaterals (deployed pools list a limited governor-added set, so the precondition may not be met on every pool). Cost to the attacker is gas plus dust deposits (recoverable), and persistence requires mempool monitoring/front-running, which makes this a medium-probability grief rather than a permanent freeze — matching the medium severity of the source report.

### Recommendation
- Do not auto-add tokens to `depositTokensOfAccount` on inbound `transfer`/`deposit on behalf` unless the recipient already holds that token, or require the recipient to have opted in (e.g., recipient-signed permit or a `pull`-style claim).
- Alternatively, do not revert inside `addToDepositTokensOfAccount` when the cap is hit for unsolicited transfers; instead allow the deposit to mint but skip listing (tracking the balance without counting it toward `depositOf`), so unsolicited dust cannot block the user.

### Proof of Concept
Hardhat-style reproduction (same pattern as `test/Pool.test.ts` "should revert when reach max tokens", Pool.test.ts:1386-1416, but driven by a real attacker transfer rather than impersonating the token):

```ts
// Pool has N listed DepositTokens; victim already holds M debt+deposit tokens,
// with M + N >= MAX_TOKENS_PER_USER (30).
for (const dt of allDepositTokens) {
  // attacker deposits dust on behalf of the victim (attacker-chosen beneficiary)
  await dt.connect(attacker).deposit(1n, victim.address);
  // or: attacker deposits for self then dust-transfers
  // await dt.connect(attacker).transfer(victim.address, 1n);
}

// victim's list is now at cap
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.lengthOf(/* >= 30 minus victim debt tokens */);

// victim tries to deposit a collateral type they don't hold yet
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim clears a slot, attacker re-fills it before the deposit confirms
await allDepositTokens[0].connect(victim).transfer(attacker.address, 1n); // slot freed
// mempool: attacker re-dusts
await allDepositTokens[0].connect(attacker).transfer(victim.address, 1n);
// victim's subsequent deposit of a new token reverts again
```

The test file already demonstrates the revert path at cap (Pool.test.ts:1386-1415); the missing piece in the existing tests is that an unprivileged third party can force entries into the victim's list via `deposit(..., onBehalfOf_)` or dust `transfer`, which `DepositToken.sol:517-519` performs unconditionally.
