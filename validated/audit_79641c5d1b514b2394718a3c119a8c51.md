### Title
Revision validation bypass via `PaginationParameter.PageToken.tree_oid` in `GetTreeEntries` - ([File: internal/gitaly/service/commit/get_tree_entries.go])

### Summary
`sendTreeEntriesUnified` derives `treeRevision` from the attacker-controlled `tree_oid` field of a base64/JSON-encoded page token instead of the RPC's `revision` field, and this value is passed straight into `repo.ReadTree` without ever going through `git.ValidateRevision`. The validation that is enforced on `in.GetRevision()` at request time (`validateGetTreeEntriesRequest`, lines 29-35) is completely bypassed for the token-derived revision.

### Finding Description
`GetTreeEntries` validates the caller-supplied revision once, via `git.ValidateRevision(in.GetRevision())` in `validateGetTreeEntriesRequest` [1](#0-0) . `ValidateRevision` rejects revisions that start with `-` (flag injection), contain NUL, whitespace, `:` or `\` [2](#0-1) .

However, in `sendTreeEntriesUnified`, when a `PaginationParameter.PageToken` is present, `decodePageToken` extracts a `tree_oid` field from the attacker-controlled, unsigned base64/JSON blob and unconditionally overwrites the revision used for tree resolution: [3](#0-2) 

This `treeRevision` is passed directly into `repo.ReadTree(ctx, git.Revision(treeRevision), ...)` [4](#0-3)  — with no call to `git.ValidateRevision` anywhere on this path. `decodePageToken` itself performs no validation beyond base64/JSON decoding and simply falls back to treating the whole raw string as an "OID-style" token on decode failure [5](#0-4) .

Downstream, `ReadTree` concatenates the treeish with a relative path (`rev := treeish + ":" + relativePath`) and passes it to `ResolveRevision`, and separately to `listEntries`, which builds a raw positional argument `fmt.Sprintf("%s:%s", treeish, relativePath)` for `git-ls-tree` [6](#0-5) [7](#0-6) . Because the token-derived value skips the checks that block a leading `-` (flag injection into `git-ls-tree`/`git-rev-parse`), embedded NUL bytes, and other characters, the RPC accepts an "unvetted revision" here that the API explicitly disallows via the normal `revision` field.

### Impact Explanation
This is a validation-bypass / unvetted-refs-accepted bug: the API contract enforces revision syntax constraints on `revision` but the pagination continuation path silently reintroduces an unchecked, attacker-forged value that reaches the same `git` subprocess invocation surface (`ls-tree`, `rev-parse`) that the check was meant to protect. Concretely, this allows a value beginning with `-` (potential git option injection) or containing otherwise-disallowed bytes to reach `git-ls-tree`/`rev-parse` argument construction, which is exactly the class of check the validation function exists to prevent. The exploitation is confined to the repository the attacker already has RPC access to (`in.GetRepository()`); there's no direct route to cross-repository access shown here, so impact is scoped to unexpected git subprocess behavior/argument injection within the caller's own repository context rather than privilege escalation across repos.

### Likelihood Explanation
Fully attacker-reachable and repeatable with only the "unprivileged, own repository" precondition: `PageToken` is never signed, HMAC'd, or bound to server-issued state — it's just base64(JSON) that the client freely constructs, as shown by `decodePageToken`/`encodePageToken` (no MAC, no nonce) [8](#0-7) . Any client calling `GetTreeEntries` with a crafted `PaginationParameter.PageToken` reaches this path on every call, deterministically.

### Recommendation
Apply `git.ValidateRevision` (or an equivalent strict OID-format check, since `tree_oid` is documented as an object ID) to `tokenTreeOID` immediately after `decodePageToken` in `sendTreeEntriesUnified`, rejecting the request if validation fails, before it is ever assigned to `treeRevision` or passed to `repo.ReadTree`.

### Proof of Concept
```go
// internal/gitaly/service/commit/get_tree_entries_test.go (illustrative)
func TestGetTreeEntries_pageTokenBypassesRevisionValidation(t *testing.T) {
    // ... standard repo/client setup ...

    forged := base64.StdEncoding.EncodeToString([]byte(`{"file_name":"a","tree_oid":"--upload-pack=evil"}`))

    stream, err := client.GetTreeEntries(ctx, &gitalypb.GetTreeEntriesRequest{
        Repository: repo,
        Revision:   []byte("HEAD"), // passes ValidateRevision at request time
        Path:       []byte("."),
        PaginationParams: &gitalypb.PaginationParameter{
            PageToken: forged,
            Limit:     1,
        },
    })
    require.NoError(t, err)

    _, err = stream.Recv()
    // Expect: the request is processed using treeRevision == "--upload-pack=evil"
    // (or another leading-dash / disallowed-byte string) without ever hitting
    // git.ValidateRevision, unlike a request that supplied the same string
    // directly via `Revision`, which would be rejected with InvalidArgument
    // at validateGetTreeEntriesRequest.
}
```
The assertion to add: sending the same forged string directly as `Revision` yields `InvalidArgument` from `validateGetTreeEntriesRequest`/`git.ValidateRevision`, while sending it through `PageToken.tree_oid` reaches `repo.ReadTree` unchecked, demonstrating the bypass.

func decodePageToken(token string) (string, string, pageTokenType) {
	var pageToken pageToken

	decodedString, err := base64.StdEncoding.DecodeString(token)
	if err != nil {
		return token, "", pageTokenTypeOID
	}

	if err := json.Unmarshal(decodedString, &pageToken); err != nil {
		return token, "", pageTokenTypeOID
	}

	return pageToken.FileName, pageToken.TreeOID, pageTokenTypeFilename
}
