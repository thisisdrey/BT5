## Analysis

The LootVoteController report describes an *unbounded per-account array that grows on every unprivileged call and is later fully iterated/scanned*, eventually making a reachable function unusable. The closest analog in `Loderfordw/java-tron--003` is the `DelegatedResourceAccountIndexStore` prefix-scan used to answer delegated-resource-index queries, fed by the fee-free `DelegateResourceContract`.

### Title
Unbounded per-owner delegated-resource index entries make `getDelegatedResourceAccountIndex(V2)` queries unboundedly expensive - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
`DelegateResourceContract` (fee = 0) lets any account create a new, permanently-stored index entry for every distinct receiver address it delegates resources to. These entries are looked up by prefix and loaded/sorted entirely in memory by `getWithPrefix`, which backs the `getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` Wallet API. An attacker can grow the number of entries for a single owner address without bound, causing that read path to degrade until the API can no longer serve the request in reasonable time.

### Finding Description
`DelegateResourceProcessor.delegateResource` / `DelegateResourceActuator.delegateResource` create a fresh `DelegatedResourceAccountIndexCapsule` keyed by `V2_FROM_PREFIX + owner + receiver` (and the symmetric `V2_TO_PREFIX` entry) for every unique `(owner, receiver)` pair: [1](#0-0) [2](#0-1) 

`calcFee()` for this contract is `0`, so an attacker pays no protocol fee to create these entries, only ordinary bandwidth/energy cost of the transaction: [3](#0-2) 

Each unique receiver address produces one more RocksDB key under the owner's prefix — this is the "unbounded proxy list" analog: instead of appending to an in-memory protobuf list, java-tron spreads the growth across many DB keys sharing a common prefix, but the read side re-assembles the full set on every query via `prefixQuery`: [4](#0-3) 

This `getWithPrefix` (invoked through `getIndex`/`getV2Index`) is exactly the unbounded loop/scan-and-sort operation, analogous to `_clearExpiredProxies` looping the unbounded `currentUserProxyVoters` array in the original report — both scale linearly (or worse, with the `O(n log n)` sort here) with attacker-controlled growth of a per-account collection that has no cap.

### Impact Explanation
`getIndex`/`getV2Index` back the Wallet query methods `getDelegatedResourceAccountIndex` / `getDelegatedResourceAccountIndexV2`, which are exposed through the node's gRPC/HTTP query surface. As the number of distinct receivers an attacker delegates to from one owner address grows (bounded only by the attacker's willingness to pay ordinary transaction bandwidth/energy, since the actuator fee is zero), each subsequent query for that owner's delegated-resource index requires scanning and in-memory sorting of an ever-larger key set. This can make the corresponding API call the node "can no longer serve" in reasonable time for that address, and repeated cheap delegate transactions to many synthetic receivers allow the attacker to keep inflating the scan cost indefinitely — a resource-exhaustion / DoS condition on a specific, unprivileged, reachable query path.

### Likelihood Explanation
Reachability is straightforward: any account holding a small amount of `FrozenV2` bandwidth/energy balance can repeatedly submit `DelegateResourceContract` transactions to a large number of freshly generated, distinct receiver addresses, each transaction being an ordinary signed transaction paying only bandwidth/energy, not extra protocol fee (`calcFee() == 0`). No special privilege (SR, witness, committee) is required. The main constraint is standard per-transaction bandwidth/energy cost, which is a normal, bounded cost per delegate — i.e., cheap in aggregate over time, matching the "Medium" severity classification of the original report (gas/energy cost grows with attacker activity but does not require abnormal privileges).

### Recommendation
- Cap the number of distinct delegation-index entries (receivers/froms) that can be tracked per owner address, or require the `prefixQuery`-based lookups to be paginated rather than fully materialized/sorted in one call.
- Consider charging a non-zero fee for `DelegateResourceContract`/`UnDelegateResourceContract` proportional to the number of distinct counter-parties, to disincentivize cheap creation of many index entries.
- Add a maximum on `prefixQuery` result set sizes returned to a single Wallet API call, with an explicit error/pagination cursor when the limit is exceeded, instead of unconditionally loading and sorting the entire result set.

### Proof of Concept
Conceptual PoC (not executed, following report methodology): an attacker with minimal `FrozenV2` bandwidth balance repeatedly signs `DelegateResourceContract` transactions from one owner address to N freshly generated receiver addresses (`N` in the thousands), each creating index entries under `V2_FROM_PREFIX`/`V2_TO_PREFIX` via `DelegateResourceProcessor.delegateResource`/`DelegatedResourceAccountIndexStore` (no protocol fee, per [3](#0-2) ). A subsequent call to the Wallet `getDelegatedResourceAccountIndexV2` API for that owner then triggers `getWithPrefix`, which performs `prefixQuery` over all N entries and sorts them in memory [4](#0-3) , with cost growing linearly (plus sort overhead) in `N`, degrading that API's latency/availability as `N` increases without bound.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
