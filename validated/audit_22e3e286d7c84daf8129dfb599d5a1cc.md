Confirmed: `try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs` validates `slot_desc.verify(&slot_validation.signer)` where `verify`/`auth_digest` (in `libstackerdb/src/libstackerdb.rs`) sign/hash only `slot_id`, `slot_version`, and `data_hash` — the `smart_contract` (StackerDB contract identifier) passed into `try_replace_chunk` is never mixed into the signed digest. Since the signer-slot assignment is shared across all `signers-N-X` contracts for a reward cycle (`stackerdb-get-signer-slots-page` in `stackslib/src/chainstate/stacks/boot/signers.clar`), a chunk validly signed for one contract (e.g. BlockResponse `signers-0-1`) is also a valid signature for the same slot in a sibling contract (e.g. StateMachineUpdate `signers-0-2`, BlockPreCommit `signers-0-3`), since both look up the same `slot_validation.signer` for that slot index and the digest doesn't distinguish them.

### Title
Cross-contract StackerDB chunk signature replay due to missing contract-id binding in signed digest - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` in `libstackerdb/src/libstackerdb.rs` computes the signed digest from only `slot_id`, `slot_version`, and `data_hash`, omitting the StackerDB's `smart_contract` identifier. Because the same signer address occupies the same numeric slot across all `signers-<reward_cycle_mod2>-<message_id>` StackerDB contracts for a reward cycle (`stackerdb-get-signer-slots-page` in `stackslib/src/chainstate/stacks/boot/signers.clar`), a signature that is valid for one contract's slot is also valid for the identically-indexed slot in a sibling contract. An unprivileged remote actor who observes a broadcast/stored chunk (via `StackerDBPushChunk` gossip or the public GET chunk RPC) can repost the exact same `(slot_id, slot_version, sig, data)` tuple to a different contract's `/v2/stackerdb/:addr/:contract/chunks` endpoint, or via P2P `StackerDBChunkInv`/push paths, and have it accepted as an authentic write there.

### Finding Description
`SlotMetadata::auth_digest()` (`libstackerdb/src/libstackerdb.rs:159-166`) hashes only `slot_id`, `slot_version`, and `data_hash`:
```
hasher.update(self.slot_id.to_be_bytes());
hasher.update(self.slot_version.to_be_bytes());
hasher.update(self.data_hash.0);
```
There is no domain separator for the target `QualifiedContractIdentifier`. `SlotMetadata::verify()` recovers the public key from this digest and compares its `Hash160` to the caller-supplied `principal` — it has no notion of which StackerDB contract the chunk is destined for.

The actual authorization check lives in `StackerDBTx::try_replace_chunk()` (`stackslib/src/net/stackerdb/db.rs:400-438`) and `PeerNetwork::validate_received_chunk()` (`stackslib/src/net/stackerdb/mod.rs:649-718`): both fetch the *expected* signer address for `(smart_contract, slot_id)` and then call `slot_desc.verify(&signer)`. The `smart_contract` parameter is used only to select which signer address to expect — it is never incorporated into what's actually being authenticated by the signature.

For the three Nakamoto signer-message StackerDB contracts (`signers-<n>-1` BlockResponse, `signers-<n>-2` StateMachineUpdate, `signers-<n>-3` BlockPreCommit — see `MessageSlotID` in `libsigner/src/v0/messages.rs:68-78` and `NakamotoSigners::make_signers_db_contract_id` in `stackslib/src/chainstate/nakamoto/signer_set.rs:1060-1073`), the underlying signer list and slot indices for a given reward cycle are identical: `stackerdb-get-signer-slots-page` (`stackslib/src/chainstate/stacks/boot/signers.clar:40-43`) returns the *same* `stackerdb-signer-slots-0/1` list to every `signers-<n>-X` contract, and `signers_db_get_slots` test (`stackslib/src/chainstate/stacks/boot/signers_tests.rs:277-341`) confirms all three contracts assign identical slot indices per signer. Consequently, signer S's slot index (and thus the expected signer address for that slot) is the same in all three contracts for that reward cycle.

This means a chunk `(slot_id=k, slot_version=v, sig, data)` that signer S validly produced and had stored/broadcast for contract `signers-0-1` will also pass `verify()` against contract `signers-0-2`'s or `signers-0-3`'s expected signer for slot `k`, because the signature never bound itself to the contract. An attacker who has observed such a chunk (broadcast network-wide via `PeerNetwork::process_stacker_db_chunks`, `stackslib/src/net/relay.rs:2385-2467`, or fetched via the public chunk-read RPC) can POST it unauthenticated to `/v2/stackerdb/<addr>/signers-0-2/chunks` (handled by `RPCPostStackerDBChunkRequestHandler` in `stackslib/src/net/api/poststackerdbchunk.rs`, which requires no caller authentication) as long as the target slot's stored version is below `slot_version`. If accepted, `try_replace_chunk` stores it and the node re-broadcasts it via `process_stacker_db_chunks`, propagating attacker-injected (replayed, contract-mismatched) data as canonical StackerDB state network-wide.

### Impact Explanation
This is an unauthenticated/unauthorized write into a StackerDB replica that was never intended for that contract, and the accepted chunk is then broadcast network-wide as legitimate (`process_stacker_db_chunks` at `stackslib/src/net/relay.rs:2445-2452`), i.e., forged/misattributed data propagation across the network. Downstream signer tooling (`libsigner/src/events.rs:722-824`, `signer_message_payload_matches_lane`) provides only a weak, best-effort filter based on a leading type-prefix byte inside the payload; it is not a security boundary for the StackerDB storage/replication layer itself, and other consumers reading the contract's chunks via the public RPC would see attacker-replayed content as the latest, "signed" state for that slot in that contract. This matches the Critical bucket: "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data."

### Likelihood Explanation
Requires only: (1) observing one legitimately signed and broadcast/stored chunk from any signer for a sibling contract (trivially available — chunks are gossiped and independently retrievable via the public GET-chunk RPC), and (2) issuing a normal, unauthenticated HTTP POST to a different StackerDB contract endpoint on any node. No secret key, node-operator privilege, or protocol race is required, and the write-version constraint (`slot_version` must exceed the target slot's current version) is easy to satisfy since sibling contracts' slot versions advance independently and are often behind.

### Recommendation
Bind the signed digest to the target StackerDB contract by including the `QualifiedContractIdentifier` (and, ideally, the intended `MessageSlotID`/lane) in `SlotMetadata::auth_digest()`, and thread the contract identifier through `SlotMetadata::sign()`/`verify()` and the `StackerDBChunkData` (de)serialization so that a signature produced for one StackerDB contract cannot be replayed against another. This is a wire/data-format change and needs coordinated versioning across `libstackerdb`, `libsigner`, and all callers that sign/verify `SlotMetadata`.

### Proof of Concept
1. Let signer S be authorized at slot `k` in both `signers-0-1` (BlockResponse) and `signers-0-2` (StateMachineUpdate) for the current reward cycle (guaranteed by the shared `stackerdb-get-signer-slots-page` list).
2. Observe/capture a legitimately signed chunk `StackerDBChunkData { slot_id: k, slot_version: v, sig, data }` that S posted to `signers-0-1` (e.g., via P2P `StackerDBPushChunk` gossip, or `GET /v2/stackerdb/<addr>/signers-0-1/<slot>`).
3. As an unrelated, unauthenticated actor, `POST` the identical JSON body to `/v2/stackerdb/<addr>/signers-0-2/chunks` (per `RPCPostStackerDBChunkRequestHandler::try_parse_request` in `stackslib/src/net/api/poststackerdbchunk.rs`, no signature over the contract path is checked).
4. `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:400`) looks up `signers-0-2`'s slot `k` signer (= S, per shared slot list), calls `slot_desc.verify(&S)`, which succeeds because `auth_digest()` never included the contract id — the chunk (originally meant for `signers-0-1`) is stored under `signers-0-2` and re-broadcast as legitimate state for that contract.
