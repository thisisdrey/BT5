### Title
Unauthenticated attachment-hash substitution in Atlas attachment download resolves/stores wrong content - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts any decoded `Attachment` from a peer's `GET /v2/attachments/{content_hash}` response without verifying that the returned attachment's actual hash matches the requested `content_hash`. A malicious peer can respond to a request for hash `H_A` with a differently-hashed attachment `H_B`, causing the node to resolve and store content under `H_B` (against instances that committed to `H_B`, not `H_A`) while the batch for `H_A` remains unresolved, gets retried, and is eventually dropped.

### Finding Description
The request/response flow is: `AttachmentRequest { content_hash: H_A, .. }` is sent via `make_request_type` (stackslib/src/net/atlas/download.rs:1110-1118) to `GET /v2/attachments/{H_A}`. On the server side, `RPCGetAttachmentRequestHandler::try_handle_request` (stackslib/src/net/api/getattachment.rs:93-130) looks up the attachment by the hash in the URL and returns `GetAttachmentResponse { attachment }` as JSON — but this is the server's *legitimate* behavior; the vulnerability is on the client (requester) side, which trusts an arbitrary response body regardless of source, since a "malicious peer" here is any peer serving a crafted HTTP response (not necessarily an honest atlas peer, but any endpoint the connection is routed to, or a peer returning a stale/different attachment for the requested URL).

The client decodes the response via `decode_atlas_get_attachment` (stackslib/src/net/api/getattachment.rs:159-165), which merely does `serde_json::from_value` into `GetAttachmentResponse` — no hash field is present in the response payload to check against, and no post-decode validation is performed.

Back in `extend_with_attachments` (stackslib/src/net/atlas/download.rs:530-558), the loop iterates `results.succeeded` keyed by `AttachmentRequest`, whose `Hash`/`Eq` are defined solely on `content_hash` (lines 1082-1086, 1065). At line 548, `self.attachments.insert(response.attachment)` is called — the `request.content_hash` is never read or compared to `response.attachment.hash()`. The `Attachment` is inserted into a `HashSet<Attachment>` keyed by its own content (its hash), so a substituted attachment with hash `H_B` is silently accepted as if it fulfilled the request for `H_A`.

In `AttachmentsDownloader::run` (stackslib/src/net/atlas/download.rs:153-169), when the batch reaches `Done`, the code iterates `context.attachments.drain()` and, for each attachment, calls `find_all_attachment_instances(&attachment.hash())` (line 157) and `context.attachments_batch.resolve_attachment(&attachment.hash())` (line 168) — both using the *actual* hash of the returned bytes, `H_B`, not `H_A`. This means:
- The batch's expectation for `H_A` is never marked resolved, since `resolve_attachment` is called with `H_B`.
- Instances that legitimately reference `H_B` (from some other, unrelated commitment) will be resolved and have `insert_instantiated_attachment(&attachment)` called on their behalf — but this only happens correctly if `H_B` is a real hash from a genuine other attachment; the attacker must know or guess a valid `H_B` payload, in which case this is effectively "confused" resolution rather than store of forged content under a wrong hash (since `Attachment::hash()` presumably computes the hash from content, the storage key used will always be correct for whatever bytes were stored — i.e., `insert_instantiated_attachment` stores by the attachment's actual hash). The exhaustion effect is that the batch for `H_A` never resolves and retries/drops (`bump_retry_count`, lines 188-199), and storage may absorb content that no instance in *this* batch asked for (though it would only satisfy instances that separately committed to `H_B` elsewhere, since `find_all_attachment_instances` queries by `H_B` and only returns instances already stored with that content_hash in the atlasdb).

### Impact Explanation
This causes batches to never resolve to their true requested hash and get bumped/retried/dropped after `max_attachment_retry_count`, which is a denial-of-resolution for legitimate `AttachmentInstance`s tied to `H_A`. However, `insert_instantiated_attachment` stores content keyed by its actual computed hash (`attachment.hash()`), so no forged content is stored "under" a hash it doesn't match — the storage-key/content invariant for the Atlas DB itself is not violated. The only instances affected are those already existing in the local `atlasdb` with `content_hash = H_B`; an attacker cannot arbitrarily inject H_B content unless they can also produce a matching payload, and even then, only instances that already committed to `H_B` on-chain (via a real Clarity transaction referencing that hash) would consume it — this is normal Atlas behavior for legitimate attachments, not attacker-controlled forgery. The concrete negative effect is limited to starving `H_A`'s instances of resolution (repeated retries, eventual batch drop), which is a resource-mistargeting/denial-of-service on Atlas attachment resolution for the specific instance, not a consensus-state or canonical-data forgery, and does not meet the "serving non-canonical state as canonical" or "attachment/BNS mismatch" bar since no mismatched content is ever served as if it matched `H_A` to any consumer — it is simply never resolved.

### Likelihood Explanation
Any peer that can respond to the outbound HTTP-based attachment-download request (reachable via `get_outbound_sync_peers`/`get_data_url`) can trivially return an unrelated attachment payload in the JSON body instead of the one matching the requested hash. This requires no special privilege, only running a peer/HTTP endpoint that the node connects to for Atlas downloads.

### Recommendation
In `extend_with_attachments` (stackslib/src/net/atlas/download.rs:547-549), before inserting into `self.attachments`, verify `response.attachment.hash() == request.content_hash`; if it doesn't match, treat it as a failed request (`report.bump_failed_requests()`) rather than accepting the substituted attachment.

        preamble: HttpRequestPreamble,
        _contents: HttpRequestContents,

        let attachment_hash = self

            .ok_or(NetError::SendError("Missing `attachment_hash`".into()))?;

        let attachment_res = node.with_node_state(
            |network, _sortdb, _chainstate, _mempool, _rpc_args| match network
                .get_atlasdb()
                .find_attachment(&attachment_hash)
            {
                Ok(Some(attachment)) => Ok(GetAttachmentResponse { attachment }),
                _ => {
                    let msg = "Unable to find attachment".to_string();
                    warn!("{msg}");
                    Err(StacksHttpResponse::new_error(
                        &preamble,
                        &HttpNotFound::new(msg),
                    ))
                }
            },
        );
        let attachment = match attachment_res {
            Ok(attachment) => attachment,
            Err(response) => {
                return response.try_into_contents().map_err(NetError::from);
            }
        };

        let preamble = HttpResponsePreamble::ok_json(&preamble);
        let body = HttpResponseContents::try_from_json(&attachment)?;
        Ok((preamble, body))
    }
