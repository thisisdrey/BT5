### Title
Dust deposit griefing fills `depositTokensOfAccount`/`debtTokensOfAccount` up to `MAX_TOKENS_PER_USER`, reverting victim deposits, borrows and inbound transfers - (File: contracts/Pool.sol)

### Summary
The Tor bug class (attacker-chosen identifiers degrading a data structure) maps to Metronome's per-account enumerable sets. `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` push tokens into `MappedEnumerableSet` arrays keyed by account, capped by `MAX_TOKENS_PER_USER` via `onlyIfAdditionWillNotReachMaxTokens` (Pool.sol:143-148). Because `DepositToken.deposit(amount_, onBehalfOf_)` accepts an arbitrary beneficiary and `_transfer`/`_mint` auto-register the token to the recipient, any unprivileged attacker can permanently drive a victim's combined token count to the cap using dust amounts. Once the cap is reached, every path that adds a token to the victim's set reverts with `UserReachedMaxTokens`: `deposit`, `DebtToken` issuance, `transfer`/`transferFrom`/`seize` inbound to the victim.

### Finding Description
- `DepositToken.deposit` mints to `onBehalfOf_` chosen by the caller (DepositToken.sol:211-237). `_mint` calls `pool.addToDepositTokensOfAccount(account_)` when the recipient's balance was zero (DepositToken.sol:485-488). `_transfer` does the same for recipients (DepositToken.sol:517-520), and `DebtToken` issuance calls `addToDebtTokensOfAccount`.
- `onlyIfAdditionWillNotReachMaxTokens` reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` (Pool.sol:143-146). Because the set add is called inside `_mint`/`_transfer`, the revert propagates and the whole deposit/transfer/issue transaction fails.
- Attacker sequence: for each deposit token i in `pool.getDepositTokens()`, call `deposit(1 wei-equivalent, victim)` — or cheaper, deposit once and dust-`transfer` to the victim (transfers register too). Repeat until the victim's combined list hits the cap (test shows the cap counts debt+deposit slots together, test/Pool.test.ts:1386-1416).
- Result: victim's `deposit()` reverts, `DebtToken.issue/mint` reverts (it calls `addToDebtTokensOfAccount` when balance goes 0→non-zero), and any msdTOKEN transfer to the victim reverts. `Pool.liquidate`'s `seize` to a liquidator at the cap also reverts, letting an attacker pre-fill their own account? — no, liquidator controls their own address; the victim's-side block is the relevant DoS.

### Impact Explanation
Temporary freezing of protocol interaction: while the victim's slots are saturated they cannot add collateral or open new debt positions. Concretely, a victim approaching liquidation cannot top up collateral via `deposit` (the tx reverts in `addToDepositTokensOfAccount`), removing their main mitigation path and exposing them to forced liquidation. Recovery requires the victim to fully zero out each dust balance (transfers only remove a token when the sender's balance hits zero, DepositToken.sol:522-525), costing one transaction per filler token and racing further dust.

### Likelihood Explanation
Fully unprivileged: `deposit` and `transfer` are public, `onBehalfOf_`/`to_` are attacker-chosen, no role, oracle, or privileged actor is needed, and no pause flag blocks it. Cost is bounded by the number of deposit/debt tokens × dust underlying plus gas — the cap is finite (MAX_TOKENS_PER_USER) so the attack is cheap and repeatable against any target, and re-appliable after recovery.

### Recommendation
Make per-account list registration non-reverting or opt-in: e.g., don't auto-add on `transfer`/`deposit` for recipients (require explicit action), or track collateral differently. Alternatively, exclude tokens added below a meaningful USD dust threshold, or let `addToDepositTokensOfAccount` silently skip at cap instead of reverting the whole deposit/transfer.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";

contract MaxTokensGriefingTest is Test {
    // Deployed-fork setup: Pool, DepositTokens, DebtTokens as in repo test suite
    IPool pool;
    address victim = address(0xBEEF);
    address attacker = address(0xA77);

    function test_dustFillBlocksVictimDeposits() public {
        uint256 max = pool.MAX_TOKENS_PER_USER();
        address[] memory dts = pool.getDepositTokens();

        // Attacker dust-deposits each collateral on behalf of victim
        for (uint256 i; i < dts.length; i++) {
            IDepositToken dt = IDepositToken(dts[i]);
            IERC20 underlying = dt.underlying();
            deal(address(underlying), attacker, 1);
            vm.startPrank(attacker);
            underlying.approve(address(dt), 1);
            dt.deposit(1, victim); // onBehalfOf = victim
            vm.stopPrank();
            if (pool.debtTokensOfAccountLength(victim) +
                pool.getDepositTokensOfAccount(victim).length >= max) break;
        }

        // Victim's own deposit now reverts
        IDepositToken dt0 = IDepositToken(dts[0]);
        deal(address(dt0.underlying()), victim, 1e18);
        vm.startPrank(victim);
        dt0.underlying().approve(address(dt0), 1e18);
        vm.expectRevert(UserReachedMaxTokens.selector);
        dt0.deposit(1e18, victim);
        vm.stopPrank();
    }
}
```
Expected result: the attacker fills the victim's combined token set to `MAX_TOKENS_PER_USER` with dust deposits; every subsequent victim deposit, borrow (`issue`), and inbound msdTOKEN transfer reverts until the victim manually zeroes out each dust balance.
