### Title
Exchange creator can front-run `ExchangeTransactionContract` swaps via `ExchangeInjectContract`/`ExchangeWithdrawContract` to capture value from users with loose `expected` slippage protection - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java, actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java, actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
Java-tron's Bancor-style TRC10 exchange (`Exchange`/`ExchangeV2`) lets a swap sender (`ExchangeTransactionContract`) protect against price movement only with a single `expected` (minimum-output) field, analogous to `debtOutMin` in the reported `SwapFacility.swapExactCollateralForDebt()` bug. The pool's reserve ratio, which fully determines the swap price, can unilaterally be moved by the exchange's creator address at any time via `ExchangeInjectContract`/`ExchangeWithdrawContract`. A malicious/compromised creator can observe a pending `ExchangeTransactionContract` in the mempool and front-run it with an inject/withdraw transaction that skews the reserve ratio immediately before the victim's swap executes, extracting most of the value from users who did not set a tight `expected` value (e.g., left it at 1, mirroring the report's "debtOutMin = 0" scenario).

### Finding Description
`ExchangeTransactionActuator.execute()`/`doValidate()` computes the swap output via `ExchangeCapsule.transaction()`, which is purely a function of the current `firstTokenBalance`/`secondTokenBalance` pool reserves: [1](#0-0) 

The only protection a swap sender has against an unfavorable price at execution time is the `expected` field, checked in validate: [2](#0-1) 

The exchange's `firstTokenBalance`/`secondTokenBalance` reserves can be changed at will by the exchange's creator (an ordinary account, not a witness/committee), via `ExchangeInjectContract`: [3](#0-2) 
and `ExchangeWithdrawContract`: [4](#0-3) 
both gated only by an "is creator" check: [5](#0-4) 

Because these are ordinary broadcastable transactions from a single signing key, the creator can watch the mempool for a victim's `ExchangeTransactionContract`, and submit an `ExchangeInjectContract`/`ExchangeWithdrawContract` with a higher energy/bandwidth priority (or via block-producer collusion) to shift the reserve ratio just before the victim's transaction is packed, exactly mirroring the report's "unvigilant user + owner front-run of a rate-affecting setter" pattern. If the victim set a loose `expected` (the on-chain analog of `debtOutMin`), their swap will still pass the `anotherTokenQuant < tokenExpected` check in `doValidate()` but execute at the manipulated price, allowing the creator to capture a large fraction of the swapped value back into the pool (and subsequently withdraw it).

### Impact Explanation
A successful front-run lets the exchange creator extract collateral/value from ordinary swap senders who rely on default or loosely-set `expected` values (the exact incentive structure the external report describes: value capture "up to 100%" in the worst case, bounded here by how far the creator can move the reserve ratio with their own token/TRX holdings and by `EXCHANGE_BALANCE_LIMIT`). This constitutes concrete unauthorized value transfer between accounts within the chain state (an account operation / theft-of-funds primitive), impacting ordinary TRC10 exchange users who transact through the wallet APIs feeding `ExchangeTransactionContract`.

### Likelihood Explanation
Likelihood is bounded by the need to observe and front-run a pending transaction in the mempool/next block, and by users typically using UI-provided defaults for `expected` — the same "seldom vigilant user" assumption underpinning the original report. Any account that created an exchange pool (a permissionless, unprivileged action via `ExchangeCreateContract`) can carry out this attack against counterparties trading against its own pool, with no special chain privilege required, making it broadly reachable by unprivileged accounts rather than requiring SR/witness collusion.

### Recommendation
- Encourage/enforce tighter `expected` bounds relative to current quoted price at the API/wallet layer that constructs `ExchangeTransactionContract`.
- Consider adding a maximum single-transaction reserve-ratio delta for `ExchangeInjectContract`/`ExchangeWithdrawContract`, or a cooldown/timelock between reserve-changing operations and swaps, to reduce the profitability of using inject/withdraw as a front-running lever.
- Consider exposing a "max acceptable price impact" parameter in addition to `expected` so unsophisticated senders get better default protection.

### Proof of Concept
1. Creator opens an exchange pool for tokens A/TRX with reserves `firstTokenBalance`, `secondTokenBalance` via `ExchangeCreateContract`.
2. Victim broadcasts `ExchangeTransactionContract` selling TRX for token A with `expected = 1` (loose slippage bound), relying on the currently displayed price.
3. Creator observes the pending transaction and submits `ExchangeWithdrawContract` (or `ExchangeInjectContract`) that sharply changes `firstTokenBalance`/`secondTokenBalance` — see `ExchangeWithdrawActuator.execute()` mutating `exchangeCapsule.setBalance(...)` [6](#0-5)  — before the victim's transaction is included.
4. Victim's swap still satisfies `anotherTokenQuant < tokenExpected` (since `expected` is loose) in `ExchangeTransactionActuator.doValidate()` [2](#0-1)  and executes at the now-unfavorable price, transferring most of the value to the pool, which the creator can subsequently reclaim via another `ExchangeWithdrawContract`.
