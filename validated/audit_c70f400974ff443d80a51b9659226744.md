### Title
Replay-Window Check-Then-Act Race Allows Duplicate Packet Processing Bypass - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the replay-window "already seen" verification into two separate, individually-locked steps (`window.Check` then, after unlocking, the actual AEAD decrypt, then a second lock for `window.Update`). This mirrors the reported Vault bug class: a state-mutating check (`adjustmentsMade[_user][_nonce]++`) is decoupled from the actual guard condition, letting an attacker exploit the gap between "check passed" and "state committed" to process the same message counter more than once.

### Finding Description
`Decrypt` and `VerifyRelay` in `connection_state.go` are structured as:
1. Lock, call `cs.window.Check(l, messageCounter)`, unlock.
2. If `true`, perform the actual AEAD `DecryptDanger` outside the lock.
3. Lock again, call `cs.window.Update(l, messageCounter)`, unlock. [1](#0-0) 

`Bits.Check` only *reads* window state to decide whether counter `i` looks unseen; it does not mark it as seen — that only happens in `Bits.Update`, guarded by a separate, later lock acquisition. [2](#0-1) 

Because `decryptLock` is released between `Check` and the AEAD decrypt call, and packets for the same tunnel/`ConnectionState` can be delivered to independent reader goroutines (Nebula supports `routines > 1`, each with its own UDP reader queue calling `readOutsidePackets`/`Decrypt` concurrently), two copies of the same captured ciphertext (a trivial UDP replay — no valid certificate or handshake participation required) delivered at close to the same time can both pass `Check` before either calls `Update`. Both goroutines then proceed to decrypt and hand the plaintext to `handleOutsideMessagePacket`/`handleOutsideRelayPacket`, i.e., the packet is accepted and processed twice despite the replay window's purpose of rejecting exactly this. [3](#0-2) [4](#0-3) 

This is analogous to the Vault report's root cause: a counter/adjustment check (`adjustmentsMade[_user][_nonce]++` then a condition using stale/aggregate state) that can be satisfied without the intended per-event effect actually being committed atomically, letting an attacker's duplicate/past event slip through the guard.

### Impact Explanation
Successful exploitation causes on-wire traffic replay: a captured legitimate encrypted packet (data-plane message, LightHouse update, or relay frame) is decrypted and delivered to the application/routing layer more than once, defeating the anti-replay guarantee documented for the replay window and metrics (`dupeCounter`, `outOfWindowCounter`). Depending on payload this can cause duplicate delivery of routing/LightHouse state or duplicate tun writes — a concrete replay bypass of a core security control, not merely a metrics inaccuracy.

### Likelihood Explanation
Exploitation requires only capturing one legitimate ciphertext packet on the wire (no CA-signed certificate or handshake participation needed) and sending two copies of it at close to the same time so they land on two different reader queues (`f.routines > 1`, which is a documented, supportable configuration and the default recommendation for higher throughput). The race window is only the interval between the `Check` unlock and decrypt completion, but as a network-timing race it is realistically triggerable by an attacker who controls packet delivery timing, especially under load.

### Recommendation
Perform the "is this counter unseen" check and the "mark as seen" commit under a single, uninterrupted critical section (or use an atomic check-and-set primitive) so that no other goroutine can observe the pre-update window state for the same counter while a decrypt is in flight. Concretely, hold `decryptLock` across the full `Check → Decrypt → Update` sequence for a given `ConnectionState`, or replace the two-phase Check/Update with a single atomic "reserve slot" operation performed before decrypting, with rollback if decrypt authentication fails.

### Proof of Concept
1. Configure Nebula with `routines > 1` (multiple UDP reader queues) so that packets for the same tunnel can be processed by two goroutines concurrently, per `f.run()`/`f.listenOut`. [5](#0-4) 
2. Establish a tunnel and capture one legitimate data-plane packet (ciphertext) with message counter `N`.
3. Immediately re-inject two copies of the exact same captured packet (e.g., via two sockets/threads sending to the listener at nearly the same instant), so the OS/kernel dispatches them to two different reader routines.
4. Both routines call `hostinfo.ConnectionState.Decrypt(f.l, N, ...)`; both see `cs.window.Check(l, N) == true` before either calls `cs.window.Update(l, N)`, because the lock is released between the two calls. [6](#0-5) 
5. Both goroutines successfully decrypt and process the packet, resulting in the same message being handled twice — the replay window has failed to reject the duplicate.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
