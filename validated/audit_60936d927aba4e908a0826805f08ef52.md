### Title
Stale Partition Assignments Persist After Repository Deletion, Causing Unrelated Repositories to Be Silently Co-Located in a Shared Partition - (File: internal/gitaly/storage/storagemgr/partition_assigner.go)

### Summary
Gitaly assigns every repository a `PartitionID` the first time it is accessed, and this `(relativePath -> PartitionID)` mapping is stored forever in the partition assignment table. When a repository is deleted, this mapping is never invalidated. If the same relative path is later reused by an unrelated repository (e.g. after a project delete/recreate, or a maliciously-chosen relative path), the new repository is silently placed into the old, still-populated partition without re-evaluating alternate/ownership relationships — mirroring the reported bug class where a reused identifier's stale associated state is trusted instead of being reset.

### Finding Description
`partitionAssigner.getPartitionIDRecursive` first consults the persistent key-value mapping before doing anything else: [1](#0-0) 

If an entry already exists for `relativePath`, it is returned immediately (line 236, 255-264) — the alternates-based logic in `assignPartitionID`/`getAlternatePartitionID` is completely bypassed: [2](#0-1) 

The mapping is written once per relative path via `setPartitionID` and is keyed purely by the relative-path string, with no repository identity, generation, or lineage check: [3](#0-2) 

Critically, Gitaly's own documentation acknowledges that this mapping is never cleaned up on deletion: [4](#0-3) 

Partitions are Gitaly's transactional/storage isolation boundary — "Each partition is essentially its own mini-database... and store[s] one or more repositories and their associated key-value entries," and repositories are deliberately co-located in the same partition only when they are genuinely related (object pool + its fork members): [5](#0-4) 

Because the assignment lookup at line 236 is unconditionally trusted, once a relative path P has ever been assigned to partition X, any later repository (fork, pool, or an unrelated one that happens to reuse P after deletion — for example a re-created project with the same namespace/path, or forks whose pool was deleted without unlinking members, per `DeleteObjectPool`'s explicit lack of member safety checks) is forced into partition X, regardless of whether it has any real relationship to the other repositories still assigned there: [6](#0-5) 

This is the direct structural analog of the reported bug: a reusable identifier (loanId ↔ relativePath) whose per-identifier local state (rewardIndex ↔ PartitionID mapping) is never reset on deletion, so a brand-new, logically distinct entity silently inherits state that was only ever valid for the deleted one.

### Impact Explanation
When an unrelated (or malicious) repository is forced to reuse a stale partition assignment, it becomes co-resident with whatever repositories are still bound to that partition (e.g. a live object pool and its member forks). Because a partition is a single write-ahead log and a single embedded KV keyspace shared by all of its member repositories, this:
- Breaks the storage isolation the partitioning model is designed to provide between unrelated repositories/tenants.
- Creates unnecessary transaction-ordering coupling and lock/serialization contention between the newly-created repository and pre-existing, unrelated repositories sharing the partition — a resource-exhaustion / availability risk (DoS of the partition's `TransactionManager`) for repositories that have nothing to do with each other.
- Can silently violate the invariant enforced elsewhere in the code (`ErrRepositoriesAreInDifferentPartitions`) that only genuinely alternate-linked repositories should ever share a partition, undermining assumptions made by other components that rely on partition membership implying an alternates relationship.

### Likelihood Explanation
Relative-path reuse after deletion is a normal, expected occurrence in Gitaly (explicitly tested in `transaction_manager_repo_test.go`'s "create repository again after deletion" case), and object pools can be deleted while members remain linked, since `DeleteObjectPool` performs no safety checks on existing members. Because the assignment table is never pruned, any of these ordinary operational sequences reach the vulnerable code path without requiring privileged access — an ordinary user's repository create/fork/delete/recreate sequence is sufficient to trigger it.

### Recommendation
Remove or invalidate the `partitionAssignmentTable` entry for a relative path when its repository is deleted (mirroring the reporter's fix of resetting stale per-identifier state on deletion), or alternatively validate at assignment-lookup time that the previously-assigned partition still legitimately corresponds to the repository (or its alternate lineage) currently on disk before trusting the cached `PartitionID`.

### Proof of Concept
1. Create repository/object pool `P` at relative path `R`; link fork `F` to `P` as an alternate so that both `P` and `F` are assigned to partition `X` (`getAlternatePartitionID`, `internal/gitaly/storage/storagemgr/partition_assigner.go:317-359`).
2. Delete `P` via `DeleteObjectPool` (`internal/gitaly/service/objectpool/delete.go:15-29`), which removes `P` from disk but performs no member unlinking/safety checks and does not clear the `partitionAssignmentTable` entry for `R` (as documented in `doc/transactions.md:70`).
3. Create a new, unrelated repository at the same relative path `R` (e.g. after a project is deleted and re-created with the same path).
4. `partitionAssigner.getPartitionIDRecursive` (`internal/gitaly/storage/storagemgr/partition_assigner.go:234-264`) finds the stale mapping `R -> X` and returns partition `X` directly, placing the new, unrelated repository into the same partition as fork `F`, without ever consulting alternates or repository identity.

```go
func (pt *partitionAssignmentTable) getPartitionID(relativePath string) (storage.PartitionID, error) {
	var id storage.PartitionID

	if err := pt.db.View(func(txn keyvalue.ReadWriter) error {
		item, err := txn.Get(pt.key(relativePath))
		if err != nil {
			if errors.Is(err, badger.ErrKeyNotFound) {
				return storage.ErrPartitionAssignmentNotFound
			}

			return fmt.Errorf("get: %w", err)
		}

		return item.Value(func(value []byte) error {
			id.UnmarshalBinary(value)
			return nil
		})
	}); err != nil {
		return 0, fmt.Errorf("view: %w", err)
	}

	return id, nil
}

func (pt *partitionAssignmentTable) setPartitionID(relativePath string, id storage.PartitionID) error {
	wb := pt.db.NewWriteBatch()
	if err := wb.Set(pt.key(relativePath), id.MarshalBinary()); err != nil {
		return fmt.Errorf("set: %w", err)
	}

	if err := wb.Flush(); err != nil {
		return fmt.Errorf("flush: %w", err)
	}

	return nil
}
```

```go
func (pa *partitionAssigner) getPartitionIDRecursive(ctx context.Context, relativePath string, recursiveCall bool, partitionHint storage.PartitionID, isRepositoryCreation bool) (storage.PartitionID, error) {
	// Check first whether the repository is already assigned into a partition. If so, just return the assignment.
	ptnID, err := pa.partitionAssignmentTable.getPartitionID(relativePath)
	if err != nil {
		if !errors.Is(err, storage.ErrPartitionAssignmentNotFound) {
			return 0, fmt.Errorf("get partition: %w", err)
		}

		// Repository wasn't yet assigned into a partition. This is the slow path. Requests attempting
		// to get or assign a partition ID concurrently are serialized.

		releaseLock, err := pa.acquireRepositoryLock(ctx, relativePath)
		if err != nil {
			return 0, fmt.Errorf("acquire repository lock: %w", err)
		}

		defer releaseLock()

		// With the repository locked, check first whether someone else assigned it into a partition
		// while we weren't holding the lock between the first failed attempt getting the assignment
		// and locking the repository.
		ptnID, err = pa.partitionAssignmentTable.getPartitionID(relativePath)
		if !errors.Is(err, storage.ErrPartitionAssignmentNotFound) {
			if err != nil {
				return 0, fmt.Errorf("recheck partition: %w", err)
			}

			// Some other goroutine assigned a partition between the failed attempt and locking the
			// repository.
			return ptnID, nil
		}
```

```go
func (pa *partitionAssigner) assignPartitionID(ctx context.Context, relativePath string, recursiveCall bool, partitionHint storage.PartitionID) (storage.PartitionID, error) {
	// Check if the repository has an alternate. If so, it needs to go into the same
	// partition with it.
	ptnID, err := pa.getAlternatePartitionID(ctx, relativePath, recursiveCall, partitionHint)
	if err != nil {
		if !errors.Is(err, gitstorage.ErrNoAlternate) {
			return 0, fmt.Errorf("get alternate partition ID: %w", err)
		}

		ptnID = partitionHint
		if ptnID == invalidPartitionID {
			// The repository has no alternate. Unpooled repositories go into their own partitions.
			// Allocate a new partition ID for this repository.
			ptnID, err = pa.allocatePartitionID()
			if err != nil {
				return 0, fmt.Errorf("acquire partition id: %w", err)
			}
		}
	}

	if err := pa.partitionAssignmentTable.setPartitionID(relativePath, ptnID); err != nil {
		return 0, fmt.Errorf("set partition: %w", err)
	}

	return ptnID, nil
}
```

```markdown
### Partitioning

Gitaly divides the data it stores into partitions. Each partition is essentially its own mini-database. They have their own write-ahead log, and store one or more repositories and their associated key-value entries. Transactions always operate against a single partition, never across them. Transactional guarantees only apply within a partition, and transactions are not ordered between different partitions.

Before a transaction can be started against a repository, Gitaly needs to determine which partition the repository belongs to. This is by looking up the repository's partition assignment from the embedded key-value store mapping. The mapping stores the assigned partition ID of each relative path in the form of `(relative_path, partition_id)`. If a mapping already exists, a transaction is started against the assigned partition. If there's no existing mapping yet, the relative path will automatically be assigned into a partition.

Gitaly automatically assigns repositories to partitions when they are first accessed:

- Object pools and all repositories connected to the object pool are placed in the same partition. Repositories that are about to be connected to an object pool, such as newly created forks, are also placed in the same partition with the object pool they are about to be connected.
  - Assigning pools and their connected repositories into the same partition ensures transactions can guarantee consistency between them. If pools were in different partitions, transaction ordering could cause issues, for example updating a reference in a fork before the objects are written into the pool.
```
