### Title
Permanent, unbounded growth of `MarketOrderStore` from every TRC10 market order (never deleted after cancel/fill) — (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
The TRON TRC10 asset-exchange ("Market") feature is a close structural analog to the Deriverse temporary-spot-client-ID bug: a per-account order-tracking record (`MarketAccountOrderCapsule`, analogous to `client_infos_acc`) and a global order object store (`MarketOrderStore`, analogous to `client_infos2_acc`) are populated on every order creation, but the underlying order record in `MarketOrderStore` is never removed for the lifetime of the chain — it is only mutated in place to `CANCELED`/`INACTIVE`. Any unprivileged asset holder can create and cancel orders repeatedly, permanently growing global on-disk state with no reclamation path.

### Finding Description
When an order is placed via `MarketSellAssetActuator.createAndSaveOrder()`, a new `MarketOrderCapsule` is always stored in `orderStore` (`MarketOrderStore`) keyed by a strictly monotonically increasing `totalCount` per account: [1](#0-0) 

The per-account cap enforced in `validate()` — `MAX_ACTIVE_ORDER_NUM = 100` — only limits the number of *currently active* orders (`marketAccountOrderCapsule.getCount()`), not the total number of orders ever created (`getTotalCount()`), so it does not bound long-term storage growth: [2](#0-1) 

When an order is filled or canceled, `MarketUtils.updateOrderState()` only removes the order ID from the account's *active* order list (`MarketAccountOrderCapsule.removeOrder`) — it does not delete the underlying `MarketOrderCapsule` from `MarketOrderStore`: [3](#0-2) 

Likewise, `MarketCancelOrderActuator.execute()` writes the canceled order back with `orderStore.put(...)` rather than deleting it: [4](#0-3) 

`MarketOrderStore` itself exposes only `get`/inherited `put`/`delete` from `TronStoreWithRevoking`, and no actuator path ever calls `delete` on a completed or canceled order record; the `MarketOrderStoreTest.testDelete` shows `delete()` exists as an API but it is not invoked by the production order lifecycle (cancel/match) code shown above: [5](#0-4) 

Because `calculateOrderId` derives the key from the account's ever-incrementing `totalCount`, no key is ever reused, and no compaction/cleanup logic exists to purge fully consumed order records. This exactly mirrors the reported bug class: a per-transaction, per-account "temporary" allocation (order object) is created on every order placement but is only deallocated conceptually (marked done) rather than physically removed, with no dedicated deallocation mechanism analogous to `finalize_spot`.

### Impact Explanation
An unprivileged order placer can repeatedly place minimal-size orders and cancel/let them match, at the cost of the market sell/cancel fees and locked token amounts, to make `MarketOrderStore` grow without bound on every full node forever. Since this store is not part of any bounded structure and is persisted by every node that processes transactions, sustained abuse increases the on-disk state size that every current and future full node must store and load, degrading node operability over time. This matches the "gradual exhaustion" DoS pattern in the original report, though the severity is bounded by the requirement to pay TRX fees for every order/cancel action (an economic rate-limiter), similar to the original bug's caveat that the attacker needs "sufficient funds."

### Likelihood Explanation
High likelihood of reachability: `MarketSellAssetContract` and `MarketCancelOrderContract` are ordinary broadcastable transactions available to any account holding TRX and a TRC10 asset, requiring no special privilege — matching the "order placer" actor explicitly listed as in-scope. The `MAX_ACTIVE_ORDER_NUM` check does not prevent the attack because it is scoped to concurrently active orders, not historical/canceled ones, so the growth vector is trivially repeatable via a create→cancel (or create→match) loop.

### Recommendation
Add a mechanism to physically remove `MarketOrderCapsule` entries from `MarketOrderStore` once an order transitions to a terminal state (`CANCELED` or fully-filled `INACTIVE`) instead of merely updating their state in place, or otherwise bound long-term historical storage of completed orders (e.g., archive off the hot store, or enforce a global/per-account lifetime order cap in addition to the active-order cap).

### Proof of Concept
1. Attacker account funds itself with the market sell fee amount and holds a minimal TRC10 asset balance (e.g., 1 unit).
2. Repeatedly broadcast `MarketSellAssetContract` transactions selling the minimal token amount for a counter asset, then immediately broadcast `MarketCancelOrderContract` to cancel the order (see `createAndSaveOrder` at `MarketSellAssetActuator.java:501-525` and cancellation at `MarketCancelOrderActuator.java:75-149`).
3. Each iteration's `MarketOrderCapsule` remains permanently in `MarketOrderStore` (verified by `MarketUtils.updateOrderState`, which only prunes the *active* order list, not the order store) — confirm via `MarketCancelOrderActuatorTest` cases showing `orderStore.get(orderId)` still returns the (now `CANCELED`) capsule after cancellation, e.g. lines 470-476 and 648-652 of `MarketCancelOrderActuatorTest.java`.
4. Repeat at scale (across many transactions/accounts) to accumulate unbounded, permanent entries in the node's `market_order` RocksDB column, growing every full node's persisted state indefinitely.

  private MarketOrderCapsule createAndSaveOrder(AccountCapsule accountCapsule,
      MarketSellAssetContract contract) {
    MarketAccountOrderCapsule marketAccountOrderCapsule = marketAccountStore
        .getUnchecked(contract.getOwnerAddress().toByteArray());
    if (marketAccountOrderCapsule == null) {
      marketAccountOrderCapsule = new MarketAccountOrderCapsule(contract.getOwnerAddress());
    }

    // note: here use total_count
    byte[] orderId = MarketUtils
        .calculateOrderId(contract.getOwnerAddress(), sellTokenID, buyTokenID,
            marketAccountOrderCapsule.getTotalCount());
    MarketOrderCapsule orderCapsule = new MarketOrderCapsule(orderId, contract);

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    orderCapsule.setCreateTime(now);

    marketAccountOrderCapsule.addOrders(orderCapsule.getID());
    marketAccountOrderCapsule.setCount(marketAccountOrderCapsule.getCount() + 1);
    marketAccountOrderCapsule.setTotalCount(marketAccountOrderCapsule.getTotalCount() + 1);
    marketAccountStore.put(accountCapsule.createDbKey(), marketAccountOrderCapsule);
    orderStore.put(orderId, orderCapsule);

    return orderCapsule;
  }

    }
  }

  }
