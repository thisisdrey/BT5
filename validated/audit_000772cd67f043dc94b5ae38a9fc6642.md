## Finding: `ValidateMultiSign` TVM precompile double-counts a single signer's weight when the same address is proven by two distinct-byte signature encodings

### Title
Double-counting of a single signer's permission weight in `ValidateMultiSign` due to per-signature (not per-address) deduplication — ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The reported AnythingLLM bug is a dedup-before-normalization flaw: two syntactically different recovery-code submissions that normalize to the same value are treated as distinct, letting one true credential satisfy a two-item uniqueness check. The analogous flaw in java-tron exists in the `ValidateMultiSign` TVM precompile, which is reachable by any contract call (unprivileged transaction broadcaster/contract caller). It deduplicates submitted multisig signatures by comparing the *raw signature bytes* (concatenated with the recovered address) instead of deduplicating by the *recovered address* alone, so two differently-encoded signatures that both recover to the same address are accepted as two distinct approvals and their weights are summed.

### Finding Description
`ValidateMultiSign.execute()` recovers a signer address from each submitted signature and accumulates permission weight until the threshold is met: [1](#0-0) 

For each signature it computes `recoveredAddr`, builds `sign = merge(recoveredAddr, sign)`, and only skips counting the weight when the *exact same merged byte sequence* (`sign`) has already been seen (`ByteArray.matrixContains(executedSignList, sign)`). If `recoveredAddr` was already seen but the raw `sign` bytes differ, the code does not `continue`; it merely calls `MUtil.checkCPUTime()` and falls through to add the weight again: [2](#0-1) 

This mirrors the AnythingLLM root cause precisely: the "already used" set is keyed on the un-normalized raw value (full signature bytes) instead of the semantically meaningful value (the recovered signer address), so a single credential (one private key) can be presented twice, in two different byte encodings that both recover to the same address, and be counted as two independent approvals.

By contrast, the equivalent on-chain signature-weight logic used for ordinary transaction broadcasting (`TransactionCapsule.checkWeight`) explicitly deduplicates by the recovered *address* and throws `"has signed twice!"` if the same address appears twice — the correct, address-keyed dedup pattern: [3](#0-2) 

The precompile deviates from this pattern by keying on `sign` (address+raw-signature-bytes) rather than address alone.

An existing test in the repo already demonstrates that a literal byte-for-byte repeated signature is properly rejected/deduplicated (`testDifferentCase`, which adds the identical `key1.sign(toSign)` twice and still only counts it once) — but that test never exercises the case of two *different* valid signature encodings for the same key (e.g., ECDSA signature malleability where `(r, s, v)` and `(r, n-s, v')` both recover to the same address), which is exactly the gap the `matrixContains(executedSignList, sign)` byte-equality check leaves open: [4](#0-3) 

Whether the ECDSA implementation enforces canonical (low-S) signatures — which would foreclose the classic `s → n-s` malleation — could not be fully confirmed from the available index; `SignatureInterface.validateComponents()` and its implementations in `ECKey.java`/`SM2.java` would need to be inspected directly to determine whether both `s` and `n-s` encodings validate. Regardless of the s-malleability question, the code path's deduplication logic is structurally unsound: it is keyed on raw signature bytes rather than the recovered address, which is the root-cause pattern matched to the reported bug class.

### Impact Explanation
If two differently-encoded signatures from a single private key can both pass `signature.validateComponents()` and recover to the same address, an attacker holding only *one* of the required private keys for a multisig `Permission` can call `ValidateMultiSign` with two encodings of that single signature to reach a threshold that should require two distinct signers (e.g., threshold=2 with two 1-weight keys). Any smart contract that gates fund transfers, permission changes, or other privileged operations on `ValidateMultiSign` returning true would then execute for a single-key holder, resulting in unauthorized account operations / theft of contract-controlled funds.

### Likelihood Explanation
Reaching this code requires only calling the `ValidateMultiSign` precompile (address `0x...a`) from a smart contract with attacker-supplied calldata containing signatures — no special privileges, no consensus/SR/witness role needed, fully reachable by any TVM contract caller once `allowTvmSolidity059()` is active. The remaining uncertainty is whether the underlying ECDSA signature validation rejects the high-S / malleated encoding; this determines actual exploitability and was not conclusively verified within the available search depth.

### Recommendation
Change the dedup key in `ValidateMultiSign.execute()` (and audit `BatchValidateSign` for the same pattern) to be keyed solely on `recoveredAddr`, matching `TransactionCapsule.checkWeight`'s address-based dedup, rather than on the concatenation of address + raw signature bytes. Reject (rather than skip/continue) any signature whose recovered address has already contributed weight, regardless of the specific byte encoding of the signature.

### Proof of Concept
Conceptual PoC (would need to be verified against the actual `validateComponents()` canonicality enforcement):
1. Create an `Active` permission with threshold=2 composed of two 1-weight keys, `key1` and `key2`.
2. Using only `key1`'s private key, produce two syntactically different but both-valid signatures over the same hash (e.g., `(r, s)` and its malleated counterpart `(r, n-s)` with adjusted recovery id), such that both recover to `key1`'s address.
3. Call the `validatemultisign` precompile with `signs = [sigA, sigB]` where both recover to `key1`.
4. If both pass `validateComponents()`, `executedSignList` will contain two different `merge(recoveredAddr, sign)` byte arrays for the same `recoveredAddr`, so the `matrixContains(executedSignList, sign)` check never matches, weight is added twice (2×1=2), and the function returns `DataWord.ONE()` even though only one real signer (`key1`) participated — bypassing the intended threshold of 2 distinct signers.
