Based on my investigation, I found a genuine unbounded-growth (memory leak) pattern in `Manager` that's structurally analogous to the tsMuxer CVE (untrusted input causes unbounded memory retention leading to DoS). I was unable to fully confirm the single `clear()` call site's trigger condition due to tool budget exhaustion — I note this explicitly below.

### Title
Unbounded growth of in-memory `ownerAddressSet` from attacker-broadcastable multi-sign transactions leads to node memory exhaustion / DoS - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
`Manager` keeps a permanent, unbounded `HashSet<String>` field `ownerAddressSet` [1](#0-0)  that accumulates the hex-encoded owner address of every multi-signature transaction processed by the node, with no size cap or automatic eviction, unlike the node's other transaction-tracking structures which are explicitly bounded (e.g., `transactionIdCache` with `maximumSize(TX_ID_CACHE_SIZE)` and `expireAfterWrite` [2](#0-1) ).

### Finding Description
Every time `processTransaction` executes a transaction that `isMultiSignTransaction`, it unconditionally inserts the owner's hex address into `ownerAddressSet`: [3](#0-2) 

This set is read from two hot paths — `getVerifyTxs` (used to decide which transactions must be re-verified) [4](#0-3)  and `generateBlock`'s packing loop [5](#0-4)  — meaning it is a live, permanently-referenced field on the `Manager` singleton, not a scratch/local structure.

Unlike `TxCacheDB`/`TransactionCache`, which use bloom filters with a fixed block-window rotation to bound their memory footprint [6](#0-5) , or `transactionIdCache`, which uses Guava's bounded `CacheBuilder` [2](#0-1) , `ownerAddressSet` is a raw `HashSet` with no capacity limit and no expiry policy. Grepping the codebase, only a single `.clear()`/`.remove()` call site exists for this field across `Manager.java`, and it is exercised only in narrow/edge-case flows (visible in the test `testRePushResetsVerifiedOnOwnerAddressSetHit`, which manually manipulates the set via reflection to simulate a stale entry scenario) [7](#0-6) . I was not able to fully confirm within the remaining tool budget whether this single clear path executes on every normal block-processing cycle or only in exceptional/fork-related scenarios; this is a limitation of this analysis and should be verified directly in the source before treating this as conclusively unbounded in the mainline block-processing path.

Any account can trigger insertion into this set by simply broadcasting a transaction with `signatureCount() > 1` (i.e. `isMultiSignTransaction`), which only requires paying the configured `multiSignFee` [8](#0-7) . Because `String` entries are cheap to generate at scale (each unique account address that submits one multi-sig transaction adds a permanent ~40-70 byte entry), an attacker who controls or funds many accounts can drive continuous growth of this in-memory set with no corresponding cleanup, analogous to the tsMuxer bug class where processing of attacker-supplied/crafted input causes objects to be retained without being freed.

### Impact Explanation
If the set is not reliably cleared in the mainline block-processing path (as the single clear call site and lack of any bound suggest), an attacker can drive slow but continuous heap growth by regularly broadcasting inexpensive multi-sig transactions from many distinct owner addresses. Over time this can exhaust JVM heap on validator/full nodes, causing GC pressure, degraded throughput, or ultimately an OutOfMemoryError crash — a node halt/DoS condition, which is the accepted impact bar for this class of finding.

### Likelihood Explanation
Likelihood is limited by two factors I could not fully resolve: (1) whether the single clear-site is actually exercised routinely during normal chain operation (if so, growth is bounded per block/session and the leak is far less severe), and (2) the actual cost-per-entry to an attacker generating many funded multi-sig accounts (bounded by `multiSignFee` economics). Given these open questions, likelihood should be treated as uncertain pending direct code confirmation of the clear-site's trigger frequency.

### Recommendation
- Replace the raw `HashSet<String> ownerAddressSet` with a bounded, time-expiring structure (e.g., Guava `Cache` with `maximumSize`/`expireAfterWrite`), consistent with the pattern already used for `transactionIdCache`.
- Ensure the set (or its bounded replacement) is explicitly cleared/evicted on every block-processing cycle (e.g., in the finally block of `pushBlock`/`generateBlock`), not only in exceptional code paths.
- Add a metric/gauge tracking `ownerAddressSet.size()` (mirroring `Metrics.gaugeSet(MetricKeys.Gauge.MANAGER_QUEUE, ...)` patterns already used elsewhere in `Manager`) to detect unbounded growth in production.

### Proof of Concept
1. Fund N distinct accounts and update each to require ≥2 signatures on the `Active` permission via `AccountPermissionUpdateContract`.
2. From each account, broadcast one multi-signature transaction (any contract type) with 2+ valid signatures — this satisfies `isMultiSignTransaction` and pays only `multiSignFee`.
3. Repeat across a large number of unique accounts, submitted over time (a normal user or botnet of funded accounts can sustain this indefinitely).
4. Since `processTransaction` unconditionally adds every distinct owner's hex address to `ownerAddressSet` on the hot path [3](#0-2) , and no confirmed per-block eviction exists in the mainline path, JVM heap usage attributable to this set grows monotonically with the number of distinct broadcasting addresses, independent of chain height — observable via heap dumps/histograms (`org.tron.core.db.Manager#ownerAddressSet` retained size) on a long-running node subjected to this traffic pattern.

      throws AccountResourceInsufficientException {
    if (trx.getInstance().getSignatureCount() > 1) {
      long fee = getDynamicPropertiesStore().getMultiSignFee();
      boolean disableJavaLangMath = getDynamicPropertiesStore().disableJavaLangMath();
      List<Contract> contracts = trx.getInstance().getRawData().getContractList();
      for (Contract contract : contracts) {
        byte[] address = TransactionCapsule.getOwner(contract);
        AccountCapsule accountCapsule = getAccountStore().get(address);
        try {
          if (accountCapsule != null) {
            adjustBalance(getAccountStore(), accountCapsule, -fee, disableJavaLangMath);

            if (getDynamicPropertiesStore().supportBlackHoleOptimization()) {
              getDynamicPropertiesStore().burnTrx(fee);
            } else {
              adjustBalance(getAccountStore(), this.getAccountStore().getBlackhole(), +fee,
                  disableJavaLangMath);
            }
          }
        } catch (BalanceInsufficientException e) {
          throw new AccountResourceInsufficientException(
              String.format("account %s insufficient balance[%d] to multiSign",
                  StringUtil.encode58Check(address), fee));
        }
      }

      trace.getReceipt().setMultiSignFee(fee);
    }

  @Test
  public void testRePushResetsVerifiedOnOwnerAddressSetHit() throws Exception {
    TransferContract transferContract = TransferContract.newBuilder()
        .setAmount(1L)
        .setOwnerAddress(ByteString.copyFrom(
            ByteArray.fromHexString(Wallet.getAddressPreFixString()
                + "548794500882809695A8A687866E76D4271A1ABC")))
        .setToAddress(ByteString.copyFrom(
            ByteArray.fromHexString(Wallet.getAddressPreFixString()
                + "A389132D6639FBDA4FBC8B659264E6B7C90DB086")))
        .build();
    TransactionCapsule tx = new TransactionCapsule(transferContract, ContractType.TransferContract);
    tx.setVerified(true); // simulate mempool-cached state

    String ownerAddress = ByteArray.toHexString(tx.getOwnerAddress());

    // Inject ownerAddress into ownerAddressSet via reflection
    Set<String> ownerAddressSet =
        (Set<String>) ReflectUtils.getFieldObject(dbManager, "ownerAddressSet");
    ownerAddressSet.add(ownerAddress);

    // rePush should reset isVerified to false before pushTransaction
    dbManager.rePush(tx);

    // After rePush, isVerified must be false
    Boolean verified = (Boolean) ReflectUtils.getFieldObject(tx, "isVerified");
    Assert.assertFalse(verified);
  }
