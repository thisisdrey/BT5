### Title
Legacy (non-hardened) global resource limit formula splits a single ratio computation into two independent divisions, causing systematic energy/bandwidth-limit precision loss - ([File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java])

### Summary
`EnergyProcessor.calculateGlobalEnergyLimit()` and `calculateGlobalEnergyLimitV2()` compute a per-account energy limit that should mathematically be `frozeBalance * totalEnergyLimit / (TRX_PRECISION * totalEnergyWeight)`. In the legacy (non-hardened) code path, instead of doing one multiplication followed by one final division, the code divides `frozeBalance` by `TRX_PRECISION` first, divides `totalEnergyLimit` by `totalEnergyWeight` separately, and then multiplies the two already-rounded results together. This is exactly the same bug class as the `getCommunityVotingPower` finding: performing division(s) on separate terms before combining them, rather than combining first and dividing once, causes accumulated/compounded rounding/precision loss versus the correct result.

### Finding Description
The buggy code: [1](#0-0) [2](#0-1) 

- In `calculateGlobalEnergyLimit`, when `hardenCalculation()` is false, `energyWeight = frozeBalance / TRX_PRECISION` truncates `frozeBalance` to whole TRX first, then multiplies by `(double) totalEnergyLimit / totalEnergyWeight`.
- In `calculateGlobalEnergyLimitV2`, the same pattern is repeated with a `double energyWeight`.

The correct/"hardened" version (used only when the chain parameter `allowHardenResourceCalculation` is enabled) instead does the multiplication of all terms first and a single division at the end, matching the fix pattern recommended in the Sherlock report (`getCommunityVotingPower`): [3](#0-2) [4](#0-3) 

Both `hardenCalculation()`/`disableJavaLangMath()` gate the fixed vs. legacy code path off the dynamic property `allowHardenResourceCalculation`: [5](#0-4) 

The project's own test explicitly demonstrates the divergence between the "buggy" (legacy) formula and the corrected BigInteger-based one: [6](#0-5) 

This `calculateGlobalEnergyLimit` value is used directly in `useEnergy()`, which is invoked on every transaction that consumes energy (i.e., any smart-contract-calling transaction from an unprivileged account): [7](#0-6) 

The analogous non-hardened bandwidth limit code exists in `ResourceProcessor`'s `calculateGlobalLimitV2`-style helpers and `BandwidthProcessor`, gated by the same flag, and reachable from ordinary bandwidth-consuming transactions.

### Impact Explanation
Whether this issue is currently exploitable in production depends entirely on the runtime value of the `allowHardenResourceCalculation` dynamic parameter, which I was unable to conclusively verify from the index (its default/genesis value and current activation state on mainnet were not found in the indexed files searched). If the parameter is not yet activated by governance (as is typical for parameters requiring a committee proposal to switch on), every account's `calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2` result is computed via the legacy, precision-lossy double-division formula, meaning:
- The energy limit granted for frozen-balance-based accounts can differ from the mathematically correct value (either rounding down, denying an account energy it should have, or in some balance/weight ratios rounding differently than intended).
- Because this determines how much energy a user can consume "for free" from frozen TRX before paying TRX for extra energy, systematic under- or over-granting of energy is a resource-accounting/fund-adjacent correctness bug reachable by any contract-calling transaction.

### Likelihood Explanation
High reachability: `calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2` are invoked on essentially every TVM contract call via `useEnergy`, so any unprivileged account triggers this code path constantly. However, the actual severity depends on (a) whether `allowHardenResourceCalculation` is off by default/still off on the live chain, and (b) the magnitude of the rounding difference for typical `frozeBalance`/`totalEnergyWeight` ratios, both of which I could not fully confirm from the code available in the index.

### Recommendation
Confirm the current activation state of the `allowHardenResourceCalculation` proposal parameter on the target network. If it is not yet enabled, prioritize enabling it (or removing the legacy double-division code path entirely) so that `calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2` (and the analogous bandwidth-limit calculations) always use the single-final-division `BigInteger` formula (`calculateGlobalLimitV1`/`calculateGlobalLimitV2`) instead of computing `frozeBalance / TRX_PRECISION` and `totalEnergyLimit / totalEnergyWeight` as independent, separately-rounded divisions before multiplying.

### Proof of Concept
Using the values from the repository's own test (`testCalculateGlobalEnergyLimitHardenedParityWithNonIntegerRatio`), with `totalEnergyLimit = 50_000_000_000`, `totalEnergyWeight = 1_234_567`, `frozeBalance = 10_000_000_000` (10,000 TRX): [8](#0-7) 

- Correct value: `BigInteger.valueOf(10000).multiply(totalEnergyLimit).divide(totalEnergyWeight)`
- "Buggy" legacy value: `10000L * (totalEnergyLimit / totalEnergyWeight)` — the test explicitly asserts `buggy != resultNew`, confirming the legacy formula (mirrored by `EnergyProcessor.calculateGlobalEnergyLimit`'s non-hardened branch at lines 164-165) produces a materially different, less-precise result whenever `totalEnergyLimit` is not an exact multiple of `totalEnergyWeight`.

I was not able to determine from the indexed files whether `allowHardenResourceCalculation` is enabled by default or currently active on mainnet/testnets — this would need to be confirmed with a live Devin session inspecting `DynamicPropertiesStore` genesis defaults and the current chain parameter state before treating this as an actively exploitable issue rather than a dormant/mitigated one.

  public long calculateGlobalEnergyLimitV2(long frozeBalance) {
    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (totalEnergyWeight == 0) {
      return 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV2(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    double energyWeight = (double) frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));

  @Test
  public void testCalculateGlobalEnergyLimitHardenedParityWithNonIntegerRatio() {
    long totalEnergyLimit = 50_000_000_000L;
    long totalEnergyWeight = 1_234_567L;
    long frozeBalance = 10_000_000_000L;

    dbManager.getDynamicPropertiesStore().saveTotalEnergyCurrentLimit(totalEnergyLimit);
    dbManager.getDynamicPropertiesStore().saveTotalEnergyWeight(totalEnergyWeight);

    AccountCapsule account = new AccountCapsule(
        ByteString.copyFromUtf8("owner"),
        ByteString.copyFrom(ByteArray.fromHexString(
            Wallet.getAddressPreFixString() + "548794500882809695a8a687866e76d4271a1abc")),
        AccountType.Normal, 0L);
    account.setFrozenForEnergy(frozeBalance, 0L);

    VMConfig.initAllowHardenResourceCalculation(0);
    long resultOld = repository.calculateGlobalEnergyLimit(account);

    VMConfig.initAllowHardenResourceCalculation(1);
    long resultNew = repository.calculateGlobalEnergyLimit(account);

    long expected = java.math.BigInteger.valueOf(10000L)
        .multiply(java.math.BigInteger.valueOf(totalEnergyLimit))
        .divide(java.math.BigInteger.valueOf(totalEnergyWeight))
        .longValueExact();
    Assert.assertEquals(expected, resultNew);
    Assert.assertEquals(resultOld, resultNew);

    long buggy = 10000L * (totalEnergyLimit / totalEnergyWeight);
    Assert.assertNotEquals(buggy, resultNew);
  }
