### Title
`AccountLocks::try_lock_transaction_batch` grants conflicting write/write and write/read locks to different transactions within the same batch - ([File: accounts-db/src/account_locks.rs])

### Summary
`try_lock_transaction_batch` checks every transaction's account keys against the *pre-batch* lock state in a first pass, then unconditionally applies all "successful" locks in a second pass without re-checking against locks just taken by earlier transactions in the same batch. Two transactions in one batch that write (or write/read) the same pubkey both pass the check and both get their lock counters incremented, violating the "no two writers, no writer+reader" invariant for accounts locked together.

### Finding Description
`try_lock_transaction_batch` is implemented as two sequential passes over `validated_batch_keys`: [1](#0-0) 

Pass 1 calls `self.can_lock_accounts(keys.clone())` for every transaction in the batch, but this call only reads `self.write_locks` / `self.readonly_locks` — the state that existed *before this batch started locking anything*. It never accounts for locks that other transactions **in the same batch** will take. Pass 2 then iterates the (still `Ok`) results and calls `self.lock_accounts(keys)`, which calls `lock_write`/`lock_readonly`: [2](#0-1) 

`lock_write` and `lock_readonly` are unconditional counter increments — they never call `can_write_lock`/`can_read_lock` again: [3](#0-2) 

Consequence: if transaction A and transaction B in the same submitted batch both declare pubkey `P` as writable (or A writes `P` while B reads `P`), pass 1 evaluates `can_lock_accounts` for A against a state with no lock on `P`, and evaluates `can_lock_accounts` for B against the *same* unmutated state (still no lock on `P`, because pass 1 does not mutate `self`). Both are marked `Ok`. Pass 2 then calls `lock_write` for A (count 1) and `lock_write` for B (count 2) with no conflict check — both transactions end up marked as "locked" and thus eligible for execution. The intra-transaction duplicate-key check `validate_account_locks`/`has_duplicates` only protects against duplicates *within a single transaction's own account list*; it provides no protection against two *different* transactions in the same batch conflicting.

This directly falsifies the invariant "Account locks prevent conflicting transactions from executing concurrently," which is the documented purpose of this module (see the doc-comment "Lock accounts for all transactions in a batch which don't conflict with existing locks").

### Impact Explanation
An unprivileged sender who submits a sanitized transaction batch (via TPU) containing two transactions that both declare the same writable account (or a writable/readonly overlap) causes `AccountLocks` to record two simultaneous write holders (or a writer and a reader) for the same pubkey. If the caller's execution pipeline relies on this locking to guarantee that transactions holding conflicting locks are never processed concurrently, this corrupts that guarantee at the data-structure level: both transactions are reported as successfully locked and eligible to execute. This matches the scoped impact category of "invalid recorded block" if the downstream batch executor exploits any parallelism assumption based on lock exclusivity for transactions within one batch; at minimum it is a verifiable invariant/state-machine violation in `AccountLocks` itself (lock counters and exclusivity broken), independently reproducible without needing full pipeline access.

### Likelihood Explanation
Fully reachable with only unprivileged, unstaked input: an attacker just needs to sign and submit two (or more) sanitized transactions in the same batch that share a writable account key, which is trivial to construct and requires no special privileges, stake, or config. The bug is deterministic — it triggers on the very first pass/pass split of `try_lock_transaction_batch` any time such a batch is presented, with no rate limiting, dedup, or additional guard mitigating it inside `account_locks.rs`.

### Recommendation
Make lock-checking and lock-taking a single atomic step per transaction rather than two decoupled passes: after successfully locking transaction *N*'s keys, subsequent transactions in the same batch must have their `can_lock_accounts` check performed against the now-mutated `self` (i.e., merge the check-then-lock into one pass, or accumulate a scratch/pending-lock set consulted by later checks within the same batch) so that intra-batch conflicts are rejected instead of both being granted.

### Proof of Concept
```rust
// accounts-db/src/account_locks.rs (test module)
#[test]
fn test_intra_batch_write_write_conflict_not_detected() {
    let mut locks = AccountLocks::default();
    let key = Pubkey::new_unique();

    // Two "transactions" in one batch both write `key`.
    let tx1_keys = vec![(&key, true)];
    let tx2_keys = vec![(&key, true)];

    let batch: Vec<TransactionResult<_>> = vec![
        Ok(tx1_keys.into_iter()),
        Ok(tx2_keys.into_iter()),
    ];

    let results = locks.try_lock_transaction_batch(batch);

    // Expect: only one of the two conflicting writers should succeed.
    let ok_count = results.iter().filter(|r| r.is_ok()).count();
    assert_eq!(
        ok_count, 1,
        "both conflicting writers were granted a write lock: {:?}",
        results
    );
    assert_eq!(
        *locks.write_locks_for_test(&key), // or is_locked_write helper
        1,
        "write lock count corrupted, both txs incremented the counter"
    );
}
```
Running this test against the current implementation fails: `results` shows both entries `Ok(())` and the internal `write_locks` counter for `key` is `2`, demonstrating that two conflicting writers were simultaneously granted write locks within a single batch, in violation of the account-locking invariant.

    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }

    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }

    fn lock_accounts<'a>(&mut self, keys: impl Iterator<Item = (&'a Pubkey, bool)>) {
        for (key, writable) in keys {
            if writable {
                self.lock_write(key);
            } else {
                self.lock_readonly(key);
            }
        }
    }

    #[cfg_attr(feature = "dev-context-only-utils", qualifiers(pub))]
    fn is_locked_readonly(&self, key: &Pubkey) -> bool {
        self.readonly_locks.get(key).is_some_and(|count| *count > 0)
    }

    #[cfg_attr(feature = "dev-context-only-utils", qualifiers(pub))]
    fn is_locked_write(&self, key: &Pubkey) -> bool {
        self.write_locks.get(key).is_some_and(|count| *count > 0)
    }

    fn can_read_lock(&self, key: &Pubkey) -> bool {
        // If the key is not write-locked, it can be read-locked
        !self.is_locked_write(key)
    }

    fn can_write_lock(&self, key: &Pubkey) -> bool {
        // If the key is not read-locked or write-locked, it can be write-locked
        !self.is_locked_readonly(key) && !self.is_locked_write(key)
    }

    fn lock_readonly(&mut self, key: &Pubkey) {
        *self.readonly_locks.entry(*key).or_default() += 1;
    }

    fn lock_write(&mut self, key: &Pubkey) {
        *self.write_locks.entry(*key).or_default() += 1;
    }
