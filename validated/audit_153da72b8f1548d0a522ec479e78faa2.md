Based on the evidence gathered, this described behavior is not a vulnerability — it is the correct, safety-preserving behavior of the runtime's receipt/state atomicity guarantees.

**Why the described scenario cannot cause an orphaned timeout entry:**

1. `alt_bn128_g1_sum`'s `decode_bool` returning `InvalidInput` for a non-0/1 sign byte produces `HostError::AltBn128InvalidInput`, which propagates up through `VMLogicError` and becomes `FunctionCallError::HostError` set on `VMOutcome.aborted`, per [1](#0-0) .

2. In `action_function_call`'s post-processing (`function_call.rs`), the entire block that reads `promise_yield_indices`, calls `enqueue_promise_yield_timeout` for pending yield receipts, builds `new_receipts`, and calls `set_promise_yield_indices` is gated behind `if execution_succeeded` [2](#0-1) . If the call aborted (as it would here), none of this runs — the `receipt_manager`'s pending PromiseYield receipt (created earlier by `promise_yield_create_with_id` calling `create_promise_yield_receipt_with_id`) is simply dropped, and `enqueue_promise_yield_timeout`/`set_promise_yield_indices` are never invoked, so no timeout entry is ever written.

3. Beyond that, even the state writes made *during* the aborted call by `create_promise_yield_receipt_with_id` (i.e. `set_promise_yield_status` and `set_yield_id_mapping` on the shared `trie_update`) are discarded, because a `FunctionCall` action failure causes the entire enclosing receipt to fail, and `apply_action_receipt` calls `state_update.rollback()` on any receipt failure, discarding all uncommitted state changes from that receipt [3](#0-2) [4](#0-3) .

The net effect: aborting after `promise_yield_create_with_id` leaves `PromiseYieldIndices` completely unchanged (the proof-idea assertion holds), and crucially it also leaves no partial/orphaned yield-status or yield-id-mapping trie entries — the whole operation is atomic and cleanly rolled back. This is exactly the intended fail-safe behavior, not a liveness violation: there is no PromiseYield receipt in state at all after the abort, so there is nothing that "can never resolve."
