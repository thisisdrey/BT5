### Title
Fee-refund-before-verification in eth Wallet Contract allows repeated draining of a wallet's balance via replay of an unresolved `EOABaseTokenTransfer` - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`rlp_execute` on the Wallet Contract (the contract that governs ETH-implicit accounts) pays out a relayer "fee" refund immediately upon parsing a signed Ethereum transaction, *before* the address-registrar check that determines whether the transaction/target is actually valid completes. In the `EOABaseTokenTransfer { address_check: Some(_), .. }` branch, the contract's nonce is deliberately **not** incremented until the asynchronous `address_check_callback` resolves, but the fee-refund promise is created unconditionally in the synchronous portion of `inner_rlp_execute`, regardless of that pending check. This mirrors the reported pattern: a critical guard (round-active / project_id nulling) is applied on one code path but not on the sibling path, letting funds move before the state that should prevent reuse is updated.

### Finding Description
`inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:347-410`) processes a parsed transaction as follows: [1](#0-0) 

Nonce increment is explicitly skipped when `address_check: Some(_)`, i.e. when the target looks like another eth-implicit wallet and the contract must first ask the address registrar whether that address is actually a registered named account (a case where the relayer is potentially faulty).

Immediately after, without any dependency on the still-pending registrar check, the fee is refunded to `predecessor_account_id`: [2](#0-1) 

The registrar lookup and its resolution happen later in `address_check_callback` (`lib.rs:134-192`). If the registrar finds a matching account (`maybe_account_id.is_some()`), the transaction is deemed to have come from a faulty relayer. But the code only bans the relayer (deletes its access key) if `env::signer_account_id() == current_account_id` — i.e., only when the caller used a Function-Call access key added to the wallet itself: [3](#0-2) 

If the call was made without such an access key (any account can call the public, non-restricted `rlp_execute` method directly, since `validate_tx_relayer_data` only checks that the transaction is signed by the wallet owner, not that the caller possesses any privilege — `internal.rs:318-368`), the code simply returns an error **without banning anyone and without ever having incremented the nonce**.

Consequently, the exact same previously-broadcast, validly-signed RLP transaction (public on-chain data) can be resubmitted to the same `rlp_execute` method again — the nonce check in `validate_tx_relayer_data` (`internal.rs:352-359`) still passes because the nonce genuinely never moved — and each resubmission again reaches the "refund the fee" branch in `inner_rlp_execute` before the (again failing) registrar check resolves. Because `has_in_flight_tx` (`lib.rs:97-105`) only prevents *concurrent* in-flight calls, not sequential replays once each call resolves, an attacker can loop this call indefinitely: each iteration drains `tx_fee` yoctoNEAR from the wallet account to whatever account calls `rlp_execute` (`predecessor_account_id`), with the state (`nonce`) never advancing to block further replays.

### Impact Explanation
This is a genuine theft-of-funds/double-spend vector reachable from an ordinary account's transaction to a deployed, standard contract (the ETH-implicit Wallet Contract used by every ETH-implicit account on NEAR). Any account can permissionlessly and repeatedly call the public `rlp_execute` method with a captured signed transaction and drain the wallet's balance one `fee` increment at a time, with no cap other than the wallet running out of funds. Because ETH-implicit accounts are a core account type supported by the protocol/runtime (not a third-party dApp), this directly matches the in-scope categories (eth-implicit wallet contract).

### Likelihood Explanation
Exploitation requires:
1. Observing (or eliciting) one validly signed RLP Ethereum transaction from the wallet owner where the parsed target resolves to `TargetKind::EthImplicit` with a non-zero `max_fee_per_gas * gas_limit` (a common, legitimate shape for relayer-compensated base-token transfers to another eth-implicit wallet).
2. That the `to` address happens to correspond to an address that is (or later becomes) registered in the address registrar as a named account — causing the "faulty relayer" branch to trigger repeatedly instead of normal execution.
3. Calling `rlp_execute` directly (not via an access key added to the wallet), so the "ban relayer" branch is never reached and thus the nonce/relayer-key state never advances.

This requires a specific but plausible target selection and a wallet owner or relayer producing a signed transaction with a non-trivial `fee`. It is a data-availability + replay condition rather than requiring privileged access, making it a realistic griefing/drain vector once triggered, though it is somewhat narrower than an always-exploitable path since it depends on the registrar state and the tx shape.

### Recommendation
- Do not send the relayer fee refund until *after* all asynchronous validations that could invalidate the transaction (including the address-registrar check) have completed successfully.
- Ensure the contract's nonce is monotonically advanced (or some other anti-replay guard is set) as soon as a transaction is accepted for processing, regardless of which downstream branch (`address_check` present or absent) is taken, so that the same signed payload can never be reprocessed twice.
- In `address_check_callback`, treat "target resolves to an existing named account" as a terminal, nonce-consuming outcome unconditionally (not only when `signer_account_id() == current_account_id`), so unauthenticated resubmission of the same payload is blocked.

### Proof of Concept
1. Wallet owner (or an already-compromised/legitimate relayer flow) produces a signed RLP transaction `tx` targeting an eth-implicit address `A` with `max_fee_per_gas * gas_limit > 0`, where `A` also happens to correspond to a *registered* named account in the address registrar.
2. Attacker (any account, no special permission needed) calls `rlp_execute(target=A, tx_bytes_b64=tx)` on the wallet contract as `predecessor_account_id = attacker`.
3. `inner_rlp_execute` parses `tx` into `TransactionKind::EthEmulation(EOABaseTokenTransfer { address_check: Some(A), fee })`; nonce is **not** incremented (`lib.rs:358-365`); the fee-refund promise transferring `fee` to `attacker` is created immediately (`lib.rs:374-385`).
4. `address_check_callback` later resolves with `maybe_account_id = Some(...)` (address is registered); since `signer_account_id() != current_account_id` (attacker did not use an access key), the callback returns an error without banning or advancing nonce (`lib.rs:161-173`).
5. Attacker repeats step 2 with the identical `tx_bytes_b64` (the nonce check still passes because `self.nonce` is unchanged) as many times as desired, receiving `fee` yoctoNEAR from the wallet's balance on every iteration.
