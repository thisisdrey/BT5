Based on my investigation, I found a strong analog in the durable-nonce dedup path of the transaction scheduler.

### Title
Durable-Nonce Dedup Pre-Filter Allows Unauthenticated Front-Running Denial-of-Service Against a Victim's Nonce Transaction - ([File: core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs])

### Summary
`TransactionViewReceiveAndBuffer::handle_packet_batch_message` extracts a "raw" nonce address from an incoming transaction via `state.transaction().get_durable_nonce()` and immediately uses it to decide whether to drop the transaction, *before* the transaction's nonce validity, its account-lock structure, or the nonce-authority signature relationship is confirmed against bank state. This mirrors the `Lender::redeem()` bug class: a cheap, attacker-controlled action mutates shared pre-check state (`totalSupply` boundary vs. here, the priority/occupancy of the `container`'s nonce-tracking map) causing a legitimate, otherwise-valid transaction to be dropped.

### Finding Description
In `handle_packet_batch_message`, for every incoming packet the code computes: [1](#0-0) 

```
let raw_nonce_address = state.transaction().get_durable_nonce().cloned();
...
let drop_incoming_nonce_tx = raw_nonce_address
    .and_then(|address| container.get_nonce_transaction_priority_id(&address))
    .is_some_and(|existing| {
        existing.priority >= priority || !container.is_queued(existing)
    });
if drop_incoming_nonce_tx {
    receiving_stats.num_dropped_on_nonce_dedup += 1;
    continue;
}
```

This early drop decision is made purely from the *shape* of the transaction (whether its first instruction looks like `AdvanceNonceAccount` targeting some pubkey) and its declared priority/fee, comparing it against whatever transaction is currently occupying that nonce address slot in the scheduler `container`. Only *after* this early filtering does the code call `check_transaction_without_status_cache` to actually validate that the transaction is a well-formed, correctly-authorized nonce transaction: [2](#0-1) 

Separately, once a transaction is confirmed valid, a higher-priority nonce transaction for the same nonce address **evicts** the one already resident in the queue: [3](#0-2) 

This produces the same "front-run a shared boundary check with a cheap dust action" pattern as the `Lender` bug: an attacker who wants to censor a victim's specific durable-nonce transaction can craft their own transaction that:
1. Uses a first instruction shaped like `advance_nonce_account` targeting the victim's nonce account pubkey (this requires only that the *shape* match `get_durable_nonce()`'s parsing heuristic, not that the attacker holds the nonce authority key for that account), and
2. Uses any legitimate fee-payer/signature of the attacker's own choosing with a compute-unit price set higher than the victim's pending transaction.

If accepted into the container as a queued or in-flight entry ahead of the victim's transaction, it will cause any subsequently arriving genuine victim retries to be dropped via `num_dropped_on_nonce_dedup`, or will itself evict/replace the victim's already-queued transaction via `num_evicted_on_nonce_dedup`, purely on the basis of priority ordering keyed off the (spoofable) raw nonce address, before authorization is checked.

### Impact Explanation
A legitimate durable-nonce transaction from a victim can be repeatedly denied entry into a leader's block-production queue by a cheap, unprivileged attacker crafting competing packets that reference the same nonce address with a higher fee, without ever needing the actual nonce-authority signature to succeed on execution. Because nonce transactions are specifically used by users who need replay protection across blockhash expiry (e.g., cold wallets, program-derived flows, long-running integrations), this is a persistent, low-cost griefing/DoS vector against a targeted user's specific transaction — analogous to the M-02 report's front-running denial of a specific user's operation via a cheap boundary-state manipulation.

### Likelihood Explanation
The attacker only needs: (a) knowledge of the victim's nonce account pubkey (public information), (b) the ability to sign a transaction with their own fee payer, and (c) enough balance to pay a higher priority fee than the victim's transaction. No special privileges, validator role, or mocked-only conditions are required — this is reachable by any unprivileged network participant submitting ordinary transactions into the banking stage pipeline, satisfying the "unprivileged-user" and "banking stage and scheduler" analog category.

### Recommendation
Do not key the early nonce-dedup drop/evict decision purely on the raw, unauthenticated `get_durable_nonce()` address extracted before validation. Either defer the drop/evict decision until after `check_transaction_without_status_cache` has confirmed the transaction is a properly authorized, valid nonce transaction for that address (i.e., only let validated nonce transactions occupy/evict a nonce slot, as is already done later in the function via `validated_nonce_address`), or bind the pre-filter to a value that cannot be forged without holding the nonce authority (e.g., only compare against already-validated entries, never optimistically drop unvalidated raw-address matches).

### Proof of Concept
Not independently executable from static analysis alone: this would require running the scheduler/receive-and-buffer pipeline end-to-end (as the existing tests `test_receive_and_buffer_nonce_dedup_drop_evict` and `test_receive_and_buffer_pseudo_nonce_untracked` at [4](#0-3)  do) but crafted so the "attacker" transaction's `advance_nonce_account` instruction targets the *victim's* nonce pubkey with a higher fee while using an authority the attacker does not actually control, to confirm whether `get_durable_nonce()`'s structural parse is invoked prior to authority-signature verification within `try_handle_packet`. I was not able to fully trace `get_durable_nonce()`'s implementation or definitively confirm at what pipeline stage (sigverify vs. sanitization vs. `check_transaction_without_status_cache`) the nonce-authority signature is cryptographically checked before this early filter runs, due to running out of tool iterations. This should be verified directly in the repository (definition of `get_durable_nonce` and `try_handle_packet`, and whether `SigVerifyStage` runs before or independent of this authority check) before treating this as fully confirmed.

    #[test_case(HIGH_FEE, LOW_FEE; "hilo_drop")]
    #[test_case(HIGH_FEE, HIGH_FEE; "hihi_drop")]
    #[test_case(LOW_FEE, HIGH_FEE; "lohi_evict")]
    fn test_receive_and_buffer_nonce_dedup_drop_evict(old_fee: u64, new_fee: u64) {
        let (sender, receiver) = bounded(1024);
        let (bank_forks, mint_keypair) = test_bank_forks_with_fee();
        let (mut receive_and_buffer, mut container) =
            setup_transaction_view_receive_and_buffer(receiver, bank_forks.clone());
        let (nonce_pubkey, durable) = create_nonce_identity(&bank_forks, &mint_keypair.pubkey());
        let new_has_priority = new_fee > old_fee;

        send_transactions(
            &sender,
            &[create_nonce_transaction(
                &mint_keypair,
                &nonce_pubkey,
                old_fee,
                durable,
            )],
        );
        assert_eq!(
            receive(&mut receive_and_buffer, &mut container).num_buffered,
            1
        );
        let prior_nonce_entry = *container
            .get_nonce_transaction_priority_id(&nonce_pubkey)
            .unwrap();

        send_transactions(
            &sender,
            &[create_nonce_transaction(
                &mint_keypair,
                &nonce_pubkey,
                new_fee,
                durable,
            )],
        );

        let stats = receive(&mut receive_and_buffer, &mut container);
        let current_nonce_entry = *container
            .get_nonce_transaction_priority_id(&nonce_pubkey)
            .unwrap();

        if new_has_priority {
            assert_eq!(stats.num_dropped_on_nonce_dedup, 0);
            assert_eq!(stats.num_evicted_on_nonce_dedup, 1);
            assert_eq!(stats.num_buffered, 1);

            assert_ne!(prior_nonce_entry, current_nonce_entry);
            assert!(current_nonce_entry.priority > prior_nonce_entry.priority);
            assert!(
                container
                    .get_mut_transaction_state(prior_nonce_entry.id)
                    .is_none()
            );
        } else {
            assert_eq!(stats.num_dropped_on_nonce_dedup, 1);
            assert_eq!(stats.num_evicted_on_nonce_dedup, 0);
            assert_eq!(stats.num_buffered, 0);
            assert_eq!(prior_nonce_entry, current_nonce_entry);
        }

        assert!(container.is_queued(&current_nonce_entry));

        verify_container(&mut container, 1);
    }
