### Title
Stale self-targeted postponed/yielded `DeleteAccount` receipt survives account deletion and drains a re-created account of the same name - (`runtime/runtime/src/actions.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`check_actor_permissions` authorizes `Action::DeleteAccount` purely by comparing `actor_id == account_id` (a plain `AccountId` string comparison), while postponed/yielded action receipts are stored in the trie keyed only by `receiver_id` (an `AccountId` string) independent of the `Account` record itself. Because deleting an account (`action_delete_account`) does not purge any `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId`/`PromiseYieldReceipt` entries scoped to that account name, an attacker can leave behind a dormant, self-targeted `DeleteAccount{beneficiary: attacker}` receipt under name `A`, delete account `A`, and later — after an unrelated party `B` re-registers `A` and funds it — trigger the stale receipt to pass authorization (since `actor_id` and `account_id` are both the string `"A"`) and redirect `B`'s balance to the attacker's beneficiary.

### Finding Description
- Authorization for `DeleteAccount` is implemented in `check_actor_permissions` at [1](#0-0) : it only checks `actor_id != account_id` (both plain `AccountId` values) and that `account.locked()` is zero on the account object present *at execution time*. There is no binding between the receipt and the specific "generation"/instance of the account it targets.
- `apply_action_receipt` derives `actor_id` from `receipt.predecessor_id()` at [2](#0-1) , i.e., from the (attacker-authored, already-committed) receipt content, not from any live signature/key check.
- A contract on account `A` can construct a receipt whose `predecessor_id == receiver_id == "A"` (a self-targeted batch, e.g. via `promise_batch_create(self)` chained off a `.then()`/yield dependency) containing a single `DeleteAccount{beneficiary_id: attacker_controlled_id}` action. Because it has unresolved `input_data_ids`, `process_action_receipt` stores it as a **postponed receipt** rather than executing it immediately: [3](#0-2) . This is persisted via `set_postponed_receipt` under `TrieKey::PostponedReceipt{receiver_id, receipt_id}` — a column (`col::POSTPONED_RECEIPT`) entirely separate from `TrieKey::Account`: [4](#0-3) [5](#0-4) .
- Separately, `A` self-deletes via a normal `DeleteAccount` transaction (which trivially passes `check_actor_permissions` since `actor_id == account_id == "A"`). `action_delete_account` refunds the current balance, burns gas keys, calls `remove_account`, and sets `*account = None`: [6](#0-5) . Nothing in this path, nor in the documented behavior of account deletion in the architecture spec ("Refunds remaining balance to beneficiary, burns gas-key balances, removes the account; requires zero locked stake"), touches the `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` (or `PromiseYieldReceipt`) entries keyed under the same `AccountId` string — these live in disjoint trie columns unrelated to the `Account` record.
- Later, a new party `B` creates a fresh account also named `A` (e.g., a reused/abandoned subaccount name) and deposits funds. `check_account_existence`/`action_create_account` create a brand-new `Account` object with no relation to the old one — there is no "generation counter" tying postponed receipts to a specific account incarnation.
- When the outstanding data dependency for the stale postponed receipt eventually arrives (`process_receipt` for the `Data`/`PromiseResume` receipt), the runtime fetches and executes the stored `DeleteAccount` receipt via `get_postponed_receipt`/`apply_action_receipt`: [7](#0-6) . `actor_id = receipt.predecessor_id()` is still the string `"A"`, `account_id` is still `"A"` (now B's newly created account), so `check_actor_permissions` passes, `account.locked()` is zero on B's fresh account, and `action_delete_account` executes, refunding B's balance to the attacker-chosen `beneficiary_id` embedded in the old receipt, then deleting B's account.

### Impact Explanation
Direct theft of funds: an ordinary, unprivileged attacker can pre-plant a time-bomb tied to an account name they control, later abandon that name, and steal the balance of anyone who reuses the name and deposits into it — a clear violation of authorization-exactness and value-conservation invariants (funds are diverted to an attacker who no longer owns the account). This matches NEAR's "theft of user funds" bounty category.

### Likelihood Explanation
- All steps are reachable purely through a normal unprivileged account: deploying a contract, issuing signed transactions/promise batches, and using standard cross-contract-call or yield/resume promise chains to create a genuinely postponed (or promise-yielded) self-targeted `DeleteAccount` receipt.
- The attacker fully controls the timing of resolving the dependency (e.g., via `yield/resume`, which can be held open for a configurable timeout window, giving ample time for a third party to re-register and fund the vacated account name).
- The only external dependency is that some other party re-creates and funds an account with the exact same name the attacker previously owned and abandoned — plausible for desirable/short subaccount names or accounts sold/reassigned off-chain.
- Repeatable: the attacker can attempt this against any name they control before releasing it.

### Recommendation
Bind postponed/yielded action receipts to the specific account instance they were created against, not just its name string. Options: (1) purge all `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId`/`PromiseYieldReceipt`/`PromiseYieldTimeout` entries for `account_id` as part of `action_delete_account`/`remove_account`; and/or (2) add an account "generation"/creation-nonce to receipts or to the stored postponed/yield entries and require it to match the live account's generation before `check_actor_permissions` grants self-actor authorization for `DeleteAccount` (and ideally for all self-actor-gated actions).

### Proof of Concept
Integration/test-loop plan (mirroring the existing pattern in `test-loop-tests/src/tests/create_delete_account.rs` and `runtime/runtime/src/tests/apply.rs::test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`):
1. Deploy a contract to account `A` that, in one call, creates a promise-yield (or a `.then()`-chained promise) targeting `A` itself with a single `Action::DeleteAccount{beneficiary_id: attacker}` batch action, leaving it postponed/yielded pending an external resume/data receipt.
2. In a separate transaction, have `A` self-delete via `DeleteAccountAction{beneficiary_id: A}` (or any other beneficiary), verifying the account record is gone but chain state still contains the postponed/yield receipt entry.
3. Submit a `CreateAccount` transaction from `B` re-creating account `A`, followed by a `Transfer` depositing `N` NEAR into it; verify via `view_account` that `A` exists with balance `N`.
4. Trigger resolution of the pending dependency (submit the resume data / satisfy the awaited promise) and advance the test loop until the postponed receipt executes.
5. Assert: `attacker`'s balance increased by `N` (`attacker_balance_after == attacker_balance_before + N`), and `view_account(A)` now returns `UnknownAccount`, proving B's freshly deposited funds were redirected to the attacker via the stale, privilege-inheriting `DeleteAccount` action.

    /// Received a new action receipt. We'll first check how many input data items
    /// were already received before and saved in the state.
    /// And if we have all input data, then we can immediately execute the receipt.
    /// If not, then we will postpone this receipt for later.
    fn process_action_receipt(
        &self,
        receipt: &Receipt,
        receipt_sink: &mut ReceiptSink,
        instant_receipts: &mut VecDeque<Receipt>,
        validator_proposals: &mut Vec<ValidatorStake>,
        state_update: &mut TrieUpdate,
        apply_state: &ApplyState,
        epoch_info_provider: &dyn EpochInfoProvider,
        pipeline_manager: &ReceiptPreparationPipeline,
        stats: &mut ChunkApplyStatsV1,
        account_id: &AccountId,
        action_receipt: VersionedActionReceipt<'_>,
        receipt_to_tx: &mut Vec<(CryptoHash, ReceiptToTxInfo)>,
    ) -> Result<Option<ExecutionOutcomeWithId>, RuntimeError> {
        let mut pending_data_count: u32 = 0;
        for data_id in action_receipt.input_data_ids() {
            if !has_received_data(state_update, account_id, *data_id)? {
                pending_data_count += 1;
                // The data for a given data_id is not available, so we save a link to this
                // receipt_id for the pending data_id into the state.
                set(
                    state_update,
                    TrieKey::PostponedReceiptId {
                        receiver_id: account_id.clone(),
                        data_id: *data_id,
                    },
                    receipt.receipt_id(),
                )
            }
        }

        if pending_data_count == 0 {
            // All input data is available. Executing the receipt. It will cleanup
            // input data from the state.
            return self
                .apply_action_receipt(
                    state_update,
                    apply_state,
                    pipeline_manager,
                    receipt,
                    receipt_sink,
                    instant_receipts,
                    validator_proposals,
                    stats,
                    epoch_info_provider,
                    receipt_to_tx,
                )
                .map(Some);
        } else {
            // Not all input data is available now.
            // Save the counter for the number of pending input data items into the state.
            set(
                state_update,
                TrieKey::PendingDataCount {
                    receiver_id: account_id.clone(),
                    receipt_id: *receipt.receipt_id(),
                },
                &pending_data_count,
            );
            // Save the receipt itself into the state.
            set_postponed_receipt(state_update, receipt);
        }

pub fn set_postponed_receipt(state_update: &mut TrieUpdate, receipt: &Receipt) {
    assert!(matches!(receipt.versioned_receipt(), VersionedReceiptEnum::Action(_)));
    let key = TrieKey::PostponedReceipt {
        receiver_id: receipt.receiver_id().clone(),
        receipt_id: *receipt.receipt_id(),
    };
    set(state_update, key, receipt);
}
