### Title
`Pool.liquidate` can never fully close an unhealthy position and, once `debtFloorInUsd` is set, small underwater positions become permanently unliquidatable — collateral and bad debt locked forever - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The Carapace report describes a liquidation/default mechanism that exists on paper but cannot actually be exercised, leaving the counterparty's capital locked indefinitely. Metronome has the same bug class in `Pool.liquidate`: the combination of the `maxLiquidable` repay cap and the `debtFloorInUsd` minimum-remaining-debt check makes it impossible for any liquidator to fully repay a position, and makes a whole band of underwater positions completely unliquidatable.

### Finding Description
`Pool.liquidate` enforces two constraints on `amountToRepay_`:

```solidity
// contracts/Pool.sol:567-579
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}
if (debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(
        address(syntheticToken_), _debtTokenBalance - amountToRepay_);
    if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
        revert RemainingDebtIsLowerThanTheFloor();
    }
}
```

`maxLiquidable` is initialized to `0.5e18` in `initialize` (contracts/Pool.sol:181), so any repayment above 50% of the debt-token balance reverts. The floor check additionally reverts whenever the remaining debt is `> 0` and `< debtFloorInUsd`. The conjunction means a liquidator can only leave remaining debt `>= debtFloorInUsd`; leaving `0` requires a 100% repay, which always exceeds `maxLiquidable` when `maxLiquidable < 1e18`.

Consequences:

1. A position can never be fully liquidated while `maxLiquidable < 1e18`. Each call repays at most `maxLiquidable` of the *current* balance, so the debt decays asymptotically and never reaches zero — a permanent dust debt position.
2. Once `debtFloorInUsd > 0` (deployed pools do set it — see `updateDebtFloor` at contracts/Pool.sol:768), any account whose debt `D` satisfies `D - D*maxLiquidable < debtFloorInUsd` (i.e., `D < debtFloorInUsd / (1 - maxLiquidable)` = `2 * floor` at the default 50%) is completely unliquidatable: every allowed `amountToRepay_` either exceeds the max or leaves a sub-floor remainder. `liquidate` reverts on every input.

Meanwhile the borrower's collateral is hard-locked: `DepositToken.unlockedBalanceOf` returns `0` whenever `_issuableInUsd == 0` (i.e., the position is underwater), which gates `withdraw`, `transfer`, `transferFrom`, `withdrawFrom` and `flashWithdraw` via `_revertIfLocked` (contracts/DepositToken.sol:180-182, 383-398, 406-427).

This mirrors the Carapace finding exactly: the mechanism that is supposed to resolve distressed positions (`liquidate` ↔ "exercise the protection") cannot be exercised for a class of positions, so the locked capital can never be released through that path — an abandoned or insolvent account's collateral stays in the Treasury forever and its debt becomes permanent bad debt.

### Impact Explanation
- Permanent freezing of funds: an underwater account with `debtInUsd < 2 * debtFloorInUsd` can never be liquidated; all its `DepositToken` collateral is unwithdrawable (`unlockedBalanceOf == 0`) and cannot be seized, so the underlying sits in the Treasury indefinitely unless the borrower voluntarily repays — which an insolvent borrower will not do.
- Protocol insolvency: the unclosable dust debt accrues interest via `DebtToken.accrueInterest` forever while the backing collateral cannot be seized, growing bad debt. Because liquidation is the only bad-debt resolution mechanism (there is no socialize/fund BadDebt path in `Pool`), the invariant "unhealthy positions are always liquidatable" is broken.

### Likelihood Explanation
Any user can create such a position without privileges: deposit collateral, `DebtToken.issue` a debt below `2 * debtFloorInUsd`, and the position becomes permanently unliquidatable the moment prices move it underwater (or via same-transaction oracle/AMM manipulation of a manipulable collateral such as a vault-share-priced asset). An attacker can also mass-produce these dust bad-debt positions cheaply. No modifier saves it: `whenNotShutdown`, `nonReentrant`, and the token-exists checks are orthogonal; `seize` bypasses `_revertIfLocked` by design, but the call never reaches it. The only caveat is that the permanent-unliquidatable band requires `debtFloorInUsd > 0`; with `debtFloorInUsd == 0` the bug degrades to "positions can never be fully closed" (asymptotic dust debt), which is still a defect but lower impact.

### Recommendation
- In `Pool.liquidate`, skip the `debtFloorInUsd` check when `amountToRepay_ == _debtTokenBalance` (full close should always be permitted), and allow repayments up to 100% of the balance when the remaining debt would otherwise fall below the floor — i.e., clamp `amountToRepay_` to `_debtTokenBalance` instead of reverting on `RemainingDebtIsLowerThanTheFloor`.
- Alternatively (or additionally), when `_debtTokenBalance` is below the floor-derived threshold, treat the position as fully liquidatable: permit `amountToRepay_ == _debtTokenBalance` even though `wadDiv` yields `1e18 > maxLiquidable`.
- Consider a permissionless bad-debt resolution path (e.g., a `closeDustPosition` that seizes remaining collateral against Treasury/fee-collector funds) for positions that no liquidator will ever profitably take.

### Proof of Concept
Foundry fork sketch (Hardhat equivalent is analogous):

```solidity
// Assumes deployed pool with maxLiquidable = 0.5e18 and debtFloorInUsd = e.g. 100e18
function test_UnliquidatableDustDebt() public {
    // 1. Attacker deposits collateral and issues ~150 USD of msAsset debt (< 2*floor)
    uint256 collateralAmt = 300e18;
    underlying.mint(attacker, collateralAmt);
    underlying.approve(address(msdToken), collateralAmt);
    msdToken.deposit(collateralAmt, attacker);
    debtToken.issue(150e18, attacker); // debtInUsd ~ $150 < $200 threshold

    // 2. Push position underwater (oracle update / same-tx AMM manipulation of collateral price)
    oracle.setPrice(address(underlying), price * 60 / 100);

    (bool healthy,,,,) = pool.debtPositionOf(attacker);
    assertFalse(healthy);

    // 3. Any liquidate call reverts:
    uint256 bal = debtToken.balanceOf(attacker);
    vm.expectRevert(AmountGreaterThanMaxLiquidable.selector);
    pool.liquidate(msAsset, attacker, bal, msdToken);            // 100% > 50%

    vm.expectRevert(RemainingDebtIsLowerThanTheFloor.selector);
    pool.liquidate(msAsset, attacker, bal / 2, msdToken);        // leaves $75 < floor

    // 4. Collateral is permanently locked:
    assertEq(msdToken.unlockedBalanceOf(attacker), 0);
    vm.expectRevert(NotEnoughFreeBalance.selector);
    vm.prank(attacker);
    msdToken.withdraw(1, attacker);
}
```

Uncertainty note: I verified `maxLiquidable = 0.5e18` is the initialized default and that `debtFloorInUsd` is a governor-set parameter; whether the specific deployed pool under audit currently has `debtFloorInUsd > 0` should be confirmed against deployment storage. If it is `0`, the "always reverts" band disappears but the "position can never be fully liquidated" defect remains, which is still worth reporting at reduced severity.
