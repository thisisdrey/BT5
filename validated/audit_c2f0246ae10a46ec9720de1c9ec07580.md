### Title
Reward Loss When Witness Total Vote Count Is Zero in `DelegationStore.accumulateWitnessVi()` - (File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java)

### Summary
`DelegationStore.accumulateWitnessVi()` computes a per-vote reward index (`vi`, TRON's equivalent of Curve's `integral_inv_supply`) by dividing accumulated block/transaction-fee rewards by the witness's total vote count for the cycle. When the total vote count for a witness in a given cycle is `0`, the function skips the division entirely and just carries forward the previous `vi` value, silently discarding the reward that was already deposited for that cycle via `MortgageService.payReward()` / `DelegationStore.addReward()`. This mirrors the reported `LiquidityGauge._checkpoint()` bug class: a denominator of zero (there, `totalSupply`; here, `voteCount`) causes real, already-accrued rewards to become permanently unclaimable by anyone.

### Finding Description
Block and transaction-fee rewards for a witness are accumulated per-cycle via `payReward()`, which stores the value with `DelegationStore.addReward(cycle, witnessAddress, value)`: [1](#0-0) 

At maintenance time, `MaintenanceManager.doMaintenance()` converts that stored reward into a claimable per-vote index by calling `DelegationStore.accumulateWitnessVi(curCycle, witness.createDbKey(), witness.getVoteCount())` for every witness, using the witness's *current* `voteCount` (not the vote count that will be recorded for the next cycle a few lines later via `setWitnessVote`): [2](#0-1) 

Inside `accumulateWitnessVi`, if `voteCount == 0` (or `reward == 0`), the accumulated reward for that cycle is simply dropped — the previous `vi` is forwarded unchanged instead of being incremented by `reward * 10^18 / voteCount`: [3](#0-2) 

This is structurally identical to the reported `LiquidityGauge._checkpoint()` flaw: a reward pool (`d_reward` / `reward` for the cycle) is divided by a supply-like denominator (`totalSupply` / `voteCount`); when that denominator is zero, the division is skipped/short-circuited and the reward silently vanishes from the accounting rather than being credited to anyone or refunded. Once `addReward` has already stored the value for that cycle, and `accumulateWitnessVi` forwards `vi` unchanged, there is no other code path that redistributes or reclaims that specific cycle's reward for that witness — it is permanently stuck as an untracked liability in `AccountStore`'s TRX balance pool (the reward was already implicitly backed by real TRX from block production allowance, but no account's `allowance`/`vi` reflects it).

The same reward-forwarding pattern also exists in the duplicate/legacy implementation `RewardViCalService.accumulateWitnessVi()`: [4](#0-3) 

A `voteCount == 0` for an elected/rewarded witness in a given cycle is plausible: `witness.getVoteCount()` used at the moment of `doMaintenance()` reflects votes tallied at that specific maintenance boundary, and any unprivileged token holder can drive it to (or keep it at) zero by withdrawing/canceling votes via `UnfreezeBalanceV2Actuator.updateVote()` (which clears votes when Tron Power becomes insufficient), immediately before a maintenance cycle executes: [5](#0-4) 

### Impact Explanation
When triggered, a cycle's worth of block reward and transaction fee reward for a witness (funded from the real network reward pool / TRX balance) is silently discarded from the `vi` accounting: none of the voters who backed that witness during the cycle can ever claim it through `VoteRewardUtil.computeReward()`/`MortgageService.computeReward()`, since both compute rewards strictly from `deltaVi = endVi - beginVi`. The result is a permanent loss (freezing) of legitimately-owed voter rewards, without any admin recovery mechanism — matching the "permanent freezing of funds" impact class.

### Likelihood Explanation
Requires a specific, adversary-influenceable condition: a witness's total vote count is `0` (or briefly zero due to vote churn) exactly at the moment `doMaintenance()` runs for the cycle in which that witness still received block/transaction-fee rewards. This is a narrow timing condition rather than something trivially reproducible by any transaction on every block, so likelihood is lower than the original report's more direct/common zero-liquidity scenario, but it is reachable purely through standard user actions (unfreeze/vote-withdrawal transactions) without any privileged access.

### Recommendation
In `DelegationStore.accumulateWitnessVi()` (and the duplicate logic in `RewardViCalService.accumulateWitnessVi()`), when `voteCount == 0` but `reward > 0`, do not silently drop the reward: either (a) roll the undistributed `reward` forward into the next cycle's reward pool for that witness so it eventually gets divided by a non-zero vote count, or (b) redirect it to the witness's own `allowance`/an admin-recoverable pool instead of discarding it.

### Proof of Concept
1. Attacker (or any voter) votes for a witness `W` with a positive `voteCount`, enabling `W` to be elected/active and receive block/transaction-fee rewards in cycle `N` via `MortgageService.payReward()` → `DelegationStore.addReward(N, W, value)`.
2. Before the maintenance boundary for cycle `N` is finalized, the voter withdraws/cancels the vote by calling `unfreezeBalanceV2` such that `UnfreezeBalanceV2Actuator.updateVote()` clears `W`'s votes (`totalVote == 0` path), driving `witness.getVoteCount()` to `0` at the time `MaintenanceManager.doMaintenance()` runs.
3. `doMaintenance()` calls `delegationStore.accumulateWitnessVi(N, W, 0)`.
4. Inside `accumulateWitnessVi`, since `voteCount == 0`, the previously stored `reward` for cycle `N` is never divided into `vi`; `vi` is left unchanged (forwarded).
5. No account can ever claim that cycle's reward via `queryReward`/`withdrawReward`, since those functions rely solely on `deltaVi` from `getWitnessVi`. The reward is permanently unaccounted for. [3](#0-2)

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
