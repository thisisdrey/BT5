### Title
Unbounded Memory Allocation from Attacker-Controlled Array Length in TVM `BatchValidateSign`/`ValidateMultiSign` Precompiles - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The Lasso CVE is a memory-depletion DoS caused by trusting an attacker-supplied length field to allocate memory before validating it against the real payload size. The analogous pattern exists in java-tron's `extractBytesArray` and `extractBytes32Array` helpers used by the `BatchValidateSign` and `ValidateMultiSign` TVM precompiled contracts, which allocate a Java array sized directly from an attacker-controlled 256-bit calldata word, with the only bound check gated behind an optional hard-fork flag.

### Finding Description
`extractBytesArray` and `extractBytes32Array` read a length directly from decoded calldata words and immediately allocate an array of that size, with no upper bound check inside the helper itself: [1](#0-0) 

`recoverAddrBySign`/`extractBytes`/etc. are only reached after this allocation, so the allocation itself happens unconditionally once these helpers are invoked.

In `ValidateMultiSign.execute`, the `MAX_SIZE` (5) bound on the derived length is enforced only when `VMConfig.allowTvmSelfdestructRestriction()` is true; when that hard-fork flag is not active, `extractBytesArray` is invoked directly with the unbounded, attacker-controlled length: [2](#0-1) 

In `BatchValidateSign.doExecute`, the same pattern applies to the signature array, and critically, `extractBytes32Array` (used to build the `addresses` array) is **always called unconditionally**, regardless of `allowTvmSelfdestructRestriction`, and has no length bound anywhere in its own code: [3](#0-2) 

Both precompiles are reachable from `Program.callToPrecompiledAddress`, which is invoked by the `CALL`/`DELEGATECALL` TVM opcodes whenever contract bytecode targets the precompile address; the only gate before `execute()` runs is an energy check computed from `data.length`, not from the decoded length field: [4](#0-3) 

Because the energy cost formulas (`getEnergyForData`) are based on `data.length / WORD_SIZE`, an attacker can craft a *short* calldata buffer (cheap in energy) whose header word specifies an enormous `len` value (up to `Integer.MAX_VALUE` via `DataWord.intValueSafe()`), triggering `new byte[len][]`, which requests gigabytes of heap for the reference array before any bounds validation against the real, tiny data buffer occurs.

### Impact Explanation
A single crafted smart-contract deployment/invocation (fully controlled by any unprivileged transaction broadcaster or contract deployer) can force the TVM to attempt allocation of an array on the order of `Integer.MAX_VALUE * 8` bytes (~17 GB on typical 64-bit JVMs) inside `extractBytesArray`/`extractBytes32Array`. This can trigger `OutOfMemoryError`, sustained GC pressure, or JVM/process instability on any full node or witness that executes the transaction, matching the "node crash/halt" impact bar for this analog class — directly analogous to the Lasso memory-depletion DoS (crafted message → uncontrolled memory allocation → denial of service).

### Likelihood Explanation
Likelihood is High for nodes/networks where the `allowTvmSelfdestructRestriction` chain parameter has not been activated (the code paths and tests, e.g. `testTip854PreActivationNoOp`, explicitly preserve and exercise this legacy, unguarded behavior), and Certain for the `extractBytes32Array` address-array path in `BatchValidateSign`, which has no gate at all tied to `allowTvmSelfdestructRestriction`. Exploitation requires only a standard `TriggerSmartContract`/`CreateSmartContract` transaction invoking the precompile address with crafted calldata — no special privileges, keys, or network position are needed.

### Recommendation
- In `extractBytesArray` and `extractBytes32Array`, validate the decoded `len` against a strict maximum (e.g., the existing `MAX_SIZE` constants) and against the actual remaining `words.length`/`data.length` *before* allocating `new byte[len][]`, unconditionally (not gated behind `allowTvmSelfdestructRestriction`).
- Make the `sigArraySize`/`addrArraySize` bound checks in `ValidateMultiSign.execute` and `BatchValidateSign.doExecute` unconditional so `extractBytesArray`/`extractBytes32Array`/`extractSigArray` are never invoked with unvalidated lengths.
- Add negative-size/overflow checks (`len < 0 || len > MAX_SIZE`) prior to any array allocation derived from `DataWord.intValueSafe()`.

### Proof of Concept
1. Deploy (or call) a contract that issues a `CALL` to the `batchValidateSign` precompile address (`...020007` per the byte layout in `PrecompiledContracts`) with calldata shaped as:
   - word[0] = arbitrary hash
   - word[1] = offset pointing to a "signatures" array header
   - the array-length word at that offset = `0xFFFFFFFF` (or another huge int-safe value)
   - remaining calldata trimmed to the minimum header size so `getEnergyForData` reports a small energy cost.
2. Ensure the chain does not have `allowTvmSelfdestructRestriction` activated (default/legacy state) so the `MAX_SIZE` guard is skipped for the `signatures` extraction, and note `extractBytes32Array` for `addresses` is unconditionally unguarded.
3. Submit this as a `TriggerSmartContract`/`CreateSmartContract` transaction from any unprivileged account.
4. On execution, `extractBytesArray`/`extractBytes32Array` executes `new byte[len][]` with `len` derived from the crafted word, causing a multi-gigabyte allocation attempt and `OutOfMemoryError`/node instability on every node that processes the transaction.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
