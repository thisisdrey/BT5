### Title
Bancor-relay exchange pool can be drained past its actual reserves due to unchecked floating-point calculation, producing a negative/insolvent token balance - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java)

### Summary
`ExchangeTransactionActuator`/`ExchangeCapsule.transaction()` lets any unprivileged account swap tokens against a TRC10 Bancor-relay pool. In the default (non-hardened) code path the swap amount is computed by `ExchangeProcessor`, which relies on `double`-precision `Math.pow` arithmetic, and the resulting new pool balances are written back **without any check that they remain non-negative**. Because the “hardened” fix (`SafeExchangeProcessor` + the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` guard) is gated behind the `allowHardenExchangeCalculation` dynamic parameter (default off), the production path is still exposed to a scenario functionally analogous to the GammaProtocol bug: the on-chain accounting can promise more of an asset than the pool actually owns — an unbacked, insolvent liability created purely by normal (extreme) trading activity, not by any privileged actor.

### Finding Description
`ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())`. [1](#0-0) 

Inside `ExchangeCapsule.transaction()`, when `hardenedCalc` is `false` (the default, since `allowHardenExchangeCalculation` must be explicitly enabled via committee proposal), the buy quantity is computed by the legacy `ExchangeProcessor`, and the new balances are simple `long` arithmetic with **no negativity check**: [2](#0-1) 

`ExchangeProcessor` performs the Bancor relay math with `double`/`Math.pow`, which is inherently imprecise for extreme reserve ratios or large trade sizes: [3](#0-2) 

The codebase’s own regression tests acknowledge this: the “hardened” `SafeExchangeProcessor` (BigDecimal-based) is explicitly tested to guarantee `result <= buyTokenBalance` for a battery of inputs, a guarantee that is not asserted for the legacy processor: [4](#0-3) 

and a dedicated test demonstrates that only the hardened path rejects a resulting negative pool balance: [5](#0-4) 

If a caller crafts a trade (extreme sell quantity relative to pool reserves) such that the floating-point Bancor computation returns a `buyTokenQuant` slightly larger than the pool’s true implied capacity, the non-hardened path subtracts it from `secondTokenBalance`/`firstTokenBalance` unchecked, driving the persisted pool balance negative (or to an inflated positive on the sell side) while crediting the trader’s account with `addAssetAmountV2`: [6](#0-5) 

This is functionally the java-tron analog of the GammaProtocol issue: the protocol’s internal accounting (the `Exchange`/`ExchangeV2` capsule reserve) can end up promising more tokens than physically exist in the vault/pool, purely as a consequence of the mathematics used to price trades under natural (large) trade volume — no admin action, oracle manipulation, or malicious SR/witness involvement is required, and the attack surface is a single signed `ExchangeTransactionContract` broadcast by any account.

### Impact Explanation
An insolvent exchange pool means the sum of all account claims on `firstTokenID`/`secondTokenID` recorded via the exchange mechanism exceeds the actual reserves the pool represents. Later legitimate participants withdrawing (`ExchangeWithdrawActuator`) or trading against the pool would fail or receive fewer tokens than entitled, and the attacker who triggered the negative-balance trade walks away with tokens effectively minted out of nothing — a permanent, unbacked-balance / theft-of-funds condition. This satisfies the "unbacked balance" / "theft of funds" bar in the validation criteria.

### Likelihood Explanation
Reaching the vulnerable path requires only creating an exchange pool (`ExchangeCreateContract`), an ordinary permissionless operation, and issuing an `ExchangeTransactionContract` with a sell quantity engineered to push the double-precision Bancor formula outside its safe precision range relative to pool reserves. Because `allowHardenExchangeCalculation` defaults to off, the vulnerable legacy `ExchangeProcessor` is the actual code path exercised on-chain today. Exploitability depends on finding reserve ratios/quantities where the `double` computation error exceeds one unit of the buy token, which is plausible for small-reserve or heavily skewed pools (an attacker fully controls pool creation and trade parameters).

### Recommendation
- Enable (or make default/mandatory) the hardened `SafeExchangeProcessor` path and the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` guard for **all** exchange transactions, not gated behind an optional proposal.
- Alternatively/additionally, add the same non-negativity assertion to the legacy path in `ExchangeCapsule.transaction()` regardless of `hardenedCalc`, rejecting any trade whose computed balances would go negative or whose `buyTokenQuant` exceeds the counter-side reserve.
- Add fuzz/property tests asserting `buyTokenQuant <= buyTokenBalance` for the legacy (non-hardened) `ExchangeProcessor` across a wide range of reserve ratios, not only for `SafeExchangeProcessor`.

### Proof of Concept
1. Create a TRC10/TRX exchange pool with small, imbalanced reserves via `ExchangeCreateActuator` (`ExchangeCreateContract`), e.g. `firstTokenBalance = X`, `secondTokenBalance = Y` chosen to maximize floating point error in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` (see `Math.pow` usage).
2. Ensure `allowHardenExchangeCalculation` is not enabled (default state) so `ExchangeTransactionActuator` uses the legacy `ExchangeProcessor` path.
3. Submit an `ExchangeTransactionContract` selling a quantity of the sparse-reserve token that drives the Bancor `Math.pow` computation into a region where double-precision error causes `buyTokenQuant` to exceed the true counter-reserve implied by the formula.
4. Observe that `ExchangeCapsule.transaction()` persists `newSecondTokenBalance = secondTokenBalance - buyTokenQuant` (or the symmetric first-token case) without any negativity check, while the trader’s account is credited the full `buyTokenQuant` via `addAssetAmountV2`, exactly as covered (for the hardened-only guard) by `ExchangeCapsuleTest.testHardenedTransactionNegativeBalanceThrows`, which confirms the negative-balance condition is only rejected when `hardenedCalc=true`. [5](#0-4)

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
