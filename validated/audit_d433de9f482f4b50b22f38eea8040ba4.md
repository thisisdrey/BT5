### Title
Malicious StackerDB replica peer serving forged chunks is only temporarily unpinned and gets re-selected as a download source in subsequent sync rounds - ([File: stackslib/src/net/stackerdb/sync.rs])

### Summary
`getchunks_try_finish` calls `self.unpin_connected_replica(network, &naddr)` only when a chunk fails `validate_downloaded_chunk`, which removes the peer from the *current round's* `connected_replicas`/priority state, but `StackerDBSync` keeps no persistent blocklist of misbehaving peers. Because the next round's replica set is rebuilt from `PeerDB` (via `find_qualified_replicas`/`find_new_replicas`) rather than from a permanent reputation list, a peer that is unpinned in round N can be re-discovered and re-selected as a download source in round N+1, allowing it to repeatedly serve forged chunks and consume schedule slots indefinitely.

### Finding Description
The state machine's chunk-fetch stage validates each received `StackerDBChunk` in `getchunks_try_finish`: [1](#0-0) 
On validation failure it calls `unpin_connected_replica`, which removes the neighbor from the sync's in-round bookkeeping (`connected_replicas` / priorities), not from any durable ban list.

The struct only tracks transient per-round state: `replicas`, `connected_replicas`, and `stale_neighbors` (populated from NACK codes), none of which persist a "known-bad" designation across `reset()` calls: [2](#0-1) 

When a round completes, `reset()` is invoked and the next round's peer set is recomputed via `find_new_replicas`, which takes whatever `connected_replicas` remained plus freshly-queried candidates from `PeerDB::find_stacker_db_replicas` (i.e., any known replica for the contract, regardless of prior bad behavior) and shuffles/refills up to `max_neighbors`: [3](#0-2) 

Because the malicious peer remains a legitimate, discoverable StackerDB replica in `PeerDB` (it still holds its slot / advertised replica status), nothing prevents `find_qualified_replicas` from re-adding it to the pool for the next round, and nothing in the priority-selection logic in `getchunks_begin` excludes previously-unpinned addresses beyond the current round. The only state that survives across rounds and could suppress a peer is `stale_neighbors`, which is populated solely from `NackErrorCodes::StaleView`/`FutureView`, not from validation failures.

### Impact Explanation
A single always-forging peer can occupy one of the bounded in-flight chunk-request slots (`MAX_CHUNKS_IN_FLIGHT = 6`) every round indefinitely, since it is re-selected after being dropped for only one round. This delays legitimate chunk retrieval and wastes request capacity/bandwidth on every sync cycle without ever being permanently excluded — a bounded compute/availability degradation on the StackerDB sync path, consistent with a "bounded compute DoS" classification. It does not cause a crash, does not corrupt stored state (the forged chunk is rejected by `validate_downloaded_chunk` and never stored), and does not let the attacker write unauthenticated data.

### Likelihood Explanation
The attacker only needs to be a normal P2P peer that is discoverable as a StackerDB replica (no privileged role, no secret) and consistently respond to `StackerDBGetChunkData` with a chunk carrying a bad signature. This is fully remote, requires no special timing, and is repeatable every sync round at negligible attacker cost — the peer just needs to remain reachable and keep serving invalid chunks.

### Recommendation
Maintain a persistent negative-reputation / blocklist keyed by `NeighborAddress` (or public key) for peers that fail chunk validation, with a cooldown or exponential backoff before they are eligible for re-selection in `find_new_replicas`/`find_qualified_replicas`, similar to how `stale_neighbors` is tracked but surviving across `reset()` calls rather than being cleared each round.

### Proof of Concept
Rust test in `stackslib::net::stackerdb::tests::sync`:
1. Set up a `StackerDBSync` with a mock `NeighborComms` where a single fake neighbor `naddr` always replies to `StackerDBGetChunk` with a `StackerDBChunkData` containing a corrupted/bad signature.
2. Round 1: drive `getchunks_begin` → `getchunks_try_finish`; assert `naddr` is removed from `self.connected_replicas` after `unpin_connected_replica` fires (validation fails at line 1164/1172).
3. Call `reset(Some(&network), &config)` to simulate moving to round 2, then invoke `find_new_replicas`/the discovery path that repopulates `connected_replicas` from `PeerDB`.
4. Round 2: assert `naddr` is present again in `self.chunk_fetch_priorities` and gets re-selected in `getchunks_begin`, proving it re-enters the download schedule after being unpinned only one round earlier — confirming there is no persistent exclusion.

    fn find_new_replicas(
        &self,
        mut connected_replicas: HashSet<NeighborAddress>,
        network: Option<&PeerNetwork>,
        config: &StackerDBConfig,
    ) -> Result<HashSet<NeighborAddress>, net_error> {
        // keep all connected replicas, and replenish from config hints and the DB as needed
        let mut peers = config.hint_replicas.clone();
        if let Some(network) = network {
            let extra_peers = self.find_qualified_replicas(network)?;
            peers.extend(extra_peers);
        }

        peers.shuffle(&mut thread_rng());

        for peer in peers {
            if connected_replicas.len() >= config.max_neighbors {
                break;
            }
            connected_replicas.insert(peer);
        }
        Ok(connected_replicas)
    }
