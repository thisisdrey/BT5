### Title
Unsanitized `tar` extraction of an attacker-influenced HTTP source in `CreateRepositoryFromSnapshot` allows storage-escaping writes - (File: internal/gitaly/service/repository/create_repository_from_snapshot.go)

### Summary
The `CreateRepositoryFromSnapshot` RPC fetches an archive from a caller-supplied `HttpUrl` and extracts it directly onto disk using the external `tar` binary with no path validation, no symlink checks, and no verification that the archive actually belongs to (or was produced from) a legitimate Gitaly repository. This mirrors the H-11 root cause: a privileged operation (writing arbitrary content into a repository's on-disk storage) is driven entirely by attacker-controlled/external data whose values are trusted without any authenticity or bounds check.

### Finding Description
`CreateRepositoryFromSnapshot` performs an HTTP GET against `in.GetHttpUrl()` and pipes the response body straight into `tar -C path -xvf -`: [1](#0-0) 

The code comment itself acknowledges the trust problem ("the received archive is trusted *a lot*"), but no mitigation is implemented: there is no verification that archive entries stay within the destination `path`, no rejection of symlinks/hardlinks, and no check that the fetched content is actually a Git object/ref/config snapshot rather than arbitrary files: [2](#0-1) 

By contrast, the analogous, better-audited path in `replicate.go` (`extractTarToDirectory`) explicitly validates every tar entry — regular files, directories, symlinks, and hard links — against the target directory boundary before writing, precisely to prevent this class of bug: [3](#0-2) [4](#0-3) 

`CreateRepositoryFromSnapshot`'s reliance on the raw system `tar` binary instead of this vetted, in-repo extraction logic means path/symlink escape protection depends entirely on the installed `tar` implementation's default behavior (which varies across GNU/BSD tar versions and configurations), rather than on an explicit, testable Gitaly-side guarantee.

Additionally, the archive is not scoped to a repository identity: any HTTP endpoint reachable via `HttpUrl` (already partially covered for SSRF via `ResolvedAddress` pinning, but still attacker-influenced content) can supply the tar stream that is unpacked as the target repository's entire on-disk state, with no validation that the content is a valid or intended Git repository payload beyond initializing an empty bare repo first.

### Impact Explanation
If the `tar` binary in the deployed environment does not fully neutralize `..`-relative paths, absolute paths, or malicious symlinks/hardlinks in archive entries (a documented weakness in older/`bsdtar`/some GNU tar configurations and in tar wrappers that pass extra flags), a crafted response from the `HttpUrl` endpoint can write or overwrite files outside the intended repository directory, on the Gitaly storage shard — a storage escape. This is functionally the same class of "unchecked external actor supplies fully attacker-controlled inputs used directly in a sensitive, storage-affecting operation without any authenticity check" that H-11 flags for `RewardsManager.updateBucketExchangeRatesAndClaim`.

### Likelihood Explanation
`CreateRepositoryFromSnapshot` is a `MUTATOR` RPC that accepts a `Repository` target plus an arbitrary `HttpUrl`/`HttpAuth`/`ResolvedAddress`. Exploitation requires the calling party (e.g., GitLab Rails, or any client authorized to call Gitaly RPCs for repository creation/import flows) to be able to point `HttpUrl` at content the attacker controls (e.g., a project import/migration flow, a compromised or malicious source instance). This is more constrained than a fully anonymous push/fetch, but it is reachable through the ordinary "import/create repository from snapshot" surface rather than a privileged operator console, and the code's own comment flags it as intentionally unhardened.

### Recommendation
- Replace the raw `tar -C path -xvf -` invocation with the same vetted, entry-by-entry validated extraction logic already implemented in `replicate.go`'s `extractTarToDirectory`/`extractFile` (path containment checks for regular files, dirs, symlinks, and hardlinks), instead of delegating to an external `tar` binary whose escape-prevention behavior isn't guaranteed by Gitaly.
- Reject or normalize absolute paths, `..` components, and symlink/hardlink entries whose resolved target escapes the destination directory.
- Consider restricting or authenticating the source of `HttpUrl` snapshots (e.g., requiring the operation to only be triggered by trusted internal replication flows rather than caller-suppliable arbitrary URLs), consistent with how `FetchRemote`/`UpdateRemoteMirror` handle DNS-rebinding via `ResolvedAddress` pinning.
- Remove or downgrade the "trusted a lot" acknowledgment once proper hardening lands, and add regression tests analogous to `TestExtractTarToDirectory_SymlinkValidation` in `replicate_test.go`.

### Proof of Concept
Not independently verified against a live Gitaly instance in this analysis (no code execution/tooling access here); the vulnerability is inferred structurally from the source:
1. Attacker (or malicious/compromised endpoint referenced by `HttpUrl`) serves a tar stream containing an entry such as `../../../etc/cron.d/evil` (or a symlink entry pointing outside the target directory followed by a regular-file entry through that symlink).
2. Client calls `CreateRepositoryFromSnapshot` with `Repository` set to a target repo path and `HttpUrl` pointing at the malicious server.
3. `untar` fetches the body and executes `tar -C <repoPath> -xvf -` with no additional flags such as `--no-same-owner`, `-P`-disabling, or explicit path containment; depending on the tar binary's version/config, the malicious entries are written outside `<repoPath>`.
Verification would require running the actual RPC against a Gitaly build with a controllable `tar` binary/version to confirm escape behavior, which the reasoning here could not execute directly.

func (s *server) untar(ctx context.Context, path string, in *gitalypb.CreateRepositoryFromSnapshotRequest) error {
	req, err := http.NewRequestWithContext(ctx, "GET", in.GetHttpUrl(), nil)
	if err != nil {
		return structerr.NewInvalidArgument("Bad HTTP URL: %w", err)
	}

	client := httpClient
	if resolvedAddress := in.GetResolvedAddress(); resolvedAddress != "" {
		client, err = newResolvedHTTPClient(in.GetHttpUrl(), resolvedAddress)
		if err != nil {
			return structerr.NewInvalidArgument("creating resolved HTTP client: %w", err)
		}
	}

	if in.GetHttpAuth() != "" {
		req.Header.Set("Authorization", in.GetHttpAuth())
	}

	rsp, err := client.Do(req)
	if err != nil {
		return structerr.NewInternal("HTTP request failed: %w", err)
	}
	defer rsp.Body.Close()

	if rsp.StatusCode < http.StatusOK || rsp.StatusCode >= http.StatusMultipleChoices {
		return structerr.NewInternal("HTTP server: %s", rsp.Status)
	}

	cmd, err := command.New(ctx, s.logger, []string{"tar", "-C", path, "-xvf", "-"}, command.WithStdin(rsp.Body))
	if err != nil {
		return err
	}

	return cmd.Wait()
}

func (s *server) extractTarToDirectory(ctx context.Context, reader io.Reader, targetDir string) error {
	targetDir = filepath.Clean(targetDir)
	tarReader := tar.NewReader(reader)

	for {
		select {
		case <-ctx.Done():
			return ctx.Err()
		default:
		}

		header, err := tarReader.Next()
		if err == io.EOF {
			break // End of archive
		}
		if err != nil {
			return fmt.Errorf("reading tar header: %w", err)
		}

		targetPath := filepath.Join(targetDir, header.Name)

		if !strings.HasPrefix(targetPath, targetDir+string(os.PathSeparator)) &&
			targetPath != targetDir {
			return fmt.Errorf("invalid file path in tar: %s", header.Name)
		}
