## Analysis Summary

The strongest analog in this repo to CVE-2018-14460 (heap-based buffer over-read in HDF5's `H5O_sdspace_decode` from an unchecked size field while decoding a data-space message) is in Bazel's **ijar** ZIP central-directory decoder.

### Title
Heap-based buffer over-read in ZIP central directory decoding due to missing bounds checks - (File: `third_party/ijar/zip.cc`)

### Finding Description
`InputZipFile::ProcessCentralDirEntry` (used by `ijar`, which Bazel runs on every Java library/import dependency jar to strip it into an interface jar) decodes central-directory record fields (`file_name_length`, `extra_field_length`, `file_comment_length`) and then blindly advances the cursor and dereferences memory without ever validating that these attacker-controlled 16-bit lengths stay inside the mapped file bounds. [1](#0-0) 

In particular, the extra-field walk:
```
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
```
lets a crafted `data_size` make `extra_p` skip past `p` (the extra-field end), so the `while (extra_p != p)` loop condition never becomes false; it continues dereferencing `get_u2le`/`get_u8le` far beyond the intended extra-field/central-directory bounds — and, since the whole file is `mmap`'d, beyond the end of the mapped region entirely. [2](#0-1) 

This is directly comparable to `InputZipFile::ProcessLocalFileEntry`, which validates every variable-length field with `EnsureRemaining()` before reading it. [3](#0-2) 
No equivalent check exists for the central directory path, which is invoked in a tight loop by both `ProcessNext()` and `CalculateOutputLength()`. [4](#0-3) [5](#0-4) 

### Impact Explanation
An attacker who publishes a malicious `.jar`/`.zip` (e.g., served at a `http_jar`/`http_archive` URL, matching its own self-computed `sha256`) supplies content that passes Bazel's download integrity check unchanged — the checksum only guarantees the bytes are exactly what the attacker crafted, not that they are well-formed. When Bazel's Java rules process this dependency, `ijar` mmaps the file and walks the central directory via `ProcessCentralDirEntry`. A crafted extra-field entry with an oversized `data_size` causes the decoder to read past the end of the mmap'd region, producing a heap/mapping-based buffer over-read that can crash the build (SIGSEGV on an unmapped page) or, before crashing, read adjacent process memory into computed size/offset values later used in `memcpy`/pointer arithmetic (`filename`, zip64 sizes), risking further memory-safety violations or information disclosure into build artifacts.

### Likelihood Explanation
`ijar` runs unconditionally on every `.jar` dependency consumed by Java build rules (`java_import`, `java_library` deps, `http_jar`), so any single malicious dependency jar reachable through a build graph triggers this path with default flags — no special configuration is required, and the attacker only needs to control the bytes served at a URL they already control (satisfying "unprivileged, publishes content the victim's build consumes").

### Recommendation
Add explicit bounds validation (mirroring `EnsureRemaining()` from `ProcessLocalFileEntry`) in `ProcessCentralDirEntry` before reading `file_name_length`, `extra_field_length`, `file_comment_length`, and before each extra-field sub-record's `data_size`, ensuring `extra_p + data_size <= p` and `p` never exceeds the mapped file end; on violation, return a decode error instead of continuing to advance/dereference the pointer.

### Proof of Concept
A C++ test analogous to the existing `CreateZipWithMalformedExtraField` helper (already used to test singlejar's `output_jar_simple_test.cc`) can be added for ijar: construct an in-memory ZIP whose central directory header declares an extra field containing a sub-record with `data_size` far exceeding the remaining extra-field bytes, feed it to `ZipExtractor::ProcessNext()`/`CalculateOutputLength()`, and assert that the call returns a decode error (via `GetError()`) instead of crashing or reading out of bounds (verifiable under ASan, which will flag the heap-buffer-overflow-read at the `get_u2le`/`get_u8le` calls inside the `while (extra_p != p)` loop). [6](#0-5)

  u8 compressed, uncompressed;
  u8 offset;
  if (!ProcessCentralDirEntry(central_dir_current_, &compressed, &uncompressed,
                              filename, PATH_MAX, &attr, &offset)) {
    return false;
  }

  // There might be an offset specified in the central directory that does
  // not match the file offset, so always update our pointer.
  p = zipdata_in_ + in_offset_ + offset;

  if (EnsureRemaining(4, "signature") < 0) {
    return false;
  }
  u4 signature = get_u4le(p);
  if (signature == LOCAL_FILE_HEADER_SIGNATURE) {
    if (ProcessLocalFileEntry(compressed, uncompressed) < 0) {
      return false;
    }
  } else {
    error("local file header signature for file %s not found\n", filename);

  }

  return true;

u8 InputZipFile::CalculateOutputLength() {
  const u1* current = central_dir_;

  u8 compressed_size = 0;
  u8 uncompressed_size = 0;
  u8 skipped_compressed_size = 0;
  u4 attr;
  u8 offset;
  char filename[PATH_MAX];

  while (true) {
    u8 file_compressed, file_uncompressed;
    if (!ProcessCentralDirEntry(current,
                                &file_compressed, &file_uncompressed,
                                filename, PATH_MAX, &attr, &offset)) {
      break;
    }

    if (processor->Accept(filename, attr)) {
      compressed_size += (u8) file_compressed;
      uncompressed_size += (u8) file_uncompressed;
    } else {
      skipped_compressed_size += file_compressed;
    }
  }

  // The worst case is when the output is simply the input uncompressed. The
  // metadata in the zip file will stay the same, so the file will grow by the
  // difference between the compressed and uncompressed sizes.
  return (u8) input_file_->Length() - skipped_compressed_size
      + (uncompressed_size - compressed_size);
}

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
