### Title
`liquidate` reverts when `amountToRepay_` exceeds current debt, enabling front-running DoS of full liquidations - (File: contracts/Pool.sol)

### Summary
`Pool.liquidate` reverts whenever `amountToRepay_` is greater than the account's current debt balance, because the `maxLiquidable` bound treats any over-repayment as exceeding 100% of the debt. An unprivileged attacker holding a dust amount of the synthetic token can front-run a full-debt liquidation with a minimal `liquidate` call, lowering the victim's debt so the original transaction reverts. This can be repeated every block, griefing liquidators who pass a fixed (full-repayment) amount.

### Finding Description
In `Pool.liquidate` the check at `contracts/Pool.sol:567` is:

```solidity
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}
```

Since `maxLiquidable <= 1e18` (HUNDRED_PERCENT), any `amountToRepay_ > _debtTokenBalance` reverts. The same over-repayment would also revert later at the debt-floor check `contracts/Pool.sol:574` (`_debtTokenBalance - amountToRepay_` underflows) and at `DebtToken._burn` via `BurnAmountExceedsBalance` (`contracts/DebtToken.sol:529`).

Attack trace (all unprivileged calls):

1. Victim has debt `D` in `msETH` and is unhealthy. Liquidator submits `pool.liquidate(msEth, victim, D, msdMET)` (e.g., amount computed off-chain or via `quoteLiquidateMax`).
2. Attacker front-runs with `pool.liquidate(msEth, victim, 1, msdMET)` (or `debtToken.repay(victim, dust)`). To obtain a dust amount of `msEth`, the attacker simply deposits collateral and calls `DebtToken.issue` on their own position — fully unprivileged.
3. The victim's debt is now `D - 1`. The liquidator's tx computes `wadDiv(D, D - 1) > 1e18 >= maxLiquidable` and reverts with `AmountGreaterThanMaxLiquidable`.
4. The attacker repeats step 2 every block indefinitely at negligible cost (each dust liquidation also earns them a liquidation incentive on the dust amount).

The analogous `DebtToken.repay` path at `contracts/DebtToken.sol:444-447` suffers the same issue (`balanceOf - _repaid` underflow / `BurnAmountExceedsBalance`), making `repay`-based keepers equally griefable.

### Impact Explanation
Temporary denial of the liquidation path for any liquidation sized as a fixed/full repayment. Since the attacker can re-run the dust liquidation each block, liquidators are forced to either repeatedly recompute shrinking amounts (and race interest accrual in `accrueInterest`/`balanceOf`, which itself shifts `D` upward each block) or submit partial liquidations. Delayed liquidation of deteriorating positions lets bad debt accumulate, weakening protocol solvency. This matches the accepted impact classes: temporary freezing of the liquidation function / contribution to protocol insolvency.

### Likelihood Explanation
- No privileged role required: the attacker only needs a dust balance of the synthetic token, obtainable via their own `issue` position or an AMM swap.
- Cost is near zero per front-run; the dust liquidation even pays out the `liquidatorIncentive` pro-rata.
- Interest accrual makes the problem worse: `balanceOf` grows every block, so a fixed `amountToRepay_` computed in a prior block is already stale — even honest liquidations can revert without an attacker. This makes the DoS cheap to sustain, though a sophisticated liquidator can use `max_uint`-style recomputation or bundle with `quoteLiquidateMax` in the same tx via `Operator.execute`/multicall, so impact is capped at Medium-level liveness degradation rather than permanent freezing.

### Recommendation
Clamp the repayment instead of reverting, mirroring the report's fix:

```solidity
// contracts/Pool.sol, after _debtTokenBalance is read
if (amountToRepay_ > _debtTokenBalance) {
    amountToRepay_ = _debtTokenBalance;
}
```

Apply the same clamp in `DebtToken.repay` (`_repaid = min(_repaid, balanceOf(onBehalfOf_))`) so over-payments return gracefully instead of reverting on underflow/`BurnAmountExceedsBalance`.

### Proof of Concept
Hardhat test sketch (extends `test/Pool.test.ts` liquidation setup where `alice` is unhealthy with `userMintAmount` msETH debt):

```ts
it('griefs full liquidation via dust front-run', async function () {
  // attacker obtains dust msEth via own collateralized position
  await msEthDebtToken.connect(griefer).issue(parseEther('0.001'), griefer.address); // after depositing own collateral

  const debt = await msEthDebtToken.balanceOf(alice.address);

  // front-run: repay 1 wei of alice's debt
  await pool.connect(griefer).liquidate(msEth.address, alice.address, 1, msdMET.address);

  // liquidator's full-repay tx now reverts
  const tx = pool.connect(liquidator).liquidate(msEth.address, alice.address, debt, msdMET.address);
  await expect(tx).revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');

  // repeatable: griefer dust-liquidates again next block
});
```
