### Title
`action_delete_account` deletes accounts and burns `Account.locked` (staked) balance instead of refunding it - (`runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` computes the payout to the beneficiary strictly from `account_ref.amount()` and never inspects or transfers `account_ref.locked()`. The account is then fully removed via `remove_account`, so any non-zero locked/staked balance is permanently destroyed rather than refunded to the beneficiary or the amount balance.

### Finding Description
In `runtime/runtime/src/actions.rs`, `action_delete_account` (lines 314-390) performs storage-usage checks and gas-key checks, then computes the payout: [1](#0-0) 
```
// We use current amount as a pay out to beneficiary.
let account_balance = account_ref.amount();
if account_balance > Balance::ZERO {
    result.new_receipts.push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
}
```
There is no check on `account_ref.locked()` anywhere in this function, no error kind analogous to a "cannot delete while staking" rejection, and no additional receipt/refund path that accounts for locked funds. After the payout computation, `remove_account` deletes the account state entirely and `*account = None`, so the locked value is not persisted or moved anywhere. This is a genuine gap: a value-conservation invariant (all `Balance` fields of a deleted `Account` must end up either refunded or explicitly burned/accounted in `tokens_burnt`) is violated for the `locked` field.

I was not able to fully verify, within the available tool budget, whether `check_actor_permissions` (referenced in the question) is the mechanism that is supposed to gate this deletion and whether it is scoped to `actor_id` vs. the target account, since I could not read its full body. However, that detail is not necessary to establish the core bug: the missing `locked` handling in `action_delete_account` is directly visible in the code and applies regardless of who the actor is (self-delete via a contract's own `FunctionCall` invoking `promise_batch_action_delete_account(current_account_id, beneficiary)`, or an authorized full-access-key `DeleteAccount` action).

### Impact Explanation
This falls under permanent token loss / token burn without accounting: staked (locked) NEAR tied to an account is destroyed when the account self-deletes, with no compensating `tokens_burnt` accounting and no refund receipt. This matches the "token inflation or loss" bounty category (in this case, loss / unaccounted burn) rather than theft, since the funds vanish rather than being redirected to an attacker-controlled beneficiary.

### Likelihood Explanation
Preconditions are attacker-affordable: fund an account, deploy a WASM contract that issues a `Stake` action targeting itself, wait for the stake to be reflected in `Account.locked` (this happens on stake-action processing, not requiring validator status), then have the same contract account issue a receipt with `DeleteAccountAction` (e.g., via `promise_batch_action_delete_account` from a `FunctionCall`). No privileged access, validator role, or node access is required — only ordinary transaction submission. This is repeatable per account instance and costs only the staked amount that is destroyed (a loss to the attacker unless they intended to burn/hide funds, e.g., to avoid storage-staking obligations or manipulate accounting elsewhere), but the impact class (silent, unaccounted token destruction and violation of value-conservation invariants) is a valid finding regardless of attacker's own incentive.

### Recommendation
In `action_delete_account`, before allowing deletion (or as part of the payout computation), check `account_ref.locked()`. Either:
1. Reject the deletion with a new `ActionErrorKind::DeleteAccountStaking`-style error while `locked() > 0`, forcing the account to fully unstake first, or
2. Include `account_ref.locked()` in the beneficiary payout (`account_balance = account_ref.amount().checked_add(account_ref.locked())`) and add it to `result.tokens_burnt`/refund accounting so the balance is conserved.

### Proof of Concept
Add a runtime/test-loop integration test in `runtime/runtime/tests/` or `test-loop-tests/src/tests/create_delete_account.rs`:
1. Create an account with a deployed contract; fund it.
2. Submit a `Stake` action for that account with `amount = X`, and advance state so `Account.locked == X` (verify via `get_account` after the stake action is applied, without needing to cross an epoch boundary if `action_stake` sets `locked` synchronously).
3. Have the contract issue `promise_batch_action_delete_account(current_account_id, beneficiary_id)` via a `FunctionCall`, producing a `DeleteAccountAction` receipt.
4. Apply the receipt and assert:
   - The account no longer exists.
   - Beneficiary's balance increased by exactly `amount + locked` (expected correct behavior), or the transaction result is an `ActionError` rejecting deletion while `locked > 0` (alternate correct behavior).
   - Currently (bug reproduction): beneficiary only receives `amount`, and `locked` (`X`) is unaccounted for — not present in beneficiary balance, not present in `result.tokens_burnt`, demonstrating the value-conservation violation.
