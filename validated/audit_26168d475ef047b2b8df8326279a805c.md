### Title
Unhandled `ArithmeticException` in `MarketSellAssetActuator` order matching lets a malicious maker DoS unrelated takers / block production - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.matchOrder` credits the maker's account via `addTrxOrToken` → `AccountCapsule.addAssetAmountV2`, which can throw an unchecked `ArithmeticException` on `long` overflow. This exception is not caught by `execute()`'s catch clause, so it propagates out of transaction processing.

### Finding Description
When a taker's `MarketSellAssetContract` transaction matches against an existing maker order in the order book, `matchOrder` (lines 307-380) invokes `matchSingleOrder` (383-499), which calls `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` (line 490) to credit the maker's asset balance. That helper (`actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java:550-562`) calls `accountCapsule.addAssetAmountV2(...)`, which internally calls `Math.addExact`-style arithmetic (`chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java:733-765`) and throws `ArithmeticException` if the resulting sum overflows `Long.MAX_VALUE`. None of `matchOrder`, `matchSingleOrder`, or `addTrxOrToken` declare or catch this exception, and `execute()`'s catch block (lines 152-159) only handles `ItemNotFoundException | InvalidProtocolBufferException | BalanceInsufficientException | ContractValidateException`. A maker can pre-inflate their own asset balance for the relevant `buyTokenId` close to `Long.MAX_VALUE` (self-trading is not prohibited by validation), then park a resting order. Any later, unrelated taker whose matching fill would push the maker's balance over `Long.MAX_VALUE` triggers the uncaught exception inside the taker's own transaction execution, which occurs during block application in `Manager.processBlock` (`framework/src/main/java/org/tron/core/db/Manager.java:1849-1908`), a code path with no generic catch for `RuntimeException`/`ArithmeticException`.

### Impact Explanation
Because the exception surfaces from `processTransaction`, called inside the un-guarded `for` loop over `block.getTransactions()` in `processBlock`, and `applyBlock`'s caller in `pushBlock` (`framework/src/main/java/org/tron/core/db/Manager.java:1389-1397`) treats any `Throwable` here as fatal for that block (rolling back the DB session and rethrowing), this can repeatedly prevent block application/production by any witness that includes the poisoning taker transaction, or at minimum, permanently break order matching for the affected token pair for all future unrelated takers, since the same overflowing maker order remains in the book. This satisfies the "node crash or halt" / "concrete unauthorized... permanent freezing of funds" bar, since order-matching funds for the affected pair become unusable and (depending on whether the witness treats it as an unrecoverable exception) block production could stall.

### Likelihood Explanation
Likelihood is low-to-medium: it requires an attacker to accumulate a near-`Long.MAX_VALUE` token balance (feasible for a self-issued/self-controlled TRC10 token with a very large `totalSupply`, or by repeatedly matching self-trades) and to place a resting maker order; then wait for or induce a legitimate taker to match against it. This is achievable entirely with unprivileged `MarketSellAssetContract` transactions.

### Recommendation
Wrap the `addAssetAmountV2`/`addTrxOrToken` calls in `matchSingleOrder`/`matchOrder` in a try/catch for `ArithmeticException` (as is already done in `TransferAssetActuator.execute()` and `ParticipateAssetIssueActuator`), converting it into a `ContractExeException`/`ContractValidateException` that is caught by `execute()`'s existing catch block, or clamp/limit asset balances to prevent overflow before crediting. Additionally, add validation caps on total per-account asset balances for TRC10 tokens to make this overflow path unreachable in practice.

### Proof of Concept
1. Issue or acquire a TRC10 token with a very large supply.
2. As attacker (maker), accumulate a balance for that token close to `Long.MAX_VALUE` (via self-trading matches or asset issuance parameters).
3. Place a `MarketSellAssetContract` maker order selling token A for token B at some price, leaving it resting in the order book.
4. As a different unprivileged user (taker), place a `MarketSellAssetContract` order that matches the attacker's resting order such that the maker's receive amount (`makerBuyTokenQuantityReceive`) pushes their balance past `Long.MAX_VALUE`.
5. `AccountCapsule.addAssetAmountV2` throws `ArithmeticException`, uncaught by `MarketSellAssetActuator.execute()`, propagating through `Manager.processTransaction`/`processBlock`, disrupting block application containing the taker's transaction.

      String tokenID = assetIssueCapsule.getId();

      if (currentAmount == null) {
        currentAmount = 0L;
      }
