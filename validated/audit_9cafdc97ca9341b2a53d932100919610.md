### Title
Missing ownership binding in `LinkRepositoryToObjectPool`/`DisconnectGitAlternates` allows cross-repository object-pool linkage - ([File: internal/gitaly/service/objectpool/link.go])

### Summary
The `RubiconRouter` bug is a case of "ownership confusion": an action (offer creation) is performed *through* an intermediary, which becomes the recorded owner of the resulting resource, so the intermediary's own trust in "am I the owner" is later abused by a third party to cancel a resource they never created. The structural analog in Gitaly is the `ObjectPoolService`, where the "ownership" relationship between a pool and its member repository is never independently verified by Gitaly itself — the RPC blindly trusts whatever `Repository`/`ObjectPool` pair is supplied in the request, with no check that the pool was actually derived from (or previously associated with) that specific repository.

### Finding Description
`LinkRepositoryToObjectPool` takes two independent identifiers directly from the request — `req.GetRepository()` and `req.GetObjectPool()` — and the only validation performed is that each one resolves to a valid, existing Git repository under the storage root: [1](#0-0) 

`s.poolForRequest` and `s.locator.ValidateRepository` only check path validity/existence, not that the `ObjectPool` was created *from* `repository`, or that the caller is authorized to associate these two specific repositories. The actual linking logic in `Link()` likewise performs no ownership/provenance check — it merely writes the pool's relative object path into the repository's `objects/info/alternates` file: [2](#0-1) 

The same pattern exists for `DisconnectGitAlternates`, which accepts only a `Repository` and disconnects whatever alternate is currently configured, again with no verification that this repository's association with that alternate was legitimately established for it: [3](#0-2) 

The proto-level documentation and comments explicitly acknowledge the lack of any binding/safety checks — e.g. `DeleteObjectPool`: "There are no safety checks in place, so if any repository is still using this object pool it will become corrupted," and `DisconnectGitAlternates`/`LinkRepositoryToObjectPool` are described purely in terms of path operations, not ownership verification: [4](#0-3) [5](#0-4) 

This is the same class of bug as the RubiconRouter report: the component that performs a mutating operation binding two resources together (offer↔owner in Rubicon; repository↔pool in Gitaly) never itself verifies that the relationship being acted upon (cancel in Rubicon; link/disconnect in Gitaly) is between the parties who actually created/are entitled to that pairing. Authorization is assumed to have been enforced entirely by an outside caller (GitLab Rails for Gitaly; the offer's true owner check for Rubicon), and neither component independently re-verifies it at the point where the sensitive action is executed.

### Impact Explanation
If GitLab Rails (or any other Gitaly RPC client) ever forwards a user-influenced `ObjectPool`/`Repository` pair without itself enforcing that the pool genuinely belongs to / was derived from the target repository (e.g., a bug or gap in access-control logic upstream, or any code path that constructs these messages from partially user-controlled input such as a repository path), an attacker's repository could be linked to an unrelated object pool. Since alternates make the pool's objects transparently readable through the linked repository (and object access RPCs will happily serve objects reachable via alternates), this leads to cross-repository object disclosure. Conversely, `DisconnectGitAlternates` on an unrelated repository can corrupt that repository if it is currently a *bona fide* member of a pool being relied upon for deduplication, since Gitaly itself states no safety checks exist to prevent corrupting other members.

### Likelihood Explanation
This requires that some caller (most likely GitLab Rails, given Gitaly RPCs are meant to be called only by trusted internal callers) presents a `Repository`/`ObjectPool` pairing that hasn't been independently validated as legitimate. Because Gitaly places 100% of this trust boundary on the caller and performs zero independent verification, the likelihood of exploitation is entirely a function of whether any upstream caller ever passes attacker-influenced identifiers into these RPCs — this is plausible given that object pool relative paths are deterministic/derivable and `Repository`/`ObjectPool` protobuf fields are simple strings that could be manipulated wherever request construction logic has a flaw.

### Recommendation
Have Gitaly independently verify pool/repository provenance before performing `LinkRepositoryToObjectPool`, `DisconnectGitAlternates`, and `DeleteObjectPool`: store and check a persisted association (e.g., pool metadata recording its origin repository, or a record of which repositories are currently valid members) rather than trusting the request's `Repository`/`ObjectPool` pair blindly. At minimum, `DisconnectGitAlternates` should refuse to act if the configured alternate doesn't match a previously-recorded, Gitaly-verified linkage, and `LinkRepositoryToObjectPool` should refuse silently redirecting a repository's alternates to a pool it was not the origin of unless that association was recorded through `CreateObjectPool`/prior legitimate `Link` calls.

### Proof of Concept
Not independently reproducible from the indexed code alone since exploitation depends on how an upstream caller (e.g. GitLab Rails) constructs the `LinkRepositoryToObjectPoolRequest`/`DisconnectGitAlternatesRequest` messages; Gitaly's own test suite (`internal/gitaly/service/objectpool/link_test.go`) demonstrates that `LinkRepositoryToObjectPool` succeeds for any valid `(Repository, ObjectPool)` pair without checking their prior relationship: [6](#0-5)

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}

// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}

func (s *server) DisconnectGitAlternates(ctx context.Context, req *gitalypb.DisconnectGitAlternatesRequest) (*gitalypb.DisconnectGitAlternatesResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	repo := s.localRepoFactory.Build(repository)

	storageRoot, err := s.locator.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return nil, fmt.Errorf("storage by name: %w", err)
	}

	f := storage.NewNoopFS(storageRoot)
	if tx := storage.ExtractTransaction(ctx); tx != nil {
		f = tx.FS()
	}

	if err := objectpool.Disconnect(ctx, f, repo, s.logger, s.txManager); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.DisconnectGitAlternatesResponse{}, nil
}

  // repository is still using this object pool it will become corrupted.
  rpc DeleteObjectPool(DeleteObjectPoolRequest) returns (DeleteObjectPoolResponse) {
    option (op_type) = {
      op: MUTATOR
    };
  }

  // LinkRepositoryToObjectPool links the specified repository to the object pool. Objects contained
  // in the object pool will be deduplicated for this repository when repacking objects.
  rpc LinkRepositoryToObjectPool(LinkRepositoryToObjectPoolRequest) returns (LinkRepositoryToObjectPoolResponse) {
    option (op_type) = {
      op: MUTATOR
    };
  }

  // DisconnectGitAlternates will disconnect the object pool member from its object pool. It will:
  //
  // 1. Link all objects from the object pool into the member repository. This essenitally
  //    reduplicates previously-duplicated objects so that the repository will continue to function
  //    after being unlinked.
  // 2. Remove the alternates link to the object pool.
  // 3. Perform a consistency check to assert that the repository is indeed fully functional after
  //    unlinking it from its pool. If the consistency check fails the alternates link is restored
  //    an the RPC fails.
  //
  // If successful, the object pool member is disconnected from the object pool and does not depend
  // on it anymore.
  //
  // This RPC does not return an error in case the repository is not linked to any object pool.
  rpc DisconnectGitAlternates(DisconnectGitAlternatesRequest) returns (DisconnectGitAlternatesResponse) {
    option (op_type) = {
      op: MUTATOR
    };
  }
