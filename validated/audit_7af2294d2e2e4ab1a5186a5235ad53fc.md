### Title
Unliquidatable debt band: `debtFloorInUsd` + `maxLiquidable` make all `liquidate()` calls revert for small unhealthy positions - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate()` enforces two independent bounds that are mutually unsatisfiable for a range of position sizes: a repayment cannot exceed `maxLiquidable` (50% of the debt balance) and cannot leave a nonzero remainder below `debtFloorInUsd`. Any borrower whose debt falls in the band `(debtFloorInUsd, debtFloorInUsd / (1 - maxLiquidable))` can never be liquidated, no matter how unhealthy the position becomes. This is an availability/protocol-solvency analog to the CVE class (unprivileged, repeatable denial of a core protocol function).

### Finding Description
In `Pool.liquidate`: [1](#0-0) 

```solidity
uint256 _debtTokenBalance = _debtToken.balanceOf(account_);

if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}

if (debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(
        address(syntheticToken_),
        _debtTokenBalance - amountToRepay_
    );
    if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
        revert RemainingDebtIsLowerThanTheFloor();
    }
}
```

Let debt `D` (in USD terms of the synth) satisfy `debtFloorInUsd < D < debtFloorInUsd / (1 - maxLiquidable)` — with the default `maxLiquidable = 0.5e18` set in `initialize` [2](#0-1) , that is `floor < D < 2·floor`.

- Any `amountToRepay_` that keeps the remainder `≥ floor` requires `amountToRepay_ ≤ D - floor < D·(1 - maxLiquidable)`, i.e. repaying enough to clear the floor is fine, but the largest allowed repayment is `maxLiquidable·D`, leaving remainder `≥ (1 - maxLiquidable)·D`. For `D < 2·floor`, `(1-0.5)·D < floor`, so the maximum permitted repayment still lands under the floor and reverts with `RemainingDebtIsLowerThanTheFloor`.
- Repaying the full balance (remainder = 0, which would pass the floor check) requires `amountToRepay_ = D`, i.e. `wadDiv = 1e18 > maxLiquidable`, reverting with `AmountGreaterThanMaxLiquidable`.

Every possible `amountToRepay_` reverts. The check `_totalSeized > depositToken_.balanceOf(account_)` at line 583 does not help; the revert happens before seizure [3](#0-2) .

### Impact Explanation
An attacker opens a collateralized position, issues debt in the toxic band, and lets the position go unhealthy (or engineers it via ordinary price movement). The position is then permanently unliquidatable: no liquidator can repay any amount without a revert. As collateral value keeps falling, the debt becomes bad debt backed by insufficient collateral, and the protocol has no mechanism to remove it — `liquidate` is the only path that burns `DebtToken` against seized collateral [4](#0-3) . Repeated across many accounts, this is a protocol insolvency vector plus a deterministic DoS of the liquidation function for those positions. The accepted-impact bar is met: permanent freezing of the liveness invariant and accrual of unbacked synthetic supply.

### Likelihood Explanation
- Fully unprivileged: the attacker only needs `DebtToken.issue`/`SyntheticToken` minting through normal public entry points; no governor, keeper, or malicious oracle is required.
- Requires `debtFloorInUsd > 0` on the deployed configuration. `debtFloorInUsd`/`updateDebtFloor` are present in `Pool.sol` and referenced in the deployment artifacts and `PoolUpgrader.sol`, indicating the parameter exists in deployed versions; I could not confirm the exact on-chain value from the indexed deployment JSONs within this session — if the floor is 0 on a given chain, this specific band collapses (the `debtFloorInUsd > 0` guard at line 571 skips the check). This is the main uncertainty.
- Likelihood also depends on the USD size of the band: it is bounded by `floor/(1-maxLiquidable) - floor`, so with a small floor the attack yields small per-position bad debt and must be scaled across many accounts.

### Recommendation
Allow the remainder check to pass when the repayment clears the entire debt, e.g. exempt `amountToRepay_ == _debtTokenBalance` from the `maxLiquidable` cap, or clamp `amountToRepay_` so that either the remainder is 0 or `≥ debtFloorInUsd`. Alternatively, enforce the floor at issuance time (`DebtToken.issue`) so positions can never enter the band, and treat full-close liquidations as always permitted.

### Proof of Concept
Foundry fork sketch (Hardhat equivalent is identical in structure):

```solidity
// Setup: use deployed Pool with debtFloorInUsd = F > 0, maxLiquidable = 0.5e18
// 1. Attacker deposits collateral via DepositToken.deposit(), issues D USD of msUSD
//    via DebtToken.issue() where F < D < 2*F.
// 2. Drop collateral price / let interest accrue until debtPositionOf(attacker).isHealthy == false.
// 3. For every amountToRepay:
//    - amountToRepay <= maxLiquidable*D  →  remaining >= (1-0.5)*D < F  →
//      reverts RemainingDebtIsLowerThanTheFloor (since remaining > 0)
//    - amountToRepay >  maxLiquidable*D  →  reverts AmountGreaterThanMaxLiquidable
//    Including amountToRepay == D (full close): reverts AmountGreaterThanMaxLiquidable.

function test_UnliquidatableBand() public {
    uint256 D = debtFloor + 1; // e.g. issue exactly floor+1 USD of debt
    // ... deposit collateral, issue D, move price to make unhealthy ...
    for (uint256 r = 1; r <= D; r += D / 10) {
        vm.expectRevert(); // either AmountGreaterThanMaxLiquidable or RemainingDebtIsLowerThanTheFloor
        pool.liquidate(msUSD, attacker, r, depositToken);
    }
    // position remains unhealthy and unliquidatable
}
```

Note: the PoC must run against a fork/configuration where `debtFloorInUsd > 0`; that deployed value is the one environmental assumption I could not verify from the index.
