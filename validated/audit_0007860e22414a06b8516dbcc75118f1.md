### Title
Storage-deposit ↔ Ethereum-gas round-trip truncation lets contract callers under-pay storage deposits in `pallet-revive` - (File: substrate/frame/revive/src/metering/gas.rs)

### Summary
The PToken report shows that computing `principal * ratio` and truncating the division (rather than rounding up) lets a borrower accrue no interest on small positions, effectively getting free use of protocol funds. `pallet-revive`'s `SignedGas` type performs the analogous unguarded truncating conversion between a storage deposit charge and an Ethereum gas amount, using `FixedPointNumber::saturating_mul_int` (round-down) in both directions of the round trip, with no compensating round-up step. Small per-operation deposit amounts can therefore be converted to gas and back to a deposit that is strictly less than what was actually owed — including zero — letting a contract execute real storage-consuming operations while accruing an under-charged (or completely uncharged) deposit.

### Finding Description
`SignedGas::from_adjusted_deposit_charge` converts a `StorageDeposit::Charge(amount)` into gas by multiplying by the reciprocal of `next_fee_multiplier`: [1](#0-0) 

and `SignedGas::to_adjusted_deposit_charge` converts the resulting gas value back into a deposit charge by multiplying by `next_fee_multiplier`: [2](#0-1) 

Both operations use `FixedPointNumber::saturating_mul_int`, which is defined (as documented directly in the revive fee-conversion code) as `div_round_down(multiplier.0 * n, FixedU128::DIV)` — i.e. it always truncates toward zero: [3](#0-2) 

Unlike the sibling helper `compute_max_integer_quotient`/`compute_max_integer_pair_quotient`, which was deliberately hardened with careful rounding math specifically because "simple division does not give the correct result" and caused transactions to run out of gas in practice, the deposit↔gas conversion in `gas.rs` uses the naive, unguarded `saturating_mul_int` on both legs of the round trip. This is structurally identical to the reported bug: a value is scaled down by a ratio, truncated, and then scaled back up by (approximately) the inverse ratio, truncated again — for small enough inputs and certain multiplier values the two truncations compound so the final deposit charge is less than the true amount owed, exactly as the PToken `principal * borrowIndex / interestIndex` truncation lets a small loan accrue no interest.

### Impact Explanation
Storage deposits back real state growth in `pallet-revive` (bytes/items added to a contract's trie), and the deposit-per-byte/per-item pricing exists specifically to make PoV/storage growth economically self-financing. If the gas↔deposit conversion under-reports the owed deposit for repeated small storage operations, a contract can grow persistent state while the chain collects less balance than the storage actually costs — an unbacked-resource-consumption bug matching the "public underpriced work that degrades block production" impact class. This is reachable by any unprivileged account issuing ordinary `eth_transact`/contract-call extrinsics against `pallet-revive` (deployed, e.g., on Asset Hub per other prdocs in this tree), with no admin, governance, relayer, or validator collusion required.

### Likelihood Explanation
The magnitude of the effect depends on `next_fee_multiplier` and `GasScale` at call time, and on how many times a contract can drive the conversion through small per-operation charges within one execution (each `SSTORE`-equivalent write triggers a deposit charge that is converted to/from gas in Ethereum execution mode). The team's own documentation shows this class of rounding problem has already caused real incidents in the sibling fee-quotient function (motivating a dedicated hardened implementation), which is strong internal evidence that the un-hardened `saturating_mul_int` round trip in `gas.rs` is similarly exploitable, though the precise threshold amounts and exact accumulation ceiling were not verified within the scope of this investigation (I did not trace every call site of `to_adjusted_deposit_charge`/`from_adjusted_deposit_charge` through `metering/mod.rs`, `exec.rs`, and `vm/evm.rs` to quantify per-block accumulation).

### Recommendation
Apply the same rigor used in `compute_max_integer_quotient`/`compute_max_integer_pair_quotient` to the deposit↔gas conversions in `SignedGas`: round the "charge" direction up and the "refund" direction down (or otherwise track and periodically settle the accumulated rounding remainder, as is already done for the related `tx_cost = effective_gas_price * gas` invariant in `pallet-revive`'s gas-used fix), so that `to_adjusted_deposit_charge(from_adjusted_deposit_charge(x)) >= x` for all charges.

### Proof of Concept
Because this is a compounding-truncation arithmetic bug rather than a logic/authorization bug, a concrete PoC requires selecting `next_fee_multiplier`/`GasScale` values and a sequence of small storage writes such that:
1. `from_adjusted_deposit_charge(Charge(d))` truncates `d * multiplier_reciprocal` down to `g`.
2. `to_adjusted_deposit_charge(Positive(g))` truncates `g * multiplier` back down to `d' < d`.
3. Repeating this over many small writes accumulates an under-charge `Σ(d - d')` that is unrecoverable, unlike the compensated `tx_cost` rounding-remainder burn described in `pr_10148.prdoc`.

I was not able to execute this scenario against the runtime within the available tool budget; confirming the exact exploitable magnitude (and whether any offsetting remainder-burning logic elsewhere in `metering/mod.rs` neutralizes it) requires running `pallet-revive`'s test harness with a crafted `next_fee_multiplier`/`GasScale` and a contract performing many minimal `SSTORE` operations, which should be done in a follow-up session with full repository/test access.

	pub fn from_adjusted_deposit_charge(deposit: &StorageDeposit<BalanceOf<T>>) -> Self {
		let multiplier = T::FeeInfo::next_fee_multiplier_reciprocal();

		match deposit {
			StorageDeposit::Charge(amount) => Positive(multiplier.saturating_mul_int(*amount)),
			StorageDeposit::Refund(amount) => {

/// Determine the maximal integer `n` so that `multiplier.saturating_mul_int(n) <= product`
///
/// See the tests `compute_max_quotient_works` below for an example why simple division does not
/// give the correct result. This level of pedantry is required because otherwise we observed actual
/// cases where limits where calculated incorrectly and the transaction ran out of gas although it
/// used the correct gas estimate.
///
/// FixedU128 wraps a 128 bit unsigned integer `self.0` and it is interpreted to represent the real
/// number self.0 / FixedU128::DIV, where FixedU128::DIV is 1_000_000_000_000_000_000.
///
/// Given an integer `n`, the operation `multiplier.saturating_mul_int(n)` is defined as
///      `div_round_down(multiplier.0 * n, FixedU128::DIV)`
/// where `div_round_down` is integer division where the result is rounded down.
///
/// To determine the maximal integer `n` so that `multiplier.saturating_mul_int(n) <= product` is
/// therefore equivalent to determining the maximal `n` such that
///      `div_round_down(multiplier.0 * n, FixedU128::DIV) <= product`
/// This is equivalent to the condition
///      `multiplier.0 * n <= product * FixedU128::DIV + FixedU128::DIV - 1`
/// This is equivalent to
///      `multiplier.0 * n < (product + 1) * FixedU128::DIV`
/// This is equivalent to
///      `n < div_round_up((product + 1) * FixedU128::DIV, multiplier.0)`
/// where `div_round_up` is integer division where the result is rounded up.
/// Since we look for a maximal `n` with this condition, the result is
///      `n = div_round_up((product + 1) * FixedU128::DIV, multiplier.0) - 1`.
///
/// We can take advantage of the function `FixedU128::checked_rounding_div`, which, given two fixed
/// point numbers `a` and `b`, just computes `a.0 * FixedU128::DIV / b.0`. It also allows to specify
/// the rounding mode `SignedRounding::Major`, which means that the result of the division is
/// rounded up.
