### Title
Witness Can Set Brokerage to 100% Leaving Voters With Permanently Zero Reward Share Despite Non-Zero Surplus - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java`)

### Summary
`UpdateBrokerageActuator.validate()` only enforces that `brokerage` lies in the range `[0, 100]` and never enforces a minimum floor that guarantees voters (the analog of the "partner" in the external report) a non-zero share of block/transaction-fee rewards. A witness can set `brokerage = 100`, which causes `MortgageService.payReward()` to route the entire reward value to the witness's own allowance and leave zero for the reward pool that voters draw from, even when the reward (`value`, the analog of "surplus") is strictly positive.

### Finding Description
`UpdateBrokerageActuator.validate()` checks: [1](#0-0) 

The only bound is `brokerage < 0 || brokerage > ActuatorConstant.ONE_HUNDRED`, so `brokerage = 100` is accepted and persisted via `delegationStore.setBrokerage(ownerAddress, brokerage)`: [2](#0-1) 

This stored brokerage is consumed by `MortgageService.payReward()`, which computes the witness's cut (`brokerageAmount`) and subtracts it from the value that would otherwise be added to the voter-facing reward pool: [3](#0-2) 

When `brokerage == 100`, `brokerageRate = 1.0`, so `brokerageAmount == value` and the post-subtraction `value` (the amount added via `delegationStore.addReward(cycle, witnessAddress, value)`, which voters later claim through `computeReward`/`withdrawReward`) becomes `0` — regardless of how large the original block reward or transaction-fee reward (`surplus`) was. Voters who delegated votes to that witness therefore receive exactly zero reward for that cycle, structurally identical to the reported bug class: a percentage split parameter with no enforced minimum, letting one party (here, the witness, analogous to the router caller) unilaterally zero out the other party's (voters', analogous to the partner's) entitled share of a non-zero surplus.

The default value (`DelegationStore.DEFAULT_BROKERAGE = 20`) is reasonable, but nothing prevents an active witness from later calling `UpdateBrokerageContract` to raise it to 100: [4](#0-3) [5](#0-4) 

The change takes effect the very next voting cycle via `MaintenanceManager.doMaintenance()`, which copies the current brokerage forward for the next cycle without any additional bound or rate-limit beyond the initial `[0,100]` check: [6](#0-5) 

### Impact Explanation
Any witness can permanently divert 100% of block rewards and transaction-fee rewards away from its voters into its own allowance, using nothing more than a single `UpdateBrokerageContract` transaction signed with the witness's own key. Voters who have frozen TRX and cast votes for that witness — expecting a share of rewards proportional to their stake — receive a permanent zero, which is a direct unauthorized diversion of funds that should have accrued to voters. This is analogous to the reported issue where a facilitator ("partner") could be cut out of surplus/slippage earnings entirely due to a missing minimum-share floor.

### Likelihood Explanation
High. No special privilege beyond being a registered witness (attainable by anyone who freezes enough TRX and runs for SR/witness) is required, and the exploit is a single, cheap, always-successful transaction (`UpdateBrokerageContract`) with `calcFee() == 0`: [7](#0-6) 
There is no cooldown, governance approval, or additional bound preventing the value 100 from being set.

### Recommendation
Enforce an upper bound below 100 (or, symmetrically, a minimum floor below 100 for the voter-facing share) in `UpdateBrokerageActuator.validate()`, e.g.:
```diff
- if (brokerage < 0 || brokerage > ActuatorConstant.ONE_HUNDRED) {
+ if (brokerage < 0 || brokerage > MAX_BROKERAGE) { // MAX_BROKERAGE < 100, e.g. 80
    throw new ContractValidateException("Invalid brokerage");
  }
```
This guarantees voters always retain a non-zero minimum share of the reward pool regardless of the witness's chosen brokerage rate.

### Proof of Concept
1. Register/operate as a witness (freeze TRX, become an SR) and have voters delegate votes to it.
2. Submit `UpdateBrokerageContract{ownerAddress: <witness>, brokerage: 100}`; `UpdateBrokerageActuator.validate()` passes since `100 <= ActuatorConstant.ONE_HUNDRED`, and `execute()` stores it via `delegationStore.setBrokerage`.
3. On the next maintenance cycle, `MaintenanceManager.doMaintenance()` carries the new brokerage forward.
4. When the witness produces a block or receives transaction-fee rewards, `MortgageService.payReward()` computes `brokerageRate = 1.0`, `brokerageAmount = value`, and `value -= brokerageAmount` yields `0`, so `delegationStore.addReward(cycle, witnessAddress, 0)` is called.
5. Voters calling `withdrawReward`/`queryReward` for that cycle receive `0` from `computeReward`, despite the witness having received a non-zero block/fee reward (the "surplus").

  public int getBrokerage(long cycle, byte[] address) {
    BytesCapsule bytesCapsule = get(buildBrokerageKey(cycle, address));
    if (bytesCapsule == null) {
      return DEFAULT_BROKERAGE;
    } else {
      return ByteArray.toInt(bytesCapsule.getData());
