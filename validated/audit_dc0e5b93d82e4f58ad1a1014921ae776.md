### Title
Unconditional TRX transfer to codeless/self-destructed contract accounts permanently locks funds - (File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java)

### Summary
`VMActuator.call()` transfers `callValue` (and TRC-10 `tokenValue`) to the target `contractAddress` unconditionally, regardless of whether the target contract actually has executable code. This mirrors the reported `receiveFunds()` bug class: value is accepted and moved into an account even along a code path that cannot make use of it, permanently locking the funds.

### Finding Description
In `VMActuator.call()`, the code first fetches the deployed contract's bytecode and only runs the VM if the code is non-empty: [1](#0-0) 

But the value transfer that follows is outside that `if` block and executes unconditionally whenever `callValue > 0` (or `tokenValue > 0`), whether or not the VM ran: [2](#0-1) 

A `contractAddress` can have a `ContractCapsule` entry (so `deployedContract` is non-null and the earlier "No contract or not a smart contract" check at lines 500-504 passes) while its code is empty — this occurs after the contract executes `SELFDESTRUCT`/`SUICIDE`. `SUICIDE` handling is implemented in `Program.java` (referenced via `OperationRegistry`/`EnergyCost`), and it removes the contract's code/storage but the destination account (and the `ContractCapsule` record used by `getContract`) can still be addressed by a `TriggerSmartContract` transaction that carries `call_value`. [3](#0-2) 

Because a smart-contract account has no associated private key, there is no way to originate a normal signed `TransferContract` *from* that account to move the funds back out, and because the code is empty there is no way to trigger contract logic (e.g. a withdraw function) either. Any `TriggerSmartContract` transaction with `call_value > 0` sent to such an address after it has become codeless therefore transfers TRX into the account with no possible code path to retrieve it — an unauthorized actor (any transaction broadcaster) can also do this to their own or another's already-destructed contract address, permanently freezing the sent TRX.

### Impact Explanation
Any TRX (and, if TRC-10 support is enabled, TRC-10 tokens via `tokenValue`) sent as `call_value`/`call_token_value` in a `TriggerSmartContract` to a codeless (post-self-destruct) contract address is irrecoverably locked. This is a permanent freezing-of-funds bug reachable directly from a single signed transaction with no privileged access required, matching the accepted impact category of "permanent freezing of funds."

### Likelihood Explanation
Likelihood is driven entirely by user/caller behavior: any account can self-destruct a contract it deployed and then (accidentally or via a phishing/scripted flow) send `callValue` to that now-codeless address, or a malicious actor could induce another user to send funds to a known-destructed contract address (e.g. via a dApp/wallet integration that doesn't verify code existence before constructing a value-bearing `TriggerSmartContract`). No special privileges, races, or chain-state manipulation are needed — a single `TriggerSmartContract` with non-zero `call_value` against a codeless address suffices.

### Recommendation
In `VMActuator.call()`, reject the transaction (throw `ContractValidateException`) when `code` is empty and `callValue > 0` or `tokenValue > 0`, instead of unconditionally executing the transfer at lines 570-579. This mirrors the report's recommendation to require that value only be accepted along code paths that can actually consume/forward it.

### Proof of Concept
1. Deploy a payable contract `C` that contains a function calling `SELFDESTRUCT`/`SUICIDE`.
2. Call that function to self-destruct `C`, clearing its bytecode while `getContract(contractAddress)` still returns the `ContractCapsule` record.
3. Submit a `TriggerSmartContract` transaction targeting `C`'s address with `call_value = N > 0` (no function selector data needed).
4. Observe: `isNotEmpty(code)` is `false`, so no VM logic executes and `program` never runs — yet lines 573-575 execute `MUtil.transfer(rootRepository, callerAddress, contractAddress, callValue)`, crediting `N` TRX to the destroyed contract's account.
5. Because `C` is a contract account (no private key) and now has no code, there is no possible subsequent transaction that can move balance `N` out of `C`; the TRX is permanently locked.
