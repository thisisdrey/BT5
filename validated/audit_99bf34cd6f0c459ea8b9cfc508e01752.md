### Title
No vulnerability: `check_actor_permissions` correctly blocks cross-account `AddKey` privilege escalation via promise batches - (File: `runtime/runtime/src/actions.rs`)

### Summary
An attacker's contract can indeed call `promise_batch_create` targeting victim account C and append `promise_batch_action_add_key_with_full_access` with zero authorization checks performed at construction time in `imports.rs`/`wasmtime_runner/logic.rs`. However, the resulting `AddKey` action is unconditionally rejected at execution time by `check_actor_permissions`, which compares the receipt's `actor_id` (predecessor) against `account_id` (receiver, i.e., C) and returns `ActionErrorKind::ActorNoPermission` on mismatch, so the invariant holds.

### Finding Description
`promise_batch_action_add_key_with_full_access` in `runtime/near-vm-runner/src/logic/logic.rs:3447-3471` (and the equivalent wasmtime path at `runtime/near-vm-runner/src/wasmtime_runner/logic.rs:3686-3717`) only checks gas payment and `is_view()`, then calls `self.ext.append_action_add_key_with_full_access(receipt_idx, public_key, nonce)` [1](#0-0) , which in `receipt_manager.rs` just appends an `Action::AddKey` onto the outgoing receipt's action list with no receiver check [2](#0-1) . So the claim that `imports.rs`-adjacent construction performs zero authorization checks is correct.

The actual guard is enforced downstream when the receipt executes against C. `apply_action` in `runtime/runtime/src/lib.rs:523-567` calls `check_actor_permissions(action, account, actor_id, account_id)` before dispatching to any handler, where `account_id = receipt.receiver_id()` (C) and `actor_id` tracks the acting identity (initially the receipt's predecessor, i.e., the attacker contract's account) [3](#0-2) . `check_actor_permissions` in `runtime/runtime/src/actions.rs:739-785` treats `Action::AddKey` (along with `DeployContract`, `Stake`, `DeleteKey`, etc.) as requiring `actor_id == account_id`, returning `ActorNoPermission` otherwise [4](#0-3) . Since the attacker's predecessor account is not C, this check fails and the `AddKey` action never executes, leaving C's account untouched. This matches the documented model: "Administrative actions like `DeployContract`, `Stake`, `AddKey`, `DeleteKey` can be proceed only if sender=receiver or the first TX action is a `CreateAccount` action" [5](#0-4) . The only bypass documented is the `CreateAccount`-first exception, which only applies when the attacker itself creates C as a brand-new subaccount (i.e., C doesn't pre-exist, contradicting the stated precondition that "victim account C exists").

This is confirmed by existing integration tests: `test_delete_account_fail` in `integration-tests/src/tests/standard_cases/mod.rs:1649-1683` shows an analogous administrative action (`DeleteAccount`) from a non-owning actor failing with exactly `ActionErrorKind::ActorNoPermission` [6](#0-5) , and `meta_tx_add_key` in `integration-tests/src/tests/features/delegate_action.rs:503-528` explicitly notes "Can only add key on own account" and constructs the receiver as the sender itself [7](#0-6) .

### Impact Explanation
No impact. The scenario as described (attacker's contract adding a full-access key to a pre-existing, unrelated victim account C via a promise batch) is blocked by `check_actor_permissions`'s `actor_id == account_id` check for `Action::AddKey`. No authorization escalation, fund theft, or freezing occurs.

### Likelihood Explanation
Not applicable — the described attack path is not exploitable given the existing guard in `runtime/runtime/src/actions.rs`.

### Recommendation
No fix required. The design intentionally defers cross-action authorization to `check_actor_permissions` at execution time rather than at VM-import construction time, since at construction time the batch's ultimate `predecessor_id`/`account_id` relationship for the *new* receipt is already fixed by `promise_batch_create`'s target and the current receipt's identity — checking it again in `imports.rs` would be redundant. If defense-in-depth is desired, a documentation note in `imports.rs` clarifying that authorization is deferred to `check_actor_permissions` would improve auditability, but this is not a security requirement.

### Proof of Concept
Extend `runtime/runtime/tests/test_async_calls.rs` (pattern from `test_create_account_with_transfer_and_full_key`) with a test where contract on account A (not creating C) calls `promise_batch_create(C)` where C is a pre-existing account with no relation to A, followed by `promise_batch_action_add_key_with_full_access`. Assert the resulting receipt's execution outcome is `FinalExecutionStatus::Failure` with `ActionErrorKind::ActorNoPermission { account_id: C, actor_id: A }`, and assert via `view_access_key` that no new key was added to C.
