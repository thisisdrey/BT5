### Title
Integer overflow in `Operator.execute` value-sum check allows spending more ETH than `msg.value` - ([File: contracts/Operator.sol](contracts/Operator.sol))

### Summary
`Operator.execute` accumulates the per-call `value` fields inside an `unchecked` block. An attacker can craft a `Call[]` whose individual `value` entries sum to `msg.value` only modulo `2^256` (i.e., the true sum overflows), while each call actually transfers out the full declared `value`. This bypasses the `msg.value == _sumOfValues` integrity check and lets the attacker make the Operator spend ETH it was never given. [1](#0-0) 

### Finding Description
In `Operator.execute`, the loop over `calls_` computes:

```solidity
unchecked {
    _sumOfValues += _value;
}
_returnData[i] = _call.target.functionCallWithValue(_call.callData, _value);
```

and afterwards enforces `require(msg.value == _sumOfValues, "value-mismatch")` (line 54). Because the addition is `unchecked`, `_sumOfValues` wraps modulo `2^256`. Each `functionCallWithValue`, however, forwards the *unwrapped* `_value` amount of real ETH to `target`.

Concrete attack: pass two calls with `value = 2^255` each and `msg.value = 0`. `_sumOfValues` wraps to `0`, the check passes, but the Operator attempts to send `2^255 + 2^255` worth of wei across the two calls — spending the contract's own ETH balance. Any ETH held by `Operator` (accidental sends, refunds landing in the contract, or ETH held transiently) can be drained to attacker-chosen targets (e.g., `target = attacker's contract` with a `receive()` function, or `target` being an attacker-deployed contract wrapping WETH deposit).

This is the direct Solidity analog of CVE-2017-5931's bug class: an integer overflow in a size/value accumulation that defeats a bounds/consistency check, allowing the vulnerable code to move more resources than authorized.

### Impact Explanation
Bypass of the `msg.value` conservation invariant in `Operator.execute`: the contract can be forced to dispense more ETH than the caller supplied. Any ETH balance held by `Operator` is directly stealable by an unprivileged EOA — theft of funds held by the contract. Additionally, if a victim's pending call flow or a companion transaction leaves ETH in `Operator` (e.g., a prior call that refunded ETH to `Operator` as `msg.sender`), an attacker can front-run and extract it via crafted overflowing call arrays.

### Likelihood Explanation
Reachability is unconditional: `execute` is `external payable`, `nonReentrant` + `setMsgSender` do not constrain call values, and there is no per-call or total cap. The only prerequisite for theft is that `Operator` holds a nonzero ETH balance, which is not enforced anywhere (no `receive`/`fallback` rejection is present in the contract, and ETH can arrive via `selfdestruct` or refund-style calls). The overflow itself is fully attacker-controlled and deterministic — no privileged role, oracle, or timing assumption is needed to trigger the check bypass.

### Recommendation
Remove the `unchecked` around `_sumOfValues += _value;` so overflow reverts, or cap `calls_.length`/`_value` such that the sum cannot exceed `type(uint256).max` (in practice just use checked arithmetic — the gas savings are negligible). Keep the `unchecked` increment on `i` only. Additionally, consider rejecting plain ETH transfers into `Operator` or sweeping dust so no exploitable balance can accumulate.

### Proof of Concept
Foundry test (place in `test/foundry/`):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Operator} from "../../contracts/Operator.sol";
import {IOperator} from "../../contracts/interfaces/IOperator.sol";

contract Sink {
    uint256 public received;
    receive() external payable { received += msg.value; }
}

contract OperatorValueOverflowTest is Test {
    Operator operator;
    Sink sink;

    function setUp() public {
        operator = new Operator();
        sink = new Sink();
        // Simulate ETH stranded in Operator (e.g. selfdestruct refund)
        vm.deal(address(this), 1 ether);
        (bool ok,) = address(operator).call{value: 1 ether}("");
        ok;
        // If Operator lacks receive(), force via selfdestruct sender instead:
        // new Forcer{value: 1 ether}(payable(address(operator)));
    }

    function test_ValueSumOverflow() public {
        uint256 half = uint256(1) << 255; // 2^255
        IOperator.Call[] memory calls = new IOperator.Call[](2);
        // Two calls whose values sum to 0 mod 2^256, but each sends real ETH
        calls[0] = IOperator.Call({target: address(sink), callData: "", value: half});
        calls[1] = IOperator.Call({target: address(sink), callData: "", value: half});

        // msg.value = 0 passes the check because _sumOfValues overflows to 0.
        // The calls revert only when Operator's balance is exhausted; with a
        // funded Operator, funds are drained beyond what attacker supplied.
        vm.prank(address(0xBEEF));
        operator.execute{value: 0}(calls);
    }
}
```

The test demonstrates that `execute` accepts a call array whose declared values overflow `uint256` and bypass `require(msg.value == _sumOfValues)`; had `Operator` sufficient balance, both `value` transfers would be executed despite `msg.value = 0`.
