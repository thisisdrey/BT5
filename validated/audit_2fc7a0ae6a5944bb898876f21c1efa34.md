### Title
Attacker can permanently block `removeDepositToken`/`removeDebtToken` by keeping dust supply — (File: contracts/Pool.sol)

### Summary
`Pool.removeDepositToken()` and `Pool.removeDebtToken()` revert with `TotalSupplyIsNotZero` whenever the target token's `totalSupply()` is greater than zero. Because `DepositToken.deposit()` is permissionless and there is no way for the governor to force-burn another account's `msdTOKEN` balance, an attacker can permanently keep `totalSupply > 0` with a dust deposit, making the token impossible to remove — the same bug class as the Rio `removeAsset` griefing finding. [1](#0-0) 

### Finding Description
The governor-facing removal functions check supply before removal:

```solidity
// contracts/Pool.sol
function removeDebtToken(IDebtToken debtToken_) external onlyGovernor {
    if (debtToken_.totalSupply() > 0) revert TotalSupplyIsNotZero();
    ...
}

function removeDepositToken(IDepositToken depositToken_) external onlyGovernor {
    if (depositToken_.totalSupply() > 0) revert TotalSupplyIsNotZero();
    ...
}
```

`totalSupply` of a `DepositToken` is only reduced by `_burn`, which is reachable only by the holder via `withdraw`/`withdrawFrom` (or liquidation paths that require the holder to be unhealthy). There is no privileged burn or "skim" path. [2](#0-1) [3](#0-2) 

Attack path for `removeDepositToken`:
1. Governor wants to remove collateral `msdX` after all legitimate users have withdrawn (or to phase out an asset).
2. Attacker calls `underlying.approve(msdX, amount)` then `depositToken.deposit(amount, attacker)` for any amount that mints `> 0` shares (`_mint` only credits supply when `amount_ > 0`). [4](#0-3) 

3. `msdX.totalSupply()` is now `> 0` forever; every `removeDepositToken(msdX)` call reverts. If a withdrawal race is attempted (attacker front-runs the governor's removal tx by re-depositing after seeing other users exit), griefing continues indefinitely at negligible cost.

Attack path for `removeDebtToken`: an unprivileged user can open a position via `DepositToken.deposit` + `DebtToken.issue(amount, attacker)` and simply never repay. `debtFloorInUsd` may raise the minimum debt size, but the attacker can still keep a small position open at the cost of posting collateral, and `totalSupply()` additionally includes accrued interest so it is strictly positive while any principal exists. [5](#0-4) [6](#0-5) 

### Impact Explanation
The governor permanently loses the ability to remove a deposit token or debt token from the pool. Deprecated/unsafe collaterals or synthetics cannot be fully delisted; `depositTokenOf[underlying]` / `debtTokenOf[syntheticToken]` remain populated and the token stays registered in `depositTokens`/`debtTokens`, which also permanently consumes a `MAX_TOKENS_PER_USER` slot, preventing a replacement collateral for the same slot count. This is a liveness/admin-function DoS equivalent to the referenced Rio finding; worst case it forces governance to keep an asset that must be delisted (e.g., deprecating vault-share collateral with a deteriorating oracle), indirectly risking user funds.

### Likelihood Explanation
Requires only an unprivileged EOA: `deposit()` has no access control, no minimum enforced beyond the deposit fee, and the attacker needs only enough underlying to mint one share. The attack is cheap, can be done preemptively or by front-running the removal transaction, and is repeatable indefinitely. The only mitigation today is `toggleIsActive()` (halts new deposits/mints) — which does not restore removability. [7](#0-6) 

### Recommendation
Do not gate removal on `totalSupply() == 0`. Either:
- Allow removal with outstanding supply while blocking new mints (`toggleIsActive` semantics), letting remaining holders withdraw/burn normally, or
- Provide a governor recovery path that can force-settle residual dust (e.g., a `sweep`-style burn of remaining `msdTOKEN` returning underlying, or socializing negligible dust).

### Proof of Concept
Hardhat (repo uses hardhat + smock; see `test/Pool.test.ts` whitelisting suite which already asserts `TotalSupplyIsNotZero` revert):

```ts
// test/Pool.test.ts context — mainnet-fork style test
it('attacker blocks removeDepositToken with dust deposit', async function () {
  // setup: msdMET DepositToken exists and has zero supply
  expect(await msdMET.totalSupply()).eq(0);

  // attacker deposits a dust amount of MET
  const attacker = alice;
  const dust = ethers.utils.parseEther('0.0001');
  await met.mint(attacker.address, dust);
  await met.connect(attacker).approve(msdMET.address, dust);
  await msdMET.connect(attacker).deposit(dust, attacker.address);

  expect(await msdMET.totalSupply()).gt(0);

  // governor can no longer remove the deposit token
  await expect(pool.removeDepositToken(msdMET.address))
    .revertedWithCustomError(pool, 'TotalSupplyIsNotZero');

  // attacker can re-grief after every attempt; there is no force-removal path
});
```

Same pattern for `removeDebtToken`: attacker deposits collateral, calls `debtToken.issue(amount, attacker)` (≥ `debtFloorInUsd` if set), never repays → `totalSupply()` stays positive via principal plus accrued interest, and removal reverts permanently. [8](#0-7)
