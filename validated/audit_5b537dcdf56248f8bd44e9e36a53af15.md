### Title
Attached deposit (`CallerDeposit`) is not refunded when intermediate cross-contract calls fail or return unparsable data in the Wallet Contract - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The eth-implicit Wallet Contract's `rlp_execute` flow tracks the caller's attached NEAR deposit in a `CallerDeposit` struct whose documented purpose is "to refund the caller's deposit if the cross-contract call fails" [1](#0-0) . However, this refund is only implemented in the final `rlp_execute_callback`, not in the two intermediate callbacks (`address_check_callback`, `nep_141_storage_balance_callback`) that can also terminate the flow with failure — mirroring the class of bug in the report, where code assumes an external call always behaves/returns data in the expected shape, and any deviation (failure, or a non-conforming/unexpected response) silently drops handling that should otherwise protect user funds.

### Finding Description
`rlp_execute` threads a `caller_deposit: Option<CallerDeposit>` value through the promise chain so it can be refunded to the predecessor on failure [2](#0-1) .

Only `rlp_execute_callback` actually performs the refund, and only on `PromiseResult::Failed`: [3](#0-2) 

But `address_check_callback`, which is invoked after calling the address registrar contract, drops `caller_deposit` entirely on both the `PromiseResult::Failed` branch and the branch where the registrar's response cannot be parsed as the expected `Option<AccountId>`: [4](#0-3) 

Likewise, `nep_141_storage_balance_callback`, invoked after calling a NEP-141 token's `storage_balance_of`, drops `caller_deposit` on `PromiseResult::Failed`, on JSON parse failure of the response, and on the "unexpected action type" branch: [5](#0-4) 

These two callbacks are reached specifically for `EOABaseTokenTransfer` with an address check, and for `ERC20Transfer` (NEP-141 emulation) [6](#0-5)  — both are relayer/fee-paying flows where `CallerDeposit::new` records a non-zero attached deposit from an external (non-self) predecessor [7](#0-6) .

Just as the Solidity report shows that an external call not conforming exactly to the expected interface (USDT's `transfer` not returning `bool`) causes downstream logic to take an unhandled failure path, here any external contract (the address registrar or an arbitrary NEP-141 token supplied by the relayer as `target`) that fails the cross-contract call, or returns data that doesn't deserialize into the exact expected schema, causes the wallet contract to take a failure branch that never restores the caller's attached deposit.

### Impact Explanation
The attached deposit is real caller-owned funds (yoctoNEAR fees paid by an external relayer per the eth-implicit wallet fee model). When the registrar or the target NEP-141 token contract fails the call (e.g., account doesn't exist, runs out of gas, panics) or returns a response the wallet contract cannot parse into the exact expected type, the funds attached by the caller are absorbed into the wallet contract's balance with no promise ever issued to return them — an unrecoverable, permanent loss of those funds for the caller, contrary to the explicit design intent documented on `CallerDeposit`.

### Likelihood Explanation
This is reachable by any unprivileged relayer/user calling `rlp_execute` with a non-zero fee on an `EOABaseTokenTransfer` targeting an unregistered eth-implicit account (triggering the registrar lookup) or an `ERC20Transfer` targeting an arbitrary NEP-141-like contract (triggering `storage_balance_of`) [8](#0-7) . A malicious or non-conforming target contract, or simply a call that runs out of allocated gas, is sufficient to trigger the `PromiseResult::Failed`/parse-error branches, so this requires no privileged access.

### Recommendation
In `address_check_callback` and `nep_141_storage_balance_callback`, on every early-return `PromiseOrValue::Value(...)` branch (both `PromiseResult::Failed` and response-parsing/type-mismatch failures), issue the same refund promise to `caller_deposit.account_id` for `caller_deposit.yocto_near` that `rlp_execute_callback` performs, instead of silently discarding the value.

### Proof of Concept
1. A relayer calls `rlp_execute` with `target` set to an unregistered eth-implicit account address and a non-zero fee, causing `EOABaseTokenTransfer { address_check: Some(address), fee }` and an attached deposit tracked as `caller_deposit`.
2. The wallet contract calls the address registrar's `lookup` and schedules `address_check_callback`.
3. If the registrar call fails (e.g., insufficient gas, registrar account misconfigured) or returns malformed JSON, `address_check_callback` hits [9](#0-8)  and returns `ExecuteResponse{success:false,...}` directly, without ever spending `caller_deposit`.
4. The attached deposit remains in the wallet contract's balance permanently; no promise is created to return it to the caller. The same applies to the `ERC20Transfer` path via `nep_141_storage_balance_callback` when the target token's `storage_balance_of` call fails or returns an unexpected shape.

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
