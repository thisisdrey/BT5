## Analysis

The reported bug class — minting/deposit amounts computed from the *current* pool ratio with no way for the caller to bound the outcome — has a direct analog in java-tron's `Exchange` (Bancor-style AMM for TRC10/TRX pairs) actuators.

### Title
Missing slippage protection in `ExchangeInjectActuator` liquidity injection - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectContract`, unlike `ExchangeTransactionContract`, carries no `expected`/minimum-output field. `ExchangeInjectActuator.execute()` computes the paired token amount (`anotherTokenQuant`) purely from the pool's *current* on-chain reserves at execution time, and unconditionally debits that computed amount from the sender's account with no user-supplied bound to reject an unfavorable result.

### Finding Description
`ExchangeInjectContract` only defines `owner_address`, `exchange_id`, `token_id`, `quant` [1](#0-0)  — there is no minimum/maximum bound field, in contrast to `ExchangeTransactionContract` which explicitly has an `expected` field used for slippage checking [2](#0-1) .

In `ExchangeInjectActuator.execute()`, the counterpart amount is derived as a straight ratio of the pool's live `firstTokenBalance`/`secondTokenBalance` at the moment the transaction executes, then immediately deducted from the user's balance/asset holdings and the pool state is updated: [3](#0-2) . `doValidate()` re-derives the exact same ratio-based `anotherTokenQuant` only to check `> 0` and balance sufficiency — never against any caller-supplied bound [4](#0-3) .

Because the pool ratio can shift between when the user constructs/signs the transaction and when it is actually executed (e.g., another `ExchangeTransactionContract` swap gets included earlier in the same block, or an attacker deliberately front-runs with a swap), the amount of the paired asset the injector is forced to contribute — and thus the value they receive credit for in the pool — is not guaranteed to match what they expected when signing. This is the same root cause as the `PortfolioToken.deposit()` issue: a value transfer that depends on pool state at execution time with no caller-enforced bound.

### Impact Explanation
An attacker who can predict or induce a victim's `ExchangeInjectContract` transaction (e.g., visible in the mempool) can submit an `ExchangeTransactionContract` swap immediately before it to skew the first/second token ratio, causing the victim's injected liquidity to be matched against an unfavorable ratio. The victim's account is unconditionally debited the ratio-computed `anotherTokenQuant` [5](#0-4) , transferring value to whoever holds/withdraws the pool position afterward (including the attacker, who can reverse their swap and withdraw). This results in a loss of funds for the injecting user, matching the impact class of the referenced report.

### Likelihood Explanation
Any unprivileged account can submit `ExchangeInjectContract` transactions, and any unprivileged account can submit `ExchangeTransactionContract` swaps against the same exchange pool to move the ratio just before the victim's transaction is packed into the same or an adjacent block — both are standard broadcastable transaction types requiring no special privilege.

### Recommendation
Add a caller-supplied bound (minimum-received or maximum-paired-amount) field to `ExchangeInjectContract`, analogous to the `expected` field already present on `ExchangeTransactionContract`, and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` before committing the debit and pool state update.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` from Victim for exchange pool `X` injecting `tokenA`.
2. Attacker submits an `ExchangeTransactionContract` swap on the same pool to skew `firstTokenBalance`/`secondTokenBalance` just before Victim's transaction executes.
3. `ExchangeInjectActuator.execute()` computes `anotherTokenQuant` from the now-skewed ratio [6](#0-5)  and debits Victim's account accordingly, with no way for Victim's transaction to reject the unfavorable outcome.
4. Attacker reverses the swap/withdraws, capturing the value discrepancy left in the pool at Victim's expense.
