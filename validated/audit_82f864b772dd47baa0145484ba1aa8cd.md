### Title
Receipt size validation is bypassed by post-validation mutation of `output_data_receivers`, allowing a receipt exceeding `max_receipt_size` to be produced and forwarded - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
An unprivileged contract can build a promise DAG (`promise_then` -> `promise_return`) so that a receipt is validated at exactly `max_receipt_size` before `output_data_receivers` is appended, and only afterward grows beyond the limit. `ReceiptSinkV2::try_forward` in `runtime/runtime/src/congestion_control.rs` only clamps its *local* `size` variable used for the bandwidth/outgoing-limit bookkeeping, it does not reject or truncate the oversized receipt itself, so the actual over-limit receipt is still placed into `outgoing_receipts` and shipped cross-shard.

### Finding Description
`try_forward` explicitly acknowledges this is a known bug in its own comment: "There is a bug which allows to create receipts that are above the size limit. Receipts above the size limit might not fit under the maximum outgoing size limit. Let's pretend that all receipts are at most `max_receipt_size` to avoid receipts getting stuck." [1](#0-0) . The clamp only affects the local `size` variable used for `forward_limit`/bandwidth accounting; the actual `receipt` object, whose real Borsh-serialized size can exceed `max_receipt_size`, is passed through unchanged and forwarded to `outgoing_receipts`.

The root cause matches the test comment: "A function call will generate a new receipt. Size of this receipt will be equal to `max_receipt_size`, it'll pass validation, but then `output_data_receivers` will be modified and the receipt's size will go above `max_receipt_size`." [2](#0-1) . This is tracked upstream as a known, already-referenced issue: https://github.com/near/nearcore/issues/12606, cited directly in the code comment.

The exploit path is via an unprivileged transaction only: fund an account, deploy a contract, and call a method that creates promise A -then-> B, where A itself creates receipt C sized to exactly `max_receipt_size` and calls `promise_return`. The runtime's own regression test `test_max_receipt_size_promise_return` reproduces exactly this scenario using `promise_then`/`promise_return` and asserts (via `assert_oversized_receipt_occurred`) that an oversized receipt does end up on-chain in the incoming receipts of the following block [3](#0-2) , confirmed by comparing serialized receipt size against `max_receipt_size` in `receipt_is_oversized` [4](#0-3) .

However, this is a **known, already-documented bug** with an existing regression test in the repository (not something requiring separate discovery), and the test's own docstring states the intended/observed behavior is that "the runtime shouldn't die when it encounters a receipt with size above `max_receipt_size`" — i.e., the existing test asserts non-fatal degraded behavior, not a panic or state-root divergence. I was not able to fully trace, within the available tool budget, whether `validate_receipt` (referenced in `runtime/runtime/src/verifier.rs` and `chain/chain/src/stateless_validation/chunk_validation.rs`) is re-invoked on the *receiving* shard at delivery time, and whether that would cause a panic/`ReceiptSizeExceeded` divergence between producer and receiving-shard chunk validators as the question hypothesizes. This determines whether the impact is merely a metering/accounting inconsistency (already tolerated per the existing test and code comment) versus an actual state-root divergence/chunk-halting panic on the receiving shard.

### Impact Explanation
As currently demonstrated by the existing test suite, the impact is: an oversized receipt (exceeding the assumed 4 MiB hard bound) is produced and forwarded cross-shard, and the runtime is explicitly designed (via the comment and clamp) to tolerate this without getting "stuck," which the existing test confirms does not crash the sending shard. Whether this constitutes a shard-halting panic or state-root divergence on the *receiving* shard specifically requires confirming what `validate_receipt` does at delivery time, which I could not fully verify with the tools available. Absent that confirmation, this maps to a "resource hygiene / oversized data" concern already known and tracked as issue #12606, not confirmed to cause fund loss, consensus divergence, or a chunk-halting panic.

### Likelihood Explanation
The precondition (funded account + deployed contract + `promise_then`/`promise_return` DAG sized to hit `max_receipt_size` exactly before `output_data_receivers` append) is fully reachable by an ordinary unprivileged account, as proven by the existing `test_max_receipt_size_promise_return` test using only `SignedTransaction::call` against a wasm contract test method. This makes the underlying receipt-size-limit bypass fully reproducible and low-cost. However, since this is a pre-existing, tracked, and already partially-mitigated bug (the clamp in `try_forward` exists specifically to prevent this from causing receipts to get "stuck"), it is not a novel finding, and the additional claim of divergent chunk-validation outcomes on the receiving shard is unverified.

### Recommendation
Since the root cause and reachability are already documented in the codebase (comment referencing nearcore#12606) and covered by an existing regression test, no new finding is being reported here beyond confirming the existing known issue. To close it: recompute/re-validate receipt size (including `output_data_receivers`) immediately before `try_forward`/`ReceiptSinkV2` accepts a receipt for outgoing buffering, reject or truncate receipts whose true Borsh size exceeds `max_receipt_size` at that point (not just at initial creation-time `validate_receipt`), and ensure `validate_receipt` on the receiving shard treats an oversized incoming receipt consistently (either as guaranteed-invalid-but-tolerated everywhere, or rejected deterministically the same way on every shard) so that no divergence in chunk-validation outcome can occur between producer and receiver.

### Proof of Concept
Use the existing `test_max_receipt_size_promise_return` in `test-loop-tests/src/tests/max_receipt_size.rs:130-208` as the base PoC (already reproducible), then extend it to additionally: (1) capture the receiving shard's application of the oversized incoming receipt, (2) call/trace `validate_receipt` on the receiving shard for that exact receipt, and (3) assert whether `ReceiptValidationError::ReceiptSizeExceeded` is raised there versus how the sending shard's `try_forward` handled it, to determine if a producer/receiver validation-outcome divergence actually occurs — this last step was not completed/verified in this analysis.

fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}

fn receipt_is_oversized(receipt: &Receipt, max_receipt_size: u64) -> bool {
    let receipt_size: u64 = borsh::object_length(receipt).unwrap().try_into().unwrap();
    if receipt_size > max_receipt_size {
        tracing::info!(%receipt_size, %max_receipt_size, "found receipt above max size");
        return true;
    }
    false
}
