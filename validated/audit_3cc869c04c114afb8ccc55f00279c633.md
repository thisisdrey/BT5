### Title
Anti-replay window `Check`/`Update` race allows a duplicated on-wire packet to bypass replay protection - ([File: connection_state.go])

### Summary
The external report's root cause is a non-atomic, two-phase update to shared global state with no locking mechanism spanning the whole operation, which lets a second, concurrent actor observe the pre-update state and cause an inconsistent/incorrect result. `nebula`'s data-plane decrypt path has the same structural flaw: the anti-replay window is checked and updated in two separate, individually-locked critical sections that are split by an unlocked, expensive AEAD decrypt operation, so two goroutines racing on the same message counter can both pass the "not yet seen" check before either one commits the "seen" update.

### Finding Description
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement the anti-replay check as:
1. Lock `decryptLock`, call `window.Check(l, messageCounter)`, unlock.
2. Perform `dKey.DecryptDanger(...)` **without holding the lock**.
3. Lock `decryptLock`, call `window.Update(l, messageCounter)`, unlock. [1](#0-0) 

`Bits.Check` only inspects whether the bit for counter `i` is already set; it does not itself mark the bit. `Bits.Update` is the only call that actually sets the bit / advances the window. Because `Check` and `Update` are not covered by a single critical section, and the AEAD decrypt in between is unlocked and comparatively slow, two threads that receive the same (or an intentionally duplicated) UDP packet with the same `messageCounter` can:
- Thread A: `Check(i)` → true (bit not yet set)
- Thread B: `Check(i)` → true (bit still not set, A hasn't called `Update` yet)
- Both threads independently run `DecryptDanger` (which will succeed identically, since AEAD decryption is deterministic given the same key/nonce/ciphertext)
- Thread A: `Update(i)` → true, marks the bit
- Thread B: `Update(i)` → false (`ErrAlreadySeen`), but only *after* it has already completed a full, successful decrypt of the duplicated ciphertext [2](#0-1) [3](#0-2) 

This is the same bug class as the report: state that gates a critical decision (`window`'s "have I seen this nonce" state) is read, then mutated, in two separate non-atomic steps, and a lock is only held around each individual step rather than around the whole check-and-commit sequence — exactly analogous to how `omniChainData` was read and written in disjoint, non-atomic cross-chain operations without an overarching lock.

### Impact Explanation
An on-path attacker (no CA-signed certificate required — they only need to observe and duplicate legitimate encrypted UDP packets between two already-handshaked peers) can replay a captured packet back at the receiver at (near-)the same moment the original arrives. Both copies can pass the replay-window `Check`, meaning the receiver will fully decrypt and could act on the duplicated ciphertext before the second copy is finally rejected by `Update`. Depending on how the decrypted output is consumed further up the pipeline (e.g., for handshake or control-plane messages processed inline, or before the final `Update` result is checked), this creates a genuine anti-replay bypass window — the receiver's replay-protection state can be raced into accepting a duplicate rather than dropping it outright at the "seen" check, which is the core guarantee the anti-replay window exists to provide.

### Likelihood Explanation
Exploitation only requires the ability to capture and retransmit a UDP packet to the same destination almost simultaneously with the original — a standard on-path/off-path duplication capability, not possession of a certificate signed by the network's CA. The race window is proportional to the cost of `DecryptDanger` under load (e.g., many concurrent tunnels/packets), which is realistic on a busy node, making the race practically triggerable rather than purely theoretical.

### Recommendation
Hold `decryptLock` across the entire check-decrypt-update sequence (or restructure `Bits` so a single atomic "claim" operation performs the check-and-set together, similar to a compare-and-swap), so no second goroutine can observe the pre-update window state for the same counter while a decrypt is in flight. This mirrors the report's mitigation guidance: eliminate the non-atomic gap by ensuring the read-then-write of the shared anti-replay state happens under one lock, not two.

### Proof of Concept
Not independently reproducible from static analysis alone (requires live packet duplication timing); the race is demonstrated structurally by the code path in `connection_state.go` lines 61-82, where `window.Check` and `window.Update` are two separate critical sections separated by an unlocked `DecryptDanger` call. Precise exploitability (e.g., whether decrypted output is acted upon before the final `Update` result is checked further up the call stack in `outside.go`) could not be fully confirmed within available tool calls and would benefit from tracing the full caller chain in `outside.go`/`interface.go`.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
