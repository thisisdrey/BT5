### Title
Precision-loss / unbounded floating-point Bancor-formula pricing in `ExchangeTransactionActuator` allows exchange-pool price manipulation and value extraction, analogous to the APC swap price-manipulation exploit - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The APC report exploited an AMM-style `swap` function that computed output amounts using an internally-tracked, manipulable price rather than a bounded/verified market price, letting the attacker pump/dump the price within one transaction and extract value. java-tron's built-in TRC10/TRX `Exchange` (a Bancor-relay style AMM reachable by any signed `ExchangeTransactionContract` transaction) has a structurally analogous weakness: its default, unhardened pricing path (`ExchangeProcessor`) computes swap output using unbounded `double` arithmetic with truncating casts and no overflow/rounding safety, while a corrected, safe implementation (`SafeExchangeProcessor`, `BigDecimal`-based, rounding-controlled, overflow-checked) exists but is only used when a chain-wide proposal flag `allowHardenExchangeCalculation` is turned on — which is off by default.

### Finding Description
`ExchangeTransactionActuator.execute()` computes the counter-asset amount via `ExchangeCapsule.transaction()`: [1](#0-0) 

`ExchangeCapsule.transaction()` selects the pricing engine based on the `allowHardenExchangeCalculation` dynamic property: [2](#0-1) 

When hardened calculation is not enabled (the default, as shown by every actuator test explicitly having to call `saveAllowHardenExchangeCalculation(1)` to exercise the safe path), the actuator uses `ExchangeProcessor`, which performs the Bancor relay formula entirely in `double` precision with truncating `(long)` casts and no bounds/overflow checking: [3](#0-2) 

By contrast, the "hardened" implementation uses `BigDecimal` with explicit rounding and `StrictMathWrapper` overflow guards, and `ExchangeCapsule.transaction()` explicitly rejects negative resulting balances only in the hardened path: [4](#0-3) [5](#0-4) 

This mirrors the APC bug class exactly: a swap/price mechanism reachable by any unprivileged transaction broadcaster (`ExchangeTransactionContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`) computes exchange output with floating-point, non-bounds-checked math instead of exact, overflow-safe arithmetic. An attacker can:
1. Use `ExchangeInjectActuator`/repeated `ExchangeTransactionContract` calls to push the pool's relative token balances to extreme ratios (as in "pump" in the APC PoC), where `double` precision loss and truncation in `exchangeToSupply`/`exchangeFromSupply` diverges most from the exact Bancor invariant.
2. Execute a trade at the manipulated ratio to extract more of the counter asset than the true invariant would allow, exploiting rounding/truncation drift accumulated across sequential trades in the unhardened processor (`(long) issuedSupply`, `(long) exchangeBalance` truncation with no negative-balance check as shown by the addExact/subtractExact only doing plain `+`/`-` unless hardened is enabled, per `AbstractExchangeActuator`): [6](#0-5) 
3. Repeat/reverse the trade to realize a net profit, draining TRX/TRC10 liquidity from the exchange pool, functionally equivalent to the APC "pump → swap at wrong price → dump" pattern, without needing an external flash loan since the manipulation and extraction all occur through the same account's sequential `Exchange*` contract calls.

### Impact Explanation
A successful exploit permits unbacked extraction of TRX or TRC10 tokens from an `Exchange` liquidity pool created by any user, i.e., theft of funds from the exchange pool's counter-party liquidity, satisfying the "theft/unbacked balance" impact bar. Because `ExchangeProcessor` is the default and live pricing path (hardening is an opt-in proposal not enabled by default), this is directly reachable in the current default configuration.

### Likelihood Explanation
Reachable by any account holding TRX/TRC10 balances and able to submit `ExchangeCreateContract`, `ExchangeInjectContract`, and `ExchangeTransactionContract` transactions — no special privilege required. The vulnerable arithmetic path (`ExchangeProcessor`) is the default behavior unless the `allowHardenExchangeCalculation` maintenance proposal has been separately activated on the network, which the repository's own tests treat as a non-default, explicitly-enabled mode.

### Recommendation
Make the `SafeExchangeProcessor` (or equivalent `BigDecimal`/overflow-checked, rounding-consistent) pricing math the mandatory, non-optional path for all `Exchange*` actuators rather than gating it behind a dynamic property that defaults to disabled. Add invariant checks (e.g., product/relay-supply must not decrease for the pool owner's benefit across sequential trades in the same block) and reject any state transition producing negative or precision-inconsistent balances regardless of the hardened flag.

I could not construct a concrete numeric PoC transaction sequence within the scope of this analysis (no ability to execute code); the finding is based on direct code-level comparison between the default unhardened `ExchangeProcessor` (double-precision, truncating, unchecked) and the hardened `SafeExchangeProcessor`/`ExchangeCapsule.transaction()` overflow guard that is conditionally skipped, per: [7](#0-6) .   public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
