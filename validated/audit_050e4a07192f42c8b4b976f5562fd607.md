### Title
Cross-StackerDB chunk replay due to missing contract-ID domain separation in signature digest - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
The signature that authorizes a StackerDB chunk write is computed only over `slot_id`, `slot_version`, and `data_hash`. It never binds to the smart-contract identifier of the StackerDB the chunk is destined for. Any node that already possesses a validly-signed chunk for one StackerDB contract can relay/replay it — unmodified — as if it were destined for a different StackerDB contract, as long as that second contract happens to assign the same slot ID to the same signer address. This breaks the intended equality "signature authorizes a write to *this* database's slot" and instead only proves "signature authorizes a write to *some* database's slot with this ID."

### Finding Description
`SlotMetadata::auth_digest` computes the digest that is signed/verified for every chunk write: [1](#0-0) 

```rust
fn auth_digest(&self) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```

Note that the `QualifiedContractIdentifier` (the StackerDB instance) is not part of the hashed material. `SlotMetadata::verify` and `StackerDBChunkData::verify`/`recover_pk` rely solely on this digest: [2](#0-1) 

On the write path, `StackerDBTx::try_replace_chunk` looks up the expected signer *only* by `(smart_contract, slot_id)` and calls `slot_desc.verify(&slot_validation.signer)` — again, the contract identity never enters the signed payload: [3](#0-2) 

The same pattern repeats on the network-received-chunk path, where `PeerNetwork::validate_received_chunk` fetches the signer for `smart_contract_id`/`slot_id` and calls `slot_metadata.verify(&addr)`, still without any contract binding in the signed bytes: [4](#0-3) 

Because `StackerDBChunkData`/`StackerDBPushChunkData` carry the destination `contract_id` as a *separate, unsigned* field alongside the signed `(slot_id, slot_version, sig, data)` tuple, a relayer or MITM-capable peer can take a chunk that was legitimately signed by principal `P` for contract `A`'s slot `N`, and re-wrap it with a different `contract_id` (`B`). If contract `B` also assigns slot `N` to principal `P` (a common occurrence in this codebase, since the signer-set StackerDB contracts `.signers-0-...` and `.signers-1-...` are re-derived every reward cycle from largely-overlapping reward sets, and slot assignment is a simple enumeration order — see `stackslib/src/chainstate/stacks/boot/signers.clar` and `stacks-signer/src/client/stacks_client.rs::get_parsed_signer_slots`), the recipient node will accept the chunk as valid for contract `B`, because every check it performs (`verify`, staleness, max-writes, size) only inspects `slot_id`/`slot_version`/`data_hash`, never the contract identity that was supposedly authorized.

### Impact Explanation
This allows an unprivileged network participant to get data authored for one StackerDB application-namespace stored/propagated under a different StackerDB namespace, as long as slot-signer alignment coincides (which is systematic for the two rotating signer-set contracts used every reward cycle). This is a "forged/misattributed data written to state without the actual private key holder's intent for that destination" bug — the owner never signed anything scoped to contract `B`, yet the write is accepted and further gossiped/broadcast network-wide via `PeerNetwork::process_stacker_db_chunks`, matching the High-impact class of "network-wide propagation of forged data" and "non-canonical/misattributed state served/stored as canonical" for that contract's replica.

### Likelihood Explanation
Any peer already relaying legitimate StackerDB traffic (a normal, unprivileged role in this gossip protocol) can perform this substitution purely by editing the unsigned `contract_id` field before rebroadcasting — no cryptographic material or privileged role is required, only knowledge of the target contract's slot-to-signer mapping, which is public (queried via the `stackerdb-get-signer-slots-page` read-only contract call, or from any node's `/v2` StackerDB endpoints).

### Recommendation
Include the `QualifiedContractIdentifier` (and ideally chain/network identifiers) as part of the hashed material in `SlotMetadata::auth_digest`, so that a signature is only valid for the specific StackerDB instance it was created for. This requires threading the contract ID into `sign()`/`verify()`/`auth_digest()` in `libstackerdb/src/libstackerdb.rs`, and updating all call sites in `stackslib/src/net/stackerdb/db.rs` and `stackslib/src/net/stackerdb/mod.rs` accordingly.

### Proof of Concept
1. Principal `P` is assigned slot `3` in both `SP000...signers-0-1` and `SP000...signers-1-1` (common when the reward-set signer roster doesn't change between the two rotating cycles).
2. `P` signs and pushes a legitimate `StackerDBChunkData{slot_id:3, slot_version:5, data, sig}` for `signers-0-1` via `StackerDBPushChunkData{contract_id: "signers-0-1", chunk_data}`.
3. An attacker-controlled relaying peer intercepts this message and re-emits `StackerDBPushChunkData{contract_id: "signers-1-1", chunk_data}` (same `chunk_data`, unmodified signature).
4. The receiving node's `handle_unsolicited_StackerDBPushChunk` → `validate_received_chunk` → `SlotMetadata::verify` all pass because none of them hash or check `contract_id`, so the chunk (data authored for the other cycle's signer set) is stored into `signers-1-1` slot 3 and rebroadcast network-wide via `process_stacker_db_chunks`.

    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
