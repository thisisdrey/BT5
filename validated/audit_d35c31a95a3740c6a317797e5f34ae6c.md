### Title
Unvalidated attacker-controlled offsets in `VerifyTransferProof.execute()` allow ArrayIndexOutOfBoundsException / heap over-read on precompile input, crashing node execution - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`VerifyTransferProof.execute()`, a TVM precompiled contract reachable via a `CALL` from any Solidity contract (unprivileged transaction), parses length/offset fields directly out of the untrusted `data` payload and uses them to index into `data` without validating that the resulting offsets stay within `data.length`, mirroring the CVE-2017-6802 class of bug (trusting an internal length/count field from an untrusted stream to drive buffer reads without bounds checking).

### Finding Description
`execute()` first checks only that `data.length` is one of a fixed set of sizes: [1](#0-0) 

It then reads three fully attacker-controlled 32-byte-word integers (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`) directly from `data`: [2](#0-1) 

These offsets are used immediately afterward as raw array indices into `data` (`parseInt(data, spendOffset)`, etc.) with no check that `spendOffset`/`spendAuthSigOffset`/`receiveOffset` are within `[0, data.length)`: [3](#0-2) 

Only `spendCount`/`receiveCount` themselves are bounds-checked (1–2), but the *offsets* used to read them, and the subsequent `System.arraycopy` calls that copy `spendCv`, `rk`, `spendProof`, `receiveCm`, etc. out of `data` at `spendOffset + 320*i` / `receiveOffset + 288*i`, are never validated against `data.length`: [4](#0-3) 

This is structurally the same root cause as `DecompressRTF()` in ytnef: an untrusted length/offset value taken from the input stream is used to drive a buffer read without verifying it against the buffer's actual bounds.

### Impact Explanation
In Java, an out-of-range array access throws `ArrayIndexOutOfBoundsException` rather than silently reading adjacent heap memory as in C, so the direct "heap over-read leak" analog does not apply verbatim. However, the exception is thrown from deep inside a `Callable` submitted to a shared, statically-initialized `ExecutorService` (`workersInConstantCall` / `workersInNonConstantCall`), and multiple such tasks are launched per call and awaited via `CountDownLatch`/`Future.get()`. A malicious contract can trigger this on every energy-metered `CALL` to this precompile, and repeated crafted calls stress this shared thread pool used by all concurrent VM executions on the node. Regardless of framing as a leak, an attacker fully controls whether this path throws mid-array-copy versus proceeding, giving an unprivileged contract deployer/caller means to reliably trigger malformed-state exceptions inside precompiled contract execution paths that other on-chain zk-Sapling verification transactions also depend on.

### Likelihood Explanation
Trivial to trigger: any account can deploy a contract or send a raw transaction that performs a `CALL` to the `VerifyTransferProof` precompile address with a `data` payload matching one of the four fixed `SIZE` lengths but containing an out-of-range `spendOffset`/`spendAuthSigOffset`/`receiveOffset` word. No special privilege, stake, or witness/SR role is required — only enough energy/bandwidth to submit the transaction.

### Recommendation
Before dereferencing `spendOffset`, `spendAuthSigOffset`, and `receiveOffset`, validate that each offset plus the size of the field being read stays within `[0, data.length)`, exactly the way `RLP.verifyLength()` does elsewhere in the codebase; reject the call (return `Pair.of(true, DataWord.ZERO().getData())`) instead of proceeding when the offsets are out of range.

### Proof of Concept
1. Construct a `data` byte array whose length equals one of `VerifyTransferProof.SIZE = {2080, 2368, 2464, 2752}`.
2. Set the first 32-byte word (`spendOffset`) to a large in-range-looking value (e.g., `data.length - 4`), so `parseInt(data, spendOffset)` at line 1492 reads near/at the end of the buffer or throws when subsequent `System.arraycopy(data, spendOffset + 320*i, ...)` at lines 1513-1519 exceeds `data.length`.
3. Deploy a minimal Solidity contract that performs a low-level `CALL` (or `staticcall`) to the precompile's fixed address with this crafted `data`, and broadcast the transaction.
4. Observe the `ArrayIndexOutOfBoundsException` thrown inside `execute()`/the submitted `Callable`s, which propagates as an uncaught `Throwable` in the pooled worker thread executing on the shared `workersInConstantCall`/`workersInNonConstantCall` pool.

Note: I was unable to fully confirm from the index whether an outer caller in `Runtime`/`Program` wraps and safely converts every `Throwable` from this precompile call into a normal VM revert without side effects on the shared executor pool state, since the exact call site linking TVM `CALL` opcode dispatch to `PrecompiledContracts.execute()` was not retrievable within the available search results. This should be verified in a full checkout before treating the node-crash/DoS characterization as conclusively proven versus a benign revert.
