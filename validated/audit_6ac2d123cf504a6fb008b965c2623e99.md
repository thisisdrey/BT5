### Title
Ordering-dependent Nakamoto block push validation aborts relay of valid co-batched blocks - (File: stackslib/src/net/relay.rs)

### Summary
`Relayer::validate_nakamoto_blocks_push()` iterates over all blocks in a single `NakamotoBlocksData` push message and calls `load_nakamoto_reward_set()` for each block's sortition/reward-cycle. If the reward-cycle lookup fails for any reason (mapped to `net_error::ChainstateError`, `net_error::DBError`, or `net_error::NoPoXRewardSet`), the function returns `Err` immediately via `?`/`return Err(...)`, aborting validation of the entire batch before later blocks are examined. The caller in `Relayer::process_pushed_nakamoto_blocks` treats this as a hard failure and `break`s out of the per-neighbor block loop entirely, so no block in that push — including ones that would have independently validated successfully — is ever processed or relayed.

### Finding Description
`validate_nakamoto_blocks_push` loops `for nakamoto_block in nakamoto_blocks_data.blocks.iter()` [1](#0-0) . For each block it resolves the sortition for its `consensus_hash`, and if the sortition is known and reward-cycle info for that sortition's reward cycle isn't already cached, it calls `load_nakamoto_reward_set(...)`, mapping any `CoordinatorError` into a `net_error` and propagating it with `?`, or explicitly returning `Err(net_error::NoPoXRewardSet(sn_rc))` when the reward set isn't yet resolvable [2](#0-1) . Any of these `Err` paths short-circuits the whole function — the loop never reaches subsequent blocks in the same `nakamoto_blocks_data.blocks` slice.

The caller, `Relayer::process_pushed_nakamoto_blocks` (in the same file, around lines 1667-1679), calls `validate_nakamoto_blocks_push` once per pushed `NakamotoBlocksData` batch, and on `Err` it logs and does `break;`, which exits the loop that would otherwise iterate `nakamoto_blocks_data.blocks.drain(..)` and process each block individually via `process_new_nakamoto_block` [3](#0-2) . Consequently, no block from that batch — valid or not — is stored or relayed, regardless of position.

Because the sender fully controls the ordering of blocks within a single `NakamotoBlocksData` push, placing a block referencing a sortition whose reward cycle is not yet resolvable (e.g., a real-but-recent sortition close to a reward-cycle boundary where the anchor block hasn't been finalized, giving `Ok(None)` → `NoPoXRewardSet`) as the *first* block in the batch causes the entire batch to be dropped before any other block is examined — even a legitimate, otherwise-valid second block.

Note: an attacker cannot forge a `consensus_hash`/sortition out of thin air — it must correspond to a real sortition already recorded in the node's `SortitionDB`. But an attacker does not need to forge anything: they only need to reference an existing, legitimately-recognized sortition whose associated reward cycle's anchor block/reward set has not yet been determined by that particular node (a naturally-occurring, timing-dependent state near reward-cycle boundaries), which triggers the `NoPoXRewardSet` early return.

### Impact Explanation
The effect is a relay-suppression / availability issue rather than data corruption: a single crafted push batch with an "unready reward-cycle" block placed first causes the relayer to discard all blocks in that batch, including co-batched blocks that would have passed validation on their own. This can suppress propagation of legitimately valid Nakamoto blocks through this particular push message, forcing reliance on other propagation paths (other peers' pushes, inventory-based download) to eventually receive the same blocks. No blocks are stored under the wrong state and no forged data is accepted as canonical; the impact is bounded to delayed/suppressed relay of specific blocks via this vector, which matches the "bounded compute/availability effect" framing given in the prompt.

### Likelihood Explanation
The attacker needs no privileged role — they only need P2P connectivity and the ability to send a `NakamotoBlocksData` push containing multiple blocks in a chosen order, one of which references a real sortition whose reward cycle is not yet resolvable by the target node. This condition (a resolvable-but-not-yet-anchored reward cycle) is a normal, recurring state near reward-cycle boundaries, making the precondition achievable without any DB/chainstate corruption. Repeating the attack is possible for every batch pushed while such a transient unresolved-reward-cycle window exists, though the recipient node will still catch up via other propagation mechanisms, limiting long-term impact.

### Recommendation
Change `validate_nakamoto_blocks_push` (and its caller) to validate each block independently, collecting per-block accept/reject results instead of returning on the first failure, so that a single unresolvable/invalid block does not prevent evaluation of the remaining blocks in the same push batch. Concretely, the `for nakamoto_block in nakamoto_blocks_data.blocks.iter()` loop in `stackslib/src/net/relay.rs` should use `continue`/`Vec<Result<...>>`-style per-item handling for reward-cycle load failures rather than propagating a single `Err` for the whole batch, and `process_pushed_nakamoto_blocks` should not `break` the entire per-neighbor processing loop on a single validation failure.

### Proof of Concept
Add a test in `stackslib/src/net/tests/relay/nakamoto.rs` similar to existing `NakamotoBlocksData` push tests:
1. Set up a Nakamoto-enabled test chainstate/sortdb where reward cycle `N+1`'s anchor block/reward set has not yet been determined (achievable by stopping tenure processing right before the prepare-phase anchor block is selected, mirroring existing test helpers in that file).
2. Construct `block_a` with `header.consensus_hash` pointing to a sortition in the still-unresolved reward cycle `N+1`.
3. Construct `block_b` as a normal, fully valid Nakamoto block from an already-resolved reward cycle (would pass validation standalone — verify this by calling `validate_nakamoto_blocks_push` with only `block_b` in a `NakamotoBlocksData` and asserting `Ok(())`).
4. Build `NakamotoBlocksData { blocks: vec![block_a, block_b] }` and call `Relayer::validate_nakamoto_blocks_push(&burnchain, &sortdb, &mut chainstate, &stacks_tip, &nakamoto_blocks_data)`.
5. Assert the call returns `Err(net_error::NoPoXRewardSet(_))` (or `net_error::ChainstateError`/`net_error::DBError` depending on the exact failure mode), demonstrating that `block_b` was never reached/validated despite being well-formed, confirming the order-dependent batch-abort behavior described.
