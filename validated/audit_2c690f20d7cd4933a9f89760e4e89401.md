### Title
Unbounded array allocation from user-controlled length in TVM precompile array extraction helpers causes node OutOfMemoryError DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The helper methods `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` read a length word directly from precompile call data and immediately allocate a Java array of that length, with no upper bound check against the actual size of the call data or any energy/memory limit evaluation before the allocation occurs.

### Finding Description
`extractBytesArray` and `extractSigArray` read `len` from `words[offset].intValueSafe()` — a value fully controlled by the calling contract's ABI-encoded input — and immediately execute `byte[][] bytesArray = new byte[len][];` before validating that `len` is consistent with the real amount of data supplied: [1](#0-0) [2](#0-1) 
`extractBytes32Array` has the identical pattern: [3](#0-2) 

These helpers are used by precompiled contracts (referenced by `ValidateMultiSignContractTest.java` and `BatchValidateSignContractTest.java`, indicating usage in the `ValidateMultiSign`/`BatchValidateSign` precompiles) that are reachable by any account issuing a normal TVM contract call that invokes the corresponding precompile address. Unlike the TVM opcode memory operations (`Memory.extend`, `EnergyCost.checkMemorySize` against `MEM_LIMIT`) which enforce a hard cap before any allocation: [4](#0-3) 
the precompile array-extraction helpers perform the allocation with no equivalent bound check on `len`, so a large `len` value (up to `Integer.MAX_VALUE`, since `intValueSafe()` only clamps to `int` range) results in an attempt to allocate an array of that many object references directly on the heap — this mirrors the Elasticsearch bug class precisely: a user-supplied count drives an allocation that isn't checked against any circuit breaker/limit before the allocation happens.

### Impact Explanation
An allocation request for `new byte[Integer.MAX_VALUE][]` (or similarly large) attempts to reserve roughly 8–16+ GB for the reference array alone, which will throw `OutOfMemoryError`. Because this is thrown outside a controlled bytecode-execution gas-accounting path (it happens during precompile input parsing, prior to normal per-instruction energy deduction), it risks propagating as an uncaught fatal error that can crash the node process — a denial-of-service impacting that node's block processing and API serving capability, analogous to the reported ES node crash.

### Likelihood Explanation
Any account can trigger the precompile call with a single, cheaply crafted transaction (no special privileges), so likelihood is high if the precompile is reachable with attacker-controlled data lengths and the surrounding actuator/interpreter does not already reject the transaction earlier via calldata-size or energy-limit checks. However, I could not verify within the available index content whether the outer `execute()` methods of `ValidateMultiSign`/`BatchValidateSign` (not shown in the retrieved snippets) impose their own length sanity check on `len` before calling these helpers, or whether the surrounding energy-cost calculation already bounds the array size indirectly via required call data length. This is the main uncertainty in confirming full exploitability.

### Recommendation
Add an explicit upper-bound check on `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` (e.g., reject if `len` exceeds a small sane maximum or if `len` is inconsistent with the actual length of `data`) before allocating the array, mirroring the `checkMemorySize`/`MEM_LIMIT` pattern used elsewhere in the VM.

### Proof of Concept
Conceptually: craft a transaction calling the `ValidateMultiSign` or `BatchValidateSign` precompiled contract address with call data whose length-prefix word (interpreted via `intValueSafe()`) is set to a very large value (e.g., `0x7FFFFFFF`) while the actual trailing data is short. This drives `extractBytesArray`/`extractSigArray` to execute `new byte[len][]` with `len` near `Integer.MAX_VALUE`, attempting a multi-gigabyte allocation on a single small, cheap transaction.

*Note: I was unable to fully view the outer `execute()` bodies of the `ValidateMultiSign`/`BatchValidateSign` precompile classes within the indexed content (only the shared helper methods and unrelated precompiles like `ModExp`, `BN128*` were retrieved), so the exact call sites and any pre-existing length validation performed by the callers could not be confirmed. A full-repository session would be needed to inspect those call sites directly.*
