### Title
Fee-exempt threshold on `TokenDiff::token_fee` for `Nep245`/`Imt` (`amount <= 1`) is applied per-intent, letting a signer bypass the protocol fee entirely by splitting one large negative delta into multiple unit-sized `TokenDiff` intents in the same `MultiPayload` - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::token_fee` waives the fee for `Nep245`/`Imt` tokens whenever the intent's own `|delta|` is `<= 1`, and `TokenDiff::execute_intent` computes `fee_ceil` independently per `TokenDiff` intent rather than over the aggregate negative delta of a token across the whole batch. A signer moving out 2 units of the same `Nep245`/`Imt` token can submit two `TokenDiff` intents of `delta = -1` each in a single signed `MultiPayload` and pay zero fee, whereas an honest signer submitting one `delta = -2` intent pays `fee_ceil(2)`.

### Finding Description
The invariant claimed (`FEES`) is: fees credited to `fee_collector` for token `T` == `Pips::fee_ceil` applied over every negative delta of `T` in the batch, independent of how the signer partitions an equivalent total transfer into multiple intents.

which explicitly special-cases `Nep245`/`Imt` tokens: fee is charged (`fee_ceil`) only `if amount > 1`; for `amount <= 1` it returns `Pips::ZERO`, per the comment "do not take fees on NFTs and MTs with `|delta| <= 1`".

`TokenDiff::execute_intent` computes this fee **per `TokenDiff` intent**, using that specific intent's own `unsigned_abs()` delta as `amount`: [2](#0-1) 

Because a `MultiPayload`/`DefuseIntents` batch can contain an arbitrary `Vec<Intent>` executed sequentially, each `TokenDiff` is dispatched and its fee is computed independently: [3](#0-2) [4](#0-3) 

There is no aggregation of deltas across intents for the same `(signer_id, token_id)` before the `amount > 1` threshold check is applied. Consequently:

- **Honest/merged submission**: one `TokenDiff{ diff: {T: -2} }` intent → `amount = 2 > 1` → `token_fee = protocol_fee` → fee collected = `protocol_fee.fee_ceil(2)` (nonzero for nonzero `protocol_fee`).
- **Split submission**: two `TokenDiff{ diff: {T: -1} }` intents in the same `MultiPayload` (same nonce space, sequentially applied) → each has `amount = 1`, hits the `TokenIdType::Nep245 | TokenIdType::Imt` catch-all arm and returns `Pips::ZERO` → fee collected = `0 + 0 = 0`.

Both submissions move the identical total quantity (2 units of `T`) out of the signer's balance and into the recipient side of the batch (via matching positive deltas elsewhere in the batch, or an equivalent counter-flow), so the net token movement is identical, yet `fee_collector`'s balance differs by `protocol_fee.fee_ceil(2)` between the two cases. None of `MultiPayload::verify`, nonce/salt checks, or `TransferMatcher::finalize` re-aggregate deltas per token across intents for fee purposes — those mechanisms validate signatures/replay/balance-conservation, not fee amount, so they do not prevent this divergence.

### Impact Explanation
Any unprivileged signer holding a `Nep245`/`Imt` balance can deterministically reduce the protocol fee on any transfer to zero (or to a lower tier) by decomposing it into multiple unit (`amount == 1`) `TokenDiff` intents within one signed batch, instead of a single intent with the true aggregate delta. This is systematic, repeatable at will by any account, for any `Nep245`/`Imt` token, and scales with volume (an attacker can always decompose any negative delta into `N` intents of `-1` to fully avoid fees, since `fee_ceil` of amount `1` is defined to be `Pips::ZERO` regardless of `protocol_fee`). This matches the explicitly listed Critical category "protocol fees bypassed or over-collected" — it is fee under-collection, directly reducing `fee_collector`'s revenue versus what the `FEES` invariant guarantees for equivalent net token movement.

### Likelihood Explanation
The attacker needs only: a `Nep245`/`Imt` balance in the Verifier of 2+ units, the ability to build and sign their own `MultiPayload` with multiple `TokenDiff` intents (standard `execute_intents` capability, no special role), and a counter-flow to balance the batch (which the same signer or a colluding counterparty can trivially construct, since `TokenDiff` intents just need matching aggregate deltas across the batch). This requires no privileged role, no victim key, and no race condition — it is a pure client-side choice of how to encode an intent, fully within the attacker's control, and is repeatable every time they transact.

### Recommendation
Aggregate the `amount` used for the `Nep245`/`Imt` fee-exemption threshold check per `(signer, token_id)` across the entire intent batch (or across all `TokenDiff` intents processed within the same `execute_intents` call) before applying the `amount > 1` test, rather than evaluating it independently per single `TokenDiff` struct. Alternatively, remove/redesign the per-intent `amount <= 1` fee waiver so it cannot be trivially defeated by partitioning a transfer into multiple unit-sized intents in the same payload.

### Proof of Concept
`cargo test` in `contracts/defuse/core/src/intents/token_diff.rs` (or an integration test in the `defuse` contract crate) that:
1. Sets up an `Engine`/`State` with a signer holding `Nep245` token `T` balance = 2, `protocol_fee = Pips::ONE_PERCENT` (nonzero), and an empty `fee_collector` balance.
2. **Merged case**: constructs one `DefuseIntents { intents: vec![TokenDiff{ diff: {T: -2, U: <matching positive> } }] }`, executes it, and records `fee_collector`'s balance of `T` — expect `protocol_fee.fee_ceil(2) > 0`.
3. **Split case**: resets state, constructs `DefuseIntents { intents: vec![TokenDiff{ diff: {T: -1, U: ...}}, TokenDiff{ diff: {T: -1, U: ...}}] }` within one payload/nonce, executes it, and records `fee_collector`'s balance of `T` — expect `0`.
4. Assert `fee_collector_balance_merged != fee_collector_balance_split` (specifically `fee_collector_balance_split == 0 < fee_collector_balance_merged`) despite both scenarios moving the identical net `-2` of `T` out of the signer's account, proving the `FEES` invariant is violated by intent partitioning.

impl ExecutableIntent for Intent {
    fn execute_intent<S, I>(
        self,
        signer_id: &AccountIdRef,
        engine: &mut Engine<S, I>,
        intent_hash: [u8; 32],
    ) -> Result<()>
    where
        S: State,
        I: Inspector,
    {
        match self {
            Self::AddPublicKey(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            Self::RemovePublicKey(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            Self::Transfer(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            Self::FtWithdraw(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            Self::NftWithdraw(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            Self::MtWithdraw(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            Self::NativeWithdraw(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            Self::StorageDeposit(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            Self::TokenDiff(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            Self::SetAuthByPredecessorId(intent) => {
                intent.execute_intent(signer_id, engine, intent_hash)
            }
            Self::AuthCall(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            #[cfg(feature = "imt")]
            Self::ImtMint(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            #[cfg(feature = "imt")]
            Self::ImtBurn(intent) => intent.execute_intent(signer_id, engine, intent_hash),
        }
    }
}
