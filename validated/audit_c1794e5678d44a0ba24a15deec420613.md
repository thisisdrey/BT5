### Title
Unbounded attacker-controlled attachment content stored as permanently-instantiated Atlas data due to missing hash verification on `GetAttachmentResponse` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
When the Atlas downloader fetches an attachment from a peer to satisfy a specific `AttachmentRequest{content_hash}`, it never checks that the returned `Attachment.content` actually hashes to the requested `content_hash` before calling `AtlasDB::insert_instantiated_attachment`. A malicious peer that is selected as a source for a legitimate, on-chain `AttachmentInstance` can return arbitrary, unrelated content instead, which gets permanently stored in the `attachments` table marked `was_instantiated = 1` — bypassing even the `evict_expired_uninstantiated_attachments()` backstop, which only targets non-instantiated rows.

### Finding Description
The broken equality is: `response.attachment.hash() == request.content_hash` is never checked.

Path:
1. `AttachmentsBatchStateContext::extend_with_attachments` decodes the HTTP response via `response.decode_atlas_get_attachment()` and unconditionally inserts the returned `Attachment` into `self.attachments` — with no comparison to the `AttachmentRequest.content_hash` that was actually requested: [1](#0-0) 
2. In `AttachmentsDownloader::run`, once the batch state machine reaches `Done`, every attachment collected in `context.attachments` is unconditionally passed to `network.atlasdb.insert_instantiated_attachment(&attachment)`, regardless of whether `find_all_attachment_instances(&attachment.hash())` found any matching confirmed instance: [2](#0-1) 
3. `evict_expired_uninstantiated_attachments()` is only called afterward and only prunes rows with `was_instantiated = 0`; content inserted via `insert_instantiated_attachment` is marked instantiated and is not subject to this or any other eviction. [3](#0-2) 

The requested `content_hash` in an `AttachmentRequest` does originate from a real, confirmed `AttachmentInstance` (i.e., the attacker cannot request arbitrary hashes), but the attacker fully controls the *content* returned in the HTTP response body for that request. Since the code never re-hashes the returned content and compares it to the hash it asked for, the peer can return any blob it wants. That blob gets stored as if it were validated, on-chain-committed content — this breaks the invariant that the `attachments` table's content is tied to a confirmed `AttachmentInstance.content_hash`.

This is worse than the question's original framing (which assumed forged content lands in the uninstantiated pool, later swept by `evict_expired_uninstantiated_attachments`): here the forged content is written directly as *instantiated*, so the only backstop cited in the question does not even apply to this specific write path.

### Impact Explanation
An attacker who is selected as a download source for at least one legitimate, unresolved `AttachmentInstance` (which requires only running an ordinary peer and advertising the relevant attachment inventory bit) can cause the victim node to permanently store attacker-chosen content in its `AtlasDB`, unbounded by any on-chain commitment and immune to the uninstantiated-attachment eviction routine. Repeated across many distinct outstanding `AttachmentInstance`s (there can be many missing BNS-name-registration attachments network-wide) and across retries, this causes attachment storage bloat that is never reclaimed. This matches the "High — attachment/BNS mismatch" impact category: content served/stored under an attachment identity does not correspond to what any on-chain operation actually committed to.

### Likelihood Explanation
- The attacker needs no privileged role: it just needs to run a normal P2P/RPC-reachable peer, respond to `GetAttachmentsInv` requests claiming to have the requested page/bit, and answer the follow-up `/v2/attachments/<hash>`-style GET with arbitrary bytes.
- The victim's peer selection logic (`get_prioritized_attachments_requests`) picks any peer whose inventory response claims to have the attachment; a malicious peer just needs to falsely claim availability to be selected as a source.
- Cost to attacker is a single crafted HTTP response per targeted `AttachmentInstance`; this is easily repeatable across every outstanding/missing attachment instance and across the `max_attachment_retry_count` retry cycle.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (stackslib/src/net/atlas/download.rs), after decoding `response.decode_atlas_get_attachment()`, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; drop/penalize (mark faulty) the peer and skip insertion if the hash does not match.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/tests.rs`:
1. Build an `AttachmentsBatchStateContext` with a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map has one `AttachmentRequest{content_hash: X}` paired with a fabricated `StacksHttpResponse` encoding `GetAttachmentResponse{ attachment: Attachment{ content: <arbitrary bytes Y> } }` where `Hash160::from_data(&Y) != X`.
2. Call `extend_with_attachments` and observe `context.attachments` contains the mismatched attachment.
3. Drive `AttachmentsDownloader::run` through to `Done`, then query `AtlasDB` (`find_attachment(&Hash160::from_data(&Y))`) and assert the mismatched content is present and `was_instantiated = 1`, while no `AttachmentInstance` in the DB has `content_hash == Hash160::from_data(&Y)` — demonstrating storage of unverified, non-canonical attachment content that survives `evict_expired_uninstantiated_attachments()`.
