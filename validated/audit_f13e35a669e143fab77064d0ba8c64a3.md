### Title
`write-freq` rate limit set by the StackerDB controlling contract is not enforced on the chunk-write acceptance path - ([File: stackslib/src/net/stackerdb/db.rs])

### Summary
The report describes an underwriter defeating a designed timing gate (`lockup period`) because the *request* side of a two-phase mechanism is enforced, but the *commit* side carries no obligation, letting the actor keep the benefit while avoiding the intended cost. The StackerDB subsystem has an analogous two-sided gate: the smart contract specifies a `write-freq` (minimum interval between writes to a slot), but this constraint is enforced only on the *pull*/download decision path, never on the *write-acceptance* path that actually persists and re-broadcasts a chunk.

### Finding Description
`StackerDBConfig` carries a contract-specified `write_freq` value [1](#0-0)  that is intended to bound how often a slot may be legitimately rewritten, and `StackerDBConfig` stores it alongside `max_writes` and `chunk_size` [2](#0-1) .

The actual chunk-acceptance routine, `try_replace_chunk`, only checks chunk size, slot-signer validity, staleness (`slot_version <= stored version`) and `max_writes` — it never reads or checks `write_freq`: [3](#0-2) 

`validate_received_chunk`, used both for chunks pulled during sync and for chunks pushed unsolicited by a peer, explicitly documents that it does *not* check write frequency: "NOTE: does not check write frequency, since the caller has different ways of doing this" [4](#0-3) , and its checks are limited to chunk size, expected-version, signer, staleness, and max-writes [5](#0-4) .

The only place `write_freq` is actually consulted is `StackerDBSync::find_missing_chunks`, which uses it purely to decide whether *this node* should bother requesting/pulling a chunk from peers — it skips chunks whose `write_ts + write_freq > now` [6](#0-5) . This is a local scheduling optimization, not an acceptance gate.

Consequently, a signer who legitimately owns a slot can submit a validly-signed chunk with a monotonically increasing `slot_version` as fast as it wants (bounded only by `max_writes`, not by time), via either:
- `POST /v2/stackerdb/:principal/:contract/chunks`, which decodes the request and hands the chunk to the StackerDB write path without any write-frequency check [7](#0-6) , or
- an unsolicited `StackerDBPushChunk` gossip message, validated only via `validate_received_chunk` (no `write_freq` check) before `try_replace_chunk` stores it.

Every chunk that clears `try_replace_chunk` is treated as "new," is committed, and is unconditionally rebroadcast network-wide: [8](#0-7) 

### Impact Explanation
This breaks the equality "contract-specified write cadence" vs. "cadence actually enforced by the replica." Any of the (potentially numerous) legitimate slot signers for a given StackerDB contract can flood the network with rapid, validly-signed rewrites of their slot up to `max_writes`, and every accepted write causes a mandatory broadcast to all directly connected peers of every node that stores that DB — an amplification of a single writer's requests into repeated network-wide propagation, at a cadence the controlling contract explicitly tried to prevent. This is a legitimate write (the signer owns the slot), so it is not an "unauthorized write" in the strict sense, but it does defeat a designed rate limit that other subsystems (and the contract author) rely on for bounding StackerDB churn/bandwidth, and it propagates every such write across the whole gossip network rather than being contained to the writer's own node.

### Likelihood Explanation
Any of the signer addresses configured for a StackerDB instance (a role that is not "the node operator" and does not require access to another party's key) can trigger this merely by issuing repeated signed HTTP POSTs or push messages; no timing coordination, race condition, or privileged access is required. It reproduces deterministically each time write_freq is set >0 by a contract, which the code and tests assume is the actual behavior.

### Recommendation
Enforce `write_freq` inside `try_replace_chunk` (or `validate_received_chunk` before calling it) by comparing `get_epoch_time_secs()` against the previously recorded `write_time` for a slot (already tracked in the `chunks` table's `write_time` column and exposed via `get_slot_write_timestamps` [9](#0-8) ), rejecting/erroring writes that arrive sooner than `write_freq` after the last accepted write for that slot, consistent with how `max_writes` and staleness are already enforced at that same call site.

### Proof of Concept
1. Deploy/observe a StackerDB contract with `write-freq: u3600` (i.e., one write per hour intended) and `max-writes: u4096`.
2. As one of the contract's registered signers, sign and submit `slot_version = 1`, then immediately `slot_version = 2`, `3`, ... in rapid succession via `POST /v2/stackerdb/:addr/:contract/chunks`.
3. Observe: `try_replace_chunk` at [3](#0-2)  accepts every submission (version strictly increasing, under `max_writes`), with no delay enforced.
4. Each accepted write is broadcast via `process_stacker_db_chunks` at [10](#0-9)  to the writer's peers, who accept it too (same missing check) and re-broadcast, defeating the contract's intended one-write-per-hour cadence across the whole network.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
