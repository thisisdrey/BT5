### Title
Sybil-account flooding of the global HOP data pool causes permanent denial of service to legitimate senders - (File: `substrate/client/hop/src/pool.rs`)

### Summary
The HOP off-chain data pool (`HopDataPool::insert`) enforces a **global** capacity (`max_size`) and a **per-`sender_id`** quota (`max_user_size`) plus a **per-`sender_id`** token-bucket rate limiter. All of these controls key exclusively on `sender_id` (an `AccountId32` derived from the submitter's signing key), which any caller can generate for free and in unlimited quantity. Because `hop_submit` only requires a locally-generated keypair plus a runtime "authorization" check that is itself account-based (`can_account_promote`), an attacker can rotate through many distinct signer identities to bypass both the per-user quota and the per-user rate limiter, filling the shared, bounded `max_size` capacity with worthless/junk data and blocking legitimate submitters from ever reserving space in the pool — directly analogous to the `MAX_BRIBES_PER_POOL` slot-filling DOS in the external report.

### Finding Description
`HopDataPool::insert` in `substrate/client/hop/src/pool.rs` performs, in order:
1. A per-account rate-limit check (`rate_limiter.check(&sender_id, accounted)`) — keyed by `sender_id`. [1](#0-0) 
2. A **global** capacity check against `max_size` via a shared `AtomicU64 current_size`. [2](#0-1) 
3. A per-account quota check (`charge_user`) against `max_user_size`, again keyed by `sender_id`. [3](#0-2) 

All fairness/anti-abuse mechanisms (rate limiter, per-user quota) are scoped to `sender_id`, while the actual scarce, shared resource — the pool's `max_size` byte budget — has no reservation, priority, or whitelist mechanism protecting legitimate senders. `sender_id` is simply `AccountId32` derived from an ed25519/sr25519/ecdsa key the caller generates locally in `HopRpcServer::submit`: [4](#0-3) 

Generating a new `AccountId32` is free (no on-chain existential deposit or balance is required to *sign* an RPC submission — this is an off-chain RPC endpoint, not an extrinsic that pays transaction fees). The only external gate is `can_account_promote`, a runtime call that determines whether an account is "authorized" to promote data on-chain, but nothing in the submit path prevents an attacker from being authorized (e.g. any account with a minimal balance/authorization threshold, which is exactly the kind of "permissionless but bounded-by-identity" check the original Sherlock report shows is insufficient) from being replicated across arbitrarily many freshly generated keys.

Because `max_user_size` and the rate limiter reset per `sender_id`, and `max_size` is shared and finite, an attacker who can obtain authorization for N distinct signer identities (each authorized the same way any genuine user would be) can submit `N × max_user_size` bytes of junk data — enough to consume the entire `max_size` global budget — causing every subsequent `insert` call from genuine senders to fail with `HopError::PoolFull`: [5](#0-4) 

Entries only free up when they expire (`retention_secs`) or are acked by all recipients (`ack`). Since the attacker's own junk entries have no legitimate recipients to ack them, they persist until `retention_secs` elapses, so the DOS lasts the full retention window and can be perpetually renewed by re-submitting new junk entries from newly rotated identities as old ones expire — mirroring the original report's ability to occupy bribe slots for arbitrarily many periods by rotating cheap resources (junk ERC20 tokens there, junk signer identities/junk data here).

### Impact Explanation
This maps to the "public underpriced work that degrades block production or stalls bridge processing" / message-queue-DOS category: the HOP pool is a message hand-off queue with a fixed capacity that legitimate senders depend on to relay data pending promotion to on-chain storage. Once `max_size` is exhausted by sybil junk entries, all genuine `hop_submit` calls fail (`PoolFull`) for the retention period, denying availability of the HOP relay mechanism to legitimate users — a direct capacity-exhaustion/service-stall analog to the BribeRewarder issue, where a bounded, permissionlessly-fillable resource is monopolized by an attacker using cheap/worthless inputs.

### Likelihood Explanation
Likelihood is high given the mechanics: no on-chain fee is charged for submission (this is an RPC path, not an extrinsic), account creation is free, and the only defenses (`max_user_size`, rate limiter) are keyed per-identity rather than being tied to any cost that scales with the number of identities. Any attacker able to satisfy `can_account_promote` for a given account (whatever threshold that runtime check enforces) can trivially replicate that condition across many keys, since key generation itself carries no cost.

### Recommendation
- Bind the shared `max_size` budget to an economic cost that scales per identity created (e.g., require the authorizing account to also stake/lock funds proportional to bytes reserved, verified via `can_account_promote`), or
- Introduce a reservation/whitelist system for the global pool capacity analogous to the fix applied to the BribeRewarder issue (`RewarderFactory`/whitelist PR): only allow authorized/whitelisted accounts (or accounts meeting a substantive stake/reputation threshold enforced per unique underlying identity, not per ephemeral key) to consume global pool capacity, and/or partition `max_size` into per-account/per-authorization-tier reserved sub-budgets so no single class of cheap identities can exhaust the shared resource.
- Consider charging bandwidth against a resource that cannot be sybil-multiplied for free (e.g., requiring a minimum bonded balance per `sender_id` verified on-chain, and rejecting further submissions from newly created accounts until they've held that balance for a cooldown period).

### Proof of Concept
Conceptual (cannot be executed without live node/runtime, since `can_account_promote` authorization logic lives in the runtime not shown here):
1. Attacker configures `max_size = S`, `max_user_size = S/K` (typical config).
2. Attacker generates `K` fresh ed25519 keypairs, each satisfying whatever minimal condition `can_account_promote` requires (e.g., existential-deposit-level balance, which is cheap/free to obtain per account).
3. For each key `i`, submit junk data via `hop_submit` up to `max_user_size` bytes with no real recipients that will ever ack it — this succeeds because `charge_user` is scoped per `sender_id`, so each of the `K` identities independently gets its full `max_user_size` allowance: [6](#0-5) 
4. After `K` submissions, `current_size` reaches `max_size`, and any subsequent `insert` from a genuine, distinct sender fails with `HopError::PoolFull`: [5](#0-4) 
5. Because the junk entries have no real recipients to `ack`, they remain until `retention_secs` expires (`cleanup_expired`), so the pool stays full and legitimate users are denied service for the full retention window; the attacker can repeat the process with new keys to sustain the DOS indefinitely. [7](#0-6) 

Note: I was unable to inspect the runtime-side implementation of `can_account_promote` (`HopRuntimeApi`) in this pass, so the exact authorization threshold/cost for obtaining a new authorized `sender_id` is unverified — this is the one variable that determines the attacker's actual cost-per-identity and thus the practical severity. If `can_account_promote` requires a substantial, non-trivially-multipliable stake per account, the sybil cost rises accordingly; if it only requires existential-deposit-level balance or is unconditionally true for any signed account, the attack is essentially free.

	fn charge_user(&self, sender_id: &SenderId, accounted: u64) -> Result<(), HopError> {
		// Fast path: sender already in map, a read guard is enough.
		{
			let usage = self.user_usage.read();
			if let Some(counter) = usage.get(sender_id) {
				return self.try_charge(counter, accounted);
			}
		}
		// Cold path: first insert from this sender — take the write guard.
		let mut usage = self.user_usage.write();
		let counter = usage.entry(*sender_id).or_default();
		self.try_charge(counter, accounted)
	}

	/// Atomically increment `counter` by `accounted`, rolling back on cap
	/// overflow. `saturating_add` clamps to `u64::MAX` if concurrent failing
	/// charges briefly inflate the previous value past the wrap point,
	/// ensuring overflow always falls into the "exceeds cap" branch.
	fn try_charge(&self, counter: &AtomicU64, accounted: u64) -> Result<(), HopError> {
		let previous = counter.fetch_add(accounted, Ordering::Relaxed);
		if previous.saturating_add(accounted) > self.max_user_size {
			counter.fetch_sub(accounted, Ordering::Relaxed);
			return Err(HopError::UserQuotaExceeded { used: previous, limit: self.max_user_size });
		}
		Ok(())
	}

	pub fn insert(
		&self,
		data: Vec<u8>,
		recipients: RecipientVec,
		sender_id: SenderId,
		signer: MultiSigner,
		signature: MultiSignature,
		submit_timestamp: u64,
	) -> Result<HopHash, HopError> {
		if recipients.is_empty() {
			return Err(HopError::NoRecipients);
		}
		let unique: BTreeSet<&MultiSigner> = recipients.iter().map(|r| &r.signer).collect();
		if unique.len() != recipients.len() {
			return Err(HopError::DuplicateRecipient);
		}

		if data.is_empty() {
			return Err(HopError::EmptyData);
		}

		let data_len = data.len() as u64;

		// Total accounted size includes bounded per-recipient metadata overhead so
		// a submitter cannot inflate memory via large recipient lists while the
		// capacity counter only tracks `data.len()`. Charge the rate limiter the
		// same accounted size, otherwise a 1-byte payload with 256 recipients
		// would cost ~10 KiB of pool capacity while only spending 1 byte of
		// bandwidth tokens — making the bandwidth dimension non-functional for
		// fan-out-heavy entries.
		let accounted = entry_accounted_size(data_len, recipients.len());

		// Rejected requests never reserve capacity — check before any atomic bump.
		if let Err(retry_after_secs) = self.rate_limiter.check(&sender_id, accounted) {
			return Err(HopError::RateLimited { retry_after_secs });
		}

		let previous_size = self.current_size.fetch_add(accounted, Ordering::Relaxed);
		if previous_size.saturating_add(accounted) > self.max_size {
			self.current_size.fetch_sub(accounted, Ordering::Relaxed);
			return Err(HopError::PoolFull(previous_size, self.max_size));
		}

		if let Err(e) = self.charge_user(&sender_id, accounted) {
			self.current_size.fetch_sub(accounted, Ordering::Relaxed);
			return Err(e);
		}

	pub fn cleanup_expired(&self) -> u64 {
		const CLEANUP_BATCH_SIZE: usize = 10_000;
		let mut total_freed: u64 = 0;
		let now_secs = SystemTime::now().duration_since(UNIX_EPOCH).unwrap_or_default().as_secs();

		loop {
			// Phase 1: Under index write lock — collect and remove up to one
			// batch of expired entries. Bounded so the lock hold scales with
			// batch size, not pool size.
			let expired: Vec<(HopHash, HopEntryMeta)> = {
				let mut index = self.index.lock();
				let expired_keys: Vec<HopHash> = index
					.iter()
					.filter(|(_, m)| now_secs >= m.expires_at)
					.map(|(h, _)| *h)
					.take(CLEANUP_BATCH_SIZE)
					.collect();

				expired_keys
					.into_iter()
					.filter_map(|hash| index.remove(&hash).map(|meta| (hash, meta)))
					.collect()
			};

			if expired.is_empty() {
				break;
			}

			// Phase 2: Update counters and batch user-quota release.
			let freed: u64 = expired
				.iter()
				.map(|(_, meta)| entry_accounted_size(meta.size, meta.recipients.len()))
				.sum();
			self.current_size.fetch_sub(freed, Ordering::Relaxed);
			total_freed = total_freed.saturating_add(freed);

			{
				let usage = self.user_usage.read();
				for (_, meta) in &expired {
					if let Some(counter) = usage.get(&meta.sender_id) {
						let accounted = entry_accounted_size(meta.size, meta.recipients.len());
						saturating_release(counter, accounted);
					}
				}
			}

			// Phase 3: Delete files from disk (best-effort, no locks held).
			for (hash, _) in &expired {
				let _ = fs::remove_file(self.blob_path(hash));
				let _ = fs::remove_file(self.meta_path(hash));
			}
		}

		// Phase 4: Reclaim per-sender counters whose owners have no live
		// entries. Holding `index.lock()` and `user_usage.write()` together
		// closes the dominant TOCTOU race (concurrent writers cannot create a
		// new index entry under our held index lock; concurrent
		// `release_user_quota` only takes `user_usage.read()` which is
		// excluded). Build a live-sender set in one index pass so retain is
		// O(senders + entries) instead of O(senders × entries).
		{
			let index = self.index.lock();
			let mut usage = self.user_usage.write();
			let live: HashSet<&SenderId> = index.values().map(|m| &m.sender_id).collect();
			usage.retain(|sender_id, counter| {
				counter.load(Ordering::Relaxed) > 0 || live.contains(sender_id)
			});
		}

		// Let the rate limiter shed stale per-sender state on the same cadence.
		self.rate_limiter.evict_stale();

		total_freed
	}
