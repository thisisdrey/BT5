### Title
Stale PromiseYieldReceipt survives DeleteAccount, causing timeout to force-execute an attacker-chosen FunctionCall against a re-created account's contract - ([File: runtime/runtime/src/lib.rs], [File: core/store/src/utils/mod.rs])

### Summary
`remove_account` in `core/store/src/utils/mod.rs` deletes `Account`, `ContractCode`, access keys, gas keys, and `ContractData`, but never removes `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, or the `YieldIdToDataId`/`DataIdToYieldId` mappings for the account being deleted. Combined with the fact that the global `PromiseYieldTimeout` queue entry (which references the account by name, not by any account-generation nonce) is processed independently in `resolve_promise_yield_timeouts`, a deleted-then-recreated account can have a stale self-directed `PromiseYield` receipt "resurrected" and executed against the new account's freshly deployed contract.

### Finding Description
1. `promise_yield_create` (`runtime/near-vm-runner/src/logic/logic.rs:3660`) creates a `PromiseYield` action receipt with `receiver_id == predecessor_id == current_account_id` (self-call) containing an attacker-chosen `FunctionCall` action, and enqueues a `PromiseYieldTimeout { account_id, data_id, expires_at }` entry in the global per-shard queue (`enqueue_promise_yield_timeout`, `core/store/src/utils/mod.rs:182`, called from `runtime/runtime/src/function_call.rs:162`).
2. When the `PromiseYield` receipt is processed, it is persisted under `TrieKey::PromiseYieldReceipt { receiver_id: a.near, data_id }` via `set_promise_yield_receipt` (`core/store/src/utils/mod.rs:200`, invoked at `runtime/runtime/src/lib.rs:1498`), along with a `PromiseYieldStatus` entry.
3. The attacker then submits `DeleteAccount` on `a.near`. `action_delete_account` (`runtime/runtime/src/actions.rs:314`) calls `remove_account` (`core/store/src/utils/mod.rs:504-575`), which removes `Account`, `ContractCode`, access keys/gas keys, and `ContractData` — but has no code path that touches `PROMISE_YIELD_RECEIPT`, `PROMISE_YIELD_STATUS`, `YIELD_ID_TO_DATA_ID`, or `DATA_ID_TO_YIELD_ID` for `account_id`. The stale `PromiseYieldReceipt`/`PromiseYieldStatus` entries remain in the trie, keyed by the now-freed account name `a.near`.
4. Anyone can subsequently `CreateAccount`/`DeployContract` a brand-new, unrelated contract at `a.near` (permitted by ordinary `check_account_existence`/`action_create_account` logic — nothing checks for leftover promise-yield state).
5. When the block height passes `expires_at`, `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3104`) dequeues the old `PromiseYieldTimeout` entry and checks `state_update.contains_key(&promise_yield_key)` where `promise_yield_key = TrieKey::PromiseYieldReceipt { receiver_id: a.near, data_id }` (`lib.rs:3047-3051`). This is still `true` because of the leak in step 3, so the runtime synthesizes a `PromiseResume(data: None)` receipt with `predecessor_id == receiver_id == a.near` (`lib.rs:3060-3068`) and forwards it.
6. This `PromiseResume` is processed by `process_receipt`/`PromiseResume` arm (`lib.rs:1500-1562`): it looks up and finds the stale `get_promise_yield_receipt`, removes the residual state, and directly calls `apply_action_receipt` on the stale `yield_receipt` — executing the attacker's original `FunctionCall(method_name, args)` against `a.near`'s **new** account/contract, with `predecessor_id == receiver_id == a.near` (i.e., appearing as a legitimate self-call).
7. Because `predecessor_id == receiver_id` is the exact pattern contracts commonly use to gate privileged/"private" methods (`assert_eq!(env::predecessor_account_id(), env::current_account_id())`), this forces execution of an attacker-chosen method with self-caller privilege on the victim's newly deployed contract before the victim ever invoked it, potentially bypassing initialization guards or triggering privileged state-mutating logic chosen entirely by the attacker before account recreation.

No existing check blocks this: `check_actor_permissions`/`check_account_existence` (`runtime/runtime/src/actions.rs:739-855`) only validate the `DeleteAccount` action itself (staking lock, actor==account), and `DeleteAccountWithLargeState` only bounds storage/contract state size — none of these inspect pending `PromiseYieldReceipt`/`PromiseYieldTimeout` state before allowing deletion.

### Impact Explanation
This is authorization escalation across accounts/promises: an attacker forces execution of an arbitrary, pre-chosen `FunctionCall` (method name + args, gas-limited by the amount prepaid at `promise_yield_create` time) against a contract the attacker never controls, with apparent self-caller (`predecessor_id == receiver_id`) authorization. If the victim's fresh contract has any privileged method gated only by the "self-call" check (a common and normally-safe pattern for internal callbacks, e.g. finalization/init/callback methods), the attacker can trigger it unsolicited — a real authorization-boundary violation matching NEAR's "authorization escalation across accounts or promises" bounty category. The concrete blast radius depends on what method/args the attacker pre-selected and what the victim's redeployed contract's self-privileged methods do (e.g., corrupting freshly initialized state, or invoking further self-privileged sub-actions), but the underlying primitive — forced unsolicited execution with spoofed self-authorization on an account the attacker doesn't own — is present regardless.

### Likelihood Explanation
- Fully attacker-reachable with an ordinary funded account: create account `a.near` (or use any existing account they control), call `promise_yield_create` with attacker-chosen callback method/args, then `DeleteAccount` — all via signed transactions, no special privileges needed.
- The only external dependency is that a third party (the "victim") independently chooses to create/deploy on the exact freed account name `a.near` before the yield timeout fires — this is a preexisting general risk of NEAR account-name reuse, but the specific mechanism here (a dangling privileged self-call receipt firing automatically at a protocol-chosen future block height) is a genuine, previously undocumented leak that other trie cleanup code (`ContractData`, access keys) explicitly avoids, indicating this is an oversight rather than intended behavior.
- Cost to the attacker is minimal: one yield-create call (prepaid gas for callback) plus one delete-account transaction; the timeout window is configurable (`yield_timeout_length_in_blocks`) and repeatable for any number of account names.

### Recommendation
In `remove_account` (`core/store/src/utils/mod.rs`), also iterate and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` entries keyed by the account being deleted (mirroring the existing access-key/gas-key/contract-data iteration-and-removal pattern), and/or have `resolve_promise_yield_timeouts` verify that the receiver account existed continuously (e.g., via an account-generation/creation nonce check) rather than relying solely on `contains_key` for the yield-receipt key.

### Proof of Concept
Test-loop integration test plan (extending `test-loop-tests/src/tests/yield_timeouts.rs` patterns, e.g. `prepare_env_with_yield`):
1. Deploy a contract to `a.near` and call a method that invokes `promise_yield_create` with `method_name = "malicious_callback"` and attacker-controlled `args`.
2. Submit `DeleteAccount { beneficiary_id: attacker }` for `a.near` in the following block; assert the account no longer exists via `view_account_query`.
3. Submit `CreateAccount` + `DeployContract` for `a.near` from a different signer, deploying a victim contract that exposes a self-privileged method (e.g., asserts `predecessor_id == current_account_id` before mutating critical state) — this simulates the "victim" recreating the account.
4. Advance blocks to `yield_timeout_height()` and `yield_timeout_height() + 1` as in `test_simple_yield_timeout`.
5. Assert that the resulting `PromiseResume` receipt executes `malicious_callback` against the victim's new contract (verify via state read that the attacker's args-driven side effect occurred, or via the transaction/receipt outcome), demonstrating the attacker forced unsolicited, self-privileged execution on the victim's account without the victim ever calling `malicious_callback`.
