### Title
`check_account_existence`/`check_actor_permissions` authorize by account-name equality only, with no per-account identity/incarnation check, letting stale postponed receipts (AddKey/DeployContract) execute against a re-created account of the same name - ([File: runtime/runtime/src/actions.rs])

### Finding Description
Both gating functions treat "same `AccountId`" as "same account" with no notion of account incarnation:

- `check_account_existence` (runtime/runtime/src/actions.rs:787-855) only inspects `account.is_none()`/`account.is_some()` for the `Option<Account>` freshly loaded from the trie at execution time. For `AddKey`, `DeployContract`, `DeleteKey`, `Stake`, etc. it merely requires `account.is_some()` [1](#0-0) .
- `check_actor_permissions` (runtime/runtime/src/actions.rs:739-785) authorizes privileged actions (`DeployContract`, `Stake`, `AddKey`, `DeleteKey`, etc.) purely via `actor_id != account_id` string comparison [2](#0-1) .

Neither function consults any field on the loaded `Account` object that could distinguish "the account that existed when this receipt/postponed action was created" from "whatever account currently occupies this `account_id`." The `Account` struct itself has no incarnation/generation counter, and these two functions are the sole authorization gates invoked by the runtime before an action executes against an account (`runtime/runtime/src/lib.rs` calls `check_account_existence`/`check_actor_permissions` per action). Consequently, if a postponed action receipt (e.g., a self-directed `AddKey` receipt created before the account was deleted, waiting on a data dependency) is later applied after the account has been deleted and a new, unrelated account with the identical `account_id` has been created, both checks pass unconditionally: `account.is_some()` is true (the new account exists) and `actor_id == account_id` still holds (the receipt was self-addressed to that name). No code path in either function compares the account's contents, code hash, storage root, or any versioning marker against the state that existed when the postponed receipt was generated.

This confirms the specific triage question: the authorization-exactness violation is structural in these two functions - they are inherently name-keyed, not instance-keyed - and is not something that could be patched by adjusting the `is_none()/is_some()` branches alone; it requires either (a) an explicit identity/version check tied to account recreation, or (b) ensuring `remove_account` fully purges/cancels any receipts (postponed or otherwise) still addressed to that name before the name becomes reusable.

### Impact Explanation
Isolated on its own, this is a missing-defense-in-depth finding: `check_account_existence`/`check_actor_permissions` provide no independent backstop against stale, previously-legitimate receipts executing on a semantically different account after deletion/recreation. Combined with the described delete-then-recreate sequence and surviving postponed `AddKey`/`DeployContract` receipt (the companion finding on `remove_account`), it enables authorization escalation across accounts: an attacker's previously-authorized (to their own now-deleted account) `AddKey` receipt fires against the new owner's account, granting the attacker a live access key on funds/contract they never controlled - matching NEAR's "authorization escalation across accounts" bounty category.

### Likelihood Explanation
Reachable entirely with unprivileged, self-funded actions: sign a function call to yourself that schedules a postponed `AddKey`/`DeployContract` receipt gated on a data dependency (callback), then delete your own account before the dependency resolves, and have any third party (or yourself via a fresh transfer) recreate an account of the same name before the postponed receipt fires. No validator/node/RPC-operator privilege is required. The remaining question is whether `remove_account`'s cleanup (evaluated separately) actually leaves such postponed receipts intact; this finding only establishes that even if it does, these two gate functions provide zero independent protection.

### Recommendation
Add an identity/version check independent of `account_id` string equality before authorizing privileged actions in `check_actor_permissions`/`check_account_existence` — e.g., bind postponed receipts to the account's storage/state root or an explicit incarnation counter incremented on `DeleteAccount`, and reject execution if the account's incarnation at receipt-creation time doesn't match the incarnation at execution time. This is a defense-in-depth complement to (not a substitute for) ensuring `remove_account` purges all postponed-receipt state for the deleted account.

### Proof of Concept
Unit test in `runtime/runtime/src/actions.rs` tests module:
1. Construct an `Option<Account>` representing a freshly created account for `account_id = "victim.near"` (different code hash/storage than any prior account of that name).
2. Call `check_actor_permissions(&Action::AddKey(...), &account, &actor_id, &account_id)` where `actor_id == account_id` (simulating a self-addressed postponed receipt originally created by the *old* incarnation of `victim.near`).
3. Call `check_account_existence(&Action::AddKey(...), &account, &account_id, &config, false)`.
4. Assert both return `Ok(())` — demonstrating no identity/incarnation check rejects execution against the new account, confirming the structural gap independent of `remove_account`'s behavior.

pub(crate) fn check_actor_permissions(
    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {
    match action {
        Action::DeployContract(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
        }
