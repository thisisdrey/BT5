### Title
Missing bounds validation when parsing ELF `.ARM.attributes` sections causes linker panic on malicious object files - ([File: src/cmd/link/internal/loadelf/ldelf.go])

### Summary
`parseArmAttributes` in `cmd/link/internal/loadelf` reads attacker-controlled 32-bit length fields (`sectionlength`, `subsectionsize`) directly from an ELF object's `.ARM.attributes` section and uses them to slice the underlying byte buffer without validating that the values are within bounds or internally consistent, analogous to the missing `IEEE80211_P2P_ATTR_CHANNEL_LIST` length validation in the CVE. In Go, this class of bug cannot cause memory corruption because slicing is bounds-checked, but it does produce an unrecoverable linker panic (`runtime error: slice bounds out of range`) when a crafted `.o`/`.a` file is linked.

### Finding Description
Attacker input: a malicious ELF relocatable object file (e.g., embedded in a `.a` archive or cgo-produced object) containing an `.ARM.attributes` section (`SHT_ARM_ATTRIBUTES`).
Go entry point: the linker's ELF object loader (`cmd/link/internal/ld` → `loadelf.Load`), which locates this section and calls `parseArmAttributes(e, data)` [1](#0-0) .

Inside `parseArmAttributes`:
- `sectionlength := e.Uint32(data)` is read directly from the file, then used as `sectiondata := data[4:sectionlength]` and `data = data[sectionlength:]` with no check that `4 <= sectionlength <= len(data)` [2](#0-1) .
- Similarly, the nested subsection length `subsectionsize := e.Uint32(sectiondata[sz:])` is used to compute `subsectiondata := sectiondata[sz+4 : subsectionsize]` and `sectiondata = sectiondata[subsectionsize:]` without validating that `subsectionsize >= sz+4` or `subsectionsize <= len(sectiondata)` [3](#0-2) .

A crafted length value (too small, too large, or causing `low > high`) triggers a Go runtime "slice bounds out of range" panic, crashing the `go build`/`go link` process instead of silently overflowing memory as in the C driver.

### Impact Explanation
This is a denial-of-service against the build/link toolchain: a victim who links a maliciously crafted ELF object (e.g., via `cgo`, a vendored `.syso`/`.o` file, or a static archive pulled in by a Go module) triggers a panic and aborts the build. There is no code execution or memory corruption because Go's runtime enforces slice bounds; the CVE's "heap-based buffer overflow" primitive does not carry over. This would likely be evaluated on Go's PUBLIC track at most, as a robustness/DoS issue in the linker's object-file parser, not a memory-safety vulnerability.

### Likelihood Explanation
The victim workflow is building/linking a Go program that includes a third-party or attacker-supplied ELF object file for ARM (via cgo or `-linkmode=external`/static archives). The attacker only needs to supply a malformed object file consumed by an ordinary `go build`, which matches an "unauthenticated"/untrusted-input premise, but per the Go Security Decisions rules, malicious *build-time source/object* consumption resulting only in a build-time panic (not code execution during `go build` itself) is a marginal case and typically not treated as a security vulnerability by the Go team since the failure mode is a panic, not arbitrary execution or memory unsafety.

### Recommendation
Add explicit bounds checks before slicing in `parseArmAttributes`: validate `sectionlength >= 4 && sectionlength <= len(data)` before computing `sectiondata`/`data`, and validate `subsectionsize >= sz+4 && subsectionsize <= len(sectiondata)` before computing `subsectiondata`/`sectiondata`; return a descriptive parse error (as already done elsewhere in the function) instead of panicking.

### Proof of Concept

```go
package loadelf

import "testing"

func TestParseArmAttributesOverflow(t *testing.T) {
    defer func() {
        if r := recover(); r == nil {
            t.Fatal("expected panic due to unchecked section length, got none")
        }
    }()
    // "A" marker byte followed by a crafted section with sectionlength=1
    // (less than the 4-byte length field itself), causing data[4:1] to panic
    // with "slice bounds out of range".
    data := []byte{'A', 0x01, 0x00, 0x00, 0x00}
    _, _, _ = parseArmAttributes(littleEndian{}, data)
}
```
Given Go's memory-safety guarantees, this reproduces only as a panic (DoS), not as the heap corruption described in the CVE — the primitives are not equivalent in severity, and I could not confirm this specific gap has been exploited or is treated as a security issue by the Go project; it is offered as the closest structural analog found in the scoped files.
