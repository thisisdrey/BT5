### Title
Unbounded on-chain fan-out via `DelegateResourceContract` allows DOS of `GetDelegatedResourceAccountIndexV2`/`GetDelegatedResourceAccountIndex` API queries - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
An unprivileged account holding a small amount of frozen bandwidth/energy can call `DelegateResourceContract` repeatedly, each time delegating the minimum allowed amount (1 TRX) to a distinct, arbitrary receiver address. Each such transaction creates a new key under the `V2_FROM_PREFIX`/`V2_TO_PREFIX` (or legacy `FROM_PREFIX`/`TO_PREFIX`) namespace in `DelegatedResourceAccountIndexStore`. There is no cap on the number of distinct receivers/senders an address can accumulate. When any client later queries `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` for that address, the node performs an unbounded `prefixQuery` over all matching keys and sorts the entire result set in memory, with no pagination or limit.

### Finding Description
`DelegateResourceActuator.validate()` only requires `delegateBalance >= TRX_PRECISION` (1 TRX) [1](#0-0)  and that owner/receiver addresses are valid and different [2](#0-1) . There is no limit on how many distinct receiver addresses a single owner can delegate to, nor on how many distinct owners can delegate to a single receiver.

Each successful delegation calls `delegatedResourceAccountIndexStore.delegate(...)`, which writes a new index entry per (from,to) pair rather than merging into a bounded structure [3](#0-2) .

The read path `getWithPrefix` (used by `getIndex`/`getV2Index`) performs a full `prefixQuery` over all keys with the address prefix, collects them into a list, and sorts them by timestamp — with no limit on the number of entries processed [4](#0-3) . This is invoked by the HTTP servlet `GetDelegatedResourceAccountIndexV2Servlet` (and its gRPC/solidity/PBFT equivalents) via `Wallet.getDelegatedResourceAccountIndexV2` on every incoming API request for the target address, with no server-side limit or pagination [5](#0-4) .

This closely mirrors the reported bug class ("adversary creates a large number of tiny objects that are later iterated over in an unbounded loop, causing resource exhaustion") — except here the amplification target is not premium accrual but the node's public query API (`prefixQuery` + full in-memory sort), which any client can trigger by simply calling the index-lookup endpoint for the victim/attacker address.

### Impact Explanation
An attacker with a very small amount of frozen TRX (minimum 1 TRX per delegation) can generate an arbitrarily large number of index entries for their address at negligible cost (bounded only by their own bandwidth/energy budget for issuing many cheap `DelegateResourceContract` transactions across many blocks). Subsequent calls to `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` for that address force the node to scan and sort potentially huge result sets on every request, degrading or blocking that API endpoint (CPU/memory exhaustion on the serving node), which matches the "API the node can no longer serve" acceptance criterion.

### Likelihood Explanation
Likelihood is Medium: the attacker needs sustained access to bandwidth/energy across many transactions to accumulate a large number of delegation entries (unlike the ProtectionPool report where object creation was essentially free), but the operation is entirely permissionless, requires no privileged role, and the resulting query-side cost per request is unbounded and paid by the node rather than the attacker.

### Recommendation
Cap the number of distinct delegation index entries per address (or enforce a maximum via aggregation instead of per-(from,to) entries), and/or add pagination/limits to `getWithPrefix`/`prefixQuery` results returned by the delegated-resource-index query APIs so a single request cannot force unbounded work.

### Proof of Concept
1. Attacker account freezes the minimum bandwidth/energy required (`FreezeBalanceV2Contract`), then repeatedly submits `DelegateResourceContract` transactions, each delegating 1 TRX (the `TRX_PRECISION` minimum, per `DelegateResourceActuator.validate()`) to a new, distinct receiver address, across many blocks.
2. Each transaction adds a new key in `DelegatedResourceAccountIndexStore` under `V2_FROM_PREFIX`/`V2_TO_PREFIX` for the attacker's address [6](#0-5) .
3. Once thousands/millions of entries exist, any client calls `GetDelegatedResourceAccountIndexV2` (HTTP/gRPC) with the attacker's address, causing `getWithPrefix` to run an unbounded `prefixQuery`, materialize the full result list, and sort it [4](#0-3) , consuming significant CPU/memory on the serving node and degrading that API for all users.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
