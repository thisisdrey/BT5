Confirmed: `ExchangeInjectContract` and `ExchangeWithdrawContract` have no minimum/expected-output slippage protection field, unlike `ExchangeTransactionContract` which includes an `expected` field [1](#0-0) . This confirms the sandwich/manipulation analog is concretely reachable.

### Title
Unprotected reliance on manipulable spot pool reserves in Exchange Inject/Withdraw actuators enables sandwich-attack value extraction - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
TRON's on-chain bancor-formula DEX (`Exchange`) computes the counterpart token amount for liquidity injection and withdrawal purely from the exchange's *current* spot reserves (`firstTokenBalance`/`secondTokenBalance`), the same class of flaw described in the report ("reliance on spot price and spot volume allows anyone to manipulate"). Unlike `ExchangeTransactionContract`, which carries an `expected` field enforced in `doValidate()` to bound slippage, `ExchangeInjectContract` and `ExchangeWithdrawContract` carry no minimum-output/maximum-input protection at all.

### Finding Description
- `ExchangeTransactionActuator` is fully permissionless (any account may call it) and directly mutates the pool's `firstTokenBalance`/`secondTokenBalance` via `ExchangeCapsule.transaction()` [2](#0-1) , changing the spot ratio within a single broadcast transaction.
- `ExchangeInjectActuator.doValidate()` and `ExchangeWithdrawActuator.doValidate()` compute `anotherTokenQuant` as a direct proportion of the current spot reserves at execution time: [3](#0-2) [4](#0-3) 
- Neither actuator's contract message provides any user-supplied bound on the resulting exchange rate, unlike `ExchangeTransactionContract.expected`, which is validated against the actual computed amount in `ExchangeTransactionActuator.doValidate()` [5](#0-4) .
- Because `ExchangeTransactionContract` swaps are unauthenticated and can be issued by any address, an attacker observing a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction from the exchange creator (the only account authorized to inject/withdraw, per the creator check in both actuators [6](#0-5) ) can sandwich it: submit a large swap immediately before it to skew the spot ratio, let the inject/withdraw execute at the manipulated ratio, then submit a reversing swap immediately after, extracting the difference at the creator's expense — mirroring exactly the reported bug class where spot reserves used for a rebalance/liquidity decision are trivially manipulable within adjacent transactions.

### Impact Explanation
An attacker can force the exchange creator's `ExchangeWithdrawContract` (or `ExchangeInjectContract`) to execute at an attacker-chosen unfavorable ratio, extracting value from the creator's withdrawn/injected tokens without their consent — an unauthorized-value-extraction/theft-of-funds scenario reachable purely from a permissionless `ExchangeTransactionContract` transaction combined with normal block-ordering control (a capability any transaction broadcaster has, since java-tron orders transactions within a block by the block producer / and mempool visibility allows front-running before finality).

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to observe a pending inject/withdraw transaction and place bracketing swap transactions around it (achievable via mempool monitoring or SR/packing timing), and requires sufficient capital to move the pool ratio meaningfully. The attack does not require any privileged role and is reachable purely through standard, permissionless `ExchangeTransactionContract` broadcasts.

### Recommendation
Add a slippage-protection field (minimum/maximum counterpart-token bound) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, analogous to the `expected` field already present in `ExchangeTransactionContract`, and enforce it in `ExchangeInjectActuator.doValidate()` / `ExchangeWithdrawActuator.doValidate()` before mutating pool balances.

### Proof of Concept
1. Exchange creator broadcasts an `ExchangeWithdrawContract` transaction to withdraw `tokenQuant` of `firstTokenID`, expecting a proportional amount of `secondTokenID` back based on current reserves `firstTokenBalance`/`secondTokenBalance`.
2. Attacker sees this transaction in the mempool/same block window and submits an `ExchangeTransactionContract` selling a large amount of `secondTokenID` into the pool immediately before it, sharply reducing `secondTokenBalance` relative to `firstTokenBalance` via `ExchangeCapsule.transaction()` [7](#0-6) .
3. The creator's withdrawal executes against the skewed reserves in `ExchangeWithdrawActuator.execute()` [4](#0-3) , receiving far less `secondTokenID` than expected, with no `expected`/minimum field to reject the unfavorable trade.
4. Attacker submits a second `ExchangeTransactionContract` reversing the initial swap, restoring the pool ratio and pocketing the difference extracted from the creator's withdrawal.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
