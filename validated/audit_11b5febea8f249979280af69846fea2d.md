### Title
Access-key nonce reuse via same-block-height DeleteKey+AddKey allows replay of an already-processed transaction - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`initial_nonce_value(block_height) = (block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` is used identically by `add_regular_key` to reset an access key's nonce whenever the key (public key) is (re-)added [1](#0-0) [2](#0-1) . Because this value only depends on the *current block height* and not on any nonce previously consumed by the same public key earlier in that same block, an attacker can delete and re-add the same public key in the same block height as a transaction that used a nonce near the top of that block's valid range, resetting the key's on-chain nonce **backward**, below a value it has already consumed. A later resubmission of the identical previously-signed transaction then passes nonce verification again and is re-executed.

### Finding Description
Nonce validation is purely monotonic against `access_key.nonce`, with an upper bound `tx_nonce < block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [3](#0-2) . Verification and nonce update happen exactly once, at the moment the `SignedTransaction` is converted into a receipt (`verify_and_charge_tx_ephemeral` computes the verdict, and the caller immediately commits `access_key.nonce = tx_nonce` in the same chunk) [4](#0-3) [5](#0-4) . Once a receipt is created, nothing about that receipt's later (possibly delayed/cross-shard) execution re-checks or depends on the signer's access-key nonce state — receipt execution and nonce validation are decoupled.

The actual defect is in `add_regular_key`/`initial_nonce_value`: whenever a public key is deleted and re-added, its nonce is reset to `(block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` for the *current* block height [6](#0-5) . If the delete+re-add happens in the **same block height H** as an earlier transaction that consumed nonce `N` for that same key, and the attacker deliberately chose `N` close to the block's upper bound (i.e. `(H-1)*MULTIPLIER < N < H*MULTIPLIER` — fully attacker-controlled, since nonce upper bound is only checked against the block height, not any lower bound), then after the delete+re-add the key's nonce becomes `(H-1)*MULTIPLIER`, which is **less than** `N`. A later resubmission of the byte-identical original `SignedTransaction` (same signature, same nonce `N`, same key) then satisfies `verify_nonce` (monotonic: `N > current_nonce`) and the upper-bound check for any subsequent block height, so it is accepted as a brand-new valid transaction and re-executed.

The existing anti-duplication guard, `UniqueChunkTransactions`, only deduplicates a transaction hash **within the same chunk** [7](#0-6) , so it does not prevent resubmission in a later block/chunk once the nonce floor has been rolled back.

This requires the delete+re-add to land in the **same chunk/block height** as the original transaction so that `initial_nonce_value` is computed for that same `H`. This can be achieved with a second full-access key on the same account signing the `DeleteKey(K)+AddKey(K)` transaction while `K` signs the transaction to be replayed, both submitted for inclusion in the same chunk — no validator/relayer privilege is needed, only an ordinary account with two access keys.

### Impact Explanation
This breaks the protocol's replay-protection invariant: a previously-processed, already-executed transaction can be legitimately reprocessed and its actions (e.g., `Transfer`, `FunctionCall` to a bridge/exchange/DEX contract, `DeleteAccount`, delegate actions relayed on behalf of the account) re-executed a second time from the same account. This is squarely in the "double-spend/replay" bounty category — any contract or off-chain system that trusts NEAR's monotonic-nonce guarantee as sufficient replay protection for a signed payload (e.g., a signed withdrawal message forwarded via `FunctionCall`) could have that payload executed twice.

### Likelihood Explanation
The attacker needs: (1) an account funded to pay two transactions' fees, (2) two access keys on the same account (trivial and cheap to set up via `AddKey`), (3) the ability to choose the nonce of the transaction to be replayed near the block's nonce ceiling (fully attacker-controlled, no permission needed), and (4) both transactions landing in the same chunk (feasible since the two transactions are signed by different keys and can be submitted together; NEAR's tx-pool selection generally allows one transaction per signer/key group per chunk, so using two distinct keys avoids that restriction). No validator, RPC-operator, or leaked-key access is required — this is fully reachable by an ordinary client. The mechanism is deterministic given the described construction, not probabilistic.

### Recommendation
Do not reset an access key's nonce purely from `block_height` on re-add. Either (a) persist a per-account/per-public-key "highest nonce ever used" watermark that survives key deletion and use `max(initial_nonce_value(block_height), previous_highest_nonce + 1)` when re-adding the same public key, or (b) forbid re-adding a public key that was deleted within the current block (or within some minimum number of blocks) until the nonce ceiling for the deletion's block height has unambiguously passed, or (c) bind nonce ranges to a strictly-increasing global counter rather than block height so a same-block reset cannot undercut an already-consumed nonce.

### Proof of Concept
Runtime/test-loop integration test outline:
1. Create account `alice` with two full-access keys, `K1` and `K2`.
2. Determine the target inclusion block height `H` (e.g., via the test loop's next-block height); construct `tx1`: `Transfer` action signed by `K1` with nonce `N = H*MULTIPLIER - 1` (just under the upper bound enforced by `verify_nonce`).
3. Construct `tx2`: `[DeleteKeyAction{K1}, AddKeyAction{K1, FullAccess}]` signed by `K2` with a valid nonce for `K2`.
4. Submit `tx1` and `tx2` in the same chunk (block height `H`); assert both succeed, and that after this block `access_key(K1).nonce == (H-1)*MULTIPLIER < N`.
5. Resubmit the original `tx1` bytes (unchanged) in a later block height `H' > H`. Assert it is accepted (no `InvalidNonce` error) and produces a **second** outcome/receipt executing the same `Transfer` — demonstrating the same signed transaction executed twice.
6. Assert this violates the expected invariant that a given `SignedTransaction` can be accepted at most once, i.e. add a regression assertion that this second acceptance is rejected once the fix is applied.

```rust
pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}
```

```rust
fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
```

```rust
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}
```
