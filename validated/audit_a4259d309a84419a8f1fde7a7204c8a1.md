## Title
Check-then-commit race in replay-window validation allows duplicate packet delivery - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the replay-window validation into two separately-locked steps — `window.Check` and `window.Update` — with the expensive `DecryptDanger` operation running in between, **outside** the lock. This mirrors the reported CEI-pattern bug: an "effect" (marking a message counter as consumed) is deferred until after an "interaction" (the AEAD decrypt), leaving a window in which the same counter can pass the check twice. Because Nebula's interface can run multiple reader goroutines (`f.routines > 1`, `listenOut`) that all call `readOutsidePackets` concurrently for the same `hostinfo`/`ConnectionState`, two threads processing the same (replayed) packet can both pass `Check` before either calls `Update`, resulting in a duplicate packet being decrypted and delivered twice instead of being rejected as a replay.

### Finding Description
`Decrypt` performs:
1. `cs.decryptLock.Lock(); result := cs.window.Check(...); cs.decryptLock.Unlock()`
2. `cs.dKey.DecryptDanger(...)` — the costly AEAD decrypt, done **without holding the lock**
3. `cs.decryptLock.Lock(); result = cs.window.Update(...); cs.decryptLock.Unlock()` [1](#0-0) 

`VerifyRelay` follows the identical pattern for relay frames: [2](#0-1) 

The lock is released between the "check" and the "commit" (`Update`), and the interaction (`DecryptDanger`) happens in that unprotected gap. `Bits.Check` only reads state without side effects; it is `Bits.Update` that actually marks the slot consumed: [3](#0-2) [4](#0-3) 

Nebula supports multiple concurrent UDP reader goroutines, each independently invoking `readOutsidePackets` (and thus `ConnectionState.Decrypt`) for packets that resolve to the same `hostinfo`/tunnel via `f.hostMap.QueryIndex`: [5](#0-4) [6](#0-5) [7](#0-6) 

Because `SupportsMultipleReaders`/`SO_REUSEPORT` distributes inbound datagrams across queues without any per-tunnel affinity, two goroutines can concurrently process two copies of the same ciphertext packet (e.g., replayed by an on-path or off-path attacker) for the same `remoteIndexId`. Both goroutines call `Check` while holding the lock only momentarily, see the message counter as not-yet-seen, release the lock, and both proceed to `DecryptDanger` and eventually into `handleOutsideMessagePacket`, which writes the decrypted payload to the TUN device: [8](#0-7) 

Only after decrypting does either goroutine call `Update`; the second `Update` call correctly returns `false`, but by then the decrypt and (for the data-plane case) the TUN write may have already happened for both copies.

### Impact Explanation
This breaks the core security guarantee of the replay-window/anti-replay mechanism: an attacker who can capture and re-inject a legitimate ciphertext packet (a normal on-path/off-path capability against UDP, no valid certificate needed) can cause the packet to be decrypted and delivered to the local TUN device more than once, under raced concurrent processing across the interface's reader queues. This is a state-poisoning / duplicate-delivery impact on the data plane rather than a corrupted-fund transfer, but it is the direct structural analog of the reported "operation performed multiple times" class of bug: the state-mutating commit (`window.Update`) is deferred until after the costly external-like operation (decrypt), instead of being reserved atomically together with the check.

### Likelihood Explanation
Exploitability requires (a) `routines > 1` (multiple UDP reader queues, a supported, non-default-but-common configuration on Linux/multiqueue-capable platforms) and (b) an attacker able to replay a captured legitimate ciphertext packet quickly enough to race two reader goroutines. Both conditions are realistic for a network-adjacent attacker without any CA-signed certificate, since capturing/replaying UDP packets requires no cryptographic capability. Likelihood is Medium: it depends on timing and multi-routine deployment, similar to the "not currently exploitable under standard assumptions but latent due to wrong operation order" characterization in the source report.

### Recommendation
Hold `decryptLock` for the entire check-decrypt-commit sequence (or otherwise make check-and-reserve atomic, e.g. by having `Check`+`Update` merged into a single locked "reserve" step before decrypting, then rolling back the reservation only on decrypt failure) so no other goroutine can observe the same counter as "not yet seen" while a decrypt for it is in flight. Apply the same fix to both `Decrypt` and `VerifyRelay`.

### Proof of Concept
1. Configure a Nebula instance with `routines` > 1 (e.g., 2), verifying platform support for multiple UDP readers (`SupportsMultipleReaders`).
2. Establish a tunnel and capture one legitimate data-plane ciphertext packet (`header.Message`/`MessageNone`).
3. From an external position, simultaneously inject two copies of the exact same captured packet at (near-)the same instant so they are likely picked up by two different `listenOut` goroutines/readers.
4. Observe that under race conditions both goroutines can pass `window.Check` before either calls `window.Update`, causing the payload to be decrypted and written to `f.readers[q]` (the TUN device) more than once for a single wire packet — confirming duplicate delivery bypassing the anti-replay window.

		return nil, ErrAlreadySeen

}

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}

func (f *Interface) handleOutsideMessagePacket(hostinfo *HostInfo, out []byte, packet []byte, fwPacket *firewall.Packet, nb []byte, q int, localCache firewall.ConntrackCache) {
	err := newPacket(out, true, fwPacket)
	if err != nil {
		hostinfo.logger(f.l).Warn("Error while validating inbound packet",
			"error", err,
			"packet", out,
		)
		return
	}

	dropReason := f.firewall.Drop(*fwPacket, true, hostinfo, f.pki.GetCAPool(), localCache)
	if dropReason != nil {
		// NOTE: We give `packet` as the `out` here since we already decrypted from it and we don't need it anymore
		// This gives us a buffer to build the reject packet in
		f.rejectOutside(out, hostinfo.ConnectionState, hostinfo, nb, packet, q)
		if f.l.Enabled(context.Background(), slog.LevelDebug) {
			hostinfo.logger(f.l).Debug("dropping inbound packet",
				"fwPacket", fwPacket,
				"reason", dropReason,
			)
		}
		return
	}

	_, err = f.readers[q].Write(out)
	if err != nil {
		f.l.Error("Failed to write to tun", "error", err)
	}
