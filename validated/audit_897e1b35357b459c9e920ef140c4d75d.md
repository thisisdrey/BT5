### Lack of NFT callbacks in Smart Accounts - ([File: tare-io__tare-contracts/contracts/SmartAccountFactory.sol])

### Summary
Smart accounts deployed via the `SmartAccountFactory` are unable to receive `LoansNFT` or other ERC-721/ERC-1155 tokens via `safeTransferFrom` because they are initialized without a fallback handler, leaving them without the required `onERC721Received` or `onERC1155Received` callbacks. [1](#0-0) 

### Finding Description
The Tare protocol relies on Gnosis Safe smart accounts to act as wallets for investors, borrowers, and other roles. These accounts are deployed using `SmartAccountFactory.deploySmartAccount`, which initializes the Safe proxy. [2](#0-1) 

Per the ERC-721 and ERC-1155 standards, a smart contract recipient must implement specific callback functions (e.g., `onERC721Received`) to accept tokens sent via `safeTransferFrom`. Gnosis Safe handles these callbacks through a `fallbackHandler`. However, the `SmartAccountFactory._buildInitializer` function explicitly sets the `fallbackHandler` to `address(0)` during the Safe's `setup` call. [3](#0-2) 

Consequently, any attempt to transfer a `LoansNFT` to a Tare Smart Account using `safeTransferFrom` will revert. This affects core protocol flows, such as `LoansExchange.acceptOffer`, which uses `LOANS_NFT.transferFrom` (invoking the safe check if the NFT is standard-compliant or if the exchange uses the safe variant). [4](#0-3)  Additionally, `TrustedSpender.executeNFTTransfer` explicitly uses `safeTransferFrom`, meaning Safes cannot receive NFTs from other Safes via this module. [5](#0-4) 

### Impact Explanation
This issue results in a Denial of Service for smart account users. Investors using Tare Smart Accounts will be unable to receive `LoansNFTs` through the `LoansExchange` or via the `TrustedSpender` module. Since the `LoansNFT` represents the right to loan cashflows, this blocks the primary utility of the investor role. Users would be forced to manually configure a fallback handler via a multisig transaction (if they have enough owners/threshold) to recover functionality, which breaks the "ready to use from day one" design goal of the factory. [6](#0-5) 

### Likelihood Explanation
The likelihood is high because the factory is the standard way to create accounts in the protocol, and the `fallbackHandler` is hardcoded to `address(0)`. Every Safe deployed via this factory will be affected by default.

### Recommendation
Modify `SmartAccountFactory.sol` to accept a `fallbackHandler` address in its constructor and pass this address to the `ISafe.setup` call in `_buildInitializer`. The recommended handler is the `TokenCallbackHandler` (or `CompatibilityFallbackHandler`) provided by the Safe team, which implements the necessary ERC-721 and ERC-1155 receiver hooks.

### Proof of Concept
1. Deploy a `Safe` using `SmartAccountFactory.deploySmartAccount`.
2. Note that the `fallbackHandler` is set to `0x0`.
3. Mint a `LoansNFT` (or any ERC-721).
4. Attempt to transfer the NFT to the Safe address using `safeTransferFrom`.
5. The transaction will revert with `ERC721InvalidReceiver` (or equivalent).
