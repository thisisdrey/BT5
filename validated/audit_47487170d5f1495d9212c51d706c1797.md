### Title
Cross-contract StackerDB chunk signature replay lets an unprivileged relayer write a signer's genuinely-signed data into the wrong `.signers-N-X` StackerDB contract - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest` — the data actually covered by a StackerDB chunk's signature — commits only to `slot_id`, `slot_version`, and `data_hash`. It never binds the signature to the specific StackerDB smart-contract instance the chunk is destined for. Because every `signers-{N}-{message_id}` contract for a given signer set `N` shares the exact same `(address → slot_id)` assignment (all derived from the single `stackerdb-signer-slots-{N}` list in `signers.clar`), a chunk that a signer validly signed for one message-type contract (e.g. `StateMachineUpdate`, `signers-0-2`) can be replayed verbatim by any network observer into a sibling contract for the same signer set (e.g. `BlockPreCommit`, `signers-0-3`), since the slot owner, and hence the signature check, is identical across contracts.

No `smart_contract_id`/`contract_name` is part of the signed material anywhere in `StackerDBChunkData`/`SlotMetadata`.

Slot ownership assignment is shared across all message-type contracts belonging to a signer set. `signers.clar` stores a single `stackerdb-signer-slots-{0,1}` list per signer set, and every `signers-{N}-{message_id}` contract fetches that same page: [3](#0-2) [4](#0-3) 
This is also confirmed by the reward-set boot logic that produces one `stackerdb_list` per reward cycle, and the `MessageSlotID` enum whose variants (`BlockResponse=1`, `StateMachineUpdate=2`, `BlockPreCommit=3`) all resolve, via `NakamotoSigners::make_signers_db_contract_id`, to distinct contracts that consume the *same* ordered signer list: [5](#0-4) 

On the receiving side (both the p2p unsolicited-push path and the HTTP POST endpoint), a chunk is authenticated purely by resolving the slot owner for the target `smart_contract_id`/slot and verifying the signature against that owner — with no check that the signature was produced *for this contract*: [6](#0-5) 
The storage layer (`try_replace_chunk`/`create_stackerdb`) likewise indexes slots purely by `(stackerdb_id, slot_id)` without incorporating the signature's binding to a particular database: [7](#0-6) 
The public POST endpoint accepts a raw JSON `StackerDBChunkData` (slot_id, slot_version, sig, data) for any resolvable contract/address pair, with no additional binding checks: [8](#0-7) 

**Root cause / equality broken:** the implicit invariant "a chunk signature authorizes writing this data to *this* StackerDB replica" is not actually enforced — the signature only proves "signer S authorized `(slot_id, slot_version, data_hash)`" with no `contract_id` in the digest. Since slot ownership is identical across `signers-N-1/2/3`, this equality collapses across sibling contracts for the same signer set, and a signature captured off the wire for one contract satisfies validation in another.

### Impact Explanation
An unprivileged network observer (anyone who can see a chunk being gossiped/pushed, or who can query any node's `/v2/stackerdb/.../chunks` for the latest chunks) can copy a validly-signed `(slot_id, slot_version, sig, data)` tuple from one `signers-N-X` contract and POST/gossip it into a different `signers-N-Y` contract for the same signer set, as long as the target contract's expected version for that slot accepts the replayed version (trivially true for slots that haven't yet been written to, since versions start at 0, or for stale/low-traffic message types). This results in an unauthorized write of foreign, non-canonical data into a StackerDB contract, injected without the signer's intent for that destination and without needing any private key. Downstream consumers (`stackerdb_listener.rs`, `signer_state.rs`) that deserialize chunks by contract type would generally fail to parse the mismatched payload and drop it, limiting immediate protocol impact to griefing (denial of a signer's slot-write opportunity by consuming/advancing its expected version in the wrong contract, or triggering deserialization-failure log noise/DoS-adjacent behavior) rather than direct consensus corruption. This aligns with "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data" (the replayed chunk is genuinely forged with respect to its new destination even though the raw signature bytes are authentic).

### Likelihood Explanation
High. Both the p2p StackerDB push-chunk path and the public HTTP `POST /v2/stackerdb/.../chunks` endpoint are open to any peer, chunks are unencrypted and readily observable/downloadable via `list_chunks`/`get_latest_chunks`, and all data needed for the replay (slot_id, version, sig, data) is exactly what's already broadcast for legitimate operation. No cryptographic secret or privileged role is required — only relaying already-public data to a different contract endpoint.

### Recommendation
Bind the chunk signature to the specific StackerDB instance by including the `smart_contract_id` (or a fixed per-database identifier) in `SlotMetadata::auth_digest`, mirroring how block/vote signatures use `make_structured_data_domain`/`structured_data_message_hash` elsewhere in the codebase (as `libsigner/src/v0/messages.rs` already does for `BlockRejection`). This requires a coordinated wire/version change across `libstackerdb`, `stacks-signer`, and `stackslib` chunk validation, since it changes the signed digest format.

### Proof of Concept
1. Signer S is assigned slot 5 in both `signers-0-2` (`StateMachineUpdate`) and `signers-0-3` (`BlockPreCommit`) contracts for reward cycle 0 (confirmed shared slot ordering, `signers.clar`).
2. S legitimately signs and pushes a `StateMachineUpdate` chunk: `StackerDBChunkData{slot_id:5, slot_version:0, sig:SIG, data:D}` to `signers-0-2`.
3. Attacker observes this chunk (via p2p relay or `GET /v2/stackerdb/.../chunks/5`) and re-POSTs the identical struct to `POST /v2/stackerdb/<addr>/signers-0-3/chunks`.
4. `validate_received_chunk`/`try_replace_chunk` for `signers-0-3` resolves slot 5's owner as S (same address as in `signers-0-2`), recomputes `auth_digest(5,0,hash(D))`, recovers S's pubkey, and accepts the write — even though S never intended `D` to be stored under `signers-0-3`. [6](#0-5)

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

                    MessageSignature::empty(),
                ];
                stmt.execute(args)?;

                slot_id += 1;
            }
        }

        Ok(())

/// Decode the HTTP request
impl HttpRequest for RPCPostStackerDBChunkRequestHandler {
    fn verb(&self) -> &'static str {
        "POST"
    }

    fn path_regex(&self) -> Regex {
        Regex::new(&format!(
            r#"^/v2/stackerdb/(?P<address>{})/(?P<contract>{})/chunks$"#,
            *STANDARD_PRINCIPAL_REGEX_STRING, *CONTRACT_NAME_REGEX_STRING
        ))
        .unwrap()
    }

    fn metrics_identifier(&self) -> &str {
        "/v2/stackerdb/:principal/:contract_name/chunks"
    }

    /// Try to decode this request.
    /// There's nothing to load here, so just make sure the request is well-formed.
    fn try_parse_request(
        &mut self,
        preamble: &HttpRequestPreamble,
        captures: &Captures,
        query: Option<&str>,
        body: &[u8],
    ) -> Result<HttpRequestContents, Error> {
        if preamble.get_content_length() == 0 {
            return Err(Error::DecodeError(
                "Invalid Http request: expected non-empty body".to_string(),
            ));
        }

        if preamble.get_content_length() > MAX_MESSAGE_LEN {
            return Err(Error::DecodeError(
                "Invalid Http request: PostStackerDBChunk body is too big".to_string(),
            ));
        }

        let contract_identifier = request::get_contract_address(captures, "address", "contract")?;
        let chunk: StackerDBChunkData = serde_json::from_slice(body).map_err(Error::JsonError)?;

        self.contract_identifier = Some(contract_identifier);
        self.chunk = Some(chunk);

        Ok(HttpRequestContents::new().query_string(query))
    }
}
