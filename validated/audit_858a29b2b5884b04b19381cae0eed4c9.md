### Title
ValidateMultiSign precompile allows weight double-counting via ECDSA signature malleability, bypassing multisig thresholds - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` TVM precompile at `PrecompiledContracts.java:1036-1121` verifies weighted multisig approval for a `permissionId` given an array of signatures, and returns "approved" once `totalWeight >= permission.getThreshold()`. Its de-duplication logic only skips a signature when the *exact same signature bytes* for an address have already been seen; if the same signer address reappears with a *different* (but still valid, ECDSA-malleable) signature encoding of the same hash, the loop falls through and adds that signer's key weight to `totalWeight` again. [1](#0-0) 

### Finding Description
In the signature loop:
```java

  byte[] recoveredAddr = recoverAddrBySign(sign, hash);

  totalWeight += weight;

``` [1](#0-0) 

The `recoveredAddr` re-seen check exists only to (a) cap CPU cost via `MUtil.checkCPUTime()` and (b) skip an *exact-byte* repeat signature. It never rejects or dedups by *address* alone — so a second, third, etc. distinct-but-valid signature from the same key (ECDSA's `(r,s)` / `(r, N-s)` malleability, or a different recovery id `v`, both recover to the same address for the same `hash`) is counted as an independent signer, adding `weight` to `totalWeight` again.

Compare this to `TransactionCapsule.checkWeight`, which was explicitly hardened against exactly this class of issue: after the `VERSION_4_7_1` hard fork it deduplicates by the recovered **address** (`encode58Check(address)`), not by raw signature bytes, and throws `PermissionException("... has signed twice!")` if the same address appears twice: [2](#0-1) 

That is the java-tron equivalent of the goshs incomplete-fix pattern: one enforcement path (`TransactionCapsule.checkWeight`, used for on-chain transaction signature validation and `Wallet.getTransactionApprovedList`) was fixed to dedupe by address, but the parallel enforcement path exercised by the `ValidateMultiSign` TVM precompile — used by smart contracts to check off-chain-style multisig approval — still dedupes by exact signature bytes, leaving the malleability-based weight-inflation bypass reachable through that entry point. `MUtil.checkCPUTime()` (gated on the same `VERSION_4_7_1` fork) throws only after the fork activates, and only serves as a DoS/CPU guard for repeated `matrixContains` scans — it does nothing to prevent the weight from being added twice. [3](#0-2) 

### Impact Explanation
Any contract can call the `ValidateMultiSign` precompile (address `0x0a`) with a crafted `sigArray` containing multiple malleable variants of a single low-weight key's signature over the same `(address, permissionId, data)` hash. This lets an attacker who controls only one key in a multisig `Permission` — with weight strictly less than the threshold — synthesize additional distinct-byte signatures that recover to that same address and inflate `totalWeight` past `permission.getThreshold()`, causing the precompile to return "approved" (`dataOne()`) even though the real signer set never met the threshold. Any smart contract that gates fund transfers, permission changes, or other privileged actions on `ValidateMultiSign` returning true is exposed to unauthorized-action / theft-of-funds risk, since callers can forge apparent multisig quorum from a single compromised or attacker-owned key.

### Likelihood Explanation
High. This requires no privileged access — any account can invoke a `TriggerSmartContract` (or have a contract call the precompile), and ECDSA signature malleability (flipping `s` to `N-s`/adjusting the recovery id) is a well-known, cheap transformation requiring no knowledge beyond a single valid signature the attacker already possesses (i.e., their own key's signature). The bug is purely a missing address-level dedup in a permissively-reachable precompile.

### Recommendation
In `ValidateMultiSign.execute`, deduplicate strictly by `recoveredAddr` (not by the concatenation of address+raw signature bytes) before adding `weight` to `totalWeight`, mirroring the address-based dedup already applied in `TransactionCapsule.checkWeight`. Reject (or simply skip without adding weight) any signature whose recovered address has already contributed weight in the current call, regardless of whether the exact signature bytes differ.

### Proof of Concept
1. Create an account with an `Active` permission (`permissionId = 2`) with threshold 2, containing a single key `K` (weight 1) and no other keys with weight ≥1 available to the attacker (attacker only controls `K`).
2. Compute `hash = sha256(address || permissionId || data)` as done by the precompile (`ByteUtil.merge` + `Sha256Hash.hash`), matching `PrecompiledContracts.java:1062-1064`.
3. Sign `hash` once with `K` to get signature `sig1 = (r, s, v)`.
4. Derive a distinct but still-valid signature `sig2 = (r, N-s, v')` for the same `hash` and same key `K` (standard ECDSA malleability).
5. Call the `validateMultiSign(address, permissionId, data, [sig1, sig2])` precompile.
6. Both `sig1` and `sig2` recover to the same address `K`; since their raw bytes differ, `matrixContains(executedSignList, sign)` is false both times, so the loop adds `weight(K)` twice, making `totalWeight = 2 * weight(K) ≥ threshold`, and the precompile returns `dataOne()` (approved) despite only one real signer.
