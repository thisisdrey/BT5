### Title
Potential NullPointerException / node crash from unchecked `DelegatedResourceCapsule` dereference in `UnDelegateResourceActuator.execute()` - (File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java)

### Summary
`UnDelegateResourceActuator.validate()` and `execute()` handle a `UnDelegateResourceContract` (broadcastable by any account holding delegated TRX resources). `validate()` treats the "unlock" and "lock" `DelegatedResourceCapsule` records as interchangeable and only requires that at least one of the two is non-null, while `execute()` unconditionally dereferences the "unlock" record fetched *after* mutating store state, without a null check.

### Finding Description
In `validate()`: [1](#0-0) 
the code fetches both `unlockResourceCapsule` (key with `false`) and `lockResourceCapsule` (key with `true`) and only rejects the transaction if **both** are null. It is therefore legal for `unlockResourceCapsule == null` while `lockResourceCapsule != null` and expired (`getExpireTimeForBandwidth()/getExpireTimeForEnergy() < now`), since the sufficiency check sums balances from whichever of the two is present/expired: [2](#0-1) 

In `execute()`, the code calls `delegatedResourceStore.unLockExpireResource(...)` (intended to migrate the expired "lock" balance into the "unlock" slot), then re-reads the unlock record and **unconditionally dereferences it**: [3](#0-2) [4](#0-3) 
There is no null-guard on `unlockResource` before calling `unlockResource.addFrozenBalanceForBandwidth(...)`, `getFrozenBalanceForBandwidth()`, etc. This is structurally the same bug pattern as the reported CVE: a code path that validates the *existence of some* backing object, but at execution time re-fetches/derives a *different, potentially stale-or-absent* reference and dereferences it without re-validating, i.e., correctness relies on an implicit invariant across two separate reads of mutable store state that is not guaranteed to hold in every case. I could not fully verify the implementation of `DelegatedResourceStore.unLockExpireResource(...)` (referenced at `chainbase/src/main/java/org/tron/core/store/DelegatedResourceStore.java`) within this investigation, so I cannot confirm with certainty whether it always persists an unlock-side `DelegatedResourceCapsule` for every combination of resource type / balance / expiry that `validate()` allows through. If there exists any edge case (e.g., rounding at the exact expiry boundary, or only one resource type – BANDWIDTH vs ENERGY – being migrated while the actuator operates on the other) where `unLockExpireResource` does not create the unlock record, `execute()` will throw an unhandled `NullPointerException`.

### Impact Explanation
If reachable, this throws an unhandled `NullPointerException` inside contract execution (`Manager` applying a block/transaction), which is a state-transition-critical code path. An uncaught exception here is either swallowed as a contract failure (denial of the specific transaction, low impact) or, depending on how the caller in `Manager`/`ChainBaseManager` handles `RuntimeException` during block processing, could crash the node processing the block or cause it to be unable to move forward — a liveness/availability impact fitting the required "node crash or halt" bar. Because `UnDelegateResourceContract` is a normal broadcastable contract type available to any account that has previously used `DelegateResourceContract`, this is reachable by an unprivileged sender with a single signed transaction.

### Likelihood Explanation
Likelihood is **uncertain** because it hinges entirely on the exact semantics of `DelegatedResourceStore.unLockExpireResource`, which I was not able to inspect in full during this session. If that method reliably guarantees the unlock record exists whenever `validate()`'s sufficiency check passes, this is not exploitable. If there is any type-specific (BANDWIDTH vs ENERGY) or precision-boundary gap, the bug is trivially and deterministically triggerable by any account that delegates resources, waits for lock expiry, and calls `UnDelegateResourceContract` in a way that only the lock-side balance (not unlock-side) satisfies the resource check.

### Recommendation
- Add explicit null checks on `unlockResource` in `UnDelegateResourceActuator.execute()` before dereferencing it (lines 137, 152, 170–176), creating a zero-balance `DelegatedResourceCapsule` if absent, mirroring the defensive pattern already used for `receiverCapsule` (`Objects.nonNull(receiverCapsule)` at lines 145 and 160).
- Audit `DelegatedResourceStore.unLockExpireResource` to confirm it always creates/persists the unlock-side capsule whenever `validate()`'s combined-balance check can pass with `unlockResourceCapsule == null`.
- Add unit tests exercising: (a) only a lock record exists and is expired, undelegate requested for BANDWIDTH only, (b) same for ENERGY only, (c) boundary cases at exact expire time, to ensure `execute()` never dereferences a null `DelegatedResourceCapsule`.

### Proof of Concept
Conceptual reproduction (pending confirmation of `unLockExpireResource` internals):
1. Account A delegates BANDWIDTH resource to Account B via `DelegateResourceContract`, creating a "lock" `DelegatedResourceCapsule` (no corresponding "unlock" record yet).
2. Wait until the lock's expire time has passed (`getExpireTimeForBandwidth() < now`), with no unlock-side record having been created by any prior action.
3. Account A broadcasts `UnDelegateResourceContract` for BANDWIDTH with `balance <= lockResourceCapsule.getFrozenBalanceForBandwidth()`.
4. `validate()` passes because `lockResourceCapsule != null` and expired.
5. During `execute()`, if `unLockExpireResource` does not persist an unlock-side capsule for this exact case, `delegatedResourceStore.get(unlockKey)` returns `null`, and `unlockResource.addFrozenBalanceForBandwidth(...)` throws `NullPointerException`, causing an unhandled exception in contract execution.

Note: Steps 4–5 assume a gap in `unLockExpireResource`'s coverage that I could not confirm from the code retrieved in this session (index size limits prevented full retrieval of `DelegatedResourceStore.java`). A Devin session with full repository access should inspect `chainbase/src/main/java/org/tron/core/store/DelegatedResourceStore.java` to confirm or refute this gap before treating this as a confirmed exploitable finding.
