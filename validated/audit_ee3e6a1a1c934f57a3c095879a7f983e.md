### Title
Stale cached `global_fee_wallet` in `MarginfiGroup.fee_state_cache` routes transfer fees to a deprecated/compromised wallet - ([File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs])

### Summary
`transfer_to_new_account` (and `transfer_to_new_account_pda`) validate the caller-supplied `global_fee_wallet` account against `MarginfiGroup.fee_state_cache.global_fee_wallet` — a value cached on the group at group-init time — instead of validating against the live `FeeState.global_fee_wallet` account. This cache is only refreshed by the permissionless `propagate_fee_state` instruction. If the global fee admin rotates `global_fee_wallet` via `edit_fee_state` (e.g. because the old wallet was compromised), every `MarginfiGroup` that has not since had `propagate_fee_state` called against it keeps directing the `ACCOUNT_TRANSFER_FEE` SOL payment to the stale wallet.

### Finding Description
`MarginfiGroup` stores a `FeeStateCache` (containing `global_fee_wallet`) that is populated once at `initialize_group` [1](#0-0) 
and can only be refreshed by the permissionless `propagate_fee_state` instruction, which copies the current `FeeState.global_fee_wallet` into the group's cache [2](#0-1) 
The global fee admin can update `FeeState.global_fee_wallet` at any time via `edit_fee_state` [3](#0-2) 
but this update does **not** propagate automatically to any existing `MarginfiGroup` — a separate, permissionless call is required for every group.

The unprivileged user-facing instruction `transfer_to_new_account` validates the fee-wallet account it will pay against the **stale cached** value on the group, not the live `FeeState`: [4](#0-3) 
This is exactly the analog of the reported bug class: a critical address (`swapProxy` in the original report, `global_fee_wallet` here) is cached once into a per-entity object (`RoyaltyManager` / `MarginfiGroup`) and reused indefinitely for real fund transfers unless an explicit refresh action is taken, even after the canonical/authoritative value has been rotated by the admin (frequently for security reasons, e.g. wallet key compromise). Contrast this with `place_order`, which correctly validates `global_fee_wallet` against the live `FeeState` account via `has_one = global_fee_wallet` on the `fee_state` loader [5](#0-4) 
demonstrating that the `transfer_account.rs` path is inconsistent and uses the wrong (cached) source of truth.

### Impact Explanation
Any unprivileged user calling `transfer_to_new_account`/`transfer_to_new_account_pda` on a group whose cache has not been refreshed will have their `ACCOUNT_TRANSFER_FEE` lamports routed to the old wallet address instead of the newly configured one. If the rotation occurred specifically because the old wallet's key was compromised (the very reason an admin would rotate `global_fee_wallet`), this means protocol fee funds continue to flow to an attacker-controlled address for every group lacking a `propagate_fee_state` call — a real (if per-transaction small) unauthorized diversion of program fee funds, persisting until each group is individually and manually refreshed.

### Likelihood Explanation
Likelihood is Medium: there is no enforcement that `propagate_fee_state` is called immediately (or ever) after `edit_fee_state` changes the wallet, and the instruction is permissionless with no automatic trigger, no on-chain reminder, and no blocking behavior. Any group left un-propagated remains exposed for as long as anyone continues transferring accounts on it, which is a routine unprivileged user action (`transfer_to_new_account`).

### Recommendation
- In `transfer_to_new_account`/`transfer_to_new_account_pda`, validate `global_fee_wallet` against the live `FeeState` account (pass `FeeState` into the instruction context and use `has_one = global_fee_wallet`, as `place_order` already does) instead of `group.fee_state_cache.global_fee_wallet`.
- Alternatively, if the cache must remain the source of truth for fee accounting, require/force the `propagate_fee_state` refresh in the same or a preceding instruction whenever `edit_fee_state` rotates the wallet, or add a version/epoch check that rejects using a stale cache beyond some staleness bound.

### Proof of Concept
1. `WishWishManager`-style scenario translated to marginfi:
   - Global fee admin calls `edit_fee_state(fee_wallet = walletNew)` because `walletOld`'s private key was compromised. `FeeState.global_fee_wallet` is now `walletNew` [3](#0-2) 
   - `MarginfiGroup` G (created earlier) still has `fee_state_cache.global_fee_wallet = walletOld` because nobody has called `propagate_fee_state` for G yet.
   - A user with an account under group G calls `transfer_to_new_account`, passing `walletOld` as `global_fee_wallet`. The `check_eq!` at [6](#0-5) 
     succeeds because it compares against the stale cache, and `ACCOUNT_TRANSFER_FEE` lamports are transferred to `walletOld` (the compromised wallet), not `walletNew`.
   - This repeats for every account transfer on group G until someone calls the permissionless `propagate_fee_state` for that specific group.

This confirms fee funds are diverted to a stale/compromised address on an unprivileged, user-reachable path, matching the reported bug class (stale cached critical address reused for real fund transfers after rotation).

pub fn propagate_fee(ctx: Context<PropagateFee>) -> Result<()> {
    let mut group = ctx.accounts.marginfi_group.load_mut()?;
    let fee_state = ctx.accounts.fee_state.load()?;

    group.fee_state_cache.global_fee_wallet = fee_state.global_fee_wallet;
    group.fee_state_cache.program_fee_fixed = fee_state.program_fee_fixed;
    group.fee_state_cache.program_fee_rate = fee_state.program_fee_rate;

    let clock = Clock::get()?;
    group.fee_state_cache.last_update = clock.unix_timestamp;
