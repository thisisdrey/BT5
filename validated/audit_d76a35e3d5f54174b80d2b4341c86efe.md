### Title
Bank interest accrual can be silently skipped for integration banks (Kamino/JupLend/Solend/Drift) via `update_bank_cache` advancing `last_update` without accruing - ([File: programs/marginfi/src/state/bank.rs])

### Summary
Native marginfi banks always call `accrue_interest(clock.unix_timestamp, ...)` before `update_bank_cache(&group)` in every instruction that touches balances (e.g. `borrow.rs` [1](#0-0) ). However, several integration flows (Kamino, JupLend, Solend deposit/withdraw, Drift withdraw) call only `bank.update_bank_cache(&group)` after mutating shares, and `update_bank_cache` unconditionally stamps `self.last_update = Clock::get()?.unix_timestamp` even though it never ran the interest math [2](#0-1) .

### Finding Description
`accrue_interest` computes `time_delta` as `current_timestamp - self.last_update` and only then updates `self.last_update` to the current timestamp after computing/crediting the corresponding interest, fees, and share-value changes [3](#0-2) . This is the checkpoint mechanism that must exactly mirror the invariant RocketPool violated: the "last calculated" marker may only be advanced past a period once that period's yield has actually been applied.

`update_bank_cache`, by contrast, is meant only to refresh the *rate* cache (borrow/lend APR, spread, etc.) for display/oracle purposes, but it independently re-stamps `last_update = Clock::get()?.unix_timestamp` at line 657 [4](#0-3) . In the code paths that were audited (`kamino_deposit`, `juplend_deposit`, `solend_deposit`, `drift_withdraw`), the instruction handler calls `bank.update_bank_cache(&group)` directly, with no preceding `bank.accrue_interest(...)` call in the same instruction body:
- `programs/marginfi/src/instructions/kamino/deposit.rs` [5](#0-4) 
- `programs/marginfi/src/instructions/juplend/deposit.rs` [6](#0-5) 
- `programs/marginfi/src/instructions/solend/deposit.rs` [7](#0-6) 
- `programs/marginfi/src/instructions/drift/withdraw.rs` [8](#0-7) 

Because `self.last_update` is advanced to `now` in these calls without the intervening interest ever being calculated/credited, any elapsed time between the bank's true `last_update` and the moment one of these integration instructions runs is permanently "lost" — mirroring exactly the RocketPool defect where `inflationCalcBlock` was reset to `block.number` without accounting for the not-yet-completed interval. The more frequently these integration-only instructions are invoked relative to native `deposit`/`borrow`/`withdraw`/`repay` (which do call `accrue_interest`), the more accrual is silently dropped, permanently understating both lender yield and borrower debt for that bank.

### Impact Explanation
This causes real accounting divergence in `asset_share_value` / `liability_share_value` versus what should have accrued: lenders systematically under-earn and borrowers systematically under-owe for the skipped windows, which is an unauthorized state change to core interest accounting and can produce insolvency/bad-debt risk in aggregate over the bank's lifetime, since the loss is never recovered (the clock has already been advanced past that window). This maps to "insolvency/bad debt" and "unauthorized state change" categories in scope for this program.

### Likelihood Explanation
Likelihood is High for actively used Kamino/JupLend/Solend/Drift banks: any user (unprivileged) can trigger these deposit/withdraw instructions as part of normal usage, and the omission is unconditional — it doesn't require an attacker to race a boundary, it happens on every single call to these paths. The more these integration instructions are used relative to the native path (which does call `accrue_interest`), the larger the cumulative loss.

### Recommendation
Ensure `accrue_interest(clock.unix_timestamp, ...)` is always invoked immediately before `update_bank_cache` in every instruction that can advance a bank's `last_update`, exactly as done in `borrow.rs`, `accrue_bank_interest.rs`, `deposit.rs`, `repay.rs`, `withdraw.rs`, and `close_balance.rs`. Alternatively, remove the `self.last_update = Clock::get()?.unix_timestamp` side effect from `update_bank_cache` entirely and require callers to explicitly call `accrue_interest` first (which already sets `last_update` correctly after applying the accrual), so `update_bank_cache` cannot silently "consume" time without crediting it.

### Proof of Concept
Not independently verified by exploit run — this assessment is based on static code-path comparison confirming that `kamino_deposit`, `juplend_deposit`, `solend_deposit`, and `drift_withdraw` invoke `bank.update_bank_cache(&group)` without a preceding `bank.accrue_interest(...)` call in the same function, unlike every native-path instruction which pairs both calls. A concrete PoC would: (1) deposit/borrow to establish non-zero `total_asset_shares`/`total_liability_shares` on a Kamino/JupLend/Solend bank, (2) wait a significant amount of time (e.g. a week), (3) call `kamino_deposit`/`juplend_deposit`/`solend_deposit` with a trivial amount, (4) observe `bank.last_update` jumps to current time while `asset_share_value`/`liability_share_value` and `cache.interest_accumulated_for` remain unchanged, confirming the elapsed interest for that period was permanently skipped. I was unable to run this test against the live program in this session and recommend a Devin/CI session to confirm the runtime behavior before treating this as fully proven.

    fn update_bank_cache(&mut self, group: &MarginfiGroup) -> MarginfiResult<()> {
        if self.cache.is_liquidation_price_cache_locked() {
            return Ok(());
        }
        let total_assets_amount: I80F48 = self.get_asset_amount(self.total_asset_shares.into())?;
        let total_liabilities_amount: I80F48 =
            self.get_liability_amount(self.total_liability_shares.into())?;

        if (total_assets_amount == I80F48::ZERO) || (total_liabilities_amount == I80F48::ZERO) {
            self.cache.reset_preserving_oracle_price();
            return Ok(());
        }

        let ir_calc = self
            .config
            .interest_rate_config
            .create_interest_rate_calculator(group);

        let utilization_rate: I80F48 = total_liabilities_amount
            .checked_div(total_assets_amount)
            .ok_or_else(math_error!())?;
        let interest_rates = ir_calc.calc_interest_rate(utilization_rate)?;

        update_interest_rates(&mut self.cache, &interest_rates);

        // Update banks last update timestamp
        self.last_update = Clock::get()?.unix_timestamp;
        Ok(())
