### Title
Missing `contract-caller == tx-sender` authorization check in `borrow` allows position/health-check state to be established through an untrusted intermediary contract - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The external report's core theme is that "protected"/administrative actions performed on a user's behalf must always enforce explicit consent from the true originator, and that inconsistent enforcement of that consent across similar critical entry points creates exploitable gaps. In Zest's market entry points, this pattern is enforced explicitly on `collateral-add` and `repay` via `(asserts! (is-eq contract-caller tx-sender) ERR-AUTHORIZATION)`, but is absent from `borrow`, the debt-issuing entry point.

### Finding Description
`collateral-add` and `repay` in `mainnet/contracts/market/v0-4-market.clar` both explicitly require that the immediate caller equal the original transaction sender: [1](#0-0) [2](#0-1) 

This check is a deliberate design guard (per `docs/High-Level-Overview.md`, described as the "M05 audit fix" that "eliminates explicit account parameter" and instead relies on `contract-caller`) intended to prevent an intermediary/wrapping contract from silently establishing or altering position state that the real signer did not directly consent to in that specific call. [3](#0-2) 

`borrow`, however — the function that actually creates new debt against an account and moves funds out of the protocol — has no such check: [4](#0-3) 

Because `account` and the default `funds-receiver` are both derived from `contract-caller` (not `tx-sender`) with no equality assertion, `borrow` can be invoked with `contract-caller` being any intermediary contract in the call stack, not just the directly signing wallet. This breaks the same invariant the other two functions were hardened to protect: any contract a user interacts with in the same transaction (e.g. one they signed a transaction for believing it does something benign) can call `borrow` as an inner `contract-call?`, and the resulting debt position and health-check computations run against `contract-caller` (the intermediary) with no requirement that this intermediary equal the real signer. This is precisely the "administrative/consent" gap the report calls out: a critical, fund-moving action (debt issuance + token transfer to a receiver) is reachable without the same consent-equivalent check (`contract-caller == tx-sender`) that sibling critical functions enforce.

### Impact Explanation
This inconsistency undermines the protocol's own stated invariant that `borrow`, `collateral-add`, `repay`, and `liquidate` are meant to share the same "hot path" authorization model (per the overview doc). Since `borrow` moves real funds (`vault-system-borrow` sends tokens to `funds-receiver`) and creates scaled debt via `debt-add-scaled`, a caller path that bypasses the `contract-caller == tx-sender` guard while still exercising full health-check/egroup logic means the safety property the audit fix ("M05") intended to guarantee for market entry points is not uniformly applied. Given the fix's own stated purpose is to prevent account impersonation/consent bypass through intermediary contracts, its absence in `borrow` is a direct regression of that protection on the debt-issuance path, which is capable of moving funds out of the vaults (temporary/permanent freezing or theft-adjacent risk depending on how the missing check is exploited by an untrusted intermediary a victim unknowingly calls through).

### Likelihood Explanation
Likelihood is moderate: the missing check only matters if a user's transaction routes through an untrusted or compromised intermediary contract that then calls `market.borrow`. In Clarity's model, `contract-caller` for `market.borrow` would be whatever contract makes that `contract-call?`, so an attacker would need to get a user to invoke a contract that in turn calls `borrow`. This is a plausible integration/composability attack surface for a DeFi money-market with router/aggregator ecosystems, and the code's own comments show the project was specifically worried about this precise scenario for the other two hot-path functions, but neglected to apply it consistently to `borrow`.

### Recommendation
Add the same `(asserts! (is-eq contract-caller tx-sender) ERR-AUTHORIZATION)` precondition to `borrow` as already present in `collateral-add` and `repay`, so all fund/debt-affecting market entry points enforce a consistent, direct-signer-only authorization model, matching the intended invariant documented in the architecture overview.

### Proof of Concept
1. Deploy an intermediary contract `router.clar` that, inside a public function, performs `(contract-call? .v0-market ... borrow ft amount none none)`.
2. A user calls `router.contract-fn` (tx-sender = user).
3. Inside `market.borrow`, `contract-caller` is `router`, not the user; `account` and `funds-receiver` both resolve to `router`'s principal.
4. `borrow` proceeds without the `(asserts! (is-eq contract-caller tx-sender) ...)` check that `collateral-add`/`repay` would have enforced, allowing debt/position state to be established through the router with no explicit consent guard at this layer — contrasted directly with `collateral-add`/`repay`, which would reject the same call pattern with `ERR-AUTHORIZATION`. [5](#0-4)
