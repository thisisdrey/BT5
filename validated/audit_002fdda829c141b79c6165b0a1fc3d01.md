### Title
FetchRemote leaks embedded URL credentials in the gRPC error message returned to callers - ([File: internal/gitaly/service/repository/fetch_remote.go])

### Summary
`FetchRemote` builds the remote URL (potentially containing `user:pass@`) purely as a git config value and never strips or sanitizes it before propagating raw `git-fetch(1)` stderr into the gRPC error returned to the caller. The only sanitization mechanism in the codebase, `internal/log/url_sanitizer.go`'s `URLSanitizerHook`, is wired solely into the logrus logger and never touches the actual `structerr` status returned over gRPC, and `internal/helper/security.go`'s `SanitizeString`/`SanitizeError` are unused dead code.

### Finding Description
In `buildCommandOpts` (`internal/gitaly/service/repository/fetch_remote.go:260-304`), the full attacker-controlled `req.GetRemoteParams().GetUrl()` (which may embed `user:pass@host`) is placed into `remote.inmemory.url` git config as-is: [1](#0-0) . When the fetch fails, `fetchRemoteAtomic` captures raw stderr from `git-fetch(1)` and forwards it verbatim into the returned gRPC error: [2](#0-1) . Git/libcurl's own authentication/HTTP error messages routinely embed the full URL including userinfo (e.g. `fatal: Authentication failed for 'https://user:pass@host/foo.git/'`), a format explicitly acknowledged by the test fixture in `internal/log/url_sanitizer_test.go:44-49` [3](#0-2) . Nothing sanitizes this string before it becomes the gRPC status message: `structerr.NewInternal("fetch remote: %q: %w", errMsg, err)` is returned directly to the RPC caller with the raw stderr embedded. The sanitization that does exist, `URLSanitizerHook`, is installed only against the logrus logger in `internal/cli/gitaly/serve.go`, scrubbing log output, not gRPC responses [4](#0-3) . `internal/helper/security.go`'s `SanitizeString`/`SanitizeError` are never called anywhere except their own test file [5](#0-4) , confirming there is no reachable sanitization path from any RPC handler's error return to the client.

By contrast, `CreateRepositoryFromURL`'s `cloneFromURLCommand` explicitly strips userinfo from the URL before passing it as a command argument (`u.User = nil`) and moves credentials into an `http.extraHeader` config value instead [6](#0-5) , so that specific RPC's argv/stderr generally would not surface raw credentials the same way — this RPC is not the primary exploit vector; `FetchRemote` is, since it never strips or moves the credentials before they reach git and its error path.

### Impact Explanation
An unprivileged user who owns a repository can trigger `FetchRemote` with a `RemoteParams.Url` of the form `https://user:pass@attacker-controlled-or-failing-host/...` and, on failure, receive the raw credentials back inside the gRPC `Internal` status message (`status.Convert(err).Message()`), which is visible in GitLab Rails logs, API responses, and any client displaying the RPC error. This is a genuine credential-disclosure bug (matches GitLab's "Sensitive information disclosure" bounty class) — though note the "credentials" disclosed are the ones the attacker themselves supplied in the URL, so the direct security value is limited to cases where the URL points at infrastructure/credentials not fully controlled by the attacker (e.g., copy-pasted org secrets, shared mirror credentials, or credentials obtained via SSRF/redirect tricks against another target where the attacker doesn't already know the full pass).

### Likelihood Explanation
Highly likely and trivially repeatable: any project owner can call `FetchRemote` (a standard, unauthenticated-beyond-normal-RBAC mutator RPC) with a crafted URL pointing to a host that will fail (bad path, non-existent repo, wrong port, auth failure), no special config or privilege needed.

### Recommendation
Sanitize any URL-derived error text before it is embedded in a returned `structerr`/gRPC status, e.g. by calling `helper.SanitizeString` (making the currently-dead code load-bearing) on `errMsg`/`stderr` in `fetchRemoteAtomic` and any other handler that forwards raw git stderr containing a remote URL, and add a regression test asserting `status.Convert(err).Message()` never contains unredacted `user:pass@` sequences for `FetchRemote`, `CreateRepositoryFromURL`, and `UpdateRemoteMirror`.

### Proof of Concept
```go
func TestFetchRemote_credentialLeakInErrorMessage(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, client := setupRepositoryService(t)
    repoProto, _ := gittest.CreateRepository(t, ctx, cfg)

    _, err := client.FetchRemote(ctx, &gitalypb.FetchRemoteRequest{
        Repository: repoProto,
        RemoteParams: &gitalypb.Remote{
            Url: "https://someuser:supersecretpassword@127.0.0.1:1/nonexistent.git",
        },
    })
    require.Error(t, err)
    msg := status.Convert(err).Message()
    // demonstrates the raw credentials survive into the client-visible gRPC message
    require.NotContains(t, msg, "supersecretpassword", "credentials must not leak in gRPC error")
}
```
Expected today: the assertion fails because `supersecretpassword` appears in the returned error message (via the embedded stderr/URL from the failed `git-fetch(1)` call).

// Fire is called by logrus.
func (hook *URLSanitizerHook) Fire(entry *logrus.Entry) error {
	mth, ok := entry.Data["grpc.method"]
	if !ok {
		return nil
	}

	mthStr, ok := mth.(string)
	if !ok || !hook.possibleGrpcMethods[mthStr] {
		return nil
	}

	if _, ok := entry.Data["args"]; ok {
		sanitizeSpawnLog(entry)
	} else if _, ok := entry.Data["error"]; ok {
		sanitizeErrorLog(entry)
	} else {
		entry.Message = sanitizeString(entry.Message)
	}

	return nil
}

// SanitizeString will clean password and tokens from URLs, and replace them

func SanitizeString(str string) string {
	return hostPattern.ReplaceAllString(str, "$1[FILTERED]@$3$4")
}

// SanitizeError does the same thing as SanitizeString but for error types
func SanitizeError(err error) error {
	return errors.New(SanitizeString(err.Error()))
