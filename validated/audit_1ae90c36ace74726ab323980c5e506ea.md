### Title
Unprivileged dust transfers fill a victim's per-account token set to `MAX_TOKENS_PER_USER`, DoSing deposits, mints, transfers and liquidations — (File: contracts/Pool.sol)

### Summary
The referenced bug class is *unauthenticated exhaustion of a finite, non-reclaimable lookup table* (the BEAM atom table) by feeding distinct attacker-controlled keys. Metronome has a direct structural analog: the per-account sets `depositTokensOfAccount` / `debtTokensOfAccount` are a bounded lookup table (`MAX_TOKENS_PER_USER = 30`, `Pool.sol:79`), and *any* third party can insert entries into a victim's table — without the victim's consent — via `DepositToken.deposit(amount_, onBehalfOf_ = victim)` or plain `DepositToken.transfer(victim, dust)`. Once the cap is hit, every code path that adds a new token to the account reverts with `UserReachedMaxTokens`, permanently blocking (until the victim manually cleans up) new collateral deposits, new synthetic debt issuance, inbound transfers, and — critically — liquidations where the seized collateral token is not already in the liquidator's or fee collector's set.

### Finding Description
`DepositToken._transfer` and `_mint` unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is zero (`contracts/DepositToken.sol:486-488, 517-520`). On the `Pool` side, `addToDepositTokensOfAccount` is guarded by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (`contracts/Pool.sol:143-148, 216-220`). The equivalent `DebtToken` path calls `addToDebtTokensOfAccount` on `issue` (`contracts/Pool.sol:204-208`).

Like the MP4 parser interning arbitrary 4-byte names, the Pool inserts attacker-chosen keys (token addresses) into a victim-keyed table the victim never asked to populate, and entries persist until the victim's balance for that token returns to zero. There is no opt-in, no minimum-amount check, and no way for the victim to prevent insertion — `deposit(amount_, onBehalfOf_)` is permissionless and accepts any beneficiary (`contracts/DepositToken.sol:211-237`).

Attack flow (unprivileged EOA, no privileged role needed):

1. For every deposit token `D_i` registered on the pool, attacker deposits a small amount for themselves and calls `D_i.transfer(victim, 1)` (or `deposit(1, victim)` where the deposit fee rounds to 0).
2. Each transfer inserts `D_i` into `depositTokensOfAccount[victim]`. Combined with debt tokens the victim already holds, the set reaches `MAX_TOKENS_PER_USER = 30`.
3. From then on:
   - `D_new.deposit(x, victim)` reverts — `_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`.
   - `DebtToken_new.issue(..., victim)` reverts — same cap via `addToDebtTokensOfAccount`.
   - `D_new.transfer(victim, ...)` / `transferFrom` revert — victim cannot receive new deposit tokens, e.g., rescue collateral sent by a helper.
   - `Pool.liquidate` seizes collateral to the liquidator via `DepositToken.seize` → `_transfer` → `addToDepositTokensOfAccount(liquidator)`; a liquidator whose own set is full (or the `feeCollector`, which receives the protocol fee mint) reverts, shrinking the set of viable liquidators for positions backed by many tokens.

The invariant broken is liveness of the per-account token registry, mirroring the atom-table exhaustion: a shared bounded resource is consumed by unsolicited entries.

### Impact Explanation
An underwater-or-nearly-underwater victim who is dusted to the cap cannot add any *new* collateral type to restore health (`deposit` reverts) and cannot open a position in any new synthetic. This can force an otherwise saveable position into liquidation — i.e., real loss of funds, not just inconvenience. More broadly, the victim's ability to interact with the pool is frozen until they notice and manually transfer out the dust (each `transfer` of the full dust balance removes one entry via `removeFromDepositTokensOfAccount`). This is a temporary freezing of funds / forced-liquidation-griefing vector that costs the attacker only gas plus ~30 dust deposits.

### Likelihood Explanation
- Fully permissionless: `deposit` and `transfer` have no allowlist on the beneficiary/recipient; the only guard (`onlyIfAdditionWillNotReachMaxTokens`) is what creates the revert.
- Cost to attacker: ~30 token acquisitions + transfers; dust amounts suffice since insertion only requires `amount_ > 0` and prior balance `== 0`.
- Feasibility depends on the pool listing enough distinct tokens — the cap counts `depositTokensOfAccount.length + debtTokensOfAccount.length` combined, so a pool with ≥30 listed deposit+debt tokens, or a victim already holding some, is reachable. On pools with fewer listed tokens the combined cap cannot be reached and the attack partially degrades (victim can still be pushed to `length == N` where every *remaining* action reverts only for not-yet-held tokens).
- Victim self-recovery exists (transfer dust away), which caps severity at Medium rather than permanent lock.

### Recommendation
- Add a `userMinBalance`/ejection mechanism: let an account call `Pool.removeFromDepositTokensOfAccount(self, token)` directly (or `DepositToken.sweep(token)`) so cleanup is one cheap call per token instead of full-balance transfers.
- Alternatively, exempt same-token deposits from the cap check ordering (check membership before `length`), or only count tokens above a non-trivial balance threshold toward the cap.
- Optionally, require `onBehalfOf_`/recipient opt-in for first-time token insertion (e.g., pull-pattern registration), mirroring the upstream fix's use of `to_existing_atom` + `:unknown` — only pre-registered names/addresses are allowed into the table.

### Proof of Concept
Hardhat fork test outline (reproducible on a fork where the pool lists ≥1 deposit tokens):

```ts
// test/grief/MaxTokensGrief.fork.ts (sketch)
// setup: fork mainnet, attach to deployed Pool + DepositTokens, impersonate victim already holding D debt+deposit tokens

const victim = "0xVictim";
const attacker = await ethers.getImpersonatedSigner("0xAttackerEOA");

const pool = await ethers.getContractAt("Pool", POOL_ADDR);
const depositTokens: string[] = await pool.getDepositTokens();

// 1) attacker fills victim's account-token set to the cap
for (const addr of depositTokens) {
  const d = await ethers.getContractAt("DepositToken", addr);
  const underlying = await ethers.getContractAt("IERC20", await d.underlying());
  await getWhaleTokens(underlying, attacker.address); // fund attacker
  await underlying.connect(attacker).approve(d.address, ethers.constants.MaxUint256);
  await d.connect(attacker).deposit(ethers.utils.parseUnits("1", await underlying.decimals()), attacker.address);
  await d.connect(attacker).transfer(victim, 1); // inserts into victim's set
}

const len = (await pool.getDepositTokensOfAccount(victim)).length
          + (await pool.getDebtTokensOfAccount(victim)).length;
expect(len).to.eq(await pool.MAX_TOKENS_PER_USER()); // 30, or == number of listed tokens

// 2) victim can no longer deposit a collateral type they don't already hold
const dNew = await ethers.getContractAt("DepositToken", NEW_DEPOSIT_TOKEN);
await expect(dNew.connect(victimSigner).deposit(1, victim))
  .to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

// 3) new synth issuance also reverts
const debt = await ethers.getContractAt("DebtToken", NEW_DEBT_TOKEN);
await expect(debt.connect(victimSigner) /* via Pool/synthetic mint path */)
  .to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");
```

On pools where the combined registered token count is below 30, steps 2–3 show the victim is still pushed to the cap boundary and every not-yet-held token becomes unusable; where the count reaches 30 the DoS is complete until cleanup.
