### Title
Concurrency limit for `PackObjectsHook` is bypassed when `RemoteIp` is loopback or unparseable - ([File: internal/gitaly/service/hook/pack_objects.go])

### Summary
`packObjectsHook` only routes requests through the `packObjectsLimiter` (via `runPackObjectsLimited`) when the client's `RemoteIp` parses to a non-loopback address. Any request whose `RemoteIp` is empty, malformed, or a loopback address falls through to `runPackObjects`, which executes `git-pack-objects` with **no concurrency limiting at all**. This mirrors the reported bug class: a resource/limit check was implemented in one code path (`updateBalance` / here, `runPackObjectsLimited`) but a sibling code path (`transferFunds`/`updateCollateralShares` / here, the unconditional `runPackObjects` call) bypasses it entirely.

### Finding Description
In `packObjectsHook`, the decision of whether to apply the concurrency limiter is based on parsing the `RemoteIp` field of the incoming `PackObjectsHookWithSidechannelRequest`: [1](#0-0) 

```go
servedBytes, created, err := s.packObjectsCache.Fetch(ctx, cacheKey, output, func(w io.Writer) error {
    ipAddr := net.ParseIP(req.GetRemoteIp())
    if ipAddr == nil {
        // Best effort, maybe the remote IP includes source port
        if ip, _, err := net.SplitHostPort(req.GetRemoteIp()); err == nil {
            ipAddr = net.ParseIP(ip)
        }
    }
    // Ignore loop-back IPs
    if ipAddr != nil && !ipAddr.IsLoopback() {
        return s.runPackObjectsLimited(
            ctx, w, ipAddr.String(), req, args, stdin, cacheKey,
        )
    }

    return s.runPackObjects(ctx, w, req, args, stdin, cacheKey)
})
```

The concurrency limiter (`s.packObjectsLimiter.Limit`, configured via `cfg.PackObjectsLimiting`) is only invoked inside `runPackObjectsLimited`: [2](#0-1) 

If `req.GetRemoteIp()` is empty, an unparseable string, or resolves to a loopback address (`127.0.0.1`, `::1`, or an unparseable value that leaves `ipAddr == nil`), `runPackObjects` is invoked directly, which executes `git-pack-objects` unconditionally, without ever entering the `packObjectsLimiter`. This is structurally identical to the reported bug: the safety check (`checkWithdrawLimits`) was folded into a single helper (`updateBalance`) and other legitimate call paths (`transferFunds`, `updateCollateralShares`) that should also honor the limit skip it because they never call that helper.

### Impact Explanation
The `packObjectsLimiter` exists specifically to bound the number of concurrent `git-pack-objects` invocations per client (see `internal/cli/gitaly/serve.go`, where `PackObjectsLimiting` concurrency/queue settings are wired up), protecting the server from resource exhaustion caused by many simultaneous CPU/memory-intensive pack generation processes. If the limiter can be trivially skipped by supplying (or omitting) a loopback/malformed `RemoteIp`, an unprivileged client using the smart HTTP or SSH upload-pack path (which populates this hook request) can spawn unlimited concurrent `git-pack-objects` processes, defeating the configured concurrency/queue protections and leading to denial of service on the Gitaly node (matches "DoS of a handler" acceptance criterion).

### Likelihood Explanation
Likelihood depends on how strictly `RemoteIp` is populated/validated before being placed into `PackObjectsHookWithSidechannelRequest`. From the code inspected, `RemoteIp` is a plain string field forwarded through the git hook environment set by `cmd/gitaly-hooks/hooks.go` and is parsed defensively (`net.ParseIP` failing silently and falling back to `runPackObjects`), which indicates the code already anticipates that this value can be missing or malformed in normal operation (e.g., unix socket connections, misconfigured proxies, or loopback testing) — not just as an intentional attack. I was not able to fully verify, within the available tool budget, whether an external, unprivileged client can directly control the exact string used to populate `RemoteIp` end-to-end (e.g., via a spoofed `X-Forwarded-For`-like header or proxy protocol field) versus it always being derived server-side from the actual TCP peer address. This uncertainty affects whether the likelihood is "any client can trivially trigger it" vs. "only triggerable under specific proxy/loopback deployment topologies."

### Recommendation
Do not skip the concurrency limiter based on the remote IP classification. Either:
- Always route through `s.packObjectsLimiter.Limit(...)`, using a fallback limiter key (e.g., authenticated user ID / `GlId`, or a constant key) when `RemoteIp` cannot be parsed or is loopback, instead of bypassing limiting entirely, or
- Fail closed (reject or limit maximally) when `RemoteIp` is empty/unparseable rather than treating it as an unlimited-loopback exemption.

### Proof of Concept
1. A client connects to Gitaly's smart HTTP/SSH `upload-pack` path such that the `PackObjectsHookWithSidechannelRequest.RemoteIp` field ends up empty, malformed, or resolves to a loopback address (this can occur, for example, when Gitaly is fronted by a proxy/unix socket that does not forward a well-formed peer IP, or when the caller of `PackObjectsHookWithSidechannel` sets `RemoteIp: ""`, as seen in several call sites in `pack_objects_test.go`).
2. The client issues many concurrent `git fetch`/`git clone` requests against the same or different repositories.
3. `packObjectsHook` computes `ipAddr := net.ParseIP(req.GetRemoteIp())`, gets `nil` or a loopback address, and calls `s.runPackObjects(...)` directly instead of `s.runPackObjectsLimited(...)`.
4. `s.packObjectsLimiter.Limit(...)` (the configured `ConcurrencyLimiter` with `QueueMax`/`MaxQueueWait`) is never invoked for these requests, so an arbitrary number of `git-pack-objects` processes run concurrently, exhausting CPU/memory on the Gitaly node — the exact resource-exhaustion outcome the limiter in `internal/cli/gitaly/serve.go` (`packObjectsLimiterAuthenticated`) was designed to prevent.

func (s *server) runPackObjectsLimited(
	ctx context.Context,
	w io.Writer,
	limitkey string,
	req *gitalypb.PackObjectsHookWithSidechannelRequest,
	args *packObjectsArgs,
	stdin io.ReadCloser,
	key string,
) error {
	ctx = context.WithoutCancel(ctx)

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	defer stdin.Close()

	if _, err := s.packObjectsLimiter.Limit(
		ctx,
		limitkey,
		func() (interface{}, error) {
			return nil,
				s.runPackObjectsFn(
					ctx,
					s.gitCmdFactory,
					w,
					req,
					args,
					stdin,
					key,
				)
		},
	); err != nil {
		return err
	}

	return nil
}
