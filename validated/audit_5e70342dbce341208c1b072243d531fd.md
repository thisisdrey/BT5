## Title
Guard-representative withdraw restriction is bypassed when reward allowance is converted to balance via `SELFDESTRUCT` - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
`WithdrawBalanceActuator.validate()` and `WithdrawRewardProcessor.validate()` both explicitly forbid a genesis "guard representative" (GP) witness account from moving its accumulated voting-reward `allowance` into spendable `balance`. However, the TVM `SUICIDE`/`SELFDESTRUCT` opcode path performs the *same* allowance→balance state mutation through a different internal function, `Program.withdrawRewardAndCancelVote()`, which never performs the guard-representative check. This mirrors the JOJO `_handleBadDebt` bug class: a privileged/guarded balance-mutating operation is duplicated in an internal code path that omits the invariant check enforced by the "normal" entry point.

### Finding Description
The GP restriction is defined identically in two places: [1](#0-0) [2](#0-1) 

Both require that `ownerAddress` not be one of the genesis-block witnesses before allowing `allowance` to be merged into `balance`.

The same underlying mutation — clearing votes, calling `VoteRewardUtil.withdrawReward`, then adding `allowance` to `balance` and zeroing `allowance` — is also performed by `Program.withdrawRewardAndCancelVote()`, invoked from `suicide2()` when a contract self-destructs: [3](#0-2) 

This private helper has **no** `isGP` check at all, unlike the two entry points above. It is called unconditionally from `suicide2()`: [4](#0-3) 

After `withdrawRewardAndCancelVote()` runs, `suicide2()` immediately transfers the account's full balance (now inflated by the previously-locked allowance) to the `obtainer` address via `MUtil.transfer`, so any allowance that should have been frozen for a GP account is both released into `balance` and swept out to another address in the very same operation, entirely bypassing the check that `WithdrawBalanceActuator`/`WithdrawRewardProcessor` enforce.

### Impact Explanation
If a genesis guard-representative address is (or becomes) a smart-contract account capable of executing `SELFDESTRUCT`, it can convert reward `allowance`, which the protocol explicitly locks for GP accounts, into spendable `balance` and transfer it to an arbitrary `obtainer` address in one transaction, circumventing the deliberate withdrawal restriction placed on guard representatives. This is an unauthorized account operation / fund-flow bypass of a protocol-level invariant, analogous to the JOJO insurance-account bug where an internal balance-mutating path skips a check that all "normal" paths enforce.

### Likelihood Explanation
Exploitation requires the guard-representative address to be able to execute contract code (i.e., act as a contract with the `SUICIDE` opcode), which is not the typical configuration for genesis witnesses but is not technically prevented by the account model. The reachability requirement is a single `SELFDESTRUCT`/`suicide2` transaction, which any TVM contract holder can trigger through ordinary contract calls — no special privileges beyond controlling the affected address are needed.

### Recommendation
Add the same `isGP` (guard-representative) check inside `Program.withdrawRewardAndCancelVote()` before moving `allowance` into `balance`, mirroring `WithdrawBalanceActuator.validate()` and `WithdrawRewardProcessor.validate()`, so that the restriction cannot be bypassed through the self-destruct code path.

### Proof of Concept
1. Configure/observe a genesis-block guard-representative address that is also capable of running contract bytecode (or a future upgrade that allows a witness account to become a contract).
2. Accrue voting reward `allowance` for that address via `MortgageService.payReward`/`VoteRewardUtil` (normal reward distribution).
3. From that address, execute a contract call ending in `SUICIDE`/`SELFDESTRUCT`, reaching `Program.suicide2()`.
4. Observe that `withdrawRewardAndCancelVote()` moves `allowance` into `balance` without the `isGP` check that blocks the equivalent `WithdrawBalanceContract` transaction, and the inflated balance is transferred to the `obtainer` address in the same transaction.

  private void withdrawRewardAndCancelVote(byte[] owner, Repository repo) {
    VoteRewardUtil.withdrawReward(owner, repo);

    AccountCapsule ownerCapsule = repo.getAccount(owner);
    if (!ownerCapsule.getVotesList().isEmpty()) {
      VotesCapsule votesCapsule = repo.getVotes(owner);
      if (votesCapsule == null) {
        votesCapsule = new VotesCapsule(ByteString.copyFrom(owner),
            ownerCapsule.getVotesList());
      } else {
        votesCapsule.clearNewVotes();
      }
      ownerCapsule.clearVotes();
      ownerCapsule.setOldTronPower(0);
      repo.updateVotes(owner, votesCapsule);
    }
    try {
      long balance = ownerCapsule.getBalance();
      long allowance = ownerCapsule.getAllowance();
      ownerCapsule.setInstance(ownerCapsule.getInstance().toBuilder()
          .setBalance(addExact(balance, allowance, VMConfig.disableJavaLangMath()))
          .setAllowance(0)
          .setLatestWithdrawTime(getTimestamp().longValue() * 1000)
          .build());
      repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);
    } catch (ArithmeticException e) {
      throw new BytecodeExecutionException("Suicide: balance and allowance out of long range.");
    }
