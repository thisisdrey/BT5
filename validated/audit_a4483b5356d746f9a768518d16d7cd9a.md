## Analysis Summary

The Vertex Authorization report's core broken invariant is: **an unprivileged actor can perpetually inject "pending work" tied to a shared resource so that a critical, time-sensitive state transition (deauthorization) can never complete**, because the guard blocking that transition treats *any* pending item as blocking, and the attacker fully controls the supply of pending items.

The closest verifiable local analog that survives the impact gate (no admin/governance-as-root-cause, no front-run-only condition, real chain/bridge-processing impact) is in the Snowbridge V2 outbound queue: a permissionless, per-block-bounded shared `MessageQueue` where an attacker can continuously inject cheap "low priority" messages from a sibling parachain to indefinitely delay processing of high-value/governance-originated messages headed to Ethereum, degrading bridge delivery guarantees rather than a single admin call.

### Title
Permissionless flooding of the shared Snowbridge V2 outbound `MessageQueue` can indefinitely delay critical/governance message delivery to Ethereum - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`Pallet::do_process_message` in the Snowbridge V2 outbound queue caps the number of messages it will commit per block via `MaxMessagesPerBlock`, yielding (`Err(Yield)`) once the cap is hit [1](#0-0) . Messages are enqueued into the shared `pallet-message-queue`, which services queues in round-robin fashion by rotating the `ReadyRing` and draining pages until the weight limit is hit [2](#0-1) . Because any sibling parachain (an unprivileged, non-governance actor) can enqueue arbitrarily many outbound messages into the same aggregate queue used for BridgeHub-root/governance messages, an attacker can keep injecting low-priority messages every block to keep the queue permanently congested, delaying delivery of security- or governance-critical messages to Ethereum — this is demonstrated directly by the existing test that shows a governance message failing to execute in the same block once the queue is congested with 40 low-priority messages [3](#0-2) .

### Finding Description
`do_process_message` reads `MessageLeaves::<T>::decode_len()` and compares it against `T::MaxMessagesPerBlock::get()`; once the threshold is reached for the block, further messages (regardless of importance) are postponed with `Yield` [4](#0-3) . The underlying `pallet-message-queue` processes queues fairly by round-robin rotation through the `ReadyRing`, servicing a bounded number of pages/messages per queue before moving to the next ready queue [5](#0-4) . Any sibling parachain sovereign account can call `deliver` to enqueue outbound messages into this shared aggregate queue via ordinary XCM export (as exercised in `mock_message`/`OutboundQueue::deliver` in the test), with no admin/governance privilege required [6](#0-5) . The existing test `governance_message_not_processed_in_same_block_when_queue_congested_with_low_priority_messages` confirms that flooding one origin's queue with 40 low-priority messages delays a `bridge_hub_root_origin()` (governance) message by at least one full block, and that this delay compounds with the number of injected messages [7](#0-6) . Because nothing prevents an attacker from repeating this injection every block (the cost is only ordinary XCM delivery fees, which the message-queue's per-block cap does not scale with), the "pending" backlog is attacker-renewable indefinitely — the same structural pattern as the front-runnable "pending transaction" check in `AuthorizationModule.deauthorizeAccount`, where an attacker-controlled pending-item supply blocks an important state transition (there: deauthorization; here: timely governance/bridge-critical message commitment).

### Impact Explanation
This falls under "public underpriced work that degrades block production or stalls bridge processing" in the impact gate: an unprivileged party can persistently delay execution of governance-originated or otherwise important outbound Snowbridge V2 messages (e.g., halting/resuming the bridge, token registration control messages, security-relevant operational mode changes) by keeping the shared queue congested with cheap low-priority traffic, without needing any admin, validator, relayer, or prover compromise.

### Likelihood Explanation
Likelihood is high: enqueuing messages into the outbound queue only requires performing ordinary XCM exports from a sibling parachain (no special origin filter is applied at the `MessageQueue`/`do_process_message` layer to prioritize governance-originated messages ahead of general traffic within the same servicing window), and the behavior is already reproduced by an existing unit test, confirming the mechanism works as described without requiring any adversarial assumption beyond controlling XCM traffic from a chain able to reach BridgeHub.

### Recommendation
Give governance/BridgeHub-root-originated messages strict priority over other origins when servicing the shared `MessageQueue` (e.g., a dedicated always-serviced-first queue or weight reservation for `bridge_hub_root_origin()`), and/or bound how much of the per-block message budget non-privileged sibling-chain origins can consume, so that congestion from ordinary traffic cannot delay critical messages beyond a bounded number of blocks regardless of attacker-controlled volume.

### Proof of Concept
The existing regression test demonstrates the mechanism end-to-end: 40 low-priority messages are submitted from a sibling parachain, then a governance message is submitted; after one block only messages from the low-priority queue are drained and the governance message's footprint remains at 1 (unprocessed), only executing in a subsequent block [3](#0-2) . An attacker can trivially repeat this pattern every block from a controlled sibling parachain to keep re-extending the delay indefinitely.

//! # Scenario: Message processing
//!
//! The pallet runs each block in `on_initialize` or when being manually called through
//! [`frame_support::traits::ServiceQueues::service_queues`].
//!
//! First it tries to "rotate" the `ReadyRing` by one through advancing the `ServiceHead` to the
//! next *ready* queue. It then starts to service this queue by servicing as many pages of it as
//! possible. Servicing a page means to execute as many message of it as possible. Each executed
//! message is marked as *processed* if the [`Config::MessageProcessor`] return Ok. An event
//! [`Event::Processed`] is emitted afterwards. It is possible that the weight limit of the pallet
//! will never allow a specific message to be executed. In this case it remains as unprocessed and
//! is skipped. This process stops if either there are no more messages in the queue or the
//! remaining weight became insufficient to service this queue. If there is enough weight it tries
//! to advance to the next *ready* queue and service it. This continues until there are no more
//! queues on which it can make progress or not enough weight to check that.

#[test]
fn governance_message_not_processed_in_same_block_when_queue_congested_with_low_priority_messages()
{
	let sibling_id: u32 = 1000;

	new_tester().execute_with(|| {
		// submit a lot of low priority messages from asset_hub which will need multiple blocks to
		// execute(20 messages for each block so 40 required at least 2 blocks)
		let max_messages = 40;
		for _ in 0..max_messages {
			// submit low priority message
			let message = mock_message(sibling_id);
			let ticket = OutboundQueue::validate(&message).unwrap();
			OutboundQueue::deliver(ticket).unwrap();
		}

		let footprint =
			MessageQueue::footprint(SnowbridgeV2(H256::from_low_u64_be(sibling_id as u64)));
		assert_eq!(footprint.storage.count, (max_messages) as u64);

		let message = mock_governance_message::<Test>();
		let ticket = OutboundQueue::validate(&message).unwrap();
		OutboundQueue::deliver(ticket).unwrap();

		// move to next block
		ServiceWeight::set(Some(Weight::MAX));
		run_to_end_of_next_block();

		// first process 20 messages from sibling channel
		let footprint =
			MessageQueue::footprint(SnowbridgeV2(H256::from_low_u64_be(sibling_id as u64)));
		assert_eq!(footprint.storage.count, 40 - 20);

		// and governance message does not have the chance to execute in same block
		let footprint = MessageQueue::footprint(SnowbridgeV2(bridge_hub_root_origin()));
		assert_eq!(footprint.storage.count, 1);

		// move to next block
		ServiceWeight::set(Some(Weight::MAX));
		run_to_end_of_next_block();

		// now governance message get executed in this block
		let footprint = MessageQueue::footprint(SnowbridgeV2(bridge_hub_root_origin()));
		assert_eq!(footprint.storage.count, 0);

		// and this time process 19 messages from sibling channel so we have 1 message left
		let footprint =
			MessageQueue::footprint(SnowbridgeV2(H256::from_low_u64_be(sibling_id as u64)));
		assert_eq!(footprint.storage.count, 1);

		// move to the next block, the last 1 message from sibling channel get executed
		ServiceWeight::set(Some(Weight::MAX));
		run_to_end_of_next_block();
		let footprint =
			MessageQueue::footprint(SnowbridgeV2(H256::from_low_u64_be(sibling_id as u64)));
		assert_eq!(footprint.storage.count, 0);
	});
