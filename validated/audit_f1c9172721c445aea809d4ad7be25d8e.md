No vulnerability found for this question.

**Reasoning:**

`session.handleChannels` is only ever invoked after a successful SSH authentication handshake completes via `ssh.NewServerConn(c, s.config)` in `sshd/server.go`, which uses `PublicKeyCallback: cc.Authenticate` backed by `ssh.CertChecker` requiring either a CA-signed certificate (`IsUserAuthority`) or a pre-authorized public key (`UserKeyFallback`) [1](#0-0) . `NewSession`, and therefore `handleChannels`, is only called after that handshake returns without error [2](#0-1) . This directly contradicts the question's premise of an "unauthenticated" attacker with no CA-signed certificate reaching this code path — such an attacker's connection fails during `ssh.NewServerConn` and is closed before `handleChannels` is ever reached [3](#0-2) .

Additionally, `handleChannels` itself contains no unsafe parsing of attacker-controlled data — it only inspects `newChannel.ChannelType()` (a string) and calls `Accept()`/`Reject()`, both of which are safe library calls in `golang.org/x/crypto/ssh` [4](#0-3) . The one place raw payload bytes are unmarshaled (`ssh.Unmarshal(req.Payload, &payload)` for the `"exec"` request type in `handleRequests`) already checks and handles the error case, preventing a panic on malformed input [5](#0-4) .

Since the target function is unreachable without valid CA/authorized-key authentication (violating the stated unprivileged-attacker constraint) and contains no exploitable unchecked parsing logic, there is no valid finding here.

func (s *session) handleChannels(chans <-chan ssh.NewChannel) {
	defer s.Close()
	for newChannel := range chans {
		if newChannel.ChannelType() != "session" {
			s.l.Error("unknown channel type", "sshChannelType", newChannel.ChannelType())
			newChannel.Reject(ssh.UnknownChannelType, "unknown channel type")
			continue
		}

		channel, requests, err := newChannel.Accept()
		if err != nil {
			s.l.Warn("could not accept channel", "error", err)
			continue
		}

		go s.handleRequests(requests, channel)
	}
}
