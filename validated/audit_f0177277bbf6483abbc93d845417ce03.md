Audit Report

## Title
Multi-asset bounty curator can permanently block permissionless unassignment, indefinitely freezing bounty funds and curator deposit - (File: `substrate/frame/multi-asset-bounties/src/lib.rs`)

## Summary
`pallet-multi-asset-bounties::unassign_curator` lacks the `update_due`-based inactivity-timeout mechanism present in legacy `pallet-bounties`/`pallet-child-bounties`. Once a bounty enters `BountyStatus::Active { curator, .. }`, the only parties who can call `unassign_curator` are `RejectOrigin`, the curator itself, or (for child bounties) the parent curator — no arbitrary signed account can permissionlessly force removal after inactivity, unlike `pallet-bounties::unassign_curator`, which slashes an inactive curator once `update_due < block_number`.

## Finding Description
In `substrate/frame/multi-asset-bounties/src/lib.rs`, the `Active` branch of `unassign_curator` [1](#0-0)  matches on `maybe_sender`:
- `None` → only reachable via `T::RejectOrigin`, which slashes the curator deposit.
- `Some(sender) if sender == *curator` → curator voluntarily gives up, deposit returned.
- `Some(sender)` (any other signed account) → requires `sender == parent_curator` (i.e., only meaningful for child bounties, and only the parent bounty's curator can act); this fails with `BadOrigin` for any ordinary third party, and there is no path at all for a top-level bounty.

By contrast, `pallet-bounties::unassign_curator`'s `Active` branch checks `update_due` and allows any signed account to slash the curator once the timeout has elapsed [2](#0-1) . A repository-wide search confirms `update_due` is used only in `pallet-bounties` and `pallet-child-bounties`, and does not appear anywhere in `pallet-multi-asset-bounties`, meaning the `BountyStatus::Active` variant in this pallet does not even carry a timeout field to support such a check. No other permissionless recovery path (e.g., expiry, close_bounty) exists in the pallet.

## Impact Explanation
This matches the "permanent user-fund lock" impact category: bounty funds held in the bounty/child-bounty sub-account, and the curator's reserved `curator_deposit`, remain locked in `BountyStatus::Active` indefinitely if a curator simply never calls `award_bounty`/`claim_bounty`/`unassign_curator`, and `RejectOrigin` (governance) does not intervene. Unlike the legacy pallets, there is no permissionless liveness guarantee.

## Likelihood Explanation
Any account that becomes curator of a funded bounty or child bounty (by being proposed and accepting the role via the pallet's normal flow) can trigger this simply by remaining inactive — no privileged access, collusion, or governance action is needed on the attacker's part. This is a low-effort, fully reproducible design gap.

## Recommendation
Reintroduce an `update_due`-style inactivity timeout into the `Active` status of `pallet-multi-asset-bounties`, and allow any signed origin to slash and unassign the curator once the timeout elapses, matching `pallet-bounties`/`pallet-child-bounties` semantics.

## Proof of Concept
1. Fund a bounty via `fund_bounty`, then `propose_curator`/`accept_curator` so status becomes `BountyStatus::Active { curator }`.
2. Curator never calls `award_bounty`, `claim_bounty`, or `unassign_curator`.
3. A third-party signed account calls `unassign_curator(origin, parent_bounty_id, None)`.
4. In the `Active` branch's `Some(sender)` arm [3](#0-2) , `parent_curator` is `None` for a top-level bounty, so `parent_curator.ok_or(BadOrigin)?` immediately errors with `BadOrigin`.
5. The bounty remains `Active` indefinitely absent `RejectOrigin` action, confirming the absence of any permissionless recovery mechanism.
