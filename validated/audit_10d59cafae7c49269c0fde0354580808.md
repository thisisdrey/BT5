### Title
Self-trade in `MarketSellAssetActuator` causes lost balance/asset updates due to stale in-memory `AccountCapsule` overwrite - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.execute()` keeps a single in-memory `AccountCapsule` (`accountCapsule`/`takerAccountCapsule`) for the taker for the whole duration of order matching, and only persists it to `AccountStore` once, at the very end of `execute()`. During matching, however, the maker side of each fill is handled by re-fetching a **separate, independent** `AccountCapsule` instance straight from `AccountStore` and immediately persisting it back. If a user's own resting order is matched against their own new order (self-trade, which is not prevented anywhere in `validate()`), the maker-side fetch/put and the taker-side fetch/put operate on two different in-memory copies of the *same* underlying account, and the last write wins — silently discarding the updates made by the other copy.

### Finding Description
In `execute()`, the taker account is loaded once: [1](#0-0) 

It is then mutated in place across several steps (fee deduction, `transferBalanceOrToken`, and matching), and only committed to the store at the very end of `execute()`: [2](#0-1) 

During matching, `matchSingleOrder` credits the taker using the *same* in-memory `takerAccountCapsule` reference (no intermediate store write), but credits the maker via `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)`, which fetches a **brand-new** `AccountCapsule` from `AccountStore` for the maker's owner address and immediately writes it back to the store: [3](#0-2) 

`validate()` never checks that the maker order's owner differs from the taker's owner address, so a user can create a sell order that immediately matches one of their own resting orders in the order book: [4](#0-3) 

When taker == maker (self-trade):
1. `accountStore.get()` at line 114 loads copy A of the account into `accountCapsule`/`takerAccountCapsule`.
2. Fee is deducted and `transferBalanceOrToken` reduces the sell-token balance on copy A (in memory only).
3. During matching, `addTrxOrToken(takerOrderCapsule, ..., takerAccountCapsule)` credits the buy-token to copy A (in memory only).
4. `addTrxOrToken(makerOrderCapsule, ...)` fetches copy B fresh from `AccountStore` (line 551-552) — copy B still has the **pre-transaction** balance, since copy A's changes have not yet been flushed. It credits the maker-side proceeds to copy B and immediately does `accountStore.put(...)` (line 561), overwriting the store with copy B.
5. Back in `execute()`, line 148 does `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` using copy A, which overwrites the store again — discarding the maker-side credit written in step 4 (copy B's update is lost), while re-applying copy A's earlier fee/sell/buy changes.

Net effect: whichever side's update is applied last (in this case copy A, since matching happens before the final `execute()` store write) silently erases the other's update. Concretely, the token/TRX the account should have received as the **maker** in the self-trade is lost (never reflected in the final on-chain balance), even though `orderStore` and other side effects (order-book removal, `MarketOrderDetail`, order state) already recorded the trade as fully executed.

This mirrors the reported Solidity bug class: two different in-memory representations of what should be the same persisted state are mutated independently, and only one write survives, silently invalidating the other mutation.

### Impact Explanation
An account can lose the assets/TRX it is entitled to receive as the maker side of a self-matched order, while the trade is still recorded as executed in `MarketOrderCapsule`/`MarketOrderDetail` and the order book. This is a permanent, unrecoverable loss of user funds triggerable by a single ordinary `MarketSellAssetContract` broadcast from any account, without any special privilege, satisfying "theft or permanent freezing of funds" under an unprivileged, single-transaction path (Wallet/actuator `execute()`).

### Likelihood Explanation
This requires only that an account (1) places a resting order on the exchange (`MarketSellAssetActuator` normal usage/`saveRemainOrder`), and (2) later places an opposing order priced to match its own resting order. Nothing in `validate()` prevents an address from matching against its own order, so this is reachable by any single account without cooperation from another party, using only the public `MarketSellAssetContract` transaction type.

### Recommendation
In `matchSingleOrder`/`addTrxOrToken`, avoid re-fetching a fresh `AccountCapsule` for the maker when the maker's owner address equals the taker's owner address (self-trade) — instead operate on the same in-memory `takerAccountCapsule` instance in that case, or otherwise ensure that the taker's outstanding in-memory changes are flushed to `AccountStore` before any maker-side fetch, and re-read the taker account fresh from the store after matching completes rather than relying on the pre-matching in-memory object. Alternatively, disallow self-trading entirely in `validate()`.

### Proof of Concept
1. Account `A` places a sell order O1 (sell 100 TokenX for 100 TRX) via `MarketSellAssetContract`; since no immediate match exists, it is saved to the order book (`saveRemainOrder`).
2. Account `A` (same address) later places a second sell order O2 (sell 100 TRX for 100 TokenX) priced to match O1.
3. In `execute()` for O2, `accountCapsule` (copy A) for address `A` is loaded, fee deducted, and `transferBalanceOrToken` reduces `A`'s TRX balance by 100 (in-memory only).
4. `matchOrder` → `matchSingleOrder` matches O2 (taker) against O1 (maker, also owned by `A`).
5. `addTrxOrToken(takerOrderCapsule, 100, takerAccountCapsule)` credits 100 TokenX to copy A (in memory).
6. `addTrxOrToken(makerOrderCapsule, 100)` fetches copy B of `A`'s account fresh from `AccountStore` (still missing steps 3's fee/TRX deduction and step 5's TokenX credit), adds 100 TRX to copy B, and persists copy B to `AccountStore`.
7. Back in `execute()`, line 148 persists copy A (with fee deducted, TRX reduced by 100, TokenX increased by 100) to `AccountStore`, overwriting copy B and permanently discarding the +100 TRX credit that should have been paid to `A` as the maker.
8. Final result: `A` paid the sell-order fee and lost 100 TRX from `transferBalanceOrToken`, gained 100 TokenX as taker, but never received the 100 TRX it was owed as maker — net fund loss of 100 TRX, even though both `MarketOrderCapsule`s show the trade as fully filled.

  private MarketOrderCapsule createAndSaveOrder(AccountCapsule accountCapsule,
      MarketSellAssetContract contract) {
    MarketAccountOrderCapsule marketAccountOrderCapsule = marketAccountStore
        .getUnchecked(contract.getOwnerAddress().toByteArray());
    if (marketAccountOrderCapsule == null) {
      marketAccountOrderCapsule = new MarketAccountOrderCapsule(contract.getOwnerAddress());
    }

    // note: here use total_count
    byte[] orderId = MarketUtils
        .calculateOrderId(contract.getOwnerAddress(), sellTokenID, buyTokenID,
            marketAccountOrderCapsule.getTotalCount());
    MarketOrderCapsule orderCapsule = new MarketOrderCapsule(orderId, contract);

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    orderCapsule.setCreateTime(now);

    marketAccountOrderCapsule.addOrders(orderCapsule.getID());
    marketAccountOrderCapsule.setCount(marketAccountOrderCapsule.getCount() + 1);
    marketAccountOrderCapsule.setTotalCount(marketAccountOrderCapsule.getTotalCount() + 1);
    marketAccountStore.put(accountCapsule.createDbKey(), marketAccountOrderCapsule);
    orderStore.put(orderId, orderCapsule);

    return orderCapsule;
  }
