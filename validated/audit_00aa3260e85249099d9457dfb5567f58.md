### Title
Unhardened tar extraction in `CreateRepositoryFromSnapshot` allows symlink-based archive extraction escape - (File: internal/gitaly/service/repository/create_repository_from_snapshot.go)

### Summary
`CreateRepositoryFromSnapshot` fetches an archive from a caller-supplied `HttpUrl` and pipes it directly into a raw `tar -C <path> -xvf -` extraction with no symlink stripping, no path validation, and no `--no-same-owner`/`-P` hardening, mirroring the root cause of the GitLab bulk-imports `UploadsPipeline` bug (untarring an archive without removing symlinks).

### Finding Description
The `untar` helper issues an HTTP GET against `in.GetHttpUrl()` (optionally authenticated with `in.GetHttpAuth()` and resolved via `in.GetResolvedAddress()`), then streams the response body straight into `tar -C path -xvf -`: [1](#0-0) 

Unlike the sibling snapshot-extraction path in `replicate.go`, which was hardened with explicit `tar.TypeSymlink`/`tar.TypeLink` boundary checks that reject absolute symlinks and validate that resolved targets stay under `targetDir`: [2](#0-1) 

...the `CreateRepositoryFromSnapshot` code path performs none of these checks. The code comment even flags this explicitly: [3](#0-2) 

Because raw `tar -xf` preserves symlinks found in the archive (it doesn't strip or validate them the way the Go-based extractor in `replicate.go` now does), an archive can contain a symlink entry (e.g. `objects/info/alternates -> /etc/passwd` or a relative `../../../../etc/passwd`-style link) that gets materialized inside the newly created repository directory. Subsequent read operations against that repository (e.g. `GetBlob`, `TreeEntry`, or any RPC that resolves paths/alternates within the repo) can then follow the symlink and disclose the contents of arbitrary files readable by the `git` user — the same "extract without removing symlinks, then load the symlinked content" pattern as the H1 report.

### Impact Explanation
If reachable with attacker-influenced input, this allows arbitrary local file disclosure (or write, depending on symlink direction and how the resulting repository is subsequently read/exported) on the Gitaly node, at the privilege level of the `git` process. This matches the accepted "extraction escape" / "cross-repository object access" class from the analog-mapping rules.

### Likelihood Explanation
`CreateRepositoryFromSnapshot` is tagged as a mutating RPC used during repository creation/replication flows (it calls `repoutil.Create` and records key creation in the WAL/migration state manager), and the request message directly exposes `HttpUrl`, `HttpAuth`, and `ResolvedAddress` fields to the caller. The comment in the code — "the received archive is trusted *a lot* … before pointing this RPC at endpoints not under our control, it should undergo a lot of hardening" — confirms the Gitaly maintainers are aware this path is not hardened against untrusted archive content. I was not able to fully verify from the available code index whether this RPC is restricted to a specific caller (e.g., only invoked internally by other Gitaly nodes during replication) or is reachable by a broader set of callers such as Rails/Workhorse-initiated imports/mirrors, since the corresponding RPC ACL/`op_type` annotation for `CreateRepositoryFromSnapshot` in `proto/repository.proto` and its callers in `internal/praefect/coordinator.go` were not fully retrievable within the index. This limits confidence in the precise reachability from an "ordinary user" action versus an admin/internal-only trust boundary.

### Recommendation
Replace the raw `tar -xf` invocation in `untar` (`internal/gitaly/service/repository/create_repository_from_snapshot.go`) with the same hardened, symlink-aware extraction logic already implemented in `extractTarToDirectory` (`internal/gitaly/service/repository/replicate.go`), which rejects absolute symlinks and validates that both symlink and hard-link targets resolve within the extraction boundary before creating them. Additionally, validate/allowlist the `HttpUrl` target and continue enforcing the existing DNS-rebinding protections in `newResolvedHTTPClient`.

### Proof of Concept
Not independently executable from static analysis alone; conceptually: 1) craft a tar archive containing a symlink entry, e.g. `Name: "objects/info/alternates", Typeflag: tar.TypeSymlink, Linkname: "/etc/passwd"` (or a relative equivalent), 2) host it at an HTTP endpoint reachable by the Gitaly node, 3) invoke `CreateRepositoryFromSnapshot` with `HttpUrl` pointing at that archive, 4) after repository creation, issue a read RPC (e.g. `GetBlob`/`TreeEntry`/`GetInfoAttributes`) against the created repository to observe whether the symlinked target's contents are disclosed. This mirrors the `TestExtractTarToDirectory_SymlinkValidation` test added for the hardened `replicate.go` path: [4](#0-3)

func (s *server) untar(ctx context.Context, path string, in *gitalypb.CreateRepositoryFromSnapshotRequest) error {
	req, err := http.NewRequestWithContext(ctx, "GET", in.GetHttpUrl(), nil)
	if err != nil {
		return structerr.NewInvalidArgument("Bad HTTP URL: %w", err)
	}

	client := httpClient
	if resolvedAddress := in.GetResolvedAddress(); resolvedAddress != "" {
		client, err = newResolvedHTTPClient(in.GetHttpUrl(), resolvedAddress)
		if err != nil {
			return structerr.NewInvalidArgument("creating resolved HTTP client: %w", err)
		}
	}

	if in.GetHttpAuth() != "" {
		req.Header.Set("Authorization", in.GetHttpAuth())
	}

	rsp, err := client.Do(req)
	if err != nil {
		return structerr.NewInternal("HTTP request failed: %w", err)
	}
	defer rsp.Body.Close()

	if rsp.StatusCode < http.StatusOK || rsp.StatusCode >= http.StatusMultipleChoices {
		return structerr.NewInternal("HTTP server: %s", rsp.Status)
	}

	cmd, err := command.New(ctx, s.logger, []string{"tar", "-C", path, "-xvf", "-"}, command.WithStdin(rsp.Body))
	if err != nil {
		return err
	}

	return cmd.Wait()
}
