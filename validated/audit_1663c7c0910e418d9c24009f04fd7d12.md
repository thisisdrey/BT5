### Title
Unauthenticated `StackerDBChunkInvData` push lets a peer claim `u32::MAX` slot versions and monopolize/steer chunk-fetch scheduling away from honest peers - ([File: stackslib/src/net/stackerdb/sync.rs])

### Summary
`StackerDBSync::add_pushed_chunk` stores an attacker-supplied `StackerDBChunkInvData` after only checking `slot_versions.len() != self.num_slots`, with no cryptographic binding between the claimed version and any actual signed chunk. Because `make_chunk_request_schedule` always prefers the *highest* claimed version per slot and *replaces* (not merges) the neighbor list when a higher version is seen, a single malicious replica advertising `u32::MAX` for every slot can unilaterally evict all honest peers from the fetch schedule for every slot, even though it never actually possesses data at that version.

### Finding Description
The broken invariant: the code assumes `remote_version` in an inventory message corresponds to a real, retrievable chunk, but nothing enforces this. `add_pushed_chunk` only checks length: [1](#0-0) 
and unconditionally inserts the attacker's inventory into `self.chunk_invs`.

`make_chunk_request_schedule` then builds `need_chunks` per slot by scanning all `chunk_invs` and keeping only the *highest* claimed `remote_version` for each slot index, clearing out any previously recorded (possibly honest, real) candidates whenever a higher version is seen: [2](#0-1) 

Since `u32::MAX` is trivially the maximum possible version, an attacker's forged inventory will always win this comparison for every slot, wholly displacing honest peers' entries from `need_chunks[i]` in `make_chunk_request_schedule` — meaning the round's `GetChunk` requests for that slot are sent only to the attacker. [3](#0-2) 

The attacker cannot satisfy the resulting `StackerDBGetChunkData` request with a valid signed chunk at that version (since none exists), so the request either times out, gets NACK'ed, or the returned chunk fails `validate_downloaded_chunk`/`network.validate_received_chunk` and the peer gets unpinned: [4](#0-3) 

The net effect within that sync round: the slot is never fetched from the honest peer that actually had the update, because the honest peer's entry was cleared out of `need_chunks` before requests were issued. This repeats every sync round since the state machine resets and re-requests inventories fresh (`StackerDBSyncState::Finished` → `reset` → `ConnectBegin`), and the attacker can re-send the same forged inventory on each round. [5](#0-4) 

Existing guards (length check in `add_pushed_chunk` and in `getchunksinv_try_finish`) only validate the shape of the message, not the truthfulness of the claimed versions, and `validate_downloaded_chunk` only runs after a chunk is actually fetched — too late to prevent the scheduling bias. [6](#0-5) 

### Impact Explanation
This is a bounded per-round scheduling denial-of-service against a specific victim's StackerDB sync for a specific contract: a connected, unprivileged StackerDB-replicating peer can, with a single unsigned message, prevent the victim from fetching real updates for any/all slots that round by claiming maximal fake versions, repeatable every sync cycle. It matches the "steering a node off the tip via false inventory"/"bounded compute DoS" High-severity category — it degrades StackerDB replica freshness/availability but does not forge state that gets written or served as canonical, nor does it crash the node.

### Likelihood Explanation
Preconditions are minimal and match the unprivileged-attacker model: the attacker just needs to be a peer the victim treats as a StackerDB replica for the target contract (reachable via ordinary P2P handshake/replication announcement) and reply to `StackerDBGetChunkInv`/push chunk-inv exchanges with a forged `StackerDBChunkInvData`. No secret, signature, or slot ownership is required to send this message since inventories are unsigned metadata. The attack is cheap (one message per sync round) and fully repeatable.

### Recommendation
Do not let inventory versions unconditionally override or evict candidates that are corroborated by other peers; require some cross-validation (e.g., only trust a claimed version once a threshold of independent peers agree, or once an actual chunk at that version has been fetched and validated) before excluding other candidates from `need_chunks`. At minimum, `make_chunk_request_schedule` should keep the previous honest candidates as fallback rather than fully replacing them, and `add_pushed_chunk`/`getchunksinv_try_finish` should track a peer's "fetch failure" history so this steering can be penalized/evicted (already partly present via `unpin_connected_replica`, but only after an actual failed chunk fetch, and only for that one peer — it doesn't restore honest peers dropped from the schedule that round).

### Proof of Concept
A Rust net test in `stackslib::net::stackerdb::tests::sync`:
1. Set up a victim `StackerDBSync` with two configured connected peers: `honest` (with a real, newer signed chunk at slot 0, version 5) and `attacker`.
2. Have `attacker` reply to `StackerDBGetChunkInv` with `StackerDBChunkInvData{slot_versions: vec![u32::MAX; num_slots], ...}` and `honest` reply with the true `slot_versions` (version 5 at slot 0).
3. Call `getchunksinv_try_finish` to ingest both invs into `self.chunk_invs` via `add_pushed_chunk`/direct insert path.
4. Call `make_chunk_request_schedule` and assert that the returned schedule for slot 0 contains **only** `attacker` in the neighbor list (honest peer excluded), i.e. `schedule.iter().find(|(req,_)| req.slot_id==0).unwrap().1 == vec![attacker_naddr]`.
5. Simulate `attacker` never responding / NACKing the subsequent `StackerDBGetChunk`, and assert that after `getchunks_try_finish`, `total_stored` for slot 0 did not increase even though `honest` held a valid newer chunk, demonstrating the steering/DoS.
