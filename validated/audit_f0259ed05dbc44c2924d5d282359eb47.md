### Title
Off-by-one in pre-liquidation health boundary allows liquidation of an exactly break-even (non-underwater) account - (File: `programs/marginfi/src/state/marginfi_account.rs`)

### Summary
The documentation states that a maintenance-health account becomes eligible for liquidation only when its health is **strictly negative** (`< 0`), while any account with health `>= 0` should be considered healthy and safe from liquidation. However, the actual boundary check in `check_pre_liquidation_condition_and_get_account_health` uses a strict `>` comparison to decide whether an account is "healthy," instead of the inclusive `>=` used everywhere else in the risk engine.

### Finding Description
`check_pre_liquidation_condition_and_get_account_health` computes `account_health = assets - liabs` and then determines whether the account is safe from liquidation with:
```rust
let healthy = account_health > I80F48::ZERO;
...
if healthy && !ignore_healthy {
    return err!(MarginfiError::HealthyAccount);
}
``` [1](#0-0) 

Because this uses `>` rather than `>=`, an account whose maintenance health is exactly `0` (assets == liabilities, i.e. break-even, not undercollateralized) is *not* flagged as healthy, and the `HealthyAccount` revert is skipped — liquidation is permitted to proceed.

This directly contradicts the project's own documented risk model:
> "Maintenance Health... If < 0, the account can be liquidated." [2](#0-1) 

By that definition, health `== 0` is *not* `< 0`, so the account should NOT be eligible for liquidation, yet the code's strict `>` boundary causes it to be treated as liquidatable. This is functionally the same bug class as the report: a boundary that should be inclusive is implemented as exclusive, causing incorrect behavior exactly at the boundary value. It is also internally inconsistent with the rest of the risk engine, which consistently uses the inclusive form for the "healthy" determination — e.g., `check_account_init_health` uses `let healthy = assets >= liabs;` [3](#0-2)  and `end_execute_order` in the order-execution flow uses `let is_healthy = account_health >= I80F48::ZERO;` [4](#0-3) .

### Impact Explanation
Any unprivileged user can call the permissionless `liquidate` instruction (`programs/marginfi/src/instructions/marginfi_account/liquidate.rs`) against a target account, and the pre-liquidation gate (`check_pre_liquidation_condition_and_get_account_health` [5](#0-4) ) will not block liquidation when the target's maintenance health is exactly `0`. This allows an unauthorized liquidator to seize collateral and impose liquidation fees/discounts on a user whose account is not actually undercollateralized by the protocol's own stated `< 0` standard — an unauthorized transfer of value from a technically-solvent user's account. Given liquidation applies fees (`LIQUIDATION_INSURANCE_FEE`, `LIQUIDATION_LIQUIDATOR_FEE`) to the liquidatee, this represents a real, if narrow, loss to the liquidatee.

### Likelihood Explanation
The condition requires an account's maintenance health to land at *exactly* zero, which is a narrow window in floating/fixed-point terms but is reachable through normal price movement, since I80F48 fixed-point values can legitimately equal zero (e.g., collateral and debt values crossing at a specific price tick, or via crafted borrow/withdraw amounts designed to land exactly at the boundary). A sophisticated liquidator (bot) could deliberately monitor for or even engineer (via price/oracle timing plus size selection) an account landing at this exact boundary to extract fees from an account that should be protected. Likelihood is Low-Medium given the precision required, but the check is reachable by any permissionless caller with no special access.

### Recommendation
Change the boundary check to be inclusive, consistent with the documented threshold and the rest of the risk engine:
```rust
let healthy = account_health >= I80F48::ZERO;
```
in `check_pre_liquidation_condition_and_get_account_health` (`programs/marginfi/src/state/marginfi_account.rs`, line 945), so that an account with health exactly zero is treated as healthy and protected from liquidation, matching the documented rule ("if `< 0`, can be liquidated").

### Proof of Concept
1. Construct a marginfi account with a deposit and a borrow such that, at current oracle prices, `assets_maint - liabs_maint == 0` exactly (achievable by choosing borrow/deposit amounts and a fixed-price oracle/mint, e.g. the `Fixed`/`FixedLow` test mints referenced in the test suite [6](#0-5) , to get deterministic fixed-point values).
2. Call the permissionless `liquidate` instruction against this account as any third-party liquidator.
3. Observe that `check_pre_liquidation_condition_and_get_account_health` computes `account_health == 0`, evaluates `healthy = 0 > 0 = false`, and does **not** return `MarginfiError::HealthyAccount` [1](#0-0) .
4. Liquidation proceeds, collateral is seized and liquidation fees are applied to the liquidatee even though the account's health is not `< 0`, contradicting the documented liquidation threshold.

Note: I was unable to find an existing unit/integration test in the repo that specifically exercises the exact `health == 0` boundary for liquidation eligibility, so I cannot confirm from test evidence whether this exact-zero case has been previously observed or intentionally accepted by the team; this assessment is based on direct code/documentation comparison.
