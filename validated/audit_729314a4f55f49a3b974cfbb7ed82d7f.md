### Title
Inflation of Pending Deposit Assets via Fee-on-Transfer Tokens - ([File: tare-io__tare-contracts/contracts/PortfolioVault.sol])

### Summary
The `PortfolioVault` contract does not account for tokens that charge a fee on transfer. When a user initiates an asynchronous deposit via `requestDeposit`, the vault records the requested `assets` amount as pending, but the actual balance increase in the vault is lower due to the transfer fee. This discrepancy causes the vault to over-allocate shares during the approval phase and corrupts the Net Asset Value (NAV) calculation by over-deducting pending assets from the idle balance.

### Finding Description
In `PortfolioVault.sol`, the `requestDeposit` function pulls `assets` from the `owner` using `assetToken.safeTransferFrom(owner, address(this), assets)`. It then increments `pendingDepositAssets[controller]` and the global `totalPendingDepositAssets` by the full `assets` amount. [1](#0-0) 

If `assetToken` is a fee-on-transfer token (like PAXG), the vault's actual balance increases by `assets - fee`. However, the contract continues to use the gross `assets` value for accounting:
1.  **NAV Corruption**: In `updateNav`, `totalPendingDepositAssets` is subtracted from the on-chain balance. Since this counter is inflated, the resulting `lastNav` is lower than the true value. [2](#0-1) 
2.  **Share Inflation**: In `approveDeposit`, shares are minted based on the gross `assets` amount. The depositor receives shares as if they contributed the full amount, effectively stealing value from existing shareholders. [3](#0-2) 

### Impact Explanation
1.  **Value Extraction**: Users can mint more shares than their actual asset contribution, leading to a direct loss for other vault participants.
2.  **NAV Corruption**: The vault's reported NAV will be lower than its actual economic value because it over-deducts "pending" funds that were never actually received.
3.  **Protocol Insolvency**: If enough fee-on-transfer deposits are approved, the `totalClaimableRedeemAssets` or other accounting counters may eventually mismatch the physical balance, potentially blocking redemptions.

### Likelihood Explanation
The likelihood is medium. While many institutional-grade assets like USDC do not currently have fees, the protocol's design (ERC-7540) suggests a generic vault architecture. Tokens like PAXG (Gold-backed) are often whitelisted in DeFi and do charge transfer fees. The protocol does not have an explicit whitelist that forbids such tokens in the current scope.

### Recommendation
Implement a "balance-before/balance-after" pattern in `requestDeposit` to record the actual amount of tokens received by the vault.

```solidity
function requestDeposit(uint256 assets, address controller, address owner) external returns (uint256 requestId) {
    // ... checks ...
    uint256 balanceBefore = assetToken.balanceOf(address(this));
    assetToken.safeTransferFrom(owner, address(this), assets);
    uint256 actualReceived = assetToken.balanceOf(address(this)) - balanceBefore;
    
    pendingDepositAssets[controller] += actualReceived;
    totalPendingDepositAssets += actualReceived;
    // ... emit event with actualReceived ...
}
```

### Proof of Concept
1.  Assume a Vault using a token with a 1% transfer fee.
2.  User A calls `requestDeposit(1000, userA, userA)`.
3.  The vault receives 990 tokens, but `pendingDepositAssets[userA]` is set to 1000.
4.  `totalPendingDepositAssets` is incremented by 1000.
5.  `updateNav` is called. The `lastNav` is calculated as `balance (990) - totalPendingDepositAssets (1000) + loansValue`. The NAV is undervalued by 10 tokens.
6.  `approveDeposit(userA, 1000)` is called. User A receives shares calculated on 1000 tokens, despite only contributing 990 tokens to the vault's actual balance.
