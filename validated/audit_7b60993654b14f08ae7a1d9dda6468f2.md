### Title
`getReward()`/`RewardBalance` precompile can report a nonzero withdrawable reward for guard-representative addresses that can never actually be withdrawn - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
This mirrors the Sablier `refundableAmountOf()` bug class: a public "amount that is available" query function omits a status/eligibility check that the corresponding state-changing function enforces, so external callers (including other on-chain contracts and off-chain integrations such as lending/DeFi protocols) can be told a nonzero balance exists when the real withdrawal path will always revert/return zero for that account.

### Finding Description
`MortgageService.queryReward(address)` computes and returns the witness voting reward available to `address` purely from cycle/vote/allowance bookkeeping [1](#0-0) . It never checks whether the address is a "guard representative" (genesis witness).

By contrast, the actual on-chain withdrawal path, `WithdrawBalanceActuator.validate()`, explicitly forbids guard representatives from withdrawing any reward/allowance: [2](#0-1) 
and the TVM-native equivalent `WithdrawRewardProcessor.validate()` enforces the identical guard-representative restriction before any reward can be moved via a smart-contract call: [3](#0-2) 

The `queryReward` value is exposed through multiple externally reachable, unprivileged read paths that never apply this same restriction:
- The HTTP API `GetRewardServlet` returns `manager.getMortgageService().queryReward(address)` directly to any anonymous API caller for any address, including genesis witnesses: [4](#0-3) 
- The TVM `RewardBalance` precompile, callable by any smart contract during a normal transaction, calls the analogous `VoteRewardUtil.queryReward()` (same computation, same missing guard-representative check) and returns the raw value to the calling contract: [5](#0-4) , [6](#0-5) 

Exactly like the Sablier report — where `refundableAmountOf()` returned a positive amount for a stream that could never actually be refunded because `isCancelable` was false — here `queryReward`/`RewardBalance` returns a positive "available reward" for an address that can never actually withdraw it, because the corresponding withdrawal actuator/processor enforces a guard-representative restriction that the query path does not replicate.

### Impact Explanation
Any smart contract or off-chain service (e.g., a lending/collateral protocol) that uses the `RewardBalance` precompile or the `/getreward` HTTP API to determine an account's redeemable/available balance for purposes such as collateral valuation, liquidation eligibility, or accounting will be misled for the small set of guard-representative addresses: it will see a nonzero, seemingly-withdrawable reward that in reality can never be extracted through `WithdrawBalanceActuator` or `WithdrawRewardProcessor`. This can lead to over-valuation of collateral/backing that is fundamentally unbacked (mirroring the disclosed risk in the original report: unbacked balance / incorrect liquidation assumptions). This is a data-integrity/oracle-style flaw reachable by any unprivileged transaction or API caller reading state — no privileged role is required to trigger it.

### Likelihood Explanation
The condition (address being one of the fixed genesis "guard representative" witnesses) is narrow and does not change over time, so the practical blast radius is limited to interactions involving those specific addresses. However, the query paths (`RewardBalance` precompile, HTTP `/getreward`) are trivially and permissionlessly reachable by any contract call or REST client, and there is no validation or filtering preventing a caller from querying a guard-representative address and receiving a misleading nonzero figure. Likelihood of triggering the discrepancy is high (any external caller can do it at will); the downside is limited to how heavily any given third-party integration relies on this specific query result for guard-representative addresses.

### Recommendation
Align the read paths with the write paths: in `VoteRewardUtil.queryReward()` and `MortgageService.queryReward()`, replicate the guard-representative check that `WithdrawBalanceActuator.validate()` / `WithdrawRewardProcessor.validate()` perform, and return `0` for such addresses (or otherwise clearly signal non-withdrawability), so that the `RewardBalance` precompile and the `/getreward` HTTP endpoint never report a reward amount that cannot actually be redeemed.

### Proof of Concept
1. Identify a genesis "guard representative" witness address (`CommonParameter.getInstance().getGenesisBlock().getWitnesses()`), which accrues voting rewards through normal `payReward`/`adjustAllowance` flow in `MortgageService`.
2. Call the HTTP endpoint `GET /getreward?address=<guard-representative-address>` — `GetRewardServlet` returns a nonzero `reward` value if that address has accrued allowance/reward.
3. Alternatively, deploy or call a contract that invokes the `RewardBalance` precompile with the guard-representative address as input; observe a nonzero return value.
4. Attempt to withdraw that reward on behalf of the guard-representative address via `WithdrawBalanceContract` (or a contract calling `withdrawReward()`), and observe `ContractValidateException`: "... is a guard representative and is not allowed to withdraw Balance" from `WithdrawBalanceActuator.validate()` / `WithdrawRewardProcessor.validate()`, confirming the queried amount is not actually redeemable, matching the reported bug class exactly.

  public long queryReward(byte[] address) {
    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return 0;
    }

    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (accountCapsule == null) {
      return 0;
    }
    if (beginCycle > currentCycle) {
      return accountCapsule.getAllowance();
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      return reward + accountCapsule.getAllowance();
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
    }
    return reward + accountCapsule.getAllowance();
  }

  public void validate(WithdrawRewardParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();

    boolean isGP = CommonParameter.getInstance()
        .getGenesisBlock().getWitnesses().stream().anyMatch(witness ->
            Arrays.equals(ownerAddress, witness.getAddress()));
    if (isGP) {
      throw new ContractValidateException(
          ACCOUNT_EXCEPTION_STR + StringUtil.encode58Check(ownerAddress)
              + "] is a guard representative and is not allowed to withdraw Balance");
    }
  }
