### Title
Wallet Contract pays relayer refund before the address-registrar check resolves, and does not advance the nonce on the resulting faulty-relayer outcome, enabling repeated fee drain via replay - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs` / `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
In `inner_rlp_execute`, the relayer fee refund for an `EOABaseTokenTransfer`/`ERC20Transfer` is dispatched unconditionally as soon as `parse_rlp_tx_to_action` succeeds, even when the transaction kind carries `address_check: Some(_)` (meaning nonce advancement is deliberately deferred to `address_check_callback`). If the registrar lookup later determines the target was actually a registered account (a "faulty relayer" outcome), the nonce is intentionally **not** advanced, but the fee has already been paid out in the same top-level call. This breaks the invariant that relayer compensation only occurs alongside a nonce advance, and it lets the same signed payload be resubmitted repeatedly to harvest the fee refund every time.

### Finding Description
`decode_b64` (`runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs:195`) is reached via `parse_rlp_tx_to_action` (`internal.rs:43`), called from `inner_rlp_execute` (`lib.rs:347`) on every `rlp_execute` invocation, including a `Transfer` action to a 64-hex/`0x`-prefixed implicit account whose emulated Ethereum payload is parsed as a base-token transfer.

Root cause is in `inner_rlp_execute` (`lib.rs:330-410`):
- Nonce advance is conditionally skipped only for `EOABaseTokenTransfer { address_check: Some(_), .. }` (`lib.rs:358-365`), explicitly to allow the registrar to be checked asynchronously before committing state.
- The very next block (`lib.rs:374-385`) matches on `EOABaseTokenTransfer { fee, .. } | ERC20Transfer { fee, .. }` **without checking `address_check`**, and if `fee` is non-zero and `predecessor_account_id != current_account_id`, it immediately issues `env::promise_batch_create` + `env::promise_batch_action_transfer` to pay the predecessor (relayer) the fee.
- This transfer receipt is queued regardless of what the function ultimately returns, because NEAR promise-batch actions are dispatched independent of the function's return value.
- Later, in `address_check_callback` (`lib.rs:134-192`), if the registrar reports the target address IS a named/registered account (`maybe_account_id.is_some()`), the code explicitly states "we intentionally do not increment the nonce" (`lib.rs:162-164`) and either bans the relayer (only if `signer_account_id == current_account_id`, i.e., an access-key relayer) or, for a plain FunctionCall-based relayer (`predecessor_account_id != current_account_id`), simply returns a failed `ExecuteResponse` (`lib.rs:168-172`) — with no compensating clawback of the fee already sent.

Consequently: an attacker acting as an unprivileged relayer (any funded NEAR account calling `rlp_execute` as a `FunctionCall`, not via an access key) that possesses a validly user-signed emulated base-token-transfer/ERC-20-transfer transaction whose `to` address happens to also be a registered account in the address registrar, and that deliberately (or opportunistically) sets `target` to the eth-implicit `0x...` form instead of the registered account name, will:
1. Trigger the immediate, unconditional fee-refund transfer to itself (the predecessor).
2. Have the wallet nonce left unchanged because the outcome is classified as a faulty-relayer/invalid-target case.
3. Be able to resubmit the exact same signed base64 payload again — `decode_b64` will decode it identically, `validate_tx_relayer_data` will accept it because `expected_nonce` never advanced — repeating steps 1–2 indefinitely.

No existing check stops this: `has_in_flight_tx` only prevents concurrent in-flight transactions, not sequential replay across separate top-level calls; nonce validation in `validate_tx_relayer_data` (`internal.rs:352-359`) only rejects a nonce mismatch, and here the nonce never changes, so it always matches.

### Impact Explanation
This allows repeated, unbounded extraction of `fee`-denominated NEAR from the ETH-implicit wallet's balance by any account that can obtain a legitimately user-signed relay payload (e.g. a malicious/rogue relayer service, or an observer of a public relayer mempool/broadcast channel) whose intended transfer destination happens to resolve to a registered account name. Each replay drains `fee` yoctoNEAR from the victim wallet without ever completing the user's intended transfer and without the wallet's protocol nonce advancing — a direct, repeatable theft of user funds via the wallet-contract/meta-transaction relayer-compensation path, matching "High - Direct theft of user funds via access-key/meta-transaction/wallet-contract authorization bypass."

### Likelihood Explanation
- The attacker needs a validly signed emulated-transfer payload with non-zero `fee` and a `to` address that is also registered in the address registrar contract; this is a realistic scenario since users may transact with addresses belonging to accounts that are (or later become) registered.
- The attacker does not need the wallet owner's private key — only possession of a signed relay payload (which is, by design, broadcastable to any relayer) and the ability to call `rlp_execute` as an ordinary FunctionCall predecessor (not via an access key).
- Cost to the attacker is only gas for repeated calls; each call yields a `fee`-sized profit, so it is economically repeatable until the wallet balance or `fee` economics make it unprofitable.
- The bug is deterministic and does not depend on race conditions, since `has_in_flight_tx` is reset (`false`) at the start of each new callback/response cycle, allowing sequential resubmission.

### Recommendation
Do not dispatch the relayer fee-refund promise until the outcome of the address-registrar check (and any other deferred validation) is known. Specifically:
- Move the fee-refund transfer for `EOABaseTokenTransfer`/`ERC20Transfer` out of the synchronous branch in `inner_rlp_execute` when `address_check: Some(_)`, and instead only pay it from within `address_check_callback` in the `None` (honest-relayer) branch, at the same point the nonce is incremented.
- Alternatively, gate the fee payment on nonce advancement so that both operations occur atomically only when `maybe_account_id.is_none()`.

### Proof of Concept
Unit/integration test plan (extends `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/emulation.rs` / `relayer.rs`):
1. Deploy the wallet contract for an eth-implicit account with a funded balance; deploy/mock an address-registrar contract that returns `Some(some_account_id)` for a chosen target address `addr_X`.
2. Craft and sign (with the wallet owner's secp256k1 key) a `Transaction2930` representing a base-token transfer to `addr_X` with `gas_price/gas_limit` set so `fee > 0`, and with `nonce = 0` (current wallet nonce).
3. As an ordinary funded relayer account (not holding an access key on the wallet), call `rlp_execute(target = "0x<addr_X_hex><suffix>", tx_bytes_b64)` via a plain `FunctionCall`.
4. Assert: `ExecuteResponse.success == false` (invalid-target/faulty-relayer error), the relayer's balance increased by ~`fee`, the intended recipient's balance did NOT change, and `get_nonce()` is still `0`.
5. Resubmit the identical `tx_bytes_b64`/`target` a second time from the same or a different relayer account.
6. Assert the relayer is paid `fee` again, `get_nonce()` remains `0`, and repeat N times to show cumulative drain of the wallet's balance by `N * fee`, confirming the invariant "relayer compensation happens only alongside a nonce advance" is violated and the drain is repeatable.
