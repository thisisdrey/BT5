### Title
Wallet Contract pays relayer fee before validating success of the corresponding transfer — analog of unchecked-transfer/CEI violation ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The eth-implicit account "Wallet Contract" (`inner_rlp_execute`) unconditionally dispatches a relayer-fee `Transfer` promise *before* the underlying emulated action (base-token transfer or ERC-20 transfer) has executed or been confirmed to succeed. The fee promise is created as an independent, unchained promise batch, so it is not gated on the outcome of the action it is meant to compensate. This mirrors the `VaultV3` bug class: a value-moving effect (the relayer fee payout) is performed without checking/waiting on the success of the paired operation, breaking Checks-Effects-Interactions and letting an unprivileged, potentially malicious relayer collect payment for work it does not actually deliver.

### Finding Description
In `inner_rlp_execute`, once a transaction is parsed as `EOABaseTokenTransfer` or `ERC20Transfer` with a non-zero `fee`, the contract immediately creates and dispatches a *separate* promise batch that transfers the fee to the relayer (`context.predecessor_account_id`): [1](#0-0) 

This fee-transfer promise is created via `env::promise_batch_create` and is not `.then()`-chained to (nor conditioned on) the promise that actually performs the user's intended action — that promise is constructed afterward, separately, in the `match transaction_kind` block: [2](#0-1) 

By contrast, the contract *does* correctly gate the `caller_deposit` refund on the actual promise result in `rlp_execute_callback`, using `env::promise_result(0)` to check `PromiseResult::Failed` vs `PromiseResult::Successful`: [3](#0-2) 

This shows the codebase already knows the correct pattern (check result before paying out) elsewhere, but the relayer fee path skips it entirely — the fee leaves the account regardless of whether the emulated action later fails at any of its steps (e.g. `nep_141_storage_balance_callback` failure, `ft_transfer`/`storage_deposit` failure, or the base-token `Transfer` failing due to a bad target).

### Impact Explanation
Any relayer submitting a user's signed Ethereum-emulated transaction to this wallet contract is compensated up front via an unconditional transfer, independent of whether the wrapped action (ERC-20 transfer or base-token transfer) succeeds. Because the nonce is incremented before dispatch for these paths (see `inner_rlp_execute`, lines 358–365), a single signed user transaction can only be replayed once, but within that one execution a relayer can cause (or simply experience) the wrapped action's failure — e.g. by supplying insufficient gas to the follow-on cross-contract calls, or racing conditions on the destination NEP-141 contract — while still keeping the fee. This is a concrete loss of user funds (the fee amount) with no corresponding service performed, granted to an unprivileged actor (the relayer) purely because the contract does not enforce Checks-Effects-Interactions between the fee payment and the action outcome.

### Likelihood Explanation
This path is reachable by any user of an ETH-implicit account using the standard NEP-518 Wallet Contract relaying flow with a non-zero fee (`EOABaseTokenTransfer` or `ERC20Transfer`), which is the documented, intended way to use relayers with these accounts. No special privileges are required by the relayer — this is exactly the "unprivileged signer" / meta-transaction-style surface explicitly in scope. The trigger condition (relayer submits transaction, wrapped action later fails) requires no exotic setup beyond a relayer that either misconfigures gas or acts adversarially, which is realistic given relayers are explicitly untrusted per the code's own comments.

### Recommendation
Follow Checks-Effects-Interactions: create the fee-transfer promise as part of the same promise chain as the wrapped action (e.g., `.then()`-scheduled after the wrapped action succeeds, or included only in the success branch of `rlp_execute_callback`/`nep_141_storage_balance_callback`/`address_check_callback`), so the relayer is paid only if `env::promise_result` for the wrapped action reports `PromiseResult::Successful`. This mirrors the fix already applied to the `caller_deposit` refund logic in `rlp_execute_callback`.

### Proof of Concept
1. User signs an Ethereum-style ERC-20 transfer transaction through their eth-implicit Wallet Contract account, specifying a non-zero `fee` for the relayer, per `EthEmulationKind::ERC20Transfer`.
2. Relayer submits `rlp_execute` with this transaction. `inner_rlp_execute` immediately fires the fee `Transfer` promise to the relayer at [4](#0-3) .
3. Separately, the contract schedules `storage_balance_of` → (`storage_deposit` +) `ft_transfer` → `rlp_execute_callback`. The relayer supplies (or the token contract enforces) conditions causing this second promise chain to fail (e.g., insufficient attached gas for `ft_transfer`, or a token contract that reverts).
4. `rlp_execute_callback` reports `success: false`, but the fee promise from step 2 already executed and is not rolled back or conditioned on step 3's outcome.
5. Net effect: the relayer receives the fee NEAR tokens, while the user's intended ERC-20 transfer never occurs — a real loss of user funds tied directly to an unchecked, unconditional value transfer, consistent with the reported bug class.

            let ext = WalletContract::ext(current_account_id).with_static_gas(callback_gas);
            let address_registrar = {
                let account_id = ADDRESS_REGISTRAR_ACCOUNT_ID
                    .trim()
                    .parse()
                    .unwrap_or_else(|_| env::panic_str("Invalid address registrar"));
                ext_registrar::ext(account_id).with_static_gas(REGISTRAR_LOOKUP_GAS)
            };
            let address = format!("0x{}", hex::encode(address));
            address_registrar.lookup(address).then(ext.address_check_callback(
                target,
                action,
                caller_deposit,
            ))
        }
        TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { receiver_id, .. }) => {
            // In the case of the emulated ERC-20 transfer, the receiving account
            // might not be registered with the NEP-141 contract (per the NEP-145)
            // storage standard. Therefore we must create a multi-step promise where
            // first we check if the receiver is registered and then if not call
            // `storage_deposit` in addition to `ft_transfer`.
            let token_id = target;
            let callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas());
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(callback_gas);
            let storage_balance_args =
                format!(r#"{{"account_id": "{}"}}"#, receiver_id.as_str()).into_bytes();
            Promise::new(token_id.clone())
                .function_call(
                    "storage_balance_of".into(),
                    storage_balance_args,
                    NearToken::from_yoctonear(0),
                    NEP_141_STORAGE_BALANCE_OF_GAS,
                )
                .then(ext.nep_141_storage_balance_callback(
                    token_id,
                    receiver_id,
                    action,
                    caller_deposit,
                ))
        }
        TransactionKind::EthEmulation(EthEmulationKind::SelfBaseTokenTransfer) => {
            // Base token transfers to self are no-ops on Near, so we do not need to
            // schedule an additional call. We can simply go straight to `rlp_execute_callback`.
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            ext.rlp_execute_callback(caller_deposit)
        }
        _ => {
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            action_to_promise(target, action)?.then(ext.rlp_execute_callback(caller_deposit))
        }
    };
