### Title
Unbounded GetFileAttributesRequest.paths causes CPU/goroutine exhaustion via unbounded CheckAttrCmd.Check loop - (File: internal/gitaly/service/repository/file_attributes.go)

### Summary
`GetFileAttributes` iterates over every entry in the attacker-controlled `GetFileAttributesRequest.paths` field and calls `CheckAttrCmd.Check` once per path with no upper bound on the number of paths and no periodic context-cancellation check, so an unprivileged caller can submit a request with millions of paths to force the RPC handler and its underlying `git check-attr(1)` subprocess to run for a very long time, tying up a Gitaly worker thread and the subprocess.

### Finding Description
`GetFileAttributes` at [1](#0-0)  loops over `in.GetPaths()` and calls `checkAttrCmd.Check(path)` for every element, with no limit on `len(in.GetPaths())` enforced in `validateGetFileAttributesRequest`, which only checks that the paths list is non-empty [2](#0-1) . Each call to `Check` writes the path to the long-lived `git check-attr --stdin -z` process's stdin, flushes, and blocks reading `count` NUL-delimited fields from stdout before returning [3](#0-2) . Neither `Check` nor the calling loop checks `ctx.Done()`/`ctx.Err()` between iterations, so cancellation of the gRPC request does not interrupt an in-progress path-by-path loop until the current `Check()` call completes and the loop condition is re-evaluated (and even then, no explicit check exists). There is no batching, page size, or streaming; the entire request must complete in a single unary RPC response. Since `paths` is a repeated proto string field, there is no protocol-level size cap other than the general gRPC max message size (default 4MB in most gRPC configs, but Gitaly's proto/grpc stack limits are not enforced here at the field-count level) — a caller can pack a very large number of short paths within a max message size and multiply the effect further via response size for matching attributes, or simply supply many paths to invoke `Check()` millions of times.

### Impact Explanation
This is a DoS of a single RPC handler and its associated subprocess: an unprivileged, low-cost request can force Gitaly to spend a long time executing `git check-attr` operations, consuming CPU and holding a `git-check-attr` subprocess and its goroutine open for the duration. This matches GitLab's DoS impact class for Gitaly RPC handlers (excessive resource consumption per request without hard bounds on attacker-supplied repeated fields), though it is a single-request/limited-concurrency degradation rather than full server compromise or crash.

### Likelihood Explanation
Any authenticated GitLab user with fetch access to a repository (own project, fork, or import) can issue a `GetFileAttributesRequest` with an arbitrarily large `paths` array up to gRPC message size limits; no special repository content (like a huge `.gitattributes`) is even required — just a large `paths` list. This is trivially and repeatably reproducible by any caller of the RPC and does not require privileged roles, secrets, or non-default configuration.

### Recommendation
Enforce a reasonable upper bound on `len(in.GetPaths())` in `validateGetFileAttributesRequest` (e.g. reject if it exceeds a fixed maximum, or require chunked/streaming RPC usage for large path sets), and add periodic `ctx.Err()` checks inside the `for _, path := range in.GetPaths()` loop in `GetFileAttributes` (and/or inside `CheckAttrCmd.Check`) so that context cancellation aborts long-running iteration promptly instead of running to completion.

### Proof of Concept
```go
func TestGetFileAttributes_LargePathsDoS(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, repoProto, repoPath := setupRepositoryService(t) // existing test helper
    client := newRepositoryClient(t, cfg)

    gittest.WriteFile(t, cfg, repoPath, ".gitattributes", []byte("*.md foo\n"))
    commitID := gittest.WriteCommit(t, cfg, repoPath, gittest.WithMessage("attrs"))

    // Build a very large paths slice (e.g. 5,000,000 short entries within
    // gRPC max message size) to simulate the attacker payload.
    paths := make([]string, 5_000_000)
    for i := range paths {
        paths[i] = "a.md"
    }

    start := time.Now()
    resp, err := client.GetFileAttributes(ctx, &gitalypb.GetFileAttributesRequest{
        Repository: repoProto,
        Revision:   []byte(commitID),
        Attributes: []string{"foo"},
        Paths:      paths,
    })
    elapsed := time.Since(start)

    // Expect the handler to take an excessive amount of time,
    // demonstrating unbounded per-path processing with no size cap
    // or cancellation responsiveness.
    require.NoError(t, err)
    require.NotNil(t, resp)
    require.Greater(t, elapsed, 10*time.Second)
}
```
Cancelling the context mid-request (e.g. via `context.WithTimeout`) shows the handler does not return promptly, since neither `GetFileAttributes` nor `CheckAttrCmd.Check` checks `ctx.Err()` during the loop.

```go
func (c CheckAttrCmd) Check(path string) (Attributes, error) {
	if strings.Contains(path, "\000") {
		return nil, fmt.Errorf("path with NUL byte not allowed")
	}

	c.m.Lock()
	defer c.m.Unlock()

	if _, err := c.stdin.WriteString(path + "\000"); err != nil {
		return nil, fmt.Errorf("write path: %w", err)
	}
	if err := c.stdin.Flush(); err != nil {
		return nil, fmt.Errorf("flush: %w", err)
	}

	attrs := Attributes{}
	buf := make([]string, 0, 3)

	// Using git-check-attr(1) with -z will return data in the format:
	// <path> NUL <attribute> NUL <info> NUL ...
	for i := 0; i < c.count; {
		word, err := c.stdout.ReadBytes('\000')
		if err != nil {
			return nil, fmt.Errorf("read line: %w", err)
		}

		buf = append(buf, string(bytes.TrimSuffix(word, []byte{0})))

		if len(buf) < 3 {
			continue // Keep going until we have 3 words
		}

		if buf[0] != path {
			return nil, fmt.Errorf("wrong path name detected, expected %q, got %q", path, buf[0])
		}
		if buf[2] != Unspecified {
			attrs = append(attrs, Attribute{Name: buf[1], State: buf[2]})
		}

		i++
		buf = buf[:0]
	}

	return attrs, nil
}
```
