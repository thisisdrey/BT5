## Finding

Based on my review, this maps most directly to a state-lock/permanent-freeze bug in the `near-wallet-contract` (eth-implicit account wallet contract), which is explicitly in scope per the rules.

### Title
Fixed-gas callback can be griefed into out-of-gas, permanently stuck `has_in_flight_tx` lock — ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The `WalletContract` (the eth-implicit account's associated contract) uses a boolean `has_in_flight_tx` as a re-entrancy/ordering lock: `rlp_execute` refuses any new transaction while a prior one's promise chain is unresolved, and only the `#[private]` callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`) reset it to `false`. Each callback is scheduled with a small, hardcoded static gas budget (`RLP_EXECUTE_CALLBACK_GAS = Gas::from_tgas(5)`), and the flag-reset (`self.has_in_flight_tx = false;`) is the first statement in every callback. [1](#0-0) [2](#0-1) 

### Finding Description
NEAR commits or rolls back *all* state changes made by a function-call receipt atomically: if the receipt errors out for any reason — including running out of allocated gas — every mutation performed during that execution, including an early `self.has_in_flight_tx = false;`, is discarded.

All three callbacks reset `has_in_flight_tx = false` as their first line, so under normal successful/failed execution the lock is always released: [3](#0-2) [4](#0-3) 

However, each callback is invoked with a fixed, small static gas allowance (`RLP_EXECUTE_CALLBACK_GAS`, 5 TGas), and part of that budget is spent *inside* the callback reading the prior promise's result via `env::promise_result(0)`: [5](#0-4) [6](#0-5) 

The size (and therefore the gas cost) of that returned value is controlled by whatever contract the user's decoded Ethereum transaction targets (`action_to_promise(target, action)` in `inner_rlp_execute`/`address_check_callback`). If that target contract returns an unusually large successful payload, reading/copying it inside the fixed-gas callback can exceed the allotted 5 TGas, causing the callback receipt to fail with an out-of-gas `FunctionCallError`. Because the flag reset is part of that same failed receipt, `has_in_flight_tx` is never actually flipped back to `false` — it stays permanently `true` on the persisted `Account` state. Since `rlp_execute` unconditionally rejects any further calls while `has_in_flight_tx` is `true` and nothing else in the contract can clear it, the wallet becomes permanently unable to process any future transaction, effectively freezing the account and any funds it can only move via `rlp_execute`. [7](#0-6) 

This is analogous to the reported bug class: an unprivileged party can, through a single crafted interaction, flip the contract into a state that can never legitimately be reversed, permanently disabling its core function (executing further transactions on behalf of the wallet owner).

### Impact Explanation
If successfully triggered, the affected eth-implicit wallet account can never again submit a transaction through `rlp_execute`, since the guard at the top of that function always short-circuits when `has_in_flight_tx == true` and there is no other method exposed to clear it. Any assets held by / accessible only through that wallet contract become permanently unusable — a freezing-of-funds impact for that account.

### Likelihood Explanation
This requires: (1) the user's decoded transaction to target a contract that is malicious or can be tricked into returning an oversized success payload, and (2) that payload's size to be large enough that copying/serializing it inside the fixed 5 TGas callback budget exceeds the gas limit. This is plausible whenever a user interacts with an untrusted or adversarial contract (e.g., an attacker-deployed dApp) as the `target` of an RLP-encoded transaction, but it is not attacker-controllable in the way the original report's scenario is (there the attacker unilaterally forces the outcome against any depositor; here the account owner has to route a transaction to an adversarial contract). Likelihood is therefore moderate rather than trivially reachable by anyone against anyone.

### Recommendation
- Avoid making the lock-clearing state mutation depend on the same limited-gas execution that also processes attacker-influenced data (e.g., clear `has_in_flight_tx` via a lower-gas-cost path that doesn't depend on the size of `promise_result`, or bound/limit the amount of promise-result data copied within the callback).
- Increase headroom in `RLP_EXECUTE_CALLBACK_GAS` or make it a function of the potential result size, and add defensive gas-limit checks.
- Provide a privileged/administrative or timeout-based recovery mechanism to clear `has_in_flight_tx` if a callback is ever detected to have failed to run to completion (similar to the report's suggestion to allow reversing a stuck lock).

### Proof of Concept
Conceptual reproduction (would need to be validated in a NEAR sandbox/testnet environment):
1. Deploy a "target" contract whose method, when called via the wallet's decoded Ethereum action, returns a very large byte array as its successful return value.
2. Sign and submit an RLP-encoded Ethereum transaction (via `rlp_execute`) from the eth-implicit wallet targeting that contract's method.
3. `inner_rlp_execute` sets `has_in_flight_tx = true` and chains `action_to_promise(...).then(rlp_execute_callback(...))` with `RLP_EXECUTE_CALLBACK_GAS` (5 TGas) as seen at: [8](#0-7) 
4. When the target's oversized result is read inside `rlp_execute_callback` via `env::promise_result(0)`, the callback exhausts its 5 TGas budget and fails.
5. Because the callback's receipt fails, `self.has_in_flight_tx = false;` (its first statement) is rolled back along with the rest of its state changes, leaving `has_in_flight_tx == true` permanently.
6. All subsequent calls to `rlp_execute` are rejected at the guard check, permanently freezing the wallet.
