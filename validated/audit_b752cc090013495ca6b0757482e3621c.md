## Analog Found: Deterministic contract address can be pre-empted before `CreateSmartContract` execution

### Title
Deterministic smart-contract address computed from pending transaction data can be frontrun to block contract deployment - (`actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
`VMActuator.create()` derives the address of a to-be-deployed smart contract deterministically from the pending, not-yet-executed `CreateSmartContract` transaction, then only proceeds if no account already exists at that address. An unprivileged observer of the pending transaction pool can compute this exact address ahead of time and race a simple transfer to occupy it first, causing the legitimate deployer's transaction to revert. This mirrors the reported Gitcoin issue where a deterministic initialization target (the `roundAddress`) can be seized by a third party before the intended actor acts on it.

### Finding Description
When a `CreateSmartContract` transaction is executed, the new contract's address is computed with: [1](#0-0) 
`generateContractAddress` hashes the transaction's raw-data hash (`txRawDataHash`, i.e. the transaction ID) together with the `ownerAddress`. Both values are fully known the moment the sender constructs and signs (or even just broadcasts) the transaction — they do not depend on any chain state that changes at execution time, and the raw transaction is visible to anyone monitoring the mempool.

`VMActuator.create()` then checks whether an account already exists at this computed address and aborts if so: [2](#0-1) 

Because `rootRepository.getAccount(contractAddress) != null` only checks for *any* existing account (not specifically an existing contract), a plain TRX transfer to that address — which implicitly creates a `Normal` account in java-tron — is sufficient to make this check fail. An attacker observing a pending `CreateSmartContract` transaction in the mempool can:
1. Compute `contractAddress = sha3omit12(txRawDataHash || ownerAddress)` from the publicly visible pending transaction.
2. Broadcast a `TransferContract` sending a trivial amount of TRX to that address with higher fee/priority so it lands in an earlier block.
3. Cause the victim's subsequent `CreateSmartContract` transaction to fail validation with `"Trying to create a contract with existing contract address..."`, wasting the victim's fee and forcing a redeploy — exactly analogous to the "wasted gas fees, forced redeploy" impact described in the original report, where a naive initialization address could be raced and claimed by an unrelated actor.

This is distinct from the intentional, documented CREATE2 collision handling (`Program.createContractImpl`, `actuator/src/main/java/org/tron/core/vm/program/Program.java:836-882`), which is bytecode-level and already anticipated/tested (`Create2Test.java`); the plain `CREATE` path in `VMActuator` has no such consideration and can be blocked by an ordinary account-funding transaction from any address.

### Impact Explanation
Any unprivileged transaction broadcaster can deny a specific, targeted smart-contract deployment by any other user, causing that user's fee to be spent for a failed transaction and forcing them to resubmit (with a new, unpredictable transaction ID/address) as many times as the attacker is willing to grief. This is a denial-of-service against a specific transaction sender's ability to deploy a contract, mirroring the Medium-severity classification of the original report (front-runnable, deterministic initialization target causing wasted fees/forced retries).

### Likelihood Explanation
Exploitation requires only observing the mempool for pending `CreateSmartContract` transactions (or transactions from a targeted address) and broadcasting a cheap TRX transfer with sufficient fee/bandwidth priority to land first — no special privileges, staking, or witness status are needed, making this reachable by any ordinary account.

### Recommendation
Do not rely solely on "account does not yet exist" as the collision guard for `CREATE`. Either bind contract-address collision handling to contract-specific state (as already done for `CREATE2`'s `isContractExist` check) so that a plain funded account does not block deployment, or make the deployed contract absorb/merge with a pre-existing non-contract account safely (as is already done in the non-Constantinople branch of `Program.createContractImpl`, which preserves the old balance rather than rejecting the operation).

### Proof of Concept
1. Victim broadcasts a `CreateSmartContract` transaction; its transaction ID (`txRawDataHash`) and `ownerAddress` are visible in the mempool.
2. Attacker computes `contractAddress = WalletUtil.generateContractAddress` equivalent off-chain using the same inputs.
3. Attacker broadcasts a `TransferContract` of 1 sun to `contractAddress` with a competitive fee so it is included in an earlier block, causing `AccountCapsule` for `contractAddress` to be implicitly created.
4. When the victim's `CreateSmartContract` transaction executes, `VMActuator.create()` (`actuator/src/main/java/org/tron/core/actuator/VMActuator.java:360-364`) finds `rootRepository.getAccount(contractAddress) != null` and throws `ContractValidateException`, failing the deployment and burning the victim's fee.

```java
  public static byte[] generateContractAddress(Transaction trx) {

    CreateSmartContract contract = ContractCapsule.getSmartContractFromTransaction(trx);
    byte[] ownerAddress = contract.getOwnerAddress().toByteArray();
    TransactionCapsule trxCap = new TransactionCapsule(trx);
    byte[] txRawDataHash = trxCap.getTransactionId().getBytes();

    byte[] combined = new byte[txRawDataHash.length + ownerAddress.length];
    System.arraycopy(txRawDataHash, 0, combined, 0, txRawDataHash.length);
    System.arraycopy(ownerAddress, 0, combined, txRawDataHash.length, ownerAddress.length);

    return Hash.sha3omit12(combined);

  }
```
