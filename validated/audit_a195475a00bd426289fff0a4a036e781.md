### Title
Stale StackerDB signer authorization persists when a controlling contract legitimately reports zero signers - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`StackerDBs::create_or_reconfigure_stackerdbs` refuses to apply a new signer configuration whenever the controlling smart contract legitimately reports an empty signer list, leaving the previous (now-unauthorized) signer set's write access intact. Because the `.signers-{0,1}-xxx` boot contracts are designed to alternate between an empty list and a populated list every reward cycle, this "fail open" guard is hit as part of normal, predictable operation rather than only as an error fallback, allowing a signer from an earlier reward cycle to keep writing/propagating chunks under the StackerDB slot that the canonical contract state says should now be unowned.

### Finding Description
`create_or_reconfigure_stackerdbs` only calls `reconfigure_stackerdb` (which is what actually updates each slot's authorized signer via `StackerDBTx::reconfigure_stackerdb`) under this condition: [1](#0-0) 


If the freshly loaded `new_config.signers` is empty, the `!new_config.signers.is_empty()` guard is false, so the branch is skipped entirely and the previously-stored slot ownership in the local `StackerDBs` database is left untouched (comment: "only reconfigure if the config has changed").

This was evidently intended to protect against a transient/error fallback (`StackerDBConfig::noop()`, which has empty `signers`) that `StackerDBConfig::from_smart_contract` is substituted for on evaluation failure. However, an empty signer list is also a **normal, expected state** for the `.signers-0-xxx` / `.signers-1-xxx` boot contracts, which simply proxy `stackerdb-get-signer-slots-page` for a fixed page (0 or 1) of the `.signers` contract's per-parity slot lists: [2](#0-1) [3](#0-2) 

Since `stackerdb-set-signer-slots` alternates which of `stackerdb-signer-slots-0`/`stackerdb-signer-slots-1` it updates based on `reward-cycle mod 2`, one of the two pages legitimately holds an empty list at any given time (confirmed directly by a unit test showing `signer_set == 0` returns an empty list while `signer_set == 1` is populated): [4](#0-3) 

So, on every reward-cycle transition, the `.signers-0-xxx` (or `.signers-1-xxx`) StackerDB replica for the "off" parity legitimately reports zero signers to `from_smart_contract`, and the local node's `create_or_reconfigure_stackerdbs` deliberately skips revoking the prior cycle's signer/slot mapping for that replica.

`validate_received_chunk` and `StackerDBTx::try_replace_chunk` authenticate incoming chunks purely against whatever signer is currently stored via `get_slot_signer`/`get_slot_validation`, not against the live contract state: [5](#0-4) 

Consequently, a signer belonging to a stale/previous reward-cycle assignment for that page (already removed by the contract, but never revoked locally because the guard blocked `reconfigure_stackerdb`) can continue signing and pushing chunks for that slot; the node — and any peer it gossips to — will accept and store them as valid, because `get_slot_signer` still returns the old address.

### Impact Explanation
This breaks the equality between "authorized signer per canonical `.signers` contract state" and "signer recorded/trusted by the local StackerDB replica." An entity that once held a legitimate signing key for a slot retains write and network-propagation capability for that StackerDB slot even after the contract has revoked/rotated it, and this chunk data is subsequently relayed to other nodes as authentic. This matches the "authenticated vs. stored" equality-break and "StackerDB chunk stored without a valid (current) owner" class explicitly called out as in-scope, and results in network-wide propagation of stale/unauthorized data under a slot that should be considered vacated.

### Likelihood Explanation
This is not a rare edge case requiring an error condition — it is a designed, periodic behavior of the `.signers-{0,1}-xxx` StackerDBs, which alternate between empty and non-empty signer lists every reward cycle by construction. Any former signer retaining their private key can exploit this without any special access, immediately after their reward-cycle assignment ends but before the replica happens to receive a config where `new_config.signers` is non-empty and different, keeping the old entry alive indefinitely for that "off" page.

### Recommendation
Remove the `!new_config.signers.is_empty()` special-case, or distinguish an explicit fetch/evaluation *error* (where the config should be left unmodified) from a successful, legitimately-empty signer list (where `reconfigure_stackerdb` should still run and clear/revoke the slots). At minimum, don't conflate `StackerDBConfig::noop()`'s error-fallback empty signer list with a contract-returned empty signer list — track success/failure of `from_smart_contract` separately from the resulting signer count.

### Proof of Concept
1. Configure a node with `.signers-0-<msg>` (page 0) tracking reward cycle parity 0.
2. During reward cycle `N` (even), `.signers` contract populates `stackerdb-signer-slots-0` with signer `A`; `create_or_reconfigure_stackerdbs` runs, `reconfigure_stackerdb` assigns slot 0 to `A` (see `stackslib/src/net/stackerdb/db.rs` `reconfigure_stackerdb`).
3. At the boundary into reward cycle `N+1` (odd), `.signers` legitimately updates only `stackerdb-signer-slots-1`, leaving `stackerdb-signer-slots-0` untouched from cycle `N-1`'s "actual" empty/stale state per the alternating page semantics shown in `signers_get_signer_keys_from_stackerdb`/`signers_db_get_slots` tests — `eval_signer_slots` for page 0 returns an empty list in the corresponding parity window.
4. `create_or_reconfigure_stackerdbs` sees `new_config.signers.is_empty()` and skips the `reconfigure_stackerdb` call entirely, leaving slot 0 still owned by `A` in the local database and any of A's peers' databases.
5. `A` (whose authorization for that page/parity has effectively lapsed per current contract state) signs and pushes a new chunk with `StackerDBChunkData::sign`; `validate_received_chunk` calls `get_slot_signer` (still `A`) and `SlotMetadata::verify` succeeds, so the chunk is accepted and gossiped network-wide, as shown by the acceptance path exercised in `test_validate_received_chunk_accepts_max_size` and `handle_unsolicited_StackerDBPushChunk` tests using the same `get_slot_signer`/`verify` flow.
