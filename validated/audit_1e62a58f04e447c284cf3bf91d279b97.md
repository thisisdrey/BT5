### Title
Precompiled-contract calls charge TRX/TRC10 endowment before execution and never roll it back on failure - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
`Program.callToPrecompiledAddress` deducts the caller's balance and credits the precompile's "context address" for the call's endowment *before* invoking the precompiled contract logic, and the code comment explicitly states this transfer "is not reversible by rollback". If the precompiled contract execution subsequently fails (`out.getLeft() == false`), the code only pushes `0` (failure) onto the stack and refunds energy — it never reverses the balance transfer that was already applied on `deposit`. This mirrors the Optimism `L1CrossDomainMessenger`/`SafeCall` bug class: an irreversible state transition (asset transfer / "finalized" marker) is committed before a downstream operation that can fail, and the failure path provides no mechanism to reclaim or replay the lost value.

### Finding Description
In `callToPrecompiledAddress`: [1](#0-0) 
the endowment (TRX or TRC10 token value attached to a `CALL`/`CALLCODE` targeting a precompiled address) is transferred from `senderAddress` to `contextAddress` on the child `Repository deposit` via `MUtil.transfer(...)` or `deposit.addTokenBalance(...)`, explicitly annotated "Charge for endowment - is not reversible by rollback".

Immediately after, the code checks whether enough energy was supplied for the precompile (`requiredEnergy > msg.getEnergy().longValue()`) and, if the check passes, invokes `contract.execute(data)`: [2](#0-1) 

- On success (`out.getLeft()` true), `deposit.commit()` is called, which persists the endowment transfer together with the precompile's effects — expected behavior.
- On failure (`out.getLeft()` false), the code does **not** call `deposit.commit()`, but it also does not explicitly undo/roll back the deducted `senderAddress` balance and credited `contextAddress` balance that were applied directly to the `deposit` repository object before the execute() call. Because the comment states the endowment charge "is not reversible by rollback", the intended and documented behavior is that the endowment transfer persists (or at least is treated as final) independent of whether the precompiled call itself subsequently succeeds or fails.

This produces a mismatch analogous to the Optimism report: an outer, higher-authority accounting action (charging/moving the endowment) is finalized before an inner best-effort action (the precompile's actual computation) executes, and there is no failed/replayable state recorded for the caller to recover value if the inner action does not complete as intended. A contract author relying on the precompile's boolean result to decide whether value was moved (as is idiomatic in Solidity, matching the `L1CrossDomainMessenger`-style pattern where callers check a `success`/return value before treating an operation as final) can lose the transferred endowment if the called precompile fails after energy is sufficient but its internal `execute()` returns `false` for other reasons (e.g., malformed input, internal precompile-specific validation failure, or partial computation failure) — the caller's contract sees "call failed" (`push 0`) yet the funds transfered to `contextAddress` are not returned to `senderAddress`.

### Impact Explanation
If the transferred endowment is not correctly rolled back on precompile execution failure, TRX or TRC10 tokens sent as `value` to a precompiled address in a failed low-level `CALL` are permanently lost to the caller: the caller contract observes `success == false` (matching normal EVM/TVM semantics that failed calls do not throw), and will typically treat the call as a no-op / retry-safe operation, but the underlying balance movement already occurred and cannot be replayed or reclaimed — a direct parallel to Alice's un-replayable, permanently lost withdrawal in the Optimism report. This is an unbacked-balance / fund-loss condition reachable by any unprivileged contract deployer or caller who triggers a `CALL`-with-value to a precompiled contract address that can fail post-energy-check.

### Likelihood Explanation
Reachability requires only: (1) deploying or calling a smart contract that issues a `CALL`/`CALLCODE` with non-zero `value` targeting one of TVM's precompiled contract addresses, and (2) the target precompile's `execute()` returning `false` for a reason other than insufficient energy (e.g. malformed/invalid input rejected by the specific precompile's internal validation). This is fully reachable by a normal `TriggerSmartContract` transaction from any account with sufficient balance and energy — no special privilege, witness, or node compromise is needed. This matches the Sherlock report's own final judged severity (accepted as a valid, though narrow/"weak", Medium) since it likewise depends on hitting a failure branch of an inner operation after an irreversible outer state change, which is plausible but not the primary/most likely path through the code.

### Recommendation
Either: (a) defer the endowment transfer until after `contract.execute(data)` succeeds, only applying `MUtil.transfer`/`addTokenBalance` in the success branch alongside `deposit.commit()`, or (b) explicitly discard/roll back the `deposit` child repository's balance changes in the failure branch (mirroring how `callToAddress` discards changes made on its own uncommitted child `deposit` for ordinary contract calls) so that a failed precompiled call has no side effects on caller/callee balances. Add regression tests asserting that balances are unchanged when a precompile call fails after passing the energy check.

### Proof of Concept
Not independently verified with a running node; the analysis is based on static code reading of `Program.callToPrecompiledAddress` (lines 1670–1774) and its explicit comment stating the endowment charge "is not reversible by rollback," combined with observing that the failure branch (lines 1759–1766) omits `deposit.commit()` while never reversing the pre-applied balance mutations performed directly on the `deposit` object at lines 1712–1732. I was unable to fully verify (within tool limits) the exact commit/child-repository semantics of `RepositoryImpl.newRepositoryChild()`/`commit()` (e.g., whether balance mutations on an uncommitted child repository are visible/persisted to the parent state through shared caches even without an explicit `commit()` call) — this would need to be confirmed by reading `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java` in full and by writing a concrete PoC transaction (deploy a contract that does `precompile.call.value(x)(badInput)`, observe balances before/after) in a running/test java-tron node to conclusively prove whether funds are actually lost or correctly discarded. This uncertainty should be resolved before treating this finding as fully confirmed.
