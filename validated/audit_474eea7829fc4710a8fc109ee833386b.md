### Title
`storage_deposit` wnear amount is debited with no refund path when `storage_deposit()` fails but `ft_transfer`/`ft_transfer_call` still succeeds - (File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs)

### Summary
`internal_ft_withdraw` debits both the withdrawn FT `amount` and the `wnear` `storage_deposit` amount in a single `withdraw()` call, then schedules `near_withdraw -> storage_deposit -> ft_transfer(_call)` as a promise chain built via `ext_ft_core::ext_on(p)`. Because NEAR's `.then()` chaining unconditionally executes the next scheduled call regardless of whether the preceding promise (`storage_deposit`) succeeded, and `ft_resolve_withdraw` only inspects the result of the *last* promise in the chain (the FT transfer), a failed `storage_deposit` leaves its debited wnear amount with no corresponding refund.

### Finding Description
Binding that should hold: `wnear_debited_for_storage_deposit == wnear_spent_on_storage + wnear_refunded_to_owner_ledger`.

In `internal_ft_withdraw` [1](#0-0) , both the FT `amount` and the `storage_deposit` (in wnear) are subtracted from the owner's internal ledger in the *same* `withdraw()` call. The promise chain is then built as:

`near_withdraw(storage_deposit)` → `do_ft_withdraw()` → (`storage_deposit()` on `token`, then `ft_transfer`/`ft_transfer_call` chained via `ext_ft_core::ext_on(p)`) → `.then(ft_resolve_withdraw)`. [2](#0-1) 

`ext_on(p)` chains the `ft_transfer`/`ft_transfer_call` action as a genuinely new dependent promise on top of `p` (the `storage_deposit` promise or a no-op `Promise::new(token)`) — confirmed by the analogous usage in `contracts/defuse/src/contract/upgrade.rs`, where `Self::ext_on(p).state_migrate()` is chained after `deploy_contract()` specifically so `state_migrate` runs in a *new* receipt with the newly-deployed code; this is only possible if `ext_on` produces a `.then()`-style dependent promise, not an action batched into the same receipt [3](#0-2) . NEAR's `.then()` semantics always execute the dependent promise regardless of the predecessor's success/failure — the callee function only reacts to failure if it explicitly calls `promise_result_checked_*`, as this same codebase does for `near_withdraw` results via `require!(promise_result_checked_void(0).is_ok(), ...)` [4](#0-3) . Critically, `ft_transfer`/`ft_transfer_call` is a plain NEP-141 method on an arbitrary external token contract — it performs no such check on the prior `storage_deposit` promise's outcome, so it executes and moves tokens even if `storage_deposit` failed.

`ft_resolve_withdraw`'s `promise_result_checked_*(0)` reflects only the result of the last promise in the chain (the FT transfer), never the `storage_deposit` sub-call, and its refund logic operates solely on the FT `amount` parameter — there is no code path that inspects or refunds the `storage_deposit` wnear amount: [5](#0-4) .

Exploit/failure flow: owner signs `FtWithdraw{ storage_deposit: Some(X), receiver_id: R, ... }` where `R`'s storage registration on `token` is engineered to fail (e.g., insufficient `X` relative to `token`'s `storage_balance_bounds`, or `R` already registered causing the token contract to reject/refund the deposit). `self.withdraw()` debits both `amount` (token) and `X` (wnear) from the ledger. `storage_deposit()` fails; the attached native NEAR (unwrapped from `X` via `near_withdraw`) is refunded by the NEAR protocol back to the Defuse contract's own account balance (not the user's internal ledger). `ft_transfer`/`ft_transfer_call`, chained via `.then()`/`ext_on`, still executes and moves `amount` tokens to `R`. `ft_resolve_withdraw` sees the FT leg succeeded, credits nothing back (correctly, for the FT amount), but never re-credits `X` because it has no knowledge of the storage-deposit leg at all.

### Impact Explanation
The `X` wnear amount debited from the withdrawing user's ledger is permanently lost from that user's perspective: it is neither registered as storage on the receiver, nor refunded to the user's internal balance. The equivalent native NEAR ends up stranded in the Defuse contract's own account, outside any user's ledger — a genuine "refund/resolver credit that does not match what failed to settle" and effectively "user funds permanently frozen," matching the Critical impact bucket. This affects the token owner performing the withdrawal (not a third-party victim) each time a `storage_deposit` sub-call fails while the paired FT transfer succeeds; it is repeatable per withdrawal call and applies identically to the analogous NEP-245 flow (`do_mt_withdraw`/`mt_resolve_withdraw`) that has the exact same structure.

### Likelihood Explanation
No special privileges are required — any account holder using `ft_withdraw` with `storage_deposit = Some(X)` can trigger this, deliberately or accidentally, by choosing an `X` that is insufficient for the target token's current storage requirements, or a `receiver_id` that is already registered (many NEP-141 implementations reject/refund `storage_deposit` for already-registered accounts, causing the deposit call to fail or refund independently of ledger accounting). This requires only a normal, unprivileged transaction — no relayer key, no DAO/role, no third-party control. It is reproducible on every call using this feature under these conditions.

### Recommendation
Track the `storage_deposit` wnear leg independently in the resolver: have `do_ft_withdraw` return/propagate whether `storage_deposit` succeeded (e.g., via a preceding `.then()` callback that inspects `promise_result(0)` for the `storage_deposit` promise specifically, before chaining the FT transfer), and have `ft_resolve_withdraw` (or a dedicated resolver) refund the `storage_deposit` amount to the owner's wnear balance whenever that specific sub-call did not succeed, independent of whether the FT transfer succeeded.

### Proof of Concept
`cargo test` (near-workspaces sandbox) plan:
1. Deploy a wnear-compatible FT contract and a receiver-token FT contract whose `storage_deposit` panics/rejects when the attached deposit is below its `storage_balance_bounds().min` (standard NEP-145 behavior).
2. Fund a Defuse account with `amount` of the receiver token and `X` (small, insufficient) of wnear.
3. Call `ft_withdraw` with `storage_deposit = Some(X)`, `receiver_id` unregistered on the receiver token, `amount > 0`.
4. Assert: the receipt for `storage_deposit()` fails (`ExecutionStatus::Failure`), while the receipt for `ft_transfer` succeeds and `receiver_id`'s token balance increases by `amount`.
5. Assert the binding: query the owner's internal wnear ledger balance before and after — expect `wnear_before - X == wnear_after` with **no** subsequent credit event, and confirm `wnear_actually_spent_on_storage (0) + wnear_refunded_to_owner_ledger (0) != X` — i.e., `X` is unaccounted for in the user's ledger, disproving the binding.

    #[private]
    pub fn do_ft_withdraw(withdraw: FtWithdraw) -> Promise {
        let min_gas = withdraw.min_gas();
        let p = if let Some(storage_deposit) = withdraw.storage_deposit {
            require!(
                promise_result_checked_void(0).is_ok(),
                "near_withdraw failed",
            );

            ext_storage_management::ext(withdraw.token)
                .with_attached_deposit(storage_deposit)
                .with_static_gas(STORAGE_DEPOSIT_GAS)
                // do not distribute remaining gas here
                .with_unused_gas_weight(0)
                .storage_deposit(Some(withdraw.receiver_id.clone()), None)
        } else {
            Promise::new(withdraw.token)
        };

        let p = ext_ft_core::ext_on(p)
            .with_attached_deposit(NearToken::from_yoctonear(1))
            .with_static_gas(min_gas)
            // distribute remaining gas here
            .with_unused_gas_weight(1);
        if let Some(msg) = withdraw.msg {
            p.ft_transfer_call(
                withdraw.receiver_id,
                withdraw.amount.into(),
                withdraw.memo,
                msg,
            )
        } else {
            p.ft_transfer(withdraw.receiver_id, withdraw.amount.into(), withdraw.memo)
        }
    }

    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
