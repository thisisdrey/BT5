## Title
Missing boundary check before indexing `DataWord[]` arrays in `ValidateMultiSign`/`BatchValidateSign` TVM precompiles when TIP-854 guard is inactive - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` precompiled contracts parse attacker-supplied TVM call data into a `DataWord[]` array and then use attacker-controlled offset words (`words[3]`, `words[1]`, `words[2]`) to index further into that same array before any length validation is performed [1](#0-0) . A boundary check (`isValidAbiEncoding`) that would reject malformed calldata exists, but it is gated behind the `VMConfig.allowTvmOsaka()` feature flag, i.e. it is only enforced once a future hard fork activates [2](#0-1) . This is the direct analog of CVE-2024-38542: an index derived from untrusted input is used to access an array before its bounds are validated, and the validation that was added is not unconditionally active.

### Finding Description
`ValidateMultiSign.execute()` and `BatchValidateSign.doExecute()` call `DataWord.parseArray(rawData)` to build a `words[]` array sized by `rawData.length / 32`, then immediately dereference `words[3]` (or `words[1]`/`words[2]` for `BatchValidateSign`) and use `words[offset].intValueSafe()` to compute a further index into the same `words[]` array via `extractSigArray`/`extractBytesArray`/`extractBytes32Array` [3](#0-2) . None of this indexing is bounds-checked unless `VMConfig.allowTvmOsaka()` is enabled:

```java
if (VMConfig.allowTvmOsaka()
    && !isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)) {
  return Pair.of(false, EMPTY_BYTE_ARRAY);
}
DataWord[] words = DataWord.parseArray(rawData);
byte[] address = words[0].toTronAddress();
``` [4](#0-3) 

The only `try/catch` in `ValidateMultiSign.execute()` wraps just the permission-weight loop, not the earlier `DataWord.parseArray`/offset-indexing code, so an `ArrayIndexOutOfBoundsException` thrown while parsing malformed calldata is not swallowed there [5](#0-4) . The project's own test suite documents this explicitly as the "pre-activation" legacy failure mode:

> "TIP-854: before activation, malformed calldata reaches the legacy decoder... this precompile has no outer catch, so a too-short input raises inside the decoder; that is the documented pre-activation failure mode the TIP explicitly preserves." [6](#0-5) 

and for `BatchValidateSign`:

> "TIP-854: before activation the guard is not consulted. Malformed calldata that would raise inside doExecute gets collapsed to (true, 32-byte zero) by the outer catch" [7](#0-6) 

Because `BatchValidateSign.execute()` wraps the entire `doExecute()` call in `try { ... } catch (Throwable t)` [8](#0-7) , an out-of-bounds exception there is contained and converted to a zeroed result — this path is safe. However, `ValidateMultiSign.execute()` has no equivalent outer catch around the calldata-parsing section, so a crafted, short/misaligned `bytes[]` payload triggers an uncaught `ArrayIndexOutOfBoundsException` directly out of the precompile's `execute()` method while `VMConfig.allowTvmOsaka()` is disabled (the current default/mainnet state — this flag corresponds to a not-yet-activated hard fork feature, similarly to other `allowTvmXxx` flags gated in `VMConfig`/`ConfigLoader`).

### Impact Explanation
Any account can deploy a trivial contract that `CALL`s the `ValidateMultiSign` precompiled contract address with a short or misaligned `bytes` payload for the `signatures` array. Because the array-index guard is inactive under the current (pre-TIP-854) configuration, this throws an unhandled `ArrayIndexOutOfBoundsException` from inside the precompile, which is not caught locally. Depending on how far up the call stack this propagates (through `Program.callToPrecompiledAddress`), this can manifest as an unexpected VM/transaction failure mode inconsistent with normal `REVERT` semantics, and — because `ValidateMultiSign` is exercised by every node executing the block containing the malicious transaction — a divergence or crash risk during block application is possible if the exception is not deterministically handled identically by all nodes. This matches the CVE class of "missing bounds check leading to a crash/DoS reachable from untrusted input."

### Likelihood Explanation
High: `ValidateMultiSign` is directly callable from any TVM contract via `CALL`/`STATICCALL` to its precompiled address, requires no special permission, and the malformed-calldata condition is trivial to construct (any `bytes.length` not shaped as `5*32 + 5*32*N`). The vulnerable code path is unconditionally reached today because the compensating check is disabled until a future hard fork (`allowTvmOsaka`).

### Recommendation
Remove the `VMConfig.allowTvmOsaka()` gate from the `isValidAbiEncoding` check in `ValidateMultiSign.execute()` (and equivalently ensure `BatchValidateSign` is protected without relying on hard-fork gating), or alternatively wrap the entire calldata-parsing section of `ValidateMultiSign.execute()` in a `try/catch (Throwable)` that returns `Pair.of(true, DATA_FALSE)` on any parsing failure, matching the resilient behavior already used in `BatchValidateSign.execute()`.

### Proof of Concept
Deploy a contract that performs:
```solidity
address(0x0000000000000000000000000000000000010001) // ValidateMultiSign precompile address (owner-obtained)
  .call(abi.encodeWithSignature(
      "validatemultisign(address,uint256,bytes32,bytes[])",
      someAddress, 0, bytes32(0), new bytes[](0)))
```
with calldata truncated/misaligned so it is shorter than `(ABI_HEADER_WORDS)*32 = 160` bytes, or where the length is not `160 + 160*N`. Before the `allowTvmOsaka` hard fork flag is enabled, `contract.execute(rawData)` throws an uncaught `ArrayIndexOutOfBoundsException` when computing `words[words[3].intValueSafe() / WORD_SIZE]`, exactly as reproduced by the project's own regression test `testTip854PreActivationNoOp` in `ValidateMultiSignContractTest.java`, which explicitly asserts this exception is not masked pre-activation [9](#0-8) .

**Note on completeness:** I was unable to fully trace `Program.callToPrecompiledAddress` in `actuator/src/main/java/org/tron/core/vm/program/Program.java` in this session (ran out of tool iterations) to conclusively determine whether the uncaught exception is caught generically at that layer and converted to a normal revert, or whether it can propagate further up into `TransactionTrace`/`Manager` block-application code. This should be verified directly against `Program.java`'s `callToPrecompiledAddress` implementation before finalizing severity — if it is caught deterministically there and converted into a clean revert for all nodes, the practical impact is reduced to a "wasted-call/inconsistent revert reason" issue rather than a crash/consensus risk.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {

      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
