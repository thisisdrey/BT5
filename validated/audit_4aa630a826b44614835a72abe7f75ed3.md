### Title
Missing URL scheme validation allows `file://` local file/repository disclosure via FetchRemote/FindRemoteRootRef/CreateRepositoryFromURL - ([File: internal/gitaly/service/repository/create_repository_from_url.go])

### Summary
Gitaly's `validateFetchRemoteRequest`, `validateCreateRepositoryFromURLRequest`, and `FindRemoteRootRef`'s inline validation only check that the remote URL string is non-empty; they never restrict the URL scheme. The `http.followRedirects=false` config pair applied to the `fetch`/`clone`/`remote` git commands in `internal/git/gitcmd/command_description.go` only affects HTTP(S) redirect-following behavior and has no effect on git's `file://` transport, so an attacker-supplied `file://` URL reaches `git clone`/`git fetch`/`git remote show` unmodified.

### Finding Description
In `internal/gitaly/service/repository/create_repository_from_url.go`, `validateCreateRepositoryFromURLRequest` only checks `req.GetUrl() == ""` [1](#0-0) , and `cloneFromURLCommand` parses the URL with `url.Parse` and passes it straight to `git clone` as a positional argument without any scheme allowlist [2](#0-1) . Likewise `validateFetchRemoteRequest` in `internal/gitaly/service/repository/fetch_remote.go` only validates that the URL is non-blank [3](#0-2) , and `FindRemoteRootRef` performs the same non-empty check before invoking `git remote show` with the attacker URL [4](#0-3) .

The `http.followRedirects=false` config injected for the `fetch`/`clone`/`push`/`remote`/`ls-remote` commands in `commandDescriptions` is a curl/HTTP-specific setting that prevents HTTP redirect-based SSRF, but it does nothing to restrict which URL scheme is used in the first place [5](#0-4) . Git's `file://` transport is a completely separate code path from libcurl and is unaffected by any `http.*` configuration.

This is demonstrated by the repository's own test `TestCreateRepositoryFromURL_fsck`, which issues `Url: "file://" + sourceRepoPath` and the clone actually executes and reads the local repository's contents (failing only later on an unrelated `fsck` duplicate-entry check, proving the local file data was read and processed) [6](#0-5) . This confirms Gitaly itself places no restriction on the `file://` scheme for these RPCs.

### Impact Explanation
An attacker who can control the `Url`/`RemoteParams.Url`/`RemoteUrl` field passed to `CreateRepositoryFromURL`, `FetchRemote`, or `FindRemoteRootRef` can point it at `file:///var/opt/gitlab/git-data/repositories/<other-namespace>/<other-repo>.git` to have Gitaly clone/fetch another repository's objects into a repository the attacker controls (cross-repository object/metadata disclosure), or at other local paths readable as git repositories. This maps to GitLab's SSRF/information-disclosure bounty impact class (local file/repo read via server-side request forgery in an import/fetch feature).

### Likelihood Explanation
Exploitability depends entirely on whether GitLab Rails (or another Gitaly caller) restricts the URL scheme before invoking these RPCs; Gitaly's own code provides zero defense-in-depth here. If Rails' URL validators for project-import-by-URL, pull-mirror configuration, or Geo/replication paths ever miss a `file://`/edge-case scheme (a known, previously-patched class of SSRF issue for GitLab's import feature), Gitaly will execute the request without any secondary check. This makes Gitaly a single point of failure for this control rather than providing the “credential/transport confinement” invariant the `http.followRedirects=false` comments suggest it enforces.

### Recommendation
Add explicit remote-URL scheme validation in `validateFetchRemoteRequest`, `validateCreateRepositoryFromURLRequest`, and `FindRemoteRootRef` (and any other RPC accepting a remote URL) that rejects `file://` and any other non-network scheme (e.g., allow only `http://`, `https://`, `git://`, `ssh://`, and scp-like syntax), independent of what GitLab Rails does, so Gitaly itself enforces the intended "network transport only" invariant instead of relying solely on `http.followRedirects` and upstream sanitization.
