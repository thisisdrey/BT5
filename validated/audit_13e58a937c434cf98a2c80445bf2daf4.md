### Title
Missing defensive copy in `DataWord(byte[])` aliases cached TVM storage-row buffers, allowing in-place opcode mutation to corrupt subsequent `SLOAD` reads within the same execution - (File: `common/src/main/java/org/tron/common/runtime/vm/DataWord.java`)

### Summary
`DataWord`'s constructor stores a caller-supplied 32-byte array by reference instead of copying it, mirroring the libsixel root cause (`sixel_frame_init()` storing a caller-owned buffer pointer without a defensive copy). Combined with `Storage.getValue()` returning the live, cached `StorageRowCapsule` byte array and several TVM opcodes mutating `DataWord` contents in place, a crafted contract can alias and corrupt a cached storage slot's backing array during its own execution.

### Finding Description
`DataWord(byte[] data)` only copies the input when `data.length < WORD_SIZE`; when the array is exactly 32 bytes it is assigned directly to the internal `data` field with no defensive copy: [1](#0-0) 

`Storage.getValue()` returns a `DataWord` built from `row.getValue()`, and separately caches the same `StorageRowCapsule` object (`row`) by reference in `rowCache` for reuse on subsequent reads of the same key within the same call/context: [2](#0-1) 

`StorageRowCapsule.getValue()`/`getInstance()` return the internal `rowValue` array directly, without cloning: [3](#0-2) 

Because `DataWord`'s constructor aliases (rather than copies) 32-byte arrays, the `DataWord` produced by `getValue()` shares the exact same underlying `byte[]` object as the cached `StorageRowCapsule.rowValue`. Several TVM opcode handlers mutate a `DataWord`'s backing array **in place** rather than allocating a new one, e.g. `ISZERO`, `LT`, `GT`, `SLT`, `SGT`, `EQ`, `BYTE`: [4](#0-3) [5](#0-4) 

Consequently, if a contract executes `SLOAD` on a slot, then applies any of these in-place-mutating opcodes to the popped value, the write via `word1.getData()[31] = ...` (or `and(DataWord.ZERO)`) mutates the shared array object still referenced by `rowCache`'s cached `StorageRowCapsule` - without ever calling `StorageRowCapsule.setValue()`/`markDirty()`. A subsequent `SLOAD` of the same key within the same execution context (e.g. after a reentrant call back into the same storage/repository context) then returns the corrupted value from the cache instead of the true persisted value, since `Storage.getValue()`'s cache-hit path re-wraps the same mutated array: [6](#0-5) 

This is structurally analogous to the libsixel CVE: a mutable, caller/owner-shared buffer is stored by reference without a defensive copy, and later in-place modification of that buffer corrupts state visible to another logical owner that still expects the original, untouched contents (dangling/aliased-buffer read producing stale/incorrect data instead of a hard crash, since Java is garbage collected).

### Impact Explanation
A malicious smart contract can deliberately corrupt its own cached storage read within a single transaction/call context (e.g. via `SLOAD` → `ISZERO`/`EQ`/`LT` → reentrant `SLOAD` on the same key). Because the dirty flag is never set, the corruption does not directly get persisted through `commit()`, but it can corrupt what subsequent code paths within the same execution "see" for that storage slot, which can be leveraged to bypass state-dependent guard checks (e.g., re-entrancy guards, "already claimed"/balance-zero checks implemented via storage) implemented purely in contract storage, enabling unauthorized double-execution of privileged/paying logic within a crafted single transaction.

### Likelihood Explanation
Reachable by any unprivileged account through ordinary `TriggerSmartContract` execution of attacker-controlled bytecode; no special privileges required. Exploitation, however, requires a contract logic pattern that relies on comparing a freshly loaded storage value and then re-reading the same slot again in the same call graph (e.g. via reentrancy), so real-world impact is dependent on how a target contract implements state checks.

### Recommendation
Make `DataWord(byte[] data)` always defensively copy its input array (mirroring the `data.length < WORD_SIZE` branch) rather than aliasing 32-byte inputs directly, and/or have `Storage.getValue()` / `StorageRowCapsule.getValue()` return cloned arrays before wrapping them in a `DataWord`, consistent with the deep-copy already performed in the `Storage(Storage storage)` copy constructor.

### Proof of Concept
1. Deploy a contract whose fallback logic does, conceptually:
   - `SLOAD slot` (loads a stored guard/balance flag into TVM stack)
   - `ISZERO` (mutates the popped `DataWord`'s backing array in place via `word1.getData()[31] = 1`)
   - Re-enter the same contract (e.g. via an external call back to itself before returning) causing a second `SLOAD` on the same `slot` within the still-active `Storage`/`rowCache` instance.
2. The second `SLOAD` returns the mutated value (now effectively "1"/nonzero regardless of the true stored content) because it is served from `rowCache` and shares the same array object mutated by `ISZERO`, instead of the actual persisted 32-byte storage value.
3. Contract logic relying on the true stored value for the second check (e.g. a re-entrancy lock or "already withdrawn" flag) observes the corrupted value and can be tricked into taking an unintended code path (e.g. permitting a duplicate withdrawal) within a single crafted transaction.

  public DataWord(byte[] data) {
    if (data == null) {
      this.data = ByteUtil.EMPTY_BYTE_ARRAY;
    } else if (data.length == WORD_SIZE) {
      this.data = data;
    } else if (data.length < WORD_SIZE) {
      System.arraycopy(data, 0, this.data, WORD_SIZE - data.length, data.length);
    } else {
      throw new RuntimeException("Data word can't exceed 32 bytes: " + ByteArray.toHexString(data));
    }
  }
