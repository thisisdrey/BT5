### Title
Stale `PromiseYieldReceipt`/`PromiseYieldStatus` survive `remove_account`, letting a re-created account inherit and auto-execute a pre-deletion yield receipt - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (core/store/src/utils/mod.rs:505-575) removes the `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` rows for a deleted account, but never removes any `PromiseYieldReceipt`, `PromiseYieldStatus`, or `yield_id` mapping rows keyed by that account's id. The global, index-keyed `PromiseYieldTimeout` queue is likewise untouched by account deletion. When the queue entry's `expires_at` height is later reached, `resolve_promise_yield_timeouts` (runtime/runtime/src/lib.rs:3009-3116) looks the pending yield up purely by `(account_id, data_id)`, finds the stale `PromiseYieldReceipt` still present, and synthesizes/executes a `PromiseResume` against whatever account currently holds that `account_id` at that time.

### Finding Description
- `promise_yield_create` stores the yield's action receipt under `TrieKey::PromiseYieldReceipt{ receiver_id, data_id }` (`set_promise_yield_receipt`, core/store/src/utils/mod.rs:200-212) and enqueues a `PromiseYieldTimeout{ account_id, data_id, expires_at }` entry into a global FIFO queue keyed only by `index` (core/store/src/utils/mod.rs:181-198; `core/primitives/src/trie_key.rs:236-241`).
- `remove_account` (core/store/src/utils/mod.rs:505-575) removes `Account`, `ContractCode`, access keys/gas-key nonces, and iterates+removes `ContractData` rows for the account — but it contains no logic that touches `col::PROMISE_YIELD_RECEIPT`, the yield status column, or the `col::PROMISE_YIELD_TIMEOUT` queue. `action_delete_account` (runtime/runtime/src/actions.rs:314-390) calls only `remove_account`, so a `DeleteAccountAction` on an account with a pending yield leaves the `PromiseYieldReceipt` and its queued timeout entry orphaned in state.
- `resolve_promise_yield_timeouts` (runtime/runtime/src/lib.rs:3009-3104) processes the queue strictly in `expires_at` order and, for each expired entry, checks `state_update.contains_key(&TrieKey::PromiseYieldReceipt{ receiver_id: queue_entry.account_id, data_id: queue_entry.data_id })` (lib.rs:3047-3051). It does **not** verify that this receipt belongs to the same "incarnation" of the account that created it — it only matches by the (never-versioned) `account_id` string. If a `PromiseYieldReceipt` still exists under that key (because `remove_account` never removed it), a `PromiseResume` receipt is created and routed to the (possibly re-created) account (lib.rs:3059-3097), and eventually the original, pre-deletion action receipt is executed via `apply_action_receipt` against the account's *current* trie state (lib.rs:1514-1560).
- Because `PromiseYield` receipts are confined to a single account, the parked receipt's `predecessor_id` and `receiver_id` are effectively the same account name, so a re-created account at the same name will see this resumed receipt arrive with `predecessor_id == receiver_id == self`. Any function invoked by that stale receipt that uses a common "callback self-auth" pattern (e.g. `assert_eq!(predecessor_account_id, env::current_account_id())`) would pass this check even though the code and storage that authored the original yield belong to a logically different deployment.
- No existing check in transaction validation, access-key permission checks, or `remove_account`'s cleanup logic prevents this, because they only operate on `Account`, `AccessKey`, `ContractCode`, and `ContractData` — the promise-yield bookkeeping is a separate storage column that `remove_account` was never extended to cover.

### Impact Explanation
This is a determinism/authorization-adjacent bug rather than a cross-account fund-theft primitive in the strict sense: the attacker must control the `account_id` at creation time (to seed the yield) and it must be re-creatable at the same name later (either by the same actor, or — for reusable top-level/sub-account names — potentially by a different party). The concrete impacts are:
- **State leak / stale trie rows**: `PromiseYieldReceipt`, `PromiseYieldStatus`, and (with `YieldWithId`) `yield_id` mapping entries persist forever for a deleted account, unbounded by account lifetime — a resource-hygiene defect.
- **Authorization ambiguity across account incarnations**: if a different owner later creates an account under the exact same `account_id` before the stale timeout fires, the runtime will execute the *original* owner's parked callback receipt against the *new* owner's deployed contract/state, with `predecessor_id` equal to the account itself — potentially satisfying naive `assert_self()`-style authorization checks in the new contract that assume only their own code could have produced a self-call. This falls under the "authorization escalation across accounts or promises" bounty category, but is bounded by requiring exact account-name reuse within the timeout window, which is a narrow and largely attacker-self-controlled precondition on mainnet (top-level account name reuse after deletion is rare/restricted; most realistic recreation is by the same actor who deleted it, in which case there is no third-party victim).
- I did not find, and could not verify in the available code, any path where this leads to a shard-halting panic — `resolve_promise_yield_timeouts` and the `PromiseResume` handling path use `?`-propagated `Result`s, not `unwrap`/`expect`, for the account lookups involved.

### Likelihood Explanation
- Cost/feasibility: trivial for an unprivileged attacker to trigger against their own account — deploy a contract, call `promise_yield_create` with a long timeout, then submit `DeleteAccountAction`, then `CreateAccountAction` for the same name, timed so the timeout height falls after recreation. This requires only ordinary signed transactions and no privileged role.
- The scenario where a *different* victim recreates the same account name is far less likely on mainnet given NEAR's account-name allocation rules (implicit accounts, registrar-gated top-level names, and sub-accounts controlled by a specific parent), so the higher-impact "victim" framing in the question is largely speculative; the self-inflicted state-leak/inconsistency is the well-supported, reproducible part.
- Repeatable: yes, deterministically, any number of times, since `remove_account`'s omission is a permanent code-level gap.

### Recommendation
Extend `remove_account` (core/store/src/utils/mod.rs) to also purge, for the account being deleted:
- Any `PromiseYieldReceipt` rows under `col::PROMISE_YIELD_RECEIPT` for that `account_id` (iterate its prefix similarly to the existing `ContractData` cleanup loop).
- The corresponding `PromiseYieldStatus` entries and `yield_id ↔ data_id` mappings.
- Additionally, consider marking/skipping stale `PromiseYieldTimeout` queue entries whose account no longer matches the account that created them (e.g. by checking `get_account` non-existence, or by removing the receipt as above so `contains_key` in `resolve_promise_yield_timeouts` naturally returns `false` and the timeout is silently dequeued, as already happens for legitimately-resumed yields).

### Proof of Concept
Test-loop integration test plan (extending `test-loop-tests/src/tests/yield_timeouts.rs` patterns):
1. Deploy a test contract on account `A` that calls `promise_yield_create` with a timeout `T` blocks in the future.
2. Submit `DeleteAccountAction` for `A` (beneficiary = some other funded account) in a block before `T`.
3. Assert (state read) that `TrieKey::PromiseYieldReceipt{ receiver_id: A, data_id }` still exists in state after deletion (demonstrating the leak) — this alone proves the bug.
4. Submit `CreateAccountAction`/`DeployContractAction` re-creating `A` with a new (different) contract that has a privileged method guarded by a self-call assertion (`predecessor_id == current_account_id`), before block height `T`.
5. Advance the chain to height `T` and `T+1`; assert that `resolve_promise_yield_timeouts` produces a `PromiseResume` receipt targeting the recreated `A`, and that the original (pre-deletion) yield receipt's actions execute against the new account's contract/state (e.g., observe state mutation or a successful call to the new contract's self-call-guarded method that the new owner never invoked).
6. Assert this occurs without a panic (liveness maintained) but that the state mutation is attributable to a receipt the new account's owner never authored — demonstrating the authorization/consistency violation.
