### Title
Trapped assets with no recovery path in `TeleportForwarderForAccountId32` (`accumulate-and-forward` XCM adapter) - ([File: polkadot/xcm/xcm-builder/src/forwarder.rs])

### Summary
The Convex report's core defect is a generic claim path that withdraws value out of a contract-controlled account, with no companion function to recover that value if it ends up stuck. The local analog is `TeleportForwarderForAccountId32::forward`, the `Forwarder` implementation used by `pallet_accumulate_and_forward::on_idle` to periodically move accumulated fees/dust/coretime-revenue off system chains to AssetHub. Once the local half of the XCM program completes (withdrawing and burning the tokens from the accumulation account, reducing local issuance and committing the transaction), the remote deposit step can still fail on the destination, permanently trapping the minted assets with no mechanism — analogous to Convex's missing "transferTokens" sweep — to recover them, because the accumulation account is a `PalletId`-derived account with no private key able to sign a `claim_assets` extrinsic on the destination chain.

### Finding Description
`pallet_accumulate_and_forward`'s `on_idle` hook periodically calls the configured `Forwarder::forward` once accumulated funds exceed `MinTransferAmount`: [1](#0-0) 

The configured forwarder for Westend system chains is `TeleportForwarderForAccountId32`, whose own doc comment already flags the risk: [2](#0-1) 

The implementation builds an XCM that withdraws the native asset locally, teleports it out (burn), and lets `InitiateTransfer` queue a remote leg that deposits the asset to a beneficiary on the destination chain: [3](#0-2) 

Crucially, `with_transaction` only guards the *local* execution: if `prepare_and_execute` reports `Outcome::Complete`, the local withdrawal/burn is committed and the function returns `Ok(())`, even though the remote leg has merely been queued, not yet executed: [4](#0-3) 

If the remote (AssetHub) execution of the queued `Xcm` fails — e.g. the `DepositAsset` instruction cannot land at `StagingLocation`/beneficiary due to a barrier change, asset-registration mismatch, or decode/weight issue — the assets that were successfully teleported in are trapped in AssetHub's `PolkadotXcm::AssetsTrapped` storage under the trap origin corresponding to the accumulation account's aliased location. The pallet-level accounting already treats this as final and successful: [5](#0-4) 

The only sanctioned recovery mechanism for trapped assets in this codebase is `pallet_xcm::claim_assets`, which requires a *signed origin* matching the trap's origin location — as exercised in the Snowbridge fallback-claimer test: [6](#0-5) 

But the accumulation account is `T::PalletId::get().into_account_truncating()` — a derived account with no private key that could ever sign a `claim_assets` extrinsic: [7](#0-6) 

Neither `pallet_accumulate_and_forward` nor the `xcm-builder` forwarder module provides an admin/root call to reclaim trapped funds on the destination chain analogous to Convex's missing `transferTokens`. This is the same broken invariant as the seed report: value is pulled out of a controlled account via a "generic" dispatch path, and no function exists to move it back out when the flow does not fully complete.

### Impact Explanation
Every successful local teleport-out that fails on the destination chain permanently locks real value (transaction fees, dust, coretime revenue accumulated from an entire system chain) as unclaimable trapped assets on AssetHub, since no key exists to submit `claim_assets` for that trap origin. This is a direct, self-inflicted, permanent fund lock in the runtime's own accounting/forwarding pipeline — matching the "permanent user-fund or bridge-state lock" impact category.

### Likelihood Explanation
This occurs on every `on_idle` forwarding cycle for which the local leg completes but the remote leg is rejected (e.g., after any misconfiguration of the destination barrier/asset registration, a decode error in the remote XCM, or an unexpected filter change on AssetHub) — a normal operational hazard for a periodic unattended runtime hook, not requiring a malicious actor, governance, or off-chain party.

### Recommendation
Either (a) do not commit the local burn until remote execution success is confirmed (e.g. via a two-phase commit/DMP acknowledgment before minting/deriving further accounting), or (b) add an explicit, permissioned "sweep trapped assets" pathway — mirroring the Curve Proxy `transferTokens` recommendation from the seed report — where a governance/root origin (or a well-known sovereign account with a resolvable signing path) can submit `claim_assets` on the destination chain for the accumulation account's aliased trap origin, and route the recovered assets back to the accumulation account or a designated treasury.

### Proof of Concept
The vulnerability is provable purely from code invariants, matching the existing rollback test that only checks the *local-failure* rollback path but not what happens when the local leg succeeds and the *remote* leg fails: [8](#0-7) 

No test in the repository exercises or reconciles the case where `Outcome::Complete` is returned locally (burning the funds and returning `Ok(())` to the pallet, which emits `ForwardSucceeded`) while the destination `DepositAsset` subsequently fails, and no `claim_assets`-driven recovery test exists for the accumulation account's derived trap origin — confirming that this failure mode has no in-repo mitigation, consistent with the forwarder's own doc comment acknowledging "no automatic recovery path."

	fn forward(source: AccountId, amount: Balance) -> Result<(), ()> {
		let dest = Dest::get();
		let asset = Asset { id: AssetId(NativeAsset::get()), fun: Fungible(amount.into()) };
		let beneficiary: Location = StagingLocation::get().into_location();

		let remote_xcm = Xcm(vec![DepositAsset { assets: Wild(AllCounted(1)), beneficiary }]);

		// The XCM flow: `ReceiveTeleportedAsset → AliasOrigin(source) → UnpaidExecution →
		// DepositAsset`. `preserve_origin: true` causes `InitiateTransfer` to prepend
		// `AliasOrigin(source_location)` to the remote XCM.
		let xcm: Xcm<XcmConfig::RuntimeCall> = Xcm(vec![
			UnpaidExecution { weight_limit: WeightLimit::Unlimited, check_origin: None },
			DescendOrigin(Junction::AccountId32 { network: None, id: source.into() }.into()),
			WithdrawAsset(asset.into()),
			InitiateTransfer {
				destination: dest,
				remote_fees: None,
				preserve_origin: true,
				assets: BoundedVec::truncate_from(alloc::vec![AssetTransferFilter::Teleport(
					Wild(AllCounted(1))
				),]),
				remote_xcm,
			},
		]);

		with_transaction(|| -> TransactionOutcome<Result<(), DispatchError>> {
			let outcome = XcmExecutor::<XcmConfig>::prepare_and_execute(
				Location::here(),
				xcm,
				&mut [0u8; 32],
				Weight::MAX,
				Weight::MAX,
			);

			match outcome {
				Outcome::Complete { .. } => TransactionOutcome::Commit(Ok(())),
				exec_error => {
					tracing::debug!(
						target: LOG_TARGET,
						?exec_error,
						"accumulate-forward: XCM execution failed"
					);

					TransactionOutcome::Rollback(Err(DispatchError::Other("XCM execution failed")))
				},
			}
		})
		.map_err(|_| ())
	}

/// Verify that when the XCM router fails (simulating a mid-program failure after `WithdrawAsset`
/// has debited the source account), `forward` rolls back all storage changes via
/// `with_transaction`. Both the source balance and total issuance must remain unchanged.
#[test]
fn forward_rolls_back_balance_and_issuance_on_xcm_failure() {
	let source: AccountId = AccountId32::from([1u8; 32]);
	let initial_balance = 1_000u128;

	new_test_ext(source.clone(), initial_balance).execute_with(|| {
		let initial_issuance = Balances::total_issuance();

		ROUTER_SHOULD_FAIL.with(|f| f.set(true));
		let result = TeleportForwarderForAccountId32::<
			TestXcmConfig,
			AssetHubLocation,
			HereLocation,
			AccumulationInterior,
		>::forward(source.clone(), 500u128);
		ROUTER_SHOULD_FAIL.with(|f| f.set(false));

		assert!(result.is_err(), "expected forward to fail when router fails");
		assert_eq!(
			Balances::balance(&source),
			initial_balance,
			"source balance must be unchanged after XCM failure"
		);
		assert_eq!(
			Balances::total_issuance(),
			initial_issuance,
			"total issuance must be unchanged after XCM failure"
		);
