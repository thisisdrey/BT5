### Title
Cross-StackerDB-contract signature replay due to `SlotMetadata` digest omitting the contract identifier - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` binds a signer's signature only to `(slot_id, slot_version, data_hash)`. It does not include the StackerDB smart-contract identifier (i.e., message type / `MessageSlotID`). Because the same signer set occupies identical slot IDs across the sibling per-reward-cycle contracts (`BlockResponse`, `StateMachineUpdate`, `BlockPreCommit`), a validly-signed chunk captured from one of these StackerDB replicas can be resubmitted verbatim as a chunk for a *different* message-type contract and pass signature verification there, as long as its `slot_version` is fresher than what the target contract currently has stored.

### Finding Description
`StackerDBChunkData`/`SlotMetadata` are authenticated purely by recovering the public key from `auth_digest()` and hashing it to compare against the expected slot owner address for the *target* `smart_contract_id` — the contract itself is never part of what's signed:

```rust
fn auth_digest(&self) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
``` [2](#0-1) 

Both the local `try_replace_chunk` write path and the network `validate_received_chunk` path fetch the expected signer for the *specific contract* passed in, then call `.verify(&addr)`, which only checks the digest above — it never checks that the signature/digest is scoped to that contract:

```rust
let slot_validation = self
    .get_slot_validation(smart_contract, slot_desc.slot_id)?
    ...
if !slot_desc.verify(&slot_validation.signer)? {
    return Err(net_error::BadSlotSigner(...));
}

Per-reward-cycle, the signer set and slot ordering are identical across the three sibling contracts (`signers-<cycle>-1` for `BlockResponse`, `-2` for `StateMachineUpdate`, `-3` for `BlockPreCommit`) since they are all derived from the same signer registration [1](#0-0) , meaning `get_slot_signer(contract_A, slot_id) == get_slot_signer(contract_B, slot_id)` for the same `slot_id` in the common case. This equality that should hold ("chunk authenticated for contract A" vs "chunk authenticated for contract B") is broken: the signature says nothing about which contract it belongs to.

### Impact Explanation
An attacker who observes a validly-signed chunk broadcast to one signer StackerDB contract (e.g. a `BlockPreCommit` chunk) can replay its raw bytes into a sibling contract for the same reward cycle (e.g. `StateMachineUpdate` or `BlockResponse`), as long as the target slot's stored `slot_version` for that signer is lower than the replayed chunk's version. The replayed chunk will pass `BadSigner`/`verify` checks and get accepted and further relayed to peers via the normal StackerDB gossip machinery, since the write and gossip paths treat it as legitimately signed data. This is a case of forged/mismatched data (wrong-typed message) being accepted and propagated as canonical for a target message channel it was never intended for, satisfying the "forged gossip relayed" / non-canonical-state-served-as-canonical category. Concretely, it could let an adversary inject a stale/foreign `BlockPreCommit` or `StateMachineUpdate` payload bytes into another slot type that consuming code (`SignerMessage` deserializer, `stackerdb_listener.rs`) will attempt to parse — most likely resulting in deserialization failure/log noise rather than a type-confused acceptance, since `SignerMessage` payloads for different types have distinct outer serialization prefixes, so the practical exploitation is bounded to slot corruption/DoS on that replica's read path rather than acceptance as a semantically different, dangerous message.

### Likelihood Explanation
Exploitation requires: (1) the attacker to observe a legitimately signed chunk on one signer contract (trivial — these are broadcast openly over StackerDB gossip / can be fetched via `list_chunks`/`get_chunks` RPC with no auth) [5](#0-4) , and (2) the target sibling contract's stored slot version for that signer to be lower than the replayed version, which is often true immediately after a reward-cycle boundary or whenever cross-contract slot versions drift. No node secret, signer key, or admin role is needed — only replay of publicly-observable network traffic, so likelihood is moderate-to-high for causing acceptance of out-of-context chunk data, though the ultimate payload utility is limited by the deserializer's type-prefix checks in the consuming `SignerMessage` code.

### Recommendation
Include the StackerDB `smart_contract_id` (or at minimum, the `MessageSlotID` message type + reward cycle) as part of the data committed to in `SlotMetadata::auth_digest()`, so a signature is cryptographically scoped to the specific StackerDB contract it was produced for. This closes the cross-contract replay path analogous to fixing the Oathkeeper cache to check requested scope rather than only expiration.

### Proof of Concept
1. Capture a validly signed `StackerDBChunkData` for `slot_id=S`, `slot_version=V`, from the `BlockPreCommit` contract for reward cycle `R` for signer `X` (e.g., via `StackerDBSession::get_chunk` on the `.signers-R-3` contract).
2. Note `X` also owns `slot_id=S` in the sibling `.signers-R-2` (`StateMachineUpdate`) contract for the same reward cycle (true whenever the signer set/order is identical, which is standard).
3. If `.signers-R-2` slot `S`'s currently stored version is `< V`, POST the exact captured chunk bytes (`slot_id=S`, `slot_version=V`, `sig`, `data`) to `.signers-R-2`'s StackerDB endpoint.
4. `validate_received_chunk`/`try_replace_chunk` recovers the same public key hash `X` from `slot_metadata.verify(&addr)` and accepts/stores/gossips the chunk, even though it was never signed for this contract — confirming the digest is not contract-scoped [6](#0-5) .

/// Trait for connecting to and querying a signer Stacker DB replica
pub trait SignerSession {
    /// connect to the replica
    fn connect(
        &mut self,
        host: String,
        stackerdb_contract_id: QualifiedContractIdentifier,
    ) -> Result<(), RPCError>;
    /// query the replica for a list of chunks
    fn list_chunks(&mut self) -> Result<Vec<SlotMetadata>, RPCError>;
    /// query the replica for zero or more chunks
    fn get_chunks(
        &mut self,
        slots_and_versions: &[(u32, u32)],
    ) -> Result<Vec<Option<Vec<u8>>>, RPCError>;
    /// query the replica for zero or more latest chunks
    fn get_latest_chunks(&mut self, slot_ids: &[u32]) -> Result<Vec<Option<Vec<u8>>>, RPCError>;
    /// Upload a chunk to the stacker DB instance
    fn put_chunk(&mut self, chunk: &StackerDBChunkData) -> Result<StackerDBChunkAckData, RPCError>;

    /// Get a single chunk with the given version
    /// Returns Ok(Some(..)) if the chunk exists
    /// Returns Ok(None) if the chunk with the given version does not exist
    /// Returns Err(..) on transport error
    fn get_chunk(&mut self, slot_id: u32, version: u32) -> Result<Option<Vec<u8>>, RPCError> {
        let mut chunks = self.get_chunks(&[(slot_id, version)])?;
        // check if chunks is empty because [0] and remove(0) panic on out-of-bounds
        if chunks.is_empty() {
            return Ok(None);
        }
        // swap_remove breaks the ordering of latest_chunks, but we don't care because we
        //  only want the first element anyways.
        Ok(chunks.swap_remove(0))
    }
