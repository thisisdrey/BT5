Audit Report

## Title
Reward for cross-chain message delivery is paid without checking the proven delivery `success` status - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`process_delivery_receipt` verifies the Ethereum event proof (gateway match, log validity via `T::Verifier::verify`) but never reads the `success` field of the decoded `DeliveryReceipt`. As a result, a delivery receipt proving that message execution on Ethereum *failed* (`success = false`) still triggers full reward payout to the relayer and permanent deletion of the `PendingOrder`, identical to a successful delivery.

## Finding Description
`submit_delivery_receipt` calls `T::Verifier::verify` on the event log/proof, decodes it into a `DeliveryReceipt` via `DeliveryReceipt::try_from`, and calls `process_delivery_receipt` [1](#0-0) . The `DeliveryReceipt` struct carries a `success: bool` field decoded straight from the `InboundMessageDispatched` Solidity event log [2](#0-1) .

Inside `process_delivery_receipt`, only `receipt.gateway` is checked against `T::GatewayAddress`; `receipt.nonce` is used purely to fetch the `PendingOrder` from storage; `receipt.success` is never read or branched on anywhere in the function [3](#0-2) . The reward is paid unconditionally whenever `order.fee > 0`, and the order is removed regardless of the proven outcome.

The `PendingOrder` struct itself has no success/failure tracking field — only `nonce`, `block_number`, and `fee` [4](#0-3) , so there is no other storage state or code path in the pallet that could compensate for this omission.

## Impact Explanation
Any relayer whose relayed message fails execution on Ethereum (dispatch reverts on the Gateway contract, emitting `InboundMessageDispatched` with `success = false`) can submit that receipt via the public `submit_delivery_receipt` extrinsic and still receive the full reward (`order.fee`) via `T::RewardPayment::register_reward`, and the `PendingOrder` is permanently removed with no other in-protocol path to retry or correctly resolve the failed delivery. This is an unconditional payout for undelivered/failed work — a duplicate/incorrect settlement that violates conservation of value between work performed and reward paid, satisfying the "public underpriced work" / "duplicate settlement or payout" impact category.

## Likelihood Explanation
This requires no malicious peer, validator, or compromised relayer assumption — any ordinary relayer submitting a legitimately obtained, cryptographically valid proof of a failed dispatch (e.g., due to insufficient gas or a reverting command on the Ethereum side, which is a normal non-adversarial occurrence) receives the payout regardless. This makes the flaw trivially and repeatably triggerable under normal operation, not merely a theoretical edge case.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` when `receipt.success == true`. For `success == false`, avoid paying the full relayer fee (e.g., emit a distinct `MessageDeliveryFailed` event and/or handle partial refund logic), and reconsider whether the `PendingOrder` should be retried instead of unconditionally removed.

## Proof of Concept
1. A message is queued via `do_process_message`, creating a `PendingOrder { nonce, fee, block_number }` in storage.
2. The relayer submits the message to Ethereum; execution reverts/fails on the Gateway, but the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. The relayer obtains a valid proof for this log and calls `submit_delivery_receipt` on-chain.
4. `T::Verifier::verify` succeeds (proof is legitimate); `DeliveryReceipt::try_from` decodes `success = false`.
5. `process_delivery_receipt` checks only `receipt.gateway`, fetches the `PendingOrder` by `receipt.nonce`, and unconditionally calls `T::RewardPayment::register_reward(&reward_account, ..., order.fee)`, then removes the order and emits `MessageDelivered`. The relayer is paid in full despite the proven delivery failure.

#[derive(Copy, Clone, Encode, Decode, Eq, PartialEq, Debug, TypeInfo)]
pub enum DeliveryReceiptDecodeError {
	DecodeLogFailed,
	DecodeAccountFailed,
}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
