### Title
Deposit-token dust transfer fills victim's `MAX_TOKENS_PER_USER` account list, permanently blocking new deposits and collateral top-ups - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`Pool` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` on the combined number of deposit and debt tokens an account may hold, reverting with `UserReachedMaxTokens` inside `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount`. `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance was zero, and `transfer()` lets any holder push dust to any address without consent. An unprivileged attacker can therefore deposit a dust amount of each listed collateral and `transfer` it to a victim, filling all 30 slots of the victim's per-account lists, after which every subsequent `deposit`, first-time `transfer` receipt, and debt `issue`/`mint` for the victim reverts.

### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts once `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30` [1](#0-0) .
- `DepositToken.transfer` calls `_transfer`, which pushes the token onto the recipient's account list whenever the recipient previously held zero, propagating the `UserReachedMaxTokens` revert to the sender of the *next* action, not the griefer [2](#0-1) [3](#0-2) .
- The same addition happens on `_mint`, so `deposit(..., onBehalfOf_ = victim)` also forcibly occupies a slot [4](#0-3) .
- Crucially, removal only happens when a balance returns to zero; the victim cannot clear entries cheaply because each dust token must be withdrawn/transferred individually, and the attacker can refill a slot in the same block via a `deposit` of a new token `onBehalfOf_` the victim or a frontrun `transfer` — the victim can never reach below 30 permanently while the attacker is active.
- Debt tokens behave the same way via `DebtToken` → `addToDebtTokensOfAccount`, so while the list is full the victim also cannot mint any new synthetic token they don't already hold [5](#0-4) .

### Impact Explanation
A targeted account is denied all protocol ingress: it cannot deposit any collateral it does not already hold (reverts in `_mint` → `addToDepositTokensOfAccount`), cannot receive msdTOKEN transfers of new tokens, and cannot mint new synthetic debt. For a victim with an open position approaching the liquidation threshold, topping up with a *different* collateral type (the common rescue path when the existing collateral's price is crashing) is impossible, so the position is forced into liquidation and the victim loses collateral to the liquidation fee/seizure. This is a temporary-to-permanent freezing of funds plus forced liquidation, matching the availability-impact class of CVE-2025-50102 (attacker-triggered denial of service of a core function).

### Likelihood Explanation
The attack is fully permissionless: `deposit` is open to any EOA, `transfer` requires no allowance from the victim, and the attacker only needs dust balances of up to 30 listed deposit tokens (30 × ~minimal unit ≈ negligible cost). No privileged role, oracle manipulation, or third-party failure is required — only public entry points on production contracts. The cap cannot be raised per-user and there is no opt-out or whitelisting of inbound transfers.

### Recommendation
- Allow the account itself (or a keeper on its behalf) to remove arbitrary entries from `depositTokensOfAccount`/`debtTokensOfAccount`, e.g. a `sweepAccountList(token)` callable by the account that validates zero balance.
- Alternatively, decouple the revert from the transfer path: make `addTo*OfAccount` non-reverting (return early) when the cap is reached and only enforce the cap on `deposit`/borrow ingress, so forced dust cannot block the victim's own actions; note that the victim's `deposit`/`issue` should still be enforceable separately.
- Consider only counting tokens the account *explicitly deposited* toward the cap, or making `depositTokensOfAccount` enumeration lazy (iterate `depositTokens` and filter by balance) so the list cannot be griefed.

### Proof of Concept
Hardhat outline (mirroring `test/Pool.test.ts` setup):

```ts
// Assume pool with N >= 30 deposit tokens dt[0..29] registered.
const victim = alice.address;
const max = await pool.MAX_TOKENS_PER_USER(); // 30

for (let i = 0; i < max; ++i) {
  // 1. Attacker deposits 1 wei of underlying on behalf of itself
  await underlying[i].mint(attacker.address, 1);
  await underlying[i].connect(attacker).approve(dt[i].address, 1);
  await dt[i].connect(attacker).deposit(1, attacker.address);
  // 2. Attacker pushes the dust msdTOKEN to the victim
  await dt[i].connect(attacker).transfer(victim, 1);
}

// Victim's lists are now full
expect((await pool.getDepositTokensOfAccount(victim)).length).eq(30);

// Victim cannot deposit a 31st collateral it doesn't hold
await underlying31.mint(victim, parseEther('1'));
await underlying31.connect(alice).approve(dt31.address, parseEther('1'));
await expect(dt31.connect(alice).deposit(parseEther('1'), victim))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');

// Victim cannot mint a synthetic token it doesn't hold
await expect(pool.connect(alice) /* issue path via DebtToken.issue */)
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');

// Any new forced dust re-adds a slot in the same block,
// so the victim cannot permanently free space while attacker is live.
```

Reproduction note: a Foundry/Hardhat fork against a deployed pool (e.g. Base/Optimism `Pool` proxies in `deployments/`) with ≥30 listed deposit tokens confirms the revert chain `deposit → _mint → addToDepositTokensOfAccount → UserReachedMaxTokens`. If a deployed pool currently lists fewer than 30 deposit/debt tokens, the attack still caps the victim's usable slots to whatever is reachable (e.g., a pool with 12 tokens leaves the victim only 30 − 12 slots and fully blocks them after receiving one of each).
