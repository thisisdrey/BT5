### Title
`PostReceivePack` has no idle/negotiation timeout, allowing a stalled push stream to hold a `git-receive-pack` process and gRPC handler open indefinitely - ([File: internal/gitaly/service/smarthttp/receive_pack.go])

### Summary
`PostReceivePack` reads the request stream via `streamio.NewReader(stream.Recv)` and simply calls `cmd.Wait()` after spawning `git-receive-pack --stateless-rpc`, with no per-RPC deadline, ticker, or idle-timeout enforcement anywhere in the handler. This is in stark contrast to `git-upload-pack`/`git-upload-archive` over SSH, which explicitly install a negotiation timeout (`runUploadCommand`, `uploadPackRequestTimeoutTickerFactory`) specifically to bound how long a client can keep a request open before completing negotiation.

### Finding Description
`PostReceivePack` (`internal/gitaly/service/smarthttp/receive_pack.go:23-67`) receives the first request, validates it, and calls `postReceivePack`, which wires `stdin := streamio.NewReader(func() ([]byte, error) { resp, err := stream.Recv(); return resp.GetData(), err })` directly into `git-receive-pack --stateless-rpc`'s stdin [1](#0-0) , and then blocks on `cmd.Wait()` [2](#0-1) .

`git-receive-pack` reads the pkt-line command list and pack data from stdin, and if the client never sends the trailing flush/pack data (i.e. never completes stdin), the process blocks reading indefinitely, and `stream.Recv()`/`cmd.Wait()` block along with it. Nothing in this call path installs:
- A context deadline / `context.WithTimeout` on the RPC handling.
- A ticker-based negotiation timeout (as `runUploadCommand` does for `upload-pack`/`upload-archive`, see `internal/gitaly/service/ssh/upload_command.go:26-103` and `internal/gitaly/service/ssh/upload_pack.go:100-114`).
- Any read-monitor equivalent to `pktline.NewReadMonitor` used for uploading commands.

The gRPC server is configured only with `grpc.KeepaliveParams(keepalive.ServerParameters{Time: 5 * time.Minute})` [3](#0-2) , which is a keepalive ping interval for detecting dead TCP connections, not an idle-stream/read timeout; a connection that keeps answering (or simply stays open, e.g. via an intervening proxy like Workhorse) is not forcibly closed by this setting. There is likewise no `Timeout` field set on `KeepaliveEnforcementPolicy`/`KeepaliveParams` that would terminate an unresponsive-but-open stream. The only other backpressure mechanism, the `[[concurrency]]` limiter (`internal/grpc/middleware/limithandler`), is opt-in per-RPC configuration (`doc/backpressure.md:15-52`) and is not applied by default — and even when configured, `max_queue_wait` only bounds time spent *waiting to enter* the handler, not time spent *inside* an already-admitted handler, exactly the scenario here since the limiter's semaphore is held for the duration of `f()` (the RPC handler) once acquired [4](#0-3) .

By contrast, `runUploadCommand` explicitly documents and implements protection against exactly this class of issue for `upload-pack`/`upload-archive`: "It installs a timeout such that we can address time-of-check-to-time-of-use-style races... use a timeout ticker such that the negotiation phase is time-boxed" [5](#0-4) . No equivalent protection exists for `receive-pack` in either the smarthttp (`internal/gitaly/service/smarthttp/receive_pack.go`) or SSH (`internal/gitaly/service/ssh/receive_pack.go`) implementations — both simply call `cmd.Wait()` unconditionally.

### Impact Explanation
An attacker who can push to a repository they control (no special GitLab role required) can open a `PostReceivePack` push and send a valid first request (with `GlId`, valid `Repository`), then stall the stdin stream indefinitely without ever completing the pack/pkt-line sequence. This:
- Keeps a `git-receive-pack --stateless-rpc` process running and consuming a process slot, memory, and file descriptors for as long as the underlying HTTP/gRPC connection stays open.
- Keeps a Gitaly-side goroutine and gRPC stream handler blocked in `cmd.Wait()`.
- If concurrency limiting is configured for this RPC (`max_per_repo`), holds the semaphore slot, blocking other legitimate pushes/fetches to the same repository from making progress (queueing until `max_queue_wait`, after which they are rejected).

Repeating this with many concurrent stalled pushes (across many repos the attacker owns/forks) can exhaust Gitaly's process table, memory, or file descriptors, matching the GitLab bounty "DoS / resource exhaustion" class for a crafted pktline/pack stream.

### Likelihood Explanation
This requires only unprivileged push access to a repository the attacker owns (or a fork/import), which is directly consistent with the described threat model. The exploit is straightforward and repeatable: open the RPC, send the mandatory first request, then withhold data (or send a byte occasionally to defeat naive idle detection, though none exists here). No special server misconfiguration is required — the default Gitaly configuration has no timeout or concurrency limit for `PostReceivePack` unless an operator explicitly adds a `[[concurrency]]` stanza, and even that stanza does not bound in-progress handler duration. The severity is bounded by how long the outer transport (e.g. Workhorse/HAProxy/LB timeouts) permits an idle HTTP connection to remain open, which is outside Gitaly's control and not a mitigating factor within Gitaly itself.

### Recommendation
Add an explicit idle/negotiation timeout to `PostReceivePack` (and `SSHReceivePack`), analogous to `runUploadCommand`'s ticker-based negotiation timeout:
- Introduce a configurable timeout (e.g. `Timeout.ReceivePackNegotiation`, mirroring `Timeout.UploadPackNegotiation`) and a read-monitor/ticker that cancels the command's context if no forward progress (e.g. no new pkt-line data) is observed within the configured window.
- Alternatively/additionally, enforce a hard maximum RPC duration bound at the gRPC layer (server-side deadline) or via a stream-idle-read timeout wrapping `stream.Recv()`, so that a stalled client cannot hold `cmd.Wait()` open indefinitely.
- Ensure the concurrency limiter documentation/config recommends enabling `[[concurrency]]` with `max_per_repo` and reasonable `max_queue_wait` for `PostReceivePack`/`SSHReceivePack` as a stopgap, while noting it does not address in-handler stalls.

```go
// internal/gitaly/service/smarthttp/receive_pack_test.go (illustrative)
func TestPostReceivePack_StalledStreamNeverTimesOut(t *testing.T) {
    cfg := testcfg.Build(t)
    cfg.SocketPath = runSmartHTTPServer(t, cfg)

    repo, _ := gittest.CreateRepository(t, testhelper.Context(t), cfg)

    client, conn := newSmartHTTPClient(t, cfg.SocketPath, cfg.Auth.Token)
    defer testhelper.MustClose(t, conn)

    ctx := testhelper.Context(t) // no deadline set by attacker-controlled client
    stream, err := client.PostReceivePack(ctx)
    require.NoError(t, err)

    // First request: only Repository/GlId, as required.
    require.NoError(t, stream.Send(&gitalypb.PostReceivePackRequest{
        Repository: repo,
        GlId:       "user-1",
    }))

    // Attacker sends a partial pkt-line command (e.g. a truncated "command" line)
    // and then never sends more data / never closes the stream.
    require.NoError(t, stream.Send(&gitalypb.PostReceivePackRequest{
        Data: []byte("003fincomplete-command-without-flush-or-pack-data"),
    }))

    // No further Send/CloseSend call — simulating a client that "never sends flush".
    // Expectation absent a fix: stream.Recv() below blocks forever (test would hang/timeout),
    // demonstrating that PostReceivePack has no idle timeout of its own and relies solely
    // on the caller-supplied context deadline (attacker-controlled) or external transport
    // timeouts to eventually terminate the handler.
    done := make(chan struct{})
    go func() {
        _, _ = stream.Recv()
        close(done)
    }()

    select {
    case <-done:
        t.Fatal("expected PostReceivePack to still be blocked without an idle timeout")
    case <-time.After(5 * time.Second):
        // Confirms the handler and underlying git-receive-pack process are still alive
        // and blocked after 5s with no built-in timeout firing.
    }
}
```
Expected result on the current code: the handler never returns on its own (no `DeadlineExceeded` is produced internally); it only terminates when the attacker's own context/connection is closed or an external proxy times it out — unlike the analogous `TestUploadPackWithSidechannel_timeout` test for `upload-pack`, which asserts a `structerr.NewDeadlineExceeded("running upload-pack: waiting for negotiation: context canceled")` is returned by the server itself [6](#0-5) , demonstrating the missing equivalent protection for `receive-pack`.

```go
// runUploadCommand runs an uploading command like git-upload-pack(1) or git-upload-archive(1). It serves multiple
// purposes:
//
//   - It sets up a large buffer reader such that we can write the data more efficiently.
//
//   - It logs how many bytes have been sent.
//
//   - It installs a timeout such that we can address time-of-check-to-time-of-use-style races. Otherwise it would be
//     possible to open the connection early, keep it open for an extended amount of time, and only do the negotiation of
//     what is to be sent at a later point when permissions of the user might have changed.
func (s *server) runUploadCommand(
	rpcContext context.Context,
	repo gitcmd.RepositoryExecutor,
	stdin io.Reader,
	stdout, stderr io.Writer,
	timeoutTicker helper.Ticker,
	boundaryPacket []byte,
	sc gitcmd.Command,
	opts ...gitcmd.CmdOpt,
) error {
	ctx, cancelCtx := context.WithCancel(rpcContext)
	defer cancelCtx()

	var stderrBuilder strings.Builder
	stderr = io.MultiWriter(stderr, &stderrBuilder)

	stdoutCounter := &helper.CountingWriter{W: stdout}
	// Use large copy buffer to reduce the number of system calls
	stdout = &largeBufferReaderFrom{Writer: stdoutCounter}

	stdinPipe, monitor, cleanup, err := pktline.NewReadMonitor(ctx, stdin, s.logger)
	if err != nil {
		return fmt.Errorf("create monitor: %w", err)
	}

	cmd, err := repo.Exec(ctx, sc, append([]gitcmd.CmdOpt{
		gitcmd.WithStdin(stdinPipe),
		gitcmd.WithStdout(stdout),
		gitcmd.WithStderr(stderr),
		gitcmd.WithFinalizer(func(context.Context, *command.Command) { cleanup() }),
	}, opts...)...)
	stdinPipe.Close() // this now belongs to cmd
	if err != nil {
		cleanup()
		return fmt.Errorf("starting command: %w", err)
	}

	go monitor.Monitor(ctx, boundaryPacket, timeoutTicker, cancelCtx)

	if err := cmd.Wait(); err != nil {
		// The read monitor will cancel the local `ctx` when we do not observe a specific packet before the
		// timeout ticker ticks. This is done to address a time-of-check-to-time-of-use-style race, where the
		// client opens a connection but doesn't yet perform the negotiation of what data the server should
		// send. Because access checks only happen at the beginning of the call, it may be the case that the
		// client's permissions have changed since the RPC call started.
		//
		// To address this issue, we thus timebox the maximum amount of time between the start of the RPC call
		// and the end of the negotiation phase. While this doesn't completely address the issue, it's the best
		// we can reasonably do here.
		//
		// To distinguish cancellation of the overall RPC call and a timeout of the negotiation phase we use two
		// different contexts. In the case where the local context has been cancelled, we know that the reason
		// for cancellation is that the negotiation phase did not finish in time and thus return a more specific
		// error.
		if ctx.Err() != nil && rpcContext.Err() == nil {
			return structerr.NewDeadlineExceeded("waiting for negotiation: %w", ctx.Err())
		}
```
