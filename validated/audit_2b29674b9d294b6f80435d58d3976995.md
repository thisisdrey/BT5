### Title
Resolver refunds full amount on malformed `ft_transfer_call` success, double-crediting `sender_id` after real tokens already left custody - (File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs)

### Summary
In `ft_resolve_withdraw`, when the `ft_transfer_call` promise resolves `Ok` but the returned JSON body cannot be parsed as `U128`, the code treats `used = 0` and refunds the *entire* `amount` back to `sender_id`. A malicious, attacker-controlled `token` contract can perform the real token transfer to `receiver_id` while intentionally returning a malformed body, causing Defuse to both let the tokens leave custody and re-credit `sender_id`'s Verifier balance for the same amount.

### Finding Description
Binding: `withdraw_debited(sender_id) == amount` should equal `tokens_delivered(receiver_id) + resolver_refund(sender_id)`, i.e. total accounted for one withdrawal attempt must equal `amount`, not `2 * amount`.

Path: `internal_ft_withdraw` (`contracts/defuse/src/contract/tokens/nep141/withdraw.rs:60-74`) immediately debits `owner_id`'s (== `sender_id`) Verifier balance by `amount` via `self.withdraw(...)`, then schedules `do_ft_withdraw` → real `token.ft_transfer_call(receiver_id, amount, memo, msg)` (`contracts/defuse/src/contract/tokens/nep141/withdraw.rs:136-150`), followed by the `#[private]` callback `ft_resolve_withdraw` (`contracts/defuse/src/contract/tokens/nep141/withdraw.rs:157-194`):

```rust
let used = if is_call {
    match promise_result_checked_json::<U128>(0) {
        Ok(Ok(used)) => used.0.min(amount.0),
        Ok(Err(_deserialize_err)) => 0,
        Err(_) => amount.0,
    }
} ...
``` [1](#0-0) 

Since `Nep141TokenId` wraps an arbitrary, unwhitelisted `AccountId`, the attacker can deploy their own FT contract as `token`, then call the standard `ft_withdraw` flow with `msg: Some(...)` so `is_call = true`. Their FT contract's `ft_transfer_call` handler performs the real internal transfer of `amount` from Defuse's account to `receiver_id` (moving real balance in the FT contract's own ledger), but returns a syntactically valid promise success carrying a body that is not a valid `U128` (e.g. `"not-a-u128"`). This hits `Ok(Err(_deserialize_err)) => 0`, so `refund = amount.0` and `self.deposit(sender_id, [(Nep141TokenId(token), amount)], REFUND_MEMO)` re-credits the full amount [2](#0-1) .

Net effect on `sender_id`'s Verifier ledger: debited `amount` at withdraw time, then credited `amount` back at resolve time — net zero change — while the real FT contract already moved `amount` out of Defuse's custody to `receiver_id`. Defuse's internal claim for that `TokenId` now exceeds what it actually custodies by `amount`, even though nothing "failed to settle." This is exactly a resolver credit that does not match what failed to settle, and creates a Verifier-wide balance mismatch (owes more than it custodies) for that `TokenId`.

The existing comment/guard only addresses the opposite direction — treating `Err(_)` (unreadable promise result, e.g. insufficient gas) as full success to avoid double-crediting due to a known NEP-141 gas-forwarding vulnerability — but leaves the `Ok(Err(_deserialize_err))` branch unguarded against an attacker-controlled callee returning a bogus-but-parseable-as-success body while still executing the real transfer.

### Impact Explanation
The attacker's own Verifier balance for a `TokenId` they fully control becomes over-claimed relative to Defuse's actual custody of that token: Defuse's ledger says `sender_id` still holds `amount`, while the underlying FT contract shows Defuse already parted with `amount` to `receiver_id`. This phantom balance can then be spent/transferred/swapped to other counterparties inside Defuse via ordinary signed intents, letting the attacker extract real value (other users' genuine tokens) in exchange for a claim that is not actually backed, i.e. the Verifier ends up owing more of that `TokenId` than it custodies. This matches the Critical category "a refund or resolver credit that does not match what failed to settle" / "a batch whose balance changes do not net to zero so the Verifier owes more than it custodies." It is repeatable per withdraw call against any `TokenId` the attacker controls the underlying contract for.

### Likelihood Explanation
Fully within the unprivileged attacker model: deploy a custom FT contract, deposit into Defuse under that `TokenId`, then call the public `ft_withdraw` (`contracts/defuse/src/contract/tokens/nep141/withdraw.rs:24-51`) with `msg: Some(...)`. No role, relayer key, or victim key is required — only control of the `token` contract used for the withdrawal. Cost is minimal (storage/gas), and the exploit is repeatable across any number of self-issued tokens and withdrawals.

### Recommendation
Do not treat an unparseable-but-`Ok` `ft_transfer_call` result as "nothing was used." Either (a) require the returned body to parse as `U128` and panic/abort the refund path if it doesn't (treating malformed success like a protocol violation rather than a failure to settle), or (b) refuse to refund on `Ok(Err(_deserialize_err))` the same way `Err(_)` is handled, only refunding when the token contract's callback truly could not be executed, not when it succeeded with a body Defuse cannot interpret.

### Proof of Concept
`cargo test` / `near-workspaces` sandbox plan:
1. Deploy a stub FT contract whose `ft_transfer_call` performs the real internal transfer of `amount` from the caller's tracked balance to `receiver_id`, but returns the literal string `"not-a-u128"` instead of a `U128` JSON on success.
2. Deposit `amount` of this stub token into Defuse for `sender_id` via `ft_transfer_call`/`ft_on_transfer`.
3. Call `ft_withdraw(token, receiver_id, amount, memo, msg=Some("x"))` as `sender_id`, driving `internal_ft_withdraw` → `do_ft_withdraw` → the stub's `ft_transfer_call` → `ft_resolve_withdraw`.
4. Assert both sides of the binding after resolution:
   - `token_balances[sender_id][Nep141TokenId(token)]` in Defuse's ledger equals `amount` (fully refunded), via `mt_balance_of`.
   - The stub token contract's own internal storage shows `receiver_id` actually received `amount` (real transfer happened).
   - Therefore total accounted (`amount` refunded in Defuse + `amount` delivered to `receiver_id`) == `2 * amount`, while only `amount` was ever debited/backed, proving the SETTLEMENT binding is violated.
