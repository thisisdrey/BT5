### Title
Unprivileged dust-transfer fills victim's per-account token list, permanently blocking deposits and new borrows (`UserReachedMaxTokens`) - (File: contracts/Pool.sol)

### Summary
`Pool.addToDepositTokensOfAccount` and `Pool.addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once an account's combined deposit+debt token count reaches `MAX_TOKENS_PER_USER` (30). Any unprivileged attacker can push arbitrary `DepositToken` dust to a victim via the public `DepositToken.transfer`/`transferFrom` (the locked-balance check only constrains the *sender*; `_transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` on first receipt). Once the victim's list is full, every path that mints a new token entry for them — `deposit` (`_mint` → `addToDepositTokensOfAccount`) and `DebtToken.issue`/`mint` (`addToDebtTokensOfAccount`) — reverts. If the victim has debt, `unlockedBalanceOf` is capped (and is 0 when unhealthy), so the victim cannot transfer the dust back out to clear slots, making the freeze permanent until their position is closed or liquidated.

### Finding Description
Bug-class analog: CVE-2024-21171 is an availability/DoS flaw (hang/crash of the server via a reachable code path). The Metronome analog is a liveness DoS on a target account's position-management surface.

Reachability:

1. Attacker deposits dust of each registered `DepositToken` into their own account (`DepositToken.deposit`, only needs `onlyIfDepositTokenExists`, no privileges).
2. Attacker calls `depositToken.transfer(victim, 1)` for every deposit token. In `DepositToken._transfer` (DepositToken.sol:498-526) the recipient-side `pool.addToDepositTokensOfAccount(recipient_)` runs whenever `_recipientBalanceBefore == 0`, and `Pool.addToDepositTokensOfAccount` (Pool.sol:216-220) only checks `onlyIfAdditionWillNotReachMaxTokens` — there is no consent/opt-in on the receiver.
3. When `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) >= 30` (Pool.sol:143-148), all subsequent adds revert with `UserReachedMaxTokens`.

Broken invariant: availability of per-account deposit/borrow functions (liveness).

Why mitigations don't stop it:

- `transfer`/`transferFrom` only enforce `_revertIfLocked` on the *sender* (DepositToken.sol:348-376); the receiver cannot refuse.
- Clearing slots requires the victim to transfer dust out, but `unlockedBalanceOf` (DepositToken.sol:383-398) returns 0 when `_issuableInUsd == 0` — i.e. exactly for the undercollateralized/unhealthy victim who most needs to deposit more collateral. Even a healthy victim with debt has unlocked balance capped below full balance, so at least some dust slots are non-clearable.
- No `pause`/`shutdown`/`SynthContext` guard applies; `transfer` is open to any EOA (or via `Operator.execute` for meta-senders).

### Impact Explanation
A victim with an open debt position can be permanently prevented from (a) depositing any new collateral type and (b) borrowing any new synth. If the victim's position deteriorates, they cannot top-up with a collateral type they don't already hold, and cannot clear the dust slots (unlocked balance is 0 while unhealthy). The attacker can time this to a victim nearing liquidation: the victim loses the ability to self-rescue via new deposits. Additionally, any `deposit(..., onBehalfOf_ = victim)` by third parties (zaps, gateways) reverts. This is a targeted freezing of position-management functionality; existing withdraw/repay still work, so impact is temporary-to-permanent freezing of the account's deposit/borrow capability rather than fund theft — consistent with Medium severity.

### Likelihood Explanation
Cost is dust amounts of each deposit token plus gas; fully unprivileged, callable via `Operator.execute` meta-transactions too. It requires the victim to have an existing position (for non-clearability) and the pool to have enough registered deposit tokens to fill 30 slots combined with the victim's existing entries — attackers control how many dust entries they create, and can combine dust deposit tokens with cheap dust debt positions (issue minimal synths to their own account then... debt tokens are non-transferable, but 30 slots are fillable with deposit tokens alone since `addDepositToken` caps pool deposit tokens at 30). Medium likelihood.

### Recommendation
Make per-account token-list additions non-griefable: e.g. do not add a token on plain `transfer`/`transferFrom` receipt (require an explicit `optIn`, or only add on `deposit`/protocol mint), or let receivers remove zero/dust balances permissionlessly via a `sweepDust` path that burns and `removeFromDepositTokensOfAccount` regardless of locked balance when the amount is below a dust threshold. Alternatively drop the cap or raise `MAX_TOKENS_PER_USER` and keep list growth bounded by real deposits.

### Proof of Concept
```ts
// Hardhat test sketch
it('grief: dust transfers freeze victim deposits', async function () {
  // victim has an open debt position close to the limit
  await depositTokenX.connect(alice).deposit(parseEther('1'), alice.address);
  await msUsdDebtToken.connect(alice).issue(alice.address, debtAmount);

  // attacker deposits dust of many deposit tokens and dust-transfers to alice
  for (const dt of depositTokens.slice(0, 30)) {
    await dt.connect(attacker).deposit('1', attacker.address);
    await dt.connect(attacker).transfer(alice.address, '1'); // adds dt to alice's list
  }
  expect(await pool.getDepositTokensOfAccount(alice.address))
      .to.have.length(30);

  // victim can no longer deposit a new collateral type
  await expect(
    depositTokenY.connect(alice).deposit('1000', alice.address)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

  // nor receive synths/mints that create a new entry
  // and cannot clear dust: unlockedBalanceOf == 0 while unhealthy
  expect(await depositTokenY.unlockedBalanceOf(alice.address)).eq(0);
  await expect(
    depositTokens[0].connect(alice).transfer(attacker.address, '1')
  ).to.be.revertedWithCustomError(depositTokens[0], 'NotEnoughFreeBalance');
});
```
