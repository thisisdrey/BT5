### Title
Per-repository concurrency-limit exhaustion enables a single ordinary client to DoS all other users of that repository - ([File: internal/grpc/middleware/limithandler/middleware.go])

### Summary
Gitaly's backpressure mechanism limits concurrent RPCs per repository using a shared, keyed token/queue pool (`max_per_repo` + `max_queue_size`). Because the lock key is derived solely from the repository's relative path — not per-caller/session — and unauthenticated callers silently fall back to sharing the *same* limiter instance as authenticated callers when no dedicated `Unauthenticated` limit is configured, a single ordinary user (or an anonymous client with only fetch access to a public repo) can saturate both the concurrency slots and the queue for that one repository. This blocks every other legitimate caller — including properly authenticated users — from performing Git operations on that repository until in-flight requests complete, mirroring the reported "exhaust a shared rate-limit window to lock out all subsequent users" bug class.

### Finding Description
The concurrency limiter keys admission purely by repository path via `LimitConcurrencyByRepo`, which extracts `info.Repository.GetRelativePath()` from the request context, with no per-user or per-connection component: [1](#0-0) 

For each RPC, the interceptor selects one of two limiter maps based on `auth.IsAuthenticated(ctx)` (which merely checks for a `username` gRPC metadata key set by GitLab's forwarding layer, not Gitaly's actual bearer-token gate): [2](#0-1) 

Critically, when an RPC has no explicit `Unauthenticated` sub-config, `methodLimitersUnauthenticated[info.FullMethod]` is unset (`ok == false`), so the code falls through and reuses the same authenticated `limiter` object — and therefore the same per-repository token pool and queue — for both authenticated and unauthenticated callers. This fallback behavior is explicitly exercised by the test `"unauthenticated falls back to authenticated limiter when not configured"`: [3](#0-2) 

The shared limiter enforces admission with `keyedConcurrencyLimiter.acquire`, which first consumes a bounded queue token and then a bounded concurrency token, both keyed by repository path: [4](#0-3) 

`ConcurrencyLimiter.Limit` rejects any caller once `max_per_repo` slots are occupied and the shared `max_queue_size` queue is also full, returning `ResourceExhausted`: [5](#0-4) 

The intended configuration model documents `max_per_repo`/`max_queue_size` as scoped "per repository," confirming the shared-key design: [6](#0-5) 

Because the key is only the repository path, any single caller with ordinary fetch/clone/push access to one repository (e.g., via `PostUploadPackWithSidechannel`, the exact RPC used as the example in the docs) can open `max_per_repo` concurrent RPCs and additionally fill the `max_queue_size` queue for that repository. This exhausts the entire admission budget for that repository — including the budget shared with fully authenticated, unrelated users — until the attacker's requests complete or time out via `max_queue_wait`.

### Impact Explanation
Any legitimate client (with valid GitLab credentials or write access) attempting to clone, fetch, or push to the targeted repository during the attack window receives `ResourceExhausted` (`ErrMaxQueueSize`/`ErrMaxQueueTime`) instead of being served, causing a denial of service scoped to that repository for as long as the attacker sustains concurrent connections. This is analogous to the reported issue's core defect: a single unprivileged actor can consume an entire shared, window/quota-bounded resource and lock out every other legitimate participant, without needing elevated privileges — only ordinary repository access.

### Likelihood Explanation
Exploitation requires only standard, unprivileged Git access to a single repository (clone/fetch permission is sufficient for read-heavy RPCs like `PostUploadPackWithSidechannel`) and does not require exceeding privileges, leaking tokens, or man-in-the-middle positioning. The vulnerable fallback path is the *default* outcome whenever an operator configures a per-repo concurrency limit but does not also configure a distinct `Unauthenticated` sub-limit for that RPC — a reasonably common, minimal configuration per the documented example in `doc/backpressure.md`.

### Recommendation
- Do not silently fall back to sharing the authenticated limiter's token pool/queue with unauthenticated callers; either require an explicit `Unauthenticated` limit to be configured before admitting unauthenticated traffic to a rate/concurrency-limited RPC, or always maintain a separate, independent (and stricter) default pool for unauthenticated requests.
- Consider adding an additional admission dimension beyond repository path (e.g., per-source-connection or per-identity sub-limits within the per-repo bucket) so that one caller cannot consume the entire per-repository budget.
- Emit metrics/alerts when a single repository's queue is saturated by requests attributable to one peer/connection, to support the incident-response recommendation from the analogous report.

### Proof of Concept
1. Configure Gitaly with a per-repo limit on a read RPC, matching the documented example, without an `unauthenticated` sub-block:
   ```toml
   [[concurrency]]
   rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
   max_per_repo = 2
   max_queue_size = 5
   max_queue_wait = "30s"
   ```
2. As an ordinary/anonymous client with fetch access to repository `R`, open `2` long-running `PostUploadPackWithSidechannel` connections against `R` (occupying both concurrency slots) and then fire `5` more concurrent requests against `R` to fill `max_queue_size`.
3. Any other legitimate/authenticated client attempting to clone or fetch `R` at this point receives `ResourceExhausted` with `LimitError{ErrorMessage: "maximum queue size reached"}`, as reproduced by the existing test `TestUnaryLimitHandler_queueing`/`TestStreamLimitHandler_error` patterns, confirming the shared-bucket exhaustion is reachable purely through the public RPC surface with only ordinary repository access.

func (sem *keyedConcurrencyLimiter) acquire(ctx context.Context, limitingKey string) (returnedErr error) {
	if sem.queueTokens != nil {
		// Try to acquire the queueing token. The queueing token is used to control how many
		// callers may wait for the concurrency token at the same time. If there are no more
		// queueing tokens then this indicates that the queue is full and we thus return an
		// error immediately.
		if err := sem.queueTokens.TryAcquire(); err != nil {
			return err
		}
		// We have acquired a queueing token, so we need to release it if acquiring
		// the concurrency token fails. If we succeed to acquire the concurrency
		// token though then we retain the queueing token until the caller signals
		// that the concurrency-limited function has finished. As a consequence the
		// queue token is returned together with the concurrency token.
		//
		// A simpler model would be to just have `maxQueueLength` many queueing
		// tokens. But this would add concurrency-limiting when acquiring the queue
		// token itself, which is not what we want to do. Instead, we want to admit
		// as many callers into the queue as the queue length permits plus the
		// number of available concurrency tokens allows.
		defer func() {
			if returnedErr != nil {
				sem.queueTokens.Release()
			}
		}()
	}

	// We are queued now, so let's tell the monitor. Furthermore, even though we're still
	// holding the queueing token when this function exits successfully we also tell the monitor
	// that we have exited the queue. It is only an implementation detail anyway that we hold on
	// to the token, so the monitor shouldn't care about that.
	sem.monitor.Queued(ctx, limitingKey, sem.queueLength())
	defer sem.monitor.Dequeued(ctx)

	if sem.maxQueueWait != 0 {
		if sem.setWaitTimeoutContext != nil {
			ctx = sem.setWaitTimeoutContext()
		} else {
			var cancel context.CancelFunc
			ctx, cancel = context.WithTimeout(ctx, sem.maxQueueWait)
			defer cancel()
		}
	}

	// Try to acquire the concurrency token now that we're in the queue.
	return sem.concurrencyTokens.Acquire(ctx)
}

func (c *ConcurrencyLimiter) Limit(ctx context.Context, limitingKey string, f LimitedFunc) (interface{}, error) {
	span, ctx := tracing.StartSpanIfHasParent(
		ctx,
		"limiter.ConcurrencyLimiter.Limit",
		[]attribute.KeyValue{
			attribute.String("key", limitingKey),
		},
	)
	defer span.End()

	if c.currentLimit() <= 0 {
		return f()
	}

	sem := c.getConcurrencyLimit(limitingKey)
	defer c.putConcurrencyLimit(limitingKey)

	start := time.Now()

	if err := sem.acquire(ctx, limitingKey); err != nil {
		queueTime := time.Since(start)
		switch {
		case errors.Is(err, ErrMaxQueueSize):
			c.monitor.Dropped(ctx, limitingKey, sem.queueLength(), sem.inProgress(), queueTime, "max_size")
			return nil, structerr.NewResourceExhausted("%w", ErrMaxQueueSize).WithDetail(&gitalypb.LimitError{
				ErrorMessage: err.Error(),
				RetryAfter:   durationpb.New(0),
			})
		case errors.Is(err, ErrMaxQueueTime):
			c.monitor.Dropped(ctx, limitingKey, sem.queueLength(), sem.inProgress(), queueTime, "max_time")
			return nil, structerr.NewResourceExhausted("%w", ErrMaxQueueTime).WithDetail(&gitalypb.LimitError{
				ErrorMessage: err.Error(),
				RetryAfter:   durationpb.New(0),
			})
		default:
			c.monitor.Dropped(ctx, limitingKey, sem.queueLength(), sem.inProgress(), queueTime, "other")
			return nil, fmt.Errorf("unexpected error when dequeueing request: %w", err)
		}
	}

```markdown
## Concurrency queue

Limit the number of concurrent RPCs that are in flight on each Gitaly node for each
repository per RPC using `[[concurrency]]` configuration:

```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
```

For example:

- One clone request comes in for repository "A" (a largish repository).
- While this RPC is executing, another request comes in for repository "A". Because
  `max_per_repo` is 1 in this case, the second request blocks until the first request
  is finished.

An in-memory queue of requests can build up in Gitaly that are waiting their turn. Because
this is a potential vector for a memory leak, two other values in the `[[concurrency]]`
configuration can prevent an unbounded in-memory queue of requests:

- `max_queue_wait` is the maximum amount of time a request can wait in the
  concurrency queue. When a request waits longer than this time, it returns
  an error to the client.
- `max_queue_size` is the maximum size the concurrency queue can grow for a
  given RPC. If a concurrency queue is at its maximum, subsequent requests
  return with an error. The queue size is per repository.
```
