### Title
False StackerDB chunk inventory advertised before the chunk is durably stored, allowing served-inventory/actual-storage divergence - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` patches an in-memory `StackerDBChunkInv` reply to claim the local node already holds the new chunk version, and immediately sends that reply to the peer, **before** the chunk is actually persisted via `try_replace_chunk`. Persistence only happens later, when the message is forwarded to the relayer (`pushed_stackerdb_chunks` → `process_stacker_db_chunks`). This breaks the "served vs. committed" equality analogous to the report's core issue: a value/state is used (here, advertised as authoritative) before the operation that actually finalizes it has completed or is guaranteed to succeed.

### Finding Description
In `handle_unsolicited_StackerDBPushChunk` (`stackslib/src/net/stackerdb/mod.rs:742-871`):

1. `make_StackerDBChunksInv_or_Nack` builds a `StackerDBChunkInvData` from the **currently stored** slot versions. [1](#0-0) 
2. `validate_received_chunk` checks size, signer, staleness, and max-writes — but does **not** write anything to the database. [2](#0-1) 
3. The in-memory inventory copy is patched to reflect the new (not-yet-stored) version: [3](#0-2) 
4. The patched inventory is signed and sent back to the peer immediately: [4](#0-3) 
5. The function returns `(false, true)`, meaning "forward to relayer for actual processing" — i.e., the real, transactional storage via `StackerDBTx::try_replace_chunk` happens **afterwards**, asynchronously, in the relay pipeline (`pushed_stackerdb_chunks` handling in `stackslib/src/net/mod.rs`, and `try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs:400-438`).

Because `validate_received_chunk` re-reads slot versions independently for each incoming message rather than atomically reserving the slot, two racing pushes for the same slot (both citing a version higher than the currently stored one, both carrying a validly-signed chunk that an attacker need only relay — no private key required) can both pass validation and both trigger an immediate "I have version X" reply, while only one of the underlying `try_replace_chunk` calls in the relay pipeline can actually succeed (the loser fails with `StaleChunk` and is silently dropped, per `stackslib/src/net/relay.rs:2412-2434`). The peer that was told "we have version N" may end up talking to a node that actually stores a different version (or none), since the acknowledgment was generated from pre-commit state rather than the eventual, actually-committed outcome.

This mirrors the report's bug class precisely: a value (`baseTokenSupply`) is used in downstream calculations/assertions before the operation that is supposed to finalize/deduct it (fee accrual) is reflected, causing later consumers to see stale, unauthoritative numbers. Here, the "downstream consumer" is the remote peer, which is told authoritative state (`slot_version = N`) before the actual, transactional write that would make that state true has been attempted or guaranteed to succeed.

### Impact Explanation
This is a "served vs. committed" divergence: a remote, unprivileged peer can cause a target node to advertise (and cryptographically sign, via `sign_for_p2p_reply`) inventory data describing a StackerDB slot version that the node has not actually committed to storage, and in some race outcomes never will. Downstream consumers (other peers doing rarest/newest-first StackerDB sync scheduling, or issuing `StackerDBGetChunk` based on the advertised version) can be misled about what the node actually possesses, i.e. "non-canonical local state (in-flight/uncommitted) served as canonical (already-stored)." This fits the High-impact category of serving non-canonical state as canonical.

### Likelihood Explanation
Any authenticated (but otherwise unprivileged) P2P peer can trigger this by relaying two validly-signed `StackerDBPushChunk` messages for the same slot with different qualifying (higher-than-current) versions through two connections/event IDs in the same processing tick — no signing key or admin privilege is required, since an attacker can simply relay chunks it observed on the network (chunk validity requires only the chunk owner's signature, not the attacker's). The race depends on message batching/ordering in `handle_unsolicited_stacks_messages`, which is plausible but not guaranteed on every attempt, making likelihood moderate rather than certain.

### Recommendation
Do not patch and send the "we already have it" inventory reply until after the chunk has actually been durably written via `try_replace_chunk` (or at minimum, ensure the reply reflects the version the node will deterministically end up storing, e.g., by attempting the store synchronously within `handle_unsolicited_StackerDBPushChunk` rather than deferring to the relayer, or by re-validating actual stored state before signing/sending the ack).

### Proof of Concept
1. Attacker relays a validly-signed `StackerDBChunkData` for slot `S`, version `N` (higher than currently stored) to target node via connection A, and simultaneously via connection B, a validly-signed chunk for the same slot `S`, version `N+1`.
2. Both arrive in the same `handle_unsolicited_stacks_messages` batch. For each, `make_StackerDBChunksInv_or_Nack` reads the *pre-write* slot version, both pass `validate_received_chunk` (both versions are numerically greater than the stored version at read time), and both trigger an immediate signed `StackerDBChunkInv` reply claiming their respective version is now stored (`stackslib/src/net/stackerdb/mod.rs:794-870`).
3. Both messages are forwarded to the relayer; only one `try_replace_chunk` call succeeds (the other returns `StaleChunk` and is dropped per `stackslib/src/net/relay.rs:2412-2434`).
4. The peer that received the "I have version N" ack (whose write lost the race) now believes the target node stores version `N`, when in fact the node stores version `N+1` (or, depending on ordering, nothing changed) — a discrepancy between advertised (served) inventory and actually committed storage.
