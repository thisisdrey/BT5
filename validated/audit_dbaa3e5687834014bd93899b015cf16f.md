### Title
Reward accumulation silently drops SR reward when a witness's vote count is zero, permanently orphaning the reward - ([File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java])

### Summary
The Notional `_accumulateRewardPerNToken()` bug is that when `totalSupply == 0`, no reward accrues for the elapsed period, yet the accumulator's timestamp is still advanced, so that period's emission is permanently lost instead of being preserved for the next depositor. java-tron's per-cycle SR vote-reward accumulator, `DelegationStore.accumulateWitnessVi` (also duplicated in `RewardViCalService.accumulateWitnessVi`), has the same structural flaw: when a witness's vote count for a cycle is `0`, the `Vi` accumulator is left unchanged (just forwarded), while the block/transaction-fee reward already recorded for that cycle via `MortgageService.payReward` -> `DelegationStore.addReward` is never folded into any voter's claimable share and becomes permanently unclaimable.

### Finding Description
`MortgageService.payReward` records SR rewards per cycle unconditionally: [1](#0-0) 

Each maintenance cycle, `MaintenanceManager.doMaintenance` accumulates the vote-index (`Vi`) for every witness based on that cycle's recorded reward and vote count, then unconditionally advances the cycle counter and refreshes each witness's vote count for the next cycle: [2](#0-1) [3](#0-2) 

The actual accumulation logic is in `DelegationStore.accumulateWitnessVi` (new algorithm) — analogous to `_accumulateRewardPerNToken`/`_getAccumulatedRewardPerToken` in the report: [4](#0-3) 

When `voteCount == 0` for that cycle (i.e., the "total supply" of votes backing that witness is zero, e.g., a freshly registered witness/candidate that has not yet received votes, or a witness whose voters withdrew all votes in a prior cycle), the branch `if (reward == 0 || voteCount == 0)` just forwards `preVi` unchanged — it never folds the reward already recorded via `addReward(cycle, witnessAddress, value)` into `Vi`. Because withdrawal/reward-query logic (`MortgageService.computeReward`, `withdrawReward`, `queryReward`) computes rewards strictly from the delta of `Vi` between cycles: [5](#0-4) 

the reward value stored via `addReward` for that specific cycle can never be attributed to any voter once the cycle boundary passes — there's no mechanism to carry the un-accumulated reward forward to the next cycle in which votes reappear. The identical drop-through exists in the pre-new-algorithm path, `MortgageService.computeReward(cycle, votes)`, which skips the cycle entirely `if (totalVote == DelegationStore.REMARK || totalVote == 0)`: [6](#0-5) 

This mirrors the reported invariant break precisely: the protocol promises SRs/voters a pro-rata share of reward "regardless of ... total supply" (here, total votes), but any reward earned in a cycle where votes are momentarily zero is silently discarded rather than deferred to the first subsequent voter.

### Impact Explanation
Reward tokens (TRX) already debited from the block/transaction-fee reward pool and recorded in `DelegationStore` for a given cycle become permanently unclaimable by any account once that cycle's `Vi` is finalized without incorporating the reward. This is a genuine, permanent loss of funds from the intended beneficiaries (voters/witnesses) — the value is neither returned to any account nor recoverable through any subsequent transaction, matching the "permanent freezing of funds" / lost-value class of impact.

### Likelihood Explanation
This path is reached automatically during ordinary consensus operation — no attacker-controlled transaction is needed. A witness (SR/SR candidate) can have zero recorded votes for a cycle in normal circumstances: right after being created (before receiving any vote), or after all its voters withdraw/redirect votes in a prior cycle while it remains in the witness list. Every `doMaintenance` cycle at least attempts `accumulateWitnessVi` for all witnesses, so the zero-vote branch is trivially and repeatably reachable under normal network conditions, not merely a contrived edge case.

### Recommendation
When `voteCount == 0` for a cycle but a nonzero `reward` was recorded (via `addReward`), do not silently drop the reward. Instead, either (a) roll the un-attributed reward forward and add it to the next cycle's `reward` bucket for that witness (`addReward(cycle + 1, address, reward)`), so it is captured by the first cycle with nonzero votes, or (b) refuse to advance/finalize the cycle's `Vi` snapshot until votes reappear, deferring both the reward and the vote-count application together, analogous to preserving `lastAccumulatedTime`/`accumulatedRewardPerNToken` state until `totalSupply > 0` in the referenced fix.

### Proof of Concept
1. Create/whitelist a new witness `W` with `voteCount == 0` for cycle `N` (e.g., immediately after `createWitness`, before any `voteWitness`).
2. Let block production and maintenance run so `MortgageService.payBlockReward`/`payTransactionFeeReward` calls `payReward(W, value)` for cycle `N`, recording `delegationStore.addReward(N, W, value)`. [1](#0-0) 
3. At the maintenance boundary, `DelegationStore.accumulateWitnessVi(N, W, 0)` is invoked with `voteCount == 0`, leaving `Vi(N, W) == Vi(N-1, W)` unchanged. [4](#0-3) 
4. Subsequently, a voter votes for `W` starting cycle `N+1`. When they later call `withdrawReward`/`queryReward`, `computeReward` uses `Vi(N+1-1) - Vi(beginCycle-1)`, which never includes the reward recorded at cycle `N`, since `Vi` never incorporated it. [5](#0-4) 
5. The `value` recorded by `addReward(N, W, value)` is now unreachable by any future computation — it is permanently lost from voter-claimable rewards.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
