Audit Report

## Title
Pre-funded pool account lets an attacker DoS/skew first `add_liquidity` in `pallet-asset-conversion` - (File: `substrate/frame/asset-conversion/src/lib.rs`)

## Summary
`do_add_liquidity` computes `reserve1`/`reserve2` directly from the live balances of the deterministic pool account via `Self::get_balance` [1](#0-0)  and branches into the "existing pool" quoting path whenever `reserve1.is_zero() || reserve2.is_zero()` is false — regardless of whether any LP tokens have actually been minted (`total_supply` is checked only later, at line 858, for LP minting math, not for the reserve-branch decision). Because the pool account address is a pure deterministic hash of the asset pair computable before pool creation, an unprivileged attacker can pre-donate a disproportionate dust amount of one asset to that address, forcing the legitimate first `add_liquidity` caller into the `quote()`-based branch with a skewed ratio, causing reverts via `AssetTwoDepositDidNotMeetMinimum`/`OptimalAmountLessThanDesired`/`AssetOneDepositDidNotMeetMinimum`.

## Finding Description
The reserve values used to decide whether a pool is being seeded for the first time are read straight from `T::Assets::balance(asset, owner)` [2](#0-1)  rather than from any state that is exclusively updated through pallet extrinsics. The pool account itself is derived deterministically via `blake2_256(pallet_id/seed, pool_id)` with no dependency on the `Pools::<T>` storage actually containing an entry [3](#0-2) , so it is fully predictable and fundable before pool creation or before the first genuine `add_liquidity`.

`do_create_pool` only calls `touch` on the pool account for `asset1`/`asset2` to allow it to hold balances; it never inspects or clears any pre-existing balance [4](#0-3) . As a result, when the legitimate LP calls `add_liquidity` for the first time, `do_add_liquidity` reads non-zero `reserve1`/`reserve2` (from the attacker's donation) and enters the `else` branch that calls `Self::quote` using the skewed reserves [5](#0-4) , even though `T::PoolAssets::total_issuance(pool.lp_token)` — checked only afterward at line 858 — is still zero, meaning no genuine liquidity exists yet. The `amount1_min`/`amount2_min`/`amount1_desired` checks in that branch can then fail on attacker-skewed ratios that have nothing to do with the caller's intended fair-market price.

The only mitigation present, `T::MintMinLiquidity::get()` (a fixed dust amount locked into the pool account on first mint, checked at lines 866 and 875), addresses a different problem (LP-share dust/rounding griefing on withdrawal) and does not gate the reserve branch on `total_supply`, so it provides no protection against this specific donation-before-first-deposit attack.

## Impact Explanation
This is a permissionless griefing/DoS vector against pool bootstrapping: an attacker with no elevated privileges can repeatedly force reverts of the legitimate first `add_liquidity` call for any not-yet-genuinely-funded pool, or coerce acceptance of an attacker-chosen skewed ratio if the caller's slippage bounds are loose. No funds are stolen and established pools (`total_supply > 0`) are unaffected, but it degrades the intended behavior of a public runtime dispatchable (`add_liquidity`), matching the "runtime bugs that compromise intended behavior" category. Severity is Medium, consistent with typical AMM "donation attack" griefing findings — annoying and blocking, not fund-draining.

## Likelihood Explanation
Likelihood is Medium: the attack requires only an ordinary, permissionless asset transfer to a computable address, is cheap (dust amounts), works pre-emptively without needing to front-run any specific transaction, and is repeatable for any new asset pair before real liquidity has been deposited.

## Recommendation
Gate the "first deposit" branch of `do_add_liquidity` on LP-token `total_supply == 0` (as already used later for minting math) rather than on raw `reserve.is_zero()`, and when `total_supply == 0`, ignore/absorb any pre-existing pool-account balance into the first minted position instead of feeding it into `Self::quote`. Alternatively, have `do_create_pool` record a canonical zero baseline or reject creation if the pool account already holds non-zero balances of `asset1`/`asset2`.

## Proof of Concept
1. Compute the deterministic pool account for `(asset1, asset2)` via `AccountIdConverter`/`AccountIdConverterNoSeed` before or after `create_pool`.
2. Transfer a small, disproportionate amount of `asset1` (or `asset2`) directly to that account.
3. Legitimate user calls `create_pool` (if needed) then `add_liquidity` with a fair-market `amount1_desired`/`amount2_desired`/`amount1_min`/`amount2_min`.
4. `do_add_liquidity` observes non-zero `reserve1`/`reserve2` from the donation despite `total_issuance(lp_token) == 0`, enters the `quote()` branch at lines 821-844, and reverts with `AssetTwoDepositDidNotMeetMinimum`/`OptimalAmountLessThanDesired`/`AssetOneDepositDidNotMeetMinimum` — reproducible as a Rust unit test in the pallet's mock runtime.

	PoolId: Encode,
	AccountId: Decode,
	Seed: Get<PalletId>,

	fn try_convert(id: &PoolId) -> Result<AccountId, &PoolId> {
