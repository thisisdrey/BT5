### Title
Quadratic-time in-memory tree construction from unbounded `UserCommitFiles` actions enables RPC-handler CPU exhaustion - (File: internal/git/localrepo/tree.go)

### Summary
`TreeEntry.Add` (and the shared `recurse` helper it uses) resolves each path component by linearly scanning the `Entries` slice of the current in-memory tree node, exactly like the reported `UpDown.isParticipating()` pattern that linearly scans a growing array on every new participant. Since `Add` is called once per file-creation action that a user submits, and each call's cost grows with the number of entries already added to the same directory, a single unprivileged mutator RPC can be crafted to make tree construction cost grow quadratically with the number of actions.

### Finding Description
`Add` walks down `currentTree.Entries` and does a `for i, entry := range currentTree.Entries { if entry.Path != firstComponent { continue } ... }` scan at every directory level to find (or fail to find) a matching child before appending a new entry. [1](#0-0) 

The `recurse` function backing tree deletion/lookup performs the identical linear-scan pattern: [2](#0-1) 

Because `Entries` is an ordinary `[]*TreeEntry` slice that only grows (`currentTree.Entries = append(currentTree.Entries, &newEntry)`), and there is no map-based lookup by path, every subsequent `Add` call targeting entries already present in the same directory must re-scan all previously added siblings — an O(n) operation per call. If a client can drive `Add`/`recurse` N times against entries accumulating in the same directory within one request (e.g., via repeated `CreateFile`/`ChmodFile`/`MoveFile`/`DeleteFile` actions in a single `UserCommitFiles` stream, which is exactly how GitLab's "commit multiple files" web/API feature and ordinary Git-independent commit-building flows invoke this code), the total cost becomes O(n²). This mirrors the reported Solidity bug class precisely: a per-operation linear scan over an ever-growing, user-controlled collection, causing the overall operation to blow up superlinearly and eventually exhaust the processing budget (CPU time in Gitaly's case, analogous to gas in the Solidity case) for the request — and by extension the goroutine/CPU resources of the serving `gitaly-server` process handling that mutator RPC.

### Impact Explanation
An authenticated, ordinary user with write access to a repository (no special privileges required) can submit a single `UserCommitFilesRequest` stream containing a large number of file actions targeting the same directory. Because tree construction is O(n²) in the number of actions within that directory, the RPC handler's CPU time grows quadratically, which can degrade or effectively stall the servicing Gitaly worker thread for a disproportionate amount of wall-clock time relative to the request size, denying prompt service to that RPC handler and consuming shared CPU resources on the Gitaly node. This is a resource-exhaustion/DoS impact of the same class as the described "playing is restricted for an unlimited amount of users" bug (unbounded users blocked because gas ran out) — here, unbounded number of actions cause CPU exhaustion of the handler rather than a hard revert, but the underlying algorithmic flaw (linear-scan-per-insertion over a monotonically growing collection driven by user input) is identical.

### Likelihood Explanation
Reaching this code path requires only ordinary repository write access and use of the standard `UserCommitFiles` RPC (used by GitLab's Web IDE / commit multiple files API) — no privileged actor, leaked token, or malicious peer is needed. The severity depends on how many actions can be packed into a single request; gRPC message-size limits and any action-count caps in the `commit_files.go` handler (which I could not fully verify due to a tool error) would bound the achievable N, and therefore bound how severe the quadratic blowup actually is in practice. Without confirming an explicit cap on the number of actions per `UserCommitFilesRequest`, the practical exploitability (i.e., whether N can be made large enough to matter) remains uncertain.

### Recommendation
Replace the linear `for i, entry := range currentTree.Entries` scans in `TreeEntry.Add` and `TreeEntry.recurse` with a map keyed by path-component name (analogous to the report's recommendation to replace array-scan membership checks with `mapping(address => bool)`), so that child lookup is O(1) rather than O(n) per insertion. Additionally, verify/introduce an explicit, sane upper bound on the number of actions accepted per `UserCommitFilesRequest` in `internal/gitaly/service/operations/commit_files.go` to bound worst-case handler CPU usage regardless of the underlying data structure.

### Proof of Concept
Conceptual PoC (algorithmic, not exploit code): a client opens a `UserCommitFiles` stream and sends N `CreateFile` actions all targeting paths under the same directory, e.g. `dir/file0001` through `dir/fileNNNN`. Each `Add` call must linearly scan the current (growing) `dir` tree's `Entries` slice to confirm the new filename doesn't already exist before appending it, so the cumulative work is O(1+2+...+N) = O(N²). For sufficiently large N (bounded only by gRPC message size / any action-count limits, which were not fully confirmed), this drives disproportionate CPU consumption in the single RPC handler goroutine.
