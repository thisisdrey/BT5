### Title
Signature-malleability double-counting in the `ValidateMultiSign` precompile lets a single key satisfy a multi-signature permission threshold - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The Concrete CMS advisory describes an authorization bypass where a secondary, weaker credential check (a per-file password) is treated as sufficient proof of access, letting it substitute for the real permission check. The reachable java-tron analog is in the `ValidateMultiSign` precompiled contract, which TVM contracts call to gate privileged logic (e.g. releasing funds from a custodial/MPC contract) on whether a set of supplied signatures reach an account permission's threshold. Its de-duplication logic only rejects an exact duplicate `(address, signature-bytes)` pair, not a duplicate *signer*, so ECDSA signature malleability lets one private key be counted twice toward the threshold.

### Finding Description
`ValidateMultiSign.execute()` iterates over the caller-supplied signature array and accumulates `totalWeight` from each recovered signer address against the target account's `Permission`: [1](#0-0) 

The dedup check only skips an entry when the *exact same signature bytes* have already been seen for that recovered address:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
```
Because secp256k1 ECDSA signatures are malleable (for any valid `(r, s)` the pair `(r, n-s)` with the flipped recovery id also recovers to the same address), a single key holder can submit two distinct byte-level signatures over the same message hash that both recover to their own address. The first pass adds their signer's weight; the second pass sees the same `recoveredAddr` but a *different* `sign` byte array, so it does not `continue` — it merely calls `MUtil.checkCPUTime()` and then adds the weight again. This lets one authorized key with weight `W` contribute `2W` (or more, with additional malleated variants) toward `permission.getThreshold()`, defeating the intended multi-party requirement.

This mirrors the CVE's root cause pattern (CWE-862): a check meant to require an independent, sufficient authorization (multiple distinct co-signers vs. `view_file` permission) is bypassed because a superficially different but equivalent secondary proof (a malleated signature vs. a file password) is accepted as if it were independent authorization.

### Impact Explanation
`ValidateMultiSign` is a general-purpose on-chain primitive intended for TVM contracts (e.g. custodial wallets, DAO/MPC controllers, exchange integrations) implementing "M-of-N" account-permission-based authorization directly against a TRON account's `Permission` structure. Any Solidity contract that trusts this precompile's boolean result to gate a transfer/withdraw/administrative action can be tricked by an attacker controlling just one signer (with sufficient individual weight combined with malleation-doubling, or combined with legitimately obtained lower-weight keys) into having the precompile falsely report `weight >= threshold`, i.e., producing an unauthorized "yes" a permission check would otherwise refuse. Depending on the calling contract's business logic, this can lead to unauthorized fund movement/theft from any contract relying on this on-chain multisig verification — a direct funds-theft impact.

### Likelihood Explanation
Exploitation requires only: (1) an account with a multi-key active permission of at least threshold 2 (or higher, achievable by chaining more malleated signatures under `MAX_SIZE = 5`), (2) the attacker controlling at least one signer with the corresponding private key, and (3) the ability to derive the standard low-s/high-s malleated variant of an ECDSA signature — a well-known, mechanical transformation requiring no cryptographic breakthrough. Any external account or contract can invoke this precompile directly with attacker-crafted call data (it takes `address`, `permissionId`, `data`, and an array of signatures as raw ABI-encoded input), making this reachable by an anonymous contract deployer/caller with no special privileges.

### Recommendation
Change the de-duplication key in `ValidateMultiSign.execute()` (and check the analogous `BatchValidateSign` precompile for the same pattern) so weight is counted at most once per unique **recovered address**, not per unique `(address, signature bytes)` pair — i.e., `continue`/skip whenever `recoveredAddr` has already contributed weight, regardless of whether the raw signature bytes differ. Additionally consider enforcing canonical low-s signatures during recovery to eliminate the malleable variant entirely.

### Proof of Concept
1. Create an on-chain account with an `Active` permission, `threshold = 2`, containing exactly one key `K` with `weight = 2` (satisfies validation on its own only once) — or, more directly, two keys `K1` and `K2` each `weight = 1`, threshold `2`, but attacker only controls `K1`.
2. Attacker computes the message hash `hash = sha256(address || permissionId || data)` per the precompile's own construction: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1062-1064`.
3. Attacker signs `hash` with `K1` to get `(r, s, v)`, then derives the malleated signature `(r, n-s, v')` (standard ECDSA malleability transform), producing two distinct 65-byte signature blobs `sig1 != sig2` that both recover to `K1`'s address.
4. Attacker calls the `ValidateMultiSign` precompile (via a trivial Solidity wrapper using the TVM precompile address) supplying `[sig1, sig2]` as the signature array.
5. In `execute()`, `sig1` is processed first, adding `K1`'s weight (`1`); `sig2` recovers to the same address, fails the exact-bytes dedup check, proceeds past `MUtil.checkCPUTime()`, and adds `K1`'s weight again (`totalWeight = 2`), meeting `threshold = 2` with only one real authorized signer — returning `dataOne()` (success) at `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1108-1109` even though `K2` never signed.
