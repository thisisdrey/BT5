### Title
Protocol fee bypass on Nep245/Imt `TokenDiff` intents by splitting a batch into per-intent amounts ≤ 1 - ([File: contracts/defuse/core/src/intents/token_diff.rs])

### Summary
`TokenDiff::execute_intent` computes the protocol fee independently for each `TokenDiff` intent, using only that intent's own per-token `delta`. For `Nep245`/`Imt` token types, `TokenDiff::token_fee` returns `Pips::ZERO` whenever `amount <= 1`. An unprivileged signer can split what would otherwise be a single `delta = -2` `TokenDiff` intent into two `TokenDiff` intents each with `delta = -1` on the same `TokenId`, executed sequentially in the same batch, so each is independently exempt from the fee while the aggregate negative delta moved is 2.

### Finding Description
The broken binding: for a single `TokenDiff` intent with `delta = -N` on a `Nep245`/`Imt` `TokenId`, the fee owed is `Pips::fee_ceil(protocol_fee, N)` when `N > 1`. Splitting the same aggregate negative delta into `k` separate `TokenDiff` intents with `delta_i` such that `|delta_i| <= 1` for each, and `Σ|delta_i| = N`, gives `fees_collected[TokenId] = Σ TokenDiff::token_fee(token_id, |delta_i|, protocol_fee).fee_ceil(|delta_i|) = 0` for every split intent, because each per-intent `amount <= 1` hits the exemption branch in `token_fee`: [1](#0-0) 

This exemption is applied inside `execute_intent`, per intent, per token, with no visibility into other intents in the batch: [2](#0-1) 

`fee_ceil` is called with the local `amount` (`delta.unsigned_abs()`) of that single intent only, so nothing aggregates the total amount moved by the signer on that `TokenId` across the whole `MultiPayload`/batch. Meanwhile, `execute_intents` processes each `Intent` in `DefuseIntents::intents` sequentially and independently invokes `TokenDiff::execute_intent` for each `TokenDiff`, so two intents each with `amount = 1` on the same `TokenId` and same signer both individually satisfy `amount <= 1` and both return `Pips::ZERO`.

The batch-level invariant enforced by `TransferMatcher`/`TokenTransferMatcher::finalize_into` only checks that deposits and withdrawals net to zero per `TokenId` across the whole batch (a balance-conservation check); it does not recompute or re-derive fees from the aggregated per-signer per-token amount: [3](#0-2) 

So an attacker can sign one `MultiPayload` (or one `DefusePayload` with multiple `TokenDiff` intents in its `intents: Vec<Intent>` list) containing, e.g., `TokenDiff{diff: {mt_token: -1}}` twice (or `k` times for a total of `k`) instead of one `TokenDiff{diff: {mt_token: -k}}`, paired with a matching counterparty deposit of `+k` (which can be split identically, or come from a single counterparty intent — the matcher only requires netting, not equal fragmentation). Each of the attacker's intents pays zero fee, while the semantically equivalent single-intent swap of the same aggregate size would owe `Pips::fee_ceil(protocol_fee, k)`.

No existing guard closes this gap: `MultiPayload::verify`/nonce checks only govern signature/replay validity, not fee aggregation; `TransferMatcher::finalize` only guards balance conservation; and `TokenDiff::token_fee` explicitly keys off the single call's `amount` argument with no batch or historical context.

### Impact Explanation
This under-collects protocol fees on `Nep245`/`Imt` token diffs: the `fee_collector` receives strictly less than `Pips::fee_ceil(protocol_fee, N)` for an aggregate negative delta of size `N > 1` split into unit-sized intents, versus the fee that a single equivalent-size `TokenDiff` intent would generate. This falls under the explicitly listed Critical category "protocol fees bypassed or over-collected." The bypass is repeatable per token, per signer, per batch, and scales linearly with the number of split intents the attacker is willing to sign/submit — an attacker can move an arbitrarily large aggregate amount of a `Nep245`/`Imt` token while paying zero fee by chunking every transfer into `amount = 1` pieces.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged signer's control: the attacker needs a `Nep245`/`Imt` balance ≥ the amount they want to move, a counterparty (which may be the attacker's own second account, or a cooperating solver) willing to supply matching deposits so `TransferMatcher::finalize` doesn't flag an invariant violation, and the ability to sign a `MultiPayload`/`DefusePayload` with multiple `TokenDiff` intents — all of which are ordinary, permitted `execute_intents` usage. No special role, relayer key, or DAO permission is required. This is trivially and cheaply repeatable (cost scales only with number of small intents/gas, not with amount moved).

### Recommendation
Aggregate the `Nep245`/`Imt` amount-per-`TokenId` across all `TokenDiff` intents from the same signer within a single `execute_intents`/batch (or across the whole `MultiPayload` set) before applying the `amount <= 1` exemption, rather than evaluating the exemption per individual intent's local `delta`. Alternatively, remove/replace the per-call `amount <= 1` MT/Imt exemption with a check based on the token's actual granularity/decimals rather than a hardcoded literal amount, since `Nep245`/`Imt` tokens are fungible-like and can be freely subdivided across intents to repeatedly hit the exemption.

    pub fn finalize_into(self, token_id: &TokenId, transfers: &mut Transfers) -> Result<(), i128> {
        // sort deposits and withdrawals in descending order
        let [mut deposits, mut withdrawals] = [self.deposits, self.withdrawals].map(|amounts| {
            let mut amounts: Vec<_> = amounts.into_iter().collect();
            amounts.sort_unstable_by_key(|(_, amount)| Reverse(*amount));
            amounts.into_iter()
        });

        // take first sender and receiver
        let (mut deposit, mut withdraw) = (deposits.next(), withdrawals.next());

        // as long as there is both: sender and receiver
        while let Some(((sender, send), (receiver, receive))) =
            withdraw.as_mut().zip(deposit.as_mut())
        {
            // get min amount and transfer
            let transfer = (*send).min(*receive);
            transfers
                .transfer(sender.clone(), receiver.clone(), token_id.clone(), transfer)
                // no error can happen since we add only one transfer for each
                // combination of (sender, receiver, token_id)
                .unwrap_or_else(|| unreachable!());

            // subtract amount from sender and receiver
            *send = send.saturating_sub(transfer);
            *receive = receive.saturating_sub(transfer);

            if *send == 0 {
                // select next sender
                withdraw = withdrawals.next();
            }
            if *receive == 0 {
                // select next receiver
                deposit = deposits.next();
            }
        }

        // only sender(s) left
        if let Some((_, send)) = withdraw {
            return Err(withdrawals
                .try_fold(send, |total, (_, s)| total.checked_add(s))
                .and_then(|total| i128::try_from(total).ok())
                .and_then(i128::checked_neg)
                .unwrap_or_default());
        }
        // only receiver(s) left
        if let Some((_, receive)) = deposit {
            return Err(deposits
                .try_fold(receive, |total, (_, r)| total.checked_add(r))
                .and_then(|total| i128::try_from(total).ok())
                .unwrap_or_default());
        }

        Ok(())
    }
