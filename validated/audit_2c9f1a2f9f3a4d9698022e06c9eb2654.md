### Title
Unbounded `estimated_len` in `/v2/fees/transaction` causes integer overflow (panic/wrap) in `estimate_tx_fee_from_cost_and_length` - ([File: stackslib/src/net/api/postfeerate.rs])

### Summary
`RPCPostFeeRateRequestHandler::try_parse_request` accepts an attacker-supplied `estimated_len: Option<u64>` field with no upper-bound validation, computes `estimated_len = max(body.estimated_len.unwrap_or(0), payload_data.len())`, and passes it into `estimate_tx_fee_from_cost_and_length`, which multiplies it by `MINIMUM_TX_FEE_RATE_PER_BYTE` with no overflow guard. A single unauthenticated POST with `estimated_len: 18446744073709551615` triggers an unchecked `u64` multiplication.

### Finding Description
In `try_parse_request` [1](#0-0) , `body.estimated_len` is deserialized directly from JSON with only a `#[serde(default)]` attribute and no range check [2](#0-1) . The only length validation performed is on the raw HTTP `content_len` (`0 < content_len < MAX_PAYLOAD_LEN`) [3](#0-2) , which bounds the size of the JSON body/hex string but does not constrain the numeric value of the `estimated_len` field inside that JSON. Because `std::cmp::max` is used, an attacker-chosen `estimated_len` (e.g., `u64::MAX`) always wins over the real `payload_data.len()`, completely decoupling the value from the actual transaction size.

This value flows unmodified into `estimate_tx_fee_from_cost_and_length`, where `let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;` performs a plain, unchecked multiplication [4](#0-3) . The repository's Cargo configuration does not enable `overflow-checks` in release profile (no `overflow-checks` setting found), meaning:
- In debug builds, this multiplication panics on overflow.
- In release builds, this multiplication silently wraps to an incorrect (nonsensical) `minimum_fee`, producing wrong fee data served to the caller only (this is a per-request-scoped local variable — it does not corrupt state served to *other* callers, since `estimated_len`/`minimum_fee` are local to this request's handler invocation and response).

The endpoint is reachable via `POST /v2/fees/transaction` and requires only that `rpc_args.get_estimators_ref()` return `Some` (a configuration precondition, not an authentication one) — confirmed no auth-token/session gate exists on this handler in the code reviewed [5](#0-4) .

### Impact Explanation
In a debug build, a single crafted request panics the thread handling the RPC request. Given Rust's default panic behavior in most async/thread-pool HTTP server setups, this could crash or hang the handling thread; whether this brings down the whole node process depends on whether the panic is caught at a thread boundary (not verified here from available code — the request handling call stack beyond `with_node_state` was not fully traced for panic-catching wrappers). In release builds (the default deployment configuration, and the more realistic threat model for a production node), the multiplication silently wraps, which only corrupts the returned fee estimate for that single request/response — it does not propagate to other callers, is not stored, and does not affect chain state, mempool admission, or other nodes.

### Likelihood Explanation
Trivial precondition: the endpoint must be reachable and fee/cost estimators configured, which is a common production-default in many stacks-node configurations. No authentication or special role is required — this is a plain unauthenticated POST. Attacker cost is one HTTP request; repeatable indefinitely.

### Recommendation
Add an explicit upper bound on `body.estimated_len` in `try_parse_request` (e.g., reject values greater than `MAX_TRANSACTION_LEN`/`MAX_PAYLOAD_LEN`), and/or replace the raw multiplication in `estimate_tx_fee_from_cost_and_length` with `checked_mul`/`saturating_mul` and return an `HttpBadRequest` on overflow instead of allowing UB/wrap.

### Proof of Concept
Add a test in `stackslib/src/net/api/tests/postfeerate.rs` (or equivalent) that:
1. Constructs a minimal valid `TransactionPayload` hex string.
2. Builds a JSON body `{"transaction_payload": "<hex>", "estimated_len": 18446744073709551615}` with `content_len` satisfying `0 < content_len < MAX_PAYLOAD_LEN`.
3. Calls `RPCPostFeeRateRequestHandler::try_parse_request` on this body — observe `self.estimated_len == Some(u64::MAX)`.
4. Calls `RPCPostFeeRateRequestHandler::estimate_tx_fee_from_cost_and_length` directly with `estimated_len = u64::MAX` and assert that in a debug build the process panics at `estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` (line 112), demonstrating the missing bound/overflow check, rather than the function returning a bounded `Result::Err`.

Note: I was unable to fully verify from the available index whether a panic in this specific RPC handler call path is caught at a higher-level thread boundary (which would downgrade the debug-build impact from "server-crashing" to "single-request-failing"), since the surrounding HTTP server dispatch code was not indexed for this review. This should be verified in a full Devin session with access to the complete server dispatch code before finalizing severity.
