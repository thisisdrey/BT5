### Title
Unstaked attacker can exhaust the shared 25% connection-handshake headroom, causing legitimate staked-peer connections to be refused with `too_many_open_connections` - (File: `streamer/src/nonblocking/swqos.rs`)

### Finding Description
`SwQos::max_concurrent_connections` returns a single, identity-agnostic cap equal to `(max_staked_connections + max_unstaked_connections) * 5 / 4`, explicitly documented as headroom "to allow for handshake" [1](#0-0) . This value gates raw connection admission before a peer's stake can be determined (stake classification only happens once the TLS handshake completes and `get_connection_stake` runs, per `build_connection_context`) [2](#0-1) .

Once a connection is classified, the stake-aware admission/eviction logic in `try_add_connection` only operates *within* the already-separated per-type tables: staked connections compete against other staked connections via `prune_random` inside `staked_connection_table`, capped at `max_staked_connections` [3](#0-2) , while unstaked connections are independently capped and self-pruned down to 90% of `max_unstaked_connections` in `prune_unstaked_connection_table` [4](#0-3) . Neither table's eviction logic reaches into, or is aware of, the shared 25% headroom counter used to gate raw/pending handshakes.

Because the headroom counter (`max_concurrent_connections()`) is checked before stake classification and is not partitioned by peer type, an unstaked attacker who opens/holds connections through the handshake stage fast enough can consume the entire 25% margin without ever being subject to the staked-preference eviction inside `try_add_connection`, since that eviction logic is scoped to the classified tables, not to the pre-classification headroom. This lets unstaked traffic push overall concurrent connections against the `max_concurrent_connections()` ceiling, causing subsequent (including staked) handshakes to be refused for capacity reasons entirely due to unstaked load.

### Impact Explanation
This is a QoS-evasion / DoS-adjacent issue: capacity that is architecturally intended as staked-preference headroom (per the "allow for handshake" comment at swqos.rs:519) can be fully consumed by zero-stake traffic, denying admission to legitimate staked peers. This falls under Agave's QoS evasion / staked-connection admission denial bounty category, scoped strictly to connection admission (not transaction execution, consensus, or state correctness).

### Likelihood Explanation
Feasibility depends entirely on network-layer timing: the attacker needs no stake and no special privilege, only the ability to complete/hold enough concurrent QUIC connections before the unstaked table's self-pruning (which caps to 90% of `max_unstaked_connections`) reduces them below the shared headroom's effective consumption, or to keep churning new handshakes fast enough to keep the shared, per-type-agnostic gate saturated. This requires sustained connection churn from a single or few IPs but no stake, and no gossip/leader/config privileges — an unprivileged network-only attacker can attempt it.

### Recommendation
Partition the handshake headroom by peer type (e.g., track separate in-flight/pending counters for staked vs. unstaked, or reserve a portion of the 25% margin exclusively for staked-peer handshakes), or make the pre-classification admission gate itself apply the staked-preference eviction used in `try_add_connection` rather than treating all pending connections identically regardless of eventual classification.

### Proof of Concept
Integration test plan (in `streamer/src/nonblocking/swqos.rs` test module or `streamer` integration tests using `testing_utilities.rs`):
1. Configure a small `SwQosConfig` (e.g., `max_staked_connections = 4`, `max_unstaked_connections = 4`, so `max_concurrent_connections() == 10`).
2. Open 8 unstaked QUIC connections concurrently (below `max_unstaked_connections` self-prune trigger but consuming shared headroom slots at the pre-classification/accept stage), asserting each is admitted (`connection_added_from_unstaked_peer` stat increments, no `too_many_open_connections` close).
3. Attempt to open 2 additional staked connections (with valid stake in `staked_nodes`) while the 8 unstaked connections remain open/pending.
4. Assert the staked connections are refused (connection closed with `CONNECTION_CLOSE_CODE_TOO_MANY` / stat `connection_add_failed_staked_node` incremented) even though `staked_connection_table.total_size` (0) is far below `max_staked_connections` (4), demonstrating denial caused purely by unstaked-held headroom rather than by staked-table exhaustion.
5. Additionally assert that no unstaked connection was evicted to make room for the staked attempt, confirming the staked-preference eviction path in `try_add_connection` (lines 356-365) was never triggered because the refusal occurred at the shared pre-classification gate, not inside the per-type tables.

    fn prune_unstaked_connection_table(
        &self,
        unstaked_connection_table: &mut ConnectionTable<ConnectionStreamCounter>,
        max_unstaked_connections: usize,
        stats: Arc<StreamerStats>,
    ) {
        if unstaked_connection_table.total_size >= max_unstaked_connections {
            // Prune the connection table down to 90% capacity
            const PRUNE_TABLE_RATIO: f64 = 0.90;
            let max_connections = (PRUNE_TABLE_RATIO * (max_unstaked_connections as f64)) as usize;
            let num_pruned = unstaked_connection_table.prune_oldest(max_connections);
            stats
                .num_evictions_unstaked
                .fetch_add(num_pruned, Ordering::Relaxed);
        }
    }

        let remote_address = connection.remote_address();
        get_connection_stake(connection, &self.staked_nodes).map_or(
            SwQosConnectionContext {
                peer_type: ConnectionPeerType::Unstaked,
                total_stake: 0,
                remote_pubkey: None,
                in_staked_table: false,
                remote_address,
                stream_counter: None,
                last_update: Arc::new(AtomicU64::new(timing::timestamp())),
            },
            |(pubkey, stake, total_stake)| {
                // The heuristic is that the stake should be large enough to have 1 stream pass through within one throttle
                // interval during which we allow max (MAX_STREAMS_PER_MS * STREAM_THROTTLING_INTERVAL_MS) streams.

                let peer_type = {
                    let max_streams_per_ms = self.staked_stream_load_ema.max_streams_per_ms();
                    let min_stake_ratio =
                        1_f64 / (max_streams_per_ms * STREAM_THROTTLING_INTERVAL_MS) as f64;
                    let stake_ratio = stake as f64 / total_stake as f64;
                    if stake_ratio < min_stake_ratio {
                        // If it is a staked connection with ultra low stake ratio, treat it as unstaked.
                        ConnectionPeerType::Unstaked
                    } else {
                        ConnectionPeerType::Staked(stake)
                    }
                };

                SwQosConnectionContext {
                    peer_type,
                    total_stake,
                    remote_pubkey: Some(pubkey),
                    in_staked_table: false,
                    remote_address,
                    last_update: Arc::new(AtomicU64::new(timing::timestamp())),
                    stream_counter: None,
                }
            },
        )
