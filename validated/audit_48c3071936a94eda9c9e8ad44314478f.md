### Title
Missing balance-invariant check in legacy `ExchangeCapsule.transaction` AMM path can allow negative/inconsistent exchange reserves - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
`ExchangeCapsule.transaction()` implements the TRC10 bancor-style AMM swap used by `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`. The method has two code paths selected by the `allowHardenExchangeCalculation` dynamic parameter: a "hardened" path using `SafeExchangeProcessor` with `StrictMathWrapper` overflow-safe arithmetic and an explicit non-negative balance invariant check, and a legacy path using plain `ExchangeProcessor` (double-based bancor math) with unchecked `long` arithmetic and no invariant check at all.

### Finding Description
In `transaction()`, the post-swap reserve balances are computed as: [1](#0-0) 

but the safety check that rejects a resulting negative reserve is gated exclusively on `hardenedCalc`: [2](#0-1) 

When `hardenedCalc` is `false` (i.e., `allowHardenExchangeCalculation()` is off), the swap output `buyTokenQuant` is computed via `ExchangeProcessor`, which relies on `double`-precision `Math.pow` calculations: [3](#0-2) 

Floating point precision loss in `exchangeToSupply`/`exchangeFromSupply` (casting `double` to `long` with truncation, no bounds enforcement) can, for certain extreme reserve ratios or repeated small trades, yield a `buyTokenQuant` that exceeds the available reserve, or interact with `sellTokenQuant`/`firstTokenBalance` such that `secondTokenBalance - buyTokenQuant` (or `firstTokenBalance - buyTokenQuant` for the reverse direction) goes negative — with no `if (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)` guard applied in this branch. Both `ExchangeTransactionActuator.doValidate()` and `.execute()` call `exchangeCapsule.transaction(...)` with `allowHarden()` from `AbstractExchangeActuator`, which is a purely dynamic-property-gated boolean: [4](#0-3) [5](#0-4) 

Because the "hardened" fix is only applied conditionally (and evidently was added later as a targeted patch, mirroring the Penumbra pattern of a narrow hotfix for a dex/AMM invariant violation), any chain/state where `allowHardenExchangeCalculation` has not been activated via governance proposal remains exposed to the original unchecked-arithmetic legacy path.

### Impact Explanation
An unauthorized negative reserve balance written into `ExchangeCapsule`/`ExchangeV2Store` corrupts the AMM pool state. Because the account-side balance updates in `ExchangeTransactionActuator.execute()` (`addAssetAmountV2`/`reduceAssetAmountV2`, `setBalance`) are applied independently of the exchange's own consistency check, a user could receive tokens/TRX that are not properly backed by the pool's committed reserves, effectively creating unbacked balance or draining exchange liquidity beyond what the pool holds. Persisted negative reserves in the store can also produce incorrect state on subsequent trades (since `ExchangeProcessor.exchange` assumes non-negative balances), which can propagate corrupted results or crashes on later transactions — a state-consistency defect matching the class of issue that caused the Penumbra dex chain halt.

### Likelihood Explanation
Reachable by any account holding TRX or the relevant TRC10 tokens: `ExchangeTransactionContract` is a standard broadcastable transaction validated in `ExchangeTransactionActuator.doValidate()`/`execute()`. No special privilege is required. The precondition is that `allowHardenExchangeCalculation` has not been enabled on the target network/config, which is plausible since it is a governance-controlled dynamic parameter (not necessarily on by default in all deployments/forks of this codebase) — I could not fully confirm the exact default value of `allowHardenExchangeCalculation` from the available index, so this is a likelihood assumption that should be verified against `DynamicPropertiesStore` initialization and the live proposal state.

### Recommendation
Move the non-negative reserve invariant check outside the `hardenedCalc` conditional so it applies unconditionally to both processors, and/or make `ExchangeProcessor`'s double-based math bounds-checked (clamp/reject negative or overflowing results) rather than only enforcing this in the "hardened" branch. Consider deprecating the legacy floating-point processor entirely and always using `SafeExchangeProcessor`.

### Proof of Concept
Not independently verified due to lack of terminal/test-execution access in this environment; the concrete proof would require running `ExchangeCapsule.transaction(sellTokenID, sellTokenQuant, useStrictMath=true/false, hardenedCalc=false)` with reserve ratios engineered (e.g., very small `secondTokenBalance` relative to `sellTokenQuant`, or many repeated small trades) to drive `buyTokenQuant` above `secondTokenBalance`, and confirming no exception/rejection occurs and a negative `secondTokenBalance` is persisted via `Commons.putExchangeCapsule`. This would need to be validated with an actual Devin session against the test harness (e.g., `ExchangeCapsuleTest`, `ExchangeTransactionActuatorTest`) to construct a concrete failing/negative-balance scenario.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
