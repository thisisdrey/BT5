### Title
Attacker can permanently block a victim from adding new collateral types by dust-filling the `MAX_TOKENS_PER_USER` account token list - (File: contracts/Pool.sol)

### Summary
The bug class in CVE-2017-6463 is an authenticated remote denial of service triggered by supplying a directive the victim did not intend. The Metronome analog is the per-account deposit/debt token registry: `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once an account holds `MAX_TOKENS_PER_USER = 30` distinct tokens [1](#0-0) . Any unprivileged user can force-add entries to a victim's list, because `DepositToken._transfer` (and `_mint` via `deposit(amount_, onBehalfOf_)`) registers the token on the recipient the first time their balance becomes non-zero [2](#0-1) [3](#0-2) . Once the list is full, every `deposit`, `transfer`, `seize`, or liquidation credit involving a token the victim doesn't already hold reverts.

### Finding Description
`Pool` tracks each account's tokens in `depositTokensOfAccount` / `debtTokensOfAccount` (`MappedEnumerableSet`) and enforces a hard cap in `onlyIfAdditionWillNotReachMaxTokens` [1](#0-0) . The only guard on `addToDepositTokensOfAccount` is that the caller is a registered deposit token — there is no consent from the account [4](#0-3) . In `DepositToken._transfer`, a first-time recipient is unconditionally registered [2](#0-1) , and `transfer`/`transferFrom` only check that the *sender's* amount is unlocked via `_revertIfLocked` [5](#0-4) . An attacker therefore deposits dust of each listed collateral and transfers 1 wei of each deposit token to the victim, filling the combined 30-slot quota (deposit tokens + debt tokens share the same cap).

### Impact Explanation
While saturated, the victim cannot `deposit` any collateral type not already in their list (the `_mint` → `addToDepositTokensOfAccount` call reverts), cannot receive `msdToken` transfers of new types, and `DepositToken.seize` reverts for a liquidator whose own list is full (DoS on `Pool.liquidate` for that collateral/liquidator pair). Critically, a victim with an unhealthy position who needs to deposit a *different* collateral to restore health is permanently prevented from doing so as long as the attacker keeps refilling freed slots (the attack is repeatable and cheap: each refill is one dust transfer). This is a liveness break on the deposit/liquidation path that can convert into direct loss of the victim's collateral through forced liquidation.

### Likelihood Explanation
Requires only an EOA: buy dust of the pool's underlying assets, call `DepositToken.deposit(1, attacker)` then `transfer(victim, 1)` (or `deposit(1+fee, victim)` directly) for each registered deposit token. No privileged role, oracle manipulation, or governance action is needed; `whenNotPaused`/`nonReentrant`/`onlyIfDepositTokenExists` do not stop it in the deployed configuration. The constraint is that the number of deposit tokens in a pool is governor-controlled, so with few collaterals the attacker can only partially fill the list — but each dust deposit on the victim's behalf consumes a slot regardless, so the cap is reachable whenever `debtTokens + depositTokens < 30` can be exhausted.

### Recommendation
- Do not register a recipient in `depositTokensOfAccount` on plain `transfer`/`transferFrom`; only track tokens the account actually deposited or explicitly opted into, or make registration lazy in `debtPositionOf`/`depositOf` by iterating pool-level token lists instead.
- Alternatively, remove the `MAX_TOKENS_PER_USER` revert on add and bound the view loops differently, or let any account permissionlessly `removeFromDepositTokensOfAccount` tokens with zero balance (already handled on burn/transfer-out, but the victim currently has no way to evict attacker-forced dust without holding and transferring it back).

### Proof of Concept
Hardhat (fork or fixture with `pool`, `depositTokenA`…`depositTokenN` deployed; victim has an open position):

```ts
// attacker fills victim's token list
for (const dt of allDepositTokens) {           // up to MAX_TOKENS_PER_USER entries
  const underlying = await ethers.getContractAt('IERC20', await dt.underlying())
  await underlying.connect(attacker).approve(dt.address, ethers.constants.MaxUint256)
  await dt.connect(attacker).deposit(ethers.utils.parseUnits('1', await dt.decimals()), attacker.address)
  await dt.connect(attacker).transfer(victim.address, 1)   // registers token on victim
}
expect(await pool.getDepositTokensOfAccount(victim.address)).length // == 30 combined w/ debt tokens

// victim can no longer deposit a collateral type it doesn't already hold
await expect(newDepositToken.connect(victim).deposit(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// liquidator (fresh, saturated or victim-side seize to a full account) also reverts
await expect(pool.connect(liquidator).liquidate(victim.address, synth.address, repayAmt, newDepositToken.address))
  .to.be.reverted // via DepositToken.seize -> addToDepositTokensOfAccount -> UserReachedMaxTokens
```
