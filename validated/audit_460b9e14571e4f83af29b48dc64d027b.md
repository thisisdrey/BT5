### Title
Unbounded length field from precompiled-contract calldata used to size array allocation and array indexing, causing OOM/crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The batch-signature precompiled-contract input decoders in `PrecompiledContracts.java` read a "length" word directly out of attacker-controlled TVM call data and use it, unchecked, both to allocate a Java array and as a loop bound to index further into the same attacker-controlled word array — mirroring the LibRaw `parseSonySRF()` pattern of trusting an in-file length/offset field without validating it against the actual buffer size.

### Finding Description
`extractBytes32Array`, `extractBytesArray` and `extractSigArray` each take `len = words[offset].intValueSafe()` from the raw ABI-encoded calldata of a precompiled-contract call and then loop `for (int i = 0; i < len; i++)` indexing `words[offset + i + 1]` with no check that `offset + i + 1 < words.length`: [1](#0-0) 

`extractBytesArray`/`extractSigArray` only guard the initial `offset`, not the derived loop bound driven by `len`, and `extractBytes` performs an unchecked `Arrays.copyOfRange(data, offset, offset + len)`: [2](#0-1) 

Because `len`/`bytesLen`/`bytesOffset` are computed from fully attacker-controlled `DataWord`s (`intValueSafe()` can return up to `Integer.MAX_VALUE`), the code can either throw an unhandled `NegativeArraySizeException`/`ArrayIndexOutOfBoundsException` while reading past the bounds of the `words`/`data` arrays, or attempt `new byte[len][]` with a huge `len`, provoking a large/failed allocation. The codebase is aware of this exact class of bug elsewhere — `RLP.fullTraverse` explicitly catches `OutOfMemoryError` around length-driven allocations because unconstrained length fields from untrusted data are a known hazard in this project: [3](#0-2) 

No equivalent length-validation or capped-allocation defense exists in the precompiled-contract array extractors.

### Impact Explanation
Any account (an unprivileged deployer or a contract caller) can invoke the affected precompiled contract with crafted calldata via a normal `CALL`/`STATICCALL` from any smart contract, since `execute(byte[] data)` receives raw TVM call data. A crafted `len`/offset combination drives out-of-bounds reads into the `words` `DataWord[]` (constructed from the raw input) or into a huge array allocation attempt, which can manifest as an uncaught runtime exception/`OutOfMemoryError` during transaction execution in the block-application path. Depending on how deep this propagates before being caught by the VM's outer exception handling, this can degrade to a node-level crash/instability rather than a clean revert, since `OutOfMemoryError` is not a safely recoverable condition for a long-running validator/node process.

### Likelihood Explanation
The precompiled contract is reachable from any signed transaction that deploys or calls a contract performing the relevant `CALL` to the reserved precompile address; the vulnerable helper methods have no length sanity checks at all, so triggering the malformed-length condition requires only crafting the ABI-encoded call data, which is trivial and requires no special privilege.

### Recommendation
Validate the decoded `len` (and derived `bytesOffset`/`bytesLen`) against `words.length` and the true `data.length` before allocating arrays or indexing, and reject the input (returning `false`/failure to the caller) rather than allowing unchecked allocation or unchecked array indexing, following the same defensive pattern used in `RLP.verifyLength`/`calcLength`.

### Proof of Concept
1. Deploy a contract that performs a low-level `call`/`staticcall` to the precompiled contract address that resolves to `extractBytesArray`/`extractSigArray`/`extractBytes32Array` (as returned by `PrecompiledContracts.getContractForAddress`), passing crafted calldata where the length word at the expected offset is set to a very large value (e.g. `0x7fffffff`).
2. Broadcast the transaction; during `execute(byte[] data)`, `len = words[offset].intValueSafe()` becomes huge, causing either an out-of-bounds `words[offset + i + 1]` access or `new byte[len][]` to attempt an oversized allocation.
3. Observe the resulting `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException`/`OutOfMemoryError` during transaction processing, and evaluate whether it destabilizes the executing node process instead of cleanly reverting the transaction.
