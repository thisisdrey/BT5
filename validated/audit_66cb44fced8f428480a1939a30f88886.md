### Title
`git_repository`/`new_git_repository` force-enables `protocol.file.allow=always` for submodule fetches, enabling attacker-controlled `.gitmodules` to read/exfiltrate arbitrary local files via `file://` submodule URLs - (`File: tools/build_defs/repo/git_worker.bzl`)

### Summary
`update_submodules()` in `tools/build_defs/repo/git_worker.bzl` unconditionally passes `-c protocol.file.allow=always` to `git submodule update --init [--recursive] --checkout --force` for every `git_repository`/`new_git_repository` fetch that enables `init_submodules`/`recursive_init_submodules`. [1](#0-0) 

This globally re-enables Git's `file://` submodule transport, which upstream Git deliberately restricts by default (`protocol.file.allow=user`) specifically to stop a submodule's `.gitmodules` from pointing at arbitrary local filesystem paths and pulling their content into the checkout — the exact class of local-file-disclosure bug this override defeats.

### Finding Description
`git_repo()` clones the pinned `remote`/`commit`/`tag`/`branch`, then calls `update_submodules(ctx, git_repo, recursive=...)` when `init_submodules` or `recursive_init_submodules` is set: [2](#0-1) 

`update_submodules` explicitly forces the file transport back on with a comment acknowledging this is a deliberate bypass of Git's own protection ("It's necessary for Git 2.38.1 and associated backport versions"): [1](#0-0) 

`git_repository` has no `sha256`/`integrity` attribute at all — trust is placed entirely in the pinned `commit`/`tag`/`branch` of the top-level repository, not in the content addressed by any submodule gitlink resolution path: [3](#0-2) 

An attacker who controls the content fetched (e.g., a public repo used as a dependency where the victim tracks a `branch`/`tag`, or a malicious contribution merged into the pinned commit before it was cut, or "files on an untrusted branch CI builds" as explicitly allowed by scope) can add or modify a `.gitmodules` entry to point a submodule URL at a `file://` path on the build machine's filesystem (e.g., another checked-out repo, a CI credentials cache, or any accessible local git repository). Because Bazel forces `protocol.file.allow=always`, `git submodule update --init --recursive` will honor that `file://` URL without the interactive/administrative opt-in Git normally requires, fetching/checking out that local path's content into the external repository directory. This mirrors the class of bug fixed by Git's `protocol.file.allow` default change (the local `file://` submodule transport can be leveraged to disclose or hard-link content from files/repositories on the local filesystem that the victim never intended to expose to this build), analogous to Jenkins Email-Ext trusting attacker-controlled `file:` image URLs without restriction.

### Impact Explanation
If reachable with a submodule pointing outside the intended checkout (e.g., at a sibling local repository, a shared cache directory, or another path readable by the build user), the build can pull arbitrary local file/repository content from the machine performing the fetch into the external repository tree, where it becomes visible to `BUILD` targets (`genrule`, `filegroup`, etc.) and can be embedded into build outputs, logs, or artifacts — effectively exfiltrating local files. This is a containment/confidentiality breach of the machine performing the fetch (developer workstation or CI runner), matching CWE-73/CVSS High-severity file-disclosure impact of the reference advisory.

### Likelihood Explanation
Requires: (1) `git_repository`/`new_git_repository` used with `init_submodules`/`recursive_init_submodules = True` (a documented, commonly used feature), and (2) attacker control over the `.gitmodules` file in content that is fetched — realistic for repos tracked by mutable `branch`/`tag`, or for any repo an attacker can contribute to before a commit is pinned, or CI configurations that build untrusted branches/PRs. No checksum or integrity mechanism exists to detect or block a malicious submodule URL, and the `protocol.file.allow=always` override applies unconditionally regardless of how trusted the remote is believed to be.

### Recommendation
Do not force `protocol.file.allow=always` for `git submodule update`. Instead, only enable it when required (and only for the local clone protection workaround it was intended for), or restrict submodule URLs to the same host/protocol as the parent `remote`, rejecting `file://`/relative-path submodules whose resolved target escapes the expected clone directory. At minimum, document and gate this behind an explicit opt-in attribute so builds that consume untrusted Git content are not silently exposed.

### Proof of Concept
1. Create a Git repository `victim.git` with `recursive_init_submodules = True`, referenced by `branch = "main"` in a `git_repository` rule.
2. As the attacker (contributor to `main`, or operator of the tracked branch), add a `.gitmodules` file:
   ```
   [submodule "leak"]
       path = leak
       url = file:///home/ci/.ssh
   ```
   (`file:///home/ci/.ssh` must itself be a git repository, or point at another local repo the attacker knows exists on typical CI images, e.g. a shared cache checkout.)
3. Victim runs `bazel build @victim//...`; Bazel's `git_worker.bzl` executes `git -c protocol.file.allow=always submodule update --init --recursive --checkout --force`, which clones from `file:///home/ci/.ssh` into `external/victim/leak/`.
4. A `BUILD` file target (`filegroup(srcs=["leak/**"])` or similar) exposes the previously-local-only files, which appear in build outputs — demonstrating cross-boundary file disclosure via `file://` submodule URLs that Bazel deliberately unblocks in `tools/build_defs/repo/git_worker.bzl:215,217`.

```text
def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
```
