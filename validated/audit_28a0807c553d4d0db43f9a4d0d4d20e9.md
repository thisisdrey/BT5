### Title
Liquidation DoS via debt-floor/maxLiquidable gap — positions can be forced into an un-liquidatable band by permissionless partial repayment - (File: contracts/Pool.sol)

### Summary
`Pool.liquidate` reverts when the post-liquidation remaining debt is in `(0, debtFloorInUsd)` (`RemainingDebtIsLowerThanTheFloor`), and also reverts when `amountToRepay_` exceeds `maxLiquidable` (50%) of the account's debt (`AmountGreaterThanMaxLiquidable`). When an account's per-synthetic-token debt falls into the band `(debtFloorInUsd, debtFloorInUsd / (1 - maxLiquidable))`, every allowed repayment amount either exceeds `maxLiquidable` or leaves a remainder below the floor — so the position can never be liquidated while it is unhealthy. An unprivileged attacker can push a victim into this band by calling the permissionless `DebtToken.repay`/`repayAll` on behalf of the victim, permanently blocking liquidation of an underwater position. This is the availability analog of CVE-2019-2780 (a hang/crash DoS): the liquidation path deterministically reverts regardless of caller, arguments, or ordering.

### Finding Description
In `contracts/Pool.sol:565-579`, `liquidate` enforces two constraints on `amountToRepay_` against the victim's debt-token balance `_debtTokenBalance`:

- `amountToRepay_ / _debtTokenBalance <= maxLiquidable` (default `0.5e18`, set in `initialize` at `contracts/Pool.sol:181`).
- The USD value of `_debtTokenBalance - amountToRepay_` must be `0` or `>= debtFloorInUsd` (`contracts/Pool.sol:571-578`).

Let `D` be the victim's debt in USD for a given synthetic token and `F` the floor. Any repayment `r` must satisfy `r <= 0.5 * D` (cap) and `D - r` must be `0` or `>= F`. If `F < D < 2F`:

- `r <= D/2` implies `D - r >= D/2 > 0` and `D - r <= D < 2F`... more precisely `D - r >= D - D/2 = D/2`. Since `D < 2F`, `D/2 < F`, so `0 < D - r < F` whenever `r <= D/2` and `r < D - F` boundary — concretely, the maximal legal repay `r = D/2` leaves `D - r = D/2 < F` (because `D < 2F`), which is strictly inside `(0, F)` and reverts.
- Full repayment (`r = D`, leaving 0) is forbidden because `D / D = 1 > maxLiquidable`.

So for any `D in (F, 2F)`, `liquidate` reverts for every possible `amountToRepay_`. No liquidator, keeper, or the victim can clear the position via `liquidate`.

Reachability for an unprivileged attacker: `DebtToken.repay` burns the caller's synthetic tokens against a target account's debt (the standard Metronome repay flow accepts an `onBehalfOf`-style account argument; the debt burn in `liquidate` itself, `contracts/Pool.sol:587-588`, shows repayments on arbitrary accounts are a supported primitive). The attacker:

1. Observes a victim with debt `D0` on synthetic token `S`, where `D0 > 2F`.
2. Buys/mints `D0 - D*` of `S` (e.g. via `Pool.swap` or on the open market) and calls `DebtToken.repay(victim, D0 - D*)` choosing `D*` inside `(F, 2F)`, e.g. `D* = 1.5F`.
3. When the victim's position goes underwater (or already is), `Pool.liquidate(S, victim, ..., depositToken)` reverts for all `amountToRepay_`: either `AmountGreaterThanMaxLiquidable` or `RemainingDebtIsLowerThanTheFloor`.

Alternatively, an attacker can deliberately engineer their own position into this band (open debt just above `F`, let collateral price drift) to make their own bad debt un-clearable, or grief every borderline victim in the pool since `repay` is not gated by `SynthContext` roles — the modifiers examined (`whenNotShutdown`, `nonReentrant`, `onlyIfSyntheticTokenExists`, `onlyIfDepositTokenExists`) do not stop it.

### Impact Explanation
Permanent or prolonged liquidation DoS: an unhealthy position in the gap band cannot be liquidated at all, not merely made less attractive. If collateral value continues to fall, the protocol accrues bad debt that no liquidator can remove — the solvency invariant (every unhealthy position is liquidatable up to `maxLiquidable`) is broken. The victim cannot even self-fix via `liquidate` (`CanNotLiquidateOwnPosition` blocks that path anyway), though they could still repay voluntarily — which a rational underwater borrower has reduced incentive to do once liquidation is impossible. The attacker's cost is bounded: they pay `(D0 - D*)` synth, some of which is recoverable from the seized... no — repay gives no collateral back; the cost is real but modest (repaying the difference between `2F` and `F` scales with the floor, typically a small USD amount), making the griefing cheap relative to the victim's frozen position size.

### Likelihood Explanation
Moderate. Requirements: `debtFloorInUsd > 0` (a governance-set but deployed-config parameter; the check at `contracts/Pool.sol:571` only activates when non-zero), `maxLiquidable < 1e18` (default 50%), and permissionless repay — all consistent with the deployed configuration. The attack window is per debt token; the attacker must spend real synth to reduce the victim's debt, but only enough to land inside the `(F, 2F)` band, and can target the largest positions for maximum bad-debt exposure. No privileged role, oracle manipulation, or reentrancy is needed — just public entry points.

### Recommendation
- Allow full liquidation when the entire remaining debt is below the cap-lethal zone: e.g., relax the `maxLiquidable` check when `amountToRepay_ == _debtTokenBalance`, so any position can always be closed completely.
- Alternatively, if `_debtTokenBalance - amountToRepay_` would fall below `debtFloorInUsd`, clamp `amountToRepay_` up to the full balance (forced full liquidation) rather than reverting.
- Optionally gate `DebtToken.repay` on behalf of other accounts (only allow repaying own debt, or allow it but combine with the clamp above so repay-griefing cannot create un-liquidatable states).

### Proof of Concept
Hardhat fork sketch (against deployed `Pool`/`DebtToken`/`DepositToken` proxies on e.g. Base):

```ts
// Setup: victim has debt D0 on msUSD with collateral in msETH DepositToken.
// Assume debtFloorInUsd = F (e.g. $100) and maxLiquidable = 0.5e18.

// 1) Attacker pushes victim into the gap band (F, 2F).
const targetDebt = F.mul(3).div(2);              // 1.5 * F
const victimDebt = await debtToken.balanceOf(victim.address); // > 2*F
const repayAmt = victimDebt.sub(targetDebt);
await syntheticToken.connect(attacker).approve(debtToken.address, repayAmt);
await debtToken.connect(attacker).repay(victim.address, repayAmt);

// 2) Victim is unhealthy (price move or already was).
const { _isHealthy } = await pool.debtPositionOf(victim.address);
expect(_isHealthy).to.be.false;

// 3) Any liquidator attempt fails for all amounts.
const bal = await debtToken.balanceOf(victim.address);   // = targetDebt
// Full repay -> exceeds maxLiquidable (50%)
await expect(
  pool.connect(liquidator).liquidate(syntheticToken.address, victim.address, bal, depositToken.address)
).to.be.revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');
// Max allowed repay (50%) -> remainder = 0.75*F < F
await expect(
  pool.connect(liquidator).liquidate(syntheticToken.address, victim.address, bal.div(2), depositToken.address)
).to.be.revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor');
// Every r in (0, bal/2] leaves remainder in (0, F) -> all revert the same way.
```

Uncertainty noted: the exact `DebtToken.repay` signature (`repay(account, amount)` vs caller-only) was not fully verified due to iteration limits; if repay on behalf of others is restricted, the self-inflicted variant (attacker opens their own position with debt in `(F, 2F)` and lets it go underwater, creating un-clearable bad debt) still stands without it.
