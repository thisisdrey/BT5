### Title
Unchecked `long` accumulation in vote-reward `allowance` can silently overflow, causing permanent freezing of legitimately accrued rewards - (File: `actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java`)

### Summary
`VoteRewardUtil.adjustAllowance` (and its duplicate logic in `MortgageService.adjustAllowance`) accumulates witness/voter reward into the persisted `AccountCapsule.allowance` field using a plain, unchecked `long` addition (`allowance + amount`), while every other place that later reads/spends that same field (`WithdrawRewardProcessor.execute`, `Program.withdrawRewardAndCancelVote`) uses `LongMath.checkedAdd` / `addExact` and throws on overflow. This mirrors the reported `Distributor._executeClaim` pattern: an unbounded accumulator (`records[beneficiary].claimed += claimableAmount`) that is updated without any overflow guard, only to be consumed elsewhere under stricter arithmetic assumptions.

### Finding Description
`VoteRewardUtil.withdrawReward` is reachable from the TVM native opcode `Program.withdrawReward()` / `Program.freeze/vote` flow — i.e. from any smart contract deployed and invoked by an unprivileged account. Each cycle a voter's reward is computed and folded into the account's allowance via: [1](#0-0) 

```java
private static void adjustAllowance(byte[] address, long amount, Repository repository) {
    if (amount <= 0) {
      return;
    }
    AccountCapsule accountCapsule = repository.getAccount(address);
    long allowance = accountCapsule.getAllowance();
    accountCapsule.setAllowance(allowance + amount);   // <-- unchecked long addition
    repository.updateAccount(accountCapsule.createDbKey(), accountCapsule);
}
```

The identical unchecked pattern exists in the non-TVM path used by SR/voter reward accounting: [2](#0-1) 

Nothing prevents `allowance` from continuing to grow every cycle if the account never calls `withdrawReward`/`WithdrawBalanceContract`. There is no cap check before the addition, unlike the contract's own reader logic, which explicitly guards the same operation: [3](#0-2) 

```java
try {
      newBalance = LongMath.checkedAdd(oldBalance, allowance);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractExeException(e.getMessage());
    }
```

and [4](#0-3) 

If `allowance` wraps around (becomes negative or a small positive value) due to the unguarded `+` in `adjustAllowance`, subsequent legitimate withdrawal attempts are permanently blocked: `WithdrawBalanceActuator.validate()` treats any non-positive allowance as "no reward" and reverts: [5](#0-4) 

### Impact Explanation
If the accumulated `allowance` field overflows `Long.MAX_VALUE` (2^63-1), the wraparound corrupts the account's recorded, already-earned reward balance. Because withdrawal-side code checks `allowance <= 0` to reject "no reward" claims, a wrapped (negative) allowance permanently locks the beneficiary out of ever withdrawing their legitimately accrued vote/witness rewards — a permanent freezing-of-funds condition. This is directly analogous to the reported `Distributor._executeClaim` overflow, where an unguarded accumulator addition corrupts a beneficiary's recorded claimed amount and disrupts the distribution/withdrawal process.

### Likelihood Explanation
Exploitability depends on being able to drive the 64-bit `allowance` accumulator to overflow, which requires an astronomically large sum of reward increments over an extremely long time (Long.MAX_VALUE ≈ 9.22×10^18, denominated in sun where total TRX supply is bounded). Under current TRX economics this is not practically reachable in a reasonable timeframe through normal reward accrual, so likelihood is low; however, the code path itself is a genuine defensive-coding gap — the same value is treated with checked arithmetic on the spending side but unchecked arithmetic on the accumulation side, and no test or explicit bound exists to prevent the accumulator from silently wrapping under any future change (e.g., increased reward-per-block parameters, or ViReward decimal changes) that shrinks the effective time-to-overflow.

### Recommendation
Use `LongMath.checkedAdd` (or `Math.addExact`) in `VoteRewardUtil.adjustAllowance` and `MortgageService.adjustAllowance` when updating `accountCapsule`'s allowance, consistent with the checked arithmetic already used in `WithdrawRewardProcessor.execute` and `Program.withdrawRewardAndCancelVote`, so that an impending overflow throws a catchable exception (or is otherwise rejected) instead of silently corrupting the stored reward balance.

### Proof of Concept
1. An account continuously freezes TRX for votes and votes for one or more witnesses via the TVM `vote`/`freeze` opcodes exposed in `Program.java`, but never calls `withdrawReward()`.
2. Every cycle boundary, `VoteRewardUtil.withdrawReward` → `adjustAllowance` performs `accountCapsule.setAllowance(allowance + amount)` with no bounds check.
3. Over a sufficiently long accumulation period (bounded only by application-level economics, not by the code itself), `allowance` approaches and then wraps past `Long.MAX_VALUE`, becoming negative.
4. `WithdrawBalanceActuator.validate()` now sees `accountCapsule.getAllowance() <= 0`, rejecting all future withdrawal attempts with "witnessAccount does not have any reward," permanently freezing the account's earned rewards, even though `WithdrawRewardProcessor`/`Program` would otherwise have used checked arithmetic and thrown loudly had the overflow occurred on their side instead.

```java
  public void adjustAllowance(AccountStore accountStore, byte[] accountAddress, long amount)
      throws BalanceInsufficientException {
    AccountCapsule account = accountStore.getUnchecked(accountAddress);
    long allowance = account.getAllowance();
    if (amount == 0) {
      return;
    }

    if (amount < 0 && allowance < -amount) {
      throw new BalanceInsufficientException(
          String.format("%s insufficient balance, amount: %d, allowance: %d",
              StringUtil.createReadableString(accountAddress), amount, allowance));
    }
    account.setAllowance(allowance + amount);
    accountStore.put(account.createDbKey(), account);
  }
```
