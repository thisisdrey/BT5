### Title
Unbounded stack/heap array allocation from attacker-controlled ABI length words in `ValidateMultiSign`/`BatchValidateSign` precompiles - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
Analogous to CVE-2021-3527 (unbounded VLA size derived from untrusted network data before validation), java-tron's `ValidateMultiSign` and `BatchValidateSign` precompiled contracts decode a "length" value straight out of attacker-controlled calldata and use it to size a Java array (`new byte[len][]`) before any upper-bound check is guaranteed to run.

### Finding Description
`extractBytesArray`, `extractSigArray`, and `extractBytes32Array` read a length field directly from the ABI-encoded calldata and immediately allocate an array of that size: [1](#0-0) [2](#0-1) [3](#0-2) 

`len`/`bytesLen` come from `words[...].intValueSafe()`, which is derived purely from the caller-supplied `data` byte array — the same class of bug as the QEMU usb-redir issue, where a combined/derived size value from untrusted input is used to size a variable-length allocation without an upper bound.

In `ValidateMultiSign.execute`, the `MAX_SIZE` (5) bound on `sigArraySize` is only enforced when the `allowTvmSelfdestructRestriction` feature flag is active: [4](#0-3) 
When that flag is not active, `extractBytesArray`/`extractSigArray` is invoked directly with an attacker-chosen `len`, and the `signatures.length > MAX_SIZE` check only happens *after* the array has already been allocated. The same pattern occurs in `BatchValidateSign.doExecute`: [5](#0-4) 

A separate mitigation (`isValidAbiEncoding`, added for "TIP-854") checks that the *overall* calldata length is consistent with the `(words - headerWords) / itemWords` shape used by the energy formula, but it does not validate that the length word actually embedded at the dynamic-array offset (`words[offset].intValueSafe()`) is bounded or consistent with the real calldata size: [6](#0-5) 
An attacker can therefore craft calldata that satisfies the structural shape check yet still contains an arbitrarily large embedded length prefix, driving `new byte[len][]` to allocate a huge object-reference array.

Whether this throws `OutOfMemoryError` depends on the call path:
- `BatchValidateSign.execute` wraps the body in a broad `catch (Throwable t)` that swallows the error and returns a zero result: [7](#0-6) 
- `ValidateMultiSign.execute` has no such outer catch around the `extractSigArray`/`extractBytesArray` call itself (only the later permission-checking block is wrapped): [8](#0-7) 
An `OutOfMemoryError` thrown there would propagate up through `Program.callToPrecompiledAddress` and further up the VM call stack.

### Impact Explanation
If uncaught, an `OutOfMemoryError`/large transient allocation from a crafted `TriggerSmartContract` calling `ValidateMultiSign` (address `0x...a`) can put memory pressure on, or crash, the node processing the transaction — this fits the "node crash or halt" acceptance criterion. Even where the outer catch in `BatchValidateSign` (or higher-level VM/actuator catches such as those in `VMActuator`) absorbs the exception, the huge transient allocation and subsequent GC pressure is a resource-exhaustion vector reachable by any account with enough energy to invoke the precompile via a plain contract call — no privileged role required.

### Likelihood Explanation
Reachability is straightforward: any account can deploy or call a smart contract that issues a `CALL`/`STATICCALL` to address `0x...9` (`BatchValidateSign`) or `0x...a` (`ValidateMultiSign`), both gated only by `VMConfig.allowTvmSolidity059()` (a long-active hard fork), and supply crafted calldata. The `getEnergyForData` cost formula is based on `data.length`, not on the internal length word, so an attacker can pay a small, bounded energy cost while the internal decode reads an inflated length value from a different word offset. The `isValidAbiEncoding` guard, active only when `allowTvmOsaka` is enabled, does not close this specific gap because it validates the aggregate shape of calldata, not the individual length word used for array sizing.

### Recommendation
Enforce an explicit upper bound (e.g., the same `MAX_SIZE` constants) on all length words read from calldata (`extractBytesArray`, `extractSigArray`, `extractBytes32Array`) *before* allocating any array, independent of the `allowTvmSelfdestructRestriction` feature flag, and validate that decoded offsets/lengths stay within `data.length` before allocation. Wrap `ValidateMultiSign.execute` in a `catch (Throwable)` boundary consistent with `BatchValidateSign`, so any unexpected allocation failure degrades gracefully instead of propagating as an uncaught `Error`.

### Proof of Concept
1. Construct calldata for `validatemultisign(address,uint256,bytes32,bytes[])` where the ABI dynamic-array offset word (`words[3]`) points to a length word crafted to decode via `intValueSafe()` to a very large positive value (e.g., close to `Integer.MAX_VALUE`), while keeping the overall data length small enough to pass `isValidAbiEncoding`'s shape check (or simply not enabling `allowTvmOsaka`/leaving `allowTvmSelfdestructRestriction` disabled, where no shape/size check runs at all).
2. Send a transaction (`TriggerSmartContract`) whose EVM bytecode issues a `CALL` to precompile address `0x0000...000a` with this calldata and sufficient energy to pass `getEnergyForData` (which is computed from `data.length`, not the internal length field).
3. Observe `extractBytesArray`/`extractSigArray` executing `new byte[len][]` with `len` derived from the crafted word, causing an oversized allocation attempt in the node's JVM heap, uncaught by any surrounding `try/catch` in `ValidateMultiSign.execute`.
