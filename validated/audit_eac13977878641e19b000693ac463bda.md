### Title
Relayer reward is paid regardless of Ethereum-side delivery `success` flag - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
`Pallet::process_delivery_receipt` in the Snowbridge V2 outbound queue decodes a `DeliveryReceipt` that carries an explicit `success: bool` field reporting whether the message actually executed successfully on the Ethereum Gateway contract, but the function never inspects or branches on this field. As a result, the relayer reward `order.fee` is registered unconditionally as long as a matching `PendingOrders` entry exists, whether the message succeeded or failed on Ethereum.

### Finding Description
The `DeliveryReceipt` struct explicitly carries a `success` flag decoded straight from the on-chain Ethereum `InboundMessageDispatched` event log: [1](#0-0) 

`submit_delivery_receipt` verifies the Merkle/beacon proof for the log and decodes the receipt, then immediately calls `process_delivery_receipt`: [2](#0-1) 

Inside `process_delivery_receipt`, the code checks the gateway address, resolves the reward account, fetches the `PendingOrder` by `nonce`, and pays out `order.fee` purely based on `order.fee > 0` — the `receipt.success` field is decoded but is dead data, never read or branched on: [3](#0-2) 

This mirrors the seed report's bug class exactly: a value that is supposed to gate which code path/behavior executes (`lookback` deciding TWAP vs spot price in the external report; `success` deciding whether a delivery reward should be paid here) is decoded into the function but the actual conditional logic ignores it, so the function always takes the same branch (`getPrice`/pay reward) independent of the intended condition.

The doc comment for the pallet even documents the intended flow as "pay reward with fee attached in the order" without any success gating, confirming the omission is structural, not merely a typo in one branch: [4](#0-3) 

No other guard in the call path re-introduces a success check — `submit_delivery_receipt` only verifies proof validity (that the log genuinely came from the Gateway) and existence of the `PendingOrder`; it says nothing about whether the *dispatched command itself* succeeded on Ethereum: [5](#0-4) 

### Impact Explanation
This is a public, unprivileged-actor-reachable payout logic bug in bridge reward accounting. Any relayer (not a privileged or malicious-infrastructure actor — any ordinary account permitted to call `submit_delivery_receipt`) that submits a valid proof for a message whose Ethereum-side execution failed (`success = false`, e.g. due to reverted commands or exhausted gas) still collects the full `order.fee` reward registered via `T::RewardPayment::register_reward`. This is "public underpriced work" in the sense that failed/low-quality relaying work is compensated identically to successful work, undermining the intended incentive design that presumably ties the fee to correct message execution, and allows systematic fee extraction for messages that never actually completed on the Ethereum side.

### Likelihood Explanation
High likelihood: this triggers on the normal `submit_delivery_receipt` code path with no special preconditions — any relayer submitting a legitimate proof of a failed-execution log will realize the incorrect reward, and the decoded `success` field being unused is directly visible in the source and not gated by any external validation.

### Recommendation
Branch on `receipt.success` before/while paying the reward — e.g. only call `T::RewardPayment::register_reward` when `receipt.success` is `true`, and otherwise handle the failure case appropriately (e.g. no reward, or a reduced/partial reward per protocol design), analogous to fixing the seed report's ternary condition to correctly gate behavior by the intended flag:

```rust
if receipt.success && order.fee > 0 {
    T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee);
}
```

### Proof of Concept
1. A message is queued via `do_process_message`, creating a `PendingOrder { nonce, fee, .. }` with `fee > 0`. [6](#0-5) 
2. On Ethereum, the Gateway contract processes the message but the command execution reverts/fails, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer builds a valid Merkle/beacon proof for this event log (the proof is valid regardless of the `success` value it contains) and calls `submit_delivery_receipt`.
4. `T::Verifier::verify` succeeds (the log is authentic), `DeliveryReceipt::try_from` decodes `success = false` into the struct. [7](#0-6) 
5. `process_delivery_receipt` is invoked; it never reads `receipt.success`, finds `order.fee > 0`, and calls `T::RewardPayment::register_reward`, paying the relayer the full fee even though the message failed on Ethereum. [8](#0-7) 

The existing test suite only exercises `success: true` paths (e.g. `submit_delivery_receipt_succeeds_after_unhalt`), so there is no regression coverage asserting rewards are withheld on `success: false`. [9](#0-8)

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

// After governance resumes the bridge, legitimate delivery receipts flow through again:
// the order is paid out and removed from storage.
#[test]
fn submit_delivery_receipt_succeeds_after_unhalt() {
	new_tester().execute_with(|| {
		let nonce = 0;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_valid_event_proof());

		// Bridge halted — receipt rejected, order untouched.
		set_verifier_halted(true);
		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);
		assert!(PendingOrders::<Test>::get(nonce).is_some());

		// Bridge resumed — same receipt succeeds and the order is settled.
		set_verifier_halted(false);
		assert_ok!(OutboundQueue::submit_delivery_receipt(origin, event));
		assert!(PendingOrders::<Test>::get(nonce).is_none());

		System::assert_has_event(mock::RuntimeEvent::OutboundQueue(Event::MessageDelivered {
			nonce,
		}));
	});
}
