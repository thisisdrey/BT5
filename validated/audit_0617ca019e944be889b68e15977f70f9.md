### Title
Unprotected use of live, swap-manipulable pool reserves in Exchange Inject/Withdraw lets an attacker sandwich liquidity providers to steal value - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java, actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
TRON's native bancor-style `Exchange` feature computes the paired-token amount for liquidity injection and withdrawal directly from the exchange pool's current `firstTokenBalance`/`secondTokenBalance` (the on-chain "reserves"), exactly the pattern flagged in the Maverick oracle report where a manipulable pool reserve ratio is used as a price without protection. Unlike `ExchangeTransactionContract`, which carries a user-supplied `expected` field enforced in `ExchangeTransactionActuator`, `ExchangeInjectContract` and `ExchangeWithdrawContract` provide no minimum/maximum bound, so the calculated counterpart amount is fully exposed to same-block reserve manipulation via ordinary swap transactions (`ExchangeTransactionContract`).

### Finding Description
`ExchangeInjectActuator.execute()` computes the amount of the "other" token to be pulled from (or credited to) the account using only the pool's live balances: [1](#0-0) 

The same reserve-ratio calculation, with the same lack of bound-checking, is repeated in validation: [2](#0-1) 

`ExchangeWithdrawActuator.execute()` mirrors this pattern for withdrawals — the amount of the paired token returned is derived purely from the pool's instantaneous balance ratio: [3](#0-2) 

These pool balances (`firstTokenBalance`/`secondTokenBalance`) are the same state mutated by ordinary swaps in `ExchangeTransactionActuator`, via `ExchangeCapsule.transaction()`, which applies the bancor relay-token formula and directly rewrites the reserves: [4](#0-3) 

Any unprivileged account can submit an `ExchangeTransactionContract` to swap a large amount into (or out of) an existing exchange pool, arbitrarily skewing the `firstTokenBalance`/`secondTokenBalance` ratio for the duration it takes to include the next transaction, exactly as the flash-loan swap in the Maverick PoC skews `getReserves()`. Because `ExchangeInjectContract`/`ExchangeWithdrawContract` carry no `expected` field (contrast with `ExchangeTransactionContract.expected` at protobuf line 36) and the actuator performs no slippage/bound check against the caller's intended ratio, an attacker who can order transactions ahead of a victim's Inject/Withdraw (classic sandwich: swap → victim's Inject/Withdraw executes at the skewed ratio → swap back) can force the victim to inject a wildly disproportionate amount of the second token, or withdraw far less than the fair share of one asset, while the attacker's back-run swap captures the difference risk-free. [5](#0-4) 

### Impact Explanation
An attacker can extract value from Exchange liquidity providers (creators, who are ordinary unprivileged accounts able to `ExchangeCreateContract`) by sandwiching their `ExchangeInjectContract`/`ExchangeWithdrawContract` transactions with `ExchangeTransactionContract` swaps that manipulate the pool ratio just before execution and revert it right after. This results in concrete unauthorized transfer/theft of TRX or TRC10 asset value from the victim to the attacker, satisfying the "theft of funds" impact bar. This is High severity because it requires no special privilege — only ordinary transaction broadcasting capability and the ability to control transaction ordering within the block/mempool (standard MEV-style front-running available to any broadcaster), and it directly steals real on-chain value.

### Likelihood Explanation
Likelihood is High: the Exchange feature is a core, always-available production feature reachable from any signed transaction (no SR/witness/committee privilege needed), the reserve values are trivially observable on-chain, and swapping to skew the ratio costs only normal transaction fees. The lack of an `expected`/minimum-bound field in the Inject/Withdraw contracts (unlike Transaction) makes this a straightforward, low-cost attack pattern analogous to sandwiching unprotected `addLiquidity`/`removeLiquidity` calls in AMMs.

### Recommendation
Add a caller-supplied bound (e.g., `expected`/minimum-received or maximum-paired-quantity, similar to `ExchangeTransactionContract.expected`) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` so the transaction reverts if the computed counterpart amount falls outside the caller's tolerance, closing the sandwich window created by reserve manipulation between blocks/transactions.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) transaction from a victim targeting exchange `id` with `firstTokenBalance`/`secondTokenBalance` currently balanced (e.g., 1:1).
2. Attacker submits (and gets ordered first, e.g. by paying higher priority/energy or via mempool visibility) an `ExchangeTransactionContract` selling a large amount of `firstTokenID` into the pool, skewing `firstTokenBalance`/`secondTokenBalance` heavily (per `ExchangeCapsule.transaction()` at [6](#0-5) ).
3. Victim's `ExchangeInjectContract` executes next, and `ExchangeInjectActuator.execute()` computes `anotherTokenQuant` from the now-skewed ratio ( [1](#0-0) ), forcing the victim to deposit far more of the second token (or receive far less on withdraw) than intended, with no `expected` field to reject the unfavorable rate.
4. Attacker submits a second `ExchangeTransactionContract` swapping back, restoring the ratio and realizing a profit extracted from the victim's mispriced injection/withdrawal, all within the reach of an ordinary unprivileged transaction broadcaster.

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
