### Title
Outbound queue commits Ethereum relayer reward using pricing parameters re-read at processing time, decoupled from the fee actually charged at send time - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
The external report describes a bug class where a public-facing operation reads a cached/mutable value (a contract address) at one point in time and that value can silently drift out of sync with the value used later, so users unknowingly interact with stale state. The Snowbridge outbound queue has a structurally identical pattern: the fee a user is charged when a message is submitted (`validate`) is computed from `T::PricingParameters::get()` read at *send time*, while the relayer reward and `max_fee_per_gas` that are permanently baked into the committed message (and paid out on Ethereum) are computed from `T::PricingParameters::get()` read again at *processing time* (`do_process_message`), which can be an arbitrary number of blocks later. There is no snapshot/binding of the pricing parameters to the message at enqueue time, so the two reads of the same "cache" are not guaranteed to agree.

### Finding Description
`Pallet::validate` (send time) computes the fee charged to the sender using the pricing parameters that are live in storage at that instant: [1](#0-0) 

The message is then only enqueued (`T::MessageQueue::enqueue_message`) — its actual commitment happens later, when the `MessageQueue` pallet invokes `do_process_message`, subject to `T::MaxMessagesPerBlock` throttling and general queue backlog: [2](#0-1) 

At that later point, `do_process_message` re-reads `T::PricingParameters::get()` from storage and uses this — possibly different — value to compute `reward` and `max_fee_per_gas`, which are permanently embedded into the `CommittedMessage` that is merkle-committed and relayed to the Ethereum gateway contract for payout: [3](#0-2) 

`PricingParameters` is a plain root-settable storage value with no versioning, timestamp, or historical mapping tying a specific value to a specific in-flight message: [4](#0-3) [5](#0-4) 

There is no mechanism analogous to `syncAllContracts`'s proposed fix (snapshot the value used, or bind the value read at commit-time to the value that was read/charged at submission-time). The two independent reads of the same mutable "cache" (`PricingParameters`) at different lifecycle stages of the same message is exactly the "old contract version mistakenly used" bug class from the external report, applied to bridge reward accounting instead of contract addresses.

### Impact Explanation
Every accepted message carries a fee that was charged upfront based on parameters `P1`, but the amount promised to the Ethereum relayer (`reward`, `max_fee_per_gas`) is computed from whatever parameters `P2` are live when the message queue eventually processes that message. If `P2 > P1` (parameters increased between send and commit, e.g. exchange rate or fee_per_gas governance update), the protocol commits to paying relayers more than was actually collected from the sender for that specific message — an unbacked/underfunded payout obligation on the reward side of the bridge. If `P2 < P1`, the sender is systematically overcharged relative to what is actually promised to relayers, and users/consumers of the outbound-queue API (e.g. XCM exporters charging fees via `calculate_fee`/`validate`) cannot know at submission time what will actually be embedded and paid out once the message clears the queue backlog. This directly violates the required invariant that "bridge rewards ... must conserve value and settle exactly once to the rightful beneficiary and amount," since the amount that is actually settled on Ethereum is decided independently of, and can diverge from, the amount collected on the Polkadot side.

### Likelihood Explanation
This does not require any privileged, malicious, or off-chain actor — it is triggered purely by the passage of time between `validate` (send) and `do_process_message` (commit), which is inherent to the design (`MaxMessagesPerBlock` throttling and normal queue backlog mean commit can happen many blocks after send). Any legitimate, routine governance update of `set_pricing_parameters` (a normal operational action documented as happening "every few weeks") that lands while messages are sitting in the outbound queue is sufficient to trigger the mismatch — no admin abuse or attacker action is needed, only ordinary operation of the bridge under load.

### Recommendation
Snapshot the pricing parameters used to charge the fee into the `Ticket`/`QueuedMessage` at `validate` time, and have `do_process_message` use that snapshotted value (rather than re-reading live `PricingParameters` storage) when computing `reward` and `max_fee_per_gas` for the committed message. Alternatively, version `PricingParameters` (similar to the `ContractSynced`-style fix in the external report) and record which version was used to charge the fee, then reconcile/refuse commit if the version has changed materially, or true up rewards from a dedicated buffer funded exactly by the fees actually collected under the corresponding parameter version.

### Proof of Concept
1. Governance sets `PricingParameters = P1` (e.g. low `fee_per_gas`/`rewards.remote`).
2. A user submits a message via `SendMessage::validate`; fee is calculated and charged using `P1` (`calculate_fee(gas_used_at_most, T::PricingParameters::get())` in `send_message_impl.rs:59-60`).
3. Message is enqueued (`deliver`) but queue is backlogged (`MaxMessagesPerBlock` cap) so it is not processed immediately.
4. Before the message reaches `do_process_message`, governance calls `set_pricing_parameters` to update to `P2` with a higher `fee_per_gas`/`rewards.remote` (a routine, non-malicious operational update, per pallet documentation).
5. `do_process_message` eventually runs for the queued message, reading `T::PricingParameters::get()` which now returns `P2`, and embeds `reward`/`max_fee_per_gas` computed from `P2` into the `CommittedMessage` (`lib.rs:332-352`).
6. The relayer reward promised on Ethereum for this message is now based on `P2`, while only the `P1`-based fee was ever collected from the user at step 2 — demonstrating the settlement-amount / charged-amount mismatch caused by reading the same mutable pricing "cache" at two different, unbound points in the message lifecycle.

			_: ProcessMessageOriginOf<T>,
			mut message: &[u8],
		) -> Result<bool, ProcessMessageError> {
			use ProcessMessageError::*;

			// Yield if the maximum number of messages has been processed this block.
			// This ensures that the weight of `on_finalize` has a known maximum bound.
			ensure!(
				MessageLeaves::<T>::decode_len().unwrap_or(0) <
					T::MaxMessagesPerBlock::get() as usize,
				Yield
			);

		pub fn set_pricing_parameters(
			origin: OriginFor<T>,
			params: PricingParametersOf<T>,
		) -> DispatchResult {
			ensure_root(origin)?;
			params.validate().map_err(|_| Error::<T>::InvalidPricingParameters)?;
			PricingParameters::<T>::put(params.clone());

			let command = Command::SetPricingParameters {
				exchange_rate: params.exchange_rate.into(),
				delivery_cost: T::InboundDeliveryCost::get().saturated_into::<u128>(),
				multiplier: params.multiplier.into(),
			};
			Self::send(PRIMARY_GOVERNANCE_CHANNEL, command, PaysFee::<T>::No)?;

			Self::deposit_event(Event::PricingParametersChanged { params });
			Ok(())
		}
