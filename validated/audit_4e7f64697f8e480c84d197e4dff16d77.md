### Title
NULL Pointer Dereference in `TransactionTrace.checkIsConstant` via Malformed `TriggerSmartContract` Parameter - (File: `chainbase/src/main/java/org/tron/core/db/TransactionTrace.java`)

### Summary
`ContractCapsule.getTriggerContractFromTransaction()` swallows `InvalidProtocolBufferException` and returns `null` when the transaction's `Any` parameter cannot be unpacked as a `TriggerSmartContract`. `TransactionTrace.checkIsConstant()` calls this method and immediately dereferences the result with `.getContractAddress()` without any null check, exactly mirroring the CVE-2019-20914 pattern where a parser helper can return a null/uninitialized handle that is dereferenced by the caller without validation.

### Finding Description
`ContractCapsule.getTriggerContractFromTransaction`: [1](#0-0) 

returns `null` on any `InvalidProtocolBufferException` while unpacking the `Any` contract parameter. The caller, `TransactionTrace.checkIsConstant()`, does not check for null before invoking `.getContractAddress()`: [2](#0-1) 

The `Contract.type` enum field (used to route dispatch to `TRX_CONTRACT_CALL_TYPE` in the `TransactionTrace` constructor) and the `Any` `parameter` field's `type_url`/payload bytes are independently attacker-controlled in a raw broadcast transaction. An attacker can craft a `Transaction.Contract` with `type = TriggerSmartContract` but with a `parameter` `Any` whose `type_url` does not match `TriggerSmartContract`, or whose payload is otherwise malformed such that `Any.unpack(TriggerSmartContract.class)` throws `InvalidProtocolBufferException`. This makes `getTriggerContractFromTransaction` return `null`, and the immediate `.getContractAddress()` call on that null reference throws an unhandled `NullPointerException`.

This is reachable through the normal transaction-processing/application path (`Manager` invokes `checkIsConstant()` as part of handling `TriggerSmartContract`-type contracts), i.e. from any signed transaction broadcast by an unprivileged account, whenever `getAllowTvmConstantinople() != 1` (the guard at the top of the method).

### Impact Explanation
An unhandled `NullPointerException` thrown during transaction/block processing in `Manager` can crash or destabilize node processing of that transaction path, potentially causing denial of service on nodes still gated by the `AllowTvmConstantinople` flag or on any deployment where that proposal parameter is 0. Depending on where in `pushBlock`/`processTransaction` the exception propagates and whether it is caught by a broad `catch (Exception e)` wrapper elsewhere in `Manager`, this can range from a single dropped transaction to a full node crash impacting all callers relying on that node (RPC/HTTP/gRPC availability).

### Likelihood Explanation
Likelihood is moderate-to-high for network configurations where `AllowTvmConstantinople` is still 0, since the exploit requires only a single self-crafted transaction with `Contract.type = TriggerSmartContract` and a corrupted `parameter.Any` payload — something well within reach of any transaction broadcaster with no special privileges. However, on the current TRON mainnet this dynamic parameter has long been set to 1, which would make the vulnerable branch dead code in practice; this significantly reduces likelihood on production mainnet but the same code path could be significant on private/test chains or forks that have not enabled `AllowTvmConstantinople`.

### Recommendation
Add a null check after calling `ContractCapsule.getTriggerContractFromTransaction()` in `TransactionTrace.checkIsConstant()` and throw a `ContractValidateException` (consistent with other null-parameter validation patterns used throughout the actuator codebase, e.g. `ClearABIContractActuator.validate()`) instead of allowing an unchecked NPE to propagate.

### Proof of Concept
1. Construct a `Transaction.raw` with a single `Contract` where `type = TriggerSmartContract`.
2. Set `Contract.parameter` to an `Any` whose `type_url` does not correspond to `TriggerSmartContract` (or whose value bytes are truncated/corrupted) so that `Any.unpack(TriggerSmartContract.class)` throws `InvalidProtocolBufferException`.
3. Sign and broadcast the transaction to a node where `getAllowTvmConstantinople() == 0`.
4. During transaction processing, `TransactionTrace.checkIsConstant()` calls `ContractCapsule.getTriggerContractFromTransaction(...)`, which returns `null`; the subsequent `triggerContractFromTransaction.getContractAddress()` throws an unhandled `NullPointerException`.

Note: I could not fully verify at what layer in `Manager` (grep showed two call sites) this exception is ultimately caught versus propagated uncaught to crash the node — this would need direct inspection of the exact call sites in `framework/src/main/java/org/tron/core/db/Manager.java`, which I was not able to complete before running out of tool iterations. This affects confidence in the exact blast radius (single-tx failure vs. broader instability) but does not change the root-cause finding of the unchecked null dereference itself.

  public static TriggerSmartContract getTriggerContractFromTransaction(Transaction trx) {
    try {
      Any any = trx.getRawData().getContract(0).getParameter();
      TriggerSmartContract contractTriggerContract = any.unpack(TriggerSmartContract.class);
      return contractTriggerContract;
    } catch (InvalidProtocolBufferException e) {
      return null;
    }
  }
