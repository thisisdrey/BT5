### Title
Unchecked boolean return value from `reduceAssetAmountV2` in `ExchangeInjectActuator.execute()` can silently skip asset debits - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
`ExchangeInjectActuator.execute()` calls `AccountCapsule.reduceAssetAmountV2(...)` twice (for `tokenID` and `anotherTokenID`) without checking the boolean it returns. `reduceAssetAmountV2` reports success/failure by return value rather than by throwing, exactly the "silent failure" pattern flagged in the ERC20 `safeTransfer` report: a state-changing balance operation whose failure signal is ignored by the caller.

### Finding Description
`reduceAssetAmountV2` in `AccountCapsule` mutates the account's asset map only when the reduction succeeds, and returns `false` (doing nothing) when it cannot deduct the requested amount: [1](#0-0) 

Several actuators that call this same method correctly check the return value and abort the transaction on failure, e.g. `TransferAssetActuator`: [2](#0-1) 
and `ParticipateAssetIssueActuator`: [3](#0-2) 

`ExchangeInjectActuator.execute()`, however, ignores the return value entirely for both legs of the injection: [4](#0-3) 

Meanwhile, the exchange pool balances (`exchangeCapsule.setBalance(...)`) are computed and persisted unconditionally at lines 75-83, and the transaction is marked `SUCESS` regardless of whether the account's asset balance was actually debited.

`ExchangeInjectActuator.validate()` does call `assetBalanceEnoughV2` before execution, which in normal operation should make `reduceAssetAmountV2` succeed: [5](#0-4) 

However, unlike `TransferAssetActuator`/`ParticipateAssetIssueActuator`, this actuator has no defense-in-depth check in `execute()` itself. If `assetBalanceEnoughV2` and `reduceAssetAmountV2` ever diverge (e.g. due to differing handling of the `AllowSameTokenName`/V1-vs-V2 asset key branches, or a future code change that alters one but not the other), the mismatch is silently absorbed: the exchange pool is credited with tokens the owner's account was never actually debited for, producing unbacked exchange liquidity. I was not able to fully verify within the available index whether `assetBalanceEnoughV2` and `reduceAssetAmountV2`'s branch conditions (V1 name-key vs. V2 token-id-key) are perfectly consistent in every historical code path of this repo; that discrepancy analysis would benefit from a full read of `AccountCapsule.assetBalanceEnoughV2`, which the search results did not fully surface.

### Impact Explanation
If the unchecked `reduceAssetAmountV2` call fails while validate's pre-check passes (due to any inconsistency between the two independent checks, or due to future refactors that touch one but not the other), the actuator would still report success and update the `ExchangeCapsule` pool balances as if the token was received, while the submitter's actual asset balance is untouched. This creates value out of nothing in the on-chain bancor-style exchange pool — a fund-integrity/inflation issue, matching the "loss of funds due to unchecked transfer" class of the original report. Because `ExchangeInjectActuator` is reachable by any account holding an exchange (a normal signed `ExchangeInjectContract` transaction), this is exploitable by an ordinary transaction broadcaster without special privilege, if the divergence condition can be triggered.

### Likelihood Explanation
Under the current code, `validate()`'s `assetBalanceEnoughV2` check appears to gate execution such that `reduceAssetAmountV2` should normally succeed, so the practical likelihood today is lower than the original ERC20 case (where the token contract is fully external and untrusted). The residual risk is architectural: the pattern of silently ignoring a success/failure boolean from a balance-mutating method is a latent hazard — it removes the fail-safe that sibling actuators (`TransferAssetActuator`, `ParticipateAssetIssueActuator`) intentionally include, and any future divergence between the validate-time and execute-time checks (e.g. asset key resolution changes, V1/V2 migration edge cases) would go undetected and produce an inconsistent, unbacked ledger state instead of a reverted transaction.

### Recommendation
In `ExchangeInjectActuator.execute()`, check the boolean returned by both `reduceAssetAmountV2` calls (lines 91 and 97-98) and throw a `ContractExeException` (mirroring `TransferAssetActuator`'s `"reduceAssetAmount failed !"` pattern) if either call returns `false`, so the transaction fails atomically rather than silently proceeding with partially-applied state.

### Proof of Concept
No standalone PoC could be constructed purely from static analysis; the divergence between `assetBalanceEnoughV2` (used in `validate()`) and `reduceAssetAmountV2` (used unchecked in `execute()`) is the condition that would need to be triggered, and confirming an exact code path where they disagree requires deeper review of `AccountCapsule.assetBalanceEnoughV2` than the available index exposed. Structurally, the defect is demonstrable by comparing `ExchangeInjectActuator.execute()` lines 85-99 (unchecked) against `TransferAssetActuator.execute()` lines 75-79 (checked) using the same underlying `reduceAssetAmountV2` API.

  public boolean reduceAssetAmountV2(byte[] key, long amount,
                                     DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    //key is token name
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAsset(nameKey, subtractExact(currentAmount, amount, disableJavaLangMath))
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenID = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenID);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }

    return false;
  }
