## Analysis Result [1](#0-0) 

### Title
Unbounded full-VotesStore scan in `Wallet.getPaginatedNowWitnessList()` allows anonymous API-driven DoS - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
`Wallet.getPaginatedNowWitnessList()`, the handler behind the public `getPaginatedNowWitnessList` gRPC/HTTP query, calls the private helper `countVote(votesStore)` on every single invocation. That helper does a full iterator scan over the entire `VotesStore` — a key-value store with one entry per distinct voting account — and, for each entry, iterates its `oldVotes` and `newVotes` lists. Unlike the analogous `MaintenanceManager.countVote()` used during block-application maintenance, this query-path variant never deletes the entries it scans, so the store keeps growing with every `VoteWitnessContract`/`VoteWitnessV2` transaction until the next maintenance cycle clears it. Because the number of records is driven entirely by unprivileged, cheap voting transactions, an attacker can inflate `VotesStore` to a very large size and then repeatedly hit this single read-only API endpoint to force the node to perform an ever-larger, unbounded, synchronous scan — the same root-cause pattern as the reported `clearLoop()` issue (an iteration count controlled by attacker-growable on-chain state, with no page/limit protecting the internal work), except here the "gas" that gets exhausted is real CPU/IO time on a public, unauthenticated query path rather than a transaction's gas limit.

### Finding Description
`getPaginatedNowWitnessList(offset, limit)` is exposed via `RpcApiService`, `FullNodeHttpApiService`, `SolidityNodeHttpApiService`, and `HttpApiOnSolidityService` (`GetPaginatedNowWitnessListServlet`), all reachable by any anonymous client without authentication. Although the method accepts `offset`/`limit` and caps `limit` at `WITNESS_COUNT_LIMIT_MAX`, that pagination is only applied to the *output* witness list; internally it unconditionally performs: [2](#0-1) 

`countVote()` walks every key in `VotesStore` and every `Vote` entry inside each `VotesCapsule`: [3](#0-2) 

`VotesStore` entries are created/updated by ordinary `VoteWitnessActuator`/`VoteWitnessProcessor` executions and are only cleared during `MaintenanceManager.doMaintenance()` at the end of each voting cycle: [4](#0-3) 

Between maintenance cycles, any account can cast a `VoteWitnessContract` (subject only to owning a minimal amount of frozen TRX/TRON Power) to add/keep an entry in `VotesStore`; an attacker who creates many low-cost voting accounts can grow the store to a large size. Every subsequent call to `getPaginatedNowWitnessList` (or `getWitnessList`-adjacent query paths that also rely on `countVote`) then re-scans the entire inflated store, so the request cost scales linearly with attacker-controlled state, with no limit or timeout, exactly mirroring the `clearLoop()` unbounded double-loop pattern but on a public read API instead of inside a single transaction.

### Impact Explanation
Because the endpoint is unauthenticated and can be invoked arbitrarily often (e.g., in a tight loop from many clients), and its internal cost grows with attacker-inflated `VotesStore` size, a full node can be made to spend increasing CPU/IO servicing this one query, degrading its ability to serve other API requests or keep up with block processing — a resource-exhaustion/API-availability impact rather than a fund-loss bug, consistent with the "Low/Medium impact, High likelihood" characterization of the original `clearLoop()` finding.

### Likelihood Explanation
High: voting is a normal, cheap, unprivileged transaction; the query endpoint requires no authentication and no rate limiting is evident in the method itself; and the scan cost is not bounded by the requested `limit`/`offset`.

### Recommendation
Cache or incrementally maintain the aggregated vote-count deltas instead of recomputing them from a full `VotesStore` scan on every query call, or bound/paginate the internal scan (e.g., process it in the maintenance-period incremental manner already used by `MaintenanceManager`, or maintain a running `Map<witness, delta>` updated at vote-transaction time rather than at query time).

### Proof of Concept
1. Create N low-cost accounts, freeze the minimum balance required to vote, and submit `VoteWitnessContract` transactions from each, so `VotesStore` accumulates N entries (this persists until the next maintenance cycle, `MaintenanceManager.doMaintenance()`, clears it).
2. Repeatedly call the public `getPaginatedNowWitnessList` HTTP/gRPC endpoint (`framework/src/main/java/org/tron/core/Wallet.java:770-822`) before maintenance runs.
3. Each call triggers `countVote(votesStore)` (`Wallet.java:842-872`), which is O(N) over the inflated store; as N grows, per-request latency and node CPU/IO usage grow correspondingly, degrading query-service availability for legitimate clients.

  public WitnessList getPaginatedNowWitnessList(long offset, long limit) throws
      MaintenanceUnavailableException {
    if (limit <= 0 || offset < 0) {
      return null;
    }
    if (limit > WITNESS_COUNT_LIMIT_MAX) {
      limit = WITNESS_COUNT_LIMIT_MAX;
    }

    /*
      In the maintenance period, the VoteStores will be cleared.
      To avoid the race condition of VoteStores deleted but Witness vote counts not updated,
      return retry error.
      Only apply to requests that rely on the latest block,
      which means the normal fullnode requests with HEAD cursor.
    */
    boolean isMaintenance = chainBaseManager.getDynamicPropertiesStore().getStateFlag() == 1;
    if (isMaintenance && !Args.getInstance().isSolidityNode() && getCursor() == Cursor.HEAD) {
      String message =
          "Service temporarily unavailable during maintenance period. Please try again later.";
      throw new MaintenanceUnavailableException(message);
    }
    // It contains the final vote count at the end of the last epoch.
    List<WitnessCapsule> witnessCapsuleList = chainBaseManager.getWitnessStore().getAllWitnesses();
    if (offset >= witnessCapsuleList.size()) {
      return null;
    }

    VotesStore votesStore = chainBaseManager.getVotesStore();
    // Count the vote changes for each witness in the current epoch, it is maybe negative.
    Map<ByteString, Long> countWitness = countVote(votesStore);

    // Iterate through the witness list to apply vote changes and calculate the real-time vote count
    witnessCapsuleList.forEach(witnessCapsule -> {
      long voteCount = countWitness.getOrDefault(witnessCapsule.getAddress(), 0L);
      witnessCapsule.setVoteCount(witnessCapsule.getVoteCount() + voteCount);
    });

    // Use the same sorting logic as in the Maintenance period
    WitnessStore.sortWitnesses(witnessCapsuleList,
        chainBaseManager.getDynamicPropertiesStore().allowWitnessSortOptimization());

    List<WitnessCapsule> sortedWitnessList = witnessCapsuleList.stream()
        .skip(offset)
        .limit(limit)
        .collect(Collectors.toList());

    WitnessList.Builder builder = WitnessList.newBuilder();
    sortedWitnessList.forEach(witnessCapsule ->
        builder.addWitnesses(witnessCapsule.getInstance()));

    return builder.build();
  }

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
  }

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }
