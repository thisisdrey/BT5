Based on my analysis, I found a strong structural analog in the ETH-implicit wallet contract's in-flight transaction bookkeeping.

### Title
Wallet Contract `has_in_flight_tx` flag is never reset if a scheduled Promise panics before invoking its callback, permanently DoSing the ETH-implicit account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The near-wallet-contract (the required entry point for all ETH-implicit accounts) tracks whether a transaction is "in flight" via a `has_in_flight_tx` boolean, intended to serialize execution so only one Ethereum-emulated transaction is processed at a time.

### Finding Description
`rlp_execute` sets `has_in_flight_tx = true` before returning a `Promise` chain, and the invariant documented on the struct requires that this flag be reset to `false` whenever the promise chain resolves [1](#0-0) . The flag is only ever cleared inside the various private callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) .

This mirrors the report's root cause exactly: a state-machine "in progress" flag is advanced when a cross-domain action is dispatched, but there is no code path that resets/recovers it if the promise chain never reaches one of the reset points (e.g. the scheduled Promise itself runs out of gas, panics, or the callback function call is malformed/host-errors before `self.has_in_flight_tx = false` executes, or if a `#[private]` callback panics due to an unexpected input from an untrusted cross-contract callee like the address registrar or a NEP-141 token). NEAR host semantics guarantee the callback function is *scheduled*, but if the callback itself panics (e.g., due to an unanticipated response shape, integer overflow, or gas exhaustion inside the callback body before the flag reset line executes), the contract state change (including the `has_in_flight_tx = false` reset) is rolled back for that receipt, leaving `has_in_flight_tx` permanently `true` in persisted state.

Once `has_in_flight_tx` is stuck `true`, every subsequent call to `rlp_execute` — the sole method by which an ETH-implicit account can be controlled — is short-circuited and rejected with "transaction already in progress" [6](#0-5) , with no method available to clear the flag externally (ETH-implicit accounts cannot have a full access key added, and `AddFullAccessKey`/`DeleteAccount`/`DeployContract` actions are explicitly unsupported through the wallet contract, per `UnsupportedAction`) [7](#0-6) .

### Impact Explanation
This permanently freezes the account: NEAR/tokens held by the ETH-implicit account become inaccessible because the wallet contract is the only interface into the account and it now unconditionally refuses to schedule any action. This satisfies the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Triggering this requires only calling `rlp_execute` with an Ethereum transaction whose downstream promise chain (self-transfer, NEP-141 transfer via `storage_balance_of`/`storage_deposit`, or address-registrar lookup for base-token transfers) causes a panic in the corresponding callback — e.g. supplying a target/token contract that returns a response the callback does not defensively handle, or crafting arguments that push a callback over its statically allocated gas (`RLP_EXECUTE_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS` are small fixed budgets) [8](#0-7) . Because these are ordinary user-facing calls (no special privileges required, callable by any relayer/account), this is reachable by an unprivileged actor, matching the report's "external pre-conditions: none."

### Recommendation
Reset `has_in_flight_tx` defensively rather than only inside the "happy path" of each callback — e.g. reset it at the very start of every `#[private]` callback before any fallible logic runs (already partially done, but a panic inside the callback itself still rolls back the reset), and/or introduce a self-recovery/timeout mechanism (analogous to NEAR's own PromiseYield timeout) that clears `has_in_flight_tx` if no callback executes within a bounded number of blocks, so a malformed or gas-exhausting downstream response cannot permanently brick the account.

### Proof of Concept
Not independently executed; derivation is based on static code review of `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`. A concrete PoC would deploy the wallet contract for an ETH-implicit account, call `rlp_execute` with an ERC-20 transfer action whose `token_id` is a malicious/misbehaving NEP-141-like contract that either (a) returns a `storage_balance_of` response causing `nep_141_storage_balance_callback`'s deserialization/matching logic to panic, or (b) is crafted so the chained `storage_deposit` + transfer calls exceed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`'s static budget, causing the callback receipt to fail with an out-of-gas panic before `self.has_in_flight_tx = false` is durably committed. Because I could not run this against a live node, I cannot confirm whether the near-sdk runtime guarantees the flag write happens-before a possible panic in the same function body (Rust field assignment order suggests it does for logic panics after the assignment, but not for panics that occur due to gas exhaustion mid-function or for promises that are scheduled but never resolve due to receiver-side congestion/failure prior to invoking the callback at all — this needs confirmation via a live Devin session with contract deployment tooling).
