### Title
Stale Votes Re-Activated on Owner Re-Addition in Multisig Account — (`aptos-move/framework/aptos-framework/sources/multisig_account.move`)

---

### Summary

`multisig_account.move` stores per-transaction votes in a `SimpleMap<address, bool>` that is never cleared when an owner is removed. `num_approvals_and_rejections_internal` counts only votes from the *current* owners list, so removal temporarily invalidates a vote. However, when the same address is re-added as an owner, its stale vote is silently re-activated and counted toward the approval threshold — without the owner ever casting a new vote. This is the direct Aptos analog of the Aave Lens "approvals not cleared on transfer" bug.

---

### Finding Description

**Vote storage** — each `MultisigTransaction` carries a `votes: SimpleMap<address, bool>` field that accumulates approvals and rejections:

```move
// multisig_account.move:1200-1203
let transaction = MultisigTransaction {
    ...
    votes: simple_map::create<address, bool>(),
    ...
};
``` [1](#0-0) 

**Vote counting** — `num_approvals_and_rejections_internal` iterates over the *current* `owners` vector and looks up each address in the `votes` map:

```move
// multisig_account.move:1532-1548
inline fun num_approvals_and_rejections_internal(owners: &vector<address>, transaction: &MultisigTransaction): (u64, u64) {
    let votes = &transaction.votes;
    owners.for_each_ref(|owner| {
        if (simple_map::contains_key(votes, owner)) {
            if (*simple_map::borrow(votes, owner)) { num_approvals += 1; }
            else { num_rejections += 1; };
        }
    });
    (num_approvals, num_rejections)
}
``` [2](#0-1) 

**Owner removal** — `update_owner_schema` removes the address from the `owners` vector but performs **no cleanup of existing transaction votes**:

```move
// multisig_account.move:1613-1631
if (owners_to_remove.length() > 0) {
    let owners_ref_mut = &mut multisig_account_ref_mut.owners;
    owners_to_remove.for_each_ref(|owner_to_remove_ref| {
        let (found, index) = vector::index_of(owners_ref_mut, owner_to_remove_ref);
        if (found) { vector::swap_remove(owners_ref_mut, index); }
    });
    ...
};
``` [3](#0-2) 

The stale entry in `votes` is never removed. When the same address is later re-added via `add_owners` → `update_owner_schema`, the address reappears in the `owners` vector and `num_approvals_and_rejections_internal` immediately counts its old vote again — without the owner casting any new vote.

The existing test at line 2269 (`test_validate_transaction_should_not_consider_removed_owners`) only verifies the *removal* half of the invariant; there is no test for the re-addition path. [4](#0-3) 

---

### Impact Explanation

A pending multisig transaction that was effectively blocked by removing a compromised or malicious owner can be silently re-enabled the moment that owner is re-added, without any explicit re-approval action. Concretely:

1. 2-of-3 multisig (owners A, B, C; threshold = 2).
2. Owner A creates malicious transaction T and approves it (1 approval).
3. Owner B approves T (2 approvals — threshold met, but not yet executed).
4. Community detects the malice; executes a multisig transaction to remove A.
5. T now has only 1 counted approval (B's); it cannot be executed.
6. Later, A is re-added (separate governance action, possibly unrelated to T).
7. A's stale `true` entry for T is immediately re-counted.
8. T again has 2 approvals and can be executed — without A ever re-voting.

The re-adding owners may be entirely unaware that re-admission silently re-activates A's old vote on every pending transaction A previously approved.

---

### Likelihood Explanation

The scenario requires the multisig to approve re-adding the removed owner, which itself needs k-of-n signatures. However:
- Owner rotation is a routine governance operation.
- The stale-vote side-effect is invisible in the UI and not documented.
- A social-engineering or key-recovery scenario (owner removed due to suspected compromise, later cleared and re-added) is realistic.
- The `vote_transanction` entry point is callable by any current owner, making the initial vote placement unprivileged within the multisig context.

---

### Recommendation

In `update_owner_schema`, after removing an owner from the `owners` vector, iterate over all pending transactions and remove the departing owner's entry from each transaction's `votes` map:

```move
// After removing owner_to_remove_ref from owners_ref_mut:
multisig_account_ref_mut.transactions.for_each_mut(|_seq, txn| {
    txn.votes.remove(&owner_to_remove_addr); // if present
});
```

Alternatively, when re-adding an owner, clear any pre-existing votes they hold in pending transactions before appending them to `owners`. Either approach mirrors the correct behavior already demonstrated for the removal path (votes from removed owners are not counted).

---

### Proof of Concept

```move
#[test(owner_1 = @0x123, owner_2 = @0x124, owner_3 = @0x125)]
fun test_stale_vote_reactivated_on_readd(
    owner_1: &signer, owner_2: &signer, owner_3: &signer
) {
    setup();
    let o1 = address_of(owner_1);
    let o2 = address_of(owner_2);
    let o3 = address_of(owner_3);
    create_account(o1);
    let ms = get_next_multisig_account_address(o1);
    create_with_owners(owner_1, vector[o2, o3], 2, vector[], vector[]);

    // Owner 1 creates + approves malicious tx; owner 2 also approves → 2-of-3 met.
    create_transaction(owner_1, ms, PAYLOAD);
    approve_transaction(owner_2, ms, 1);
    assert!(can_be_executed(ms, 1), 0); // threshold met

    // Community removes owner 1 → only 1 approval remains.
    let ms_signer = &create_signer(ms);
    remove_owners(ms_signer, vector[o1]);
    assert!(!can_be_executed(ms, 1), 1); // blocked

    // Owner 1 is re-added (separate governance action).
    add_owners(ms_signer, vector[o1]);

    // Stale vote re-activated — threshold met again without owner 1 re-voting.
    assert!(can_be_executed(ms, 1), 2); // BUG: should still be blocked
}
```

The final assertion passes (the transaction is executable again) despite owner 1 never casting a new vote after re-admission, demonstrating the stale-approval re-activation.
