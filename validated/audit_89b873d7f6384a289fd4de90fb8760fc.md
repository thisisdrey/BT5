The `setDefaults` bug class (an admin setter accepting multiple interdependent parameters without cross-field validation, breaking market invariants) does not have a reachable analog in the in-scope code that also breaks a custody-relevant binding:

- `contracts/defuse/src/contract/fees.rs` `set_fee`/`set_fee_collector` are role-gated, single-parameter setters; `fee` is a `Pips` type intrinsically bounded to `0..=MAX` [1](#0-0) , so there is no cross-field invariant to violate and no possibility of an out-of-range fee being set.
- `contracts/outlayer/app/src/contract.rs` `oa_set_code`/`oa_transfer_admin` are single-purpose admin setters with explicit auth and hash checks, no multi-field interdependency [2](#0-1) .
- `contracts/wallet` timeout/subwallet parameters are fixed at initialization and immutable afterward, per the documented design [3](#0-2) , so there is no post-deployment setter to misconfigure.
- `contracts/defuse/src/contract/config.rs` `DefuseConfig`/`RolesConfig` are only consumed once at `Contract::new` with unchecked role application guarded by `require!` [4](#0-3) , not a repeatedly-callable admin setter analogous to `setDefaults`.
- The only place with real interdependent-fee validation logic (`Params::validate`, `validate_fees`, `MAX_FEE` cap) is `contracts/escrow-swap/src/state.rs`, which is explicitly out of scope [5](#0-4) .

None of these reachable setters combine multiple parameters whose cross-validation failure would cross an authorisation, replay, conservation, settlement, identity, or fee boundary as required by the rules.
