Audit Report

## Title
`process_delivery_receipt` pays relayer reward and permanently settles the order regardless of the decoded `success` flag - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` from a verified Ethereum `InboundMessageDispatched` event, which explicitly carries a `success: bool` field indicating whether the message dispatch on Ethereum succeeded or reverted, but the function never reads or branches on this field. It unconditionally pays the relayer/`reward_address` the full `order.fee` (when `fee > 0`) and permanently removes the `PendingOrder` from storage, even when `success == false`.

## Finding Description
`submit_delivery_receipt` at bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs (L298-317) verifies the Merkle/BEEFY proof via `T::Verifier::verify`, decodes the log into `DeliveryReceipt::try_from`, and passes the receipt directly into `process_delivery_receipt` without inspecting `receipt.success`. [1](#0-0) 

`process_delivery_receipt` (L445-480) only checks `receipt.gateway` against `T::GatewayAddress`, resolves `reward_account`, looks up the `PendingOrder` by `receipt.nonce`, pays `order.fee` via `T::RewardPayment::register_reward` when `order.fee > 0`, then calls `<PendingOrders<T>>::remove(nonce)` and emits `Event::MessageDelivered` — all without ever reading `receipt.success`. [2](#0-1) 

The `DeliveryReceipt` struct decodes `success` directly from the Solidity `InboundMessageDispatched` event (`event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address);`) via `TryFrom<&Log>`, confirming the field is populated with real on-chain delivery status but simply discarded by the caller. [3](#0-2) 

A `grep` across the entire `outbound-queue-v2` pallet source confirms zero references to `success` outside the primitive decode module — the field is decoded and immediately dropped. The existing test `submit_delivery_receipt_succeeds_after_unhalt` only exercises the halted/unhalted verifier path and never constructs or asserts on a `success: false` event, so this gap is untested.

The only existing guards are: (1) gateway address match, (2) `PendingOrders` lookup by nonce. Neither guard is related to delivery outcome, so a genuinely proven `success: false` event still passes both checks and triggers payout + order deletion identically to a `success: true` event.

## Impact Explanation
This is a "duplicate settlement or payout" / incorrect-condition payout class issue in BridgeHub/Snowbridge outbound reward accounting. A cross-chain message whose execution reverted on Ethereum (e.g., out-of-gas dispatch or a reverting command) still results in the relayer (or an attacker-supplied `reward_address` embedded in the genuine event) receiving `order.fee`, and the `PendingOrder` is irreversibly removed, eliminating any possibility of retry, refund, or distinguishing failed deliveries in on-chain state. This matches the required impact: "duplicate settlement or payout" and "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" — here settlement advances despite execution failure.

## Likelihood Explanation
Likelihood is Medium: no privileged actor, malicious relayer, or forged proof is needed. `submit_delivery_receipt` is a public, unprivileged extrinsic (`ensure_signed(origin)` accepts any signed account), and the only precondition is a normal, legitimately occurring reverted dispatch on the Ethereum side, followed by any relayer submitting the correctly-proven event log.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: if `true`, proceed as today (pay reward, remove order); if `false`, skip (or reduce) the reward payment and transition the order to a distinct failed/reprocessable state instead of unconditionally removing it via `<PendingOrders<T>>::remove(nonce)`.

## Proof of Concept
1. A message is enqueued via `do_process_message`, inserting `PendingOrder { nonce, fee, block_number }` into `PendingOrders`. [4](#0-3) 
2. On Ethereum, the corresponding command execution reverts; the Gateway contract emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer builds a valid `EventProof` for this real log and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success: false` correctly, but `process_delivery_receipt` ignores this and pays the reward, then removes the order — identical to the `success: true` path exercised in `submit_delivery_receipt_succeeds_after_unhalt`. [5](#0-4) 
5. Add a unit test that constructs a mock event log with `success: false`, submits it, and asserts that `register_reward` is NOT called and the order is retained/marked failed — this test would fail against current code, confirming the bug.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

sol! {
	event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address);
}

/// Delivery receipt
#[derive(Clone, Debug)]
pub struct DeliveryReceipt {
	/// The address of the outbound queue on Ethereum that emitted this message as an event log
	pub gateway: H160,
	/// The nonce of the dispatched message
	pub nonce: u64,
	/// Message topic
	pub topic: H256,
	/// Delivery status
	pub success: bool,
	/// The reward address
	pub reward_address: [u8; 32],
}

#[derive(Copy, Clone, Encode, Decode, Eq, PartialEq, Debug, TypeInfo)]
pub enum DeliveryReceiptDecodeError {
	DecodeLogFailed,
	DecodeAccountFailed,
}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
