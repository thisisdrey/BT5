Based on my investigation, I've confirmed a real analog of the reported bug class in the Nakamoto tenure-download path.

### Title
Malicious peer serving invalid/forged tenure blocks is only marked "dead" (unbanned, freely reconnectable) instead of "broken" (banned) - ([File: stackslib/src/net/download/nakamoto/tenure_downloader_set.rs])

### Summary
In `NakamotoTenureDownloaderSet::run`, when a remote peer's response fails validation inside `NakamotoTenureDownloader::handle_next_download_response` (bad signer signature, wrong tenure, out-of-order/forged block cursor, exceeded tenure length, etc.), the failure is reported to `neighbor_rpc.add_dead(..., DropReason::DeadConnection(...), ...)` rather than `add_broken(...)`. The same pattern occurs in `NakamotoDownloadStateMachine::run_unconfirmed_downloaders` for the unconfirmed-tenure downloader. Because `do_network_block_sync_nakamoto` (`stackslib/src/net/download/nakamoto/mod.rs`) only bans peers drawn from `take_broken()`, and merely disconnects (via `deregister_neighbor`, no deny-period) peers drawn from `take_dead()`, a peer that serves cryptographically invalid or structurally forged Nakamoto blocks is never penalized — it is simply dropped and can reconnect and repeat the same bogus response indefinitely.

### Finding Description
The download pipeline explicitly documents two peer-failure categories: "dead" (communication/liveness failure) and "broken" ("in protocol violation") — see `NeighborComms::add_dead`/`add_broken` in `stackslib/src/net/neighbors/comms.rs:46-61` and their concrete implementation in `stackslib/src/net/neighbors/rpc.rs:47-75`. `deregister_and_ban_neighbor` (`stackslib/src/net/p2p.rs:2190-2211`) applies an actual deny-period ban via `PeerDB::set_deny_peer`/`process_bans`, while `deregister_neighbor` (`stackslib/src/net/p2p.rs:2171-2188`) only disconnects with no penalty.

However, in the Nakamoto confirmed-tenure downloader (`NakamotoTenureDownloaderSet::run`, `stackslib/src/net/download/nakamoto/tenure_downloader_set.rs:623-646`), *all* response-validation failures — including cryptographic/content violations coming from `NakamotoTenureDownloader::try_accept_tenure_blocks`/`try_accept_tenure_start_block`/`try_accept_tenure_end_block` (`stackslib/src/net/download/nakamoto/tenure_downloader.rs:178-462`, which reject bad signer signatures, block-ID/cursor mismatches, and tenure-length overflows with `NetError::InvalidMessage`) — are funneled into `neighbor_rpc.add_dead(..., DropReason::DeadConnection(...), DropSource::NakamotoTenureDownloader)`. The identical pattern appears for the unconfirmed-tenure downloader in `NakamotoDownloadStateMachine::run_unconfirmed_downloaders` (`stackslib/src/net/download/nakamoto/download_state_machine.rs:1253-1264`), even though `NakamotoUnconfirmedTenureDownloader::try_accept_*` (`stackslib/src/net/download/nakamoto/tenure_downloader_unconfirmed.rs:390-582`) performs the same kind of signature/structure/cursor authenticity checks.

Downstream, `do_network_block_sync_nakamoto` (`stackslib/src/net/download/nakamoto/mod.rs:174-203`) takes `take_broken()` results and bans via `deregister_and_ban_neighbor`, but takes `take_dead()` results and only disconnects via `deregister_neighbor` — with no deny-period applied. This breaks the intended equality "protocol violation ⇒ banned" vs. "communication failure ⇒ merely disconnected": a peer that supplies forged/invalid signed blocks (a protocol violation, not a liveness issue) is treated identically to a peer that merely timed out, so it incurs zero durable penalty and can reconnect and repeat the attack. ### Impact Explanation
This matches the reported bug class: an unauthenticated/unprivileged peer supplying data that fails validation (forged block content, bad signer signature, out-of-sequence cursor — analogous to Zebra's `AboveLookaheadHeightLimit`) causes the sync/download machinery to merely reset/disconnect that connection without any misbehavior scoring or ban, so the same peer can reconnect indefinitely and repeat the attack at no cost to itself, continuously wasting the victim's tenure-download cycles and confirmed-tenure download schedule slots (`self.attempt_failed_tenures`/`deprioritized_peers` only provide a soft, in-memory, short-lived deprioritization, not a real ban). This is a bounded compute/availability degradation on a node during IBD/steady-state sync, reachable from a single unauthenticated, unauthorized peer with negligible resources (no mining, no valid chain data, one crafted response per cycle).

### Likelihood Explanation
High likelihood: any inbound P2P peer that has completed a handshake and been assigned a tenure/unconfirmed-tenure download (which happens automatically as part of normal sync) can trigger this simply by returning a single malformed/forged Nakamoto block in response to a `/v3/tenure/...` GET request. No privileged data, key material of others, or mining capability is required — an attacker only needs an arbitrary keypair to sign a not-matching block or omit/corrupt required fields to hit the `NetError::InvalidMessage` paths shown above.

### Recommendation
Route protocol-violation failures returned from `NakamotoTenureDownloader::handle_next_download_response` / `NakamotoUnconfirmedTenureDownloader::handle_next_download_response` (i.e., `NetError::InvalidMessage` and other content/signature-validation errors) to `neighbor_rpc.add_broken(...)` instead of `add_dead(...)`, reserving `add_dead` for genuine liveness/communication failures (`PeerNotConnected`, poll timeouts, DNS failures, etc.). This ensures `do_network_block_sync_nakamoto` bans (applies a deny-period via `deregister_and_ban_neighbor`) peers that serve cryptographically or structurally invalid tenure data, consistent with how `deregister_and_ban_neighbor` is already used for other confirmed protocol violations elsewhere in the codebase (e.g., `stackslib/src/net/p2p.rs:3318-3328`, `stackslib/src/net/inv/nakamoto.rs:1135-1138`).

### Proof of Concept
1. Stand up a malicious peer that completes the P2P handshake with the victim `stacks-node` and gets selected as a source for a wanted tenure (or the unconfirmed tenure) by the download scheduler (`NakamotoTenureDownloaderSet::make_tenure_downloaders` / `NakamotoDownloadStateMachine::run_unconfirmed_downloaders`).
2. When the victim issues a `/v3/tenure/*` request for the tenure-start, tenure-end, or tenure blocks, respond with a syntactically valid HTTP body containing a `NakamotoBlock` whose signer signature does not verify (or whose `block_id`/`consensus_hash` does not match what was requested).
3. Observe that `NakamotoTenureDownloader::try_accept_tenure_start_block`/`try_accept_tenure_blocks` (or the unconfirmed counterparts) return `Err(NetError::InvalidMessage)`, which is caught in `NakamotoTenureDownloaderSet::run` / `run_unconfirmed_downloaders` and routed to `neighbor_rpc.add_dead(...)`.
4. Confirm via `do_network_block_sync_nakamoto` that the peer is only `deregister_neighbor`'d (disconnected, no deny-period in `PeerDB`), and can reconnect immediately and repeat step 2 indefinitely with zero cost, since it was never passed through `deregister_and_ban_neighbor`.

    /// Perform block sync.
    /// Drive the state machine, and clear out any dead and banned neighbors
    pub fn do_network_block_sync_nakamoto(
        &mut self,
        burnchain_height: u64,
        sortdb: &SortitionDB,
        chainstate: &mut StacksChainState,
        ibd: bool,
    ) -> Result<HashMap<ConsensusHash, Vec<NakamotoBlock>>, NetError> {
        if self.connection_opts.disable_block_download {
            return Ok(HashMap::new());
        }

        let res = self.sync_blocks_nakamoto(burnchain_height, sortdb, chainstate, ibd)?;

        let Some(mut block_downloader) = self.block_downloader_nakamoto.take() else {
            return Ok(res);
        };

        for broken in block_downloader.neighbor_rpc.take_broken() {
            self.deregister_and_ban_neighbor(&broken.key, broken.reason, broken.source);
        }

        for dead in block_downloader.neighbor_rpc.take_dead() {
            self.deregister_neighbor(&dead.key, dead.reason, dead.source);
        }

        self.block_downloader_nakamoto = Some(block_downloader);
        Ok(res)
    }

    /// Deregister by neighbor key
    pub fn deregister_neighbor(
        &mut self,
        neighbor: &NeighborKey,
        reason: DropReason,
        source: DropSource,
    ) {
        debug!("Disconnect from {neighbor:?}");
        if !self.events.contains_key(neighbor) {
            return;
        };
        self.deregister_peer(DropPeer {
            reason,
            address: neighbor.addrbytes.clone(),
            source,
            port: neighbor.port,
        });
    }

    /// Deregister and ban a neighbor
    pub fn deregister_and_ban_neighbor(
        &mut self,
        neighbor: &NeighborKey,
        reason: DropReason,
        source: DropSource,
    ) {
        debug!("Disconnect from and ban {neighbor:?}");
        let event_id = self.events.get(neighbor).map(|event_id| {
            self.bans.insert(*event_id);
            *event_id
        });
        self.relayer_stats.process_neighbor_ban(neighbor);
        if event_id.is_some() {
            self.deregister_peer(DropPeer {
                reason,
                address: neighbor.addrbytes.clone(),
                source,
                port: neighbor.port,
            });
        }
    }
