### Title
Missing archive-content validation in `CreateRepositoryFromSnapshot`'s `untar()` allows path traversal / repository storage escape via crafted `HttpUrl` field - (File: `internal/gitaly/service/repository/create_repository_from_snapshot.go`)

### Summary
The `CreateRepositoryFromSnapshot` RPC extracts an externally-fetched tar archive directly into a freshly created repository directory using the system `tar` binary, with no validation of archive entry names, symlinks, or hard links. The code's own comment acknowledges this is unhardened. This mirrors the "missing check" bug class from the reference report (a security-relevant precondition check that other, similar code paths in the codebase *do* perform, but this path omits).

### Finding Description
`untar()` fetches archive bytes from an attacker/caller-supplied `HttpUrl` (optionally with `HttpAuth` header and a pinned `ResolvedAddress`) and pipes the response body directly into `tar -C <path> -xvf -`: [1](#0-0) 

Unlike other tar/archive-extraction code paths in the same codebase — e.g. `extractTarToDirectory` in `internal/gitaly/service/repository/replicate.go`, which explicitly validates that every regular file, directory, symlink target, and hard-link target stays within the destination directory before writing: [2](#0-1) 

`CreateRepositoryFromSnapshot`'s `untar()` performs **no equivalent check**. It shells out to the system `tar` binary and trusts whatever the fetched HTTP response contains, including entry names that may contain `..` traversal, absolute paths, or symlink/hardlink members pointing outside the target repository directory. The code's own comment flags this gap explicitly: [3](#0-2) 

This is the same class of defect as the reference report: a security-relevant validation step that exists elsewhere in equivalent code paths (`extractTarToDirectory`, and the recovery CLI's `extractArchive`/`extractBackup` also lack it, though those are admin-only tools and out of scope here) is missing on this particular reachable path.

### Impact Explanation
Because the extraction target is the storage path of a repository the caller is creating, and `tar` extraction is unconstrained, a malicious or compromised archive source (reachable because the RPC caller fully controls `HttpUrl`/`HttpAuth`/`ResolvedAddress`) could:
- Write files outside the intended repository directory within the storage root (path/archive extraction escape), potentially clobbering unrelated repository data, hooks, or configuration files elsewhere in the storage.
- Plant symlinks/hardlinks that later cause Gitaly or Git tooling to read/write outside the repository boundary.
- Combined with the fact that `HttpUrl` is fully attacker-influenced RPC input, this also carries an SSRF component: Gitaly will make an outbound HTTP(S) request to whatever URL is supplied (mitigated only by DNS-rebinding protection via `ResolvedAddress`, not by any allowlist of destinations).

### Likelihood Explanation
Exploitability requires the ability to invoke the `CreateRepositoryFromSnapshot` RPC with attacker-chosen `HttpUrl`/`HttpAuth` fields — this is the intended mechanism of the RPC (used for repository import/migration), so any caller authorized to invoke Gitaly RPCs (e.g., a compromised or malicious internal caller, or a bug in the calling layer that forwards user-supplied URLs) can reach this code path. The maintainers' own comment underscores that the RPC is not meant to be exposed to arbitrary/untrusted endpoints without further hardening — meaning the hardening is understood to be absent today.

### Recommendation
Replace the raw `tar -xvf` shell-out with the same validated, path-confined extraction logic used in `extractTarToDirectory` (`internal/gitaly/service/repository/replicate.go`): validate that every tar entry's resolved target path stays within the destination directory, reject absolute symlink targets, and reject symlink/hardlink targets that resolve outside the extraction directory. Additionally, restrict/allowlist destinations reachable via `HttpUrl` or otherwise gate this RPC behind proper caller authorization to reduce SSRF exposure.

### Proof of Concept
1. Invoke `CreateRepositoryFromSnapshot` with a `Repository` target and `HttpUrl` pointing to an attacker-controlled HTTP server.
2. The attacker server responds with a tar stream containing an entry such as `../../../other-repo.git/hooks/pre-receive` (or a symlink entry pointing outside the target directory).
3. `untar()` executes `tar -C <repoPath> -xvf -` on this stream with no path validation, as shown at `create_repository_from_snapshot.go` lines 115-120, allowing the entry to be written outside `<repoPath>`.
4. Compare against `extractTarToDirectory` in `replicate.go` (lines 334-391), which would reject the same crafted entries with `"symlink target escapes extraction directory"` or `"invalid file path in tar"` errors — demonstrating the missing check in the snapshot code path. [4](#0-3) [5](#0-4)

func (s *server) untar(ctx context.Context, path string, in *gitalypb.CreateRepositoryFromSnapshotRequest) error {
	req, err := http.NewRequestWithContext(ctx, "GET", in.GetHttpUrl(), nil)
	if err != nil {
		return structerr.NewInvalidArgument("Bad HTTP URL: %w", err)
	}

	client := httpClient
	if resolvedAddress := in.GetResolvedAddress(); resolvedAddress != "" {
		client, err = newResolvedHTTPClient(in.GetHttpUrl(), resolvedAddress)
		if err != nil {
			return structerr.NewInvalidArgument("creating resolved HTTP client: %w", err)
		}
	}

	if in.GetHttpAuth() != "" {
		req.Header.Set("Authorization", in.GetHttpAuth())
	}

	rsp, err := client.Do(req)
	if err != nil {
		return structerr.NewInternal("HTTP request failed: %w", err)
	}
	defer rsp.Body.Close()

	if rsp.StatusCode < http.StatusOK || rsp.StatusCode >= http.StatusMultipleChoices {
		return structerr.NewInternal("HTTP server: %s", rsp.Status)
	}

	cmd, err := command.New(ctx, s.logger, []string{"tar", "-C", path, "-xvf", "-"}, command.WithStdin(rsp.Body))
	if err != nil {
		return err
	}

	return cmd.Wait()
}
