### Title
Non-reproducible module extension `facts` in `MODULE.bazel.lock` are trusted without re-invoking the extension, letting attacker-controlled lockfile data bypass the extension's own validation - (File: `src/test/py/bazel/bzlmod/bazel_lockfile_test.py`)

### Summary
Bazel's `module_extension` `facts` mechanism lets a non-reproducible extension persist "universally true" data (e.g. artifact hashes) in `MODULE.bazel.lock` and reuse it on later builds without re-running the extension. Bazel's default `--lockfile_mode=update` accepts and reuses whatever `facts` values are present in the lockfile it reads, even when those values were not produced locally but arrived via a branch switch, pull, or externally supplied lockfile. This mirrors the Cooler bug class: a value that is supposed to be produced only through a validated path (the extension's own implementation, which is meant to fetch/verify data such as checksums) can instead be supplied directly by whoever controls the lockfile content the build consumes, bypassing the extension's intended validation entirely.

### Finding Description
The `facts` field of `module_ctx.extension_metadata()` is documented as being intended for values such as "the hashes of artifacts in an immutable repository" that the extension would otherwise fetch from the network [1](#0-0) . For non-reproducible extensions, on subsequent invocations the extension implementation reads `ctx.facts` and, if a key is already present, skips re-fetching/re-validating and simply trusts the stored value [2](#0-1) .

Bazel's lockfile handling explicitly reuses externally-modified `facts` data without re-running the extension. The test `testExternallyUpdatedFactsKeptByUpdateModeForNonReproducibleExtension` documents this precisely: it simulates "the workspace lockfile changing underneath a warm output base, e.g. due to a branch switch or pull that brings in facts produced by an evaluation of the extension on a different machine," and asserts that in `--lockfile_mode=update` the added fact is kept and the extension is *not* re-evaluated [3](#0-2) [4](#0-3) . Likewise, `testDeletedFactsRegeneratedByUpdateMode` shows facts are restored from a cached (hidden lockfile) copy "without rerunning the extension," reinforcing that the extension's own fetch-and-validate logic is not invoked once facts exist for a key [5](#0-4) .

Because `MODULE.bazel.lock` is an ordinary tracked file, an attacker who can get a modified lockfile pulled into a victim's checkout — e.g. via a pull/merge from a branch, or any CI job that builds an untrusted branch containing a crafted `MODULE.bazel.lock` — supplies the `facts` map that the extension will trust on the next `update`-mode build, with the extension's own implementation code (which is the intended "validating caller," analogous to `Clearinghouse.rollLoan()`) never actually re-executing to independently fetch or verify that data. This is architecturally the same bypass as the reported Cooler issue: the party meant to gate/validate a value (the extension re-fetching from a trusted source and computing/verifying a checksum) is skipped, and the attacker supplies the "interest_/loanToCollateral_/duration_"-equivalent value (here, an artifact URL+hash pair or other fact) directly through an unguarded channel (the lockfile).

### Impact Explanation
If a module extension stores security-relevant values in `facts` — such as a URL/checksum pair for an artifact used by a downstream `repository_rule` download — an attacker who can influence the `MODULE.bazel.lock` a build reads (via a branch merge, PR, or shared/CI-built untrusted branch) can substitute both the URL and the checksum simultaneously. Because the recorded fact is trusted as-is and the extension is not re-run to independently verify it, the checksum no longer functions as an integrity guard against a hostile origin — it is simply attacker-supplied data paired with attacker-supplied content, defeating the purpose of using a checksum at all for that extension's downloads on subsequent builds.

### Likelihood Explanation
This requires no privileged access: the attacker only needs their branch/PR content (including `MODULE.bazel.lock`) to be checked out by a build (e.g. CI building an untrusted branch, or a maintainer pulling a contributor's branch), which fits the stated threat model of "files on an untrusted branch CI builds." The behavior is the documented default (`--lockfile_mode=update`), not a rare edge case, and is explicitly covered/asserted as intended behavior by the test suite.

### Recommendation
For non-reproducible extensions, do not unconditionally trust externally-modified `facts` entries as equivalent to locally-verified data. At minimum, extensions that store security-sensitive material (URLs plus checksums) in `facts` should not treat lockfile-sourced facts as immutable ground truth; Bazel could offer a mode/flag requiring re-validation (e.g., checksum verification at use time) rather than skipping extension re-evaluation solely because a `facts` key is present, especially when the containing lockfile was not produced by a local, verified evaluation.

### Proof of Concept
The existing regression test demonstrates the trust behavior end-to-end and can be adapted to show a hostile substitution: [6](#0-5)  — an attacker-controlled `MODULE.bazel.lock` with a forged `facts` entry (e.g. `{"hash": "<attacker-controlled>"}` paired with an attacker-controlled URL used elsewhere in the extension) is accepted by `bazel build --lockfile_mode=update` without the extension re-running to fetch/verify it, exactly as asserted by `testExternallyUpdatedFactsKeptByUpdateModeForNonReproducibleExtension` [4](#0-3) .

Note: the underlying Java implementation (likely in `BazelLockFileFunction`/`SingleExtensionEvalFunction`/lockfile "facts" merging code) that performs this reuse could not be located in the indexed codebase within the available search results — only the Starlark-facing documentation and the Python integration tests were retrievable. A Devin session with full repository access would be needed to pinpoint and confirm the exact Java method responsible for merging/trusting lockfile `facts` without re-invoking the extension.

  def _addFactToLockfile(self, extension_id, fact_key, fact_value):
    """Adds a facts entry to the workspace lockfile."""
    # Simulates the workspace lockfile changing underneath a warm output base,
    # e.g. due to a branch switch or pull that brings in facts produced by an
    # evaluation of the extension on a different machine.
    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    lockfile['facts'][extension_id][fact_key] = fact_value
    with open(self.Path('MODULE.bazel.lock'), 'w') as f:
      json.dump(lockfile, f, indent=2)

  def testDeletedFactsRegeneratedByUpdateMode(self):
    """Facts deleted from the workspace lockfile are restored by UPDATE mode.

    Regression test for https://github.com/bazelbuild/bazel/issues/29161. For a
    non-reproducible extension, the deleted facts are restored from the hidden
    lockfile's copy without rerunning the extension: its cached result is
    locked in the workspace lockfile, so a cold machine would not rerun it
    either.
    """
    extension_id = self._setUpExtensionWithFacts(reproducible=False)
    self._dropFactsFromLockfile(extension_id)

    _, _, stderr = self.RunBazel(
        ['build', '@hello//:all', '--lockfile_mode=update']
    )
    self.assertNotIn('lockfile_ext is being evaluated', '\n'.join(stderr))

    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    self.assertEqual(
        lockfile['facts'][extension_id],
        {'1.25.0': {'hash': 'olleh'}, '1.26.1': {'hash': 'hello'}},
    )

  def testExternallyUpdatedFactsKeptByUpdateModeForNonReproducibleExtension(
      self,
  ):
    """UPDATE mode keeps updated facts of a non-reproducible extension.

    The hidden lockfile records the facts produced by the most recent local
    evaluation of the extension. If the workspace lockfile's facts for a
    non-reproducible extension change without any of its inputs changing (e.g.
    a branch switch or pull brings in a re-pin performed on another machine),
    the cached result must be reused with the new facts as is: a cold machine
    would not rerun the extension either and a rerun could require network
    access or credentials that are only available to the person updating the
    pins.
    """
    extension_id = self._setUpExtensionWithFacts(reproducible=False)
    self._addFactToLockfile(extension_id, '1.27.0', {'hash': 'hola'})

    _, _, stderr = self.RunBazel(
        ['build', '@hello//:all', '--lockfile_mode=update']
    )
    self.assertNotIn('lockfile_ext is being evaluated', '\n'.join(stderr))

    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    self.assertEqual(
        lockfile['facts'][extension_id],
        {
            '1.25.0': {'hash': 'olleh'},
            '1.26.1': {'hash': 'hello'},
            '1.27.0': {'hash': 'hola'},
        },
    )
