### Title
Stale duplicated `tokenSpeeds` lets users accrue and claim rewards after the underlying Vesper reward rate ended or changed — (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor` stores `tokenSpeeds[token]` — a manually synced copy of Vesper's effective reward rate (`rewardRates * treasuryBalance / totalSupply`) — instead of reading it live. `_calculateTokenIndex` accrues rewards using this stored value unconditionally, with no `periodFinish` or freshness check. When Vesper's `rewardRates` drops or `periodFinish` passes, the distributor keeps accruing at the stale (higher) speed until the `tokenSpeedKeeper` calls `syncTokenSpeed` or the governor calls `updateTokenSpeed`. Any holder of a tracked DepositToken/DebtToken can call the public `claimRewards` during the desync window to harvest rewards that were never funded by Vesper, draining the distributor's `rewardToken` balance and leaving other users' accrued yield unclaimable.

### Finding Description
`syncTokenSpeed` recomputes the "true" speed from the external Vesper pool: `_speed = rewardRates * vPool.balanceOf(treasury) / vPool.totalSupply`, and only when `block.timestamp < periodFinish` — otherwise `_speed = 0` [1](#0-0) . This proves `tokenSpeeds` is intended to mirror an external, time-varying value — exactly the duplicated-data bug class.

However, accrual in `_calculateTokenIndex` uses `tokenSpeeds[token_]` directly with no check of `periodFinish` or the external rate: `uint256 _tokensAccrued = _deltaTimestamps * _speed` accrues for every elapsed second at whatever speed was last stored [2](#0-1) .

The desync windows are permissionless to exploit:
- `updateBeforeMintOrBurn` is explicitly callable by anyone ("may be called by anyone to update stored indexes") [3](#0-2) .
- `claimRewards(address[], IERC20[])` is fully public and transfers `rewardToken` to any account up to the contract's balance [4](#0-3) .
- `_transferRewardIfEnoughTokens` silently pays out up to the distributor's balance and resets `tokensAccruedOf` — first claimants win; later claimants get nothing [5](#0-4) .

Because the underlying Vesper rate can decrease at any time (e.g., on `notifyRewardAmount` with a lower rate, treasury share dilution as other depositors enter `vPool`, or `periodFinish` expiry), the stored speed can be arbitrarily stale while accrual continues.

### Impact Explanation
Theft of unclaimed yield / direct loss of reward funds. During a desync window the index accrues rewards not backed by actual Vesper emissions. An attacker holding (or newly depositing into) a tracked deposit token calls `claimRewards` and extracts `rewardToken` from the distributor at inflated accrual. Since payouts are first-come-first-served against the contract's real balance, honest users' accrued rewards become unclaimable. In the extreme case (keeper never syncs after `periodFinish`), accrual continues indefinitely at the stale speed until the distributor is fully drained.

### Likelihood Explanation
- The keeper sync is inherently asynchronous; every `rewardRates` change, treasury share change, or `periodFinish` crossing creates a desync window.
- The attacker needs no privileges: deposit into the DepositToken, wait for or observe a rate decrease/period expiry on the underlying Vesper `poolRewards`, then call public `updateBeforeMintOrBurn`/`claimRewards`.
- Nothing in the accrual path (no `onlyIfDistributorExists` on the read path, no pause flag, no freshness bound on `tokenStates.timestamp`) stops it; `nonReentrant` does not matter since the attack is a single call.

### Recommendation
Do not rely on a stored duplicate of the external rate. Options:
- Cap accrual at the underlying `periodFinish`: in `_calculateTokenIndex`, clamp `_deltaTimestamps` to `min(block.timestamp, periodFinish) - supplyState.timestamp` and/or read `rewardRates` directly instead of `tokenSpeeds`.
- If the stored speed must remain for gas reasons, have `updateBeforeMintOrBurn`/`updateBeforeTransfer`/`claimRewards` trigger `syncTokenSpeed` permissionlessly (remove the `onlyTokenSpeedKeeper` gate on the recomputation path) so the index is always updated from a fresh value before accruing.

### Proof of Concept
Foundry fork test outline:

```solidity
// Fork mainnet; resolve deployed RewardsDistributor, DepositToken (msdX), rewardToken,
// the Vesper vPool behind depositToken.underlying(), and its poolRewards.

function testStaleSpeedDrain() public {
    // 1. Keeper has synced: tokenSpeeds[msdX] = speed0 (rewardRates * tBal / tSupply)
    uint256 speed0 = distributor.tokenSpeeds(address(msdX));
    assertGt(speed0, 0);

    // 2. Vesper reward period ends (or rewardRates is lowered via notifyRewardAmount)
    //    Use vm.warp past poolRewards.periodFinish(rewardToken).
    vm.warp(poolRewards.periodFinish(address(rewardToken)) + 1);

    // 3. tokenSpeeds is STILL speed0 -- keeper has not called syncTokenSpeed yet.

    // 4. Attacker holds ms dToken balance (deposit beforehand).
    uint256 before = rewardToken.balanceOf(attacker);

    // 5. Anyone can trigger accrual + claim at the stale speed.
    distributor.claimRewards(attacker); // accrues deltaT * speed0 even though
                                      // _rewards.periodFinish already passed
    uint256 gained = rewardToken.balanceOf(attacker) - before;

    // gained includes emissions for every second after periodFinish at speed0,
    // none of which was funded by Vesper -> distributor balance drained,
    // later claimants receive nothing (_transferRewardIfEnoughTokens skips).
    assertGt(gained, /* expected honest accrual before periodFinish */);
}
```

Key assertion: after `periodFinish`, `distributor.claimable(attacker)` keeps growing linearly with elapsed time at `speed0`, whereas `syncTokenSpeed` would have set the speed to `0`. The excess is paid out of the shared `rewardToken` balance, stealing other users' unclaimed yield.
