### Title
Residual bad debt is left permanently unbacked after liquidating an underwater position — no mechanism to clear it - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The Insure report's bug class is *unhandled system-level shortfall*: when all backstop layers fail, debt is parked on the books with no repayment mechanism. Metronome has a direct analog in `Pool.liquidate`. When an account's collateral value falls below its debt (underwater position), the liquidator can only seize up to `depositToken_.balanceOf(account_)` (`AmountIsTooHigh` check, `Pool.sol:583-585`). The portion of `DebtToken` balance exceeding what the collateral covers is burned only pro-rata; the remainder stays as an open debt position against an account with zero collateral. There is no treasury cover, insurance fund, socialized-loss, or bad-debt write-off path anywhere in `Pool.sol`, `DebtToken.sol`, `Treasury.sol`, or `DepositToken.sol`.

### Finding Description
In `Pool.liquidate` (contracts/Pool.sol:537-596):

1. The repay amount is capped by `maxLiquidable` (`amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable` reverts) and by the collateral balance via `quoteLiquidateOut` + the `AmountIsTooHigh` check.
2. `quoteLiquidateMax` (Pool.sol:419-440) returns `min(debt * maxLiquidable, amount covered by remaining collateral)` — i.e., once a position is underwater, the maximum repayable amount is the amount purchasable with the leftover collateral.
3. After `depositToken_.seize` empties the collateral, the account's `DebtToken` balance is still `> 0`. With zero collateral in every deposit token, no further `liquidate` call can succeed (any `amountToRepay_ > 0` produces `_totalToSeize > balanceOf(account_) == 0` → `AmountIsTooHigh`), and the account has no incentive and no forced path to call `DebtToken.repay`.
4. The residual debt continues to accrue interest through `DebtToken.accrueInterest`, so the unbacked synthetic supply grows over time.

The protocol's own test suite confirms the end state: in the "collateral:debt < 1" scenario, after max liquidation `msdMET.balanceOf(alice)` is ~0 while `msEthDebtToken.balanceOf(alice)` remains `> 0` and `_isHealthy` stays `false` (test/Pool.test.ts:807-818).

There is no `badDebt`, `shortfall`, cover, or socialize mechanism in the codebase — only a `Repay` path the debtor can voluntarily call. Unlike a normal undercollateralized-but-backed position, this debt is permanently unrecoverable: the corresponding `SyntheticToken` supply in circulation is no longer backed by collateral in the `Pool`/`Treasury`.

### Impact Explanation
Protocol insolvency. Every synthetic token in circulation is a claim on the pool's solvency (redeemable/swappable via `Pool.swap` at oracle price). Bad debt means `SyntheticToken.totalSupply` claims exceed the collateral backing them. Because `Pool.swap` prices swaps purely from `MasterOracle` quotes and does not haircut for unbacked supply, the deficit is socialized implicitly across all synth holders and solvent depositors only at collapse — the accounting never recognizes the loss. Like the Insure bug, the system "may incorrectly handle insolvency ... generating system instability," except here the shortfall is permanently unresolvable rather than merely pending repayment.

### Likelihood Explanation
Requires a collateral price crash faster than liquidators react (or liquidator absence for small/dust positions, worsened by `debtFloorInUsd` and `maxLiquidable` throttling partial liquidations). An unprivileged actor does not need to trigger the crash — they only need to hold a max-leverage mint position that becomes underwater, then refuse repayment; griefing/strategic default is free since the residual debt cannot be seized. Fast-crash scenarios are realistic for high-volatility listed collaterals; the gap between the collateral-factor buffer and 100% LTV is the only protection, and it evaporates exactly when bad debt materializes.

### Recommendation
Add an explicit bad-debt resolution path, e.g.:

- Allow a liquidation mode that seizes *all* remaining collateral of every deposit token while burning the corresponding debt portion, and write off the residual `DebtToken` balance by burning it without minted-synth repayment, recording the loss explicitly (socialized across depositors or absorbed by `Treasury`/feeCollector reserves).
- Alternatively maintain an insurance/backstop balance (e.g., protocol fees accumulated in `Treasury`) that `liquidate` draws on to cover `amountToRepay_ - collateralCovered` before writing off the rest.
- Emit an event accounting for written-off debt so solvency tracking is auditable.

### Proof of Concept
Hardhat test sketch (repo's existing fixture style, `test/Pool.test.ts`):

```ts
// given: alice deposits MET and mints msETH at max issuance
await msdMET.connect(alice).deposit(userDepositAmount, alice.address)
await msEthDebtToken.connect(alice).issue(userMintAmount, alice.address)

// when: collateral price crashes so debt > collateral
await masterOracle.updatePrice(met.address, toUSD('0.50')) // collateral:debt < 1

// liquidator repays the maximum possible
const amountToRepay = await pool.quoteLiquidateMax(msEth.address, alice.address, msdMET.address)
await pool.connect(liquidator).liquidate(msEth.address, alice.address, amountToRepay, msdMET.address)

// then: all collateral gone, debt remains forever
expect(await msdMET.balanceOf(alice.address)).to.closeTo(0, 6000)
const residualDebt = await msEthDebtToken.balanceOf(alice.address)
expect(residualDebt).to.gt(0) // <-- unbacked msETH supply, never repayable

// any further liquidation attempt reverts: seize > zero balance
await expect(
  pool.connect(liquidator).liquidate(msEth.address, alice.address, 1, msdMET.address)
).to.revertedWithCustomError(pool, 'AmountIsTooHigh')
```

This mirrors the existing test at `test/Pool.test.ts:791-819` which already demonstrates the residual-debt end state; the missing piece is that nothing in `Pool.sol`, `DebtToken.sol`, or `Treasury.sol` can ever clear it.
