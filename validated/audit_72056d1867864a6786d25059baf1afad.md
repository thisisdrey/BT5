### Title
Unbounded per-instruction precompile signature-verification loop lets an attacker force costly cryptographic work far exceeding the fee actually charged - (File: precompiles/src/secp256k1.rs, precompiles/src/ed25519.rs)

### Summary
The Nouns DAO report shows that a fee/refund mechanism whose cost is a fixed base amount can be exploited when the actual work performed scales with an attacker-controlled, effectively unbounded input (a long `reason` string), letting the attacker externalize real cost onto the protocol. The closest reachable analog in Agave is the secp256k1/ed25519 precompile `verify()` routines, which loop over an attacker-controlled `count`/`num_signatures` byte (up to 255) doing a full hash + signature-recovery/verification per iteration, while the fee and cost-model accounting for these operations is computed separately from, and prior to, the actual work being performed.

### Finding Description
`precompiles/src/secp256k1.rs::verify()` reads `count = data[0]` (up to 255) and, for `i in 0..count`, parses `SecpSignatureOffsets`, slices out a message via attacker-chosen `message_data_offset`/`message_data_size`, computes a Keccak-256 hash of the message, and performs a full `libsecp256k1::recover` (ECDSA public-key recovery): [1](#0-0) [2](#0-1) 

Similarly, `precompiles/src/ed25519.rs::verify()` loops `num_signatures` (up to 255) times, each iteration performing a full Ed25519 `verify_strict` signature check over an attacker-chosen message slice: [3](#0-2) [4](#0-3) 

Neither loop is metered against a compute budget inside the `verify()` function itself — there is no `compute_meter.consume_checked()` call anywhere in these files, unlike ordinary SVM syscalls (e.g., `SyscallSecp256k1Recover`, `SyscallLogData`) which explicitly charge CUs proportional to work performed: [5](#0-4) [6](#0-5) 

Instead, the *only* accounting for this work is a coarse, fixed-per-signature constant used purely for block-space/cost-model bookkeeping, not to bound or charge for the actual cryptographic work in `verify()`: [7](#0-6) [8](#0-7) 

This is structurally the same disconnect as the Nouns bug: the fee/cost model measures a fixed, coarse quantity (`count` × constant), while the real work executed by `verify()` scales with `count` × message length, and the "count" field is entirely attacker-controlled inside the precompile instruction's own data, independent of the transaction's declared number of signatures (which is what the base transaction fee is keyed off of). A single ≤1232-byte transaction (bounded only by packet size) can declare `count = 255` and have all offsets reference overlapping regions of a small payload, forcing up to 255 Keccak-256 hashes plus 255 full ECDSA recoveries (secp256k1) — or 255 Ed25519 strict verifications — to be executed for the cost of one packet.

Whether this executes pre- or post-fee-deduction depends on the `move_precompile_verification_to_svm` feature gate — `feature-set/src/lib.rs` shows this is a relatively recent SIMD-0159 feature, and both `Bank` and `SVM` code paths still reference precompile verification (`runtime/src/bank.rs`, `program-runtime/src/invoke_context.rs`), indicating the legacy path (verification performed in `Bank::verify_transaction`/`verify_if_precompile`, prior to entering the fee-charging execution pipeline) still exists for compatibility: [9](#0-8) 

I was not able to fully confirm, within tool budget, the exact call site and ordering guarantees relative to fee deduction on the currently-default code path (whether `move_precompile_verification_to_svm` is unconditionally active and whether fee deduction always strictly precedes precompile verification in that path). This is a material uncertainty that affects whether the "free" (never-fee-charged) variant of the exploit applies universally or only pre-activation/legacy paths.

### Impact Explanation
An unprivileged network participant can submit small, cheap-to-send transactions that force any validator (leader doing sigverify, or any node performing `verify_transaction` during replay/forwarding) to perform on the order of 255 expensive asymmetric-crypto operations (ECDSA recovery or Ed25519 verification, each preceded by a hash over attacker-chosen data) per transaction, at a cost far exceeding the transaction-fee-based accounting used to gate/price CPU usage. If this executes prior to fee collection (e.g., a transaction crafted to fail sig verification or fail to land in a block), the attacker pays nothing for the CPU cycles consumed by every validator that processes the packet — a "grossly underpriced pre-fee work" condition that can be used to degrade validator throughput/QoS at low cost, analogous to how the Nouns voter could burn ETH by forcing expensive event-emission work that wasn't proportionally charged.

### Likelihood Explanation
Constructing such a transaction requires no special privileges — only a valid signed transaction containing a `secp256k1_program`/`ed25519_program` instruction with a large `count`/`num_signatures` byte and offsets pointing at overlapping regions of the transaction's own instruction data (well within the 1232-byte packet limit). No validator or operator role is needed, and the mechanism is reachable from the standard QUIC/UDP transaction-ingestion path feeding `SigVerifyStage`/`Bank::verify_transaction`.

### Recommendation
Meter the precompile `verify()` loops against a per-transaction compute/CPU budget proportional to `count` and total message bytes processed (mirroring how `SyscallSecp256k1Recover`/`SyscallLogData` charge CUs), and/or cap `count`/`num_signatures` and enforce it during early transaction sanitization (before any hashing/recovery work is attempted), so that the cost incurred cannot exceed what the declared transaction fee (or an admission-control heuristic keyed to the same field) actually covers.

### Proof of Concept
Not independently executable from the indexed code alone (would require constructing a transaction with `secp256k1_program`/`ed25519_program` instruction data setting `count`/`num_signatures = 255` with `SecpSignatureOffsets`/`Ed25519SignatureOffsets` referencing overlapping small regions of the same instruction, then measuring CPU time in `precompiles::secp256k1::verify` / `precompiles::ed25519::verify` versus the fee actually charged). Confirming the precise fee/verification ordering under the currently-active feature set would require running the validator with a debugger/profiler, which is outside the scope of this static analysis.

/// Check that a program is precompiled and if so verify it
pub fn verify_if_precompile(
    program_id: &Pubkey,
    precompile_instruction: &CompiledInstruction,
    all_instructions: &[CompiledInstruction],
    feature_set: &FeatureSet,
) -> Result<(), PrecompileError> {
    for precompile in PRECOMPILES.iter() {
        if precompile.check_id(program_id, |feature_id| feature_set.is_active(feature_id)) {
            let instruction_datas: Vec<_> = all_instructions
                .iter()
                .map(|instruction| instruction.data.as_ref())
                .collect();
            return precompile.verify(
                &precompile_instruction.data,
                &instruction_datas,
                feature_set,
            );
        }
    }
    Ok(())
}
