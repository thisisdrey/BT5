## Analysis

The Solidity bug described in the report is a classic **"trust an identifier without validating the caller is authorized to act on the resource it maps to"** pattern — `vaultAddress` is used to index into `vaults[vaultAddress]` and drive a fund-moving `transferFrom` without checking the vault was ever initialized.

The closest reachable analog in `nebula--016` (no CA-signed certificate required) is in `f.handleRecvError`, which processes unauthenticated `header.RecvError` packets. `RecvError` is dispatched in `readOutsidePackets` *before* any hostinfo/certificate check is performed: [1](#0-0) 

The handler resolves the attacker-supplied `RemoteIndex` to a `HostInfo` via `QueryReverseIndex`, then is supposed to validate that the packet's source address matches the hostinfo's known remote before tearing the tunnel down: [2](#0-1) 

### Root cause
The spoof check `hr.IsValid() && hr != addr` only executes when `hr` (the hostinfo's stored remote) is valid. `hostinfo.remote` is only populated on non-relayed paths — `SetRemote` is skipped whenever `via.IsRelayed` is true: [3](#0-2) [4](#0-3) 

For any host reached purely through a relay (a supported, common Nebula topology, see `relay_manager.go`/e2e relay tests), `hostinfo.remote` is never set, so `hr.IsValid()` is always `false`, and the address-check branch is **never evaluated** — exactly like `vaultAddress` never being checked against `vaults[vaultAddress].tradeStart`. The `RemoteIndex` (the "unchecked identifier") is trusted implicitly to authorize a destructive action (`closeTunnel` + `DeleteHostInfo`) regardless of who actually sent the packet.

### Title
Unvalidated source address allows unauthenticated remote teardown of relayed tunnels via spoofed RecvError - (File: `outside.go`)

### Summary
`handleRecvError` in `outside.go` resolves an attacker-controlled `RemoteIndex` to a live `HostInfo` and closes the tunnel, but only verifies the packet's source address against `hostinfo.GetRemote()` when that field `IsValid()`. Because relayed hostinfos never populate `remote` (see `handshake_manager.go` lines 792-793 and 886-888), the validation is unconditionally skipped for every relay-only tunnel, exactly mirroring the reported bug class of using an identifier/address to authorize a state-changing action without checking whether the associated validation state was actually initialized.

### Finding Description
`RecvError` is one of the few message types processed in `readOutsidePackets` before any certificate/handshake state is required [1](#0-0) , making it reachable by any network attacker who can reach the UDP listener, with no CA-signed certificate. `handleRecvError` looks up the target purely by the 32-bit `RemoteIndex` taken from the packet header [5](#0-4) , then is meant to gate the destructive `closeTunnel`/`DeleteHostInfo` call behind a source-address match `hr.IsValid() && hr != addr` [6](#0-5) . For relay-only tunnels, `hostinfo.remote` is structurally never set [4](#0-3) , so `hr.IsValid()` is always false and the whole spoof-detection branch is dead code for that class of hosts — the "vaultAddress" analog (`RemoteIndex`) is trusted without confirming it maps to a validated/initialized trust relationship with the sender.

### Impact Explanation
An attacker who learns or brute-forces a valid `RemoteIndex` for a relayed tunnel can spoof a `RecvError` packet from any arbitrary UDP source and unilaterally force `closeTunnel` and `DeleteHostInfo`, tearing down the victim's relayed tunnel without possessing any certificate. This is a remote, unauthenticated DoS/state-poisoning primitive (repeated teardown prevents relayed peers from maintaining stable tunnels), and it can be triggered against the entire pool of relay-dependent tunnels in a deployment.

### Likelihood Explanation
Exploitation only requires network reachability to the target's UDP port and knowledge of a `RemoteIndex` (generated via `generateIndex`, 32-bit). Any actively-communicating relayed tunnel is exposed via observed traffic containing the same `RemoteIndex` field in cleartext headers, or simple brute force at UDP-scale rates, making this practically triggerable without any cryptographic material.

### Recommendation
Do not gate the RecvError spoof check on `hr.IsValid()`. For relay-carried hostinfos, either reject direct (non-relayed) RecvError packets outright, or validate the packet against the relay's known peer/relay hostinfo (`relayState`) instead of `hostinfo.GetRemote()`. At minimum, when `hr` is invalid, the handler should fail closed (drop) rather than proceed to `closeTunnel`.

### Proof of Concept
1. Attacker observes (or brute forces) the `RemoteIndex` used for a relay-only tunnel between `victim` and `them`.
2. Attacker crafts a raw UDP packet with `header.RecvError` type and that `RemoteIndex`, sent from an arbitrary source address to `victim`'s listener.
3. `readOutsidePackets` dispatches it to `handleRecvError` before any cert check [7](#0-6) .
4. `QueryReverseIndex` finds the relayed `HostInfo`; `hr.IsValid()` is false (never set for relayed tunnels), so the `addr` spoof check is skipped, and `f.closeTunnel(hostinfo)` executes unconditionally [8](#0-7) .
5. The victim's relayed tunnel is torn down by an attacker holding no valid certificate.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
```
