## Analysis

I found a strong, code-level analog of the git-fastclone bug class (CVE-2015-8968: malicious `.gitmodules` driving unintended local-resource interaction during submodule operations) inside Bazel's own `git_repository` implementation.

### Title
Bazel's `git_repository`/`git_worker.bzl` force-enables `protocol.file.allow=always` for submodule updates, reintroducing arbitrary local-repository disclosure via attacker-controlled `.gitmodules` - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_worker.bzl`'s `update_submodules` unconditionally passes `-c protocol.file.allow=always` to `git submodule update --init [--recursive] --checkout --force` whenever a `git_repository` rule is fetched with `init_submodules` or `recursive_init_submodules` set. This bypasses Git's own hardening (the `protocol.file.allow` allowlist, defaulted to `user`/disabled for automated operations since Git 2.38.1) that was introduced specifically to stop the class of attacks where a hostile repository's `.gitmodules` directs Git to clone from arbitrary local paths during recursive/submodule operations — the same "content dictates unexpected local interaction during submodule fetch" bug class as the git-fastclone advisory.

### Finding Description
`update_submodules` in [1](#0-0)  runs:

```
_git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
```

for every submodule update, with a comment noting it's needed "for Git 2.38.1 and associated backport versions" (referencing bazelbuild/bazel#17040). Git 2.38.1 changed `protocol.file.allow`'s default specifically as a mitigation against submodule/recursive-clone attacks where a `.gitmodules`-declared `url` can point to a local `file://` path, letting a hostile superproject direct Git to touch arbitrary local repositories during clone/checkout of a submodule. Bazel unconditionally re-enables this disabled protocol for every `git_repository(init_submodules=True)` or `git_repository(recursive_init_submodules=True)` invocation — not just for the specific test/CI scenario the linked issue was trying to fix (bazelbuild/bazel#17040, about local test git servers) — regardless of whether the remote repository is trusted.

An attacker who publishes or controls a Git remote (e.g. an "outer" repository a victim's `MODULE.bazel`/`WORKSPACE` fetches via `git_repository`) fully controls its `.gitmodules` file, exactly the untrusted-content vector in CVE-2015-8968. With `protocol.file.allow=always` forced by Bazel, a submodule entry can declare `url = file:///absolute/local/path`, and `git submodule update --init` will happily clone/checkout from that local path without any user confirmation — the exact operation upstream Git chose to disable by default because of this attack surface.

### Impact Explanation
This lets a malicious remote git repository — reachable simply by being named as `remote` in a `git_repository` rule with submodule initialization enabled — direct the victim's Git client to read from arbitrary local filesystem paths and place their contents into the fetched external repository directory, which Bazel then makes visible to `BUILD` targets. This is a concrete "read outside the repository" primitive: content the repository author never intended to be part of the build (files or entire other repositories on the victim's disk) can be smuggled into the build graph and, downstream, exfiltrated or consumed by build actions.

### Likelihood Explanation
`init_submodules`/`recursive_init_submodules` are documented, commonly-used attributes of `git_repository` (see test coverage at [2](#0-1)  and [3](#0-2) ). Any project that depends on a third-party or less-trusted git dependency with `recursive_init_submodules = True` triggers this code path automatically on `bazel build`/`bazel fetch`, with no additional user action beyond adding the dependency — matching the "unprivileged outsider publishes content a victim's build consumes" threat model exactly.

### Recommendation
Scope `protocol.file.allow=always` narrowly (e.g., only re-enable it for the specific local-clone scenario #17040 addresses, such as when `remote` itself is a local path), or drop the override entirely and let Git's default protection stand, requiring users to explicitly opt in (e.g., via a new `allow_file_protocol` attribute) when they know the remote is trusted.

### Proof of Concept
Extend the existing submodule test harness (`src/test/shell/bazel/starlark_git_repository_test.sh`) with a malicious "outer" repository whose `.gitmodules` declares a submodule pointing at an absolute local path outside the intended clone directory (e.g. a sibling directory containing sensitive/marker content that is itself a bare git repo). Configure a `git_repository(remote=..., recursive_init_submodules=True)` pointing at the malicious repo and assert that after `bazel build`, the marker content from the out-of-scope local path has been checked out into the external repository directory — demonstrating that Bazel's forced `protocol.file.allow=always` let attacker-controlled `.gitmodules` content read local resources the victim never intended to expose to the build. def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")

```shellscript
function test_git_repository_submodules() {
  local outer_planets_repo_dir=$TEST_TMPDIR/repos/outer-planets

  # Create a workspace that clones the outer_planets repository.
  cat >> MODULE.bazel <<EOF
git_repository = use_repo_rule('@bazel_tools//tools/build_defs/repo:git.bzl', 'git_repository')
git_repository(
    name = "outer_planets",
    remote = "$outer_planets_repo_dir",
    tag = "1-submodule",
    init_submodules = 1,
    build_file = "//:outer_planets.BUILD",
)
EOF

  cat > BUILD <<EOF
exports_files(['outer_planets.BUILD'])
EOF
  cat > outer_planets.BUILD <<EOF
filegroup(
    name = "neptune",
    srcs = ["neptune/info"],
    visibility = ["//visibility:public"],
)

filegroup(
    name = "pluto",
    srcs = ["pluto/info"],
    visibility = ["//visibility:public"],
)
EOF

  mkdir -p planets
  cat > planets/BUILD <<EOF
genrule(
    name = "planet-info",
    srcs = [
        "@outer_planets//:neptune",
        "@outer_planets//:pluto",
    ],
    outs = ["planet-info.txt"],
    cmd = "cat \$(SRCS) > \$@",
)
EOF

  bazel build //planets:planet-info >& $TEST_log \
    || echo "Expected build/run to succeed"
  cat bazel-bin/planets/planet-info.txt > $TEST_log
  expect_log "Neptune is a planet"
  expect_log "Pluto is a planet"
}
```
