### Title
Missing account-existence check in `WithdrawRewardProcessor` before unconditional dereference - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawRewardProcessor.java`)

### Summary
`WithdrawRewardProcessor`, the native-contract handler invoked from TVM opcode execution for reward withdrawal, dereferences `repo.getAccount(ownerAddress)` unconditionally in `execute()` without ever checking that the account exists, in `validate()` or `execute()`. This is the same bug class as CVE-2024-56782: a helper that is normally called with a guaranteed-non-null object dereferences it without a defensive null check, unlike every sibling processor in the same package that performs this exact check before use.

### Finding Description
`WithdrawRewardProcessor.validate()` only rejects genesis-witness addresses; it never confirms that `repo.getAccount(ownerAddress)` returns a non-null `AccountCapsule`: [1](#0-0) 

`execute()` then calls `repo.getAccount(ownerAddress)` again and immediately dereferences the result without a null check: [2](#0-1) 

This is inconsistent with every other native-contract processor in the same package, all of which explicitly null-check the `AccountCapsule` returned from `repo.getAccount(...)` before touching it:
- `FreezeBalanceV2Processor.validate()`: [3](#0-2) 
- `UnfreezeBalanceV2Processor.validate()`: [4](#0-3) 
- `DelegateResourceProcessor.validate()`: [5](#0-4) 
- `UnDelegateResourceProcessor.validate()`: [6](#0-5) 

`WithdrawRewardProcessor` is the outlier that omits this check entirely, exactly mirroring the kernel pattern where `acpi_quirk_skip_serdev_enumeration()` dereferenced `adev` without the null guard that similar call sites already had.

### Impact Explanation
If `repo.getAccount(ownerAddress)` ever returns `null` for the address passed into `WithdrawRewardProcessor.execute()` — e.g., through a codepath where the reward-eligible address (a voter/witness address distinct from the calling contract's own context address) has no backing `AccountCapsule` record, or via future contract-suicide/account-pruning interactions not covered by today's callers — `accountCapsule.getBalance()` on line 44 throws an unguarded `NullPointerException` inside TVM opcode execution. Because this occurs inside transaction/block processing (`Manager` block application via `VMActuator`/`Program`), an uncaught `NullPointerException` (not a handled `ContractExeException`/`ContractValidateException`) can propagate out of block execution, causing a node crash or halt while processing an otherwise valid signed transaction or contract call — a concrete node-crash/halt impact within the report's acceptance criteria.

### Likelihood Explanation
Today's known caller path for this processor derives `ownerAddress` from the calling contract's own context address (which must exist to be executing), so under the currently exercised call site the NPE is not trivially reachable — matching the "at the moment never called with null, but better safe than sorry" characterization of the original CVE. The reachability of a null `AccountCapsule` here could not be fully confirmed from this codebase (I did not locate/verify the exact `Program.java` opcode call site and its argument derivation for `WithdrawRewardParam.ownerAddress`, nor whether an outer `try/catch` wraps arbitrary `RuntimeException` from native-contract execution). This should be treated as an unresolved gap: further investigation of the opcode dispatch that constructs `WithdrawRewardParam` and of the exception-handling wrapper around `processor.execute()` is needed to establish whether an attacker-controlled address can actually reach `execute()` with a non-existent account. Given the inconsistency with sibling processors and the class of past CVE (an unreachable-today but real latent NPE), Medium severity as a defensive gap is warranted; it should not be treated as a confirmed high-likelihood attacker path without that additional verification.

### Recommendation
Add a null check for the `AccountCapsule` returned by `repo.getAccount(ownerAddress)` in `WithdrawRewardProcessor.validate()` (throwing `ContractValidateException` on missing account, consistent with `FreezeBalanceV2Processor`/`UnDelegateResourceProcessor`), and/or add a defensive null check immediately before use in `execute()`, so that any future or currently-unverified call path cannot trigger an unguarded `NullPointerException` during TVM/block execution.

### Proof of Concept
Not independently reproducible from static review alone: constructing a concrete PoC requires confirming, in `Program.java`/`OperationRegistry.java`, the exact opcode that constructs `WithdrawRewardParam.ownerAddress` and demonstrating that this address can, for some legitimate signed transaction, correspond to a non-existent `AccountCapsule` at the moment `WithdrawRewardProcessor.execute()` runs. This verification step was not completed within the current investigation and is flagged as an open item for a follow-up session with full repository/tooling access.
