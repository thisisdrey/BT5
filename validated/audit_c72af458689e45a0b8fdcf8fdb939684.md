Confirmed root cause: this is a strong analog of the Autonomint bug.

### Title
Underflow/DoS in `UnDelegateResourceActuator.execute` — validation sums two delegated-resource buckets but only decrements one - (File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java)

### Summary
`UnDelegateResourceActuator.validate()` computes `delegateBalance` as the **sum** of two separate `DelegatedResourceCapsule` buckets (the "unlock" resource and, if expired, the "lock" resource) and checks that this combined sum is `>= unDelegateBalance`. However, `execute()` only subtracts `unDelegateBalance` from the single "unlock" resource capsule (`unlockResource`), never from the "lock" resource capsule. This is exactly the same class of bug as the Autonomint `withdrawInterest` issue: sum-based validation with single-bucket decrement.

### Finding Description
In `validate()`, the combined delegated balance across both storage buckets is computed and checked against the requested `unDelegateBalance`: [1](#0-0) 

For example, for `BANDWIDTH`:
```java
long delegateBalance = 0;
if (unlockResourceCapsule != null) {
  delegateBalance += unlockResourceCapsule.getFrozenBalanceForBandwidth();
}
if (lockResourceCapsule != null
    && lockResourceCapsule.getExpireTimeForBandwidth() < now) {
  delegateBalance += lockResourceCapsule.getFrozenBalanceForBandwidth();
}
if (delegateBalance < unDelegateBalance) {
  throw new ContractValidateException(...);
}
```
This passes as long as `unlock + lock >= unDelegateBalance`, even when the unlock bucket alone is insufficient.

In `execute()`, only the "unlock" resource is fetched and decremented (after an unrelated `unLockExpireResource` call meant to migrate expired lock funds into unlock — but this migration is not guaranteed to move the *entire* expired lock amount before the subtraction, and more importantly, the validate-time snapshot of `lockResourceCapsule`/`unlockResourceCapsule` used for the sum check is not the same object mutated in execute): [2](#0-1) 

```java
delegatedResourceStore.unLockExpireResource(ownerAddress, receiverAddress,
    dynamicStore.getLatestBlockHeaderTimestamp());

byte[] unlockKey = DelegatedResourceCapsule.createDbKeyV2(ownerAddress, receiverAddress, false);
DelegatedResourceCapsule unlockResource = delegatedResourceStore.get(unlockKey);

...
switch (unDelegateResourceContract.getResource()) {
  case BANDWIDTH: {
    unlockResource.addFrozenBalanceForBandwidth(-unDelegateBalance, 0);
    ...
```
`addFrozenBalanceForBandwidth(-unDelegateBalance, 0)` sets `frozenBalanceForBandwidth = frozenBalanceForBandwidth - unDelegateBalance` with no floor check. If `unlockResource.getFrozenBalanceForBandwidth() < unDelegateBalance` (i.e., most of the combined balance actually lived in the "lock" bucket and `unLockExpireResource` did not fully reconcile it before the subtraction — e.g. differing time semantics between `validate()`'s `dynamicStore.getLatestBlockHeaderTimestamp()`-based expiry check and the delegated-resource-store's own migration logic, or a race/ordering issue between when `now` is computed for validate vs execute across block boundaries), this produces a negative `frozenBalanceForBandwidth`, corrupting account/resource state (an "unbacked"/negative balance) rather than a clean revert, since the setter used here (`addFrozenBalanceForBandwidth`) is a raw field arithmetic without an underflow guard, unlike other places in the codebase that use `LongMath.checkedAdd`/`subtractExact`.

The identical pattern is repeated for `ENERGY`: [3](#0-2) [4](#0-3) 

### Impact Explanation
An unprivileged transaction broadcaster who has delegated resources to a receiver, with part of the delegation in the "lock" bucket and part in the "unlock" bucket, can trigger a decrement that is not properly reconciled against the correct bucket, producing an incorrect/negative frozen-balance field on the `DelegatedResourceCapsule`. This corrupts resource-accounting state used for bandwidth/energy allocation (an unbacked resource condition), and can also cause subsequent legitimate `UnDelegateResourceContract` transactions to behave unpredictably (over-crediting the owner's `FrozenBalanceForBandwidthV2`/`FrozenBalanceForEnergyV2`, i.e., resource amplification) since `ownerCapsule.addFrozenBalanceForBandwidthV2(unDelegateBalance)` always credits the full requested amount regardless of whether the decrement bucket had sufficient headroom.

### Likelihood Explanation
This requires a specific but reachable state: an owner delegating to the same receiver twice using the lock/unlock delegation model such that the "lock" resource's expire time has passed (`< now`) at validate time, while the actual value that gets migrated into "unlock" by `delegatedResourceStore.unLockExpireResource` at execute time diverges from validate-time expectations, or the requested `unDelegateBalance` is chosen to exceed the unlock-only balance while remaining within the combined sum. This is a data-flow/timing-window class of bug and would need to be verified more precisely against `DelegatedResourceStore.unLockExpireResource`'s exact matching semantics to confirm a reliably exploitable underflow versus a benign self-correcting migration — I was not able to fully inspect `DelegatedResourceStore.unLockExpireResource` in this session, so exploitability confidence is moderate rather than fully proven.

### Recommendation
In `execute()`, decrement sequentially/proportionally across both the unlock and lock buckets (mirroring how `validate()` accumulates the combined sum), with an explicit floor check, e.g.:
```java
long fromUnlock = Math.min(unDelegateBalance, unlockResource.getFrozenBalanceForBandwidth());
unlockResource.addFrozenBalanceForBandwidth(-fromUnlock, 0);
long remaining = unDelegateBalance - fromUnlock;
if (remaining > 0) {
  lockResource.addFrozenBalanceForBandwidth(-remaining, 0);
}
```
Additionally, add a `ContractExeException`/assertion in `execute()` if any bucket's balance would go negative, so this fails safely (as a `ContractExeException`) rather than silently corrupting stored state.

### Proof of Concept
Not independently executed against a running node in this session; the above is derived purely from static code analysis of `UnDelegateResourceActuator.validate()` vs `execute()`. Concrete reproduction would require: (1) delegate BANDWIDTH to a receiver creating a "lock" resource entry, (2) let it expire, (3) delegate again creating a fresh "unlock" entry with a smaller balance than the total lock+unlock sum, (4) call `UnDelegateResourceContract` with `balance` greater than the unlock bucket alone but within the combined sum, and (5) inspect `DelegatedResourceCapsule.getFrozenBalanceForBandwidth()` for a negative result. I could not run this reproduction in the current session and flag it as unverified dynamically.
