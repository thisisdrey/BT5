### Title
Dust DepositToken donations keep victim permanently enrolled in `depositTokensOfAccount` and can exhaust `MAX_TOKENS_PER_USER` to block deposits - (File: contracts/DepositToken.sol)

### Summary
The external report describes a strategy exit/trigger keyed on `balance == 0`, which an attacker defeats by donating dust. Metronome has the same pattern: `Pool` tracks each account's collateral set via `depositTokensOfAccount`, and `DepositToken` adds/removes the account based solely on whether the balance crosses zero. Any EOA can `transfer` 1 wei of a `DepositToken` to a victim, forcing them back into the set (reverting any removal) and — worse — filling their per-account token slots until `UserReachedMaxTokens` bricks the victim's ability to deposit new collateral or receive deposit-token transfers.

### Finding Description
`DepositToken._transfer` adds the recipient to the pool's per-account set whenever their balance transitions from zero, and removes the sender only when their balance hits exactly zero (`contracts/DepositToken.sol:517-525`). The same zero-crossing logic exists in `_mint`/`_burn` (`contracts/DepositToken.sol:459-462,485-488`). `Pool.addToDepositTokensOfAccount` enforces `MAX_TOKENS_PER_USER` and reverts with `UserReachedMaxTokens` when full (`contracts/Pool.sol:32`), and the set is a `MappedEnumerableSet` used by `debtPositionOf`/`depositOf` to iterate all of an account's collaterals.

Attack path, all public:
1. Attacker deposits a minimal amount into every `DepositToken` in the pool (or just holds dust of each).
2. Attacker calls `DepositToken.transfer(victim, 1)` for each deposit token. Each call executes `pool.addToDepositTokensOfAccount(victim)` because `_recipientBalanceBefore == 0`.
3. Once the victim's set reaches `MAX_TOKENS_PER_USER`, every subsequent `_mint` (deposit) or `_transfer` to the victim for a *new* token reverts — the victim cannot deposit a different collateral, cannot be added via `SmartFarmingManager` leverage flows, and cannot receive transfers.
4. Even before the cap is hit, each dust donation re-adds the victim after they fully withdraw (`_burn` removes them only at `balanceAfter == 0`), so the "exit on zero balance" invariant is defeated exactly as in the report — the victim can never actually leave the set while an attacker keeps donating.

No modifier stops this: `transfer` is a plain public ERC20 entry point, `SynthContext` checks don't apply, and the add happens unconditionally on the recipient's balance transition. The victim can clear slots by transferring dust out (which removes them only for tokens they fully empty), but the attacker can re-add at will — and the victim's own deposits of new collaterals revert in the meantime.

### Impact Explanation
Temporary freezing of funds: the victim's `deposit()` for any new collateral token reverts with `UserReachedMaxTokens` while the set is full, and leverage/deposit flows targeting the victim fail. It is temporary rather than permanent because the victim can shed slots by transferring each dust balance away, but the attacker can cheaply re-grief. The zero-balance exit invariant (account is removed from the tracking set when balance hits 0) is broken — identical mechanism to the reported `hasZeroBalance` bypass.

### Likelihood Explanation
Requires only an EOA holding dust of the pool's deposit tokens and public `transfer` calls. Cost is negligible (1 wei per token). No privileged role, oracle manipulation, or flash loan needed. The main limitation is that the DoS is escapable (victim transfers dust out), which is why impact is griefing-class rather than direct theft.

### Recommendation
Mirror the fix proposed in the report: treat balances below a dust threshold as zero for set membership — e.g., in `DepositToken._transfer`/`_mint`, only call `pool.addToDepositTokensOfAccount` when `amount_` (or resulting balance) exceeds a `DUST_AMOUNT`, and in `_burn`/`_transfer` remove the account when `balanceAfter <= DUST_AMOUNT`. Alternatively, only add an account on `deposit()` (initiated by/for the account) rather than on arbitrary inbound `transfer`s, so third-party donations cannot expand the victim's tracked set.

### Proof of Concept
```solidity
// Foundry fork test sketch
function test_dustDonationGriefing() public {
    // victim holds no deposit tokens
    // attacker deposits 1 wei of underlying into each DepositToken
    for (uint i; i < depositTokens.length; ++i) {
        IDepositToken dt = IDepositToken(depositTokens[i]);
        underlying.approve(address(dt), 1);
        dt.deposit(1, attacker);
    }
    // attacker dusts victim with every deposit token
    for (uint i; i < depositTokens.length; ++i) {
        IDepositToken(depositTokens[i]).transfer(victim, 1);
    }
    assertEq(pool.getDepositTokensOfAccount(victim).length, depositTokens.length);

    // victim deposits a new collateral token -> reverts inside _mint
    vm.startPrank(victim);
    newUnderlying.approve(address(newMsdToken), type(uint256).max);
    vm.expectRevert(UserReachedMaxTokens.selector);
    newMsdToken.deposit(100e18, victim);
    vm.stopPrank();

    // victim fully withdraws token[0]; attacker re-adds with 1 wei
    vm.prank(victim);
    IDepositToken(depositTokens[0]).withdraw(1, victim);
    IDepositToken(depositTokens[0]).transfer(victim, 1); // attacker re-adds
    assertTrue(isStillInSet(victim, depositTokens[0]));
}
```
