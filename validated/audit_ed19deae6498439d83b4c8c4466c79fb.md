Single-Step, Unvalidated Account Permission Transfer in `AccountPermissionUpdateActuator` Can Permanently Lock an Account - ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
`AccountPermissionUpdateContract` lets an account holder overwrite its `Owner`, `Witness`, and `Active` permission key sets in a single transaction, with no two-step confirmation and no verification that the new key addresses correspond to controllable accounts, mirroring the reported "no transfer ownership pattern" bug class.

### Finding Description
The actuator processes the contract directly, replacing the account's permission structure in one step: [1](#0-0) 

Validation (`validate()`) only checks structural/format constraints on the new keys — count limits, threshold sums, name length, distinctness, and address *format* validity via `DecodeUtil.addressValid`: [2](#0-1) 

`DecodeUtil.addressValid` only checks byte length and address prefix; it does not check that the address belongs to an existing, key-controlled account: [3](#0-2) 

There is no acceptance/confirmation step from the new key holder(s) analogous to `acceptOwnership()`. Once `execute()` calls `account.updatePermissions(...)` and persists the account, the previous owner permission is irreversibly discarded — this is the exact single-step, no-validation ownership-transfer pattern flagged in the external report (`OpOwner.transferOwnership`).

### Impact Explanation
If a user submits an `AccountPermissionUpdateContract` with a mistyped, unowned, or otherwise uncontrolled address in the `Owner` permission's key list (any syntactically valid 21-byte address with the correct prefix passes validation), the account permanently loses the ability to satisfy its own `Owner` permission threshold. Since the `Owner` permission governs all subsequent `AccountPermissionUpdateContract` transactions for that account (as well as any other permission-checked contract types when active permissions are misconfigured), this results in **permanent freezing of all funds and control of that account**, with no path to recovery — matching the report's core impact category (permanent loss/freezing of funds due to an unvalidated one-step ownership handover).

### Likelihood Explanation
This is reachable by any account holder in a single broadcast transaction (`AccountPermissionUpdateContract`) requiring only that `AllowMultiSign` is enabled on the network (already the case on mainnet) and that the caller has a valid, existing account. No special privilege is required. The only barrier is that the caller must accidentally or maliciously (e.g., a compromised or buggy wallet/tool) submit a permission structure the caller cannot satisfy — a classic operator/UX error class the referenced report specifically targets, so likelihood should be assessed as low-to-moderate (typo/tooling error), consistent with the Medium severity of the original finding.

### Recommendation
Introduce a two-step confirmation for `Owner` permission changes: require a subsequent transaction, signed under the *new* permission set, that explicitly acknowledges/accepts the change before it is finalized (analogous to `acceptOwnership()`), or at minimum simulate/verify locally (client-side and/or optionally on-chain) that the new `Owner` permission's key set can satisfy its own threshold before allowing the contract to persist. Additionally, consider warning/rejecting permission updates where none of the new owner keys match a previously known, actively used key, to reduce accidental self-lockout.

### Proof of Concept
1. Account `A` holds `TRX` and has default owner/active permissions with `A`'s own key.
2. `A` submits `AccountPermissionUpdateContract` with `owner_address = A`, and `owner` permission's key list containing address `B` (a syntactically valid but non-existent/uncontrolled address — e.g., a typo of a real address) with `threshold = 1`.
3. `validate()` passes: `DecodeUtil.addressValid(B)` returns true because it only checks length/prefix, all other structural checks pass.
4. `execute()` calls `account.updatePermissions(owner, witness, actives)` and persists — `A`'s owner permission is now controlled solely by `B`'s (unknown/uncontrolled) private key. [1](#0-0) 
5. Account `A` can never again submit a valid `AccountPermissionUpdateContract` (or any owner-permission-gated action) because it cannot produce a signature satisfying the new `Owner` permission — all funds and control are permanently frozen.

    if (ArrayUtils.isEmpty(address)) {
