### Title
Attacker can permanently fill a victim's account token list with dust deposits, causing `UserReachedMaxTokens` reverts that block all new deposits and issuances - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to the Multer bug — where a degenerate input (empty field name) triggers an unhandled exception that DoSes the process — an unprivileged attacker can send degenerate dust deposits/transfers of `DepositToken`s to a victim, filling the victim's per-account token set. Once `debtTokensOfAccount + depositTokensOfAccount` reaches `MAX_TOKENS_PER_USER` (30), every subsequent first-time mint or issuance to that account reverts with `UserReachedMaxTokens`, denying the victim the ability to deposit new collateral or issue new synthetics.

### Finding Description
`DepositToken._mint` and `DepositToken._transfer` unconditionally register the token in the recipient's account list whenever the recipient's balance moves from zero:

```solidity
// contracts/DepositToken.sol:517-520 (transfer path) and 486-488 (mint path)
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
```

`Pool.addToDepositTokensOfAccount` enforces the cap via `onlyIfAdditionWillNotReachMaxTokens`, which reverts once the combined list reaches `MAX_TOKENS_PER_USER = 30` [1](#0-0)  and [2](#0-1) . The same guard applies to `addToDebtTokensOfAccount` [3](#0-2) .

Attack path, all public/unprivileged:
1. For every deposit token registered in the pool, attacker calls `depositToken.deposit(1 wei underlying, victim)` (or deposits dust to self and calls `transfer(victim, 1)`). Each call mints/transfers a nonzero balance to a zero-balance recipient, so `addToDepositTokensOfAccount(victim)` adds the token to `depositTokensOfAccount[victim]`.
2. Thereafter, any `deposit`, `transfer`, `transferFrom`, `seize` (liquidation), or `issue`/`mint`/`flashIssue`/`leverage`/`Operator.execute` batch that would introduce a *new* token to the victim's list reverts — the `_mint`/`_transfer`/`DebtToken._mint` internal call into `addTo*TokensOfAccount` throws `UserReachedMaxTokens` and bubbles up, reverting the whole transaction.

### Impact Explanation
The victim is denied the ability to onboard any new collateral type or take on any new synthetic debt until they manually clear slots (by transferring an entire dust balance out to trigger `removeFromDepositTokensOfAccount`). Concretely:

- If the victim's position drifts toward liquidation, they cannot top up with a collateral they don't already hold, so an otherwise rescuable position gets liquidated — direct loss of funds.
- `SmartFarmingManager.leverage`/`flashRepay` and `Pool.swap` flows that mint a new token to the victim permanently revert.
- The dust tokens themselves are economically worthless to the attacker, so the griefing cost is ~30 dust deposits plus gas.

This maps to "temporary freezing of funds" / forced liquidation: the invariant broken is account liveness — a benign-looking edge case (1-wei nonzero balance) triggers a global revert on an unrelated, legitimate operation.

Caveat on reachability: the combined list must actually reach 30. The attacker can only populate the deposit side (debt tokens cannot be transferred — `DebtToken.transfer`/`transferFrom` revert with `TransferNotSupported` [4](#0-3) ). The attack therefore fully blocks the victim only if the pool has close to 30 deposit tokens, or the victim already holds several positions. With few registered collateral types the impact degrades to partial slot exhaustion.

### Likelihood Explanation
Likelihood is moderate: deposits of arbitrary `to_` are permissionless, dust amounts are accepted (`deposit` only rejects `amount_ == 0`), and no modifier (`whenNotShutdown`, `nonReentrant`, `SynthContext`) prevents the recipient-side list mutation. The only real constraint is the number of distinct deposit tokens deployed in the target pool, which is configuration-dependent.

### Recommendation
Do not couple pool-level list bookkeeping to attacker-influenced balance transitions for third-party recipients. Options:
- Only register a token in `depositTokensOfAccount` when the *caller* is the beneficiary (i.e., `deposit` self-deposits), and require recipients to opt in (e.g., `claim`/`accept` pattern) for transferred tokens.
- Alternatively, treat dust below a per-token minimum (e.g., a `dustThreshold`) as not list-worthy, or make `addToDepositTokensOfAccount` a no-op (rather than revert) at the cap and track positions via a different structure for excess tokens.

### Proof of Concept
```solidity
// Hardhat/Foundry fork, unprivileged attacker EOA
// Assumes pool with N registered deposit tokens; victim initially holds none.
for (uint256 i = 0; i < depositTokens.length; ++i) {
    IERC20 underlying = IERC20(depositTokens[i].underlying());
    // acquire 1 wei of each underlying
    underlying.approve(address(depositTokens[i]), 1);
    depositTokens[i].deposit(1, victim); // mints dust, registers token for victim
}
// depositTokensOfAccount[victim].length == N
// Repeat via transfers until length == MAX_TOKENS_PER_USER (30),
// or rely on victim's existing positions to make up the remainder.

// Any subsequent first-time deposit/mint to victim reverts:
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newDepositToken.deposit(1e18, victim); // reverts in _mint -> addToDepositTokensOfAccount

// Also blocks victim issuing a new synthetic:
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
debtToken.issue(victim, 100e18); // reverts in _mint -> addToDebtTokensOfAccount
```
