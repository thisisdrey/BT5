Based on my research, the strongest analog to the reported "unbounded loop over dynamic array" bug class in this Gitaly codebase is in the `FindMergeBase` RPC handler.

### Title
Unbounded `revisions` array in FindMergeBase causes resource exhaustion / oversized git-merge-base argv - ([File: internal/gitaly/service/repository/merge_base.go])

### Summary
The `FindMergeBase` RPC handler iterates over the client-supplied `revisions` repeated field without any upper-bound check and passes the resulting unbounded slice directly as command-line arguments to `git merge-base`, mirroring the reported bug class of "for loop over a dynamic array" without a max-length guard.

### Finding Description
`FindMergeBase` only validates that at least two revisions were supplied, then loops over the entire `req.GetRevisions()` slice to build the `revisions` string slice, which is passed unmodified as `Args` to the `git merge-base` command: [1](#0-0) [2](#0-1) 

There is no check on the maximum number of elements in `revisions`, unlike other size-sensitive RPCs in the codebase which explicitly cap batch sizes (e.g. `listPoolUpstreamsBatchSize` in `internal/cli/common/pool.go`) or stream unbounded results in chunks rather than accepting unbounded input in one message, as required by the documented RPC development guidelines: [3](#0-2) 

The proto definition itself documents that the field exists mainly for hypothetical future-proofing ("if we needed that in the future"), implying the design never anticipated large N: [4](#0-3) 

Because `FindMergeBase` is an `ACCESSOR` RPC reachable by any authenticated client with access to a repository (not privileged, not requiring a malicious peer or leaked token), a caller can submit a single request with an extremely large `revisions` array (bounded only by the gRPC max message size, which is large and separately configurable), causing Gitaly to build a correspondingly large `os/exec` argument list and spawn a `git merge-base` process with that huge argv.

### Impact Explanation
Building and executing a process with an oversized argument vector consumes significant server-side memory and CPU per request (argv marshaling, `git merge-base` internally processing every revision), and multiple concurrent requests of this shape can exhaust available resources on the Gitaly node, resulting in denial of service for the RPC handler and potentially for co-located repositories/services on the same node. This is a resource-limit gap on an RPC handler, matching the "DoS of a handler" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate-to-high: `FindMergeBase` requires only an authenticated gRPC client with access to a repository (a normal Gitaly caller, e.g. via GitLab Rails or a direct gRPC client), does not require any privileged position, malicious peer, or token leak, and the vulnerable code path is a straightforward unbounded loop with no length validation before command execution.

### Recommendation
Enforce a maximum number of entries (and/or total byte size) for `FindMergeBaseRequest.revisions` in `internal/gitaly/service/repository/merge_base.go`, returning `InvalidArgument` when the limit is exceeded, consistent with the batch-size patterns used elsewhere in the codebase (e.g. `listPoolUpstreamsBatchSize`). Additionally consider validating each revision's format (as `UpdateReferences` and `GetBlobs` do for their repeated fields) before it is used to construct git command arguments.

### Proof of Concept
A gRPC client can call `FindMergeBase` with a `Repository` it has access to and a `revisions` field containing an extremely large number of entries (e.g., hundreds of thousands of short strings), up to the gRPC max message size:
```
FindMergeBaseRequest{
  Repository: <valid repo>,
  Revisions: [][]byte{ "HEAD", "HEAD", ..., "HEAD" }  // N large, e.g. 500,000 entries
}
```
This causes the handler's loop at `internal/gitaly/service/repository/merge_base.go:19-26` to build a `revisions` slice of the same size and pass it as `Args` to `git merge-base` at lines 28-39, resulting in an oversized process invocation. Repeated/concurrent submission of such requests can degrade or exhaust Gitaly node resources.

**Note on verification limits:** I was unable to fully confirm within available tool calls whether `gitcmd.Command`'s argument-validation layer (`internal/git/gitcmd/command.go`, `command_options.go`) enforces any additional leading-dash/flag-injection or size checks on `Args` before exec, which could partially mitigate or compound this issue; further review of that argument-validation code is recommended (a Devin session with full file access could inspect this).

// FindMergeBaseRequest is a request for the FindMergeBase RPC.
message FindMergeBaseRequest {
  // repository is the repo to find the merge base in. The storage_name and
  // relative_path attributes must be provided.
  Repository repository = 1 [(target_repository)=true];
  // revisions is the revisions to find the merge base for.
  // We use a repeated field because rugged supports finding a base
  // for more than 2 revisions, so if we needed that in the future we don't
  // need to change the protocol.
  repeated bytes revisions = 2;
}
