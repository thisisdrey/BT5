### Title
Unbounded heap array read in `ValidateMultiSign` precompile signature-array extraction leads to uncaught `ArrayIndexOutOfBoundsException` (analog of CVE-2020-23269 `stbl_GetSampleSize`-style OOB read) - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
CVE-2020-23269 is a heap-based OOB read/write in `stbl_GetSampleSize` caused by trusting an attacker-controlled length/index field taken from a crafted media file without validating it against the buffer bounds before indexing. The same bug class — trusting an attacker-controlled offset/length word to index into a byte buffer without a bounds check — exists in the `ValidateMultiSign` precompiled contract's signature-array extraction path, reachable from any TVM contract call (i.e. any signed transaction that triggers a `CALL` to precompile address `0x…0a`).

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute` [1](#0-0) , the offset used to locate the signature array is taken directly from attacker-controlled call data: `words[3].intValueSafe() / WORD_SIZE`, and then `extractBytesArray`/`extractSigArray` is invoked with that offset before any bound checking against `words.length` or `rawData.length` occurs for the general (non-`allowTvmSelfdestructRestriction`) code path.

`extractBytesArray` reads `len = words[offset].intValueSafe()` and then, for each `i < len`, computes `bytesOffset` and `bytesLen` from further attacker-controlled words and calls `extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, bytesLen)` [2](#0-1) , which does `Arrays.copyOfRange(data, offset, offset + len)` with no bounds validation [3](#0-2) . `extractSigArray` has the identical unguarded indexing pattern with a fixed `SIG_LENGTH` [4](#0-3) . `words[offset]` itself can throw `ArrayIndexOutOfBoundsException` if `offset` (fully attacker-controlled via `words[3]`) exceeds `words.length`, and `Arrays.copyOfRange` throws the same when computed positions exceed `data.length`.

Crucially, this extraction code executes **outside** the `try { ... } catch (Throwable t)` block that wraps only the `AccountCapsule`/permission-weight logic later in the method [5](#0-4) . The `isValidAbiEncoding` guard added under TIP-854 (`VMConfig.allowTvmOsaka()`) only checks that the overall data length is consistent with a fixed header/item-word shape [6](#0-5)  — it does not validate that the dynamically-supplied offset in `words[3]` actually points within the declared bounds. Additionally, this hardening is feature-flag gated behind `allowTvmOsaka`; the vulnerable extraction path is unconditionally reachable and unguarded when that flag is inactive.

Unlike `BatchValidateSign`, whose `execute` wraps the entire `doExecute` call in a `try { ... } catch (Throwable t)` that safely converts any exception to `Pair.of(true, new byte[WORD_SIZE])` [7](#0-6) , `ValidateMultiSign.execute` has no such top-level guard, so an `ArrayIndexOutOfBoundsException` thrown while parsing the malicious offset/length propagates out of the precompile call.

### Impact Explanation
Any address can craft a `CALL`/`STATICCALL` to the `validateMultiSign` precompile (address ending `...0a`, gated only by `VMConfig.allowTvmSolidity059()`, which is generally enabled on mainnet) with a manipulated `words[3]` offset word so that `extractBytesArray`/`extractSigArray` or the earlier `words[offset]` access reads past the array bounds. Because the exception is thrown outside the guarded try/catch and there is no top-level catch for `ValidateMultiSign` (unlike `BatchValidateSign`), the uncaught `ArrayIndexOutOfBoundsException` propagates up through transaction execution. Depending on how far up the exception is caught (or not) in the VM/actuator/Manager stack, this can cause transaction execution/block application to fail unexpectedly for all nodes processing that transaction — a consensus-relevant crash/DoS condition, since every full node must deterministically execute the same TVM call.

### Likelihood Explanation
High reachability: this precompile is invocable by any unprivileged contract-calling transaction, with fully attacker-controlled call data, and no special privileges are required — only the ability to broadcast a transaction that triggers a `CALL` to the precompile address. The only precondition is that `allowTvmSolidity059` is enabled (a mainnet-active feature per the code's naming convention).

### Recommendation
Add explicit bounds validation for the offset(s) derived from `words[3]`/`words[1]`/`words[2]` in `ValidateMultiSign` and `BatchValidateSign` before indexing (`offset >= 0 && offset < words.length`, and range checks in `extractBytesArray`/`extractSigArray`/`extractBytes32Array` for `offset + i + 1`, `bytesOffset + offset + 2`, and `bytesLen` against `data.length`/`words.length`). Wrap the entirety of `ValidateMultiSign.execute` in a single outer `try { ... } catch (Throwable t)` (mirroring `BatchValidateSign.execute`) so any residual malformed-input exception degrades to a safe `Pair.of(true, DATA_FALSE)` rather than propagating uncaught. Make the `isValidAbiEncoding`-style bounds check unconditional rather than gated behind `allowTvmOsaka`.

### Proof of Concept
1. Construct ABI-encoded call data to `validateMultiSign(address,uint256,bytes32,bytes[])` where the dynamic offset word normally pointing to the `bytes[]` array header (`words[3]`) is replaced with a large value (e.g. `0xFFFFFFFF`), while keeping the overall data length matching the `(words - 5) / 5` shape expected by `isValidAbiEncoding`/`getEnergyForData` so that the length-shape guard passes (or simply invoke with `VMConfig.allowTvmOsaka()` disabled, which skips the guard entirely).
2. Deploy a trivial contract that performs `CALL` to precompile address `0x...0a` with this crafted data and sufficient gas.
3. Broadcast a `TriggerSmartContract` transaction invoking that call.
4. Observe `words[words[3].intValueSafe() / WORD_SIZE]` or the subsequent `Arrays.copyOfRange` in `extractBytes`/`extractBytesArray` throw `ArrayIndexOutOfBoundsException`, uncaught by any surrounding handler in `ValidateMultiSign.execute`, propagating out of the precompile call during TVM execution.

      return false;
    }
