### Title
Self-trade balance overwrite causes silent loss of matched proceeds in `MarketSellAssetActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator` never rejects an order that matches against the same owner's own resting order (no self-trade check exists in `validate()` or `matchOrder()`), and it updates the taker's and maker's account balances through two different code paths that both eventually write to the same `AccountStore` key. When taker and maker are the same address, the final unconditional overwrite of the account capsule at the end of `execute()` discards the credit that was applied mid-loop for the "maker" side of the match, permanently losing the matched proceeds — the same "duplicate vs. stale, sequential same-key update" root cause described in the reported `Ticket._beforeTokenTransfer` bug class, except manifesting here as fund loss rather than duplication.

### Finding Description
In `execute()` the taker's account object is fetched once and kept in memory for the whole call: [1](#0-0) [2](#0-1) 

`matchOrder`/`matchSingleOrder` performs the credit for the taker side directly on this in-memory `takerAccountCapsule`, but the credit for the maker side is done via a helper that independently re-fetches the account **from the store** and immediately persists it: [3](#0-2) 

At the end of `execute()`, the taker's in-memory `accountCapsule` — which does **not** include any maker-side updates applied to that same key during the loop — is written back unconditionally: [4](#0-3) 

There is no check anywhere in `validate()` preventing the taker's `MarketSellAssetContract` from matching one of the taker's own previously placed resting orders — order book matching only checks price, not owner identity: [5](#0-4) [6](#0-5) 

Consequently, if an attacker places a resting sell order and later submits a matching `MarketSellAssetContract` from the same account, the second `addTrxOrToken(makerOrderCapsule, ...)` call reads the pre-transaction account state (since the taker's in-memory changes—fee deduction, sell-token debit, taker-side buy-token credit—have not yet been persisted), credits the maker-side proceeds to that stale copy, and writes it to the store. Immediately afterward, `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` at the end of `execute()` overwrites that record with the taker's in-memory capsule, which never received the maker-side credit. The result is that the token quantity sold to "itself" as maker is debited but never credited back, silently vanishing.

### Impact Explanation
This is a fund-loss bug reachable by any account with a normal signed transaction (no special privilege required): sell-token balance is permanently reduced without the corresponding buy-token credit for the maker leg of a self-match, i.e., a form of permanent freezing/destruction of user funds triggered purely by transaction content. Depending on match sequencing (multiple maker legs, partial fills, `MAX_MATCH_NUM` matches per call), the loss can be repeated within a single transaction across several self-owned resting orders.

### Likelihood Explanation
Likelihood is high: the attacker fully controls both sides of the trade (their own resting order and their own new sell order), requiring no cooperation from any other party, no privileged role, and no additional preconditions beyond `AllowMarketTransaction` being enabled on-chain (a standard, already-active feature flag). Reproducing this only requires placing one order and then a second matching order from the same account.

### Recommendation
- Reject matches where the maker order's owner address equals the taker's owner address in `matchOrder`/`matchSingleOrder`, mirroring the self-transfer guard already present in `TransferActuator` (`Arrays.equals(toAddress, ownerAddress)` check) and `DelegateResourceActuator`/`DelegateResourceProcessor`.
- Alternatively, refactor `addTrxOrToken`/`matchSingleOrder` to operate on a single consistent in-memory `Map<address, AccountCapsule>` (or re-read/re-merge from store before each write) so that maker-side and taker-side updates to the same account key are never silently clobbered by a later unconditional `accountStore.put`.

### Proof of Concept
1. Enable market transactions (`AllowMarketTransaction`) and fund account `A` with `sellTokenID` balance.
2. From `A`, submit `MarketSellAssetContract(sellTokenId=X, sellTokenQuantity=100, buyTokenId=Y, buyTokenQuantity=100)` — this becomes a resting maker order in the `X→Y` order book (no counter order exists yet), per `transferBalanceOrToken`/`createAndSaveOrder`.
3. From the same account `A`, submit a second `MarketSellAssetContract(sellTokenId=Y, sellTokenQuantity=100, buyTokenId=X, buyTokenQuantity=100)`. This is the exact inverse pair price, so `hasMatch`/`matchOrder` will match it against `A`'s own resting order from step 2 (`matchSingleOrder`).
4. Observe that after execution, `A`'s balance of token `X` (which should be credited back to `A` as "maker" proceeds of the trade) is not present: it was applied to a stale copy of `A`'s account and then overwritten by the final `accountStore.put(accountCapsule...)` in `execute()`, resulting in `A` losing the `X` tokens it originally sold in step 2 without ever getting them back, despite the trade nominally "completing" successfully (`ret.setStatus(fee, code.SUCESS)`).

  private void matchOrder(MarketOrderCapsule takerCapsule, MarketPrice takerPrice,
      TransactionResultCapsule ret, AccountCapsule takerAccountCapsule)
      throws ItemNotFoundException, ContractValidateException {

    byte[] makerSellTokenID = buyTokenID;
    byte[] makerBuyTokenID = sellTokenID;
    byte[] makerPair = MarketUtils.createPairKey(makerSellTokenID, makerBuyTokenID);

    // makerPair not exists
    long makerPriceNumber = pairToPriceStore.getPriceNum(makerPair);
    if (makerPriceNumber == 0) {
      return;
    }
    long remainCount = makerPriceNumber;

    // get maker price list
    List<byte[]> priceKeysList = pairPriceToOrderStore
        .getPriceKeysList(MarketUtils.getPairPriceHeadKey(makerSellTokenID, makerBuyTokenID),
            (long) (MAX_MATCH_NUM + 1), makerPriceNumber, true);

    int matchOrderCount = 0;
    // match different price
    while (takerCapsule.getSellTokenQuantityRemain() != 0) {
      // get lowest ordersList
      MarketPrice makerPrice = hasMatch(priceKeysList, takerPrice);
      if (makerPrice == null) {
        return;
      }

      byte[] pairPriceKey = priceKeysList.get(0);

      // if not exists
      MarketOrderIdListCapsule orderIdListCapsule = pairPriceToOrderStore.get(pairPriceKey);

      // match different orders which have the same price
      while (takerCapsule.getSellTokenQuantityRemain() != 0
          && !orderIdListCapsule.isOrderEmpty()) {
        byte[] orderId = orderIdListCapsule.getHead();
        MarketOrderCapsule makerOrderCapsule = orderStore.get(orderId);

        matchSingleOrder(takerCapsule, makerOrderCapsule, ret, takerAccountCapsule);

        // remove order
        if (makerOrderCapsule.getSellTokenQuantityRemain() == 0) {
          // remove from market order list
          orderIdListCapsule.removeOrder(makerOrderCapsule, orderStore,
              pairPriceKey, pairPriceToOrderStore);
        }

        matchOrderCount++;
        if (matchOrderCount > MAX_MATCH_NUM) {
          throw new ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM);
        }
      }

      // the orders of makerPrice have been all consumed
      if (orderIdListCapsule.isOrderEmpty()) {
        pairPriceToOrderStore.delete(pairPriceKey);

        // need to delete marketPair if no more price(priceKeysList is empty after deleting)
        priceKeysList.remove(0);

        // update priceInfo's count
        remainCount = remainCount - 1;
        // if really empty, need to delete token pair from pairToPriceStore
        if (remainCount == 0) {
          pairToPriceStore.delete(makerPair);
          break;
        } else {
          pairToPriceStore.setPriceNum(makerPair, remainCount);
        }
      }
    } // end while
  }

  private MarketOrderCapsule createAndSaveOrder(AccountCapsule accountCapsule,
      MarketSellAssetContract contract) {
    MarketAccountOrderCapsule marketAccountOrderCapsule = marketAccountStore
        .getUnchecked(contract.getOwnerAddress().toByteArray());
    if (marketAccountOrderCapsule == null) {
      marketAccountOrderCapsule = new MarketAccountOrderCapsule(contract.getOwnerAddress());
    }

    // note: here use total_count
    byte[] orderId = MarketUtils
        .calculateOrderId(contract.getOwnerAddress(), sellTokenID, buyTokenID,
            marketAccountOrderCapsule.getTotalCount());
    MarketOrderCapsule orderCapsule = new MarketOrderCapsule(orderId, contract);

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    orderCapsule.setCreateTime(now);

    marketAccountOrderCapsule.addOrders(orderCapsule.getID());
    marketAccountOrderCapsule.setCount(marketAccountOrderCapsule.getCount() + 1);
    marketAccountOrderCapsule.setTotalCount(marketAccountOrderCapsule.getTotalCount() + 1);
    marketAccountStore.put(accountCapsule.createDbKey(), marketAccountOrderCapsule);
    orderStore.put(orderId, orderCapsule);

    return orderCapsule;
  }
