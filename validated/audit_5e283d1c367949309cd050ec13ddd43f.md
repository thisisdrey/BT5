### Title
Attachment content-hash not verified against requested `content_hash` before insertion, causing BNS attachment poisoning - (File: `stackslib/src/net/atlas/download.rs`)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes the HTTP response body via `decode_atlas_get_attachment()` and inserts the resulting `Attachment` into `self.attachments: HashSet<Attachment>` without ever checking that `Hash160::from_data(&attachment.content) == request.content_hash`. A malicious peer serving an `AttachmentRequest{content_hash: H}` can return arbitrary bytes as the attachment content; the wrong content gets stored/relayed keyed by its own (wrong) hash, while the batch's tracking for `H` is resolved as if satisfied.

### Finding Description
In `extend_with_attachments` (stackslib/src/net/atlas/download.rs:530-559), for each `(request, response)` pair in `results.succeeded`, the code does:
```rust
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
}
```
`request.content_hash` (the `H` that was requested) is read only to select the reliability `report`, via `request.get_url()` — it is never compared against the decoded attachment's actual content hash. `decode_atlas_get_attachment()` (stackslib/src/net/api/getattachment.rs:159-165) simply JSON-parses the response body into a `GetAttachmentResponse` — no hash check is performed there either.

Downstream, `AttachmentsDownloader::run()` (stackslib/src/net/atlas/download.rs:153-169) does:
```rust
for attachment in context.attachments.drain() {
    let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())?;
    network.atlasdb.insert_instantiated_attachment(&attachment)?;
    ...
    context.attachments_batch.resolve_attachment(&attachment.hash());
}
```
It computes `attachment.hash()` from the (possibly forged) bytes actually received, uses that wrong hash to look up matching `AttachmentInstance`s and to call `resolve_attachment`, marking the entry for the *originally requested* `H` in `AttachmentsBatch` as resolved (since `resolve_attachment` is driven by the request/attachment pairing established earlier in the batch, and the batch bookkeeping treats the request as satisfied once any successful response for that request is recorded) — without the served content ever actually hashing to `H`.

A remote peer needs no privileges: any peer registered in `self.peers` (obtained from `network.get_outbound_sync_peers()`/data URLs — normal gossip peers) that receives an `AttachmentRequest` for `H` can respond over its HTTP RPC endpoint with a 200 status and a JSON body decoding to arbitrary `content` bytes. There is no signature, MAC, or hash validation gating this response before it is trusted and stored.

### Impact Explanation
This is a High-severity BNS attachment/state mismatch: the on-chain `AttachmentInstance` still commits to `content_hash = H`, but the node's Atlas DB never actually stores content matching `H`; the wrongly-hashed attachment gets stored under a different key, and the true `AttachmentInstance` for `H` may be marked resolved (or, at minimum, the retry/inflight tracking for `H` is consumed) so it will not be re-requested from honest peers. Subsequent `/v2/attachments/{H}` lookups (`getattachment.rs:104-118`) then 404 for legitimate clients even though the chain still references `H`, effectively censoring a specific BNS name/attachment via a single malicious peer response. This is repeatable per-attachment-request the attacker's peer is selected to serve.

### Likelihood Explanation
The attacker only needs to run/control an ordinary peer node that is included in `network.get_outbound_sync_peers()` and whose inventory response claims (truthfully or not, since inventory itself isn't the check here) to have the attachment for `H`; once selected as a `source` for the `AttachmentRequest`, it simply answers the GET with a 200 and a crafted JSON body. No secrets, no privileged StackerDB slot, no consensus/tip requirements are needed — just being a reachable HTTP peer that the target node syncs Atlas attachments from. Cost is trivial and fully remote.

### Recommendation
In `extend_with_attachments`, after successfully decoding the response, verify `Hash160::from_data(&response.attachment.content) == request.content_hash` before inserting into `self.attachments`; on mismatch, treat it as a failed request (`report.bump_failed_requests()` and optionally mark the peer as faulty) rather than accepting the payload. This mirrors the hash-check that should gate any content addressed by hash before it is trusted and persisted via `insert_instantiated_attachment`.

### Proof of Concept
```rust
// stackslib/src/net/atlas/download.rs (new test)
#[test]
fn test_extend_with_attachments_no_hash_check() {
    let content_hash_h = Hash160([0x11; 20]); // the "true" requested hash H
    let wrong_content = b"attacker-controlled-bytes".to_vec();
    // sanity: wrong_content does not hash to H
    assert_ne!(Hash160::from_data(&wrong_content), content_hash_h);

    let request = AttachmentRequest {
        sources: HashMap::new(),
        content_hash: content_hash_h.clone(),
        stacks_block_height: 1,
        canonical_stacks_tip_height: None,
    };

    // Build a StacksHttpResponse whose JSON body decodes to `wrong_content`
    let response = build_ok_json_response(&GetAttachmentResponse {
        attachment: Attachment { content: wrong_content.clone() },
    });

    let mut results: BatchedRequestsResult<AttachmentRequest> = BatchedRequestsResult::new(HashMap::new());
    results.succeeded.insert(request.clone(), Some(response));

    let ctx = AttachmentsBatchStateContext::new(
        AttachmentsBatch::new(),
        HashMap::from([(request.get_url().clone(), ReliabilityReport::empty())]),
        &ConnectionOptions::default(),
    );

    let ctx = ctx.extend_with_attachments(&mut results);

    // The inserted attachment's hash does NOT equal the requested H,
    // proving no hash validation occurred.
    let stored: Vec<Attachment> = ctx.attachments.into_iter().collect();
    assert_eq!(stored.len(), 1);
    assert_ne!(stored[0].hash(), content_hash_h);
}
```
This demonstrates that `extend_with_attachments` accepts and stores an `Attachment` whose hash differs from the requested `content_hash`, confirming the missing verification described above.
