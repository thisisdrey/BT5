### Title
Consensus-critical energy-limit arithmetic uses `BigInteger.longValueExact()`, which reverts with `ArithmeticException` on values that must not fail, breaking TVM energy accounting when hardened resource calculation is enabled - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`, `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java`)

### Summary
The external report describes UniswapV3's `FullMath.sol` being migrated to Solidity 0.8 without wrapping the code in `unchecked{}`, so operations that previously relied on implicit wraparound now revert on legitimate inputs, breaking the calling contract. The java-tron codebase contains an analogous migration pattern: legacy `long`/`double` resource-accounting math (bandwidth/energy limit calculations, VI-reward math) is being replaced by a "hardened" path using `BigInteger` arithmetic terminated with `.longValueExact()` or `LongMath`-style exact operations, gated by `allowHardenResourceCalculation()` / `VMConfig.allowHardenResourceCalculation()`. Unlike the old code (which silently truncated/overflowed via `long` or `double` casts and always returned a value), the new path throws `ArithmeticException` whenever the computed value cannot be represented exactly as a `long` — a scenario the legacy code never treated as fatal.

Just as `FullMath.sol`'s migration to Solidity 0.8 turned previously-tolerated overflow/wraparound into a revert, this migration turns previously-tolerated `long`/`double` truncation into an `ArithmeticException` whenever the exact `BigInteger` result cannot be represented as a `long`. Because `.longValueExact()` (and `divideCeilExact`, which itself calls `StrictMathWrapper.addExact`) are strict-by-construction, any combination of frozen balance, `totalEnergyLimit`, and `totalEnergyWeight` (or usage/precision/windowSize) that produces an intermediate/final value exceeding `Long.MAX_VALUE`, or a non-integral `divideCeilExact` overflow when adding 1, causes an unconditional exception instead of the previous tolerant behavior.

### Impact Explanation
If this hardened path is enabled network-wide (controlled by the `allowHardenResourceCalculation` dynamic property, i.e. once activated by proposal it applies uniformly), any account or contract interaction whose accounting inputs push these calculations outside representable `long` range will throw `ArithmeticException` during transaction execution/energy consumption — a path reachable by any ordinary contract call. If any node in the network has not synchronized the same dynamic-property state, or if the exception is not uniformly caught across all call sites (validate vs. execute vs. background maintenance calls like `updateAdaptiveTotalEnergyLimit()`/`updateTotalEnergyAverageUsage()` which are called during block-cycle maintenance in `Manager`, not inside a try/catch around actuator execution), this can cause transaction processing to fail unexpectedly for legitimate transactions or, in the maintenance-cycle methods, propagate an uncaught exception during block application, potentially halting block processing for affected nodes. This matches the "breaks the contract when it shouldn't" class from the original report and can escalate to a node processing/consensus disruption if triggered inside the periodic maintenance cycle rather than inside a caught actuator execution.

### Likelihood Explanation
Reaching the vulnerable arithmetic requires only ordinary use of the freeze/energy/bandwidth system (any account freezing TRX for energy/bandwidth and consuming energy via a contract call), which is available to any unprivileged user. However, triggering an actual overflow requires extreme values of `totalEnergyWeight`, `totalEnergyLimit`, or `frozenBalance` that are governed by network-wide totals rather than a single attacker's balance, and the `hardenResourceCalculation` feature itself is a governance-gated flag that must be enabled before this code path is exercised at all. I was not able to fully verify from the available index whether `updateAdaptiveTotalEnergyLimit()`/`updateTotalEnergyAverageUsage()` (which call the hardened `scaleByRate`/`increase` helpers) are invoked from a point in `Manager`'s block-application flow that lacks an exception guard — this would need to be confirmed by a Devin session with full file access, since some call-site catch blocks may already be present but were not fully visible in the indexed excerpts.

### Recommendation
- For all "hardened" replacements of legacy resource/reward arithmetic (`RepositoryImpl`, `ResourceProcessor`, `EnergyProcessor`, `BandwidthProcessor`), ensure `.longValueExact()`/`divideCeilExact` failures are always caught at every call site — including background maintenance routines invoked during block application — and either fall back to a safe deterministic value or reject the specific transaction rather than allowing the exception to propagate into block application.
- Audit `Manager`'s per-block/per-maintenance-cycle invocations of `updateAdaptiveTotalEnergyLimit`, `updateTotalEnergyAverageUsage`, and similar calls to confirm they are wrapped in exception handling equivalent to how `ExchangeInjectActuator`/`ExchangeWithdrawActuator` already catch `ArithmeticException` and convert it into a `ContractExeException`.
- Consider bounding intermediate values (e.g., via saturation or explicit range checks before the exact conversion) rather than relying solely on exceptions, mirroring the recommendation to use unchecked/wrapped arithmetic only where wraparound is truly safe, and exact/checked arithmetic only where failure is properly handled without affecting consensus-critical block application.

  private long increase(long lastUsage, long usage, long lastTime, long now, long windowSize) {
    long averageLastUsage;
    long averageUsage;
    if (hardenResourceCalculation()) {
      BigInteger biPrecision = BigInteger.valueOf(precision);
      BigInteger biWindowSize = BigInteger.valueOf(windowSize);
      averageLastUsage = divideCeilExact(
          BigInteger.valueOf(lastUsage).multiply(biPrecision), biWindowSize);
      averageUsage = divideCeilExact(
          BigInteger.valueOf(usage).multiply(biPrecision), biWindowSize);
    } else {
      averageLastUsage = divideCeil(lastUsage * precision, windowSize);
      averageUsage = divideCeil(usage * precision, windowSize);
    }

    if (lastTime != now) {
      assert now > lastTime;
      if (lastTime + windowSize > now) {
        long delta = now - lastTime;
        double decay = (windowSize - delta) / (double) windowSize;
        averageLastUsage = round(averageLastUsage * decay, VMConfig.disableJavaLangMath());
      } else {
        averageLastUsage = 0;
      }
    }
    averageLastUsage += averageUsage;
    return getUsage(averageLastUsage, windowSize);
  }

  private long getNewWindowSize(long lastUsage, long lastWindowSize, long usage,
      long windowSize, long newUsage) {
    if (hardenCalculation()) {
      BigInteger bi = BigInteger.valueOf(lastUsage).multiply(BigInteger.valueOf(lastWindowSize))
          .add(BigInteger.valueOf(usage).multiply(BigInteger.valueOf(windowSize)));
      return bi.divide(BigInteger.valueOf(newUsage)).longValueExact();
    }
    return (lastUsage * lastWindowSize + usage * windowSize) / newUsage;
  }
