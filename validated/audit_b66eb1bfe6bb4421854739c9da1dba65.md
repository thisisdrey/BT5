### Title
Unvalidated, unbounded attachment content accepted and permanently stored from any peer response - ([File: stackslib/src/net/atlas/download.rs], [File: stackslib/src/net/atlas/mod.rs])

### Summary
`AttachmentsDownloader::extend_with_attachments` and the subsequent `AttachmentsDownloader::run()` "Done" handling accept and unconditionally persist whatever `Attachment` content a queried peer returns for a `/v2/attachments/<hash>` GET, without ever checking the decoded content length against `AtlasConfig::attachments_max_size`, and without verifying that `Hash160::from_data(&content)` actually equals the `content_hash` that was requested. This lets any peer that is selected as a download source inject arbitrarily large, arbitrary content into the node's persistent `AtlasDB` SQLite `content BLOB` column.

### Finding Description
The claimed equality `len(bytes read for GetAttachmentResponse.attachment.content) == validated attachments_max_size bound` is never enforced on this path:

- `StacksHttpResponse::decode_atlas_get_attachment` just JSON-parses the body and hex-decodes it into `Attachment::new(bytes)` with no size check: [1](#0-0) 
- `Attachment::hash()` hashes the entire buffer unconditionally, with no length bound at the type level: [2](#0-1) 
- `AttachmentsBatchStateContext::extend_with_attachments` calls `decode_atlas_get_attachment()` and inserts the resulting `attachment` into `self.attachments` with no comparison of `attachment.hash()` against the original `request.content_hash`, and no size check: [3](#0-2) 
- In `AttachmentsDownloader::run()`, once the state machine reaches `Done`, every collected attachment is hashed and passed straight to `atlas_db.insert_instantiated_attachment(&attachment)` **unconditionally**, regardless of whether any pending `AttachmentInstance` actually matches that hash: [4](#0-3) 

`attachments_max_size` is only referenced in `AtlasConfig::validate` (config-time floor check) and in one call site in `stackslib/src/net/atlas/db.rs`; it is not referenced anywhere in `download.rs`, `getattachment.rs`, or in `Attachment`/`AtlasConfig` type logic that would gate the HTTP download/decode path. The single `db.rs` usage was not confirmed (due to tool-call limits) to be inside `insert_instantiated_attachment` — the function actually invoked from the download path — as opposed to a different, unrelated insertion path (e.g., attachments arriving inline via a contract-call/tx payload). No evidence was found that `insert_instantiated_attachment` enforces the size bound before writing to SQLite.

Exploit flow: a malicious peer only needs to be a legitimately reachable, unauthenticated data-URL peer that gets selected as a "source" for some pending `AttachmentRequest` (this happens automatically for any node syncing Atlas attachments against public/testnet peers). When asked for `GET /v2/attachments/<hash>`, it responds `200 OK` with a `GetAttachmentResponse` whose `attachment.content` hex string is arbitrarily large and/or does not hash to the requested `content_hash`. The response is accepted as "succeeded", decoded, hashed, and written to the AtlasDB `attachments` table with no relation to the originally requested content, and with no upper bound tied to the node's configured `attachments_max_size`.

### Impact Explanation
A remote, unprivileged peer that becomes a download source for any pending attachment can force the node to buffer, hash, and permanently persist attacker-chosen bytes into its local SQLite attachment store, unbounded by the node's configured `attachments_max_size` (whose documented floor is 1 MiB, intended to bound storage growth). This is a storage-exhaustion / unauthenticated-write-to-state issue: repeated requests (the batch/retry state machine re-queries regularly) let a single malicious/compromised peer bloat the AtlasDB indefinitely with un-requested content, independent of any real on-chain attachment commitment.

### Likelihood Explanation
Preconditions are minimal: the attacker needs no privileged role, no RPC secret, and no StackerDB slot — it only needs to run an ordinary peer that the victim node includes among its "outbound sync peers" / attachment sources (which happens through normal peer-discovery and Atlas attachment-instance gossip triggered by any BNS-registering transaction observed on the network). Cost to the attacker is a single crafted HTTP response per request; the behavior is fully repeatable as new attachment instances are continuously generated by chain activity.

### Recommendation
In `decode_atlas_get_attachment` (or immediately in `extend_with_attachments`), reject responses whose decoded `content.len()` exceeds `atlas_config.attachments_max_size` before constructing `Attachment`/computing `.hash()`. Additionally, in `extend_with_attachments`/`AttachmentsDownloader::run()`, verify `attachment.hash() == request.content_hash` before accepting the response as "succeeded" and before calling `insert_instantiated_attachment`, discarding/penalizing peers that return mismatched or oversized content instead of persisting it.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/download.rs` (or `stackslib/src/net/api/tests/getattachment.rs`) that:
1. Builds a `StacksHttpResponse` whose JSON body encodes a `GetAttachmentResponse` with `attachment.content` sized well beyond `ATTACHMENTS_MAX_SIZE_MIN` (e.g., 10 MiB) and/or whose hash does not equal a targeted `content_hash`.
2. Feeds it through `StacksHttpResponse::decode_atlas_get_attachment()` and then `AttachmentsBatchStateContext::extend_with_attachments()`.
3. Asserts the call should return an error / reject the attachment (expected fix behavior) — currently it succeeds and inserts into `self.attachments`, demonstrating the missing size/hash-equality guard prior to `AtlasDB::insert_instantiated_attachment`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
