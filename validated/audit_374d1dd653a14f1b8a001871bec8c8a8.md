### Title
Missing `contract-caller == tx-sender` check in `collateral-remove` allows cross-user collateral theft when a shared intermediary contract is used - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`collateral-remove` in the market contract resolves the acting user's identity as `contract-caller` without validating that `contract-caller` equals `tx-sender`, unlike every other position-mutating entry point in the same contract (`collateral-add`, `supply-collateral-add`, `repay`). This is the same root cause as the referenced `FeeWrapper` finding: when calls pass through any intermediary contract, the market can no longer distinguish between the individual end users behind that intermediary, because it only tracks positions by the immediate caller's principal.

### Finding Description
`collateral-add` explicitly enforces direct-caller-only semantics: [1](#0-0) 

The same pattern is enforced in `supply-collateral-add`: [2](#0-1) 

and in `repay`: [3](#0-2) 

However, `collateral-remove` binds `account` to `contract-caller` and immediately proceeds to resolve/mutate that account's position, **without** asserting `(is-eq contract-caller tx-sender)`: [4](#0-3) 

The rest of the function (health checks, `.v0-market-vault collateral-remove` call, receiver resolution) operates purely on this unchecked `account`: [5](#0-4) 

The identical gap exists in the `local-testing` mirror of this contract: [6](#0-5) 

Because `market-vault.collateral-remove` (and `resolve`) key all state purely off whatever principal is passed as `account` (i.e., whatever `contract-caller` happens to be at the point market.clar is invoked): [7](#0-6) 

this is exactly the msg.sender/`contract-caller` confusion described in the H-09 report: `RubiconRouter`'s `msg.sender` became `FeeWrapper`'s address, so all state ended up attributed to the wrapper rather than the individual end user. Here, if any intermediary/aggregator contract (deployed by an attacker or a third party, and then adopted by other users who deposit collateral "through" it, expecting it to forward `collateral-add`/`collateral-remove` calls on their behalf) is used by more than one user, `market.clar` attributes **all** of those users' collateral to a single shared position — the position keyed by the intermediary contract's own principal — because `contract-caller` inside `market.clar` is always the immediate calling contract, not the original end user (`tx-sender`).

Once multiple victims' collateral is pooled under that single shared "account", any user of the same intermediary (attacker included) can call the intermediary again to trigger `collateral-remove`, withdrawing collateral that in reality belongs to other victims, and can direct it to an attacker-controlled `receiver`, since `receiver` is a free-form optional principal: [8](#0-7) 

There is no accounting inside `market.clar`/`market-vault.clar` to prevent the shared-identity holder from withdrawing more than their individual fair share — the pooled position simply reflects an aggregate balance with no sub-user bookkeeping.

### Impact Explanation
This lands on **Critical — direct theft of user funds at rest**. Any collateral routed into the market through a shared intermediary contract (the missing check makes `collateral-remove` reachable by any contract acting on behalf of multiple depositors) can be withdrawn by any other user of that same intermediary to an address of their choosing, exactly mirroring the confirmed H-09 impact in the source report (attacker steals victim's assets that were deposited via a shared wrapper).

### Likelihood Explanation
Likelihood is moderate-to-high: it requires an intermediary contract (a "wrapper"/aggregator built on top of Zest, which the protocol's own documentation encourages via `collateral-add`/`collateral-remove`/`supply-collateral-add` being public entry points intended for composability) to be used by multiple depositors. The bug is a straightforward code-consistency gap — three of four analogous entry points already enforce `contract-caller == tx-sender`; `collateral-remove` alone omits it, strongly suggesting an unintentional omission rather than deliberate design.

### Recommendation
Add `(asserts! (is-eq contract-caller tx-sender) ERR-AUTHORIZATION)` to `collateral-remove` in `mainnet/contracts/market/v0-4-market.clar` (and the `local-testing` mirror), consistent with `collateral-add`, `supply-collateral-add`, and `repay`, so that only the direct originating signer can remove their own collateral, closing the shared-identity/impersonation vector for any intermediary contract.

### Proof of Concept
1. Deploy an intermediary contract `Router` that, on behalf of any caller, forwards `(contract-call? .v0-market collateral-add ft amount price-feeds)` and `(contract-call? .v0-market collateral-remove ft amount receiver price-feeds)`.
2. Victim calls `Router` to deposit collateral. Inside `v0-4-market.clar`, `contract-caller` = `Router`'s principal (not the victim), so the victim's collateral is recorded under the `Router` principal's position via `.v0-market-vault collateral-add`.
3. A second user (attacker) also uses `Router` to deposit a small amount of collateral — this merges the attacker into the same pooled `Router`-keyed position.
4. Attacker calls `Router`'s `collateral-remove` forwarding function directly, specifying `receiver = attacker`. Because `collateral-remove` never checks `contract-caller == tx-sender`, and market-vault's balance for the `Router` account contains the victim's collateral, `.v0-market-vault collateral-remove` succeeds and sends the (victim-funded) collateral to the attacker.
5. Victim's collateral is now gone; the position resolves to the shared `Router` identity, with no query path distinguishing which underlying user actually owns which portion.
