Audit Report

## Title
Unchecked `debug_assert!`-guarded fund transfers in `claim_bounty`/`claim_child_bounty` allow bounty state finalization and success events without actual payout, permanently locking funds - ([File: substrate/frame/bounties/src/lib.rs], [File: substrate/frame/child-bounties/src/lib.rs])

## Summary
Both `pallet_bounties::Pallet::claim_bounty` and `pallet_child_bounties::Pallet::claim_child_bounty` perform `T::Currency::transfer(...)` calls to pay curator fees and beneficiary payouts, guarding only with `debug_assert!(res.is_ok())`, which is compiled out entirely in release/production builds. If a transfer fails (e.g., due to a `Lock`/`Freeze` placed on the deterministically-derived bounty account by an unrelated permissionless call such as `pallet_vesting::vested_transfer`), the extrinsic proceeds to unconditionally delete the bounty/child-bounty storage record and emit `BountyClaimed`/`Claimed` events with the full intended payout, despite no funds actually moving.

## Finding Description
In `substrate/frame/bounties/src/lib.rs`, `claim_bounty` computes `final_fee` and `payout` from the bounty account's `free_balance`, then calls: [1](#0-0) 
Both transfers are checked only via `debug_assert!`, which is a no-op when `debug-assertions` are disabled (the default for release/production runtime builds). Regardless of transfer outcome, `*maybe_bounty = None` is set, `BountyDescriptions` is removed, and `Event::BountyClaimed { payout, beneficiary }` is emitted with the full computed payout. [2](#0-1) 

The identical pattern exists in `substrate/frame/child-bounties/src/lib.rs`'s `claim_child_bounty`: [3](#0-2) 

`bounty_account_id`/`child_bounty_account_id` are pure functions of a public `PalletId` and public bounty indices, so any unprivileged account can precompute the exact address off-chain. `T::Currency::transfer(..., AllowDeath)` only relaxes the existential-deposit requirement; it does not bypass `Lock`/`Freeze` restrictions from providers such as `pallet_vesting`. An attacker can call the standard, permissionless `pallet_vesting::vested_transfer` targeting the derived bounty account, attaching a long-duration vesting lock that overlaps the fee/payout amount. When `claim_bounty`/`claim_child_bounty` later executes, `ensure_can_withdraw` rejects the withdrawal and `T::Currency::transfer` returns `Err`, which the `debug_assert!` silently swallows in production, and the function proceeds to delete state and emit a false success event anyway.

## Impact Explanation
This breaks the invariant that "payout state must only advance after ... settlement succeed[s] atomically." The bounty/child-bounty account funds become permanently orphaned — the storage record that tracked them (`Bounties`/`ChildBounties`) is deleted, so the pallet can never again reference or reclaim that account's balance through its normal flow, and no other on-chain path exists to recover it (permanent user-fund lock). Additionally, a `BountyClaimed`/`Claimed` event asserting a successful payout of the exact `payout` amount is emitted even though no funds moved, misleading downstream indexers/accounting (false settlement attestation). This is an unprivileged, permissionless attack requiring no governance, validator, or relayer role.

## Likelihood Explanation
Moderate-to-high: the derived account address is trivially computable off-chain from public `PalletId` + bounty index; `pallet_vesting::vested_transfer` is a standard public extrinsic available to any signed account with minimal balance; the attack requires no privileged capability, no race condition beyond sending the lock transaction before the claim, and is fully repeatable against any bounty/child-bounty instance.

## Recommendation
Replace the `debug_assert!(res.is_ok())` checks in both `claim_bounty` (`substrate/frame/bounties/src/lib.rs`) and `claim_child_bounty` (`substrate/frame/child-bounties/src/lib.rs`) with real error propagation (`?`/`ensure!`) so a failed fee/payout transfer aborts the extrinsic before storage removal and event emission occur. Consider verifying the actual transferred amount against the intended amount prior to advancing state and emitting events.

## Proof of Concept
1. Attacker computes `bounty_account_id(bounty_id)` (or `child_bounty_account_id(parent_id, child_id)`) off-chain from the public `PalletId` and index.
2. Before the bounty reaches claim time, attacker calls `pallet_vesting::vested_transfer` sending funds with a long vesting schedule to that derived account, attaching a `Lock`/`Freeze` exceeding the withdrawable (unlocked) balance needed for fee/payout.
3. After the payout delay elapses, anyone calls `claim_bounty(bounty_id)` / `claim_child_bounty(parent_id, child_id)`.
4. `T::Currency::transfer(&bounty_account, &curator/beneficiary, amount, AllowDeath)` fails with a liquidity-restriction error due to the lock; `debug_assert!(res.is_ok())` is compiled out in release builds and does not abort execution.
5. `*maybe_bounty = None` (or `*maybe_child_bounty = None`) executes, descriptions/counts are updated, and `Event::BountyClaimed`/`Event::Claimed` is emitted with the full intended `payout`.
6. The actual funds remain stuck in the now-untracked derived account; a Rust integration test can simulate this by configuring a mock `Currency` (or using `pallet_vesting` in a test runtime) to lock the bounty account's balance before invoking `claim_bounty`, then asserting the bounty record is removed, the event is emitted, yet the curator/beneficiary balance is unchanged and the bounty account retains the locked balance.
