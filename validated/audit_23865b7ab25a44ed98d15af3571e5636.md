### Title
`remove_liquidity`'s strict non-zero output check permanently strands a liquidity provider's residual LP tokens - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`Pallet::do_remove_liquidity` computes the underlying-asset amounts owed for a given LP-token burn via floor-division (`mul_div`), then requires both outputs to be strictly non-zero before it will proceed. Exactly like the Whirlpool `updateFeesAndRewards` bug — where an operation that must run as part of "fully exit a position" reverts precisely when the remaining state reaches the value that triggers the exit — a liquidity provider's final, small LP-token remainder rounds down to `0` underlying tokens and the extrinsic then unconditionally reverts, permanently blocking that LP balance from ever being redeemed at the current pool size.

### Finding Description
`do_remove_liquidity` (`substrate/frame/asset-conversion/src/lib.rs:895-966`) computes: [1](#0-0) 

```
let total_supply = T::PoolAssets::total_issuance(pool.lp_token.clone());
let withdrawal_fee_amount = T::LiquidityWithdrawalFee::get() * lp_token_burn;
let lp_redeem_amount = lp_token_burn.saturating_sub(withdrawal_fee_amount);

let amount1 = Self::mul_div(&lp_redeem_amount, &reserve1, &total_supply)?;
let amount2 = Self::mul_div(&lp_redeem_amount, &reserve2, &total_supply)?;

ensure!(
    !amount1.is_zero() && amount1 >= amount1_min_receive,
    Error::<T>::AssetOneWithdrawalDidNotMeetMinimum
);
ensure!(
    !amount2.is_zero() && amount2 >= amount2_min_receive,
    Error::<T>::AssetTwoWithdrawalDidNotMeetMinimum
);
```

`mul_div` performs integer (floor) division, so any `lp_token_burn` whose corresponding share of `reserve1`/`reserve2` is less than one indivisible unit rounds down to `0`. The `ensure!` guards then unconditionally reject the call with `AssetOneWithdrawalDidNotMeetMinimum` / `AssetTwoWithdrawalDidNotMeetMinimum` for *any* `lp_token_burn` value that produces that zero output — there is no fallback branch that lets a caller redeem "dust" LP tokens for nothing, nor any mechanism (analogous to Whirlpool's `decreaseLiquidity` reordering fix) to route the final withdrawal through a different, always-succeeding code path.

This is structurally identical to the reported class of bug: a public-entrypoint operation intended to let a user fully exit their position is guarded by a strict non-zero precondition that the exit itself can drive to zero, so the very last step of a full withdrawal always reverts — leaving a residual balance permanently unreachable through the normal call, exactly as the Whirlpool position's last unit of liquidity became permanently unwithdrawable through `updateFeesAndRewards`.

`do_add_liquidity` (`substrate/frame/asset-conversion/src/lib.rs:800-892`) similarly locks a fixed `T::MintMinLiquidity::get()` LP amount into the pool account forever, which guarantees `total_supply` never returns to zero and thus that the "last LP holder" scenario — where a provider tries to redeem essentially all remaining liquidity — routinely produces sub-unit `lp_redeem_amount * reserve / total_supply` results for any account holding a small residual balance relative to the pool.

### Impact Explanation
Any liquidity provider whose remaining LP-token balance represents less than one indivisible unit of `asset1` or `asset2` in the pool can never redeem that balance while the pool state stays the same — the transaction will always fail via `AssetOneWithdrawalDidNotMeetMinimum`/`AssetTwoWithdrawalDidNotMeetMinimum`. This is a permanent, protocol-level fund lock for the affected balance: the user retains a non-zero LP-token balance representing real value that is functionally unspendable, matching the "permanent user-fund lock" impact category. Because pools can have arbitrarily large reserves relative to a late/small LP, this can affect any provider adding a small amount to a deep pool and later trying to fully exit.

### Likelihood Explanation
No privileged actor, governance, relayer, or malicious peer is required — an ordinary, unprivileged liquidity provider triggers this simply by calling the public `remove_liquidity` extrinsic (or the `MutateLiquidity::remove_liquidity` trait method, including via the `AssetConversion` revive precompile at `substrate/frame/asset-conversion/precompiles/src/lib.rs:462-493`) with an `lp_token_burn` value whose calculated share rounds to zero. This condition arises naturally for small depositors in large pools, or for the tail end of any withdrawal sequence, making it easily and repeatably triggerable without any adversarial setup.

### Recommendation
Mirror the Whirlpool fix pattern (avoid calling into a state-dependent operation that can't handle the terminal state): when `amount1`/`amount2` compute to zero for a positive `lp_token_burn`, do not unconditionally reject the call. Instead, either (a) allow a best-effort/rounding-favorable path that lets users burn small remainders without transferring dust (explicitly forfeiting negligible value with clear documentation), or (b) compute withdrawal amounts using rounding that favors the withdrawing user for the final redemption, or (c) provide a dedicated "close position"/sweep extrinsic that lets an LP redeem their entire remaining balance even when it maps to sub-unit underlying amounts, by socializing the rounding loss instead of reverting.

### Proof of Concept
1. Create a pool with large reserves, e.g. `reserve1 = reserve2 = 1_000_000_000`, `total_supply = 1_000_000_000` LP tokens (minus `MintMinLiquidity` locked forever).
2. A liquidity provider ends up holding a small LP balance, e.g. `lp_token_burn = 1` (after fees/rounding from a prior partial withdrawal).
3. Call `remove_liquidity` (or `MutateLiquidity::remove_liquidity`) with `lp_token_burn = 1`:
   - `lp_redeem_amount = 1 - withdrawal_fee_amount` (fee often rounds to 0 for such small amounts, so `lp_redeem_amount = 1`).
   - `amount1 = mul_div(1, 1_000_000_000, 1_000_000_000) = 1` — but if `reserve1 < total_supply` even slightly, `amount1` floors to `0`.
4. The call reverts with `Error::<T>::AssetOneWithdrawalDidNotMeetMinimum` (or `AssetTwoWithdrawalDidNotMeetMinimum`), per [2](#0-1) .
5. Because the LP's balance cannot be increased through any means other than adding more liquidity (which is not something the user wants to do just to exit), and the pool state that makes the division non-zero may never materialize on its own, that LP-token balance — and the value it represents — is permanently stranded.

Note: I was not able to fully verify `mul_div`'s exact rounding semantics (only its call sites, not its body, were retrieved), so I cannot cite the precise rounding direction from source in this pass; this should be double-checked in a follow-up session, but the guard logic shown above independently confirms that any zero-rounding output unconditionally reverts, which is the core of the analog finding.
