### Title
Unbounded per-account token list allows an attacker to force-fill a victim's `depositTokensOfAccount`/`debtTokensOfAccount` set via dust transfers, permanently (until relieved) blocking the victim from receiving any new collateral type - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
Analogous to the libp2p protocol-book interning map (unbounded, attacker-insertable entries), the `Pool` tracks every deposit/debt token an account holds in `MappedEnumerableSet` sets (`depositTokensOfAccount`, `debtTokensOfAccount`). Any `DepositToken.transfer`/`transferFrom` whose recipient has a zero balance unconditionally calls `Pool.addToDepositTokensOfAccount(recipient_)` [1](#0-0) , which pushes the token address into the victim's list. The only bound is `MAX_TOKENS_PER_USER = 30` [2](#0-1) , and once the combined count reaches it, every subsequent `addTo*` call reverts with `UserReachedMaxTokens`, reverting the whole transfer/mint.

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` push into `MappedEnumerableSet` and revert once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [3](#0-2) .
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` for any first-time receipt, with no opt-in from the recipient and no minimum amount [4](#0-3) .
- `DepositToken._mint` (from `deposit()`) does the same, so a victim can also be force-added entries via `deposit(amount, onBehalfOf_ = victim)` [5](#0-4) .
- Like the protobook map, entries are never GC'd on the victim's behalf: an entry is removed only when the victim's own balance of that token returns to zero (`removeFromDepositTokensOfAccount` on full transfer/burn) [6](#0-5) .

Attack: the attacker deposits once into each of the pool's deposit tokens (or `deposit`s dust `onBehalfOf` the victim), then calls `transfer(victim, 1)` for each distinct deposit token until the victim's combined list hits 30 entries.

### Impact Explanation
Once the list is full:
- The victim cannot `deposit` into any deposit token they don't already hold (`_mint` → `addToDepositTokensOfAccount` → revert).
- Nobody can `transfer`/`transferFrom`/`seize` a new deposit-token type to the victim; `seize` reverts too, so liquidation proceeds that would credit the victim (or flows through `Operator.execute` minting new collateral types) revert.
- The victim's position cannot be improved with new collateral types; if the victim's existing tokens don't include the pool's liquid collateral, their collateral is effectively frozen against top-ups. The freeze persists until the victim fully empties a slot, so it is temporary freezing of funds/liveness rather than permanent theft — but recovery requires the victim to know to fully withdraw one token type, and each new attack dust re-fill costs the attacker essentially nothing (1 wei dusts), so the attacker can keep the victim pinned indefinitely by monitoring and re-topping slots.

### Likelihood Explanation
Requires only unprivileged calls: `DepositToken.deposit`/`transfer`. Cost is the gas plus a dust balance in each of up to 30 registered deposit tokens; on pools with many registered deposit tokens (base/optimism deployments list multiple msd tokens) this is cheap relative to the damage. No privileged role, oracle manipulation, or trusted-remote assumption needed. The only prerequisite is that the pool exposes enough distinct deposit (or attacker-forceable) tokens to reach 30, or fewer if the victim already holds debt tokens.

### Recommendation
Decouple "can receive" from the account-list cap. Options:
- Do not revert the whole transfer/mint when the cap is hit; skip the list insertion and compute `depositOf`/`debtOf` iterably only for listed tokens, or
- Only auto-insert on `deposit`/`issue` initiated for the account (not on bare `transfer`), so dust transfers cannot inflate the list, or
- Replace the enumerable-per-account structure with a per-token balance check plus an off-chain index, matching the report's suggestion that interning/dedup bookkeeping isn't worth an unbounded attacker-writable map.

### Proof of Concept
Hardhat (fork or local) sketch, per existing test harness in `test/Pool.test.ts`:

```ts
// pool has registered deposit tokens: msdA, msdB, ..., msdN
const victim = bob.address
// 1) attacker seeds itself with dust in each deposit token
for (const d of depositTokens) {
  await underlying(d).approve(d.address, DUST)
  await d.deposit(DUST, attacker.address)
}
// 2) fill victim's depositTokensOfAccount until combined length == 30
for (const d of depositTokens) {
  if ((await pool.getDepositTokensOfAccount(victim)).length +
      (await pool.getDebtTokensOfAccount(victim)).length < 30) {
    await d.transfer(victim, 1) // adds entry for victim
  }
}
// 3) victim can no longer deposit into a token type not already held
await underlying(freshToken).connect(bob).approve(freshToken.address, amount)
await expect(freshToken.connect(bob).deposit(amount, victim))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')
// 4) anyone transferring a new token type to victim also reverts
await expect(otherToken.transfer(victim, 1))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')
// 5) attacker can re-pin freed slots: whenever victim empties a token,
//    attacker transfers 1 wei of a not-yet-held token to refill the slot
```

        address sender_,
        address recipient_,
        uint256 amount_
    ) private updateRewardsBeforeTransfer(sender_, recipient_) {
        if (sender_ == address(0)) revert TransferFromTheZeroAddress();
        if (recipient_ == address(0)) revert TransferToTheZeroAddress();

        uint256 _senderBalanceBefore = balanceOf[sender_];
        if (_senderBalanceBefore < amount_) revert TransferAmountExceedsBalance();
        uint256 _recipientBalanceBefore = balanceOf[recipient_];

        unchecked {
            balanceOf[sender_] = _senderBalanceBefore - amount_;
            balanceOf[recipient_] += amount_;
        }

        emit Transfer(sender_, recipient_, amount_);

        // Add this token to the deposit tokens list if the recipient is receiving it for the 1st time
        if (_recipientBalanceBefore == 0 && amount_ > 0) {
            pool.addToDepositTokensOfAccount(recipient_);
        }

        // Remove this token from the deposit tokens list if the sender's balance goes to zero
        if (amount_ > 0 && balanceOf[sender_] == 0) {
            pool.removeFromDepositTokensOfAccount(sender_);
        }
    }
