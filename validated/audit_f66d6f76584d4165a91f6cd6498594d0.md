### Title
HTTP request-smuggling primitive: Stacks node's request parser ignores `Transfer-Encoding` and frames bodies solely by `Content-Length` - (File: stackslib/src/net/http/request.rs)

### Summary
The reported CVE-2025-55315 is a CWE-444 "inconsistent interpretation of HTTP requests" (request/response smuggling) bug in Kestrel, caused by disagreement between two HTTP parsers about how a request body is framed (`Content-Length` vs `Transfer-Encoding: chunked`). The Stacks node's own HTTP-request preamble parser exhibits the identical class of framing-equality violation: it silently drops `Transfer-Encoding` semantics for **requests**, and always frames the request body by `Content-Length` alone.

### Finding Description
`HttpRequestPreamble::consensus_deserialize` in [1](#0-0)  iterates request headers and specifically recognizes only `host`, `content-type`, `content-length`, `connection`, and `set-cookie`. Any `Transfer-Encoding` header supplied by the client falls into the generic `else` branch and is stored as an ordinary opaque header string — it has **zero effect** on how the body is delimited.

Compare this to the **response** parser, `HttpResponsePreamble::consensus_deserialize`, which explicitly tracks `chunked_encoding` and rejects a message that carries both `Content-Length` and `Transfer-Encoding: chunked` as invalid: [2](#0-1) . No equivalent guard exists on the request side.

Framing for requests is then driven purely by `Content-Length` in `ProtocolFamily::payload_len` for `StacksHttp`: [3](#0-2) , and consumed accordingly in `read_payload`, which slices exactly `content_length` bytes off the stream for a `Request`, regardless of any `Transfer-Encoding` header present: [4](#0-3) . Chunked decoding logic (`HttpChunkedTransferReaderState`, `stream_payload`) exists in this codebase but is only reachable for **unknown-length messages**, i.e., HTTP responses, never for requests: [5](#0-4) .

This breaks the equality that must hold between two cooperating HTTP parsers in a chain: "the byte offset where request N ends and request N+1 begins must be identical for every parser in the path." If this Stacks node sits behind any RFC-7230-compliant intermediary (reverse proxy, load balancer, or another Stacks node acting as HTTP relay) that gives `Transfer-Encoding` precedence over `Content-Length` when both are present — which is the mandated behavior per RFC 7230 §3.3.3 and is exactly the compliant posture that made Kestrel's *deviation* from it a bypass — the intermediary will treat the chunked body as the true message boundary, while this node will treat only the `Content-Length` prefix as the message and interpret the remaining "chunked" bytes as the start of an entirely new, attacker-smuggled request on the same persistent connection.

### Impact Explanation
This is a classic CL.TE / TE.CL desynchronization primitive (CWE-444), matching the impact class explicitly called out in the rules: "request smuggling or auth bypass." A node operator who fronts the RPC/API surface with a reverse proxy (a common Stacks node deployment pattern for rate limiting or IP allow-listing of write endpoints such as the StackerDB chunk-upload or transaction-submission endpoints) can have that proxy's trust decisions bypassed: a single client-controlled TCP connection can be used to smuggle a second, fully-attacker-controlled HTTP request that the proxy never inspected/authorized, but which the Stacks node will process as if it originated from the trusted proxy itself.

### Likelihood Explanation
Exploitability is fully remote, unauthenticated, and requires only a handful of crafted bytes over a normal keep-alive HTTP connection — no privileged position, no node secret, and no signer key is needed. It does, however, depend on the node being deployed behind (or interoperating with) another HTTP endpoint that honors `Transfer-Encoding` differently than this parser does, which is a very common deployment topology for Stacks API nodes (reverse proxies in front of `/v2/*` RPC).

### Recommendation
Mirror the response-parser's discipline on the request side in `stackslib/src/net/http/request.rs`:
- Detect and record `Transfer-Encoding` on requests exactly as done for responses.
- Reject (400) any request that specifies both `Content-Length` and `Transfer-Encoding: chunked`.
- Reject (400) any request with an unsupported/ambiguous `Transfer-Encoding` value.
- If chunked request bodies must be supported, wire the same `HttpChunkedTransferReaderState` decoder used for responses into `stream_payload`/`payload_len` for the `Request` preamble path, so framing decisions in this node cannot silently diverge from any spec-compliant peer/proxy.

### Proof of Concept
Against a Stacks node RPC listener sitting behind a compliant reverse proxy that prioritizes `Transfer-Encoding` per RFC 7230:
```
POST /v2/transactions HTTP/1.1
Host: victim-node:20443
Content-Length: 4
Transfer-Encoding: chunked

0

GET /v2/some-restricted-admin-endpoint HTTP/1.1
Host: victim-node:20443
...
```
- The proxy (RFC-7230-compliant) treats this as a single chunked request terminated by the `0\r\n\r\n` chunk terminator and forwards only that first request.
- The Stacks node, per `consensus_deserialize`/`payload_len` above, ignores `Transfer-Encoding`, reads exactly `Content-Length: 4` bytes (`"0\r\n\r\n"`... effectively the literal 4 bytes) as the body of the first request, and then re-enters preamble parsing on the *remaining* bytes — interpreting the smuggled `GET /v2/some-restricted-admin-endpoint ...` as an independent, subsequent request on the same connection, attributed to the trusted proxy's identity/IP.

**Note on confidence**: I could not fully trace `get_content_length()`'s exact fallback value when no `Content-Length` header is present (e.g., whether it defaults to 0), nor did I locate the specific reverse-proxy deployment guidance/documentation for Stacks nodes confirming this topology is officially supported. These would be useful for a background engineer to verify before finalizing a fix, but the core parser asymmetry (`Content-Length`-only framing for requests vs. the explicit CL/TE conflict check that exists only for responses) is directly confirmed in the cited source.
