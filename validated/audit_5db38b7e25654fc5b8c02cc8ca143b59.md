## Finding: Stale cached signature/permission verification reused across transactions within the same block

This has the same root-cause pattern as CVE-2022-22576: a piece of state that was validated under one authorization context (account permissions) gets cached and later reused as if it were still valid under a *different* authorization context, without re-checking.

### Title
Stale signature/permission-verification cache (`isVerified`) allows a revoked key to execute a later transaction packed in the same block - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
`Manager.processBlock` parallel-validates every transaction in an incoming block *before* any transaction in that block has been applied, via `preValidateTransactionSign`, which calls `TransactionCapsule.validateSignature(...)` and sets the capsule's `isVerified` flag to `true` based on the **pre-block** `AccountStore` state. Once a block's transactions are then executed sequentially, `Manager.processTransaction` calls `trxCap.validateSignature(...)` again, but because `isVerified` is already `true`, the check is a cached no-op and is never re-run against the account state as it exists *after* earlier transactions in the same block have executed.

### Finding Description [1](#0-0)  shows `processBlock` calling `preValidateTransactionSign(txs)` up front for the whole block using the current (pre-block) `chainBaseManager.getAccountStore()`/`DynamicPropertiesStore()`. That helper submits each `TransactionCapsule` to `ValidateSignTask`, which calls `trx.validateSignature(...)`: [2](#0-1) 

`TransactionCapsule.validateSignature`/`validatePubSignature` are guarded by the `isVerified` flag and set it to `true` after a single successful check, short-circuiting any future calls: [3](#0-2) [4](#0-3) 

Later, when the block's transactions are actually applied one by one in `processBlock`'s main loop, `processTransaction` calls `trxCap.validateSignature(...)` again as part of normal execution, but this is now a no-op due to the cached `isVerified` flag: [5](#0-4) [6](#0-5) 

If a permission-changing transaction (e.g. `AccountPermissionUpdateContract`, whose `execute()` directly overwrites the account's `Permission` set via `AccountCapsule.updatePermissions`, see [7](#0-6)  and [8](#0-7) ) is placed earlier in the same block than a second transaction signed by a key that permission-change revokes, the second transaction's signature was already pre-validated against the *old* permission set before the block started applying, and its `isVerified=true` flag means the actual per-transaction execution path never re-checks against the *new*, post-update permission state.

The codebase already contains an explicit, tested fix for the analogous case in `switchFork` — clearing `isVerified` on every transaction of a re-applied branch because "account permissions may have changed" and "a cached signature-verification result is no longer trustworthy" — see the comment and code at [9](#0-8) , validated by `switchForkShouldResetTransactionSignVerifiedOnNewBranch` in `ManagerTest.java`. That same reasoning was never applied to the ordinary in-block execution path where `preValidateTransactionSign` pre-validates the whole block up front.

### Impact Explanation
An attacker who has a key with weight in an account's active/owner permission can:
1. Submit transaction A: an `AccountPermissionUpdateContract` that removes/lowers that key's weight (e.g., transferring control to a new key set).
2. Submit transaction B: a transfer/other contract signed only by the soon-to-be-revoked key, sequenced after A in the mempool/block.

Because `preValidateTransactionSign` validates B against the pre-block permission set (where the key is still authorized) and marks `isVerified=true`, B's execution in the sequential loop skips re-validation entirely, letting B execute using authorization that no longer exists at the time it is actually applied. This is an unauthorized-account-operation / permission-bypass primitive that can move funds or otherwise act with a key that has been revoked within the very block that revokes it — a concrete violation of "unauthorized account operation" impact criteria.

### Likelihood Explanation
This requires no privileged role, malicious witness, or unusual network conditions — it is triggerable purely by an ordinary unprivileged account owner controlling multiple keys, by simply broadcasting two ordinary transactions (A then B) that get included in the same block, which any honest SR packing the mempool in arrival/priority order would do without any special manipulation.

### Recommendation
Do not rely on the pre-block-wide `isVerified` cache set by `preValidateTransactionSign` for transactions later in the same block. Either: (a) reset `isVerified` on all subsequent same-block transactions whenever a permission-affecting contract (`AccountPermissionUpdateContract`, or any actuator that mutates `Permission`) from the same owner is applied earlier in block processing, mirroring the fix already applied in `switchFork`; or (b) always re-run `validateSignature` against current in-block state at actual execution time in `processTransaction` rather than trusting the pre-validation cache, reserving `preValidateTransactionSign` purely as an early-reject optimization rather than an authoritative check.

### Proof of Concept
1. Create account X with active permission containing key `K1` (weight sufficient to authorize transfers) as well as `K2`.
2. Build transaction A = `AccountPermissionUpdateContract` from X, signed by enough weight, removing `K1` from the new active permission set.
3. Build transaction B = `TransferContract` from X (or any contract type) signed only by `K1`, with valid TAPOS/expiration.
4. Submit A and B to the network so they land in the same block with A ordered before B (e.g., broadcast A slightly earlier so it's picked up first by block packing, or coordinate with mempool ordering).
5. Observe: `preValidateTransactionSign` validates B's signature against the state before A applied (where `K1` still has weight) and sets `isVerified=true` on B's capsule.
6. During block application, A executes first and calls `AccountCapsule.updatePermissions`, removing `K1`'s authority.
7. B executes next; `processTransaction` calls `trxCap.validateSignature(...)`, which is a no-op due to `isVerified=true`, so B is authorized and executed despite `K1` no longer having permission — demonstrating the bypass.

  private static class ValidateSignTask implements Callable<Boolean> {

    private TransactionCapsule trx;
    private CountDownLatch countDownLatch;
    private ChainBaseManager manager;

    ValidateSignTask(TransactionCapsule trx, CountDownLatch countDownLatch,
        ChainBaseManager manager) {
      this.trx = trx;
      this.countDownLatch = countDownLatch;
      this.manager = manager;
    }

    @Override
    public Boolean call() throws ValidateSignatureException {
      try {
        trx.validateSignature(manager.getAccountStore(), manager.getDynamicPropertiesStore());
      } catch (ValidateSignatureException e) {
        throw e;
      } finally {
        countDownLatch.countDown();
      }
      return true;
    }
  }

  public boolean validatePubSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore)
      throws ValidateSignatureException {
    if (!isVerified) {
      if (this.transaction.getSignatureCount() <= 0
              || this.transaction.getRawData().getContractCount() <= 0) {
        throw new ValidateSignatureException("miss sig or contract");
      }
      if (this.transaction.getSignatureCount() > dynamicPropertiesStore
              .getTotalSignNum()) {
        throw new ValidateSignatureException("too many signatures");
      }

      byte[] hash = getTransactionId().getBytes();

      long startNs = System.nanoTime();
      try {
        if (!validateSignature(this.transaction, hash, accountStore, dynamicPropertiesStore)) {
          isVerified = false;
          throw new ValidateSignatureException("sig error");
        }
      } catch (SignatureException | PermissionException | SignatureFormatException e) {
        isVerified = false;
        throw new ValidateSignatureException(e.getMessage());
      } finally {
        logSlowSigVerify(startNs);
      }
      isVerified = true;
    }
    return true;
  }

  public boolean validateSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore) throws ValidateSignatureException {
    if (!isVerified) {
      //Do not support multi contracts in one transaction
      Transaction.Contract contract = this.getInstance().getRawData().getContract(0);
      if (contract.getType() != ContractType.ShieldedTransferContract) {
        validatePubSignature(accountStore, dynamicPropertiesStore);
      } else {  //ShieldedTransfer
        byte[] owner = getOwnerAddress();
        if (!ArrayUtils.isEmpty(owner)) { //transfer from transparent address
          validatePubSignature(accountStore, dynamicPropertiesStore);
        } else { //transfer from shielded address
          if (this.transaction.getSignatureCount() > 0) {
            throw new ValidateSignatureException("there should be no signatures signed by "
                    + "transparent address when transfer from shielded address");
          }
        }
      }
      isVerified = true;
    }
    return true;
  }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
