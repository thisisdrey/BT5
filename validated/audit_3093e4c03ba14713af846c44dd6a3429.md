### Title
Asset-conversion pool price/reserves are read from live account balances, letting anyone manipulate the AMM oracle via direct transfers - (`substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`pallet-asset-conversion`'s `get_reserves` (and the quoting functions built on top of it) do not track reserves as protected state — they read the pool account's *current* on-chain asset balance every time, exactly like the vulnerable `Pair.baseTokenReserves()` / `_baseTokenReserves()` pattern from the Caviar report. Because the pool account is an ordinary `AccountId` derived deterministically by `T::PoolLocator`, anyone can send tokens directly to it with a plain `transfer`, inflating the reported reserves and skewing the quoted price without going through the swap/add-liquidity invariant checks. This manipulable price is then consumed both by external integrations reading `AssetConversionApi` (RPC/state_call, precompile) and internally by `pallet-asset-conversion-tx-payment` to determine how much of a non-native asset to charge for transaction fees.

### Finding Description
`get_reserves` fetches live balances rather than an internally-updated reserve value: [1](#0-0) 

`quote_price_exact_tokens_for_tokens` / `quote_price_tokens_for_exact_tokens` then use those live-balance "reserves" directly to compute swap quotes: [2](#0-1) [3](#0-2) 

There is no analog to Uniswap V2's `reserve0`/`reserve1` storage that is only updated on `mint`/`burn`/`swap` (the `_update` pattern the report's remediation calls for). Any account can call `Balances::transfer_keep_alive` / `Assets::transfer` to the pool account address (obtainable via `PoolLocator::pool_address`, a pure function of the two asset kinds) and instantly change the value returned by `get_reserves`, `quote_price_exact_tokens_for_tokens`, and `quote_price_tokens_for_exact_tokens` — with no invariant check comparable to the swap-path `K`-constant enforcement.

This manipulable price is exposed as a runtime API consumed by third parties (asset-hub runtimes and the base node runtime wire it up verbatim): [4](#0-3) 

and by the EVM precompile that exposes `getReserves`/`quoteExactTokensForTokens`/`quoteTokensForExactTokens` to Solidity contracts on `pallet-revive`: [5](#0-4) [6](#0-5) 

It is also consumed internally: `pallet-asset-conversion-tx-payment`'s `ChargeAssetTxPayment` extension calls `quote_price_tokens_for_exact_tokens` to convert the native-fee amount into an amount of the chosen fee asset to withdraw from the payer, as exercised in its test suite: [7](#0-6) 

### Impact Explanation
Because the "reserve" is just `T::Assets::balance(pool_account)`, an unprivileged attacker can:
- Donate tokens directly to a pool account to skew `get_reserves`/quote outputs read by any downstream contract, DEX aggregator, or off-chain integration that treats this pallet as a price oracle (the exact scenario judged valid in the referenced report), or
- Manipulate the fee-asset quote consumed by `ChargeAssetTxPayment`, causing transaction senders to be overcharged/undercharged in the fee asset relative to the true market rate, i.e., a wrong-amount settlement of a public entrypoint's incidental accounting.

This is a runtime-level accounting/oracle-integrity bug that compromises intended behavior of a shipped pallet and its dependent pallet/precompile, matching the "runtime bugs that compromise intended behavior" and "public underpriced work" impact classes, not merely an external-protocol concern.

### Likelihood Explanation
High: no privileged role, governance action, or malicious relayer/validator is required. Any signed account can call the standard `transfer` extrinsic (or `Assets::transfer`) targeting the deterministic pool address returned by `PoolLocator::pool_address`, which is derivable by anyone off-chain, and immediately affect subsequent reads of `get_reserves`/quote functions in the same or later block, with no fee beyond a normal transfer.

### Recommendation
Track per-pool reserves as pallet storage updated only inside `add_liquidity`, `remove_liquidity`, and `swap`/`credit_swap` (mirroring Uniswap V2's `_update`), instead of deriving them from `T::Assets::balance(pool_account)` at query time. `get_reserves`, `quote_price_exact_tokens_for_tokens`, and `quote_price_tokens_for_exact_tokens` should read this tracked state, and any direct token inflow to the pool account should be swept/ignored rather than treated as reserve growth. If donation-based reserve growth must be supported (e.g., for fee accrual), gate its effect behind an explicit `sync`-style call rather than implicit balance reads used for pricing.

### Proof of Concept
1. `user` creates a pool for `(Native, AssetId(2))` and calls `add_liquidity` with `liquidity1 = 10_000`, `liquidity2 = 200`, establishing pool account `P` with `Native=10_000`, `Asset2=200` and setting price `50:1`.
2. Attacker `A` (no special privilege) calls `Balances::transfer_keep_alive(P, 1_000_000)`, directly inflating `P`'s native balance to `1_010_000` without touching LP shares or going through `swap`.
3. Any caller invoking `AssetConversion::get_reserves(Native, Asset2)` (via `substrate/frame/asset-conversion/src/lib.rs:1499`), the `AssetConversionApi::get_reserves` runtime call (`substrate/bin/node/runtime/src/lib.rs:3735`), or the `getReserves` precompile function (`substrate/frame/asset-conversion/precompiles/src/lib.rs:494`) now observes `Native=1_010_000` instead of `10_000`, skewing the quoted price by ~100x.
4. If a transaction payer chose `Asset2` as the fee asset, `ChargeAssetTxPayment::validate_and_prepare` (exercised in `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/tests.rs:1580`) calls `quote_price_tokens_for_exact_tokens` using the same manipulated balances, so the fee-asset amount withdrawn from the payer is computed against the attacker-skewed price rather than the true pool ratio.

		pub fn quote_price_tokens_for_exact_tokens(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount: T::Balance,
			include_fee: bool,
		) -> Option<T::Balance> {

			if amount.is_zero() {
				return None;
			}
			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2).ok()?;

			let (balance1, balance2) = Self::get_reserves(asset1.clone(), asset2.clone()).ok()?;

			if balance1.is_zero() {
				return None;
			}

			// Swap withdrawals from pools use `keep_alive=true` (Preserve). Use the same
			// preservation level to determine the actual withdrawable amount.
			let max_output =
				T::Assets::reducible_balance(asset2.clone(), &pool_account, Preserve, Polite);
			if amount > max_output {
				return None;
			}

			if include_fee {
				let fee = Self::pool_fee_for(&asset1, &asset2).ok()?;
				Self::get_amount_in(fee, &amount, &balance1, &balance2).ok()
			} else {
				Self::quote(&amount, &balance2, &balance1).ok()
			}
		}

	fn quote_exact_tokens_for_tokens(
		call: &IAssetConversion::quoteExactTokensForTokensCall,
		env: &mut impl Ext<T = Runtime>,
	) -> Result<Vec<u8>, Error> {
		// Quote is always a single-pair operation (the Solidity interface takes two assets,
		// not a path). The actual cost is just reserve reads + arithmetic, but no dedicated
		// benchmark exists yet. Charging the swap weight for path length 2 is a safe
		// overestimate since swaps include transfer costs that quotes do not.
		env.charge(
			<Runtime as pallet_asset_conversion::Config>::WeightInfo::swap_exact_tokens_for_tokens(
				2,
			),
		)?;

		let asset1 = Self::decode_asset_kind(&call.asset1)?;
		let asset2 = Self::decode_asset_kind(&call.asset2)?;

		let quoted =
			<pallet_asset_conversion::Pallet<Runtime> as QuotePrice>::quote_price_exact_tokens_for_tokens(
				asset1,
				asset2,
				Self::to_balance(call.amount)?,
				call.includeFee,
			)
			.ok_or(Error::Revert(Revert { reason: ERR_POOL_NOT_FOUND.into() }))?;

		Ok(IAssetConversion::quoteExactTokensForTokensCall::abi_encode_returns(&Self::to_u256(
			quoted,
		)?))
	}

	fn get_reserves(
		call: &IAssetConversion::getReservesCall,
		env: &mut impl Ext<T = Runtime>,
	) -> Result<Vec<u8>, Error> {
		env.charge(<Runtime as pallet_asset_conversion::Config>::WeightInfo::get_reserves())?;

		let asset1 = Self::decode_asset_kind(&call.asset1)?;
		let asset2 = Self::decode_asset_kind(&call.asset2)?;

		let (reserve1, reserve2) = pallet_asset_conversion::Pallet::<Runtime>::get_reserves(
			asset1, asset2,
		)
		.map_err(|e| match e {
			pallet_asset_conversion::Error::InvalidAssetPair => {
				Error::Revert(Revert { reason: ERR_INVALID_ASSET_PAIR.into() })
			},
			pallet_asset_conversion::Error::PoolEmpty => {
				Error::Revert(Revert { reason: ERR_POOL_EMPTY.into() })
			},
			// get_reserves only produces the two variants above; list the rest
			// exhaustively so adding a new Error variant triggers a compile error.
			pallet_asset_conversion::Error::PoolExists |
			pallet_asset_conversion::Error::WrongDesiredAmount |
			pallet_asset_conversion::Error::AmountOneLessThanMinimal |
			pallet_asset_conversion::Error::AmountTwoLessThanMinimal |
			pallet_asset_conversion::Error::ReserveLeftLessThanMinimal |
			pallet_asset_conversion::Error::AmountOutTooHigh |
			pallet_asset_conversion::Error::PoolNotFound |
			pallet_asset_conversion::Error::Overflow |
			pallet_asset_conversion::Error::AssetOneDepositDidNotMeetMinimum |
			pallet_asset_conversion::Error::AssetTwoDepositDidNotMeetMinimum |
			pallet_asset_conversion::Error::AssetOneWithdrawalDidNotMeetMinimum |
			pallet_asset_conversion::Error::AssetTwoWithdrawalDidNotMeetMinimum |
			pallet_asset_conversion::Error::OptimalAmountLessThanDesired |
			pallet_asset_conversion::Error::InsufficientLiquidityMinted |
			pallet_asset_conversion::Error::ZeroLiquidity |
			pallet_asset_conversion::Error::ZeroAmount |
			pallet_asset_conversion::Error::ProvidedMinimumNotSufficientForSwap |
			pallet_asset_conversion::Error::ProvidedMaximumNotSufficientForSwap |
			pallet_asset_conversion::Error::InvalidPath |
			pallet_asset_conversion::Error::NonUniquePath |
			pallet_asset_conversion::Error::IncorrectPoolAssetId |
			pallet_asset_conversion::Error::BelowMinimum |
			pallet_asset_conversion::Error::FeeTooHigh => {
				frame_support::defensive!("get_reserves returned unexpected error");
				Error::Revert(Revert { reason: ERR_UNEXPECTED.into() })

				reserve1: Self::to_u256(reserve1)?,
				reserve2: Self::to_u256(reserve2)?,
			},
		))
	}
