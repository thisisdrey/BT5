### Title
`SignedDelegateAction` / `VersionedSignedDelegateAction` meta-transaction signatures carry no chain-binding value, enabling cross-fork replay of authorized actions - ([File: core/primitives/src/action/delegate.rs])

### Summary
NEAR's meta-transaction scheme (NEP-366, `Action::Delegate` / `Action::DelegateV2`) signs a payload that contains `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key`, hashed under a NEP-461-style domain discriminant. [1](#0-0)  Unlike a plain `SignedTransaction`, which is anchored to a specific `block_hash` that must exist within the chain's recent history (`transaction_validity_period`), a `DelegateAction`/`DelegateActionV2` has no block-hash or chain-identifying field at all — only an absolute `max_block_height` ceiling. [2](#0-1)  This is analogous to the reported Beanstalk bug: a signature that omits any chain/network-binding value (there `chainId`, here an equivalent such as `block_hash`/genesis id) can be replayed unmodified on a different, but state-identical, chain (e.g. after a fork).

### Finding Description
The signature verification for both delegate-action versions only checks the NEP-461-tagged hash of the action fields against the signer's key; it never incorporates any value that ties the signature to one specific chain/fork: [3](#0-2) [4](#0-3) 

The discriminant used in `SignableMessage` only encodes the NEP number and an on-chain/off-chain flag — it is not a per-network or per-genesis value: [5](#0-4) 

By contrast, ordinary `SignedTransaction`s include `block_hash`, which the runtime validates against the specific chain's recent block history (`chain_validate`) before acceptance: [6](#0-5) 

`nearcore` explicitly documents that this `block_hash` binding is what stops stale/foreign-chain transactions from being replayed, and that mirroring transactions from one chain to a state-forked chain requires re-signing precisely because `block_hash` differs between the two chains: [7](#0-6) 

`DelegateAction`/`DelegateActionV2` never goes through this `block_hash` check — the only "recency"-like control it has is `max_block_height`, a chain-agnostic upper bound rather than a binding to a specific block or fork: [8](#0-7) 

Replay protection for delegate actions instead relies solely on the access key's `nonce` (or gas-key nonce), which is per-account state: [9](#0-8) 

If the same account/access-key state exists on two independently valid chains sharing common history (a protocol fork, or an official/unofficial "mirror" of the chain built from forked state, which nearcore itself documents and tools/mirror/README.md describes), the nonce on both chains will initially be identical (both derived from the same pre-fork state). Consequently a `SignedDelegateAction` produced once by a user can be embedded, by any unprivileged relayer, into a freshly-signed outer transaction (whose own `block_hash` is trivially chain-valid on either fork) and executed independently on each fork, since nothing in the delegate-action payload or its signature differs between the two chains.

### Impact Explanation
An account owner who signs a single `DelegateAction` authorizing a state-changing action (e.g. a token transfer, key addition, or contract call routed through `sender_id`/`receiver_id`) can have that exact authorization executed a second time on a sibling chain that shares the same pre-fork account/access-key state, without any additional consent. Because meta-transactions are specifically designed so that a possibly-untrusted relayer submits them on the user's behalf, this does not even require the sender to cooperate — any relayer holding the previously-broadcast `SignedDelegateAction` bytes can replay the authorization on the other chain. This can lead to unintended/duplicated fund transfers, key grants, or other privileged actions being executed twice across two ledgers that the user only authorized once, which is the direct meta-transaction analog of the cross-chain replay theft described in the Beanstalk report.

### Likelihood Explanation
This requires two chains to independently share identical account/access-key state at some common point (e.g. a genuine protocol fork, or forked/derived networks built from the same state such as the scenario `tools/mirror` is built to support). This is a narrower precondition than an ordinary EVM chain split, since it depends on nearcore-specific forking/state-derivation events rather than everyday operation. However, unlike ordinary transactions (which are inherently protected by the `block_hash` recency check), delegate actions have zero chain-binding, so whenever such a fork condition exists, exploitation is straightforward and requires no special access — any party in possession of a previously broadcast `SignedDelegateAction` can replay it.

### Recommendation
Include a chain-binding value in the signed `DelegateAction`/`DelegateActionV2` payload (e.g. the genesis hash or a `block_hash` similar to `SignedTransaction`, or a dedicated chain/network identifier), and verify it against the executing chain's own identity during `validate_delegate_action_key`/`apply_delegate_action`, mirroring the protection `SignedTransaction` already receives via `chain_validate`. This closes the gap between the two authorization mechanisms and prevents a single meta-transaction signature from being valid across more than one chain.

### Proof of Concept
1. Chain A forks into Chain A and Chain B at height `H`, both inheriting identical account state including access key `nonce` values (this can also be modeled via `tools/mirror`'s documented forked-state workflow, absent its key-remapping step for the inner delegate signature).
2. Before the fork, Alice signs `DelegateAction { sender_id: alice, receiver_id: ft_token, actions: [transfer(bob, 100)], nonce: N, max_block_height: H+1000, public_key: alice_pk }` via `SignedDelegateAction::sign`, producing `sig` over `get_nep461_hash()` — see [10](#0-9) .
3. A relayer wraps this `SignedDelegateAction` inside a normal transaction (`Action::Delegate`) and submits it on Chain A; it succeeds and increments Alice's access-key nonce to `N+1` on Chain A only.
4. The same relayer (or any party who observed the broadcast bytes) wraps the identical, unmodified `SignedDelegateAction` bytes inside a freshly-signed transaction (new relayer nonce and Chain-B-valid `block_hash`) and submits it on Chain B, where Alice's access key nonce is still `N` (Chain B state diverged independently and never saw the first submission). Because `SignedDelegateAction::verify` only checks the action fields and signature — not any chain identity — and `validate_delegate_action_key` only checks the nonce against Chain B's own state, the transfer executes again on Chain B.
5. Result: Alice's single signature has now moved `100` FT to Bob on two independent ledgers, though she authorized only one transfer.

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}
