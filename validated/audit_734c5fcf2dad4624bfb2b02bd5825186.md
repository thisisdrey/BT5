### Title
Attacker-controlled peer can permanently poison Atlas attachment resolution for a `content_hash` by returning mismatched attachment bytes with no hash verification - ([File: stackslib/src/net/atlas/download.rs] and [File: stackslib/src/net/api/getattachment.rs])

### Summary
`StacksHttpResponse::decode_atlas_get_attachment` and `AttachmentsBatchStateContext::extend_with_attachments` never verify that the returned `Attachment`'s hash matches the requested `content_hash`. A malicious peer that is selected as the "most reliable source" for a given `content_hash` can return arbitrary (mismatched) attachment bytes, get counted as a *successful* request (boosting its reliability score so it keeps being selected), and thereby prevent `AttachmentsBatch::resolve_attachment` from ever clearing that instance, until `max_attachment_retry_count` is reached and the batch is dropped with the attachment never resolved.

### Finding Description
The equality the question is built on: `valid_committed_content_hash resolved == true` should hold for any attachment whose `content_hash` was validly committed on-chain and whose bytes exist somewhere in the network. This equality is broken because content integrity is never checked on the client side of the attachment-download flow.

- `AttachmentRequest::get_most_reliable_source` picks the peer with the highest `ReliabilityReport::score()` [1](#0-0) .
- When the response comes back, `extend_with_attachments` decodes it via `decode_atlas_get_attachment` and, on success, inserts the attachment into `self.attachments` and calls `report.bump_successful_requests()` — with **no check that `response.attachment.hash() == request.content_hash`** [2](#0-1) .
- `decode_atlas_get_attachment` itself only performs JSON deserialization, with no hash/content validation [3](#0-2) .
- Back in `AttachmentsDownloader::run`, for every attachment drained from `context.attachments`, the code calls `context.attachments_batch.resolve_attachment(&attachment.hash())` [4](#0-3) . `resolve_attachment` only removes tracked entries whose `content_hash` equals `attachment.hash()` [5](#0-4) . If the attacker returns bytes for a different attachment, the mismatched hash means the specific tracked `content_hash` is **never removed** from `attachments_instances`.
- Because the attacker's `report` was bumped as *successful* (not failed), its `ReliabilityReport::score()` [6](#0-5)  increases, making it more likely to remain the top-ranked source in `AttachmentRequest::cmp`/`get_most_reliable_source` on every subsequent retry [7](#0-6) , so the same malicious peer is re-selected each retry cycle.
- Since `has_fully_succeed()` checks `attachments_instances_count() == 0` [8](#0-7) , and the entry is never cleared, `run()`'s re-enqueue logic bumps `retry_count` each cycle via `bump_retry_count()` [9](#0-8)  until `retry_count >= connection_options.max_attachment_retry_count`, at which point the batch is dropped with the log "Atlas: dropping batch ... retries count exceeded" and never re-enqueued [10](#0-9) .

The result: the `content_hash` never appears in `resolved_attachments`, `find_attachment`/`find_uninstantiated_attachment` will never find it (used by `/v2/attachments/:hash`, see `getattachment.rs` lines 104-109), and any dependent consumer (e.g., a BNS zonefile lookup keyed on that attachment hash) will permanently treat validly-committed content as absent.

### Impact Explanation
A remote, unprivileged peer that (a) is discoverable via `network.get_outbound_sync_peers()`/has a data URL, and (b) claims (truthfully, via the attachments-inv response) to have the attachment in its inventory, can be selected to serve a specific `content_hash` and can poison resolution for that hash by returning wrong bytes on every retry. This is a High-severity "attachment/BNS mismatch" issue: it causes a node to permanently serve/represent a validly-committed attachment as unresolved/absent, which is exactly the category the prompt calls out. It does not corrupt other peers' data (no store/relay of unverified content into the shared `AtlasDB.attachments` table as instantiated, since `insert_instantiated_attachment` is only called on `context.attachments.drain()` values — but note this **does** mean the wrong/attacker attachment itself IS inserted as instantiated in the local AtlasDB under its own (different) hash, though it doesn't get linked to the victim instance because `resolve_attachment` keys off content_hash, not the instance link). The primary damage is denial of resolution for the targeted `content_hash`, repeatable per-batch, at negligible attacker cost (a handful of crafted HTTP 200 responses).

### Likelihood Explanation
- Preconditions: attacker must run/control a peer the victim considers an outbound sync peer with a resolvable data URL, and must appear to have the target attachment in its Atlas inventory (attacker fully controls its own `/v2/attachments/inv` and `/v2/attachments/:hash` responses, so this is trivial to satisfy).
- No secrets, signatures, or privileged roles required — this is exactly the "unprivileged remote peer" threat model in scope.
- Attack is cheap and fully repeatable up to `max_attachment_retry_count` (a `ConnectionOptions` value) per batch; the attacker only needs to keep answering the periodic re-tries with mismatched bytes, and its reliability score keeps improving because success/failure accounting is based on JSON-decodability, not content-hash correctness, making re-selection likely rather than incidental.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs`), after decoding the response, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments` and before calling `bump_successful_requests()`; treat a hash mismatch as a failed request (`bump_failed_requests()`) and ideally record the offending peer for downgraded reliability. This ensures `resolve_attachment` correctness and prevents malicious peers from gaming `ReliabilityReport::score()` with fabricated "successful" mismatched responses.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/tests.rs`:
1. Construct an `AttachmentsBatchStateContext` with a single tracked `(contract_id, attachment_index) -> content_hash = H` and one peer URL `P`.
2. Simulate `BatchedRequestsResult<AttachmentRequest>.succeeded` containing one entry: `AttachmentRequest{content_hash: H, sources: {P: report}}` mapped to `Some(StacksHttpResponse)` whose JSON body decodes via `decode_atlas_get_attachment` to a `GetAttachmentResponse{attachment: Attachment(content: b"WRONG")}` (i.e., `Attachment::new(b"WRONG".to_vec()).hash() != H`).
3. Call `extend_with_attachments` and assert: `report.total_requests_success == 1` (proves the missing check inflates reliability) and `context.attachments.len() == 1` but the stored attachment's `hash() != H`.
4. Drive `AttachmentsDownloader::run` in a loop for `max_attachment_retry_count` cycles reusing the same mismatched-response peer as top source each time (asserted via `get_most_reliable_source`), each time asserting `attachments_batch.has_fully_succeed() == false` and `attachments_batch.retry_count` incrementing.
5. After the final cycle, assert the batch is no longer present in `priority_queue` (dropped) and assert `resolved_attachments` returned across all `run()` calls never contains an entry for the `AttachmentInstance` with `content_hash == H`, while `network.atlasdb.find_attachment(&H)` still returns `Ok(None)`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    pub fn bump_retry_count(&mut self) {
        self.retry_count += 1;
        let delay = cmp::min(
            MAX_RETRY_DELAY,
            2u64.saturating_pow(self.retry_count as u32).saturating_add(
                thread_rng().gen::<u64>() % 2u64.saturating_pow((self.retry_count - 1) as u32),
            ),
        );

        debug!("Atlas: Re-attempt download in {} seconds", delay);
        self.retry_deadline = get_epoch_time_secs() + delay;
    }

    pub fn resolve_attachment(&mut self, content_hash: &Hash160) {
        for missing_attachments in self.attachments_instances.values_mut() {
            let mut keys = vec![];
            for (k, hash) in missing_attachments.iter() {
                if hash == content_hash {
                    keys.push(*k);
                }
            }
            for key in keys {
                missing_attachments.remove(&key);
            }
        }
    }
