### Title
Operator.execute leaks the authenticated `MSG_SENDER` context to arbitrary called contracts, letting any contract invoked during a user's batch impersonate that user and drain their collateral - (File: contracts/Operator.sol)

### Summary
When a user calls `Operator.execute`, the contract stores the user's EOA in a transient slot (`MSG_SENDER_STORAGE`) that remains set for the entire duration of the batch (`contracts/Operator.sol:20-24`). Every `SynthContext` contract (`Pool`, `DepositToken`, `DebtToken`, `SyntheticToken`, `SmartFarmingManager`, gateways) resolves `_msgSender()` by calling `Operator.getActualMsgSender()` whenever `msg.sender == operator` (`contracts/utils/SynthContext.sol:14-24`). Because the stored sender is not cleared or scoped per-target, **any contract reached during the batch** — including an attacker-deployed contract, or any third-party contract the batch legitimately calls that then reenters a Metronome contract — can act with the victim's identity. This is the direct analog of the scs-library-client bug: the authorization context (the user's identity) is forwarded across a "redirect" (the arbitrary `target` call in `execute`) to a third party that should not have received it.

### Finding Description
`execute` iterates user-supplied `Call[]` and performs `target.functionCallWithValue(callData, value)` with no restriction on `target` (`contracts/Operator.sol:42-52`). The `setMsgSender` modifier sets `MSG_SENDER_STORAGE = msg.sender` before the loop and clears it only after all calls complete. `getActualMsgSender()` is callable by anyone and returns the victim's address throughout the batch (`contracts/Operator.sol:28-31`).

Concrete theft path: an attacker contract is invoked anywhere inside the victim's `execute` batch (e.g., as a malicious zap/router/swap target, or by reentering from a token callback of a legitimate target). The attacker contract then calls:

```solidity
depositToken.withdraw(amount, attacker);
```

`DepositToken.withdraw` resolves `_msgSender()` → Operator → the **victim's** address, checks only `unlockedBalanceOf(victim)`, burns the victim's deposit tokens, and pulls the underlying collateral from Treasury to the **attacker-chosen `to_`** (`contracts/DepositToken.sol:406-411`, `:536-553`). Similarly, `transfer(attacker, unlockedBalance)` (`contracts/DepositToken.sol:348-353`) and `approve(attacker, type(uint256).max)` (`:187-189`) work as the victim, and `Pool.swap`, `DebtToken` repayment, `SyntheticToken` transfers, and `NativeTokenGateway`/`VesperGateway` functions are all callable with the victim's identity.

### Impact Explanation
Direct theft of user funds: any unlocked collateral in a victim's account can be withdrawn to the attacker via `DepositToken.withdraw(amount, attacker)` or transferred via `DepositToken.transfer`. Even for positions with debt, the attacker can swap collateral synths, mint up to the victim's remaining issuable capacity, or approve themselves over the victim's `DepositToken`/`SyntheticToken` balances to strip value — all signed with the victim's identity. The invariant broken is authentication/identity: the authorization granted implicitly to a specific call is propagated to untrusted third-party code, exactly as the `Authorization` header was propagated to the S3 redirect target in GHSA-7p8m-22h4-9pj7.

### Likelihood Explanation
The precondition is that the victim's `execute` batch contains (directly or transitively) a call to attacker-controlled code. This mirrors the advisory's requirement of interacting with a third-party S3 backend: users use `Operator.execute` precisely to batch interactions with external protocols (swaps, zaps, approvals). A malicious router, aggregator calldata, or ERC-20 token with a callback (`transfer` hook / `permit`-style UX, or a token whose `transferFrom` reenters) that appears anywhere in a batch gains full impersonation of the user for that transaction. `nonReentrant` on `execute` only prevents reentering `Operator` itself — it does not stop a called contract from calling `Pool`/`DepositToken`, and `ReentrancyGuardTransient` on `DepositToken.withdraw` does not block it because the call chain enters fresh through the attacker contract, not via reentry into the same function. Pause/shutdown flags must be off (normal operation), and no governor/keeper/oracle cooperation is needed — the attacker is a purely unprivileged deployed contract, which is in scope per the threat model.

### Recommendation
Scope the forwarded identity to the intended call rather than the whole transaction, e.g.:
- Store the sender per-call and clear `MSG_SENDER_STORAGE` before/after each `functionCallWithValue`, plus a re-set+clear around each iteration — though this alone doesn't prevent a target from calling back, so additionally
- Restrict `SynthContext._msgSender()` resolution to calls where `tx.origin`/immediate caller chain is the Operator **and** maintain a whitelist of Metronome protocol contracts that may read `getActualMsgSender()`, so third-party contracts reached during `execute` cannot trigger authenticated reads of the user's identity, or
- Have `execute` require all targets to be registered/whitelisted protocol contracts when `value`/privileged flows are involved.

### Proof of Concept
Hardhat/Foundry fork (e.g., Base, where `Operator` is deployed at `0x64b5bb3b7eF0267019fee5b826c60Cb9B7609373`):

```solidity
contract Evil {
    function pwn(IDepositToken dt, address victim) external {
        uint256 amt = dt.unlockedBalanceOf(victim);
        // _msgSender() inside DepositToken resolves to `victim` via Operator
        dt.withdraw(amt, address(this)); // collateral pulled from Treasury to Evil
    }
}

// test
function testCredentialLeak() public {
    // victim deposited WETH into Pool via msdWETH; has unlocked balance
    Evil evil = new Evil();

    IOperator.Call[] memory calls = new IOperator.Call[](1);
    // victim batches what they believe is a benign interaction with `evil`
    calls[0] = IOperator.Call({
        target: address(evil),
        value: 0,
        callData: abi.encodeCall(Evil.pwn, (msdWETH, victim))
    });

    vm.prank(victim);
    operator.execute(calls);

    assertGt(underlying.balanceOf(address(evil)), 0);  // stolen collateral
    assertEq(msdWETH.unlockedBalanceOf(victim), 0);
}
```

The call chain is `victim → Operator.execute → Evil.pwn → DepositToken.withdraw(amount, evil)`, where `DepositToken._msgSender()` returns `victim`, passes `_revertIfLocked(victim, amount)`, and `Treasury.pull(evil, withdrawn)` transfers the victim's underlying collateral to the attacker — reproducing the leak-of-authorization-context-on-redirect bug class on Metronome's own code.
