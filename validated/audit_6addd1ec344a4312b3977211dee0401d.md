### Title
Excessive memory allocation via unbounded array-length words in `PrecompiledContracts.extractBytesArray`/`extractBytes32Array`/`extractSigArray` - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.java` contains helper methods that read an attacker-controlled 256-bit word from TVM calldata, coerce it to an `int` via `intValueSafe()`, and immediately use it as an allocation size for a `byte[][]` array, with no upper bound check before allocation.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` each read a length word straight from the ABI-encoded calldata (`words[offset].intValueSafe()`) and allocate `new byte[len][]` before doing any bounds/size validation against the actual data length: [1](#0-0) [2](#0-1) [3](#0-2) 

`intValueSafe()` clamps a `DataWord` to `Integer.MAX_VALUE` rather than rejecting oversized values, so a caller can set the length field to a very large value (e.g. `0x7fffffff`) and force `new byte[len][]` — a top-level object-array allocation whose element count alone (independent of the sub-array contents) can already exhaust heap, analogous to the Wireshark MS-WSP dissector allocating memory purely from an untrusted length field before validating it against actual packet size (CVE-2021-22207).

This is directly analogous to the excessive-memory-consumption bug class in the CVE: a length value taken from untrusted, attacker-supplied input is used to size a memory allocation before the corresponding payload/backing data is validated to actually contain that many elements.

I was not able to fully trace, within the available context, which specific precompiled contract(s) invoke `extractBytesArray`/`extractBytes32Array`/`extractSigArray` at runtime (grep for their call sites beyond definitions did not return results in the indexed portion of the file), so I cannot confirm with certainty that these helpers are wired into a currently reachable precompile dispatch path (e.g. `BatchValidateSign` or a multisig-validation precompile) versus being dead/legacy code. The other memory-allocation candidates I examined in the VM (`EnergyCost.getVoteWitnessCost`/`getVoteWitnessCost2`, `VerifyTransferProof`) were confirmed to have proper bounds checks (`spendCount`/`receiveCount` limited to 1–2, and `getVoteWitnessCost3`/BigInteger-based overflow checks with explicit `OutOfMemoryException` per `VoteWitnessCost3Test.java`), so those are not vulnerable.

### Impact Explanation
If reachable from a live precompile executed during `CALL`/`STATICCALL` from a smart contract (which any transaction broadcaster or contract deployer can trigger), this allows an attacker to force a large heap allocation per invocation with minimal calldata, potentially causing `OutOfMemoryError` and crashing/halting the node that executes the transaction — matching the "node crash or halt" acceptance criterion. Given the uncertainty about whether these specific helper methods are on a live, energy-metered call path, the actual severity depends on confirming the call site and its energy costing.

### Likelihood Explanation
Low-to-medium confidence pending verification of the call site: the vulnerable pattern (unchecked attacker length → immediate array allocation) exists in the codebase in a security-sensitive file (`PrecompiledContracts.java`), and the underlying data (calldata to a precompile) is fully attacker-controlled and reachable via a single unprivileged transaction/contract call.

### Recommendation
Before allocating `new byte[len][]` (or similar) in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate `len` against the actual bounds of the supplied `data`/`words` array (e.g., require `len * elementSize` not to exceed `data.length - offset`), and reject with an early return / exception if `len` is unreasonably large, mirroring the bound checks already present in `VerifyTransferProof` (`spendCount`/`receiveCount` range checks) and RLP's `verifyLength` pattern.

### Proof of Concept
Not fully verifiable without confirming the live call site; conceptually: craft calldata to whatever precompile invokes `extractBytesArray`/`extractBytes32Array`/`extractSigArray` such that the length word at the expected offset is set to a large value (e.g., `0x7fffffff`), while keeping the surrounding data minimal, then invoke that precompile via a `CALL` opcode from a deployed contract — the resulting `new byte[len][]` allocation would attempt to allocate memory proportional to the attacker-chosen length before any validation against the real payload size.

    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
