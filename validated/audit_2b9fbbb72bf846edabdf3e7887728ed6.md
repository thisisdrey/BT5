### Title
NullPointerException in `MarketOrderIdListCapsule` deserialization when a market order's price bucket key is missing - ([File: chainbase/src/main/java/org/tron/core/capsule/MarketOrderIdListCapsule.java])

### Summary
`MarketOrderIdListCapsule(byte[] data)` only guards against `InvalidProtocolBufferException` when calling `MarketOrderIdList.parseFrom(data)`, but not against `data == null`. `MarketPairPriceToOrderStore.get(byte[] key)` passes the raw result of `revokingDB.get(key)` straight into this constructor without a null check, and `MarketCancelOrderActuator.execute()` calls that `get()` on a key derived from the *cancelled* order itself, not from a verified existing-key iterator (unlike `MarketSellAssetActuator.matchOrder`, which only reads keys already confirmed present via `getPriceKeysList`). This is structurally analogous to CVE-2021-33447 (mJS `mjs_print()` NPE): a missing null check on a value before it's dereferenced/parsed, reachable from ordinary, unprivileged input.

### Finding Description
- `MarketOrderIdListCapsule(final byte[] data)` (chainbase/src/main/java/org/tron/core/capsule/MarketOrderIdListCapsule.java:24-30) calls `MarketOrderIdList.parseFrom(data)` inside a try/catch that only catches `InvalidProtocolBufferException`. `com.google.protobuf.AbstractParser#parseFrom(byte[])` throws a `NullPointerException` (not `InvalidProtocolBufferException`) when `data` is `null`, so this constructor will let an NPE propagate uncaught.
- `MarketPairPriceToOrderStore.get(byte[] key)` (chainbase/src/main/java/org/tron/core/store/MarketPairPriceToOrderStore.java:24-28) does:
  ```java
  byte[] value = revokingDB.get(key);
  return new MarketOrderIdListCapsule(value);
  ```
  If `key` is absent from the underlying revoking DB, `revokingDB.get(key)` returns `null`, which is passed unchecked into the capsule constructor above.
- `MarketCancelOrderActuator.execute()` (actuator/src/main/java/org/tron/core/actuator/MarketCancelOrderActuator.java:112-121) recomputes `pairPriceKey` from the order's own sell/buy token ids and quantities (taken from `orderCapsule`, itself fetched by `orderId` supplied in the `MarketCancelOrderContract`), then calls `pairPriceToOrderStore.get(pairPriceKey)` and immediately calls `.removeOrder(...)` on the result — with **no null check** and no `ItemNotFoundException` guard around this specific line (the surrounding `catch` block only catches `ItemNotFoundException`, `InvalidProtocolBufferException`, `BalanceInsufficientException`; an NPE is a `RuntimeException` and is not caught).
- In the normal happy path this key exists (it was created when the order was placed), but any inconsistency between `orderStore` state and `pairPriceToOrderStore` state — e.g. state corruption from a prior aborted/failed transaction, a race in concurrent order matching/removal, or a future code change that deletes the price bucket before all its orders are removed — makes `pairPriceToOrderStore.get()` return an empty/absent-key capsule build off `null`, triggering an uncaught `NullPointerException` inside actuator `execute()`.
- `execute()` on a broadcastable actuator runs inside `Manager.processTransaction()` → `TransactionTrace.exec()`, which is on the block-application path (`Manager.pushBlock` → `applyBlock`/`processBlock`). An uncaught `RuntimeException`/`NullPointerException` escaping actuator execution during block application is not part of the actuator's declared `ContractExeException`/`ContractValidateException` contract, so it is not handled the way validation failures are; it surfaces as an unexpected `Throwable` during `processTransaction`, which is caught generically higher up in `generateBlock`'s packing loop (logged and skipped) but, when replaying blocks received from the network (`processBlock`/`applyBlock`), an unexpected `RuntimeException` is not in the declared checked-exception list handled by `TronNetDelegate.processBlock`'s catch clauses, causing the block application to fail unexpectedly for that block.

### Impact Explanation
An unhandled NPE at the actuator-execution layer during block application can cause inconsistent handling of the transaction (untracked failure not mapped to a proper `ContractExeException`), and if triggered while applying a block from the network (not just when packing a block locally), it is outside of the checked exceptions that `Manager.processBlock`/`TronNetDelegate.processBlock` explicitly handle, risking abrupt processing failure for the whole block rather than a clean rejection of a single bad transaction. This matches the "node crash or halt" acceptance criterion for a Medium-severity NPE analog.

### Likelihood Explanation
Triggering this exact path requires the on-disk market state to be inconsistent (the price-bucket key absent while an order referencing it still exists), which should not normally happen if the store is always kept consistent by `MarketSellAssetActuator`/`MarketCancelOrderActuator`. I was not able to fully verify within tool limits whether such an inconsistency is externally reachable via a single crafted transaction sequence (e.g., a race between concurrent `MarketCancelOrderActuator` and `MarketSellAssetActuator.matchOrder` executions, or a specific ordering of cancel/match operations that leaves `pairPriceToOrderStore` and `orderStore` out of sync). Given the missing null check is a genuine defensive-programming gap analogous to the CVE, but the precise transaction sequence needed to desynchronize the two stores was not confirmed by code inspection, I rate likelihood as **uncertain/low-to-medium** pending further review of `matchOrder`/`removeOrder`/`MarketCancelOrderActuator` interleaving.

### Recommendation
- Add an explicit null check in `MarketOrderIdListCapsule(byte[] data)` before calling `parseFrom`, returning a default/empty instance (mirroring the no-arg constructor) when `data == null`, exactly as `MarketOrderIdListCapsule.get(...).getUnchecked(...)` callers already handle nulls defensively elsewhere (e.g., `Wallet.getMarketOrderListByPair`, `MarketSellAssetActuator.saveRemainOrder`).
- In `MarketCancelOrderActuator.execute()`, use `pairPriceToOrderStore.getUnchecked(pairPriceKey)` (as done elsewhere in the codebase, e.g. `MarketSellAssetActuator.saveRemainOrder`) and explicitly check for `null`/empty before calling `removeOrder`, throwing a `ContractExeException`/logging an error instead of allowing an NPE to propagate.

### Proof of Concept
A concrete, externally-triggerable PoC could not be fully constructed within the available investigation: the vulnerable code path requires `pairPriceToOrderStore` to be missing the key that `MarketCancelOrderActuator` derives from an order still present in `orderStore`. I was unable to confirm, purely from static code review, a legitimate single-transaction or interleaved-transaction sequence that produces this desync (the two stores appear to be updated together in both `MarketSellAssetActuator` and `MarketCancelOrderActuator` under normal conditions). Confirming exploitability would require either (a) finding a code path that deletes/overwrites the price-bucket key without removing all referencing orders, or (b) a race condition in concurrent order placement/cancellation/matching that leaves the stores transiently inconsistent across a persisted block boundary. This should be validated with a live/test-node reproduction before treating the severity as confirmed.
