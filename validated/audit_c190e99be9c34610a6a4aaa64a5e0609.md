### Title
Attached NEAR deposit is permanently stuck in the Wallet Contract when an intermediate cross-contract call fails - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (ETH-implicit account contract, NEP-518) tracks an external caller's attached deposit via `CallerDeposit` so it can be refunded if the user's requested action ultimately fails. This refund logic is implemented only in the final `rlp_execute_callback`, but two other callbacks that can also terminate the promise chain on failure — `address_check_callback` and `nep_141_storage_balance_callback` — return a failure `ExecuteResponse` without ever refunding the tracked `CallerDeposit`. This is analogous to the Axelar `Executor._executeWithToken()` finding: funds are handed to the contract's balance upfront (the analog of the token `approve`), and if the downstream call chain doesn't "claim"/route them back out, they are permanently stranded.

### Finding Description
When an external (non-self) caller invokes `rlp_execute` with an attached deposit, `CallerDeposit::new` records that deposit for potential refund [1](#0-0) . Because `rlp_execute` itself succeeds (it just returns a `Promise`), the attached deposit is unconditionally credited to the Wallet Contract account's balance regardless of what happens downstream; the only path back to the caller is the manual promise-based refund performed in the callback logic.

That manual refund is implemented correctly in `rlp_execute_callback`: [2](#0-1) 

However, `inner_rlp_execute` can route the promise chain through two other callbacks before ever reaching `rlp_execute_callback`, depending on `TransactionKind`:

1. `address_check_callback`, invoked when the target is another eth-implicit account (registrar lookup path) [3](#0-2) . If the call to the address registrar contract fails, the function returns a failure response and simply drops `caller_deposit` without refunding it: [4](#0-3) 

2. `nep_141_storage_balance_callback`, invoked for emulated ERC-20 transfers to check NEP-145 storage registration [5](#0-4) . If the call to `storage_balance_of` on the token contract fails, the function again returns failure and drops `caller_deposit` without any refund: [6](#0-5) 

In both cases the `caller_deposit: Option<CallerDeposit>` parameter is accepted by the function signature (so the contract clearly intends to be able to refund it later, as evidenced by the correct handling in `rlp_execute_callback`), but on these particular failure branches it is silently discarded. The deposit remains part of the Wallet Contract account's balance forever, with no code path left to send it back to the caller (the transaction has already terminated with a failure response and `has_in_flight_tx` reset to `false`).

### Impact Explanation
Any external, non-owner relayer/caller that attaches a NEAR deposit while calling `rlp_execute` for (a) a base-token transfer to another eth-implicit account that requires an address-registrar lookup, or (b) an emulated ERC-20 transfer to a receiver that requires a NEP-141 storage-balance check, will have that attached deposit permanently and irrecoverably absorbed into the Wallet Contract's account balance if the corresponding intermediate cross-contract call (`address_registrar.lookup` or `storage_balance_of`) fails (e.g., due to the target contract not existing, being out of gas, panicking, or being temporarily unavailable). This is a genuine, unrecoverable loss of user funds, matching the "concrete... permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
This requires an external caller to attach a non-zero deposit to `rlp_execute` (a supported, documented usage pattern per `CallerDeposit::new`) while triggering one of the two token/registrar dependent paths, combined with the intermediate cross-contract call failing. Cross-contract calls to arbitrary target contracts routinely fail (non-existent account, insufficient gas, contract panic, target contract paused), so this is not a contrived edge case — it is a realistic operational failure mode for a relayer-driven wallet contract that is meant to be robust to failures.

### Recommendation
Refund `caller_deposit` in the `PromiseResult::Failed` branches of both `address_check_callback` and `nep_141_storage_balance_callback`, mirroring the refund logic already present in `rlp_execute_callback`. Additionally, audit all other early-return `ExecuteResponse::success = false` paths that currently receive a `caller_deposit` parameter to ensure none of them drop it without refunding.

### Proof of Concept
1. An external relayer account calls `rlp_execute` on a user's Wallet Contract with a non-zero `attached_deposit`, targeting an emulated ERC-20 `ft_transfer` to a `receiver_id` that is not yet registered with the token contract (forcing the `nep_141_storage_balance_callback` path) [5](#0-4) .
2. `CallerDeposit::new` records the relayer's deposit since `predecessor_account_id != current_account_id` [1](#0-0) .
3. The token contract's `storage_balance_of` call fails (e.g., token account does not exist, or is temporarily out of gas/paused).
4. `nep_141_storage_balance_callback` receives `PromiseResult::Failed` and returns `ExecuteResponse { success: false, ... }` without issuing any refund promise for `caller_deposit` [6](#0-5) .
5. The relayer's originally attached NEAR deposit remains permanently in the Wallet Contract's account balance with no further code path to reclaim it.

    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
