### Title
Replay-window Check/Update race allows duplicate-packet decryption and replay bypass - ([File: connection_state.go])

### Summary
The reported Solana bug is a classic check-then-use (TOCTOU) flaw: `pre_swap` snapshots a balance, releases control to another actor, and later trusts the stale snapshot instead of atomically enforcing the invariant. Nebula's anti-replay logic in `ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` has the same structural flaw: the replay-window `Check` and the replay-window `Update` are two separate, independently-locked operations with an unlocked decrypt/verify step in between, so two concurrent packets carrying the same `messageCounter` can both pass `Check` before either calls `Update`.

### Finding Description
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement replay protection with this pattern: [1](#0-0) 

Note that `decryptLock` is acquired and released independently for `Check` and for `Update`, with the (comparatively expensive) AEAD decrypt/verify operation running *unlocked* in between:
1. Lock, `window.Check(messageCounter)`, unlock.
2. Decrypt/verify the packet (no lock held).
3. Lock, `window.Update(messageCounter)`, unlock.

`Bits.Check` only inspects state; it does not mark the counter as seen — that only happens in `Update`: [2](#0-1) 

Because nebula runs multiple UDP reader goroutines per configuration (`listen.routines`), packets for the same tunnel/`ConnectionState` can be processed concurrently on different goroutines. If an attacker captures one legitimate encrypted packet and replays it twice in quick succession (arriving on two different reader goroutines, or even the same one interleaved with another slow decrypt), both copies can call `Check` before either calls `Update`, since the lock is dropped between the two calls. Both `Check` calls observe "not yet seen" and return `true`, so both packets proceed to decrypt/verify and are accepted as legitimate — the second `Update` call will report a duplicate only after the fact, by which point the payload of the duplicate has already been delivered up the stack (written to the tun device or, for `VerifyRelay`, already forwarded/processed as a relay frame).

This mirrors the external report's root cause precisely: a value is read ("balance"/"counter has not been seen") to gate an operation, but the enforcement of that invariant (marking it consumed) is deferred to a second, separately-guarded step, leaving an exploitable window for a race between the check and the commit.

### Impact Explanation
This is a replay-protection bypass in the core Noise transport-layer read path. A successful race lets an attacker who can capture and replay a valid data-plane or relay packet cause it to be processed twice by the target node — defeating the guarantee `ReplayWindow`/`Bits` is specifically designed to provide (see also the CHANGELOG entries confirming past regressions in exactly this area: "Advance the replay window on relayed packets…", "Fix a race in relay state handling.", "Lock replay window updates so concurrent readers can't corrupt it."). Depending on payload semantics this can result in duplicate delivery of application traffic through the tun device or duplicate forwarding through a relay, i.e., a concrete traffic-replay condition reachable by any peer that can observe/replay ciphertext on the wire — no valid certificate or privileged position is required beyond already having an established tunnel to send crafted/replayed UDP frames to.

### Likelihood Explanation
Exploitability requires winning a narrow race between the unlocked `Check`→decrypt→`Update` sequence on two reader goroutines processing the same connection simultaneously. With multiple listener routines configured (a supported and common configuration) and the attacker fully controlling packet timing/duplication, this is a realistic, attacker-triggerable race rather than a purely theoretical one, though it is probabilistic rather than deterministic per attempt.

### Recommendation
Make replay-window check-and-mark atomic: hold `decryptLock` for the entire "check not seen → decrypt/verify → mark seen" sequence (or perform the `Update`/mark-as-seen step immediately after `Check` succeeds and only decrypt after the counter has been durably marked, rolling back on decrypt failure). At minimum, ensure no other packet with the same counter can pass `Check` while a prior packet with that counter is still being processed.

### Proof of Concept
1. Establish a tunnel between two nebula nodes with `listen.routines` > 1 (multiple UDP reader goroutines).
2. Capture a single legitimate encrypted data-plane (or relay) packet with `messageCounter = N`.
3. Simultaneously inject two copies of that exact packet into the receiver's UDP socket (e.g., via two concurrent `sendto` calls or by relying on kernel/OS scheduling to deliver both to separate reader goroutines within the same instant).
4. Observe that under an unlucky-but-reachable interleaving, both copies pass `window.Check(l, N)` (both see “unset”) before either calls `window.Update(l, N)`; both are then decrypted/verified and delivered, i.e., the payload for counter `N` is processed twice, or, on the relay path, an existing e2e test (`TestRelayReplayProtection`) is the correct place to strengthen assertions to catch this window by tightening the race (concurrent injects instead of sequential ones).

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
