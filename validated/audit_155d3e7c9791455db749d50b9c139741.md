## Analysis Result [1](#0-0) 

### Title
Floating-point Bancor-relay math in java-tron's native Exchange lets an unprivileged trader extract mispriced output via `ExchangeTransactionContract` - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
Java-tron's native decentralized exchange (`ExchangeCreate/Inject/Withdraw/TransactionContract`) implements a Bancor-style constant-relay AMM. The default, still-reachable trade path (`ExchangeCapsule.transaction()` with `hardenedCalc=false`) computes the swap output using `ExchangeProcessor`, which relies on `double`-precision `Math.pow()` arithmetic rather than exact integer/BigDecimal math. This is directly analogous to the Indexed Finance root cause: an AMM pool-math routine (`calcSingleOutGivenPoolIn()` there, `exchangeToSupply`/`exchangeFromSupply` here) computing an incorrect `tokenAmountOut`/`buyTokenQuant` due to flawed formula precision, which is reachable and exploitable by any transaction sender.

### Finding Description
`ExchangeTransactionActuator.execute()` — callable by any account holding tokens/TRX in an existing exchange pair — invokes `ExchangeCapsule.transaction(tokenID, tokenQuant, useStrictMath, allowHarden())` [2](#0-1) . Inside `ExchangeCapsule.transaction()`, when `hardenedCalc` is `false` (the historical/default behavior, gated by the `AllowHardenExchangeCalculation` proposal), the swap is delegated to `ExchangeProcessor` [3](#0-2) .

`ExchangeProcessor.exchangeToSupply()` and `exchangeFromSupply()` compute the swap using `double` floating point and `Maths.pow(...)`, then truncate to `long` via a `(long)` cast [4](#0-3) . Unlike Balancer/Indexed Finance's Solidity fixed-point `bpow`, this uses IEEE-754 double math for a virtual-supply Bancor relay with fixed exponents (`0.0005`/`2000.0`). Floating point `pow` is not guaranteed to round consistently across inputs of very different magnitude (e.g., extreme `tokenQuant` values relative to pool `balance`, or balances near the configured `ExchangeBalanceLimit`), so the computed `buyTokenQuant` can deviate from the true closed-form invariant result — the exact same class of bug as Indexed Finance's `calcSingleOutGivenPoolIn()` returning a wrong `tokenAmountOut`.

The codebase itself acknowledges this defect: a parallel `SafeExchangeProcessor` was added that redoes the same formula with `BigDecimal` and `StrictMathWrapper`, only used when `hardenedCalc`/`allowHarden()` is true [5](#0-4) [6](#0-5) . Until that chain parameter is enabled by committee proposal on a given network, `ExchangeTransactionActuator` — reachable directly from a single signed transaction with no privilege beyond owning assets — executes the imprecise floating point path.

### Impact Explanation
An attacker who can choose `tokenQuant` and repeatedly submit `ExchangeTransactionContract` trades against a pool (potentially amplified by borrowing assets, i.e., a flash-loan-equivalent sequence of trades within the trust boundary of a single owner-controlled exchange pool) can exploit floating-point rounding/precision loss in `exchangeToSupply`/`exchangeFromSupply` to receive `anotherTokenQuant` larger than the invariant should allow, extracting value from the pool's TRX/TRC10 reserves — analogous to the $9,925 loss in the Indexed Finance incident. Because `ExchangeInjectActuator`/`ExchangeWithdrawActuator` also read/write the same pool balances (with their own ratio-based math), skewed reserves from a mispriced swap compound further extraction opportunities for the same actor across subsequent inject/withdraw/trade calls.

### Likelihood Explanation
Medium: `ExchangeTransactionContract` is a standard, unprivileged transaction type reachable by any account (only requires holding the sell-side asset/TRX and fee), matching the scope of "order placer" style access. However, exploitability depends on whether a given chain has already enabled `AllowHardenExchangeCalculation` (which routes to `SafeExchangeProcessor` and avoids the floating point path) and on the specific pool balances/quant combinations needed to produce a favorable rounding error, which requires careful selection of trade sizes.

### Recommendation
- Confirm `AllowHardenExchangeCalculation` is enabled (or make the `SafeExchangeProcessor`/`BigDecimal` path the unconditional default) so `ExchangeProcessor`'s `double`-based `Math.pow` calculation is never reachable.
- Add invariant-based sanity checks after every swap (verify the Bancor relay's product/invariant does not increase beyond rounding tolerance) similar to the "Not precise enough" checks already present in `ExchangeWithdrawActuator`/`ExchangeInjectActuator` validation [7](#0-6) , but for `ExchangeTransactionActuator`.
- Consider deprecating the legacy `ExchangeProcessor` double-math implementation entirely.

### Proof of Concept
Not independently reproducible from static analysis alone — exploitation requires simulating specific pool balances/`tokenQuant` values against `ExchangeProcessor.exchange()` to find inputs where truncation/rounding of the double `pow()` computation yields a `buyTokenQuant` exceeding the value implied by the exact invariant, then submitting the corresponding `ExchangeTransactionContract`. This would need to be validated with numeric experimentation (e.g., a JUnit test driving `ExchangeCapsule.transaction()` with `hardenedCalc=false` across a range of balances/quantities and comparing against the `BigDecimal` result from `SafeExchangeProcessor`), which is out of scope for this read-only investigation.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
