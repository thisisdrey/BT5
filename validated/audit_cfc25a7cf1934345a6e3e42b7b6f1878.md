### Title
StackerDB chunk signatures are not bound to the target contract, enabling cross-contract chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the digest that a StackerDB writer signs from only `slot_id`, `slot_version`, and `data_hash` [1](#0-0) . It omits the `QualifiedContractIdentifier` (the specific StackerDB/contract the chunk is being written to). Because multiple StackerDB contracts can legitimately assign the *same* signer address to the *same* `slot_id` (e.g. per-reward-cycle signer message "lanes" `signers-<cycle>-<message_id>`, which share one signer set/slot assignment across several sibling contracts), a validly-signed chunk that was broadcast for contract A can be replayed verbatim by any unprivileged network peer into contract B, and it will pass every server-side check (`SlotMetadata::verify`, freshness, size) even though the signer never authorized that data for contract B.

### Finding Description
Chunk authenticity is decided by `SlotMetadata::verify()`, which recovers the pubkey hash from `auth_digest()` and compares it to the configured signer for `(contract_id, slot_id)`: [2](#0-1) 

The digest itself, however, is contract-agnostic: [3](#0-2) 

Both the write path (`StackerDBTx::try_replace_chunk`) and the network-relay validation path (`PeerNetwork::validate_received_chunk`) look up the expected signer *per contract* and then call this contract-agnostic `verify()`: [4](#0-3) [5](#0-4) 

Neither check re-derives or re-verifies which `contract_id` the signature was originally produced for — the contract is only used to look up "who is the expected signer for this slot," not incorporated into what was actually signed. If the same signer address is assigned the same `slot_id` in two different StackerDB contracts (which the signer-message "lane" contracts intentionally do, per `get_signers_db_signer_set_message_id` in `libsigner/src/events.rs`, which maps several sibling `signers-<cycle>-<id>` contracts to the same underlying signer set), then an attacker who merely observes a legitimately-signed chunk broadcast on one contract can resubmit the identical `(slot_id, slot_version, sig, data)` tuple against a different sibling contract. `SlotMetadata::verify()` will succeed against the wrong contract because the signature never committed to a contract identifier in the first place, and the write will be accepted as long as the target contract's slot version is behind the replayed version.

This is directly analogous to the reported DKIM bug class: an equality check ("authenticated" vs. "authenticated for *this* namespace") is broken because the identifier/digest used for authentication omits a field that should scope the authorization (there, `sigMeta`/`canonizedHeaders` needed to bind to the specific recovery action; here, the signed digest needs to bind to the specific StackerDB contract).

### Impact Explanation
This allows an unprivileged remote attacker (no signer key, no admin role) to write attacker-chosen-but-signer-authored data into a StackerDB slot in a contract other than the one it was authored for, overwriting the "canonical" latest chunk for that slot/contract with stale or out-of-context data. Depending on which sibling contract/lane is targeted, this can desynchronize signer message routing (a message intended for one signing round/lane appears as canonical in another), corrupt state that other nodes replicate as ground truth via StackerDB gossip, and propagate this forged/misattributed data network-wide via the normal StackerDB push/relay mechanism (`PeerNetwork::validate_received_chunk`, `handle_unsolicited_StackerDBPushChunk`). This matches the "High" impact bucket: serving non-canonical/mismatched (cross-contract) state as canonical, and forged-data propagation across the network, all without requiring any secret key or elevated privilege.

### Likelihood Explanation
Medium. It requires (a) two StackerDB contracts that intentionally reuse the same signer→slot assignment (the signer-message lane contracts for a given reward cycle are the clearest example, since they are explicitly designed to share a signer set/slot layout across message-id lanes), and (b) the target contract's current slot version being behind the replayed chunk's version so the freshness check (`slot_version <= slot_validation.version`) doesn't reject it. Both conditions are realistic in normal operation of the signer StackerDB lanes, and the attacker requires no privileged material — only passive observation of any chunk broadcast on the p2p network or fetched via the RPC/StackerDB APIs, which are unauthenticated read operations by design.

### Recommendation
Include the target `QualifiedContractIdentifier` (or a fixed, canonical contract-scoping value) in `SlotMetadata::auth_digest()` so that a signature is only valid for the specific StackerDB it was produced for. This requires a wire/consensus-compatible migration: e.g., extend `auth_digest()` to hash the contract identifier bytes in addition to `slot_id`, `slot_version`, and `data_hash`, and correspondingly update `sign()`/`verify()` call sites (`StackerDBTx::try_replace_chunk`, `PeerNetwork::validate_received_chunk`) to pass in the contract identifier being written to, rejecting any chunk whose signature was computed against a different contract scope.

### Proof of Concept
1. Identify two sibling StackerDB contracts that share a signer set/slot assignment for the same reward cycle — e.g. `signers-<cycle>-1` and `signers-<cycle>-2` — as mapped in `get_signers_db_signer_set_message_id` (`libsigner/src/events.rs`).
2. Passively capture a legitimately-signed `StackerDBChunkData` (`slot_id`, `slot_version`, `sig`, `data`) broadcast for `signers-<cycle>-1` by any signer, via the p2p `StackerDBPushChunk` message or the `/v2/stackerdb/.../<slot_id>` read endpoint.
3. Confirm the same signer address owns the same `slot_id` in `signers-<cycle>-2`, and that its currently stored slot version is `< slot_version` from step 2 (true for a freshly-created or lagging lane).
4. Submit the exact same `(slot_id, slot_version, sig, data)` tuple to `signers-<cycle>-2` via `POST /v2/stackerdb/<contract>/chunks` (or by pushing a `StackerDBPushChunk` p2p message for that contract).
5. `SlotMetadata::verify()` (`libstackerdb/src/libstackerdb.rs:181-193`) succeeds because `auth_digest()` never referenced the contract; `try_replace_chunk`/`validate_received_chunk` accept and store the chunk as the new canonical latest chunk for `signers-<cycle>-2`'s slot, even though the signer never authored data for that contract.

```rust
    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }
```

```rust
    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
```
