### Title
Allowance double-spend race on `DepositToken.approve` lets a spender steal locked-collateral claims - (File: contracts/DepositToken.sol)

### Summary
CVE-2020-15396 is a TOCTOU race: `faxsetup` performs a privileged `chown` on a path inside a user-owned directory, and the attacker wins the race by swapping the path's target between the check and the privileged write. The on-chain analog in Metronome is the ERC-20 allowance race on `DepositToken.approve`: an existing spender races the owner's `approve(spender, newAmount)` transaction, spending the old allowance in a front-run transaction and then spending the new allowance once the owner's `approve` lands. `approve` unconditionally overwrites `allowance[owner][spender]` with `amount_` (contracts/DepositToken.sol:187-190, 432-438), while `transferFrom` only checks the *current* allowance at execution time (contracts/DepositToken.sol:357-376). Since msdTOKEN represents withdrawable collateral (`_withdraw` burns the deposit token and pulls underlying from `Treasury`, contracts/DepositToken.sol:536-554), the double-spent allowance converts directly into stolen collateral.

### Finding Description
- `DepositToken.approve` sets the allowance to an absolute value with no requirement that it go through `0` first: `_approve(_msgSender(), spender_, amount_)` (contracts/DepositToken.sol:187-190).
- `DepositToken.transferFrom` debits `allowance[sender_][spender]` based on the value live at execution time (contracts/DepositToken.sol:364-371).
- Attack: Alice has approved attacker EOA for `N` msdMET. Alice sends `approve(attacker, M)` (e.g., to reduce or replace it). The attacker front-runs with `transferFrom(alice, attacker, N)`, letting Alice's tx then set allowance back to `M`, and back-runs with `transferFrom(alice, attacker, M)` — total extracted `N + M`.
- The stolen msdTOKEN is immediately redeemable via `withdraw` (subject to `unlockedBalanceOf`, contracts/DepositToken.sol:383-398) for underlying from `Treasury.pull`, or via `NativeTokenGateway.withdraw` for ETH (contracts/NativeTokenGateway.sol:61-70). `transferFrom` itself is `nonReentrant` but that does not serialize separate transactions in a block; the race is cross-transaction, which is exactly what front-running enables on-chain.
- Mitigation helpers exist (`increaseAllowance`/`decreaseAllowance`, contracts/DepositToken.sol:195-203, 255-259) but `approve` remains publicly callable and unsafe, same class as OpenZeppelin's documented ERC-20 race.
- Note: the same pattern is present in `SyntheticToken.approve`/`transferFrom` (`contracts/SyntheticToken.sol`, same storage layout in `contracts/storage/SyntheticTokenStorage.sol`), so the finding covers both token types.

### Impact Explanation
Direct theft of user funds: the attacker obtains up to `N + M` msdTOKEN instead of `M`, and can withdraw the excess as underlying collateral (WETH/USDC/etc.) or msUSD/msETH, draining value Alice never intended to spend.

### Likelihood Explanation
Requires a victim to send a non-zero → non-zero `approve` change while a prior allowance is still live, and the attacker must win mempool ordering (front-run + back-run). On L2s with public/private mempools this is a known, reproducible pattern; bundlers make the sandwich atomic. Likelihood is moderate: conditional on victim behavior but fully deterministic once ordering is won.

### Recommendation
Make `approve` require `allowance == 0 || amount_ == 0` (OpenZeppelin `safeApprove` semantics), or remove `approve` and keep only `increaseAllowance`/`decreaseAllowance`. Apply identically to `SyntheticToken`.

### Proof of Concept
Hardhat (adapted from `test/DepositToken.test.ts`):

```ts
// given: alice approved attacker for N
await metDepositToken.connect(alice).approve(attacker.address, N)

// attacker front-runs alice's pending approve(attacker, M)
await metDepositToken.connect(attacker).transferFrom(alice.address, attacker.address, N)

// alice's tx executes (simulated): allowance set to M
await metDepositToken.connect(alice).approve(attacker.address, M)

// attacker spends the "new" allowance too
await metDepositToken.connect(attacker).transferFrom(alice.address, attacker.address, M)

// attacker redeems stolen msdTOKEN for underlying
await metDepositToken.connect(attacker).withdraw(N.add(M), attacker.address)
expect(await met.balanceOf(attacker.address)).eq(N.add(M))
```

Expected: attacker ends with `N + M` underlying withdrawn from `Treasury`, while Alice only ever authorized `M` post-change — invariant broken: allowance accounting no longer bounds total spend.
