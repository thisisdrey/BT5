### Title
Permissionless `TransferToGasKeyAction` can push a victim's gas-key balance above `MAX_BALANCE_TO_BURN`, permanently blocking `DeleteKey`/`DeleteAccount` on that key - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
The Loop Finance report describes an ERC-4626 vault where a permissionless deposit (backrun) can push a shared accounting value (`totalSupply`) across a hard-coded threshold (`MIN_SHARES`), causing a subsequent, legitimate state-changing call (withdrawal) from another user to permanently revert unless a third party intervenes. The nearcore analog is `TransferToGasKeyAction`: any account can permissionlessly deposit funds into another account's gas key, and once the gas-key balance exceeds the hard-coded `GasKeyInfo::MAX_BALANCE_TO_BURN` cap, both `DeleteKey` and `DeleteAccount` on that key revert with `GasKeyBalanceTooHigh`, until the owner separately calls `WithdrawFromGasKey`.

### Finding Description
`action_transfer_to_gas_key` in [1](#0-0)  adds `action.deposit` to `gas_key_info.balance` for the target `account_id`/`public_key` with no check that the predecessor is the account itself. The Rosetta adapter's handling of `TransferToGasKeyOperation`, which sets a distinct `receiver_account_id` (the gas-key owner) and a distinct `sender_account_id` (`InitiateTransferToGasKeyOperation`), confirms this action behaves like an ordinary `Transfer` in that it can be issued by one account and land on another account's gas key: [2](#0-1) . `validate_transfer_to_gas_key_action` only checks that the `GasKeys` protocol feature is enabled - it applies no restriction requiring `predecessor_id == receiver_id`: [3](#0-2) .

The gas-key balance is capped by design: `delete_gas_key` refuses to delete a gas key whose balance exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN`, returning `ActionErrorKind::GasKeyBalanceTooHigh` instead: [4](#0-3) . The same cap is enforced again at account-deletion time, which sums *all* gas-key balances on the account and fails the whole `DeleteAccount` action if the sum is too high: [5](#0-4) . This mirrors the code anchor documented in the protocol spec: "Account deletion sums all gas-key balances against the same threshold" [6](#0-5) .

This is structurally identical to the `StakingLPEth` bug class: a hard threshold check (`MIN_SHARES` there, `MAX_BALANCE_TO_BURN` here) gates a legitimate state-changing operation (withdraw there, delete-key/delete-account here), and an unprivileged third party can permissionlessly move the checked value across that threshold via an ordinary deposit action, without the consent of the account being affected.

### Impact Explanation
An attacker can grief any account that owns a gas key by repeatedly calling `TransferToGasKeyAction` against that key until its balance exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN`. From that point on:
- The owner's `DeleteKey` action on that gas key always reverts (`GasKeyBalanceTooHigh`).
- The owner's `DeleteAccount` action reverts as well if this (or the sum of all) gas-key balance(s) crosses the same cap.

This is a availability/DoS impact on the victim's ability to remove a key or delete their account - the funds are not immediately stolen, but the account's key-management/account-deletion capability is bricked until the owner separately issues `WithdrawFromGasKey` to bring the balance back under the cap (assuming that action is restricted to the owner's own signer). Because any unprivileged account can trigger this griefing at negligible cost (a small `TransferToGasKeyAction` deposit) and repeat it, it satisfies the "DoS / permanent-until-remediated locking" bug class analogous to the original Medium-severity finding.

### Likelihood Explanation
Likelihood is moderate-to-high: `TransferToGasKeyAction` requires no special permission on the receiver side (unlike `AddKey`/`DeleteKey`/`Stake`/`DeleteAccount`, which are restricted to `predecessor_id == receiver_id` per the action model), and the deposit amount needed to cross `MAX_BALANCE_TO_BURN` is a fixed, small, attacker-known constant. Any account holder who has published a gas key (a `GasKeys`-protocol-version feature) is a potential target, and the attack is purely economic (cost of one deposit transaction) rather than requiring any privileged role, mempool position, or validator collusion.

### Recommendation
- Consider requiring `predecessor_id == receiver_id` for `TransferToGasKeyAction`, consistent with other self-authorizing actions (`AddKey`, `DeleteKey`, `Stake`, `DeleteAccount`), so a gas key can only be funded by its own account.
- Alternatively, remove/relax the `MAX_BALANCE_TO_BURN` hard-revert behavior in `delete_gas_key`/`action_delete_account`: e.g., allow deletion to always succeed by burning (or refunding) the excess balance rather than reverting the whole action when the cap is exceeded.
- If third-party funding of gas keys is an intentional design goal, cap the *effective* balance used for the burn check at `MAX_BALANCE_TO_BURN` and refund any excess to `beneficiary_id`/the depositor instead of blocking deletion.

### Proof of Concept
1. Victim account `alice.near` adds a gas key via `AddKey` with `AccessKey::gas_key_full_access(...)`.
2. Attacker `mallory.near` sends `Action::TransferToGasKey(TransferToGasKeyAction { public_key: alice_gas_key, deposit: <amount> })` targeting `alice.near`'s gas key, repeating/sizing the deposit so the cumulative `gas_key_info.balance` exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN` (see `runtime/runtime/src/access_keys.rs:103`, `runtime/runtime/src/actions.rs:355`).
3. `alice.near` submits `DeleteKey` for that public key: the transaction fails with `ActionErrorKind::GasKeyBalanceTooHigh` (`access_keys.rs:103-111`).
4. `alice.near` submits `DeleteAccount`: it likewise fails because `compute_gas_key_balance_sum` exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN` (`actions.rs:354-363`).
5. `alice.near` must issue an additional `WithdrawFromGasKey` transaction to reduce the balance below the threshold before either `DeleteKey` or `DeleteAccount` can succeed - the attacker forced an unwanted, unplanned remediation transaction on the victim, purely at the cost of a small deposit.

Note: I was not able to fully verify from the indexed code whether `WithdrawFromGasKeyAction` execution enforces `predecessor_id == receiver_id` (i.e., whether only the account owner, via their own signer, can withdraw) — this constrains whether the griefing is self-recoverable or could compound further. Confirming that authorization check (likely enforced in `runtime/runtime/src/verifier.rs` or the receipt/action dispatch path rather than in `action_validation.rs`) would require a Devin session with full repository access, since the indexed snippets did not show explicit self-only enforcement for `TransferToGasKey`/`WithdrawFromGasKey`.

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
