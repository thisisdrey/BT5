### Title
Slow-loris stream starvation via strictly sequential per-connection stream processing in `handle_connection` - ([File: streamer/src/nonblocking/quic.rs])

### Summary
`handle_connection` processes uni-directional QUIC streams on a TPU connection **strictly sequentially**: it calls `connection.accept_uni()`, then fully drains that one stream (until `Finished`, an error, or a `wait_for_chunk_timeout` timeout) before looping back to accept the next stream. An unprivileged attacker can hold a single stream (or all streams up to the connection's allotted `max_concurrent_uni_streams`) open indefinitely by sending one byte every `wait_for_chunk_timeout - ε`, which resets the per-read timeout on each call and never triggers the 30s connection idle timeout, permanently blocking the connection's ability to accept/process any further legitimate stream.

### Finding Description
In `streamer/src/nonblocking/quic.rs`, `handle_connection` runs this loop: [1](#0-0) 

then for the accepted `stream` it enters an inner loop that repeatedly calls `tokio::time::timeout(wait_for_chunk_timeout, stream.read_chunks(&mut chunks))`: [2](#0-1) 

Only once this inner loop exits (via `StreamState::Finished`, a read error, or an actual timeout with no data — `Err(_)`) does control return to the outer `'conn` loop to call `connection.accept_uni()` again: [3](#0-2) 

Because a new `tokio::time::timeout` future is created for every individual `read_chunks()` call, any successful partial read—no matter how small—resets the timer. The comment at line 648-650 even documents this: the timeout is meant to catch a peer that "stops sending," not one that trickles data. If the attacker writes 1 byte on the currently-accepted stream every interval slightly shorter than `wait_for_chunk_timeout` (`DEFAULT_WAIT_FOR_CHUNK_TIMEOUT` = 2s, per `streamer/src/nonblocking/quic.rs:54`), the inner loop never times out and never receives the terminating zero-length chunk (`n_chunks == 0`) that would mark `StreamState::Finished` in `handle_chunks`.

Since this drains happen inline in the *single task* that owns the connection (spawned once per connection in `setup_connection` via `tasks.spawn(handle_connection(...))`, `streamer/src/nonblocking/quic.rs:521-531`), the connection's `accept_uni()` is never called again while the attacker's stream is being "processed." This means:
- The QoS layer's `on_new_stream`/`on_stream_accepted` throttling (`streamer/src/nonblocking/swqos.rs:445-516`, `streamer/src/nonblocking/simple_qos.rs:352-420`) is irrelevant here — it only governs how fast *new* streams are admitted, but the connection task never even reaches `accept_uni()` again to admit a new stream.
- `QUIC_MAX_TIMEOUT` (30s idle timeout, `streamer/src/quic.rs:38`) never fires because the connection is not idle — the attacker keeps sending traffic.
- No mechanism enforces a maximum *total* lifetime for a single stream regardless of incremental activity; `max_stream_data_bytes` only bounds total bytes, not time (`handle_chunks`, `streamer/src/nonblocking/quic.rs:748-755`).

Consequently, an attacker opening one or more uni-streams and drip-feeding 1 byte every `wait_for_chunk_timeout - ε` on the currently-accepted stream can block that connection's stream-processing pipeline forever, using negligible bandwidth (< 1 byte/sec). No legitimate transaction submitted on a *new* stream on that connection will ever be accepted/processed, because `accept_uni()` is never called again.

### Impact Explanation
This is a slow-loris-style resource-starvation of TPU QUIC stream capacity for a given connection/source: the attacker occupies a connection slot (and its dedicated tokio task, held for the connection's lifetime) with a single dripping stream, permanently denying that connection's ability to process any further transaction stream. Multiplied by `max_connections_per_unstaked_peer` (default 8, `DEFAULT_MAX_QUIC_CONNECTIONS_PER_UNSTAKED_PEER`, `streamer/src/quic.rs:41`) an attacker can tie up all connection slots it is permitted, and because `open_unstaked_connections`/`max_unstaked_connections` (default 2000, `streamer/src/quic.rs:48`) is a shared global pool, many such connections from few sources reduce total connection capacity available to legitimate unstaked traffic — a bounded-resource/QoS-evasion class DoS matching the described scoped impact.

### Likelihood Explanation
Fully reachable by an unprivileged, unstaked remote client — no stake, gossip participation, or special config is required, only the ability to open a QUIC connection to the public TPU port and open uni-streams. The trick (send < 1 chunk before `wait_for_chunk_timeout`, never send the terminating empty chunk) is trivial to implement with any QUIC client library and costs the attacker essentially zero bandwidth/CPU, making it highly repeatable and cheap to sustain indefinitely.

### Recommendation
Enforce a bounded *total* stream lifetime independent of per-chunk activity (e.g., track `accum.start_time` in `PacketAccumulator` and abort the stream if `Instant::now() - start_time` exceeds a max duration, regardless of trickling reads), and/or decouple stream acceptance from stream draining so `accept_uni()` can keep being polled (e.g., spawn a bounded number of concurrent per-stream reader tasks instead of processing one stream fully before accepting the next) so that a single slow/malicious stream cannot block acceptance of new streams on the same connection.

### Proof of Concept
```rust
// streamer/src/nonblocking/quic.rs (integration test, alongside test_quic_stream_timeout)
#[tokio::test(flavor = "multi_thread")]
async fn test_quic_stream_slowloris_blocks_new_streams() {
    agave_logger::setup();
    let SpawnTestServerResult { join_handle, receiver, server_address, stats, cancel } =
        setup_quic_server(None, QuicStreamerConfig::default_for_tests(), SwQosConfig::default());

    let conn = make_client_endpoint(&server_address, None).await;

    // Open one stream and drip 1 byte just under DEFAULT_WAIT_FOR_CHUNK_TIMEOUT repeatedly,
    // never sending the terminating zero-length chunk.
    let mut slow_stream = conn.open_uni().await.unwrap();
    let drip_interval = DEFAULT_WAIT_FOR_CHUNK_TIMEOUT - Duration::from_millis(200);
    let attacker_task = tokio::spawn(async move {
        loop {
            if slow_stream.write_all(&[0u8]).await.is_err() { break; }
            tokio::time::sleep(drip_interval).await;
        }
    });

    // Give the connection task time to accept & get stuck on the slow stream.
    tokio::time::sleep(Duration::from_secs(1)).await;

    // Now attempt a legitimate, complete transaction on a NEW stream on the SAME connection.
    let mut legit_stream = conn.open_uni().await.unwrap();
    legit_stream.write_all(&[1u8; 128]).await.unwrap();
    legit_stream.finish().unwrap();

    // Expect it to arrive quickly if fairness holds; assert it does NOT arrive within
    // a reasonable bound, proving starvation.
    let got_packet = tokio::time::timeout(Duration::from_secs(5), async {
        loop {
            if let Ok(batch) = receiver.try_recv() {
                if !batch.is_empty() { return true; }
            }
            tokio::time::sleep(Duration::from_millis(100)).await;
        }
    }).await;

    assert!(got_packet.is_err(), "legitimate stream was starved by slow-loris stream");

    attacker_task.abort();
    cancel.cancel();
    join_handle.await.unwrap();
}
```
Expected result on the current implementation: the legitimate stream's packet never arrives (timeout fires) because `handle_connection`'s outer loop never returns to `connection.accept_uni()` while the attacker's stream is still dripping.
