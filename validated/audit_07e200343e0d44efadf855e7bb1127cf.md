### Title
`lookup_peer()` inverts the neighbor-key expiry check, pre-loading expired public keys as "known" while treating still-valid keys as unknown - ([File: stackslib/src/net/p2p.rs])

### Summary
`PeerNetwork::lookup_peer()` is documented to return the stored `Neighbor` record only when its public key is **unexpired**, but the actual comparison is inverted: it returns `Some(neighbor)` when the key **has already expired**, and `None` when the key is still valid. This equality inversion is used directly in `register_peer()` to decide what public key to pre-attach to a brand-new inbound/outbound `ConversationP2P` before any handshake has been received or verified.

### Finding Description
The function is: [1](#0-0) 

```rust
/// Get the neighbor if we know of it and it's public key is unexpired.
fn lookup_peer(
    &self,
    cur_block_height: u64,
    peer_addr: &SocketAddr,
) -> Result<Option<Neighbor>, net_error> {
    ...
    match neighbor_opt {
        None => Ok(None),
        Some(neighbor) => {
            if neighbor.expire_block < cur_block_height {
                Ok(Some(neighbor))
            } else {
                Ok(None)
            }
        }
    }
}
```

`neighbor.expire_block < cur_block_height` is true exactly when the neighbor's stored public key has **already expired** (the current burn height has passed the key's expiry block). The doc comment states the opposite intent ("unexpired"), and the branches are swapped: an already-expired key causes `Some(neighbor)` (treated as "known good"), while a still-valid, unexpired key causes `None` (treated as "unknown").

This return value is consumed immediately by `register_peer()`: [2](#0-1) 

```rust
let neighbor_opt = match self.lookup_peer(self.chain_view.burn_block_height, &client_addr) {
    Ok(neighbor_opt) => neighbor_opt,
    ...
};
...
let (pubkey_opt, neighbor_key) = match neighbor_opt {
    Some(neighbor) => (Some(neighbor.public_key.clone()), neighbor.addr),
    None => (
        None,
        NeighborKey::from_socketaddr(...),
    ),
};
...
new_convo.set_public_key(pubkey_opt);
```

Because of the inversion:
- When the on-file neighbor's key is **still valid/current** (the canonical, non-expired identity), `lookup_peer` discards it (`None`), so the new conversation is initialized with **no** known public key.
- When the on-file neighbor's key has **actually expired** (non-canonical/stale credential material), `lookup_peer` returns it, and `register_peer` pre-loads that stale key onto the brand-new socket/conversation via `new_convo.set_public_key(pubkey_opt)`, *before* any handshake message from the actual remote peer at that address/port has been received or authenticated.

This breaks the intended equality "pre-attach a key to a conversation only if it is still the canonical, currently-valid identity for that address." Instead, the code serves an explicitly-expired (non-canonical) key as if it were the canonical current identity of whoever connects next from that `SocketAddr`, while genuinely canonical (still-valid) identities are dropped and forgotten by this path.

### Impact Explanation
This falls into the "serving non-canonical state as canonical" category: a peer's already-expired public key (which the protocol's own expiry semantics say should no longer be trusted) is reused as the presumed identity for a fresh, not-yet-authenticated connection from the same `SocketAddr`. Any new/legitimate remote peer that connects from that IP:port with a fresh handshake now has its conversation's authentication state anchored to a stale, expired key rather than starting from a clean, unauthenticated state — inverting the exact safety property the expiry mechanism (`expire_block`) is supposed to provide. Meanwhile, valid/current neighbor records are silently discarded on every new connection attempt, degrading the peer database's utility for authenticated peers.

### Likelihood Explanation
This path executes unconditionally on every new inbound or outbound socket registration (`register_peer`), for any address that has a prior `Neighbor` record in the peer database — no attacker action beyond normal peer churn (waiting for a neighbor's `expire_block` to pass, or reconnecting from an address with previously-expired peer state) is required to trigger the inverted branch.

### Recommendation
Fix the comparison to match the documented intent, e.g.:
```rust
if neighbor.expire_block >= cur_block_height {
    Ok(Some(neighbor))
} else {
    Ok(None)
}
```
so that only neighbors with a still-valid (unexpired) key are returned and pre-attached to new conversations, and expired entries are treated as unknown.

### Proof of Concept
1. Node A previously handshakes with a peer at address `X:port`, storing a `Neighbor` record with `expire_block = E`.
2. Burnchain advances such that `chain_view.burn_block_height > E` (the key is now expired per protocol semantics).
3. Any TCP connection arrives at Node A claiming to originate from `X:port` (attacker-controlled or legitimately a different peer that now holds that address).
4. `register_peer()` calls `lookup_peer(chain_view.burn_block_height, X:port)`; since `E < cur_block_height`, the inverted check returns `Some(neighbor)` with the **stale/expired** public key.
5. `new_convo.set_public_key(Some(stale_pubkey))` pre-authenticates the conversation with the expired identity before any handshake is validated, contrary to the documented "unexpired" guarantee. [3](#0-2)
