### Title
Per-connection (not per-IP) stream throttling in unstaked QUIC QoS allows multiplying admitted stream throughput via connection churn - ([File: streamer/src/nonblocking/swqos.rs])

### Summary
The unstaked stream-rate limit (`max_unstaked_load_in_throttling_window`) is enforced per `ConnectionStreamCounter`, which is created fresh for every new QUIC connection rather than being aggregated per source IP. An unstaked attacker who opens multiple connections from the same IP (each staying within `max_connections_per_unstaked_peer`) obtains a separate throttling budget per connection, multiplying total admitted streams for that IP within a single `STREAM_THROTTLING_INTERVAL_MS` window.

### Finding Description
`SwQos::try_add_connection` stores per-connection state in `ConnectionTable<ConnectionStreamCounter>`, creating a brand-new `ConnectionStreamCounter::new()` for each accepted connection [1](#0-0) . The per-IP limit enforced there is only a *connection count* limit (`max_connections_per_unstaked_peer` / `max_connections_per_unstaked_peer`) [2](#0-1) , not a stream-rate limit.

Stream-rate throttling itself happens in `on_new_stream`, which computes `max_streams_per_throttling_interval` from `StakedStreamLoadEMA::available_load_capacity_in_throttling_duration` and then calls `throttle_stream` against the connection's own `stream_counter` [3](#0-2) . For `ConnectionPeerType::Unstaked`, the available capacity is a fixed global constant (`max_unstaked_load_in_throttling_window = MAX_UNSTAKED_TPS * STREAM_THROTTLING_INTERVAL_MS / 1000`), independent of how many connections the same IP has open [4](#0-3) .

`throttle_stream` and `ConnectionStreamCounter::reset_throttling_params_if_needed` track `stream_count` and `last_throttling_instant` purely per `Arc<ConnectionStreamCounter>` instance [5](#0-4) . Because this counter is scoped to a single connection object (created in `cache_new_connection` and dropped on `remove_connection`), closing a connection and opening a new one from the same IP yields a brand-new counter starting at zero, with no memory of the previous connection's stream consumption.

Thus, an unstaked peer that opens `N` connections concurrently or sequentially (churning faster than `STREAM_THROTTLING_INTERVAL_MS` = 100ms) can get `N × max_unstaked_load_in_throttling_window` streams admitted per 100ms window from a single IP, up to the bound `max_connections_per_unstaked_peer` and the global `max_unstaked_connections` table cap. The `StakedStreamLoadEMA` load tracking (`increment_load`) only tracks staked load for the EMA (`if peer_type.is_staked()`), so unstaked amplification does not even feed back into the staked/unstaked global load model [6](#0-5) .

### Impact Explanation
This is a QoS evasion bug: the QUIC ingress QoS design intends stream admission fairness to be enforced against the connecting IP/peer, but the enforcement primitive (`ConnectionStreamCounter`) is keyed to an ephemeral connection object instead of the peer identity/IP. An attacker can obtain a multiple of the intended unstaked-per-IP stream budget by churning short-lived connections, consuming disproportionate leader TPU stream-processing capacity relative to other unstaked/staked peers, at the cost of connection-setup overhead (QUIC handshake). The impact is bounded (still capped by `max_connections_per_unstaked_peer` and total unstaked connection table capacity), so this is a QoS fairness/rate-limit evasion finding rather than an unbounded resource exhaustion or consensus-safety bug.

### Likelihood Explanation
Preconditions: the attacker must be able to open and close QUIC connections to the leader's TPU port faster than the 100ms `STREAM_THROTTLING_INTERVAL_MS` window, which only requires ordinary network access and a QUIC client capable of connection churn — no stake or special privilege is required. This is straightforward and repeatable; the only cost is the QUIC handshake overhead per connection, which is cheap relative to the throughput gain.

### Recommendation
Move stream-rate throttling state (`stream_count` / `last_throttling_instant`) from being keyed per-connection (`Arc<ConnectionStreamCounter>` owned by the connection) to being keyed per source identity (e.g., per IP for unstaked, per pubkey for staked), stored in a shared table that persists across connection open/close for that peer within the throttling window, similar to how `ConnectionTable` already keys connections by `ConnectionTableKey::new(remote_addr.ip(), pubkey)`.

### Proof of Concept
Integration test plan (in `streamer/src/nonblocking/swqos.rs` or a new test module using `SwQos`):
1. Construct an `SwQos` with `SwQosConfig { max_connections_per_unstaked_peer: 4, .. }` and a small `max_streams_per_ms` so `max_unstaked_load_in_throttling_window` is a known small number (e.g. 20).
2. From one fixed source IP, open 4 sequential unstaked connections in rapid succession (faster than `STREAM_THROTTLING_INTERVAL_MS`), each sending exactly `max_unstaked_load_in_throttling_window` streams via `on_new_stream`, then closing the connection (`remove_connection`) before opening the next.
3. Assert that `throttle_stream` never blocks/sleeps within any single connection (each connection consumes its own fresh budget), yet the aggregate stream count admitted for that IP across all 4 connections within the 100ms window is `4 × max_unstaked_load_in_throttling_window`, exceeding the intended single-IP budget of `max_unstaked_load_in_throttling_window`.
4. Expected (post-fix) assertion: total streams admitted for the IP across all its connections within one `STREAM_THROTTLING_INTERVAL` stays bounded by `available_load_capacity_in_throttling_duration(Unstaked, total_stake)`, not multiplied by connection count.

            ConnectionPeerType::Staked(stake) => {

                    // 1 is added to `max_unstaked_load_in_throttling_window` to guarantee that staked
                    // clients get at least 1 more number of streams than unstaked connections.
                    self.max_staked_load_in_throttling_window
                        .saturating_mul(stake)
                        .checked_div(total_stake)
                        .unwrap_or(self.max_unstaked_load_in_throttling_window + 1)
                        .max(self.max_unstaked_load_in_throttling_window + 1)
                } else {
                    self.max_staked_load_in_throttling_window
                }
            }

pub struct ConnectionStreamCounter {
    pub(crate) stream_count: AtomicU64,
    last_throttling_instant: RwLock<tokio::time::Instant>,
}

impl OpaqueStreamerCounter for ConnectionStreamCounter {}

impl ConnectionStreamCounter {
    pub fn new() -> Self {
        Self {
            stream_count: AtomicU64::default(),
            last_throttling_instant: RwLock::new(tokio::time::Instant::now()),
        }
    }

    /// Reset the counter and last throttling instant and
    /// return last_throttling_instant regardless it is reset or not.
    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }
}

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }
}
