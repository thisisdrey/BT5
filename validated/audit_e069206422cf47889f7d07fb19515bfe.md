Audit Report

## Title
Transaction fees payable in non-native assets are priced from the instantaneous AMM spot reserves with no TWAP or bound, letting a user manipulate `pallet-asset-conversion` pool state within a block to underpay fees - ([File: substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs])

## Summary
`SwapAssetAdapter::withdraw_fee`, `can_withdraw_fee`, and `correct_and_deposit_fee` all price non-native fee-asset amounts via `S::quote_price_tokens_for_exact_tokens`/`quote_price_exact_tokens_for_tokens`, which resolve to `pallet_asset_conversion::Pallet`'s quote functions reading the pool's current reserves at extrinsic-execution time. Because `pallet-asset-conversion` pools are permissionlessly created and their reserves are freely adjustable by any signed account via ordinary swap/liquidity calls, an attacker can skew a pool's reserves with one extrinsic, pay an artificially cheap fee with a following extrinsic in the same block, and then reverse the skew, underpaying the intended native-equivalent transaction fee.

## Finding Description
`SwapAssetAdapter::withdraw_fee` computes `asset_fee` via `S::quote_price_tokens_for_exact_tokens(asset_id, A::get(), fee, true)` and withdraws exactly that quoted amount from the payer, with no caller-supplied bound: [1](#0-0)  `correct_and_deposit_fee` likewise re-quotes the refund leg with `S::quote_price_exact_tokens_for_tokens(A::get(), asset_id, refund_amount, true)` at settlement time using then-current reserves: [2](#0-1)  Both quote functions are pure functions of the pool's live reserve balances (`get_reserves`), and the pallet's own doc-comment on `quote_price_exact_tokens_for_tokens` explicitly acknowledges the quote reflects a moment-in-time price that can move before execution, recommending `amount_out_min`/`amount_in_max` for slippage control on ordinary swap calls — a control that `SwapAssetAdapter` never exposes to the fee payer. Since `pallet-asset-conversion`'s swap and liquidity calls are ordinary signed extrinsics reachable by any account, and a block's extrinsics from the same account execute sequentially with each mutation visible to the next, an attacker fully controls a same-block sandwich: skew reserves, pay a fee priced off the skewed reserves, then unwind the skew. No slippage/floor protection exists anywhere in `payment.rs` for the fee-payer's own quote (verified: no `max_asset_fee`/slippage bound exists in this adapter).

## Impact Explanation
This allows an unprivileged user to systematically underpay the fee-asset cost of executing their own extrinsics relative to the price a non-manipulated pool would produce, extracting value from the block author / fee recipient (`OU::on_unbalanceds`) and from liquidity providers who absorb the AMM slippage — matching the impact gate's "public underpriced work that degrades block production" category, since fee payment via `ChargeAssetTxPayment` is a mandatory code path whenever a chain configures a non-native fee asset with `SwapAssetAdapter`.

## Likelihood Explanation
Exploitation requires only ordinary signed-extrinsic access to a permissionless `pallet-asset-conversion` pool for the configured fee asset — no governance, validator, or privileged role is needed, and the attacker fully controls extrinsic ordering for their own account/nonce sequence within a block. Effectiveness scales inversely with pool depth (thinner pools are more exploitable), but the underlying mechanism requires nothing beyond what every user can already do.

## Recommendation
Do not price mandatory non-native fee conversion purely off instantaneous spot reserves in `withdraw_fee`/`correct_and_deposit_fee`. Introduce a TWAP/moving-average oracle over pool reserves for fee pricing, bound deviation between the quoted fee and a recent average with fallback/rejection on excess deviation, and/or expose an explicit caller-supplied `max_asset_fee` bound analogous to swap calls' `amount_in_max` so manipulated quotes cannot go unchecked.

## Proof of Concept
1. Attacker funds a permissionless `(Native, X)` pool where `X` is configured as `SwapAssetAdapter`'s accepted fee asset.
2. In block N, from the same account/nonce sequence: (a) `swap_exact_tokens_for_tokens` pushes a large amount of `X` into the pool, skewing reserves; (b) a call wrapped in `ChargeAssetTxPayment::from(tip, Some(X))` triggers `withdraw_fee`, which calls `quote_price_tokens_for_exact_tokens(X, Native, fee, true)` against the skewed reserves at [3](#0-2) , producing an artificially low `asset_fee`; (c) a follow-up swap reverses the skew, recovering most of the value spent in step (a) net of AMM fee.
3. Compare the `X` actually debited in step (b) against the amount that would be quoted from the pool's pre-manipulation reserves — as demonstrated by the pallet's own quote-based test pattern at [4](#0-3)  — showing the fee-asset amount consumed is decoupled from the "fair" pre-attack price while the native-equivalent `fee` credited to `OU` is unchanged.
