### Title
Truncated `BlockProposal` chunk with missing version byte is silently accepted as `BlockProposalData::empty()` instead of rejected - (File: libsigner/src/events.rs)

### Summary
`BlockProposalData::consensus_deserialize` treats a failed read of the leading `version` byte as a non-error, returning `Ok(Self::empty())` instead of propagating the underlying `CodecError`. Because `BlockProposal::consensus_deserialize` first fully deserializes `block`, `burn_height`, and `reward_cycle` before calling into `BlockProposalData::consensus_deserialize`, an attacker who truncates a serialized `BlockProposal` exactly at the point where the `block_proposal_data.version` byte begins causes the whole `BlockProposal` to still deserialize successfully, but with fabricated `version=1`/empty diagnostic data instead of erroring out.

### Finding Description
The relevant code: [1](#0-0) 

```rust
fn consensus_deserialize<R: Read>(fd: &mut R) -> Result<Self, CodecError> {
    let Ok(version) = read_next(fd) else {
        return Ok(Self::empty());
    };
    ...
}
```

This is invoked from `BlockProposal::consensus_deserialize` only after the (potentially large) `NakamotoBlock`, `burn_height`, and `reward_cycle` fields have already been fully and successfully parsed: [2](#0-1) 

The broken equality: for a legitimately serialized `BlockProposal` with `block_proposal_data.version == 3` and `miner_diagnostic_data == Some(..)`, if the byte stream is truncated right where the version byte would start (i.e., EOF at that point), `read_next(fd)` fails with an I/O/codec error, but instead of that error propagating up through `BlockProposal::consensus_deserialize` (which would cause the whole message to be correctly rejected), the local `let ... else` swallows it and manufactures `BlockProposalData::empty()` (`version=1`, `server_version=""`, `miner_diagnostic_data=None`, `unknown_bytes=vec![]`). The result is a `BlockProposal` value that is returned as `Ok(..)` to the caller, with the same `block`/`burn_height`/`reward_cycle` as the original message but forged/emptied proposal metadata — even though the actual bytes on the wire were an incomplete/corrupted message that should have been rejected as malformed.

### Impact Explanation
Any code path that calls `BlockProposal::consensus_deserialize` on attacker/miner-controlled bytes (e.g., StackerDB `.miners` chunk processing for `BlockProposal` signer messages) will accept a truncated message as valid, silently discarding `server_version` and `miner_diagnostic_data` (fields used for diagnostics/miner-version tracking by signer tooling) without any indication of failure. This is a parsing/data-integrity defect confined to metadata fields — it does not forge the `NakamotoBlock` itself or affect consensus validation, since `block`, `burn_height`, and `reward_cycle` are deserialized before this bug triggers and are unaffected. The severity is bounded: it degrades diagnostic/version-reporting fidelity for a `BlockProposal` rather than causing state corruption, unauthorized writes, or a crash.

### Likelihood Explanation
Triggering this requires the attacker to control (or replay a truncated copy of) the raw bytes fed into `BlockProposal::consensus_deserialize`, e.g., a `.miners` StackerDB chunk. The full reachability chain from network bytes → this deserializer (including whatever chunk-signature checks occur beforehand) was not verified within available tool budget, so it's uncertain whether an unprivileged party (without the miner's signing key) could get a truncated payload past prior signature/authenticity checks on the `.miners` StackerDB slot. This uncertainty affects whether the bug is remotely triggerable by a fully unprivileged attacker or only by a legitimate slot holder sending malformed data.

### Recommendation
Propagate the error from the version-byte read instead of masking it:
```rust
let version = read_next(fd)?;
```
removing the `let ... else { return Ok(Self::empty()) }` fallback, so any truncated/malformed `BlockProposalData` causes the whole `BlockProposal::consensus_deserialize` to fail with `Err(CodecError::...)`.

use stacks_common::codec::StacksMessageCodec;

#[test]
fn truncated_block_proposal_data_is_rejected_not_emptied() {
    let proposal = /* construct BlockProposal with block_proposal_data.version == 3,

    let mut buf = vec![];
    proposal.consensus_serialize(&mut buf).unwrap();

    // Find offset where block_proposal_data begins (after block+burn_height+reward_cycle)
    // and truncate exactly there, removing the version byte and everything after.
    let truncated = &buf[..offset_of_version_byte];

    let mut reader = truncated;
    let result = BlockProposal::consensus_deserialize(&mut reader);

    // Current (buggy) behavior: Ok(..) with block_proposal_data == BlockProposalData::empty()

This reproduces the exact fault: `result` is `Ok` with `version == 1` and `miner_diagnostic_data == None` despite the original message having `version == 3` and diagnostic data present, confirming the equality break described in the question.

    fn consensus_deserialize<R: Read>(fd: &mut R) -> Result<Self, CodecError> {
        let Ok(version) = read_next(fd) else {
            return Ok(Self::empty());
        };
        let inner_bytes: Vec<u8> = read_next_at_most(fd, BLOCK_RESPONSE_DATA_MAX_SIZE)?;
        let mut inner_reader = inner_bytes.as_slice();
        let server_version: Vec<u8> = read_next(&mut inner_reader)?;
        let server_version = String::from_utf8(server_version).map_err(|e| {
            CodecError::DeserializeError(format!("Failed to decode server version: {:?}", e))
        })?;
        let miner_diagnostic_data = if version >= 3 {
            Some(MinerDiagnosticData::consensus_deserialize(
                &mut inner_reader,
            )?)
        } else {
            None
        };
        Ok(Self {
            version,
            server_version,
            miner_diagnostic_data,
            unknown_bytes: inner_reader.to_vec(),
        })
    }
