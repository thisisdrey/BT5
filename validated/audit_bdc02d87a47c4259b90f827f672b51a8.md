### Title
Non-constant-time comparison of the `Authorization` secret token enables remote timing-based recovery of `auth_token` - ([File: stackslib/src/net/api/postblock_proposal.rs])

### Summary
The `/v3/block_proposal` and `/v3/blocks/simulate/:block_id` HTTP endpoints authenticate callers by comparing the `Authorization` request header against the node's configured `auth_token` secret using a plain Rust `String` `!=` comparison. `String`/`&str` equality in Rust short-circuits on the first mismatching byte, so the comparison time leaks how many leading bytes of the guessed token are correct. This is the classic “secret protected by a weak/leaky mechanism” bug class (CWE-208/CWE-522 family, same root idea as the referenced advisory of a secret not being adequately protected), applied here to the network-facing comparison instead of on-disk storage.

### Finding Description
Both HTTP handlers implement the authorization check identically: [1](#0-0) 

```rust
let Some(password) = &self.auth else {
    return Err(Error::Http(400, "Bad Request.".into()));
};
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```

and the equivalent in the block-replay/simulate endpoint: [2](#0-1) 

The equality operator used here (`PartialEq` for `String`) is a standard byte-wise comparison that returns as soon as a mismatch is found — it is not constant-time. An unauthenticated, remote attacker who can repeatedly send `POST /v3/block_proposal` (or `/v3/blocks/simulate/...`) requests with different guessed `Authorization` values can, in principle, measure response latency differences to infer how many leading bytes of their guess match the real secret, and thereby recover `auth_token` byte-by-byte far faster than brute-forcing the whole secret space. Both endpoints require the caller to supply zero prior knowledge — they are unauthenticated network entry points guarded solely by this token check — so this is the exact place where the “secret” (`auth_token`/`auth_password`, described in the node config as securing the node-signer channel) is protected, and here.

The equality that should hold — "attacker knows the secret" vs "server accepts the request" — is not cleanly separated because the comparison leaks partial-match information through timing, degrading the secrecy assumption the endpoint relies on.

### Impact Explanation
`auth_token` is explicitly documented as the credential that authorizes `stacks-signer` to submit block proposals for validation and to broadcast blocks via `/v2/blocks?broadcast=1`: [3](#0-2) 

Recovering this secret via a timing side channel would let a remote, unprivileged attacker impersonate the signer to the `/v3/block_proposal` endpoint (auth bypass), matching the report's "Critical - ... auth bypass" impact category for this scope. In practice, network jitter makes such attacks harder than in low-noise environments, but the underlying weakness (non-constant-time secret comparison over the network) is a real, well-known vulnerability class distinct from a purely theoretical concern, since it is the literal comparison guarding a privileged write endpoint.

### Likelihood Explanation
Exploitation requires many repeated requests and statistical timing analysis to overcome network noise, which raises practical difficulty compared to a local/high-precision timing attack. However, the endpoint is reachable by any remote peer that can route to the node's RPC port, requires no authentication to attempt, and the comparison is unconditionally the first (and only) gate before further processing, making the timing signal directly tied to the secret comparison rather than incidental work.

### Recommendation
Replace the `!=` string comparison in both `RPCBlockProposalRequestHandler::try_parse_request` (`stackslib/src/net/api/postblock_proposal.rs`) and `RPCNakamotoBlockSimulateRequestHandler::try_parse_request` (`stackslib/src/net/api/blocksimulate.rs`) with a constant-time comparison (e.g., `subtle::ConstantTimeEq`, or hashing both sides with a keyed MAC and comparing digests) so that comparison time is independent of how many leading bytes match.

### Proof of Concept
1. Configure a node with `[connection_options] auth_token = "<secret>"`.
2. From a remote unauthenticated client, send repeated `POST /v3/block_proposal` requests with the `Authorization` header set to different candidate strings that share increasingly long correct prefixes of `<secret>`.
3. Measure response latency for the 401 rejection path (`stackslib/src/net/api/postblock_proposal.rs:1142-1144`); statistically, requests whose header matches more leading bytes take marginally longer due to the byte-wise `!=` short-circuit, allowing incremental recovery of `<secret>` without needing to guess it in full.
