Audit Report

## Title
Unverified fire-and-forget XCM in Snowbridge reward payout can permanently lose relayer rewards - (File: `bridges/snowbridge/primitives/core/src/reward.rs`)

## Summary
`pallet_bridge_relayers::claim_rewards_to` lets an unprivileged relayer redeem an accrued reward to an arbitrary `Location` beneficiary via `PayAccountOnLocation::pay_reward`, which only checks that `XcmSender::deliver` succeeds (i.e., the message was queued) before returning `Ok(())`. The calling `do_claim_rewards` then commits removal of the reward entry from `RelayerRewards` storage based solely on this local queuing success, not on the remote `DepositAsset` on AssetHub actually succeeding.

## Finding Description
`do_claim_rewards` in [1](#0-0)  uses `try_mutate_exists` to take the stored reward and call `T::PaymentProcedure::pay_reward`; the closure only errors out (leaving the reward record intact) if `pay_reward` returns `Err`. For the Snowbridge reward kind, `pay_reward` is `PayAccountOnLocation::pay_reward` in [2](#0-1) , which builds an XCM program ending in `DepositAsset { assets: AllCounted(1).into(), beneficiary }`, validates it, charges fees, and calls `XcmSender::deliver(ticket)`. The function returns `Ok(())` as soon as `deliver` succeeds — this only confirms the message was accepted into the outbound queue/channel, not that the remote `DepositAsset` instruction executed successfully on AssetHub. If the beneficiary cannot receive the asset (e.g., non-existent account below existential deposit), the `try_mutate_exists` closure in `do_claim_rewards` has already committed the storage removal and emitted `RewardPaid`, while the asset itself is trapped on the destination chain with no path back to the relayer.

The mock tests in the same file (`pay_reward_fails_on_delivery`, `pay_reward_success`) confirm the implementation's only failure modes are validate/charge-fees/deliver failures — there is no remote-execution confirmation mechanism, matching the claim's characterization exactly.

## Impact Explanation
This matches the "duplicate settlement or payout" / "permanent user-fund or bridge-state lock" impact category: the relayer's accrued reward is irreversibly deleted from `RelayerRewards` storage based on local message-queuing success alone, without any receipt-based confirmation that the remote `DepositAsset` succeeded. A relayer supplying a beneficiary `Location` that cannot accept the deposit on AssetHub (e.g., unfunded account below ED) permanently loses the reward with no local retry or reconciliation path.

## Likelihood Explanation
`claim_rewards_to` is public and unprivileged, requiring only `ensure_signed(origin)` as shown in [3](#0-2) . No existence/ED check on the `beneficiary` `Location` is performed before the storage mutation commits, and `pay_reward`'s only validations are XCM send/fee-charging success. This is deterministically triggerable by a relayer through an operational mistake (an unfunded destination account) without requiring any malicious peer, validator, or governance action.

## Recommendation
Do not treat `XcmSender::deliver() == Ok` as final settlement confirmation for reward accounting. Keep the reward pending until a delivery/execution receipt confirms the remote `DepositAsset` succeeded before clearing `RelayerRewards`, or validate that the beneficiary account exists/meets ED on the destination chain prior to committing the storage removal, or provide a safe re-credit path if the XCM program traps the assets.

## Proof of Concept
1. A relayer accrues a Snowbridge reward via `register_reward`, populating `RelayerRewards`.
2. The relayer calls `claim_rewards_to(BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(loc))` where `loc` is an `AccountId32` never funded on AssetHub (below existential deposit).
3. `do_claim_rewards` ( [4](#0-3) ) takes the reward from storage and calls `pay_reward`, which succeeds because `XcmSender::deliver` only confirms message routing ( [5](#0-4) ); the storage removal commits and `RewardPaid` is emitted.
4. On AssetHub, `DepositAsset` fails because the beneficiary account cannot satisfy ED, trapping the reserve-deposited asset.
5. The relayer has no reward left in storage and never receives funds — permanent loss with no automatic recovery.

		fn do_claim_rewards(
			relayer: T::AccountId,
			reward_kind: T::Reward,
			beneficiary: BeneficiaryOf<T, I>,
		) -> DispatchResult {
			RelayerRewards::<T, I>::try_mutate_exists(
				&relayer,
				reward_kind,
				|maybe_reward| -> DispatchResult {
					let reward_balance =
						maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;
					T::PaymentProcedure::pay_reward(
						&relayer,
						reward_kind,
						reward_balance,
						beneficiary.clone(),
					)
					.map_err(|e| {
						tracing::error!(
							target: LOG_TARGET,
							error=?e,
							?relayer,
							?reward_kind,
							?reward_balance,
							?beneficiary,
							"Failed to pay rewards"
						);
						Error::<T, I>::FailedToPayReward
					})?;

					Self::deposit_event(Event::<T, I>::RewardPaid {
						relayer: relayer.clone(),
						reward_kind,
						reward_balance,
						beneficiary,
					});
					Ok(())
				},
			)

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
