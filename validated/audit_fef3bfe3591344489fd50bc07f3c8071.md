### Title
Griefing `feeCollector`'s per-account token list to `MAX_TOKENS_PER_USER` permanently DoSes `Pool.liquidate` fee seizure — (File: contracts/Pool.sol)

### Summary
`Pool` tracks each account's held deposit/debt tokens in `MappedEnumerableSet` lists, and any addition is guarded by `onlyIfAdditionWillNotReachMaxTokens` (`MAX_TOKENS_PER_USER = 30`) in `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount`. During `liquidate`, the protocol fee is moved via `depositToken_.seize(account_, feeCollector, _fee)`, which performs a deposit-token transfer to the fee collector — triggering `addToDepositTokensOfAccount(feeCollector)` whenever the collector's balance of that token goes `0 → >0`. An unprivileged attacker can pre-fill `feeCollector`'s list to 30 entries (via `DepositToken.deposit(amount, feeCollector)` dust donations and `DebtToken.issue(amount, feeCollector)` against that donated collateral), leaving at least one deposit token absent. Every subsequent `liquidate` call that must pay a fee in that token reverts with `UserReachedMaxTokens`, permanently blocking liquidations in a pool with more than 30 total token types. This mirrors CVE-2023-2019's bug class: improper management of a per-entity counter/membership reference leading to denial of service.

### Finding Description
- `Pool.addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are callable only by registered tokens, but they are invoked from `DepositToken`/`DebtToken` balance-transition hooks (`deposit`, `transfer`, `transferFrom`, `seize`, `issue`), all of which are reachable by any EOA with arbitrary `onBehalfOf`/recipient arguments (`deposit(amount_, onBehalfOf_)` mints to any recipient; `issue(amount_, onBehalfOf_)` can mint debt+synth to any account whose position stays healthy).
- The combined counter `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_)` is the "reference count" that must stay `< MAX_TOKENS_PER_USER` (30) for any new token addition (`Pool.sol:143-148`, `204-220`).
- `liquidate` calls `depositToken_.seize(account_, _poolRegistry.feeCollector(), _fee)` when `_fee > 0` (`Pool.sol:591-593`). `seize` moves deposit tokens to the collector; if the collector's balance of that deposit token was zero, the hook calls `addToDepositTokensOfAccount(feeCollector)`, which reverts once the collector is at 30 entries.
- Attack sequence (all unprivileged, single EOA, no privileged role):
  1. For each registered `DepositToken` except a chosen victim token `D`, call `D_i.deposit(dust_i, feeCollector)` — filling the collector's `depositTokensOfAccount`.
  2. Deposit enough collateral to `feeCollector` to make its position healthy, then call `debtToken_j.issue(smallAmount_j, feeCollector)` for enough debt tokens to bring the combined count to exactly 30, while `D` remains absent from its list.
  3. Any `liquidate(synth, victim, amt, D)` with `protocolFee > 0` reverts at the fee `seize` with `UserReachedMaxTokens`. Since `feeCollector` cannot remove entries without someone spending its balances (it is a passive collector; its deposit-token balances can only be moved by treasury/governance flows), the block is effectively permanent for `D`.

### Impact Explanation
Positions whose only/remaining seizable collateral is `D` (or any token the collector doesn't already hold) cannot be liquidated while `protocolFee > 0`. Underwater positions accumulate bad debt, threatening protocol solvency — a direct liveness break of the liquidation invariant, matching the "reachable denial of service affecting contract operations" and "insolvency" impact classes.

### Likelihood Explanation
Requires: (a) `protocolFee > 0` in `feeProvider.liquidationFees()`, (b) total registered debt + deposit tokens > 30 so the cap can be hit while leaving a deposit token out, and (c) attacker funds for dust deposits and collateral to back minimal `issue` calls (recoverable value sits with the fee collector, i.e., a donation cost). The revert is unconditional once the state is reached; the victim cannot delist tokens or work around it. Uncertain: exact deployed token count and whether `issue`'s `onlyIfCanMint` path adds extra checks on `onBehalfOf` — should be confirmed on the target deployment.

### Recommendation
Do not apply `onlyIfAdditionWillNotReachMaxTokens` on additions to privileged/system accounts such as `feeCollector` (and optionally the treasury), or make `seize`-to-fee-collector bypass the per-account cap. Alternatively, cap `deposit()`/`issue()` to `onBehalfOf` addresses other than `msg.sender`, or track fee-collector holdings in a separate uncapped set.

### Proof of Concept
```solidity
// Foundry fork test sketch
// Assumes: protocolFee > 0, N registered deposit tokens, M debt tokens, N + M > 30.

address feeCollector = poolRegistry.feeCollector();
uint256 slots = 0;

// 1) Fill feeCollector's deposit list with dust, skipping victim token D
for (uint i; i < depositTokens.length && slots < 30; ++i) {
    IDepositToken dt = IDepositToken(depositTokens[i]);
    if (address(dt) == address(D)) continue;
    underlying_i.approve(address(dt), dust);
    dt.deposit(dust, feeCollector);          // addToDepositTokensOfAccount(feeCollector)
    slots++;
}

// 2) Top up with debt tokens issued to feeCollector (backed by donated collateral)
while (slots < 30) {
    debtToken_j.issue(smallAmount, feeCollector); // addToDebtTokensOfAccount(feeCollector)
    slots++;
}
assertEq(pool.getDepositTokensOfAccount(feeCollector).length
       + pool.getDebtTokensOfAccount(feeCollector).length, 30);

// 3) Liquidation repaying debt against collateral D now always reverts
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
pool.liquidate(synth, underwaterVictim, amountToRepay, D);
```

Note: I was unable to fully verify the internals of `DepositToken.seize`/`_afterTokenTransfer` and `DebtToken.issue`'s access checks within the available iterations; the finding assumes the standard balance-transition → `addTo*TokensOfAccount` hook confirmed by `test/DepositToken.test.ts` and should be validated against those files before reporting.
