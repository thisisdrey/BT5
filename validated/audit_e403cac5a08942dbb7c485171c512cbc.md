Based on the evidence gathered, I found a structurally analogous "escalation backdoor" pattern in the account multi-sig permission system, though I was unable to fully inspect `TransactionCapsule.checkPermission()`'s complete body in this pass — I note that gap explicitly below.

### Title
Active permission can be granted the AccountPermissionUpdateContract operation, allowing self-escalation to Owner control - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator` lets an account's `Owner` permission holder define arbitrary `Active` permissions, including which contract types ("operations") that active key is authorized to broadcast. The bitmap validation for these operations is checked against the full `getAvailableContractType()` set [1](#0-0) , which — unlike the narrower `getActiveDefaultOperations()` bitmap used only for brand-new default accounts — is not shown anywhere in the actuator to exclude `AccountPermissionUpdateContract` itself. The test suite confirms this asymmetry: the "default active operations" set explicitly excludes `AccountPermissionUpdateContract` [2](#0-1) , while the "available contract type" set used for `checkPermission()` validation does not exclude it (only `UNRECOGNIZED` and `UpdateBrokerageContract` are excluded) [3](#0-2) .

### Finding Description
This mirrors the Nounsbuilder bug class: a privileged actor (the account's `Owner` permission, analogous to the "founder") can plant a persistent backdoor by explicitly assigning a lower-trust `Active` permission (analogous to a "minter" role) the ability to invoke a sensitive, ownership-level operation — here, `AccountPermissionUpdateContract` itself — even though the system's own defaults intentionally omit this capability from active permissions [4](#0-3) . Because `checkPermission()` only validates the operations bitmap against the broad `getAvailableContractType()` bitmap rather than a restricted set that excludes ownership-management operations, an account owner (e.g. before finalizing multi-sig / DAO-style ownership) can craft a custom `AccountPermissionUpdateContract` that grants an `Active` permission (with a low threshold, potentially a single key) the operation bit for `AccountPermissionUpdateContract`. The `AccountPermissionUpdateActuator.execute()` method then unconditionally applies whatever owner/witness/active permissions are supplied in the transaction, without any special-cased requirement that changes to the `Owner` permission must be authorized specifically by a signature meeting the `Owner`-tier threshold as opposed to merely meeting a compromised `Active` permission's threshold [5](#0-4) . This means the holder of that "backdoored" active key can later call `AccountPermissionUpdateContract` again to overwrite the `Owner` permission entirely, self-escalating to full account/DAO control — analogous to a founder secretly assigning itself an unrestricted "minter" role that survives after nominal control is meant to shift to a higher-trust (e.g., multi-sig) governance structure.

### Impact Explanation
If exploited, an account owner (acting maliciously before establishing a genuine multi-sig/DAO-style `Owner` permission) can retain unauthorized permanent control over the account by embedding the ability to rewrite `Owner`/`Active`/`Witness` permissions into a nominally lower-trust `Active` key. This subverts the entire purpose of TRON's multi-sig permission model, allowing unauthorized account takeover, arbitrary asset movement, and undermining any assumption that `Active`-permission holders are restricted from account-governance actions.

### Likelihood Explanation
This requires the account's current `Owner` permission holder to deliberately craft such a permission update — it is a self-inflicted backdoor requiring the owner's own signature to set up, exactly matching the analog report's "founder" trust model where the actor is initially trusted but later expected to lose that unilateral power. Once set up, exploitation by the backdoor key holder requires only a normal signed `AccountPermissionUpdateContract` transaction, which is straightforward.

### Recommendation
Explicitly exclude `AccountPermissionUpdateContract` (and other governance-critical contract types) from the set of operations permitted to be assigned to `Active`/`Witness` permissions in `AccountPermissionUpdateActuator.checkPermission()`, mirroring the exclusion already present in `getActiveDefaultOperations()`. Alternatively, require that `AccountPermissionUpdateContract` transactions can only be authorized via the `Owner` permission's `permissionId`, regardless of any operations bitmap granted to `Active` permissions.

### Proof of Concept
Note: this could not be fully validated end-to-end because I was unable to inspect the complete body of `TransactionCapsule.checkPermission(int permissionId, Permission permission, Contract contract)` in this session, which is the code path that ultimately decides whether a given `permissionId`/signature is accepted for a given contract type. The finding is based on: (1) `AccountPermissionUpdateActuator.checkPermission()` validating active-permission operations against the broad `getAvailableContractType()` bitmap rather than the restrictive `getActiveDefaultOperations()` bitmap, and (2) confirmed test evidence that `AccountPermissionUpdateContract` is present in `getAvailableContractType()` but deliberately absent from `getActiveDefaultOperations()`. Concretely reproducing full account takeover would require: an owner issuing an `AccountPermissionUpdateContract` setting an `Active` permission with `operations` byte 0 bit 30 set (bit corresponding to `AccountPermissionUpdateContract`'s enum id) and a low threshold/single key; then, using that active key, submitting a follow-up `AccountPermissionUpdateContract` with `permissionId=2` (active) to overwrite the `Owner` permission. Full confirmation of whether `TransactionCapsule.checkPermission` blocks this specific contract-type-to-permission-tier mismatch requires further code review.
