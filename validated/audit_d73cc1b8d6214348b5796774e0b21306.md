Audit Report

## Title
`process_delivery_receipt` pays relayer reward and clears the pending order regardless of delivery outcome - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
The public, unprivileged extrinsic `submit_delivery_receipt` accepts a genuine, correctly-proven Ethereum event log and forwards the decoded `DeliveryReceipt` (which carries a `success: bool` field reflecting whether the message actually executed on the Gateway contract) to `process_delivery_receipt`. That function never inspects `receipt.success` before crediting `order.fee` to a caller-chosen `reward_account` and permanently removing the `PendingOrder`, so a message that reverted on Ethereum is paid and settled exactly as if it had succeeded.

## Finding Description
`DeliveryReceipt` is decoded from the Solidity event `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)` via `TryFrom<&Log>`, which faithfully copies `event.success` into `DeliveryReceipt.success` at [1](#0-0) . The extrinsic `submit_delivery_receipt` calls `ensure_signed(origin)`, verifies the proof via `T::Verifier::verify`, decodes the receipt, and passes it straight to `Self::process_delivery_receipt(relayer, receipt)` with no filtering of `success` [2](#0-1) . Inside `process_delivery_receipt`, the only checks performed are gateway-address matching and pending-order existence; `reward_account` is derived from attacker-controlled `receipt.reward_address`, `order.fee` is unconditionally paid via `T::RewardPayment::register_reward` when nonzero, and `<PendingOrders<T>>::remove(nonce)` unconditionally deletes the order state, all without ever reading `receipt.success` [3](#0-2) . A repository-wide search confirms the `success` field is never referenced anywhere in the outbound-queue-v2 pallet logic.

## Impact Explanation
This matches the "theft or unbacked mint/unlock" and "duplicate settlement or payout" impact classes: any holder of a legitimate `success: false` receipt can claim the full `order.fee` reward for a message that never executed successfully, and the corresponding `PendingOrder` is permanently removed from `PendingOrders`, precluding any retry, refund, or correct resolution of the failed delivery — a permanent bridge-state settlement to the wrong outcome.

## Likelihood Explanation
The precondition — a Gateway-side execution failure after message acceptance — is an expected code path represented explicitly by the `success: bool` field, not a rare edge case. No privileged role, governance action, or compromise of any party is needed: any signed account holding a genuine Ethereum receipt/proof with `success = false` for a nonce with an outstanding `PendingOrder` can trigger the flaw by calling the already-public `submit_delivery_receipt` extrinsic, exactly as it would for a legitimate success receipt.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: on `false`, skip `T::RewardPayment::register_reward` and either retain the `PendingOrder` for retry/resubmission or transition it to a distinct "failed" state instead of unconditionally calling `<PendingOrders<T>>::remove(nonce)`, and emit a `MessageDeliveryFailed` event rather than `MessageDelivered`.

## Proof of Concept
1. `do_process_message` inserts `PendingOrders[nonce] = { nonce, fee: F, block_number }` for an outbound message [4](#0-3) .
2. On Ethereum, Gateway execution of that message reverts, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. Any signed account calls `submit_delivery_receipt(origin, event)` with a valid proof and `reward_address` set to their own account; `T::Verifier::verify` and `DeliveryReceipt::try_from` both succeed since the log is genuine.
4. `process_delivery_receipt` runs: `order.fee > 0` triggers `T::RewardPayment::register_reward(&reward_account, ..., order.fee)` and `<PendingOrders<T>>::remove(nonce)` deletes the order — despite `receipt.success == false` — paying the caller in full and permanently closing the failed order.

			relayer: <T as frame_system::Config>::AccountId,

		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
