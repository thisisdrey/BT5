### Title
Unbounded array allocation from attacker-controlled length word in `ValidateMultiSign`/`BatchValidateSign` precompiles causes memory-exhaustion DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
CVE-2017-11525 is a class of bug where a file format's length field is trusted to size a memory allocation without validating it against the actual available data, letting an attacker request an allocation far larger than the input itself, causing memory exhaustion. The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts contain the same pattern: `extractBytesArray` allocates a `byte[][]` sized directly from an attacker-supplied 32-byte word, with no cross-check against the actual `data.length`, when the `allowTvmSelfdestructRestriction` hard fork flag is not active.

### Finding Description
`extractBytesArray` reads the array length directly from calldata and allocates accordingly, with no upper bound and no relation to the real payload size: [1](#0-0) 

`ValidateMultiSign.execute()` only guards the length with a `MAX_SIZE` check (and switches to the safer `extractSigArray`) **when `VMConfig.allowTvmSelfdestructRestriction()` is enabled**. If that hard-fork switch is not enabled, it calls `extractBytesArray` directly, with no size cap applied before the allocation happens: [2](#0-1) 

The same conditional pattern (guard only under the flag, otherwise unguarded `extractBytesArray`) exists in `BatchValidateSign.doExecute()`: [3](#0-2) 

The length value comes from `words[offset].intValueSafe()`, which decodes an arbitrary 32-byte word supplied in the calldata of a `CALL` to the precompile address `0x...9` (`BatchValidateSign`) or `0x...a` (`ValidateMultiSign`); these addresses are reachable whenever `VMConfig.allowTvmSolidity059()` is enabled: [4](#0-3) 

Because `len` is taken from a word chosen by the caller and is not bounded by `data.length` before the `new byte[len][]` allocation in `extractBytesArray`, an attacker can set this word to a very large value (e.g. `Integer.MAX_VALUE`), forcing the JVM to attempt to allocate an array of that many object references. This throws `java.lang.OutOfMemoryError`, and critically, this call happens **before** the `try { ... } catch (Throwable t)` block inside `ValidateMultiSign.execute()`, so the error is not contained locally and propagates up through `Program.callToPrecompiledAddress`/the VM interpreter loop.

### Impact Explanation
An uncaught `OutOfMemoryError` thrown while executing a TVM opcode inside block/transaction processing can destabilize or crash the node process (or at minimum abort the currently executing transaction/block-application thread in an unclean state), since it is thrown outside any bounded/contained exception handling for this specific allocation. This is reachable by any contract deployer or transaction broadcaster capable of triggering a `CALL` to the `ValidateMultiSign`/`BatchValidateSign` precompile addresses — no special privilege is required, matching the "node crash or halt" impact category.

### Likelihood Explanation
Exploitability depends entirely on whether `allowTvmSelfdestructRestriction` (a chain-parameter/TIP activation flag) is enabled on the target network. I was unable to confirm from the available index whether this flag is already activated by default/committee-proposal on current mainnet/testnet deployments of this fork — `common/src/main/java/org/tron/core/vm/config/VMConfig.java` could not be located in the index to verify its default value. If the flag is still off (e.g., on a private/test network, or prior to the corresponding committee proposal being passed on mainnet), the vulnerable, unguarded `extractBytesArray` path is directly reachable from any signed transaction that invokes the precompile. If the flag is already permanently enabled on the network in question, this specific path is dead code and not exploitable — this should be verified against the live network's activated proposals before treating it as an active issue.

### Recommendation
Apply the same `MAX_SIZE` bound check unconditionally, before calling `extractBytesArray`, regardless of `allowTvmSelfdestructRestriction`, and additionally bound `len` inside `extractBytesArray`/`extractBytes32Array` against `(data.length - offset*WORD_SIZE) / WORD_SIZE` so the declared count can never exceed what the actual payload can support, consistent with the `verifyLength`/`isValidAbiEncoding` pattern already used elsewhere in this file.

### Proof of Concept
1. Craft a transaction that performs a TVM `CALL` to precompile address `0x...a` (`validateMultiSign`) with calldata shaped as `(address, uint256 permissionId, bytes32 hash, bytes[] signatures)`.
2. Set the ABI offset/length word for the `signatures` array (the word at `words[3]`'s target offset) to `0x7FFFFFFF` instead of a real array count, while keeping the rest of the calldata minimal.
3. Ensure the network has NOT yet activated `allowTvmSelfdestructRestriction` (verify via `DynamicPropertiesStore`/committee proposal state on the target chain).
4. Broadcast the transaction; `ValidateMultiSign.execute()` calls `extractBytesArray(words, offset, rawData)`, which executes `new byte[0x7FFFFFFF][]`, throwing `OutOfMemoryError` outside of the local `try/catch`, before any `MAX_SIZE` bound is applied. [1](#0-0) [2](#0-1)

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
