### Title
Unbounded central-directory field parsing causes heap out-of-bounds read in `InputZipFile::ProcessCentralDirEntry` - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` (used by `ijar`/`singlejar` when reading a `.jar`/`.zip` supplied as build input, e.g. a downloaded Java dependency or third-party archive) parses attacker-controlled, variable-length central-directory fields (`file_name_length`, `extra_field_length`, `file_comment_length`) and advances/copies from the mmap'd input buffer using these lengths without validating that the resulting reads stay within the mapped file bounds.

### Finding Description
Unlike `InputZipFile::ProcessLocalFileEntry`, which calls `EnsureRemaining()` before every variable-length read [1](#0-0) , `ProcessCentralDirEntry` reads the length fields directly from the mapped buffer and immediately does `memcpy(filename, p, len)` and pointer arithmetic (`p += file_name_length`, `extra_p += data_size`, `p += file_comment_length`) with no bounds check against `input_file_->Length()` or the known central-directory size: [2](#0-1) 

The extra-field loop is especially unguarded: `while (extra_p != p) { ... extra_p += data_size; ... }` trusts the attacker-supplied `data_size` and `extra_field_length` to line up exactly; a crafted `data_size` that never equals `p` causes the loop to walk arbitrarily far past the mapped region while dereferencing `get_u2le`/`get_u8le` at `extra_p`, reading out of bounds memory [3](#0-2) .

This is the same bug class as CVE-2020-7039: a parser for attacker-supplied variable-length protocol/format fields (there, IRC DCC fields in `tcp_emu`; here, ZIP central-directory length fields) advances buffer pointers and copies data based on untrusted lengths without validating the source buffer bounds, leading to out-of-bounds memory access.

### Impact Explanation
An out-of-bounds read on the mmap'd input file can read adjacent heap/mapped memory into the fixed `filename[PATH_MAX]` buffer (bounded copy, so no destination overflow, but a source over-read) and, via the extra-field loop, can walk the cursor past the end of the mapping and dereference unmapped pages, causing a crash (SIGSEGV/DoS) of the build tool processing the untrusted jar, or leaking adjacent process memory bytes into the truncated filename that is subsequently used/echoed by downstream processing.

### Likelihood Explanation
`ijar`'s `ProcessCentralDirEntry` runs on every `.zip`/`.jar` that Bazel's `singlejar`/`ijar` tooling ingests, which includes third-party jars fetched by build rules from external sources; the required inputs (bogus `file_name_length`/`extra_field_length`/`data_size` values in a crafted central directory record) are attacker-controllable without any privilege beyond publishing the archive content the victim's build consumes.

### Recommendation
Add `EnsureRemaining`-style bounds checks in `ProcessCentralDirEntry` before reading/copying `file_name_length`, `extra_field_length`, and `file_comment_length` bytes, and bound the extra-field iteration loop by an explicit end pointer derived from validated `extra_field_length`, rejecting entries whose fields would run past the mapped central directory or file end.

### Proof of Concept
A JUnit/`src/test/shell/bazel` style repro: construct a minimal ZIP whose EOCD/central-directory record declares a `file_name_length` or extra-field `data_size` value that, added to the entry's start offset, exceeds the actual mapped file length (e.g., set `file_name_length = 0xFFFF` on a short file, or a ZIP64 extra field whose `data_size` never lands exactly on the recorded `extra_field_length` boundary). Feed this file to `ijar`/`singlejar`'s zip-reading path (`InputZipFile::ProcessNext` → `ProcessCentralDirEntry`) and observe an out-of-bounds read/crash instead of a clean parse error, contrasting with `ProcessLocalFileEntry`, which correctly rejects the same malformed lengths via `EnsureRemaining`.

Note: I was not able to fully trace every caller (e.g., how singlejar's higher-level driver code consumes `ProcessCentralDirEntry`) within the available search iterations, so the exact end-to-end exploitation path (crash vs. memory disclosure) is not independently verified in this pass and would need confirmation in a full build/test environment.
