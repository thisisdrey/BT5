### Title
Cross-tenant object disclosure via `DisconnectGitAlternates` hard-linking the entire object pool into a single member - ([File: internal/git/objectpool/disconnect.go])

### Summary
The reported Convex SPELL bug is a "leftover assets never returned to their rightful owner, later scoopable by anyone who touches the same storage" bug: `WConvexPools.burn()` moves *all* reward tokens (CRV, CVX, and extra incentive tokens) into the spell contract, but `ConvexSpell.openPositionFarm()`/`closePositionFarm()` only refunds `CVX`, leaving the rest sitting in a shared contract where a subsequent, unrelated caller of `_doRefund()` can claim them. The Gitaly analog is `Disconnect()` in the object-pool package, which — when a single pool member asks to leave the pool — hard-links **every object file found anywhere in the pool's alternate object directory**, not just the objects that are actually reachable from that member's own refs, into the disconnecting member's own `objects/` directory.

### Finding Description
Object pools are shared, alternate object stores used to deduplicate objects across forks (`doc/object_pools.md`). Gitaly deliberately keeps *all* objects that have ever been fetched into the pool alive forever by converting them into `refs/dangling/$OID` references so `git gc`/`git prune` never removes them: [1](#0-0) . These dangling objects can belong to *any* pool member, including objects from branches that were force-pushed away or made private by a *different* fork owner: [2](#0-1) .

When a member repository calls `DisconnectGitAlternates`, Gitaly's `Disconnect()` function walks the alternate object directory (the pool's object store) with `findObjectFiles()`, which returns **every** object file in the pool except files under `info/`, without any filtering for reachability from the disconnecting repository's own references: [3](#0-2) [4](#0-3) 

Each of these object files — including dangling objects that originate from other pool members' deleted or force-pushed-away history, kept alive only inside the pool's `refs/dangling/` namespace — is then hard-linked directly into the disconnecting member's own `objects/` directory: [5](#0-4) 

Once hard-linked, the object physically exists in the disconnecting repository's own object store. This happens irrespective of whether that object was ever reachable by any of the disconnecting repository's own branches/tags — it just needs to exist anywhere in the shared pool. From that point forward, any RPC that can read loose objects by OID from that repository (e.g. `CatFile`, `GetBlob`, `TreeEntry`, etc.) can retrieve the object's content, as long as the caller knows or can enumerate its OID.

This mirrors the SPELL bug precisely: a shared pool of assets (rewards / pool objects) is only partially "refunded" to the entity it belongs to, and the leftover shared assets (extra rewards / dangling objects belonging to other members) become permanently claimable by whoever performs the closing/settlement operation (`_doRefund()` / `DisconnectGitAlternates`) — an operation any legitimate but unprivileged actor (a fork owner) is entitled to invoke on their own repository.

### Impact Explanation
A user who controls one fork/member of an object pool can call the unprivileged `DisconnectGitAlternates` RPC and gain permanent, private, local possession of any object that another pool member (including a sibling fork whose visibility is unrelated, or whose data was intentionally deleted/force-pushed away) ever pushed into the shared pool, provided the object was retained by the pool's dangling-object-rescue mechanism. This is a repository-level confidentiality violation: data an owner believed removed (via force-push) or a sibling fork's private-only content can leak into an unrelated fork's own object store, from which it can subsequently be read via ordinary Gitaly RPCs.

### Likelihood Explanation
The RPC is reachable by any actor who owns (or forked into) a pool member repository — no special privilege beyond normal fork/repository access is required, matching the "ordinary user's push/fetch/fork" reachability bar. The only requirement to actually exfiltrate content is knowledge of (or the ability to brute-force/guess or otherwise learn) the OID of the object of interest, which is a realistic constraint but does not prevent the underlying disclosure of arbitrary pool objects into the disconnecting member's local store.

### Recommendation
`Disconnect()` should only re-materialize objects that are actually reachable from the disconnecting repository's own references (e.g., via `git rev-list --objects --all` scoped to the member's refs, or `git repack`/`git fsck --connectivity-only` restricted to that repo) rather than hard-linking every object file present in the shared alternate directory. Alternatively, perform the re-duplication via a `git fetch`/`git repack` operation from the pool scoped to the member's own reachable object graph instead of a raw filesystem walk of the pool's `objects/` tree.

### Proof of Concept
1. Create an object pool `P` and link two members `A` and `B` to it (`CreateObjectPool`, `LinkRepositoryToObjectPool`).
2. In `B`, push a commit on a branch, then force-push it away (delete the branch/ref). A subsequent `FetchIntoObjectPool` housekeeping run rescues this now-unreferenced commit into `P` as `refs/dangling/<OID>`, per `rescueDanglingObjects()`: [6](#0-5) .
3. As the owner of `A` (unrelated to `B`), call `DisconnectGitAlternates` on `A`. `Disconnect()` walks `P`'s `objects/` directory and hard-links every object file, including the object from `B`'s deleted branch, into `A`'s own `objects/` directory: [3](#0-2) .
4. `A`'s owner, now knowing or guessing the OID (e.g., from prior observation, logs, or brute force), issues `GetBlob`/`TreeEntry`/`CatFile` RPCs against repository `A` for that OID and successfully retrieves `B`'s force-pushed-away content, even though `A` was never linked to that commit via any of its own refs.

```markdown
## Dangling Objects

When fetching from pool members into the object pool, then any force-updated
references may cause objects in the pool to not be referenced anymore. For
normal repositories, it is perfectly fine to delete those references after a
certain time. In the context of object pools, any other member of the pool may
still use any of those unreferenced objects. Deleting them would thus
potentially cause corrupt repositories.

This issue is kind of unsolvable: there is no point in time where it's safe to
delete objects from the object pool, as we do not know which repositories may be
linked to it. And even if we knew, we cannot determine all references of all
repositories at once in a race-free manner. We thus must consider each object to
still be referenced somewhere.

As a safeguard to not lose any objects by accident, we thus create dangling
references in the object pool after the fetch in `FetchIntoObjectPool`. For each
dangling object, a reference `refs/dangling/$OID` is created which points into
the object. This assures that each object is still referenced.
```

```markdown
Having unreachable objects kept alive in this fashion does have its problems:

- For busy repositories, we generate loads of dangling references. While these
  references [cannot be seen by clients](#references), they are seen when
  performing housekeeping tasks on the object pool itself. Fetches into the
  object pool and repacking of references can thus become quite expensive.

- Keeping dangling references alive makes Git consider them as reachable. While
  this is the exact effect we want to achieve, it will also cause Git to
  generate packfiles which may use such objects as delta bases which would under
  normal circumstances be considered as unreachable. The resulting packfile is
  thus potentially suboptimal. Gitaly works around this issue by using a delta
  island for `refs/heads/` and `refs/tags/`. This can only be considered a
  best-effort strategy, as it only considers a single object pool member's
  reachability while ignoring potential reachability by any other pool member.
```

```go
func findObjectFiles(altDir string) ([]string, error) {
	var objectFiles []string
	if walkErr := filepath.Walk(altDir, func(path string, info os.FileInfo, err error) error {
		if err != nil {
			return err
		}

		rel, err := filepath.Rel(altDir, path)
		if err != nil {
			return err
		}

		if strings.HasPrefix(rel, "info/") {
			return nil
		}

		if info.IsDir() {
			return nil
		}

		objectFiles = append(objectFiles, rel)

		return nil
	}); walkErr != nil {
		return nil, walkErr
	}

	sort.Sort(objectPaths(objectFiles))

	return objectFiles, nil
}
```
