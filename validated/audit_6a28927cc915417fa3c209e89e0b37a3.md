### Title
Caller-controlled `Timeout` in `FetchRemote` can break the claimed atomicity of `fetchRemoteAtomic`, leaving pruned references committed while dependent reference updates are lost - (File: internal/gitaly/service/repository/fetch_remote.go)

### Summary
`FetchRemote` lets an ordinary client supply a `Timeout` field that is turned directly into the RPC's `context.Context` deadline. [1](#0-0)  `fetchRemoteAtomic` is documented as atomic ("to be atomic, fetched objects are quarantined and only migrated before committing the reference transaction") but it actually performs two sequential, independently-committed reference transactions plus an unrelated quarantine migration step in between. [2](#0-1)  If the attacker-controlled timeout expires after `prunedUpdater.Commit()` succeeds but before `refUpdater.Commit()` completes, pruned/deleted references are permanently applied while the corresponding updated references and their newly fetched objects are dropped, breaking the atomicity guarantee the function claims and potentially causing loss of reachable history. This is the same bug class as the Optimism report: an externally supplied "budget" parameter (`l2Gas` there, `Timeout` here) that, if underprovisioned, causes a multi-step operation to fail partway after an irreversible step has already been committed, leaving state in a broken/lossy condition.

### Finding Description
`FetchRemote` converts the request's `Timeout` field directly into the context deadline for the whole `fetchRemoteAtomic` call, with no minimum bound or validation against how long the remaining unavoidable steps (fetch, ref transactions, quarantine migration) need: [3](#0-2) 

Inside `fetchRemoteAtomic`, two separate `updateref.Updater` transactions are used specifically because bulk atomic updates cannot express F/D-conflict-safe pruning, so pruned refs are committed **first**, in their own transaction, before the remaining ref updates are prepared: [4](#0-3) [5](#0-4) 

Only after `prunedUpdater.Commit()` has already been durably applied does the code proceed to `refUpdater.Prepare()`, migrate the quarantined objects out of the temporary directory, and finally `refUpdater.Commit()`: [6](#0-5) 

Because all of these calls share the single context created from the caller-supplied `Timeout`, a small enough timeout value lets `prunedUpdater.Commit()` finish (its own git-update-ref subprocess exits before the deadline) while the *subsequent* `refUpdater.Prepare()`, `quarantineDir.Migrate(ctx)`, or `refUpdater.Commit()` calls are cut short by context cancellation and return an error. The quarantine directory is unconditionally cleaned up via `defer quarantineCleanup()` regardless of how the function returns, and the design explicitly states that objects only staged in the quarantine (never migrated) are discarded on cancellation: [7](#0-6) [8](#0-7) 

The net effect: the RPC returns an error (e.g. "committing reference update: context deadline exceeded" from line 234-236), giving the caller the impression the fetch failed and nothing changed, yet the pruned-reference transaction already deleted references on disk permanently, and the newly-fetched objects/refs that should have replaced them are discarded with the quarantine directory. Any commits that were only reachable through the pruned refs (and not yet linked by the un-applied `refUpdater` updates) become unreachable and are eligible for garbage collection — a partial, silent, and irrecoverable divergence from the caller's expectations, directly analogous to a partially-funded L2 message that debits L1 but never credits L2.

### Impact Explanation
This is a violation of the atomicity contract that `fetchRemoteAtomic` explicitly promises in its own documentation. An ordinary caller of the `FetchRemote` RPC (e.g., a pull-mirror sync, which is a standard, unprivileged-relative-to-the-repo operation) can trigger this by supplying an aggressively low `timeout_seconds` field relative to the size/duration of the fetch. The result is a repository left in a state where references were deleted (pruned) without the corresponding updates being applied — data (previously-reachable commits) can become unreachable and eventually pruned by garbage collection, which is a form of repository corruption/loss of committed history reachable only through the deleted refs, requiring administrator intervention to detect and potentially unrecoverable once GC runs.

### Likelihood Explanation
Likelihood is moderate: it requires (a) a fetch that includes both pruned refs and other ref updates, and (b) a `Timeout` value tight enough to let the first `git-update-ref` transaction (pruned refs, typically fast) complete but not the second (which includes the potentially large `Migrate` step copying newly fetched objects). Since `Timeout` is a caller-supplied field with no server-side floor, a caller (malicious, careless automation, or a misconfigured mirror sync) can reliably reproduce this by tuning the timeout against the fetch/migrate duration, similar to intentionally underpaying `l2Gas` to trigger a specific partial-failure window.

### Recommendation
- Do not let a single caller-supplied deadline span multiple independently-committed, order-dependent transactions. Either treat `prunedUpdater` and `refUpdater` as a single logical unit that both succeed or both roll back, or defer/skip the prune commit until the primary ref transaction is guaranteed to also succeed.
- Enforce a server-side minimum/derived timeout budget so that a caller cannot request a deadline shorter than what's needed to safely complete or cleanly abort the whole atomic sequence.
- If partial commit is unavoidable given F/D-conflict constraints, make the failure mode explicit and safe: e.g., detect that pruned refs were already committed but the main ref update failed, and surface this loudly (structured error/metric) rather than a generic `context deadline exceeded`, and/or attempt best-effort re-linking or refuse to prune until the corresponding replacement refs are staged.
- Document the risk clearly if it cannot be fully engineered away, per the same “Recommendation” pattern used for `DisconnectGitAlternates`, which already acknowledges and documents a similar "repository stays in a broken state until an administrator intervenes" risk. [9](#0-8) 

### Proof of Concept
1. Set up a repository with pull-mirror-style refspecs such that a fetch will both (a) prune at least one local ref not present on the remote, and (b) update/fetch a separate ref with a reasonably large new object graph (e.g. a large new commit/blob).
2. Call `FetchRemote` with `remote_params` pointing at the crafted remote and `timeout` set to a small value tuned so that:
   - `git-fetch --dry-run` completes,
   - `prunedUpdater.Start/Prepare/Commit` (fast, only ref pointer deletion) completes before the deadline,
   - but `quarantineDir.Migrate(ctx)` (copying/linking the large new objects) or `refUpdater.Commit()` is interrupted by context cancellation.
3. Observe the RPC returns an error such as `"migrating quarantined objects: context deadline exceeded"` or `"committing reference update: context deadline exceeded"`. [10](#0-9) 
4. Inspect the repository: the pruned reference is gone (committed in step 2's `prunedUpdater.Commit()`), but the reference that should have been updated with new commits is unchanged/missing, and the fetched objects were discarded with the quarantine directory cleanup. Any commit(s) reachable only via the pruned ref and not yet re-linked by the un-applied update are now unreachable, and will be removed by a subsequent `git gc`.

func (s *server) FetchRemote(ctx context.Context, req *gitalypb.FetchRemoteRequest) (*gitalypb.FetchRemoteResponse, error) {
	if err := s.validateFetchRemoteRequest(ctx, req); err != nil {
		return nil, err
	}

	if req.GetTimeout() > 0 {
		var cancel context.CancelFunc
		ctx, cancel = context.WithTimeout(ctx, time.Duration(req.GetTimeout())*time.Second)
		defer cancel()
	}

	tagsChanged, repoChanged, err := s.fetchRemoteAtomic(ctx, req)
	if err != nil {
		return nil, err
	}

	return &gitalypb.FetchRemoteResponse{TagsChanged: tagsChanged, RepoChanged: repoChanged}, nil
}

	// A repository cannot contain references with F/D (file/directory) conflicts (i.e.
	// `refs/heads/foo` and `refs/heads/foo/bar`). If fetching from the remote repository
	// results in an F/D conflict, the reference update fails. In some cases a conflicting
	// reference may exist locally that does not exist on the remote. In this scenario, if
	// outdated references are first pruned locally, the F/D conflict can be avoided. When
	// `git-fetch(1)` is performed with the `--prune` and `--dry-run` flags, the pruned
	// references are also included in the output without performing any actual reference
	// updates. Bulk atomic reference updates performed by `git-update-ref(1)` do not support
	// F/D conflicts even if the conflicted reference is being pruned. Therefore, pruned
	// references must be updated first in a separate transaction. To accommodate this, two
	// different instances of `updateref.Updater` are used to keep the transactions separate.
	prunedUpdater, err := updateref.New(ctx, quarantineRepo)
	if err != nil {
		return false, false, fmt.Errorf("spawning pruned updater: %w", err)
	}
	defer func() {
		if err := prunedUpdater.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("cancel pruned updater: %w", err)
		}
	}()

	// All other reference updates can be queued as part of the same transaction.
	refUpdater, err := updateref.New(ctx, quarantineRepo)
	if err != nil {
		return false, false, fmt.Errorf("spawning ref updater: %w", err)
	}
	defer func() {
		if err := refUpdater.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("cancel ref updater: %w", err)
		}
	}()
