### Title
Out-of-bounds slice access in Go linker's archive symbol-map parser `readArmap` on a malformed host archive - (File: src/cmd/link/internal/ld/ar.go)

### Summary
`readArmap` in the Go linker parses the `/` or `/SYM64/` symbol-map member of a host archive (e.g. `libgcc.a` or any `.a` file supplied to `cgo`/host linking) without validating that the declared member size is large enough to hold the fixed-size count field or that the resulting name table actually contains a NUL terminator. A crafted archive with a short or truncated symbol-map member causes the linker to panic with an out-of-bounds slice/index access, mirroring the crafted-binary out-of-bounds read in `core_anal_bytes` from CVE-2018-20461.

### Finding Description
`hostArchive` reads the archive magic and first header, then calls `readArmap(name, f, arhdr)` when the member name is `/` or `/SYM64/`. Inside `readArmap`: [1](#0-0) 
`contents` is allocated with the size taken directly from the attacker-controlled ASCII header field `arhdr.size` (via `atolwhex`), then `binary.BigEndian.Uint32/Uint64(contents)` is read unconditionally and `contents = contents[wordSize:]` is sliced without checking `len(contents) >= wordSize`. If the archive declares a member size smaller than `wordSize` (or zero), `binary.BigEndian.Uint32/Uint64` and the subsequent slice will panic with an out-of-range/short-buffer access.

Further down, the name-table walk is equally unchecked: [2](#0-1) 
`names[n] != 0` scans for a NUL terminator with no bound on `n`; if the crafted symbol-map member never contains a terminating NUL (or `c` is inflated relative to the real content length via `names := contents[c*uint64(wordSize):]`), the loop indexes past the end of `names` and panics with "index out of range". This is the direct analog of `core_anal_bytes`'s missing bounds check before dereferencing attacker-controlled offsets in a crafted binary.

### Impact Explanation
The impact is a crash (denial of service) of the `go` linker/build process when it processes a maliciously crafted archive file, analogous to the radare2 crash on a crafted binary. There is no memory corruption because Go's runtime converts the out-of-bounds access into a panic rather than a silent OOB read, but the linker process still terminates unexpectedly. This would be assessed on Go's PUBLIC track as a low-severity DoS in a build tool, since it requires the victim to explicitly link against an untrusted archive.

### Likelihood Explanation
Exploitation requires a victim to run `go build`/`go link` (typically via cgo) against a host archive file (`.a`) that the attacker controls or has tampered with — for example, a dependency's bundled static library or a value supplied via `CGO_LDFLAGS`. This is a real but narrow workflow: it is not an unauthenticated network path, and per Go's security decisions, `go build` invoking the linker on locally supplied archives is closer to "processing local build artifacts" than "malicious source execution," but it still fits the "malicious/crafted file consumed by an ordinary workflow" pattern from the report if the archive originates from an untrusted third-party dependency's prebuilt object.

### Recommendation
In `readArmap` (`src/cmd/link/internal/ld/ar.go`), validate `len(contents) >= wordSize` before reading `Uint32`/`Uint64` and before slicing `contents[wordSize:]`; validate `c*wordSize <= len(contents)` before computing `names`; and bound the NUL-scan loop (`for n < len(names) && names[n] != 0`) to avoid indexing past the end of the buffer, returning a descriptive linker error (e.g. via `Exitf`) instead of panicking.

func readArmap(filename string, f *bio.Reader, arhdr ArHdr) archiveMap {
	is64 := arhdr.name == "/SYM64/"
	wordSize := 4
	if is64 {
		wordSize = 8
	}

	contents := make([]byte, atolwhex(arhdr.size))
	if _, err := io.ReadFull(f, contents); err != nil {
		Exitf("short read from %s", filename)
	}

	var c uint64
	if is64 {
		c = binary.BigEndian.Uint64(contents)
	} else {
		c = uint64(binary.BigEndian.Uint32(contents))
	}
	contents = contents[wordSize:]
