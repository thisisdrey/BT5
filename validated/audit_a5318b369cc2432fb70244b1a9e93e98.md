### Title
Attacker can fill a victim's `depositTokensOfAccount` list with dust deposit tokens via `deposit(onBehalfOf)`/`transfer`, blocking the victim from adding new collateral types and forcing avoidable liquidation - ([File: contracts/DepositToken.sol])

### Summary
The QEMU bug class is a resource-exhaustion DoS: a repeated cheap operation (device unplug) leaks a finite resource until the process dies. The Metronome analog is the per-account token list in `Pool`: each account may hold at most `MAX_TOKENS_PER_USER = 30` distinct deposit/debt tokens, tracked in `depositTokensOfAccount`/`debtTokensOfAccount` (`MappedEnumerableSet`). Anyone can forcibly grow another account's list by depositing dust `onBehalfOf` the victim or by transferring dust msdTokens to them, since `_mint`/`_transfer` call `pool.addToDepositTokensOfAccount(recipient_)` with no opt-in from the recipient.

### Finding Description
`Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (`Pool.sol:143-148`, `Pool.sol:216-220`). `DepositToken._mint` and `DepositToken._transfer` unconditionally add the recipient to the list when their balance goes from 0 to non-zero (`DepositToken.sol:485-489`, `DepositToken.sol:517-520`). There is no minimum amount and no recipient consent:

- `deposit(amount_, onBehalfOf_)` lets an attacker mint dust msdTokens directly to any victim address (`DepositToken.sol:211-237`).
- `transfer`/`transferFrom` let an attacker push 1-wei dust of each deposit token to the victim (`DepositToken.sol:348-376`).

After the attacker's first fill, every subsequent `addToDepositTokensOfAccount(victim)` reverts, so `deposit` into any *new* collateral type, `deposit` on behalf of the victim, and inbound transfers of new msdTokens all revert. The victim can only free a slot by fully withdrawing/transferring one of the dusted tokens — which the attacker can immediately re-fill by front-running with another dust deposit/transfer, keeping the account saturated indefinitely at near-zero marginal cost.

### Impact Explanation
Denial of the deposit path for new collateral types. If the victim holds a leveraged/debt position that drifts toward the liquidation threshold, the victim cannot add a new collateral asset to restore health — every `deposit` of a collateral they don't already hold reverts inside `_mint` → `addToDepositTokensOfAccount`. While the position is unhealthy, `Pool.liquidate` can be executed by anyone, so the victim suffers liquidation losses (seized collateral + protocol fee) that proper top-up would have avoided. This is a temporary freezing of funds / forced-liquidation outcome, not merely a gas-grief: the attacker can sustain the block by re-dusting freed slots each block. Mirroring CVE-2017-5579, repeated cheap operations exhaust a bounded resource (the 30-slot list) to deny service.

### Likelihood Explanation
- Fully unprivileged: any EOA can call `deposit(amount, victim)` or `transfer(victim, dust)` on each whitelisted `DepositToken`; no privileged role, oracle manipulation, or malicious endpoint needed.
- Cost is bounded by acquiring tiny amounts of each whitelisted underlying (or buying dust msdTokens once and re-dusting after each victim cleanup). It only becomes expensive if the pool has ~30 deposit tokens; on deployments with fewer collaterals it is trivially cheap.
- Caveats: (1) the victim can free slots by emptying a dusted position, so the attacker must keep front-running or re-dusting; (2) the victim can still deposit into collateral types they already hold, so the attack matters most when the victim needs a *new* collateral to avoid liquidation or when a victim expects a specific deposit (e.g., via `NativeTokenGateway`/zap flows that would revert).

### Recommendation
- Enforce a minimum first-deposit/mint amount per account-token pair, or a minimum USD value, so filling all 30 slots costs real capital.
- Alternatively, require recipient opt-in for list insertion: skip `addToDepositTokensOfAccount` on `transfer`/`deposit(onBehalfOf != msg.sender)` below a threshold, or make `addToDepositTokensOfAccount` idempotent and lazy (only add when the recipient's balance exceeds a dust floor).
- At minimum, let `deposit` succeed without adding to the list when the minted amount is below a configurable dust threshold, so griefing dust cannot occupy slots.

### Proof of Concept
Hardhat-style PoC (pool with at least two deposit tokens `dtA`, `dtB`; victim already holds `dtA` and a debt position):

```ts
// Attacker fills victim's 30 slots with dust
const depositTokens = await pool.getDepositTokens(); // N collaterals
for (const dt of depositTokens) {
  const token = await ethers.getContractAt('DepositToken', dt);
  const underlying = await ethers.getContractAt('IERC20', await token.underlying());
  await underlying.connect(attacker).approve(token.address, 1);
  // mint 1 wei of msdTOKEN directly to the victim
  await token.connect(attacker).deposit(1, victim.address);
}
// Optional: also dust a debt token to victim via repay on victim's behalf
// to push debtTokensOfAccount.length + depositTokensOfAccount.length to 30.

// Victim now cannot deposit a collateral type it does not already hold
const newDt = await ethers.getContractAt('DepositToken', someNewCollateral);
await underlyingOf(newDt).connect(victim).approve(newDt.address, amount);
await expect(
  newDt.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// While blocked, victim's position drifts unhealthy (price move)
await expect(
  pool.connect(liquidator).liquidate(victim.address, repayAmt, dtA.address, msSynth.address)
).to.emit(pool, 'PositionLiquidated');

// If victim withdraws a dust token to free a slot, attacker front-runs:
await newDtDust.connect(attacker).transfer(victim.address, 1); // re-fills slot
await expect(
  newDt.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Invariants checked: `onlyIfAdditionWillNotReachMaxTokens` is the only guard and it protects the pool, not the victim; `nonReentrant`, pause flags, and `SynthContext` checks do not prevent dust `deposit`/`transfer` to arbitrary recipients.
