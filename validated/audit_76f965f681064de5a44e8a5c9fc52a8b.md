### Title
Unrestricted Git URL schemes in `CreateRepositoryFromURL`/`FetchRemote`/`UpdateRemoteMirror` allow arbitrary command execution via git's `ext::` transport - ([File: internal/gitaly/service/repository/create_repository_from_url.go])

### Summary
Gitaly builds `git-clone(1)`/`git-fetch(1)`/`git-remote(1)` invocations using a user-supplied remote URL (`CreateRepositoryFromURLRequest.Url`, `FetchRemoteRequest.RemoteParams.Url`, `Remote.Url` in `UpdateRemoteMirror`, `FindRemoteRootRefRequest.RemoteUrl`) without ever restricting the URL's transport scheme. Because Gitaly invokes `git` via `exec.CommandContext` with an argv array (not a shell), the classic pm2-style `;`-based shell injection does not apply here. However, git itself supports the `ext::<command>` remote helper transport, which executes an arbitrary shell command as part of establishing the "remote" connection. Since Gitaly passes the caller-supplied URL string through essentially unvalidated (only scheme-based rewriting for DNS-rebind protection, and generic `url.Parse`/`url.ParseRequestURI`), an actor who can trigger any of these RPCs with an attacker-chosen remote URL can achieve command execution in the context of the `gitaly` process.

### Finding Description
`cloneFromURLCommand` in `internal/gitaly/service/repository/create_repository_from_url.go` takes `req.GetUrl()`, parses it with `url.Parse`, and passes the resulting string directly as a positional argument to `git clone`: [1](#0-0) 

There is no allow-list of schemes (`http`, `https`, `git`, `ssh`) enforced before the URL reaches `git-clone(1)`. The only validation performed is `validateCreateRepositoryFromURLRequest`, which merely checks that the URL is non-empty: [2](#0-1) 

The same unrestricted-URL pattern recurs in `buildCommandOpts` for `FetchRemote`: [3](#0-2) 
and in `validateFetchRemoteRequest`, which likewise only checks for blank/empty URL: [4](#0-3) 

and in `updateRemoteMirror`: [5](#0-4) 

and in `findRemoteRootRefCmd`: [6](#0-5) 

`GetURLAndResolveConfig`, the only helper that inspects the URL structure, only special-cases `http://`, `https://`, `git://`, `ssh://`, and falls back to treating anything else as an SCP-like URL — it does not reject dangerous schemes such as `ext::` or `fd::`, and it is only invoked when `resolved_address` is set, so it provides no protection in the default path: [7](#0-6) 

Because Git natively implements the `ext::<command>` remote helper (`git help remote-ext`), supplying a URL like `ext::sh -c "id > /tmp/pwned"` to any of these RPCs will cause git itself to spawn the specified command when Gitaly executes `git clone`/`git fetch`/`git remote show` against that URL — regardless of the fact that Gitaly's own `exec.CommandContext` call is not a shell invocation. The vulnerability is functionally analogous to the reported pm2 issue: an externally-supplied string embedded into a tool invocation (there: `tar`; here: `git`) is interpreted by that downstream tool in a way that results in arbitrary command execution, because the calling code failed to sanitize/allow-list the untrusted value before handing it to the subprocess.

### Impact Explanation
Any caller able to invoke `CreateRepositoryFromURL`, `FetchRemote`, `UpdateRemoteMirror`, or `FindRemoteRootRef` with an attacker-controlled URL (e.g., a project import/mirror configuration surfaced by GitLab, or any consumer of the Gitaly gRPC API that forwards a user-specified remote/import URL) can achieve remote code execution inside the Gitaly process, running with the privileges of the `gitaly` service account. This is a full compromise of the Gitaly node: attackers could read/write arbitrary repositories on that storage, exfiltrate secrets accessible to the process, or pivot further into the infrastructure.

### Likelihood Explanation
The RPCs are reachable directly via gRPC by any client holding a valid Gitaly auth token (which in a GitLab deployment includes the Rails/GitLab application on behalf of ordinary users performing "import project by URL" or "set up push/pull mirror" actions — an ordinary, unprivileged user-facing feature). No special privilege beyond normal repository-management permissions is required to supply the URL field, since Gitaly performs no scheme allow-listing itself and relies entirely on the caller (GitLab) to have done so. If GitLab's Rails-layer URL validation is bypassed, is incomplete, or if a caller talks to Gitaly directly, the RCE is trivially reachable.

### Recommendation
Add strict remote-URL scheme validation in Gitaly itself, independent of any upstream (GitLab Rails) checks, before passing URLs to `git clone`/`git fetch`/`git remote`:
- Reject any URL whose scheme is not in an explicit allow-list (`http`, `https`, `git`, `ssh`, and SCP-like `user@host:path` forms).
- Explicitly reject `ext::`, `fd::`, `file://`, and any other Git "remote helper" scheme forms.
- Consider setting `GIT_ALLOW_PROTOCOL`/`protocol.allow` git configuration on all invoked git subprocesses to restrict transports at the Git level as defense-in-depth, since no such restriction currently appears to be applied globally.
- Apply this validation uniformly across `CreateRepositoryFromURL`, `FetchRemote`, `UpdateRemoteMirror`, and `FindRemoteRootRef`.

### Proof of Concept
1. Call the `CreateRepositoryFromURL` RPC with:
```
Repository: { storage_name: "default", relative_path: "poc.git" }
Url: "ext::sh -c \"touch /tmp/gitaly_pwned\""
```
2. Gitaly's `cloneFromURLCommand` builds and executes `git clone --quiet --bare ext::sh -c "touch /tmp/gitaly_pwned" <target-path>`.
3. Git's `ext::` remote helper spawns `sh -c "touch /tmp/gitaly_pwned"` as a subprocess of the Gitaly process, creating `/tmp/gitaly_pwned`, demonstrating arbitrary command execution.

(Note: I could not fully verify within the available index whether any upstream caller such as the GitLab Rails application performs its own scheme allow-listing before invoking these RPCs, nor whether `GIT_ALLOW_PROTOCOL` is set at the OS/environment level outside of the repo. If such external mitigations exist, the practical exploitability could be reduced, but no such control was found within the Gitaly codebase itself.)

func buildCommandOpts(ctx context.Context, opts *localrepo.FetchOpts, req *gitalypb.FetchRemoteRequest) error {
	remoteURL := req.GetRemoteParams().GetUrl()
	var config []gitcmd.ConfigPair

	for _, refspec := range getRefspecs(req.GetRemoteParams().GetMirrorRefmaps()) {
		config = append(config, gitcmd.ConfigPair{
			Key: "remote.inmemory.fetch", Value: refspec,
		})
	}

	if resolvedAddress := req.GetRemoteParams().GetResolvedAddress(); resolvedAddress != "" {
		modifiedURL, resolveConfig, err := gitcmd.GetURLAndResolveConfig(remoteURL, resolvedAddress)
		if err != nil {
			return fmt.Errorf("couldn't get curloptResolve config: %w", err)
		}

		remoteURL = modifiedURL
		config = append(config, resolveConfig...)
	}

	config = append(config, gitcmd.ConfigPair{Key: "remote.inmemory.url", Value: remoteURL})

	if featureflag.FetchRemoteProactiveAuth.IsEnabled(ctx) {
		if u, err := url.Parse(remoteURL); err == nil && u.User != nil {
			password, _ := u.User.Password()
			if u.User.Username() != "" && password != "" {
				config = append(config, gitcmd.ConfigPair{
					Key:   "http.proactiveAuth",
					Value: "basic",
				})
			}
		}
	}

	if authHeader := req.GetRemoteParams().GetHttpAuthorizationHeader(); authHeader != "" {
		config = append(config, gitcmd.ConfigPair{
			Key:   fmt.Sprintf("http.%s.extraHeader", req.GetRemoteParams().GetUrl()),
			Value: "Authorization: " + authHeader,
		})
	}

	opts.CommandOptions = append(opts.CommandOptions, gitcmd.WithConfigEnv(config...))

	return nil
}

func GetURLAndResolveConfig(remoteURL string, resolvedAddress string) (string, []ConfigPair, error) {
	if remoteURL == "" {
		return "", nil, fmt.Errorf("URL is empty")
	}

	if resolvedAddress == "" {
		return "", nil, fmt.Errorf("resolved address is empty")
	}

	resolvedIP := net.ParseIP(resolvedAddress)
	if resolvedIP == nil {
		return "", nil, fmt.Errorf("resolved address has invalid IPv4/IPv6 address")
	}

	switch {
	case strings.HasPrefix(remoteURL, "http://"), strings.HasPrefix(remoteURL, "https://"), strings.HasPrefix(remoteURL, "git://"):
		return getURLAndResolveConfigForURL(remoteURL, resolvedAddress)
	case strings.HasPrefix(remoteURL, "ssh://"):
		return getURLAndResolveConfigForSSH(remoteURL, resolvedAddress)
	default:
		return getURLAndResolveConfigForSCP(remoteURL, resolvedAddress)
	}
