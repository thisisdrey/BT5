### Title
Oracle price data becomes permanently stale after prolonged feeder downtime and is served to consumers without any freshness signal - (File: `substrate/frame/honzon/oracle/src/default_combine_data.rs`)

### Summary
`pallet-oracle`'s default aggregation strategy, `DefaultCombineData`, filters out expired raw submissions using an `ExpiresIn` window, but when *all* raw values become expired (e.g. because oracle operators go silent/offline for longer than `ExpiresIn`), it falls back to silently re-returning the last known aggregated value (`prev_value`) as if it were current. This value is then written back into the `Values` storage map and served through `DataProvider::get()` (and the runtime's `OracleApi::get_value`) with the timestamp stripped, so any consumer using the plain `DataProvider` interface cannot detect that the price is stale. This mirrors the reported UniswapV3-on-L2 bug class: a pricing oracle extrapolates old data across a "downtime" period, and callers unconditionally treat the extrapolated value as fresh, enabling exploitation of a stale price once activity (a transaction) resumes.

### Finding Description
`DefaultCombineData::combine_data` at [1](#0-0)  works as follows:

```rust
fn combine_data(..., mut values: Vec<TimestampedValueOf<T, I>>, prev_value: Option<TimestampedValueOf<T, I>>) -> Option<TimestampedValueOf<T, I>> {
    let expires_in = ExpiresIn::get();
    let now = T::Time::now();
    values.retain(|x| x.timestamp.saturating_add(expires_in) > now);
    let count = values.len() as u32;
    let minimum_count = MinimumCount::get();
    if count < minimum_count || count == 0 {
        return prev_value;
    }
    ...
}
```

If every operator's raw submission has aged out (`count == 0`, i.e. no operator has fed a value within `ExpiresIn`), the function does not return `None` — it returns `prev_value` unchanged, timestamp and all. `do_feed_values` at [2](#0-1)  then writes this stale, unchanged value straight back into `Values<T, I>` any time even a single operator feeds *any* unrelated key (because `combined()` is invoked per fed key, but the storage write path re-uses the exact same stale `TimestampedValue`).

More importantly, `Values` storage keeps returning this old entry indefinitely via `Pallet::get()`, [3](#0-2) . Consumers that use the plain `DataProvider` trait — the interface the pallet documents as the integration point for other pallets ("other pallets can use the `DataProvider` trait to read the aggregated data") — get only the raw value with the timestamp stripped:

```rust
impl<T: Config<I>, I: 'static> DataProvider<T::OracleKey, T::OracleValue> for Pallet<T, I> {
    fn get(key: &T::OracleKey) -> Option<T::OracleValue> {
        Self::get(key).map(|timestamped_value| timestamped_value.value)
    }
}
``` [4](#0-3) 

The same stripping happens in the kitchensink runtime's exposed `OracleApi::get_value`:
```rust
fn get_value(_provider_id: u32, key: u32) -> Option<u128> {
    pallet_oracle::Pallet::<Runtime>::get(&key).map(|v| v.value)
}
``` [5](#0-4) 

No expiry/liveness check is performed at the consumption boundary — the pallet's freshness protection (`ExpiresIn`) is purely internal to `combine_data`, and it explicitly degrades to "keep serving the old value" instead of "fail closed" the moment feeder liveness is lost for longer than the configured window. Any downstream pallet built on `DataProvider<OracleKey, OracleValue>` (the pallet's own documented consumption pattern) inherits this silent staleness with zero mitigation, exactly like `_validateAndGetPrice` extrapolating a stale TWAP across sequencer downtime.

### Impact Explanation
If oracle members (feeders) stop submitting for longer than `ExpiresIn` — due to a coordinated pause, network partition, feeder client outage, or simply governance temporarily reducing/rotating `Members` — the last aggregated price keeps being treated as authoritative and fresh by any consuming pallet that relies on `DataProvider::get()`/`OracleApi::get_value` without independently re-checking the timestamp via `DataProviderExtended`. Any pricing, collateralization, liquidation, or peg/PSM-style logic built on top of this primitive would accept an outdated price once feeding resumes or continues intermittently, letting an attacker who is aware of the true off-chain price act against the stale on-chain quote (borrow against overvalued collateral, mint against an inflated peg, avoid liquidation, or trigger unwarranted liquidation of others) — a direct analog to the reported "false state acceptance" / "public underpriced work" impact class, rooted in an implementation bug rather than any admin/relayer misbehavior.

### Likelihood Explanation
No privileged action is required to trigger this: oracle feeder downtime can occur naturally (client crash, network partition) or be induced by any actor capable of temporarily preventing feeders from submitting (e.g., transaction-pool congestion targeting oracle accounts, or simply waiting out a known low-liquidity/inactive period). Because `combine_data`'s fallback to `prev_value` is the pallet's *only* fallback path and it is unconditionally silent (no error, no `None`, no event indicating staleness), any runtime wiring `pallet-oracle` behind price-sensitive logic via the documented `DataProvider` trait is affected by default with no extra configuration needed to reproduce.

### Recommendation
- Change `DefaultCombineData::combine_data` to return `None` (rather than `prev_value`) once the previous value's own timestamp has exceeded `ExpiresIn`, so genuinely stale data cannot be perpetually recycled.
- Extend the `DataProvider` trait (or provide a `get_no_op`-safe variant) that exposes staleness/expiry status to consumers, and update pallet documentation to require consumers to check `DataProviderExtended`/timestamp rather than the bare `DataProvider::get()`.
- Consider emitting an event/flag when the oracle falls back to `prev_value` so downstream governance/monitoring can react to feeder liveness loss.

### Proof of Concept
1. Configure a runtime with `pallet-oracle` using `DefaultCombineData<T, MinimumCount, ExpiresIn>` and a consuming pallet (e.g., a hypothetical lending/PSM pallet) that reads prices via `pallet_oracle::DataProvider::get(key)`.
2. Feed a price at `T::Time::now() = t0` from `MinimumCount` operators; `Values<key>` is set to `{value: P, timestamp: t0}`.
3. Advance time past `t0 + ExpiresIn` with no further submissions (simulating "sequencer/oracle-feeder downtime").
4. Any other unrelated `feed_values` call that triggers `combined()` for `key` finds `count == 0` after the `retain` filter and returns `prev_value = {value: P, timestamp: t0}` verbatim, re-persisting stale `P` into `Values<key>`.
5. A consumer calls `DataProvider::get(&key)` (or `OracleApi::get_value`) and receives `P` with no indication it is stale — the same `P` that was valid at `t0` is now treated as the live market price at `t0 + ExpiresIn + Δ`, even though the real off-chain price may have diverged significantly, exactly as `OracleLibrary.consult()` extrapolates a stale TWAP across L2 sequencer downtime in the referenced report.

	fn combine_data(
		_key: &<T as Config<I>>::OracleKey,
		mut values: Vec<TimestampedValueOf<T, I>>,
		prev_value: Option<TimestampedValueOf<T, I>>,
	) -> Option<TimestampedValueOf<T, I>> {
		let expires_in = ExpiresIn::get();
		let now = T::Time::now();

		values.retain(|x| x.timestamp.saturating_add(expires_in) > now);

		let count = values.len() as u32;
		let minimum_count = MinimumCount::get();
		if count < minimum_count || count == 0 {
			return prev_value;
		}

		let mid_index = count / 2;
		// Won't panic as `values` ensured not empty.
		let (_, value, _) =
			values.select_nth_unstable_by(mid_index as usize, |a, b| a.value.cmp(&b.value));
		Some(value.clone())
	}
