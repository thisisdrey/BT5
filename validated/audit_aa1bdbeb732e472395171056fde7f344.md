### Title
Floating-point precision loss in the TRX/TRC10 Exchange (Bancor-formula) pricing engine allows value extraction via crafted trade sequences - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
The Balancer incident stemmed from a rounding/invariant-calculation defect in an AMM pricing engine that let an attacker manipulate pool math to extract more value than deposited. java-tron's built-in `Exchange`/`ExchangeV2` market (a Bancor-formula AMM between TRX and TRC10 tokens, driven by `ExchangeInjectActuator`, `ExchangeTransactionActuator`, and `ExchangeWithdrawActuator`) has an analogous bug class: its default pricing math (`ExchangeProcessor`) computes trade output using Java `double` floating point and `Math.pow`, rather than the exact `BigDecimal` arithmetic used by the newer `SafeExchangeProcessor`.

### Finding Description
`ExchangeCapsule.transaction()` selects between two pricing implementations depending on a governance-controlled flag: [1](#0-0) 

When `hardenedCalc` is false (the historical/default behavior unless the `ALLOW_HARDEN_EXCHANGE_CALCULATION` committee proposal has been activated), every trade routes through `ExchangeProcessor`, which computes the Bancor "relay" issuance and redemption using IEEE-754 `double` math and `Math.pow`: [2](#0-1) 

This is invoked directly from `ExchangeTransactionActuator.execute()`/`doValidate()` for any unprivileged, signed `ExchangeTransactionContract`: [3](#0-2) 

Floating-point `pow`/division introduces rounding error that is *asymmetric* with respect to trade direction and size — this is precisely the class of bug (invariant/rounding manipulation in a pooled AMM) that Balancer's incident exploited to drain value through carefully sized, repeated operations. The project's own regression test confirms the two math paths diverge for the same inputs: [4](#0-3) 

The `AbstractExchangeActuator` explicitly gates the exact-arithmetic (`addExact`/`subtractExact`) balance updates on the same governance flag, meaning under default configuration the plain non-hardened arithmetic paths are used everywhere in the actuators: [5](#0-4) 

### Impact Explanation
If the floating-point path is reachable in production (i.e., the hardened-calculation proposal has not been activated on a given chain), an attacker who understands the specific rounding behavior of `Math.pow` at chosen input magnitudes could structure a sequence of `ExchangeTransactionContract` and `ExchangeInjectContract`/`ExchangeWithdrawContract` calls (all reachable by any signed transaction, no privilege required) to accumulate systematic rounding gains at the expense of the pool's TRX/TRC10 balances, resulting in unbacked-balance extraction from the exchange pool — a direct funds-theft/permanent-freezing-of-funds class impact matching the required severity bar.

### Likelihood Explanation
Likelihood depends entirely on whether `ALLOW_HARDEN_EXCHANGE_CALCULATION` is active on the target network; the presence of the `SafeExchangeProcessor`/`hardenedCalc` remediation path and its dedicated tests indicates the maintainers already identified and partially mitigated float-precision risk in this code area, but the mitigation is opt-in via governance rather than the default computational path, so any chain/environment where the proposal has not passed remains exposed to the original floating-point rounding weakness in the live actuators.

### Recommendation
Make `SafeExchangeProcessor` (BigDecimal-based, `RoundingMode`-explicit) the unconditional default for `ExchangeCapsule.transaction()` rather than gating it behind a proposal flag, and add fuzzing/property tests asserting rounding is always in the protocol's favor across boundary values.

### Proof of Concept
Not independently verified in this pass — validating exploitability requires confirming the live value of `allowHardenExchangeCalculation()`/its DynamicPropertiesStore default and constructing a concrete profitable trade sequence against `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`; this would require running the actuator with representative pool balances (as in `ExchangeProcessorTest`) to demonstrate net-positive extraction, which was not completed due to tool/iteration limits.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
