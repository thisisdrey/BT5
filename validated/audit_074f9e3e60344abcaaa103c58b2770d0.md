### Title
Attacker-triggerable panic in `OccurrenceStrategy` background goroutines can crash the shared Gitaly process - (File: internal/bundleuri/strategy_occurences.go)

### Summary
The bundle-URI `OccurrenceStrategy` spawns detached background goroutines (`startEvaluationWorker`, `startGenerationWorkers`, `startStateGc`) via plain `go func(){...}` in `Start()` [1](#0-0) , none of which are wrapped with panic recovery. Any panic inside these goroutines — including inside the attacker-influenced generation callback executed via `request.cb(request.ctx, request.repo)` in `startGenerationWorkers` [2](#0-1)  — happens on a goroutine stack that `panichandler.handleCrash`'s `recover()` (bound only to the RPC-handling goroutine via `defer` in `UnaryPanicHandler`/`StreamPanicHandler`) cannot catch, per Go's per-goroutine `recover()` semantics [3](#0-2) , and would crash the whole `gitaly` process.

### Finding Description
`GenerateBundleURI` RPC calls `s.bundleURIManager.Generate(ctx, repo)` [4](#0-3) , which (per `internal/bundleuri/manager.go`) ultimately feeds requests into `OccurrenceStrategy.Evaluate`, queued onto `evaluateQueue`/`generateQueue` and processed asynchronously by the background workers started in `Start()`. These workers run in goroutines separate from the gRPC handler's call stack; the panic-handling interceptors (`UnaryPanicHandler`/`StreamPanicHandler`) only install a `defer handleCrash(...)` on the goroutine executing the interceptor/handler chain for that specific RPC call [5](#0-4) . Because Go's `recover()` only unwinds panics on the same goroutine, a panic raised inside `startEvaluationWorker`, `startGenerationWorkers`, or `startStateGc` — for example from `state.occurrences[len(state.occurrences)-1]` indexing bugs, a nil `request.repo`, or a panic surfaced from the `cb` bundle-generation callback processing attacker-influenced repository content — is unrecoverable by `handleCrash` and will propagate up, terminating the entire process per Go runtime semantics.

I could not fully verify (within tool budget) the exact code path inside `cb`/`bundleuri.Manager.Generate` that executes `git bundle create` against repository content, but the structural gap is clear: the `Start()` goroutines lack any panic-recovery wrapper, unlike the codebase's own dedicated `internal/dontpanic` package (`dontpanic.Go`/`dontpanic.Try`) which exists specifically to recover panics in "fire-and-forget" background goroutines [6](#0-5) . `OccurrenceStrategy.Start` does not use `dontpanic` for any of its three worker functions [7](#0-6) .

### Impact Explanation
A panic in any bundle-URI background worker crashes the entire `gitaly` process, terminating all in-flight RPCs and denying service to every repository/tenant hosted on that Gitaly node — full-process crash DoS, matching GitLab's "Denial of Service" bounty impact class for a shared multi-tenant service.

### Likelihood Explanation
Requires an unprivileged user able to trigger `GenerateBundleURI` (or repeated fetch/clone activity that drives bundle-URI generation via the occurrence strategy) against a repository they control, and requires an actual panic-inducing bug to exist in the callback/worker logic reachable from repository content. I was not able to confirm within the available context a concrete panic-inducing input (e.g., a specific nil-dereference or index-out-of-range triggerable purely by repo content) in the generation callback path (`bundleuri.Manager.Generate` / `cb`), so likelihood is currently unproven pending deeper review of `internal/bundleuri/manager.go` and the actual bundle-generation callback implementation.

### Recommendation
Wrap `startEvaluationWorker`, `startGenerationWorkers` (and its inner per-worker goroutines), and `startStateGc` with the existing `internal/dontpanic` package (`dontpanic.Go`/`dontpanic.Try`) or an equivalent `recover()`-based guard, so a panic in one bundle-generation task logs/reports to Sentry and only fails that task instead of crashing the process. Apply the same review to any other `go func(...)` spawn sites reachable from gRPC-triggered code that currently lack recovery.

### Proof of Concept
Not able to provide a concrete reproducible PoC without confirming an actual panic-triggering code path inside the generation callback (`cb`) or `evaluate`/`loadState` logic driven purely by attacker-controlled repository content; this would require inspecting `internal/bundleuri/manager.go` and the bundle-generation command construction, which was not fully retrieved before the tool budget was exhausted. func UnaryPanicHandler(logger log.Logger) grpc.UnaryServerInterceptor {
	return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (resp interface{}, err error) {
		defer handleCrash(logger, info.FullMethod, func(grpcMethodName string, r interface{}) {
			err = toPanicError(grpcMethodName, r)
		})

		return handler(ctx, req)
	}
}

func StreamPanicHandler(logger log.Logger) grpc.StreamServerInterceptor {

		})

	}
}

func handleCrash(logger log.Logger, grpcMethodName string, handler PanicHandler) {
	if r := recover(); r != nil {
		logger.WithFields(log.Fields{
			"error":     r,
			"method":    grpcMethodName,
			"backtrace": string(debug.Stack()),
		}).Error("grpc panic")

		handler(grpcMethodName, r)

		for _, fn := range additionalHandlers {
			fn(grpcMethodName, r)
		}
	}
}

// Try will wrap the provided function with a panic recovery. If a panic occurs,
// the recovered panic will be sent to Sentry and logged as an error.
// Returns `true` if no panic and `false` otherwise.
func Try(logger log.Logger, fn func()) bool { return catchAndLog(logger, fn) }

// Go will run the provided function in a goroutine and recover from any
// panics.  If a panic occurs, the recovered panic will be sent to Sentry
// and logged as an error. Go is best used in fire-and-forget goroutines where
// observability is lost.
func Go(logger log.Logger, fn func()) { go Try(logger, fn) }
