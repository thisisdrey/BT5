### Title
Unsanitized `backup_id` in `BackupRepositoryRequest` allows path traversal / storage escape when resolving backup manifest, bundle, and refs paths - (File: internal/backup/locator.go)

### Summary
The `BackupRepository`/`RestoreRepository` server-side backup RPCs build all on-disk/object-storage paths for a backup (manifest `.toml`, `NNN.bundle`, `NNN.refs`, custom hooks archive) by directly joining the caller-supplied `backup_id` (and `latest_backup_id`) into the target path, without validating that the identifier is a safe path component. This is the same class of bug as the report: "data loaded/used during initialization/chaining is not sufficiently validated," except here the identifier used to resolve the persisted chain of backup steps is attacker-influenced and unsanitized, allowing the chain-building logic (`BeginIncremental`) to read and write outside of the intended per-repository backup directory.

### Finding Description
`validateBackupRepositoryRequest` in `internal/gitaly/service/repository/backup_repository.go` validates the repository fields and the `path_prefix` (via `backup.ValidatePathPrefix`, which explicitly rejects absolute paths and `..` segments), but it never validates `in.GetBackupId()` beyond checking it is non-empty:

```go
func (s *server) validateBackupRepositoryRequest(ctx context.Context, in *gitalypb.BackupRepositoryRequest) error {
	if in.GetBackupId() == "" {
		return fmt.Errorf("empty BackupId")
	}
	...
	if err := backup.ValidatePathPrefix(in.GetPathPrefix()); err != nil {
		return err
	}
	return nil
}
```

The unsanitized `backupID` is subsequently used verbatim to build every storage path for the backup "chain":

```go
func manifestPath(repo storage.Repository, backupID string, backupPathPrefix string) string {
	return path.Join(manifestDirectory(repo, backupPathPrefix), backupID+".toml")
}
``` [1](#0-0) 

and in `ManifestLocator.BeginFull`/`BeginIncremental`:
```go
BundlePath:      filepath.Join(cfg.pathPrefix, storageName, relativePath, backupID, "001.bundle"),
RefPath:         filepath.Join(cfg.pathPrefix, storageName, relativePath, backupID, "001.refs"),
CustomHooksPath: filepath.Join(cfg.pathPrefix, storageName, relativePath, backupID, "001.custom_hooks.tar"),
``` [2](#0-1) 

Because `path.Join`/`filepath.Join` collapse `..` segments, a `backup_id` value such as `../../other-repo/relative/path` (or an absolute-looking value once joined) lets the resulting relative path escape the `storageName/relativePath/backupID/` directory that the design assumes is exclusive to the target repository. The same unsanitized identifier is reused for `latest_backup_id` in `BeginIncremental` (`internal/backup/locator.go:51-118`), which is used to `Find`/`ReadLatestManifest` the "previous" step in the chain, load its `PreviousRefPath`/`Steps`, and then derive the next step from it - this is the direct analog of the reported bug: a chain-linking identifier loaded from (attacker-influenced) storage/RPC input is not validated as a safe path component before being used to resolve the "parent" state and derive/write the "child" state.

Unlike `path_prefix`, which is explicitly hardened with `ValidatePathPrefix` (rejecting `..` and absolute paths) after a prior incident, `backup_id` receives no equivalent treatment anywhere in the request validation, manifest read/write path, or the `ReadLatestBackupID`/`WriteBackupID` marker-file logic.

### Impact Explanation
An actor able to invoke `BackupRepository`/`RestoreRepository` (or drive `gitaly-backup create`/`restore` with a controlled `--backup-id`) can supply a crafted `backup_id` containing `../` sequences to:
- Write/overwrite manifest (`.toml`), bundle, refs, and custom-hooks files at chosen paths within the backup sink for *other repositories or storages*, corrupting their backup chains.
- Cause `RestoreRepository` to read (`GetReader`) attacker-chosen relative paths within the sink, potentially disclosing bundle/refs/manifest content belonging to another repository if the identifier is echoed back on restore.
- Corrupt the "chain" of incremental backups analogous to the reported issue: since `BeginIncremental` uses the (unsanitized) previous backup identifier to locate the prior manifest and derive `PreviousRefPath`, a crafted identifier can point the chain-building logic at manifests it should not have access to, producing an incremental backup whose base state does not correspond to the actual current repository, silently producing corrupted, unrestorable backups.

This matches the required "concrete storage escape ... via crafted RPC field" bucket in the validation rules.

### Likelihood Explanation
`backup_id`/`latest_backup_id` are plain RPC string fields with no format constraints in `proto/repository.proto`, and are also settable via the `gitaly-backup create --backup-id` CLI flag which is meant to be driven by orchestration tooling. In deployments where `BackupRepository` is reachable by less-trusted callers than the backup orchestration tooling itself (e.g., via Praefect routing without additional identifier validation, as seen in `internal/praefect/backup_repository.go`, which forwards the request unchanged), the missing validation is directly exploitable. Even in trusted-orchestration deployments, this is a latent defect: a single malformed/malicious `backup_id` value (e.g., from a misconfigured integration) silently escapes the intended directory instead of being rejected, unlike `path_prefix` which was explicitly hardened for the exact same class of input.

### Recommendation
Add a `ValidateBackupID`-style check (mirroring `backup.ValidatePathPrefix`) that rejects empty values, absolute paths, path separators/`..` segments, and any characters that are unsafe as a single path component, and apply it to both `backup_id` and `latest_backup_id` in `validateBackupRepositoryRequest`/`validateRestoreRepositoryRequest`, as well as in `ManifestLocator.BeginFull`/`BeginIncremental`/`Find` and `IDManager.WriteBackupID`/`ReadLatestBackupID` before they are joined into any sink path. Additionally, verify after `path.Join`/`filepath.Join` that the resulting path is still contained within the expected `storageName/relativePath` (or `manifestDirectory`) prefix, similar to `storage.ValidateRelativePath` used elsewhere in Gitaly for repository-relative paths.

### Proof of Concept
1. Deploy Gitaly with server-side backups configured (`backup.go_cloud_url`) and `BackupRepository`/`RestoreRepository` reachable by the attacker (directly, or via a Praefect proxy that does not add its own validation, as in `internal/praefect/backup_repository.go`).
2. Call `BackupRepository` with:
   - `repository`: attacker-controlled repository A
   - `backup_id`: `"../../victim-storage/victim/relative/path"`
   - `incremental`: false
3. Observe that `ManifestLoader.WriteManifest`/`Sink.GetWriter` writes the manifest/bundle/refs/custom-hooks files under the traversed path (`manifestPath`/`BeginFull` join `backupID` unsanitized - `internal/backup/manifest.go:113-115`, `internal/backup/locator.go:35-45`), landing outside repository A's own backup directory and potentially colliding with or corrupting an existing backup chain for another repository.
4. A subsequent `RestoreRepository`/incremental `BackupRepository` call using the same traversal-crafted `backup_id`/`latest_backup_id` will then read/derive its `PreviousRefPath`/chain state from that escaped location (`ManifestLocator.BeginIncremental`, `internal/backup/locator.go:51-118`), demonstrating that the un-validated identifier corrupts the intended chain-of-custody for incremental backups, directly analogous to the reported `shnarf`/parent-hash chain corruption.
