Audit Report

## Title
Unbacked ERC20 asset minting in XCM via phantom `transfer()` return-value trust - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` treat a non-reverting `IERC20::transfer` call that ABI-decodes to `true` as sufficient proof that `amount` tokens moved, without ever querying `balanceOf` before/after the call. Combined with `ERC20Matcher`, which accepts any `Location` of the form `(0, [AccountKey20 { .. }])` as a valid fungible asset with no allow-list or registration, an unprivileged attacker can deploy a contract whose `transfer` always returns `true` without moving any balance, then mint `AssetsInHolding` credit backed by nothing via a public XCM program.

## Finding Description
`withdraw_asset_with_surplus` resolves the asset id/amount via `Matcher::matches_fungibles(what)?` [1](#0-0) , then calls the user-supplied contract's `transfer(checking_address, amount)` via `pallet_revive::Pallet::<T>::bare_call` [2](#0-1) . It only checks `did_revert()` and the ABI-decoded boolean return before minting `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — with no verification that any real balance changed [3](#0-2) . `deposit_asset_with_surplus` mirrors this: it calls `transfer(beneficiary, amount)` from the checking account and treats `Ok(true)` as full success [4](#0-3) .

The asset identity for both paths comes from `ERC20Matcher = MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>` [5](#0-4) , where `IsLocalAccountKey20` matches purely on location shape `(0, [AccountKey20 { .. }])` [6](#0-5)  and `AccountKey20ToH160::convert` takes the raw key straight from the XCM location into the `H160` asset id, with no allow-list or on-chain registration check [7](#0-6) . Nowhere in the crate does the code call `balanceOf` to confirm real balance deltas; a repo-wide search for `balanceOf`/`balance_of` calls turns up nothing in `erc20_transactor.rs`, confirming the absence of any such check.

This is wired into a live runtime configuration: `ERC20Transactor`/`ERC20Matcher` are referenced from `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`, confirming this is production `AssetTransactors` wiring rather than test-only code.

## Impact Explanation
An attacker who deploys a phantom-`transfer` contract that always returns `true` while performing no real balance movement can obtain `AssetsInHolding` credit for an arbitrary `amount` via `WithdrawAsset` in a permissionless XCM program, matching the "theft or unbacked mint" impact class. That fabricated holding can then be chained within the same XCM program into swaps, reserve transfers, or teleports involving other configured `AssetTransactors`/pools to potentially convert unbacked value into genuinely backed assets.

## Likelihood Explanation
Exploitation requires only that the attacker deploy a bespoke `pallet-revive` contract implementing the `IERC20::transfer(address,uint256)` selector to return `abi.encode(true)` unconditionally, and submit a signed XCM program via `pallet_xcm::execute`/`send`. No privileged, validator, or off-chain infrastructure control is required — the path is reachable entirely through public extrinsics and the runtime's configured `AssetTransactors`, which include `ERC20Transactor`.

## Recommendation
Replace boolean-return/non-revert trust with an explicit `balanceOf` check on the relevant account (checking account for withdraw, beneficiary for deposit) before and after the `transfer` call, requiring the delta to equal `amount` exactly. Alternatively, restrict `ERC20Matcher`/`ERC20Transactor` to an allow-list of vetted/registered contract addresses instead of matching any `AccountKey20` location.

## Proof of Concept
1. Deploy a `pallet-revive` contract at address `E` implementing:
   ```solidity
   function transfer(address, uint256) external returns (bool) { return true; }
   ```
   with no internal balance accounting.
2. As a normal signed user, submit an XCM program via `pallet_xcm::execute` containing `WithdrawAsset` for `Location(0, [AccountKey20{ key: E }])` with an arbitrary `amount`. This invokes `ERC20Transactor::withdraw_asset_with_surplus`, which calls `E.transfer(checking_account, amount)`; since it doesn't revert and decodes to `true`, `AssetsInHolding::new_from_fungible_credit(..., Erc20Credit(amount))` is minted per [8](#0-7) .
3. Chain the fabricated holding into a further XCM instruction (e.g., a swap through `pallet_asset_conversion` or a reserve/teleport transfer) to extract genuinely backed assets, despite `E`'s real ERC20 balance for the checking account never having increased.

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}
