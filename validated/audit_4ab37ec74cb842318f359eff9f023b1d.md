### Title
Unauthenticated attachment-hash forgery via `extend_with_attachments` — served content is never checked against the requested `content_hash` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts any `GetAttachmentResponse` returned by a remote peer for an `AttachmentRequest` and inserts `response.attachment` into `self.attachments` without ever comparing `Hash160::from_data(&attachment.content)` to the `content_hash` that was actually requested. Any peer serving Atlas attachment data can therefore return arbitrary bytes for any requested hash, and that arbitrary content will be persisted into `AtlasDB` under its own (attacker-chosen) hash, while the legitimately-requested hash is never resolved — enabling unbounded, unauthenticated growth of stored attachment blobs that no on-chain name operation ever committed to.

### Finding Description
The equality that should hold is `served_attachment.hash() == AttachmentRequest.content_hash` for every entry placed into `AttachmentsBatchStateContext::attachments`. This is never checked.

In `extend_with_attachments`: [1](#0-0) 
the code iterates `results.succeeded`, decodes the HTTP response via `decode_atlas_get_attachment()`, and on success unconditionally does `self.attachments.insert(response.attachment)` — with no comparison to `request.content_hash`, which is discarded (the `request` variable is only used to fetch `report`/`get_url()`).

Downstream, in `AttachmentsDownloader::run`, the batch is drained and processed keyed by the *attachment's own* hash, not the originally requested one: [2](#0-1) 
`network.atlasdb.find_all_attachment_instances(&attachment.hash())` and `context.attachments_batch.resolve_attachment(&attachment.hash())` both use `attachment.hash()` (i.e., `Hash160::from_data` of whatever bytes the peer sent) rather than the tracked `content_hash` that the on-chain `AttachmentInstance` committed to. Critically, `network.atlasdb.insert_instantiated_attachment(&attachment)` is called unconditionally for every drained attachment, regardless of whether any matching instance was found.

Exploit flow: a remote, unprivileged peer responds to `StacksHttpRequest::new_getattachment` (sent for a legitimate pending `content_hash = H`) with a `GetAttachmentResponse` whose `Attachment.content = C` where `Hash160::from_data(&C) = H' != H`. `extend_with_attachments` stores this in `self.attachments` unchecked. In `run()`, `find_all_attachment_instances(&H')` returns empty (no instance was ever tracked under H'), so no `resolved_attachments` pairing occurs and the real pending request for `H` is never resolved (and will be retried/eventually dropped after `max_attachment_retry_count`). Meanwhile `insert_instantiated_attachment(&attachment)` still writes the attacker-supplied blob into `AtlasDB`, keyed by `H'`, a hash that no `AttachmentInstance`/name operation ever referenced.

No existing guard prevents this: there is no `MAX_PAYLOAD_LEN`-style hash-equality check in `extend_with_attachments`, `decode_atlas_get_attachment`, or in the `run()` drain loop before calling `insert_instantiated_attachment`.

### Impact Explanation
Any single malicious/compromised peer selected during Atlas attachment sync can, per HTTP response, cause the node to permanently store an arbitrary attacker-chosen blob (bounded by the attachment size limit enforced at decode time, if any) in `AtlasDB`, keyed under a hash that is not tied to any committed on-chain name operation. Repeating this with different payloads each time yields unbounded storage growth in the node's local Atlas attachments table — an unauthenticated write to persistent state (`AtlasDB`) driven purely by unauthenticated network responses. This matches the "unauthenticated/unauthorized write to state" / storage-exhaustion category, and additionally serves as an attachment/content-hash mismatch, since the legitimate pending request for `H` never resolves while unrelated content accumulates.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to be selected as one of the "outbound sync peers" that the node queries for attachment inventories/content (`network.get_outbound_sync_peers()`), which any peer running the p2p protocol can become without holding privileged keys or the RPC secret. The attacker responds to a routine `GetAttachment` request with crafted, non-matching content. This is fully remote, repeatable per attachment request cycle, and costs the attacker only the bandwidth to run a peer and answer HTTP GETs — no signature, secret, or admin role is needed.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, after decoding the response, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; discard/blacklist the peer and bump `report.bump_failed_requests()` on mismatch. Additionally, in `AttachmentsDownloader::run`, `insert_instantiated_attachment` should only be called for attachments whose hash corresponds to a tracked `AttachmentInstance`/pending request, not unconditionally for every drained entry.

### Proof of Concept
Rust test in `stackslib::net::atlas::tests` (or a new test module under `stackslib/src/net/atlas/download.rs`):
1. Construct an `AttachmentsBatchStateContext` with `attachments_batch` tracking one `AttachmentInstance{content_hash: H, ...}`, and a `peers` map with one URL.
2. Build a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map has key `AttachmentRequest{content_hash: H, ...}` mapped to `Some(StacksHttpResponse)` wrapping a `GetAttachmentResponse{ attachment: Attachment{ content: C } }` where `Hash160::from_data(&C) = H' != H` (craft `C` directly, e.g. `b"malicious-blob"`).
3. Call `context.extend_with_attachments(&mut results)` and assert `context.attachments` contains an `Attachment` whose `.hash()` equals `H'`, not `H`.
4. Simulate the `run()` drain step: call `atlasdb.find_all_attachment_instances(&H')` and assert it returns empty (no instance registered under `H'`), then call `atlasdb.insert_instantiated_attachment(&attachment)` and assert `atlasdb.find_attachment(&H')` now returns `Some(attachment)` — demonstrating a DB row keyed by `H'` was created from unverified attacker content while the pending instance for `H` remains unresolved (`attachments_batch.has_fully_succeed() == false`).

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
