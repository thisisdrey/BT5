### Title
Authenticated re-handshake accepts a new `node_public_key` claim without proof of possession, allowing unverified key overwrite of a peer's identity - (File: stackslib/src/net/chat.rs)

### Summary
`ConversationP2P::validate_handshake` only calls `message.verify_secp256k1(&handshake_data.node_public_key)` in the `None` branch (first handshake) but skips this check entirely in the `Some(_)` branch (already-authenticated re-handshake), only checking address/port for outbound peers. Consequently, `update_from_handshake_data` can adopt a brand-new `node_public_key` value that was never used to sign anything, and for outbound connections this unverified value is persisted into the local `PeerDB` neighbor record.

### Finding Description
In `stackslib/src/net/chat.rs::validate_handshake` [1](#0-0) , the `None` branch verifies the envelope signature against the *claimed* `handshake_data.node_public_key`: [2](#0-1) 

But the `Some(_)` branch — taken when `self.connection.get_public_key()` is already set (i.e. we already trust this connection) — performs no signature-to-claimed-key check at all; it only validates the self-reported address/port for outbound peers: [3](#0-2) 

The rest of `validate_handshake` (public-key format validity, expiry, self-handshake rejection) does not check that the claimed `node_public_key` produced the enveloping signature either. `handle_handshake` then calls `update_from_handshake_data`, which (per its usage from both `handle_handshake` and `handle_handshake_accept`) installs the *claimed* key via `self.connection.set_public_key(...)` and returns whether the key was `updated`: [4](#0-3) . For outbound connections, if `updated` is true, the new (unverified) key is persisted to the `PeerDB` via `Neighbor::load_and_update` / `neighbor.save_update`: [5](#0-4) .

The enveloping signature on the second (re-key) message is only checked by the underlying `ConnectionP2P` against the *currently stored* (old) key before the message is dequeued — per the explicit comment in `chat()`: [6](#0-5) . That means only the real holder of the OLD private key can get a re-key message admitted at all — so this is not an arbitrary third-party impersonation attack. However, the holder of the OLD key can, in a single authenticated re-handshake message, claim an arbitrary NEW `node_public_key` value that they never proved they control (no signature exists that was produced by that new key), and that claim is adopted and stored.

### Impact Explanation
For an outbound connection (a case reachable by any unprivileged remote party that first completes a normal handshake and is later dialed/rewalked, or that itself is dialed as a neighbor), the peer can cause the local node to write an attacker-chosen, unproven public key into its `PeerDB` neighbor record for that peer's address via `Neighbor::save_update`. This is an unauthenticated write of unverified identity data into persistent peer state, and such neighbor records can subsequently be relayed to other nodes through neighbor-walk/`GetNeighbors` gossip, potentially propagating a forged key/address association. It does not, by itself, allow forging another node's signature or bypassing envelope-level authentication of unrelated messages, since all subsequent traffic on that connection must still be signed by whatever key is *currently* installed — if the peer claims a key it doesn't control, it will simply be unable to authenticate any further message on that same connection (a self-inflicted break), unless it re-associates with its true key later.

### Likelihood Explanation
Preconditions: the attacker must first complete a normal handshake with its own real key (trivially available to any unprivileged remote party), and the connection must be `outbound` from the victim node's perspective for the PeerDB write to occur (`self.stats.outbound` gate in `handle_handshake`). The attacker does not need any privileged role, secret, or another party's key. This is repeatable across reward-cycle/heartbeat handshakes.

### Recommendation
In the `Some(_)` branch of `validate_handshake`, when `handshake_data.node_public_key` differs from the currently stored key, require the envelope signature to verify against the *claimed new* key (not just against the old stored key), e.g. call `message.verify_secp256k1(&handshake_data.node_public_key)` whenever the claimed key differs from `self.connection.get_public_key()`, mirroring the `None` branch's proof-of-possession check, before allowing `update_from_handshake_data` to adopt/persist it.

### Proof of Concept
Rust net test plan (extending existing `chat.rs` test harness, e.g. `convo_handshake_rekey`-style test at [7](#0-6) ):
1. Perform an initial handshake between `convo_1`(local, outbound) and `convo_2`, both signed with `local_peer_1.private_key` (K1), so `convo_1.connection.get_public_key()` on the peer side and vice versa become `Some(K1)`.
2. Craft a second `HandshakeData` whose `node_public_key` field is set to an arbitrary key `K2` (e.g. from a freshly generated `Secp256k1PrivateKey` that is never used to sign anything), but sign the enclosing `StacksMessage` with `local_peer_1.private_key` (K1) via `convo_1.sign_message(..., &local_peer_1.private_key, StacksMessageType::Handshake(handshake_data_k2))`.
3. Send it through `convo_send_recv` to the peer conversation that has `self.stats.outbound == true` and already has `Some(K1)` stored.
4. Assert that `handle_handshake` returns `updated == true`, that `self.connection.get_public_key()` now equals `K2`, and that the `PeerDB` neighbor record for that address now stores `K2` — despite no message ever being signed by `K2`. This confirms `update_from_handshake_data`/`validate_handshake` accepted a claimed key without proof of possession.
