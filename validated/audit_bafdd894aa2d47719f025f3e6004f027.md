### Title
Division-before-multiplication precision loss in legacy vote reward calculation - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes each voter's share of a witness's total reward by first dividing `userVote` by `totalVote` as a `double`, then multiplying that ratio by `totalReward`, instead of multiplying first and dividing last. [1](#0-0) 

### Finding Description
The legacy reward algorithm computes `voteRate = (double) userVote / totalVote` and then `reward += voteRate * totalReward`, performing the division before the multiplication. [2](#0-1) 
This is functionally the same bug class as the referenced GMX report: dividing first truncates/loses precision from the fractional vote-share before it is scaled back up by `totalReward`, so the computed reward for each voter deviates from the mathematically correct `userVote * totalReward / totalVote`. This is invoked from `computeReward(beginCycle, endCycle, accountCapsule)` for any cycle prior to `newRewardAlgorithmEffectiveCycle`, via `getOldReward`, which is reachable from `withdrawReward(address)` whenever an account's unwithdrawn vote-reward cycle range predates the algorithm switch. [3](#0-2) 
`withdrawReward` itself is triggered from unprivileged, signed transactions — `WithdrawBalanceActuator` (legacy `WithdrawBalanceContract`) and `WithdrawRewardProcessor` (TVM native `withdrawreward` opcode) both call it to pay out an account's accrued voting reward. [4](#0-3) 

The newer reward algorithm (post-`newRewardAlgorithmEffectiveCycle`) already avoids this class of bug by using `BigInteger` multiply-then-divide (`deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD)`), confirming the project is aware of and has already fixed this exact pattern elsewhere, but the old-algorithm code path (still reachable for accounts with unwithdrawn cycles predating the switch) remains unpatched. [5](#0-4) 

### Impact Explanation
The impact is bounded to rounding-level inaccuracy (typically fractions of a `sun`, TRON's smallest unit) in the legacy vote-reward distribution per voter per cycle — it is not a large-scale value-extraction primitive; the double-precision floating point division/multiplication error is generally too small to enable meaningful theft, and any surplus/deficit stays within the pool aggregated from `delegationStore.getReward(cycle, srAddress)`, which is fixed at reward-accrual time from `payReward`. There is no mechanism visible here for an attacker to amplify or systematically extract value beyond negligible float-rounding noise, since vote counts and total rewards are public, deterministic values, not attacker-controlled inputs that can be crafted to maximize the error.

### Likelihood Explanation
The old-algorithm code path only executes when `beginCycle < newRewardAlgorithmEffectiveCycle` for the withdrawing account, meaning it only matters for accounts that have not withdrawn rewards since before the algorithm cutover happened on-chain — this is a shrinking, effectively legacy, code path rather than the primary reward flow used by the current network.

### Recommendation
Restructure `computeReward(long cycle, List<Pair<byte[], Long>> votes)` in `MortgageService.java` to compute `userVote * totalReward / totalVote` using integer or `BigInteger` arithmetic (multiplying before dividing), consistent with the fix already applied in the new-algorithm path (`BigInteger` VI-based calculation) and in `RewardViCalService`/`DelegationStore.accumulateWitnessVi`.

### Proof of Concept
Given `totalReward = 100`, `totalVote = 3`, `userVote = 1`:
- Correct: `1 * 100 / 3 = 33` (integer division).
- Current legacy code: `voteRate = 1.0/3.0 = 0.3333...`; `reward = (long)(0.3333... * 100) = 33` (in this trivial case matches, but for larger reward/vote magnitudes near double precision limits — e.g. `totalReward` near `Long.MAX_VALUE` and `totalVote` large — the double-precision division-then-multiplication path in `computeReward` accumulates rounding error not present in the multiply-first/BigInteger approach used elsewhere in the codebase).   private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
