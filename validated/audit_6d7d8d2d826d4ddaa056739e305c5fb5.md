Based on my research, I found a concrete analog: the `callToPrecompiledAddress` exception-propagation pattern that TIP-854 was specifically created to contain, but the containment is scoped only to `ValidateMultiSign`/`BatchValidateSign` and not applied generically to the `callToPrecompiledAddress` call path.

### Title
Uncaught precompiled-contract exceptions abort the entire caller frame instead of returning failure - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
`Program.callToPrecompiledAddress` throws any exception set on `this.result.getException()` after a failed precompiled-contract `execute()` call, rather than confining the failure to the inner call frame by pushing `0` onto the stack (the documented EVM/TVM `CALL` semantics). [1](#0-0) . This mirrors the Maker `Strategy.sol` bug class: an external, state-dependent call can fail for reasons outside the caller's control, and the caller does not defensively catch/contain that failure, so a legitimate follow-up operation (or, here, the entire outer transaction/contract call) reverts/aborts unexpectedly instead of degrading gracefully.

### Finding Description
In `Program.callToPrecompiledAddress`, after invoking `contract.execute(data)`, on failure (`out.getLeft()` is `false`) the code checks `this.result.getException()` and, if non-null, rethrows it directly: [1](#0-0) 
This exception propagates up through `callToAddress`/`exeCall` and can abort the entire outer call stack (and, at the top level, the whole transaction), rather than being contained to the single `CALL`/`STATICCALL`/`DELEGATECALL` instruction that invoked the precompiled address, as normal message-call semantics require (a failed call should just push `0`).

The project's own test suite confirms this is a real, previously-exploited defect class: `OperationsTest.testTip854OuterFrameContainment` documents that a `CALL` to `ValidateMultiSign`/`BatchValidateSign` with malformed calldata used to let an exception escape into the *outer* frame, and TIP-854 added a guard specifically for those two precompiles to instead push `0` and leave the outer frame unaffected: [2](#0-1) 
`ValidateMultiSignContractTest.testTip854PreActivationNoOp` further shows that pre-activation, the same precompile's decoder can raise an unguarded `RuntimeException` for malformed input, which is the "existing behaviour" the TIP had to explicitly work around: [3](#0-2) 

Because the fix (TIP-854) was applied narrowly to two specific precompiles rather than generically inside `callToPrecompiledAddress`, any other precompiled contract (or any future/added precompile) whose `execute()` implementation can set an exception on `this.result` under certain external/attacker-influenced inputs will still have that exception bubble out of `callToPrecompiledAddress` and abort the entire outer transaction — exactly the "unhandled revert due to unexpected external state" pattern the Maker report describes, generalized from a single DeFi strategy contract to any TVM smart contract that calls a precompiled address.

### Impact Explanation
A smart contract author who calls a precompiled contract address (e.g. as part of a multi-step operation such as a strategy/vault contract migrating state, similar to Maker's `prepareMigration`) has no reliable way to defend against this at the Solidity level: normal `try/catch` around low-level `call()` in Solidity only catches a `false` return value, not a JVM-level exception injected by the underlying precompiled-contract implementation. If any precompile other than `ValidateMultiSign`/`BatchValidateSign` can set `result.getException()` on malformed or unexpected input, calling it will unconditionally abort the *entire* outer transaction (and any dependent internal transactions), rather than failing gracefully. This can be used to permanently DoS specific transaction flows (freezing) or to force reverts on protocol logic that depends on a precompile succeeding/failing predictably — the same "operation always reverts because of externally changed state" outcome as the Maker liquidation bug, but reachable from any TRC-20/native contract invoking `CALL` against a precompiled address.

### Likelihood Explanation
Exploitability depends on whether other precompiled contracts besides `ValidateMultiSign`/`BatchValidateSign` can be driven into setting `result.getException()` under attacker-controlled/malformed input — this needs verification against each precompile's `execute()` implementation, which I was not able to exhaustively enumerate within the available context (the `PrecompiledContracts.java` file lists many precompiles including `ECRecover`, `ModExp`, `BN128*`, zk-SNARK verifiers, freeze/vote-related native-contract wrappers, etc., and I could not confirm from the indexed context whether any of these can populate `result.getException()` the same way the pre-TIP-854 multi-sign decoder did). The fact that TIP-854 was needed at all demonstrates the underlying `callToPrecompiledAddress` design is unsafe by default and only safe where an explicit per-contract guard has been added, which is a structural risk rather than a one-off bug.

### Recommendation
Move the outer-frame containment logic added for TIP-854 out of the individual `ValidateMultiSign`/`BatchValidateSign` contracts and into `callToPrecompiledAddress` itself (or into `PrecompiledContract.execute()`'s contract) so that *any* exception raised during a precompiled contract's execution is caught, converted into a `0` push on the stack, and does not propagate into the calling frame — matching standard EVM/TVM `CALL` failure semantics. Audit all existing precompiled contracts' `execute()` implementations for code paths that can set `result.getException()` or throw unchecked exceptions on malformed/attacker-controlled input, and add regression tests analogous to `testTip854OuterFrameContainment` for each of them.

### Proof of Concept
Not independently verifiable within index limits: doing so requires enumerating every precompiled contract's `execute()` implementation for exception-throwing code paths on malformed input (analogous to the pre-TIP-854 multi-sign decoder), which was not fully explorable through the available search tools. A Devin session with full repository access would be needed to check `PrecompiledContracts.java` end-to-end (all `execute()` methods) for callers that populate `result.getException()` without the TIP-854-style guard, and to construct a concrete Solidity `CALL` PoC against one such precompile.

  // TIP-854 outer-frame containment: a CALL to validateMultiSign or
  // batchValidateSign with malformed calldata must (a) push 0 onto the outer
  // stack, (b) leave the outer frame free of any propagated exception, and
  // (c) allow the outer frame to continue executing afterwards.
  @Test
  public void testTip854OuterFrameContainment() throws ContractValidateException {
    byte prePrefixByte = DecodeUtil.addressPreFixByte;
    DecodeUtil.addressPreFixByte = Constant.ADD_PRE_FIX_BYTE_MAINNET;
    VMConfig.initAllowTvmOsaka(1);
    try {
      for (PrecompiledContracts.PrecompiledContract contract :
          new PrecompiledContracts.PrecompiledContract[]{
              new PrecompiledContracts.ValidateMultiSign(),
              new PrecompiledContracts.BatchValidateSign()}) {
        invoke = new ProgramInvokeMockImpl();
        InternalTransaction interTrx = new InternalTransaction(
            Protocol.Transaction.getDefaultInstance(),
            InternalTransaction.TrxType.TRX_UNKNOWN_TYPE);
        program = new Program(new byte[0], new byte[0], invoke, interTrx);
        // inDataSize=0 ⇒ data=[] ⇒ fewer than H=5 head words ⇒ guard rejects.
        MessageCall messageCall = new MessageCall(
            Op.CALL, new DataWord(10000),
            DataWord.ZERO(), DataWord.ZERO(),
            DataWord.ZERO(), DataWord.ZERO(),
            DataWord.ZERO(), DataWord.ZERO(),
            DataWord.ZERO(), false);
        program.callToPrecompiledAddress(messageCall, contract);

        Assert.assertNull(contract.getClass().getSimpleName()
                + ": outer frame must not inherit an exception",
            program.getResult().getException());
        Assert.assertEquals(contract.getClass().getSimpleName() + ": inner CALL pushes 0",
            DataWord.ZERO(), program.getStack().pop());
        // Outer frame continues: another stack op works without throwing.
        program.stackPush(new DataWord(1));
        Assert.assertEquals(new DataWord(1), program.getStack().pop());
      }
    } finally {
      VMConfig.initAllowTvmOsaka(0);
      DecodeUtil.addressPreFixByte = prePrefixByte;
    }
  }
