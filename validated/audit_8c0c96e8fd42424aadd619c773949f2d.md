### Title
Lack of a reference-update count limit in `git-receive-pack` requests enables push-flooding griefing of a repository's RPC handlers - (File: `internal/gitaly/service/smarthttp/receive_pack.go`, `internal/gitaly/hook/receivepack/receive_pack.go`, `internal/gitaly/hook/postreceive.go`)

### Summary
Gitaly places no limit on the number of reference-update commands (`<old-oid> <new-oid> <ref-name>`) that a single `git-receive-pack` invocation may contain. Any user with push access can send one push containing an arbitrarily large number of ref updates (e.g., thousands/millions of tiny branch creates). Gitaly's only backpressure mechanism, described in `doc/backpressure.md`, limits *concurrent RPCs per repository*, not the size/shape of an individual RPC. A single oversized push therefore occupies that one concurrency slot for a long time while internally fanning out into per-reference hook invocations and (when transactions are enabled) per-reference votes, degrading the repository for every other user — directly analogous to the Debita "no minimum size" griefing pattern, where a lack of a floor/ceiling on unit-of-work count let an attacker flood the system with tiny units to grief other participants.

### Finding Description
- `internal/git/stats/receive_pack.go`'s `Parse` function walks the entire pkt-line command list with no bound on `Commands`/`Creates`/`Deletes`/`Updates`, confirming the command list itself is unbounded by design: [1](#0-0) 
- `PostReceivePack` (SmartHTTP) and the analogous SSH handler stream the client's raw pkt-line body directly into `git receive-pack --stateless-rpc`, with no server-side cap on the number of ref-update lines before invoking the real `receive-pack` subprocess: [2](#0-1) 
- Once `git receive-pack` accepts the push, Gitaly's proc-receive hook processes reference updates from `handler.ReferenceUpdates()`; in the non-atomic path it iterates and performs a separate `receivePackReferenceUpdates` call (and thus a separate hook invocation / git subprocess) **per individual reference**, with no cap on the number of iterations: [3](#0-2) 
- The post-receive hook likewise parses and counts every reference update line from stdin with `countRefUpdates`, with no upper bound, and this data flows into the internal API call plus GitLab hook processing for every single one of the (potentially millions of) refs: [4](#0-3) 
- Per `doc/design_ha.md`, each reference update triggers Git's reference-transaction hook, which round-trips to Praefect to collect votes from every Gitaly node before the reference is allowed to commit: [5](#0-4) . An attacker-controlled push with N tiny ref updates therefore forces N synchronous vote round-trips inside a single RPC call.
- Gitaly's only protective mechanism is `[[concurrency]]` limiting of *concurrent RPCs per repository*, not of push size: [6](#0-5) . A single massive push occupies the `max_per_repo` slot (commonly configured to `1` for push-type RPCs) for the whole duration of processing thousands/millions of ref updates, queuing out every other legitimate push/fetch against that repository until `max_queue_wait` expires.
- Elsewhere in the codebase, Gitaly authors have already recognized this exact "unbounded small-unit flood" risk and added explicit caps for comparable code paths — e.g. `UpdateRemoteMirror` caps `pushBatchSize = 10` and `maxDivergentRefs = 100` — but no equivalent cap exists for the number of ref-update commands accepted from an ordinary client push via `PostReceivePack`/`SSHReceivePack`: [7](#0-6) 

### Impact Explanation
Any authorized pusher (not necessarily privileged) can grief other legitimate users of the same repository by submitting one push with a huge number of trivial ref-update commands. This:
- Monopolizes the per-repository concurrency slot for RPCs such as `PostReceivePack`/`SSHReceivePack`, blocking other pushes/fetches to the same repository for the queue-wait duration.
- Forces the reference-transaction hook / Praefect voting machinery, and non-atomic proc-receive per-reference hook loop, to perform work proportional to the (attacker-controlled, unbounded) number of ref updates, multiplying CPU, subprocess-spawn, and network overhead for the whole cluster handling that single request.
- Downstream RPCs that enumerate references (`ListRefs`, `FindAllBranches`, etc.) and repository housekeeping (pack-refs, GC) subsequently have to deal with the inflated ref count, degrading performance for all future operations against the repository — mirroring the Debita report's core harm (borrowers/lenders unable to efficiently locate/act on their own, now fragmented, records).

### Likelihood Explanation
Reachable by any client with ordinary push access (HTTP or SSH) to a repository — no privileged role, leaked token, or malicious peer/MITM is required. Git's pack protocol places no inherent limit on the number of ref-update commands in the reference-update request, and Gitaly does not add one before invoking `git receive-pack`. The only mitigating factor is that eventual `git receive-pack` execution time and Praefect voting overhead grow with the number of refs, making the attack self-limiting in extreme cases, but a moderately large number of refs (thousands) is trivial to construct and push.

### Recommendation
Enforce an explicit, configurable maximum number of reference-update commands accepted per `git-receive-pack` invocation (mirroring the caps already used in `update_remote_mirror.go`), rejecting/erroring pushes that exceed the limit before spawning `git receive-pack` or invoking per-reference hook processing in `internal/gitaly/hook/receivepack/receive_pack.go` and `internal/gitaly/hook/postreceive.go`. Consider surfacing this limit in the `stats.ReceivePack` parser (already tracking `Commands`) so it can be checked before the packfile is even streamed to the subprocess.

### Proof of Concept
1. As a user with push access to a repository, craft a `git-receive-pack` request whose pkt-line command list contains N (e.g., 500,000) distinct `refs/heads/branch-<i>` create commands, each `zero-oid -> <same trivial commit oid>`, followed by a flush and a minimal packfile.
2. Submit this via `PostReceivePack` (HTTP) or `SSHReceivePack`. Gitaly forwards the entire command list to `git receive-pack --stateless-rpc` without any count check (`internal/gitaly/service/smarthttp/receive_pack.go`).
3. Observe that: (a) the RPC occupies the repository's `max_per_repo` concurrency slot for the full duration of hook/vote processing over N refs, (b) the non-atomic proc-receive path performs N separate `receivePackReferenceUpdates` calls, and (c) subsequent `ListRefs`/`FindAllBranches` calls against the repository become measurably slower due to the inflated ref count — demonstrating the griefing/DoS effect on both the pushing RPC and future repository consumers.

// countRefUpdates counts the reference updates from the post-receive hook's
// stdin. Each line has the format "<oldOID> <newOID> <refname>". A reference
// is considered created when its old OID is all-zeroes and deleted when its new
// OID is all-zeroes; everything else is an update.
func countRefUpdates(changes []byte) refUpdateStats {
	var stats refUpdateStats

	scanner := bufio.NewScanner(bytes.NewReader(changes))
	for scanner.Scan() {
		fields := strings.Fields(scanner.Text())
		if len(fields) != 3 {
			continue
		}

		stats.total++

		oldZero := isZeroOID(fields[0])
		newZero := isZeroOID(fields[1])
		switch {
		case oldZero && !newZero:
			stats.created++
		case !oldZero && newZero:
			stats.deleted++
		default:
			stats.updated++
		}
	}

	return stats
}

**File:** doc/design_ha.md (L374-388)
```markdown
1. Gitaly executes `git receive-pack` and passes incoming data to it.
1. After `git receive-pack` has received all references that are to be updated,
   it executes the reference-transaction hook for each reference which is to be
   updated.
1. The reference-transaction hook reaches out to Praefect and notifies it about
   all reference update it wants to perform.
1. Praefect waits until all Gitaly nodes have notified it about the reference
   update. After it has received all notifications, it verifies that all nodes
   want to perform the same update. If so, it notifies them that they may go
   ahead by sending a "commit" message. Otherwise, it will send an "abort"
   message.
1. When receiving the response, the hook will either return an error in case it
   got an "abort" message, which will instruct Git to not update the references.
   Otherwise, the hook will exit successfully and Git will proceed.
1. Gitaly returns success to Praefect and the transaction is done.
```
