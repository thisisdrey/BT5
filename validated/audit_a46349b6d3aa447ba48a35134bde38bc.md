This confirms it: only the `registrar_account_id` can create short top-level accounts, and non-top-level (sub-account) creation requires the predecessor to be the direct parent [1](#0-0) . Long top-level named accounts (≥ `min_allowed_top_level_account_length`) can be created by anyone. Implicit accounts (near/eth-implicit) are deterministically named by public key, so "recreating" one requires controlling the same key — no new attacker gains anything there. Sub-accounts can never be reclaimed by a different owner. So the only case where a *different* party can grab a deleted account's name is a sufficiently long top-level named account — a narrow but real (not purely speculative) precondition.

### Title
Stale `PromiseYieldReceipt`/`PromiseYieldTimeout` survive `DeleteAccount`, allowing a residual self-authorized action to execute against a re-created account of the same name - (File: core/store/src/utils/mod.rs, runtime/runtime/src/lib.rs)

### Summary
`remove_account` (core/store/src/utils/mod.rs) deletes an account's `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` entries but never removes that account's `PromiseYieldReceipt`, `PromiseYieldStatus`, or `YieldIdToDataId`/`DataIdToYieldId` entries [2](#0-1) . The global `PromiseYieldTimeout` queue is index-keyed, not account-keyed, so it is unaffected by account deletion and continues to fire on schedule [3](#0-2) . When the timeout eventually fires, `resolve_promise_yield_timeouts` only checks `contains_key(PromiseYieldReceipt{account_id, data_id})` before manufacturing a `PromiseResume` receipt with `predecessor_id == receiver_id == account_id` [4](#0-3) ; since the stale receipt was never cleared, this check still succeeds, and the resulting resume causes the old parked action receipt's actions to be executed against whatever account currently occupies that name [5](#0-4) .

### Finding Description
1. An attacker-controlled contract at account `V` calls `promise_yield_create`, which enqueues a `PromiseYieldTimeout{account_id: V, data_id, expires_at}` in the global queue and stores a `PromiseYieldReceipt` keyed by `(V, data_id)` [6](#0-5) [7](#0-6) .
2. `V` submits a `DeleteAccount` action. `action_delete_account` calls `remove_account`, which never touches `PromiseYieldReceipt`/`PromiseYieldStatus`/yield-id mapping keys for `V` [8](#0-7) [2](#0-1) . The stale `PromiseYieldReceipt` and `PromiseYieldStatus` remain in state.
3. If `V` is a sufficiently long top-level account name, any other unprivileged user can now claim `V` via `CreateAccount` and deploy a different contract there [1](#0-0) .
4. When `apply_state.block_height` reaches `expires_at`, `resolve_promise_yield_timeouts` walks the still-live `PromiseYieldTimeout` queue entry (unaffected by the deletion since it's indexed globally, not by account) [9](#0-8) , finds `contains_key(PromiseYieldReceipt{V,data_id}) == true` (stale data), and forwards a `PromiseResume{predecessor_id: V, receiver_id: V, data: None}` receipt [10](#0-9) .
5. On the next chunk, `process_receipt`'s `PromiseResume` arm fetches the stale `yield_receipt`, removes the promise-yield bookkeeping, and executes the old receipt's actions via `apply_action_receipt` against the *current* (recreated) account `V` [5](#0-4) .

No existing check re-validates that the account identity/contract at execution time matches the one that created the yield; the promise-scoping invariant ("a parked continuation belongs to the account that created it, for its whole lifetime") is broken because `remove_account` is not made aware of promise-yield state associated with the account it deletes.

### Impact Explanation
This is an authorization-scoping bug (NEAR bounty category "authorization escalation across accounts or promises"): an action receipt, marked as `predecessor_id == receiver_id == current_account_id` (the idiomatic "self-call" trust pattern many contracts use to gate privileged internal logic, e.g. `assert_self()`), can be injected into an account by a party who never authorized it — the receipt's method name/args were chosen long before by whoever previously owned that account name. If the new owner's contract happens to expose a like-named callback trusting self-calls, the stale receipt executes it without the new owner's consent. There is no theft of a third party's live funds in the general case (the deposit attached to the receipt, if any, was already reserved when the receipt was originally created and simply lands on the account that now exists), but it is a genuine confused-deputy/self-trust bypass and a state-consistency defect (dangling trie entries that never get cleaned up if the account is never recreated).

### Likelihood Explanation
Preconditions are narrow but reachable purely by an unprivileged client: the attacker must (a) control the yield-creating contract, (b) delete that account, and (c) either be the party who later recreates it (self-only benefit, low value) or rely on someone else claiming a sufficiently long top-level account name that they intentionally vacate (opportunistic/low-probability unless the attacker also controls or predicts reuse of that specific name). Sub-accounts and implicit accounts cannot be hijacked by a different party, which significantly limits real-world exploitability. Cost to the attacker is minimal (one yield-create call, one delete-account call); the bug is deterministically reproducible in a unit/integration test.

### Recommendation
In `remove_account` (core/store/src/utils/mod.rs), when deleting an account also remove any `PromiseYieldReceipt`, `PromiseYieldStatus`, and `YieldIdToDataId`/`DataIdToYieldId` entries keyed by that account (mirroring the existing access-key/contract-data cleanup iteration), and either eagerly dequeue the associated `PromiseYieldTimeout` queue entries or have `resolve_promise_yield_timeouts` treat a deleted-and-recreated account's timeout entries as inert (e.g., by additionally validating an account/epoch-scoped nonce stored with the yield rather than trusting bare `contains_key`).

### Proof of Concept
Runtime/test-loop integration test plan (mirroring `test-loop-tests/src/tests/yield_timeouts.rs` and `create_delete_account.rs` patterns):
1. Deploy `rs_contract` to account `V` (a long top-level account, e.g. `verylongaccountname123.near`, to avoid the registrar restriction) and call `call_yield_create_return_promise` to create a pending yield, capturing `data_id`.
2. Before the timeout height, submit `DeleteAccount` for `V` with some beneficiary; assert the account no longer resolves via `view_account_query`.
3. From a different signer, submit `CreateAccount` for the exact same `V` and deploy a distinct test contract (e.g., one exposing a differently-behaving method with the same name used in the original callback).
4. Advance chain height to `expires_at`; assert `resolve_promise_yield_timeouts` still produces a `PromiseResume` receipt for `V` (i.e., the stale `PromiseYieldReceipt` was found via `contains_key`).
5. Advance one more block and assert the callback action executed against the *new* contract's code/state at `V` (e.g., by checking a state mutation or log emitted only by the second contract, and/or that `get_yield_data_ids_in_state` / `get_promise_yield_receipt` shows the entry was removed only during this post-recreation resume, not during the original `DeleteAccount`).
6. As the negative/expected-fixed assertion, after applying the recommended fix, assert that `remove_account` clears the `PromiseYieldReceipt` at step 2 and that no `PromiseResume` receipt (or only a no-op one) is produced at step 4.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
