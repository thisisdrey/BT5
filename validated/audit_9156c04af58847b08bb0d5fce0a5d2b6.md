### Title
StackerDB unsolicited-push handler advertises a chunk as stored via the immediate inventory reply before the chunk is actually committed, letting a validation/commit race serve non-canonical inventory as canonical - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` patches the outgoing `StackerDBChunkInv` reply's `slot_versions` entry to the *newly pushed* version as soon as `validate_received_chunk` (signature + size + monotonic-version check) succeeds, and immediately sends that reply back to the pusher. The actual write to the on-disk StackerDB (`StackerDBTx::try_replace_chunk`) does not happen here; it happens later and asynchronously, once the message is forwarded to the relayer and processed via `Relayer::process_pushed_stacker_db_chunks` / `process_stacker_db_chunks`. This creates a window in which the node's advertised inventory ("I have version V of slot S") does not match what is actually committed to the database.

### Finding Description
In `handle_unsolicited_StackerDBPushChunk`: [1](#0-0) 
after `validate_received_chunk` returns true, the code does:
```
*slot_version = chunk_data.chunk_data.slot_version;
```
directly on the `StackerDBChunkInv` reply payload, and this reply is signed and sent back to the peer a few lines later: [2](#0-1) 

`validate_received_chunk` only checks size, signer signature, and that `slot_version` is monotonically ≥ the last known version and ≤ `max_writes`: [3](#0-2) 
It does **not** perform the actual storage — storage is explicitly deferred to `StackerDBTx::try_replace_chunk`, which is only invoked later by the relayer: [4](#0-3) [5](#0-4) 

`try_replace_chunk` re-checks the slot's *currently stored* version (`slot_validation.version`) and rejects with `StaleChunk` if a concurrent write has already advanced the slot past the version this chunk assumed, or with `TooManySlotWrites`/DB errors for other reasons. When that happens, `process_stacker_db_chunks`/`process_pushed_stacker_db_chunks` only logs a `debug!`/`warn!` and silently drops the chunk — no correction is ever sent back to the peer that already received the "accepted" `StackerDBChunkInv` reply.

Meanwhile, the receiving peer stores that (now stale/incorrect) claim in its own bookkeeping: [6](#0-5) 
and later uses it to decide whether it still needs to fetch/push that slot from/to this node (rarest-first scheduling): [7](#0-6) 

So the equality "signature+version validated ⇒ actually committed to the local replica" is broken: a node can advertise (and get remembered by peers as) holding a chunk version it never actually stored, because the inventory reply is derived from the pre-commit validation step, not from post-commit state.

### Impact Explanation
This is a "served vs committed" / "authenticated vs stored" break: the node serves inventory data that does not reflect canonical (actually persisted) local state. Peers that rely on this false inventory will believe this replica already holds the newest chunk for the affected slot and will stop offering it that chunk, or stop requesting it, stalling propagation of that StackerDB slot for this node indefinitely (until an unrelated event forces a resync). This matches the "High: serving non-canonical state as canonical" impact category — no crash or unauthorized write occurs, but the replicated-inventory contract is broken by ordinary, remotely-triggerable races.

### Likelihood Explanation
The remote actor needs only a *valid signer key for a slot they are legitimately entitled to write* (a normal StackerDB participant, e.g., any signer registered in a `.signers-*`-style contract, or an app operator who owns a slot in their own StackerDB) — no secret belonging to another party or elevated privilege is required. Triggering the race only requires sending two overlapping, validly-signed pushes for the same slot (e.g., over two TCP connections to the same victim, or exploiting normal concurrent relay/sync activity) so that the fast-path `validate_received_chunk` accepts and advertises one version while `try_replace_chunk` later rejects it as stale due to the other push landing first. This condition can occur naturally under legitimate concurrent StackerDB writes and is easy to force deliberately, making it fairly likely to trigger, though the resulting impact (temporary replication desync of one slot) is moderate rather than severe.

### Recommendation
Do not patch/send the `StackerDBChunkInv` reply's slot version optimistically based on pre-commit validation. Either:
1. Defer sending the `StackerDBChunkInv` reply until after the chunk has actually been committed by the relayer (requires restructuring the unsolicited-push flow to be commit-then-reply), or
2. On commit failure (`StaleChunk`, `TooManySlotWrites`, DB error) in `process_pushed_stacker_db_chunks`/`process_stacker_db_chunks`, proactively send a corrective/latest `StackerDBChunkInv` to the affected peer(s) reflecting the true, currently-stored version, so downstream bookkeeping (`chunk_invs`) is not left holding stale/false state.

### Proof of Concept
1. Set up a StackerDB slot with a legitimate signer key the attacker controls.
2. Open two P2P connections to the victim node.
3. Simultaneously send two `StackerDBPushChunk` messages for the same `(contract_id, slot_id)` with `slot_version = N` (both validly signed, differing payload/content), one on each connection, timed so both pass `handle_unsolicited_StackerDBPushChunk`'s `validate_received_chunk` fast-path check before either is actually committed.
4. Both connections receive a `StackerDBChunkInv` reply claiming `slot_versions[slot_id] = N`.
5. When the relayer processes both pushes via `process_pushed_stacker_db_chunks`, one call to `try_replace_chunk` succeeds and the other fails with `StaleChunk` (logged at `debug!` and dropped) — but the peer on the failed connection already believes (from step 4) that the victim node holds version `N`.
6. That peer will not re-offer or re-request slot `slot_id` from the victim (per `make_chunk_request_schedule`'s freshness comparison), even though the victim's actual DB never advanced to `N` via that peer's push — demonstrating the served-vs-committed inventory mismatch.

        config: &StackerDBConfig,

                smart_contract_id,
                data.slot_id,
                data.data.len(),
                config.chunk_size
            );
            return Ok(false);
        }

        // validate -- must be a valid chunk
        let Some(expected_version) = expected_versions.get(data.slot_id as usize) else {
            info!(
                "Received StackerDBChunk for {} ID {}, which is too big ({})",
                smart_contract_id,
                data.slot_id,
                expected_versions.len()
            );
            return Ok(false);
        };

        // validate -- must be signed by the expected author
        let addr = match self
            .stackerdbs
            .get_slot_signer(smart_contract_id, data.slot_id)?
        {
            Some(addr) => addr,
            None => {
                return Ok(false);
            }
        };

        let slot_metadata = data.get_slot_metadata();
        if !slot_metadata.verify(&addr)? {
            info!(
                "StackerDBChunk for {} ID {} is not signed by {}",
                smart_contract_id, data.slot_id, &addr
            );
            return Ok(false);
        }

        // validate -- must be the current or newer version
        if data.slot_version < *expected_version {
            info!(
                "Received StackerDBChunk for {} ID {} version {}, which is stale (expected {})",
                smart_contract_id, data.slot_id, data.slot_version, *expected_version
            );
            return Ok(false);
        }

        // validate -- must not exceed max writes
        if data.slot_version > config.max_writes {
            info!(
                "Write count exceeded for StackerDBChunk for {} ID {} version {} (max is {})",
                smart_contract_id, data.slot_id, data.slot_version, config.max_writes
            );
            return Ok(false);
        }

        Ok(true)

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
