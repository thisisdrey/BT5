### Title
Unliquidatable underwater positions: `debtFloorInUsd` + `maxLiquidable` + collateral-balance checks permanently brick `Pool.liquidate`, causing protocol bad debt - (File: contracts/Pool.sol)

### Summary
Analogous to CVE-2019-2966 (low-privileged input that reliably crashes/hangs a core service path), an unprivileged borrower can craft a position for which every possible `liquidate` call reverts. Three checks in `Pool.liquidate`/`quoteLiquidateOut` interact so that no `amountToRepay_` value satisfies all of them simultaneously: `AmountGreaterThanMaxLiquidable` (caps repayment at `maxLiquidable`, default 50%), `RemainingDebtIsLowerThanTheFloor` (forbids leftover debt in `(0, debtFloorInUsd)`), and `AmountIsTooHigh` (seizure capped at the account's `depositToken` balance). The result is a repeatable, unconditional DoS of liquidation for that position, forcing the protocol to absorb bad debt.

### Finding Description
`liquidate` enforces, in order:

1. `amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable` → repay at most 50% of debt (`Pool.sol:567`, `maxLiquidable` initialized to `0.5e18` at `Pool.sol:181`).
2. If `debtFloorInUsd > 0`: `_newDebtInUsd` must be `0` or `>= debtFloorInUsd` (`Pool.sol:571-579`).
3. `_totalSeized = fee + toLiquidator` must be `<= depositToken_.balanceOf(account_)` (`Pool.sol:581-585`), where `_toLiquidator` is the oracle-priced collateral amount inflated by `liquidatorIncentive` (`Pool.sol:456-471`).

Consider a deployed config with `debtFloorInUsd = 1000e18` and `maxLiquidable = 0.5e18`. Attacker opens a position with debt `D` where `D/2 < debtFloorInUsd <= D` (e.g., D ≈ $1,500) and collateral barely above `D` in USD value (e.g., $1,520). Then the collateral price drops slightly (or the attacker lets interest accrue / the synth appreciates) so collateral value < `D * (1 + liquidatorIncentive + protocolFee)`:

- Repaying `<= 50%` of D leaves remaining debt in `(0, debtFloorInUsd)` → `RemainingDebtIsLowerThanTheFloor`.
- Repaying 100% of D requires seizing collateral worth `D * (1 + incentives + fee)` > `depositToken.balanceOf(account_)` → `AmountIsTooHigh`.

Every `amountToRepay_` reverts. `quoteLiquidateMax` confirms the same dead end for keepers. The position is permanently unliquidatable and accrues interest via `DebtToken.accrueInterest`, deepening the shortfall.

No guard stops this: `liquidate` is permissionless, the attacker is a normal borrower (not governor/keeper), `nonReentrant`/`whenNotShutdown`/`onlyIfSyntheticTokenExists`/`onlyIfDepositTokenExists` are all satisfied, and the attacker can force the underwater state cheaply via same-transaction price manipulation through `Pool.swap`-driven quotes or by simply depositing minimal collateral and waiting for normal volatility/interest accrual.

### Impact Explanation
Permanently unliquidatable positions → the DebtToken balance keeps growing while backing collateral is worth less than the debt. Once the collateral is exhausted the residual debt is socialized across `SyntheticToken` holders (protocol insolvency / bad debt), the exact availability-then-solvency failure the source CVE class describes (repeatable crash of a core service). Invariant broken: liquidation liveness / protocol solvency.

### Likelihood Explanation
Any EOA can open such a position with modest capital (collateral just above `debtFloorInUsd` worth of debt). A mildly volatile collateral tick or accrued interest pushing the position underwater by more than the liquidation incentive is enough to trigger the dead zone. Liquidation bots calling `quoteLiquidateMax`/`liquidate` will always revert.

### Recommendation
In `Pool.liquidate`, when the position is deeply underwater, allow the liquidation to proceed by (a) waiving the `debtFloorInUsd` check when the remaining collateral cannot cover the remaining debt, or (b) capping `_totalSeized`/`amountToRepay_` to what the collateral balance can cover and writing off the residual debt (bad-debt socialization via `DebtToken`), so no position can become permanently unliquidatable.
