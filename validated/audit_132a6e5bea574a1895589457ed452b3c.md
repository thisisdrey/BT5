### Title
Unbounded creation of dust market orders bloats chain storage - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.validate()` only rejects orders with `sellTokenQuantity <= 0` or `buyTokenQuantity <= 0` [1](#0-0) . There is no minimum notional/economic-value floor on an order (e.g. a sell quantity of `1` unit of a token is accepted), so any account can flood the on-chain market order book with dust orders that persist in global stores until cancelled or matched.

### Finding Description
Each successful `MarketSellAssetContract` transaction writes permanent entries to four separate stores: `MarketOrderStore`, `MarketAccountStore` (via `MarketAccountOrderCapsule`), `MarketPairToPriceStore`, and `MarketPairPriceToOrderStore` [2](#0-1) . The only quantitative validation performed is:
- `sellTokenQuantity <= 0 || buyTokenQuantity <= 0` → reject [1](#0-0) 
- an upper bound `quantityLimit` check [3](#0-2) 
- a per-account cap `MAX_ACTIVE_ORDER_NUM = 100` [4](#0-3) [5](#0-4) 

There is no minimum order size (e.g. requiring the sell/buy quantity times price to exceed some floor). Because there is no minimum, an attacker can place an order selling `1` unit of any token for a large buy quantity of another token (or TRX), which will almost never match and will remain resident in the order book indefinitely, occupying entries in `MarketOrderStore`, `MarketPairToPriceStore` and `MarketPairPriceToOrderStore` — none of which are pruned except by matching or an explicit `MarketCancelOrderActuator` call by the order owner.

Although the 100-order cap limits a single account, it does not limit the number of distinct accounts an attacker controls. Creating a new account only requires a small TRX transfer (`CreateAccountActuator`/implicit account creation), which is comparatively cheap, and each new account can then open up to 100 dust orders across arbitrary token pairs, multiplying the number of distinct `MarketPairToPriceStore`/`MarketPairPriceToOrderStore` price-level entries created (since each unique price ratio derived from `sellTokenQuantity`/`buyTokenQuantity` creates a new price key) [6](#0-5) .

### Impact Explanation
This is analogous to the Acala `deposit_dex_share` bug: absence of a minimum economically-meaningful trade size lets an attacker cheaply create large numbers of near-worthless, permanent entries across multiple key-value stores (`MarketOrderStore`, `MarketAccountStore`, `MarketPairToPriceStore`, `MarketPairPriceToOrderStore`). Because java-tron persists all of these in its LevelDB/RocksDB-backed stores that every full node must maintain, sustained abuse increases disk/state size and node maintenance cost for all network participants, and could degrade node performance for market-related queries (`getMarketOrderByAccount`, `getMarketPriceByPair`, etc.) that iterate these stores.

### Likelihood Explanation
Reaching this path only requires the attacker to have a TRON account holding minimal TRX (for account creation and the market-sell fee) and to construct standard `MarketSellAssetContract` transactions — an unprivileged, permissionless action fully reachable by any transaction broadcaster, with no special/authority checks required beyond `supportAllowMarketTransaction()` being enabled network-wide [7](#0-6) . The 100-order-per-account cap somewhat throttles a single account but is trivially bypassed with more (cheaply created) accounts.

### Recommendation
Introduce a minimum order size/notional check in `MarketSellAssetActuator.validate()` (e.g., require `sellTokenQuantity` and/or the implied trade value to exceed a configurable minimum, similar to the existing `quantityLimit` upper bound check at lines 227-230), and/or charge a storage-proportional fee for resting (unmatched) orders to disincentivize dust-order spam.

### Proof of Concept
1. Attacker creates N accounts, each funded with the minimal TRX needed to pay the market-sell fee.
2. From each account, attacker repeatedly submits `MarketSellAssetContract` transactions with `sellTokenQuantity = 1` (any token or TRX) and an arbitrary `buyTokenQuantity`, up to `MAX_ACTIVE_ORDER_NUM = 100` orders per account.
3. Each call passes `validate()` because it only checks `sellTokenQuantity > 0`, `buyTokenQuantity > 0`, and the upper `quantityLimit` bound — no minimum trade value is enforced [8](#0-7) .
4. Each call succeeds and writes a new resting order into `MarketOrderStore`/`MarketAccountStore`/`MarketPairToPriceStore`/`MarketPairPriceToOrderStore` [2](#0-1) , permanently occupying storage until the attacker (or anyone) cancels or someone matches the dust order.
5. Repeating across many self-created accounts scales storage growth roughly linearly with the number of accounts and transactions, at a cost far below the value of storage consumed.
