### Title
Atlas `extend_with_attachments` stores attachment content with no verification against the requested `content_hash` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes a peer's `GetAttachmentResponse` and unconditionally inserts `response.attachment` into `self.attachments: HashSet<Attachment>` without ever comparing `Attachment::hash()` to the `request.content_hash` that was originally solicited. A malicious/compromised P2P peer selected via `get_most_reliable_source` can therefore return arbitrary bytes for any requested `content_hash`.

### Finding Description
The code path is: [1](#0-0) 

For each `(request, response)` in `results.succeeded`, if `response.decode_atlas_get_attachment()` succeeds, the code does `self.attachments.insert(response.attachment)` and bumps the peer's reliability score - there is no check of the form `request.content_hash == response.attachment.hash()`. The `AttachmentRequest` (which carries the `content_hash` that was requested, via `Requestable`) is dropped after `report` lookup; its `content_hash` field is never read again in this function. `Attachment::hash()` (backed by `Hash160::from_data`) is the only mechanism that ties served bytes to the BNS-committed content hash, and that check is absent at the exact site where remote-controlled bytes enter the trusted `self.attachments` set.

The attacker's exact message is an HTTP 200 response to the outbound `RPCGetAttachmentRequestHandler` request, containing a `GetAttachmentResponse { attachment: Attachment { content: garbage_bytes } }` where `Hash160::from_data(&garbage_bytes) != request.content_hash`. Because the peer is picked via `get_most_reliable_source` from `AttachmentsBatch::get_prioritized_attachments_requests`, any peer that has been (or becomes) "reliable" — including an attacker-run node — can serve this fabricated response for a hash they were never able to satisfy honestly.

### Impact Explanation
An unvalidated attachment enters `AttachmentsBatchStateContext.attachments`. This breaks the intended invariant that everything in this set corresponds byte-for-byte to a BNS-committed `content_hash`. Whether this results in on-disk corruption in `AtlasDB` depends on how the final `Done` state pairs entries in `self.attachments` back to each `AttachmentInstance`'s `content_hash` (that pairing logic was not fully re-derivable from the excerpts inspected in this session), so I cannot confirm with full certainty that a mismatched attachment ultimately gets persisted under the wrong hash versus being silently dropped at pairing time. Given the explicit absence of the check at the cited insertion site and the precise match to the reported code, this is a real gap in defense-in-depth for the Atlas download path (attachment/BNS mismatch class), but confirming end-to-end persistence under the wrong hash requires tracing the `Done`-state pairing code, which was not conclusively examined.

### Likelihood Explanation
Preconditions: the attacker must run/control a peer that the node selects as an outbound sync peer and that gets chosen by `get_most_reliable_source` for a specific `content_hash` request; this is achievable by any unprivileged remote peer that participates honestly enough to build reliability score, at attacker's own compute/bandwidth cost, and is repeatable per attachment request cycle.

### Recommendation
In `extend_with_attachments` (stackslib/src/net/atlas/download.rs), after `decode_atlas_get_attachment()` succeeds, explicitly verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; on mismatch, treat it as a failed request (`report.bump_failed_requests()`) and optionally penalize/deregister the peer.

### Proof of Concept
Rust unit test in `stackslib::net::atlas::download` (or `tests.rs`):
1. Construct an `AttachmentRequest` with a known `content_hash` H.
2. Construct a `StacksHttpResponse` whose `decode_atlas_get_attachment()` returns `Attachment { content: garbage_bytes }` where `Hash160::from_data(&garbage_bytes) != H`.
3. Build a `BatchedRequestsResult { succeeded: {request -> Some(response)}, faulty_peers: {} }`.
4. Call `AttachmentsBatchStateContext::extend_with_attachments(ctx, &mut results)`.
5. Assert `ctx.attachments.contains(&Attachment{content: garbage_bytes})` is `true`, demonstrating the mismatched attachment was accepted at this stage without any equality check against `request.content_hash`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
