### Title
Exchange liquidity withdrawal has no slippage/minimum-output protection, enabling sandwich attacks against pool creators - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeWithdrawContract` (Bancor-style TRC10 exchange liquidity withdrawal) computes the amount of the paired token to return using the exchange pool's *current* on-chain balances at validate/execute time, but the protobuf message provides no way for the caller to bound the acceptable output, unlike `ExchangeTransactionContract` which has an explicit `expected` (minimum) field checked in `ExchangeTransactionActuator`.

### Finding Description
`ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected`/minimum-output field, as documented in the protocol spec [1](#0-0) .

In `ExchangeWithdrawActuator.doValidate()` and `execute()`, the amount of the "other" token to be withdrawn (`anotherTokenQuant`) is derived purely from the exchange's live `firstTokenBalance`/`secondTokenBalance` ratio at the moment the transaction is processed: [2](#0-1) 

Compare this to `ExchangeTransactionActuator`, which does have a caller-supplied `tokenExpected` and enforces it against the freshly computed `anotherTokenQuant`, rejecting the transaction if it falls short: [3](#0-2) 

No equivalent check exists for `ExchangeWithdrawActuator` (nor for `ExchangeInjectActuator`, which also computes proportional amounts without a caller-specified bound). Because the pool ratio is mutated by any preceding `ExchangeTransactionContract` trade against the same `exchange_id` within the same block (`ExchangeCapsule.transaction()` mutates `firstTokenBalance`/`secondTokenBalance` in place, see [4](#0-3) ), and transactions in a block are validated and executed sequentially in submission order (see `processBlock` iterating `block.getTransactions()` and calling `processTransaction` per tx: [5](#0-4) ), an attacker can place a large `ExchangeTransactionContract` trade immediately before a victim's `ExchangeWithdrawContract` to skew the pool ratio, then reverse the trade immediately after — a classic sandwich attack. The withdrawer has no on-chain mechanism to cap the resulting slippage/loss.

### Impact Explanation
This is the same bug class as the source report: a value-bearing operation whose output is priced off a mutable on-chain AMM state has no user-configurable minimum-output/slippage bound, so a single-block MEV sandwich attack (achievable by any account submitting an `ExchangeTransactionContract` broadcast transaction) can force the withdrawing exchange creator to receive substantially less than the fair-value amount of the paired asset, with the sandwiching attacker capturing the difference. This is a concrete loss-of-funds vector reachable purely via broadcastable transactions, matching "theft of funds" impact criteria.

### Likelihood Explanation
Any account can create the preceding/following trade transactions (`ExchangeTransactionContract` is a permissionless, unprivileged operation), and block producers/relayers or the attacker themselves can order transactions to achieve the sandwich within a single block. Exploitation requires only submitting ordinary signed transactions, no special privileges. Note: `isExchangeTransaction`/`rejectExchangeTransaction` in `Manager.java` shows `ExchangeTransactionContract` is rejected after fork `VERSION_4_8_0_1` unless `allowHardenExchangeCalculation` is active [6](#0-5) , meaning on networks where this legacy exchange feature is still active (or hardened calculation is enabled but withdraw/inject remain unguarded), the exposure persists since the reject-check only targets `ExchangeTransactionContract`, not `ExchangeWithdrawContract`/`ExchangeInjectContract`.

### Recommendation
Add a caller-supplied minimum acceptable output (and/or maximum acceptable input) field to `ExchangeWithdrawContract` and `ExchangeInjectContract`, analogous to the `expected` field already present in `ExchangeTransactionContract`, and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` and `ExchangeInjectActuator.doValidate()`/`execute()` before mutating balances.

### Proof of Concept
1. Attacker observes a pending `ExchangeWithdrawContract` from the pool creator for `exchange_id = X` requesting withdrawal of `tokenQuant` of `firstToken`.
2. Attacker submits an `ExchangeTransactionContract` trade against the same exchange `X` that shifts `firstTokenBalance`/`secondTokenBalance` sharply (e.g., dumping a large amount of `secondToken` into the pool), ordered to execute immediately before the victim's withdrawal in the same block.
3. The victim's `ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` off the now-skewed ratio (`actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java` lines 74-89), returning far less of `secondToken` than expected, since there is no `expected`/minimum field to reject the trade.
4. Attacker submits a reverse `ExchangeTransactionContract` immediately after to restore the ratio and lock in profit extracted from the victim's withdrawal.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private boolean isExchangeTransaction(Transaction transaction) {
    if (getDynamicPropertiesStore().allowHardenExchangeCalculation()) {
      return false;
    }
    Contract contract = transaction.getRawData().getContract(0);
    switch (contract.getType()) {
      case ExchangeTransactionContract: {
        return true;
      }
      default:
        return false;
    }
  }

  private void rejectExchangeTransaction(Transaction transaction) throws ContractValidateException {
    if (isExchangeTransaction(transaction) && chainBaseManager.getForkController()
            .pass(Parameter.ForkBlockVersionEnum.VERSION_4_8_0_1)) {
      throw new ContractValidateException("ExchangeTransactionContract is rejected");
    }
  }
