### Title
SCP-style URL host-pinning bypass in `getURLAndResolveConfigForSCP` allows SSRF/DNS-rebinding protection evasion - (File: internal/git/gitcmd/command_resolve.go)

### Summary
`getURLAndResolveConfigForSCP` computes the `userPrefix` by searching for the first `@` in the *entire* raw URL string rather than only within the host segment (text before the first `:`), while the host/path split is computed independently via `strings.SplitN(remoteURL, ":", 2)`. When an attacker supplies a scp-like URL whose path portion (after the first colon) contains an `@`, the resulting reconstructed string retains the original attacker-controlled hostname as the leading, colon-terminated host token, with the resolved IP address buried inside what git parses as the path/user component — completely defeating the resolved-address pinning meant to prevent DNS-rebinding SSRF.

### Finding Description
`GetURLAndResolveConfig` (`internal/git/gitcmd/command_resolve.go:27`) dispatches non-`http(s)`/`git`/`ssh://` URLs to `getURLAndResolveConfigForSCP` (`internal/git/gitcmd/command_resolve.go:62`). That function:

1. Splits on the first `:` to get `hostAndPath` — `hostAndPath[0]` is meant to be `[user@]host`, `hostAndPath[1]` the path.
2. Independently computes `userPrefix` via `strings.SplitAfterN(remoteURL, "@", 2)` over the **whole original URL**, not `hostAndPath[0]`.
3. Reconstructs: `fmt.Sprintf("%s%s:%s", userPrefix, resolvedAddress, hostAndPath[1])`.

If the attacker crafts a URL where the host segment (before the first `:`) contains **no** `@`, but the path segment (after the first `:`) does contain one — e.g. `host:user@evilhost:repo.git` — then:
- `hostAndPath` = `["host", "user@evilhost:repo.git"]` (passes the `/`-in-host check).
- The first `@` in the whole string is inside the path segment, so `SplitAfterN` yields `userPrefix = "host:user@"` — which improperly re-includes the original, untouched hostname `host` and its colon.
- Final URL = `"host:user@" + resolvedAddress + ":" + "user@evilhost:repo.git"` = `"host:user@203.0.113.5:user@evilhost:repo.git"`.

When this string is later handed to `git` as an scp-like remote (via `remote.inmemory.url` config in `internal/gitaly/service/repository/fetch_remote.go:280` or the clone `Args` in `internal/gitaly/service/repository/create_repository_from_url.go:81`), git's own scp-URL parser splits on the *first* colon to find host/path, which is `host` — the original, unresolved, attacker-supplied hostname — not `resolvedAddress`. The resolved IP and the rest end up folded into the path/command argument, never used as the actual SSH connection target. This is exactly the "Git is never re-configured by input" / anti-DNS-rebinding invariant being defeated: the caller (GitLab Rails) resolves the hostname to a vetted IP specifically so Gitaly pins the SSH connection to that IP regardless of subsequent DNS changes, but this code path silently reverts to dialing the original hostname string. ### Impact Explanation
This breaks the anti-DNS-rebinding SSRF mitigation for the SSH transport path of `FetchRemote` and `CreateRepositoryFromURL`. An attacker who controls `RemoteParams.Url`/`Url` (a repo owner configuring a pull mirror or import URL) together with the caller-computed `ResolvedAddress` can cause Gitaly's `git` invocation to connect over SSH to the original, untrusted hostname string embedded in the URL instead of being pinned to the vetted resolved IP — reintroducing classic TOCTOU DNS-rebinding SSRF against internal/private network services reachable over SSH from the Gitaly host. This matches GitLab's SSRF bounty impact class.

### Likelihood Explanation
Fully reachable by an unprivileged authenticated GitLab user through standard pull-mirror/import flows that populate `RemoteParams.Url`/`ResolvedAddress` and reach `FetchRemote`/`CreateRepositoryFromURL`; no special role, secret, or non-default configuration is required. Crafting the payload only requires knowledge of the scp-like URL format (`host:path` with an embedded `@` in the path) and is fully deterministic/repeatable.

### Recommendation
Compute `userPrefix` only from within `hostAndPath[0]` (the host segment), not from the whole `remoteURL`. E.g., replace `strings.SplitAfterN(remoteURL, "@", 2)` with a split of `hostAndPath[0]` alone (`strings.SplitAfterN(hostAndPath[0], "@", 2)`), and reject/validate that `hostAndPath[0]` (the true host token) doesn't itself contain unexpected embedded colons/at-signs beyond a single optional `user@` prefix.

func getURLAndResolveConfigForSCP(remoteURL, resolvedAddress string) (string, []ConfigPair, error) {
	hostAndPath := strings.SplitN(remoteURL, ":", 2)
	if len(hostAndPath) != 2 {
		return "", nil, fmt.Errorf("invalid protocol/URL encountered: %s", remoteURL)
	}

	if strings.Contains(hostAndPath[0], "/") {
		return "", nil, fmt.Errorf("SSH URLs with '/' before colon are unsupported")
	}

	var userPrefix string

	if userAndHost := strings.SplitAfterN(remoteURL, "@", 2); len(userAndHost) > 1 {
		userPrefix = userAndHost[0]
	}

	return fmt.Sprintf("%s%s:%s", userPrefix, resolvedAddress, hostAndPath[1]), nil, nil
}
