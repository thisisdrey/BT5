### Title
Handshake re-keying skips signature-to-key binding check, allowing forged `node_public_key` and PeerDB poisoning - ([File: stackslib/src/net/chat.rs])

### Summary
`validate_handshake` in `ConversationP2P` only calls `message.verify_secp256k1(&handshake_data.node_public_key)` when `self.connection.get_public_key()` is `None` [1](#0-0) . Once a key is cached (`Some(_)`), the `Some(_)` branch only checks the peer's self-reported address for outbound connections and never re-verifies that the message's cryptographic signature actually corresponds to the newly-claimed `handshake_data.node_public_key` [2](#0-1) .

### Finding Description
The equality that should hold — "the signer of this message == the `node_public_key` embedded in the handshake payload" — is only enforced on the very first handshake (`None` branch). On any subsequent `Handshake` for an already-keyed conversation, that binding check is dropped entirely; the code merely validates the claimed address/port for outbound peers and otherwise falls through [2](#0-1) .

`handle_handshake` calls `validate_handshake`, and on success unconditionally calls `update_from_handshake_data`, which reads `handshake_data.node_public_key`, compares it to the currently-cached key, and if different, calls `self.connection.set_public_key(Some(pubk.clone()))` — rekeying the conversation to whatever key was embedded in the payload, with no proof that the message was actually signed by that key [3](#0-2) . If the conversation is outbound and the key changed, the code goes further and persists this unverified key to the `PeerDB` via `Neighbor::load_and_update` / `neighbor.save_update` [4](#0-3) .

An attacker with an established, keyed outbound conversation (i.e. a peer the node dialed and already handshook with once, caching key K1) can send a second `Handshake` message, signed with their own valid key K1 (so it passes the outer wire-level authentication check tied to the cached key), but with `handshake_data.node_public_key` set to an arbitrary key K2 they do not control the private key for (e.g., a victim node's real public key). Because the `Some(_)` branch of `validate_handshake` never checks that the message signature corresponds to K2, this forged handshake passes validation. `update_from_handshake_data` then rekeys the conversation to K2 and, being an outbound connection, persists this attacker-chosen, unproven key into the local `PeerDB` neighbor record for that address.

### Impact Explanation
This is an unauthenticated/unauthorized write to persistent node state: the local `PeerDB` neighbor entry is updated with a public key the attacker never proved ownership of, corrupting the node's record of a peer's true identity. This can cause identity confusion (associating an address with a key belonging to someone else), and it desynchronizes the conversation's cached key from what any future legitimate signer can produce, degrading or breaking authentication for that peer relationship going forward. Repeatable per outbound conversation the attacker can influence.

### Likelihood Explanation
Requires the attacker to already hold an established outbound conversation with the victim node (attacker is remotely reachable and unprivileged, satisfying the P2P port reachability requirement) and to send one additional crafted `Handshake` message with a mismatched `node_public_key` field, signed with their own already-cached key. No secret, admin role, or privileged access is needed — only the ability to complete a normal handshake and send a follow-up message, which is cheap and repeatable.

### Recommendation
In the `Some(_)` branch of `validate_handshake`, always verify `message.verify_secp256k1(&handshake_data.node_public_key)` regardless of whether the connection already has a cached public key, so that any claimed rekey is cryptographically bound to the new key before `update_from_handshake_data`/`PeerDB` writes occur.

### Proof of Concept
Rust test plan (in `stackslib/src/net/chat.rs` or its test module):
1. Establish a `ConversationP2P` as outbound, perform an initial signed `Handshake` with key K1 so `self.connection.get_public_key() == Some(K1)`.
2. Construct a second `StacksMessage` containing `StacksMessageType::Handshake(HandshakeData { node_public_key: K2_buffer, .. })`, sign the message with K1 (valid outer signature, so it passes normal message-level auth), but leave `node_public_key` set to K2 where the test does not sign with K2's private key at all.
3. Call `handle_handshake(&mut network, &mut msg, true, false)` and assert it returns `Ok` (no `InvalidHandshake`/`InvalidMessage`) despite K2 never being proven.
4. Assert `self.connection.get_public_key() == Some(K2)` after the call, and (for outbound) that the `PeerDB` neighbor record was updated to K2 — demonstrating the forged rekey succeeded without the signature-to-key binding check that exists in the `None` branch.
