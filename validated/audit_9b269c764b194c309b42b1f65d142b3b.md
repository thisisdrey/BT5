### Title
Missing `AllowTvmCompatibleEvm`/contract-version check in `TransferAssetActuator` allows sending TRC10 assets to version-1 contracts (control-flow inconsistency mirrors the FastChat sibling-handler omission) - (File: actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java)

### Summary
The FastChat advisory describes a moderation bypass where a control-flow fix (`add_text`) was applied to only one of several structurally-identical handler files, leaving sibling code paths unprotected. java-tron has the same bug-class pattern between its two "transfer" actuators: `TransferActuator` and `TransferAssetActuator` implement nearly identical `validate()`/`execute()` logic for sending value to another account, but a specific safety check that was added to `TransferActuator` was never mirrored into `TransferAssetActuator`.

### Finding Description
`TransferActuator.validate()` contains two guarded checks before allowing a transfer to a contract account:
1. `ForbidTransferToContract` — blocks sending TRX to any smart contract.
2. `AllowTvmCompatibleEvm` — additionally blocks sending TRX to a smart contract whose `ContractCapsule.getContractVersion() == 1` (a legacy, non-EVM-compatible contract), instructing callers to use `TriggerSmartContract` instead: [1](#0-0) 

`TransferAssetActuator.validate()`, which performs the analogous operation for TRC10 asset transfers, only carries over the first check (`ForbidTransferToContract`) and completely omits the version-1 / `AllowTvmCompatibleEvm` restriction: [2](#0-1) 

Both actuators are reachable directly from a single signed, unprivileged broadcast transaction (`TransferContract` / `TransferAssetContract`) via `TransactionCapsule`/`Manager` execution, so any account holding a TRC10 token balance can invoke `TransferAssetActuator` to route asset balance into a version-1 contract that the protocol otherwise explicitly forbids TRX from reaching through the same control-flow branch in `TransferActuator`.

### Impact Explanation
The `AllowTvmCompatibleEvm`+version-1 guard exists specifically because legacy (version-1) contracts are not expected to safely receive value transfers outside of `TriggerSmartContract`; forcing all transfers through `TriggerSmartContract` ensures the contract's fallback/payable logic executes correctly. By omitting the same guard in `TransferAssetActuator`, TRC10 asset balances can be pushed into contracts that never anticipated or handle such asset receipts through this bypassed path, which can result in assets becoming unrecoverable/stuck in the contract (permanent freezing of user funds) since there is no way for the contract's un-triggered logic to route or refund the asset.

### Likelihood Explanation
Trivial to trigger: any account owning any TRC10 token balance can broadcast a `TransferAssetContract` transaction targeting a known version-1 smart-contract address; no special privilege, contract deployment, or governance proposal state is required beyond the token balance itself, since the `ForbidTransferToContract`-only check still permits the transfer to succeed against contract accounts when that flag doesn't independently block it.

### Recommendation
Mirror the `AllowTvmCompatibleEvm` + `ContractCapsule.getContractVersion() == 1` check from `TransferActuator.validate()` into `TransferAssetActuator.validate()` so TRC10 transfers to legacy version-1 contracts are rejected the same way TRX transfers are, keeping the two sibling actuators' control-flow consistent.

### Proof of Concept
1. Deploy or identify an existing version-1 (non-EVM-compatible) contract, `deployedContract.getContractVersion() == 1`.
2. Enable `AllowTvmCompatibleEvm` (already enabled on networks where this proposal is active).
3. As any account, broadcast a `TransferContract` sending TRX to that contract address — this fails with "Cannot transfer TRX to a smartContract which version is one."
4. As the same account, broadcast a `TransferAssetContract` sending a TRC10 asset the account owns to the identical contract address — `TransferAssetActuator.validate()` at [3](#0-2)  only checks `ForbidTransferToContract`, so the transaction succeeds and the asset balance is moved into the version-1 contract with no compatible path to retrieve it.
