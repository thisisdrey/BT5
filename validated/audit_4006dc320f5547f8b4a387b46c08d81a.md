## Title
Transient XCM execution failures are misclassified as permanent, causing queued cross-chain messages to be dropped instead of retried - (File: polkadot/xcm/xcm-builder/src/process_xcm_message.rs)

### Summary
The Sherlock report's core broken invariant is: a condition that is actually **recoverable/transient** (a negative-but-valid price) gets funneled through a generic error path that the outer system treats as **permanent**, so a legitimately queued unit of work (an order) is destroyed instead of being retried once conditions normalize. The equivalent invariant in `polkadot-sdk` is how `pallet-message-queue` classifies `ProcessMessageError` variants returned by `T::MessageProcessor::process_message` into "permanent" (drop forever) vs "transient" (retry later, via `Yield`/`Overweight`). `ProcessXcmMessage`, the concrete `MessageProcessor` used to execute HRMP/UMP/bridge XCM messages, collapses *every* non-stack-limit XCM execution error into `ProcessMessageError::Unsupported`, which `pallet-message-queue` always treats as a **permanent** failure. [1](#0-0) 

### Finding Description
`ProcessXcmMessage::process_message` executes the XCM and inspects the `Outcome`: [2](#0-1) 

Any `Outcome::Error` other than `ExceedsStackLimit` is mapped to `ProcessMessageError::Unsupported`:
```
let error = match error {
    xcm::latest::Error::ExceedsStackLimit => ProcessMessageError::StackLimitReached,
    _ => ProcessMessageError::Unsupported,
};
```
This includes execution-time errors such as fee-payment failures (`FeesNotMet`, `NotHoldingFees`), barrier rejections, `TooExpensive`, transient asset-lookup failures, etc. — conditions that are a function of the *current* chain state (balances, exchange rates, other in-flight messages) at the moment of execution, not a structural defect in the message itself.

`pallet-message-queue::process_message_payload` then classifies the returned error: [3](#0-2) 

`Err(Yield)` is the only path treated as `Unprocessable { permanent: false }` (retryable). `BadFormat | Corrupt | Unsupported` are all treated as `Unprocessable { permanent: true }` — i.e., the message is deposited as `ProcessingFailed` and then dropped/skipped permanently: [4](#0-3) 

Because `ProcessXcmMessage` maps essentially all recoverable execution failures to `Unsupported` (the same bucket as truly malformed/incompatible messages), a message that fails only because of a **momentary** condition — e.g., the sender's account does not yet hold enough of the fee asset at the exact block the queue happens to service it, or a transient price/exchange-rate parameter used by a `Barrier`/`BuyExecution` check is briefly unfavorable — is permanently discarded rather than retried, exactly like the GMX order that gets canceled because a temporarily negative price was routed through the "revert" path instead of the recognized recoverable-error path.

This is the direct structural analog of the external bug: **the plumbing that is supposed to separate "should retry" from "must drop" collapses a class of recoverable failures into the "must drop" bucket**, causing legitimate, already-accepted work items (XCM messages carrying asset transfers/`Transact` calls, analogous to open orders) to be irrecoverably canceled.

### Impact Explanation
Dropped XCM messages can carry `WithdrawAsset`/`DepositAsset`/`Transact` instructions that move or unlock funds, register assets, or execute privileged calls forwarded from another chain. If such a message is discarded solely because of a transient condition (e.g., fee assets not yet available, a `Barrier` momentarily failing due to unrelated queue state), the funds/intent encoded in that message are lost or require manual/governance intervention to recover — matching the report's "orders... canceled, leading to losses" impact class, mapped onto message queues / cross-chain dispatch instead of a price oracle.

### Likelihood Explanation
This path is exercised on every HRMP/UMP/bridge XCM message processed through `pallet-message-queue`, which is the default queueing backend across the Polkadot SDK relay/parachain runtimes and Snowbridge inbound/outbound processors that reuse the same permanent/transient classification convention. No malicious peer, validator, collator, or governance actor is required — an ordinary, honestly-submitted XCM message can hit a transient execution error purely due to timing/state at the moment it is serviced, since queue processing is decoupled in time from message submission.

### Recommendation
Distinguish recoverable/transient XCM execution errors (fee/asset availability, barrier/weight-dependent failures) from genuinely permanent ones (malformed encoding, unsupported version/instruction) when mapping `xcm::latest::Error` to `ProcessMessageError` in `ProcessXcmMessage::process_message`. Route the transient category to `ProcessMessageError::Yield` (or a dedicated retry-with-backoff mechanism) instead of `Unsupported`, so `pallet-message-queue` retries the message on a later service pass instead of unconditionally treating it as `Unprocessable { permanent: true }`.

### Proof of Concept
1. Enqueue an XCM message via HRMP/UMP whose only instruction requiring funds is a `BuyExecution`/`DepositAsset` sequence, where the paying account does not yet hold the required fee asset at the block the queue happens to service it (e.g., a race with another pending inbound transfer that would have funded the account one block later).
2. `pallet-message-queue::service_queue` invokes `ProcessXcmMessage::process_message`; `XcmExecutor::execute` returns `Outcome::Error(InstructionError { error: xcm::latest::Error::FeesNotMet, .. })` (or similar).
3. `ProcessXcmMessage` maps this to `ProcessMessageError::Unsupported` (line 118-121 above).
4. `process_message_payload` matches `Unsupported` in the `BadFormat | Corrupt | Unsupported` arm, emits `Event::ProcessingFailed`, and returns `Unprocessable { permanent: true }` (lines 1609-1613).
5. `service_page_item` marks the item `is_processed = true` and calls `page.skip_first(true)`, permanently discarding the message even though, one block later, the account would have had sufficient funds and the exact same message would have executed successfully — the message is never retried.
