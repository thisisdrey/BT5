### Title
Unhardened `ExchangeCapsule.transaction()` allows negative token balances via unprotected subtraction when `allowHardenExchangeCalculation` is disabled - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java)

### Summary
This is a direct analog of the reported issue: an unprotected subtraction that consumes the (possibly erroneous) output of a rate/quantity calculation, with no floor/error check unless a specific hardening flag is active, allowing corrupted state to persist and compound in future trades.

### Finding Description
`ExchangeCapsule.transaction()` computes a `buyTokenQuant` via `Processor.exchange()`, then applies it directly with plain subtraction/addition to update the pool's token balances: [1](#0-0) 

The negative-balance guard is only enforced when `hardenedCalc` is `true`: [2](#0-1) 

When `hardenedCalc` is `false` (i.e., the `allowHardenExchangeCalculation` chain parameter has not been activated by committee proposal), `newFirstTokenBalance`/`newSecondTokenBalance` are computed with plain `long` arithmetic (`firstTokenBalance - buyTokenQuant`, etc.) and stored unconditionally, with no check that the result is non-negative. The `hardenedCalc` flag is threaded from `AbstractExchangeActuator.allowHarden()`, which reads directly from `DynamicPropertiesStore.allowHardenExchangeCalculation()`, a proposal-gated, initially-disabled parameter: [3](#0-2) [4](#0-3) 

`ExchangeProcessor.exchange()` (the non-hardened calculator, still selectable by the default committee configuration) computes `buyTokenQuant` using floating-point `double` math (`Math.pow`) over the bonding-curve supply formula, casting the result to `long`: [5](#0-4) 

Floating-point rounding/edge cases (extreme balance ratios, very small/large `quant`, near-zero `newBalance`, or a computed `supply` drifting negative across repeated trades) can produce a `buyTokenQuant` larger than the available pool balance, or otherwise erroneous. Because the non-hardened path performs the subtraction (`secondTokenBalance - buyTokenQuant`) without any bound check, this can drive `firstTokenBalance`/`secondTokenBalance` negative and this corrupted state is persisted to the `ExchangeStore`/`ExchangeV2Store` via `Commons.putExchangeCapsule(...)`, exactly mirroring the reported bug class where an unchecked subtraction on an unvalidated intermediate value permanently corrupts on-chain state used by all subsequent rate calculations for that market.

### Impact Explanation
Once a pool's `firstTokenBalance`/`secondTokenBalance` become negative or otherwise invalid, every subsequent `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` operation against that exchange ID computes further exchange rates and balances off the corrupted values, perpetuating and potentially amplifying the error (identical failure-propagation pattern to the original report). This can permit an attacker to extract more tokens than the pool legitimately backs (unbacked balance / theft of pooled funds) or permanently freeze/break the exchange (denial of service for that market), since further trades keep operating on inconsistent state.

### Likelihood Explanation
Exploitability depends on whether `allowHardenExchangeCalculation` is active on the target network; if it has not been enabled via committee proposal, the vulnerable, non-hardened `ExchangeProcessor` path (using floating point double math without a negative-balance guard) is the default execution path for `exchangeCreate`/`exchangeInject`/`exchangeWithdraw`/`exchangeTransaction` transactions, all of which are reachable by any unprivileged, signed transaction from an ordinary account holder.

### Recommendation
Apply the negative-balance validation unconditionally in `ExchangeCapsule.transaction()` regardless of `hardenedCalc`, i.e., always throw `ContractValidateException` if `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` after computing pool updates, not only in the hardened branch. Consider deprecating/removing the double-based `ExchangeProcessor` computation path entirely in favor of the `SafeExchangeProcessor` (`BigDecimal`-based) implementation to eliminate floating-point error sources.

### Proof of Concept
Not independently reproduced in this analysis (index-based review only); the vulnerable code path was confirmed by static review of `ExchangeCapsule.transaction()` and `ExchangeProcessor.exchange()`, showing the negative-balance check at line 160 is conditioned on `hardenedCalc`, which is `false` unless the `allowHardenExchangeCalculation` chain parameter proposal has been passed. A concrete numeric PoC (finding input balances/quantities that drive `buyTokenQuant` past pool balance under the double-based `Maths.pow` formula) would require running the code with a fuzzed set of `firstTokenBalance`/`secondTokenBalance`/`sellTokenQuant` combinations, which was not performed here.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
