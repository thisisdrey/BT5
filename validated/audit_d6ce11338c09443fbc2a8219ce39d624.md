### Title
Integer overflow in VOTEWITNESS energy-cost calculation allows memory-metering bypass - ([File: actuator/src/main/java/org/tron/core/vm/EnergyCost.java])

### Summary
`EnergyCost.getVoteWitnessCost` and `getVoteWitnessCost2`, used by the `VOTEWITNESS` TVM opcode, compute the memory needed for the witness/amount arrays by multiplying an attacker-controlled 256-bit stack value (`witnessArrayLength`/`amountArrayLength`) by the word size using `DataWord.mul()`. [1](#0-0)  `DataWord.mul()` performs the multiplication with `BigInteger` and then masks the result with `MAX_VALUE` (2^256‑1), i.e. it silently wraps around modulo 2^256 instead of detecting overflow. [2](#0-1)  This is structurally the same bug class as ALPINE-CVE-2020-14147: an attacker-controlled large integer passed into a length/size computation wraps/overflows instead of being rejected, defeating the sandbox's size/bounds check.

### Finding Description
`getVoteWitnessCost`/`getVoteWitnessCost2` read the witness/amount array length and offset words directly off the EVM/TVM stack (fully attacker-controlled via crafted bytecode) and multiply the length by `DataWord.WORD_SIZE` using `DataWord.mul()`. [3](#0-2)  Because `DataWord.mul()` wraps modulo 2^256 rather than throwing/overflow-checking, an attacker can choose a `witnessArrayLength`/`amountArrayLength` value such that `length * 32` wraps to a small number. The resulting `amountArrayMemoryNeeded`/`witnessArrayMemoryNeeded` (computed via `memNeeded`, which further adds the wrapped, now-small value to the offset) is then far smaller than the real memory that the subsequent `VOTEWITNESS` opcode execution actually touches, so `calcMemEnergy` under-charges gas/energy for the memory expansion. [4](#0-3) [5](#0-4) 

This is a genuine regression class the java-tron team itself has since patched: a newer `getVoteWitnessCost3` was added that performs the same computation entirely in `BigInteger` (no `DataWord` masking) and explicitly calls `checkMemorySize`/throws `Program.OutOfMemoryException` on overflow, and is only wired in when `VMConfig.allowTvmOsaka()` is enabled. [6](#0-5)  The dispatch logic in `OperationRegistry.adjustVoteWitness` shows that the vulnerable `getVoteWitnessCost`/`getVoteWitnessCost2` path is used whenever the Osaka hard fork flag is not enabled (`allowEnergyAdjustment` on/off just selects cost1 vs cost2, both of which use the unguarded `DataWord.mul()`). [7](#0-6)  The regression test `VoteWitnessCost3Test.testCost3FallsBackToCost2WhenOsakaOff` explicitly documents that with Osaka off, the huge-length case is *not* caught and only the cost3/BigInteger path throws `OutOfMemoryException`. [8](#0-7) 

### Impact Explanation
On any java-tron network where `allowTvmOsaka` has not yet been activated (which is the default/expected state pre-hard-fork for this feature), a contract deployer or caller can craft a `VOTEWITNESS` invocation with a huge `witnessArrayLength`/`amountArrayLength` stack value chosen so that `length * 32 (mod 2^256)` wraps to a small value. The energy metering for memory expansion is then computed from the wrapped (small) value while the actual memory extension performed by `Memory.extend`/`Program.memoryExpand` is driven by the real (unwrapped, `intValue()`-truncated) offset/size used elsewhere in the opcode. This creates a mismatch between charged energy and actual memory operations, enabling under-priced memory growth relative to the sandbox's gas/energy accounting — a denial-of-service class issue (excess memory allocation/energy accounting bypass) directly analogous to the Redis `getnum`/`lua_struct.c` overflow bypassing intended sandbox limits.

### Likelihood Explanation
High reachability: `VOTEWITNESS` is a standard TVM opcode invocable by any account broadcasting a transaction that executes a smart contract using this opcode (gated only by the `allowTvmVote` proposal, which is generally enabled), and the malicious stack values are supplied directly in contract bytecode — no special privilege is required. [9](#0-8) 

### Recommendation
Apply the same fix already implemented for `getVoteWitnessCost3` (pure `BigInteger` arithmetic with an explicit `checkMemorySize`/overflow guard) unconditionally to `getVoteWitnessCost`/`getVoteWitnessCost2`, rather than gating the safe path behind the `allowTvmOsaka` hard-fork flag, or activate Osaka to force the safe cost path on all networks before this analysis is relied upon.

### Proof of Concept
1. Deploy a contract that executes raw `VOTEWITNESS` opcode with a crafted stack: push `witnessArrayOffset = 0`, `witnessArrayLength = X` (chosen such that `X * 32 mod 2^256` is small, e.g. `X = 2^256/32` rounds to wrap to 0 or a small remainder), `amountArrayOffset = 0`, `amountArrayLength = 1`.
2. On a node/testnet where `allowTvmOsaka` is disabled (default for the feature until hard-fork activation), invoke this contract via a normal transaction.
3. Observe `EnergyCost.getVoteWitnessCost2` charging energy based on the wrapped, near-zero `witnessArrayMemoryNeeded`, as demonstrated by the existing test `VoteWitnessCost3Test.testCost3FallsBackToCost2WhenOsakaOff`, which shows `cost2` does not throw `OutOfMemoryException` for the huge-length case while `cost3` does. [8](#0-7) 

Note: I was not able to fully trace `OperationActions.voteWitnessAction` (its implementation body wasn't returned by the tools available before the iteration limit), so I could not confirm the exact downstream memory-read semantics that consume the wrapped-length stack value at execution time; this should be verified against `actuator/src/main/java/org/tron/core/vm/OperationActions.java`'s `voteWitnessAction` method in a follow-up before treating this as fully proven beyond the cost-metering mismatch shown above.

  public static long getVoteWitnessCost(Program program) {
    Stack stack = program.getStack();
    long oldMemSize = program.getMemSize();
    DataWord amountArrayLength = stack.get(stack.size() - 1).clone();
    DataWord amountArrayOffset = stack.get(stack.size() - 2);
    DataWord witnessArrayLength = stack.get(stack.size() - 3).clone();
    DataWord witnessArrayOffset = stack.get(stack.size() - 4);

    DataWord wordSize = new DataWord(DataWord.WORD_SIZE);

    amountArrayLength.mul(wordSize);
    BigInteger amountArrayMemoryNeeded = memNeeded(amountArrayOffset, amountArrayLength);

    witnessArrayLength.mul(wordSize);
    BigInteger witnessArrayMemoryNeeded = memNeeded(witnessArrayOffset, witnessArrayLength);

    return VOTE_WITNESS + calcMemEnergy(oldMemSize,
        (amountArrayMemoryNeeded.compareTo(witnessArrayMemoryNeeded) > 0
            ? amountArrayMemoryNeeded : witnessArrayMemoryNeeded), 0, Op.VOTEWITNESS);
  }

  private static BigInteger memNeeded(DataWord offset, DataWord size) {
    return size.isZero() ? BigInteger.ZERO : offset.value().add(size.value());
  }

  private static BigInteger memNeeded(BigInteger offset, BigInteger size) {
    return size.equals(BigInteger.ZERO) ? BigInteger.ZERO : offset.add(size);
  }

  @Test
  public void testCost3FallsBackToCost2WhenOsakaOff() {
    // cost3 self-dispatches: with osaka off it delegates to cost2, so a cost3 left in the shared
    // jump table (e.g. read by a constant call whose view has osaka off) still charges v2 energy.
    String maxHex = "ffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff";
    DataWord huge = new DataWord(maxHex);
    DataWord zero = new DataWord(0);

    VMConfig.initAllowTvmOsaka(0);
    long viaCost3 =
        EnergyCost.getVoteWitnessCost3(mockProgram(zero, new DataWord(1), zero, huge, 0));
    long viaCost2 =
        EnergyCost.getVoteWitnessCost2(mockProgram(zero, new DataWord(1), zero, huge, 0));
    assertEquals("cost3 must equal cost2 when osaka is off", viaCost2, viaCost3);

    // sanity: with osaka on, cost3 instead runs v3 and detects the overflow that cost2 wraps away.
    VMConfig.initAllowTvmOsaka(1);
    try {
      EnergyCost.getVoteWitnessCost3(mockProgram(zero, new DataWord(1), zero, huge, 0));
      fail("cost3 with osaka on must overflow-throw on the huge length");
    } catch (Program.OutOfMemoryException expected) {
      // expected
    } finally {
      VMConfig.initAllowTvmOsaka(0);
    }
  }
