### Title
Truncated Integer Exponent Ratio in Graduated Liquidation Curve Causes Wrong Liquidation Severity - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`calc-liq-factor-exp` approximates the graduated-liquidation curve `factor^(exp/BPS)` by first computing the *integer* division `(/ exp BPS)` and only then exponentiating/dividing, instead of doing the power computation on the true rational exponent. This is the same "division-before-multiplication" rounding-loss pattern flagged in the referenced report (dividing two quantities that should stay as a ratio before they are combined with a subsequent operation, causing the fractional part to be silently discarded to zero).

### Finding Description
`calc-liq-factor-exp` is defined as: [1](#0-0) 

```
(define-private (calc-liq-factor-exp (factor uint) (exp uint))
  (if (is-eq exp BPS) 
    factor
    (if (> exp BPS) 
        (/ (pow factor (/ exp BPS)) (pow BPS (- (/ exp BPS) u1)))
        (sqrti (* factor BPS)))))
```

`exp` and `BPS` are both scaled by `10000`. To raise `factor` to the power `exp/BPS` (e.g. exponent `1.5`), the code needs the exact rational exponent. Instead it computes `(/ exp BPS)` — an **integer** division — before using the result as the exponent in `pow`. For any `exp` value that is not an exact multiple of `BPS` (e.g. `curve-exponent = 15000` meaning `1.5`), `(/ exp BPS)` truncates to `1`, so the whole branch collapses to `(/ (pow factor 1) (pow BPS 0))`, i.e. it silently computes `factor^1` instead of the intended `factor^1.5`. The fractional part of the configured curve exponent is discarded before it is ever used in the power/ratio math — exactly the "divide first, losing precision, then combine" bug class from the external report, just manifesting on the exponent input rather than the multiplicand.

This function feeds directly into the graduated-liquidation parameter calculation: [2](#0-1) 

`calc-liquidation-params` uses `liq-pct-scaled` (the output of the buggy exponentiation) to derive both `liq-penalty` (via `calc-liq-factor-bound`) and `max-debt-usd` (via `calc-liq-debt-repay`), which are then used to size collateral seizure in `process-collateral-asset` / `calc-final-liquidation-amounts`: [3](#0-2) 

Because `factor ≤ BPS` (a fraction ≤ 1), any exponent `> 1` should shrink `factor` (convex curve, less aggressive liquidation at low health-factor breach). The truncated-exponent bug makes the code use exponent `1` for the entire `(BPS, 2*BPS)` exponent-config range, so `liq-pct-scaled` comes out **larger** than the curve designer intended, which in turn makes both the liquidation-penalty and the maximum liquidatable debt percentage larger than intended for any borrower whose LTV sits between the partial- and full-liquidation thresholds.

### Impact Explanation
This is not a DAO-misconfiguration issue: for any legitimately configured non-integer `curve-exponent` (a normal graduated-liquidation parameter, e.g. `1.5x`), the on-chain math permanently computes a different (harsher) liquidation curve than the one the DAO configured, for every liquidation of every affected asset. An ordinary, unprivileged liquidator calling the public liquidation entry point benefits from this miscalculation: they can seize more collateral (with the liquidation bonus baked into `calc-liq-collateral-repay`) than the intended curve allows, at the expense of the liquidated borrower. This is a temporary/permanent freezing and mis-transfer of borrower collateral funds beyond the protocol's intended liquidation-severity design — theft of user (borrower) funds at rest via miscalculated liquidation size, reachable from an ordinary principal's `liquidate` call.

### Likelihood Explanation
The bug triggers deterministically whenever `curve-exponent` is any value strictly between `BPS` and `2*BPS` that is not `BPS` itself (i.e., most "graduated"/superlinear exponent configurations, which is the entire point of the feature), and whenever a borrower's LTV falls in the partial-liquidation band. No attacker-controlled input or oracle manipulation is required — only an ordinary liquidation call against an eligible position, making this a high-likelihood/always-on miscalculation rather than an edge case.

### Recommendation
Do not truncate the exponent ratio via integer division before exponentiating. Either compute the exponent in fixed-point (e.g. scale `pow`/`sqrti` calls to operate on `exp` directly using a fixed-point power function), or restrict `curve-exponent` to only the exact values the integer-power implementation can represent (documented and enforced at config-set time), or implement a proper fixed-point `pow(factor, exp/BPS)` (e.g., via repeated `sqrti`/binary-exponentiation on the fixed-point ratio) so fractional exponents between `1x` and `2x` are computed with their intended fractional precision instead of being rounded down to `1`.

### Proof of Concept
1. DAO configures `curve-exponent = 15000` (`1.5x`) for an asset's graduated liquidation curve, intending `liq-factor = liq-pct-linear^1.5`.
2. A borrower's LTV falls into the partial-liquidation band, giving e.g. `liq-pct-linear = 5000` (50% of BPS).
3. `calc-liq-factor-exp` computes `(/ exp BPS)` = `(/ 15000 10000)` = `1` (integer truncation), so it returns `(/ (pow 5000 1) (pow 10000 0))` = `5000`, instead of the intended `factor^1.5 ≈ 3535` (in the same fixed-point scale).
4. The inflated `liq-pct-scaled = 5000` (instead of `~3535`) is passed to `calc-liq-factor-bound` and `calc-liq-debt-repay`, producing a larger `liq-penalty` and `max-debt-usd` than the DAO's configured curve intended.
5. Any unprivileged liquidator calling the public liquidation entry point on this borrower's position seizes more collateral (with penalty) than the intended curve design allows, for every such liquidation while the mismatched `curve-exponent` is configured.

  (liq-penalty-max uint)
