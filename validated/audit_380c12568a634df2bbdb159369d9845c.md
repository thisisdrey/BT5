### Title
Non-constant-time comparison of the RPC `auth_token` allows remote timing-based secret recovery - (File: `stackslib/src/net/api/blocksimulate.rs`)

### Summary
Several privileged HTTP RPC endpoints in `stackslib/src/net/api/` (`blocksimulate.rs`, `blockreplay.rs`, `txsimulate.rs`, `fastcallreadonly.rs`, and equivalents wired through `postblock_proposal.rs` / `postblock_v3.rs`) gate access by comparing the client-supplied `authorization` header directly against the node's configured `auth_token` using Rust's default `String`/`&str` `PartialEq` (`!=`), which is not constant-time. This is the same bug class as CVE-2017-18239 (authentikat-jwt): a secret-bearing equality check that leaks timing information proportional to the matching-byte-prefix length, letting a remote, unauthenticated attacker recover the secret token byte-by-byte via repeated requests.

### Finding Description
`RPCNakamotoBlockSimulateRequestHandler::try_parse_request` performs the authorization check as: [1](#0-0) 
```
let Some(password) = &self.auth else {
    return Err(Error::Http(400, "Bad Request.".into()));
};
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```
This `!=` on `String`/`&str` uses Rust's slice equality (`str::eq`), which is a byte-by-byte comparison that returns as soon as a mismatch is found (via memcmp-like short-circuiting) — it is not constant-time with respect to the length of the matching prefix. The same pattern (`self.auth`/`password` compared against the `authorization` header) is wired into the RPC dispatch table alongside other auth-gated handlers that share this construction, including `postblock_proposal::RPCBlockProposalRequestHandler` and `postblock_v3::RPCPostBlockRequestHandler`, both of which are registered with `self.auth_token.clone()`: [2](#0-1) 

The `auth_token` config value is explicitly documented as the shared secret between the node and `stacks-signer` used to authorize `/v3/block_proposal` and `/v2/blocks?broadcast=1`: [3](#0-2) 

Because the check is a plaintext value that "must exactly equal" the configured password (per the API docs) and is compared with a non-constant-time operator, an attacker who can send many HTTP requests to a node's RPC endpoint (no other credentials or privileged role needed) can measure response-time differences to infer how many leading bytes of their guessed token match the real secret, and iteratively brute-force the full `auth_token` — exactly analogous to the JWT signature-guessing attack in the reported advisory. Once obtained, the attacker fully impersonates the trusted `stacks-signer` and can submit forged block proposals / broadcast blocks to the privileged `/v3/block_proposal` and `/v2/blocks?broadcast=1` endpoints, i.e., unauthenticated/unauthorized write access to privileged node state — reaching the "auth bypass" impact category.

### Impact Explanation
Successful recovery of `auth_token` gives a remote, unprivileged attacker the ability to bypass the auth gate protecting `/v3/block_proposal` (block validation requests) and `/v2/blocks?broadcast=1`, effectively achieving unauthorized write/administrative access without ever holding the node's secret or another party's key beforehand (the secret itself is what's being attacked). This matches the Critical impact bucket for "unauthenticated/unauthorized write to state" and "auth bypass."

### Likelihood Explanation
Exploitation requires purely network-level access to the RPC endpoint and a moderate/large number of requests with statistical timing analysis; no cryptographic secret, node access, or privileged role is needed a priori. Real-world exploitation of remote timing side channels of this kind is nontrivial due to network jitter but has been demonstrated to be practical (this is literally the underlying vulnerability class of the cited CVE), especially over LAN/low-jitter links between a node and its configured signer, or against nodes reachable with low latency. Likelihood is assessed as moderate-to-high given repeated, unauthenticated attempts are possible with no rate limiting evident in the shown code path.

### Recommendation
Replace the plaintext `!=`/`==` comparison of `auth_header` against `password`/`auth_token` in `blocksimulate.rs`, `blockreplay.rs`, `txsimulate.rs`, `fastcallreadonly.rs`, `postblock_proposal.rs`, and `postblock_v3.rs` with a constant-time comparison (e.g., using the `subtle` crate's `ConstantTimeEq`/`ct_eq`, or comparing fixed-length HMAC digests of the token instead of the raw token) so that comparison time is independent of the position of the first differing byte. Additionally consider hashing both sides (e.g., SHA-256) before constant-time comparison to further reduce any residual signal, and add basic rate-limiting/lockout on repeated auth failures for these endpoints.

### Proof of Concept
1. Configure a stacks-node with `connection_options.auth_token = "<secret>"`.
2. Send repeated HTTP requests to `POST /v3/blocks/simulate/<block_id>` (or `/v3/block_proposal`) with an `authorization` header containing a guessed prefix followed by all possible next bytes, e.g. incrementally build the guess `g0, g0g1, g0g1g2, ...`.
3. Measure round-trip time for each candidate; because the header comparison in `try_parse_request` (`stackslib/src/net/api/blocksimulate.rs:159`) short-circuits on the first mismatched byte, correct-prefix guesses take measurably longer to fail than incorrect first-byte guesses.
4. Repeat this per-byte oracle until the full `auth_token` is reconstructed, then use it to submit a forged request to `/v3/block_proposal` or broadcast a block via `/v2/blocks?broadcast=1`.
