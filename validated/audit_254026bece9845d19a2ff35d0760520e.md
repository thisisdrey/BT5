### Title
Missing zero-weight guard causes `ArithmeticException` in `RepositoryImpl.calculateGlobalEnergyLimit`, crashing TVM contract execution - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit(AccountCapsule)`, the TVM-side energy-limit calculator used during every smart-contract call, divides by `totalEnergyWeight` with only a Java `assert` as a guard, and Java assertions are disabled by default in production JVMs. If `totalEnergyWeight` is `0`, the hardened calculation path performs `BigInteger.divide(BigInteger.ZERO)`, throwing an uncaught `ArithmeticException`, analogous to the libtiff divide-by-zero crash in ALPINE-CVE-2022-2057.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit` computes the energy limit for an account based on its frozen-for-energy balance and the network-wide `totalEnergyWeight`: [1](#0-0) 

Note that the only zero-check is `assert totalEnergyWeight > 0;` at line 1001. Unlike the sibling implementation `EnergyProcessor.calculateGlobalEnergyLimit`, which explicitly returns `0` when `totalEnergyWeight <= 0`: [2](#0-1) 

`RepositoryImpl` (the repository object actually wired into TVM execution via `ContractState`, which simply forwards `calculateGlobalEnergyLimit` to the underlying `Repository`) has no such guard: [3](#0-2) 

Because Java `assert` statements are stripped/no-op unless the JVM is started with `-ea` (not the default for production `java-tron` node launches), the `assert totalEnergyWeight > 0;` provides no actual protection at runtime. If `totalEnergyWeight` is `0` and hardened resource calculation is enabled (`VMConfig.allowHardenResourceCalculation()`), the code executes `BigInteger.valueOf(energyWeight).multiply(...).divide(BigInteger.valueOf(0))`, which throws `java.lang.ArithmeticException: BigInteger divide by zero`. This mirrors the CVE-2022-2057 root cause pattern: an unchecked/ineffective guard before a division whose denominator can become zero, causing a crash instead of the intended computation.

### Impact Explanation
An uncaught `ArithmeticException` thrown deep inside TVM/repository code during contract execution (triggered by any ordinary `TriggerSmartContract` transaction that consumes energy) is not part of the normal `ContractValidateException`/`ContractExeException`/VM-`OutOfEnergyException` handling paths that the actuator framework expects. If it propagates out of the block-application path in `Manager`/`VMActuator` rather than being converted into a controlled TVM revert, it can abort processing of the transaction/block, denying service to legitimate contract calls that rely on `calculateGlobalEnergyLimit` for energy accounting — a concrete node crash/halt scenario relevant to unprivileged callers, matching the "Medium" DoS severity class of the referenced CVE.

### Likelihood Explanation
Exploitability hinges on `totalEnergyWeight` reaching `0`, which is a chain/global state value (aggregate of all frozen-for-energy weight across the network) rather than something a single transaction can set directly under `allowUnfreezeDelay`/current mainnet conditions where SRs and large freezers maintain nonzero weight. This makes the condition harder to trigger on established mainnet, but is plausible on freshly bootstrapped networks, private/test chains, or in edge-case scenarios where all frozen-for-energy balance is unfrozen (a state the codebase itself anticipates, since `EnergyProcessor` and `calculateGlobalEnergyLimitV2` both explicitly guard against it) before `RepositoryImpl`'s guard was omitted. I could not fully verify within this pass whether any additional invariant elsewhere in the codebase guarantees `totalEnergyWeight > 0` at all call sites of `RepositoryImpl.calculateGlobalEnergyLimit` during contract execution (e.g., `VMActuator`, `Program`/energy-check call sites) — this would require further tracing of the TVM energy-accounting entry point.

### Recommendation
Replace the ineffective `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit` with an explicit runtime check (mirroring `EnergyProcessor`/`calculateGlobalEnergyLimitV2`) that returns `0` (or another safe default) when `totalEnergyWeight <= 0`, before entering either the `BigInteger` or `double` division branches.

### Proof of Concept
1. Reach chain state where `dynamicPropertiesStore.getTotalEnergyWeight()` returns `0` (e.g., a private/test network at genesis before any energy freezes, or after all frozen-for-energy balances are fully unfrozen) with `VMConfig.allowHardenResourceCalculation()` enabled.
2. Any unprivileged account with `frozeBalance >= TRX_PRECISION` (frozen-for-energy balance) broadcasts a `TriggerSmartContract` transaction.
3. During execution, the TVM energy path calls `Repository.calculateGlobalEnergyLimit(accountCapsule)` (forwarded through `ContractState` to `RepositoryImpl`), reaching:
`actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java:1003-1007` — `BigInteger.valueOf(totalEnergyWeight)` is `BigInteger.ZERO`, so `.divide(BigInteger.valueOf(totalEnergyWeight))` throws `ArithmeticException: BigInteger divide by zero`. [4](#0-3)

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
