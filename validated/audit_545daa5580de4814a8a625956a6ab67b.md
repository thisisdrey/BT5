### Title
Remote panic via `assert!(mblock_len <= MAX_PAYLOAD_LEN as usize)` in `make_microblocksdata_messages` due to `MicroblocksData::consensus_deserialize` bounding by `MAX_MESSAGE_LEN` instead of `MAX_PAYLOAD_LEN` - (File: stackslib/src/net/relay.rs)

### Summary
`MicroblocksData::consensus_deserialize` deliberately uses a "loose upper-bound" `BoundReader::from_reader(fd, MAX_MESSAGE_LEN as u64)` when parsing the `microblocks` vector, rather than bounding each microblock (or the whole payload) by `MAX_PAYLOAD_LEN`. `make_microblocksdata_messages` later assumes, via a hard `assert!`, that every microblock it re-serializes is `<= MAX_PAYLOAD_LEN`, with the comment claiming this must hold because otherwise the message could not have been parsed. That assumption is false given the deserializer's actual bound.

### Finding Description
The claimed invariant is: bound enforced at deserialization time (`MAX_MESSAGE_LEN`) == bound assumed at the assert site (`MAX_PAYLOAD_LEN`). Inspecting the code shows these are two distinct constants and the deserializer explicitly uses the larger one: [1](#0-0) 

```
fn consensus_deserialize<R: Read>(fd: &mut R) -> Result<MicroblocksData, codec_error> {
    let index_anchor_block = read_next(fd)?;
    let microblocks: Vec<StacksMicroblock> = {
        // loose upper-bound
        let mut bound_read = BoundReader::from_reader(fd, MAX_MESSAGE_LEN as u64);
        read_next(&mut bound_read)
    }?;
    ...
```

This is bounded by `MAX_MESSAGE_LEN`, not `MAX_PAYLOAD_LEN`, and there is no additional per-microblock or per-vector cap against `MAX_PAYLOAD_LEN` inside this path. Meanwhile, `make_microblocksdata_messages` re-serializes each microblock pulled from the map and asserts the opposite bound: [2](#0-1) 

The remote-reachable path into this function is `preprocess_pushed_microblocks`, which is fed directly from `network_result.pushed_microblocks` — data deserialized off the wire from an unauthenticated peer push — and stores each microblock into the `new_microblocks` map before calling `Relayer::make_microblocksdata_messages(new_microblocks)`: [3](#0-2) [4](#0-3) 

The comment at relay.rs:1130 explicitly rests on the false assumption that the parser already enforces `MAX_PAYLOAD_LEN`, but the parser (codec.rs:546-558) only enforces the larger `MAX_MESSAGE_LEN`. Since a microblock passes through `chainstate.preprocess_streamed_microblock` before being inserted into `new_microblocks`, the actual exploitability depends on whether that chainstate-level validation independently re-checks total serialized length against `MAX_PAYLOAD_LEN`; I was not able to inspect `preprocess_streamed_microblock`'s internals within the available tool budget to confirm or rule out such a check, so this is an open verification gap.

### Impact Explanation
If a microblock whose serialized length falls between `MAX_PAYLOAD_LEN` and `MAX_MESSAGE_LEN` survives `chainstate.preprocess_streamed_microblock` unmodified, then `make_microblocksdata_messages` will panic on the `assert!` at relay.rs:1130, crashing the relay thread/process. This would be a remotely-triggerable, unauthenticated crash from a single crafted push message — matching the Critical DoS category — repeatable against any node that accepts pushed microblocks.

### Likelihood Explanation
The precondition is that a remote, unauthenticated peer can push a `MicroblocksData` message containing a microblock in the size gap between `MAX_PAYLOAD_LEN` and `MAX_MESSAGE_LEN`, and that this microblock passes `preprocess_streamed_microblock`'s validation (structural/signature checks) without being rejected for size. The size of that gap and whether `preprocess_streamed_microblock` enforces `MAX_PAYLOAD_LEN` independently are the two facts that determine real-world exploitability, and I could not fully verify either within the tool budget available. The mismatched bound in `consensus_deserialize` is a confirmed code fact; whether it is independently guarded downstream is unconfirmed.

### Recommendation
Enforce `MAX_PAYLOAD_LEN` (not `MAX_MESSAGE_LEN`) as the bound in `MicroblocksData::consensus_deserialize`'s `BoundReader`, and/or replace the `assert!` in `make_microblocksdata_messages` with a graceful rejection/skip-and-log path so that even if an oversized microblock somehow reaches this function, it cannot cause a process-wide panic.

### Proof of Concept
Rust test plan (net test):
1. Construct a `StacksMicroblock` whose `consensus_serialize` output length is between `MAX_PAYLOAD_LEN` and `MAX_MESSAGE_LEN` (e.g., by padding transactions in `txs`).
2. Serialize a `MicroblocksData { index_anchor_block, microblocks: vec![oversized_mblock] }` and deserialize it via `MicroblocksData::consensus_deserialize`, confirming it succeeds (i.e., the `MAX_MESSAGE_LEN` bound admits it).
3. Feed the resulting microblock into a `HashMap` matching `make_microblocksdata_messages`'s input shape and call `Relayer::make_microblocksdata_messages`, asserting the process panics at `relay.rs:1130`.
4. Separately, to fully confirm remote reachability, trace/instrument `StacksChainState::preprocess_streamed_microblock` to verify it does not itself reject microblocks exceeding `MAX_PAYLOAD_LEN` before they reach `new_microblocks` — this step remains unverified in this audit and should be completed before treating the finding as fully proven end-to-end.
