The pnpm advisory concerns deriving an unsafe filename directly from attacker-controlled manifest `name`/`version` fields without validating for path traversal. The closest analog in this Go repository is the module cache download path in `src/cmd/go/internal/modfetch/fetch.go` (`unzip`, `Fetcher.Unzip`) and `src/cmd/go/internal/modfetch/cache.go` (`DownloadDir`, `CachePath`), but this path is explicitly guarded: [1](#0-0) , which calls `module.EscapePath`, `gover.ModIsValid`, and `module.CanonicalVersion` before ever constructing a filesystem path from the module path/version — precisely the class of check that pnpm was missing.

Additionally, the zip contents themselves are double-checked against a `path@version/` prefix before extraction: [2](#0-1) , and there are dedicated regression tests (`mod_bad_filenames.txt`, `mod_load_badzip.txt`) confirming malformed/escaping paths inside module zips are rejected rather than written outside the destination. The actual per-file extraction logic (`golang.org/x/mod/zip.Unzip`) that does the final path-join and write is not part of this repository's tracked source (it's an external module dependency), so its internals cannot be verified from files in scope, and no root cause can be established here.

Given the existing validation (`EscapePath`/`CanonicalVersion`/prefix check) at the reachable Go entry points, and the inability to inspect the actual extraction sink within this repo's scope, there is no reproducible analog to the pnpm CVE-2026-55700 primitive in this codebase.
