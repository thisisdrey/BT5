### Title
Exchange pool funds can become permanently frozen once either token side balance reaches exactly 0 - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeCreateActuator`/`ExchangeTransactionActuator` create and drive an on-chain AMM-style bancor pool (`ExchangeCapsule`). Both `ExchangeInjectActuator` and `ExchangeWithdrawActuator` unconditionally reject any operation on a pool whenever either side's token balance equals exactly `0`, treating the exchange as permanently "closed." Because the only two actuators that can change the pool's balances back to a workable state (`ExchangeInjectActuator` to top up, `ExchangeWithdrawActuator` to unwind) are gated by this same `== 0` check, once a legitimate/anonymous trading sequence via `ExchangeTransactionActuator` drives one side's balance down to exactly zero, the pool's creator can never withdraw the remaining (non-zero) balance of the other token, and nobody can re-inject liquidity to revive it. This is structurally the same bug class as the reported Rio issue: a zero-value invariant check on a *shared, pool-level* counter that blocks the only code paths capable of freeing/utilizing the pooled funds, even though those funds are real and otherwise recoverable.

### Finding Description
`ExchangeWithdrawActuator.doValidate()` throws if either balance is zero: [1](#0-0) 

The identical check exists in `ExchangeInjectActuator` and `ExchangeTransactionActuator`, meaning once one side is zero, none of the three actuators that touch `ExchangeCapsule` balances can succeed: [2](#0-1) 

`ExchangeTransactionActuator` is reachable by any signed transaction and drives the pool via the bancor-style `Processor.exchange()` math implemented in `ExchangeProcessor`/`SafeExchangeProcessor`: [3](#0-2) 

The pow-based bancor formula asymptotically approaches, but is not mathematically guaranteed to avoid, an exact-zero outcome once long/double truncation and integer rounding via `(long)` casts (`ExchangeProcessor`) or `setScale(0, RoundingMode.DOWN)` (`SafeExchangeProcessor`) are applied to real balances that can be small. A sell large enough relative to remaining balance, or repeated small trades exploiting rounding-down of `buyTokenQuant`, can plausibly drive a token side balance to exactly `0` (or the code already treats `<= 0` conditions as invalid entry but does not prevent the *resulting* balance from landing on exactly `0` after a valid trade, since only negative results are guarded): [4](#0-3) 

Once that happens, the creator's only recovery path — `ExchangeWithdrawActuator` — is itself gated by the same zero check, so the remaining, non-zero balance of the other token becomes permanently unreachable by any actuator.

### Impact Explanation
This causes permanent freezing of funds belonging to the exchange creator (and effectively the remaining locked TRX/TRC10 asset value in the pool), since there is no actuator or path in `Wallet`/`TronJsonRpcImpl` that allows withdrawing from or resetting a pool once one side balance is `0`. This satisfies the "permanent freezing of funds" acceptance bar for a Medium/High-severity finding, analogous to the Rio report's "funds become unusable due to an over-restrictive zero-check on a pooled value."

### Likelihood Explanation
Reaching this state requires either (a) a legitimate but carefully crafted large trade against a low-liquidity pool, or (b) repeated small trades exploiting the floor-rounding division in `exchangeFromSupply`, both of which are reachable by any unprivileged account issuing `ExchangeTransactionContract` transactions — no special privileges are required. However, I was not able to fully verify through static analysis alone whether the specific floating-point/BigDecimal arithmetic in `ExchangeProcessor`/`SafeExchangeProcessor` can produce an output that exactly equals the full remaining balance (as opposed to asymptotically approaching but never fully draining it) without running a numeric simulation; this is the main source of uncertainty in confirming actual exploitability versus a purely theoretical concern.

### Recommendation
Change `ExchangeWithdrawActuator` (and ideally `ExchangeInjectActuator`) to allow recovery when a balance is zero — e.g., permit the creator to withdraw the remaining single-sided balance directly rather than always requiring both sides nonzero, or add a dedicated "close/rescue" path for a degenerate pool. At minimum, ensure `ExchangeTransactionActuator` cannot produce a resulting balance of exactly zero on either side (require the post-trade balance to remain `> 0` with a safety margin) so the pool can never enter the unrecoverable state in the first place.

### Proof of Concept
1. Creator calls `ExchangeCreateActuator` to create a pool with tokens A/B and initial balances `firstTokenBalance = X`, `secondTokenBalance = Y`.
2. An unprivileged trader repeatedly (or with a single large trade) calls `ExchangeTransactionActuator` selling token A, driving `secondTokenBalance` (token B side) down to exactly `0` via the bancor curve in `ExchangeCapsule.transaction()`.
3. Creator calls `ExchangeWithdrawActuator` to reclaim the remaining `firstTokenBalance` (token A) still sitting in the pool.
4. `doValidate()` hits `if (firstTokenBalance == 0 || secondTokenBalance == 0)` and throws `ContractValidateException("Token balance in exchange is equal with 0, the exchange has been closed")`, permanently blocking withdrawal of the remaining token A balance. [5](#0-4)

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
