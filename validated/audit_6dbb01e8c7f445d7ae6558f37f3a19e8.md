### Title
Wallet Contract state has no storage-layout versioning while all legacy ETH-implicit accounts are forcibly upgraded to the current binary - ([File: runtime/runtime/src/contract_code.rs])

### Summary
`near-wallet-contract`'s `WalletContract` persisted state struct is a plain, unversioned Borsh struct, unlike `Account`, which correctly uses a versioned enum (`InitializedAccount::{V1,V2}`) for its on-trie layout. The runtime unconditionally redirects *any* ETH-implicit account whose code hash matches *any* known legacy wallet-contract variant (`MAINNET`, `TESTNET`, `OLD_TESTNET`, `LOCALNET`) to execute using the single *current* global wallet contract binary for that chain, regardless of which historical binary actually wrote that account's persisted state. This is the direct analog of the Mento `LockingBase` bug: new fields can be added to an on-chain-state struct across upgrades without any mechanism ensuring old persisted bytes are compatible with the new layout.

### Finding Description
`WalletContract` is defined as a bare Borsh struct with no version wrapper: [1](#0-0) 

Contrast this with `core/primitives-core/src/account.rs`, where `Account` is explicitly documented to require adding a new versioned variant (`AccountV[NewVersion]`) whenever the storage layout changes: [2](#0-1) 

For ETH-implicit accounts, `near-wallet-contract/src/lib.rs` tracks four *different* legacy WASM variants that have been deployed over time (`MAINNET`, `TESTNET`, `OLD_TESTNET`, `LOCALNET`), explicitly noting that `OLD_TESTNET` "had a bug in its implementation" and was replaced: [3](#0-2) 

Despite tracking these as distinct binaries, `code_hash_matches_wallet_contract` intentionally treats accounts whose code hash matches *any* legacy variant as eligible to run the *current* wallet contract code for that chain: [4](#0-3) 

This routing decision is enforced at execution time in `RuntimeContractIdentifier::resolve`, which detects any legacy ETH-implicit wallet code hash and forcibly substitutes the *current* global contract hash for execution, irrespective of which binary actually created and last wrote the account's persisted contract state: [5](#0-4) 

Because `WalletContract` has no version enum or explicit migration step, if the current binary's struct (`nonce: u64, has_in_flight_tx: bool`) ever gains, loses, or reorders fields relative to an older deployed variant (exactly the kind of change implied by the `OLD_TESTNET` "bug fix" comment), Borsh deserialization of an old account's stored bytes under the new struct layout will either misinterpret field boundaries (corrupting `nonce`/`has_in_flight_tx`) or fail outright. This is structurally identical to the Mento issue: a persisted-state struct is extended across upgrades without any slot/field accounting to keep old instances' storage compatible with the new binary that will be forced to read it.

### Impact Explanation
- If deserialization misreads bytes rather than failing, the `nonce` field used to prevent Ethereum-transaction replay (`rlp_execute`) could be corrupted to a stale or attacker-influenceable value, enabling replay of an already-executed relayed transaction (double-spend of the account's funds).
- If `has_in_flight_tx` is corrupted, the reentrancy-guard invariant documented on the struct ("must be `true` when a mutable method... returns a promise") could be violated, allowing overlapping executions of the wallet contract's promise-based transfer/call logic — a path to duplicate token/fund movement.
- If deserialization fails outright, every call to the account (which can only be operated through this contract, since ETH-implicit accounts "cannot be deleted, nor can a full access key be added") would permanently revert, resulting in permanent freezing of the account's NEAR balance.

### Likelihood Explanation
The forced-upgrade routing in `RuntimeContractIdentifier::resolve` is unconditional and applies today to real, already-existing legacy accounts (the `OLD_TESTNET` variant is explicitly still recognized and remapped). The risk materializes any time the `WalletContract` struct's fields change between the version that created an account's persisted state and the "current" version the runtime forces it to run under — a change class the maintainers have already made once (per the `OLD_TESTNET` "bug" comment) and could make again with no compile-time or protocol-level safeguard preventing it, since there is no versioned wrapper analogous to `Account`.

### Recommendation
Wrap `WalletContract`'s persisted state in a versioned enum (mirroring `Account`'s `V1`/`V2` pattern) so old field layouts can be explicitly migrated/interpreted on read, and add either (a) a migration step executed the first time an upgraded binary loads state written by an older wallet-contract variant, or (b) an explicit reserved/gap field policy so future field additions cannot silently shift the byte layout of already-deployed accounts’ state.

### Proof of Concept
1. Deploy `OLD_TESTNET`'s wallet-contract WASM as a legacy local-code ETH-implicit account (as already exists on testnet, e.g. `0xcc5a584f545b2ca3ebacc1346556d1f5b82b8fc6`).
2. Have that account execute `rlp_execute` so its persisted `WalletContract` state (nonce/has_in_flight_tx) is written using `OLD_TESTNET`'s struct layout.
3. Because `RuntimeContractIdentifier::resolve` (`runtime/runtime/src/contract_code.rs:58-66`) always substitutes the *current* `TESTNET` global contract hash for any recognized legacy wallet code hash, all subsequent calls to this account execute using the current `TESTNET` binary's `WalletContract::deserialize` on bytes written by the old binary.
4. If the current struct's field set/order differs from `OLD_TESTNET`'s (as implied by the documented bug fix), deserialization either misreads `nonce`/`has_in_flight_tx` or errors, demonstrating the corrupted-state/frozen-funds outcome described above.

/// Checks if the given code hash corresponds to the wallet contract (signalling
/// the runtime should treat the wallet contract as the code for the account).
pub fn code_hash_matches_wallet_contract(chain_id: &str, code_hash: &CryptoHash) -> bool {
    let magic_bytes = wallet_contract_magic_bytes(&chain_id);

    if code_hash == magic_bytes.hash() {
        return true;
    }

    // Extra check needed for an old version of the wallet contract
    // that was on testnet. Accounts with that hash are still intentionally
    // made to run the current version of the wallet contract because
    // the previous version had a bug in its implementation.
    if chain_id == chains::TESTNET {
        let alt_testnet_code = OLD_TESTNET.magic_bytes();
        return code_hash == alt_testnet_code.hash();
    }

    false
}
