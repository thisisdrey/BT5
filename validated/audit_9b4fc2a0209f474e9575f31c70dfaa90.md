### Title
Uncontrolled memory allocation from attacker-controlled ABI array length in precompiled-contract calldata decoding - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The precompiled-contract calldata decoders `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` read a 32-byte "array length" word directly from attacker-supplied `data` and immediately use it to allocate a Java array (`new byte[len][]`) *before* validating that `len` is consistent with the actual size of the supplied calldata. [1](#0-0) 

This is the same root-cause pattern as the reported eth-abi ZST DoS: a parser trusts a compact, attacker-controlled length field and performs an allocation proportional to that field's value rather than to the actual bytes present in the payload, letting a tiny transaction request an enormous in-memory structure.

### Finding Description
`extractBytes32Array` takes the length purely from `words[offset].intValueSafe()` and allocates `new byte[len][]` with **no bound check at all** relative to `words.length`:
```java
private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
  int len = words[offset].intValueSafe();
  byte[][] bytes32Array = new byte[len][];
  ...
}
``` [2](#0-1) 

`extractBytesArray` and `extractSigArray` only guard the *offset* (`offset > words.length - 1`) but not `len` itself, so `len` can still be set to an attacker-chosen huge value while `offset` remains in range, causing an oversized allocation before any element is actually validated against the payload:
```java
private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
  if (offset > words.length - 1) {
    return new byte[0][];
  }
  int len = words[offset].intValueSafe();
  byte[][] bytesArray = new byte[len][];
  ...
}
``` [3](#0-2) [4](#0-3) 

`DataWord.intValueSafe()` clamps the value into the `int` range, meaning `len` can be as large as `Integer.MAX_VALUE` (~2.1 billion). `new byte[Integer.MAX_VALUE][]` (or any large fraction of it) allocates that many array-reference slots (8 bytes each on a 64-bit JVM, i.e. multi-gigabyte allocation) immediately, purely from a single 32-byte word in the calldata, with no relationship to how much actual data was sent in the transaction — exactly analogous to declaring a huge-length array of zero-sized elements in the ABI-decoder DoS report, where the declared count drives allocation independent of on-wire payload size.

The utility function `isValidAbiEncoding` exists elsewhere in the same file to sanity-check that a payload's length is consistent with a claimed header/item word count, but it is not applied before these three array-length reads, so the guard that would prevent this class of bug is present in the codebase but not used at this call site. [5](#0-4) 

### Impact Explanation
These helpers decode calldata for precompiled contracts reachable from ordinary smart-contract calls (e.g. multi-sig validation / batch signature verification precompiles addressed by any deployed contract via `CALL`/`STATICCALL`). Because the length used for allocation is taken straight from attacker-controlled calldata before any correlation with actual payload size, a single transaction with a crafted small calldata blob can force the node to attempt a very large heap allocation while executing that transaction. This can throw `OutOfMemoryError` or otherwise stall/crash the node process executing the transaction, which is a node-crash / denial-of-service impact reachable by any unprivileged contract caller.

### Likelihood Explanation
Likelihood is high for triggering an exception/crash attempt: the attacker only needs to control the calldata sent to a contract that invokes the vulnerable precompile, set the corresponding "array length" word to a large value (e.g. close to `Integer.MAX_VALUE`), and does not need any special permission, stake, or witness/SR role — any account able to submit a transaction that triggers a `CALL` into the precompile is sufficient.

### Recommendation
Before allocating `new byte[len][]` (or similar) in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate `len` against the actual remaining size of `words`/`data` (analogous to the existing but unused `isValidAbiEncoding` check), and reject/return an empty result (or throw a bounded exception) when the declared length is inconsistent with, or grossly exceeds, the bytes actually supplied in the transaction's calldata.

### Proof of Concept
Construct calldata for a precompile that internally calls one of the vulnerable extractors (e.g. the signature-array or bytes32-array parameter of a multi-sig / batch-signature precompile) where the 32-byte word at the expected "array length" offset is set to a large value such as `0x000000000000000000000000000000000000000000000000000000FFFFFFFF`, while the actual calldata otherwise remains short. Submitting a contract call whose input reaches this precompile with that crafted word causes `extractBytesArray`/`extractSigArray`/`extractBytes32Array` to execute `new byte[len][]` with `len` far larger than the number of elements actually encoded, forcing an oversized allocation attempt purely from a small calldata payload.
