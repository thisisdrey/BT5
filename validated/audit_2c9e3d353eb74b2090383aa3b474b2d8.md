### Title
Dust-transfer griefing of `MAX_TOKENS_PER_USER` permanently blocks victim deposits, borrows and leverage - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` enforces a hard cap of 30 on the combined length of `debtTokensOfAccount` + `depositTokensOfAccount` per account via `onlyIfAdditionWillNotReachMaxTokens`. Because `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to >0, any EOA can force-add deposit tokens to an arbitrary victim's list by transferring 1 wei of each `msdTOKEN`. Once the victim's list reaches `MAX_TOKENS_PER_USER`, every subsequent action that would add a new token to their list reverts with `UserReachedMaxTokens` — including `DebtToken.issue`/`mint` (borrow), `DepositToken.deposit`/`_mint` of a collateral type they don't already hold, and SmartFarmingManager leverage flows that mint new deposit or debt tokens to them. The attacker can re-fill the list every time the victim clears a slot, sustaining the denial of service indefinitely for negligible cost.

### Finding Description
- `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30` (Pool.sol:143-148, 216-220). The only authorization is that `msg.sender` is a registered deposit token — the *recipient* never consents.
- `DepositToken._transfer` adds the token to the recipient's list whenever their prior balance is 0 and `amount_ > 0` (DepositToken.sol:517-520). `transfer`/`transferFrom` only require the *sender's* balance to be unlocked (`_revertIfLocked` checks `_msgSender`/`sender_`, DepositToken.sol:348-373), so an attacker who deposits collateral can freely push dust to any victim.
- Symmetrically, `DebtToken` minting (`issue`, called by `Pool.mint`/`SmartFarmingManager`) calls `pool.addToDebtTokensOfAccount`, so once the combined list is full, `DebtToken._mint` reverts and borrowing is impossible.
- `_mint` in `DepositToken` also adds to the recipient's list (DepositToken.sol:485-488), so `deposit(amount, victim)` and leverage mints to the victim revert as well.
- Removal only happens when a balance returns to zero, and removal requires the victim to actively spend gas transferring each dust token back — after which the attacker can immediately refill the slot.

### Impact Explanation
Liveness break / freezing of position functionality: the victim is permanently (or repeatedly, at the attacker's cost of ~1 wei per token + gas) unable to open new collateral positions, receive msdTOKEN transfers, or mint any new synthetic debt in that pool. If the victim relies on borrowing additional synthetics or topping up with a *new* collateral type to restore health before liquidation, the griefing prevents remediation and forces liquidation/bad debt. The DoS needs no privileged role, no oracle manipulation, and only public `deposit`/`transfer` entry points.

### Likelihood Explanation
An attacker needs only to deposit a minimal amount in each registered deposit token once (or receive dust), then `transfer(victim, 1)` on up to 30 distinct `msdTOKEN`s. Every call is permissionless; `SynthContext`/`onlyIfAdditionWillNotReachMaxTokens`/`nonReentrant` provide no defense since the check is the vulnerability. The victim cannot preemptively block receipt — there is no opt-in for being added to `depositTokensOfAccount`.

### Recommendation
Decouple the accounting list from forced adds: e.g., only register tokens on protocol-mediated paths (`deposit`, `_mint`) where the recipient calls or approves the action, or make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` idempotent without reverting and bound iteration cost instead of a hard revert, or let users maintain an explicit allowlist / pull-based claim for msdTOKENs.

### Proof of Concept
Reproducible in Hardhat using the repo's existing test scaffolding (pattern shown in `test/Pool.test.ts` `addToDepositTokensOfAccount`):

```ts
// Attacker deposits 1 wei of each deposit token for themselves
for (const dt of depositTokens /* up to 30 registered DepositTokens */) {
  await underlying.mint(attacker.address, 1)
  await underlying.connect(attacker).approve(dt.address, 1)
  await dt.connect(attacker).deposit(1, attacker.address)
  // push dust to victim: _transfer -> addToDepositTokensOfAccount(victim)
  await dt.connect(attacker).transfer(victim.address, 1)
}
// victim's depositTokensOfAccount.length == number of pool deposit tokens;
// with the victim's existing tokens the combined count hits MAX_TOKENS_PER_USER = 30

// Victim can no longer borrow any synthetic (DebtToken.issue -> _mint ->
// addToDebtTokensOfAccount reverts UserReachedMaxTokens)
await expect(pool.connect(victim).mint(msUSD.address, 1))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// Victim cannot deposit a collateral type they don't already hold
await expect(newDepositToken.connect(victim).deposit(1e18, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// Clearing one slot then attacker re-fills it in the same block
await depositTokens[0].connect(victim).transfer(attacker.address, 1)
await depositTokens[0].connect(attacker).transfer(victim.address, 1) // re-grief
```

The invariant broken is liveness of `mint`/`deposit` for a targeted account — the analog of CVE-2021-2166's unprivileged, cheap, repeatable denial-of-service crash.
