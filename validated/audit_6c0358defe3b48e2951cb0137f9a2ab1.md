### Title
Deposit-token dust stuffing of the `feeCollector` account list makes `Pool.liquidate` revert for any collateral the fee collector has not yet received - (File: contracts/DepositToken.sol)

### Summary
`Pool` tracks a per-account set of deposit/debt tokens capped at `MAX_TOKENS_PER_USER = 30` [1](#0-0) . Every `DepositToken` transfer unconditionally registers the recipient in `depositTokensOfAccount` when their prior balance is zero [2](#0-1) , and `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once the combined list hits 30 [3](#0-2) . `DepositToken.transfer` only checks the *sender's* locked balance — anyone can send dust to any address [4](#0-3) . During `Pool.liquidate`, seized collateral is moved via `DepositToken.seize`, which routes through `_transfer` and therefore performs the same recipient registration [5](#0-4) .

### Finding Description
An unprivileged attacker deposits minimal collateral across the pool's deposit tokens (or simply holds dust balances) and calls `depositToken.transfer(feeCollector, 1 wei)` on each of the pool's `DepositToken`s. Because `feeCollector` starts with zero balance of each token, each transfer appends the token to `depositTokensOfAccount[feeCollector]` via `Pool.addToDepositTokensOfAccount` [6](#0-5) . The number of deposit tokens plus any debt tokens the collector ever holds quickly reaches the cap of 30.

From then on, any call to `Pool.liquidate` whose `_fee > 0` portion is seized to `feeCollector` in a deposit token the collector does not already hold reverts inside `_transfer` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`. Since `liquidate` is `nonReentrant` and the revert propagates atomically, the whole liquidation fails [7](#0-6) . Note the `_withdraw` path has the same fee flow: `_transfer(account_, _pool.feeCollector(), _fee)` reverts identically, DoS-ing withdrawals that charge a fee for tokens not yet in the collector's list [8](#0-7) .

### Impact Explanation
Liquidations are the solvency backstop of the pool. With the collector's list full, every liquidation that would credit a new collateral type to `feeCollector` reverts, so unhealthy positions in those collaterals cannot be liquidated at all. The `debtFloorInUsd`/`maxLiquidable` machinery is never reached — the revert occurs inside the seize transfer. This allows bad debt to accumulate while collateral prices fall, leading to protocol insolvency. At minimum it is a temporary freezing of funds (liquidators cannot act, and fee-bearing `withdraw` calls revert), plausibly permanent for collaterals never previously held by the collector, since the attacker can re-stuff the list if the collector ever empties a slot.

Caveat I could not fully verify within the tool budget: I did not read `Pool.liquidate` lines 560+ to confirm the exact seize recipients (`_toLiquidator` vs `feeCollector`) or whether the deployed `feeCollector` is a contract capable of self-emptying its list. If the fee seizure goes only to the liquidator, the same attack applies to a liquidator's own list — but a liquidator can choose `to_` or pre-clear, so the protocol-level DoS hinges on the fee collector receiving `_fee`, which `quoteLiquidateIn`/`quoteLiquidateOut` compute and which `_withdraw` demonstrably sends to `feeCollector` [9](#0-8) .

### Likelihood Explanation
The attack requires only dust amounts of each underlying and ordinary ERC-20-style transfers through public entry points — no privileged role, oracle manipulation, or flash loan. Cost is bounded by the number of deposit tokens needed to reach 30 entries. The only precondition is a nonzero `protocolFee`/`withdrawFee` in `FeeProvider`, which the quote functions show is a configurable-but-expected parameter [10](#0-9) .

### Recommendation
Do not register the `feeCollector` (or any internal/protocol account) in `depositTokensOfAccount`, or make `Pool.addToDepositTokensOfAccount` a no-op instead of reverting when the cap is reached (the list is only used for `depositOf`/`debtPositionOf` health computation, which is irrelevant for the fee collector since it never borrows). Alternatively, wrap the registration call in a try/catch inside `DepositToken._transfer`/`_mint` so a full list cannot brick transfers, seizures, or withdrawals.

### Proof of Concept
Hardhat (deployed-configuration fork) outline:

```ts
// 1. Enumerate pool deposit tokens
const tokens = await pool.getDepositTokens(); // IERC20/DepositToken list

// 2. For each token, acquire dust and send to feeCollector
const feeCollector = await pool.feeCollector();
for (const t of tokens) {
  const dep = await ethers.getContractAt("DepositToken", t);
  const underlying = await ethers.getContractAt("IERC20", await dep.underlying());
  await underlying.connect(whaleOrAttacker).approve(dep.address, 10);
  await dep.deposit(10);                       // attacker gets dust msdTokens
  await dep.connect(attacker).transfer(feeCollector, 1); // adds to collector's list
}
// repeat over debt tokens if needed until:
expect(await pool.getDepositTokensOfAccount(feeCollector))
  .length.to.be.gte(await pool.MAX_TOKENS_PER_USER());

// 3. Victim position goes unhealthy (price move or second attacker position)
// 4. Liquidator attempts:
await expect(
  pool.connect(liquidator).liquidate(msUsd, victim, repayAmt, victimDepositToken)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");
// whenever feeCollector's balance of `victimDepositToken` was 0 before seize.

// 5. Withdraw with fee also reverts for any account whose fee token is new to collector:
await expect(dep.connect(user).withdraw(amt, user.address))
  .to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");
```

Confirmed on-chain mechanics: recipient registration is unconditional on transfers [2](#0-1) , the cap check precedes insertion [3](#0-2) , and the existing test suite already verifies `UserReachedMaxTokens` reverts at 30 combined entries [11](#0-10) .
