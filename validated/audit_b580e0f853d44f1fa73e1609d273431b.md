### Title
`RecurringAirdrop.claim` binds the merkle leaf identity to `msg.sender`, permanently locking airdrop rewards for contract-based beneficiaries - (File: contracts/utils/RecurringAirdrop.sol)

### Summary
The bug class is "identity derived from `msg.sender` instead of resolving the true beneficiary on-chain." In The Graph's `Escrow.redeem`, using `msg.sender` as the indexer prevented vesting contracts from ever redeeming. Metronome's `RecurringAirdrop.claim` (and its `MetAirdrop` specialization) has the same flaw: the merkle leaf is `keccak256(abi.encodePacked(msg.sender, amount_))`, so the beneficiary account is forced to be the transaction's immediate caller. Any beneficiary that is a smart contract which cannot directly invoke `claim` (vesting contracts restricted to approved call targets, or users routing through `Operator.execute` where `msg.sender` becomes the `Operator` contract) can never claim its allocation.

### Finding Description
In `RecurringAirdrop.claim`, the account is not a parameter — it is hard-wired to `msg.sender`:

- Leaf: `keccak256(abi.encodePacked(msg.sender, amount_))` [1](#0-0) 
- Claimed accounting and payout both keyed on `msg.sender` [2](#0-1) 

`RecurringAirdrop` is a plain `ReentrancyGuardTransient`/`Governable` contract — it does not inherit `SynthContext`, so there is no `Operator`-aware `_msgSender()` resolution [3](#0-2) . Contrast with `Operator.execute`, which stores the real EOA in a transient slot and expects downstream contracts to resolve it via `getActualMsgSender()`/`SynthContext._msgSender()` [4](#0-3) [5](#0-4) . A user calling `claim` through `Operator.execute` sees `msg.sender == Operator`, the leaf hash mismatches, and the call reverts with `InvalidProof`.

`MetAirdrop._transferReward` compounds this: rewards are locked into `esMET` via `ESMET.lockFor(to_, ...)`, where `to_` is still `msg.sender` [6](#0-5) . If a beneficiary can only act via an intermediary contract, the esMET lock is attributed to the wrong identity or the call simply reverts.

### Impact Explanation
Permanent freezing of unclaimed yield. A merkle-tree beneficiary that is a contract unable to call `claim` directly — e.g., a vesting/timelock contract that only permits whitelisted function signatures and targets (the exact Graph vesting-contract scenario), or a wallet whose operational path is `Operator.execute` — can never produce a valid leaf because the leaf commits to `msg.sender`. Its `amount_` of `MET`/reward tokens stays in the distributor forever; there is no admin recovery path (no `sweep`/rescue function exists on `RecurringAirdrop`) [7](#0-6) .

### Likelihood Explanation
Medium-low. It requires the airdrop allocation to belong to a restricted smart contract rather than an EOA. That population is real — this is precisely the user segment the original Graph report described (vesting contracts holding protocol positions). Note that fixing this by taking `account_` as a parameter is safe because the merkle proof already binds the amount to the account; a relayer cannot redirect funds since payout still goes to `account_`.

### Recommendation
Change the leaf to commit to an explicit beneficiary parameter and pay that address, mirroring the upstream fix (derive the beneficiary from on-chain state/parameters rather than the caller):

```solidity
function claim(address account_, uint256 amount_, bytes32[] calldata proof_) external nonReentrant {
    if (merkleRoot == bytes32(0)) revert NothingToClaim();
    bytes32 _leaf = keccak256(abi.encodePacked(account_, amount_));
    if (!MerkleProof.verify(proof_, merkleRoot, _leaf)) revert InvalidProof();
    uint256 _claimable = amount_ - claimed[account_];
    if (_claimable == 0) revert NothingToClaim();
    claimed[account_] += _claimable;
    _transferReward(account_, _claimable);
    emit RewardClaimed(account_, _claimable);
}
```

This preserves security (proof still binds `account_` ↔ `amount_`) while letting any caller trigger claims for contract beneficiaries.

### Proof of Concept
Foundry-style PoC: a beneficiary contract that cannot invoke `claim` (e.g., a vesting contract with a restricted function whitelist, modeled here as a contract with no `claim` path) is included in the merkle tree but can never claim.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {RecurringAirdrop} from "contracts/utils/RecurringAirdrop.sol";
import {ERC20Mock} from "contracts/mock/ERC20Mock.sol";

// Mimics a vesting contract: it holds the allocation but its
// restricted call target list does not include RecurringAirdrop.claim.
contract RestrictedBeneficiary {
    // no function that calls RecurringAirdrop.claim
}

contract MsgSenderAirdropTest is Test {
    ERC20Mock token;
    RecurringAirdrop airdrop;
    RestrictedBeneficiary vesting;

    function setUp() public {
        token = new ERC20Mock("Reward", "RWD", 18);
        airdrop = new RecurringAirdrop(token);
        vesting = new RestrictedBeneficiary();
        token.mint(address(airdrop), 100 ether);
    }

    function test_contractBeneficiaryCannotClaim() public {
        // Leaf = [vestingContract, amount]
        bytes32 leaf = keccak256(abi.encodePacked(address(vesting), uint256(100 ether)));
        // Single-leaf tree: root == leaf
        airdrop.updateMerkleRoot(leaf, bytes32("ipfs"));

        bytes32[] memory proof = new bytes32[](0);

        // Any EOA/relayer calling on the vesting contract's behalf fails:
        // leaf commits to msg.sender, which is this test contract / relayer.
        vm.expectRevert(InvalidProof.selector);
        airdrop.claim(100 ether, proof);

        // The vesting contract itself cannot call claim at all.
        // Result: 100 ether of rewards are permanently stuck.
        assertEq(token.balanceOf(address(airdrop)), 100 ether);
    }

    function test_operatorCallerMismatch() public {
        // Even a direct call works only if msg.sender == beneficiary,
        // so Operator.execute-based users get InvalidProof because
        // msg.sender resolves to the Operator contract.
        bytes32 leaf = keccak256(abi.encodePacked(address(this), uint256(50 ether)));
        airdrop.updateMerkleRoot(leaf, bytes32("ipfs"));
        // Calling through any proxy/operator contract whose address != leaf account reverts.
    }
}
```

Caveat: a plain EOA or unrestricted contract can still claim for itself, so this is a freezing-of-yield issue affecting restricted contract beneficiaries rather than a universally exploitable theft path.
