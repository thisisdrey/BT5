### Title
TVM vote-reward computation permanently loses pre-upgrade reward for `beginCycle < newRewardAlgorithmEffectiveCycle` - (File: actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java)

### Summary
`VoteRewardUtil.computeReward` (the TVM/native-contract path used by `withdrawReward()` opcode, the `RewardBalance` precompile, and self-destruct reward flush) only implements the new VI-delta reward algorithm. It has no branch to route pre-upgrade cycles through the legacy per-cycle reward formula the way the non-TVM `MortgageService.computeReward` does. This mirrors the Sherlock report pattern: two parallel implementations of the same accounting logic where one path omits a threshold-dependent special case, silently dropping value that should be forwarded to the user.

### Finding Description
`MortgageService.computeReward(beginCycle, endCycle, accountCapsule)` (used by the `WithdrawBalanceActuator` / `UnfreezeBalanceV2Actuator` path) explicitly splits the reward computation at `newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle()`: [1](#0-0) 

For `beginCycle < newAlgorithmCycle` it explicitly calls `getOldReward(...)`, which computes reward for those cycles using the legacy `getReward`/`getWitnessVote` ratio method (or the backfilled `RewardViCalService` VI table), and only uses `delegationStore.getWitnessVi` delta for the remaining cycles `>= newAlgorithmCycle`. [2](#0-1) 

The TVM equivalent, `VoteRewardUtil.computeReward`, used for `WithdrawRewardProcessor.execute` (TVM `withdrawReward()` opcode), `Program.withdrawRewardAndCancelVote` (suicide/self-destruct settlement), and the `RewardBalance` precompile (`VoteRewardUtil.queryReward`), has no such branch — it unconditionally computes the reward purely from `delegationStore.getWitnessVi(beginCycle-1,...)` / `getWitnessVi(endCycle-1,...)` delta, with no call into any "old reward" fallback: [3](#0-2) [4](#0-3) 

`DelegationStore`'s VI values are only accumulated going forward once `useNewRewardAlgorithm()` becomes true (see `MaintenanceManager.doMaintenance`, which only calls `delegationStore.accumulateWitnessVi(...)` when `dynamicPropertiesStore.useNewRewardAlgorithm()` is true): [5](#0-4) 

So for any TVM voting account whose `beginCycle` predates `newRewardAlgorithmEffectiveCycle`, `delegationStore.getWitnessVi(beginCycle-1, ...)` returns `BigInteger.ZERO` (not backfilled in `DelegationStore` — the backfill only lives in the separate `rewardViStore` used by `RewardViCalService`, which `VoteRewardUtil` never queries). The resulting `deltaVi` therefore only reflects VI accumulated from `newAlgorithmCycle` onward, and the entire pre-upgrade reward window (`beginCycle` .. `newAlgorithmCycle-1`) is computed as zero and never credited to the account's `allowance`.

Once `VoteRewardUtil.withdrawReward` runs, it unconditionally advances and persists `beginCycle`/`endCycle` via `repository.updateBeginCycle` / `updateEndCycle` — even though the pre-upgrade reward for that window was computed as (effectively) zero — so the missed reward becomes permanently unrecoverable. [6](#0-5) 

### Impact Explanation
Any smart contract account that cast TVM votes (via the vote opcode) with a `beginCycle` earlier than the network's `newRewardAlgorithmEffectiveCycle`, and later calls `withdrawReward()` (directly, or implicitly via `SELFDESTRUCT`/`Program.withdrawRewardAndCancelVote`), permanently loses the reward accrued for cycles before the algorithm switch. This is a direct, unbacked loss of legitimately earned voting rewards for TVM contract accounts — a concrete loss-of-funds condition reachable purely through ordinary signed transactions (deploy contract, vote, withdraw).

### Likelihood Explanation
This requires: (1) the account is a smart contract (TVM voting is contract-only), (2) it voted while `beginCycle < newRewardAlgorithmEffectiveCycle`, and (3) `allowTvmVote` was already active at that time (or the vote predates the algorithm-switch cycle while TVM voting was active). I was unable to fully confirm from the code the exact chronological ordering of the `ALLOW_TVM_VOTE` proposal activation versus `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE` activation on mainnet — if TVM voting was only ever enabled network-wide after the reward-algorithm switch cycle had already passed, then `beginCycle` for any TVM-voting contract would always be `>= newAlgorithmCycle`, and this specific code path would be effectively unreachable in practice today. This uncertainty should be verified against the deployed proposal history before treating this as an active, currently-exploitable issue; the logic asymmetry between `MortgageService.computeReward` and `VoteRewardUtil.computeReward` is nonetheless a real code defect.

### Recommendation
Make `VoteRewardUtil.computeReward` mirror `MortgageService.computeReward`: fetch `newRewardAlgorithmEffectiveCycle` from `repository.getDynamicPropertiesStore()`, and for `beginCycle < newAlgorithmCycle`, compute the legacy per-cycle reward (via `delegationStore.getReward`/`getWitnessVote`, or by exposing the same `getOldReward`/`RewardViCalService` fallback to the `Repository`/TVM path) before applying the VI-delta method to the remaining cycles. Add a regression test exercising a TVM-voting contract with `beginCycle` set prior to the reward-algorithm switch cycle to confirm reward parity with the native `MortgageService` path.

### Proof of Concept
Conceptual reproduction (cannot be fully executed without confirming proposal activation order, see Likelihood):
1. Set `newRewardAlgorithmEffectiveCycle = N` and enable `allowTvmVote` at a cycle `< N` (or manually seed `DelegationStore` with a `beginCycle < N` for a contract, as done in `ComputeRewardTest`/`DelegationServiceTest`, then invoke the TVM path).
2. Deploy a voting contract and cast votes at `beginCycle < N`; let several cycles pass with rewards accruing via `MortgageService.payReward`/`delegationStore.addReward`.
3. Call the TVM `withdrawReward()` opcode (or `RewardBalance` precompile) on the contract and compare against `mortgageService.queryReward()` computed for an equivalent non-contract account with the same vote history — the TVM contract's reward will be lower, missing the pre-`N` cycle contribution, because `VoteRewardUtil.computeReward` (lines 90-110) skips the `getOldReward` branch present in `MortgageService.computeReward` (lines 209-214).   private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

      adjustAllowance(address, reward, repository);
