### Title
`storage_deposit` intent permanently burns signer's wNEAR ledger balance if downstream `storage_deposit` NEAR call fails - ([File: contracts/defuse/src/contract/intents/state.rs])

### Summary
`State::storage_deposit` debits the signer's wNEAR `token_balances` synchronously via `self.withdraw(...)` before the async `near_withdraw` → `do_storage_deposit` → `ext_storage_management::storage_deposit` promise chain executes. Unlike other withdrawal paths (e.g. `ft_withdraw`, and `resolve_deposit_internal`) which schedule a resolver callback that re-credits the ledger on failure, `do_storage_deposit` returns the outbound `storage_deposit` `Promise` directly with no `.then()` resolver, so a failure anywhere downstream leaves the debited balance permanently unrecovered.

### Finding Description
The claimed invariant is: `token_balances[signer][wNEAR]_before - storage_deposit.amount == token_balances[signer][wNEAR]_after` **only if** `do_storage_deposit`'s NEAR-side `storage_deposit` call to `storage_deposit.contract_id` succeeds; on failure it should instead hold `token_balances[signer][wNEAR]_after == token_balances[signer][wNEAR]_before` (full re-credit). Tracing the code:

1. `State::storage_deposit` in `contracts/defuse/src/contract/intents/state.rs:265-297` calls `self.withdraw(owner_id, [(wnear_token_id, amount)], Some("withdraw"), false)`, which in `contracts/defuse/src/contract/tokens/mod.rs::withdraw` (lines 76-128) synchronously does `owner.token_balances.sub(token_id, amount)` and `self.storage.state.total_supplies.sub(...)`. This happens in the *same receipt* as `execute_intents`, so it is committed regardless of what happens later. [1](#0-0) [2](#0-1) 

2. After the synchronous debit, the code schedules `ext_wnear::near_withdraw(amount)` followed by `.then(... .do_storage_deposit(storage_deposit))`, then `.detach()` — the outer function has no visibility into, or callback wired to, the eventual success/failure of this chain. [3](#0-2) 

3. `do_storage_deposit` in `contracts/defuse/src/contract/tokens/nep141/storage_deposit.rs` checks only that `near_withdraw` succeeded (`require!(promise_result_checked_void(0).is_ok(), "near_withdraw failed")`), and then directly **returns** the `ext_storage_management::storage_deposit(...)` `Promise` with no `.then()` resolver attached to inspect its outcome: [4](#0-3) 

4. Contrast with the pattern used elsewhere in the same file (`contracts/defuse/src/contract/tokens/mod.rs::resolve_deposit_internal`, lines 152-220), which is explicitly designed to re-credit `token_balances` when a downstream deposit/transfer fails or is partially refunded by the receiver. `do_storage_deposit` has no equivalent resolver. [5](#0-4) 

Root cause: the debit-then-async-external-call pattern used for `storage_deposit` (and identically for `native_withdraw`/`auth_call`, which do have their own `do_*` callbacks but those are out of scope for this specific question) lacks a resolve callback for `do_storage_deposit`'s outbound `ext_storage_management::storage_deposit` promise. If that call fails (e.g., target contract doesn't implement `storage_deposit`, panics, or the attached deposit is below its minimum), the NEAR that was unwrapped from wNEAR is returned by the NEAR runtime to the predecessor of that failed FunctionCall action — i.e., back to the Defuse contract's own NEAR account balance — but there is no code path that turns this refunded native NEAR back into a `token_balances` credit for the signer. The ledger entry is gone forever while the actual NEAR sits unaccounted for in the contract's account balance.

None of the listed guards (`MultiPayload::verify`, nonce/salt checks, `TransferMatcher::finalize`, `checked_*` arithmetic) address this — the vulnerability is in the promise/callback wiring after intent execution has already committed the debit, not in signature or accounting-delta validation.

### Impact Explanation
Any signer whose `StorageDeposit` intent targets a `contract_id` that rejects the NEP-145 `storage_deposit` call (non-existent account, non-conforming contract, insufficient deposit for that receiver's minimum balance, or any panic in the callee) permanently loses `storage_deposit.amount` of wNEAR from their Verifier-tracked `token_balances`, with no re-credit. This is a direct "value debited != value delivered + value re-credited on failure" break — matching the Critical category "user funds permanently frozen" (funds are burned from the ledger, not merely locked, but the net effect is the same: the signer's authorized balance disappears without any corresponding settlement). It is repeatable per signer, per intent, and can be triggered by any attacker acting against their own account by simply specifying a bad `contract_id`/`deposit_for_account_id`, or unintentionally by any well-meaning user, with 100% reproducibility.

### Likelihood Explanation
No special privileges are required — this is triggerable by any unprivileged user submitting a `StorageDeposit` intent (via `execute_intents`) referencing a `contract_id` that will reject the storage deposit call. The only precondition is having wNEAR balance recorded in `token_balances` and constructing/signing a normal `MultiPayload` with a `StorageDeposit` intent. This is a highly likely, easily reproducible bug (deterministic — not dependent on race conditions or validator behavior).

### Recommendation
Attach a `.then()` resolver callback to the `ext_storage_management::storage_deposit(...)` promise inside `do_storage_deposit`, mirroring the pattern in `resolve_deposit_internal`/`ft_withdraw`'s resolve callbacks: on promise failure (or on a returned refund amount from the callee), re-credit `owner_id`'s `token_balances` (and `total_supplies`) for the wNEAR amount that failed to settle, symmetric to how other withdrawal flows already refund on failure.

### Proof of Concept
`cargo test` (near-workspaces sandbox), added under `tests/src/tests/defuse/storage/mod.rs` or `tests/src/tests/defuse/intents/mod.rs`:
1. Deploy `defuse` contract and a wNEAR-storage-managed FT/mock token; register a signer account with wNEAR `token_balances` = `X`.
2. Sign a `MultiPayload` containing a `StorageDeposit` intent with `contract_id` = an account that does NOT implement `storage_deposit` (e.g., a plain deployed contract with no NEP-145 methods, or simply a non-existent AccountId), `amount` = some `Y <= X`.
3. Call `execute_intents` with this payload.
4. Assert (binding check):
   - Before: `balance_of(signer, wnear_token_id) == X`.
   - After promise chain resolves (await all receipts in sandbox): assert `ext_storage_management::storage_deposit` receipt failed (as expected, since callee doesn't implement it).
   - Assert `balance_of(signer, wnear_token_id)` — expected (per correct behavior) to be `X` (fully refunded) but actual result is `X - Y` (permanently debited), proving the binding `debited == delivered + re-credited` is violated.
5. Additionally assert that `total_supplies` for wNEAR token also decreased by `Y` with no corresponding NEAR ever entering any user's ledger balance, confirming permanent loss rather than a delayed credit.

    fn storage_deposit(
        &mut self,
        owner_id: &AccountIdRef,
        storage_deposit: StorageDeposit,
    ) -> Result<()> {
        self.withdraw(
            owner_id,
            [(
                Nep141TokenId::new(self.wnear_id().into_owned()).into(),
                storage_deposit.amount.as_yoctonear(),
            )],
            Some("withdraw"),
            false,
        )?;

        ext_wnear::ext(self.wnear_id.clone())
            .with_attached_deposit(NearToken::from_yoctonear(1))
            .with_static_gas(NEAR_WITHDRAW_GAS)
            // do not distribute remaining gas here
            .with_unused_gas_weight(0)
            .near_withdraw(U128(storage_deposit.amount.as_yoctonear()))
            .then(
                // do_storage_deposit only after unwrapping NEAR
                Self::ext(env::current_account_id())
                    .with_static_gas(Self::DO_STORAGE_DEPOSIT_GAS)
                    // do not distribute remaining gas here
                    .with_unused_gas_weight(0)
                    .do_storage_deposit(storage_deposit),
            )
            .detach();

        Ok(())
    }

    pub fn resolve_deposit_internal<'a, I>(&mut self, receiver_id: &AccountIdRef, tokens: I)
    where
        I: IntoIterator<Item = (TokenId, &'a mut u128)>,
        I::IntoIter: ExactSizeIterator,
    {
        let tokens_iter = tokens.into_iter();
        let tokens_count = tokens_iter.len();

        let requested_refunds = promise_result_checked_json_with_len::<Vec<U128>>(0, tokens_count)
            .ok()
            .and_then(Result::ok)
            .filter(|refunds| refunds.len() == tokens_count);

        let mut burn_event = MtBurnEvent {
            owner_id: Cow::Borrowed(receiver_id),
            authorized_id: None,
            token_ids: Vec::with_capacity(tokens_count).into(),
            amounts: Vec::with_capacity(tokens_count).into(),
            memo: Some(REFUND_MEMO.into()),
        };

        let Some(receiver) = self
            .storage
            .accounts
            .get_mut(receiver_id)
            .map(Lock::as_inner_unchecked_mut)
        else {
            tokens_iter.for_each(|(_, amount)| *amount = 0);
            return;
        };

        for ((token_id, deposited), requested_refund) in
            tokens_iter.zip_eq(requested_refunds.map_or_else(
                || Either::Right(std::iter::repeat_n(None, tokens_count)),
                |v| Either::Left(v.into_iter().map(|elem| Some(elem.0))),
            ))
        {
            let requested_refund = requested_refund.unwrap_or(*deposited);
            let balance_left = receiver.token_balances.amount_for(&token_id);
            // NOTE: refunds are capped by deposited amounts and balance left on the receiver
            let refund_amount = requested_refund.min(*deposited).min(balance_left);
            *deposited = refund_amount;
            if refund_amount == 0 {
                continue;
            }

            burn_event.token_ids.to_mut().push(token_id.to_string());
            burn_event.amounts.to_mut().push(refund_amount);

            receiver
                .token_balances
                .sub(token_id.clone(), refund_amount)
                .ok_or(DefuseError::BalanceOverflow)
                .unwrap_or_else(|err| err.panic());

            self.storage
                .state
                .total_supplies
                .sub(token_id, refund_amount)
                .ok_or(DefuseError::BalanceOverflow)
                .unwrap_or_else(|err| err.panic());
        }

        if !burn_event.amounts.is_empty() {
            // NOTE: No need for `check_refund()` here since this IS the refund.
            // The refund memo size was already accounted for in the original mint.
            MtEvent::MtBurn([burn_event].as_slice().into()).emit();
        }
    }

    #[private]
    pub fn do_storage_deposit(storage_deposit: StorageDeposit) -> Promise {
        require!(
            promise_result_checked_void(0).is_ok(),
            "near_withdraw failed",
        );

        ext_storage_management::ext(storage_deposit.contract_id)
            .with_attached_deposit(storage_deposit.amount)
            .with_static_gas(STORAGE_DEPOSIT_GAS)
            // do not distribute remaining gas here
            .with_unused_gas_weight(0)
            .storage_deposit(Some(storage_deposit.deposit_for_account_id), None)
    }
