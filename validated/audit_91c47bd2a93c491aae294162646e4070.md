### Title
`SmartFarmingManager` swap calls carry no deadline, so pending `leverage`/`flashRepay` transactions can execute at stale prices - (File: contracts/SmartFarmingManager.sol)

### Summary
`SmartFarmingManager.leverage` and `SmartFarmingManager.flashRepay` route AMM swaps through `ISwapper.swapExactInput`, whose interface (`contracts/interfaces/external/ISwapper.sol:6-12`) accepts only `tokenIn_`, `tokenOut_`, `amountIn_`, `amountOutMin_`, and `receiver_` — no `deadline` parameter. Because the slippage bounds (`depositAmountMin_`, `swapAmountOutMin_`) are fixed at transaction-submission time, a transaction that sits pending in the mempool can be executed much later under materially different prices, with only the stale `amountOutMin` protecting the user. This is the same bug class as the referenced USSD issue: `amountOutMinimum` existed there too; the missing deadline is the flaw.

### Finding Description
- `leverage()` performs up to two swaps via the internal `_swap`, both invoked with `amountOutMin_ = 0` (`contracts/SmartFarmingManager.sol:184`, `contracts/SmartFarmingManager.sol:197`), relying solely on the post-hoc `depositAmountMin_` check at line 198.
- `flashRepay()` swaps withdrawn collateral to synth via `_swap(swapper(), _collateralOf(depositToken_), _syntheticToken, _withdrawn, 0)` (`contracts/SmartFarmingManager.sol:125`) and only afterwards enforces `swapAmountOutMin_` (line 126).
- `_swap` calls `swapper_.swapExactInput(...)` (`contracts/SmartFarmingManager.sol:305`), and `ISwapper` exposes no deadline parameter (`contracts/interfaces/external/ISwapper.sol:6-12`).
- `swapper()` resolves to `pool.poolRegistry().swapper()` (`contracts/SmartFarmingManager.sol:216-218`), an external AMM-backed swapper, so execution price depends on pool state at inclusion time, not at signing time.

If the user's tx is pending during volatile conditions, the market can move so that the previously-reasonable `amountOutMin` is far below fair value, and a sandwiching bot can push execution to exactly that bound.

### Impact Explanation
An unprivileged attacker can sandwich a pending `leverage`/`flashRepay` transaction: the user's collateral is sold at the stale minimum, transferring value to MEV bots. For `flashRepay`, degraded swap output still repays debt but leaves the user worse off; for `leverage`, the user ends with a smaller deposit than the market warranted. This is direct loss of user funds caused by the absence of a validity window.

### Likelihood Explanation
Requires only that a victim's transaction remain pending (high gas periods) while price drifts, and an MEV bot — both common on mainnet/Base where these contracts are deployed. All entry points are public and unprivileged (`whenNotShutdown`, `nonReentrant` only; no deadline input exists for the caller to pass).

### Recommendation
Add a `deadline` parameter to `leverage`, `flashRepay` (and the `ISwapper.swapExactInput` signature), forwarding it to the underlying router call, e.g. `require(block.timestamp <= deadline)` before executing swaps, or extend `ISwapper` to accept and enforce a deadline so stale transactions revert instead of executing at outdated slippage bounds.

### Proof of Concept
Reproducible on a fork: a user calls `leverage(tokenIn, depositToken, msAsset, amountIn, 2e18, depositAmountMin)`; the tx stays pending while the collateral/msAsset pool price moves adversely; when mined, `_swap` executes `swapExactInput` with `amountOutMin = 0` internally and the stale `depositAmountMin_` check still passes, leaving the user with an under-priced deposit and an attacker capturing the difference via a sandwich. There is no mechanism in `SmartFarmingManager` or `ISwapper` to expire the intent.
