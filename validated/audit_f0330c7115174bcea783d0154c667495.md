Fee bypass on `Nep245`/`Imt` tokens via splitting a `TokenDiff` into multiple unit-delta intents - ([File: contracts/defuse/core/src/intents/token_diff.rs])

### Summary
`TokenDiff::execute_intent` computes the protocol fee independently for each `TokenDiff` struct in the intents vector, using `Self::token_fee(token_id, amount, protocol_fee)` where `amount` is the `|delta|` of that single intent, not the signer's aggregate negative delta for the token across the whole batch. For `Nep245`/`Imt` token types the fee function returns `Pips::ZERO` whenever `amount <= 1` [1](#0-0) , so a signer can split a `delta=-2` trade into two separate `TokenDiff{diff:{T:-1}}` intents to avoid the fee entirely.

### Finding Description
Binding claimed broken: `fee_collected(T) == Pips::fee_ceil(protocol_fee, |sum_of_negative_deltas_for_T_in_batch|)` vs actual `fee_collected(T) == sum over each TokenDiff intent of Pips::fee_ceil(protocol_fee_after_token_fee_threshold(|delta_i|), |delta_i|)`.

In `TokenDiff::execute_intent`, for each negative delta the fee is `Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount)`, computed and applied per intent inside the loop `for (token_id, delta) in &self.diff` [2](#0-1) . `token_fee` explicitly zeroes the fee for `Nep245`/`Imt` when `amount <= 1`:
```
TokenIdType::Nep245 | TokenIdType::Imt if amount > 1 => {}
TokenIdType::Nep171 | TokenIdType::Nep245 | TokenIdType::Imt => return Pips::ZERO,
``` [1](#0-0) 

The multi-intent execution path processes each `Intent` (including each `TokenDiff`) completely independently: `DefuseIntents::execute_intent` iterates `for intent in self.intents { intent.execute_intent(...)? }` [3](#0-2) , and nothing merges deltas for the same `TokenId` across distinct `TokenDiff` structs before the fee calculation — merging only happens later in `TransferMatcher`/`Deltas` for balance bookkeeping, which is fee-agnostic [4](#0-3) .

Attacker's payload: a single `MultiPayload` signing one `DefusePayload<DefuseIntents>` whose `intents` vector contains two `TokenDiff` structs: `TokenDiff{diff:{T:-1}}` and `TokenDiff{diff:{T:-1}}`, both on the same `Nep245`/`Imt` `TokenId` T, with fee=`Pips::ONE_PERCENT`. Each is evaluated with `amount=1`, hitting the `amount <= 1` branch and returning `Pips::ZERO`, so `fees_collected` stays empty for both, and no balance is added to `fee_collector` [5](#0-4) . Had the signer submitted one `TokenDiff{diff:{T:-2}}` instead, `token_fee(T, 2, fee)` would return the nonzero `fee` (since `amount>1`), and `fee.fee_ceil(2)` would be nonzero for `Pips::ONE_PERCENT` (`fee_ceil(2) = ceil(2*10000/1_000_000) = 1`) [6](#0-5) .

None of the existing guards (`MultiPayload::verify`, nonce/salt checks, `has_public_key`) prevent this, because they operate on payload authenticity/replay, not on fee computation semantics, and the engine's per-intent loop in `execute_signed_intent` simply calls `intents.execute_intent(...)` once per signed payload with no cross-intent aggregation of same-token deltas for fee purposes [7](#0-6) .

### Impact Explanation
The `fee_collector` account under-collects protocol fees on `Nep245`/`Imt` token trades whenever the signer splits any trade into a sequence of `|delta|<=1` `TokenDiff` intents targeting the same token within one signed payload (or across multiple payloads in one `execute_intents`/`simulate_intents` batch). This is fully repeatable by any unprivileged signer, for arbitrary MT amounts (split N units into N unit-delta intents), and scales the fee bypass to the full traded volume. This matches the Critical category "protocol fees bypassed or over-collected."

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: the signer only needs to hold ≥2 units of a `Nep245`/`Imt` token `T` in the Verifier and sign a payload whose `intents` vector contains multiple `TokenDiff` structs with `|delta|=1` on `T` instead of one merged `TokenDiff`. No special role, relayer key, or victim key is needed — this is entirely within the "unpriviledged signer" scope. It costs only the gas of one extra intent entry in the payload and is trivially repeatable per trade, per token, per account.

### Recommendation
Aggregate `|delta|` per `TokenId` across all `TokenDiff` intents belonging to the same signer within a `DefuseIntents`/batch before applying the `Nep245`/`Imt` `amount <= 1` fee-exemption threshold and before computing `fee_ceil`, rather than evaluating `token_fee` independently per `TokenDiff` struct. Alternatively, merge all `TokenDiff` intents from the same signer on the same token into a single net delta prior to fee computation.
