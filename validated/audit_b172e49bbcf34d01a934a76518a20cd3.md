### Title
Unauthenticated `RecvError` handling permits spoofed tunnel teardown - ([File: outside.go])

### Summary
`readOutsidePackets` dispatches `header.RecvError` packets to `handleRecvError` before any decryption, certificate verification, or cryptographic authentication takes place. `handleRecvError` then tears down (`closeTunnel` + `DeleteHostInfo`) an established, already-authenticated tunnel based solely on an unauthenticated header field (`h.RemoteIndex`) and a source-address comparison that can be defeated by UDP address spoofing. This mirrors the reported bug class: a state-mutating operation (deleting/altering owner/session state) that lacks proper authorization and can be triggered by a party that never proved its identity via the protocol's normal authentication path (the Noise handshake + certificate verification), analogous to `GigaNameNFTBeforeUpdateHandler.update()` being callable by anyone instead of being restricted to the authenticated caller.

### Finding Description
In `outside.go`, `readOutsidePackets` parses the header and, for `header.RecvError`, calls the handler immediately, prior to any HostInfo lookup by session key, decryption, or peer-certificate check: [1](#0-0) 

`handleRecvError` looks up the hostinfo purely from the (unencrypted, attacker-visible) `RemoteIndex` field, and only rejects the request if the currently recorded remote address is valid and does not match the packet's source address: [2](#0-1) 

Because `RemoteIndex` travels in cleartext in every packet of a tunnel, and UDP source addresses are trivially spoofable (particularly for attackers on-path or capable of address spoofing), an attacker who observes even one packet of a target tunnel can craft a `RecvError` packet with the tunnel's `RemoteIndex` and a spoofed source address matching the peer's currently recorded remote endpoint, causing the receiver to invoke `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` — destroying session/hostmap state for two parties that both hold valid certificates, without the attacker itself ever presenting one.

This is directly analogous to the reported issue: a function that mutates important ownership/session state (`update()` in the report; `closeTunnel`/`DeleteHostInfo` here) is reachable by an unauthorized actor because the access check that should gate the state mutation (proof of identity/certificate ownership, or of legitimately owning the tunnel) is missing or bypassable.

### Impact Explanation
An attacker with no valid Nebula certificate can force termination of an established, mutually-authenticated tunnel between two legitimate peers, causing denial of service and forcing a costly re-handshake, purely by spoofing a UDP source address and replaying an observable index value. This is a remote state-poisoning / service-disruption impact reachable pre-authentication.

### Likelihood Explanation
Exploitation requires the attacker to (1) observe or otherwise learn a tunnel's `RemoteIndex` (present in cleartext in every packet header) and (2) spoof a UDP packet with a source address matching the peer's currently recorded remote endpoint. Both conditions are realistic for an on-path attacker or in networks/paths that do not enforce anti-spoofing (no BCP38 filtering), which is common on the public internet paths Nebula is designed to traverse.

### Recommendation
Do not act on unauthenticated `RecvError` signals to unilaterally destroy tunnel state. At minimum, require it to be delivered from the recorded remote endpoint before recording a "spoof" event (already partially done) and additionally rate-limit/challenge before tearing down, or require some proof tied to the session (e.g., a token/counter derived from session state) rather than a bare index+source-address match, since UDP source addresses are not a proof of identity.

### Proof of Concept
1. Establish a tunnel between hosts A and B; observe any single UDP packet between them to learn the wire-visible `RemoteIndex` used in headers.
2. As attacker C (no valid Nebula certificate), craft a UDP packet with header `Type = header.RecvError`, `RemoteIndex` matching the observed value, and a spoofed source IP/port equal to B's known current UDP endpoint (`hostinfo.GetRemote()` on A's side).
3. Send this packet to A. `readOutsidePackets` on A routes it directly to `handleRecvError` prior to any decryption/authentication (outside.go:81-83).
4. `handleRecvError` finds the hostinfo via `QueryReverseIndex`, sees `hr == addr` (the spoofed source matches B's recorded remote), and calls `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)` — tearing down the tunnel between A and B without C ever presenting a certificate.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
