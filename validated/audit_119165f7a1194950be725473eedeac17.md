### Title
Missing per-action storage-proof check for non-FunctionCall actions at protocol version 86 lets a DeleteKey/Stake-heavy receipt exceed the 4MB per-receipt storage-proof hard limit undetected - ([File: runtime/runtime/src/lib.rs])

### Summary
`apply_action_receipt` seeds `storage_proof_size_before_receipt` whenever `EnforcePerReceiptStorageProofLimit` is enabled (PV ≥ 86) but only computes `storage_proof_limit_for_all_actions` when `EnforceStorageProofLimitForAllActions` is enabled (PV ≥ 87). At exactly protocol version 86, the guard `if let (true, Some(size_before), Some(limit))` never fires because `limit` is `None`, so a receipt composed of non-`FunctionCall` actions (e.g., many `DeleteKey`/`Stake` actions) is never checked against `per_receipt_storage_proof_size_limit`, while the in-VM `RecordedStorageCounter` doesn't apply to these action kinds either.

### Finding Description
In `apply_action_receipt` (`runtime/runtime/src/lib.rs:871-889`): [1](#0-0) 
`storage_proof_size_before_receipt` is `Some(..)` starting at PV 86 (`EnforcePerReceiptStorageProofLimit`), while `storage_proof_limit_for_all_actions` is `Some(..)` only starting at PV 87 (`EnforceStorageProofLimitForAllActions`), per `core/primitives-core/src/version.rs:598` and `:603`: [2](#0-1) 
The post-action check that would catch actions other than `FunctionCall` is gated on both being `Some`: [3](#0-2) 
At PV 86 this tuple is `(true, Some(_), None)`, so the `if let` never matches and `ReceiptStorageProofSizeExceeded` can never be raised for that receipt, regardless of how much storage proof its `DeleteKey`/`Stake`/`AddKey` actions record. The in-VM `RecordedStorageCounter` (`runtime/near-vm-runner/src/logic/recorded_storage_counter.rs`) is only invoked from the WASM host-function path for `FunctionCall`, so it cannot cover these action kinds either, as the code comment itself states (`runtime/runtime/src/lib.rs:879`, `core/primitives-core/src/version.rs:451-456`): [4](#0-3) 

An attacker account with hundreds of access keys can, from a single `FunctionCall`-triggered promise batch, issue up to `max_actions_per_receipt` `DeleteKey` actions (each `promise_batch_action_delete_key`) targeting its own many access keys. Each `DeleteKey` action walks/removes an access-key trie subtree, recording storage-proof nodes proportional to the number of existing keys — the existing test `test_add_keys_after_large_read_exceed_receipt_storage_proof_limit` (`runtime/runtime/src/tests/apply.rs:1694-1755`) already demonstrates that `AddKey`/related access-key actions against a large existing key set can record proof on the order of the 4MB limit within a handful of actions; the same access pattern applies to `DeleteKey`. [5](#0-4) 

Existing generic safeguards do not stop this at PV 86:
- `RecordedStorageCounter` – VM-only, doesn't run for non-`FunctionCall` actions.
- `main_storage_proof_size_soft_limit`/`check_proof_size_limit_exceed` – checked only *before starting a new receipt* to decide delayed-queue placement (`runtime/runtime/src/lib.rs:2407-2416`, `core/store/src/trie/mod.rs:702-704`), not mid-receipt, so a receipt already in progress can blow past this soft limit unbounded. [6](#0-5) 
- Gas/action-count limits (`max_actions_per_receipt`) bound the number of actions but not the storage-proof cost per action.

### Impact Explanation
This is a real, code-confirmed gap between the activation heights of `EnforcePerReceiptStorageProofLimit` (PV 86) and `EnforceStorageProofLimitForAllActions` (PV 87). While the network is running at PV 86, an unprivileged attacker can craft a receipt whose recorded storage-proof size for non-`FunctionCall` actions exceeds the documented 4MB per-receipt hard cap without any check firing. Because `main_storage_proof_size_soft_limit` is enforced only at receipt-boundary granularity, a single oversized receipt can drive the chunk's total storage-proof/witness size well past intended bounds, risking breach of the compile-time hard caps (`MAX_UNCOMPRESSED_STATE_WITNESS_SIZE`/`MAX_COMPRESSED_STATE_WITNESS_SIZE`) that gate witness distribution/validation, which could cause chunk production/validation for the shard to stall — a shard-halting-class impact within scope. It does not directly cause fund theft, inflation, or a producer/validator disagreement (since both compute with the same protocol-version logic deterministically), but it does defeat the documented METERING_TOTALITY guarantee for the per-receipt hard proof-size cap during that window.

### Likelihood Explanation
Preconditions: the attacker needs an account they control and hundreds of access keys on that account (cheap to create — self-funded, no privileged access needed), and the network must be running at protocol version 86 specifically (a real, time-bounded window per the protocol-versioning schedule referenced in the repo's spec docs, since PV 86 is a real mainnet-voted version preceding PV 87). The exploit itself (a promise batch of many `DeleteKey`/`AddKey`/`Stake` actions) is trivially reproducible and repeatable, requiring only gas to cover action costs (which is normal transaction cost, not a bypass). The likelihood is entirely conditioned on the chain currently sitting at exactly PV 86; once PV 87 activates, the gap closes.

### Recommendation
Decouple the "before" size measurement from the "for-all-actions" limit's independent feature gate, or make `EnforceStorageProofLimitForAllActions` activate at the same protocol version as `EnforcePerReceiptStorageProofLimit` (or make the latter imply the former) so there is no version at which `storage_proof_size_before_receipt` is `Some` while `storage_proof_limit_for_all_actions` is `None`. Concretely, change the guard to check the receipt's recorded size against `per_receipt_storage_proof_size_limit` whenever `storage_proof_size_before_receipt` is `Some`, independent of the second feature flag, or bump `EnforceStorageProofLimitForAllActions`'s `protocol_version()` to be ≤ `EnforcePerReceiptStorageProofLimit`'s.

### Proof of Concept
Unit test in `runtime/runtime/src/tests/apply.rs`, modeled on `test_add_keys_after_large_read_exceed_receipt_storage_proof_limit`:
1. Force `apply_state.current_protocol_version = 86` (i.e., `EnforcePerReceiptStorageProofLimit.protocol_version()`, which is `< EnforceStorageProofLimitForAllActions.protocol_version()`).
2. Set up an account with hundreds of existing access keys (as in the existing test's `existing_signers`).
3. Build a receipt whose actions are a large number of `DeleteKey` (or `AddKey`/`Stake`) actions targeting/creating keys on that account, sized so that cumulative recorded storage-proof growth is expected to exceed `per_receipt_storage_proof_size_limit` (4MB).
4. Apply the receipt with a trie configured via `recording_reads_new_recorder()`.
5. Assert: `result.status` is `ExecutionStatus::SuccessValue`/no `ReceiptStorageProofSizeExceeded` error, while `trie.recorded_storage_size_upper_bound()` growth for the receipt measurably exceeds `per_receipt_storage_proof_size_limit` — demonstrating the hard cap was silently bypassed at PV 86, in contrast to the same receipt applied at PV 87 where `ActionErrorKind::ReceiptStorageProofSizeExceeded` is correctly raised.
