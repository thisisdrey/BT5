### Title
StackerDB chunk signatures are not bound to the target contract, enabling cross-StackerDB replay of signed chunks - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` — the digest that `StackerDBChunkData::sign`/`verify` operate over — commits only to `slot_id`, `slot_version`, and `data_hash`. It never commits to the StackerDB's `smart_contract_id`. Consequently, a chunk validly signed by an address for slot `S` in StackerDB `A` is indistinguishable, at the signature-verification layer, from a chunk signed for slot `S` in a completely different StackerDB `B`, as long as the same address is registered as the owner of slot `S` in both `A` and `B`. This is the network-layer analog of the "one vault can enter another vault" bug: a scoping flag/parameter (the contract identity) that should gate acceptance is missing from the authenticated payload, so authorization granted in one context is silently accepted in another.

### Finding Description
`SlotMetadata::auth_digest` in `libstackerdb/src/libstackerdb.rs` computes:
```
hasher.update(self.slot_id.to_be_bytes());
hasher.update(self.slot_version.to_be_bytes());
hasher.update(self.data_hash.0);
``` [1](#0-0) 

There is no inclusion of the StackerDB's `QualifiedContractIdentifier` (the `smart_contract_id`) anywhere in the signed material. `sign`/`verify` both operate purely on this digest. [2](#0-1) 

Both the write path (`PeerNetwork::validate_received_chunk`, used for gossip pushes and downloads) and the local write path (`StackerDBTx::try_replace_chunk`, invoked from the `POST /v2/stackerdb/:address/:contract/chunks` handler) resolve the expected signer *per-contract* via `get_slot_signer(smart_contract_id, slot_id)`, then call `slot_metadata.verify(&addr)`:
```
let addr = match self.stackerdbs.get_slot_signer(smart_contract_id, data.slot_id)? { ... };
let slot_metadata = data.get_slot_metadata();
if !slot_metadata.verify(&addr)? { ... }
``` [3](#0-2) 

The RPC handler forwards the client-controlled `contract_identifier` from the URL path straight to `try_replace_chunk`, and the resulting signer/slot lookup and signature check are entirely local to that one contract's config: [4](#0-3) 

Because the *signature itself* never encodes which contract/StackerDB it was produced for, an attacker who observes (via gossip or the public read API) a legitimately signed chunk `(slot_id, slot_version, sig, data)` published to StackerDB `A` can resubmit that exact same tuple to StackerDB `B`'s `POST /v2/stackerdb/.../chunks` endpoint (or replay it over the p2p `StackerDBChunkInv`/`StackerDBPushChunk` gossip path). If the address that signed it also happens to be the registered signer of the same `slot_id` in `B` (a realistic condition in Nakamoto, where the same signer set is frequently reused across multiple cycle-specific StackerDB contracts, e.g. `signers-N-<page>` boot contracts, and slot assignment order for a signer set tends to be stable), the chunk passes `verify()` for `B` even though the signer never authorized that data for `B`. The remaining checks — size, freshness (`slot_version`), and write-count — are all per-`B`-local state and do not prevent this, since they don't validate provenance/context, only version monotonicity. [5](#0-4) 

### Impact Explanation
This breaks the equality "signed by X *for this contract*" vs. "signed by X" — the authentication check verifies the latter but the system relies on the former. The result is an unauthenticated/unauthorized write into a StackerDB replica: content intended for (and only validly signed for) contract `A` can be planted into contract `B`'s slot, and will then be relayed/propagated to other peers replicating `B` as if it were legitimately authored data for `B`. This matches the "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data" impact categories, since accepted chunks are further gossiped via `StackerDBChunkInv`/push-chunk handling to the rest of `B`'s replica set. [6](#0-5) 

### Likelihood Explanation
Exploitability requires only that the same signing address be the registered slot-owner for the same `slot_id` in two different StackerDB contracts — no private key access is needed, since the attacker is replaying an already-observed, validly-signed chunk (chunks are broadcast in cleartext over gossip and readable via the public StackerDB read RPCs). Given that Nakamoto's signer-set StackerDBs are provisioned per reward cycle from the same underlying signer registrations, and slot assignment tends to follow a deterministic order derived from stacking weight/registration, address-to-slot_id collisions across contracts are plausible in practice, making this a realistic, unprivileged, remote attack path rather than a purely theoretical one.

### Recommendation
Bind the target StackerDB's `smart_contract_id` (and ideally a network/consensus-hash context, similar to what `StackerDBPushChunkData::rc_consensus_hash` already provides at the message level) into `SlotMetadata::auth_digest`, e.g.:
```rust
fn auth_digest(&self, contract_id: &QualifiedContractIdentifier) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(contract_id.to_string().as_bytes());
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```
and thread the contract identifier through `sign`/`verify`/`recover_pk` and every call site (`validate_received_chunk`, `try_replace_chunk`, the RPC handler, and StackerDB sync code), so a signature is only valid for the specific StackerDB it was produced for.

### Proof of Concept
1. Configure two StackerDB contracts, `A` and `B`, where address `signer_addr` (controlled by a legitimate signer, not the attacker) is registered as the owner of `slot_id = 0` in both `A` and `B` (a realistic setup when the same signer set is reused across cycle-specific contracts).
2. `signer_addr` legitimately signs and publishes chunk `data = D`, `slot_version = 1` to `A` (either via the RPC `POST /v2/stackerdb/<signer_addr>/A/chunks` or via p2p gossip). This chunk is broadcast in cleartext to `A`'s replica set and is readable by anyone via `GET /v2/stackerdb/<signer_addr>/A/chunks/0`.
3. Attacker (who has no key material) copies the tuple `(slot_id=0, slot_version=1, sig, data=D)` and submits it to `B`'s endpoint `POST /v2/stackerdb/<signer_addr>/B/chunks`.
4. `try_replace_chunk`/`validate_received_chunk` for `B` looks up `get_slot_signer(B, 0) == signer_addr`, then calls `slot_metadata.verify(&signer_addr)`, which succeeds because `auth_digest` never included the contract id — the check passes exactly as it would for `A`. [3](#0-2) 
5. Chunk `D` (which the signer never authorized for `B`) is stored as slot 0's authoritative content in `B` and propagated to `B`'s replica peers.

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
