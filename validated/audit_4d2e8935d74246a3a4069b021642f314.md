### Title
Delegating away frozen balance does not checkpoint rewards or invalidate stale votes, allowing an account to keep earning voting rewards for TronPower it no longer holds - (File: `actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java`)

### Summary
`DelegateResourceActuator`/`UnDelegateResourceActuator` (and their TVM equivalents `DelegateResourceProcessor`/`UnDelegateResourceProcessor`) move an account's `FrozenV2Balance` into `DelegatedFrozenV2Balance` — directly reducing the TronPower that is supposed to back that account's existing votes — but never checkpoint the account's vote-reward accounting (`mortgageService.withdrawReward` / `VoteRewardUtil.withdrawReward`) and never re-validate/clear votes that now exceed the remaining TronPower. This mirrors the reported `_seize()` bug class: a balance-moving operation that fails to checkpoint the accrual index of the value being moved, letting the moved-from party keep earning yield/reward it no longer legitimately backs.

### Finding Description
Vote rewards in java-tron accrue per cycle based on a *snapshot* of `accountCapsule.getVotesList()` taken by `withdrawReward()` (`chainbase/.../MortgageService.java` and `actuator/.../vm/utils/VoteRewardUtil.java`). Any code path that changes the TronPower backing an account's votes is expected to (a) checkpoint the reward via `withdrawReward` before mutating balances, and (b) invalidate stale votes if the account can no longer back its vote count.

This pattern is followed by `UnfreezeBalanceActuator.execute()` and `UnfreezeBalanceV2Actuator.execute()`, which both call `mortgageService.withdrawReward(ownerAddress)` / `mortgageService.withdrawReward` before reducing frozen balance: [1](#0-0) [2](#0-1) 

The V2 unfreeze path additionally re-checks whether the account's TronPower still covers its cast votes, and clears the votes if not, via `updateVote`, and the TVM `UnfreezeBalanceProcessor` explicitly clears votes when `tronPower < usedTronPower`: [3](#0-2) 

`VoteWitnessActuator`/`VoteWitnessProcessor` also always checkpoint reward first and bound new votes by current TronPower: [4](#0-3) [5](#0-4) 

By contrast, `DelegateResourceActuator.execute()` moves balance from `FrozenBalanceForBandwidthV2`/`FrozenBalanceForEnergyV2` into `DelegatedFrozenV2Balance` (reducing the owner's TronPower-backing balance) with **no call to `withdrawReward`** and **no check against the owner's existing `votesList`**: [6](#0-5) 

The same omission exists in the TVM native-contract equivalent `DelegateResourceProcessor.execute()`: [7](#0-6) 

`UnDelegateResourceActuator`/`UnDelegateResourceProcessor` restore balance to the owner (`addFrozenBalanceForBandwidthV2`/`EnergyV2`) but likewise never checkpoint reward or re-validate votes for the owner: [8](#0-7) [9](#0-8) 

Because the reward computation used by `withdrawReward` relies purely on the previously stored vote snapshot (`accountVote`) for each cycle rather than re-checking current TronPower at reward time, an account whose backing TronPower has been reduced via delegation continues to be paid rewards computed from a vote snapshot taken before the delegation. This directly parallels the reported bug: the "seize"-equivalent operation (delegating away the stake) does not checkpoint the account's yield-accrual state (vote reward begin/end cycle, or vote invalidation) before shrinking the balance backing it.

### Impact Explanation
An account can freeze balance, cast votes with full TronPower, then delegate that frozen balance away to another address (still receiving delegation "rent"/benefits or simply parking it), while its stale vote snapshot keeps earning witness voting rewards it no longer economically backs. Since reward payouts come from the shared reward pool (`DelegationStore.addReward`), this allows extracting more reward than the account's real staked value justifies, at the expense of other voters/reward pool — a fund-theft class issue, matching the "drain the interest market" impact of the original report, scaled to the TRON voting-reward pool.

### Likelihood Explanation
Reachable by any unprivileged, signed `DelegateResourceContract`/`UnDelegateResourceContract` transaction, or the corresponding TVM native contract call from a smart contract — no special privilege needed. The actuators explicitly validate the transaction and are part of the normal user-facing resource delegation feature (introduced with Stake 2.0), so this path is exercised by all delegation transactions on mainnet.

### Recommendation
In `DelegateResourceActuator.execute()`/`DelegateResourceProcessor.execute()` and `UnDelegateResourceActuator.execute()`/`UnDelegateResourceProcessor.execute()`, call `mortgageService.withdrawReward(ownerAddress)` (or `VoteRewardUtil.withdrawReward` in the TVM path) before mutating the owner's frozen/delegated balances, mirroring `UnfreezeBalanceV2Actuator`. Additionally, after reducing the owner's TronPower-backing balance, check whether `accountCapsule.getTronPower()` (or `getAllTronPower()`) still covers the sum of the owner's `votesList`, and clear/invalidate the votes exactly as `UnfreezeBalanceV2Processor`/`UnfreezeBalanceProcessor` do, to prevent stale over-committed votes from continuing to earn rewards after the backing stake has been delegated away.

### Proof of Concept
Conceptual reproduction (analogous to the report's POC), pending live-node validation:
1. Freeze balance for BANDWIDTH/ENERGY to obtain TronPower.
2. Vote for a witness using the full TronPower (`VoteWitnessContract`), which checkpoints reward via `withdrawReward` and snapshots `votesList`.
3. Immediately submit `DelegateResourceContract` to delegate the same frozen balance to another address (`DelegateResourceActuator.execute`), which reduces `FrozenV2BalanceForBandwidth/Energy` without calling `withdrawReward` or clearing votes.
4. Wait for one or more reward cycles and call `WithdrawBalanceActuator`/`withdrawReward()`; reward is computed from the still-intact `votesList` snapshot from step 2, even though the account's real backing TronPower has been moved away in step 3.
5. Repeat delegate/undelegate cycles across many addresses to compound reward extraction beyond what any single stake should earn.

Note: I was unable to fully trace `AccountCapsule.getTronPower()`/`getAllTronPower()`'s exact interplay with `DelegatedFrozenV2Balance` before running out of tool budget, so the precise numeric magnitude of extractable reward per cycle is not confirmed here — the structural gap (missing `withdrawReward` + missing vote-invalidation check in the Delegate/UnDelegate actuators, present everywhere else votes/TronPower are touched) is confirmed by direct code comparison.
