### Title
UpdateBrokerageActuator allows an SR to change its reward-cut ("fee") for the currently running cycle, retroactively affecting already-accrued voter rewards - (File: actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java)

### Summary
`UpdateBrokerageActuator` is the java-tron analog of `BribeVault.setFee` — it lets an account (a witness) set the percentage cut ("brokerage") it takes from block/transaction-fee rewards before the remainder is distributed to voters. As with the reported `setFee` issue, the value can be pushed up to 100% instantly, applies to reward accounting for value that voters have already accrued in the currently active cycle (analogous to "already-settled deposits"), and there is no timelock preventing a witness from changing it right before reward distribution.

### Finding Description
`UpdateBrokerageActuator.execute` unpacks `UpdateBrokerageContract` and stores the new brokerage percentage via `delegationStore.setBrokerage(ownerAddress, brokerage)`: [1](#0-0) 

`validate()` only bounds the value to `[0, 100]` (`ActuatorConstant.ONE_HUNDRED`) — i.e. a witness can set their cut to 100%, taking the entire reward and leaving voters nothing: [2](#0-1) 

`setBrokerage(address, brokerage)` is a convenience wrapper that writes the value keyed under a special sentinel `cycle = -1` ("pending" value): [3](#0-2) 

This pending value is only rolled forward into the *next* cycle's key during `MaintenanceManager.doMaintenance()`: [4](#0-3) 

However, `MortgageService.payReward` reads the brokerage for the **current, already-in-progress** cycle every time a block/transaction-fee reward is paid: [5](#0-4) 

`getBrokerage(cycle, address)` falls back to `DEFAULT_BROKERAGE` (20%) only if no value exists for that exact `cycle` key; once `doMaintenance` has copied the pending (`-1`) value into `nextCycle`'s key for a witness, that per-cycle key stays fixed for the remainder of the cycle: [6](#0-5) 

Because the current cycle's brokerage percentage was set at the immediately preceding maintenance boundary from whatever value the SR most recently pushed to `UpdateBrokerageContract`, a witness can broadcast an `UpdateBrokerageContract` transaction to change its cut at any time up until the maintenance boundary (cycle rollover), and that new cut is then applied uniformly to **all** reward accrual for the entire following cycle — including rewards computed via VI-delta math over voting periods that already started before the change, and the value transacted through `MortgageService.computeReward`/`VoteRewardUtil.computeReward`, which compute reward using `deltaVi` accumulated across cycles without regard to when voters actually cast their votes: [7](#0-6) 

This mirrors all three concerns from the `BribeVault.setFee` report:
1. No meaningful upper bound below 100% is enforced (only `[0,100]`).
2. The parameter can be changed and takes effect for reward periods that voters have already begun accruing rewards in (their vote was cast, and Vi/reward math for the cycle boundary was already set up), analogous to changing fees on already-deposited funds.
3. There is no timelock — an SR can broadcast `UpdateBrokerageContract` right up to the maintenance boundary to "frontrun" the next reward cycle's payout calculation, disadvantaging voters who cannot react in time since votes/reward accrual for the cycle are already locked in via `VoteRewardUtil`/`MortgageService` cycle bookkeeping.

### Impact Explanation
Voters who have staked (frozen TRX) and voted for a witness earn rewards proportional to their vote share, minus the witness's brokerage cut. A malicious or careless witness can raise its brokerage to 100% right before a cycle rollover, capturing the entire reward pool for that cycle and leaving voters with zero return despite already having committed their vote/stake for that period. This is a fund-siphoning / unauthorized value-extraction issue directly affecting funds that would otherwise be paid to voters (`accountCapsule.getAllowance()`), reachable purely by an unprivileged (but SR) account submitting a signed `UpdateBrokerageContract` transaction — no special node privilege is required beyond being a registered witness, and voters have no on-chain guardrail (no cap below 100%, no delay) protecting their expected reward share.

### Likelihood Explanation
Any active witness (there is no super-admin-only gate — just `WitnessStore.get(ownerAddress) != null`) can submit this transaction at will via the public `/wallet/updateBrokerage` HTTP endpoint or the equivalent gRPC/TVM path, at any time and at negligible cost (`calcFee()` returns `0`), making this trivially and repeatedly exploitable each cycle. [8](#0-7) 

### Recommendation
- Lower the maximum allowed brokerage value well below 100% (e.g., a governance-configurable cap), so an SR cannot ever claim voters' entire reward.
- Apply brokerage changes with a delay of at least one full cycle beyond the next rollover (e.g., require the change to only take effect two maintenance cycles later) so voters have visibility and time to react (unvote) before the new rate is enforced.
- Consider capturing and emitting an event/log on brokerage changes so wallets/voters can be notified promptly.

### Proof of Concept
1. Attacker controls a witness account `W` that currently has many voters and a brokerage of 20% (default).
2. Attacker sends `UpdateBrokerageContract{owner_address: W, brokerage: 100}` (validated only against `[0,100]`) via `/wallet/updateBrokerage`, right before the next maintenance/cycle boundary. [2](#0-1) 
3. At the next `doMaintenance()` call, this pending (`cycle=-1`) value 100 is copied into `nextCycle`'s brokerage key for `W`. [4](#0-3) 
4. For the entirety of the next cycle, every `payReward` call for `W` computes `brokerageAmount = value` (100%), so `value -= brokerageAmount` leaves `0` credited to `delegationStore.addReward`. [5](#0-4) 
5. Voters who voted for `W` prior to this change receive zero reward for that cycle when they call `withdrawReward`/`queryReward`, despite having already locked their TRX and cast their vote for that period.

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
