### Title
Frontrunning partial liquidation DoSes full/near-full liquidations via underflow and debt-floor revert - ([File: contracts/Pool.sol])

### Summary
`Pool.liquidate` requires the liquidator to specify an exact `amountToRepay_`, which is then burned from the account's `DebtToken` balance. An unprivileged attacker (including a second address of the liquidated user) can frontrun a liquidator's transaction with a tiny partial liquidation, shrinking the account's debt balance so that the liquidator's precomputed `amountToRepay_` exceeds the remaining balance and reverts inside `_debtToken.burn(account_, amountToRepay_)` (arithmetic underflow / burn-exceeds-balance). Additionally, the `debtFloorInUsd` check makes the griefing cheaper: an attacker can leave the account's debt just above the floor, so that the liquidator's planned repayment lands the remainder inside `(0, debtFloorInUsd)` and reverts with `RemainingDebtIsLowerThanTheFloor`.

### Finding Description
In `Pool.liquidate` (contracts/Pool.sol:537-596):

- `amountToRepay_` is an exact amount chosen at tx-build time; liquidators use `quoteLiquidateMax` (lines 419-440) which computes the cap from the *current* `debtToken.balanceOf(account_)` at line 435.
- The only upper-bound checks are `amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable` (line 567) and the debt-floor check (lines 571-579). Nothing caps `amountToRepay_` to the actual remaining balance.
- `_debtToken.burn(account_, amountToRepay_)` at line 588 subtracts the amount from the account's debt balance, so any `amountToRepay_ > balance` reverts.

Attack trace (all unprivileged, public entry point):

1. Alice's position is unhealthy; debt = `D`, collateral sufficient.
2. Bob calls `quoteLiquidateMax(synth, alice, depositToken)` and sends `liquidate(synth, alice, maxAmount, depositToken)`.
3. Attacker (any healthy EOA holding the synth, possibly Alice's second account — `CanNotLiquidateOwnPosition` only checks `_msgSender == account_`) frontruns with `liquidate(synth, alice, dust, depositToken)`. The attacker's tx passes the `maxLiquidable` cap (dust is small) and the floor check (it leaves debt ≥ floor, or floor is 0).
4. Bob's tx now executes with `_debtTokenBalance < amountToRepay_`; `burn` reverts → full liquidation blocked.
5. Variant: if `debtFloorInUsd > 0`, attacker frontruns leaving debt at `floor + ε`. Any liquidation that doesn't repay the entire balance reverts at lines 571-578, and the forced full repay is then itself frontrunnable per step 3 — a self-reinforcing DoS loop. Repeating the attack leaves permanently uncleansable dust debt just above the floor.

The attacker only needs a healthy position and a small amount of the synthetic token (obtainable by minting against their own collateral or via `Pool.swap`); `whenNotShutdown`, `nonReentrant`, and the token-existence modifiers do not stop this.

### Impact Explanation
Liquidations are the protocol's solvency mechanism. Blocking full liquidation forces liquidators into smaller, less efficient partial liquidations, leaves dust debt positions that can never be fully cleared (especially when `debtFloorInUsd > 0`, where the remainder cannot be partially repaid at all), and lets the liquidated user (via a second address) protect their collateral bonus. Underwater positions can persist longer than intended, threatening protocol solvency — a liveness/DoS impact on the liquidation path.

### Likelihood Explanation
Anyone holding the synthetic token can perform the frontrun; the cost is a dust-sized repayment plus gas, and on public mempools (Ethereum mainnet deployment exists) the liquidation tx is visible before execution. No privileged role, oracle manipulation, or governance action is required. Note that if `maxLiquidable < 1e18`, "full" liquidation is already capped, but the attack still applies to the maximum allowed repayment, and can be repeated on every retry.

### Recommendation
Allow `amountToRepay_ == type(uint256).max` (or add an `isFullLiquidation` flag) and resolve it to the account's current debt balance inside `liquidate` after `accrueInterest()`, e.g.:

```solidity
if (amountToRepay_ == type(uint256).max) {
    amountToRepay_ = _debtToken.balanceOf(account_);
}
```

applied before the `maxLiquidable`/floor checks, and skip the debt-floor check when the entire remaining debt is repaid.

### Proof of Concept
Foundry-style reproduction against deployed pool proxies (same structure as the source report's PoC):

```solidity
function testLiquidationDoS() public {
    // alice is unhealthy: debt = 5500 msUSD backed by $10000 collateral
    // attacker is a healthy account holding some msUSD
    // bob is a liquidator

    uint256 max = pool.quoteLiquidateMax(msUSD, alice, msUSDDepositToken);

    // 1. attacker frontruns bob, repays 2000 wei of debt
    vm.prank(attacker);
    pool.liquidate(msUSD, alice, 2000, msUSDDepositToken);

    // 2. bob's tx reverts: amountToRepay_ > remaining debt balance -> underflow in DebtToken.burn
    vm.expectRevert(); // arithmetic underflow
    vm.prank(bob);
    pool.liquidate(msUSD, alice, max, msUSDDepositToken);
}
```

Debt-floor variant: attacker repays down to `floor + ε`; bob's tx reverts with `RemainingDebtIsLowerThanTheFloor` at contracts/Pool.sol:577 unless he repays 100% — which is itself frontrunnable as above.

Caveat: I could not open `DebtToken.sol` within the iteration budget to quote the exact revert in `burn`, but any conforming debt-token burn that decrements the account's principal/balance by `amountToRepay_` necessarily reverts when the amount exceeds the balance; the revert point may alternatively be the `wadDiv`/quote paths, which equally produces a revert of the liquidator's transaction.
