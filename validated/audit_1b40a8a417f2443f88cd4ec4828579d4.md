### Title
Argument/scheme injection into locally-spawned `git` process via an untrusted `remote` field in `git_repository` sources — ([File: tools/build_defs/repo/git_worker.bzl])

### Summary
`git_repository` (and Bazel-module sources declared with `"type": "git_repository"` in a registry's `source.json`) forwards the `remote` string directly, unsanitized, into a locally-executed `git` subprocess as a positional command-line argument. Unlike the `archive` source type, which is bound by a mandatory `integrity`/sha256 checksum, the `git_repository` source type has no integrity check on the `remote` field at all — it is simply "directly forwarded to the underlying `git_repository` repo rule". This mirrors the analog CVE class: an untrusted, remote-supplied string reaches a locally spawned process's argument vector unvalidated, letting the origin of that string dictate command behavior on the developer/CI machine.

### Finding Description
In `tools/build_defs/repo/git_worker.bzl`, the git worker builds `_GitRepoInfo.remote = str(ctx.attr.remote)` and immediately uses it as a literal CLI argument: [1](#0-0) [2](#0-1) 

`add_origin` calls `_git(ctx, git_repo, "remote", "add", "origin", remote)`, which is executed by `_execute` as:
```
git -c core.fsmonitor=false remote add origin <remote>
``` [3](#0-2) 

No scheme allowlist, no `--` separator before the value, and no length/character validation is applied to `remote` anywhere in `git.bzl` or `git_worker.bzl`. Because the value is handed to `git` exactly as a "user-supplied" URL argument (the same trust class as a URL typed directly on a command line), Git's own remote-helper mechanism will honor transport-helper syntax such as `ext::<command>` or `fd::` under the default `protocol.*.allow=user` policy, since the value did not arrive via an untrusted redirect/`.gitmodules` channel but as a first-class CLI argument. An attacker who controls this string can therefore make Git invoke an arbitrary local command when the repo is fetched (`git fetch origin` reads the configured remote URL and dispatches to the corresponding transport/helper).

The `remote` field reaches this path from two attacker-influenceable origins in the module system:
1. A registry (added via `--registry` or a compromised/malicious mirror of a registry the victim's `MODULE.bazel` depends on) can serve a `source.json` with `"type": "git_repository"` whose `remote` field is forwarded verbatim to the repo rule — the registry docs explicitly state these fields (`remote`, `commit`, `shallow_since`, `tag`, ...) "are directly forwarded to the underlying `git_repository` repo rule." [4](#0-3) 
2. The test helper `createGitRepoModule` in the Bazel test suite demonstrates exactly this shape of `source.json`, confirming the field is a first-class, unauthenticated datum forwarded from registry content to the repo rule. [5](#0-4) 

Critically, while the `archive` source type is bound by a mandatory `integrity` (SHA-256/SRI) field that Bazel verifies before trusting downloaded bytes, the `git_repository` source type carries **no such integrity binding on `remote`** — only `commit` is pinned, and the pinned commit hash does nothing to constrain the URL/scheme used to reach it. This is the exact invariant break analogous to the CVE: a value that should be constrained by a checksum or an allow-listed protocol set is instead passed straight through to a locally spawned process's argument list.

### Impact Explanation
If a registry (including a third-party or compromised mirror a user has opted into via `--registry`) serves a `source.json` of `type: git_repository` with a `remote` value like `ext::sh -c "id > /tmp/pwned"`, then on `bazel build`/`bazel fetch`, Bazel's repo-rule machinery will run `git remote add origin ext::sh -c "id > /tmp/pwned"` followed by `git fetch origin`, causing Git to execute the attacker-chosen shell command as the user running Bazel. This is local command execution on the developer/CI workstation, driven entirely by content served by an external, non-root-repo source — directly analogous to the BOSH CLI CVE where a compromised Director could inject SSH options into a locally-spawned `ssh` process.

### Likelihood Explanation
Exploitation requires only that the victim's Bazel invocation resolves a module via a registry serving (or redirected/mirrored to serve) a `git_repository`-typed `source.json` with an attacker-controlled `remote` value — no access to the victim's machine, credentials, or root-repo `.bzl`/`MODULE.bazel` files is needed, satisfying the "hostile registry" threat model. This is a first-fetch scenario (no separate integrity check exists to block it), so it triggers on the very first `bazel build`/`fetch` that resolves the malicious module version.

### Recommendation
- Require/enforce an allowed-scheme list (e.g., `http(s)://`, `git://`, `ssh://`, `file://`) for the `remote` attribute of `git_repository`/`new_git_repository`, rejecting values containing `::` transport-helper syntax or leading `-`.
- Reject `remote` values in registry-supplied `source.json` of type `git_repository` unless they match the allow-list, and treat this as untrusted, non-command-line input rather than passing it through unchanged to `_git`.
- Consider prefixing positional URL/ref arguments passed to `git` with `--` (Bazel already does this for `fetch`'s ref args) to prevent option-style parsing, and explicitly set `GIT_ALLOW_PROTOCOL`/`protocol.allow=never` defaults for the invoked `git` process, only re-enabling protocols actually required.

### Proof of Concept
1. Set up a local registry serving a module version with `source.json`:
```json
{
  "type": "git_repository",
  "remote": "ext::sh -c \"touch /tmp/pwned\""
}
```
(mirrors the pattern used by `createGitRepoModule` in `src/test/py/bazel/bzlmod/test_utils.py`) [5](#0-4) 
2. Add this registry via `--registry=file://<path>` (or have the victim's existing `--registry` mirror serve this content).
3. Declare a `bazel_dep` on that module in `MODULE.bazel` and run `bazel build @that_module//...`.
4. Bazel's repo-rule machinery invokes `git remote add origin ext::sh -c "touch /tmp/pwned"` then `git fetch origin` via `tools/build_defs/repo/git_worker.bzl`'s `add_origin`/`fetch`, causing `/tmp/pwned` to be created on the victim's machine, demonstrating local command execution driven by unauthenticated registry content. def _execute(ctx, git_repo, args):
    # "core.fsmonitor=false" disables git from spawning a file system monitor which can cause hangs when cloning a lot.
    # See https://github.com/bazelbuild/bazel/issues/21438
    start = ["git", "-c", "core.fsmonitor=false"]
    return ctx.execute(
        start + args,
        environment = ctx.os.environ | _GIT_LOCAL_ENV_VARS,
        working_directory = str(git_repo.directory),
    )
