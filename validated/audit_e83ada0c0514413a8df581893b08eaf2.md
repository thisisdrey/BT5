### Title
Unbounded per-message validation compute in `handle_unsolicited_stacks_messages` bypasses the StackerDB buffer quota - (File: stackslib/src/net/unsolicited.rs)

### Summary
`handle_unsolicited_stacks_messages` runs `handle_unsolicited_stacks_message` (which for `StackerDBPushChunk` payloads triggers full signature-recovery/DB-lookup validation) unconditionally for **every** message already present in a peer's inbox, before ever consulting `can_buffer_data_message`. The buffer-quota check (`can_buffer_data_message`, `max_buffered_stackerdb_chunks`) is only consulted afterward, to decide whether a message that still needs re-validation later should be persisted in `self.pending_messages` — it does not gate how many messages get *validated* in a single pass.

### Finding Description
In `stackslib/src/net/unsolicited.rs`, `handle_unsolicited_stacks_messages` (line 714) iterates `inbox.messages` and for each one unconditionally calls:
```rust
let (to_buffer, relay) = self.handle_unsolicited_stacks_message(
    chainstate, *event_id, &message.preamble, &message.payload, buffer,
);
if buffer && to_buffer {
    self.buffer_stacks_data_message(*event_id, neighbor_key, message.clone());
    return false;
}
``` [1](#0-0) 

The quota check `can_buffer_data_message` (line 94) is only invoked inside `buffer_stacks_data_message` (line 166), i.e. *after* `handle_unsolicited_stacks_message` has already run and returned `to_buffer == true`. [2](#0-1) 

For `StackerDBPushChunk` payloads, `handle_unsolicited_stacks_message` dispatches into `handle_unsolicited_StackerDBPushChunk`, which calls `validate_received_chunk` in `stackslib/src/net/stackerdb/mod.rs` to check the chunk's signature and metadata against the StackerDB config before deciding whether to accept, buffer, or drop it. Messages that fail validation (e.g., wrong signer key, as in `test_handle_unsolicited_stackerdb_push_chunk_future_view_validation`) return `(false, false)` and are simply dropped, without ever reaching `can_buffer_data_message` or occupying a buffer slot — but the full validation work (signature recovery, DB/config lookups) is still performed. This means the buffer-quota mechanism, which is intended to bound resource consumption per connection, does not bound the number of `validate_received_chunk` calls incurred by a burst of always-invalid messages placed into a single inbox before this function runs.

### Impact Explanation
An authenticated peer (any remote party who completes the P2P handshake — no privileged secret or role required) can craft a burst of `StackerDBPushChunk` messages that are cheap to construct but each force the node to perform a full signature-recovery and StackerDB-config lookup, then get discarded. Because the buffer quota is only enforced on the "should I persist this for later" path and not on the "should I validate this at all" path, the amount of CPU work done per inbox-processing pass scales with however many such messages the attacker manages to get accumulated in `inbox.messages` for that event/peer, not with `max_buffered_stackerdb_chunks`. This is a bounded-compute DoS confined to processing of a single peer connection's inbox, consistent with a High-severity "bounded compute DoS" finding, repeatable indefinitely by re-sending bursts.

### Likelihood Explanation
Preconditions: attacker only needs to be an authenticated P2P peer (`check_peer_authenticated`, line 56, requires a completed handshake, which is available to any unprivileged remote party who can connect and complete the protocol handshake — not a privileged secret). Attacker cost is minimal: constructing `StackerDBPushChunk` messages with syntactically valid but cryptographically wrong signer data is cheap, while the receiving node pays the cost of signature recovery and lookups per message. The attack is remotely reachable via the P2P port and repeatable on every processing cycle.

### Recommendation
Enforce a per-inbox/per-peer cap on the number of `StackerDBPushChunk` (and `NakamotoBlocks`) messages processed by `handle_unsolicited_stacks_message` in a single call, independent of whether they end up being buffered — i.e., check `can_buffer_data_message`-equivalent limits (or a dedicated "messages processed this pass" counter) *before* invoking validation, not only before persisting to `pending_messages`. Alternatively, perform a cheap pre-check (e.g., basic structural sanity or rate-limiting per neighbor) before invoking `validate_received_chunk`'s expensive signature-recovery path.

### Proof of Concept
Extend the existing `test_handle_unsolicited_stackerdb_push_chunk_future_view_validation`-style test in `stackslib/src/net/stackerdb/tests/sync.rs` / `stackslib/src/net/tests/relay/nakamoto.rs`:
1. Construct N `StacksMessage`s with `StackerDBPushChunkData` payloads, each signed with a random (wrong) private key, all directed at the same `event_id`/`neighbor_key`, with N > `connection_opts.max_buffered_stackerdb_chunks`.
2. Insert them all into a single `PendingMessagesFrom.messages` inbox (simulating them having arrived in the same batch, e.g. via a single `StacksHttpRecvStream`/socket read prior to invoking the handler).
3. Call `peer.network.handle_unsolicited_stacks_messages(&mut chainstate, unsolicited, true)`.
4. Instrument/assert (via a counter or timing) that `validate_received_chunk` is invoked N times (not capped at `max_buffered_stackerdb_chunks`), while confirming via `self.pending_messages` that far fewer (or zero) chunks were actually buffered — demonstrating validation compute is not bounded by the buffer quota.

Note: I could not fully retrieve the internals of `validate_received_chunk`/`handle_unsolicited_StackerDBPushChunk` in this session (tool budget exhausted) to confirm the exact cost of each failed-validation branch (e.g., confirming signature recovery specifically occurs before the `(false,false)` return in every rejection branch); this should be verified against `stackslib/src/net/stackerdb/mod.rs` before finalizing severity.
