The bug class is an index used beyond the bounds/valid range of the data it indexes. The strongest Metronome analog is the reward-account index fallback in `RewardsDistributor._calculateTokenDelta`, which fails to initialize `accountIndexOf` when the global index is exactly `INITIAL_INDEX`, crediting a user's entire token balance as accrued rewards.

### Title
Missing account-index initialization when `tokenIndex == INITIAL_INDEX` lets an attacker claim rewards equal to their full balance - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`_calculateTokenDelta` only substitutes `INITIAL_INDEX` for an unset `accountIndexOf` when the global token index is **greater than** `INITIAL_INDEX`. When the index equals `INITIAL_INDEX` — which is the case during the entire block in which a token is first registered via `updateTokenSpeed`/`syncTokenSpeed` — an account with no stored index computes `_deltaIndex = INITIAL_INDEX - 0 = 1e18`, accruing `balanceOf(account).wadMul(1e18) = balanceOf(account)` as claimable reward tokens.

### Finding Description [1](#0-0) 

```solidity
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

A token's state is initialized to `{index: INITIAL_INDEX, timestamp: block.timestamp}` the first time a non-zero speed is set [2](#0-1) . Until `block.timestamp` advances past that timestamp, `_updateTokenIndex` cannot raise the index (both branches of `_calculateTokenIndex` require `_deltaTimestamps > 0`) [3](#0-2) . So within that block `_tokenIndex == INITIAL_INDEX` exactly, the `> INITIAL_INDEX` guard is false, and a never-indexed account gets `_tokensDelta = balance * 1e18 / 1e18 = balance`.

The accrual is reachable from public entry points with no privilege:

- `claimRewards(address[] accounts_, IERC20[] tokens_)` — `nonReentrant` only, no caller/accounts relationship check [4](#0-3) 
- `updateBeforeMintOrBurn(token, account)` / `updateBeforeTransfer` — callable by anyone [5](#0-4) 
- Payout is immediate: `_transferRewardIfEnoughTokens` transfers the whole `tokensAccruedOf[account]` to `account` whenever the distributor's reward-token balance covers it [6](#0-5) 

### Impact Explanation
An attacker who already holds a DepositToken/DebtToken balance (deposits/borrows in a prior block) can, in the same block the governor or `tokenSpeedKeeper` registers a new reward token, call `claimRewards(attacker, [token])` and have `tokensAccruedOf[attacker]` set to their entire token balance. Since DepositToken balances reflect deposited underlying, a large deposit converts directly into reward-token payout up to the distributor's full balance. This is theft of unclaimed yield belonging to all other users of the distributor — the reward pool is drained by an index bookkeeping error, not by earned accrual.

### Likelihood Explanation
Requires no privilege: the attacker front-runs or bundles after `updateTokenSpeed` (or a `syncTokenSpeed` first-registration call) in the same block. With Flashbots/private orderflow, landing in the same block as a governance transaction is realistic; the only other cost is holding a DepositToken/DebtToken balance, which can be flash-sized via ordinary deposits since rewards don't check deposit duration. Reward is bounded by `rewardToken.balanceOf(distributor)`, which for a newly-enabled reward token is typically the full funded amount.

### Recommendation
Change the fallback to initialize the account index whenever it is unset and the global index is at least `INITIAL_INDEX`:

```solidity
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX; // or _tokenIndex
}
```

Equivalently, set `_accountIndex = _tokenIndex` when `_accountIndex == 0`, which is safe for all index values and removes the boundary condition entirely.

### Proof of Concept
Hardhat/fork sketch:

```ts
// Attacker deposits collateral in an earlier block and holds msDEPOSIT balance.
await depositToken.deposit(amount); // via Pool, block N

// Block M: governor enables rewards for the deposit token.
await rewardsDistributor.connect(governor).updateTokenSpeed(depositToken.address, speed);
// tokenStates[depositToken] = {index: 1e18, timestamp: block.timestamp(M)}

// Same block M (attacker tx, e.g., via flashbots bundle):
await rewardsDistributor.claimRewards(attacker.address, [depositToken.address]);
// _calculateTokenDelta: _accountIndex=0, _tokenIndex=1e18 (not > INITIAL_INDEX)
//   -> _deltaIndex = 1e18 -> _tokensDelta = depositToken.balanceOf(attacker)
// tokensAccruedOf[attacker] = attackerBalance; paid out immediately
expect(await rewardToken.balanceOf(attacker.address)).to.equal(attackerDepositBalance);
```

Alternatively the same accrual is triggered with no claim call at all: `updateBeforeMintOrBurn(depositToken, attacker)` in block M writes the inflated `tokensAccruedOf`, and any later `claimRewards` pays it out.
