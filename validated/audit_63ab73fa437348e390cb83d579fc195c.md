## Finding

Java-tron's `MasterChef`-style delegation reward mechanism (Stake 2.0 vote rewards) contains the same "reward accrual with zero denominator gets silently discarded" bug as the Tokemak report, in `DelegationStore.accumulateWitnessVi` / `MaintenanceManager.doMaintenance`.

### Title
Vote rewards paid to a witness with zero total votes are permanently lost/frozen - (File: `chainbase/src/main/java/org/tron/core/store/DelegationStore.java`)

### Summary
java-tron's Stake 2.0 delegation reward system uses a `Vi` (value-per-vote) accumulator identical in design to the reported `rewardPerToken()` MasterChef pattern: `Vi` is only incremented proportionally to `reward / voteCount`, and if `voteCount == 0` for a witness in a given cycle, the `Vi` update is skipped while the reward that was already credited to that witness/cycle is never redistributed anywhere else.

### Finding Description
Each cycle, `MaintenanceManager.doMaintenance()` iterates over all witnesses and calls `delegationStore.accumulateWitnessVi(curCycle, witness.createDbKey(), witness.getVoteCount())` [1](#0-0) . That method is the exact analog of the vulnerable `rewardPerToken()`:

```java
public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      ...
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
}
``` [2](#0-1) 

When `voteCount == 0` (the exact equivalent of `totalSupply() == 0` in the report), the branch simply "forwards" the previous `Vi` value and does **not** distribute the `reward` that was already accumulated for that cycle via `delegationStore.addReward(cycle, witnessAddress, value)` in `MortgageService.payReward` [3](#0-2) . Since `Vi` is the sole mechanism by which voters later compute their claimable share (`computeReward` subtracts `beginVi` from `endVi` and multiplies by the voter's vote count) [4](#0-3) , any reward credited while `voteCount == 0` becomes permanently unclaimable — nobody's `Vi` delta ever reflects it, and there is no other bookkeeping to reclaim it.

This state (`voteCount == 0` for an *active, block-producing* witness) is directly reachable by unprivileged users: a witness's `WitnessCapsule.getVoteCount()` and the active witness set are only refreshed once per cycle at `doMaintenance()` via `countVote()` [5](#0-4) . In between maintenance cycles, ordinary account holders can broadcast `UnfreezeBalanceV2Contract` (or `UnfreezeBalanceContract`) transactions that clear all of an account's votes, e.g. via `updateVote()` in `UnfreezeBalanceV2Actuator` / `UnfreezeBalanceV2Processor`, which calls `accountCapsule.clearVotes()` [6](#0-5) . If the last remaining voter(s) for a witness unfreeze/unvote mid-cycle, that witness's live vote count in `WitnessStore` drops to (or already was) 0, while it is still scheduled and continues to earn `payBlockReward`/`payTransactionFeeReward` for the remainder of the cycle (these are invoked from `Manager` during block application, independent of the live vote count). At the next `doMaintenance()`, `accumulateWitnessVi` sees `voteCount == 0` for that witness/cycle and drops the accrued reward.

### Impact Explanation
TRX credited via `delegationStore.addReward()` for a witness with zero live votes in that cycle can never be claimed by any account, because the `Vi` accumulator (the only mechanism voters use to compute owed rewards) is never incremented for that cycle. This is a permanent freezing/loss of minted block-reward and transaction-fee TRX — funds that should have gone either to voters or been otherwise accounted for are stuck unclaimed in the delegation reward bookkeeping.

### Likelihood Explanation
Reachable purely by unprivileged transactions: any voter can submit `UnfreezeBalanceV2Contract`/`UnfreezeBalanceContract` to clear votes for a witness they voted for. Because the active-witness/vote-count snapshot used for reward attribution is only refreshed once per cycle, there is a window in every cycle in which a witness can be actively producing blocks (and earning rewards) with zero currently-registered votes — this does not require any malicious SR/witness/peer behavior, only ordinary account actions timed relative to the maintenance cycle boundary.

### Recommendation
When accruing reward for a cycle where `voteCount == 0`, either (a) refuse to add further reward to a witness with zero votes at the time of `payReward`, or (b) redirect/burn/roll-over the un-distributable cycle reward explicitly (e.g., forward it into the next cycle's reward pool for that witness, or send it to a defined sink) instead of silently discarding it in `accumulateWitnessVi`. The same fix is needed in the historical-migration duplicate of this logic in `RewardViCalService.accumulateWitnessVi` [7](#0-6) .

### Proof of Concept
1. Voter `A` votes for witness `W` using `FreezeBalanceV2`/`VoteWitnessContract`, making `W` part of the active witness set.
2. Within the current cycle, `W` produces blocks; `MortgageService.payBlockReward`/`payTransactionFeeReward` call `delegationStore.addReward(cycle, W, value)`, accumulating reward for `W` at the current cycle.
3. Before the next `doMaintenance()`, `A` submits `UnfreezeBalanceV2Contract` unfreezing all TRON Power, which clears `A`'s votes via `updateVote()`, effectively driving `W`'s live vote count in `WitnessStore` toward 0 for that cycle (if `A` was the sole/majority voter).
4. At `doMaintenance()`, `MaintenanceManager` calls `delegationStore.accumulateWitnessVi(curCycle, W, witness.getVoteCount())` with `voteCount == 0`; the branch that would compute `deltaVi` from `reward` is skipped, so the cycle's reward for `W` is never reflected in `Vi`.
5. No subsequent voter, using `MortgageService.computeReward` (which is entirely `Vi`-delta driven), can ever recover that reward — the TRX credited in step 2 is permanently stuck.
