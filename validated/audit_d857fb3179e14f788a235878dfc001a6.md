### Title
`SmartFarmingManager.leverage`/`flashRepay` swaps have no expiration protection - (`contracts/SmartFarmingManager.sol`)

### Summary
`SmartFarmingManager` routes DEX swaps through the external `ISwapper.swapExactInput` inside `leverage` and `flashRepay`. Neither function accepts a user-supplied deadline, so a transaction that sits in the mempool for a long time can still execute at stale market conditions. If the price moved but remains inside the user's slippage bounds (`depositAmountMin_` / `swapAmountOutMin_`), the trade completes at a worse effective rate than the user intended when signing.

### Finding Description
Both public entry points perform one or more external swaps atomically and only check user-supplied minimum-amount parameters:

- `leverage` swaps `tokenIn_` → collateral with `amountOutMin_ = 0` and synth → collateral with `amountOutMin_ = 0`, relying solely on the final `depositAmountMin_` check at `SmartFarmingManager.sol:198`.
- `flashRepay` swaps collateral → synth with `amountOutMin_ = 0` and relies on `swapAmountOutMin_` at `SmartFarmingManager.sol:126`.

There is no `deadline`/`expiry` parameter in `leverage`, `flashRepay`, or the `ISwapper` interface (`swapExactInput(tokenIn, tokenOut, amountIn, amountOutMin, receiver)`). Like the referenced Tokemak finding, the swap cannot expire: a pending transaction is still valid after arbitrary delay.

### Impact Explanation
If a user's `leverage` or `flashRepay` transaction is delayed (congestion, low gas, mempool withholding), market prices can drift significantly. The transaction still executes because only slippage - not time - is enforced. The user may receive an acceptable-but-stale fill, realizing a loss relative to current market prices that they never consented to at execution time. Loss is bounded by the chosen slippage parameter, matching the medium-severity profile of the reference issue.

### Likelihood Explanation
Requires the user's transaction to remain pending while prices move within their slippage tolerance. This is a common mempool condition on all deployed chains (mainnet, Base, Optimism, Hemi, Plasma, Swell), and users routinely set non-trivial slippage for leverage operations, widening the window where a stale execution succeeds.

### Recommendation
Add a `deadline` parameter to `leverage` and `flashRepay` (and to `ISwapper.swapExactInput` or the swapper's downstream calls) and revert when `block.timestamp > deadline`, letting users bound the validity window of their swap-bearing transactions.

### Proof of Concept
Foundry/Hardhat scenario (using the existing `SwapperMock` harness in `test/SmartFarmingManager.test.ts`):

1. Alice calls `leverage(vaDAI, msdVaDAI, msUSD, amountIn, 1.5e18, depositAmountMin)` with `depositAmountMin` set for ~5% slippage. Note the call carries no deadline.
2. Simulate mempool delay by advancing time/blocks (`evm_increaseTime`, `vm.warp`), then drop the swapper rate by ~4% (`swapper.updateRate(0.96e18)`), emulating adverse market drift.
3. Re-submit the identical calldata. The transaction succeeds because `depositAmount >= depositAmountMin`, even though the price has moved and Alice would not have broadcast the trade at the new price. With a deadline parameter, step 3 would revert.

The same applies to `flashRepay` with `swapAmountOutMin_`.
