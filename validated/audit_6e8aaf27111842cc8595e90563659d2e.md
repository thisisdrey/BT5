### Title
Unbounded per-transaction `subtransactions` slice enables O(n²) DoS of a single Praefect `RegisterTransaction` session via mass reference-transaction hook invocations - ([File: internal/praefect/transactions/transaction.go])

### Summary
Praefect's in-memory reference-transaction coordinator keeps a `transaction.subtransactions []*subtransaction` slice that grows by one element every time a voting node needs a fresh subtransaction, and is scanned linearly, under a mutex, on essentially every vote for the lifetime of the transaction. Nothing bounds how many subtransactions a single registered transaction can accumulate, so a client that drives many separate reference-transaction hook invocations within one push/RPC forces this slice — and the per-vote linear scan over it — to grow without limit, degrading to O(n²) total work while holding `transaction.lock`.

### Finding Description
Each vote cast by a Gitaly node calls `transaction.vote()` → `getOrCreateSubtransaction()`, which:
1. Calls `getPendingNodeSubtransactions()`, which iterates the *entire* `t.subtransactions` slice from index 0 for every single vote: [1](#0-0) 
2. If the node has no pending work, it appends a brand-new subtransaction with `t.subtransactions = append(t.subtransactions, subtransaction)`: [2](#0-1) 

The entire operation is serialized by `t.lock.Lock()` for the whole duration of `getOrCreateSubtransaction` and `cancelNodeVoter`: [3](#0-2) 

There is no cap on `len(t.subtransactions)` anywhere in `transaction.go` or in `Manager.RegisterTransaction`/`voteTransaction`: [4](#0-3) [5](#0-4) 

A new subtransaction gets created every time a node has fully committed on all prior subtransactions and votes again — this happens once per reference-transaction hook invocation for that node. Git's reference-transaction hook is invoked separately for every reference-update "session" and, notably, gets invoked twice per delete-then-loose-update sequence and once per non-atomic push segment, as documented: [6](#0-5) 

Each such invocation triggers `voteOnTransaction` → `Manager.VoteTransaction` → `transaction.vote()`, i.e., one more potential subtransaction append per hook invocation. An ordinary authenticated user who can push can trigger a large number of reference-transaction hook invocations within the scope of a single Praefect-registered transaction/RPC (e.g., a request touching a very large number of distinct reference-update sessions, or repeated small votes/cancellations that repeatedly exhaust and recreate pending subtransactions via `cancelNodeVoter`, which also appends when no pending subtransaction exists): [7](#0-6) 

This is structurally analogous to the reported `activeTransactionBlocks` bug class: an unbounded, per-actor-growable list that is walked in full on every subsequent operation, with no upper bound and no O(1) removal/lookup strategy (an `EnumerableMap`-style structure), letting a caller force ever more expensive scans.

### Impact Explanation
Because the scan and mutation happen under `t.lock` (a single mutex per transaction), and because `Manager.voteTransaction` holds the write-lock path serialized via `lockRepoForTransaction`, a transaction with an artificially large `subtransactions` slice causes every subsequent vote from every voter (primary and all secondaries) on that transaction to pay increasing linear cost, and to contend on the same lock while doing so. This throttles or stalls voting for that repository's transaction, which given `PraefectSerializedWrite`/repo write-lock semantics can back up other requests to the same repository, producing a repository/RPC-handler resource-exhaustion condition triggerable by an ordinary pushing user without any special privilege.

### Likelihood Explanation
Reaching this path requires only an ordinary push through Praefect with transactions enabled — no privileged actor, leaked token, or malicious peer is required, satisfying the validation constraints. The exact magnitude of subtransactions per push is bounded by how many hook invocations/vote rounds a single push can trigger (which scales with number of distinct reference update "sessions" or forced voter cancellations), so likelihood of a severe DoS depends on how easily a client can force many hook invocations within one transaction — this reduces confidence somewhat versus a directly attacker-controlled loop counter, but the underlying growth-then-full-rescan pattern is unambiguously present and unguarded.

### Recommendation
- Bound the number of subtransactions a single transaction may accumulate (e.g., `maxSubtransactionsPerTransaction`), rejecting/failing the transaction gracefully once exceeded.
- Avoid full linear rescans of `t.subtransactions` for every vote: track, per node, an index/pointer to its next pending subtransaction (or use a small deque/ring keyed by node) so lookup is O(1) amortized instead of O(n).
- Consider pruning/compacting `t.subtransactions` once all voters have reached a terminal state on the oldest entries, rather than retaining the full history for the life of the transaction.

### Proof of Concept
Conceptual sequence (cannot be executed here, but derivable from the code paths cited):
1. Client establishes a Praefect-routed mutator RPC that becomes a registered transaction with N voters via `RegisterTransaction`.
2. Client structures the push/reference updates such that the `reference-transaction` hook fires many times in sequence for the same transaction ID (e.g., a push containing many distinct force-delete + loose-update sessions, or repeated timeouts causing `CancelTransactionNodeVoter`/`cancelNodeVoter` calls that force new subtransaction creation, per `transaction.go:326-347`).
3. Each hook invocation results in a new `*subtransaction` appended to `t.subtransactions` (`transaction.go:245`), and every subsequent `vote()`/`cancelNodeVoter()` call re-scans the now-larger slice from the start (`transaction.go:253-264`).
4. As the slice grows to size N over the course of one push, the cumulative scanning cost grows O(N²), all serialized behind `t.lock`, stalling further votes on this transaction and any RPCs waiting for the repository's write lock.

// cancelNodeVoter cancels the undecided voters associated with
// the specified node for all pending subtransactions.
func (t *transaction) cancelNodeVoter(node string) error {
	t.lock.Lock()
	defer t.lock.Unlock()

	// Get all undecided subtransactions for node.
	pendingSubtransactions, err := t.getPendingNodeSubtransactions(node)
	if err != nil {
		return err
	}

	// If there are no pending subtransactions a new one should
	// be created and added to the transaction so the failure
	// can be tracked.
	if len(pendingSubtransactions) == 0 {
		sub, err := t.createSubtransaction()
		if err != nil {
			return err
		}

		t.subtransactions = append(t.subtransactions, sub)
		pendingSubtransactions = []*subtransaction{sub}
	}

func (mgr *Manager) RegisterTransaction(ctx context.Context, voters []Voter, threshold uint) (Transaction, CancelFunc, error) {
	mgr.lock.Lock()
	defer mgr.lock.Unlock()

	transactionID := atomic.AddUint64(&mgr.idSequence, 1)

	transaction, err := newTransaction(transactionID, voters, threshold)
	if err != nil {
		return nil, nil, err
	}

	if _, ok := mgr.transactions[transactionID]; ok {
		return nil, nil, errors.New("transaction exists already")
	}
	mgr.transactions[transactionID] = transaction

	mgr.logger.WithFields(log.Fields{
		"transaction.id":     transactionID,
		"transaction.voters": voters,
	}).DebugContext(ctx, "RegisterTransaction")

	mgr.counterMetric.WithLabelValues("registered").Add(float64(len(voters)))

	return transaction, func() error {
		return mgr.cancelTransaction(ctx, transaction)
	}, nil
}

func (mgr *Manager) voteTransaction(ctx context.Context, transactionID uint64, storageName, repoRelativePath, node string,
	phase gitalypb.VoteTransactionRequest_Phase, vote voting.Vote,
) (returnedErr error) {
	mgr.lock.Lock()
	transaction, ok := mgr.transactions[transactionID]
	mgr.lock.Unlock()

	if !ok {
		return fmt.Errorf("%w: %d", ErrNotFound, transactionID)
	}

	err := mgr.lockRepoForTransaction(ctx, transactionID, storageName, repoRelativePath, phase)
	if err != nil {
		return fmt.Errorf("lock transaction %d: %w", transactionID, err)
	}
	defer func() {
		mgr.unlockRepoForTransaction(ctx, transactionID, returnedErr, phase)
	}()
	if err := transaction.vote(ctx, node, vote); err != nil {
		return err
	}

	return nil
}
