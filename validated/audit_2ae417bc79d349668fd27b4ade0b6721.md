### Title
`DeleteAccount` fails to purge `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` trie keys, allowing a stale postponed receipt to execute against a subsequently recreated account of the same name - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (invoked by the `DeleteAccount` action) only clears `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData` for the deleted account, but never clears `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` entries keyed by that `receiver_id`. If a receipt is postponed for an account (waiting on multiple input data dependencies) and the account is deleted and a new account with the identical name is created before the remaining input data arrives, the stale postponed `ActionReceipt` will later be resumed and its actions (function calls / transfers) executed against the newly created account's state and balance.

### Finding Description
`set_postponed_receipt` writes an `ActionReceipt` under `TrieKey::PostponedReceipt { receiver_id, receipt_id }` [1](#0-0)  together with associated `PendingDataCount`/`PostponedReceiptId` bookkeeping keyed by the same `receiver_id`, all independent of any particular "incarnation" of the account.

`remove_account`, which is the function that implements account deletion side effects, only removes:
- `TrieKey::Account`
- `TrieKey::ContractCode`
- access keys / gas key nonces (iterated via `get_raw_prefix_for_access_keys`)
- `TrieKey::ContractData` entries (iterated via `get_raw_prefix_for_contract_data`) [2](#0-1) 

It never iterates or removes anything under the postponed-receipt trie key prefixes. Because `TrieKey::PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` are addressed purely by the string `receiver_id` (not by any account-generation nonce or incarnation identifier), a receipt postponed for `VICTIM` before deletion remains fully intact in the trie after `DeleteAccount(VICTIM)` and after a subsequent `CreateAccount(VICTIM)` by an unrelated predecessor. When the second dependency `ReceivedData` for that postponed receipt is later delivered, the runtime's postponed-receipt resumption logic (in `runtime/runtime/src/lib.rs`) looks up the postponed receipt purely by `(receiver_id, receipt_id)` and, upon satisfying the pending-data count, executes its actions against whatever account state currently exists under that receiver ID — i.e., the newly created account, not the account that existed when the receipt was queued.

I was not able to fully re-trace the exact resumption code path (`apply_data_receipt` / promise resumption logic) in `runtime/runtime/src/lib.rs` within the available iterations to double check whether there is an additional guard (e.g., a check that the account still exists / matches an incarnation marker) before executing the postponed receipt's actions. This is a residual verification gap. However, the trie-key evidence is unambiguous: `remove_account` does not clear postponed-receipt-related state, and `TrieKey::PostponedReceipt` has no incarnation/generation component, so nothing in the schema itself prevents this cross-incarnation execution.

### Impact Explanation
If confirmed end-to-end, this allows execution of a stale `ActionReceipt` (containing arbitrary function calls/transfers that the pre-deletion contract queued) against the balance and storage of a brand-new, unrelated account holder who simply reused a freed account name. This matches the "authorization escalation across accounts/promises" and potential "theft of funds" bounty categories, since actions from an old contract incarnation execute under a new owner's funded account without their consent.

### Likelihood Explanation
The precondition set is narrow and requires specific setup: a contract that produces an output receipt to itself with more than one `input_data_id` dependency (so one branch is postponed), the account owner voluntarily calling `DeleteAccount` while a dependency is still outstanding, and a third party immediately creating a new account with the exact same name before the remaining data receipt is delivered. This is a race/coordination-dependent scenario (the attacker essentially needs to induce or wait for a third party to "squat" on the freed name), which limits general repeatability but is fully within reach of an unprivileged account owner controlling their own contract and DeleteAccount action — no validator/node privilege is required.

### Recommendation
`remove_account` (or the `DeleteAccount` action handler) should also enumerate and remove all `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceiptId` entries for the account before finalizing deletion (refunding/discarding the postponed receipts, e.g., by generating refund receipts), or `DeleteAccount` should be disallowed while the account has any outstanding postponed receipts.

### Proof of Concept
Integration test plan (runtime-loop level):
1. Deploy a contract on `victim` whose method issues a batch receipt to `victim` itself requiring two `input_data_id`s (e.g., via two cross-contract calls used as promise dependencies).
2. Submit the triggering `FunctionCall`; assert via `get_postponed_receipt`/direct trie read that a `TrieKey::PostponedReceipt { receiver_id: victim, receipt_id }` row exists after only one dependency is satisfied.
3. Submit `DeleteAccount(victim)` from `victim`'s key; assert `TrieKey::Account { victim }` is gone but `TrieKey::PostponedReceipt` for `victim` still exists.
4. Submit `CreateAccount(victim)` from a different predecessor/new key, funding it and optionally deploying a different contract.
5. Deliver the second data receipt satisfying the postponed dependency; run block application.
6. Assert the postponed receipt executed (state changes such as balance transfer or method execution) against the *new* `victim` account's state, and that `sum` of trie writes from the resumed receipt is applied post-recreation — demonstrating the invariant violation.

pub fn set_postponed_receipt(state_update: &mut TrieUpdate, receipt: &Receipt) {
    assert!(matches!(receipt.versioned_receipt(), VersionedReceiptEnum::Action(_)));
    let key = TrieKey::PostponedReceipt {
        receiver_id: receipt.receiver_id().clone(),
        receipt_id: *receipt.receipt_id(),
    };
    set(state_update, key, receipt);
}

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
