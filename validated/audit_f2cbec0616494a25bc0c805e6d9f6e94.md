### Title
Unauthenticated handshake flood forces expensive Noise DH + AEAD work on every stage-1 packet before certificate rejection - ([File: handshake_manager.go], [File: handshake/machine.go])

### Summary
The reported bug class is a "push"-style resource-exhaustion attack: an unauthenticated party can cheaply trigger the target to perform costly work (fee transfer / result posting) that is guaranteed to fail, and repeating this at volume floods and overloads the honest participants (solvers) with no way to recoup the cost. The reachable analog in Nebula is the responder side of the handshake path: any UDP sender with no CA-signed certificate can send a well-formed stage-1 (`MessageCounter == 1`, `RemoteIndex == 0`) handshake packet, and `HandshakeManager.beginHandshake` will unconditionally build a fresh Noise `Machine` and run a full asymmetric Diffie-Hellman + AEAD decrypt cycle via `machine.ProcessPacket` *before* any certificate/CA validation succeeds or fails.

### Finding Description
`Interface.readOutsidePackets` dispatches any packet with `h.Type == header.Handshake` straight to `f.handshakeManager.HandleIncoming` with no other precondition [1](#0-0) .

`HandshakeManager.HandleIncoming` only checks the handshake subtype, an optional underlay allow-list, and that `RemoteIndex == 0` for a stage-1 message — none of these require the sender to hold a certificate signed by a trusted CA. Any packet meeting this shape is routed to `beginHandshake` [2](#0-1) .

`beginHandshake` then unconditionally constructs a new Noise `handshake.Machine` and calls `machine.ProcessPacket(nil, packet)`: [3](#0-2) 

Inside `Machine.ProcessPacket`, the very first crypto-heavy step is `m.hs.ReadMessage(nil, packet[header.Len:])`, which performs the Noise IX ephemeral/static Diffie-Hellman computation and AEAD decryption of the payload — this executes regardless of whether the embedded certificate (checked only afterwards, in `validateCert`/`m.verifier`) will ultimately be trusted by the CA pool: [4](#0-3) [5](#0-4) 

Only after this DH computation, AEAD decrypt, and certificate-recombination work is done does `validateCert` invoke the CA-backed verifier and potentially reject the packet. There is no stateless "cookie"/proof-of-work gate (as used by, e.g., WireGuard's `MAC1`/`MAC2` and cookie reply) before this cost is incurred, and no rate limiting per source address is present anywhere in this path — the only allow-list check (`AllowUnknownVpnAddr`) is a static CIDR filter, not a rate limiter, and is entirely absent when the packet arrives via a relay (`via.IsRelayed`) [6](#0-5) . This mirrors the reported root cause pattern: work is performed for an as-yet-unauthenticated/untrusted counterparty before that party's legitimacy is confirmed, and the attacker can walk away (never complete/never hold a valid cert) leaving the target to have paid the cost.

The firewall/conntrack layer shows the same class of gap is a known, unaddressed limitation in this codebase: the `Firewall` struct explicitly notes `// TODO: need conntrack max tracked connections handling` and `NewFirewallFromConfig` still carries a `//TODO: max_connections` with no bound implemented [7](#0-6) [8](#0-7) . That path, however, requires an already-established (CA-signed) tunnel, so per the analysis rules it is excluded as a "valid-certificate-holder" analog; the handshake-flood path above is the one reachable strictly by an attacker with no CA-signed certificate.

### Impact Explanation
A remote, completely unauthenticated attacker (no valid Nebula certificate, no CA trust) can send an arbitrary volume of cheaply-crafted stage-1 handshake packets to a node's UDP listener. Each packet forces the responder to allocate a `handshake.Machine`, run a Noise IX Diffie-Hellman exchange and AEAD decryption, and attempt certificate recombination before it can be rejected. At sufficient packet rate this consumes CPU cycles that would otherwise service legitimate handshakes and data-plane traffic, producing a denial-of-service condition analogous to the reported "flood with thousands of requests to prevent legitimate work from completing/being compensated" bug class — here, legitimate peers' handshakes are starved of CPU/processing time by garbage handshake floods from parties that never possess a trusted certificate.

### Likelihood Explanation
Likelihood is moderate-to-high on any node with `lighthouse.remote_allow_list` unset or permissive (the default), since the only gate before expensive processing is that static, non-rate-limiting allow-list. Traffic arriving via relay bypasses even that check. Because Nebula listens on UDP, no connection setup is needed and packets are trivial to spoof/generate at volume from a botnet or single high-bandwidth host, making the attack straightforward to mount.

### Recommendation
Add a stateless, low-cost anti-flood gate ahead of the expensive Noise processing in `beginHandshake`/`HandleIncoming` — e.g., a cookie/MAC-based challenge (as in WireGuard) or per-source-IP rate limiting/backoff — so that packets from senders who have not demonstrated even minimal round-trip cost cannot force full DH + AEAD + certificate-recombination work. Additionally, implement the still-outstanding conntrack `max_connections` bound noted in `firewall.go` to cap resource growth from any single source once authenticated.

### Proof of Concept
Not directly executable from the indexed context (no packet-capture/harness reproduction was run). Conceptually: repeatedly send well-formed stage-1 handshake packets (`header.Handshake`, `HandshakeIXPSK0`, `MessageCounter == 1`, `RemoteIndex == 0`) with a valid-looking but arbitrary ephemeral key from many source ports/addresses to a target's listening UDP port; observe via `hostmap.pending.hosts`/CPU metrics that the target performs full Noise DH + cert-recombination processing for each one in `beginHandshake`/`Machine.ProcessPacket` before rejection, as shown in the cited code paths.

```go
func (hm *HandshakeManager) HandleIncoming(via ViaSender, packet []byte, h *header.H) {
	// Gate on known handshake subtypes. Unknown subtypes (or future ones we
	// don't yet support) are dropped here rather than silently routed through
	// the IX path. Add a case when introducing a new pattern.
	switch h.Subtype {
	case header.HandshakeIXPSK0:
		// supported
	default:
		hm.l.Debug("dropping handshake with unsupported subtype",
			"from", via, "subtype", h.Subtype)
		return
	}

	// First remote allow list check before we know the vpnIp
	if !via.IsRelayed {
		if !hm.lightHouse.GetRemoteAllowList().AllowUnknownVpnAddr(via.UdpAddr.Addr()) {
			hm.l.Debug("lighthouse.remote_allow_list denied incoming handshake", "from", via)
			return
		}
	}

	// First message of a new handshake. The wire format requires RemoteIndex
	// to be zero here (the initiator has no responder index to fill in yet),
	// and generateIndex never allocates 0, so any non-zero RemoteIndex on a
	// stage-1 packet is malformed or someone probing for an index collision.
	// Drop without paying the cost of running noise on a pending Machine.
	if h.MessageCounter == 1 {
		if h.RemoteIndex != 0 {
			hm.l.Debug("dropping stage-1 handshake with non-zero RemoteIndex",
				"from", via, "remoteIndex", h.RemoteIndex)
			return
		}
		hm.beginHandshake(via, packet, h)
		return
	}
```

```go
func (m *Machine) ProcessPacket(out, packet []byte) ([]byte, *Result, error) {
	if m.failed {
		return nil, nil, ErrMachineFailed
	}
	if len(packet) < header.Len {
		return nil, nil, ErrPacketTooShort
	}
	// Reject packets whose subtype doesn't match the one this Machine was
	// built for. A pending handshake that suddenly receives a different
	// subtype on its index is either a stray packet that matched by chance
	// or a peer protocol violation; drop it without failing the Machine so
	// the legitimate retransmit can still complete.
	if header.MessageSubType(packet[1]) != m.subtype {
		return nil, nil, ErrSubtypeMismatch
	}
	if m.result.Initiator && m.hs.MessageIndex() == 0 {
		m.failed = true
		return nil, nil, ErrInitiateNotCalled
	}

	// The (eKey, dKey) ordering here is correct for IX, where the initiator
	// completes the handshake by reading the responder's stage-2 message.
	// noise returns (cs1, cs2) where cs1 is the initiator->responder cipher.
	// For 3-message patterns where a responder finishes by reading the final
	// message, this ordering would be wrong; revisit when XX/pqIX lands.
	msg, eKey, dKey, err := m.hs.ReadMessage(nil, packet[header.Len:])
	if err != nil {
		// Noise ReadMessage failed. The noise library checkpoints and rolls back
		// on failure, so the Machine is still alive. The caller can retry with
		// a different packet.
		return nil, nil, fmt.Errorf("noise ReadMessage: %w", err)
	}

	// From here on, noise state has advanced. Any error is fatal.
	flags := m.peerMsgFlags()

	if err := m.processPayload(msg, flags); err != nil {
		return nil, nil, err
	}
```

```go
func (m *Machine) validateCert(payload Payload) error {
	cred := m.getCred(m.myVersion)
	if cred == nil {
		m.failed = true
		return fmt.Errorf("%w: %v", ErrNoCredential, m.myVersion)
	}
	rc, err := cert.Recombine(
		cert.Version(payload.CertVersion),
		payload.Cert,
		m.hs.PeerStatic(),
		cred.Cert.Curve(),
	)
	if err != nil {
		m.failed = true
		return fmt.Errorf("recombine cert: %w", err)
	}

	if !bytes.Equal(rc.PublicKey(), m.hs.PeerStatic()) {
		m.failed = true
		return ErrPublicKeyMismatch
	}

	// Version negotiation, if the peer sent a different version and we have it, switch
	if rc.Version() != m.myVersion {
		if m.getCred(rc.Version()) != nil {
			m.myVersion = rc.Version()
		}
	}

	verified, err := m.verifier(rc)
	if err != nil {
		m.failed = true
		return fmt.Errorf("verify cert: %w", err)
	}

	m.result.RemoteCert = verified
	m.remoteCertSet = true
	return nil
}
```
