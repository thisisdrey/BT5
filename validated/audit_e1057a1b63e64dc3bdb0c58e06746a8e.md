### Title
Unbounded per-connection SSH handshake blocking allows slow-client resource exhaustion - ([File: sshd/server.go])

### Summary
`(*SSHServer).run` accepts a TCP connection and spawns a goroutine that calls `ssh.NewServerConn(c, s.config)` with no `net.Conn.SetDeadline`/`SetReadDeadline` before the handshake. The only mechanism that would ever close the raw socket (`sessionContext` tied to the parent `ctx`) is triggered by server shutdown, not by per-connection inactivity, so a client that trickles bytes slowly or never completes the handshake keeps the accepted `net.Conn`, its goroutine, and associated buffers alive indefinitely.

### Finding Description
In `sshd/server.go`, `run` loops on `listener.Accept()` and for every accepted connection spawns a goroutine: [1](#0-0) 

The comment explicitly acknowledges that `NewServerConn` may block on the handshake, and "guards" against a bad client only by wiring the socket close to `sessionContext`, which is derived from the server-wide `ctx` (cancelled on `Stop()`/shutdown), not from any per-connection timer: [2](#0-1) 

There is no call to `c.SetDeadline`, `c.SetReadDeadline`, or any `context.WithTimeout` scoped to a single connection anywhere in `sshd/server.go` or the rest of the `sshd` package (confirmed by searching for `Timeout`/`deadline`/`MaxAuthTries` in that package — no matches). `ssh.ServerConfig` also sets no `MaxAuthTries` or timeout-related field, only `PublicKeyCallback` and `ServerVersion`: [3](#0-2) 

An unauthenticated attacker who can reach the sshd management port can open many TCP connections and trickle handshake bytes slowly (or send nothing after the initial SYN/connect), causing each corresponding goroutine to park inside `ssh.NewServerConn` indefinitely. Each such connection holds a file descriptor, a goroutine, and `golang.org/x/crypto/ssh` handshake buffers for as long as the attacker keeps the TCP connection open — bounded only by OS-level socket/FD limits, not by any code in this package.

### Impact Explanation
This is a process-wide resource exhaustion vector against the nebula process's management SSH server: enough stalled connections can exhaust file descriptors or memory, which can starve other parts of the same process (including the tunnel data path), degrading or crashing nebula for all peers sharing that process — not just denying access to sshd management itself. This matches a remote crash/wedge / process-wide DoS impact class.

### Likelihood Explanation
Preconditions are narrow but realistic: `sshd.enabled=true` (an operator-enabled feature) and no external/OS-level connection-rate limiting (e.g., no firewall `iptables`/`ulimit` mitigations in front of the port). Given those, the attack requires only unprivileged network access to the sshd port and repeated `net.Dial` + partial byte writes — no credentials, no CA trust, no host access. It is fully repeatable and requires no race conditions or timing tricks, making it straightforward to reproduce with a simple load test.

### Recommendation
Set an explicit deadline on the accepted `net.Conn` before calling `ssh.NewServerConn`, e.g. `c.SetDeadline(time.Now().Add(handshakeTimeout))`, and clear/reset it after a successful handshake (before entering the session loop). Optionally also bound total concurrent unauthenticated connections (a semaphore) to cap worst-case FD/goroutine usage independent of the deadline.

### Proof of Concept
Integration test plan:
1. Start `SSHServer.Run` on a test listener with a valid host key/config.
2. Open N (e.g., 500) raw TCP connections via `net.Dial` to the listener address, writing only a partial/invalid SSH banner (or nothing) on each, and never completing the handshake.
3. Assert that after a bounded time window (e.g., 5–10s), the number of goroutines spawned by `run` and open server-side file descriptors is bounded/decreasing (i.e., connections are force-closed), rather than growing linearly with N and staying open indefinitely.
4. Current expected result (bug present): goroutine/FD count remains at N indefinitely since no deadline forces closure; after the fix, connections are closed and goroutines/FDs return to baseline after `handshakeTimeout`.
