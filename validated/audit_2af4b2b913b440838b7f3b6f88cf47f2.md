### Title
Unstaked QoS per-peer connection limit is keyed by self-issued pubkey instead of source IP, allowing a single attacker to multiply `max_connections_per_unstaked_peer` via pubkey churn - ([File: streamer/src/nonblocking/quic.rs])

### Summary
`ConnectionTableKey::new` buckets connections by `Pubkey` whenever the QUIC client presents one, and only falls back to `IpAddr` when no pubkey is available. Since the TLS handshake pubkey is self-issued and unstaked peers can generate arbitrary keypairs for free, a single attacker at one source IP can rotate ephemeral pubkeys to obtain a fresh `ConnectionTable` slot per identity, each independently allowed up to `max_connections_per_unstaked_peer` connections, instead of all connections from that IP being confined to one shared bucket.

### Finding Description
`ConnectionTableKey::new` chooses the key as follows: [1](#0-0) 

`try_add_connection` enforces `max_connections_per_peer` only *within* the `Vec<ConnectionEntry>` stored under a single `ConnectionTableKey` entry in the `IndexMap`: [2](#0-1) 

In `SwQos::cache_new_connection`, the per-connection cap used for unstaked peers is `self.config.max_connections_per_unstaked_peer`, applied to the bucket selected by `ConnectionTableKey::new(remote_addr.ip(), conn_context.remote_pubkey)`: [3](#0-2) 

Because the client fully controls the pubkey embedded in its self-signed QUIC TLS certificate, and unstaked peers need no real delegated stake to complete the handshake and be classified `ConnectionPeerType::Unstaked`, an attacker can present a distinct ephemeral pubkey per connection attempt. Each distinct pubkey produces a distinct `ConnectionTableKey::Pubkey(pubkey)` entry in the `IndexMap`, so the `max_connections_per_unstaked_peer` cap is enforced per fabricated identity rather than per physical source, letting the attacker accumulate `N × max_connections_per_unstaked_peer` connections from one IP (bounded only by the global aggregate cap `max_unstaked_connections`, which is enforced via `prune_oldest`/`prune_random`, not per-IP). This is confirmed by the existing unit test that treats distinct pubkeys as fully independent buckets, each individually allowed up to `max_connections_per_peer`: [4](#0-3) 

The only path that collapses connections into a single bucket is the `None`-pubkey / `IP` key branch, which real clients need never take since presenting some pubkey is essentially free.

### Impact Explanation
This is a QoS-evasion / unfair-resource-allocation bug (scoped as "QoS evasion" per the audit categories). A single unstaked attacker from one IP can consume a disproportionate share of the shared unstaked connection/stream budget (up to the global `max_unstaked_connections`/stream-throttling ceiling) by rotating pubkeys, instead of being limited to `max_connections_per_unstaked_peer` as the per-peer QoS knob intends. Because global pruning (`prune_oldest`) evicts the least-recently-active bucket regardless of source IP, the attacker's continuously-refreshed rotating identities can starve legitimate unstaked clients on other IPs of connection slots, degrading transaction ingress fairness for genuine unstaked traffic.

### Likelihood Explanation
Fully feasible and repeatable by an unprivileged remote client: it only requires generating disposable `Keypair`s locally and opening QUIC connections presenting a different self-signed cert/pubkey each time — no stake, gossip participation, or validator control needed. The relevant per-peer cap check happens purely in-process against the `ConnectionTableKey` derived from the attacker-supplied pubkey.

### Recommendation
For `ConnectionPeerType::Unstaked` connections, key the connection table (or at minimum enforce an additional per-IP aggregate cap) by `IpAddr` rather than by the client-supplied pubkey, since an unstaked pubkey carries no verified identity guarantee. Only staked (delegated-stake-backed) pubkeys should be trusted as a distinguishing key, because minting a new staked identity has real economic cost; unstaked pubkeys should be treated as attacker-controlled and not used to partition per-peer QoS accounting.

### Proof of Concept
Rust integration test sketch (using existing test helpers in `streamer/src/nonblocking/quic.rs`'s `test` module and `SwQos`):

```rust
#[tokio::test]
async fn test_unstaked_pubkey_churn_bypasses_per_peer_cap() {
    let cancel = CancellationToken::new();
    let stats = Arc::new(StreamerStats::default());
    let config = SwQosConfig {
        max_connections_per_unstaked_peer: 2,
        max_unstaked_connections: 1000, // large aggregate budget
        ..SwQosConfig::default()
    };
    let mut table = ConnectionTable::new(ConnectionTableType::Unstaked, cancel.clone());
    let ip = IpAddr::from([127, 0, 0, 1]);

    // Simulate 50 distinct ephemeral pubkeys from the SAME source IP.
    for _ in 0..50 {
        let pubkey = Pubkey::new_unique();
        for _ in 0..config.max_connections_per_unstaked_peer {
            let ok = table.try_add_connection(
                ConnectionTableKey::new(ip, Some(pubkey)),
                0,
                ClientConnectionTracker::new(stats.clone(), 10_000).unwrap(),
                None,
                ConnectionPeerType::Unstaked,
                Arc::new(AtomicU64::new(0)),
                config.max_connections_per_unstaked_peer,
                || Arc::new(NullStreamerCounter {}),
            );
            assert!(ok.is_some());
        }
    }

    // Assert: total accepted connections from a single IP grossly exceed
    // max_connections_per_unstaked_peer (2), demonstrating the per-peer
    // cap is not enforced per source IP.
    assert_eq!(table.total_size, 100); // 50 * 2, vs intended cap of 2 for one peer
}
```
Expected (buggy) result: `table.total_size == 100` despite `max_connections_per_unstaked_peer == 2`, showing the per-IP effective quota is multiplied by the number of rotated pubkeys. A fixed implementation (keying unstaked connections by IP) should instead assert the total stays bounded at `max_connections_per_unstaked_peer` for the single source IP.
