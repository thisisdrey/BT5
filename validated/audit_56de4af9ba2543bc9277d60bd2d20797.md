### Title
Ambiguous concatenation in `createArchiveCacheKey` allows cache-key collisions across different `GetArchive` requests, enabling cross-repository archive cache poisoning - ([File: internal/gitaly/service/repository/archive.go])

### Summary
`GetArchive` computes the key for the shared, server-wide `archiveCache` by concatenating `GlProjectPath`, the `git archive` positional args, and the pathspecs with no unambiguous separator between fields, then hashing the result with SHA-256. Because the join is ambiguous, two semantically different requests (potentially for different repositories/paths) can serialize to the identical byte string and therefore to the identical cache key, exactly analogous to the Astaria `LienToken` bug where a deterministic ID was derived from an insufficient/ambiguous set of inputs and collided across logically distinct entities.

### Finding Description
`createArchiveCacheKey` builds the key like this: [1](#0-0) 

`cacheKeyHash.Write([]byte(gitLabProjectPath))` is followed directly by `strings.Join(args, ",")` and `strings.Join(pathspecs, ",")`, with no length-prefixing, delimiter, or field-boundary marker between `gitLabProjectPath` and the joined `args`, nor between `args` and `pathspecs`. Because `Write` calls on a hash are simply concatenated, this is equivalent to hashing one flat string built by naive concatenation of variable-length attacker/caller-influenced fields — the same class of flaw as the lien ID in the report, which packed `collateralId`, `vault`, and strategy terms into a single digest without enough distinguishing structure, so distinct intents could hash identically.

Concretely: if `gitLabProjectPath = "foobar"` with `args = []`/`pathspecs = []`, the hashed bytes are `"foobar"`. If instead `gitLabProjectPath = "foo"` and `args = ["bar"]` (`pathspecs = []`), the hashed bytes are also `"foo"+"bar"` = `"foobar"`. The two requests produce the identical `sha256` cache key despite referring to different projects/paths/commit ids.

The key is used to `Fetch` from `s.archiveCache`, a single process-wide `streamcache.Cache` instance shared by all repositories on the Gitaly node (not scoped per repository): [2](#0-1) [3](#0-2) 

`args` is built from the client-supplied `CommitId` (and optionally the requested `Path`), and `pathspecs` is built from the client-supplied `Path`/`Exclude` fields: [4](#0-3) 

Since `CommitId`, `Path`, and `Exclude` are attacker/caller-controlled fields of `GetArchiveRequest`, and `GlProjectPath` is a caller-supplied field of the `Repository` message, an attacker who can issue `GetArchive` RPCs (e.g., as an ordinary authenticated user hitting a project they have read access to) can craft a request whose concatenation collides with another project's/commit's cache key.

### Impact Explanation
If Requestor A first triggers caching of a sensitive archive under key `K` (formed from `projectA/commitA/pathA`), and Requestor B (or the same attacker probing other projects) can construct `projectB/commitB/pathB` values whose concatenation also serializes to the identical byte string, Requestor B's `GetArchive` call becomes a cache hit against A's data — the archive content generated for project A/commit A/path A is served in response to B's differently-intended request. Because the cache is shared across all repositories on the storage node rather than partitioned per repository, this is a genuine cross-repository disclosure vector (serving repository archive contents to a caller who requested a different repository/commit/path), which is stronger than the original report's simple "operation reverts" DoS. At minimum, even where full collision engineering is difficult, this construction is fragile and can also cause unexpected reuse of stale/incorrect archive content across unrelated inputs.

### Likelihood Explanation
Exploitation requires the attacker to find or influence `gitLabProjectPath`, `CommitId`, and `Path`/`Exclude` values such that the concatenated byte sequences coincide — this is a boundary-injection problem (like a path-traversal/ambiguous serialization bug), not a cryptographic SHA-256 collision, so it is far easier to construct than a genuine hash collision. Any authenticated caller able to invoke `GetArchive` for at least one project under their control can attempt to align field boundaries. The practical difficulty is knowing/matching the target's exact `commitId`/`projectPath` values, which somewhat limits blind exploitation, but git commit IDs and project paths are frequently public or discoverable, and internal callers (Rails/Workhorse) proxy these values largely unvalidated for uniqueness purposes.

### Recommendation
Do not build the cache key by naively concatenating variable-length strings. Use an unambiguous encoding, e.g., write each field's length before its content (length-prefixing) or write a fixed-width separator/null byte between fields before hashing, or hash each field independently and then hash the concatenation of the fixed-size digests (similar to how `compositeKeyHashHex` in `internal/cache/keyer.go` uses `prefixLen` to length-prefix each hashed component). Apply this to `createArchiveCacheKey` in `internal/gitaly/service/repository/archive.go`.

### Proof of Concept
```go
// Two logically different requests collide in createArchiveCacheKey.
keyA := createArchiveCacheKey("foobar", nil, nil)                 // project="foobar", no args
keyB := createArchiveCacheKey("foo", []string{"bar"}, nil)         // project="foo", commit-id arg="bar"
// keyA == keyB because sha256(Write("foobar")) == sha256(Write("foo")+Write("bar"))
```
Mapped to real RPC fields: request 1 has `Repository.GlProjectPath = "foobar"`, `GetArchiveRequest.CommitId = ""` (elided path scenario) producing `args = []`; request 2 has `Repository.GlProjectPath = "foo"`, `GetArchiveRequest.CommitId = "bar"` producing `args = ["bar"]`. Both serialize identically before hashing, so once one is cached in the shared `archiveCache`, the other's `GetArchive` call will be served the first's cached archive stream.

// createArchiveCacheKey creates a cache key using the GitLab project's path, the `git archive`
// command arguments and the pathspecs. The goal is to create a key that is unique not only
// across repository, but also across the content of each archive within the same repository.
func createArchiveCacheKey(gitLabProjectPath string, args []string, pathspecs []string) string {
	cacheKeyHash := sha256.New()
	cacheKeyHash.Write([]byte(gitLabProjectPath))
	cacheKeyHash.Write([]byte(strings.Join(args, ",")))
	cacheKeyHash.Write([]byte(strings.Join(pathspecs, ",")))
	return hex.EncodeToString(cacheKeyHash.Sum(nil))
}
