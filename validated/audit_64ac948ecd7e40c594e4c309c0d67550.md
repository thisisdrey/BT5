Found a valid analog. The pattern from the report — a boolean-returning transfer/reduce call whose failure indication is silently discarded while the state is still committed as "success" — recurs in three java-tron actuators.

### Title
Unchecked `reduceAssetAmountV2` return value in Exchange actuators causes accounting desync between account, exchange pool and market state - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
`AccountCapsule.reduceAssetAmountV2` returns a `boolean` indicating whether the requested TRC10 asset amount could actually be deducted from the account. `TransferAssetActuator.execute` correctly checks this return value and throws a `ContractExeException` on failure [1](#0-0) . However, `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeCreateActuator` call the same method and completely ignore its return value, unconditionally proceeding to update the exchange pool balances and mark the transaction as successful.

### Finding Description
In `ExchangeTransactionActuator.execute`, the owner's asset is reduced via `accountCapsule.reduceAssetAmountV2(tokenID, tokenQuant, dynamicStore, assetIssueStore);` without checking the boolean result [2](#0-1) . Regardless of whether the deduction actually succeeded, the code proceeds to credit `anotherTokenID` to the same account, persist the mutated `accountCapsule`, persist the updated `ExchangeCapsule` (whose balances were already mutated earlier by `exchangeCapsule.transaction(...)`), and set `ret.setStatus(fee, code.SUCESS)` [3](#0-2) .

The same unchecked pattern exists in `ExchangeInjectActuator.execute` for both `tokenID` and `anotherTokenID` reductions [4](#0-3) , and in `ExchangeCreateActuator.execute` for both `firstTokenID` and `secondTokenID` reductions [5](#0-4) .

This mirrors exactly the reported bug class: a function that signals failure via a boolean return value (like a non-reverting ERC20 `transfer`) is treated as always successful because the caller never inspects the return value, while other bookkeeping (here, the exchange pool's `firstTokenBalance`/`secondTokenBalance`, which is computed and committed *before* the reduction check even happens) is updated as if the transfer had succeeded.

### Impact Explanation
If `reduceAssetAmountV2` returns `false` (e.g., the account's actual asset balance is insufficient at execution time even though earlier validation passed, due to a TOCTOU-style race from other transactions in the same block/pool, or from an integer/edge-case in `AccountCapsule`'s internal asset map bookkeeping), the exchange pool (`ExchangeCapsule`) balances are still updated with the trade quantities and the counterparty asset (`anotherTokenID`) is still credited to the trader's account. The trader receives the "bought" token without their "sold" token actually being deducted, and the on-chain `ExchangeCapsule` and `AccountStore` state diverge from the truth — creating an unbacked asset increase for the trader and permanently corrupting the exchange pool's internal balance/price accounting relative to real backing assets. Because `ExchangeCreateActuator`/`ExchangeInjectActuator` similarly ignore the failure, a malicious or buggy account state can seed or inject into a pool without actually contributing the claimed token amount, corrupting the AMM-style pricing for all subsequent traders. This is a concrete unbacked-balance / broken-accounting condition reachable from ordinary signed `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeCreateContract` transactions.

### Likelihood Explanation
This requires `reduceAssetAmountV2` to actually return `false` at execution time despite `validate()` passing. Whether current validation logic in these actuators makes such a false return achievable in practice is not fully confirmed here — I could not locate and inspect `AccountCapsule.reduceAssetAmountV2`'s implementation within the indexed content to determine all the conditions under which it returns `false` rather than throwing, or whether `validate()` in these three actuators is airtight against every one of those conditions. This uncertainty should be resolved by inspecting `chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java` in full and diffing the validate() paths of `TransferAssetActuator` (which checks the return) against `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeCreateActuator` (which don't), to identify concrete scenarios where validate() passes but execute()'s reduction call still returns false.

### Recommendation
In `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeCreateActuator`, check the boolean return value of every `reduceAssetAmountV2` call the same way `TransferAssetActuator` does, and throw `ContractExeException` (aborting the transaction, matching TRON's actuator execute()/validate() failure-handling contract) on `false`, before any exchange pool or counterparty account mutation is persisted.

### Proof of Concept
1. Construct account/exchange state where `validate()` for `ExchangeTransactionContract` (or Inject/Create) passes but the account's actual TRC10 asset ledger cannot support the reduction at `execute()` time (this needs to be confirmed against the exact internal logic of `reduceAssetAmountV2`, which was not fully retrievable from the index — a Devin session with full repo access should trace `AccountCapsule.reduceAssetAmountV2` to enumerate all `false`-return branches).
2. Submit the `ExchangeTransactionContract` transaction; observe that `execute()` still credits `anotherTokenID` to the trader, updates the `ExchangeCapsule` balances, and returns `code.SUCESS`, despite the sold-token deduction failing.
3. Compare on-chain `AccountStore`/`ExchangeV2Store` state to confirm the trader gained the bought asset without giving up the sold asset, and the exchange pool balances no longer reflect real backing.
