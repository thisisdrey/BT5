Audit Report

## Title
Permanent lock of XCM-bridged assets when the underlying ERC20 contract's `transfer()` callback reverts or exceeds the hardcoded weight budget - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor` implements `TransactAsset::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` by delegating settlement to an external `bare_call` into an arbitrary Solidity contract's `transfer()` function on `pallet-revive`, with no fallback ledger accounting. [1](#0-0)  The `ERC20Matcher` used to resolve which contract backs an asset accepts *any* local `AccountKey20` location and converts it directly to an `H160` contract address with no allow-list or registry check, so any Ethereum-style address is treated as a valid backing ERC20 contract. [2](#0-1)  A contract engineered to revert on `transfer()` calls from the `TransfersCheckingAccount`, or to exceed the hardcoded `ERC20TransferGasLimit`, can permanently prevent settlement for that asset.

## Finding Description
Both settlement paths gate value movement on an external call into arbitrary Solidity code:

- Withdraw: signs as the caller and calls `IERC20::transfer(checking_address, amount)` on the asset contract; any revert or decode/gas failure returns `XcmError::FailedToTransactAsset` with no alternate accounting path. [3](#0-2) 
- Deposit: signs as `TransfersCheckingAccount` and calls `IERC20::transfer(beneficiary, amount)`; identical unconditional failure modes. [4](#0-3) 

The matcher wiring in asset-hub-westend confirms the transfer gas/weight budget and checking account are fixed constants, not adjustable per-message: `ERC20TransferGasLimit`, `ERC20TransferStorageDepositLimit`, and `ERC20TransfersCheckingAccount` are all `parameter_types!` constants plugged into `ERC20Transactor`. [5](#0-4)  The matcher itself, `ERC20Matcher`, is defined as `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>`, where `IsLocalAccountKey20` matches *any* local `AccountKey20` location and `AccountKey20ToH160` performs a raw, unconditional conversion of that key into an `H160` address used as the contract id — there is no governance-gated registry, allow-list, or existence/type check that the address is actually a well-behaved ERC20 contract deployed by a trusted party. [2](#0-1)  This confirms the report's premise that any account can pick an arbitrary 20-byte address as the "asset id" for this transactor, matching the unprivileged-attacker requirement.

Reachability from unprivileged input is confirmed: `WithdrawAsset` in the XCM executor calls `Config::AssetTransactor::withdraw_asset_with_surplus` with the message's own origin, which for an XCM message dispatched via `pallet_xcm::execute`/`send` can be any signed account. [6](#0-5)  On the deposit side, `deposit_assets_with_retry` calls `deposit_asset_with_surplus`, and on failure the asset is left in `self.holding`, causing `post_process` to trap it via `Config::AssetTrap::drop_assets`. [7](#0-6) [8](#0-7) 

However, the claim's final step — "any subsequent claim attempt re-invokes the identical `deposit_asset_with_surplus` path against the same `Evil` contract and fails identically" — does not hold as stated. `ClaimAsset` invokes `Config::AssetTrap::claim_assets`, which calls `AssetTransactor::mint_asset`, not `deposit_asset_with_surplus`. [9](#0-8)  `ERC20Transactor` does not override `mint_asset`; the default trait implementation simply returns `XcmError::Unimplemented` without performing any contract call. [10](#0-9)  This means a claim attempt for a trapped ERC20 asset does not replay the failing `transfer()` call at all — it simply fails to mint anything back into holding (since `mint_asset` is unimplemented for this transactor), and the executor's tuple-composed `AssetTransactor` would report `AssetNotFound`/`Unimplemented` for that specific transactor. This is a materially different (and in some ways more severe, in others less specifically-described) failure mode than the PoC's claimed "replay of identical failing call," and the exact downstream behavior of `claim_assets` for this untested asset type (whether value is silently forfeited, or the trap simply cannot be redeemed for this asset class at all) was not verified against a concrete integration test in this codebase.

Separately, on the withdraw side, if `withdraw_asset_with_surplus` itself fails inside a `WithdrawAsset` instruction, `Config::TransactionalProcessor::process` rolls back the whole instruction, so no asset ever enters holding to be trapped in the first place — the source account balance in the ERC20 contract is simply never debited, and the XCM instruction fails outright with `XcmError::FailedToTransactAsset`. This is a failed-transaction outcome (the message errors), not a "fund lock" of already-committed value, for the withdraw path specifically.

The deposit-side scenario (reserve-transfer/teleport into holding, then a beneficiary-side `transfer()` that a malicious contract deliberately reverts for) is the concrete, plausible lock scenario: value that has already been credited/minted into holding on this chain (e.g., via `ReserveAssetDeposited` from a trusted foreign chain, or via `mint_asset`/`Erc20Credit` construction on withdraw from a different account) genuinely cannot reach the beneficiary if the contract's `transfer()` is adversarial, and per the trap/claim analysis above, the standard asset-trap "claim" path does not obviously provide the attacker/beneficiary a way to recover it either (since `mint_asset` is unimplemented for this transactor), making the described "permanent lock" plausible even if the precise mechanistic detail (identical-call replay) in the PoC is inaccurate.

## Impact Explanation
This matches the "permanent user-fund or bridge-state lock" impact category: value already committed to on-chain holding (via a trusted reserve-transfer/teleport, or via `withdraw_asset_with_surplus`'s successful mint of `Erc20Credit`) can become permanently undeliverable to any beneficiary if the ERC20 contract backing the asset adversarially reverts or burns weight on its `transfer()` function, and the generic asset-trap/claim recovery mechanism does not appear to provide redemption for this transactor since `mint_asset` is left as the default `Unimplemented` implementation. [10](#0-9) 

## Likelihood Explanation
The matcher (`ERC20Matcher`) is permissionless in the sense that it will convert *any* local `AccountKey20` location to an `H160` "asset id" with no on-chain registry check that the address corresponds to a trusted, well-behaved ERC20 contract. [2](#0-1)  Any account can deploy an arbitrary contract under `pallet-revive` and reference it by address in an XCM message as an asset id, satisfying the "unprivileged attacker" requirement. The precise conditions under which value first reaches holding for such an attacker-chosen address (e.g., whether a trusted reserve location would ever actually credit such an asset, versus only a local withdraw/mint by the attacker's own account) determine how much of the total value at risk is "attacker's own funds" (self-lock, low-severity) versus a third party's funds (bridge/beneficiary lock, higher severity) — this distinction was not fully traceable from the available files.

## Recommendation
1. Implement `mint_asset` for `ERC20Transactor` (or otherwise wire a recovery path) so trapped ERC20 assets can actually be reclaimed without depending on the same fragile external call, or explicitly document/enforce that ERC20-backed assets must never be trapped (e.g., by disallowing them as `IsReserve`/teleport-eligible assets).
2. Restrict `ERC20Matcher`/`ERC20Transactor` registration to a vetted allow-list of contracts rather than accepting any `AccountKey20` address.
3. Make the weight/gas budget for the `transfer()` callback auditable and provide a governance or automatic path to raise it or bypass a misbehaving contract's callback for legitimate recovery.

## Proof of Concept
1. Deploy an ERC20 contract `Evil` under `pallet-revive` whose `transfer()` reverts when `msg.sender == ERC20TransfersCheckingAccount` or spins to exceed `ERC20TransferGasLimit`.
2. Have a trusted reserve location (or the attacker's own `withdraw_asset_with_surplus` call) place `Evil`-denominated value into holding on Asset Hub.
3. Attempt `DepositAsset` to any beneficiary; `deposit_asset_with_surplus` calls `Evil::transfer()` as `TransfersCheckingAccount`, which reverts, producing `XcmError::FailedToTransactAsset("ERC20 contract reverted")`. [11](#0-10) 
4. The instruction rolls back and the asset is trapped via `post_process`/`drop_assets`. [12](#0-11) 
5. Attempt `ClaimAsset` for the trapped asset; `claim_assets` calls `mint_asset`, which `ERC20Transactor` does not implement, so the asset is not restored to holding and remains unrecoverable via the standard XCM recovery mechanism. [13](#0-12) [10](#0-9)

pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

	/// This includes refunding surplus weight, trapping extra holding funds, and returning any

	pub fn post_process(mut self, xcm_weight: Weight) -> Outcome {
		// We silently drop any error from our attempt to refund the surplus as it's a charitable
		// thing so best-effort is all we will do.
		let _ = self.refund_surplus();

				holding_register = ?self.holding,
				context = ?self.context,

				"Trapping assets in holding register",
			);

	/// Deposit `to_deposit` assets to `beneficiary`, without giving up on the first (transient)
	/// error, and retrying once just in case one of the subsequently deposited assets satisfy some
	/// requirement.
	///
	/// Most common transient error is: `beneficiary` account does not yet exist and the first
	/// asset(s) in the (sorted) list does not satisfy ED, but a subsequent one in the list does.
	///
	/// Any per-asset failure on the retry pass propagates as `Err`, and the surrounding
	/// `transactional_process` rolls back the whole instruction (storage changes are reverted by
	/// `Config::TransactionalProcessor`, and `self.holding` is restored from its
	/// pre-instruction backup). Anything left in `self.holding` after the program finishes is
	/// then trapped by `post_process` via `Config::AssetTrap::drop_assets`, so funds are never
	/// silently lost.
	///
	/// This function can write into storage and also return an error at the same time, it should
	/// always be called within a transactional context.
	fn deposit_assets_with_retry(
		to_deposit: AssetsInHolding,
		beneficiary: &Location,
		context: Option<&XcmContext>,
	) -> Result<Weight, XcmError> {
		let mut total_surplus = Weight::zero();
		let mut failed_deposits = AssetsInHolding::new();

		// First pass: try to deposit each asset; failures go to retry.
		for single in to_deposit.into_per_asset_holdings() {
			match Config::AssetTransactor::deposit_asset_with_surplus(single, beneficiary, context)
			{
				Ok(surplus) => total_surplus.saturating_accrue(surplus),
				Err((unspent, _)) => {
					// First-pass failure: keep for retry. A subsequent deposit in the same
					// pass may create the destination account (by satisfying ED), allowing
					// the retry pass to succeed for assets that fall here.
					failed_deposits.subsume_assets(unspent);
				},
			}
		}

		// Retry previously failed deposits, this time short-circuiting on any error.
		for single in failed_deposits.into_per_asset_holdings() {
			let surplus =
				Config::AssetTransactor::deposit_asset_with_surplus(single, beneficiary, context)
					.map_err(|(unspent, error)| {
					tracing::debug!(
						target: "xcm::deposit_assets_with_retry",
						?error,
						?unspent,
						"Retry-pass deposit failed"
					);
					error
				})?;
			total_surplus.saturating_accrue(surplus);
		}

		Ok(total_surplus)
	}

impl<T: Config> ClaimAssets for Pallet<T> {
	fn claim_assets(
		origin: &Location,
		ticket: &Location,
		assets: &Assets,
		context: &XcmContext,
	) -> Option<AssetsInHolding> {
		let mut versioned = VersionedAssets::from(assets.clone());
		match ticket.unpack() {
			(0, [GeneralIndex(i)]) => {
				versioned = match versioned.into_version(*i as u32) {
					Ok(v) => v,
					Err(()) => return None,
				}
			},
			(0, []) => (),
			_ => return None,
		};
		let hash = BlakeTwo256::hash_of(&(origin.clone(), versioned.clone()));
		match AssetTraps::<T>::get(hash) {
			0 => return None,
			1 => AssetTraps::<T>::remove(hash),
			n => AssetTraps::<T>::insert(hash, n - 1),
		}
		let mut claimed = AssetsInHolding::new();
		for asset in assets.inner() {
			match <T::XcmExecutor as XcmAssetTransfers>::AssetTransactor::mint_asset(asset, context)
			{
				Ok(minted) => {
					// SAFETY: Any fungible imbalances are now effectively duplicated because they
					// were not resolved when the asset was trapped (so total issuance tracks
					// trapped assets too), and now a duplicate asset was just minted.
					// To balance the system and keep total issuance constant, we drop and resolve
					// one of the duplicates. As a result, total issuance doesn't change.
					//
					// Note: This may emit Burned/Minted events even though the net issuance change
					// is zero. The mint creates a +X imbalance, and dropping the clone resolves -X,
					// resulting in no net change but potentially two events. This is an acceptable
					// tradeoff for the asset trap/claim mechanism.
					minted.fungible.iter().for_each(|(_, imbalance)| {
						let to_resolve = imbalance.unsafe_clone();
						core::mem::drop(to_resolve);
					});
					claimed.subsume_assets(minted)
				},
				Err(error) => tracing::debug!(
					target: "xcm::pallet_xcm::claim_assets",
					?asset, ?error, "Asset claimed from trap but unable to mint."
				),
			}
		}
		Self::deposit_event(Event::AssetsClaimed {
			hash,
			origin: origin.clone(),
			assets: versioned,
		});
		Some(claimed)
	}
