### Title
`updateMerkleRoot` can be frontrun to claim a soon-to-be-reduced airdrop allocation - ([File: contracts/utils/RecurringAirdrop.sol])

### Summary
`RecurringAirdrop` (and its `MetAirdrop` derivative deployed on mainnet) lets the governor decrease an account's cumulative allocation by publishing a new Merkle root via `updateMerkleRoot`. Because the old root remains valid until the update transaction is mined, a beneficiary who sees a pending root update that reduces their allocation can frontrun it and call `claim` under the old, more generous root — the same bug class as Tokensoft's `adjust` frontrun.

### Finding Description
In `contracts/utils/RecurringAirdrop.sol`, `claim` verifies a leaf `keccak256(abi.encodePacked(msg.sender, amount_))` against the current `merkleRoot` and pays out `amount_ - claimed[msg.sender]` (lines 52–66). The governor reduces entitlements only by replacing `merkleRoot` via `updateMerkleRoot` (lines 81–90). There is no per-account revocation, no claim delay, no grace-period-free claim window after an update announcement, and no transaction-ordering protection:

- If a governor's `updateMerkleRoot` tx (with a lower cumulative amount for user X) is visible in the mempool, user X can submit `claim(oldAmount, oldProof)` with higher gas. The old proof still verifies against the still-current `merkleRoot`, `claimed[X]` is set to `oldAmount`, and tokens are transferred.
- When the governor's tx then executes, `merkleRoot` is replaced. Since `claimed[X] >= newAmount`, X can never claim again (`_claimable` would underflow / revert `NothingToClaim`), but the already-extracted tokens are not recoverable.

`MetAirdrop` (deployed, `deployments/mainnet/MetAirdrop.json`) inherits this flow and only overrides `_transferReward` to lock into esMET — the value is still extracted.

### Impact Explanation
Direct theft of tokens the protocol intended to claw back: the attacker receives the difference between the old (higher) and new (lower) cumulative allocation, draining distribution tokens that the governor explicitly sought to withhold. This is analogous to the reported `adjust` frontrun where a beneficiary extracts a pre-reduction claimable amount.

### Likelihood Explanation
Requires a governor root update that decreases some account's cumulative allocation and that the tx is observable before inclusion (public mempool; on L2s with private/sequenced mempools this is harder). The attack is a single `claim` call with a publicly known proof, so any affected beneficiary can execute it at negligible cost.

### Recommendation
- Only ever increase cumulative allocations per account across root updates (enforce off-chain; document the invariant), or
- Track per-round claims (e.g., include a round/epoch id in the leaf and key `claimed` by round) so an old root cannot be replayed, or
- Submit `updateMerkleRoot` through a private relay (e.g., Flashbots) when it reduces allocations, or add a short claim-freeze period around root updates.

### Proof of Concept
Hardhat test sketch against the existing fixture in `test/MetAirdrop.test.ts`:

```ts
it('frontruns a reducing root update', async function () {
  // round 0: alice entitled to rewards0[alice] = 100 MET
  const amount0 = rewards0[alice.address]

  // governor builds a new root where alice's cumulative amount is reduced to 50
  // and broadcasts updateMerkleRoot(merkleRootReduced, hash)

  // alice sees the pending tx and frontruns it:
  const leaf = generateLeaf(alice.address, amount0)
  const proof = merkleTree0.getHexProof(leaf)
  await airdrop.connect(alice).claim(amount0, proof) // pays 100

  // governor's tx then lands
  await airdrop.updateMerkleRoot(merkleRootReduced, `0x${randomBytes(32).toString('hex')}`)

  // alice keeps the 50 MET she should have been denied; claiming now reverts
  const leafReduced = generateLeaf(alice.address, reducedAmount)
  await expect(
    airdrop.connect(alice).claim(reducedAmount, merkleTreeReduced.getHexProof(leafReduced))
  ).to.be.reverted // claimable = 50 - 100 underflows / NothingToClaim
})
```
