Audit Report

## Title
`process_delivery_receipt` ignores the `DeliveryReceipt.success` flag, paying relayer rewards and settling orders even on failed Ethereum dispatch - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
`DeliveryReceipt` decodes the `InboundMessageDispatched` Ethereum event, which carries an explicit `success: bool` field documented as "Delivery status" [1](#0-0) . `Pallet::process_delivery_receipt` never reads or branches on `receipt.success`; it unconditionally pays the relayer reward for `order.fee > 0` and removes the `PendingOrder` from storage [2](#0-1) .

## Finding Description
The extrinsic entrypoint `submit_delivery_receipt` is callable by any signed account (`ensure_signed(origin)?`), performs proof verification via `T::Verifier::verify`, decodes the log into `DeliveryReceipt`, and forwards to `process_delivery_receipt` [3](#0-2) . Inside `process_delivery_receipt`, the only checks performed are: gateway address match, and existence of a `PendingOrder` for `receipt.nonce` [4](#0-3) . There is no branch that treats `success == false` differently from `success == true` — both paths pay the reward and remove the order, emitting `Event::MessageDelivered` regardless [5](#0-4) . The field is decoded faithfully from the real Ethereum event data (`event.success`) [6](#0-5) , confirming it is a genuine on-chain-derived value that the pallet's business logic discards entirely — a grep across the entire pallet confirms zero references to `success` anywhere in `outbound-queue-v2/src`.

## Impact Explanation
A relayer submitting a receipt for a failed dispatch (`success = false`) still collects the fee and the order is permanently removed from `PendingOrders`, closing off any possibility of retry or re-settlement for that nonce. This is a fund-flow correctness bug in a public, unprivileged extrinsic that governs bridge reward payout, matching the "duplicate settlement or payout" / "permanent bridge-state lock" impact class, since a failed message's `PendingOrder` state is irreversibly finalized without regard to actual delivery outcome.

## Likelihood Explanation
Any relayer that observes a genuine Gateway `InboundMessageDispatched` event with `success = false` can submit it through `submit_delivery_receipt` — no privileged origin or governance action is required, only a valid Ethereum proof, which is the standard relayer workflow. No test in the repository exercises `success: false`, confirming the flag is unvalidated dead weight in current logic.

## Recommendation
Branch on `receipt.success` in `process_delivery_receipt`: only invoke `T::RewardPayment::register_reward` when `success == true`; for `success == false`, implement explicit failure-path semantics (e.g., withhold reward and retain/transition the order to a distinct terminal state) instead of unconditionally removing the order and emitting `Event::MessageDelivered`.

## Proof of Concept
1. A message is queued via `do_process_message`, creating `PendingOrders[nonce]` with `fee > 0` [7](#0-6) .
2. The message is relayed to Ethereum; dispatch fails on the Gateway, emitting `InboundMessageDispatched` with `success = false`.
3. Any signed relayer submits this event log with valid proof via `submit_delivery_receipt`; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success: false` faithfully.
4. `process_delivery_receipt` finds `order.fee > 0`, calls `T::RewardPayment::register_reward`, and removes the order — identical to the success path — despite `receipt.success == false` never being inspected [8](#0-7) .

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
