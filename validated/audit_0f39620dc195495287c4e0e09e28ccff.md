Audit Report

## Title
`privatize` burns the full uncapped counterpart-token amount while placing on hold only the pot-limited (capped) payout amount, permanently destroying the difference - (File: substrate/frame/nis/src/lib.rs)

## Summary
In `privatize` (`substrate/frame/nis/src/lib.rs:856-900`), the counterpart burn quantity is computed from the receipt's full, uncapped `proportion` while the actual funds placed on hold for the user are capped to the pot's available balance via `max_amount.min(T::Currency::balance(&our_account))`. Because the call succeeds (no error is raised when the cap is applied), the burn is never reduced to match the capped payout, so the user permanently loses the difference between the value burned and the value received.

## Finding Description
`privatize` computes `max_amount = receipt.proportion * effective_issuance` and then `amount = max_amount.min(T::Currency::balance(&our_account))` at [1](#0-0) , explicitly anticipating that the pot may not hold enough funds to cover the full proportional claim. Immediately after, it burns `T::CounterpartAmount::convert(receipt.proportion)` — sized to the *uncapped* proportion, not to `amount` — at [2](#0-1) . It then transfers and holds only the capped `amount` at [3](#0-2) , and records `receipt.owner = Some((who, amount))` with `amount < max_amount` whenever the cap is triggered.

Unlike the `thaw_communal` path (which is protected by FRAME's automatic per-extrinsic storage-transaction wrapping — every `#[pallet::call]` dispatchable is executed inside `frame_support::storage::with_storage_layer`, per [4](#0-3)  and documented at [5](#0-4) , so any `Err` return rolls back the burn along with the rest of the call), `privatize` does **not** return an error when the cap is applied. The call completes with `Ok(())`, so the burn (full proportion) and the hold (capped `amount`) both commit, with no atomic rollback safety net to fall back on — the value loss is a direct logic bug, not merely a transactional-ordering fragility.

The precondition — pot (`Self::account_id()`) holdings falling below the aggregate `required` claim — is not a contrived edge case: `issuance_with` computes `effective = other / (1 - proportion_owed)` and `required = proportion_owed * effective`, where `other` is `total_issuance - holdings` [6](#0-5) . Since `other` grows naturally as the network's active issuance increases (e.g., staking/inflationary rewards) while pallet `holdings` stay fixed, `required` can exceed `holdings` purely through ordinary chain operation, exactly the condition the pallet's own `IssuanceInfo::required` doc anticipates: "If it is more than `holdings`, then the pallet will need funding" [7](#0-6) .

## Impact Explanation
Any unprivileged holder of a communal NIS receipt who calls the public extrinsic `privatize` while the pot is under-funded relative to their proportional claim burns their full counterpart-token entitlement but is credited (via hold) with strictly less value, with the difference permanently and silently destroyed — no error, no recovery path, and no compensating receipt/claim retained for the shortfall. This matches the "theft or unbacked mint/unlock" and "permanent user-fund lock" impact categories: user value is unilaterally and irreversibly destroyed in a normal, documented, unprivileged operation.

## Likelihood Explanation
No malicious actor, governance action, or privileged party is required — only that pot holdings fall below the pallet's own computed `required` value, a state the pallet's `IssuanceInfo` struct is explicitly designed to detect and that arises naturally from ordinary active-issuance growth (e.g., inflation/staking rewards) relative to fixed pot holdings. Any receipt holder calling `privatize` while this condition holds is affected and can trigger the loss repeatably.

## Recommendation
In `privatize`, derive the counterpart burn amount from the same capped `amount` value that is actually transferred/held, not from the uncapped `receipt.proportion`. If partial redemption is desired, split the receipt's proportion into a redeemed portion sized exactly to `amount` and retain the remainder as an outstanding communal claim (rather than burning tokens for value never delivered), ensuring burn quantity always equals settled payout quantity.

## Proof of Concept
1. Let the pot (`Nis::account_id()`) accumulate a `holdings` value below the pallet-computed `required` value — reachable via normal network operation as `other` (external active issuance) grows relative to fixed `holdings`, per `issuance_with`'s calculation (`substrate/frame/nis/src/lib.rs:979-992`).
2. A user holding a communal receipt with `proportion = p` calls `privatize(index)`.
3. `max_amount = p * effective_issuance` is computed; since `T::Currency::balance(our_account) < max_amount`, `amount = T::Currency::balance(our_account) < max_amount`.
4. `T::Counterpart::burn_from(&who, T::CounterpartAmount::convert(p), ...)` burns the full `p`-sized counterpart amount (`substrate/frame/nis/src/lib.rs:877-884`).
5. `T::Currency::transfer_and_hold(..., amount, ...)` holds only the reduced `amount` (`substrate/frame/nis/src/lib.rs:889`), and `receipt.owner = Some((who, amount))` records only the reduced value.
6. The extrinsic returns `Ok(())` — no error is raised — and the user has permanently lost `max_amount - amount` in counterpart-token value with no compensating claim. A unit test asserting `receipt.owner.1 == max_amount` after `privatize` under a pot-balance-constrained `MockCurrency` will fail, demonstrating the shortfall is silently absorbed rather than reverted or retained as an outstanding claim.

		pub fn issuance_with(
			our_account: &T::AccountId,
			summary: &SummaryRecordOf<T>,
		) -> IssuanceInfo<BalanceOf<T>> {
			let total_issuance =
				T::Currency::active_issuance().saturating_sub(T::IgnoredIssuance::get());
			let holdings =
				T::Currency::balance(our_account).saturating_add(summary.receipts_on_hold);
			let other = total_issuance.saturating_sub(holdings);
			let effective =
				summary.proportion_owed.left_from_one().saturating_reciprocal_mul(other);
			let required = summary.proportion_owed * effective;
			IssuanceInfo { holdings, other, effective, required }
		}
