### Title
Incomplete Storage Cleanup on Contract Self-Destruct Allows a Redeployed Contract to Inherit the Destroyed Contract's Storage - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
When a contract is destroyed via `SELFDESTRUCT`, java-tron removes the account, contract-metadata and code entries for that address, but never purges the contract's key/value storage rows. Because storage rows are addressed only by `sha3(address)` (plus a raw key suffix) in a flat, global `StorageRowStore` rather than being nested inside the account's own state (as in an account-scoped Merkle trie), any new contract later deployed at the same address (e.g. via `CREATE2` with attacker-controlled salt/bytecode, or address reuse after account deletion) can `SLOAD` and act on the leftover storage values written by the previous, "deleted" occupant of that address — mirroring CVE-2019-12902's "incomplete cleanup of a user's data upon deletion... allows a new [entity] with the same ID to restore the deleted [entity]'s data."

### Finding Description
`RepositoryImpl.deleteContract()` only clears three stores: [1](#0-0) 

It never touches the storage rows kept in `StorageRowStore`. Storage rows are composed purely from a hash of the contract's address (`addrHash`) plus the raw storage key — with `contractVersion` and `generateAddrHash` only mixing in the deploying transaction hash for a subset of `CREATE2` paths: [2](#0-1) 

`Storage` exposes no method to bulk-delete all rows belonging to an address; `commit()` only rewrites rows already loaded into `rowCache`, and `getValue()` reads straight through to the persistent `StorageRowStore` for any key not already cached: [3](#0-2) 

On `SELFDESTRUCT`, `Program.suicide`/`suicide2` transfer balance, TRC10 tokens, and frozen/delegated resources to the beneficiary and mark the address in the `selfDestructCache`, but at no point invoke any storage-clearing routine: [4](#0-3) 

Subsequently, `createContractImpl` determines whether an address is free for a new deployment purely from whether an `AccountCapsule` exists / `isContractExist`, and if it proceeds, writes the new bytecode with `deposit.saveCode(newAddress, code)` without ever clearing prior storage rows for that address: [5](#0-4) [6](#0-5) 

Because a `CREATE2` address is fully attacker-controlled (deployer address + salt + init-code hash), an unprivileged contract deployer can: (1) deploy contract A at a `CREATE2` address, have it write secret/attacker-favorable values into storage, (2) `SELFDESTRUCT` contract A, and (3) redeploy contract B at the identical address with the same salt/init-code-hash combination. Because storage rows survive the destroy step, contract B's fresh `SLOAD`s (which most compilers assume start at zero for a newly constructed contract) return the stale values left by A instead of zero.

### Impact Explanation
Smart-contract logic on TRON (like on any EVM-compatible chain) is generally written under the assumption that a freshly created contract has entirely zeroed storage. A contract redeployed at a reused address that unexpectedly inherits non-zero storage can have its invariants violated — e.g., access-control flags, allowances, ownership slots, initialized/paused flags, or balance/accounting slots could appear pre-set, letting the attacker (who fully controls both the destroyed and redeployed contract's bytecode) or any third party interacting with the new contract bypass intended initialization logic. In accounting-style or proxy/vault contracts this can translate into unauthorized privilege elevation or manipulation of on-chain accounting state, i.e., a concrete “unbacked/inconsistent state” condition analogous to the CVE's data-resurrection impact.

### Likelihood Explanation
Reachable end-to-end by any address that can broadcast `TriggerSmartContract`/`CreateSmartContract` transactions — no special privilege, SR/witness/committee status, or node access is required. `CREATE2` gives the attacker full determinism over the redeploy address, so the "same ID" precondition from the CVE is trivially satisfiable on-chain in two ordinary transactions (destroy, then redeploy).

### Recommendation
On successful self-destruct commit (and/or immediately before allowing a `CREATE`/`CREATE2` to reuse an address that was previously self-destructed / had code), enumerate and delete all storage rows keyed by that address's `addrHash` from `StorageRowStore`, mirroring what `deleteContract()` does for the account/code/contract stores. Alternatively, ensure `Storage.generateAddrHash` incorporates a stable per-deployment nonce/creation-transaction identifier for both `CREATE` and `CREATE2` paths so that a redeployed contract can never collide with the destroyed occupant's storage rows.

### Proof of Concept
1. Deploy factory contract `F`. Call `F.deploy2(saltX, bytecodeA)` to `CREATE2`-deploy contract `A` at deterministic address `X`; have `A`'s constructor write a sentinel value (e.g. `slot0 = 0xdeadbeef`) via `SSTORE`.
2. From an EOA, call `A.selfdestruct(beneficiary)`, destroying `A` at address `X` (`Program.suicide`) — this removes `A`'s account/code/contract-metadata but leaves the `slot0` row untouched in `StorageRowStore`.
3. Call `F.deploy2(saltX, bytecodeB)` with the same salt (and same init-code hash if required) to redeploy a different contract `B` at the same address `X`.
4. Call `B`'s accessor for `slot0` (or any TVM-level `SLOAD 0`) — it returns `0xdeadbeef` instead of `0`, proving `B` inherited `A`'s "deleted" storage, exactly as `Storage.getValue()`/`RepositoryImpl.deleteContract()` show no path exists to clear those rows.

Note: I was not able to fully trace, within the available iterations, the exact production call site that turns `ProgramResult.getDeleteAccounts()`/`markSelfDestruct` markers into an actual `deleteContract()` invocation at block-commit time (e.g., inside `Manager`/`TransactionTrace`). That link should be verified in a full session, but the absence of any storage-clearing logic in `deleteContract()`, `Storage`, and the `suicide`/`createContractImpl` paths themselves is directly confirmed from the code shown above and is sufficient to establish the root cause.

  public Storage(Storage storage) {
    this.addrHash = storage.addrHash.clone();
    this.address = storage.getAddress().clone();
    this.store = storage.store;
    this.contractVersion = storage.contractVersion;
    storage.getRowCache().forEach((DataWord rowKey, StorageRowCapsule row) -> {
      StorageRowCapsule newRow = new StorageRowCapsule(row);
      this.rowCache.put(rowKey.clone(), newRow);
    });
  }

  private byte[] compose(byte[] key, byte[] addrHash) {
    if (contractVersion == 1) {
      key = Hash.sha3(key);
    }
    byte[] result = new byte[key.length];
    arraycopy(addrHash, 0, result, 0, PREFIX_BYTES);
    arraycopy(key, PREFIX_BYTES, result, PREFIX_BYTES, PREFIX_BYTES);
    return result;
  }

  // 32 bytes
  private static byte[] addrHash(byte[] address) {
    return Hash.sha3(address);
  }

  private static byte[] addrHash(byte[] address, byte[] trxHash) {
    if (ByteUtil.isNullOrZeroArray(trxHash)) {
      return Hash.sha3(address);
    }
    return Hash.sha3(ByteUtil.merge(address, trxHash));
  }

  public DataWord getValue(DataWord key) {
    if (rowCache.containsKey(key)) {
      return new DataWord(rowCache.get(key).getValue());
    } else {
      StorageRowCapsule row = store.get(compose(key.getData(), addrHash));
      if (row == null || row.getInstance() == null) {
        return null;
      }
      rowCache.put(key, row);
      return new DataWord(row.getValue());
    }
  }

  public void put(DataWord key, DataWord value) {
    if (rowCache.containsKey(key)) {
      rowCache.get(key).setValue(value.getData());
    } else {
      byte[] rowKey = compose(key.getData(), addrHash);
      StorageRowCapsule row = new StorageRowCapsule(rowKey, value.getData());
      rowCache.put(key, row);
    }
  }

  public void commit() {
    rowCache.forEach((DataWord rowKey, StorageRowCapsule row) -> {
      if (row.isDirty()) {
        if (new DataWord(row.getValue()).isZero()) {
          this.store.delete(row.getRowKey());
        } else {
          this.store.put(row.getRowKey(), row);
        }
      }
    });
  }
