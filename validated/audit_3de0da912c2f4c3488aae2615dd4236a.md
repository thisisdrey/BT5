### Title
Path-scoped revision with embedded newline lets an unprivileged user inject a git-rev-list `--stdin` option line, bypassing the "operand-only" invariant - ([File: internal/git/gitcmd/command_description.go])

### Summary
`git.ValidateRevision` with `git.AllowPathScopedRevision()` only validates the ref portion of a `HEAD:path` revision and explicitly allows the path portion to contain any byte except NUL, including newlines and leading dashes. Several revision-consuming RPCs (`ListBlobs`, `ListAllBlobs`, `CheckObjectsExist`, LFS pointer listing, blob diffing) validate revisions this way and then feed the raw revision strings to `git-rev-list(1)` via `--stdin`, joined with `\n`, rather than through `commandDescription.args`'s per-argument `validatePositionalArg` dash check. A crafted revision such as `HEAD:foo\n--output=/some/path` therefore smuggles a second, option-like line into `git-rev-list --stdin`'s per-line argument parser.

### Finding Description
`ValidateRevision` in [1](#0-0)  cuts the revision at the first `:` when `allowPathScopedRevision` is set, and only the pre-colon ref portion is checked for leading `-`, whitespace, `:` and `\`. The post-colon path portion is completely unchecked, and the code comment states this is intentional: "it may contain all bytes except for the NUL byte." [2](#0-1) . `revision_test.go` explicitly confirms newlines are permitted in the path portion (`"refs/heads/main:path\n\t\r :\\"`, no error). [3](#0-2) 

`blobs.go`'s `verifyListBlobsRequest` validates each attacker-supplied `ListBlobsRequest.Revisions` entry with exactly `git.AllowPathScopedRevision()` (plus `AllowPseudoRevision()`), so a revision like `HEAD:x\n--output=/tmp/evil` passes validation. [4](#0-3) 

These revisions are then passed straight into `gitpipe.Revlist`, which does **not** route them through `commandDescription.args`'s positional-argument dash check (`validatePositionalArg`, which would reject a line starting with `-` — see [5](#0-4) ). Instead, `Revlist` joins all revisions with `\n` and streams them via `gitcmd.WithStdin` to `git rev-list --stdin`: [6](#0-5) . `git-rev-list --stdin` parses each line from stdin exactly as if it were a separate command-line argument (this is documented Git behavior), so an injected line beginning with `-` is treated as an option to `git-rev-list`, not as a revision operand.

The `args()` function's dash-based positional-argument guard in `command_description.go` never sees these individual stdin lines — it only validates argv-level `args`/`postSepArgs`, not stdin content — so the "user-controlled revisions are passed as operands only" invariant is violated for this code path. This is precisely the boundary the question calls out: a path-scoped revision's path portion carries option-like bytes (a newline followed by `-`) that escape operand-only handling.

### Impact Explanation
An unprivileged repository owner who can drive `ListBlobs` (or `ListAllBlobs`/`CheckObjectsExist`/LFS pointer RPCs that reuse the same `AllowPathScopedRevision` validation and stdin-based rev-list invocation) can inject an arbitrary `git-rev-list` option, e.g. `--output=<path>`, which since Git 2.19 lets rev-list write its output to an arbitrary file path reachable by the Gitaly process user — a file-write primitive outside the intended repository, and a stepping stone to further option injection (e.g. more exotic rev-list flags) in this and other revision-driven RPCs sharing the same validation helper. This matches the targeted GitLab bounty class of git argument/config injection via revision fields.

### Likelihood Explanation
Fully reachable by an ordinary, unprivileged GitLab user who owns/pushes to a repository and can call `ListBlobs` (or the sibling RPCs) with attacker-chosen `revisions` strings — no special role, no admin access, no secret required. The exploit only needs a single crafted revision string containing a `\n` followed by a dash-prefixed rev-list option; validation explicitly permits this today.

### Recommendation
When `AllowPathScopedRevision` (or any revision validation feeding a `--stdin`-based git invocation) is used, additionally reject newline bytes in the path component (not just the ref component), since Git's `--stdin` line-based parsers treat embedded newlines as argument separators. Alternatively, route all revision operands supplied to `--stdin` through the same positional-argument dash-prefix enforcement that `commandDescription.args` performs for argv, e.g. by validating each `\n`-split segment of the joined stdin payload before writing it, or by using `--end-of-options`-style stdin markers where supported.
