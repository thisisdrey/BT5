### Title
Positions with debt below `debtFloorInUsd / (1 - maxLiquidable)` become permanently unliquidatable, trapping bad debt - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate` enforces two bounds on the same `amountToRepay_`: it must not exceed `maxLiquidable` of the account's total debt, and the remaining debt must either be zero or stay at/above `debtFloorInUsd`. When `debtFloorInUsd > 0` and `maxLiquidable < 100%`, any account whose outstanding debt in a synthetic asset is smaller than `debtFloorInUsd / (1 - maxLiquidable)` cannot be liquidated at all: a full repay violates the max-liquidable cap and any partial repay violates the floor. Every call path reverts, so the position's collateral and bad debt are permanently frozen.

### Finding Description
In `Pool.liquidate` the repay amount is capped first: [1](#0-0) 

and then a floor check forces the remainder to be zero or `>= debtFloorInUsd`: [2](#0-1) 

Let `D` be the account's debt (in synth units) and `F_usd` the floor (converted via `quoteTokenToUsd`). For a liquidation to succeed the caller needs either:

- `amountToRepay_ = D` (erase debt) — but this requires `wadDiv(D, D) = 1e18 <= maxLiquidable`, i.e. only works when `maxLiquidable == 100%`, or
- `amountToRepay_ <= D * maxLiquidable` **and** `usdValue(D - amountToRepay_) >= F_usd`, i.e. `usdValue(D) - usdValue(D*maxLiquidable) >= F_usd`.

When `usdValue(D) < F_usd / (1 - maxLiquidable)` both branches fail for every `amountToRepay_`. There is no alternative entry point to clear such a position — `DebtToken.repay`/`repayAll` only let the account repay its own debt with its own synth, which does not rescue an underwater account that already spent the minted synth. The debt-floor check also applies symmetrically in `DebtToken.repay` (lines 442–450), so the same trap applies to voluntary partial repayment, though `repayAll` still works for the borrower.

An attacker can deliberately create such positions: deposit collateral, issue debt just above `debtFloorInUsd`, and let interest accrual or a price move push it underwater while keeping `usdValue(D)` inside the dead zone. Because `debtFloorInUsd` and `maxLiquidable` are pool-wide parameters and the check uses the debt token of the chosen `syntheticToken_`, an attacker holding multiple small debts across different synthetic assets can make each of them individually unliquidatable. The only recovery paths (governance lowering the floor or raising `maxLiquidable` to 100%) are privileged and out of the unprivileged-attacker model.

### Impact Explanation
Permanently unliquidatable positions mean seized-collateral proceeds can never be applied to the debt; the position's collateral is frozen inside `DepositToken` and the debt becomes bad debt backed by nothing once collateral value falls below debt value — direct protocol insolvency / permanent freezing of funds. This is the closest analog to the CVE's crash-DoS class: an edge-case arithmetic/config combination causes every liquidation call to revert unconditionally, killing the liveness of the liquidation mechanism for the affected positions.

### Likelihood Explanation
Likelihood is conditional: it requires `debtFloorInUsd > 0` and `maxLiquidable < 1e18` on the deployed pool (both are governor-set parameters, so if production config uses floor = 0 or maxLiquidable = 100% the bug is unreachable). When both hold, triggering is permissionless — any EOA can open a position sized into the dead zone, and ordinary price movement or interest accrual makes it unhealthy. No privileged role, oracle manipulation, or malicious infrastructure is needed; the attacker's cost is the collateral they deposit, which is also locked by the same mechanism.

### Recommendation
In `Pool.liquidate`, exempt full repayments from the `maxLiquidable` cap when the resulting remainder would be below the floor, e.g. allow `amountToRepay_ == _debtTokenBalance` regardless of `maxLiquidable`, or clamp the permitted repay so the remainder is either `0` or `>= debtFloorInUsd` (compute `_minRepay = _debtTokenBalance - floorInSynth` and cap liquidations to `[_minRepay, _debtTokenBalance]` when a partial liquidation would leave dust). Alternatively, when the position is in the dead zone, permit repaying the entire debt.

### Proof of Concept
Hardhat sketch (reproducible against the repo's existing fixtures in `test/Pool.test.ts`):

```ts
// setup: pool with debtFloorInUsd = F > 0 and maxLiquidable = 0.5e18 (50%)
await pool.updateDebtFloor(F);                       // e.g. parseEther('3000')
await pool.updateMaxLiquidable(parseEther('0.5'));

// attacker deposits collateral and issues debt D such that
// usd(D) is in (F, F / (1 - 0.5)) => e.g. usd(D) = $4,500 < $6,000
await msdMET.connect(attacker).deposit(collateral, attacker.address);
await msEthDebtToken.connect(attacker).issue(D, attacker.address); // usd(D) ≈ $4,500

// price moves -> position unhealthy
await masterOracle.updatePrice(met.address, crashPrice);
expect((await pool.debtPositionOf(attacker.address))._isHealthy).to.be.false;

// 1) full liquidation reverts on maxLiquidable
await expect(
  pool.liquidate(msEth.address, attacker.address, D, msdMET.address)
).revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');

// 2) max-allowed partial liquidation reverts on the floor
const max = await pool.quoteLiquidateMax(msEth.address, attacker.address, msdMET.address);
await expect(
  pool.liquidate(msEth.address, attacker.address, max, msdMET.address)
).revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor');

// every amountToRepay_ in (0, D] reverts -> position is permanently unliquidatable
```

The two reverts are exercised at `Pool.sol:567` and `Pool.sol:577` respectively; together they cover the entire domain of `amountToRepay_`, demonstrating permanent freezing of the account's collateral and unrecoverable bad debt.
