### Title
Unprivileged asset transfers force involuntary consumer-reference consumption on the recipient, enabling a `MaxConsumers` exhaustion DoS - (File: `substrate/frame/assets/src/functions.rs`)

### Summary
`pallet-assets` lets any transfer of a **non-sufficient** asset to a fresh (zero-balance) account silently create that account and bump the recipient's `frame_system` consumer-reference counter — exactly the same "receiver state forcibly changed by sender, with recurring downstream cost" pattern flagged in the external ParaSpace report (auto-enabling collateral for the receiver). Here the forced state is a `consumers` increment, and the downstream cost is exhaustion of the account's fixed `MaxConsumers` budget, which blocks the victim from later performing any other consumer-gated action (staking bond, vesting, holds, additional non-sufficient asset accounts, etc.).

### Finding Description
When `transfer_and_die` credits a destination account that has no existing `Account` entry for the asset, it calls `Self::new_account(dest, details, None)`: [1](#0-0) 

`new_account` decides how the new asset-account "pays" for its existence. For a non-sufficient asset (the default and most common case — `create()` produces `is_sufficient: false`), it unconditionally increments the recipient's consumer reference count, with no consent or opt-out from the recipient: [2](#0-1) 

The only guard is `can_inc_consumer`, which merely prevents a *single* increment from overflowing `MaxConsumers` — it does nothing to stop an attacker from repeating this across many different asset IDs to slowly fill up the victim's finite consumer budget: [3](#0-2) 

Because `create()` for a new asset class is a public, permissionless extrinsic (subject only to a refundable `AssetDeposit` paid by the creator, not the victim), an attacker can mint an arbitrary number of distinct non-sufficient asset classes and push a minimal (min-balance) transfer of each into the victim's account. Each such transfer silently consumes one of the victim's limited consumer slots (`System::Account.consumers`), exactly mirroring the reported bug class: the sender's normal, permissionless action ("transfer collateral" / "transfer an asset") forces an unwanted persistent state change ("collateral enabled" / "consumer ref taken") onto the receiver, whose future operations become more constrained/expensive as a result.

### Impact Explanation
Once an attacker drives the victim's `consumers` counter to `MaxConsumers`, the victim can no longer perform any action elsewhere in the runtime that requires taking a new consumer reference — this includes bonding for staking, acquiring additional holds/locks, or opening more non-sufficient asset accounts — because `inc_consumers` will return `DispatchError::TooManyConsumers`: [4](#0-3) 

This is a genuine denial-of-service against the victim's account capabilities, imposed entirely by an unprivileged third party at low cost (only the `AssetDeposit`, which the attacker retains custody of/can reclaim later) and with zero opt-in from the victim, matching the "runtime bug that compromises intended behavior" and account-capability lock categories in scope.

### Likelihood Explanation
High feasibility: `create()` and `transfer()` are both plain, unprivileged, publicly dispatchable extrinsics; no governance, admin, relayer, or validator collusion is required. The only cost to the attacker is the per-asset `AssetDeposit`, and the number of distinct asset classes needed to exhaust `MaxConsumers` is small (bounded by the runtime's configured `MaxConsumers`, commonly a two- or three-digit value across production runtimes).

### Recommendation
Do not force a consumer reference onto the *recipient* purely as a side effect of an inbound transfer initiated by someone else. Options:
- Require the recipient to explicitly `touch`/opt in to holding a non-sufficient asset (as already supported by `do_touch`) before an unsolicited transfer can create the account, or
- Charge the depositor/sender (not the recipient) for account creation and avoid consuming the recipient's consumer budget, similar to how `DepositFrom` already lets a third party pay a deposit instead of taking a consumer ref: [5](#0-4) 

### Proof of Concept
1. Attacker calls `Assets::create` `N` times to mint `N` distinct non-sufficient asset classes (paying `N × AssetDeposit`), then `Assets::mint` a minimal supply to itself for each.
2. For each asset class `i`, attacker calls `Assets::transfer(origin=attacker, id=i, target=victim, amount=min_balance_i)`.
3. Each transfer hits `transfer_and_die`, sees `victim` has no `Account` entry for asset `i`, and calls `new_account`, which increments `victim`'s `System::Account.consumers` by 1 — without any action or consent from `victim`.
4. Repeat until `victim.consumers == MaxConsumers`.
5. `victim` subsequently attempts a consumer-gated action (e.g., `Staking::bond`, another `Assets` `touch`, or a `Balances::hold`) and receives `DispatchError::TooManyConsumers`/`NoProviders`-style failures, unable to proceed until they manually clean up the unwanted asset accounts (paying gas/weight for each `refund`/`transfer_ownership`/dust cleanup) — the same "victim pays to undo a state the attacker forced on them" pattern as the ParaSpace collateral report.

	pub(super) fn new_account(
		who: &T::AccountId,
		d: &mut AssetDetails<T::Balance, T::AccountId, DepositBalanceOf<T, I>>,
		maybe_deposit: Option<(&T::AccountId, DepositBalanceOf<T, I>)>,
	) -> Result<ExistenceReasonOf<T, I>, DispatchError> {
		let accounts = d.accounts.checked_add(1).ok_or(ArithmeticError::Overflow)?;
		let reason = if let Some((depositor, deposit)) = maybe_deposit {
			if depositor == who {
				ExistenceReason::DepositHeld(deposit)
			} else {
				ExistenceReason::DepositFrom(depositor.clone(), deposit)
			}
		} else if d.is_sufficient {
			frame_system::Pallet::<T>::inc_sufficients(who);
			d.sufficients.saturating_inc();
			ExistenceReason::Sufficient
		} else {
			frame_system::Pallet::<T>::inc_consumers(who)
				.map_err(|_| Error::<T, I>::UnavailableConsumer)?;
			// We ensure that we can still increment consumers once more because we could otherwise
			// allow accidental usage of all consumer references which could cause grief.
			if !frame_system::Pallet::<T>::can_inc_consumer(who) {
				frame_system::Pallet::<T>::dec_consumers(who);
				return Err(Error::<T, I>::UnavailableConsumer.into());
			}
			ExistenceReason::Consumer
		};
		d.accounts = accounts;
		Ok(reason)
	}

	/// Increment the reference counter on an account.
	///
	/// The account `who`'s `providers` must be non-zero and the current number of consumers must
	/// be less than `MaxConsumers::max_consumers()` or this will return an error.
	pub fn inc_consumers(who: &T::AccountId) -> Result<(), DispatchError> {
		Account::<T>::try_mutate(who, |a| {
			if a.providers > 0 {
				if a.consumers < T::MaxConsumers::max_consumers() {
					a.consumers = a.consumers.saturating_add(1);
					Ok(())
				} else {
					Err(DispatchError::TooManyConsumers)
				}
			} else {
				Err(DispatchError::NoProviders)
			}
		})
	}

/// The reason for an account's existence within an asset class.
#[derive(Clone, Encode, Decode, Eq, PartialEq, Debug, MaxEncodedLen, TypeInfo)]
pub enum ExistenceReason<Balance, AccountId> {
	/// A consumer reference was used to create this account.
	#[codec(index = 0)]
	Consumer,
	/// The asset class is `sufficient` for account existence.
	#[codec(index = 1)]
	Sufficient,
	/// The account holder has placed a deposit to exist within an asset class.
	#[codec(index = 2)]
	DepositHeld(Balance),
	/// A deposit was placed for this account to exist, but it has been refunded.
	#[codec(index = 3)]
	DepositRefunded,
	/// Some other `AccountId` has placed a deposit to make this account exist.
	/// An account with such a reason might not be referenced in `system`.
	#[codec(index = 4)]
	DepositFrom(AccountId, Balance),
}
