### Title
Single-IP QUIC handshake-attempt flooding evades per-IP connection rate limiting and monopolizes the global concurrent-connection budget - (File: streamer/src/nonblocking/quic.rs, streamer/src/nonblocking/connection_rate_limiter.rs)

### Summary
`ConnectionRateLimiter::is_allowed` in `streamer/src/nonblocking/connection_rate_limiter.rs:34-40` is a non-mutating token check, and `register_connection` (line 42-50) is only invoked in `setup_connection` (`streamer/src/nonblocking/quic.rs:483`) after the QUIC handshake completes inside a `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting)` (line 472, 2-second window). An attacker from a single source IP can therefore open many concurrent handshake attempts before any of them completes, and every one of them will pass `is_allowed` because no tokens are consumed until a handshake finishes.

### Finding Description
In `run_server` (`streamer/src/nonblocking/quic.rs:304-411`), each accepted `incoming` connection is checked against:
1. `overall_connection_rate_limiter.current_tokens() == 0` (non-mutating check, line 347)
2. `rate_limiter.is_allowed(&incoming.remote_address().ip())` (non-mutating check, line 359)
3. `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())` (line 371-379), which is the only *mutating* gate at accept time, and it enforces a **global**, not per-IP, cap (`streamer/src/nonblocking/quic.rs:236-252`, comparing `stats.open_connections` to `max_concurrent_connections()`).

Only after `incoming.accept()` succeeds does `setup_connection` run (line 389-399), which awaits the handshake with a 2-second timeout (line 472) and only calls `rate_limiter.register_connection(&from.ip())` (line 483) — the sole token-consuming call — once the handshake actually completes.

Because `is_allowed` never mutates state, and `register_connection` fires only post-handshake, an attacker holding open N parallel half-completed QUIC handshakes from the same source IP will have all N of them pass `is_allowed` (since none has yet decremented a token) and will occupy N slots of the *global* `ClientConnectionTracker` / `max_concurrent_connections` budget and N slots of `stats.outstanding_incoming_connection_attempts` for up to the full `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) — all attributable to one IP address. The per-IP `ConnectionRateLimiter` (`DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE`) provides no bound on the number of *outstanding/unregistered* attempts from a given IP; it only throttles the rate of *completed* handshakes. The `overall_connection_rate_limiter` check at line 347 is similarly a non-mutating pre-check (actual `consume_tokens` happens post-handshake at line 495), so it too can be raced by an in-flight-attempt flood before any single attempt completes and decrements it.

The comment at lines 332-340 acknowledges the design tradeoff ("shed fast... before a peer has asserted control over their ip via retry... to avoid enabling IP-spoofing attacks") but this tradeoff means the only real defense against attempt flooding is the **global** `max_concurrent_connections` limit from `ClientConnectionTracker`, not a per-IP cap on outstanding attempts.

### Impact Explanation
A single unstaked/unprivileged remote client can consume the server's entire global handshake/connection-attempt budget (`qos.max_concurrent_connections()`) and inflate `stats.outstanding_incoming_connection_attempts` for the full 2-second handshake window, by opening many parallel QUIC Initial packets from one IP without ever completing a handshake. This starves other IPs (including legitimate stakers) from being able to open new QUIC connections to the TPU port during that window, since `ClientConnectionTracker::new` will fail once the global cap is hit (`refused_connections_too_many_open_connections`, line 374-378). This is a resource-exhaustion/QoS-evasion issue: cheap attacker-side work (opening TCP-less UDP/QUIC Initial packets) forces disproportionate server-side handshake CPU/memory and denial of connection slots to others, consistent with the "unprivileged attacker forcing work vastly exceeding fees collected, degrading the leader" bounty category.

### Likelihood Explanation
Highly feasible and repeatable: it requires only opening many parallel QUIC connections (`Endpoint::connect`/raw UDP Initial packets) from one source IP, deliberately stalling or not completing the handshake (e.g., not responding to the server's Handshake-phase packets) so they remain "outstanding" for the full 2-second timeout, and repeating this continuously. No stake, keys, or special access is required — this is exactly the "unstaked remote client opening QUIC connections to a leader's public TPU port" attacker model in scope. The only precondition is that the attacker's aggregate outstanding attempts approach `qos.max_concurrent_connections()`, which is a fixed, known validator-side constant.

### Recommendation
Add a per-IP cap on outstanding/unregistered connection attempts (distinct from the post-handshake rate limiter), e.g., track `outstanding_incoming_connection_attempts` per `IpAddr` (similar structure to `ConnectionRateLimiter`'s `KeyedRateLimiter`) and reject/`incoming.ignore()` new accepts from an IP that already has more than a small fixed number (e.g., a few) of in-flight, unregistered handshake attempts. Alternatively, consume a rate-limiter token optimistically at accept time (before the handshake) and refund it if the handshake fails/times out, so that `is_allowed`/`register_connection` semantics can't be raced by attempt volume rather than completed-connection volume.

### Proof of Concept
Integration test plan (extends existing tests near `streamer/src/nonblocking/quic.rs` test module and `check_block_multiple_connections`, `streamer/src/nonblocking/quic.rs:1177+`):
1. Spawn a QUIC test server via `setup_quic_server` with a low `max_connections_per_ipaddr_per_min` (e.g., 8, matching `DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE`) and a moderately-sized `qos.max_concurrent_connections()`.
2. From a single client IP (loopback test harness), spawn `N` (e.g., 50) parallel `quinn` client connection attempts that intentionally stall the handshake (e.g., connect but never send/receive the final Handshake packet, or use a client-side delay > `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`).
3. While these are in flight, poll `stats.outstanding_incoming_connection_attempts` and assert it grows well beyond `max_connections_per_ipaddr_per_min` (i.e., not bounded by any per-IP cap), only bounded by the global `max_concurrent_connections`.
4. Concurrently attempt a legitimate connection from a *different* IP and assert it is refused (`refused_connections_too_many_open_connections` stat increments) due to the global cap being exhausted by the single attacking IP — demonstrating that one IP can deny service to others.

Expected result confirming the bug: `stats.outstanding_incoming_connection_attempts` for the attacking IP exceeds `max_connections_per_ipaddr_per_min` and approaches the global `max_concurrent_connections`, and a legitimate different-IP connection is refused due to global exhaustion, proving there is no per-IP bound on outstanding attempts as the existing `ConnectionRateLimiter` only gates completed (post-handshake) connections.
