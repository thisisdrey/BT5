## Confirmed: `repay()` does NOT require oracle price resolution
Good — `repay` in `v0-4-market.clar` (and `market.clar`) only reads scaled debt, computes `amount-to-repay`, and calls `vault-system-repay` / `debt-remove-scaled`. It never calls `get-assets`, `get-notional-evaluation`, `write-feeds`, or `price-resolve`. So repay is unaffected by oracle outages. The vulnerable path is specifically `collateral-remove` (and `borrow`, `liquidate`, `collateral-add` new-collateral path) when the position has debt.

### Title
Single failing collateral/debt asset price oracle (including external `ststx-ratio` callcode dependency) reverts `collateral-remove`/`borrow`/`liquidate` for a user's entire position, freezing withdrawal of unrelated, healthy collateral - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`collateral-remove`, `borrow`, and `liquidate` all require a full notional (USD) valuation of *every* asset (collateral and debt) a user currently holds before allowing the requested operation, even when that operation only concerns a single, unrelated asset. This valuation is produced by `get-assets` → `price-multi-resolve` → `iter-price-multi` → `price-resolve`, which folds over the full list of held asset oracle configs and aborts the *entire* batch if any single asset's price resolution fails [1](#0-0) . Price resolution for `stSTX`/`zstSTX`/`zstSTXbtc` assets additionally depends on a live external contract call to `'SP4SZE494VC2YC5JYG7AYFQ44F5Q4PYV7DVMDPBG.block-info-nakamoto-ststx-ratio-v2 get-ststx-ratio-v3` via `resolve-ststx`/`call-ststx-ratio` [2](#0-1) [3](#0-2) . If that external protocol reverts, pauses, or the Pyth/DIA feed for one held asset goes stale/unavailable, `price-resolve` returns an error via `unwrap!`, `ERR-ORACLE-CALLCODE`/`ERR-ORACLE-INVARIANT` propagates through `iter-price-multi`, and `price-multi-resolve` fails the whole batch with `ERR-ORACLE-MULTI`, which is force-unwrapped with `unwrap-panic` inside `get-assets` [4](#0-3) .

This mirrors the SafEth `stake()` root cause: a single failing external dependency for one item in a multi-item batch causes the entire transaction (and thus operations on unrelated, healthy items) to revert.

### Finding Description
In `collateral-remove`, when the user has any debt, the function must compute `collateral-value`/`debt-value` across the user's *entire* position mask before allowing removal of a single specific collateral asset [5](#0-4) . This is done via:
- `assets (get-assets position-mask)` — resolves prices for every collateral+debt asset the user holds [4](#0-3) .
- `get-notional-evaluation` folds over that asset list to sum collateral/debt USD values [6](#0-5) .

`get-assets` calls `price-multi-resolve`, which `fold`s `iter-price-multi` over the oracle configs of all held assets and asserts the whole result is `valid` [1](#0-0) . `iter-price-multi` short-circuits to `valid: false` the moment any single `price-resolve` call fails [7](#0-6) , and `price-multi-resolve` then returns `ERR-ORACLE-MULTI` for the batch, which `get-assets` immediately `unwrap-panic`s, aborting the entire transaction [8](#0-7) .

`price-resolve` itself depends on external, out-of-protocol systems that can independently fail:
- Pyth: `resolve-pyth`/`call-pyth` reading `pyth-storage-v4` — reverts `ERR-ORACLE-PYTH` if unavailable, and also enforces a confidence-ratio check that can revert `ERR-PRICE-CONFIDENCE-LOW` [9](#0-8) .
- DIA: `resolve-dia`/`call-dia` — reverts `ERR-ORACLE-DIA` [10](#0-9) .
- Callcode transforms: `resolve-ststx` calls the external `block-info-nakamoto-ststx-ratio-v2` contract; any revert there (pause, upgrade, unavailability) propagates as `ERR-ORACLE-CALLCODE` [2](#0-1) [3](#0-2) .
- Freshness: `oracle-timestamp-fresh`/`oracle-price-legal` checks inside `price-resolve` also abort with `ERR-ORACLE-INVARIANT` if a feed is stale for even one held asset [11](#0-10) .

Because `get-assets` resolves prices for *every* asset in the user's mask (not just the asset being withdrawn), a user holding e.g. a healthy `USDC` collateral position and also a small `stSTX` collateral position cannot withdraw the `USDC` at all if the `stSTX` ratio provider or its Pyth/DIA feed is temporarily broken — even though the requested withdrawal has nothing to do with `stSTX`. The same applies to `borrow` (which requires `assets`/notional evaluation of the full mask before allowing any new borrow) [12](#0-11)  and to `liquidate` (which also computes full-position notional value before any partial liquidation can proceed) [13](#0-12) .

By contrast, `repay()` is unaffected because it performs no price resolution at all — confirmed by direct code inspection [14](#0-13) .

### Impact Explanation
This is a **temporary freezing of funds** issue: users holding multiple collateral/debt assets simultaneously lose the ability to withdraw perfectly healthy, unrelated collateral (or to borrow, or for liquidators to liquidate unhealthy positions) for as long as any single one of their held assets' oracle/callcode dependency is degraded (stale Pyth/DIA feed, DIA outage, or the external `ststx-ratio` contract reverting/pausing). During a market downturn this is precisely when liquidations are most needed, so a stalled `liquidate()` path due to one asset's oracle failure can also delay bad-debt realization protocol-wide, compounding losses. This lands in the in-scope **Impact** class of "temporary freezing of funds."

### Likelihood Explanation
Likelihood is moderate: it requires (a) a user to hold at least two distinct assets in one position (a normal, encouraged usage pattern given the "rehypothecatable collateral"/multi-asset egroup design), and (b) one of those assets' price feed or callcode dependency to fail or go stale, which can happen due to legitimate operational events on the third-party oracle/`ststx-ratio` provider side (pause, upgrade, RPC outage, guardian-set rotation for Pyth, DIA node downtime) without any malicious action needed. Given six supported assets and cross-asset egroups being a core design feature, multi-asset positions should be common.

### Recommendation
- Decouple price resolution needed for the *specific* asset being withdrawn/borrowed/liquidated from resolution of the full position mask where possible, or allow degraded-mode valuation (e.g., skip/exclude an asset whose oracle is failing from the notional sum with a conservative penalty, similar to how `collateral-remove`'s "disabled collateral" branch already handles asset-specific price lookups) rather than failing the entire batch.
- In `iter-price-multi`/`price-multi-resolve`, consider a partial-success mode: return per-asset success/failure and let the caller decide whether the failing asset is relevant to the requested operation, instead of `unwrap-panic`-ing the whole list on any single failure.
- For the `stSTX` external ratio dependency specifically, cache the last-known-good ratio with a bounded staleness window so a momentary revert from `block-info-nakamoto-ststx-ratio-v2` doesn't block operations on other assets.

### Proof of Concept
1. User deposits `USDC` as collateral and separately deposits `stSTX` as collateral, then borrows some `USDC`-equivalent debt against the combined position (multi-asset egroup).
2. The `stSTX` ratio provider `'SP4SZE494VC2YC5JYG7AYFQ44F5Q4PYV7DVMDPBG.block-info-nakamoto-ststx-ratio-v2` is paused/upgraded/reverts (or the Pyth feed backing `stSTX`'s base price goes stale beyond `max-staleness`).
3. User calls `collateral-remove` to withdraw only their `USDC` collateral, well within health limits, unrelated to `stSTX`.
4. `collateral-remove` (has-debt branch) invokes `get-assets position-mask` → `price-multi-resolve` → `iter-price-multi`, which calls `price-resolve` for the `stSTX` oracle entry, which calls `resolve-ststx` → `call-ststx-ratio` → the paused/reverting external contract [2](#0-1) .
5. This failure propagates as `ERR-ORACLE-CALLCODE`/stale-feed `ERR-ORACLE-INVARIANT` through `iter-price-multi` → `price-multi-resolve` returns `(err ERR-ORACLE-MULTI)` → `get-assets`'s `unwrap-panic` aborts the whole transaction [4](#0-3) .
6. Result: the user cannot withdraw their healthy `USDC` collateral (nor borrow more, nor be liquidated if unhealthy) until the unrelated `stSTX` oracle/callcode dependency is restored — funds are temporarily frozen due to a dependency wholly unrelated to the requested operation.
