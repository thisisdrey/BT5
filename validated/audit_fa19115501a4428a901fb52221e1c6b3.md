This confirms the analog. `ExchangeTransactionContract` (swap) has an explicit `expected` slippage-protection field checked at validation time (`ExchangeTransactionActuator.java:175,190-192,217-221`), but `ExchangeInjectContract` and `ExchangeWithdrawContract` (liquidity add/remove) have no equivalent minimum/maximum bound — the "another token" amount is computed purely from whatever the pool's reserve ratio happens to be at execution time, with no way for the caller to cap it.

### Title
Missing Slippage Protection in ExchangeInject/ExchangeWithdraw Allows Frontrunning-Induced Fund Loss - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java, actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
The TRON on-chain bancor-style `Exchange` (AMM-like liquidity pool, `ExchangeCapsule`) lets any account inject or withdraw liquidity proportional to the pool's current reserve ratio via `ExchangeInjectContract`/`ExchangeWithdrawContract`. Unlike `ExchangeTransactionContract` (a swap), which carries an `expected` field enforced against the computed output before execution, the inject/withdraw contracts carry no counterpart slippage bound on the computed "another token" amount.

### Finding Description
In `ExchangeInjectActuator.execute()`, the amount of the paired token (`anotherTokenQuant`) is derived strictly from the exchange's live `firstTokenBalance`/`secondTokenBalance` at execution time: [1](#0-0) 
The same pattern exists for `ExchangeWithdrawActuator.execute()`: [2](#0-1) 
Both contracts (`ExchangeInjectContract`, `ExchangeWithdrawContract`) only carry `exchange_id`, `token_id`, and `quant` — no `expected`/minimum field: [3](#0-2) 
By contrast, `ExchangeTransactionContract` explicitly validates the computed output against a caller-supplied `expected` minimum before it is allowed to execute: [4](#0-3) 

Because a validator/miner or any user can submit an `ExchangeTransactionContract` (swap) transaction that shifts `firstTokenBalance`/`secondTokenBalance` before a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` from another account is applied within the same block or via reordering across blocks, the victim's inject/withdraw is executed against a manipulated ratio with no on-chain mechanism to reject an unfavorable outcome — directly mirroring the reported `buyShares` frontrunning class where the pool's reserve ratio at execution time, not at submission time, determines value received, and no return-value/slippage check exists to protect the caller.

### Impact Explanation
A frontrunner can imbalance the pool's reserve ratio immediately before a victim's `ExchangeInjectContract` executes, causing the victim to be charged an excess amount of the "another token" (computed via `floorDiv(multiplyExact(...))` off the manipulated balances) relative to the ratio they intended when constructing the transaction. The attacker can then reverse their swap or withdraw, extracting value contributed by the victim. The same applies symmetrically to `ExchangeWithdrawActuator`, where the victim can receive less of the paired token than expected. This is a direct, unauthorized value transfer between chain participants with no minimum-bound enforcement, unlike the swap path.

### Likelihood Explanation
This is reachable by any account submitting ordinary signed transactions (`ExchangeInjectContract`, `ExchangeWithdrawContract`, `ExchangeTransactionContract`) — no special privileges are required. Given that transaction ordering within a block is controlled by the block-producing witness and transactions are visible in the mempool/network before confirmation, an attacker can reliably front-run a known pending inject/withdraw transaction.

### Recommendation
Add an `expected`-style bound (minimum acceptable `anotherTokenQuant` for inject, and minimum/maximum for withdraw) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` and `ExchangeWithdrawActuator.doValidate()`/`execute()`, analogous to the existing `tokenExpected` check in `ExchangeTransactionActuator.java:219-221`.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` from victim (`exchange_id=E`, `token_id=firstToken`, `quant=Q`) in the mempool.
2. Attacker submits an `ExchangeTransactionContract` swap against exchange `E` that shifts `firstTokenBalance`/`secondTokenBalance` significantly, and ensures it lands in the same block before the victim's transaction (via fee/energy ordering or by broadcasting through a cooperating SR).
3. Victim's `ExchangeInjectContract` executes: `anotherTokenQuant` is recomputed off the now-imbalanced `secondTokenBalance`/`firstTokenBalance` [5](#0-4) , causing the victim to be debited a different (unfavorable) `anotherTokenQuant` than they would have gotten against the pre-manipulation ratio, with `doValidate()` performing no check that this matches the victim's expectations.
4. Attacker reverses the initial swap, extracting the value shifted from the victim's excess contribution.
