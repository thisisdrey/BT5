### Title
Unbounded body read in `process_event` allows single-request memory-exhaustion DoS against the signer's event listener - (File: libsigner/src/events.rs)

### Summary
`process_event<T, E>` reads the entire HTTP request body via `request.as_reader().read_to_string(&mut body)` with no size cap, unlike the chunked-decoding path in `libsigner/src/http.rs` which bounds reads with `MAX_MESSAGE_LEN`. Because the signer's event-receiver port is commonly configured to bind on `0.0.0.0` (per the sample configs) and performs no authentication on inbound POSTs, a remote unprivileged attacker who can reach that port can send a single POST with an oversized body to force an unbounded allocation/read.

### Finding Description
`SignerEventReceiver::next_event` dispatches POST requests to `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, and `/new_block` into `process_event::<T, E>` [1](#0-0) . Inside `process_event`, the body is read fully into a `String` with no bound: `let mut body = String::new(); request.as_reader().read_to_string(&mut body)` before any `serde_json::from_slice` deserialization is attempted [2](#0-1) . This contrasts with `libsigner/src/http.rs::decode_http_body`, which bounds chunked bodies using `HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into())` [3](#0-2) . No equivalent cap exists in the `events.rs` path, confirming the broken equality the question describes: bytes read == whatever the client sends, not a bounded/validated size.

The signer's event endpoint (`SignerEventReceiver::bind`, used by `Signer::spawn`) is a plain `tiny_http::Server` with no authentication check on inbound requests in this code path [4](#0-3) . The reference sample configuration explicitly instructs operators to bind this listener to `0.0.0.0:30000` [5](#0-4) , meaning in a realistic deployment following the documented configuration, this endpoint is remotely reachable without any credential (the `auth_password`/`auth_token` pairing documented in these configs governs the signer's outbound calls to the node's RPC, not inbound POSTs to the signer's own listener).

### Impact Explanation
An attacker who can open a TCP connection to the signer's event-receiver port can POST to any of the four dispatched URLs with a large `Content-Length` and body, causing the signer process to allocate memory proportional to the attacker-supplied body before any validation or size check occurs. Because `tiny_http`'s reader is bound only by the actual bytes transferred (not merely the declared header), exploitation requires the attacker to transmit the oversized payload, but no authentication, size cap, or early rejection exists to stop it once transmission begins. Repeated requests can be used to repeatedly drive up memory usage or degrade the single-threaded `next_event` loop, since only one request is processed at a time in `main_loop`.

### Likelihood Explanation
Preconditions: the operator must have configured the signer's `endpoint` to be reachable from the network (the shipped sample config explicitly recommends `0.0.0.0:30000`), and no additional network-level firewalling restricts access. No secrets, peer identity, or StackerDB slot ownership are required — this is a bare TCP connection to an HTTP listener. This matches the "attacker is unprivileged remote party" threat model. The attack is trivially repeatable at low attacker cost (one HTTP POST per attempt), though the cost scales with payload size since actual bytes must be transmitted, distinguishing it from a pure header-only trigger.

### Recommendation
Impose a `MAX_MESSAGE_LEN`-style cap in `process_event` before/while reading the body — e.g., check the `Content-Length` header against a maximum and reject oversized requests early, and/or use a bounded reader (`Read::take(MAX_MESSAGE_LEN)`) instead of unconditional `read_to_string`, mirroring the bound already applied in `libsigner/src/http.rs::decode_http_body`.

### Proof of Concept
```rust
// libsigner/src/tests (illustrative)
#[test]
fn test_process_event_unbounded_body() {
    let mut receiver: SignerEventReceiver<SomeSignerMessageType> = SignerEventReceiver::new(false);
    let addr = receiver.bind("127.0.0.1:0".parse().unwrap()).unwrap();
    let handle = std::thread::spawn(move || receiver.next_event());

    let mut stream = std::net::TcpStream::connect(addr).unwrap();
    let huge_body = vec![b'A'; 500_000_000]; // 500MB, non-JSON
    let req = format!(
        "POST /stackerdb_chunks HTTP/1.1\r\nHost: {addr}\r\nContent-Length: {}\r\n\r\n",
        huge_body.len()
    );
    stream.write_all(req.as_bytes()).unwrap();
    stream.write_all(&huge_body).unwrap();

    // Assertion: process memory/RSS grows by ~500MB proportional to the single
    // request before any JSON validation or length cap is applied in
    // `process_event` (libsigner/src/events.rs:524-537), unlike the
    // MAX_MESSAGE_LEN-bounded path in libsigner/src/http.rs:207.
    let _ = handle.join();
}
```
