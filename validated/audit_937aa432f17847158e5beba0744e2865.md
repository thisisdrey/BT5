## Title
Panic-on-underflow in `Bank::accrue_interest` time-delta calculation can permanently brick a bank - (File: `programs/marginfi/src/state/bank.rs`)

### Summary
The RRUtils report is about a comparison/subtraction of two numbers that is expected to be monotonic (RFC1982 serial numbers) but is implemented with a signed subtraction that can revert on legitimate wraparound inputs instead of handling them safely. The closest reachable analog in marginfi-v2 is `Bank::accrue_interest`, which computes the elapsed time since the bank's last update via a raw signed subtraction and an infallible `.try_into().unwrap()` cast, with no saturating/checked fallback, unlike the rest of the codebase which consistently uses `checked_sub`/`saturating_sub` for this exact class of arithmetic.

### Finding Description
`Bank::accrue_interest` computes the interest-accrual time window as: [1](#0-0) 

```rust
fn accrue_interest(
    &mut self,
    current_timestamp: i64,
    group: &MarginfiGroup,
    #[cfg(not(feature = "client"))] bank: Pubkey,
) -> MarginfiResult<()> {
    ...
    let time_delta: u64 = (current_timestamp - self.last_update).try_into().unwrap();
    if time_delta == 0 {
        return Ok(());
    }
    ...
```

This is called unconditionally from every unprivileged, revenue-generating instruction that touches a bank — deposit, withdraw, borrow, repay, liquidate, and the permissionless `lending_pool_accrue_bank_interest` — via `bank.accrue_interest(clock.unix_timestamp, &group, ...)`: [2](#0-1) [3](#0-2) 

If `self.last_update` (an `i64` field on `Bank`) is ever greater than the live `clock.unix_timestamp` supplied to this function, `current_timestamp - self.last_update` becomes negative. Converting a negative `i64` into a `u64` via `try_into()` returns `Err`, and `.unwrap()` on that `Err` triggers a Rust panic, which aborts the whole transaction with an unrecoverable program error (not a graceful `MarginfiError`) for every single instruction that touches that bank going forward, since `accrue_interest` runs before any of the bank's other state can be mutated. This exactly mirrors the RRUtils flaw: an arithmetic comparison that is supposed to represent "time elapsed since last update" is implemented with a raw signed op instead of the safe pattern (`checked_sub`/`saturating_sub`) used everywhere else in the codebase (e.g. `checked_sub` for oracle staleness in `programs/marginfi/src/state/price.rs`, `saturating_sub` in `programs/marginfi/src/state/marginfi_group.rs`).

`self.last_update` is set to `Clock::get()?.unix_timestamp` on every `accrue_interest`/`update_bank_cache` call: [4](#0-3) 

Under strictly monotonic validator clocks this invariant should hold. However, this reasoning is not proven safe in-repo: there is no `checked_sub`/saturating guard here, unlike the analogous, more carefully written computations elsewhere in the codebase, and Solana's `Clock::unix_timestamp` is *not* guaranteed strictly monotonic across all slots/leaders in all conditions (minor backward jitter across leader transitions is a known Solana characteristic). Given that `accrue_interest` gates every single unprivileged user action (deposit/withdraw/borrow/repay/liquidate) on this unchecked arithmetic, any clock regression — however rare — permanently panics and blocks all interactions with the affected bank.

### Impact Explanation
If the underflow is ever triggered, the impacted bank becomes permanently unusable: every deposit, withdraw, borrow, repay, and liquidation against that bank panics before completing, because `accrue_interest` runs first in each of these unprivileged instruction handlers. This is a permanent lock/freeze of a core accounting path with no unprivileged recovery mechanism, since the panic occurs deterministically for any `current_timestamp <= self.last_update` and there is no user-facing instruction that can reset `last_update`.

### Likelihood Explanation
Likelihood is low-to-uncertain because it depends on an anomaly in `Clock::unix_timestamp` moving backward (or otherwise being less than a previously recorded value) between two on-chain calls to `accrue_interest` for the same bank — something the code implicitly assumes never happens but does not defensively guard against, unlike comparable timestamp arithmetic elsewhere in the same codebase. I could not find and did not have tooling access to confirm a concrete, attacker-controlled trigger for a backward clock value within this repository; this is analogous to the ENS finding itself being rated Medium precisely because the triggering condition, while real, requires specific edge-case conditions.

### Recommendation
Replace the unchecked signed subtraction/cast with a checked or saturating computation, e.g.:
```rust
let time_delta: u64 = current_timestamp
    .checked_sub(self.last_update)
    .filter(|&d| d >= 0)
    .map(|d| d as u64)
    .unwrap_or(0);
```
or explicitly reject/no-op on a negative delta with a proper `MarginfiError` instead of panicking, consistent with the `checked_sub`/`saturating_sub` patterns already used for similar timestamp math throughout `programs/marginfi/src/state/price.rs` and `programs/marginfi/src/state/marginfi_group.rs`.

### Proof of Concept
Not independently reproducible with the tools available in this session (no execution/test-running capability). Conceptually: any sequence of two on-chain calls to `Bank::accrue_interest` for the same bank where the second call's `clock.unix_timestamp` argument is less than or equal to the value that was stored in `self.last_update` by the first call will hit `(current_timestamp - self.last_update).try_into().unwrap()` with a negative operand, causing an unrecoverable panic on every subsequent unprivileged instruction (deposit/withdraw/borrow/repay/liquidate) against that bank.
