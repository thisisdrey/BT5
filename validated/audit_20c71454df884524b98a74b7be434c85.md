### Title
Missing zero-address check on `new_authority` in `transfer_to_new_account` / `transfer_to_new_account_pda` permanently locks migrated funds - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
The `transfer_to_new_account` and `transfer_to_new_account_pda` instructions let an account authority migrate all lending positions from an old `MarginfiAccount` to a brand-new one under a caller-supplied `new_authority` pubkey. The `new_authority` account is explicitly annotated as unchecked and no validation (including a non-zero check) is performed on it before it's written into the new account's `authority` field.

### Finding Description
In `TransferToNewAccount`/`TransferToNewAccountPda`, `new_authority` is declared as: [1](#0-0) [2](#0-1) 

with the comment "New authority is completely unchecked". The handler passes this value straight into `initialize_migrated_account`, which sets it as the new account's `authority` via `MarginfiAccount::initialize`: [3](#0-2) [4](#0-3) 

There is no `require!(new_authority.key() != Pubkey::default(), ...)` (or equivalent) anywhere in `transfer_to_new_account`/`transfer_to_new_account_pda`. All lending-account balances (assets and liabilities) from the old account are copied into the new account, and the old account is disabled (`ACCOUNT_DISABLED`) and marked as migrated, with no way to reverse the migration (`AccountAlreadyMigrated` guards re-migration): [5](#0-4) 

Ownership checks for any subsequent account action rely purely on `authority == signer` (or group admin when frozen): [6](#0-5) 

Because `Pubkey::default()` (the all-zero address) has no known private key, if `new_authority` is set to it (by accident or by a malicious relayer/front-end bug), the resulting account's `authority` field becomes unsignable. No one — not even the group admin in the non-frozen case — can subsequently `Signer`-authenticate as that authority to withdraw, repay, or otherwise operate on the migrated position, since `is_signer_authorized` only allows the admin path when `ACCOUNT_FROZEN` is set, which is not automatically the case here. Note the off-chain CLI (`p0-cli`) is aware of this exact risk and defensively guards against it before sending the instruction, but the on-chain program does not enforce the same check: [7](#0-6) 

This mirrors the report's bug class: functions accepting an address argument (here, `new_authority`) do not validate it against the zero address, and the client-side comment/CLI guard shows the maintainers recognize the danger but only mitigated it off-chain, not on-chain.

### Impact Explanation
If `new_authority` is the zero address, all of the old account's assets and liabilities are irreversibly transferred to a new `MarginfiAccount` whose `authority` can never sign a transaction. This results in a permanent freeze/lock of the migrated funds (deposits become unwithdrawable, and any owed liabilities can never be repaid by the "owner", though the bank's liability shares remain outstanding, potentially leading to protocol bad debt if the position is later liquidatable but nobody can manage/top it up). This matches the accepted impact category of "permanent lock/freeze" (and can compound into insolvency/bad debt for the affected bank).

### Likelihood Explanation
`transfer_to_new_account`/`transfer_to_new_account_pda` are unprivileged, permissionless-for-the-signer instructions callable by any account authority at will (no admin gating, `is_signer_authorized` only requires the caller to be the current authority). Any client bug, malformed transaction builder, copy-paste error, or malicious dApp front-end that supplies `Pubkey::default()` (or any other address the user does not control, e.g., accidentally re-using a PDA with no signer) as `new_authority` triggers the issue in a single transaction. The presence of an explicit, deliberate guard in the off-chain CLI (`p0-cli/src/processor/account.rs:1179-1181`) is itself evidence that this is a realistic failure mode the team already anticipated for one client, but did not enforce at the program level for all callers.

### Recommendation
Add an explicit on-chain check that `new_authority.key() != Pubkey::default()` (and ideally that it is not equal to the `System Program` or other known unusable addresses) in both `transfer_to_new_account` and `transfer_to_new_account_pda`, mirroring the check already present in `p0-cli/src/processor/account.rs`. Return a dedicated error (e.g., `MarginfiError::InvalidAuthority` or similar) if the check fails.

### Proof of Concept
1. Create a `MarginfiAccount` with authority `A`, deposit collateral, and optionally borrow against it.
2. Call `transfer_to_new_account` (or `transfer_to_new_account_pda`) with `authority = A` and `new_authority = Pubkey::default()` (`11111111111111111111111111111111` / system program ID... actually the all-zero pubkey), and a fresh `new_marginfi_account`.
3. The instruction succeeds: the old account is disabled/migrated (`migrated_to` set, `ACCOUNT_DISABLED` flag set, balances zeroed) and the new account is initialized with `authority = Pubkey::default()`, carrying over all balances from step 1 (see `finalize_migrated_old_account` / `initialize_migrated_account` at [8](#0-7) ).
4. Attempt any subsequent user instruction (withdraw, repay, close account, transfer again) on the new account: every such instruction requires a `Signer<'info>` matching `authority`; since no keypair exists for the zero address, `is_signer_authorized`/Anchor's `Signer` constraint can never be satisfied outside the frozen+admin path, permanently locking the funds.

**Note on completeness:** I was not able to execute this PoC in an actual test/validator environment (no filesystem/terminal access in this mode); the analysis is based on static code review of the cited files. To fully confirm exploitability (e.g., whether any other safety net like automatic freezing exists), a Devin session with test-execution access would be needed to run the scenario against the local test suite (e.g., extending `programs/marginfi/tests/admin_actions/account_transfer.rs`).

pub fn is_signer_authorized(
    marginfi_account: &MarginfiAccount,
    group_admin: Pubkey,
    signer: Pubkey,
    allow_receivership: bool,
    allow_order_execution: bool,
) -> bool {
    if allow_receivership && marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP) {
        return marginfi_account.authority != signer; // forbidden to take receivership of your own account
    }

    if allow_order_execution && marginfi_account.get_flag(ACCOUNT_IN_ORDER_EXECUTION) {
        return true;
    }

    if marginfi_account.get_flag(ACCOUNT_FROZEN) {
        return group_admin == signer;
    }

    marginfi_account.authority == signer
}

impl MarginfiAccountImpl for MarginfiAccount {
    /// Set the initial data for the marginfi account.

        self.authority = authority;
        self.group = group;
        self.emissions_destination_account = Pubkey::default();

        self.migrated_to = Pubkey::default();

        self.indexer_flags.was_active_60d = 1;
        self.active_orders = 0;
