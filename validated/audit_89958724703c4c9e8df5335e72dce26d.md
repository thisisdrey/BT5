### Title
Remote/URL fields accept `ext::`/`fd::` git transport helpers, bypassing the "operands only" invariant - (File: internal/git/gitcmd/command.go, internal/git/gitcmd/command_description.go)

### Summary
`CommandArgs` (via `commandDescription.args` and `validatePositionalArg`) only rejects positional arguments that start with `-`; it performs no check on the *content* of a value, so a string like `ext::sh -c ...` or `fd::0` passes validation unchanged. Multiple gRPC handlers (`FetchRemote`, `UpdateRemoteMirror`, `FindRemoteRootRef`, `CreateRepositoryFromURL`) forward an attacker-supplied `url`/`remote_url` string directly into `git fetch`/`git clone`/`remote.<name>.url` without checking the URL scheme, so Git itself will interpret `ext::` (or `fd::`) as a transport helper and execute the given command.

### Finding Description
`internal/git/gitcmd/command_description.go` defines `validatePositionalArg`: [1](#0-0) 
This is the only validation applied to `Args` in `commandDescription.args`, which `CommandArgs` (`internal/git/gitcmd/command.go`, lines 42-65) calls to build the final argv passed to `git`. There is no check that a value does not use the `ext::` or `fd::` remote-helper syntax, nor any `GIT_ALLOW_PROTOCOL`/`protocol.allow` allowlist configured anywhere in the codebase — a repo-wide search for `GIT_ALLOW_PROTOCOL`/`protocol.allow`/`protocol.ext` found no such enforcement in source (only unrelated CHANGELOG text).

Concretely, several RPC handlers take an attacker-controlled remote URL and pass it straight through as either a positional git argument or a `remote.*.url` git config value:

- `CreateRepositoryFromURL` → `cloneFromURLCommand` passes `req.GetUrl()` as a clone URL argument: `internal/gitaly/service/repository/create_repository_from_url.go` lines 60-84 (`Args: []string{urlString, repositoryFullPath}`).
- `FetchRemote` → `buildCommandOpts` sets `remote.inmemory.url` from `req.GetRemoteParams().GetUrl()` unconditionally: `internal/gitaly/service/repository/fetch_remote.go` lines 260-320 (`validateFetchRemoteRequest` only checks the URL is non-empty).
- `UpdateRemoteMirror` sets `remote.<name>.url` from `remote.GetUrl()`: `internal/gitaly/service/remote/update_remote_mirror.go` lines 76-91 and `validateUpdateRemoteMirrorRequest` (lines 279-293) only checks the URL is non-empty.
- `FindRemoteRootRef` sets `remote.inmemory.url` from `request.GetRemoteUrl()` with no validation at all: `internal/gitaly/service/remote/find_remote_root_ref.go` lines 17-31.

None of these paths reject `ext::` or `fd::` schemes, and `CommandArgs`/`validatePositionalArg` provides no such defense either — it only guards against leading `-` to stop option injection, not transport-helper injection. `GetURLAndResolveConfig` (`internal/git/gitcmd/command_resolve.go`) does restrict schemes, but it is only invoked when `resolved_address` is set (DNS-rebinding protection path); when `resolved_address` is empty (the common/default case), the raw attacker URL flows unchecked into the git config/argument.

### Impact Explanation
An unprivileged GitLab user who can trigger a mirror pull, `FetchRemote`, `FindRemoteRootRef`, or import-from-URL (`CreateRepositoryFromURL`) can supply a URL such as `ext::sh -c "id > /tmp/pwned"` or `fd::N`. Git's `ext::` helper spawns an arbitrary shell command as the Gitaly process user, and `fd::N` can be abused to interact with pre-opened file descriptors of the git process. This is remote code execution / arbitrary file read on the Gitaly host, i.e. the "Git argument/config injection or command execution" impact class called out in the question.

### Likelihood Explanation
Preconditions match the unprivileged threat model exactly: mirror/pull-mirror configuration, `FetchRemote`, `FindRemoteRootRef`, and repository-import-by-URL are reachable by an ordinary project owner/importer without any elevated GitLab role, and the `url`/`remote_url` field is entirely attacker-controlled. No secret, no MITM, no special configuration is required — this is directly reachable through standard mirror/import gRPC calls once the corresponding RPC is exposed to the user's own project.

### Recommendation
Add a strict allowlist of accepted remote URL schemes (e.g. `http`, `https`, `git`, `ssh`, and SCP-like syntax) at request-validation time for every RPC that accepts a URL (`FetchRemote`, `UpdateRemoteMirror`, `FindRemoteRootRef`, `CreateRepositoryFromURL`), rejecting `ext::`, `fd::`, and any other non-network transport-helper syntax before the value is placed in a git config or argument. Additionally, set `GIT_ALLOW_PROTOCOL`/`protocol.allow`/`protocol.ext.allow=never` (and `protocol.fd.allow=never`) globally for all spawned git subprocesses in `gitcmd` as defense in depth, independent of per-RPC validation.

### Proof of Concept
```go
func TestFetchRemote_RejectsExtTransport(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, repo, _ := setupRepositoryService(t)
    client := newRepositoryClient(t, cfg)

    _, err := client.FetchRemote(ctx, &gitalypb.FetchRemoteRequest{
        Repository: repo,
        RemoteParams: &gitalypb.Remote{
            Url: "ext::sh -c 'touch /tmp/pwned'",
        },
    })
    // Currently: request proceeds to git-fetch, which executes the shell command.
    // Expected: structerr.NewInvalidArgument for disallowed URL scheme.
    require.Error(t, err)
    _, statErr := os.Stat("/tmp/pwned")
    require.True(t, os.IsNotExist(statErr), "ext:: helper must not have executed")
}
```
Equivalent gRPC-level PoC: call `FindRemoteRootRef` or `UpdateRemoteMirror` with `remote_url`/`Remote.url` set to `ext::sh -c id` — the same lack of scheme validation applies.
