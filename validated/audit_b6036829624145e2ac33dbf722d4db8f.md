### Title
Pre-funding the reserved TIP-2935 `HISTORY_STORAGE_ADDRESS` before activation permanently freezes the sender's TRX with no recovery path - (File: framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java)

### Summary
`HistoryBlockHashUtil.deploy()` installs the TIP-2935 `BlockHashHistory` system contract at a fixed, well-known address (`HISTORY_STORAGE_ADDRESS`) when the `ALLOW_TVM_PRAGUE` committee proposal is processed. Any unprivileged account can trivially "claim" that address ahead of time by transferring TRX to it (this lazily creates a normal `AccountCapsule` there). When `deploy()` later fires, it does not treat this as an error or refund the funds — it silently converts the pre-existing account in place into a `Contract`-type account, preserving the balance [1](#0-0) . The deployed bytecode is the read-only TIP-2935 ring-buffer contract with no transfer/withdraw entrypoint [2](#0-1) , so any TRX balance sitting at that address at activation time becomes permanently unspendable — there is no private key that can produce a signed transaction from a contract account, and the contract itself never moves its balance out.

### Finding Description
This is the same bug-class as the reported `PerpOwnable.transferPerpOwner` issue: a state-transition that is supposed to be "claimed" exactly once by a specific, privileged actor is reachable by any unprivileged party beforehand via ordinary means, and the eventual privileged claim silently absorbs/overwrites whatever the unprivileged party put there instead of rejecting it.

- `HISTORY_STORAGE_ADDRESS` is a fixed constant, not derived from any signature scheme reachable by users [3](#0-2) .
- Any unprivileged user can create a `Normal` account at that address today, before the `ALLOW_TVM_PRAGUE` proposal is ever passed, simply by sending it TRX via an ordinary `TransferContract` — TRON creates accounts lazily on first transfer.
- When the committee proposal activating TIP-2935 is later processed, `ProposalService.process()` calls `HistoryBlockHashUtil.deploy(manager)` unconditionally for `ALLOW_TVM_PRAGUE` [4](#0-3) .
- `deploy()` only skips if *code* or *contract metadata* already exists at the address; a pre-existing plain account with a balance is explicitly treated as the expected/handled case and is upgraded in place, preserving the balance and clearing any delegated resources [5](#0-4) . This "collision" branch is exercised and asserted by the project's own test `deployUpgradesPreExistingNormalAccountPreservingBalance` [6](#0-5) .
- The installed bytecode is a fixed, minimal EIP-2935 style ring buffer (`SLOAD`-only semantics via `STATICCALL`), with no code path that can move the account's TRX balance back out [7](#0-6) . Once the account type becomes `Contract`, there is no private key controlling it and the contract bytecode contains no transfer logic, so any balance held there is permanently locked with no possible recovery transaction.

### Impact Explanation
Whoever holds a balance at `HISTORY_STORAGE_ADDRESS` when the `ALLOW_TVM_PRAGUE` proposal activates permanently loses access to those funds — this matches the "permanent freezing of funds" impact class explicitly listed as acceptable. Because the address is public and known ahead of any hard-fork rollout (it must be published for cross-chain tooling/wallets to recognize the TIP-2935 precompile), any TRX sent there prior to activation is destroyed. This can happen accidentally (a user/exchange address-scanning bot or a script that funds "system" addresses) or can be weaponized by an attacker who tricks a victim into sending funds to this address (e.g., via a phishing "airdrop claim" or fake faucet address) knowing that the funds will be irrecoverably burned the moment governance activates the proposal.

### Likelihood Explanation
Likelihood is limited by the fact that the address must be known and the trigger (`ALLOW_TVM_PRAGUE` proposal) requires committee approval, which is not something an arbitrary unprivileged actor controls the timing of directly — the "front-run" here is against a scheduled/governance-controlled event rather than a mempool race. However, the precondition (any account sending TRX to a fixed public address) is trivially reachable by any unprivileged transaction broadcaster with zero cost beyond the transfer amount, and the described project comments themselves acknowledge this exact scenario ("anyone can transfer TRX there to activate it as an EOA") as an expected, handled case rather than a rejected one — i.e., the code deliberately accepts and destroys such deposits instead of refusing activation or refunding the balance.

### Recommendation
- When `deploy()` detects a pre-existing account with a non-zero balance at `HISTORY_STORAGE_ADDRESS`, do not silently convert it into a balance-trapping contract. Either refund/redirect the pre-existing balance (e.g., to the black-hole/burn address with proper accounting, or back to depositors via an on-chain record) before flipping the account type, or reject/delay activation until the address is provably empty.
- Document the reserved address publicly ahead of any TIP-2935 rollout and add a safety check/log that surfaces (and ideally blocks) activation when unexpected non-zero balances are detected at the canonical address, rather than treating it as a routine "preserve balance" case.
- Add explicit accounting (e.g., an event or governance-visible metric) whenever the pre-existing-account branch fires with non-zero balance, so operators can react before/at the same activation block.

### Proof of Concept
1. Before the `ALLOW_TVM_PRAGUE` committee proposal is passed, any account sends a `TransferContract` transaction of TRX to `HISTORY_STORAGE_ADDRESS` (`410000f90827f1c53a10cb7a02335b175320002935`). This lazily creates a `Normal` `AccountCapsule` there holding a balance, exactly as demonstrated by the test setup in `deployUpgradesPreExistingNormalAccountPreservingBalance` [8](#0-7) .
2. The committee later approves and the chain processes the `ALLOW_TVM_PRAGUE` proposal; `ProposalService.process()` invokes `HistoryBlockHashUtil.deploy(manager)` [4](#0-3) .
3. `deploy()` finds the pre-existing account, upgrades its type to `Contract`, and preserves its balance in place [1](#0-0) , matching the assertion in the test that `after.getBalance() == balance` while `after.getType() == Contract` [9](#0-8) .
4. From this point on, the address only executes the fixed TIP-2935 bytecode, which has no logic to transfer TRX out [2](#0-1) , and no private key exists to sign a transaction moving the balance — the funds are permanently unrecoverable.

  /**
   * Deploy the TIP-2935 BlockHashHistory contract at {@code HISTORY_STORAGE_ADDRESS}.
   * If foreign code or contract metadata already sits at the canonical address,
   * logs a warning and returns without writing — the collision is deterministic
   * across nodes (same pre-state ⇒ same decision), so the proposal flag still
   * commits and chain consensus is intact. The foreign contract executes as-is
   * on every node; TIP-2935 functionality is silently absent at this address.
   * A SHA-3 pre-image of the address is the only realistic way that branch
   * fires, so it's belt-and-braces. A pre-existing non-contract account at the
   * address is the common case (anyone can transfer TRX there to activate it
   * as an EOA), so we upgrade its type to {@code Contract} in place — matching
   * the CREATE2 collision branch ({@code updateAccountType} +
   * {@code clearDelegatedResource}) and preserving balance/asset state.
   *
   * <p>Called only from {@code ProposalService} inside maintenance-time block
   * processing. Proposal validation rejects re-activation, so this runs at most
   * once per chain history; the three store writes share the block's revoking
   * session, so any node-local exception (RocksDB / IO) propagates and rolls
   * the {@code saveAllowTvmPrague(1)} write back atomically.
   */
  public static void deploy(Manager manager) {
    if (manager.getCodeStore().has(HISTORY_STORAGE_ADDRESS)
        || manager.getContractStore().has(HISTORY_STORAGE_ADDRESS)) {
      logger.warn("TIP-2935: foreign state at {}, skipping deploy",
          Hex.toHexString(HISTORY_STORAGE_ADDRESS));
      return;
    }

    manager.getCodeStore().put(HISTORY_STORAGE_ADDRESS,
        new CodeCapsule(HISTORY_STORAGE_CODE));
    manager.getContractStore().put(HISTORY_STORAGE_ADDRESS,
        new ContractCapsule(HISTORY_STORAGE_CONTRACT));

    AccountCapsule account = manager.getAccountStore().get(HISTORY_STORAGE_ADDRESS);
    boolean accountExisting = account != null;
    if (!accountExisting) {
      account = new AccountCapsule(HISTORY_STORAGE_ACCOUNT);
    } else {
      account.updateAccountType(Protocol.AccountType.Contract);
      account.clearDelegatedResource();
    }
    manager.getAccountStore().put(HISTORY_STORAGE_ADDRESS, account);

  public void deployUpgradesPreExistingNormalAccountPreservingBalance() {
