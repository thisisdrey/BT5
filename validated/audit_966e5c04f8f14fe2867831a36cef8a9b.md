Audit Report

## Title
`ERC20Transactor` initiates ERC20 transfers without a zero-amount guard, causing XCM asset transfers to revert for weird ERC20 tokens - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` build and dispatch an ERC20 `transfer(to, value)` call via `pallet_revive::Pallet::<T>::bare_call` using whatever `amount` the `MatchesFungibles` matcher returns, without checking `amount != 0` first. If the underlying ERC20 contract reverts on zero-value transfers (a known real-world token behavior, e.g. LEND), any XCM leg that legitimately resolves to a zero amount for that asset will cause `XcmError::FailedToTransactAsset` and fail the enclosing instruction/program.

## Finding Description
Verified against the source: `withdraw_asset_with_surplus` calls `Matcher::matches_fungibles(what)?` to obtain `(asset_id, amount)` and unconditionally encodes `IERC20::transferCall { to: checking_address, value: EU256::from(amount) }` before dispatching via `bare_call`, with no `amount == 0` short-circuit. [1](#0-0) 
The same unconditional pattern is present in `deposit_asset_with_surplus`, which transfers from the checking account to the beneficiary. [2](#0-1) 
Both functions map a contract revert (`return_value.did_revert()`) directly to `XcmError::FailedToTransactAsset`. [3](#0-2) [4](#0-3) 
I confirmed there is no zero-amount filtering in the generic `TransactAsset` trait or in the XCM executor's instruction processing in `polkadot/xcm/xcm-executor/src/lib.rs` and `polkadot/xcm/xcm-executor/src/traits/transact_asset.rs` — no `is_zero`/`ZeroAssetTransfer` handling exists in that crate (those terms only appear in `xcm-builder`'s weight logic and `pallet-xcm`, unrelated to this path). This confirms nothing upstream filters a zero-amount fungible asset before it reaches `ERC20Transactor`. The Snowbridge outbound-queue-v2 converter's `ZeroAssetTransfer` guard demonstrates this exact class of "weird ERC20 zero-transfer" issue is already known and explicitly guarded against elsewhere in the same codebase, confirming the missing guard here is an inconsistency rather than an accepted design choice.

## Impact Explanation
This is a genuine runtime bug that compromises intended behavior: any XCM message routing a zero amount of an ERC20-backed asset (via wildcard/partial resolution, fee/remainder computation, or an explicit `Fungible(0)` asset) through `ERC20Transactor` will unconditionally revert if the registered ERC20 contract reverts on zero-value transfers, failing the enclosing XCM instruction. This falls under "runtime bugs that compromise intended behavior" in the impact gate. However, I could not verify within the available tooling that this results in a *permanent* fund lock: XCM executors generally trap already-withdrawn/held assets (via the asset-trap mechanism) rather than destroying them irrecoverably when a later instruction fails, so the more severe "permanent user-fund lock" framing in the original claim is not fully substantiated — only a transaction-failure / denial-of-transacting condition for that specific asset is clearly supported by the code reviewed.

## Likelihood Explanation
Triggering this requires no privileged actor: any party able to construct/route an XCM message that causes `Matcher::matches_fungibles` to yield `amount == 0` for an ERC20 asset registered via `ERC20Transactor` can hit this path. It is conditioned on the specific registered ERC20 contract reverting on zero-value transfers, which is a known but non-universal ERC20 behavior, making exploitation asset-specific rather than universally exploitable across all ERC20 assets on the chain.

## Recommendation
Add an `amount == 0` short-circuit (return success/no-op) in both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`, before constructing/dispatching the `IERC20::transferCall`, mirroring the `ZeroAssetTransfer`-style guard used in the Snowbridge outbound-queue-v2 converter.

## Proof of Concept
1. Register an ERC20 contract as an XCM asset id via `ERC20Transactor` whose `transfer` reverts when `value == 0`.
2. Construct an XCM program (e.g. `WithdrawAsset`/`DepositAsset` with a wildcard or explicit `Fungible(0)`) such that `Matcher::matches_fungibles` returns `amount == 0` for that asset.
3. Execute the XCM message; `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` (`cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs` L159-181 / L236-266) calls `bare_call` with `value: 0`.
4. Observe `return_value.did_revert() == true`, yielding `XcmError::FailedToTransactAsset("ERC20 contract reverted")` and failing the XCM instruction, demonstrating the denial-of-transacting condition without any privileged actor involved.
