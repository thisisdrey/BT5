## Title
Out-of-bounds read via unvalidated `local_header_offset`/size fields when merging jar entries during `bazel build` (singlejar) - ([File: src/tools/singlejar/input_jar.h], [File: src/tools/singlejar/transient_bytes.h])

### Summary
`singlejar` (used internally by Bazel's Java rules to merge/deploy jars, e.g. `_deploy.jar` creation and `META-INF/desugar_deps` merging) parses attacker-influenced jar/zip files. When iterating central directory entries, the local-header offset taken from an untrusted `CDH` record is converted to a pointer without a bounds check, and later the uncompressed/compressed size fields (also untrusted, from `LH`/`CDH`, including the Zip64 extension) are used directly as a `memcpy`/copy length in `TransientBytes::Append`/`CopyOut` without validating them against the actual mapped file size. This is analogous to `nfs_readlink_req` in CVE-2019-15938, where an attacker-supplied length field is trusted for a `memcpy` without checking it against the real buffer bounds.

### Finding Description
`InputJar::NextEntry()` validates that the *next central directory record* pointer is inside the mapped file [1](#0-0) , but `LocalHeader(cdh)` computes the `LH*` pointer from the untrusted `cdh->local_header_offset()` field via `mapped_file_.address()` with **no bounds check at all**: [2](#0-1) 

`MappedFile::address()` performs no clamping, it simply adds the offset to the mapped base pointer: [3](#0-2) 

Once callers have an `LH*`, `uncompressed_file_size()`/`compressed_file_size()` are read straight from the (potentially out-of-bounds) header bytes, including via the `Zip64ExtraField` 64-bit extension, entirely attacker-controlled: [4](#0-3) 

These sizes are then used directly as copy lengths, e.g. in `TransientBytes::ReadEntryContents`, which calls `Append(lh->data(), uncompressed_file_size)`: [5](#0-4) 

`Append()` then walks `data` for `data_size` bytes, copying them into internal buffers with `copy()`/`memcpy`-style operations, with no check that `[data, data+data_size)` lies within the mapped file: [6](#0-5) 

This code path is exercised, for instance, by `Java8DesugarDepsChecker::Merge`, which merges `META-INF/desugar_deps` entries and then copies the buffer out with `CopyOut` (also a raw `memcpy` of `data_size()` bytes into a heap allocation sized by the same untrusted length) [7](#0-6) , and by `OutputJar::AddJar` while merging duplicate entries (`entry_info.combiner_->Merge(jar_entry, lh)`) [8](#0-7) .

The attacker model fits the required scope: a hostile jar can be introduced via `http_jar`/`http_archive` inputs, or a hostile CI-visible dependency artifact that gets merged with `singlejar` as part of building a Java target — no access to the victim's machine or trusted BUILD/.bzl files is required, only the ability to publish a malicious jar the build consumes.

### Impact Explanation
A crafted jar with a bogus `local_header_offset` (pointing near or past the end of the mapped file) combined with an oversized `uncompressed_file_size`/`compressed_file_size` (or Zip64 extension value) can cause `singlejar` to read far past the end of the memory-mapped input file and copy that out-of-bounds memory into the output artifact or into a heap buffer sized from the same attacker-controlled value. Depending on layout this can crash the build process (segfault reading unmapped pages) or leak adjacent process memory into build outputs. This matches the "read outside the repository/exec root/output base" / memory-safety-violation class described in the rules, on the strongest reachable native archive-parsing surface in this codebase (there is no `ZipDecompressor`/`TarFunction` Java equivalent bug of this exact shape; the C++ `singlejar`/`ijar` layer is the actual analog).

### Likelihood Explanation
`singlejar` is invoked automatically for essentially every Java build/deploy-jar action, so any dependency jar (including ones fetched from an external, potentially compromised source) is parsed by this code with default flags — no special configuration is required. The only precondition is that the attacker's zip/jar bytes are fed into a `singlejar` merge operation, which happens routinely in ordinary Java builds.

### Recommendation
- In `InputJar::LocalHeader()`/`NextEntry()`, validate `cdh->local_header_offset() + preamble_size_` against `mapped_file_.mapped(...)` before dereferencing it as an `LH*`, mirroring the existing check already done for `new_cdr`.
- In `LH`/`CDH` accessors (or at the call sites in `TransientBytes::ReadEntryContents`/`DecompressEntryContents`/`Append`/`CopyOut`), bound-check `uncompressed_file_size()`/`compressed_file_size()` (and the Zip64 extension values) against the remaining bytes between the entry's data pointer and `mapped_file_.end()` before using them as copy lengths, rejecting the entry with a diagnostic (as already done for other consistency checks like "central directory and file header inconsistent").

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` style repro:
1. Construct a minimal, otherwise well-formed jar (single entry) so `LocateCentralDirectory` succeeds.
2. Patch the single `CDH`'s `local_header_offset32` field to a value near `mapped_file_.size()` (e.g. `size - 4`), and patch the corresponding (fabricated) `LH` region's `uncompressed_file_size32`/`compressed_file_size32` to a large value (e.g. `0x7FFFFFFF`), or add a Zip64 extra field claiming a 64-bit size far larger than the file.
3. Run `singlejar --output out.jar --sources crafted.jar` (or drive an `OutputJar::AddJar` unit test directly with this crafted `InputJar`).
4. Observe that reading proceeds past the end of the mapped file (detectable as an ASan heap/global-buffer-overflow or SIGSEGV under a debug/ASan build of `singlejar`), demonstrating the missing bounds check on `local_header_offset` and the size fields.

Note: I was not able to fully verify at what exact size the mapping is placed (e.g. exact page-alignment behavior of `MappedFile::Open`) which could affect whether the OOB read reliably crashes or merely reads adjacent heap/page data; a background agent with build/test execution access would need to confirm exact crash/leak behavior with a live ASan-instrumented build.
