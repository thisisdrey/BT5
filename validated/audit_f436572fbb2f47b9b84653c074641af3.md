### Title
Recovery inheritor-control filter is bypassed by wrapping the restricted call in `pallet_utility::batch` - (File: `substrate/frame/recovery/src/lib.rs`, demonstrated in `substrate/frame/recovery/src/tests.rs`)

### Summary
The external report's core broken invariant is: a function meant to gate a privileged state-changing action (`revokeRole`) delegates to a lower-level primitive (`super._revokeRole()`) that does not re-apply the access check, so the wrapper's restriction is trivially bypassed. The same invariant break exists in the recovery pallet's `control_inherited_account`, which is meant to let a recovered account's `inheritor` execute calls *as* the recovered account while filtering out dangerous calls (like `slash_attempt`). Because the filter is (per the test) applied only to the outer dispatched `RuntimeCall` and the pallet lets that call be `pallet_utility::Call::batch { .. }`, the inner `slash_attempt` call — which the filter is supposed to block — is dispatched unfiltered inside the batch, exactly mirroring `revokeRole()` calling `super._revokeRole()` and skipping the access-control layer.

### Finding Description
`Recovery::control_inherited_account` is the "public wrapper" that should restrict which calls an `inheritor` can force through the recovered account's origin. The test `inheritor_cannot_bypass_filter_via_utility_batch` explicitly constructs a `RecoveryCall::slash_attempt` (a call the wrapper's filter should block) and wraps it inside a `pallet_utility::Call::batch`, then submits the `batch` call itself as the argument to `control_inherited_account` [1](#0-0) . The comment in the test states the filter only checks the outer call type, so the inner `slash_attempt` still executes with the recovered account's authority [2](#0-1) .

This is structurally identical to the `AccessControlDelayed` bug: the public entry point (`revokeRole` / `control_inherited_account`) intends to gate a sensitive action, but the actual state mutation is reached through an internal/unfiltered path (`super._revokeRole()` / `pallet_utility::batch`'s per-call `dispatch`) that does not re-check the wrapper's restriction. `pallet_utility::batch` itself only strips filters when the *batch* is submitted by `Root` via `dispatch_bypass_filter`; for non-root batches it uses `call.dispatch(origin.clone())`, which relies entirely on whatever filter is attached to `origin` [3](#0-2) . If `control_inherited_account`'s filter is not composed as an origin-level filter that recursively applies to nested calls dispatched through `batch`, an attacker-controlled inner call escapes the intended restriction.

### Impact Explanation
An `inheritor` (an otherwise unprivileged actor with respect to `slash_attempt` and similar restricted calls) can force execution of calls that the recovery pallet's access-control filter is designed to block, using the recovered account's authority. In the demonstrated scenario this allows unauthorized slashing of a friend's security deposit — an unbacked/unauthorized fund movement caused by a public-wrapper origin-filter bypass, matching the "Public wrappers ... must not widen origin, bypass filters" pivot.

### Likelihood Explanation
The bypass requires no privileged actor, governance, validator, or malicious peer — any account holding the `inheritor` role (attainable through the normal recovery/inheritance flow) can trigger it by simply wrapping the restricted call in `pallet_utility::batch`, a widely available public pallet. This is a low-effort, unprivileged, always-available attack path once the inheritor role is obtained.

### Recommendation
`control_inherited_account`'s filter must be applied at the origin level (via `origin.add_filter(...)`, as `batch_all` does to prevent nested `batch_all` recursion) rather than only checked against the top-level call variant, so that filtering recurses into `batch`/`batch_all`/`as_derivative`-wrapped calls. Alternatively, explicitly reject `pallet_utility::Call::batch`/`batch_all`/`force_batch`/`dispatch_as` variants (and any other call-wrapping call) as top-level input to `control_inherited_account`.

### Proof of Concept
The existing test in the repository is itself the proof of concept: it builds a `slash_attempt` call, wraps it in `pallet_utility::Call::batch`, submits the batch through `Recovery::control_inherited_account`, and asserts/panics if the wrapped `slash_attempt` executed and slashed the victim's balance [4](#0-3) .

**Caveat:** I could not retrieve the exact filter-construction code inside `control_inherited_account` in `substrate/frame/recovery/src/lib.rs` (grep confirmed the symbols exist but the tool budget ran out before I could read the surrounding lines), so I cannot cite the precise filter implementation. The finding rests on the test's explicit design and comments, which describe and check for exactly this bypass.
