### Title
Unbounded iteration over `VotesStore` in `MaintenanceManager.doMaintenance()` / `countVote()` can cause block-application slowdown or halt as voter count grows without bound - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
`MaintenanceManager.applyBlock()` triggers `doMaintenance()` every maintenance cycle when a block's timestamp crosses `nextMaintenanceTime` [1](#0-0) . `doMaintenance()` calls `countVote(votesStore)`, which iterates the entire `VotesStore` — a key-value store keyed by every voter address that changed votes in the epoch — and for each entry runs nested `forEach` loops over `getOldVotes()`/`getNewVotes()` [2](#0-1) . The equivalent scan-and-clear logic also exists in `Wallet.countVote()` [3](#0-2) .

### Finding Description
This is the same bug class as the reported `StakingPool.sol` issue: a `for`/iterator loop whose length is driven by the number of distinct accounts that voted in an epoch, with no cap on how many entries can accumulate. Every account that calls `VoteWitnessActuator`/`VoteWitnessProcessor` to vote for witnesses adds/updates an entry in `VotesStore` [4](#0-3) , so an attacker (or organic growth) can grow this store to an arbitrarily large size over time simply by having many distinct accounts submit `VoteWitnessContract` transactions each epoch — this is fully reachable by any unprivileged transaction broadcaster since it just requires enough frozen balance to vote and no upper bound exists on the total number of distinct voting accounts. Unlike the individual per-account vote list (capped by `MAX_VOTE_NUMBER`), the *number of voters* processed by `countVote()` in a single maintenance cycle is unbounded.

### Impact Explanation
`doMaintenance()` runs synchronously inside block application on every full node (`MaintenanceManager.applyBlock`), which is invoked from block-processing paths reachable by any transaction broadcaster indirectly (by causing many accounts to vote). If the `VotesStore` grows large enough, the maintenance-cycle work (iterating every entry, plus nested forEach over old/new votes, computing `countWitness` map updates, and subsequent witness updates) can consume enough time/CPU to slow or stall block production/import across the network at every maintenance boundary — a chain-wide processing delay/halt condition, not an isolated per-user gas failure like the original TVM report, but structurally the same unbounded-loop-in-consensus-critical-path pattern.

### Likelihood Explanation
Reaching this requires no privileged access — any account holder can submit `VoteWitnessContract` transactions, and a large number of low-value distinct accounts voting in the same epoch would inflate `VotesStore` size and, transitively, the cost of `countVote()`/`doMaintenance()` at the next maintenance interval. This is Acknowledged-class rather than Critical because block-processing is not per-transaction gas metered, and mitigations (real DB iteration cost, hardware page cache, etc.) reduce practical severity, matching the "Acknowledged" status of the original report rather than a proven crash.

### Recommendation
Bound or paginate maintenance-cycle vote-counting work: cap the number of distinct voters processed per maintenance cycle and carry over remainder work to subsequent cycles/blocks, or maintain running aggregate counters per witness instead of a full-store rescan each epoch, mirroring the original recommendation to "limit loop iterations and allow batched processing."

### Proof of Concept
Not independently executable from the available context — this requires operating many accounts to accumulate entries in `VotesStore` across maintenance cycles and measuring `doMaintenance()`/`countVote()` execution time growth; this was not run in this analysis, and only static code review of `MaintenanceManager.java` and `Wallet.java` was used to establish the unbounded loop.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }
