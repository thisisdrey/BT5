### Title
EIP-7918 reserve-price check in `calcExcessBlobGas` compares against per-blob price instead of per-gas-unit blob base fee, causing `ExcessBlobGas` to diverge from the specification - (File: consensus/misc/eip4844/eip4844.go)

### Summary
`calcExcessBlobGas` implements the post-Osaka EIP-7918 "reserve price" branch by comparing `reservePrice` (`BLOB_BASE_COST * parent.BaseFee`) against `bcfg.blobPrice(parentExcessBlobGas)`, which is the *per-blob* price (`blobBaseFee * BlobTxBlobGasPerBlob`), instead of the *per-gas-unit* blob base fee (`bcfg.blobBaseFee(...)`) that the reserve-price mechanism is defined against.

### Finding Description
`consensus/misc/eip4844/eip4844.go` defines two helper values:
- `blobBaseFee(excessBlobGas)` — the fee **per unit of blob gas**, computed via `fakeExponential` [1](#0-0) 
- `blobPrice(excessBlobGas)` — the price of **one whole blob**, i.e. `blobBaseFee * params.BlobTxBlobGasPerBlob` (a multiplier of `1<<17` = 131072) [2](#0-1) 

In `calcExcessBlobGas`, the EIP-7918 reserve-price gate is computed as:
```go
reservePrice = baseCost.Mul(baseCost, parent.BaseFee)   // BLOB_BASE_COST * base_fee_per_gas
blobPrice    = bcfg.blobPrice(parentExcessBlobGas)       // per-blob price (131072x the per-gas rate)
if reservePrice.Cmp(blobPrice) > 0 { ... }
``` [3](#0-2) 

`reservePrice` is a quantity with units of wei representing `BLOB_BASE_COST` (a fixed *gas* amount, `params.BlobBaseCost = 1<<13 = 8192`) priced at the block's execution base fee per gas [4](#0-3) . This is meant to be compared directly against the **per-unit-of-blob-gas** fee (`get_base_fee_per_blob_gas` in the EIP-7918 spec), which is exactly what `bcfg.blobBaseFee(...)` returns. Instead, the code compares it against `blobPrice`, which is inflated by a factor of `BlobTxBlobGasPerBlob` (131072) relative to the per-gas rate. This makes the reserve-price branch trigger far less often than the specification requires (the RHS is ~131072x larger than intended), and only becomes true when `parent.BaseFee` is roughly five orders of magnitude larger than the blob base fee.

Because `CalcExcessBlobGas` directly determines the consensus-critical `header.ExcessBlobGas` field, and `VerifyEIP4844Header` rejects any block whose `ExcessBlobGas` does not exactly match the locally recomputed value [5](#0-4) , this divergence from the EIP-7918 formula means this implementation will compute (and accept/reject) a different `ExcessBlobGas`/blob base fee than a spec-conformant client under conditions where the reserve-price mechanism should (or should not) kick in.

### Impact Explanation
`ExcessBlobGas` and the derived blob base fee are consensus fields checked on every post-Cancun header (`VerifyEIP4844Header`). A client using the incorrect comparison would compute a different expected `ExcessBlobGas` than spec-compliant clients in scenarios where the true per-gas blob base fee is low relative to `BLOB_BASE_COST * base_fee_per_gas` but the inflated per-blob price is not — i.e. whenever `blobBaseFee < reservePrice ≤ blobPrice`. In that window, this client would use the EIP-4844 "normal" decrement formula while other clients apply the EIP-7918 "reserve" scaling formula (or vice versa), producing different `ExcessBlobGas` values and therefore rejecting each other's otherwise-valid blocks — a mainnet consensus split. This falls squarely under the "Critical" category (Geth accepts/rejects a mainnet block that other clients treat oppositely).

### Likelihood Explanation
This branch is only active post-Osaka (`isOsaka` gate) and only affects computation when total blob gas usage exceeds target, so it is reachable on essentially every over-target block once Osaka/BPO forks activate — this is not a crafted-attacker scenario but a systematic formula error that will manifest whenever blob demand and execution base fee fall into the affected ratio range, which is plausible under normal low blob-demand / rising execution-fee market conditions.

### Recommendation
Compare `reservePrice` against the per-gas blob base fee, not the per-blob price:
```go
reservePrice := new(big.Int).Mul(big.NewInt(params.BlobBaseCost), parent.BaseFee)
blobBaseFee := bcfg.blobBaseFee(parentExcessBlobGas)
if reservePrice.Cmp(blobBaseFee) > 0 {
    ...
}
```
Add/adjust unit tests to cover the boundary where `blobBaseFee < reservePrice ≤ blobPrice`, since the existing `TestCalcExcessBlobGasEIP7918` cases (`basefee=1` and `basefee=1_000_000_000`) do not straddle this specific window and therefore did not catch the bug.

### Proof of Concept
I could not execute code in this environment, so this is a manual trace rather than an executed PoC:

1. Suppose after Osaka, `parentExcessBlobGas = X` such that `bcfg.blobBaseFee(X) = 100` wei/gas-unit, and `parent.BaseFee = 100000` wei/gas.
2. `reservePrice = BLOB_BASE_COST(8192) * 100000 = 819,200,000`.
3. Per spec, this must be compared to `blobBaseFee(X) = 100`. Since `819,200,000 > 100`, the reserve-price branch should trigger, and `ExcessBlobGas` should be computed via the scaled-excess formula.
4. In the current code, the comparison uses `blobPrice(X) = 100 * 131072 = 13,107,200`. Since `819,200,000 > 13,107,200` as well in this example the branch still triggers — but for a smaller base fee, e.g. `parent.BaseFee = 2000`:
   - `reservePrice = 8192 * 2000 = 16,384,000`
   - Spec comparison: `16,384,000 > 100` → reserve branch should trigger.
   - Code's comparison: `16,384,000 > 13,107,200` → still triggers here, but shrink `parent.BaseFee` further to `1600`: `reservePrice = 13,107,200`, exactly at the code's threshold, versus spec threshold of `100`. Any `parent.BaseFee` between `~1` and `~1600` (in this example) causes `reservePrice > blobBaseFee` (per spec, branch should trigger) while `reservePrice ≤ blobPrice` (per code, branch does NOT trigger) — a direct divergence window whose width scales with the ratio `BlobTxBlobGasPerBlob / BlobBaseCost` (~16x band in base-fee terms).

Because I could not run Go tests in this session, I recommend a background agent add a unit test asserting `CalcExcessBlobGas` matches the reference EIP-7918 Python spec formula (comparing against `blobBaseFee`, not `blobPrice`) across this divergence window to conclusively confirm the mismatch before merging a fix.
