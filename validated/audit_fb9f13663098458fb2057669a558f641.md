### Title
Access-key nonce reset in `add_regular_key` moves nonce backwards, enabling free transaction replay for zero-balance accounts - ([File: runtime/runtime/src/access_keys.rs])

### Finding Description
`add_regular_key` (runtime/runtime/src/access_keys.rs:230-255) unconditionally sets a newly (re-)added key's nonce to `initial_nonce_value(block_height)` = `(block_height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [1](#0-0) [2](#0-1) . This is done with no comparison to, or carry-over of, the access key's prior nonce value. The documented invariant explicitly requires the opposite: "If the new access key reuses the same public key, the nonce of the new access key should be equal to the nonce of the old access key. It's required to avoid replaying old transactions again." [3](#0-2) . That carry-over is not implemented for `action_delete_key`/`action_add_key` on the same public key: `delete_regular_key` simply removes the trie record (`remove_access_key`) with no memory of the old nonce [4](#0-3) , and the subsequent `action_add_key` treats it as brand-new because `get_access_key` returns `None` [5](#0-4) .

Replay protection is enforced in `verify_nonce` (`runtime/runtime/src/verifier.rs:210-237`) purely against the *currently stored* nonce (`effective_nonce = max(access_key.nonce, pending.max_nonce)`), with `NonceMode::Monotonic` requiring `tx_nonce > current_nonce` [6](#0-5) [7](#0-6) . Because the stored nonce is silently rewritten to `(block_height-1)*M` on every `AddKey`, if the attacker executes `DeleteKey(pk)+AddKey(pk)` for the same public key at (or very near) the same block height at which earlier transactions on that key were already executed, the new stored nonce can fall *below* nonces of transactions that were already successfully executed. Any previously-signed transaction with a nonce greater than the new (lower) stored value but less than the block-height upper bound then passes `verify_nonce` again and is re-executed — a full nonce-based replay.

The bug is height-window-dependent: since `M = ACCESS_KEY_NONCE_RANGE_MULTIPLIER` is large (10^6), the reset only creates a *backwards* jump when the `DeleteKey+AddKey` batch executes at essentially the same block height as the transactions being targeted for replay (i.e., within the same `(height-1)*M .. height*M` bucket as the nonces already consumed). This is achievable by submitting two transactions from the same signer (e.g., one ordinary tx, then a follow-up tx containing `[DeleteKey(pk), AddKey(pk)]`) that land in the same or an adjacent block/chunk — a normal capability of an unprivileged account, no validator/relayer/node privilege required.

The zero-balance-account exemption in `check_storage_stake`/`is_zero_balance_account` (runtime/runtime/src/verifier.rs:47-89, `ZERO_BALANCE_ACCOUNT_STORAGE_LIMIT = 770`) removes the only economic friction that would otherwise discourage repeated `DeleteKey+AddKey` cycling: as long as `account.storage_usage() <= 770` bytes (satisfied by one `FullAccess` key plus the base account record), the account is exempt from needing balance to cover storage stake for these actions, so the cycle can be repeated indefinitely at negligible net cost (only gas, which for a zero-balance account with allowance-covering function-call keys or a sponsor/relayer can also be minimized) [8](#0-7) .

### Impact Explanation
This breaks the nonce-monotonicity replay-protection invariant for the affected access key: an attacker can re-execute an already-settled transaction of their own account (e.g., a `Transfer`, `FunctionCall`, or any other action) by first "rewinding" the key's nonce via `DeleteKey+AddKey`. Since the attack only replays the attacker's *own* transactions signed by a key the attacker controls, direct third-party fund theft is not established here — the primary abuse is against the attacker's own account's internal state/nonce accounting (e.g., re-triggering a `FunctionCall` receipt, re-consuming/re-crediting internal contract state keyed by "processed once per tx" logic, or confusing off-chain systems, like exchanges/relayers, that rely on nonce-uniqueness as an idempotency guarantee for a given account). This maps to a **double-spend/replay** category bug (weakened nonce invariant), scoped to accounts within the zero-balance storage exemption, but the underlying reset logic is a protocol-level correctness bug independent of the zero-balance angle. It does not, on its own within this scope, allow draining other accounts' funds or forging signatures — it only allows replay of an attacker's own previously-valid, previously-executed transaction against itself.

### Likelihood Explanation
Preconditions: a newly created zero-balance account with one `FullAccess` key (storage_usage ≤ 770 bytes) — this is a normal account state reachable by any unprivileged user, and NEP-448's zero-balance mechanism is a standard onboarding path. The attacker needs the ability to get two of their own transactions (one ordinary action, one `DeleteKey+AddKey`) processed at nonce-bucket-adjacent heights, which is feasible by submitting both to a public RPC/mempool in quick succession. The `DeleteKey`+`AddKey` cycle costs only gas (no storage-stake requirement due to the exemption), so it is cheap and fully repeatable at will, with no interaction from validators or privileged actors required.

### Recommendation
When re-adding an access key with a public key that previously existed on the account (detectable during `DeleteKey`, or by retaining a tombstone/high-water-mark of the last nonce used per public key), `add_regular_key` should set the new nonce to `max(initial_nonce_value(block_height), previous_nonce)` rather than unconditionally overwriting it with `initial_nonce_value(block_height)`. Since `action_add_key` currently rejects re-adding an existing (non-deleted) key, the fix requires persisting the last-known nonce for a public key across a delete, at least for enough time/height range to guard against a same-height (or same-nonce-bucket) recreation, or alternatively disallowing `AddKey` reuse of a public key that was deleted within the same block/nonce-bucket window.

### Proof of Concept
Unit test in `runtime/runtime/src/access_keys.rs` (or an integration/test-loop test):
1. Create a zero-balance account with a `FullAccess` key `pk`, at block height `H0`; assert `access_key.nonce == (H0-1)*M`.
2. Sign and execute `TX_A` with `nonce = (H0-1)*M + 1` doing a benign action (e.g., `Transfer` to self or a no-op `FunctionCall`); assert it succeeds and the stored `access_key.nonce == (H0-1)*M + 1`.
3. At the same block height `H0` (or a height `H1` such that `(H1-1)*M <= (H0-1)*M + 1`), submit `TX_B` = `[DeleteKey(pk), AddKey(pk, FullAccess)]` signed with a valid, higher nonce; execute via `action_delete_key`/`action_add_key`; assert the account remains a zero-balance account (`storage_usage() <= ZERO_BALANCE_ACCOUNT_STORAGE_LIMIT`) and that `check_storage_stake` returns `Ok(())` with zero balance throughout.
4. Assert the resulting stored `access_key.nonce == (H1-1)*M`, which is `<=` the nonce used by `TX_A`.
5. Re-submit `TX_A` (identical signed transaction) and assert `verify_nonce`/`verify_and_charge_tx_ephemeral` returns `TxVerdict::Success` (i.e., no `InvalidNonce` error), demonstrating replay of an already-executed transaction, and that this cycle can be repeated N times while `storage_usage` never exceeds 770 bytes.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER

fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}

pub fn check_storage_stake(
    account: &Account,
    account_balance: Balance,
    runtime_config: &RuntimeConfig,
) -> Result<(), StorageStakingError> {
    let billable_storage_bytes = account.storage_usage();
    let required_amount = runtime_config
        .storage_amount_per_byte()
        .checked_mul(u128::from(billable_storage_bytes))
        .ok_or_else(|| {
            format!(
                "Account's billable storage usage {} overflows multiplication",
                billable_storage_bytes
            )
        })
        .map_err(StorageStakingError::StorageError)?;
    let available_amount = account_balance
        .checked_add(account.locked())
        .ok_or_else(|| {
            format!(
                "Account's amount {} and locked {} overflow addition",
                account.amount(),
                account.locked(),
            )
        })
        .map_err(StorageStakingError::StorageError)?;
    if available_amount >= required_amount {
        Ok(())
    } else {
        if is_zero_balance_account(account) {
            return Ok(());
        }
        Err(StorageStakingError::LackBalanceForStorageStaking(
            required_amount.checked_sub(available_amount).unwrap(),
        ))
    }
}

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}
