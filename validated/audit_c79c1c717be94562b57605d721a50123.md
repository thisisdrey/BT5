### Title
An unprivileged borrower can front-run a liquidation with dust repayment and force `Pool.liquidate` to revert - ([File: contracts/Pool.sol])

### Summary
`Pool.liquidate` requires the caller-supplied `amountToRepay_` to remain within `maxLiquidable` of the borrower’s current debt balance, but any third party can first reduce that balance through `DebtToken.repay`. A borrower or attacker can therefore spend as little as 1 wei of synthetic token before a liquidation transaction, making the previously valid liquidation amount exceed the current debt and revert. [1](#0-0) [2](#0-1) 

### Finding Description
`DebtToken.repay` is publicly callable and explicitly accepts an `onBehalfOf_` account while burning synthetic tokens from the caller. [3](#0-2) 

The repaid amount is burned from the payer and the corresponding debt-token balance is burned from `onBehalfOf_`, so an unprivileged account can reduce a borrower’s debt by dust. [4](#0-3) 

`Pool.liquidate` snapshots the debt balance after interest accrual and reverts when `amountToRepay_ / debtBalance > maxLiquidable`. [5](#0-4) 

When `maxLiquidable` is 100%, a liquidation transaction for the entire observed debt necessarily reverts after even a 1-wei repayment because the numerator is now greater than the denominator. [1](#0-0) 

The same issue affects smaller liquidations whenever the requested amount is close to the configured liquidation limit; a dust repayment can push the ratio over that limit. [6](#0-5) 

Unlike a private repayment helper, `DebtToken.repay` requires no borrower approval because the payer supplies and burns its own synthetic tokens. [7](#0-6) 

### Impact Explanation
A borrower can repeatedly front-run pending liquidation transactions with inexpensive dust repayments, causing liquidators’ transactions to revert while the position remains unhealthy. [8](#0-7) 

The delay is economically meaningful when collateral prices are falling because postponed liquidation increases the probability that collateral becomes insufficient to cover the remaining debt, potentially leaving the protocol with bad debt. [9](#0-8) 

The attacker does not need ownership of the borrower account, privileged roles, oracle manipulation, or a special contract; holding a dust amount of the relevant synthetic token is sufficient to call `repay`. [2](#0-1) 

### Likelihood Explanation
Liquidators commonly calculate an exact debt amount or the maximum liquidable amount off-chain before submitting a transaction, making this stale-amount race practical. [10](#0-9) 

The borrower already possesses newly minted synthetic tokens in normal issuance flows and can use a tiny fraction of them for the griefing repayment. [11](#0-10) 

The attack only delays rather than permanently prevents liquidation because a liquidator can retry with the reduced balance, but a motivated borrower can continue front-running retries as long as doing so remains cheaper than liquidation. [12](#0-11) 

### Recommendation
Normalize the repayment amount inside `liquidate` instead of reverting when the requested amount exceeds the current bound:

```solidity
uint256 _maxAmount = _debtTokenBalance.wadMul(maxLiquidable);
uint256 _amountToRepay = Math.min(amountToRepay_, _maxAmount);
if (_amountToRepay == 0) revert AmountIsZero();
```

Then use `_amountToRepay` consistently for the debt-floor check, collateral quote, synthetic-token burn, debt-token burn, and event. [12](#0-11) 

Alternatively, add an explicit `repayAll` or `liquidateAll` mode so callers intending to erase the current debt do not commit to a stale exact amount. [13](#0-12) 

### Proof of Concept
The following Hardhat test can be placed inside the existing unhealthy-position liquidation context in `test/Pool.test.ts`, where Alice has minted `msETH`, the position is unhealthy, and `maxLiquidable` is 100%. [14](#0-13) 

```typescript
it('front-running dust repayment reverts a full liquidation', async function () {
  const debtBefore = await msEthDebtToken.balanceOf(alice.address)

  await ethers.provider.send('evm_setAutomine', [false])

  // Alice spends 1 wei of her own msETH to reduce her debt.
  const dustRepayTx = await msEthDebtToken
    .connect(alice)
    .repay(alice.address, 1)

  // Liquidator's tx was built against `debtBefore`.
  const liquidationTx = await pool
    .connect(liquidator)
    .liquidate(msEth.address, alice.address, debtBefore, msdMET.address)

  await ethers.provider.send('evm_mine', [])
  await ethers.provider.send('evm_setAutomine', [true])

  await dustRepayTx.wait()
  await expect(liquidationTx).revertedWithCustomError(
    pool,
    'AmountGreaterThanMaxLiquidable'
  )

  // The debt was reduced only by dust and the position remains liquidatable.
  expect(await msEthDebtToken.balanceOf(alice.address)).eq(debtBefore.sub(1))
  expect((await pool.debtPositionOf(alice.address))._isHealthy).false

  // A manually recalculated retry succeeds, demonstrating temporary DoS.
  await pool
    .connect(liquidator)
    .liquidate(msEth.address, alice.address, debtBefore.sub(1), msdMET.address)

  expect(await msEthDebtToken.balanceOf(alice.address)).eq(0)
})
```

The first transaction succeeds because `repay` allows Alice to burn her own synthetic token to reduce her own debt balance, while the second reverts because `debtBefore / (debtBefore - 1) > 1`. [15](#0-14) [1](#0-0)
