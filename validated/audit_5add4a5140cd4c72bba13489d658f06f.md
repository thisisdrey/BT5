### Title
Unprivileged attacker can force-revert a victim's deposits and new borrows by dust-filling the victim's per-account token lists up to `MAX_TOKENS_PER_USER` - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` caps the combined number of `debtTokensOfAccount` and `depositTokensOfAccount` entries per account at `MAX_TOKENS_PER_USER = 30` via `onlyIfAdditionWillNotReachMaxTokens` [1](#0-0) . `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever a recipient's balance goes from 0 to non-zero [2](#0-1) . Any EOA can therefore transfer 1 wei of every whitelisted msd-token to a victim until their list is full, after which every `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` call reverts with `UserReachedMaxTokens`. This is the reachable analog of the reported "hang/crash (DoS)" bug class: it denies service to a targeted account's deposit, transfer-in, and new-debt-issuance paths.

### Finding Description
- Entry point: `DepositToken.transfer(victim, 1)` (public, no pause check on transfers — `_transfer` has no `whenNotPaused`/`whenNotShutdown`) [3](#0-2) .
- Because `transfer` only requires `unlockedBalanceOf(attacker) >= amount` [4](#0-3) , the attacker deposits a small amount of each collateral once, then dust-transfers `1` wei of each of the N supported deposit tokens to the victim. No privileged role is needed; the deposit-tokens list only accepts genuine pool tokens (`_revertIfSenderIsNotDepositToken`) [5](#0-4) , so fake tokens cannot bypass this — the attacker must use real dust, which is cheap.
- Once `length >= 30`, all subsequent paths that add a new token type revert: `deposit` into a collateral the victim doesn't hold (`_mint` → `addToDepositTokensOfAccount`) [6](#0-5) , receiving msd-token transfers, `DebtToken.issue`/`leverage`/`swap` outputs that would add a new debt token (`_mint` → `addToDebtTokensOfAccount`), and `liquidate`/`seize` flows where a new deposit token lands on the victim or `feeCollector` (a `seize` fee transfer to `feeCollector` also reverts once its list is full, potentially reverting `Pool.liquidate` calls for collateral types the collector has never held).

### Impact Explanation
Targeted denial of service on a lending protocol: the victim cannot top up collateral of a new type or open a new debt position while an oracle price move pushes their position toward liquidation — i.e., temporary freezing of funds and blocked access to health-restoring actions. Until the victim burns each dust balance (a `withdraw`/`transfer` per token, at their own gas cost), every adding path reverts. Protocol-level impact is bounded (per-account, reversible), matching a medium DoS severity analogous to CVE-2020-14789's availability-only impact.

### Likelihood Explanation
- Fully unprivileged: any EOA holding dust msd-tokens can execute it; no governor/guardian/oracle manipulation required.
- Cost is bounded by depositing minimum amounts of up to ~30 collaterals and N transfer transactions; on pools with few listed collaterals the attacker must also dust debt tokens? No — debt tokens are soulbound (no public transfer), so the attack is limited to the number of whitelisted deposit tokens plus debt entries the victim already has. If the pool has few deposit tokens (<30) and the victim has no other positions, the cap may not be reachable; the attack works when `debtTokens + depositTokens` can be pushed to 30, i.e., pools with many listed collaterals (up to `MAX_TOKENS_PER_USER`) or victims already holding several positions.
- The dust remains locked unless the victim cleans it; cleaning costs the victim one transaction per token.

### Recommendation
- Cap the griefing surface: either (a) make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` non-reverting when full (e.g., skip indexing — the account lists are only used for oracle iteration in `debtOf`/`depositOf`, so skipping would break accounting and is unsafe), or better (b) require opt-in for receiving a *new* token type: revert transfers that would add a token unless `recipient == sender` or recipient has registered consent, or (c) make `DepositToken.transfer` push the token via a claim pattern. Simplest minimal fix: in `DepositToken._transfer`, do not call `pool.addToDepositTokensOfAccount` for unsolicited transfers; only index on `deposit`/`seize` paths, and have `depositOf`/`debtOf` iterate a bounded registry or require explicit registration.

### Proof of Concept
Hardhat-style outline (against real pool setup, not mocks):

```ts
// given: pool with K whitelisted deposit tokens; victim has D debt+deposit tokens,
// K + D >= MAX_TOKENS_PER_USER
const max = await pool.MAX_TOKENS_PER_USER();

// attacker deposits dust and transfers 1 wei of each deposit token to victim
for (const dt of depositTokens) {
  const underlying = await ethers.getContractAt('ERC20', await dt.underlying());
  await underlying.approve(dt.address, 1);
  await dt.deposit(1, attacker.address);           // attacker self-deposit
  await dt.transfer(victim.address, 1);            // fills victim's list
}
// victim now at MAX_TOKENS_PER_USER
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.lengthOf(max);

// victim's deposit into a new collateral reverts
await expect(newDepositToken.connect(victim).deposit(100, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim issuing a new synthetic debt type reverts
await expect(newDebtToken.connect(victim).issue(1))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');

// any incoming transfer of a new msd-token reverts
await expect(dt2.connect(attacker).transfer(victim.address, 1))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Caveat: this DoS is temporary — the victim can `withdraw`/`transfer` each dust position to shrink their list — and it requires the pool to list enough deposit tokens (or the victim to already carry debt positions) for the combined count to reach 30.
