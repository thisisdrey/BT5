### Title
Bancor-formula `ExchangeProcessor` uses raw `double`/`Math.pow` arithmetic for TRC10 pair exchange, letting an attacker force asymmetric rounding that drains pool reserves - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
`ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` all execute their token conversion through `ExchangeCapsule.transaction()`, which by default (unless `allowHardenExchangeCalculation` is enabled) delegates to `ExchangeProcessor`, a Bancor-curve implementation that performs its core conversion math in `double` precision with `Math.pow`. This mirrors the Wise Lending root cause: a share/asset conversion formula whose rounding/precision behavior is not proven safe against adversarial inputs, allowing value to be extracted from the pool instead of a fair 1:1-value swap. [1](#0-0)  The hardened replacement, `SafeExchangeProcessor`, exists specifically to fix this class of precision bug but is opt-in via a chain parameter, so any exchange created/traded while the flag is off (its default state) is exposed. [2](#0-1) 

### Finding Description
`ExchangeCapsule.transaction()` selects between the unsafe `ExchangeProcessor` and the safer `SafeExchangeProcessor` based on the `hardenedCalc` flag, which is read from `dynamicStore.allowHardenExchangeCalculation()`/similar governance parameter and defaults to disabled: [3](#0-2) 

In the unsafe path, `exchangeToSupply` and `exchangeFromSupply` compute the Bancor "relay" conversion using native `double` arithmetic and `Math.pow`, then truncate to `long` with a plain cast:
```java
double issuedSupply = -supply * (1.0 - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
long out = (long) issuedSupply;
```
and symmetrically in `exchangeFromSupply`. [1](#0-0) 

Unlike the hardened `SafeExchangeProcessor`, which routes the same math through `BigDecimal` with an explicit 18-digit scale and `RoundingMode.HALF_UP`/`DOWN` [4](#0-3) , the default `ExchangeProcessor` has no bound on the accumulated floating-point error from `Math.pow` over repeated small-quantity trades against an attacker-chosen pool ratio. An unprivileged account can:
1. Call `ExchangeCreateActuator` to create an exchange with an arbitrarily skewed, minimal-liquidity token pair (only requires `firstTokenBalance > 0` and `secondTokenBalance > 0`, no minimum liquidity enforced) [5](#0-4) .
2. Repeatedly call `ExchangeTransactionActuator`, which performs no independent BigDecimal cross-check on the `ExchangeProcessor` result (unlike `ExchangeWithdrawActuator`, which does compare against a BigDecimal remainder threshold) [6](#0-5) , feeding quantities chosen to maximize the double-precision rounding bias in `(long) issuedSupply`/`(long) exchangeBalance` in its favor.
3. Extract successive small "profits" from the `double` truncation bias, or, at pool extremes (small `supply`/`newBalance`), trigger disproportionate `exchangeFromSupply` outputs relative to the tokens actually deposited, draining the counter-token reserve held in `ExchangeCapsule`.

This is architecturally the same bug class flagged in the Wise Lending report: a share/asset conversion function whose numerical precision was not hardened against adversarial parameter choices, letting an attacker siphon pooled value through legitimate-looking transactions.

### Impact Explanation
If exploitable at scale, this allows unauthorized extraction of counter-party token/TRX reserves from an `Exchange` pool that other TRC10 holders and market participants funded via `ExchangeInjectActuator`/`ExchangeCreateActuator`, i.e., theft of pooled funds reachable purely through the public `ExchangeCreateContract`/`ExchangeTransactionContract` transaction types — no special privilege required. This is a concrete Medium/High-severity finding under the "theft of funds via unbacked balance / unauthorized account operation" category, directly analogous in mechanism and severity band to the ~$464K Wise Lending loss.

### Likelihood Explanation
Likelihood is Medium: the vulnerable `ExchangeProcessor` path is the *default* (hardening is opt-in via `allowHardenExchangeCalculation`), and pool creation/parameter selection (initial `firstTokenBalance`/`secondTokenBalance`) is fully attacker-controlled with no minimum-liquidity floor, making it feasible to engineer a low-liquidity pool that maximizes floating-point rounding bias. However, actually quantifying a profitable, repeatable exploit requires precise numerical analysis of `Math.pow`/`double` truncation behavior at chosen `supply`/`balance` ratios, which I could not fully verify without executing the formula against candidate inputs — this uncertainty should be resolved via targeted numerical simulation/testing before treating this as confirmed-exploitable rather than a hardening gap.

### Recommendation
- Make `allowHardenExchangeCalculation` (routing all exchanges through `SafeExchangeProcessor`) mandatory/default-on rather than opt-in, or remove the legacy `ExchangeProcessor` double-based path entirely.
- Add the same BigDecimal remainder/precision-threshold check used in `ExchangeWithdrawActuator.doValidate()` to `ExchangeTransactionActuator` so no exchange result can be accepted if it deviates beyond a bounded tolerance from an exact BigDecimal/BigInteger computation.
- Enforce a minimum liquidity/minimum pool balance in `ExchangeCreateActuator.doValidate()` to prevent creation of pathologically small, precision-attack-friendly pools.

### Proof of Concept
Conceptual PoC (requires numerical simulation to fully confirm profitable parameters):
1. Attacker calls `ExchangeCreateContract` to create an exchange with minimal reserves, e.g. `firstTokenBalance = 1`, `secondTokenBalance = 1` (only constraint is `> 0` and `<= exchangeBalanceLimit`) [5](#0-4) .
2. Attacker (or colluding accounts) inject additional legitimate liquidity via `ExchangeInjectContract` to reach a ratio where `Math.pow(1 + quant/newBalance, 0.0005)` truncation in `exchangeToSupply`/`exchangeFromSupply` systematically favors the trader over many `ExchangeTransactionContract` calls.
3. Repeated `ExchangeTransactionContract` calls against `ExchangeTransactionActuator`, which trusts the raw `ExchangeProcessor.exchange()` output with no BigDecimal sanity check [6](#0-5) , progressively extract more counter-token value than deposited, draining the pool reserve tracked in `ExchangeCapsule.firstTokenBalance/secondTokenBalance`.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
