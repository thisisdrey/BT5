### No Vulnerability found for this question.

Analysis: The overflow guarded by `ExecutionResultState::new` (`current_account_balance = context.account_balance.checked_add(context.attached_deposit).expect(...)` at [1](#0-0)  ) is never reachable via an attacker-controlled `FunctionCall` because the runtime performs an explicit checked-add guard *before* constructing the `VMContext`/calling into `execute_function_call`, returning a graceful `Err` instead of panicking: [2](#0-1) 

This check occurs in `action_function_call` prior to `execute_function_call` populating `VMContext.account_balance`/`attached_deposit` ( [3](#0-2) ), which is what eventually flows into `ExecutionResultState::new`. Any deposit that would overflow `account.amount() + deposit` is rejected with `StorageError::StorageInconsistentState(...)` and surfaced as an `Err(RuntimeError)`, not a panic.

Independently, the precondition of the scenario — inflating a contract's balance to near `u128::MAX` via "repeated transfers" — is not economically or protocol-feasible: NEAR's total token supply is fixed at genesis (~1e33 yoctoNEAR) and is conserved by the balance-checker across every applied chunk ( [4](#0-3) ), which is many orders of magnitude below `u128::MAX` (~3.4e38). Transfers move existing balance and cannot mint new tokens, so no unprivileged attacker can push any account's balance anywhere near the range needed to trigger the overflow, even in principle. The `action_transfer` path itself also has a checked-add guard returning `StorageInconsistentState` rather than panicking ( [5](#0-4) ).

Given (1) an existing pre-check in `function_call.rs` that intercepts the overflow before it reaches `ExecutionResultState::new`, and (2) the total-supply conservation invariant making the described attacker-controlled balance state unreachable on mainnet, this is not an exploitable finding under the given rules (no reachable mainnet scenario; existing checks already stop it).

## Balance checker

Balance checker computes the total incoming balance and the total outgoing balance.

The total incoming balance consists of the following:

- Incoming validator rewards from validator accounts update.
- Sum of the initial accounts balances for all affected accounts. We compute it using the snapshot of the initial state.
- Incoming receipts balances. The prepaid fees and gas multiplied their gas prices with the attached balances from transfers and function calls.
  Refunds are considered to be free of charge for fees, but still has attached deposits.
- Balances for the processed delayed receipts.
- Initial balances for the postponed receipts. Postponed receipts are receipts from the previous blocks that were processed, but were not executed.
  They are action receipts with some expected incoming data. Usually for a callback on top of awaited promise.
  When the expected data arrives later than the action receipt, then the action receipt is postponed.
  Note, the data receipts are 0 cost, because they are completely prepaid when issued.

The total outgoing balance consists of the following:

- Sum of the final accounts balance for all affected accounts.
- Outgoing receipts balances.
- New delayed receipts. Local and incoming receipts that were not processed this time.
- Final balances for the postponed receipts.
- Total rent paid by all affected accounts.
- Total new validator rewards. It's computed from total gas burnt rewards.
- Total balance burnt. In case the balance is burnt for some reason (e.g. account was deleted during the refund), it's accounted there.
- Total balance slashed. In case a validator is slashed for some reason, the balance is account here.

When you sum up incoming balances and outgoing balances, they should match.
If they don't match, we throw an error.
