### Title
Standby-witness (SR) tie-break sorts on attacker-chosen address/URL, letting a party guarantee it wins reward slots over equally-voted competitors - ([File: chainbase/src/main/java/org/tron/core/store/WitnessStore.java])

### Summary
The SEDA finding is a class of bug where a deterministic ascending/descending sort over participant-controlled keys is used to decide who receives a scarce reward when multiple participants tie on the metric that should determine payout, letting an attacker who can freely choose that key always win. `WitnessStore.sortWitnesses()` and `WitnessStore.sortWitness()` exhibit the same pattern in java-tron: when two witnesses have identical `voteCount`, the tie is broken by the witness's own address-derived string, a value the witness owner fully controls before submitting `WitnessCreateContract`.

### Finding Description
`WitnessStore.sortWitnesses()` orders witnesses primarily by `voteCount` but ties are broken deterministically using values derived from the witness's own address: [1](#0-0) 

- With `allowWitnessSortOptimization()` enabled, ties are broken by `Comparator.comparing(WitnessCapsule::createReadableString).reversed()` — i.e. by the Base58Check-encoded address string, descending.
- With the optimization disabled, ties are broken by `Comparator.comparingInt(w -> w.getAddress().hashCode()).reversed()` — i.e. by the Java `String.hashCode()` of the address bytes, descending.

This ordering is used to select:
1. The **top 27 active witnesses** (block producers, block rewards) via `DposService.updateWitness()`/`MaintenanceManager.doMaintenance()`.
2. The **top 127 standby witnesses** that share `getWitness127PayPerBlock()` via `MortgageService.payStandbyWitness()`, which calls `witnessStore.getWitnessStandby()` → `sortWitnesses()`: [2](#0-1) [3](#0-2) 

A witness account is created by any funded account via a single broadcastable `WitnessCreateContract` transaction (paying `getAccountUpgradeCost()`), and the resulting `WitnessCapsule` address is exactly the caller-supplied `ownerAddress`: [4](#0-3) 

Because private/public key pairs (and therefore the resulting TRON address / its Base58Check string / its Java `hashCode()`) can be generated offline in bulk at negligible cost (vanity-address style brute force), an attacker can pre-compute an address whose `createReadableString()` (or `hashCode()`) sorts as high as possible under the reversed comparator, then register that address as a witness. When that witness's vote count exactly ties the boundary vote count of the 27th active seat or the 127th standby seat, the attacker-controlled address deterministically wins the seat over any equally-voted honest competitor, exactly mirroring the SEDA bug where a pubkey chosen to sort first is always prioritized for reward.

### Impact Explanation
The winner of the 27th active witness slot receives block-production rewards (`payBlockReward`/`payTransactionFeeReward` via `Manager.payReward()`), and standby slots 28–127 receive a pro-rata share of `getWitness127PayPerBlock()`. An attacker who can force a tie at the cutoff (by adjusting self-vote/stake precisely, which is well within an unprivileged account's control) can deterministically displace a legitimate participant from the reward-eligible list purely by choosing a favorably-sorting address, unfairly capturing SR/standby rewards that should be split or awarded based on genuine stake/vote weight rather than an artifact of string/hash ordering.

### Likelihood Explanation
Creating a witness is a single low-cost, unprivileged transaction (`WitnessCreateContract`), and address generation to bias `createReadableString()` or `hashCode()` ordering is cheap, offline, parallelizable brute force (comparable to vanity-address mining). The only additional requirement is engineering the vote count to land exactly on the tie boundary, which the attacker fully controls via `VoteWitnessContract` self-voting or coordinated bribery among voters. This makes exploitation practical, though it depends on an exact vote-count tie occurring at the relevant threshold, which somewhat limits how often it materially changes outcomes versus a clear vote-count win.

### Recommendation
Replace the deterministic, attacker-influenceable tie-break in `WitnessStore.sortWitnesses()`/`sortWitness()` with a source that is not derived from the witness's own chosen address bytes or its string encoding — e.g., use a random deterministic tie-break seeded by block-level entropy (such as the block hash for the cycle), or simply split rewards proportionally among tied candidates instead of granting a strict ordering advantage.

### Proof of Concept
1. Offline, brute-force generate TRON key pairs until the resulting address's Base58Check string (or, if `allowWitnessSortOptimization` is disabled, its byte-array `hashCode()`) is lexicographically/numerically maximal relative to other candidate witnesses expected to tie at the vote-count cutoff.
2. Fund that address and submit `WitnessCreateContract` (`WitnessCreateActuator.execute`) to register it as a witness.
3. Submit `VoteWitnessContract` votes so the new witness's `voteCount` exactly ties the vote count of the witness currently holding the 27th (active) or 127th (standby) position.
4. At the next `MaintenanceManager.doMaintenance()` cycle, `WitnessStore.sortWitnesses()` places the attacker's witness ahead of the legitimate tied competitor purely due to address ordering, and `MortgageService.payStandbyWitness()` / `IncentiveManager.reward()` pays the attacker instead of (or in addition to sharing with) the displaced participant.

```java
  public static void sortWitnesses(List<WitnessCapsule> witnesses, boolean isSortOpt) {
    witnesses.sort(Comparator.comparingLong(WitnessCapsule::getVoteCount).reversed()
        .thenComparing(isSortOpt
            ? Comparator.comparing(WitnessCapsule::createReadableString).reversed()
            : Comparator.comparingInt((WitnessCapsule w) -> w.getAddress().hashCode()).reversed()));
  }
```

```java
  public void payStandbyWitness() {
    List<WitnessCapsule> witnessStandbys = witnessStore.getWitnessStandby(
        dynamicPropertiesStore.allowWitnessSortOptimization());
    long voteSum = witnessStandbys.stream().mapToLong(WitnessCapsule::getVoteCount).sum();
    if (voteSum < 1) {
      return;
    }
    long totalPay = dynamicPropertiesStore.getWitness127PayPerBlock();
    double eachVotePay = (double) totalPay / voteSum;
    for (WitnessCapsule w : witnessStandbys) {
      long pay = (long) (w.getVoteCount() * eachVotePay);
      payReward(w.getAddress().toByteArray(), pay);
      logger.debug("Pay {} stand reward {}.", Hex.toHexString(w.getAddress().toByteArray()), pay);
    }
  }
```
