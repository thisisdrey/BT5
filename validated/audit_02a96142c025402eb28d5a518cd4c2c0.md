### Title
Wallet Contract permanently loses an external caller's attached deposit when a faulty relayer's target address matches an existing named account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`inner_rlp_execute` tracks any deposit an external (non-owner) caller attaches to `rlp_execute` in a `CallerDeposit`, so it can be refunded if the underlying cross-contract call fails [1](#0-0) . This refund is only wired up through `rlp_execute_callback`, which sends the refund transfer when `PromiseResult::Failed` is observed [2](#0-1) . However, in the `address_check_callback` path — reached when an emulated base-token transfer targets an address that must first be checked against the address registrar — the `caller_deposit` is silently dropped in both outcomes of that branch, so the refund transfer is never created and the caller's deposit is stuck in the contract permanently.

### Finding Description
When `inner_rlp_execute` builds an `EOABaseTokenTransfer` with `address_check: Some(address)`, it schedules a call to the address registrar and, in `.then(...)`, forwards `caller_deposit` into `address_check_callback` [3](#0-2) .

Inside `address_check_callback`, once the registrar lookup result is known, there are exactly two ways it can resolve when `maybe_account_id.is_some()` (i.e., the destination address actually maps to an existing named account, indicating the relayer submitted a bad/faulty transaction):

```rust
let promise = if maybe_account_id.is_some() {
    if env::signer_account_id() == current_account_id {
        create_ban_relayer_promise(current_account_id)
    } else {
        return PromiseOrValue::Value(ExecuteResponse {
            success: false,
            success_value: None,
            error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
        });
    }
} else {
    ...
    match action_to_promise(target, action).map(|p| p.then(ext.rlp_execute_callback(caller_deposit))) { ... }
};
``` [4](#0-3) 

- Branch A: `create_ban_relayer_promise(current_account_id)` is called without `caller_deposit` at all [5](#0-4) . This promise deletes the relayer's access key and calls `ban_relayer`, which merely resets `has_in_flight_tx` and returns a failure `ExecuteResponse`, with no reference to `caller_deposit` anywhere [6](#0-5) .
- Branch B: the function returns `PromiseOrValue::Value(...)` directly, again with no reference to `caller_deposit`.

In both branches the `caller_deposit` value captured earlier (representing real yoctoNEAR attached by an external, non-owner predecessor account, e.g. a relayer paying on behalf of the user) is simply dropped. Since the deposit was already attached to (and deducted into) the current account's balance when the `#[payable]` `rlp_execute` call was made [7](#0-6) , and no transfer-back promise is ever constructed on this path, the deposit remains stuck in the Wallet Contract's balance with no code path to return it to the caller.

By contrast, the intended behavior — demonstrated in the `nep_141_storage_balance_callback` path and validated by `test_caller_refunds` — is that any failure of the on-chain execution refunds the caller's deposit via `rlp_execute_callback`'s `PromiseResult::Failed` branch [8](#0-7) . The `address_check_callback` failure branches bypass `rlp_execute_callback` entirely, so that refund logic never executes.

### Impact Explanation
This causes permanent freezing/loss of funds for an external, non-owner caller (typically a relayer) whenever it submits a base-token-transfer transaction whose Ethereum-style `to` address happens to correspond to an already-registered named NEAR account and attaches a non-zero NEAR deposit to `rlp_execute`. The deposit becomes irrecoverably locked in the ETH-implicit account's Wallet Contract balance, since there is no method exposed to withdraw or reclaim it on behalf of the caller. This matches the "permanent freezing of funds" acceptance criterion for this scan.

### Likelihood Explanation
Likelihood is moderate: it requires (1) an external caller attaching a non-zero deposit to `rlp_execute` (a supported, documented usage pattern for relayers per `CallerDeposit`'s doc comments), and (2) the emulated transaction's target address matching a registered named account — which happens whenever a user or relayer submits (accidentally or through a stale/incorrect encoding) an Ethereum-style transfer whose target resolves to an existing NEAR account rather than a fresh eth-implicit address. This is a realistic relayer/user error path, not a contrived edge case, and it is unprivileged — any ordinary account can trigger it by calling `rlp_execute` with a deposit.

### Recommendation
Thread `caller_deposit` through both resolution branches of `address_check_callback` when `maybe_account_id.is_some()`:
- In the "faulty relayer" branch, append a refund transfer to `create_ban_relayer_promise`'s promise chain (or issue a separate refund promise) before/alongside banning the relayer, analogous to the refund logic in `rlp_execute_callback`.
- In the direct-error-return branch, likewise issue a refund promise for `caller_deposit` before returning the failure `ExecuteResponse`, or restructure `address_check_callback` so that both failure outcomes flow through `rlp_execute_callback`'s existing refund logic instead of duplicating (and this time omitting) it.

### Proof of Concept
1. Deploy the Wallet Contract for an ETH-implicit account `A` (owned by a Secp256k1 key), matching the setup in `test_wallet_contract_interaction` / `test_caller_refunds` [8](#0-7) .
2. Have an external relayer account `R` (not the owner) call `rlp_execute` on `A`, attaching a non-zero NEAR deposit, with an RLP-encoded Ethereum transaction whose `to` address requires the address-registrar lookup path (`EOABaseTokenTransfer { address_check: Some(address), .. }`), and where `address` happens to decode/hash to an address already registered to an existing named account (e.g., a value equal to `keccak256` of a known registered account's address, obtainable via the `AddressRegistrar` used in `test_register_without_deposit` [9](#0-8) ).
3. Observe that `address_check_callback` is invoked with `maybe_account_id = Some(...)`.
4. Confirm the resulting `ExecuteResponse` reports failure, and check `R`'s NEAR balance before and after the call (analogous to the balance assertions in `test_caller_refunds`): unlike the "call fails" scenario tested there, `R`'s balance will show the deposit was **not** refunded, while `A`'s (the wallet contract's) balance retains the deposit — demonstrating the funds are permanently stuck.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

/// Test asserting the address registrar requires a deposit.
#[tokio::test]
async fn test_register_without_deposit() -> anyhow::Result<()> {
    let TestContext { worker, address_registrar, .. } = TestContext::new().await?;

    let method = "register";
    let args = br#"{"account_id": "birchmd.near"}"#;
    let result = address_registrar.call(method).args(args.to_vec()).transact().await?;
    assert!(result.is_failure(), "Call without deposit must fail");

    let pre_tx_account_balance = address_registrar.as_account().view_account().await?.balance;
    let deposit_amount = NearToken::from_yoctonear(320000000000000000000);
    let result = worker
        .root_account()?
        .call(address_registrar.id(), method)
        .args(args.to_vec())
        .deposit(deposit_amount)
        .transact()
        .await?;

    let output: Option<String> = result.json()?;
    assert_eq!(output.as_deref(), Some("0x4bfcff9a964925adf801c866f6ada98bd7ec40ca"));
    let post_tx_account_balance = address_registrar.as_account().view_account().await?.balance;
    assert!(
        post_tx_account_balance.as_yoctonear() - pre_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    // Sending a duplicate transaction does not take the deposit again.
    let pre_tx_account_balance = post_tx_account_balance;
    let result = worker
        .root_account()?
        .call(address_registrar.id(), method)
        .args(args.to_vec())
        .deposit(deposit_amount)
        .transact()
        .await?;

    let output: Option<String> = result.json()?;
    assert_eq!(output, None);
    let post_tx_account_balance = address_registrar.as_account().view_account().await?.balance;
    assert!(
        post_tx_account_balance.as_yoctonear() - pre_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    Ok(())
}
