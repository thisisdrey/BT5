### Title
Locked delegated resource re-locks entire accumulated balance on repeated `DelegateResourceContract` calls, extending prior lockups - ([File: actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java])

### Summary
`DelegateResourceActuator` implements a "locked delegation" feature (`DelegateResourceContract.lock=true`) that freezes an owner's resource delegation to a receiver until an `expireTime`. When an owner sends a second locked-delegate transaction to the same receiver (e.g., to add more delegated bandwidth/energy), the actuator overwrites the expire time for the *entire accumulated* locked balance rather than tracking the new increment separately — directly analogous to the reported "Share Lock Extension on Subsequent Deposits" bug class, where a global/per-recipient lock timestamp gets reset on every new contribution instead of being tracked per-deposit.

### Finding Description
In `DelegateResourceActuator.delegateResource`, when `lock=true`, a new `expireTime` is computed from `now + lockPeriod * BLOCK_PRODUCED_INTERVAL` and applied via `DelegatedResourceCapsule.addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy`: [1](#0-0) 

`DelegatedResourceCapsule.addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy` add the new balance to the existing accumulated total and unconditionally overwrite the single `expireTimeForBandwidth`/`expireTimeForEnergy` field for the whole balance: [2](#0-1) 

There is no per-tranche tracking of lock expiration — the `DelegatedResource` protobuf stores only a single `frozen_balance` and a single `expire_time` per (owner, receiver, lock) key, so a delegation made at `t1` (which would unlock at `t1+lockPeriod`) is merged with a later delegation at `t2` and the *combined* balance is relocked until `t2+lockPeriod`. The owner cannot partially undelegate the earlier, already-mostly-unlocked portion; the entire accumulated locked balance is bound by the newest expire time.

The validation logic (`validRemainTime`) only enforces that the *new* lock period cannot be *shorter* than the remaining time of the existing lock — it does not prevent extension, and it does not protect against the case where the caller simply wants to add a small amount of additional delegated balance but is forced to accept relocking of the whole existing locked amount: [3](#0-2) [4](#0-3) 

This is directly structurally analogous to the reported vault issue: a single mapping/field tracks "unlock time for the whole balance," and any incremental top-up transaction (reachable by any account holder issuing a `DelegateResourceContract` with `lock=true`) resets/extends that unlock time for the entire previously-committed balance, not just the increment.

### Impact Explanation
An account owner who has locked-delegated resources to a receiver, intending part of the balance to unlock soon, will have that expectation broken if they (or, in shared/custodial wallet setups, any party with signing capability) issue another locked delegate transaction to the same receiver — the entire balance becomes locked until the new, later expiration. This can cause TRX-backing resources (bandwidth/energy delegated with lock) to be inaccessible for undelegation for longer than the user expects/intends, effectively freezing funds for an extended, unbounded-per-call duration (bounded only by `MAX_DELEGATE_LOCK_PERIOD`, itself a large parameter, e.g. up to ~1 year based on `MAX_DELEGATE_LOCK_PERIOD` proposal range `(86400, 10512000]` seen in `ProposalUtil`). Since the underlying frozen TRX cannot be unfrozen while delegated (`FreezeBalanceV2`/`UnDelegateResourceContract` semantics), this design fragility can result in prolonged, unintended freezing of user funds — a medium-severity availability/funds-lock issue matching the reported bug class exactly.

### Likelihood Explanation
This is reachable by any account holder using ordinary broadcast transactions (`DelegateResourceContract` with `lock=true`), no special privilege required. The behavior is deterministic and reproducible on every repeated locked delegation to the same receiver; it does not require any malicious actor beyond normal usage patterns (e.g., a user or wallet auto-topping-up delegated resources), making the likelihood of accidental trigger moderate-to-high, though it requires the user/receiver pair to intentionally use the "lock" delegation feature repeatedly.

### Recommendation
- Track lock expiration per delegation tranche (or per-transaction) rather than a single aggregate `expire_time` field on `DelegatedResourceCapsule`, so that adding more locked-delegated balance does not extend the unlock time of previously delegated amounts.
- Alternatively, when merging into an existing locked delegation, only extend the expire time if the caller opts in, or require the new lock period to apply solely to the incremental balance (e.g., splitting frozen balance by expiry bucket similar to `UnFreezeV2` list entries, which java-tron already does for unfreeze operations).
- Add explicit documentation/warnings in `DelegateResourceContract` semantics that subsequent locked delegations to the same receiver reset the unlock time for the full accumulated balance.

### Proof of Concept
1. Owner freezes bandwidth (`FreezeBalanceV2`), then delegates part of it with lock at `t1`: `DelegateResourceContract{lock=true, lockPeriod=L1}` → `DelegatedResourceCapsule.expireTimeForBandwidth = t1 + L1*BLOCK_PRODUCED_INTERVAL` (see `delegateResource` in `DelegateResourceActuator.java:290-311`).
2. Before `t1+L1` elapses, owner delegates additional bandwidth to the same receiver with lock at `t2` (`t1 < t2 < t1+L1`): `DelegateResourceContract{lock=true, lockPeriod=L2}`.
3. `validRemainTime` only requires `L2*BLOCK_PRODUCED_INTERVAL >= (expireTimeForBandwidth - t2)` i.e. it must not shrink the remaining lock — the transaction with an equal or larger `L2` succeeds.
4. `addFrozenBalanceForBandwidth` then sets `frozenBalanceForBandwidth += newBalance` and `expireTimeForBandwidth = t2 + L2*BLOCK_PRODUCED_INTERVAL` for the **combined** balance — the originally-almost-unlockable amount from step 1 is now locked until the new, later time, confirmed by the existing test `testMaxDelegateLockPeriodForBandwidth` which shows the expire time being reset to the latest call's computed value for the whole `lockedResourceCapsule` balance: [5](#0-4) 

This confirms the core mechanism: a single global expire-time field is overwritten on each new locked delegation, relocking the entire accumulated balance — the same "share lock extension on subsequent deposits" pattern flagged in the external report.

  private void validRemainTime(ResourceCode resourceCode, long lockPeriod, long expireTime,
      long now) throws ContractValidateException {
    long remainTime = expireTime - now;
    if (lockPeriod * BLOCK_PRODUCED_INTERVAL < remainTime) {
      throw new ContractValidateException(
          "The lock period for " + resourceCode.name() + " this time cannot be less than the "
              + "remaining time[" + remainTime + "ms] of the last lock period for "
              + resourceCode.name() + "!");
    }
  }
