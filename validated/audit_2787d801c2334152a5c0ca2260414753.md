### Title
CreateAccount succeeds unconditionally over orphaned PostponedReceipt/PendingDataCount/ReceivedData/PromiseYield* rows left by DeleteAccount - ([File: runtime/runtime/src/actions.rs, core/store/src/utils/mod.rs])

### Summary
`remove_account` in `core/store/src/utils/mod.rs` only clears `TrieKey::Account`, `TrieKey::ContractCode`, access keys, gas key nonces, and `TrieKey::ContractData` for the deleted account. It never touches `TrieKey::PostponedReceipt`, `PendingDataCount`, `ReceivedData`, or `PromiseYield*` keys scoped to that `account_id`. `action_create_account` (in `runtime/runtime/src/actions.rs`) operates purely on the in-memory `Account` struct being constructed and does not query the trie for any of these leftover key types before allowing account creation to proceed.

### Finding Description
`remove_account` explicitly enumerates the trie key classes it purges: [1](#0-0)  and then iterates and removes access keys/gas key nonces [2](#0-1)  and contract data [3](#0-2) , finally returning without any interaction with `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, `TrieKey::ReceivedData`, or any `TrieKey::PromiseYield*`/`YieldIdToDataId`/`DataIdToYieldId` variant for that account.

`action_create_account`'s imports show it only pulls in `near_store::{StorageError, TrieUpdate, compute_gas_key_balance_sum, get_access_key, get_gas_key_nonce, remove_account, set_access_key, set_gas_key_nonce}` [4](#0-3)  — there is no import of `get_postponed_receipt`, `has_promise_yield_receipt`, `has_promise_yield_status`, `has_yield_id_mapping`, or any received-data/pending-data-count accessor. Since Rust requires these helpers to be imported to call them, and none are imported into `actions.rs`, `action_create_account` structurally cannot be performing any leftover-row check against those trie key families before creating the account.

### Impact Explanation
This confirms the root cause underlying the escalation scenario: `DeleteAccount` (leaving a survivor row such as a pending `PostponedReceipt`) followed by `CreateAccount` for the same `account_id` proceeds unconditionally, with no defensive check or purge. Any receipt/data logic keyed on the old account's leftover state (e.g., resumed postponed action receipts, received-data callbacks, or promise-yield timeouts) can then be misattributed to or interact with the newly created account, constituting an authorization/state-integrity violation across account identities (the "authorization exactness" invariant is broken because the new account inherits protocol-level residue it never produced).

### Likelihood Explanation
No privileged access is required — any unprivileged account holder can submit `DeleteAccount` followed by `CreateAccount` (or the implicit-account creation path) for the same account id in ordinary transactions, and repeat this at will. No existing check in `action_create_account` or `remove_account` gates or purges these leftover rows.

### Recommendation
Extend `remove_account` to also purge `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, `TrieKey::ReceivedData`, and all `PromiseYield*`/yield-id-mapping keys scoped to the account being deleted (or defer the deletion / refuse recreation until these are drained), mirroring the cleanup already done for access keys and contract data.

### Proof of Concept
Unit test plan: 1) construct a `TrieUpdate` and use `near_store::set_postponed_receipt` (or manually `set` a `TrieKey::PostponedReceipt { receiver_id, receipt_id }`) for account `"a.near"`. 2) Call `remove_account(&mut state_update, &"a.near".parse().unwrap())` and assert via `get_postponed_receipt` that the row still exists (proving no purge). 3) Invoke `action_create_account` for `"a.near"` with a fresh `Account`/`ActionResult` and assert it returns `Ok`/success with no error and no additional trie mutation touching the `PostponedReceipt` key — demonstrating creation proceeds unconditionally despite the orphaned row.
