### Title
Unbounded `HashSet<u32>` allocation from `pages_indexes` query parameter before cap enforcement - (File: stackslib/src/net/api/getattachmentsinv.rs)

### Summary
`RPCGetAttachmentsInvRequestHandler::try_parse_request` parses every comma-separated `pages_indexes` value into a `HashSet<u32>` with no size limit during parsing. The `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` (8) check is only applied afterward in `try_handle_request`, once the full HashSet already has been materialized in memory.

### Finding Description
The claimed equality — "query-parameter-derived allocation size == validated page cap, enforced before allocation" — is broken. In `try_parse_request` [1](#0-0) , the handler iterates over `entry in pages_indexes_value.split(',')`, parses each as `u32`, and unconditionally inserts into `page_indexes: HashSet<u32>` with no bound check at all. Only later, in `try_handle_request`, is `page_indexes.len() > MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` checked and the request rejected with 400 [2](#0-1) . By this point the full deduplicated set of distinct `u32` values (up to tens of thousands, or theoretically up to 2^32 distinct values bounded only by request size) has already been allocated, hashed, and inserted, and then collected into a `Vec<u32>` and sorted at line 118-119 before the cap is checked. A remote, unauthenticated caller can send `GET /v2/attachments/inv?index_block_hash=...&pages_indexes=0,1,2,...,N` with a large `N` of distinct comma-separated integers to force the node to perform this parsing, hashing, and allocation work on every single request, only to be rejected afterward. This endpoint is reachable without any RPC secret or privileged role — it is a public GET RPC endpoint.

### Impact Explanation
Each malicious request forces the node to do O(N) parsing, hashing/insertion into a `HashSet`, and O(N log N) sorting of a `Vec<u32>` before rejecting the request, where N is bounded only by the HTTP request/query-string size the node accepts. This is repeatable per-request at negligible attacker cost (one HTTP GET), consuming CPU and transient memory on the node's RPC handling thread for each request. This matches the explicitly allowed category "bounded compute DoS on a read endpoint" (High).

### Likelihood Explanation
No authentication, secret, peer relationship, or StackerDB slot is required — any remote client that can reach the node's RPC port can send this request. The attack requires no special node/tip state and is trivially repeatable at will, making it low-cost to execute and high-frequency to repeat, though the impact is bounded per-request (not a crash) since parsing eventually completes and the request is rejected with 400.

### Recommendation
Cap the number of distinct entries in `pages_indexes` during parsing itself (e.g., track a count of accepted entries and break/error out as soon as more than `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` distinct or even raw comma-separated entries are seen), rather than deferring the length check to `try_handle_request`. Additionally, bound the number of `split(',')` segments processed before ever inserting into the `HashSet`.

### Proof of Concept
Add a test in `stackslib/src/net/api/tests/getattachmentsinv.rs` that constructs an `HttpRequestPreamble`/query string like `pages_indexes=0,1,2,...,50000` (50,000 distinct comma-separated `u32` values) with a valid `index_block_hash`, and calls `RPCGetAttachmentsInvRequestHandler::try_parse_request` directly. Assert that the parsing itself performs unbounded work by instrumenting/measuring the size of the resulting `self.page_indexes` `Vec` immediately after `try_parse_request` succeeds (it will be far larger than `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST`), demonstrating that the cap in `try_handle_request` (line 159) is applied only after the costly parse/hash/sort work in `try_parse_request` (lines 88-119) is already done.
