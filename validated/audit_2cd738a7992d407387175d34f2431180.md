Audit Report

## Title
Snowbridge tip funds are irrecoverably burned and lost on remote-dispatch failure with no refund/claim mechanism - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`, `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`pallet-snowbridge-system-frontend::add_tip` on AssetHub swaps the user's tip asset for Ether and irreversibly burns it via `burn_for_teleport` before dispatching an XCM `Transact` to BridgeHub's `snowbridge-pallet-system-v2::add_tip`. [1](#0-0)  If that remote call fails — because the target nonce was already consumed in the inbound queue or the pending order no longer exists in the outbound queue — the already-burned value is merely recorded into a write-only `LostTips` storage map with no extrinsic, hook, or governance call anywhere in the repository that reads it back out to refund the sender.

## Finding Description
On AssetHub, `add_tip` calls `swap_fee_asset_and_burn`, which either swaps the tip asset for Ether and burns it via `swap_and_burn`, or directly burns the fee asset via `burn_for_teleport` if it is already Ether. [2](#0-1)  This burn happens synchronously in the same extrinsic call, before the XCM `Transact` carrying `EthereumSystemCall::AddTip` is even sent to BridgeHub. [3](#0-2) 

On BridgeHub, `EthereumSystemV2::add_tip` forwards the call to `InboundQueue::add_tip` or `OutboundQueue::add_tip` depending on message direction. [4](#0-3)  The inbound queue's implementation returns `AddTipError::NonceConsumed` if the message nonce has already been processed. [5](#0-4)  The outbound queue's implementation returns `AddTipError::UnknownMessage` if the `PendingOrders` entry for that nonce has already been removed (i.e., the message was already delivered). [6](#0-5) 

If either call fails, `EthereumSystemV2::add_tip` swallows the error and only increments the `LostTips` map for the sender, still returning `Ok(())` from the extrinsic. [7](#0-6)  The storage item itself is documented as write-only pending future work: *"Capturing the lost tips here supports implementing a recovery method in the future."* [8](#0-7)  A repository-wide search for `LostTips` confirms it is only referenced in `system-v2/src/lib.rs` (write) and in test files (`system-v2/src/tests.rs`, `snowbridge_v2_outbound.rs`) that assert the counter incremented — no dispatchable, hook, or trait implementation reads and pays it out anywhere in the codebase.

The root cause is a lack of atomicity between the AssetHub-side burn and the BridgeHub-side registration: XCM `Transact` execution is asynchronous and there is no guaranteed ordering between the remote tip-registration call and the relayer's normal message-processing calls (`submit` consuming the inbound nonce, or delivery-receipt processing removing the outbound `PendingOrders` entry).

## Impact Explanation
This matches the "permanent user-fund or bridge-state lock" category in the accepted impact gate: a user's real asset value is irreversibly destroyed on AssetHub via `burn_for_teleport`, and if the corresponding remote registration fails, no compensating mint, refund, or claim path exists — the value is permanently unrecoverable, tracked only in a dangling `LostTips` counter with no consumer. [8](#0-7) 

## Likelihood Explanation
High and requires no privileged or malicious actor. An ordinary unprivileged signed user calling `add_tip` (`bridges/snowbridge/pallets/system-frontend/src/lib.rs:261`) can trigger this simply by targeting a message whose nonce/order is processed by a normal, honest relayer between the AssetHub burn and the BridgeHub `Transact` execution — an entirely expected race under regular bridge operation with no adversarial timing needed. [1](#0-0) 

## Recommendation
Avoid burning the tip asset on AssetHub until the remote tip registration on BridgeHub is confirmed successful (e.g., via a receipt/callback pattern), or implement a `claim_lost_tip`-style extrinsic that lets the original sender reclaim the value recorded in `LostTips::<T>` (e.g., `LostTips::<T>::take(sender)` followed by minting/teleporting the amount back to them). At minimum, wire up a recovery path so the "future recovery method" referenced in the code comment actually exists. [8](#0-7) 

## Proof of Concept
1. User calls `SnowbridgeSystemFrontend::add_tip(origin, MessageId::Inbound(N), asset)` on AssetHub for an inbound nonce `N` not yet processed.
2. `swap_fee_asset_and_burn` swaps/burns the asset via `burn_for_teleport`, destroying the value on AssetHub. [2](#0-1) 
3. The XCM `Transact` carrying `EthereumSystemCall::AddTip{sender, message_id: Inbound(N), amount}` is sent to BridgeHub via `send_transact_call`. [9](#0-8) 
4. Before the `Transact` executes, a relayer submits/processes message `N`, setting `Nonce::<T>::set(N)` in the inbound queue. [10](#0-9) 
5. When the `Transact` executes, `EthereumSystemV2::add_tip` calls `InboundQueue::add_tip(N, amount)`, which returns `Err(AddTipError::NonceConsumed)`. [5](#0-4) 
6. `EthereumSystemV2::add_tip` catches the error and only mutates `LostTips::<T>`, emitting `TipProcessed{success: false}`. [11](#0-10) 
7. The user's `amount`, already burned in step 2, is permanently unrecoverable — no extrinsic exists anywhere in the codebase to reclaim `LostTips` value.

			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether
			let ether_asset = Asset::from((ether_location.clone(), ether_gained));

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}

		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			// If the nonce is already processed, return an error
			ensure!(!Nonce::<T>::get(nonce.into()), AddTipError::NonceConsumed);
			// Otherwise add the tip.
			Tips::<T>::mutate(nonce, |tip| {
				*tip = Some(tip.unwrap_or_default().saturating_add(amount));
			});
			return Ok(());
		}

	impl<T: Config> AddTip for Pallet<T> {
		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			PendingOrders::<T>::try_mutate_exists(nonce, |maybe_order| -> Result<(), AddTipError> {
				match maybe_order {
					Some(order) => {
						order.fee = order.fee.saturating_add(amount);
						Ok(())
					},
					None => Err(AddTipError::UnknownMessage),
				}
			})
		}
	}
