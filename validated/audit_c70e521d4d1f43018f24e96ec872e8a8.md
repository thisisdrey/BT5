### Title
Account owner permission can be set to the unspendable zero address via `AccountPermissionUpdateContract`, permanently locking the account - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator` lets any account holder replace their `Owner`/`Witness`/`Active` permissions with a new set of `Key` addresses. Validation of each key address only calls `DecodeUtil.addressValid()`, which checks length and the network prefix byte but never rejects the all-zero address (`0x41` followed by 20 zero bytes). This mirrors the reported bug class: an address field that is meant to identify a controllable signer can be set to a value nobody can control, permanently disabling authorization.

### Finding Description
`checkPermission()` validates every key in a `Permission` solely with `DecodeUtil.addressValid`: [1](#0-0) 

`DecodeUtil.addressValid` only checks that the byte array is 21 bytes long and starts with the correct prefix byte — it never checks that the remaining 20 bytes are non-zero: [2](#0-1) 

Consequently, a `Permission.Key` whose address is `addressPreFixByte` + 20 zero bytes ("zero address") passes validation like any other address, as long as the weight/threshold arithmetic checks pass: [3](#0-2) 

On `execute()`, this permission set (including the zero-address key) is written directly onto the account via `AccountCapsule.updatePermissions`, replacing the previous `Owner` permission: [4](#0-3) [5](#0-4) 

Since nobody holds the private key for the zero address, once the `Owner` permission's key set is composed only of unusable (zero or otherwise uncontrollable) key addresses meeting the threshold, no future transaction signed by the account can satisfy the owner permission, and (if `AccountPermissionUpdateContract` itself requires owner permission) the account can never again update its own permissions, transfer funds requiring owner-level signatures, or perform any operation gated by the `Owner` permission.

### Impact Explanation
This results in permanent loss of control over the account's `Owner` permission (and any `Active`/`Witness` permission set the same way), effectively freezing any funds or resources that require owner-level authorization forever, with no path to recovery (no `require(newAdmin != 0)`-style guard exists anywhere in `checkPermission`). This matches the "permanent freezing of funds" / "unauthorized loss of account control" impact bar.

### Likelihood Explanation
This is reachable directly from a single signed `AccountPermissionUpdateContract` transaction, broadcastable by any account holder with `AllowMultiSign` enabled (a normal, non-privileged, already-live feature per `dynamicStore.getAllowMultiSign()`). No special SR/witness/committee privilege is required — only that the account submitting the transaction currently satisfies its own existing owner permission. It could occur by user error (crafting the wrong contract or reusing address `0` as a placeholder) or be used maliciously against a target who is tricked into signing/co-signing a multisig update.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()`, in addition to `DecodeUtil.addressValid`, explicitly reject the all-zero address (and consider rejecting other well-known "burn"/black-hole addresses) for every `Key` in `owner`, `witness`, and `actives` permissions, e.g.:
```java
if (Arrays.equals(key.getAddress().toByteArray(), new byte[]{DecodeUtil.addressPreFixByte, /*20 zero bytes*/})) {
  throw new ContractValidateException("key address must not be the zero address");
}
```

### Proof of Concept
1. Enable multisign (`AllowMultiSign = 1`, already required to reach this code path).
2. Attacker (or the account owner by mistake) crafts an `AccountPermissionUpdateContract` for `OWNER_ADDRESS` where the `Owner` permission's single key has weight ≥ threshold and address = `addressPreFixByte + 20×0x00` (the zero address), and a valid `Active` permission list to satisfy `getActivesCount()` checks.
3. `AccountPermissionUpdateActuator.validate()` passes because `checkPermission()` only calls `DecodeUtil.addressValid`, which accepts the zero address.
4. `execute()` calls `AccountCapsule.updatePermissions`, overwriting the account's real `Owner` permission with the zero-address key.
5. No subsequent transaction can ever satisfy this `Owner` permission (no one holds the zero address's private key), so the account's owner-gated operations, including any subsequent `AccountPermissionUpdateContract` to fix the mistake, are permanently blocked.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
