### Title
Signature Malleability in `ValidateMultiSign` Precompile Allows Double-Counting of a Single Signer's Weight - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ECDSASignature.validateComponents()` check used throughout java-tron's signature-recovery paths only verifies that `r` and `s` lie in `[1, SECP256K1N)` — it does not enforce the canonical/low-`s` form (`s <= HALF_CURVE_ORDER`). This is the same root cause as the reported `castVoteBySig` malleability issue: a single ECDSA keypair can produce two distinct-but-valid signatures `(r, s, v)` and `(r, N-s, v')` over the same hash that both recover to the same address. In the `ValidateMultiSign` precompiled contract, the weight-deduplication logic keys off the exact signature bytes rather than solely off the recovered address, so a malleable variant of an already-counted signature is not deduplicated and its key weight is added to the running total a second time. [1](#0-0) 

### Finding Description
`ECDSASignature.validateComponents()` accepts any `s` in `(0, N)`, with no canonical-form (low-`s`) restriction: [1](#0-0) . The canonicalization helper `toCanonicalised()` exists in the same class but is never invoked on this validation path [2](#0-1) .

This lax validation is used by the TVM `ValidateMultiSign` precompiled contract, reachable by any smart contract call (i.e., by an unprivileged contract caller broadcasting a transaction). For each signature in the caller-supplied array, the contract recovers an address via `recoverAddrBySign` (which calls `signature.validateComponents()` without any malleability/canonical check) [3](#0-2) , then accumulates weight: [4](#0-3) 

The dedup check is:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
        continue;
    }
    MUtil.checkCPUTime();
}
```
Here `sign` is `merge(recoveredAddr, sign)` — i.e., the tuple of (address, raw signature bytes). The outer check correctly detects "this address has already contributed weight," but the inner check only skips adding weight again if the *exact byte-for-byte signature* was already seen. Because a malleable variant `(r, N-s)` produces a *different* byte sequence than the original `(r, s)` while still recovering to the *same* address, the inner `matrixContains` check fails to match, `continue` is skipped, and `totalWeight += weight` executes again for the same key/address.

### Impact Explanation
`ValidateMultiSign` is a general-purpose precompile intended to let smart contracts (e.g. custom multi-sig wallets, escrow, exchange/order-approval contracts) verify that a threshold of weighted keys from a Tron account `Permission` has approved an action, by summing weights of independently recovered signer addresses until `totalWeight >= permission.getThreshold()`. By generating two signatures over the same message with the same private key (one canonical, one with `s' = N - s`), a single key holder can inflate their contributed weight, effectively satisfying a multi-signature threshold that was supposed to require additional independent signers. This allows unauthorized approval of an on-chain operation (fund transfer, contract execution, order placement, etc.) gated by this precompile — i.e., unauthorized account operation / theft of funds guarded by a smart-contract-level multisig scheme.

### Likelihood Explanation
Exploitation only requires knowledge of one private key already present with nonzero weight in the target `Permission`, and the ability to derive the mathematically trivial malleable counterpart of an ECDSA signature (negate `s` mod curve order, flip parity bit) — no cryptographic breakage is needed. The attacker calls the smart contract (or the precompile directly via a crafted contract call) with two entries in the signature array. This is reachable from any unprivileged contract caller/transaction broadcaster.

### Recommendation
Enforce canonical (low-`s`) signature form in `ECDSASignature.validateComponents()` (or specifically in the `ValidateMultiSign`/`recoverAddrBySign` path) by rejecting `s > HALF_CURVE_ORDER`, consistent with `toCanonicalised()`. Additionally/alternatively, change the dedup logic in `ValidateMultiSign.execute` to key strictly on the **recovered address** (skip immediately once an address has contributed weight), rather than on the exact `(address, signature-bytes)` tuple, since the semantic intent is "one key contributes weight once."

### Proof of Concept
1. Create a Tron account with an `Active` `Permission` containing key `K1` (weight `w1`) and key `K2` (weight `w2`), with `threshold = w1 + w2` (i.e., both keys required).
2. Attacker controls only `K1`. Compute `hash = sha256(address || permissionId || data)` as done by `ValidateMultiSign.execute` [5](#0-4) .
3. Sign `hash` with `K1` to get `sig1 = (r, s, v)`.
4. Derive the malleable counterpart `sig2 = (r, N-s, v XOR 1)` (standard ECDSA malleability transform); `sig2` recovers to the same address as `sig1`.
5. Call the contract (or the precompile) with `signatures = [sig1, sig2]`.
6. In `ValidateMultiSign.execute`, iteration 1 adds `w1` for `K1`'s address and records `(address, sig1)`. Iteration 2: `recoveredAddr` == `K1`'s address (outer `matrixContains` true), but `merge(recoveredAddr, sig2)` != the stored `(address, sig1)` tuple, so inner `matrixContains` is false and `continue` is skipped; `w1` is added again, giving `totalWeight = 2*w1`.
7. If `2*w1 >= threshold`, the call returns `DATA_ONE` (success) even though only one real key participated — bypassing the intended 2-of-2 requirement [6](#0-5) .

Note: full exploit reproduction (actual byte-level construction/verification of `sig2` recovering to the same address, and its interaction with `Rsv.fromSignature`/`recoverAddrBySign`) was not runnable in this read-only analysis; the vulnerability is derived from static review of `ECDSASignature.validateComponents()` and `ValidateMultiSign.execute`'s deduplication logic, which are directly and precisely cited above.

      if (s.compareTo(HALF_CURVE_ORDER) > 0) {
        // The order of the curve is the number of valid points that
        // exist on that curve. If S is in the upper
        // half of the number of valid points, then bring it back to
        // the lower half. Otherwise, imagine that
        //    N = 10

        // which is canonical.

        return this;
      }
    }
