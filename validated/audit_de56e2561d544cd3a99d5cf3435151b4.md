Audit Report

## Title
Permanent Fund Lock in Child/Parent Bounty Claim via Unchecked Transfer Result - (File: `substrate/frame/child-bounties/src/lib.rs`)

## Summary
`claim_child_bounty` in `substrate/frame/child-bounties/src/lib.rs` and `claim_bounty` in `substrate/frame/bounties/src/lib.rs` transfer bounty funds to a beneficiary/curator using `T::Currency::transfer(..., AllowDeath)` but only assert success via `debug_assert!`, which is compiled out in production (release) builds. The bounty storage entry is deleted unconditionally right after, regardless of whether the transfer actually succeeded, so a payout below the `ExistentialDeposit` to a non-existent beneficiary account silently fails while the pallet advances state as if settlement succeeded.

## Finding Description
In `claim_child_bounty`, the beneficiary payout is executed with `T::Currency::transfer(&child_bounty_account, beneficiary, payout, AllowDeath)` and guarded only by `debug_assert!(payout_transfer_result.is_ok())` [1](#0-0) . Immediately afterward, regardless of the transfer's outcome, the extrinsic decrements `ParentChildBounties`, removes `ChildBountyDescriptionsV1`, and sets `*maybe_child_bounty = None`, permanently erasing the bounty record [2](#0-1) .

The parent `pallet-bounties::claim_bounty` has the identical pattern: `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` guarded by `debug_assert!(res.is_ok())`, followed unconditionally by `*maybe_bounty = None` and `BountyDescriptions::<T, I>::remove(bounty_id)` [3](#0-2) .

The beneficiary account is supplied freely by the curator at award time via `award_bounty`, with no existence or minimum-payout check performed against it [4](#0-3) . Since `T::Currency::transfer` (legacy `Currency` trait, not `Fungible`) with `AllowDeath` on a non-existent destination account requires the transferred amount to be at least `ExistentialDeposit` or it returns an error and moves no funds, a curator-controlled `value`/`fee` split that yields a nonzero `payout` below ED for a fresh beneficiary account causes the transfer to fail while `debug_assert!` performs no check in a release build. Execution continues, the bounty record is deleted, and the funds sitting in the keyless `child_bounty_account`/`bounty_account` become permanently unreachable, since no other extrinsic references that removed bounty index.

## Impact Explanation
This matches the explicitly in-scope impact "permanent user-fund or bridge-state lock" from the Polkadot SDK Impact Gate: payout state (bounty storage removal) advances even though the underlying settlement transfer did not succeed, violating the required invariant that "payout state must only advance after ... settlement succeed[s] atomically." Funds remain stranded in a derived sub-account with no extrinsic capable of reclaiming them once the bounty record is gone.

## Likelihood Explanation
The curator role is assigned via `propose_curator`/`accept_curator`, which requires only that the assigned account accept the role and post a curator deposit via `accept_curator` [5](#0-4) ; once active, the curator freely chooses the `beneficiary` account and the `fee`/`value` split at `award_bounty` time with no ED validation, making it straightforward to engineer a sub-ED payout to a fresh account. `debug_assert!` provides no protection in standard (non-debug-assertions) production runtime builds, so this reachable via the standard bounty/curator lifecycle without needing sudo or governance intervention as the direct trigger.

## Recommendation
- Replace `debug_assert!(...is_ok())` with `?`/`ensure!`-based error propagation so `claim_bounty`/`claim_child_bounty` fail atomically (and can be retried) if the transfer does not succeed, instead of silently deleting bounty state.
- Validate at `award_bounty`/`award_child_bounty` time that the computed payout (and curator fee) will satisfy `ExistentialDeposit` for the chosen beneficiary, or use ED-safe transfer semantics (e.g., `Preservation`-aware `Fungible::transfer`, or top-up/`mint_creating`-style handling for sub-ED amounts).
- Ensure any failure path leaves the bounty retryable/reclaimable rather than unconditionally removing the record.

## Proof of Concept
1. Governance/`RejectOrigin` proposes a curator for a bounty; curator calls `accept_curator`, then `award_bounty`/`award_child_bounty` with `beneficiary` = a brand-new zero-balance account and a `value`/`fee` split such that `payout = balance.saturating_sub(fee)` is nonzero but below `ExistentialDeposit`.
2. After `unlock_at`, any signed account calls `claim_bounty`/`claim_child_bounty`.
3. `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` returns `Err` because `beneficiary` doesn't exist and `payout < ED`; in a release build, `debug_assert!` performs no check [6](#0-5) .
4. Execution proceeds: `*maybe_bounty = None` / `*maybe_child_bounty = None`, `BountyDescriptions`/`ChildBountyDescriptionsV1` removed.
5. The residual `payout` balance in `bounty_account_id`/`child_bounty_account_id` is now permanently stranded, with no extrinsic left referencing the removed bounty index.

		pub fn accept_curator(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
		) -> DispatchResult {
			let signer = ensure_signed(origin)?;

			Bounties::<T, I>::try_mutate_exists(bounty_id, |maybe_bounty| -> DispatchResult {
				let bounty = maybe_bounty.as_mut().ok_or(Error::<T, I>::InvalidIndex)?;

				match bounty.status {
					BountyStatus::CuratorProposed { ref curator } => {
						ensure!(signer == *curator, Error::<T, I>::RequireCurator);

						let deposit = Self::calculate_curator_deposit(&bounty.fee);
						T::Currency::reserve(curator, deposit)?;
						bounty.curator_deposit = deposit;

						let update_due = Self::treasury_block_number()
							.saturating_add(T::BountyUpdatePeriod::get());
						bounty.status =
							BountyStatus::Active { curator: curator.clone(), update_due };

						Self::deposit_event(Event::<T, I>::CuratorAccepted {
							bounty_id,
							curator: signer,
						});
						Ok(())
					},
					_ => Err(Error::<T, I>::UnexpectedStatus.into()),
				}
			})?;
			Ok(())
		}

		pub fn award_bounty(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
			beneficiary: AccountIdLookupOf<T>,
		) -> DispatchResult {
			let signer = ensure_signed(origin)?;
			let beneficiary = T::Lookup::lookup(beneficiary)?;

			Bounties::<T, I>::try_mutate_exists(bounty_id, |maybe_bounty| -> DispatchResult {
				let bounty = maybe_bounty.as_mut().ok_or(Error::<T, I>::InvalidIndex)?;

				// Ensure no active child bounties before processing the call.
				ensure!(
					T::ChildBountyManager::child_bounties_count(bounty_id) == 0,
					Error::<T, I>::HasActiveChildBounty
				);

				match &bounty.status {
					BountyStatus::Active { curator, .. } => {
						ensure!(signer == *curator, Error::<T, I>::RequireCurator);
					},
					_ => return Err(Error::<T, I>::UnexpectedStatus.into()),
				}
				bounty.status = BountyStatus::PendingPayout {
					curator: signer,
					beneficiary: beneficiary.clone(),
					unlock_at: Self::treasury_block_number() + T::BountyDepositPayoutDelay::get(),
				};

				Ok(())
			})?;

			Self::deposit_event(Event::<T, I>::BountyAwarded { index: bounty_id, beneficiary });
			Ok(())
		}
