### Title
Deposit attached to `DeterministicStateInit` action is silently lost (not credited, not refunded) when the referenced global contract does not exist - (File: `runtime/runtime/src/deterministic_account_id.rs`)

### Summary
When a `DeterministicStateInit` action (created e.g. via `promise_batch_action_state_init_by_account_id`) references a global contract identifier that does not exist, `action_deterministic_state_init` returns early after `use_global_contract` sets `GlobalContractDoesNotExist`, skipping all of the deposit-crediting/refund logic below it. The `action.deposit` balance that was already deducted from the sender and attached to the outgoing receipt is neither added to the (newly created, zero-balance) receiver account nor refunded via a new receipt, so it is permanently lost.

### Finding Description
`DeterministicStateInit` is explicitly exempted from the normal "account must exist" validation that other actions rely on: `check_account_existence` treats both existing and non-existing receivers as valid for this action [1](#0-0) . This means the usual protective path — where a receipt targeting a nonexistent account is failed wholesale and its balance is fully refunded — is bypassed by design for this action type, and instead an empty account is unconditionally created: [2](#0-1) 

`deploy_deterministic_account` first calls `use_global_contract` to bind the contract code; if the identifier does not exist, `GlobalContractDoesNotExist` is set on `result.result` and the function returns immediately: [3](#0-2) [4](#0-3) 

Back in `action_deterministic_state_init`, the caller checks `result.result.is_err()` and returns `Ok(())` right away, **before** reaching the deposit-handling code that would either credit the deposit to the account or push a `Receipt::new_balance_refund`: [5](#0-4) 

The attacker's flow: attach a non-zero `amount` when calling `promise_batch_action_state_init_by_account_id` (which deducts the balance from the caller immediately via `self.result_state.deduct_balance(amount)?`) [6](#0-5) , targeting a `GlobalContractIdentifier::AccountId` that has never deployed a global contract. The receipt executes, `use_global_contract` fails with `GlobalContractDoesNotExist`, and the action-level early return means the attached deposit is dropped entirely — never added to the newly created (zero-balance) account, never refunded to the sender.

The existing test `test_deterministic_state_init_missing_global_contract` only asserts that the transaction fails with `GlobalContractDoesNotExist`; it does not assert the deposit is refunded [7](#0-6) , so the missing-refund behavior is not currently covered/caught by tests.

### Impact Explanation
This causes permanent loss/freezing of the funds an ordinary user attaches to a `DeterministicStateInit` action whenever they (or a contract acting on their behalf) reference a global contract identifier that turns out not to exist. This falls under the "permanent freezing/loss of user funds" bounty category. Because the account-existence bypass for this action is a deliberate design choice (to support lazy initialization on possibly pre-existing accounts), any typo, race condition (global contract not yet propagated to the target shard), or malicious targeting of a bogus identifier by a relaying contract/dApp will strand the attached deposit with no recovery path.

### Likelihood Explanation
Precondition is only a funded account able to submit a transaction or a signed delegate action containing a `DeterministicStateInitAction` (directly, or indirectly via `promise_batch_action_state_init_by_account_id` from an already-deployed wasm contract) with a nonzero deposit and a `GlobalContractIdentifier::AccountId` pointing at an account that has not deployed a global contract (trivial to construct — no special access needed). The cost to trigger is just gas + the deposit amount, and it is fully repeatable/deterministic; it can also occur non-maliciously (e.g., because global-contract propagation to a shard hasn't completed yet, as noted in the doc comment "It may take a while for it to propagate to all shards").

### Recommendation
In `action_deterministic_state_init` (`runtime/runtime/src/deterministic_account_id.rs`), when `deploy_deterministic_account` fails with `result.result.is_err()` (e.g. `GlobalContractDoesNotExist`), issue a `Receipt::new_balance_refund` for the full `action.deposit` back to `receipt.balance_refund_receiver()` before returning, mirroring the refund logic already present later in the function for the success path.

### Proof of Concept
Integration test (test-loop, modeled on `test_deterministic_state_init_missing_global_contract`):
1. Setup a funded user account, do NOT deploy any global contract.
2. Record the user's balance before the transaction.
3. Submit a `DeterministicStateInitAction` (or via `promise_batch_action_state_init_by_account_id`) referencing a nonexistent `GlobalContractIdentifier::AccountId`, with `deposit = Balance::from_near(1)`.
4. Assert the outcome fails with `ActionErrorKind::GlobalContractDoesNotExist`.
5. Assert `user_balance_after == user_balance_before - gas_cost` (i.e., the 1 NEAR deposit was refunded), and additionally assert the newly created deterministic account's balance is `Balance::ZERO` (not holding the stranded deposit either).
6. Current code is expected to fail this assertion because the deposit is neither refunded to the user nor credited to the account.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
