## Title
Missing Token Name/Symbol Uniqueness Validation in `AssetIssueActuator` Allows Duplicate TRC10 Token Names/Abbreviations — (File: `actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java`)

### Summary
The `AssetIssueActuator.validate()` method only rejects a duplicate token `name` when the chain parameter `AllowSameTokenName` is disabled (`getAllowSameTokenName() == 0`). Once `AllowSameTokenName` is enabled — which is the long-standing, irreversible production state of the TRON mainnet — any account can call `createAssetIssue` (an `AssetIssueContract` broadcast by any unprivileged asset issuer) and freely reuse the `name` and `abbr` (symbol) of any existing, legitimate token. This is the exact bug class described in the external report for `LiquidityFreeLaunchFactory`: unvalidated uniqueness of token name/symbol enabling confusion and scam impersonation of existing tokens.

### Finding Description
In `AssetIssueActuator.validate()`, the only uniqueness check on the asset name is: [1](#0-0) 

This check is explicitly bypassed when `dynamicStore.getAllowSameTokenName() != 0`. There is no equivalent check anywhere in `validate()` against the `abbr` (symbol) field either — the only validation applied to `abbr` is a length/format check via `TransactionUtil.validAssetName`: [2](#0-1) 

The remaining per-account restriction ("An account can only issue one asset") only limits one issuance per address, not one name per network: [3](#0-2) 

The `AllowSameTokenName` dynamic property was introduced as a one-way, network-wide upgrade switch (once turned on via chain governance it stays on), so on any live network that has passed this proposal, the name-uniqueness guard at lines 210-214 is permanently dead code, and the platform has no defense against an attacker issuing a token with an identical name/abbr to a popular, legitimate TRC10 asset.

This directly affects the query paths that resolve tokens by name: `Wallet.getAssetIssueByName` scans all `AssetIssueV2Store` entries filtering by name and throws `NonUniqueObjectException` (silently converted to `null` by callers) whenever more than one asset shares that name: [4](#0-3) [5](#0-4) 

An attacker can also flood `GetAssetIssueListByName` results with impostor tokens carrying an identical name/symbol to a legitimate one, since that endpoint returns every match: [6](#0-5) 

### Impact Explanation
Any unprivileged asset issuer can create a duplicate-name/duplicate-symbol TRC10 token that impersonates an existing legitimate token. Wallets, exchanges, or dApps that resolve tokens by `name`/`abbr` via `GetAssetIssueByName`/`GetAssetIssueListByName` can be misled into displaying, trading, or crediting the wrong (attacker-controlled) asset, enabling scams and user fund loss through impersonation — matching the "concrete unauthorized account operation" bar via social-engineering-driven token substitution. This is a Medium-severity issue consistent with the client's own acknowledged severity rating in the original report.

### Likelihood Explanation
High likelihood of exploitation: creating an `AssetIssueContract` requires only a signed transaction and payment of the standard `AssetIssueFee` — no special privilege is needed, and `AllowSameTokenName` being enabled removes the only uniqueness guard present in the codebase.

### Recommendation
Even with `AllowSameTokenName` enabled (multiple tokens allowed to reduce ID collisions), the platform should still enforce that `name`+`abbr` combinations (or at minimum `abbr`, the primary user-facing ticker) cannot exactly duplicate an already-existing active asset's identifiers, or clearly surface asset `id` prominently in all name-based lookup APIs and warn/reject when ambiguous matches occur, rather than silently returning `null` on `NonUniqueObjectException`.

### Proof of Concept
1. Ensure `AllowSameTokenName` dynamic property is `1` (true on current mainnet).
2. Account A broadcasts `AssetIssueContract` with `name="POPULARCOIN"`, `abbr="POP"`.
3. Account B (attacker) broadcasts a second `AssetIssueContract` with identical `name="POPULARCOIN"`, `abbr="POP"` — `AssetIssueActuator.validate()` at lines 210-214 does not fire because `getAllowSameTokenName() != 0`, and no check exists on `abbr` uniqueness at all.
4. Both tokens now coexist; queries to `GetAssetIssueByName`/`GetAssetIssueListByName` for "POPULARCOIN" return either an ambiguous `null` (via `NonUniqueObjectException`) or a list containing the attacker's token, which downstream consumers may present to end users as the legitimate asset.
