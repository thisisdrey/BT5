### Title
Asset name used as sole uniqueness key for token issuance allows front-running/squatting to permanently block legitimate issuers - ([File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java])

### Summary
`AssetIssueActuator.validate()` rejects an `AssetIssueContract` with the message `"Token exists"` whenever an asset with the same `name` already exists in `assetIssueStore` (the V1 token-name keyspace), independent of who submitted the winning transaction. The uniqueness key is derived purely from user-supplied content (the asset name) with no binding to `msg.sender`/owner address or any nonce — structurally the same defect class as the SEDA `requestId` finding (`deriveRequestId()` hashing only content fields, with the fix being to add `msg.sender`/nonce).

### Finding Description
When `AllowSameTokenName == 0` (the legacy V1 path, still present and reachable in this codebase), `AssetIssueActuator.validate()` performs: [1](#0-0) 
which looks up the asset purely by `assetIssueContract.getName()` in `assetIssueStore` — a store keyed only by the name string, with no owner/sender component and no nonce. On success, `AssetIssueActuator.execute()` persists the capsule under `assetIssueCapsule.createDbKey()` (the name): [2](#0-1) 

Any account can broadcast an `AssetIssueContract` naming any arbitrary token name it chooses, as the only preconditions are: an existing account (`accountStore.has(ownerAddress)`), the account not having already issued an asset, and sufficient balance to cover `calcFee()` (`AssetIssueFee`) — no special privilege is required: [3](#0-2) 

Because the collision check is name-only, any unprivileged account watching the mempool can front-run a legitimate issuer's `AssetIssueContract` transaction with the same `name` (or preemptively squat well-known/expected names), and once claimed, the name can never be reused by anyone else (the check is a hard revert, not upgradable per-sender). This mirrors the SEDA bug class exactly: a content-derived "ID" (there: `requestId`; here: token `name`) is used as the sole existence/duplication key with no `msg.sender`/nonce component, enabling attacker-controlled blocking of a legitimate party's on-chain operation.

### Impact Explanation
A malicious, unprivileged account can permanently deny a target business/user the ability to ever issue a TRC10 token under a specific name in the V1 (`AllowSameTokenName == 0`) namespace, since the check has no relation to the intended issuer's address. This is a griefing/denial-of-service against asset issuance — a targeted victim's token-issuance transaction can be blocked indefinitely by any address willing to pay the `AssetIssueFee`, and the name is permanently taken (since there is no unfreezing/renaming of an issued V1 asset name). This can cause direct financial/business harm (inability to launch an intended asset under its name) and is exploitable by any address able to broadcast a signed transaction — matching the "unauthorized account operation on victim's expected action" impact bar.

### Likelihood Explanation
The attack requires only: (1) an existing TRON account, (2) balance for `getAssetIssueFee()`, and (3) knowledge/observation of the victim's intended asset name (mempool front-running, or squatting popular names preemptively). No special role, timing race outside normal front-running, or contract deployment is needed — this is directly reachable via a standard `AssetIssueContract` transaction. This is somewhat mitigated because `AllowSameTokenName` is a chain-parameter flag; if it is permanently set to `1` on current mainnet, the vulnerable branch (`dynamicStore.getAllowSameTokenName() == 0`) is not exercised in production, which is a caveat I could not fully verify from static code — the flag's live value is set at runtime via governance proposals and was not determinable from the codebase alone.

### Recommendation
For the legacy V1 path, either (a) deprecate/permanently disable the `AllowSameTokenName == 0` branch if it's no longer intended to be reachable, or (b) if still supported, bind the uniqueness check to `(name, ownerAddress)` or otherwise require reservation/commit-reveal so a name cannot be squatted by an unrelated account, analogous to adding `msg.sender`/nonce to the SEDA `requestId` derivation.

### Proof of Concept
1. Attacker observes a pending `AssetIssueContract` transaction (or knows in advance) from a legitimate business intending to issue token named `"ACME"`.
2. Attacker, with any funded account satisfying `AssetIssueFee`, submits their own `AssetIssueContract` with `name = "ACME"` and a higher fee/priority so it lands first.
3. `AssetIssueActuator.validate()` succeeds for the attacker (no prior "ACME" record) and `execute()` stores it keyed by `"ACME"` in `assetIssueStore`.
4. The legitimate business's transaction with the same name now fails validation at: [1](#0-0) 
with `"Token exists"`, permanently preventing them from issuing under that name — confirmed by existing test `IssueSameTokenNameAssert` demonstrating the same-name rejection behavior: [4](#0-3)
