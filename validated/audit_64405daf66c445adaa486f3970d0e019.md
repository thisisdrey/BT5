Audit Report

## Title
Partial BestEffort claim reported as full success permanently strands leftover reserved swap funds - (File: substrate/frame/atomic-swap/src/lib.rs)

## Summary
`claim_swap`'s `BalanceSwapAction::claim` treats any `Ok` result from `repatriate_reserved` as full success even though `repatriate_reserved` performs a `Precision::BestEffort` transfer capped by `reducible_total_balance_on_hold`. If a freeze/lock on the source's account reduces the transferable amount below the swap's committed `value`, `claim_swap` still deletes the `PendingSwaps` entry and emits `success: true`, leaving the shortfall permanently stuck in `reserved` with no remaining dispatchable path to release it.

## Finding Description
`BalanceSwapAction::claim` calls `C::repatriate_reserved(source, target, self.value, BalanceStatus::Free).is_ok()` [1](#0-0) . `repatriate_reserved` invokes `do_transfer_reserved` with `Precision::BestEffort` and `Fortitude::Polite`, then returns `Ok(value.saturating_sub(actual))` regardless of whether `actual < value` [2](#0-1) . `do_transfer_reserved` caps `actual` at `max = reducible_total_balance_on_hold(slashed, fortitude)` via `value.min(max)` under `BestEffort` [3](#0-2) , and `reducible_total_balance_on_hold` subtracts `frozen.saturating_sub(free)` from `reserved` when not forced [4](#0-3) .

Because `claim()` only checks `.is_ok()` and discards the shortfall, `claim_swap` unconditionally deletes the `PendingSwaps` entry and emits `SwapClaimed { success: true }` even on a partial transfer [5](#0-4) . Once the entry is removed, `cancel_swap` — the only other path that calls `action.cancel()` (i.e., `unreserve`) — fails with `Error::NotExist` since it depends on `PendingSwaps::get` succeeding [6](#0-5) . No other pallet-balances extrinsic can unreserve this generic reserved balance created via `action.reserve()` in `create_swap` [7](#0-6) .

Freeze enforcement itself is correctly respected (locked/frozen value cannot be withdrawn beyond what `reducible_total_balance_on_hold` allows), so this is not a bypass/theft path — it is a mishandling of the `BestEffort` partial-success signal that leads to irreversible loss of dispatchable control over the shortfall.

## Impact Explanation
A portion of the source account's balance becomes permanently locked in the `reserved` state with no on-chain path to free it, matching the "permanent user-fund lock" impact category in the Polkadot SDK Impact Gate.

## Likelihood Explanation
The condition is reachable purely through public extrinsics: the source account can apply an ordinary lock/freeze (e.g., vesting, staking bonding, or any other freeze) to itself between `create_swap` and `claim_swap`, causing `frozen.saturating_sub(free)` to exceed zero and reduce `reducible_total_balance_on_hold` below the swap's committed `value`. No privileged access, governance action, or malicious relayer/validator behavior is required — an ordinary account acting through standard public calls triggers the shortfall, and the target merely needs to call `claim_swap` normally for the bug to manifest.

## Recommendation
In `BalanceSwapAction::claim`, use `Precision::Exact` (or explicitly check that the returned shortfall from `repatriate_reserved` is zero) before reporting success. If the full `value` cannot be transferred, avoid removing the `PendingSwaps` entry (or provide an explicit recovery/unreserve path) so the source can still recover or the target can retry once conditions change.

## Proof of Concept
1. Source calls `create_swap(target, hashed_proof, action=Balance(value=100), duration)`, reserving 100 from source's free balance via `action.reserve(&source)`.
2. Source applies a public lock/freeze on itself (e.g., via vesting or staking bonding extrinsics) such that `reducible_total_balance_on_hold(source, Polite)` drops below 100 (e.g., to 70) due to `frozen.saturating_sub(free) > 0`.
3. Target calls `claim_swap(proof, action)`. `repatriate_reserved` computes `actual = min(100, 70) = 70`, moves only 70, and returns `Ok(30)` (shortfall). `claim()` returns `true` since `.is_ok()`.
4. `claim_swap` deletes the `PendingSwaps` entry and emits `SwapClaimed { success: true }`, even though only 70 of the promised 100 was transferred.
5. Source attempts `cancel_swap(target, hashed_proof)` — fails with `Error::NotExist` because the entry is gone. The remaining 30 stays in `reserved` indefinitely with no dispatchable call available to release it.

				Error::<T>::DurationNotPassed,
			);

			PendingSwaps::<T>::remove(&target, hashed_proof);

			Self::deposit_event(Event::SwapCancelled { account: target, proof: hashed_proof });

			Ok(())
		}

			};

	fn reducible_total_balance_on_hold(who: &T::AccountId, force: Fortitude) -> Self::Balance {
		// The total balance must never drop below the freeze requirements if we're not forcing:
		let a = Self::account(who);
		let unavailable = if force == Force {
			Self::Balance::zero()
		} else {
			// The freeze lock applies to the total balance, so we can discount the free balance
			// from the amount which the total reserved balance must provide to satisfy it.
			a.frozen.saturating_sub(a.free)
		};
		a.reserved.saturating_sub(unavailable)
	}
