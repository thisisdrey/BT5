### Title
Unbounded `u32` page index passed to `AtlasDB::get_attachments_available_at_page_index` allows integer-overflow panic / bounded compute DoS - (File: `stackslib/src/net/api/getattachmentsinv.rs`)

### Summary
`RPCGetAttachmentsInvRequestHandler::try_handle_request` only caps the *number* of page indexes (`MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` = 8) but never caps the numeric *value* of each `u32` page index before passing it straight into `AtlasDB::get_attachments_available_at_page_index`. Since a page index is turned into a byte-range/offset (`page_index * ATTACHMENTS_INV_PAGE_SIZE`) inside the Atlas DB layer, an attacker-supplied value near `u32::MAX` (e.g. `4294967295`) causes that multiplication to overflow.

### Finding Description
In `try_parse_request` (getattachmentsinv.rs:91-101) each comma-separated token from the `pages_indexes` query parameter is parsed with `entry.parse::<u32>()` and inserted into a `HashSet<u32>` with no upper-bound check on the value itself — only the parse succeeding (any value 0..=4294967295 is accepted) is required [1](#0-0) . In `try_handle_request`, the only validation performed is on `page_indexes.len()` against `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` (8) [2](#0-1) ; there is no check that any individual `page_index` value is small. Each raw `u32` is then passed unchecked into `network.get_atlasdb().get_attachments_available_at_page_index(*page_index, &index_block_hash)` [3](#0-2) . Inside `AtlasDB` (`stackslib/src/net/atlas/db.rs`), the page index is converted into an attachment-index range by multiplying by the fixed page size (`ATTACHMENTS_INV_PAGE_SIZE`), so a `page_index` close to `u32::MAX` causes this multiplication to exceed `u32::MAX`. In any build compiled with overflow checks enabled (Rust's default `dev`/`test` profile, and any custom `release` profile that opts into `overflow-checks = true`), this triggers an unconditional panic ("attempt to multiply with overflow"), crashing the thread handling the RPC request. In a standard `release` profile without `overflow-checks`, the multiplication instead silently wraps, producing an incorrect/undefined page range rather than a crash — so the concrete impact depends on the node's build configuration.

### Impact Explanation
- Where overflow checks are active (debug builds, CI, or a release profile compiled with `overflow-checks = true`): a single unauthenticated GET request to `/v2/attachments/inv` with a crafted `pages_indexes` value can panic the request-handling thread — a bounded, single-request read-endpoint DoS, repeatable at will and remotely reachable without any secret or role, matching the "High: bounded compute DoS on a read endpoint" category.
- Where overflow checks are disabled (the common `cargo build --release` default without extra flags): the multiplication wraps silently, and the endpoint returns incorrect/empty page data rather than crashing — this degrades to incorrect behavior, not a DoS.

Because the actual severity is contingent on the node's build/profile configuration (which I could not confirm from the indexed files — the `Cargo.toml` `[profile.release]` overflow-checks setting was not retrieved in this session), I cannot assert with full confidence that production mainnet/testnet nodes are built with overflow checks enabled.

### Likelihood Explanation
The endpoint `/v2/attachments/inv` requires no RPC secret or peer authentication and is reachable by any remote party who can connect to the node's RPC port [4](#0-3) . Attacker cost is a single crafted HTTP GET request; it is trivially repeatable. The precondition for the crash path (as opposed to silent-wrap) is that the target node binary was compiled with `overflow-checks` enabled, which is not the default for `--release` builds unless explicitly configured in `Cargo.toml`.

### Recommendation
Explicitly bound each parsed `page_index` (e.g., reject values above a small sane maximum such as `u16::MAX` or compute the byte range with `checked_mul`/`saturating_mul` and return an `HttpBadRequest` on overflow) both in `try_parse_request` (getattachmentsinv.rs) and defensively inside `AtlasDB::get_attachments_available_at_page_index` (atlas/db.rs), rather than relying on build-profile overflow-check behavior.

### Proof of Concept
Add a test in `stackslib/src/net/api/tests/getattachmentsinv.rs` that constructs a `RPCGetAttachmentsInvRequestHandler`, calls `try_parse_request` with a query string `index_block_hash=<valid hash>&pages_indexes=4294967295`, then invokes `try_handle_request` against a `StacksNodeState` with a populated `AtlasDB`. Assert that the call either panics (`std::panic::catch_unwind` capturing an overflow panic message) when compiled with `overflow-checks=true` (e.g. `cargo test`, which uses the `dev` profile by default), versus a bounded-time success/`HttpNotFound` response for `pages_indexes=0` — comparing wall-clock/behavioral disparity for a single page index near `u32::MAX` versus a small value.
