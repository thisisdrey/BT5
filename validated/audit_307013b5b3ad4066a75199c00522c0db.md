### Title
Unchecked relay packet length causes slice-bounds panic (DoS) in `VerifyRelay` - (`connection_state.go`)

### Summary
`ConnectionState.VerifyRelay` slices the incoming relay `packet` using `len(packet)-cs.dKey.Overhead()` without checking that `len(packet) >= cs.dKey.Overhead()`. Since `Overhead()` is a fixed AEAD tag size (16 bytes for both the AES-GCM and ChaCha20-Poly1305 backends), an attacker-controlled relay frame shorter than that size drives a negative slice bound, causing a runtime panic rather than a graceful authentication failure.

### Finding Description
`VerifyRelay` is documented to trust its caller for length validation: "packet must be length-checked by the caller" [1](#0-0) . Internally it does:
```go
signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
signatureValue := packet[len(packet)-cs.dKey.Overhead():]
``` [2](#0-1) 

`Overhead()` on both AEAD backends returns the AEAD's fixed tag size (16 bytes), independent of `packet` content: [3](#0-2) [4](#0-3) 

If `len(packet) < cs.dKey.Overhead()`, the expression `len(packet)-cs.dKey.Overhead()` becomes negative, and `packet[:negative]` / `packet[negative:]` produces a Go runtime panic ("slice bounds out of range") before the AEAD `Open`/authentication call in `DecryptDanger` is ever reached. This happens prior to any cryptographic authentication, so the packet's authenticity is irrelevant — the crash occurs purely from length manipulation.

The function's own doc comment concedes there is no internal guard and defers the responsibility entirely to the caller in `outside.go`. Whether that caller path enforces a length check specifically against `cs.dKey.Overhead()` (as opposed to a more generic minimum like `header.Len`) could not be conclusively confirmed from the available index for `outside.go`, but the exported function itself contains no defensive bound check and is not safe to call with attacker-controlled lengths under `Overhead()`. Given nebula's threat model — arbitrary/spoofed unauthenticated UDP frames reaching relay processing before any AEAD authentication succeeds — any caller path that does not precisely validate `len(packet) >= cs.dKey.Overhead()` results in a remotely triggerable panic.

### Impact Explanation
A remote, unauthenticated attacker who can get a UDP frame routed onto the relay-verification path with a payload shorter than the AEAD tag size (16 bytes) can trigger a slice-bounds panic in the receiving Nebula node's data-plane goroutine, crashing or restarting that connection processing (DoS / remote crash), before any cryptographic authentication check occurs.

### Likelihood Explanation
The precondition is minimal: the attacker only needs to reach the relay verification call with a byte slice shorter than 16 bytes, which requires no valid certificate, no handshake completion, and no cryptographic material — only knowledge that a packet will be routed to `VerifyRelay`. The likelihood therefore depends entirely on whether `outside.go`'s dispatch to `VerifyRelay` validates length strictly enough (`>= Overhead()`), which is the exact check the function's own documentation says it does *not* perform internally.

### Recommendation
Add an explicit length guard at the top of `VerifyRelay` (defense in depth, regardless of caller behavior):
```go
if len(packet) < cs.dKey.Overhead() {
    return ErrInvalidRelayPacket // or similar
}
```
This ensures the function is safe to call with arbitrary attacker-controlled lengths and removes the caller-trust assumption documented in the comment.

### Proof of Concept
Add a unit test in `connection_state_test.go`:
```go
func TestVerifyRelay_ShortPacket(t *testing.T) {
    cs := ... // construct ConnectionState with a real dKey (Overhead() == 16)
    for n := 0; n < cs.dKey.Overhead(); n++ {
        packet := make([]byte, n)
        func() {
            defer func() {
                if r := recover(); r != nil {
                    t.Fatalf("VerifyRelay panicked on packet len %d: %v", n, r)
                }
            }()
            err := cs.VerifyRelay(nil, 1, packet, make([]byte, 12))
            if err == nil {
                t.Fatalf("expected error for short packet len %d, got nil", n)
            }
        }()
    }
}
```
Expected (current, buggy) behavior: panic ("slice bounds out of range") for `n < 16`. Expected (fixed) behavior: a graceful non-nil error for every `n < Overhead()`, no panic.
