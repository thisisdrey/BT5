### Title
Malformed calldata to `ValidateMultiSign` precompile causes uncaught exception via unchecked array-index/length parsing - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE describes FAAD2's `mp4ff_read_stsd` trusting an attacker-controlled length/atom field without bounds checking, causing an invalid memory read and crash. The analogous pattern in java-tron is the `extractBytesArray`/`extractSigArray`/`extractBytes32Array` helper methods used by the `ValidateMultiSign` precompiled contract's `execute()` path, which derive array lengths and offsets directly from attacker-supplied `DataWord[]` calldata words without validating them against the actual buffer size before indexing.

### Finding Description
`extractBytesArray` and `extractBytes32Array` read a `len` value straight from calldata (`words[offset].intValueSafe()`), allocate `new byte[len][]`, then loop `i < len` reading `words[offset + i + 1]` and computing further offsets/lengths (`bytesOffset`, `bytesLen`) also taken from calldata: [1](#0-0) 

Unlike the sibling helper `extractSigArray`, which at least guards `offset > words.length - 1` before reading, `extractBytes32Array` performs no such check at all, and even the guarded variants do not validate that `offset + i + 1` (or the derived `bytesOffset`) stays within the bounds of the `words` array as `len` grows — a crafted large or negative `len`/offset value can drive the index past the end of `words`, producing an `ArrayIndexOutOfBoundsException`, or a crafted `bytesLen` can drive `extractBytes` past the end of `data`. A companion test file explicitly documents that for the pre-TIP-854-activation code path, this class of malformed-calldata input "raises inside the decoder" because "this precompile has no outer catch": [2](#0-1) 

This mirrors the FAAD2 bug class precisely: a length/offset field taken from untrusted input is used to index into a buffer without verifying it stays within that buffer's true bounds, and the resulting exception is allowed to propagate uncaught rather than being handled gracefully by the containing precompile's `execute()`.

### Impact Explanation
An uncaught `RuntimeException`/`ArrayIndexOutOfBoundsException` thrown out of a precompiled contract's `execute()` during TVM execution is not the normal, expected exceptional-halt path that TVM opcodes are designed to catch (e.g. `OutOfGasException`, `ContractValidateException`). Depending on how the caller (`Program`/`OperationActions` contract-call dispatch) handles a raw uncaught Java exception versus the TVM's expected exception types, this can propagate up through block/transaction processing in `Manager`, causing a node to fail to process an otherwise valid block containing this transaction — a potential denial-of-service / node-crash condition reachable by any account that can submit a `TriggerSmartContract` transaction calling this precompile address. This matches the CVE's DoS impact class (crash on malformed/crafted input), scoring similarly at Medium under the "no memory corruption but reachable, unauthenticated crash" model.

### Likelihood Explanation
The precompile is reachable by any unprivileged account via a normal `TriggerSmartContract`/constant-call to the fixed `ValidateMultiSign` precompile address; no special permission, staking or governance action is required — an attacker only needs to craft calldata words with out-of-range length/offset fields. The comment and dedicated test (`testTip854PreActivationNoOp`) in the test suite confirm the maintainers are aware that pre-activation calldata parsing here has no outer exception guard and preserves the "existing" (unsafe) behavior intentionally, indicating the crash path is real and currently accepted rather than defended against.

### Recommendation
Add explicit bounds validation in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` (and any downstream `extractBytes` calls) so that `len`, `offset + i + 1`, and any derived `bytesOffset`/`bytesLen` are checked against `words.length` and `data.length` before use, returning a "false"/empty failure result (consistent with the rest of the precompile's fail-safe returns) instead of allowing an exception to escape uncaught. Ensure `execute()` in `ValidateMultiSign` wraps the entire parsing/verification logic in a `catch (Throwable)` block consistent with other precompiles (e.g. `ECRecover`, `VerifyMintProof`) so malformed input degrades to a rejected/invalid result rather than an uncaught crash.

### Proof of Concept
A transaction calling the `ValidateMultiSign` precompile (via `TriggerSmartContract`) with an ABI-encoded input where the dynamic array length word (consumed by `extractBytesArray`/`extractSigArray`) is set to a very large value (e.g., `Integer.MAX_VALUE` or a value that makes `offset + i + 1` exceed `words.length`) will cause `words[offset + i + 1]` to throw `ArrayIndexOutOfBoundsException` (or, for `extractBytes32Array`, simply omit the bounds guard entirely to trigger the same fault at even smaller offsets). This is directly analogous to the `testTip854PreActivationNoOp` test's use of a too-short/malformed input array to trigger the documented "no outer catch" uncaught-exception behavior: [3](#0-2)

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
