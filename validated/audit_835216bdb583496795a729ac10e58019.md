### Title
Missing attribute-count validation before indexing Zip64 extra field in singlejar - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`CDH::compressed_file_size()`, `CDH::uncompressed_file_size()`, and `CDH::local_header_offset()` fetch a `Zip64ExtraField` and read its 8-byte `attr64(index)` entries whenever the corresponding 32-bit field is `0xFFFFFFFF`, but never check that the attacker-supplied extra field actually contains enough attributes (`attr_count()`) to satisfy the index being requested.

### Finding Description
`Zip64ExtraField::attr64(int index)` blindly returns `le64toh(attr_[index])` with no bounds check [1](#0-0) . The field is located generically by `ExtraField::find`, which only validates that the field's declared `size()` (header + `payload_size()`) fits inside the enclosing `extra_fields` buffer — it does not validate that `payload_size()` is large enough to contain the specific attribute index that callers will later request [2](#0-1) .

Callers in `CDH` decide which `attr64` index to read purely from the *unrelated* 32-bit size fields (`uncompressed_file_size32()`, `compressed_file_size32()`), not from the zip64 field's own `attr_count()`:
- `compressed_file_size()` calls `z64->attr64(ziph::zfield_has_ext64(uncompressed_file_size32()))` [3](#0-2) .
- `uncompressed_file_size()` calls `z64->attr64(0)` unconditionally once zfield_has_ext64 is true [4](#0-3) .
- `local_header_offset()` computes `attr_no` by summing two independent flags and calls `z64->attr64(attr_no)`, so `attr_no` can be 0, 1, or 2 [5](#0-4) .

An attacker who publishes a crafted `.jar`/`.zip` (consumed via `http_jar`/`http_archive`, or checked into an untrusted branch that CI builds with `singlejar`) can construct a Central Directory Header where:
1. `uncompressed_file_size32` and/or `compressed_file_size32` are set to `0xFFFFFFFF` (triggering the zip64 path), while
2. the accompanying Zip64 extra field (tag `0x0001`) is present but has `payload_size` smaller than required (e.g. `payload_size = 0` or `8`, giving `attr_count() == 0` or `1`), so `attr_count()` never actually gets consulted or checked against the index used.

`ExtraField::find` will accept this field because its declared `size()` fits the `extra_fields` buffer — the mismatch between the *declared* size fields on `CDH`/`LH` and the *actual* payload size of the zip64 extra field is never cross-checked. This is the same class of bug as the hns3 VLAN issue: a value (index/id) taken from attacker-controlled input is used to index into a fixed-size structure without validating it against the structure's actual bounds.

### Impact Explanation
`attr64(index)` performs `attr_[index]`, an unchecked pointer-arithmetic read of 8 bytes past the (correctly bounds-checked) extra field but potentially past the mapped input file if the crafted field sits near the end of the memory-mapped jar (`MappedFile`, used by `InputJar`). This yields:
- An out-of-bounds heap read whose garbage value is then used as `compressed_file_size()`/`uncompressed_file_size()`/`local_header_offset()`. These derived sizes/offsets subsequently drive further pointer arithmetic and memory operations in the jar-merging pipeline (`InputJar`, `OutputJar`), so a corrupted size/offset can propagate into further OOB reads/writes or crashes during the Java build's singlejar step.
- This is a memory-safety violation (`C: H/I: H/A: H`-class impact), matching the severity class of the analog CVE, though it manifests as a native OOB read/computation rather than a kernel bitmap write.

### Likelihood Explanation
Likelihood is high once a project fetches/builds an attacker-influenced `.jar` through `singlejar` (a core, always-invoked component for any target depending on `java_library`/`java_binary` deploy jars). No credentials, MITM, or code execution are needed — only the ability to publish a byte stream that ends up as a build input (dependency archive, cached artifact, or file in a repo an untrusted CI builds). Existing checksum verification (`sha256`/`integrity` on `http_archive`/`http_jar`) does not help here because the *entire* file — including this malformed structure — can be legitimately checksum-pinned by the attacker publishing it; the vulnerability is in how `singlejar` parses the (correctly downloaded, correctly checksummed) bytes, not in fetch integrity.

I was not able to fully trace every downstream consumer of `compressed_file_size()`/`uncompressed_file_size()`/`local_header_offset()` in `output_jar.cc`/`input_jar.cc` within the available iterations (the file was only partially read before the tool budget ended), so I cannot cite the exact `memcpy`/allocation call sites that consume the corrupted size value. This should be verified before treating this as fully proven.

### Recommendation
In `Zip64ExtraField`, before indexing, validate `index < attr_count()` and return an explicit error (or `0xFFFFFFFF`/failure sentinel already used for `nullptr`) when the caller's requested index exceeds the field's declared `attr_count()`. Equivalently, harden the `CDH`/`LH` accessors (`compressed_file_size`, `uncompressed_file_size`, `local_header_offset`) to check `z64->attr_count()` against the number of `0xFFFFFFFF`-flagged fields that must be present, and fail closed (diagnostic + abort, consistent with existing `diag_errx`/`diag_warnx` handling elsewhere in this file) when the zip64 extra field is too small for the fields it's supposed to back.

### Proof of Concept
Not executed — the analog is based on static code review only (no filesystem/terminal access available in this mode). A reproducible PoC would need a `BuildIntegrationTestCase`/`zip_headers_test.cc`-style unit test that:
1. Constructs a `CDH` with `uncompressed_file_size32() == 0xFFFFFFFF`.
2. Appends a Zip64 extra field (tag `0x0001`) with `payload_size = 0` (or too small for the needed `attr64` index).
3. Calls `CDH::uncompressed_file_size()` / `local_header_offset()` and observes the OOB read (e.g., via ASan) instead of a validation error.

                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
