The CVE-2018-7167 concerns a Node.js-specific hang in `Buffer.fill()`/`Buffer.alloc()` when certain byte-length string encoding parameters caused an internal loop to spin. This is not a generic "buffer fill" keyword match — it's a specific interaction between Node's `normalizeEncoding`/`byteLength` parsing and its fill loop.

Searching the Go standard library fork in this repo for analogous fill/zero-fill code turned up only legitimate, well-tested implementations with no attacker-controlled hang potential:

- `bytes.Buffer` test helpers `fillString`/`fillBytes` are test-only code, not production paths [1](#0-0) 
- `math/big.Int.FillBytes` zero-fills a caller-provided buffer and panics (not hangs) if the value doesn't fit — a bounded, well-defined check [2](#0-1) 
- `runtime` memory-zeroing paths (`memclrNoHeapPointers`, `allocNeedsZero`, arena zeroing) are allocator-internal and not driven by untrusted external input in a way that could hang [3](#0-2) 
- `bufio.Reader.fill` and the compiler's `syntax/source.fill` bound their read retries with a fixed iteration count (`maxConsecutiveEmptyReads` / a hardcoded `10`) and return `io.ErrNoProgress` rather than spinning indefinitely [4](#0-3) [5](#0-4) 

None of these exhibit the Node.js primitive of an encoding-parameter-driven infinite/near-infinite loop in a fill/alloc routine reachable from unauthenticated/untrusted input. No credible analog exists in this codebase for CVE-2018-7167.
