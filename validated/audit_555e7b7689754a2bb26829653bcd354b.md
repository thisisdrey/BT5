Audit Report

## Title
Integer-division truncation in Snowbridge outbound-queue fee conversion lets senders underpay for guaranteed relayer rewards - (File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs)

## Summary
`Pallet::calculate_fee` converts an Ethereum-denominated (18-decimal) fee into native currency by calling `convert_from_ether_decimals`, which performs floor division `value.checked_div(denom)` [1](#0-0) . Because `do_process_message` independently commits `reward: pricing_params.rewards.remote` to the outbound message without re-deriving it from the same rounded value, the fee actually collected from the sender can be strictly less than (including exactly zero for) the reward unconditionally promised on the Ethereum side.

## Finding Description
`calculate_fee` computes the remote-fee-in-ether via `calculate_remote_fee`, downcasts to `u128`, applies `multiplier`/`exchange_rate` via `FixedU128`, and finally calls `convert_from_ether_decimals` to scale from 18 decimals down to the native currency's decimals [2](#0-1) . `convert_from_ether_decimals` computes `denom = 10^(18 - T::Decimals)` and does plain `checked_div` with no rounding-up or remainder handling [3](#0-2) . For DOT (`Decimals = 10`), `denom = 10^8`; any intermediate `value < 10^8` truncates to `0`, and any non-multiple loses its remainder.

Independently, `do_process_message` reads `pricing_params.rewards.remote` directly and writes it as the `reward` field of the `CommittedMessage` that gets merkle-committed and relayed to Ethereum [4](#0-3) . This value is not derived from, or reconciled with, the rounded fee actually charged to the sender in `calculate_fee`/`validate` [5](#0-4) .

No guard exists anywhere in `validate`, `deliver`, or `do_process_message` ensuring the calculated fee is non-zero or sufficient to cover the committed reward — the only `expect(...)` calls guard against a zero *divisor*, not a zero or insufficient *result* [6](#0-5) .

## Impact Explanation
This is a public, permissionless path (any XCM sender or `snowbridge_pallet_system::send`) through which the native-currency fee collected for a message can be silently zero or under-collected relative to the reward unconditionally committed and later paid out to relayers on Ethereum per the documented settlement formula `Min(GasPrice, MaxFeePerGas) * GasUsed() + Message.Reward` [7](#0-6) . This falls under "public underpriced work that degrades block production or stalls bridge processing" since it allows accruing a value shortfall in the bridge's fee/reward accounting with no privileged action required.

## Likelihood Explanation
The rounding is a deterministic, purely arithmetic property of `convert_from_ether_decimals`, exercised on every `calculate_fee` call, which itself runs on every outbound message send via `SendMessage::validate` [8](#0-7) . Triggering the worst case (zero fee) requires specific governance-configured `PricingParameters` (small `rewards.remote`/`fee_per_gas` combined with `Decimals`/`multiplier`/`exchange_rate` pushing the intermediate value below `10^(18-Decimals)`), which is plausible but not confirmed against current live BridgeHub production parameters.

## Recommendation
- Use ceiling/rounding-up division in `convert_from_ether_decimals` (e.g., `(value + denom - 1) / denom` or `sp_arithmetic`'s rounding helpers) so the collected fee never under-covers the promised reward.
- Re-derive the committed `reward` from the same rounded value actually collected, rather than writing the un-rounded `pricing_params.rewards.remote` independently in `do_process_message`.
- Add an explicit `ensure!(fee.remote > 0 ...)` (or a sufficiency check against the reward) so degenerate parameter combinations cannot silently produce an under-collected fee for a non-zero reward commitment.

## Proof of Concept
1. Governance sets `PricingParameters` such that, for a command's `gas_used_at_most`, the value passed into `convert_from_ether_decimals` after `calculate_remote_fee`/`multiplier`/`exchange_rate` adjustment is smaller than `10^(18 - T::Decimals)` (e.g., `< 10^8` for DOT).
2. Any user calls `SendMessage::validate` for a command with this gas profile; `calculate_fee` returns `Fee { remote: 0, .. }`, the amount actually withdrawn from the sender.
3. `deliver` enqueues the message; `do_process_message` still writes `reward: pricing_params.rewards.remote` (full, ungoverned-by-rounding wei amount) into the committed message [9](#0-8) .
4. On Ethereum, the relayer is paid the full `Message.Reward`, while the parachain collected `0` from the sender for the remote fee component — a demonstrable value shortfall from the rounding-down decimal conversion.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		// 1 DOT has 10 digits of precision
		// 1 KSM has 12 digits of precision
		// 1 ETH has 18 digits of precision
		pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
			let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
			let denom = 10u128.saturating_pow(decimals);
			value.checked_div(denom).expect("divisor is non-zero; qed").into()
		}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}
