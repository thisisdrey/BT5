Audit Report

## Title
Irreversible tip burn before destination-side validation causes permanent, unrecoverable user fund loss in `snowbridge-pallet-system-frontend::add_tip` - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`EthereumSystemFrontend::add_tip` swaps the caller's tip asset for Ether and irreversibly burns it via `burn_for_teleport` before the destination chain (BridgeHub) has validated that the target message nonce is still eligible to receive a tip. If the nonce is stale or already processed, `snowbridge-pallet-system-v2::add_tip` simply records the amount into `LostTips<T>`, a storage map that is written to but never drained, refunded, or reclaimed anywhere in the codebase, resulting in permanent loss of the burned funds.

## Finding Description
`add_tip` in `bridges/snowbridge/pallets/system-frontend/src/lib.rs` first calls `Self::swap_fee_asset_and_burn(who.clone().into(), asset)?`, which swaps the caller's asset for Ether and then irreversibly destroys it via `burn_for_teleport` [1](#0-0) . The actual burn happens inside `swap_and_burn`/`swap_fee_asset_and_burn`, both of which call `burn_for_teleport::<T::AssetTransactor>` unconditionally as part of asset conversion, before any destination-side confirmation exists [2](#0-1) [3](#0-2) .

Only after this destructive step does the pallet build and dispatch an XCM `AddTip` transact call to `EthereumSystem` on BridgeHub via `send_transact_call` [4](#0-3) .

On BridgeHub, `snowbridge-pallet-system-v2::add_tip` attempts to apply the tip to the corresponding inbound/outbound queue nonce, and if `InboundQueue::add_tip`/`OutboundQueue::add_tip` returns an error (e.g. because the nonce is unknown or already consumed), the amount is added to `LostTips<T>` instead of being credited: [5](#0-4) .

The `LostTips` storage declaration itself confirms there is no current recovery mechanism, with its own doc comment stating recovery is only a hypothetical future feature: [6](#0-5) . A repo-wide search confirms `LostTips` is referenced only in `system-v2/src/lib.rs` (write), `system-v2/src/tests.rs`, and the integration test file — there is no extrinsic, hook, or drain logic anywhere that reads and refunds this value to the affected user.

The integration test `tip_to_invalid_nonce_is_added_to_lost_tips` demonstrates this exact flow end-to-end: a tip for a non-existent nonce is submitted on Asset Hub (burning the asset), fails to apply on BridgeHub, and is recorded into `LostTips` with `success: false`, with no further recovery step available.

## Impact Explanation
This is a genuine "permanent user-fund lock" (in this case, permanent unbacked burn) impact: an unprivileged user calling the public extrinsic `add_tip` can have real value irreversibly destroyed via `burn_for_teleport` while receiving no benefit and no compensation, because the destination-side validity check (whether the nonce is still eligible for a tip) occurs strictly after the irreversible source-side burn. The `LostTips<T>` storage map is provably a dead-end: it is only mutated on failure and never read or drained by any extrinsic or hook in the reviewed code, confirming the loss is permanent under the current implementation, not merely a documentation mismatch.

## Likelihood Explanation
Triggering this requires no privileged actor, malicious peer, or complex race — a normal user submitting `add_tip` for a message nonce that has already been delivered/finalized/removed by the time the XCM transact reaches BridgeHub (an ordinary consequence of asynchronous XCM delivery between Asset Hub and BridgeHub, or simple user error providing a stale nonce) will trigger the loss. This is a realistic, repeatable condition reachable in normal bridge operation by any unprivileged sender, not an edge case requiring adversarial timing manipulation.

## Recommendation
Reorder the operation so the destination-side validity of the tip (i.e., that the target nonce is still pending/eligible) is confirmed before irreversibly burning the source-side asset — for example, via a query/lookup mechanism, an escrow/hold instead of an immediate burn, or a two-phase commit where the burn is finalized only after BridgeHub confirms success. Alternatively (or additionally), implement the recovery mechanism that the `LostTips` doc comment references but that does not currently exist: an extrinsic or hook that lets affected senders reclaim or be compensated for amounts recorded in `LostTips<T>`.

## Proof of Concept
1. User calls `EthereumSystemFrontend::add_tip(origin, message_id=Outbound(N), asset)` on Asset Hub for nonce `N` [1](#0-0) .
2. `swap_fee_asset_and_burn` executes: the asset is swapped for Ether and burned via `burn_for_teleport`, irreversibly removing value from the user's account [3](#0-2) .
3. The XCM `AddTip` transact call is dispatched to BridgeHub's `snowbridge-pallet-system-v2::add_tip`.
4. Nonce `N` has already been delivered/removed by the time the XCM lands, so `OutboundQueue::add_tip` returns an error.
5. `system-v2::add_tip` catches the error and records the amount into `LostTips::<T>` for the sender, as reproduced by the integration test `tip_to_invalid_nonce_is_added_to_lost_tips` in `cumulus/parachains/integration-tests/emulated/tests/bridges/bridge-hub-westend/src/tests/snowbridge_v2_outbound.rs` [7](#0-6) .
6. The user's burned Ether is permanently gone; `LostTips` has no reader/drain/refund logic anywhere in the reviewed pallets, confirming permanent, unrecoverable fund loss.

		fn swap_and_burn(
			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether
			let ether_asset = Asset::from((ether_location.clone(), ether_gained));

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}

		#[pallet::call_index(3)]
		#[pallet::weight(<T as pallet::Config>::WeightInfo::add_tip())]
		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}
