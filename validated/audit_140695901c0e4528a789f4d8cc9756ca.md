### Title
Attacker can fill a victim's per-account token list to `MAX_TOKENS_PER_USER` via dust deposits/transfers, freezing the victim's ability to hold new collateral or mint new synthetics - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to CVE-2016-9066 (crash caused by unbounded memory allocation against attacker-controlled incoming data), `Pool` keeps a bounded per-account array (`MappedEnumerableSet.AddressSet`) capped at `MAX_TOKENS_PER_USER = 30` entries (`debtTokensOfAccount + depositTokensOfAccount`). Any unprivileged user can force entries into a victim's list — either by transferring dust `DepositToken` shares (`DepositToken._transfer` auto-registers the recipient on first receipt) or, more cheaply, by calling `deposit(amount_, onBehalfOf_ = victim)` with a dust amount, which mints directly to the victim. Once the combined count hits 30, `onlyIfAdditionWillNotReachMaxTokens` reverts, so the victim cannot receive/deposit any additional collateral type and cannot open a position in a new synthetic asset.

### Finding Description
- `DepositToken._mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's prior balance is 0 (`DepositToken.sol:486-488`). `deposit()` accepts an arbitrary `onBehalfOf_` beneficiary (`DepositToken.sol:211-234`), so the attacker mints dust msdToken straight into the victim's list without needing victim action.
- `DepositToken._transfer` does the same for plain transfers (`DepositToken.sol:518-519`).
- The cap check is `Pool.onlyIfAdditionWillNotReachMaxTokens`, which reverts with `UserReachedMaxTokens` when the combined list length is `>= 30` (`Pool.sol:143-148`), enforced inside `addToDepositTokensOfAccount` (`Pool.sol:216-220`) and `addToDebtTokensOfAccount` (`Pool.sol:204-208`).
- Consequences once saturated: `deposit()` to the victim with any not-yet-held collateral reverts; `transfer`/`transferFrom`/`seize` of a not-yet-held deposit token to the victim reverts; and `DebtToken` issuance (mint/flashIssue on first borrow of a new synthetic) reverts, since those paths hit the same modifier.
- Modifiers do not help: the revert happens inside the token/pool call, not behind a guard the victim controls. `whenNotPaused`, `nonReentrant`, `SynthContext._msgSender`, and supply caps are irrelevant here.

### Impact Explanation
The victim's account is partially frozen: it cannot onboard any new collateral type and cannot mint any new debt token until entries are removed. Existing funds are not stolen, but new deposits directed at the victim revert, and incoming transfers/seizures of new deposit tokens revert — a temporary freezing of funds/positions matching the CVE's DoS-on-large-inputs class. The victim can recover by clearing entries (transferring/withdrawing each dust balance to zero, since `_burn`/`_transfer` call `removeFromDepositTokensOfAccount` when the balance hits 0), but this costs gas per poisoned entry and the attacker can re-poison at dust cost, so the freeze is repeatable.

### Likelihood Explanation
The attack only requires an EOA, dust amounts of each listed underlying, and public entry points (`deposit` with `onBehalfOf_ = victim`, or `transfer`). No privileged role, oracle manipulation, or flash loan is needed. Cost is proportional to the number of registered deposit tokens (bounded by pool configuration), and it is cheap relative to the harm of blocking a victim's account. It is a griefing vector rather than fund theft, and recovery is possible, so likelihood is high but severity is moderate.

### Recommendation
- Do not auto-register recipients on `deposit(..., onBehalfOf_)`/`transfer`: either require an opt-in flag, or make `addToDepositTokensOfAccount` skip (rather than revert) silently-failing additions and handle over-cap accounts lazily.
- Alternatively, track positions by iterating pool-level `depositTokens`/`debtTokens` (bounded by governance listing) instead of a per-account set, or raise/remove `MAX_TOKENS_PER_USER` and bound health-check loops by the pool's registered token count.

### Proof of Concept
Hardhat (fork or unit) outline:
```ts
// pool, depositTokenA..N registered; victim = fresh account
for (const dt of depositTokens) {
  await underlying.approve(dt.address, DUST);
  await dt.deposit(DUST, victim.address); // _mint -> addToDepositTokensOfAccount(victim)
}
// after 30 combined debt+deposit entries:
await expect(depositTokenNew.deposit(1, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(debtToken.connect(victim).issue(1))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens'); // addToDebtTokensOfAccount reverts
// victim recovers per entry by zeroing the dust balance:
await depositTokens[0].connect(victim).transfer(attacker.address, dustBal); // removeFromDepositTokensOfAccount
```
Expected: all `deposit`/`issue` calls for not-yet-held tokens revert while the list is saturated; succeeds again after the victim clears one entry, confirming a temporary freeze rather than theft.
