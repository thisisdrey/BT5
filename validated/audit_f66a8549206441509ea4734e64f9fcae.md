### Title
Cross-repository lock-order inversion in `partitionAssigner.getPartitionIDRecursive` causes handler deadlock via mutually-aliased alternates - ([File: internal/gitaly/storage/storagemgr/partition_assigner.go])

### Summary
`partitionAssigner` serializes per-repository partition assignment using a map of per-relative-path locks acquired via `acquireRepositoryLock`/`releaseRepositoryLock` [1](#0-0) . When assigning a repository that has an `objects/info/alternates` file, `getAlternatePartitionID` recursively acquires the lock of the alternate (pool) repository while still holding the lock of the original repository [2](#0-1) . The single-level "chain of alternates" guard (`ErrAlternateHasAlternate`) only prevents a *single* goroutine's own recursion depth from exceeding one hop; it does not prevent two independent, concurrently-running top-level requests, each targeting one of two repositories that reference each other as alternates, from acquiring their own repository's lock first and then blocking indefinitely trying to acquire the other's lock — a classic AB-BA lock-order inversion.

### Finding Description
`getPartitionIDRecursive(relativePath)` acquires `pa.repositoryLocks[relativePath]` and holds it (via `defer releaseLock()`) for the duration of `assignPartitionID` → `getAlternatePartitionID`, which reads the target repository's `objects/info/alternates` file and, if present, recurses into `getPartitionIDRecursive(alternateRelativePath, recursiveCall=true, ...)` — acquiring a **second** lock while the first is still held [3](#0-2) .

Two ordinary, unprivileged requests can each be the "first" to enter this code with a different starting repository:
- Goroutine 1: assigns partition for repo `B` → locks `B` → reads `B`'s alternates → finds `C` → tries to lock `C` (blocks).
- Goroutine 2: assigns partition for repo `C` → locks `C` → reads `C`'s alternates → finds `B` → tries to lock `B` (blocks).

Both goroutines now wait on each other's lock forever (or until the RPC's context is cancelled). The existing `ErrAlternateHasAlternate` guard [4](#0-3)  can never fire in this scenario because it is only reached *after* the nested lock is successfully acquired — but the nested acquisition is exactly what is stuck waiting.

This requires two repositories, `B` and `C`, whose `objects/info/alternates` files point at each other. `LinkRepositoryToObjectPool` writes an alternates file into whatever repository is passed as `Repository` in the request, with no check that the target is not itself a pool or that this wouldn't create a two-node alternate cycle [5](#0-4) [6](#0-5) . An ordinary user with access to two repositories/pools can therefore call `LinkRepositoryToObjectPool(Repository=B, ObjectPool=C)` and then `LinkRepositoryToObjectPool(Repository=C, ObjectPool=B)` to set up the mutual reference (the `linkedToRepository` check only rejects a *different* existing pool reference, not a fresh one [7](#0-6) ). Once configured, any two concurrent RPCs against `B` and `C` (e.g. ordinary fetches/pushes) that require partition assignment will race into the deadlock in `getPartitionIDRecursive`.

### Impact Explanation
This is a Denial of Service of Gitaly's storage manager: once the deadlock occurs, both goroutines processing the RPCs are stuck holding `partitionAssigner.mutex`-protected map entries indefinitely (or until client-side/context timeout, which in Gitaly config can be long or absent for internal calls), and any other request targeting `B` or `C` will also queue up behind the same locks. This maps to the report's underlying bug class — a resource-serialization guard that only correctly handles the single-caller/local case and fails when the same class of resource is legitimately (or through crafted configuration) reachable from two directions in the same "transaction space."

### Likelihood Explanation
Requires: (1) an actor with access to at least two repositories that can be pool/member pairs, and (2) precise timing to trigger the race (both requests must be "first" to reach the un-cached partition-assignment path around the same time, before the assignment is cached in the key-value store). This makes it a real but somewhat narrow-window concurrency bug rather than a trivially reliable exploit; it is nonetheless deterministically reachable given repeated attempts, since the deadlock condition is stable once the mutual-alternates configuration exists and only the initial race is probabilistic.

### Recommendation
Enforce a canonical lock-acquisition order in `acquireRepositoryLock`/`getPartitionIDRecursive` (e.g., always resolve and lock repositories in lexicographic order of relative path, or detect at `Link()` time whether the target `ObjectPool`'s repository already has (or would create) a two-node alternate cycle and reject it, similar to the existing self-pointing and chain-length checks in `getAlternatePartitionID`).

### Proof of Concept
1. Create two repositories/pools `B` and `C`.
2. Call `LinkRepositoryToObjectPool(Repository=B, ObjectPool=C)` — writes `B/objects/info/alternates` → `C`.
3. Call `LinkRepositoryToObjectPool(Repository=C, ObjectPool=B)` — writes `C/objects/info/alternates` → `B` (no existing check rejects this since `linkedToRepository` only fails for alternates pointing elsewhere, not for creating this cycle).
4. Delete/invalidate any prior partition assignment for `B` and `C` (or use freshly created repos before first access) so both require fresh assignment.
5. Concurrently issue any repository-scoped RPC (e.g. `RepositoryExists`, a fetch) against `B` and against `C` at the same time.
6. Observe both requests hang indefinitely in `partitionAssigner.acquireRepositoryLock`, reproducing the deadlock described above.

Note: I was unable to execute this PoC in a live environment (no filesystem/runtime access) — this trace is based on static analysis of `internal/gitaly/storage/storagemgr/partition_assigner.go`, `internal/git/objectpool/link.go`, and `internal/gitaly/service/objectpool/link.go`. A background Devin session with repository access could run this scenario end-to-end to confirm the deadlock empirically.

func (pa *partitionAssigner) acquireRepositoryLock(ctx context.Context, relativePath string) (func(), error) {
	pa.mutex.Lock()
	// See if some other goroutine already locked the repository. If so, wait for it to complete.
	if lock, ok := pa.repositoryLocks[relativePath]; ok {
		// Register ourselves as a waiter.
		lock.goroutines++
		pa.mutex.Unlock()
		select {
		case <-lock.semaphore:
			// It's our turn now.
		case <-ctx.Done():
			pa.releaseRepositoryLock(relativePath, false)
			return nil, ctx.Err()
		}
	} else {
		// No other goroutine had locked the repository yet. Lock the repository so other goroutines
		// wait while we assign the repository a partition.
		pa.repositoryLocks[relativePath] = &repositoryLock{
			semaphore:  make(chan struct{}, 1),
			goroutines: 1,
		}
		pa.mutex.Unlock()
	}

	return func() { pa.releaseRepositoryLock(relativePath, true) }, nil
}

func (pa *partitionAssigner) getPartitionIDRecursive(ctx context.Context, relativePath string, recursiveCall bool, partitionHint storage.PartitionID, isRepositoryCreation bool) (storage.PartitionID, error) {
	// Check first whether the repository is already assigned into a partition. If so, just return the assignment.
	ptnID, err := pa.partitionAssignmentTable.getPartitionID(relativePath)
	if err != nil {
		if !errors.Is(err, storage.ErrPartitionAssignmentNotFound) {
			return 0, fmt.Errorf("get partition: %w", err)
		}

		// Repository wasn't yet assigned into a partition. This is the slow path. Requests attempting
		// to get or assign a partition ID concurrently are serialized.

		releaseLock, err := pa.acquireRepositoryLock(ctx, relativePath)
		if err != nil {
			return 0, fmt.Errorf("acquire repository lock: %w", err)
		}

		defer releaseLock()

		// With the repository locked, check first whether someone else assigned it into a partition
		// while we weren't holding the lock between the first failed attempt getting the assignment
		// and locking the repository.
		ptnID, err = pa.partitionAssignmentTable.getPartitionID(relativePath)
		if !errors.Is(err, storage.ErrPartitionAssignmentNotFound) {
			if err != nil {
				return 0, fmt.Errorf("recheck partition: %w", err)
			}

			// Some other goroutine assigned a partition between the failed attempt and locking the
			// repository.
			return ptnID, nil
		}

		// With the repository under lock, verify it is a Git directory before we assign it into a partition.
		// It's okay if the repository doesn't yet exist as this transaction may be about to create it.
		if err := storage.ValidateGitDirectory(filepath.Join(pa.storagePath, relativePath)); err != nil {
			if errors.Is(err, fs.ErrNotExist) {
				if !isRepositoryCreation {
					return 0, relativePathNotFoundError(relativePath)
				}

				// Repository creations are allowed to target non-existing repositories. They create the partition
				// where the repository is to be created.
			} else {
				return 0, fmt.Errorf("validate git directory: %w", err)
			}
		}

		ptnID, err = pa.assignPartitionID(ctx, relativePath, recursiveCall, partitionHint)
		if err != nil {
			return 0, fmt.Errorf("assign partition ID: %w", err)
		}
	}

	return ptnID, nil
}

func (pa *partitionAssigner) getAlternatePartitionID(ctx context.Context, relativePath string, recursiveCall bool, partitionHint storage.PartitionID) (storage.PartitionID, error) {
	alternate, err := gitstorage.ReadAlternatesFile(filepath.Join(pa.storagePath, relativePath))
	if err != nil {
		return 0, fmt.Errorf("read alternates file: %w", err)
	}

	if recursiveCall {
		// recursive being true indicates we've arrived here through another repository's alternate.
		// Repositories in Gitaly should only have a single alternate that points to the repository's
		// pool. Chains of alternates are unexpected and could go arbitrarily long, so fail the operation.
		return 0, storage.ErrAlternateHasAlternate
	}

	// The relative path should point somewhere within the same storage.
	alternateRelativePath, err := storage.ValidateRelativePath(
		pa.storagePath,
		// Take the relative path to the repository, not 'repository/objects'.
		filepath.Dir(
			// The path in alternates file points to the object directory of the alternate
			// repository. The path is relative to the repository's own object directory.
			filepath.Join(relativePath, "objects", alternate),
		),
	)
	if err != nil {
		return 0, fmt.Errorf("validate relative path: %w", err)
	}

	if alternateRelativePath == relativePath {
		// The alternate must not point to the repository itself. Not only is it non-sensical
		// but it would also cause a dead lock as the repository is locked during this call
		// already.
		return 0, storage.ErrAlternatePointsToSelf
	}

	// Recursively get the alternate's partition ID or assign it one. This time
	// we set recursive to true to fail the operation if the alternate itself has an
	// alternate configured.
	ptnID, err := pa.getPartitionIDRecursive(ctx, alternateRelativePath, true, partitionHint, false)
	if err != nil {
		return 0, fmt.Errorf("get partition ID: %w", err)
	}

	return ptnID, nil

func linkedToRepository(ctx context.Context, pool, repo *localrepo.Repo) (bool, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting repo path: %w", err)
	}

	altInfo, err := stats.AlternatesInfoForRepository(repoPath)
	if err != nil {
		return false, fmt.Errorf("getting alternates info: %w", err)
	}

	if !altInfo.Exists || len(altInfo.ObjectDirectories) == 0 {
		return false, nil
	}

	relPath := altInfo.ObjectDirectories[0]
	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return false, err
	}

	if relPath == expectedRelPath {
		return true, nil
	}

	if filepath.Clean(relPath) != filepath.Join(poolPath, "objects") {
		return false, fmt.Errorf("unexpected alternates content: %q", relPath)
	}

	return false, nil
}
