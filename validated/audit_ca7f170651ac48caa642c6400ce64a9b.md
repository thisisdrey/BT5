### Title
Missing caller/identity validation on `CreateRelayRequest.RelayFromAddr` allows relay state poisoning — (File: `relay_manager.go`)

### Summary
`relayManager.handleCreateRelayRequest` trusts the attacker-controlled `RelayFromAddr` field of an incoming `CreateRelayRequest` control message as the identity being relayed, without ever checking it against the actual authenticated peer (`h`, the `HostInfo` whose Noise-verified tunnel delivered the message). This is the same bug class as the reported `V3Utils.execute()` issue: a privileged action (registering relay state that redirects traffic for a given VPN address) is performed using an attacker-supplied identity parameter instead of the caller's own cryptographically-verified identity.

### Finding Description
An authenticated Nebula peer sends a `NebulaControl_CreateRelayRequest` message identifying itself with `RelayFromAddr` (its own VPN address) and the desired relay target with `RelayToAddr`. On the honest sending path this invariant always holds — every call site sets `RelayFromAddr` to the sender's own address: [1](#0-0) [2](#0-1) 

However, `HandleControlMsg` only checks that `RelayFromAddr`/`RelayToAddr` are non-nil before dispatching — it never checks that the claimed `from` matches the sender's authenticated VPN address(es) (`h.vpnAddrs`): [3](#0-2) 

`handleCreateRelayRequest` then reads `from := protoAddrToNetAddr(m.RelayFromAddr)` directly from the message body and, when this host is the terminal relay target, uses that attacker-controlled `from` value as the `PeerAddr` associated with the sender's `HostInfo h` in the hostmap's relay tables — with no verification that `from` is actually one of `h.vpnAddrs`: [4](#0-3) 

This mirrors the reported flaw exactly: `h` is the equivalent of `msg.sender` (cryptographically authenticated via the completed Noise handshake and `hostMap.QueryIndex`), while `from` is an unchecked, caller-supplied "identity" parameter (like `V3Utils`'s `recipient`/`tokenId` owner assumption) that is used to perform a state-changing, trust-sensitive action — creating durable relay routing state (`AddRelay`) keyed on an address the caller does not actually own.

### Impact Explanation
Any authenticated Nebula peer (no special privilege required beyond having a valid, CA-signed cert and an established tunnel to the target) can claim an arbitrary victim VPN address as `RelayFromAddr` in a `CreateRelayRequest`. The receiving node will call `AddRelay(rm.l, h, f.hostMap, from, ...)` and register `h` (the attacker's own hostinfo) as the terminal relay for the victim's address in `hm.Relays` / `relayState`. This poisons this node's relay routing tables: subsequent traffic that this node believes should be relayed to/for the victim address can be misdirected through the attacker's tunnel instead of the victim's real tunnel, enabling relay-hijack/traffic redirection or persistent denial-of-service against the victim's reachability through this relay, with no cryptographic proof that the attacker actually controls the claimed address.

### Likelihood Explanation
Reachable by any peer that can complete a normal handshake with the target node (no lighthouse/relay role, no CA compromise, and no valid certificate for the claimed victim address is required — only a valid cert for the attacker's own identity). The only precondition is that the target has `relay.am_relay` (or acts as a terminal relay target) enabled, which is a common relay-participant configuration.

### Recommendation
In `handleCreateRelayRequest`, before trusting `from` as an identity to bind relay state to, verify that `from` is contained in `h.vpnAddrs` (the certificate-derived, handshake-authenticated address set of the actual sender), e.g.:

```go
if !slices.Contains(h.vpnAddrs, from) {
    logMsg.Error("RelayFromAddr does not match sender's authenticated vpnAddrs")
    return
}
```

Apply the same check consistently in `handleCreateRelayResponse` / `EstablishRelay` paths that consume peer-supplied address fields, to ensure every relay-address field used to mutate hostmap/relay state matches the authenticated identity that transmitted the control message.

### Proof of Concept
1. Establish an authenticated tunnel between attacker node `A` and a relay-capable node `R` (`relay.am_relay=true` on `R`), where `R` also has (or can reach) a legitimate victim node `V`.
2. From `A`, send `R` a `NebulaControl_CreateRelayRequest` with `RelayFromAddr = V's VPN address` (not `A`'s own address) and `RelayToAddr = R`'s own address.
3. `R.handleCreateRelayRequest` executes the "target is me" branch, calling `AddRelay(rm.l, h=A's HostInfo, f.hostMap, from=V's address, ...)`, registering `A`'s hostinfo as the terminal relay for `V`'s address — despite `A` never proving ownership of `V`'s VPN address/certificate.
4. Observe `R`'s relay state (`hm.Relays`, `h.relayState`) now associates `V`'s address with `A`'s tunnel, which can be leveraged to intercept or blackhole traffic intended to reach `V` via `R`.
