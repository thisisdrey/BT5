Audit Report

## Title
`process_delivery_receipt` pays relayer reward without checking the decoded `success` field of the delivery receipt - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
The Ethereum `Gateway` contract emits `InboundMessageDispatched(nonce, topic, success, reward_address)`, decoded into `DeliveryReceipt { gateway, nonce, topic, success, reward_address }` [1](#0-0) . `process_delivery_receipt` decodes and carries the `success` boolean but never inspects it before paying the relayer reward and clearing the pending order, only checking the gateway address and nonce existence [2](#0-1) .

## Finding Description
`submit_delivery_receipt` verifies only that the event log is authentically included in a finalized Ethereum block via `T::Verifier::verify`, which proves inclusion but says nothing about whether the underlying dispatch succeeded [3](#0-2) . The semantic success/failure outcome is carried exclusively in `receipt.success`, decoded faithfully from the on-chain event in `TryFrom<&Log>` [4](#0-3) . In `process_delivery_receipt`, the code checks `T::GatewayAddress::get() == receipt.gateway` and fetches the `PendingOrders` entry by `receipt.nonce`, then unconditionally calls `T::RewardPayment::register_reward` whenever `order.fee > 0`, and unconditionally removes the order and emits `MessageDelivered` [5](#0-4) . No branch on `receipt.success` exists anywhere in the pallet — confirmed by a search across `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` which returns zero hits for `success`.

## Impact Explanation
Any relayer holding a genuinely finalized Ethereum log where the Gateway emitted `success=false` (dispatch reverted/failed on the Ethereum side, e.g. due to insufficient relayer-supplied gas or a caught execution error) can submit that receipt and still collect the full `order.fee` reward as if delivery fully succeeded, since the reward payout and `PendingOrders` removal happen unconditionally regardless of `receipt.success`. This is public underpriced/over-rewarded relayer work and duplicate/incorrect settlement of bridge rewards, matching the "duplicate settlement or payout" and "public underpriced work" impact categories.

## Likelihood Explanation
The call path is reachable by any signed account via the public `submit_delivery_receipt` extrinsic with a legitimately finalized Ethereum log (`ensure_signed(origin)` only) [6](#0-5) . No forgery is needed — `success=false` occurs naturally on Ethereum for a variety of benign reasons, making this a realistic, unprivileged, repeatable exploit path.

## Recommendation
Branch on `receipt.success` in `process_delivery_receipt`: only call `T::RewardPayment::register_reward` when `receipt.success == true`; for `success == false`, withhold or reduce the reward, emit a distinct failure event (e.g. `MessageDeliveryFailed`), and/or route to a retry/refund mechanism instead of unconditionally paying the full fee and clearing the order.

## Proof of Concept
1. BridgeHub processes a message and inserts `PendingOrder { nonce, fee, .. }` via `do_process_message` [7](#0-6) .
2. On Ethereum, the Gateway dispatch fails and emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains the finalized inclusion proof and calls `submit_delivery_receipt`.
4. `T::Verifier::verify` succeeds because the log is genuinely included/finalized; `DeliveryReceipt::try_from` correctly decodes `success: false`.
5. `process_delivery_receipt` ignores `success`, pays `order.fee` to the reward account, and removes the order — full reward collected despite failed delivery.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
