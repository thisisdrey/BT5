### Title
Anti-Replay Window Check/Update Race Allows Duplicate Message Counter to Bypass Replay Protection - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement the anti-replay window as two separate, independently-locked operations: `window.Check` (verify not-yet-seen) and `window.Update` (mark as seen), with the AEAD `DecryptDanger` call sandwiched in between and the `decryptLock` released and re-acquired around it. [1](#0-0)  This mirrors the root cause of the referenced report: two logically-coupled state transitions (a threshold "may I proceed" check and a state-mutating "commit" step) are not executed atomically, so the order/interleaving of concurrent invocations determines whether the guard is actually enforced.

### Finding Description
`Decrypt` performs:
1. Lock, `window.Check(messageCounter)` (read-only "have I seen this counter" check), Unlock.
2. `dKey.DecryptDanger(...)` (no lock held).
3. Lock, `window.Update(messageCounter)` (mutates the bitmap, marking the counter seen), Unlock. [1](#0-0) 

`VerifyRelay` follows the identical Check → decrypt → Update pattern for relayed frames. [2](#0-1) 

Because the lock is dropped between `Check` and `Update`, two goroutines processing two copies of the exact same on-wire packet (an attacker-duplicated/replayed UDP datagram, or two racing reads of the same packet arriving via different paths, e.g. direct + relay) with the same `messageCounter` can both pass `Check` (both see "not yet in window") before either has called `Update`. Both then proceed to decrypt and both call `Update`, and — depending on scheduling — the anti-replay guarantee that a given nonce/counter is processed at most once is not actually enforced by the locking discipline; the mutex only protects the internal bitmap data structure from corruption, not the check-then-act invariant across the unlocked decrypt step. This is directly analogous to the `heal`/`escape` bug: two functions gate on shared mutable state (`activeAgents` / `window.current` bitmap) with the guard and the mutation split apart, so an attacker who controls the interleaving (here, by sending duplicate ciphertext packets fast enough to race two receive goroutines) can make the "already seen" check meaningless for a duplicate delivery.

### Impact Explanation
The anti-replay window is a nonce/replay-handling primitive that is core to the security guarantees of the Noise-based transport — its entire purpose is to guarantee at-most-once processing of a given `messageCounter`/nonce, and per the Noise/AEAD threat model, reusing a nonce for genuinely new plaintext is catastrophic, but even reprocessing a duplicate ciphertext through `DecryptDanger` twice concurrently means the packet payload can be delivered to the TUN device / relay path twice, defeating replay protection guarantees the design document explicitly attributes to this component (`ReplayWindow`, `Bits.Check`/`Update`). A successful race allows an on-path or off-path attacker who can duplicate/replay observed ciphertext at the UDP layer (no CA-signed certificate required — this operates purely on already-observed wire bytes) to cause duplicate delivery of a packet that the replay window is supposed to reject exactly once.

### Likelihood Explanation
This requires the attacker to duplicate a captured UDP packet and deliver both copies to the victim node in a tight enough time window that both reads pass through `outside.go`'s packet-processing pipeline concurrently before the first `Update` commits. Nebula's UDP read path can use multiple reader goroutines/batched reads (`recvmmsg` on Linux, RIO on Windows) feeding the same `ConnectionState`, which increases the likelihood of a genuine concurrent race versus a single-threaded reader. This is a race condition with a narrow timing window rather than a deterministic bypass, so likelihood is moderate, not high.

### Recommendation
Collapse `Check` and `Update` into a single atomic, lock-held operation (i.e., hold `decryptLock` across the check, or better, perform the "reserve" step atomically before decrypt and only roll back on decrypt failure) so that two concurrent deliveries of the same `messageCounter` cannot both pass the check before either commits. A `CheckAndUpdate`-style API which reserves the counter under one critical section, decrypts, and rolls back the reservation only on decryption failure would close the race.

### Proof of Concept
Not independently verified with a running reproduction (no test harness run); the race window is inferred directly from the source: `cs.decryptLock.Unlock()` at connection_state.go:65 releases the lock before `DecryptDanger` runs, and the lock is only re-acquired at connection_state.go:75 for `Update`. Two goroutines calling `Decrypt` concurrently with the same `messageCounter` and valid ciphertext will both observe `window.Check` return `true` if scheduled such that both `Check` calls execute before either `Update` call, which can be demonstrated with a targeted Go test spawning two goroutines against the same `*ConnectionState` with duplicate packets and asserting both calls return `nil, nil` (no `ErrAlreadySeen`) instead of exactly one succeeding. func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
