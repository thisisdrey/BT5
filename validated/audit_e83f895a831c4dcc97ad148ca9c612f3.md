### Title
Unvalidated client-supplied `GitObjectDirectory` / `GitAlternateObjectDirectories` fields allow object-directory injection when Gitaly spawns Git subprocesses - (File: internal/git/gitcmd/command_factory.go)

### Summary
Any RPC that accepts a `Repository` protobuf message lets the caller set `GitObjectDirectory` and `GitAlternateObjectDirectories`. These fields are meant to only be populated internally when Gitaly re-creates a Git object-quarantine environment for hook callbacks. In `ExecCommandFactory.newCommand`, however, these attacker/RPC-controlled fields are joined onto the repository path and injected as `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` for every spawned Git process with **no path-traversal or storage-root validation**, unlike the equivalent, validated code path in `internal/git/localrepo/paths.go`.

### Finding Description
`alternates.Env` builds the object-directory environment variables by simply joining the repository path with the caller-supplied strings: [1](#0-0) 

`ExecCommandFactory.newCommand` calls this helper directly using the raw `Repository.GetGitObjectDirectory()`/`GetGitAlternateObjectDirectories()` values with no sanitization before spawning the Git process: [2](#0-1) 

Contrast this with the dedicated `Repo.ObjectDirectoryPath` helper, which explicitly validates the same fields against `storage.ValidateRelativePath` and rejects directory traversal / storage escape (`"../bazqux.git"`, `"objects/../.."`, etc.): [3](#0-2) [4](#0-3) 

The only guard against clients abusing these fields lives in the WAL/partitioning middleware, and the code comments there explicitly acknowledge this is an unresolved gap: [5](#0-4) 

That middleware only rejects **mutator** RPCs when it is active, and is itself gated behind WAL being enabled (`TestMiddleware_transactional` skips when WAL is disabled), leaving accessor RPCs and non-WAL deployments to reach `newCommand` with attacker-supplied object directories that are trusted implicitly, mirroring the "unbounded, unchecked delegation" root cause of the reported DeFi bug class (a caller-supplied field granting broader access than intended because it is never independently validated by the consuming code path).

### Impact Explanation
An attacker who can set `GitObjectDirectory`/`GitAlternateObjectDirectories` on a `Repository` message in an accessor RPC (or any RPC not covered by the WAL mutator check) can point Git's object search path at a directory outside of the intended repository/quarantine tree - e.g., pointing `GIT_ALTERNATE_OBJECT_DIRECTORIES` at another repository or an arbitrary path within the storage - and thereby read/expose objects from a repository the caller should not have access to (cross-repository object disclosure), similar in spirit to `internal/git/dirs.go`'s `alternateOutsideStorageError` protections that exist for the on-disk `objects/info/alternates` file but are bypassed here for the RPC-level fields.

### Likelihood Explanation
Reaching this code requires only sending a normal gRPC request with a `Repository` message that happens to set `GitObjectDirectory`/`GitAlternateObjectDirectories` - fields exposed on every `Repository` proto and therefore settable by any client of an accessor RPC, without any special privilege. The explicit code comment in `middleware.go` ("This allows for circumventing the transaction management ... We'll leave this unaddressed for now") indicates the gap is real and known but not closed for the general case.

### Recommendation
Validate `GitObjectDirectory` and `GitAlternateObjectDirectories` the same way `Repo.ObjectDirectoryPath` does (via `storage.ValidateRelativePath` against the storage root and expected quarantine prefix) before they are used in `alternates.Env`/`newCommand`, for all RPC types (not only WAL mutators), or strip/ignore these fields entirely unless the request is proven to originate from Gitaly's own quarantine/snapshot machinery.

### Proof of Concept
1. Call any Gitaly accessor RPC (e.g. `ObjectFormat`, `CommitIsAncestor`) with a `Repository` message where `GitAlternateObjectDirectories` is set to a relative path that escapes the repository (e.g. `"../../other-repo/objects"`).
2. Because `beginTransactionForRepository`'s guard only fires for mutator RPCs under WAL and `newCommand`/`alternates.Env` perform no path validation, the resulting Git subprocess is launched with `GIT_ALTERNATE_OBJECT_DIRECTORIES` pointing outside the caller's own repository.
3. Objects from the other repository become readable through the accessor RPC's output, demonstrating cross-repository object access analogous to the tests in `internal/git/dirs_test.go` (`TestObjectDirsOutsideStorage`) that show the *file-based* alternates path is defended, while the *RPC field* path (`command_factory.go`) is not.

// Env returns the alternate object directory environment variables.
func Env(repoPath, objectDirectory string, alternateObjectDirectories []string) []string {
	var env []string
	if objectDirectory != "" {
		env = append(env, fmt.Sprintf("GIT_OBJECT_DIRECTORY=%s", filepath.Join(repoPath, objectDirectory)))
	}

	if len(alternateObjectDirectories) > 0 {
		var dirsList []string

		for _, dir := range alternateObjectDirectories {
			dirsList = append(dirsList, filepath.Join(repoPath, dir))
		}

		env = append(env, fmt.Sprintf("GIT_ALTERNATE_OBJECT_DIRECTORIES=%s", strings.Join(dirsList, ":")))
	}

	return env
}

func (repo *Repo) ObjectDirectoryPath(ctx context.Context) (string, error) {
	repoPath, err := repo.Path(ctx)
	if err != nil {
		return "", err
	}

	objectDirectoryPath := repo.GetGitObjectDirectory()
	if objectDirectoryPath == "" {
		return "", structerr.NewInvalidArgument("object directory path is not set")
	}

	storagePath, err := repo.locator.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return "", fmt.Errorf("get storage by name: %w", err)
	}

	// Ensure the path points somewhere in the storage.
	relativeObjectDirectoryPath, err := storage.ValidateRelativePath(storagePath, filepath.Join(repoPath, objectDirectoryPath))
	if err != nil {
		return "", structerr.NewInvalidArgument("validate relative path: %w", err)
	}
