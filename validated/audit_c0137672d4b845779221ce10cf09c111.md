### Title
Fixed-Window Stream Throttle Allows QoS Evasion via Burst-Timing Around Window Boundary - (File: `streamer/src/nonblocking/stream_throttle.rs`)

### Summary
The QUIC stream throttle (`throttle_stream` / `ConnectionStreamCounter::reset_throttling_params_if_needed`) enforces "N streams per `STREAM_THROTTLING_INTERVAL`" using a **fixed, non-overlapping counting window** rather than continuous, time-proportional accrual. Because the counter is fully reset to `0` the instant the interval elapses (with no scaling or carry-over based on how much of the window was actually used), a client can concentrate `max_streams_per_throttling_interval` streams at the very end of one window and another full batch immediately after the reset at the start of the next window — achieving up to ~2x the intended sustained stream rate in a much shorter real time span. This mirrors the reported bug class: the rate-control mechanism's outcome depends on the *timing/pattern* of requests relative to arbitrary window boundaries rather than being strictly proportional to elapsed wall-clock time.

### Finding Description
`ConnectionStreamCounter::reset_throttling_params_if_needed` [1](#0-0)  resets `stream_count` to `0` and reassigns `last_throttling_instant = now()` as soon as `now - last_throttling_instant > STREAM_THROTTLING_INTERVAL` (100 ms). `throttle_stream` then only sleeps if the count within the *current* fixed window reaches `max_streams_per_throttling_interval` [2](#0-1) .

This is a discrete fixed-window counter, not a token-bucket or sliding-window limiter (contrast with `TokenBucket::update_state`, which correctly scales minted tokens by exact elapsed microseconds [3](#0-2) ). Because the window reset is a hard boundary with no accounting for how the allowed budget should be prorated across overlapping time spans, a peer can:
1. Open a stream burst of `max_streams_per_throttling_interval` streams just before a window boundary.
2. Immediately after the reset (which can occur on the very next stream), open another full burst of `max_streams_per_throttling_interval` streams.

The two bursts can land within a real elapsed time much smaller than `2 × STREAM_THROTTLING_INTERVAL`, so the observed throughput is not proportional to elapsed time — exactly the class of defect described in the reference report (an accrual/consumption mechanism accepting per-interval quotas without scaling by actual elapsed time, making the aggregate outcome depend on request timing/frequency rather than solely on time and quota).

This throttle is invoked per QUIC connection via `SwQos::on_new_stream` in `swqos.rs` for both staked and unstaked peers [4](#0-3) , so it is directly reachable by any unprivileged remote peer that can open a QUIC connection to the TPU streamer — no validator/operator role is required.

### Impact Explanation
This allows an unprivileged peer to evade the intended per-connection QoS/stream-rate cap by roughly 2x through simple timing of stream creation around the fixed 100 ms window boundary. Since `max_streams_per_throttling_interval` is derived from stake-weighted budget allocation via `StakedStreamLoadEMA::available_load_capacity_in_throttling_duration` [5](#0-4) , this weakens the fairness/QoS guarantees the mechanism is meant to provide (protecting shared streamer/banking-stage resources from a single connection consuming disproportionate stream-processing capacity), qualifying as a QoS evasion.

### Likelihood Explanation
High likelihood of triggering: any remote client establishing a QUIC connection to the TPU streamer can control exactly when it opens new unidirectional streams, making the boundary-straddling burst pattern trivial to execute deterministically and repeatably, requiring no special privileges, stake, or race-condition luck beyond normal client-side timing control.

### Recommendation
Replace the fixed-window reset counter with a token-bucket style continuous refill (as already implemented correctly in `TokenBucket`/`update_state`, `net-utils/src/token_bucket.rs`) or a sliding-window algorithm that prorates the allowed stream budget by the exact elapsed time since the last stream, eliminating the boundary-doubling effect. Add unit/integration tests asserting that stream throughput over `2 × STREAM_THROTTLING_INTERVAL` never exceeds `2 × max_streams_per_throttling_interval` regardless of burst timing relative to window boundaries.

### Proof of Concept
1. Establish a QUIC connection as a staked or unstaked peer to the TPU streamer, obtaining `max_streams_per_throttling_interval` = `N` from `SwQos::max_streams_per_throttling_interval`.
2. At time `t0`, open `N` unidirectional streams in rapid succession — `throttle_stream` allows all `N` because they land within the current window (`stream_count` starts at 0, increments to `N`).
3. Wait until just past `t0 + STREAM_THROTTLING_INTERVAL` (100 ms) so that the next call to `reset_throttling_params_if_needed` observes `now - last_throttling_instant > STREAM_THROTTLING_INTERVAL` and resets `stream_count` to `0` [6](#0-5) .
4. Immediately open another `N` streams — they are all allowed since the counter was just reset.
5. Net effect: `2N` streams delivered in slightly more than `STREAM_THROTTLING_INTERVAL` (~100 ms) real time, i.e., double the intended sustained rate of `N` streams per `100 ms`, with no throttling sleep triggered in either burst.

    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }

    /// Updates internal state of the bucket by
    /// depositing new tokens (if appropriate)
    fn update_state(&self, now: u64) {
        // fetch last update time
        let last = self.last_update.load(Ordering::SeqCst);

        // If time has not advanced, nothing to do.
        if now <= last {
            return;
        }

        // Try to claim the interval [last, now].
        // If we can not claim it, someone else will claim [last..some other time] when they
        // touch the bucket.
        // If we can claim interval [last, now], no other thread can credit tokens for it anymore.
        // If [last, now] is too short to mint any tokens, spare time will be preserved in credit_time_us.
        match self.last_update.compare_exchange(
            last,
            now,
            Ordering::AcqRel,  // winner publishes new timestamp
            Ordering::Acquire, // loser observes updates
        ) {
            Ok(_) => {
                // This thread won the race and is responsible for minting tokens
                let elapsed = now.saturating_sub(last);

                // also add leftovers from previous conversion attempts.
                // we do not care about who uses the spare_time_us, so relaxed is ok here.
                let elapsed =
                    elapsed.saturating_add(self.credit_time_us.swap(0, Ordering::Relaxed));

                let new_tokens_f64 = elapsed as f64 * self.new_tokens_per_us;

                // amount of full tokens to be minted
                let new_tokens = new_tokens_f64.floor() as u64;

                let time_to_return = if new_tokens >= 1 {
                    // Credit tokens, saturating at max_tokens
                    self.add_tokens(new_tokens);
                    // Fractional remainder of elapsed time (not enough to mint a whole token)
                    // that will be credited to other minters
                    (new_tokens_f64.fract() / self.new_tokens_per_us) as u64
                } else {
                    // No whole tokens minted → return whole interval
                    elapsed
                };
