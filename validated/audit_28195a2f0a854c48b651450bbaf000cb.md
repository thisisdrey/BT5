### Title
Duplicate `data_id` entries in `ActionReceipt::input_data_ids` cause `PendingDataCount` to never reach zero, permanently postponing the receipt and freezing its attached balance - (File: runtime/runtime/src/lib.rs)

### Summary
`Runtime::process_receipt`'s `Data` arm decrements `PendingDataCount` by exactly one for each distinct `Data` receipt received, keyed only by `data_id` [1](#0-0) . If an `ActionReceipt`'s `input_data_ids` list contains the same `data_id` more than once, the postponement bookkeeping counts each occurrence toward `pending_data_count`, but only a single physical `Data` receipt for that `data_id` will ever be produced by the sending shard, so the counter can never reach zero and the receipt (along with the balance/gas it holds) is stuck in state forever.

### Finding Description
When a receipt is postponed because some of its `input_data_ids` are not yet resolved, the runtime records a `PostponedReceiptId` entry per unresolved `data_id` and a `PendingDataCount` equal to the number of unresolved entries in the `input_data_ids` list. The decrement path in `process_receipt`'s `Data` arm only fires once per unique `data_id` that is received - it looks up `TrieKey::PostponedReceiptId { receiver_id, data_id }`, removes it, and decrements `PendingDataCount` by 1 [2](#0-1) . Because `data_id`s are unique identifiers of a single promise-dependency output, exactly one `Data` receipt is ever generated for a given `data_id`. If an attacker's contract constructs a promise/`ActionReceipt` whose `input_data_ids` contains a duplicate entry for the same `data_id` (e.g., by joining the same promise index twice via the promise API), the initial postponement bookkeeping will set `pending_data_count = 2` for that single `data_id` dependency, but only one `Data` receipt will ever arrive to decrement it. The count is checked with `pending_data_count == 1` to finalize execution and otherwise just written back with `checked_sub(1)` [3](#0-2) , so it settles at `1` and is never removed, permanently parking the postponed `ActionReceipt` (and any attached deposit) in state.

I was not able to fully verify the exact initialization code in `apply_action_receipt` that computes `pending_data_count` from `action_receipt.input_data_ids()` within the tool budget available, nor confirm whether `validate_action_receipt` in `runtime/runtime/src/verifier.rs` rejects duplicate `data_id` entries in `input_data_ids` at admission time. The `validate_receipt` function visible at [4](#0-3)  dispatches to `validate_action_receipt` for `Action`/`PromiseYield` receipts, but the body of that function (and any dedup check) was not retrieved before the tool budget was exhausted.

### Impact Explanation
If confirmed, this would permanently freeze the balance/gas attached to the stuck postponed receipt, matching the "permanent freezing of user funds" bounty category. The severity depends on whether the promise-joining host functions actually allow a contract to produce duplicate `data_id`s in a single `input_data_ids` list, and whether `validate_action_receipt` already rejects such receipts at admission - both of which I could not conclusively verify.

### Likelihood Explanation
Uncertain. This requires (1) confirming that NEAR's promise API (e.g., `promise_and`/`promise_batch_then` composition) allows an unprivileged contract to construct a promise with a duplicated dependency on the exact same `data_id`, and (2) confirming that `validate_action_receipt` does not already reject such duplicate `input_data_ids`. Without inspecting both of these code paths directly, likelihood cannot be established with confidence.

### Recommendation
Deduplicate `input_data_ids` when computing `pending_data_count` during receipt postponement (count unique `data_id`s, not list length), and/or reject `ActionReceipt`s with duplicate `data_id` entries in `input_data_ids` during `validate_action_receipt`/`validate_receipt` admission checks.

### Proof of Concept
Add a unit test in `runtime/runtime/src/tests/apply.rs` that constructs an `ActionReceipt` with `input_data_ids = [X, X]` targeting a receiver, submits it so it is postponed, then delivers a single `Receipt::Data` receipt for `X`. Assert whether the postponed receipt executes (would indicate special-case handling exists) or remains permanently in `PostponedReceiptId`/`PendingDataCount` state (confirming the freeze). Cross-check by also asserting whether `validate_receipt`/`validate_action_receipt` rejects the receipt construction with duplicate `input_data_ids` before it reaches `process_receipt`.

**Note:** Due to incomplete exploration (tool budget exhausted before retrieving the `apply_action_receipt` postponement-initialization code and the body of `validate_action_receipt`), this finding cannot be fully confirmed as reachable/exploitable versus already mitigated. I recommend verifying these two code paths directly (or via a Devin session with full repo access) before treating this as a confirmed vulnerability.

pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

    // We retain these checks here as to maintain backwards compatibility
    // with AccountId validation since we illegally parse an AccountId
    // in near-vm-logic/logic.rs#fn(VMLogic::read_and_parse_account_id)
    AccountId::validate(receipt.predecessor_id().as_ref()).map_err(|_| {
        ReceiptValidationError::InvalidPredecessorId {
            account_id: receipt.predecessor_id().to_string(),
        }
    })?;
    AccountId::validate(receipt.receiver_id().as_ref()).map_err(|_| {
        ReceiptValidationError::InvalidReceiverId { account_id: receipt.receiver_id().to_string() }
    })?;

    match receipt.versioned_receipt() {
        VersionedReceiptEnum::Action(action_receipt)
        | VersionedReceiptEnum::PromiseYield(action_receipt) => validate_action_receipt(
            limit_config,
            action_receipt,
            receipt.receiver_id(),
            current_protocol_version,
            mode,
        ),
        VersionedReceiptEnum::Data(data_receipt)
        | VersionedReceiptEnum::PromiseResume(data_receipt) => {
            validate_data_receipt(limit_config, &data_receipt)
        }
        VersionedReceiptEnum::GlobalContractDistribution(_) => Ok(()), // Distribution receipt can't be issued without a valid contract
    }
