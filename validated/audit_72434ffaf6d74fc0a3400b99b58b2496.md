### Title
Unbounded array allocation from attacker-controlled length word in TVM signature precompiles (`ValidateMultiSign`/`BatchValidateSign`) - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.extractBytesArray`, `extractSigArray`, and `extractBytes32Array` read a 32-byte "length" word directly out of attacker-supplied EVM call data and immediately allocate a Java array sized by that raw value — `new byte[len][]` — before any bound is enforced against the amount of data actually present. This mirrors the hiredis/redis-cli bug class in the report: a length field taken from untrusted input is used to drive a heap allocation (`calloc`/`new`) without validating it against the real payload size first.

### Finding Description
`extractBytes32Array` has no size cap at all: [1](#0-0) 

`extractBytesArray` and `extractSigArray` likewise derive `len` straight from calldata and allocate before any validation: [2](#0-1) 

In `ValidateMultiSign.execute`, a `MAX_SIZE` pre-check on the declared array size only runs when the `allowTvmSelfdestructRestriction()` feature flag is active; when it is not, `extractBytesArray`/`extractSigArray` are invoked with the raw, unchecked `len`: [3](#0-2) 

`BatchValidateSign.doExecute` follows the same pattern for `signatures`, and unconditionally calls `extractBytes32Array` for `addresses` with **no size gate whatsoever**, regardless of the feature flag: [4](#0-3) 

Energy cost for these precompiles is computed from the actual `data.length` of the call, not from the attacker-declared array-length word: [5](#0-4) 

This means a caller can submit a small, cheap calldata blob (a handful of 32-byte words) where one word — interpreted as the array-length field — is set to a very large value (e.g., near `Integer.MAX_VALUE`, subject to `intValueSafe()` clamping). The resulting `new byte[len][]` allocation attempts to create an array of object references sized by that huge value, which can trigger a large, disproportionate memory allocation attempt relative to the tiny amount of energy actually charged and the tiny amount of real call data supplied.

### Impact Explanation
The allocation size is driven entirely by attacker-controlled call data, while the energy fee charged for the call is based on the small on-wire calldata size, not the declared array length. This creates an asymmetric cost model: a cheap, small transaction can force the executing node to attempt a very large heap allocation. `BatchValidateSign.execute` wraps the call in a catch-`Throwable`, so a resulting `OutOfMemoryError` there is caught and does not crash that call path directly, but the JVM-wide GC pressure and large transient allocation attempt it causes affects the whole node process (shared heap across all concurrently executing transactions/block application in `Manager`). `ValidateMultiSign.execute`, by contrast, calls `extractBytesArray`/`extractSigArray` **outside** any try/catch, so an `OutOfMemoryError` or `ArrayIndexOutOfBoundsException` raised there is not locally contained and propagates out of `execute()` into the TVM call dispatch path.

### Likelihood Explanation
Reachable by any unprivileged account: `ValidateMultiSign` and `BatchValidateSign` are precompiled contracts callable via a normal `CALL`/`STATICCALL` from any smart contract or directly as a `TriggerSmartContract` transaction, requiring only enough energy to cover the base `getEnergyForData` cost (which, as shown, does not scale with the attacker's declared array length). Whether the vulnerable code path is reachable in the current network state depends on whether the `allowTvmSelfdestructRestriction` hard-fork/dynamic-parameter is active; for `ValidateMultiSign`/the sig-array branches, activation of that flag adds a `MAX_SIZE` pre-check that mitigates the issue, but `extractBytes32Array` (used for the `addresses` array in `BatchValidateSign`) is never gated by that check in any configuration I could confirm from the available code. I was not able to determine, within the indexed code, the default/activation status of `allowTvmSelfdestructRestriction` on the target chain, so this should be verified against `DynamicPropertiesStore`/`ProposalUtil` before treating this as exploitable on a live, fully-upgraded mainnet.

### Recommendation
- In `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`, validate the declared `len` against a hard maximum (e.g., the existing `MAX_SIZE` constants) and against the actual remaining `words`/`data` length *before* allocating the array, unconditionally (not only under a feature flag).
- Wrap the array-extraction calls in `ValidateMultiSign.execute` in the same try/catch used for the rest of the method so unexpected allocation failures degrade to `DATA_FALSE` instead of propagating uncaught.
- Ensure `getEnergyForData` cannot be gamed to be cheap while the actual work/allocation performed by `execute` is unbounded.

### Proof of Concept
1. Construct a `TriggerSmartContract` transaction (or an internal `CALL`) targeting the `BatchValidateSign` precompile address with minimal calldata: header words (`hash`, `sigOffset`, `addrOffset`, ...), where the word at `addrOffset` (interpreted as `addrArraySize`/`len` in `extractBytes32Array`) is set to a large value such as `0x7FFFFFFF`.
2. If `allowTvmSelfdestructRestriction()` is not active for the current chain state, the `addrArraySize > MAX_SIZE` guard is skipped entirely, and `extractBytes32Array(words, offset)` executes `new byte[0x7FFFFFFF][]` directly.
3. Observe attempted large heap allocation / `OutOfMemoryError` while the actual call data submitted is a few hundred bytes and the energy charged (per `getEnergyForData`) is minimal, producing a disproportionate resource-exhaustion effect versus the cost paid by the caller.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }

      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }
