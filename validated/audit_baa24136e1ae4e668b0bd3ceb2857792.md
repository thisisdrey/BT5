### Title
`ValidateMultiSign` TVM precompile omits `PermissionType` check present in the native tx path, letting non-`Active` permission keys (e.g. Witness) satisfy contract-level multisig authorization - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` precompiled contract, reachable by any deployed smart contract via a plain `STATICCALL`/`CALL`, authenticates a signer set purely by resolving `account.getPermissionById(permissionId)` and checking accumulated `weight >= threshold`. It never validates `permission.getType()`. Every other authorization surface in java-tron that resolves a permission by id enforces that a non-zero `permissionId` must resolve to a `PermissionType.Active` permission before accepting it as a valid authorization role. This is the same class of bug as the reported TLS issue: an entity presents credentials that are cryptographically valid and chain to a trusted root/account, but whose declared "role" (KeyUsage/EKU there, `PermissionType` here) does not authorize the action being gated, and the verifier fails to check that role field.

### Finding Description
`TransactionCapsule.checkPermission` (the native transaction authorization gate used by `validateSignature`, `addSign`, `Wallet.getTransactionApprovedList`, and `TransactionUtil.getTransactionSignWeight`) explicitly requires: [1](#0-0) 

This mirrors `AccountPermissionUpdateActuator.checkPermission`, which shows that only `PermissionType.Active` permissions may carry an `operations` bitmap restricting which contract types the key is authorized for; `Owner` and `Witness` permissions are role-scoped in a fundamentally different way (full account control vs. block-signing only) and cannot carry such restrictions: [2](#0-1) 

In contrast, the `ValidateMultiSign` TVM precompile — invocable from any deployed contract as a general-purpose "is this signer set authorized for this account+permissionId" oracle for custom dApp access control — resolves the permission and checks only weight/threshold, never the type: [3](#0-2) 

A smart contract author who builds role-gated logic (e.g., "only keys under this account's operator/Active permission, restricted by its `operations` bitmap to a specific set of native contract types, may approve this dApp action") using `ValidateMultiSign(address, permissionId, data, sigs)` receives no signal from the precompile about whether the resolved `permissionId` is actually `Active`-typed. An attacker who controls the account's `Witness` permission key (id 1, intended solely for SR block-production identity, not for arbitrary application-level authorization) can pass `permissionId=1` and have their signature accepted by any contract that trusts the precompile's boolean result as proof of "authorized operator," exactly as the serverAuth-only certificate is wrongly accepted as proof of "authorized client" because the verifier never inspects EKU.

### Impact Explanation
Any smart contract that uses `ValidateMultiSign` as an access-control primitive keyed by attacker- or account-supplied `permissionId` (a documented, encouraged usage pattern for TRON's native multisig precompile) can be tricked into authorizing an action based on a key held under a permission role never intended for that purpose. Because `Witness`-type permissions are single-key and separately managed from `Active` permissions, and are not subject to the `operations` contract-type restriction that governs what an `Active` key may approve, this allows unauthorized account operations/fund movement within any contract-level multisig or guardian scheme relying on this precompile, without compromising any private key outside its intended scope.

### Likelihood Explanation
Reaching this path only requires deploying or calling into a contract that uses the `ValidateMultiSign` precompile with attacker-influenced `permissionId` — a standard, publicly documented usage pattern for building on-chain multisig/authorization logic on TRON. No special privileges are needed beyond normal contract deployment/interaction, and the omitted type check is a pure logic gap, not a probabilistic condition.

### Recommendation
In `PrecompiledContracts.ValidateMultiSign.execute` (and the analogous `BatchValidateSign` if it resolves permissions), after `account.getPermissionById(permissionId)`, reject unless `permission.getType() == PermissionType.Active` (mirroring `TransactionCapsule.checkPermission`), or otherwise clearly document/enforce that callers must not treat any non-`Active` permission id as equivalent authorization for TVM-level multisig gating.

### Proof of Concept
1. Account `A` configures an `Active` permission (id=2) with `operations` scoped to authorize only a narrow set of native contract types, intended as the sole "operator" role for a deployed dApp's multisig guardian check.
2. Account `A` separately holds a `Witness` permission (id=1) with a single key, used only for SR block signing, per `AccountPermissionUpdateActuator.checkPermission`'s type-specific rules. [4](#0-3) 
3. A contract deployed by anyone calls `ValidateMultiSign(A, 1, data, [sig_by_witness_key])` expecting to gate an action to "authorized Active operator" role holders.
4. `ValidateMultiSign` resolves `permission = account.getPermissionById(1)` (the Witness permission), computes `totalWeight` from the witness key's signature, and returns `true` once `totalWeight >= permission.getThreshold()` — without ever checking `permission.getType()`: [5](#0-4) 
5. The witness-only key is accepted as a valid multisig approver by the contract, despite never having been granted that role under the account's `Active`/`operations`-scoped permission model.
