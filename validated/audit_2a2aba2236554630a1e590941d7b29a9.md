### Title
Cross-Shard Dependency Deadlock on Transaction Abort — (`aptos-move/aptos-vm/src/sharded_block_executor/cross_shard_client.rs`)

---

### Summary

`CrossShardCommitSender` only sends `RemoteTxnWriteMsg` for keys present in a committed transaction's **write set**. When a transaction with cross-shard dependent edges commits with a failed output (Move abort, gas exhaustion), the cross-shard key is absent from the write set. The dependent shard's `CrossShardStateView` entry for that key remains in `RemoteValueStatus::Waiting` forever, blocking the dependent shard's execution thread on a condvar that is never notified, while the `CrossShardCommitReceiver` thread is simultaneously blocked on a channel that never receives a message. Both threads in the rayon scope are permanently wedged.

---

### Finding Description

**Step 1 — Hook interface has no abort callback.**

`TransactionCommitHook` exposes only `on_transaction_committed`. There is no `on_transaction_aborted`. [1](#0-0) 

**Step 2 — `CrossShardCommitSender` implements only the success path.**

`on_transaction_committed` calls `send_remote_update_for_success`, which iterates exclusively over the committed output's write set. For a failed transaction (Move abort, gas exhaustion), the write set contains only gas-charge writes to the sender's account — the cross-shard key K is absent. [2](#0-1) [3](#0-2) 

Because K is not in the write set, no `RemoteTxnWriteMsg` is ever sent to the dependent shard for K. The comment in `messages.rs` (`// The write op is None if the transaction is aborted`) confirms the design intended to send `RemoteTxnWriteMsg(None)` for aborted transactions, but no code path ever does so. [4](#0-3) 

**Step 3 — Dependent shard's `CrossShardStateView` blocks forever.**

`create_cross_shard_state_view` inserts every required cross-shard key as `RemoteStateValue::Waiting`. `get_value()` spins on a `Condvar` until `set_value()` is called. `set_value()` is only called by `CrossShardCommitReceiver::start` upon receiving a `RemoteTxnWriteMsg`. [5](#0-4) [6](#0-5) 

**Step 4 — The two rayon threads in the dependent shard deadlock each other.**

`execute_transactions_with_dependencies` spawns two tasks in a rayon scope:

- **Thread A** (`CrossShardCommitReceiver::start`): loops on `receive_cross_shard_msg`, which blocks on a channel `recv()`. It will only exit on `StopMsg`.
- **Thread B** (`execute_block`): executes transactions; when transaction B reads key K it blocks on the condvar in `get_state_value`. After `execute_block` finishes it sends `StopMsg` to its own shard's receiver. [7](#0-6) 

Thread B never finishes (blocked on condvar for K), so it never sends `StopMsg` to Thread A. Thread A never receives a `RemoteTxnWriteMsg` for K (shard-0 never sent one), so it never calls `set_value` to unblock Thread B. The rayon scope never completes. The shard thread is permanently wedged.

---

### Impact Explanation

If sharded block execution is active, a single crafted transaction that (a) is assigned a cross-shard dependent edge by the partitioner and (b) fails at runtime (gas exhaustion or Move abort) permanently deadlocks the dependent shard's rayon scope. All subsequent sub-blocks for that shard — and therefore all user transactions assigned to it — are permanently blocked. No fund movement or state transition can occur on the affected shard for the lifetime of the process.

---

### Likelihood Explanation

Any transaction that touches a key shared across shards and then runs out of gas or hits a Move abort triggers this. Gas exhaustion is trivially achievable by any user (set `max_gas_amount` to a value just below what the transaction actually consumes). The partitioner, not the user, assigns cross-shard edges, but the partitioner does so deterministically based on read/write sets, which a user can influence by choosing which keys to access.

---

### Recommendation

In `CrossShardCommitSender::on_transaction_committed`, after calling `send_remote_update_for_success`, iterate over all entries in `dependent_edges[global_txn_idx]` and send `RemoteTxnWriteMsg(RemoteTxnWrite::new(state_key, None))` for every key that was **not** present in the committed write set. This matches the documented intent of the `write_op: Option<WriteOp>` field (`None` = aborted/not written).

Alternatively, add an `on_transaction_aborted` method to `TransactionCommitHook` and call it from the block executor for every transaction that commits with a non-success status, sending `RemoteTxnWriteMsg(None)` for all its dependent edges.

```

  - Two shards (shard-0, shard-1), one round.
  - Shard-0 sub-block: txn A writes key K, has dependent edge → shard-1 txn B on K.
  - Shard-1 sub-block: txn B reads key K (required edge from shard-0 txn A).
  - Txn A is given max_gas_amount = 1 (guaranteed gas exhaustion).

Expected (correct) behavior:
  - Shard-0 commits txn A with failed output; sends RemoteTxnWriteMsg(None) for K to shard-1.
  - Shard-1 receives the message, sets K = None, txn B proceeds.

Actual behavior:
  - Shard-0 commits txn A; send_remote_update_for_success iterates write set → K absent → no message sent.
  - Shard-1 CrossShardCommitReceiver blocks on recv() forever.
  - Shard-1 execute_block blocks on condvar for K forever.
  - Rayon scope never exits. Shard-1 thread permanently wedged.
  - Assert: shard-1 result channel never receives a value within a 5-second timeout → confirmed deadlock.
