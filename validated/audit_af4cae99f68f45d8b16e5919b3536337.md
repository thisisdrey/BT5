Confirmed: `do_purchase` in `substrate/frame/broker/src/dispatchable_impls.rs` computes the price from `RCBlockNumberProviderOf::<T::Coretime>::current_block_number()`, i.e. the relay chain block number, not the Coretime chain's own block counter. This is the exact analog to the Zeno bug: a Dutch-auction-style linear price decay keyed to an external "clock" that keeps advancing independently of whether the chain running the sale logic (the Coretime parachain) is actually able to process transactions.

### Title
Coretime sale price decays against relay-chain block number, letting `purchase`/`renew` clear cores at stale/underpriced levels after a Coretime-chain stall - (File: `substrate/frame/broker/src/dispatchable_impls.rs`)

### Summary
`pallet-broker`'s bulk-coretime Dutch auction (`sale_price`) linearly decreases price from `start_price` to `end_price` over `leadin_length`, using `now = RCBlockNumberProviderOf::<T::Coretime>::current_block_number()` [1](#0-0)  — the **relay chain** block number, not the local Coretime-chain block number. `do_purchase` uses this same clock to gate `TooEarly` and to compute the price a buyer pays [2](#0-1) . Because the relay chain keeps producing blocks independently of the Coretime parachain's own liveness, any period during which the Coretime chain cannot include extrinsics (congestion, collator unavailability, backing/networking issues) still "spends" leadin blocks on the relay-chain clock. This mirrors the reported Zeno issue: an external, uncontrollable clock keeps advancing the auction's price curve while the venue itself is unable to execute trades.

### Finding Description
The leadin price is `T::PriceAdapter::leadin_factor_at(through) * end_price`, where `through = (now - sale_start).min(leadin_length) / leadin_length` and `now` comes from `RelaychainDataProvider<Runtime>::current_block_number()` on the Coretime chain (via `CoretimeAllocator::RelayChainBlockNumberProvider`) [3](#0-2) . That provider reads `ValidationData::<T>::relay_parent_number`, falling back to a cached `last_relay_block_number()` when unavailable [4](#0-3) . In either case the value tracks the relay chain's own progress, which is unaffected by whether the Coretime parachain is itself able to build/include blocks.

If the Coretime chain stalls for a stretch of relay-chain blocks (e.g. due to collator/networking problems, or a backlog that prevents block authoring) while the relay chain continues to finalize blocks normally, `sale.sale_start` stays fixed but `now` keeps climbing. When the chain resumes, the very first `purchase`/`renew` call sees `now` already far past (or at) `sale.sale_start + leadin_length`, so `sale_price` has already decayed to (or near) `end_price` regardless of how many parachain blocks were actually available for competing bids during the leadin window [1](#0-0) . `do_purchase`'s only checks are `now > sale.sale_start` (`TooEarly`) and `price_limit >= price` (`Overpriced`) [5](#0-4)  — there is no check that the local chain was actually live and accepting bids throughout the leadin period, and no floor tied to elapsed *parachain* time or number of parachain blocks produced during the leadin.

### Impact Explanation
An unprivileged, ordinary signed account can capture Bulk Coretime cores at the auction's reserve/`end_price` (or a price far below what the intended leadin curve would have produced under normal liveness) simply by being the first to submit `purchase` once the chain resumes after a stall, transferring protocol revenue loss from the Coretime sale to that buyer. This is public underpriced work with direct chain/bridge-scale financial impact matching the "public underpriced work that degrades block production or stalls bridge processing" and "theft or unbacked mint/unlock"-adjacent impact classes, without requiring any admin, governance, validator, or relayer misbehavior — only ordinary network/liveness conditions on the executing chain.

### Likelihood Explanation
Requires the Coretime parachain to experience a liveness gap relative to the relay chain (congestion, collator downtime, or any period where block production/inclusion stalls) that spans a meaningful fraction of the `leadin_length` window, which is a plausible operational condition for any Substrate parachain and does not require a malicious actor to trigger — an attacker only needs to be the first to submit `purchase`/`renew` once the chain recovers.

### Recommendation
Do not key the leadin decay purely to the relay-chain clock. Either (a) also track and cap elapsed leadin progress by the number of local (Coretime-chain) blocks actually produced/observed since `sale_start`, so a relay-clock jump during a local stall cannot advance the price curve faster than real local liveness allows, or (b) detect abnormal relay-vs-local block-number divergence at the start of a block and pause/extend the sale (shift `sale_start`/`leadin_length`) by the stalled amount before allowing `purchase`/`renew` to price against `now`.

### Proof of Concept
1. Start a bulk coretime sale via `start_sales`, establishing `sale.sale_start` and `leadin_length` in relay-chain block units [6](#0-5) .
2. Simulate a Coretime-chain liveness stall: relay chain block production continues, but the Coretime chain does not include any extrinsics for a span of relay blocks approaching `leadin_length` (e.g., via `RelaychainDataProvider::set_block_number` advancing far ahead while no `purchase` extrinsics land, as exercised in test helpers such as `advance_to` in `substrate/frame/broker/src/tests.rs`).
3. Once the Coretime chain resumes, call `purchase(price_limit = end_price)` as any signed account. Per `do_purchase`, `now` already exceeds `sale.sale_start + leadin_length`, so `Self::sale_price` returns `end_price` [7](#0-6) , letting the caller acquire the core at the fully-decayed reserve price despite no genuine competitive bidding having occurred during the (stalled) leadin window.

```rust
	pub fn sale_price(sale: &SaleInfoRecordOf<T>, now: RelayBlockNumberOf<T>) -> BalanceOf<T> {
		let num = now.saturating_sub(sale.sale_start).min(sale.leadin_length).saturated_into();
		let through = FixedU64::from_rational(num, sale.leadin_length.saturated_into());
		T::PriceAdapter::leadin_factor_at(through).saturating_mul_int(sale.end_price)
	}
```

```rust
	pub(crate) fn do_purchase(
		who: T::AccountId,
		price_limit: BalanceOf<T>,
	) -> Result<RegionId, DispatchError> {
		let status = Status::<T>::get().ok_or(Error::<T>::Uninitialized)?;
		let mut sale = SaleInfo::<T>::get().ok_or(Error::<T>::NoSales)?;
		Self::ensure_cores_for_sale(&status, &sale)?;

		let now = RCBlockNumberProviderOf::<T::Coretime>::current_block_number();
		ensure!(now > sale.sale_start, Error::<T>::TooEarly);
		let price = Self::sale_price(&sale, now);
		ensure!(price_limit >= price, Error::<T>::Overpriced);

		let core = Self::purchase_core(&who, price, &mut sale)?;
```
