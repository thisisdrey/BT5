### Title
Shared static singleton PrecompiledContract instances hold mutable per-call context that is set without save/restore, permitting cross-execution state confusion under concurrent VM calls - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The libxslt advisory describes a use-after-free class of bug where a shared XPath evaluation context node is mutated during a nested evaluation and never restored, so a later use of that context observes stale/incorrect state. java-tron's TVM precompiled-contract dispatch has the same structural weakness: every precompiled contract (`ecRecover`, `sha256`, `batchValidateSign`, `validateMultiSign`, `rewardBalance`, `isSrCandidate`, `voteCount`, the FreezeV2 precompiles, etc.) is instantiated **once** as a `private static final` singleton [1](#0-0) , yet each invocation mutates instance state on that same shared object (`setCallerAddress`, `setRepository`, `setResult`, `setConstantCall`) immediately before calling `execute(data)` [2](#0-1) . Nothing saves the previous caller/repository/result context before overwriting it and nothing restores it afterward.

### Finding Description
`Program.callToPrecompiledAddress` resolves the target precompile once per `CALL`/`STATICCALL`/`DELEGATECALL` via `PrecompiledContracts.getContractForAddress`, then directly overwrites the singleton's caller address, repository (the per-call `Repository` deposit backing all state reads/writes for that invocation), result object, and constant-call flag before running `execute(data)`: [3](#0-2) 

Because the target object is a `static final` field shared process-wide, this is exactly the "nested-context-mutated-but-never-restored" pattern from the libxslt advisory: any second execution path that reaches the same precompiled contract instance while the first has not yet returned will clobber `repository`/`callerAddress`/`result` mid-flight. The comment in `Wallet.callConstantContract` explicitly acknowledges that constant calls execute "on a pooled RPC worker" thread and that VM-related thread-local state must be scrubbed to avoid leaking across executions on the same thread [4](#0-3)  — but that mitigation only clears `VMConfig`'s thread-local snapshot, not the mutable fields on the shared `PrecompiledContracts` singletons, which are ordinary (non-thread-local, non-synchronized) instance fields.

### Impact Explanation
If two VM executions (e.g., two constant-call/JSON-RPC queries served concurrently by different pooled worker threads, or a top-level transaction and a re-entrant internal call inside the same batch-processing pipeline) both invoke the same precompiled address (for example `RewardBalance`, `VoteCount`, `IsSrCandidate`, or one of the `FreezeV2` resource precompiles that read/write account, vote, or delegation data through the injected `Repository`), one execution's `setRepository`/`setCallerAddress` call can overwrite the context that the other execution is mid-way through using. This can cause a precompile to read or, for the resource/energy-related precompiles, act on the wrong account's `Repository` context — leading to information disclosure across unrelated transactions or, for precompiles that mutate state via the repository, corrupted account/vote/resource bookkeeping. This falls into the "unauthorized account operation" / "unbacked balance or accounting corruption" impact bucket.

### Likelihood Explanation
Exploitation likelihood depends on the concurrency model of transaction execution and constant-call servicing, which I could not fully verify within the available search budget — I found the explicit RPC/worker-pool comment confirming multi-threaded constant-call handling, but could not confirm (or rule out) whether ordinary block-application/transaction execution in `Manager`/`VMActuator` is single-threaded (which would make normal broadcast-transaction exploitation harder) versus whether concurrent constant calls alone are sufficient to trigger the race. I was also unable to locate any `synchronized` block or lock guarding the setter calls in `Program.callToPrecompiledAddress`, nor could I confirm the base `PrecompiledContract` class's field declarations due to a search/tooling limitation on this file. Given the confirmed pooled-thread execution of constant calls, an unprivileged API client issuing concurrent `TriggerConstantContract`/JSON-RPC `eth_call` requests against contracts that invoke the same precompile address appears to be a realistic trigger, but I cannot certify the practical race window or its observable effect without further investigation.

### Recommendation
Make precompiled-contract execution stateless with respect to per-call context: pass `callerAddress`, `repository`, `result`, and the constant-call flag as parameters to `execute(...)` (or construct a short-lived per-call wrapper/context object) rather than mutating shared singleton instance fields. If singleton reuse must be kept for performance, guard the mutate-then-execute-then-read-result sequence with proper synchronization or switch to `ThreadLocal`-scoped instances, and audit every implementation of `PrecompiledContract` for other mutable, non-reentrant instance state.

### Proof of Concept
I could not construct a concrete, verifiable proof-of-concept trigger within the current investigation because confirming actual concurrent invocation of the same precompiled contract instance (two constant calls or a top-level/internal call pair hitting, e.g., `RewardBalance` or `VoteCount` simultaneously) requires runtime/environment access (thread-timing control, multiple concurrent gRPC/JSON-RPC clients, or a debugger) that is outside the scope of static code search. This would need to be validated in a running node — recommend a Devin session with terminal/test-execution access to write a race-condition regression test (e.g., two threads simultaneously calling `Wallet.callConstantContract` against contracts that both invoke `RewardBalance`/`VoteCount`) and assert whether cross-thread `Repository` contamination is observable.
