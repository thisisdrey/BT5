## Title
Out-of-bounds heap read when parsing central directory entries in `ijar`'s ZIP reader — `third_party/ijar/zip.cc` (`InputZipFile::ProcessCentralDirEntry`)

## Summary
`InputZipFile::ProcessCentralDirEntry` — the routine that parses each ZIP central-directory record while `ijar`/`singlejar`/`unzip_bin` read a `.jar`/`.zip` file — reads all header fields (`compressed_size`, `uncompressed_size`, `file_name_length`, `extra_field_length`, `file_comment_length`, and the ZIP64 extra-field `header_id`/`data_size` pairs) with raw `get_u4le`/`get_u2le`/`get_u8le` calls and then advances the cursor `p` by these attacker-controlled lengths, without ever checking that `p` stays inside the mapped input file buffer.

## Finding Description
This is analogous to the SDL BMP bug class: a size/length value taken directly from untrusted file content is used to index/advance into a buffer without validating it against the buffer's actual bounds, producing an out-of-bounds heap read.

Contrast the two parsing paths in the same file:
- `ProcessLocalFileEntry` explicitly guards every field read with `EnsureRemaining(...)` before touching memory: [1](#0-0) 
- `ProcessCentralDirEntry`, which parses the *central directory* (the structure `FindZipCentralDirectory` locates and that `ProcessNext`/`CalculateOutputLength` iterate over), has **no equivalent bounds check** at all. It reads the fixed header, filename, extra field and comment length fields and blindly advances `p` by attacker-supplied `file_name_length`, `extra_field_length`, and `file_comment_length`: [2](#0-1) 

Worse, the ZIP64 extra-field walk inside the same function iterates `while (extra_p != p)`, advancing `extra_p` by an attacker-controlled `data_size` read from the (unbounded) buffer each iteration. If `data_size` doesn't land `extra_p` exactly back on `p`, the loop keeps reading `header_id`/`data_size` from arbitrary, ever-increasing heap offsets — with no ceiling check against the mapped file's end — producing an unbounded out-of-bounds heap read until a crash (or by chance re-syncing on unrelated heap bytes): [3](#0-2) 

The caller loop that drives this, `ProcessNext`/`ProcessAll`/`CalculateOutputLength`, has no additional validation either — it just keeps calling `ProcessCentralDirEntry(central_dir_current_, ...)` until the signature no longer matches: [4](#0-3) [5](#0-4) 

`FindZipCentralDirectory` does sanity-check that `central_dir_offset + central_dir_size <= in_length` before pointing `central_dir_` into the mmap'd file: [6](#0-5)  — but this only validates the *nominal* central-directory span from the End-Of-Central-Directory record; it does nothing to stop `ProcessCentralDirEntry`'s cursor `p` from walking past that span (or even past the mapped file entirely) once individual entry length fields are attacker-forged to be inconsistent with the declared central-directory size.

## Impact Explanation
`ijar` is Bazel's native C++ tool used to build interface jars from `.jar` inputs (and the `unzip_bin`/`zipper` tool built from the same `zip.cc`/`zip_main.cc`), which can be exercised on `.jar`/`.zip` archives originating from external, attacker-controlled sources (e.g. `http_jar`/`http_archive`-fetched dependencies, `java_import` targets, or files checked into an untrusted branch that CI builds). A crafted ZIP central directory can drive `ProcessCentralDirEntry` to read heap memory outside the `mmap`'d input file: at minimum this crashes the `ijar`/`unzip` process (denial of service for that build action); more seriously, out-of-bounds bytes are treated as further header fields (lengths, filenames, attributes) that get echoed back through `processor->Accept`/`processor->Process` and error strings, which is a classic heap-overread building-block that on some platforms/allocators can be escalated into information disclosure or further memory corruption, matching the class of bug in the referenced SDL BMP CVE (missing bounds validation on attacker-supplied structure lengths before dereferencing memory).

## Likelihood Explanation
Any dependency that is fetched as a `.jar`/`.zip` and processed by `ijar` (which is unconditionally invoked by Bazel's Java rules to produce interface jars, and by `zip_main`'s `unzip`/`zipper`) is reachable by an outsider who controls the archive bytes served at a dependency URL or committed in a repository that untrusted CI builds. No credentials, sandbox escape, or local machine access are required — only the ability to publish/serve a malicious `.jar`/`.zip`. The bug is in the always-executed central-directory parsing path (`ProcessNext`/`CalculateOutputLength`), not a rarely-hit corner case.

## Recommendation
Add the same `EnsureRemaining`-style bounds validation used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry` for every field read (fixed header, `file_name_length`, `extra_field_length`, `file_comment_length`, and each ZIP64 extra-field `header_id`/`data_size` pair), and bound the ZIP64 extra-field loop so `extra_p` can never advance past `p` or past the mapped file end.

## Proof of Concept
A `BuildIntegrationTestCase`/shell test (in the spirit of `src/test/shell/bazel/external_integration_test.sh`'s zip/jar tests) can:
1. Build a well-formed ZIP EOCD record (so `FindZipCentralDirectory` succeeds) pointing at a crafted central directory whose single entry declares `extra_field_length = 0xFFFF` and includes a ZIP64 extra-field `data_size` value engineered so that `extra_p` overshoots `p` inside `ProcessCentralDirEntry`'s `while (extra_p != p)` loop, with the buffer truncated shortly after.
2. Feed this file to the `ijar`/`unzip_bin` binary (e.g. via `java_import` consuming this `.jar`, or directly invoking `unzip_bin` on the crafted archive).
3. Observe a segmentation fault / ASan heap-buffer-overflow report from `InputZipFile::ProcessCentralDirEntry`, demonstrating the out-of-bounds heap read.

                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;

    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
