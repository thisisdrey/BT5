## Analog Found

### Title
Unsynchronized iteration over `pendingTransactions`/`rePushTransactions` races with concurrent mutation, risking `ConcurrentModificationException` during block application - ([File: framework/src/main/java/org/tron/core/db/Manager.java])

### Summary
The CVE fixes a missing RCU read-lock around `perf_iterate_ctx()`, which traverses an RCU list that can be concurrently mutated by another thread. The analogous pattern in java-tron is the traversal of `Manager.pendingTransactions` and `Manager.rePushTransactions` in `getTxFromPending()` / `getTxListFromPending()` — both reachable from unauthenticated HTTP endpoints — without any lock, while the same collections are mutated elsewhere under `synchronized (this)` (in `pushTransaction`) or unsynchronized (in `PendingManager.close()`), which runs on the block-application thread for every block.

### Finding Description
`Manager.pushTransaction()` adds to `pendingTransactions` only while holding the object's intrinsic lock: [1](#0-0) 

But the read paths that enumerate the same collections do not take any lock at all: [2](#0-1) 

These read paths (`getTxFromPending`, `getTxListFromPending`) are exposed directly to unauthenticated HTTP clients: [3](#0-2) 

On the write side, `PendingManager.close()` — invoked once per block during normal block application/pop-and-push cycles inside `Manager` — iterates and `clear()`s these same lists: [4](#0-3) 

This mirrors the structural root cause of CVE-2025-21889: a list that is concurrently mutated from one context (block application / transaction push, analogous to `perf_event_exec`'s mutation path) is traversed from another context (an API-facing read, analogous to `perf_iterate_ctx`'s reader) without any lock/guard protecting the traversal against concurrent structural modification.

### Impact Explanation
`ArrayList`-style fail-fast iterators throw `ConcurrentModificationException` when structurally modified during iteration. Because `PendingManager.close()` performs unsynchronized `clear()`/`add` on `pendingTransactions`/`rePushTransactions` on the block-application thread while an HTTP client concurrently calls `GetTransactionListFromPendingServlet`/`GetTransactionFromPendingServlet` (which call `getTxListFromPending`/`getTxFromPending` with no lock), a `ConcurrentModificationException` can be raised. If it surfaces in the block-application call stack (inside `PendingManager.close()`, which itself is not wrapped in a try/catch for this exception type), it can interrupt block application and degrade node availability; at minimum it reliably breaks the pending-transaction query API for any anonymous caller, matching the "node ... can no longer serve" API-availability criterion.

### Likelihood Explanation
Any anonymous client can repeatedly call `/wallet/gettransactionlistfrompending` or `/wallet/gettransactionfrompending` while the node is actively producing/processing blocks (which happens continuously and is externally triggerable by simply broadcasting transactions to keep the pending pool active). No privileged access or special timing precision beyond ordinary network request timing is required, making this readily triggerable, similar to how the kernel bug was hit by an ordinary unprivileged `perf probe`+`unshare` sequence.

### Recommendation
Wrap all reads and writes of `pendingTransactions` and `rePushTransactions` (and any other shared mutable collections exposed through `Manager`) in the same lock discipline — either use `synchronized` blocks consistently around both mutation and iteration (mirroring the `synchronized (this)` used in `pushTransaction`), or switch these fields to a `CopyOnWriteArrayList`/`Collections.synchronizedList` with defensive copy-then-iterate semantics, analogous to how `PeerManager` iterates over `new ArrayList<>(peers)` snapshots rather than the live list.

### Proof of Concept
1. Start a node and continuously broadcast transactions to keep `pendingTransactions`/`rePushTransactions` non-trivially populated across blocks.
2. Concurrently issue a tight loop of HTTP requests to `/wallet/gettransactionlistfrompending` (or `/wallet/gettransactionfrompending`).
3. As blocks are produced, `PendingManager.close()` runs on the block-application thread, calling `.clear()`/mutating `pendingTransactions`/`rePushTransactions` while the HTTP-serving thread's `forEach` traversal in `getTxListFromPending`/`getTxFromPending` is in flight, raising `ConcurrentModificationException` in one or both threads — reliably reproducible under sustained concurrent load since neither path takes a shared lock.

  public TransactionCapsule getTxFromPending(String txId) {
    AtomicReference<TransactionCapsule> transactionCapsule = new AtomicReference<>();
    Sha256Hash txHash = Sha256Hash.wrap(ByteArray.fromHexString(txId));
    pendingTransactions.forEach(tx -> {
      if (tx.getTransactionId().equals(txHash)) {
        transactionCapsule.set(tx);
        return;
      }
    });
    if (transactionCapsule.get() != null) {
      return transactionCapsule.get();
    }
    rePushTransactions.forEach(tx -> {
      if (tx.getTransactionId().equals(txHash)) {
        transactionCapsule.set(tx);
        return;
      }
    });
    return transactionCapsule.get();
  }

  public Collection<String> getTxListFromPending() {
    Set<String> result = new HashSet<>();
    pendingTransactions.forEach(tx -> {
      result.add(tx.getTransactionId().toString());
    });
    rePushTransactions.forEach(tx -> {
      result.add(tx.getTransactionId().toString());
    });
    return result;
  }
