### Title
Unbounded per-cycle reward computation loop in `MortgageService.withdrawReward`/`queryReward` can render withdrawal/vote/unfreeze transactions permanently unprocessable - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.withdrawReward()` and `queryReward()` compute a voter's accumulated reward by iterating cycle-by-cycle (and vote-by-vote) between the account's `beginCycle` and the current cycle, exactly mirroring the reported `_updateWithdrawalQueue` bug class: a synchronous, in-transaction loop whose length is controlled by "how long has it been since the last claim" rather than by any hard bound. For any account whose `beginCycle` still predates `newRewardAlgorithmEffectiveCycle` and `allowOldRewardOpt` is not enabled, `getOldReward()` walks every single cycle one at a time and, for every one of the account's votes, performs `DelegationStore` reads.

### Finding Description
`withdrawReward(address)` and `queryReward(address)` call `computeReward(beginCycle, endCycle, accountCapsule)`: [1](#0-0) 

When `beginCycle < newRewardAlgorithmEffectiveCycle`, the code falls back to the old, per-cycle algorithm via `getOldReward`, which explicitly loops `for (long cycle = begin; cycle < end; cycle++)` and, inside that loop, iterates over every vote the account has cast, doing a DB read per SR per cycle: [2](#0-1) [3](#0-2) 

There is no cap on `endCycle - beginCycle`: unlike the bounded loops elsewhere in the codebase (e.g. `UNFREEZE_MAX_TIMES = 32` in `UnfreezeBalanceV2Actuator`, or `MAX_VOTE_NUMBER` in `VoteWitnessProcessor`, or `MAX_MATCH_NUM` in `MarketSellAssetActuator.matchOrder`), this reward-catch-up loop is fully open-ended - the number of iterations grows linearly with the number of cycles (maintenance periods, occurring multiple times per day) that have elapsed since the account's last claim. `withdrawReward` is invoked unconditionally at the start of every `UnfreezeBalanceActuator.execute`, `UnfreezeBalanceV2Actuator.execute`, `VoteWitnessActuator.countVoteAccount`, and `WithdrawBalanceActuator.execute`: [4](#0-3) [5](#0-4) [6](#0-5) 

It is also reachable from smart contracts through the `WithdrawReward` TVM opcode, which invokes `VoteRewardUtil.withdrawReward`, whose logic mirrors `MortgageService`'s unbounded design pattern (though that specific variant does not fall back to a per-cycle loop, `MortgageService`'s legacy path does, and both are triggered by ordinary signed transactions from an unprivileged account): [7](#0-6) [8](#0-7) 

This is directly analogous to the reported `_updateWithdrawalQueue` issue: a single unprivileged action (any vote, freeze, unfreeze, or withdraw transaction) triggers processing of an ever-growing backlog (elapsed cycles) entirely within one transaction, with no per-call limit on how much of the backlog is processed.

### Impact Explanation
Because a normal account never needs to interact with the chain to accumulate a backlog (cycles/maintenance periods elapse automatically over time), any voter who abstains from claiming rewards for a sufficiently long period accumulates a `beginCycle` to `endCycle` gap that keeps growing. When that account (or anyone acting on its behalf, e.g. by sending it a transaction that triggers `withdrawReward`, such as `UnfreezeBalance`/`VoteWitness`/`WithdrawBalance`) finally interacts again, the node must execute the entire unbounded cycle loop synchronously inside actuator execution/block application. If the elapsed-cycle count is large enough, this can exceed the transaction's CPU/energy budget or block-processing time limits, effectively making it impossible to ever successfully process that account's vote/unfreeze/withdraw transaction - a permanent freezing-of-funds condition for that account's rewards and staked/frozen balance, without requiring any special privilege from the transaction sender.

### Likelihood Explanation
Reachability requires no special condition beyond time passing and the account being on the legacy reward path (`beginCycle < newRewardAlgorithmEffectiveCycle`, `allowOldRewardOpt` disabled) - both are chain-wide configuration/state conditions outside the attacker's control, so exploitability depends on live chain parameters that could not be fully confirmed from the indexed code (e.g., current value of `newRewardAlgorithmEffectiveCycle` and `allowOldRewardOpt` on the target network). If those parameters currently force all live accounts onto the new O(1) `RewardViCalService`-based algorithm, the unbounded per-cycle path may be effectively dead code for present-day interactions, which would reduce likelihood significantly. This uncertainty could not be resolved with the available search tools.

### Recommendation
Cap the number of cycles processed per call to `withdrawReward`/`queryReward` in `MortgageService` (and by extension `computeReward`/`getOldReward`), analogous to the fix applied to `_updateWithdrawalQueue`: process a bounded number of cycles per transaction and persist partial progress (updating `beginCycle` incrementally) so that a backlog can be drained across multiple transactions instead of requiring a single unbounded pass. Alternatively, ensure the new O(1) reward algorithm (`RewardViCalService`) is unconditionally active for all accounts so the legacy per-cycle loop path can no longer be triggered.

### Proof of Concept
1. Configure/observe a chain state where `allowOldRewardOpt` is disabled and an account's `beginCycle` is far behind `newRewardAlgorithmEffectiveCycle`/current cycle (e.g., an account that voted long ago and never claimed).
2. As an unprivileged sender, submit any transaction that triggers `withdrawReward` for that account - e.g. a `VoteWitnessContract`, `UnfreezeBalanceContract`, or `WithdrawBalanceContract` transaction referencing that owner address.
3. Observe `MortgageService.computeReward` → `getOldReward` iterating `for (long cycle = begin; cycle < end; cycle++)`, with an inner loop over all of the account's votes performing DB lookups per SR per cycle - the total work scales with `end - begin` (elapsed cycles) and vote-list size, with no upper bound enforced anywhere in the call path shown above.
4. With a sufficiently large elapsed-cycle gap, the single-transaction execution time/resource consumption grows unbounded, preventing the transaction (and thus reward/balance access for that account) from completing successfully.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
    if (dynamicPropertiesStore.allowOldRewardOpt()) {
      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
    }
    long reward = 0;
    for (long cycle = begin; cycle < end; cycle++) {
      reward += computeReward(cycle, votes);
    }
    return reward;
  }

  public static void withdrawReward(byte[] address, Repository repository) {
    if (!VMConfig.allowTvmVote()) {
      return;
    }
    AccountCapsule accountCapsule = repository.getAccount(address);
    long beginCycle = repository.getBeginCycle(address);
    long endCycle = repository.getEndCycle(address);
    long currentCycle = repository.getDynamicPropertiesStore().getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account, repository);
        adjustAllowance(address, reward, repository);
        reward = 0;
      }
      beginCycle += 1;
    }
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      repository.updateBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule, repository);
      adjustAllowance(address, reward, repository);
    }
    repository.updateBeginCycle(address, endCycle);
    repository.updateEndCycle(address, endCycle + 1);
    repository.updateAccountVote(address, endCycle, accountCapsule);
  }
