The trait documentation explicitly settles this question: NEP-641's `w_resolve_auth` is documented as offchain-only, view-only, and by design NOT providing replay protection.The premise of the question is addressed directly by the NEP-641 trait documentation, and this is a documented, intentional design decision rather than a bug.

`AuthResolver::w_resolve_auth` is explicitly specified as a **view-only, offchain-only** method: [1](#0-0)  The doc comment states verbatim: "DO NOT call this view-method in on-chain transactions!... NEP-641 standard is NOT designed to be used for on-chain transfer 'approvals' or any other actions that modify state of the blockchain. Offchain messages are intended to be verified only offchain as they don't mutate any state and, hence, cannot prevent replay attacks. Instead, use on-chain messages (e.g. request messages, transactions, delegate actions), which are specifically designed with replay-protection mechanism in mind." [2](#0-1) 

The wallet contract's own on-chain path, `w_execute_signed` consuming `RequestMessage`, is the mechanism that IS designed with replay protection via a timeout-bounded nonce bitmap: [3](#0-2)  This is distinct from `OffchainMessage` used in the `Signature` branch of `resolve_auth`, which intentionally has no nonce field, only a `timestamp` future-check [4](#0-3) , because `w_resolve_auth` never mutates state — confirmed by the `&self` (non-mutating) signature on `resolve_auth` and `w_resolve_auth`: [5](#0-4) [6](#0-5) 

The question's own framing acknowledges this is conditional on "any consuming contract treats `AuthorizationResolution.payload` as single-use without its own replay protection" — that is a hypothetical flaw in a downstream/consuming contract's design, not a reachable vulnerability in this repo's wallet contract, and per the rules, theoretical findings with no demonstrated on-chain impact path through this repo, and issues requiring unaudited third-party consumer behavior, are out of scope. There is no `execute_intents`/Verifier code path in this repo that consumes `w_resolve_auth`'s output as an on-chain, single-use authorization without its own replay defenses — the documented and intended flow is that any consumer (e.g., the offchain `RpcResolver` in `crates/signatures/nep641/src/resolver/mod.rs`) performs verification off-chain and only the on-chain `w_execute_signed`/nonce path is authoritative for state changes.
