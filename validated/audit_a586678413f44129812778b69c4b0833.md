### Title
Unbounded blocking read in `process_event` allows a single slow POST to stall the signer's event loop - ([File: libsigner/src/events.rs])

### Summary
`process_event` reads the HTTP body via `request.as_reader().read_to_string(&mut body)` with no explicit maximum body size or read timeout enforced before the call. Since `SignerEventReceiver::next_event`/`main_loop` is single-threaded and processes one connection at a time via `http_server.recv()` then `process_event`, a client that sends a `POST` with a large `Content-Length` and then withholds the remaining bytes can block this single call indefinitely, starving the signer's event loop.

### Finding Description
`next_event` calls `http_server.recv()` to accept one `HttpRequest`, then dispatches synchronously to `process_event::<T, E>(request)` for routes like `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block` [1](#0-0) . Inside `process_event`, the body is read with:
```rust
let mut body = String::new();
if let Err(e) = request.as_reader().read_to_string(&mut body) { ... }
``` [2](#0-1) 

`tiny_http`'s reader for a request honors the client-supplied `Content-Length` and will keep reading from the socket until either that many bytes are received or the stream errors/EOFs. There is no code in this function (or in `with_server`/`next_event`) that: (1) caps the maximum body length before calling `read_to_string`, or (2) applies a read/idle timeout on the underlying stream. If a client declares `Content-Length: 100000000` but sends only a handful of bytes and then simply holds the TCP connection open (no more writes, no close), `read_to_string` will block on the socket read waiting for more bytes that never arrive. Because `SignerEventReceiver` processes requests synchronously and single-threaded inside `main_loop`/`next_event` [3](#0-2) , this one connection blocks the entire receiver from calling `http_server.recv()` again, so no further events (including legitimate ones from the node, e.g. real `/stackerdb_chunks` posts) can be processed for as long as the attacker holds the connection open.

None of the four routed handlers apply a byte-cap or authentication before reaching `process_event`; the only content-based gating happens after the full read completes (JSON deserialization, then chunk signature checks in `TryFrom<StackerDBChunksEvent>` at lines 544-625), which never executes while blocked in `read_to_string`.

### Impact Explanation
A single crafted, unauthenticated TCP connection to the signer's HTTP event port can stall `SignerEventReceiver::next_event` for as long as the attacker keeps the socket open without completing the declared body, since there is no maximum-body-size guard or read timeout enforced in `process_event` prior to `read_to_string`. This blocks the signer from consuming any further legitimate events forwarded by the node's event dispatcher, effectively denying service to the signer's block-processing/response pipeline for the duration — a bounded, single/few-connection compute/resource DoS on a read endpoint rather than generic volumetric flooding.

### Likelihood Explanation
Exploitability depends entirely on whether the signer's event-receiver HTTP port (bound via `SignerEventReceiver::bind`, `HttpServer::http(listener)` [4](#0-3) ) is reachable from an unprivileged remote party. This listener is a private channel between the node's event-observer and the signer, distinct from the node's P2P or RPC ports referenced by the threat model's attacker definition; whether it is bound to a loopback-only address or an externally reachable interface is an operator/config decision (`event_server`/endpoint setting in `stacks-signer/src/config.rs`), not something enforced by this code path. No authentication (secret, signature, etc.) gates any of the four POST routes before the body is read, so if the port is reachable, the attack requires only opening one TCP connection and sending a partial HTTP request with a large `Content-Length` — trivial attacker cost, fully repeatable per connection held open.

### Recommendation
Enforce a hard maximum body length (e.g., checked against the `Content-Length` header before reading, and/or wrap the reader with a size-limited adapter) and a read/idle timeout on the underlying `TcpStream` in `SignerEventReceiver`/`process_event`, rejecting or aborting requests that exceed either bound instead of calling `read_to_string` unconditionally.

    fn main_loop(&mut self) {
        loop {
            if self.is_stopped() {
                info!("Event receiver stopped");
                break;
            }
            let next_event = match self.next_event() {
                Ok(event) => event,
                Err(EventError::UnrecognizedEvent(..)) => {
                    // got an event that we don't care about (not a problem)
                    continue;
                }
                Err(EventError::Terminated) => {
                    // we're done
                    info!("Caught termination signal");
                    break;
                }
                Err(e) => {
                    warn!("Failed to receive next event: {:?}", &e);
                    continue;
                }
            };
            if !self.forward_event(next_event) {
                info!("Failed to forward event");
                break;
            }
        }
        info!("Event receiver main loop exit");
    }

            // were we asked to terminate?

                return Err(EventError::Terminated);
            }
            debug!("Request handling");
            let request = http_server.recv()?;
            debug!("Got request"; "method" => %request.method(), "path" => request.url());

            if request.url() == "/status" {
                request
                .respond(HttpResponse::from_string("OK"))
                .expect("response failed");
                return Ok(SignerEvent::StatusCheck);
            }

            if request.method() != &HttpMethod::Post {
                return Err(EventError::MalformedRequest(format!(
                    "Unrecognized method '{}'",
                    request.method(),
                )));
            }
            debug!("Processing {} event", request.url());
            if request.url() == "/stackerdb_chunks" {
                process_event::<T, StackerDBChunksEvent>(request)

            } else if request.url() == "/new_burn_block" {
                process_event::<T, BurnBlockEvent>(request)
            } else if request.url() == "/shutdown" {

                ack_dispatcher(request);

            }
        })?
