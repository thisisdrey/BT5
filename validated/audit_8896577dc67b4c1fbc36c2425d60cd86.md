### Title
Replay-window check/update race allows message-counter reuse and packet replay - (File: connection_state.go)

### Summary

### Finding Description
`ConnectionState.Decrypt` protects against replayed UDP data packets using a sliding anti-replay bitmap (`Bits`). The check-then-decrypt-then-update sequence is not atomic: `window.Check` is performed and released under `decryptLock`, the AEAD decryption is performed **without** holding the lock, and only afterwards is `window.Update` performed under a second, separate lock acquisition: [1](#0-0) 

Because `Check()` only inspects the window state and `Update()` is the step that actually marks a counter as consumed, two packets carrying the *same* `messageCounter` that arrive close together can both pass `Check()` before either has called `Update()`. Nebula's outside packet path invokes `hostinfo.ConnectionState.Decrypt` directly from `readOutsidePackets`, and Nebula supports multiple concurrent UDP read routines (`listen.routines`) that all decrypt inbound traffic against the same shared `HostInfo`/`ConnectionState`: [2](#0-1) 

This mirrors the root cause described in the external report: a piece of state (`isProcessed[_requestId]`) is meant to make an action idempotent, but the "mark as done" step is decoupled from the action that consumes it, so the same input can be accepted twice when timing allows the second consumer to slip in before the first one finalizes the state. Here, `window.Update` is the idempotency marker, and it is separated from `window.Check`/decrypt by lock release/reacquire, opening a TOCTOU window.

### Impact Explanation
An attacker who can observe/capture a single legitimate ciphertext UDP packet (no valid certificate or trusted peer status required — this is on-the-wire ciphertext, not something requiring PKI trust) can re-inject that exact packet a second time while the original is still mid-flight through decryption. If the two decrypts race, both will pass `Check()` and both `DecryptDanger` calls will succeed (AEAD decryption success does not depend on replay-window state), producing two deliveries of the same plaintext packet to the TUN device / application layer. This is a traffic-replay bypass of the anti-replay mechanism that Nebula's cipher layer relies on to guarantee message uniqueness, and can lead to duplicate packet delivery (e.g., duplicated application-layer commands) — directly analogous to the reported "double deposit" impact where the intended one-time state transition is executed twice due to non-atomic accounting.

### Likelihood Explanation
Likelihood is low-to-medium: it requires (a) capturing a genuine ciphertext packet (trivial for any on-path observer, since Nebula packets traverse UDP/IP and are not integrity-protected against capture-and-replay at the network layer — that is exactly what the replay window is meant to stop), and (b) winning a narrow race between two decrypt calls on the same `ConnectionState`, which is more likely when the node is configured with multiple UDP read routines (a supported, common performance configuration) so that two packets can be processed by different goroutines truly in parallel rather than serialized by a single reader loop.

### Recommendation
Perform the replay check and window update atomically under a single lock acquisition that spans the entire decrypt operation (or use a compare-and-swap style "reserve the counter" step before decryption and roll it back only on decryption failure), so that a duplicate counter can never pass `Check()` while an in-flight decrypt for the same counter has not yet called `Update()`.

### Proof of Concept
Conceptual reproduction (would require local instrumentation to force the race deterministically):
1. Establish a tunnel between two Nebula nodes with `listen.routines` > 1 on the receiving side.
2. Capture one legitimate outbound data packet (ciphertext) from the sender.
3. Simultaneously inject two copies of the identical captured packet into the receiver's UDP socket (e.g., via two different UDP read queues/threads) so both are read by different goroutines at nearly the same time.
4. Both goroutines call `ConnectionState.Decrypt`; both call `window.Check(messageCounter)` before either calls `window.Update(messageCounter)`, so both succeed and both deliver the decrypted payload to the TUN device — the replay window fails to block the duplicate.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
