### Title
Remote-fee truncation in `OutboundQueue::calculate_fee` lets senders underpay the Ethereum relayer reward, draining bridge funds - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
`Pallet::calculate_fee` converts the Ethereum-side (18-decimal) remote fee into the parachain's native currency (10 or 12 decimals) using an integer division that silently truncates to zero whenever the scaled value is smaller than the decimal-conversion denominator. A pallet test already demonstrates this with realistic, non-zero pricing parameters, yet the charged fee comes out as `0`, even though `reward.remote` (the amount promised to the relayer on the Ethereum gateway contract) is set independently and unaffected by this truncation.

### Finding Description
The fee pipeline is: [1](#0-0) 

`calculate_remote_fee` returns `fee_per_gas * gas_used + reward` denominated in Ether-Wei-scale units: [2](#0-1) 

This value is then converted to the local currency's decimal precision via `convert_from_ether_decimals`, which performs `value.checked_div(denom)` where `denom = 10^(18 - Decimals)` (`10^8` for a 10-decimal chain, `10^6` for a 12-decimal chain): [3](#0-2) 

Because this is plain integer (floor) division, any computed value smaller than `denom` collapses to `0`. The existing unit test proves this occurs with legitimate, non-degenerate pricing parameters (`exchange_rate = 1`, `fee_per_gas = 1`, `reward.remote = 1`, `multiplier = 1`): [4](#0-3) 

Critically, the `reward` field actually embedded in the `CommittedMessage` sent to Ethereum (and paid out to relayers by the gateway contract) is taken directly from the governance-set `PricingParameters`, not from the fee that was actually charged/collected from the sender: [5](#0-4) 

This decouples "what the sender pays" from "what the relayer is promised." When the computed native-currency fee truncates to zero (a condition reachable simply by sending small/cheap commands, or by any command whose `max_dispatch_gas` combined with governance `fee_per_gas`/`reward.remote` values fall under the truncation threshold for the configured `Decimals`), the message is still accepted, queued, assigned a nonce, and committed for relay — with the sender paying (up to) zero for the remote-fee component while the protocol still promises the full `reward.remote` payout on Ethereum. No guard in `do_process_message` checks that the computed fee is non-zero or that it actually matches/exceeds the promised reward before enqueuing/committing the message.

### Impact Explanation
This breaks the intended fee-conservation invariant described in the pallet's own documentation ("An upfront fee must be paid for delivering a message... covers... an additional reward paid out to relayers"). An unprivileged actor able to trigger outbound messages (e.g., via XCM export through `EthereumBlobExporter::deliver`, or any pallet on the parachain permitted to call `send_message_impl`) can repeatedly submit messages that are charged effectively zero in the remote-fee component while relayers are still promised `reward.remote` per message on the Ethereum gateway. Because there is no check preventing enqueuing of a zero/near-zero-fee message, this is "public underpriced work" that can be repeated at scale (bounded only by `MaxMessagesPerBlock`), depleting the fee/reward economics that back relayer incentives and potentially causing message backlogs or relayer disincentivization — degrading or stalling bridge processing, which is within the accepted impact set.

### Likelihood Explanation
The bug requires no privileged actor, governance action, or malicious relayer/validator — only ordinary usage with pricing parameters and gas amounts that are entirely plausible in production (the test itself uses realistic-looking values, not edge-case extremes). Any parachain team or user able to originate outbound Snowbridge messages can trigger it deterministically, and the condition is already codified (and left unresolved) in the pallet's own test suite, which explicitly flags it as behavior "which should be avoided."

### Recommendation
- Reject or clamp fee calculation when the computed native-currency fee would truncate to zero (e.g., require `checked_div` to round up, or enforce a minimum fee floor tied to `reward.remote`).
- Tie the `reward` field embedded in `CommittedMessage` to the fee actually collected from the sender, or validate at enqueue time that the calculated fee is sufficient to cover `reward.remote` plus gas costs before accepting the message.
- Add an explicit `ensure!(fee.remote > 0, ...)` (or equivalent) guard in the message validation path prior to `do_process_message` committing the message.

### Proof of Concept
The existing test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` is itself the proof of concept: [4](#0-3) 
It shows that with `exchange_rate = 1`, `fee_per_gas = 1`, `reward.remote = 1`, `multiplier = 1`, and `gas_used = 250000`, `OutboundQueue::calculate_fee` returns `fee.remote == 0`. Any message processed under these (or similarly-scaled) `PricingParameters` will be committed via `do_process_message` and promise `reward.remote` to the relayer on Ethereum, while the sender's charged remote-fee component is zero.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {
		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
			exchange_rate: FixedU128::from_rational(1, 1),
			fee_per_gas: 1_u32.into(),
			rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});
