### Title
Disabled collateral cannot be withdrawn if its oracle fails to resolve, permanently trapping the user's collateral - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
Zest lets the DAO disable an asset's `collateral` flag via the assets registry (the analog of "blacklisting" a Safe extension in the reNFT report). Unlike the bug reported for reNFT, Zest's `collateral-remove` was specifically patched to *allow* withdrawal of already-disabled collateral. However, this fix reintroduces the same class of bug through a different path: withdrawing disabled collateral is made conditional on a live, successful oracle `price-resolve` call for that specific asset. Since assets are typically disabled by the DAO precisely because something is wrong with them (e.g. a broken/manipulated/stale oracle feed), the very condition that triggers disabling an asset is also the condition that makes it permanently un-withdrawable — trapping the user's funds exactly like the reNFT "can't disable a blacklisted module" bug traps a safe owner.

### Finding Description
In `collateral-remove`, when the asset being withdrawn is disabled (`is-collateral-enabled` is `false`) and the account has open debt, the contract unconditionally requires a fresh oracle price for that disabled asset: [1](#0-0) 

If `price-resolve` fails — which happens whenever the oracle timestamp is stale, the confidence ratio check fails, or the callcode/oracle type call reverts — the entire `unwrap!` bubbles up as `ERR-DISABLED-COLLATERAL-PRICE-FAILED` and the whole `collateral-remove` transaction reverts: [2](#0-1) 

The DAO's only tool for disabling a collateral asset is the registry `disable` function, which simply flips the collateral bit with no ability to make an exception for withdrawal-only access: [3](#0-2) 

In practice, assets get disabled by the DAO precisely *because* something is broken — e.g. the oracle for that asset is manipulated, stale, or a price feed provider stopped publishing. That is the same condition that causes `price-resolve` to fail. So the one case where a user most urgently needs to pull disabled collateral out of the market (before the position becomes unhealthy or before an oracle-based liquidation using stale data occurs) is the exact case in which `collateral-remove` is guaranteed to revert. A user with debt open who also holds this disabled collateral has no way to ever remove it — mirroring the reNFT root cause where blacklisting a module removed the ability to disable/unwind it.

### Impact Explanation
Any account holding open debt and a DAO-disabled collateral asset whose oracle has failed is permanently unable to withdraw that collateral via `collateral-remove`/`collateral-remove-redeem`. This is a temporary-to-permanent freezing of user funds: the asset's oracle failure (the reason it was disabled) is often not something users or even the DAO can trivially fix, so the collateral can remain locked indefinitely while the account still bears full liquidation risk from the frozen, potentially worthless collateral.

### Likelihood Explanation
This requires no attacker action — it triggers naturally any time the DAO disables an asset due to an oracle problem while users still hold debt-backed positions with that collateral, a realistic and expected operational sequence (disable-due-to-oracle-issue is the standard incident-response playbook this contract is designed to support).

### Recommendation
Decouple the disabled-collateral withdrawal path from live oracle freshness requirements: allow withdrawal using the last-known-good cached price (or a DAO-settable fallback/override price) when the live oracle call fails for a disabled asset, so users can always exit disabled collateral even when its oracle is broken.

### Proof of Concept
1. DAO lists asset X with collateral enabled; oracle for X has `max-staleness` = 120s.
2. User deposits X as collateral and borrows asset Y against it.
3. Asset X's oracle provider stops publishing fresh prices (or gets manipulated), so DAO calls `disable(X, true)` to protect the protocol (`mainnet/contracts/registry/v0-assets.clar` lines 280-304).
4. User now calls `collateral-remove` for X. Since `has-debt` is true and `is-collateral-enabled` is false, the code path at `v0-4-market.clar` lines 1145-1153 calls `price-resolve` for X's oracle.
5. Because X's oracle is stale/broken (the reason it was disabled), `oracle-timestamp-fresh` fails and `price-resolve` returns an error (`v0-4-market.clar` lines 386-395), causing `unwrap!` to revert with `ERR-DISABLED-COLLATERAL-PRICE-FAILED`.
6. The user's X collateral can never be withdrawn while debt remains open, for as long as the oracle stays broken.
