### Title
Unbounded per-filter result queue growth in `eth_newFilter`/`handleLogsFilter` allows memory-exhaustion DoS via anonymous JSON-RPC client - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogFilterAndResult.java`)

### Summary
Apache Tomcat's WebSocket chat example DoS (CVE-2026-66299) stems from an uncontrolled resource consumption pattern where server-side per-connection buffers grow without bound because nothing caps how much data can accumulate before being drained by the client. java-tron's JSON-RPC event-filter subsystem has the same structural flaw: each `eth_newFilter` log filter owns a `LinkedBlockingQueue` that the block-processing pipeline appends to on every matching block, with no maximum-size check, while draining only happens if/when the client calls `eth_getFilterChanges`/`eth_getFilterLogs`.

### Finding Description
`TronJsonRpcImpl.newFilter()` lets any anonymous JSON-RPC client register a log filter with an empty `FilterRequest` (no address, no topics), which `LogFilterWrapper`'s "Strategy 1" turns into a filter matching **every log emitted network-wide** from the current block onward (`fromBlock = currentMaxBlockNum`, `toBlock = Long.MAX_VALUE`): [1](#0-0) 

Only the *count* of filters is capped (`maxLogFilterNum`, default 20000): [2](#0-1) 

But each individual filter's result buffer, `LogFilterAndResult.result`, is an unbounded `LinkedBlockingQueue` with no capacity limit and no size check in `add()`: [3](#0-2) 

Every block, `Manager`/`RealtimeEventService` invokes `TronJsonRpcImpl.handleLogsFilter()`, which iterates all live filters and, for any match, appends the full list of matched `LogFilterElement`s to that filter's queue via `getResult().addAll(localResults)` — with **no cap analogous to `LogBlockQuery.MAX_RESULT`/`LogMatch.matchBlockOneByOne()`'s 10,000-item guard**: [4](#0-3) 

The only bound on how long this can accumulate is the filter's 5-minute expiry (`EXPIRE_SECONDS`), which is refreshed only when the client actually polls (`updateExpireTime()` inside `getFilterResult`, which fully drains via `popAll()`): [5](#0-4) [6](#0-5) 

Because a client that never polls simply lets the filter accumulate for up to 5 minutes of full-network log traffic, and can open many such match-all filters (up to `maxLogFilterNum`, itself as high as 20,000), the aggregate heap consumption is `(network log volume in 5 minutes) × (number of open match-all filters)` — entirely decoupled from any resource the attacker pays for (JSON-RPC calls carry no bandwidth/energy cost, unlike broadcasting transactions). This mirrors the Tomcat advisory's root cause: unbounded server-side buffering per client session with draining left entirely to the client's discretion.

### Impact Explanation
An anonymous, unauthenticated JSON-RPC client (any caller of the exposed `eth_newFilter` endpoint, which is commonly enabled on FullNode/Solidity JSON-RPC deployments) can open many match-all filters and simply never poll them. Each filter buffers copies of every log emitted network-wide for up to 5 minutes; with up to `maxLogFilterNum` concurrently open filters, this multiplies memory pressure by that factor with a single class of cheap RPC calls, risking heap exhaustion / OOM and node crash — a Denial-of-Service against the API-serving node, consistent with the "node crash or halt" / "API the node can no longer serve" acceptance criteria.

### Likelihood Explanation
High likelihood: `eth_newFilter` requires no authentication, no fee, no on-chain transaction, and no special privilege — it is reachable by any anonymous JSON-RPC client per the explicitly in-scope "HTTP/gRPC/JSON-RPC query paths into Wallet and TronJsonRpcImpl" surface. The match-all filter shape (empty `FilterRequest`) is a documented, supported strategy (Strategy 1) rather than an edge case, and normal network transaction volume alone (without attacker-authored contracts) is sufficient to fill the buffers.

### Recommendation
Add a per-filter maximum queued-element cap in `LogFilterAndResult`/`BlockFilterAndResult` (mirroring `LogBlockQuery.MAX_RESULT`/`LogMatch`'s 10,000-item guard) so that `add()`/`addAll()` either drop oldest entries, refuse new entries, or mark/expire the filter once its queue exceeds the cap, and consider bounding total buffered elements across all filters via a node-wide limit similar to `RealtimeEventService.maxEventSize`.

### Proof of Concept
1. Enable `node.jsonrpc.httpFullNodeEnable = true` (a common FullNode configuration).
2. As an anonymous client, repeatedly call `eth_newFilter` with an empty `FilterRequest` (`{}` / all fields omitted), up to `maxLogFilterNum` times (default 20000), without ever calling `eth_getFilterChanges`/`eth_getFilterLogs`.
3. Let normal network traffic run for several minutes; each of the 20000 filters' `LinkedBlockingQueue` independently accumulates a full copy of every `LogFilterElement` from every matching transaction on the network via `TronJsonRpcImpl.handleLogsFilter()` → `processLogFilterEntry()` → `result.addAll(localResults)`.
4. Observe unbounded heap growth proportional to `(open filters) × (network log volume)` until the process OOMs or GC pauses degrade/halt the JSON-RPC service.
