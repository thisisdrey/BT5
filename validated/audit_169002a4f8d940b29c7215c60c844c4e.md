Based on my investigation, I found a legitimate analog to the CVE-2020-11939 bug class (attacker-controlled length field used to size a heap allocation without adequate bounds checking, reachable via a length field embedded in remote/network-supplied data).

### Title
Unbounded attacker-controlled array-length allocation in `BatchValidateSign` precompile leads to OutOfMemoryError / node crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The nDPI CVE stems from an attacker-controlled length field being used to compute a buffer/array size without validating it against sane bounds, causing memory corruption. The `BatchValidateSign` TVM precompiled contract has a structurally similar pattern: an attacker-controlled 32-byte word from contract calldata is converted to an `int` length via `intValueSafe()` and used directly to allocate a Java array, with the size-limiting guard only applied conditionally.

### Finding Description
In `PrecompiledContracts.BatchValidateSign.doExecute`, the signature-array length is read straight from calldata: [1](#0-0) 

The `MAX_SIZE` (16) bound is only enforced when `VMConfig.allowTvmSelfdestructRestriction()` is active: [2](#0-1) 

When that TIP flag is not active, `extractBytesArray` is invoked directly with an unchecked, attacker-controlled `len`: [3](#0-2) 

`words[offset].intValueSafe()` can return any value up to `Integer.MAX_VALUE` (`DataWord.intValueSafe`, `common/src/main/java/org/tron/common/runtime/vm/DataWord.java:222-229`), and this value is fed directly into `new byte[len][]`, which for a large `len` triggers an `OutOfMemoryError`. `execute()` catches `Throwable`, but a genuine `OutOfMemoryError` can still destabilize the JVM heap for concurrently executing threads (the precompile also spins up a thread pool, `workers`) before/while the catch handles it, and repeated invocation lets a broadcaster continuously force large transient allocations. [4](#0-3) 

### Impact Explanation
While `execute()` wraps `doExecute()` in a `try { } catch (Throwable t)`, this only prevents the *call itself* from crashing the VM invocation — it does not prevent a large `OutOfMemoryError` from disrupting the JVM's heap, other concurrent threads, and Manager/block application. Repeated calls (e.g., from a batch of transactions in the same block or continuous transaction spam) using this precompile with maximal `len` values could produce sustained memory pressure. This is a resource-exhaustion/availability concern reachable from an ordinary smart-contract call, not full RCE, and is bounded by the fact that `execute()` catches `Throwable`. Given the CVE-class comparison (integer/length-driven heap overflow → RCE) does not directly translate to Java (no raw pointer corruption is possible here), the strongest concretely provable impact is a node-availability degradation via uncontrolled allocation, not memory corruption or RCE.

### Likelihood Explanation
Reachable by any unprivileged contract call to the `BatchValidateSign` precompiled address with crafted calldata; no special privilege required. However, the actual severity depends on the runtime environment's available heap and GC behavior, which I could not fully verify from static analysis alone (I was unable to confirm from the index whether `allowTvmSelfdestructRestriction()` is enabled by default on mainnet, which determines whether the unguarded `extractBytesArray` path is actually reachable in production).

### Recommendation
Enforce the same `MAX_SIZE` bound on `sigArraySize`/`addrArraySize` (or on `words[offset].intValueSafe()` for `len`) unconditionally in `extractBytesArray`/`extractSigArray`/`extractBytes32Array`, regardless of the `allowTvmSelfdestructRestriction()` flag, before allocating any array.

### Proof of Concept
Construct calldata for `BatchValidateSign` where word[1] (offset to signature-array) points to a slot whose value is `0x7FFFFFFF` (or another very large but `intValueSafe`-representable value), with `allowTvmSelfdestructRestriction()` not yet activated. Calling this precompile triggers `new byte[0x7FFFFFFF][]` in `extractBytesArray`, forcing an immediate large allocation attempt.

**Caveat:** I could not fully verify (a) whether `allowTvmSelfdestructRestriction` is active by default in the current mainnet configuration (which would make the guarded path the only reachable one), or (b) whether an `OutOfMemoryError` here can escalate beyond the `catch (Throwable)` boundary to affect other concurrently-executing threads/blocks in this JVM version — the index does not contain enough operational/config detail to confirm this beyond doubt. This is a moderate-confidence DoS-class analog, not a confirmed heap-corruption/RCE equivalent to the CVE.
