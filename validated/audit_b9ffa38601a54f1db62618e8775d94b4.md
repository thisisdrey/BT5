### Title
Out-of-bounds read in ZIP central-directory extra-field parsing during ijar interface-jar generation - ([File: third_party/ijar/zip.cc])

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses the "extra field" data of a ZIP/JAR central directory entry using attacker-controlled length fields, with no per-field bounds validation against the declared `extra_field_length`, mirroring the class of bug in CVE-2024-31036 (length-prefixed byte-stream parser that reads past the buffer boundary on malformed/crafted input).

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from attacker-supplied bytes in the ZIP central directory, without validating them against the remaining size of the memory-mapped file [1](#0-0) . It then walks the extra-field region with an unchecked, fixed-size-read loop:

```
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  if (header_id == ZIP64_EXTRA_FIELD_TAG) {
    if (*uncompressed_size == U4_MAX) *uncompressed_size = get_u8le(extra);
    ...
``` [2](#0-1) 

Two independent unsafe assumptions are made here:
1. The loop reads 4 bytes (`header_id` + `data_size`) at `extra_p` on every iteration without checking that at least 4 bytes remain before `p` (the declared end of the extra field). A crafted entry whose `extra_field_length` is not an exact multiple of the encoded sub-field sizes can push `extra_p` past `p`. The loop condition is `extra_p != p`, not `extra_p < p`, so once `extra_p` overshoots `p` it does not terminate on reaching the boundary and continues consuming attacker-influenced `data_size` values to walk further through the mapped file, well past the bounds implied by the record.
2. When `header_id == ZIP64_EXTRA_FIELD_TAG`, the code unconditionally reads 8 bytes (`get_u8le(extra)`) for `uncompressed_size`/`compressed_size`/`offset`, without verifying that `data_size >= 8` (or `>= 24` for all three). A crafted Zip64 extra field with a `data_size` smaller than 8 causes an 8-byte read that runs past the end of the declared sub-field, and — combined with (1) — potentially past the mapped file region entirely.

There is no code analogous to `EnsureRemaining()` (used elsewhere in the same file for local-file-entry parsing, e.g. [3](#0-2) ) guarding these reads in `ProcessCentralDirEntry`. `get_u2le`/`get_u8le` are raw pointer dereferences over the memory-mapped input file with no bounds checks of their own [4](#0-3) .

### Impact Explanation
This parser runs whenever Bazel builds an interface jar (`ijar`) from a `.jar`/ZIP dependency — the default code path for Java library targets that depend on any prebuilt JAR (e.g., fetched via `http_jar`, Maven, or any other external JAR dependency an attacker-controlled origin can serve). Because the crafted lengths are read straight from bytes in a hostile ZIP file and used to drive pointer arithmetic and fixed-size reads with no bounds validation, a malicious jar publisher can trigger an out-of-bounds read of the memory-mapped input file (and potentially adjacent memory once the cursor runs past the mapped region), corrupting the parsed offsets/sizes used later to build the output. This is a genuine memory-safety violation in Bazel's own native C++ code (not a third-party or sandbox issue), directly reachable from attacker-served archive bytes with no code execution or local access required by the attacker.

### Likelihood Explanation
Any project depending on an externally hosted/mirrored JAR (common in Java rules) will run this exact code path during a normal build the moment the dependency is fetched and Bazel derives its ijar. No special privileges, root-repo Starlark, or existing local access are required — a hostile origin or a compromised mirror serving a crafted `.jar`/ZIP is sufficient, and unlike `http_archive`/`http_jar` downloads, ijar's ZIP central-directory parsing does not go through a checksum/integrity gate that could reject a "wrong" byte-for-byte-different-but-still-integrity-matching file (the sha256/integrity check validates the outer downloaded bytes are what was pinned — if the attacker controls what gets pinned, or the dependency lacks a pin/lockfile entry as is common for internal/mirrored artifacts, the crafted content reaches this parser unmodified).

### Recommendation
Add explicit bounds checks in `InputZipFile::ProcessCentralDirEntry`'s extra-field loop:
- Require at least 4 remaining bytes before reading `header_id`/`data_size`, and require `data_size` bytes remain before advancing `extra_p`; reject/error out otherwise (mirroring the existing `EnsureRemaining()` pattern already used for local file header parsing).
- For the Zip64 extra field, verify `data_size` is large enough (as required, up to 24 bytes) before reading `get_u8le(extra)` for each of `uncompressed_size`, `compressed_size`, and `offset`.
- Change the loop termination condition from `extra_p != p` to `extra_p < p` combined with an explicit check that `extra_p + 4 <= p` before each 4-byte header read, so malformed length fields cannot walk the cursor past the declared/mapped region.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` or C++ unit test analogous to the existing `output_jar_simple_test.cc` malformed-extra-field test can be adapted for ijar: craft a ZIP whose central directory entry declares `extra_field_length` such that the encoded sub-field `data_size` does not evenly divide the declared length (or declares `ZIP64_EXTRA_FIELD_TAG` with `data_size < 8`), feed it to `ZipExtractor::Create`/`ProcessAll()` (as `ijar` does when building an interface jar from a dependency jar), and observe that `extra_p` advances past `p` / past the mapped file bounds, verified under AddressSanitizer as a heap-buffer-overflow read — directly mirroring the `read_byte` heap-buffer-overflow parsing pattern from CVE-2024-31036. Note: full exploitability confirmation (e.g., ASan crash trace) would require running this PoC in Devin's build/test environment, which was not available during this analysis; the code path and missing bounds checks were confirmed by static inspection of `third_party/ijar/zip.cc`.
