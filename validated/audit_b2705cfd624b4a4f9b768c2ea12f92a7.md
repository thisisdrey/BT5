### Title
Dust-transfer griefing fills a victim's per-account token slots (`MAX_TOKENS_PER_USER`), permanently DoS-ing all inbound deposits/transfers of new tokens - (File: contracts/Pool.sol)

### Summary
`Pool` tracks the deposit tokens and debt tokens a user holds in two per-account sets (`depositTokensOfAccount`, `debtTokensOfAccount`). Any addition to those sets goes through `onlyIfAdditionWillNotReachMaxTokens`, which reverts with `UserReachedMaxTokens` once the combined count reaches `MAX_TOKENS_PER_USER = 30` (`contracts/Pool.sol:79`, `contracts/Pool.sol:143-148`). `DepositToken._transfer`/`_mint` add the token to the *recipient's* set whenever their balance goes from 0 to >0 (`contracts/DepositToken.sol:486-488`, and the symmetric add in `_transfer`), so any EOA can force entries into an arbitrary victim's set by sending dust amounts of whitelisted deposit tokens. This mirrors the bug class of the DoQ/DoH3 advisory: attacker-controlled resource consumption (per-account set slots) with no cost-proportional bound, causing denial of service.

### Finding Description
- `Pool.addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are callable only by registered token contracts, but the *account* argument is attacker-controlled via a plain `DepositToken.transfer(victim, 1 wei)` — the token contract then calls `addToDepositTokensOfAccount(victim)` with `_msgSender()` = itself, passing the `SenderIsNotDepositToken` check (`contracts/Pool.sol:216-220`, `contracts/Pool.sol:194-196`).
- The attacker repeats this across every whitelisted deposit token (up to 30 combined deposit+debt slots). The dust is only removed from a slot when the victim's balance returns exactly to 0 (`contracts/DepositToken.sol:460-462`), so 1 wei per token suffices.
- Once `length(debtTokensOfAccount) + length(depositTokensOfAccount) >= 30` for the victim, every path that would add a *new* token reverts:
  - `DepositToken.deposit`/`mint` into the victim for a collateral they don't already hold (the `_mint` add reverts, reverting the whole deposit).
  - Any inbound `transfer`/`transferFrom` of a deposit token the victim doesn't hold — the recipient-side add reverts, so the victim cannot be paid in that token.
  - `DebtToken.issue`/`mint` for a synthetic the victim hasn't borrowed before — victim cannot open new debt positions.
  - `SmartFarmingManager.leverage` and gateway deposits into new collaterals for the victim revert.
- Reentrancy guards, `SynthContext` sender checks, pause flags, and supply caps do not mitigate this; `onlyIfAdditionWillNotReachMaxTokens` is exactly the mechanism being abused.

### Impact Explanation
Denial of service against a targeted account: the victim is locked out of depositing any new collateral type, receiving any new deposit token (including liquidation seizure proceeds if the liquidator's address is pre-filled), and issuing any new synthetic debt, for as long as the dust remains. In bounded form this is temporary freezing of funds/position-management capability; where inbound transfers revert, funds sent to the victim in new token types are blocked entirely. The victim can recover slots by transferring the dust balances out, but each dust position must be individually swept, and the attacker can front-run refill since the attack costs only 1 wei per slot plus gas.

### Likelihood Explanation
An unprivileged EOA needs only to acquire dust balances of each whitelisted deposit token (buy a tiny amount of each underlying and call `deposit`, or chain transfers) — no privileged role, oracle manipulation, or governance interaction is required. Cost scales with the number of enabled deposit tokens (capped at 30 slots); on pools with many collaterals the attack is proportionally cheap per victim. Motivation exists for griefing liquidations/vault automation contracts that must receive arbitrary collateral tokens.

### Recommendation
- Do not add to `depositTokensOfAccount` on recipient in `DepositToken._transfer` for amounts below a meaningful threshold, or make additions permissioned to deposits rather than transfers (track a "deposited" flag set only in `deposit()`/`mint` paths).
- Alternatively, allow the account itself (or anyone, since removal is benign) to force-remove entries: add a public `removeFromDepositTokensOfAccountIfZeroBalance` cleanup so a victim can clear dust slots in one transaction without paying per-token transfer gas, and exempt `addTo...` reverts on the seize/liquidation path so liquidations cannot be blocked by a filled liquidator or fee-collector set.

### Proof of Concept
Hardhat sketch (real deployment, no mocks):

```ts
// setup: pool with N whitelisted depositTokens, victim = alice
for (const dt of depositTokens /* up to 30 combined slots */) {
  const underlying = await ethers.getContractAt('IERC20', await dt.underlying());
  // attacker acquires dust of underlying and deposits, or just transfers 1 wei of dt
  await dt.connect(attacker).transfer(victim.address, 1);
}
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.lengthOf(30);

// victim tries to deposit a collateral type they don't already hold
const newDt = depositTokens[31 - existing]; // any not-yet-held token
await underlying.connect(victim).approve(newDt.address, amount);
await expect(newDt.connect(victim).deposit(amount))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// any inbound transfer of a new token also reverts
await expect(otherDt.connect(attacker).transfer(victim.address, 1))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

The same pattern applies to `debtTokensOfAccount` via `DebtToken.issue` to fill remaining slots, blocking all new borrows.
