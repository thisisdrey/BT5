### Title
Permissionless reward index updates let an attacker burn emissions via `wadDiv` truncation against an inflated `totalSupply` - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor.updateBeforeMintOrBurn` is explicitly callable by anyone, and each call advances the per-token reward index timestamp while computing the index delta as `_tokensAccrued.wadDiv(_totalSupply)`, truncating toward zero. An unprivileged attacker can flash-inflate a reward-bearing token's `totalSupply` (e.g., a `DepositToken` via a flash-funded deposit, or a `DebtToken` via a flash-funded borrow), call the permissionless index update so the entire interval's emission truncates to ~0, then unwind — permanently destroying accrued-but-undistributed rewards for all other holders. Repeating this each block/starving window burns the emission stream. This is the same bug class as the external report: overly frequent/sensitive accrual triggers combined with precision loss in reward accounting.

### Finding Description
In `RewardsDistributor._calculateTokenIndex`, the index increment is computed as `_ratio = _tokensAccrued.wadDiv(_totalSupply)` where `_tokensAccrued = _deltaTimestamps * _speed`. [1](#0-0)  `wadDiv` truncates the fraction, so up to `totalSupply / 1e18` reward tokens of accrual are lost on every update — and if `totalSupply > _tokensAccrued * 1e18`, the entire interval's emission rounds to zero.

Crucially, when `_ratio` truncates to 0, `_newIndex` still equals the old (non-zero) index and `_newTimestamp` is set to `block.timestamp`, so `_updateTokenIndex` stores the new timestamp while the accrued rewards for that interval are never credited to anyone — they are permanently unallocated. [2](#0-1) 

The trigger is permissionless: `updateBeforeMintOrBurn` has no access control and the dev comment states it "may be called by anyone to update stored indexes". [3](#0-2)  `claimRewards` likewise calls `_updateTokenIndex` on any token with an initialized index. [4](#0-3)  The only token validation is `onlyIfTokenExists` on the speed-setting path, not on the public index-update path — the attacker only needs the token's `tokenStates[token_].index > 0`.

The missing piece to confirm is whether same-transaction supply inflation is feasible on the deployed config: `Pool.deposit` mints `DepositToken` supply (and `DebtToken.issue` inflates debt supply), and `DepositToken._revertIfLocked` may restrict same-block withdraw but does not prevent mint-then-update within one transaction — the attacker does not need to withdraw in the same block, only to restore supply before honest users' next accrual, or simply tolerate holding the position since the emission was destroyed rather than redirected.

### Impact Explanation
Theft/destruction of unclaimed yield: emissions that accrued during the manipulated interval are never credited to any index, so honest depositors/borrowers permanently lose that period's rewards; the tokens remain idle in the distributor or are effectively burned from the reward schedule. With a flash-loan-sized `totalSupply`, a single call destroys the full interval emission; sustained repetition destroys the emission stream for the targeted token. Loss per call is bounded below by the truncation error (`< totalSupply/1e18` tokens), which grows with attacker-controlled supply.

### Likelihood Explanation
Requires: a reward token with `index > 0` and `speed > 0`, and an attacker able to temporarily inflate `totalSupply` (flash loan → `Pool.deposit`, or `DebtToken` flash issue / borrow). No privileged role, oracle manipulation, or governance action is needed — `updateBeforeMintOrBurn` is permissionless and not `nonReentrant`-gated. Cost is gas plus flash-loan fees; profit is indirect (griefing/competitor harm rather than direct theft), so the realized impact is medium, matching the original report's severity.

### Recommendation
- Record the remainder when computing `_ratio` (carry-forward rounding debt, à la Liquity) instead of truncating it into the void, or revert/skip the timestamp update when `_ratio == 0` but `_tokensAccrued > 0` so emissions are not silently destroyed.
- Gate `updateBeforeMintOrBurn`/`updateBeforeTransfer` to the Pool/DepositToken/DebtToken contracts only, removing the "callable by anyone" surface.
- Use a snapshot `totalSupply` taken at the last index update (or a TWAP/floor) rather than spot `totalSupply()` so same-transaction supply inflation cannot zero out accruals.

### Proof of Concept
Hardhat sketch (fork or mocked pool per `test/RewardDistributor.test.ts`):

```ts
// setup: rewardDistributor initialized, updateTokenSpeed(msdToken, 1e18),
// index initialized, honest users hold small depositToken balances.
// state: tokenStates[msdToken].index = INITIAL_INDEX, timestamp = T0

// attacker tx (after time T0 + dt):
const hugeAmount = speed.mul(dt).mul(parseEther('1')).add(1); // > dt*speed*1e18
// 1) flash-borrow underlying -> pool.deposit(underlying, hugeAmount)
//    => msdToken.totalSupply() now ~= hugeAmount
await rewardDistributor.updateBeforeMintOrBurn(msdToken.address, attacker.address);
// _tokensAccrued = dt * speed; _tokensAccrued * 1e18 < totalSupply => _ratio = 0
// tokenStates[msdToken].timestamp = block.timestamp, index unchanged
// 2) (next block or after lock window) pool.withdraw -> repay flash loan

const { index, timestamp } = await rewardDistributor.tokenStates(msdToken.address);
expect(index).to.eq(INITIAL_INDEX);      // no accrual recorded
expect(timestamp).to.be.gt(T0);          // interval consumed anyway
// honest users' claimable() for [T0, block.timestamp] is 0 — emission destroyed
```

Note: a full fork PoC depends on `DepositToken`'s lock semantics (`_revertIfLocked`) and whether `Pool.deposit` in the target deployment permits immediate same-tx minting — I did not fully trace `DepositToken.mint`/`Pool.deposit` internals within this pass, but neither the permissionless index update nor the truncation depends on them.
