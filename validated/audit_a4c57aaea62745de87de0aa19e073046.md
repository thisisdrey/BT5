### Title
`RecurringAirdrop.claim` uses raw `msg.sender` instead of the Operator-aware `SynthContext._msgSender`, breaking claims for users routed through `Operator.execute` - (File: contracts/utils/RecurringAirdrop.sol)

### Summary
Metronome's `Operator.execute` lets users batch arbitrary calls "on sender's behalf", and protocol contracts resolve the real caller via `SynthContext._msgSender()`, which reads the transient `MSG_SENDER` slot when `msg.sender == operator`. `RecurringAirdrop` does not inherit `SynthContext` and derives both the Merkle leaf and the payout/`claimed[]` accounting from raw `msg.sender`. Like the Biconomy enable-mode bug (where one field was forced to serve two incompatible roles, so only validator-type modules worked), here the claim identity is hard-bound to the immediate caller, so the feature silently does not work for the meta-transaction path the protocol otherwise supports. Airdrop claims submitted through `Operator.execute` always revert, freezing rewards for accounts that can only act via the Operator.

### Finding Description
`claim()` builds the leaf as `keccak256(abi.encodePacked(msg.sender, amount_))` and keys `claimed[msg.sender]` and the transfer on the same raw `msg.sender` [1](#0-0) . When a user calls it via `Operator.execute`, `msg.sender` inside `RecurringAirdrop` is the `Operator` contract address [2](#0-1) . All other user-facing contracts (`DepositToken`, `Pool`, `SyntheticToken`, `VesperGateway`, `NativeTokenGateway`, `SmartFarmingManager`, `ProxyOFT`) route identity through `SynthContext._msgSender()`, which unwraps `getActualMsgSender()` when the caller is the registered Operator [3](#0-2) . `RecurringAirdrop` is the lone exception: it cannot distinguish an Operator-batched call from a direct call by the Operator contract itself.

Two consequences:
1. A user calling `claim` through `Operator.execute` reverts with `InvalidProof`, because the leaf is verified against the Operator's address, not the user's.
2. Even if the Operator contract somehow had a valid leaf, `claimed[]` and the payout would be attributed to the Operator contract, not the user — rewards would be locked to a contract with no withdrawal path for them.

### Impact Explanation
Unclaimed airdrop rewards are unreachable for any account that cannot produce a direct EOA transaction to `RecurringAirdrop` — e.g., smart accounts or flows built on `Operator.execute` batching, which is the protocol's own mechanism for EOAs to perform batched calls. This constitutes freezing of unclaimed yield for that class of users, and permanently attributes accounting to the wrong principal if a leaf ever exists for the Operator address. Severity is bounded by the fact that plain EOAs can still claim directly.

### Likelihood Explanation
Any user batching a claim through `Operator.execute` hits the revert deterministically — no attacker action, privileged role, or oracle assumption is required. The misrouting requires only the deployed configuration (Operator registered in `PoolRegistry`, RecurringAirdrop outside `SynthContext`), which matches the shipped code. No modifier, pause flag, or reentrancy guard compensates; `nonReentrant` is irrelevant to the identity bug.

### Recommendation
Make `RecurringAirdrop` (and any contract meant to be reachable via `Operator.execute`) inherit `SynthContext` and use `_msgSender()` for the leaf, `claimed[]` accounting, and `_transferReward` target — mirroring how `DepositToken`/`Pool` already resolve the actual sender. Alternatively, explicitly document and enforce that `claim` must be called directly, though that contradicts the protocol-wide Operator batching model.

### Proof of Concept
Foundry test sketch against deployed-style wiring:

```solidity
// contracts/utils/RecurringAirdrop.sol + contracts/Operator.sol
function test_claimViaOperatorReverts() public {
    // Setup: user is in the merkle tree with leaf = keccak256(abi.encodePacked(user, amount))
    bytes32 leaf = keccak256(abi.encodePacked(user, amount));
    bytes32[] memory proof = buildProof(leaf); // root set via updateMerkleRoot by governor

    // Direct claim works
    vm.prank(user);
    airdrop.claim(amount, proof); // succeeds

    // Same user via Operator.execute always reverts:
    // leaf is recomputed as keccak256(abi.encodePacked(address(operator), amount))
    IOperator.Call[] memory calls = new IOperator.Call[](1);
    calls[0] = IOperator.Call({
        target: address(airdrop),
        value: 0,
        callData: abi.encodeCall(RecurringAirdrop.claim, (amount, proof))
    });
    vm.prank(user);
    vm.expectRevert(InvalidProof.selector);
    operator.execute(calls);
}
```

The revert at the leaf-verification step demonstrates that the claim path is unreachable through the Operator, confirming the identity mis-binding.
