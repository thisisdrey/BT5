### Title
Unbounded witness registration inflates `WitnessStore`, degrading `doMaintenance()` block-application performance - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`, `chainbase/src/main/java/org/tron/core/store/WitnessStore.java`, `actuator/src/main/java/org/tron/core/actuator/WitnessCreateActuator.java`)

### Summary
`WitnessCreateActuator.validate()` never caps the total number of registered witnesses; it only checks address validity, URL validity, duplicate witness/consensus address, and that the caller's balance covers `AccountUpgradeCost`. Any account meeting the (fixed, non-scaling) cost can register as a witness, and there is no global maximum candidate count analogous to CoreDAO's `CANDIDATE_COUNT_LIMIT` fix. Every registered witness is then iterated, and — critically — sorted with a comparator that performs a store read per comparison, in `MaintenanceManager.doMaintenance()`, which runs synchronously inside block application every maintenance cycle.

### Finding Description
`WitnessCreateActuator.validate()` [1](#0-0)  imposes no limit on the number of witnesses that can exist system-wide — it only rejects duplicate operator/consensus addresses and insufficient balance. Each successful call persists a new entry into `WitnessStore` [2](#0-1) .

Every maintenance cycle (`MaintenanceManager.applyBlock` → `doMaintenance`), which runs synchronously as part of block application, iterates **all** witnesses in the store multiple times: once to accumulate `Vi` values, once to build `newWitnessAddressList` from `getAllWitnesses()`, and once via `countWitness.forEach`: [3](#0-2) .

That full list is then sorted by `ConsensusDelegate.sortWitness` → `WitnessStore.sortWitness`, whose comparator performs a **store lookup (`get(b.toByteArray())`) for every comparison** during the sort: [4](#0-3) . This makes the maintenance-cycle cost effectively O(n log n) database reads where n is the *total* number of ever-registered witnesses — not bounded by `MAX_ACTIVE_WITNESS_NUM` (127) until after the sort/cap is applied in `DposService.updateWitness` [5](#0-4) .

The same unbounded read-and-sort pattern is reachable from the public API path `Wallet.getPaginatedNowWitnessList`, which loads the *entire* `WitnessStore` (`getAllWitnesses()`), applies `countVote`, then sorts the whole list with `WitnessStore.sortWitnesses` before paging: [6](#0-5) .

This mirrors the CoreDAO finding: an unprivileged actor (anyone with enough balance to pay `AccountUpgradeCost` per address) can grow an unbounded array (`WitnessStore`) that is walked/sorted in a critical, per-cycle loop (`doMaintenance`, called from block application) and in a public query API (`getPaginatedNowWitnessList`), with no analog of CoreDAO's `CANDIDATE_COUNT_LIMIT` guard in `WitnessCreateActuator.validate()`.

### Impact Explanation
`doMaintenance()` executes inside `MaintenanceManager.applyBlock`, called synchronously during block application/consensus processing. If the witness count grows large enough (attacker only needs many distinct funded accounts, each paying `AccountUpgradeCost`), the per-cycle DB-read-per-comparator-call sort and multiple full-list iterations could materially slow down or stall block production at every maintenance boundary (every 6 hours by default), risking missed block production windows / degraded consensus throughput across the network. It also degrades the `getPaginatedNowWitnessList` API for all callers since it must load and fully sort the entire witness set regardless of pagination parameters.

### Likelihood Explanation
Likelihood is bounded by cost: each witness registration costs `AccountUpgradeCost` TRX (a fixed dynamic-store parameter, not scaling with existing witness count), so the attack is economically gated but not prevented — there is no hard cap on total witnesses, unlike CoreDAO's fix. An attacker with sufficient capital (spread across many accounts) can register an arbitrarily large number of witnesses over time to grow the store indefinitely, since registrations are never pruned once created (only active-set membership is capped, not total store size).

### Recommendation
Add an explicit maximum total witness count check in `WitnessCreateActuator.validate()` (analogous to CoreDAO's `CANDIDATE_COUNT_LIMIT`), rejecting new registrations once `witnessStore` size reaches the configured limit. Additionally, avoid per-comparison DB reads in `WitnessStore.sortWitness`/`sortWitnesses` by pre-fetching vote counts into a map before sorting, and consider capping/paginating the maintenance-cycle iteration to only witnesses with nonzero votes or within a bounded standby list, rather than the full historical registration set.

### Proof of Concept
1. Attacker funds a large number of distinct accounts, each with balance ≥ `DynamicPropertiesStore.getAccountUpgradeCost()`.
2. For each account, broadcast a `WitnessCreateContract` transaction (via `CreateWitnessServlet`/`CreateWitness2` gRPC), which succeeds because `WitnessCreateActuator.validate()` [7](#0-6)  has no cap on total witness count.
3. Repeat until `WitnessStore` contains a very large number of entries (bounded only by attacker capital, not by protocol).
4. At the next maintenance boundary, `MaintenanceManager.doMaintenance()` iterates and sorts the entire witness set with a per-comparison store read [4](#0-3) , increasing block-application latency proportionally to the inflated witness count; concurrently, any client calling `getPaginatedNowWitnessList` triggers the same full-store load-and-sort [6](#0-5) .

  private void createWitness(final WitnessCreateContract witnessCreateContract)
      throws BalanceInsufficientException {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    WitnessStore witnessStore = chainBaseManager.getWitnessStore();
    //Create Witness by witnessCreateContract
    final WitnessCapsule witnessCapsule = new WitnessCapsule(
        witnessCreateContract.getOwnerAddress(),
        0,
        witnessCreateContract.getUrl().toStringUtf8());

    logger.debug("createWitness,address[{}]", witnessCapsule.createReadableString());
    witnessStore.put(witnessCapsule.createDbKey(), witnessCapsule);
    AccountCapsule accountCapsule = accountStore
        .get(witnessCapsule.createDbKey());
    accountCapsule.setIsWitness(true);
    if (dynamicStore.getAllowMultiSign() == 1) {
      accountCapsule.setDefaultWitnessPermission(dynamicStore);
    }
    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    long cost = dynamicStore.getAccountUpgradeCost();
    adjustBalance(accountStore, witnessCreateContract.getOwnerAddress().toByteArray(), -cost);
    if (dynamicStore.supportBlackHoleOptimization()) {
      dynamicStore.burnTrx(cost);
    } else {
      adjustBalance(accountStore, accountStore.getBlackhole(), +cost);
    }
    dynamicStore.addTotalCreateWitnessCost(cost);
  }

  public void sortWitness(List<ByteString> list, boolean isSortOpt) {
    list.sort(Comparator.comparingLong((ByteString b) -> get(b.toByteArray()).getVoteCount())
        .reversed().thenComparing(isSortOpt
            ? Comparator.comparing(
                (ByteString b) -> ByteArray.toHexString(b.toByteArray())).reversed()
            : Comparator.comparingInt(ByteString::hashCode).reversed()));
  }
