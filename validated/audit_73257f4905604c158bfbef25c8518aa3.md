### Title
Faulty/reverting single-asset oracle feed causes DOS to `borrow`/`repay`/`collateral-add`/`collateral-remove` for any position that shares that asset - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`v0-4-market.clar` composes multiple independent external calls (per-asset Pyth/DIA oracle calls, plus per-vault `accrue` calls) into a single all-or-nothing operation via `get-assets`/`price-multi-resolve` and `accrue-user-debts`/`accrue-user-collateral`. Exactly like the Telcoin "faulty iPlugin" pattern where one bad plugin call blocks unrelated `stake` calls, here one bad/stale/reverting oracle or vault call for *any* asset in a user's position mask aborts the entire market operation for that user, even when the user's intended action does not concern the failing asset.

### Finding Description
`get-assets` builds the list of all assets relevant to a position (via `user-safe-mask`/`mask-to-list-collateral`) and resolves prices for **all of them at once** with a single `unwrap-panic`: [1](#0-0) 

`price-multi-resolve` folds over every asset's oracle data and calls `price-resolve` for each one; if a single `price-resolve` call fails (stale timestamp, oracle contract error, confidence check failure, `ERR-ORACLE-PYTH`, `ERR-ORACLE-DIA`, etc.), the whole fold is marked invalid and the function returns `ERR-ORACLE-MULTI`: [2](#0-1) 

Because `get-assets` wraps this in `unwrap-panic`, that single failing oracle call turns into an unrecoverable panic for the *entire* market call - not a graceful `err` the caller could work around. `price-resolve` itself performs several chained external calls (the oracle call itself, plus `resolve-callcode` which can call `call-ststx-ratio` on an external stSTX-ratio contract, or the ztoken cache resolver) so any one of these sub-calls failing DoSes the whole price resolution: [3](#0-2) [4](#0-3) 

Similarly, `accrue-user-debts`/`accrue-user-collateral` call `accrue-and-cache` for every asset in the user's debt/collateral lists, each wrapped in `unwrap-panic`. `accrue-and-cache` in turn calls `vault-accrue`, which fans out to one of six independent vault contracts (`v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-usdc`, `v0-vault-usdh`, `v0-vault-ststxbtc`): [5](#0-4) [6](#0-5) [7](#0-6) 

`collateral-add` calls `accrue-user-debts`/`accrue-user-collateral` for the user's *entire* existing position before proceeding, and the collateral-management flows (`collateral-add`, `collateral-remove`, and by the same pattern `borrow`/`repay`) call `get-assets`/`get-notional-evaluation` over the full mask of enabled collateral+debt in order to run the health check: [8](#0-7) [9](#0-8) 

Since all of these fan-out calls are aggregated with `unwrap-panic`/`asserts!` that abort the whole transaction on any single failure, a position holding a mix of assets is fully coupled: an oracle/vault problem confined to one asset (e.g. a stale DIA feed for USDH, a paused/mis-integrated vault, or a reverting stSTX-ratio callcode dependency) blocks every operation - `borrow`, `repay`, `collateral-add`, `collateral-remove`, and by extension `liquidate` (which also needs `get-notional-evaluation`/`get-egroup`/pricing) - touching that user's position, even for actions that target a completely different, healthy asset.

### Impact Explanation
This is a temporary freezing-of-funds condition: affected users cannot add/remove collateral, borrow, or repay debt (and liquidators may be unable to liquidate unhealthy positions holding the affected asset) for as long as the faulty oracle/vault dependency remains broken. This maps to the in-scope "temporary freezing of funds" impact class, analogous to the referenced Telcoin finding where a faulty plugin DOSes the whole Staking Module rather than only the affected feature.

### Likelihood Explanation
Likelihood is moderate: it requires one of the several external dependencies used per price/accrual resolution (Pyth, DIA, the stSTX-ratio callcode contract, or any of the six vault contracts) to enter a failing/stale state - not an attacker-controlled event but a realistic operational failure mode (e.g. oracle staleness beyond `max-staleness`, an oracle contract outage, or a vault-side pause/edge-case revert). Because the market code aggregates all of a user's asset resolutions into one atomic, panic-on-failure sequence, any single such failure has an outsized blast radius across users holding that asset anywhere in their position.

### Recommendation
Avoid coupling unrelated assets' external-call failures into a single all-or-nothing transaction: replace `unwrap-panic` fan-outs in `get-assets`, `price-multi-resolve`, `accrue-user-debts`, and `accrue-user-collateral` with logic that can gracefully skip/isolate a failing asset when it is not required for the specific health check being performed (e.g., only require price resolution/accrual for assets actually involved in the requested operation's health check, and consider allowing partial fallback/staleness tolerance or an admin-settable oracle override per asset) so a single faulty dependency cannot block operations that don't depend on it.

### Proof of Concept
1. A user holds collateral in `stSTX` and `USDC`, and debt in `USDH`.
2. DIA's oracle for `USDH` becomes stale (exceeds `max-staleness`) or the `dia-oracle` contract is temporarily broken/paused.
3. The user calls `collateral-add` to top up their `USDC` collateral (unrelated to `USDH`). `collateral-add` triggers `accrue-user-debts`/`get-egroup`/health-check flows that call `get-assets`, which calls `price-multi-resolve` over the user's full asset mask, including `USDH`.
4. `resolve-dia` for `USDH` fails (`ERR-ORACLE-DIA` via `call-dia`'s `unwrap!`), `price-resolve` propagates the error, `price-multi-resolve` marks `valid: false` and returns `ERR-ORACLE-MULTI`, and the enclosing `unwrap-panic` in `get-assets` panics, aborting the entire transaction.
5. The user cannot add `USDC` collateral, repay debt, borrow, or otherwise interact with their position until the `USDH` DIA feed is fixed - despite their intended action having nothing to do with `USDH` pricing.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
