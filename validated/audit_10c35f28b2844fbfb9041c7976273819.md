## Analysis

The external report's core broken invariant: **funds sent to a not-yet-deployed, deterministically-addressed contract can become permanently unrecoverable once the holding account becomes "dormant" (reaped) before the contract's constructor runs, because the deployment path re-creates the account from scratch with no mechanism to reconcile or restore whatever balance existed there before.**

I traced the equivalent lifecycle in `pallet-revive` for `CREATE`/`CREATE2` addresses combined with this fork's dust-routing infrastructure (`pallet-dap` / `pallet-accumulate-and-forward`), and found a structurally identical gap.

### Title
Prefunded `CREATE2` contract addresses permanently lose their balance to the dust-accumulation account if reaped before the constructor runs - ([File: substrate/frame/revive/src/exec.rs])

### Summary
`pallet-revive` computes deterministic `CREATE`/`CREATE2` addresses ahead of deployment via `address::create2`/`address::create1` [1](#0-0) , and it is an explicitly supported pattern to prefund such an address before the contract is deployed — the test `existential_deposit_shall_not_be_charged_twice` sends the exact `min_balance()` to a `create2` address and later deploys a contract there, verifying the ED is not charged twice [2](#0-1) . That test only covers the case where the prefund equals exactly the existential deposit. It never covers the case where the account's balance later drops below the existential deposit before the constructor executes.

### Finding Description
When the constructor frame is entered, `pallet-revive` only checks whether the account currently exists; if it does not, it (re)creates it from scratch via `T::Deposit::init_contract`, which mints a fresh existential deposit and immediately deactivates it — nothing here reads or restores whatever balance previously lived at that address: [3](#0-2) 

`init_contract`'s implementation confirms it mints a brand-new ED unconditionally, with no notion of "was this account previously dusted/reaped": [4](#0-3) 

Separately, this fork routes ordinary dust removal (any account whose free balance drops below ED and has no providers/consumers) into a pot/accumulation account rather than burning it — e.g. `pallet_accumulate_and_forward::Pallet::on_unbalanced` deposits the dust into `Self::accumulation_account()`: [5](#0-4) 

This dust-forwarding behavior is exercised end-to-end in multiple runtime test suites, confirming that a reaped account's balance is swept into a pallet-controlled pot and the original account is fully zeroed (`bob` ends at `0`): [6](#0-5) 

Putting the two pieces together: a `CREATE2` address is a plain, ordinary `AccountId` before deployment — it has no consumer/provider reference protecting it (that protection only starts once `init_contract` + `inc_consumers` run inside the constructor frame, per the same code at lines 1343-1354). If, after prefunding but before the constructor transaction lands, *any* event reduces that account's free balance below the existential deposit (a partial spend, a fee debit, a partial withdrawal, or simply the account having been funded below ED to begin with via any prior partial transfer sequence that still nets a below-ED remainder), the account is reaped by ordinary `pallet-balances` dust logic and its remaining balance is transferred to the `pallet-accumulate-and-forward`/`pallet-dap` buffer — permanently, since that pot account has no path back to the original depositor.

When the constructor later runs at that same address, `frame_system::Pallet::<T>::account_exists` returns `false` (the account was killed), so `init_contract` simply mints a **new, independent** ED. The contract deploys successfully and looks correct, but the funds a user legitimately prefunded to the known future address are gone — captured by the dust pot, with no restoration mechanism anywhere in the constructor path.

### Impact Explanation
This is a permanent user-fund lock/loss: value that a user deliberately and legitimately pre-committed to a contract address (the same "prefund a CREATE2 address" pattern explicitly supported and tested by `existential_deposit_shall_not_be_charged_twice`) can vanish into an unrelated system pot with no way for the depositor or the eventually-deployed contract to reclaim it. This matches the "permanent user-fund lock" impact category directly, requires no malicious peer/validator/governance action, and is reachable purely through normal public account/contract operations.

### Likelihood Explanation
The only precondition is that the prefunded account's balance dips below the existential deposit at any point between prefunding and constructor execution — which can happen through the depositor's own subsequent partial withdrawal, or through any other legitimate balance-reducing operation on that address before the deploying transaction is included. The gap is silent: nothing reverts, nothing warns, deployment succeeds, and only careful balance auditing reveals the shortfall. The existing regression test suite only validates the exact-ED, no-intervening-mutation case, so this scenario is untested and unguarded.

### Recommendation
- Before minting a fresh ED in `T::Deposit::init_contract` (or before `push_frame` for a `Constructor`), have the constructor path check whether the target address was previously known/registered (e.g. via an event log or a short-lived "pending CREATE2" marker) so that any dust routed away from it can be reconciled, or
- At minimum, exclude not-yet-deployed but "reserved" `CREATE2`/`CREATE1` addresses from ordinary dust reaping (similar to how a contract's system consumer already protects a *deployed* contract account, per `exec.rs` lines 1350-1354), and
- Add a regression test mirroring `existential_deposit_shall_not_be_charged_twice` that funds a `create2` address, drives its balance below ED to force a reap into the accumulation/dap pot, then deploys the contract and asserts the original balance is preserved rather than silently dropped.

### Proof of Concept
1. Compute a `CREATE2` address `addr` for a not-yet-deployed contract (via `address::create2`, as in `substrate/frame/revive/src/tests/pvm.rs` around `existential_deposit_shall_not_be_charged_twice`).
2. Fund `addr` with slightly more than `Contracts::min_balance()`.
3. Have `addr` (or any other reducing event) transfer/spend enough to drop its balance below `min_balance()`, with no providers/consumers registered — pallet-balances reaps the account, and (in a runtime wired with `pallet-dap`/`pallet-accumulate-and-forward` as the `DustRemoval` handler, as in the cited `dust_removal_goes_to_accumulation_account` tests) the remaining dust is transferred into the accumulation/buffer pot.
4. Deploy the contract to `addr` via `bare_instantiate` with the matching salt/initcode.
5. Observe: deployment succeeds; `Contracts::min_balance()` is minted fresh for `addr` via `init_contract`; the dust that was swept away in step 3 remains in the accumulation/dap pot and is never returned to `addr` or the original depositor — the prefunded value is permanently lost.

fn existential_deposit_shall_not_be_charged_twice() {
	let (code, _) = compile_module("dummy").unwrap();

	let salt = [0u8; 32];

	ExtBuilder::default().build().execute_with(|| {
		let _ = <Test as Config>::Currency::set_balance(&ALICE, 100_000_000_000_000);
		let callee_addr = create2(
			&ALICE_ADDR,
			&code,
			&[0u8; 0], // empty input
			&salt,
		);
		let callee_account = <Test as Config>::AddressMapper::to_account_id(&callee_addr);

		// first send funds to callee_addr
		let _ = <Test as Config>::Currency::set_balance(&callee_account, Contracts::min_balance());
		assert_eq!(get_balance(&callee_account), Contracts::min_balance());

		// then deploy contract to callee_addr using create2
		let Contract { addr, .. } = builder::bare_instantiate(Code::Upload(code.clone()))
			.salt(Some(salt))
			.build_and_unwrap_contract();

		assert_eq!(callee_addr, addr);

		// check we charged ed only 1 time
		assert_eq!(get_balance(&callee_account), Contracts::min_balance());
	});
}

	/// The native ED is freshly minted and immediately
	/// [`deactivated`](frame_support::traits::fungible::Unbalanced::deactivate) so that
	/// active issuance, and therefore opengov conviction, inflation accounting, etc., is
	/// undisturbed by contract creation. The contract holds a system consumer for as long as it
	/// exists, so this minted ED is not extractable: the account cannot be reaped.
	fn init_contract(to: &T::AccountId) -> DispatchResult {
		let ed = T::Currency::minimum_balance();
		T::Currency::mint_into(to, ed)?;
		T::Currency::deactivate(ed);
		Ok(())
	}
