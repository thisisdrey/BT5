### Title
Exchange (Bancor-style AMM) formula lets floating-point precision blow-up mint an unbacked balance beyond pool reserves - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
java-tron's TRX/TRC10 Exchange feature (`ExchangeCreateContract`, `ExchangeInjectContract`, `ExchangeTransactionContract`) implements a Bancor-style constant-relay-supply AMM in `ExchangeCapsule.transaction()`. By default (legacy/non-hardened path), the swap output is computed with double-precision `Math.pow`/`StrictMath.pow` in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` [1](#0-0) , and the result is only bounds-checked for negative pool balances when the `allowHardenExchangeCalculation` chain parameter is enabled [2](#0-1) . This mirrors the Cetus root cause: an unaudited/edge-case math formula (division/exponent near a boundary) that produces an output disconnected from real reserves, and no invariant check catches it before funds move.

### Finding Description
The exchange math is implemented as:
```
issuedSupply = -supply * (1 - (1 + quant/newBalance)^0.0005)
exchangeBalance = balance * ((1 + supplyQuant/supply)^2000 - 1)
``` [1](#0-0) 

Both stages use `double` arithmetic (`Maths.pow`, ultimately `Math.pow`/`StrictMath.pow`), and the final result is truncated with a raw `(long)` cast with no overflow or sanity check [3](#0-2) . Unlike Cetus's `get_liquidity_from_a`, which blew up as a tick-range denominator approached zero, here the danger is the same class of bug: an attacker-controlled ratio (`quant/newBalance`, or `supplyQuant/supply`) fed into a power function whose result is not checked against the actual token reserves before crediting the counter-party. The only place that validates the post-trade pool balances is the "hardened" path:
```java
if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
  throw new ContractValidateException("Exchange balance must be >=0 after transaction");
}
``` [2](#0-1) 
This check is gated behind `allowHardenExchangeCalculation()`, a chain parameter that must be separately enabled via governance proposal [4](#0-3) . When the legacy (non-hardened) path is active, `ExchangeTransactionActuator.execute()` unconditionally credits the buyer with whatever `ExchangeProcessor.exchange()` returns and debits the pool's booked balance, without ever verifying the pool balance stays non-negative or backed by real assets [5](#0-4) . If the credited token is TRX, this directly increases the trader's real TRX balance via `accountCapsule.setBalance(addExact(newBalance, anotherTokenQuant))` [6](#0-5) , or via `addAssetAmountV2` for TRC10 — a genuine balance credit, while the pool's own booked reserve is only decremented in-place with no floor, since the legacy code path uses plain `-`/`+` arithmetic instead of the checked variants: `secondTokenBalance - buyTokenQuant` with no bound [7](#0-6) .

The existence of `SafeExchangeProcessor` (BigDecimal-based, exact arithmetic) and the `allowHardenExchangeCalculation`/`allowStrictMath` proposal flags [8](#0-7)  confirms that the project itself recognizes the original floating-point Bancor formula as imprecise/unsafe and is migrating away from it — but the fix is optional/governance-gated rather than mandatory, so any network state where the hardened flag is not yet activated retains the exact bug class described in the Cetus report: an unchecked math formula whose edge-case output can exceed the actual backing reserve.

### Impact Explanation
If triggered on a network/testnet where `allowHardenExchangeCalculation` is not active, a crafted sequence of `ExchangeInjectContract`/`ExchangeTransactionContract` calls with extreme but achievable long-range balance ratios can cause `ExchangeProcessor`'s floating-point Bancor formula to produce a `buyTokenQuant` that exceeds the exchange pool's actual second/first token reserve. Because the legacy arithmetic path has no negative-balance guard, this credits the trader with tokens/TRX not actually backed by the pool's assets — an unbacked-balance / fund-theft condition matching the "Medium/High/Critical, concrete unbacked balance" criteria.

### Likelihood Explanation
Reachable by any unprivileged account via a signed `ExchangeTransactionContract`/`ExchangeInjectContract` transaction — no special privilege required, matching the "single signed transaction" requirement. However, exploitability depends on the `allowHardenExchangeCalculation` and `allowStrictMath` proposal states on the target network; if hardened calculation is already active network-wide (which appears to be the direction the codebase is moving), the negative-balance guard blocks the exact drain path, reducing likelihood to require precise governance-state conditions I could not fully confirm (default value of `allowHardenExchangeCalculation` at genesis was not verified in this pass).

### Recommendation
- Make the hardened/negative-balance check (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) unconditional, not gated behind `allowHardenExchangeCalculation`.
- Replace the floating-point `Math.pow`/`StrictMath.pow` Bancor implementation (`ExchangeProcessor`) with the `BigDecimal`-based `SafeExchangeProcessor` as the sole/default implementation, removing the legacy path entirely rather than leaving it opt-in.
- Add invariant assertions after every exchange operation verifying `buyTokenQuant <= buyTokenBalance` before crediting the counter-party's account.

### Proof of Concept
Not independently reproduced in this pass — exploitability is conditional on the exact `allowHardenExchangeCalculation`/`allowStrictMath` governance state of the target chain, which I was unable to fully confirm (default values at genesis vs. current mainnet-activated state). A concrete PoC would require: (1) confirming hardened exchange calculation is inactive, (2) creating an `ExchangeCreateContract` pool with a low-balance token pair, (3) issuing an `ExchangeTransactionContract` with a `quant` chosen to maximize the `(1+quant/newBalance)^0.0005` and subsequent `(1+supplyQuant/supply)^2000` terms, and (4) verifying the resulting `buyTokenQuant` exceeds the pool's actual counter-token reserve. This should be validated in a live/test Devin session against the actual current dynamic-parameter defaults before treating this as a confirmed exploitable bug.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }
