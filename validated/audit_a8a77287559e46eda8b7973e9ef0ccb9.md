### Title
Multisig weight double-counting via signature malleability in `ValidateMultiSign` precompile bypasses on-chain permission threshold - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` TVM precompiled contract, reachable from any smart-contract call via the `validatemultisign` opcode, deduplicates supplied signatures by comparing exact signature bytes rather than by the recovered signer address alone. Because ECDSA signatures are malleable (a valid `(r, s)` has an equally valid `(r, n-s)` counterpart with flipped recovery id), a single private key can produce two byte-distinct but validly-recovering signatures for the same message. Both are accepted and their weights are summed, letting an attacker satisfy a multi-signature permission's threshold using signatures from fewer distinct keys than the permission actually requires.

### Finding Description
`ValidateMultiSign.execute` in [1](#0-0)  iterates over caller-supplied signatures, recovers each signer address, and de-duplicates using:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```
The inner check only skips counting weight when the *exact byte sequence* of the signature has already been seen for that address. If the same address recovers from two *different* signature byte sequences (e.g., the canonical `s` and its malleable complement `n-s`, or any other valid re-encoding), the `matrixContains(executedSignList, sign)` check fails, execution falls through `checkCPUTime()`, and the same key's weight is added to `totalWeight` a second (or further) time. This lets a single private key contribute multiple times toward a `Permission.threshold`, effectively bypassing the intended access-control guarantee that N distinct authorized keys must co-sign.

This differs from the transaction-broadcast-level dedup in `TransactionCapsule.checkWeight`, [2](#0-1) , which (after fork `VERSION_4_7_1`) keys its `HashMap` by the recovered `address` rather than by raw signature bytes, correctly preventing the same double-count. The TVM precompile path was not hardened the same way and still allows the malleability-based double count regardless of fork state, since the vulnerable comparison is unconditional in `ValidateMultiSign.execute`.

### Impact Explanation
Any Solidity/TVM contract relying on `validatemultisign` (address `0x100...09`) to gate privileged operations — e.g., custodial multisig wallets, DAO/committee approvals, treasury releases — can be tricked into treating a single signer as satisfying a higher threshold. An attacker holding just one authorized private key (with weight below the threshold) can forge a second malleable signature from that same key and pass it alongside the original, inflating `totalWeight` past `permission.getThreshold()`. This is a concrete authorization bypass that can lead to unauthorized execution of privileged contract logic and potential theft or unauthorized movement of funds guarded by on-chain multisig checks — directly analogous to the GitLab flaw where a user was treated as authorized when they were not.

### Likelihood Explanation
The precompile is reachable by any account able to submit a `TriggerSmartContract`/deploy that calls `validatemultisign`, i.e., any unprivileged contract deployer or caller — no special privilege needed. Constructing an ECDSA malleable signature variant (`s' = n - s`, flipped `v`) from a signature the attacker already possesses (their own signature) is a standard, well-known cryptographic operation requiring no private key exposure beyond what the attacker already controls. The only precondition is that the target permission's `weight` for that single key is less than `threshold` but the double-counted weight reaches it (e.g., weight=1, threshold=2, single key with weight 1 signs twice using malleable variants to reach weight 2).

### Recommendation
Change the dedup logic in `ValidateMultiSign.execute` to key strictly on `recoveredAddr` (skip weight addition whenever the address has already been counted, regardless of the specific signature bytes), matching the address-based dedup used in `TransactionCapsule.checkWeight` post `VERSION_4_7_1`. Remove reliance on comparing raw signature bytes for deduplication purposes.

### Proof of Concept
1. Deploy or call a contract that invokes the `validatemultisign` precompile against an account with a permission `{threshold: 2, keys: [{address: A, weight: 1}]}` (single key with weight below threshold).
2. Off-chain, sign the message hash once with `A`'s private key to get signature `sig1 = (r, s, v)`.
3. Compute the malleable counterpart `sig2 = (r, n - s, 1 - v)` (or platform-equivalent recovery-id flip) — a validly-recovering signature for the same private key and hash.
4. Submit both `sig1` and `sig2` in the `signatures` array argument to `validatemultisign`.
5. Observe `ValidateMultiSign.execute` recovers `A` from both, the exact-byte check `matrixContains(executedSignList, sign)` fails for the second (different bytes), so both weights (1 + 1 = 2) are added, `totalWeight >= threshold(2)` becomes true, and the precompile returns "true" (`dataOne()`), even though only one distinct authorized key ever signed.

Note: I was not able to directly inspect the `recoverAddrBySign`, `merge`, and `matrixContains` helper implementations within the available index (only match counts were returned, not file contents), so the exact byte-level format details of `sign` concatenation could not be fully confirmed; the core dedup logic shown at [3](#0-2)  is taken directly from the indexed source and demonstrates the flaw as described.

    long currentWeight = 0;

      throw new PermissionException(

    HashMap addMap = new HashMap();

          .signatureToAddress(hash, base64, CommonParameter.getInstance().isECKeyCryptoEngine());
      long weight = getWeight(permission, address);
