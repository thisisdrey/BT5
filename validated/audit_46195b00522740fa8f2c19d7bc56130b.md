### Title
Unchecked `long` addition in `WithdrawBalanceActuator.execute()` can silently wrap the account balance - (File: `actuator/src/main/java/org/tron/core/actuator/WithdrawBalanceActuator.java`)

### Summary
`WithdrawBalanceActuator.validate()` performs an overflow-safe check with `LongMath.checkedAdd(accountCapsule.getBalance(), accountCapsule.getAllowance())` [1](#0-0) , but `execute()` recomputes `allowance` **after** calling `mortgageService.withdrawReward(...)`, which can increase the account's allowance by crediting newly-accrued voting reward, and then adds it to `oldBalance` with a plain, unchecked `+` operator instead of a checked-arithmetic call [2](#0-1) . This mirrors the reported bug class: two values that are computed/updated independently (validated allowance vs. reward-augmented allowance) are combined at execution time without re-validating the sum, and the final combination arithmetic itself is unchecked.

### Finding Description
In `validate()`, the safety check reads `accountCapsule.getAllowance()` *before* the pending reward for the current cycle has been settled onto the account, and only verifies that this (stale, smaller) sum does not overflow `long`: [1](#0-0) 

In `execute()`, `mortgageService.withdrawReward(ownerAddress)` is invoked first, which internally calls `computeReward(...)` and `adjustAllowance(address, reward)` to add the newly computed cycle reward directly onto `accountCapsule`'s allowance field [3](#0-2) [4](#0-3) . Only after this call does `execute()` re-read `accountCapsule.getAllowance()` (now larger than what `validate()` checked) and add it to `oldBalance` using the raw `+` operator with no overflow check:
```java
long oldBalance = accountCapsule.getBalance();
long allowance = accountCapsule.getAllowance();
...
.setBalance(oldBalance + allowance)
``` [5](#0-4) 

This is inconsistent with the codebase's own pattern elsewhere: the TVM-native equivalent, `WithdrawRewardProcessor.execute()`, performs the exact same "add allowance to balance" operation but wraps it in `LongMath.checkedAdd` and throws `ContractExeException` on overflow [6](#0-5) . The plain `WithdrawBalanceActuator` path lacks this protection, so if `oldBalance + allowance` exceeds `Long.MAX_VALUE`, the `long` addition wraps silently to a negative/garbage value that is persisted directly into the account's balance field via `setBalance(...)`.

### Impact Explanation
A silent `long` overflow in `setBalance(oldBalance + allowance)` corrupts the account's on-chain TRX balance into an incorrect (potentially negative, when read as unsigned/misinterpreted, or drastically wrong) value. Because the corrupted value is written straight to the account capsule and persisted to the account store, this is a state-corruption / fund-integrity issue matching the category of "unbacked balance" or "permanent freezing of funds" cited in the validation rules — the account's balance would no longer correctly reflect the sum of its economic inputs, and depending on the wrap value could either lock the account out of using its balance or (if wrapping produces a large positive number due to two's-complement wraparound edge cases) create value out of nothing.

### Likelihood Explanation
The trigger is a single signed `WithdrawBalanceContract` transaction from any witness/SR account, which is the standard, unprivileged reward-withdrawal path available to any voting-reward recipient — no special permissions are needed beyond being a witness with allowance. The core defect (validate-time check on stale data plus an unchecked add on fresh data at execute time) is a straightforward TOCTOU-style arithmetic gap that exists in the code regardless of whether real-world reward magnitudes are likely to reach `Long.MAX_VALUE` in the short term; it directly parallels the reported vulnerability's root cause (independently-set/updated values recombined at settlement without a final bounds check).

### Recommendation
In `WithdrawBalanceActuator.execute()`, replace the unchecked `oldBalance + allowance` with `LongMath.checkedAdd(oldBalance, allowance)` (as already done in `WithdrawRewardProcessor.execute()`), and catch/handle `ArithmeticException` by aborting the transaction the same way `validate()` does. Additionally, re-validate the combined sum after `mortgageService.withdrawReward(...)` runs in `execute()`, since that call can change `allowance` relative to what was checked in `validate()`.

### Proof of Concept
1. An account accrues voting rewards across cycles such that `accountCapsule.getAllowance()` at `validate()` time is just small enough to pass `LongMath.checkedAdd(balance, allowance)`.
2. Between `validate()` and `execute()` (or within `execute()` itself), `mortgageService.withdrawReward(...)` credits additional reward onto `allowance` via `adjustAllowance` [7](#0-6) .
3. `execute()` then computes `oldBalance + allowance` using the new, larger `allowance` with a plain `+`, which — if the sum exceeds `Long.MAX_VALUE` — wraps around instead of throwing, and the wrapped value is persisted via `accountCapsule.setInstance(...).setBalance(oldBalance + allowance)` [8](#0-7) , corrupting the account's stored balance without the transaction failing.

  public void withdrawReward(byte[] address) {
    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return;
    }
    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;
        logger.info("Latest cycle reward {}, {}.", beginCycle, account.getVotesList());
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      delegationStore.setBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
      adjustAllowance(address, reward);
    }
    delegationStore.setBeginCycle(address, endCycle);
    delegationStore.setEndCycle(address, endCycle + 1);
    delegationStore.setAccountVote(endCycle, address, accountCapsule);
    logger.info("Adjust {} allowance {}, now currentCycle {}, beginCycle {}, endCycle {}, "
            + "account vote {}.", Hex.toHexString(address), reward, currentCycle,
        beginCycle, endCycle, accountCapsule.getVotesList());
  }

  public void adjustAllowance(AccountStore accountStore, byte[] accountAddress, long amount)
      throws BalanceInsufficientException {
    AccountCapsule account = accountStore.getUnchecked(accountAddress);
    long allowance = account.getAllowance();
    if (amount == 0) {
      return;
    }

    if (amount < 0 && allowance < -amount) {
      throw new BalanceInsufficientException(
          String.format("%s insufficient balance, amount: %d, allowance: %d",
              StringUtil.createReadableString(accountAddress), amount, allowance));
    }
    account.setAllowance(allowance + amount);
    accountStore.put(account.createDbKey(), account);
  }
