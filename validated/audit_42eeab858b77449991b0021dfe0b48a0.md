### Title
Case-sensitive `disabledApiList` matching causes HTTP/gRPC API-disable policy to fail open - ([File: framework/src/main/java/org/tron/core/services/filter/HttpApiAccessFilter.java])

### Summary
`HttpApiAccessFilter.isDisabled()` and `RpcApiAccessInterceptor.isDisabled()` both normalize only the *incoming* endpoint name to lower-case before checking membership in the operator-supplied `disabledApiList`, but never normalize the entries of `disabledApiList` itself. This mirrors the gRPC-Go xDS RBAC bug class described in GHSA-qc2q-p7wx-3px3: a deny-style policy (here, "this API must be blocked") is compared against a case-insensitively-derived runtime value, so any mismatch in the casing of the configured list entry silently fails the match and the policy fails open.

### Finding Description
`HttpApiAccessFilter` guards every HTTP wallet/monitor/net endpoint on the FullNode, Solidity, and PBFT HTTP services: [1](#0-0) 

The check lower-cases the path segment taken from the live request (`endpoint.split("/")[2].toLowerCase(Locale.ROOT)`) and then tests `disabledApiList.contains(...)`. `disabledApiList` is populated verbatim from operator configuration (e.g. `node.conf`'s `http.disabledApiList` / equivalent CLI/config property) and is never itself normalized to lower-case before being stored in `CommonParameter`.

The identical pattern exists for the gRPC path: [2](#0-1) 

Here `endpoint.split("/")[1].toLowerCase(Locale.ROOT)` is compared against the same unnormalized `disabledApiList`.

Consequence: if an operator configures the disabled-API deny-list using any entry that isn't already all-lowercase (e.g. `GetAccount`, `ListNodes`, `Monitor/GetStatsInfo` — a very plausible operator mistake given TronJsonRpc/Wallet API names are conventionally mixed-case such as `getNowBlock`, `GetAccount`), the comparison `disabledApiList.contains(lowercasedIncomingName)` never succeeds, because the list entry keeps its original casing while the compared value is always fully lower-cased. The intended "deny" rule silently evaluates as a non-match — functionally identical to the reported xDS RBAC bug where an uppercase header matcher (`X-Role`) never matches the unconditionally-lowercased runtime metadata key, causing the DENY rule to fail open.

### Impact Explanation
Any anonymous HTTP or gRPC client can reach an API endpoint that the node operator explicitly intended to disable (via `http.disabledApiList` / rpc equivalent) whenever that operator used non-lowercase casing in the config — a natural mistake given the API names are documented and used in mixed case throughout the wallet/JSON-RPC surface. This is "an API the node can no longer serve [as intended]" in reverse: functionality that operators deliberately turned off (often for resource-exhaustion, information-leak, or attack-surface reduction reasons, e.g. `monitor/getstatsinfo`, `monitor/getnodeinfo`, `net/listnodes`, or heavy wallet query endpoints) remains silently reachable. The security control is bypassed with no error or warning to the operator, matching the "fails open" impact class of the referenced advisory.

### Likelihood Explanation
Exploitation requires no privileges beyond making a normal HTTP GET/POST or gRPC call — it is purely a misconfiguration-triggered bypass, not an attacker-crafted payload. Likelihood of the misconfiguration occurring is moderate-to-high because: (1) API names in java-tron's Wallet/HTTP surface are canonically mixed-case (`getAccount`, `getNowBlock`), so an operator copying names verbatim into the disable list is a natural, easy mistake; (2) there is no validation or warning when `disabledApiList` entries fail to ever match; (3) the existing test suite (`HttpApiAccessFilterTest`) only exercises already-lowercase entries (`getaccount`, `getnowblock`), so the case-sensitivity gap is untested and unnoticed. [3](#0-2) 

### Recommendation
Normalize `disabledApiList` entries to lower-case at load time (or when set via `CommonParameter.setDisabledApiList`) so the comparison in both `HttpApiAccessFilter.isDisabled()` and `RpcApiAccessInterceptor.isDisabled()` is consistently case-insensitive in both directions, eliminating the fail-open condition.

### Proof of Concept
1. Configure the node with `http.disabledApiList = ["GetAccount"]` (mixed case, as an operator familiar with the documented API name `getAccount` would naturally write it).
2. Start the FullNode HTTP API service.
3. Send `GET /wallet/getaccount` (any casing) as an anonymous client.
4. `HttpApiAccessFilter.isDisabled()` computes `endpoint.split("/")[2].toLowerCase(Locale.ROOT)` → `"getaccount"`, and checks `disabledApiList.contains("getaccount")`. Since the list actually contains `"GetAccount"` (not `"getaccount"`), `contains()` returns `false`.
5. The request is *not* blocked and is forwarded to the real servlet, despite the operator's explicit intent to disable it — reproducing the "fails open" behavior described in the advisory, applied to java-tron's API-disable access-control mechanism rather than gRPC-Go's xDS RBAC filter.

  private boolean isDisabled(String endpoint) {
    boolean disabled = false;

    try {
      endpoint = URI.create(endpoint).normalize().toString();
      List<String> disabledApiList = CommonParameter.getInstance().getDisabledApiList();
      if (!disabledApiList.isEmpty()) {
        disabled = disabledApiList.contains(endpoint.split("/")[2].toLowerCase(Locale.ROOT));
      }
    } catch (Exception e) {
      logger.warn("check isDisabled except, endpoint={}, {}", endpoint, e.getMessage());
    }

    return disabled;
  }
