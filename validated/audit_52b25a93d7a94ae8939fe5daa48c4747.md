## Finding

### Title
Missing slippage protection in `ExchangeInjectContract` / `ExchangeWithdrawContract` enables sandwich extraction of exchange liquidity value - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
java-tron's built-in bancor-style token exchange lets an account swap tokens via `ExchangeTransactionContract`, and that path correctly includes an `expected` (minimum-received) field checked on-chain, exactly the slippage protection recommended in the referenced report. However the two other operations that mutate the same AMM-like pool — adding liquidity (`ExchangeInjectContract`) and removing liquidity (`ExchangeWithdrawContract`) — compute the counter-asset amount purely from the pool's *current* on-chain balances at execution time, with no user-supplied minimum/maximum bound at all.

### Finding Description
`ExchangeTransactionActuator` validates the swap output against a user-chosen floor: [1](#0-0) 

In contrast, `ExchangeInjectActuator.doValidate()` computes the proportional counter-token amount from the live pool ratio with no `expected`/min bound: [2](#0-1) 

and `ExchangeWithdrawActuator.doValidate()` does the same for withdrawals, only checking that the computed amount is "precise enough", never that it meets a user-specified floor: [3](#0-2) 

The protobuf contracts confirm neither message carries an `expected`/min field, unlike `ExchangeTransactionContract`: [4](#0-3) 

Because the counter-token quantity is derived strictly from whatever the pool ratio happens to be *at execution time*, any account can shift that ratio immediately before the inject/withdraw transaction executes (via a normal `ExchangeTransactionContract` swap) and shift it back immediately after, extracting the value differential from the exchange creator's liquidity operation — the same "no slippage tolerance" bug class described in the report, just applied to add/remove-liquidity instead of the swap-only path (which java-tron already protects).

### Impact Explanation
An attacker observing a pending `ExchangeInjectContract` or `ExchangeWithdrawContract` transaction (submitted by the exchange creator, the only account authorized to call these — enforced by the "is not creator" check) can front-run it with an `ExchangeTransactionContract` swap to skew `firstTokenBalance`/`secondTokenBalance`, causing the creator's proportional deposit/withdrawal to be computed against an artificially skewed ratio, then back-run with a reverse swap to restore the ratio and capture the resulting arbitrage profit. This is a concrete unauthorized value-extraction/theft-of-funds vector against the exchange creator's pooled assets, since token balances are moved (`accountCapsule.reduceAssetAmountV2` / `addAssetAmountV2`, `exchangeCapsule.setBalance`) strictly based on the manipulated on-chain state.

### Likelihood Explanation
Any unprivileged account can broadcast the sandwiching `ExchangeTransactionContract` swaps around a pending inject/withdraw transaction using only standard transaction broadcast APIs; no special privilege, malicious SR/witness behavior, or off-chain infrastructure is required beyond ordinary mempool observation and timing, which is a realistic capability for any anonymous API client.

### Recommendation
Add `expected`/min (and optionally max) fields to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and validate the on-chain-computed `anotherTokenQuant` against them in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`, mirroring the existing check in `ExchangeTransactionActuator` at lines 217-221.

### Proof of Concept
1. Exchange creator submits `ExchangeInjectContract` with `token_id = firstToken`, `quant = X`, expecting `anotherTokenQuant ≈ secondBalance*X/firstBalance` based on current pool state.
2. Attacker broadcasts an `ExchangeTransactionContract` swap that executes just before the inject, shifting `firstTokenBalance`/`secondTokenBalance`.
3. The inject executes against the skewed ratio (no floor check exists per `ExchangeInjectActuator.java` lines 209-230), causing the creator to inject a disadvantageous ratio of assets.
4. Attacker immediately submits a reverse `ExchangeTransactionContract` swap, restoring the ratio and pocketing the arbitrage difference extracted from the creator's newly injected liquidity.
