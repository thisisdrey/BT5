This confirms the vulnerability. The default sample configs bind the signer's event listener to `0.0.0.0:30000` (e.g., `sample/conf/signer/mainnet-signer-conf.toml:39`), meaning it is reachable from any remote host that can route to that port, and the `/shutdown` branch in `next_event` performs no authentication check whatsoever — unlike the node's RPC endpoints, there is no `auth_password`/`auth_token` comparison anywhere in this dispatch logic.

### Title
Unauthenticated remote `/shutdown` POST permanently halts the signer's event receiver `main_loop` - (`libsigner/src/events.rs`)

### Summary
The signer's HTTP event-listener dispatches on `request.url()` in `SignerEventReceiver::next_event`, and the `/shutdown` branch unconditionally sets `stop_signal` and returns `EventError::Terminated` with no credential, token, or source check. Any remote party who can reach the bound listener socket (which sample configs bind to `0.0.0.0:<port>`) can send a single unauthenticated `POST /shutdown` to permanently terminate the signer's event-processing loop.

### Finding Description
The intended invariant is "only the configured Stacks node (paired via `auth_token`/`auth_password`) can control the signer's event receiver," but the `/shutdown` branch in `next_event` provides no such check:

```rust
} else if request.url() == "/shutdown" {
    event_receiver.stop_signal.store(true, Ordering::SeqCst);
    Err(EventError::Terminated)
}
``` [1](#0-0) 

This is reached identically to any other `POST` to the listener — no `auth_password` comparison, no shared secret, no source-IP allowlist exists anywhere in `next_event` or `with_server`. Compare to the legitimate internal caller `SignerStopSignaler::send`, which crafts the exact same unauthenticated request to trigger its own shutdown:

```rust
let req = format!(
    "POST /shutdown HTTP/1.1\r\nHost: {}\r\nConnection: close\r\nContent-Length: {}\r\nContent-Type: text/plain\r\n\r\n{}",
    self.local_addr, body.len(), body
);
``` [2](#0-1) 

The auth mechanism configured between node and signer (`auth_token`/`auth_password`) is only enforced on the *node's* RPC endpoints (e.g., block-proposal validation) — it is never checked by the signer's own event listener, as confirmed by the doc coordination table listing `auth_password`/`auth_token` as matching only the node-RPC block-proposal path, with no mention of protecting `/shutdown`. [3](#0-2) 

Once `stop_signal` is set, `is_stopped()` returns true and `main_loop` breaks on the next iteration regardless of who set it:
```rust
Err(EventError::Terminated) => {
    info!("Caught termination signal");
    break;
}
``` [4](#0-3) 

Because the listener is spawned via `Signer::spawn(bind_addr)` directly from the configured `endpoint`, and the sample/reference signer config binds to `0.0.0.0:30000` by default, the listener is reachable from any remote host with network access, not just from `127.0.0.1`. [5](#0-4) [6](#0-5) 

### Impact Explanation
A single unauthenticated `POST /shutdown` permanently halts the signer's event-processing thread; the `SignerRunLoop` thread will no longer receive `StackerDBChunksEvent`/`BlockValidateResponse`/burn-block/new-block events forwarded through `forward_event`, effectively taking that signer offline until manually restarted. This matches "Critical - remote crash/unauthenticated DoS from few messages": the signer stops signing/validating blocks it should be participating in, degrading network liveness/safety margins if enough signers are targeted, all from one crafted request repeatable at will against any exposed signer.

### Likelihood Explanation
No preconditions beyond TCP reachability to the configured `endpoint` port are required — no key, no `auth_password`, no StackerDB slot ownership, no P2P handshake. Attacker cost is a single raw HTTP POST. The condition is amplified because the reference/sample configs (`mainnet-signer-conf.toml`, used as the documented starting point) bind to `0.0.0.0`, and `docs/signing.md`'s own warning acknowledges the risk of exposing the signer beyond localhost, but the code offers no enforcement to back that warning up. [7](#0-6) 

### Recommendation
Require the same shared secret used elsewhere in the signer/node pairing (or a dedicated one) to be presented (e.g., as a header or in the body) before honoring `/shutdown`, and reject the request otherwise; alternatively restrict the branch to only be reachable via the internal `SignerStopSignaler` (e.g., by binding the shutdown path to a loopback-only side channel rather than the same public HTTP listener that receives node events).

### Proof of Concept
Rust test plan (extending `libsigner/src/tests/mod.rs` `test_simple_signer` pattern):
1. Spawn a `SignerEventReceiver`/`RunningSigner` bound to `127.0.0.1:<port>` as in existing tests.
2. From a separate unauthenticated `TcpStream::connect` (not via `SignerStopSignaler`), send raw bytes: `POST /shutdown HTTP/1.1\r\nHost: 127.0.0.1:<port>\r\nContent-Length: 0\r\n\r\n`.
3. Assert that `running_signer.stop()` / `join()` returns promptly (i.e., `main_loop` in `libsigner/src/events.rs:296-300` already broke out) rather than blocking, and that no subsequent `/stackerdb_chunks` POST sent afterward is ever processed (the listener socket is gone/thread exited), demonstrating the attacker fully and permanently disabled the receiver with a single unauthenticated message.
