### Title
Unbounded `git_alternate_object_directories` Repeated Field Enables Resource-Exhaustion DoS via Quarantine/Alternates Propagation - (File: internal/git/quarantine/quarantine.go)

### Summary
The `Repository` protobuf message exposes a client-settable, unbounded repeated string field `git_alternate_object_directories` [1](#0-0) . This field flows unchecked into `quarantine.Apply()`, which appends it into a new slice with no cap on length or content size [2](#0-1) , and the resulting `GitAlternateObjectDirectories` is what determines whether Gitaly starts a new transaction at all, per `beginTransactionForRepository` [3](#0-2) . This mirrors the reported bug class: an unbounded, attacker-influenced collection (`accountsWithOpenLoans`) that is later iterated/processed without a size limit, creating a DoS vector.

### Finding Description
`Repository.GitAlternateObjectDirectories` is a normal repeated-string field on the `Repository` message used throughout Gitaly's RPC surface (it is embedded in almost every RPC request that carries a `Repository`) [4](#0-3) . There is no validation of the number of entries or their length before this field is used to build `GIT_ALTERNATE_OBJECT_DIRECTORIES` (see `gitcmd/hooks_options.go`/`hooks_payload.go` usage), nor before it is merged in `quarantine.Apply()`:
```
alternateObjectDirs := make([]string, 0, len(repo.GetGitAlternateObjectDirectories())+1)
alternateObjectDirs = append(alternateObjectDirs, objectDir)
alternateObjectDirs = append(alternateObjectDirs, repo.GetGitAlternateObjectDirectories()...)
``` [2](#0-1) 

Every subsequent `git` invocation for that request inherits this list via environment variables, so Git itself must open/stat every one of the (attacker-supplied) directory paths when resolving objects — this is analogous to the reported issue where `accountsWithOpenLoans` is unboundedly appended and later iterated at cost proportional to array size, causing a gas/DoS blowup.

Additionally, `beginTransactionForRepository` treats the mere *presence* of any alternate directory entries (`len(targetRepo.GetGitAlternateObjectDirectories()) > 0`) as a signal that the request is a "looped-back" quarantine repository from Rails access checks, bypassing normal transaction admission and going through `restoreSnapshotRelativePath` instead [3](#0-2) . A crafted request that legitimately reaches an accessor RPC with a very large `git_alternate_object_directories` list can therefore both skip the normal admission/concurrency-limiting path and force expensive filesystem lookups against a large number of attacker-chosen paths per RPC call, with no cap enforced anywhere in this flow.

This differs meaningfully from the already-mitigated concurrency queue (`internal/limiter/concurrency_limiter.go`), which is refcounted and evicts unused keys immediately [5](#0-4) , and from `AlternateObjectDirectories`/`altObjectDirs`, which does cap recursion depth via `maxAlternatesDepth` when *reading* the on-disk alternates file [6](#0-5) . No equivalent cap exists for the field-supplied list processed in `quarantine.Apply`.

### Impact Explanation
An ordinary authenticated user (or a component looping a crafted `Repository` message back through Gitaly, e.g., during access checks) can supply an arbitrarily large `git_alternate_object_directories` list on a single RPC request. Each subsequent Git subprocess spawned for that request must process the entire list (opening/stat'ing each path, building an equally large environment variable), multiplying per-request CPU/IO cost with no upper bound — this is a repository/RPC-handler resource-exhaustion DoS, consistent with the "unbound storage array" class from the report (analogous to iterating an unbounded `accountsSynthLoans`-style array causing failures once the cost exceeds allowed limits).

### Likelihood Explanation
Likelihood is moderate: any RPC that carries a `Repository` protobuf and does not explicitly reject a populated `git_alternate_object_directories`/`git_object_directory` (documented as intended only for Rails-looped-back quarantine requests) can be abused by supplying a large list directly, since I found no explicit bound/validation on the field size in the reachable code paths (`quarantine.Apply`, `beginTransactionForRepository`, `gitcmd` hook/env construction).

### Recommendation
- Enforce an explicit maximum count (and maximum total byte length) on `Repository.GitAlternateObjectDirectories` at the RPC boundary (e.g., in `storage.Locator.ValidateRepository` or a dedicated validation step in `beginTransactionForRepository`), rejecting requests that exceed the limit before any quarantine/alternates processing occurs.
- Apply the same bound inside `quarantine.Apply()` so that even internally-constructed repository messages cannot exceed it.
- Consider deduplicating entries (mirroring the "only push if not already present" fix pattern from the source report) to avoid redundant processing of repeated paths.

### Proof of Concept
Note: I was unable to execute this against a live server; the following describes the exploit path based on the code reachable and cited above, and should be validated empirically:
1. Issue any RPC accepting a `Repository` message (e.g., `RepositoryService`/`CommitService` accessor RPC) with `git_alternate_object_directories` populated with tens of thousands of distinct nonexistent-but-well-formed relative path strings.
2. Because `beginTransactionForRepository` sees `len(targetRepo.GetGitAlternateObjectDirectories()) > 0` and treats it as an already-quarantined snapshot-scoped request, the normal transaction bookkeeping/validation path is bypassed [3](#0-2) .
3. Downstream, `quarantine.Apply()` (if the RPC also triggers quarantine, e.g., via a write RPC also touching the field) merges the full unbounded list without a limit check [2](#0-1) , and any Git subprocess for that request must process the entire `GIT_ALTERNATE_OBJECT_DIRECTORIES` list.
4. Repeating this with increasingly large lists increases per-request CPU/IO cost linearly/superlinearly, degrading or exhausting Gitaly node resources for concurrent requests — the DoS analog of the reported unbound-array bug.

// putConcurrencyLimit drops the reference to the concurrency limit identified by the given key.
// This must only ever be called after `getConcurrencyLimit()` for the same key. If the reference
// count of the concurrency limit drops to zero then it will be destroyed.
func (c *ConcurrencyLimiter) putConcurrencyLimit(limitingKey string) {
	c.m.Lock()
	defer c.m.Unlock()

	ref := c.limitsByKey[limitingKey]
	if ref == nil {
		panic("semaphore should be in the map")
	}

	if ref.refcount <= 0 {
		panic(fmt.Sprintf("bad semaphore ref refcount %d", ref.refcount))
	}

	ref.refcount--
	if ref.refcount == 0 {
		delete(c.limitsByKey, limitingKey)
	}
}
