### Title
Unauthenticated `RecvError` packets allow remote state poisoning (forced tunnel teardown) via spoofed UDP source address - (File: `outside.go`)

### Summary
`Interface.handleRecvError()` tears down an established, authenticated tunnel in response to a `header.RecvError` packet whose only "authentication" is a check that the UDP source address matches the tunnel's currently known remote `netip.AddrPort`. Because `RecvError` is an unencrypted, unauthenticated packet type processed before any certificate or AEAD verification, and UDP source addresses are trivially spoofable, any attacker who can spoof the known remote address (which is frequently public/static, e.g. a lighthouse) and who can observe or guess the 32-bit `RemoteIndex` can force teardown of a victim's tunnel with zero cryptographic proof of identity, mirroring the `collectedFee`-style bug class: state that other trusted components rely on (the hostmap/tunnel state) can be manipulated by an unauthenticated caller because there is no real access restriction, only a weak address-equality heuristic.

### Finding Description
In `readOutsidePackets`, `header.RecvError` is dispatched immediately after header parsing, before any per-tunnel decryption or certificate check is performed: [1](#0-0) 

`handleRecvError` then looks up the hostinfo purely by the attacker-controlled `h.RemoteIndex` field from the unauthenticated header, and the only integrity check is comparing the packet's source `addr` against the currently stored remote address for that tunnel: [2](#0-1) 

If that comparison passes, `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` are called unconditionally — no certificate, no AEAD tag, no proof of possession of any cryptographic material is required. The "protection" is entirely reliant on the assumption that only the legitimate peer can send from that IP:port, which does not hold against a network attacker capable of UDP source-address spoofing (routable spoofing, off-path capable networks, or simply an attacker positioned on a shared/broadcast network segment). `acceptRecvErrorConfig.ShouldRecvError(addr)` further gates this, but per the CHANGELOG this defaults to allowing recv_error handling: [3](#0-2) 

This is structurally analogous to the `collectedFee` issue: a state-mutating operation (`closeTunnel`/`DeleteHostInfo`, analogous to updating `collectedFee`) is reachable and fully controllable by an unauthenticated party with only trivially-forgeable inputs (`RemoteIndex`, spoofed source address), because no cryptographic/identity-based access restriction gates the call.

### Impact Explanation
An unauthenticated remote attacker can repeatedly and reliably tear down active Nebula tunnels between arbitrary pairs of nodes (denial of service / remote state poisoning of the hostmap), forcing constant re-handshakes and disrupting connectivity, without holding any CA-signed certificate or private key material for the network.

### Likelihood Explanation
Exploitability depends on the attacker's ability to spoof the legitimate peer's `UdpAddr` (source IP:port). This is realistic for on-path or same-broadcast-domain attackers, and for many real-world deployments (unencrypted UDP, no BCP38 filtering) source-IP spoofing toward a known peer address (e.g., a lighthouse's public static address) is not difficult. `RemoteIndex` is only a 32-bit locally-chosen value but is observable on the wire in every packet exchanged with that peer, making it easy to obtain for any attacker who can also see traffic (a prerequisite similar to being able to spoof the source in the first place).

### Recommendation
Do not allow `RecvError`-driven teardown to be trusted based solely on source-address equality. Options include: requiring `RecvError` messages to be authenticated (e.g., HMAC/AEAD-protected using the tunnel's derived keys) rather than sent as bare unauthenticated headers, rate-limiting/backing off repeated `RecvError` handling per remote index, or removing automatic teardown in favor of a lighter-weight probe/re-handshake trigger that doesn't destroy established state on unauthenticated input.

### Proof of Concept
1. Observe (or otherwise learn) the `RemoteIndex` value used between victim node A and node B by passively observing any packet exchanged over the tunnel (the index is present in the unencrypted header of every packet).
2. Craft a bare `header.RecvError` packet (`header.Encode(..., header.RecvError, 0, RemoteIndex, 0)`) with no encryption/authentication.
3. Spoof the UDP source address to match B's known `UdpAddr` and send the packet to A.
4. `handleRecvError` on A finds the hostinfo by `RemoteIndex`, sees `hr == addr`, and calls `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)`, tearing down the tunnel without any cryptographic proof from the sender. [4](#0-3)

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```
