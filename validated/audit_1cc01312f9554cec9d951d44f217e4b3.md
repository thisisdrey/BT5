### Title
Overly Strict Length Equality Check in `MultiEd25519Signature::verify()` Blocks All k-of-n JSON Multisig Submissions Where k < n — (`api/types/src/transaction.rs`)

---

### Summary

The `VerifyInput::verify()` implementation for `MultiEd25519Signature` in the REST API layer enforces `public_keys.len() == signatures.len()`. This is structurally wrong for a k-of-n multisig scheme: a valid authenticator carries **n** public keys but only **k** signatures (k ≤ n), with a bitmap indicating which k keys signed. The check unconditionally rejects every valid k-of-n JSON submission where k < n, making the JSON transaction-submission endpoint non-functional for the majority of real-world multisig accounts. The BCS path is unaffected because it skips `VerifyInput::verify()` entirely.

---

### Finding Description

**Root cause — the wrong invariant:** [1](#0-0) 

At line 1624 the guard reads:

```rust
} else if self.public_keys.len() != self.signatures.len() {
    bail!(
        "MultiEd25519 signature does not have the same number of signatures as public keys"
    )
```

`MultiEd25519` is explicitly documented as a k-of-n scheme: [2](#0-1) 

The correct on-chain representation (produced by the `From` conversion at lines 2464–2490) places all **n** public keys in `public_keys` and only the **k** actual signatures in `signatures`, with a 4-byte bitmap encoding which positions signed: [3](#0-2) 

The crypto layer's own `verify_arbitrary_msg` uses the bitmap to map each of the k signatures to its corresponding public key among the n keys — it never requires k == n: [4](#0-3) 

**Trigger path (JSON submission only):**

```
POST /transactions (application/json)
  → submit_transaction()                          [api/src/transactions.rs:487]
  → SubmitTransactionPost::verify()               [api/src/transactions.rs:99-104]
  → SubmitTransactionRequest::verify()
  → TransactionSignature::MultiEd25519Signature(inner) => inner.verify()
  → MultiEd25519Signature::verify()               [api/types/src/transaction.rs:1624]
  → bail!("...does not have the same number of signatures as public keys")
``` [5](#0-4) [6](#0-5) 

BCS submissions skip `VerifyInput::verify()` entirely (line 102 returns `Ok(())`), so the BCS path is unaffected.

**Existing test confirms the breakage:**

The test `test_multi_ed25519_signed_transaction` (marked `#[ignore]` with the comment *"TODO: migrate once multi-ed25519 is supported"*) demonstrates a 3-of-11 multisig: 11 public keys, 3 signatures, threshold 3, bitmap `0xe0000000`. It submits via BCS (succeeds), then attempts the same via JSON and expects HTTP 202. The JSON leg fails precisely because of the check at line 1624 (11 ≠ 3). [7](#0-6) 

---

### Impact Explanation

Any account whose authentication key was derived from a `MultiEd25519PublicKey` with threshold k < n (the normal case: 2-of-3, 3-of-5, 3-of-11, etc.) **cannot submit transactions through the JSON REST API**. Every such submission is rejected at the input-validation layer before the transaction reaches the mempool or VM. The user's funds are inaccessible via the JSON API path; the only workaround is the BCS endpoint, which most SDK users and integrators do not use by default.

---

### Likelihood Explanation

- The JSON REST API is the primary integration surface for wallets, dApps, and SDKs.
- k-of-n multisig with k < n is the standard configuration (n-of-n is rarely used in practice).
- The bug is triggered by any ordinary user who holds a multisig account and attempts a JSON submission — no special privilege or crafted payload is required.
- The `#[ignore]` test and its comment confirm the developers are aware the JSON path is broken for multisig.

---

### Recommendation

Replace the strict equality check with a check that signatures do not exceed the number of public keys and meet the threshold:

```rust
// Before (wrong):
} else if self.public_keys.len() != self.signatures.len() {
    bail!("MultiEd25519 signature does not have the same number of signatures as public keys")

// After (correct):
} else if self.signatures.len() > self.public_keys.len() {
    bail!("MultiEd25519 signature has more signatures than public keys")
```

The existing threshold check at line 1628 (`self.signatures.len() < self.threshold as usize`) already enforces the lower bound; only the upper bound needs to be `<= public_keys.len()`.

---

### Proof of Concept

1. Create a 3-of-11 `MultiEd25519` account on mainnet (or devnet).
2. Build and sign a transaction with any 3 of the 11 keys.
3. Serialize the signed transaction to JSON (11 entries in `public_keys`, 3 entries in `signatures`, threshold 3, valid 4-byte bitmap).
4. `POST /transactions` with `Content-Type: application/json`.

**Result:** HTTP 400 — `"MultiEd25519 signature does not have the same number of signatures as public keys"` — transaction never reaches the mempool.

**Contrast:** Submit the identical transaction as BCS (`Content-Type: application/x.aptos.signed_transaction+bcs`) → HTTP 202, transaction accepted.

The exact JSON shape that triggers the rejection is documented in the ignored test at `api/src/tests/transactions_test.rs:1027–1053`. [8](#0-7)

impl VerifyInput for MultiEd25519Signature {
    fn verify(&self) -> anyhow::Result<()> {
        if self.public_keys.is_empty() {
            bail!("MultiEd25519 signature has no public keys")
        } else if self.signatures.is_empty() {
            bail!("MultiEd25519 signature has no signatures")
        } else if self.public_keys.len() > MAX_NUM_OF_KEYS {
            bail!(
                "MultiEd25519 signature has over the maximum number of public keys {}",
                MAX_NUM_OF_KEYS
            )
        } else if self.signatures.len() > MAX_NUM_OF_SIGS {
            bail!(
                "MultiEd25519 signature has over the maximum number of signatures {}",
                MAX_NUM_OF_SIGS
            )
        } else if self.public_keys.len() != self.signatures.len() {
            bail!(
                "MultiEd25519 signature does not have the same number of signatures as public keys"
            )
        } else if self.signatures.len() < self.threshold as usize {
            bail!("MultiEd25519 signature does not have enough signatures to pass the threshold")
        } else if self.threshold == 0 {
            bail!("MultiEd25519 signature threshold must be greater than 0")
        }
        for signature in self.signatures.iter() {
            if signature.inner().len() != ED25519_SIGNATURE_LENGTH {
                bail!("MultiEd25519 signature has a signature with the wrong signature length")
            }
        }
        for public_key in self.public_keys.iter() {
            if public_key.inner().len() != ED25519_PUBLIC_KEY_LENGTH {
                bail!("MultiEd25519 signature has a public key with the wrong public key length")
            }
        }

        if self.bitmap.inner().len() != BITMAP_NUM_OF_BYTES {
            bail!(
                "MultiEd25519 signature has an invalid number of bitmap bytes {} expected {}",
                self.bitmap.inner().len(),
                BITMAP_NUM_OF_BYTES
            );
        }

        Ok(())
    }
}

    fn verify_arbitrary_msg(
        &self,
        message: &[u8],
        public_key: &MultiEd25519PublicKey,
    ) -> Result<()> {
        // NOTE: Public keys need not be validated because we use ed25519_dalek's verify_strict,
        // which checks for small order public keys.
        match bitmap_last_set_bit(self.bitmap) {
            Some(last_bit) if (last_bit as usize) < public_key.public_keys.len() => (),
            _ => {
                return Err(anyhow!(
                    "{}",
                    CryptoMaterialError::BitVecError("Signature index is out of range".to_string())
                ))
            },
        };
        let num_ones_in_bitmap = bitmap_count_ones(self.bitmap);
        if num_ones_in_bitmap < public_key.threshold as u32 {
            return Err(anyhow!(
                "{}",
                CryptoMaterialError::BitVecError(
                    "Not enough signatures to meet the threshold".to_string()
                )
            ));
        }
        if num_ones_in_bitmap != self.signatures.len() as u32 {
            return Err(anyhow!(
                "{}",
                CryptoMaterialError::BitVecError(
                    "Bitmap ones and signatures count are not equal".to_string()
                )
            ));
        }
        let mut bitmap_index = 0;
        // TODO: Eventually switch to deterministic batch verification
        for sig in &self.signatures {
            while !bitmap_get_bit(self.bitmap, bitmap_index) {
                bitmap_index += 1;
            }
            let pk = public_key
                .public_keys
                .get(bitmap_index)
                .ok_or_else(|| anyhow::anyhow!("Public key index {bitmap_index} out of bounds"))?;
            sig.verify_arbitrary_msg(message, pk)?;
            bitmap_index += 1;
        }
        Ok(())
    }
