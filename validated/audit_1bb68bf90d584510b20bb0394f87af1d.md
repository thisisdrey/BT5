### Title
USDC blacklist on `disburse()` permanently strands investor principal with no on-chain refund route - (File: `contracts/Loans.sol`)

### Summary
`Loans.disburse()` performs a push-payment `currency.safeTransfer(borrowers[loanId], netDisbursedAmount)` to move investor-funded principal to the borrower's off-ramp address. If that borrower address is on the USDC blacklist (or becomes blacklisted between `create()`/`fund()` and `disburse()`), the `safeTransfer` call reverts every time, and there is no alternate on-chain path to move the already-funded principal out of `ACC_CASH`, mirroring the underlying root cause in the external report: a mandatory push-transfer to a potentially-blacklisted address blocks the only settlement path and strands LP/investor funds in the contract.

### Finding Description
The audited repo's own AI audit findings list already documents this exact class of issue for `Loans.disburse`: [1](#0-0) 

This matches the operational workflow: after `create()` and `fund()`, the investor's USDC sits in the loan's `ACC_CASH`, and `disburse()` is the single defined path that moves it to the borrower: [2](#0-1) 

The only documented recovery mechanism is `updateBorrower`, which requires the *new* borrower address to already be registered in the servicer's address book — a permissioned, off-chain-dependent action that has no unprivileged trigger and can stall indefinitely if the servicer does not act (or the loan's originator/servicer relationship is otherwise unavailable). Absent that servicer intervention, the funded principal has no route out of `ACC_CASH`: `disburse()` cannot succeed (repeated `safeTransfer` revert), and no unprivileged path (e.g., an investor-initiated refund or cancellation) exists to reclaim the funded USDC once `fund()` has moved the loan past `Created`/`FullyFunded` status.

This is structurally identical to the report's root cause: a mandatory, non-bypassable push-transfer to a borrower-controlled address that can enter a token blacklist, with the only recourse being a privileged/manual off-chain-dependent fix, and profit/principal otherwise permanently stuck in the contract.

### Impact Explanation
If a borrower's address is (or becomes) blacklisted by USDC between `create`/`fund` and `disburse`, the investor's fully-committed principal for that loan becomes permanently locked in the `Loans` contract's `ACC_CASH` for that loan, with no unprivileged claim/refund mechanism. This is a real, practically unrecoverable lock of investor USDC caused by a normal, unprivileged lifecycle step (`fund` → `disburse`), which is an explicitly allowed impact under the "Permanent or practically unrecoverable lock of USDC ... caused by an unprivileged path" category. The only recovery (`updateBorrower`) depends on privileged, off-chain-coordinated servicer action and is not guaranteed to be available or timely, so the affected investor's capital is at risk of indefinite loss of access.

### Likelihood Explanation
Likelihood is low-to-moderate and event-driven: it requires USDC's blacklist mechanism to be triggered against a specific borrower's off-ramp address in the narrow window between full funding and disbursement (or generally at any time before a successful disbursement). This mirrors the external report's assessed rarity, but the impact (locked investor principal with no unprivileged recovery) is the same class of issue accepted as in-scope here since it is not merely "malicious token/off-chain system" behavior — it's a structural single-point-of-failure in the protocol's disbursement flow with an inadequate, privilege-gated recovery path.

### Recommendation
Add an unprivileged (or investor-initiated) fallback: if `disburse()` reverts due to a failed transfer to `borrowers[loanId]`, allow the funds to be pulled/claimed by the borrower (or refunded to the investor if disbursement cannot occur) via a `claims`-style mapping instead of a single mandatory push-transfer, and/or allow the investor to cancel/reclaim `ACC_CASH` for a loan that cannot be disbursed within a reasonable window, without requiring a privileged `updateBorrower` intervention.
