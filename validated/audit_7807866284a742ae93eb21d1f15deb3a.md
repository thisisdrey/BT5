## Analysis Summary

The external report's core broken invariant: a fee formula that includes a **user-controlled input to a lower-fee-favoring direction**, without a floor/minimum bound, letting the attacker manipulate that input to make the charged fee collapse toward zero while the underlying (paid-for) resource consumption remains real. I found a structurally identical pattern in Snowbridge's outbound queue v2 gas-metering code, where the attacker-supplied `gas` field of a `Command::CallContract` is fed unclamped into the remote-fee formula.

### Title
Unbounded, attacker-controlled `gas` field in `Command::CallContract` lets senders under-price Snowbridge Ethereum-delivery fees - (File: bridges/snowbridge/primitives/outbound-queue/src/v2/message.rs)

### Summary
`ConstantGasMeter::maximum_dispatch_gas_used_at_most` returns a hardcoded constant for every `Command` variant except `CallContract`, for which it directly returns the caller-supplied `gas` value: `Command::CallContract { gas: gas_limit, .. } => *gas_limit` [1](#0-0)  This `gas` originates unchecked from the XCM `Transact` payload decoded as `ContractCall::V1 { target, calldata, gas, value }` in the XCM→command converter, and is copied straight into `Command::CallContract` with no minimum-bound validation: [2](#0-1) 

### Finding Description
The Snowbridge outbound delivery fee for Ethereum-bound messages follows: `RemoteFee(Message) = MaxGasRequired(Message) * Params.MaxFeePerGas + Params.Reward`, as documented for the v1 pallet (v2 shares the same gas-meter abstraction) [3](#0-2) . For all other commands (`Upgrade`, `UnlockNativeToken`, `RegisterForeignToken`, `MintForeignToken`, `SetOperatingMode`), `MaxGasRequired` is a fixed protocol constant that cannot be manipulated by the sender. For `CallContract`, however, `MaxGasRequired` is taken verbatim from the sender-supplied `gas` field of the XCM `Transact` instruction, with **no minimum enforced** anywhere in the converter or the gas meter.

This mirrors the SpinLottery bug exactly: instead of `_totalSlots` being pushed to a huge value to round the fee to zero, here the attacker pushes `gas` down (e.g. to `0` or `1`) to make `MaxGasRequired(Message)` collapse the remote fee to near-`Params.rewards.remote` only — stripping out the entire gas-cost component of the fee that is supposed to reimburse relayers for real Ethereum execution costs.

### Impact Explanation
An attacker can enqueue arbitrary `CallContract` commands to the outbound queue, each carrying a near-zero `gas` value, paying only the minimal reward/local fee while still consuming: BridgeHub message-queue capacity, merkle-leaf/commitment slots, and forcing relayers to process/submit messages to Ethereum that either can't cover their true gas cost (draining relayer incentive economics) or must be dropped/reverted (since the gateway enforces `Min(GasPrice, Message.MaxFeePerGas) * GasUsed() + Message.Reward` as noted in the module docs, but `MaxGasRequired` set by the attacker underrepresents `GasUsed`). This is public underpriced work that can flood/exhaust the bridge delivery pipeline and starve honest messages of queue capacity and relayer willingness to process them — a direct analog to draining/exhausting a shared, pre-funded resource via a manipulable divisor/multiplier in a public entrypoint.

### Likelihood Explanation
Medium: any account able to route an XCM program containing a `Transact` instruction through the `EthereumBlobExporter`/`snowbridge_pallet_system_v2::Pallet::send` path (subject only to the `AllowedAliasOrigin` filter on the *origin*, not on the `gas` value) can freely choose an arbitrarily small `gas`. No code path clamps or defends against a low/zero `gas`, unlike the constants used for every other command kind.

### Recommendation
Enforce a protocol-level minimum (and possibly maximum) bound on the `gas` field of `Command::CallContract` before it is used in `maximum_dispatch_gas_used_at_most`, e.g. validate `gas >= MIN_CALL_CONTRACT_GAS` in the XCM converter (`convert.rs`) or in `ConstantGasMeter`, rejecting/clamping messages that understate gas, so that `RemoteFee` can never fall below the real minimum cost of dispatching a contract call on Ethereum.

### Proof of Concept
1. Attacker constructs an XCM program with `WithdrawAsset`/`PayFees`, an allowed `AliasOrigin`, `DepositAsset`, and a `Transact` instruction whose encoded call decodes to `ContractCall::V1 { target, calldata, gas: 0, value }`.
2. `XcmConverter::convert` accepts this without validating `gas`, producing `Command::CallContract { gas: 0, .. }` [4](#0-3) .
3. `ConstantGasMeter::maximum_dispatch_gas_used_at_most` returns `0` for this command [5](#0-4) .
4. The remote fee formula `fee_per_gas * gas_used_at_most + reward` collapses to just `reward`, so the message is enqueued, committed, and dispatched for near-zero cost while consuming real queue/relayer/Ethereum-side resources.
5. Repeating this at scale drains relayer reward economics and queue capacity — the direct analog of repeatedly calling `spin()` with an inflated `_totalSlots` to zero out `spinCost`.

**Uncertainty note:** I could not fully verify from the indexed code whether `AllowedAliasOrigin` in production runtime configs (e.g. bridge-hub-westend/rococo) is restrictive enough to block ordinary end users from crafting this XCM (it only gates the aliased *origin*, not the `gas` field), nor whether a downstream check elsewhere (not found via search) clamps `gas`. If a background Devin session is desired to confirm exact runtime configuration of `AllowedAliasOrigin` and check for any missed floor/cap on `gas`, that would need direct repository access beyond this index.

impl GasMeter for ConstantGasMeter {
	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64 {

			Command::SetOperatingMode { .. } => 40_000,
			Command::Upgrade { initializer, .. } => {
				// total maximum gas must also include the gas used for updating the proxy before
				// the the initializer is called.

			Command::MintForeignToken { .. } => 100_000,
			Command::CallContract { gas: gas_limit, .. } => *gas_limit,
		}
	}
}
