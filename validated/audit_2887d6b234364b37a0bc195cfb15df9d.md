### Title
Dust transfer of whitelisted deposit/debt tokens fills a victim's `MAX_TOKENS_PER_USER` slots, reverting all subsequent token additions (DoS) - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
CVE-2022-2719 is a crafted-input assertion failure that aborts processing (a NULL image list passed to `WriteImages`). The closest Metronome analog is a per-account accounting invariant that, once violated, causes every subsequent state-changing call to revert: the `debtTokensOfAccount`/`depositTokensOfAccount` lists are capped at `MAX_TOKENS_PER_USER = 30`, and `Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert with `UserReachedMaxTokens()` when the combined length reaches the cap (`Pool.sol:143-148`, `Pool.sol:204-208`, `Pool.sol:216-220`). Because `DepositToken._transfer` and `_mint` add the token to the recipient's list whenever the recipient's prior balance is zero (`DepositToken.sol:518-520`, `DepositToken.sol:486-488`), any unprivileged EOA can push dust balances of every whitelisted deposit token to a victim and permanently fill all 30 slots.

### Finding Description
1. The pool whitelists N deposit tokens (mseth, msbtc, msfrxeth, etc.). An attacker acquires a dust balance (1 wei) of each `DepositToken`.
2. The attacker calls `DepositToken.transfer(victim, 1)` for each token. Each transfer hits `_transfer` → `balanceOf[victim] == 0` → `pool.addToDepositTokensOfAccount(victim)` (`DepositToken.sol:517-520`). There is no minimum amount and no opt-in by the victim.
3. Once `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) >= 30`, `onlyIfAdditionWillNotReachMaxTokens` reverts (`Pool.sol:143-148`).
4. From then on, any action that would add a new token to the victim's account reverts:
   - `DepositToken.deposit(amount, onBehalfOf = victim)` for any collateral the victim does not yet hold → `_mint` → `addToDepositTokensOfAccount` → revert (`DepositToken.sol:211-237`, `469-489`).
   - `DebtToken.issue`/mint of a new synthetic → `DebtToken._mint` → `pool.addToDebtTokensOfAccount` → revert (`DebtToken.sol:597-600`).
   - Anyone transferring or seizing (`seize` → `_transfer`) a new token type to the victim reverts (`DepositToken.sol:343-345`, `517-520`).

The assertion in ImageMagick fired on a NULL list; here the revert fires on a "full" list — same bug class: an attacker-controlled account state makes a blanket guard assertion fail, denying service on a public entry point.

### Impact Explanation
Temporary freezing / liveness DoS: the victim cannot onboard any new collateral type, cannot mint any new synthetic debt token, and cannot receive new deposit tokens (including via liquidation `seize` if targeted as recipient) until they manually remove dust tokens one by one via `withdraw`/`transfer` (each removal frees one slot via `removeFromDepositTokensOfAccount`). Recovery is possible but requires a transaction per dust token, and the attacker can re-grief cheaply. Existing balances of already-listed tokens remain withdrawable, so this is bounded to temporary freezing of position-management functionality — matching the medium-severity DoS profile of the CVE.

### Likelihood Explanation
- Fully unprivileged: only public `transfer`/`deposit` calls; attacker supplies own tokens. No governor, keeper, or oracle needed.
- Cost is N dust transfers; the dust is recoverable afterward.
- Constraint: impact is bounded by the number of distinct whitelisted tokens and is remediable by the victim, so it does not rise to permanent loss.

### Recommendation
- Do not auto-add tokens to `depositTokensOfAccount`/`debtTokensOfAccount` on `transfer`/`seize` receipt for accounts that never opted in, or only add on `deposit`/`issue` for `onBehalfOf_ == _msgSender()`.
- Alternatively require a minimum economic amount (e.g., > dust threshold) before list insertion, or make list membership opt-in and derive `depositOf`/`debtOf` from explicit registration.

### Proof of Concept
Foundry fork outline (Hardhat equivalent):

```solidity
// fork mainnet at a block with live Pool + DepositTokens
function test_dustGrief() public {
    IPool pool = IPool(POOL);
    address victim = makeAddr("victim");
    address[] memory dts = getAllDepositTokens(pool); // whitelisted deposit tokens

    // victim already holds one position (optional)
    // attacker dusts victim with each deposit token
    for (uint i; i < dts.length; ++i) {
        deal(address(IDepositToken(dts[i]).underlying()), attacker, 1);
        IDepositToken(dts[i]).deposit(1, attacker);      // attacker gets dust msdToken
        IDepositToken(dts[i]).transfer(victim, 1);       // adds token to victim's list
    }
    assertEq(
        pool.depositTokensOfAccountLength(victim) + pool.debtTokensOfAccountLength(victim),
        30 // MAX_TOKENS_PER_USER
    );

    // victim tries to deposit a new collateral type -> reverts
    IDepositToken newDt = IDepositToken(dts[0] == NEW_DT ? dts[1] : NEW_DT);
    vm.expectRevert(IPool.UserReachedMaxTokens.selector);
    newDt.deposit(1e18, victim); // or any transfer of an unheld token to victim
}
```

Caveat: if the deployed pool has few whitelisted tokens, the attacker needs ~30 distinct deposit/debt tokens to fully exhaust the cap; partial filling still blocks proportionally. Also note this class may overlap with previously reported/known account-list griefing issues, which would downgrade it per the engagement rules.
