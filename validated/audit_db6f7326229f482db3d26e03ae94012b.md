### Title
Attacker Can Front-Run `updateMaxTotalSupply()` to DoS `DepositToken.deposit()` - (File: contracts/DepositToken.sol)

### Summary
`DepositToken._mint()` enforces `totalSupply <= maxTotalSupply` with a revert, and the governor can lower `maxTotalSupply` via `updateMaxTotalSupply()` at any time. An unprivileged user who observes a cap-lowering transaction in the mempool can front-run it with a `deposit()` that pushes `totalSupply` above the new cap. After the governor's transaction lands, every subsequent `deposit()` reverts with `SurpassMaxDepositSupply`, temporarily freezing the deposit feature until governance raises the cap again.

### Finding Description
The mint path checks the supply cap inside `_mint()`:

```solidity
// contracts/DepositToken.sol
totalSupply += amount_;
if (totalSupply > maxTotalSupply) revert SurpassMaxDepositSupply();
``` [1](#0-0) 

`deposit()` is a public, permissionless entry point callable by any holder of the underlying collateral token (only guarded by `whenNotPaused`, `nonReentrant`, `onlyIfDepositTokenExists`): [2](#0-1) 

`updateMaxTotalSupply()` is `onlyGovernor` and sets the cap unconditionally with no validation that the new value stays above current `totalSupply`, and no timelock/delay: [3](#0-2) 

Attack scenario (mirrors the reference bug class):

1. `maxTotalSupply = 10_000`, `totalSupply = 2_000`.
2. Governor broadcasts `updateMaxTotalSupply(5_000)`.
3. Attacker front-runs it with `deposit(5_000, attacker)` → `totalSupply = 7_000`.
4. Governor's tx executes → `maxTotalSupply = 5_000 < totalSupply = 7_000`.
5. All `deposit()` calls now revert. Only `withdraw`/`burn` paths or a governance cap increase restore liveness.

The same pattern exists in `DebtToken._mint()` (`if (totalSupply_ > maxTotalSupply) revert SurpassMaxDebtSupply()`), where an attacker could front-run a debt-cap reduction by calling `Pool.issue()` to mint debt above the new cap, DoS-ing `issue`/`leverage` — but the DepositToken path is the cleanest analog since `deposit()` requires no health-factor or collateral checks. [4](#0-3) 

### Impact Explanation
Temporary freezing of funds/liveness: the `deposit` feature is fully bricked (no user can mint msdTOKEN) until governance intervenes to raise the cap or users withdraw below it. The attacker keeps their collateral deposited in the protocol (earning any applicable rewards/fees) while denying the feature to everyone else. No funds are stolen, so this is a griefing/DoS, matching the Medium severity of the reference report.

### Likelihood Explanation
Requires a governance transaction lowering `maxTotalSupply` to be observable in the mempool, and the attacker must hold (or flash-obtain) enough underlying to push `totalSupply` above the target cap. Cap reductions are a normal operational action (the docs list `maxTotalSupply` as a standard per-pool lever: `docs/emergency-flags.md` lines 51-55), so the opportunity is realistic on any chain where the governor's transactions are publicly visible. Cost to the attacker is a deposit that is itself withdrawable afterwards (modulo withdrawal fees), making it nearly free. [5](#0-4) 

### Recommendation
- In `updateMaxTotalSupply()`, revert if `newMaxTotalSupply_ < totalSupply` (and equivalently in `DebtToken.updateMaxTotalSupply`), so the cap can never be set below live supply; or
- Change the check in `_mint` to `if (amount_ + totalSupply > maxTotalSupply) revert` (current behavior) but allow the governor update to be a no-op/bounded; or
- Add a timelock/delay on cap decreases so users cannot sandwich the change, or make cap decreases effective only when `totalSupply` falls below the target.

### Proof of Concept
Hardhat sketch (pattern follows `test/DepositToken.test.ts` `deposit` suite):

```typescript
// given: cap 10, supply 2
await metDepositToken.updateMaxTotalSupply(parseEther('10000'));
await metDepositToken.connect(alice).deposit(parseEther('2000'), alice.address);

// governor queues cap reduction to 5000; attacker front-runs it
await metDepositToken.connect(attacker).deposit(parseEther('5000'), attacker.address);
// totalSupply = 7000

// governor tx lands
await metDepositToken.connect(governor).updateMaxTotalSupply(parseEther('5000'));

// then: all deposits revert
await expect(
  metDepositToken.connect(bob).deposit(parseEther('1'), bob.address)
).revertedWithCustomError(metDepositToken, 'SurpassMaxDepositSupply');
```

Equivalent Foundry variant: call `deposit()` as a pranked attacker to raise `totalSupply` above the pending cap, prank governor to call `updateMaxTotalSupply()`, then `vm.expectRevert(SurpassMaxDepositSupply.selector)` on any further `deposit()`.
