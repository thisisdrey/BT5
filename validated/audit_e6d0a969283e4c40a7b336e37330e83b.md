## Title
`deposit` mints vault shares to an arbitrary attacker-supplied `recipient` with no validation that the recipient can ever move or use them, mirroring the OGV `stake(amount, duration, to)` fund-loss pattern - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
The referenced report describes `OgvStaking.stake(amount, duration, to)`, which lets any caller create a locked position for an arbitrary `to` address. If `to` is a contract that cannot itself call `unstake`/interact with the staking contract, the deposited funds become permanently unrecoverable, because only `to` (as `msg.sender`) can operate on the position. The same "deposit-for-arbitrary-unvalidated-receiver" pattern exists in each Zest vault's `deposit` entry point.

### Finding Description
Every Zest vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`) exposes: [1](#0-0) 

`deposit` takes underlying tokens from `contract-caller` but mints the resulting `zft` shares to an arbitrary caller-supplied `recipient` principal, with no check that `recipient` is capable of acting on the position afterward.

Once minted, only the holder of the `zft` balance can move it further: [2](#0-1) 

`transfer` requires `(or (is-eq tx-sender from) (is-eq contract-caller from))` — i.e., only the `recipient` itself (as `tx-sender`/`contract-caller`) can move the shares out, exactly like `OgvStaking.unstake` requiring the staker to be the caller. Likewise, `redeem` requires `account contract-caller` to equal the balance holder: [3](#0-2) 

And using the shares as market collateral is also strictly tied to the caller identity — `v0-4-market.clar`'s `supply-collateral-add`/`collateral-add` always set `account contract-caller`, never a supplied receiver: [4](#0-3) 

So a `recipient` supplied to `deposit` who cannot call arbitrary contract functions (e.g. an immutable/limited contract, a contract without a fallback path to call Stacks contract functions on this vault, or simply the wrong address) can never call `redeem`, `transfer`, or `collateral-add`/`supply-collateral-add` on the resulting balance. The deposited underlying assets that funded the mint are permanently locked at that address — the exact "loss of staked funds" failure mode described in the OGV report, just replacing "stake position" with "vault share balance."

### Impact Explanation
This maps to **Critical – permanent freezing of funds**: any user who calls `deposit` with a `recipient` that turns out to be unable to interact with the vault contract (a common integration mistake, or a contract deliberately crafted by an attacker to look interactive but that actually has no code path to call `transfer`/`redeem`) causes the underlying deposited assets to be irrecoverably stuck, with no admin/governance recovery path exposed in the vault contracts reviewed.

### Likelihood Explanation
Likelihood is realistic: `deposit`'s `recipient` argument is fully attacker/user controlled and unauthenticated relative to `tx-sender`, exactly as in the original OGV bug. No additional privilege or DAO action is needed to trigger it — any ordinary principal calling `deposit` for another address (their own deployed contract, a friend's contract, a bridge/aggregator address that isn't designed to redeem zTokens) reaches this path directly.

### Recommendation
Follow the same fix pattern the OGV report recommends: split `deposit` into a self-only `deposit(amount, min-out)` that always mints to `contract-caller`, and a separate `deposit-for(amount, min-out, recipient)` used only by trusted/authorized flows (e.g. the market contract's `supply-collateral-add`, which already deposits then immediately consumes the shares under the same account). Additionally, document/verify off-chain (or via a capability check) that any explicit `recipient` passed to a "for" variant can call back into the vault, to avoid unintentionally minting unrecoverable shares to non-interactive addresses.

### Proof of Concept
1. Attacker (or an honest but mistaken user) calls `deposit(amount, min-out, recipient)` on `v0-vault-stx.clar` where `recipient` is a contract with no exposed function capable of invoking `transfer`, `redeem`, or `supply-collateral-add`/`collateral-add` on this vault (e.g. a minimal SIP-010 wrapper contract with no generic call-forwarding).
2. `deposit` succeeds: underlying tokens are pulled from `contract-caller`, `zft` shares are minted to `recipient`.
3. Because `transfer` (lines 752-759) and `redeem` (lines 797-810) both gate on `tx-sender`/`contract-caller` equal to the balance holder (`recipient`), and `recipient` cannot originate a transaction as itself in a useful way, the minted shares — and the underlying value they represent — can never be moved, redeemed, or pledged as collateral.
4. Funds are permanently frozen at `recipient`, with no recovery mechanism in the vault contract.
