### Title
Same-block DeleteAccount+self-Transfer recreation reseeds a NEAR-implicit account's nonce below its own already-consumed high-water mark, enabling transaction replay - (File: runtime/runtime/src/actions.rs)

### Summary
`action_implicit_account_creation_transfer` (`runtime/runtime/src/actions.rs:213-244`) reseeds a recreated NEAR-implicit account's `FullAccess` key nonce to `initial_nonce_value(block_height) = (block_height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` using the *current processing block height*. If the account is deleted and recreated by two locally-processed receipts within the *same* block height `H`, the new seed `(H-1)*1e6` can fall below nonces already consumed by the pre-deletion incarnation during block `H` (which only had to satisfy `< H*1e6`), reopening the nonce-collision window that NEP #3779 (`runtime/runtime/src/access_keys.rs:46-50`) was meant to close.

### Finding Description
`initial_nonce_value` (`runtime/runtime/src/access_keys.rs:46-50`) and its use in `action_implicit_account_creation_transfer` (`runtime/runtime/src/actions.rs:227-228`) always seed to `(block_height-1)*1_000_000`, where `block_height` is the height at which the *recreation receipt* is applied — not the height at which the *account was previously used*. `verify_nonce` (`runtime/runtime/src/verifier.rs:229-234`) only bounds a transaction's nonce by `block_height*1_000_000` of the block in which that transaction is processed, so a nonce `N` can legitimately reach up to just under `H*1_000_000` while being processed in block `H`.

The regression NEP #3779 test (`integration-tests/src/tests/features/access_key_nonce_for_implicit_accounts.rs:112-194`) demonstrates the fix only for a cross-block delete→recreate sequence, where `blocks_number = 5` height-separation guarantees the reseed height is always at least as large as the height in which the old nonce was consumed, so `new_nonce ≥ old_nonce_ceiling`.

That guarantee depends on the recreation Transfer being processed at a height `≥ H+1` relative to the deletion. Per `docs/RuntimeSpec/Components/RuntimeCrate.md:61` and `runtime/runtime/AGENTS.md:27`, a receipt is only processed in the *same* block as its generating transaction when `signer_id == receiver_id` ("local receipt"). An attacker who is the sole holder of the implicit account's private key can submit, within a single chunk:
1. `tx1 = DeleteAccount(signer=self, receiver=self, beneficiary=self, nonce=N1)`
2. `tx2 = Transfer(signer=self, receiver=self, deposit=D, nonce=N2)`, with `N1 < N2`, both close to the upper bound `H*1_000_000` for the block height `H` the chunk is applied at.

Both are local receipts (`predecessor_id == receiver_id == near_implicit_account_id`), and per the documented apply order ("Process local receipts (in order of transactions that generated them)"), receipt1 (`DeleteAccount`) executes first, removing the account (`runtime/runtime/src/actions.rs:371-388`), and receipt2 (`Transfer`) executes immediately after in the *same* block height `H`, triggering `action_implicit_account_creation_transfer` with `block_height = H` (`runtime/runtime/src/actions.rs:213-244`). The reseeded nonce becomes `(H-1)*1_000_000`, which is *less than* `N1` and `N2` that were already consumed earlier in that same block by the pre-deletion incarnation.

Once the key's nonce is regressed this way, any previously signed-and-executed transaction with nonce `M` satisfying `(H-1)*1e6 < M < H*1e6` (including `N1`/`N2` themselves, or any earlier transaction from that key with a nonce in that band) becomes replayable: `verify_nonce`'s `Monotonic` check (`M > (H-1)*1e6`) and upper-bound check (`M < H'*1e6` for any future processing height `H' ≥ H`) both pass.

### Impact Explanation
This breaks the nonce-based replay-prevention invariant for NEAR-implicit accounts, allowing the account's key holder to re-execute an already-applied signed transaction (e.g., a `Transfer`, `FunctionCall`, or other action) a second time. This matches the "double-spend/replay" bounty category, scoped to the implicit account itself: any counterparty or contract that trusted a specific transaction from that account occurring exactly once (e.g., a one-time claim/vote/purchase action, or an outgoing payment) can have that action duplicated.

### Likelihood Explanation
- Requires only an unprivileged attacker who controls the private key of a NEAR-implicit account they already created and used (fully within the described threat model).
- Requires precise but achievable timing: pushing the account's nonce near the current block's ceiling (`height*1_000_000`) by submitting a rapid sequence of transactions, then submitting a `DeleteAccount(beneficiary=self)` and a self-`Transfer` in the *same* chunk so both are processed as local receipts at the same height.
- Cost to the attacker is limited to gas/fees for a handful of transactions; fully repeatable since the attacker fully controls timing and key usage of their own implicit account.
- I was not able to fully re-verify from primary source in this session (a) that access-key nonce updates happen at transaction-conversion time rather than at receipt-execution time, and (b) the exact guaranteed ordering of same-block local receipts relative to interleaved refund receipts generated by `DeleteAccount`; both are strongly implied by `docs/RuntimeSpec/Components/RuntimeCrate.md` and `runtime/runtime/AGENTS.md` but should be confirmed by a concrete unit/integration test before treating this as fully proven.

### Recommendation
Seed the recreated key's nonce using a height strictly greater than any height at which the account could have had nonces validated, e.g., track and persist the highest nonce/height ever used by an account's identity across delete/recreate cycles (or seed using `apply_state.block_height + 1` consistently, and additionally validate that `initial_nonce_value` is monotonic with respect to any nonce that could have been consumed in the same block by using the block height at which the *transaction that produced this receipt* was originally accepted, not the height the receipt happens to execute at). At minimum, disallow `DeleteAccount` and the recreating `Transfer` for the same NEAR-implicit account id from being processed as local receipts within the same block height (e.g., force a same-account delete-then-recreate sequence to always take effect no earlier than the following block).

### Proof of Concept
Integration/test-loop test mirroring `get_status_of_tx_hash_collision_for_near_implicit_account` in `integration-tests/src/tests/features/access_key_nonce_for_implicit_accounts.rs`, but instead of using `check_tx_processing` (which advances `blocks_number = 5` between steps), submit within the same chunk/height `H`:
1. Fund and create the NEAR-implicit account (advance blocks normally).
2. In a single chunk at height `H`: submit `tx1 = DeleteAccount(signer=near_implicit, receiver=near_implicit, beneficiary=near_implicit, nonce=N1)` and `tx2 = Transfer(signer=near_implicit, receiver=near_implicit, deposit>0, nonce=N2)` with `(H-1)*1_000_000 < N1 < N2 < H*1_000_000`.
3. Produce the block and assert both succeed within height `H` (verifying they were processed as local receipts, not delayed to `H+1`).
4. Read back the access key nonce and assert it equals `(H-1)*1_000_000`.
5. Re-submit an earlier already-executed signed transaction with nonce `M` where `(H-1)*1_000_000 < M < H*1_000_000` (e.g. reuse `N1` or `N2`'s signed bytes, or an even earlier consumed nonce in that band) and assert `ProcessTxResponse::ValidTx` / successful execution — demonstrating the replay, versus the expected `InvalidTxError::InvalidNonce`.
