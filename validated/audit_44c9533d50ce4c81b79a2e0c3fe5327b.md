## Title
Unrated-limited, non-constant-time `auth_token` comparison enables brute-force of privileged RPC endpoints - (File: `stackslib/src/net/api/fastcallreadonly.rs`, `stackslib/src/net/api/txsimulate.rs`, `stackslib/src/net/api/blockreplay.rs`, `stackslib/src/net/api/blocksimulate.rs`, `stackslib/src/net/api/postblock_proposal.rs`, `stackslib/src/net/api/postblock_v3.rs`)

### Summary
Every privileged RPC endpoint that is gated by the node's `connection_options.auth_token` performs the authorization check with a single, unrate-limited `String` inequality test against the `authorization` header. There is no rate limiting, lockout, or constant-time comparison anywhere in `stackslib/src/net`, mirroring the report's core bug class: an unauthenticated, boolean pass/fail oracle over a shared secret that can be probed without bound.

### Finding Description
The handlers `RPCFastCallReadOnlyRequestHandler::try_parse_request`, `RPCTransactionSimulateRequestHandler::try_parse_request`, `RPCNakamotoBlockReplayRequestHandler::try_parse_request`, `RPCNakamotoBlockSimulateRequestHandler::try_parse_request`, and `RPCBlockProposalRequestHandler::try_parse_request` all implement the identical pattern: [1](#0-0) 

```rust
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```

The same pattern repeats verbatim in `blockreplay.rs` [2](#0-1) , `blocksimulate.rs` [3](#0-2) , `postblock_proposal.rs` [4](#0-3) , `txsimulate.rs` [5](#0-4) , and the broadcast path in `postblock_v3.rs` [6](#0-5) .

This equality check is the exact analog of the AVideo `password == $parameters['video_password']` oracle: a single unauthenticated request yields a binary "authorized"/"unauthorized" answer, the comparison is over `String`/`&str` (standard library equality, not `subtle::ConstantTimeEq` or any constant-time primitive), and there is no `checkRateLimit()`-equivalent anywhere in `stackslib/src/net` (confirmed by the absence of any `rate_limit`/`RateLimit` symbol in that tree). A remote, unauthenticated client can therefore send an unbounded number of guesses at the `auth_token` with no CAPTCHA, throttling, or lockout, and — because the comparison is not constant-time — can additionally exploit the position-dependent short-circuit of byte/length comparison to narrow the search space faster than a pure brute force, exactly as the report describes ("no rate limiting... enabling efficient offline-speed brute-force").

### Impact Explanation
`auth_token` is the sole authorization mechanism protecting several RPC endpoints, most notably the read-only Clarity execution surfaces `/v3/contracts/fast-call-read/...` (`fastcallreadonly.rs`) and `/v3/transactions/simulate` (`txsimulate.rs`). These endpoints execute attacker-supplied Clarity calls/transactions against chain state under a bounded time/memory budget. An attacker who recovers the `auth_token` via unrated-limited probing gains standing access to repeatedly invoke these compute-bounded read endpoints, producing a sustained bounded-compute DoS surface that would otherwise be gated behind a secret the operator intended to keep private. This matches the in-scope "High - bounded compute DoS on a read endpoint" impact tier once the shared secret is recovered.

### Likelihood Explanation
The likelihood of full compromise depends on operators using a low-entropy `auth_token` (sample configs merely warn it "must match" the signer's `auth_password`, with no minimum-strength requirement) and on the presence of measurable timing signal over the network — the same practical assumptions the original report relies on for the video password (where dictionary attacks are said to be "likely to succeed quickly"). The complete absence of any rate limiting on these endpoints (not one throttling mechanism exists in the entire `stackslib/src/net` tree) is a concrete, easily verified gap independent of the network-timing question, which is what elevates this from a purely theoretical timing issue to a genuine unmitigated brute-force surface.

### Recommendation
1. Rate-limit failed `authorization` header checks per source IP (exponential backoff or fixed lockout window) across all handlers using the `auth`/`password` field.
2. Replace the `!=`/`auth_header != password` comparisons with a constant-time comparison (e.g., `subtle::ConstantTimeEq`) to remove the timing side channel.
3. Consider requiring a minimum-entropy `auth_token` and documenting this requirement in the sample configs (`sample/conf/mainnet-miner-conf.toml`, `sample/conf/signer/mainnet-signer-conf.toml`).

### Proof of Concept
```bash
# Repeatedly probe the fast-call-read-only endpoint with guessed tokens;
# no throttling or lockout is ever triggered by the server.
for token in guess1 guess2 guess3 ...; do
  curl -s -o /dev/null -w "%{http_code} $token\n" \
    -X POST "http://NODE:20443/v3/contracts/fast-call-read/SP000.../contract/function" \
    -H "authorization: $token" \
    -H "Content-Type: application/json" -d '{"sender":"SP000...","arguments":[]}'
done
# Every attempt returns 401 until the exact token is found, with no rate limiting;
# response timing for the "authorization != password" comparison can additionally
# be used to narrow the search space byte-by-byte.
```
