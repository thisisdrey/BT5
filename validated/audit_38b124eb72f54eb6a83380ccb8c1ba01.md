Audit Report

## Title
Snowbridge relayer reward is permanently lost on premature success reporting when the cross-chain deposit is never checked - (File: `bridges/snowbridge/primitives/core/src/reward.rs`)

## Summary
`PayAccountOnLocation::pay_reward` returns `Ok(())` as soon as the reward-minting XCM is validated, fees are charged, and the message is handed to the transport layer via `XcmSender::deliver`, without any confirmation that the `DepositAsset` instruction actually executes successfully on AssetHub. `pallet-bridge-relayers::do_claim_rewards` treats this `Ok(())` as final settlement, deleting the `RelayerRewards` entry and emitting `RewardPaid` before the destination-side crediting is confirmed, so a legitimately-earned reward can be permanently and irrecoverably lost if execution fails at the destination.

## Finding Description
`PayAccountOnLocation::pay_reward` at [1](#0-0)  only performs three local checks — `validate_send`, `XcmExecutor::charge_fees`, and `XcmSender::deliver` — and returns `Ok(())` immediately after `deliver` succeeds. None of these calls confirm that the `ReserveAssetDeposited`/`DepositAsset { assets: AllCounted(1), beneficiary }` instructions embedded in the constructed XCM at [2](#0-1)  will actually execute successfully once the message reaches AssetHub. `deliver()` only guarantees transport-layer hand-off, not destination execution success.

The caller, `do_claim_rewards`, treats this `Ok(())` as final settlement: it calls `maybe_reward.take()` to permanently remove the reward from `RelayerRewards` storage, then invokes `PaymentProcedure::pay_reward`, and finally emits `Event::RewardPaid` — all irreversibly — as shown at [3](#0-2) . There is no attempted/pending intermediate state and no mechanism to detect or recover from destination-side execution failure. The `PaymentProcedure` trait itself, defined at [4](#0-3) , only allows a single synchronous `Result` with no notion of "pending" settlement, unlike the `pallet-treasury` `Paymaster`/`PaymentStatus` pattern referenced in the claim.

If `DepositAsset` fails on AssetHub (e.g., beneficiary account cannot satisfy the reward asset's existential deposit, or the asset is not yet registered), the reserve-deposited assets are trapped by XCM's asset-trap mechanism. Reclaiming a trapped asset requires reconstructing the exact original origin context (`DescendOrigin(InboundQueueLocation) + UniversalOrigin(Ethereum)`), which an ordinary relayer account cannot authorize, since only the inbound queue's own execution context can produce that origin. Meanwhile the on-chain reward record on BridgeHub is already gone.

## Impact Explanation
This is a permanent bridge-state/fund lock: the `RelayerRewards` storage entry (settlement state) advances to a final, non-retryable state and the `RewardPaid` event fires before the actual crediting of the beneficiary on AssetHub is confirmed. A relayer with a legitimately-earned reward can lose it permanently through no fault of their own, with no route to reclaim, since the reward record is deleted from BridgeHub and the trapped assets on AssetHub require an origin context the relayer cannot reconstruct.

## Likelihood Explanation
No privileged or adversarial actor is required. Any relayer calling the public, signed-origin `claim_rewards_to` extrinsic with a beneficiary account on AssetHub that cannot satisfy the reward foreign-asset's existential deposit (or any other destination-side execution failure condition) will trigger this unconditionally — `validate_send`, `charge_fees`, and `deliver` will all succeed locally regardless of the destination-side outcome, since none of them inspect the destination execution result.

## Recommendation
Do not treat successful `deliver()` as final settlement. Introduce an attempted/pending reward state (mirroring `pallet-treasury`'s `Paymaster`/`PaymentStatus` pattern with `Attempted { id }` and `check_status`) so `do_claim_rewards` transitions rewards to a pending state on send rather than deleting them outright, and only clears the entry once destination-side execution success is confirmed (e.g., via a delivery/execution receipt or callback), reverting to a claimable state if the destination execution fails.

## Proof of Concept
1. On BridgeHub, accumulate a `BridgeReward::Snowbridge` reward for a relayer via `register_reward`.
2. Call `claim_rewards_to` with an `AssetHubLocation` beneficiary unable to satisfy the destination foreign-asset's existential deposit. `validate_send`, `charge_fees`, and `deliver` all succeed locally, so `pay_reward` returns `Ok(())`; `do_claim_rewards` removes the `RelayerRewards` entry and emits `RewardPaid` ( [5](#0-4) ).
3. On AssetHub, the XCM executes; `DepositAsset` fails because the beneficiary cannot satisfy the reward asset's ED, so the reserve-deposited assets are trapped rather than credited.
4. The relayer calls `claim_rewards_to` again and receives `Error::NoRewardForRelayer` — the reward is gone from BridgeHub storage and the trapped assets on AssetHub cannot be reclaimed by the relayer.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
