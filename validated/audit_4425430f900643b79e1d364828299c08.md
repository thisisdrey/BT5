Audit Report

## Title
Outbound queue fee-to-remote-currency conversion truncates to zero for small remote fees, permitting free/underpriced message delivery - (bridges/snowbridge/pallets/outbound-queue/src/lib.rs)

## Summary
`Pallet::calculate_fee` in `bridges/snowbridge/pallets/outbound-queue/src/lib.rs` computes the remote (ETH-denominated) delivery fee and rescales it to the local currency's decimals via `convert_from_ether_decimals`, which floor-divides by `10^(ETHER_DECIMALS - T::Decimals::get())` with no rounding-up and no minimum-fee floor. When the pre-conversion fixed-point value is smaller than this divisor — reachable with valid, non-zero `PricingParameters` that pass `PricingParameters::validate()` — the division truncates to `0`, and the message is accepted/queued without the intended remote-fee component. [1](#0-0) 

## Finding Description
`calculate_fee` computes the remote fee in wei via `calculate_remote_fee`, downcasts to `u128`, applies `multiplier`/`exchange_rate`, and calls `convert_from_ether_decimals` to rescale from 18 decimals to the chain's native `T::Decimals`: [2](#0-1) 

`convert_from_ether_decimals` computes `denom = 10^(18 - T::Decimals)` and performs `value.checked_div(denom)`, a floor division with no rounding-up and no error/minimum-fee path: [3](#0-2) 

`PricingParameters::validate()` only rejects hard-zero `exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, or `multiplier` — it does not check that the post-conversion result is non-zero: [4](#0-3) 

The pallet's own test confirms that valid, non-zero `PricingParameters` (`fee_per_gas = 1`, `rewards.remote = 1`, `exchange_rate = 1`, `multiplier = 1`) yield `fee.remote == 0`, with a comment acknowledging this is invalid: [5](#0-4) 

The computed `fee` (including a potentially-zero `remote` component) is returned from `SendMessage::validate` in `send_message_impl.rs` as part of the outbound message's `Ticket`/`Fee`, alongside the message being encoded and readied for `deliver`: [6](#0-5) 

## Impact Explanation
This is a genuine cost-correctness defect in scoped code: `fee.remote` is meant to reimburse the relayer for gas spent delivering the message on Ethereum, and truncating it to zero via `checked_div` floor-division allows the remote-fee component to be `0` while local fee (`fee.local`) remains nonzero — this matches "public underpriced work" language in the impact gate, since the actual charging/reservation of `fee.remote` happens upstream (e.g., in XCM exporter fee-charging code that consumes `Fee<Balance>`), not within this pallet itself. However, whether this is actually exploitable "for free" delivery in production depends on the concrete `T::Decimals` and `PricingParameters` values configured for live BridgeHub runtimes (Rococo/Westend BridgeHub configs were only partially inspected), and whether any fee-collection logic downstream enforces a nonzero minimum independent of this pallet. Based on the code reviewed, the truncation is real and reproducible with valid parameters, but confirming real-world reachability under the actual on-chain `PricingParameters` (which are governance-set and expected to reflect realistic ETH/DOT exchange rates and gas costs) was not verifiable from the code alone within this review.

## Likelihood Explanation
No malicious peer, relayer, or validator action is needed — the bug is a deterministic arithmetic truncation reachable by any combination of `Decimals` (10 for DOT, 12 for KSM) sufficiently smaller than 18 and low `fee_per_gas`/`exchange_rate`/`multiplier` values, which are governance-configured parameters rather than attacker-controlled. Ordinary users calling `SendMessage::validate` (via XCM message export) with the misconfigured-but-valid parameters observed in the existing test would receive `fee.remote == 0`. The precondition (parameters small enough relative to `10^8`/`10^6` divisor) requires specific governance-set pricing that has not been shown to reflect actual production `PricingParameters` values on live BridgeHub chains.

## Recommendation
Change `convert_from_ether_decimals` in `bridges/snowbridge/pallets/outbound-queue/src/lib.rs` to round up (e.g., via `multiply_by_rational_with_rounding`/`Rounding::Up`, or `checked_div` plus remainder-based ceiling) instead of floor-dividing, and add an explicit non-zero floor/error (analogous to `AmountTooSmallAfterConversion` patterns used elsewhere in the codebase) so any non-zero pre-conversion value maps to at least `1` post-conversion, preventing silent zero-fee outcomes for otherwise-valid `PricingParameters`.

## Proof of Concept
The existing unit test in the repository already demonstrates the issue deterministically:

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		/// Calculate fee in remote currency for dispatching a message on Ethereum
		pub(crate) fn calculate_remote_fee(
			gas_used_at_most: u64,
			fee_per_gas: U256,
			reward: U256,
		) -> U256 {
			fee_per_gas.saturating_mul(gas_used_at_most.into()).saturating_add(reward)
		}

		/// The local component of the message processing fees in native currency
		pub(crate) fn calculate_local_fee() -> T::Balance {
			T::WeightToFee::weight_to_fee(
				&T::WeightInfo::do_process_message().saturating_add(T::WeightInfo::commit_single()),
			)
		}

		// 1 DOT has 10 digits of precision
		// 1 KSM has 12 digits of precision
		// 1 ETH has 18 digits of precision
		pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
			let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
			let denom = 10u128.saturating_pow(decimals);
			value.checked_div(denom).expect("divisor is non-zero; qed").into()
		}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };
