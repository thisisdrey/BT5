### Title
Unchecked negative-balance invariant on the legacy (default) TRX/TRC10 Exchange bonding-curve path allows floating-point rounding to drain exchange reserves - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java)

### Summary
The Radiant Capital incident stemmed from an exploitable rounding/precision flaw in DeFi accounting logic that let an attacker extract more value than the protocol's reserves actually backed. java-tron's on-chain Bancor-style token `Exchange` (TRX↔TRC10 AMM, reachable by any unprivileged account via `ExchangeTransactionContract`/`ExchangeWithdrawContract`) contains an analogous class of bug: the legacy pricing path performs the relay-token math in `double` floating point and, unlike the newer "hardened" path, never verifies that the resulting pool reserves stay non-negative before being persisted.

### Finding Description
`ExchangeCapsule.transaction()` selects between two pricing engines depending on the `allowHardenExchangeCalculation` dynamic parameter: [1](#0-0) 

- When `hardenedCalc` is `false` (the default value of `ALLOW_HARDEN_EXCHANGE_CALCULATION` is `0`, as seen in `DynamicPropertiesStore.getAllowHardenExchangeCalculation()`), the legacy `ExchangeProcessor` is used, which computes the Bancor relay/exchange amounts entirely with Java `double` arithmetic and `Math.pow`-based exponentiation, truncating to `long` via a naked cast: [2](#0-1) 

- After computing `buyTokenQuant`, `ExchangeCapsule.transaction()` updates `newFirstTokenBalance`/`newSecondTokenBalance` and only guards against negative reserves **when `hardenedCalc` is true**: [3](#0-2) 

Because this invariant check is gated on `hardenedCalc`, the default/legacy code path persists whatever balances the floating-point formula produces — even if `buyTokenQuant` (derived from imprecise `double` math, especially near pool-balance extremes or after repeated trades that accumulate rounding error) exceeds the actual reserve of the token being bought. The test suite explicitly documents that legacy (`useStrictMath=false`) and even "strict-math" legacy runs diverge from the BigDecimal-based `SafeExchangeProcessor` result, confirming the imprecision is real and non-trivial: [4](#0-3) 

The purpose-built `SafeExchangeProcessor` (BigDecimal, 18-digit scale, `RoundingMode.HALF_UP`) and the `hardenedCalc` negative-balance check were added later specifically to close this gap: [5](#0-4) 

but they only take effect once a Super Representative committee proposal activates `ALLOW_HARDEN_EXCHANGE_CALCULATION`, which is off by default: [6](#0-5) 

`ExchangeTransactionActuator.execute()` reaches this exact code path with attacker-fully-controlled `tokenID`/`tokenQuant`, and unconditionally credits the account with whatever `anotherTokenQuant` the (potentially imprecise/overstated) processor returns, then persists the mutated `ExchangeCapsule` reserves: [7](#0-6) 

### Impact Explanation
On any exchange pool where `allowHardenExchangeCalculation` has not been enabled (the chain default), an attacker able to craft trade sizes that trigger floating-point rounding drift can receive more of the counter-token than the pool's real reserves justify, driving the persisted reserve balance negative (or effectively unbacked) without any actuator-level rejection. Repeated exploitation drains the pool of value that legitimate liquidity providers/withdrawers can no longer redeem — an unbacked-balance / theft-of-funds condition directly analogous to the DeFi precision-exploit pattern referenced in the Radiant Capital report, but here occurring inside java-tron's own on-chain AMM rather than an external contract.

### Likelihood Explanation
Any account holder can broadcast `ExchangeTransactionContract` transactions against any existing TRX/TRC10 exchange pool; no special privileges, contract deployment, or governance access is required. The exploitability depends only on finding reserve ratios/trade sizes where the `double`-based Bancor formula's truncation yields an overstated `buyTokenQuant`, which is a mechanical/mathematical property of the formula rather than a rare edge case — the project's own regression tests show measurable divergence between the legacy and BigDecimal implementations across many realistic balance/quantity combinations.

### Recommendation
Enforce the non-negative reserve invariant unconditionally in `ExchangeCapsule.transaction()` (not only when `hardenedCalc` is true), and/or make `SafeExchangeProcessor`/hardened arithmetic the sole code path for all Exchange actuators, removing the legacy floating-point `ExchangeProcessor` from production use. At minimum, retro-actively activate `ALLOW_HARDEN_EXCHANGE_CALCULATION` network-wide and reject any `ExchangeTransactionContract`/`ExchangeWithdrawActuator` execution that would leave `firstTokenBalance` or `secondTokenBalance` negative, regardless of which processor computed the amount.

### Proof of Concept
1. Create (or identify) an `Exchange` pool via `ExchangeCreateActuator` with reserve values chosen so that the legacy `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` `double` computation for a chosen `sellTokenQuant` truncates to a `buyTokenQuant` larger than the true bonding-curve output (demonstrated divergence pattern shown in `ExchangeProcessorTest.testStrictMath`, e.g. rows such as `{5618633L, 556559904655L, 1L}` where legacy and BigDecimal results differ).
2. Submit an `ExchangeTransactionContract` via the public API selling that token quantity; `ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, allowStrictMath, allowHarden())` with `allowHarden()==false` by default, so the legacy processor and no negative-balance check apply [8](#0-7) .
3. Repeat trades that similarly overstate `buyTokenQuant`; because `ExchangeCapsule.transaction()` skips the `< 0` check for `hardenedCalc == false`, the persisted `secondTokenBalance`/`firstTokenBalance` can be driven below the real backing amount, letting the attacker's account accumulate more counter-token/TRX than the pool ever received, at the expense of other liquidity holders.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
