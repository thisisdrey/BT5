### Title
Fee Bypass on Coarse-Grained NEP-245/IMT Token Swaps via `TokenDiff` Unit-Amount Exemption - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::token_fee` exempts NEP-245 (multi-token) and IMT deltas from the protocol fee whenever the absolute delta amount is `<= 1`, based on an assumption that such deltas represent NFT-like, negligible-value transfers. This assumption is not enforced anywhere: the "amount" is simply the raw integer unit of whatever `TokenId` is being swapped, and the value per unit is entirely determined by the token issuer/depositor. This lets a signer route arbitrarily large economic value through a `TokenDiff` intent while paying zero protocol fee, breaking the equality `fees_owed(value_moved) == fees_collected`.

### Finding Description
`TokenDiff::execute_intent` computes fees only for negative deltas (`token_in`), using `Self::token_fee`: [1](#0-0) 

The fee-exemption logic is: [2](#0-1) 

For `TokenIdType::Nep141` the fee is always applied. For `TokenIdType::Nep245` (multi-token, backing both deposited external MT tokens and internally-minted `Imt` tokens) and `TokenIdType::Imt`, the fee is applied **only if `amount > 1`**; if the delta magnitude is exactly `1`, `Pips::ZERO` is returned and no fee is collected, regardless of the underlying economic value that single unit represents.

This mirrors the reported bug class precisely: a threshold-based protection (there, minimum collateral; here, "amount <= 1 == NFT-like, no fee") is enforced correctly along one execution path but is bypassable because the check relies on a raw magnitude rather than actual value, and nothing constrains the granularity/decimals chosen by whoever mints or deposits the NEP-245/IMT token. A user who controls (or simply deposits into) a NEP-245-compliant contract, or who mints an `Imt` token, can choose to represent the tradable asset with a single indivisible unit worth an arbitrary amount (e.g., 1 unit == 1,000,000 USDC-equivalent). Any `TokenDiff` swap on that token, no matter how much value crosses, always has `|delta| == 1` and is fee-exempt.

### Impact Explanation
This directly falls under the explicitly listed Critical impact category "fees bypassed or over-collected." Any solver/user routing swaps through a NEP-245 or IMT `TokenId` with coarse (unit == 1) granularity permanently avoids the protocol fee on that leg of the trade, i.e., `fees_owed != fees_collected` for the value actually transferred. Because `Imt` tokens are minted directly inside this contract (`contracts/defuse/core/src/intents/imt.rs`, `contracts/defuse/src/contract/tokens/imt.rs`), and because deposits of arbitrary external NEP-245 tokens are permitted, an attacker does not need to compromise anything — they only need to choose the token representation, which is fully within their control as a normal, unprivileged user of the protocol.

### Likelihood Explanation
High. No special privileges, oracle assumptions, or race conditions are required — only choosing to represent value with unit-granularity IMT/NEP-245 tokens (mintable/depositable by any account) and performing normal `TokenDiff` swaps through `execute_intents`/`simulate_intents`. This is strictly cheaper than the analogous minimum-collateral bypass in the original report, since it requires no repeated deposit/borrow/repay/withdraw cycle — a single swap suffices.

### Recommendation
Do not exempt fees based purely on `|delta| <= 1`. Either:
- Charge protocol fee on NEP-245/IMT deltas identically to NEP-141 (proportional `Pips` fee), removing the unit-amount carve-out, or
- If the exemption is meant only for genuinely non-fungible items, gate it on `TokenIdType::Nep171` (true single-copy NFTs) alone, and additionally require that the underlying NEP-245 token collection has `max_supply == 1` per `token_id` (or similar collection-level metadata proving true NFT semantics) before waiving fees, rather than trusting the runtime delta magnitude which is attacker-selectable.

### Proof of Concept
1. Attacker mints (or deposits) a NEP-245/`Imt` token type where the entire economically meaningful position is represented as `1` unit (e.g., via `contracts/defuse/core/src/intents/imt.rs` mint flow, choosing not to subdivide the token).
2. Attacker (as maker) and a counterparty (as taker) each sign a `TokenDiff` intent: maker's diff is `{ nep245_or_imt_token_id: -1, nep141_usdc: +N }`, taker's diff is the closure `{ nep245_or_imt_token_id: +1, nep141_usdc: -N }` for a large `N`.
3. In `TokenDiff::execute_intent`, for the `nep245_or_imt_token_id` leg, `delta.unsigned_abs() == 1`, so `Self::token_fee` returns `Pips::ZERO` per [3](#0-2) , and no fee is collected on that leg even though the trade moves value `N` on the other leg (fee on the `nep141_usdc` leg is separately owed only if that leg itself is the negative delta for that signer — a solver structuring the trade so their own negative delta is always the unit-amount token pays zero fee on their swap-in side).
4. Because `token_fee` is evaluated per-leg independent of the counter-asset's value, the fee due for the actual economic size of the trade is never charged on the exempted leg, confirming `fees_owed != fees_collected`.

Note: full verification of the exact `Imt` minting constraints and whether any external validation limits token granularity was not completed due to tool-call exhaustion (`crates/primitives/token-id/src/imt.rs` and `contracts/defuse/core/src/intents/imt.rs` file contents were not retrievable in the final pass); this should be confirmed by a follow-up review of those files before treating the PoC as fully validated.

    pub fn token_fee(token_id: impl Into<TokenIdType>, amount: u128, fee: Pips) -> Pips {
        let token_id = token_id.into();
        match token_id {
            TokenIdType::Nep141 => {}
            TokenIdType::Nep245 | TokenIdType::Imt if amount > 1 => {}
