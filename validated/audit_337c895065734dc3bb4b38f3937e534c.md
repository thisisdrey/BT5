## Title
Fee-on-transfer NEP-141 tokens allow over-crediting the internal ledger beyond custodied balance - (File: contracts/defuse/src/contract/tokens/nep141/deposit.rs)

### Summary
`Contract::ft_on_transfer` credits a depositor's internal balance with the full nominal `amount` parameter reported by the calling NEP-141 token contract, without ever verifying how much of that value was actually received into the intents contract's own token-ledger balance. A token contract that implements any internal transfer fee (deflationary/tax token, common ERC-20 pattern, permitted since NEP-141 places no restriction on this) will call `ft_on_transfer(sender_id, amount, msg)` with the gross `amount` debited from the sender while crediting the intents contract's on-token balance with `amount - fee`. Defuse mints the full gross `amount` into its internal accounting (`total_supplies` and the depositor's `token_balances`), producing a permanent gap between the sum of internal claims for that `TokenId` and the real balance the contract custodies on the token contract.

### Finding Description
`ft_on_transfer` reads the `amount: U128` argument supplied by the predecessor (the token contract) and passes it straight into `self.deposit(...)`: [1](#0-0) 

`deposit()` then unconditionally increases `total_supplies` and the owner's `token_balances` by that same `amount`, with no cross-check against the contract's actual token balance: [2](#0-1) 

Per NEP-141, the `amount` passed to `ft_on_transfer` is whatever the *token contract* chooses to report; nothing forces it to equal the delta actually added to the receiver's balance in that token's own ledger. A fee-on-transfer token can legitimately deduct `amount` from the sender, add `amount - fee` to the intents contract's balance on the token, and still call `ft_on_transfer(sender_id, amount, msg)` with the gross `amount`. Defuse has no allowlist restricting which NEP-141 contracts may deposit — `token_id` is derived directly from `env::predecessor_account_id()` — so any externally deployed fee-bearing token can be used.

This breaks the custody binding: `sum(internal claims for TokenId) == actual token balance held by defuse`. After such a deposit, internal claims exceed the real custodied balance by the fee amount.

The symmetric case doesn't correct this: on withdrawal, `ft_resolve_withdraw` treats a successful plain `ft_transfer` promise as delivering the full `amount.0` to the receiver, with no refund logic tied to actual amount received by the destination: [3](#0-2) 
So the shortfall introduced at deposit time is never detected or reconciled; it simply persists as an under-collateralization of that `TokenId`'s pool inside defuse.

### Impact Explanation
Once over-credited, the depositor's inflated internal balance is fungible within the intents system — it can be used in `Transfer` or `TokenDiff` intents to acquire real value from other users' genuine token balances, exactly as if it were fully backed. The shortfall is only discovered later, when some holder of that `TokenId` attempts to withdraw and the outgoing `ft_transfer`/`ft_transfer_call` either delivers less than expected (if the token also charges a fee on the way out) or, in the worst case, the aggregate withdrawal requests for that token can no longer be satisfied because defuse's own token balance is insufficient — funds effectively frozen/lost for the users left holding the now-uncollateralized ledger balance. This is a conservation-breaking bug (claimed internal supply vs. real custodied value), fitting the Critical bucket of fees/asset accounting bypassed and funds permanently frozen for later holders.

### Likelihood Explanation
No privileged role is required. Any unprivileged user can deploy or use an existing NEP-141 contract that applies a transfer fee and call `ft_transfer_call` into `defuse`'s `ft_on_transfer`; the contract accepts deposits for arbitrary NEP-141 tokens with no allowlist, and the crediting logic performs no balance verification against the token contract. The only precondition is the existence of such a fee-charging token, which is a normal and legal NEP-141 implementation choice, not a deployment misconfiguration of `defuse` itself.

### Recommendation
After the deposit-triggering transfer call resolves, verify the actual balance change of the specific `token_id` held by the intents contract (e.g., via `ft_balance_of` before/after, or by requiring depositors to only use tokens known to transfer exactly `amount`), and credit the internal ledger with the real delta rather than the caller-supplied nominal `amount`. Alternatively, restrict deposits to an allowlist of NEP-141 tokens verified not to implement transfer fees.

### Proof of Concept
1. Deploy (or use) a NEP-141 token `FEE_FT` whose `ft_transfer_call` implementation deducts `amount` from the sender but credits the receiver only `amount * 99 / 100` (1% fee), then calls `receiver_id.ft_on_transfer(sender_id, amount, msg)` with the full, un-discounted `amount` as required data for the callback.
2. Attacker calls `FEE_FT::ft_transfer_call(defuse, 1_000_000, msg=deposit-to-self)`.
   - `FEE_FT` ledger: attacker -1,000,000; `defuse` (as token holder) +990,000.
   - `defuse::ft_on_transfer(attacker, 1_000_000, msg)` executes `self.deposit(attacker, [(FEE_FT_token_id, 1_000_000)])`, per [4](#0-3) , crediting the attacker's internal balance and `total_supplies` for `FEE_FT_token_id` with the full 1,000,000, per [5](#0-4) .
3. Internal ledger now claims 1,000,000 of `FEE_FT` are custodied, while `defuse`'s real balance on `FEE_FT` is only 990,000 — a 10,000-unit shortfall.
4. Attacker uses a `Transfer`/`TokenDiff` intent to swap part of this inflated 1,000,000 balance for another user's genuine token holdings, realizing real value while leaving the `FEE_FT` pool permanently under-collateralized for whoever withdraws last.

```rust
    fn ft_on_transfer(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        msg: String,
    ) -> PromiseOrValue<U128> {
        require!(amount.0 > 0, "zero amount");

        let token_id = TokenId::Nep141(Nep141TokenId::new(env::predecessor_account_id()));

        let DepositMessage {
            receiver_id,
            action,
        } = if msg.is_empty() {
            DepositMessage::new(sender_id.clone())
        } else {
            msg.parse().unwrap_or_else(|e| panic!("{e}"))
        };

        self.deposit(
            receiver_id.clone(),
            [(token_id.clone(), amount.0)],
            Some("deposit"),
        )
        .unwrap_or_else(|err| err.panic());
```
