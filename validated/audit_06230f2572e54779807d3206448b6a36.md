### Title
Unbounded HTTP response buffering in `StackerDBSession`/`run_http_request` allows a malicious StackerDB replica/node to OOM-crash a signer - ([File: libsigner/src/http.rs])

### Summary
`StackerDBSession::rpc_request` (in `libsigner/src/session.rs`) uses `run_http_request` (in `libsigner/src/http.rs`) to talk to the StackerDB HTTP RPC endpoint hosted by a Stacks node. `run_http_request` reads the entire HTTP response into memory with `sock.read_to_end(&mut buf)` before any size checking is applied, and the non-chunked body path in `decode_http_body` simply does `buf.to_vec()` with no size limit at all. This is the same bug class as the Ollama advisory (`io.ReadAll` with no bound on an untrusted HTTP response), except here it is triggered by an untrusted/compromised StackerDB host rather than a gzip decoder.

### Finding Description
`run_http_request` performs:
```rust
let mut buf = vec![];
sock.read_to_end(&mut buf)?;
``` [1](#0-0) 

There is no cap on how many bytes are read from the socket before `decode_http_response`/`decode_http_body` are even invoked. In the chunked-encoding path, `decode_http_body` does apply `MAX_MESSAGE_LEN` via `HttpChunkedTransferReader`, but the raw `read_to_end` call that fills `buf` in `run_http_request` has already consumed unbounded bytes regardless of transfer encoding, and the "not chunked" body branch just does `buf.to_vec()` with zero size enforcement: [2](#0-1) 

`StackerDBSession::rpc_request`/`list_chunks`/`get_chunks`/`put_chunk` invoke this same unbounded read path when talking to whatever host is configured, and a size check (`SIGNERS_STACKERDB_CHUNK_SIZE`/`STACKERDB_MAX_CHUNK_SIZE`) is only applied *after* the full unbounded response has already been buffered in memory, in `get_latest_chunks`: [3](#0-2) 

So the equality that should hold — "response body size is bounded before allocation, then validated against the protocol limit" — is broken: the size limit is checked only *after* the entire, unbounded payload has already been materialized in a `Vec<u8>`.

### Impact Explanation
A malicious or compromised endpoint that a signer connects to over `StackerDBSession` (e.g. a node presenting itself as a StackerDB replica, or a MITM on that connection) can send an HTTP response with a huge (or effectively unbounded, if using `Connection: close` and a slow/never-ending stream terminated only by connection close) body. `read_to_end` will keep growing `buf` until memory is exhausted, crashing the signer process — a remote, unauthenticated Denial of Service against the signer. This matches CWE-400/409 in the same manner as the Ollama advisory: unbounded buffering of an untrusted HTTP response.

### Likelihood Explanation
Likelihood is moderate: the signer must be pointed at (or MITM'd against) a malicious host for its StackerDB RPC session. `socket_timeout` bounds the *time* per read but not the *total number of bytes* transferred over that time, so a slow-drip attacker sending data just under the read timeout repeatedly can still deliver unbounded bytes before completion, or a fast attacker can flood the full body_in one burst since there's no size ceiling at all on the initial buffer.

### Recommendation
Bound the total bytes read in `run_http_request` (e.g., wrap `sock` in a `Take`/limited reader capped at `MAX_MESSAGE_LEN` or a StackerDB-specific max chunk size) before/while calling `read_to_end`, and reject responses that exceed the cap instead of buffering them fully first, mirroring the bound already used for the chunked-encoding path in `decode_http_body`.

### Proof of Concept
1. Stand up a TCP listener acting as a rogue StackerDB host that a `StackerDBSession` connects to (attacker-controlled `host`, or MITM of the real host).
2. On accept, write `HTTP/1.1 200 OK\r\nConnection: close\r\n\r\n` followed by an unbounded stream of bytes (no `Content-Length`, not chunked), continuously, without closing the connection (or closing only after gigabytes have been sent).
3. Have the signer call `StackerDBSession::list_chunks()` / `get_chunks()`, which calls `rpc_request` → `run_http_request`, which calls `sock.read_to_end(&mut buf)`.
4. Observe the signer process's memory grow unbounded as it reads all attacker-supplied bytes into `buf`, eventually leading to OOM and process crash.

/// Decode an HTTP body, given the headers.
pub fn decode_http_body(headers: &HashMap<String, String>, mut buf: &[u8]) -> io::Result<Vec<u8>> {
    let chunked = if let Some(val) = headers.get("transfer-encoding") {
        val == "chunked"
    } else {
        false
    };

    let body = if chunked {
        // chunked encoding
        let ptr = &mut buf;
        let mut fd = HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into());
        let mut decoded_body = vec![];
        fd.read_to_end(&mut decoded_body)?;
        decoded_body
    } else {
        // body is just as-is
        buf.to_vec()
    };

    Ok(body)
}
