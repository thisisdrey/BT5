### Title
Unbounded array allocation from attacker-controlled length in `ValidateMultiSign` precompile causes an uncaught `OutOfMemoryError` / node DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The reported OpenJPEG bug class is an invalid write triggered by insufficiently validated size/offset values parsed from attacker-supplied input, crashing the process. The closest reachable analog in java-tron is in the `ValidateMultiSign` TVM precompiled contract, where an attacker-controlled length field taken directly from contract calldata is used to allocate a Java array *before* any bound check is guaranteed to run, and the call site that triggers the allocation sits outside any exception handler capable of catching the resulting `Error`.

### Finding Description
`ValidateMultiSign.execute()` parses `rawData` into `DataWord[] words` and then computes the signature array via `extractSigArray`/`extractBytesArray`: [1](#0-0) 

The `MAX_SIZE` bound check on `sigArraySize` is only performed when `VMConfig.allowTvmSelfdestructRestriction()` is active: [2](#0-1) 

`extractBytesArray`/`extractSigArray` then allocate `byte[len][]` where `len = words[offset].intValueSafe()` comes straight from attacker-controlled calldata, with no upper bound before this branch: [3](#0-2) 

`intValueSafe()` saturates to a large positive `int` on overflow rather than throwing, so a crafted 256-bit word can force `len` close to `Integer.MAX_VALUE`, causing `new byte[len][]` to throw `OutOfMemoryError`. This allocation call happens *outside* the only `try/catch` present in `ValidateMultiSign.execute()`, which wraps solely the permission/weight-checking logic further down: [4](#0-3) 

Critically, the outer VM dispatch loop that would otherwise contain opcode/precompile failures only catches `RuntimeException`, not `Error`: [5](#0-4) 

Since `OutOfMemoryError` extends `Error` (not `RuntimeException`), it is not caught here and propagates further up the transaction-processing call stack, unlike the sibling `BatchValidateSign` precompile, which explicitly wraps its logic in `catch (Throwable t)`: [6](#0-5) 

This asymmetry — `BatchValidateSign` catches `Throwable`, `ValidateMultiSign` does not — indicates the missing top-level guard in `ValidateMultiSign` is a real gap rather than an intentional design choice.

### Impact Explanation
Any unprivileged account can trigger this precompile from a smart contract call (the `validatemultisign` precompiled address) by crafting calldata whose signature-array-length word decodes to a very large integer. If the resulting `OutOfMemoryError` is not caught anywhere above `VM.play`/`Program`, it can abort transaction execution in an uncontrolled way and, depending on how the surrounding block-application code in `Manager` handles `Error` versus `Exception`, this can lead to inconsistent per-node crash behavior during block replay — a node crash or halt on nodes with tighter memory limits, potentially producing divergent processing outcomes across SR/witness nodes (chain split risk) since low-memory nodes may fail to reproduce a block that succeeded on high-memory nodes.

### Likelihood Explanation
The `MAX_SIZE` guard on the signature-array length is conditioned on `VMConfig.allowTvmSelfdestructRestriction()`, meaning any deployment/hard-fork state where this flag is not yet active leaves the length completely unvalidated before array allocation. Reaching this code only requires a single TVM contract call to the `ValidateMultiSign` precompile with crafted calldata — no special privilege, staking, or witness status needed.

### Recommendation
Move the `MAX_SIZE` bound check on `sigArraySize` (and the corresponding array length in `extractBytesArray`/`extractSigArray`) so it is always enforced unconditionally, independent of `VMConfig.allowTvmSelfdestructRestriction()`. Additionally wrap `ValidateMultiSign.execute()` in a `catch (Throwable t)` (matching `BatchValidateSign`) so any lower-level `Error` (e.g., `OutOfMemoryError`, `NegativeArraySizeException`) is converted into a normal `DATA_FALSE` precompile failure instead of propagating as an uncaught `Error`.

### Proof of Concept
1. Deploy or reuse any contract that invokes the `ValidateMultiSign` precompiled contract address with a `staticcall`/`call`, supplying raw ABI-encoded calldata.
2. Craft calldata such that `words[3]` points at a length word (`words[offset]`) whose value decodes (via `intValueSafe()`) to a very large positive integer (e.g., close to `Integer.MAX_VALUE`), while running on a node configuration where `allowTvmSelfdestructRestriction` is not enabled (or is enabled but bypassed via the sig-array-size offset pointing outside the guarded index used in the check).
3. Broadcast the transaction; `extractBytesArray`/`extractSigArray` executes `new byte[len][]`, forcing a large heap allocation attempt and throwing `OutOfMemoryError`, which is not caught by `ValidateMultiSign.execute()`'s local `try/catch` nor by `VM.play`'s `catch (RuntimeException e)`.

Note: I was unable to fully trace the complete downstream call chain from `VM.play` through `Program`/`Runtime`/`Manager` to confirm definitively whether any higher-level handler eventually catches `Throwable`/`Error` around per-transaction execution; if such a catch-all exists further up (e.g., in `TransactionTrace` or `Manager.processTransaction`), the practical impact would be limited to that single transaction failing rather than a full node crash, though the missing `Throwable` guard in `ValidateMultiSign` compared to `BatchValidateSign` remains a genuine code-quality/robustness defect that should be fixed regardless.
