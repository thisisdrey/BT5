Confirming the key fact: the signature digest in `SlotMetadata::auth_digest()` binds only to `(slot_id, slot_version, data_hash)` and never to the target StackerDB's `smart_contract_id`. This is the load-bearing detail for a cross-contract replay analog.### Title
StackerDB chunk signature is not bound to the target smart-contract ID, enabling cross-StackerDB signature/chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
The JWT report's bug class is "a signed credential is accepted without validating the field that scopes it to its intended context (`aud`)." The closest reachable analog in this repo is `StackerDB` chunk authentication: `SlotMetadata::auth_digest()` computes the signed digest solely from `(slot_id, slot_version, data_hash)` and never includes the `smart_contract_id` (the StackerDB "audience") that the chunk write/relay path checks against separately. A signer whose key owns a slot in more than one StackerDB instance can have a validly-signed chunk for StackerDB A accepted as authentic for StackerDB B, as long as slot_id/version/data match — the same missing-scope-binding pattern as the CVE.

### Finding Description
`SlotMetadata::auth_digest()` hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

`sign()`/`verify()` operate purely over that digest, recovering a public key and comparing its hash to a caller-supplied `principal: &StacksAddress` — no contract/DB identifier is part of the signed material: [2](#0-1) 

The "audience" check (i.e., which `smart_contract_id`/StackerDB instance this chunk is destined for) happens outside the signature, as a separate DB lookup of the expected signer for that `(smart_contract_id, slot_id)` pair, then simply asserting the *recovered* key matches that signer:

- Local write path: `StackerDBTx::try_replace_chunk` looks up `slot_validation.signer` for `(smart_contract, slot_desc.slot_id)` and calls `slot_desc.verify(&slot_validation.signer)`, which only checks the digest-bound fields, not that the signature was created *for this contract*: [3](#0-2) 

- Gossip/relay path: `StackerDBSync::validate_received_chunk` does the same thing — fetch `get_slot_signer(smart_contract_id, data.slot_id)` then `slot_metadata.verify(&addr)`: [4](#0-3) 

Because the smart-contract identity is never folded into the signed digest, if the same signer address is assigned the same `slot_id` in two different StackerDB contracts (which is normal: many StackerDB configs reuse the same signer set, e.g., signer-coordination StackerDBs across reward cycles or multiple `.signers-*` contracts), a chunk `(slot_id, slot_version, data)` legitimately signed and broadcast for contract A verifies just as well as a chunk for contract B with the same `(slot_id, slot_version, data_hash)`. An attacker (any unprivileged network peer, or the API caller of `POST /v2/stackerdb/:principal/:contract/chunks`, whose contract path segment is taken directly from the URL and not bound into the signature) can therefore submit/relay a chunk under contract B's path using the exact bytes and signature that were valid for contract A, and it will pass `BadSigner` checks and be stored/gossiped as authentic data for contract B.

### Impact Explanation
This breaks the equality "signature proves authorship *for this specific StackerDB instance*" — the signature only proves "this signer authored slot X/version Y/hash Z," with no binding to which StackerDB it belongs to. This enables unauthorized cross-contract write / forged-data propagation: data that a signer only intended, and could only cryptographically attest, for one StackerDB context is stored as authentic for another. Where StackerDB writes drive protocol behavior (e.g., signer-coordination StackerDBs consumed by `stacks-signer`/miners), cross-context replay could inject stale or out-of-context, but validly-signed, payloads into a different StackerDB replica set, propagating network-wide via the P2P push/gossip path in `stackslib/src/net/stackerdb/mod.rs` and `sync.rs`.

### Likelihood Explanation
Exploitability hinges on whether any real deployed StackerDB configuration assigns the same signer address to the same `slot_id` across two distinct contracts — this is plausible by design, since StackerDB signer sets are commonly derived from the same reward-cycle signer set across multiple StackerDB contracts, and slot assignment order is deterministic (`create_stackerdb`/`reconfigure_stackerdb` assign slot IDs in list order) . I could not fully verify from the indexed code whether current production configs (e.g., `.signers-N-M` contracts) always produce non-overlapping signer/slot_id pairings across contracts, so likelihood is moderate/context-dependent rather than proven-in-production.

### Recommendation
Include the `smart_contract_id` (and ideally a network/chain identifier) as part of the signed `auth_digest()` in `libstackerdb/src/libstackerdb.rs`, so verification in `db.rs::try_replace_chunk` and `stackerdb/mod.rs::validate_received_chunk` cryptographically binds the signature to the specific StackerDB instance it was intended for, mirroring how `jwt.WithAudience()` binds a JWT to its intended service.

### Proof of Concept
1. Configure two StackerDB contracts, A and B, both assigning slot 0 to the same signer address (achievable when both contracts pull from the same underlying signer set with matching order).
2. Signer signs and posts a legitimate chunk for contract A: `slot_id=0, slot_version=1, data=X` via `POST /v2/stackerdb/<addr>/<contractA>/chunks`; it is accepted (`stackslib/src/net/api/poststackerdbchunk.rs`).
3. Attacker (no signer key needed) resubmits the identical `StackerDBChunkData` (same `slot_id`, `slot_version`, `sig`, `data`) to `POST /v2/stackerdb/<addr>/<contractB>/chunks`.
4. `try_replace_chunk` for contract B looks up its own `slot_validation.signer` (same address), calls `slot_desc.verify(&signer)` — which succeeds because the digest never referenced contract A or B — and the chunk is stored as authentic data for contract B, despite never having been signed with contract B in mind.     fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
