### Title
Unvalidated Arbitrary Price Ratio in TRC10 Exchange Pool Creation Enables Permanent Price Manipulation and Trader Fund Loss - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`)

### Summary
Any account can create a bancor-style TRC10↔TRX/TRC10 liquidity pool (`ExchangeCreateContract`) with a first/second token balance ratio it chooses arbitrarily, since `ExchangeCreateActuator` only checks that balances are positive and below a global cap — it never validates the resulting price against any external reference. Because a TRC10 token can be freely minted by any asset issuer before the pool is created, an attacker can seed a pool with a self-issued worthless token against real TRX/TRC10 at a wildly distorted ratio and then use `ExchangeTransactionActuator` to make tiny, cheap trades that barely move the bancor-formula price, keeping the false price stable indefinitely and draining or trapping counter-party value from any user who swaps against it. This directly mirrors the MonoX "Pool Blocking" bug class: unrestricted pool creation price + no minimum/maximum trade size to prevent price-pinning micro-trades.

### Finding Description
`ExchangeCreateActuator.doValidate()` validates only:
- token IDs differ,
- both balances `> 0`,
- both balances `<= dynamicStore.getExchangeBalanceLimit()`,
- the creator actually owns the funds being deposited. [1](#0-0) 

There is no check that `firstTokenBalance / secondTokenBalance` reflects any external market price — this ratio *is* the pool's initial exchange rate, analogous to Monoswap's `_price` argument in `listNewToken`/`_createPool`, which the MonoX report calls out as unvalidated against third-party data.

Because any account can issue a new TRC10 token and immediately create an `Exchange` pairing it with TRX or another established token, the attacker fully controls both the token's total supply and the pool's seed ratio, letting them fix the price of their own token in TRX terms to any value they like.

Once created, the price evolves per-trade using the bancor invariant in `ExchangeCapsule.transaction()`: [2](#0-1) 

`ExchangeTransactionActuator` enforces only that the sell quantity is `> 0`, `tokenExpected > 0`, and the post-trade balance stays under the global `balanceLimit` — there is no minimum trade size and no lock period on price changes: [3](#0-2) 

Because the bancor formula's price impact for a trade scales with `sellQuant / reserveBalance`, an attacker who seeds one side of the pool with a very large reserve (up to `getExchangeBalanceLimit()`, i.e. `1_000_000_000_000_000`) can execute negligible-size trades (`ExchangeTransactionContract.quant` as low as 1) periodically to keep the manipulated price effectively frozen — the same "micro-exchange to hold the price" pattern described in the MonoX report, just without needing a block-count lock since there is none here to bypass. Any unsuspecting third party who swaps against this pool via `ExchangeTransactionActuator`/`swapExactTokenForToken`-equivalent gets executed at the attacker's fabricated rate and permanently loses value (their TRX or legitimate TRC10 tokens are exchanged for a token the attacker controls at an inflated rate).

### Impact Explanation
Victims trading against the manipulated pool receive tokens (often freshly minted, worthless TRC10 assets) far below fair value, i.e. concrete unauthorized value transfer/theft of funds from any account that swaps into the poisoned pool, reachable purely by unprivileged asset-issuer + order-placer actions (`ExchangeCreateContract` + `ExchangeTransactionContract`), matching the required "concrete... theft... of funds" impact bar.

### Likelihood Explanation
No privileged role is required: TRC10 asset issuance and `Exchange` pool creation are both open to any funded account, and sustaining the manipulated price only costs negligible per-trade fees/quantities. This is straightforward to execute repeatedly and cheaply.

### Recommendation
Introduce pool-creation and trade-size safeguards analogous to the MonoX fix: require a minimum initial liquidity/ratio sanity check (e.g., relative to any comparable existing pool for the same token, or a minimum absolute reserve size) in `ExchangeCreateActuator.doValidate()`, and add a minimum trade quantity (relative to pool reserves) enforcement in `ExchangeTransactionActuator`/`ExchangeCapsule.transaction` to prevent negligible trades from being used to pin a manipulated price indefinitely.

### Proof of Concept
1. Attacker issues a new TRC10 token `X` with a large total supply via the asset-issue contract.
2. Attacker submits `ExchangeCreateContract` pairing `X` and TRX with `firstTokenBalance` (TRX) set very low and `secondTokenBalance` (X) set very high (within `getExchangeBalanceLimit()`), producing an inflated TRX price for `X`. `ExchangeCreateActuator.doValidate()` accepts this since it only checks `>0` and `<= balanceLimit`.
3. A victim, seeing pool `X/TRX`, submits `ExchangeTransactionContract` to swap TRX for `X`, receiving far fewer `X` tokens than fair value dictates (or vice versa if attacker inverts the pair), realizing a loss.
4. Attacker periodically submits `ExchangeTransactionContract` with `quant=1` (minimal size) to keep the bancor-formula price effectively pinned near its manipulated starting point, since `doValidate()` in `ExchangeTransactionActuator` (lines 182-205) imposes no minimum trade size or price-staleness lock.
