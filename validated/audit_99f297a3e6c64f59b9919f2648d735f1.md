This confirms the priority-floor mechanism is a saturation-triggered optimization layered on top of pre-existing, independent rate limiting at ingress. Unstaked/zero-fee traffic is already bounded before it ever reaches sigverify.

### Analysis

The scenario described is not a new vulnerability — sigverify with `floor==0` behaves exactly as `ed25519_verify_serial`/dedup always have, prior to the priority-floor feature existing at all. The priority floor (`SchedulerPriorityFloor`, `apply_priority_floor_to_batch`) is explicitly documented as a saturation-only backpressure optimization: "when saturated, the scheduler publishes the queue-min transaction's priority" [1](#0-0) . It is not, and was never claimed to be, the primary bound on sigverify CPU work; that bound is enforced upstream at the QUIC/streamer ingress layer via stake-weighted QoS.

Specifically, unstaked connections are capped to `MAX_UNSTAKED_TPS = 200` and additionally rate-limited per-interval by `StakedStreamLoadEMA::available_load_capacity_in_throttling_duration` [2](#0-1) [3](#0-2) , concurrent stream counts are capped via `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS` [4](#0-3) , and connection counts/tables are pruned via `SwQos::prune_unstaked_connection_table` and `max_unstaked_connections` [5](#0-4) . This is validated directly by `test_throttling_check_no_packet_drop`, which shows unstaked traffic capped to ~100 TPS regardless of how fast the client tries to send [6](#0-5) . An unprivileged attacker sending "N max-size zero-fee packets" cannot bypass these caps by connecting once; the packet arrival rate into sigverify is already bounded by this pre-existing, independent QoS layer, regardless of the priority floor's state.

Additionally, dedup (`dedup_packets_and_count_discards`) runs before the floor check and drops exact-duplicate packets cheaply [7](#0-6) , so naive duplicate-packet flooding is already discounted; and `ed25519_verify_serial` itself is O(1) signature-verify cost per packet bounded by `VERIFY_PACKET_CHUNK_SIZE`-scale batches [8](#0-7) , not unbounded per packet. The "floor stays 0 → full sigverify cost" behavior described is simply baseline system behavior under light/idle load — the same cost every unstaked packet has always incurred since sigverify's inception, gated by the ingress-level QUIC/QoS rate limits, not by the newer priority-floor mechanism. There is no code path where an attacker forces more sigverify throughput than the QUIC ingress admits.
