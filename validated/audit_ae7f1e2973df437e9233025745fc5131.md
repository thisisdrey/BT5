### Title
Unbounded per-address bad-remote list forces linear scan on every RemoteList rebuild, enabling remote-triggered CPU exhaustion - (File: `remote_list.go`)

### Summary
`RemoteList.badRemotes` is an unbounded `[]netip.AddrPort` slice that is linearly scanned via `unlockedIsBad` for every address candidate during `unlockedCollect`, which runs on every `Rebuild` call. `Rebuild` is invoked from hot, remote-triggerable paths (`ForEach`, `CopyAddrs`, `Len`), including holepunching and promotion logic driven by handshake/lighthouse traffic. Because nothing bounds the size of `badRemotes` and it accumulates over the life of a `RemoteList`, an attacker who can repeatedly cause "wrong host responded" events can grow this list unboundedly, making every subsequent address rebuild/dedup operation linear in the number of bad remotes recorded, mirroring the Swafe `assoc` vector scan pattern (unbounded structure + mandatory full scan on a frequently-triggered operation).

### Finding Description
`RemoteList` keeps a dedicated bad-address blocklist: [1](#0-0) 

`unlockedIsBad` performs an O(n) `slices.Contains` scan against this slice: [2](#0-1) 

This scan is invoked once per candidate address inside `unlockedCollect`, for every V4/V6 reported/learned entry and every DNS-resolved address, each time the dedup cache is rebuilt: [3](#0-2) 

`unlockedCollect` is only reached through `Rebuild`, which in turn backs the commonly-called, remote-influenced accessors `Len`, `ForEach`, and `CopyAddrs`: [4](#0-3) 

These accessors are used on hot paths tied to remote-driven activity, e.g. `TryPromoteBest`/hole-punch code that runs continuously per hostinfo: [5](#0-4) [6](#0-5) 

There is no cap, eviction, or deduplication policy on `badRemotes` visible in `remote_list.go`; each qualifying event simply appends. Unlike `RemoteList.addrs`/`.reported`, which are explicitly capped by `MaxRemotes` (`c.reported = c.reported[:0]; ... to[:minInt(len(to), MaxRemotes)]` in `unlockedSetV4`), `badRemotes` has no analogous bound: [7](#0-6) 

This is structurally identical to the Swafe finding: an unbounded per-entity vector (`assoc` there, `badRemotes` here) that must be linearly scanned on every invocation of a frequently-triggered operation (`initiate_recovery`/`verify_update` there, `Rebuild`/`unlockedCollect` here), with attacker control over the growth of that vector.

### Impact Explanation
An unauthenticated or semi-trusted remote peer that can trigger repeated "wrong responder" / address-block events against a victim's hostinfo can grow `badRemotes` without bound. Because every `Rebuild` call re-scans the full deduplicated address set against the full `badRemotes` list (multiplicatively, since the scan happens per candidate address per rebuild), CPU cost for routine operations like hole-punch scheduling and remote promotion grows unbounded over the tunnel's lifetime, leading to increased latency and potential CPU exhaustion / degraded packet processing for that hostinfo (and, if triggered broadly, for the process as a whole given `Rebuild` runs under a lock held on the shared `RemoteList`).

### Likelihood Explanation
Likelihood depends on how easily a remote party can cause repeated "bad remote" markings without a CA-signed relationship being fully established (e.g., during handshake wrong-responder scenarios, as exercised in `TestHandshakeWrongResponderPacketStore`). Because this path is exercised during handshake completion/roaming logic rather than requiring a fully authenticated tunnel, it is plausibly reachable by a network-adjacent attacker able to spoof source addresses or race handshake responses, similar in spirit to the reachable-without-cert categories called out in scope. Confidence is moderate: I was not able to fully trace every call site that appends to `badRemotes` within the given tool budget, so the exact attacker trigger frequency/rate-limiting (if any) is unverified.

### Recommendation
- Bound `badRemotes` with a fixed capacity (analogous to `MaxRemotes`) and evict oldest/least-relevant entries when the cap is reached.
- Replace the linear `slices.Contains` scan with a `map[netip.AddrPort]struct{}` for O(1) membership checks.
- Add expiry/TTL to bad-remote entries so stale blocks don't accumulate indefinitely.
- Rate-limit or dedupe the events that cause an address to be marked bad.

### Proof of Concept
Conceptual reproduction (not independently executed against a live build, given tool limitations):
1. Establish a tunnel context where `RemoteList` is populated for a victim host.
2. Repeatedly induce "wrong host responded" conditions (e.g., via spoofed/racing handshake responses as in `TestHandshakeWrongResponderPacketStore`) so that many distinct `netip.AddrPort` values are appended to `badRemotes` over time.
3. Observe that each subsequent `Rebuild`/`ForEach`/`CopyAddrs` call (invoked continuously by `TryPromoteBest` and hole-punch scheduling) takes increasingly longer as `badRemotes` grows, since `unlockedCollect` performs an `unlockedIsBad` scan per candidate address per rebuild.

**Caveat:** I could not, within the available tool budget, fully enumerate every call site that appends to `badRemotes` (17 matches were found in `remote_list.go` but not individually inspected), so the precise attacker-reachable trigger rate is unverified and should be confirmed before treating this as confirmed-exploitable rather than a plausible analog.

func (r *RemoteList) Len(preferredRanges []netip.Prefix) int {
	r.Rebuild(preferredRanges)
	r.RLock()
	defer r.RUnlock()
	return len(r.addrs)
}

		return nil
	}

	r.RLock()
	defer r.RUnlock()
	c := make([]netip.AddrPort, len(r.addrs))
	for i, v := range r.addrs {
		c[i] = v
	}
	return c
