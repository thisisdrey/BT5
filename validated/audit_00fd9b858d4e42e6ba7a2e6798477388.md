### Title
Remote peer can crash the signer's `/metrics` thread via `.expect()` panic on early connection close - (File: stacks-signer/src/monitoring/server.rs)

### Summary
`MonitoringServer::main_loop` calls `request.respond(response).expect("Failed to send response")` for `/metrics` (and the same pattern for `/info`, `/`, `/heartbeat`, and 404 responses). `tiny_http`'s `respond` performs the actual socket write and returns `Err` if the underlying TCP write fails (e.g., `EPIPE`/`ECONNRESET` because the client already closed/reset the connection). Any unauthenticated remote client that opens a TCP connection to the signer's metrics port, sends a valid HTTP GET, and then aborts the connection (RST) before the response is fully written can force `respond()` to return `Err`, causing the `.expect()` to panic and permanently terminate the `signer_metrics` thread.

### Finding Description
The equality being broken is: "a remote peer closing its socket == the server thread survives to serve the next request." In `main_loop`, every response path uses `.expect()` on the `Result` returned by `request.respond(...)`: [2](#0-1)  for `/metrics`, and similarly for `/info`, `/`, `/heartbeat`, and the 404 fallback at lines 138-169. `tiny_http::Request::respond` writes the HTTP response body to the TCP stream; if the peer already closed or reset the connection, the write returns an I/O error (broken pipe/connection reset), which `respond()` propagates as `Err`. There is no `match`/`if let Err(...)` handling around any of these calls—only `.expect()`, so any write failure immediately panics the thread executing `main_loop`.

The attacker's exact message is a syntactically valid `GET /metrics HTTP/1.1\r\nHost: x\r\n\r\n` (or any of the other routed paths), sent over a raw TCP connection to the configured `metrics_endpoint`, followed by closing/resetting the socket (e.g., `shutdown(Both)` or a TCP RST) before the server finishes writing the response. No authentication or secret is required to reach this endpoint—`metrics_endpoint` is a plain `tiny_http` HTTP server with no auth gate. The `signer_metrics` thread is spawned via `std::thread::Builder::new().name("signer_metrics".to_string()).spawn(...)` in `start_serving_monitoring_metrics`, and the returned `JoinHandle` is discarded (`let _ = ...spawn(...)`), so no supervisor observes or restarts the thread once it panics. [3](#0-2) 

Existing guards do not prevent this: there is no message-length cap, signature check, or auth gate applicable here because `/metrics` is intentionally unauthenticated by design, and the failure mode is not a malformed-request check but an I/O write failure after the request was already validly parsed and routed.

### Impact Explanation
Once the panic occurs, `main_loop` never returns to `self.http_server.recv()` again, so the metrics HTTP listener silently stops accepting/serving any further requests (`/metrics`, `/info`, `/heartbeat`, `/`) for the remaining lifetime of the signer process. This is a single-message, unauthenticated, remotely triggerable permanent denial of service against the signer's monitoring subsystem, matching the "Critical - remote crash/unauthenticated DoS from few messages" category. Any external monitoring/alerting or liveness-probing infrastructure relying on `/metrics` or `/heartbeat` will silently go dark, and the attack is trivially repeatable against a fresh instance if the process is otherwise still running (the signer's core consensus logic is unaffected, only the monitoring thread dies, since the panic is thread-local in Rust and does not abort the process).

### Likelihood Explanation
Preconditions are minimal: `metrics_endpoint` must be configured, which is a common/typical deployment aid for operators. No peer identity, StackerDB slot, secret, or privileged role is needed—only network reachability to the metrics port. The attack cost is a single TCP connection and an immediate disconnect, and it is deterministically repeatable.

### Recommendation
Replace all `.expect(...)` calls on `request.respond(...)` in `main_loop` (server.rs lines 134, 141, 149, 162, 169) with error logging (`if let Err(e) = ... { warn!(...); }`) so that a failed write due to a disconnected peer does not panic the thread, allowing the loop to `continue` to the next `recv()`.

### Proof of Concept
1. Build a `MonitoringServer` bound to a `127.0.0.1:0`-style ephemeral port (or the configured `metrics_endpoint`) and spawn `main_loop` in a `std::thread`.
2. From the test, open a raw `TcpStream` to that address, write a minimal valid request line `GET /metrics HTTP/1.1\r\nHost: localhost\r\n\r\n`, then immediately call `stream.shutdown(std::net::Shutdown::Both)` (or set `SO_LINGER` to 0 and drop the stream to force an RST) before reading any response bytes.
3. Join the spawned thread and assert it panicked (`JoinHandle::join()` returns `Err`), confirming the crash site is `request.respond(response).expect("Failed to send response")` at `stacks-signer/src/monitoring/server.rs:134`.
4. Optionally, open a second, well-behaved connection afterward and show `recv()`/`respond()` never happens again, proving the thread is dead and the endpoint is permanently unresponsive.
