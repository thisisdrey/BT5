### Title
Unbounded array allocation from unchecked length field in TVM precompiled-contract ABI decoding leads to node DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` helper methods in `PrecompiledContracts.java` decode a length field directly from attacker-supplied call data and use it, unvalidated, to allocate a Java array before any bound check against the actual size of the remaining data. This mirrors the GraphicsMagick CVE-2017-18229 bug class: a size/length value taken from untrusted input is used to drive a memory allocation without first checking that it is consistent with the amount of data actually available, allowing a crafted input to trigger an oversized allocation attempt.

### Finding Description
`extractBytesArray` and `extractSigArray` read `len` from `words[offset].intValueSafe()` and immediately allocate `new byte[len][]`: [1](#0-0) [2](#0-1) 
`extractBytes32Array` does the same pattern without even the `offset > words.length - 1` guard: [3](#0-2) 

The `len` value comes from `DataWord.intValueSafe()`, which is documented to clamp to `Integer.MAX_VALUE` on overflow rather than reject the input: [4](#0-3) 

Because `words` is derived from raw precompiled-contract call `data` (fully controlled by whoever invokes the precompile via a `CALL`/`STATICCALL` opcode in a smart contract), an attacker can craft a 32-byte ABI "length" word close to `0x7fffffff` at the expected offset. This causes `new byte[len][]` (an array of up to ~2^31 object references, ~8-16GB) to be attempted before any check that `len` corresponds to actual remaining bytes in `data` — exactly the class of bug described in the CVE: file/blob size fields used to size allocations without being bounded by the real amount of available data.

### Impact Explanation
A single crafted transaction that calls a TVM contract which in turn invokes the affected precompiled contract with malicious ABI-encoded call data can force the executing full node to attempt a massive heap allocation. This can throw `OutOfMemoryError`, potentially destabilizing or crashing the JVM process for the node executing/validating the block, which is a node-crash / halt condition reachable by any unprivileged contract caller.

### Likelihood Explanation
Likelihood is limited by which precompiled contract(s) actually invoke these three helper methods with attacker-controlled offsets/lengths at the time of the call — this could not be fully confirmed within the available search results (no direct call sites for `extractBytesArray`/`extractSigArray`/`extractBytes32Array` were found in the same file during this investigation, which is unusual since they are declared there). This is a noted limitation: further confirmation of the exact call sites and whether energy/gas metering effectively bounds `len` before reaching the allocation is required to determine real-world exploitability.

### Recommendation
Add an explicit upper bound check on `len` (e.g., against `(words.length - offset - 1)` or a small sane constant) in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` before allocating the array, rejecting the precompiled call (returning `false`/empty) instead of allocating unconditionally. Apply the same defensive bound to any other precompile helper that derives an allocation size from `DataWord.intValueSafe()`/`longValueSafe()` off call data.

### Proof of Concept
Not fully verified — the exact caller of `extractBytesArray`/`extractSigArray`/`extractBytes32Array` that is reachable from an unprivileged TVM `CALL` could not be located within the indexed portion of `PrecompiledContracts.java` during this session. A confirmed PoC would require identifying the specific precompiled contract address/dispatch that uses these helpers and constructing ABI-encoded call data with a large length word at the expected offset, then invoking it via a deployed contract's `CALL` opcode.
