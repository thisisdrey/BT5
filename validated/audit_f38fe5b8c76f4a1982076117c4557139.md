This is the Go standard library itself (`net/http`), not an application. The CVE describes a Java app (ujcms) that trusts a spoofable `X-Forwarded-For` header for security decisions. In this repo, the only place X-Forwarded-For is handled is in `httputil.ReverseProxy`, which sets/forwards the header for the proxy's *outbound* request — it never uses XFF for authentication, access control, or template rendering, so there's no analogous "trust decision" to exploit.

The `Director` field's documentation explicitly warns that a malicious client can retain a spoofed `X-Forwarded-For` header if the deprecated `Director` doesn't strip it, and recommends `Rewrite`/`SetXForwarded` instead, which always deletes client-supplied `Forwarded`/`X-Forwarded-*` headers before calling the user function. [1](#0-0) [2](#0-1) 

This is documented, known, and intentional behavior (the caller is responsible for deciding whether to trust upstream proxies), not a bug in the Go standard library — it doesn't match the CVE's root cause (an application blindly trusting/executing content from the header). No production Go stdlib code path parses X-Forwarded-For for spoofing-sensitive logic (auth, template execution, code execution), so there is no reachable analog vulnerability here.
