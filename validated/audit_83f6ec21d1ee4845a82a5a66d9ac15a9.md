### Title
`DeleteAccount` action can permanently burn an account's balance when `beneficiary_id` is a non-existent account - (File: `runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` unconditionally issues a `Transfer` to `delete_account.beneficiary_id` via `Receipt::new_balance_refund`, without verifying that the beneficiary account exists. Action validation (`validate_delete_action` in `runtime/runtime/src/action_validation.rs:399-403`) only checks that `beneficiary_id` is a syntactically valid `AccountId` — analogous to how the CollateralToken bug never checked that `releaseTo` was a valid/non-zero address before transferring the NFT.

### Finding Description
When a `DeleteAccountAction` executes, `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) takes the account's remaining balance and creates a refund receipt to `beneficiary_id`: [1](#0-0) 

This refund receipt has `predecessor_id == "system"` (`Receipt::new_balance_refund`, [2](#0-1) ). When this refund receipt is later processed by `apply_action` and `beneficiary_id` does not correspond to an existing account, `check_account_existence` is invoked with `is_refund = true` for a `Transfer` action ( [3](#0-2) ). Because `implicit_account_creation_eligible` is `false` for refunds ( [4](#0-3) ), `check_transfer_to_nonexisting_account` unconditionally returns `AccountDoesNotExist` ( [5](#0-4) ).

Per the documented refund semantics: "If the execution of a refund fails, the refund amount is burnt" ( [6](#0-5) ). The only validation performed on `beneficiary_id` at action-creation time is a syntactic `AccountId::validate` check with no existence check: [7](#0-6) [8](#0-7) 

Any syntactically-valid `AccountId` that simply doesn't happen to be registered on-chain (e.g. a typo'd account name, or an account that was itself deleted between transaction submission and receipt execution) passes validation, but the deposit refund to it will fail and be permanently burned.

### Impact Explanation
This causes permanent, unrecoverable loss of the deleted account's entire remaining NEAR balance whenever `beneficiary_id` is a syntactically valid but non-existent account. This can happen from an ordinary user's own transaction (e.g. `DeleteAccount` submitted via `promise_batch_action_delete_account`, or a plain `SignedTransaction` with a `DeleteAccountAction`) — no privileged role is required. It qualifies as concrete permanent freezing/loss of funds, as required by the validation criteria.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires the caller (user or a contract building a batch promise) to specify a `beneficiary_id` that is syntactically valid but does not exist — e.g. a typo, a not-yet-created implicit account (implicit accounts cannot be created via refunds, per the comment at [9](#0-8) ), or a race where the beneficiary account is deleted between when the `DeleteAccount` action is issued and when it executes. This is plausible in practice, especially for contracts programmatically constructing beneficiaries, or races involving concurrently-deleted accounts.

### Recommendation
Either (a) reject `DeleteAccountAction` at action-validation or execution time if `beneficiary_id` does not correspond to an existing account, returning a clear `ActionError`, or (b) make failed deposit refunds from `DeleteAccount` fall back to some safe default (e.g. returning to `predecessor_id`) rather than silently burning them, consistent with how other value-transferring actions guard against non-existent recipients.

### Proof of Concept
1. Create account `alice.near` with a non-zero balance.
2. Submit `SignedTransaction::delete_account(nonce, "alice.near", "alice.near", "nonexistent123.near", signer, block_hash)` where `nonexistent123.near` is a syntactically valid `AccountId` that was never created (see `SignedTransaction::delete_account` helper at [10](#0-9) ).
3. `validate_delete_action` accepts the action since `nonexistent123.near` parses as a valid `AccountId`.
4. `action_delete_account` deletes `alice.near` and emits a `Receipt::new_balance_refund(&"nonexistent123.near", account_balance)`.
5. When that refund receipt is processed, `check_account_existence` returns `AccountDoesNotExist` because the receipt is a refund (`is_refund == true`), so `implicit_account_creation_eligible` is `false`.
6. Per `runtime/runtime/src/lib.rs` refund-failure handling (`stats.balance.other_burnt_amount`), `alice.near`'s entire remaining balance is burned rather than delivered anywhere — permanent loss of funds.
