Audit Report

## Title
Collection Admin/Issuer/Freezer roles are not reset on `transfer_ownership`, letting a former owner retain control of an NFT collection - (File: substrate/frame/nfts/src/features/transfer.rs)

## Summary
`do_transfer_ownership` in `pallet-nfts` updates only the `owner` field of `CollectionDetails` and never clears `CollectionRoleOf` entries for the collection, unlike `do_set_team` which explicitly calls `clear_roles` before installing new roles. As a result, any account previously granted Issuer, Admin, or Freezer by the outgoing owner retains those privileges after the collection is transferred to a new owner, since role-gated extrinsics check `has_role` independently of `details.owner`.

## Finding Description
`do_transfer_ownership` at `substrate/frame/nfts/src/features/transfer.rs` lines 124-162 mutates `details.owner`, moves the deposit, and updates `CollectionAccount`, but at no point touches `CollectionRoleOf` for the collection. [1](#0-0) 

The only function that clears roles is `do_set_team`, via `Self::clear_roles(&collection)?` prior to reinserting new role assignments. [2](#0-1) 

`CollectionRoleOf` is queried by `has_role`, which is keyed independently by `(collection, account)` and has no reference to the current `owner` field: [3](#0-2) 

Downstream extrinsics gate purely on role, not on ownership. `do_lock_item_transfer`/`do_unlock_item_transfer` check `has_role(&collection, &origin, CollectionRole::Freezer)`, and `do_lock_item_properties` checks `has_role(&collection, &check_origin, CollectionRole::Admin)`. [4](#0-3) [5](#0-4) 

Because ownership transfer never invalidates these roles, a former owner who had appointed themselves (or a confederate) as Freezer/Admin/Issuer before the transfer retains full ability to lock item transfers, lock item metadata/attributes, or (via Issuer) mint new items into the collection now nominally owned by someone else. The existing checks (`ensure!(origin == details.owner, ...)` in `do_transfer_ownership`) only validate that the *caller of transfer_ownership* is the current owner — they do nothing to invalidate pre-existing role grants, so they are insufficient to prevent this persistence of privilege.

## Impact Explanation
This is a runtime bug that compromises intended behavior and results in unauthorized execution/origin escalation: a new owner reasonably expects that acquiring collection ownership grants full administrative control, but a prior owner's Admin/Freezer/Issuer appointees (which could be the prior owner themself) retain the ability to freeze item transfers, lock item metadata/attributes, or mint items without the new owner's consent. This matches the "runtime bugs that compromise intended behavior" and "unauthorized execution or origin escalation" categories in the impact gate, since privileged operations execute under a role binding that should have been invalidated by the ownership change but was not — the corrupted/stale value is the `CollectionRoleOf` entry for the collection, which is never cleared even though the collection's `owner` field has changed.

## Likelihood Explanation
The exploit path requires only unprivileged, public extrinsics: `create`, `set_team`, `set_accept_ownership`, and `transfer_ownership`, all callable by any account that owns or is offered a collection. No malicious peer, validator, leaked key, or privileged governance action is required — the vulnerable state (self-appointed roles persisting across a self-initiated ownership transfer) is entirely under the control of the attacker (the outgoing owner) and is a natural, ordinary usage pattern (`set_team` is a standard, documented way to delegate collection administration).

## Recommendation
In `do_transfer_ownership` (`substrate/frame/nfts/src/features/transfer.rs`), call `Self::clear_roles(&collection)?` as part of the ownership-transfer mutation, mirroring the reset performed in `do_set_team`, unless the new owner explicitly opts to preserve the existing team. Apply the analogous fix to `pallet-uniques::transfer_ownership`, resetting `issuer`/`admin`/`freezer` fields on `CollectionDetails`. Alternatively, require new owners to affirmatively confirm or re-establish team roles as part of accepting ownership.

## Proof of Concept
1. Account A calls `Nfts::create(A, A, config)` to create a collection.
2. A calls `Nfts::set_team(A, collection, Some(A), Some(A), Some(A))`, so `CollectionRoleOf(collection, A) = Issuer|Admin|Freezer` per `do_set_team`. [6](#0-5) 
3. Account B calls `Nfts::set_accept_ownership(B, Some(collection))`; A then calls `Nfts::transfer_ownership(A, collection, B)`. `do_transfer_ownership` sets `details.owner = B` but leaves `CollectionRoleOf(collection, A)` untouched. [7](#0-6) 
4. A (no longer owner) calls `Nfts::lock_item_transfer(A, collection, item)` or `Nfts::lock_item_properties(A, collection, item, true, true)`; both succeed because `has_role(&collection, &A, CollectionRole::Freezer/Admin)` still returns `true`, despite B now being the sole intended controller of the collection.

	pub(crate) fn do_transfer_ownership(
		origin: T::AccountId,
		collection: T::CollectionId,
		new_owner: T::AccountId,
	) -> DispatchResult {
		// Check if the new owner is acceptable based on the collection's acceptance settings.
		let acceptable_collection = OwnershipAcceptance::<T, I>::get(&new_owner);
		ensure!(acceptable_collection.as_ref() == Some(&collection), Error::<T, I>::Unaccepted);

		// Try to retrieve and mutate the collection details.
		Collection::<T, I>::try_mutate(collection, |maybe_details| {
			let details = maybe_details.as_mut().ok_or(Error::<T, I>::UnknownCollection)?;
			// Check if the `origin` is the current owner of the collection.
			ensure!(origin == details.owner, Error::<T, I>::NoPermission);
			if details.owner == new_owner {
				return Ok(());
			}

			// Move the deposit to the new owner.
			T::Currency::repatriate_reserved(
				&details.owner,
				&new_owner,
				details.owner_deposit,
				Reserved,
			)?;

			// Update account ownership information.
			CollectionAccount::<T, I>::remove(&details.owner, &collection);
			CollectionAccount::<T, I>::insert(&new_owner, &collection, ());

			details.owner = new_owner.clone();
			OwnershipAcceptance::<T, I>::remove(&new_owner);
			frame_system::Pallet::<T>::dec_consumers(&new_owner);

			// Emit `OwnerChanged` event.
			Self::deposit_event(Event::OwnerChanged { collection, new_owner });
			Ok(())
		})
	}

	pub(crate) fn do_set_team(
		maybe_check_owner: Option<T::AccountId>,
		collection: T::CollectionId,
		issuer: Option<T::AccountId>,
		admin: Option<T::AccountId>,
		freezer: Option<T::AccountId>,
	) -> DispatchResult {
		Collection::<T, I>::try_mutate(collection, |maybe_details| {
			let details = maybe_details.as_mut().ok_or(Error::<T, I>::UnknownCollection)?;
			let is_root = maybe_check_owner.is_none();
			if let Some(check_origin) = maybe_check_owner {
				ensure!(check_origin == details.owner, Error::<T, I>::NoPermission);
			}

			let roles_map = [
				(issuer.clone(), CollectionRole::Issuer),
				(admin.clone(), CollectionRole::Admin),
				(freezer.clone(), CollectionRole::Freezer),
			];

			// only root can change the role from `None` to `Some(account)`
			if !is_root {
				for (account, role) in roles_map.iter() {
					if account.is_some() {
						ensure!(
							Self::find_account_by_role(&collection, *role).is_some(),
							Error::<T, I>::NoPermission
						);
					}
				}
			}

			let roles = roles_map
				.into_iter()
				.filter_map(|(account, role)| account.map(|account| (account, role)))
				.collect();

			let account_to_role = Self::group_roles_by_account(roles);

			// Delete the previous records.
			Self::clear_roles(&collection)?;

			// Insert new records.
			for (account, roles) in account_to_role {
				CollectionRoleOf::<T, I>::insert(&collection, &account, roles);
			}

			Self::deposit_event(Event::TeamChanged { collection, issuer, admin, freezer });
			Ok(())
		})
	}
