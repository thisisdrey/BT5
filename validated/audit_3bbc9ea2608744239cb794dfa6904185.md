## Title
Missing length validation on ZIP central-directory field lengths causes out-of-bounds read/crash when Bazel's ijar parses untrusted `.jar`/`.zip` dependency archives - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar's zip reader parses the `file_name_length`, `extra_field_length`, and `file_comment_length` fields of each ZIP central-directory record and unconditionally advances the cursor `p` by those attacker-controlled values with **no bounds check against the mapped file's length**, unlike its sibling `ProcessLocalFileEntry`, which validates every field via `EnsureRemaining()` before reading. This is the same bug class as CVE‑2017‑12183 (X.Org XFIXES): a length field taken from untrusted input is trusted without validating it against the actual buffer size before being used to advance a read cursor / compute offsets.

### Finding Description
`ProcessCentralDirEntry` reads 16 bytes of fixed fields, then: [1](#0-0) 

It reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from the record and does `p += file_name_length; ... p += extra_field_length; ... p += file_comment_length;` with **no `EnsureRemaining()` call anywhere in this function**. Compare this to `ProcessLocalFileEntry`, which validates every variable-length field before reading it: [2](#0-1) 

The file is opened via `mmap` (`InputZipFile::Open()`/`zipdata_in_`), and the only overall sanity check performed before per-entry parsing begins is that `central_dir_offset + central_dir_size <= in_length` in `FindZipCentralDirectory`: [3](#0-2) 

This check bounds the *total* central directory region but never validates that a *single* entry's `file_name_length + extra_field_length + file_comment_length` stays inside that region, nor that the resulting pointer stays inside the mmap'd buffer `zipdata_in_ .. zipdata_in_ + in_length`. A malicious archive can declare a large `extra_field_length` or `file_comment_length` on the last (or an early) central-directory entry, which pushes `p` past the end of the mapped region. The very next `get_u4le(p)` read in `ProcessCentralDirEntry` (called again from `ProcessNext`/`CalculateOutputLength` loops) or in `InputZipFile::ProcessNext` dereferences memory outside the mapping.

This is reached from real build workflows: ijar is Bazel's built-in tool for producing interface jars from `.jar` inputs (any `java_library`/`java_import` whose jar comes from an `http_archive`, `http_jar`, `http_file`, or third-party Maven/registry dependency). An attacker who controls the origin server or a compromised mirror can supply a `.jar` file whose declared `sha256`/`integrity` matches (i.e., the attacker crafts the malicious ZIP *and* publishes its correct hash, or the victim omits the hash as the docs explicitly warn is common) — the checksum only guarantees byte-for-byte reproducibility of the attacker's chosen bytes, not that those bytes form a well-formed ZIP central directory. Once fetched, ijar (or any other consumer of `third_party/ijar/zip.cc`, e.g. `zip_main.cc`'s `extract`/`build_zip`, or `src/main/cpp/archive_utils.cc`'s `PartialZipExtractor`) parses the file and hits the unchecked pointer arithmetic.

### Impact Explanation
An out-of-bounds read past an `mmap`'d region typically causes SIGSEGV (crash) for a page-unmapped read, but because the corrupted `file_name_length`/`extra_field_length` values feed further offset computations (`filename` buffer fill, subsequent local-file-header offset lookups via `ProcessNext`'s `p = zipdata_in_ + in_offset_ + offset`), it can also read adjacent heap/mapped memory into buffers whose contents are later written into a derived interface jar or extracted files, allowing memory-content disclosure, in addition to build-process crashes (denial of service against the build). This directly matches the reported CVE class: "missing length validation … allowing malicious client to cause crash or possibly execute arbitrary code."

### Likelihood Explanation
Any build target that consumes a third-party `.jar`/`.zip` (via `http_archive`, `http_jar`, `maven_install`, or a vendored dependency URL) invokes ijar's ZIP parser on attacker-influenceable bytes. No Starlark trust boundary or credential access is required by the attacker — only the ability to serve/publish the archive content that the victim's build later downloads and processes. This makes the likelihood high wherever ijar is used against externally-sourced jars, which is the default in every Bazel Java build.

### Recommendation
Add `EnsureRemaining()`-style bounds checks (bounding the read against `zipdata_in_ + input_file_->Length()`) before consuming `file_name_length`, `extra_field_length`, and `file_comment_length` inside `InputZipFile::ProcessCentralDirEntry`, mirroring what `ProcessLocalFileEntry` already does, and reject/abort parsing with an error rather than silently overrunning the buffer. Additionally, validate that each central-directory entry (header + variable fields) stays within `[central_dir_, central_dir_ + central_dir_size]` before the outer loop advances `p`/`current`.

### Proof of Concept
Extend the existing ijar shell test harness (`third_party/ijar/test/zip_test.sh`, which already has a `test_no_path_traversal` pattern) with a new fixture ZIP whose central directory contains a single entry with a valid signature and header fields but with `extra_field_length` (or `file_comment_length`) set to a value larger than the remaining bytes in the mapped file (e.g., `0xFFFF` while only a few bytes remain). Running `$ZIPPER x crafted.jar` (or `ijar crafted.jar`) over this file should be shown to crash (SIGSEGV) or read out-of-bounds under ASan, whereas a well-formed archive with the same total file size succeeds — demonstrating that `ProcessCentralDirEntry` lacks the same `EnsureRemaining` protection present in `ProcessLocalFileEntry`.
