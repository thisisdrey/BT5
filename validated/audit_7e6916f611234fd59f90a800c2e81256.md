### Title
`total_send_fees` uses the outer transaction's `sender_is_receiver` flag instead of the inner `DelegateAction`'s sender/receiver relationship, causing the burnt gas fee for delegated actions to be miscalculated - ([File: runtime/runtime/src/config.rs])

### Summary
In `total_send_fees` (config.rs:141-153, 154-167), the `Delegate`/`DelegateV2` arms recurse into the inner actions using the caller-supplied `sender_is_receiver` flag rather than recomputing it from `delegate_action.sender_id == delegate_action.receiver_id`. Since `calculate_tx_cost` derives this flag once from `signer_id == tx.receiver_id` (config.rs:442) and passes it straight through, a relayer who sets the outer transaction's `receiver_id` equal to its own `signer_id` (submitting the `Delegate` action "to itself") forces the inner action's send fee to be charged at the discounted `sir` (sender-is-receiver) rate even though the actual delegated sender and receiver differ.

### Finding Description
`total_send_fees` is called from `calculate_tx_cost` with `sender_is_receiver = (receiver_id == signer_id)` computed from the *outer* transaction fields [1](#0-0) . For a `Delegate` action, this same boolean is threaded straight into the recursive call over the delegate's inner actions instead of being recalculated for the delegate's own `sender_id`/`receiver_id`: [2](#0-1) 

Contrast this with `total_prepaid_send_fees`, which correctly recomputes `sender_is_receiver` from the inner delegate action before calling `total_send_fees`: [3](#0-2) 

Exploit flow: attacker controls account `A` (used both as the relayer/signer and as `delegate_action.sender_id`) and constructs `SignedDelegateAction{sender_id: A, receiver_id: C, actions: [Transfer]}`, wrapping it in `Transaction{signer_id: A, receiver_id: A, actions: [Delegate(...)]}`. Because the outer transaction's `receiver_id` (A) equals `signer_id` (A), `calculate_tx_cost` sets `sender_is_receiver = true`. This `true` value is passed down through the `Delegate` arm of `total_send_fees` to compute the send fee of the inner `Transfer` action, even though the true relationship for that inner action is `sender_id=A != receiver_id=C`. As a result, `burnt.gas` (which contributes to `gas_burnt` / `burnt_amount`, charged immediately at the current gas price) is computed using the cheaper `sir` transfer send fee, while `total_prepaid_send_fees` — used only for `gas_remaining`, the gas purchased for later execution — correctly uses the more expensive `not_sir` fee for the same inner action. No existing check (signature, nonce, access-key, action validation) inspects this fee-rate mismatch; the transaction is otherwise fully valid and processes normally, with only the fee accounting being wrong.

### Impact Explanation
This causes a real, quantifiable underpayment of burnt gas: `gas_burnt` in `TransactionCost` (and therefore `burnt_amount`, the tokens irreversibly burnt for converting the transaction into a receipt) is computed using the cheaper "sir" per-action send-fee multiplier instead of the correct "not-sir" multiplier for the inner delegated `Transfer` action. This matches NEAR's "token inflation / fee-bypass" bounty category to the extent that it lets an attacker systematically underpay burnt gas relative to what the protocol's fee schedule specifies for the true sender/receiver relationship, retaining the fee difference. It does not cause consensus divergence by itself since both validators computing `tx_cost` from the same transaction would derive the same (wrong) `gas_burnt` value deterministically — the impact is limited to a discount on the burn fee, not double-spend or state-root divergence.

### Likelihood Explanation
Preconditions are trivial and fully within an unprivileged attacker's control: own account `A`, and any distinct third-party receiver `C` (does not even need to be attacker-controlled). The attacker only needs to set the outer transaction's `receiver_id` field equal to its own `signer_id` when wrapping the `SignedDelegateAction` — this is a normal, permitted field combination with no special validation preventing it. The exploit is fully repeatable on every meta-transaction the attacker submits with this shape, at zero additional cost beyond crafting the transaction fields correctly.

### Recommendation
In `total_send_fees` (config.rs:141-167), recompute `sender_is_receiver` for the recursive call based on the delegate action's own `sender_id`/`receiver_id` (as `total_prepaid_send_fees` already does), i.e. `let inner_sender_is_receiver = delegate_action.sender_id == delegate_action.receiver_id;` and pass `inner_sender_is_receiver` instead of the outer `sender_is_receiver` into the recursive `total_send_fees` call for both `Delegate` and `DelegateV2` arms.

### Proof of Concept
Unit test in `runtime/runtime/src/config.rs` (or a test module using `calculate_tx_cost`):
1. Construct a `SignedDelegateAction` with `sender_id = A`, `receiver_id = C` (C != A), `actions = [Transfer(...)]`.
2. Construct `Transaction { signer_id: A, receiver_id: A, actions: [Delegate(signed_delegate_action)] }` (outer sender_is_receiver = true).
3. Call `calculate_tx_cost(...)` and capture `gas_burnt`.
4. Independently compute:
   - `buggy = total_send_fees(config, true, &delegate_action.get_actions(), &C)` (current/buggy behavior)
   - `correct = total_send_fees(config, false, &delegate_action.get_actions(), &C)` (expected behavior per `total_prepaid_send_fees`'s logic)
5. Assert that the `burnt.gas` component attributable to the inner Transfer action in `gas_burnt` equals `buggy.gas`, not `correct.gas`, and assert `correct.gas > buggy.gas`, quantifying the gas (and thus yoctoNEAR at `current_gas_price`) discount obtained by the attacker.
