### Title
Unbounded growth of the housekeeping middleware's `repoActivity`/`statsCache` maps via mutator RPCs on non-existent repository paths - ([File: internal/grpc/middleware/housekeeping/middleware.go])

### Summary
The gRPC housekeeping middleware maintains an in-memory `map[repoKey]*activity` (`m.repoActivity`) plus a `sync.Map` (`m.statsCache`) keyed by `{storage, relativePath}` values taken verbatim from the `Repository` field of incoming RPC requests. Neither structure has any size limit, TTL, or eviction routine, and entries for the mutator path are added even when the referenced repository does not exist. A client that is authenticated to the Gitaly node (any ordinary token holder, not a privileged actor) can call cheap mutator RPCs with a unique, non-existent `relative_path` on every call to make the server permanently retain a map entry, driving unbounded memory growth — the same bug class as the CL-2026-07 libp2p protocol-book issue (an attacker-controlled string is inserted into a never-gc'd map).

### Finding Description
`Middleware.getRepoKey` builds the map key directly from client-supplied fields: [1](#0-0) 

For `OpMutator` RPCs, the unary/stream interceptors run the handler and then unconditionally call `scheduleHousekeeping` unless the returned error code is one of `FailedPrecondition`, `ResourceExhausted`, or `PermissionDenied`: [2](#0-1) 

Notably, `codes.NotFound` (the error a repository-not-found failure normally returns) is **not** in the exclusion list, so any mutator call against a repository path that doesn't exist still reaches `scheduleHousekeeping`.

`scheduleHousekeeping` never checks whether the repository actually exists before mutating the map — it just looks up (or creates) an `activity` entry for the key and stores it forever: [3](#0-2) 

There is no eviction, TTL, or maximum-size mechanism for `m.repoActivity` anywhere in this file (unlike other caches in the codebase such as `internal/git/catfile/cache.go`'s `maxLen`-bounded LRU, `internal/unarycache/cache.go`'s `lru.New(maxEntries, ...)`, or `internal/praefect/datastore/storage_provider.go`'s `lru.NewWithEvict(2<<20, ...)`). Each distinct `(storage, relativePath)` pair the attacker supplies creates a permanent `*activity` object (containing a `writeCountAtLastRun` map) that is never released for the lifetime of the process.

### Impact Explanation
An authenticated Gitaly client can repeatedly invoke any `OpMutator` RPC (e.g., branch/tag mutation RPCs) with a `Repository{StorageName: "default", RelativePath: <random-unique-string>}` that does not correspond to a real repository. Each such call is rejected with `NotFound` by the underlying handler but still causes the middleware to insert a new, permanent entry into `m.repoActivity`. Because relative paths are arbitrary strings under client control and each RPC is cheap to issue, the attacker can grow this map without bound, exhausting node memory and causing a denial of service for all repositories served by that Gitaly node — directly analogous to the "RPC-handler resource limits" bug class in the report.

### Likelihood Explanation
Likelihood is high: exploitation requires only an ordinary, already-authenticated Gitaly client (the same trust level as any GitLab-side caller using the shared Gitaly auth token) issuing repeated RPCs with distinct relative paths — no privilege escalation, token theft, or peer/network position is required. This matches the "ordinary user's ... crafted RPC field" acceptance criterion.

### Recommendation
- Verify the target repository exists (or otherwise bound key admission) before creating an `activity`/`statsCache` entry in `scheduleHousekeeping` and `scheduleHousekeepingIfNeeded`.
- Replace the plain `map[repoKey]*activity` and unbounded `sync.Map` with a size-bounded, evicting cache (e.g., the LRU pattern already used in `internal/unarycache` or `internal/praefect/datastore/storage_provider.go`), or add a periodic sweep that drops idle/nonexistent-repo entries.
- Reconsider the mutator-path exclusion list so that `codes.NotFound` (and other errors indicating the repository was never valid) also skip `scheduleHousekeeping`.

### Proof of Concept
1. Obtain a valid Gitaly client auth token (the same one any ordinary internal caller uses).
2. In a loop, call any `OpMutator`-classified RPC (per `protoregistry`) with a `Repository` whose `relative_path` is a freshly generated random string each iteration, e.g. `repo-<uuid>.git`, causing each call to fail with `NotFound`.
3. Observe via process memory metrics (or a heap profile) that `housekeeping.Middleware.repoActivity` grows by one entry per unique iteration and is never reclaimed, with RSS climbing proportionally to the number of distinct fake paths sent — reproducible purely with client-side request volume, without ever needing a real repository to exist on disk.

func (m *Middleware) scheduleHousekeeping(ctx context.Context, repo *gitalypb.Repository, force bool) {
	m.mu.Lock()
	defer m.mu.Unlock()

	key := m.getRepoKey(repo)

	a, ok := m.repoActivity[key]
	if !ok {
		a = newActivity()
		m.repoActivity[key] = a
	}
	a.writeCount++
