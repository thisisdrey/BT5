### Title
Unprivileged dust-transfer fills victim's token list to `MAX_TOKENS_PER_USER`, blocking all new deposit/debt token operations — (`contracts/Pool.sol:143`)

### Summary
`Pool` maintains a per-account set of deposit/debt tokens (`depositTokensOfAccount`, `debtTokensOfAccount`, `MappedEnumerableSet` in `contracts/storage/PoolStorage.sol:78-83`) capped at `MAX_TOKENS_PER_USER = 30` (`contracts/Pool.sol:79`). The `onlyIfAdditionWillNotReachMaxTokens` modifier on `addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` reverts once the combined count reaches 30. An unprivileged attacker can deposit dust into every whitelisted collateral and `transfer`/`transferFrom` dust `DepositToken` balances to a victim, filling the victim's set. Every subsequent operation that would add a *new* token to the victim's set (depositing a new collateral type, receiving a new `DepositToken`, minting a new synthetic) reverts — a liveness denial analogous to the Xen event-flood hang of CVE-2020-27673.

### Finding Description
- `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` are called by `DepositToken`/`DebtToken` whenever an account's balance transitions from 0 to non-zero (`contracts/Pool.sol:204-220`).
- The modifier checks `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` and reverts with `UserReachedMaxTokens()` *before* the add is attempted (`contracts/Pool.sol:143-148`). Once the cap is hit, every add path reverts regardless of the token.
- Attack path: for each whitelisted `DepositToken`, attacker calls `deposit(dust)` on their own account, then `depositToken.transfer(victim, dust)`. Each transfer triggers a 0→nonzero balance on the victim and registers the token in the victim's set. After N transfers the victim's set is at the cap.
- No authorization gates the victim's side: there is no opt-in, the recipient cannot refuse the transfer, and SynthContext/pause flags do not help. Attacker needs only an EOA and public entry points.

### Impact Explanation
While capped, the victim cannot deposit any collateral type they don't already hold (new-collateral `deposit` reverts inside the `DepositToken` hook), cannot receive any new `DepositToken` by transfer, and cannot mint/issue any new synthetic (`DebtToken` add reverts), also breaking `SmartFarmingManager.leverage` flows that would open a new token position for them. This is a temporary freezing of funds/positions sustained as long as the attacker keeps the set filled; the victim can only recover by fully transferring out a dust balance to shrink the set, which the attacker can front-run and re-fill at dust cost. Positions that are already multi-token or need a new collateral to stay healthy are the most exposed.

### Likelihood Explanation
Requires only a normal EOA, public `deposit`/`transfer`, and dust amounts of each whitelisted underlying (bounded by the number of registered deposit tokens, which is itself limited). No privileged role, oracle manipulation, or timing dependency. Cost is gas plus unrecoverable dust per token.

### Recommendation
- Replace the hard revert in `onlyIfAdditionWillNotReachMaxTokens` with a no-op (or allow overflow) when the token is already in the set, and only enforce the cap for genuinely new entries, so users holding ≤30 tokens are never bricked by incoming dust.
- Alternatively, let accounts self-remove entries (e.g., a `removeDepositTokenOfAccount` that the account can call when its balance of that token is below a threshold), or check membership (`contains`) before enforcing the cap.

### Proof of Concept
Hardhat fork sketch (deployments exist under `deployments/` for mainnet/base/optimism):

```ts
const pool = await ethers.getContractAt("Pool", POOL_PROXY);
const depositTokens: string[] = await pool.getDepositTokens(); // whitelisted collaterals

const victim = victimAddr;
for (const dt of depositTokens) {
  const token = await ethers.getContractAt("DepositToken", dt);
  const underlying = await ethers.getContractAt("IERC20", await token.underlying());
  // acquire dust of underlying, then:
  await underlying.approve(token.address, 1n);
  await token.deposit(1n);                 // attacker deposits dust
  await token.transfer(victim, 1n);        // fills victim's depositTokensOfAccount
}
expect(await pool.getDepositTokensOfAccount(victim)).to.have.length(30);

// victim can no longer receive a new collateral type or mint a new synthetic:
await expect(token.connect(victimSigner).deposit(1n)).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");
```

*Caveat: I verified the cap enforcement and per-account sets in `contracts/Pool.sol` and `contracts/storage/PoolStorage.sol`; the exact `DepositToken`/`DebtToken` hook that invokes `addToDepositTokensOfAccount` on 0→nonzero balances was not read in this session, but the function's NatSpec (`called from DepositToken when user's balance changes from 0`, `contracts/Pool.sol:211-213`) documents that call path.*
