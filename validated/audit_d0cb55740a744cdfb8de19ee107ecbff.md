### Title
Reftable binary length fields trusted without bounds validation causing out-of-range panic (DoS) - (File: internal/git/reftable/reftable.go)

### Summary
The external report describes `fd_bank` trusting length/size fields (`payload_sz`, `message_off`, etc.) that arrive from another process (`fd_pack`) via shared memory, and using them directly in memory-copy/hash operations without validating them against the actual buffer bounds, causing memory corruption. The closest reachable analog in Gitaly is the custom reftable binary parser in `internal/git/reftable/reftable.go`, which decodes length-prefixed fields straight out of a `.ref` table file and uses them immediately to slice byte buffers, without validating that the decoded lengths actually fit inside the buffer that is being read.

### Finding Description
`Table.getRefsFromBlock` decodes `prefixLength` and `suffixLength` via `getVarInt` and then immediately does: [1](#0-0) 

Neither `prefixLength` (bounded only implicitly by the length of `prefix`, the previous refname) nor `suffixLength` is checked against the remaining bytes available in `src` before being used to slice `prefix[:prefixLength]` and `src[idx:idx+suffixLength]`. The same pattern repeats for the SHA/target fields and for symref sizes: [2](#0-1) 

`getVarInt` itself only bounds-checks the *continuation* bytes of the varint against `blockEnd`, not the final decoded value against the size of `src`: [3](#0-2) 

Because Go slice indexing performs a runtime bounds check (unlike the C `fd_memcpy`/`blake3_append` in the referenced report, which crash via out-of-bounds memory access), a malformed or truncated reftable block causes a Go runtime panic (`index out of range` / `slice bounds out of range`) rather than silent memory corruption. This still satisfies the same root-cause bug class: **trusting a length field that originates from another entity/serialized data source without validating it against the real buffer size before performing a memory operation.**

`Table` objects are produced by `reftable.ParseTable`, which reads the file header/footer, but never re-validates the internal block contents referenced by `getRefsFromBlock`/`parseRefBlock` — validation is limited to the header magic, version, and footer CRC32, not to per-record length fields inside the block bodies: [4](#0-3) 

Reachable call sites include:
- `internal/gitaly/storage/storagemgr/partition/reftable.go`'s `stageTables`, which parses tables newly written as part of a write transaction (i.e., triggered by an ordinary user's push / `WriteRef` / branch creation when the reftable backend is used): [5](#0-4) 
- Repository replication (`ReplicateRepository`), which snapshots a source repository (including its raw `.git/reftable` files) and re-creates the target from that snapshot: [6](#0-5) 
- Backup/restore code paths that read reftable tables (`internal/backup/repository.go`).

### Impact Explanation
A malformed reftable block — whether from disk corruption, a partially-written/compacted table observed mid-write, or any table whose internal record encoding does not match the exact assumptions made by this hand-rolled parser — triggers an unrecovered Go slice-bounds panic inside `getRefsFromBlock`/`parseRefBlock`/`getVarInt`. If the panic occurs on a goroutine without a `recover()` (e.g., inside a background transaction-manager or replication goroutine rather than directly inside a gRPC handler wrapped by panic-recovery middleware), it can crash the entire `gitaly` process, denying service to all repositories served by that node. Even if caught by request-level recovery middleware, it constitutes a reliable DoS of the affected RPC/transaction path (`ReplicateRepository`, transaction commit for reftable-backed repositories, or any RPC that lists references from a reftable-backed repo).

### Likelihood Explanation
The likelihood of a *purely* user-triggered malformed reftable file is moderate: table files are normally generated by `git`'s own trusted reftable writer, so most day-to-day pushes/branch operations won't produce out-of-spec encodings. However, the parser is a full reimplementation of the reftable format that does not itself validate all invariants the C git writer guarantees, and it operates on files that can arrive from copy/replication/backup-restore paths (`stageTables`, `createFromSnapshot`) where the byte-for-byte format is trusted implicitly rather than being independently validated on ingestion. Any repository whose reftable data becomes corrupted, truncated, or mismatched in transit (e.g. an interrupted write, a partially-copied snapshot, or a bug in table resequencing/patching logic in `stageTables`/`PatchUpdateIndexes`) will hit this unguarded path the next time references are read.

### Recommendation
Harden `Table.getVarInt`, `Table.getRefsFromBlock`, and `Table.parseRefBlock` to validate every decoded length field against the actual bounds of `src`/`prefix` before using it to slice, returning a descriptive error instead of allowing a panic (mirroring the existing "exceeded block length" error style already used for the varint continuation check). In particular:
- Validate `prefixLength <= len(prefix)`.
- Validate `suffixLength` and `idx+suffixLength <= len(src)` (and `<= b.RestartStart`/`b.FullBlockSize` as appropriate).
- Validate hash-size slices (`idx+hashSize <= len(src)`) for regular/peeled references.
- Validate symref `size` against remaining buffer length.
Additionally, wrap top-level goroutines that call into this parser (transaction manager, replication) with panic recovery so a malformed table degrades to a request-level error rather than a full process crash.

### Proof of Concept
Construct or corrupt a `.ref` reftable file so that a ref-block record's suffix-length varint (or the trailing SHA/symref-size field) decodes to a value larger than the remaining bytes in the block (e.g., set the low bits so `suffixLength >> 3` exceeds `b.RestartStart - idx`). Feed this file to `reftable.ParseTable(...).GetReferences()` (directly, or via the `stageTables`/`ReplicateRepository` code paths that call `reftable.ParseTable`). The call to `src[idx:idx+suffixLength]` or `prefix[:prefixLength]` in `getRefsFromBlock` panics with `slice bounds out of range`, since neither value is checked against the length of `src`/`prefix` before use — directly analogous to the reported `fd_bank` crash where an untrusted length field (`payload_sz`) was used unchecked in a downstream memory operation (`fd_blake3_append`).

// getVarInt parses a variable int and increases the index.
func (t *Table) getVarInt(src []byte, start uint, blockEnd uint) (uint, uint, error) {
	var val uint

	val = uint(src[start]) & 0x7f

	for (uint(src[start]) & 0x80) > 0 {
		start++
		if start > blockEnd {
			return 0, 0, fmt.Errorf("exceeded block length")
		}

		val = ((val + 1) << 7) | (uint(src[start]) & 0x7f)
	}

	return start + 1, val, nil
}

func ParseTable(absolutePath string) (_ *Table, returnedErr error) {
	src, err := os.Open(absolutePath)
	if err != nil {
		return nil, fmt.Errorf("open: %w", err)
	}

	defer func() {
		if returnedErr != nil {
			if err := src.Close(); err != nil {
				returnedErr = errors.Join(returnedErr, fmt.Errorf("close: %w", err))
			}
		}
	}()

	t := &Table{src: src, absolutePath: absolutePath}

	var h header
	if err := parseHeader(src, &h); err != nil {
		return nil, fmt.Errorf("parse header: %w", err)
	}

	footerOffset, err := src.Seek(int64(-h.Version.FooterSize()), io.SeekEnd)
	if err != nil {
		return nil, fmt.Errorf("seek footer: %w", err)
	}

	t.footerOffset = uint(footerOffset)

	if err := parseFooter(src, &t.footer); err != nil {
		return nil, fmt.Errorf("parse footer: %w", err)
	}

	if h != t.footer.header {
		return nil, fmt.Errorf("footer doesn't match header")
	}

	t.blockSize = parseUint24(t.footer.BlockSize)

	return t, nil
}
