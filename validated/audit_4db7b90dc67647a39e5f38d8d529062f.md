### Title
Ambiguous `//`-prefixed URI causes `HttpApiAccessFilter` to check the wrong path segment, bypassing the operator-configured `disabledApiList` - (File: framework/src/main/java/org/tron/core/services/filter/HttpApiAccessFilter.java)

### Summary
`HttpApiAccessFilter.isDisabled()` is the security gate that blocks calls to any HTTP wallet API an operator has put in `disabledApiList` (via `CommonParameter`). It reconstructs the request path from `contextPath + servletPath` and re-parses it with `java.net.URI.create(endpoint).normalize()` before checking `endpoint.split("/")[2]` against the disabled-API set. This is exactly the same class of bug as the Coraza advisory: a security-relevant string is parsed twice by two different parsers (the servlet container's path/servlet dispatch logic, and this filter's manual `URI.create` re-parse), and a `//`-prefixed path is interpreted differently by each. [1](#0-0) 

### Finding Description
`isDisabled()` builds `endpoint` from the servlet container's own path resolution and then feeds it to `URI.create(endpoint)`: [2](#0-1) [3](#0-2) 

`java.net.URI` treats a string that begins with `//` as a network-path reference: the first path segment after `//` is parsed as the *authority* (host), not as part of the path. For example `URI.create("//wallet/getnowblock")` yields authority=`wallet`, path=`/getnowblock`. `normalize()` only simplifies dot-segments in the path and does not touch the authority, so `toString()` still reproduces `//wallet/getnowblock`. When this string is then split on `/`, `endpoint.split("/")[2]` yields `"wallet"` instead of the actual API name `"getnowblock"` — the exact same category of confusion the Coraza advisory describes for `REQUEST_FILENAME` (URL parsed as absolute/authority-bearing instead of as a plain path). The unit test for this method already demonstrates that the check is brittle to any structural difference between the raw path and the literal per-segment index it inspects (e.g. `..` segments shifting the index), confirming the check relies on exact segment counting rather than robust path semantics: [4](#0-3) 

Because Jetty's own servlet-path resolution (used to actually dispatch the request to the target servlet, e.g. `GetNowBlockServlet` mapped at `/wallet/getnowblock`) is a *different* parser/normalizer than `java.net.URI`, a request whose raw path begins with `//` can be dispatched by Jetty to the intended (and supposedly disabled) servlet while `HttpApiAccessFilter.isDisabled()` computes the wrong segment index and therefore never matches the entry in `disabledApiList`, letting the request through with a 200 response rather than the intended 404 "API unavailable" block.

This same filter is chained in front of every wallet/walletsolidity/walletpbft HTTP endpoint set: [5](#0-4) [6](#0-5) [7](#0-6) 

so the bypass potentially reaches any HTTP wallet API an operator relies on `disabledApiList` to block.

### Impact Explanation
`disabledApiList` is the operator's control for turning off specific HTTP API endpoints on a node (for example to prevent exposure of sensitive account/broadcast/asset endpoints on a public-facing node while still running other services). If the segment-matching logic can be defeated with a crafted `//`-prefixed path, an operator's explicit security control silently fails to apply, and an "unprivileged" HTTP client can still reach an API the node operator intended to be closed. Depending on which API the operator disabled (this is config-defined, so it may include write-affecting endpoints reachable through the wallet HTTP surface), this can expose functionality the operator deliberately walled off, which is a concrete availability/config-security failure of a security control that unprivileged clients can trigger directly over HTTP.

### Likelihood Explanation
Exploitation only requires an anonymous HTTP client to send a request whose path starts with `//` (e.g. `GET //wallet/getnowblock`) against a node where the target API is present in `disabledApiList` — no authentication, special permissions, or on-chain transaction is needed. The main uncertainty is whether the embedded Jetty version/`UriCompliance` configuration in this deployment will accept and dispatch such an ambiguous path to the real servlet rather than normalizing/rejecting it before it reaches routing; this depends on Jetty version and compliance settings that were not directly inspected in the available index, so likelihood should be validated against the exact Jetty configuration in use.

### Recommendation
Do not re-derive the security-relevant path from `URI.create(contextPath + servletPath)` and split-by-index. Instead, use the servlet-container-resolved `servletPath`/`pathInfo` values directly (which Jetty has already normalized for dispatch) to extract the API name, or compare against `disabledApiList` using the same normalized value the container used to route the request, so the filter's decision and the dispatcher's decision are always derived from a single canonical parse.

### Proof of Concept
1. Configure `disabledApiList` to include `getnowblock` (or any other wallet API).
2. Send `GET //wallet/getnowblock HTTP/1.1` to the node's HTTP API port (instead of `GET /wallet/getnowblock`).
3. In `isDisabled`, `endpoint` becomes `//wallet/getnowblock`; `URI.create(endpoint).normalize().toString()` remains `//wallet/getnowblock` (authority `wallet`, path `/getnowblock`); `endpoint.split("/")[2]` evaluates to `"wallet"`, which is not in `disabledApiList`, so `isDisabled` returns `false`.
4. If Jetty's routing still maps the ambiguous `//wallet/getnowblock` request to the `getnowblock` servlet, the disabled API responds normally instead of returning the configured 404 block — confirming the bypass. (This last step's outcome depends on the Jetty version's URI-ambiguity handling and should be verified empirically against the deployed Jetty configuration.)

  private boolean isDisabled(String endpoint) {
    boolean disabled = false;

    try {
      endpoint = URI.create(endpoint).normalize().toString();
      List<String> disabledApiList = CommonParameter.getInstance().getDisabledApiList();
      if (!disabledApiList.isEmpty()) {
        disabled = disabledApiList.contains(endpoint.split("/")[2].toLowerCase(Locale.ROOT));
      }
    } catch (Exception e) {
      logger.warn("check isDisabled except, endpoint={}, {}", endpoint, e.getMessage());
    }

    return disabled;
  }
