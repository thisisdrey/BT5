Audit Report

## Title
`process_delivery_receipt` ignores the `success` field of the delivery receipt and always pays the relayer reward - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt` carries a `success: bool` field decoded from the Ethereum `InboundMessageDispatched(nonce, topic, success, reward_address)` event, indicating whether the message actually executed successfully on the Ethereum Gateway. `Pallet::process_delivery_receipt` decodes and validates the gateway and nonce, but never checks `receipt.success` before paying the reward and clearing the pending order.

## Finding Description
`DeliveryReceipt` is decoded with an explicit `success` field populated directly from the Ethereum log [4](#0-3) .

`process_delivery_receipt` checks only the gateway address and the pending nonce, then unconditionally pays `order.fee` to `reward_account` and removes the order, discarding `receipt.success` entirely [5](#0-4) . The public, permissionless `submit_delivery_receipt` extrinsic reaches this function after only verifying proof authenticity and log decoding — neither of which examines the `success` flag's value, only its presence as a decoded field [6](#0-5) . Once verification and decoding succeed (proving only that a genuine `InboundMessageDispatched` log for a matching nonce/gateway was included on Ethereum, not that `success` was `true`), the pallet pays out and settles regardless of the actual dispatch outcome recorded in that same log.

## Impact Explanation
If message execution fails on the Ethereum Gateway (destination-side revert, out-of-gas, invalid command, etc.) but the receipt log itself is legitimately emitted with `success: false`, the relayer is nevertheless rewarded via `T::RewardPayment::register_reward` and the corresponding `PendingOrder` is removed from `PendingOrders`. This settles bridge bookkeeping and pays fees for work that did not actually complete correctly — a duplicate/incorrect settlement of bridge reward state despite an ignored error/status code, matching the "public underpriced work that degrades... stalls bridge processing" and "duplicate settlement or payout" impact categories.

## Likelihood Explanation
The path requires no privileged actor: any signed account may call `submit_delivery_receipt` with a legitimately produced Ethereum receipt for a message whose on-chain dispatch failed — a condition that arises naturally whenever a real cross-chain command reverts on the Gateway, not only via malicious action. The verifier and decode checks gating this function do not examine `success`, so the flawed downstream logic in `process_delivery_receipt` is reached on every dispatch-failure receipt with no extra attacker effort.

## Recommendation
Check `receipt.success` in `process_delivery_receipt` and branch accordingly: only pay the full reward when `success == true`; for `success == false`, take a distinct code path (e.g., settle delivery-attempt accounting without rewarding as a success, or emit a distinct failure event and apply reduced/no fee logic per protocol intent). At minimum, the `success` value should be consciously handled rather than silently discarded.

## Proof of Concept
1. A message is queued via `do_process_message`, creating `PendingOrders[nonce]` with a non-zero `fee` [7](#0-6) .
2. On Ethereum, the Gateway attempts dispatch and reverts/fails, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a valid receipt/execution proof for that legitimately emitted, failed log and calls `submit_delivery_receipt`; verification succeeds because it only checks proof validity, not the `success` flag [8](#0-7) .
4. `DeliveryReceipt::try_from` decodes `success: false` correctly, but `process_delivery_receipt` never reads it [9](#0-8) .
5. The relayer is paid `order.fee` and `PendingOrders[nonce]` is removed as if the message were successfully delivered.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
