### Title
Invalid/negative `Content-Length` header silently downgrades to `None`→`0`, enabling HTTP request smuggling on keep-alive RPC connections - (File: stackslib/src/net/http/request.rs)

### Summary
`HttpRequestPreamble::consensus_deserialize` parses the `Content-Length` header with `value.parse::<u32>()` and, on any parse failure (e.g. `-1`, non-numeric, or overflow), silently stores `None` instead of rejecting the request. `get_content_length()` then defaults a missing/invalid `Content-Length` to `0`, so a request with a malformed `Content-Length` header is treated by the framing/body-consumption logic as having zero body bytes even though the client can still send an arbitrary number of body bytes after the headers.

### Finding Description
In `HttpRequestPreamble::consensus_deserialize`, the header loop for `content-length` is: [1](#0-0) 
Any value that isn't a valid non-negative `u32` (e.g. `"-1"`, `"abc"`, or an out-of-range number) fails `parse::<u32>()` and is coerced to `None` rather than causing `consensus_deserialize` to return an error. Crucially, this is the *only* place `content-length` is validated — no other check downstream rejects a preamble with `content_length: None` when a body is actually present.

Later, request framing uses: [2](#0-1) 
`get_content_length()` explicitly documents "If there is no valid Content-Length header, then the Content-Length is 0" — this is the fallback the question describes. Any connection-layer code that determines how many bytes constitute this request's body (i.e., `payload_len`/body-consumption logic invoked after the preamble is parsed) would use `get_content_length()` to know how many bytes to strip off the stream as this request's body.

**Attacker's exact message on a keep-alive connection:**
```
POST /v2/transactions HTTP/1.1\r\n
Host: <node>\r\n
Content-Type: application/octet-stream\r\n
Content-Length: -1\r\n
Connection: keep-alive\r\n
\r\n
<N attacker-chosen bytes>
GET /v2/info HTTP/1.1\r\n
Host: <node>\r\n
\r\n
```
With `Content-Length: -1`, `content_length` becomes `None`, so `get_content_length()` returns `0`. If the body-consumption path for this request pulls `0` bytes as the body (matching `get_content_length()`), the `N` attacker bytes remain in the connection's read buffer and are handed to the *next* preamble parse — meaning the attacker has smuggled `N` bytes that get reinterpreted as (part of) the following pipelined request, or as a forged prefix to whatever the next legitimate client request is on that same connection.

### Impact Explanation
This breaks the framing equality the server relies on for keep-alive connections: "bytes treated as this request's body" must equal "bytes the client actually sent as body." Because it doesn't, an attacker who can open a keep-alive RPC connection can inject bytes that get parsed as an independent, attacker-controlled subsequent HTTP request on the same connection. This is request smuggling — matching the Critical category defined in scope ("request smuggling or auth bypass"). The severity depends on what shares that keep-alive connection (e.g., a proxy or another client multiplexing requests), but purely within a single attacker-controlled connection, the smuggled bytes are simply reparsed as another attacker request, which by itself doesn't cross a privilege boundary. The exploitable, repeatable impact is that the RPC handler's framing/state machine desyncs — parsing subsequent bytes at the wrong offset — as long as the actual body-consumption path keys off `get_content_length()` for skip/streaming length, rather than an independent authoritative check.

### Likelihood Explanation
I could not fully verify, within the available tool budget, the exact code that performs body/stream consumption (e.g., `stream_payload` or equivalent logic in `stackslib/src/net/httpcore.rs` / `stackslib/src/net/connection.rs`) to confirm it unconditionally uses `get_content_length()` as the byte count to skip/read for this request's body, and that no other layer (e.g., `httparse`, or a subsequent explicit `Content-Length` re-validation, or requiring `content_length.is_some()` for POST-accepting endpoints) rejects or otherwise safely handles the `None` case before reaching the framing logic. The parsing behavior in `request.rs` (silent `None` on invalid `Content-Length`, and `get_content_length()` defaulting to `0`) is confirmed directly in the source, but the second half of the claimed chain — that the connection layer actually consumes exactly `get_content_length()` bytes as the body regardless of what the client sends afterward — was not directly confirmed due to running out of iterations before reading `stream_payload`/connection-layer body consumption code.

### Recommendation
In `HttpRequestPreamble::consensus_deserialize` (`stackslib/src/net/http/request.rs`, lines 392-398), return a `CodecError::DeserializeError` instead of silently defaulting to `None` when `Content-Length` fails to parse as a valid `u32`. Likewise, audit the `host` (lines 381-386) and other header-parsing branches for the same silent-failure pattern. Additionally, review the connection/body-consumption logic (in `httpcore.rs`/`connection.rs`) that calls `get_content_length()` to confirm it cannot be tricked into treating a non-zero actual body as zero-length.
