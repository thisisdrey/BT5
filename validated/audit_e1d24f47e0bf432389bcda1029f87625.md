### Title
Missing certificate binding validation of RelayFromAddr/RelayToAddr allows relay state poisoning with attacker-chosen vpnAddr - (File: relay_manager.go)

### Summary
`relayManager.HandleControlMsg`, `handleCreateRelayRequest`, and `handleCreateRelayResponse` decode `RelayFromAddr`/`RelayToAddr` (or their v1-encoded `OldRelayFromAddr`/`OldRelayToAddr` equivalents) directly from the attacker-controlled `NebulaControl` protobuf payload and pass them straight into `AddRelay` without ever checking that these addresses match the certificate-verified `vpnAddrs` of the sending `HostInfo h`. This lets an already-tunneled but unprivileged peer register relay state (`h.relayState`) under an arbitrary `PeerAddr` it does not own.

### Finding Description
In `relay_manager.go` `HandleControlMsg` (`relay_manager.go:298-342`), the only validation performed on `msg.RelayFromAddr`/`msg.RelayToAddr` is a nil-check (`relay_manager.go:322-334`); there is no check that these decoded addresses correspond to the actual certificate `vpnAddrs` bound to the sending `HostInfo h` (h.vpnAddrs, set from h's verified cert during the handshake). The v1/v2 detection heuristic (`if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0`, `relay_manager.go:307`) only decides which wire encoding to decode from — it does not add any authentication of the resulting address values, and an attacker fully controls which branch is taken and what value ends up in `RelayFromAddr`/`RelayToAddr` regardless of encoding chosen.

In `handleCreateRelayRequest` (`relay_manager.go:426-604`), `from := protoAddrToNetAddr(m.RelayFromAddr)` is used directly as the key installed into `h.relayState` via `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)` (`relay_manager.go:482`), with `h` being whatever real `HostInfo` sent the control message. The only checks performed are that `from` is not one of *my* own addresses (`relay_manager.go:441-444`) and that `target` is not one of my own addresses (`relay_manager.go:447`) — there is no assertion that `from == h.vpnAddrs[i]` for any `i`, i.e., that the claimed relay-from address is actually the sender's own cert-issued address. Similarly `handleCreateRelayResponse` (`relay_manager.go:344-424`) trusts `m.RelayFromAddr`/`m.RelayToAddr` from the response without cross-checking against `h.vpnAddrs`.

Because of this, a peer with a valid but unrelated certificate can send a `CreateRelayRequest` where `RelayFromAddr` is set to some other vpnAddr it does not own (disjoint from its own certificate networks), and the relay/terminal node will still call `AddRelay` and install relay state (`Relay{PeerAddr: from, ...}`) keyed to that spoofed address, tied to the attacker's actual `HostInfo`/tunnel `h`.

### Impact Explanation
This is a remote state-poisoning bug in the relay subsystem: `hm.Relays[index]` / `h.relayState` entries can be created and keyed by vpnAddr values that were never certificate-verified for the requesting peer, violating the intended identity binding between a relay path and the certificate vpnAddr it claims to represent. Any downstream logic that trusts `Relay.PeerAddr`/`RelayFromAddr` for identity or firewall-scoping purposes on the relay/terminal node would then be operating on an unauthenticated value rather than the peer's real cert vpnAddr, which is the specific concern the question raises about "violating firewall/identity binding for relay path establishment." I was not able to fully trace and confirm the exact firewall-matching code path (`handleOutsideRelayPacket`) in this session, so the precise blast radius (whether it directly yields a firewall bypass or is limited to relay bookkeeping/DoS against the state map) could not be fully verified from the code read so far.

### Likelihood Explanation
Low precondition burden: any unprivileged node that already has a legitimate signed certificate and an established tunnel to the relay/terminal node (a normal, non-malicious-peer scenario per the question's framing, since it only requires crafting one field of an otherwise-normal control message) can trigger this by simply setting `RelayFromAddr` to an arbitrary value in its own outgoing `CreateRelayRequest`. No cryptographic bypass or race condition is required — it's a straightforward missing-validation bug, fully reproducible.

### Recommendation
In `handleCreateRelayRequest` and `handleCreateRelayResponse`, validate that `from` (`RelayFromAddr`) is contained in `h.vpnAddrs` (the certificate-verified addresses of the sending `HostInfo`) before calling `AddRelay`, and reject/log-and-drop the control message otherwise. This should be enforced independent of whether the message used the v1 (`OldRelayFromAddr`/`OldRelayToAddr`) or v2 (`RelayFromAddr`/`RelayToAddr`) encoding.

### Proof of Concept
Unit test plan in `relay_manager_test.go` (or extending `control_test.go`):
1. Build two `HostInfo`s: `h` with real `vpnAddrs = [A]`, and a victim address `X` not in `h.vpnAddrs` and not present elsewhere in the hostmap.
2. Construct a `NebulaControl{Type: CreateRelayRequest, RelayFromAddr: netAddrToProtoAddr(X), RelayToAddr: netAddrToProtoAddr(myVpnAddr)}` (target = the node under test, so the "target==me" branch is taken).
3. Call `rm.HandleControlMsg(h, msg.Marshal(), f)`.
4. Assert that `h.relayState.QueryRelayForByIp(X)` returns `ok == false` (i.e., no relay state should have been created for an address not owned by `h`), and expect a rejection log rather than a successful `CreateRelayResponse` being sent for `RelayFromAddr = X`.
5. Currently, the assertion fails: `AddRelay` succeeds and `h.relayState` contains a relay keyed on `X`, and a `CreateRelayResponse` is sent back echoing `RelayFromAddr = X`, demonstrating the missing certificate-vpnAddr binding check.
