### Title
Unvalidated `GitObjectDirectory`/`GitAlternateObjectDirectories` fields let custom hooks escape storage root via `GIT_OBJECT_DIRECTORY` environment injection - (File: internal/gitaly/hook/custom.go, internal/gitaly/hook/prereceive.go)

### Summary
Gitaly has two independent implementations that turn a repository's `GitObjectDirectory`/`GitAlternateObjectDirectories` protobuf fields into an on-disk path. `localrepo.Repo.ObjectDirectoryPath()` performs careful bounds checking (storage-root containment plus an explicit quarantine-directory-prefix check) before trusting these fields. However, the hook-execution code path — `hook.getRelativeObjectDirs()` and `hook.customHooksEnv()` — recomputes/consumes the very same fields with no equivalent validation, mirroring the IdleCDO pattern of two divergent price-calculation implementations that should have been unified into one.

### Finding Description
`localrepo.Repo.ObjectDirectoryPath()` treats the repository's `GitObjectDirectory` as untrusted input and validates it against the storage root and the expected quarantine-directory prefix before use: [1](#0-0) 

By contrast, when a `pre-receive`/`update`/`post-receive` custom hook is executed, the same `GitObjectDirectory`/`GitAlternateObjectDirectories` fields are turned into `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` environment variables with a bare `filepath.Join`, with no call to `storage.ValidateRelativePath` or any quarantine-prefix check: [2](#0-1) 

Feeding this pipeline, `preReceiveHook()` recomputes `repo.GitObjectDirectory`/`repo.GitAlternateObjectDirectories` from the `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` environment variables carried in the RPC request itself, using `filepath.Rel()`, which happily produces paths containing `..` segments and performs no containment check: [3](#0-2) [4](#0-3) 

The only validation performed on the inbound `PreReceiveHookRequest.Repository` is `ValidateRepository`, which only checks `StorageName`/`RelativePath` — it never inspects `GitObjectDirectory` or `GitAlternateObjectDirectories`: [5](#0-4) [6](#0-5) 

Thus a `Repository` message whose `GitObjectDirectory`/`GitAlternateObjectDirectories` fields (or the corresponding `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` env vars forwarded in the hook RPC) contain path-traversal sequences such as `../../../../tmp/evil` will pass straight through `getRelativeObjectDirs()`/`customHooksEnv()` untouched, and the resulting absolute path is exported as `GIT_OBJECT_DIRECTORY` to every custom hook subprocess that Gitaly spawns for that push — exactly the kind of "two implementations, one strict one permissive" divergence the IdleCDO report warns about, except here the divergence is security-relevant rather than an accounting rounding difference.

### Impact Explanation
Any git process invoked by a custom hook (or the custom hook binary itself, since it also inherits the crafted `GIT_DIR`/`GIT_OBJECT_DIRECTORY` pair) can be redirected to read or write Git objects at an attacker-chosen filesystem location outside of the intended repository/storage root. This can be used to: leak objects from other repositories into the malicious repo's object store (cross-repository object access), corrupt or plant files at a path the operator did not intend (storage escape via quarantine/hook environment), or otherwise bypass the invariant — enforced everywhere else in the codebase (`localrepo.paths.go`, `internal/gitaly/storage/locator.go`) — that object-directory paths must stay inside the storage root.

### Likelihood Explanation
The `GitObjectDirectory`/`GitAlternateObjectDirectories` values are meant to be relative, quarantine-scoped paths produced internally by Git/Gitaly during a push, and are normally re-derived faithfully. However, because `ValidateRepository()` never checks these two fields, and `getRelativeObjectDirs()`/`customHooksEnv()` perform no containment check unlike their sibling implementation in `localrepo/paths.go`, any component in the request chain that forwards a `Repository` message with attacker-influenced `GitObjectDirectory`/`GitAlternateObjectDirectories` (or forwards raw `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` environment variables reaching the `PreReceiveHookRequest`) can trigger the divergence deterministically — there is no probabilistic race condition involved, only a missing validation call that exists elsewhere in the same codebase.

### Recommendation
Route `GitObjectDirectory`/`GitAlternateObjectDirectories` resolution through a single, shared implementation — the same containment/quarantine-prefix validation already implemented in `localrepo.Repo.ObjectDirectoryPath()` — and call it from `hook.getRelativeObjectDirs()` and `hook.customHooksEnv()` instead of doing ad hoc `filepath.Join`/`filepath.Rel`. Additionally, extend `storage.Locator.ValidateRepository()`/`ValidateRepositoryOption` to validate these two fields whenever they are present on an inbound `gitalypb.Repository` message, closing the gap that lets `pre_receive.go`'s `validatePreReceiveHookRequest` accept unchecked values.

### Proof of Concept
1. Craft (or cause to be forwarded) a `PreReceiveHookRequest` whose `Repository.GitObjectDirectory` is set to a path-traversal string, e.g. `../../../../tmp/evil-objects`, or whose forwarded environment contains `GIT_OBJECT_DIRECTORY=/tmp/evil-objects` and `GIT_ALTERNATE_OBJECT_DIRECTORIES=/tmp/evil-objects` for a repository whose real path is `/var/opt/gitlab/git-data/repositories/<hashed>/repo.git`.
2. `preReceiveHook()` calls `getRelativeObjectDirs(repoPath, "/tmp/evil-objects", "/tmp/evil-objects")`, which via `filepath.Rel` returns `../../../../tmp/evil-objects` without error, and stores it into `repo.GitObjectDirectory`.
3. `customHooksEnv()` computes `filepath.Join(repoPath, "../../../../tmp/evil-objects")` = `/tmp/evil-objects` and exports it as `GIT_OBJECT_DIRECTORY` to every configured custom pre-receive hook process.
4. Any `git` invocation performed by that custom hook (or a maliciously crafted custom hook script that simply reads `$GIT_OBJECT_DIRECTORY`) now operates against `/tmp/evil-objects`, entirely outside the storage root that `localrepo.ObjectDirectoryPath()` would have rejected with `InvalidArgument: not a valid relative path`.

func (m *GitLabHookManager) customHooksEnv(ctx context.Context, payload gitcmd.HooksPayload, pushOptions []string, envs []string) ([]string, error) {
	repoPath, err := m.locator.GetRepoPath(ctx, payload.Repo, storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, err
	}

	customEnvs := append(command.AllowedEnvironment(envs), pushOptionsEnv(pushOptions)...)

	objectDirectory := env.ExtractValue(envs, "GIT_OBJECT_DIRECTORY")
	if objectDirectory == "" && payload.Repo.GetGitObjectDirectory() != "" {
		objectDirectory = filepath.Join(repoPath, payload.Repo.GetGitObjectDirectory())
	}
	if objectDirectory != "" {
		customEnvs = append(customEnvs, "GIT_OBJECT_DIRECTORY="+objectDirectory)
	}

	alternateObjectDirectories := env.ExtractValue(envs, "GIT_ALTERNATE_OBJECT_DIRECTORIES")
	if alternateObjectDirectories == "" && len(payload.Repo.GetGitAlternateObjectDirectories()) != 0 {
		var absolutePaths []string
		for _, alternateObjectDirectory := range payload.Repo.GetGitAlternateObjectDirectories() {
			absolutePaths = append(absolutePaths, filepath.Join(repoPath, alternateObjectDirectory))
		}
		alternateObjectDirectories = strings.Join(absolutePaths, ":")
	}
	if alternateObjectDirectories != "" {
		customEnvs = append(customEnvs, "GIT_ALTERNATE_OBJECT_DIRECTORIES="+alternateObjectDirectories)
	}

func getRelativeObjectDirs(repoPath, gitObjectDir, gitAlternateObjectDirs string) (string, []string, error) {
	repoPathReal, err := filepath.EvalSymlinks(repoPath)
	if err != nil {
		return "", nil, err
	}

	gitObjDirRel, err := filepath.Rel(repoPathReal, gitObjectDir)
	if err != nil {
		return "", nil, err
	}

	var gitAltObjDirsRel []string

	for _, gitAltObjDirAbs := range strings.Split(gitAlternateObjectDirs, ":") {
		gitAltObjDirRel, err := filepath.Rel(repoPathReal, gitAltObjDirAbs)
		if err != nil {
			return "", nil, err
		}

		gitAltObjDirsRel = append(gitAltObjDirsRel, gitAltObjDirRel)
	}

	return gitObjDirRel, gitAltObjDirsRel, nil
}

func (m *GitLabHookManager) preReceiveHook(ctx context.Context, payload gitcmd.HooksPayload, repo *gitalypb.Repository, pushOptions, envs []string, changes []byte, stdout, stderr io.Writer) error {
	repoPath, err := m.locator.GetRepoPath(ctx, repo)
	if err != nil {
		return structerr.NewInternal("getting repo path: %w", err)
	}

	if gitObjDir, gitAltObjDirs := env.ExtractValue(envs, "GIT_OBJECT_DIRECTORY"), env.ExtractValue(envs, "GIT_ALTERNATE_OBJECT_DIRECTORIES"); gitObjDir != "" && gitAltObjDirs != "" {
		gitObjectDirRel, gitAltObjectDirRel, err := getRelativeObjectDirs(repoPath, gitObjDir, gitAltObjDirs)
		if err != nil {
			return structerr.NewInternal("getting relative git object directories: %w", err)
		}

		repo.GitObjectDirectory = gitObjectDirRel
		repo.GitAlternateObjectDirectories = gitAltObjectDirRel
	}

// ValidateRepository validates whether the given path points to a valid Git repository. This
// function returns:
//
// - ErrRepositoryNotFound when the path cannot be found.
// - ErrRepositoryNotValid when the repository is not a valid Git repository.
// - An unspecified error when stat(3P)ing files fails due to other reasons.
func (l *configLocator) ValidateRepository(ctx context.Context, repo storage.Repository, opts ...storage.ValidateRepositoryOption) error {
	var cfg storage.ValidateRepositoryConfig
	for _, opt := range opts {
		opt(&cfg)
	}

	// Only checking for `nil` isn't sufficient as Protobuf messages may be non-nil, but still
	// either invalid or empty. Thus we also explicitly verify whether both the storage name and
	// the relative path are unset.
	if repo == nil || repo.GetStorageName() == "" && repo.GetRelativePath() == "" {
		return structerr.NewInvalidArgument("%w", storage.ErrRepositoryNotSet)
	}

	relativePath := repo.GetRelativePath()
	if len(relativePath) == 0 {
		return structerr.NewInvalidArgument("%w", storage.ErrRepositoryPathNotSet)
	}
