### Title
Stale `PromiseYield` state survives `DeleteAccount`, letting a resumed/timed-out yield execute with self-call privilege against a re-created account's new contract - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` in `core/store/src/utils/mod.rs` deletes the `Account`, `ContractCode`, access keys, and contract data for an account, but never removes `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, or `TrieKey::DataIdToYieldId` entries belonging to that account. Because `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls only `remove_account` and does not separately purge these keys, a `PromiseYield` created by the account before deletion remains parked in state and its already-scheduled timeout entry remains in the `PromiseYieldTimeout` queue. When the timeout later fires (or if the stale `PromiseResume` is otherwise delivered), the runtime executes the original parked receipt with `predecessor_id == receiver_id == account_id`, i.e. full "self-call" trust, against whatever contract now occupies that account id.

### Finding Description
`set_promise_yield_receipt` stores the entire pending action receipt keyed only by `(receiver_id, data_id)` [1](#0-0) , and this receipt's `predecessor_id` is set to the yielding account itself at creation time [2](#0-1) . `enqueue_promise_yield_timeout` independently records a `(account_id, data_id, expires_at)` entry in the global FIFO timeout queue [3](#0-2) .

`remove_account` iterates and removes `Account`, `ContractCode`, access/gas keys, and `ContractData`, but has no logic touching `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId` for the account being deleted [4](#0-3) . `action_delete_account` simply calls `remove_account` and clears the in-memory `Account` [5](#0-4) ; there is no code path that also calls `remove_promise_yield_receipt`, `remove_promise_yield_status`, or `remove_yield_id_mappings`, nor one that scans/dequeues the account's pending `PromiseYieldTimeout` entries.

Consequently:
1. Attacker controls account `A`. From a contract call on `A`, it issues `promise_yield_create` targeting itself (`receiver_id == A`) with a chosen callback method/args, which writes `PromiseYieldReceipt{receiver_id: A, data_id}` and a corresponding `PromiseYieldTimeout` queue entry with `account_id: A`.
2. Attacker submits `DeleteAccount(A)`. `action_delete_account`/`remove_account` deletes the account and code but leaves the `PromiseYieldReceipt`/timeout entry intact.
3. Account id `A` is later re-created (e.g. by a subaccount-name registrar/factory flow where a different logical owner ends up controlling `A`) and a victim deploys their own contract to `A`.
4. When the timeout expires, `resolve_promise_yield_timeouts` checks only `state_update.contains_key(&PromiseYieldReceipt{A, data_id})` — it does not check that the account is "the same" account that created the yield — and, finding it still present, synthesizes and forwards a `PromiseResume` for `A` [6](#0-5) .
5. Processing that `PromiseResume` fetches the still-stored yield receipt via `get_promise_yield_receipt(state_update, account_id, data_id)` and executes it via `apply_action_receipt`, without any re-validation that the account/contract is still the same entity that originally created the yield [7](#0-6) .
6. The executed receipt carries `predecessor_id == receiver_id == A` (self-call), matching exactly the trust condition many contracts use for privileged internal-only callbacks (`assert_self()`-style checks), so the attacker's pre-planted `FunctionCall` action runs against the victim's freshly deployed contract with full self-call authorization.

No existing check (signature, nonce, access-key permission, or the `DeleteAccountStaking`/`DeleteAccountWithLargeState`/`GasKeyBalanceTooHigh` checks in `action_delete_account`) touches promise-yield trie state, so nothing stops this stale data from persisting across deletion and recreation of the account id.

### Impact Explanation
This is an authorization-escalation / promise-privilege-containment violation: a receipt that should only ever be resumable by the exact same logical contract instance that created it can instead fire against a completely different (later) contract deployed under the same account id, executing with the maximally-trusted `predecessor_id == receiver_id` self-call condition. Depending on what privileged logic the victim's contract gates behind a self-call check (owner/admin actions, upgrades, minting, access-control changes), this allows the original attacker to pre-arm an authorization bypass that fires automatically once the account id is reused, causing arbitrary state mutation / code-path hijack on the victim's contract — a real authorization-escalation impact.

### Likelihood Explanation
Exploitability depends on the account id actually being reusable by a different logical owner after deletion — e.g. subaccount name-reuse via a registrar/factory pattern, or any workflow where a previously-attacker-controlled account id is later handed to (or reclaimed by) a different party who deploys their own contract before the yield timeout (default ~hundreds of blocks) expires. Given that pattern, the attack is cheap (a single `yield_create` call plus a `DeleteAccount` transaction, both ordinary unprivileged actions) and fully repeatable for any account id the attacker previously owned. The core code defect itself (missing cleanup in `remove_account`) is unconditionally present regardless of the reuse scenario.

### Recommendation
`action_delete_account` (or `remove_account`) should purge all promise-yield-related state for the account being deleted before removing the account: iterate/remove any `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId` entries for the account, and mark or drop any outstanding `PromiseYieldTimeout` queue entries referencing it (e.g., by checking account existence — not just receipt existence — in `resolve_promise_yield_timeouts` and in `PromiseResume` processing before executing the parked receipt).

### Proof of Concept
Integration/test-loop test modeled on the existing `runtime/runtime/src/tests/apply.rs::test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code` and `test-loop-tests/src/tests/yield_timeouts.rs` helpers:
1. Deploy a contract on account `A` that calls `promise_yield_create` targeting itself with a callback `FunctionCall` action to method `malicious_privileged_call`.
2. Submit `DeleteAccount(A)` from `A` itself.
3. Recreate `A` (simulating a different owner) and deploy a victim contract exposing a self-only-gated method with the same name as the attacker's chosen callback method (or reachable through the stored action).
4. Advance blocks past `yield_timeout_length_in_blocks` so `resolve_promise_yield_timeouts` fires the stale `PromiseResume`.
5. Assert that the victim contract's privileged method executed successfully with `predecessor_id == receiver_id == A`, despite never being invoked by the victim's own code — proving unauthorized self-privileged execution and demonstrating that `remove_account` failed to purge `PromiseYieldReceipt`/`PromiseYieldTimeout` state.

        VersionedReceiptEnum::PromiseYield(action_receipt) => {
            assert!(action_receipt.input_data_ids().len() == 1);
            let key = TrieKey::PromiseYieldReceipt {
                receiver_id: receipt.receiver_id().clone(),
                data_id: action_receipt.input_data_ids()[0],
            };
            set(state_update, key, receipt);
        }
        _ => unreachable!("Expected PromiseYield receipt"),
    }

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
