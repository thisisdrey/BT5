### Title
Out-of-bounds read while parsing a malicious ZIP central directory entry - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses each ZIP central directory record (`file_name_length`, `extra_field_length`, `file_comment_length`, and the ZIP64 extra-field sub-records) with no bounds checking against the end of the mapped file buffer, unlike the local-file-header path (`ProcessLocalFileEntry`) which explicitly calls `EnsureRemaining()` before every field read [1](#0-0) . A crafted archive with an oversized `extra_field_length` or an inconsistent ZIP64 extra-field `data_size` can advance the cursor `p`/`extra_p` past the end of the mmap'd input, causing subsequent `get_u2le`/`get_u4le`/`memcpy` reads to occur out of bounds.

### Finding Description
`ProcessCentralDirEntry` reads fixed header fields and then walks the "extra field" region using only the untrusted `extra_field_length` supplied by the attacker, with a loop bounded solely by `while (extra_p != p)`, never checking against the input buffer's actual end: [2](#0-1) 

Contrast this with `ProcessLocalFileEntry`, which guards every read with `EnsureRemaining(...)` against `input_file_->Length()`: [3](#0-2) [4](#0-3) 

The only global containment check is in `FindZipCentralDirectory`, which validates that `cd.central_dir_offset + cd.central_dir_size <= in_length` for the *aggregate* central directory region [5](#0-4) . Nothing constrains an *individual* entry's `file_name_length`/`extra_field_length`/`file_comment_length` to remain inside that region or inside the mapped file. A record near the end of the central directory (or one whose extra field advertises a `data_size` that overshoots the declared `extra_field_length`) advances `p`/`extra_p` past the mapped buffer, and the next `get_u4le(p)` (signature check in `ProcessNext`/`CalculateOutputLength`) or the `memcpy(filename, p, len)` copy reads out-of-bounds heap memory adjacent to the mmap region.

This routine is invoked whenever Bazel's `ijar`/`zipper`/`singlejar` toolchain processes a `.jar`/`.zip` file — including third-party jars pulled in via `http_file`/`http_archive`/`http_jar` and Maven-style dependencies that an unprivileged attacker (a malicious mirror/registry/dependency author) fully controls. A pinned `sha256`/`integrity` value only guarantees the downloaded bytes match what was recorded; it does nothing to prevent the attacker from choosing malicious bytes and publishing the matching hash themselves, so checksum verification does not stop this class of bug.

### Impact Explanation
An out-of-bounds heap read while parsing a build-time dependency archive can leak adjacent process memory into the extracted file name buffer (`filename[PATH_MAX]`) or crash the `ijar`/`singlejar` process (denial of service), and in the worst case (overshoot large enough to leave the mapped page) trigger a SIGSEGV. Because this executes as part of ordinary `bazel build`, any project depending on a hostile jar mirror or malicious third-party jar dependency is affected without any additional attacker foothold.

### Likelihood Explanation
Any unprivileged party that can publish a jar/zip artifact consumed by a Bazel build (e.g., a compromised or malicious dependency host, or an untrusted PR branch's referenced prebuilt jar) can trigger this by crafting a central directory entry with an inconsistent `extra_field_length`/ZIP64 extra sub-record. No credentials, sandbox escape, or additional user interaction beyond a routine build are required.

### Recommendation
Add explicit bounds checks in `ProcessCentralDirEntry` (and its `extra_field` sub-record loop) so that all reads are validated against the mapped buffer boundary (`zipdata_in_ + in_length`), mirroring the `EnsureRemaining` checks already used in `ProcessLocalFileEntry`. Also validate that `extra_p + 4 <= p` before reading each `header_id`/`data_size` pair, and that `extra_p + data_size <= p` before advancing, failing the parse otherwise.

### Proof of Concept
A JUnit/`BuildIntegrationTestCase`-style reproduction would:
1. Programmatically build a minimal ZIP whose single central directory entry declares `extra_field_length` large enough to place the true end of the (mmap'd) file inside what should be the extra field, and embeds a ZIP64 extra tag whose `data_size` further overshoots the declared extra field length.
2. Feed this file to `devtools_ijar::ZipExtractor::Create`/`ProcessAll()` (as `ijar_main`/`zipper` does) and run under ASan/Valgrind to observe the heap-buffer-overflow read reported inside `InputZipFile::ProcessCentralDirEntry`.
3. Confirm the crash/leak occurs purely from feeding the crafted bytes, with no additional privileges, matching the "attacker publishes a dependency artifact" threat model.

  // Check that at least n bytes remain in the input file, otherwise
  // abort with an error message.  "state" is the name of the field
  // we're about to read, for diagnostics.
  int EnsureRemaining(size_t n, const char *state) {
    size_t in_offset = p - zipdata_in_;
    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "
                   "expected %zd more bytes but found %zd.\n",
                   in_offset, state, n, remaining);
    }
    return 0;
  }
