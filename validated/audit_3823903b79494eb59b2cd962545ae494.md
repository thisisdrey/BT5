### Title
Dust `DepositToken` transfers fill a victim's 30-token account slots, DoS-ing new collateral deposits and new debt issuance — ([File: contracts/Pool.sol](contracts/Pool.sol), [contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` across `depositTokensOfAccount` + `debtTokensOfAccount` in the `onlyIfAdditionWillNotReachMaxTokens` modifier [1](#0-0) [2](#0-1) . `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes 0 → nonzero, with no opt-in from the recipient [3](#0-2) . An unprivileged attacker can therefore dust-transfer 1 wei of every whitelisted deposit token to a victim, permanently occupying the victim's account slots. Thereafter every `deposit` into a collateral type the victim doesn't already hold reverts in `_mint → addToDepositTokensOfAccount → UserReachedMaxTokens` [4](#0-3) , and `DebtToken.issue` of any synth the victim doesn't already owe reverts in `_mint → addToDebtTokensOfAccount` [5](#0-4) .

### Finding Description
The bug-class analog is "attacker-controlled tokens/deposits block the victim's exit/claim path". In OpenQ it was unbounded `depositId`s and a reverting token; in Metronome the bounded 30-entry account list is itself the exploitable resource, and entry insertion is attacker-driveable via plain `DepositToken.transfer`/`transferFrom` — `transfer` only checks `_revertIfLocked` on the *sender*, never the recipient [6](#0-5) .

Attack steps:

1. Attacker deposits a few wei of underlying into every whitelisted `DepositToken` (cheap; only dust needed).
2. Attacker calls `depositToken.transfer(victim, 1)` for each token. Each call adds that token to `depositTokensOfAccount[victim]` [7](#0-6) .
3. Once `depositTokens + debtTokens` hits 30, `onlyIfAdditionWillNotReachMaxTokens` reverts on any further *new* entry [2](#0-1) .

Consequences for the victim:

- `DepositToken.deposit` into a collateral they don't already hold reverts (the whole tx rolls back after `_mint → addToDepositTokensOfAccount`), so they cannot diversify/top-up with a new collateral type.
- `DebtToken.issue` of a new synth reverts, so they cannot open a new borrow position.
- Self-recovery requires transferring each dust token out to zero-balance (`removeFromDepositTokensOfAccount`) [8](#0-7) . But `transfer`/`withdraw` are gated by `_revertIfLocked → unlockedBalanceOf`, which returns 0 whenever `debtPositionOf` shows `_issuableInUsd == 0` (i.e. the victim is at/below max borrow) [9](#0-8) . A victim carrying a large debt relative to collateral cannot remove the dust slots at all, and simultaneously cannot add new collateral — their only escape is acquiring synths externally to `repay` their debt. Combined with an adverse price move, the victim is prevented from topping up collateral and is pushed into liquidation, losing the liquidation fee spread.

### Impact Explanation
Temporary freezing of funds and forced-liquidation exposure: a levered victim near the health boundary is denied the standard defense (depositing more collateral or issuing other synths) while their position decays. For debt-free victims the impact reduces to blocked deposits until they dust the tokens back out (griefing only). No modifier stops it: `transfer` has no `whenNotShutdown` recipient consent, and `addToDepositTokensOfAccount` only verifies the caller is a registered deposit token, which all whitelisted collaterals are [10](#0-9) .

### Likelihood Explanation
Low-to-moderate cost: one dust deposit + one transfer per whitelisted deposit token (number of collateral types per pool is small, typically < 15). Requires the victim to hold a meaningful position and for slots to matter (victim wanting a *new* collateral/debt type or needing to recover slots while locked). Impact is bounded — the victim retains withdraw/repay paths for tokens already held — so overall severity is Medium rather than the High of the source report.

### Recommendation
- Skip `addToDepositTokensOfAccount` (or use a separate accounting list) for transfers/deposits below a dust threshold, or track per-account tokens only when balance exceeds a minimum.
- Alternatively, allow recipients to purge their own account-list entries via a `removeDepositTokenFromAccount(address token)` user-facing function that verifies `balanceOf == 0`-equivalent conditions, or have `addToDepositTokensOfAccount` evict/zero-check rather than revert when the cap is hit and the added entry is dust.

### Proof of Concept
```ts
// Hardhat fork, pool with >=1 whitelisted DepositToken (e.g. msWETH-like vault share)
// Precondition: victim has an open debt position with _issuableInUsd ~= 0
//               (borrowed near collateral-factor limit).

const depositTokens = await pool.getDepositTokens() // whitelisted collaterals

// 1) Attacker mints dust of each DepositToken and transfers 1 wei to victim
for (const dt of depositTokens) {
  const token = await ethers.getContractAt('DepositToken', dt)
  const underlying = await token.underlying()
  await erc20(underlying).depositOrDeal(attacker, 10)          // dust underlying
  await erc20(underlying).connect(attacker).approve(token.address, 10)
  await token.connect(attacker).deposit(10, attacker.address)  // mints msdTOKEN
  await token.connect(attacker).transfer(victim.address, 1)    // occupies a slot
}

// 2) depositTokensOfAccount[victim] now == all whitelisted tokens
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.lengthOf(depositTokens.length)

// 3) If combined slots (deposits + debts) >= 30, victim cannot use a new collateral:
//    `deposit` reverts inside _mint -> addToDepositTokensOfAccount -> UserReachedMaxTokens
//    `debtToken.issue` of a new synth reverts -> UserReachedMaxTokens

// 4) Victim cannot evict dust: transfer(victim->anywhere, 1) reverts NotEnoughFreeBalance
//    because unlockedBalanceOf(victim) == 0 while _issuableInUsd == 0
await expect(
  dToken.connect(victim).transfer(attacker.address, 1)
).revertedWithCustomError(dToken, 'NotEnoughFreeBalance')
```
The revert chain: `DepositToken.transfer` → `_revertIfLocked` → `unlockedBalanceOf` returns 0 → `NotEnoughFreeBalance`; and `deposit`/`issue` → `addTo*TokensOfAccount` → `UserReachedMaxTokens`. [11](#0-10) [9](#0-8)
