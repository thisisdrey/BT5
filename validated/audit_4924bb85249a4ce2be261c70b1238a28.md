### Title
Access-key nonce reset via same-height DeleteKey+AddKey allows nonce-range underflow and transaction replay - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
`initial_nonce_value(block_height)` reseeds a recreated access key's nonce to `(H-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, which is the *minimum*, not the maximum, of the per-block nonce band `[(H-1)*M, H*M)`. If a key is deleted and re-added (same public key) at the same block height `H` at which it had already consumed a nonce `Y` in that same band (a very common case, since wallets/SDKs conventionally pick nonces close to `current_height * M`), the new nonce seed `(H-1)*M` is strictly less than `Y`. Because the only nonce-replay check is "new nonce > stored nonce," a previously-signed, previously-applied transaction with nonce `Y` for that key becomes valid again and can be resubmitted and re-executed.

### Finding Description

It is used both for regular keys (`add_regular_key`, which sets `access_key.nonce = initial_nonce_value(block_height)`) and for gas keys (`add_gas_key`, which seeds all nonce slots with `initial_nonce_value(block_height)`): [2](#0-1) [3](#0-2) 

`delete_regular_key` fully removes the access-key trie entry (including its stored nonce), losing all history of the highest nonce previously consumed under that key: [4](#0-3) 

The comment on `initial_nonce_value` references issue #3779 and is designed to prevent hash collisions when a key is *later* re-added at a strictly greater block height (`H2 > H`), because then `(H2-1)*M ≥ H*M > Y` for any `Y` consumed under the old incarnation at height `H`. This dominance property does **not** hold when the DeleteKey+AddKey pair executes at the *same* height `H` as the last usage of that key: `(H-1)*M` is the floor of the current band, so any `Y` in `((H-1)*M, H*M)` already consumed by the pre-deletion key is *not* dominated by the new seed.

Exploit flow (fully within one attacker-controlled account, no privileged access required):
1. Attacker's account has full-access key `K1` (used for ordinary transactions) and a second full-access key `K2` (to perform DeleteKey/AddKey).
2. Attacker signs and submits transaction `T1` with key `K1`, nonce `Y` (following the common convention `Y ≈ current_block_height * M`), performing some valuable action (e.g., a `FunctionCall` to a third-party contract that relies on `(signer, nonce)` uniqueness for idempotency, such as a one-time claim/airdrop/voting contract). `T1` is included and applied at block height `H`, and the access key for `K1` is updated to nonce `Y`.
3. In the same block height `H` (a different receipt/transaction, signed with `K2`), the attacker submits `[DeleteKey(K1), AddKey(K1)]`. This calls `action_delete_key` → `delete_regular_key` (erasing `K1`'s stored nonce) followed by `action_add_key` → `add_regular_key`, which reseeds `K1`'s nonce to `initial_nonce_value(H) = (H-1)*M`, which is `< Y`.
4. The attacker resubmits the exact same signed transaction `T1` (same signature, same nonce `Y`). The nonce-freshness check (`Y > stored nonce`) now passes again because the stored nonce was reset to `(H-1)*M < Y`, and the transaction is re-applied, duplicating its effects.

Existing checks that would normally stop replay — the strictly-increasing nonce requirement — are exactly what is bypassed here, because the check compares against the *current* stored nonce, and that value was rolled backward by the reseed logic rather than forward-only as the design assumes.

### Impact Explanation
This breaks NEAR's documented nonce/replay-protection guarantee for a given signer+nonce pair, letting an attacker who controls only their own account replay a previously-applied transaction under the same key. Concrete impact depends on what the replayed transaction does but concretely enables double-execution of any once-only `FunctionCall` action (e.g., double redemption of an airdrop/faucet/staking-reward claim, double-voting, or any state transition a receiving contract assumed could only happen once per nonce) — this is a genuine double-spend/replay category impact (token inflation/loss of funds at the receiving contract, or authorization/idempotency bypass), matching the "double-spend/replay" bounty category.

### Likelihood Explanation
Preconditions are cheap and fully attacker-controlled: own account, two full-access keys, and ordinary transaction submission to a public RPC — no validator/node access needed. It requires getting the DeleteKey+AddKey transaction included at the *same block height* as the last high-value use of the target key, which is a normal, easily arranged timing (submit both transactions back-to-back; NEAR's typical SDK nonce convention of `nonce ≈ height*M` makes the vulnerable band the *common* case rather than an edge case, as the question's own dominance-failure table demonstrates for essentially the entire top band below `H*M`).

### Recommendation
Do not derive the new nonce purely from `(block_height - 1) * M`. Track the maximum nonce ever used by a public key (or account-wide monotonic counter) independent of key deletion, and seed new/recreated keys to `max(initial_nonce_value(block_height), <highest nonce previously observed for this public key/account>) `, or persist a tombstone/high-watermark for deleted keys rather than fully erasing nonce state, so a same-height (or same-band) recreation can never seed below a nonce already consumed.

### Proof of Concept
Pure Rust unit test (no runtime needed), matching the described differential/table test:
```rust
// runtime/runtime/src/access_keys.rs (inside #[cfg(test)] mod tests)
#[test]
fn initial_nonce_value_does_not_dominate_same_height_band() {
    const M: u64 = near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER;
    for h in [10u64, 1_000, 1_000_000] {
        let seed = initial_nonce_value(h); // (h-1)*M
        for k in [1u64, 1_000, 500_000, 999_999] {
            let y = h * M - k; // Y in [(h-1)*M, h*M)
            // Expected safety property: seed > y (reseed dominates every consumed value)
            // This assertion FAILS for all k tested, proving the collision class is the norm.
            assert!(seed > y, "seed {seed} does not dominate y {y} at height {h}");
        }
    }
}
```
Expected result: the assertion fails for every `(h, k)` pair in the top band below `h*M`, confirming `initial_nonce_value` does not satisfy the safety invariant when DeleteKey+AddKey occurs at the same height as prior nonce consumption. A full end-to-end confirmation would extend `runtime/runtime/src/tests/apply.rs`'s existing nonce/apply test harness to: sign+apply a tx with `K1` at nonce `Y` at height `H`; apply `[DeleteKey(K1), AddKey(K1)]` at the same height `H`; then re-apply the original signed tx and assert it is accepted (no `InvalidNonce`/`InvalidAccessKeyError`), demonstrating actual replay through the runtime.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

fn add_gas_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    gas_key_info: &GasKeyInfo,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    // For gas keys, nonce stored on access key is not used and should always be zero
    let mut access_key = access_key.clone();
    access_key.nonce = 0;
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    // Set up nonces for gas key
    let num_nonces = gas_key_info.num_nonces;
    let nonce = initial_nonce_value(block_height);
    for i in 0..num_nonces {
        set_gas_key_nonce(state_update, account_id.clone(), public_key.clone(), i, nonce);
    }

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(gas_key_storage_cost(fee_config, public_key, &access_key, num_nonces))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
