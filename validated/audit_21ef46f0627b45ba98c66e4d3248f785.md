## Analog Found

### Title
Unbacked-balance creation via floating-point precision loss and skipped invariant check in ExchangeCapsule.transaction (default/non-hardened path) - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
CVE-2018-2612 describes a high-privileged-but-limited attacker corrupting InnoDB internal state to achieve unauthorized data modification/DoS. The closest reachable analog in java-tron is the Bancor-style TRX/TRC10 `Exchange` market: any unprivileged account can create an exchange (`ExchangeCreateContract`) and trade on it (`ExchangeTransactionContract`/`ExchangeWithdrawContract`). The core balance-update routine, `ExchangeCapsule.transaction`, silently skips its own overflow/negative-balance invariant check unless a proposal-gated flag is enabled, and by default routes through a floating-point (`double`) pricing engine that is known (by the codebase's own tests) to diverge from the exact `BigInteger`/`BigDecimal` result.

### Finding Description
`ExchangeCapsule.transaction()` computes new pool balances using either the hardened `SafeExchangeProcessor` (BigDecimal + `StrictMathWrapper.addExact/subtractExact`) or the legacy `ExchangeProcessor` (raw `double` math with plain `+`/`-`), selected by the `hardenedCalc` parameter, which is fed from `AbstractExchangeActuator.allowHarden()` → `dynamicPropertiesStore.allowHardenExchangeCalculation()` — a chain-parameter flag in the same family as `allowStrictMath`/`getAllowSameTokenName`, i.e., disabled until turned on by a committee proposal: [1](#0-0) 

Critically, the post-update sanity check that balances stay non-negative is gated on the *same* flag: [2](#0-1) 

Specifically, line 160 only enforces `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` when `hardenedCalc` is true. When the flag is off (the non-hardened/legacy default state), the plain `+`/`-` arithmetic can wrap silently on `long` overflow, and the pool balance is committed to the store with **no bounds check at all**: [3](#0-2) 

The legacy `ExchangeProcessor` computes both `exchangeToSupply` and `exchangeFromSupply` via `double` arithmetic and `Maths.pow`, casting the final `double` result to `long` with truncation: [4](#0-3) 

The project's own regression test (`testStrictMath`) explicitly asserts that the legacy processor's output **differs** from the hardened/strict result for a large table of realistic inputs: [5](#0-4) 

and a dedicated hardened-mode test demonstrates that the hardened path throws `ArithmeticException` on pool states that the legacy path would silently mishandle (e.g., near-`Long.MAX_VALUE` balances): [6](#0-5) 

Because `ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` and then unconditionally debits/credits the trader's account with whatever `anotherTokenQuant` the (unsafe) processor returns: [7](#0-6) 

an attacker who repeatedly primes an exchange pool near overflow boundaries or exploits the double-precision truncation asymmetry between `exchangeToSupply`/`exchangeFromSupply` can extract more of the counter-asset than is economically backed by the pool, or drive a pool balance negative/overflowed without the transaction failing — an unbacked-balance / unauthorized-value-creation condition, analogous in class (privileged-but-bounded actor silently corrupting critical stored data) to the InnoDB CVE.

### Impact Explanation
A successful sequence lets an attacker mint value out of an Exchange pool (theft/unbacked balance) or corrupt exchange pool state (permanently frozen/inconsistent pool, denial of further trading on that market) — satisfying "unauthorized account operation / theft or permanent freezing of funds / unbacked balance" from the validation criteria.

### Likelihood Explanation
Reaching this path requires only a normal signed `ExchangeCreateContract` (to control/seed a pool, or reuse an existing pool) and `ExchangeTransactionContract`/`ExchangeWithdrawContract` calls — fully within reach of an anonymous, unprivileged wallet. The vulnerable code path (`hardenedCalc == false`) is the state of the chain until/unless the community explicitly enables `allowHardenExchangeCalculation` via a committee proposal, so it is plausible the flag is off on many/most live network configurations. Exploitation requires precise selection of pool balances and quant values to trigger truncation/overflow, which raises the bar somewhat but is a bounded, computable search rather than requiring any privileged access.

### Recommendation
Remove the `hardenedCalc &&` gate on the negative-balance check in `ExchangeCapsule.transaction` so it always applies regardless of the flag, and make `SafeExchangeProcessor` (BigDecimal-based, exact) the unconditional processor, retiring the `double`-based `ExchangeProcessor` entirely rather than keeping it as a togglable default.

### Proof of Concept
Not independently executed against a running node (out of scope for static analysis); reasoning is based on the code paths and the project's own tests (`ExchangeProcessorTest.testStrictMath`, `ExchangeTransactionActuatorTest.hardenedExecuteOverflowThrowsArithmeticException`) which already demonstrate (a) numeric divergence between the legacy and hardened processors on realistic inputs, and (b) that only the hardened path detects/rejects overflow — confirming the non-hardened default path lacks equivalent protection.

**Note on uncertainty:** I could not directly confirm via search the literal default value (0/1) of the `allowHardenExchangeCalculation` dynamic property in `DynamicPropertiesStore.java` (the getter/default-initializer text wasn't retrieved within the available search results). This assessment relies on the strong convention in this codebase that such `allowX`/hardening flags are proposal-gated and off until explicitly enabled — consistent with `allowStrictMath`, `getAllowSameTokenName`, and other `ALLOW_*` proposal parameters seen in `ProposalUtil.java`. A Devin session with full file access could confirm the exact default constant.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }
