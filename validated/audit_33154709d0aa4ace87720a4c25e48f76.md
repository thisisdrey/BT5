## Title
Stale-inventory acknowledgment for unstored StackerDB push-chunks — `handle_unsolicited_StackerDBPushChunk()` advertises a chunk version before it is actually persisted (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` validates a pushed `StackerDBPushChunkData` and, on success, patches an in-memory `StackerDBChunkInvData` reply to claim the new `slot_version` has been accepted [1](#0-0) , then sends that reply back to the pusher immediately [2](#0-1) . The chunk itself is not written to the StackerDB at this point — it is queued into `pushed_stackerdb_chunks` [3](#0-2)  and only actually persisted later, asynchronously, by `Relayer::process_stacker_db_chunks` → `StackerDBTx::try_replace_chunk` [4](#0-3) . This mirrors the reported bug class: a piece of state (the advertised/committed value) is updated based on an *intended* outcome rather than the *actual, confirmed* outcome of a later operation, creating a window where the advertised inventory diverges from what is truly stored on disk.

### Finding Description
`validate_received_chunk()` checks size, expected slot version, signature, staleness and max-writes against a snapshot of `self.stackerdbs.get_slot_versions(...)` fetched at the top of `make_StackerDBChunksInv_or_Nack` [5](#0-4)  — a live read of the on-disk table at that instant. If validation passes, the code patches the *ephemeral* `data.slot_versions` array used only for the reply message, not the DB itself [6](#0-5) , and immediately sends this `StackerDBChunkInv` back to the peer, telling it "I now have slot X at version V" [7](#0-6) .

Actual persistence happens later and separately: unsolicited push chunks are buffered in `pushed_stackerdb_chunks` [3](#0-2) , converted into `StackerDBSyncResult`s, and only written via `tx.try_replace_chunk()` inside `process_stacker_db_chunks` [4](#0-3) . `try_replace_chunk` re-validates chunk size, slot signer, staleness against `get_slot_validation`, and max-writes [8](#0-7) . Any failure other than `StaleChunk` is only logged with `warn!` and the chunk is silently dropped (`continue`) — no correction message is ever sent to the peer that was already told the chunk was accepted [9](#0-8) . Likewise, if the StackerDB was reconfigured/removed between the ack and the deferred processing, the whole batch for that contract is dropped with only a debug log [10](#0-9) .

This breaks the equality "advertised inventory == actually stored data": the pushing peer (and, transitively, any peer that queries this node's real inventory via `StackerDBGetChunkInv`, which does read the true on-disk versions via `get_slot_signer`/`get_slot_versions`) can end up with inconsistent views, but more importantly the *pusher* itself now believes replication succeeded when it may not have.

### Impact Explanation
This is a StackerDB liveness/consistency issue rather than a direct auth-bypass or memory-disclosure bug: because the true on-disk inventory (served via `StackerDBGetChunkInv`) is unaffected, a false-positive ack only misleads the single peer that receives it, causing it to believe replication of a slot is more advanced than it is. This can suppress re-pushes/re-fetches of that chunk from that peer's perspective and cause otherwise-durable signer/miner-set state (StackerDB is used for signer messages) to silently fail to replicate on this node without any error surfaced back to the network. This is at most a bounded, single-hop data-availability inconsistency (closer to "High: steering a node off tip via false inventory," but scoped only to a single StackerDB ack rather than the canonical chain tip), and does not by itself allow unauthorized writes (the eventual `try_replace_chunk` still re-checks the signer and version) nor remote code execution or memory disclosure.

### Likelihood Explanation
Triggering the mismatch requires only sending a validly-signed `StackerDBPushChunk` and then observing the ack, which is available to any remote unauthenticated peer that can push a StackerDB chunk (this is by design an operation available before p2p handshake completion is required for consumption, subject to `validate_stackerdb_push` bandwidth throttling only). No secret key or privileged role is needed. However, actually causing the deferred store to *fail* after a successful preliminary validation requires a narrow race (e.g., DB write error, config removal, or a competing chunk from a different origin overtaking the queued one before the transaction commits), so exploitation reliability is moderate, and the effect is transient/local rather than persistent falsified state.

### Recommendation
Do not construct and send the "accepted" `StackerDBChunkInv` reply based on validation alone; only advertise the new slot version after `try_replace_chunk` (or equivalent) has actually committed the chunk to the StackerDB, or explicitly follow up with a corrective NACK/inventory update if the deferred store later fails. Alternatively, perform the actual chunk write synchronously in `handle_unsolicited_StackerDBPushChunk` before replying, similar to how `StackerDBSync::validate_downloaded_chunk` is later paired with actual storage in the sync path.

### Proof of Concept
Not independently reproducible from static analysis alone; the mechanism is demonstrated by tracing the two code paths:
1. `handle_unsolicited_StackerDBPushChunk` validates and immediately replies with a patched `StackerDBChunkInvData` claiming the new version is stored [11](#0-10) .
2. The actual write occurs later and independently in `process_stacker_db_chunks`, where failures (other than `StaleChunk`) are silently dropped with only a `warn!` log and no reply to the original pusher [12](#0-11) .

I was not able to fully verify under what concrete conditions `try_replace_chunk` would fail *after* `validate_received_chunk` already succeeded (the two check sets appear largely redundant), so the exact reliability of forcing a divergent outcome is uncertain and would need dynamic testing (e.g., racing two chunk pushes or a StackerDB config removal) to confirm exploitability in practice.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }

            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
