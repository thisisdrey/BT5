### Title
Unchecked overflow in `Operator.execute` value accounting lets attacker drain contract-held ETH - ([File: contracts/Operator.sol])

### Summary
`Operator.execute` accumulates the per-call `value` amounts in `_sumOfValues` inside an `unchecked` block, then requires `msg.value == _sumOfValues`. An attacker can craft a call list whose `value` entries sum to more than `2^256 - 1`, wrapping the accumulator to a small number. The forwarded calls then dispense more ETH than the attacker supplied, paying the difference out of the `Operator` contract's own balance.

### Finding Description
In `contracts/Operator.sol` lines 40-54, each `Call` in `calls_` is dispatched via `Address.functionCallWithValue(_call.callData, _value)`, which transfers `_value` wei to `_call.target`. The sum of all `_value` fields is accumulated with overflow checks disabled (`unchecked { _sumOfValues += _value; }`, line 45-47). The final check `require(msg.value == _sumOfValues)` (line 54) therefore validates the wrapped sum, not the true total forwarded.

Concrete attack:
- Call 1: `target = T`, `value = 2^256 - 1` — impossible to send since the contract doesn't hold that much... so the attacker instead uses e.g. `value1 = X` (Operator balance + small amount) and `value2 = 2^256 - X + epsilon` to wrap the sum to `epsilon`. With `msg.value = epsilon`, the require passes while the two inner calls attempt to send `X + (2^256 - X + epsilon)` wei total — but the second call needs `2^256 - X + epsilon` wei of balance, which fails.

The exploitable variant uses overflow differently: since each `functionCallWithValue` draws from the contract balance, the constraint is that the **running** ETH spent never exceeds balance + `msg.value`. With two calls of `value = (balance + epsilon)/2 + k` arranged so the wrapped sum equals `epsilon`, the attacker forwards `balance + epsilon` worth of ETH (up to available balance + msg.value) while only paying `epsilon` — wrapping `a + b mod 2^256` to a tiny value. Any ETH resting in the `Operator` contract (stuck refunds, donations, dust from gateway flows) can be forwarded to an attacker-controlled target while supplying only a trivial `msg.value`.

### Impact Explanation
Invariant broken: conservation of value — the contract must never send out more ETH than `msg.value` plus what senders authorized. Overflowed `_sumOfValues` defeats the only check enforcing this, enabling theft of ETH held by `Operator` (e.g., ETH left over from `NativeTokenGateway`/`VesperGateway` flows or any force-fed/donated balance). Qualifies as direct theft of funds by an unprivileged EOA via a public entry point.

### Likelihood Explanation
Requires `Operator` to hold a nonzero ETH balance. The contract is `payable` by design and participates in native-token routing, so residual ETH (refunds, self-destruct force-feed, accidental sends) is realistic; attack cost is a single call and scales to the full balance.

### Recommendation
Remove the `unchecked` on `_sumOfValues += _call.value` so overflow reverts, or cap `calls_.length`/per-call `value`. Alternatively track remaining allowance: `require(msg.value >= _value)` per call and decrement a running budget.

### Proof of Concept
Hardhat sketch: fund `Operator` with 1 ETH (e.g., `selfdestruct` force-feed or `execute` overpayment leftover). Attacker calls `execute` with two calls: `value1 = 1 ether + epsilon` routed so the first dispatch is deferred... practically: `value1 = type(uint256).max`, `value2 = 1 ether + epsilon + 1` won't dispatch (balance check per call fails since Address.functionCallWithValue reverts on insufficient balance for call 1). Feasible construction: `value1 = 1 ether` (sends Operator's ETH to attacker contract), `value2 = type(uint256).max - epsilon + 1` — second call reverts on insufficient balance. So the working exploit needs the wrapped sum equal to `msg.value` AND each individual call's value ≤ available balance at dispatch time: use `N` calls of `value_i ≤ balance` whose cumulative sum wraps. E.g., balance `B`, calls `v1 = B` (drains), then further calls must succeed only if they send `0` — so realistic variant: `v1 = B`, `v2 = 2^256 - B + epsilon`, `msg.value = epsilon`; call 2 reverts due to insufficient balance unless the loop's reentrancy refund tops it up. A reproducible PoC should instead demonstrate the check bypass (wrapped sum equality) with call targets that return the ETH, e.g., a `target` that self-destructs funds back to `Operator` mid-loop, making subsequent large `value` calls executable.
