### Title
Unbounded memory allocation from attacker-controlled length field in TVM precompiled contract signature array parsing - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The helper functions `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` read an array-length value directly from attacker-supplied contract call data and immediately allocate a Java array of that size, with no upper bound check against the actual size of the input buffer or against any energy-metered limit before the allocation occurs. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`extractBytes32Array(DataWord[] words, int offset)` computes `len = words[offset].intValueSafe()` and then executes `byte[][] bytes32Array = new byte[len][];` before any validation that `len` is consistent with the amount of data actually supplied in `words`. [1](#0-0) 

`extractBytesArray` and `extractSigArray` follow the identical pattern: `len` is taken from a single 32-byte word inside the caller-supplied `data` (via `words[offset].intValueSafe()`), and a `byte[len][]` (or `byte[len][32]`/`byte[len][64]`-shaped) array is allocated immediately, with the only guard being a check that `offset` itself is within `words.length` — nothing bounds `len`. [4](#0-3) 

`DataWord.intValueSafe()` is designed to clamp/return large values (up to `Integer.MAX_VALUE`) rather than throwing, so a transaction can encode a length word such as `0x7fffffff` and the array-allocation call becomes `new byte[Integer.MAX_VALUE][]`, an allocation of roughly 8–16 GB of pointer/array overhead (and further per-element allocations inside the subsequent loop) attempted synchronously inside the JVM handling TVM execution. This is structurally identical to the reported Go `archive/tar` bug class: a length field taken from untrusted, attacker-controlled input is used to size a memory allocation with no upper bound, so a single malicious input can force unbounded memory consumption.

This code is reachable by any unprivileged account: these extraction helpers back the precompiled-contract signature/array parsing used by contracts such as `BatchValidateSign` and `ValidateMultiSign`, which are invoked by ordinary TVM `CALL`/`STATICCALL` instructions to the corresponding precompile address. Any contract deployer can write a trivial forwarding contract, and any transaction broadcaster can call it with crafted `data`, driving execution into `PrecompiledContract.execute()` for the target precompile, which in turn calls these `extract*Array` helpers on attacker-supplied `data`. [2](#0-1) 

### Impact Explanation
A crafted transaction that triggers a call into one of these precompiled contracts with a maliciously large encoded array-length word causes the java-tron node executing/validating that transaction to attempt an outsized memory allocation. This can throw `OutOfMemoryError`, destabilize or crash the JVM process (denial of service for the node), and because every full node processing the block/transaction performs the same computation, this can be replicated across the network — a node crash / halted API service class of impact, which is within the accepted impact categories (node crash or halt).

### Likelihood Explanation
Likelihood is high for any node that executes the transaction (validating nodes, SRs producing/executing blocks, and full nodes serving TVM `eth_call`/`triggerConstantContract` JSON-RPC or HTTP requests): the trigger is a single signed transaction or a single constant-call API request with crafted call data — no special privileges, staking, or witness/SR role is required. The only gating factor is that the call must reach a precompile that uses these extraction helpers with an attacker-influenced offset/length word, which is straightforward via a wrapper contract or a direct `triggerConstantContract`/`triggerSmartContract` call.

### Recommendation
Add an explicit sanity bound on `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before allocating the destination array — e.g., reject if `len` is negative, exceeds a small protocol-defined maximum (matching the actual maximum number of items the specific precompile contract can legitimately process, such as the maximum signature/spend/output counts already enforced elsewhere in this file), or if `len` is inconsistent with the remaining bytes in `data`/`words`. This mirrors the Go fix pattern of capping the size derived from an untrusted length field before performing the allocation.

### Proof of Concept
1. Deploy (or use an existing) contract that forwards call data to the `BatchValidateSign` / `ValidateMultiSign` precompiled contract address via `CALL`/`STATICCALL`.
2. Craft `data` such that the ABI-encoded array-length word at the offset consumed by `extractBytesArray`/`extractSigArray` (e.g., the signatures-array length field) is set to a very large value such as `0x000000000000000000000000000000000000000000000000000000ffffffff`.
3. Submit a `TriggerSmartContract` transaction (or call `triggerConstantContract` via the HTTP/JSON-RPC Wallet API) invoking the forwarding contract with this crafted `data`.
4. On execution, `extractBytesArray`/`extractSigArray` executes `byte[len][]` with `len` derived from the crafted word, causing the node to attempt to allocate an outsized array, resulting in `OutOfMemoryError`/severe GC pressure and potential process crash on the executing node.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
