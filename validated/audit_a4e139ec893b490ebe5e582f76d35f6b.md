### Title
Double-counted send fee for actions nested in `Delegate`/`DelegateV2` inflates `tx_cost` - ([File: runtime/runtime/src/config.rs])

### Summary
`calculate_tx_cost` computes `burnt` using `total_send_fees(actions)`, whose `Delegate`/`DelegateV2` arm recursively folds in the send fee of the *inner* actions [1](#0-0) . The same inner-action send fee is independently recomputed and added again into `gas_remaining` via `total_prepaid_send_fees` [2](#0-1) , so for a transaction whose sole action is `Delegate(FunctionCall)` the inner `FunctionCall`'s send fee is charged twice in the signer's `total_cost`.

### Finding Description
`calculate_tx_cost` builds `burnt` from `new_action_receipt` send fee plus `total_send_fees(config, sender_is_receiver, actions, receiver_id)` [3](#0-2) . For an action list `[Delegate(actions=[FunctionCall])]`, `total_send_fees` matches the `Delegate` arm, which computes `delegate_cost` (the delegate action's own send fee) **and then adds `total_send_fees` of the inner actions on top of it** — i.e. it recurses into the wrapped `FunctionCall` and folds its send fee directly into the value returned for the outer `Delegate` action [1](#0-0) . That recursive result becomes part of `burnt`, which is burnt immediately (`burnt_amount`) at transaction-to-receipt conversion time on the signer's shard [4](#0-3) .

Separately, `gas_remaining` is computed as `prepaid_gas + prepaid_send_fee.gas + receipt_cost.gas + prepaid_exec_fee.gas` [5](#0-4) , where `prepaid_send_fee = total_prepaid_send_fees(config, actions)`. For the same `Delegate(FunctionCall)` action list, `total_prepaid_send_fees`'s `Delegate` arm calls `total_send_fees` again on the very same inner actions to compute the fee that is supposedly "prepaid" for later use [6](#0-5) .

Because both `burnt` (via the recursive `Delegate` arm inside `total_send_fees`) and `gas_remaining` (via `total_prepaid_send_fees`) independently compute and add the identical inner `FunctionCall` send-fee term, `total_cost = burnt_amount + remaining_gas_amount + deposit_cost` contains that term twice: `new_action_receipt_send + delegate_send + fc_send` (in `burnt`) plus `fc_send` again (in `gas_remaining`), instead of `fc_send` appearing exactly once. This is a real arithmetic redundancy reachable purely from the shape of `total_send_fees` and `total_prepaid_send_fees` as written in this file; no signature, nonce, access-key, or size-limit check inspects this arithmetic, since those checks are orthogonal to fee-amount computation.

I was not able to fully verify, from the code available to me, whether the on-chain execution path (`apply_delegate_action` in `runtime/runtime/src/actions.rs`) actually burns this duplicated inner send fee a second time when it later constructs the receipt for the inner actions, or whether the extra gas attached via `gas_remaining` is simply refunded unspent. That distinction determines whether the impact is a permanent token loss (if the duplicate portion is truly burnt) versus merely an inflated upfront balance requirement with most of it refunded later (if the duplicate gas is never consumed and comes back through the standard unspent-gas refund). This is a limitation of the available index; a background agent with full repository/test access should trace `apply_delegate_action`'s fee-burning arithmetic to confirm which side the extra token flow lands on.

### Impact Explanation
At minimum this is a liveness/availability defect: a signer whose balance is calculated as exactly the theoretically-correct (non-doubled) `tx_cost` for `Delegate(FunctionCall)` will have their transaction rejected for insufficient balance, because `calculate_tx_cost`/`tx_cost` (used by `validate_transaction`-style balance checks) actually returns a higher `total_cost` due to the double-counted inner send fee. If the duplicated portion is genuinely burnt rather than refunded, this becomes a real, non-recoverable overcharge of user funds on every `Delegate`/`DelegateV2`-wrapped transaction, which would fall under permanent loss of user funds.

### Likelihood Explanation
The precondition is trivial and requires no privilege: any funded account can sign a `Delegate` or `DelegateV2` action wrapping a `FunctionCall` (or any other inner action) — this is a standard NEP-366 meta-transaction pattern available to any ordinary client. The defect triggers on every such transaction, deterministically, with no special contract or timing needed, making it fully repeatable.

### Recommendation
Remove the redundant computation: `total_send_fees`'s `Delegate`/`DelegateV2` arm should only account for the delegate action's own `delegate_cost` (the fee of sending the `Delegate` action itself), not recursively fold in the inner actions' send fees — those belong exclusively to `total_prepaid_send_fees`, which is the function specifically documented as computing the "prepaid" send cost of the wrapped actions. Concretely, in `total_send_fees` (`runtime/runtime/src/config.rs:141-167`), the `Delegate`/`DelegateV2` arms should evaluate to just `delegate_cost`, without the nested `total_send_fees` call over `delegate_action.get_actions()`.

### Proof of Concept
Add a unit test in `runtime/runtime/src/config.rs`'s `tests` module that:
1. Builds a `Transaction` with `actions = [Action::Delegate(SignedDelegateAction { delegate_action: DelegateAction { actions: [FunctionCallAction{...}], .. }, .. })]`.
2. Computes `tx_cost(config, &tx, gas_price)`.
3. Independently computes the expected non-doubled total: `new_action_receipt_send_fee + delegate_send_fee + fc_send_fee (burnt) + fc_exec_fee + fc_prepaid_gas + receipt_exec_fee (gas_remaining)`.
4. Asserts `tx_cost.total_cost` equals the manually computed non-doubled expectation, and additionally asserts `tx_cost.gas_burnt` does not already include `fc_send_fee` at the same time `tx_cost.gas_remaining` includes it — i.e., assert the sum of `total_send_fees(&[Delegate])` (used for `burnt`) minus `delegate_cost` is `0`, distinct from `total_prepaid_send_fees(&[Delegate])`, which should equal `fc_send_fee`. As written, the test will show `tx_cost.total_cost` exceeds the manually-summed expectation by exactly one `fc_send_fee`, confirming the double count.

pub fn total_prepaid_send_fees(
    config: &RuntimeConfig,
    actions: &[Action],
) -> Result<ParameterCost, IntegerOverflowError> {
    let mut result = ParameterCost::ZERO;
    for action in actions {
        use Action::*;
        let delta = match action {
            Delegate(signed_delegate_action) => {
                let delegate_action = &signed_delegate_action.delegate_action;
                let sender_is_receiver = delegate_action.sender_id == delegate_action.receiver_id;

                total_send_fees(
                    config,
                    sender_is_receiver,
                    &delegate_action.get_actions(),
                    &delegate_action.receiver_id,
                )?
            }
            DelegateV2(signed_delegate_action) => {
                let delegate_action =
                    VersionedDelegateActionRef::from(&signed_delegate_action.delegate_action);
                let sender_is_receiver =
                    delegate_action.sender_id() == delegate_action.receiver_id();

                total_send_fees(
                    config,
                    sender_is_receiver,
                    &delegate_action.get_actions(),
                    delegate_action.receiver_id(),
                )?
            }
            _ => ParameterCost::ZERO,
        };
        result = result.checked_add_result(delta)?;
    }
    Ok(result)
}
