### Title
Unauthenticated peers can set an arbitrary self-reported `data_url` that the node later dereferences as a trusted network endpoint, enabling SSRF against internal resources - ([File: stackslib/src/net/chat.rs])

### Summary
During P2P handshake, a remote peer supplies a free-form `data_url` string that is stored verbatim on the `ConversationP2P` and later dereferenced by multiple subsystems (StackerDB sync, general neighbor RPC) to build outbound HTTP requests. Unlike the P2P `addrbytes`/`port` fields, which are checked against the observed socket address, and unlike the mempool-sync code path, which explicitly filters private/reserved IP ranges before connecting, the `data_url` used for StackerDB replication and generic neighbor RPC has no such check. This lets any unauthenticated/unprivileged peer redirect the node's outbound HTTP traffic to an attacker-chosen host:port (localhost services, cloud metadata endpoints, internal admin APIs), which is the same bug class as CVE-2021-3779 (CWE-610, externally controlled reference to a resource in another sphere).

### Finding Description
When a handshake is processed, the peer-supplied `HandshakeData.data_url` is copied verbatim into the conversation state with no validation against the peer's actual observed address: [1](#0-0) 

Compare this to the `addrbytes`/`port` fields, which *are* checked to match the observed socket address for outbound connections: [2](#0-1) 

No equivalent check exists for `data_url`. The only sanity check applied anywhere to a URL string is `has_routable_host()`, which merely rejects the any-net addresses (`0.0.0.0`/`::`) — it does not reject loopback, link-local, or RFC1918 private ranges: [3](#0-2) 

This attacker-controlled `data_url` is then used directly to build the `PeerHost` for outbound HTTP requests and to open sockets to it, with no private/reserved-range filtering: [4](#0-3) 

This `NeighborRPC`/`RPC` machinery (`net/neighbors/rpc.rs`) is exactly what `StackerDBSync` (in `net/stackerdb/sync.rs`) uses to fetch chunk inventories and chunk data from "qualified replicas." Although `find_qualified_replicas` filters candidate `NeighborAddress`es by `is_in_private_range()` on the P2P `addrbytes`: [5](#0-4) 

...this filtering is applied to the P2P handshake address, not to the HTTP `data_url` that is actually dereferenced when the request is sent. An attacker can pass the P2P-address private-range filter with a legitimate public P2P endpoint, while still supplying an arbitrary/private `data_url` in the handshake, because `get_peer_host`/`send_request` in `neighbors/rpc.rs` blindly trust `convo.data_url`.

By contrast, `mempool_sync_send_query` in the (in-scope) `net/mempool/mod.rs` explicitly guards against exactly this scenario before connecting to a peer-derived URL: [6](#0-5) 

This shows the security invariant that should hold everywhere a peer-supplied `data_url` is dereferenced ("do not connect to private/local addresses unless explicitly configured to"), but it is inconsistently enforced — it is missing from the generic `NeighborRPC` path used by StackerDB sync.

### Impact Explanation
Any remote peer that can complete a normal, unprivileged P2P handshake (no signer key, no admin role, no StackerDB slot ownership required) can set `data_url` to point at an internal-only resource reachable from the victim node's host (e.g., a loopback service, an internal management API, or a cloud metadata endpoint). The node will then autonomously issue outbound HTTP GET/POST requests to that destination whenever it performs StackerDB replica synchronization. This is a Server-Side Request Forgery: the victim node acts as a confused deputy, using its own network position/trust to reach resources the attacker cannot reach directly. Depending on the internal target, this can result in unauthorized reads (credential/metadata disclosure) or unauthorized state-changing requests against internal-only services — squarely in the spirit of "unauthenticated/unauthorized write to state" and "memory/credential disclosure" impact categories.

### Likelihood Explanation
Likelihood is high: setting an arbitrary `data_url` requires nothing beyond completing a standard handshake, which any peer can already do. No cryptographic proof of the URL's ownership or reachability is required, and StackerDB sync runs continuously and automatically for any configured StackerDB contract, giving the attacker many chances to be selected as a "qualified replica" and have their `data_url` dereferenced.

### Recommendation
Apply the same private/reserved-range gating used in `net/mempool/mod.rs::mempool_sync_send_query` to every code path that dereferences a peer-supplied `data_url`, in particular `net/neighbors/rpc.rs::get_peer_host`/`send_request` (used by `StackerDBSync`). Concretely: before calling `connect_http`, resolve the URL's host and reject connections to private/loopback/link-local/reserved addresses unless `connection_opts.private_neighbors` is explicitly set, mirroring the existing mempool-sync check. Consider centralizing this check in `UrlString`/`PeerHost` construction so it cannot be bypassed by new callers.

### Proof of Concept
1. Attacker runs a Stacks node (or lightweight P2P client) with a public, routable P2P `addrbytes`/`port` so it passes `find_qualified_replicas`'s private-range filter, but sets `HandshakeData.data_url` to `http://127.0.0.1:6379/` (or any internal service address reachable from the victim, e.g. a cloud metadata IP).
2. Complete the handshake with the victim node; `update_from_handshake_data` stores this `data_url` unmodified on the conversation (`stackslib/src/net/chat.rs:1147`).
3. Register/announce this node as a replica for a StackerDB contract the victim is configured to sync (or wait for the victim's `find_qualified_replicas` to select it based on `PeerDB` records).
4. When `StackerDBSync` performs its next sync round, it uses `NeighborRPC`/`RPC::send_request` (`stackslib/src/net/neighbors/rpc.rs`), which calls `PeerHost::try_from_url(&convo.data_url)` and connects to `127.0.0.1:6379` (or the internal target) from the victim's own network position, issuing an HTTP request the attacker fully controls the destination of.

Note: I was not able to fully trace every downstream consumer of `NeighborRPC`/`RPC` beyond `stackerdb/sync.rs` within the tool-call budget (e.g., whether other in-scope callers add their own private-range guard before invoking `send_request`), so it is possible some call sites add an additional check I did not locate. However, `neighbors/rpc.rs` itself — the shared primitive — contains no such guard, which is the root-cause site cited above.

    /// Is this URL routable?
    /// i.e. is the host _not_ 0.0.0.0 or ::?
    pub fn has_routable_host(&self) -> bool {
        let url = match url::Url::parse(&self.to_string()) {
            Ok(x) => x,
            Err(_) => {
                // should be unreachable
                return false;
            }
        };
        match url.host_str() {
            Some(host_str) => {
                if host_str == "0.0.0.0" || host_str == "[::]" || host_str == "::" {
                    return false;
                } else {
                    return true;
                }
            }
            None => {
                return false;
            }
        }
    }
