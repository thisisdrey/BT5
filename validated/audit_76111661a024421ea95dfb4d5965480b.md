### Title
Unprivileged dust transfers fill a victim's `MAX_TOKENS_PER_USER` slots, permanently reverting their deposits/mints and blocking collateral top-ups to avoid liquidation - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to CVE-2017-16818 (an authenticated low-privilege user posts crafted input that trips an assertion and causes denial of service), any EOA can force a victim's account in a Metronome `Pool` into a state where every `DepositToken` deposit, `DepositToken.transfer` receipt, `DebtToken.issue`/`mint`, leverage, and `SmartFarmingManager` operation that would register a *new* token reverts with `UserReachedMaxTokens`. The attacker only needs to send dust (1 wei) of each enabled `DepositToken`/`DebtToken` to the victim; no privileged role is required.

### Finding Description
`Pool` maintains per-account enumerable sets `depositTokensOfAccount` and `debtTokensOfAccount`, capped by `MAX_TOKENS_PER_USER = 30` (`Pool.sol:79`). Registration is push-based and attacker-controlled:

- `DepositToken` calls `pool.addToDepositTokensOfAccount(to)` whenever a recipient's balance goes `0 → >0`, i.e. on `deposit(..., onBehalfOf_)`, `transfer`, `transferFrom`, and liquidation `seize`.
- `DebtToken._mint` calls `pool.addToDebtTokensOfAccount(account_)` when balance goes `0 → >0` (`DebtToken.sol:597-600`).
- Both pool functions enforce the cap via `onlyIfAdditionWillNotReachMaxTokens`, which reverts once `debt + deposit` slots reach 30 (`Pool.sol:143-148, 204-220`).

Attack path (all public, unprivileged):
1. Attacker deposits dust into every enabled `DepositToken` (or mints dust debt positions in every enabled `DebtToken`) from their own account.
2. Attacker `transfer`s 1 wei of each deposit token to the victim (or repays/`issue`s dust debt to them if a path exists). Each transfer triggers `addToDepositTokensOfAccount(victim)`.
3. Once the victim's combined list hits 30 entries, every subsequent action that would add a *new* token to the victim reverts with `UserReachedMaxTokens`:
   - `depositToken.deposit(amount, victim)` reverts → victim cannot add a *new* collateral type.
   - `debtToken.issue`/`mint` for a synth the victim doesn't already hold reverts → victim cannot open new debt.
   - `SmartFarmingManager.leverage` and `NativeTokenGateway`/`VesperGateway` deposit routes revert when they mint a token the victim lacks.
   - Anyone sending the victim a deposit token they don't hold reverts.

The critical consequence: a victim whose position is approaching the liquidation threshold and who needs to deposit a *different* collateral type to restore health is blocked — their rescue transaction reverts, so the position becomes liquidatable and is seized. Like the CVE, a low-privilege requester supplies input that the protocol asserts on, turning it into a liveness failure.

No guard prevents this: `whenNotPaused`/`nonReentrant` don't apply, there is no opt-in for receiving positions, the cap counts the two sets jointly, and SynthContext/`_msgSender` resolution faithfully attributes the push to the token contracts.

### Impact Explanation
An unprivileged attacker can (a) DoS all "new token" operations for a targeted account, and (b) combine the griefing with market movement to prevent collateral top-ups, forcing otherwise-avoidable liquidations and loss of the victim's collateral via `DepositToken.seize`. Cleanup is possible (the victim must transfer each dust token back out to shrink its list), but requires the victim to discover the issue and spend gas per token — during which the account is bricked for new positions.

### Likelihood Explanation
The attack is cheap: dust deposits/transfers of already-held tokens. It requires the pool to have enough enabled deposit+debt tokens for the attacker to fill 30 slots; pools with ≥30 offerings are fully vulnerable to permanent griefing, and pools with fewer still let an attacker consume the remaining headroom so legitimate users hit the cap sooner. Front-running a victim's pending deposit transaction makes it reliably revert.

### Recommendation
- Make list registration pull/lazy: don't add tokens on passive receipt — only register on explicit user actions (`deposit` for self, `issue` initiated by the account), or let `addTo*TokensOfAccount` silently skip instead of reverting when the cap is hit and fall back to iterating only registered tokens for health checks while still crediting balances.
- Alternatively, remove the `onlyIfAdditionWillNotReachMaxTokens` revert for unsolicited inbound transfers (e.g., track "actively used" tokens only), so dust cannot exhaust the cap.

### Proof of Concept
```ts
// Hardhat, fork of a chain where `pool` has >= N enabled DepositTokens.
// attacker = EOA, victim = target account.
const tokens: DepositToken[] = [...] // all deposit tokens enabled in pool
for (const dt of tokens.slice(0, 30)) {
  const amount = await smallestUnit(dt)            // 1 wei / 1 unit
  await underlying(dt).approve(dt.address, amount)
  await dt.connect(attacker).deposit(amount, attacker.address)
  await dt.connect(attacker).transfer(victim.address, 1) // adds dt to victim's set
}
// victim now has 30 registered tokens
await expect(
  newDepositToken.connect(victim).deposit(parseUnits('1000', 6), victim.address)
).revertedWithCustomError(pool, 'UserReachedMaxTokens')
// Likewise victim's `debtToken.issue(...)` for a synth they don't hold reverts,
// so they cannot mint debt or add new collateral to escape liquidation.
```
The revert propagates out of `DepositToken.deposit`/`_transfer` because the token unconditionally calls `Pool.addToDepositTokensOfAccount`, which reverts inside `onlyIfAdditionWillNotReachMaxTokens` (`Pool.sol:143-148, 216-220`). [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
