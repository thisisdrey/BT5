### Title
Attached NEAR deposit is permanently lost in `address_check_callback`'s early-return branches - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
`CallerDeposit::new` records a refundable deposit whenever `predecessor_account_id != current_account_id`, and `inner_rlp_execute` threads that `CallerDeposit` through the `EOABaseTokenTransfer{address_check: Some(_)}` path via `address_registrar.lookup(...).then(address_check_callback(...))`. Two of the three code paths inside `address_check_callback` return an `ExecuteResponse::Value` directly and simply drop the `caller_deposit` parameter without issuing any refund or forwarding transfer, permanently stranding the attached yoctoNear in the wallet contract's balance.

### Finding Description
An unprivileged NEAR account acting as a "relayer" calls `rlp_execute` (`lib.rs` `WalletContract::rlp_execute`, lines 88-128) on some target eth-implicit wallet contract, attaching a nonzero `attached_deposit`. Because `predecessor_account_id != current_account_id`, `CallerDeposit::new` (`types.rs` lines 180-192) returns `Some(CallerDeposit{account_id: predecessor, yocto_near})`, intended to be refundable if the subsequent cross-contract action fails.

If the parsed transaction resolves to `TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer{address_check: Some(address), ..})` (reachable via `internal::parse_rlp_tx_to_action`/`parse_tx_data` whenever `target` is another eth-implicit account, e.g. unparsable calldata or a `SelfNearNativeAction` sent to a different wallet — `internal.rs` lines 83-122), `inner_rlp_execute` (`lib.rs` lines 412-432) builds a promise chain: `address_registrar.lookup(address).then(ext.address_check_callback(target, action, caller_deposit))`. The nonce is intentionally *not* incremented for this branch (`lib.rs` lines 358-365), and `caller_deposit` is carried into the callback as an argument, not yet spent.

Inside `address_check_callback` (`lib.rs` lines 134-192):
- If the registrar `lookup` promise fails (`PromiseResult::Failed`, lines 141-148), the function returns `PromiseOrValue::Value(ExecuteResponse{success:false, ...})` immediately. `caller_deposit` is simply dropped — no refund promise is created.
- If `maybe_account_id.is_some()` (the address is already registered to a named account) and `env::signer_account_id() != current_account_id` (the normal case for a third-party relayer, i.e. not a self-signed owner transaction), the function again returns `PromiseOrValue::Value(ExecuteResponse{success:false, error: Some("Invalid target...")})` (lines 165-173), again dropping `caller_deposit` without any refund.

Only the third branch (`maybe_account_id.is_none()`) forwards `caller_deposit` onward to `rlp_execute_callback`, which is the *only* place that actually implements the refund logic (`lib.rs` lines 296-312). Both of the other two branches bypass that refund logic entirely.

An attacker with full control over the transaction inputs (target account, RLP calldata, and attached deposit) can deterministically hit either dropped-deposit branch: e.g., choose `target` to be an address already registered in the address registrar (forcing `maybe_account_id.is_some()`), guaranteeing the "Invalid target" branch fires and the deposit is stranded, since the check `env::signer_account_id() == current_account_id` will be false for an ordinary third-party relayer call. No signature, nonce, or access-key check blocks this — `validate_tx_relayer_data` only validates the Ethereum-side signature/nonce/gas fields of the emulated tx, not the Near-level deposit handling in the callback.

### Impact Explanation
The yoctoNear attached to `rlp_execute` becomes permanently locked in the wallet contract's account balance: it is not delivered to any receiver action, not refunded to the relayer/caller who attached it, and not reachable by the wallet owner through any subsequent call (the transaction ends with a plain `ExecuteResponse::Value`, no promise references the funds again). This is a permanent freezing of user/relayer funds, falling under the "permanent freezing of funds" bounty category. The amount lost per call is bounded by whatever the relayer chooses to attach, and the bug is repeatable indefinitely against any wallet-contract instance.

### Likelihood Explanation
The precondition is trivial and fully attacker-controlled: any NEAR account can call `rlp_execute` on any eth-implicit wallet contract, attach a deposit, and select a `target`/calldata combination that routes into the `EOABaseTokenTransfer{address_check: Some(_)}` path. Forcing the "existing named account" branch only requires choosing a target address already present in the address registrar (a public, low-cost lookup), or alternatively engineering/waiting for the registrar `lookup` cross-contract call to fail. No special privileges, access keys, or validator/node access are required, and the loss is deterministic and repeatable. The only self-limiting factor is that the attacker/relayer must be the one funding the deposit, so financially the direct victim is typically the relayer itself (or an honest relayer duped by a malicious/unregistered flow) — but this is still an unconditional value-conservation break reachable by an ordinary client.

### Recommendation
In `address_check_callback` (`lib.rs`), issue a refund `Promise::promise_batch_create`/`promise_batch_action_transfer` to `caller_deposit.account_id` for `caller_deposit.yocto_near` in both early-return branches (the registrar `lookup` failure branch and the "Invalid target: existing named account" branch) before returning `ExecuteResponse::Value`, mirroring the refund logic already present in `rlp_execute_callback`.

### Proof of Concept
Integration test (extending `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/relayer.rs` or `emulation.rs` style tests) plan:
1. Deploy a `WalletContract` instance for an eth-implicit account plus a mock `AddressRegistrar` contract at `ADDRESS_REGISTRAR_ACCOUNT_ID`.
2. Fund a distinct relayer account `R` with NEAR.
3. Craft an RLP-encoded Ethereum transaction whose `to` matches another eth-implicit account `target` (different from the wallet's own address), with calldata that is unparsable/self-transfer-like so `parse_rlp_tx_to_action` yields `EOABaseTokenTransfer{address_check: Some(address), ..}`.
4. Register `target`'s address in the mock registrar so `lookup` returns `Some(existing_account_id)` (or alternatively configure the mock registrar to panic/fail on `lookup`).
5. From account `R`, call `rlp_execute(target, tx_bytes_b64)` attaching a specific `deposit_amount` (e.g. 1 NEAR).
6. Resolve the promise chain in the test runtime (`lookup` → `address_check_callback`).
7. Assert: `ExecuteResponse.success == false`; account `R`'s balance decreased by exactly `deposit_amount` (plus gas); no receipt was created transferring `deposit_amount` back to `R`; and the wallet contract's account balance increased by `deposit_amount` with no code path left to reclaim it (confirmed by inspecting `WalletContract` state/subsequent calls showing the funds are unaccounted for).
