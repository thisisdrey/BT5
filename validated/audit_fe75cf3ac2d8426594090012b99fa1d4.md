### Title
Deleting and re-adding a FunctionCall access key resets its nonce floor to `initial_nonce_value(block_height)`, enabling replay of previously-consumed nonces and double-spend of the key's allowance/balance - (File: `runtime/runtime/src/access_keys.rs`, `runtime/runtime/src/verifier.rs`)

### Summary
`add_regular_key` unconditionally sets `access_key.nonce = initial_nonce_value(block_height)` whenever a public key is (re-)added, with no memory of nonces already consumed by a prior incarnation of that same public key. If a FunctionCall key is exhausted, deleted, and re-added at (or effectively within) the same nonce-range window, a previously-executed `SignedTransaction` whose nonce lies between the new floor and the old `current_nonce` passes `verify_nonce` again and is re-applied, causing `check_and_compute_new_allowance` to deduct the deposit/gas cost a second time from the freshly restored allowance and a second real balance debit.

### Finding Description
`add_regular_key` (runtime/runtime/src/access_keys.rs:230-255) resets the nonce purely from the current block height: [1](#0-0) 
`initial_nonce_value` (runtime/runtime/src/access_keys.rs:46-50) computes this floor as `(block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, with no reference to any nonce previously consumed under the same public key: [2](#0-1) 

`action_add_key` only blocks re-adding a key while it still exists (`AddKeyAlreadyExists`), so a `DeleteKeyAction` immediately followed by an `AddKeyAction` for the identical public key is fully permitted and re-runs `add_regular_key`: [3](#0-2) 

`verify_nonce` in `verify_and_charge_tx_ephemeral` validates a transaction's nonce solely against the *current* `access_key.nonce` (post re-add), with no cross-check against the account's historical high-water mark for that key: [4](#0-3) 

`check_and_compute_new_allowance` (runtime/runtime/src/verifier.rs:239-260) then deducts `total_cost` from whatever allowance is present on the *current* key state, and the balance debit happens unconditionally at lines 310-320: [5](#0-4) [6](#0-5) 

Exploit flow: the account's full-access key issues `AddKeyAction` (create FunctionCall key with allowance A at height H), several deposit-bearing `FunctionCall` transactions with nonces X1<...<Xn consuming the allowance, then `DeleteKeyAction` and `AddKeyAction` (same public key, fresh allowance A) all landing in a chunk at height H (a chunk can carry many transactions from one signer, and different access keys have independent nonce spaces, so the delete/re-add on the full-access key and the exhausting calls on the FunctionCall key can be submitted together and land in the same chunk without any network-level privilege). Because the re-add happens at the same height H, the new floor `(H-1)*MULTIPLIER` equals the original floor, which is strictly less than every previously used `Xi`. Any observer can now relay one of the already-executed signed transactions (e.g. `Xn`) — this passes `verify_nonce` again against the reset key, re-executes the deposit-bearing call, and `check_and_compute_new_allowance` deducts a second time from the fresh allowance while the real account balance is debited a second time as well.

None of the existing checks (signature, nonce-vs-current-key-nonce, allowance, storage-staking) prevent this because they are all evaluated against the *current* on-trie `AccessKey` value, which has no memory that this exact public key/nonce pair already executed a payment before deletion.

### Impact Explanation
This breaks the nonce-based replay-protection invariant and the allowance authorization-exactness invariant: a `SignedTransaction` that already executed and moved funds/executed a deposit-bearing call can be re-applied, doubling both the token debit from the signer's real balance and the allowance consumption relative to what one `AddKeyAction`'s allowance was meant to authorize. This matches the "double-spend/replay" and "theft ... of user funds" bounty categories, since the double-charge is a real NEAR balance movement, not merely a bookkeeping inconsistency.

### Likelihood Explanation
Requires: (1) control of a full-access key on the account (to perform delete+re-add of the FunctionCall key), and (2) the delete+re-add landing at the same block height as some already-executed FunctionCall transaction's nonce range — achievable by submitting all transactions to the mempool together, since a chunk commonly batches many transactions from one signer and different access keys use independent nonce spaces. No validator, node-operator, or peer privileges are needed; only ordinary transaction submission (self-attack, or an unprivileged relayer resending a previously public signed transaction after observing the key rotation). Repeatable at will by the account/key holder.

### Recommendation
Do not derive the new access key's nonce floor solely from the current block height when re-adding a public key that has previously existed on the account. Options: (a) persist a per-`(account_id, public_key)` high-water-mark (e.g., a tombstone record surviving `DeleteKeyAction`) and take `max(initial_nonce_value(block_height), tombstone_nonce)` in `add_regular_key`; or (b) forbid re-adding a public key identical to one deleted in a way that can regress the nonce floor below any nonce previously consumed for that key, by tracking a monotonic per-account nonce ceiling independent of key deletion.

### Proof of Concept
Unit/integration test in `runtime/runtime/src/access_keys.rs` (or a `test-loop-tests` runtime test) driving the flow at a fixed `block_height`:
1. `action_add_key` — create a FunctionCall key with allowance `A` at `block_height = H`.
2. Apply several `verify_and_charge_tx_ephemeral`/`FunctionCall` deposit-bearing transactions with increasing nonces `X1<...<Xn`, persisting the resulting `AccessKeyUpdate` each time, driving the allowance down close to zero; capture `Xn` and the signed transaction bytes used for it.
3. At the same `block_height = H`, call `action_delete_key` for that public key, then `action_add_key` again with the same public key and a fresh allowance `A`.
4. Re-run `verify_and_charge_tx_ephemeral` (or the full apply path) with the previously captured transaction (nonce `Xn`) against the re-added key.
5. Assert it currently succeeds (`TxVerdict::Success`), deducting `total_cost` a second time from account balance and from the freshly restored allowance — demonstrating cumulative allowance/balance debit exceeding one fresh allowance's worth, i.e. `allowance_consumed_total > A`. A fixed version should assert `TxVerdict::Failed(InvalidTxError::InvalidNonce { .. })` instead.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

        result.result = Err(ActionErrorKind::AddKeyAlreadyExists {
            account_id: account_id.to_owned(),

        }
        .into());
        return Ok(());
    }

    let fee_config = &apply_state.config.fees;

        add_gas_key(
            fee_config,

            account_id,
            &add_key.public_key,
            &add_key.access_key,
            gas_key_info,
            apply_state.block_height,
        )?;

        add_regular_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            apply_state.block_height,
        )?;
    }

    Ok(())
}

fn check_and_compute_new_allowance(
    access_key: &AccessKey,
    account_id: &AccountId,
    public_key: &PublicKey,
    total_cost: Balance,
) -> Result<Option<Balance>, InvalidTxError> {
    let Some(fc) = access_key.permission.function_call_permission() else {
        return Ok(None);
    };
    let Some(allowance) = fc.allowance else {
        return Ok(None);
    };
    let new_allowance = allowance.checked_sub(total_cost).ok_or_else(|| {
        InvalidTxError::InvalidAccessKeyError(InvalidAccessKeyError::NotEnoughAllowance {
            account_id: account_id.clone(),
            public_key: public_key.clone().into(),
            allowance,
            cost: total_cost,
        })
    })?;
    Ok(Some(new_allowance))
}
