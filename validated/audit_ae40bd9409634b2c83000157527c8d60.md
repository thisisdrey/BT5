### Title
`SlotMetadata`'s signature omits the StackerDB contract ID, allowing cross-StackerDB chunk-signature replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
The signature that authenticates a StackerDB chunk (`SlotMetadata::sign`/`verify`) is computed only over `slot_id`, `slot_version`, and `data_hash`. It never binds the signature to the specific StackerDB smart contract (`QualifiedContractIdentifier`) the chunk was written for. Because slot-signer assignment is deterministic (sorted by public-key bytes) and reused across many different `.signers-*` StackerDB contracts/reward cycles, the same signer address frequently occupies the *same* `slot_id` in multiple distinct StackerDBs. An unprivileged network peer can therefore capture a legitimately-signed, publicly-gossiped chunk from StackerDB A and replay it as a valid chunk for StackerDB B, without ever holding the signer's private key.

### Finding Description
`SlotMetadata::auth_digest()` hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

`sign()` and `verify()` operate purely over this digest, with no contract/domain separator included anywhere in the signed payload: [2](#0-1) 

The chunk-validation path (`PeerNetwork::validate_received_chunk`, used both for downloaded chunks and unsolicited pushed chunks) looks up the expected signer *per contract* via `get_slot_signer(smart_contract_id, data.slot_id)`, then calls `slot_metadata.verify(&addr)` — which, as shown above, checks nothing about which contract the signature was intended for: [3](#0-2) 

Only `slot_version` freshness and `max_writes` are checked against the *target* contract's config — there is no check that the signature was ever produced with that contract in mind: [4](#0-3) 

Signer-slot assignment is deterministic: slots are assigned by sorting signer addresses by their public-key byte order for a given `.signers-N-*` reward-cycle StackerDB contract, as seen in the `.signers` boot contract and its `stackerdb-get-signer-slots-page`: [5](#0-4) [6](#0-5) 

Because the same relative ordering of signer public keys tends to persist across reward cycles (when the signer set doesn't change dramatically) and across the sibling/rotating `.signers-0-*` / `.signers-1-*` StackerDBs, the same signer address commonly holds the same `slot_id` in more than one distinct StackerDB contract instance. This is corroborated by client-side code that computes per-cycle signer slot indices purely as a function of sorted signer-slot lists, independent of which contract instance is queried: [7](#0-6) 

Given this, an attacker who observes (via normal, public p2p StackerDB gossip) a validly-signed `StackerDBChunkData` intended for contract A slot `i` version `v` can repackage it inside a `StackerDBPushChunkData` targeting contract B (a different StackerDB where the same address also owns slot `i`), and push it through `handle_unsolicited_StackerDBPushChunk`: [8](#0-7) 

If `v` satisfies B's freshness/`max_writes` constraints, `validate_received_chunk` returns `true` even though the signer never signed anything for contract B — because the digest never encoded which contract it belonged to. The forged chunk is accepted into B's inventory and subsequently propagated onward to other peers as legitimate data for B (per the comment on `make_StackerDBChunksInv_or_Nack` broadcast logic), i.e. network-wide propagation of forged data attributed to a signer who never authorized it for that DB.

This is precisely the reNFT `RentPayload` replay bug class: a signed payload lacks a field that uniquely scopes it to its intended context (there, the order hash; here, the StackerDB contract ID), so a valid signature produced for context A can be replayed, unmodified, into context B.

### Impact Explanation
This breaks the equality "signed for contract A" vs. "accepted as authentic for contract B." Consequences:
- Forged data can be injected into and gossiped as canonical content of a StackerDB the signer did not intend to write, misattributing content to a signer's cryptographic identity.
- Depending on which StackerDB message types collide (e.g., different message-slot StackerDBs sharing the same underlying signer-slot ordering), this could let an attacker cross-post a chunk meant for one signer message type/reward-cycle into a different one, polluting downstream consumption (e.g., signer state-machine evaluation, block-response tallying) with attacker-selected, but validly-"signed", stale/foreign content.
- No private key, and no elevated network position, is required — only the ability to observe a publicly gossiped chunk and re-push it to a different StackerDB replica. This satisfies "network-wide propagation of forged data."

### Likelihood Explanation
Medium-High. Exploitability depends on finding two distinct StackerDB contracts in which the same signer address holds an identical `slot_id` and where the replayed `slot_version` also satisfies the target's freshness/`max_writes` gates. Given deterministic, pubkey-sorted slot assignment reused across `.signers-0-*`/`.signers-1-*` reward-cycle contracts (and any other StackerDB contracts using the same signer-slot assignment scheme), such collisions are not a rare coincidence but a structural property of the slot-assignment algorithm, making this practically reachable rather than purely theoretical.

### Recommendation
Include the StackerDB contract identifier (`QualifiedContractIdentifier`) as part of the signed digest in `SlotMetadata::auth_digest()`, so that a chunk signature is cryptographically bound to the specific StackerDB it was produced for. This mirrors the recommended reNFT fix of embedding the (equivalent of an) order hash into the signed payload. This is a wire-format/protocol change and requires coordinated rollout across `libstackerdb`, `stackslib/src/net/stackerdb/**`, and signer client code that builds/signs chunks (e.g., `stacks-signer/src/client/stackerdb.rs`, `stacks-node/src/nakamoto_node/signer_coordinator.rs`).

### Proof of Concept
1. Identify two distinct StackerDB contracts, A and B, whose signer-slot lists (computed by the `.signers` boot contract's pubkey-sorted assignment) place the same signer address at the same `slot_id` (e.g., two different `.signers-0-*` contracts across reward cycles with a largely-overlapping signer set, or two message-type StackerDBs derived from the same underlying signer ordering).
2. Passively observe a `StackerDBChunkData` legitimately gossiped for contract A, slot `i`, version `v`, with signature `sig` (public — no secrecy on the wire).
3. Construct `StackerDBPushChunkData { contract_id: B, rc_consensus_hash: <B's current view>, chunk_data: StackerDBChunkData { slot_id: i, slot_version: v', sig, data } }`, choosing `v'` to satisfy B's freshness/`max_writes` checks (may need to reuse `v` itself, or a version B hasn't yet advanced past).
4. Send this as an unsolicited push to any peer replicating B. `handle_unsolicited_StackerDBPushChunk` → `validate_received_chunk` looks up B's slot signer for slot `i` (the same address), calls `slot_metadata.verify(&addr)`, which succeeds because the digest never referenced contract A or B.
5. The forged chunk is accepted into B and gossiped onward to B's other replicas, completing propagation of data the signer never authorized for contract B.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
