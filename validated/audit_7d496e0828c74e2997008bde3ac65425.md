### Title
Integer overflow in Exchange (TRX/TRC10 AMM pool) balance accounting allows draining exchange reserves without proportional deposit - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
Similar to the USSD report — where minting logic failed to enforce that new stablecoin issuance stays backed by deposited collateral — java-tron's on-chain Exchange (bancor-style TRX/TRC10 swap pool, created via `ExchangeCreateContract` and traded via `ExchangeTransactionContract`) fails to guarantee that swap output amounts stay backed by the pool's real reserves, because balance-limit validation and reserve-balance updates are only overflow-checked when a committee-gated "harden" flag is enabled. In the default (non-hardened) path, arithmetic uses raw `long` `+`/`-` instead of checked arithmetic, so both the pre-trade balance-limit validation and the reserve update after the trade can silently wrap around on overflow.

### Finding Description
An unprivileged account can broadcast an `ExchangeTransactionContract`/`ExchangeInjectContract` transaction. The actuator computes the counter-asset amount via `ExchangeCapsule.transaction()`, which uses either the legacy floating-point bancor processor (`ExchangeProcessor`, using `double`/`Math.pow`) or the checked `SafeExchangeProcessor`, and then updates the pool's reserve balances: [1](#0-0) 

The reserve-balance updates (`newFirstTokenBalance`/`newSecondTokenBalance`) are computed with checked `StrictMathWrapper` arithmetic **only** when `hardenedCalc` (i.e. `allowHarden()`) is true; otherwise plain `+`/`-` is used, which silently wraps on `long` overflow instead of throwing.

The `allowHarden()` gate itself is implemented in the shared actuator base class and is also used to decide whether the *validation* step's balance-limit arithmetic is checked: [2](#0-1) 

The pre-trade validation for `ExchangeTransactionContract` relies on this same `addExact` helper to check that the post-trade balance won't exceed `getExchangeBalanceLimit()`: [3](#0-2) 

Because `addExact`/`subtractExact` fall back to unchecked `x + y` / `x - y` when the harden flag is off, a large enough `tokenQuant` value (still within the individually-checked asset-balance-ownership requirement, since a user only needs to *own* that much of the sold token, not that the pool holds it) can cause `tokenBalance + tokenQuant` to overflow and wrap to a small or negative `long`, silently passing the `> balanceLimit` check that was meant to prevent this. The trade then proceeds through `ExchangeCapsule.transaction()`, updating `firstTokenBalance`/`secondTokenBalance` again using unchecked arithmetic in the non-hardened path, corrupting the pool's recorded reserves. This breaks the AMM's fundamental invariant that outputs paid to a trader must be backed by the token actually held in the pool's tracked balances — directly analogous to USSD minting stablecoins without maintaining sufficient backing collateral.

### Impact Explanation
A corrupted/overflowed reserve balance lets an attacker extract more of the counter-asset (TRX or TRC10) from the exchange pool than the pool's real backing supports, and/or drive the pool's tracked balance to unbacked/insolvent state. Subsequent legitimate traders and the pool creator (who can call `ExchangeWithdrawActuator`) then interact with corrupted state, letting the attacker or subsequent actors withdraw funds the pool does not have — an unbacked balance / theft of funds scenario reachable from a single signed transaction by any account holding enough of the sold asset.

### Likelihood Explanation
Reachable directly via a standard, unprivileged broadcast transaction (`ExchangeTransactionContract` or `ExchangeInjectContract`) against any existing exchange pool — no special permission, SR/witness role, or off-chain access required. The only precondition is that `allowHardenExchangeCalculation()` is not enabled (the flag exists specifically to opt into checked arithmetic, implying the un-checked path is/was the historical default behavior retained for backward compatibility), and that the attacker controls (or can otherwise obtain) enough of the traded asset amount to trigger `long` overflow in the balance-limit arithmetic. `getExchangeBalanceLimit()` is intended to bound this exactly, but the bound-check itself uses the vulnerable unchecked addition.

### Recommendation
Make overflow-checked arithmetic (`StrictMathWrapper`/`Math.addExact`/`subtractExact`) unconditional in `AbstractExchangeActuator.addExact/subtractExact` and in the non-hardened branch of `ExchangeCapsule.transaction()`, rather than gating correctness behind the `AllowHardenExchangeCalculation` committee proposal. Additionally, replace the floating-point `ExchangeProcessor` with the `BigDecimal`-based `SafeExchangeProcessor` unconditionally, and add an explicit post-trade invariant check verifying that no reserve balance ever goes negative or below the amount actually escrowed, independent of the harden flag.

### Proof of Concept
Conceptual (cannot be fully executed without a live network, but the code path is deterministic):
1. Attacker creates or finds an `ExchangeTransactionContract`-eligible pool with a small `firstTokenBalance`.
2. Attacker holds/owns a `tokenQuant` such that `tokenBalance + tokenQuant` (both `long`) overflows `Long.MAX_VALUE`, wrapping to a small or negative value, in `ExchangeTransactionActuator` validate step at [3](#0-2) , thereby bypassing the `getExchangeBalanceLimit()` check (which normally exists precisely to prevent overflow-scale trades).
3. `execute()` proceeds to `exchangeCapsule.transaction(...)`, which updates `firstTokenBalance`/`secondTokenBalance` via unchecked arithmetic (non-hardened path) at [4](#0-3) , corrupting the recorded reserves while the attacker's account still receives `anotherTokenQuant` computed from the (now-corrupted or under-collateralized) `Processor.exchange()` call.
4. The pool's on-chain reserve state no longer matches actual backing, permitting later withdrawal/drain of funds the pool cannot truly cover.

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }
