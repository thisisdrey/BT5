### Title
MVCC cache commit skips durable publish on hash round-trip, allowing local writes to diverge from the replicated/canonical object-storage state - ([File: internal/git/mvcc/cache.go])

### Summary
`LocalCache.Commit()` in Gitaly's MVCC (multi-version concurrency control) cache layer determines whether to publish new Git artifacts by comparing the manifest hash recorded at the *end* of a mutator RPC against the manifest hash recorded at the *start* (`baseHash`). If they match, the function returns immediately, skipping both artifact upload (`putNewArtifacts`) and the compare-and-swap that advances the canonical manifest pointer (`m.rs.Commit`). This is structurally the same bug class as CVE-2024-32644: a system derives "no state change occurred" purely from equality of a final snapshot vs. an origin snapshot, ignoring that intermediate mutations within the same request may have already had externally observable effects that are not reverted by the round-trip.

### Finding Description
`Commit()` reads the manifest hash written to the RPC's temp manifest file (`GIT_MVCC_MANIFEST_PATH`) and short-circuits when it equals `m.baseHash`: [1](#0-0) 

`baseHash`/`baseManifest` are captured once, at `prepare()` time, from the manifest pointer that existed when the mutator RPC began: [2](#0-1) 

Between `prepare()` and `Commit()`, an arbitrary number of Git invocations can run against the local MVCC-backed reftable cache (this is a mutator RPC, e.g. driven by a push/receive-pack flow, potentially spanning pre-receive/update/post-receive hooks and multiple `git` subprocess invocations, all sharing the same `GIT_MVCC_MANIFEST_PATH` environment variable). Any of those intermediate steps can write new local artifacts on disk via `createFileAtomic`/`prepareArtifacts`, and each write can advance the local manifest file to a new hash. The `Commit()` gate only ever inspects the *final* hash relative to the *initial* one; it has no visibility into whether an intermediate hash was reached, published, voted on, or otherwise consumed by another component before the local state was rewound back to the starting value.

This mirrors the Evmos root cause precisely: `stateObject.Commit()` in Evmos only persists `dirtyStorage` when it differs from `originStorage`, discarding the fact that a precompile call executed against the *intermediate* state already had durable side effects elsewhere. Here, `LocalCache.Commit()` only persists to `ObjectStorage` when the final local manifest hash differs from the RPC's starting hash, discarding the possibility that intermediate local artifacts were already relied upon (read, hard-linked, hashed into a vote, or handed to a hook) by code running earlier in the same RPC.

### Impact Explanation
If any intermediate manifest state produced mid-RPC is observed or acted upon outside of the final `Commit()` gate — for example by a hook, a nested/loopback RPC, or logic that reads `GIT_MVCC_MANIFEST_PATH` mid-flight and treats its content as durable — and the RPC subsequently drives the local manifest back to the original hash (e.g. via a rejected/rolled-back sub-operation, a compensating ref update, or repeated create/delete of the same ref within one RPC), `Commit()` will silently no-op: new artifacts already materialized locally are never uploaded via `putNewArtifacts`, and the canonical pointer in `ObjectStorage` is never advanced. This produces state inconsistency between what was locally computed/observed during the RPC and what is durably recorded, which is exactly the "improper synchronization between two state representations" pattern (CWE-1223 / analog of CWE-662) underlying the CVE.

### Likelihood Explanation
This requires a specific and non-trivial sequence: a mutator RPC that internally performs a manifest-visible mutation and then reverts it to the exact original hash before the RPC's single `Commit()` call, combined with some other component treating the intermediate state as meaningful before that point. I could not confirm, within the code reachable via `codebase_search`/`grep_search`/`read_file`, that any such intermediate-state consumer currently exists inside a single RPC's `Prepare`→`Commit` window (the manifest pointer normally isn't exposed to peers until `rs.Commit` runs). This significantly lowers confidence that the pattern is *currently* exploitable end-to-end from an ordinary push/fetch, as opposed to being a latent, structurally risky design for future extension of the MVCC cache (which per `doc/mvcc_rpc_flow.md` and its recent introduction appears to be an in-progress feature).

### Recommendation
- Track and durably record (or at least log/metric) every distinct manifest hash reached during a mutator RPC's lifetime, not just the first and last, so that a hash round-trip cannot silently discard artifacts that were computed and potentially consumed mid-RPC.
- Any component that reads `GIT_MVCC_MANIFEST_PATH` or otherwise treats an intermediate manifest as authoritative (hooks, nested RPCs, voting) should require that hash to have gone through `Commit()`'s CAS, not be trusted purely because a file on local disk changed.
- Add explicit tests exercising the "A → B → A" round-trip case within a single mutator RPC to confirm no artifacts are silently orphaned and no external consumer observed the intermediate state B without a corresponding durable publish.

### Proof of Concept
Not constructed: reaching this in production requires a concrete external consumer of the intermediate manifest state inside the `Prepare()`/`Commit()` window, which I was unable to locate in the indexed code (`internal/git/mvcc/*`, `internal/grpc/middleware/mvcc/mvcc.go`, `internal/git/gitcmd/command_factory.go`).
