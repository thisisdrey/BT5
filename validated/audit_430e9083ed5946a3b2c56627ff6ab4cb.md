### Title
Certificate revalidation is deferred to a periodic ticker instead of per-packet, allowing continued use of a stale/expired certificate's tunnel between checks - (File: connection_manager.go)

### Summary
Nebula's certificate revalidation logic mirrors the reported MaltDataLab pattern of trusting an infrequently refreshed value instead of validating freshness at the point of use. Certificate validity (`isInvalidCertificate`) is only re-checked by `connectionManager`'s ticker on a `checkInterval`/`pendingDeletionInterval` cadence, while the actual per-packet decrypt path (`ConnectionState.Decrypt`) never re-validates the peer certificate at all.

### Finding Description
The packet processing path in `outside.go` calls `hostinfo.ConnectionState.Decrypt` for every inbound message, which only performs replay-window checks and AEAD decryption — it never touches certificate validity: [1](#0-0) 

Certificate expiry/blocklist enforcement is instead delegated entirely to `connectionManager.isInvalidCertificate`, which is invoked only from `makeTrafficDecision`, itself driven by a ticking `trafficTimer` on `checkInterval`/`pendingDeletionInterval`, not on every packet: [2](#0-1) [3](#0-2) [4](#0-3) 

Even when the check fires, the tunnel is only torn down for expired/invalid certs if the operator has enabled `pki.disconnect_invalid` (`cm.intf.disconnectInvalid.Load()`); otherwise the code explicitly keeps serving traffic on an already-invalid certificate: [5](#0-4) 

This is structurally the same defect class as the MaltDataLab report: a security-relevant property (price freshness there, certificate validity here) is not checked at the point where it actually matters (auction start there, packet decrypt here) but only by a separate, periodically-ticking process. Between ticks — and indefinitely when `disconnect_invalid` is false — the data plane keeps trusting state that is already known to be stale/invalid.

### Impact Explanation
A peer whose certificate has expired, or whose certificate is later blocklisted, continues to have its data-plane traffic decrypted and accepted for up to a full `checkInterval`/`pendingDeletionInterval` window (and indefinitely if `pki.disconnect_invalid` is not enabled), because the enforcement point (`connectionManager`) is decoupled from the enforcement-relevant action (`Decrypt`/packet acceptance in `outside.go`). This allows a node with a certificate that should already be untrusted to keep communicating over the mesh, which is a state-poisoning / stale-trust-window issue rather than a purely cosmetic delay: the firewall's `match` function and other decisions consume `hostinfo.ConnectionState.peerCert` as ground truth for the connection's identity/groups even while it is stale.

### Likelihood Explanation
No attacker action or collusion is required beyond ordinary certificate expiry or a CA blocklist update; the window exists for every certificate lifecycle transition and depends solely on operator configuration (`checkInterval`, `pendingDeletionInterval`, `pki.disconnect_invalid`) and unrelated traffic timing on the tunnel (the check is deferred further while `inTraffic` keeps resetting the timer via `tryRehandshake`, not immediately closing on invalidity in this path). This is a reachable protocol-logic gap, not a hypothetical.

### Recommendation
Re-validate the cached peer certificate (via `CAPool.VerifyCachedCertificate`) inline on the packet-processing hot path (e.g., in `outside.go`'s `readOutsidePackets`/`handleOutsideMessagePacket`, or inside `ConnectionState.Decrypt`) rather than relying solely on the connection manager's periodic tick, and make `pki.disconnect_invalid`-style enforcement independent of whether the tunnel currently has active traffic keeping the pending-deletion timer reset.

### Proof of Concept
1. Establish a tunnel between A and B with `pki.disconnect_invalid: false` (or default) as in `Test_NewConnectionManagerTest_DisconnectInvalid`.
2. Let B's certificate expire (`NotAfter` passes) — confirmed to be detected only by `isInvalidCertificate` at the next `checkInterval` tick: [6](#0-5) .
3. Because `Decrypt` performs no certificate check, A continues to accept and process B's inbound messages through `outside.go`'s `readOutsidePackets` → `handleOutsideMessagePacket` for every packet until the next connection-manager tick, and indefinitely if `disconnect_invalid` remains false.

	defer clockSource.Stop()

	p := []byte("")

		select {
		case <-ctx.Done():
			return

		case now := <-clockSource.C:

			for {
				localIndex, has := cm.trafficTimer.Purge()
				if !has {
					break
				}

		}
	}

// isInvalidCertificate decides if we should destroy a tunnel.
// returns true if pki.disconnect_invalid is true and the certificate is no longer valid.
// Blocklisted certificates will skip the pki.disconnect_invalid check and return true.
func (cm *connectionManager) isInvalidCertificate(now time.Time, hostinfo *HostInfo) bool {
	remoteCert := hostinfo.GetCert()
	if remoteCert == nil {
		return false //don't tear down tunnels for handshakes in progress
	}

	caPool := cm.intf.pki.GetCAPool()
	err := caPool.VerifyCachedCertificate(now, remoteCert)
	if err == nil {
		return false //cert is still valid! yay!
	} else if err == cert.ErrBlockListed { //avoiding errors.Is for speed
		// Block listed certificates should always be disconnected
		hostinfo.logger(cm.l).Info("Remote certificate is blocked, tearing down the tunnel",
			"error", err,
			"fingerprint", remoteCert.Fingerprint,
		)
		return true
	} else if cm.intf.disconnectInvalid.Load() {
		hostinfo.logger(cm.l).Info("Remote certificate is no longer valid, tearing down the tunnel",
			"error", err,
			"fingerprint", remoteCert.Fingerprint,
		)
		return true
	} else {
		//if we reach here, the cert is no longer valid, but we're configured to keep tunnels from now-invalid certs open
		return false
	}
}
