### Title
Out-of-bounds read via unvalidated Zip64 extra-field attribute count in singlejar's `CDH`/`LH` size accessors - (File: src/tools/singlejar/zip_headers.h)

### Summary
`CDH::compressed_file_size()`, `CDH::local_header_offset()`, and the analogous `LH` accessors read 64-bit attributes from a `Zip64ExtraField` by computing an attribute index (`attr_no`) purely from which 32-bit size/offset fields in the base header equal `0xFFFFFFFF`, and then call `Zip64ExtraField::attr64(attr_no)` without ever checking that value against the extra field's own declared `attr_count()`. This mirrors the ocfs2 bug class: an attacker-controlled, disk/on-wire-encoded size field (`l_tree_depth` in ocfs2; here, the Zip64 extra field's `payload_size`/implied attribute count) is trusted to index into a fixed-shape array without validating it is large enough for the computed index, leading to an out-of-bounds read.

### Finding Description
`Zip64ExtraField::attr_count()` derives the number of valid 64-bit attributes purely from `payload_size()`: [1](#0-0) 

`ExtraField::find()` only validates that the field's *declared* size (`sizeof(ExtraField) + payload_size()`) fits within the surrounding `extra_fields` buffer — it never checks that `payload_size()` is large enough to cover the number of attributes that the caller is about to read: [2](#0-1) 

The consumers, however, compute the attribute index independently from the base header's 32-bit fields, not from the extra field's actual `attr_count()`. For example, `CDH::local_header_offset()` builds `attr_no` up to 2 based on whether `uncompressed_file_size32()` and `compressed_file_size32()` equal `0xFFFFFFFF`, then blindly calls `z64->attr64(attr_no)`: [3](#0-2) 

`CDH::compressed_file_size()` similarly picks index 0 or 1 based on `zfield_has_ext64(uncompressed_file_size32())`: [4](#0-3) 

`Zip64ExtraField::attr64()` performs no bounds check against `attr_count()`, it just indexes the flexible array member directly: [5](#0-4) 

A crafted central-directory/local-header entry can set `uncompressed_file_size32 = 0xFFFFFFFF` and `compressed_file_size32 = 0xFFFFFFFF` (requiring `attr_no` up to 2, i.e. 3 attributes / 24-byte payload) while attaching a `Zip64ExtraField` whose `payload_size` is only, e.g., 0 or 8 bytes (0 or 1 attribute). `find()` accepts this field because its own declared (small) size fits within `extra_fields`; but `attr64(2)` then reads 8 bytes at an offset the declared field never covers — a heap out-of-bounds read relative to the memory-mapped input jar buffer (`third_party/ijar` / `src/tools/singlejar` map the entire input jar file into memory and hand out pointers into it, e.g. `InputZipFile`/`AddJar` operate directly on `input_jar.mapped_start()`), potentially reading past the mapped region into adjacent memory.

This is reachable from `OutputJar::AddJar`, singlejar's core jar-merging routine, which reads `jar_entry->local_header_offset()`, `jar_entry->compressed_file_size()`, and `jar_entry->uncompressed_file_size()` directly off entries obtained by iterating an attacker-suppliable input JAR: [6](#0-5) 

Input JARs merged by singlejar during a Bazel Java build (e.g., `java_import`, downloaded via `http_jar`/`maven_install`/registry-hosted artifacts) are exactly the kind of "content a victim's build consumes" that an unprivileged, hostile origin can serve; nothing about singlejar's zip parsing verifies internal Zip64 attribute-count consistency, and there is no checksum-based rejection of malformed but well-formed-enough zip entries (checksum verification, e.g. `sha256`, only protects the archive as a whole at fetch time, not internal structural consistency of a byte-valid zip that Bazel is permitted to fetch).

### Impact Explanation
An out-of-bounds heap read during archive processing can leak adjacent process memory into visible build output (e.g. propagated size/offset values corrupting subsequent parsing, or a crash from reading unmapped memory near the end of the `mmap`'d region), and in the worst case can be leveraged as an information-disclosure primitive or, combined with further logic in `AddJar`/`WriteEntry` that uses the resulting (attacker-influenced) size to drive further `memcpy`/`WriteBytes` calls, corrupt subsequent read/copy operations. This matches the ocfs2 CVE's class of "corrupted structure size field used to index/traverse memory without validation," which was rated High/CVSS 7.8 due to local-file-corruption-triggered OOB access.

### Likelihood Explanation
Likelihood is moderate to high for any Bazel build that merges third-party JARs with `singlejar` (a default and pervasive step in Java rules) where at least one input jar originates from an untrusted or compromised source (public Maven artifact, mirror, or `http_jar`/`http_archive` URL controlled by an attacker who publishes a malicious release). Constructing a byte-valid ZIP that satisfies `ExtraField::find`'s bounds check yet has a Zip64 extra field payload smaller than the base header's 32-bit sentinel fields imply is a matter of crafting header bytes; no cryptographic bypass is needed since this is a structural/logic inconsistency, not an integrity-check bypass.

### Recommendation
Before calling `Zip64ExtraField::attr64(index)` from any `LH`/`CDH` accessor (`compressed_file_size`, `uncompressed_file_size`, `local_header_offset`), validate `index < z64->attr_count()`; if the check fails, treat the archive as malformed and abort/error out (as is already done elsewhere in `output_jar.cc` for malformed extra fields, e.g. `diag_errx(1, "malformed extra field ...")`). Apply the same validation symmetrically in `LH::compressed_file_size()` / `LH::uncompressed_file_size()`.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/tools/singlejar` unit test analogous to the existing `zip_headers_test.cc` cases can construct a `CDH` in a byte buffer with:
- `compressed_file_size32 = 0xFFFFFFFF`
- `uncompressed_file_size32 = 0xFFFFFFFF`
- `local_header_offset32 = 0xFFFFFFFF`
- an attached `Zip64ExtraField` with `payload_size = 8` (i.e., `attr_count() == 1`)

then call `cdh->local_header_offset()`, which computes `attr_no = 2` and calls `z64->attr64(2)`, reading 8 bytes past the field's declared/allocated payload — detectable under ASan as a heap-buffer-overflow read when the buffer is allocated exactly to the declared extra-field size (matching how `output_jar.cc`'s `ReserveCdh` allocates central-directory buffer space based on `entry->extra_fields_length()`).

                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
