### Title
`action_delete_account` size guard ignores Postponed/PromiseYield receipt storage, allowing accounts with large leftover trie state to bypass `DeleteAccountWithLargeState` - (`runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` computes `account_storage_usage` solely from `Account::storage_usage()` (minus contract-code size) and compares it to `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE`, but `account.storage_usage()` is never incremented when postponed action receipts or PromiseYield receipts are written under that account's name. An account can therefore accumulate large amounts of postponed-receipt trie state while its `storage_usage` field stays near zero, and successfully pass the deletion size check, leaving the bulky state permanently orphaned in the trie under the now-deleted account id.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:314-353`) computes the deletable size as: [1](#0-0) 
This value is derived only from `account_ref.storage_usage()`, i.e. the `Account` record's own `storage_usage` field.

Postponed action receipts are written via `process_action_receipt` when a receiver has unmet `input_data_ids`: [2](#0-1) 
This path calls `set(state_update, TrieKey::PendingDataCount{...}, ...)` and `set_postponed_receipt(state_update, receipt)`, both of which write directly into the trie via `set()`/`set_postponed_receipt` (`core/store/src/utils/mod.rs:120-127`), with no corresponding call to increment `account.storage_usage()` or `set_account`. The same holds for `set_promise_yield_receipt` (`core/store/src/utils/mod.rs:200-212`).

This is corroborated independently by the genesis storage-usage calculator, `StorageComputer::process_record`, which explicitly treats `StateRecord::PostponedReceipt(_)` as contributing **zero** bytes to the owning account's storage usage: [3](#0-2) 
confirming, by design, that postponed-receipt bytes are never counted against the receiver account's storage-staking/deletion accounting.

An attacker (ordinary account owner of A) can therefore:
1. Send itself (or have another account send) many `ActionReceipt`s targeting A with unmet `input_data_ids` and bulky action lists — each becomes a `PostponedReceipt` keyed by `(receiver_id=A, receipt_id)` in the trie, without ever resolving the pending data (so the receipts stay parked indefinitely).
2. Never bump A's own `Account.storage_usage` field, since these keys are written independently of the account record.
3. Call `DeleteAccount` on A. `action_delete_account` reads `account_ref.storage_usage()` (small/near-zero) and passes the `MAX_ACCOUNT_DELETION_STORAGE_USAGE` (10,000-byte) check even though tens/hundreds of KB of `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` trie entries remain keyed to A's account id, and `remove_account` (invoked at `actions.rs:371`) does not appear (from what could be verified) to purge these postponed/promise-yield entries.

### Impact Explanation
Within the narrow scope of this question, the finding is a genuine **metering-totality/liveness bug**: the storage-based blast-radius guard on `DeleteAccount` (`Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE`) does not reflect the account's actual retained trie footprint, so it cannot bound or prevent deletion of accounts carrying large postponed/PromiseYield state. This matches the described invariant violation exactly and is directly supported by code (`actions.rs:326-353`, `lib.rs:1608-1655`, `core/store/src/utils/mod.rs:120-127`, `state_applier.rs:44-76`).

By itself, this leads to orphaned/unaccounted state growth tied to a now-nonexistent account id — a storage-accounting inconsistency rather than a directly provable fund-loss, double-spend, or consensus-halting event. The prompt's "scoped impact" frames this as an enabler for a separate escalation ("clusters A/B") in which the surviving `PostponedReceipt` could later be resolved and executed after A's name is reused/recreated, potentially applying stale actions against a new account. That chained escalation was explicitly marked out of scope for this question and was not independently verified here (I could not confirm within this investigation whether `remove_account` purges postponed/PromiseYield trie entries, nor trace the full re-creation + resolution path). Absent that verified chain, the concrete, provable impact of this specific check is limited to unbounded/unmetered trie bloat rather than a directly demonstrated theft, freeze, or consensus-divergence event.

### Likelihood Explanation
Preconditions are cheap and fully attacker-controlled: an ordinary account can generate many action receipts with unsatisfied `input_data_ids` targeting itself (e.g., via cross-contract calls awaiting callbacks that are never satisfied), each carrying a large action list, at normal gas cost. No validator/node access, no leaked keys. The account's own `storage_usage` field is unaffected by this activity, so the deletion size check can be satisfied trivially and repeatably.

### Recommendation
Include the sizes of `PostponedReceipt`, `PendingDataCount`, `PostponedReceiptId`, and `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId` trie entries associated with an account in the storage-usage accounting used by `action_delete_account` (or reject deletion while any such entries exist for the account), and ensure `remove_account` purges all such entries on deletion so no state remains orphaned under a deleted account id.

### Proof of Concept
Unit test plan (in `runtime/runtime/src/actions.rs` test module, following the existing `test_delete_account_*` helpers):
1. Build a `TrieUpdate` for account `alice` with `Account::new(..., storage_usage=0 or near-zero)`.
2. Write ~50KB of `PostponedReceipt` entries via `set_postponed_receipt`/`set(TrieKey::PendingDataCount, ...)` directly (simulating what `process_action_receipt` would persist for several bulky, data-dependent action receipts targeting `alice`), without touching `account.storage_usage`.
3. Call `action_delete_account` on `alice`.
4. Assert `action_result.result` is `Ok` (no `DeleteAccountWithLargeState`), and separately assert (via `state_update`/trie inspection) that the `PostponedReceipt`/`PendingDataCount` entries for `alice` still exist in the trie after deletion, demonstrating the surviving ~50KB footprint despite successful deletion under the size guard.
