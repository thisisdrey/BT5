### Title
Active-permission holder can escalate to full Owner control via `AccountPermissionUpdateContract` if `AccountPermissionUpdateContract` is included in an Active permission's operations bitmap - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator` (the analog of Nextcloud Deck's board-resharing feature) lets the holder of any permission whose `operations` bitmap authorizes `AccountPermissionUpdateContract` rewrite the account's `Owner` permission, `Witness` permission, and all `Active` permissions in one transaction. The actuator's `checkPermission`/`validate` logic only checks that the new permission's operation bits are a subset of the chain-wide `getAvailableContractType()` set, never that the signer's *own* permission scope or threshold is respected when granting *new, broader* permissions to itself or others.

### Finding Description
`AccountPermissionUpdateContract` is executed by `AccountPermissionUpdateActuator.execute()`, which unconditionally calls `account.updatePermissions(...)` with attacker-supplied `Owner`, `Witness`, and `Active` permission structures [1](#0-0) . The only structural checks performed in `validate()`/`checkPermission()` are on key counts, weights, thresholds, name length, `parentId`, and that the `Active` permission's operation bitmap is a subset of `dynamicStore.getAvailableContractType()` [2](#0-1) . Nothing in this actuator verifies that the specific signer authorizing the transaction (identified via the transaction's `permission_id`) is limited to an authority no greater than what it already holds, nor that it cannot use its own `Active` permission to rewrite the `Owner` permission to add itself (or an accomplice) with weight sufficient to meet a lowered threshold.

Which permission is required to sign an `AccountPermissionUpdateContract` transaction is entirely determined by the *account's own configured Active-permission operations bitmap*, checked at signing/verification time via `checkPermissionOperations` / `checkWeight` in `TransactionCapsule` [3](#0-2) . By default, `AccountPermissionUpdateContract` is excluded from the default Active-permission bitmap (confirmed by the test `checkActiveDefaultOperationsCorrespondingToCode`, which explicitly skips `ContractType.AccountPermissionUpdateContract` when building the default bitmap) [4](#0-3) . However, this exclusion is only a *default* value — the account owner (or, more importantly, anyone who already controls an Owner-level or high-threshold Active-level key) can explicitly set an Active permission whose 32-byte operations bitmap includes the `AccountPermissionUpdateContract` bit, since `checkPermission()` only rejects bits that fall outside the globally valid contract-type set, not this specific bit [5](#0-4) .

Once such an Active permission exists (e.g., an account owner delegates a narrow "Active" permission intended only for token transfers or contract calls, but the operations bitmap is misconfigured/over-broad to also include `AccountPermissionUpdateContract`), any key holder satisfying that Active permission's threshold — which can be far weaker than the account's Owner threshold — can submit a new `AccountPermissionUpdateContract` that overwrites the `Owner` permission entirely, e.g., setting itself as sole Owner key with threshold 1. This is the direct analog of CVE-2020-8182: a principal holding a restricted grant (Active permission, analogous to a "shared board" access) reshares/re-grants itself broader permissions (Owner) that it was never actually entitled to hold, using the very same "share" mechanism (`AccountPermissionUpdateContract`) that was supposed to be scoped by its own limited authority.

### Impact Explanation
If an account owner (or any multisig co-signer setup) ever grants an Active permission that includes `AccountPermissionUpdateContract` in its operations bitmap — a configuration the protocol allows and does not warn against — any holder of a key in that Active permission can unilaterally seize full Owner control of the account, altering all permission sets (Owner/Witness/Active) and effectively locking out or robbing the legitimate owner(s). This is an "unauthorized account operation" resulting in permanent loss of account control and potential theft of funds (since Owner permission also generally governs top-level asset operations), matching the impact bar of concrete unauthorized account operation / theft or permanent freezing of funds.

### Likelihood Explanation
Exploitation requires that some Active permission on the target account has `AccountPermissionUpdateContract` enabled in its operations bitmap — this is not the chain default, so it requires either an intentional (but reasonable-looking) misconfiguration by the account owner when delegating multisig permissions, or a malicious co-owner setting up permissions this way for later abuse of a co-signer. This bounds likelihood to accounts with custom multisig setups where the operations bitmap for a shared/delegated Active permission is set too broadly (e.g. by copying/adjusting bitmaps without realizing bit index for `AccountPermissionUpdateContract` is included). This is a realistic operational-security pitfall given the actuator provides no warning or restriction preventing an Active permission from controlling permission management itself.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()`, unconditionally forbid the `AccountPermissionUpdateContract` bit from being set in any `Active` permission's operations bitmap, regardless of the account's chain-wide `getAvailableContractType()`, so that permission management can never be delegated to a sub-Owner authority level. Additionally, consider enforcing in `validate()`/`execute()` that the signer's `permission_id` for an `AccountPermissionUpdateContract` transaction must always be the Owner permission (`permission_id == 0`), never an Active permission, closing off any possibility of an Active-level authority rewriting Owner/Witness/Active permission structures.

### Proof of Concept
1. Account `A` has default Owner permission (threshold 1, key `A`) and an Active permission (id=2) with a custom operations bitmap that an owner has enabled to include bit for `ContractType.AccountPermissionUpdateContract`, and includes key `B` with weight meeting the Active threshold.
2. `B` submits an `AccountPermissionUpdateContract` transaction (`permission_id=2`), signed only with `B`'s key, satisfying the Active permission's threshold.
3. `TransactionCapsule.checkPermission`/`checkWeight` accept the signature because the Active permission's bitmap authorizes this contract type [6](#0-5) .
4. `AccountPermissionUpdateActuator.execute()` applies the contract's new `Owner` permission — set by `B` — replacing `A`'s Owner permission with one where `B` is the sole Owner key at threshold 1 [7](#0-6) .
5. `B` now fully owns account `A`, despite having originally only held a scoped, lower-privilege Active permission.

  public void addSign(byte[] privateKey, AccountStore accountStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = this.transaction.getRawData().getContract(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwnerAddress();
    AccountCapsule account = accountStore.get(owner);
    if (account == null) {
      throw new PermissionException("Account is not exist!");
    }
    Permission permission = account.getPermissionById(permissionId);
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    List<ByteString> approveList = new ArrayList<>();
    SignInterface cryptoEngine = SignUtils
        .fromPrivate(privateKey, CommonParameter.getInstance().isECKeyCryptoEngine());
    byte[] address = cryptoEngine.getAddress();
    if (this.transaction.getSignatureCount() > 0) {
      checkWeight(permission, this.transaction.getSignatureList(),
          this.getTransactionId().getBytes(),
          approveList);
      if (approveList.contains(ByteString.copyFrom(address))) {
        throw new PermissionException(encode58Check(address) + " had signed!");
      }
    }

    long weight = getWeight(permission, address);
    if (weight == 0) {
      throw new PermissionException(
          ByteArray.toHexString(privateKey) + "'s address is " + encode58Check(address)
              + " but it is not contained of permission.");
    }
    ByteString sig = ByteString.copyFrom(cryptoEngine.Base64toBytes(cryptoEngine
        .signHash(getTransactionId().getBytes())));
    this.transaction = this.transaction.toBuilder().addSignature(sig).build();
  }

  private static void checkPermission(int permissionId, Permission permission, Transaction.Contract contract) throws PermissionException {

        throw new PermissionException("Permission type is error");
      }

        throw new PermissionException("Permission denied");
      }
    }
  }
