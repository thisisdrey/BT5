### Title
Missing bounds check on `local_header_offset` lets a malicious ZIP/JAR overrun the mapped file in singlejar's `InputJar::LocalHeader` - (File: `src/tools/singlejar/input_jar.h`)

### Summary
`InputJar::NextEntry` validates that each Central Directory Header (`CDH`) stays inside the mmap'd archive before dereferencing it, but the companion `LocalHeader()` accessor that resolves the corresponding Local File Header (`LH`) performs **no bounds check at all** on the attacker-controlled offset it uses.

### Finding Description
`InputJar::NextEntry` explicitly checks that the next CDH record is inside the mapped file: [1](#0-0) 

But `LocalHeader()`, used to resolve the `LH*` for that same entry, computes the address directly from the CDH-supplied `local_header_offset()` (plus `preamble_size_`) and returns it with **no call to `mapped_file_.mapped(...)`**: [2](#0-1) 

`local_header_offset()` is a 32/64-bit field read straight out of the CDH record, which is fully attacker-controlled content inside a ZIP/JAR the archive can set to any value (including values pointing before `mapped_file_.start()` or past `mapped_file_.end()`). The unchecked pointer is then dereferenced by callers such as `OutputJar::AddJar`, which reads `lh->size()`, `lh->compressed_file_size()`, `lh->uncompressed_file_size()`, and computes byte counts to copy directly from this potentially out-of-bounds `LH*`: [3](#0-2) [4](#0-3) 

and by `TransientBytes::ReadEntryContents` / `DecompressEntryContents`, which read `lh->data()` for `uncompressed_file_size`/`compressed_file_size` bytes: [5](#0-4) 

This is the same bug class as the analog CVE: a structural offset embedded in otherwise-trusted, checksummed container metadata (there the journal-entry offset inside the superblock "clean" section; here the `local_header_offset` inside a CDH record) is used to index into a buffer without verifying it stays within the buffer's bounds, allowing an out-of-bounds read once dereferenced.

### Impact Explanation
An attacker who can get a victim's Bazel build to combine an attacker-supplied JAR/ZIP (e.g., a malicious `http_jar`/`http_archive` dependency, a JAR checked into an untrusted branch that CI builds, or any JAR consumed by `singlejar`'s `--sources`/deploy-jar assembly) can craft a CDH whose `local_header_offset` points outside the mmap'd input file. When `singlejar` processes it via `OutputJar::AddJar`, it dereferences the out-of-bounds `LH*` to read header fields and to compute a byte count/copy source used in `WriteBytes(input_jar.mapped_start() + copy_from, num_bytes)`, producing an out-of-bounds read (information disclosure of adjacent process memory into the output jar, and/or a crash / memory-safety violation) during a normal Bazel build action. This runs in the context of the build/action execution, not just as a data-parsing convenience, so leaked memory could end up embedded in build outputs.

### Likelihood Explanation
`singlejar` is invoked automatically by Bazel's Java rules (e.g., assembling deploy jars, merging jars for `java_binary`/`java_import`), so any dependency JAR — including ones fetched from a hostile origin, mirror, or found in an untrusted branch — is routinely fed through this exact code path with default flags on a current release. The bug requires only a crafted CDH inside an otherwise well-formed ZIP/JAR structure (the file itself can pass its outer sha256/integrity check since that check covers only the whole downloaded archive bytes, not the semantic validity of internal offset fields), making it straightforward for an unprivileged attacker publishing a dependency artifact to trigger.

### Recommendation
Add a bounds check in `InputJar::LocalHeader()` analogous to the one already performed in `NextEntry()`: verify that `mapped_file_.mapped(address)` holds for the computed LH address, and additionally verify that `address + sizeof(LH)` and the full LH record (`file_name_length + extra_fields_length` and subsequent data length) remain within `mapped_file_.end()` before returning the pointer or before any field of `LH` is read. On failure, treat this the same as other corruption cases (`diag_errx`/`diag_warnx` and abort processing of that jar) rather than silently returning an unchecked pointer.

### Proof of Concept
A JUnit-independent reproduction using the existing C++ test harness pattern in `output_jar_simple_test.cc` (which already builds crafted ZIP byte streams, see `CreateZipWithMalformedExtraField`) can be adapted: construct a ZIP with one CDH whose `local_header_offset32` is set to a very large or negative-appearing offset (e.g., `0xFFFFFFF0`, or an offset equal to `mapped_file_.size()`), leave the corresponding LH pointer's own extra-field/size subject to no forward validation, run it through `OutputJar::AddJar` (or directly call `InputJar::LocalHeader` after `NextEntry`), and observe (under ASan) an out-of-bounds read when the code dereferences `lh->size()`/`lh->compressed_file_size()`/`lh->file_name()`. This exercises the exact same missing-bounds-check pattern demonstrated by `CreateZipWithMalformedExtraField` in `src/tools/singlejar/output_jar_simple_test.cc:1179-1225`, but targeting `local_header_offset` instead of an extra-field payload size. std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
