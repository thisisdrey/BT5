### Title
Dust-transfer griefing fills a victim's `MAX_TOKENS_PER_USER` slots, blocking new deposits and debt issuance — (File: contracts/Pool.sol)

### Summary
`Pool` keeps two per-account enumerable sets (`depositTokensOfAccount`, `debtTokensOfAccount`) capped jointly at `MAX_TOKENS_PER_USER = 30`. `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes 0 → >0, and `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once the combined list length reaches 30. An unprivileged attacker can deposit dust into many `DepositToken`s and `transfer` 1 wei to a victim, permanently occupying all 30 slots. After that, any victim action that registers a *new* token — `DepositToken.deposit` into a collateral they don't already hold (via `_mint` → `addToDepositTokensOfAccount`) or `DebtToken.issue`/`SmartFarmingManager.leverage` of a new synthetic (via `addToDebtTokensOfAccount`) — reverts.

### Finding Description
- `Pool.MAX_TOKENS_PER_USER` is 30 and `onlyIfAdditionWillNotReachMaxTokens` counts `debtTokensOfAccount.length + depositTokensOfAccount.length` [1](#0-0) 
- `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` are callable only by registered tokens, but any EOA can trigger them via public `DepositToken.transfer`/`transferFrom` [2](#0-1) 
- `DepositToken._transfer` adds the token to the recipient's list with no opt-in and no minimum amount [3](#0-2) 
- `DepositToken._mint` (reached via `deposit`) calls `pool.addToDepositTokensOfAccount(account_)` on first receipt, so `deposit` reverts once the victim is at 30 [4](#0-3) 
- No pause, shutdown, reentrancy guard, or health check prevents this: transfers only require the sender's balance to be unlocked, and the attacker's dust is unlocked.

### Impact Explanation
Denial of service on the victim's account: they cannot onboard any new collateral type nor issue any new synthetic debt (including via `SmartFarmingManager.leverage`). If the victim's position later needs a *different* collateral to stay healthy, top-ups revert and the position can be liquidated — compounding DoS into real loss. The victim can free slots only by discovering the dust tokens and transferring each balance fully out; the attacker can re-fill freed slots cheaply, making this a persistent griefing war with asymmetric cost (attacker pays dust + gas; victim must enumerate and clear entries).

### Likelihood Explanation
Fully permissionless: requires only small deposits into existing `DepositToken`s and ordinary ERC20-style `transfer` calls — no privileged role, oracle manipulation, or timing. Cost scales linearly with the number of distinct deposit/debt tokens registered in the pool; effectiveness depends on the pool having ≥30 registered tokens (combined cap). On deployments with fewer than 30 tokens the attack is infeasible since the cap can't be reached — this is the main constraint.

### Recommendation
Track opt-in membership: only add to `*TokensOfAccount` on deposits/mints initiated by the account (or via an explicit `enableCollateral` toggle), not on incoming transfers — i.e., move the `addToDepositTokensOfAccount` call out of `_transfer` into `_mint`/deposit paths, or add an `accountSettings`-style allowlist. Alternatively, let anyone call `removeFromDepositTokensOfAccount(account)` for zero-balance entries, or exclude zero/de-minimis balances from counting toward `MAX_TOKENS_PER_USER`.

### Proof of Concept
Hardhat sketch (pattern matches `test/Pool.test.ts` "should revert when reach max tokens" at `test/Pool.test.ts:1386-1416`, but driven through public `transfer`):

```ts
// attacker deposits 1 wei of underlying into each DepositToken, then:
for (const dt of depositTokens) {
  await underlying.approve(dt.address, 1);
  await dt.deposit(1, attacker.address);
  await dt.transfer(victim.address, 1);   // adds dt to victim's list
}
// victim list now at 30
await expect(newDepositToken.deposit(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(newDebtToken.issue(victim.address, amount))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Note: feasibility requires the pool to expose enough registered deposit/debt tokens to reach the 30 combined cap; on pools with fewer tokens this vector does not trigger, which should be verified against the deployed configuration before reporting.
