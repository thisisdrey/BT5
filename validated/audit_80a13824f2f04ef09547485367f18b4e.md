### Title
Spend cap keyed only by `max_amount` lets unrelated origins/asset-kinds share and deplete each other's spend allowance in `fund_bounty` / `fund_child_bounty` — ([File: substrate/frame/multi-asset-bounties/src/lib.rs])

### Summary
`pallet-multi-asset-bounties::fund_bounty` enforces a per-origin spend cap using a transient `SpendContext` whose accumulator map is keyed by `max_amount` (the numeric value returned by `T::SpendOrigin::ensure_origin`) rather than by the origin's identity, track, or asset kind. Any two calls within the same dispatch context (e.g. a `utility.batch`/`batch_all`) that happen to resolve to the same `max_amount` — whether from the same origin funding different asset kinds/bounties, or from two structurally different `SpendOrigin` tracks that coincidentally return the same numeric cap — accumulate into the *same* `spend_in_context` bucket. This mirrors the referral-bonus bug class: a single shared counter is used to enforce a cap that is supposed to apply to one specific "kind" of accumulation, but silently also absorbs unrelated accumulations, causing legitimate spends to be wrongly rejected once the shared bucket is exhausted by unrelated activity.

### Finding Description [1](#0-0) 
declares `SpendContext<Balance>` with a `BTreeMap<Balance, Balance>` keyed by the spend limit value itself, not by origin identity. [2](#0-1) 
In `fund_bounty`, `max_amount` is obtained from `T::SpendOrigin::ensure_origin(origin)?`. The code then does:
```
with_context::<SpendContext<T::Balance>, _>(|v| {
    let context = v.or_default();
    let funding = context.spend_in_context.entry(max_amount).or_default();
    if funding.checked_add(&native_amount).map(|s| s > max_amount).unwrap_or(true) {
        Err(Error::<T, I>::InsufficientPermission)
    } else {
        *funding = funding.saturating_add(native_amount);
        Ok(())
    }
})
```
The intended invariant is: "the total amount spent under a given spend permission within one dispatch context must not exceed that permission's `max_amount`." The implementation instead enforces: "the total amount spent by *any* call that resolves to a numerically identical `max_amount`, regardless of which origin/track produced it, must not exceed that shared number." Because different `SpendOrigin` configurations (e.g. distinct OpenGov tracks or committee thresholds) can legitimately return identical `Balance` values as their `Success` type, and because `asset_kind`/`curator`/`bounty` are irrelevant to the key, unrelated funding operations dispatched together (via `utility.batch`, `utility.batch_all`, or any other multi-call wrapper that preserves the dispatch context) are pooled into one bucket. A user or governance process funding bounty A under origin X (cap = N) in the same batch as bounty B under an unrelated origin Y that also happens to have cap = N will have B's spend silently debited against the same allowance as A's, causing `InsufficientPermission` to trigger prematurely even though neither individual origin's true limit was exceeded.

This is the same underlying flaw class as the ULTI referral bug: a cap-enforcement counter (`claimableBonuses[]` / `spend_in_context[max_amount]`) is shared across categories that were never supposed to be commingled, so legitimate accumulation from one category is blocked or under-counted because of unrelated accumulation recorded under the same key. Existing guards (`native_amount <= max_amount` and the context-map check) only validate the numeric magnitude and never verify that the entries being summed belong to the same origin/spend authority.

### Impact Explanation
This degrades intended runtime behavior for the treasury/bounty spend-authorization path: legitimate, properly-authorized bounty funding can be wrongly rejected (`InsufficientPermission`) purely due to an unrelated concurrent spend sharing the same numeric cap, and conversely two distinct origins with the same cap value are treated as sharing one wallet of spending power instead of each having their own — a violation of the "public wrappers must not undercharge/miscompute nested execution" and "settle exactly once to the rightful beneficiary and amount" pivots. The practical severity is bounded (denial of legitimate spend rather than fund theft), matching the "Low impact / High likelihood" classification of the source referral-bonus report, since spend caps of this kind (percentage-based, threshold-based) commonly repeat identical values across tracks.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: `SpendOrigin` configurations frequently use `EnsureWithSuccess`/track-based origins whose `Success` values are round numbers (e.g. treasury tiers), making numeric collisions between unrelated origins plausible. Any governance or committee process that batches multiple `fund_bounty`/`fund_child_bounty` calls (a normal operational pattern for treasury spending) can trigger the collision without any malicious actor — an ordinary combination of legitimate spends is enough.

### Recommendation
Key `SpendContext::spend_in_context` by the origin's identity (or a stable discriminant derived from the origin/track) combined with `max_amount`, rather than by `max_amount` alone, so that unrelated origins never share an accumulator bucket. Alternatively, scope the map by `(OriginId, max_amount)` or pass an explicit `track`/origin tag from `T::SpendOrigin` into the context key.

### Proof of Concept
1. Configure two distinct `SpendOrigin` tracks/thresholds, `OriginA` and `OriginB`, whose `ensure_origin` both resolve to the same `max_amount = N` (a realistic configuration when tiers share round-number caps).
2. Submit a `utility.batch_all` containing:
   - `fund_bounty(OriginA, asset_kind_1, value = N/2, ...)`
   - `fund_bounty(OriginB, asset_kind_2, value = N/2 + 1, ...)`
3. Each call individually satisfies `native_amount <= max_amount` for its own origin.
4. Because `with_context` shares the same dispatch context across both calls in the batch, and `SpendContext::spend_in_context` is keyed only by `max_amount = N`, the second call's `native_amount` is added to the bucket already holding the first call's spend, causing `funding.checked_add(&native_amount) > max_amount` to trip and the second (fully authorized, unrelated) `fund_bounty` call to fail with `Error::InsufficientPermission`, even though `OriginB`'s own cap was never approached in isolation.
