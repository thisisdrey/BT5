### Title
Precompile signature verification cost is decoupled from the fee charged per instruction, allowing underpriced CPU work via oversized `message_data_size` - (File: precompiles/src/secp256k1.rs)

### Summary
Solana charges a fixed lamports-per-signature fee for secp256k1/ed25519/secp256r1 "precompile" instructions based solely on the declared signature `count` byte (`data[0]`), while the actual CPU cost of verification scales with the attacker-controlled `message_data_size` field that is hashed/verified per signature. This mirrors the Optimism bug class: the value used to determine compensation (signature count → fee) is decoupled from the value that determines actual resource consumption (message size → hashing/verification work), letting a user pay for "1 unit" of work while forcing the validator to perform disproportionately more.

### Finding Description
The fee for a transaction containing precompile instructions is computed purely from signature counts: [1](#0-0) 
and the per-instruction signature count used for fee/cost purposes is read directly from the first byte of the instruction's own data, which is fully attacker-controlled: [2](#0-1) 

Separately, the cost model reserves a flat, fixed `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT` compute-unit budget for a precompile instruction (independent of `message_data_size`), and the VM/CU-meter consumes **zero** CUs for precompile instructions during execution, since verification happens outside the BPF VM: [3](#0-2) 

The actual verification logic in `secp256k1::verify` recovers a slice of the message from anywhere in the transaction's instruction data using an offset and a 16-bit `message_data_size` (up to 65,535 bytes per signature-offsets entry), and hashes that entire slice with Keccak-256 before doing an ECDSA recovery: [4](#0-3) [5](#0-4) 

Neither `message_data_size` nor the size of the referenced data is charged for: the fee only counts `count` (number of `SecpSignatureOffsets` entries, i.e. `data[0]`), and the cost model's `data_bytes_cost`/`programs_execution_cost` accounting is also decoupled from this internal offset-driven read (the compute-unit reservation for a precompile instruction is fixed at `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT` regardless of the message size it will process). A user can therefore set `count = 1` (minimum fee: one signature charge and a fixed CU reservation) while setting `offsets.message_data_size` close to `u16::MAX` and pointing it at a large data blob elsewhere in the transaction (e.g., a padded memo/system instruction's data), forcing the validator to Keccak-hash up to ~64KB per verify call while paying for the cheapest possible unit of work. This is directly analogous to the Optimism finding: the value that determines payment (`count`/signature charge) is disjoint from the value that determines validator work (`message_data_size`), and the disjunction can be maximized by the attacker.

The `ed25519` and `secp256r1` precompiles follow the same offset/count/message-size structure and are subject to the same decoupling (not independently re-verified here, but architecturally identical per `PrecompileSignatureDetailsBuilder`).

### Impact Explanation
This allows underpriced pre-fee CPU work: an attacker can flood the cluster (or a leader) with many transactions, each containing minimally-charged precompile instructions (`count=1`) with maximal `message_data_size`, causing the validator to spend Keccak-256 hashing time proportional to ~64KB per instruction while paying the fee of a single 5,000-lamport signature. At scale (many transactions per block, each with multiple secp256k1/ed25519 instructions), this creates a CPU-bound DoS/QoS-evasion vector during signature verification / precompile execution, without commensurate compensation, matching the "grossly underpriced pre-fee work" acceptance criterion.

### Likelihood Explanation
Moderate-to-high likelihood: constructing such a transaction requires no privileged access — any unprivileged user can submit `secp256k1_program`/`ed25519_program` instructions with a valid signature count of 1 and carefully-set offsets referencing a large padding blob in another instruction of the same transaction. The main constraint is total transaction size (~1232 bytes for legacy packets), which limits per-transaction amplification, but the fee-per-verification-work ratio is still much worse than intended, and the pattern can be repeated across many transactions/instructions to compound validator CPU cost cheaply.

### Recommendation
Incorporate `message_data_size` (and total bytes read via signature/eth-address/message offsets) into both the fee calculation and the cost-model's compute-unit reservation for precompile instructions, rather than relying solely on the declared `count` byte. At minimum, cap or charge proportionally to the sum of `message_data_size` across all `SecpSignatureOffsets`/equivalent structures in a precompile instruction so that verification cost tracks compensation, similar to how the OP recommendation ties the L1 gas floor to `_data.length`.

### Proof of Concept
1. Construct a `secp256k1_program` instruction with `data[0] = 1` (one signature) and a single `SecpSignatureOffsets` entry whose `message_data_size = u16::MAX` (or near it) and `message_instruction_index` pointing at another instruction in the same transaction containing a large filler buffer (e.g., a memo instruction with ~64KB of dummy data, subject to overall transaction size limits, or by referencing overlapping/duplicated data across multiple precompile instructions to amplify aggregate hashed bytes across a batch of transactions).
2. Submit many such transactions (each priced at the 1-signature fee floor and the fixed builtin CU reservation as shown by `test_builtin_ix_precompiled`, [3](#0-2) ).
3. Observe that `secp256k1::verify` performs Keccak-256 hashing over the full `message_data_size` for each instruction [5](#0-4)  while the fee charged only reflects `count=1` signatures per `calculate_signature_fee` [1](#0-0) , demonstrating the underpriced CPU-work mismatch.

/// Calculate fees from signatures.
pub fn calculate_signature_fee(
    SignatureCounts {
        num_transaction_signatures,
        num_ed25519_signatures,
        num_secp256k1_signatures,
        num_secp256r1_signatures,
    }: SignatureCounts,
    lamports_per_signature: u64,
) -> u64 {
    let signature_count = num_transaction_signatures
        .saturating_add(num_ed25519_signatures)
        .saturating_add(num_secp256k1_signatures)
        .saturating_add(num_secp256r1_signatures);
    signature_count.saturating_mul(lamports_per_signature)
}
