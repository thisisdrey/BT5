### Title
Fee bypass via Nep245/Imt `TokenDiff` amount-fragmentation exploiting the `amount<=1` fee exemption - (File: `contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee` waives the protocol fee entirely on `Nep245` and `Imt` token deltas whenever the per-delta `amount` is `<= 1`. Because the fee decision is made per single `TokenDiff` intent/token entry rather than on the aggregate volume moved by an account, an unprivileged attacker can split any amount of a `Nep245`/`Imt`-typed asset into many unit (`amount == 1`) deltas across multiple `TokenDiff` intents that net to zero in the same `execute_intents`/`simulate_intents` batch, moving arbitrary value while paying zero protocol fee, whereas doing the same trade as a single delta with `amount > 1` would be charged the configured `Pips` fee.

### Finding Description
`TokenDiff::execute_intent` computes and collects the protocol fee independently for each `(token_id, delta)` pair inside a single diff, based solely on that pair's magnitude: [2](#0-1) 

The fee rate itself is zeroed out for `Nep245`/`Imt` tokens whenever the delta's absolute amount is `<= 1`: [3](#0-2) 

This exemption is intended for NFT-like, indivisible token semantics (a percentage fee on "1 unit" doesn't make economic sense for a unique item). However, `Nep245TokenId` is used far more broadly than NFTs in this codebase — it also represents fully divisible, fungible wrapped balances (e.g. one Defuse deployment's NEP-141 balance wrapped as a NEP-245 position inside another Defuse deployment, as exercised in the cross-defuse wrapping tests), where "amount" is an arbitrary fungible quantity, not an indivisible unit count. [4](#0-3) 

Because the `TokenDiff` intent settlement model works over arbitrary batches of independently signed intents whose deltas must net to zero (via `TransferMatcher`/invariant checking), an attacker fully controlling both legs of a trade (e.g., two accounts they control, or coordinating with a counterparty) can decompose a large `Nep245`/`Imt` volume transfer into `N` separate `TokenDiff` intents, each carrying a delta of magnitude `1` on the same token, and submit them together in one `execute_intents`/`simulate_intents` call. Each individual delta hits the `amount <= 1` branch of `token_fee`, so `Pips::ZERO` is applied to every leg, and the aggregate fee collected is `0`, versus `fee_ceil(total_amount)` had it been expressed as a single diff. [5](#0-4) 

### Impact Explanation
This breaks the "fees owed versus fees collected" custody binding: the protocol is configured to charge `Pips` fee on `Nep245`/`Imt` token flows above a de minimis size, but the implementation allows total evasion of that fee for any volume by fragmenting a single logical trade into many unit-sized `TokenDiff` legs within one batch. The `fee_collector` account receives strictly less than what the deployed fee configuration entitles it to, for trades on any `Nep245`/`Imt` asset that is fungible/divisible in practice (e.g. cross-Defuse wrapped balances). This matches the explicitly listed Critical impact: "fees bypassed or over-collected."

### Likelihood Explanation
Exploitation requires no privileges — any user (or pair of colluding users/self-controlled accounts) can sign and submit an arbitrary number of `TokenDiff` intents in a single `execute_intents`/`simulate_intents` call, since batches of multiple independently-signed intents are a normal, supported usage pattern (as shown throughout the `token_diff.rs` and cross-defuse NEP-245 tests). The only cost to the attacker is proportional gas/transaction overhead for `N` intents instead of `1`; for any fee rate exceeding that marginal overhead per unit, this is profitable, and profitability increases without bound as the notional value per "1 unit" of the wrapped/fungible Nep245 asset increases.

### Recommendation
Determine the fee-exemption for `Nep245`/`Imt` tokens based on the token's actual divisibility/semantics (e.g. an explicit "is this ID NFT-like" flag or a per-contract configuration) rather than solely on the instantaneous per-delta `amount` of a single intent leg. If the `amount <= 1` heuristic must be retained for genuinely indivisible tokens, ensure it cannot be used to zero-fee fragment divisible balances, for example by aggregating and charging fee on the net `Nep245`/`Imt` volume per signer/token across the whole batch rather than per individual `TokenDiff` diff entry.

### Proof of Concept
1. Configure a `Defuse` contract with a non-zero `Pips` fee and a `Nep245` token representing a fungible/divisible balance (e.g. `nep245:<other-defuse-id>:<wrapped-ft-token-id>`, as constructed in `mt_transfer_call_circullar_deposit`-style setups).
2. Attacker (account A) wants to move `1_000_000` units of this `Nep245` asset to account B (which they also control, or a cooperating counterparty), and A holds the corresponding balance.
3. Baseline: A signs one `TokenDiff` with `diff = {nep245_token: -1_000_000}` and B signs the matching `{nep245_token: +1_000_000}` closure (adjusted for fee via `TokenDiff::closure_delta`). This attracts `fee_ceil(1_000_000)` protocol fee, per `token_fee`/`Self::token_fee` returning the configured `fee` since `amount > 1`.
4. Fragmented attack: instead, A signs `1_000_000` separate `TokenDiff` intents, each `diff = {nep245_token: -1}`, and B signs `1_000_000` matching `TokenDiff` intents, each `diff = {nep245_token: +1}`. All `2_000_000` intents are submitted together in one `execute_intents`/`simulate_intents` call.
5. For every one of these `2_000_000` intent legs, `Self::token_fee` sees `amount == 1` for a `Nep245` token id and returns `Pips::ZERO` at `contracts/defuse/core/src/intents/token_diff.rs:211`, so `fee_ceil(1) == 0` is collected for every leg.
6. The batch nets to zero (satisfying the `TransferMatcher`/invariant check) and executes successfully, moving the full `1_000_000` units from A to B with `0` total protocol fee collected, versus the non-zero fee that would have been owed under step 3.

                .state
