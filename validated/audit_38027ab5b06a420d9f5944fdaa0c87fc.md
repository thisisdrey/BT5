### Title
Missing `chain_id` in `SignerCapabilityOfferProofChallengeV2` Enables Cross-Chain Replay of Signer-Capability Delegation — (`File: aptos-move/framework/aptos-framework/sources/account/account.move`)

---

### Summary

`SignerCapabilityOfferProofChallengeV2` omits the `chain_id` field that `RotationCapabilityOfferProofChallengeV2` explicitly includes to prevent cross-chain replay. A signature produced for `offer_signer_capability` on one Aptos chain (e.g., testnet, devnet, or a fork) is structurally valid on every other chain whenever the signer's sequence number matches, allowing an attacker to replay the delegation and obtain an authorized signer over a victim account on mainnet.

---

### Finding Description

`RotationCapabilityOfferProofChallengeV2` is documented as the V2 upgrade that adds `chain_id` and `source_address` specifically to prevent replay:

```move
/// This V2 struct adds the `chain_id` and `source_address` to the challenge message,
/// which prevents replaying the challenge message.
struct RotationCapabilityOfferProofChallengeV2 has drop {
    chain_id: u8,          // ← chain binding
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
``` [1](#0-0) 

`SignerCapabilityOfferProofChallengeV2`, introduced at the same time, silently omits `chain_id`:

```move
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
    // chain_id is ABSENT
}
``` [2](#0-1) 

`offer_rotation_capability` correctly constructs its challenge with `chain_id::get()`:

```move
let proof_challenge = RotationCapabilityOfferProofChallengeV2 {
    chain_id: chain_id::get(),
    sequence_number: account_resource.sequence_number,
    source_address: addr,
    recipient_address,
};
``` [3](#0-2) 

The parallel `offer_signer_capability` function constructs `SignerCapabilityOfferProofChallengeV2` without any chain binding. Because BCS-serialization of the struct does not include a chain discriminator, the same byte sequence is valid on every Aptos chain that shares the same `sequence_number` and `source_address`.

---

### Impact Explanation

`offer_signer_capability` records a `signer_capability_offer` in the victim's `Account` resource. Any account holding that offer can subsequently call `create_authorized_signer` to obtain a live `signer` for the victim's address and execute arbitrary transactions on their behalf — transferring APT, fungible assets, rotating keys, or any other privileged operation. [4](#0-3) 

This maps directly to the allowed-impact category: **unauthorized transaction execution caused by broken signature verification / chain binding**.

---

### Likelihood Explanation

The only constraint is that `sequence_number` must match across chains. This is trivially satisfied for:

- Any account whose sequence number is `0` on both chains (new accounts, the most common case).
- Any account that has executed the same number of transactions on both chains.

An attacker can:
1. Trick or observe a victim signing an `offer_signer_capability` transaction on testnet/devnet (e.g., via a dApp that targets testnet).
2. Extract the raw `account_scheme`, `account_public_key_bytes`, and `signer_capability_sig_bytes` from the submitted transaction.
3. Submit an identical `offer_signer_capability` call on mainnet while the victim's mainnet sequence number still matches.

No privileged access is required; the attacker only needs to observe a testnet transaction.

---

### Recommendation

Add `chain_id: u8` to `SignerCapabilityOfferProofChallengeV2` and populate it with `chain_id::get()` inside `offer_signer_capability`, exactly as `RotationCapabilityOfferProofChallengeV2` does. Because this changes the BCS layout of the signed message, existing off-chain signers must re-sign; coordinate a framework upgrade with a clear migration notice.

---

### Proof of Concept

1. **Testnet**: Alice (address `A`, sequence number `0`) is tricked into calling `offer_signer_capability` granting Bob (`B`) signer capability. The signed `SignerCapabilityOfferProofChallengeV2` BCS bytes are `bcs({ seq: 0, src: A, recipient: B })`.

2. **Mainnet**: Alice's mainnet account also has sequence number `0`. Bob submits the identical call to mainnet's `offer_signer_capability` with the same `account_scheme`, `account_public_key_bytes`, and `signer_capability_sig_bytes`.

3. The Move VM constructs `SignerCapabilityOfferProofChallengeV2 { sequence_number: 0, source_address: A, recipient_address: B }` — byte-for-byte identical to the testnet challenge — and the signature verifies successfully.

4. Alice's mainnet `Account` resource now has `signer_capability_offer.for = Some(B)`.

5. Bob calls `create_authorized_signer(bob_signer, A)` on mainnet and receives a valid `signer` for Alice's address, enabling arbitrary asset transfers or key rotation. [2](#0-1) [1](#0-0)
