## Title
Exchange (Bancor-style AMM) pool permanent Denial of Service via zero-balance lock - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
java-tron's `Exchange*` contract family (`ExchangeCreateContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`, `ExchangeTransactionContract`) implements a Bancor-formula AMM pool for TRX/TRC10 pairs. Just like the reported first-depositor griefing bug, once either side of an exchange's balance reaches exactly `0`, all further `Inject`, `Withdraw`, and `Transaction` operations on that `exchangeId` permanently revert, and there is no reset/recovery path in this codebase (unlike the fix described in the external report, which resets the pool when supply is 0 but staked balance is nonzero).

### Finding Description
`ExchangeCreateActuator.doValidate()` only requires `firstTokenBalance > 0 && secondTokenBalance > 0`, so any anonymous account can create an exchange pool with balances as low as `1` unit on each side: [1](#0-0) 

Trading is performed via `ExchangeCapsule.transaction()`, which applies a Bancor power-formula (`ExchangeProcessor`/`SafeExchangeProcessor`) to compute the counter-token amount and update both balances with integer arithmetic: [2](#0-1) 

With a minimal seeded pool (e.g. balances of `1`/`1`, or any small values), a single crafted `ExchangeTransactionContract` trade can drive one side of the pool down to exactly `0` due to integer truncation in the exchange math. Once that happens, every subsequent actuator that touches the pool immediately reverts:

- `ExchangeInjectActuator.doValidate()`: [3](#0-2) 
- `ExchangeWithdrawActuator.doValidate()`: [4](#0-3) 
- `ExchangeTransactionActuator.doValidate()`: [5](#0-4) 

All three throw `"Token balance in exchange is equal with 0,the exchange has been closed"` and there is no code path anywhere in `ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, or `ExchangeTransactionActuator` that resets a zero-balance pool the way the external report's "corrected" pool logic does (reset when supply is 0 but staked/remaining balance > 0). The unit tests explicitly encode this permanent-revert behavior as expected: [6](#0-5) 

### Impact Explanation
Once an exchange's balance is zero on either side, the pool is permanently bricked:
- Any remaining balance on the *other* side of the pool (deposited by the creator or subsequent `Inject` calls before the drain) becomes permanently frozen — there is no withdraw path once `firstTokenBalance == 0 || secondTokenBalance == 0`, since `ExchangeWithdrawActuator` also reverts on this condition.
- The `exchangeId` becomes permanently unusable for trading, injection, or withdrawal by anyone, including the original creator.
- This is reachable by any unprivileged account (order placer) via a normal signed `ExchangeCreateContract` + `ExchangeTransactionContract` sequence — no special privileges required.

This matches the "permanent freezing of funds" / "API the node can no longer serve" criteria: legitimate users' locked asset balances in that exchange pool become unrecoverable, and the exchange functionality for that pool is permanently denied.

### Likelihood Explanation
Any account can call `ExchangeCreateActuator` to create a minimally-funded pool (balances as small as `1`), then immediately follow up with a crafted `ExchangeTransactionContract` to drain one side to `0` via the Bancor formula's integer truncation. This requires no coordination with other users and can be done cheaply by a single account in two back-to-back transactions, closely mirroring the "malicious user... instantly depositing 1 wei" pattern in the external report.

### Recommendation
Add a reset/guard mechanism analogous to the cited fix: when a trade, injection, or a newly-created exchange would leave (or start with) `firstTokenBalance == 0 || secondTokenBalance == 0`, either reject the operation that would create the zero-balance state (e.g. enforce a minimum resulting balance greater than a floor in `ExchangeCapsule.transaction()`), or provide an explicit re-seed/reset code path (similar to `ExchangeCreateActuator`) so a pool that has decayed to zero-balance can be revived rather than being permanently unusable while still holding user funds on the non-zero side. Additionally, consider raising the minimum allowed `firstTokenBalance`/`secondTokenBalance` in `ExchangeCreateActuator.doValidate()` beyond `> 0` to make griefing via tiny seed pools economically harder.

### Proof of Concept
1. Attacker calls `ExchangeCreateContract` with `firstTokenBalance = 1`, `secondTokenBalance = 1` (passes the `> 0` check in `ExchangeCreateActuator.doValidate()`).
2. Attacker immediately calls `ExchangeTransactionContract` selling a tiny/optimal `tokenQuant` computed against `ExchangeProcessor`'s Bancor formula so that the resulting `newAnotherTokenBalance` in `ExchangeCapsule.transaction()` truncates to `0`.
3. Any subsequent call to `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, or `ExchangeTransactionActuator` for that `exchangeId` now unconditionally throws `"Token balance in exchange is equal with 0,the exchange has been closed"`, as verified by the existing test `SameTokenNameCloseTokenBalanceZero`/`SameTokenNameOpenTokenBalanceZero` in `ExchangeTransactionActuatorTest.java`, `ExchangeInjectActuatorTest.java`, and `ExchangeWithdrawActuatorTest.java`, permanently freezing any remaining balance and denying the exchange to all users.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
